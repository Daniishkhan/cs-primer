Imbalance, Thresholds & Calibration

When positives are rare, accuracy stops being informative, resampling tricks tempt you, and a model's probabilities quietly stop meaning what they say. This chapter separates what imbalance really changes from what it does not, shows how to choose an operating point from costs or capacity, and explains calibration: when a score of 0.3 should be right three times in ten, and how to make it so.

Why this matters

Fraud, disease, defaults, churn, defects, abuse: most valuable prediction problems have rare positives. Chapter 2 showed why accuracy fails there and derived the cost-minimising threshold, p > CFP / (CFP + CFN), which assumes the model's output is an honest probability. This chapter earns that assumption. Many practitioners reach for oversampling or class weights as a matter of habit and then feed the resulting scores into a cost formula that no longer applies; others report probabilities from a boosted model that are confidently wrong. You will learn which "imbalance fixes" change ranking and which only distort probabilities, how to set a threshold from cost, capacity or a recall target (and how uncertain each is), how to measure and repair calibration, and how to keep it repaired when the world changes.

What imbalance does, and what it does not

A dataset is imbalanced when one class is much rarer than the other. The rare class is usually the one you care about, called the positive class, and its share is the base rate or prevalence: 1% fraud, 0.2% default, 5% churn. Three separate problems hide under the one word, and they have different remedies.

  1. The metric problem. A model that always says "negative" is 99% accurate at a 1% base rate. Accuracy rewards ignoring the class you care about. The remedy is the choice of metric (precision-recall, average precision, cost), not any change to the data. See chapter 2.
  2. The information problem. With 1% positives, 40,000 rows contain only 400 positive examples, and that number, not 40,000, sets how much the model can learn about positives and how precisely you can estimate recall. No resampling creates information that is not there. The remedy is more positives, better features, or honesty about uncertainty.
  3. The optimisation problem. Training losses average over rows, so negatives dominate the gradient, and flexible models can reach a low loss by ignoring positives. Sometimes a model needs help seeing the minority (a tree with a minimum leaf size larger than the number of nearby positives never isolates them). This is the only part that resampling and weighting actually address.

The information problem is easy to underestimate, so measure it. Suppose you must promise "we catch 90% of fraud". You pick the threshold on a validation set that gives exactly 90% recall on its positives, and ship it. How close to 90% is the recall you will actually get? The script simulates a fixed scorer (positives and negatives each Gaussian, 1.5 standard deviations apart) and repeats the choice 300 times for validation sets of different sizes, then scores each chosen threshold on a huge fresh reference set.

"""Choosing 'the threshold that gives 90% recall' from a validation set with few positives."""
import numpy as np
rng = np.random.default_rng(17)
def draw(n_pos, n_neg):
    s = np.r_[rng.normal(1.5, 1, n_pos), rng.normal(0, 1, n_neg)]; y = np.r_[np.ones(n_pos, int), np.zeros(n_neg, int)]
    return s, y
st, yt = draw(200_000, 2_000_000)                                  # a huge reference set: the true behaviour of each threshold
print(f"{'positives in validation':>24}{'mean recall on fresh data':>27}{'5th to 95th percentile':>26}")
for n_pos in (20, 50, 200, 1000):
    rec, prec = [], []
    for _ in range(300):
        sv, yv = draw(n_pos, n_pos * 99)                              # 1% positives
        thr = np.quantile(sv[yv == 1], 0.10)                          # threshold that gives exactly 90% recall on this validation set
        flag = st >= thr
        rec.append((flag & (yt == 1)).sum() / (yt == 1).sum()); prec.append((flag & (yt == 1)).sum() / flag.sum())
    rec = np.array(rec)
    print(f"{n_pos:>24}{rec.mean():>27.3f}{np.percentile(rec, 5):>14.3f} to {np.percentile(rec, 95):.3f}")

With 20 positives in validation, the promise "90% recall" delivers 75% to 96% (the central 90% of outcomes), and on average slightly less than promised (0.864), because a threshold tuned to a small sample is itself a noisy, optimistic pick. With 1,000 positives the range narrows to 0.884 to 0.916. If your validation set has 30 positives, say what you know: the recall is "around 90%, plausibly 80% to 95%". The same arithmetic applies to every threshold-based metric on a rare class, which is why chapter 13 stratifies folds and pools out-of-fold predictions before computing them.

Four ways to train on rare positives

The common recipes are all attempts at the optimisation problem. Class weights multiply the loss on each positive row by a factor w (often the ratio of negatives to positives, the "balanced" setting), so one positive counts as w negatives. Undersampling throws away negatives until the classes are balanced or nearly. Oversampling repeats positives, and SMOTE (Chawla et al., 2002, "SMOTE: Synthetic Minority Over-sampling Technique") invents new ones by interpolating between a minority row and one of its nearest minority neighbours. Each changes what the model sees; the question is what each changes in what comes out.

The experiment trains a logistic regression on 40,000 rows with a 1.0% base rate (403 positives) and tests on 400,000. It compares plain training, balanced class weights, undersampling to 1:1, and undersampling followed by a probability correction we will derive in a moment. For each it reports ranking quality (ROC AUC, average precision), whether the probabilities are honest (their mean should equal the base rate; log loss measures it), and money: the expected cost per case at the cost-formula threshold of 0.0476 for CFN = 100 and CFP = 5 (chapter 2), and at the best threshold in hindsight.

D = 8

    return X, (rng.random(n) < sigmoid(X @ w_true - 6.4)).astype(int)

Putting the probabilities back

The distortion is predictable, which means it can be undone. Suppose undersampling keeps a fraction β of the negatives (here β = 0.0102, as 403 positives were matched with about as many negatives) and all of the positives. In the sampled data, positives are relatively β−1 times more common than in the real data. Odds scale the same way: the odds of positive in the sampled world are the real odds divided by β. Writing ps for the probability the model learned from the sample and p for the real-world probability,

ps / (1 − ps) = [p / (1 − p)] / β  ⇒  p = β ps / (β ps − ps + 1)

This is the correction in Dal Pozzolo, Caelen, Johnson and Bontempi (2015), "Calibrating Probability with Undersampling for Unbalanced Classification", and it is the last row of the table: mean 0.0091, log loss 0.0392, nearly the plain model's 0.0389, and cost at the formula threshold back to 0.647. Class weights have the same structure: a weight w on positives multiplies the odds by w, so divide the odds by w to correct. Two cautions. The correction is exact only when the model is otherwise well specified and calibrated in the sampled world, and the researchers who proposed it note that it is not suitable for all models. And you must still know the sampling rate. A cleaner alternative is not to rebalance at all unless you have a reason, and then to recalibrate on untouched data (the second half of this chapter).

Evidence from the risk-prediction literature agrees. van den Goorbergh and colleagues (2022), "The harm of class imbalance corrections for risk prediction models" (JAMIA), simulated logistic regression under no correction, random undersampling, random oversampling and SMOTE. They found the corrections did not improve discrimination (AUC) and produced poorly calibrated models that strongly overestimated the minority class probability.

Common misconception

"Imbalanced data must be balanced before training." Balancing changes the training distribution, which changes the probabilities; it does not reliably improve ranking, and for a model that is already learning the positives it adds nothing. Use it for a reason (training cost, a model that ignores positives, a library whose loss needs it), apply it inside each training fold only (chapter 14: oversampling before splitting copies validation rows into training), and undo its effect on the probabilities before they meet a threshold.

from sklearn.linear_model import LogisticRegression
from imblearn.pipeline import Pipeline            # a pipeline that resamples ONLY during fit
from imblearn.over_sampling import SMOTE
from imblearn.under_sampling import RandomUnderSampler

plain    = LogisticRegression(C=1.0)
weighted = LogisticRegression(C=1.0, class_weight="balanced")        # positives weighted ~ n_neg / n_pos
smote    = Pipeline([("smote", SMOTE(k_neighbors=5, random_state=0)), ("clf", LogisticRegression(C=1.0))])
under    = Pipeline([("under", RandomUnderSampler(random_state=0)), ("clf", LogisticRegression(C=1.0))])
# Judge all of them with the same stratified folds, average precision, AND a calibration check.

Choosing the operating point

Once the scores are honest, the model's job is to rank; the operating point (the threshold, or the number of cases to act on) is a separate decision driven by the business, and there are three principled ways to make it.

  1. By cost. Price the two errors and flag when p > CFP/(CFP + CFN) (chapter 2). It needs calibrated probabilities and trustworthy cost estimates, and it adapts automatically if costs change: only the threshold moves.
  2. By capacity. If analysts can review 2,000 cases a day, the decision is not a threshold but "act on the top k". Judge the model by the precision and recall of the top k and by lift, the precision in that group divided by the base rate.
  3. By a service promise. "Catch at least 90% of cases" or "no more than one false alarm in five" fixes recall or precision, and the threshold follows, with the sampling uncertainty shown above.

All three are read off one curve. The script takes the plain model from the experiment above and prints what happens at different review capacities.

Look at the table as a menu. Reviewing the top 0.5% of cases (2,000 of 400,000) gives precision 0.317, a lift of 33, but catches only 16.6% of the positives. Reviewing the top 5% catches 55.6% of them at precision 0.106. That is the nature of a rare event with imperfect features, and it is why the capacity plan matters more than the algorithm.

Some practical points. Whichever route you choose, tune the threshold on data the model has not seen and, with few positives, quote its uncertainty. If you use capacity, remember that the base rate in production can drift, so "the top 2%" is a moving quantity worth monitoring. If you use a threshold, recheck it when costs, base rate or the model change. scikit-learn (1.5 and later) offers TunedThresholdClassifierCV, which picks a threshold by cross-validation for a metric you supply; check the documentation for the version you run.

Calibration: do the numbers mean what they say?

A classifier is calibrated if, among the cases to which it gives probability p, a fraction p turn out positive: of everything scored 0.3, about 30% are positive. This is a separate property from ranking. A model can have a perfect ROC AUC and terrible calibration (any monotone distortion of the scores leaves AUC untouched), and a model can be perfectly calibrated and useless (always predict the base rate). You need calibration whenever the number itself is used: in the cost threshold, in expected-loss calculations ("this portfolio has 40 expected defaults"), when probabilities from several models are combined, when a human reads "70% likely", and when the score is compared across populations or over time.

The idea has a long history in forecasting. Brier (1950), "Verification of forecasts expressed in terms of probability", proposed scoring weather forecasts that say "30% chance of rain" by the squared difference from what happened, and checking whether such forecasts come true 30% of the time. Machine learning inherited the vocabulary.

Reading a reliability diagram

The standard picture is the reliability diagram (or calibration curve). Sort the cases into bins by predicted probability (say ten equal-width bins), and for each bin plot the mean predicted probability on the horizontal axis against the observed fraction of positives on the vertical. A calibrated model lies on the diagonal. Points below the diagonal mean the model is overconfident there (it said more than happened); above, underconfident.

Here is a model that is plainly miscalibrated for an ordinary reason: it has 41 parameters (40 features and an intercept) and almost no regularisation, trained on only 1,200 rows with 129 positives, so it fits noise and its scores are too extreme. A separate calibration set of 1,500 rows is held out to fix it, and a 100,000-row test set judges everything. Two repairs are compared: Platt scaling (Platt, 1999), which fits a logistic regression with two parameters on the logit of the score, and isotonic regression, which fits the best non-decreasing step function through the (score, outcome) pairs by the pool-adjacent-violators algorithm. Beneath the code are the metrics, then the reliability table.

"""Calibrating an overconfident model: reliability table, Platt scaling, isotonic regression."""
import numpy as np
from lib import *

rng = np.random.default_rng(16)
D = 40
w_true = np.r_[np.array([0.9, -0.8, 0.7, 0.6, -0.5, 0.5]), np.zeros(D - 6)]
def make(n):
    X = rng.normal(size=(n, D)); return X, (rng.random(n) < sigmoid(X @ w_true - 2.9)).astype(int)

Xtr, ytr = make(1200); Xcal, ycal = make(1500); Xte, yte = make(100_000)
b = fit_logreg(Xtr, ytr, l2=0.01, iters=30)                    # almost unregularised: 41 parameters, 1,200 rows, 95 positives
raw = lambda X: predict_proba(b, X)
print(f"train positives {ytr.sum()} of {len(ytr)}; test base rate {yte.mean():.3f}")

def platt_fit(s, y):                                            # logistic regression on the logit of the score: 2 parameters
    z = np.log(np.clip(s, 1e-9, 1 - 1e-9) / (1 - np.clip(s, 1e-9, 1 - 1e-9)))
    a = fit_logreg(z[:, None], y, l2=1e-6, iters=30); return lambda s2: predict_proba(a, np.log(np.clip(s2, 1e-9, 1 - 1e-9) / (1 - np.clip(s2, 1e-9, 1 - 1e-9)))[:, None])

def isotonic_fit(s, y):                                         # pool adjacent violators, then step-interpolate
    o = np.argsort(s); xs, ys = s[o], y[o].astype(float)
    vals, wts, ends = [], [], []
    for i in range(len(ys)):
        vals.append(ys[i]); wts.append(1.0); ends.append(xs[i])
        while len(vals) > 1 and vals[-2] > vals[-1]:
            v = (vals[-2] * wts[-2] + vals[-1] * wts[-1]) / (wts[-2] + wts[-1]); w = wts[-2] + wts[-1]
            vals[-2:] = [v]; wts[-2:] = [w]; ends[-2:] = [ends[-1]]
    return lambda s2: np.interp(s2, ends, vals)

def metrics(p, y):
    pc = np.clip(p, 1e-6, 1 - 1e-6)
    bins = np.minimum((p * 10).astype(int), 9)
    ece = sum(abs(p[bins == k].mean() - y[bins == k].mean()) * (bins == k).mean() for k in range(10) if (bins == k).any())
    t = 5 / 105; flag = p >= t
    cost = ((flag & (y == 0)).sum() * 5 + (~flag & (y == 1)).sum() * 100) / len(y)
    return roc_auc(p, y), np.mean((p - y) ** 2), -np.mean(y * np.log(pc) + (1 - y) * np.log(1 - pc)), ece, cost

Scoring calibration: Brier, log loss, ECE

A picture needs numbers beside it. Three are standard.

  • Log loss (cross-entropy, as in maximum likelihood and loss functions) is the average of −log of the probability assigned to what happened. It punishes confident mistakes ferociously.
  • The Brier score is the mean squared difference between the predicted probability and the 0/1 outcome. Lower is better; always predicting the base rate b scores b(1 − b), a useful reference.
  • Expected calibration error (ECE; Naeini et al., 2015) bins the predictions, takes the gap between the mean prediction and the observed rate in each bin, and averages the gaps weighted by bin size. It is easy to read, and it is the number most people quote.

Log loss and the Brier score are proper scoring rules: their expected value is minimised exactly when the model reports the true probabilities, so improving either (without changing the ranking) means improving calibration. They mix calibration and ranking quality in one number. ECE isolates calibration but has two weaknesses: it depends on the binning (the number of bins, equal-width or equal-count), and a model that always predicts the base rate has an ECE near zero while being useless. So report ECE together with a ranking metric and a proper score, never alone. In the results above, Platt scaling improved all of ECE (0.030 to 0.006), Brier (0.0842 to 0.0826) and log loss (0.2902 to 0.2789) and left AUC at 0.826.

Why models are miscalibrated

Calibration is not a fixed property of an algorithm, but there are patterns, documented across many datasets by Niculescu-Mizil and Caruana (2005), "Predicting Good Probabilities with Supervised Learning". Max-margin methods (boosted trees and stumps, support vector machines) push scores away from 0 and 1 into a sigmoid-shaped distortion; naive Bayes tends to the opposite error, with extreme probabilities; neural networks and bagged trees were well calibrated on their benchmarks. Later work found that modern deep networks trained long with little regularisation are typically overconfident (Guo et al., 2017, "On Calibration of Modern Neural Networks"), which is where temperature scaling comes from: divide the logits by one number T fitted on held-out data. For plain logistic regression trained by maximum likelihood, the training predictions are calibrated on average by construction, and miscalibration appears when the model overfits (as above), when the data shifts, or when you resample.

Temperature scalingOne parameter dividing the logits (multi-class and neural nets)Cannot change the predicted class; very stableFixes only a uniform stretch, not bias at one end

In the experiment, isotonic regression was worse than Platt (log loss 0.2945 against 0.2789, ECE 0.0185 against 0.0063) because 1,500 calibration rows with 170 or so positives are too few for a free-form step function. Niculescu-Mizil and Caruana make the same observation: isotonic regression is the more powerful tool but needs more data. Three rules follow.

  1. Calibrate on rows the model did not train on. A model's scores on its own training rows are the most overconfident scores it will ever produce. Use a held-out calibration set, or cross-fit (calibrate on out-of-fold predictions; scikit-learn's CalibratedClassifierCV does this internally).
  2. Match the method to the data. Under a few thousand calibration rows or very few positives, prefer Platt or temperature scaling. Move to isotonic when there are many thousands.
  3. Recalibration is a monotone map. It never changes the ranking (except for ties that isotonic can introduce), so AUC and the top-k list are unchanged. It makes the numbers honest; it cannot make the model better at separating cases.

When the world moves: prior shift

A calibrated model can become miscalibrated without anything being wrong with it. Suppose the model was trained when 1% of cases were positive, and later the positive rate triples. The way positives look has not changed; there are simply more of them. This is prior shift (or label shift). The model still ranks well, but its probabilities are now too low. The adjustment is the same odds rescaling as for undersampling: multiply the odds by the ratio of new to old prior odds (Saerens, Latinne and Decaestecker, 2002, "Adjusting the Outputs of a Classifier to New A Priori Probabilities"). The script tests it on a model trained at a 1.07% base rate and deployed at four different rates.

"""Prior shift: a calibrated model meets a population where the positive rate has tripled."""
import numpy as np
from lib import *

rng = np.random.default_rng(18)
D = 8
mu_pos = np.array([1.0, -0.8, 0.7, 0.5, -0.4, 0.3, 0.0, 0.0])            # class-conditional means; identity covariance

def make(n, rate):
    y = (rng.random(n) < rate).astype(int)
    return rng.normal(size=(n, D)) + np.outer(y, mu_pos), y

Xtr, ytr = make(60_000, 0.01)
b = fit_logreg(Xtr, ytr, l2=1.0)
pi_train = ytr.mean()
print(f"trained at positive rate {pi_train:.4f}")
print(f"{'deployment rate':>16}{'mean predicted':>16}{'actual rate':>13}{'gap in mean':>14}{'after odds shift':>18}{'gap':>8}")
for rate in (0.005, 0.01, 0.03, 0.10):
    X, y = make(200_000, rate)
    p = predict_proba(b, X)
    odds = p / (1 - p) * (rate / (1 - rate)) / (pi_train / (1 - pi_train))   # rescale prior odds from training rate to deployment rate
    p2 = odds / (1 + odds)
    print(f"{rate:>16.3f}{p.mean():>16.4f}{y.mean():>13.4f}{abs(p.mean() - y.mean()):>14.4f}{p2.mean():>18.4f}{abs(p2.mean() - y.mean()):>8.4f}")

At the training rate the model is fine (mean prediction 0.0106, actual 0.0100). When the true rate rises to 3%, the mean prediction is 0.0123 against an actual 0.0303; at 10% it is 0.0177 against 0.1014. After the odds shift (using the known new rate) the gaps shrink to 0.0004 and 0.0015. In real life you often do not know the new rate immediately; you estimate it from a sample of recent labelled cases, or with the expectation-maximisation procedure described in the same paper. If instead the relationship between features and outcome changes (concept drift), no simple rescaling works and you recalibrate or retrain on recent data. Either way, calibration is something to monitor continuously: compute the reliability table on the latest labelled cases as they arrive and alert when ECE or the mean gap drifts (metrics and histograms; chapter 21 on monitoring).

Systems connection

Treat the probability as a contract between the model service and whatever consumes it. The consumer (a rules engine, a review queue, a pricing system) bakes in a threshold or an expected-loss figure, so a silent change in the score's meaning breaks it as surely as a changed field type would. When you retrain, recalibrate, resample or change the feature set, version the calibration map with the model, test it on a recent labelled sample before release, and roll out gradually (designing with ML and LLMs; deployment strategies).

Calibration and fairness

When a score is used on different groups, there are several things "fair" could mean, and calibration is one of them: within each group, a score of 0.3 should mean 30%. Another is equal error rates across groups. When base rates differ between groups, a score cannot in general satisfy both at once, which is the heart of the COMPAS dispute covered in case study 7. For now, remember the practical implication: check your reliability diagram per subgroup, because a model can be calibrated overall and badly miscalibrated for a minority group.

A recipe for a rare-event decision

  1. Evaluate with the right metrics. Average precision and the precision-recall curve for ranking, log loss or Brier for probabilities; never accuracy alone. Use stratified, group-aware or time-aware folds (chapter 13).
  2. Train plainly first. A baseline without resampling or weights (chapter 4). Add weights or undersampling only if a measurable problem remains, and record the factor.
  3. Recalibrate on held-out data. Platt or temperature scaling by default; isotonic with plenty of rows. Put the calibration step inside the cross-validation so its effect is measured honestly.
  4. Choose the operating point from the decision. Cost threshold if costs are known, top-k if capacity binds, a recall target with an interval if a promise is made.
  5. Check subgroups and extremes. Reliability by group; behaviour at the highest and lowest scores, where the rows are few.
  6. Monitor in production. Base rate, mean score, reliability on delayed labels, and the realised cost, with an owner and an alert.

State of play, October 2026

Practice has moved away from default rebalancing for tabular risk models, and towards honest probabilities plus a threshold or capacity choice made from costs. The van den Goorbergh et al. (2022) result on logistic regression was extended to machine-learning models by Carriero and colleagues, whose published version reports that models without an imbalance correction had equal or better calibration than corrected ones. Library details (the names of calibration and threshold-tuning utilities) change between releases, so check the documentation of the version you use rather than relying on this page.

Key takeaways

  • Imbalance causes three different problems: a misleading metric, scarce information about positives, and an optimisation that ignores the minority. Only the third is helped by resampling or weights.
  • In the experiment, class weights, undersampling and plain training had the same AUC (0.904 to 0.906), average precision (0.176 to 0.184) and best-possible cost (0.640 to 0.647). The first two inflated the mean probability 25-fold.
  • Undo rebalancing before using probabilities: p = βps / (βps − ps + 1) for undersampling at rate β. Resample only inside training folds.
  • Choose the operating point from costs, from capacity, or from a promise, and remember that a recall target tuned on 20 positives can land anywhere from 75% to 96%.
  • Calibration means a score of p is right a fraction p of the time. Check it with a reliability diagram and score it with Brier or log loss; ECE alone can be gamed by a useless constant.
  • Repair it with Platt or temperature scaling (few data) or isotonic regression (much data), fitted on rows the model did not train on. It changes the probabilities, not the ranking.
  • Calibration decays under prior shift and drift. Rescale odds for a changed base rate, monitor reliability on fresh labels, and check subgroups.

Check your understanding

You train a logistic regression with class_weight="balanced" on data with a 0.5% base rate. Ranking quality is as good as an unweighted model, but you plan to flag cases using the cost threshold 0.05. What will happen?

  1. Nothing: the cost formula works for any model that ranks well.
  2. Too few cases will be flagged, because weights make the model conservative.
  3. The model will flag exactly the right cases, because balanced weights make probabilities equal to frequencies.
  4. Too many cases will be flagged, because the weighted model reports probabilities for a world where positives are common.
Weighting positives by roughly 200 multiplies the odds by about 200, so most scores sit far above the real probabilities. A threshold of 0.05 then flags a large share of all cases. The ranking is unchanged, so either correct the odds (divide by the weight) or choose a much higher threshold on the weighted scale.

A fraud model has ROC AUC 0.95 and average precision 0.30 at a 0.5% base rate. After isotonic recalibration on a held-out set, AUC is still 0.95. Why is that expected?

  1. Isotonic regression ignores the scores entirely.
  2. Recalibration is a monotone, non-decreasing map of the score, so it preserves the ranking that AUC measures (apart from ties).
  3. AUC is insensitive to the model's quality.
  4. The calibration set was too small to change anything.
AUC depends only on the ordering of scores. A non-decreasing map keeps that ordering, so AUC stays put, while log loss, Brier and ECE can improve a great deal. Isotonic can merge neighbouring scores into ties, which is why AUC can wobble very slightly in practice.

A reliability diagram shows a point at predicted 0.85, observed 0.65, with most other points also below the diagonal at high scores. How do you read this?

  1. The model is overconfident at high scores: it says 85% and is right 65% of the time.
  2. The model is underconfident at high scores.
  3. The model's ranking is poor.
  4. The base rate has fallen.
Below the diagonal means the observed frequency is less than predicted, which is overconfidence. Reliability diagrams say nothing directly about ranking; a model can be badly miscalibrated and rank perfectly. A changed base rate would shift all bins, though prior shift and overfitting can look alike on one plot, which is why you check the training and deployment base rates.

You have only 300 labelled calibration rows (35 positives) and a boosted model that is clearly overconfident. Which repair is most sensible?

  1. Isotonic regression, because it is the most flexible.
  2. Retrain on the calibration rows too and skip calibration.
  3. Platt scaling (or temperature scaling): two parameters that can be estimated from few rows.
  4. Do nothing, since calibration only matters for neural networks.
Isotonic regression has many degrees of freedom and overfits small calibration sets, as the chapter's experiment showed. A two-parameter sigmoid map is the standard choice when data is scarce, and it fits the sigmoid-shaped distortion typical of boosted trees. Calibration matters for any model whose probabilities are used.

A team tunes a threshold to achieve 90% recall on a validation set with 25 positives and tells the business "recall will be 90%". What is the most accurate criticism?

  1. Recall cannot be tuned, only precision can.
  2. The validation set should have been balanced.
  3. 90% is too ambitious for rare events.
  4. With so few positives, the realised recall is highly uncertain (in the chapter's simulation it ranged roughly from 75% to 96%) and on average slightly lower than the target, so a range should be quoted.
Both the choice of threshold and the estimate of recall use the same few positives, so the promise carries sampling noise and a mild optimistic bias. Balancing the validation set would not add positives and would distort precision. The remedy is more positives, an interval, or a safety margin.

A model trained when 2% of cases were positive is deployed where the rate is 6%. The class-conditional feature distributions have not changed. Which statement is correct?

  1. Ranking and calibration are both fine, because the model is unchanged.
  2. Ranking is still fine, but probabilities will be too low; rescaling the odds by the ratio of new to old prior odds repairs them.
  3. The model must be retrained from scratch before it can be used.
  4. Probabilities will be too high, because rare events become rarer after training.
Under prior shift the evidence in the features has the same meaning, but the starting odds have tripled roughly, so the posterior odds should rise by the same factor. The model, trained at 2%, bakes in the old prior and under-predicts. Retraining is unnecessary if the shift is only in the prior, though you should verify that assumption on fresh labels.

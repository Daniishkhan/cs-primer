Feature Engineering

A model can only use what its columns say. Feature engineering is the work of turning raw records into columns that make the useful pattern easy to find: encoding categories, summarising histories, combining quantities and encoding what a domain expert knows. This chapter explains why each technique works, builds the dangerous one (target encoding) so that it is safe, and shows how much each is worth with numbers.

Why this matters

On tabular problems, which are most of the machine learning that businesses actually run, the choice of columns usually moves the result more than the choice of algorithm. Chapter 9 gave you the strongest general-purpose learner for tables, and it will still miss a relationship that no column expresses. This chapter is where you add that expression. It is also where leakage most often enters: a target encoding or a customer aggregate computed carelessly is a leak with a respectable name (chapter 14). After it you will be able to pick an encoding for any categorical column, build target encodings that survive honest validation, compute history aggregates as of a prediction date, add ratio and date features from domain knowledge, and say which of these a given model needs.

What a model can and cannot see

A feature is one column of the matrix X (shape (n_samples, n_features)) that the model receives, and feature engineering is the construction of those columns from raw data. The point is easy to state and easy to forget: the model never sees your database, your PDF or your customer. It sees numbers in columns. Whatever you want it to use must be a number in a column, in a form its learning algorithm can exploit.

That second condition is the interesting one, because each model family has things it finds easy and things it cannot do at all. A linear model computes a weighted sum, so it can use a feature only through a straight line: it cannot see that risk rises with the ratio of debt to income, because a ratio is not a weighted sum of debt and income, and it cannot see that the effect of age differs by region unless you supply the product. A decision tree (chapter 8) asks one question at a time about one column, so it needs many splits to approximate a diagonal boundary and cannot do arithmetic on two columns at all. A nearest-neighbour model (chapter 7) lives or dies on the scale of its columns, because distance adds squared differences and a column measured in pounds drowns one measured in years. A neural network can in principle build its own combinations, but it needs far more data to do so reliably on a table (chapter 19).

One more thing to keep in mind from the start. Features are fitted things. A mean used to centre a column, the frequency of a category, the average label of a group, a customer's order count as of last Friday: each is computed from data, and each can be computed from the wrong data. Chapter 14's rule applies in full: anything with a fit belongs inside the fold. Keep the rule in view, because several techniques below only become safe when you honour it.

Numbers: transforms that match the model

Numeric columns need less work than categorical ones, but three habits pay for themselves.

Tame skew with a logarithm. Money, counts, durations and populations are usually right-skewed: most values are small and a few are enormous. For a linear model or a neural network, a few huge values dominate the fit; a log transform, log(1 + x) so that zeros survive, turns multiplicative differences into additive ones and pulls the tail in. Trees do not care, because they only use the order of the values, so a log changes nothing for them. This is the first place where "which model?" decides "which features?".

Scale when the model measures distance or uses a penalty. Standardising a column (subtract the mean, divide by the standard deviation) matters for nearest neighbours, for regularised linear models (the L1 and L2 penalties of chapter 6 treat a coefficient of 1 as equally costly whatever the column's units) and for neural networks. It is harmless but pointless for trees. The mean and deviation are learned from the training rows only.

Keep missingness as information. Missing values are rarely random: an absent income may mean "self-employed", an absent lab result may mean "the doctor did not think it necessary", which is itself a signal about the patient. If you impute (fill in) a missing number with the median, also add a binary column income_missing. Boosted-tree libraries handle missing values natively by learning which side of a split missing rows should go to, which is often better than imputing; linear models and neural networks need the explicit fill and flag. The EDA habits in chapter 3 tell you how the missingness arises, which decides whether the flag helps.

Two optional numeric tools deserve a sentence. Binning (cutting age into bands) gives a linear model a step-shaped curve it could not otherwise draw, at the cost of throwing away within-band detail; tree models do this for themselves. And clipping (capping values at the 1st and 99th percentile, learned on training data) limits the damage of a measurement error.

Categories: choosing an encoding

A categorical column holds labels from a set: region, merchant, product code, browser. Models need numbers, so the question is which numbers. The first distinction is between nominal categories (no natural order: region, colour) and ordinal ones (ordered: "low, medium, high", shirt sizes). The second is cardinality, the number of distinct values: 8 regions is low, 30,000 postcodes is high.

One-hot encoding
One 0/1 column per category. Lets a linear model give every category its own offset. For 30,000 categories it creates 30,000 mostly-zero columns.
Ordinal (label) encoding
Replace each category by an integer, 0, 1, 2, and so on. Correct for truly ordinal columns. For nominal ones it invents an order; a linear model will treat "west = 3" as three times "south = 1".
Frequency (count) encoding
Replace each category by how often it appears. One column of any cardinality; useful when popularity itself predicts the target, and blind to everything else about the category.
Hashing
Hash the category name into one of a fixed number of columns. Fixed width and no lookup table to store, at the price of collisions where two categories share a column.
Target encoding
Replace each category by a summary of the target within it, usually the mean. One informative column of any cardinality, and the most dangerous encoding here; the next section is about doing it safely.
Embedding
A learned vector per category, trained with the model (neural networks) or taken from a pre-trained model (text and product catalogues). Powerful, needs enough data per category, and is outside the scope of a classical pipeline except as an input.

The next experiment shows the first three on an unordered column. There are 8 regions with unequal sizes, each with its own true effect on the log-odds of a positive outcome, and the effects are deliberately unrelated to alphabetical order. A logistic regression gets the numeric age plus the region in each encoding, and we compare held-out ROC AUC (chapter 2).

"""Encoding a nominal column: ordinal codes, one-hot and frequency, scored by held-out AUC of a logistic regression."""
import numpy as np
from lib import *

rng = np.random.default_rng(17)
N = 12000
regions = ["north", "south", "east", "west", "centre", "coast", "island", "border"]
effect = np.array([0.9, -1.1, 0.2, -0.3, 1.2, -0.8, 0.6, -0.5])        # true log-odds shift per region (unordered)
p_region = np.array([.30, .22, .14, .10, .08, .07, .05, .04])           # how common each region is
region = rng.choice(8, N, p=p_region)
age = rng.normal(40, 12, N)
z = -0.4 + effect[region] + 0.03 * (age - 40)
y = (rng.random(N) < sigmoid(z)).astype(int)
tr, te = np.arange(8000), np.arange(8000, N)
print(f"{N} rows, 8 regions, {y.mean():.1%} positive; alphabetical order of names is the 'ordinal' code")

order = np.argsort(regions)                      # alphabetical rank of each region name
rank = np.empty(8); rank[order] = np.arange(8)
def score(cols):
    A = np.column_stack(cols); mu, sd = A[tr].mean(0), A[tr].std(0) + 1e-9
    b = fit_logreg((A[tr] - mu) / sd, y[tr], l2=1.0)
    return roc_auc(predict_proba(b, (A[te] - mu) / sd), y[te])

onehot = [(region == k).astype(float) for k in range(8)]
freq = np.bincount(region[tr], minlength=8) / len(tr)
print(f"age only                      AUC {score([age]):.3f}")
print(f"age + ordinal code (one col)  AUC {score([age, rank[region]]):.3f}")
print(f"age + frequency (one col)     AUC {score([age, freq[region]]):.3f}")
print(f"age + one-hot (8 cols)        AUC {score([age] + onehot):.3f}")
12000 rows, 8 regions, 43.4% positive; alphabetical order of names is the 'ordinal' code
age only                      AUC 0.577
age + ordinal code (one col)  AUC 0.585
age + frequency (one col)     AUC 0.603
age + one-hot (8 cols)        AUC 0.740

One-hot encoding lifts the AUC from 0.577 (age alone) to 0.740, because it lets every region have its own offset. The ordinal code adds almost nothing (0.585): a single column that must change in a straight line with the alphabet cannot represent effects that jump up and down from one region to the next. The frequency encoding does a little better (0.603), and it is worth understanding why. Frequency has no knowledge of the target. It helped here only because, by chance, the commonest regions have slightly more positive effects than the rare ones (the correlation between a region's share of rows and its true effect is +0.10, and the biggest region, north, has a large positive effect). On other data it could carry no signal at all, which is the general character of frequency encoding: a cheap extra column worth trying, not a substitute for a real encoding.

Common misconception

"Label-encode categories and let the model sort it out." For a tree ensemble this is often acceptable, since a tree can carve out any subset of integers with enough splits, but it is arbitrary: the splits it needs depend on which integer you gave which category, and with many levels the trees waste their depth. For a linear model or a neural network it is wrong, because it asserts an order and a spacing that do not exist. Choose the encoding deliberately, and prefer a library's native categorical handling (LightGBM, CatBoost and recent XGBoost versions can take category columns directly) over integers.

For high-cardinality columns, one-hot encoding stops being practical. Two cheap steps help before any encoding. Group the rare levels into an "other" bucket using counts computed on the training rows: a postcode seen twice has almost nothing to say, and the model's estimate for it would be noise. And decide what happens to a level that appears at prediction time but never in training (a new merchant): it must map to a defined value ("other", the overall mean, or a missing-value code), and your validation should include such cases, because production will. The strongest option for high-cardinality columns, when the target is available, is the next section.

Target encoding, done safely

The idea and the trap

Target encoding (also called mean encoding or likelihood encoding) replaces each category by the average of the target for that category: the default rate of customers in postcode "AB12", the average sale price in each neighbourhood. It was described for high-cardinality columns by Micci-Barreca (2001), "A preprocessing scheme for high-cardinality categorical attributes in classification and prediction problems", and it compresses a 30,000-level column into one informative number. It is also how you most easily put the label into your own features.

Why it is dangerous follows from what it computes. Take a category with four training rows, one of them positive: the naive encoding is 0.25. For the positive row, that 0.25 contains its own label; for the negative rows it contains the positive row's label. The encoded column is partly a copy of the target. On a rare level with a single row, the encoding is the label. The model, trained on rows where this column agrees with the label more than it ever will on new data, learns to trust it too much, and then validation, if the encoding was computed before the split, shares the leak. This is the same pattern as in chapter 14: a learned statistic that has touched the rows it is later applied to.

Three defences, in the order you should reach for them.

  1. Smooth. A level with 3 rows should not be trusted as much as one with 3,000. Replace the raw mean by a blend of the level's mean and the overall mean, weighted by how many rows support it:

    encoded = (n × level_mean + m × overall_mean) / (n + m)

    where n is the number of rows in the level and m is a smoothing weight, which you can read as "the number of imaginary average rows added to every level". With m = 20, a level of 3 rows sits 87% of the way to the overall mean; a level of 3,000 only 0.7% of the way. This is empirical Bayes shrinkage, the same instinct as the ridge penalty of chapter 6.
  2. Encode out of fold. Smoothing reduces how much of the label leaks, but does not remove it. To remove it, never compute a row's encoding from a set that contains that row. Split the training rows into k folds (5 is usual); for each fold compute the level statistics from the other k − 1 folds and apply them to the held-out fold. Every training row now carries an encoding that was made without its own label, which is how the column will look for new rows. For validation and production, use statistics from all training rows.
  3. Do it inside your validation. The out-of-fold encoding is made within the training part of each cross-validation split. The validation fold is encoded with statistics from that split's training part only. Getting this wrong is the commonest bug, because it appears to work: the encoded column goes into a pipeline before cross_val_score and everything looks excellent.

The stepper walks through the out-of-fold procedure once.

Step through

Out-of-fold target encoding with five folds

  1. Five folds of training rows. The training set is cut into five parts. Each row will receive an encoding, and we want that number never to be built from the row's own label.
  2. Hold one fold out. Fold 1 (yellow) is the fold being encoded. The other four (green) are the only rows allowed to contribute statistics.
  3. Count in the green folds. For every category, count its rows and positives in folds 2 to 5, then apply the smoothed formula. The example uses m = 20 and an overall rate of 0.30 in those folds.
  4. Write the encoding into fold 1. Every row of fold 1 receives the value for its category. None of those values saw a fold 1 label.
  5. Rotate. Fold 2 is now held out, folds 1, 3, 4 and 5 supply the counts, and fold 2 is encoded.
  6. Repeat for folds 3, 4 and 5. When the loop ends the whole training column has been built out of fold. It is noisier than the naive encoding, and honestly so.
  7. Encode new data. For validation, test and production rows, nobody needs to hold anything out: use the statistics from all the training rows. In cross-validation, "all training rows" means the training part of that split.

Measuring the damage

The experiment builds a column of 400 levels with very uneven frequencies (about a hundred rows for the commonest levels, a handful for most) and 5,000 training rows. It runs twice: in A the category has no effect whatever on the label, so any apparent signal is leakage; in B each level has a real effect of standard deviation 0.5 on the log-odds. For each encoding it reports the ROC AUC of the encoded column alone on the training rows and on 5,000 fresh rows, and the test AUC of a logistic regression that also has one honest numeric feature, with the weight it gave the encoding. Four encodings: naive mean, smoothed in-sample, leave-one-out (each row's own label removed from its level's mean) and smoothed out-of-fold.

"""Target encoding on a 400-level column: naive, smoothed, leave-one-out and out-of-fold, with and without real signal."""
import numpy as np
from lib import *

K, NTR, NTE, M = 400, 5000, 5000, 20
def make(seed, level_sd):
    rng = np.random.default_rng(seed)
    cat = rng.choice(K, NTR + NTE, p=rng.dirichlet(np.full(K, 0.5)))      # very uneven level frequencies
    x1 = rng.normal(size=NTR + NTE)                                         # one honest numeric feature
    z = -1.0 + 0.8 * x1 + rng.normal(0, level_sd, K)[cat]                   # level_sd = 0: category is pure noise
    y = (rng.random(NTR + NTE) < sigmoid(z)).astype(int)
    return cat, x1, y

def counts(cat, y):
    return np.bincount(cat, minlength=K).astype(float), np.bincount(cat, weights=y, minlength=K)
def enc(n, s, prior, m):                                   # (sum + m*prior) / (count + m); levels never seen -> prior
    return np.where(n + m > 0, (s + m * prior) / np.maximum(n + m, 1e-9), prior)

def encodings(cat, y, tr, te):
    n, s = counts(cat[tr], y[tr]); prior = y[tr].mean()
    out = {"naive mean": (enc(n, s, prior, 0)[cat[tr]], enc(n, s, prior, 0)[cat[te]]),
           f"smoothed (m={M})": (enc(n, s, prior, M)[cat[tr]], enc(n, s, prior, M)[cat[te]])}
    ni, si = n[cat[tr]], s[cat[tr]]
    loo = np.where(ni > 1, (si - y[tr]) / np.maximum(ni - 1, 1), prior)
    out["leave-one-out"] = (loo, enc(n, s, prior, 0)[cat[te]])
    oof = np.zeros(len(tr)); fold = np.arange(len(tr)) % 5
    for f in range(5):
        a = tr[fold != f]; na, sa = counts(cat[a], y[a])
        oof[fold == f] = enc(na, sa, y[a].mean(), M)[cat[tr][fold == f]]
    out[f"out-of-fold (m={M})"] = (oof, enc(n, s, prior, M)[cat[te]])
    return out

tr, te = np.arange(NTR), np.arange(NTR, NTR + NTE)
for title, sd in (("A. category is pure noise", 0.0), ("B. category has a real effect (sd 0.5 on log-odds)", 0.5)):
    cat, x1, y = make(23, sd); E = encodings(cat, y, tr, te)
    print(f"{title}\n{'encoding':<22}{'AUC alone, train':>17}{'AUC alone, test':>16}{'LR test AUC':>13}{'LR weight':>11}")
    for name, (a, b) in E.items():
        A, B = np.c_[x1[tr], a], np.c_[x1[te], b]; mu, sd_ = A.mean(0), A.std(0)
        beta = fit_logreg((A - mu) / sd_, y[tr], l2=1.0)
        print(f"{name:<22}{roc_auc(a, y[tr]):>17.3f}{roc_auc(b, y[te]):>16.3f}"
              f"{roc_auc(predict_proba(beta, (B - mu) / sd_), y[te]):>13.3f}{beta[2]:>+11.2f}")
    print()

cat, x1, y = make(23, 0.0); n, s = counts(cat[tr], y[tr]); big = np.argmax(n); rows = np.where(cat[tr] == big)[0]
loo = (s[big] - y[tr][rows]) / (n[big] - 1)
print(f"largest level: {int(n[big])} rows; its leave-one-out values take {len(np.unique(loo.round(9)))} distinct values")
print(f"within that level, AUC of the LOO value against the label = {roc_auc(loo, y[tr][rows]):.3f} (0.0 means it separates the labels perfectly, reversed)")

Read the A table first, where the truth is that the column carries nothing. The naive and smoothed in-sample encodings reach a training AUC of 0.646 and 0.637 from pure noise, and fall to 0.490 and 0.488 on fresh data. The logistic regression sees a column that predicts the training labels and gives it a weight of +0.63 and +0.50, but the same model with the out-of-fold column gives it +0.01, which is the right answer: nothing. The test AUC of the whole model is 0.667 and 0.673 for the in-sample encodings against 0.707 for out-of-fold. The wasted weight cost about 0.04 of AUC in this small example, and the damage grows with cardinality and with model flexibility: a boosted-tree model can split on the encoded value very precisely and chase the leak even harder.

In B, with a real level effect, the pattern is the same but milder. Alone, the column's test AUC is 0.594 to 0.598 for every method (the signal is there and all methods find it); the in-sample versions still have a train AUC of 0.693 and 0.679 against 0.580 for out-of-fold, and the out-of-fold model has the best end-to-end test AUC, 0.722 against 0.706 for the naive mean.

Leave-one-out looks attractive and deserves a warning. Its training AUC is honest on average (0.501 in A), and the logistic model does fine with it (0.706 and 0.718). But the last two lines of output show the trap. Within the largest level (133 rows) the leave-one-out value takes only two distinct values, one for each label, and it is perfectly reversed: every positive row has a lower value than every negative row. The encoding is the label, flipped. A linear model on the whole table cannot exploit this, but a tree model can isolate it with two splits within a level, and a boosted ensemble finds it. Prefer out-of-fold, whose per-row noise breaks the pattern.

Common misconception

"Target encoding is just a group average, so it can't leak the way a label can." It is a group average of the label, and a small group's average is mostly its own members' labels. The leak is invisible in the training metrics and in any validation that shares the encoding. Compare the encoded column's AUC on training rows with its AUC on fresh rows: a gap like 0.646 against 0.490 is the symptom. CatBoost (Prokhorenkova et al., 2018, discussed in chapter 9) builds the same protection into the algorithm with ordered target statistics, where each row is encoded using only the rows before it in a random order.

A few practical notes complete the picture. For a regression target the "mean" is the mean of the numeric target, and other summaries (median, standard deviation) can be added as extra columns. For a multiclass target, encode one column per class (the share of each class in the level). Unseen levels get the overall mean, the same value a level of zero rows would have under the formula. Choose m by validation or by thinking about how many rows you would need before trusting a level's own rate; 10 to 100 is a common range, and a hierarchy (postcode, then district, then region) can be handled by shrinking each level towards its parent instead of the global mean. And remember that the whole procedure is a fitted step: in a cross-validation loop it runs inside each fold, with its own nested out-of-fold pass over that fold's training rows. The scikit-learn TargetEncoder (added in version 1.3) does this cross-fitting internally; check the documentation of your installed version, and note that its fit_transform on training data differs from fit followed by transform for exactly the reason discussed above.

Aggregates: summarising a history

Much real data does not arrive as one row per thing you want to predict. It arrives as events: card transactions, page views, sensor readings, support tickets, lab results. To predict something about a customer, an account or a patient you must collapse that customer's many rows into a few columns. This is aggregation, and the aggregate features it produces are often the strongest in the whole model.

The vocabulary is a grid of choices. Entity: what you group by (customer, device, merchant, postcode). Function: count, sum, mean, maximum, standard deviation, number of distinct values, share of a type, time since the last event. Window: the period you aggregate over (the last 7, 30 and 90 days, or all history). A classic combination from marketing is RFM: recency (days since the last purchase), frequency (purchases in a window) and monetary value (money spent in it). Three numbers per customer, and for decades the backbone of customer models. More useful still are comparisons: this week against this customer's own typical week, this order against the merchant's average order, the last 30 days against the 60 before that. A raw count says "busy", a ratio of recent to earlier activity says "waking up or going quiet", which is what the future depends on.

Aggregate as of a date, or leak

An aggregate over events has a time dimension that a plain column does not, and this is where it goes wrong. The prediction is made at some moment, the cutoff (also called the prediction date or as-of date). Every aggregate must be computed from events strictly before it. The label is defined by what happens after. The next figure shows the layout for a customer who might buy in the next 30 days.

The script simulates this. There are 4,000 customers with a hidden daily purchase rate that depends on their plan, and a drift that makes some customers warm up and others cool down over the period. The log is 150 days long; the cutoff is day 120; the label is "at least one purchase in the next 30 days". Four sets of features are compared with a logistic regression on a held-out 1,200 customers: age and plan only; plus as-of aggregates (purchases in the last 30 and 90 days, log of days since the last purchase, and the ratio of recent to earlier rate); and, as a deliberate mistake, the same plus a count over a 20-day window centred on the cutoff. The oracle scores customers by their true hidden rate over the next 30 days, which no model can see.

"""Aggregates from an event log, computed as of a cutoff date, versus the same aggregates computed with the future in them."""
import numpy as np
from lib import *

rng = np.random.default_rng(31)
C, DAYS, CUT = 4000, 150, 120                       # customers, days of log, prediction date (day 120)
plan = rng.integers(0, 3, C)                        # 0 free, 1 standard, 2 premium
age = rng.normal(38, 11, C)
rate = np.exp(rng.normal(-4.7, 0.9, C) + 0.3 * plan)           # latent purchases per day: never observed directly
drift = rng.normal(0, 0.012, C)                                  # some customers are warming up or cooling down
t = np.arange(DAYS)
lam = rate[:, None] * np.exp(drift[:, None] * (t[None, :] - CUT))
events = rng.poisson(lam)                                        # events[c, d] = purchases by customer c on day d
y = (events[:, CUT:CUT + 30].sum(1) > 0).astype(int)            # label: any purchase in the 30 days after the cutoff
print(f"{C} customers, {int(events.sum())} purchase events, label rate {y.mean():.1%}")

def last_gap(ev):                                                # days since last purchase before the cutoff
    out = np.full(len(ev), 120.0)
    for i, row in enumerate(ev):
        nz = np.nonzero(row)[0]
        if len(nz): out[i] = len(row) - 1 - nz[-1]
    return out
past = events[:, :CUT]                                           # ONLY days before the cutoff
F_raw = np.c_[age, plan]
F_agg = np.c_[age, plan, past[:, -30:].sum(1), past[:, -90:].sum(1), np.log1p(last_gap(past)),
              past[:, -30:].sum(1) / (past[:, -90:-30].sum(1) / 2 + 0.5)]       # recent rate / earlier rate (momentum)
F_leak = np.c_[F_agg, events[:, CUT - 10:CUT + 10].sum(1)]       # "last 20 days" window centred on the cutoff by mistake
names = {"age + plan only": F_raw, "+ as-of aggregates": F_agg, "+ a window that straddles the cutoff": F_leak}

idx = rng.permutation(C); tr, te = idx[:2800], idx[2800:]
for nm, F in names.items():
    mu, sd = F[tr].mean(0), F[tr].std(0) + 1e-9
    b = fit_logreg((F[tr] - mu) / sd, y[tr], l2=1.0)
    print(f"{nm:<40} test AUC {roc_auc(predict_proba(b, (F[te] - mu) / sd), y[te]):.3f}")
# the honest ceiling: score customers with their true latent rate over the next 30 days
print(f"{'oracle (true latent rate)':<40} test AUC {roc_auc(lam[:, CUT:CUT+30].sum(1)[te], y[te]):.3f}")
4000 customers, 15701 purchase events, label rate 36.7%
age + plan only                          test AUC 0.573
+ as-of aggregates                       test AUC 0.669
+ a window that straddles the cutoff     test AUC 0.734
oracle (true latent rate)                test AUC 0.789

Age and plan alone give 0.573. The as-of aggregates lift it to 0.669: the model now sees who has been active lately. The mistaken window raises the number again, to 0.734, and it is the most tempting number on the page and the only one that is not real: ten of its twenty days are after the cutoff, so it counts some of the very purchases the label asks about. A deployed model would not have those days. The ceiling is 0.789, so the honest features capture a good part of what is knowable. The pattern is the one from chapter 14: a leak makes the metric better and the system no better.

Practical rules follow. Express every window relative to the cutoff and compute it from a time-filtered table: events[events.time < cutoff]. When one customer has several training examples at different cutoffs, build the features separately for each cutoff (a point-in-time or as-of join). Be suspicious of "lifetime" columns in a warehouse, such as total spend to date, which are overwritten as time passes and therefore describe the present, not the cutoff. And compute training and serving features with the same code, which the next-but-one section returns to.

Interactions, ratios and what domain knowledge adds

An interaction is a feature that combines columns so that the model can see a relationship it could not see from either alone: a product, a ratio, a difference, a flag for "both conditions at once". The case for them comes from the table at the start of the chapter. A linear model cannot form products or ratios; a tree can only approximate them with many splits. Giving the model the right combination removes that burden. The right combination is nearly always suggested by domain knowledge, an understanding of what is being measured and what matters in it:

  • Finance. Debt-to-income ratio, loan-to-value, utilisation (balance divided by credit limit), days between a due date and a payment date.
  • Health. Body-mass index from height and weight; estimated kidney function from creatinine, age and sex; change in a lab value since the last visit.
  • Retail and logistics. Price per unit, price relative to the category median, distance between origin and destination, days since last restock.
  • Software. Lines changed per commit, error rate (errors divided by requests), time since the previous deploy, age of a dependency in months.
  • Time. Hour, day of week, month, public holiday, days to payday: derived from a timestamp, as described next.

Three transformations recur so often that they deserve naming. Ratios normalise a quantity by its natural scale, so that a debt of 20,000 means something different for an income of 25,000 and one of 250,000. Differences between dates or measurements turn two large, nearly equal numbers into a small, meaningful one; a tree given due_date and paid_date as separate day numbers has to find the difference by luck. And cyclic encoding handles quantities that wrap around: hour 23 is close to hour 0, but as raw numbers they are 23 apart. Replace h by the pair (sin(2πh/24), cos(2πh/24)), which places the hours on a circle so that midnight sits next to 23:00. A linear model with only the raw hour can fit one slope across the day; with the pair it can fit a daily wave of any phase, since any cosine of the right period is a weighted sum of the two.

The next experiment puts numbers on it. There are 8,000 loan applications. The true default risk depends on the debt-to-income ratio, on how many days late the payment was (paid date minus due date, both stored as days since 2020), and on the hour of day with a peak at 03:00. The raw columns are income, debt, due date, paid date and hour. A logistic regression and a boosted-tree model (a small least-squares booster of the kind built in chapter 9, 120 rounds of depth-3 trees) train on 2,000 rows and are scored on the other 6,000.

"""Domain features: a ratio, a date difference and a cyclic hour. Linear model and boosted trees, raw versus engineered inputs."""
import numpy as np
from lib import *

rng = np.random.default_rng(41)
N = 8000
income = np.exp(rng.normal(10.8, 0.5, N))                   # yearly income, right-skewed
debt = np.exp(rng.normal(9.6, 0.9, N))                      # outstanding debt, right-skewed
due = rng.integers(0, 1500, N).astype(float)             # invoice due date, as days since 2020-01-01
paid = due + rng.normal(2, 6, N)                           # payment date: close to the due date
hour = rng.integers(0, 24, N)                               # hour of day of the application
ratio = debt / income                                       # the domain quantity: debt-to-income
late = paid - due                                           # days late (negative = early)
z = -2.6 + 2.6 * ratio + 0.18 * late + 0.9 * np.cos(2 * np.pi * (hour - 3) / 24)   # risk peaks at 03:00 and is lowest at 15:00
y = (rng.random(N) < sigmoid(z)).astype(int)
print(f"{N} applicants, default rate {y.mean():.1%}, debt-to-income median {np.median(ratio):.2f}, 95th pct {np.percentile(ratio, 95):.2f}")

sets = {
    "raw columns":         np.c_[income, debt, hour, due, paid],
    "+ ratio, days late":              np.c_[income, debt, hour, due, paid, ratio, late],
    "+ ratio, days late, cyclic hour": np.c_[income, debt, due, paid, ratio, late, np.sin(2*np.pi*hour/24), np.cos(2*np.pi*hour/24)],
}
tr, te = np.arange(2000), np.arange(2000, N)
print(f"{'features':<34}{'logistic AUC':>13}{'boosted-trees AUC':>19}")
for nm, F in sets.items():
    mu, sd = F[tr].mean(0), F[tr].std(0)
    b = fit_logreg((F[tr] - mu) / sd, y[tr], l2=1.0)
    a_lin = roc_auc(predict_proba(b, (F[te] - mu) / sd), y[te])
    a_gb = roc_auc(Boost(rounds=120, lr=0.08, depth=3, min_leaf=30).fit(F[tr], y[tr].astype(float)).predict(F[te]), y[te])
    print(f"{nm:<34}{a_lin:>13.3f}{a_gb:>19.3f}")
print(f"{'oracle (true probability)':<34}{roc_auc(z[te], y[te]):>13.3f}")
8000 applicants, default rate 32.8%, debt-to-income median 0.30, 95th pct 1.67
features                           logistic AUC  boosted-trees AUC
raw columns                               0.742              0.751
+ ratio, days late                        0.837              0.838
+ ratio, days late, cyclic hour           0.852              0.838
oracle (true probability)                 0.856

With the raw columns, logistic regression scores 0.742 and the boosted trees 0.751: neither has the debt-to-income ratio nor the days late, and each has to approximate them. Adding the two domain columns lifts both to 0.837 and 0.838, a gain of 0.09, about ten times the difference between the two algorithms. The cyclic hour is the interesting last row. It lifts the logistic regression to 0.852, almost at the oracle's 0.856, and does nothing for the trees (0.838): a tree can already cut the raw hour into the bands it needs, so the sine and cosine give it no new information. This is the table at the top of the chapter in numbers. The same feature is essential for one family and redundant for another.

Two cautions. First, interactions multiply: with d columns there are d(d−1)/2 pairwise products, and testing all of them on a modest dataset will find some that look useful by chance. Add interactions that you can explain; use model-based discovery (looking at what a boosted-tree model splits on together, or at an interaction measure from chapter 16) to suggest candidates, then validate them. Second, a ratio has its own failure: a zero or tiny denominator. Decide in advance what a ratio with zero income means, and add a small constant or a missing-value code rather than letting a division by zero reach production.

Analogy: the kitchen and the ingredients

A chef given a whole pig, a sack of flour and a cabbage can cook many dishes, but a better dish usually comes from prepared ingredients: stock already reduced, onions already caramelised. Feature engineering is the preparation. A powerful stove (a bigger model) helps, but it does not turn raw cabbage into stock.

Where it breaks down: in a kitchen, preparation never changes what the diner has already eaten. In a feature pipeline, preparation can quietly mix in the answer (a target encoding or an aggregate over the future), so a prepared ingredient needs a check that it was made from what was available at serving time.

One pipeline, fitted in the fold

Every technique in this chapter shares a structure: a learned part and an applied part. The learned part looks at data and stores a table: the mean and deviation of each column, the list of rare levels, the target mean per level, the 99th percentile. The applied part uses the stored table to transform rows. The discipline is to learn from the training rows only and to apply to everything else.

Two consequences matter in practice. The first is that in cross-validation the entire figure is repeated inside each fold, which is what a scikit-learn Pipeline (or any equivalent wrapper) does for you; chapter 13 and chapter 14 measured what happens when it is not. The second is train/serve skew: if the feature code that fills the training table is not the code that runs in production, the model is served columns computed differently from the ones it learned on. A median imputed in a notebook and a hard-coded constant in the service, an aggregate computed in SQL for training and in application code for serving, a timezone handled one way in each. The defences are boring and effective: write each feature once as a function, run the same function in both places (or use a feature store that guarantees the same definition), and test parity by recomputing a sample of historical cases through the production path and diffing the result against the training table. Designing with ML & LLMs covers feature stores in the context of serving.

Systems connection

As-of correctness is the same problem as reading from a database at a consistent snapshot. A point-in-time join over an event log is the ML name for "give me the state of the world at time T", and it depends on how the data is stored and replicated: streams and change data capture are how most feature pipelines see events in order, and data platforms cover the lineage and data-quality checks that tell you when an upstream column changed meaning. Train/serve skew is a version-skew bug of the kind schema evolution exists to prevent.

How many features, and which ones

It is easy to produce hundreds of features, and tempting to keep them all. Extra columns have costs: more chances for chance correlations to fool a validation score, more things to compute and monitor in production (every feature is a dependency that can break), and for linear and distance-based models, more noise. Modern boosted trees tolerate many irrelevant columns well, which makes pruning optional rather than urgent; a model with 50 columns that you understand is easier to maintain than one with 500 you do not.

Judge a candidate feature the way you would judge a model: by its effect on honest validation. The simplest tool is an ablation: train with and without the feature (or the group of features) under the same cross-validation, and compare the scores and their spread. Permutation importance (chapter 16) tells you what a trained model leans on. Two warnings apply to every one of these. Importance is not value: a feature that duplicates another will look unimportant in each model that has both. And a feature with unusually high importance is a leak suspect first and a discovery second, so before you celebrate, run the single-column scan from chapter 14.

Automated feature generation exists. The best-known approach, Kanter and Veeramachaneni (2015), "Deep Feature Synthesis: Towards Automating Data Science Endeavors", stacks aggregation and transformation primitives across related tables automatically, and the open-source library Featuretools implements it. Such tools generate the groups-by-functions-by-windows grid of the aggregate section faster than a person can and are a good way to produce candidates. They do not know which of the thousands of results are leaks, sensible, or affordable to serve, so the same human checks remain. Embeddings from pre-trained text or image models are the other common source of features: a vector from a language model for a free-text field can be fed to a boosted-tree model beside the ordinary columns, with the usual caveat that the embedding model must not have seen your test labels.

State of play, October 2026

Tooling has moved a lot of this chapter into libraries. LightGBM, CatBoost and XGBoost accept categorical columns natively, CatBoost uses ordered target statistics internally, and scikit-learn has shipped a cross-fitting TargetEncoder since version 1.3 (2023). Tabular foundation models such as TabPFN (chapter 19) take raw columns and make several of these steps unnecessary on small tables. None of that removes the work that depends on your problem: deciding the cutoff, building leak-free aggregates, and adding the ratio an expert knows matters. Library behaviour and defaults change between versions, so read the documentation of the version you install.

Key takeaways

  • A model sees only its columns, and each family can express different things. Linear models cannot form ratios or products; trees cannot do arithmetic on pairs; distance-based models need scaling. Engineer for the model you use.
  • Choose categorical encodings deliberately. On unordered regions, one-hot gave AUC 0.740, an alphabetical ordinal code 0.585, because the ordinal code asserts an order that is not there.
  • Target encoding is powerful and leaks by construction. On pure-noise levels, the in-sample encoding reached a training AUC of 0.646 against 0.490 on fresh data and earned a model weight of +0.63; out-of-fold gave +0.01.
  • Defend with smoothing (n × level mean + m × overall mean, over n + m), then out-of-fold encoding inside every validation fold. Leave-one-out leaves a reversed copy of the label inside each level.
  • History aggregates must be computed as of a cutoff. A window centred on the cutoff raised AUC from an honest 0.669 to 0.734 for the wrong reason.
  • Domain features (ratios, date differences, cyclic time) gave +0.09 AUC to both a logistic model and boosted trees, ten times the gap between those algorithms. The cyclic hour mattered to the linear model and not to the trees.
  • Feature code is a fitted step: learn on training rows, apply everywhere else, use one implementation for training and serving, and test parity.

Check your understanding

A logistic regression predicts loan default from region (12 unordered values, stored as integers 0 to 11). Performance is poor. What is the most likely cause and fix?

  1. The model is overfitting; add a stronger L2 penalty.
  2. The integers are too small; standardise the column.
  3. The integer code forces the effect of region to be a straight line in the code, which is meaningless for unordered regions; use one-hot or a safe target encoding.
  4. Logistic regression cannot use categorical information; switch to a tree.
A linear model gives the column a single slope, so region 8 must have an effect eight times that of region 1 and region 7 must lie between regions 6 and 8. One-hot columns (or a target encoding) give each region its own offset. Regularisation and standardisation do not remove the false order, and logistic regression can use categories perfectly well once they are encoded.

You target-encode merchant (30,000 levels) using the mean label per merchant over the whole training set, then run 5-fold cross-validation and see AUC 0.93. Production AUC is 0.71. What went wrong?

  1. Each row's encoding contained its own label, and the encoding was computed before the split, so the validation folds also saw label information from their own rows.
  2. Thirty thousand levels is too many for any encoding to work.
  3. The cross-validation used too few folds.
  4. The merchant column should have been one-hot encoded for a fair comparison.
Encoding from all training rows lets labels of validation-fold rows flow into their own features, especially on small merchants, so the CV score is inflated. The remedy is smoothing, an out-of-fold encoding built inside each fold, and statistics for the validation fold taken from the fold's training part only. Many levels is the reason to use target encoding, not an argument against it; fold count is secondary; and one-hot encoding 30,000 levels is rarely practical.

A level has 4 rows, 3 of them positive. The overall positive rate is 0.20 and the smoothing weight m is 16. What is the smoothed encoding?

  1. 0.75
  2. 0.20
  3. 0.35
  4. 0.31
(3 + 16 × 0.20) / (4 + 16) = 6.2 / 20 = 0.31. The raw mean 0.75 trusts four rows too much; 0.20 would ignore the level entirely; 0.35 comes from weighting the level and the prior equally, which would need m = 4.

Why does leave-one-out target encoding still tend to hurt tree-based models even though no row's encoding includes its own label?

  1. It produces values that are too smooth for trees to split on.
  2. Within a level, rows with a positive label get a lower encoding than rows with a negative label, so the encoded value reveals the label to a flexible model.
  3. It uses too little data per level.
  4. It cannot be applied to regression targets.
Removing the row's own label makes the level mean fall for positives and rise for negatives. Inside a level the encoding takes just two values, one per label. A model that can split within a level reads the label off it. The values are not smooth or sparse in any way that matters here, and the method does extend to regression; the problem is the reversed relationship, not the data volume.

A churn model uses "orders in the 30 days around the prediction date" (15 days before, 15 days after). Offline AUC is 0.91; the pilot gets 0.74. What is the right diagnosis?

  1. The model underfits; add deeper trees.
  2. The pilot sample is too small to trust.
  3. The window includes 15 days after the prediction date, so the feature contained part of the outcome offline; windows must end at the cutoff.
  4. Order counts are unreliable features in general.
A window centred on the cutoff contains the future. Offline the model saw orders that had not happened at prediction time, so the offline number was inflated. Deeper trees would make the gap worse; a small pilot adds noise but not a systematic 0.17 drop; order counts are fine when computed as of the cutoff.

Adding a debt / income ratio column improves a logistic regression a lot and a gradient-boosted tree model a little. What explains the difference?

  1. Trees are always better than linear models, so they have less to gain.
  2. A linear model cannot form a ratio from its inputs, while a tree can approximate it with splits on the two raw columns, so the explicit ratio matters more to the linear model.
  3. Boosted trees ignore numeric columns that are ratios.
  4. The ratio leaks the label into the logistic regression only.
A weighted sum of debt and income is not their ratio, whereas a deep enough ensemble of trees can approximate the ratio's contours at the cost of data and depth. The effect is not universal (a tree may gain a lot when the ratio is subtle and the data small), and there is no leak: the ratio uses only inputs.

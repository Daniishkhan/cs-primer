Interpreting Models

Once a model predicts well, people ask why: which inputs does it rely on, how does it respond to them, and what drove this one decision? This chapter builds the three standard tools (permutation importance, partial dependence and SHAP) from first principles, runs them on a model we understand completely, and then spends equal time on what they cannot tell you.

Why this matters

Explanations serve four jobs: debugging (a model leaning on a leaked column, chapter 14), trust (does it behave sensibly in regions you can check?), communication (a loan officer, clinician or regulator asks for reasons) and discovery (what might be going on in the world?). The first three are well served by the tools in this chapter. The fourth is where people go wrong: an explanation describes the model, not the world, and reading it as a statement about causes leads to confident, mistaken decisions. After this chapter you will be able to compute each explanation from scratch, choose between them, spot the situations in which they mislead (correlated features above all), and say precisely what a given explanation supports.

Three questions, three kinds of explanation

"Interpretability" bundles questions that need different answers. A global explanation describes the model as a whole; a local explanation describes one prediction.

A separate choice is between models that are interpretable by design (a linear model whose coefficients you read, chapter 5; a shallow tree, chapter 8; a sparse rule list) and post-hoc explanations of an opaque model, which is what this chapter mostly covers. Rudin (2019), "Stop explaining black box models for high stakes decisions and use interpretable models instead", argues that for high-stakes decisions the first option should be tried seriously before accepting the second; chapter 4's habit of measuring a simple model first is how you find out what accuracy you would give up.

A model we understand completely

To judge an explanation you need to know the right answer, so we use synthetic data with a known mechanism: 1,500 training and 1,500 test houses, seeded. House price (in thousands of pounds) grows with floor area, and the premium for area is larger near the centre (a built-in interaction); it falls with age up to about 40 years and then rises mildly; a house with area over 120 m² within 5 km of the centre earns an extra premium; and noise of standard deviation 18 is added. There are five columns: area_m2, age_years, dist_centre_km, rooms (area divided by 28, plus noise, rounded, so strongly correlated with area but not a cause of price in the mechanism), and noise (random, unrelated to price). The model is a small neural network (24 tanh units) trained by gradient descent in NumPy; any model with a predict function would do, and every method below treats it as a black box. It reaches R2 0.967 on the training houses and 0.960 on the test houses.

Go deeper optional: the data generator and model code (ex_model.py)

Both scripts below import this module. Save it as ex_model.py. The helpers are those of earlier chapters; the network is a plain one-hidden-layer regression net with momentum.

import numpy as np
names = ["area_m2", "age_years", "dist_centre_km", "rooms", "noise"]
def make(n, rng):
    area = rng.normal(95, 30, n).clip(30, 250)
    age = rng.uniform(0, 80, n)
    dist = rng.gamma(3, 2.5, n)
    rooms = np.round(area / 28 + rng.normal(0, 0.5, n)).clip(1, 9)          # strongly tied to area
    noise = rng.normal(size=n)
    price = (2.4 * area * (1 + 0.8 * np.exp(-dist / 4)) - 0.9 * np.minimum(age, 40) + 0.2 * (age - 40).clip(0) * (age > 40)
             + 15.0 * (area > 120) * (dist < 5) + rng.normal(0, 18, n))      # price in thousands of pounds
    return np.c_[area, age, dist, rooms, noise], price

class MLP:
    def __init__(self, d, h, rng): 
        self.W1 = rng.normal(0, 0.5, (d, h)); self.b1 = np.zeros(h); self.W2 = rng.normal(0, 0.5, h); self.b2 = 0.0
    def forward(self, X):
        A = np.tanh(X @ self.W1 + self.b1); return A, A @ self.W2 + self.b2
def fit_mlp(X, y, h=24, epochs=3000, lr=0.02, seed=0):
    rng = np.random.default_rng(seed)
    mu, sd = X.mean(0), X.std(0); ym, ys = y.mean(), y.std()
    Z = (X - mu) / sd; t = (y - ym) / ys
    m = MLP(X.shape[1], h, rng)
    ps = [m.W1, m.b1, m.W2]; vel = [np.zeros_like(p) for p in ps]; vb = 0.0
    for e in range(epochs):
        A, out = m.forward(Z); err = (out - t) / len(t)
        gW2 = A.T @ err; gb2 = err.sum(); dA = np.outer(err, m.W2) * (1 - A ** 2)
        grads = [Z.T @ dA, dA.sum(0), gW2]
        for i, (p, g) in enumerate(zip(ps, grads)):
            vel[i] = 0.9 * vel[i] - lr * g * 10; p += vel[i]
        vb = 0.9 * vb - lr * gb2 * 10; m.b2 += vb
    return lambda Xn: m.forward((Xn - mu) / sd)[1] * ys + ym
def r2(y, p): return 1 - np.sum((y - p) ** 2) / np.sum((y - y.mean()) ** 2)

A word on the impurity-based importance that tree ensembles report by default (the "feature importances" attribute in scikit-learn forests and boosted trees): it sums the impurity reduction from every split on a feature. It is free, but it is computed on training data, so an overfit model can credit pure noise, and it favours features with many distinct values (Strobl et al., 2007, "Bias in random forest variable importance measures"). Treat it as a rough first look, and prefer the held-out methods below.

Permutation importance

The idea is the simplest in the field: permutation importance measures how much a feature matters by destroying the information in it and seeing how much worse the model gets. Take held-out data, score the model, then shuffle one column (breaking its link to the target and to the other columns, while keeping its distribution) and score again. The increase in error is the importance of that feature. Repeat the shuffle several times to average out luck. Breiman (2001) introduced it for random forests; Fisher, Rudin and Dominici (2019) generalised it to a "model reliance" for any model.

Analogy: swapping an ingredient

To find out how much a recipe depends on the butter, you could replace the butter in each cake with butter taken from a random other cake, then taste. If the cakes are barely different, the recipe did not really use the butter. If they are ruined, it did. Permutation importance is that taste test, done with the model's error as the taster.

Where it breaks down: in a real kitchen the ingredients are chosen together. Swap the sugar of a chocolate cake with the sugar of a lemon tart and you may taste a failure caused by the odd pairing, not by the sugar. Shuffled data rows can be combinations that never occur, and a model asked about them is being asked about territory it was never trained for.

The first half of the script computes the importance on the test houses, 20 shuffles per feature, as the increase in RMSE. The second half is the trap: it adds a column, area_sqft, which is area_m2 converted to square feet, a perfectly redundant twin. The network is refit, and the importances are recomputed.

"""Permutation importance on held-out data, and what correlated features do to it."""
import numpy as np
from ex_model import *
rng = np.random.default_rng(16)
Xtr, ytr = make(1500, rng); Xte, yte = make(1500, rng)
f = fit_mlp(Xtr, ytr)
print(f"R^2 train {r2(ytr, f(Xtr)):.3f}, test {r2(yte, f(Xte)):.3f}; RMSE test {np.sqrt(np.mean((yte - f(Xte)) ** 2)):.1f} (thousand pounds)")

def perm_importance(f, X, y, repeats=20, seed=0):
    r = np.random.default_rng(seed); base = np.sqrt(np.mean((y - f(X)) ** 2)); out = []
    for j in range(X.shape[1]):
        d = []
        for _ in range(repeats):
            Xp = X.copy(); Xp[:, j] = r.permutation(Xp[:, j])
            d.append(np.sqrt(np.mean((y - f(Xp)) ** 2)) - base)       # increase in RMSE when column j is shuffled
        out.append((np.mean(d), np.std(d)))
    return out
print(f"\n{'feature':<16}{'RMSE increase when shuffled (test)':>38}")

Xtr2 = np.c_[Xtr, Xtr[:, 0] * 10.764]; Xte2 = np.c_[Xte, Xte[:, 0] * 10.764]
f2 = fit_mlp(Xtr2, ytr, seed=3)

names2 = names + ["area_sqft"]
print(f"{'feature':<16}{'RMSE increase when shuffled (test)':>38}")
for n, (m, s) in zip(names2, perm_importance(f2, Xte2, yte)):
    print(f"{n:<16}{m:>30.2f} +/- {s:.2f}")
# Shuffle the twins together (a group)

for _ in range(20):

    d.append(np.sqrt(np.mean((yte - f2(Xp)) ** 2)) - base)

For the first model the ranking matches the mechanism: shuffling area_m2 adds 98.2 to the RMSE, dist_centre_km 34.6, age_years 4.4, while rooms (1.7) and noise (−0.02, zero within the ± 0.12 shuffle-to-shuffle noise) barely matter. The model learned that rooms adds nothing once area is known.

Now the twin. Test R2 barely changes (0.961), but the importances do: area_sqft gets 122.3 while area_m2, the original, drops to 16.6. The network happened to build its function mostly on one copy. A reader of that table would conclude that floor area in square metres hardly matters and square feet matters enormously, when they are the same information. Shuffling one twin alone also produces houses whose two area columns disagree, which the model never saw. The honest repair is to shuffle correlated features together as a group, as the last line does: the pair's joint importance is 97.2, close to the 98.2 of the single original column. With correlated features, importance belongs to the group, not to its members.

Some practical rules for permutation importance. Compute it on held-out data: on training data an overfit model assigns weight to features it merely memorised. Use a metric that matches the use (RMSE, average precision, log loss). Report the spread over shuffles. Group correlated columns. And remember what it measures: how much this particular fitted model relies on the feature, not how much the feature matters in nature. A feature the model ignores in favour of a correlated twin gets a low score even if it carries real information.

Partial dependence and ICE: how the prediction responds

Importance says how much a feature matters, not how. Partial dependence (Friedman, 2001, in the gradient boosting paper) shows the shape. To draw the curve for distance to the centre: pick a value (say 3 km), set the distance of every house in the data to 3, run the model on all of them, and average the predictions. Repeat over a grid of values and plot average prediction against value. The average removes the influence of the other features (as far as an average can), leaving the model's average response to this one.

An average can hide a lot. Individual conditional expectation (ICE) curves (Goldstein et al., 2015) skip the averaging: one curve per case, showing what the prediction would be for that case as the feature varies, with its other features held fixed. If the curves are parallel, the partial dependence is a fair summary; if they fan out or cross, the average is describing no real case, which signals an interaction. The script prints the partial dependence on distance and the ICE curves for three houses of 60, 95 and 140 square metres.

Exact Shapley values for one prediction

For the question "why 443.7 for this house?" we use Shapley values, borrowed from cooperative game theory (Shapley, 1953). Imagine the features as players who together produce the prediction, and ask how to divide the credit fairly. The Shapley value of feature j is its average marginal contribution over every order in which the features could be "added to the team":

φj = ∑S ⊂ F \ {j} [ |S|! (d − |S| − 1)! / d! ] · ( v(S ∪ {j}) − v(S) )

Here F is the set of d features, S ranges over subsets not containing j, and v(S) is the model's expected output when the features in S are fixed to this case's values and the others are not known. The weight in brackets counts how many orderings put exactly the features of S before j. Three properties make this the unique fair split (Shapley's axioms): efficiency (the contributions add up to the prediction minus the baseline), symmetry (features that play identical roles get equal credit) and the dummy property (a feature that never changes anything gets zero).

What does "the others are not known" mean for a model that needs all its inputs? The common answer (the one used for the "interventional" SHAP of Lundberg and Lee, 2017, "A Unified Approach to Interpreting Model Predictions") is to fill them in from a background sample: average the model's output over background rows with the features in S overwritten by this case's values. Below, v(S) is computed exactly that way, with a 200-house background, and the sum over all 25 = 32 subsets is done by brute force.

First, the partial dependence. The average predicted price falls from 347.4 at 1 km to 206.3 at 16 km, steeply at first (about 54 thousand lost between 1 and 3 km) and almost flat beyond 12 km, which matches the built-in premium that decays like exp(−distance/4). The ICE columns tell the part the average hides: the same move from 1 km to 16 km lowers the 60 m² house's price by 98 thousand, the 95 m² house's by 141 and the 140 m² house's by 181. The curves are far from parallel because the premium multiplies area: the effect of distance depends on size, an interaction a single average curve cannot show.

Now the Shapley values for the 140 m², 78.7-year-old house, 2.7 km from the centre, 5 rooms. The background average prediction is 237.3 and the model says 443.7, a gap of 206.5 to explain. area_m2 accounts for +148.1, dist_centre_km for +64.9, and the other three features together for −6.5 (age −1.8, rooms −1.2, noise −3.5). The efficiency property holds exactly in the last line: contributions sum to +206.5, the same as prediction minus baseline. Note two things. This house is large and central, so its distance contribution (+64.9) is larger than the typical distance effect, because Shapley values share each interaction between the features that take part in it. And noise receives −3.5: this feature has no role in the data-generating mechanism, but the fitted network responds a little to it (permutation importance had it at zero on average, but a particular value of 1.9 nudges one prediction). SHAP explains the model's behaviour, including its quirks.

Cost, approximations and variants

Brute force needs 2d subsets, fine for five features and hopeless for 500. Practical SHAP therefore comes in two forms. KernelSHAP estimates the values by sampling subsets and fitting a weighted linear model (Lundberg and Lee, 2017), model-agnostic but slow and noisy. TreeSHAP (Lundberg et al., 2020, "From Local Explanations to Global Understanding with Explainable AI for Trees") computes exact Shapley values for tree ensembles in polynomial time by walking the trees, which is why SHAP is so common with XGBoost, LightGBM and random forests (chapter 9). Averaging the absolute SHAP values over many rows gives a global importance; plotting each row's value against its feature value gives a dependence plot.

The definition leaves a choice about how to treat the features outside S. The version above, sampling them from the background independently of the features in S, is called interventional or marginal. The alternative, sampling them conditionally on the features in S, respects correlations but credits a feature for information it merely correlates with. Chen, Janizek, Lundberg and Lee (2020), "True to the Model or True to the Data?", discuss the trade-off: the interventional version is true to the model, the conditional version is closer to the data, and neither is "the" explanation.

Common misconception

"The most important feature is the one that causes the outcome." Importance, partial dependence and SHAP describe how a fitted model uses its inputs. A model can rely heavily on a feature because it is a convenient proxy for a cause (hospital ward as a proxy for illness severity), because it is a leak (chapter 14), or because it is a consequence of the outcome. In the running example rooms is correlated with price (through area) but does not cause it; a model that used it would explain just as plausibly, and "add a room to raise the price" would be a false policy conclusion.

What explanations cannot tell you

The tools above are sound arithmetic. The failures come from the claims people attach to them.

  • They describe the model, not the world. If the model is wrong, the explanation faithfully reports a wrong mechanism. It is evidence about the model's reliance; evidence about the world needs separate arguments.
  • They are not interventions. A partial dependence curve says what the model predicts when the feature is set to a value; it does not say what would happen to the outcome if you changed it. Moving "income" in a credit model alters the prediction, not the person's ability to repay. Causal questions need experiments (chapter 21 on A/B tests) or explicit causal assumptions.
  • Correlated features confuse every method. Permutation importance splits credit arbitrarily between twins (shown above); partial dependence and interventional SHAP evaluate the model at combinations like "a 250 m² house with one room" that the data never contains, where the model's behaviour is extrapolation. Accumulated local effects (ALE; Apley and Zhu, 2020, "Visualizing the Effects of Predictor Variables in Black Box Supervised Learning Models") avoid some of this by averaging local differences within narrow slices of the data. Group features when they are one concept.
  • Attributions are not unique. Kumar et al. (2020), "Problems with Shapley-value-based explanations as feature importance measures", show how the chosen value function and the axioms can give attributions that do not match what users assume. Always state the baseline and the value function.
  • Explanations can be gamed. Slack et al. (2020), "Fooling LIME and SHAP", built models that behave biasedly on real inputs yet look innocent to those methods, because the methods query the model on off-distribution points. An explanation produced by the party being audited is evidence, not proof.
  • A plausible story is not a validated one. People find explanations convincing whether or not they are faithful. Adebayo et al. (2018), "Sanity Checks for Saliency Maps", found that several popular image saliency methods gave nearly the same maps for a trained network and for one with randomised weights. The remedy is to test explanation methods the way this chapter does: on a model and data whose truth you know.

Used within these limits, the tools earn their place. A strong, odd feature in the importance ranking is the first clue to a leak. A partial dependence curve with a cliff where there should be a slope is a data-quality clue. A local explanation that cites a protected attribute or its proxy is an audit finding. And an explanation that a domain expert finds absurd is a reason to investigate before shipping.

Systems connection

In production, explanations are an operational interface. Logging the top contributing features with each prediction (structured events) turns a user complaint into a lookup, and comparing attribution distributions week to week is a cheap drift detector: if dist_centre_km suddenly dominates, a feature pipeline probably changed. Remember that explanations also reveal information about the model and its training data, so treat their exposure like any other API surface (data protection and privacy).

Key takeaways

  • Match the tool to the question: permutation importance for global reliance, partial dependence and ICE for shape, SHAP for one prediction. None of them answers a causal question.
  • Permutation importance measures the loss in held-out score when a column is shuffled. With a redundant twin, the credit moved arbitrarily (98.2 for the original, then 16.6 against 122.3 for its copy); shuffle correlated features as a group (97.2).
  • Partial dependence averages; ICE curves show whether the average is representative. Parallel curves mean no interaction, fanning curves mean one (here distance mattered more for larger houses).
  • Shapley values split a prediction fairly among features and sum exactly to prediction minus baseline (+206.5 in the example). They cost 2d evaluations unless the model is a tree ensemble (TreeSHAP) or you accept sampling (KernelSHAP).
  • The choice of baseline and of how to treat absent features changes the answer. State both.
  • An explanation is true to the model, not necessarily to the world. Validate explanation methods on a model with a known mechanism, and prefer an interpretable model when it is accurate enough.

Check your understanding

A model's permutation importance is computed on the training set, and a random-noise column receives a clearly positive score. What is the most likely explanation?

  1. The noise column is secretly predictive.
  2. Permutation importance cannot be computed on training data.
  3. The model has overfit and partly memorised the training rows, including quirks tied to the noise column, so shuffling hurts training performance.
  4. The shuffling was not random.
An overfit model uses whatever helps it reproduce training labels, including noise. Shuffling such a column harms the training score even though it carries no real signal. On held-out data the same shuffle costs nothing, which is why permutation importance should be computed there.

Two features, floor area in m² and floor area in square feet, are both in a model. Permutation importance gives the first a tiny score and the second a huge one. What should you conclude?

  1. The model relies on floor area, but the credit is split arbitrarily between the redundant twins; shuffle them as a group to measure the reliance.
  2. Square feet matter much more than square metres.
  3. The square-metre column can be dropped without loss only if you keep the other one; that proves it is unimportant.
  4. Permutation importance is broken and should not be used.
Shuffling one twin alone leaves the other intact, so the model can still read the information from it; yet which twin the model happened to rely on is an accident of training. The group shuffle measures reliance on the shared information. Calling one twin unimportant is the reading mistake the chapter warns about.

ICE curves for distance to centre are far from parallel: they fan out, with larger houses falling much more steeply than small ones. What does that tell you?

  1. The partial dependence curve is exactly right for every house.
  2. The model is overfitting.
  3. The distance feature is irrelevant.
  4. The effect of distance depends on other features (an interaction), so the single averaged curve describes no individual house well.
Parallel ICE curves would mean the effect of the feature is the same everywhere, so the average would be representative. Fanning shows the effect varies with another feature (here area). It does not mean overfitting, and distance is clearly relevant because every curve moves a lot.

The Shapley values of a prediction are +148.1, +64.9, −1.8, −1.2 and −3.5, and the baseline is 237.3. What is the model's prediction?

  1. Cannot be determined without the model.
  2. About 443.8, because the values sum to the prediction minus the baseline (efficiency).
  3. 206.5, the sum of the values.
  4. 237.3 × 206.5.
Efficiency says the contributions add up to the prediction minus the baseline: 148.1 + 64.9 − 1.8 − 1.2 − 3.5 = 206.5, so the prediction is 237.3 + 206.5 = 443.8 (443.7 in the full-precision calculation). The sum alone is the gap, not the prediction, and the quantities add rather than multiply.

A SHAP analysis of a pneumonia-mortality model shows that "asthma" lowers the predicted risk of death. A colleague proposes advising doctors that asthma is protective. What is the best response?

  1. Accept it: SHAP values reveal causal effects.
  2. Reject the model and use a neural network instead.
  3. Treat it as a model finding to investigate: such patterns can arise from how patients were treated (for example, asthma patients receiving more aggressive care), so the explanation describes the data and model, not a causal effect of asthma.
  4. Remove the feature and retrain without further thought.
This is a well-known cautionary pattern in medical ML (Caruana et al., 2015, reported it for a pneumonia-risk model): a feature can look protective because of treatment decisions or selection in the data. The explanation faithfully reports what the model learned; whether it is causal needs domain knowledge or experiments. Blind removal discards information and does not address the underlying treatment effect.

Why is exact Shapley-value computation impractical for a model with 200 features, and what are the usual workarounds?

  1. It requires evaluating 2200 subsets; use TreeSHAP for tree ensembles or sampling-based KernelSHAP for other models.
  2. It requires labels for every row; use unlabelled data instead.
  3. It is only defined for linear models; use coefficients.
  4. It needs more rows than features; collect more data.
The exact formula sums over all subsets of the other features, which grows exponentially. TreeSHAP exploits tree structure to get exact values in polynomial time; KernelSHAP samples subsets for any model at the cost of noise. Shapley values are defined for any model and need no labels.

Fit and compare models

The first decision in any project is what to compare against. These two cards cover the reference library and the family that wins most tabular problems.

scikit-learn

Install: uv pip install scikit-learn (or pip install scikit-learn) · Import name: sklearn · Alternatives: statsmodels (statistical models with standard errors and tests), SciPy for optimisation and distributions, and the models in the other cards for boosted trees · Chapters: 4, 5, 6, 7, 10, 11, 13

scikit-learn gives every model the same small interface: fit(X, y) learns, predict(X) (or predict_proba) uses what was learned, and transform(X) is what preprocessing steps do. X has shape (n_samples, n_features), y has one entry per row. Because the interface is uniform, a pipeline can chain a scaler and a model into one object, and a cross-validation function can refit that whole object inside each fold, so the scaler never sees validation rows (leakage through preprocessing). The same library holds dummy baselines, metrics, splitters and inspection tools, which is why it is the default workbench.

10-minute guided exercise

Compare a do-nothing baseline, a scaled logistic regression and a histogram gradient-boosting model with five-fold stratified cross-validation, scored by average precision (the right yardstick for a 4% positive rate, chapter 2). Then ask which columns the boosted model actually uses by shuffling each one on held-out rows.

What to look for

  • The dummy model scores 0.040: the positive rate. That is the floor for average precision, not zero. Every other number is a multiple of it (baselines first).
  • The logistic regression beat the boosted trees. The hidden formula is mostly additive, so a simple model is enough; the interaction is too weak to repay the extra flexibility. Do not assume the fancier model wins; the comparison is the point.
  • Permutation importance ranks columns by damage when shuffled: f0, f1 and logins matter, and the other ten noise columns do not. It uses held-out rows, so it measures use, not memorisation (chapter 16).
  • Predict before you run: would you expect the standard deviation across folds to be larger than the gap between the two models? Here the logistic model's lead (0.192 against 0.165) is about the size of the fold spread (0.02 to 0.03), so the honest summary is "no clear winner".

The same contract in plain NumPy (optional). Writing the interface yourself shows why a Pipeline exists: the scaler is fitted inside each fold. Without scaling, my hand-written gradient-descent logistic regression fails on features with very different scales (accuracy 0.48, a coin flip), and with it works (0.81).

"""The scikit-learn contract in 45 lines of NumPy: fit(X, y), predict(X), transform(X), a Pipeline, and a leak-safe k-fold."""
import numpy as np

class StandardScaler:
    def fit(self, X, y=None):
        self.mean_, self.scale_ = X.mean(0), X.std(0) + 1e-12; return self
    def transform(self, X): return (X - self.mean_) / self.scale_

class LogisticRegression:
    def __init__(self, C=1.0, steps=300, lr=0.5): self.C, self.steps, self.lr = C, steps, lr
    def fit(self, X, y):
        self.coef_, self.intercept_ = np.zeros(X.shape[1]), 0.0
        for _ in range(self.steps):
            p = self.predict_proba(X)[:, 1]
            self.coef_ -= self.lr * (X.T @ (p - y) / len(y) + self.coef_ / (self.C * len(y)))
            self.intercept_ -= self.lr * (p - y).mean()
        return self
    def predict_proba(self, X):
        z = np.clip(X @ self.coef_ + self.intercept_, -50, 50); p = 1 / (1 + np.exp(-z)); return np.column_stack([1 - p, p])
    def predict(self, X): return (self.predict_proba(X)[:, 1] > 0.5).astype(int)

class Pipeline:
    def __init__(self, steps): self.steps = steps
    def fit(self, X, y):
        for _, s in self.steps[:-1]: X = s.fit(X, y).transform(X)
        self.steps[-1][1].fit(X, y); return self
    def predict_proba(self, X):
        for _, s in self.steps[:-1]: X = s.transform(X)
        return self.steps[-1][1].predict_proba(X)

def cross_val_accuracy(make_model, X, y, k=5, seed=0):
    idx = np.random.default_rng(seed).permutation(len(y)); folds = np.array_split(idx, k); scores = []
    for i in range(k):
        te, tr = folds[i], np.concatenate(folds[:i] + folds[i + 1:])
        m = make_model().fit(X[tr], y[tr]); scores.append(((m.predict_proba(X[te])[:, 1] > .5) == y[te]).mean())
    return np.array(scores)

rng = np.random.default_rng(0)
X = rng.normal(0, 1, (1000, 3)) * [1, 50, 0.01] + [0, 200, 5]            # three features on very different scales
y = ((X[:, 0] + (X[:, 1] - 200) / 50 + rng.normal(0, 1, 1000)) > 0).astype(int)
for name, make in (("LogisticRegression alone", lambda: Pipeline([("clf", LogisticRegression())])),
                   ("StandardScaler + LogisticRegression", lambda: Pipeline([("scale", StandardScaler()), ("clf", LogisticRegression())]))):
    s = cross_val_accuracy(make, X, y)
    print(f"{name:38s} folds {np.round(s, 3)}  mean {s.mean():.3f}")
LogisticRegression alone               folds [0.465 0.475 0.475 0.485 0.515]  mean 0.483
StandardScaler + LogisticRegression    folds [0.79  0.825 0.83  0.845 0.77 ]  mean 0.812

Common pitfalls

  • Fitting a scaler or encoder on the whole table before splitting leaks validation information. Put preprocessing in the pipeline.
  • cross_val_score shuffles nothing by default for plain integer folds; for rare classes use a stratified splitter, for repeated entities a grouped one, and for time a time-ordered one (chapter 13).
  • predict uses a 0.5 threshold; for rare events use predict_proba and choose the threshold from costs (chapter 15).
  • Defaults are not tuned for your problem. Regularisation strength, tree depth and iteration count matter; set them by validation, not by habit.

XGBoost, LightGBM & CatBoost

Install: uv pip install xgboost lightgbm catboost (macOS: brew install libomp first) · Alternatives: scikit-learn's own HistGradientBoostingClassifier (no extra install, fewer features) · Chapters: 9, 17, 20 · Case: XGBoost as a system

All three libraries build gradient-boosted decision trees: many small trees added one after another, each fitted to the errors of the sum so far (chapter 9). They differ in engineering. XGBoost is the long-standing standard, with a histogram mode, regularisation terms in the objective and a mature ecosystem. LightGBM grows trees leaf by leaf and bins features aggressively, so it is often the fastest on large tables. CatBoost handles categorical columns natively with an ordered scheme that reduces the leakage of naive target encoding (chapter 17) and has strong defaults. On this kind of data their accuracy is usually close; the choice is about speed, categorical handling and what your team already runs.

10-minute guided exercise

Fit all three on the same split, each with early stopping on a validation block, and compare the held-out average precision, the number of trees kept and the time. The 30-level region column is given to each library in the way it prefers (integer codes for XGBoost, a pandas category for LightGBM, strings plus cat_features for CatBoost).

What to look for

  • The three scores are within 0.006 of each other (0.204 to 0.210), smaller than the fold-to-fold spread you saw in the previous card. Do not pick a library from one run; use several seeds or folds.
  • Early stopping chose 172 to 380 trees from a ceiling of 1,000. The validation block, not you, decides how many; the test block stays untouched (validation done right).
  • CatBoost is slowest here and the most accurate by a hair; LightGBM is fastest. Both facts depend on the machine and the data; treat them as a prompt to measure on yours.
  • The boosted models score around 0.205, the logistic regression of the previous card around 0.19, on a different split. Compare models only on the same split and metric.

What makes them fast (optional). A tree needs the best place to split each feature. Trying every value is expensive; the histogram method sorts values into at most 255 bins once, stores each as one byte, and then every round only accumulates gradients into the bins and scans 255 candidates. The script below does one split search both ways on 400,000 values and finds almost the same threshold and gain.

"""Why histogram-based boosting is cheap: bin once, then each round's best split scans 255 bins, not 400,000 values."""
import time, numpy as np
rng = np.random.default_rng(1)
n, rounds = 400_000, 30
x = rng.normal(0, 1, n); y = np.sin(2 * x) + rng.normal(0, 1, n)

t0 = time.perf_counter(); order = np.argsort(x); xs = x[order]                       # exact method: presort once
t_pre_exact = time.perf_counter() - t0
t0 = time.perf_counter(); edges = np.quantile(x, np.linspace(0, 1, 256)[1:-1]); b = np.searchsorted(edges, x).astype(np.uint8)
t_pre_hist = time.perf_counter() - t0                                                 # histogram method: bin once, one byte per value

def exact(g):                                                                         # scan every position of the sorted column
    cs = np.cumsum(g[order])[:-1]; k = np.arange(1, n); gain = cs ** 2 / k + (g.sum() - cs) ** 2 / (n - k)
    return xs[int(gain.argmax())], gain.max()
def hist(g):                                                                          # accumulate gradients into 255 bins, scan the bins
    s, c = np.bincount(b, g, 255), np.bincount(b, minlength=255); cs, cn = np.cumsum(s)[:-1], np.cumsum(c)[:-1]
    gain = cs ** 2 / cn + (g.sum() - cs) ** 2 / (n - cn)
    return edges[int(gain.argmax())], gain.max()

g = y - y.mean(); res = {}
for name, fn in (("exact", exact), ("histogram", hist)):
    t0 = time.perf_counter()
    for r in range(rounds): thr, gain = fn(g * (1 + 0.01 * r) + 0.001 * r)              # a new gradient each round
    res[name] = (time.perf_counter() - t0, thr, gain)
print(f"one-off preparation: exact presort {t_pre_exact*1000:.0f} ms, histogram binning {t_pre_hist*1000:.0f} ms; column bytes {x.nbytes:,} (float64) vs {b.nbytes:,} (uint8)")
for name, (dt, thr, gain) in res.items():
    print(f"{name:10s} {rounds} rounds: {dt*1000:7.1f} ms  ({dt/rounds*1000:5.2f} ms a round)  last threshold {thr:+.4f}  gain {gain:,.0f}")
one-off preparation: exact presort 58 ms, histogram binning 67 ms; column bytes 3,200,000 (float64) vs 400,000 (uint8)
exact      30 rounds:   164.7 ms  ( 5.49 ms a round)  last threshold -0.0048  gain 175,412
histogram  30 rounds:    81.9 ms  ( 2.73 ms a round)  last threshold -0.0067  gain 175,359

The histogram search is about twice as fast per round here for one feature, and the byte-sized column uses an eighth of the memory; the gap grows with rows and features, and a real library also subtracts a child's histogram from its parent's to avoid half the work. The gain is nearly identical, which is why the approximation costs little accuracy (the XGBoost case covers the other engineering tricks).

Common pitfalls

  • Tuning on the test set. Early stopping needs a validation set separate from the final test.
  • Numeric codes for categories. Passing arbitrary integer codes implies an order that does not exist; use each library's categorical support or a safe encoding.
  • Learning rate and tree count go together. Halving the rate needs roughly twice the trees; fix a small rate and let early stopping set the count.
  • Imbalance. Reweighting positives changes the scores' meaning; recalibrate afterwards (chapter 15).

Explain a model

Explanations are tools for debugging and communication, not proof of cause. Use them with the cautions in the chapter.

SHAP

Install: uv pip install shap · Alternatives: permutation importance and partial dependence (both in scikit-learn's inspection module), the built-in contribution outputs of XGBoost, LightGBM and CatBoost, InterpretML · Chapters: 16

SHAP (Lundberg and Lee, 2017, "A Unified Approach to Interpreting Model Predictions") splits one prediction into a baseline plus one contribution per feature, using Shapley values from cooperative game theory: each feature's contribution is its average marginal effect over all orders in which features could be revealed. The contributions add up exactly to the difference between this prediction and the average one. For tree ensembles, shap.TreeExplainer computes them quickly and exactly; for other models there are slower sampling-based explainers. The result is an Explanation object with .values (one row per example, one column per feature), .base_values and .data.

10-minute guided exercise

Fit a LightGBM model, explain the held-out rows, verify the additivity property, then read the explanation globally (mean absolute contribution) and locally (the riskiest row).

import numpy as np, lightgbm, shap
from sklearn.inspection import permutation_importance
from tb_data import make

X, y = make(); Xn = X.drop(columns="region")
tr, te = slice(0, 30_000), slice(30_000, 40_000)
model = lightgbm.LGBMClassifier(n_estimators=170, learning_rate=0.05, num_leaves=15, verbose=-1).fit(Xn[tr], y[tr])
print("shap", shap.__version__)
explainer = shap.TreeExplainer(model)
sv = explainer(Xn[te])                                                        # an Explanation: .values, .base_values, .data
values = sv.values if sv.values.ndim == 2 else sv.values[:, :, 1]
raw = model.predict(Xn[te], raw_score=True)                                    # the model's log-odds
gap = np.abs(values.sum(1) + sv.base_values - raw).max()
print(f"additivity: base value + sum of SHAP values equals the log-odds to within {gap:.1e}")

order = np.argsort(-np.abs(values).mean(0))[:5]
print("\nglobal view: mean |SHAP| (log-odds units)")
for i in order: print(f"  {Xn.columns[i]:8s} {np.abs(values[:, i]).mean():.3f}")

i = int(np.argmax(raw)); print(f"\nlocal view: the highest-risk row in the test set (log-odds {raw[i]:+.2f}, base value {float(np.ravel(sv.base_values)[i]):+.2f})")
for j in np.argsort(-np.abs(values[i]))[:4]: print(f"  {Xn.columns[j]:8s} = {Xn.iloc[30_000 + i, j]:7.2f}   pushes log-odds {values[i, j]:+.2f}")

What to look for

  • Additivity holds to 1e-14. Base value plus the sum of a row's SHAP values reproduces the model's log-odds; use this as a sanity check on any explanation pipeline. The units are log-odds, not probability.
  • The global ranking puts f0, f1 and logins first, matching the permutation importance in the scikit-learn card. Two methods agreeing is reassuring; disagreement would be a prompt to look for correlated features.
  • The local view says what pushed this row up, not what would change the outcome. An explanation of a model is not an explanation of the world: logins being low is associated with churn in the data, and raising it may not help (chapter 16).
  • Plots (not run here, since they need a display): shap.plots.beeswarm(sv) for the global picture with direction, and shap.plots.waterfall(sv[i]) for one row.

The definition by brute force (optional). For four features you can compute exact Shapley values by trying every subset of features: fix the features in the subset to this customer's values, average the model over background rows for the rest, and weight the marginal effects. This is exactly what the library avoids for models with many features.

"""Exact Shapley values for one prediction of a small model, by trying every coalition of features. This is what SHAP approximates."""
import itertools, math, numpy as np
rng = np.random.default_rng(3)
names = ["logins_14d", "tickets_30d", "tenure_months", "payment_failed"]
background = np.column_stack([rng.poisson(5, 500), rng.poisson(0.5, 500), rng.gamma(2, 9, 500), rng.random(500) < 0.05]).astype(float)
w, b = np.array([-0.30, 0.45, -0.03, 1.1]), -0.4
f = lambda X: 1 / (1 + np.exp(-(X @ w + b)))                              # a fixed logistic model: P(churn)

x = np.array([1.0, 3.0, 4.0, 1.0])                                         # one customer: few logins, tickets, new, failed payment
n = len(x)
def value(S):
    """Expected prediction when the features in S are fixed to x and the rest are drawn from the background rows."""
    Z = background.copy(); Z[:, list(S)] = x[list(S)]; return f(Z).mean()

phi = np.zeros(n)
for i in range(n):
    for r in range(n):
        for S in itertools.combinations([j for j in range(n) if j != i], r):
            weight = math.factorial(r) * math.factorial(n - r - 1) / math.factorial(n)
            phi[i] += weight * (value(S + (i,)) - value(S))
base, pred = value(()), f(x[None, :])[0]
print(f"average prediction over background: {base:.4f}   prediction for this customer: {pred:.4f}")
for nm, v in zip(names, phi): print(f"  {nm:15s} x = {x[names.index(nm)]:5.1f}   contribution {v:+.4f}")
print(f"sum of contributions {phi.sum():+.4f}  =  prediction - average {pred - base:+.4f}")
print(f"coalitions evaluated: {sum(math.comb(n - 1, r) for r in range(n)) * n} for {n} features; for 40 features each feature would need 2^39 = {2**39:,} coalitions")

Common pitfalls

  • Correlated features share credit in ways that depend on the background data; do not read a single number as the feature's "true" effect.
  • Choosing the background matters. Contributions are relative to a reference population; say which.
  • Explanations can leak or mislead stakeholders. A neat waterfall plot invites a causal reading it does not support, and detailed reasons given to adversaries (for example fraudsters) help them evade.

Track experiments and learn from others

Results are only useful if you can find them again and trust the comparison.

MLflow & Weights & Biases

Install: uv pip install mlflow (open source, runs locally or on your own server); uv pip install wandb (hosted service with a free tier for individuals; check its current terms) · Alternatives: DVC (data and experiment versioning in git), TensorBoard (curves for deep learning), or a plain JSON-lines file, as in the NumPy script below · Chapters: 13, 21

An experiment tracker stores, for every training run, the parameters you set, the metrics you measured, artefacts (the model file, plots) and the context (code version, data version, time). A comparison table across runs then answers "which configuration was best, and can I reproduce it?". MLflow also has a model registry and a standard packaging format; Weights & Biases emphasises live charts, sweeps and team dashboards. For a person working alone, the table of runs is the main value (chapter 13 on why a leaderboard of your own tries needs care).

What a tracker records, in 30 lines (optional). Appending one JSON line per run gives the core of the idea: parameters, metrics and a fingerprint of the data. The script fits ridge regression at six regularisation strengths and prints the leaderboard.

"""What an experiment tracker records, in 30 lines: parameters, metrics, a data fingerprint and a code version per run."""
import hashlib, json, time, numpy as np
rng = np.random.default_rng(0)
X = rng.normal(0, 1, (400, 8)); w = np.array([3, -2, 1, 0, 0, 0, 0.5, 0]); y = X @ w + rng.normal(0, 2, 400)
Xtr, ytr, Xva, yva = X[:300], y[:300], X[300:], y[300:]
data_hash = hashlib.sha256(X.tobytes() + y.tobytes()).hexdigest()[:10]

def log_run(path, params, metrics):
    run_id = sum(1 for _ in open(path)) + 1
    rec = {"run": run_id, "time": round(time.time()), "data": data_hash, "params": params, "metrics": metrics}
    open(path, "a").write(json.dumps(rec) + "\n")

open("runs.jsonl", "w").close()
for lam in (0.0, 0.1, 1.0, 10.0, 100.0, 1000.0):
    beta = np.linalg.solve(Xtr.T @ Xtr + lam * np.eye(8), Xtr.T @ ytr)
    rmse = lambda A, b: float(np.sqrt(np.mean((A @ beta - b) ** 2)))
    log_run("runs.jsonl", {"model": "ridge", "lambda": lam}, {"train_rmse": round(rmse(Xtr, ytr), 3), "val_rmse": round(rmse(Xva, yva), 3)})

runs = [json.loads(l) for l in open("runs.jsonl")]
print(f"{'run':>3} {'lambda':>7} {'train':>7} {'val':>7}  data")
for r in sorted(runs, key=lambda r: r["metrics"]["val_rmse"]):
    print(f"{r['run']:3d} {r['params']['lambda']:7g} {r['metrics']['train_rmse']:7.3f} {r['metrics']['val_rmse']:7.3f}  {r['data']}")

Common pitfalls

  • Logging only the winner. Selecting the best of fifty runs by validation score inflates it; keep all runs and keep a final test set you touch once.
  • Not logging the data version or seed, so a good run cannot be reproduced.
  • Secrets in parameters. Tracking servers are shared; never log keys or personal data (data protection).

10-minute guided exercise

First, the part that needs no account: see why a public leaderboard is not the truth. The script scores 2,000 submissions of pure noise on a 30% public subset and tracks the best one by public score, then reports the same submission's score on the hidden 70%.

"""Overfitting a public leaderboard: 2,000 submissions of pure noise, picked by their public score."""
import numpy as np
rng = np.random.default_rng(7)
n, public_share = 3_000, 0.3
y = (rng.random(n) < 0.5).astype(int)
public = rng.random(n) < public_share                                      # the rows whose score is shown during the competition
def auc(y, s):
    r = np.argsort(np.argsort(s)) + 1; n1 = y.sum()
    return (r[y == 1].sum() - n1 * (n1 + 1) / 2) / (n1 * (len(y) - n1))
print(f"public rows {public.sum():,}, private rows {(~public).sum():,}; every submission is random noise (true AUC 0.5)")
best_pub, best_priv, best_i = 0, 0, 0
for i in range(1, 2001):
    s = rng.random(n); a, b = auc(y[public], s[public]), auc(y[~public], s[~public])
    if a > best_pub: best_pub, best_priv, best_i = a, b, i
    if i in (1, 10, 100, 2000): print(f"after {i:5d} submissions: best public AUC {best_pub:.4f} (submission {best_i}), its private AUC {best_priv:.4f}")

What to look for

  • Noise reached a public AUC of 0.562 after 2,000 tries, while its private AUC was 0.506, essentially chance. Selecting by a small public subset selects luck. This is why winners trust their own cross-validation and why the final ranking uses the hidden rows (chapter 20).
  • After 100 submissions the best public score looks like skill (0.545), yet its private score is 0.497. A few modest submissions will not do this to you; many submissions chosen by public score will.
  • On a real competition, read the rules on external data and team merging, build a local validation that mirrors the public/private split, and read the discussion forum for leaks before you model (case 6).

Common pitfalls

  • Optimising the leaderboard instead of the problem: giant ensembles that win by a fourth decimal place and could never be deployed (the Netflix Prize).
  • Treating free GPU time as unlimited. Quotas and session limits apply and change; check the current ones.
  • Sharing the account token. The API token acts as you; keep it out of notebooks you publish.

Monitor after launch

A model is only as good as the data it sees now. Monitoring turns "the world changed" from a post-mortem into an alert.

Drift monitoring tools

Install: uv pip install evidently (open source; the exercise uses 0.7.23) · Alternatives: NannyML, Alibi Detect, whylogs, Deepchecks, or a few lines of NumPy as below; managed platforms from the major clouds · Chapters: 21 · Case: Google Flu Trends

Data drift means the distribution of inputs in production differs from the training data. A drift tool compares a reference table (usually the training or a recent good period) with a current one, column by column, using a statistical test or a distance, and summarises how many columns moved. Evidently builds such reports and can also compute prediction drift, data-quality checks and, when labels arrive, model-quality metrics. Drift is a symptom: inputs can shift without hurting accuracy, and accuracy can fall with no input shift (the relationship changed). It tells you where to look.

10-minute guided exercise

What to look for

  • Two of four columns drifted (share 0.5), the two I changed; logins_14d (0.038) and region (0.010) are far below the 0.1 threshold. A tool that flags the right columns and not the others is doing its job; one that flags everything gets ignored.
  • Different columns use different measures: a normalised Wasserstein distance for the numeric ones, Jensen-Shannon distance for the categorical-like ones, each against a threshold of 0.1 by default. The method is printed in the metric name; know what yours is measuring.
  • Open drift.html (3.8 MB, a standalone file) to see per-column distributions side by side. A distance does not tell you whether the shift matters for the model: check the columns the model relies on (SHAP or permutation importance) first.

The same check by hand (optional). The population stability index (PSI) bins the reference column into deciles and sums (current share − reference share) × ln(current share / reference share) over bins. The Kolmogorov-Smirnov statistic is the largest gap between the two cumulative distributions. Both fit in a few lines of NumPy.

"""What a drift report computes: the population stability index (PSI) and a two-sample KS statistic, per feature, by hand."""
import numpy as np
rng = np.random.default_rng(5)
n = 20_000
ref = {"logins_14d": rng.poisson(5, n).astype(float), "tenure_months": rng.gamma(2, 9, n), "plan_price": rng.choice([8., 12., 20.], n, p=[.5, .35, .15])}
cur = {"logins_14d": rng.poisson(5, n).astype(float),              # unchanged
       "tenure_months": rng.gamma(2, 9, n) * 0.6,                  # younger customers: an acquisition campaign
       "plan_price": rng.choice([8., 12., 20.], n, p=[.2, .3, .5])}   # a price-tier shift

def psi(a, b, bins=10):
    edges = np.unique(np.quantile(a, np.linspace(0, 1, bins + 1))); edges[0], edges[-1] = -np.inf, np.inf
    pa = np.histogram(a, edges)[0] / len(a) + 1e-6; pb = np.histogram(b, edges)[0] / len(b) + 1e-6
    return float(((pb - pa) * np.log(pb / pa)).sum())

def ks(a, b):
    grid = np.sort(np.concatenate([a, b]))
    return float(np.abs(np.searchsorted(np.sort(a), grid, side="right") / len(a) - np.searchsorted(np.sort(b), grid, side="right") / len(b)).max())

print(f"{'feature':15s} {'ref mean':>9s} {'cur mean':>9s} {'PSI':>7s} {'KS':>6s}  reading")
for k in ref:
    p, d = psi(ref[k], cur[k]), ks(ref[k], cur[k])
    print(f"{k:15s} {ref[k].mean():9.2f} {cur[k].mean():9.2f} {p:7.3f} {d:6.3f}  {'stable' if p < 0.1 else 'watch' if p < 0.25 else 'shifted'}")
# the trap: a shift in a feature does not say the model is worse
print("\nPSI < 0.1 'stable', 0.1 to 0.25 'watch', > 0.25 'shifted' is a rule of thumb from credit scoring, not a law.")

The rule-of-thumb labels (below 0.1 stable, above 0.25 shifted) come from credit scoring practice and are conventions, not laws; set thresholds from the cost of a false alarm and the cost of a missed shift.

Common pitfalls

  • Alert fatigue. With dozens of columns, some will drift by chance each week. Alert on the model's prediction distribution and on important columns, and review the rest weekly.
  • Drift is not a performance drop. Labels may arrive weeks late (see the fraud studio), so monitor inputs and scores in the meantime and compute real quality as labels mature.
  • The reference window. A reference that already contains an anomaly makes everything look normal; choose it deliberately and refresh it when you retrain.
  • Personal data in reports. HTML reports embed sample values; treat them like the data they come from.

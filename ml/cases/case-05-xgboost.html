XGBoost: A System, Not Just an Algorithm

By 2015 a gradient-boosting library called XGBoost appeared in a large share of the published winning solutions on Kaggle. The mathematics underneath was already ten years old. What the 2016 paper by Tianqi Chen and Carlos Guestrin added was engineering: how to scan sparse data, how to read memory in an order the CPU cache likes, and how to train on data that does not fit in RAM. The case is about why that engineering, not a new loss function, is what made the method a favourite.

What I could and could not read

I read the paper itself, Chen and Guestrin, "XGBoost: A Scalable Tree Boosting System" (arXiv 1603.02754, the 2016 KDD paper). The HTML version was fetched through a tool that summarises long pages, so the section, table and figure numbers below are as that tool reported them, and I quote only short passages. I also read the current XGBoost documentation on external memory and the 3.0.0 release notes. I did not read the XGBoost source code, any independent re-run of the paper's benchmarks, or the Kaggle blog posts behind the "17 of 29" count, so every speed-up in this page is the authors' own measurement on their hardware in 2015 or 2016. The timings in my scripts are from my laptop and are my own; they show mechanisms, not the paper's numbers.

The pattern in one sentence

When two methods optimise nearly the same objective, the one that makes better use of sparsity, memory layout and storage can win in practice, because it can be tuned, cross-validated and ensembled many more times in the same afternoon.

Context: a library that kept appearing in the winners' write-ups

The previous chapter on random forests and gradient boosting explains the algorithm: fit a tree to the errors of the current ensemble, add it with a small weight, repeat. Jerome Friedman published gradient boosting machines in 2001. By the mid-2010s many libraries implemented it, including one in scikit-learn and one in R (gbm). XGBoost, in the paper's words, is "a scalable end-to-end tree boosting system".

The paper opens with a claim about adoption. "Among the 29 challenge winning solutions published at Kaggle's blog during 2015, 17 solutions used XGBoost." A footnote, as the summarising tool reported it, says these are the top three teams per competition. The paper adds that eight of those used XGBoost alone, that the second most popular method, deep neural networks, appeared in 11 solutions, and that in the KDD Cup 2015 every team in the top 10 used XGBoost. Read this with care: it counts published solutions, so it carries a selection effect (teams that write up their work are not a random sample), and it says "used", not "was the deciding factor". It still tells us the library was a default choice for tabular problems in that period, which is consistent with how competitions are won.

The question for this case is the one the paper itself raises: what did the authors build that the existing implementations did not have? They list four contributions: a scalable end-to-end system, a weighted quantile sketch for proposing split points, a sparsity-aware algorithm for parallel tree learning, and a cache-aware block structure for out-of-core learning. All but the quantile sketch are about how the computer is used, and those are where this page spends its time.

Gradient boosting
Building an ensemble of trees one at a time, each fitted to the gradient of the loss with respect to the current predictions.
Split finding
The inner loop of tree training: for a node, try candidate thresholds on each feature and keep the one that most improves the objective.
Sparse data
A table where most entries are zero or missing. One-hot encoding a categorical column with 50 levels creates 50 columns, 49 of which are zero in each row.
Default direction
XGBoost's rule for rows whose value for a feature is missing: each split stores a branch (left or right) to which such rows are sent, learned from the data.
Cache miss
A memory read that the small, fast CPU cache cannot answer, so the CPU waits for slower main memory. Reading memory in order avoids most of them.
Out-of-core
Training with the data kept on disk and streamed through memory in pieces, because it is bigger than RAM.

What the algorithm needs from the machine

The learning objective is the one from the boosting chapter plus a penalty. For a set of trees fk, the paper's regularised objective is the sum of the loss over examples plus the sum over trees of Ω(f) = γT + ½λ‖w‖2, where T is the number of leaves and w the vector of leaf weights. The paper notes that with the penalty set to zero this "falls back to the traditional gradient tree boosting". The penalty is useful, but it is a few lines in a formula. It does not explain why people reached for the library.

What does cost time is the inner loop. To choose a split, the algorithm keeps for each row the first and second derivatives of the loss, gi and hi (the derivatives chapter in A0 covers where they come from). For a candidate threshold it needs GL and HL, the sums of g and h for rows on the left, and then the gain

gain = ½ [ GL2/(HL+λ) + GR2/(HR+λ) − (GL+GR)2/(HL+HR+λ) ]

To evaluate every threshold on one feature in one pass, the rows must be visited in sorted order of that feature while the running sums GL and HL grow. So the cost of training is dominated by three things: how many entries are visited, how long it takes to fetch each one's gradient, and how long it takes to bring the data to the CPU at all. Those map onto the three techniques below.

Problem 1: sparse data, and the learned default direction

Real tabular data is full of holes. A column may be blank for some customers. A categorical column with 50 levels, after one-hot encoding, is 50 columns of which exactly one is non-zero per row. The paper names three causes: missing values, frequent zero entries in the statistics, and the by-products of feature engineering such as one-hot encoding.

The obvious way to cope is to impute a value (the mean, or zero) and then treat the matrix as dense. That costs time, because every row is visited for every feature, and it hides information, because "was missing" is not the same as "was zero". XGBoost's answer, in Section 3.4, is to give each split a default direction. When a value is missing, "the instance is classified into the default direction", and the optimal default directions are "learnt from the data". To learn it, the algorithm scans the non-missing entries in ascending order with the missing rows assumed to go right, then scans them in descending order with the missing rows assumed to go left, and keeps the better of the two. The paper's Algorithm 3 visits only non-missing entries, so its cost is linear in the number of non-missing entries.

The first script reproduces the choice on that six-row toy. The second implements the two ways of scanning for the best split over a larger sparse matrix: a naive one that touches every row of every column, and a sparsity-aware one that touches only the present entries. Both are my own NumPy code, not XGBoost's.

import numpy as np

nan = np.nan
x = np.array([0.2, 0.5, 1.4, nan, nan, 2.0])        # two of six values are missing
g = np.array([-1.0, -0.8, 0.9, 1.1, 1.0, 0.8])      # gradients; hessians are all 1
lam, G, H = 1.0, g.sum(), 6.0

def gain(GL, HL):
    GR, HR = G - GL, H - HL
    return 0.5 * (GL**2/(HL+lam) + GR**2/(HR+lam) - G**2/(H+lam))

present = ~np.isnan(x)
left = present & (x < 1.0)                           # candidate split: x < 1.0
GL, HL = g[left].sum(), left.sum()
GM, HM = g[~present].sum(), (~present).sum()
print(f"present rows going left: {left.sum()}, missing rows: {HM}, G_missing = {GM:.1f}")
print(f"missing -> left : gain = {gain(GL + GM, HL + HM):.3f}")
print(f"missing -> right: gain = {gain(GL, HL):.3f}")
present rows going left: 2, missing rows: 2, G_missing = 2.1
missing -> left : gain = 0.205
missing -> right: gain = 1.698

The two missing rows have large positive gradients (their targets are low), so they behave like rows 3 and 6 and the algorithm sends them right, where the gain is eight times larger. Nothing was imputed: the data told the tree which side the unknowns resemble.

import time
import numpy as np

rng = np.random.default_rng(7)
n, m, density, lam = 50_000, 200, 0.02, 1.0

# A sparse, one-hot-like matrix: NaN means "missing / not present".
X = np.full((n, m), np.nan)
present = rng.random((n, m)) < density
X[present] = rng.normal(size=present.sum())
y = np.nan_to_num(X[:, :5]).sum(axis=1) + rng.normal(0, 0.3, n)
g, h = -y, np.ones(n)            # squared error from prediction 0: g = pred - y, h = 1
G, H = g.sum(), h.sum()

def gain(GL, HL):
    GR, HR = G - GL, H - HL
    ok = (HL > 0) & (HR > 0)
    out = np.full(GL.shape, -np.inf)
    out[ok] = 0.5 * (GL[ok]**2/(HL[ok]+lam) + GR[ok]**2/(HR[ok]+lam) - G**2/(H+lam))
    return out

def best(gs, hs, gm, hm):
    """Scan sorted entries; try missing values going right, then left."""
    cg, ch = np.cumsum(gs), np.cumsum(hs)
    gr, gl = gain(cg, ch), gain(cg + gm, ch + hm)
    return (gr.max(), "right", gr.argmax()) if gr.max() >= gl.max() else (gl.max(), "left", gl.argmax())

def naive():                      # visits all n rows of every column
    res = []
    for j in range(m):
        order = np.argsort(X[:, j])                 # NaN sorts last
        miss = np.isnan(X[order, j])
        gs, hs = np.where(miss, 0, g[order]), np.where(miss, 0, h[order])
        gm, hm = g[order][miss].sum(), h[order][miss].sum()
        res.append((*best(gs, hs, gm, hm), j))
    return max(res)

t0 = time.perf_counter()
blocks = []                       # built once: per column, sorted non-missing (value, g, h)
for j in range(m):
    rows = np.flatnonzero(~np.isnan(X[:, j])); o = rows[np.argsort(X[rows, j])]
    blocks.append((g[o], h[o], g[rows].sum(), h[rows].sum()))

build_ms = (time.perf_counter() - t0) * 1000

def sparse():                     # visits only the non-missing entries
    res = []
    for j, (gs, hs, gp, hp) in enumerate(blocks):
        res.append((*best(gs, hs, G - gp, H - hp), j))
    return max(res)

for f in (naive, sparse):
    t = time.perf_counter(); r = f(); dt = time.perf_counter() - t
    print(f"{f.__name__:7s} gain={r[0]:.3f} missing->{r[1]:5s} feature={r[3]} time={dt*1000:7.1f} ms")
print(f"entries scanned: naive {n*m:,}  sparse {int(present.sum()):,}  ratio {n*m/present.sum():.0f}x")
print(f"one-off cost of building the sorted blocks: {build_ms:.1f} ms")
naive   gain=224.077 missing->right feature=1 time=  556.3 ms
sparse  gain=224.077 missing->right feature=1 time=   11.8 ms
entries scanned: naive 10,000,000  sparse 199,834  ratio 50x
one-off cost of building the sorted blocks: 31.4 ms

Both versions find the identical best split (same feature, same gain, same default direction), so the sparse scan loses nothing. It visits 199,834 entries instead of 10,000,000, and it is about fifty times faster in this run. The ratio of entries is almost exactly 1 divided by the density I chose (2 per cent), which is why it lands near the paper's reported "50 times faster" on Allstate-10K; that is a coincidence of my parameter, not a reproduction of their benchmark. Notice also the line at the bottom: the sorted blocks cost something to build once. That leads to the second problem.

Common misconception

"XGBoost wins because boosting with second-order information is a better learning algorithm than the older kind." The paper's own list of contributions is mostly about systems, and its comparison in Table 3 (500 trees on one million rows of the Higgs dataset) shows XGBoost and scikit-learn with test AUCs of 0.8304 and 0.8302 while the time per tree differs from 0.68 to 28.5 seconds. Same model quality, very different cost. The advantage is that you can afford to try more settings, more folds and more seeds, which is what competition winners describe doing.

Problem 2: sorting, and the cost of reading memory in the wrong order

Split finding needs rows in sorted order of each feature. Sorting at every node is wasteful, because the order of rows by a feature does not change as the tree grows. Section 4.1 stores the data in blocks "in the compressed column (CSC) format, with each column sorted by the corresponding feature value", computed "only once before training" and reused. The paper gives the complexity of the original sparsity-aware algorithm as O(K d‖x‖0 log n) and with blocks as O(K d‖x‖0 + ‖x‖0 log n), where K is the number of trees, d the maximum depth and ‖x‖0 the number of non-missing entries. The sort moves out of the loop: it becomes a "one time preprocessing cost that can be amortized".

That fixes the arithmetic but creates a memory problem, which is the paper's Section 4.2. After sorting a column by value, the row numbers are in scrambled order. The gradient statistics are stored by row. So walking down the sorted column means reading g[row] at scattered addresses: "a non-continuous memory access". When those statistics do not fit in the CPU cache, the paper says, this "slows down split finding" through cache misses. The remedy is to allocate "an internal buffer in each thread", fetch the gradient statistics into it, and accumulate from the buffer in mini-batches. For the approximate algorithm, the paper tests block sizes and concludes that 216 examples per block balances cache behaviour against parallelism. It reports that for the exact greedy algorithm the cache-aware version is "twice as fast as the naive version when the dataset is large".

Analogy: the filing cabinet

You have 8 million folders stored in the order they arrived. A list tells you to process them in alphabetical order of customer name. Following the list means walking back and forth across the room to a different drawer for every folder. Reading the folders in storage order would be a single walk. The prefetch buffer is the clerk who collects a trolley-load of the folders you will need next, in one sweep, before you start working through the list.

Where it breaks down: a CPU does not walk anywhere and the "trolley" is a cache line of 64 bytes or so; the real hardware also prefetches by itself when it recognises a sequential pattern, which is exactly why sequential access is so much cheaper than random access.

My second script shows the underlying effect without any tree code. It sums the same 8 million gradient values twice: once indexing them in a random order (as a column sorted by value would), once in memory order.

import time
import numpy as np

rng = np.random.default_rng(0)
n = 8_000_000
g = rng.normal(size=n)                      # gradient statistics, indexed by row id (64 MB)
by_value = rng.permutation(n)               # row ids in the order of a feature's sorted values
by_row = np.sort(by_value)                  # same ids, but in memory order

def timeit(idx, reps=5):
    best = 1e9
    for _ in range(reps):
        t = time.perf_counter(); s = g[idx].sum(); best = min(best, time.perf_counter() - t)
    return best * 1000, s

t_rand, s1 = timeit(by_value)
t_seq, s2 = timeit(by_row)
print(f"gather g[row ids] in value order : {t_rand:7.1f} ms")
print(f"gather g[row ids] in memory order: {t_seq:7.1f} ms   ({t_rand/t_seq:.1f}x faster)")
print("same sum:", abs(s1 - s2) < 1e-6)

# Block offsets: inside a block of 2**16 rows, a row index fits in 16 bits.
block = 2**16
ids32 = np.arange(n, dtype=np.int32)
ids16 = (ids32 % block).astype(np.uint16)
print(f"row ids: {ids32.nbytes/1e6:.0f} MB as int32, {ids16.nbytes/1e6:.0f} MB as uint16 offsets")
gather g[row ids] in value order :    56.1 ms
gather g[row ids] in memory order:     9.0 ms   (6.2x faster)
same sum: True
row ids: 32 MB as int32, 16 MB as uint16 offsets

The same arithmetic on the same numbers is several times slower when the reads are scattered. The size of the gap depends on the machine, the array size and the run (I saw roughly 5 to 6 times over several runs here); the paper's own 2 times is for a whole training algorithm where gathering is only part of the work. The last two lines show the idea behind the compressed row indices of the next section: inside a block of 216 rows a row's position fits in 16 bits, so storing it as an offset halves the memory for the index compared with a 32-bit integer.

Problem 3: data larger than memory

The third idea is for data that cannot be held in RAM. The blocks of Section 4.1 are the natural unit: they are written to disk and streamed in during training. The paper points out that the cost is now the disk, so "it is important to reduce the overhead and increase the throughput of disk IO", and gives two techniques (Section 4.3). Block compression: each block is "compressed by columns, and decompressed on the fly by an independent thread when loading into main memory", trading some CPU for less I/O. The paper reports "roughly a 26% to 29% compression ratio" on most datasets it tested, and notes that row indices are stored as 16-bit offsets. Block sharding: blocks are spread over several disks "in an alternative manner", each disk has its own prefetch thread, and the training thread reads from each buffer in turn.

The paper tests this on Criteo, a click-through dataset with 1.7 billion examples and 67 features after preprocessing ("more than one terabyte in LibSVM format"), on one AWS c3.8xlarge machine. It reports that "compression helps to speed up computation by factor of three", that sharding onto two disks gives a further factor of two, and that the basic algorithm handles only about 200 million examples whereas the final method processes "1.7 billion examples on a single machine". For the distributed setting the paper reports that XGBoost "is able to handle the entire 1.7 billion data with only four machines".

Systems connection

Every technique here has a direct counterpart in the engineering courses. Cache misses and why sequential access wins are the subject of the memory hierarchy; measuring where time goes before optimising is performance engineering; reading column data compressed and on the fly is what column stores do for analytics queries; and overlapping I/O with compute across threads is the general idea behind parallelism. The authors were, in effect, applying database and operating-system ideas to a learning algorithm.

State of play, October 2026

The 2016 paper describes the system as it was then. The project has moved on: XGBoost 3.0.0 was released on 27 February 2025, and its release notes list external memory as a headline change, with a new ExtMemQuantileDMatrix class for the hist method and GPU support that stages data in host memory and fetches it in batches, which the notes say "can handle up to terabytes of data". The current external-memory documentation says external memory "is not supported by the exact tree method", that CPU training since version 2.0 uses mmap, that disk I/O speed largely determines CPU training speed, and that the feature "is considered experimental but ready for public testing in 3.0". It also advises that if the data fits in memory, QuantileDMatrix can be much faster. These are details of one library at one date; check the current documentation before relying on them. Chapter 9 compares the other boosted-tree libraries, and chapter 19 discusses when neural networks and foundation models compete with boosted trees on tables.

What critics and later work said

  • The headline adoption number has limits. It counts published winning solutions in one year, and it says nothing about how much of each score came from the library compared with feature engineering and validation. The paper itself says deep networks appeared in more solutions than any method except XGBoost, so the picture was not "trees beat everything".
  • The benchmarks are the authors'. Table 3 and Table 4 compare XGBoost with other systems run by the same authors, with settings chosen by them. That is normal for a systems paper and is not evidence of unfairness, but I did not find or read an independent replication, and the R gbm AUC of 0.6224 on Higgs is low enough that a reader should ask whether the configuration was comparable. The paper's text, as I read it, does not explain the gap.
  • The pieces were copied and recombined. Chapter 9 compares XGBoost with LightGBM and CatBoost, which take different approaches to the same problems (histogram-based splits, different handling of categories). I did not read their papers for this case, so I make no claim here about who first did what.
  • Fast is not the same as better calibrated or fairer. A faster loop lets you tune more, which also lets you overfit a validation set more efficiently. The guidance in cross-validation applies with more force, not less.

Key takeaways

  • XGBoost is gradient boosting with a regularised objective; what the 2016 paper adds is mostly systems work.
  • A learned default direction handles missing values and lets split finding scan only the non-missing entries; my toy scans 50 times fewer entries and finds the identical split.
  • Sorting once into column blocks and prefetching gradients into a buffer attack cache misses; the paper reports about 2 times on large data.
  • Compressed, sharded blocks streamed by background threads let one machine train on 1.7 billion rows; the paper reports 3 times from compression and a further 2 times from two disks.
  • All speed figures here are the authors' own; the adoption figure (17 of 29) counts published solutions and says nothing about causes.

Check your understanding

A column in a one-hot encoded table is non-zero in 2 per cent of rows. What does a sparsity-aware split search cost, compared with a dense one that visits every row?

  1. About the same, because sorting dominates either way
  2. About 2 per cent as many entries visited, plus a one-off cost to build the sorted blocks
  3. Exactly zero, because zero entries carry no information
  4. About twice as much, because it tries two default directions
The scan is linear in the non-missing entries, so 2 per cent density means about 50 times fewer entries, as in the script. Trying two directions doubles the scan of a small set, which is still far less than a dense pass. Zero entries do carry information (they are rows that fall on one side of the split), and they are accounted for through the totals rather than visited one by one.

After sorting a column by value, why is split finding slow when the gradient statistics are too big for the CPU cache?

  1. Sorting has to be repeated at every node
  2. Floating-point sums are slow
  3. The trees are too deep
  4. The rows come out in scrambled order, so reading each row's gradient is a scattered memory access that causes cache misses
Gradients are stored by row index, but the sorted column lists rows in value order. The paper's fix is to prefetch them into a per-thread buffer. Repeated sorting is the problem the block structure already removes, and depth and arithmetic speed are not the issue described in Section 4.2.

In the paper's Higgs comparison, XGBoost has AUC 0.8304 and scikit-learn 0.8302, but takes 0.68 s per tree against 28.5 s. What is the best conclusion?

  1. On that dataset the difference is in cost, not in model quality, which supports an engineering explanation for the speed
  2. XGBoost is a more accurate algorithm than scikit-learn's
  3. scikit-learn's implementation is incorrect
  4. AUC is too insensitive to compare boosting libraries
Equal quality at very different cost is what an implementation advantage looks like. A difference of 0.0002 in AUC is not evidence of a better algorithm, and nothing in the paper says the other implementation is wrong. AUC is a standard choice here.

Which statement about the "17 of 29 Kaggle winners used XGBoost" figure is most accurate?

  1. It proves XGBoost was the cause of those wins
  2. It shows deep learning was rarely used in 2015
  3. It counts published top solutions in one year, so it shows popularity but not cause, and selection into publication may bias it
  4. It is the fraction of all Kaggle competitions won by XGBoost
The paper's own text says eleven solutions used deep networks, and the sample is solutions published on one blog, with top three teams per competition. Popularity among winners is consistent with usefulness but does not isolate the library from feature engineering and validation.

Toolbox

Four tools carry Artifact 1. Two are Karpathy's repositories: autoresearch, the loop you replicate, and nanochat, the training stack its train.py was cut from. One is the public record of a training speedrun, modded-nanogpt, which is the standard for how a claimed gain should be documented. The last is the Rust toolchain you will rebuild the runner with. Each card has a ten-minute exercise that needs no GPU.

How to use this page

What I ran. On 15 October 2026 I cloned autoresearch (commit 228791f, 25 March 2026) and nanochat (commit 92d63d4, 3 July 2026) onto the lab VM (16 vCPUs, no GPU) and read their code there. Every listing below that has an output block was run, and the output is real. Outputs labelled lab VM ran there; the modded-nanogpt exercise ran on a laptop with Python 3 and curl. The Rust toolchain was installed on the VM with rustup (cargo 1.99.0, 27 August 2026) and its tests and program ran there.

What I did not run. Nothing on this page trains on a GPU. autoresearch's own train.py needs an NVIDIA card and a FlashAttention 3 kernel, so it does not run on the VM as published; Workbench 1 runs a CPU-sized copy and says what was changed. I did not run nanochat's training script, only its model-construction code on PyTorch's meta device (shapes without weights). I did not rerun any modded-nanogpt record: they need 8 H100 GPUs. Commands that touch the network, such as git clone and curl, fetch whatever the repository holds on the day you run them, which may be newer than what I saw.

The loop and its trainer

These two repositories are the thing Artifact 1 replicates. autoresearch is a small harness around a single training file; nanochat is the larger stack that file was simplified from. Read the first for the contract between an agent and an experiment, and the second for how a small-model training recipe is sized from one number.

autoresearch

Install: git clone https://github.com/karpathy/autoresearch, then uv sync (MIT licence; Python 3.10 or newer; needs an NVIDIA GPU, tested on an H100, and downloads PyTorch built for CUDA 12.8) · Alternatives: community forks listed in its README for macOS (miolini/autoresearch-macos, trevin-creator/autoresearch-mlx), Windows (jsegov/autoresearch-win-rtx) and AMD (andyluo7/autoresearch), and the CPU-sized copy of Workbench 1 · Chapters: 1, 2

autoresearch is three files and an instruction sheet. prepare.py holds the fixed parts: data download, tokeniser training, the data loader and the evaluation function, which the README says is not to be modified. train.py holds the GPT model, the optimiser (Muon for matrices, AdamW for the rest) and the training loop, and is the only file the agent edits. program.md is the agent's instructions, edited by the human. The contract is in program.md: make a branch, run train.py for a fixed five-minute training budget, read val_bpb (validation bits per byte: lower is better, and independent of vocabulary size), keep the commit if it improved and reset if it did not, and write one line per experiment to an untracked results.tsv with the columns commit, val_bpb, memory_gb, status and description. The README estimates about 12 experiments an hour and about 100 overnight.

10-minute guided exercise

Find the three facts that decide how much to trust a result, in the code, before running anything. They are the budget, the seed and the keep rule. Each is one line:

$ git clone --depth 1 https://github.com/karpathy/autoresearch && cd autoresearch
$ git log -1 --format="%h %ad" --date=short
$ grep -n "^TIME_BUDGET" prepare.py
$ grep -n "manual_seed" train.py
$ grep -n "val_bpb improved\|equal or worse" program.md
228791f 2026-03-25
31:TIME_BUDGET = 300        # training time budget in seconds (5 minutes)
458:torch.manual_seed(42)
459:torch.cuda.manual_seed(42)
103:8. If val_bpb improved (lower), you "advance" the branch, keeping the git commit
104:9. If val_bpb is equal or worse, you git reset back to where you started

Read it as a reviewer would. The budget is wall-clock time: 300 seconds of training, so the number of optimiser steps a run gets depends on how fast the machine is at that moment. The seed is fixed at 42 for every experiment, so a candidate and the best differ in the edit but not in the initial weights. The rule is a single comparison: lower is kept, equal or worse is reset. Chapter 2 asks what each of those does to the noise, and the workbench measures it.

Now summarise a results.tsv the way the write-up will need it. The script reads columns by name, so it works on the format in program.md and on the log of Workbench 1, which adds a few columns. Here it ran on the Workbench 1 log of 30 experiments:

"""Summarise an autoresearch results.tsv.

Usage:  python3 results_summary.py results.tsv [noise_floor]

Columns are read by name (status, val_bpb), so the format in program.md
works, and so does the log of Workbench 1, which adds more columns.
"""
import csv
import sys

# ── 1. Read the rows ─────────────────────────────────────────────────
rows = list(csv.DictReader(open(sys.argv[1]), delimiter="\t"))
floor = float(sys.argv[2]) if len(sys.argv) > 2 else None
status = [r["status"] for r in rows]
bpb = [float(r["val_bpb"]) if r["val_bpb"] not in ("", "None") else None
       for r in rows]

# ── 2. Counts, and the best score so far ─────────────────────────────
print(f"{len(rows)} rows: " + ", ".join(
    f"{status.count(s)} {s}" for s in ("keep", "discard", "crash")))
kept = [b for s, b in zip(status, bpb) if s == "keep"]
print(f"baseline {kept[0]:.4f}, best {min(kept):.4f}, "
      f"gain {kept[0] - min(kept):.4f}")
if floor:
    print(f"gain / noise floor {floor}: {(kept[0] - min(kept)) / floor:.2f}")

# ── 3. The longest dry spell ─────────────────────────────────────────
longest = run = 0
for s in status[1:]:
    run = 0 if s == "keep" else run + 1
    longest = max(longest, run)
print(f"longest run without a keep: {longest}")
31 rows: 3 keep, 28 discard, 0 crash
baseline 2.2006, best 2.1543, gain 0.0463
gain / noise floor 0.0589: 0.79
longest run without a keep: 20

What to look for. The count of kept experiments and how far the best score is below the baseline in units of the noise floor you measured (chapter 2), and the longest run without a keep. On a real GPU run, repeat it on your own results.tsv before you write any sentence that begins "the loop found".

nanochat

Install: git clone https://github.com/karpathy/nanochat, then uv sync --extra gpu (CUDA) or uv sync --extra cpu (CPU or Apple MPS); MIT licence · Alternatives: nanoGPT and minGPT for the plain model; modded-nanogpt for speed · Chapters: 1, 3

nanochat is Karpathy's minimal end-to-end stack for training and talking to a small chat model on one GPU node: tokeniser, pretraining, fine-tuning, evaluation, inference and a chat interface. Its entry point for pretraining is scripts/base_train.py; autoresearch's train.py is a cut-down single-file relative of it, not a copy. The README keeps a "time to GPT-2" leaderboard, whose target is a CORE score above 0.256525 (the score it gives the original GPT-2 checkpoint) on an 8-GPU H100 node. Its six entries, from 29 January to 14 March 2026, fall from 3.04 hours to 1.65 hours. Entries 5 and 6 are labelled "autoresearch round 1" (9 March) and "round 2" (14 March), credited to @karpathy. The README shows val_bpb 0.71808 for round 1 and 0.71800 for round 2, and CORE 0.2690 and 0.2626: the metric the loop optimised barely moved, and the leaderboard's own metric went down. Both rows are above the threshold, and I do not know how much of that CORE change is noise; I point it out because it is the proxy-versus-target question of this course in a real table.

The detail that matters for Artifact 1 is how nanochat sizes a run from one number. --depth sets the number of layers; width is 64 × depth rounded up to a multiple of the head size; the training horizon in tokens is --target-param-data-ratio (default 12; Chinchilla's is about 20) times the "scaling" parameters; and the batch size follows the tokens by a power law (from the Power Lines paper, as the source comments say), with the learning rate and weight decay rescaled to match. The file calls its d12 model the reference "where a lot of hyperparameters are tuned and then transfered to higher depths (muP style)".

10-minute guided exercise

Rebuild nanochat's sizing table without training anything. The script imports nanochat's own model class and builds it on the meta device, where tensors have shapes and no storage, so parameter counts cost nothing. The constants are the defaults of scripts/base_train.py.

"""nanochat's one-dial sizing, computed without training anything.

Run inside a nanochat checkout:  python3 nanochat_sizing.py
It rebuilds base_train.py's arithmetic (width from depth, tokens from
parameters, batch size from tokens) on PyTorch's meta device, so no
weights are allocated.
"""
import math
import torch
from nanochat.gpt import GPT, GPTConfig

# ── 1. Constants copied from scripts/base_train.py (defaults) ────────
ASPECT = 64           # --aspect-ratio: model_dim = depth * 64
HEAD_DIM = 128        # --head-dim
RATIO = 12            # --target-param-data-ratio: tokens per parameter
B_REF = 2 ** 19       # batch size tuned at d12, in tokens
VOCAB = 32768         # GPTConfig's default vocabulary size


# ── 2. Build a model on the meta device and count its parameters ─────
def build(depth):
    dim = -(-depth * ASPECT // HEAD_DIM) * HEAD_DIM      # round up
    cfg = GPTConfig(sequence_len=2048, vocab_size=VOCAB, n_layer=depth,
                    n_head=dim // HEAD_DIM, n_kv_head=dim // HEAD_DIM,
                    n_embd=dim)
    with torch.device("meta"):
        return GPT(cfg)


def scaling_params(model):
    counts = model.num_scaling_params()
    return counts["transformer_matrices"] + counts["lm_head"]


# ── 3. The reference model d12 fixes the batch-size scale ────────────
d_ref = RATIO * scaling_params(build(12))
print(f"{'depth':>5} {'dim':>5} {'params M':>9} {'scaling M':>10} "
      f"{'tokens B':>9} {'batch':>9} {'steps':>7}")
for depth in (4, 8, 12, 16, 20, 26):
    m = build(depth)
    total = m.num_scaling_params()["total"]
    n = scaling_params(m)
    tokens = RATIO * n
    batch = 2 ** round(math.log2(B_REF * (tokens / d_ref) ** 0.383))
    print(f"{depth:5d} {m.config.n_embd:5d} {total / 1e6:9.1f} "
          f"{n / 1e6:10.1f} {tokens / 1e9:9.2f} {batch:9,d} "
          f"{tokens // batch:7,d}")
depth   dim  params M  scaling M  tokens B     batch   steps
    4   256      36.7       11.5      0.14   262,144     528
    8   512     125.8       41.9      0.50   262,144   1,920
   12   768     286.3      110.1      1.32   524,288   2,520
   16  1024     536.9      234.9      2.82   524,288   5,376
   20  1280     896.5      435.2      5.22 1,048,576   4,980
   26  1664    1681.8      918.4     11.02 1,048,576  10,510

What to look for. The d12 reference has width 768 and about 110 million scaling parameters, so its horizon at ratio 12 is 1.32 billion tokens and its batch is the reference 524,288 tokens. The d26 model, the depth the README associates with GPT-2-level capability, has 1.68 billion parameters in total (918 million that count for scaling) and a horizon of 11 billion tokens. Notice that the "scaling" count is well below the total, because embeddings are left out: which parameters you count changes the recipe, and the source file's comments say the choice was made because it gave the cleanest scaling laws. Now compare with the four-layer, 128-wide model of Workbench 1: the CPU proxy is a toy by this table, and chapter 3 is about what can still be learned from one.

modded-nanogpt

The speedrun asks for the fastest training run that reaches 3.28 validation loss on FineWeb with 8 H100 GPUs. The runner

Rust and cargo

Install: curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal installs rustup, rustc and cargo into ~/.cargo without root (the VM got cargo 1.99.0 of 27 August 2026 and rustc 1.99.0 of 28 September 2026) · Alternatives: your system package manager's rustc (usually older); Python with subprocess if you only need to read the runner · Chapters: 5

cargo is Rust's build tool and package manager: cargo new makes a project, cargo build compiles it, cargo run builds and runs it, cargo test runs its tests. A project is a Cargo.toml file and a src/ folder; the compiler is strict about ownership and types, which is the point of using it for a runner that has to supervise untrusted experiments. Chapter 5 reads the Artifact 1 runner. Here you only need the loop of editing, testing and running.

10-minute guided exercise

Read the run store of Lab 1 from Rust. The lab writes JSON lines. The first thing the Rust runner must be able to do is read them and agree with Python. This crate uses only the standard library (no serde, so nothing to download): it counts the kinds of record and sums the gains of the kept experiments. Create it with cargo new runlog, then write these two files:

[package]
name = "runlog"
version = "0.1.0"
edition = "2021"
//! runlog: summarise a Lab 1 run store with the standard library only.
use std::collections::BTreeMap;
use std::env;
use std::fs;

/// The text after `"key":` up to the next comma or brace, unquoted.
fn field<'a>(line: &'a str, key: &str) -> Option<&'a str> {
    let pattern = format!("\"{}\":", key);
    let start = line.find(&pattern)? + pattern.len();
    let rest = &line[start..];
    let end = rest.find(|c| c == ',' || c == '}').unwrap_or(rest.len());
    Some(rest[..end].trim_matches('"'))
}

/// A numeric field, or 0.0 if it is missing.
fn num(line: &str, key: &str) -> f64 {
    field(line, key).and_then(|s| s.parse().ok()).unwrap_or(0.0)
}

fn main() {
    let path = env::args().nth(1).expect("usage: runlog FILE.jsonl");
    let text = fs::read_to_string(&path).expect("cannot read the log");

    let mut kinds: BTreeMap<String, usize> = BTreeMap::new();
    let (mut kept, mut proxy, mut held) = (0, 0.0_f64, 0.0_f64);
    for line in text.lines() {
        let kind = field(line, "kind").unwrap_or("?");
        *kinds.entry(kind.to_string()).or_insert(0) += 1;
        if kind == "experiment" && field(line, "keep") == Some("true") {
            kept += 1;
            proxy += num(line, "proxy_gain");
            held += num(line, "heldout_gain");
        }
    }
    for (kind, n) in &kinds {
        println!("{kind:11} {n}");
    }
    println!("kept {kept}: proxy +{proxy:.4}, held-out +{held:.4}");
}

#[cfg(test)]
mod tests {
    use super::field;

    #[test]
    fn reads_a_string_and_a_number() {
        let line = r#"{"kind":"run","seed":4,"proxy":0.25}"#;
        assert_eq!(field(line, "kind"), Some("run"));
        assert_eq!(field(line, "seed"), Some("4"));
        assert_eq!(field(line, "proxy"), Some("0.25"));
    }

    #[test]
    fn a_missing_key_is_none() {
        assert_eq!(field(r#"{"a":1}"#, "b"), None);
    }
}

What to look for. Rust's answer must equal Python's. Lab 1's demo run kept 7 of its 60 experiments for a cumulative proxy gain of +0.1200 and a held-out gain of +0.0116, and so does this program, from the same 658 lines. That agreement is the first test of Artifact 1's runner.

A Runner in Rust, Read from Python

In Artifact 1 the part of the loop that runs an experiment, enforces its deadline, reads the score and decides keep or revert is rewritten in Rust. This chapter explains why that part, and only that part, is worth moving, and teaches the Rust you need to read it and change it by comparing it, line by line, with the same program in Python. Every listing here was compiled and run.

Why this matters

This chapter serves the Rust-runner step of Artifact 1. In the original autoresearch, the runner is the agent following a paragraph of instructions: it types the command, waits, greps the log and resets git. The artifact replaces that with a small program that does the same things deterministically, so the agent proposes and the runner disposes. After the chapter you can read a 75-line Rust runner, say what each piece does in Python terms, build it with rustc or cargo, and change its deadline, its decision rule or its output format. You also know exactly what it does not protect you from, which is the subject of A11 chapter 2. It assumes the loop of chapter 01 and the run-store schema of chapter 04, and uses ideas from A0 chapter 22 (timeouts and separate processes).

Why move the runner at all

Start with the honest comparison. The runner is a supervisor: a program whose job is to start another program, watch it, limit it and report on it. Its job here is small: start a child process, give it a deadline, collect its output, parse one number, compare it, and write a row. Python does this well. The listing below is the whole thing in 25 lines, using the standard library's subprocess. The Rust version that follows is 76 lines. If the only goal were to get the job done, Python would win.

"""The same runner in Python, for comparison."""
import subprocess, sys

def main(argv):
    limit, best, log = float(argv[1]), float(argv[2]), argv[3]
    cmd = argv[argv.index("--") + 1:]
    try:                                       # run with a hard deadline
        with open(log, "w") as out:
            done = subprocess.run(cmd, stdout=out, stderr=out, timeout=limit,
                                  env={"PATH": "/usr/bin:/bin"})
        label = "exit %d" % done.returncode
        code = done.returncode
    except subprocess.TimeoutExpired:
        label, code = "timeout", None
    bpb = None
    for line in open(log):                     # grep "^val_bpb:" run.log
        if line.startswith("val_bpb:"):
            bpb = float(line.split(":")[1])
    if code == 0 and bpb is not None:
        status = "Keep" if bpb < best else "Discard"
    else:
        status = "Crash"
    print("%s\t%.6f\t%s" % (status, bpb or 0.0, label))

main(sys.argv)

The case for Rust is about what kind of program this is, not about speed (a runner spends its life waiting). Three properties matter.

  1. It is the trusted part of an untrusted loop. The runner sits between a proposer that writes code and the machine. It must not crash on odd input, must not hang, and must not be influenced by the Python environment that the proposed code runs in. A compiled binary has no import path to shadow and no interpreter configuration to inherit. The agent can edit train.py, but it does not change what the runner is made of.
  2. It runs for days. A supervisor that leaks a file handle or leaves zombie processes fails at hour 30 of a run, not in the first test. Rust's ownership rules, introduced below, make these specific mistakes hard to write.
  3. The compiler checks that every case is handled. The runner's central decision has four situations (finished with a score, finished without one, exited with an error, timed out). In Rust a match that forgets one does not compile. Section "Enums and match" shows the actual compiler message.

The cost is real: more lines, a compile step, and a learning curve. A reasonable plan is the one the artifact follows: prototype in Python (chapter 01 and Lab 1), then rewrite the runner once its behaviour is pinned down, and keep the Python as a test oracle. Both programs should print the same row for the same inputs, and the next sections show that they do.

The runner, read from Python

Here is the full Rust listing. Read it once, ignoring what you do not know, and notice that its shape is the Python's: parse arguments, run with a deadline, read the log, decide, print. The headings after it explain each unfamiliar idea with a Python parallel.

The idea

  1. args: a time limit, the best score so far, a log path, then the command after --
  2. run: start the child with a clean environment; poll until it exits or the deadline passes; if late, kill it and reap it
  3. parse: find a line starting with val_bpb: in the log
  4. decide: exit 0 with a lower score is keep; exit 0 with a higher one is discard; anything else is crash
  5. print one tab-separated row
//! runner: run one experiment under a deadline, then decide keep/discard/crash.
//! usage: runner TIMEOUT_SECS BEST_BPB LOGFILE -- CMD [ARGS...]
use std::env;
use std::fs::File;
use std::process::{Command, Stdio};
use std::thread::sleep;
use std::time::{Duration, Instant};

// ── 1. What can happen to a run, as a type the compiler checks ───────────
enum Outcome {
    Finished(i32), // exit code
    TimedOut,
}

#[derive(Debug)]
enum Status {
    Keep,
    Discard,
    Crash,
}

// ── 2. Run the child with a clean environment and a hard deadline ────────
fn run(cmd: &[String], log: &str, limit: Duration) -> std::io::Result<Outcome> {
    let out = File::create(log)?;
    let mut child = Command::new(&cmd[0])
        .args(&cmd[1..])
        .env_clear() // nothing inherited: no keys, no tokens
        .env("PATH", "/usr/bin:/bin:/usr/local/bin")
        .stdout(Stdio::from(out.try_clone()?))
        .stderr(Stdio::from(out))
        .spawn()?;
    let start = Instant::now();
    loop {
        if let Some(code) = child.try_wait()? {
            return Ok(Outcome::Finished(code.code().unwrap_or(-1)));
        }
        if start.elapsed() > limit {
            child.kill()?; // SIGKILL; then reap so no zombie is left
            child.wait()?;
            return Ok(Outcome::TimedOut);
        }
        sleep(Duration::from_millis(20));
    }
}

// ── 3. Read the metric out of the log, like grep "^val_bpb:" run.log ─────
fn parse_bpb(log: &str) -> Option<f64> {
    let text = std::fs::read_to_string(log).ok()?;
    text.lines()
        .find_map(|l| l.strip_prefix("val_bpb:"))
        .and_then(|v| v.trim().parse().ok())
}

// ── 4. Decide: the only place a number turns into a status ───────────────
fn decide(outcome: &Outcome, bpb: Option<f64>, best: f64) -> Status {
    match (outcome, bpb) {
        (Outcome::Finished(0), Some(v)) if v < best => Status::Keep,
        (Outcome::Finished(0), Some(_)) => Status::Discard,
        _ => Status::Crash, // timeout, non-zero exit, or no metric printed
    }
}

fn main() {
    let a: Vec<String> = env::args().collect();
    let sep = a.iter().position(|s| s == "--").expect("missing --");
    let limit = Duration::from_secs_f64(a[1].parse().unwrap());
    let best: f64 = a[2].parse().unwrap();
    let outcome = run(&a[sep + 1..], &a[3], limit).expect("spawn failed");
    let bpb = parse_bpb(&a[3]);
    let status = decide(&outcome, bpb, best);
    let label = match outcome {
        Outcome::Finished(c) => format!("exit {}", c),
        Outcome::TimedOut => "timeout".to_string(),
    };
    println!("{:?}\t{:.6}\t{}", status, bpb.unwrap_or(0.0), label);
}

Types, let and mut

Rust is statically typed: every value has a type known at compile time, which the compiler usually infers. let best: f64 = ... is Python's best = float(...) with the type written down. Variables are immutable by default; let mut child opts in to change, like marking a Python variable as one you intend to reassign. The effect is that a reader can tell at a glance which values change.

Ownership and borrowing

This is the idea that makes Rust different. Every value has exactly one owner, and when the owner goes out of scope the value is freed. Passing a value to a function moves it: the caller can no longer use it. If you only want to look, you pass a reference (written &), which borrows the value without taking it. In Python, names are shared references and a garbage collector decides when memory is freed; in Rust the compiler decides, before the program runs. The first program below breaks the rule on purpose and the compiler explains it.

fn save(row: String) -> usize { row.len() }

fn main() {
    let row = String::from("keep\t0.9702");
    let n = save(row);       // `row` is moved into save()
    println!("{} bytes, row = {}", n, row);
}

The message is the lesson: row was moved into save, so it cannot be used afterwards. The note even suggests the fix, borrow instead of own. Changing the parameter to &str and passing &row lends the string for the call:

fn save(row: &str) -> usize { row.len() }

fn main() {
    let row = String::from("keep\t0.9702");
    let n = save(&row);      // lend `row`; we still own it
    println!("{} bytes, row = {:?}", n, row);
}
11 bytes, row = "keep\t0.9702"

In the runner, fn run(cmd: &[String], log: &str, ...) borrows its arguments: the caller keeps them. The same reasoning is why the runner cannot leave a log file handle open by accident: the File is owned by one place, and when that place ends the file closes.

Option, Result and ?

Python signals "no value" with None and failure with exceptions, and nothing in the function signature warns you. Rust puts both in the type. An Option<f64> is either Some(number) or None; parse_bpb returns one because a log might have no score. A Result<T, E> is either Ok(value) or Err(error); run returns one because starting a process can fail. You cannot use the number inside an Option without saying what to do for None. The ? operator after a call means "if this failed, return the error from my function now", which is what an uncaught exception does, but visible in the code. In parse_bpb the chain .ok()? and .and_then(...) makes the same promise: any failure along the way becomes None, which the decision treats as a crash.

Enums and match

An enum is a type with a fixed list of variants, some carrying data: Outcome::Finished(i32) holds an exit code, Outcome::TimedOut holds nothing. In Python you would reach for a string constant or a class hierarchy and trust yourself to test every case. A match expression takes apart an enum, and the compiler checks that all cases are covered. The runner's decide function ends with a catch-all arm (_ => Status::Crash) on purpose. Remove it and replace it with only the timeout case, and the compiler refuses:

error[E0004]: non-exhaustive patterns: `(&Outcome::Finished(i32::MIN..=-1_i32), _)` and `(&Outcome::Finished(1_i32..=i32::MAX), _)` not covered
  --> bad.rs:56:11
   |
56 |     match (outcome, bpb) {
   |           ^^^^^^^^^^^^^^ patterns `(&Outcome::Finished(i32::MIN..=-1_i32), _)` and `(&Outcome::Finished(1_i32..=i32::MAX), _)` not covered
   |
   = note: the matched value is of type `(&Outcome, Option<f64>)`
help: ensure that all possible cases are being handled by adding a match arm with a wildcard pattern, a match arm with multiple or-patterns as shown, or multiple match arms
   |
59 ~         (Outcome::TimedOut, _) => Status::Crash,
60 ~         (&Outcome::Finished(i32::MIN..=-1_i32), _) | (&Outcome::Finished(1_i32..=i32::MAX), _) => todo!(),
   |
error: aborting due to 1 previous error
For more information about this error, try `rustc --explain E0004`.

The compiler lists the unhandled case, an exit code below zero or above zero, and shows how to add an arm. That is the point of decide being the only place a number becomes a status: every way a run can end must be named, and a new variant added later (say, OutOfMemory) breaks the build everywhere it is not handled instead of falling through silently. The Python version's final else: status = "Crash" gives the same behaviour for today's cases, but nothing would flag an uncovered tomorrow.

Iterators and closures

The line text.lines().find_map(|l| l.strip_prefix("val_bpb:")) is a loop written as a pipeline. lines() yields each line, the closure |l| ... (like Python's lambda l: ...) returns the part after the prefix if the line has one, and find_map stops at the first line where it returned something. The Python equivalent is a for loop with an if line.startswith("val_bpb:") and a break. Pipelines like this are common in Rust because the compiler turns them into the same loop.

Running it

The runner's behaviour is checked against a stand-in training script, fake_train.py, that prints the same summary lines as the real train.py (val_bpb:, then peak_vram_mb:) and can be told to crash or hang. Build with rustc -O runner.rs -o runner (or cargo build --release from a cargo new project; I checked both) and run four cases: a better score than the best so far (0.9800), a worse one, a crash and a hang with a two-second deadline.

import sys, time
mode = sys.argv[1]
if mode == "hang":
    time.sleep(60)
if mode == "crash":
    print("step 41 loss nan"); sys.exit(1)
print("step 100 loss 3.1")
print("---")
print("val_bpb:          %s" % sys.argv[2])
print("peak_vram_mb:     44210.3")
$ PY=$(which python3)
$ ./runner 2 0.9800 run.log -- $PY fake_train.py ok 0.9702
Keep	0.970200	exit 0
$ ./runner 2 0.9800 run.log -- $PY fake_train.py ok 0.9951
Discard	0.995100	exit 0
$ ./runner 2 0.9800 run.log -- $PY fake_train.py crash x

The four rows are exactly the four branches of the state machine from chapter 01: Keep, Discard, and two ways to Crash, one with an exit code of 1 and one with a timeout. The Python runner, given the same four commands, prints the same four rows:

$ PY=$(which python3)
$ $PY runner.py 2 0.9800 run.log -- $PY fake_train.py ok 0.9702
Keep	0.970200	exit 0
$ $PY runner.py 2 0.9800 run.log -- $PY fake_train.py ok 0.9951
Discard	0.995100	exit 0
$ $PY runner.py 2 0.9800 run.log -- $PY fake_train.py crash x
Crash	0.000000	exit 1
$ $PY runner.py 2 0.9800 run.log -- $PY fake_train.py hang x
Crash	0.000000	timeout

That agreement is the test that matters during the rewrite: the Rust runner is correct when it matches the Python one on every case, including the awkward ones you add. A hang is a good case to keep, because it is the one a naive runner fails: with no deadline, the loop would wait forever at 3 a.m.

The standard library has no "wait with a timeout" call for a child process. Its documentation lists kill, try_wait, wait and wait_with_output, and says that try_wait checks without blocking and, on Unix, reaps the process if it has exited. So the runner polls every 20 milliseconds, and when the deadline passes it kills the child and then calls wait. The second call matters. The documentation states that a terminated process that has not been waited on is still around as a zombie (a dead process whose exit status nobody has collected), that too many zombies can exhaust process IDs, and that the standard library does not wait on children for you, even when the handle is dropped. A runner that killed but never waited would leak one process table entry per timeout, which over a night of hundreds of runs is a slow failure you would only find later.

Common misconception

"The runner is written in Rust, so the loop is sandboxed." Rust gives the runner memory safety: no buffer overruns while parsing the log, no use-after-free. It does nothing about what the child can do. env_clear() removes inherited environment variables; the second listing below shows the child cannot see a secret exported to the runner. But the child is still an ordinary process of the same user. It can read your files, open network connections, and spawn processes of its own. Killing the child on a timeout does not kill a grandchild it started. Real containment needs operating-system features (user namespaces, resource limits, a network allowlist, a separate user) that the standard library does not expose and that belong to the sandboxing material in A11.

$ SECRET_KEY=abc123 ./runner 2 0.98 probe.log -- $PY env_probe.py
Keep	0.965000	exit 0
$ cat probe.log
child sees env keys: ['LC_CTYPE', 'PATH', '__CF_USER_TEXT_ENCODING']
val_bpb:          0.9650

The probe prints the keys of the environment the child saw. SECRET_KEY is absent. The three keys it does see are PATH (set by the runner) and two that Python itself adds on macOS at start-up. The practical rule for the artifact is to clear the environment, then add back only what the experiment needs by name (a cache directory, say), never the reverse.

Analogy: a foreman with a stopwatch

On a factory floor, the foreman hands each worker one job, starts a stopwatch, checks the finished part against the drawing, and either passes it or sends it to scrap. The foreman does not make parts; the foreman's job is to make sure the line keeps moving and the scrap bin is honest. The runner is the foreman and the agent is a very fast, sometimes careless worker.

Where it breaks down: a foreman can see what the worker does with the tools. A runner sees only the exit code, the log and the clock. What the child did to the rest of the machine in between is invisible unless you add the sandboxing and monitoring covered in A11.

Systems connection

The runner is a process supervisor, the same job that systemd, supervisord and container runtimes do. Spawn, watch, enforce a limit, kill, reap and report is the whole lifecycle, and zombie reaping, signal handling and timeouts are the problems every supervisor has to solve. If you have debugged a service that "runs forever but is stuck", or a CI job killed at 60 minutes with no log, you already know why a deadline belongs in the supervisor and not in the code it supervises: the supervised code is the thing that might not return.

What else belongs in the Rust half

The listing handles the run. Three more pieces complete the Artifact 1 runner, and each has a Python prototype in the lab:

  • The run store. The listing prints a row; a real runner appends it to the store of chapter 04. A tab-separated file needs only the standard library. A SQLite store needs a database crate such as rusqlite, which is the only external dependency the artifact should need; add it deliberately and pin its version.
  • The held-out evaluation. After a keep, the runner runs the evaluation on the split the loop never reads and stores the second number next to the first, which is the gap column of chapter 02. Because the runner, not the agent, performs it, the agent cannot read or influence it.
  • Resource limits and process groups. To kill the child's own children and cap memory and CPU time, the runner has to call operating-system interfaces directly. In Rust this normally means the libc or nix crates. I did not write or run that part for this chapter, and I would not trust a sketch of it; it is the first thing A11's lab asks you to build and test.

Key takeaways

  • The runner is a supervisor: spawn, watch, enforce a deadline, reap, parse, decide, record. Python does it in 25 lines; Rust in 76. The reasons to move it are trust, longevity and exhaustive case handling, not speed.
  • Reading Rust from Python: let mut marks what changes; ownership and borrowing replace garbage collection; Option and Result put "no value" and "failed" in the type; an enum with match makes the compiler check every case.
  • The standard library has no wait-with-timeout. Poll try_wait, and on a deadline kill then wait; the second call stops zombies accumulating.
  • A Rust runner is memory safe but is not a sandbox. env_clear() hides secrets from the child; it does not stop the child reading files, using the network or leaving grandchildren behind.
  • Keep the Python runner as an oracle: the Rust one is right when it prints the same row for the same case, including hangs and crashes.

Check your understanding

The runner's child hangs. Which design catches it?

  1. Call child.wait() and trust the child to finish.
  2. Poll try_wait against a deadline, then kill and wait.
  3. Use env_clear().
  4. Parse the log first.
wait blocks forever on a hang. Clearing the environment is about secrets, and the log of a hung run has no score to parse yet. Polling with a deadline is the only option that returns control.

What does the compiler do when decide's match forgets a case of Outcome?

  1. Treats it as a crash at run time.
  2. Skips it silently.
  3. Prints a warning and continues.
  4. Refuses to compile and lists the unhandled patterns.
The listing above shows error E0004, non-exhaustive patterns, naming the exit codes not covered. The point is that omission is caught before the program ever runs; Python would fall through silently.

Why does the runner call child.wait() after child.kill()?

  1. To collect the exit status so the operating system can release the process entry; otherwise it stays as a zombie.
  2. To give the child time to save its work.
  3. Because kill sends a polite request that may be ignored.
  4. To read the log.
The documentation says a terminated but un-waited process remains a zombie and that std does not wait for you. kill is SIGKILL, which cannot be ignored or used to save work. Reading the log is a separate step.

A teammate says: "The runner is in Rust, so a malicious train.py cannot read our API keys." What is the most accurate response?

  1. Correct, Rust prevents all unsafe behaviour.
  2. Correct, because env_clear() blocks all file access.
  3. Only partly: clearing the environment hides keys held in variables, but the child is a normal process that can read files, use the network and spawn others unless a sandbox stops it.
  4. Incorrect, because Rust programs cannot clear the environment.
The probe shows SECRET_KEY is not inherited, which is a real but narrow protection. Rust's safety guarantees apply to the runner's own memory, not to a separate process it launches. The standard library does clear environments, so the last option is false.

In save(row) from the move example, what is the smallest change that makes the program compile and keeps row usable afterwards?

  1. Make row a mut variable.
  2. Have save borrow a &str and call it with &row.
  3. Call save twice.
  4. Delete the println!.
Mutability does not affect moves. Borrowing lends the string for the call, so the caller still owns it. Deleting the print compiles but does not keep row usable, which is what was asked.

When is the move from Python to Rust for the runner justified?

  1. After the Python runner's behaviour is fixed by tests, because the Rust one is a long-running trusted component and the Python one remains the oracle.
  2. Before writing any tests, to avoid Python's slowness.
  3. Never; Python is always enough.
  4. Only if the training itself moves to Rust.
The runner spends its time waiting, so speed is not the reason. Rewriting after behaviour is pinned down means you know what correct looks like and can compare the two outputs. Training stays in Python regardless.

Scaling Laws & μP Transfer for Proxies

A five-minute run is only useful if what you learn from it holds for a bigger run. Two tools make that claim testable: a scaling law, which predicts a big run's loss from small ones, and μP, a way of setting hyperparameters so that the best values found on a small model carry over to a wide one. This chapter works through both with numbers, and is honest about what neither one promises.

Why this matters

Artifact 1 optimises a five-minute proxy and asks whether the gains hold up at a larger scale. Without a way to reason about scale you can only say "I hope so". This chapter serves the middle of the artifact: choosing the proxy's size and budget, deciding which hyperparameters need re-tuning when you change width, and designing the longer re-run that measures the held-out gain of chapter 02. It builds on A2 chapter 18 (scaling laws) and A2 chapter 16 (the 6ND rule), and the Chinchilla case study reads the paper in full. After this chapter you can compute a compute-optimal model size from a fitted law, say how fragile a fit from small runs is, and explain why the hidden-layer learning rate has to shrink as width grows. You also know the difference between a prediction about loss and a prediction about whether an idea will help.

Two kinds of transfer

"Small to large" hides two different questions, and mixing them up causes most of the confusion about proxies.

Does the loss transfer?

Given the loss of several small models trained on several amounts of data, can I predict the loss of a bigger one? This is the job of a scaling law: a fitted formula for loss as a function of model size and data.

Do the settings transfer?

If I tune the learning rate on a small model, does that value work for a wide one? This is the job of a parametrisation such as μP, a rule for how initial values and learning rates change with width.

Neither answers the third question that a research loop actually asks: will this change, which helped at five minutes, still help at the larger scale? A scaling law describes one fixed training recipe. It says nothing about whether a new optimiser tweak shifts the curve. μP says the old tuned settings stay good, not that your new idea works. Keep the three questions apart, and the rest of the chapter is about how far each of the first two can be pushed.

A scaling law, term by term

Hoffmann et al. ("Training Compute-Optimal Large Language Models", 2022, known as the Chinchilla paper) trained over 400 models, from 70 million to over 16 billion parameters, on 5 to 500 billion tokens. They fitted a function of the number of parameters N and training tokens D. I read the paper's third approach in its PDF; its equation 10 gives the fitted form and constants, which I quote faithfully below.

Plug in numbers. The script prints each term for one model, then changes one input at a time to show which penalty each move attacks.

The idea

  1. floor ← E
  2. size penalty ← A ÷ Nα; data penalty ← B ÷ Dβ
  3. loss ← floor + size penalty + data penalty
  4. try 10× the data, 10× the parameters, and both
"""The Chinchilla loss law, one printed line per build-up step.

L(N, D) = E + A / N**alpha + B / D**beta with the constants reported by
Hoffmann et al. (2022) for their parametric fit.
"""
E, A, B, ALPHA, BETA = 1.69, 406.4, 410.7, 0.34, 0.28

def show(n, d):
    floor = E                                   # step 1: the floor
    size_term = A / n ** ALPHA                  # step 2: too few parameters
    data_term = B / d ** BETA                   # step 3: too little data
    total = floor + size_term + data_term       # step 4: add them up
    print("N=%.0e D=%.0e  floor %.3f  size %.3f  data %.3f  loss %.3f" %
          (n, d, floor, size_term, data_term, total))

# ── 1. A 1B-parameter model on 20B tokens, then change one thing ─────────
show(1e9, 2e10)
show(1e9, 2e11)       # ten times the data
show(1e10, 2e10)      # ten times the parameters
show(1e10, 2e11)      # both
N=1e+09 D=2e+10  floor 1.690  size 0.354  data 0.536  loss 2.580
N=1e+09 D=2e+11  floor 1.690  size 0.354  data 0.281  loss 2.325
N=1e+10 D=2e+10  floor 1.690  size 0.162  data 0.536  loss 2.388
N=1e+10 D=2e+11  floor 1.690  size 0.162  data 0.281  loss 2.133

Ten times the data lowers the loss from 2.580 to 2.325, by cutting the data penalty from 0.536 to 0.281 and leaving the size penalty alone. Ten times the parameters lowers it to 2.388 and attacks only the size penalty. Doing both reaches 2.133. The floor of 1.690 never moves, which is why returns diminish: at the last row the two penalties together are still 0.443.

Spending a fixed budget: compute-optimal sizing

Compute is the thing you actually pay for. Training a Transformer costs about 6 FLOPs per parameter per token (two for the forward pass, four for the backward, see A2 chapter 16), so C ≈ 6ND. For a fixed C, a bigger model means fewer tokens. The question Chinchilla asked is which split minimises the loss. Substituting D = C / 6N into the law gives a function of N alone, and the script below searches over N for several budgets.

The idea

  1. for a compute budget C and each candidate model size N: D ← C ÷ 6N
  2. loss(N) ← E + A ÷ Nα + B ÷ Dβ
  3. pick the N with the lowest loss; report its tokens per parameter
"""Compute-optimal sizing from the Chinchilla parametric fit.

L(N, D) = E + A / N**alpha + B / D**beta, with the constants Hoffmann et
al. (2022) report for their third approach. Compute is C = 6 * N * D.
"""
E, A, B, ALPHA, BETA = 1.69, 406.4, 410.7, 0.34, 0.28

# ── 1. The predicted loss for a model of N parameters on D tokens ────────
def loss(n, d):
    return E + A / n ** ALPHA + B / d ** BETA

# ── 2. For a compute budget, search model sizes (D follows from C) ───────
def best_split(c):
    best = None
    for k in range(0, 4001):
        n = 10 ** (6 + k * 0.002)              # 1e6 .. 1e14 parameters
        d = c / (6 * n)
        if d < 1:
            break
        cand = (loss(n, d), n, d)
        best = cand if best is None or cand < best else best
    return best

# ── 3. A table over six orders of magnitude of compute ───────────────────
print("compute C   best N    best D    tokens/param  predicted loss")
for exp in (16, 18, 20, 22, 24):
    l, n, d = best_split(10.0 ** exp)
    print("1e%-2d FLOPs  %7.2e  %7.2e  %8.1f      %.3f" % (exp, n, d, d / n, l))

# ── 4. Why not just the biggest model? Same compute, three splits ────────
c = 1e20
print("\nat C = 1e20 FLOPs")
for n in (1e9, 7e9, 3e10):
    d = c / (6 * n)
    print("N=%.0e  D=%.1e  tokens/param %6.1f  loss %.3f" %
          (n, d, d / n, loss(n, d)))

The table has two messages. The first is the shape: at a fixed budget the loss is a U-shaped function of model size. At 1020 FLOPs the best model has about 6.5×108 parameters, trained on 2.6×1010 tokens (40 tokens per parameter). A 1-billion-parameter model is close (2.608 against 2.600), while a 7-billion-parameter model starved of tokens (0.3 per parameter) is far worse at 2.845. The second is the trend: under this fitted law, the best ratio of tokens to parameters rises with the budget, from 16 to 98 across the rows. That matches the exponents the paper reports for this approach (optimal parameters grow as C0.46 and optimal tokens as C0.54), while their other two approaches give 0.50 and 0.50 or 0.49 and 0.51. The authors' headline is "near equal scaling": double the model, double the data. Their three methods disagree in the second decimal, and so will your small-scale fits.

For a proxy, the useful reading is practical. The autoresearch model has a fixed depth of 8 and a fixed five-minute budget, so its size and token count are set by the machine, not chosen for optimality. Changing the budget or the model size moves the proxy along these curves, and the optimum moves too. nanochat takes the opposite route: its README describes a single --depth setting from which every other hyperparameter, including the training horizon, is derived "to keep models compute-optimal". One dial, and the law does the rest.

How fragile is a fit from small runs?

The constants in the paper come from over 400 runs, some of them large. A proxy-based project fits a law from a handful of tiny runs, and the question is how far the extrapolation can be trusted. The experiment below plants a known law, simulates five small models at 1 to 16 million parameters with measurement noise, fits a floor plus power law to them, and predicts the loss of a model 100 times larger. It repeats this 300 times at four noise levels and reports the error of the prediction.

The idea

  1. truth: L(N) = c + A ÷ Nα; five small N; add Gaussian noise to each loss
  2. fit: scan the floor c; for each, regress log(L − c) on log N; keep the best-fitting c
  3. predict the loss at 100 times the largest fitted N; compare with the truth
  4. repeat with fresh noise; report the median and the 10th to 90th percentile of the error
"""Fit a power law on small runs, predict a run 100x larger.

Truth is the Chinchilla fit at a fixed 2e10 tokens, so
L(N) = c + A / N**alpha with c = E + B / D**beta. Small-run losses get
Gaussian noise. The fit knows the form but not c, A or alpha.
"""
import math
import random
import statistics as st

E, A, B, ALPHA, BETA, D = 1.69, 406.4, 410.7, 0.34, 0.28, 2e10
C = E + B / D ** BETA                       # the irreducible part at this D
SMALL = [1e6, 2e6, 4e6, 8e6, 1.6e7]         # model sizes we can afford
BIG = 1.6e9                                 # the size we care about
true = lambda n: C + A / n ** ALPHA

# ── 1. Fit c + A/N^alpha: scan c, regress log(L - c) on log N ────────────
def fit(ns, ls):
    best = None
    for k in range(0, 400):
        c = k * 0.01                        # candidate floors 0.00 .. 3.99
        if c >= min(ls) - 1e-6:
            break
        xs = [math.log(n) for n in ns]
        ys = [math.log(l - c) for l in ls]
        slope, icpt = st.linear_regression(xs, ys)
        sse = sum((icpt + slope * x - y) ** 2 for x, y in zip(xs, ys))
        if best is None or sse < best[0]:
            best = (sse, c, slope, icpt)
    _, c, slope, icpt = best
    return lambda n: c + math.exp(icpt + slope * math.log(n))

# ── 2. Repeat with fresh noise; how far off is the big-run prediction? ───
print("true loss at N=%.1e: %.3f" % (BIG, true(BIG)))
for noise in (0.0, 0.003, 0.01, 0.03):
    rng = random.Random(0)
    errs = []
    for _ in range(300):
        ls = [true(n) + rng.gauss(0, noise) for n in SMALL]
        errs.append(fit(SMALL, ls)(BIG) - true(BIG))
    errs.sort()
    print("noise %.3f  median err %+.3f   10th..90th pct [%+.3f, %+.3f]" %
          (noise, errs[150], errs[30], errs[270]))
true loss at N=1.6e+09: 2.528
noise 0.000  median err +0.002   10th..90th pct [+0.002, +0.002]
noise 0.003  median err -0.002   10th..90th pct [-0.027, +0.028]
noise 0.010  median err -0.009   10th..90th pct [-0.095, +0.087]
noise 0.030  median err -0.064   10th..90th pct [-0.574, +0.229]

With no noise the fit recovers the law (the 0.002 error is the grid step). With noise of 0.003 in the loss, about the size of the seed noise in chapter 02, the median is still fine but the 10th to 90th range is already plus or minus 0.028. At 0.010 it is about plus or minus 0.09, and at 0.030 the prediction can be off by half a nat or more. Three floor-and-exponent parameters fitted from five points leave very little slack, and the floor and the exponent trade off against each other. The practical rules: use more model sizes than parameters, make each loss measurement as clean as the noise floor allows (chapter 02), and quote the extrapolation with its range, never as a point.

μP: making hyperparameters transfer

The second tool addresses a more mundane problem. You find a good learning rate on a small model and train a wider one with it. The wider model diverges, or trains badly, and you have to search again at the expensive size. Why does the best learning rate move with width?

The reason is arithmetic. Take one hidden layer, h = Wx, where W has n columns, so every output is a sum over n inputs. Adam, the standard optimiser (A0 chapter 10), moves each weight by roughly the learning rate in the direction of its gradient's sign. For this layer the gradient of each weight is a product of two numbers, so the sign pattern of the update lines up with the sign pattern of x. All n terms in the sum then add in the same direction, and the change in h grows in proportion to n. A learning rate that moves a 64-wide layer gently moves a 4,096-wide layer 64 times as far. The script measures this directly.

The idea

  1. x ← random inputs of size n; delta ← random backward signal
  2. Adam-like update: every weight moves by lr in the sign of its gradient
  3. measure the root-mean-square change in W x
  4. repeat with the learning rate scaled by 64 ÷ n
"""How far does one Adam step move a hidden layer's output, by width?

Adam changes every weight by about lr, in the direction of its gradient's
sign. For a hidden layer h = W x with n inputs, the gradient of W is
outer(delta, x), so each weight moves by lr * sign(delta_i) * sign(x_j)
and all n terms in sum_j dW_ij * x_j add up in the same direction.
"""
import numpy as np

LR = 1e-3
rng = np.random.default_rng(0)

# ── 1. Measure the change in pre-activations after one sign-like step ────
def rms_change(n, lr):
    x = rng.normal(size=n)                    # incoming activations, O(1)
    delta = rng.normal(size=n)                # backward signal, any signs
    dW = -lr * np.outer(np.sign(delta), np.sign(x))   # Adam-like update
    dh = dW @ x                               # change in W x
    return float(np.sqrt(np.mean(dh ** 2)))

# ── 2. Same lr at every width, then lr scaled as 1/width ─────────────────
print("width   rms change, lr fixed   rms change, lr = 1e-3 * 64/width")
for n in (64, 256, 1024, 4096):
    fixed = rms_change(n, LR)
    scaled = rms_change(n, LR * 64 / n)
    print("%5d   %18.4f   %18.4f" % (n, fixed, scaled))
width   rms change, lr fixed   rms change, lr = 1e-3 * 64/width
   64               0.0478               0.0495
  256               0.2034               0.0443
 1024               0.8502               0.0515
 4096               3.2885               0.0508

With one fixed rate, the typical change in a hidden layer's output goes 0.048, 0.203, 0.850, 3.289 as the width quadruples each time: it grows in proportion to width, as predicted. With the rate scaled as 1/width the change stays at about 0.05 at every width. That one-line fix is the core of the hidden-layer rule in μP (maximal update parametrisation): choose how each layer's initial values and learning rate scale with width so that each layer's updates change its outputs by a width-independent amount. Yang et al. ("Tensor Programs V: Tuning Large Neural Networks via Zero-Shot Hyperparameter Transfer", 2022) show that under this parametrisation many optimal hyperparameters stay stable as the model grows. The workflow they call μTransfer follows: parametrise the target model in μP, tune on a small proxy, copy the tuned values to the large model without tuning it directly.

I fetched the paper's abstract page on 15 October 2026. It reports, for Transformers, that transferring from a 13-million-parameter model outperformed the published BERT-large results (an encoder-only Transformer of 350 million parameters) at a total tuning cost about equal to pretraining BERT-large once. It reports that transferring from a 40-million-parameter model outperformed published results for the 6.7-billion-parameter GPT-3 (generative pre-trained Transformer 3) model at a tuning cost of about 7% of pretraining. The authors provide a PyTorch implementation as the mup package. Those are the authors' claims on their setups; I did not reproduce them, and the full table of per-layer rules for each optimiser is in the paper, not here. The demonstration above shows why a rule of this kind must exist, not that every detail of it is right.

Common misconception

"A scaling law (or μP) tells me whether my change will help at scale." Neither does. A scaling law is fitted to one recipe; a new optimiser tweak changes the curve, and the only way to know by how much is to fit again or to run the larger experiment. μP is about the width axis: it promises that tuned hyperparameters carry over when the model gets wider. It does not promise that depth, batch size or training length transfer, and it says nothing about whether a code change that wins at five minutes still wins at an hour. Treat both as tools for choosing a proxy and sizing a re-run, not as proofs that a result transfers.

Analogy: a scale model in a wind tunnel

An aircraft designer tests a one-twentieth model in a wind tunnel and predicts the full aircraft's drag. It works because the designer matches dimensionless quantities (such as the Reynolds number, a ratio of inertial to viscous effects) between model and aircraft, so the airflow is similar. A scaling law is the fitted curve through the model's measurements, and μP is the rule for matching quantities across sizes.

Where it breaks down: fluid dynamics gives the designer a short list of matching conditions derived from physics. For neural networks the conditions are empirical and incomplete: μP matches one family of them (width and learning rate), and nobody can list everything else that changes with scale. A proxy that is a good wind tunnel for one change can be a poor one for another.

Systems connection

Capacity planning for a service does the same job. You load-test a one-tenth-size replica, fit a curve of latency against load, and extrapolate to production. Engineers learn that the fit holds until a new bottleneck (a lock, a network link, a cache size) appears at a scale the test never reached. A scaling-law fit has the same blind spot: it holds inside the range of sizes it was fitted on, and nothing in the formula warns you when a new effect takes over.

Key takeaways

  • Three questions are separate: does the loss transfer (scaling laws), do the settings transfer (μP), and does an idea transfer (neither tool answers it).
  • Chinchilla's fitted law is a floor plus a size penalty plus a data penalty. With C ≈ 6ND, the best split for a budget is a U-shaped minimum, and under the parametric fit the best tokens-per-parameter ratio rises with the budget.
  • Fits from a few small runs are fragile: floor and exponent trade off, and measurement noise at the level of a seed produces prediction ranges of a few hundredths of a nat. Quote the range.
  • One Adam step changes a hidden layer's output in proportion to its width, which is why the best learning rate moves with width. Scaling the rate as 1/width removes that growth, and this is the core of μP's hidden-layer rule.
  • μTransfer's reported savings (tuning from 13M or 40M parameter models) are the authors' claims; the abstract does not promise transfer across depth, batch size or training length.
  • A proxy is trustworthy only inside the range where its transfer has been checked. The check is a larger run.

Check your understanding

Using L = 1.69 + 406.4/N0.34 + 410.7/D0.28, you move from a 1B-parameter model on 20B tokens to a 1B model on 200B tokens. Which statement is right?

  1. Both penalties fall, because more data also reduces the size penalty.
  2. Only the data penalty falls (0.536 to 0.281); the size penalty and the floor are unchanged.
  3. The loss falls to the floor 1.69.
  4. The loss is unchanged, because the model is the same size.
The size penalty depends only on N and the floor on neither. The data penalty falls, so the loss goes from 2.580 to 2.325. It does not reach the floor, because two penalties remain positive.

At a fixed compute budget, why is a much larger model not better?

  1. Larger models cannot be trained at all.
  2. The size penalty rises with N.
  3. Larger models always overfit.
  4. With C ≈ 6ND fixed, a larger N leaves fewer tokens D, so the data penalty grows faster than the size penalty shrinks.
The size penalty falls with N; the data penalty rises because D = C / 6N shrinks. The minimum of the sum is the compute-optimal size. Overfitting is not the mechanism in the law, and the first two options contradict it.

In the extrapolation experiment, what is the main reason noise of 0.01 in the small-run losses gives prediction errors of about plus or minus 0.09 at 100 times the size?

  1. The fit has three free parameters (floor, scale, exponent) and only five points, so noise moves the floor and exponent together and the error is amplified in extrapolation.
  2. The true law is not a power law.
  3. The simulation draws different seeds for each model size.
  4. Small models cannot follow scaling laws.
The true law in the simulation is exactly a floor plus a power law, so the form is not the problem. Extrapolating far beyond the fitted range magnifies small errors in the exponent. The seed argument is irrelevant (each draw is independent noise by design).

In mup_step.py the fixed-rate change grows from 0.048 to 3.289 as width goes from 64 to 4,096 (64 times). What is the cause?

  1. Larger layers use a larger learning rate by default.
  2. Random initialisation differs by width.
  3. Each output is a sum of n terms whose update signs line up with the input signs, so the change grows in proportion to n.
  4. Floating-point error.
The update for each weight has the sign of an outer product of the backward signal and the input, so all n contributions to an output coordinate agree in sign. The sum grows with n, here by 64 times for 64 times the width. The rate in the demonstration is identical at every width.

A colleague says: "μP means the five-minute win of my new attention variant is guaranteed to hold on the big model." What is the best reply?

  1. Correct, as long as the learning rate is tuned.
  2. No: μP's claim concerns hyperparameters staying near-optimal as width grows; whether a code change still helps at scale needs its own larger run.
  3. Correct, because μP removes the proxy gap.
  4. No, because μP only works for BERT.
μTransfer is a statement about tuned hyperparameters, with the paper's evidence on Transformers and ResNets. It is silent on new architecture variants and on longer training. The last option is wrong: the abstract's experiments include both BERT and GPT-3.

The RE-Bench scaling-law task permits experiments of 1016 FLOPs or less and scores a 5×1017 FLOP run. About how far must the extrapolation reach, in compute?

  1. 50 times.
  2. 5 times.
  3. 500 times.
  4. 5,000 times.
5×1017 divided by 1016 is 50. Because most of the experiments will be smaller than the 1016 limit, the typical reach is larger than 50 times, which is why the previous experiment's warning about extrapolation matters.

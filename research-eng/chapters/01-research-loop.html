The Research Loop as a Program

Karpathy's autoresearch is a research method written as a program: an agent edits one file, a run of fixed length scores the edit, and the edit is kept only if the score improves. This chapter reads that loop closely, rebuilds it as a state machine with a budget, and shows what the fixed time budget does to every number the loop produces. It ends with the places where such a loop can quietly go wrong, which the rest of the course is about.

Why this matters

This chapter serves the first step of Artifact 1, autoresearch-rs: you cannot rewrite the runner, the sandbox and the run store in Rust until you can say exactly what the original loop does and which parts of it are policy rather than mechanism. Everything later hangs on three ideas introduced here: the loop is a small state machine with a budget; its only memory is a git branch and a results table; and its score is one noisy number measured under a fixed clock. After this chapter you can read program.md and say which rule protects what. You can write the loop as code in about fifty lines. You can also compute how many experiments a night buys and what a change that slows each step costs. Lab 1 turns this chapter into a runnable keep-or-revert loop, and chapter 02 asks whether the numbers it keeps can be believed.

What autoresearch is

In 2026 Andrej Karpathy published karpathy/autoresearch (its README carries a note dated March 2026), a small repository with a large idea: let a coding agent do the experiment loop of a training researcher, unattended, on one GPU. I read the repository's README, its program.md and its train.py on 15 October 2026 for this chapter. The README puts the idea in one sentence: an agent edits the code, trains for five minutes, checks whether the result improved, keeps or discards the change, and repeats, so that you come back to a log of experiments and, with luck, a better model.

Three files carry the whole design. prepare.py holds the fixed things: the data download, the tokeniser training, the data loader and the evaluation function. train.py is the one file the agent may edit. It holds a small model in the style of a generative pre-trained Transformer (GPT), its optimiser and the training loop, so the architecture, the hyperparameters, the optimiser and the batch size are all open to change. The training code is a simplified single-GPU cut in the style of Karpathy's nanochat project, but it is autoresearch's own file; nanochat's own training entry point is a different script (scripts/base_train.py). The third file, program.md, is a plain-English instruction sheet for the agent. The README is explicit that the human's lever is that sheet, not the Python: you are programming the Markdown.

That inversion is the interesting part. In an ordinary training repository the code is the program and a human runs it. Here the program is the procedure, written as instructions, and the agent is the interpreter. A research loop is a program whose instructions happen to be in English. Reading it as a program, with states, transitions, a budget and a log, is what lets you rebuild it in a language with types and a process API, which is Artifact 1.

Research loop
A repeated cycle of propose a change, measure it, and keep or discard it, run without a human between iterations.
Proxy
A cheap measurement standing in for the thing you care about. A five-minute run is a proxy for a full training run; chapter 02 is about when it can be trusted.
val_bpb
Validation bits per byte: the model's average cross-entropy on held-out text, converted into bits and divided by the number of bytes of text. Lower is better. Counting bytes rather than tokens makes scores comparable between models with different tokenisers (see A2 chapter 14).
Wall-clock budget
A limit on elapsed real time, as opposed to a limit on steps or tokens.
Keep-or-revert
The decision rule: if the new score beats the best so far, keep the change; otherwise undo it.

The loop as a state machine

A state machine is a program described by the situations it can be in (its states) and the events that move it between them (its transitions). It is the right description here because the loop has no cleverness in its control flow. The cleverness is all in the proposal, and that comes from the agent. Everything around the proposal is bookkeeping with a few exits.

program.md spells the control flow out. Setup comes first: agree a run tag from today's date, create a fresh branch autoresearch/<tag> (it must not already exist), read the three files, check that the data and tokeniser are cached, and create results.tsv with only its header. The first run is always the unmodified script, to establish the baseline. After that the loop is nine numbered steps in the file, which I paraphrase here:

  1. Look at the current branch and commit.
  2. Edit train.py with an experimental idea.
  3. Commit the change.
  4. Run uv run train.py > run.log 2>&1, redirecting all output so it does not flood the agent's context.
  5. Read the result with grep "^val_bpb:\|^peak_vram_mb:" run.log.
  6. If the grep prints nothing, the run crashed: read the tail of the log, try a fix, and give up after a few attempts.
  7. Record the result in results.tsv, which stays untracked by git.
  8. If val_bpb went down, keep the commit and advance the branch.
  9. If it is equal or higher, reset to where the branch started.

results.tsv is tab-separated with five columns: commit, val_bpb, memory in GB, status and a short description. The status is keep, discard or crash, and a crash is logged with zeros in the numeric columns. Two more rules close the machine's exits. A run that exceeds ten minutes is killed and treated as a failure. And once setup is confirmed the agent must not stop to ask whether to continue: the file says the loop runs until the human interrupts it, and the README says to expect about twelve experiments an hour and about a hundred over a night.

Notice what the machine does not contain. It has no notion of "this idea is promising", no population, no memory of rejected ideas other than the log the agent may re-read, and no model of noise. It is greedy hill-climbing with a hard accept rule. That is a feature for a first artifact: you can see exactly what it does and measure it. It is also the thing the later artifacts compare against (chapter 02 of A10 asks when tree search beats this greedy rule).

Where the loop is allowed to write

The design has one more structural feature that is easy to read past: a write boundary, the set of things the proposer may change. The agent may edit train.py and may append to results.tsv. It may read prepare.py, which holds evaluate_bpb, the function program.md calls "the ground truth metric", but it may not change it, may not install packages and may not change the evaluation.

The principle is the one that will carry through this path: the thing that scores a proposal must sit outside what the proposal can change. If the agent could edit the evaluation function it could lower val_bpb by making the function return a smaller number, and the loop would faithfully keep that "improvement". In the files I read, that boundary is stated in prose for the agent to obey. I did not find a mechanism in the repository that enforces it. That is a reasonable choice for a research demo run on your own machine, and it is exactly the gap Artifact 1's Rust runner and sandbox close, and Artifact 3 hardens further (see A7 chapter 15 on evaluator hacking and A11 chapter 1 on the threat model of a research loop).

Systems connection

The loop is a job scheduler's retry-and-rollback logic in miniature. Each experiment is a short batch job with a hard timeout. Git is the rollback mechanism: committing before the run and resetting after a failure is what makes every iteration start from a known state, the same idea as an idempotent deployment step. Writing results.tsv outside git is the same reason a database keeps its write-ahead log outside the data it can roll back: the record of what happened must survive the undo. If you have ever debugged a flaky nightly job, you already know the three questions to ask of this loop: what happens on a hang, what happens on a crash, and what is the one place the state lives.

A fixed budget is a schedule, not just a limit

The budget is the loop's most consequential design choice, and it is worth understanding in detail. Each run gets a fixed wall-clock budget of five minutes, not a fixed number of steps or tokens. The README states the reason: it makes experiments directly comparable whatever the change is. If one idea doubles the model width and another halves the batch, a fixed step count would compare unlike amounts of work. A fixed clock gives every idea the same amount of your resource, and asks which idea buys the most val_bpb with it.

In train.py the budget is implemented as a progress variable. Progress is the counted training time divided by the time budget, and only steps after the tenth count, which excludes compilation and warm-up. Training stops when the budget is used up, so the number of steps depends on how fast the hardware is. The learning rate follows a schedule driven by that progress: there is no warm-up (the warm-up ratio is zero), the rate stays flat until half the budget has gone, then decays linearly to zero over the second half. The script also exits with an error code if the loss is not a number or exceeds 100, which is how a diverged run becomes a clean crash instead of a hang.

The consequences follow from the arithmetic. If a step takes t seconds, the number of steps is about:

steps ≈ 10 + 300 s ÷ t

The tokens seen are the steps times the tokens per step (219, about 524,000, in the script's constants). Run the arithmetic for three cases. The step times are illustrative assumptions; the structure is what matters.

The idea

  1. progress ← counted training seconds ÷ 300
  2. learning-rate multiplier ← 1 while progress < 0.5, then falls linearly to 0 at progress 1
  3. skip the first 10 steps when counting time (compilation, warm-up)
  4. stop when counted time reaches 300; report steps, tokens and val_bpb
"""What a fixed wall-clock budget means for step counts and the LR schedule.

train.py counts only steps after step 10 towards the budget, keeps the
learning rate flat for the first half of progress, then decays it linearly
to zero. Step times below are illustrative assumptions, not measurements.
"""
TIME_BUDGET = 300.0        # seconds of counted training time
WARMUP_STEPS = 10          # steps not counted (compilation, warm-up)
WARMDOWN = 0.5             # fraction of progress spent decaying the LR
TOKENS_PER_STEP = 2 ** 19  # TOTAL_BATCH_SIZE in train.py

# ── 1. Learning-rate multiplier as a function of progress ────────────────
def lr_mult(progress):
    if progress < 1 - WARMDOWN:
        return 1.0
    return max(0.0, (1 - progress) / WARMDOWN)

# ── 2. Simulate one run: how many steps fit in the budget? ───────────────
def run(step_s):
    counted, step, log = 0.0, 0, {}
    while counted < TIME_BUDGET:
        step += 1
        if step > WARMUP_STEPS:
            counted += step_s
        for mark in (0.25, 0.5, 0.75, 1.0):   # note the LR at these marks
            if counted / TIME_BUDGET >= mark and mark not in log:
                log[mark] = (step, lr_mult(counted / TIME_BUDGET))
    return step, log

# ── 3. Compare three machines/ideas on the same budget ───────────────────
for name, step_s in (("baseline", 0.35), ("10% slower idea", 0.385),
                     ("slower GPU", 0.55)):
    steps, log = run(step_s)
    print("%-16s steps=%4d tokens=%6.1fM" %
          (name, steps, steps * TOKENS_PER_STEP / 1e6))
    print("   lr multiplier at 25/50/75/100%% of budget: %s" %
          " ".join("%.2f" % log[m][1] for m in sorted(log)))
baseline         steps= 868 tokens= 455.1M
   lr multiplier at 25/50/75/100% of budget: 1.00 1.00 0.50 0.00
10% slower idea  steps= 790 tokens= 414.2M
   lr multiplier at 25/50/75/100% of budget: 1.00 1.00 0.50 0.00
slower GPU       steps= 556 tokens= 291.5M
   lr multiplier at 25/50/75/100% of budget: 1.00 1.00 0.50 0.00

Read the output as a statement about incentives. A change that makes every step 10% slower must repay the 78 steps it loses (868 down to 790) with a better loss per step, and a slower GPU gets only 556 steps and 291 million tokens, so its val_bpb is not comparable with the faster machine's at all. This is why the README says results are comparable on the same platform but not across platforms. It is also why the schedule has to be a function of time rather than of step: the learning-rate decay lands in the last half of the budget however many steps that turns out to be. The metric rewards ideas that make training better and ideas that make it faster, and it cannot tell them apart.

Common misconception

"A fixed time budget makes the comparison fair, so a lower val_bpb means the idea is better." It makes the comparison fair at that budget on that machine. An idea that wins in five minutes may win because it learns fast early (a larger learning rate, a smaller model that fits more steps), and lose or tie over a longer run when the slower-starting alternative catches up. Whether five-minute winners are also longer-run winners is a question about transfer, and it is the extension Artifact 1 adds: log the gap between the proxy gain and a held-out gain for every kept experiment, so overfitting to the five-minute proxy is measured instead of assumed. Chapters 02 and 03 build the tools for it.

The loop in about fifty lines

To see the state machine, write it. The script below is a deliberately small stand-in. Its train function plays the part of train.py: it maps a config (a learning rate and a depth) to a score with a known optimum and some seed noise, and crashes six times in a hundred. The proposer changes one thing at random; a real agent would change something sensible, but the control flow around it is identical. The loop spends an eight-hour night in units of 340 seconds, which is the 300-second run plus 40 seconds that I assumed for start-up, evaluation and the git commit.

The idea

  1. kept ← baseline config; best ← its score (run 0, unmodified)
  2. while the clock allows one more run:
  3.    candidate ← kept with one change; score ← run it
  4.    no score ⇒ crash; score < best ⇒ keep and update; else discard
  5.    append a row to the log
"""A keep-or-revert research loop as a state machine with a budget.

The 'train' function stands in for train.py: a score that depends on the
config plus seed noise. Lower is better, as with val_bpb.
"""
import hashlib
import random

BUDGET_S = 8 * 3600        # wall-clock allowance for the whole night
RUN_S, OVERHEAD_S = 300, 40  # 5 minutes of training + startup/eval/commit
TIMEOUT_S = 600            # program.md: kill anything over 10 minutes

# ── 1. The inner task: config in, noisy score out ────────────────────────
def train(cfg, rng):
    lr, depth = cfg["lr"], cfg["depth"]
    ideal = 0.89 + 9.0 * (lr - 0.03) ** 2 + 0.004 * (depth - 10) ** 2
    if rng.random() < 0.06:                  # a run that crashes
        return None
    return ideal + rng.gauss(0, 0.003)       # seed noise, sd 0.003

# ── 2. The proposer: change one thing in the kept config ─────────────────
def propose(cfg, rng):
    new = dict(cfg)
    if rng.random() < 0.5:
        new["lr"] = round(cfg["lr"] * rng.choice([0.8, 0.9, 1.1, 1.25]), 4)
    else:
        new["depth"] = max(2, cfg["depth"] + rng.choice([-2, -1, 1, 2]))
    return new

# ── 3. The loop: PROPOSE -> RUN -> DECIDE, until the budget is spent ─────
rng = random.Random(7)
kept = {"lr": 0.05, "depth": 8}
best = train(kept, rng)                      # run 0: the unmodified baseline
clock, rows = RUN_S + OVERHEAD_S, [("baseline", best, "keep")]
while clock + RUN_S + OVERHEAD_S <= BUDGET_S:
    cand = propose(kept, rng)
    score = train(cand, rng)                 # RUN
    clock += RUN_S + OVERHEAD_S
    tag = hashlib.sha1(repr(sorted(cand.items())).encode()).hexdigest()[:7]
    if score is None:                        # DECIDE: crash -> discard
        rows.append((tag, 0.0, "crash"))
    elif score < best:                       # DECIDE: lower is better -> keep
        kept, best = cand, score
        rows.append((tag, score, "keep"))
    else:                                    # DECIDE: equal or worse -> revert
        rows.append((tag, score, "discard"))

# ── 4. The log, as results.tsv would show it ─────────────────────────────
counts = {s: sum(r[2] == s for r in rows) for s in ("keep", "discard", "crash")}
print("experiments:", len(rows), counts)
print("clock used : %.2f h of %.1f h" % (clock / 3600, BUDGET_S / 3600))
print("kept config:", kept, " best score %.4f" % best)
for r in rows[:6]:
    print("%-9s %.6f  %s" % r)

Eighty-four experiments fit in the night: the clock reaches 7.93 hours of 8, so the budget, not the proposer, ends the loop. Nine proposals were kept, seventy-one discarded and four crashed. That is about 10.5 experiments an hour. The README's "about 12 an hour" is the five-minute ceiling (60 divided by 5); my 40 seconds of overhead per run is an assumption, and the real overhead on your machine is the first thing to measure in Lab 1, because it decides what "a hundred overnight" actually costs. The last block shows the log: the baseline row, a keep, a crash (note the zeros, the convention from program.md), another keep, and two discards.

Look at what the three branches of DECIDE do to the future. A keep changes the state: the kept config is now the new starting point and the bar to beat is lower. A discard changes nothing except the log. A crash also changes nothing, but it spent five minutes or more of the budget, so a proposer that crashes often is expensive even though no score was recorded. Three kinds of waste, one budget.

One pass, step by step

The stepper below follows a single iteration through the files and processes involved. The numbers are illustrative.

Step through

One pass of the loop, from idea to log row

  1. Start from a baseline. The branch exists, and results.tsv holds one row: the unmodified train.py scored 0.9751 (illustrative numbers throughout).
  2. The agent edits train.py. Any idea inside the file is allowed: architecture, optimiser, batch size.
  3. Commit before running. Every experiment is a commit, so a revert is one git command and the history is the lab notebook.
  4. Run for the fixed budget. All output is redirected to run.log; the agent does not watch it stream.
  5. Read two lines. grep pulls val_bpb and peak_vram_mb from the log. If the lines are missing, the run crashed.
  6. Compare. 0.9702 is lower than the best so far, 0.9751, so the change is an improvement as far as one run can tell.
  7. Record and advance. A row marked keep is appended, and the branch moves forward to this commit.
  8. Or revert, then repeat. Had the score been equal or worse, the row would say discard and the branch would reset to the previous commit. Either way the loop returns to the agent.

Analogy: a test kitchen with one oven slot

Imagine a test kitchen where every recipe tweak gets exactly one twenty-minute oven slot, a tasting panel scores the result, and the head chef's rule is: if it tastes better than the current best, it becomes the house recipe; otherwise the old recipe goes back on the board. A junior cook can run this overnight with no supervision, and the notebook of every attempt is the log. The fixed slot is the time budget: a tweak that needs thirty minutes to shine never gets the chance.

Where it breaks down: a tasting panel scores the same dish similarly each time, while a training run's score changes with the random seed even when nothing about the recipe changed. A kitchen also tastes the dish it will serve. Here the dish that is scored (a five-minute model) is not the dish anyone cares about (a long run), so the panel can be fooled by a recipe that only works in a small oven.

What can go wrong

Because the loop is so simple, its failure modes are easy to list. Each one is a place where an assumption in the design does not hold.

Crashes and hangs

A run can fail with an exception, produce NaN, run out of memory or never return. The ten-minute kill and the grep-for-nothing test turn all of these into one status, crash. A runner that only handles the exception case will hang the night on the first infinite loop.

A lucky keep

The accept rule compares two noisy numbers. When the true change is zero, half of all candidates will beat the baseline by luck at the first comparison, and the bar then moves to the lucky value. Chapter 02 quantifies this.

A moved boundary

If the agent can edit the evaluation, install a package that changes the data, or read a file that leaks the validation set, the score stops meaning what it says. The rule is written down; enforcing it is engineering.

There are quieter ones too. The log is the only memory the loop has, so if the agent forgets what it already tried it may repeat a rejected idea. The budget measures time, so an idea that raises memory use but not speed is free as far as the score is concerned, which is why program.md treats VRAM as a soft constraint. And the instruction "simpler is better, all else being equal" is a tie-breaker the accept rule cannot express: removing code for an equal score is counted as a win in the prose, but the numeric rule (strictly lower) would discard it. A faithful reimplementation has to decide how to honour that.

Key takeaways

  • autoresearch is a research method written as a program: three files, a git branch, a results table and a ten-minute kill. train.py is the only file the agent edits, and prepare.py holds the evaluation it may not change.
  • The loop is a state machine: propose, run, decide, with keep, discard and crash as exits, repeated until the budget is spent. Its only memory is git and results.tsv.
  • A fixed wall-clock budget makes ideas comparable, but it turns every score into a function of the hardware and the step time, and it rewards speed as well as quality.
  • About 12 experiments an hour is the five-minute ceiling; overhead lowers it. Measure your overhead before planning a night.
  • The rule that the evaluator sits outside the proposer's write boundary is the most important sentence in the design, and in the files read it is stated, not enforced.
  • A strictly-lower accept rule on a single noisy score is the weak point. Chapter 02 shows how large the damage is.

Check your understanding

A colleague proposes replacing the five-minute wall-clock budget with a fixed 1,000 steps per run, "so it is the same on every GPU". What is the main thing this changes about the loop?

  1. Nothing: the same number of steps is always the same amount of training.
  2. Ideas that make each step slower are no longer penalised, so the loop stops rewarding speed and can drift towards slow, expensive changes.
  3. The learning-rate schedule can no longer be a function of progress.
  4. Runs can no longer crash.
Under a time budget a slower step means fewer steps, so speed is part of the score. With a fixed step count that pressure disappears; a wider model is just better per step and costs nothing in the metric. The schedule can still follow progress (steps over 1,000), and runs can still crash. The first option confuses equal steps with equal cost.

In program.md, why is the run's output redirected to run.log and read with grep, instead of letting it stream to the agent?

  1. To make the run faster.
  2. Because git cannot commit streamed output.
  3. To make the run reproducible.
  4. To keep the agent's context small, and to give a crash an unambiguous signature: the grep prints nothing.
The file gives the reason of context: hundreds of lines of training logs would crowd out the agent's working memory. A side benefit is that "no val_bpb line" is a single, checkable crash signal. Redirecting output does not change speed or reproducibility.

The night in loop.py ends at 7.93 hours of an 8-hour allowance with 84 experiments, though 12 an hour would suggest 96. What explains the gap?

  1. Each experiment costs more than its five minutes of training: start-up, evaluation and the commit add overhead, 40 seconds in the script's assumption.
  2. Crashes are not counted in the budget.
  3. The loop stops as soon as a kept change is found.
  4. The learning-rate schedule shortens each run.
60 divided by 5 is the ceiling only if overhead is zero. With 340 seconds per experiment, 8 hours gives 84. Crashes are counted (they cost a full slot), the loop does not stop on a keep, and the schedule shapes the learning rate inside the five minutes without shortening them.

Which statement about the evaluation function evaluate_bpb in prepare.py is correct?

  1. The agent may rewrite it if the new version is faster.
  2. It lives in train.py so the agent can tune it.
  3. It is the ground-truth metric; program.md forbids changing it, but in the files read the rule is prose rather than an enforced boundary.
  4. It is enforced by a sandbox that makes prepare.py read-only.
The rule is in program.md and I found no mechanism enforcing it. That distinction is why a runner that holds the evaluator outside the agent's reach is a worthwhile Artifact 1 component. The first two options contradict the file; the fourth claims an enforcement the files do not show.

An idea raises the time per step from 0.35 s to 0.385 s but improves the loss per step slightly. From budget.py it gets 790 steps instead of 868. What must be true for the loop to keep it?

  1. Its loss per step improvement must be positive.
  2. Its per-step improvement must outweigh the roughly 9% of steps it loses, so that its val_bpb after 790 steps is still below the baseline's after 868.
  3. Nothing: any improvement per step is kept.
  4. It must use less memory.
The metric is measured at the end of a fixed clock, not at equal steps. A per-step gain that is smaller than the cost of 78 lost steps ends with a higher val_bpb and is discarded. Memory is a soft constraint and does not enter the keep rule.

In results.tsv, which row would you expect for a run that was killed at ten minutes?

  1. Status discard with the last printed loss.
  2. Status keep, because it never got worse.
  3. No row at all.
  4. Status crash with zeros in the numeric columns.
program.md treats an over-ten-minute run as a failure, discarded and reverted, and logs crashes with zeros. A discard row is for a run that finished with a worse score. Leaving no row would lose the record that the idea was tried, and the log is the loop's memory.

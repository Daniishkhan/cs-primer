Ablation Design & Run Tracking

After a night of keeps you hold a configuration that scores better than the baseline and a pile of changes nobody can separate. An ablation takes the pile apart to find which changes earned their place. This chapter covers how to design one so that interactions are visible, how much noise it can tolerate, and what a run store must record so that every number in a write-up can be traced to a row and replayed.

Why this matters

Artifact 1 produces a run store with at least a hundred experiments and a claim that a loop found real improvements. A reviewer's first questions are "which of these changes mattered?" and "can I rerun row 37?". This chapter serves the Rust run-store step (chapter 05) and the ablation behind the extension (chapter 06). It builds on A0 chapter 4 (seeds and logs) and A0 chapter 22 (caching by content hash and archives you can replay). After it you can design a two-level factorial experiment, read main effects and an interaction from it, say why one-change-at-a-time search misses things, and write a schema for SQLite, a small database engine that ships with Python, for a run store with a replay check. The lab's run store is this schema.

What an ablation is

An ablation removes or switches off one component of a system and measures how much worse (or better) it gets. The word comes from medicine, where tissue is removed to see what it did. In machine learning it answers "which parts of my recipe are doing the work?". The vocabulary is small:

Factor
One thing you can vary: the learning rate, whether a warm-down is used, the weight decay.
Level
A value a factor takes. Two-level designs use "off" and "on", or "baseline" and "changed".
Main effect
The average change in the score when a factor goes from its low level to its high level, averaged over the levels of the other factors.
Interaction
A case where the effect of one factor depends on the level of another: two changes that help alone but not together, or only together.
Confounding
When two changes are made together and cannot be separated afterwards. "I changed the optimiser and the data order" is confounded.

A research loop manufactures confounding. After a night, the kept configuration differs from the baseline by every accepted change, nine of them in the example of chapter 01. Each was accepted because it looked good against the configuration at that moment, in the order the agent tried them. That history is an unreliable guide to the contribution of each change, for the winner's-curse reason of chapter 02 and because some accepted changes may have only mattered in the presence of an earlier one.

One at a time versus all corners

The natural way to find out which of three changes matters is to try them one at a time: add A, keep it if it helps, add B on top, and so on. It is cheap (one run per change) and it is exactly what the greedy loop does. Its blind spot is that it only ever visits some of the possible combinations. The alternative is a full factorial design: run every combination of the factor levels. For three two-level factors that is 2 × 2 × 2 = 8 runs. In the picture below, the left square is the greedy path through two factors and the right cube is the factorial.

The experiment below makes the difference concrete. The simulated truth, which the script knows and the experimenter does not, is that A (a higher learning rate) lowers the score by 0.004, B (a longer warm-down) lowers it by 0.003, C (more weight decay) does nothing, and A and B interact: both fix the same problem, so together they help 0.005 less than the sum of their separate effects. Noise has a standard deviation of 0.0008. The script runs the greedy search, then the eight-run factorial, and estimates each effect as the average score at the high level minus the average at the low level.

The idea

  1. greedy: baseline; baseline + A (keep if lower); then + B on top of A (keep if lower)
  2. factorial: one run at each of the 8 corners of (A, B, C)
  3. effect of a factor ← mean score where it is on − mean where it is off
  4. interaction A × B ← mean where A and B agree − mean where they differ
"""One-at-a-time versus a 2^3 factorial design, on a simulated score.

Three binary changes: A = higher learning rate, B = longer warm-down,
C = more weight decay. True effects on val_bpb (negative helps):
A -0.004, B -0.003, C 0, and an A x B interaction of +0.005 (they fix the
same problem, so together they help less than the sum). Noise sd 0.0008.
"""
import itertools
import random

SIGMA = 0.0008
rng = random.Random(5)

def score(a, b, c):                       # each argument is 0 or 1
    return (0.9200 - 0.004 * a - 0.003 * b + 0.005 * a * b
            + rng.gauss(0, SIGMA))

# ── 1. One-at-a-time, greedy: try A, keep it, then try B on top ──────────
base = score(0, 0, 0)
a_only = score(1, 0, 0)
print("OFAT  baseline %.4f  +A %.4f  (%s)" %
      (base, a_only, "keep A" if a_only < base else "revert"))
with_b = score(1, 1, 0)
print("OFAT  +A+B %.4f vs +A %.4f  (%s)" %
      (with_b, a_only, "keep B" if with_b < a_only else "revert B"))

# ── 2. Full factorial: all 8 corners, one run each ───────────────────────
runs = {cell: score(*cell) for cell in itertools.product((0, 1), repeat=3)}
print("\n A B C   val_bpb")
for cell, v in runs.items():
    print(" %d %d %d   %.4f" % (*cell, v))

# ── 3. Effects from contrasts: mean at high minus mean at low ────────────
def effect(sign):                         # sign(cell) is +1 or -1
    hi = [v for c, v in runs.items() if sign(c) > 0]
    lo = [v for c, v in runs.items() if sign(c) < 0]
    return sum(hi) / len(hi) - sum(lo) / len(lo)

print("\neffect (negative helps), standard error about %.4f" %
      (SIGMA * (2 / 4) ** 0.5))
for name, f in (("A", lambda c: 2 * c[0] - 1), ("B", lambda c: 2 * c[1] - 1),
                ("C", lambda c: 2 * c[2] - 1),
                ("A x B", lambda c: (2 * c[0] - 1) * (2 * c[1] - 1))):
    print("  %-5s %+.4f" % (name, effect(f)))

The greedy search accepts A and then rejects B, because B on top of A scored 0.9185, worse than A alone at 0.9151. It concludes that B is useless. In truth B helps by 0.003 on its own; the interaction cancelled that benefit once A was present. The greedy path never ran B without A, so it could not see this. A different order (B first) would have kept B and then rejected A. The answer depended on the order the ideas arrived in, which is a bad property for a conclusion.

The factorial gets the whole picture from eight runs, each used several times. The A × B interaction is estimated at +0.0019: positive means the score goes up (worse) when both are on, matching the planted +0.005 diluted by the way contrasts average the corners. The main effects of A and B are small and negative (they help, on average over the other factor's levels), and each is estimated with a standard error of about 0.0006, from the formula for a difference of two four-run means.

Notice the row for C. It shows +0.0015, which is 2.6 standard errors from zero, and in truth C does nothing. This is not a bug. With four effects estimated from one noisy table, there is a real chance that one of them looks significant. If you test four independent effects at the 5% level, the chance that at least one looks significant is about 1 − 0.954 ≈ 19%. This is the multiple-comparisons problem of chapter 02 again, in a small design. Two remedies are standard: replicate the experiment on fresh seeds (the same eight corners again) and require an effect to persist, and keep the number of factors small enough that you can afford replication.

Go deeper optional

A full factorial grows as 2k: 8 runs for three factors, 128 for seven. A fractional factorial runs a carefully chosen subset (half, a quarter) and accepts that some effects are confounded with each other, typically high-order interactions that are assumed negligible. In a five-minute loop, 27 runs is a night's budget, so for a handful of kept changes you can afford the full design; for twenty you cannot, and you would instead remove kept changes in groups (leave-one-out, or halves) and follow up on the ones that matter.

The reverse direction is often more useful at the end of a night. Start from the final kept configuration and switch off each kept change in turn, paired over seeds. A change whose removal costs nothing was not earning its place and can be deleted, which the "simpler is better" rule of program.md rewards. A change whose removal costs more than the noise floor has evidence behind it that does not depend on the order in which the loop found it.

Common misconception

"Each kept change was tested, so the final configuration is the sum of independent gains." The change was tested once, in the configuration of the moment, against one noisy baseline. The sum of the reported gains is not the gain of the final configuration: the earlier example reported a gain 4.5 times the true one. Gains from different changes can overlap, as A and B did, and some changes were accepted on luck. The only reliable statement about the final configuration is a direct paired comparison of it against the baseline on fresh seeds.

Run tracking: a row that can be replayed

The experiments above are only as useful as their record. A run store is a table with one row per run, and its purpose is to make three things possible later: finding the runs behind any number in a write-up, comparing runs that should be comparable, and rerunning a run to check it. Each purpose dictates columns.

  • The config, exactly. Store the full configuration, in a canonical form (sorted keys, no whitespace), plus its hash. The same configuration always gives the same hash, so repeated runs of one config group together, and a cache keyed by hash (A0 chapter 22) can skip work already done.
  • The seed and the code version. The seed fixes the randomness. The code version (the git commit of train.py) fixes the program. Without both, a stored config is a recipe for a different dish.
  • The environment. Library versions, the GPU model and driver, and the step count actually reached under the time budget. Chapter 02 showed that the step count is a source of noise; store it.
  • The outcome. A status (keep, discard, crash), the proxy score, the held-out score, the time taken, and the parent run (the kept run whose config this one edited). The parent column turns the table into a tree you can walk back from any kept run to the baseline.

The script builds this table in SQLite (part of the Python standard library, and the same engine you will use from Rust). It records a baseline, three seeds of one candidate and a second candidate, then asks the questions a reviewer would ask: how many runs per config, with what mean proxy and held-out scores and what gap. Finally it replays a stored row and checks that the result is identical.

The idea

  1. canonical form of a config ← JSON with sorted keys; cfg_hash ← first 8 hex digits of its sha1
  2. every run inserts one row: parent, hash, config, seed, status, proxy, held-out, seconds
  3. group by cfg_hash to see replicates; compute the mean gap between held-out and proxy
  4. replay: read a row back, rerun its config with its seed, compare the numbers
"""A run store in SQLite: one row per run, replayable from its config."""
import hashlib
import json
import random
import sqlite3

# ── 1. Schema: everything needed to replay a run, and to judge it ────────
SCHEMA = """
CREATE TABLE runs (
  run_id     INTEGER PRIMARY KEY,
  parent_id  INTEGER REFERENCES runs(run_id),  -- the kept run it edits
  cfg_hash   TEXT NOT NULL,                    -- sha1 of canonical config
  config     TEXT NOT NULL,                    -- canonical JSON
  seed       INTEGER NOT NULL,
  status     TEXT CHECK (status IN ('keep','discard','crash')),
  proxy_bpb  REAL, heldout_bpb REAL,           -- NULL when it crashed
  seconds    REAL
);
CREATE INDEX runs_hash ON runs(cfg_hash);"""

def canon(cfg):                               # same dict -> same bytes
    return json.dumps(cfg, sort_keys=True, separators=(",", ":"))

def train(cfg, seed):                         # deterministic stand-in
    r = random.Random(canon(cfg) + str(seed))
    base = 0.90 + 9 * (cfg["lr"] - 0.03) ** 2
    return base + r.gauss(0, 0.003), base + 0.004 + r.gauss(0, 0.003)

db = sqlite3.connect(":memory:")
db.executescript(SCHEMA)

# ── 2. Record runs, including three seeds of the same config ─────────────
def record(parent, cfg, seed, status):
    proxy, held = train(cfg, seed)
    h = hashlib.sha1(canon(cfg).encode()).hexdigest()[:8]
    cur = db.execute("INSERT INTO runs VALUES (NULL,?,?,?,?,?,?,?,?)",
                     (parent, h, canon(cfg), seed, status, proxy, held, 301.5))
    return cur.lastrowid

root = record(None, {"lr": 0.05, "depth": 8}, 0, "keep")
for seed in (0, 1, 2):
    record(root, {"lr": 0.04, "depth": 8}, seed, "discard")
record(root, {"lr": 0.035, "depth": 8}, 0, "keep")

# ── 3. Queries a reviewer would ask ──────────────────────────────────────
print("per config: runs, mean proxy, mean held-out, mean gap")
for row in db.execute("""SELECT cfg_hash, config, COUNT(*), AVG(proxy_bpb),
        AVG(heldout_bpb), AVG(heldout_bpb - proxy_bpb)
        FROM runs GROUP BY cfg_hash ORDER BY MIN(run_id)"""):
    print("  %s %-24s n=%d  %.4f  %.4f  gap %+.4f" % row)

# ── 4. Replay: re-run a stored row from its config and compare ───────────
run_id, cfg_json, seed, stored = db.execute(
    "SELECT run_id, config, seed, proxy_bpb FROM runs WHERE run_id = 3"
).fetchone()
again, _ = train(json.loads(cfg_json), seed)
print("replay of run %d: stored %.6f, again %.6f, identical: %s" %
      (run_id, stored, again, stored == again))
per config: runs, mean proxy, mean held-out, mean gap
  aef45ea1 {"depth":8,"lr":0.05}    n=1  0.9026  0.9062  gap +0.0035
  86e8fd4f {"depth":8,"lr":0.04}    n=3  0.9030  0.9040  gap +0.0010
  3f9b4c3c {"depth":8,"lr":0.035}   n=1  0.9062  0.9098  gap +0.0036
replay of run 3: stored 0.905935, again 0.905935, identical: True

Three runs of the lr 0.04 config sit under one hash with their mean scores, and the gap column (held-out minus proxy, so positive means the held-out score is worse) is recorded next to the score it qualifies. The replay line is the test of the design: re-running run 3 from its stored config and seed gives the identical number, 0.905935, because every source of randomness was declared. In this script that is trivial, since the stand-in is seeded from the config and seed. On a real GPU it is not, and the honest statement of the guarantee changes: with the same code, config, seed and library versions, a replay should land within the noise floor of the original (or exactly, if you enable deterministic kernels and accept the speed cost). A replay that differs by more than that signals an undeclared source of randomness, such as an unseeded data shuffle or a changed library version. Treat that as a bug to find before the night starts.

Analogy: a mixing desk

A sound engineer with a mixing desk of forty sliders knows that changing one slider at a time finds problems fast, and that two sliders can fight: raising the bass and lowering the low-mid might each sound better alone and muddy together. A good engineer writes down the position of every slider for each take, so a take can be recreated. A factorial design is a systematic pass over a few sliders; the run store is the sheet of slider positions.

Where it breaks down: the engineer hears the result immediately and can undo it. A training run takes minutes and returns one noisy number, so you cannot tweak and listen. That is why the design has to be settled before you start.

Systems connection

A run store is an append-only log with a content-addressed key, the same pattern as a version-control object store or an event-sourced system. Rows are written once and never edited; a correction is a new row that points at the old one. The hash of the canonical config is a content address: equal inputs give equal keys, which is also what makes build caches and deduplicating storage work. The parent column is a pointer that makes the log a tree. If you have used a write-ahead log, an immutable audit trail or a package lockfile, you already know why "store what you ran, not what you meant to run" is the rule.

State of play, October 2026

Two public records show these habits at work, both read on 15 October 2026. The modded-nanogpt README keeps a numbered table of records with, for each, a time, a description of what changed, a date and the contributors, and its listing credits individual techniques (for example the Muon optimiser, rotary embeddings, 8-bit floating-point (FP8) matrix multiplication and capturing a whole training step as a CUDA graph (CUDA is Nvidia's GPU programming platform)). Each record folder carries run logs, and the README requires enough of them to show significance (see chapter 02). nanochat's leaderboard likewise records for each entry the time, the validation score, a CORE score (a multi-task benchmark average), the metric in nanochat's README and a one-line description, such as "d26 +fp8" or "Dataset changed to NVIDIA ClimbMix". Neither is a schema you must copy. Both show the same habit: one row per claim, a description of the single change, and logs behind it. What may change: the records, scores and formats. The need for a row per run does not.

Key takeaways

  • An ablation toggles one component and measures the change. A loop's final configuration is a pile of confounded changes, so the ablation is how you earn the right to say which ones mattered.
  • One-at-a-time search visits few corners and can miss or reverse an effect through an interaction. A full factorial runs every combination and estimates main effects and interactions from the same runs.
  • With several effects estimated from one noisy table, one will often look significant by chance. Replicate on fresh seeds before believing it.
  • The sum of reported gains is not the gain of the final configuration. Compare the final configuration against the baseline directly, paired over seeds.
  • A run row stores the canonical config and its hash, the seed, the code version, the environment and step count, the status, the proxy and held-out scores and the parent. Replay a row to test that nothing random was left undeclared.
  • On a GPU, replay is exact only with deterministic kernels; otherwise expect agreement within the noise floor.

Check your understanding

Why can a greedy one-change-at-a-time search wrongly reject a change that helps on its own?

  1. Because it always runs the changes in the wrong order.
  2. Because each change is tested with too many seeds.
  3. Because the change is tested only on top of earlier accepted changes, and an interaction can cancel its benefit there.
  4. Because ablations cannot detect help.
B was tested only with A already on, where the interaction removed its benefit. The order is arbitrary rather than always wrong, and more seeds would not help the greedy path visit the missing corner.

How many runs does a full factorial over four two-level factors need, and how many corners does one-change-at-a-time visit if it tests each change once?

  1. 16, and 5 (baseline plus four).
  2. 8, and 4.
  3. 4, and 16.
  4. 16, and 16.
24 = 16 corners. The greedy search runs the baseline and then one extra run per change, 1 + 4 = 5, which visits only 5 of the 16 corners.

In the factorial output, factor C (truly no effect) shows an effect of +0.0015 with a standard error of about 0.0006. What should you do?

  1. Conclude that C hurts and remove it permanently.
  2. Conclude that C has no effect because the true value was zero.
  3. Ignore the whole table.
  4. Treat it as a possible chance result among several estimated effects, and replicate on fresh seeds before acting.
Four effects are estimated from one table, so the chance that at least one looks 2 standard errors out is about one in five. You cannot know the true value, which the script does but the experimenter does not. Acting on the first estimate would repeat the winner's-curse mistake; discarding the table wastes the other estimates.

The reported gains of nine kept changes sum to 0.012, but a direct paired comparison of the final configuration against the baseline on fresh seeds gives 0.005. What is the most likely explanation?

  1. The paired comparison is biased low.
  2. Selection on noise inflated the individual gains, and some changes overlap, so the gains do not add.
  3. The baseline changed.
  4. Nine is too many changes to ablate.
Both effects from chapter 02 and this chapter point the same way: kept gains are inflated by luck and gains can overlap through interactions. A paired comparison on fresh seeds is the unbiased check. The baseline is fixed by definition, and nine changes can be ablated in the leave-one-out way described above.

Which column set is the minimum for a run row that can be replayed?

  1. Canonical config, seed, code version, and the environment (including libraries and hardware).
  2. Status and score only.
  3. The agent's description of the idea and the score.
  4. The hash of the score.
Replay needs everything that determines the run: what to run, with which randomness, on which code and in which environment. A description or a score alone cannot recreate the run, and a hash of the score identifies nothing about how it was produced.

A replay of a stored GPU run lands 0.0015 away from the original, inside a noise floor of 0.003. How should you read this?

  1. The run store is broken.
  2. The original run was wrong.
  3. It is consistent with run-to-run nondeterminism; exact equality would need deterministic kernels, or a stricter bitwise check.
  4. The replay proves the idea works.
Within the noise floor means the replay is statistically consistent with the original. Bitwise equality is a stronger property you get only by removing nondeterminism. A single replay can neither prove nor disprove the idea; it checks that the record is complete.

Workbench 1: autoresearch on a CPU Proxy

Karpathy's autoresearch is a loop in which an agent edits one training file, trains for a fixed five minutes on a GPU, keeps the edit if val_bpb went down and undoes it otherwise. The lab VM has no GPU. Here you cut the real train.py down until it runs on sixteen CPU cores, with every change written down, and then run the real loop on it. You measure what the loop's own log cannot tell you: how long an experiment takes, how far the score moves when nothing changed, and whether the "improvements" survive a re-run on seeds the loop never used.

Why measure it

This workbench is the groundwork for Artifact 1, autoresearch-rs. Before you rewrite the runner, sandbox and run store in Rust, you should know the numbers it has to reproduce: seconds per experiment, the noise floor, and what the stock keep rule does with that noise. Chapter 1 describes the loop; chapter 2 says that a single comparison of two noisy scores is a coin toss when nothing changed. Both are easy to read and easy to believe too much. A proxy here is a cheap stand-in for the thing you care about (a 30-second CPU run in place of a five-minute GPU run). The noise floor is how far the score moves when nothing is changed. A wall-clock budget is a limit in seconds, not steps. After this page you can say, with measured numbers, how much of an autoresearch log is signal.

What you need

  • Machine: the lab VM (16 vCPUs, 64 GB, Python 3.12, PyTorch CPU, uv). No GPU. The scripts were run there and nowhere else.
  • Disk and downloads: 351 MB for four data shards (three for training and the pinned validation shard) plus the tokeniser, and three small Python packages (rustbpe, pyarrow, requests).
  • Time: about three hours with reading. The 24 noise runs took 20 minutes; the 30-experiment loop with its confirmation took 41 minutes with the time budget and 35 with the step budget.
  • Optional: an OpenAI API key, for the proposer that asks a small chat model for the next edit. One call measured 486 tokens, so a 30-experiment loop is about 15,000 tokens, far below the few dollars you might budget. Without a key, use --proposer random.
  • A shared machine. The VM was also running other people's jobs while I measured. Its load average was between 12 and 30 on 16 vCPUs, and every table below has a load column so you can see it. Your numbers will differ, and that is part of the lesson.

Predict before you run

Autoresearch fixes the time and lets the amount of training vary. How much training a budget buys is a division: the machine's peak speed times the fraction of it you actually use (the model FLOPs utilisation, MFU), times the seconds, divided by the FLOPs one token costs. The rule of thumb that a token costs about six FLOPs per parameter, forward and backward, is the "6ND" rule of A2 chapter 16; the script h100_budget.py below uses autoresearch's own count, which adds the attention term.

D = (Fpeak × MFU × t) / C

Here D is the number of training tokens, Fpeak the peak FLOP/s (989.5 trillion, the constant train.py divides by), t the budget in seconds and C the FLOPs per token. The noise side of the page rests on the paired test of chapter 2: a difference is believed only when it is large against the spread of differences.

Your prediction

Write down four numbers before you read on. (1) The published setting is a depth-8, width-512 model, 50.3 million parameters, 239 million FLOPs per token (computed below). At 25%, 40% and 50% MFU, how many tokens and optimiser steps does 300 seconds buy on one H100? (2) The CPU proxy here is a 5-million-parameter model trained for 30 seconds. How long will one whole experiment take on this VM, including start-up and the final evaluation? (3) Run the unmodified baseline six times with nothing changed. What standard deviation of val_bpb do you expect, (a) with the same seed and a time budget, (b) with new seeds and a time budget, (c) with the same seed and a step budget, (d) with new seeds and a step budget? (4) In 30 experiments with the stock keep rule, how many do you expect to be kept, and if you re-run the first and last kept versions on fresh seeds, does the last one win?

Check my reasoning, then the measurements below

The H100 arithmetic is the formula above; the only guess is MFU, and the script prints the real mfu_percent when you run train.py on a GPU. For the noise I reasoned from the mechanism. A seed fixes the initial weights and the order of the data; a step budget fixes how many updates happen. So (c), the same seed and the same number of steps, should repeat bit for bit if the CPU kernels are deterministic, and its standard deviation should be zero. (d) adds seed noise only. (a) adds a different number of steps each run, because the budget is seconds and the machine is shared; (b) adds both. If throughput noise were large, (a) and (b) would show a bigger spread than (d). For (4) I had no prior: the stock rule keeps any lower score, so with noise this size I expected several keeps that are not real. The measurements below say how it turned out.

Set up: a CPU copy of autoresearch, and exactly what changed

Autoresearch's train.py will not run on a CPU as published. It loads FlashAttention 3 through the kernels package, which needs an NVIDIA card; it calls torch.cuda in several places; and prepare.py, which holds the data loader and the evaluation, pins memory and puts buffers on the GPU. A CPU port is therefore a set of edits, and the first rule of this page is that the edits are listed, applied by a script that refuses to run if the upstream file has moved on, and shown as a diff. Two further warnings. prepare.py says its evaluation is "DO NOT CHANGE", because it is the fixed metric; I changed its constants (the context length and the number of validation tokens) to make a CPU run possible, so the val_bpb numbers here are not comparable with anyone else's, including numbers from a GPU run of the real thing. And I used the repository as it stood on 15 October 2026: commit 228791f of 25 March 2026.

The measurement script

The idea

  1. run train.py as a subprocess with the seed, the time budget and an optional step budget in its environment, and parse the summary block
  2. noise: run the unmodified baseline 6 times in each of four cells (time or step budget, same seed or new seeds) and print the spread
  3. edit one constant of train.py per experiment; a rule or a small chat model chooses which
  4. loop: run it, keep it if val_bpb is strictly lower than the best so far, otherwise put the old file back (the stock rule)
  5. write one line per experiment to results.tsv, with the steps, the wall time and the machine load beside the score
  6. afterwards, re-run the first and the last kept version on fresh seeds, paired by seed, and report the gain and its t value
"""autoresearch on a CPU proxy: run the loop, then measure its noise.

Run on the lab VM, after cpu_patch.py and prepare.py (see the page):

    python3 autoresearch_cpu.py noise --repo ~/work/re-build/ar-cpu
    python3 autoresearch_cpu.py loop  --repo ~/work/re-build/ar-cpu \
        --experiments 30 --proposer api      # or --proposer random

noise  runs the unmodified baseline several times in four conditions
       (time or step budget, same seed or new seeds) and prints how far
       val_bpb moves with nothing changed.
loop   is autoresearch's loop: propose one edit to a hyperparameter
       constant in train.py, run it, keep it if val_bpb is strictly
       lower than the best so far, otherwise put the old file back.
       Then it re-runs the first and the last kept version on fresh
       seeds, to see whether the "improvement" holds. With --fixed-steps
       every run stops after --steps optimiser steps, not after --budget
       seconds.

Needs: Python 3.9+, a patched autoresearch checkout, the standard
library only. --proposer api needs OPENAI_API_KEY in the environment
(source ~/.config/lab.env); it is read, never printed or written.
"""
import argparse
import hashlib
import json
import math
import os
import random
import re
import shutil
import subprocess
import sys
import time
import urllib.request

# ── 1. Settings ──────────────────────────────────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("cmd", choices=["noise", "loop"])
ap.add_argument("--repo", default=os.path.expanduser("~/work/re-build/ar-cpu"))
ap.add_argument("--budget", type=int, default=30)     # seconds of training
ap.add_argument("--steps", type=int, default=30)      # step-budget runs
ap.add_argument("--seeds", type=int, default=6)       # noise: runs per cell
ap.add_argument("--threads", type=int, default=4)     # OMP_NUM_THREADS
ap.add_argument("--experiments", type=int, default=30)
ap.add_argument("--proposer", choices=["random", "api"], default="random")
ap.add_argument("--model", default="gpt-5.4-nano")
ap.add_argument("--confirm", type=int, default=5)     # loop: fresh seeds
ap.add_argument("--fixed-steps", action="store_true")  # loop: step budget
ap.add_argument("--seed", type=int, default=0)        # proposer's own seed
ap.add_argument("--out", default="w01_out")
args, _ = ap.parse_known_args()        # notebooks pass their own flags
os.makedirs(args.out, exist_ok=True)
TRAIN = os.path.join(args.repo, "train.py")
FIXED = args.cmd == "loop" and args.fixed_steps
STAT = re.compile(r"^(\w+):\s+(-?[\d.]+)\s*$", re.M)


# ── 2. One training run, as a subprocess ─────────────────────────────
def run_train(seed, budget=None, steps=0):
    """Run train.py once. Returns a dict, with val_bpb None on a crash."""
    steps = steps or (args.steps if FIXED else 0)
    env = dict(os.environ, AR_SEED=str(seed), OMP_NUM_THREADS=str(
        args.threads), AR_BUDGET=str(budget or args.budget),
        AR_STEPS=str(steps))
    load1 = os.getloadavg()[0]
    t0 = time.time()
    try:
        done = subprocess.run([sys.executable, "train.py"], cwd=args.repo,
                              env=env, capture_output=True, text=True,
                              timeout=20 * (budget or args.budget))
        text = done.stdout.split("---")[-1] if "---" in done.stdout else ""
    except subprocess.TimeoutExpired:
        text = ""
    stats = {k: float(v) for k, v in STAT.findall(text)}
    return {"seed": seed, "val_bpb": stats.get("val_bpb"),
            "steps": int(stats.get("num_steps", 0)),
            "train_s": stats.get("training_seconds"),
            "wall_s": round(time.time() - t0, 1), "load1": round(load1, 1)}


def mean(xs):
    return sum(xs) / len(xs)


def sd(xs):
    m = mean(xs)
    return math.sqrt(sum((x - m) ** 2 for x in xs) / (len(xs) - 1))


# ── 3. noise: nothing changed, how much does val_bpb move? ───────────
def noise():
    cells = [("time budget, same seed", dict(), lambda i: 42),
             ("time budget, new seeds", dict(), lambda i: i + 1),
             ("step budget, same seed", dict(steps=args.steps), lambda i: 42),
             ("step budget, new seeds", dict(steps=args.steps),
              lambda i: i + 1)]
    print(f"{'condition':26s} {'mean':>7s} {'sd':>7s} {'range':>7s} "
          f"{'floor':>7s} {'steps':>6s} {'wall s':>7s} {'load':>5s}")
    log = open(os.path.join(args.out, "noise.jsonl"), "w")
    for name, kw, seed_of in cells:
        runs = [run_train(seed_of(i), **kw) for i in range(args.seeds)]
        for r in runs:
            log.write(json.dumps(dict(r, cell=name)) + "\n")
        log.flush()
        v = [r["val_bpb"] for r in runs if r["val_bpb"] is not None]
        if len(v) < 2:
            print(f"{name:26s} fewer than 2 runs finished")
            continue
        floor = 1.96 * math.sqrt(2) * sd(v)
        print(f"{name:26s} {mean(v):7.4f} {sd(v):7.4f} "
              f"{max(v) - min(v):7.4f} {floor:7.4f} "
              f"{mean([r['steps'] for r in runs]):6.1f} "
              f"{mean([r['wall_s'] for r in runs]):7.1f} "
              f"{mean([r['load1'] for r in runs]):5.1f}")


# ── 4. Editing train.py: one constant at a time ──────────────────────
KNOBS = {   # name: (allowed values, or None for a free multiplier, lo, hi)
    "EMBEDDING_LR": (None, 0.05, 3.0), "UNEMBEDDING_LR": (None, 0.0005, 0.05),
    "MATRIX_LR": (None, 0.005, 0.3), "SCALAR_LR": (None, 0.05, 3.0),
    "WEIGHT_DECAY": (None, 0.0, 1.0), "WARMDOWN_RATIO": (None, 0.1, 0.9),
    "WARMUP_RATIO": ([0.0, 0.05, 0.1, 0.2], 0.0, 0.2),
    "FINAL_LR_FRAC": ([0.0, 0.05, 0.1, 0.2], 0.0, 0.2),
    "DEPTH": ([3, 4, 5, 6], 3, 6),
}


def read_knob(name):
    for line in open(TRAIN):
        m = re.match(rf"^{name}\s*=\s*([^#\n]+?)\s*(#.*)?$", line)
        if m:
            return eval(m.group(1), {})      # our own file, plain numbers
    raise KeyError(name)


def write_knob(name, value):
    src = open(TRAIN).read()
    new, n = re.subn(rf"^({name}\s*=\s*)[^#\n]+?(\s*(#.*)?)$",
                     lambda m: m.group(1) + repr(value) + m.group(2),
                     src, count=1, flags=re.M)
    assert n == 1, name
    open(TRAIN, "w").write(new)


# ── 5. Two proposers: a rule, and a small model ──────────────────────
class RandomProposer:
    """Stand-in for the agent: scale one constant by a random factor."""

    def __init__(self, seed):
        self.rng = random.Random(seed)

    def propose(self, history):
        name = self.rng.choice(sorted(KNOBS))
        allowed, lo, hi = KNOBS[name]
        cur = read_knob(name)
        if allowed:
            value = self.rng.choice([v for v in allowed if v != cur])
        else:
            value = cur * self.rng.choice([0.5, 0.7, 1.4, 2.0])
            value = round(min(hi, max(lo, value)), 6)
        return name, value, "random rescale"


class ApiProposer:
    """A small chat model reads the constants and the results table."""

    def __init__(self, model, fallback):
        self.model, self.fallback = model, fallback
        self.tokens = 0

    def propose(self, history):
        knobs = {k: read_knob(k) for k in KNOBS}
        rows = "\n".join(f"{h['name']}={h['value']} -> {h['val_bpb']} "
                         f"({h['status']})" for h in history[-12:])
        prompt = (
            "You tune a tiny GPT trained for 30 seconds on a CPU. Lower "
            "val_bpb is better. Current constants:\n"
            f"{json.dumps(knobs)}\nRecent experiments:\n{rows or 'none'}\n"
            "Change exactly ONE constant to a new number. Reply with JSON "
            'only: {"name": ..., "value": ..., "why": "one sentence"}. '
            f"Names allowed: {sorted(KNOBS)}.")
        body = {"model": self.model, "max_completion_tokens": 300,
                "messages": [{"role": "user", "content": prompt}]}
        req = urllib.request.Request(
            "https://api.openai.com/v1/chat/completions",
            data=json.dumps(body).encode(),
            headers={"content-type": "application/json",
                     "authorization": "Bearer " + os.environ["OPENAI_API_KEY"]})
        try:
            with urllib.request.urlopen(req, timeout=60) as r:
                reply = json.loads(r.read())
            self.tokens += reply["usage"]["total_tokens"]
            data = json.loads(re.search(r"\{.*\}", reply["choices"][0][
                "message"]["content"], re.S).group(0))
            name, value = data["name"], float(data["value"])
            allowed, lo, hi = KNOBS[name]
            if name == "DEPTH":
                value = int(value)
            assert lo <= value <= hi and value != read_knob(name)
            return name, value, str(data.get("why", ""))[:80]
        except Exception as e:                    # bad reply: use the rule
            name, value, why = self.fallback.propose(history)
            return name, value, f"fallback ({type(e).__name__})"


# ── 6. loop: keep if strictly lower, else put the old file back ──────
def loop():
    rule = RandomProposer(args.seed)
    prop = rule if args.proposer == "random" else ApiProposer(args.model, rule)
    tsv = open(os.path.join(args.out, "results.tsv"), "w")
    tsv.write("exp\tstatus\tval_bpb\tsteps\twall_s\tload1\tchange\twhy\n")
    first_src = open(TRAIN).read()
    base = run_train(42)
    best, history = base["val_bpb"], []
    tsv.write(f"0\tkeep\t{best:.6f}\t{base['steps']}\t{base['wall_s']}\t"
              f"{base['load1']}\tbaseline\t\n")
    print(f"exp  0 keep    {best:.4f}  baseline, {base['steps']} steps")
    for i in range(1, args.experiments + 1):
        name, value, why = prop.propose(history)
        before = open(TRAIN).read()
        write_knob(name, value)
        r = run_train(42)
        v = r["val_bpb"]
        status = "crash" if v is None else "keep" if v < best else "discard"
        if status == "keep":
            best = v
        else:
            open(TRAIN, "w").write(before)             # revert
        history.append(dict(name=name, value=value, val_bpb=v, status=status))
        tsv.write(f"{i}\t{status}\t{v if v is None else f'{v:.6f}'}\t"
                  f"{r['steps']}\t{r['wall_s']}\t{r['load1']}\t"
                  f"{name}={value}\t{why}\n")
        tsv.flush()
        print(f"exp {i:2d} {status:7s} "
              f"{'-' if v is None else f'{v:.4f}'}  {name}={value}")
    if args.proposer == "api":
        print(f"API tokens used by the proposer: {prop.tokens:,}")
    last_src = open(TRAIN).read()
    confirm(first_src, last_src)


def confirm(first_src, last_src):
    """Fresh seeds, paired by seed: does the kept version beat the first?"""
    diffs = []
    for k in range(args.confirm):
        seed = 1000 + k
        open(TRAIN, "w").write(first_src)
        a = run_train(seed)["val_bpb"]
        open(TRAIN, "w").write(last_src)
        b = run_train(seed)["val_bpb"]
        if a is not None and b is not None:
            diffs.append(a - b)
            print(f"confirm seed {seed}: first {a:.4f}  last {b:.4f}  "
                  f"gain {a - b:+.4f}")
    if len(diffs) > 1:
        t = mean(diffs) / (sd(diffs) / math.sqrt(len(diffs)))
        print(f"mean gain {mean(diffs):+.4f}  sd {sd(diffs):.4f}  "
              f"t = {t:.2f} on {len(diffs)} paired seeds")
    open(TRAIN, "w").write(last_src)


if __name__ == "__main__":
    {"noise": noise, "loop": loop}[args.cmd]()

The script is autoresearch_cpu.py, with a paired notebook, autoresearch_cpu.ipynb. It keeps the stock rule on purpose: lower is kept, equal or worse is reverted, one run on each side, seed 42. The stand-in proposer only changes numeric constants (the learning rates, weight decay, the warm-down fraction, the depth); the real agent edits code, so what it can find is far richer, but the loop around it is identical.

Part 1: the noise floor of the baseline

Run the baseline six times in each of four conditions. A time budget stops each run after 30 seconds of training, as upstream does (upstream does not count the first ten steps against the budget, nor does this port). A step budget stops after 30 steps, via the optional AR_STEPS switch added by the patch.

$ python3 autoresearch_cpu.py noise --repo run-noise --seeds 6

time budget, new seeds      2.1974  0.0208  0.0603  0.0577   45.8    54.7  22.7

What you should see: the noise

The first row is the key one: the same seed, the same code, a 30-second budget, and the score still moved. Its six scores ranged from 2.1396 to 2.1961. The step column explains why: the budget is in seconds, the VM was shared, and the runs completed between 43 and 56 optimiser steps. The run that got 56 steps scored 2.1396; the five that got 43 to 46 scored between 2.18 and 2.20. More steps in the same time meant a better score, and the number of steps depended on what else the machine was doing.

Row 3 is the opposite case. With a step budget and the same seed, all six runs gave 2.277715 exactly: standard deviation zero. The CPU kernels are deterministic here, so a run is a pure function of its seed and step count. That is also the property that Lab 1's replay needs. Row 4 adds new seeds: the spread comes back, 0.022, and the scores split into two groups (three near 2.279 and three between 2.305 and 2.332), so six seeds is a small sample and the sd itself is uncertain by roughly a third either way.

Rows 1, 2 and 4 all have a standard deviation near 0.021 and a single-comparison floor near 0.06 (1.96 × √2 × sd, as in Lab 1). With six runs per cell I cannot say that the time budget adds noise on top of seed noise, only that each source alone is about 0.02, and the two overlap. What I can say is that two single runs of the same code on this machine differ by more than 0.06 in about one comparison in twenty, and that any claim below that needs repeats. Compare the size of the effects the loop will chase: weight decay or a learning rate nudged by 10 or 20% moves this proxy by less than the floor.

Read it as a reviewer would, not as a result. The loop reports a gain of 0.0463 bits per byte, from 2.2006 to 2.1543, with two keeps. Look at the step counts. The baseline got 42 steps; the second keep, UNEMBEDDING_LR=0.006, got 49, on a quieter machine (load 13). The 20 runs after it got 37 to 44 steps and none of them could beat it; the nearest, EMBEDDING_LR=0.25, scored 2.1740 at 44 steps. Across the 31 runs the correlation between the number of steps and val_bpb is −0.81: most of the variation in this log is how many steps the run happened to complete. The loop then spent twenty experiments, a third of an hour, failing to beat a lucky run. Both kept changes are also smaller than the single-comparison floor of 0.059 (the gain is 0.79 of it).

The confirmation answers a different question: is the final version better than the first on seeds the loop never used? It re-runs both on five fresh seeds, paired by seed:

confirm seed 1002: first 2.2389  last 2.2147  gain +0.0242

It is. On fresh seeds the final version is better on all five, by 0.0272 on average (sd 0.0053, a paired t of 11.5 on 4 degrees of freedom, against 2.776 needed). So the loop did find something real: the combination of a lower weight decay and a higher unembedding learning rate helps this proxy. But the gain on fresh seeds is 0.027, about 59% of the 0.046 that the log claimed, and each fresh-seed gain is smaller than the stock rule's single-comparison floor. A paired test over seeds sees what a single comparison cannot. Two cautions. This is the proxy: I did not check it against anything larger. And the confirmation also used the time budget, so its gains include whatever throughput the two runs happened to get.

Part 3: the same loop with the machine's noise removed

Run the same loop with a step budget: every run takes exactly 30 optimiser steps, whatever the machine is doing, and the proposer is the seeded random rule (no API calls). The seed is still 42 for every experiment, as upstream, so a candidate and the best differ only by the edit. With a step budget and a fixed seed a run is repeatable bit for bit, so the stock rule has no run-to-run noise to be fooled by. That is a good place to ask a sharper question: do kept experiments that win on seed 42 also win on other seeds?

Three things stand out. First, determinism pays. With a step budget, an experiment repeated from the same state gives the same score to six decimals. Three of the 30 proposals were exact repeats of an earlier one (experiments 13, 16 and 17 returned the scores of 11, 12 and 10), and the loop ran them again for nothing. The run store of Lab 1, keyed by config hash and seed, would have served them from cache. Second, the logged gain is tiny. Seven experiments were kept, but six of them moved the score by 0.0016 or less; one, FINAL_LR_FRAC=0.2, accounts for 0.0121 of the total 0.0167. That total is 0.27 of the noise floor for new seeds (0.061), so a single seed-42 comparison would call every one of these keeps a win and the noise table says a new seed could erase them.

Third, the confirmation did not confirm. On five fresh seeds the last version beat the first on four and lost on one (seed 1002, −0.0196). The mean gain is +0.0242, but the standard deviation is 0.0341, so t = 1.59 on 4 degrees of freedom, well short of the 2.776 needed. I cannot tell from five seeds whether the final version is better, equal or worse than the baseline. Compare Part 2: there the logged gain was 0.79 of the floor, fresh seeds showed 59% of it, and the paired difference was consistent (t = 11.5). Here the logged claim is a quarter of the floor and the fresh seeds do not settle it. Both are the same lesson: the number to believe is the paired difference on seeds the loop did not use, with its spread.

What the five-minute H100 budget buys: not run here

I have no GPU, so nothing below was measured on an H100. This is arithmetic from numbers in train.py itself, with one assumption marked as such. h100_budget.py builds autoresearch's own model class on PyTorch's meta device for the published setting (depth 8, width 512, vocabulary 8,192, 2,048-token context, 524,288 tokens per step) and for this page's CPU proxy, and converts FLOPs per token into tokens per budget, using the 989.5e12 FLOP/s that the script uses for its utilisation figure. The utilisation (MFU) is a guess; the script prints the real mfu_percent at the end of a GPU run.

  at 25% MFU:    310 M tokens,   592 steps, 10.6 tokens per scaling parameter
  at 40% MFU:    497 M tokens,   947 steps, 16.9 tokens per scaling parameter
  at 50% MFU:    621 M tokens,  1184 steps, 21.1 tokens per scaling parameter

  FLOPs per token (fwd+bwd): 12.0 M, batch 8,192 tokens

If an H100 sustains 40% of peak, 300 seconds buys about 497 million tokens, 947 optimiser steps, and about 17 tokens per scaling parameter, a little under the Chinchilla-style 20 per parameter that nanochat's help text gives. The range is 310 to 621 million tokens for 25% to 50%, so the published setting is plausibly close to compute-optimal for its size, which is a reasonable thing for a time-budgeted search loop to be. The CPU proxy here is a very different regime: 41 steps and about 0.3 million tokens, roughly 0.2 tokens per scaling parameter against the Chinchilla-style 20, so it is nowhere near converged and its scores mostly measure how fast a model learns in its first few dozen steps. The README's own estimate is about 12 experiments an hour on the GPU. On this VM an experiment cost about 59 seconds with the time budget and about 50 with the step budget (means over the two loops), so about 60 an hour.

Break it

Three experiments, each with a prediction. I ran none of them: they are for you, and my predictions are reasoning from the numbers above, not results.

  1. Make the loop paired. Port keep_or_revert from Lab 1 into the loop: run each candidate and the best on three seeds and keep only on a significant paired gain. Prediction: with three seeds the test has two degrees of freedom and needs t > 4.3, so it keeps almost nothing at this noise level (the seven small keeps of Part 3 all vanish), at three times the cost per experiment. Which of the two time budgets does it hurt more?
  2. Lengthen the budget. Run noise with --budget 120. Prediction: the number of steps in a run scales up by about four, the relative spread in the step count shrinks a little, and the sd of val_bpb falls, but not by a factor of four, because seed noise does not shrink with a longer run. Does the step-budget row with new seeds move?
  3. Put the cache in. Add Lab 1's RunStore to run_train and key a run by config hash and seed. Prediction: in the step-budget loop 3 of 30 experiments become free, and in the time-budget loop none do, because the same edit gives a different score each time. Why does the cache help in one case and not in the other?

Key takeaways

  • Autoresearch's budget is wall-clock time, its seed is fixed at 42 and its keep rule is one comparison. On a shared CPU, that makes a run's score depend on how many steps it happened to complete: across the 31 runs of the first loop, steps and val_bpb correlated at −0.81.
  • With nothing changed, the baseline's standard deviation was about 0.021 (single-comparison floor about 0.06), and the same seed with a step budget repeated to six decimals.
  • The stock rule kept two changes in 30 experiments and logged a gain of 0.046. On five fresh paired seeds the gain was 0.027 (t = 11.5): real, and about 59% of what the log claimed.
  • With a step budget the loop kept seven changes for a logged gain of 0.017, 0.27 of the floor, and the fresh-seed confirmation (+0.024, t = 1.59) could not settle it.
  • An experiment cost about a minute on the VM. A deterministic loop re-ran 3 of 30 proposals for nothing; a run store would have caught them.
  • The H100 numbers on this page are arithmetic, not measurements: about 500 million tokens and about 950 steps in five minutes at an assumed 40% utilisation.

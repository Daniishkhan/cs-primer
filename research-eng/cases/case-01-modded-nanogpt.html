modded-nanogpt: a Speedrun as a Research Record

The first row of the modded-nanogpt record table, dated 28 May 2024, is Andrej Karpathy's llm.c reproduction of GPT-2 (124 million parameters) at 45 minutes on 8 H100 GPUs. The last row, dated 30 August 2026, reaches the same validation loss in 0.665 minutes, about 40 seconds. Between the two sit 90 accepted records, each a pull request that had to bring its own logs, its own statistics and a reviewer's agreement. This case study reads the repository as a research instrument: what a record must show, how the rules turned a leaderboard into an evidence ledger, which gains held up, and where the ledger is still only a proxy for what we care about.

What I could and could not read

On 15 October 2026 I fetched and read: the repository README (raw file, 54,932 bytes, including the rules, the record table of 92 numbered records and the Q&A); the README of one record (2025-01-04 SoftCap, with its list of 80 validation losses); one complete record log (the Muon record of 10 October 2024, 471,924 bytes); Keller Jordan's Muon post (8 December 2024); Karpathy's llm.c discussion 481 (28 May 2024); and the GitHub API's public repository fields (stars, forks, dates, contributor count). The tables, counts and charts below come from my own parse of the README table, and the scripts are on this page.

Not read: the posts on X that the table links to for most records (I cannot fetch them), the pull-request discussions, the other 90 record logs and the code of the later records. I did not rerun any record: that needs 8 H100 GPUs. I cannot verify that any logged number was produced as logged; I can check that the logs exist and read the one I fetched. The README is the project's own account, written by its maintainer. Where I say "survived" or "did not" I mean what the README table and technique list show, not an ablation I ran.

The pattern in one sentence

Turn "make this faster" into a public ledger by fixing the task, the target and the hardware, and by accepting a claim only when it arrives with the logs, the statistics and the code that let anyone else check it.

Context: a baseline, a target and an open invitation

The task the repository fixes is one sentence: train a neural network to at most 3.28 cross-entropy validation loss on FineWeb (a large filtered web-text corpus) using 8 NVIDIA H100 GPUs, as fast as possible. The number 3.28 was chosen to match Karpathy's llm.c reproduction of GPT-2 small. In that post (28 May 2024) Karpathy reports training the 124-million-parameter model on 10 billion tokens of FineWeb on one 8-GPU A100 node in about 90 minutes, reaching a loss of "about 3.29" and a HellaSwag score of 29.9 against 29.4 for OpenAI's GPT-2. The speedrun README starts its table at 45 minutes for the llm.c baseline, on its own H100 timing. The two figures describe different hardware, so I do not compare them.

The repository's description of its own purpose is unusually direct. It asks why this is not "just another idiosyncratic benchmark" and answers: because it is competitive. Anyone who sets a record has an open invitation to publish it and take the credit, so a method that works has every incentive to be shown, instead of dying unreported in a private repository. The README quotes the statistician Ben Recht: "Artificial intelligence advances by inventing games and gloating to goad others to play."

Speedrun
A competition to reach a fixed result in the least time. Here the result is a validation loss of 3.28 and the time is measured on 8 H100 GPUs.
Validation loss
The model's average cross-entropy on text it was not trained on. Lower means it predicts that text better. The speedrun measures it on a fixed set of FineWeb tokens.
Record
A change to the training code that reaches the target faster than the previous record, accepted into the repository's history with its log.
Run log
The text file a training run writes: the script's own source, the library versions, the GPU, the loss at checkpoints and the timer. A record pull request must include one.
Inter-run variance
The spread of final validation loss across repeated runs of the same code with different random seeds.
Statistical significance
Evidence that a result is not an accident of that variance. The rules ask for a p-value below 0.01 (chapter 2 explains what that means).
Loss buffer
The small margin (about 0.001 to 0.002) by which the current record is kept below 3.28, so that new submissions are easier to validate.
Provenance
The chain from a claim back to the evidence that produced it: who ran what code, on which machine, with what result.

The mechanism: what a record must show

A leaderboard becomes a research record through its rules. The README lists four conditions for a new record, and I give them in the project's own order, with its wording where short:

  1. Do not change the data. The train and validation pipelines are fixed. Batch size, sequence length and attention structure may change, "just don't change the underlying streams of tokens."
  2. Reach 3.28 in mean, with evidence. "Due to inter-run variance, submissions must provide enough run logs to attain a statistical significance level of p<0.01 that their mean val loss is ≤3.28." The README links an example calculation. It waives this for submissions that "improve speed by optimizing the systems performance, without touching the ML".
  3. No extra compiler flags. No additional torch._inductor.config or torch.compile flags. These "can save a few seconds, but they can also make compilation take >30min". The rule was introduced after record 21.
  4. Be faster than the previous record, on the same hardware.

Two discretionary grounds for refusal complete the picture. A change may be rejected if it "disproportionately degrades the readability of the codebase" (the README's example: a 200-line kernel that saves 300 ms is fine; 500 lines that tangle the optimiser for 50 ms will likely be refused). And because the current record is "intentionally kept roughly 0.001-0.002 loss below 3.28 to make validation simpler", a pull request that spends this buffer must do better than the obvious alternative of simply running fewer steps at equal loss. That last rule closes a loophole in a speed benchmark with a loss target: any run can be made faster by stopping earlier and landing nearer the target line.

What a log shows

The log is the unit of evidence. The one I fetched (record 4, the Muon improvements of 10 October 2024) is a plain text file in three parts: first the full source of the training script that produced it, between two lines of 100 equals signs; then the library version and the output of nvidia-smi, which lists the GPUs; then one line per step with the training loss and the elapsed time, and a validation line every 125 steps. Putting the source inside the log is the key design choice. A log that sits next to the code can drift from it; a log that contains the code cannot. The first thing a reviewer does is read it:

"""Read one speedrun record log the way a reviewer does.

Usage:  python3 read_log.py record.txt

The log is the file a record PR must include: the training script's own
source, the library and GPUs it ran on, then one line per step.
"""
import re
import sys

# ── 1. Split the log into source, machine header and step lines ──────
text = open(sys.argv[1], encoding="utf-8").read()
run = re.search(r"^Running (?:py|Py)[Tt]orch (\S+)", text, re.M)
source, rest = text[:run.start()], text[run.start():]
steps = re.search(r"^step:", rest, re.M)
header, steps = rest[:steps.start()], rest[steps.start():]
gpus = re.findall(r"NVIDIA (H\d+[\w ]*?)\s+On", header)
print(f"source lines : {source.count(chr(10))}")
print(f"library      : PyTorch {run.group(1)}")
print(f"GPUs         : {len(gpus)} x {gpus[0]}")

# ── 2. Pull out the validation checkpoints ───────────────────────────
VAL = re.compile(r"step:(\d+)/(\d+) val_loss:([\d.]+) train_time:(\d+)ms")
vals = [(int(a), int(b), float(c), int(d))
        for a, b, c, d in VAL.findall(steps)]
print(f"steps        : {vals[0][1]}, validated {len(vals)} times")
print(f"val_loss     : {vals[0][2]} at step 0, {vals[-1][2]} at the end")

# ── 3. Is the timer honest? It should only ever run forward ──────────
TRAIN = re.compile(r"step:(\d+)/\d+ train_loss:[\d.]+ train_time:(\d+)ms")
clock = [(int(s), int(t)) for s, t in TRAIN.findall(steps)]
for (s0, t0), (s1, t1) in zip(clock, clock[1:]):
    if t1 < t0:
        print(f"timer reset  : between step {s0} and step {s1} "
              f"(the untimed grace period)")

# ── 4. The claim a record makes ──────────────────────────────────────
TARGET = 3.28
print(f"timed run    : {vals[-1][3] / 60000:.2f} minutes")
print(f"margin       : {TARGET - vals[-1][2]:.4f} under the {TARGET} "
      f"target, from one run")
source lines : 526
library      : PyTorch 2.4.1+cu121
GPUs         : 8 x H100 80GB HBM3
steps        : 6200, validated 51 times
val_loss     : 10.9264 at step 0, 3.2785 at the end
timer reset  : between step 10 and step 11 (the untimed grace period)
timed run    : 22.32 minutes
margin       : 0.0015 under the 3.28 target, from one run

Three things stand out. The timer resets between steps 10 and 11: that is the 10-step untimed "grace period" for kernel warm-up that the README says was replaced after record 21 by an explicit warm-up section, which added about 850 ms to the timed part. The run is 6,200 steps in 22.32 minutes on 8 H100 GPUs, matching the table's 22.3. And the final validation loss, 3.2785, is under the 3.28 target by 0.0015 in this one run. That is a thin margin to rest a claim on, and it is why the rules ask for many runs.

The statistics a record must carry

The README does not name the test; it links to the 2025-01-04 record (record 18, "Lower logit softcap from 30 to 15", by Braden Koszarsky) as the example. That record's README lists 80 validation losses from 80 runs and computes a one-sided one-sample t-test of them against 3.28: mean 3.2791, standard deviation 0.0019, p = 0.0001. The logic is the same paired and unpaired reasoning as Lab 1, applied to a threshold instead of a baseline: is the mean loss below the line by more than the run-to-run spread explains?

Running the numbers shows why 80 runs, not 3, were needed. The mean is 0.0009 below the target and the standard deviation is 0.0019, so a single run lands above the line more often than you would like: 25 of the 80 runs ended above 3.28. A record that wins "on average" is not one that wins every time, and the README's rule is explicit that it is the mean that must clear the target. The table below uses the same arithmetic to show what the rule buys.

What the ledger shows

From my parse of the table, the 92 numbered records span 28 May 2024 to 30 August 2026, 824 days, with a median of 4 days between one record and the next and a longest gap of 120 days. 52 distinct handles appear in the contributor column; the most frequent, with 18 of the 92 rows, is one person (@classiclarryd), followed by the maintainer (@kellerjordan0, 10 rows) and @varunneal (8). The GitHub API reports 68 contributors to the repository, 5,947 stars and 911 forks as of 15 October 2026. My rough count (commas, "&" and "and") finds 18 rows with more than one name. Three rows have no log link: record 3 (the introduction of Muon, 24.9 minutes, 4 October 2024), record 66 (a PyTorch 2.10 upgrade) and record 86, which links only its pull request. All the others link a log file or a log folder.

The README's list of techniques gives a sense of what the gains were made of: a modern architecture (rotary embeddings, QK-norm, squared ReLU), the Muon optimiser, 8-bit floating point (FP8) for the output head and later the MLP and attention projections, FlashAttention 3 with sliding windows, value embeddings, skip connections, a bigram hash table, and "many systems optimizations". Some records are plainly ML (a new optimiser, an extra embedding), some are plainly systems (record 22, "Faster gradient all-reduce"; record 25, a PyTorch upgrade) and many are both.

What held, what was changed, what was refused

Held and grew

Muon arrived at record 3 and was refined in records 4, 6, 20, 38 (Polar Express replacing Newton-Schulz), 41 (NorMuon), 57 and 80. Value embeddings appear at record 14 and are revised in 15, 16, 17 and 63 (untied). FlexAttention (record 12) was followed by FlashAttention 3 (record 29) for the same job.

Reversed or simplified

Record 8 untied the embedding and the output head (November 2024). Record 51 retied them (December 2025). Record 73 added partitioned hyperconnections; record 77 replaced them with a single saved activation (its log folder is named SimplifyHC). Records 17, 30 and 35 each dropped an attention or MLP layer.

Refused or fenced off

A run with a different tokeniser (2.77 minutes, 20 January 2025) is listed as "technically outside the rules" because the token stream must be fixed. A test-time-training run (23 January 2026) is "a valid probability model" but not a record, since "we are not allowing untimed backward passes."

I want to be careful with the first two cards. They are my reading of the table's descriptions, and the table does not say that record 51 retied the embeddings because record 8 was wrong. Tying and untying were both accepted in their time, when the surrounding model, optimiser and schedule were different. What the pattern shows is not a failed claim but a ledger in which an idea can be undone by a later record without anyone having to argue about it: the rule is only "faster on the same hardware, with the evidence".

Two rule changes mark where the ledger found a gap in its own method. After record 21 the 10-step grace period was replaced by an explicit untimed warm-up, and coordinate_descent_tuning was banned: it saves about 25 minutes of untimed compilation but costs about 3 seconds at run time. Record 21 was re-timed under the new rules, to 2.997 minutes (1 February 2025) and again on a later PyTorch to 3.014 minutes (24 May 2025). The table keeps those re-timings in separate rows, "not a new record". The speed number is only meaningful with its rule version, and the repository records the version.

Common misconception

That the table is a clean sequence of independent, comparable measurements. It is not. The times come from different PyTorch versions (record 7 is a PyTorch upgrade, record 25 another, record 66 a third), different timing rules, and many records bundle several changes in one pull request (records 5, 9, 20, 32 and 90 among them). Record 92 reports a drop from 1.126 to 0.665 minutes with a list of six changes in its description (sampled softmax, FP8 throughout the MLP, a hashed n-gram table, a new optimiser stack, depth reduction, CUDA-graph capture). The table cannot say how much of the drop each change earned. It is evidence that the combination reaches the target faster, which is what the rules ask for, and nothing more.

Where the proxy is only a proxy

The speedrun's own FAQ raises the objection that applies to every benchmark in this course: it "probably won't scale and is just overfitting to val loss". The answer there is honest. It says the objection "is hard to refute, since 'at scale' is an infinite category", that some methods, "particularly those which impose additional structure on the network, such as logit softcapping", are unlikely to scale, and then offers one piece of evidence: a straightforward scale-up of the 18 October 2024 version of the speedrun to 1.5 billion parameters reached GPT-2 (1.5B)-level HellaSwag at $233 against $576 for Karpathy's baseline, according to the README. That is a claim by the maintainer about one scale-up of one early version. The later 70 records have not been through a comparable check that I could find in the README.

The structure of the problem is the one of Lab 1. Every record is selected against the same fixed validation set, the first 10,485,760 tokens of the FineWeb validation split; the target loss is the proxy for a better language model; and 90 successive selections have been made against it. The README keeps the evidence rule (many runs, p<0.01) but the held-out question, whether the gain survives a different dataset, a different scale or a downstream task, sits outside the ledger. The project's strength is that the proxy is cheap, fixed and public, so everyone can check the same claim. Its limit is the same fact.

Muon is a useful test of how far one can trust the process. Jordan's post (8 December 2024) presents Muon as an optimiser for hidden layers, reports a 1.35 times faster speedrun record and gains at 774 million and 1.5 billion parameters, and argues that evidence from a competitive task is stronger than from papers whose baselines may be under-tuned. He also lists what he did not know at the time of writing: whether it scales to much larger training runs, whether it can be distributed across large clusters, and whether it works for fine-tuning or reinforcement learning. The ledger and the author agree on what was shown and on what was not.

Analogy: an athletics record book

A world record in athletics counts only if it was timed with certified equipment, the wind was within a limit, the track was measured and officials signed the result. The record is the claim plus its paperwork, and rules change (a new type of shoe, a revised wind gauge limit) without erasing earlier records, which stay on the list with their date. The speedrun does the same for a training run: certified hardware, a fixed course (the data), a stopwatch (the logged timer) and a rule on statistics in place of the wind gauge.

Where it breaks down: a 100-metre dash has one course and one meaning of fast. A training run is scored on a validation loss that stands in for "a good language model", and the course, FineWeb on 8 H100 GPUs, is only one of the courses a model will ever run.

Five records name an AI system

In the README table, the contributors for records 32, 60, 69, 72 and 87 read "a handle & AI system" followed by a link: hiverge.ai, Locus, Aster, Station and Recursive respectively. The README does not say what part the system played, whether it proposed the change, ran experiments or wrote the code, and I cannot tell from the table. What the table does show is that a ledger designed for human contributors accepted entries produced with automated research systems under the same rules, with the same logs, and recorded that fact in the credit. For Artifact 1 this is the interesting part. A loop like autoresearch can propose changes at a rate no person can, and a ledger like this one is a model of what such a loop must hand over: the code, the logs, the statistics and an honest account of who or what did the work. The same standards apply to your own loop in the write-up chapter.

Try it yourself: read the ledger and the evidence

Two short scripts, standard library only. Fetch the README, the SoftCap record's README and the Muon log (the commands are in the script docstrings), then run them. The output below is from my run on 15 October 2026; a later run will show later records, because the README keeps growing.

"""Read the modded-nanogpt record table and one record's own p-value.

Usage:  python3 record_log.py README.md softcap_README.md

Part 1 parses the "World record history" table of the speedrun README.
Part 2 repeats the acceptance test of one record (80 logged val losses
against the 3.28 target) with the standard library only.
"""
import math
import re
import statistics
import sys

# ── 1. The table ─────────────────────────────────────────────────────
def parse_table(text):
    rows = []
    for line in text.splitlines():
        m = re.match(r"^(\d+) \| ([\d.]+) (minutes?) \| (.*?)\s*\| "
                     r"(\d\d/\d\d/\d\d) \| (.*?) \| (.*)$", line)
        if m:
            n, mins, _, desc, date, log, who = m.groups()
            if rows and int(n) < rows[-1]["n"]:
                break                      # the second table (track 2)
            if desc.startswith("21st record"):
                continue                   # a re-timing, not a new record
            rows.append({"n": int(n), "min": float(mins),
                         "date": date, "log": log.strip(),
                         "who": who.strip()})
    return rows


def year_of(date):
    return 2000 + int(date[-2:])


# ── 2. The record's own acceptance test ──────────────────────────────
def t_sf(t, df):
    """P(T > t) for Student's t, by numerical integration (t > 0)."""
    def pdf(x):
        c = math.exp(math.lgamma((df + 1) / 2) - math.lgamma(df / 2))
        c /= math.sqrt(df * math.pi)
        return c * (1 + x * x / df) ** (-(df + 1) / 2)
    n, hi = 20000, t + 60.0
    h = (hi - t) / n
    s = pdf(t) + pdf(hi)
    for i in range(1, n):
        s += pdf(t + i * h) * (4 if i % 2 else 2)
    return s * h / 3


def one_sample_less(xs, target):
    n = len(xs)
    mean, sd = statistics.fmean(xs), statistics.stdev(xs)
    t = (mean - target) / (sd / math.sqrt(n))
    return mean, sd, t, n - 1, t_sf(-t, n - 1) if t < 0 else 1.0


if __name__ == "__main__":
    rows = parse_table(open(sys.argv[1], encoding="utf-8").read())
    print(f"rows parsed: {len(rows)}   last record: #{rows[-1]['n']} "
          f"{rows[-1]['min']} min on {rows[-1]['date']}")
    no_log = [r["n"] for r in rows if "[log]" not in r["log"]]
    print(f"records with no log link: {no_log}")
    multi = sum(1 for r in rows if "," in r["who"] or "&" in r["who"]
                or " and " in r["who"])
    print(f"records credited to more than one name: {multi} of {len(rows)}")
    for y in (2024, 2025, 2026):
        ys = [r for r in rows if year_of(r["date"]) == y]
        first = ys[0]["min"]
        last = ys[-1]["min"]
        print(f"{y}: {len(ys):2d} records, "
              f"{first:g} -> {last:g} min (x{first / last:.2f})")
    steps = [rows[i]["min"] / rows[i + 1]["min"]
             for i in range(len(rows) - 1)]
    print(f"median gain per record: x{statistics.median(steps):.3f}; "
          f"largest: x{max(steps):.2f} "
          f"(record {rows[steps.index(max(steps)) + 1]['n']})")

    text = open(sys.argv[2], encoding="utf-8").read()
    block = text[text.index("accs = ["):text.index("]", text.index(
        "accs = ["))]
    accs = [float(x) for x in re.findall(r"3\.\d+", block)]
    mean, sd, t, df, p = one_sample_less(accs, 3.28)
    print(f"SoftCap record: n={len(accs)} mean={mean:.4f} sd={sd:.4f} "
          f"t={t:.2f} df={df} p={p:.4f}")
    worst = max(accs)
    print(f"runs above the 3.28 target: "
          f"{sum(a > 3.28 for a in accs)} of {len(accs)} (worst {worst})")

The lessons

  • A claim is a package. The code, the logs, the machine and the statistics travel together, and the log contains the code so they cannot drift apart. Your Artifact 1 write-up needs the same package, with a command that reproduces it (chapter 6).
  • State the noise rule before the result. The rule is "enough runs for p<0.01 against 3.28", and a margin of 0.0015 on one run is not enough. This is the noise floor of chapter 2 and the paired test of Lab 1.
  • Close the cheap loopholes in writing. Compiler flags, an untimed warm-up and a step-count shortcut all changed the number without improving the method, and each got a rule. A research loop whose evaluator has no such rules will find the loopholes itself (A7 chapter 15).
  • A fixed proxy is both the strength and the limit. Everyone can check the same claim, and everyone is optimising the same number. The 1.5B-parameter check in the README is the right kind of question; asking it for each record is the held-out discipline of A7 chapter 16.
  • Small proxies transfer unevenly. The README itself says logit softcapping is unlikely to scale. What a 40-second run teaches about a 40-hour run is the subject of chapter 3.
  • Bundles hide attribution. A record that combines six changes proves the sum. Ablations that separate them are chapter 4.

Key takeaways

  • The speedrun fixes the task, the target (3.28 validation loss on FineWeb), the hardware (8 H100 GPUs) and the evidence a record must carry: logs, code and a p<0.01 test that the mean loss is at most the target.
  • The log embeds the source of the script that produced it. Record 4's log shows a 6,200-step run, a final loss of 3.2785 and a timer reset that the rules later removed.
  • A mean can beat the target while many single runs miss it: for the SoftCap record, 25 of 80 runs ended above 3.28 at a mean of 3.2791.
  • From my parse of the README table: 92 records in 824 days, 45 minutes down to 0.665, 52 handles, five rows crediting an "AI system" alongside a handle.
  • The ledger is a proxy for training faster, selected against one validation set. The project says so itself, and offers one scale-up check; the rest is outside the ledger.
  • Rule changes (compiler flags, warm-up, buffers) are part of the record. A speed figure means nothing without its rule version.

Connect it

Connections

The ledger is a software supply chain applied to results. A pull request is a signed, reviewed change; the log folder is the artifact attached to a release; the rules on compiler flags and warm-up are the reproducible-build discipline that stops a number depending on the build machine. In your own work the matching pieces are a pinned environment and seeds (A0 chapter 4), the statistics of A0 chapter 15 (Statistics for Experiments), compute accounting (A2 chapter 16) and scaling laws (A2 chapter 18). The Chinchilla case asks the same question of a different proxy: what does a small run say about a large one?

Check your understanding

A new submission reaches a mean validation loss of 3.2795 in a single run that took 30 seconds less than the record. Under the repository's rules, why is that not yet a record?

  1. Single runs are never allowed to be faster than the previous record
  2. The loss must be at most 3.2795 exactly, and this is above it
  3. Because of inter-run variance, enough run logs must show the mean loss is at most 3.28 at p<0.01; one run with a 0.0005 margin does not
  4. Because the previous record holder must approve every new record
The rules ask for statistical evidence about the mean, since run-to-run spread (about 0.0019 for the SoftCap record) is larger than the margin. The target is 3.28, not 3.2795 (second option). There is no rule against fast single runs (first) and no veto for the previous holder (fourth).

Why does the README say the current record is "intentionally kept roughly 0.001-0.002 loss below 3.28"?

  1. So that validating a new submission is simpler, and so that a pull request spending the buffer must beat just running fewer steps
  2. Because the loss of 3.28 cannot be reached exactly on this hardware
  3. To make the p-value computation unnecessary
  4. To leave room for the data pipeline to change
The buffer is a margin for validation (so that the mean clears the line) and a guard against trading loss for time by stopping early. It does not replace the p-value (third), the data pipeline may not change at all (fourth), and the target is reachable (second).

Record 92 in the table drops from 1.126 to 0.665 minutes with a description that lists six changes. What can you conclude about the individual changes?

  1. Each one gave about one sixth of the speed-up
  2. The first one listed gave most of the speed-up
  3. None of them worked on their own, only the combination
  4. Nothing about their individual contributions: the record shows that the combination meets the rules, and separating the changes needs ablations
A bundled pull request proves the sum. Equal shares and a dominant first item are guesses, and "none worked alone" is also unsupported: the table gives no ablation either way.

Records 8 (untie the embedding and the head) and 51 (retie them) are 13 months apart. What does this show about the process?

  1. Record 8 was an error that should not have been accepted
  2. An accepted change can be reversed later when the surrounding model and schedule have changed; the ledger only asks for evidence and speed at each step
  3. The p-value test is unreliable
  4. The maintainer reverts records when the README is updated
Nothing in the table says record 8 was wrong when it was made. Both were accepted on the same evidence rule against different baselines. It says nothing about the reliability of the test (third), and the table does not describe the maintainer reverting anything (fourth).

Lab 1: A Keep-or-Revert Research Loop

Karpathy's autoresearch is a loop that edits a training script, runs it for a fixed time, keeps the edit if one number went down and undoes it otherwise. This lab builds the spine of that loop at toy scale. It fixes three things the bare version leaves open. A run is not written down in a form you can audit. A single comparison cannot tell a gain from luck. Nothing says whether the number the loop climbs is the number you care about. You build an append-only run store, a noise floor and a paired keep-or-revert test. Then you log proxy and held-out scores for every experiment, detect a loop that overfits its own yardstick, and replay the log byte for byte.

Why this lab matters

This lab is a step of Artifact 1, autoresearch-rs: the keep-or-revert loop with a Rust runner whose extension is the proxy-versus-held-out gap, logged for every experiment. The Rust runner of chapter 5 is this lab's Python reference rewritten: the same record shapes, the same decision rule, the same replay. After this lab you can say, for any claimed improvement of a research loop, how many runs it rests on, how large the noise was, what the loop was optimising and what happened to the number the loop never saw.

Three standards of the artifact track show up as code. A sustained trend, not one lucky accept becomes a paired test over several seeds (milestone 3). Scores on data the loop never saw becomes the held-out column, logged but never used to decide (milestone 4), with a detector on its gap (milestone 5). A fixed budget stated up front becomes a count of experiments times seeds, and a store that shows exactly how many runs were spent (milestone 1). The chapters behind it are chapter 1 (the loop as a state machine), chapter 2 (noise floors and proxies) and chapter 4 (run tracking and replay).

Determinism, requirements and the toy task

Python 3.9 or newer and nothing else: the standard library only, no network, no clock. Every random number comes from a seeded random.Random, so a failing check prints its seed and the same code gives the same numbers on every run. The whole check takes about 15 seconds for the reference solution.

The "training run" is deliberately tiny so that 600 of them take seconds: fit a polynomial to 48 noisy points with minibatch stochastic gradient descent (SGD). It stands in for nanochat's train.py, which the real Artifact 1 loop edits and which Workbench 1 runs on a CPU. Two details matter and are not accidents. The proxy is a run of 40 steps scored on a 16-point validation slice, as cheap as autoresearch's five minutes are next to a real training run. The held-out score is a run of 300 steps scored on 400 fresh points, the stand-in for "what we actually want". One caveat on replay: Python's math functions come from the machine's C library, so byte-identical replay is guaranteed on one machine and Python build, not across platforms.

What you'll build

The task: a config is four numbers (learning rate, polynomial degree, L2 penalty, batch size). The baseline is lr 0.02, degree 3, l2 0.001, batch 16. The proposer, a seeded stand-in for the agent, changes one or two of them per experiment. Six milestones:

  1. A run store: hash a config, key a run by hash and seed, append every run to a JSONL file that is never rewritten, and serve repeats from it.
  2. A noise floor: run the baseline on K seeds and measure how far two single runs differ by reseeding alone.
  3. Keep or revert on a paired test: compare the candidate with the best on the same seeds, and keep it only if the gain is positive and larger than the seed noise.
  4. Both scores per experiment: decide on the proxy, log the held-out gain beside it, and run the loop.
  5. The gap: cumulative proxy and held-out gain, the trend of their difference, a detector that fires when the proxy keeps climbing and the held-out score does not, and a text chart.
  6. Replay: re-run the whole log from configs and seeds and prove the new file is the same bytes, or point at the first line that is not.

Milestone 1: an append-only run store keyed by config hash

A research loop that cannot show its runs is a story. Autoresearch's own record is a results.tsv next to a git history: one line per experiment, with the commit, val_bpb, memory and a keep, discard or crash status (the format program.md asks the agent to write, in the version I read: commit 228791f of 25 March 2026). It is a good habit and a thin record. It holds the outcome of each comparison, not the runs behind it, and nothing stops a line being edited. The store you build here has three properties that the rest of the lab leans on.

Keyed by content. A run is identified by what was run: the config and the seed. Hash the config's canonical JSON (keys sorted, no spaces) with Secure Hash Algorithm 256 (SHA-256), a standard hash function, and keep 12 hex characters. The key is then hash:seed. Two configs that mean the same thing hash the same whatever order their keys were written in, and a config that differs in one digit hashes differently. This is the content-addressed cache of A0 chapter 22 and the same idea as a git commit id.

Append-only. Records are lines of JSON (the JSON Lines format, abbreviated JSONL), written one dump_line at a time to the end of the file, and a key that is already there is refused, not overwritten. The consequence is that the file is its own audit trail: to check a result you read it, and to claim a run happened you must have appended it. A crash can leave half a line at the end; your loader must drop that fragment instead of failing, and cut it off the file so the next append is valid.

A cache. evaluate(config, seed, store) trains only if the key is new. In the loop, the best config is compared with a fresh candidate on the same seeds again and again; the store makes every repeat free, and the count of real training runs becomes the loop's honest budget.

Your task

check.py verifies: a hand-computed hash (the SHA-256 of {"a":1} starts 015abd7f5cc5); key order does not matter; the file holds exactly one dump_line per record; a duplicate key raises DuplicateKey and leaves the file alone; a reopened store has the same records; a torn last line is ignored and the next append still gives a valid file; evaluate trains once and then serves from the store, including after a reopen.

Solution spoiler 
def config_hash(config):
    """12 hex characters of SHA-256 over the canonical JSON of config."""
    text = json.dumps(config, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:12]

def run_key(config, seed):
    return f"{config_hash(config)}:{seed}"

class RunStore:
    """Append-only JSONL file. Opening an existing file loads it."""

    def __init__(self, path):
        self.path = path
        self.records = {}
        self.load()

    def load(self):
        """Read the file (if it exists) into self.records."""
        if os.path.exists(self.path):
            with open(self.path, encoding="utf-8") as fh:
                text = fh.read()
            keep = text[:text.rfind("\n") + 1]    # drop a torn last line
            if keep != text:
                with open(self.path, "w", encoding="utf-8") as fh:
                    fh.write(keep)
            for line in keep.splitlines():
                rec = json.loads(line)
                self.records[rec["key"]] = rec

    def append(self, record):
        key = record["key"]
        if key in self.records:
            raise DuplicateKey(key)
        with open(self.path, "a", encoding="utf-8") as fh:
            fh.write(dump_line(record))
        self.records[key] = record

    def get(self, key):
        return self.records.get(key)

    def __len__(self):
        return len(self.records)

def evaluate(config, seed, store):
    """The run record for (config, seed); train only if it is new."""
    key = run_key(config, seed)
    rec = store.get(key)
    if rec is None:
        proxy, held = train_and_score(config, seed)
        rec = {"kind": "run", "key": key, "hash": config_hash(config),
               "seed": seed, "config": config,
               "proxy": proxy, "heldout": held}
        store.append(rec)
    return rec

Milestone 2: a noise floor from baseline seeds

Run the baseline twice with different seeds and you get two different scores. Nothing changed except the random initial weights and the order of the minibatches, so the difference is the noise floor of the setup: the size of change that reseeding alone produces. Until you know it, "the score went from 0.333 to 0.318" is not a finding. Chapter 2 gives the theory and calls the standard deviation of the scores the noise floor; here you measure it, and the code also reports the larger number that governs a comparison of two single runs.

With K baseline runs, estimate the spread by the sample standard deviation s, which divides by K − 1 because the mean was estimated from the same data. A difference between two single runs has spread √2 times larger (the variances add), and 95% of such differences fall within 1.96 of those units. So the code's floor is:

floor = 1.96 × √2 × s

That is the size of gap that two runs of the same config exceed only one time in twenty. A single comparison that finds a candidate "better" by less than the floor has found nothing. The reference solution reports it for both scores, and the proxy's is four times the held-out one, which is the first thing this lab is built to show: a short run scored on a small slice is a noisy yardstick.

Your task

check.py verifies: sample_sd([2,4,4,4,5,5,7,9]) is 2.1381 (not 2.0, which is the population value); a fake training function with proxy = seed gives mean 2.5, sd 1.2910 and floor 3.5785 on seeds 1 to 4; all runs land in the store; a second call trains nothing.

Hints try without first

  • Compute both scores in one loop over ("proxy", "heldout"); only the key into each record differs.
Solution spoiler 
def mean(xs):
    return sum(xs) / len(xs)

def sample_sd(xs):
    """Standard deviation with n - 1 in the denominator."""
    m = mean(xs)
    return math.sqrt(sum((x - m) ** 2 for x in xs) / (len(xs) - 1))

def noise_floor(config, seeds, store):
    """How far two single runs of one config differ by reseeding alone."""
    recs = [evaluate(config, s, store) for s in seeds]
    out = {"n": len(recs)}
    for name in ("proxy", "heldout"):
        vals = [r[name] for r in recs]
        sd = sample_sd(vals)
        out[name] = {"mean": mean(vals), "sd": sd,
                     "floor": 1.96 * math.sqrt(2) * sd}
    return out

Milestone 3: keep or revert on a paired test

The rule in autoresearch's program.md is to keep a change if val_bpb is lower than before. With one run on each side, a change that does nothing at all beats a typical best score about half the time. After a lucky accept the bar is that lucky run, so later no-ops pass less often, but then the loop ratchets on luck instead of on effect. Over 100 overnight experiments the result is a stream of accepted changes that were not improvements, each built on top of the last. The fix is to ask a statistical question instead: is the mean difference over several seeds larger than the seed-to-seed variation of those differences?

Two choices make the test sharp. First, pair the runs: run the best config and the candidate on the same seeds, and look at the difference per seed, di = best − candidate (scores are errors, so a positive d means the candidate is better). Anything that moves both runs of a seed together, such as an unlucky initialisation, cancels in the difference, and what is left is the candidate's effect plus the noise that the two runs do not share. Second, test the mean of the differences with a paired t-test:

t = d̄ / (sd / √n)

where d̄ is the mean difference, sd their sample standard deviation and n the number of seeds. With n = 5 there are 4 degrees of freedom, and the two-sided 95% critical value of Student's t is 2.776, so the candidate is kept only if its mean gain is positive and |t| exceeds that. The lab gives you a table of critical values; the paired test itself is yours.

The test has a limit that milestone 3's own check does not hide. A paired test is very sensitive when the effect is consistent, and it will call a change "significant" even if it is tiny. The demo run at the end of this page keeps one experiment whose gain rounds to 0.0000 with t = 6.1, because a change to the L2 penalty shifted every seed by the same sliver. Significance says the effect is real; it does not say it is worth keeping. The noise floor of milestone 2 is the natural yardstick for "worth"; a minimum effect is one of the exercises under Going further.

Your task

Write paired_test(diffs), returning (mean, sd, t, df, significant), and keep_or_revert(best, cand, seeds, store), which runs both configs on every seed through evaluate, forms best.proxy - cand.proxy per seed and returns {"keep", "mean_gain", "t", "df"}. Decide on the proxy only.

check.py verifies: [1,2,3,4,5] gives mean 3, sd 1.5811, t = 4.243, significant; a mixed series with mean 0.1 is not; zero spread is handled (t = 0, or ±infinity for a nonzero mean); over 4,000 seeded no-effect trials the rule keeps about 2.5% while a single comparison keeps about half; a fake task with huge shared seed noise and a 0.10 gain is kept because the seeds are paired; a worse or identical candidate is reverted; a 0.05 gain buried in 0.4 of independent noise is almost never kept.

Hints try without first
  • With zero spread you would divide by zero. Return t = 0.0 when the mean is 0 as well, and math.copysign(math.inf, mean) otherwise.
  • The sign matters: a large negative t is a significant loss. Keep only if the mean gain is positive and the test is significant.
  • t_critical(df) is given; df = n - 1.
Solution spoiler 
def paired_test(diffs):
    """(mean, sd, t, df, significant) for per-seed differences."""
    n = len(diffs)
    m = mean(diffs)
    sd = sample_sd(diffs)
    if sd == 0:
        t = 0.0 if m == 0 else math.copysign(math.inf, m)
    else:
        t = m / (sd / math.sqrt(n))
    df = n - 1
    return m, sd, t, df, abs(t) > t_critical(df)

def keep_or_revert(best, cand, seeds, store):
    """Keep `cand` only if it beats `best` on the proxy, paired by seed."""
    diffs = []
    for s in seeds:
        b = evaluate(best, s, store)["proxy"]
        c = evaluate(cand, s, store)["proxy"]
        diffs.append(b - c)           # positive: the candidate is better
    m, sd, t, df, sig = paired_test(diffs)
    return {"keep": m > 0 and sig, "mean_gain": m, "t": t, "df": df}

Milestone 4: proxy and held-out, logged for every experiment

Now the extension that makes this Artifact 1 and not a re-implementation. The loop sees one number, the proxy, because it is cheap: in autoresearch it is the val_bpb after five minutes. What you want is a model that is better at the thing the proxy stands in for. The two can come apart, and the way to find out is to compute the second number for every experiment and write it next to the first. The held-out number must never be used in keep_or_revert; if it were, it would become part of what the loop optimises and stop being a check. This is the same discipline as the search, selection and test sets of A7 chapter 16.

An experiment now produces one record with: the experiment index, the hash of the best config, the candidate config, the seeds used, the decision, the proxy gain (the decision's mean gain), the held-out gain (the mean over the same seeds of best.heldout - cand.heldout) and their gap, proxy gain minus held-out gain. A positive gap on a kept experiment says the proxy flattered the change.

Two details are easy to get wrong. Fresh seeds per experiment: experiment_seeds(index, k) gives each experiment its own K seeds. If every experiment reused seeds 0 to 4, the loop would slowly select for configs that happen to suit those five initialisations, and the baseline would be measured on the same lucky draws every time. One training run per key: the best config appears in every experiment but on different seeds, so most of its runs are new, and your store must train each (config, seed) pair exactly once.

Your task

Write run_experiment(index, best, cand, store, k), which appends and returns the experiment record (kind "experiment", key "exp:0003" for index 3, and the fields above), and research_loop(proposer, n, store, k, start), which asks proposer.propose(best, i) for each candidate, keeps the winner as the new best and returns (best, history).

check.py verifies: a fake task where the proxy improves with the learning rate but the held-out score worsens is still kept (held-out never decides) and logs a negative held-out gain and the right gap; the proposer is shown the kept config and not the reverted one; every experiment is in the store with fresh seeds; on the real task, 12 experiments train every (config, seed) pair exactly once.

Hints try without first
  • The decision comes from keep_or_revert; call evaluate again for the held-out numbers, it is a cache hit.
  • Copy the start config with dict(start or BASELINE) so the module constant is never changed.
Solution spoiler 
def run_experiment(index, best, cand, store, k=5):
    seeds = experiment_seeds(index, k)
    dec = keep_or_revert(best, cand, seeds, store)
    held = [evaluate(best, s, store)["heldout"]
            - evaluate(cand, s, store)["heldout"] for s in seeds]
    proxy_gain = dec["mean_gain"]
    held_gain = mean(held)
    rec = {"kind": "experiment", "key": f"exp:{index:04d}",
           "index": index, "best_hash": config_hash(best),
           "cand_config": cand, "seeds": seeds, "keep": dec["keep"],
           "t": dec["t"], "proxy_gain": proxy_gain,
           "heldout_gain": held_gain, "gap": proxy_gain - held_gain}
    store.append(rec)
    return rec

def research_loop(proposer, n, store, k=5, start=None):
    """n experiments; returns (best_config, list of experiment records)."""
    best = dict(start or BASELINE)
    history = []
    for i in range(n):
        cand = proposer.propose(best, i)
        rec = run_experiment(i, best, cand, store, k)
        history.append(rec)
        if rec["keep"]:
            best = cand
    return best, history

Milestone 5: the gap, its trend, and a text chart

A single experiment's gap is mostly noise. What you want is the trend: does the proxy keep rising while the held-out score stops? Sum the gains of the kept experiments as they happen. The cumulative proxy gain is how far the loop thinks it has come; the cumulative held-out gain is how far it has really come; the cumulative gap is the difference. A slope of the gap over a recent window answers "is the loop still telling the truth?". The slope of a list of numbers against 0, 1, 2, ... is the least-squares line, which has a closed form: the sum of (x − mean x)(y − mean y) divided by the sum of (x − mean x)².

A rising gap on its own is not a fault. Early gains are often real on both scores, and a short run can gain more than a long one from the same change (a higher learning rate helps 40 steps more than 300). The detector therefore asks for two things in the same window: the gap slopes up by at least min_slope per experiment, and the cumulative held-out gain has stopped rising (slope at most zero). Proxy climbing while held-out is flat is what overfitting to the proxy looks like in a log. This is the 'sustained trend' of the artifact standards, applied in the opposite direction: a trend of the proxy that the held-out score does not share.

Last, a text chart, because a chart that needs a plotting library will not be in the log's directory when a reviewer opens it. Every every experiments, print two bars scaled to the largest cumulative value: P for the proxy and H for the held-out. A negative gain draws no bar, but its signed number stays on the line.

Your task

Write cumulative(history) (one entry per experiment; only kept experiments add), ols_slope(ys), detect_overfit(cum_proxy, cum_heldout, window, min_slope) (the first index where both conditions hold, or None) and text_chart(cum_proxy, cum_heldout, every, width) in exactly the format of its docstring.

check.py verifies: slopes of simple lines; a hand-built history; a detector that fires at the end of the first full window when the proxy climbs by 1 per step and the held-out is flat, stays silent when both climb together or when the held-out still climbs slowly, and stays silent with fewer experiments than one window; the chart against an exact expected string, and negative values; three complete 60-experiment loops in which the detector must fire and the proxy gain must dwarf the held-out gain.

Hints try without first

  • For the slice of a window ending at i, use [i - window + 1 : i + 1].
  • The chart line is f"{i + 1:>4} {tag} {'#' * n:<{width}} {v:+.4f}"; round, not int, for the bar length.
Solution spoiler 
def cumulative(history):
    """Running totals over kept experiments: proxy, heldout and gap."""
    p = h = 0.0
    cp, ch, cg = [], [], []
    for rec in history:
        if rec["keep"]:
            p += rec["proxy_gain"]
            h += rec["heldout_gain"]
        cp.append(p)
        ch.append(h)
        cg.append(p - h)
    return cp, ch, cg

def ols_slope(ys):
    """Least-squares slope of ys against 0, 1, 2, ..."""
    n = len(ys)
    xbar = (n - 1) / 2
    ybar = mean(ys)
    num = sum((i - xbar) * (y - ybar) for i, y in enumerate(ys))
    den = sum((i - xbar) ** 2 for i in range(n))
    return num / den

def detect_overfit(cum_proxy, cum_heldout, window=10, min_slope=0.002):
    """First index where, over the last `window` experiments, the proxy
    gain climbs at >= min_slope per experiment while the held-out gain
    does not climb at all (its slope is <= 0)."""
    for i in range(window - 1, len(cum_proxy)):
        lo = i - window + 1
        gap = [p - h for p, h in zip(cum_proxy[lo:i + 1],
                                     cum_heldout[lo:i + 1])]
        if (ols_slope(gap) >= min_slope
                and ols_slope(cum_heldout[lo:i + 1]) <= 0):
            return i
    return None

def text_chart(cum_proxy, cum_heldout, every=10, width=30):
    scale = max(max(cum_proxy), max(cum_heldout), 1e-12)
    lines = []
    for i in range(every - 1, len(cum_proxy), every):
        for tag, v in (("P", cum_proxy[i]), ("H", cum_heldout[i])):
            n = max(0, round(width * v / scale))
            lines.append(f"{i + 1:>4} {tag} {'#' * n:<{width}} {v:+.4f}")
    return "\n".join(lines)

Milestone 6: byte-identical replay from the log

A log you cannot re-run is a claim. The test of whether your loop is a research instrument is whether someone else, holding only the log, can reproduce it: not "get similar numbers" but the same bytes. That is possible here because every record is a pure function of (config, seed) and the order of events, and the order is in the file. The one rule is that nothing else may enter a record: no timestamp, no hostname, no wall-clock duration, no process id. The moment a record holds the time it took, replay can never match, and you have to choose between a log with the timing in it and a log that proves itself. The usual answer is two files: a deterministic log for replay and a separate, disposable one for timing. Autoresearch's wall-clock budget is a version of the same problem, which Workbench 1 measures: a run that stops after thirty seconds does a different number of steps on a busy machine.

Write first_difference(path_a, path_b), which returns the 1-based number of the first line at which the two files differ as bytes (a shorter file differs at its first missing line), or None. Then replay(path, out_path): read the log in file order, re-execute each record into a brand-new store (a run record by calling evaluate; an experiment record by calling run_experiment with its logged candidate and the best so far), and return first_difference(path, out_path). If someone edited a score in the original, the re-executed value disagrees and the replay names the line.

def first_difference(path_a, path_b):
    """1-based number of the first differing line, or None if the two
    files are byte-identical."""
    with open(path_a, "rb") as fa, open(path_b, "rb") as fb:
        a = fa.read().split(b"\n")
        b = fb.read().split(b"\n")
    for i in range(max(len(a), len(b))):
        la = a[i] if i < len(a) else None
        lb = b[i] if i < len(b) else None
        if la != lb:
            return i + 1
    return None

def replay(path, out_path):
    """Re-execute every record of the log at `path` into a fresh store
    at out_path, in file order; then compare the two files."""
    if os.path.exists(out_path):
        os.remove(out_path)
    store = RunStore(out_path)
    best = dict(BASELINE)
    with open(path, encoding="utf-8") as fh:
        for line in fh:
            rec = json.loads(line)
            if rec["kind"] == "run":
                evaluate(rec["config"], rec["seed"], store)
            else:
                again = run_experiment(rec["index"], best,
                                       rec["cand_config"], store,
                                       len(rec["seeds"]))
                if again["keep"]:
                    best = rec["cand_config"]
    return first_difference(path, out_path)

Going further

  1. A minimum effect. Experiment 16 above was kept for a gain that rounds to zero. Require mean_gain to exceed a tenth of the proxy noise floor as well as be significant. How many of the seven kept experiments survive, and does the held-out curve change?
  2. Choose K. Rerun the false-keep experiment of milestone 3 with K = 3, 5 and 10 seeds, and plot the rate of keeping a real gain of 0.02 against the cost in runs. Chapter 2 calls this power; here you can measure it.
  3. Reuse the seeds. Change experiment_seeds to return seeds 0 to 4 every time. Run 100 experiments. What happens to the proxy gain and to the held-out gain, and why can no paired test notice?
  4. Close the gap. Let the loop decide on a mix: the proxy, plus the held-out score every tenth experiment only if the detector has fired. Does the held-out curve keep rising? What did you spend, in runs?
  5. A better proxy. Make the proxy 100 steps scored on 64 points. How does the noise floor change, how does the final gap change, and what is the cost per experiment? This is the trade-off chapter 3 prices.

Systems connection

The run store is a write-ahead log in miniature: records are appended in order, never edited, and the current state (the best config, the chart, the noise floor) is a function you can recompute by reading the log from the start. Databases rely on exactly this to recover after a crash, which is why milestone 1 cares about the torn last line, and why a stream processor can rebuild a table by replaying events. The content-addressed key is the same idea as a build system's cache key or a container image digest. And byte-identical replay is what distributed systems call determinism: a state machine that depends only on its inputs and their order can be run on a second machine and checked against the first. A clock, a hostname or a process id in a record is hidden input, which is why the failing example above breaks.

What you learned

  • A research loop's record should be an append-only log of runs keyed by the hash of what was run and the seed; it doubles as a cache and, after a crash, drops the torn last line.
  • The seed-to-seed noise floor of the setup, 1.96 × √2 × the standard deviation, is the size of difference a single comparison cannot be trusted below. Here the proxy's was 0.068 and the held-out score's 0.017.
  • Keeping a change when one run is lower accepts a no-effect change about half the time. A paired t-test over fresh seeds per experiment accepted them 2.5% of the time, at the price of 2K runs for each experiment.
  • Pairing by seed makes the test sharp, so it will also call a tiny, consistent effect significant. Significance is not size: add a minimum effect.
  • Log the held-out gain for every experiment, never decide on it, and watch the trend of the gap: in the demo run the proxy reported ten times the gain that the held-out score confirmed.
  • Replay is the test of a log. A record may depend only on its config, its seed and the order of events; a timestamp in a record makes replay impossible.

Check your understanding

A loop keeps any candidate whose single run beats the best's single run. The candidate changes nothing that matters. About how often is it kept?

  1. Almost never, because the scores are identical
  2. About half the time, because the two runs differ only by noise and either can be lower
  3. About 5% of the time, the usual significance level
  4. Every time, because the candidate is new
With no real difference, which of two noisy runs is lower is a coin toss. The scores are not identical because the seeds differ (first option). The 5% belongs to a test with a threshold, which a single comparison does not have (third). Newness plays no part (fourth).

Why does the lab run the best config and the candidate on the same seeds within an experiment?

  1. To halve the number of training runs
  2. Because the store only accepts one seed per config
  3. To make the held-out score equal to the proxy
  4. So that seed luck shared by both runs cancels in the per-seed difference, leaving a sharper test of the candidate's effect
Pairing does not save runs (each side still needs K), the store accepts any number of seeds per config, and it does nothing to the relation between the proxy and held-out scores. What it does is remove the part of the noise that both sides share.

The demo loop finishes with a proxy gain of +0.120 and a held-out gain of +0.012. What is the most defensible description of what happened?

  1. The loop improved the proxy a great deal and the thing the proxy stands in for very little; most of the gain was specific to the short run on the small slice
  2. The loop failed, because the held-out gain is positive but small
  3. The held-out set is wrong, because it disagrees with the loop
  4. The loop worked, because both gains are positive
Both gains are positive, but the loop reported ten times more than the held-out score can confirm. Calling it a failure (second) overstates a small real gain; blaming the held-out set (third) reverses the roles, since it is the one the loop never optimised; and "both positive" (fourth) ignores the size of the gap.

A colleague adds "seconds": time.time() - t0 to every run record "for information". What breaks, and where does the lab's check notice?

  1. The paired test, because the seeds change
  2. The hash, because the config now has a new field
  3. Replay: the re-executed record has a different duration, so the new file is not byte-identical, and milestone 6 names the first line
  4. Nothing breaks; the field is ignored
The hash is of the config only, and the test uses scores, so milestones 1 to 5 still pass. The clock is an input that is not in the log, so no replay can reproduce it. Timing belongs in a separate file that nobody expects to replay.

The detector fires when the gap slopes up and the cumulative held-out gain stops rising. Why does it not fire on a gap that slopes up while the held-out gain is still rising slowly?

  1. Because a rising held-out gain always means the proxy is perfect
  2. Because the proxy may gain more than the held-out score from the same real improvement, so a widening gap alone is not evidence of overfitting; the held-out score must also have stalled
  3. Because the slope of the held-out gain cannot be computed on a short window
  4. Because the detector only looks at the gap
A 40-step run can gain more from a higher learning rate than a 300-step run, so the gap can widen while both scores genuinely improve. The detector uses both slopes; the fourth option describes a simpler detector that would raise false alarms. The held-out gain can rise and the proxy still be imperfect (first option).

You want the loop to be cheaper and decide to reuse seeds 0 to 4 in every experiment, so the baseline never needs re-running. What is the main cost?

  1. The store will refuse the duplicate keys
  2. The false-keep rate rises to 50%
  3. The paired test no longer works with fewer than 10 seeds
  4. The loop slowly selects configs that suit those five initialisations, so every decision shares the same luck and the gains it reports are inflated
The store happily serves repeats from cache (that is its job), and the paired test still works with five seeds. The false-keep rate on any one experiment stays near 2.5%, but across many experiments the survivors are the ones that fit those seeds, so selection effects accumulate. Fresh seeds per experiment keep each decision independent of the last.

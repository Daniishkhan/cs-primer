GPUs, Clouds & What Compute Costs

Every plan in AI work eventually meets three numbers: how many operations, how many bytes, and how many dollars an hour. This chapter explains what a GPU is built to do, why moving data usually costs more than computing on it, how to tell whether a job fits in memory, and how to turn a model size and a token count into a defensible bill.

Why this matters

Before a project is approved someone asks "what will it cost and how long will it take?", and "we will see" is not an answer. The engineers who can answer within a factor of two in ten minutes, and say which assumption the answer is most sensitive to, make the plans that get funded and avoid the runs that burn a month of budget before failing. This chapter gives you the vocabulary (FLOP/s, bandwidth, memory, utilisation), a handful of rules of thumb you can derive, and a script. The later courses refine each piece: Parameters, FLOPs & Memory counts a transformer exactly, GPU Memory & Why Training Runs Out of It goes deep on memory, and The Economics of a Token prices serving. The studio Budget the Compute for a Project puts this chapter to work.

What a GPU is good at

A CPU is built to run one stream of instructions as fast as possible, with big caches and clever prediction to hide delays. A GPU (graphics processing unit) makes the opposite trade: thousands of simpler arithmetic units that all do the same kind of operation on different data at once, and a very wide connection to memory. Graphics needed this because every pixel is computed independently by the same small program. Neural networks need it for the same reason: a layer's output is thousands of independent dot products, as you saw in Matrices as Functions.

Modern data-centre GPUs add dedicated tensor cores, units that multiply small matrix tiles in one step at low precision (the bf16 and fp8 formats from Floating Point & Numerical Stability). That is why the peak numbers on a datasheet are quoted per precision: the same chip is several times faster in bf16 than in fp32. The earlier engineering course covers the hardware idea in Parallelism, SIMD & GPUs; here we need only the consequences:

  • GPUs are fast when there is a lot of regular, parallel arithmetic: large matrix multiplications, the same operation over many tokens or images.
  • GPUs are slow at branching, small irregular work and one-at-a-time sequential steps. A Python loop over a thousand tiny operations keeps a GPU idle.
  • GPU memory is a separate, limited pool. Data must be copied in from the host and fits only if the total fits.

Analogy: one master chef and a hall of line cooks

A CPU is a master chef who can cook anything, quickly, one dish at a time. A GPU is a hall of line cooks who each chop the same vegetable the same way: far more chopping per hour, if you can hand every cook a pile to chop. The kitchen's limit is often not the cooks but the single door through which ingredients arrive from the store room.

Where it breaks down: line cooks are interchangeable and can stop and start freely, while GPU threads run in lock-step groups, and the hall is only fast when the whole group works on the same step. A dish that needs one cook to wait for another leaves most of the hall standing around.

FLOPs versus bytes

A FLOP is one floating-point operation: one addition or one multiplication. FLOP/s (written FLOPS on datasheets) is how many per second. Do not confuse it with the lowercase plural FLOPs, a count of operations in a job. A matrix product of an (m, k) matrix by a (k, n) matrix needs m×n×k multiplies and about the same number of adds, so 2mnk FLOPs. Multiplying two 1,024 × 1,024 matrices costs 2 × 1,0243, about 2.1 billion FLOPs.

Doing arithmetic requires that the operands first arrive from memory. Memory bandwidth is how many bytes per second the processor can read and write from its main memory. The ratio of the two is the key quantity: arithmetic intensity is FLOPs performed per byte moved. Adding two vectors does 1 FLOP per element but must read two numbers and write one: with 4-byte floats that is 12 bytes, an intensity of about 0.083 FLOP/byte. The matrix product above reads two inputs and writes one output of 1,024 × 1,024 numbers, 12.6 MB at 4 bytes each, and does 2.1 billion FLOPs, an ideal intensity of about 170 FLOP/byte in fp32. Run the experiment on your own computer:

import time
import numpy as np

def best_time(fn, repeats=5):
    fn()                                   # warm-up
    times = []
    for _ in range(repeats):
        t = time.perf_counter(); fn(); times.append(time.perf_counter() - t)
    return min(times)

n = 1024
a = np.random.default_rng(0).standard_normal((n, n), dtype=np.float32)
b = np.random.default_rng(1).standard_normal((n, n), dtype=np.float32)
t = best_time(lambda: a @ b)
flops = 2 * n**3                           # n^2 outputs, each n multiplies and n adds
bytes_moved = 3 * n * n * 4                # read a, read b, write c (ideal, each once)
print(f"matmul {n}x{n}: {flops/t/1e9:7.1f} GFLOP/s, intensity {flops/bytes_moved:6.1f} FLOP/byte")

m = 20_000_000
x = np.random.default_rng(2).standard_normal(m, dtype=np.float32)
y = np.random.default_rng(3).standard_normal(m, dtype=np.float32)
out = np.empty_like(x)
t = best_time(lambda: np.add(x, y, out=out))
bytes_moved = 3 * m * 4                    # read x, read y, write out
print(f"vector add {m:,}: {m/t/1e9:7.1f} GFLOP/s, intensity {m/bytes_moved:6.3f} FLOP/byte, {bytes_moved/t/1e9:5.1f} GB/s")
matmul 1024x1024:  2036.6 GFLOP/s, intensity  170.7 FLOP/byte
vector add 20,000,000:     9.5 GFLOP/s, intensity  0.083 FLOP/byte, 113.8 GB/s

These numbers come from the machine this book was written on and will differ on yours, but the shape will not. The matrix product runs at hundreds of times the FLOP/s of the vector add, even though both are plain arithmetic, because the vector add spends nearly all its time waiting for memory. Its 113.8 GB/s is close to what this machine's memory can deliver, so no amount of faster arithmetic would help it. Programs like that are memory-bound. Programs whose speed is limited by the arithmetic units are compute-bound.

The roofline

Put the two limits on one chart and you get the roofline model (Williams, Waterman and Patterson, 2009). For a chip with peak compute P and bandwidth B, the best a program with intensity I can achieve is

attainable FLOP/s = min(P, B × I)

On the left of the ridge point I = P/B you are on the sloped memory roof; on the right, the flat compute roof. For an NVIDIA H100 SXM, the datasheet lists 3.35 TB/s of HBM3 memory bandwidth and 1,979 TFLOP/s of bf16 tensor-core throughput with structured sparsity; the dense figure is half of that, about 989 TFLOP/s. Using the dense number, the ridge is 989 × 1012 / 3.35 × 1012 ≈ 295 FLOP/byte. Any operation with lower intensity cannot come close to the chip's peak, whatever the code does.

This explains two facts that otherwise seem strange. Training large networks is mostly big matrix products with high intensity, so it can approach the compute roof. Generating text one token at a time reads every weight to produce one token's worth of arithmetic, so it sits on the memory roof, and speed is set by how fast weights stream from memory, not by FLOP/s. That is why batching many requests together is the central trick in serving, and why cutting weights to 4 bits speeds decoding even though it adds arithmetic; the full story is in The KV Cache & the Cost of Decoding. Fusing several small operations into one kernel (Kernels & Performance) raises intensity by avoiding round trips to memory in the middle.

Common misconception

"A GPU with twice the peak FLOP/s will run my job twice as fast." Only if the job is compute-bound and the code keeps the arithmetic units busy. A memory-bound job speeds up with bandwidth, not peak FLOP/s; a job dominated by small operations is limited by launch overhead and by the CPU feeding it. Always ask first which roof you are under, and measure what fraction of the peak you actually reach.

Will it fit? Memory arithmetic

The cheapest check you can make is whether the job fits in GPU memory, since a job that does not fit does not run slowly, it fails. Two things fill the memory.

Inference needs the weights, plus the KV cache for the sequences in flight (the cached keys and values of earlier tokens; the KV cache chapter sizes it). Weight memory is parameters × bytes per parameter: 2 for bf16, 1 for int8 or fp8, about 0.5 for 4-bit formats.

Training also needs gradients and, with the Adam optimiser from Gradient Descent & Optimisers, two more numbers per weight. The usual mixed-precision recipe (Micikevicius et al., 2018; the ZeRO paper of Rajbhandari et al., 2020, tabulates it) keeps bf16 or fp16 weights and gradients for the fast arithmetic, plus an fp32 master copy of the weights and fp32 Adam moments for accuracy:

ItemPrecisionBytes per parameter
Weights for forward and backwardbf162
Gradientsbf162
Master copy of weightsfp324
Adam first moment (m)fp324
Adam second moment (v)fp324
Total16

Sixteen bytes per parameter, before activations, the intermediate results the backward pass needs, which grow with batch size, sequence length and depth. A 7-billion-parameter model therefore needs 7 × 109 × 16 = 112 GB of state alone, more than one 80 GB GPU holds. The remedy is to spread the state across several GPUs (sharding, Parallel Training) or to avoid training every weight (the low-rank adapters of LoRA, built on the SVD ideas of Eigenvectors, SVD & Low Rank).

How many FLOPs does training take?

For a dense transformer there is a famous shortcut. A forward pass through a layer does about one multiply and one add per weight per token, so about 2 FLOPs per parameter per token. The backward pass computes gradients with respect to both activations and weights, about twice the forward work. Together:

training FLOPs ≈ 6 × N × D

where N is the number of parameters and D the number of training tokens (Kaplan et al., 2020, and Hoffmann et al., 2022, use this approximation). It ignores attention's extra cost over long sequences and some smaller terms, and for sparse mixture-of-experts models N must be the parameters active per token. Check it against a published figure: the Llama 3 paper trained a 405-billion-parameter model on 15.6 trillion tokens and reports about 3.8 × 1025 FLOPs. The rule gives 6 × 405 × 109 × 15.6 × 1012 = 3.79 × 1025. It agrees well enough to plan with. The exact counting, with attention and embeddings, is in Parameters, FLOPs & Memory; the Chinchilla rule of thumb for choosing D given a compute budget is in Scaling Laws.

FLOPs become time through MFU (model FLOPs utilisation): the fraction of the chip's peak that useful model arithmetic achieves. It is never 100%: memory-bound operations, communication between GPUs, data loading and idle waiting all take a share. Large well-tuned runs are commonly reported at somewhere between a third and a half of peak; a first attempt with a new code base is often well below. We will assume 40% for planning and treat it as the assumption to measure on a short real run.

Renting hardware

Few teams buy GPUs for exploratory work. You rent, and the choices that matter are:

The decision between renting GPUs and calling an API is the same build versus buy trade-off as elsewhere in engineering. At low volume the API wins because you pay nothing when idle; at high, steady volume owning the serving can win, but only if you can keep the GPUs busy, which is where Load Testing & Capacity Planning and Cost & Efficiency apply directly. GPU cost is also not the whole bill: storage for checkpoints and datasets, network egress, a 24/7 on-call for a serving fleet, and engineers' time often matter as much.

State of play, October 2026

Hardware specifications are stable once published; prices are not. H100 figures in this chapter come from NVIDIA's datasheet (80 GB HBM3, 3.35 TB/s, 700 W maximum for SXM, as repeated in several copies) and were cross-checked in secondary sources; the dense bf16 figure is half the headline number because the headline assumes sparsity. For rental prices, public roundups I could read in 2026 put H100 on-demand rates anywhere from about $1.4 to more than $8 per GPU-hour, with a market median of roughly $2.3 to $3.1 on specialist clouds and higher list prices at the hyperscalers, plus much cheaper interruptible capacity. Some of these roundups are published by GPU sellers, so they are leads, not benchmarks. Newer GPU generations keep arriving and push the price of older ones down. Before you commit to a budget, read the provider's own pricing page that day, and keep the price as an explicit input you can change.

Estimating a bill

An estimate is a chain of small calculations, each with a stated assumption. Here is the chain for a training run:

This script does the memory and cost calculations from this chapter. Every input is a named constant you can change.

GB = 1e9

def weights_gb(params, bytes_per_param):
    return params * bytes_per_param / GB

def train_state_gb(params):
    """Mixed-precision Adam: bf16 weights (2) + bf16 grads (2) + fp32 master, m, v (12) = 16 bytes/param.
    Activations and framework overhead are extra."""
    return params * 16 / GB

def train_flops(params, tokens):
    return 6 * params * tokens                   # the 6ND rule: ~2ND forward + ~4ND backward

def gpu_hours(flops, peak_flops, mfu):
    return flops / (peak_flops * mfu) / 3600

H100_PEAK_BF16 = 989e12                          # dense bf16 FLOP/s, NVIDIA datasheet
H100_BANDWIDTH = 3.35e12                         # bytes/s
print(f"H100 ridge point: {H100_PEAK_BF16 / H100_BANDWIDTH:.0f} FLOP/byte")

print("\n-- memory --")
for name, p in [("1B", 1e9), ("7B", 7e9), ("70B", 70e9)]:
    print(f"{name:>3}: bf16 weights {weights_gb(p,2):6.1f} GB | int4 weights {weights_gb(p,0.5):5.1f} GB"
          f" | full training state {train_state_gb(p):6.0f} GB")

print("\n-- a 7B model on 2T tokens, 40% MFU, $2.50 per GPU-hour (assumed) --")
f = train_flops(7e9, 2e12)
h = gpu_hours(f, H100_PEAK_BF16, 0.40)
print(f"FLOPs {f:.2e} | GPU-hours {h:,.0f} | 1,024 GPUs: {h/1024/24:.1f} days | bill ${h*2.5:,.0f}")

print("\n-- sanity checks against published numbers --")
f = train_flops(405e9, 15.6e12)
print(f"Llama 3 405B: 6ND = {f:.2e} FLOPs (paper reports about 3.8e25)")
h = 2_788_000
print(f"DeepSeek-V3: {h:,} GPU-hours x $2 = ${h*2:,} (report: $5.576M)")

The 7-billion-parameter example costs about 59,000 GPU-hours or roughly $147,000 at the assumed $2.50 an hour. On 1,024 GPUs the arithmetic says 2.4 days; that assumes perfectly linear scaling, which never holds, since communication between GPUs grows with the cluster. The last two lines are sanity checks. The 6ND rule reproduces the Llama 3 405B figure. The DeepSeek-V3 line only multiplies the report's own numbers: its technical report (DeepSeek-AI, 2024) states 2.788 million H800 GPU-hours priced at an assumed $2 an hour, $5.576 million. Read the fine print of that number: the report presents it as the cost of the official training run at an assumed rental price, and it excludes the research, ablations and failed experiments that came before. That is the **overhead multiplier** in the diagram. Projects often spend several times the cost of the final run on everything around it. Choose a multiplier, write it down, and label it as an assumption.

Cost in practice: avoiding waste

  • Test small first. A smoke test on a small model catches shape bugs and out-of-memory errors for cents, before the expensive run. Use the same code path, smaller sizes.
  • Measure throughput early. Run 100 steps, compute tokens per second and MFU, then extrapolate. Replace the assumptions in your estimate with measured values.
  • Checkpoint and tolerate loss. Spot capacity is cheap only if a pre-emption costs you minutes, not a day (Checkpoints, Failures & Long Runs).
  • Turn it off. A GPU instance costs money while idle. Set auto-shutdown, tag resources with an owner, and check the bill weekly. Forgotten notebooks are the most common cause of a surprise invoice.
  • Log cost with the run. Add GPU-hours and dollars to the run record from Reproducible Experiments, so a later comparison knows what each result cost.

Systems connection

Everything here has a counterpart you have met. Memory bandwidth versus compute is the memory hierarchy again, with the cache replaced by a few megabytes of on-chip memory in front of much slower HBM. Estimating with stated assumptions is the method of Back-of-the-Envelope Estimation. Making a program faster by finding the true bottleneck is Performance Engineering. Keeping utilisation high and idle capacity low is the story of Cost & Efficiency.

Key takeaways

  • A GPU trades single-thread speed for a huge amount of parallel arithmetic and fast memory. It is fast on large, regular, batched matrix work and slow on small or sequential steps.
  • Arithmetic intensity (FLOPs per byte) tells you which roof you are under. On an H100 the ridge is near 295 FLOP/byte (dense bf16); one-token-at-a-time decoding sits far below it and is memory-bound.
  • Memory is a hard limit: inference needs about 2 bytes per parameter in bf16 plus the KV cache; mixed-precision Adam training needs about 16 bytes per parameter before activations.
  • Training FLOPs are roughly 6ND. Divide by peak FLOP/s times MFU for time, and multiply by the hourly price for dollars.
  • Prices and GPU generations change monthly. Keep them as named inputs, date them, and read the provider's page before committing.
  • A good estimate names its weakest assumptions and ranges them. Measure real throughput on a short run as soon as you can.

Check your understanding

Adding two large fp32 vectors element by element on a GPU achieves a small fraction of the chip's peak FLOP/s. Why?

  1. GPUs cannot add numbers efficiently; they are built only for multiplication.
  2. The vectors are too small to occupy the GPU, regardless of how large they are.
  3. Each element needs one FLOP but 12 bytes of memory traffic, so the operation is limited by memory bandwidth, not arithmetic.
  4. fp32 is not supported by GPUs, so the operation falls back to the CPU.
At about 0.083 FLOP per byte the operation is far to the left of the ridge point, under the memory roof. Faster arithmetic would not help. Size is not the problem here: large vectors make it bandwidth-bound. GPUs do support fp32 and addition.

You want to fully fine-tune a 3-billion-parameter model with Adam in the usual bf16-plus-fp32 mixed-precision recipe. Roughly how much GPU memory do weights, gradients and optimiser state need, before activations?

  1. About 48 GB (16 bytes per parameter).
  2. About 6 GB (2 bytes per parameter).
  3. About 12 GB (4 bytes per parameter).
  4. About 3 GB, because only the changed weights are stored.
3 × 109 × 16 bytes is 48 GB: bf16 weights and gradients (4) plus fp32 master weights and two Adam moments (12). The 6 GB figure is the bf16 weights alone, which is all that inference needs. Nothing is saved by "changed weights only" unless you use a parameter-efficient method such as LoRA.

A plan trains a 20-billion-parameter model on 1 trillion tokens. Using the 6ND rule, about how many FLOPs is that?

  1. About 1.2 × 1020
  2. About 1.2 × 1022
  3. About 2 × 1022
  4. About 1.2 × 1023
6 × 20 × 109 × 1012 = 120 × 1021 = 1.2 × 1023. The options below it are off by factors of ten or forget the 6 (2 × 1022 is 1ND).

Your estimate assumes 40% MFU, but a 100-step test run measures 20%. What happens to GPU-hours and the bill, other things equal?

  1. Both stay the same; MFU only affects speed, not cost.
  2. Both double, because the same FLOPs take twice as long on the same rented GPUs.
  3. Both halve, because lower utilisation means the GPUs work less.
  4. GPU-hours double but the bill stays the same, since the price per hour is fixed.
GPU-hours are FLOPs divided by (peak × MFU), so halving MFU doubles them, and you pay per hour, so the bill doubles too. A rented GPU is billed whether or not the arithmetic units are busy, which is why measuring MFU early matters.

A published report says a model "cost $5.6 million to train". What is the most careful way to treat that number when planning your own project?

  1. As the total cost of building the model, including all research.
  2. As a price you can obtain from any cloud provider today.
  3. As meaningless, since rental prices vary.
  4. As the cost of the final run at a stated rental price, to be multiplied by an explicit overhead for experiments and failures.
Such figures usually price GPU-hours of the main run at an assumed hourly rate and exclude earlier research and failed runs. They are useful as a scale reference, not as a total or a quote. Calling them meaningless discards the real information (GPU-hours); treating them as total cost underestimates by a large factor.

Why does generating text for a single user, one token at a time, run far below an H100's peak FLOP/s?

  1. The model's arithmetic is too complicated for tensor cores.
  2. Python is slow, and that is the only bottleneck.
  3. Each token needs every weight read from memory for only a couple of FLOPs per weight, so the work has low arithmetic intensity and is memory-bound.
  4. GPUs can only run one operation at a time, which stops them batching.
With batch size 1 the intensity is about 1 FLOP per byte in bf16, far left of the 295 FLOP/byte ridge. Serving many requests together reuses each weight read across tokens and raises the intensity. Framework overhead can matter, but it is not the core reason, and GPUs batch very well.

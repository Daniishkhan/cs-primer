NumPy, Arrays & Broadcasting

An array is a block of memory plus a small description of how to read it. Once you hold that picture, shapes, strides, views, axes and broadcasting stop being separate rules to memorise and become consequences of one design. This chapter builds the picture and then uses it to read, write and debug the array code that every later course assumes you can follow.

Why this matters

NumPy is the model for every tensor library. PyTorch, JAX and TensorFlow copy its vocabulary (shape, dtype, axis, broadcasting, views) almost word for word, so what you learn here transfers directly to PyTorch as an Autodiff Engine and to every model implementation in the deep-learning and LLM-training courses. Most bugs in ML code are not wrong mathematics; they are wrong shapes that happened to run: a mean taken over the wrong axis, a column broadcast against a flat array, a slice that silently aliases the original. After this chapter you will be able to predict the shape of any array expression before running it, explain what is copied and what is shared, and spot the three or four mistakes that account for most array bugs.

The ndarray: memory plus a description

The central object in NumPy is the ndarray (n-dimensional array). It consists of two parts. The first is a flat block of memory holding the values back to back. The second is a small header that says how to interpret that block:

  • the dtype: what one element is (float64, float32, int64, uint8, bool…) and so how many bytes it occupies (itemsize);
  • the shape: how many elements there are along each axis, written as a tuple (rows, columns) for a matrix, as in the notation used throughout this course;
  • the strides: how many bytes to step in memory to move one position along each axis;
  • an offset into the block, and flags saying whether the array owns its memory and how it is laid out.

The element at index (i, j) of a two-dimensional array lives at byte offset + i×stride0 + j×stride1. That formula is the whole addressing scheme, and it generalises to any number of axes. Let us check it numerically rather than take it on trust:

import numpy as np

a = np.arange(6, dtype=np.float64).reshape(2, 3)
print(a)
print("shape   :", a.shape)
print("dtype   :", a.dtype, " itemsize:", a.itemsize, "bytes")
print("strides :", a.strides, "(bytes to step one row, one column)")
print("nbytes  :", a.nbytes)

# find element (1, 2) by hand: offset + i*stride0 + j*stride1
i, j = 1, 2
byte_offset = i * a.strides[0] + j * a.strides[1]
flat = a.ravel()
print("byte offset of a[1, 2]:", byte_offset, "-> flat index", byte_offset // a.itemsize, "->", flat[byte_offset // a.itemsize])

t = a.T                     # transpose: no data moves
print("a.T shape/strides:", t.shape, t.strides)
print("shares memory    :", np.shares_memory(a, t))
print("C-contiguous?    :", a.flags["C_CONTIGUOUS"], t.flags["C_CONTIGUOUS"])

A 2×3 array of float64 values has strides (24, 8): to go down one row skip three 8-byte values (24 bytes), to go along one column skip one (8 bytes). Element (1, 2) is at byte 1×24 + 2×8 = 40, which is value number 5 of the flat block, and the printout confirms it holds 5.0. This ordering, where the last axis varies fastest, is called row-major or C order, and it is NumPy's default. (Fortran and MATLAB use the opposite, column-major.)

Now the payoff. The transpose a.T has shape (3, 2) and strides (8, 24): the numbers are swapped and nothing else changes. No data moved. np.shares_memory says the two arrays use the same block, and the flags show the price: the original is contiguous (its elements sit next to each other in row-major order), the transpose is not.

Analogy: one bookshelf, several reading orders

Picture 48 bytes as a single shelf of books. "Read left to right, three books per row" is one way to see a 2×3 grid. "Take every third book, starting from the left" is the way to see a column. Neither reading rearranges the shelf; each is only a set of instructions (where to start, how far to step, how many to take). Strides are exactly those instructions.

Where it breaks down: a real shelf has no cost for a different reading order. Memory does: a reading order that jumps far between neighbouring reads wastes the processor's cache, which we measure later in this chapter.

Dtypes: how many bytes and how many digits

The dtype fixes both the memory per element and the arithmetic. Integer types (int8 to int64, and unsigned uint8 to uint64) wrap around on overflow, silently. Floating-point types (float16, float32, float64) have a limited number of significant digits. Both behaviours surprise newcomers, so look at them once:

import numpy as np

img = np.array([250, 251, 252], dtype=np.uint8)
print("uint8 + 10      :", img + 10)                 # wraps around silently
print("as float32 + 10 :", img.astype(np.float32) + 10)
print("int8 range      :", np.iinfo(np.int8).min, np.iinfo(np.int8).max)
print("float32 eps     :", np.finfo(np.float32).eps, " float64 eps:", np.finfo(np.float64).eps)

x32 = np.float32(16777216.0)
print("float32: 16777216 + 1 =", x32 + np.float32(1))   # the +1 is below float32 resolution
print("float64: 16777216 + 1 =", np.float64(16777216.0) + 1)

h = np.ones(3, dtype=np.float32)
print("float32 array * Python float ->", (h * 0.1).dtype)
print("float32 array * float64 array ->", (h * np.ones(3)).dtype)
print("int array / 2 ->", (np.arange(3) / 2).dtype, "; int array // 2 ->", (np.arange(3) // 2).dtype)

Four things to read from that output. Adding 10 to a uint8 image whose pixels are 250 to 252 gives 4 to 6: the values wrapped past 255 with no warning, a notorious source of corrupted images, fixed by casting up first (astype(np.float32)). Float32 has machine epsilon about 1.2×10−7 against 2.2×10−16 for float64, so a float32 cannot even represent 16,777,217: adding 1 to 16,777,216 changes nothing. Mixing types follows type promotion rules: float32 array times a plain Python float stays float32 (NumPy 2 treats Python scalars as "weak", so they do not widen the array), but float32 times a float64 array gives float64. And / on integer arrays returns floats, whereas // stays integer.

For machine learning the practical rule is: use float32 for data and weights unless you have a reason not to (it halves memory and matches what GPUs expect), accumulate and compare in float64 when you are checking correctness, and be deliberate about anything smaller. The 16-bit and 8-bit formats are the subject of chapter 11.

Views and copies

Because an array is memory plus a description, many operations can return a new description of the same memory instead of new memory. That new object is a view. Writing through a view changes the original. An operation that must build new memory returns a copy, which is independent. Knowing which operation does which is essential, so test them:

import numpy as np

a = np.arange(12).reshape(3, 4)

row = a[1]               # basic slice: a view
row[0] = 100
print("a[1, 0] after writing to the view:", a[1, 0])

col = a[:, 2]            # strided view: every 4th element in memory
print("column strides:", col.strides, " shares memory:", np.shares_memory(a, col))

fancy = a[[0, 2]]        # integer-array indexing: a copy
fancy[0, 0] = -1
print("a[0, 0] after writing to the copy:", a[0, 0])

mask = a > 6             # boolean mask -> 1-D copy of the selected elements
print("mask picks:", a[mask], " shares memory:", np.shares_memory(a, a[mask]))

r = a.reshape(4, 3)      # reshape of a contiguous array: a view
print("reshape is a view:", np.shares_memory(a, r))
tr = a.T.reshape(12)     # cannot be expressed with strides: a copy
print("reshape after .T is a view:", np.shares_memory(a, tr))
print("owns its data: copy", a.copy().flags["OWNDATA"], "| slice", a[1].flags["OWNDATA"])
a[1, 0] after writing to the view: 100
column strides: (32,)  shares memory: True
a[0, 0] after writing to the copy: 0
mask picks: [100   7   8   9  10  11]  shares memory: False
reshape is a view: True
reshape after .T is a view: False
owns its data: copy True | slice False

The rules the output illustrates:

  • Basic slicing (a[1], a[:, 2], a[::2]) returns a view. Even a column, whose elements are 32 bytes apart in memory, is a view with a stride of 32.
  • Advanced indexing with a list or array of integers, or a boolean mask, returns a copy, because the selected elements need not be evenly spaced and so cannot be described by a stride.
  • reshape returns a view when the new shape can be described with strides over the same memory, and silently makes a copy when it cannot (as for a transposed array). ravel follows the same rule; flatten always copies.
  • np.shares_memory(x, y) and the OWNDATA flag let you check; x.copy() makes the independent copy you want when you intend to modify without touching the original.

Common misconception

"Slicing makes a smaller copy, like slicing a list." For Python lists that is true; for arrays it is the reverse. batch = data[:32] is a window onto data, so batch -= batch.mean() quietly rewrites the first 32 rows of your dataset. The opposite mistake also bites: data[idx] = 0 with an index array assigns in place, but sub = data[idx]; sub[:] = 0 modifies only a copy, and the original is unchanged. When in doubt, ask np.shares_memory, and write .copy() at the moment you mean it.

Creating and indexing arrays

A short vocabulary covers most creation needs: np.array([[1, 2], [3, 4]]) from nested lists; np.zeros((3, 4)), np.ones and np.full for constants; np.arange(0, 10, 2) and np.linspace(0, 1, 5) for ranges (the first has a step, the second a count, and linspace includes both endpoints); np.eye(3) for the identity matrix; and rng = np.random.default_rng(seed) followed by rng.normal(size=(2, 3)) for random numbers. Use the Generator object from default_rng rather than the older global np.random.seed; chapter 4 explains why. The functions reshape, transpose, swapaxes, concatenate and stack then rearrange what you have.

Indexing has three flavours, and mixing them is how most confusion starts:

  • Integer and slice indexing, per axis: a[0, 1:3] is row 0, columns 1 and 2. A : keeps a whole axis, ... stands for "all the axes I did not mention", and None (also called np.newaxis) inserts a new axis of size 1, so v[:, None] turns a (n,) vector into an (n, 1) column. Negative indices count from the end. This flavour gives views.
  • Boolean masks: a[a > 0] picks the elements where the condition holds, flattened into 1-D. np.where(cond, x, y) chooses element-wise between two arrays. This flavour gives copies.
  • Integer-array ("fancy") indexing: emb[token_ids] picks rows by position, and is exactly how an embedding lookup is written in Embeddings. It gives copies.

Axes and reductions

A reduction collapses an array by combining the elements along an axis: sum, mean, max, argmax, std. The axis argument names the axis that disappears. Summing a (2, 3) array over axis=0 removes the rows axis and leaves a (3,) result with one value per column; summing over axis=1 removes the columns axis and leaves (2,). Without an axis, everything collapses to one number. A reliable habit: say aloud "the axis I am collapsing" and write down the resulting shape before running the line.

With more than two axes, the same rule holds and negative axes become the natural way to write it. In a language model a batch of hidden states has shape (B, T, D): batch, tokens, features. x.mean(axis=-1) always means "average over the features of each token", whatever the number of leading axes. That is exactly the normalisation inside a Transformer layer; here it is on random data:

import numpy as np

x = np.array([[1., 2., 3.],
              [4., 5., 6.]])          # shape (2, 3): 2 rows, 3 columns

print("sum all      :", x.sum())
print("sum axis=0   :", x.sum(axis=0), "shape", x.sum(axis=0).shape, " (collapse the rows)")
print("sum axis=1   :", x.sum(axis=1), "shape", x.sum(axis=1).shape, " (collapse the columns)")
print("keepdims     :", x.sum(axis=1, keepdims=True).shape)

# a batch of 2 sequences, 4 tokens each, 3 features per token: shape (B, T, D)
rng = np.random.default_rng(0)
h = rng.normal(size=(2, 4, 3))
mean = h.mean(axis=-1, keepdims=True)     # (2, 4, 1): one mean per token
std = h.std(axis=-1, keepdims=True)
z = (h - mean) / std                       # layer-norm style, broadcast back to (2, 4, 3)
print("h", h.shape, "mean", mean.shape, "z", z.shape)
print("per-token mean of z ~ 0:", np.allclose(z.mean(axis=-1), 0))
print("per-token std of z  ~ 1:", np.allclose(z.std(axis=-1), 1))
sum all      : 21.0
sum axis=0   : [5. 7. 9.] shape (3,)  (collapse the rows)
sum axis=1   : [ 6. 15.] shape (2,)  (collapse the columns)
keepdims     : (2, 1)
h (2, 4, 3) mean (2, 4, 1) z (2, 4, 3)
per-token mean of z ~ 0: True
per-token std of z  ~ 1: True

Note keepdims=True. Without it the mean would have shape (2, 4), and subtracting it from an array of shape (2, 4, 3) would be a shape error, or worse, a silent misalignment. With it the mean has shape (2, 4, 1), which broadcasts against (2, 4, 3). Broadcasting is the next idea.

Broadcasting

You can add two arrays of the same shape, and you can add a scalar to an array. Broadcasting is the rule that generalises both: NumPy will combine arrays of different shapes when the shapes can be made to agree, by virtually repeating values along axes of size 1. It is the reason x - x.mean(axis=0) works without writing a loop and without building a copy of the mean for every row.

The rule has three lines. Given two shapes:

  1. Align from the right. Line up the last axes. If one shape is shorter, pretend it has extra axes of size 1 on its left.
  2. Compare axis by axis. Two sizes are compatible if they are equal, or if one of them is 1.
  3. Stretch the 1s. The result size on each axis is the larger of the two; an axis of size 1 acts as if repeated to match. If any axis is incompatible, NumPy raises a ValueError.

Step through the most instructive case: a column (4, 1) plus a row (1, 3) gives a (4, 3) table, a so-called outer sum.

Step through

Broadcasting (4, 1) + (1, 3)

  1. The question. A has shape (4, 1) and B has shape (1, 3). They are not the same shape, yet A + B is legal. To see why, apply the three-line rule.
  2. Align from the right and compare. The last axes are 1 and 3: compatible because one of them is 1. The next axes are 4 and 1: compatible for the same reason. The result will be (4, 3).
  3. A is stretched along its columns. Its single column behaves as if repeated across three columns. NumPy does this by giving that axis a stride of 0, so every column reads the same memory.
  4. B is stretched along its rows. Its single row behaves as if repeated down four rows, again with a stride of 0.
  5. Add element by element. Both operands now have shape (4, 3), so ordinary element-wise addition applies. The 12 results come from only 7 stored numbers, and no temporary stretched arrays were built.

The code below confirms the picture, including the claim about strides, and tries several shape pairs, one of them failing:

import numpy as np

col = np.array([[0], [10], [20], [30]])     # shape (4, 1)
row = np.array([1, 2, 3])                   # shape (3,)  ->  treated as (1, 3)
table = col + row                           # (4, 1) + (1, 3) -> (4, 3)
print(table)
print("result shape:", table.shape)

# nothing is copied: broadcasting gives the stretched axis a stride of 0
b = np.broadcast_to(row, (4, 3))
print("broadcast view strides:", b.strides, " real memory:", row.nbytes, "bytes")

The broadcast view has strides (0, 8): moving down the rows costs 0 bytes, so every row reads the same three numbers, and the "4×3 array" occupies the 24 bytes of the original row. That is why broadcasting is both convenient and cheap. Try your own shape pairs in the explorer. It applies the rule one axis at a time and points at the first axis that fails.

    Three broadcasting patterns you will meet constantly

    Row vector over a matrix

    (n, d) minus (d,): subtract a per-feature mean from every example. The (d,) is treated as (1, d), so the same row is applied to all n rows. This is data centring and bias addition.

    Column vector over a matrix

    (n, d) divided by (n, 1): scale every row by its own number, such as its norm or a per-token mean. The keepdims=True from the reductions section produces exactly this shape.

    Column against row

    (n, 1) with (1, m) gives (n, m): every pairing of the two sets. Outer products, distance tables and attention masks are all this pattern.

    Worked example: all pairwise distances without loops

    A concrete use of the third pattern, which returns in Dense Retrieval and in clustering: given n points X of shape (n, d) and m points Y of shape (m, d), compute the n×m table of Euclidean distances. The Euclidean distance between points x and y is √(∑k (xk − yk)2). Insert axes so that X becomes (n, 1, d) and Y becomes (1, m, d); broadcasting subtracts every pairing to give (n, m, d), and summing over the last axis finishes the job. The code checks it against the obvious double loop, and then against a second, leaner formula: since |x − y|2 = |x|2 − 2 x·y + |y|2, one matrix product replaces the big intermediate array.

    import math
import numpy as np

rng = np.random.default_rng(42)
X = rng.normal(size=(5, 3))      # 5 points in 3 dimensions: (n, d)
Y = rng.normal(size=(4, 3))      # 4 points: (m, d)

# reference: two loops over pairs
ref = np.zeros((5, 4))
for i in range(5):
    for j in range(4):
        ref[i, j] = math.sqrt(sum((X[i, k] - Y[j, k]) ** 2 for k in range(3)))

# broadcasting: (5, 1, 3) - (1, 4, 3) -> (5, 4, 3), then sum over the last axis
diff = X[:, None, :] - Y[None, :, :]
dist = np.sqrt((diff ** 2).sum(axis=-1))
print("diff shape :", diff.shape)
print("dist shape :", dist.shape)
print("matches loops:", np.allclose(dist, ref))

# memory-light version: |x - y|^2 = |x|^2 - 2 x.y + |y|^2, using one matrix product
sq = (X ** 2).sum(axis=1)[:, None] - 2 * X @ Y.T + (Y ** 2).sum(axis=1)[None, :]
dist2 = np.sqrt(np.maximum(sq, 0))
print("matches expanded form:", np.allclose(dist2, ref))
print("nearest Y for each X:", dist.argmin(axis=1))

print("2000x2000 pairs via broadcast would need", 2000 * 2000 * 128 * 8 / 1e9, "GB for diff;")
print("the matrix-product form needs", 2000 * 2000 * 8 / 1e6, "MB for the result")
    diff shape : (5, 4, 3)
dist shape : (5, 4)
matches loops: True
matches expanded form: True
nearest Y for each X: [3 1 3 2 2]
2000x2000 pairs via broadcast would need 4.096 GB for diff;
the matrix-product form needs 32.0 MB for the result

    Both vectorised versions match the loops to floating-point tolerance. The last two lines are the reason the second version exists: the broadcast approach creates an (n, m, d) intermediate, which for 2,000 points of 128 dimensions each way would need about 4 GB, whereas the matrix-product form needs only the 32 MB result. Broadcasting avoids copying its inputs, but the intermediate it computes still takes memory. (A small caution about the expanded formula: rounding can leave tiny negative values for nearly identical points, which is why the code clips with np.maximum(sq, 0) before the square root.)

    Matrix products, einsum and batched shapes

    Three operations are easy to confuse. a * b is element-wise: matching positions are multiplied, shapes must broadcast. a @ b is the matrix product: for shapes (n, k) and (k, m) it gives (n, m), each output entry being a dot product of a row of a with a column of b (chapter 6 develops why). np.dot overlaps with both for some shapes and is best avoided in new code. The last lines of the listing below show the difference on a 2×2 example.

    For arrays with more than two axes, @ treats the last two axes as the matrices and every earlier axis as a batch that is broadcast. That makes the attention score computation from Attention from First Principles a one-liner: queries Q of shape (B, T, D) times the transposed keys of shape (B, D, T) give scores of shape (B, T, T), one T×T table per example in the batch.

    np.einsum (Einstein summation) gives the same product a different notation: you name each axis with a letter and say which letters survive. "bqd,bkd->bqk" reads "for each batch b, for each query position q and key position k, sum over the feature d of Q[b, q, d] times K[b, k, d]". Letters that appear on the input side but not after the arrow are summed. Many people find this clearer than a chain of transposes, and the attention chapter uses it.

    import numpy as np

rng = np.random.default_rng(7)
B, T, D = 2, 5, 4
Q = rng.normal(size=(B, T, D))      # queries: (batch, tokens, features)
K = rng.normal(size=(B, T, D))      # keys

scores_matmul = Q @ K.transpose(0, 2, 1)            # (B,T,D) @ (B,D,T) -> (B,T,T)
scores_einsum = np.einsum("bqd,bkd->bqk", Q, K)     # name the axes instead
scores_loops = np.zeros((B, T, T))
for b in range(B):
    for q in range(T):
        for k in range(T):
            scores_loops[b, q, k] = sum(Q[b, q, d] * K[b, k, d] for d in range(D))

print("shapes:", Q.shape, "@", K.transpose(0, 2, 1).shape, "->", scores_matmul.shape)
print("matmul == einsum :", np.allclose(scores_matmul, scores_einsum))
print("matmul == loops  :", np.allclose(scores_matmul, scores_loops))

# elementwise * versus matrix @ versus dot-by-axis
a = np.array([[1, 2], [3, 4]])
b = np.array([[10, 20], [30, 40]])
print("a * b =", (a * b).tolist(), "  a @ b =", (a @ b).tolist())
    shapes: (2, 5, 4) @ (2, 4, 5) -> (2, 5, 5)
matmul == einsum : True
matmul == loops  : True
a * b = [[10, 40], [90, 160]]   a @ b = [[70, 100], [150, 220]]

    Three implementations (matrix product, einsum and an explicit triple loop over b, q and k) agree. The loop is the definition; the other two are the same arithmetic written at a higher level.

    Where the bugs live

    Broadcasting is generous: it makes many shape mistakes legal. The classic is a column against a flat array. Suppose a model returns predictions as a (4, 1) column, while the targets are a flat (4,) array, and you compute a mean squared error:

    import numpy as np

y_true = np.array([1.0, 2.0, 3.0, 4.0])             # shape (4,)
y_pred = np.array([[1.1], [1.9], [3.2], [3.8]])     # shape (4, 1): a column, as many models return

err = y_pred - y_true                                # intended: 4 errors
print("error shape:", err.shape)                     # actually (4, 4)
print("MSE as computed :", round(float(np.mean(err ** 2)), 4))

right = y_pred.ravel() - y_true                      # make the shapes agree first
print("MSE as intended :", round(float(np.mean(right ** 2)), 4))
assert right.shape == y_true.shape                   # a one-line shape contract
    error shape: (4, 4)
MSE as computed : 2.375
MSE as intended : 0.025

    The subtraction did not fail. Aligned from the right, (4, 1) and (4,) become (4, 1) and (1, 4), and the result is a (4, 4) table of every prediction minus every target. The mean of its squares is 2.375, nearly a hundred times the true 0.025, and the code ran cleanly. Nothing was loudly wrong; the loss was merely meaningless, and a model trained against it would quietly fit something else. Frameworks warn about this particular case (PyTorch emits a warning for mismatched target shapes in its MSE loss), but the general lesson is yours to apply: check shapes at boundaries.

    Habits that catch these bugs early:

    • Write the expected shape in a comment next to each line: # (B, T, D).
    • Assert shapes where data enters a function: assert y_pred.shape == y_true.shape, (y_pred.shape, y_true.shape). It costs one line and turns a silent wrong answer into an immediate failure.
    • Prefer the shape-explicit forms: keepdims=True, x[:, None] and reshape(-1, 1) over relying on implicit alignment.
    • Test with sizes that are all different (for example B=2, T=5, D=4), because a test with T equal to D cannot tell which axis you meant.
    • For heavy tensor code, notation libraries such as einops (Rogozhnikov, ICLR 2022) make the axes part of the code and checked.
    Go deeper optional: strides as a tool, and why some reshapes copy

    Windows without copies. Because strides are just numbers in a header, you can build arrays that overlap. A "sliding window" of length 4 over a vector of 10 numbers has shape (7, 4), and consecutive windows share three of their four elements, which is expressible with strides (8, 8): one step down a row moves one element, as does one step along a column. NumPy packages this safely as sliding_window_view:

    import numpy as np
from numpy.lib.stride_tricks import sliding_window_view

x = np.arange(10, dtype=np.float64)          # [0 1 2 ... 9]
w = sliding_window_view(x, 4)                # every run of 4 neighbours
print("window view shape  :", w.shape, " strides:", w.strides)
print("shares memory      :", np.shares_memory(x, w))
print("moving average     :", w.mean(axis=1))

# the same answer with an explicit loop
loop = np.array([x[i:i + 4].mean() for i in range(len(x) - 3)])
print("matches loop       :", np.allclose(w.mean(axis=1), loop))
print("bytes: x =", x.nbytes, " if windows were copied =", w.size * x.itemsize)
    window view shape  : (7, 4)  strides: (8, 8)
shares memory      : True
moving average     : [1.5 2.5 3.5 4.5 5.5 6.5 7.5]
matches loop       : True
bytes: x = 80  if windows were copied = 224

    The view has shape (7, 4) and strides (8, 8) and uses the original 80 bytes; a copied version would need 224. This is the trick behind fast moving averages and the unfold step of convolutions in Convolutions & Images. The raw tool, np.lib.stride_tricks.as_strided, accepts any shape and strides without checking them, so a wrong stride reads memory that does not belong to the array. Prefer the checked wrappers.

    Why a reshape after a transpose copies. A reshape is a view only if the new shape can be written as strides over the existing memory. Flattening a.T from the earlier figure would need the order 0, 3, 1, 4, 2, 5 in memory, and no single stride produces that sequence, so NumPy must copy the elements into a fresh block in the requested order. The same reasoning explains why ravel sometimes returns a view and sometimes not, and why code that must not copy should call reshape and then check np.shares_memory in a test.

    Memory layout and speed

    Views are free, but they are not always fast. The processor reads memory in cache lines (64 bytes on most chips, 128 on some) at a time; if your next element is in the line you just loaded, the read is almost free, and if it is 48,000 bytes away, each read pulls in a fresh line and uses a fraction of it (see The Memory Hierarchy). With a row-major array, walking along the last axis is the cheap direction. A 6,000×6,000 float64 array makes the effect visible:

    import time
import numpy as np


def best(fn, repeats=7):
    ts = []
    for _ in range(repeats):
        t0 = time.perf_counter()
        fn()
        ts.append(time.perf_counter() - t0)
    return min(ts) * 1000


n = 6000
a = np.ones((n, n))                     # C order: each row is contiguous in memory

print(f"copy of a                         : {best(lambda: a.copy()):7.1f} ms")
print(f"copy of a.T (strided reads)       : {best(lambda: np.ascontiguousarray(a.T)):7.1f} ms")

def rows():
    return [a[i].sum() for i in range(0, n, 20)]    # 300 contiguous rows

def cols():
    return [a[:, j].sum() for j in range(0, n, 20)] # 300 strided columns

print(f"sum 300 rows    (stride 8 bytes)  : {best(rows):7.2f} ms")
print(f"sum 300 columns (stride 48000 B)  : {best(cols):7.2f} ms")
    copy of a                         :     5.3 ms
copy of a.T (strided reads)       :    50.6 ms
sum 300 rows    (stride 8 bytes)  :    0.33 ms
sum 300 columns (stride 48000 B)  :    9.14 ms

    Summing rows (contiguous, stride 8 bytes) is about 28 times faster than summing the same number of columns (stride 48,000 bytes), and materialising the transpose with np.ascontiguousarray(a.T) takes roughly ten times as long as a straight copy, because each read leaps across memory. Two practical conclusions. First, put the axis you will traverse most in the last position, which is why batch-first layouts such as (B, T, D) are the norm. Second, a transpose is free to create but may be expensive to use; if you will read a transposed array many times, one up-front np.ascontiguousarray can pay for itself. (NumPy's own reductions are smart about this, so a plain a.sum(axis=0) is not slow; the penalty shows up in code that picks columns out one at a time and in copies.)

    Temporaries are the other cost. An expression such as x * 2.0 + 1.0 creates a full-sized array for x * 2.0 before adding. Reusing buffers with in-place operators (y += 1.0) or the out= argument avoids allocation, which matters when arrays are gigabytes in size. Do not apply it everywhere: in-place updates change values that other views may share, which is precisely the aliasing risk from earlier, and for small arrays the difference is negligible.

    Systems connection

    A view is the array-sized cousin of a pointer or a file offset: one underlying store, many ways to address it, and the cost depends on how the access pattern meets the cache (The Memory Hierarchy). Contiguous, same-typed data is also what lets a CPU use SIMD instructions and a GPU run thousands of threads on adjacent elements (Parallelism, SIMD & GPUs). The same shape and stride bookkeeping reappears in the GPU memory and FLOPs accounting of Parameters, FLOPs & Memory.

    State of play, October 2026

    The examples ran on NumPy 2.5 with Python 3.14. NumPy 2.0 (June 2024) changed some behaviour that older tutorials still show: type promotion now follows NEP 50, under which Python scalars are "weak" and do not widen an array's dtype (the float32 case above), and a number of long-standing aliases were removed from the main namespace. When you read code written before 2024, check the NumPy version it assumed. The array API standard (array-api specification) defines a common core that NumPy, PyTorch, JAX and CuPy are converging on, so code written against the shared subset moves between them more easily. Check the release notes of the version you pin (see chapter 4) rather than assuming.

    Key takeaways

    • An ndarray is a flat block of memory plus a header (dtype, shape, strides, offset). Element (i, j) is at offset + i×stride0 + j×stride1.
    • Transposes, basic slices and many reshapes are views: new descriptions of the same bytes. Integer-array and boolean indexing make copies. Check with np.shares_memory.
    • The axis you name in a reduction is the axis that disappears; keepdims=True keeps it as size 1 so the result broadcasts back.
    • Broadcasting aligns shapes from the right, treats missing axes as 1 and stretches axes of size 1 (with a stride of 0, so no copying). Anything else is an error.
    • Broadcasting makes many shape mistakes legal. A (n, 1) column minus a (n,) array silently gives (n, n). Assert shapes and write them in comments.
    • Integer dtypes wrap silently; float32 has about seven digits. Choose dtypes deliberately.
    • Reading along the last axis is fast; strided access is slow. Layout, not arithmetic, often decides the speed.

    Check your understanding

    A float64 array a of shape (4, 6) is C-contiguous. What are its strides, in bytes?

    1. (4, 6)
    2. (8, 48)
    3. (48, 8)
    4. (24, 4)
    Moving one column along the last axis skips one 8-byte element; moving one row skips six elements, 6 × 8 = 48 bytes. Option 2 swaps them (that is the transpose's strides). Strides are in bytes, not elements, which rules out option 1.

    You run b = a[:, 1:3] and then b[0, 0] = 99. What happens to a?

    1. a[0, 1] becomes 99, because basic slicing returns a view of the same memory.
    2. a is unchanged, because slicing copies the selected block.
    3. a is unchanged unless a is a float array.
    4. NumPy raises an error, because a slice is read-only.
    Basic (slice) indexing gives a view, so writes go through to the original. Option 2 is true for Python lists and for advanced indexing, which is why it is tempting. Slices are writable unless the array was explicitly made read-only.

    Which pair of shapes can not be broadcast together?

    1. (5, 1) and (1, 7)
    2. (2, 3, 4) and (4,)
    3. (6,) and ()
    4. (3, 4) and (3,)
    Aligning from the right, (3, 4) and (3,) compare 4 against 3 on the last axis: unequal, neither is 1, so it fails (a column of size (3, 1) would have worked). The others align: 1 stretches against 7, (4,) matches the last axis, and a scalar broadcasts against anything.

    A model outputs predictions of shape (100, 1) and the labels have shape (100,). The code computes np.mean((pred - labels) ** 2) and runs without error. What is the most likely problem?

    1. None: NumPy aligns the two arrays element by element.
    2. The subtraction broadcast to (100, 100), so the loss averages over all 10,000 prediction and label pairings instead of 100 matching pairs.
    3. The result is float32 instead of float64.
    4. NumPy silently truncates the longer array.
    (100, 1) against (100,) aligns the (100,) as (1, 100), and both size-1 axes stretch, giving (100, 100). NumPy never truncates or pairs elements implicitly by position when shapes differ. The fix is to make the shapes agree first, for example pred.ravel(), and to assert them.

    For h of shape (B, T, D), you want to subtract each token's mean over its features. Which line is correct?

    1. h - h.mean(axis=0)
    2. h - h.mean(axis=1, keepdims=True)
    3. h - h.mean(axis=-1, keepdims=True)
    4. h - h.mean(axis=-1)
    The features are the last axis, so average over axis -1 and keep it as size 1 to get (B, T, 1), which broadcasts back to (B, T, D). Axis 0 averages over the batch and axis 1 over tokens, both different statistics. Without keepdims the mean is (B, T), which does not align with (B, T, D) (it usually errors, and silently mis-subtracts when the sizes happen to line up).

    Why can summing 300 columns of a large row-major array one at a time be many times slower than summing 300 rows?

    1. Column elements are far apart in memory, so each read loads a cache line of which only one value is used; row elements are adjacent.
    2. Columns contain more numbers than rows.
    3. NumPy converts columns to Python lists before summing.
    4. Column slices are copies, and rows are views.
    Both are views of the same size; the cost difference comes from memory access pattern and the cache. Option 4 is the tempting wrong answer, but a column slice is a strided view, not a copy. Rows and columns hold the same number of elements in this test, so option 2 is also wrong.

Reproducible Experiments

An experiment you cannot rerun is an anecdote. This chapter lists everything a result depends on (code, data, configuration, software, randomness), shows how to pin each one, explains why a seed is necessary but nowhere near sufficient, and builds a small run log so that next month you can still say what produced a number.

Why this matters

Machine-learning work is a long series of small comparisons: this learning rate against that one, this prompt against another, this model against last week's. Each comparison is only as good as your ability to say what changed. Without a record you will hit the same four problems sooner or later: a result nobody can regenerate, a "regression" that was only a library update, an improvement that was seed noise, and a colleague who cannot run your notebook. The habits here are small (a lock file, an explicit seed, a one-line log record) and they are the base for the statistics of experiments in Part 4, for the eval harnesses of Assertions & Eval Harnesses, and for every lab in this path, which relies on deterministic checks.

What a result depends on

A run is reproducible when someone else (or you, in six months) can repeat it from its record and get the same result, exactly or within a stated tolerance. That needs five things to be fixed and written down:

Two levels of "same" are worth separating. Bitwise reproducibility means identical bytes out, which is achievable for CPU code with fixed seeds and pinned versions and often impractical on GPUs. Statistical reproducibility means a rerun lands within the natural run-to-run variation, which is what scientific claims need and what the later statistics chapters quantify. Decide which you are promising, and say so.

Environments: pinning the software

Your code runs on top of an interpreter and dozens of packages, and each package has a version. Update NumPy, scikit-learn or PyTorch and numbers can shift for good reasons (a bug fixed, a default changed, a different algorithm) with no change to your code. NumPy 2.0 changed type-promotion rules, and pandas 3.0 changed string handling and copy semantics (see the notes in chapter 2 and chapter 3). An unpinned environment is a hidden input to every experiment.

Virtual environments and lock files

A virtual environment is a directory holding its own interpreter link and its own installed packages, so that each project's dependencies stay separate from the system's and from each other. The standard library creates one with python3 -m venv .venv; activating it makes python and pip refer to that directory. Two files then describe it:

  • A requirements file (or the dependencies list in pyproject.toml) states what you ask for, usually with loose bounds such as numpy>=2.0. It is the intent.
  • A lock file records what was actually installed: every package, including indirect dependencies, at an exact version (and ideally with file hashes). It is the fact. Installing from it gives the same set tomorrow, on a colleague's machine, and in a container. With plain pip the simplest lock is the output of pip freeze > requirements.lock; modern tools such as uv write and read richer lock files (uv lock, uv sync) that also pin the Python version and resolve for several platforms.

A pin is only useful if you can read it back. The script below prints the fingerprint of the environment it runs in, using only the standard library. Put code like this at the top of every training script and record its output with every run:

import platform
import sys
from importlib import metadata

print("python    :", sys.version.split()[0], f"({platform.python_implementation()})")
print("platform  :", platform.system(), platform.machine())
print("executable:", "inside a venv" if sys.prefix != sys.base_prefix else "system interpreter (no venv)")
for pkg in ("numpy", "pip"):
    print(f"{pkg:10}:", metadata.version(pkg))

# the same information in the form pip freeze / requirements files use
pins = [f"{d.metadata['Name']}=={d.version}" for d in metadata.distributions()
        if d.metadata["Name"].lower() in ("numpy",)]
print("pinned    :", pins)

This run is on the system interpreter, not a venv, and the output says so, which is itself a warning sign for a project. Beyond Python packages, three more layers can matter: the Python version (pin it in .python-version or in requires-python), system libraries such as CUDA, cuDNN and BLAS (not installed by pip, and a common cause of "same code, different numbers"), and the operating system. When those matter, the outer layer is a container image built from a pinned base image and the lock file.

Systems connection

Pinning dependencies is also a security practice. An unpinned install executes whatever the package index serves today, which is how a malicious or broken release reaches your training job. Hash-checked lock files, private mirrors and reviewing upgrades are covered in Memory Safety & the Supply Chain. The same reasoning as deployment applies: build once from the lock, run the identical artefact everywhere (containers).

Randomness and seeds

Machine learning is full of deliberate randomness: initial weights, shuffling the data, splitting train from test, dropout, sampling from a model. Computers produce this with a pseudorandom number generator (PRNG): a deterministic recipe that turns a starting number, the seed, into a long sequence that looks random. The same seed gives the same sequence, which is what makes a run repeatable.

Seed everything, explicitly

There are several independent sources, and each needs its own seed. Python's random module, NumPy, and every ML framework keep separate generators. The NumPy advice since 2019 is to create a Generator object, rng = np.random.default_rng(seed), and pass rng to the code that needs it, rather than calling the legacy global np.random.seed. Passing generators explicitly has two advantages: a function's randomness is visible in its signature, and independent components can get independent streams (np.random.SeedSequence(seed).spawn(n)) instead of accidentally reusing the same numbers.

One source surprises almost everyone. Python randomises the hash of strings at start-up for security, so the iteration order of a set of strings differs between processes unless PYTHONHASHSEED is fixed:

import subprocess
import sys

code = "print(list({'cat', 'dog', 'fox', 'owl', 'ant'}))"
for seed in ("1", "2", "1"):
    out = subprocess.run([sys.executable, "-c", code], capture_output=True, text=True,
                         env={"PYTHONHASHSEED": seed}).stdout.strip()
    print(f"PYTHONHASHSEED={seed}: {out}")
PYTHONHASHSEED=1: ['dog', 'cat', 'owl', 'fox', 'ant']
PYTHONHASHSEED=2: ['cat', 'ant', 'owl', 'dog', 'fox']
PYTHONHASHSEED=1: ['dog', 'cat', 'owl', 'fox', 'ant']

The same five words come out in a different order under seeds 1 and 2, and the same order again under seed 1. Any code that iterates over a set (building a vocabulary, assigning ids, picking "the first" element) can therefore change its behaviour between runs. The cure is to avoid depending on set order: sort before iterating.

A seed is a sample, not a setting

The deeper point about seeds is statistical. One seed gives one draw from the distribution of possible outcomes, and a comparison between two methods on one seed is a comparison of two draws. To see the size of the problem, consider two classifiers on synthetic data. Model A uses all five features; model B uses only the three strongest. We build the data, split 140/60 and score both, repeating for ten seeds:

import numpy as np


def make_data(rng, n=200, d=5):
    y = rng.integers(0, 2, size=n)
    X = rng.normal(size=(n, d)) + 0.5 * (2 * y[:, None] - 1) * np.array([1, 1, 1, 0.3, 0.0])
    return X, y


def centroid_accuracy(Xtr, ytr, Xte, yte, cols):
    c0 = Xtr[ytr == 0][:, cols].mean(axis=0)
    c1 = Xtr[ytr == 1][:, cols].mean(axis=0)
    d0 = ((Xte[:, cols] - c0) ** 2).sum(axis=1)
    d1 = ((Xte[:, cols] - c1) ** 2).sum(axis=1)
    return float(((d1 < d0).astype(int) == yte).mean())


results = []
for seed in range(10):
    rng = np.random.default_rng(seed)
    X, y = make_data(rng)
    idx = rng.permutation(len(y))
    tr, te = idx[:140], idx[140:]
    a = centroid_accuracy(X[tr], y[tr], X[te], y[te], cols=[0, 1, 2, 3, 4])   # all features
    b = centroid_accuracy(X[tr], y[tr], X[te], y[te], cols=[0, 1, 2])         # drops the two weakest
    results.append((a, b))
    print(f"seed {seed}: A={a:.3f}  B={b:.3f}  B-A={b - a:+.3f}")

a, b = np.array(results).T
diff = b - a
print(f"A: mean {a.mean():.3f}, min {a.min():.3f}, max {a.max():.3f}   B: mean {b.mean():.3f}, min {b.min():.3f}, max {b.max():.3f}")
print(f"mean B-A = {diff.mean():+.4f}, std = {diff.std(ddof=1):.4f}, B better in {(diff > 0).sum()} of 10 seeds")
print(f"standard error of the mean difference = {diff.std(ddof=1) / np.sqrt(10):.4f}")

Look at what the numbers say. Model A alone ranges from 0.700 to 0.883 across seeds: a swing of eighteen percentage points from the random split alone. The mean difference between B and A is +0.0033 with a standard deviation of 0.0172, and B is better in only 3 of ten seeds (equal in six, worse in one). Had you run only seed 3, you would have reported "B improves accuracy by 3.3 points"; had you run seed 0, "B is 3.3 points worse". Both statements are true of their seed and useless as claims. The mean difference (0.0033) is smaller than its own standard error (0.0054), so the data do not distinguish the models. The tools for making that judgement properly are the confidence intervals, bootstrap and paired tests of chapter 15, applied to LLM evaluation in Statistics for Evals. The practical rule for now: for any comparison whose difference is small, run several seeds, report the mean and spread, and compare paired (same seed for both methods). Henderson et al. (AAAI 2018) showed how badly reinforcement-learning results can depend on seeds and implementation details, and the lesson generalises.

Common misconception

"I set the seed, so my experiment is reproducible." The seed fixes one of five inputs. It does nothing about a different library version, a changed dataset file, an edited config or a different git commit. And on GPUs, some operations are non-deterministic even with every seed fixed, because they add numbers in an order that depends on thread timing (next section). Frameworks provide switches that force deterministic kernels at some speed cost (see the PyTorch note on randomness in Further reading), but the safe claim is "repeatable within a tolerance, given this record".

Non-determinism that seeds cannot fix

Floating-point addition is not associative (chapter 1), so the order of a sum affects its last digits. A parallel reduction on many cores or a GPU adds partial sums in whatever order the threads finish, which can differ run to run. This script sums the same million float32 numbers in five different orders:

import numpy as np

rng = np.random.default_rng(0)
x = rng.normal(size=1_000_000).astype(np.float32)

sums = []
for trial in range(5):
    order = np.random.default_rng(trial).permutation(len(x))
    sums.append(float(np.sum(x[order], dtype=np.float32)))   # same numbers, different order
for t, s in enumerate(sums):
    print(f"order {t}: {s:.6f}")
print("distinct float32 sums:", len(set(sums)))
print("float64 reference    :", f"{float(np.sum(x.astype(np.float64))):.6f}")
print("largest spread       :", f"{max(sums) - min(sums):.2e}")
order 0: 998.570557
order 1: 998.570740
order 2: 998.570374
order 3: 998.570679
order 4: 998.570557
distinct float32 sums: 4
float64 reference    : 998.570663
largest spread       : 3.66e-04

Four distinct answers from five orders, spread over 3.7×10−4 on a total near 998.57 (about 4 parts in ten million, in the range float32 can resolve), and none exactly equals the float64 reference. For a single sum this is harmless. Over a training run of billions of such operations, tiny differences can grow, which is why two "identical" GPU runs often have slightly different loss curves, and why the right test of reproduction is "within the usual seed-to-seed spread", not "identical to the last digit".

Notebooks and scripts

A notebook (Jupyter or similar) mixes code, output and prose in cells you run in any order. That makes it excellent for exploring a dataset or explaining a result, and risky for anything you need to repeat. The danger is hidden state: variables live in the running kernel, so a notebook can hold values left over from a cell you deleted or ran out of order, and it can produce an answer that no top-to-bottom run reproduces. A script runs from a clean start every time, takes its configuration from arguments or a file, and can be called from a scheduler, a test or a colleague's terminal.

NotebookScript or module
Best forExploration, plots, teaching, reports with narrativeTraining runs, data pipelines, anything repeated or scheduled
StateHidden in the kernel; order of execution mattersStarts clean; state is explicit
Version controlDiffs are noisy (JSON with outputs); needs a tool such as nbstripout or jupytextPlain text diffs and reviews
TestingHard to unit-test cell codeFunctions can be imported and tested
ConfigurationEdited in cells, easy to forget what was runArguments or a config file, logged with the run

Whatever you choose, one rule rescues most notebooks: before sharing or trusting a result, restart the kernel and run all cells from the top. If it does not work or gives different numbers, the notebook was relying on hidden state.

Experiment logs: the run record

The final piece is writing down each run. An experiment log is a record per run of the five inputs and the outputs. The minimum useful fields are: a run id; the configuration (hyperparameters, seed, data splits); the code version (git commit and whether the working tree had uncommitted changes); a data identifier (a content hash of the input file, so an edited file is detectable); the environment fingerprint; the metrics; and timing. A single JSON line per run, appended to a file, is enough to start with and easy to load and compare. The script below does that, using the standard library plus NumPy, and runs a toy regression three times, the last two with identical configuration:

import hashlib
import json
import platform
import subprocess
import sys
import time
from importlib import metadata
from pathlib import Path

import numpy as np

LOG = Path("runs.jsonl")


def sha256_of(path):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for block in iter(lambda: f.read(1 << 20), b""):
            h.update(block)
    return h.hexdigest()[:12]


def git_state():
    try:
        commit = subprocess.run(["git", "rev-parse", "--short", "HEAD"], capture_output=True, text=True, check=True).stdout.strip()
        dirty = bool(subprocess.run(["git", "status", "--porcelain"], capture_output=True, text=True).stdout.strip())
        return {"commit": commit, "dirty": dirty}
    except (subprocess.CalledProcessError, FileNotFoundError):
        return {"commit": "unknown", "dirty": None}


def run_experiment(config, data_path):
    started = time.time()
    rng = np.random.default_rng(config["seed"])
    data = np.loadtxt(data_path, delimiter=",")
    idx = rng.permutation(len(data))
    train, test = data[idx[:config["n_train"]]], data[idx[config["n_train"]:]]
    w = np.polyfit(train[:, 0], train[:, 1], deg=config["degree"])
    rmse = float(np.sqrt(np.mean((np.polyval(w, test[:, 0]) - test[:, 1]) ** 2)))
    record = {
        "run_id": hashlib.sha256(json.dumps(config, sort_keys=True).encode()).hexdigest()[:8],
        "config": config,
        "data_sha256": sha256_of(data_path),
        "git": git_state(),
        "env": {"python": platform.python_version(), "numpy": metadata.version("numpy")},
        "metrics": {"test_rmse": round(rmse, 4)},
        "seconds": round(time.time() - started, 3),
    }
    with LOG.open("a") as f:
        f.write(json.dumps(record, sort_keys=True) + "\n")
    return record


if __name__ == "__main__":
    LOG.unlink(missing_ok=True)
    rng = np.random.default_rng(123)
    x = np.linspace(0, 3, 60)
    np.savetxt("data.csv", np.column_stack([x, 2 * x ** 2 - x + rng.normal(0, 0.5, 60)]), delimiter=",", fmt="%.6f")
    for cfg in ({"seed": 0, "degree": 1, "n_train": 40}, {"seed": 0, "degree": 2, "n_train": 40},
                {"seed": 0, "degree": 2, "n_train": 40}):
        r = run_experiment(cfg, "data.csv")
        print(r["run_id"], cfg, "->", r["metrics"], "data", r["data_sha256"])
    rows = [json.loads(line) for line in LOG.open()]
    print("log has", len(rows), "records; identical config gives identical run_id and metric:",
          rows[1]["run_id"] == rows[2]["run_id"] and rows[1]["metrics"] == rows[2]["metrics"])
    print("one record:", json.dumps(rows[1], sort_keys=True)[:260], "...")

Read the output as a test of the record. The two runs with the same configuration have the same run id (a hash of the config) and identical metrics, which is the repeatability we wanted; the degree-1 and degree-2 fits are told apart by id and by RMSE (1.42 against 0.52, because the data were generated from a quadratic). The data hash would change if anyone edited data.csv. Because the working directory is not a git repository, the record honestly says the commit is "unknown" instead of inventing one; in a real project that field is the link from a number back to the exact code, and recording whether the tree was dirty tells you when the link is not exact.

Hand-rolled logs scale to a few dozen runs. Beyond that, experiment trackers (MLflow, Weights & Biases, Neptune and similar, or a plain database) add a web view, comparison charts and artefact storage, and data-versioning tools (DVC, lakeFS, or table formats with snapshots) manage large datasets. The tool matters less than the discipline: never edit a dataset in place, give every snapshot an identifier, and log it with every run. A scientist who cannot say which spreadsheet produced a figure is in the position of the economists in the first case study.

Analogy: a lab notebook and a recipe card

A chemist writes down the exact reagents, quantities, temperature and date, because "I mixed the usual things" cannot be repeated by anyone, including the chemist next month. A run record is the same: it turns a one-off event into a procedure that others can follow.

Where it breaks down: a chemist records physical facts, which stay put. Software facts move under you: a package you did not pin changes beneath the recipe, and a data file can change while keeping the same name. That is why a software record needs hashes and lock files, not just names.

A reproducibility checklist

Pulling the chapter together, here is a checklist worth pasting into the README of every project in this path:

  1. One command creates the environment from the lock file, and one command reproduces the headline result.
  2. Python and package versions are pinned; system-level dependencies (CUDA, drivers) are recorded.
  3. Data is immutable and identified by a hash or version; the README says where it comes from and how to fetch it.
  4. All randomness is seeded through explicit generators, with seeds in the config; set iteration order does not matter.
  5. Configuration is in a file or arguments, never edited in code between runs, and is logged.
  6. Every run appends a record with commit, dirty flag, config, data hash, environment, metrics.
  7. Claims come with spread: several seeds, mean and an interval, not a single best run.
  8. Notebooks restart and run clean before anyone trusts them.

State of play, October 2026

The tooling here changes quickly, so treat names as examples. uv (from Astral) has become a common way to create environments and write lock files, and installed on the machine used to build this chapter; check its documentation for the current commands. PEP 723 lets a single script declare its own dependencies in a comment block, which suits small reproducible scripts, and the Python packaging community has been standardising a cross-tool lock-file format (see the Python Packaging User Guide for its status). Experiment trackers and data-versioning products come and go. The five-input model in this chapter does not.

Try it yourself

Create a fresh folder and an isolated environment, install nothing, and run the fingerprint script inside it.

$ python3 -m venv .venv && . .venv/bin/activate
$ python3 env_fingerprint.py

The script's third line should now report a venv, and the NumPy lookup will fail until you install it: why? Then install NumPy, run pip freeze and compare its output with the fingerprint. Next, run the seed experiment with range(10) replaced by range(100) and look at how the standard error shrinks; roughly how many seeds do you need before the +0.0033 difference is bigger than twice its standard error? Finally, extend the logger to store the full output of pip freeze as a hash, and check that changing a package version changes it.

Key takeaways

  • A result depends on five inputs: code, data, configuration, environment and randomness. Reproducibility means being able to name all five.
  • Pin the environment with a virtual environment and a lock file (exact versions, indirect dependencies included); record Python version and system libraries too.
  • Seed every source of randomness through explicit generators, avoid depending on set order, and remember that a seed makes one draw, not a guarantee.
  • Seed-to-seed variation can be much larger than the difference between methods. Run several seeds, compare paired, and report spread.
  • GPU and parallel reductions are not bitwise deterministic because floating-point sums depend on order; aim for statistical reproducibility.
  • Use notebooks to explore and scripts to run; restart-and-run-all before trusting a notebook.
  • Log one record per run, with config, commit, data hash, environment and metrics, and never edit data in place.

Check your understanding

A teammate reruns your training script with the same seed and gets a different accuracy. Which is not a plausible cause?

  1. A dependency was upgraded between the runs.
  2. The dataset file was edited or replaced.
  3. A seed is a hash of the file name, so a renamed file reseeds the generator.
  4. A GPU kernel summed numbers in a different order.
Seeds are numbers you pass in; they do not depend on file names. The other three are real: library behaviour, data changes and non-associative parallel sums all alter results with an unchanged seed.

What is the difference between a requirements file with numpy>=2.0 and a lock file?

  1. The requirements file states what you ask for; the lock file records the exact versions, including indirect dependencies, that were installed.
  2. The lock file is faster to download.
  3. There is none: both are lists of package names.
  4. The requirements file pins versions; the lock file lists only the direct dependencies.
Intent versus fact. A loose bound can resolve to different versions on different days; the lock freezes the resolved set. Option 4 reverses the roles.

Across ten seeds, method B beats method A in 6 seeds and loses in 4, with a mean difference of +0.2 points and a standard deviation of 1.5 points. What is the best conclusion?

  1. B is better, since it wins more often.
  2. A is better, since the losses were larger.
  3. The methods are exactly equal.
  4. The evidence does not separate them; the difference is small compared with seed-to-seed variation, so more seeds or a proper interval are needed before claiming anything.
A 6-4 record and a 0.2-point mean against a 1.5-point spread is well within noise. Claiming a winner is unjustified, but so is claiming exact equality; the correct stance is that the data are inconclusive.

A notebook gives a great result, but on "restart and run all" the numbers change. What is the likely reason?

  1. Notebooks cannot be rerun.
  2. Hidden state: cells were run out of order or variables from deleted cells influenced the result.
  3. Restarting changes the CPU's clock speed.
  4. The kernel forgets the random seed.
The kernel's state depends on execution history, so a different order or leftover variables yields a different result. Option 4 is tempting; if the seed is set in a cell, rerunning from the top sets it again.

Why is it useful to store a hash of the data file in every run record?

  1. It makes the training run faster.
  2. It encrypts the data for safety.
  3. It reveals whether the data changed between runs, even if the file name stayed the same.
  4. It replaces the need for a random seed.
A content hash changes whenever the bytes change, catching silent edits. It does not speed anything up, is not encryption, and is unrelated to seeding.

Your code builds an id for each word by iterating over a Python set of strings. Ids differ between runs with identical seeds. What is the most likely cause and fix?

  1. NumPy's generator is not seeded; call np.random.seed.
  2. String hashing is randomised per process, so set iteration order varies; sort the words before assigning ids.
  3. The set is too large; use a list instead of a set.
  4. Python lists are stored in a random order.
Hash randomisation of strings changes set order across processes. Sorting removes the dependence. NumPy seeding is irrelevant here, and a list would work only because it has a defined order (so would a sorted set).

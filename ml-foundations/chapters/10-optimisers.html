Gradient Descent & Optimisers

A gradient tells you which way is downhill, not how far to walk. This chapter covers the update rule that turns gradients into learning, the step size that decides whether training glides, crawls or explodes, and the family of refinements (minibatches, momentum, Adam, AdamW, schedules, clipping) that real training runs depend on. It ends with the failure modes and a checklist for diagnosing them.

Why this matters

Chapters 8 and 9 produce a gradient of the loss with respect to every weight. Something must then decide how to change the weights, and that choice often decides whether a run succeeds. A learning rate a few times too high wastes a week of GPUs on nan; an optimiser whose settings were copied from a different setup learns slowly or generalises worse; the optimiser itself stores two extra numbers per weight, which is a large share of training memory (A3, chapter 2). This chapter underlies linear and logistic regression (A1, chapter 5), the training dynamics of deep networks (A2, chapter 3), the stability tricks of large runs (A2, chapter 17) and every fine-tuning method in A3. You will build the optimisers yourself in Lab 3, and Case 3 follows one famous optimiser detail in depth.

The update rule and the step size

Gradient descent is a loop. Start with weights w. Compute the gradient ∇L(w), which points uphill. Take a step the other way:

w ← w − η ∇L(w).

The positive number η (eta) is the learning rate or step size. It is the most important setting in training, and the simplest case shows exactly why. Take one weight and the loss L(x) = ½ λ x², a bowl with its minimum at 0 and curvature λ (chapter 8). The gradient is λ x, so one step gives

x ← x − η λ x = (1 − ηλ) x.

Every step multiplies x by the same factor r = 1 − ηλ, so after t steps x is rt times its starting value. Everything follows from r:

  • 0 < r < 1 (small η): x shrinks smoothly towards 0. The closer r is to 1, the slower.
  • r = 0 (η = 1/λ): the minimum is reached in one step. This is the best a quadratic allows.
  • −1 < r < 0: each step overshoots the minimum and lands on the other side, but a little closer. Converges, with sign flipping.
  • r = −1 (η = 2/λ): bounces between +x and −x forever.
  • r < −1 (η > 2/λ): each overshoot is bigger than the last. Divergence.

The rule is η < 2/λ: the step size is bounded by the curvature. Running it, for λ = 10 (so the limit is 0.2):

# Gradient descent on f(x) = 0.5 * lam * x^2, whose gradient is lam * x.
lam = 10.0
print(f"curvature lam = {lam}, so the stability limit is 2/lam = {2 / lam}")
print(f"{'eta':>6} {'factor 1-eta*lam':>17} {'x after 12 steps':>17}   behaviour")

        what = "bounces forever"
    else:
        what = "diverges"
    print(f"{eta:6.2f} {factor:17.2f} {x:17.4g}   {what}")

Analogy: walking down a hill in fog

You cannot see the valley; you can only feel the slope under your feet. Each step goes downhill, and the stride length is your choice. Tiny strides are safe but take all day. Huge strides carry you across the valley onto the opposite slope, higher than where you began. The best stride depends on how sharply the ground curves: gentle terrain tolerates long strides, a narrow gully does not.

Where it breaks down: a hiker adjusts stride by sight. Plain gradient descent uses one fixed stride in every direction, although the curvature differs from one direction to another, and that mismatch is exactly what the following sections address.

A real loss is not a single bowl but, locally, a bowl in every direction. For a loss with many parameters the curvature in direction i is an eigenvalue λi of the Hessian (chapters 7 and 8), and the step must satisfy η < 2/λmax, the sharpest direction. The practical lesson is the same as the toy: find the largest learning rate that does not blow up, then back off. Chapter 17 of A2 returns to the odd fact that large training runs often sit close to this edge.

Narrow valleys: why one step size is not enough

Now give the loss two directions with different curvature: f(x, y) = ½(x² + κ y²), with κ = 20 meaning y is twenty times steeper than x. The stability limit is set by the steep direction: η < 2/κ = 0.1. But progress along the gentle x direction needs a large η, because x shrinks by (1 − η) per step and with η = 0.09 that is only 9% per step. The ratio of the largest to the smallest curvature, κ = λmax / λmin, is the condition number. With the best fixed η = 2/(λmin + λmax), the error shrinks each step by the factor (κ − 1)/(κ + 1), which is close to 1 when κ is large: the number of steps grows in proportion to κ.

The orange path is the behaviour you get in any ill-conditioned problem: steep sides send the iterate bouncing across the valley while it creeps along the floor. The next section's fix is in blue. First, measure the effect. For each κ, the script searches 400 learning rates and reports the fewest steps to bring the error below 10−6, next to the theoretical count, and next to the same search with momentum 0.9 (introduced just below):

import numpy as np
from opts import SGD

def run(kappa, mu, lr, tol=1e-6, cap=20000):
    """Iterations to bring |w| below tol on f = 0.5*(x^2 + kappa*y^2), from (1, 1)."""
    H = np.array([1.0, kappa])
    w, opt = np.array([1.0, 1.0]), SGD(lr, mu)
    for t in range(1, cap + 1):
        w = opt.step(w, H * w)
        if not np.all(np.isfinite(w)) or np.abs(w).max() > 1e6:
            return None
        if np.linalg.norm(w) < tol:
            return t
    return None

def best(kappa, mu):
    grid = np.geomspace(1e-4, 2.0, 400)
    res = [(run(kappa, mu, lr), lr) for lr in grid]
    res = [(t, lr) for t, lr in res if t is not None]
    return min(res)

print(f"{'kappa':>6} {'SGD iters':>10} {'theory':>8} {'momentum 0.9 iters':>19}")
for kappa in (10, 100, 1000):
    t0, lr0 = best(kappa, 0.0)
    t1, lr1 = best(kappa, 0.9)
    rate = (kappa - 1) / (kappa + 1)
    theory = np.log(1e-6 / np.sqrt(2)) / np.log(rate) if rate > 0 else 1
    print(f"{kappa:6d} {t0:10d} {theory:8.0f} {t1:19d}")

Plain gradient descent needs about 7,000 steps at κ = 1000, almost exactly 100 times what it needs at κ = 10, and the theory (a one-line formula) predicts it to within about 2%. Ill-conditioning is not a vague nuisance; it sets the cost. It is also common: the loss surface of a neural network has curvatures that span many orders of magnitude.

Stochastic gradient descent

So far the gradient was exact. For a dataset of N examples the loss is an average, L(w) = (1/N) ∑i ℓi(w), and the full gradient costs a pass over all the data per step. For a billion-example dataset that is hopeless. Stochastic gradient descent (SGD) takes the average over a small random minibatch of B examples instead. This estimate is unbiased (its average over random draws equals the full gradient) but noisy. The noise is easy to quantify: the variance of an average of B independent draws falls as 1/B, so the standard deviation falls as 1/√B. Measured on linear regression with 20,000 examples (true slope 3), evaluating gradients at w = 0:

import numpy as np

rng = np.random.default_rng(0)
N = 20000
x = rng.standard_normal(N)
y = 3 * x + rng.standard_normal(N)         # true slope 3, noise sd 1
w = 0.0                                    # evaluate gradients at w = 0
per_example = -2 * x * (y - w * x)         # d/dw of (y - w x)^2, one value per example
full = per_example.mean()
print(f"full-batch gradient at w=0: {full:.3f}  (theory: -6)")
print(f"{'batch B':>8} {'mean of minibatch grads':>24} {'std':>8} {'std * sqrt(B)':>14}")
for B in (1, 4, 16, 64, 256, 1024):
    g = np.array([per_example[rng.integers(0, N, B)].mean() for _ in range(4000)])
    print(f"{B:8d} {g.mean():24.3f} {g.std():8.3f} {g.std() * np.sqrt(B):14.3f}")

The mean stays at the true gradient (about −6) for every batch size: unbiased. The standard deviation, however, falls from 8.4 to 0.28, and the last column, std × √B, is constant to within a few per cent, confirming the 1/√B law. Three consequences matter in practice.

  • Noise is a feature and a floor. Early in training the signal is large and cheap noisy steps are almost as good as exact ones. Late in training, with a fixed η, the iterate jitters around the minimum rather than settling in it; decaying η (below) shrinks the jitter.
  • Diminishing returns on batch size. Quadrupling B halves the noise but costs four times the compute per step. Beyond a problem-dependent critical batch size (McCandlish et al., 2018), larger batches stop reducing the number of steps needed.
  • Batch size and learning rate move together. A common rule of thumb for SGD (Goyal et al., 2017) is to scale η in proportion to B, with a warmup period. For Adam-style optimisers a square-root scaling is the more usual heuristic. Treat both as starting points to test, not laws.

Common misconception

"SGD is just gradient descent with a worse gradient, so full-batch is better when you can afford it." Noise is not purely a cost. It is cheap (a step per few examples instead of per dataset), it lets the iterate escape sharp, narrow dips, and it often correlates with better generalisation. Large-batch training has to work to avoid giving up some of that, which is why batch size is a hyperparameter to tune with the learning rate rather than something to push to the memory limit.

Momentum

The zigzag in the valley has a clear signature: the sideways components of successive gradients alternate in sign, while the component along the valley keeps the same sign. If you average recent gradients, the sideways parts cancel and the consistent part survives. Momentum keeps a running velocity v and steps along it:

v ← β v + g,    w ← w − η v,    with β typically 0.9.

Unrolling shows what v is: vt = gt + β gt−1 + β² gt−2 + …, an exponentially weighted sum of past gradients whose weights fade geometrically, with an effective memory of about 1/(1 − β) = 10 steps. If the gradient were constant, v would settle at g/(1 − β) = 10 g, so momentum with β = 0.9 takes steps ten times larger in the consistent direction. That is why the learning rate usually needs to be smaller with momentum (the optimum above moves from 0.0189 to 0.005 in the table later), and why it accelerates the flat direction without increasing oscillation in the steep one. Also called the heavy-ball method (Polyak, 1964): the iterate behaves like a ball with inertia rolling in a bowl with friction.

In the κ table above, momentum 0.9 needs 199, 218 and 254 steps at κ = 10, 100 and 1000, nearly independent of κ, where plain descent needs 70, 693 and 7,021. The speed-up grows with ill-conditioning (the theory says the step count scales like √κ rather than κ). Note the κ = 10 row: momentum is slower there, because inertia makes the iterate overshoot and oscillate when the problem needed no help. A technique is a good match to a problem structure, not a free gain. A variant, Nesterov momentum, evaluates the gradient at the point momentum is about to carry you to; it has slightly better guarantees and is a one-line change in libraries.

Adaptive methods: a step size per weight

Momentum smooths the direction. A different idea tackles the scale. If the gradient for weight A is typically 100 times bigger than for weight B, a single η is wrong for at least one of them. Divide each weight's gradient by a running estimate of its own typical size. This is the thread through a family of methods:

  • AdaGrad (Duchi, Hazan and Singer, 2011) divides by the square root of the sum of all past squared gradients. Rarely-active parameters keep large steps; but the sum only grows, so steps shrink to nothing.
  • RMSProp (Tieleman and Hinton, 2012, in a lecture, never published as a paper) replaces the sum by an exponential moving average, s ← ρ s + (1 − ρ) g², so the scale estimate forgets, and steps by η g / (√s + ε).
  • Adam (Kingma and Ba, 2014) combines RMSProp's scale estimate with momentum's direction estimate.

Adam keeps two running averages per parameter: m, an average of the gradient (the direction), and v, an average of the squared gradient (the scale), with decay rates β1 and β2. Both start at zero, which biases early estimates towards zero: after the first step m = (1 − β1) g, only 10% of g. If the gradient has a steady mean, the expected value of m after t steps is (1 − β1t) times that mean, so dividing by (1 − β1t) removes the bias. The same applies to v. The final step is

The idea

  1. settings: η = 0.1, β1 = 0.9, β2 = 0.999, ε = 1e−8
  2. m ← β1 m + (1−β1) g; v ← β2 v + (1−β2) g²
  3. m̂ ← m ÷ (1−β1t); v̂ ← v ÷ (1−β2t)
  4. step ← m̂ ÷ (√v̂ + ε); w ← w − η × step
  5. run on gradients 2, 200, and 2 then −2
"""One Adam update by hand: w <- w - lr * m_hat / (sqrt(v_hat) + eps).
One weight, so every number can be checked on a calculator."""
import math

# ── 1. Settings and a starting point ─────────────────────────────────────
LR = 0.1                                 # eta, the learning rate
BETA1, BETA2 = 0.9, 0.999                # decay of the two running averages
EPS = 1e-8                               # keeps the division safe near 0


def adam_steps(grads, w=1.0):
    """Run Adam over a list of gradients; print each stage of each step."""
    m = v = 0.0                          # both averages start at zero
    for t, g in enumerate(grads, start=1):
        # ── 2. Two running averages: direction m, squared size v ─────────
        m = BETA1 * m + (1 - BETA1) * g
        v = BETA2 * v + (1 - BETA2) * g * g
        # ── 3. Undo the bias towards zero from starting at zero ──────────
        m_hat = m / (1 - BETA1 ** t)
        v_hat = v / (1 - BETA2 ** t)
        # ── 4. Divide direction by typical size, then scale by lr ────────
        ratio = m_hat / (math.sqrt(v_hat) + EPS)
        w = w - LR * ratio
        print(f"t={t} g={g:g} m={m:.3f} v={v:.3f} m^={m_hat:.3f} "
              f"v^={v_hat:.1f} step={ratio:.3f} w={w:.3f}")
    return w

Here, in full, are the four optimisers as short NumPy classes. These are the ones the widget and the table below use:

import numpy as np

class SGD:
    def __init__(self, lr, momentum=0.0):
        self.lr, self.mu, self.v = lr, momentum, None
    def step(self, w, g):
        if self.v is None:
            self.v = np.zeros_like(w)
        self.v = self.mu * self.v + g          # heavy-ball buffer (mu = 0 gives plain SGD)
        return w - self.lr * self.v

class RMSProp:
    def __init__(self, lr, beta=0.9, eps=1e-8):
        self.lr, self.beta, self.eps, self.s = lr, beta, eps, None
    def step(self, w, g):
        if self.s is None:
            self.s = np.zeros_like(w)
        self.s = self.beta * self.s + (1 - self.beta) * g * g
        return w - self.lr * g / (np.sqrt(self.s) + self.eps)

class Adam:
    def __init__(self, lr, b1=0.9, b2=0.999, eps=1e-8, wd=0.0, decoupled=False):
        self.lr, self.b1, self.b2, self.eps, self.wd, self.decoupled = lr, b1, b2, eps, wd, decoupled
        self.m = self.v = None
        self.t = 0
    def step(self, w, g):
        if self.m is None:
            self.m, self.v = np.zeros_like(w), np.zeros_like(w)
        if self.wd and not self.decoupled:
            g = g + self.wd * w                # L2 penalty folded into the gradient (Adam)
        self.t += 1
        self.m = self.b1 * self.m + (1 - self.b1) * g
        self.v = self.b2 * self.v + (1 - self.b2) * g * g
        mhat = self.m / (1 - self.b1 ** self.t)      # bias correction
        vhat = self.v / (1 - self.b2 ** self.t)
        w = w - self.lr * mhat / (np.sqrt(vhat) + self.eps)
        if self.wd and self.decoupled:
            w = w - self.lr * self.wd * w      # decoupled decay (AdamW)
        return w

A direct consequence of the formula is worth checking, because it explains much of Adam's behaviour. At the first step, m̂ = g and v̂ = g², so the step is η g / (|g| + ε), which is η × sign(g) whatever the size of g. Adam's per-weight step is bounded at about η, independent of gradient scale:

This is why Adam is forgiving across weights of very different scale (embeddings next to layer norms) and also why its learning rate means something different from SGD's: it is roughly the size of a step in weight units, typically 10−4 to 10−3 for transformers. The ε term (default 10−8) keeps the division finite when v is near 0; it matters when gradients are tiny, which is a real concern in 16-bit arithmetic (chapter 11).

Weight decay, and why AdamW exists

Weight decay shrinks every weight a little on each step, w ← (1 − ηλwd) w, which discourages large weights and acts as regularisation (A1, chapter 6). For plain SGD it is equivalent to adding the L2 penalty ½ λwd |w|² to the loss, because the penalty's gradient is λwd w. That equivalence is the trap. In Adam, if the penalty is added to the gradient, it flows through the m and v machinery and gets divided by √v̂: weights with large gradients are decayed less, and weights with small gradients more, so the effective regularisation depends on gradient scale instead of on the setting you chose. Loshchilov and Hutter (2017, published at ICLR 2019; see Further reading) proposed AdamW: apply the decay directly to the weights, outside the adaptive step. The last block of the output above measures it. Weights whose gradients have typical size 0.01, 0.1, 1 and 10 are decayed per step by 10−3, 7×10−4, 10−4 and 10−5 under L2-in-the-gradient, a hundredfold spread; under AdamW all four are decayed by ηλwd = 10−4. (The quiet weight is regularised ten times too hard and the loud one ten times too softly, relative to the setting you asked for.) Case 3 tells the story and the evidence. By convention decay is usually applied to weight matrices but not to biases or normalisation scales.

Learning-rate schedules

A good learning rate is not constant over a run. Early on you want a big step to make progress; late in the run a big step makes the iterate jitter around the minimum (the SGD noise floor). Practice converged on schedules with a few common pieces:

  • Warmup. Start near zero and ramp linearly to the peak over the first few hundred or thousand steps. Early in training Adam's v̂ is estimated from few samples and the weights are random, so full-size steps can be destabilising; warmup lets the statistics settle first.
  • Decay. Reduce the learning rate over the run. Cosine decay (from Loshchilov and Hutter's SGDR, 2016) follows half a cosine wave from the peak down to a floor, often 10% of the peak. Linear and step decay are also used.
  • Warmup-stable-decay (WSD). Hold the peak constant for most of the run and decay only at the end (described, for example, in the MiniCPM report, Hu et al., 2024). Because the stable phase does not depend on the final length, a run can be extended or branched to produce checkpoints at several budgets.
import math

def warmup_cosine(t, total, warmup, floor=0.1):
    """Linear warmup to 1.0, then cosine decay to `floor` (all as fractions of the peak LR)."""
    if t < warmup:
        return t / warmup
    progress = (t - warmup) / (total - warmup)
    return floor + (1 - floor) * 0.5 * (1 + math.cos(math.pi * progress))

def wsd(t, total, warmup, decay_start, floor=0.1):
    """Warmup, long stable phase at the peak, then a linear decay to `floor`."""
    if t < warmup:
        return t / warmup
    if t < decay_start:
        return 1.0
    return 1.0 - (1 - floor) * (t - decay_start) / (total - decay_start)

Gradient clipping

Occasionally a batch produces an enormous gradient (a rare example, a numerical glitch, a region of sharp curvature). One such step can throw the weights far away and wreck a run. Gradient clipping by global norm is the standard guard: compute the L2 norm of the entire gradient (all parameters concatenated), and if it exceeds a threshold c (often 1.0), multiply every gradient by c divided by the norm. Because one common factor is applied, the direction is preserved and only the length is capped:

import numpy as np

def clip_by_global_norm(grads, max_norm):
    """Scale ALL gradients by one factor so that their combined L2 norm is at most max_norm."""
    total = np.sqrt(sum(float((g ** 2).sum()) for g in grads))
    scale = min(1.0, max_norm / (total + 1e-6))
    return [g * scale for g in grads], total, scale

rng = np.random.default_rng(0)
shapes = [(64, 32), (32,), (32, 8), (8,)]
normal = [rng.standard_normal(s) * 0.02 for s in shapes]
spike = [g * 40 for g in normal]            # a bad batch: every gradient 40 times larger

for name, grads in (("ordinary batch", normal), ("spike batch", spike)):
    clipped, total, scale = clip_by_global_norm(grads, 1.0)
    after = np.sqrt(sum(float((g ** 2).sum()) for g in clipped))
    d0 = grads[0].ravel() / np.linalg.norm(grads[0]); d1 = clipped[0].ravel() / np.linalg.norm(clipped[0])
    print(f"{name:15s} norm before {total:7.2f}  scale {scale:.4f}  norm after {after:.3f}  direction unchanged: {np.allclose(d0, d1)}")
ordinary batch  norm before    0.97  scale 1.0000  norm after 0.971  direction unchanged: True
spike batch     norm before   38.82  scale 0.0258  norm after 1.000  direction unchanged: True

The ordinary batch passes through untouched (norm 0.97 < 1); the 40× spike is scaled by 0.026, so its step is no bigger than a normal one. Clipping is cheap insurance, and the fraction of steps clipped is worth logging: if it climbs towards 100%, the learning rate is too high or something upstream is wrong.

The race

Which optimiser is best depends on the surface, and the learning rate matters more than the choice. In the widget, all four optimisers start at the ring on the same surface and share one learning rate; adjust it and watch which survive. On the narrow valley, SGD with a rate that suits the steep direction crawls, and with a larger one explodes. On Rosenbrock's banana (a curved valley with minimum at (1, 1), standard in optimisation tests), plain methods inch along the floor. On the double well, which optimiser reaches which well depends on the small initial offset.

For a fairer comparison than one shared learning rate, the script below gives each optimiser its own best rate from a 14-value grid (10−4 to 0.5) and reports the loss after 300 steps. Both surfaces are the ones from the widget.

import numpy as np
from opts import SGD, RMSProp, Adam

def bowl(w):                       # narrow valley, curvature ratio 100
    return 0.5 * (w[0] ** 2 + 100 * w[1] ** 2), np.array([w[0], 100 * w[1]])

def rosen(w):                      # Rosenbrock: minimum 0 at (1, 1), a curved narrow valley
    x, y = w
    f = (1 - x) ** 2 + 100 * (y - x * x) ** 2
    return f, np.array([-2 * (1 - x) - 400 * x * (y - x * x), 200 * (y - x * x)])

SURF = {"bowl (kappa=100)": (bowl, np.array([-1.5, 1.0])), "Rosenbrock": (rosen, np.array([-1.2, 1.0]))}
MAKE = {
    "SGD":          lambda lr: SGD(lr),
    "momentum 0.9": lambda lr: SGD(lr, 0.9),
    "RMSProp":      lambda lr: RMSProp(lr),
    "Adam":         lambda lr: Adam(lr),
}
GRID = np.geomspace(1e-4, 0.5, 14)

def final_loss(f, w0, make, lr, steps=300):
    w, opt = w0.copy(), make(lr)
    for _ in range(steps):
        l, g = f(w)
        if not np.isfinite(l) or l > 1e8:
            return np.inf
        w = opt.step(w, g)
    return f(w)[0]

print("final loss after 300 steps, best learning rate from a grid of 14 values (1e-4 to 0.5):")
for name, (f, w0) in SURF.items():
    print(f"\n{name}   start loss {f(w0)[0]:.3f}")
    for oname, make in MAKE.items():
        best = min((final_loss(f, w0, make, lr), lr) for lr in GRID)
        print(f"  {oname:13s} lr {best[1]:.4f}  loss {best[0]:.2e}")

Read it with care. On the valley with tuned rates everything but RMSProp gets close to the minimum, with momentum and Adam far ahead of plain SGD. RMSProp with a fixed rate cannot settle: its step is about η in size whatever the gradient, so it hops around the minimum at a distance of order η (the same property as Adam, without momentum's smoothing). On Rosenbrock, momentum does best, plain SGD and RMSProp are still on the way after 300 steps, and Adam's best learning rate sits at the top of the grid (0.5), so its figure is probably not its best possible. This is a miniature, one start per surface, not evidence about which optimiser wins on neural networks. For those, large-scale experience, not test functions, is the guide.

What an optimiser costs in memory

An optimiser is state as well as an equation. SGD with momentum stores one extra number per weight (the velocity), Adam stores two (m and v). Together with the weights themselves and their gradients, that is the "static" part of training memory, before activations (chapter 9). With mixed precision (16-bit weights and gradients with 32-bit master weights, chapter 11), the accounting used in the ZeRO paper (Rajbhandari et al., 2020) comes to 16 bytes per parameter for Adam:

    "Adam, fp32":                      {"weights": 4, "gradients": 4, "m": 4, "v": 4},
    "Adam, mixed precision":           {"weights (bf16)": 2, "gradients (bf16)": 2, "master weights (fp32)": 4, "m (fp32)": 4, "v (fp32)": 4},
}
sizes = {"1B": 1e9, "7B": 7e9, "70B": 70e9}
print(f"{'optimiser':24s} {'bytes/param':>11} " + " ".join(f"{k:>8s}" for k in sizes))
for name, parts in layouts.items():
    b = sum(parts.values())
    print(f"{name:24s} {b:11d} " + " ".join(f"{b * n / 1e9:6.0f} GB" for n in sizes.values()))
optimiser                bytes/param       1B       7B      70B
SGD, fp32                          8      8 GB     56 GB    560 GB

A 7-billion-parameter model trained with Adam needs about 112 GB for weights, gradients and optimiser state alone: more than one 80 GB accelerator holds, before a single activation. This is the starting point of A3's memory chapter and of sharding methods that split the optimiser state across devices (A3, chapter 3). It is also why memory-lean optimisers keep appearing.

State of play, October 2026

Recipes I checked. The GPT-3 paper (Brown et al., 2020) trained with Adam (β1 = 0.9, β2 = 0.95, ε = 10−8), clipped the global gradient norm at 1.0, used cosine decay to 10% of the peak over 260 billion tokens, a linear warmup over the first 375 million tokens, and weight decay 0.1. The Llama 2 paper (Touvron et al., 2023) reports AdamW with β1 = 0.9, β2 = 0.95, ε = 10−5, a cosine schedule with 2,000 warmup steps decaying to 10% of the peak, weight decay 0.1 and clipping at 1.0. Note β2 = 0.95 rather than the original paper's 0.999: a shorter memory for v reacts faster to the changing gradient scale of language-model training.

Newer optimisers. AdamW remains the common default for large-model training. Alternatives that orthogonalise or otherwise precondition updates per weight matrix have been proposed; one, Muon, was reported by its authors (Liu et al., 2025, Muon is Scalable for LLM Training) to need roughly half the compute of AdamW in their scaling experiments and was used to train a 3B/16B-parameter mixture-of-experts model on 5.7 trillion tokens. These are the authors' own claims, which I read in the paper's abstract only; independent comparisons are still accumulating. Treat the field as moving and read the recipe, not the name, when you reproduce a result.

What goes wrong, and how to find out

  • Loss goes to nan or infinity. The step is too large for the curvature (r < −1 above), or a numerical problem (overflow in 16-bit, log of zero, chapter 11). Cut the learning rate by 3 to 10 times, add warmup and clipping, and check the first steps with a tiny batch.
  • Loss decreases painfully slowly. Learning rate too low, or an ill-conditioned problem (try momentum or Adam), or vanishing gradients (chapter 8), or a bug that freezes parameters (chapter 9: detached tensors, gradients never reaching a layer).
  • Loss oscillates without improving. Learning rate near the stability limit, or batches too small for the noise. Lower the rate, or decay it.
  • Sudden spikes mid-run. Common in large runs. Typical remedies: clipping, a lower peak rate, a smaller β2, a larger ε, skipping the offending batch, and restarting from an earlier checkpoint (A2 chapter 17; A3, chapter 5).
  • Training loss falls, validation loss does not. Not an optimisation failure: this is generalisation (A1, chapter 1).
  • Plateaus and saddles. Regions where the gradient is tiny (chapter 8) but you are not at a minimum. In high dimensions these are far more common than bad local minima, and momentum and noise help to leave them.

A debugging checklist

  1. Overfit one batch. Take 8 to 32 examples and train on them alone. The loss should go to nearly 0. If it does not, the model, loss or gradient flow is broken, and no tuning will help.
  2. Check the starting loss. For a classifier with K balanced classes the initial cross-entropy should be near ln K (2.30 for 10 classes). A very different value suggests a bug in the loss or labels.
  3. Sweep the learning rate by factors of about 3 (a "range test", Smith, 2017: raise it steadily over a short run and note where loss starts to fall and where it blows up). Pick a value a little below the edge of stability.
  4. Add warmup, then a decay schedule, then clipping, one at a time, and keep what helps.
  5. Log the gradient norm and the fraction of clipped steps. A norm that trends up or spikes is the earliest warning.

Systems connection

Gradient descent is a feedback loop: measure the error, apply a correction proportional to it. The learning rate is the gain, and the rule η < 2/λ is the familiar condition that a loop with too much gain overshoots by more each time and oscillates out of control. The same dynamic appears in autoscalers and retry loops that react too strongly, producing the self-sustaining overload described in Reliability, chapter 11. Warmup is the training equivalent of ramping traffic to a cold service, and clipping is a rate limiter on the update.

Key takeaways

  • The update is w ← w − η ∇L. On a quadratic with curvature λ each step multiplies the error by (1 − ηλ), so training is stable only for η < 2/λmax.
  • Ill-conditioning (a large ratio κ of largest to smallest curvature) forces a step size set by the steep direction, making progress in flat directions slow: plain descent needs roughly κ steps.
  • Minibatch gradients are unbiased with noise falling as 1/√B. Noise helps early and sets a floor late, so learning-rate decay and batch size are tuned together.
  • Momentum averages gradients to cancel oscillation and accelerate consistent directions. Adaptive methods divide by a running gradient scale per weight; Adam combines both, takes steps of about η per weight, and needs bias correction.
  • In Adam, L2 regularisation and weight decay differ. AdamW decays the weights directly, so the regularisation does not depend on gradient scale.
  • Real recipes combine warmup, cosine or WSD decay, global-norm clipping and weight decay. Adam stores two extra numbers per parameter, about 16 bytes per parameter in all with mixed precision.
  • When training misbehaves: overfit one batch, check the initial loss, sweep the learning rate, then add stabilisers one by one.

Check your understanding

The sharpest direction of a loss has curvature 40. About what is the largest learning rate for which plain gradient descent is stable?

  1. 0.5
  2. Just under 0.05
  3. 0.025
  4. There is no limit, because the gradient shrinks near the minimum
Each step multiplies the error along that direction by (1 − 40η), which stays inside (−1, 1) only for η < 2/40 = 0.05. The value 0.025 = 1/40 is the step that reaches the minimum in one go along that direction; it is stable but not the largest stable one. The gradient shrinking near the minimum does not help if the step overshoots: it overshoots by more each time.

You increase the minibatch size from 64 to 256, keeping everything else fixed. By what factor does the standard deviation of the minibatch gradient change?

  1. It falls by a factor of 4
  2. It does not change, because the estimate is unbiased
  3. It falls by a factor of 2
  4. It rises by a factor of 2, because there is more data to sum
The variance of an average of B independent draws is σ²/B, so the standard deviation is σ/√B: 4 times the batch means half the noise. Unbiasedness concerns the mean (which does not change), not the spread. The table in the chapter shows std × √B staying constant.

Adam with learning rate 10−3 takes its very first step on a weight whose gradient is 5,000. About how large is that step?

  1. About 10−3, because m̂/(√v̂ + ε) is about sign(g) at the first step
  2. About 5, because the step is proportional to the gradient
  3. About 0.1, because the first-step moment estimates are 10% of the gradient
  4. About 5 × 10−7, because Adam divides by the gradient size
After bias correction m̂ = g and v̂ = g² on step 1, so the update is η g/(|g| + ε) ≈ η sign(g), with magnitude about 10−3 regardless of the gradient's scale. Option 2 is plain SGD behaviour (with η = 10−3 it would be 5), and the 10% figure is the uncorrected m, which the bias correction undoes.

Which statement correctly distinguishes L2 regularisation from decoupled weight decay (AdamW) in Adam?

  1. They are mathematically identical for every optimiser
  2. AdamW regularises more strongly in total because it also changes the loss
  3. L2 acts only on biases, AdamW acts on all weights
  4. With L2 added to the gradient, the penalty is divided by √v̂, so weights with large gradients are decayed less; AdamW shrinks all weights by the same fraction
The two coincide for plain SGD, which is why the distinction is easy to miss. Inside Adam the L2 term joins the gradient and is rescaled per weight by the adaptive denominator, so the effective decay varies with gradient scale. AdamW applies ηλwdw after the adaptive step, so it does not. AdamW does not change the loss (option 1) and neither is restricted to biases.

A run diverges within the first 100 steps with Adam but is stable at one tenth of the learning rate. Which change is most likely to let you keep a high peak learning rate?

  1. Switching to a larger batch size only
  2. Adding a linear warmup so the learning rate ramps up while the moment estimates settle
  3. Removing weight decay
  4. Setting ε to zero
Early in training the weights are random and Adam's v̂ is estimated from very few gradients, so full-size steps are risky; warmup is the standard fix. A larger batch changes noise, not the early-step instability. Weight decay is not the cause of early divergence. Setting ε = 0 removes the guard against dividing by a tiny number and makes divergence more likely, not less.

You train a 7-billion-parameter model with mixed-precision Adam (16-bit weights and gradients, 32-bit master weights, m and v). About how much memory do weights, gradients and optimiser state take, before activations?

  1. About 14 GB, since the weights are 16-bit
  2. About 28 GB, two copies of the 16-bit weights
  3. About 112 GB, 16 bytes per parameter
  4. About 224 GB, 32 bytes per parameter
The accounting is 2 (weights) + 2 (gradients) + 4 (fp32 master copy) + 4 (m) + 4 (v) = 16 bytes per parameter, so 7×109 × 16 = 112 GB. Counting only the 16-bit weights gives 14 GB (option 0), which is the cost of serving, not training. This is more than a single 80 GB accelerator holds before any activations.

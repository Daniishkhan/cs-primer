Data Wrangling: pandas, SQL & Tidy Data

Before any model sees a number, someone has loaded a file, joined two tables, dropped the rows that made no sense and decided what a "row" even is. This chapter covers that work: the shape of a good table, the four operations (select, filter, group, join) that answer most questions, the ways each one quietly goes wrong, and the questions to put to any dataset before trusting it.

Why this matters

Models are rarely the weak link. A duplicated key doubles revenue, a sentinel value of -999 becomes a feature, a join keeps the future in a training set: each of these produces a model that scores well and fails in production. Every later course starts from tables: exploratory analysis and leakage in the machine-learning course, labelled examples for fine-tuning, and the test sets that error analysis slices by category. After this chapter you can load data with its types intact, answer questions in SQL and in pandas, predict how many rows a join should return, and run a short list of checks that catches the common faults before they reach a model.

What a table is, and what a row means

A table is a collection of rows that all have the same columns. Each column has one type (a number, a string, a date) and a name. If you know databases, this is the relational model; a pandas DataFrame is the same idea held in memory, with each column stored as a NumPy array (the arrays of the previous chapter).

The first question to ask of any table is deceptively simple: what does one row represent? One order? One customer? One customer per day? One click? A table that mixes levels (some rows are orders, some are customer summaries) cannot be averaged or counted safely, and a model trained on it learns the mixture. The second question follows: what is the key, the column or set of columns that identifies a row uniquely? Everything else in this chapter, joins especially, depends on knowing the answer and checking that it is true.

Tidy data

Hadley Wickham (2014, "Tidy Data", Journal of Statistical Software) gave a name to a layout that makes analysis easy. A table is tidy when:

  1. Each variable is a column. Month is a variable, so there should be a month column.
  2. Each observation is a row. One store in one month is one observation.
  3. Each type of observational unit is its own table. Stores (with their address) and monthly sales (with their amounts) are different units; keep them in separate tables linked by a key.

Spreadsheets tempt people to break the first rule by putting one month per column. That "wide" layout (as opposed to the "long" one below) is fine for reading and bad for computing, because the variable "month" is hiding in the headers. Converting to the "long" layout is often the first step of a real analysis:

# A "wide" table: one column per month. The month is data, hiding in the header.
wide = [
    {"store": "north", "jan": 120, "feb": 135, "mar": 150},
    {"store": "south", "jan": 90,  "feb": None, "mar": 110},
]

# tidy ("long"): one row per (store, month) observation
long = [
    {"store": r["store"], "month": m, "sales": r[m]}
    for r in wide for m in ("jan", "feb", "mar")
]
for row in long:
    print(row)

# in long form, questions become one-liners
total = {}
for row in long:
    if row["sales"] is not None:
        total[row["store"]] = total.get(row["store"], 0) + row["sales"]
print("total by store:", total)
print("rows:", len(long), "= stores x months = 2 x 3: one row per cell of the wide table")
{'store': 'north', 'month': 'jan', 'sales': 120}
{'store': 'north', 'month': 'feb', 'sales': 135}
{'store': 'north', 'month': 'mar', 'sales': 150}
{'store': 'south', 'month': 'jan', 'sales': 90}
{'store': 'south', 'month': 'feb', 'sales': None}
{'store': 'south', 'month': 'mar', 'sales': 110}
total by store: {'north': 405, 'south': 200}

Loading: where types go wrong

A CSV file is only text. Every number, date and missing-value marker in it is a string until some code decides otherwise, and a loader that guesses can guess wrongly. Four faults recur, and the standard library's csv module shows all of them without any help from a framework:

import csv
import io

text = """id,postcode,height_cm,joined
a,02134,170,2025-03-01
b,90210,N/A,2025-03-02
c,10001,-999,03/04/2025
"""
rows = list(csv.DictReader(io.StringIO(text)))
print("raw strings   :", rows[0])
print("int(postcode) :", int("02134"), " <- the leading zero is gone")
print("height values :", [r["height_cm"] for r in rows])
try:
    float("N/A")
except ValueError as e:
    print("float('N/A')  : ValueError:", e)
print("-999 parses fine as a number:", float("-999"), " <- a sentinel posing as data")
print("joined values :", [r["joined"] for r in rows], " <- two date formats; 03/04/2025 is 3 April or 4 March?")
raw strings   : {'id': 'a', 'postcode': '02134', 'height_cm': '170', 'joined': '2025-03-01'}
int(postcode) : 2134  <- the leading zero is gone
height values : ['170', 'N/A', '-999']
float('N/A')  : ValueError: could not convert string to float: 'N/A'
-999 parses fine as a number: -999.0  <- a sentinel posing as data
joined values : ['2025-03-01', '2025-03-02', '03/04/2025']  <- two date formats; 03/04/2025 is 3 April or 4 March?
  • Identifiers are not numbers. A postcode, phone number or product code with a leading zero must stay a string, because arithmetic on it is meaningless and conversion destroys information. Declare it (dtype={"postcode": "string"} in pandas) rather than trusting inference.
  • Missing values hide in many spellings. N/A, NA, null, an empty string and a dash all mean "unknown"; so does a number such as -999 or 9999. The last kind, a sentinel value, is the dangerous one, because it parses as a perfectly good number. Find sentinels by looking at the minimum, the maximum and the most common values of every numeric column.
  • Dates are ambiguous. 03/04/2025 is 3 April in most of the world and 4 March in the United States. Store dates in ISO 8601 form (2025-04-03), parse them explicitly with a stated format, and record the time zone for any timestamp.
  • Encodings and delimiters. A file saved by a spreadsheet may use a different text encoding or separator than you expect. State both when you read it.

A good habit is to load everything as strings first, count the distinct "unusual" values in each column, and then convert with explicit rules. It is slower than letting the library guess, and it is the step that finds the faults.

A small dataset to work with

The rest of the chapter uses one tiny, deliberately flawed dataset: seven users and twelve orders from an imaginary shop. It is loaded into an in-memory SQLite database, which ships with Python and runs the same SQL you would write for PostgreSQL or a warehouse (the sqlite3 tool card has more). The flaws are planted: a duplicated order row, a missing amount, an amount of -1, an order from a user who does not exist, and two users with no orders.

import csv
import io
import sqlite3

USERS_CSV = """user_id,country,signup,postcode
1,US,2025-01-05,02134
2,GB,2025-01-09,SW1A 1AA
3,US,2025-02-14,10001
4,DE,2025-02-20,10115
5,GB,2025-03-01,EC1A 1BB
6,US,2025-03-11,
7,DE,2025-03-15,80331
"""

ORDERS_CSV = """order_id,user_id,amount,status,created
100,1,25.00,paid,2025-02-01
101,1,40.00,paid,2025-03-05
102,2,15.50,paid,2025-02-11
103,3,99.00,refunded,2025-03-02
104,3,12.00,paid,2025-03-20
105,4,-1,paid,2025-03-22
106,4,30.00,paid,2025-03-25
106,4,30.00,paid,2025-03-25
107,5,,paid,2025-03-28
108,9,18.00,paid,2025-03-30
109,2,22.50,paid,2025-04-02
110,1,60.00,paid,2025-04-10
"""


def load():
    """Build an in-memory SQLite database from the two CSV texts."""
    db = sqlite3.connect(":memory:")
    db.execute("CREATE TABLE users (user_id INTEGER, country TEXT, signup TEXT, postcode TEXT)")
    db.execute("CREATE TABLE orders (order_id INTEGER, user_id INTEGER, amount REAL, status TEXT, created TEXT)")
    for row in csv.DictReader(io.StringIO(USERS_CSV)):
        db.execute("INSERT INTO users VALUES (?,?,?,?)",
                   (int(row["user_id"]), row["country"], row["signup"], row["postcode"] or None))
    for row in csv.DictReader(io.StringIO(ORDERS_CSV)):
        amount = float(row["amount"]) if row["amount"] != "" else None
        db.execute("INSERT INTO orders VALUES (?,?,?,?,?)",
                   (int(row["order_id"]), int(row["user_id"]), amount, row["status"], row["created"]))
    return db

Four questions, one pipeline: SQL in its logical order

Almost every analytical question reduces to four moves: select the columns you need, filter the rows you want, group rows and summarise each group, and join tables on a key. SQL writes them in a fixed grammar, but it does not run them in the order they are written. The logical order is the one worth memorising, because it explains most surprises.

Interrogate before you trust

Start with questions about the table itself, before any analysis. Each line of the script below is a check you should be able to write in any tool:

from shop_data import load

db = load()

print("rows in users, orders :", q("SELECT (SELECT COUNT(*) FROM users), (SELECT COUNT(*) FROM orders)")[0])

print("suspicious amounts    :", q("SELECT order_id, amount FROM orders WHERE amount <= 0 OR amount IS NULL"))

Read what the data says about itself. Twelve rows but only eleven distinct order ids: a duplicate. COUNT(*) is 12 and COUNT(amount) is 11: one amount is missing, because COUNT(column) skips NULLs. Order 105 has an amount of -1, a sentinel. Order 108 belongs to user 9, who is not in the users table (an orphan row, a broken reference). Users 6 and 7 never ordered. And NULL, SQL's marker for an unknown value, does not behave like a value: NULL = NULL is not true but unknown (shown here as None), so you must test with IS NULL; AVG divides by the 11 non-null amounts, not by 12, so the average silently excludes the very rows that are missing.

Analogy: a guest list and a seating plan

A join is matching two lists by name: the guest list (users) and the table assignments (orders). If every name appears once in each, the combined list has one line per guest. If a guest is listed twice on one sheet, they appear twice in the result. If someone appears on the seating plan but not on the guest list, an inner join discards them without comment, while a left join keeps them with blank fields.

Where it breaks down: real names are not unique and are typed inconsistently ("J. Smith", "John Smith"). Joins in data work depend on keys that someone has made unique and consistent, and a good part of wrangling is making that true.

Joins: count the rows you expect

A join combines rows from two tables where a key matches. An inner join keeps only matches. A left join keeps every row of the left table and fills the right-hand columns with NULL where there is no match. The row count is the first diagnostic. Before running a join, predict the result size; afterwards, compare.

from shop_data import load

db = load()
q = lambda sql: db.execute(sql).fetchall()

clean = """(SELECT DISTINCT order_id, user_id, amount, status, created
            FROM orders WHERE amount > 0 AND status = 'paid')"""

print("orders (raw)          :", q("SELECT COUNT(*) FROM orders")[0][0])
print("orders in clean       :", q(f"SELECT COUNT(*) FROM {clean}")[0][0])
print("INNER JOIN rows       :", q(f"SELECT COUNT(*) FROM {clean} o JOIN users u USING (user_id)")[0][0])
print("LEFT JOIN rows        :", q(f"SELECT COUNT(*) FROM {clean} o LEFT JOIN users u USING (user_id)")[0][0])
print("users LEFT JOIN orders:", q(f"SELECT COUNT(*) FROM users u LEFT JOIN {clean} o USING (user_id)")[0][0])

print("revenue by country (inner join):")
for row in q(f"""SELECT u.country, COUNT(*) AS n_orders, ROUND(SUM(o.amount), 2) AS revenue
                 FROM {clean} o JOIN users u USING (user_id)
                 GROUP BY u.country ORDER BY revenue DESC"""):
    print("  ", row)

# a second table with several rows per user: campaign touches
db.execute("CREATE TABLE touches (user_id INTEGER, channel TEXT)")
db.executemany("INSERT INTO touches VALUES (?, ?)",
               [(1, "email"), (1, "ads"), (1, "sms"), (2, "email"), (3, "ads")])

joined = q(f"""SELECT ROUND(SUM(o.amount), 2), COUNT(*) FROM {clean} o
               JOIN touches t USING (user_id)""")[0]

print("after joining touches :", joined, "<- revenue and rows both inflated")

safe = q(f"""SELECT ROUND(SUM(o.amount), 2) FROM {clean} o
             JOIN (SELECT user_id, COUNT(*) AS n_touches FROM touches GROUP BY user_id) t
             USING (user_id)""")[0][0]
print("aggregate first, join :", safe, "(only users that have touches)")

Follow the counts. After removing the duplicate and the unusable amounts and refunds, 8 clean orders remain. An inner join to users returns 7, because order 108 has no user and is discarded: the join has quietly dropped data. A left join returns all 8, with a NULL country on the orphan, so the problem is visible instead of hidden. Reversing the direction, users left-joined to orders gives 10 rows: 6 users with orders produce one row per order, and users 6 and 7 appear once each with NULLs. The size of a join is determined by the key relationships (one-to-one, many-to-one, many-to-many), and a mismatch between what you expected and what you got always means something about the data.

Fan-out: when a join multiplies rows

The most expensive mistake in this chapter is fan-out: joining on a key that is not unique in the table you thought it was. Suppose you add a table of marketing touches with several rows per user and join it to orders to see revenue by channel. User 1 has three orders and three touches, so the join produces 3 × 3 = 9 rows for that user, and every order is counted three times.

Common misconception

"Joining adds columns; it cannot change my row count (or my totals)." A left join preserves the left table's rows only when the right table is unique on the key. If it is not, each left row is repeated once per match, and any sum over the result is inflated. A join that unexpectedly shrinks the data (an inner join with unmatched keys) is the opposite failure. In both cases the guard is the same: know the cardinality you expect (one_to_one, many_to_one) and test it. pandas offers this directly as the validate= argument of merge; in SQL, compare COUNT(*) before and after.

Windows and "as of" features

Two techniques account for much of feature building. A window function computes a value over a related set of rows without collapsing them: ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created DESC) numbers each user's orders from newest, so keeping number 1 gives the latest order per user. The second technique concerns time. A model that predicts on a given date may only use what was known before it, so features must be computed "as of" a cutoff, with a strict date filter:

from shop_data import load

db = load()
q = lambda sql: db.execute(sql).fetchall()

# latest paid order per user, using a window function
print("latest paid order per user:")
for row in q("""SELECT user_id, order_id, amount, created FROM (
                  SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created DESC) AS rn
                  FROM (SELECT DISTINCT * FROM orders WHERE amount > 0 AND status = 'paid'))
                WHERE rn = 1 ORDER BY user_id"""):
    print("  ", row)

# a feature for predicting on 2025-03-15: only use what was known BEFORE that date
cutoff = "2025-03-15"
print(f"spend before {cutoff}  :")
for row in q(f"""SELECT u.user_id, COALESCE(SUM(o.amount), 0) AS spend_before
                 FROM users u LEFT JOIN
                   (SELECT DISTINCT * FROM orders WHERE amount > 0 AND status = 'paid'
                      AND created < '{cutoff}') o USING (user_id)
                 GROUP BY u.user_id ORDER BY u.user_id"""):
    print("  ", row)
leaky = q("SELECT ROUND(SUM(amount), 2) FROM (SELECT DISTINCT * FROM orders WHERE amount > 0 AND status='paid' AND user_id = 1)")[0][0]
print("user 1 lifetime spend (leaks the future if used at the cutoff):", leaky)

For the cutoff 15 March 2025, user 1's feature is 65.00 (the orders of 1 February and 5 March), while a careless "lifetime spend" of 125.00 would include April orders that, at prediction time, had not happened. A model trained on the second number is peeking at the future, and its offline accuracy will not survive deployment. This is the mechanism behind leakage, which that chapter treats fully, and the reason pipelines record a timestamp for every event. Users 3 to 7 get zero because they had no earlier paid orders; whether "no history" should be 0 or NULL is a modelling decision to make deliberately (it matters to a tree or a linear model).

The same work in pandas

pandas expresses the same operations as methods on a DataFrame. The listing below does the cleaning, the join and the grouped summary from the SQL above, and the melt and pivot from the tidy-data section. pandas is not installed in the environment used to produce this course's outputs, so this listing was not run here and has no output block; the results it would produce are the same numbers as the SQL: three countries, with US 4 orders and 137.0 revenue, GB 2 orders and 38.0, and DE 1 order and 30.0.

import pandas as pd

users = pd.read_csv("users.csv", dtype={"postcode": "string"}, parse_dates=["signup"])
orders = pd.read_csv("orders.csv", parse_dates=["created"])

orders = orders.drop_duplicates()                                  # order 106 now appears once
clean = orders[(orders["amount"] > 0) & (orders["status"] == "paid")]   # NaN > 0 is False, so 107 drops too

merged = clean.merge(users, on="user_id", how="inner", validate="many_to_one")
revenue = (merged.groupby("country")
                 .agg(n_orders=("order_id", "count"), revenue=("amount", "sum"))
                 .sort_values("revenue", ascending=False))
print(revenue)

wide = pd.DataFrame({"store": ["north", "south"], "jan": [120, 90], "feb": [135, None], "mar": [150, 110]})
long = wide.melt(id_vars="store", var_name="month", value_name="sales")   # wide -> tidy
back = long.pivot(index="store", columns="month", values="sales")        # tidy -> wide

The mapping between the two notations is worth learning once. WHERE is boolean indexing (df[mask]); JOIN is merge; GROUP BY ... SUM is groupby(...).agg(...); window functions are groupby(...).transform and rank; CASE WHEN is np.where. pandas wins when the data fits in memory and you are exploring interactively, because you can look at each intermediate step. SQL wins when the data lives in a database or warehouse and when you want the query to be portable, reviewable and optimised by a planner. Strong practitioners use both, and increasingly an in-process engine such as DuckDB that reads CSV and Parquet files with SQL (see Column Stores & Analytics and the DuckDB tool card).

State of play, October 2026

pandas 3.0 was released on 21 January 2026. According to its release notes, two defaults changed: strings now use a dedicated str dtype (backed by PyArrow when installed) instead of generic object, and copy-on-write semantics became the default, so an indexing result always behaves as a copy and the old chained-assignment idiom (df[mask]["col"] = 0) no longer modifies the original. The pandas team advises upgrading to 2.3 first and fixing warnings. Code and tutorials from before 2026 may assume the old behaviour, so check the version you pin (chapter 4). Polars and DuckDB are widely used alternatives for larger-than-comfortable tables. Verify current versions and defaults against the pandas documentation before relying on any detail here.

Cleaning decisions, and the questions to ask any dataset

Cleaning is a series of decisions, and each should be written down, not made silently. For every fault you find, you choose among a few responses: fix it if the correct value is knowable (a unit conversion, a known typo); drop the row if it is unusable and rare (but count how many, and check the dropped rows are not systematically one kind, since that biases the result); flag it with an extra column, such as amount_missing, so a model or analyst can use the fact; or keep it and handle it downstream. Order 107's missing amount, order 105's -1 and the duplicate row each deserve a line in a log that says what was done and why. Deleting a row because a plot looked odd is how analyses become irreproducible; the first case study of this course, A Spreadsheet Error That Shaped Policy, shows what a hidden cleaning step can cost.

Beyond the mechanics are questions about the data's origin, which no code can answer. Put these to every dataset, and write the answers in the project's README or design doc:

QuestionWhat it protects you from
What does one row represent, and what is the key?Double counting; mixing levels; broken joins.
Who or what produced this data, and who is missing from it?Selection bias: a model trained on users who completed a form says little about those who abandoned it.
When was each field recorded, and when would it be known at prediction time?Leakage from fields filled in after the outcome.
What are the units, types and valid ranges of each column?Sentinels, mixed currencies, kilometres versus miles.
What is missing, how is it encoded, and is it missing at random?Biased averages; models that learn "missing" as a signal.
Where do labels come from, and how noisy are they?An accuracy ceiling set by label error, not by the model.
Are there duplicates or near-duplicates, within and across splits?Inflated test scores when the same item is in train and test.
Does this sample resemble what the system will see in use?Distribution shift between development and deployment.
What am I allowed to do with it?Privacy and licence problems (see Privacy & Data Handling for AI).

Sambasivan and colleagues (CHI 2021) interviewed practitioners in high-stakes domains and named the result of neglecting such questions data cascades: data problems that compound silently through a pipeline and surface late, often as a failure in production. The paper reports how widespread cascades were among the practitioners it interviewed (read it for the figures); the lesson is to spend the first hours of a project on the data, not the model.

Turn the questions into checks

Anything you can state as an invariant, you can test automatically, and a test that runs on every load is worth more than a note. The script below runs six checks against the orders table. It is exactly the shape of a data-validation step in a production pipeline, and the same checks, expressed in a framework of your choice, catch the daily surprises when the data changes:

from shop_data import load


def check_orders(db):
    """Return a list of (check name, number of offending rows)."""
    one = lambda sql: db.execute(sql).fetchone()[0]
    return [
        ("order_id is unique",           one("SELECT COUNT(*) - COUNT(DISTINCT order_id) FROM orders")),
        ("amount is never NULL",         one("SELECT COUNT(*) FROM orders WHERE amount IS NULL")),
        ("amount is positive",           one("SELECT COUNT(*) FROM orders WHERE amount <= 0")),
        ("every order has a known user", one("""SELECT COUNT(*) FROM orders
                                               WHERE user_id NOT IN (SELECT user_id FROM users)""")),
        ("status is a known value",      one("SELECT COUNT(*) FROM orders WHERE status NOT IN ('paid','refunded')")),
        ("dates are ISO 8601",           one("SELECT COUNT(*) FROM orders WHERE created NOT GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'")),
    ]


db = load()
failed = 0
for name, bad in check_orders(db):
    print(("PASS" if bad == 0 else "FAIL"), f"{name:30} offending rows: {bad}")
    failed += bad > 0
print(f"{failed} of 6 checks failed")
FAIL order_id is unique             offending rows: 1
FAIL amount is never NULL           offending rows: 1
FAIL amount is positive             offending rows: 1
FAIL every order has a known user   offending rows: 1
PASS status is a known value        offending rows: 0
PASS dates are ISO 8601             offending rows: 0
4 of 6 checks failed

Four of six fail, each by exactly one row: the duplicate, the NULL amount, the non-positive amount and the orphan. Run on the first day, this report is a to-do list; run every day after, it is an alarm. Note what the checks do not cover. They cannot tell you that every amount is in dollars when last week's were in cents, or that the collection process changed. Distribution checks (compare means and category frequencies against a reference window) catch some of that, and so does a human reading a sample of raw rows, which is always worth doing.

Systems connection

Everything here is database practice in miniature. A key is a primary key and an orphan is a violated foreign key; a join's cost depends on indexes and on the planner's choice of algorithm; analytics over wide tables favour column stores; and a validation step in a pipeline is the same idea as the schema evolution and contract checks in Encoding & Schema Evolution. Key takeaways

  • Know what one row means and what the key is. Tidy data has one variable per column, one observation per row and one table per kind of unit; wide-to-long reshaping (melt) is routinely the first step.
  • CSV is text. Declare types, keep identifiers as strings, hunt for sentinels like -999, and store dates in ISO 8601.
  • SQL runs FROM and JOIN, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT in that logical order. pandas offers the same moves as methods.
  • Predict a join's row count before running it. A non-unique key multiplies rows and inflates sums; an inner join silently drops unmatched rows. Assert cardinalities.
  • NULL is not a value: NULL = NULL is unknown, and aggregates skip NULLs, so averages exclude exactly the rows that are missing.
  • Compute features "as of" the prediction time. Using the future is leakage, however innocent the column name.
  • Write cleaning decisions down, and turn invariants into automatic checks that run on every load.

Check your understanding

You left-join a table of 1,000 orders to a table of marketing touches and the result has 2,600 rows. Which is the most likely cause?

  1. Left joins always add rows from the right table that had no match.
  2. The touches table has several rows per join key, so each order is repeated once per matching touch.
  3. The orders table contained NULL keys, which are duplicated by the join.
  4. SQL adds a row for each column of the right table.
A left join keeps every left row and repeats it once per match, so a non-unique right-hand key multiplies rows. Unmatched right rows are not added by a left join (that would be a full outer join), and NULL keys never match anything.

A column holds 12 rows, one of them NULL. What do COUNT(*), COUNT(col) and AVG(col) use?

  1. 12, 12, and a sum divided by 12
  2. 11, 11, and a sum divided by 12
  3. 12, 12, and the NULL treated as 0
  4. 12, 11, and a sum divided by 11
COUNT(*) counts rows; COUNT(col) and AVG skip NULLs. Treating NULL as zero would be a deliberate choice (COALESCE), not the default, and it changes the average.

You compute "total spend per customer" over all history and use it as a feature to predict whether a customer buys in March. Offline accuracy is excellent; in production it collapses. What is the most likely reason?

  1. The feature included purchases made during and after March, which are unknown at prediction time, so the model was using the future.
  2. SQL window functions are not reproducible.
  3. The customers table was in third normal form.
  4. The model was too small for the data.
Aggregates must be computed as of the prediction time. A lifetime total includes the outcome itself, a form of leakage. Model size and schema normal form do not cause an offline-versus-online gap of this kind.

A CSV column of postcodes is loaded and the value 02134 becomes 2134. What is the best fix?

  1. Pad the numbers back to five digits after loading, on every use.
  2. Convert the column to float for consistency.
  3. Declare the column as a string when loading, since an identifier is not a quantity.
  4. Drop the column, because it is not numeric.
Identifiers should never be inferred as numbers: they have no arithmetic meaning and conversion loses information. Padding later patches the symptom and fails for codes of other lengths; float makes it worse; dropping loses a possibly useful field.

You want only the countries whose total revenue exceeds 100. Where does the condition on the sum go?

  1. In WHERE, because it filters rows.
  2. In HAVING, because the sum exists only after grouping.
  3. In ORDER BY, which filters while sorting.
  4. In SELECT, which discards rows that do not match.
WHERE runs before grouping, on individual rows, where the group sum is not yet defined. HAVING filters groups after aggregation. ORDER BY and SELECT do not remove rows.

A numeric column has minimum -999 and 4% of its values equal -999, and the rest are between 18 and 90. What should you do first?

  1. Leave it: the mean will average out the outliers.
  2. Standardise the column so the scale no longer matters.
  3. Delete the column.
  4. Treat -999 as a probable missing-value code: confirm with the data's owner or documentation, then convert it to a proper missing value and decide how to handle it.
A single repeated extreme value is the signature of a sentinel. Averaging or standardising it spreads the damage into every statistic. Deleting the column discards 96% good data; confirm the meaning and then handle the missingness explicitly.

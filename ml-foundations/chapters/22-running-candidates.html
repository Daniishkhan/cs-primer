Running Many Candidates Safely

A program that improves programs by trial runs thousands of pieces of code that nobody has read. Some will crash, some will never stop, and some will eat all the memory. This chapter shows how to run each one behind a wall and how to run many at once. It also covers repeatable randomness, a cache so you never pay twice for the same program, and a log you can replay.

Why this matters

The previous chapter, Programs as Data, showed how to read, change and run code as a value. Running code you did not write is where things go wrong. One infinite loop freezes a search for a night. One crash kills a run that has taken hours. One unseeded random number makes a good result impossible to repeat. After this chapter you can write a small evaluator that survives all three, and that is the engine room of the evolution engine lab. The process tools here are taught again, in a security setting, in Sandboxes & Permissions and Safety of Self-Modifying Systems. Both later pages link back to this one.

A search loop is a factory

Picture a loop that improves a program. It takes a program, changes it a little, and scores the new version. It keeps the better ones and repeats. Each new version is a candidate: a piece of code whose quality we do not yet know. A real run makes thousands of them. Often a language model writes them, so a person has read none of them.

That makes the loop a factory with an inspection line. Candidates arrive in bulk. Each must be tested, and the test must never hurt the factory. Three things go wrong in practice.

FailureWhat it looks likeWhat catches it
CrashAn exception, such as dividing by zero or calling a name that does not exist.A process boundary and an exit code, or try/except in the parent.
HangA loop that never ends, or a call that waits for something that never arrives.A timeout: a limit on how long the parent waits before it gives up and kills the child.
Resource bombMemory that grows until the machine swaps, or a file that grows until the disk is full.Operating-system resource limits: caps on CPU time, memory and file size, enforced by the kernel.

There is one rule that ties these together: every outcome becomes a score. The search must never receive an exception, a freeze or a missing value. It receives a number. A candidate that crashes gets the worst score the problem allows. A candidate that hangs gets the same. The selection step then discards both without a single special case. The loop stays simple because the evaluator is total: every input maps to an output.

Analogy: the exam hall

Think of an exam hall. Each candidate gets a separate desk, so one person's mess cannot spill onto another's paper. There is a clock on the wall, and when it runs out, the invigilator takes the paper whatever state it is in. Whatever happens, every candidate leaves with a mark, even if that mark is zero. That is the design here: a desk (a process), a clock (a timeout) and a mark for everyone (a score).

Where it breaks down: an exam candidate wants to pass and obeys the rules. A broken program does not know it is being watched, and it cannot be reasoned with. Also, the desks share one building. The processes share one operating-system kernel, so a program that is actively hostile can sometimes reach out of its desk. We are guarding against accidents, not against an attacker.

A process as a wall

A process is a running program with its own private memory, managed by the operating system. If a process crashes, the operating system cleans it up and no other process notices. That is the wall we want. If you run a candidate inside your own process with exec, an infinite loop freezes you, and sys.exit() inside the candidate ends your program. For the underlying mechanics, see Processes.

Python's subprocess.run starts a new Python interpreter as a child. We pass the candidate in as text and ask for a JSON answer on standard output. capture_output=True collects what the child prints. timeout=2.0 sets the clock. The flag -I starts Python in isolated mode, which ignores environment variables and the user's own packages, so the child behaves the same on every machine.

The idea

  1. run(code): start a child interpreter with a 2 s clock; never raise
  2. if the clock ran out: "timeout"; if exit code is not 0: "crash"
  3. else parse stdout as JSON; unparseable output is "bad output"
  4. run five snippets and print one row each: outcome, seconds, detail
"""Run five untrusted snippets, each in its own child process."""
import json
import subprocess
import sys
import time

WALL_SECONDS = 2.0  # real (clock) time a child may take

SNIPPETS = {
    "fine": "import json\nprint(json.dumps({'score': 42}))",
    "crash": "print(1 / 0)",
    "spin": "while True:\n    pass",
    "sleep": "import time\ntime.sleep(60)",
    "garbage": "print('not json at all')",
}


# ── 1. Run one snippet, never raise ─────────────────────────────────────
def run(code):
    """Return (outcome, detail). Every path returns; nothing escapes."""
    try:
        done = subprocess.run(
            [sys.executable, "-I", "-c", code],
            capture_output=True,
            text=True,
            timeout=WALL_SECONDS,
        )
    except subprocess.TimeoutExpired:
        return "timeout", f"no answer in {WALL_SECONDS}s"
    if done.returncode != 0:
        last = done.stderr.strip().splitlines()[-1]
        return "crash", last
    # ── 2. Parse the answer; a bad answer is an outcome too ─────────────
    try:
        return "ok", json.loads(done.stdout)["score"]
    except (ValueError, KeyError):
        return "bad output", done.stdout.strip()


# ── 3. Table of outcomes ────────────────────────────────────────────────
for name, code in SNIPPETS.items():
    start = time.perf_counter()
    outcome, detail = run(code)
    took = time.perf_counter() - start
    print(f"{name:8s} {outcome:11s} {took:4.1f}s  {detail}")
fine     ok           0.0s  42
crash    crash        0.0s  ZeroDivisionError: division by zero
spin     timeout      2.0s  no answer in 2.0s
sleep    timeout      2.0s  no answer in 2.0s
garbage  bad output   0.0s  not json at all

Read the table row by row. The healthy snippet returns 42. The crash comes back as an exit code that is not zero, and the last line of the error text names the exception. The two bad loops both take exactly two seconds, because that is when the clock ends them. The last row shows a third kind of failure: the child ran fine and printed nonsense. The parent treats that as an outcome too.

What a timeout actually kills

When the clock runs out, subprocess.run kills the child and waits for it to be gone, then raises TimeoutExpired. That is a hard kill. The child gets no chance to tidy up. It kills only the child, though. If the candidate itself started other processes, those carry on. The standard fix on Linux and macOS is to start the child in its own process group with start_new_session=True and, on timeout, kill the whole group with os.killpg. For code that must not start anything, give it no way to: the stronger sandboxes in Sandboxes & Permissions do this.

Common misconception

"I can run the candidate in a thread and put a timeout on the thread." A thread shares memory with the rest of your program. Python has no way to stop a thread from outside. A timeout on thread.join or future.result only stops you waiting. The runaway loop keeps spinning inside your process and keeps using a CPU core. Only a separate process can be killed from outside, which is why the wall is a process.

Resource limits: the kernel as the second guard

A wall-clock timeout measures real time. A CPU-time limit measures how long the processor actually worked for the child. The two catch different things. A busy loop is stopped by either. A candidate that sleeps for a minute uses almost no CPU, so only the wall clock catches it. A candidate that waits on the network is the same. You want both guards.

Python's resource module sets limits that the kernel enforces. RLIMIT_CPU caps CPU seconds: when it is reached, the kernel sends the signal SIGXCPU. A signal is a small message from the kernel to a process, and by default this one ends it. RLIMIT_AS caps the size of the address space, which is roughly the memory a process can ask for. Limits must be set inside the child, before the candidate starts. The classic way is the preexec_fn argument: a function the child runs after it is created and before it loads the program.

The idea

  1. apply_limits(): CPU cap 1 s; on Linux also a 200 MiB memory cap
  2. run(code): same as before, but pass preexec_fn=apply_limits
  3. a negative exit code means the kernel killed the child with a signal
  4. try a busy loop, a sleeper and a 1 GB allocation
"""Add operating-system limits to a child, then see which ones hold."""
import resource
import subprocess
import sys

WALL_SECONDS = 3.0
CPU_SECONDS = 1  # the kernel stops the child after this much CPU time
MEMORY_BYTES = 200 * 1024 * 1024  # address-space cap: 200 MiB

SNIPPETS = {
    "spin": "while True:\n    pass",
    "sleep": "import time\ntime.sleep(60)",
    "memory": "blob = bytearray(1_000_000_000)\nprint(len(blob))",
}


# ── 1. Limits, applied in the child before the candidate starts ─────────
def apply_limits():
    cpu = (CPU_SECONDS, CPU_SECONDS)
    resource.setrlimit(resource.RLIMIT_CPU, cpu)
    if sys.platform.startswith("linux"):
        # macOS refuses to set this limit, so only Linux gets it
        mem = (MEMORY_BYTES, MEMORY_BYTES)
        resource.setrlimit(resource.RLIMIT_AS, mem)


# ── 2. Run a snippet under those limits ─────────────────────────────────
def run(code):
    try:
        done = subprocess.run(
            [sys.executable, "-I", "-c", code],
            capture_output=True,
            text=True,
            timeout=WALL_SECONDS,
            preexec_fn=apply_limits,
        )
    except subprocess.TimeoutExpired:
        return "wall-clock timeout"
    if done.returncode < 0:
        return f"killed by signal {-done.returncode}"
    if done.returncode > 0:
        return "crashed: " + done.stderr.strip().splitlines()[-1]
    return "finished: " + done.stdout.strip()


# ── 3. One line per snippet ─────────────────────────────────────────────
for name, code in SNIPPETS.items():
    print(f"{name:7s} {run(code)}")
spin    killed by signal 24
sleep   wall-clock timeout
memory  finished: 1000000000

The busy loop was ended by signal 24 after one CPU second. A negative exit code -N in Python means "ended by signal N". The sleeper used no CPU, so only the three-second wall clock stopped it. The third row is the surprise. The memory bomb finished, because this run was on macOS and the script does not set a memory cap there.

Which limits work where

I checked on the macOS machine used to write this chapter (Python 3.14). RLIMIT_CPU works. Asking for RLIMIT_AS raised ValueError: current limit exceeds maximum limit, so memory caps through setrlimit are not available there. On Linux, RLIMIT_AS is enforced: the kernel refuses the allocation and the child gets a MemoryError. I did not run Linux for this chapter, so treat that line as the documented behaviour, not my measurement. On Windows there is no resource module and no preexec_fn. There you rely on the wall-clock timeout, or on job objects through other libraries. Whatever the platform, the wall clock is the one guard that works everywhere. Note also that RLIMIT_AS counts address space, not memory in use, so set it generously: Python itself reserves a lot.

The Python documentation warns that preexec_fn is not safe if your program uses threads, because the child can deadlock in the short gap before it starts. We will use threads in the final script, so that script avoids preexec_fn and has the child set its own limits as its first act. That works the same way and also runs on every platform.

Last, be honest about what this wall is. Limits stop runaway loops and bombs. They do not stop a candidate from reading your files or opening a network connection. For those you need containers or a virtual machine; see Containers & Virtual Machines and Injection & Untrusted Input. The fuel budgets from the previous chapter are a third layer, inside the interpreter, and they are cheap. Use all of them that you can afford.

Many at once

One candidate at a time wastes the machine. A modern laptop has several cores, and candidates do not depend on each other, so we can score several in parallel. Python offers two kinds of pool in concurrent.futures. A worker pool is a fixed set of workers that take jobs from a queue; see Queues, Thread Pools & Backpressure. ThreadPoolExecutor uses threads, and ProcessPoolExecutor uses processes.

The choice matters because of the global interpreter lock (GIL): in standard CPython, only one thread runs Python bytecode at any moment, so threads cannot speed up a CPU-bound task. Threads covers the general idea. Processes each have their own interpreter and their own lock, so they do run in parallel. The script below scores the same sixteen tasks four ways. Each task packs 4,000 items with best fit, so each one is CPU-bound.

The idea

  1. fitness(seed): pack 4,000 random items by best fit; return bins used
  2. timed(): run 16 tasks through an executor with N workers; time it
  3. time a plain loop first, then 1, 2 and 4 processes, then 4 threads
"""Time a CPU-bound fitness with a plain loop, process pools and threads."""
import random
import time
from concurrent.futures import ProcessPoolExecutor
from concurrent.futures import ThreadPoolExecutor

CAPACITY = 100
ITEMS = 4000  # items per instance: enough work to time
TASKS = 16  # one task = one candidate scored on one instance

SETUPS = [
    ("processes x1", ProcessPoolExecutor, 1),
    ("processes x2", ProcessPoolExecutor, 2),
    ("processes x4", ProcessPoolExecutor, 4),
    ("threads x4", ThreadPoolExecutor, 4),
]


# ── 1. A CPU-bound fitness: best-fit packing, bins used ─────────────────
def fitness(seed):
    rng = random.Random(seed)
    free = []  # free space left in each open bin
    for _ in range(ITEMS):
        item = rng.randint(20, 60)
        best = -1
        for i, rem in enumerate(free):
            if rem >= item and (best < 0 or rem < free[best]):
                best = i
        if best < 0:
            free.append(CAPACITY - item)
        else:
            free[best] -= item
    return len(free)


# ── 2. Same work, different executors ───────────────────────────────────
def timed(executor_cls, workers):
    start = time.perf_counter()
    with executor_cls(max_workers=workers) as pool:
        bins = sum(pool.map(fitness, range(TASKS)))
    return time.perf_counter() - start, bins


# ── 3. Report; the guard stops spawned workers re-running this block ────
if __name__ == "__main__":
    start = time.perf_counter()
    total = sum(fitness(s) for s in range(TASKS))
    base = time.perf_counter() - start
    print(f"{'plain loop':13s} {base:5.2f}s  bins {total}")
    for label, cls, workers in SETUPS:
        took, bins = timed(cls, workers)
        print(f"{label:13s} {took:5.2f}s  bins {bins}"
              f"  speed-up {base / took:4.2f}x")
plain loop     1.02s  bins 27571
processes x1   0.82s  bins 27571  speed-up 1.25x
processes x2   0.44s  bins 27571  speed-up 2.33x
processes x4   0.34s  bins 27571  speed-up 2.97x
threads x4     0.81s  bins 27571  speed-up 1.26x

Every row packs the same instances, so all rows report 27,571 bins. That check matters: a parallel version must give the same answers as the serial one. The timings are from one laptop and will differ on yours, and even between two runs on mine. Three things are worth reading from them. Four threads did no better than the plain loop, as the GIL predicts. Four processes were clearly faster, but not four times faster: starting a worker costs time, sending the work across costs time, and the machine is not idle. One process was no faster than the plain loop, because it adds cost and no parallelism. os.cpu_count() reports your core count.

Note the if __name__ == "__main__": guard. On macOS and Windows, each worker starts as a fresh interpreter that imports your file. Without the guard, every worker would run the pool-creating code again. Python 3.14 moved the Linux default away from fork as well, so code that worked by accident on older Linux may need the guard now.

A hung worker poisons a pool

Pools make parallel runs easy and make timeouts hard. Look at what future.result(timeout=...) does when the task never ends. A future is a placeholder for a result that a worker will produce later. result(timeout=0.5) raises an error after half a second. It does not stop the worker.

The idea

  1. submit stuck(), which sleeps 4 s, to a pool with one worker
  2. result(timeout=0.5) raises; check running() and cancel()
  3. submit quick(); see how long its answer takes
"""A timeout on result() stops the waiting, not the worker."""
import time
from concurrent.futures import ProcessPoolExecutor
from concurrent.futures import TimeoutError as FutureTimeout

WAIT_SECONDS = 0.5  # how long we are willing to wait for an answer
STUCK_SECONDS = 4.0  # how long the "hung" candidate really runs


def stuck():
    time.sleep(STUCK_SECONDS)
    return "finally done"


def quick():
    return "quick answer"


# ── 1. Submit a stuck task, give up waiting after 0.5 s ─────────────────
if __name__ == "__main__":
    start = time.perf_counter()
    with ProcessPoolExecutor(max_workers=1) as pool:
        future = pool.submit(stuck)
        try:
            future.result(timeout=WAIT_SECONDS)
        except FutureTimeout:
            print(f"{time.perf_counter() - start:4.1f}s  gave up waiting")
        # ── 2. The worker is still busy; we cannot cancel it ────────────
        print(f"        running={future.running()}"
              f" cancel()={future.cancel()}")
        # ── 3. The only worker is taken, so new work queues behind it ───
        second = pool.submit(quick)
        print(f"        second answer: {second.result()}")
        print(f"{time.perf_counter() - start:4.1f}s  second task done")
 0.5s  gave up waiting
        running=True cancel()=False
        second answer: quick answer
 4.1s  second task done

We gave up at 0.5 seconds, but the task was still running and could not be cancelled. The next job waited behind it until 4.1 seconds. If the stuck task had been an endless loop, the pool would have been dead for good, and leaving the with block would hang forever. This is what "poisoning" means: one bad candidate takes a worker out of service, and enough of them stop the whole search.

There are two ways out. The first is to use the pool for trusted work only, such as scoring a fixed set of instances on code that has already passed the wall. The second is the design in the right half of the figure: give every candidate its own child process, and use cheap threads only to wait on the children. A thread that waits on a child uses almost no CPU, so the GIL does not matter. Each child has its own timer and can be killed. This is what the final script does. Python 3.14 also added ProcessPoolExecutor.terminate_workers() and kill_workers(), which end a pool's workers by force. That rescue throws away every job in flight, so the per-task design is cleaner.

Systems connection

A timeout is the same tool that makes networks safe: you never wait forever for a reply, because "slow" and "dead" look the same from outside. Failure, Timeouts & Retries explains why. The one-child-per-task design is the bulkhead pattern from reliability engineering: a failure is contained to one compartment. And the pool's queue is the bounded queue of Queues, Thread Pools & Backpressure.

Determinism: one generator per candidate

An evolution run uses randomness everywhere: which parent to pick, which edit to make, which instances to test on. Reproducible Experiments showed why one seed fixes a whole run. In a parallel run, that idea needs one more step. A pseudo-random generator is a function that produces a long sequence of numbers that look random but are fully decided by a starting number, its seed. Python's top-level random.randint uses one hidden shared generator. If four workers share a generator, or each worker starts its own from operating-system noise, then the numbers a candidate sees depend on timing and on which worker took it. Two runs of the same program then give different results.

The fix is to stop sharing. Make one random.Random(seed) object per candidate, and compute its seed from a parent seed and the candidate's index. These are called child seeds. A hash is a good way to do it, because it scrambles nearby inputs, so candidates 7 and 8 get unrelated streams. Use hashlib, not Python's built-in hash(): string hashing in Python is deliberately randomised for each process, so hash() would give each worker different seeds.

The idea

  1. child_seed(parent, i): hash "parent/i"; first 8 bytes become an int
  2. draw_global(i) uses the shared generator; draw_own(i) uses its own
  3. run both through a 3-worker pool, twice; then with 1 worker
  4. compare results, and replay candidate 2 on its own
"""Give every candidate its own random generator, derived from one seed."""
import hashlib
import random
from concurrent.futures import ProcessPoolExecutor

RUN_SEED = 2024  # the one number that names the whole run
ITEMS = 5  # item sizes drawn per candidate, kept short to print


# ── 1. Child seeds: a stable function of (parent seed, index) ───────────
def child_seed(parent, index):
    """Hash, not hash(): str hashing is randomised per process."""
    text = f"{parent}/{index}".encode()
    digest = hashlib.sha256(text).digest()
    return int.from_bytes(digest[:8], "big")


# ── 2. Two ways to draw the same kind of numbers ────────────────────────
def draw_global(_index):
    return [random.randint(20, 60) for _ in range(ITEMS)]


def draw_own(index):
    rng = random.Random(child_seed(RUN_SEED, index))
    return [rng.randint(20, 60) for _ in range(ITEMS)]


def run_all(draw, workers):
    with ProcessPoolExecutor(max_workers=workers) as pool:
        return list(pool.map(draw, range(4)))


# ── 3. Compare: same inputs, different worker counts ────────────────────
if __name__ == "__main__":
    print("shared global generator, two runs of 3 workers:")
    print("  run A, candidate 0:", run_all(draw_global, 3)[0])
    print("  run B, candidate 0:", run_all(draw_global, 3)[0])
    print("one Random per candidate, derived from the run seed:")
    one = run_all(draw_own, 1)
    three = run_all(draw_own, 3)
    print("  1 worker, candidate 0:", one[0])
    print("  3 workers, candidate 0:", three[0])
    print("  all four identical:", one == three)
    print("  replay of candidate 2:", draw_own(2) == one[2])

  run A, candidate 0: [29, 50, 59, 49, 27]
  run B, candidate 0: [50, 36, 34, 60, 33]
one Random per candidate, derived from the run seed:
  1 worker, candidate 0: [38, 57, 44, 26, 48]
  3 workers, candidate 0: [38, 57, 44, 26, 48]

With the shared generator, two runs gave different numbers for the same candidate. With a generator per candidate, one worker and three workers gave identical answers, and candidate 2 could be replayed alone, on any machine, without running the other candidates. That last property is what makes a bug reproducible: "candidate 2 of run 2024" names an exact experiment. One more trap: if the parent builds a single Random object and workers inherit copies of it, every copy produces the same stream. Per-candidate generators avoid that as well.

Caching by content: never pay twice

Evolution repeats itself. A mutation can undo the last mutation. Two parents can produce the same child. A language model asked for a variation often returns the program it was given, with different comments. Scoring is the expensive step, so the same program should be scored once. A cache stores the answer to a question so the second ask costs nothing.

The cache needs a key, and the key must treat "the same program" as the same. Two sources that differ only in comments or spacing are the same program. The previous chapter's canonical form solves this: parse the source into a tree and print the tree back. Comments and spacing vanish in the round trip, and what is left is one standard text for each program. Then a content hash of that text gives a short, fixed-size name. A content hash is a fixed-size fingerprint of the bytes, made here with the secure hash algorithm (SHA) SHA-256 from hashlib. It is the same idea as the data hashes in Reproducible Experiments.

Two layers make sense. functools.lru_cache remembers answers inside one running process; with a size limit set, the least recently used (LRU) entries would be dropped first. A JSON file on disk remembers answers across runs and restarts. The lookup goes memory, then disk, then a real run.

The idea

  1. canonical(src): parse, print the tree back; digest = hash prefix
  2. the disk cache is one JSON file: {digest: score}
  3. real_evaluation: pack 2,000 items using the candidate's priority
  4. score_canonical: memory, then disk, then a real run (counted)
  5. ask five times, restart (clear memory) and ask again
"""Never score the same program twice: memory cache, then disk cache."""
import ast
import hashlib
import json
import random
import tempfile
from functools import lru_cache
from pathlib import Path

CACHE_FILE = Path(tempfile.gettempdir()) / "scores_demo.json"
CACHE_FILE.unlink(missing_ok=True)  # start the demo from an empty disk
evaluations = 0  # how many times we paid for a real run

A = "def priority(item, rem):\n    return -(rem - item)\n"
B = "# best fit\ndef priority( item,rem ):\n    return -(rem-item)  # tight\n"
C = "def priority(item, rem):\n    return 0\n"


# ── 1. Canonical form: comments and spacing vanish when we re-print ─────
def canonical(source):
    return ast.unparse(ast.parse(source))


def digest(canon):
    return hashlib.sha256(canon.encode()).hexdigest()[:12]


# ── 2. The disk cache is a JSON file: {hash: score} ─────────────────────
def disk_get(key):
    if not CACHE_FILE.exists():
        return None
    return json.loads(CACHE_FILE.read_text()).get(key)


def disk_put(key, score):
    table = json.loads(CACHE_FILE.read_text()) if CACHE_FILE.exists() else {}
    table[key] = score
    CACHE_FILE.write_text(json.dumps(table))


# ── 3. The slow part: pack 2,000 items with the candidate's priority ────
def real_evaluation(canon):
    scope = {}
    exec(canon, scope)  # safe here only because we wrote the programs
    priority = scope["priority"]
    rng = random.Random(7)
    free = []
    for _ in range(2000):
        item = rng.randint(20, 60)
        fits = [i for i, rem in enumerate(free) if rem >= item]
        if fits:
            pick = max(fits, key=lambda i: priority(item, free[i]))
            free[pick] -= item
        else:
            free.append(100 - item)
    return len(free)


# ── 4. Memory cache (lru_cache) in front, disk behind, real run last ────
@lru_cache(maxsize=None)
def score_canonical(canon):
    global evaluations
    key = digest(canon)
    found = disk_get(key)
    if found is not None:
        return found
    evaluations += 1  # stand-in for a slow, real evaluation
    score = real_evaluation(canon)
    disk_put(key, score)
    return score


def score(source):
    return score_canonical(canonical(source))


# ── 5. Ask five times, pay for two ──────────────────────────────────────
for name, src in [("A", A), ("B", B), ("A", A), ("C", C), ("B", B)]:
    print(f"{name} {digest(canonical(src))} -> {score(src)}")
print("real evaluations:", evaluations)
score_canonical.cache_clear()  # simulate a restart: memory is gone
print("after restart, A ->", score(A), "| real evaluations:", evaluations)
A b9190cb8d219 -> 855
B b9190cb8d219 -> 855
A b9190cb8d219 -> 855
C d77be4499026 -> 857
B b9190cb8d219 -> 855
real evaluations: 2
after restart, A -> 855 | real evaluations: 2

Programs A and B look different on the page, and B has two comments, yet both hash to b9190cb8d219. Five questions cost two real evaluations. After a simulated restart, memory was empty but the disk answered, so nothing was recomputed. Two limits are worth knowing. Renaming a variable changes the canonical text, so those programs are treated as different. That is safe: a miss only costs time, while a wrong hit would give a wrong score. And a cache is valid only while the evaluation is the same. If you change the instances, the seeds or the scoring rule, delete the file or include those settings in the key.

The archive is a log

A long run produces a lot of facts: which candidate came from which parent, what it scored, how it ended. Keep all of them, in order, and never rewrite a line. This is an append-only log. Each record is written once at the end of the file, and nothing in the middle changes. The most convenient format is JSON Lines: one JSON object per line. Each record holds the candidate's hash, its parent's hash, the source, the score, the outcome, the seed and the elapsed seconds. The parent hash turns the file into a family tree.

An append-only file is also a good way to survive a crash. If power fails while a record is being written, only the last line is damaged, and all earlier lines are intact. If you rewrote a whole results file in place, a crash halfway through could destroy everything. The reader's job is easy: skip any last line that does not parse. Calling os.fsync after each write asks the operating system to push the bytes to disk; Durability explains why a plain write may not be enough. This is the same idea as the write-ahead logs and event logs in Logs, Streams & Exactly-Once, at a much smaller scale.

The idea

  1. append(record): one JSON line at the end, flush, fsync
  2. replay(): parse every line; skip any line that does not parse
  3. best_so_far(): walk the log in order; print each new low score
  4. write five records, add a half-written line, then replay
"""An append-only archive: one JSON line per candidate, replayed on demand."""
import json
import os
import tempfile
from pathlib import Path

ARCHIVE = Path(tempfile.gettempdir()) / "archive_demo.jsonl"
ARCHIVE.unlink(missing_ok=True)

#  (hash, parent, bins used, outcome, seed, seconds)
RUN = [
    ("a1f3", None, 410, "ok", 11, 0.8),
    ("b7c2", "a1f3", 396, "ok", 12, 0.9),
    ("c9d0", "a1f3", 2000, "timeout", 13, 3.0),
    ("d4e8", "b7c2", 391, "ok", 14, 0.9),
    ("e5aa", "b7c2", 398, "ok", 15, 0.8),
]


# ── 1. Append one record: write, flush, ask the OS to persist it ────────
def append(record):
    line = json.dumps(record, sort_keys=True) + "\n"
    with open(ARCHIVE, "a") as handle:
        handle.write(line)
        handle.flush()
        os.fsync(handle.fileno())


# ── 2. Read every complete line; a torn last line is skipped ────────────
def replay():
    records = []
    for line in ARCHIVE.read_text().splitlines():
        try:
            records.append(json.loads(line))
        except ValueError:
            print("  skipped a torn line:", line[:30] + "...")
    return records


# ── 3. Rebuild the best-so-far curve from the log alone ─────────────────
def best_so_far(records):
    best = None
    for r in records:
        if r["outcome"] == "ok" and (best is None or r["score"] < best):
            best = r["score"]
            print(f"  candidate {r['hash']}: new best {best}"
                  f" (parent {r['parent']})")
    return best


for h, parent, score, outcome, seed, secs in RUN:
    source = f"def priority(item, rem): ...  # {h}"
    append({"hash": h, "parent": parent, "source": source, "score": score,
            "outcome": outcome, "seed": seed, "elapsed": secs})

with open(ARCHIVE, "a") as handle:  # a crash mid-write leaves half a line
    handle.write('{"hash": "f600", "parent": "d4e8", "sour')

print("lines in file:", len(ARCHIVE.read_text().splitlines()))
print("replaying:")
log = replay()
print("complete records:", len(log), "| best:", best_so_far(log))

replaying:
  skipped a torn line: {"hash": "f600", "parent": "d4...
  candidate a1f3: new best 410 (parent None)
  candidate b7c2: new best 396 (parent a1f3)
  candidate d4e8: new best 391 (parent b7c2)
complete records: 5 | best: 391

The file has six lines, one of them torn. The replay kept five records and rebuilt the improvement history from scratch: 410, then 396, then 391. The timeout row carries a penalty score of 2,000, so it can never become the best. One detail to handle in a real run: if you restart and append straight after a torn line, the new record glues onto the broken one. On start-up, check whether the file ends in a newline, and write one if it does not. Because the file records the seed of each candidate, a replay can also rerun any record and check that it gives the same score again.

Putting it together

The last script combines everything except the cache and the archive, which attach in a few lines each. It scores six bin-packing heuristics on the same five instances: first fit, best fit, worst fit, a crash, an infinite loop and a sleeper. Each runs in its own child, supervised by a thread, with a three-second wall clock and a two-second CPU limit set by the child itself. Anything that is not a clean result gets the penalty score: one bin per item, which is worse than any real packing.

The idea

  1. child program: set CPU limit, run the candidate, print total bins
  2. make_instances: five instances of 300 items, built from seeds
  3. evaluate_one: spawn a child, map every ending to (bins, outcome)
  4. evaluate_many: a thread pool; each thread waits on one child
  5. time 1 worker and 4 workers; print the table, best first
"""evaluate_many: score untrusted bin-packing heuristics, safely."""
import json
import random
import subprocess
import sys
import time
from concurrent.futures import ThreadPoolExecutor

CAPACITY = 100  # bin size; items are 20 to 60
ITEMS = 300  # items per instance
INSTANCE_SEEDS = range(5)  # the same five instances for every candidate
WALL_SECONDS = 3.0  # parent's clock: catches sleeping or blocked children
CPU_SECONDS = 2  # kernel's clock: catches busy loops

# The child program. It limits itself first, then runs the candidate.
RUNNER = """
import json
import sys
job = json.load(sys.stdin)
try:
    import resource
    cpu = job["cpu"]
    resource.setrlimit(resource.RLIMIT_CPU, (cpu, cpu))
except ImportError:
    pass  # Windows has no resource module: only the wall clock helps
scope = {}
exec(job["source"], scope)
priority = scope["priority"]
total = 0
for items in job["instances"]:
    free = []
    for item in items:
        fits = [i for i, r in enumerate(free) if r >= item]
        if fits:
            best = max(fits, key=lambda i: priority(item, free[i]))
            free[best] -= item
        else:
            free.append(job["capacity"] - item)
    total += len(free)
print(json.dumps({"bins": total}))
"""


# ── 1. Instances, built once in the parent from seeds ───────────────────
def make_instances():
    out = []
    for seed in INSTANCE_SEEDS:
        rng = random.Random(seed)
        out.append([rng.randint(20, 60) for _ in range(ITEMS)])
    return out


# ── 2. One candidate, one child process, always a result ────────────────
def evaluate_one(task):
    name, source, instances = task
    penalty = sum(len(inst) for inst in instances)  # one bin per item
    job = json.dumps({"source": source, "instances": instances,
                      "cpu": CPU_SECONDS, "capacity": CAPACITY})
    start = time.perf_counter()
    bins = penalty
    try:
        done = subprocess.run(
            [sys.executable, "-I", "-c", RUNNER],
            input=job, capture_output=True, text=True,
            timeout=WALL_SECONDS,
        )
        if done.returncode == 0:
            bins = json.loads(done.stdout)["bins"]
            outcome = "ok"
        elif done.returncode < 0:
            outcome = f"killed (signal {-done.returncode})"
        else:
            outcome = "error: " + done.stderr.strip().splitlines()[-1][:44]
    except subprocess.TimeoutExpired:
        outcome = "timeout"
    return name, bins, outcome, time.perf_counter() - start


# ── 3. Many at once: threads only wait; the work is in the children ─────
def evaluate_many(sources, instances, workers):
    tasks = [(name, src, instances) for name, src in sources.items()]
    with ThreadPoolExecutor(max_workers=workers) as pool:
        return list(pool.map(evaluate_one, tasks))


HEAD = "def priority(item, rem):\n"
CANDIDATES = {
    "first fit": HEAD + "    return 0\n",
    "best fit": HEAD + "    return -(rem - item)\n",
    "worst fit": HEAD + "    return rem - item\n",
    "crash": HEAD + "    return item / 0\n",
    "spin": HEAD + "    while True:\n        pass\n",
    "sleep": "import time\n" + HEAD + "    time.sleep(99)\n",
}

# ── 4. Run, print the table ─────────────────────────────────────────────
if __name__ == "__main__":
    data = make_instances()
    bound = sum(-(-sum(inst) // CAPACITY) for inst in data)
    print(f"lower bound: {bound} bins over {len(data)} instances")
    for workers in (1, 4):
        start = time.perf_counter()
        rows = evaluate_many(CANDIDATES, data, workers)  # keep the last
        print(f"workers={workers}: {time.perf_counter() - start:.1f}s")
    print(f"{'candidate':10s} {'bins':>5s} {'secs':>5s}  outcome")
    for name, bins, outcome, secs in sorted(rows, key=lambda r: r[1]):
        print(f"{name:10s} {bins:5d} {secs:5.1f}  {outcome}")
lower bound: 601 bins over 5 instances
workers=1: 5.2s
workers=4: 3.0s
candidate   bins  secs  outcome
best fit     649   0.0  ok
first fit    651   0.0  ok
worst fit    672   0.0  ok
crash       1500   0.0  error: ZeroDivisionError: division by zero
spin        1500   2.0  killed (signal 24)

Read the table from the top. Best fit beat first fit by two bins and worst fit lost by twenty-three, all above the 601-bin lower bound. The crash was caught in the child and scored as a failure. The spin was stopped by the kernel after two CPU seconds (signal 24). The sleeper was stopped by the wall clock after three. All three failures score 1,500, so selection ignores them with no special case.

The timing line is the other lesson. With one worker the run took 5.2 seconds; with four it took 3.0. The three good candidates take almost no time, so the floor is set by the slowest bad one, the sleeper at three seconds. With enough workers, the total wall time is about the longest timeout, not the sum of all of them. That is a good reason to keep timeouts as short as the real work allows.

Thread: bin packing

In online bin packing a candidate is a priority function, and the score is the total bins used over a fixed set of instances. This evaluator will run thousands of priority functions in the labs. Every candidate gets a child process and the same instances. A failure scores one bin per item. A crashing heuristic therefore scores 1,500 bins against best fit's 649, and evolution drops it. The cache and the archive attach to the same loop: hash each priority function, look up its score, and append the result to the log.

Key takeaways

  • A search loop runs code nobody has read. Three things go wrong: crashes, hangs and resource bombs. Make the evaluator total, so every outcome becomes a score.
  • A separate process is the only wall you can kill from outside. A timeout on a thread only stops you waiting.
  • Use two clocks: a wall-clock timeout in the parent and a CPU limit in the kernel. Memory limits through setrlimit work on Linux, not on macOS, and the resource module does not exist on Windows.
  • Processes beat threads for CPU-bound scoring because of the GIL. A shared pool cannot rescue a hung worker, so give risky code one child per candidate and use threads to wait.
  • Give each candidate its own random.Random, with a seed derived by hashing. Then the result does not depend on the number of workers, and any single candidate can be replayed.
  • Cache by the hash of the canonical source, in memory and on disk. Never pay twice, and invalidate the cache when the scoring rule changes.
  • Keep the archive as an append-only JSON Lines log. Summaries are rebuilt by replaying it, and a crash can only damage the last line.
  • Process limits stop accidents. They are not a security boundary against hostile code.

Check your understanding

A candidate calls time.sleep(60) inside its scoring function. You have set a one-second CPU-time limit and a three-second wall-clock timeout on the child. What happens?

  1. The CPU limit ends it after one second.
  2. The wall-clock timeout ends it after three seconds; the CPU limit never triggers.
  3. Neither limit applies, because sleeping is not running.
  4. It runs for sixty seconds, then reports an error.
A sleeping process uses almost no CPU time, so the CPU limit never reaches one second. The parent's wall clock counts real time and does end it. The first option confuses the two clocks, and that confusion is the reason to use both.

In a process pool you call future.result(timeout=0.5) and it raises a timeout error. What is true of the task?

  1. It has been killed, and the worker is free again.
  2. It has been cancelled, and cancel() will return True.
  3. It is paused until you ask for the result again.
  4. It keeps running in its worker, which stays busy, and cancel() returns False.
The timeout limits how long you wait. The worker is untouched, and a running call cannot be cancelled. If it never ends, that worker is lost. Killing the worker needs a separate process you control, such as a child per candidate.

You score 16 CPU-bound candidates. Which setup gives a real speed-up on a four-core machine in standard CPython?

  1. A ProcessPoolExecutor with four workers.
  2. A ThreadPoolExecutor with four workers.
  3. A ThreadPoolExecutor with sixteen workers.
  4. A ProcessPoolExecutor with one worker.
The global interpreter lock lets only one thread run Python code at a time, so extra threads add overhead and no parallelism, as the timing table showed. Separate processes have separate locks. One process adds start-up cost and no parallelism.

A parallel run gives different scores each time, although you set random.seed(1) in the parent. Which change makes it repeatable for any number of workers?

  1. Call random.seed(1) again at the start of every worker.
  2. Use Python's built-in hash() of the candidate text as its seed.
  3. Give each candidate its own random.Random, seeded from a hash of the run seed and the candidate's index.
  4. Run the workers one after another.
The third option ties each candidate's numbers to the candidate, not to the worker or the timing. Seeding every worker with the same number makes all workers draw the same stream. The built-in hash() of text changes between processes. Running one at a time works but throws away the speed-up.

Two candidate sources differ only in a comment and in spacing. Why do they share one cache entry in the chapter's design?

  1. The cache compares source text and ignores any lines that start with #.
  2. The key is the hash of the canonical form made by parsing the code and printing it back, which removes comments and spacing.
  3. Both programs always give the same score, whatever they contain.
  4. The cache stores the first 12 characters of the file.
Printing the parsed tree gives one standard text for each program, so formatting differences vanish before hashing. Renamed variables would still miss, which is safe. The cache never assumes unseen programs score alike.

The computer loses power while the archive's last record is half written. Why is an append-only JSON Lines file a good choice here?

  1. The operating system repairs half-written lines automatically.
  2. JSON Lines files cannot be damaged by a crash.
  3. The archive is kept in memory, so the disk does not matter.
  4. Earlier lines were never rewritten, so only the last line is damaged, and the reader can skip it.
Appending touches only the end of the file, so a crash can spoil only the line being written. A reader that skips unparseable lines recovers every earlier record. Nothing repairs the line automatically, and any file can be damaged by a crash. The point is that the damage is small and easy to detect.

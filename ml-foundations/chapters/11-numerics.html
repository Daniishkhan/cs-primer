Floating Point & Numerical Stability

Computers do not store real numbers; they store a finite set of them, packed densely near zero and sparsely far away. This chapter explains how a float is laid out, where rounding, overflow and underflow come from, why a softmax of large logits returns nan unless you subtract the maximum, and why modern training moves between float32, bfloat16, float16 and fp8 with care.

Why this matters

Chapters 8 to 10 treated numbers as exact. On a machine they are not, and the gap shows up as the classic failures of machine-learning code: a loss that turns nan at step 40,000, a model that trains in float32 but not in float16, a gradient that silently becomes zero, a probability that rounds to exactly 1. After this chapter you will be able to read a float's bits, predict when an expression overflows or loses precision, write the stable forms of softmax and cross-entropy, and explain mixed-precision training. It prepares the ground for mixed-precision training and loss spikes (A2, chapter 17), quantisation (A3, chapter 19), and the memory arithmetic of A3, chapter 2. Two cases follow these ideas in real systems: the Patriot missile clock and mixed-precision training, and Lab 4 asks you to write a stable log-softmax.

How a float is stored

You met the idea in chapter 1: Python's float is a 64-bit IEEE 754 number with about 16 significant digits. Here is the layout. A floating-point number is scientific notation in base 2: a sign, a power of two, and a fraction. For a normal number, the value is

(−1)sign × 1.mantissa × 2(exponent − bias)

The bits are split into three fields. The sign is one bit. The exponent field says which power of two. The mantissa (also called the significand or fraction) holds the digits after the binary point; the leading 1 is implied and not stored (the hidden bit), which buys one free bit of precision. The exponent is stored with a bias (127 for float32) so that it can be an unsigned integer. Float32 has 1 + 8 + 23 bits. The script reads the fields of a few numbers and rebuilds the value from them using the formula:

import struct

def fields32(x):
    bits = struct.unpack(">I", struct.pack(">f", x))[0]
    return bits >> 31, (bits >> 23) & 0xFF, bits & 0x7FFFFF

def rebuild32(s, e, m):
    if e == 0:
        return (-1) ** s * (m / 2 ** 23) * 2.0 ** -126            # subnormal: no hidden 1
    return (-1) ** s * (1 + m / 2 ** 23) * 2.0 ** (e - 127)

print(f"{'x':>12} {'sign':>4} {'exp':>4} {'(unbiased)':>12}  {'mantissa bits':23}  rebuilt")
for x in (1.0, -2.5, 0.1, 1 / 3, 1e-40):

float32 of 0.1 is really 0.10000000149011611938

Read the 0.1 row. The exponent field is 123, so the power is 2123−127 = 2−4, and the mantissa 1001 1001 1001… is the repeating pattern of one-tenth in binary. Ten ends up as a repeating fraction in base 2, just as 1/3 does in base 10, so it must be cut off and rounded: the float32 closest to 0.1 is 0.100000001490116…, not 0.1. That is the origin of 0.1 + 0.2 != 0.3. The last row shows a subnormal number: when the exponent field is 0 the hidden bit is dropped and the value is mantissa × 2−149, a graceful slide towards zero with shrinking precision rather than a cliff.

The designer of a format chooses how to split a bit budget. More exponent bits give more range; more mantissa bits give more precision. The formats used in machine learning are all points on that trade-off, drawn above and tabulated below.

Rounding and spacing

Between any two powers of two there are the same number of floats (223 for float32), so the gaps double each time you pass a power of two. The toy format in the figure has only 2 mantissa bits, so the effect is easy to see; the real formats work the same way with finer ticks.

The relative gap between neighbours is roughly constant, about 2−23 ≈ 1.2 × 10−7 for float32, a number called machine epsilon (the gap from 1.0 to the next float above it). That means a float32 is good to about 7 significant decimal digits at any scale, and a float64 to about 16. The absolute gap, though, grows with the number, as the script shows:

Analogy: a ruler whose marks spread out

Imagine a measuring tape engraved with ticks, but the ticks double their spacing every time the length doubles. Near the start you can read to a hair; at a hundred metres you can only read to the nearest metre. Every measurement is rounded to the closest tick. A float is that tape: precision is always about the same fraction of the number, which is wonderful for a huge range of magnitudes and harmful when you add numbers of very different size.

Where it breaks down: a tape is read once, but a computation reads and rounds again at every operation, so errors compound. Hardware also rounds correctly (to the nearest tick), which makes single operations accurate to half a gap, but a chain of them can drift much further.

Three consequences recur in machine learning code.

  • Absorption. Adding a number smaller than half the gap to a big number does nothing: in float32, 224 + 1 = 224, as the output shows. A small update to a large weight, or one more term in a long running sum, can vanish.
  • Cancellation. Subtracting two nearly equal numbers cancels the leading digits and leaves mostly rounding noise. The output computes the variance of 10000, 10001, 10002 (true value 2/3) as E[x²] − E[x]² in float32 and gets exactly 0.0: the two terms are about 108, each rounded to a gap of 8, and their difference is lost. The two-pass formula, subtract the mean first, then square, gives 0.666667. Same data, same precision, and the algebraically equivalent formula is wrong by 100%.
  • Non-associativity. (a + b) + c can differ from a + (b + c). Sums of many numbers depend on order, which is why GPU reductions can give slightly different totals from run to run (chapter 4, reproducibility) and why accumulating in a higher precision than the inputs is standard practice.

Common misconception

"Floating-point error is tiny, so it only matters for scientific computing." Each rounding is small, but the failures are not. A naive variance returned 0 instead of 0.67, a softmax returns nan for logits of 1000 (below), and the rounding error in converting 0.1 s clock ticks, accumulated to about 0.34 s over 100 hours of uptime, helped cause a missed missile interception (Case 2). Treat float arithmetic as an engineering material with known failure modes, and learn the stable form of each formula you use.

Range: overflow, underflow and NaN

The exponent field limits how large and how small a number can be. The numbers in the table are computed from the layouts in the figure, with float16 and float32 cross-checked against NumPy:

import numpy as np

def describe(name, ebits, mbits, ieee=True, max_override=None):
    bias = 2 ** (ebits - 1) - 1
    emax = (2 ** ebits - 2 if ieee else 2 ** ebits - 1) - bias
    top = (2 - 2.0 ** -mbits) if ieee else (2 - 2.0 ** (1 - mbits))      # E4M3 loses its top mantissa code to NaN
    vmax = max_override or top * 2.0 ** emax
    min_norm = 2.0 ** (1 - bias)
    min_sub = 2.0 ** (1 - bias - mbits)
    return name, 1 + ebits + mbits, ebits, mbits, vmax, min_norm, min_sub, 2.0 ** -mbits

The columns tell you what each format is for. Overflow happens when a result exceeds the maximum: IEEE formats produce inf (the fp8 E4M3 format has no infinity and produces NaN instead). In float16, e12 = 162,755 already overflows, since the maximum is 65,504. Underflow is the opposite: results below the smallest subnormal become 0, and results between the smallest normal and the smallest subnormal lose precision gradually. A float16 gradient of 10−8 becomes exactly 0; in bfloat16 it is fine.

The special values obey rules that are useful to know. inf arises from overflow or division by zero; inf − inf, 0 × inf, 0/0 and inf/inf give NaN ("not a number"). NaN is contagious: any arithmetic with a NaN gives NaN, so a single bad value early in a network infects the loss, the gradients and every weight within one step. NaN even compares unequal to itself (nan != nan is true), which is the standard test for it. This is why a training run goes from perfectly healthy to all-nan in a single step.

Writing stable code

Softmax and the log-sum-exp trick

The softmax turns scores z1, …, zK into probabilities: pi = ezi / ∑j ezj. Transcribed literally it breaks on large scores, since exp overflows: e89 is already past the float32 maximum, and logits in the hundreds are normal in practice (attention scores before scaling, large-vocabulary language models, a confident classifier). The repair follows from an identity. For any constant c,

ezi−c / ∑j ezj−c = (e−c ezi) / (e−c ∑j ezj) = pi,

because e−c cancels. Softmax is unchanged by shifting every score by the same amount, so choose c = maxj zj. Now the largest exponent is e0 = 1, so no overflow is possible, and at least one term of the sum is 1, so the sum cannot underflow to zero either. Terms that underflow to 0 were negligible anyway.

The same shift gives the stable log-sum-exp, logsumexp(z) = ln ∑j ezj = c + ln ∑j ezj−c, and hence the stable log-softmax: ln pi = zi − logsumexp(z). Working in log space avoids a second hazard. A probability like e−200 is 1.4 × 10−87, below float32's smallest number, so it becomes 0, and then ln 0 = −inf. Cross-entropy needs −ln p of the true class, so the right approach never forms p at all. The script runs both routes:

import numpy as np

np.seterr(all="ignore")   # hide overflow warnings so the output is readable; in real code, keep them on

def softmax_naive(z):
    e = np.exp(z)
    return e / e.sum()

def softmax_stable(z):
    e = np.exp(z - z.max())            # shift so the largest logit is 0: exp never exceeds 1
    return e / e.sum()

def log_softmax(z):
    m = z.max()
    return z - (m + np.log(np.exp(z - m).sum()))     # z - logsumexp(z)

z = np.array([1000.0, 1001.0, 1002.0], dtype=np.float32)
print("logits", z)
print("naive :", softmax_naive(z), "   (exp(1000) overflows float32: inf/inf = nan)")
print("stable:", softmax_stable(z))

z16 = np.array([12.0, 11.0, 10.0], dtype=np.float16)
print("\nfloat16, logits", z16, " exp(12) =", np.exp(z16)[0], "(the float16 maximum is 65504)")
print("naive :", softmax_naive(z16))
print("stable:", softmax_stable(z16))

z = np.array([0.0, -200.0], dtype=np.float32)

print("\nlogits", z, " probabilities", p)
print("log(softmax(z)) via probabilities :", np.log(p), " <- log(0) = -inf")
print("log_softmax(z), done in log space :", log_softmax(z), " <- exact")

In float32 the naive softmax of [1000, 1001, 1002] is all NaN (inf divided by inf), while the shifted version returns the right answer, [0.090, 0.245, 0.665]. In float16, where exp(12) already overflows, the naive version loses even a modest logit set. And for logits [0, −200], the naive cross-entropy of the second class is inf where the log-space version returns the exact 200. This is why frameworks provide fused functions (log_softmax, cross_entropy taking logits, binary_cross_entropy_with_logits): they apply these identities for you. Passing probabilities to a loss that expected logits, or applying softmax and then log yourself, throws the protection away.

Mixed precision: using fewer bits on purpose

Lower precision is attractive because bits are cost. Half the bits means half the memory for weights and activations and roughly twice the arithmetic throughput on hardware with 16-bit units, and for memory-bound work, such as decoding one token at a time, the bytes moved set the speed (Systems, chapter 21; chapter 2). But a 16-bit format has either less range (float16) or less precision (bfloat16). Mixed-precision training (Micikevicius et al., 2017) keeps each quantity in the format that can hold it:

  • Master weights in float32. The weights are stored in float32 and rounded to 16 bits for the forward and backward pass. The update is applied to the float32 copy. Why this matters is the next demonstration.
  • Loss scaling (float16 only). Multiply the loss by a constant (say 1024) before the backward pass so that small gradients move into float16's range, then divide the gradients by the same constant in float32 before the optimiser step. Adaptive loss scaling, which raises and lowers the factor when overflows occur, is standard.
  • Sensitive operations in float32. Reductions (sums, softmax denominators, normalisation statistics) and the loss itself are computed or accumulated in float32, even when their inputs are 16-bit.

Each rule answers an observed failure. This script reproduces three of them, with float16 from NumPy and bfloat16 emulated by rounding a float32 to its top 16 bits:

import numpy as np

def to_bf16(x):
    """Round float32 to bfloat16: keep the top 16 bits of the float32, rounding to nearest even."""
    b = np.asarray(x, dtype=np.float32).view(np.uint32).astype(np.uint64)
    b = (b + 0x7FFF + ((b >> 16) & 1)) & 0xFFFF0000
    return b.astype(np.uint32).view(np.float32)

Underflow of gradients. A gradient of 10−8 is 0 in float16 but survives in bfloat16 (same range as float32). Scaling by 1024 first brings it into float16's range (1.0252 × 10−5 is a subnormal there, coarsely rounded, but non-zero), and dividing afterwards in float32 gives back 1.001 × 10−8, which is within 0.1% of the original. Lost updates. Adding 10−4 to a weight of 1.0 ten thousand times should give 2.0. In float16 the gap near 1.0 is about 10−3, so each +10−4 rounds back to 1.0 and the weight never moves; in bfloat16 the gap is 0.0078, so the same. Only the float32 weight learns (it reaches 2.0002, not exactly 2: even float32 shows rounding drift, here a 0.01% error, which is the Patriot effect in miniature). This is exactly why master weights exist. Stuck accumulators. Summing 100,000 numbers around 1 in a float16 accumulator stops at 4,096: from there the gap is 4, and adding a number below 2 changes nothing. The true sum is about 100,000. Always accumulate in higher precision, as GPU matrix units do internally.

Why have two 16-bit formats? Float16 has the finer precision (10 mantissa bits) but a narrow range, so it needs loss scaling and care about overflow. bfloat16 (introduced by Google for its TPUs, hence "brain float") copies float32's 8 exponent bits, so it has float32's range and normally needs no loss scaling, at the price of only 7 mantissa bits, about 2 to 3 significant decimal digits. For training, whose gradients span many orders of magnitude, range tends to matter more than precision, so bfloat16 became the common default on recent hardware, with float32 for the sensitive parts. The training-stability chapter (A2, chapter 17) shows what happens when the lost precision bites.

Going lower: fp8

Eight-bit floats halve the cost again. Micikevicius et al. (2022, FP8 Formats for Deep Learning) proposed two encodings, E4M3 (4 exponent bits, 3 mantissa bits; maximum 448, no infinities) and E5M2 (5 and 2; IEEE-style, maximum 57,344). The typical split is E4M3 for the forward pass (weights and activations, which need precision) and E5M2 for gradients (which need range). With only 4 or 5 exponent bits, the representable range is narrow (see the figure), so a tensor's values must be scaled into it. The standard device is a scale factor per tensor (or per block of values): divide by a number chosen so that the tensor's largest absolute value (its amax) maps to the format's maximum, quantise, and remember the scale to undo it. The script has a small quantiser, checked against NumPy's float16, and applies it to data with a standard deviation of 0.002:

import numpy as np

def quantise(x, ebits, mbits, vmax, ieee=True):
    """Round x to the nearest value of a small float format (round half to even, saturate at vmax)."""
    bias = 2 ** (ebits - 1) - 1
    emin = 1 - bias                                    # exponent of the smallest normal number
    x = np.asarray(x, dtype=np.float64)
    e = np.floor(np.log2(np.maximum(np.abs(x), 1e-300)))
    e = np.maximum(e, emin)                            # below emin the step stays fixed: subnormals
    step = 2.0 ** (e - mbits)
    q = np.round(x / step) * step                      # np.round rounds half to even
    return np.clip(q, -vmax, vmax)

# Sanity check of the quantiser against numpy's own float16
rng = np.random.default_rng(0)
x = rng.standard_normal(10000) * 10
print("matches np.float16 on 10,000 values:", np.array_equal(quantise(x, 5, 10, 65504.0), x.astype(np.float16).astype(np.float64)))

Without scaling, 37% of the values are rounded to exactly zero in E4M3 (the smallest subnormal is 0.00195), and those that survive are 55% off on average. Scaling by amax brings the error down to 2%, and no value is lost. E5M2 has a wider range so it tolerates the unscaled data better (5% error) but is coarser once scaled (4.5%). Mean relative error of 2% to 5% is the price of 8 bits, and is tolerable in matrix multiplications because errors are random and average out over thousands of terms, with accumulation kept in higher precision.

State of play, October 2026

Hardware support decides what is practical, and it changes with each accelerator generation. Fp8 matrix units arrived with Nvidia's Hopper generation and are well supported in training libraries. Beyond fp8, block-scaled formats store a small group of values (often 16 or 32) with a shared scale factor: the Open Compute Project's "microscaling" (MX) specification v1.0, ratified in 2023, defines MXFP8 and a 4-bit MXFP4 with 32-element blocks, and Nvidia's NVFP4 is a related 4-bit format with 16-element blocks and a finer-grained scale. I confirmed these descriptions only in secondary sources (papers and documentation excerpts), not in the specifications themselves. How much accuracy 4-bit training costs, and which recipe is best, is an active research area. Use the principle (range via exponent bits, precision via mantissa bits, scaling to fit) and check your hardware and library documentation for what is actually supported.

Systems connection

Numeric formats are a storage decision as well as an arithmetic one. A weight stored in 2 bytes instead of 4 halves the memory bandwidth needed to read it, and for token-by-token decoding, which is bound by memory bandwidth rather than arithmetic, that translates almost directly into speed (Systems, chapter 22, on finding the real bottleneck). Storage matters for training too, but less than one might hope: the 16 bytes per parameter of Adam state in chapter 10 includes float32 master weights and two float32 moments, so moving weights and gradients to 16 bits trimmed the total rather than halving it.

Finding the source of a NaN

When a run produces nan or inf the first priority is to catch it where it starts, not where it is noticed (usually the loss, several operations downstream). A workable procedure:

  1. Reproduce on a small scale. Fix the random seed (chapter 4), find the step number where the first NaN appears, and restart from the last good checkpoint with that batch.
  2. Find the first non-finite value. Check intermediate tensors with isfinite after each layer or turn on the framework's anomaly detection (for example PyTorch's torch.autograd.set_detect_anomaly(True), slow but effective), which raises on the operation that produced the first NaN in the backward pass.
  3. Classify it. Overflow (a huge activation or logit: unscaled attention, an exploding layer, loss scale too high), invalid operation (log of 0 or a negative number, sqrt of a negative, 0/0, a division by a variance of exactly 0), or bad data (a NaN or inf in an input row; a missing value that was not handled).
  4. Apply the matching fix. Overflow: stable softmax, lower precision-sensitive scale, normalisation, clipping, bfloat16 instead of float16. Invalid operation: epsilon, clamp inputs, log1p, fused loss. Data: validate and filter inputs.
  5. Check ε against the format. Adam's default ε = 10−8 is below float16's smallest subnormal (6 × 10−8) and underflows to 0 there, which silently removes the safeguard against dividing by zero. Optimiser state should be kept in float32 for this reason.

Key takeaways

  • A float is sign × 1.mantissa × 2exponent. Exponent bits set the range; mantissa bits set the relative precision. Neighbouring floats are about 2−m apart in relative terms (1.2 × 10−7 for float32), so the absolute gap grows with the number.
  • Decimal fractions such as 0.1 are not exactly representable; single operations are correctly rounded, but absorption, cancellation and order-dependence make long computations drift or fail.
  • Overflow gives inf, underflow gives 0, invalid operations give nan, which spreads through every later calculation.
  • Subtract the maximum before exponentiating. Use log-softmax and fused cross-entropy on logits, log1p, expm1, hypot, and two-pass or Welford variance.
  • Float16 has precision but little range (needs loss scaling); bfloat16 has float32's range but about 2 to 3 digits (needs float32 master weights and accumulation); fp8 formats need per-tensor or per-block scale factors.
  • Mixed precision works by assigning each quantity the cheapest format that can hold it, and accumulating in float32.
  • To debug a NaN, find the first non-finite value, classify it as overflow, invalid operation or bad data, then apply the matching stable form.

Check your understanding

A float32 softmax is applied to logits [900, 905, 910]. What happens, and what is the minimal fix?

  1. It works, because the three values are close together
  2. It returns zeros because the probabilities underflow; switch to float64
  3. exp overflows to inf and the division gives nan; subtract the largest logit before exponentiating
  4. It returns the right answer but slowly; use log-softmax for speed
e900 is far beyond float32's maximum (about e88.7), so exp returns inf, and inf/inf is nan. The closeness of the values does not help the overflow. Float64 would only postpone it (its limit is about e709); the shift z − max(z) fixes the problem at any magnitude because softmax is shift-invariant.

In float16 you add an update of 10−4 to a weight equal to 1.0, many times. What happens, and why?

  1. The weight never changes, because the gap between floats near 1.0 is about 10−3 and each update rounds back to 1.0
  2. The weight grows normally, because 10−4 is above float16's smallest subnormal
  3. The weight becomes nan after a few updates
  4. The weight changes by 10−3 each time, rounding the update up
Representability of the update (it is above 6×10−8) is not the issue: the sum 1.0001 must be rounded to a float16 near 1, and the nearest is 1.0. This is why master weights are kept in float32. Rounding to nearest never rounds an update up by a factor of ten, and nothing here overflows.

Why can bfloat16 usually train without the loss scaling that float16 needs?

  1. It has more mantissa bits, so gradients are represented more precisely
  2. It stores gradients in float32 internally
  3. It rounds more cleverly than float16
  4. It has the same 8 exponent bits as float32, so tiny gradients such as 10−8 are in its range instead of underflowing
The difference is the exponent: bfloat16 has 8 bits, like float32, so its range is the same (to about 10−38 for normal numbers), while float16 has 5 and underflows below about 6×10−8. bfloat16 actually has fewer mantissa bits than float16 (7 versus 10), so option 0 is backwards.

A classifier's cross-entropy loss is computed as -log(softmax(z)[target]), and for some examples the loss is inf even though the logits are finite and moderate (the target logit is 200 below the maximum). The best fix is:

  1. Add a small constant to the loss
  2. Compute the loss from logits with a fused log-softmax (zt − logsumexp(z)), never forming the probability
  3. Clip the probabilities to the interval [0, 1]
  4. Convert the logits to float16
The probability e−200 is about 10−87, below float32's range, so it underflows to 0 and log(0) = −inf. The log-space formula gives exactly 200 without ever creating the tiny number. Clipping to [0, 1] does nothing for a value that is already 0, and float16 has an even smaller range.

You quantise a tensor of values with typical size 0.002 to fp8 E4M3 (smallest subnormal about 0.002, maximum 448) with no scaling, and many entries become 0. What is the standard remedy?

  1. Switch to float64 for that tensor
  2. Add noise to the tensor before quantising
  3. Multiply by a per-tensor (or per-block) scale factor chosen so that the largest magnitude maps near 448, then divide it out afterwards
  4. Round the values up instead of to nearest
The problem is that the values sit near the bottom of E4M3's range. Scaling shifts them upward into the range where the format has resolution, and the scale is kept to undo it. In the chapter's experiment this cut the zeroed fraction from 37% to 0 and the error from 55% to 2%. Float64 defeats the purpose of fp8, and rounding up or adding noise does not change the range.

You compute the variance of values near 104 in float32 as E[x²] − E[x]² and get exactly 0.0, though the data clearly vary. What explains it?

  1. Catastrophic cancellation: both terms are about 108 with a rounding gap of several units, so their small difference is swallowed
  2. Float32 cannot store numbers as large as 108
  3. The data contain a NaN
  4. NumPy's mean is inaccurate for small arrays
Float32 holds 108 easily (its limit is 3.4×1038), but near 108 adjacent floats are 8 apart, so a true difference of 0.67 vanishes. Subtracting the mean first (two-pass) keeps the numbers small and the answer exact. No NaN is involved; a NaN would make the result NaN, not 0.

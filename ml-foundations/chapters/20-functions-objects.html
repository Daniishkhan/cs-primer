Functions, Closures & Objects

Some programs try many small variations of an idea, score each one, and keep the best. Three plain-Python tools build such a program: a function you can pass around, a record that carries its own score, and a guard that survives a crash. This chapter teaches those three tools one at a time, with scripts you can run.

Why this matters

Picture a loop that makes a variant of a program, runs it, scores it, and keeps it if it beats the rest. Every line of that loop uses a feature this course has not yet taught. Variants are functions stored in a table. Each scorer remembers its test data. Each variant is a small record. A variant that crashes must become a bad score, not a dead program.

Earlier chapters used some of these features without teaching them. The autograd engine in chapter 9 builds each backward step as a closure and overloads __mul__. The labs in the search and evolution course use dataclasses, custom exceptions and finally. After this chapter you can read all of that code, and write your own. It builds on chapter 1 (numbers, lists, loops, comprehensions) and chapter 4 (seeds). The next two chapters treat code as data (chapter 21) and run it safely (chapter 22).

Functions are values

In Python, a function value is a function treated like any other piece of data. It can sit in a variable, travel as an argument, come back as a result, or live in a list or a dictionary. This is not a special feature. The line def add_three(x) creates a function object and binds the name add_three to it, just as n = 3 binds n to a number.

The consequence is large. If a function is a value, you can write code that does not care what to do, only that something should be done. A sorting routine does not need to know how to rank your records. You hand it the ranking as a function. A search loop does not need to know how to change a candidate. You hand it a table of change functions.

Passing, returning and storing

There are three moves. You can pass a function into another function, as in apply_twice(add_three, 10). Inside, f(f(x)) calls whatever was passed. You can return a function, as in make_adder(10), which builds a new function each time it runs. And you can store functions in a collection and pick one by name.

The third move is the one an evolution loop leans on. A mutation is a small random change to a candidate. A search usually has several kinds of mutation, so we keep them in an operator table: a dictionary whose keys are names and whose values are the mutation functions. To apply a mutation we look it up by name and call it. Adding a new kind of mutation means adding one line to the dictionary. The loop itself never changes.

Thread: bin packing

Through the builder chapters we use one problem: online bin packing. Bins hold 100 units. Items of size 20 to 60 arrive one at a time. A heuristic, which is a rule of thumb, is a function priority(item, rem) that scores a bin by its remaining space rem. The item goes into the highest-scoring bin that fits. If none fits, it opens a new bin. A heuristic is a value, so we can keep many in a table and compare them. The last section builds that loop.

The idea

  1. pass a function in; return a function out
  2. OPERATORS: name → mutation function; pick by name, call it
  3. sorted / max / min take key=function; lambda for one-offs
"""Functions are values: pass them, return them, keep them in a dict."""
import random

SEED = 4
GENES = [5, 2, 8, 1]


# ── 1. Pass a function in, get a function out ───────────────────────
def add_three(x):
    return x + 3


def apply_twice(f, x):
    return f(f(x))


def make_adder(n):
    def add(x):
        return x + n

    return add


print("apply_twice(add_three, 10) =", apply_twice(add_three, 10))
add_ten = make_adder(10)
print("make_adder(10)(1) =", add_ten(1))
print("a function has a name:", add_three.__name__)


# ── 2. An operator table: names mapped to mutation functions ────────
def tweak(genes, rng):
    out = list(genes)
    i = rng.randrange(len(out))
    out[i] += rng.choice([-1, 1])
    return out


def swap(genes, rng):
    out = list(genes)
    i, j = rng.sample(range(len(out)), 2)
    out[i], out[j] = out[j], out[i]
    return out


OPERATORS = {"tweak": tweak, "swap": swap}

rng = random.Random(SEED)
for name, op in OPERATORS.items():
    print(f"{name:5s}", GENES, "->", op(GENES, rng))
chosen = rng.choice(sorted(OPERATORS))
print("picked by name:", chosen, "->", OPERATORS[chosen](GENES, rng))


# ── 3. key= functions: sorted and max take a function ───────────────
runs = [("a", 7.5), ("b", 3.0), ("c", 9.1)]


def by_score(run):
    return run[1]


print("sorted :", sorted(runs, key=by_score))
print("best   :", max(runs, key=by_score))
print("lambda :", min(runs, key=lambda run: run[1]))
print("by len :", sorted(["pear", "fig", "banana"], key=len))

Read the output line by line. apply_twice(add_three, 10) gives 16, because 10 + 3 + 3 = 16. The operator table holds tweak and swap. The loop for name, op in OPERATORS.items() pulls out each name and its function together, then calls op(GENES, rng). The same line of code ran two different behaviours.

Note that each mutation copies the list first (out = list(genes)). Without the copy, the parent would be changed too. Chapter 1 showed that a list assigned to a second name is one list with two names. The same care applies here, and we meet it again with dataclasses.

Functions that take a key

You have already used functions as values without saying so. sorted(runs, key=by_score) calls by_score on every element and sorts by what it returns. max and min take the same argument. The last four lines of the script show it: max(runs, key=by_score) picks the run with the highest score, and sorted(words, key=len) passes the built-in len as a function.

Notice what is not there. We wrote key=by_score and not key=by_score(run). The brackets would call the function now. Leaving them off passes the function itself, to be called later by sorted. Mixing these up is the most common beginner slip with function values.

Lambda: a small anonymous function

A lambda is a function written as one expression with no name: lambda run: run[1]. It is the same as a def that returns that expression. The script's last min call uses one to avoid writing by_score for a one-off ranking.

Use a lambda when the body is a single short expression used once, usually as a key=. Use a named def when any of these is true.

  • The body needs more than one expression, a loop or a try.
  • You use the function in two places.
  • A failure message should name it. A lambda shows up in a traceback as <lambda>, which is no help at 2 a.m.
  • It deserves a docstring.

Closures: functions that remember

Chapter 1 showed that a variable made inside a function disappears when the function returns. A closure is the exception: an inner function that keeps using variables from the outer function after the outer function has finished. The inner function carries those variables with it.

Analogy: a packed lunchbox

You pack a lunchbox at home and carry it to work. At lunchtime you open it and eat what you packed that morning, even though your kitchen is miles away. A closure is the lunchbox. The kitchen is the outer function, and the food is the variables it packed. Pack a second box and it has its own food. Eating from one does not empty the other.

Where it breaks down: a lunchbox holds a copy of the food, and what you eat is gone for good. A closure holds the variable itself, not a copy of its value. If the variable changes later, the closure sees the new value. That difference causes the trap below.

A counter that remembers

Start with make_counter. It sets count = 0 and defines tick, which adds one to count and returns it. Then it returns tick without calling it. Each call to make_counter() makes a fresh count and a fresh tick bound to it. So a and b count separately.

The word nonlocal matters. Inside tick, the statement count += 1 assigns to count. Python's rule is that assigning to a name inside a function makes that name local to the function. Without a declaration, tick would look for a local count, find none, and raise an error. The line nonlocal count says: this name belongs to the enclosing function, so assign there. Reading a captured variable needs no declaration. Rebinding it does.

A scorer that captures its test data

The same idea gives us the evaluator an evolution loop needs. make_scorer(instances) takes the test cases once. It returns score(f), which measures how well a candidate function f does on those cases. The caller of score never touches the test data. Nothing can change it by accident, and the data is not passed around on every call.

Check the numbers by hand. The test pairs are (1, 3), (2, 5), (3, 7), (4, 10). The candidate 2x + 1 predicts 3, 5, 7, 9. The errors are 0, 0, 0, 1, so the mean is 0.25. The candidate 3x predicts 3, 6, 9, 12. The errors are 0, 1, 2, 2, so the mean is 1.25. The output matches. Lower is better, and the two candidates are scored against identical data, which is what makes the comparison fair.

The idea

  1. make_counter: tick shares one cell; nonlocal rebinds it
  2. make_scorer(instances) → score(f) closes over the instances
  3. loop lambdas all read the same i; i=i freezes each value
  4. partial(power, exponent=2) pins an argument
  5. lru_cache: key = arguments (hashable), value = result
"""Closures: a function that remembers the variables it was made with."""
from functools import lru_cache, partial


# ── 1. A counter that remembers its count ───────────────────────────
def make_counter():
    count = 0

    def tick():
        nonlocal count  # without this, count += 1 would raise an error
        count += 1
        return count

    return tick


a = make_counter()
b = make_counter()
print("a:", a(), a(), a(), " b:", b())


# ── 2. A scorer that captures its test instances ────────────────────
def make_scorer(instances):
    def score(f):
        errors = [abs(f(x) - y) for x, y in instances]
        return sum(errors) / len(errors)

    return score


score = make_scorer([(1, 3), (2, 5), (3, 7), (4, 10)])
print("2x+1 :", score(lambda x: 2 * x + 1))
print("3x   :", score(lambda x: 3 * x))


# ── 3. The late-binding trap, and its fix ───────────────────────────
trap = [lambda: i for i in range(3)]
fixed = [lambda i=i: i for i in range(3)]
print("trap :", [f() for f in trap])
print("fixed:", [f() for f in fixed])


# ── 4. partial: fix some arguments now, supply the rest later ───────
def power(base, exponent):
    return base**exponent


square = partial(power, exponent=2)
print("square(7) =", square(7))

# ── 5. lru_cache: remember results, never recompute a repeat ────────
CALLS = 0


@lru_cache(maxsize=None)
def slow_fitness(genes):
    global CALLS
    CALLS += 1
    return sum(g * g for g in genes)


for genes in [(1, 2), (3, 4), (1, 2), (1, 2)]:
    slow_fitness(genes)
print("real calls:", CALLS, " ", slow_fitness.cache_info())
try:
    slow_fitness([1, 2])
except TypeError as err:
    print("TypeError:", err)

The late-binding trap

Trap: closures capture variables, not values

The line [lambda: i for i in range(3)] looks as if it builds three functions that return 0, 1 and 2. It builds three functions that all return 2. Each lambda holds the variable i, not the value it had at the time. The functions run later, after the loop has finished with i = 2. Python looks up the variable when a function is called, which is why this is called late binding.

The fix is to freeze the value at the moment of creation. A default argument is evaluated once, when the def or lambda runs. So lambda i=i: i gives each function its own private i holding 0, 1 or 2. In the output, fixed shows [0, 1, 2]. A second fix is to build each function inside a helper such as make_adder. Each call to the helper makes a new variable.

This trap bites in real search code. Suppose you build one evaluator per test instance in a loop, then run them later. Without the fix, every evaluator quietly tests the last instance. The results look plausible, which is what makes it dangerous.

partial and lru_cache

Two tools in the standard library functools module are closures in disguise. Partial application fixes some arguments of a function now and leaves the rest for later. partial(power, exponent=2) returns a new function that squares its input. You could write it as a closure by hand. partial says what you mean in one line.

Memoisation means remembering the result of a call so a repeat call costs nothing. functools.lru_cache does it with a decorator, which is a line starting with @ placed above a def. The decorator wraps the function in a closure that holds a dictionary from arguments to results. The name means "least recently used" (LRU): when the cache is full, it drops the entry used longest ago. We passed maxsize=None to keep everything.

The output shows four calls but only two real runs: CacheInfo(hits=2, misses=2, ...). The two repeats of (1, 2) were answered from the dictionary. For an expensive fitness, such as one that packs thousands of items, that saving is large. Evolution loops produce the same candidate again and again, so a cache can remove much of the work.

The last two lines show the catch. The arguments become dictionary keys, and keys must be hashable: Python can compute a fixed number (a hash) from them that never changes. Tuples of numbers are hashable. Lists are not, because they can change. Passing a list raises TypeError: unhashable type: 'list'. So a cached fitness takes a tuple, not a list. Memoising is also only safe for a pure function, one whose result depends on its arguments alone. A fitness that reads a random generator or the clock would return a stale answer.

Objects: bundling data with behaviour

So far a candidate has been a bare list of numbers. That works until you want to attach a score, a name, or a note about where it came from. Then you carry three lists in step, and every function takes three arguments. One slip pairs a score with the wrong candidate. An object bundles the pieces so they travel together, and puts the functions that work on them next to the data.

A small class

A class is a blueprint for objects. The class Plain in the script has an __init__ method, which Python calls when you write Plain("a", [1, 2, 3]). Its first parameter, self, is the object being built. The lines self.name = name store data on that object. A method is a function defined inside a class. It also takes self first, so it can read the object's own fields. Calling p.total() passes p as self automatically.

Two things in the output are unhelpful. Printing a plain object shows only its type and a memory address. And two objects built from identical data are not ==, because by default Python compares identity ("same object?"), not contents. Both are fixable by writing methods by hand. Fortunately there is a shortcut.

Dataclasses

A dataclass is a class whose boring methods are written for you. Put @dataclass above the class and list the fields with type annotations. Python generates __init__, a readable __repr__ (the text print shows) and an __eq__ that compares field by field. The output shows Cand(name='a', genes=[1, 2, 3], score=0.0), and the two copies now compare equal.

Fields can have defaults, such as score: float = 0.0. A field with a default must come after the fields without one. The next section explains the one default that needs special care.

The idea

  1. plain class: __init__ and a method; == compares identity
  2. @dataclass writes __init__, __repr__, __eq__; default_factory
  3. a default [] is shared in functions, refused in dataclasses
  4. frozen → immutable, hashable; order → sortable; compare=False
"""From a bare class to a dataclass: bundling data with behaviour."""
from dataclasses import FrozenInstanceError, dataclass, field


# ── 1. A plain class: __init__ sets fields, methods use self ────────
class Plain:
    def __init__(self, name, genes):
        self.name = name
        self.genes = genes

    def total(self):
        return sum(self.genes)


p = Plain("a", [1, 2, 3])
print("total:", p.total(), "| default repr is noise:", "object at" in repr(p))
print("equal copies?", Plain("a", [1, 2, 3]) == p)


# ── 2. The same thing as a dataclass: the boilerplate is written ────
@dataclass
class Cand:
    name: str
    genes: list = field(default_factory=list)  # a fresh list per object
    score: float = 0.0

    def total(self):
        return sum(self.genes)


c = Cand("a", [1, 2, 3])
print(c)
print("equal copies?", Cand("a", [1, 2, 3]) == c)
x, y = Cand("x"), Cand("y")
x.genes.append(9)
print("x.genes:", x.genes, " y.genes:", y.genes)

Common misconception

"A default value is made fresh each time." For dataclass fields declared with field(default_factory=list) this is true: x.genes.append(9) leaves y.genes empty, as the output shows. For a plain function default it is false. The default in def bad_append(item, seen=[]) is built once, when the def runs, and every call shares it. The second call printed [1, 2] for both. Dataclasses protect you from the same mistake: writing genes: list = [] raises ValueError and tells you to use default_factory, a function called once per new object to make its default.

Frozen, ordered and hashable

Three options on @dataclass matter for search code.

frozen=True
Fields cannot be reassigned after creation. The script shows FrozenInstanceError when we try. Use it for a candidate that has been scored: nothing should be able to change it after the score is known.
order=True
Generates <, >, <= and >= by comparing the fields in the order they are declared, like comparing tuples. So sorted(results) and min(results) work with no key=. Put the field you rank by first. In the output, the two results with 3.5 bins are ordered by their second field, key.
field(compare=False)
Leaves a field out of equality, ordering and hashing. A free-text note should not make two otherwise identical candidates differ. The output confirms it: results differing only in note are equal.

Why does hashing matter? A set and the keys of a dict need hashable members. This is how an archive works: a dictionary or set that stores every candidate seen so far, so duplicates are noticed and the best ones are kept. Python's rule is strict. If a class defines __eq__, and equal objects must have equal hashes, then a mutable object cannot have a stable hash. So a plain @dataclass sets its hash to nothing. The script shows TypeError: unhashable type: 'Cand' when we try to hash one. Adding frozen=True makes Python generate a hash from the compared fields. Three results went into the set, two were equal, and the set size is 2.

One more catch: the hash is computed from the field values, so each field must itself be hashable. A frozen dataclass holding a list field cannot be hashed. Store genes as a tuple when the candidate must live in a set.

Dunder methods

Names like __init__ and __repr__ are dunder methods, short for "double underscore". Python calls them for you when you use an operator or built-in. Writing 3 + 4 runs (3).__add__(4). The script prints both and they agree. Writing len(x) runs x.__len__(). This is how your own classes can behave like built-in types.

The small Vec class defines __add__ and __mul__, so v + w and v * 3 work. It also sets __rmul__. When Python meets 2 * v, the integer 2 does not know how to multiply a Vec. Python then tries the right-hand object's reflected method, __rmul__. This is exactly what the Value class in chapter 9 relies on. It overloads __mul__ so that a * b builds a node in the computation graph and not just a number.

Two other dunders are worth knowing here. Defining __lt__ ("less than") lets sorted and min rank your objects. The decorator functools.total_ordering fills in the other comparisons from __eq__ and one ordering method. And __call__ makes an object callable like a function: after tick = Counter(), writing tick() runs __call__. Compare this with make_counter. A closure is a one-method object, and an object is a closure with many methods. Choose the closure when one function plus a little remembered state is enough. Choose a class when several functions share state.

A warning that follows from the hashing rule: if you write __eq__ by hand and do not write __hash__, Python sets __hash__ to nothing, and your objects stop working in sets. That is why the generated dataclass methods are safer than hand-written ones.

The idea

  1. a + b is a.__add__(b); len(x) is x.__len__()
  2. Vec defines __add__, __mul__, __rmul__, __repr__
  3. __lt__ gives sorting; __call__ makes an object callable
"""Dunder methods: how + and < and f() reach your own classes."""
from functools import total_ordering


# ── 1. Operators are method calls in disguise ───────────────────────
print("3 + 4          =", 3 + 4)
print("(3).__add__(4) =", (3).__add__(4))
print("len('abc')     =", len("abc"), " via", "abc".__len__())


# ── 2. A small vector that supports + and scalar * ──────────────────
class Vec:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Vec({self.x}, {self.y})"

    def __add__(self, other):
        return Vec(self.x + other.x, self.y + other.y)

    def __mul__(self, k):
        return Vec(self.x * k, self.y * k)

    __rmul__ = __mul__  # lets 2 * v work too, not only v * 2


v = Vec(1, 2)
w = Vec(3, 4)
print(v + w, v * 3, 2 * v)


# ── 3. __lt__ makes a class sortable; __call__ makes it callable ────
@total_ordering
class Run:
    def __init__(self, name, bins):
        self.name = name
        self.bins = bins

    def __repr__(self):
        return f"Run({self.name!r}, {self.bins})"

    def __eq__(self, other):
        return self.bins == other.bins

    def __lt__(self, other):
        return self.bins < other.bins


runs = [Run("a", 7), Run("b", 5), Run("c", 6)]
print(sorted(runs), "best:", min(runs), " a >= b:", runs[0] >= runs[1])

Exceptions: crashes as data

An exception is Python's way of saying "something went wrong, stop what you are doing". Dividing by zero, indexing past the end of a list and calling a missing function all raise one. If nothing handles it, the exception travels up through the callers and ends the program with a traceback.

For most scripts, ending is right. For a search loop it is a disaster. The loop tries thousands of candidates, and some will be broken in ways you did not predict: a division by zero, an infinite loop, a list index out of range. One bad candidate must not kill a run that has been going for hours. The loop must treat a crash as information: this candidate is bad, so give it the worst score and move on.

try, except, else, finally

The try statement has four parts.

  • try: holds the risky code.
  • except SomeError: runs only if the try block raised that kind of error.
  • else: runs only if the try block raised nothing.
  • finally: runs always, whether or not there was an error, and even when the block exits through return.

The demo function prints a line in each part so the order is visible. With 2, you see try, else, finally. With 0, you see try, except, finally. Both runs print the finally line before the value comes back, even though return appears earlier in the code.

Why keep else separate from try? Code in else is outside the guard. If it raises an error, the except clause does not hide it. Keep the try block as short as you can, so that an except only catches the errors you meant to catch.

Raising your own

You can raise an exception yourself with raise. To make a new kind, write a class that inherits from Exception: class Rejected(Exception). The body can be a docstring, since the class only needs a name. The benefit is precision. except Rejected catches your validation failures and nothing else, so a real bug, such as a typo that raises NameError, does not get mistaken for an invalid candidate.

In the script, build raises Rejected with a message saying what was wrong. It is a guard: a check at the door that stops bad input before expensive work starts. A candidate with the wrong number of genes never reaches the maths.

A total evaluator

An evaluator is total if it returns a result for every input and never raises. safe_score shows the shape. A valid candidate returns its real score, 18.0 for [4, 5, 8, 13]. A Rejected one returns PENALTY, a constant worse than any real score. A crash that nobody predicted, here a division by zero when a gene equals 3, returns a slightly different penalty, so the two causes can be told apart in the results.

Why a number and not None? Because every later step, sorting, comparing, averaging, expects numbers. A penalty score flows through the same code with no special case. A None would crash the sort three steps later, far from the cause.

The idea

  1. try / except / else / finally, in the order they run
  2. build() raises Rejected for invalid input
  3. safe_score turns each failure into a penalty number
  4. leaky restores by hand; careful restores in finally
"""Exceptions: turn every crash of a candidate into a score."""

PENALTY = -1000.0  # worse than any real score, but still a number
STEP_LIMIT = 100  # a global setting that evaluations may change


class Rejected(Exception):
    """The candidate is invalid and must not be scored."""


# ── 1. The four clauses, in the order they run ──────────────────────
def demo(value):
    try:
        print("  try: dividing 10 by", value)
        result = 10 / value
    except ZeroDivisionError:
        print("  except: caught it")
        return None
    else:
        print("  else: no error happened")
        return result
    finally:
        print("  finally: always runs")


print("demo(2):", demo(2))
print("demo(0):", demo(0))


# ── 2. Raise your own: validation says what is wrong ────────────────
def build(genes):
    if len(genes) != 4:
        raise Rejected(f"need 4 genes, got {len(genes)}")
    if min(genes) < 0:
        raise Rejected("genes must be non-negative")
    return [10 / (g - 3) for g in genes]  # g == 3 will crash


# ── 3. A total evaluator: every outcome becomes a number ────────────
def safe_score(genes):
    try:
        return sum(build(genes))
    except Rejected as err:
        print("  rejected:", err)
        return PENALTY
    except ZeroDivisionError:
        print("  crashed: ZeroDivisionError")
        return PENALTY - 1


for genes in [[4, 5, 8, 13], [1, 2], [1, -2, 4, 5], [3, 4, 5, 6]]:
    print(genes, "->", safe_score(genes))


# ── 4. finally restores state, even when the body crashes ───────────
def evaluate():
    raise RuntimeError("candidate crashed")


def leaky(limit):
    global STEP_LIMIT
    old = STEP_LIMIT
    STEP_LIMIT = limit
    evaluate()
    STEP_LIMIT = old  # never reached when evaluate() raises


def careful(limit):
    global STEP_LIMIT
    old = STEP_LIMIT
    STEP_LIMIT = limit
    try:
        evaluate()
    finally:
        STEP_LIMIT = old  # runs on success and on crash


for fn in (leaky, careful):
    try:
        fn(5)
    except RuntimeError:
        pass
    print(f"after {fn.__name__:7s}: STEP_LIMIT = {STEP_LIMIT}")
    STEP_LIMIT = 100

Common misconception

"Catch everything with a bare except: to be safe." A bare except: also catches KeyboardInterrupt (the user pressing Ctrl-C) and SystemExit, so the program can no longer be stopped. Write except Exception when you want to survive any ordinary failure, and name the specific classes you handle differently. Never let an except body be empty without a comment saying why. A swallowed error that nobody counts is how a search silently stops improving.

Why finally restores state

Some evaluations change shared settings for a while: a step limit, a random seed, a working directory, an open file. If the evaluation crashes halfway, code after the crash does not run, so the setting stays changed. The script shows it. After leaky(5) crashes, STEP_LIMIT is still 5. Every later evaluation in the run silently inherits a limit of 5, and results shift for reasons no one can see.

The function careful puts the restore in finally. It runs on success and on crash, so the setting is back to 100 either way. Python also offers the with statement, which is try/finally packaged as a reusable guard. You have met it in with open(path) as f:, which closes the file even if reading fails. Chapter 22 returns to this pattern when candidates run in separate processes.

Systems connection

The same discipline runs through production systems. A server that dies on one bad request is a denial-of-service bug, so request handlers catch errors at the boundary and turn them into error responses (Networking, chapter 16 on failure). Cleanup that must always run, such as releasing a lock or closing a connection, belongs in finally, for the same reason it does here. An evaluator that returns a penalty for a crash is a small error boundary.

Type hints as documentation

A type hint is a note that says what kind of value a name should hold. You write it after a colon on a parameter, and after -> for the return value: def nudge(genes: list[int], step: int) -> list[int]. Hints serve readers first. They tell the next person, or you in a month, what goes in and what comes out.

The ones you need in evolution code are few.

  • list[Candidate], dict[str, float], tuple[int, ...]: containers and what they hold.
  • Optional[X]: either an X or None. Newer code writes X | None.
  • Callable[[int, int], float]: a function that takes two integers and returns a float. The first bracket lists the argument types, the second item is the result type. A mutation function might be Callable[[list[int], int], list[int]].

Giving a name to a long hint, as the script does with Mutator, keeps signatures readable. The signature of apply_all then says, in one line, "give me a table of mutators and some genes, and I give back a list of gene lists".

The idea

  1. annotate arguments, results and function-valued arguments
  2. show that annotations are stored, not enforced
"""Type hints document intent. Python does not check them at run time."""
from typing import Callable, Optional

# A mutator takes genes and a step size, and returns new genes.
Mutator = Callable[[list[int], int], list[int]]


# ── 1. Hints on a function: inputs, output, and a function argument ─
def best_of(scores: list[float], key: Optional[Callable] = None) -> float:
    return max(scores, key=key)


def nudge(genes: list[int], step: int) -> list[int]:
    return [g + step for g in genes]


def apply_all(ops: dict[str, Mutator], genes: list[int]) -> list[list[int]]:
    return [op(genes, 1) for op in ops.values()]


print(best_of([2.5, 9.0, 4.0]))
print(apply_all({"nudge": nudge}, [1, 2]))

# ── 2. Nothing is enforced: a wrong call still runs ─────────────────
print(nudge.__annotations__)
print(best_of(["pear", "fig"]))  # strings, not floats: no complaint
print(nudge([1.5, 2.5], 1))  # floats, not ints: no complaint
9.0

{'genes': list[int], 'step': <class 'int'>, 'return': list[int]}

The output makes the key point. The function nudge is annotated for integers, yet nudge([1.5, 2.5], 1) runs without complaint. best_of is annotated for floats, yet it returned pear for a list of strings. Python stores the hints in __annotations__ and then ignores them. They are not checked at run time. A separate tool such as mypy or an editor's checker reads the hints and warns before you run anything. Treat a hint as a promise that a checker, or a reviewer, can hold you to.

Putting it together

Now we combine the pieces into a small but complete search loop on the bin-packing problem. Every part is something you have just met.

Thread: bin packing

The heuristics here are plain Python functions, built by a closure. make_priority(target) returns priority(item, rem), which prefers the bin whose leftover gap after placing the item is closest to target. With target = 0 it is best fit, which picks the tightest bin. With a larger target it prefers a looser fit. One integer describes a whole heuristic, and that integer is what we search over. Chapter 21 will let the search change the heuristic's source code itself.

The design has four parts.

  1. A frozen, ordered dataclass, Candidate, holds the score first (so min finds the best), then target, then a free-text origin that is excluded from comparison.
  2. A closure, make_evaluator(instances), captures five fixed test instances of 200 items. It returns evaluate, which validates a target (raising Rejected if it is not an integer from 0 to 50) and scores it as the mean number of bins used.
  3. An operator table maps three names to mutations of the target. nudge adds a small step. jump picks a fresh value. wild multiplies, which often produces an invalid target on purpose, so we can watch Rejected work.
  4. A dict archive keyed by target keeps one candidate per target. The key is hashable, so a repeated target is noticed and never re-evaluated.

The idea

  1. make_priority(target) → priority(item, rem); pack uses it
  2. make_evaluator(instances) → evaluate(target) or Rejected
  3. OPERATORS maps names to mutations of target
  4. loop: min(archive) → mutate → evaluate → archive[target]
"""A tiny evolution loop from functions, closures and dataclasses.
Heuristic family: prefer the bin whose leftover gap is closest to TARGET."""
import random
from dataclasses import dataclass, field

CAP = 100  # bin capacity
GENERATIONS = 40
SEED = 7


class Rejected(Exception):
    """A candidate that must not be scored."""


@dataclass(frozen=True, order=True)
class Candidate:
    bins: float  # first field, so order=True ranks by it (lower is better)
    target: int  # the hashable key of the archive
    origin: str = field(default="seed", compare=False)


# ── 1. Heuristics as plain functions, built by a closure ────────────
def make_priority(target):
    def priority(item, rem):
        return -abs((rem - item) - target)

    return priority


def pack(priority, items):
    rems = []  # remaining space of each open bin
    for item in items:
        fits = [r for r in rems if r >= item]
        if not fits:
            rems.append(CAP - item)
            continue
        best = max(fits, key=lambda r: priority(item, r))
        rems[rems.index(best)] -= item
    return len(rems)


# ── 2. A closure evaluator that remembers the instances ─────────────
def make_evaluator(instances):
    def evaluate(target, origin):
        if not isinstance(target, int) or not 0 <= target <= 50:
            raise Rejected(f"target {target!r} is not an int in 0..50")
        priority = make_priority(target)
        total = sum(pack(priority, items) for items in instances)
        return Candidate(total / len(instances), target, origin)

    return evaluate


# ── 3. The operator table: names -> mutation functions ──────────────
OPERATORS = {
    "nudge": lambda t, rng: t + rng.choice([-3, -1, 1, 3]),
    "jump": lambda t, rng: rng.randrange(0, 51),
    "wild": lambda t, rng: t * rng.choice([0.5, 2, 5]),
}

# ── 4. Select, vary, archive ────────────────────────────────────────
rng = random.Random(SEED)
sizes = random.Random(1)
instances = [[sizes.randint(20, 60) for _ in range(200)] for _ in range(5)]
evaluate = make_evaluator(instances)
lower = sum(sum(items) / CAP for items in instances) / len(instances)

archive = {40: evaluate(40, "seed")}  # keyed by target: no duplicates
print("seed:", archive[40])
rejected = 0
for gen in range(GENERATIONS):
    parent = min(archive.values())  # order=True: the fewest bins
    name = rng.choice(sorted(OPERATORS))
    child_target = OPERATORS[name](parent.target, rng)
    if child_target in archive:
        continue
    try:
        child = evaluate(child_target, name)
    except Rejected:
        rejected += 1
        continue
    archive[child.target] = child
    if child.bins < parent.bins:
        print(f"gen {gen:2d} {name:5s} target={child.target:2d} "
              f"bins={child.bins}")

print(f"archive={len(archive)} rejected={rejected} lower bound={lower:.1f}")
for c in sorted(archive.values())[:3]:
    print(c)

Read the output. The seed, target 40, uses 90.6 bins on average. Over 40 generations the loop finds better ones, step by step. Each printed line is a strict improvement in mean bins, and the best found is target 1 at 87.4. The lower bound printed at the end, 80.1, is a floor: total item size divided by 100. No packing, online or not, can use fewer bins.

Six of the 40 children were rejected, and the loop carried on. The archive holds 19 distinct scored targets, including the seed. The other generations landed on a target already seen, which cost nothing.

Be honest about what this shows. We measured the family's best fit separately: target = 0, which is best fit, scores 87.2. So this tiny search came close to a heuristic everyone already knows but did not beat it. That is a real result. The search space was one integer, and best fit is already good. To discover something new, the search needs a space that contains new ideas, such as the source code of the priority function. That is what the next chapter prepares.

Step through

One generation of the loop

  1. Pick a parent. min(archive.values()) works because Candidate has order=True: the first field, mean bins, decides.
  2. Mutate. Choose a name, look it up in the operator table, call the function. The loop does not know which mutation it ran.
  3. Validate. evaluate raises Rejected for a target that is not an integer from 0 to 50. The loop counts it and moves on.
  4. Evaluate. The closure still holds the five test instances. It builds make_priority(target), packs every instance and returns a frozen Candidate.
  5. Archive. The child is stored under its hashable target. A target seen before is skipped, so each heuristic is scored once. Then the loop repeats.

Seeds, caches and what the loop forgets

Two details come from earlier chapters. The loop takes its randomness from random.Random(SEED), an object you own, not the module-level functions. This is the practice of chapter 4, and it is why the output above is the same on every run. And the archive acts like the lru_cache from earlier: a repeated key costs nothing. Add a cache like that to evaluate only if target is the only input, and only if the instances never change.

The loop also forgets a lot. It keeps the best candidate per target but not the path that led there. It uses only min to choose parents, so it can get stuck in one region. The evolution course returns to these choices. Evolution for Builders covers what biology does, and Evolutionary Algorithms covers the search methods built on it.

Key takeaways

  • A function is a value. Pass it, return it, or keep it in a dict. An operator table of mutation functions is the core of a search loop.
  • A closure remembers variables from where it was made. Use nonlocal to change them. Beware late binding in loops, and fix it with i=i.
  • partial pins arguments. lru_cache remembers results, needs hashable arguments, and is safe only for pure functions.
  • A dataclass bundles data and writes __init__, __repr__ and __eq__. Use default_factory for list fields, frozen=True for hashable records and order=True to sort by the first field.
  • Dunder methods let your classes use operators and built-ins. __mul__ in autograd is the same idea as __lt__ here.
  • A search loop must be total: raise your own exception for invalid candidates, catch Exception (not a bare except), score every failure, and restore shared state in finally.
  • Type hints document intent and are not enforced at run time.

Check your understanding

What does [f() for f in [lambda: i for i in range(3)]] return?

  1. [0, 1, 2]
  2. [2, 2, 2]
  3. [3, 3, 3]
  4. It raises an error, because i is out of scope.
Each lambda holds the variable i, not its value at creation. By the time they are called the loop has ended with i = 2, so all three return 2. [0, 1, 2] is what you would get with lambda i=i: i. It is not 3, because range(3) stops at 2. There is no error, because the lambdas keep i alive.

Why does @dataclass refuse genes: list = [] and ask for field(default_factory=list)?

  1. Because lists cannot be stored in a dataclass at all.
  2. Because an empty list is falsy, and dataclasses reject falsy defaults.
  3. Because the default would be copied on every attribute access, which is slow.
  4. Because one list would be built once and shared by every instance, so changing it in one object would change them all.
A default expression runs once, when the class is defined. A shared list is the same trap as def f(x, seen=[]). The factory is called once per new object, so each gets its own list. Lists are allowed as fields, and truthiness is irrelevant.

A candidate raises RuntimeError inside a try block that has a finally but no except. What happens?

  1. The finally block runs, then the error keeps travelling up to the caller.
  2. The error is silently discarded and the code after the block continues.
  3. The finally block is skipped, because the error was not handled.
  4. Python converts the error into a Rejected exception.
finally always runs, which is why it restores state. It does not handle the error, so the error continues to the caller. Skipping finally on an unhandled error is the opposite of what it is for. Nothing is converted or discarded unless an except clause does so.

An evaluation loop wraps each candidate in try: ... except: with no class named. What is the real problem?

  1. It is slower than naming the class.
  2. It cannot catch ZeroDivisionError.
  3. It also catches KeyboardInterrupt and SystemExit, so you can no longer stop the run with Ctrl-C.
  4. It makes the finally clause stop working.
A bare except: catches everything, including the signals meant to stop the program. except Exception leaves those alone. The speed difference is negligible. A bare except does catch ZeroDivisionError, and it does not affect finally.

You decorate a fitness function with @lru_cache and call it with a list of genes. You get TypeError: unhashable type: 'list'. What is the best fix?

  1. Increase maxsize.
  2. Pass the genes as a tuple, which is hashable.
  3. Remove the type hints.
  4. Catch the TypeError and return 0.
The cache uses the arguments as dictionary keys, and keys must be hashable. A tuple of numbers is. The cache size is unrelated, type hints are not involved, and returning 0 would hide a real problem and give wrong scores.

You write def f(x: int) -> int: return x * 2 and call f("ab"). What happens?

  1. A TypeError is raised before the body runs.
  2. It returns None.
  3. Python converts "ab" to an integer and fails.
  4. It runs and returns "abab". A checker such as mypy would have warned beforehand.
Type hints are not checked at run time. String repetition makes "ab" * 2 valid, so the body works. Only a separate static checker, or your own isinstance test, would complain. Python never converts types because of hints.

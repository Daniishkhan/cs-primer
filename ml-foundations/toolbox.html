Explore and keep it reproducible

A notebook is where a number is first seen; an environment and a script are what make it come back.

Jupyter & notebooks

Install: uv pip install jupyterlab inside a virtual environment (see the uv card), then jupyter lab · Alternatives: VS Code or PyCharm notebooks, Google Colab and Kaggle (hosted, see below), Marimo (a notebook that re-runs dependent cells automatically) · Chapters: 1, 3, 4

A Jupyter notebook is a file (.ipynb, JSON underneath) of cells, each of which you can run in any order against one running Python process, the kernel. That is exactly why notebooks are good for exploration and risky for results: the kernel remembers every variable you ever defined, including ones whose cell you later deleted. Chapter 4 calls this hidden state, and the discipline it asks for is simple: a notebook is not finished until Restart and Run All gives the same answer from a clean kernel.

10-minute guided exercise

Create a notebook with hidden state, then run it from a clean kernel. This is the check you would run in continuous integration. The script writes a three-cell notebook in which the last cell uses cutoff, a variable that the notebook never defines (imagine the author defined it once in a cell they later deleted).

import nbformat as nbf
nb = nbf.v4.new_notebook()
nb.cells = [
    nbf.v4.new_code_cell("import numpy as np\nrng = np.random.default_rng(0)\nscores = rng.normal(70, 10, 200)"),
    nbf.v4.new_code_cell("threshold = 75      # (the author later deleted the cell that defined this)\npassed = (scores > threshold).mean()\nprint(f'pass rate {passed:.1%}')"),
    nbf.v4.new_code_cell("print(f'{(scores > cutoff).mean():.1%} above the cutoff')"),
]
nbf.write(nb, "fragile.ipynb")
$ python make_nb.py
$ jupyter nbconvert --to notebook --execute fragile.ipynb --output fragile_out.ipynb  # a clean kernel runs every cell, top to bottom (last lines shown)
Cell In[3], line 1
----> 1 print(f'{(scores > cutoff).mean():.1%} above the cutoff')

NameError: name 'cutoff' is not defined

Now fix it by defining cutoff = 75 at the top of the last cell, rerun, and read back the execution counts and outputs from the executed copy:

$ jupyter nbconvert --to notebook --execute fixed.ipynb --output fixed_out.ipynb
[NbConvertApp] Writing 2134 bytes to fixed_out.ipynb
$ python -c "import nbformat as nbf; [print(c.execution_count, [o.get('text','').strip() for o in c.outputs]) for c in nbf.read('fixed_out.ipynb', 4).cells]"
1 []
2 ['pass rate 32.0%']
3 ['32.0% above the cutoff']

(The command also prints a warning about the kernel running over TCP without encryption; that is normal for a local kernel.) Two details to try next, which I did not run here: jupyter nbconvert --to script fixed.ipynb turns a notebook into a plain .py file you can review in a diff, and jupyter lab opens the interface at a local address, where Kernel → Restart Kernel and Run All Cells does by hand what --execute did above.

What to look for

  • The failing run stops at the third cell with a NameError that the interactive session would have hidden. The execution counts in the fixed copy are 1, 2, 3 in order: a notebook whose counts are out of order (3, 1, 7) was run in an order a reader cannot reproduce.
  • The seed is set in the first cell (default_rng(0)), so the 32.0% is identical on every run (chapter 4).
  • Exploration happens in cells; anything you will rely on later (a function, a data-cleaning step) belongs in a .py file that the notebook imports.

Common pitfalls

  • Large outputs and images are saved inside the file, which makes diffs unreadable and repositories heavy. Clear outputs before committing, or use a tool that strips them automatically (nbstripout is one; jupytext pairs a notebook with a plain-text file).
  • Secrets pasted into a cell are saved in the file. Read keys from environment variables.
  • The kernel is not your project's environment unless you make it so. Install Jupyter in the same environment as your libraries, or register a kernel for it, otherwise import numpy may work in the terminal and fail in the notebook.
  • Running --execute needs permission to open local network ports (the kernel talks over local sockets). In a locked-down sandbox it fails with a permission error that has nothing to do with your notebook.

uv & virtual environments

Install: brew install uv (macOS) or the installer script from the uv documentation, or pip install uv · Alternatives: python -m venv with pip, conda/mamba, Poetry, pip-tools · Chapters: 4

A virtual environment is a private folder of Python packages for one project, so that two projects can need different versions of the same library without fighting. uv (from Astral, written in Rust) creates environments, installs packages, locks exact versions of everything into a file, and runs commands inside the environment. The lock file is the point: with it, a collaborator, a server or you next year gets the same package versions you used. Chapter 4 explains why that matters for experiments.

10-minute guided exercise

Make a project with pinned dependencies and look at what uv wrote. Run this in an empty folder (it needs network access to the Python package index). --bare creates only a pyproject.toml.

Timings, and the Python and package versions, will differ on your machine and in your month. Open pyproject.toml again: uv add wrote numpy>=2.5.4 and pandas>=3.0.6 into dependencies, a range that says what the code needs, while uv.lock records the exact versions of all four packages (including the two you never asked for). What to look for

  • Six packages were resolved but four installed. The lock file covers every platform, so it includes the project itself and tzdata (needed only on some systems, such as Windows), while your machine installs just what it needs. Read the + lines to see exactly what arrived.
  • uv tree shows why a package is present: six is there only because python-dateutil needs it, and pandas needs that.
  • uv run uses the project's environment without activating it, so a script run this way does not depend on which shell you opened.

Common pitfalls

  • A range in pyproject.toml is not a pin. Reproducibility comes from the lock file; share both.
  • A lock file does not pin your hardware. GPU drivers, CUDA versions and the operating system sit outside it; record them in the run record as well.
  • Do not mix pip install into a uv-managed environment for project dependencies: the lock file will not know about it. Use uv add, or uv pip install for throwaway experiments.
  • Mixing tools makes bugs hard to trace. Pick one per project and say which in the README.

Arrays, tables and plots

These three do almost all the day-to-day work of looking at numbers.

NumPy

Install: uv add numpy (or pip install numpy) · Alternatives: PyTorch tensors and JAX arrays (the same ideas on GPUs, with automatic differentiation), CuPy (NumPy on a GPU) · Chapters: 2, 5, 6, 7

NumPy gives Python the ndarray: a block of same-typed numbers in memory plus a description (shape, dtype, strides) of how to read it as a grid. Almost every numerical Python tool, including PyTorch and pandas, is built on or modelled after it, so the habits transfer. Chapter 2 develops the model; this exercise puts three of its traps on one screen.

10-minute guided exercise

Run three small experiments on views, broadcasting and float precision. Predict each output before you run it.

import numpy as np
x = np.arange(6, dtype=np.float32).reshape(2, 3)
print("shape", x.shape, "dtype", x.dtype, "strides", x.strides, "bytes", x.nbytes)
print("transpose shares memory:", np.shares_memory(x, x.T), "| strides", x.T.strides, "| contiguous:", x.T.flags["C_CONTIGUOUS"])

# the classic silent broadcasting bug: (n,) minus (n,1) is an (n, n) matrix, not an error
pred, target = np.array([1.0, 2.0, 3.0]), np.array([[1.0], [2.0], [4.0]])
err = pred - target
print("pred", pred.shape, "- target", target.shape, "->", err.shape)
print("wrong mean squared error:", (err ** 2).mean(), "| right:", ((pred - target.ravel()) ** 2).mean())

# float32 versus float64: the same sum, different answers
big = np.full(10_000_000, 0.1, dtype=np.float32)
print("float32 sum", big.sum(), "| running total (cumsum) in float32", np.cumsum(big)[-1], "| float64 sum", big.astype(np.float64).sum())
shape (2, 3) dtype float32 strides (12, 4) bytes 24
transpose shares memory: True | strides (4, 12) | contiguous: False
pred (3,) - target (3, 1) -> (3, 3)
wrong mean squared error: 2.3333333333333335 | right: 0.3333333333333333
float32 sum 1.0000001e+06 | running total (cumsum) in float32 1.087937e+06 | float64 sum 1000000.0149011612

What to look for

  • Strides (12, 4) mean "move 12 bytes to the next row, 4 to the next column" (a float32 is 4 bytes, a row has three). The transpose has strides (4, 12) and shares the same memory: no data was copied, only the description changed, which is why x.T is instant and also why it is no longer contiguous (chapter 2, views and memory layout).
  • (3,) minus (3, 1) silently gave a 3 × 3 matrix, and the "wrong" mean squared error is seven times the right one (2.33 against 0.33). Broadcasting did what its rules say; the shapes were wrong for what you meant. Printing .shape of intermediate results is the cheapest debugging tool in numerical code.
  • The three float sums disagree. NumPy's sum uses pairwise summation, which kept the float32 total at 1,000,000.1 (the float64 answer is 1,000,000.0149: the tiny difference is the float32 representation of 0.1 itself). A running total (cumsum) accumulates rounding error step by step and ended at 1,087,937, almost 9% too high. Precision is a property of the algorithm as well as the type (chapter 11).
  • Also try np.dot against a Python loop for two vectors of a million numbers, with time.perf_counter, and see the vectorisation gap of chapter 1 on your own machine.

Common pitfalls

  • Views versus copies. Slicing gives a view; assigning to it changes the original. Use .copy() when you mean a copy, and np.shares_memory when you are unsure.
  • Integer and float surprises. An integer array stays integer: np.array([1, 2]) / 2 is float, but assigning 0.5 into an integer array truncates it.
  • Axis confusion. sum(axis=0) collapses the rows and leaves one value per column; check the shape of the result against what you expected.
  • Seed a generator, not the global state: rng = np.random.default_rng(0) and pass rng around (chapter 4).

pandas & DuckDB

Install: uv add pandas duckdb · Alternatives: Polars (a fast dataframe library with a different API), SQLite (data toolbox), a notebook plus plain SQL on a real database · Chapters: 3

pandas holds a table in memory as a DataFrame and gives you filtering, joining and grouping as method calls. DuckDB is a database that runs inside your Python process (no server) and can query CSV and Parquet files with SQL directly, and it can hand its result back as a DataFrame. They overlap deliberately: the same question can be asked either way, which is a useful way to check yourself. Chapter 3 shows the same pipeline in SQL's logical order and in pandas.

10-minute guided exercise

Make a small ticket table, ask the same question in both tools, and then ask the question that matters. First generate 20,000 simulated support tickets with a seed. This is the data of the experiment-design studio, with each ticket randomly assigned to the old or new assistant.

What to look for

  • The join kept 20,000 rows. validate="many_to_one" would have raised an error if customers.csv had duplicate ids, which would silently multiply rows. Always compare row counts before and after a join (chapter 3).
  • The two tools agree (same numbers: True), but only because the question was the same. Writing it twice in different languages is a cheap way to catch a mistake in either.
  • The last query is the finding. 3,965 customers appear in both arms: the assignment in the generator was random per ticket, not per customer, so customers saw both versions. In a real experiment this contaminates the arms and breaks the independence assumption of the standard error (Studio 1, stage 5). No statistics were needed to find it, only one grouping query and the habit of asking "what is the unit?".
  • The per-tier differences (about 1 point) are the sort of number that looks like an effect and is not yet one; chapter 15 and the studio show how to put an interval on it.

Common pitfalls

  • Joins that multiply or drop rows (duplicate keys, how="inner" silently dropping unmatched rows). Count, and use validate=.
  • Booleans and missing values. A mean over a boolean column is a rate; a missing value is skipped by mean but not by count(*). Be clear which one you computed.
  • pandas copies a lot. A 5 GB file may need 15 GB of memory. For larger files, let DuckDB (or Polars) read only the columns and rows it needs.
  • Version changes bite. pandas 3 changed some defaults (string handling and copy behaviour) compared with 2.x; if old code behaves differently, read the release notes before you blame your data.

matplotlib

Install: uv add matplotlib · Alternatives: seaborn (a statistics layer over matplotlib), plotly and Altair (interactive), a plain print of the numbers · Chapters: 3, 12, 15

matplotlib is the standard Python plotting library. The skill it teaches is not the syntax but the habit: plot the data before you trust a number computed from it, and make each plot answer one question. This exercise redraws the offline comparison from the experiment-design studio: the bootstrap distribution of a 2.4-point accuracy gain on 500 questions.

10-minute guided exercise

import matplotlib
matplotlib.use("Agg")                      # draw to a file; no window needed
import matplotlib.pyplot as plt
import numpy as np
rng = np.random.default_rng(101)
n, only_a, only_b = 500, 14, 26
d = np.r_[np.ones(only_b), -np.ones(only_a), np.zeros(n - only_a - only_b)]      # per-question difference, B minus A
boot = d[rng.integers(0, n, (10_000, n))].mean(axis=1) * 100
lo, hi = np.percentile(boot, [2.5, 97.5])
fig, ax = plt.subplots(figsize=(6, 3.2), dpi=120)
ax.hist(boot, bins=40, color="#7aa2f7", edgecolor="white")
ax.axvline(0, color="black", lw=1, label="no difference")
ax.axvline(d.mean() * 100, color="#e0af68", lw=2, label=f"observed {d.mean() * 100:+.1f} points")
ax.axvspan(lo, hi, color="#9ece6a", alpha=0.25, label=f"95% interval [{lo:+.1f}, {hi:+.1f}]")
ax.set_xlabel("accuracy gain of B over A (percentage points)"); ax.set_ylabel("bootstrap resamples")
ax.set_title("Paired bootstrap on 500 questions"); ax.legend(fontsize=7, loc="upper left")
fig.tight_layout(); fig.savefig("gain.png")
import os
print(f"interval [{lo:+.2f}, {hi:+.2f}]; wrote gain.png ({os.path.getsize('gain.png') / 1024:.0f} KB), size {fig.get_size_inches()} in at {fig.dpi:.0f} dpi")
interval [+0.00, +4.80]; wrote gain.png (26 KB), size [6.  3.2] in at 120 dpi

Open gain.png (the first run may also print a notice that matplotlib is building its font cache; that is harmless). I looked at the image it produced: a histogram centred on +2.4 with a shaded band that starts exactly at the zero line.

What to look for

  • The shaded band touches zero. The plot says in one glance what a sentence takes longer to say: the interval just reaches "no difference" (chapter 15).
  • The histogram is lumpy, with a comb-like pattern. The bootstrap gains are exact multiples of 0.2 points (one question out of 500), and 40 bins do not line up with that grid, so some bins catch two values and some one. The lumps are an artefact of the bins, not a feature of the data. Try bins=np.arange(-2.6, 7.4, 0.2) to align them. Whenever a plot of discrete values looks strange, suspect the binning first.
  • Every element is labelled: a title, axis labels with units, and a legend that says what each line means. A plot without those has not yet answered a question.
  • Also try plotting the same numbers as an interval with a point estimate (an error bar, via ax.errorbar) for several systems side by side; this is how results tables should be drawn.

Common pitfalls

  • No display on a server or in a script. Select a non-interactive backend (matplotlib.use("Agg")) and save to a file. In a notebook, plots appear inline automatically.
  • The two interfaces. plt.plot(...) (the state machine) and fig, ax = plt.subplots() (explicit objects) both exist; use the explicit one as soon as there is more than one panel.
  • Truncated axes and dual axes mislead. A bar chart that starts at 70% makes a one-point gap look huge. Show the interval, start bars at zero, or use a dot plot.
  • Save the code with the figure. A plot you cannot regenerate is a screenshot, not a result.

Colab & Kaggle notebooks

Nothing to install: a Google account for Colab (colab.research.google.com) and a Kaggle account for Kaggle Notebooks (kaggle.com) · Alternatives: a GPU rented by the hour from a specialist or large cloud (Studio 2 budgets one), a university cluster, a local GPU · Chapters: 17

Illustrative card: I did not run anything on these services. Both give you a hosted notebook with a GPU you can borrow, which is enough to feel the difference between a CPU and a GPU, to run the labs' ideas at a larger scale, and to fine-tune small models. Both come with limits that are not guaranteed.

State of play, October 2026

Colab's own FAQ (read on 14 October 2026) says free-tier usage limits are not published because they vary over time, that notebooks run for at most 12 hours depending on availability and idle runtimes time out, that the GPU types on offer change and that access to the expensive ones is heavily restricted on the free tier; paid plans work on a balance of compute units, and when it runs out you are returned to free-tier limits. For Kaggle I could not read the official documentation; secondary sources describe a quota of about 30 GPU-hours a week with a choice between a single P100 or two T4 GPUs, but they disagree on the length of a session (9 or 12 hours). Treat all of this as a snapshot: look at the account's own settings page and the "usage" indicator before you plan anything long.

10-minute guided exercise (illustrative)

Find out what you were given, then measure it against chapter 17. In a new notebook with a GPU runtime selected (Colab: Runtime → Change runtime type; Kaggle: Settings → Accelerator), run these cells. The first lines are shell commands, marked with ! in a notebook.

!nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv
import torch
print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))
import time, torch
def best_time(fn, repeats=5):
    fn(); torch.cuda.synchronize()          # warm up, then wait for the GPU (it runs asynchronously)
    times = []
    for _ in range(repeats):
        t = time.perf_counter(); fn(); torch.cuda.synchronize(); times.append(time.perf_counter() - t)
    return min(times)
n = 4096
for dtype in (torch.float32, torch.bfloat16):
    a = torch.randn(n, n, device="cuda", dtype=dtype); b = torch.randn(n, n, device="cuda", dtype=dtype)
    t = best_time(lambda: a @ b)
    print(dtype, f"{2 * n**3 / t / 1e12:.1f} TFLOP/s")

I am not pasting output because I did not run it; the shape of the result is what to check. What to look for

  • Which GPU and how much memory. The memory number is what decides which models fit (chapter 17: 2 bytes per parameter to run a model in bf16, 16 to train it with Adam). Do the sum for the model you wanted to use before you start the download.
  • bf16 against float32. On a card with tensor cores the bf16 line should be several times faster; some older free-tier cards do not support bf16 well, and that is a fact about the card, not your code. Compare either number with the card's datasheet peak and say what fraction of it you reached.
  • The first call is slow (initialisation, warm-up), which is why the benchmark warms up and synchronises. Timing GPU code without torch.cuda.synchronize() times only the launch.

Common pitfalls

  • The session ends and takes your state with it. Save checkpoints and outputs to persistent storage (Drive on Colab, the output folder or a dataset on Kaggle) from the first minute, not at the end.
  • Idle sessions still use quota. Close the notebook or disconnect the runtime when you stop; a forgotten GPU session is the most common way to lose a week's allowance.
  • Do not put credentials in a shared notebook. Use each service's secrets feature; a notebook you share or publish includes its code and often its outputs.
  • These services are for learning and small experiments. A run that must finish, or that handles private data, belongs on hardware whose terms you have read.

arXiv, Semantic Scholar & Papers with Code

Nothing to install: arxiv.org, semanticscholar.org and the Hugging Face Papers pages in a browser; both APIs below need only Python's standard library · Alternatives: Google Scholar, OpenReview (reviews and discussion for many conference papers), a reference manager such as Zotero, a reading list in a plain text file · Chapters: 16

Most machine learning papers appear first on arXiv, a free preprint server: a paper there has usually not been peer reviewed, and may have several versions. Semantic Scholar is a search and citation index that tells you what a paper cites and who cites it. A third kind of tool links papers to code. Chapter 16 teaches how to read a paper; this card is about finding the right one, the right version, and what has been said about it since.

State of play, October 2026

Papers with Code, the site that linked papers to code and leaderboards, was run by Meta and shut down in July 2025; its address now redirects to Hugging Face's Trending Papers page, and the old leaderboards were not carried over. I read this in secondary reports (a news article and two summaries), not in an announcement I could fetch, so the exact date varies by source. Community copies of the old data exist as static archives, with nothing added after July 2025. For code that goes with a paper, check the paper's own abstract page and the authors' repository, and use Hugging Face's paper pages and model cards as a second route.

10-minute guided exercise

1. Look papers up by id and read the version history. The arXiv API is a plain web address that returns an Atom (XML) feed; the manual asks for a pause of about three seconds between repeated requests, and the script respects it. This uses only the standard library.

"""Look papers up by arXiv id: title, versions, dates and the authors' own comment. Standard library only."""
import time, urllib.request, xml.etree.ElementTree as ET
NS = {"a": "http://www.w3.org/2005/Atom", "x": "http://arxiv.org/schemas/atom"}
ids = ["1706.03762", "2407.21783", "2106.09685"]
url = "https://export.arxiv.org/api/query?id_list=" + ",".join(ids) + "&max_results=10"
with urllib.request.urlopen(url, timeout=30) as r:
    feed = ET.fromstring(r.read())
for e in feed.findall("a:entry", NS):
    title = " ".join(e.find("a:title", NS).text.split())
    version = e.find("a:id", NS).text.rsplit("v", 1)[-1]

"""Semantic Scholar Graph API: counts change daily, and the unauthenticated tier is rate-limited, so retry politely."""
import json, time, urllib.error, urllib.request
def get(url, tries=5):
    for i in range(tries):
        try:
            with urllib.request.urlopen(url, timeout=30) as r:
                return json.load(r)
        except urllib.error.HTTPError as e:
            if e.code != 429: raise
            wait = 2 ** (i + 1)
            print(f"  429 too many requests; waiting {wait}s")
            time.sleep(wait)
    raise SystemExit("gave up: ask for a free API key")

What to look for

  • Versions matter. The Transformer paper is on its seventh version (posted in 2017, updated in August 2023); the LoRA paper's author comment says its second version "includes better baselines, experiments on GLUE, and more on adapter latency". A number you read in a blog post may come from a different version than the one you have open. Cite the version you read.
  • The "authors" field can be long. The Llama 3 paper lists 561 authors in the arXiv metadata. A summary of what the paper claims is not a reason to skip its evaluation section, and a long author list is not evidence of quality (chapter 16: checking whether a claim is believable).
  • Citation counts are a popularity signal, not a correctness signal. The counts printed above (about 24,000 for LoRA and 172,000 for Adam on 14 October 2026) will have changed by the time you run it. They tell you which papers a field relies on, which is a reason to read them closely and to look for the follow-up papers that test them.
  • Next steps: open the paper's arXiv page and check the comment and subject fields; on Semantic Scholar page through the citations of an important paper sorted by year to find replications and critiques; for any claim you plan to rely on, apply the checks of chapter 16 before you cite it.

Common pitfalls

  • A preprint is not a verdict. It may be wrong, withdrawn or substantially revised. Look at the version history, and at whether the claim was later tested by others.
  • Being polite to the APIs. Cache results, keep to a few requests per few seconds, and for anything larger request an API key (Semantic Scholar) or the bulk data options (arXiv) instead of hammering the endpoint.
  • Search terms. The arXiv API's search_query uses field prefixes such as ti: (title), au: (author) and abs: (abstract) combined with AND and OR; a plain-word query can return surprising results, so test it in the browser first.
  • Leaderboards decay. A "state of the art" claim is dated the day it was made; the site that once collected them for you no longer does. Record the date with any claim you copy into notes.

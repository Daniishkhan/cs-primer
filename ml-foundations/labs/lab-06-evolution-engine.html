Lab 6: A Tiny Evolution Engine

Some good programs are easier to find than to design. In this lab you build a small machine that finds them. It keeps a few short Python functions, changes them at random, scores each change and keeps the better ones. No language model is involved. The only things doing the work are a syntax tree, a scorer and a notebook of everything tried.

Why this lab matters

A search loop over programs has the same three parts every time: something that proposes a change, something that judges it, and something that remembers. Most of the engineering sits in the judge and the memory. Proposing is the easy part, and later courses swap in smarter proposers without touching the rest.

You build all three parts here, with the simplest proposer possible: random edits to the program's syntax tree. When you meet a system where a language model writes the changes, you will already know where the loop's weight sits, and what must never be trusted. A later lab, A Mini FunSearch, plugs a stand-in for a model into the same shape.

Pure Python, deterministic, about a second

Standard library only (ast, hashlib, json, random), Python 3.9 or newer. Every random number comes from a random.Random that you pass around. A failure prints its seed, and python3 check.py solution 3 12 replays milestone 3 on seed 12 only. Nothing touches the network or the clock. The full check takes about a second.

What you'll build

You need three ideas from earlier chapters. Chapter 20 covers functions, closures, dataclasses and exceptions. Chapter 21 covers reading a program as a tree with ast, editing the tree, and running it with compile and exec. Chapter 22 covers budgets, caching by hash, JSON-lines logs and seeded randomness. If a term below is unfamiliar, the matching chapter defines it.

The problem is online bin packing. Items arrive one at a time, and each must go into a bin straight away. Every bin holds 100 units. Item sizes run from 20 to 60. A program decides which bin gets each item, and the aim is to use as few bins as possible.

  1. Check and compile: validate and make_heuristic turn a source string into a function, or refuse it with Rejected.
  2. Pack and score: pack and score. Every outcome, including a crash or an endless loop, becomes a number.
  3. Mutate: three edits to the syntax tree, and mutate to choose between them. Seeded, and always valid.
  4. Remember: canonical_hash and an Archive that never stores a program twice, keeps a JSON-lines log and knows the best.
  5. Evolve: evolve ties it together, then you test the winner on instances the search never saw.

The problem, by hand

A heuristic here is a function priority(item, rem). For each open bin that can still hold the item, it is called with the item's size and the bin's remaining space rem. The item goes to the bin with the highest score. If no bin fits, a new bin opens. Ties go to the earliest bin.

Two classic heuristics fit in one line. First fit returns 0 for every bin, so every score ties and the earliest bin wins. Best fit returns -(rem - item), which is minus the space left over after the item goes in. The tightest fit scores highest.

Take the items 20, 30, 60, 20, 50. Both heuristics put 20 and 30 in the first bin (50 left) and 60 in a second bin (40 left). The fourth item, 20, fits in either. First fit takes bin 1, leaving 30. The last item, 50, then fits nowhere, so first fit opens a third bin. Best fit sees leftovers of 30 and 20, picks bin 2 (the tighter fit, 20 left over) and keeps bin 1 at 50. Item 50 fits there exactly. Best fit uses 2 bins and first fit uses 3.

The score of a heuristic is the mean number of bins over a set of instances. Lower is better. No packing, online or not, can use fewer than the lower bound: the total size divided by 100, rounded up. It tells you how far from perfect any answer is.

Analogy: a baker's notebook

A baker wants a better loaf. Each day she changes her recipe a little: a bit more salt, ten minutes less in the oven. She bakes the new loaf, tastes it and writes the recipe and the verdict in a notebook. She never bakes a recipe that is already in the book. At the end of the week she starts from the best loaves and changes those.

The mutation is the small change. The tasting is the score. The notebook is the archive. The best loaves she keeps are the elites.

Where it breaks down: the baker knows why salt matters, so her changes are not random. The loop in this lab has no idea why a change helps. It only learns that a change did.

Milestone 1: check and compile a candidate

A candidate is a string of Python that nobody has read. Running it with exec would hand it your whole machine. The program could import os, open files or loop forever. A real evolution system makes thousands of candidates, so you cannot read them all. The code must protect itself in three layers.

  1. Look before running. Parse the source into a tree and walk every node. Accept only node types on an allow-list, such as Return, BinOp, Compare and Constant. Anything else, like Import, Attribute or Lambda, raises Rejected.
  2. Run with almost nothing in scope. Pass exec a namespace whose builtins hold only abs, min and max. A name like len then raises NameError when called.
  3. Give it fuel. A fuel budget is a step counter. The given instrument function edits the tree so the function, and every while body, calls _tick() first. Each tick spends one unit. When the budget is gone, OutOfFuel stops the program.

Here is what instrument does to best fit. You do not write this. You call it.

def priority(item, rem):
    _tick()
    return -(rem - item)

You write two functions. validate(src) returns the parsed tree or raises Rejected. make_heuristic(src, fuel) validates, instruments and compiles the source, runs the definition in the restricted namespace and returns the priority function.

A teaching sandbox, not a security boundary

These three layers stop accidents and silly programs. They are not strong enough for code written by an attacker, because Python has many ways around a clever tree check. Real systems also run candidates in a separate process with memory and time limits. Chapter 22 shows how.

def validate(src):
    if len(src) > MAX_CHARS:
        raise Rejected("source too long")
    try:
        tree = ast.parse(src)
    except (SyntaxError, ValueError, RecursionError):
        raise Rejected("syntax error")
    body = tree.body
    if len(body) != 1 or not isinstance(body[0], ast.FunctionDef):
        raise Rejected("expected exactly one function")
    fn = body[0]
    params = [a.arg for a in fn.args.args]
    a = fn.args
    plain = not (a.defaults or a.vararg or a.kwarg or a.kwonlyargs)
    if fn.name != "priority" or params != ["item", "rem"] or not plain:
        raise Rejected("must be exactly def priority(item, rem)")
    nodes = list(ast.walk(tree))
    if len(nodes) > MAX_NODES:
        raise Rejected("too many nodes")
    for node in nodes:
        if not isinstance(node, ALLOWED_NODES):
            raise Rejected(f"{type(node).__name__} is not allowed")
        if isinstance(node, ast.Name) and node.id.startswith("_"):
            raise Rejected(f"name {node.id!r} is not allowed")
        if isinstance(node, ast.Call):
            ok = isinstance(node.func, ast.Name)
            if not ok or node.func.id not in SAFE_CALLS:
                raise Rejected("only abs, min and max may be called")
    return tree


def make_heuristic(src, fuel):
    tree = instrument(validate(src))
    code = compile(tree, "<candidate>", "exec")
    builtins = {"abs": abs, "min": min, "max": max}
    namespace = {"__builtins__": builtins, "_tick": fuel.tick}
    exec(code, namespace)
    return namespace["priority"]

Milestone 2: every outcome becomes a number

Random edits make bad programs all the time. Some divide by zero. Some loop for ever. Some return a string. Your loop must not stop for any of them. So the scorer never raises. It turns every failure into a penalty, a fixed score of 10,000 bins that loses to every working program.

The penalty is a finite number on purpose. You can compare it, average it and sort it like any other score. Infinity or None would need special cases everywhere downstream.

pack(priority, items) is the packing loop from the problem section. It returns the number of bins. If priority returns something that is not a finite int or float, such as nan, a string or True, pack raises ValueError. Python treats True as the number 1, so check the exact type.

score(src, instances, fuel_budget=FUEL) makes a fresh Fuel, compiles the source, packs every instance and returns the mean bin count. Fuel runs out while packing, not while compiling, so one try must wrap both steps. Catch Exception, and return PENALTY.

Common misconception

"Catching every exception hides bugs." Here it is the whole point. The candidate is untrusted, so any failure in it is data about the candidate, not a bug in your loop. The bugs to worry about are in your code, and the check tests those with normal inputs where a crash would show.

Solution spoiler 
def pack(priority, items):
    bins = []
    for item in items:
        best = None
        best_p = None
        for i, rem in enumerate(bins):
            if rem < item:
                continue
            p = priority(item, rem)
            if type(p) not in (int, float) or not math.isfinite(p):
                raise ValueError(f"priority returned {p!r}")
            if best_p is None or p > best_p:
                best = i
                best_p = p
        if best is None:
            bins.append(CAP - item)
        else:
            bins[best] -= item
    return len(bins)


def score(src, instances, fuel_budget=FUEL):
    fuel = Fuel(fuel_budget)
    try:
        fn = make_heuristic(src, fuel)
        counts = [pack(fn, items) for items in instances]
    except Exception:
        return PENALTY
    return sum(counts) / len(counts)

Milestone 3: mutate the syntax tree

A mutation is a small random change to a program. Changing the text, say by flipping a character, would almost always give a syntax error. Changing the tree keeps the program well formed, because you only swap one valid piece for another.

The seed program of this lab is the following. It is worst fit: it prefers the bin with the most space left, which is the opposite of what you want.

def priority(item, rem):
    gap = rem - item
    return gap * 1

You write three edits. Each takes a tree and an rng and changes the tree in place. It returns True after a change, or False when the tree has nothing to change.

  • perturb_constant adds one of NUDGES to a random number. Example: gap * 1 becomes gap * -3.
  • swap_operator replaces one of + - * with a different one. Example: gap * 1 becomes gap + 1.
  • wrap_expression picks a return or an assignment. It wraps the value in abs(...), or squares it as e * e. Example: gap * 1 becomes abs(gap * 1).

Then mutate(src, rng) chooses an edit with rng.choice(OPERATORS), applies it to the parsed tree and unparses the result. The edit may do nothing, or give the same text, or break a rule such as the node limit. So mutate tries up to ten times and returns the first result that differs from the input and passes validate. If every try fails, it returns the input.

Why squaring has a limit

Squaring copies the expression, so the tree doubles in size. Squaring again and again over many generations grows it past a billion nodes, and the reference solution once hung for exactly this reason. That is why wrap_expression only squares small expressions (at most SQUARE_LIMIT nodes) and uses abs otherwise. A program-editing loop needs size limits, as well as a validity check.

Determinism matters here. Take every random choice from the rng argument, never from the global random module. Then the same program and the same rng state always give the same child, and a whole run can be replayed from one seed.

  • Use copy.deepcopy for the second copy in e * e. Sharing one node twice in a tree causes confusing bugs.

def perturb_constant(tree, rng):
    consts = [n for n in ast.walk(tree)
              if isinstance(n, ast.Constant) and type(n.value) in (int, float)]
    if not consts:
        return False
    node = rng.choice(consts)
    node.value = node.value + rng.choice(NUDGES)
    return True


def swap_operator(tree, rng):
    sites = [n for n in ast.walk(tree)
             if isinstance(n, ast.BinOp) and isinstance(n.op, ARITH)]
    if not sites:
        return False
    node = rng.choice(sites)
    others = [op for op in ARITH if not isinstance(node.op, op)]
    node.op = rng.choice(others)()
    return True


def wrap_expression(tree, rng):
    sites = [n for n in ast.walk(tree)
             if isinstance(n, (ast.Return, ast.Assign))]
    if not sites:
        return False
    node = rng.choice(sites)
    small = len(list(ast.walk(node.value))) <= SQUARE_LIMIT
    if rng.random() < 0.5 or not small:
        node.value = ast.Call(ast.Name("abs", ast.Load()), [node.value], [])
    else:
        twin = copy.deepcopy(node.value)
        node.value = ast.BinOp(node.value, ast.Mult(), twin)
    return True


def mutate(src, rng, attempts=10):
    base = ast.unparse(ast.parse(src))
    for _ in range(attempts):
        tree = ast.parse(base)
        operator = rng.choice(OPERATORS)
        if not operator(tree, rng):
            continue
        ast.fix_missing_locations(tree)
        new = ast.unparse(tree)
        if new == base:
            continue
        try:
            validate(new)
        except Rejected:
            continue
        return new
    return base

Milestone 4: remember everything once

Mutation repeats itself. The seed above has only a handful of places to edit, so many mutants are the same program reached by different edits. Scoring costs far more than mutating, so each distinct program should be scored once. To spot a repeat you need a name for a program that does not depend on how it is written.

A canonical form is one standard text for programs that mean the same. ast.unparse(ast.parse(src)) gives one: it drops comments, fixes spacing and normalises brackets. A hash is a short fingerprint of a text. Equal texts always give equal hashes, and different texts almost never do. So canonical_hash(src) is the Secure Hash Algorithm (SHA) 256 hash of the canonical form, cut to its first 12 hex digits.

These two sources get the same hash, b9190cb8d219, even though they look different:

def priority(item, rem):
    return -(rem - item)

def priority(item,rem):
  # best fit
  return   -(rem-item)

The Archive is a dataclass holding every program tried. It has an entries dict from hash to Entry (given: hash, parent hash, score, canonical source), and a list of lines. Its methods are:

  • add(src, parent, score) stores a new program and returns True. If the hash is already there it stores nothing and returns False. A new entry also adds one JSON line, and appends it to the file at self.path when a path was given.
  • best() returns the entry with the lowest score. Ties go to the shorter source, then to the smaller hash, so the answer never depends on insertion order.

The log is JSON lines: one JSON object per line, appended as events happen. Each line is complete on its own, so a crash loses at most the last line, and you can read the file with grep or replay it into a new archive. Because every entry names its parent, the log is also a family tree. You can follow the best program back to the seed.

{"hash": "01d9dd32d96c", "parent": "", "score": 90.625, "src": "def priority(item, rem):\n    gap = rem - item\n    return gap * 1"}

Solution spoiler 
def canonical_hash(src):
    text = ast.unparse(ast.parse(src))
    return hashlib.sha256(text.encode()).hexdigest()[:12]


@dataclass
class Archive:
    path: str = ""
    entries: dict = field(default_factory=dict)
    lines: list = field(default_factory=list)

    def add(self, src, parent, score):
        h = canonical_hash(src)
        if h in self.entries:
            return False
        canon = ast.unparse(ast.parse(src))
        entry = Entry(h, parent, score, canon)
        self.entries[h] = entry
        line = json.dumps({"hash": h, "parent": parent,
                           "score": score, "src": canon})
        self.lines.append(line)
        if self.path:
            with open(self.path, "a") as f:
                f.write(line + "\n")
        return True
    def best(self):
        if not self.entries:
            return None
        return min(self.entries.values(),
                   key=lambda e: (e.score, len(e.src), e.hash))

Milestone 5: the loop, and an honest test

Now connect the parts. evolve(seed, generations, pop_size) works like this:

  1. Make rng = random.Random(seed) and the training instances. Score the seed program, add it to the archive with parent "", and make it the whole population.
  2. For each generation, make pop_size - 2 children. For each, pick a parent with tournament, then call mutate.
  3. If the child is already in the archive, skip it. Otherwise score it, add it, and keep its entry.
  4. The next population is the two best of the old one plus the new children, sorted best first and cut to pop_size.

Tournament selection picks three programs at random and takes the best of them. A good program is likely to win, but a middling one sometimes does, so the population does not collapse onto one lineage too soon. Elitism keeps the best two programs unchanged from one generation to the next. Without it a lucky mutation could be lost, and the best score could get worse.

The search sees only 8 training instances (seeds 0 to 7). Its result is judged on 20 held-out instances (seeds 100 to 119) that it never touched. Without this step, a program that merely fits the training items would look as good as one that packs well in general.

Reproducibility is part of the contract. The check runs each seed twice and demands the same log, line for line. One rng, a fixed tie-break and no iteration over a set are enough.

def evolve(seed, generations, pop_size, train_seeds=TRAIN_SEEDS,
           path=""):
    rng = random.Random(seed)
    train = make_instances(train_seeds)
    archive = Archive(path)
    first = ast.unparse(ast.parse(SEED_SRC))
    archive.add(first, "", score(first, train))
    population = [archive.best()]
    for _ in range(generations):
        children = []
        for _ in range(pop_size - ELITES):
            parent = tournament(population, rng)
            child = mutate(parent.src, rng)
            if child in archive:
                continue
            archive.add(child, parent.hash, score(child, train))
            children.append(archive.entries[canonical_hash(child)])
        pool = population[:ELITES] + children
        pool.sort(key=lambda e: (e.score, len(e.src), e.hash))
        population = pool[:pop_size]
    return archive

What the loop actually finds

Run the reference solution with seed 0. The archive ends with 62 programs. The loop made 300 proposals (30 generations of 10 children), so about four in five were repeats of something already in the notebook and cost nothing to skip.

The best program's family tree has four steps. The seed scores 90.625 bins on the training set. Its first child, gap * -3, scores 87.75, and the next two children only change the constant again (to -7, then -6). All three score 87.75 because multiplying by any negative number puts the bins in the same order as best fit does. This is neutral drift: changes that do not alter the score, which let the search wander along a flat ridge.

What blind mutation achieves

The loop starts worse than first fit, beats first fit by 0.15 bins on held-out instances, and matches best fit. It does not beat best fit, and ten times as many generations did not change that in a trial run. With three small edits, the programs it can reach are variations of "score by the gap, scaled", and best fit is the best of those. To do better the loop needs edits that add new ideas, such as "if the gap is under 5, treat it as a perfect fit". Those need richer mutation than flipping a constant, and that is where a language model earns its place as a proposer. The Mini FunSearch lab uses richer edits and the same loop, and chapter 19 of the open-ended course explains the design.

Going further

  • A rule-inserting edit. Add a fourth operator that inserts if gap < 5: return 100 after the first assignment. Allow If and comparisons in your mutants, and see whether the loop can now beat best fit on held-out instances. This is the step that the next lab takes.
  • Crossover. Write combine(a, b, rng) that copies one statement from a second parent into the first. Does it help, or does it only add invalid programs?
  • Replay the log. Read an archive file and rebuild the best program's family tree. Print each step as a one-line diff of the source.
  • Count the waste. Record how many proposals were duplicates, how many were rejected, and how many scored the penalty. Which edit makes the most waste?
  • A size penalty. Change the ordering so that, among equal scores, shorter source wins. Then add a small cost per node to the score. What happens to neutral drift?
  • Parallel scoring. Score a generation's children in separate processes, with a time limit, using chapter 22. Check that the log is still identical for the same seed.
  • A new problem. Replace bin packing with another task whose answer is a small function, such as ordering items for a knapsack, and reuse every other part.

Systems connection

In this lab scoring one program takes a few milliseconds. In a real system, scoring may take minutes on a cluster, and then the archive is a cost saver. Every duplicate that the hash catches saves a full evaluation. The same reasoning drives caching in build systems and in the candidate runner of chapter 22.

What you learned

  • A search loop over programs has a proposer, a judge and a memory. The judge must be total: every failure becomes a number.
  • Untrusted code needs three layers: an allow-list on the tree, a tiny set of builtins, and a fuel budget.
  • Edit the tree, not the text. Edits stay well formed, and every edit still needs a validity check and a size limit.
  • Hash the canonical form to avoid scoring a program twice. A JSON-lines log with parent hashes gives you a family tree for free.
  • Tournament selection spreads the pressure, elitism protects the best, and a held-out set shows whether the result is real.
  • Blind edits found best fit and stopped. Richer proposals are what get past that ceiling.

Check your understanding

A candidate program divides by zero. Your score returns 10,000 instead of raising. What is the main reason?

  1. Exceptions are slow in Python, so the loop would run too slowly
  2. A crash tells you the program is dangerous, so it should be deleted from the archive
  3. The loop has thousands of candidates to judge, and a failure in one should lose the comparison, not stop the run
  4. Python cannot recover after an uncaught ZeroDivisionError
The candidate is untrusted, so its failures are normal data. A big finite number lets the crashed program take part in sorting and averages and lose to everything that works. The first option is tempting but wrong: speed is not the issue, and Python recovers from a caught exception easily. The penalty program is still stored, so the loop does not try it again.

Two candidates differ only in a comment and in spacing. What happens in your loop?

  1. They have the same hash, so the second is skipped without being scored
  2. They have different hashes, so both are scored and the second wins ties
  3. They have the same hash, so both are scored but only one is logged
  4. They have different hashes, but add returns False for the second
ast.unparse drops comments and fixes spacing, so both give the same canonical text and the same hash. evolve checks the archive before scoring, so the second one costs nothing. Hashing the raw source instead would make the second option true and waste evaluations.

You delete elitism, so all 12 programs in each generation are new children. What is the most likely consequence?

  1. The run becomes faster and finds better programs
  2. The archive stops recording the best program
  3. Every program in the population becomes identical
  4. The best score in the population can get worse from one generation to the next
Most mutations do not help, so a generation made only of children may contain nothing as good as its parents. The population forgets its best. The archive still holds the best program ever seen, which is why the second option is wrong. Elitism protects the population, not the archive.

The best program scores 87.75 on the training instances, and 87.65 on 20 held-out instances. Why report the second number?

  1. Held-out instances are easier, so it makes the result look better
  2. The search chose its winner by training score, so that number can be flattered by luck; held-out instances were never used to choose
  3. The training score is always wrong because mutation changes the instances
  4. Held-out instances use a different capacity, so they test a wider problem
When you pick the best of many candidates by a score, the winner tends to be partly lucky on that score. A fresh set gives an honest estimate. Here the two numbers agree, because the heuristic is simple. In bigger searches they often do not. The held-out set is built the same way as the training set, so it is neither easier nor wider.

You run the loop for 300 generations and it still never beats best fit. Which change is most likely to help?

  1. A larger population of the same kind of programs
  2. More training instances
  3. An edit that can add new structure, such as an if rule for nearly full bins
  4. A smaller tournament size
The three edits can only reach programs that score by a scaled gap, and best fit is already the best of them. More search over that set cannot find something outside it. The population and tournament options only change how the same space is searched. More training instances change the evidence, not the set of programs that can be reached.

Someone replaces rng.choice(OPERATORS) in mutate with random.choice(OPERATORS), the global generator. The code still runs and finds good programs. What have they broken?

  1. Nothing that matters, since random choice is random either way
  2. Reproducibility: the same seed no longer gives the same run, so results cannot be replayed or compared
  3. Validity: mutants may now fail validate
  4. Fuel: programs may run for more steps
The global generator is not controlled by the seed you pass to evolve, so the run changes every time. You could not replay a surprising result or tell whether a code change helped. Validity and fuel do not depend on where the random numbers come from.

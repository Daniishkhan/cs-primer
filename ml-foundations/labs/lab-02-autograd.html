Lab 2: Build an Autograd Engine

Chapter 9 showed a short Value class that learned XOR, and you took its correctness on trust. In this lab you write the engine yourself, operation by operation, and then prove it right the way practitioners do: by comparing every gradient it produces against a numerical estimate computed from nothing but the forward pass. By the end it trains a small network to classify points into three groups, and you will know exactly what loss.backward() does when you call it in PyTorch.

Why this lab matters

Training any neural network, from this toy to a frontier language model, is "compute a loss, get its gradient with respect to every parameter, take a step". The gradient step is automatic differentiation, and the two ways it goes wrong are both silent: a wrong local derivative produces a model that trains badly rather than a crash, and a forgotten zero_grad produces gradients that are quietly the sum of several steps. Engineers who have built a tiny engine recognise both from the symptoms. Engineers who have not blame the learning rate.

The habit this lab installs is the gradient check: whenever you write or modify something that has a derivative (a custom layer, a loss, a new operation), differentiate it twice, once by your rules and once by finite differences, and demand agreement. It takes five lines and it catches most backward-pass bugs. The same check later guards backpropagation in A2, the optimisers lab and the custom losses of post-training.

Pure Python, deterministic, about a second

Standard library only (math and random), Python 3.9 or newer. Weights start from random.Random(seed), the random expressions in check.py are generated from seeds, and a failure prints its seed: python3 check.py solution 3 12 replays milestone 3 on seed 12 only. The independent oracle in check.py evaluates expressions on plain floats with math, never through your Value class, so a bug in your engine cannot hide behind a matching bug in the test. The full check takes about a second.

What you'll build

The design is the one in chapter 9, which follows Andrej Karpathy's micrograd (2020). A Value holds a number (data), the gradient of the final loss with respect to it (grad), the Values it was computed from (_parents), a label (_op) and a closure (_backward) that knows how to pass gradient to its parents. Notation: if L is the loss, v.grad holds ∂L/∂v once L.backward() has run.

  1. The Value class: addition, subtraction, multiplication, negation and the reflected forms (3 + v), recording the graph as it goes.
  2. The backward pass: a topological ordering of the graph, backward(), and the derivative rules for + and *, including a value used more than once.
  3. More operations and the gradient checker: division, powers, exp, log, tanh, relu, sigmoid; numerical_grad, autograd_grad and max_error.
  4. Training: zero_grad, sgd_step, mse_loss and train, then XOR and a line fit.
  5. Classification: a stable logsumexp, softmax and cross_entropy, and a three-class problem.

Milestone 1: the Value class, forward only

Start with the part that looks like ordinary arithmetic. The goal is that you can write a * b + a with Value objects and get a Value whose data is the right number. What makes it more than a wrapper is that every operation also records how its result was made, as _parents (a tuple of the operand Values, the very same objects, not copies) and _op (a short label). That record is the computation graph from chapter 9, built as a side effect of ordinary arithmetic. Nothing in this milestone differentiates anything; it only keeps the receipts that milestone 2 needs.

Python's operator overloading does the work. When Python sees a + b it calls a.__add__(b); when the left operand is a plain number, as in 3 + a, int.__add__ gives up and Python falls back to a.__radd__(3). So you need both. Operands may be plain numbers, so each method wraps a non-Value in Value(...) first, which also makes constants into graph nodes with no parents.

Four of the methods are one-liners built from the others, which is how you keep the number of derivative rules small: -a is a * -1, a - b is a + (-b), 3 - a is (-a) + 3, and 3 * a and 3 + a just swap operands. Only addition and multiplication will need their own backward rules.

Common misconception

"The graph is something you build before you compute." In this design there is no separate graph-building step: the graph is the trail of objects pointing at each other, created while the forward computation runs. That is why frameworks in this style are called define-by-run, and why a Python if or for in the middle of your model just works. Each forward pass builds a fresh graph, which also means each one costs memory (see milestone 4).

Milestone 2: the backward pass

Now teach each result how to send gradient back to the Values it came from. Recall the chain rule from chapter 8: if the loss L depends on out, and out depends on a parent a, then

∂L/∂a += (∂out/∂a) × (∂L/∂out)

The second factor, ∂L/∂out, is out.grad, which has to be complete before it is used. The first factor, the local derivative, depends only on the operation: for out = a + b it is 1 for both parents; for out = a * b it is b.data for a and a.data for b. Each operation stores this as a closure, out._backward, that adds the right quantity into each parent's grad.

Two details decide correctness. First, the update is +=, not =, because a Value can be used more than once. In a * a + a at a = 3, the leaf a is used three times and its derivative, 2a + 1 = 7, is the sum of the contributions from all three. Second, order: a node's gradient must be complete before it is passed to its parents, which means visiting children before parents. That is reverse topological order of the graph, and topo_order(root) computes the forward topological order (parents first, root last) so that backward() can walk it backwards.

Step through the smallest graph that shows both details: f = x × y + x at x = 2, y = 3, where x is used twice.

Step through

backward() on f = x * y + x at (2, 3)

  1. Forward pass. Building f computed p = x × y = 6 and f = p + x = 8, and recorded the parents of each node. Note that x has two outgoing edges: it is used in the product and in the sum.
  2. Seed the gradient. f.backward() sets f.grad = 1, because the derivative of f with respect to itself is 1. Everything else starts at 0.
  3. Through the addition. f = p + x has local derivatives 1 and 1, so both parents receive f.grad × 1: p.grad becomes 1 and x.grad becomes 1. That is only the first of x's two contributions.
  4. Through the multiplication. p = x × y has local derivatives y = 3 for x and x = 2 for y, each times p.grad = 1. So x.grad gets +3 on top of its 1 (the +=), ending at 4, and y.grad is 2.
  5. Check. By hand, ∂f/∂x = y + 1 = 4 and ∂f/∂y = x = 2. Central differences on the forward function agree to eleven digits. This comparison is the subject of milestone 3.

One more practical point. topo_order is usually written as a recursive depth-first search, and that is a trap here. Python limits recursion to about 1,000 frames, and a graph can be far deeper than any layer count suggests: an RNN unrolled over 5,000 steps, or a loop that accumulates a loss one term at a time, is one long chain. The check builds a chain of 5,000 multiplications. Write the search with an explicit stack (a list you push to and pop from) instead.

Hints try without first

  • In the closure, use other.data and self.data, not the Values themselves: you are multiplying numbers.

class Value:
    ...

    def __add__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data + other.data, (self, other), "+")

        def _backward():                 # milestone 2: d(a+b)/da = 1 and d(a+b)/db = 1
            self.grad += out.grad
            other.grad += out.grad
        out._backward = _backward
        return out

    def __mul__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data * other.data, (self, other), "*")

        def _backward():                 # milestone 2: d(ab)/da = b and d(ab)/db = a
            self.grad += other.data * out.grad
            other.grad += self.data * out.grad
        out._backward = _backward
        return out

    def backward(self):
        order = topo_order(self)
        self.grad = 1.0
        for node in reversed(order):
            node._backward()

def topo_order(root):
    """All Values reachable from root, parents before children, each exactly once, root last.

    Must handle a graph 10,000 nodes deep, so recurse with an explicit stack, not Python's call stack.
    """
    order, seen = [], set()
    stack = [(root, False)]
    while stack:
        node, expanded = stack.pop()
        if expanded:
            order.append(node)
            continue
        if id(node) in seen:
            continue
        seen.add(id(node))
        stack.append((node, True))              # emit this node after all its parents
        for p in node._parents:
            if id(p) not in seen:
                stack.append((p, False))
    return order

Milestone 3: more operations, and checking them

An engine with only + and * can express polynomials. Neural networks also need division (normalisation), powers (squared error), exp and log (softmax, cross-entropy), and nonlinearities. Each is a forward value plus a local derivative, and you have already seen the pattern:

OperationForwardLocal derivative (multiply by out.grad)
a ** n (n a plain number)ann an−1
a / ba · b−1nothing new: built from * and ** -1
expeaea (the result itself)
logln a (a > 0)1/a
tanhtanh a1 − tanh2 a
relumax(0, a)1 if a > 0, else 0
sigmoid1/(1 + e−a)σ(1 − σ), where σ is the result

Three edge cases are worth deciding deliberately. log of a non-positive number raises ValueError rather than returning a nan that surfaces five layers later. relu has a kink at 0 where the derivative does not exist (chapter 8); by convention it uses 0 there. And sigmoid must not overflow: math.exp(1000) raises OverflowError, so compute 1/(1 + exp(-x)) for x ≥ 0 and exp(x)/(1 + exp(x)) for x < 0, where the exponent is always at most 0.

The gradient checker

Now the tool that makes all of this trustworthy. A derivative is a slope, and a slope can be measured without any calculus rules: nudge the input up and down by a tiny step h and divide the change in output by the width of the nudge. This is the central difference:

f'(x) ≈ (f(x + h) − f(x − h)) / (2h)

Expanding f in a Taylor series, the f'' terms cancel and the error is about (h2/6) f''': it shrinks with the square of h. So make h tiny? Not too tiny. The two values f(x ± h) each carry a rounding error of about 10−16 times their size; their difference cancels most digits, and dividing by 2h magnifies the leftover error as 1/h. The total error is a V shape with a best step near h = 10−6 to 10−5, as the measurements below show.

Three small functions turn this into a harness. numerical_grad(f, xs) takes a function from a list of Values to a Value, and estimates the gradient with respect to each input by building fresh Values from the floats xs, nudged by ±eps, and reading .data off the result. autograd_grad(f, xs) runs the same f once on fresh Values, calls backward() and reads the grad fields. max_error(a, b) compares the two lists: the largest of |ai − bi| / max(1, |ai|, |bi|). The “max with 1” is deliberate: it makes tiny gradients compare in absolute terms (nobody cares that 10−12 differs from 10−13 by a factor of ten) and large ones in relative terms.

Here is the checker doing its job on a function that uses tanh, a power and a constant, and then catching a classic slip, a tanh derivative that forgets the square:

class Value:
    ...

    def __truediv__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        return self * other ** -1

    def __rtruediv__(self, other):
        return (self ** -1) * other

    def __pow__(self, n):
        if isinstance(n, Value):
            raise TypeError("only constant exponents are supported: v ** 2, not v ** w")
        out = Value(self.data ** n, (self,), f"**{n}")

        def _backward():                 # d(v^n)/dv = n v^(n-1)
            self.grad += n * self.data ** (n - 1) * out.grad
        out._backward = _backward
        return out

    def exp(self):
        e = math.exp(self.data)
        out = Value(e, (self,), "exp")

        def _backward():                 # d(e^v)/dv = e^v
            self.grad += e * out.grad
        out._backward = _backward
        return out

    def log(self):
        if self.data <= 0:
            raise ValueError(f"log of a non-positive number: {self.data}")
        out = Value(math.log(self.data), (self,), "log")

        def _backward():                 # d(ln v)/dv = 1/v
            self.grad += out.grad / self.data
        out._backward = _backward
        return out

    def tanh(self):
        t = math.tanh(self.data)
        out = Value(t, (self,), "tanh")

        def _backward():                 # d(tanh v)/dv = 1 - tanh^2 v
            self.grad += (1.0 - t * t) * out.grad
        out._backward = _backward
        return out

    def relu(self):
        out = Value(self.data if self.data > 0 else 0.0, (self,), "relu")

        def _backward():                 # 1 where the input was positive, else 0 (including at 0)
            self.grad += (1.0 if self.data > 0 else 0.0) * out.grad
        out._backward = _backward
        return out

    def sigmoid(self):
        x = self.data
        s = 1.0 / (1.0 + math.exp(-x)) if x >= 0 else math.exp(x) / (1.0 + math.exp(x))   # no overflow for x = -1000
        out = Value(s, (self,), "sigmoid")

        def _backward():                 # d(sigma)/dv = sigma (1 - sigma)
            self.grad += s * (1.0 - s) * out.grad
        out._backward = _backward
        return out
def numerical_grad(f, xs, eps=EPS):
    """d f / d xs[i] for every i by central differences: (f(x + eps) - f(x - eps)) / (2 eps).

    f takes a list of Values and returns a Value. Call it on fresh Values built from plain
    floats (never reuse a Value whose grad you care about) and read .data off the result.
    """
    grads = []
    for i in range(len(xs)):
        hi = [Value(x + (eps if j == i else 0.0)) for j, x in enumerate(xs)]
        lo = [Value(x - (eps if j == i else 0.0)) for j, x in enumerate(xs)]
        grads.append((f(hi).data - f(lo).data) / (2.0 * eps))
    return grads

def autograd_grad(f, xs):
    """d f / d xs[i] for every i, using your engine: build Values, call f, call backward."""
    vals = [Value(x) for x in xs]
    f(vals).backward()
    return [v.grad for v in vals]

def max_error(a, b):
    """The largest relative difference between two lists of numbers.

    Relative to the bigger magnitude, but never dividing by less than 1:
    max over i of |a[i] - b[i]| / max(1, |a[i]|, |b[i]|).
    """
    return max(abs(x - y) / max(1.0, abs(x), abs(y)) for x, y in zip(a, b))

Milestone 4: training with gradient descent

You now have everything to learn a function. Gradient descent (chapter 10) is the loop: compute the loss, get its gradient, move every parameter a small step against it. In code, four small functions:

  • zero_grad(params) sets every parameter's grad to 0.0.
  • sgd_step(params, lr) does p.data -= lr * p.grad for each parameter.
  • mse_loss(preds, targets) is the mean of (pred − target)2, built from Values so it is differentiable. Its gradient with respect to a prediction is 2(pred − target)/n.
  • train(params, loss_fn, steps, lr) runs the loop and returns the list of losses. loss_fn takes no arguments, returns a Value, and closes over the model and the data.

The order inside the loop is the whole lesson: zero, forward, backward, update. Because every _backward adds with +=, gradients from one step are still sitting in .grad at the next, and without zero_grad each update uses the sum of all gradients so far. The effect on the simplest possible problem, minimising (w − 3)2 from w = 0 with a learning rate of 0.1:

def run(zero, steps=12, lr=0.1):
    w = Value(0.0)
    trace = []
    for _ in range(steps):
        if zero:
            zero_grad([w])
        loss = (w - 3.0) ** 2
        loss.backward()
        sgd_step([w], lr)
        trace.append(w.data)
    return trace

zero_grad no :  0.600  1.680  3.024  4.363  5.430  6.010  5.989  5.370  4.276  2.928  1.594  0.541

With zeroing, w creeps towards 3 by a factor of 0.8 of the remaining distance each step (wk = 3(1 − 0.8k), exactly, which is how check.py tests it). Without it, the accumulated gradient behaves like a heavy, unintended momentum: w overshoots 3 at step 4, reaches 6, and swings back. The network still “trains” in a sense, which is what makes the bug dangerous; it just does something else.

The network classes are given. MLP([2, 4, 1], seed=1) builds a multi-layer perceptron with 2 inputs, 4 hidden neurons and 1 output: each neuron computes w · x + b and applies an activation (tanh by default), and the 4 × (2 + 1) + 1 × (4 + 1) = 17 parameters are Values, so a forward pass through model(x) builds a graph that reaches all of them. The initial weights come from random.Random(seed), so training is reproducible.

The test that matters most in this milestone checks the engine against numbers it has never seen: for a 13-parameter network on three data points, check.py runs backward once, then nudges each parameter's data by ±10−6, re-evaluates the loss and compares the central difference with the gradient your engine produced. If every operation passed milestone 3 but this fails, the bug is in how gradients combine: a Value shared by several neurons, a missing +=, a node visited twice. Then come the demonstrations that it learns: XOR (the same problem as chapter 9, now with your code) and a line fit.

One cost is worth seeing before you move on. graph_size(loss) counts the Values behind a loss. For XOR with 4 examples it is 192; for a batch of 400 random inputs the same network gives 17,220. The graph grows with the batch because every intermediate result is kept alive until backward() has used it. That is the memory cost of reverse mode that chapter 9 describes, and it is why real frameworks let you free the graph after each step and why training memory scales with batch size.

Solution spoiler 
def zero_grad(params):
    """Reset .grad to 0.0 on every parameter. backward() adds, so without this gradients pile up."""
    for p in params:
        p.grad = 0.0

def sgd_step(params, lr):
    """One gradient-descent update: data <- data - lr * grad, for every parameter."""
    for p in params:
        p.data -= lr * p.grad

def mse_loss(preds, targets):
    """Mean squared error: the average of (pred - target)^2. preds are Values, targets are numbers."""
    if len(preds) != len(targets) or not preds:
        raise ValueError("preds and targets must be non-empty and the same length")
    total = Value(0.0)
    for p, t in zip(preds, targets):
        total = total + (p - t) ** 2
    return total * (1.0 / len(preds))

def train(params, loss_fn, steps, lr):
    """Run `steps` rounds of: zero the gradients, compute loss = loss_fn(), backward, sgd_step.

    loss_fn takes no arguments and returns a Value (it closes over the model and the data).
    Returns the list of loss values, one per step (the loss BEFORE that step's update).
    """
    losses = []
    for _ in range(steps):
        zero_grad(params)
        loss = loss_fn()
        loss.backward()
        sgd_step(params, lr)
        losses.append(loss.data)
    return losses

Milestone 5: softmax and cross-entropy

For classification, a network ends in one number per class, the logits z, and the loss compares them with the true class t. Chapter 13 derived it: turn the logits into probabilities with the softmax pi = ezi / ∑j ezj, and take the negative log-probability of the right class, the cross-entropy L = −ln pt (chapter 14 gives it the information-theoretic reading, and it is the loss of language-model pre-training and supervised fine-tuning in A3).

Two things are worth writing carefully.

Stability. With logits like (1000, 1001), e1000 overflows. The fix is the identity log ∑ ezj = m + log ∑ ezj − m for any m; choosing m = max z makes every exponent at most 0. This is logsumexp. Softmax is then exp(z_i - logsumexp(z)), and the cross-entropy is just logsumexp(z) - z[t], with no separate softmax and no log(0). One subtlety about gradients: the maximum is a constant shift (use its plain number, max(z.data ...), not a Value). The result is mathematically the same function whatever m is, so the shift contributes no gradient and nothing is lost by treating it as a constant.

The gradient. Differentiate L = −zt + ln ∑j ezj with respect to zi: the first term gives −1 if i = t and 0 otherwise; the second gives ezi / ∑j ezj = pi. So

∂L/∂zi = pi − [i = t]

“The prediction minus the one-hot target” is the cleanest gradient in machine learning: it is positive for classes the model over-weights, negative for the true class, and sums to zero across classes. Your engine should produce it without being told, by differentiating through exp, log and +. check.py asserts exactly that, including for logits (1, 2, 3) with target 2, where the answer is (0.0900, 0.2447, −0.3348).

The final test is a small end-to-end problem: 45 points in the plane drawn from three Gaussian blobs, a MLP([2, 8, 3]) with tanh hidden units and linear outputs, and the mean cross-entropy over the batch as the loss. A hundred steps at a learning rate of 0.3 take the loss from 0.77 to 0.058 and the training accuracy to 98%. The model is tiny and the points are separable, so the numbers matter less than the fact that every line of the stack is yours: the arithmetic, the graph, the chain rule, the loss and the update.

Solution spoiler 
def logsumexp(zs):
    """log(sum(exp(z))) for a list of Values, stable: subtract the largest z first.

    The maximum is a CONSTANT shift (use its plain number, not a Value), so it adds no
    gradient path; the result is  m + log(sum(exp(z - m))).
    """
    m = max(z.data for z in zs)
    total = Value(0.0)
    for z in zs:
        total = total + (z - m).exp()
    return total.log() + m

def softmax(zs):
    """The probabilities exp(z_i) / sum_j exp(z_j), as a list of Values, stable for any size of z."""
    lse = logsumexp(zs)
    return [(z - lse).exp() for z in zs]

def cross_entropy(logits, target):
    """-log softmax(logits)[target] for a list of logit Values and an integer class index.

    Computed as logsumexp(logits) - logits[target]: no separate softmax, no log(0).
    """
    if not 0 <= target < len(logits):
        raise IndexError(f"target {target} out of range for {len(logits)} classes")
    return logsumexp(logits) - logits[target]

Systems connection

Your engine allocates a Python object per number, so one training step on 4 XOR examples creates 192 of them and a step on 400 examples creates 17,220, each with a closure. Production frameworks make the same graph out of whole tensors, so one node represents millions of numbers and the per-node overhead disappears (A2, chapter 5). The cost that remains is the one you measured with graph_size: activations are kept alive for the backward pass, which is why training needs several times the memory of inference, why chapter 17 budgets for it, and why techniques such as recomputing activations exist.

What you learned

  • Reverse-mode autodiff is three ideas: record parents during the forward pass, store each operation's local derivative as a closure, and run the closures in reverse topological order with +=.
  • A value used several times must sum its gradient contributions; gradients also accumulate across backward() calls, so training loops zero them first.
  • A central difference (f(x + h) − f(x − h))/2h has error that is V-shaped in h, best near 10−6; comparing it with the autograd result catches wrong or missing derivatives.
  • Softmax followed by log is unsafe for large logits; logsumexp with the maximum subtracted is safe, and the cross-entropy gradient is the predicted probabilities minus the one-hot target.
  • The graph is kept alive until the backward pass, so memory grows with the batch.

Check your understanding

In a * a + a at a = 3, the leaf a ends with grad = 7. Which implementation detail of backward makes that work?

  1. Each node is visited once per parent, so a is processed three times
  2. Each backward closure adds to its parents' gradients with +=, so contributions from different uses sum
  3. The engine stores a separate gradient for each use and averages them at the end
  4. Python evaluates a * a before + a, so only one gradient is ever computed
The derivative of a2 + a is 2a + 1 = 7: two contributions of 3 from the product (one per factor) and one of 1 from the sum, added together. Using = instead of += would keep only the last contribution. The topological order lists each node once, not once per use, so the first option describes something that does not happen; nothing is averaged.

You shrink the step in numerical_grad from 10−6 to 10−13 hoping for a more accurate gradient. What happens, and why?

  1. The estimate gets worse: f(x + h) and f(x − h) agree to almost every digit, so their difference is mostly rounding error, which dividing by 2h magnifies
  2. The estimate gets better, because the Taylor error h2 shrinks further
  3. The estimate is unchanged, because central differences are exact for any h
  4. The function raises a ZeroDivisionError, because 10−13 underflows
Truncation error does keep shrinking, which is why the second option is tempting, but a second error grows as h falls: the numerator is a difference of nearly equal numbers, each with rounding error near 10−16, divided by a tiny 2h. In the sweep above the error is 8 × 10−13 at h = 10−6 and 4 × 10−5 at 10−12. Central differences are exact only for polynomials up to degree 2, not for any function.

A colleague's training loop calls loss.backward() and sgd_step(params, lr) but never zero_grad. The loss still goes down at first. What is the most accurate description of what the optimiser is doing?

  1. Ordinary gradient descent, slightly slower
  2. Gradient descent with the learning rate silently doubled
  3. Nothing: the gradients cancel, so the parameters stay put after the first step
  4. Descent along the running sum of all past gradients, a heavy and unintended momentum that overshoots and oscillates
Each backward() adds the new gradient to what is already in .grad, so step k moves along the sum of the first k gradients. In the demo, w overshoots the optimum, peaks at about 6 and swings back, where the zeroed loop converges smoothly. It sometimes looks like it is learning, which is why the bug survives code review; compare a loss curve with a known-good loop, or print p.grad after two steps.

The gradient of softmax cross-entropy is p − one-hot, so for the true class it is 0.665 − 1 = −0.335. A negative gradient means that increasing this logit would reduce the loss, so gradient descent raises it. The other two logits receive +0.245 and +0.090, and the three numbers sum to zero. Plus 0.665 is the probability itself, forgetting the one-hot term.

For the XOR network, one loss over 4 examples builds a graph of 192 Values. Roughly how big is the graph for a batch of 400 examples?

  1. About 770, because only the 17 parameters are shared and the rest are constant
  2. About 17,000: each example adds about 43 nodes, and the 17 parameters are shared
  3. About 1,900, because the graph grows with the logarithm of the batch
  4. 192, because the graph depends on the network and not on the data
Every example runs its own forward pass through the network and adds its own nodes (a multiplication and an addition per weight, an activation per neuron, the squared error), while the parameters are shared leaves. Measured: 192 for 4, 1,740 for 40 and 17,220 for 400. Memory in training therefore grows linearly with batch size, and that is a first-order constraint on batch sizes at scale.

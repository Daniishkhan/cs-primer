Design a Customer-Support Agent

Design an agent that answers customer questions, looks up orders and accounts, and issues refunds inside limits, handing anything difficult to a person and leaving a record finance can show an auditor. The core problems are policy that a model cannot talk around, money movements that happen exactly once, and an escalation path that works.

How a design studio works

This page is a mock design session of 60 to 90 minutes, not a chapter. At each stage there is a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer is one strong design with its reasoning, not the only right one. The stages follow the usual order for an AI system: clarify the problem and users, decide how success is measured, estimate tokens, cost and latency, design the tools and context, draw the architecture, go deep on the hard parts, name the failure modes, plan the rollout, and say it out loud. A rubric at the end separates mid-level from senior signals. All numbers on this page are assumptions to reason with, not measurements; the scripts are small enough to change and rerun with your own.

📐 The brief

A product lead says: "We run an online subscription and retail business, about 20,000 support contacts a day by chat and email. Build an agent that answers questions, looks up orders and accounts, and issues small refunds, and hands anything difficult to a person. Finance wants a record of every money movement they can show an auditor."

  • The agent can move money. A wrong answer is embarrassing; a wrong refund is a loss, and a refund issued twice is a loss nobody notices until the books are reconciled.
  • Customers are strangers who type whatever they like, including text pasted from emails and web pages, and some of it is hostile.
  • Builds on workflow patterns, durable execution and tool design, with the tool loop, agent security and the durable-agent lab underneath. Background: failure, timeouts and retries, sagas, authorisation.
  • You have 60 to 90 minutes. Work the stages in order and write your own answer before opening each worked one.

Two scope decisions are worth saying out loud. First, version one answers and looks up; it refunds only inside tight limits, because every extra write tool multiplies the failure surface. Why the stakes are real: a chatbot's words can bind the company

In Moffatt v. Air Canada (British Columbia Civil Resolution Tribunal, 2024) a chatbot told a grieving customer he could claim a bereavement fare retroactively, which the airline's actual policy did not allow. The tribunal found the airline responsible for what its chatbot said and ordered it to pay the customer. Reports of the exact sums differ, so read the decision for figures; the lesson does not depend on them. Read the case study in the retrieval course. For this studio it is the argument for grounding answers in policy documents and for refusing, as a designed behaviour, anything the agent cannot ground.

The evaluation has three layers, in the order evaluating agents recommends: deterministic checks first (did the refund tool get called with the right arguments, did the policy engine allow it, is the final state of the test database correct), trajectory review (read the transcripts of the failures), and a model judge only for fuzzy qualities such as tone and groundedness, calibrated against human labels (LLM-as-judge).

The test set is built from real tickets, redacted, with the expected end state written by a support lead: "refund 38.00 on order A100", "no refund; explain 30-day window", "escalate". Plan roughly 300 cases at launch: 200 ordinary, 60 near the policy limits, 40 adversarial (injection, impersonation, pressure, "my previous agent promised me"). How many is enough for the money guardrail?

"""How many test conversations do you need before 'zero bad refunds' means anything?"""
import math

def upper_bound_zero_failures(n, conf=0.95):
    """Exact one-sided bound when 0 of n trials failed: 1 - (1-conf)^(1/n)."""
    return 1 - (1 - conf) ** (1 / n)

def wilson(k, n, z=1.96):
    p = k / n
    d = 1 + z * z / n
    centre = (p + z * z / (2 * n)) / d
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return centre - half, centre + half

print("zero failures observed:")
for n in (30, 100, 300, 600, 1000):
    print(f"  n={n:5d}: true failure rate could still be as high as {upper_bound_zero_failures(n):.2%} (95% bound)")
need = math.ceil(math.log(0.05) / math.log(1 - 0.005))
print(f"  to bound the rate below 0.5% you need {need} clean conversations\n")
print("resolution rate, 82 resolved of n:")
for n in (100, 400):
    k = round(0.82 * n)
    lo, hi = wilson(k, n)
    print(f"  n={n}: {k/n:.0%} observed, 95% interval {lo:.1%} to {hi:.1%}")

  • Zero failures in 300 cases does not show a failure rate of zero. It shows the rate is probably under about 1%. To bound it under 0.5% with 95% confidence you need about 600 clean cases. That is the "rule of three": zero failures in n trials bounds the rate near 3/n. See statistics for evals.
  • The resolution rate carries wide error bars at this sample size: 82 of 100 is anywhere from 73% to 88%. A comparison between two prompt versions on 100 cases is mostly noise, so compare them on the same cases, paired, and look at the failures instead of the average.
  • The consequence for rollout is the point: offline evaluation cannot prove safety at the 0.1% level. You buy the rest of the evidence with a staged rollout and hard limits in code (stage 11), so that a rare failure is small by construction.

3Estimate: volume, tokens, cost and latency

How many model calls does a day of support involve, what does a conversation cost, and what dominates the bill: the model or the people?

Compare with a worked answer

Model each intent with a number of model steps (each step is one pass through the tool loop), a fixed prompt of system text and tool definitions that is the same on every step (so a provider's prompt cache can serve it), and a small amount of new text per step. Prices below are an assumed shape, not any provider's list price; change them first.

"""Support agent: volume, tokens, cost, latency. Every input is an assumption."""
contacts_per_day = 20_000
mix = {"answer (FAQ, policy)": (0.55, 3), "account lookup": (0.30, 5), "refund or dispute": (0.15, 8)}  # share, model steps
prompt_fixed = 3_500        # system prompt + tool definitions, identical every step (cacheable)
step_new_in = 700           # new tokens appended per step (user turn, tool result)
step_out = 180              # output tokens per step (tool call or reply)
p_in, p_cache, p_out = 3.00, 0.30, 15.00   # $ per million tokens: ASSUMED list-price shape, not a quote
human_cost = 4.50           # $ per human-handled contact, ASSUMED fully loaded
step_s = 2.5                # seconds per model step incl. tool call, ASSUMED

def conv_cost(steps):
    inp_cached = fresh = 0
    for k in range(steps):
        history = k * (step_new_in + step_out)
        inp_cached += prompt_fixed + history if k else 0   # steps after the first read the prefix from cache
        fresh += step_new_in + (0 if k else prompt_fixed + 0)
    out = steps * step_out
    return (fresh * p_in + inp_cached * p_cache + out * p_out) / 1e6, fresh + inp_cached, out

  • A conversation costs about 4 cents of model time. At 20,000 contacts that is roughly $750 a day. The same contacts handled entirely by people at an assumed $4.50 would cost $90,000.
  • The bill is dominated by the humans the agent does not replace. Moving containment from 40% to 80% saves about $36,000 a day; halving the model price saves about $370. Optimise containment and correctness, not tokens. That does not make token cost irrelevant: a runaway loop at 50 steps costs ten times the average, which is why the loop has a step budget (chapter 2).
  • Input tokens dominate. Each step re-reads the growing history. Caching the fixed prefix is worth designing for: put the stable system prompt and tool definitions first and volatile content (the customer's name, today's date, retrieved passages) after them, or the cache never hits (context engineering).
  • Latency is the sum of steps. A refund conversation of 8 steps at 2.5 s each is 20 s of model time. Stream the reply, answer the easy intents with a short path (stage 5), and show progress for slow lookups.
  • Concurrency is modest. Little's law on 2 new conversations a second at the busiest hour gives about 22 conversations in flight in model time, and the provider's rate limits (requests and tokens per minute) matter more than your servers. Plan back-pressure and a degraded mode (stage 10).

For queueing and load behaviour behind these estimates see queueing theory and overload.

4Tools and context

Which tools does the agent get, what do their arguments look like, and what goes into the context window on each turn?

Compare with a worked answer

Apply tool design: start from tasks, not endpoints, and give the model fewer, richer tools whose results carry exactly what the next step needs. The backend has dozens of endpoints; the agent sees seven.

ToolKindArguments the model suppliesNot supplied by the model

Three design choices carry most of the safety.

  • The model proposes, the harness disposes. The tool is called propose_refund on purpose. The model supplies what it believes the customer is owed; code decides whether it happens. A tool named issue_refund invites a prompt-only safety design.
  • Identity is never an argument. A tool that takes customer_id as a parameter lets an injected instruction ("look up customer 4412") work. Bind the customer to the session when the conversation starts and close over it in every tool. This is the same rule as the confused deputy defence in any service.
  • Errors teach and do not leak. "Order not found for this customer" is returned both when the order does not exist and when it belongs to someone else, so the agent cannot be used to probe other people's orders.

Context per turn, in cache-friendly order: (1) stable system prompt (role, tone, what the agent must never do, how to escalate); (2) tool definitions; (3) policy summary for the intent the router chose, with its version; (4) session facts the harness already verified (customer first name, tier, locale); (5) the conversation so far, with old tool results compacted to a line each ("order A100: 38.00, delivered 3 Oct"); (6) the latest user message. Tool results are wrapped and labelled as data (delimiters). Long-term memory of past conversations is off in version one: it is a privacy surface with unclear benefit (memory).

5High-level architecture

Draw the system. Where is the trust boundary, which parts are fixed code and which are a model loop, and where do humans sit?

Compare with a worked answer

Life of a conversation:

  1. The gateway authenticates the session (or marks it anonymous), rate-limits per customer and per IP, and attaches the customer id to the conversation state. Nothing downstream asks the model who the customer is.
  2. The router is a small, cheap classification step (a fixed prompt, or a small model) that labels the message with an intent and a risk class: info, account read, account write, out of scope or sensitive. This is the routing pattern. Sensitive intents (fraud, legal threats, bereavement, self-harm language) go straight to a person with no agent loop.
  3. Information intents use a fixed workflow: retrieve policy passages, answer from them, cite the document and version, abstain if retrieval finds nothing relevant (RAG end to end, grounding and abstention). No tools, no write access, so nothing in the text can cause an action.
  4. Account intents run the agent loop with the read tools, plus the gated write tools if the router said account write. Narrowing the tool list per intent is cheap least privilege: a conversation classified as a delivery question does not carry propose_refund.
  5. Each write goes to the policy engine (stage 6), then to the tool layer, which attaches an idempotency key and calls the system of record (stage 7). Cases that need a person go to the human queue with a packet (stage 8).
  6. The journal records every model reply, tool call, policy decision and human action as it happens, so a crashed process can resume and an auditor can reconstruct what happened (stages 7 and 9).

Why not one big agent with every tool? Three reasons. The easy 55% of traffic does not need a loop, and a fixed workflow is cheaper, faster and easier to test. A single agent with every tool has the widest blast radius if it is steered. And separate paths can be evaluated and released separately. The loop earns its place only where the next step depends on what a lookup returns, which is true of account problems and not of FAQs (workflows versus agents).

6Deep dive 1: refund limits that a prompt cannot talk around

Write the rules for when a refund is automatic, when it needs a person and when it is refused. Where do they live, and what must be impossible for the model to influence?

Compare with a worked answer

A prompt that says "never refund more than $50" is a request. A model can be persuaded, confused by a long history, or injected. A limit that matters is code the model cannot edit: a function that takes the proposed action and returns a decision. The model is told the rules so it can explain them politely and avoid pointless proposals; it is not trusted to apply them.

The script below holds a small policy and runs six proposals, as a scripted stand-in model would produce them, through it. Note what the model does not supply: the customer id, which comes from the authenticated session.

"""Refund policy lives in code, outside the prompt. The model proposes; the harness decides."""
from dataclasses import dataclass
from llm import ScriptedModel, tool_use, tool_calls

@dataclass
class Order: id: str; customer: str; total: float; age_days: int; refunded: float = 0.0
ORDERS = {"A100": Order("A100", "ana", 38.00, 6), "A200": Order("A200", "ana", 180.00, 12),
          "A300": Order("A300", "ben", 640.00, 9), "A400": Order("A400", "cy", 25.00, 75)}
RECENT_REFUNDS = {"ana": 0, "ben": 0, "cy": 3}
AUTO_MAX, APPROVE_MAX, WINDOW_DAYS, MAX_RECENT = 50.00, 250.00, 30, 2

def decide(order_id, amount, customer):
    o = ORDERS.get(order_id)
    if o is None or o.customer != customer:
        return "deny", "order not found for this customer"        # one message for both cases: no probing
    if o.age_days > WINDOW_DAYS:
        return "escalate", f"outside the {WINDOW_DAYS}-day window"
    if amount + o.refunded > o.total:
        return "deny", "refund would exceed the order total"
    if RECENT_REFUNDS[customer] >= MAX_RECENT:
        return "escalate", "refund velocity limit reached"
    if amount <= AUTO_MAX:
        return "allow", "within automatic limit"
    if amount <= APPROVE_MAX:
        return "needs_approval", f"over ${AUTO_MAX:.0f}, a human must approve"
    return "escalate", f"over ${APPROVE_MAX:.0f}, human-only"

proposals = [("A100", 38.00, "ana"), ("A200", 180.00, "ana"), ("A300", 640.00, "ben"),
             ("A400", 25.00, "cy"), ("A300", 20.00, "ana"), ("A100", 90.00, "ana")]
model = ScriptedModel([[tool_use("issue_refund", {"order_id": o, "amount": a}, id=f"t{i}")]
                       for i, (o, a, c) in enumerate(proposals)])
print(f"{'order':6}{'amount':>8}  {'customer':9}{'decision':16}reason")
for o, a, c in proposals:
    call = tool_calls(model.complete([{"role": "user", "content": "refund please"}]))[0]
    # the customer id comes from the authenticated session, never from the model's arguments
    verdict, why = decide(call["input"]["order_id"], call["input"]["amount"], c)
    print(f"{o:6}{a:8.2f}  {c:9}{verdict:16}{why}")
order   amount  customer decision        reason
A100     38.00  ana      allow           within automatic limit
A200    180.00  ana      needs_approval  over $50, a human must approve
A300    640.00  ben      escalate        over $250, human-only

  • Four outcomes, not two. allow runs the refund. needs_approval parks it for a person (stage 8). escalate says the case is not for the agent. deny returns an explanation the agent relays. Collapsing these into allow or deny forces either too much risk or too many tickets.
  • Limits stack. Per-refund ($50 automatic, $250 with approval), per-order (cannot exceed the order total, counting earlier partial refunds), per-customer velocity (more than two recent refunds escalates), and per-day totals across the whole agent (a circuit breaker: if automatic refunds in an hour exceed a budget, the agent stops refunding and pages someone). The last one bounds the damage of a bug nobody has noticed.
  • The model's reason code is data, not authority. It is recorded and shown to the approver, and it can route (a damaged-item claim asks for a photo), but "the customer says the manager promised it" never raises a limit.
  • The policy has an owner and a version. Finance reviews the rules in a pull request; each decision in the audit log carries the policy version. When limits change, the evaluation set re-runs.

Common misconception

"We told the model the limit and it followed it in every test." Following a limit in tests is evidence about the average conversation, not about the one where a customer pastes a long persuasive story, or where a web page has been summarised into the context. Limits you rely on must hold when the model is wrong. See sandboxes and permissions for the general rule: policy in the harness, containment underneath.

7Deep dive 2: a crash in the middle of a refund

The process dies after the payment provider accepted the refund and before your system recorded it. What happens on restart, and what must be true for the customer to be refunded exactly once?

Compare with a worked answer

This is the dangerous window from durable execution: the side effect has happened in the world, and the memory of it lives only in a process that no longer exists. A supervisor restarts the run, the journal shows no refund, and a naive loop issues a second one. The same failure appears whenever a network call times out after the server acted (failure, timeouts and retries) and in every payment integration (exactly-once).

The fix has two parts: derive an idempotency key from the identity of the step (conversation, step number, order, amount), and send it with the request, so a repeat is recognised by the provider; and write the intent to the journal before the call, the result after. The script crashes once between the call and the journal write, with and without a key.

"""A crash between 'refund issued' and 'refund recorded'. Same retry, with and without an idempotency key."""
import hashlib

class Ledger:                                   # stands in for the payment provider
    def __init__(self): self.refunds, self.by_key = [], {}
    def refund(self, order, amount, key=None):
        if key and key in self.by_key:          # provider replays the stored result for a repeated key
            return self.by_key[key]
        r = {"refund_id": f"re_{len(self.refunds)+1}", "order": order, "amount": amount}
        self.refunds.append(r)
        if key: self.by_key[key] = r
        return r

class Crash(Exception): pass

def run_step(ledger, journal, conv, step, order, amount, use_key, crash_once):
    """One tool step: do the action, then record it. The process can die between the two."""
    key = hashlib.sha256(f"{conv}:{step}:{order}:{amount}".encode()).hexdigest()[:16] if use_key else None
    if any(e["step"] == step for e in journal):           # already recorded: do nothing
        return "skipped (journal says done)"
    result = ledger.refund(order, amount, key)
    if crash_once[0]:
        crash_once[0] = False
        raise Crash("process killed after the provider call, before the journal write")
    journal.append({"step": step, "result": result})
    return result["refund_id"]

for use_key in (False, True):
    ledger, journal, crash = Ledger(), [], [True]
    label = "with idempotency key" if use_key else "no key"
    for attempt in (1, 2):                                # the supervisor restarts the run once
        try:
            out = run_step(ledger, journal, "conv-77", 3, "A100", 38.00, use_key, crash)
            print(f"[{label}] attempt {attempt}: ok {out}")
        except Crash as e:
            print(f"[{label}] attempt {attempt}: {e}")
    total = sum(r["amount"] for r in ledger.refunds)
    print(f"[{label}] ledger: {len(ledger.refunds)} refund(s), ${total:.2f} paid for a ${38.00:.2f} order\n")
[no key] attempt 1: process killed after the provider call, before the journal write
[no key] attempt 2: ok re_2
[no key] ledger: 2 refund(s), $76.00 paid for a $38.00 order

[with idempotency key] attempt 1: process killed after the provider call, before the journal write
[with idempotency key] attempt 2: ok re_1

  • Without a key the retry paid twice: $76.00 for a $38.00 order, discovered at reconciliation, if ever.
  • With a key, the provider replays its stored answer. The key must be derived from the step, not generated fresh on each attempt. A random UUID created inside the retry loop defeats the purpose. Most payment providers document this behaviour, and keys expire after a period, so a retry days later needs a reconciliation read first (look up refunds on the payment before issuing another).
  • Approval waits must survive restarts too. A refund waiting two hours for a person is a row in a database with a state (pending_approval), not a process holding a conversation open. When the approver clicks, a worker loads the journal and continues. The conversation can even continue without the refund: "I have asked a colleague to approve this; you will get an email."
  • Saga thinking for multi-step changes. "Cancel the order, then refund, then email" has three effects. Order them so a crash leaves a state a person can understand, and give each a compensating action or a reconciliation job (sagas). The durable-agent lab builds the loop and the key.
  • The customer sees one story. If the refund is recorded but the confirmation message was lost, the next turn says "Your refund of $38.00 was issued earlier"; it never issues again because the journal and the provider both say it was done.

8Deep dive 3: escalation and the human handoff

When does the agent give up, what does the person receive, and how do you stop the queue from drowning or becoming a rubber stamp?

Compare with a worked answer

Escalation is a product, not an error path. Customers judge the whole service by the moment the agent says "let me bring in a colleague". There are two kinds of trigger, and they should not be mixed.

  • Rules the harness evaluates every turn: the customer asks for a person, legal or regulatory language, a policy escalation, two tool errors in a row, two rejected answers, a conversation past twelve turns. Rules are predictable, testable and cannot be talked out of.
  • Judgement the model contributes through escalate_to_human: "this customer is distressed", "the order data contradicts what they say". Useful, but advisory; the router's risk class and the rules take priority.

The handoff packet is assembled by the harness from verified state, not written freehand by the model, so it cannot include a claim that no tool ever returned.

"""Escalation triggers (rules the harness evaluates every turn) and the packet a human receives."""
import json, re

LEGAL = re.compile(r"\b(lawyer|solicitor|sue|chargeback|regulator|ombudsman|gdpr|data protection)\b", re.I)
HUMAN = re.compile(r"\b(human|real person|agent|manager|supervisor)\b", re.I)

def triggers(state):
    t = []
    if HUMAN.search(state["last_user"]):            t.append("customer asked for a person")
    if LEGAL.search(state["last_user"]):            t.append("legal or regulatory language")
    if state["policy_escalations"]:                 t.append("policy engine escalated: " + state["policy_escalations"][-1])
    if state["tool_errors"] >= 2:                   t.append("two tool errors in a row")
    if state["failed_answers"] >= 2:                t.append("customer rejected two answers")
    if state["turns"] >= 12:                        t.append("conversation longer than 12 turns")
    return t

def packet(state, why):
    return {"reason": why, "customer_id": state["customer"], "summary": state["summary"],
            "verified_facts": state["facts"], "actions_taken": state["actions"],
            "proposed_next_step": state["proposal"], "transcript_ref": state["transcript"]}

state = {"customer": "cus_81", "last_user": "This is the third time. Let me speak to a real person.",
         "policy_escalations": ["over $250, human-only"], "tool_errors": 0, "failed_answers": 1, "turns": 7,
         "summary": "Charged twice for order A300 (640.00). Wants the duplicate refunded.",
         "facts": ["order A300 paid twice on 2026-10-02 (pay_81a, pay_81b)", "identity verified by email link"],
         "actions": ["lookup_order A300", "refund proposal 640.00 blocked by policy"],
         "proposal": "refund pay_81b in full", "transcript": "conv-77"}
why = triggers(state)
print("escalate:", bool(why)); print(json.dumps(packet(state, why), indent=2))

  • The person starts where the agent stopped. The packet has a summary, verified facts with their sources, actions already taken, and a proposed next step. The customer is not asked to repeat anything. If the human finds the packet misleading, that is a labelled bad escalation and a test case.
  • Approvals are a queue with a service level. At 15% of 20,000 contacts being refund-related and perhaps one in five of those needing approval, that is about 600 approvals a day, or 40 an hour across a 15-hour service day. With the assumed 20 per hour per approver at peak, that is two to three people on approvals, which is cheap. The queue must show the proposal, the evidence and the rule that sent it there, so the person can decide in thirty seconds.
  • Rubber-stamping is the failure to design against. If an approver clicks "approve" on 99.8% of items, the approval is theatre. Measure approval rate and time per item; sample approved items for second review; seed a few known-bad proposals in the queue to check attention; and raise the automatic limit when a category has been approved without edits for long enough, which removes work and focuses humans on the rest (the same review habits apply to code).
  • Out of hours. The agent says plainly that a person will respond by a stated time, creates the ticket with the packet, and does not pretend to help further with things it may not do. A designed "I cannot do that, here is what happens next" is better than an agent that improvises.

9Deep dive 4: the audit trail finance can show an auditor

What exactly do you record, how do you make it hard to rewrite quietly, and how do you keep personal data out of it?

Compare with a worked answer

The audit trail answers one question months later: why did this money move? It is the same journal that makes the agent resumable, written with a stricter schema. Each record has a sequence number, an actor (agent:v14, policy, human:maya, system), an action, a short detail, the policy and prompt versions in force, and the hash of the previous record. Together they let you reconstruct a conversation, check that the rule applied was the rule in force, and detect edits.

"""A tamper-evident audit trail: each record carries the hash of the one before it."""
import hashlib, json, re

def redact(s):                                   # keep ids, drop card numbers and emails
    s = re.sub(r"\b\d{13,16}\b", "[card]", s)
    return re.sub(r"[\w.]+@[\w.]+", "[email]", s)

class AuditLog:
    def __init__(self): self.rows = []
    def append(self, actor, action, detail):
        prev = self.rows[-1]["hash"] if self.rows else "0" * 64
        row = {"seq": len(self.rows), "actor": actor, "action": action, "detail": redact(detail), "prev": prev}
        row["hash"] = hashlib.sha256(json.dumps(row, sort_keys=True).encode()).hexdigest()
        self.rows.append(row)
    def verify(self):
        prev = "0" * 64
        for r in self.rows:
            body = {k: v for k, v in r.items() if k != "hash"}
            if r["prev"] != prev or hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest() != r["hash"]:
                return f"BROKEN at seq {r['seq']}"
            prev = r["hash"]
        return f"ok, {len(self.rows)} records"

log = AuditLog()
log.append("agent:v14", "tool_call", "lookup_order order=A200 customer=cus_81")
log.append("policy", "decision", "needs_approval amount=180.00 rule=over_auto_max")
log.append("human:maya", "approve", "approved refund 180.00; customer wrote from ana@example.com, card 4242424242424242")
log.append("system", "refund_issued", "re_9 key=7f3a9c01 amount=180.00")
print("verify:", log.verify())
print("record 2 detail:", log.rows[2]["detail"])
log.rows[1]["detail"] = "allow amount=180.00 rule=within_auto_max"     # someone rewrites history
print("after editing record 1:", log.verify())
verify: ok, 4 records
record 2 detail: approved refund 180.00; customer wrote from [email], card [card]
after editing record 1: BROKEN at seq 1
  • Hash chaining makes silent edits visible, not impossible. Changing record 1 breaks the chain at record 1. Someone who can rewrite every later record can still forge a consistent history, so periodically write the latest hash somewhere the application cannot modify (a write-once storage bucket, a separate account, a signed timestamp). Then an auditor can verify that nothing before that point has changed.
  • Record decisions, not the full text of everything. Keep ids, amounts, rule names and versions. Keep the transcript in a separate store with a shorter retention and tighter access, linked by id. The script redacts card numbers and emails from details before they are written; redaction at write time is the only kind that is certain (data protection, privacy for AI).
  • Keep what an investigator needs from the model too. The model identifier and prompt version, the tool calls with arguments and results, and the retrieved policy passage with its document version. Model replies are not reproducible; the record of what they were is the evidence.
  • Access to the log is itself logged, and the people who run the agent cannot delete from it. Separation of duties is an audit requirement before it is a technical one (audit logs).
  • Observability is a different consumer of similar data. Traces for engineers (latency, token counts, tool errors) go to your tracing system (tracing for LLM systems); the audit log is a smaller, slower-changing record with different retention and access.

The lethal trifecta check is worth doing explicitly: the account agent has private data (orders) and reads untrusted content (customer text, product data), so the third leg, a way to send data out, must be absent. 11Rollout, monitoring and trade-offs

How do you go from zero to handling real customers with real money, what do you watch, and what would you change if the requirements moved?

Compare with a worked answer

Autonomy is earned in stages, and each stage has an exit criterion written down in advance.

StageWhat the agent doesExit criterion
0. ShadowReads real conversations and proposes replies and actions; staff see them and do the work. Nothing reaches customersStaff accept proposals unchanged at least 70% of the time; no unsafe proposals in the reviewed sample
1. AssistStaff send agent drafts after review; the agent answers FAQs directly for a small share (say 5%) of chat trafficCorrect resolution and customer satisfaction at least equal to the human baseline on the same intents
2. Answer and look upAgent handles info and read-only account intents alone; all writes still go to humansFour weeks without a policy violation; bad escalations under 10%
3. Small refundsAutomatic refunds under $25, approval above; a global daily budget as a circuit breakerZero unauthorised movements; reconciliation matches the journal to the provider each day
4. Raise limitsRaise the automatic limit by category only where approvals were granted unchanged for a long periodFinance sign-off on the new limit with the evidence

What to watch (and who gets paged): containment, escalation and bad-escalation rates, policy-engine denials per hour (a spike means either an attack or a prompt problem), refund spend against the budget, p95 latency, model error rate, cost per conversation, and the daily reconciliation difference between journal and provider, which must be zero. A weekly review reads a random sample of conversations and every escalation tagged "wrong". Deployments use a canary and keep both versions running until in-flight conversations finish (deployment strategies; the research system case calls this a rainbow deployment). The improvement flywheel turns bad conversations into new test cases.

Trade-offs and "what if requirements change".

  • Autonomy versus cost: every notch of limit raises containment and exposure. Decide per action with finance, and let evidence move it.
  • Fixed workflow versus agent loop: the loop handles messy account problems, the workflow is cheaper and safer. Keep both, and move an intent to a workflow once its steps stop varying.
  • Bigger model versus smaller: use a small model for routing and extraction, a stronger one for the account loop, and measure before choosing (cost, latency and quality).
  • If volume grows 10x, the model bill is still small; the constraints become provider rate limits, the approval queue and the abuse surface. If the business enters a regulated market (financial products), approvals and the audit trail become compliance controls, which is the subject of the regulated back-office studio. If customers want voice, latency drops from seconds to well under one, which changes the architecture more than any other requirement.

Give the design in about five minutes, as if to a product lead and a finance partner. Practise aloud, then compare.

How a senior engineer would summarise this

"This agent moves money for strangers who can type anything, so I split it into a part that talks and a part that decides. A router sends easy questions, about half of traffic, to a fixed retrieve-and-answer workflow with no tools. Account problems go to a tool loop with seven narrow tools, and the model can only propose a refund. A policy engine in code decides: automatic under $50, a human approves up to $250, anything larger or odd escalates, with per-order, per-customer and global-budget limits, and the customer id comes from the session, never from the model. Money calls carry an idempotency key derived from the step and are journalled before and after, so a crash between the provider and the database cannot pay twice; I showed that failing without the key and passing with it. Escalations come with a packet of verified facts so nobody repeats themselves, and I watch approval rates so approvers do not become a rubber stamp. Every decision goes in a hash-chained audit log with policy and prompt versions, redacted at write time, anchored somewhere the app cannot edit. The model costs about four cents a conversation, so the economics are decided by containment, not tokens. We launch in shadow, then assist, then read-only, then refunds under $25, each with a written exit criterion, and sampled tests cannot prove a 0.1% failure rate, so the hard limits are what make rare failures small."

Notice the shape: scope and stakes → measures and honest statistics → router and narrow tools → policy in code → idempotent, journalled writes → human handoff → audit → named failures → staged autonomy.

Key takeaways

  • Split the system into a part that talks (a model) and a part that decides (code). The model proposes a refund; a policy engine allows, queues or refuses it.
  • Identity comes from the session, never from an argument the model fills in.
  • Cost is dominated by the humans the agent does not replace: optimise containment and correctness before tokens.
  • Money-moving calls need an idempotency key derived from the step and a journal written before and after, or a crash pays twice.
  • An escalation is a product: harness-evaluated triggers, a packet of verified facts, and a queue designed so approvers do not rubber-stamp.
  • The audit trail records decisions, versions and evidence, redacts at write time and anchors its hash chain outside the application.
  • Zero failures in 300 tests only bounds the rate near 1%: earn autonomy in stages and keep limits in code so rare failures stay small.

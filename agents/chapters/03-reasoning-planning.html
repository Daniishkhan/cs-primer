Reasoning, ReAct & Planning

A loop that only reacts will wander. An agent that thinks between actions, plans ahead where it can and checks its own work does better. This chapter covers three patterns that give the loop direction: thinking before each action, planning the steps first, and checking the result afterwards. It also covers what changes now that many models reason internally before they answer.

Why this matters

The loop from chapter 2 decides one step at a time. With nothing steering it, a long task drifts, repeats itself or stops early, and per-step errors compound. Reasoning, planning and reflection are the three levers engineers use to steer. Each answers three questions. Where does the thinking happen: before an action, up front, or after? Who sees it? What checks it? The levers also decide cost. After this chapter you can pick a pattern for a task, implement it in plain code, and say what you give up with each.

Thinking before acting

A language model produces one token per forward pass. A fixed amount of computation therefore lies behind each token, however hard the question. When the model writes intermediate steps before the answer, later tokens can read those steps, so the whole answer draws on much more serial computation. That is one common explanation for a finding by Wei et al. (2022), "Chain-of-Thought Prompting Elicits Reasoning in Large Language Models". Showing a model worked examples with step-by-step reasoning improved its accuracy on arithmetic and reasoning benchmarks. Kojima et al. (2022), "Large Language Models are Zero-Shot Reasoners", found that even the plain instruction "Let's think step by step" could help. A chain of thought is such a written reasoning trace.

For an agent the idea has a natural extension. If thinking helps before an answer, it should help before each action. Look at what you know, say what you still need, then choose a tool. That is the pattern the next section names.

ReAct: thought, action, observation

Yao et al. (2022), "ReAct: Synergizing Reasoning and Acting in Language Models", proposed interleaving the model's reasoning with its actions. Each turn of the loop has three parts:

  1. Thought. The model writes a short piece of reasoning: what it knows, what is missing, what to do next.
  2. Action. The model names a tool and its arguments.
  3. Observation. Your program runs the tool and appends the result. The model reads it and begins the next thought.

The paper tested interactive decision-making on two benchmarks: ALFWorld, a text-based household environment, and WebShop, a simulated online shop. It reports that ReAct beat imitation-learning and reinforcement-learning methods by absolute success rates of 34 and 10 percentage points. It used only one or two examples in the prompt. On question answering (HotpotQA) and fact checking (FEVER), consulting a Wikipedia API reduced the hallucination and error propagation seen in chain-of-thought alone. Read those results as evidence for the idea, not for any particular modern system. The models are from 2022.

The original format is plain text. The prompt shows the model Thought:, Action: and Observation: lines. The model continues the pattern, and your harness parses out the action. The crucial detail is the stop sequence Observation:. Without it the model happily writes its own observation, inventing what the tool would have said. With it, generation halts after the action and your code supplies the real result.

import re
from llm import ScriptedModel, text_of

WIKI = {"eiffel tower": "The Eiffel Tower in Paris was completed in 1889.",
        "brooklyn bridge": "The Brooklyn Bridge in New York opened in 1883."}

def search(q):
    return WIKI.get(q.lower(), f"No page called {q!r}.")

def calc(expr):
    if not re.fullmatch(r"[0-9+\-*/(). ]+", expr):
        return "error: only arithmetic allowed"
    return str(eval(expr))          # safe only because of the whitelist above

ACTIONS = {"search": search, "calc": calc}
PATTERN = re.compile(r"Action:\s*(\w+)\[(.*)\]")

def react(model, question, max_steps=6):
    transcript = f"Question: {question}\n"
    for step in range(1, max_steps + 1):
        out = text_of(model.complete([{"role": "user", "content": transcript}], system="Use Thought/Action/Observation."))
        transcript += out + "\n"
        m = PATTERN.search(out)
        if "Final Answer:" in out:
            return transcript
        if not m:
            return transcript + "[parse error: no Action line]\n"
        name, arg = m.groups()
        obs = ACTIONS[name](arg) if name in ACTIONS else f"unknown action {name!r}"
        transcript += f"Observation: {obs}\n"
    return transcript + "[step budget used]\n"

model = ScriptedModel([
    "Thought: I need the completion year of each structure.\nAction: search[Eiffel Tower]",
    "Thought: Eiffel is 1889. Now the bridge.\nAction: search[Brooklyn Bridge]",
    "Thought: 1889 and 1883. The bridge is older; subtract.\nAction: calc[1889 - 1883]",
    "Thought: I have what I need.\nFinal Answer: The Brooklyn Bridge is older, by 6 years.",
])
print(react(model, "Which is older, the Eiffel Tower or the Brooklyn Bridge, and by how many years?"))

From text parsing to native tool calls

Parsing Action: lines with a regular expression is fragile, because a stray bracket breaks it. Modern APIs make the action structured. The tool_use block from chapter 2 is the Action, and the tool_result block is the Observation. The Thought is the text block that may precede the tool request in the same reply. You saw an empty text='' in chapter 2's transcript because the scripted model skipped it. To get ReAct-style behaviour with native tool calls, ask in the system prompt for a short sentence of reasoning before each tool call. Alternatively, use a model's built-in thinking, described below. The control flow is unchanged. It is the same loop, with the thought as free text.

Analogy: cooking and tasting

A cook working from a pinch of salt to a finished soup tastes as they go. They taste (observation), decide it needs acid (thought), add lemon (action) and taste again. They do not follow a recipe blindly to the end and find out at the table. ReAct is this tasting loop.

Where it breaks down: The cook's tongue is trustworthy and the same each time. A tool observation can be wrong, stale, truncated or planted by an attacker, and the model treats it as ground truth unless something checks it. The tasting spoon is only as good as the tool behind it.

Plan, then execute

ReAct decides one step at a time, which makes it adaptive but also myopic. It can wander, repeat work, or forget a requirement ten steps ago. The alternative is to separate planning from doing. First a planner call turns the goal into an explicit list of steps. Then an executor carries them out in order. The executor can be a plain loop or a small agent per step. If a step fails, the harness asks the planner to revise the remaining steps, giving it the failure as input.

import json
from llm import ScriptedModel, text_of

def planner(model, goal):
    return json.loads(text_of(model.complete([{"role": "user", "content": f"Plan as a JSON list of steps. Goal: {goal}"}])))

def execute(step, state):
    """Stand-in executor: a real one would be a small agent loop per step."""
    if step["do"] == "fetch_invoice" and state.get("flaky", True):
        state["flaky"] = False
        return False, "invoice service timed out"
    return True, f"ok: {step['do']}"

def run(goal, planner_model):
    plan = planner(planner_model, goal)
    state, i, replans = {}, 0, 0
    while i < len(plan):
        ok, note = execute(plan[i], state)
        print(f"step {i+1}/{len(plan)} {plan[i]['do']:<14} {'OK ' if ok else 'FAIL'} {note}")
        if ok:
            i += 1
        elif replans < 1:                      # one replan allowed, with the failure as input
            replans += 1
            plan = plan[:i] + json.loads(text_of(planner_model.complete(
                [{"role": "user", "content": f"Step failed: {note}. Re-plan the remaining steps."}])))
            print("   re-planned; remaining:", [s['do'] for s in plan[i:]])
        else:
            return "gave up"
    return "plan complete"

planner_model = ScriptedModel([
    json.dumps([{"do": "fetch_invoice"}, {"do": "check_totals"}, {"do": "send_summary"}]),
    json.dumps([{"do": "retry_fetch"}, {"do": "check_totals"}, {"do": "send_summary"}]),
])
print(run("Summarise invoice 77 for finance", planner_model))
step 1/3 fetch_invoice  FAIL invoice service timed out
   re-planned; remaining: ['retry_fetch', 'check_totals', 'send_summary']
step 1/3 retry_fetch    OK  ok: retry_fetch
step 2/3 check_totals   OK  ok: check_totals
step 3/3 send_summary   OK  ok: send_summary
plan complete

Notice what the plan buys. It is inspectable. A person or a rule can read three steps and veto "send_summary" before anything runs. Anthropic's "Building effective agents" lists this transparency among its three principles. It is cheap to execute, because the executor needs only the current step and its inputs, not the whole history. The ReWOO paper (Xu et al., 2023) pushes this to the limit. It plans all tool calls first, with placeholders for results, before executing any. And it is testable, because you can evaluate plans separately from execution. The cost is rigidity. A plan made before seeing any data can be wrong in ways only observation reveals. Hence the replanning branch. Replanning needs its own limit (one replan above), or it becomes a loop of its own.

Reflection: checking your own work

The third lever acts after an attempt. In reflection the system evaluates its output, turns the verdict into feedback and tries again. Shinn et al. (2023), "Reflexion: Language Agents with Verbal Reinforcement Learning", had agents write a short self-critique after a failed attempt and carry it into the next try as extra context. The loop is easy to write. The question that decides whether it helps is what produces the feedback.

from llm import ScriptedModel, text_of

TESTS = [("Hello, World!", "hello-world"), ("  Agents  & Tools ", "agents-tools"), ("a--b", "a-b")]

def run_tests(src):
    ns = {}
    try:
        exec(src, ns)
        fn = ns["slugify"]
    except Exception as e:
        return [f"could not load code: {e!r}"]
    failures = []
    for given, want in TESTS:
        got = fn(given)
        if got != want:
            failures.append(f"slugify({given!r}) returned {got!r}, expected {want!r}")
    return failures

def reflect_loop(model, task, max_rounds=3):
    messages = [{"role": "user", "content": task}]
    for round_no in range(1, max_rounds + 1):
        reply = model.complete(messages)
        src = text_of(reply)
        failures = run_tests(src)                  # grounded feedback: real tests, not opinion
        print(f"round {round_no}: {len(TESTS) - len(failures)}/{len(TESTS)} tests pass")
        for f in failures:
            print("   ", f)
        if not failures:
            return src
        messages += [reply.as_message(), {"role": "user", "content": "Tests failed:\n" + "\n".join(failures) + "\nFix the code."}]
    return None

v1 = "def slugify(s):\n    return s.strip().lower().replace(' ', '-')\n"
v2 = ("import re\n"
      "def slugify(s):\n"
      "    return '-'.join(re.findall(r'[a-z0-9]+', s.lower()))\n")
model = ScriptedModel([v1, v2])
print(reflect_loop(model, "Write slugify(s) in Python."))
round 1: 0/3 tests pass
    slugify('Hello, World!') returned 'hello,-world!', expected 'hello-world'
    slugify('  Agents  & Tools ') returned 'agents--&-tools', expected 'agents-tools'
    slugify('a--b') returned 'a--b', expected 'a-b'
round 2: 3/3 tests pass
import re
def slugify(s):
    return '-'.join(re.findall(r'[a-z0-9]+', s.lower()))

Here the feedback came from running tests, a fact the model cannot argue with. The second attempt had precise information about what was wrong. Compare that with asking the model "is your answer correct?" Huang et al. (2023), "Large Language Models Cannot Self-Correct Reasoning Yet", tested this. When models had to judge and revise their own reasoning without any external signal, accuracy often did not improve and sometimes fell. The practical rule is: reflect against something outside the model's own opinion. Good sources of grounded feedback include:

  • Test results, type checks, linters and compiler errors (coding agents, chapter 18).
  • Schema and business-rule validators (chapter 1's retry loop is reflection against a validator).
  • Retrieval: does the cited passage actually contain the claim (A5 chapter 16)?
  • A separate judge model with a rubric, which is weaker than a deterministic check but better than self-approval (A6 chapter 3).

Cap the rounds, as the code does. A reflection loop with no ceiling is a retry storm with extra tokens. The general form of this pattern is a generator and a critic in a loop. It appears in chapter 13 as the evaluator-optimiser workflow.

Common misconception

"The written reasoning is a faithful account of why the model did what it did." It is generated text like any other. Turpin et al. (2023), "Language Models Don't Always Say What They Think", showed that chain-of-thought explanations can omit the real influence on an answer. One example is a biasing hint in the prompt. The explanation can still sound perfectly plausible. Use reasoning traces to debug and to give humans something to review. Do not treat them as an audit log of the computation. Do not let a plausible explanation substitute for a check on the result.

Why steering matters: the arithmetic of long tasks

Chapter 0 gave the formula: with per-step success p, n steps succeed together with probability pn. Plans, thoughts and reflection do not change the formula. They change p, and they break the independence assumption by adding checks. A verification step after every few actions turns "one error ruins the run" into "one error is caught and retried". That is why long-running agents are built around checkpoints.

Planning and reflection each attack a different part of this curve. A plan shortens the path the model must discover, so there are fewer steps at risk. Grounded reflection raises the chance that a failed step is noticed and repaired. Better tools and prompts raise p itself. Measuring p honestly is the job of agent evals (A6 chapter 8).

What reasoning models change

Everything above treats reasoning as something you ask the model to write in its visible output. Since late 2024 a class of reasoning models does this by training. They are optimised with reinforcement learning against checkable outcomes, such as correct answers or passing tests. The result is a long internal chain of thought before the final reply. The approach reported for DeepSeek-R1 in 2025 is an open example, and A3 chapter 14 explains the training idea. Three consequences matter for agents.

  1. Prompting changes. "Think step by step" becomes largely redundant, since the model already deliberates. Heavy scaffolding can get in its way. State the goal, constraints and success criteria clearly and let the model plan inside its own reasoning.
  2. Thinking becomes a billed, tunable resource. Reasoning tokens are generated tokens. They count as output tokens, add latency and take space in the context window. APIs let you control how much a model may think. The older style is a fixed token budget. The newer style lets the model decide per request, with an effort setting (see the dated note).
  3. Thinking interacts with tool use. A model can reason between tool calls, reading each result before deciding. This is called interleaved thinking. The provider's documentation specifies that, in a tool loop, prior thinking blocks must be passed back unchanged with the tool results. The loop's message list therefore now contains a third kind of block alongside text, tool_use and tool_result.
{
  "role": "assistant",
  "content": [
    {"type": "thinking", "thinking": "The order is shipped; I need the carrier status...", "signature": "..."},
    {"type": "tool_use", "id": "toolu_01", "name": "track_shipment", "input": {"carrier": "UPS"}}
  ],
  "stop_reason": "tool_use"
}

Does this make ReAct, plans and reflection obsolete? No. It moves some of the thinking inside the model, which is often enough for a modest task. Explicit structure is still worth having in four cases. The first is when you need to review a plan before acting. The second is when you need to split work across workers or time, since a plan is data you can persist and resume. The third is when you need to verify with outside checks. The fourth is when you need to bound cost, because a reasoning model left to think without limits can spend far more than a plain model plus a short plan. The guidance that holds across generations: use the least machinery that reaches your reliability target, and measure, with the same evaluation, whether the extra thinking pays for itself.

State of play, October 2026

Anthropic's documentation (read October 2026) describes two ways to control thinking. The older "extended thinking" with a fixed budget_tokens (minimum 1,024, below max_tokens) is deprecated on the 4.6 model generation. It is rejected with a 400 error on 4.7 and later. Those models use adaptive thinking (thinking: {type: "adaptive"}), where the model decides whether and how much to think, and an effort setting steers depth. The API returns summarised thinking, thinking tokens are billed as output tokens (a usage field reports how many), and adaptive thinking interleaves reasoning between tool calls without a beta header. Other providers expose similar controls under different names. These details change with each model generation, so check the current reference and treat the model-specific facts here as a dated snapshot.

Systems connection

Plan-then-execute is a query planner with a language model as the optimiser: a declarative goal becomes an explicit plan, which is then executed and may be re-planned when estimates prove wrong. Reflection loops share the usual retry hazards. They need a cap, a backoff of sorts (changed information, not just another try), and care that a retried action is idempotent. And thinking-token cost is a capacity question, like those in the token economics chapter.

Key takeaways

  • ReAct alternates thought, action and observation; the thought keeps the run on course and the observation grounds it. The stop sequence prevents invented observations; native tool calls make the action structured.
  • Plan-then-execute trades adaptivity for reviewability, cheaper steps and less drift; give it a bounded replan path for failures.
  • Reflection helps when feedback comes from outside the model (tests, validators, retrieval, a rubric judge) and not from its own opinion; cap the rounds.
  • Reasoning traces are generated text, not an audit log of the computation.
  • Reliability decays as pn; steering patterns help by shortening paths, adding checks and raising p.
  • Reasoning models move planning inside the model and make thinking a billed, tunable resource; keep explicit structure where you need review, resumption, verification or cost control.

Check your understanding

In a text-format ReAct loop, why do you set Observation: as a stop sequence?

  1. To make the model's answers shorter and cheaper
  2. To force the model to use the calculator tool
  3. To stop the model writing its own invented tool output, so the harness can insert the real result
  4. To let the model reason for longer before it acts
Without the stop sequence the model continues the pattern and fabricates an observation. Stopping after the action hands control to your code, which runs the tool and supplies the true result. Shortening output is a side effect, not the purpose.

Which task is the best fit for plan-then-execute rather than plain ReAct?

  1. An invoice approval procedure with fixed stages that a manager wants to review before it runs
  2. Debugging an unfamiliar failing test with no known cause
  3. Open-ended research where each finding changes the next question
  4. Exploring a website to find where a setting lives
A known procedure that needs sign-off benefits from an explicit, reviewable plan. The other three are exploratory: the next step depends on what is discovered, which is where ReAct's step-by-step adaptivity earns its cost.

A coding agent writes a function, asks itself "is this correct?", answers "yes", and stops. The function has a bug. Which change would most improve the loop?

  1. Ask the model to be more confident
  2. Raise the temperature so it explores more
  3. Add a second self-critique round with the same question
  4. Run the project's tests and feed the failures back as the reflection signal
Self-critique with no outside signal is unreliable, so repeating it (option 3) is unlikely to help. Real test failures are a grounded signal the model cannot argue with, and they point at what is wrong. Temperature and confidence do not provide new information.

A 30-step agent task has per-step success of 95 per cent, independent across steps. Which number is closest to the chance of finishing without error?

  1. 95 per cent
  2. 21 per cent
  3. 50 per cent
  4. 5 per cent
0.9530 is about 0.215. Option 95 per cent ignores compounding. Fifty per cent is roughly the chance after 13 steps, and 5 per cent is about the chance after 58 steps. This is why verification checkpoints matter on long tasks.

You switch from a plain model with a "think step by step" prompt to a reasoning model with thinking enabled. Which statement is most accurate?

  1. The explicit prompt is now essential, because the model cannot reason without it
  2. Thinking tokens are free because they are not shown
  3. Thinking tokens are generated tokens: they add latency and are billed as output, so the extra reasoning must earn its cost
  4. Tool use no longer needs a loop, since the model plans everything internally
Reasoning is generated text even when hidden or summarised, so it is billed and slows the response. The prompt is largely redundant, not essential. Tools still return new information the model could not have predicted, so the loop remains.

A colleague says: "The agent's thought said it chose the refund tool because the customer was angry, so we know why it acted." What is the best reply?

  2. That is correct, since the reasoning is what produced the action
  3. It is correct only if the temperature was 0
  4. It is incorrect because models do not produce reasoning, only actions

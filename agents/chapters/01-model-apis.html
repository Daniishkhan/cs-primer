Talking to a Model

Before an agent can loop, a program has to hold one clean conversation with a model over HTTP. This chapter covers what a request contains, who says what, which knobs matter, how streaming arrives, and how to get output your code can rely on instead of prose it has to guess at.

Why this matters

Many agent failures look mysterious: "it forgot", "it cut off mid-answer", "the JSON was invalid", "the bill doubled". Each one traces back to a fact about this layer. The model keeps no memory between calls. Output has a hard length cap. Text arrives in pieces. Nothing guarantees the shape of what comes back unless you ask the right way.

Chapter 2 builds the agent loop out of exactly these calls. After this chapter you can read an API request and response fluently and predict what each parameter does. You can also choose between three ways to get structured output: parsing the reply, retrying, or forcing the format while the model writes.

One request, one response

A model API is an ordinary web API, the kind where you send an HTTPS POST with a JSON body and receive a JSON body back. Nothing about it is special at the network level. What is special is the contents. Here is the shape of a request to Anthropic's Messages API, which this course uses for its examples. OpenAI and Google offer the same ideas under slightly different names, and chapter 6 lines them up.

POST https://api.anthropic.com/v1/messages
{
  "model": "MODEL-ID",
  "max_tokens": 1024,
  "system": "You are a concise support assistant for an online shop.",
  "messages": [
    {"role": "user", "content": "Where is order A-1001?"}
  ],
  "temperature": 0.2,
  "stop_sequences": ["###"],
  "stream": false
}

Each field answers one question:

model
Which model to run. An identifier string. It changes as models are released and retired, so keep it in configuration, not scattered through code.
max_tokens
A hard cap on how many tokens the model may generate. A token is the unit a model reads and writes, a word, part of a word or a punctuation mark (A2 chapter 13). It is required, and it is a ceiling, not a target.
system
Standing instructions for the whole conversation. Covered below.
messages
The conversation so far, as an ordered list of turns.
temperature, stop_sequences, stream
Sampling control, early-stop strings and delivery mode. Each has its own section.
tools
Optional functions the model may request. Chapter 2.

The response is equally regular. It carries the generated content as a list of blocks, a stop_reason that says why generation ended, and a usage count of input and output tokens, which is what you are billed on. An illustrative response (the exact extra fields vary by provider and version):

{
  "role": "assistant",
  "content": [{"type": "text", "text": "Order A-1001 shipped yesterday."}],
  "stop_reason": "end_turn",
  "usage": {"input_tokens": 31, "output_tokens": 9}
}

Messages and roles

A conversation is an ordered list of messages, each with a role that says who spoke. Two roles appear in the list. The user role is everything that comes in: the person's words, and later the results of tools. The assistant role is what the model said. The turns alternate. Providers differ over where the standing instructions go. Anthropic takes a separate system field, while OpenAI-style chat APIs put a system or developer message at the top of the same list. The idea is the same.

The content of a message is either a plain string or a list of content blocks. Blocks let one turn contain several typed parts: some text, then a request to use a tool, then more text. The three block types used throughout this course are text, tool_use (the model asks for a tool) and tool_result (your program answers). They are what lab-support/llm.py models, and chapter 2 is about the last two.

The model remembers nothing

This is the single most important fact in the chapter. The API is stateless, as HTTP is: each request stands alone. A "conversation" exists only because your program keeps the list and re-sends it. Watch what that does to the input size over three turns:

from llm import ScriptedModel, text_of

model = ScriptedModel(["Paris.", "About 2.1 million people live in the city proper.", "Yes, the Seine."])
system = "You are a concise geography assistant."
messages, total_in = [], 0
for q in ["Capital of France?", "How many people live there?", "Is there a river through it?"]:
    messages.append({"role": "user", "content": q})
    reply = model.complete(messages, system=system)
    messages.append(reply.as_message())          # YOU keep the history; the API does not
    total_in += reply.usage["input_tokens"]
    print(f"sent {len(model.calls[-1]['messages'])} messages, input_tokens={reply.usage['input_tokens']:>3}, "
          f"output_tokens={reply.usage['output_tokens']:>2} -> {text_of(reply)}")
print("total input tokens billed:", total_in)
sent 1 messages, input_tokens= 15, output_tokens= 2 -> Paris.
sent 3 messages, input_tokens= 24, output_tokens=13 -> About 2.1 million people live in the city proper.
sent 5 messages, input_tokens= 44, output_tokens= 4 -> Yes, the Seine.
total input tokens billed: 83

The stand-in counts about four characters per token, which is crude but monotone. The pattern is real. The second question ("How many people live there?") only makes sense because the first exchange travels with it. Each call's input is longer than the last. A ten-turn chat bills the first turn ten times. A3 chapter 22 explains why input and output tokens are priced differently, and chapter 10 is about spending that growing budget wisely.

Analogy: the expert with no memory

Imagine consulting a brilliant specialist who forgets everything the moment you leave the room. To get help on a long case you hand them the complete case file at the start of every visit, including their own earlier notes. They read it all, add one more page, and you take the file home. The file is your messages list, and the visit is one API call.

Where it breaks down: a human reads a file once and skims it. The model is charged for, and slowed by, every token of the file on every visit, and it can attend badly to material buried in the middle of a very long one. Real specialists also do not change their answer because of how a note was worded.

System prompts

A system prompt is text, placed outside the turn-by-turn conversation, that sets the role, the rules and the style for the whole session. Models are trained to give it more weight than ordinary user text. Use it for things that should hold on every turn: who the assistant is, what it may and may not do, the output format, the tools' etiquette. Keep per-request facts, such as this customer's order or today's date, in the user turn or a tool result. Then the system prompt stays stable and cacheable.

Two cautions, both revisited later. First, a system prompt is an instruction, not a security boundary. A model can be talked out of its rules by text it reads, which is the subject of chapter 19. Real limits belong in code and permissions. Second, system prompts are programs written in English, and they deserve the care of programs. Chapter 4 covers writing, testing and versioning them.

Parameters that matter

max_tokens and stop reasons

max_tokens caps the output. If the model reaches the cap mid-sentence, generation stops and the response says so with stop_reason: "max_tokens". The reply you got is truncated, which is a common source of bugs. Truncated JSON does not parse, and a truncated tool_use block is unusable. Always read stop_reason before trusting the content.

stop_reasonMeaningWhat your code should do
end_turnThe model finished its reply.Use the answer (in an agent: the loop may end).
max_tokensHit your cap; output is cut off.Raise the cap, shorten the request or continue; never parse the output as complete.
stop_sequenceThe model produced one of your stop_sequences.Treat the text before it as the answer.
tool_useThe model wants one or more tools run.Run them and send the results (chapter 2).
refusal and othersProvider-specific cases such as a safety refusal or a paused turn.Handle each explicitly; check the provider's list, which grows.

Temperature and top-p

A model does not choose a word. It computes a score for every token in its vocabulary, called a logit. It turns the scores into probabilities with a softmax and samples one token (A2 chapter 15 derives this). Temperature T divides the logits before the softmax. The probability of token i is exp(zi / T) divided by the sum of exp(zj / T) over all tokens. Low T sharpens the distribution toward the top token. High T flattens it. Top-p (nucleus sampling) keeps only the smallest set of top tokens whose probabilities add up to p, then renormalises. Here are made-up logits for the next token after "The capital of France is":

import math, random

# Illustrative logits for the next token after "The capital of France is"
logits = {" Paris": 9.0, " Lyon": 6.5, " the": 6.0, " a": 4.0, " Rome": 3.5}

def softmax(logits, T):
    scaled = {t: v / T for t, v in logits.items()}
    m = max(scaled.values())
    exps = {t: math.exp(v - m) for t, v in scaled.items()}
    z = sum(exps.values())
    return {t: e / z for t, e in exps.items()}

def top_p(probs, p):
    kept, total = {}, 0.0
    for t, q in sorted(probs.items(), key=lambda kv: -kv[1]):
        kept[t] = q
        total += q
        if total >= p:
            break
    z = sum(kept.values())
    return {t: q / z for t, q in kept.items()}

for T in (0.2, 1.0, 2.0):
    probs = softmax(logits, T)
    print(f"T={T}: " + "  ".join(f"{t.strip()}={q:.3f}" for t, q in probs.items()))

probs = top_p(softmax(logits, 1.0), 0.95)
print("T=1.0, top_p=0.95 keeps:", {t.strip(): round(q, 3) for t, q in probs.items()})

rng = random.Random(7)
for T in (0.2, 1.0, 2.0):
    probs = softmax(logits, T)
    draws = rng.choices(list(probs), weights=list(probs.values()), k=1000)
    print(f"T={T}: Paris chosen {draws.count(' Paris')} / 1000 times")
T=0.2: Paris=1.000  Lyon=0.000  the=0.000  a=0.000  Rome=0.000
T=1.0: Paris=0.875  Lyon=0.072  the=0.044  a=0.006  Rome=0.004
T=2.0: Paris=0.604  Lyon=0.173  the=0.135  a=0.050  Rome=0.039
T=1.0, top_p=0.95 keeps: {'Paris': 0.883, 'Lyon': 0.073, 'the': 0.044}
T=0.2: Paris chosen 1000 / 1000 times
T=1.0: Paris chosen 876 / 1000 times
T=2.0: Paris chosen 637 / 1000 times

For agents the practical advice is short. Use a low temperature (or the provider's default) for steps where a wrong choice breaks the run: picking a tool, filling arguments, classifying. Allow more for drafting prose where variety is welcome. Do not rely on temperature to get determinism. Even at temperature 0, providers do not promise byte-identical output across calls. Floating-point and batching effects on the serving side cause the differences. Write tests that tolerate variation rather than comparing whole strings. Some newer models also fix or restrict sampling parameters, so the model's own documentation is the authority.

stop_sequences

A stop sequence is a string that ends generation as soon as the model produces it. It is a blunt, useful tool. The classic ReAct prompt of chapter 3 stops at the text Observation:, so the model cannot invent a tool result for itself.

Streaming

A model produces tokens one at a time, and generating a long answer can take many seconds. With "stream": true the server sends the response as it is produced, using server-sent events (SSE). This is a long-lived HTTP response in which the server writes lines of the form event: name and data: {json} as things happen. Streaming does not make the model faster. It shows the first words after a fraction of a second, which makes a chat interface feel alive. It also keeps connections from timing out on long outputs.

The stream follows a fixed grammar. It opens with a message_start event. Each content block is then announced by content_block_start, filled by a run of content_block_delta events and closed by content_block_stop. A final message_delta carries the stop_reason and usage, and message_stop ends it. Text arrives as text_delta pieces. A tool request arrives as input_json_delta pieces, each holding a fragment of the JSON for the tool's arguments. Those fragments are not valid JSON until you have joined them all. A client must therefore buffer the string and parse it only at content_block_stop. This client folds a recorded stream into finished blocks:

import json

# A hand-written event stream in the shape of the documented Messages streaming events.
events = [
  {"type": "message_start", "message": {"role": "assistant", "content": [], "usage": {"input_tokens": 52, "output_tokens": 1}}},
  {"type": "content_block_start", "index": 0, "content_block": {"type": "text", "text": ""}},
  {"type": "content_block_delta", "index": 0, "delta": {"type": "text_delta", "text": "Let me check "}},
  {"type": "content_block_delta", "index": 0, "delta": {"type": "text_delta", "text": "the order."}},
  {"type": "content_block_stop", "index": 0},
  {"type": "content_block_start", "index": 1, "content_block": {"type": "tool_use", "id": "toolu_1", "name": "lookup_order", "input": {}}},
  {"type": "content_block_delta", "index": 1, "delta": {"type": "input_json_delta", "partial_json": ""}},
  {"type": "content_block_delta", "index": 1, "delta": {"type": "input_json_delta", "partial_json": "{\"order_id\":"}},
  {"type": "content_block_delta", "index": 1, "delta": {"type": "input_json_delta", "partial_json": " \"A-10"}},
  {"type": "content_block_delta", "index": 1, "delta": {"type": "input_json_delta", "partial_json": "01\"}"}},
  {"type": "content_block_stop", "index": 1},
  {"type": "message_delta", "delta": {"stop_reason": "tool_use"}, "usage": {"output_tokens": 38}},
  {"type": "message_stop"},

blocks, partial = {}, {}
for ev in events:

    if t == "content_block_start":
        blocks[ev["index"]] = dict(ev["content_block"])
        partial[ev["index"]] = ""

    elif t == "message_delta":
        stop = ev["delta"]["stop_reason"]
print("stop_reason:", stop)
print(json.dumps(list(blocks.values()), indent=1))

For an agent, streaming has a twist: you can show text to the user as it arrives, but a tool cannot run until its arguments are complete. The loop in chapter 2 therefore works on whole messages. Streaming is a presentation layer around it.

Structured output

Code needs data, and a model writes text. Most "it worked in the demo" failures live in that gap. There are three levels of defence, from weakest to strongest.

Level 1: ask, parse, validate, retry

Describe the format in the prompt, parse the reply with a real JSON parser, validate the result against the schema you expect, and on failure send the error back and ask again. Avoid using a regular expression to dig JSON out of prose. Never trust the parse alone, because valid JSON can still have the wrong keys or a value outside the allowed set.

import json
from llm import ScriptedModel, text_of

SCHEMA = {"required": {"sentiment": str, "score": int}, "enum": {"sentiment": {"positive", "neutral", "negative"}}}

def validate(raw):
    """Return (obj, None) if raw is valid JSON matching SCHEMA, else (None, reason)."""
    try:
        obj = json.loads(raw)
    except json.JSONDecodeError as e:
        return None, f"not valid JSON ({e.msg} at char {e.pos})"
    if not isinstance(obj, dict):
        return None, "top level must be an object"
    for key, typ in SCHEMA["required"].items():
        if key not in obj:
            return None, f"missing key {key!r}"
        if not isinstance(obj[key], typ) or isinstance(obj[key], bool):
            return None, f"{key!r} must be {typ.__name__}, got {type(obj[key]).__name__}"
    if obj["sentiment"] not in SCHEMA["enum"]["sentiment"]:
        return None, f"sentiment {obj['sentiment']!r} not in {sorted(SCHEMA['enum']['sentiment'])}"
    return obj, None

def extract(model, review, max_attempts=3):
    messages = [{"role": "user", "content": f"Classify this review as JSON.\n<review>{review}</review>"}]
    for attempt in range(1, max_attempts + 1):
        reply = model.complete(messages, system="Reply with JSON only: {\"sentiment\": ..., \"score\": 1-5}")
        obj, problem = validate(text_of(reply))
        print(f"attempt {attempt}: {text_of(reply)[:60]!r} -> {'OK' if obj else problem}")
        if obj:
            return obj
        messages += [reply.as_message(), {"role": "user", "content": f"That was rejected: {problem}. Reply again with valid JSON only."}]
    raise ValueError("no valid output after retries")

model = ScriptedModel(['Sure! Here is the JSON: {"sentiment": "positive", "score": 5}',
                       '{"sentiment": "great", "score": 5}',
                       '{"sentiment": "positive", "score": 5}'])
print(extract(model, "Fast delivery, works perfectly."))
attempt 1: 'Sure! Here is the JSON: {"sentiment": "positive", "score": 5' -> not valid JSON (Expecting value at char 0)
attempt 2: '{"sentiment": "great", "score": 5}' -> sentiment 'great' not in ['negative', 'neutral', 'positive']
attempt 3: '{"sentiment": "positive", "score": 5}' -> OK
{'sentiment': 'positive', 'score': 5}

The scripted model plays out the two most common failures: chatty framing around the JSON, and a plausible value outside the allowed set. The retry loop works, but it costs a full extra call for every failure. The retries are not guaranteed to succeed either. Cap the attempts, as above, and decide what happens when they run out. Options are an error, a human queue or a default.

Level 2: a tool as the schema

Providers already force models to emit JSON for tool calls, validated against a JSON Schema you supply (chapter 2). A common trick is to define a tool whose only purpose is to receive the structured answer, for example record_sentiment(sentiment, score), and require the model to call it. You never run anything. The arguments are the output. This leans on the model's training for tool use, which is usually more reliable than "reply with JSON" in prose.

Level 3: constrained decoding

The strongest option changes the sampler instead of asking politely. In constrained decoding the server compiles your schema into a grammar. At every step it masks out tokens that would break the grammar, so an invalid document cannot be produced. Anthropic's structured outputs take the schema in output_config.format with type: "json_schema". A separate strict: true on a tool definition guarantees that tool inputs match the tool's schema. The documented limits matter in practice. The guarantee does not hold when the model refuses (stop_reason: "refusal") or runs out of tokens, since max_tokens can leave incomplete JSON. Some schema features are also unsupported, such as recursive schemas and numeric range constraints. The first request with a new schema pays extra latency while the grammar compiles.

Common misconception

"Constrained decoding means the output is correct." It means the output is well-formed: valid JSON with the right keys and types. A model can still put the wrong customer id in a perfectly valid field, or pick the wrong enum value. Schema validity removes parsing failures. It does not remove wrong answers. You still validate business rules in code, such as whether this order id exists and whether this amount is within the limit.

State of play, October 2026

Parameter names in this chapter were checked against Anthropic's API documentation in October 2026; other providers differ and all of them change. Three details moved recently. First, structured outputs use the output_config.format field. The older output_format parameter is deprecated, and the beta header is no longer needed. Second, the fixed-budget form of extended thinking (thinking: {type: "enabled", budget_tokens: N}) is deprecated on the 4.6 model generation. It is rejected with a 400 error on 4.7 and later, which use adaptive thinking instead (chapter 3 explains thinking). Third, model identifiers keep changing. Treat any parameter list as a snapshot and read the provider's current reference before you ship.

Systems connection

A model call is a slow, occasionally failing remote call, so the usual rules for failures, timeouts and retries apply. Set a client timeout. Retry only errors that can succeed on retry, such as rate limit 429, overloaded or 5xx responses. Use exponential backoff with jitter, and honour any retry-after header. Generating text is not idempotent in the useful sense, since a retry may give different words. A retry must never repeat a side effect that the first attempt already caused. Service level objectives (SLOs) for model calls need a latency target for the first token and one for the full reply, because streaming separates them.

Key takeaways

  • A model call is a stateless HTTPS request. Your program owns the conversation list and re-sends all of it every time, so input cost grows with every turn.
  • Messages alternate user and assistant; standing rules go in the system prompt; content blocks (text, tool_use, tool_result) carry typed parts.
  • Read stop_reason before trusting output: max_tokens means truncated, tool_use means a tool is wanted.
  • Temperature reshapes the probabilities but not their order; use low values where mistakes are costly, and never count on determinism.
  • Streaming improves time to first token, not total time; tool arguments arrive as JSON fragments that are only parseable once complete.
  • For structured output, prefer constrained decoding or a forced tool, validate business rules in code, and cap retries.

Check your understanding

A user asks a follow-up that only makes sense given the previous answer, and your program sends just the new question. What happens?

  1. The API looks up the earlier turns using a conversation id
  2. The model answers from its own memory of the previous call
  3. The model has no access to the earlier turns and answers without them
  4. The request is rejected because the roles do not alternate
The API is stateless: only what is in this request exists for the model. Nothing stores the earlier turns for you, which is why your program must keep the list and re-send it. A single user message is perfectly valid, so it is not rejected; it simply lacks context.

A response arrives with stop_reason: "max_tokens" and a JSON document that fails to parse near the end. What is the most likely cause and fix?

  1. The output was truncated by your cap; raise max_tokens or shorten the task
  2. The temperature was too high; set it to 0
  3. The system prompt was ignored; move the format rules to the user turn
  4. The model API is unreliable; retry the identical request
The reason is stated by the stop reason: generation hit the cap and was cut mid-document. A retry with the same cap hits the same wall. Temperature affects which tokens are chosen, not how many are allowed.

Next-token probabilities at temperature 1 are 0.875, 0.072 and 0.044 for three tokens. What does raising the temperature to 2 do?

  1. It makes the second token the most likely
  2. It removes the least likely token
  3. It leaves the probabilities unchanged but makes sampling random
  4. It lowers the top probability and raises the others, keeping the same ranking
Dividing the logits by a larger temperature flattens the softmax, so the leader loses probability and the tail gains it, but the order never changes. Sampling was already random at temperature 1; only the shape of the distribution differs.

You stream a response that ends in a tool request. When can your code safely run the tool?

  1. As soon as the tool name arrives in content_block_start
  2. After the fragments of partial_json have been joined and parsed at the end of the block
  3. After each input_json_delta, parsing it independently
  4. Only after the whole HTTP connection closes
The arguments arrive as JSON fragments that are not valid until complete, so you buffer them and parse at content_block_stop. Running on the name alone would use empty arguments. Waiting for the connection to close is later than needed, though it would also work.

With constrained decoding every reply is valid JSON matching your schema. Which problem can still occur?

  1. A well-formed reply whose field values are wrong, such as a non-existent order id
  2. A reply containing a stray sentence before the JSON
  3. A reply with a missing required key
  4. A string where the schema demands an integer
Constrained decoding guarantees form, not truth. Chatty framing, missing keys and wrong types are exactly what it prevents (barring refusals and truncation). Wrong content in a correctly shaped field is still possible, so business rules must be checked in code.

A 10-turn chat re-sends every earlier turn each time. Assume call k sends the 500-token system prompt plus 200 × (k − 1) tokens of history (ignore the new question). Which is closest to the total input tokens billed over the ten calls?

  1. 2,500
  2. 7,000
  3. 14,000
  4. 25,000
Call k sends 500 + 200(k − 1) tokens, so the total is 10 × 500 + 200 × (0 + 1 + ... + 9) = 5,000 + 9,000 = 14,000. 7,000 forgets that earlier turns are re-sent; 2,500 counts only the system prompt and two turns.

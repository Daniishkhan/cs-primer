Durable Execution for Agents

An agent that works for ten minutes, or waits three days for a manager's approval, will be interrupted: by a deploy, a crashed container, a rate limit or a closed laptop. This chapter explains how to make the interruption harmless. You will keep an event log, resume from it, make side effects safe to repeat, and pause for a human without holding a process open.

Why this matters

The loop in chapter 2 keeps its state in memory. That is fine for a demo and wrong for anything that sends money, email or tickets. When the process dies halfway, the memory is gone but the refund is not, and a naive restart either abandons the task or does it twice. Production agents, including the research systems in chapter 14, resume from where an error occurred rather than restarting. After this chapter you can build that: a journal-backed loop, idempotency keys that close the dangerous window, approval gates that survive a restart, and a short list of questions to ask of any framework that claims to be "durable". Lab 5 has you build it.

What breaks when an agent runs for a while

Most software that talks to people finishes in milliseconds, so a crash costs one retry. An agent is different in three ways. It runs for minutes to hours, because every step is a model call of several seconds. It acts on the world in the middle of that time, with tools that charge cards, write files and send messages. And it sometimes waits for people, who answer in hours or days. Each property turns an ordinary interruption into a design problem.

Interruptions are common and mundane. A rolling deploy replaces the container (the rainbow deployments in chapter 14 exist because of this). A process is killed for using too much memory. A cloud instance reserved at a discount is reclaimed. A provider returns a rate-limit error and your retry budget runs out. A person closes the tab. None needs a bug in your code.

The cost of handling this badly has two parts: the work you pay for twice and the actions you perform twice. Take the first. Suppose a run has n steps and each step independently has probability p of the process dying during it (both numbers are assumptions for illustration). A restart from scratch repeats everything done so far. Resuming repeats at most the interrupted step. The script simulates both with a fixed seed.

# restart_cost.py: how much work is thrown away when a run of n steps can die at any step? (p is ASSUMED)
import random

def attempts_scratch(n, p, rng):
    """Restart from step 1 after every crash. Returns (steps executed, crashes)."""
    executed = crashes = 0
    while True:
        for step in range(n):
            executed += 1
            if rng.random() < p:
                crashes += 1; break
        else:
            return executed, crashes

def attempts_resume(n, p, rng):
    """Resume at the step that was interrupted. The crashed step is repeated, nothing else."""
    executed = crashes = done = 0
    while done < n:
        executed += 1
        if rng.random() < p: crashes += 1
        else: done += 1
    return executed, crashes

rng, trials = random.Random(7), 20000
print(f"{'steps n':>8}{'p(crash)':>9}{'no crash':>10}{'scratch: steps':>16}{'resume: steps':>15}{'waste ratio':>13}")
for n, p in [(10, 0.01), (40, 0.01), (40, 0.03), (100, 0.01), (100, 0.03)]:
    s = sum(attempts_scratch(n, p, rng)[0] for _ in range(trials)) / trials
    r = sum(attempts_resume(n, p, rng)[0] for _ in range(trials)) / trials
    print(f"{n:>8}{p:>9.2f}{(1-p)**n:>9.0%}{s:>16.1f}{r:>15.1f}{s/r:>12.1f}x")

A ten-step run barely notices. A hundred-step run with a 3% chance of dying at each step needs about 667 steps of work with restarts from scratch, against 103 when it resumes: 6.5 times the model calls, and in practice several times the bill and the wait. Agent runs are heading towards the long, many-step end of this table, and the exponent is why durable execution matters more as agents get more capable. The second cost, repeated actions, is worse than any bill, and most of this chapter is about it.

Three ways to survive a crash

Durable execution means that a program's progress is stored outside the process, so that a new process can continue where the old one stopped and finish the job exactly once as far as the outside world can tell. There are three broad designs, from weakest to strongest.

Restart from scratch
Keep nothing. Run again from the first step. Correct only if every step is safe to repeat and cheap, which an agent that sends refunds is not.
Checkpoint
A checkpoint is a saved snapshot of the agent's state (its messages, its variables, where it was) at a known point, such as the end of each step. After a crash, load the latest snapshot and continue. LangGraph's persistence works this way: a checkpointer saves graph state, and a thread_id picks which saved state to load.
Event log (journal)
An event log, also called a journal, is an append-only list of everything that happened: each model reply, each tool result, each human decision. The current state is not stored at all; it is computed by reading the log from the start. Temporal calls its version the Event History and describes it as the source of truth for a workflow.

Checkpoints and logs are close relatives. A checkpoint is a log that has been folded into a value; a log is a stream of checkpoints' differences. The distinction that matters for agents is what each makes easy. A checkpoint is quick to load and cheap to understand, but it records where you are, not what was done to the world on the way. A log keeps the history, so it can answer "was the refund issued?" after the fact, audit what the agent did, and rebuild state in any shape you later need. The same idea is known as event sourcing, and a log makes recovery tractable. This chapter uses a log because the hardest problem, side effects, needs a record of intent.

A journal-backed agent loop

Here is the whole idea in about forty lines. The loop is the one from chapter 2, with one change to its structure: at the top of every iteration it reads the journal to find out what to do next, and every decision or observation is appended to the journal before the loop moves on. If the journal ends with a model reply that asked for tools, the missing tool results are the next job. If it ends with a tool result, the model is asked what to do next. If it ends with a model reply that contains only text, the run is finished.

Two design rules sit behind this code.

  1. Log the non-deterministic parts, recompute the rest. A model gives different answers when asked twice, so its reply is a fact to be recorded, not recomputed. Tool results from the world are facts too. The message list the model sees is derived: rebuild folds the journal into it every time. This is why a resumed run does not ask the model again about steps it has already taken.
  2. Write the event before you act on it, and fsync. fsync asks the operating system to flush the file to disk; without it a power cut can lose events the program believes are saved (see the files and filesystems chapter). An event counts only once it is durable.
# durable.py: an event-sourced agent loop. The journal file is the only state.
import json, os
from llm import tool_result

class Crash(Exception):
    """Stands in for a power cut, an OOM kill or a deploy."""

def append(path, event):
    with open(path, "a") as f:
        f.write(json.dumps(event) + "\n")
        f.flush(); os.fsync(f.fileno())          # an event counts only once it is on disk

def load(path):
    return [json.loads(line) for line in open(path)] if os.path.exists(path) else []

def rebuild(task, log):
    """Fold the journal back into the message list the model sees."""
    msgs = [{"role": "user", "content": task}]
    for ev in log:
        if ev["type"] == "model":
            msgs.append({"role": "assistant", "content": ev["content"]})
        elif ev["type"] == "result":
            if msgs[-1]["role"] == "assistant":
                msgs.append({"role": "user", "content": []})
            msgs[-1]["content"].append(tool_result(ev["id"], ev["output"]))
    return msgs

def run(task, path, model, tools, run_id="run1", use_key=True, hook=lambda phase, name: None, max_calls=6):
    while True:
        log = load(path)
        last = next((e for e in reversed(log) if e["type"] == "model"), None)
        uses = [b for b in last["content"] if b["type"] == "tool_use"] if last else []
        if last and not uses:
            return last["content"][0]["text"]                       # final answer
        done = {e["id"] for e in log if e["type"] == "result"}
        todo = [u for u in uses if u["id"] not in done]
        if todo:                                                    # execute what the journal says is pending
            seq = sum(e["type"] == "model" for e in log)
            for u in todo:
                key = f"{run_id}:{seq}:{u['id']}" if use_key else None
                hook("before", u["name"])
                out = tools[u["name"]](u["input"], key)             # the side effect happens here
                hook("after", u["name"])                            # ...and the result is not yet recorded
                append(path, {"type": "result", "id": u["id"], "output": out})
        else:                                                       # ask the model what to do next
            if sum(e["type"] == "model" for e in log) >= max_calls:
                raise RuntimeError("model-call budget exhausted")
            resp = model.complete(rebuild(task, log), tools=[])
            append(path, {"type": "model", "content": resp.content})

Notice what run does with the model's reply to "refund order 42": it appends the reply, including its tool_use block and that block's id, before it executes the tool. That ordering is the seed of the next section. The id the model chose is now permanent, so it can be used to name this particular attempt to refund.

Analogy: the ship's logbook

A ship's officers do not trust their memories of the voyage. Every course change, reading and order goes into the logbook as it happens, and a new watch officer takes over by reading it, not by asking the previous one. If the first officer collapses mid-watch, the second still knows where the ship is and what was ordered.

Where it breaks down: an officer writes the entry and then acts, or acts and then writes, and a log kept at sea cannot tell you whether the last order was carried out before the officer collapsed. For software that gap is the hardest case, because the world can have changed without the log knowing. The next section is about that gap.

The window between doing and recording

The journal records what the agent decided and what it was told. It cannot atomically include what the world did, because the world is a different system (the same limit as in any network call: you cannot tell a request that failed from a reply that was lost). Look at the two lines in run that matter:

out = tools[u["name"]](u["input"], key)    # 1. the refund happens in the bank
                                           #    ---- the process can die here ----
append(path, {"type": "result", ...})      # 2. the journal learns about it

If the process dies between the two lines, the bank has issued the refund and the journal does not know. The restarted process reads the journal, sees a refund request with no result, and does the sensible thing from where it stands: runs it again. Two refunds. No choice of ordering removes this: record first and you risk a result you never produced; act first and you risk an action you never recorded. The honest guarantee a journal gives for actions is at-least-once. To get effectively-once, the repeated attempt must be recognised by the other side as a repeat.

That is what an idempotency key does. The caller attaches a unique string to the request; the service stores the outcome under that string and, if it sees the key again, returns the stored outcome rather than acting a second time. Stripe's API popularised the approach for payments. The agent-specific question is where the key comes from.

  • A random key generated at call time is useless: the restarted process generates a different one.
  • A timestamp-based key fails the same way.
  • A key derived from the journal works: the run's id, the position of the model event that asked for the action, and the tool-call id. All three are in the journal before the effect happens, so every attempt, in every process, computes the same key. That is the f"{run_id}:{seq}:{u['id']}" in the listing. Including the position matters because a model can legitimately make the same call twice in one run (two identical-looking refunds for two different reasons), and those must not collapse into one.
Step through

A crash inside the window, and the key that closes it

  1. Intent first. The model asks for a refund of order 42. The loop appends that reply to the journal, which fixes the tool-call id, and derives the idempotency key K from the run, the position and that id.
  2. The effect. The loop calls the bank with K. The bank issues refund number 1 and stores the outcome under K.
  3. The crash. The process is killed after the bank acted and before the loop wrote the result. The journal holds the request but no result, and the bank's reply goes nowhere. This is the window.
  4. Recovery starts. A new process starts with empty memory, loads the journal, and finds a refund with no result. From its point of view the refund may or may not have happened.
  5. Repeat the call, same key. It does the safe thing: calls the bank again. K is computed from journal contents, so it is identical to the first attempt's.
  6. The bank recognises K. It finds the stored outcome and returns it without refunding again. The customer has one refund.
  7. Record and continue. The result goes into the journal. The model is called next, with exactly the messages it would have seen had nothing gone wrong.

Now the experiment that the diagram only describes. crash_demo.py runs a refund task, kills the agent at two moments (just before the refund call and just after it, before the result is recorded), restarts it, and counts refunds at the bank. The "bank" is a plain object that outlives the agent, with an optional idempotency key. The model is a stateless ScriptedModel from lab-support/llm.py: its reply depends on the messages, so a restarted process can ask it again and get the right continuation.

# crash_demo.py: kill the agent at every awkward moment, restart it, count the refunds
import os, tempfile
from llm import ScriptedModel, tool_use, text_of
import durable

class Bank:                                   # an external system: it outlives the agent process
    def __init__(self): self.refunds, self.seen = [], {}
    def refund(self, args, key):
        if key in self.seen: return self.seen[key]           # same key: replay the first answer
        self.refunds.append(args["order"]); out = f"refund #{len(self.refunds)} issued"
        if key: self.seen[key] = out
        return out

def script(messages, tools, system):          # a stateless stand-in: the reply depends on the history only
    n = sum(1 for m in messages if isinstance(m["content"], list) for b in m["content"] if b["type"] == "tool_result")
    return [[tool_use("lookup", {"order": 42})], [tool_use("refund", {"order": 42})], "Order 42 refunded."][n]

def trial(strategy, crash_phase):
    bank, path, model_calls = Bank(), tempfile.mktemp(), 0
    tools = {"lookup": lambda a, k: "order 42: delivered, 30.00", "refund": bank.refund}
    state = {"armed": True}
    def hook(phase, name):                    # crash once, around the refund
        if state["armed"] and name == "refund" and phase == crash_phase:
            state["armed"] = False; raise durable.Crash()
    for attempt in range(2):                  # attempt 0 crashes; attempt 1 is the restart
        if strategy == "restart from scratch" and attempt == 1 and os.path.exists(path): os.remove(path)
        model = ScriptedModel(script)
        try:
            durable.run("Refund order 42", path, model, tools, use_key=(strategy == "journal + keys"), hook=hook)
        except durable.Crash:
            pass
        model_calls += len(model.calls)
    return len(bank.refunds), model_calls

Read the table as a decision list. Restarting from scratch pays for five model calls instead of three, and refunds twice if the crash falls after the effect. A journal alone saves the model calls, and still refunds twice in the window, because it cannot see the refund that the dead process did. A journal plus keys is correct at both crash points. The journal and the key solve different halves of the problem, and you need both.

Common misconception

"If I save the conversation after every step, the agent is safe to restart." Saving messages records what the model has seen, not what the world has done. The crash window above lies between two saves: the effect happened, the save did not. A conversation snapshot with no idempotency discipline restarts correctly and still refunds twice. Durable state and safe side effects are two separate guarantees.

Not every tool can take a key

An idempotency key needs cooperation from the other side. Most of the tools an agent uses fall into four groups, and the right treatment differs.

Kind of toolExampleIf repeatedWhat to do
Read-onlyLook up an order, search the webHarmless, only costs timeRepeat freely. The journal lets you skip it anyway.
Naturally idempotent writeSet status to "shipped", PUT a file at a pathSame final stateRepeat freely. Prefer these shapes when you design tools (chapter 5).
Keyed writePayment or refund API with an idempotency keyService replays the first answerDerive the key from the journal, as above. Pass it on every attempt.
Unkeyed writeSend an email, post to chat, call a legacy APIA second email, a second postLook before you leap: check whether it already happened (search sent mail for the message id you stamped in). Otherwise say so and gate it behind a human (below).

For the last group, put a deterministic marker into the effect itself (a header, a field, a subject tag containing the key) so that "did I already do this?" becomes a query. Where even that is impossible, treat the step as at-least-once, record that decision where the design is reviewed, and make duplicates cheap: an email that is a notification is tolerable twice, a wire transfer is not. When a later step fails after an irreversible one, the repair is a compensation, the saga pattern: a new action that cancels the earlier one's business effect, itself journalled and keyed.

Systems connection

Everything in this section is the standard material on partial failure, applied to a loop with a language model inside. The bank and the agent cannot share a transaction, so the "two generals" problem appears again. The key that turns at-least-once into effectively-once is the idempotency key described earlier in this chapter. The journal is a write-ahead log: databases use the same log-then-apply idea, with checkpoints.

Replaying code versus restoring state

The loop above rebuilds messages from the journal and lets the loop's own logic decide what to do next. That is a design choice, and the two systems most agent teams meet make it differently.

Temporal is a general durable-execution engine. In Temporal's documentation a workflow's Event History is "a complete, ordered log of everything that has already happened", and to resume a paused workflow Temporal re-runs the workflow code from the beginning and uses the history to steer it back to where it was. Work that touches the outside world (API calls, database queries, LLM invocations, file I/O) goes in activities. An activity's result is stored in the history, and during replay the stored result is returned instead of running it again. The cost of this design is a rule: the workflow code must be deterministic, meaning that given the same history it makes the same decisions. It must not read the system clock, draw random numbers or make network calls directly; it uses replay-safe versions that record their values once. Our run function is the same idea in miniature, and the "model reply" plays the part of an activity result.

LangGraph, a library for agent graphs, takes the checkpoint route. A checkpointer saves the graph's state as it runs; passing the same thread_id loads the saved state for that run, and a durable checkpointer is expected in production. Its human-in-the-loop primitive, interrupt(), pauses a node, saves the state and hands a value to the caller; Command(resume=...) with the same thread id continues, and the resume value becomes the return value of the paused interrupt() call. One caveat in the documentation is exactly the failure this chapter keeps returning to: on resume the node re-runs from its beginning, not from the line of the interrupt, so side effects before the interrupt should be idempotent or moved after it.

Both designs, correctly used, give the same two guarantees: progress survives a crash, and the world is not touched twice by the same logical step. Neither gives them for free. The effect-before-record window exists in both, and the answer in both is an idempotent effect.

State of play, October 2026

Durable-execution engines (Temporal is the best-documented) and graph libraries with checkpointers (LangGraph) are the two families agent teams meet most, and agent SDKs from the model labs increasingly expose some form of saved sessions or resumable runs. The statements about Temporal and LangGraph above come from their documentation as read in October 2026; both products change their APIs, defaults and hosted offerings often, so check the current pages before you copy code, and check what a "resume" feature actually guarantees about side effects. Anthropic's June 2025 post on its multi-agent Research feature says its system resumes from where an error occurred rather than restarting, and that deployments are staged gradually so running agents are not interrupted. The post does not publish an implementation.

Versioning: the code changes while runs are in flight

A run that lasts hours will often outlive the deploy that started it. The journal then holds events produced by version 1 of the system, and version 2 reads them. Four things can quietly differ: the prompt (a resumed run now has a different system prompt from the one that produced its history), the tool definitions (a journalled call refers to an argument that version 2 renamed), the tool behaviour, and the shape of the journal events themselves. In a code-replay engine a changed order of steps can make replay diverge from history and fail; in a state-checkpoint engine an old state may not fit a new graph.

Practical rules, all cheap to adopt on day one:

  • Write a version field in the first journal event: the prompt hash, the tool-schema hash and the code version.
  • Prefer draining to migrating: let running jobs finish on the old version while new jobs start on the new one, which is the rainbow-deployment idea from chapter 14 and the staged rollouts used for ordinary services.
  • Make tool changes additive: add an optional argument, keep the old name working for a release (the schema-evolution habits of databases and APIs).
  • When you must resume a job across a change, replay old events with old parsers and write new events in the new format.

Checkpoints, snapshots and a journal that grows

A journal grows with every step, and reading it from the start gets slower as the run gets longer. The standard cure from databases is a snapshot (also called a checkpoint): periodically store the folded state together with the position in the log it covers, so recovery loads the snapshot and replays only the tail. Databases use the same trick for write-ahead logs.

A subtle point for agents: context compaction is itself a decision that must be journalled. Chapter 10 describes summarising a long history into a shorter one. A summary is produced by a model, so it is not reproducible. If you replay the journal and "recompute" the summary, you get a different one, and the resumed agent now works from a different memory than the one that made the earlier decisions. Record the compaction as an event containing the summary text and which events it replaced. The same goes for anything else generated at run time that later steps depend on: a plan, a chosen random seed, a timestamp used in a decision.

What belongs in a snapshot beyond messages? Everything a restarted process would otherwise guess: the budget already spent (steps, tokens, money), the attempt counts for each step, any pending approvals, the run version, and the identifiers of external objects the run has created (the ticket number, the draft id) so it can find them again.

Human approval gates

Some actions should not happen without a person: sending a large refund, deleting data, emailing a customer, spending past a limit. An approval gate is a point in the run where the agent proposes an action, stops, and continues only when a human approves it. The security reasons are in chapter 19 and the permission prompts in chapter 20. The durability question is narrower: what happens to the agent while it waits?

If the agent holds a process open, it holds memory, a database connection and probably a model session, for as long as a manager takes to read an email. That cannot last a weekend, a deploy or a reboot. With a journal the answer is clean: the agent writes an approval_request event, exits, and costs nothing while it waits. The reviewer's decision is another event. Whatever process next picks up the run folds the journal, sees the decision, and goes on. The code below does exactly this for a refund over a limit of 25.00 and records what the journal looks like.

# approval_demo.py: a refund above 25.00 waits for a human; the process exits and a later one resumes
import hashlib, json, os, tempfile
from llm import ScriptedModel, tool_use
import durable
from crash_demo import Bank, script

class Paused(Exception): pass

def digest(args): return hashlib.sha256(json.dumps(args, sort_keys=True).encode()).hexdigest()[:8]

def gated(fn, path, limit):
    def wrapped(args, key):
        if args["amount"] <= limit: return fn(args, key)
        evs = durable.load(path)
        verdict = next((e for e in evs if e["type"] == "approval" and e["key"] == key), None)
        if verdict is None:
            if not any(e["type"] == "approval_request" and e["key"] == key for e in evs):
                durable.append(path, {"type": "approval_request", "key": key, "args": args, "hash": digest(args)})
            raise Paused(key)
        if verdict["hash"] != digest(args): return "error: approval was granted for different arguments"
        if verdict["decision"] != "approve": return "refused by reviewer: " + verdict["reason"]
        return fn(args, key)
    return wrapped

def decide(path, decision, reason="", shown=None):
    req = [e for e in durable.load(path) if e["type"] == "approval_request"][-1]
    durable.append(path, {"type": "approval", "key": req["key"], "decision": decision, "reason": reason,
                          "hash": shown or req["hash"]})

def attempt(path, bank):
    tools = {"lookup": lambda a, k: "order 42: delivered, 30.00", "refund": gated(bank.refund, path, 25.00)}
    def sc(messages, tools_, system):
        r = script(messages, tools_, system)
        if isinstance(r, list) and r[0]["name"] == "refund": return [tool_use("refund", {"order": 42, "amount": 30.00})]
        if isinstance(r, str) and messages[-1]["content"][0]["content"].startswith(("error", "refused")):
            return "I could not refund order 42: " + messages[-1]["content"][0]["content"]
        return r
    model = ScriptedModel(sc)
    try: out = durable.run("Refund order 42", path, model, tools)
    except Paused: out = "PAUSED, waiting for a human"
    print(f"  process exits with: {out}   (model calls this process: {len(model.calls)})")

bank, path = Bank(), tempfile.mktemp()
print("process 1"); attempt(path, bank)
print("a reviewer reads the request and approves"); decide(path, "approve")
print("process 2, started later"); attempt(path, bank)
print("refunds issued:", bank.refunds)
print("journal:")

    if e["type"] == "model":
        b = e["content"][0]; return f"{b['name']}({json.dumps(b['input'])})" if b["type"] == "tool_use" else b["text"]
    if e["type"] == "result": return e["output"]
    if e["type"] == "approval_request": return f"args hash {e['hash']}"
    return f"{e['decision']}, hash {e['hash']}"

  process exits with: I could not refund order 42: error: approval was granted for different arguments   (model calls this process: 1)
refunds issued: []

Three details in that output are the substance of a good gate.

  1. The approval is bound to the arguments. The request stores a hash of the exact arguments (c59f39f3), and the decision carries the hash the reviewer was shown. In the second run the decision was recorded against different arguments, so the tool refused to run and returned an error to the model. Without the binding, a prompt-injected agent could change the amount after approval, or a reviewer could approve "a refund" without knowing which. Approve the action, not the intent.
  2. The decision is an event, not a flag in memory. The audit trail needs to answer who approved what, when, and on which version. Add the reviewer's identity and a timestamp to the event; here they are left out to keep the listing short.
  3. The resumed process called the model once. It did not re-ask what to do about the lookup or the refund, because both were in the journal. The wait cost no tokens.

Rules for approval gates that hold up

  • Show the action, not the model's summary of it. The reviewer should see the tool name and the exact arguments the tool will receive, rendered by your code. A model's description of its own action can be wrong or can be shaped by an injected instruction.
  • Re-check preconditions on resume. Three days have passed. The order may have been refunded by another channel. The gate hands over to execution, and execution should read current state again before it acts, as a database re-validates a row after taking its lock.
  • Give requests an expiry. An approval for a refund that nobody decided on for ten days should lapse into "escalate or cancel", not wait forever.
  • Gate by risk, not by volume. A reviewer who approves two hundred requests a day clicks through all of them. Reserve the gate for actions that are irreversible or costly, and make the rest reversible (compensations) or bounded (limits).
  • Do not put interrupt in a loop or in a try/except that swallows it, and keep anything before the pause idempotent. LangGraph's documentation lists these as pitfalls for the same reason: the code after a resume is not the code that ran before the pause.
  • A denial is information. Return it to the model as a tool result (as the demo does) so it can explain, offer an alternative or stop. Do not let it retry the same call in a loop.

Retries, budgets and the step that kills the process

A durable agent needs the same discipline about retries as any distributed client, with two additions that come from the agent being a loop that spends money.

Retry by class of failure. A tool that times out is retried with backoff and jitter, within a cap. A tool that returns a clear business error ("order already refunded") is not retried: it is returned to the model as a result. A model call that is rate-limited waits; one that returns malformed output may be retried once with the error attached. Each of these decisions is an event in the journal, so a restart does not reset the counters.

Budgets live in the journal. Chapter 2 gave the loop an iteration budget and a token budget. If the counter is a variable in memory, a crash resets it to zero. A task that crashes on its fortieth step restarts with forty fresh steps, and a task that triggers a crash by design (a huge tool result that exhausts memory) gets an unlimited budget. Count from the journal: sum(e["type"] == "model" for e in log) is what the demo's max_calls check does.

Poison steps. Occasionally a particular step kills the process every time: a tool result that blows memory, a parser bug on one document. A durable agent will dutifully resume into the same crash forever. Defend with an attempt counter per step in the journal (write "attempt 3 started" before you execute), a limit, and a policy of what to do on exceeding it: mark the run as failed, route it to a human queue and stop. This is a dead-letter queue, a pattern familiar from event-driven systems.

The journal is your trace. Because every model reply, tool call, result and decision is already recorded with ordering, the journal is most of what you would put in a trace. Add timestamps, durations and token counts to each event and you can answer "what did the agent do, how long did each step take and what did it cost?" for a run last week. It is also the raw material for the evaluations in course A6 and for debugging by replay: load a failed run's journal, change the prompt, and re-run from the point of failure with the tool results held fixed.

Key takeaways

  • Agent runs are long, they act on the world and they sometimes wait for people. Interruptions are normal, so progress must live outside the process.
  • An append-only journal of model replies, tool results and human decisions lets any process rebuild the state. Log what is non-deterministic, recompute what is derived, and fsync before you move on.
  • Between doing an action and recording its result lies a window no ordering removes. A journal alone gives at-least-once effects; an idempotency key derived from the journal turns that into effectively-once.
  • Classify every tool: read-only, naturally idempotent, keyed, or unkeyed. Unkeyed writes need a way to ask "did this already happen?", a human gate, or an explicit at-least-once decision.
  • Temporal replays deterministic code against a recorded history; LangGraph restores checkpoints and may re-run a node from its start. Both require idempotent effects.
  • Version runs, journal generated artefacts such as summaries and plans, and keep budgets and attempt counts in the journal so that a crash cannot reset them.
  • An approval gate is an event, bound to the exact arguments by a hash, with an expiry. The agent exits while waiting and costs nothing.

Check your understanding

An agent journals every model reply and tool result. The process is killed after the payment API charged a card but before the result was written. On restart the agent repeats the call and the customer is charged twice. Which change fixes the cause?

  1. Write the result to the journal before calling the payment API
  2. Snapshot the whole conversation after every step instead of journalling events
  3. Send an idempotency key derived from journal contents (run id, event position, call id) with every attempt
  4. Ask the model on restart whether the charge happened
The effect and the record are in two different systems, so one can happen without the other whatever the order. A key that every attempt computes identically lets the payment service recognise the repeat. Writing the result first would record an outcome that may never have occurred. A snapshot has the same window. The model only knows what its messages say, and they do not contain the answer.

Why is the model's reply stored in the journal rather than recomputed during recovery?

  1. Asking again may give a different reply, so the resumed run would diverge from what was actually done, and it would cost tokens
  2. Model replies are too large to recompute quickly
  3. Providers forbid sending the same prompt twice
  4. Journalled replies make the model more accurate
The reply is a non-deterministic fact: the decision that was made. If the run recomputes it, the new answer might call a different tool than the one already executed. Size and speed are secondary, there is no such provider rule, and replay does not change the model's accuracy.

A run is paused on an approval. The reviewer's decision is stored as approve with a flag in the web server's memory, and the server is redeployed overnight. What is the problem, and what is the fix?

  1. No problem: flags in memory are fast, and the agent will just ask again
  2. The reviewer should approve twice for safety
  3. The agent should keep polling the server until it answers
  4. The decision is lost with the process; store it as an event in durable storage, bound to the hash of the proposed arguments
State needed after a restart must outlive the process. Asking the reviewer again is a poor experience and not a design. Polling keeps a process alive for a decision that may take days. Binding the decision to the arguments' hash also stops the approved action from being changed afterwards.

A run of 100 steps has a 3% chance of the process dying at each step. In the simulation, restarting from scratch needed about 667 steps of work and resuming needed about 103. What explains the large gap?

  1. Resuming makes each step faster
  2. Each crash from scratch discards all progress, and a clean 100-step run (5% chance) is rare, so the work is repeated many times; resuming repeats only the interrupted step
  3. Restarting from scratch has a higher crash probability per step
  4. The simulation counts model calls twice when resuming
The per-step probability is the same in both strategies. The difference is what a crash throws away: with 3% per step, only about 5% of 100-step attempts reach the end. Resuming never loses more than one step. The gap grows quickly with n, which is why it matters more as agents run longer.

LangGraph's documentation warns that on resume a node re-runs from its beginning, not from the interrupt call. A node sends a confirmation email and then calls interrupt() to ask for approval. What happens, and what should you do?

  1. Nothing: code before the interrupt is skipped on resume
  2. The email is sent once, because checkpoints record that it was sent
  3. The email can be sent again on resume; move it after the interrupt, or make it idempotent
  4. The graph raises an error and refuses to resume
The node's earlier code executes again, and a checkpoint of state does not stop an external call. Ordering the interrupt first, or making the call safe to repeat, removes the duplicate. The same reasoning applies to any replay-based design.

Your agent summarises its history when the context gets long. A recovered run replays the journal and re-runs the summarisation step. What is the risk, and how do you avoid it?

  1. No risk: the summary is deterministic given the same history
  2. A new summary may differ from the original, so the run continues from a different memory than the earlier decisions used; journal the summary as an event and reuse it
  3. Summaries are always lost on a crash, so skip them
  4. The journal becomes too large, so delete older events
A summary comes from a model call and is not reproducible. Anything generated at run time that later steps depend on (summaries, plans, random seeds, timestamps) should be recorded when produced. Deleting events does not help, and skipping compaction removes a needed capability.

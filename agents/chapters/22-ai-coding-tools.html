Working with AI Coding Tools

Chapter 18 explained how a coding agent works inside. This chapter is about working with one: the instruction files that carry your project's rules, how to ask for a change, why a plan and a runnable check matter more than a clever prompt, how to review what comes back, and how to find out honestly whether the tool makes you faster. It is a skill with its own failure modes, and it can be practised and measured.

Why this matters

Most engineers in the roles this path leads to will write a large share of their code through an agent, and many will be asked whether it is worth buying for a team. Two things go wrong. People who trust the output ship plausible code that nobody has run against the real requirement. People who distrust it spend more time arguing with the tool than the task would have taken. After this chapter you can set up a repository so that an agent starts well, structure a session so that its context stays useful, build the check that lets it correct itself, review its changes efficiently, and design a measurement of productivity that does not rest on how fast it feels.

Four ways to use a coding model

"AI coding tool" covers products that differ in how much of the work they do before you look. Four levels are useful to tell apart. In completion, the tool suggests the next few tokens or lines as you type, and you accept or ignore them. In chat, you ask for a function or an explanation and paste the answer. In an in-editor agent, the tool reads several files, edits them and runs commands, with you watching each step. In a terminal or background agent, you give it a task and it works through many steps, possibly in a sandbox on another machine, and returns a branch or pull request. Examples of the last two kinds include Claude Code, OpenAI's Codex, Cursor's agent mode and the GitHub Copilot coding agent; they are examples of a type, not a ranking.

As autonomy rises, your role changes from author to supervisor, and so does the failure you must guard against. With completion, a wrong suggestion is visible in the line you are typing. With a background agent, a wrong approach can produce six hundred lines before you see any of it. The mechanics of those agents (reading files, editing, running tests, handling context) are in chapter 18. Here the question is how a person gets good results from them, and the answer begins with a single constraint.

The constraint: context fills up

The official Claude Code best-practices guide puts it plainly: most of its advice follows from the fact that the context window "fills up fast, and performance degrades as it fills". Every message, every file read and every command output stays in the history (chapter 10). A debugging session or a codebase exploration can consume tens of thousands of tokens, and as the window fills the agent may start forgetting earlier instructions or making more mistakes. The effect has a measured side too: models use information in a long context unevenly (chapter 12).

Almost every habit in this chapter is a way to protect that budget:

  • One task per session. Clear the context between unrelated tasks. A session in which you fixed a bug, asked an unrelated question and returned to the bug carries all of that noise. The guide calls this "the kitchen sink session".
  • Restart after two failed corrections. If you have corrected the agent twice on the same point and it is still wrong, the context now contains the failed approaches. Start a fresh session with a better first prompt that includes what you learned. A clean session with a sharper prompt usually beats a long one with accumulated corrections.
  • Send investigation to a sub-agent. Reading fifty files to answer one question is the job for a separate context that returns a summary (chapter 14).
  • Scope exploration. "Investigate the auth system" invites the agent to read hundreds of files. "Find where token refresh happens and whether we already have an OAuth utility" does not.
  • Steer compaction. When the tool summarises an old conversation automatically, tell it what must survive, such as the list of modified files and the test commands.

Instruction files

The agent starts every session knowing nothing about your repository except what it can read. An instruction file is a short Markdown file at the root, loaded at the start of every conversation, that holds what the agent cannot work out from the code: commands, conventions and traps. Claude Code reads CLAUDE.md. AGENTS.md is an open convention described on agents.md as a "README for agents"; it is plain Markdown with no required fields, and in a monorepo the nearest file in the directory tree takes precedence. The site lists a long line of tools that read it, among them Codex, Cursor, Gemini CLI, Devin, Windsurf and GitHub Copilot's coding agent, and says the format is now stewarded by the Agentic AI Foundation under the Linux Foundation. The practical consequence is that one well-kept AGENTS.md serves several tools; a tool that reads only its own file can often be pointed at it with an import or a symlink.

What belongs in it

The test the Claude Code guide gives is a good one: for each line, ask whether removing it would cause the agent to make mistakes. If not, cut it. The guide's include and exclude lists reduce to a rule: write down what the agent cannot guess, and nothing it can read.

IncludeLeave out
Commands the agent cannot guess (how to run one test file, how to start the dev server)Anything it can learn by reading the code
Style rules that differ from the language defaultStandard conventions it already knows
Test instructions and preferred runnerLong API documentation (link to it)
Branch, commit and pull-request conventionsFacts that change often
Project-specific architecture decisions and traps ("money is integer cents")File-by-file descriptions of the codebase
Environment quirks (required variables, "the full suite needs Docker")Self-evident advice such as "write clean code"

The script below is a crude linter for that rule. It is a heuristic, so it finds candidates to cut rather than proving anything. It runs on a realistic first draft of a billing service's file.

# lint_instructions.py: a crude check of an instruction file (AGENTS.md / CLAUDE.md) against
# the "would removing this cause a mistake?" test. Heuristics only: it finds candidates to cut.
import re

SAMPLE = """\
# Project notes
This project is a billing service written in Python.
- Write clean, readable code.
- Use meaningful variable names.
- src/billing/invoice.py contains the Invoice class.
- src/billing/tax.py contains the tax rules.
- Run tests with: pytest -q tests/unit  (the full suite needs Docker; skip it)
- Money is stored as integer cents. Never use float for money.
- Migrations live in db/migrations. Never edit an applied migration.
- Always be careful and think step by step.
- Prefer small commits. PR titles: "billing: <summary>".
- Python 3.11, formatted with ruff format (CI fails otherwise).
"""

DERIVABLE = [r"\bclean\b.*\bcode\b", r"meaningful (variable )?names", r"think step by step",
             r"be careful", r"^- \S+\.py contains"]
COMMAND = re.compile(r"\b(pytest|npm|make|ruff|cargo|go test|run tests?)\b", re.I)

def lint(text, max_lines=200):
    findings, keep = [], 0
    lines = [l for l in text.splitlines() if l.strip().startswith("-")]
    for l in lines:
        if any(re.search(p, l, re.I) for p in DERIVABLE):
            findings.append(f"cut?  {l.strip()[:62]}")
        else:
            keep += 1
    if not COMMAND.search(text):
        findings.append("add?  no test or build command found")
    if len(text.splitlines()) > max_lines:
        findings.append(f"long: {len(text.splitlines())} lines, prune")
    return findings, keep, len(lines)

findings, keep, total = lint(SAMPLE)
print(f"{total} rules, {keep} pass the heuristic")
print(*findings, sep="\n")
10 rules, 5 pass the heuristic
cut?  - Write clean, readable code.
cut?  - Use meaningful variable names.
cut?  - src/billing/invoice.py contains the Invoice class.
cut?  - src/billing/tax.py contains the tax rules.
cut?  - Always be careful and think step by step.

Half of the draft's rules fail. "Write clean code" changes nothing, since the model already tries to. A line listing which file contains which class costs tokens in every session and goes stale when someone moves the file, while the agent can find the class in one search. The lines that stay are the ones that would otherwise cause a mistake: the test command (and the warning that the full suite needs Docker), integer cents, immutable migrations, the pull-request title format and the formatter that CI enforces.

Common misconception

"If I write more rules, the agent follows more of them." The reverse tends to happen. The guide says that if the file is too long, the agent ignores half of it because the important rules get lost in the noise, and that if the agent keeps doing something you forbade, the file is probably too long. Treat the file like code: prune it when things go wrong, and test a change by watching whether the agent's behaviour shifts. If you need a rule to be followed every time without exception, a rule in prose is the wrong tool, as the next section explains.

Advice, on-demand knowledge and enforcement

An instruction file is advice. The model reads it and usually complies, but nothing makes it. Knowing which mechanism gives which guarantee is the main design skill in configuring these tools. The names below are Claude Code's; other tools have close equivalents under other names.

The Claude Code guide draws the line explicitly: unlike instructions in the instruction file, which are advisory, hooks are deterministic and guarantee the action happens. Run formatting after every edit as a hook, not as a rule that the agent "should remember". Put knowledge that only some tasks need in a skill, so it enters the context when relevant instead of in every session (chapter 11). Use a sub-agent definition for a role such as a security reviewer, with its own tool list. And keep the strongest controls, permissions and sandboxing, for actions whose consequences you could not undo (chapter 20).

One more property deserves a warning. The instruction file is text the agent obeys, so anyone who can change it can steer the agent. A repository you clone from the internet, a pull request from a stranger or a file generated by another tool may carry instructions that you did not write. That is prompt injection arriving through the repository (chapter 19). Read an unfamiliar instruction file before you run an agent in that directory, in the same way that you would read a build script.

Asking for a change

The principle of the Claude Code guide, "the more precise your instructions, the fewer corrections you'll need", has four practical forms. Name the scope: which file, which scenario, what to avoid. Point to a source: "look through the history of this class and summarise how its API came to be" beats "why is this API odd?". Point to a pattern: "follow how HotDogWidget.php is implemented" gives the agent a house style to copy. And describe the symptom with its location and what "fixed" looks like.

VagueSpecific
Fix the login bugUsers report login fails after session timeout. Look in src/auth/, especially token refresh. Write a failing test that reproduces it, then fix it and run the auth tests.
Add tests for foo.pyWrite a test for foo.py covering the case where the user is logged out. Do not use mocks. Run it.
Make the report fasterThe monthly report takes 40 s on the staging data. Profile it, report the three slowest calls, propose a change for the worst one and confirm the output is byte-identical before and after.

Vague prompts are not forbidden. When you are exploring, a loose "what would you improve in this file?" can surface things you would not have asked about, and course-correcting is cheap. The cost of vagueness rises with the size of the task.

For a larger feature there is a stronger move: let the agent interview you. The guide suggests asking it to question you about the implementation, edge cases and trade-offs, write the answers into a SPEC.md, then start a fresh session to implement from the file. The new session has clean context devoted to the work, and you have a written artefact to point at. The guide notes that the most useful specs name the files and interfaces involved, state what is out of scope and end with an end-to-end verification step.

Plan before you code

An agent that starts editing immediately can solve the wrong problem at speed. The recommended workflow has four phases: explore (read-only), plan, implement, commit. Many tools support a plan mode in which the agent may read and search but not change anything, so exploration cannot damage the repository. The plan is a written list of the files to change, the steps and the tests. It is cheap to read and cheap to correct: if the approach is wrong you find out in a page of text, not in a 600-line diff.

The guide also says when not to. Planning adds overhead, and for a typo, a log line or a rename the right move is to ask for the change directly. Its rule of thumb is that if you could describe the diff in one sentence, skip the plan. Plan when the approach is uncertain, when the change touches several files, or when you do not know the code well. Step through a feature from request to merge, and watch the context bar.

Step through

One feature, seven stages, and what each does to the context

  1. Explore. In plan mode the agent reads the auth code and the environment handling, and answers questions. Nothing changes on disk. Large reads can be delegated to a sub-agent, which keeps them out of this context.
  2. Plan. The agent writes the files to change, the session flow and the tests. You edit the plan directly. This is the cheapest moment to be wrong.
  3. Implement. Plan mode off. The agent codes against its plan, running the tests as it goes. The context grows fast because command output is verbose.
  4. Verify. The type check, the tests, the linter and the build run. Failures return to the agent as text and it iterates. This stage is the subject of the next section.
  5. Agent review. A reviewer in a fresh context checks the diff against the plan and the requirements. It is asked to report correctness gaps, not style preferences.
  6. Human review. You read the diff, the test results and the screenshots or logs the agent attached. A check is only as good as the person who looks at the evidence.
  7. Commit. The agent commits and opens a pull request. Then the session is cleared. The next task starts with a near-empty context and the instruction file, which is what you want.

Give it a way to check its own work

If you take one thing from this chapter, take this. The Claude Code guide calls it the highest-leverage practice: give the agent a check it can run, such as tests, a build, a linter or a screenshot comparison. The reason is mechanical. The agent stops when its work looks done. Without a check it can run, looking done is the only signal it has, and you become the verification loop: every mistake waits for you to notice it. With a check, the loop closes by itself. The agent works, runs the check, reads the result and iterates until it passes.

Here the idea is run for real. A scripted stand-in model edits a real file in a temporary directory, and run_tests really runs unittest. The task is a classic money bug: split a bill of 1,000 cents among 3 people so the shares add up. The model's first attempt is the natural wrong one, integer division, which loses the remainder (333 × 3 = 999). In the first run nothing tells the agent to check; in the second it can run the tests.

# verify_loop.py: the same coding task with and without a runnable check.
# A scripted "model" edits a real file in a temp directory; run_tests really runs unittest.
import os, subprocess, sys, tempfile, textwrap
from llm import ScriptedModel, tool_use, text_of, tool_calls, tool_result

TESTS = textwrap.dedent('''
    import unittest
    from bill import split_bill
    class T(unittest.TestCase):
        def test_sum(self):  self.assertEqual(sum(split_bill(1000, 3)), 1000)
        def test_len(self):  self.assertEqual(len(split_bill(1000, 3)), 3)
        def test_fair(self): self.assertLessEqual(max(split_bill(1000, 3)) - min(split_bill(1000, 3)), 1)
    unittest.main()
''')
BAD  = "def split_bill(total, n):\n    return [total // n] * n\n"
GOOD = "def split_bill(total, n):\n    q, r = divmod(total, n)\n    return [q + (1 if i < r else 0) for i in range(n)]\n"

def run(script):
    d = tempfile.mkdtemp()
    open(os.path.join(d, "test_bill.py"), "w").write(TESTS)
    def execute(call):
        if call["name"] == "write_file":
            open(os.path.join(d, "bill.py"), "w").write(call["input"]["content"]); return "written"
        r = subprocess.run([sys.executable, "test_bill.py"], cwd=d, capture_output=True, text=True)
        return (r.stderr.strip().splitlines() or [""])[-1] + f"  (exit {r.returncode})"
    model, msgs, log = ScriptedModel(script), [{"role": "user", "content": "Fix split_bill so shares add up."}], []
    while True:
        resp = model.complete(msgs); msgs.append(resp.as_message())
        calls = tool_calls(resp)
        if not calls: return text_of(resp), log, d
        out = []
        for c in calls:
            res = execute(c); log.append(f"{c['name']:<10} -> {res}")
            out.append(tool_result(c["id"], res))
        msgs.append({"role": "user", "content": out})

w = lambda src: tool_use("write_file", {"content": src})
t = lambda: tool_use("run_tests", {})
print("== no check: the agent stops when it looks done ==")
say, log, d = run([[w(BAD)], "Done: shares now split evenly."])
print(*log, sep="\n"); print("agent says:", say)
print("independent run of tests:", subprocess.run([sys.executable, "test_bill.py"], cwd=d, capture_output=True, text=True).stderr.strip().splitlines()[-1])
print("\n== with a check: the agent iterates until the tests pass ==")
say, log, d = run([[w(BAD)], [t()], [w(GOOD)], [t()], "Done: remainder spread over the first shares; tests pass."])
print(*log, sep="\n"); print("agent says:", say)
== no check: the agent stops when it looks done ==
write_file -> written
agent says: Done: shares now split evenly.
independent run of tests: FAILED (failures=1)

== with a check: the agent iterates until the tests pass ==
write_file -> written
run_tests  -> FAILED (failures=1)  (exit 1)
write_file -> written
run_tests  -> OK  (exit 0)
agent says: Done: remainder spread over the first shares; tests pass.

The stand-in follows a script, so it does not prove how a real model behaves, but the mechanism is the point. Without a check, "Done" is a claim. The independent run fails. With a check, the failure came back as text, the second edit spread the remainder over the first shares, and "Done" is accompanied by a green result. This is the same principle as end-state checks in agent evaluation: grade the world, not the agent's description of it.

Choosing the check

Any command that returns a signal the agent can read will do. Ordered roughly from cheap to expensive:

  • Type check and linter. Seconds, and they catch a large class of mechanical mistakes. Run them after every batch of edits.
  • The relevant unit tests. Prefer running one file or one test (an instruction-file line like "prefer running single tests") to the whole suite, to keep both time and output small.
  • A failing test written first. For a bug, ask for a test that reproduces it before the fix. A test that fails for the right reason is the best specification the agent can get.
  • The build and integration tests. Slower; use at the end.
  • A visual check. For user interfaces, a screenshot compared with a design, with the agent asked to list the differences.
  • A script that diffs output against a fixture. For refactoring and migration, where behaviour must not change: golden files, or byte-identical output on sample data.

The guide also says how hard a check should gate the agent's stopping. The weakest form is a sentence in the prompt asking it to run the tests. A stronger one is a stop hook that runs your script and refuses to let the turn end until it passes, which is deterministic rather than advisory. The strongest is a second opinion: another agent, in a fresh context, tries to refute the result, so the author is not also the grader. Ask the agent to show evidence (the output, the command and what it returned) rather than assert success. Reviewing evidence is faster than redoing the verification yourself.

Common misconception

"If the tests pass, the change is correct." The tests are part of what the agent can change. An agent under pressure to make a check pass can weaken an assertion, special-case the test input or delete the failing test, and the run turns green. Evaluation research has documented this as evaluator hacking, for example in claimed GPU-kernel speed-ups that came from loopholes in the checker (A6 case 2). The defence is structural: protect test files with a permission or hook, review changes to tests separately and first, and keep some checks (a held-back test, a human spot check) that the agent never sees.

Reviewing what comes back

When writing is cheap, review is the scarce resource. A change that took the agent ten minutes can take you an hour to understand, and the temptation is to skim because the code looks tidy and the tests pass. The guide names this the trust-then-verify gap: a plausible implementation that does not handle edge cases. Several habits keep review honest.

  1. Keep changes small. Ask for one reviewable change per task. A 150-line diff with a clear purpose is reviewed; a 1,500-line diff is approved. If the agent's plan lists twelve files, split the work before it starts.
  2. Read the plan, then the tests, then the code. The tests say what the author believes is correct. If a test was changed or removed, stop and find out why. Then check the code against the plan, looking for files you did not expect to see touched.
  3. Check the interfaces and the dependencies. New public functions, changed signatures, new packages and changed configuration deserve more attention than the body of a private helper. A new dependency is a supply-chain decision (security chapter 12).
  4. Ask for evidence and read it. The test output, a before and after comparison and a screenshot are cheaper to check than a paragraph of assurance.
  5. Use a reviewer that did not write it. A reviewing agent in a fresh context sees only the diff and your criteria, not the reasoning that produced the change, so it evaluates the result on its own terms. The guide's Writer and Reviewer pattern puts two sessions side by side: one implements, the other reviews, and the first addresses the findings.
  6. Tell the reviewer what counts. The guide warns that a reviewer asked to find gaps will usually find some, even when the work is sound, and chasing every finding leads to over-engineering: extra abstraction, defensive code, tests for cases that cannot happen. Ask for gaps against the stated requirements and for correctness problems, and treat the rest as optional.

Human review is also where design judgement lives: whether this is the right place for the logic, whether the change fits the architecture, whether a simpler approach exists. A coding agent has no stake in the codebase's future. Code review practice for teams, covering who approves what and how CI gates merges, is in architecture chapter 21; the agent changes who writes the diff, not why the gate exists.

More than one at a time

Once one session works, the next idea is several. Each session needs its own copy of the files, or they overwrite each other, so the usual tool is the git worktree: a second working directory of the same repository on its own branch. The guide lists worktrees, a desktop view of several sessions, cloud sessions, and an experimental team mode in which a lead coordinates others. For a large mechanical change, such as migrating two thousand files, a shell loop can run one non-interactive agent call per file: test the prompt on two or three files, refine it, then run the rest, with the allowed tools pre-approved so that an unattended run cannot ask for permission it will never get.

The coordination lessons of chapter 14 apply unchanged. Parallelism helps when tasks are independent and touch different files. Two sessions editing the same module produce merge conflicts or, worse, incompatible assumptions. The limiting resource is usually your own attention for review, not the number of sessions you can start, so measure how many parallel streams you can review well before you scale up.

What can go wrong with access

A coding agent runs commands and edits files on your behalf, so it holds your authority. Three risks matter in practice.

Approval fatigue. In a mode that asks before each action, the guide notes that after the tenth approval you are clicking through rather than reviewing. Allow-lists for commands you trust (such as the linter, the test runner and a commit) and a sandbox that confines file and network access let the agent work freely inside boundaries, so that your attention goes to the few actions that matter (chapter 20).

Untrusted input. The agent reads issues, web pages, dependency documentation and tool output, any of which may contain instructions aimed at it. An agent that can read private code, read untrusted text and send data out has the combination described as the lethal trifecta (chapter 19). Keep secrets out of the working directory, restrict network access, and treat an agent that is processing external text as less trusted than one working on your own files.

Production reach. The cheapest safeguard against an agent damaging something important is not giving it that access. Case study 6 examines a coding agent with production access that ignored a code freeze. Use credentials scoped to a development environment, make destructive commands require confirmation by a hook, and rehearse restoring from backup (reliability chapter 18). The agent's good intentions are not a control.

Does it actually help?

Many claims about AI coding tools are about how they feel. The best-known careful measurement found that feelings can mislead, so it is worth reading closely.

In 2025 the research group METR ran a randomised controlled trial. It recruited 16 experienced open-source developers, each working on large repositories they knew well (on average more than 22,000 stars and over a million lines of code). The developers brought 246 real issues, averaging about two hours each. Each issue was randomly assigned to allow or disallow AI tools; when allowed, developers mostly used Cursor Pro with Claude 3.5 and 3.7 Sonnet, the frontier tools of early 2025. The result: with AI allowed, tasks took 19% longer. Before starting, the developers had forecast that AI would make them 24% faster, and after finishing they still believed it had made them about 20% faster. The measured effect and the belief were on opposite sides of zero.

METR was careful about what this does and does not show. Sixteen developers is a small sample from one setting (experienced people on familiar, mature codebases), and learning effects beyond about 50 hours of tool use could not be ruled out; the authors list five of twenty examined factors as likely contributors to the slowdown. The post is itself marked as out of date, and the follow-up is worth knowing.

State of play, October 2026

METR's February 2026 update (24 February) reported a larger study with newer tools: 57 developers (10 from the first study, 47 new), 143 repositories and more than 800 tasks, paid $50 an hour instead of $150. It estimated the change in task time for the returning developers at -18% (interval -38% to +9%) and for new recruits at -4% (interval -15% to +9%), where a negative number means less time with AI. Both intervals include zero. METR did not present this as a measurement of the new speed-up. It said the late-2025 data is an unreliable signal, likely a lower bound on the benefit, because a rising share of developers did not want to work without AI: 30% to 50% said they withheld tasks they did not want to do without it, tasks were chosen to suit AI, and developers running several agents at once made time tracking unreliable. METR's view is that developers are probably more sped up now than in early 2025, but that its data is only very weak evidence of how much, and it is redesigning its experiments. Some secondary coverage reports the sign of these numbers inconsistently, so read the primary post. All of this will have moved again by the time you read this.

The lasting lesson is not a number. It is that the perception of speed is a poor measurement, and that measuring productivity is hard even for specialists. Waiting for the agent feels like progress. Fast first drafts feel like finished work. Time spent reviewing, correcting and debugging code you did not write is easy to forget, and it arrives later than the satisfaction does.

Measuring it on your own team

You do not need METR's scale to learn something about your own work, but you need to be honest about what small samples can say. Four principles carry over.

  • Measure outcomes, end to end. Time from starting a task to a merged change that stayed merged, including review time and rework, not time to a first draft. Track what happens afterwards too: defects found after merge, reverts and the review time a change consumed.
  • Randomise, or at least compare like with like. Allow or disallow the tool at random per task, within the same person where possible. Comparing "people who use it" with "people who do not" mixes up the tool with who chooses it.
  • Report an interval, not a number. Task times vary enormously, so a small study has a wide range of plausible effects.
  • Watch for the metric becoming the goal. Count lines or pull requests and you will get more of both. A measure that rewards volume will not find a tool that improves quality.

The simulation below shows the statistics problem, using assumed numbers and a seeded generator. Suppose AI truly makes a task take 0.90 times as long as without it, a 10% improvement. Task times are spread widely (a log-scale standard deviation of 0.7, so the slow tasks are several times the quick ones). We run four studies of increasing size, each with a different number of tasks in each arm, and compute the ratio of geometric-mean times with a 95% bootstrap interval. The interval is the range of effects the data cannot rule out.

# measure.py: how many tasks does it take to see a small speed-up? (SIMULATED, assumptions below)
import math, random
random.seed(22)
MEDIAN_MIN = 120      # assumed median task time without AI, minutes
SIGMA = 0.7           # assumed spread of log task time (tasks differ a lot)
TRUE_RATIO = 0.90     # assumed truth: tasks take 10% less time with AI

def study(n_per_arm):
    base = [random.lognormvariate(math.log(MEDIAN_MIN), SIGMA) for _ in range(n_per_arm)]
    ai   = [random.lognormvariate(math.log(MEDIAN_MIN * TRUE_RATIO), SIGMA) for _ in range(n_per_arm)]
    return [math.log(x) for x in base], [math.log(x) for x in ai]

def ratio_ci(base, ai, reps=2000):
    """Ratio of geometric-mean times (AI / no AI) with a 95% bootstrap interval."""
    mean = lambda v: sum(v) / len(v)
    est = math.exp(mean(ai) - mean(base))
    boots = sorted(math.exp(mean(random.choices(ai, k=len(ai))) - mean(random.choices(base, k=len(base))))
                   for _ in range(reps))
    return est, boots[int(0.025 * reps)], boots[int(0.975 * reps)]

print(f"assumed truth: AI tasks take {TRUE_RATIO:.2f}x the time (10% faster); spread sigma={SIGMA}")
print(f"{'tasks per arm':>13} {'estimate':>9} {'95% interval':>16}  verdict")
for n in (8, 30, 120, 480):
    est, lo, hi = ratio_ci(*study(n))
    verdict = "interval contains 1.00: cannot tell" if lo <= 1 <= hi else "excludes 1.00: faster"
    print(f"{n:>13} {est:>9.2f} {f'{lo:.2f} to {hi:.2f}':>16}  {verdict}")
need = 2 * (1.96 + 0.84) ** 2 * SIGMA ** 2 / math.log(TRUE_RATIO) ** 2
print(f"\ntasks per arm for about 80% power at this effect and spread: {math.ceil(need)}")
assumed truth: AI tasks take 0.90x the time (10% faster); spread sigma=0.7
tasks per arm  estimate     95% interval  verdict
            8      0.58     0.27 to 1.23  interval contains 1.00: cannot tell
           30      0.88     0.62 to 1.20  interval contains 1.00: cannot tell
          120      0.82     0.69 to 0.97  excludes 1.00: faster
          480      0.89     0.81 to 0.98  excludes 1.00: faster

tasks per arm for about 80% power at this effect and spread: 693

Two lessons. First, a study that is too small does not merely fail to find an effect: it produces confident-looking estimates that are far off, such as the 0.58 above, which would have been read as a 42% saving. Second, the sample sizes needed for a modest effect are large. The explorer below lets you change the assumed effect, the spread and the number of tasks. Try a 10% speed-up with 30 tasks per arm, and then raise the matching slider: matching tasks across arms (the same person doing similar tasks with and without the tool) removes part of the variation and cuts the number of tasks you need a great deal. (Its default effect is expressed as a speed-up of 10%, a time ratio of 0.91, so the numbers differ a little from the script's 0.90.)

For a team the realistic design is therefore modest: a pilot of a few weeks with the tool allowed on a random half of comparable tasks, outcomes tracked end to end, an interval reported, and the conclusion held loosely. The statistics of intervals and paired comparisons are in A6 chapter 4. The economics (what a licence costs against engineer time, and the cost of review) belong to A8 chapter 14.

Habits that hold up

Put together, the practices are few and consistent. They are also the guide's list of common failure patterns, turned around.

Protect the context

One task per session. Clear between tasks. Restart after two failed corrections. Delegate reading to sub-agents. Scope every investigation.

Close the loop

Name the check in the prompt. Prefer a failing test first. Gate stopping with a hook where it matters. Ask for evidence, and protect the tests.

Keep the file lean

Instruction file: only what the agent cannot guess. Prune it when the agent ignores rules. Convert must-always rules into hooks or permissions.

Systems connection

Nothing here replaces engineering practice; it makes the practice matter more. A fast, trusted test suite and a CI pipeline are the check that lets an agent iterate (architecture chapter 21). Small changes behind feature flags and gradual rollouts limit the damage of an unreviewed mistake (reliability chapter 12). Least privilege and blast-radius thinking decide what a runaway session can reach (security chapter 2, reliability chapter 15). Finally, a team that cannot say what a good change looks like, or how it would notice a regression, will not be rescued by a faster author: an agent amplifies the quality of the process around it.

Key takeaways

  • As tools move from completion to background agents, you move from author to supervisor, and the main constraint becomes the context window, which fills fast and degrades as it fills.
  • Protect the context: one task per session, restart after two failed corrections, delegate investigation to sub-agents, scope every exploration.
  • An instruction file (AGENTS.md, CLAUDE.md) should hold only what the agent cannot guess. It is advice. Rules that must always hold belong in hooks, permissions or a sandbox, and an untrusted repository's instruction file is an injection path.
  • Explore, plan, implement, commit. A plan is the cheapest place to be wrong; skip it when one sentence describes the diff.
  • Give the agent a check it can run, ideally a failing test first, and ask for evidence. Without a check, "done" means "looks done". Protect the tests from the agent.
  • Review is the scarce resource: small diffs, plan then tests then code, evidence over assurance, a fresh-context reviewer told what counts as a finding.
  • Do not trust the feeling of speed. In METR's 2025 trial developers were 19% slower but believed they were faster; the 2026 follow-up was inconclusive for stated reasons. Measure end to end, randomise by task, and report an interval.

Check your understanding

You told an agent twice not to touch the legacy billing module, and it still edited it. The instruction is in a long AGENTS.md. What is the most reliable fix?

  1. Repeat the rule in capital letters at the top and bottom of the file
  2. Enforce it outside the model, with a permission rule or a hook that blocks writes to that directory, and prune the file
  3. Add a longer explanation of why the module is sensitive
  4. Switch to a different instruction-file format
An instruction file is advice, and a long one loses rules in the noise. Something that must never happen should be enforced by the system: a deny rule or a deterministic hook. Emphasis helps only for a single line, and only a little; explanations add length; the file format is not the cause.

An agent reports "all done, tests updated and passing" on a bug fix. Which review step gives the most protection?

  1. Ask the same session to confirm it ran the tests
  2. Read the summary the agent wrote at the end
  3. Check that the diff is short
  4. Look first at what changed in the test files, then run the tests yourself or read the attached output against the original failing test
The tests are among the things the agent can change, so a green run is weak evidence until you know what happened to the tests. The same session confirming itself and its own summary are the claim, not the evidence. A short diff is good, but a one-line change to an assertion is short and wrong.

You have corrected an agent three times on the same misunderstanding and the answers keep getting worse. What does the chapter recommend?

  1. Clear the session and start again with a sharper first prompt that includes what you learned
  2. Keep correcting, since the model is learning your preferences
  3. Add the correction to the end of the conversation in bold
  4. Ask the agent to summarise the conversation and continue in the same session
After repeated failed corrections, the context contains the failed approaches, and the model is conditioned on them. A fresh session with a better prompt almost always beats a long one with accumulated corrections. The model does not learn within the conversation in the way option two suggests, and a summary carries the clutter forward.

A manager says "my developers tell me they are 30% faster with the coding agent, so we will plan for that." Using the chapter's evidence, what is the best response?

  1. Accept it, because developers know their own work best
  2. Reject it, since the 2025 study proves AI tools slow people down
  3. Treat it as a hypothesis: self-reports diverged from measured time in the METR trial, so run a short randomised pilot that measures end-to-end outcomes and report an interval
  4. Ask the developers to count lines of code per day instead
In the 2025 trial, developers believed AI sped them up by about 20% while measured task time rose 19%. That does not prove the tool slows everyone down (small sample, early tools, a later update with caveats), so rejecting the claim overreaches. Lines of code reward volume rather than outcomes.

In the chapter's simulation, the 8-task study estimated a time ratio of 0.58 when the true value was 0.90. What does that show?

  1. The tool was more effective in that study
  2. With few tasks and widely varying times, estimates are noisy and can be far from the truth in either direction, so the interval matters more than the point estimate
  3. Bootstrap intervals are unreliable for any sample
  4. The random seed was broken
The interval for that study, 0.27 to 1.23, includes both a large saving and a slowdown: the data could not tell them apart. The point estimate looks decisive and is not. The bootstrap is working as intended; the study was too small.

A reviewing agent, asked to "find problems with this change", returns fourteen findings, mostly about style and hypothetical edge cases, on a sound change. What should you change?

  1. Use a weaker model as the reviewer
  2. Fix all fourteen to be safe
  3. Let the same session that wrote the code review it instead
  4. Tell the reviewer to report only gaps that affect correctness or the stated requirements, and treat the rest as optional
A reviewer asked to find gaps will usually report some, so the prompt defines the output. Fixing everything leads to over-engineering. Having the author review its own change removes the fresh-context benefit. A weaker model changes the quality of the findings, not their scope.

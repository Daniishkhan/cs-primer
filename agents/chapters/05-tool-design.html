Designing Tools for Agents

A tool is the only part of your system the model can touch, and the only description of it the model ever reads is the text you wrote. This chapter treats a tool as an interface for a reader with no memory, no manual and a limited budget of attention. It covers how to choose tools, name them and describe them. It then covers how to shape their arguments, size their results and make their errors teach.

Why this matters

When an agent fails, the first suspect is usually the model. Very often the cause is a tool. Two tools may have overlapping descriptions. An argument may be something the model cannot know. A result of 10,000 tokens may bury the one fact it needed. An error message may say "400" and nothing else. These are cheap to fix and expensive to ignore. Every wasted step costs tokens, time and a chance to go wrong (chapter 2 showed how the loop multiplies them). After this chapter you can review a toolset the way you would review an API for a new teammate. You can also measure two designs against each other and write tools that are safe to retry. Lab 2 then makes you do it with numbers.

A tool is an interface for a model

In chapter 2 a tool was three things the model can read (a name, a description and an input schema) plus a function that only your program can run. That arrangement is an agent-computer interface (ACI): the set of commands, formats and feedback through which a model operates a system. The phrase comes from the Software Engineering (SWE) agent project (Yang et al., 2024, "SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering"). It showed that giving a language model a purpose-built file viewer and editor, instead of a bare shell, changed how well it fixed real software issues. Case study 2 reads that work in detail. The lesson that matters here is the framing: the same model with a better interface does better, so interface design is engineering work, not decoration.

Human interface design has a well-worn habit: put yourself in the user's position. The user here is unusual. It has read a great deal about the world but knows nothing about your company, your database or this tool until it reads your definition. It cannot ask a colleague, cannot browse your documentation unless you give it a tool to do so, and starts every conversation with a blank memory. It does not get tired, but its attention thins as the context fills (chapter 10). Everything you want it to know about the tool has to be in the definition or in the results it gets back.

Analogy: the new colleague on day one

Imagine handing a capable new colleague a phone and a card listing the company's internal commands, with nobody to ask. A good card gives each command a clear name. It says in a sentence when to use it and when not to, shows an example, and makes the replies short and readable. A poor card says "get_data: gets data". Writing a tool definition is writing that card, and the colleague follows it literally.

Where it breaks down: a colleague will phone you after the third confusing reply. The model has no such instinct: it tries again, guesses, or confidently does the wrong thing. Also, a person reads your card once and remembers it; the model re-reads every definition on every request, so every sentence on the card has a running cost.

A running example: billing support

Throughout this chapter the agent works for a fictional subscription company, Northwind, answering billing questions and issuing small refunds. A customer writes: "Ana Silva here, ana@example.com. I was charged twice for March. Can you refund the duplicate?" The backend is an ordinary REST (Representational State Transfer) API with endpoints for customers, invoices, payments and refunds. The tempting first design wraps each endpoint as a tool:

  • get_customer(id), list_invoices(customer), get_invoice(id), list_payments(invoice), create_refund(payment, amount).

It is easy to build and it looks complete. It is also a design for a different user. That user is a programmer who already holds the customer id, reads the API documentation, and is happy to fetch four resources and join them. The model holds an email address, has no documentation, and every call will cost it context. The next sections take that toolset apart.

Choose the tools before you write them

The first design decision is not how to write a tool but which tools to have. Three principles help.

Start from tasks, not endpoints. List what the agent has to accomplish ("find the customer", "answer what they owe", "refund a payment"). Give each a tool that does the whole job a person would do in one step. Anthropic's engineering post "Writing effective tools for agents" (2025) puts the contrast with ordinary software this way. A function written for a deterministic caller can be small and precise. An agent is a different kind of caller, and tools should be built for what it needs in order to finish a task. Their example: instead of three tools that list users, list events and create events, offer one that schedules a meeting by finding a free time. In our example, "what does this customer owe?" needs a customer, their open invoices and their latest payment. That is three REST resources and one tool: billing_get_account_summary.

Make the first step reachable. A tool's arguments must be values the model can obtain. The thin get_customer(id) needs a customer id; the user supplied an email. The model will either invent an id, pass the email in the id field and get a 404, or burn a call on guessing which other tool accepts an email. A billing_find_customer(email_or_name) tool starts from what the model actually has.

Keep the set small. Every tool definition is sent with every request. So each one costs input tokens on every iteration of the loop, and each one is a candidate the model must rule out when choosing. Overlapping tools are worse than many tools: if search_customers and find_customer both exist, the model has to guess, and sometimes it will guess differently on identical inputs. Consolidating related actions (one tool with an action argument, or a handful of tools that each own a clear step) is the usual remedy. Providers also offer ways to keep rarely used definitions out of the context until needed. Anthropic documents a tool-search feature and a defer_loading option, so check the current docs. This matters once a server exposes dozens of tools. Chapter 7 returns to that, because MCP (the Model Context Protocol) makes it easy to attach far more tools than a model can use well.

Consolidation has a limit. A single tool that takes a 20-field "request" object is not simpler for the model; it only moves the confusion into the schema. A good test is the human one: could a new support colleague tell, from the tool name and one sentence, whether this is the command they need? If you cannot write that sentence without the word "and", the tool is probably two tools.

Step through

One refund request, two toolsets

  1. The request. The model has an email address and a complaint. Both lanes have to turn that into a refund against the right payment.
  2. Lane A, call 1: a dead end. get_customer wants an id. The model passes the email, as the only identifier it has, and gets a 404 with no hint about what a valid id looks like.
  3. Lane A, call 2: a flood. By trial it finds that list_invoices accepts an email. It returns every invoice with addresses, line items and audit trails: 10,523 tokens measured with this chapter's stand-in token counter. Those tokens are now in the context for every later call.
  4. Lane A, call 3: more joining. The payments live behind another endpoint, keyed by invoice, so the model joins the data itself.
  5. Lane A, call 4: the action. The refund tool takes a payment and an amount. Nothing in the interface says amounts are in cents, why a refund is made, or when to stop and ask a human.
  6. Lane B, call 1: start from what you have. billing_find_customer takes an email or a name and returns candidate ids.
  7. Lane B, call 2: one call for the question. The summary tool joins customer, open invoices and latest payment on the server, in a few dozen tokens, and includes the payment_id the refund needs.
  8. Lane B, call 3: a refund with guard rails. The schema has an enum for the reason and an amount in cents; the description states the cap and that the action cannot be undone.
  9. The comparison. Same model, same task. Lane B spends about 1% of Lane A's result tokens and cannot waste a step on a wrong identifier. The price is paid up front, in longer definitions, which the next section counts.

Names

A name is the first thing the model uses to choose, and it is repeated everywhere: in the definition, in every tool_use block, in logs. Good names are plain verbs on plain nouns (find_customer, issue_refund) that say what the tool does in the vocabulary of the task. Keep one convention across the set: if one tool is get_ then do not call its sibling fetch_ or retrieve_, because the model will treat the difference as meaningful.

When tools come from several systems, namespacing (a shared prefix such as billing_, crm_, asana_) keeps them apart and makes selection easier as the list grows. The Anthropic post notes that prefixing by service or suffixing by action can affect results in non-trivial ways, and the effect varies by model. It recommends testing the choice on your own evaluations rather than adopting a rule. Anthropic's tool-definition documentation gives the practical constraint for its API: names must match ^[a-zA-Z0-9_-]{1,128}$. The MCP specification (revision 2025-11-25) is slightly broader. It recommends 1 to 128 characters from letters, digits, underscore, hyphen and dot. It also says names should be unique within a server and case-sensitive. A name that is legal on one side may need rewriting on the other, one of the details a provider-neutral adapter handles (chapter 6).

Descriptions

The description is the most heavily weighted text in the definition. Anthropic's documentation says it plainly: detailed descriptions are by far the most important factor in tool performance. It suggests at least three or four sentences per tool, and more for complex ones. It lists what to cover. Say what the tool does and when it should be used (and when it should not). Say what each parameter means and what caveats apply, including what the tool does not return.

Read those four as a template and the redesigned billing_get_account_summary description makes sense:

  1. What it does: "Summarise one customer's billing: plan, open invoices with amounts and due dates, and the most recent payment with its payment_id."
  2. When to use it: "Use for any question about what a customer owes or paid."
  3. Side effects: "Read-only."
  4. Limits: "Does not list closed invoices older than 90 days." The model now knows what absence means; without this sentence a missing invoice looks like proof it never existed.

Two more habits pay off. First, say which tool to use instead. In billing_find_customer the sentence "It does not return invoices; use billing_get_account_summary for those" hands the model a map. Overlap between tools is the commonest cause of wrong choices, and the cheapest remedy is a pointer in each direction. Second, state the implicit knowledge: units ("amounts are in cents"), formats (year, month, day, as in "2026-01-31"), identifier shapes ("like cus_1042") and domain terms the model might read differently than your business does. The Anthropic post recommends writing as though for a new team member and being explicit about niche terminology and query formats. It also describes a case where a web-search tool made Claude append the year to its queries, which biased the results. A clearer description fixed it. Small wording changes can have large effects, so treat descriptions as something you test, not something you write once.

For tools with awkward inputs, Anthropic's API accepts an optional input_examples array of sample inputs validated against the schema. Its documentation estimates roughly 20 to 50 tokens per simple example and 100 to 200 for complex nested ones. Use them where words alone do not pin the format down.

Tell the truth about cost

Longer descriptions are not free. The script below is a tiny tool linter. It flags the weaknesses discussed so far: thin descriptions, generic argument names, undescribed arguments and near-duplicate descriptions. It also counts the definition tokens with the lab stand-in counter, which uses about four characters per token and is a rough guide only. It runs on both toolsets.

import json, re, itertools
from llm import count_tokens

GENERIC = {"id", "name", "query", "data", "input", "value", "user", "text", "x"}

def words(s):
    return set(re.findall(r"[a-z]{3,}", s.lower())) - {"the", "and", "for", "with", "this", "that", "from", "are", "you"}

def lint(tools):
    out = []
    for t in tools:
        d = t["description"]
        if len(d.split()) < 15:
            out.append(f"{t['name']}: description is {len(d.split())} words; say what, when, when not, and what comes back")
        if words(d) <= words(t["name"].replace("_", " ")):
            out.append(f"{t['name']}: description only restates the name")
        for p, spec in t["input_schema"].get("properties", {}).items():
            if p in GENERIC:
                out.append(f"{t['name']}.{p}: generic argument name; prefer customer_id, invoice_id ...")
            if "description" not in spec and "enum" not in spec:
                out.append(f"{t['name']}.{p}: no description")
    for a, b in itertools.combinations(tools, 2):
        wa, wb = words(a["description"]), words(b["description"])
        j = len(wa & wb) / max(1, len(wa | wb))
        if j >= 0.35:
            out.append(f"{a['name']} vs {b['name']}: descriptions overlap {j:.0%}; a model may confuse them")
    return out

def schema(props, req):
    return {"type": "object", "properties": props, "required": req}

The linter is crude, as any such tool is, but the numbers say something real. The redesigned set has fewer tools and no findings, yet its definitions are more than twice as large (488 tokens against 217). That extra 271 tokens is sent on every model call. Over a 20-call task it is 5,420 input tokens if nothing is cached; against that, a single oversized result in the thin design cost 10,523. Prompt caching (the repeated-prefix saving chapter 2 modelled) lowers the price of definitions that do not change, which is one reason to keep tool lists stable between calls. The point is not that longer is better, but that every sentence should earn its place by preventing a mistake you have seen or can foresee.

Arguments

Arguments are where most invalid calls originate. Four practices reduce them.

Name them unambiguously. user_id beats user, and customer_id beats id. The Anthropic post makes exactly this point: a bare user could be an id, an email or a display name, and the model will pick one. Descriptive names also protect you when two tools share an argument: invoice_id and payment_id cannot be swapped by accident the way two arguments called id can.

Make invalid calls hard to write. Manufacturing calls this poka-yoke (mistake-proofing): design the thing so the mistake cannot happen. Use enum for closed sets (reason above), integer types with bounds for amounts, and formats for dates. The Anthropic post "Building effective agents" (2024) tells a story about a coding agent. It made mistakes with relative file paths after it had moved out of the root directory. Changing the tool to require absolute paths removed the failures. Constraints in the schema work because the model reads them before writing; code-side validation catches the rest.

Prefer values the model has. Ask for the name or email in the user's message and look up the id inside the tool, not the other way round. Where an id is unavoidable, say where it comes from ("from billing_find_customer") and what it looks like ("cus_1042").

Keep the shape flat and the optional parts few. Deeply nested objects and many optional fields invite partial or inconsistent filling. Give optional arguments sensible defaults and say what the default is. The schema itself is plain JSON Schema; chapter 6 covers which parts of it providers enforce and which they merely suggest.

Common misconception

"A good model will work out a badly designed tool." Sometimes it does, which hides the cost. A strong model recovers from a bad interface by spending extra calls, extra tokens and extra chances to take a wrong turn. The weaker or cheaper model you may deploy next quarter will not recover at all. Test with the model you plan to ship, read transcripts for wasted calls, and fix the tool rather than the prompt wherever you can.

Results: send back what the next step needs

The result of a tool call goes straight into the context window. There it stays for the rest of the run and is re-sent on every later call, which is the quadratic growth chapter 2 measured. A result should therefore contain the information the model needs for its next decision and little else. Returning the raw API response is the commonest mistake, because it is the easiest thing to build.

The Anthropic post gives several concrete moves. Return semantic, human-meaningful identifiers rather than opaque internal ones where you can, and keep the identifiers later calls will need. Offer a response-format argument, for example an enum of concise and detailed, so the agent chooses how much it wants. The post's own example is a Slack tool. Its detailed result was 206 tokens and its concise result 72, about a third. The concise form omitted identifiers needed only for follow-up calls. For anything that can be large, provide pagination, filtering, range selection and truncation with sensible defaults. The post reports that Claude Code restricts tool responses to 25,000 tokens by default.

The script below builds the invoice data from the running example and shows what each choice costs.

import json, random
from llm import count_tokens

def make_invoices(n=60, seed=7):
    rng = random.Random(seed)
    rows = []
    for i in range(n):
        rows.append({
            "id": f"inv_{3000 + i}", "customer_id": "cus_1042", "status": rng.choice(["paid", "paid", "open", "overdue"]),
            "amount_cents": rng.randrange(900, 20000), "currency": "GBP", "created_at": f"2026-{1 + i % 9:02d}-{1 + i % 27:02d}",
            "billing_address": {"line1": "12 Mill Lane", "city": "Leeds", "postcode": "LS1 4AB", "country": "GB"},
            "line_items": [{"sku": f"plan-{k}", "qty": 1, "unit_cents": 900 * k} for k in range(1, 4)],
            "audit_trail": [{"at": "2026-01-01T09:00:00Z", "actor": "system", "event": "created"}] * 4,
        })
    return rows

def shape(rows, fmt="concise", limit=10, offset=0, status=None):
    if status:
        rows = [r for r in rows if r["status"] == status]
    page = rows[offset:offset + limit]
    keep = ("id", "status", "amount_cents") if fmt == "concise" else ("id", "status", "amount_cents", "currency", "created_at", "line_items")
    body = {"invoices": [{k: r[k] for k in keep} for r in page], "total_matching": len(rows)}
    if offset + limit < len(rows):
        hint = "" if status else ", or pass status='overdue' to narrow"
        body["note"] = f"Showing {offset + 1}-{offset + len(page)} of {len(rows)}. Pass offset={offset + limit} for more{hint}."
    return json.dumps(body)

That last point deserves a moment. A short result is only better if it is still sufficient. A page of ten arbitrary rows out of sixty cannot answer "what is the largest overdue invoice?". A tool that returns ten rows without saying there are more invites a confident, wrong answer. The tool should say how many matched, what was shown and how to get the rest, as the note field in the script does. Try the trade-off yourself.

Two further points about results. First, text beats clever structure for the model's own reading, but structure still matters to your code. MCP (chapter 7) lets a tool return both a human-readable content list and a machine-readable structuredContent object. Keeping those separate lets you show the model a short summary while your application uses the full data. Second, truncate with guidance. When you cut a result, say so, and say how to narrow the next request. For example: "output truncated at 200 lines; pass a path or a pattern to search a smaller area". A silent cut looks to the model like a complete answer.

Errors that teach

When a call fails the model has one source of information: the error text. The loop in chapter 2 returns failures as tool_result blocks with is_error set, so the model can react instead of the run crashing. What the text says decides whether the next call is a fix or a repeat. The advice from the Anthropic post is to state what went wrong and what to change, with an example of a valid input. Avoid opaque codes and raw tracebacks. The MCP specification draws the same line. Input validation errors are best reported inside the tool result (isError: true) so a model can correct itself. Protocol-level errors, such as an unknown tool name, are less likely to be recoverable.

The experiment below makes the difference visible. A tool expects an ISO date (the international standard format, such as 2026-03-03); the stand-in model starts with "3 March 2026". In the first run the error says only 400 Bad Request. In the second it says what is wrong, what to use and that nothing happened. The stand-in is written to fix its call only when the message gives it something to fix with. So read the result as an illustration of the mechanism and not as evidence about any real model's skill.

import json, re
from datetime import date, datetime
from llm import ScriptedModel, tool_use, tool_calls, tool_result, text_of

def list_invoices(since, style):
    try:
        d = date.fromisoformat(since)
    except ValueError:
        if style == "opaque":
            raise ValueError("400 Bad Request")
        raise ValueError(f"since={since!r} is not an ISO date. Use YYYY-MM-DD, for example 2026-01-31. "
                         "Nothing was fetched; retry with the corrected value.")
    return json.dumps({"invoices": [{"id": "inv_3001", "due": "2026-03-20"}], "since": d.isoformat()})

def standin(messages, tools, system):
    """Stand-in for a model that fixes its call only if the error tells it how."""
    last = messages[-1]["content"]
    if isinstance(last, list):                       # we are looking at a tool_result
        r = last[0]
        hint = re.search(r"\d{4}-\d{2}-\d{2}", r["content"])
        if r["is_error"] and hint:
            old = messages[-2]["content"][0]["input"]["since"]          # the call that failed
            return [tool_use("list_invoices", {"since": datetime.strptime(old, "%d %B %Y").date().isoformat()})]
        if r["is_error"]:
            return [tool_use("list_invoices", {"since": "3 March 2026"})]   # repeats the same mistake
        return "Found 1 invoice, due 2026-03-20."
    return [tool_use("list_invoices", {"since": "3 March 2026"})]

def run(style, max_iter=5):
    model, msgs = ScriptedModel(standin), [{"role": "user", "content": "Invoices since 3 March?"}]
    for i in range(1, max_iter + 1):
        reply = model.complete(msgs, tools=[])
        msgs.append(reply.as_message())
        if not tool_calls(reply):
            return f"{style:10} answered after {i} model calls: {text_of(reply)}"
        c = tool_calls(reply)[0]
        try:
            res = tool_result(c["id"], list_invoices(c["input"]["since"], style))
        except ValueError as e:
            res = tool_result(c["id"], str(e), is_error=True)
        print(f"  [{style}] call {i}: since={c['input']['since']!r} -> {'ERROR ' if res['is_error'] else ''}{res['content'][:70]}")
        msgs.append({"role": "user", "content": [res]})
    return f"{style:10} gave up after {max_iter} model calls"

for style in ("opaque", "actionable"):
    print(run(style))

The opaque version burns its whole budget repeating one mistake. In production that is real money and, for write tools, sometimes real damage. Four guidelines follow.

  • Say what was wrong, what is valid and whether anything changed. "Nothing was fetched" tells the model that retrying is safe.
  • Make retryable and permanent failures look different. "Rate limited, retry after 5 seconds" and "that customer does not exist" demand different next steps. The distinction matters on the wire too, where clients retry some failures and not others.
  • Keep internals out. Stack traces waste tokens and leak file paths, table names and sometimes secrets into a context that may be logged or shown to users.
  • Handle empty results deliberately. "No invoices found for cus_1042 since 2026-03-03" is better than [], because it tells the model the call worked and the answer is "none", not "the tool is broken".

Tools that change things

Read-only tools can be retried freely. A tool that moves money, sends an email or deletes a file needs more care, and the interface is where much of it lives. The distinctions the model needs are in the description ("this moves real money and cannot be undone"). But the guarantees your system needs must be enforced in code, because a description is a request and not a barrier. Four patterns carry most of the weight.

Idempotency key
A caller-chosen token sent with a write, so that repeating the same request has the same effect as sending it once. It is how a retry after a timeout avoids a second refund. The reliability and API chapters cover the mechanism (API design); for agents it matters doubly, because the loop itself may repeat a call.
Dry run
A mode in which a tool reports what it would do and changes nothing. It lets the model, or a human approving the step, check the effect before committing.
Hard limits in code
Caps, allow-lists and ownership checks enforced by the function, not by the prompt. The refund cap below is checked in Python, whatever the model was told.
Human approval
A pause before irreversible actions, handled by the harness. Chapter 15 builds approval gates that survive restarts.

This version of the refund tool uses the first three, and returns messages in the style recommended above:

import json
PAYMENTS = {"pay_88123": {"total_cents": 4900, "refunded_cents": 0}}
SEEN = {}                                   # idempotency_key -> earlier result
CAP = 10000

def billing_issue_refund(payment_id, amount_cents, reason, idempotency_key, dry_run=False):
    if idempotency_key in SEEN:
        return SEEN[idempotency_key] + " (repeat of an earlier call: no money moved again)"
    p = PAYMENTS.get(payment_id)
    if p is None:
        return f"Error: no payment {payment_id!r}. Payment ids look like pay_88123; get one from billing_get_account_summary."
    left = p["total_cents"] - p["refunded_cents"]
    if not 1 <= amount_cents <= min(left, CAP):
        return f"Error: amount_cents must be between 1 and {min(left, CAP)} for {payment_id}; got {amount_cents}. Amounts are in cents."
    if dry_run:
        return f"Dry run: would refund {amount_cents} cents of {payment_id} ({reason}). Nothing was changed."
    p["refunded_cents"] += amount_cents
    SEEN[idempotency_key] = f"Refunded {amount_cents} cents of {payment_id}; {left - amount_cents} cents still refundable."
    return SEEN[idempotency_key]

for args in [dict(payment_id="pay_88123", amount_cents=2500, reason="duplicate", idempotency_key="r1", dry_run=True),
             dict(payment_id="pay_88123", amount_cents=2500, reason="duplicate", idempotency_key="r1"),
             dict(payment_id="pay_88123", amount_cents=2500, reason="duplicate", idempotency_key="r1"),
             dict(payment_id="pay_88123", amount_cents=250000, reason="goodwill", idempotency_key="r2"),
             dict(payment_id="88123", amount_cents=100, reason="goodwill", idempotency_key="r3")]:
    print(billing_issue_refund(**args))
Dry run: would refund 2500 cents of pay_88123 (duplicate). Nothing was changed.
Refunded 2500 cents of pay_88123; 2400 cents still refundable.
Refunded 2500 cents of pay_88123; 2400 cents still refundable. (repeat of an earlier call: no money moved again)
Error: amount_cents must be between 1 and 2400 for pay_88123; got 250000. Amounts are in cents.
Error: no payment '88123'. Payment ids look like pay_88123; get one from billing_get_account_summary.

Note what the fourth call does. The model asked for 250,000 cents; the tool refused, stated the legal range, and reminded it of the unit. The cap is enforced even if a prompt injection later talks the model into asking. That layering (tell the model, but enforce in code) is the thread of chapter 19 and chapter 20. The same holds for ordinary services: authorisation belongs in the server, never in the client's good behaviour (authorization).

MCP lets a server annotate tools with hints such as whether a tool is read-only or destructive. The specification is careful to say that clients must treat annotations as untrusted unless they come from a trusted server. Use them to drive confirmation prompts and interface hints, never as the only safety control.

Systems connection

Tool design is API design with an unusual consumer. The same instincts apply: stable names, one obvious way to do each thing, pagination, explicit error contracts and idempotent writes (API design, how programs talk). What changes is that your client reads documentation as prose, cannot be sent a changelog, and pays for every byte it receives. Tool arguments are also untrusted input like any other: validate them, and see injection and untrusted input for what happens when you do not.

Measuring a tool design

You cannot tell whether a toolset is good by reading it. Anthropic's post lays out a process worth copying, and Lab 2 follows it with a scripted model. In outline:

  1. Prototype quickly and try the tools by hand with a real client, to catch obvious problems before you measure.
  2. Write realistic tasks, grounded in real data and in the multi-step work users do. The post advises that strong tasks may need many tool calls; a single-lookup task tests little.
  3. Give each task a verifiable outcome, by exact match or a careful judge, without being so strict that correct answers in different words fail. (Evaluating agents treats end-state checks properly.)
  4. Run each task in its own simple loop and record accuracy, runtime, number of tool calls, tokens and tool errors.
  5. Read the transcripts. Repeated calls suggest the interface wastes steps; many invalid-argument errors suggest unclear names or schemas; unused tools may be redundant.
  6. Hold out some tasks so improvements are not only overfitting to the tasks you tuned against.

The post also suggests letting a model help. Feed transcripts back to an agent and ask it to propose edits to the tool descriptions. This is cheap and often productive, provided you verify the edits against the held-out tasks. Statistics matter here as everywhere: with a twenty-task set, a difference of two tasks is noise (statistics for evals).

State of play, October 2026

The principles above are stable, but the surrounding features move. As of 14 October 2026, Anthropic's tool-definition docs describe optional input_examples, a strict flag for schema-guaranteed inputs, and deferred tool loading with a tool-search tool for large catalogues. The MCP revision 2025-11-25 supports optional tool title, outputSchema and structuredContent. A later revision (2026-07-28, see chapter 7) asks servers to return tools/list in a deterministic order so clients and prompt caches can rely on it. Check each provider's current documentation before depending on any of these by name.

Key takeaways

  • A tool is an interface for a reader with no memory and no manual. The model sees names, descriptions, schemas and results; everything else about your system is invisible.
  • Design tools around tasks, not endpoints. Make the first step reachable from what the model has, and keep overlapping tools out of the set.
  • Descriptions carry the most weight: what it does, when to use it and when not, what each argument means, what it does not return, and which tool to use instead.
  • Constrain arguments in the schema (enums, bounds, formats, unambiguous names) so that wrong calls are hard to write.
  • Shape results: only what the next step needs, a concise/detailed switch, pagination and filters, truncation with guidance, and an honest count of what was left out.
  • Errors are instructions: say what was wrong, what is valid and whether anything changed.
  • Enforce safety in code: caps, idempotency keys, dry runs and approvals. A description is a request, not a barrier.
  • Measure designs with realistic tasks, read the transcripts and keep a held-out set.

Check your understanding

A support agent has get_customer(id), but users only ever provide an email address. In traces the model often calls get_customer with the email, gets a 404, and then tries several other tools. What is the best first fix?

  1. Add a sentence to the system prompt telling the model never to pass an email to get_customer.
  2. Add a tool (or change this one) so the first step accepts what the model has, such as billing_find_customer(email_or_name), and say where ids come from.
  3. Switch to a larger model so it can work out the id format by itself.
  4. Return the full customer database from get_customer so the model can search it.
The cause is an interface that asks for a value the model cannot know. Fixing the interface removes the failure for any model. A prompt rule (first option) patches one symptom and spends tokens on every request. A bigger model (third) hides the cost rather than removing it. Dumping the database (fourth) creates a result-size problem far worse than the one it fixes.

A list_invoices tool returns every field for all 60 of a customer's invoices (about 10,500 tokens by this chapter's counter). The task is "what is the largest overdue invoice?". Which redesign is best?

  1. Return only the first 10 invoices with the same fields, so results are small.
  2. Keep the dump but ask the model in the description to ignore irrelevant fields.
  3. Return only the amount field, since the question is about the largest amount.
  4. Accept a status filter and a concise format with id, status and amount, and report how many rows matched and how to see more.
A good result is small and sufficient. The first option is small but can miss the answer, and says nothing about the rest. Asking the model to ignore fields (second) does not remove their tokens from the context. Amount alone (third) loses the invoice id and status the answer needs. The fourth gives the right rows, the needed fields and a count, so the agent can tell whether it has seen everything.

A model gets Error: invalid input from a tool and calls it again with the same arguments three times. Which change to the tool most directly addresses this?

  1. Return a message that names the bad argument, states the valid format with an example, and says whether anything was changed.
  2. Lower the model's temperature to zero so it stops repeating itself.
  3. Raise the iteration limit so it has more attempts.
  4. Hide the error and return an empty result so the model moves on.
The model repeats because the error gives it nothing to change. An actionable message gives it a different next call. Temperature zero would make repetition more likely, not less. More iterations only spend more on the same failure, and hiding the error (fourth) turns a visible fault into a silent wrong answer.

You add 35 more tools from several MCP servers to an agent that worked well with 6. Accuracy drops and costs rise, even on tasks that only need the original tools. Which explanation fits best?

  1. The model has a hard limit of about ten tools and ignores the rest.
  2. Larger tool lists make the model produce longer answers.
  3. All definitions are sent on every request and compete for attention, and similar descriptions make choosing between tools harder.
  4. Tools from MCP servers are slower to execute than local ones.
Definitions cost input tokens on every call and each extra tool is another candidate to rule out; overlapping descriptions make wrong choices more likely. There is no universal ten-tool limit (first), answer length is not driven by tool count (second), and execution speed (fourth) would not cause worse choices. Remedies include fewer, consolidated tools, clearer descriptions, and deferred loading with tool search.

An agent's refund tool says in its description "never refund more than 10,000 cents". Which statement is most accurate?

  1. The description is enough, because current models follow instructions reliably.
  2. The description helps the model behave, but the cap must also be enforced in the tool's code, because the description can be ignored or overridden by injected text.
  3. The cap should live only in the system prompt, where it has higher priority.
  4. The cap is unnecessary if the tool has an idempotency key.
Descriptions and prompts steer behaviour; code enforces limits. An injected instruction in a document the agent reads can talk a model past a stated rule, but not past an if statement. An idempotency key (fourth) prevents duplicate execution of the same request; it does nothing about a single request for too large an amount.

You rewrite your tool descriptions and a 20-task evaluation goes from 11 correct to 13 correct. What is the most defensible conclusion?

  1. The rewrite is a clear improvement and should ship.
  2. The rewrite made things worse because 20 tasks is too few to show anything.
  3. The result is encouraging but within the range of noise; run the held-out tasks, repeat runs, and look at which tasks changed and why before deciding.
  4. Descriptions do not matter, because the result barely moved.
Two tasks out of twenty is a small difference with a wide error bar, particularly when runs are stochastic and you tuned on these same tasks. It is neither proof of improvement (first) nor of harm (second). Reading the transcripts of the tasks that changed tells you whether the rewrite fixed the failure you aimed at; a held-out set protects against fooling yourself.

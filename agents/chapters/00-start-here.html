Start Here

An agent is a language model running in a loop, choosing tools and reading what they return. That sentence is easy to say and hard to make reliable. This chapter separates workflows from agents, shows why agents fail in predictable ways, and lays out how the rest of the course builds the loop from the wire up.

Why this matters

Most of the AI systems that companies actually ship are not one prompt and one answer. They call a search index, read a ticket, update a record, ask a person to approve a step. The engineering question is how much of that sequence the programmer fixes in code and how much the model decides at run time. Choose too little freedom and the system cannot handle real inputs. Choose too much and it becomes slow, expensive and unpredictable. After this chapter you will have a vocabulary for that choice, a small working example, and a map of the course.

Two ways to put a model in a system

A language model (LLM) is a program that, given text, produces more text; course A3 explains how one is trained and served. On its own it can only write. A tool is a function the surrounding program offers to the model: look up an order, run a query, send an email. The model never runs the function itself. It writes a structured request ("call lookup_order with A-1001"), your program runs the function, and your program feeds the result back as more text.

Once a model can request tools, there are two broad ways to arrange the pieces. Anthropic's December 2024 essay "Building effective agents" draws the line this way. Workflows are "systems where LLMs and tools are orchestrated through predefined code paths." Agents are "systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks." In plain terms:

Workflow
The programmer writes the sequence: step 1 fetch, step 2 summarise, step 3 send. The model fills in the steps (it writes the summary) but never chooses the next step.
Agent
A loop. The model looks at the situation, picks an action or a tool, sees the result, and decides again, until it decides it is finished or a limit stops it. The path is not known in advance.
Agent loop
The cycle of "ask the model, run what it requested, append the result, ask again". Chapter 2 builds it in full.

A first taste: the same job both ways

Here is a customer asking where their order is. The two programs below use the stand-in models that every lab in this path uses: ScriptedModel from lab-support/llm.py replays replies written in advance, so the output is real and identical on every run. Messages use content blocks, small typed pieces (text, tool_use, tool_result) that together make up one turn; chapter 1 explains the format.

from llm import ScriptedModel, tool_use, text_of, tool_calls, tool_result

ORDERS = {"A-1001": {"status": "shipped", "total": 42.50}}

def lookup_order(order_id):
    return ORDERS.get(order_id, "error: no such order")

TOOLS = {"lookup_order": lookup_order}

# --- Workflow: the programmer fixed the path in advance --------------------
def workflow(question, model):
    order_id = "A-1001"                          # step 1: code decides what to fetch
    facts = lookup_order(order_id)               # step 2: code calls the tool
    prompt = f"Order data: {facts}\nQuestion: {question}"
    return text_of(model.complete([{"role": "user", "content": prompt}]))

# --- Agent: the model decides the path --------------------------------------
def agent(question, model, max_steps=5):
    messages = [{"role": "user", "content": question}]
    for step in range(max_steps):
        reply = model.complete(messages, tools=[{"name": "lookup_order"}])
        messages.append(reply.as_message())
        calls = tool_calls(reply)
        if not calls:                            # no tool requested: the model is done
            return text_of(reply), step + 1
        results = [tool_result(c["id"], str(TOOLS[c["name"]](**c["input"]))) for c in calls]
        messages.append({"role": "user", "content": results})
    return "stopped: step budget used", max_steps

m1 = ScriptedModel(["Your order A-1001 has shipped."])
print("workflow:", workflow("Where is my order?", m1))

m2 = ScriptedModel([[tool_use("lookup_order", {"order_id": "A-1001"}, id="t1")],
                    "Your order A-1001 has shipped; the total was 42.50."])
print("agent:   ", agent("Where is order A-1001?", m2))
workflow: Your order A-1001 has shipped.
agent:    ('Your order A-1001 has shipped; the total was 42.50.', 2)

Read the two functions side by side. In workflow the order id is hard-coded by the programmer; the model is called exactly once, whatever the question. In agent the model chose to call lookup_order, and the id came from the model's own request. The loop ran twice: once to get the tool request, once to get the final answer. The ten lines of agent are the heart of this entire course. Everything else (MCP, memory, multi-agent teams, sandboxes) is about making that loop do useful things, cheaply, without breaking anything.

Common misconception

"An agent is a smarter version of a chatbot, so more autonomy is an upgrade." Autonomy is a cost you pay for flexibility. A workflow that handles 95 per cent of tickets with one fixed path is usually cheaper, faster, easier to test and easier to explain to an auditor than an agent that handles 99 per cent with a path nobody can predict. The question is never "can we make this an agent?" but "does this task need the model to choose the steps?"

Why agents fail

The same four forces explain most failures you will see, and each gets a chapter later.

Errors compound

Suppose each step of a task, picking the right tool, giving it the right arguments, reading the result correctly, succeeds with probability p, independently. A task of n steps then succeeds with probability pn. Independence is an assumption (real errors correlate), but the shape of the curve is the point.

# If each step succeeds independently with probability p, a task of n steps succeeds with p**n.
print("steps  p=0.99  p=0.95  p=0.90")
for n in (1, 5, 10, 20, 50):
    print(f"{n:>5}  " + "  ".join(f"{p**n:6.3f}" for p in (0.99, 0.95, 0.90)))
steps  p=0.99  p=0.95  p=0.90
    1   0.990   0.950   0.900
    5   0.951   0.774   0.590
   10   0.904   0.599   0.349
   20   0.818   0.358   0.122
   50   0.605   0.077   0.005

A 95 per cent reliable step sounds excellent. Chain twenty of them and the task works barely a third of the time. This is why good prompts, well-designed tools and honest evaluation matter more than clever architecture, and why loops need checks that catch an error before the next step builds on it.

Cost and latency grow faster than the step count

Every turn of the loop re-sends the whole conversation to the model. Ten steps do not cost ten times one step; they cost closer to the sum of ten growing prompts. Chapter 2 puts numbers on this and gives you a widget to explore it.

Context fills up

The conversation is the model's only working memory, and it has a fixed size. Long tool outputs, repeated failures and stale facts crowd out the instructions that matter. Part 3 of the course treats context as a budget to be spent deliberately.

Untrusted text becomes instructions

An agent reads web pages, emails and documents, and a model cannot reliably tell "data to summarise" from "orders to follow". A hidden sentence in a web page can steer an agent that also holds your private files and can send messages. Part 6 builds the threat model; the short version is that this is injection again, with a language model as the interpreter.

Systems connection

An agent loop is a client making repeated calls to remote services that can time out, fail halfway and be retried. Everything known about timeouts, retries and partial failure applies: a tool that charges a card must be idempotent, or a retry will charge twice. Long-running agents also meet the problem of exactly-once effects and the saga pattern. Part 4 returns to both.

Choosing the simplest design that works

Think of a dial from "one model call" to "fully autonomous agent". Anthropic's essay recommends finding "the simplest solution possible, and only increasing complexity when needed", and it names the patterns in between: prompt chaining, routing, parallelisation, orchestrator-workers and evaluator-optimiser loops. Part 4 implements each as ordinary code. A workable rule of thumb:

  1. Can one well-prompted call, with retrieved context, do it? Stop there.
  2. Are the steps known in advance and always the same? Write a workflow.
  3. Do inputs vary so much that the next step depends on what the last step found, and the number of steps cannot be predicted? Consider an agent, with budgets and checks.
  4. Does a single agent run out of context or time on the whole task? Only then consider several agents, and read chapter 14 on what that costs.

State of play, October 2026

The vocabulary above (workflow, agent, tool call, loop) has been stable since 2024. What moves quickly is the layer around it: model names and prices, framework APIs, and the protocol specifications for connecting tools (MCP) and agents (A2A). This course keeps those facts in dated boxes like this one and builds the durable parts from first principles, so a new SDK or spec revision changes details rather than understanding. Key takeaways

  • A workflow fixes the sequence in code; an agent lets the model choose the next step inside a loop with stop conditions.
  • The agent loop is about ten lines: ask the model, run the tools it requested, append the results, repeat.
  • Agents fail predictably: errors compound (pn), cost grows faster than steps, context fills up, and untrusted text can act as instructions.
  • Use the simplest design that works: one call, then a workflow, then an agent, then several agents.
  • This course builds the loop first and adds tools, context, structure, real jobs and defences in that order.

Check your understanding

A pipeline always fetches a customer's record, asks a model to draft a reply, and sends it. Which description fits?

  1. An agent, because it uses a language model
  2. A workflow, because the code fixes the sequence and the model only fills in one step
  3. An agent, because it calls a tool
  4. Neither, because agents must use more than one model
What defines an agent is that the model chooses the next action inside a loop. Using a model, or calling a tool, does not make a system an agent; here the programmer chose every step in advance, which is a workflow.

An agent task needs 20 sequential steps and each step independently succeeds 95 per cent of the time. Which number is closest to the chance the whole task succeeds?

  1. 95 per cent
  2. 75 per cent
  3. 60 per cent
  4. 36 per cent
0.9520 is about 0.358. The tempting answer 95 per cent forgets that every step must work. 60 per cent is roughly the value at 10 steps, not 20.

Your support bot handles four fixed kinds of ticket, each needing the same three steps. What is the most sensible design?

  1. A router that classifies the ticket, then a fixed workflow per kind
  2. A fully autonomous agent with every tool, for flexibility
  3. Several agents that debate the answer
  4. A single agent with no step limit, since it will stop itself
Known, repeatable steps favour a workflow: it is cheaper, faster, testable and predictable. Autonomy pays when the path cannot be known in advance, which is not the case here. A loop with no step limit is also unsafe, because stopping then depends entirely on the model.

In the agent function above, what ends the loop in normal operation?

  1. The programmer's code decides the task is complete
  2. The tool returns the string "done"
  3. The model replies without requesting any tool
  4. The loop always runs exactly max_steps times
The model signals it is finished by answering without a tool request; max_steps is only the safety limit for when it never does. Tool results do not stop the loop on their own, and the loop usually ends well before the limit.

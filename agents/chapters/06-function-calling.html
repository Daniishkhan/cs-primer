Function Calling Across Providers

Every major model API can ask your program to run a function, and every one spells the request differently. This chapter separates the idea from the dialects: the JSON Schema contract that describes a function, the shapes of calls and results on the wire, parallel calls, forcing or forbidding tools, and a small provider-neutral adapter that keeps your agent loop from caring which API is underneath.

Why this matters

The loop from chapter 2 and the tool design from chapter 5 are provider-independent ideas, but the bytes you send are not. A message that is valid for one API is a 400 error on another, an argument that arrives as an object in one arrives as a string of JSON in the next, and a flag such as "force this tool" has three spellings. Teams that hard-wire one dialect into their loop pay for it when they want to compare models, add a fallback provider, or move to a local model. After this chapter you can read any provider's tool-calling documentation quickly, because you know what it must contain, and you can write the thin layer that hides the differences.

One idea, several dialects

The idea is the one you built in chapter 2. You describe functions to the model; the model replies with a structured request to call one, naming it and supplying arguments; your program runs it and sends back a result; the model continues. The word the industry settled on is function calling (OpenAI's term, from 2023) or tool use (Anthropic's), and the two mean the same mechanism for the functions you define. Google's Gemini API and most open-model servers use one of these two styles, or a close variant.

What differs is the envelope. Where does the call live in the response? Is the argument an object, or a string you must parse? How is a result tied to its call? What does the schema key look like? What happens when the model wants several calls at once? These are plumbing questions, and they are answered differently enough that code written for one API does not run on another. Since the models improve and the prices change on a timescale of months, a design that keeps the dialect at the edge is cheap insurance.

Analogy: travel plug adapters

The electricity is the same everywhere, but the sockets are not, so travellers carry adapters. You do not rewire the laptop for each country; you put a small piece between it and the wall. A provider-neutral adapter is that piece: your loop plugs into one shape and the adapter fits it to each provider's socket.

Where it breaks down: electricity is interchangeable, but provider features are not. A strict-schema guarantee, a thinking block that must be passed back, or a server-side search tool exists on one side and not the other. An adapter can hide spelling; it cannot make a missing feature appear, and a design that pretends otherwise fails in odd places.

The contract: JSON Schema

Every dialect describes a function's arguments with JSON Schema, the standard vocabulary for saying what shape a JSON document must have. Only a small subset matters for tools:

  • type: object, string, integer, number, boolean, array.
  • properties and required for objects; items for arrays.
  • enum for a closed set of values, and description on every property (chapter 5 explains why that text is the most valuable part).
  • additionalProperties: false to forbid fields you did not declare, and numeric bounds such as minimum.

The schema plays two roles, and keeping them apart avoids a lot of confusion. It is advice to the model: the model reads it before writing the call. It is also a specification you can enforce: your program can check the model's arguments against it before running anything. Nothing makes those two agree automatically. A model can and does produce arguments that violate the schema it was shown, for instance the string "2" where an integer was required, a value outside an enum, or a missing field. Argument validation is therefore your job, in the same way that validating a web form on the server is your job however good the form's JavaScript is (untrusted input).

The checker below implements the subset in about thirty lines and turns the problems into messages a model can act on. It also shows strictify, which rewrites a schema into the closed form that OpenAI's strict mode requires.

import json

TYPES = {"string": str, "integer": int, "number": (int, float), "boolean": bool, "object": dict, "array": list}

def validate(value, schema, path="$"):
    """Check a value against the small subset of JSON Schema that tool contracts use."""
    errs, t = [], schema.get("type")
    if t and (not isinstance(value, TYPES[t]) or (t in ("integer", "number") and isinstance(value, bool))):
        return [f"{path}: expected {t}, got {type(value).__name__} {value!r}"]
    if "enum" in schema and value not in schema["enum"]:
        errs.append(f"{path}: {value!r} is not one of {schema['enum']}")
    if "minimum" in schema and isinstance(value, (int, float)) and value < schema["minimum"]:
        errs.append(f"{path}: {value} is below the minimum {schema['minimum']}")
    if t == "object":
        for k in schema.get("required", []):
            if k not in value:
                errs.append(f"{path}: missing required field {k!r}")
        for k, v in value.items():
            if k in schema.get("properties", {}):
                errs += validate(v, schema["properties"][k], f"{path}.{k}")
            elif schema.get("additionalProperties") is False:
                errs.append(f"{path}: unexpected field {k!r}")
    if t == "array":
        for i, v in enumerate(value):
            errs += validate(v, schema.get("items", {}), f"{path}[{i}]")
    return errs

def strictify(schema):
    """Rewrite a schema into the form OpenAI strict mode asks for: closed objects, every field required,
    optional fields expressed as a union with null."""
    s = dict(schema)
    if s.get("type") == "object":
        props, req = s.get("properties", {}), set(s.get("required", []))
        s["properties"] = {}
        for k, v in props.items():
            v = strictify(v)
            if k not in req:
                v = {**v, "type": [v["type"], "null"]} if "enum" not in v else {**v, "type": [v["type"], "null"], "enum": v["enum"] + [None]}
            s["properties"][k] = v
        s["required"], s["additionalProperties"] = list(props), False
    if s.get("type") == "array":
        s["items"] = strictify(s["items"])
    return s

In real code you would use a library such as jsonschema in Python or Ajv in JavaScript, but a hand-rolled version makes the point: validation is cheap, local and deterministic. Send the failures back as an is_error tool result, in the style of chapter 5, and most invalid calls repair themselves on the next turn.

Strict mode: making the schema binding

Several providers can go further and constrain the model's output so that the arguments are guaranteed to match the schema. The technique is constrained decoding (also called grammar-constrained sampling): the schema is compiled into a grammar, and at each step the model may only emit tokens that keep the output valid. Anthropic documents it as strict: true on a tool definition and describes the guarantee as inputs that strictly follow input_schema with a valid tool name; the example in its documentation is a booking tool where, without strict mode, passengers might arrive as the string "2", and with it the value is always the integer 2. OpenAI offers the same idea as "strict": true on a function tool and attaches rules to it. As of the Responses API documentation I read on 14 October 2026:

  • every object in parameters must set additionalProperties: false;
  • every key in properties must also appear in required;
  • an optional field is written as a union with null, such as "type": ["string", "null"].

That is what strictify above does. The same page says that on the Responses API, omitting strict makes the service try to normalise your schema and fall back to non-strict if that fails, whereas Chat Completions tools remain non-strict by default. Both vendors restrict which JSON Schema keywords strict mode supports, so check the current lists before relying on a bound or a pattern.

Common misconception

"With strict mode on, the tool arguments are correct." They are well-formed: the right types, the right fields, a value from the enum. Whether the value is the right one is a different matter. A strict call can still ask to refund the wrong payment, pass yesterday's date as "tomorrow", or choose reason: "goodwill" when the customer said "duplicate". Schema-valid is not the same as sensible, so authorisation, range checks and business rules still belong in your code (chapter 5), and strict mode also does not stop the model from picking the wrong tool unless you restrict choices as described below.

The wire formats side by side

Here is one conversation turn in four dialects: the model asks for two weather lookups, and the program answers both. Read the figure by rows: how the request is carried, how the answers are carried, where the schema goes.

Each box in that figure has a story. Some of the details are worth spelling out.

Anthropic Messages
The shape this course uses throughout. The assistant message holds text and tool_use blocks. All results go back in a single user message as tool_result blocks, placed before any extra text, each carrying the call's tool_use_id and an optional is_error.
OpenAI Chat Completions
The assistant message has a tool_calls array; each entry has an id and a function with a name and arguments, which is a string containing JSON. Each result is its own message with role: "tool" and a tool_call_id. This is also the shape that most local servers (vLLM, Ollama, LM Studio) and many third-party hosts imitate, so it is the most widely compatible.
OpenAI Responses
The conversation is a list of typed items. A call is an item of type function_call with an id, a call_id, a name and string arguments; your answer is a function_call_output item with the same call_id and an output that is typically a string. Tool definitions are flat (no nested function key). OpenAI's documentation notes that some newer models require this API for tool calling.
Gemini
The Gemini function-calling guide I fetched on 14 October 2026 documents the newer Interactions API: tools are declared with type: "function", name, description and parameters; the model's request is a function_call step with an id, name and arguments object; your reply is a function_result step with a call_id. The long-standing generateContent style, which the adapter below targets, carries functionCall and functionResponse parts inside model and user turns, and matches a response to a call by function name. I wrote that shape from memory of the documentation and did not re-check it, so verify it before use.

Converting between them

The neutral format in this course is the content-block shape of lab-support/llm.py: messages with text, tool_use and tool_result blocks, tools as {name, description, input_schema}. It is the Anthropic shape with the vendor-specific extras left out, which makes the Anthropic adapter the identity function. The other three are translations. This module does them; the script after it translates the weather conversation from the figure and prints the beginning of each entry.

import json

def to_anthropic(messages, tools):                       # our neutral format IS this shape
    return {"messages": messages, "tools": tools}

def to_openai_chat(messages, tools):
    out = []
    for m in messages:
        if isinstance(m["content"], str):
            out.append(m)
            continue
        calls = [b for b in m["content"] if b["type"] == "tool_use"]
        results = [b for b in m["content"] if b["type"] == "tool_result"]
        words = "".join(b["text"] for b in m["content"] if b["type"] == "text")
        for r in results:                                # each result becomes its own "tool" message
            out.append({"role": "tool", "tool_call_id": r["tool_use_id"], "content": r["content"]})
        if calls:
            out.append({"role": "assistant", "content": words or None, "tool_calls": [
                {"id": c["id"], "type": "function",
                 "function": {"name": c["name"], "arguments": json.dumps(c["input"])}} for c in calls]})
        elif words:
            out.append({"role": m["role"], "content": words})
    return {"messages": out, "tools": [{"type": "function", "function": {
        "name": t["name"], "description": t["description"], "parameters": t["input_schema"]}} for t in tools]}

def to_openai_responses(messages, tools):
    items = []
    for m in messages:
        if isinstance(m["content"], str):
            items.append(m)
            continue
        for b in m["content"]:
            if b["type"] == "text":
                items.append({"role": m["role"], "content": b["text"]})
            elif b["type"] == "tool_use":
                items.append({"type": "function_call", "call_id": b["id"], "name": b["name"],
                              "arguments": json.dumps(b["input"])})
            elif b["type"] == "tool_result":
                items.append({"type": "function_call_output", "call_id": b["tool_use_id"], "output": b["content"]})
    return {"input": items, "tools": [{"type": "function", "name": t["name"], "description": t["description"],
                                       "parameters": t["input_schema"]} for t in tools]}

def to_gemini_generate_content(messages, tools):         # results are matched by NAME, so remember id -> name
    names, contents = {}, []
    for m in messages:
        role = "model" if m["role"] == "assistant" else "user"
        if isinstance(m["content"], str):
            contents.append({"role": role, "parts": [{"text": m["content"]}]})
            continue
        parts = []
        for b in m["content"]:
            if b["type"] == "text":
                parts.append({"text": b["text"]})
            elif b["type"] == "tool_use":
                names[b["id"]] = b["name"]
                parts.append({"functionCall": {"name": b["name"], "args": b["input"]}})
            elif b["type"] == "tool_result":
                parts.append({"functionResponse": {"name": names[b["tool_use_id"]], "response": {"result": b["content"]}}})
        contents.append({"role": role, "parts": parts})
    return {"contents": contents, "tools": [{"functionDeclarations": [
        {"name": t["name"], "description": t["description"], "parameters": t["input_schema"]} for t in tools]}]}

Look at what each translation has to do. For OpenAI Chat, a single neutral user message that holds two results becomes two tool messages, and the assistant's calls move out of the content list into tool_calls with the input serialised to a string. For Responses, one message turns into several flat items. For Gemini, the result must be tagged with the function name, which the neutral format does not carry on the result, so the adapter keeps a dictionary from call id to name as it walks the history. Conversion is a pure function of the history, so you can test it without any network: feed it a conversation and compare with a fixture.

The reverse direction matters just as much, because the model's reply has to come back into the neutral shape. The one subtlety is OpenAI's string arguments: the model writes JSON text, and nothing guarantees it is complete.

import json
from llm import Response

STOP = {"tool_calls": "tool_use", "stop": "end_turn", "length": "max_tokens"}

def from_openai_chat(choice):
    """One OpenAI Chat Completions choice -> the neutral Response used everywhere else."""
    msg, blocks, problems = choice["message"], [], []
    if msg.get("content"):
        blocks.append({"type": "text", "text": msg["content"]})
    for tc in msg.get("tool_calls") or []:
        raw = tc["function"]["arguments"]
        try:
            args = json.loads(raw or "{}")                 # a JSON *string* on the wire, an object for us
        except json.JSONDecodeError as e:
            problems.append(f"{tc['function']['name']}: arguments are not valid JSON ({e.msg}): {raw!r}")
            args = {}
        blocks.append({"type": "tool_use", "id": tc["id"], "name": tc["function"]["name"], "input": args})
    return Response(blocks, STOP.get(choice["finish_reason"], "end_turn")), problems

The second call shows a real failure mode. The reply stopped because it hit the output limit (finish_reason: "length") in the middle of the arguments, so the JSON is cut off. The adapter does not guess: it records the problem and the stop reason becomes max_tokens. The loop must not run a tool with half its arguments. It should either retry with a larger limit or report the problem to the model, which is the same advice as for any other malformed call. Strict mode and constrained decoding make malformed JSON rarer, but a truncated reply can still occur.

Parallel tool calls

A model may answer one turn with several tool calls, as in the weather example. This is useful: when calls are independent, running them together cuts latency to that of the slowest call. It also raises three questions that every dialect answers in roughly the same way.

Who decides the order? You do. Anthropic's documentation says the API does not prescribe an execution order: run the calls concurrently, sequentially, or any mix that suits the tools. Independent read-only operations are usually safe to run in parallel; calls with side effects, shared state or ordering requirements may need to run one after another. The model cannot know which of your tools are safe to overlap, so the harness decides.

What goes back? One result for every call, and for Anthropic all in the same user message, matched by id and not by position. If you chose not to run a call, say because an earlier write in the same batch failed, you still return a result for it, with is_error set and a short explanation. A missing result is a malformed history that the API will reject.

How do failures combine? Independently. One failing call must not throw away the others' results. The script runs three calls both ways, with one deliberate failure.

import json, time
from concurrent.futures import ThreadPoolExecutor
from llm import tool_use, tool_result

def get_weather(city):
    time.sleep({"Leeds": 0.2, "Paris": 0.3}.get(city, 0.1))
    if city == "Atlantis":
        raise KeyError("no such city: 'Atlantis'. Try a real city name.")
    return f"{city}: 14C"

CALLS = [tool_use("get_weather", {"city": c}, id=f"t{i}") for i, c in enumerate(["Leeds", "Paris", "Atlantis"])]

def run_one(call):
    try:
        return tool_result(call["id"], get_weather(**call["input"]))
    except Exception as e:                                      # one failure must not lose the others
        return tool_result(call["id"], f"{type(e).__name__}: {e}", is_error=True)

t0 = time.perf_counter()
sequential = [run_one(c) for c in CALLS]
t_seq = time.perf_counter() - t0

t0 = time.perf_counter()
with ThreadPoolExecutor() as pool:
    concurrent = list(pool.map(run_one, CALLS))                 # map keeps the order of CALLS
t_con = time.perf_counter() - t0

assert [r["tool_use_id"] for r in concurrent] == [c["id"] for c in CALLS]
print(f"sequential {t_seq:.1f}s, concurrent {t_con:.1f}s")
user_message = {"role": "user", "content": concurrent}         # ONE message, one result per call id
for r in user_message["content"]:
    print(json.dumps(r))

Every provider also lets you switch parallel calls off when ordering matters or when you want simpler logs: Anthropic's disable_parallel_tool_use option on tool_choice and OpenAI's parallel_tool_calls: false, which the documentation says ensures zero or one call per turn. Gemini's approach, as documented, is to declare several functions and let the response contain several call steps. Because calls arrive in one turn, an idempotency key on writes matters even more than usual (chapter 5): a retried batch must not repeat its effects.

Forcing and forbidding tools

By default the model decides whether to call a tool at all. Each API lets you override that, which is how you build a classifier or extractor out of a tool call, or finish a run with a summary and no more actions. The options map onto four intents.

OpenAI also documents allowed_tools, which restricts the model to a subset of the tools you passed while keeping the full list (and with it the cached prompt prefix) unchanged, and Gemini's guide describes the same restriction through an allowed-tools list and a further mode, validated. Mappings differ in small ways that your adapter should encode in one place, as in this function, which turns a neutral intent into each provider's spelling and then shows what happens when forcing is misused in a loop.

import json
from llm import Model, Response, text, tool_use, tool_calls, tool_result

def tool_choice_for(provider, mode, name=None, parallel=True):
    """Neutral intent -> each provider's spelling. mode: auto | required | tool | none."""
    if provider == "anthropic":
        tc = {"auto": {"type": "auto"}, "required": {"type": "any"}, "none": {"type": "none"},
              "tool": {"type": "tool", "name": name}}[mode]
        if not parallel and mode != "none":
            tc["disable_parallel_tool_use"] = True
        return {"tool_choice": tc}
    if provider == "openai_responses":
        tc = {"auto": "auto", "required": "required", "none": "none",
              "tool": {"type": "function", "name": name}}[mode]
        return {"tool_choice": tc, "parallel_tool_calls": parallel}
    if provider == "gemini":
        cfg = {"auto": {"mode": "AUTO"}, "required": {"mode": "ANY"}, "none": {"mode": "NONE"},
               "tool": {"mode": "ANY", "allowedFunctionNames": [name]}}[mode]
        return {"toolConfig": {"functionCallingConfig": cfg}}

for p in ("anthropic", "openai_responses", "gemini"):
    print(f"{p:17}", json.dumps(tool_choice_for(p, "tool", "extract_invoice", parallel=False)))

class ForcedModel(Model):
    """Stand-in that obeys tool_choice the way a real API does: forced means a tool call EVERY time."""
    def complete(self, messages, *, tool_choice="auto", **kw):
        if tool_choice == "required":
            return Response([tool_use("extract_invoice", {"text": "..."})], "tool_use")
        return Response([text("Extracted: total 49.00 GBP.")], "end_turn")

def run(policy, max_iter=4):
    model, msgs = ForcedModel(), [{"role": "user", "content": "Read this invoice."}]
    for i in range(1, max_iter + 1):
        reply = model.complete(msgs, tool_choice=policy(i))
        msgs.append(reply.as_message())
        if reply.stop_reason != "tool_use":
            return f"finished on call {i}"
        msgs.append({"role": "user", "content": [tool_result(tool_calls(reply)[0]["id"], "{'total': 4900}")]})
    return f"still calling the tool after {max_iter} calls: budget exhausted"

The second half is the classic mistake. If you leave a tool forced for every turn of a loop, the model has no way to finish, because "answer in words" is no longer allowed. The loop runs until the iteration budget stops it. The remedy is to force only the first turn (or only the turn that needs structure) and return to auto afterwards. The stand-in model there obeys tool_choice the way a real API does; it is a toy, but the control flow is the real thing.

A few caveats from the documentation I read on 14 October 2026:

  • Anthropic: when a tool is forced with any or tool, the API pre-fills the assistant turn, so the model emits no explanatory text before the call, and thinking is skipped. With manual extended thinking enabled, any and tool are errors. Its documentation also lists some current models that return a 400 for forced tool use altogether, recommending auto with strict tool use instead. Changing tool_choice between requests invalidates cached message blocks (tool definitions and system prompt stay cached).
  • OpenAI: "required" means one or more calls; a specific function means exactly that one; "none" behaves as if no functions were supplied.

Forcing is not a safety control. It narrows what the model may emit; it does not make the arguments right, and it should not be the only thing between a prompt injection and a dangerous tool (chapter 19).

A provider-neutral adapter

Put the pieces together and the design is a small version of what is called ports and adapters (hexagonal architecture, the adapter pattern). The agent loop talks to one interface, complete(messages, tools, tool_choice), and every provider hides behind an implementation of it.

Some rules make an adapter layer worth having rather than a source of bugs.

  1. Normalise to the richest shape you need and no richer. The content-block format is enough for text and tool calls. Add fields (such as a cache hint or an image block) only when more than one provider has a real equivalent.
  2. Test conversions without the network. Keep a few recorded conversations as fixtures and assert that each adapter produces the expected request. The lab-support module offers a recorder and replayer for exactly this.
  3. Validate on both sides. Check arguments against the schema before running a tool, whatever the provider promises, and check the shape of your outgoing request (every call has exactly one result) before sending it.
  4. Make unsupported features loud. If a caller asks for strict schemas and an adapter cannot provide them, raise an error or log a clear warning. Silent downgrade is how a "portable" system produces provider-specific bugs.
  5. Pass back what the provider needs. Providers that return reasoning content, such as thinking blocks or reasoning items, document that it should be returned unmodified in later turns of a tool conversation. A neutral format that drops it breaks multi-turn tool use on those models; check each provider's guidance and carry such items through opaquely.
  6. Map errors and limits. Rate limits, overloads and context-length errors have different codes and retry hints per provider. The adapter should present them in one vocabulary, because the retry logic in your loop depends on it (failure, timeouts and retries).

Frameworks and gateways offer this layer prepackaged, and chapter 21 discusses when to use one. The advantage of writing the thin version yourself once is that you know exactly what the packaged one is hiding. The shape of HTTP requests, headers and status codes underneath is plain web plumbing (HTTP, APIs and serialisation).

Systems connection

Adapters are the oldest answer to "many vendors, one interface", and the same advice holds: keep a narrow port, keep translation in one place and test it with fixtures (hexagonal architecture). Schemas that describe messages are the same idea as an API contract, and a model's arguments are untrusted input to your service just as any client's are (injection and untrusted input). The tool results you return can in turn carry attacker-controlled text, which is the subject of chapter 19.

Key takeaways

  • All providers implement the same loop: describe functions, receive a call, return a result tied to the call. The spellings differ, mostly in where the call lives, whether arguments are an object or a JSON string, and how results are matched.
  • JSON Schema is both advice to the model and a contract you can enforce. Validate arguments yourself and return failures as error results.
  • Strict mode (constrained decoding) guarantees well-formed arguments, not correct ones. Providers attach rules to it, such as closed objects and all fields required.
  • Parallel calls cut latency to the slowest call but you control execution order; return one result per call, and never lose the others when one fails.
  • Forcing a tool is for single-turn structure; leave it on for a whole loop and the run cannot end.
  • A thin neutral adapter keeps dialects at the edge. Test conversions with fixtures, make unsupported features loud, and pass provider-specific reasoning items back unchanged.

Check your understanding

A tool is declared with strict: true and an enum reason of duplicate, service_issue, goodwill. The customer says the charge was a duplicate, but the model calls the tool with reason: "goodwill". What does strict mode tell you here?

  1. This cannot happen: strict mode guarantees correct values.
  2. It is a bug in the provider, which should have rejected the call.
  3. The call is schema-valid, so strict mode did its job; choosing the right value is a separate problem for descriptions, evaluation and business checks.
  4. Strict mode failed because enums are not supported.
Constrained decoding makes the output conform to the schema's shape: right types, declared fields, a value from the enum. It does not know what the customer meant. Fixing wrong-but-valid choices is the job of clearer descriptions, evaluation, and checks in your tool code.

The model returns three tool calls in one turn. You run them sequentially, and the second fails because its input was invalid, so you skip the third. What should the next request contain?

  1. One result for each of the three calls: success for the first, an error result for the second, and an error result for the third saying it was not executed.
  2. Only the result for the first call, since the batch was abandoned.
  3. Results for the first two calls; the third was never run, so there is nothing to report.
  4. Nothing: drop the assistant message and ask the model again.
Every call needs exactly one result, matched by id, or the history is malformed and the API rejects it. Reporting the skipped call as an error with a short explanation keeps the history valid and tells the model what happened. Dropping the turn (fourth) discards work and can loop.

Your OpenAI Chat adapter receives a tool call whose arguments is the text {"city": "Le with finish_reason: "length". Which behaviour is correct?

  1. Run the tool with an empty argument object and see what happens.
  2. Fix the JSON by closing the quote and brace, then run it.
  3. Ignore the call and continue the loop as if the model had answered in words.
  4. Treat it as a truncated reply: do not run the tool, and retry with a larger output limit or report the problem to the model.
The reply was cut off by the output limit, so the arguments are incomplete, and guessing the rest could run the tool on a wrong city (or worse, a wrong payment). Running with empty arguments (first) or repairing by guesswork (second) both act on invented data. Ignoring the call (third) silently loses it.

An extraction agent forces a tool on every call with tool_choice set to "required". It never produces a final answer and stops only when it hits the iteration limit. What is the best fix?

  1. Increase the iteration limit.
  2. Force the tool only on the turn that needs structured output, then return to auto so the model may answer in words.
  3. Remove the tool and ask for JSON in the prompt.
  4. Lower the temperature so the model stops calling tools.
With a tool forced on every turn, "reply in plain text" is never allowed, so the loop cannot end. Forcing belongs on single turns. A bigger limit only runs the same loop longer; temperature does not override the forced choice; removing the tool (third) loses the schema guarantees that made forcing useful.

You must support both Anthropic and a local server that speaks the OpenAI Chat style. Where should the translation between the two live?

  1. Inside each tool function, which checks which provider is running.
  2. In the system prompt, which tells the model to answer in whichever format the provider expects.
  3. In the agent loop, with an if-statement on the provider in every step.
  4. In one adapter layer behind a single interface, so the loop, validation and budgets are written once against a neutral shape.
Translation is deterministic plumbing and belongs in one tested place at the edge. Scattering provider checks through tools (first) or the loop (third) multiplies the places that must change when an API does, and a prompt (second) cannot change the wire format of a request your own code sends.

Which of these does a provider-neutral adapter handle least well, and so should be treated as a deliberate, visible exception?

  1. A provider-specific feature with no equivalent elsewhere, such as a server-side search tool or a schema-guarantee mode.
  2. Renaming input_schema to parameters.
  3. Serialising a tool input object to a JSON string.
  4. Splitting one message of results into several tool messages.
The last three are mechanical translations a pure function can do and test. A feature that exists on one side only cannot be translated; the adapter can refuse loudly, degrade explicitly, or expose it as a documented provider-specific option, but silent pretence leads to surprises.

Sandboxes & Permissions

An agent that can run commands will sooner or later run one you did not intend, because it misread a task or because an attacker steered it. This chapter separates the two controls that limit the damage: permissions, which decide what the agent may attempt, and sandboxes, which decide what an attempt can touch. It covers containers, virtual machines, network allow-lists, least privilege and confirmation prompts, with working code for the parts that are easy to get wrong.

Why this matters

Chapter 19 ended with the uncomfortable conclusion that a model cannot be made reliably immune to injection, and that the dependable defences are the ones that hold when the model is fooled. This chapter builds those defences. It is also the answer to the plainer problem that agents make ordinary mistakes: a coding agent that runs rm -rf in the wrong directory, a shell tool that pushes to the wrong remote. After this chapter you can choose an isolation level for a given agent, write a command and path policy that does not have the usual holes, set up a network allow-list that is not defeated by a suffix match, keep credentials out of reach, and design confirmation prompts people will actually read.

Two questions, two controls

Security for an agent comes down to two questions that sound alike and are not.

May the agent do this?

A permission is a rule in the harness: allow, ask the user, or deny a given tool call. It is cheap, flexible and fine-grained, and it runs before the action. Its weakness is that it is software deciding about arbitrary strings, and it only protects against what it recognises.

What can it reach if it does it anyway?

A sandbox is an enforced boundary around the running code: the operating system, a hypervisor or a network proxy refuses what is outside the boundary, whatever the code or the model intends. It acts during the action. Its weakness is cost and friction: someone has to decide what to put inside.

You want both, in this order, as layers. The permission layer keeps the agent from attempting most harmful things and keeps humans informed. The sandbox is what remains true if a permission rule has a hole, the model has been injected, or a person approved something without reading it. The principle is defence in depth from security design principles, applied to a component that is unusually good at finding unexpected paths.

Least privilege, applied to agents

Least privilege means giving a component only the access its task requires. For a human, "only what the job needs" is a role. For an agent it should be narrower still, because the agent's intentions are uncertain and its inputs are untrusted. Work through five dimensions for every agent you deploy.

DimensionQuestionTypical narrow answer
FilesWhich paths can it read and write?Read and write the project directory; read-only system libraries; nothing under ~/.ssh, cloud credential folders or other projects
CommandsWhich programs can it start?Test runner, formatter, git read operations; not package installs from arbitrary indexes, not curl | sh
NetworkWhich hosts can it contact?The package mirror and the code host; nothing else by default
CredentialsWhose authority does it act with?A task-scoped, short-lived token with read-only database access, not the developer's login
ResourcesHow much CPU, memory, time and money?A wall-clock limit, a process limit, a token and spend cap

Start from nothing allowed and add. The reverse (start from a developer's full session and subtract) always leaves something. The cost of a missing permission is a failed tool call the model can read and report, which is cheap; the cost of an extra permission is paid once, in the worst case. The widely discussed case of a coding agent that deleted a production database during a declared code freeze, covered in case study 6, is a least-privilege failure at heart: the agent had a credential that could do something its task did not need.

Permissions: policy in the harness

A permission system has three possible answers for each tool call: allow (run it), ask (show it to the user), deny (refuse and say why). The design questions are how rules are written, which wins when several match, and what the default is.

Claude Code's documentation is a representative modern example. Rules are evaluated in the order deny, then ask, then allow, and the first match decides; a broad deny such as Bash(aws *) cannot be overridden by a narrower allow. Reads inside the working directory are allowed by default, shell commands ask except for a built-in list of read-only ones, and the user can save "don't ask again" rules. Deny-first is a good rule to copy: an exception should never be able to reopen something an administrator closed.

Commands are harder to match than they look

The obvious design is a list of allowed command prefixes: "anything starting with git status or ls is fine". It fails in several ways, because a shell command string is a small program, not a name. A semicolon, &&, a pipe, a command substitution $(...) or a newline turns one allowed command into two. A prefix like ls also matches lsof. An allowed program may accept flags that write files or load code. The script below puts a naive prefix check next to a stricter one (refuse shell metacharacters outright, parse with shlex, check the program, then check its arguments).

# policy20.py: a permission check for shell commands. Naive prefix matching versus parse-then-allow.
import shlex

ALLOW_PREFIXES = ["git status", "git diff", "ls", "cat", "python3 -m pytest"]      # the naive rule set

def naive(cmd):
    return any(cmd.startswith(p) for p in ALLOW_PREFIXES)

META = set(";&|<>()`$\n\\")                      # anything that lets one string become several commands
SAFE = {                                          # argv[0] -> test on the remaining args
    "ls":  lambda a: True,
    "cat": lambda a: all(not x.startswith("/") and ".." not in x for x in a),
    "git": lambda a: a[:1] in (["status"], ["diff"]) and not any(x.startswith("-c") or x.startswith("--output") for x in a),
    "python3": lambda a: a[:2] == ["-m", "pytest"],
}
def strict(cmd):
    if any(c in META for c in cmd): return False          # refuse what we cannot reason about
    argv = shlex.split(cmd)
    return bool(argv) and argv[0] in SAFE and SAFE[argv[0]](argv[1:])

The naive check approves all ten, including a command that downloads and runs a script, one that deletes the home directory, one that sends the .env file to an outside server, and lsof, which merely begins with ls. The strict version refuses them, and also refuses git diff --output=..., which writes a file. But the last row is the instructive one: python3 -m pytest -p evil_plugin passes the strict check because the test runner was allowed, and -p tells it to load a plugin, which is arbitrary Python. Narrowing arguments is whack-a-mole. Claude Code's own documentation says this plainly. A deny rule such as Bash(curl *) stops curl https://example.com but not /usr/bin/curl https://example.com or sh -c 'curl https://example.com'; the page states that such a rule "isn't a security boundary around the program" and points to the sandbox for enforcement. It also warns that rules meant to restrict curl to GitHub URLs miss options placed before the URL, other protocols, redirects and variables. It also splits compound commands on &&, ||, ;, |, & and newlines and requires each part to match, which is the right behaviour and still not a boundary.

The takeaway is not "write better rules". It is that a permission rule is a convenience and a speed bump, and the sandbox is the boundary. Rules reduce the number of surprises; they must not be the only thing between a command and your files.

Paths: the same trap

"Is this path inside the workspace?" looks like a one-line check. The script tries three implementations against five attacks on a real temporary directory tree, including a symlink inside the workspace that points out of it.

# fs20.py: "is this path inside the workspace?" Three implementations, five attacks, on a real temp tree.
import os, tempfile
root = os.path.realpath(tempfile.mkdtemp(prefix="fs20_"))
ws, sib = f"{root}/proj", f"{root}/proj-secrets"
for d in (ws, sib, f"{root}/home"): os.makedirs(d)
open(f"{sib}/key.txt", "w").write("secret"); open(f"{root}/home/id_rsa", "w").write("secret")
os.symlink(f"{root}/home", f"{ws}/shortcut")          # a symlink inside the workspace pointing out

def v1(p):   return p.startswith(ws)                                       # string prefix
def v2(p):   return os.path.abspath(p).startswith(ws)                       # normalises ..
def v3(p):                                                                  # resolves symlinks, compares whole path components
    return os.path.commonpath([os.path.realpath(p), ws]) == ws

ATTACKS = [("inside, fine",       f"{ws}/src/app.py"),
           ("dot-dot",            f"{ws}/../home/id_rsa"),
           ("sibling prefix",     f"{sib}/key.txt"),
           ("symlink out",        f"{ws}/shortcut/id_rsa"),
           ("far away",           "/etc/passwd")]
print(f"{'path':16}{'string prefix':>15}{'abspath':>10}{'realpath':>10}")
for name, p in ATTACKS:
    print(f"{name:16}{str(v1(p)):>15}{str(v2(p)):>10}{str(v3(p)):>10}")

A string-prefix check accepts ../ traversal and a sibling directory whose name starts with the workspace's name (proj-secrets begins with proj). Normalising with abspath fixes the first and not the others. Only resolving symlinks with realpath and comparing whole path components catches all four. Even that is a check at one moment: between the check and the open, another process (or the agent itself, in an earlier command) can swap a path for a symlink, the classic time-of-check to time-of-use race from systems chapter 11. The robust fix is again below the application: a sandbox that makes the outside invisible, so there is nothing to race to.

Confirmation prompts people will read

A confirmation prompt is a permission with a human as the policy engine. Humans are slow, attentive for a short time, and prone to clicking through. So the design goal is to ask rarely and meaningfully:

  • Show the real action. The full command, the recipient, the amount, the destination URL. "Allow shell command?" is not a prompt; it is a speed bump.
  • Ask only for what matters: irreversible operations (delete, send, pay, publish), actions that leave the organisation, and anything that widens permissions. Let the sandbox handle the rest silently.
  • Make "no" cheap and informative. A refusal returns a message to the model saying what was refused, so it can try something safer instead of retrying the same call.
  • Bind approval to exactly what was shown. An approval for one command should not authorise "similar" ones, and a "don't ask again" rule should say precisely what it covers.
  • Persist the gate for long jobs. An approval that arrives hours later must survive restarts, which is the durable-execution design of chapter 15.

The strongest argument for the sandbox is arithmetic about prompts. Anthropic's description of the sandbox in Claude Code (20 October 2025) reports that it reduces permission prompts by 84% in internal usage. Fewer prompts is a security gain, not only convenience: each remaining prompt gets real attention.

Sandboxes: containment below the agent

A sandbox changes what is possible. Choosing one is choosing how much of the host the untrusted code shares with it, which trades strength against cost, start-up time and compatibility. The options form a spectrum.

Process limits are not a sandbox

The cheapest layer is operating-system resource control on a child process (A0 chapter 22 introduces it from scratch): a CPU limit, a file-size limit, a limit on open files, a wall-clock timeout, and a clean environment so the child inherits none of your secrets. These stop runaway loops and accidents. They do not stop reading files. The script runs six untrusted snippets under these limits.

# proc20.py: run untrusted code with resource limits and a scrubbed environment, then see what that does NOT stop.
import os, resource, subprocess, sys, tempfile, textwrap

def limits():
    resource.setrlimit(resource.RLIMIT_CPU, (2, 2))                  # 2 CPU seconds
    resource.setrlimit(resource.RLIMIT_FSIZE, (1_000_000, 1_000_000))  # files up to 1 MB
    resource.setrlimit(resource.RLIMIT_NOFILE, (32, 32))
    os.setsid()                                                      # own process group: kill it all on timeout

def run(code, timeout=5):
    work = tempfile.mkdtemp(prefix="proc20_")
    env = {"PATH": "/usr/bin:/bin", "HOME": work}                    # nothing inherited
    try:
        r = subprocess.run([sys.executable, "-I", "-c", textwrap.dedent(code)], cwd=work, env=env,
                           capture_output=True, text=True, timeout=timeout, preexec_fn=limits)
        return f"exit {r.returncode}: " + ((r.stdout + r.stderr).strip().splitlines() or [""])[-1][:90]
    except subprocess.TimeoutExpired:
        return "killed by wall-clock timeout"

os.environ["ANTHROPIC_API_KEY"] = "sk-demo-not-real"

The scrubbed environment hid the API key. The busy loop was stopped by the CPU limit (exit code −24 means the process received signal 24, SIGXCPU), the sleeper by the timeout, and the 5 MB write by the file-size limit. The last two lines are the point: the process still read /etc/hosts and listed the real home directory. Resource limits cap how much the code consumes, never what it can see. Treat this layer as a seat belt for accidents.

OS-level sandboxes

Modern operating systems let a process give up capabilities permanently, or be started with a policy it cannot change. On macOS this is Seatbelt; on Linux there are namespaces (bubblewrap is a small tool that builds a restricted view of the file system and network from them), Landlock for file-system rules and seccomp for filtering system calls. Anthropic's write-up on Claude Code's sandbox (20 October 2025) says it is built on these operating-system features, bubblewrap on Linux and Seatbelt on macOS, and enforces two boundaries together: file-system isolation (read and write access to the working directory, changes outside it blocked) and network isolation (connections only to approved servers, via a proxy that runs outside the sandbox). Both are needed together: without network isolation a compromised agent could leak files, and without file-system isolation it could tamper with the sandbox's own configuration to remove the network limit. The advantage over a container is that nothing has to be installed or started: it wraps the tools you already have on your own machine.

Containers, and why "Docker" is not a security boundary by itself

A container is an ordinary process with a restricted view: namespaces give it its own process table, network and file-system view; control groups (cgroups) cap its resources; seccomp filters limit the system calls it may make. All containers on a host share one kernel (systems chapter 19). A bug in the kernel, or a misconfiguration such as a mounted Docker socket, a privileged flag or a host directory mounted writable, gives the code in the container the host. For code you wrote and trust, a container is excellent packaging. For code a model wrote after reading a stranger's web page, it is a good first layer with sensible flags, not a guarantee. The illustrative command below shows the restrictive settings to reach for (not run here: the Docker daemon was not available in this environment).

$ docker run --rm --network none --read-only --cap-drop ALL \
    --security-opt no-new-privileges --pids-limit 128 --memory 512m \
    -v "$PWD":/work -w /work python:3.12-slim python3 agent_task.py

That command removes the network, makes the image's own file system read-only, drops all Linux capabilities, forbids gaining privileges, and caps processes and memory; only /work is writable. Then add exactly what the task needs, for example a proxy-only network for the package mirror.

User-space kernels and virtual machines

When the code is hostile or the tenants are strangers, put a stronger boundary under the container. gVisor is an application kernel written in Go that runs in user space: its component called the Sentry handles the program's system calls itself instead of passing them to the host kernel, and its runsc runtime plugs into Docker and Kubernetes. It trades compatibility and some speed for a much smaller host attack surface. A microVM runs the code in its own virtual machine with its own guest kernel, so an escape must cross the hypervisor. Firecracker, the microVM monitor behind AWS Lambda and Fargate, is described in Agache et al. (2020, "Firecracker: Lightweight Virtualization for Serverless Applications"): with a minimal guest kernel configuration the paper reports memory overhead below 5 MB per microVM, boot to application code in under 125 ms, and creation of up to 150 microVMs per second per host. Those figures are what made it practical to give every function, and now every agent task, its own machine. Several cloud services that sell sandboxes for running agent-written code use microVMs or similar isolation; check a vendor's own description of what it uses. The related online code judge studio faces the same problem for contest submissions.

Common misconception

"The agent runs in Docker, so it is sandboxed." A container with the default settings, a mounted home directory or Docker socket, full network access and your cloud credentials in its environment is a convenient package, not a boundary. Check four things before you call it a sandbox: what is mounted, what network it can reach, what credentials it can read, and which kernel it shares. The second misconception is the mirror image: "we ask the user to approve everything, so we do not need a sandbox." Approval fatigue turns that into no control at all.

The network: the leg you can actually cut

Of the three legs of the lethal trifecta, the external-communication leg is usually the one an engineer can remove without ruining the product. A sandbox with no default route to the internet, plus a proxy that decides which hosts may be contacted, turns "can the agent send data out?" into a question the proxy answers, not the model. The proxy sits outside the sandbox, so code inside cannot reconfigure it; Anthropic's design also lets the user confirm new domains as they come up.

Allow-list matching has its own traps, mirrored from the path checks above. The script compares a suffix match (does the host end with an allowed name?) with a proxy that matches whole labels and then checks the resolved address.

# egress20.py: the decision an egress proxy makes. Hostname rules, then the address it resolves to.
import ipaddress
from urllib.parse import urlparse

ALLOW = {"pypi.org", "files.pythonhosted.org", "github.com"}

def v1(url):  return any(urlparse(url).hostname.endswith(h) for h in ALLOW)            # suffix match
def v2(url, resolved_ip="93.184.216.34"):
    host = urlparse(url).hostname
    if host not in ALLOW and not any(host.endswith("." + h) for h in ALLOW): return "deny: host"
    ip = ipaddress.ip_address(resolved_ip)
    if ip.is_private or ip.is_loopback or ip.is_link_local: return f"deny: resolves to {ip}"
    return "allow"

The suffix match accepts evilpypi.org because it ends in pypi.org. The whole-label proxy refuses it, and refuses pypi.org.evil.test and the github.com@evil.test trick (the real host is the part after the @). The final row shows why the address check exists: an allowed name whose DNS answer points at 169.254.169.254, the cloud metadata endpoint, would hand the agent the machine's cloud credentials. That is the SSRF pattern from security chapter 11 and the way the Capital One breach unfolded (security case 3); the network lessons of zero trust and cloud and container security apply directly. Two more cautions. DNS lookups themselves can carry data (a name like AKIA123.evil.test is a message), so the sandbox should not be allowed to resolve arbitrary names, and the proxy should do the resolving. And as chapter 19 showed, an allow-list that includes a service the attacker can also read (a public paste or file-sharing site) is a hole, so list hosts you control and reach shared services only with approval.

Credentials: what is not in the sandbox cannot be stolen

The cleanest defence for secrets is absence. The environment of a sandboxed process should contain no cloud keys, no long-lived tokens and no SSH agent socket, and the file system should not expose credential directories (the scrubbed environment in proc20.py is the minimal version). When the agent needs to authenticate, give it the narrowest thing that works:

  • Task-scoped, short-lived tokens with only the scopes and resources the task needs (OAuth scopes), expiring in minutes rather than months.
  • Injection at the boundary: the proxy or tool server holds the secret and attaches it to approved requests, so the agent can use an API without being able to read the key or send it elsewhere.
  • Read-only roles by default for databases and storage; a separate, audited path for writes (authorisation).
  • Separate environments: an agent working on code gets a development database or a copy, never production. If it must touch production, it does so through a narrow tool with its own limits (chapter 5) and a human gate.

Systems connection

Every layer here is a mechanism from the earlier courses. Resource limits and process groups are processes and signals; namespaces, cgroups and hypervisors are containers and virtual machines; the proxy is a forward proxy, and the cloud network controls are in cloud networking; least privilege and complete mediation are security design principles. For hostile tenants, multi-tenancy sets out the isolation options.

State of play, October 2026

Operating-system sandboxing is now built into at least some leading terminal coding agents (Anthropic described Claude Code's in October 2025), and cloud providers sell microVM-based "sandboxes for agents". Claude Code's documentation, as of this writing, describes a bypassPermissions mode that skips all prompts and recommends it only for isolated environments such as containers or VMs where the agent cannot cause damage; this is the right way round, with isolation first and autonomy second. Product names, defaults and flags change quickly; read the vendor's current documentation before relying on any behaviour described here, and test that the boundary holds (try reading ~/.ssh and connecting to an unlisted host from inside it).

A reference setup

Putting the layers together for a coding agent that works on a repository you own:

  1. Work on a copy. A branch or git worktree, so undo is one command and the main checkout is never touched.
  2. Run inside an OS sandbox or container with the working copy as the only writable path, read-only access to the toolchain, and an empty environment apart from what the task needs.
  3. Route all network through an allow-listing proxy that resolves names itself, listing only the package mirror and code host; log blocked attempts.
  4. Hold no production credentials. Use a development database and short-lived scoped tokens.
  5. Write permission rules for the common case (test runner and formatter allowed; destructive and publishing commands ask or are denied), accepting that these are speed bumps, not walls.
  6. Gate the irreversible: pushing, publishing, deleting and spending always ask, showing the full action, and the approval survives a restart.
  7. Keep a record. Log every tool call, decision and blocked request so a reviewer can reconstruct what happened (chapter 15).
  8. Test the boundary by trying to escape it, as in Lab 7.

Analogy: rules on the door and locks on the door

A sign on a workshop door saying "authorised staff only, no tools out of the building" is a permission: it informs honest people and lets the manager ask questions, but it stops no one who ignores it. A locked door, a fenced yard and a security desk that checks bags are a sandbox. A sensible workshop has both: the sign for the everyday case, and the lock for the day someone ignores the sign.

Where it breaks down: a person ignores a sign deliberately and can be held accountable. A model may ignore a rule because it was misled, or because of a misunderstanding, and has no accountability. It is also much faster than a person, so the lock has to hold against thousands of attempts, not one.

Key takeaways

  • Permissions decide what an agent may attempt; sandboxes decide what an attempt can reach. Use both, and make the sandbox the boundary, because permission rules over command strings and paths have holes.
  • Least privilege for agents: files, commands, network, credentials and resources, each starting from nothing. Absent credentials cannot be stolen.
  • Isolation is a spectrum from process limits to microVMs. Process limits cap consumption, not visibility. Containers share the host kernel. Stronger isolation (gVisor, Firecracker-style microVMs) is for hostile code and many tenants, at a cost in start-up time and compatibility.
  • Cut the network by default and enforce an allow-list in a proxy outside the sandbox: match whole host labels, check the resolved address against private and metadata ranges, and avoid listing shared services an attacker can read.
  • Confirmation prompts work when they are rare, show the real action with full arguments, and cover only irreversible or external effects. Sandboxing reduced prompts by 84% in Anthropic's internal usage, which is how the remaining prompts stay meaningful.
  • Test the boundary from inside: try to read secrets, write outside the workspace and reach an unlisted host.

A harness allows any shell command that starts with ls or git status. Which problem makes this rule unsafe?

  1. Shell commands are case sensitive
  2. One string can contain several commands (for example git status; curl ... | sh) and a prefix such as ls also matches other programs like lsof
  3. The model cannot produce commands that start with ls
  4. Prefix rules are slower than regular expressions
A command line is a small program; separators, substitutions and pipes chain more commands after an allowed prefix. In the experiment the naive check approved all ten commands, including the dangerous ones. Case and speed are irrelevant, and models write such commands routinely.

A team runs its coding agent in a container started with default flags, with the developer's home directory mounted, full internet access and cloud credentials in environment variables. What is the most accurate description?

  1. Fully sandboxed, because containers isolate processes
  2. Sandboxed for files but not for the network
  3. Sandboxed as long as the image is up to date
  4. Packaged, not sandboxed: the agent can read the mounted home directory and credentials and send them anywhere, and the container shares the host kernel
What matters is what is mounted, what network it can reach, which credentials it can read and which kernel it shares. Here all four are permissive. Image freshness does not change those exposures, and the home mount means even file isolation is absent.

In proc20.py, the untrusted code could not see the API key, was stopped by the CPU limit and could not write a 5 MB file, yet could still list the real home directory. What does this show?

  1. Resource limits and a clean environment bound consumption and inherited secrets, but do not restrict which files the process can see
  2. The CPU limit failed to work
  3. The home directory listing proves the sandbox was misconfigured
  4. Environment scrubbing is pointless
rlimits cap how much a process can use; they have no notion of paths. Scrubbing did work (the key was invisible). Hiding the file system requires a namespace, a mount policy or a VM, which is why process limits are only the first layer.

Which allow-list implementation is correct for the allowed host pypi.org?

  1. Allow any host whose name ends with pypi.org
  2. Allow any host whose name contains pypi.org
  3. Allow the exact host or its true sub-domains (matching whole labels), then check that the resolved address is not private, loopback or link-local
  4. Allow the host only if the URL is long enough to contain a path
Ends-with accepts evilpypi.org, and contains accepts pypi.org.evil.test. Matching whole labels fixes names; the address check closes the case where a permitted name resolves to an internal address such as the cloud metadata endpoint. URL length is irrelevant.

Why is it a security improvement, not only a convenience, that a sandbox lets a coding agent run with far fewer permission prompts?

  1. Prompts slow the model down and increase token costs
  2. Frequent prompts cause approval fatigue, so people stop reading them; fewer prompts means the remaining ones get real attention
  3. Sandboxes make prompts unnecessary for every action
  4. Users prefer fewer clicks regardless of risk
The human is the policy engine in a prompt, and attention is limited. Enforcing boundaries in the sandbox leaves prompts for rare, consequential decisions. A sandbox does not remove the need for approval of irreversible or external actions, and the speed argument is secondary.

You must run code submitted by anonymous users, up to thousands of short jobs a minute. Which isolation choice best fits?

  1. A plain process with resource limits, because it is fastest to start
  2. A shared container per user with default settings
  3. No isolation but a strong system prompt
  4. A microVM or user-space-kernel sandbox per job, so hostile code cannot reach the host kernel, with a network proxy and no credentials
Hostile code and many tenants call for a boundary stronger than a shared kernel, and microVMs such as Firecracker boot fast enough (under 125 ms in the paper) to make one per job practical. Process limits show no protection from reading files, and default containers share the kernel.

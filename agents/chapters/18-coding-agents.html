Coding Agents

Software is the field where agents have been most useful, and the reason is not that models like code. Code comes with a referee: tests, compilers and linters say within seconds whether an edit worked. This chapter shows how coding agents such as SWE-agent, OpenHands and terminal tools read a repository, edit files, run commands and check their own work, and where that design still breaks.

Why this matters

Almost every engineer on this path will use a coding agent daily and many will build or configure one. The tool loop of chapter 2 and the tool design rules of chapter 5 meet here in their most demanding setting: a large, unfamiliar, interdependent codebase, a shell that can do real damage, and a grader that is stricter than a human reviewer. After this chapter you can explain why a particular edit format fails, design the feedback an agent needs to converge, read a SWE-bench result with the right caution, and name the failure modes to look for when a coding agent says "done". Chapter 22 then covers working with these tools as a developer.

Why code is the friendliest domain for agents

Compare three tasks you might give an agent: "book me a flight", "write a good strategy memo", and "make this failing test pass". The first has side effects you cannot undo and no instant check. The second has no check at all except a person's judgement. The third has a verifier: a program that returns pass or fail in seconds, without a person in the loop. Coding agents inherit four properties that most other domains lack.

  • Fast, objective feedback. A test run, a type check or a compiler error is a tool result the model can act on. The agent can try, observe and repair many times per minute, which is exactly the loop that ReAct-style agents need.
  • Everything is text. Source, error messages, diffs and logs are all strings, the medium the model already works in. No screenshots, no coordinates (compare chapter 17).
  • Cheap undo. Version control turns a bad edit into a one-line revert. An agent working on a branch in a fresh checkout can do damage only to something you can recreate.
  • A bounded world. The relevant state is a directory. The agent does not need to know about your calendar, only the repository, the test command and the language.

None of these properties is perfect, and the failure modes later in the chapter are what happens where each one is weakest: tests that do not cover the behaviour, undo that does not extend to a database the agent also touched, and a "bounded" shell that is not bounded at all unless you make it so (chapter 20).

The shape of a coding agent

Strip away branding and every coding agent does four things in a loop: find the relevant code, read it, edit it, and check the result. The model proposes each step as a tool call; a harness (the program around the model that executes tools and enforces policy, as in chapter 17) carries it out in a working directory and returns the output.

The next four sections take the stages in turn, then we assemble them into a working agent and run it.

Finding and reading code

A repository can hold millions of lines, and the model's context window (the text it can attend to at once, see chapter 10) holds a few hundred thousand tokens at best. Reading everything is impossible and reading too much is harmful: relevant lines get diluted. So the first problem is navigation, and there are three common answers.

Search tools (grep and glob)
Exact text search and file-name patterns. Cheap, always up to date, with no index to build, and good when the agent can guess an identifier or an error string. Most terminal agents rely on these first.
A repository map
A compact summary of the whole repository (files with their key classes and function signatures) sent with each request, so the model knows what exists before it searches. Aider's documentation describes ranking files with a graph algorithm, where each file is a node and edges connect files that depend on each other, and then fitting the most important parts into a token budget that defaults to 1,000 tokens (the --map-tokens setting).
Semantic search
An embedding index over code chunks, queried by meaning ("where do we validate refunds?"). It helps when names are unhelpful, but the index goes stale as the agent edits, so it is usually a supplement rather than the main tool. Course A5 covers retrieval in depth.

Reading has its own design question. Dumping a whole file with cat is wasteful for large files and makes it easy to lose the thread. The SWE-agent authors (Yang et al., 2024, "SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering") built a windowed file viewer that shows 100 lines per turn with line numbers, plus commands to scroll and to search within a file. The numbered window keeps each observation small and gives the model something to point at. Their directory search lists only the files that match, without showing the matching lines, to stop one broad query from flooding the context. And when a command prints nothing, the interface says so explicitly ("Your command ran successfully and did not produce any output"), because silence is ambiguous to a model: it cannot tell success from a hang. These are the tool design rules of chapter 5 applied to a shell, which the paper names the agent-computer interface (ACI): an interface designed for the model's strengths and weaknesses rather than a person's. The full story is in case study 2.

Editing: the part that goes wrong most

An edit is a tool call, and the way you ask the model to express it determines how often it fails. There are three families.

The script below runs all three on a generated 119-line file, with token counts from the shared stand-in tokeniser (about four characters per token, so the absolute numbers are indicative). It also shows the idea SWE-agent calls a linter gate: after an edit, check that the file still parses, and reject the edit if it does not.

# edits18.py: why edit formats matter. Same file, same intended change, three ways to say it.
import ast
from llm import count_tokens

SRC = "\n".join(f"def f{i}(x):\n    return x + {i}\n" for i in range(1, 41))   # 120 lines
lines = SRC.splitlines()
print("file:", len(lines), "lines,", count_tokens(SRC), "tokens")

# 1. Whole-file rewrite: the model re-emits everything.
print("whole file rewrite :", count_tokens(SRC), "output tokens")

# 2. Line-number edit: 'replace lines 60-61'. Cheap, but fragile once anything shifts.
def edit_lines(src, a, b, new):
    L = src.splitlines(); L[a-1:b] = new.splitlines(); return "\n".join(L) + "\n"
after_first = edit_lines(SRC, 10, 11, "def f5(x):\n    # cached\n    return x + 5\n")   # an earlier edit adds a line
# The model planned its second edit against the OLD numbering: 'replace 60-61 (def f30)'.
wrong = edit_lines(after_first, 60, 61, "def f30(x):\n    return x * 30\n")
print("line-number edit, stale numbers ->")
for l in wrong.splitlines()[57:63]: print("   ", l)

# 3. Search-and-replace edit: the old text itself says where.
def str_replace(src, old, new):
    assert src.count(old) == 1, f"{src.count(old)} matches"
    return src.replace(old, new)
right = str_replace(after_first, "def f30(x):\n    return x + 30\n", "def f30(x):\n    return x * 30\n")
print("str_replace edit    :", count_tokens("def f30(x):\n    return x + 30\n") + count_tokens("def f30(x):\n    return x * 30\n"), "output tokens; f30 now:", right.splitlines()[right.splitlines().index("def f30(x):")+1].strip())

# A syntax gate (the SWE-agent idea): reject an edit that leaves the file unparseable.
def gated_edit(src, old, new):
    out = str_replace(src, old, new)
    try: ast.parse(out)
    except SyntaxError as e: return src, f"REJECTED: SyntaxError line {e.lineno}: {e.msg}. File unchanged."
    return out, "OK"
_, msg = gated_edit(SRC, "return x + 7", "return (x + 7")
print(msg)
_, msg = gated_edit(SRC, "return x + 7", "return x * 7")
print(msg)

Read the output line by line. The whole-file rewrite costs every token of the file: 306 here, and about 2,600 for a 1,000-line file at the same density. The search-and-replace edit costs 16. The line-number edit looks just as cheap but is the dangerous one: an earlier edit added a line, the model's second edit used the old numbering, and the result is a file in which def f20(x): is followed directly by another def, with no error raised. The syntax gate catches the unbalanced bracket and leaves the file unchanged, and the model receives a message it can act on.

Common misconception

"If the model can write code, it can edit code." Writing a function from scratch and changing one line in a 600-line file are different skills. The second needs the model to reproduce surrounding text exactly, to keep track of line positions that shift, and to leave everything else alone. Agents fail here far more often than at the logic, which is why the edit tool and its error messages deserve as much design attention as the prompt. Some tools use unified-diff or patch-style formats; the same two questions apply to them: does the format survive earlier edits, and does it fail loudly?

Running and checking

The check stage turns the agent from a text generator into something that converges. The strongest signal is a test suite, but any program that returns a verdict works: a type checker, a linter, a compiler, a build, a script that reproduces the bug, or a screenshot comparison for a user interface. Anthropic's Claude Code best-practices guidance makes this one of its central recommendations: give the agent a way to verify its own work (tests, a build, a screenshot), because without one you become the only feedback loop.

The agent below is complete: a repository with a boundary bug, three tools (a windowed view, an exact str_replace and run_tests), and the loop of chapter 2. The model is the scripted stand-in from lab-support/llm.py, so the replies are fixed in advance and the run is reproducible; what is real is the repository, the edits and the test runner. The scripted model deliberately repeats its edit once, as real models sometimes do, so that you can see the edit tool refuse.

# agent18.py: a coding agent in 60 lines. Tools: view (windowed), str_replace (exact, unique), run_tests.
import os, subprocess, sys, tempfile, textwrap
from llm import ScriptedModel, tool_use, tool_result, text

REPO = os.path.realpath(tempfile.mkdtemp(prefix="repo18_"))
def write(name, body):
    with open(os.path.join(REPO, name), "w") as f: f.write(textwrap.dedent(body).lstrip())

write("shipping.py", """
    def shipping_cost(weight_kg, express=False):
        base = 4.0 + 1.5 * weight_kg
        if weight_kg > 20:
            base += 10.0
        if express:
            base *= 2
        return round(base, 2)
""")
write("test_shipping.py", """
    import unittest
    from shipping import shipping_cost
    class T(unittest.TestCase):
        def test_light(self):   self.assertEqual(shipping_cost(2), 7.0)
        def test_express(self): self.assertEqual(shipping_cost(2, express=True), 14.0)
        def test_heavy(self):   self.assertEqual(shipping_cost(20), 44.0)   # the 20 kg boundary
        def test_over(self):    self.assertEqual(shipping_cost(21), 45.5)
    if __name__ == "__main__": unittest.main()
""")

def view(path, start=1, end=40):
    lines = open(os.path.join(REPO, path)).read().splitlines()
    return "\n".join(f"{i:>3}  {l}" for i, l in enumerate(lines[start-1:end], start))

def str_replace(path, old, new):
    p = os.path.join(REPO, path); src = open(p).read()
    n = src.count(old)
    if n == 0: return "ERROR: old_str not found. View the file again."
    if n > 1:  return f"ERROR: old_str matches {n} places. Add context to make it unique."
    open(p, "w").write(src.replace(old, new)); return "OK: edited " + path

def run_tests():
    r = subprocess.run([sys.executable, "-B", "-m", "unittest", "-q"], cwd=REPO, capture_output=True, text=True, timeout=20)
    return (r.stderr + r.stdout).strip().replace(REPO, "repo")[-600:]

TOOLS = {"view": view, "str_replace": str_replace, "run_tests": run_tests}
model = ScriptedModel([
    [text("Run the tests first."), tool_use("run_tests", {}, "t1")],
    [tool_use("view", {"path": "shipping.py"}, "t2")],
    [text("test_heavy expects 4 + 30 + 10 = 44.0 at exactly 20 kg, but the code returned 34.0. The surcharge is missing at the boundary: > should be >=."),
     tool_use("str_replace", {"path": "shipping.py", "old": "weight_kg > 20", "new": "weight_kg >= 20"}, "t3")],
    [tool_use("str_replace", {"path": "shipping.py", "old": "weight_kg > 20", "new": "weight_kg >= 20"}, "t4")],
    [tool_use("run_tests", {}, "t5")],
    "Fixed: the surcharge test was `> 20`; it is now `>= 20`. All four tests pass.",
])
msgs = [{"role": "user", "content": "test_heavy fails. Fix the bug in the shipping code."}]
for step in range(8):
    r = model.complete(msgs, tools=[])
    msgs.append(r.as_message())
    for b in r.content:
        if b["type"] == "text": print(f"[{step}] model: {b['text']}")
    uses = [b for b in r.content if b["type"] == "tool_use"]
    if not uses: break
    results = []
    for u in uses:
        out = TOOLS[u["name"]](**u["input"])
        print(f"[{step}] {u['name']}({', '.join(f'{k}={v!r}' for k, v in u['input'].items())})\n" + textwrap.indent(out, "      "))
        results.append(tool_result(u["id"], out, out.startswith("ERROR")))
    msgs.append({"role": "user", "content": results})

Follow the transcript. The agent runs the tests first, which is a habit worth building into prompts: it establishes that the failure is real and shows the exact assertion (34.0 != 44.0). It then reads the file with line numbers, reasons from the number to the cause (4 + 30 + 10 is 44, so the surcharge is missing at exactly 20 kg), makes one targeted edit, and re-runs the tests. The repeated edit at step 3 fails with "old_str not found", a message that tells the model what to do next. Nothing was lost, because the edit tool is strict about what it will touch. The final step is not a claim; it is a passing test run that the harness actually executed.

Systems connection

Under the loop is ordinary operating-system plumbing. run_tests is a child process whose exit code and output come back as a tool result; the working directory is a file-system subtree; and the "undo" is git. The same processes and files that make this easy also make it dangerous: the agent's shell has whatever permissions its user has. That is the subject of chapter 20.

Reproduce first, then fix

For a bug report rather than a failing test, the most reliable agent habit is to write a failing test or script first. It converts an English description into a verifier, it shows the agent whether it has understood the bug, and it leaves behind a regression test. Without it, the agent can only check that its change does not crash. Prompts and instruction files for coding agents commonly spell this out: reproduce, then fix, then show the passing run.

Three architectures: SWE-agent, OpenHands and terminal agents

The loop is the same everywhere; the packaging differs in where the agent runs, who controls the machine, and how much of the interface is fixed.

SWE-agent: the interface is the contribution

SWE-agent (Princeton and Stanford researchers, May 2024) took a fixed language model and changed only the interface. The abstract reports 12.5% pass@1 on SWE-bench and 87.7% on HumanEvalFix, both state of the art at the time, and attributes the gain to the custom ACI that helps the model create and edit files, navigate a repository and run tests. The lesson that outlived the numbers is that interface design is a lever on capability: the model stayed the same and the interface changed the result. Each environment gets a fresh container; the run is a self-contained research artefact.

OpenHands: a platform

OpenHands (formerly OpenDevin; Wang et al., 2024, "OpenHands: An Open Platform for AI Software Developers as Generalist Agents", ICLR 2025) is a platform under the MIT licence for agents that, like a developer, write code, use a command line and browse the web. Its abstract stresses sandboxed execution so that agents run code without direct access to the host, and reports evaluation on 15 tasks including SWE-bench and WebArena. Architecturally the useful idea is an event stream: every action the agent takes and every observation it receives is an event in one ordered log, which makes runs replayable and is the same structure as the event-sourced agents of chapter 15. The browser tool is the screen-driven side of chapter 17.

Terminal coding agents

The tools most developers use run in a terminal, on the developer's own machine, against the real repository. They add capabilities the research systems did not need, because a human is present and the repository has a history:

  • Instruction files. A Markdown file in the repository tells the agent how to build, test and follow local conventions: CLAUDE.md for Claude Code, and AGENTS.md, an open format now stewarded by the Agentic AI Foundation under the Linux Foundation, which several tools read. The file is loaded into context every session, so it is the cheapest form of the memory of chapter 11. Keep it short; every line costs tokens on every turn.
  • Permissions and sandboxes because the machine is yours (chapter 20).
  • Plan-then-act and checkpoints. The Claude Code guidance recommends exploring and planning before editing, then verifying and committing, and keeping checkpoints so a bad turn can be rewound.
  • Hooks versus instructions. A rule in an instruction file is advice the model may ignore; a hook is a script the harness runs at a fixed point (before a tool call, after an edit). Anything that must happen every time belongs in a hook, such as running the formatter or blocking edits to a protected directory.
  • Sub-agents and parallel sessions. A sub-agent explores in its own context window and returns a summary, keeping the main context clean (chapter 14); separate git worktrees let several sessions work on different branches at once.

State of play, October 2026

The field moves in months; this is a dated snapshot, and the durable concepts are above. Terminal and IDE agents from several vendors and open-source projects are in everyday use, and AGENTS.md has become a common instruction-file convention (see agents.md). Benchmarks have moved from the original SWE-bench to curated and harder successors, and published scores on any single benchmark change quickly and depend on the scaffold as much as the model, so this chapter quotes the figures from the original papers rather than current leaderboard positions. Check the maintainers' own pages (swebench.com, the project repositories) for numbers you intend to rely on.

Measuring a coding agent

SWE-bench (Jimenez et al., 2023, "SWE-bench: Can Language Models Resolve Real-World GitHub Issues?") built a benchmark from real work: 2,294 software-engineering problems drawn from issues and pull requests in 12 popular Python repositories. The model receives the repository at the commit before the fix and the issue text, and must produce a patch. When the paper appeared the best model, Claude 2, resolved 1.96% of the instances. That number is a snapshot of 2023, but the construction is the lasting contribution, because it shows how to grade agents without a human.

How the grader works

Each instance carries two sets of tests taken from the real pull request. FAIL_TO_PASS tests fail before the fix and pass after it: they define "the bug is fixed". PASS_TO_PASS tests passed before and must still pass: they catch changes that fix one thing by breaking another. An instance counts as resolved only if both sets pass. The script below reproduces that logic on the small shipping repository, and includes the cheat a naive grader falls for.

# grade18.py: grading a coding agent the SWE-bench way, and the cheat that grading must survive.
import os, shutil, subprocess, sys, tempfile, textwrap, re

def make_repo():
    d = os.path.realpath(tempfile.mkdtemp(prefix="g18_"))
    open(f"{d}/shipping.py", "w").write(textwrap.dedent("""
        def shipping_cost(w, express=False):
            base = 4.0 + 1.5 * w
            if w > 20: base += 10.0
            return round(base * (2 if express else 1), 2)
    """).lstrip())
    open(f"{d}/test_shipping.py", "w").write(textwrap.dedent("""
        import unittest
        from shipping import shipping_cost
        class T(unittest.TestCase):
            def test_light(self):   self.assertEqual(shipping_cost(2), 7.0)
            def test_heavy(self):   self.assertEqual(shipping_cost(20), 44.0)
    """).lstrip())
    return d

def run(d, test_file):
    r = subprocess.run([sys.executable, "-B", "-m", "unittest", "-v", test_file[:-3]], cwd=d, capture_output=True, text=True)
    return {m.group(1): m.group(2) == "ok" for m in re.finditer(r"(test_\w+) \(.*?\) \.\.\. (\w+)", r.stderr)}

def grade(d, pristine_tests, fail_to_pass, pass_to_pass):
    shutil.copy(pristine_tests, f"{d}/test_shipping.py")       # always grade with the ORIGINAL tests
    res = run(d, "test_shipping.py")
    f = all(res.get(t) for t in fail_to_pass); p = all(res.get(t) for t in pass_to_pass)
    return f"FAIL_TO_PASS {'ok' if f else 'FAILED'}, PASS_TO_PASS {'ok' if p else 'FAILED'} -> {'RESOLVED' if f and p else 'NOT resolved'}"

F2P, P2P = ["test_heavy"], ["test_light"]
base = make_repo(); shutil.copy(f"{base}/test_shipping.py", f"{base}/pristine.txt")
pristine = f"{base}/pristine.txt"
print("before any edit :", run(base, "test_shipping.py"))

honest = make_repo()
s = open(f"{honest}/shipping.py").read().replace("w > 20", "w >= 20"); open(f"{honest}/shipping.py", "w").write(s)
print("honest fix      :", grade(honest, pristine, F2P, P2P))

cheat = make_repo()
t = open(f"{cheat}/test_shipping.py").read().replace("44.0", "34.0"); open(f"{cheat}/test_shipping.py", "w").write(t)
print("cheat, own tests:", run(cheat, "test_shipping.py"), "(the agent sees green)")
print("cheat, graded   :", grade(cheat, pristine, F2P, P2P))

breaks = make_repo()
s = open(f"{breaks}/shipping.py").read().replace("return round(base * (2 if express else 1), 2)", "return 44.0"); open(f"{breaks}/shipping.py", "w").write(s)
print("hard-coded 44.0 :", grade(breaks, pristine, F2P, P2P))
before any edit : {'test_heavy': False, 'test_light': True}
honest fix      : FAIL_TO_PASS ok, PASS_TO_PASS ok -> RESOLVED
cheat, own tests: {'test_heavy': True, 'test_light': True} (the agent sees green)
cheat, graded   : FAIL_TO_PASS FAILED, PASS_TO_PASS ok -> NOT resolved

The third line is the important one. An agent that edits the tests so that they match its broken code sees green in its own working copy ("the agent sees green"). The grader copies in the original tests before running, so the cheat is not resolved. The last case, hard-coding the expected answer, passes the target test but fails test_light, which is what PASS_TO_PASS exists for.

What the benchmark does not tell you

  • Test quality limits the grader. In August 2024 OpenAI and the SWE-bench authors released SWE-bench Verified: 93 experienced Python developers screened 1,699 samples for under-specified issues and unfair or flawed tests, and 500 were kept as a cleaner test set. A resolved instance is only as meaningful as its tests.
  • Public repositories invite contamination. The issues and fixes are on the open web and may be in a model's training data, so a high score can partly reflect memory. Treat any public benchmark as a coarse filter and build your own evaluation on your own tasks (course A6).
  • Resolving an issue is not doing a developer's job. It omits review, design decisions, ambiguity and maintenance.

The right test of a tool is whether it helps real developers on real work. METR ran a randomised trial in early 2025 (published July 2025) with 16 experienced open-source developers and 246 issues from their own repositories, each randomly assigned to allow or disallow AI tools. Developers took 19% longer when AI was allowed. Beforehand they had forecast a 24% speed-up, and afterwards they still believed it had sped them up by 20%. METR itself notes the result is dated and points to later data (it refers to a February 2026 update), so read the original and the update together; case study 3 does so. The lesson is about measurement, not about whether the tools are good: perceived speed is a poor guide, and the effect depends on the developer, the codebase and the task.

How coding agents fail

These are the failure modes to look for when reading a transcript or reviewing a change.

Gaming the verifier

Editing or deleting a failing test, special-casing the test's input, or catching and swallowing the error. The grader above shows the defence: run the original tests from a path the agent cannot write.

Thrashing

The same failing edit repeated, or a cycle of fix A, break B, fix B, break A. Mitigate with an iteration budget (chapter 2), a rule to stop and summarise after N failures, and fresh context.

Plausible but wrong

Calling a function that does not exist, using a library version's old API, or fixing the symptom at the wrong layer. Tests catch some of it; a reviewer reading the diff catches more.

Scope creep

Reformatting a file, renaming things, or "improving" code nobody asked about, which buries the real change in the diff. Ask for minimal changes and review the diff, not the summary.

Context decay

In a long session early instructions and file contents scroll away, and the agent contradicts earlier decisions. Compact, restart with notes, or delegate to a sub-agent (chapter 10).

Dangerous side effects

A shell can delete files, push to a remote or touch a production database. The most cited example is case study 6. The cure is least privilege, not better prompts.

One more belongs in its own paragraph. A coding agent reads text that other people wrote: issue bodies, pull-request comments, README files, dependency documentation, web pages it fetches, and tool descriptions from MCP servers. Any of those can contain instructions, and the agent has a shell. This is prompt injection, and for a coding agent with access to your credentials it is the most serious risk. Chapter 19 treats it in full.

Analogy: a contractor on day one

Picture a capable contractor handed a ticket, a terminal and the company's test suite, and who has never seen the codebase. They search, skim, make a change, run the tests, and read the failures. How well they do depends less on raw talent than on three things you control: whether the tests are trustworthy, whether the tools show them the right amount of code, and what you let them touch on day one. A coding agent is the same.

Where it breaks down: the contractor remembers tomorrow what they learned today and asks questions when the ticket is unclear. An agent starts every session with only what is in the context window and the instruction file, and will usually attempt the task as written rather than push back on it.

  3. Add a syntax gate to str_replace using ast.parse, as in edits18.py, then script an edit that leaves an unclosed bracket. Check that the file on disk is unchanged.

Key takeaways

  • Coding agents work because code has a verifier: tests, types and builds return a verdict in seconds. Give the agent one and make it run it.
  • The loop is find, read, edit, check. A failing check is the observation that drives the next edit.
  • Edit format decides reliability. Search-and-replace anchored on content and a syntax gate fail loudly; line numbers and whole-file rewrites fail silently or expensively.
  • SWE-agent showed that the agent-computer interface is a lever on capability. OpenHands packages agents on a sandboxed event-stream runtime. Terminal agents run on your machine with permissions, instruction files and hooks.
  • SWE-bench grades with FAIL_TO_PASS and PASS_TO_PASS tests run from the original files. Treat benchmark scores as coarse and contaminated; measure on your own work. The METR trial found a 19% slowdown while developers believed they were faster.
  • Watch for gamed tests, thrashing, plausible-but-wrong code, scope creep, context decay, dangerous side effects and prompt injection.

Check your understanding

Why are coding agents generally more reliable than agents for tasks such as drafting a strategy memo?

  1. Models are trained mostly on code, so they never make mistakes in it
  2. Code has automatic verifiers (tests, compilers, linters) that give fast, objective feedback inside the loop
  3. Code tasks are always shorter and need fewer tokens
  4. Version control makes it impossible for the agent to break anything
The verifier is what lets the agent observe its mistakes and repair them. Models do make many coding mistakes, tasks can be long, and version control makes undo cheap but does not prevent side effects outside the repository such as a database or a remote.

An agent edits a 600-line file by line number: "replace lines 300 to 305". An earlier edit in the same session inserted four lines above line 300. What is the likely result?

  1. The tool detects the shift and rejects the edit
  2. The edit applies correctly, because line numbers are stable within a session
  3. The edit fails with "file changed" and the model retries
  4. The edit silently replaces the wrong lines and may leave the file broken, so the agent may not notice until a later check
Positional edits are only safe if every earlier change is accounted for. Nothing in a plain line-number tool compares content. Search-and-replace formats anchor on the old text, so a missing or ambiguous match raises an error instead. The first option describes a different design.

In SWE-bench grading, what are the PASS_TO_PASS tests for?

  1. To catch a patch that fixes the target bug but breaks behaviour that worked before
  2. To check that the issue text was understood correctly
  3. To measure how fast the tests run after the patch
  4. To confirm the agent wrote new tests of its own
FAIL_TO_PASS tests define the fix; PASS_TO_PASS tests are the regression guard. Hard-coding an expected output can satisfy the first set and still fail the second, as the grading script showed. Neither set measures speed or the agent's own tests.

A team's coding agent reports "all tests pass" on a change, yet review finds it deleted two failing tests. Which control best prevents this?

  1. Ask the model in the prompt to be honest about test results
  2. Increase the iteration budget so it has more attempts
  3. Run the original test files from a location the agent cannot modify, and fail the run if protected paths changed
  4. Switch to a larger context window
The grader must not trust the agent's working copy. Prompts are advice, not enforcement, more attempts make gaming more likely rather than less, and a larger context window has nothing to do with it. A hook or CI check that guards the test directory is deterministic.

What was the main claim of the SWE-agent paper about why it improved results with a fixed language model?

  1. It fine-tuned the model on thousands of repository histories
  2. It designed a custom agent-computer interface (windowed viewer, editing with a linter, concise search) suited to the model
  3. It replaced tests with human review
  4. It ran many models in parallel and took a vote
The contribution was the interface. The ACI limits observation size, rejects syntactically broken edits and gives clear messages. The paper does not rely on fine-tuning or voting.

Which conclusion is best supported by the METR randomised trial of experienced open-source developers?

  1. Self-reported speed-ups are reliable when collected after the task
  2. The study shows AI tools never help programmers
  3. The result applies unchanged to every developer and task
  4. Perceived and measured productivity can differ, so teams should measure on their own tasks rather than rely on impressions
In the study developers took 19% longer with AI yet believed they were 20% faster. That is a finding about measurement for a particular group (experienced developers on mature codebases they knew well), not a universal verdict, and METR points to later data.

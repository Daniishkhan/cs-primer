Long Context versus Retrieval

Context windows now hold hundreds of thousands of tokens, which raises an honest question: why build a search system at all when you can paste the whole corpus into the prompt? This chapter works out what each approach costs, what each gets wrong, and how to measure the difference on your own questions instead of trusting a rule of thumb.

Why this matters

Every agent that answers from documents makes this choice, often without noticing: the policy bot, the contract reviewer, the codebase assistant. Pick retrieval when you needed the whole picture and you get confident wrong counts. Pick stuffing when you needed cheap, permissioned, citable lookups and you get a large bill and a slow product. After this chapter you can estimate the cost of each, name the failure each one has, design a small experiment that settles the question for your data, and recognise the hybrids that usually win.

Two ways to give a model what it needs to know

A language model answers from two places: what it absorbed in training, and what is in its prompt. Training knowledge is frozen, incomplete about your private documents and unaware of anything recent. So for most business questions the facts must arrive in the prompt. The context window is the maximum number of tokens (the sub-word pieces models read, roughly three quarters of an English word each) that one request can hold: instructions, history, documents and the answer being written. Chapter 1 showed how a request is assembled; chapter 10 treats the window as a budget.

There are two basic strategies for getting documents into it.

Long-context stuffing
Put the whole corpus (or a large slice of it) in the prompt, add the question, and let the model find what it needs. No index, no ranking, no chunking decisions.
Retrieval (RAG)
Retrieval-augmented generation searches an index first, puts only the few most relevant chunks in the prompt, and asks the model to answer from those. The index, the ranking and the chunk size are all engineering you own. Chapter 23 covers the dense half of it; here we only need its shape.

Neither lane is a default. They differ in four things you can put numbers on: what each query costs, how well the model uses what it is given, which questions each can answer at all, and what it takes to keep answers correct, permitted and citable. We take them in that order.

What a long prompt costs

API providers bill input tokens, and they bill them again on every request, because a model call is stateless: nothing is remembered between requests unless you send it again. So stuffing a 200,000-token corpus means paying for 200,000 input tokens every time anyone asks anything. Retrieval pays for roughly the size of the retrieved slice, whatever the corpus size. Latency follows the same shape: before a model emits its first output token it must process the whole prompt in a phase called prefill, and prefill time grows with prompt length (A3 chapter 18 explains prefill and the KV cache that stores its result).

The arithmetic is worth doing once with explicit assumptions. The script below uses illustrative prices, not any provider's current list: $3 per million input tokens, and a prompt cache with the commonly published shape (a write costs 1.25 times the normal price, a read 0.1 times). Prompt caching lets the provider keep the processed prefix of a prompt for a few minutes, so a repeated prefix is read cheaply. It matters here because a stuffed corpus is exactly a large, identical prefix.

# cost.py: per-query cost of "stuff the corpus" versus "retrieve a few chunks" (all prices are ASSUMPTIONS)
PRICE_IN = 3.00          # dollars per million input tokens (assumption)
WRITE, READ = 1.25, 0.10 # cache write / read multipliers (5-minute cache, typical published ratios)
QUERIES_PER_HOUR = 600   # assumption: busy enough that the cache stays warm
ANSWER_TOKENS_IN = 300   # question + instructions
RAG_CONTEXT = 4_000      # retrieved chunks sent per query (assumption)

def stuff_uncached(corpus):
    return (corpus + ANSWER_TOKENS_IN) * PRICE_IN / 1e6

def stuff_cached(corpus, warm=0.99):
    # a cache hit reads the corpus at 0.1x; a miss re-writes it at 1.25x
    per_token = warm * READ + (1 - warm) * WRITE
    return (corpus * per_token + ANSWER_TOKENS_IN) * PRICE_IN / 1e6

def retrieve(corpus):
    return (RAG_CONTEXT + ANSWER_TOKENS_IN) * PRICE_IN / 1e6   # independent of corpus size

print(f"{'corpus tokens':>13} {'stuff':>9} {'stuff+cache':>12} {'retrieve':>9} {'x vs RAG':>9} {'x cached':>9}")
for corpus in (20_000, 100_000, 200_000, 500_000, 1_000_000):
    a, b, c = stuff_uncached(corpus), stuff_cached(corpus), retrieve(corpus)
    print(f"{corpus:>13,} {a:>9.4f} {b:>12.4f} {c:>9.4f} {a/c:>8.1f}x {b/c:>8.1f}x")
day = 24 * QUERIES_PER_HOUR
print(f"\n200k-token corpus, {day:,} queries/day: stuff ${day*stuff_uncached(200_000):,.0f}, "

Three things stand out. Uncached stuffing is expensive even at modest sizes, 4.7 times the retrieval cost at only 20,000 tokens and 47 times at 200,000. Caching changes the picture sharply: at 20,000 tokens a warm cache makes stuffing cheaper than retrieval, and the two cross again as the corpus grows (at roughly 40,000 tokens under these assumptions). And caching has conditions. The 0.99 warm fraction assumes steady traffic; if requests arrive less often than the cache lifetime, most of them pay the write price instead. Caching also does nothing for latency of the first request after the cache goes cold, and it requires that the corpus prefix is identical across requests, which fails the moment you want per-user documents in front of the shared text.

Attention itself adds a second cost that a price list hides. In a Transformer every token looks at every earlier token, so the work to process a prompt grows faster than linearly with its length, and the stored keys and values that make later tokens cheap occupy GPU memory in proportion to length (A2 chapter 9 derives this; A3 chapter 22 turns it into money). Providers fold much of it into a flat per-token price, but you feel it as latency: a 500,000-token prompt can take many seconds before the first word appears.

State of play, October 2026

Anthropic's context-window documentation lists 1M-token windows as the default for most current Claude models, billed at standard per-token rates with one model-specific exception for prompts above 100,000 tokens; other providers publish windows of similar or larger size. Prompt-caching multipliers are published as 1.25 times for a 5-minute write, 2 times for a 1-hour write and 0.1 times for a read, with lower read multipliers listed for some newer models. All of these change often: read your provider's pricing and context-window pages before you do the arithmetic for a real system, and re-run the script with the numbers you find. A window being available says nothing about the model using it well, which is the next question.

Does the model actually use what you give it?

If a model read 500,000 tokens as reliably as it reads 500, the cost question would be the only question. It does not, and the evidence has accumulated in layers, each fixing a flaw in the one before.

Needle in a haystack, and why passing it proves little

The simplest probe is the needle-in-a-haystack test: hide one sentence (the needle, "the vault code is 41872") at some depth inside a long stretch of unrelated text (the haystack), then ask for it. Greg Kamradt popularised it in late 2023, and providers quote near-perfect heat maps. It is a useful smoke test and a weak guarantee. The needle is a literal string that stands out from irrelevant filler, and the question repeats its words. Real documents are full of near-duplicates, and real questions paraphrase.

The script below is a needle test you can point at any model. It runs here against a stand-in that reads perfectly, so its output is a control that proves the harness works, not a result about any real model. Set LAB_MODEL (see the shared llm.py header) to measure a real one.

# needle_sweep.py: does a model find one fact, as the prompt gets longer and the fact moves?
import random, re
from llm import get_model, ScriptedModel, text_of, count_tokens

FILLER = ["The depot reopened after the winter closure.", "Invoices are archived for seven years.",
          "Staff rotas are published on the first Monday of each month.", "Pallets are stacked no higher than four layers.",
          "Visitors sign in at the front desk.", "The canteen serves lunch between noon and two."]

def haystack(n_tokens, depth, needle, rnd):
    sentences = []
    while count_tokens(" ".join(sentences)) < n_tokens:
        sentences.append(rnd.choice(FILLER))
    sentences.insert(int(depth * len(sentences)), needle)         # depth 0 = start, 1 = end
    return " ".join(sentences)

def trial(model, n_tokens, depth, seed):
    rnd = random.Random(seed); secret = f"{rnd.randrange(10**5):05d}"
    prompt = haystack(n_tokens, depth, f"The vault code for Annex 7 is {secret}.", rnd)
    prompt += "\n\nWhat is the vault code for Annex 7? Answer with the digits only."
    return secret in text_of(model.complete([{"role": "user", "content": prompt}], max_tokens=20))

def stand_in(messages, tools, system):                            # reads perfectly: a control, not a result
    m = re.search(r"vault code for Annex 7 is (\d+)", messages[-1]["content"]); return m.group(1) if m else "?"

model = get_model(default=ScriptedModel(stand_in))               # set LAB_MODEL to test a real one
depths = (0, 0.25, 0.5, 0.75, 1)
print("tokens  " + "".join(f"depth {d:<5}" for d in depths))
for n in (2_000, 8_000, 32_000):
    print(f"{n:>6}  " + "".join(f"{sum(trial(model, n, d, s) for s in range(10)) / 10:<11.2f}" for d in depths))

What harder tests found

Four lines of research each tightened the test, and the findings are consistent in direction even where the numbers differ.

  • Position matters. Liu et al., 2023 ("Lost in the Middle: How Language Models Use Long Contexts", published in TACL) tested multi-document question answering and key-value retrieval. Accuracy was highest when the relevant information was at the start or end of the input and dropped significantly when it sat in the middle, even for models built for long contexts.
  • Claimed length is not usable length. Hsieh et al., 2024 ("RULER: What's the Real Context Size of Your Long-Context Language Models?", COLM 2024) extended the needle test to 13 tasks including multi-hop tracing and aggregation, and evaluated 17 models. Models that passed the plain needle test still lost a lot as length grew, and only about half of them kept satisfactory performance at 32,000 tokens despite claiming that length or more.
  • Remove the word overlap and it gets harder. Modarressi et al., 2025 ("NoLiMa: Long-Context Evaluation Beyond Literal Matching", ICML 2025) wrote questions and needles with minimal shared wording, so the model must infer the link. At 32,000 tokens, 11 of the 13 models tested fell below half of their own short-context score; the paper reports GPT-4o dropping from 99.3% to 69.7%.
  • Distractors hurt, unevenly. Chroma's July 2025 technical report "Context Rot" tested 18 models and found that adding distractors (passages that resemble the answer but are wrong) lowered accuracy, that the effect grew with input length, and that performance fell faster when the needle and the question were less similar. The authors are explicit that their tasks are simple and controlled, that they did not establish the mechanism, and that one finding rests on only two haystack topics.

Anthropic's own context-engineering guidance describes the same effect as context rot: as the number of tokens grows, the model's ability to recall information from the context decreases, and the post connects it to the fact that attention spreads over n² pairwise relationships for n tokens, an "attention budget" that is finite. Treat that as an explanation offered by the vendor, not a proven mechanism. What is solid is the behaviour: more tokens in the window means more places to be misled, and the cost shows up on exactly the realistic tasks (paraphrased questions, lookalike passages) that the easy test omits.

Common misconception

"The model passed needle-in-a-haystack at one million tokens, so it can reason over a million tokens." The test shows it can retrieve one literal string from unrelated filler. It says nothing about combining facts that are far apart, counting across a corpus, ignoring near-duplicates or following a question phrased differently from the text. RULER and NoLiMa exist precisely because the easy test saturated while the harder behaviours did not.

Analogy: the open-book exam

Stuffing is an open-book exam where the whole library is on the desk. Retrieval is a librarian who fetches three books before you start. With a thin, well-indexed library the desk is fine. With a huge one you waste the exam time skimming, you may grab a lookalike page, and the librarian's three books may be the wrong three.

Where it breaks down: a student can notice that they are lost and say so, and can re-read selectively. A model reads the prompt in one pass and gives no reliable signal that its attention has thinned.

What retrieval gets wrong

Retrieval fails in a different way: it can leave the answer out of the prompt, and the model, having never seen the missing fact, either says it does not know or, worse, answers from what it did see. The useful quantity is evidence recall: for what share of questions did the context you built contain everything needed? If it is not in the prompt, no model quality fixes it. Three question types break single-shot retrieval predictably.

  1. Multi-hop questions. "What is the refund window at the branch managed by Priya Nair?" The name lives in a staff directory; the refund window lives in a different document about a branch the question never names. A search on the question finds the directory but not the policy page.
  2. Aggregation. "How many branches in the North region offer Sunday delivery?" The answer depends on a dozen documents, and top-k retrieval returns three or eight. The model counts what it was shown, and the count is wrong, not absent, which is the dangerous case.
  3. Vocabulary gaps. The user writes "money back" and the policy says "refund window". Lexical search misses it; dense retrieval often catches it; neither is perfect.

Retrieval also has a design cost that stuffing avoids entirely: chunk size, ranking, reranking, index freshness and evaluation are all yours (chunking, rerankers). Each is a place for a subtle bug, and each needs its own measurements.

Measuring the difference on your own questions

Rules of thumb stop at the edges of your data. The reliable method is a small comparison: write the questions you expect, with known answers; run every strategy on them; and report accuracy with an honest error bar, plus tokens. This is a miniature of the evaluation habits in course A6.

The test corpus below is synthetic and deliberately cross-referenced: 50 branch policy documents (one per branch) and 5 regional staff directories, 55 documents and about 5,000 tokens in all. The corpus builder and a small BM25-style retriever are in the optional box; the harness itself is the listing after it. The "model" is a stand-in reader built on ScriptedModel: it parses facts from the prompt and answers from them, and says "I don't know" when a fact is absent. That makes it an ideal reader. It cannot be distracted or lose the middle of a long prompt, so this experiment isolates one thing, whether the right evidence reached the context. Attention failures need a real model (set LAB_MODEL).

import math, random, re
from collections import Counter
from llm import count_tokens

CITIES = ("Leeds Bristol Derby Exeter Hull York Bath Ely Wells Truro Perth Stirling Cardiff Swansea Newport Bangor "
          "Lincoln Oxford Reading Slough Luton Dover Poole Crewe Stoke Wigan Bolton Oldham Preston Carlisle Durham "
          "Ripon Whitby Buxton Chester Warwick Lichfield Worcester Hereford Gloucester Salisbury Taunton Plymouth "
          "Falmouth Penzance Norwich Ipswich Colchester Chelmsford Cambridge").split()
FIRST = "Priya Tom Aisha Liam Mei Omar Grace Jon Sara Ravi Elena Dev Nora Kofi Hana Ben Zara Luis Ines Paul".split()
LAST = "Nair Hughes Khan Moore Chen Farouk Bell Reid Ali Patel Rossi Shah Cole Owusu Sato Fox Malik Diaz Costa Webb".split()
REGIONS = ["North", "South", "East", "West", "Central"]
FILLER = ["Parcels are held for {d} days before they are returned to the depot.",
          "The {c} depot opens at {h}:00 and closes at {h2}:00 on weekdays.",
          "Damaged goods must be reported within {d} days of delivery.",
          "Staff at {c} complete safety training every {d} months.",
          "Gift cards bought at {c} cannot be refunded to a card."]

def build(seed=7):
    rnd = random.Random(seed)
    people = rnd.sample([f"{f} {l}" for f in FIRST for l in LAST], len(CITIES))
    branches = []
    for i, city in enumerate(CITIES):
        branches.append({"city": city, "region": REGIONS[i % 5], "mgr": people[i],
                         "refund": rnd.choice([14, 28, 30, 45, 60]), "sunday": rnd.random() < 0.4})
    docs = []
    for b in branches:                                     # one policy document per branch
        s = [f"Branch policy: {b['city']}.", f"{b['city']} is in the {b['region']} region.",
             f"At {b['city']}, the refund window is {b['refund']} days.",
             f"{b['city']} " + ("offers" if b["sunday"] else "does not offer") + " Sunday delivery."]
        for t in rnd.sample(FILLER, 4):
            s.append(t.format(c=b["city"], d=rnd.choice([3, 5, 7, 10]), h=rnd.choice([7, 8, 9]), h2=rnd.choice([17, 18, 19])))
        docs.append({"id": "policy-" + b["city"].lower(), "text": " ".join(s)})
    for r in REGIONS:                                      # one staff directory per region
        s = [f"Staff directory: {r} region."] + [f"{b['mgr']} manages the {b['city']} branch."
                                                 for b in branches if b["region"] == r]
        docs.append({"id": "directory-" + r.lower(), "text": " ".join(s)})
    return branches, docs

def words(t): return re.findall(r"[a-z0-9]+", t.lower())

class Index:                                               # BM25-style scoring over whole documents
    def __init__(self, docs):
        self.docs, self.tf = docs, [Counter(words(d["text"])) for d in docs]
        self.n, self.avg = len(docs), sum(sum(c.values()) for c in self.tf) / len(docs)
        self.df = Counter(w for c in self.tf for w in c)
    def search(self, query, k):
        scores = []
        for d, c in zip(self.docs, self.tf):
            L, s = sum(c.values()), 0.0
            for w in set(words(query)):
                if c[w]:
                    idf = math.log(1 + (self.n - self.df[w] + .5) / (self.df[w] + .5))
                    s += idf * c[w] * 2.2 / (c[w] + 1.2 * (0.25 + 0.75 * L / self.avg))
            scores.append((s, d["id"], d))
        scores.sort(key=lambda x: (-x[0], x[1]))
        return [d for s, _, d in scores[:k]]

# harness.py: the same questions answered with different context strategies; a stand-in reader
import math, random, re
from llm import ScriptedModel, text_of
from corpus import build, Index

def reader(messages, tools, system):
    """Stand-in model: reads ONLY what is in the prompt (an honest oracle: no guessing)."""
    p = messages[-1]["content"]; q = p.split("Question:")[-1].strip(); ctx = p.split("Question:")[0]
    refund = dict((c, int(n)) for c, n in re.findall(r"At (\w+), the refund window is (\d+) days", ctx))
    mgr = dict((m, c) for m, c in re.findall(r"([A-Z]\w+ [A-Z]\w+) manages the (\w+) branch", ctx))
    region = dict(re.findall(r"(\w+) is in the (\w+) region", ctx))
    sunday = {c: o == "offers" for c, o in re.findall(r"(\w+) (offers|does not offer) Sunday delivery", ctx)}
    m = re.search(r"managed by ([A-Z]\w+ [A-Z]\w+)", q)
    if m: city = mgr.get(m.group(1)); return f"{refund[city]} days" if city in refund else "I don't know"
    m = re.search(r"refund window at (\w+)", q)
    if m: return f"{refund[m.group(1)]} days" if m.group(1) in refund else "I don't know"
    m = re.search(r"How many branches in the (\w+) region offer Sunday", q)
    if m: return str(sum(1 for c, r in region.items() if r == m.group(1) and sunday.get(c)))
    return "I don't know"

def make_questions(branches, rnd):
    q = []
    for b in rnd.sample(branches, 8):
        q.append(("lookup", f"What is the refund window at {b['city']}?", f"{b['refund']} days"))
    for b in rnd.sample(branches, 8):
        q.append(("multi-hop", f"What is the refund window at the branch managed by {b['mgr']}?", f"{b['refund']} days"))
    for r in (["North", "South", "East", "West", "Central"] * 2)[:8]:
        n = sum(1 for b in branches if b["region"] == r and b["sunday"])
        q.append(("count", f"How many branches in the {r} region offer Sunday delivery?", str(n)))
    return q

def prompt(docs, question):
    return "Documents:\n" + "\n".join(f"[{d['id']}] {d['text']}" for d in docs) + f"\nQuestion: {question}"

def stuff(ix, question, model):    return prompt(ix.docs, question)
def rag(k):
    def run(ix, question, model): return prompt(ix.search(question, k), question)
    return run
def agentic(k):                    # retrieve, read the result, then search again with what was learnt
    def run(ix, question, model):
        hits = ix.search(question, k)
        m = re.search(r"managed by ([A-Z]\w+ [A-Z]\w+)", question)
        extra = ""
        if m:
            for d in hits:
                f = re.search(re.escape(m.group(1)) + r" manages the (\w+) branch", d["text"])
                if f: extra = f.group(1)
        seen = {d["id"] for d in hits}
        hits += [d for d in ix.search(question + " " + extra, k) if extra and d["id"] not in seen]
        return prompt(hits, question)
    return run

def wilson(c, n, z=1.96):
    p = c / n; d = 1 + z * z / n; mid = (p + z * z / (2 * n)) / d
    h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return mid - h, mid + h

if __name__ == "__main__":
    branches, docs = build(); ix = Index(docs); qs = make_questions(branches, random.Random(1))
    print(f"{len(qs)} questions over {len(docs)} documents\n")
    print(f"{'strategy':<14}{'lookup':>8}{'multi-hop':>11}{'count':>7}{'all (95% CI)':>22}{'avg input tok':>15}")

        model, right, toks = ScriptedModel(reader), {"lookup": 0, "multi-hop": 0, "count": 0}, 0
        for kind, q, gold in qs:
            r = model.complete([{"role": "user", "content": strat(ix, q, model)}])
            right[kind] += text_of(r) == gold; toks += r.usage["input_tokens"]
        n = len(qs); c = sum(right.values()); lo, hi = wilson(c, n)

Read the table row by row. Stuffing is perfect and costs 5,491 input tokens a question, about 17 times more than retrieving three documents (326). Retrieval gets every simple lookup right and every multi-hop and counting question wrong. Raising k from 3 to 8 helps nothing here: the missing document is not in the top eight, and the count needs about ten. Agentic retrieval, a loop that reads the first results, learns the branch name and searches again (the idea behind the loops of chapter 2), repairs multi-hop for a few hundred extra tokens but still cannot count across a dozen documents.

Two cautions about reading a table like this. First, the interval: 24 questions is small. The overall score of 67% for the agentic row comes with a 95% Wilson interval of 47% to 82%, wide enough that on a real model a gap of a few points between two strategies would mean nothing (A6 chapter 4). Second, the stand-in is kind to stuffing. On a real model, stuffing's 100% is the number most likely to move, and by how much depends on length, position and lookalike content. That is why the harness is pluggable: the same questions through get_model() give you the real line.

A decision guide and the hybrids that usually win

Put the measurements next to the engineering facts and a pattern emerges. Neither approach dominates; the data decides.

FactorFavours stuffingFavours retrieval
Corpus sizeFits in the window with room for history and answerLarger than the window, or most of it
Question shapeWhole-corpus views: summarise, compare, count, find contradictionsPoint lookups: one fact in one or two places
Update rateStatic, so a cached prefix stays validChanges constantly; re-indexing a chunk is cheaper than re-sending everything
Queries per dayFew (build cost matters more), or many against one cached prefixMany, with differing content
Access controlEveryone may see everything in the promptDifferent users may see different documents; filter before the model sees anything
CitationsModel can quote, but must be verifiedChunk ids give provenance by construction
Engineering effortLow: no index to build or tuneHigher: chunking, ranking, freshness, evaluation

Hybrids

Most production systems sit between the two lanes, and the research points the same way.

  • Route per query. Li et al., 2024 ("Retrieval Augmented Generation or Long-Context LLMs? A Comprehensive Study and Hybrid Approach", EMNLP 2024 industry track) found that with enough resources long-context models outperformed RAG on average, while RAG was much cheaper. Their Self-Route method sends each query to RAG first and falls back to the long context only when the model judges the retrieved chunks insufficient, keeping most of the quality at lower cost. The paper's full text has the numbers; the abstract does not give them.
  • Retrieve documents, read whole documents. Use the index to choose which three contracts matter, then put those contracts in full into the prompt rather than 400-token fragments. You get provenance and permissions from the index and coherence from the long read.
  • Subsume only where it is measured. Lee et al., 2024 (the LOFT benchmark, "Can Long-Context Language Models Subsume Retrieval, RAG, SQL, and More?") reported that long-context models rival specialised retrieval and RAG pipelines on several tasks without being trained for them, yet still struggle with compositional, SQL-like reasoning, and that prompting strategy mattered a great deal.
  • Small corpora can skip the index. Anthropic's September 2024 "Contextual Retrieval" post advised that a knowledge base under about 200,000 tokens (roughly 500 pages) can be included whole in the prompt, with prompt caching making that faster and cheaper. The same post reported that for retrieval, adding context to each chunk cut failed retrievals by 35%, and by 49% when combined with BM25 and 67% with reranking, on its own evaluation set (baseline failure rate 5.7% for the top 20 chunks).

The constraints that are not about accuracy

Some reasons to retrieve survive any improvement in long-context models, because they are properties of the system rather than the model.

Permissions. A prompt is a flat bag of text. If it contains a document, the model can repeat it. A shared corpus stuffed into every request gives every user the union of what anyone may read. Retrieval lets you filter by the caller's rights before any text reaches the model.

Provenance. An answer that cites chunk 4,311 of a named source can be checked by a person or a program. A model asked to "quote where you found that" from a quarter-million tokens may produce a plausible quotation that does not exist; the citation must be verified against the source either way.

Untrusted text. Every document in the window is text the model might obey. Stuffing a thousand documents multiplies the places an injected instruction can hide, and a single poisoned page can steer an answer it has nothing to do with (chapter 19). Retrieval narrows exposure but does not remove it.

Freshness and cost of change. Updating one chunk in an index is cheap. Updating a cached prefix invalidates the cache for everyone, and the next requests pay the write price again.

Systems connection

Prompt caching is the oldest idea in systems applied to a new place: keep the expensive, repeated part close, and expect the usual cache questions about hit rate, expiry and invalidation. Filtering by caller before the model sees data is authorisation done at the data layer rather than hoped for in the prompt (multi-tenancy). And the cost model above is a back-of-envelope estimate in the sense of design chapter 2: write the assumptions down, compute, then check against the invoice.

Agents change the arithmetic

Everything above priced one request. An agent makes many. In the loop from chapter 2 every iteration re-sends the whole conversation, so a 150,000-token stuffed corpus carried through a 20-call task is about 3 million input tokens before any tool result is counted, and the chapter-2 budget widget showed how fast history alone grows. Caching softens this but does not make the corpus free, and every added token is still context the model must not be distracted by.

This is why agent designs lean towards just-in-time retrieval: keep lightweight references (file paths, ids, queries) in context and load the content when the model asks for it with a search or read tool. It trades the one big prefill for several small, targeted ones, and it lets the model do its own multi-hop by searching again, the very case single-shot RAG failed above. Chapter 10 covers selection and compaction; chapter 11 covers what to keep between sessions. Long windows still earn their place in agents: a coding agent may reasonably read one large file whole, and a research agent may hold a long report while it checks one claim against it. The skill is deciding what deserves residence in the window and what should stay one tool call away.

Key takeaways

  • Stuffing pays for the whole corpus on every request; retrieval pays for a small slice. Prompt caching narrows the gap for large, stable, frequently reused prefixes but needs warm traffic and identical text.
  • A window being large is not evidence of being used well. Position, distractors and paraphrase degrade recall; the easy needle test saturates while RULER, NoLiMa and context-rot style tests do not.
  • Retrieval fails by omission: multi-hop and aggregation questions need evidence that top-k search does not return, and a partial context can yield a confident wrong count.
  • Measure on your own questions: a small set per question type, accuracy with an interval, tokens per answer, and a pluggable reader so the same harness can test a real model.
  • Permissions, provenance, injection exposure and update cost can decide the question regardless of accuracy.
  • Hybrids (route per query, retrieve then read whole documents, agentic retrieval) usually beat either pure lane. In agent loops, prefer references in context and content on demand.

Check your understanding

A support bot answers from a fixed 150,000-token handbook and handles thousands of questions an hour. Under a cost model like the chapter's, which change reduces the bill most without changing any answer?

  1. Moving the handbook from the start of the prompt to the end
  2. Asking the model to answer in fewer words
  3. Keeping the handbook as an identical, cached prefix so most requests read it at a fraction of the normal input price
  4. Splitting the handbook across several requests per question
The input side dominates: 150,000 tokens per question. A warm prompt cache reads an identical prefix at about a tenth of the price (assuming steady traffic). Shortening the answer changes only the small output side. Moving the handbook does not change the number of input tokens and could even break the cache. Splitting across several requests multiplies calls.

A vendor reports a model scored 100% on needle-in-a-haystack at its full window. What can you conclude?

  1. It will answer questions that need facts from several distant places just as reliably
  2. It can retrieve one literal string that stands out from unrelated filler; harder abilities remain untested
  3. Retrieval systems are unnecessary for corpora up to that size
  4. Position in the prompt no longer affects its accuracy
The test checks one easy behaviour. RULER and NoLiMa found models that pass it still degrade on multi-hop, aggregation and low-overlap questions as length grows. The other options each extrapolate far beyond what the test measures.

In the chapter's harness, "rag k=8" scores 0 of 8 on the counting questions while still answering the lookups. Why is raising k not a fix?

  1. The BM25 scorer is broken for numbers
  2. The reader model cannot count above three
  3. Retrieval always returns the same documents regardless of k
  4. Each count needs about ten policy documents, so eight retrieved documents give the reader partial evidence and a wrong total
The reader counts what it is shown, and the evidence is incomplete, so it returns a confident wrong number. The reader is not the limitation, since it counts correctly when all documents are present (the stuffing row). k does change results, but 8 is still short of the roughly ten to twelve documents each region needs.

A company's contracts all fit in a 600,000-token window, but each employee may read only their own department's contracts. Which design best fits?

  1. Retrieve with a department filter applied before the model sees any text, then read the permitted documents
  2. Stuff every contract and instruct the model not to reveal other departments' contracts
  3. Stuff every contract but cache the prefix so it is cheaper
  4. Give each employee a separate fine-tuned model
A prompt instruction is not an access control: injected text or a clumsy question can make the model repeat what it holds. Filtering before the model sees data enforces the rule in code. Caching helps cost, not permission. Fine-tuning per employee is heavy and does not give reliable separation either.

You compare two strategies on 24 questions and get 92% against 100%. What is the most defensible next step?

  1. Adopt the 100% strategy; the gap is eight points
  2. Adopt the 92% strategy because it is cheaper
  3. Compute an interval, expect it to be wide at n = 24, and add more questions (or compare per-question outcomes) before concluding
  4. Remove the two failing questions as unrepresentative
With 24 items, one or two questions swing the score by four to eight points; intervals for the two strategies overlap heavily. Dropping failing questions biases the test. Cost may well decide in the end, but only once you know the quality difference is real or negligible.

A coding agent carries a stuffed 150,000-token corpus through 20 model calls with no caching. Roughly how many input tokens does the corpus alone cost across the task?

  1. 150,000, because the corpus is sent once
  2. About 3 million, because each of the 20 calls re-sends it
  3. About 300,000, because only the first and last calls include it
  4. About 30 million, because each call sends it twice
A model call is stateless, so every request carries the whole prompt: 20 times 150,000 is 3,000,000. This repeated sending is why agents favour references and just-in-time retrieval, and why caching matters so much in loops.

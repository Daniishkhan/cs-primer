MCP in Production

A server that works on your laptop over a pipe is not yet a service. This chapter takes MCP onto the network: how remote transports behave behind a load balancer, why the protocol was redesigned to be stateless, how authorisation works with OAuth, and how to build clients and servers that survive the next specification change.

Why this matters

The previous chapter ended with a local server that answered a client over stdin and stdout. Real deployments differ in three ways. The server runs on several machines behind a balancer, so anything it remembers in memory is sometimes missing. It serves users who must prove who they are, and a tool call may spend their money or touch their data. And the protocol itself keeps changing: the revision dated 2026-07-28 removed the handshake that chapter 7 taught. If you only know the demo, each of these arrives as a production incident. After this chapter you can read an MCP gateway log, explain why a request was rejected with 401, 403 or 400, design a server that scales horizontally, and keep an integration working across protocol revisions. Lab 3 exercises the message layer; Case 4 tells the longer history.

What changes when the server is remote

A stdio server is a child process of one client: nothing to scale, nothing to authenticate (the user's own account launched it), no network between the two. A remote server inverts all of that. It is a long-running service that many clients and users reach over HTTP through load balancers, so requests arrive on any replica, connections break and a request may be an attack. The transport is Streamable HTTP, introduced in the 2025-03-26 revision to replace the older HTTP+SSE transport. In every revision it has the same outline: one HTTP endpoint, each JSON-RPC message sent as a POST, and a reply that is either a single JSON object or a Server-Sent Events (SSE) stream, a long-lived HTTP response that delivers a sequence of text events.

What changed is how much the server must remember between two requests. That one question explains most of the protocol's recent history.

Why sessions hurt: the 2025 design

In revisions up to 2025-11-25, a connection began with the initialize handshake you built in chapter 7. On HTTP, a server could also hand out a session identifier in an Mcp-Session-Id header, and the client then sent it on every later request. A client could open a second long-lived connection with a GET request to receive messages the server wanted to push, and a server could send its own JSON-RPC requests (to ask the user a question, or to ask the client's model for a completion) down an SSE stream. Interrupted streams could be resumed with the standard Last-Event-ID header.

Each of those features needs the server to remember something: which sessions exist, which capabilities each one negotiated, which stream belongs to which client, which events were already delivered. With one process that is a dictionary. With three replicas, the dictionary lives in one of them. The next request, routed by a balancer that knows nothing about MCP, may land on a replica that has never heard of the session. The simulation below uses three replicas and four clients, each sending an initialize followed by three calls.

import itertools

class LegacyReplica:                      # keeps the session in this process's memory
    def __init__(self): self.sessions = set()
    def call(self, sid, method):
        if method == "initialize":
            self.sessions.add(sid); return "ok"
        return "ok" if sid in self.sessions else "400 unknown session"

class ModernReplica:                      # everything arrives in the request itself
    def call(self, sid, method):
        return "ok"

def run(replicas, sticky):
    rr = itertools.cycle(range(len(replicas)))
    pick = {}                              # sticky: remember which replica each client landed on
    failures = 0
    for sid in ["c1", "c2", "c3", "c4"]:
        for method in ["initialize", "tools/list", "tools/call", "tools/call"]:
            i = pick.setdefault(sid, next(rr)) if sticky else next(rr)
            if replicas[i].call(sid, method) != "ok":
                failures += 1
    return failures

print("legacy, round-robin :", run([LegacyReplica() for _ in range(3)], sticky=False), "of 16 requests failed")
print("legacy, sticky      :", run([LegacyReplica() for _ in range(3)], sticky=True), "of 16 requests failed")
print("modern, round-robin :", run([ModernReplica() for _ in range(3)], sticky=False), "of 16 requests failed")
legacy, round-robin : 8 of 16 requests failed
legacy, sticky      : 0 of 16 requests failed
modern, round-robin : 0 of 16 requests failed

Half of the requests fail under round-robin routing, because three requests in four reach a replica that holds no session for that client. There are two standard remedies, and both cost something. Sticky routing pins each client to one replica: it works, but a deployment, a crash or a scale-down destroys the sessions on that replica, and the balancer must now understand MCP. Shared session storage (a database or cache every replica reads) works and survives restarts, but it adds a dependency on the hot path of every request and is a new thing to secure and keep consistent (caching has the failure modes). Neither is wrong; both are infrastructure that a tool server written to look up an order should not need.

The reasoning of the MCP maintainers, as the specification now states it, is that a protocol-level session is the wrong place for this state. The statelessness section of the base protocol says all information needed to process a request must be in the request itself, that a server must not rely on earlier requests on the same connection, and that an open connection such as a stdio process is not a conversation. If a server genuinely needs to remember something across calls (a shopping basket, say), that state must be "referenced by an explicit identifier the client passes on each request". The model receives the identifier from one tool and passes it as an argument to the next, which is exactly how it already handles an order id.

Everything a request needs

Here is the heart of the change in code. The server below is a pure function from one HTTP request to one reply, and it keeps nothing between calls. The checks are the ones the specification requires of a Streamable HTTP server: validate the Origin header (a defence against a web page in the user's browser talking to a local server, see the browser security model), require the _meta fields, refuse versions it does not speak, and refuse requests whose headers disagree with their bodies.

import json

VERSIONS = ["2026-07-28"]
ALLOWED_ORIGINS = {"https://app.example.com"}
TOOLS = [{"name": "orders_lookup", "description": "Look up one order by id.",
          "inputSchema": {"type": "object", "properties": {"order_id": {"type": "string"}},
                          "required": ["order_id"]}}]
ORDERS = {"A-100": {"item": "kettle", "cents": 4200}, "A-101": {"item": "toaster", "cents": 3100}}

def err(status, code, message, mid=None, data=None):
    e = {"code": code, "message": message, **({"data": data} if data else {})}
    return status, {"jsonrpc": "2.0", "id": mid, "error": e}

def handle(headers, body):
    """One HTTP POST in, (status, JSON-RPC reply) out. No state survives between calls."""
    h = {k.lower(): v for k, v in headers.items()}
    if "origin" in h and h["origin"] not in ALLOWED_ORIGINS:
        return err(403, -32600, "Origin not allowed")
    try:
        msg = json.loads(body)
    except ValueError:
        return err(400, -32700, "Parse error")
    mid, method, params = msg.get("id"), msg.get("method"), msg.get("params") or {}
    meta = params.get("_meta", {})
    version = meta.get("io.modelcontextprotocol/protocolVersion")
    if version is None or "io.modelcontextprotocol/clientCapabilities" not in meta:
        return err(400, -32602, "Missing required _meta fields", mid)
    if version not in VERSIONS:
        return err(400, -32022, "Unsupported protocol version", mid,
                   {"supported": VERSIONS, "requested": version})
    for header, want in (("mcp-protocol-version", version), ("mcp-method", method),
                         ("mcp-name", params.get("name") if method == "tools/call" else None)):
        if want is not None and h.get(header) != want:
            return err(400, -32020, f"Header mismatch: {header}", mid)
    info = {"io.modelcontextprotocol/serverInfo": {"name": "orders", "version": "1.0.0"}}
    if method == "server/discover":
        result = {"supportedVersions": VERSIONS, "capabilities": {"tools": {}}, "ttlMs": 3600000, "cacheScope": "public"}
    elif method == "tools/list":
        result = {"tools": sorted(TOOLS, key=lambda t: t["name"]), "ttlMs": 60000, "cacheScope": "public"}
    elif method == "tools/call" and params.get("name") == "orders_lookup":
        order = ORDERS.get(params.get("arguments", {}).get("order_id"))
        text = json.dumps(order) if order else "No such order. Ids look like A-100."
        result = {"content": [{"type": "text", "text": text}], "isError": order is None}
    else:
        return err(404, -32601, "Method not found", mid)
    return 200, {"jsonrpc": "2.0", "id": mid, "result": {"resultType": "complete", **result, "_meta": info}}

Why must the headers match the body at all? The headers exist so that a gateway can route, rate-limit or log by method and tool name without parsing JSON. If a gateway allowed a request labelled orders_lookup through while the body actually called refund_order, the gateway's policy would be meaningless. So any server that reads the body must reject a mismatch, and intermediaries that enforce policy from the headers should refuse versions old enough that nobody validates them. Run the server through seven requests, including the failures:

Read the failures as a gateway operator would. A status of 400 with -32020 means a client or an intermediary rewrote one side of the message. 400 with -32022 carries the list of versions the server will accept, so a client can retry; this replaces the negotiation that used to happen once at the start. 403 on a bad Origin is the DNS-rebinding defence. Note also that the unknown order id is a successful response with isError set: it is the model's mistake to read and fix, as in chapter 7, not a protocol failure.

Analogy: the order slip

A stateful server is a barista who remembers that you take oat milk. It is pleasant until your usual barista is off and the new one has never met you. A stateless server is the order slip: it says "large, oat milk, name Sam", so any barista on the shift can make the drink. The slip does the remembering.

Where it breaks down: a paper slip is trusted because you wrote it in front of the barista. A request that travels through a client is not: anything the server hands out to be echoed back can be altered on the way. The next section shows what that requires, and why moving state into the request does not make it disappear. It moves the work to making the state safe to carry.

Asking the user a question without a session

The most interesting casualty of statelessness is the server-initiated request. A refund tool might want to ask "Refund 4,200 cents on A-100?" before it acts. In the old design the server sent an elicitation/create request down an open stream and waited, holding the pending tool call in memory. Whichever replica held that call had to receive the answer.

The new pattern is called multi round-trip requests. The server does not wait. It ends the request with a result whose resultType is input_required, carrying inputRequests (what it needs, keyed by names it chooses) and an opaque string requestState. The client gathers the answers and sends the original request again, with a new id, adding inputResponses and echoing requestState byte for byte. Each of the two requests is complete in itself, so they can even reach different replicas. Only tools/call, prompts/get and resources/read may return input_required.

The catch is the one the analogy hinted at. requestState passes through the client, so the specification tells servers to treat it as attacker-controlled input: if it influences authorisation, resources or business logic, protect its integrity with an HMAC or authenticated encryption, and reject anything that fails verification. To limit replay, it should also contain the authenticated principal, a short expiry and a digest of the request. Here is a refund server that does exactly that, with two "replicas" that share only a signing key, followed by five ways to misuse the state.

import base64, hashlib, hmac, json

SECRET = b"shared-signing-key"          # the ONLY thing the server instances share

def sign(payload):
    raw = json.dumps(payload, sort_keys=True).encode()
    mac = hmac.new(SECRET, raw, hashlib.sha256).digest()
    return base64.urlsafe_b64encode(raw + mac).decode()

def verify(token, principal, now, digest):
    blob = base64.urlsafe_b64decode(token.encode())
    raw, mac = blob[:-32], blob[-32:]
    if not hmac.compare_digest(mac, hmac.new(SECRET, raw, hashlib.sha256).digest()):
        raise ValueError("bad signature")
    p = json.loads(raw)
    if p["sub"] != principal: raise ValueError("different principal")
    if p["exp"] < now:        raise ValueError("expired")
    if p["args"] != digest:   raise ValueError("different arguments")
    return p

class Server:
    """A stateless instance: no dict of pending refunds, nothing to share between replicas."""
    def __init__(self, name): self.name = name
    def refund(self, principal, args, now, input_responses=None, request_state=None):
        digest = hashlib.sha256(json.dumps(args, sort_keys=True).encode()).hexdigest()[:12]
        if request_state is None:
            state = sign({"sub": principal, "exp": now + 300, "args": digest})
            ask = {"confirm": {"method": "elicitation/create", "params": {
                "message": f"Refund {args['cents']} cents on {args['order_id']}?",
                "requestedSchema": {"type": "object", "properties": {"ok": {"type": "boolean"}}}}}}
            return {"resultType": "input_required", "inputRequests": ask, "requestState": state}
        verify(request_state, principal, now, digest)
        if not input_responses["confirm"]["content"]["ok"]:
            return {"resultType": "complete", "content": "Cancelled by user.", "isError": False}
        return {"resultType": "complete", "content": f"Refunded {args['cents']} on {args['order_id']} (served by {self.name})", "isError": False}

Case 2 is the point of the design: a different replica completes the refund. Cases 3 to 6 are the reasons for each field in the signed payload. The specification adds a warning worth repeating: these checks bound replay and block cross-user reuse, but they do not make the state single-use. A one-time redemption, such as a refund that must happen at most once, needs a server-side record keyed by an idempotency key, exactly as in failure, timeouts and retries. That matters twice here, because a client whose response stream breaks must re-issue the request with a new id; the server cannot tell a retry from a fresh call unless you give it something to compare.

Common misconception

"Stateless MCP means servers cannot keep state, so stateful tools such as a shopping basket or a database transaction are gone." The protocol dropped protocol-level state, not application state. A tool can create a basket and return a basket_id; later tools take it as an argument, and the server looks it up in its own database. The state is now explicit, visible in the transcript, durable across restarts and shareable across replicas, which is better engineering than a session that silently vanished when a pod was rescheduled. What you give up is the convenience of implicit context.

Other changes worth knowing

  • Change notifications. A client that wants "tools changed" or "resource updated" messages sends subscriptions/listen naming the types it wants; the response is an SSE stream that stays open. Servers should send X-Accel-Buffering: no so proxies such as nginx do not buffer the events.
  • Caching. List and read results carry ttlMs and cacheScope (public or private), modelled on HTTP caching. Servers should also return tools in a deterministic order. The tool list is part of the model's prompt, so a reordered or edited list changes the start of every prompt and invalidates the provider's prompt cache (chapter 10): release tool changes deliberately, in batches.
  • Long-running work and extensions. The experimental tasks feature moved out of the core into an official extension (io.modelcontextprotocol/tasks), polled with tasks/get. Code written against the experimental version had to be migrated, a fair warning about adopting experimental features. Extensions have a formal route now: reverse-DNS identifiers in an extensions map, versioned independently.
  • Deprecations. Roots, sampling and logging are deprecated but still work; the specification suggests tool parameters or resource URIs, direct calls to model providers, and stderr or OpenTelemetry respectively. Dynamic Client Registration (below) and the old HTTP+SSE transport are deprecated too. A new lifecycle policy requires at least twelve months between deprecation and removal.
  • Tracing. The _meta keys traceparent, tracestate and baggage carry W3C trace context, so one user request can be followed through the host, the MCP server and the systems behind it (distributed tracing).

State of play, October 2026

The 2026-07-28 revision is published and breaking: it removes the handshake and sessions, so a client written only for 2025-11-25 cannot talk to a server that implements only the new revision, and the reverse. The specification gives a compatibility matrix: dual-era clients work with both kinds of server, and a dual-era server can answer both kinds of client on the same endpoint. I did not survey which hosts, SDKs and public servers have moved; assume a mixed fleet for some time, and check the SDK tier and release notes of whatever you depend on. The deprecation window (twelve months at minimum) means sampling, roots and logging should keep working through 2027, but new code should not rely on them. Details here are from the 2026-07-28 changelog; if you read this later, check what has been added since.

Authorisation: who is allowed to call this?

Over stdio the question hardly arises, since the user launched the process, and the specification says stdio servers should take credentials from the environment instead. Over HTTP, anyone who can reach the URL can send a request, so the server must establish who is calling and what they may do. MCP does not invent a scheme. It profiles OAuth 2.1, the consolidated version of the OAuth framework covered in OAuth 2.0 and OpenID Connect, and assigns the roles as follows. The MCP server is an OAuth resource server: it accepts and validates access tokens and does not issue them. The MCP client is an OAuth client acting for a user. A separate authorisation server authenticates the user, obtains consent and issues tokens. It may run alongside the MCP server or be an entirely different company's identity provider.

The reason for this split is that a client cannot know in advance which identity provider protects an arbitrary MCP server. So the protocol makes it discoverable. Step through the full flow for a client meeting a protected server for the first time.

Step through

First contact with a protected MCP server

  1. An anonymous request. The client has only a URL. It sends an ordinary MCP request, with no credentials, to find out what the server wants.
  2. The challenge. The server answers 401 and adds a WWW-Authenticate: Bearer header carrying resource_metadata (a URL) and, ideally, the scope needed. This is plain HTTP authentication (HTTP) with one extra pointer.
  3. Resource metadata. The client fetches that document, defined by RFC 9728. Every MCP server must provide it, and it names the authorisation server or servers that can issue tokens for this resource.
  4. Authorisation server metadata. The client reads the authorisation server's description of itself (RFC 8414 or OpenID Connect discovery): its endpoints, its issuer identifier and what it supports. The client records the issuer now, from this validated document.
  5. The authorisation request. The client opens a browser for the user. It includes a PKCE challenge (a hash of a secret only this client knows, so a stolen code is useless to anyone else), the resource parameter naming the MCP server, and the scope. The user signs in and consents. The redirect carries a code and, ideally, an iss parameter, which the client compares with the issuer it recorded in step 4 before using the code.
  6. The token. The client exchanges the code, proving possession with the PKCE verifier and repeating the resource parameter. The token it receives is bound to that resource as its audience.
  7. An authorised call. From now on every HTTP request carries Authorization: Bearer, never in the query string. The server must verify that the token was issued for it, is unexpired and carries enough scope.
  8. Step-up. When a call needs a scope the token lacks, the server answers 403 with error="insufficient_scope" and the scope required. The client requests a token with the union of old and new scopes, retrying only a few times so a permanent refusal does not loop.

The checks a server makes on every request

The flow is fiddly, but what a resource server does is short and worth writing down. The sketch below uses a keyed hash in place of a real signed token and has no network, so it can run anywhere. In a real server you would verify a JWT's signature against the authorisation server's published keys, or call its introspection endpoint (sessions, cookies and tokens has the pitfalls).

import base64, hashlib, hmac, json

AS_KEY = b"authorization-server-key"           # in real life: a public key fetched from the AS's JWKS
RESOURCE = "https://mcp.example.com"           # this server's canonical URI
METADATA_URL = RESOURCE + "/.well-known/oauth-protected-resource"

def issue(aud, scopes, exp, sub="alice"):       # what the authorization server does
    body = json.dumps({"iss": "https://auth.example.com", "aud": aud, "scope": " ".join(scopes),
                       "exp": exp, "sub": sub}).encode()
    return base64.urlsafe_b64encode(body).decode() + "." + hmac.new(AS_KEY, body, hashlib.sha256).hexdigest()

def check(authorization, needs, now):           # what the MCP server does on EVERY request
    if not authorization or not authorization.startswith("Bearer "):
        return 401, f'Bearer resource_metadata="{METADATA_URL}", scope="{needs}"'
    b64, mac = authorization[7:].rsplit(".", 1)
    body = base64.urlsafe_b64decode(b64)
    if not hmac.compare_digest(mac, hmac.new(AS_KEY, body, hashlib.sha256).hexdigest()):
        return 401, f'Bearer error="invalid_token", resource_metadata="{METADATA_URL}"'
    claims = json.loads(body)
    if claims["exp"] < now or claims["aud"] != RESOURCE:       # audience binding: the token must be FOR us
        return 401, f'Bearer error="invalid_token", resource_metadata="{METADATA_URL}"'
    if needs not in claims["scope"].split():
        return 403, f'Bearer error="insufficient_scope", scope="{needs}", resource_metadata="{METADATA_URL}"'
    return 200, f'ok, acting for {claims["sub"]}'

The second row is the important one. A token minted for a billing API is a perfectly good token, signed by the right authorisation server, and the MCP server must still refuse it. The specification says a server must accept only tokens issued for itself and must not accept or pass on any others. If it forwarded the caller's token to a downstream API ("token passthrough"), the downstream service would believe the user had approved that exact call, and the MCP server would become a confused deputy: a component that uses its own authority on behalf of someone who lacks it (authorisation covers the pattern). If the MCP server needs to call another API, it should obtain a separate token for that API.

The rest of the authorisation requirements bind every token to a purpose:

  • Resource indicators. The client sends the resource parameter in both the authorisation and the token request, naming the MCP server by its canonical URI (https://mcp.example.com), whether or not the authorisation server supports it.
  • Issuer checks. The client records the issuer from validated metadata and compares the iss in the authorisation response before redeeming the code. This defeats mix-up attacks, where a malicious authorisation server tricks a client into sending a code to the wrong place.
  • Client registration. A client gets its id from a client ID metadata document (the client uses an HTTPS URL as its id, and the authorisation server fetches a JSON description from it), from pre-registration, or from Dynamic Client Registration, which is deprecated. The first avoids manual registration and an unbounded registry of anonymous clients.
  • Scopes. Ask for what the current operation needs. The challenge's scope is authoritative; the rest comes through step-up.

Systems connection

Nothing in this section is specific to AI. A 401 with a challenge, a bearer token in a header and an audience check are the standard recipe from OAuth 2.0 and OpenID Connect; the confused deputy is the same hazard that authorisation describes; and a signed requestState is an ordinary signed cookie (applied cryptography explains the MAC). What is new is the consequence of a mistake. A tool server holds a model's judgement between a user and their data, so an over-broad token is more dangerous than it first appears: the model may be steered by text it read (chapter 19), and then acts with every permission the token carries.

Operating a remote server

A server that is correct still has to be run. Three habits matter most.

Use the headers at the gateway. Because Mcp-Method and Mcp-Name mirror the body, a gateway can apply policy without parsing JSON: a lower rate limit for refund_order than for orders_lookup, a role check on risky tools, a tenant's traffic routed to its own pool, an audit line for every invocation. A server can also mark a tool parameter with x-mcp-header so that clients copy its value into an Mcp-Param- header (the specification's example is a region name, used for routing). The security value is the equality check above: a gateway and a server must never disagree about what a request says.

Make retries safe. A request stands alone, which makes retrying easy and idempotency your job. The transport rules say a broken response stream loses the in-flight request and the client must send it again with a new id. For a read, that is harmless. For a tool that creates a ticket or moves money, the first attempt may have succeeded before the connection dropped. Give such tools an idempotency key argument that the server remembers, say so in the description so the model supplies it, and set deadlines so a model never waits indefinitely (failure, timeouts and retries, tool design). Long jobs belong behind the tasks extension or your own job id.

Log one structured event per request: method, tool, caller, protocol version, status, duration and the trace id from traceparent (logs and structured events). Counting requests by protocol version tells you when an old version can be dropped; counting isError results by tool tells you which descriptions confuse the model. Decide deliberately what you store of the arguments, which may be sensitive.

Surviving spec changes

Between November 2024 and July 2026 the protocol went through at least five dated revisions, replaced its remote transport, added and then changed authorisation, and finally removed its handshake. It will keep changing, and your integration needs to be built for that, not rescued after each release. These practices cost little and pay for themselves at the first revision.

  1. Put MCP behind your own interface. Your agent should depend on something like list_tools() and call_tool(name, args) that you define, with one module translating to MCP. When the wire changes, that module changes and nothing else does.
  2. Pin and record versions. Pin the SDK, name the protocol version you ask for, and log the version actually used. "It stopped working" becomes a diff.
  3. Gate on capabilities, not version numbers. Ask what a peer declares (capabilities, extensions) and degrade gracefully. The specification requires the other side to fall back to core behaviour or refuse clearly.
  4. Handle both eras if your fleet is mixed. Try a modern request first. A recognised modern error such as -32022 means a modern server: retry with a version it lists. Anything else means a legacy server: fall back to initialize. Cache the answer per server. On stdio the probe is server/discover. Never key the fallback on one error code, because legacy servers answer unknown methods however they like, or not at all.
  5. Keep recorded transcripts as regression tests. Save real traces (one JSON message per line) for each server and version and replay them in continuous integration.
  6. Read the deprecation registry. The twelve-month minimum is your warning. Search your code for roots, sampling and logging now.
  7. Treat the tool list as a dependency. Descriptions are instructions to your model. Record a hash of each tool's name, description and schema when a human approves it, and re-approve on change. This catches honest drift and a hostile server that changes behaviour after you trust it (chapter 19).

Here is practice 4 in running code: a dual-era client that connects to a modern server (the one above), to a legacy server that insists on initialize, and to a modern server when the client prefers an old version.

import json
from mcp_modern import handle as modern_http     # the stateless server from earlier

def legacy_http(headers, body):
    """A 2025-11-25 style server: wants initialize first and knows nothing of the new methods."""
    msg = json.loads(body)
    if msg["method"] == "initialize":
        return 200, {"jsonrpc": "2.0", "id": msg["id"], "result": {"protocolVersion": "2025-11-25", "capabilities": {"tools": {}}}}
    return 400, {"jsonrpc": "2.0", "id": msg["id"], "error": {"code": -32600, "message": "Call initialize first"}}

MODERN = {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}}

def connect(server, prefer="2026-07-28"):
    """Dual-era client: try a modern request first; a recognised modern error means 'modern server'."""
    meta = {**MODERN, "io.modelcontextprotocol/protocolVersion": prefer}
    body = json.dumps({"jsonrpc": "2.0", "id": 1, "method": "server/discover", "params": {"_meta": meta}})
    status, reply = server({"MCP-Protocol-Version": prefer, "Mcp-Method": "server/discover"}, body)
    if status == 200:
        return "modern", reply["result"]["supportedVersions"]
    if reply.get("error", {}).get("code") == -32022:                      # modern server, other version
        supported = reply["error"]["data"]["supported"]
        return ("modern, retry with " + supported[0]) if prefer not in supported else ("modern", supported)
    status, reply = server({}, json.dumps({"jsonrpc": "2.0", "id": 2, "method": "initialize", "params": {}}))
    return "legacy: fell back to initialize", [reply["result"]["protocolVersion"]]

print("modern server :", connect(modern_http))
print("legacy server :", connect(legacy_http))
print("old preference:", connect(modern_http, prefer="2025-11-25"))
modern server : ('modern', ['2026-07-28'])
legacy server : ('legacy: fell back to initialize', ['2025-11-25'])
old preference: modern, retry with 2026-07-28

Key takeaways

  • Remote MCP servers run behind load balancers. Any state a server keeps in a replica's memory between requests is lost whenever a request lands elsewhere; sticky routing and shared stores are workarounds, not fixes.
  • The 2026-07-28 revision made MCP stateless: no handshake, no Mcp-Session-Id, version and capabilities in each request's _meta, discovery by server/discover, and routing headers that must match the body.
  • Server-initiated questions became multi round-trip requests: input_required plus a retry. The requestState passes through the client, so it must be signed and bound to the user, the request and an expiry, and it does not give single-use semantics.
  • Authorisation is OAuth 2.1: the MCP server is a resource server that advertises its authorisation server through protected resource metadata. Tokens are audience-bound with the resource parameter, issuers are checked, scopes are minimal with step-up on 403, and tokens for other services are never accepted or passed on.
  • Statelessness removes protocol state, not application state: use explicit handles such as a basket id, and idempotency keys for anything with side effects.
  • Survive revisions by isolating MCP behind your own interface, pinning and logging versions, probing for both eras, replaying recorded transcripts and hashing approved tool definitions.

Check your understanding

A 2025-era MCP server keeps sessions in memory and runs as four replicas behind a round-robin balancer. About what fraction of non-initialize requests from a new client fail, and what is the cleanest long-term fix?

  1. About one in four; add retries on the client
  2. About three in four; remove the dependency on in-memory protocol state (the 2026-07-28 design)
  3. Almost none, because the balancer retries on another replica
  4. About half; use a larger instance so one replica handles everything
Only the replica that handled initialize knows the session, so with four replicas roughly three requests in four go elsewhere and fail. Retrying (option 0) just rolls the dice again and still needs the session. A balancer cannot know which replica has the session, which rules out option 2. A single big instance (option 3) gives up horizontal scaling and availability. The durable fix is to stop needing the state.

A gateway receives Mcp-Method: tools/call and Mcp-Name: orders_lookup, but the JSON body calls refund_order. What should a conforming server do, and why does the rule exist?

  1. Execute the body, because the body is the source of truth
  2. Execute the header's tool, because headers are validated first
  3. Ignore the headers, since they are only hints for logging
  4. Reject with 400 and error -32020, because a gateway applying policy to the headers must never disagree with the server about what the request does
The headers are required to match the body precisely so intermediaries can enforce policy from them. If a server executed the body, an attacker could pass a policy that allows orders_lookup while performing refund_order. Executing the header's tool (option 1) or ignoring the headers (option 2) leaves the same gap in different places. Rejecting the request is the only safe outcome.

An MCP client holds a valid token that a billing API's authorisation server issued for https://billing.example.com. It sends that token to an MCP server at https://mcp.example.com. What should the MCP server do?

  1. Reject it with 401, because the token's audience is not this server
  2. Accept it, since the signature is valid and the user is the same
  3. Accept it and forward it to the billing API to save a second login
  4. Accept it if the scopes look sufficient
Audience binding is the point of the resource parameter: a token is valid for the resource it was issued for. Accepting tokens meant for others, or passing yours onward, is the confused-deputy pattern the specification forbids. A valid signature (option 1) proves who issued the token, not who it is for, and scopes (option 3) are irrelevant to the wrong audience.

In the multi round-trip pattern, the server returns requestState and the client echoes it on the retry. Which design is correct?

  1. Put the pending refund amount in plain JSON in requestState and trust it on retry, since the server issued it
  2. Store the pending refund in the replica's memory and put only its id in requestState
  3. Sign the state with a key the replicas share, and include the user, an expiry and a digest of the request; also record one-time actions server-side
  4. Encrypt the state so the client cannot read it, with no other checks
The state crosses an untrusted client, so integrity matters, and binding it to principal, expiry and request limits replay and cross-user reuse. Plain JSON (option 0) lets a client edit the amount. In-memory storage (option 1) reintroduces the replica affinity the pattern removes. Encryption without checks (option 3) hides content but still allows replay by another user or after expiry, and nothing here by itself guarantees single use, which needs a server-side record.

Your client must work with both old (initialize-based) and new (stateless) servers. Over HTTP it sends a modern request and gets 400 with a JSON-RPC error body containing code -32022 and a supported list. What now?

  1. Fall back to initialize, since the request failed
  2. Treat the server as modern and retry with a version from the list
  3. Give up, because the versions do not match
  4. Fall back to the deprecated HTTP+SSE transport
A recognised modern error identifies a modern server, so the client should negotiate by retrying with a mutually supported version. Falling back (options 0 and 3) is only for responses that are not recognised modern errors, such as an empty 400 or a 404 without the expected error body. Giving up (option 2) ignores that the list tells you exactly what the server accepts.

A team says "stateless MCP means our basket tool can no longer work". Which reply is most accurate?

  1. Correct: stateful tools must move to stdio
  2. Correct: they must wait for the sessions feature to return
  3. Incorrect, but only if they use sticky routing
  4. Incorrect: the basket becomes an explicit handle (a basket id) that tools take as an argument and the server looks up in its own storage
The revision removed protocol-level sessions, not application state. Passing an explicit handle makes the state visible and durable. Sticky routing (option 2) is what the redesign removes the need for, and nothing needs to be moved to stdio (option 0).

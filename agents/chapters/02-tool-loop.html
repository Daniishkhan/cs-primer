Tool Calling: The Agent Loop

A model can only write text. Tool calling is the arrangement that turns written requests into real actions: you describe functions, the model asks for one, your program runs it and reports back, and a loop repeats until the job is done or a limit says stop. This chapter builds that loop completely, including the parts that keep it from running away.

Why this matters

Everything else in this course sits on top of this loop: tool design, MCP servers, memory, multi-agent teams, computer use and coding agents are all this loop with something added. Get its mechanics exactly right and the rest is variations. Get them subtly wrong, with a missing tool result, an unbounded cycle or a retried payment, and you meet failures that are expensive, confusing or unsafe. After this chapter you can write the loop from scratch, say precisely what travels in each turn, handle errors and parallel calls, and put hard limits around cost and time. Lab 1 has you build it.

What a tool is

A tool is a function your program makes available to the model, described by three things: a name, a plain-language description of what it does and when to use it, and an input schema that says what arguments it takes. The schema is written in JSON Schema, a standard vocabulary for describing the shape of a JSON document: which keys exist, their types, which are required. Here are two tools for an order-support agent:

import json
from llm import ScriptedModel, tool_use, text_of, tool_calls, tool_result

ORDERS = {"A-1001": {"status": "shipped", "total_cents": 4250, "carrier": "UPS"},
          "A-1002": {"status": "processing", "total_cents": 1999, "carrier": None}}
TRACKING = {"UPS": "Out for delivery in Leeds"}

def get_order(order_id):
    return json.dumps(ORDERS[order_id])               # KeyError for unknown ids
def track_shipment(carrier):
    return TRACKING[carrier]

REGISTRY = {
    "get_order": (get_order, {"name": "get_order", "description": "Fetch one order by its id, e.g. A-1001.",
        "input_schema": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}}),
    "track_shipment": (track_shipment, {"name": "track_shipment", "description": "Latest tracking event for a carrier name.",
        "input_schema": {"type": "object", "properties": {"carrier": {"type": "string"}}, "required": ["carrier"]}}),
}
TOOL_DEFS = [d for _, d in REGISTRY.values()]

Two lists matter. REGISTRY maps each name to the real Python function; it stays in your program. TOOL_DEFS is the part sent to the model with every request, in the tools field from chapter 1. The model sees only names, descriptions and schemas. It never sees your code and it cannot run anything. This is the point people most often get wrong.

Common misconception

"The model calls the function." It does not. The model writes a structured request naming a tool and its arguments; your program decides whether to run it, runs it, and reports what happened. That gap is the entire safety story of agents: allow-lists, argument validation, permissions, approvals and sandboxes all live in the code that stands between "the model asked" and "the function ran". Providers also offer a few server-side tools (web search, code execution) that the provider runs for you, but the mechanism you build here, client-side tools, is the general case.

Analogy: the order slip and the kitchen

In a restaurant the diner does not cook. A waiter writes an order slip in a fixed format ("table 4, dish 12, no onions"), the kitchen reads it, makes the dish or sends the slip back saying "out of stock", and the answer returns to the table. The model writes the slips; your program is the kitchen; tool_result is the plate or the "out of stock" note.

Where it breaks down: a kitchen can be certain a slip came from a real waiter. Your program cannot be certain a request is wise or even well-formed: the "waiter" may have been misled by text in a document it read, so the kitchen must check each slip instead of trusting it.

The turn structure

When you send a request with tools and the model decides to use one, its reply has stop_reason: "tool_use" and contains one or more tool_use blocks. Each has a unique id, the tool name and an input object that should satisfy the schema. Your program then sends the next request with the history extended by two messages: the assistant message exactly as received, and a user message holding a tool_result block for each request, tied to it by tool_use_id.

A few rules follow, and providers enforce them with a 400 error if you break them. The tool results travel in a user message because, from the model's side, they are information arriving from outside. Every tool_use id needs exactly one tool_result; a missing one leaves the conversation in an invalid state. Anthropic's API also expects the tool_result blocks to come first in that user message, before any extra text. OpenAI's Chat Completions API expresses the same idea differently, with an assistant message carrying tool_calls and a separate tool-role message per result; chapter 6 maps the two.

The loop

Put the pieces together and the loop is short. This version keeps the tool functions above, runs each requested tool, returns failures as data, and stops after max_iterations model calls no matter what.

def run_tool(call):
    fn, _ = REGISTRY[call["name"]]
    try:
        return tool_result(call["id"], fn(**call["input"]))
    except Exception as e:                          # the model sees failures as data
        return tool_result(call["id"], f"{type(e).__name__}: {e}", is_error=True)

def agent_loop(model, question, max_iterations=6):
    messages = [{"role": "user", "content": question}]
    for i in range(1, max_iterations + 1):
        reply = model.complete(messages, system="You are a support agent.", tools=TOOL_DEFS)
        messages.append(reply.as_message())
        calls = tool_calls(reply)
        print(f"[{i}] stop_reason={reply.stop_reason:<8} text={text_of(reply)!r} calls={[c['name'] + json.dumps(c['input']) for c in calls]}")
        if reply.stop_reason != "tool_use":
            return messages, "done"
        messages.append({"role": "user", "content": [run_tool(c) for c in calls]})
    return messages, "iteration budget exhausted"

if __name__ == "__main__":
    model = ScriptedModel([
        [tool_use("get_order", {"order_id": "A-1001"}, id="t1")],
        [tool_use("track_shipment", {"carrier": "UPS"}, id="t2")],
        "Order A-1001 shipped with UPS and is out for delivery in Leeds.",
    ])
    messages, status = agent_loop(model, "Where is order A-1001?")
    print("status:", status, "| messages in history:", len(messages))
    print(json.dumps(messages[2], indent=1))

Read the output as the loop's heartbeat. Iteration 1 returned a tool request, so the loop ran the tool and went round again. Iteration 3 returned end_turn with no tool request, which is the normal exit. The history now holds six messages: the question, then two (assistant, user) pairs for the tool round trips, then the final answer. Step through it slowly:

Step through

Three model calls, two tool runs, one answer

  1. The history starts with the question. Your program holds one message. The model has seen nothing yet, and will see only what you send.
  2. Call 1. The program sends the history and the tool definitions. This is an ordinary stateless request.
  3. The model asks for a tool. The reply has stop_reason: "tool_use" and a get_order request. The assistant message is appended to the history exactly as received.
  4. The program runs the tool. It looks up get_order in its own registry, calls the real function with the model's arguments and gets a result. The model played no part in this step.
  5. The result is appended. A user message with a tool_result block, tied to the request by id, joins the history. Nothing has been sent to the model yet.
  6. Call 2. The whole, longer history is sent again. The model reads the order, sees a carrier, and asks for track_shipment. Another assistant message is appended.
  7. Second tool run. The program runs track_shipment and appends its result as another user message.
  8. Call 3 ends the loop. With both facts in the history the model answers in text. The stop reason is end_turn, no tool is requested, and the program returns the answer. Three calls, each longer than the last.

When a tool fails

Tools fail: an id does not exist, a service times out, the arguments do not fit. What should the loop do? The robust answer is to return the failure to the model as a tool result with is_error: true and a message it can act on. The model is good at reading an error, and often corrects its own mistake on the next turn. Raising the exception and killing the run wastes the whole conversation so far.

import json
from llm import ScriptedModel, tool_use, text_of
from loop import agent_loop

# The model first asks for an order that does not exist, reads the error, and corrects itself.
model = ScriptedModel([
    [tool_use("get_order", {"order_id": "A-9999"}, id="t1")],
    [tool_use("get_order", {"order_id": "A-1002"}, id="t2")],
    "I could not find A-9999, but A-1002 is still processing.",
])
messages, status = agent_loop(model, "Check order A-9999 for me")
print(json.dumps(messages[2]["content"][0], indent=1))

That error text, KeyError: 'A-9999', is poor: it exposes an implementation detail and says nothing about what to do next. A better tool returns "No order with id A-9999. Order ids look like A-1001; use search_orders to find one by customer email." Error messages are part of the tool's interface, and chapter 5 treats them as such. Two further rules belong in run_tool in any real system:

  • Validate before you run. Check the model's input against the tool's schema, and check the tool name is in your registry. A hallucinated tool name or an argument of the wrong type should come back as an error result, not crash the harness. The tools example above uses REGISTRY[call["name"]], which would raise KeyError on an unknown name before the try block; a production version looks the name up inside the guarded region.
  • Never turn the model's text into code. Passing a model-written string to eval, a shell or a SQL string concatenation is injection with a language model as the author. Use fixed functions with typed arguments, as with SQL injection, where the fix is parameterised queries.

Several tool calls in one turn

A model may request several tools in a single reply when the calls do not depend on each other: the status of two orders, the weather in three cities. The reply then contains several tool_use blocks. Your obligation is to answer all of them in the one next user message. Because they are independent, you can run them concurrently and save wall-clock time.

import json
from concurrent.futures import ThreadPoolExecutor
from llm import ScriptedModel, tool_use, text_of, tool_calls, tool_result
from loop import TOOL_DEFS, run_tool

def check_pairing(messages):
    """Every tool_use id in an assistant turn needs a tool_result in the very next user turn."""
    for i, m in enumerate(messages):
        if m["role"] != "assistant" or isinstance(m["content"], str):
            continue
        wanted = {b["id"] for b in m["content"] if b["type"] == "tool_use"}
        if not wanted:
            continue
        nxt = messages[i + 1]["content"] if i + 1 < len(messages) else []
        got = {b["tool_use_id"] for b in nxt if b["type"] == "tool_result"}
        if wanted - got:
            return f"turn {i}: no tool_result for {sorted(wanted - got)}"
    return "pairing ok"

model = ScriptedModel([
    [tool_use("get_order", {"order_id": "A-1001"}, id="ta"), tool_use("get_order", {"order_id": "A-1002"}, id="tb")],
    "A-1001 shipped; A-1002 is processing.",
])
messages = [{"role": "user", "content": "Status of A-1001 and A-1002?"}]
reply = model.complete(messages, tools=TOOL_DEFS)
messages.append(reply.as_message())
calls = tool_calls(reply)
print("one assistant turn asked for", len(calls), "tools:", [c["id"] for c in calls])
with ThreadPoolExecutor() as pool:                     # independent calls can run concurrently
    results = list(pool.map(run_tool, calls))          # map keeps the order of `calls`
messages.append({"role": "user", "content": results})  # ONE user message carries ALL results
print(check_pairing(messages))
broken = messages[:-1] + [{"role": "user", "content": results[:1]}]
print(check_pairing(broken))
print(text_of(model.complete(messages, tools=TOOL_DEFS)))

pairing ok
turn 1: no tool_result for ['tb']

The check_pairing helper is worth keeping in a test suite: it catches the single most common loop bug, dropping a result when two calls fail or one is skipped. Two cautions about parallelism. First, concurrency is safe only for calls without side-effect ordering: "create the folder" then "write the file" cannot run at once, and the model cannot always tell. Second, if one call is a payment or a deletion, think about what happens if the other fails; you are back in saga territory. For tools with side effects, the safe default is to run them one at a time, in the order the model listed them.

Stopping: the loop must be able to end

Left alone, a model may keep calling tools forever: it cannot find the answer, a tool keeps returning an error, or two steps undo each other. A loop therefore needs stop conditions that your code enforces, not ones you hope the model respects. There is one natural exit and several forced ones.

The usual forced stops, and what each protects against:

Iteration cap
Maximum model calls per task (5 to 50 is typical; the right value comes from measuring how many your tasks need). It bounds cost and time and is the simplest backstop.
Token or cost budget
A cap on total input plus output tokens, or on money. Needed because iterations are not equal: the twentieth call carries a far longer history than the second.
Wall-clock timeout
A deadline for the whole task, plus a timeout on each tool call. Users give up long before a budget runs out.
Loop detection
Stop when the same tool is called with identical arguments more than a few times. A model stuck on one failing call burns its iteration budget for nothing.
Human checkpoint
Pause for approval before a consequential action (a refund, a deletion, an email). This is a stop condition too: the loop halts until a person answers.
import json
from llm import ScriptedModel, tool_use, tool_calls
from loop import TOOL_DEFS, run_tool

def guarded_loop(model, question, max_iterations=8, max_input_tokens=600, max_repeats=2):
    messages, seen, spent = [{"role": "user", "content": question}], {}, 0
    for i in range(1, max_iterations + 1):
        reply = model.complete(messages, tools=TOOL_DEFS)
        spent += reply.usage["input_tokens"]
        messages.append(reply.as_message())
        if reply.stop_reason != "tool_use":
            return f"done after {i} calls, {spent} input tokens"
        if spent > max_input_tokens:
            return f"stopped: token budget ({spent} > {max_input_tokens}) after {i} calls"
        results = []
        for c in tool_calls(reply):
            key = (c["name"], json.dumps(c["input"], sort_keys=True))
            seen[key] = seen.get(key, 0) + 1
            if seen[key] > max_repeats:
                return f"stopped: {c['name']} called with identical input {seen[key]} times (loop) after {i} calls"
            results.append(run_tool(c))
        messages.append({"role": "user", "content": results})
    return f"stopped: iteration budget ({max_iterations}) after {max_iterations} calls, {spent} input tokens"

def stuck(i=0):                       # a model that never gives up on the same call
    return ScriptedModel(lambda m, t, s: [tool_use("get_order", {"order_id": "A-1001"})])

def wanderer():                       # a model that keeps trying new things
    n = {"i": 0}
    def fn(m, t, s):
        n["i"] += 1
        return [tool_use("track_shipment", {"carrier": f"carrier-{n['i']}"})]
    return ScriptedModel(fn)

print(guarded_loop(stuck(), "Where is A-1001?"))
print(guarded_loop(wanderer(), "Where is A-1001?"))
print(guarded_loop(wanderer(), "Where is A-1001?", max_input_tokens=100000))
stopped: get_order called with identical input 3 times (loop) after 3 calls
stopped: token budget (625 > 600) after 5 calls
stopped: iteration budget (8) after 8 calls, 1144 input tokens

Three different stops, each reported with its reason. The reason matters: when a budget ends the run, the harness should return the partial result and say which limit was hit, so the caller (or a person) can decide whether to retry with a larger budget, hand over, or give up. A silent timeout is the worst outcome, because nobody knows whether the work was done.

What the loop costs

Return to the stateless fact from chapter 1: every iteration re-sends the whole history. Suppose the fixed part of the prompt (system prompt plus tool schemas) is 2,000 tokens and each iteration adds 700 tokens (the model's request plus the tool's result). Iteration k then sends 2,000 + 700(k − 1) tokens, and the total over n iterations is the sum of an arithmetic series: n × 2,000 + 700 × n(n − 1) / 2. The second term grows with the square of n.

# Every iteration re-sends the whole history, so input tokens grow quadratically with iterations.
BASE, DELTA = 2000, 700          # assumptions: system prompt + tool schemas; tokens added per iteration

def input_tokens(n):
    return sum(BASE + (k - 1) * DELTA for k in range(1, n + 1))

print(" iters  total input tokens  context at last call")
for n in (1, 5, 10, 20, 40):
    print(f"{n:>6}  {input_tokens(n):>18,}  {BASE + (n - 1) * DELTA:>20,}")
 iters  total input tokens  context at last call
     1               2,000                 2,000
     5              17,000                 4,800
    10              51,500                 8,300
    20             173,000                15,300
    40             626,000                29,300

Two things follow. First, cost per task is superlinear in the number of steps, so an agent that takes 40 steps costs far more than twice one that takes 20 (626,000 versus 173,000 input tokens here, about 3.6 times). Reducing the number of iterations, and keeping each result short, are the two biggest levers. Second, prompt caching changes the arithmetic. Providers can store the processed form of a repeated prefix (the key-value cache, A3 chapter 18) and bill reads of it at a fraction of the normal input price. Because an agent loop re-sends an ever-growing but unchanging prefix, it is close to the ideal customer. Try the numbers yourself:

With the defaults, ten iterations at an assumed $3 per million input tokens cost about 15 cents without caching; with caching modelled at 0.1× for reads and 1.25× for writes, the billed-equivalent total falls from 51,500 to about 14,700 tokens, roughly a 70 per cent saving. Those multipliers are assumptions modelled on typical published prices; check your provider's current pricing and cache lifetimes before you plan around them. Note also the last line of the widget output: at 97 per cent reliability per step, ten steps succeed about 74 per cent of the time, and twenty steps (move the slider) about 54 per cent, the compounding from chapter 0. A cheaper loop is not a more reliable one.

State of play, October 2026

The tool_use and tool_result structure is shared in spirit across the major providers, but names and details differ and keep changing. Anthropic's SDKs include helper "tool runner" loops, and OpenAI's and Google's SDKs offer equivalents; use them in production if you like, but write the loop by hand once so that you know what they do for you (the advice in Anthropic's "Building effective agents" about not hiding behind a framework applies). Providers also now offer hosted tools such as web search and code execution, where the provider runs the tool and the results appear inside the same response. Model tool-calling accuracy has improved a great deal since 2023, yet argument errors and wrong-tool choices remain the main loop failure, which is why validation and error results stay mandatory.

How loops go wrong

Before adding safety machinery it helps to know what actually breaks. These are the failures that recur in real transcripts, with the first thing to check for each. Reading a handful of failed runs end to end is the best way to learn them; A6 chapter 1 turns that habit into a method.

FailureWhat you see in the transcriptFirst thing to check
Wrong toolThe model calls a search tool when a lookup tool was right.Are the descriptions distinguishable? Do two tools overlap?
Bad argumentsA string where an integer is needed; an invented id; a date in the wrong format.Schema types and examples; add validation with a corrective error message.
Invented resultThe model states a tool outcome it never requested, or continues a "pretend" observation.The loop must append real results only; use stop sequences in text-format ReAct (chapter 3).
Lost resultA 400 error about a tool_use without a tool_result.The pairing check; exceptions that skip appending.
Runaway loopThe same call repeated, or alternating calls that undo each other.Iteration cap and repeated-call detection; a hint in the error text.
Giant outputOne tool result of 50,000 tokens pushes everything else out.Truncate or paginate inside the tool (chapter 5); a size limit in run_tool.

Repeated side effectTwo emails sent, two refunds issued.Idempotency keys; whether a retry was the harness's or the model's.

Notice how few of these are the model being "unintelligent". Most are interface problems: an unclear tool description, a vague error, a missing limit. That is why tool design gets its own deep chapter, and why Anthropic reports spending more time optimising tools than the overall prompt when building its SWE-bench agent ("Building effective agents", 2024).

The history is the state

Look again at agent_loop. Its entire state is the messages list (plus a few counters). If you saved that list after each iteration, a crashed process could load it and call the model again; the model would see exactly what it saw before and carry on. This is why the loop is easy to checkpoint, to replay in tests with a scripted model, to hand to another worker, and to inspect when something goes wrong. It is also why compacting the history (summarising old turns, chapter 10) changes what the agent "remembers": there is no other memory.

Two refinements follow for production. Persist before running a side-effecting tool, with its idempotency key, so a restart does not repeat it. And record which tool calls have already produced results, so a resumed run does not ask the model to redo them. Chapter 15 builds this into an event-sourced agent.

Telling the model how to behave in the loop

Code enforces limits; the prompt shapes behaviour inside them. A few instructions in the system prompt reliably help. State how much effort a task deserves, since models over-invest without guidance: Anthropic's account of its multi-agent research system describes early versions spawning dozens of sub-agents for simple queries until effort-scaling rules were written into the prompt. Say when to stop ("answer as soon as you have the order status; do not look up unrelated orders"). Say what to do on failure ("if a tool returns an error twice, explain the problem to the user instead of trying a third time"). And ask for short reasoning before tool choices when accuracy matters, which is the subject of chapter 3. Prompts are tested, not hoped over: chapter 4 shows how.

Go deeper the same loop in OpenAI Chat Completions format

The loop is identical; only the message shapes differ. In OpenAI's Chat Completions API the assistant message carries a tool_calls list, each entry with an id, a type of "function" and a function object holding the name and arguments. The arguments are a JSON-encoded string, not an object, so you must json.loads them (and they may be invalid JSON, which is another reason to validate). Each result goes back as its own message with role: "tool", the matching tool_call_id and a string content. The stop signal is finish_reason: "tool_calls" rather than stop_reason: "tool_use". The shared module lab-support/llm.py converts the content-block format to this one inside RealModel, so a loop written once runs against either provider; chapter 6 writes that adapter by hand.

Making the loop safe to run

A loop that works in a demo needs four more properties before it touches anything that matters.

Side effects need idempotency

Model mistakes and network faults both cause repeats: a timeout on a "charge card" call, a retry, and the customer is charged twice. The remedy is the standard one for retried calls: give each side-effecting call an idempotency key, a unique value the server remembers so that the second request with the same key returns the first result instead of acting again. For a tool, derive the key from the task and the step, not from a fresh random value on each attempt. Long-running agents take this further with durable logs, covered in chapter 15.

Least privilege per tool

Expose the narrowest tool that does the job. refund(order_id, amount) with a server-side limit is safer than run_sql(query). The loop should run tools with the end user's permissions, not a super-user's, so a confused or manipulated model cannot do more than the user could. Chapter 20 develops this into sandboxes and approval prompts.

Log every iteration

An agent run is a trace: each model call, each tool call, arguments, results, token counts, durations and the stop reason. Record them as structured events from day one (distributed tracing gives the vocabulary of spans). When a run goes wrong, reading the transcript is the fastest diagnosis, and the same logs become your evaluation data (A6 chapter 1).

Treat tool output as untrusted

Whatever a tool returns goes into the model's context, including a web page or an email body that an attacker wrote. The model may follow instructions inside it. Never grant a tool-reading agent both private data and an outward channel without a control in between; the lethal-trifecta analysis is in chapter 19.

Systems connection

The harness around the loop is an ordinary service: it needs timeouts, retries with backoff and jitter, circuit breakers on flaky tools, and idempotent writes. Running tools concurrently is an ordinary threading question. And an agent that crashes halfway through a ten-step task raises the question that sagas answer for services: what do we undo, and how do we resume without repeating?

Key takeaways

  • A tool is a name, a description and a JSON Schema. The model sees these and writes requests; your program decides whether to run them.
  • The loop: call the model; if stop_reason is tool_use, run every requested tool, append the assistant message and one user message holding a tool_result for each id, and call again.
  • Return tool failures to the model as is_error results with actionable text; validate names and arguments before running anything.
  • Independent calls in one turn can run concurrently, but all must be answered together; keep side-effecting calls sequential.
  • Enforce stop conditions in code: iteration cap, token or cost budget, timeout, repeated-call detection and human checkpoints, and always report which one fired.
  • Input cost grows roughly with the square of the iteration count because the history is re-sent; caching and shorter results are the levers, and per-step errors still compound.

Check your understanding

Where does the code of a tool, such as get_order, run in a client-side tool-calling loop?

  1. Inside the model, which has been given the function
  2. In your own program, which executes it when the model's request arrives
  3. On the model provider's servers, from the schema alone
  4. Wherever the model chooses, because it picks the runtime
The model only sees a name, a description and a schema and writes a request. Your program looks up the real function and runs it, which is why all validation, permissions and approvals can live in your code. Providers do run a few hosted tools themselves, but that is a different mechanism.

The model's reply contains two tool_use blocks, ids ta and tb. Your code runs only ta and sends a user message with one tool_result. What should you expect?

  1. The model infers tb was skipped and continues normally
  2. The model reruns tb itself
  3. The result for ta is accepted and tb is quietly dropped
  4. The provider rejects the request, because every tool_use needs a matching tool_result
The pairing rule is enforced: an unanswered tool_use leaves the history invalid and the call fails with an error. The model cannot run tools and nothing is silently dropped. A test like check_pairing catches this before it reaches the provider.

A tool raises TimeoutError while fetching an order. What is the best handling inside the loop?

  1. Return a tool_result with is_error true and a clear message so the model can retry, change course or tell the user
  2. Let the exception propagate and end the whole run
  3. Return an empty string so the loop carries on
  4. Retry silently forever until it works
The model can act on a clear error, and the run's earlier work is preserved. An empty result hides the failure and invites a wrong answer. Infinite silent retries ignore the budget, and crashing throws away the conversation. A bounded harness-level retry for transient errors is fine, but it still reports the final failure.

With a fixed prompt of 2,000 tokens and 700 tokens added per iteration, roughly how many input tokens are sent in total over 20 iterations?

  1. About 54,000
  2. About 40,000
  3. About 173,000
  4. About 15,000
The total is 20 × 2,000 + 700 × (20 × 19 / 2) = 40,000 + 133,000 = 173,000. 40,000 counts only the fixed prompt and ignores the history that is re-sent; 15,000 is roughly the size of the last call alone, which ignores all the earlier calls.

An agent keeps calling search("annual report") with the same arguments and gets the same empty result. Which stop condition catches this earliest?

  1. A wall-clock timeout of ten minutes
  2. A cap of 50 iterations
  3. A token budget of one million tokens
  4. Repeated-call detection that stops after the same call recurs a few times
All the others eventually stop the run, but only after wasting most of their budget. Repeated-call detection fires after two or three identical calls. The other limits remain useful as backstops for other failure patterns, such as a model wandering through new but useless calls.

A tool charges a card. The call times out, and the loop retries it. What design prevents a double charge?

  1. Lower the model's temperature to 0
  2. Send an idempotency key derived from the task and step, so a repeat returns the first result
  3. Ask the model to remember whether it already charged
  4. Never retry, and tell the user to try again
The server must recognise a repeat, and an idempotency key lets it do that. Temperature does not control whether a harness retries, and the model has no reliable memory of a call whose outcome it never saw. Never retrying leaves the customer unsure whether they were charged at all.

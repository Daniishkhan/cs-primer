Context Engineering

An agent's behaviour on step forty depends on what happens to be in its window at step forty. The window is the text the model reads on each call. This chapter treats that window as a budget to be spent. It covers what to put in, what to take out and what to write down elsewhere. It also covers what to hand to a helper and how to tell whether your choices helped. The goal is the smallest set of tokens that makes the next decision a good one.

Why this matters

Most agent failures that look like "the model got confused" are context failures. A tool returned forty pages and buried the one line that mattered. An early instruction scrolled out of attention. A stale note contradicted a new fact. Or the loop simply ran out of room on step thirty. Better prompts help at the start of a task; they do nothing for the middle of a long one. Context engineering is the discipline for the middle. After this chapter you can account for every token in an agent's window. You can choose among clearing old results, summarising the history (compaction), notes, retrieval and sub-agents for a given failure. You can write a compaction step that you can test, and use a simulator to see how a policy behaves on a long run. The chapter builds on the loop cost arithmetic in chapter 2 and the tool output shaping in chapter 5. It leads into memory and long context versus retrieval.

From prompt engineering to context engineering

The context window is the text a model reads on one call: everything from the system prompt to the latest tool result. The model has no other working memory. Anything it should use must be in the window, and anything in the window is read again on every call.

Early work on prompts concentrated on one string, the system prompt, written once. An agent changes the situation, because the window is assembled afresh on every turn from many sources. Anthropic's engineering team describes context engineering as the practice of curating and maintaining the optimal set of tokens during inference. That includes everything that lands in the window beyond the prompt: tools, external data and message history. The question it poses is iterative: what configuration of context is most likely to produce the behaviour we want, at this step? You answer it each time you build a call, and a long-running agent builds hundreds.

This anatomy suggests a first discipline: know your numbers. Count tokens by component (system prompt, tool definitions, loaded memory, history, tool results, retrieved text) for a typical run and for a long one. Teams that do this are often surprised that 60 to 90 per cent of a long window is tool output the model has already used. You cannot manage what you have not measured.

The window as a budget

Three things are spent from the same pool of tokens: money, time and quality.

Money and time. Chapter 2 showed that a loop re-sends its whole history on each call. So the total input of a run grows roughly with the square of the number of turns. Provider-side prompt caching softens the money part. The unchanged start of the request is read from a cache at a fraction of the normal price. The chapter on the key-value (KV) cache explains why that start can be reused. But a cache works only on an unchanged prefix. Editing or removing anything early in the window invalidates everything after it. The simulation below runs one 40-turn task three ways, using the same tool result sizes each time, and reports input tokens with and without a cache. The cache multipliers are illustrative assumptions modelled on typical published pricing, not any provider's terms. Writes cost 1.25 times the base price and reads cost 0.1 times.

import random

SYSTEM = [("sys", 3000)]                       # system prompt + tool definitions: stable, cacheable
WRITE, READ = 1.25, 0.10                       # illustrative prompt-cache multipliers on the input price

def run(strategy, turns=40, trigger=40_000, keep=4, seed=7):
    rng = random.Random(seed)                  # same task for every strategy: same tool result sizes
    ctx, prev, billed, peak, events, sizes = list(SYSTEM), [], 0.0, 0, 0, []
    for t in range(turns):
        ctx += [(f"a{t}", 200), (f"r{t}", rng.randint(800, 3000))]
        total = sum(n for _, n in ctx)
        if total > trigger and strategy == "clear":
            results = [i for i, (k, _) in enumerate(ctx) if k.startswith("r") and not k.endswith("*")]
            for i in results[:-keep]:
                ctx[i] = (ctx[i][0] + "*", 25)             # replace an old result with a short stub
            events += 1
        elif total > trigger and strategy == "compact":
            ctx = SYSTEM + [(f"summary{t}", 1500)] + ctx[-4:]
            events += 1
        total = sum(n for _, n in ctx)
        hit = 0                                 # tokens in the unchanged prefix are read from cache
        for a, b in zip(ctx, prev):
            if a != b: break
            hit += a[1]
        billed += hit * READ + (total - hit) * WRITE
        peak, prev = max(peak, total), list(ctx)
        sizes.append(total)
    return peak, billed, events, sizes, sum(sizes)

if __name__ == "__main__":
    print(f"{'strategy':<9}{'peak':>8}{'input sent':>12}{'cache-billed':>14}{'events':>8}")
    for s in ("none", "clear", "compact"):
        peak, billed, events, _, raw = run(s)
        print(f"{s:<9}{peak:>8,}{raw:>12,}{billed:>14,.0f}{events:>8}")
strategy     peak  input sent  cache-billed  events
none       76,672   1,682,843       256,457       0
clear      38,375     927,111       199,660       2
compact    38,160     849,365       180,170       2

Read the table in two ways. Without a cache ("input sent"), clearing cuts total input by about 45 per cent and compaction by about half, because every later call is smaller. With a cache ("cache-billed", in base-price token equivalents), the same policies save only 22 and 30 per cent. The keep-everything run was already paying a tenth of the price for most of what it re-sent. Each clear or compaction also forces part of the prefix to be rewritten at the higher write price. Caching makes growth cheaper but does not remove it. The case for managing context is therefore only partly about cost. It is also about the limit, meaning the run that never fits. It is about latency, because the model still processes every token, cached or not, so long inputs slow the first token. And it is about quality, which is next.

Context rot: why more is not better

If models used every token in the window perfectly, a larger window would be strictly better. This chapter would then be about keeping things short only for cost. They do not. The informal name for the effect is context rot: as the amount of text grows, the model's ability to use any particular piece of it declines.

Three sources show the shape of the problem. Liu et al. (2023), "Lost in the Middle: How Language Models Use Long Contexts", found that performance is often highest when the relevant information is at the beginning or end of the input. It drops when the information sits in the middle, even for models built for long inputs. A Chroma technical report by Hong, Troynikov and Huber (July 2025), "Context Rot", tested 18 models on deliberately simple tasks. It reported that performance degraded as input length grew in every experiment. Extra irrelevant text alone was enough to cause it when the question and answer were held fixed. The decline was steeper when the answer was less similar to the question. A single distractor passage that resembled the answer reduced accuracy further, and more distractors reduced it more. Anthropic's context engineering post describes the same pattern. It cites needle-in-a-haystack recall that falls as context grows, and calls it a gradient in performance rather than a hard cliff.

Why does it happen? The explanations on offer are plausible rather than proven. Anthropic points to the architecture. Every token attends to every other, so n tokens create n2 pairwise relationships, and attention is spread thinner as n grows. Anthropic also points to training data, since models have seen fewer very long sequences than short ones. The Chroma authors state that they did not test mechanisms. Treat these as working explanations. What matters for engineering is the behaviour: relevant information should be present, easy to find and surrounded by as little irrelevant text as possible. Anthropic puts the goal as finding "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome".

Common misconception

"My model accepts a very large window, so I can put everything in and let it sort it out." That belief is wrong. A window size is the most text the model will accept, not the amount it will use well. The studies above used simple tasks and found degradation with length in all of them. The effects were larger with distractors that look like the answer, which is exactly what a pile of retrieved or accumulated text contains. Large windows are useful (chapter 12 measures when), but they raise the ceiling rather than remove the problem. The sound approach is to measure on your own task, with and without the extra context, instead of assuming either way. The studies' limits also apply here: simple synthetic tasks, a specific set of models in mid-2025, and newer models may degrade more slowly.

Analogy: the desk and the filing cabinet

Think of the window as the top of a desk. You can work only with what is on it. A tidy desk with the three documents for today's job is faster to work at than one buried under every file you have touched this week, even if the pile technically fits. Good practice is to keep the desk for the current task and file the rest in a cabinet where you can find it. Write a one-page note before you clear the desk for the next job.

Where it breaks down: a person ignores the pile and reads only what they need. A model reads the whole desk on every call and has to decide what matters each time. So clutter has a cost on every step, not just a visual one. Also, the cabinet is only useful if you can search it: notes you cannot find, or that went stale, are worse than no notes.

Select: put in only what this step needs

Retrieve just in time

The classic approach is to retrieve up front, a pattern called retrieval-augmented generation (RAG). Embed the user's question, fetch the closest passages and put them in the prompt (RAG end to end). It is fast, and for a fixed question-answering task it is often the right design. For agents, Anthropic describes a shift towards just-in-time context. The agent holds lightweight references, such as file paths, saved queries and links. It loads the data itself, using tools, when it needs it. Claude Code, which works with large codebases and data, is the example they give. It writes targeted queries and uses commands such as head and tail to look at parts of a file without loading all of it.

This works because the references themselves carry information. A file called tests/test_refunds.py in a folder named billing says something about purpose before it is opened, and timestamps and naming hint at relevance. The agent explores step by step, with each result informing the next, and the window holds only what it has chosen to look at. This is called progressive disclosure. The trade-offs the post names are real. Exploring at runtime is slower than reading pre-computed results. Without good guidance the agent can waste its budget by misusing tools or chasing dead ends. A hybrid is common. Load a small, stable set of orientation material at the start, as Claude Code does with its CLAUDE.md instruction file. Then let the agent retrieve the rest as it works. The advice attached to this, "do the simplest thing that works", is a good default. Start with a plain retrieve-then-answer design and add runtime exploration only where measurements show it earns its cost.

Keep the tool set small

Tool definitions sit in every call. A server with sixty tools may spend thousands of tokens on descriptions the model rarely needs, and overlapping tools make selection harder. The post's test is a good one. If a human engineer cannot say definitively which tool applies in a situation, the agent cannot be expected to do better. Give each task only the tools it needs and merge overlapping tools. Put detail in tool results only when asked for (chapter 5 on output shaping and pagination). Changing the tool list changes the start of the prompt and breaks the cache, so change it deliberately. Chapter 8 notes that servers using the Model Context Protocol (MCP) should return tools in a deterministic order for this reason.

Pack to a budget, then order

When you assemble context from candidates (retrieved passages, memory items, tool outputs), treat it as a small optimisation problem. Maximise relevance within a token budget. A greedy rule, relevance per token with a minimum relevance floor, works well and is easy to explain. Then order what you chose. Accuracy tends to be best for material at the beginning and end of a long input. So put the strongest items at the edges and the weakest in the middle. The packing code below includes a required item (the order being discussed), refuses weak matches even when there is room, and shows two budgets.

from llm import count_tokens

ITEMS = [  # (id, kind, relevance 0..1 from a retriever, text)
    ("policy-refunds",  "doc",  0.92, "Refunds over 10000 cents need a human approver. " * 6),
    ("policy-shipping", "doc",  0.31, "Standard shipping takes 3 to 5 working days. " * 12),
    ("order-A100",      "tool", 0.88, "Order A-100: kettle, 4200 cents, delivered 2 March, card ending 4411. " * 3),
    ("order-A101",      "tool", 0.12, "Order A-101: toaster, 3100 cents, in transit. " * 3),
    ("faq-returns",     "doc",  0.64, "Items can be returned within 30 days if unused. " * 20),
    ("faq-giftcards",   "doc",  0.18, "Gift cards never expire and cannot be refunded. " * 25),
    ("ticket-history",  "tool", 0.75, "Customer wrote twice about a dented lid. Agent promised a call back. " * 8),
]

def pack(items, budget, must=()):
    """Greedy: required items first, then best relevance per token until the budget is spent."""
    chosen, used = [], 0
    for it in items:
        if it[0] in must:
            chosen.append(it); used += count_tokens(it[3])
    rest = sorted((i for i in items if i[0] not in must), key=lambda i: -i[2] / count_tokens(i[3]))
    for it in rest:
        n = count_tokens(it[3])
        if used + n <= budget and it[2] >= 0.5:          # refuse weak matches even when there is room
            chosen.append(it); used += n
    return chosen, used

def order(chosen):
    """Strongest items at the edges, weakest in the middle: the least-used position."""
    ranked = sorted(chosen, key=lambda i: -i[2])
    return ranked[0::2] + ranked[1::2][::-1]             # best first, second best last, weakest between

for budget in (400, 1000):
    chosen, used = pack(ITEMS, budget, must=("order-A100",))
    print(f"budget {budget}: used {used} tokens")
    for it in order(chosen):
        print(f"   {it[0]:<16} relevance {it[2]:.2f}  {count_tokens(it[3])} tokens")
    dropped = [i[0] for i in ITEMS if i not in chosen]
    print("   dropped:", ", ".join(dropped))

   ticket-history   relevance 0.75  138 tokens
   order-A100       relevance 0.88  53 tokens
   dropped: policy-shipping, order-A101, faq-returns, faq-giftcards
budget 1000: used 503 tokens
   policy-refunds   relevance 0.92  72 tokens

   order-A100       relevance 0.88  53 tokens

Three behaviours are worth noticing. The budget is a ceiling, not a target: the larger budget includes only one more passage because nothing else cleared the relevance floor. The required item is always present, whatever its score. And the ordering puts the strongest passage first and the second strongest last. Relevance scores come from your retriever; if they are poor, packing cannot rescue the result, which is why retrieval quality is measured separately (relevance metrics).

Compress: shrink what is already there

Clear tool results first

The cheapest and safest compression is to replace old tool outputs with a short placeholder. Once an agent has read a 3,000-token file listing and acted on it, it rarely needs the raw text again. If it does, it can call the tool again. Anthropic calls this one of the safest, lightest-touch forms of compaction. The calls and the model's own messages stay, so the story of what was done remains intact, while the bulky evidence goes. Keep the most recent few results, and exclude results that are costly or impossible to reproduce.

Compaction: summarise and restart

Compaction goes further: when the window nears its limit, summarise the history and begin a fresh window with the summary. In Claude Code, according to the same post, the model keeps architectural decisions, unresolved bugs and implementation details. It discards redundant tool output. The agent then continues with the compressed context plus the five most recently accessed files. The art is in what the summary keeps. Anthropic's tuning advice is to maximise recall first. Make sure nothing important is lost, even if the summary is long. Then improve precision by removing what is superfluous. Do it in that order, because a fact dropped by an over-eager summary is gone, while a redundant sentence only costs a few tokens.

Because the summary is itself model output, it must be tested like any other component. The code below does three things. It clears old tool results. It compacts a history using a summariser. And it checks the result against a list of facts that must survive: the sort of decision, bug and ticket number that a successor needs. The two summaries are scripted with ScriptedModel so that the run is reproducible; they stand for a careful summary and a vague one. A real model can produce either.

from llm import ScriptedModel, count_tokens, message_text, text

def size(msgs): return sum(count_tokens(message_text(m)) for m in msgs)

def clear_old_results(msgs, keep=2):
    """Tool-result clearing: swap the raw output of all but the newest results for a stub."""
    idx = [(i, j) for i, m in enumerate(msgs) if isinstance(m["content"], list)
           for j, b in enumerate(m["content"]) if b.get("type") == "tool_result"]
    out = [dict(m, content=[dict(b) for b in m["content"]] if isinstance(m["content"], list) else m["content"]) for m in msgs]
    for i, j in idx[:-keep]:
        out[i]["content"][j]["content"] = "[result cleared to save space; call the tool again if needed]"
    return out

def compact(msgs, summariser, keep_last=2):
    """Replace the history with a model-written summary, keeping the newest turns verbatim."""
    ask = {"role": "user", "content": "Summarise for a colleague taking over. Keep decisions, open bugs, "
                                      "constraints and ids. Drop raw tool output."}
    summary = summariser.complete(msgs + [ask]).content[0]["text"]
    return [{"role": "user", "content": "Summary of earlier work:\n" + summary}] + msgs[-keep_last:]

def tr(i, body): return {"role": "user", "content": [{"type": "tool_result", "tool_use_id": f"t{i}", "content": body}]}
HISTORY = [{"role": "user", "content": "Migrate the orders service off table orders_v1."}]
for i, body in enumerate(["schema dump " * 150, "grep results " * 200, "test log " * 250, "query plan " * 100], 1):
    HISTORY += [{"role": "assistant", "content": [text(f"step {i}")]}, tr(i, body)]

MUST_SURVIVE = ["orders_v1", "do not drop", "migration 0042", "fails on nulls", "ticket OPS-311"]
GOOD = ("Goal: migrate orders off orders_v1. Decision: keep orders_v1 until cutover; do not drop it. "
        "Done: migration 0042 applied. Open bug: backfill fails on nulls in ship_date. Tracking: ticket OPS-311.")
LOSSY = "The agent explored the schema, ran searches and tests, and made good progress on the migration."

print(f"original history: {size(HISTORY)} tokens in {len(HISTORY)} messages")
cleared = clear_old_results(HISTORY, keep=1)
print(f"after clearing:   {size(cleared)} tokens (all {len(cleared)} messages kept)")
for label, summary in (("good summary", GOOD), ("lossy summary", LOSSY)):
    new = compact(HISTORY, ScriptedModel([summary]))
    kept = " ".join(message_text(m) for m in new).lower()
    lost = [f for f in MUST_SURVIVE if f.lower() not in kept]
    print(f"after compaction ({label}): {size(new)} tokens; facts kept {len(MUST_SURVIVE) - len(lost)}/{len(MUST_SURVIVE)}; lost: {lost or 'none'}")

after clearing:   343 tokens (all 9 messages kept)
after compaction (good summary): 332 tokens; facts kept 5/5; lost: none
after compaction (lossy summary): 307 tokens; facts kept 0/5; lost: ['orders_v1', 'do not drop', 'migration 0042', 'fails on nulls', 'ticket OPS-311']

Both approaches cut the history by more than 80 per cent, and the vague summary is even smaller than the good one. A token count would rate the vague summary as the better compaction. Only the survival check shows it has thrown away the migration, the instruction not to drop the old table, and the open bug. The next step could then cheerfully drop orders_v1. Measure compaction by what survives, not by how small it is. In a real system the facts to preserve come from your own failure analysis (error analysis), and the check belongs in your regression suite.

Now step through the whole cycle as the window sees it, including the notes written before the summary.

Step through

One compaction cycle, window by window

  1. A fresh window. The system prompt and tool definitions are most of what is in it. Everything here is cheap and highly relevant.
  2. Work accumulates. Each turn adds the model's message and a tool result. Results grow faster than conversation, because a search or a file read returns far more text than the model writes.
  3. Approaching the trigger. The window is still within its limit, but a large share is old tool output that the agent has already acted on. This is the stage where quality is quietly at risk, long before anything breaks.
  4. The trigger fires. The harness stops the loop and asks for two things: write what must survive to a notes file outside the window, and produce a summary. Writing the notes first means a poor summary cannot lose the key facts for good.
  5. The window is rebuilt. History is replaced by the summary (yellow). The newest few turns stay verbatim, so the agent keeps its immediate footing. The window is a fraction of its previous size.
  6. Work resumes. The agent carries on from the summary and notes, and the window starts growing again. A long task may go through this cycle many times. That is why the quality of the summary is a property of the whole agent, not a detail.

Write: notes outside the window

Compaction is lossy by nature. The complement is to write important things down in a place that survives it. This is structured note-taking, which Anthropic describes as the agent regularly writing notes to storage outside the context window, to be read back later. Examples are a to-do list the agent updates as it works, or a NOTES.md file listing decisions, open questions and next steps. The post tells of an agent playing a long game. It kept tallies across thousands of steps, and it could resume after its window was reset by reading its own notes. The pattern pays off on tasks with milestones, where progress should not depend on one window staying intact.

There are two rules. Notes must be written deliberately: ask the agent to record decisions and open items when they arise, and not only at the moment of crisis. And notes must be read back at the start of each window, which is why the instruction "check your notes first" belongs in the system prompt. The next chapter, Memory: Notes, Retrieval and Skills, covers how to design the notes and when to retrieve rather than load everything. It also covers how to expire what is stale and how to store reusable procedures.

Isolate: spend someone else's window

Some work consumes a lot of context to produce a small answer. Examples are reading forty pages to find the clause that matters, or searching a codebase for a function's callers. Doing it in the main window pollutes it with material that is useless once the answer is known. A sub-agent does the work in its own clean window and returns a distilled result. Anthropic's post notes that a sub-agent may use tens of thousands of tokens or more and return a summary of often 1,000 to 2,000 tokens. The lead agent's window sees only the summary.

The costs are real. Anthropic's multi-agent write-up reports that multi-agent systems used about 15 times the tokens of a chat interaction. The hand-off also loses detail. If the sub-agent's summary leaves out what the lead needed, the lead cannot recover it. Use isolation where the task is wide and the answer is narrow, and give the sub-agent a precise brief and a required output format. Chapter 14 treats the pattern in full, and chapter 9 covers the case where the helper belongs to someone else.

Instructions: the right altitude

The system prompt is the one part of the window you write by hand, and it has its own failure modes. Anthropic describes two opposite ones. One is hard-coded, brittle if-then logic that tries to anticipate every case and breaks on the first surprise. The other is vague guidance that assumes the model shares your context. The target is "the right altitude": specific enough to steer behaviour, flexible enough to leave the model heuristics to reason from. Practical consequences:

  • Start minimal, then add from failures. Begin with the shortest prompt that states the task and run it on realistic cases. Add an instruction only when you see a failure it would fix. Minimal does not mean short; it means no sentence without a reason (chapter 4 for prompts you can test).
  • Prefer canonical examples to rule lists. A few diverse, representative examples carry more than a long list of edge cases. For a model, examples are the pictures worth a thousand words.
  • Separate sections clearly with headers or XML-style tags, so instructions, background, tool guidance and output format are distinguishable.
  • Put standing facts early and the current question last. Early material is also what the prompt cache keeps; the end is where attention is strong.

How context fails

It helps to name the failures, because each points to a different remedy.

Stale or wrong content persists

A mistaken inference, a hallucinated detail or an injected instruction enters the window (or a notes file). It is then treated as fact on every later step. Remedy: write only verified facts to notes, and re-read primary sources for anything consequential (chapter 19).

Distraction

Large piles of plausible-looking but irrelevant text pull the model away from the task, as the distractor experiments showed. Remedy: select, clear, and cap tool output.

Confusion and clash

Too many overlapping tools, or new information that contradicts earlier instructions, leave the model unsure what to follow. Remedy: a small tool set, and when facts change, replace the old statement instead of appending a correction.

Try the dynamics yourself

The widget below runs the same simulator as the earlier table, in your browser. Compare the three policies, then change the average tool result size and see which policy fires first. Set a working ceiling that reflects what you think a good window is for your task. Then notice how many calls run above it under each policy.

Two observations are common. With small tool results, clearing hardly ever triggers within a normal run, so the cheap fix is to cap result sizes in the tools. With large results, clearing fires often and the window oscillates, so compaction's single reset can be calmer. Neither is universally better, and the next section is how to find out for your agent.

Measuring whether it helped

Context policies change behaviour in ways that are hard to predict, so treat each as an experiment.

  1. Fix a task set that includes long runs, not only short ones. Many context failures appear only after thirty steps. See evaluating agents for end-state checks and trajectory review.
  2. Vary one thing: a clearing threshold, a summary prompt, the number of tools. Keep the model, tools and tasks the same.
  3. Record tokens and outcomes together: success rate, input tokens per task, calls per task and peak window size. Also record how often the agent re-did earlier work, which is a sign that something useful was dropped.
  4. Read the traces of failures from the long runs and ask what was in the window at the first wrong step (error analysis).
  5. Test survival for any summary or note: a list of must-keep facts, checked automatically, as in the code above.

State of play, October 2026

Platform features for this are changing quickly, so check the documentation before building on any detail. As documented on 14 October 2026, Anthropic's API offers context editing (behind the beta header context-management-2025-06-27). It clears old tool results on the server before the prompt reaches the model, while your application keeps the full history. Its tool-result strategy is named clear_tool_uses_20250919. It takes a trigger (default 100,000 input tokens), a number of recent tool uses to keep (default 3), an optional minimum amount to clear, and a list of tools to exclude. The docs note that clearing invalidates the cached prefix, so a minimum clear size helps justify the cost. The same page says that server-side compaction is the primary strategy for most long-running conversations and refers to a compact_20260112 edit. A memory tool (chapter 11) is offered for notes that survive resets. Other providers have their own mechanisms, and open-source agent frameworks implement the same moves in their own ways. The concepts in this chapter should outlast the parameter names; the numbers (thresholds, defaults, window sizes) will not.

Systems connection

Context management is memory management under a new name. The window is a fixed-size working set. Evicting old tool results is a cache eviction policy. Compaction is lossy compression with a recovery cost when you get it wrong. Notes files are a write to stable storage that survives a crash. The prompt cache is an ordinary prefix cache with invalidation, so the usual caching rule about what a change invalidates applies word for word. Sub-agents are the familiar trick of spending another worker's memory. For the model-side reason that long inputs are slow and memory-hungry, see the KV cache.

  4. Use the widget to find, for 2,500-token average results, the smallest trigger at which clearing never fires in an 80-turn run. What does that tell you about where to spend effort: policy or tool output size?

Where this sits on the harness-engineering ladder

This chapter is the first rung of a ladder that the path climbs in A10. The harness is everything around the model: how it is prompted, what it sees, which tools it can call and how its results are checked. Rung one is context engineering, which you have just studied: you choose by hand what goes into the window. Rung two is a workflow, where the steps, tools and checks around the model are designed by hand (the tool loop of chapter 2, the coding agent of chapter 18). Rung three is a harness that improves itself: a loop that edits the context or the harness code and keeps the edits that score better on data it was not tuned on.

Two recent papers sit on the third rung. Agentic Context Engineering (ACE; Zhang et al., arXiv 2510.04618, first submitted October 2025) treats the context as an evolving playbook, updated by a cycle of generation, reflection and curation. Its stated aim is to avoid two failures this chapter also covers: concise summaries that drop useful detail, and repeated rewriting that wears detail away. The authors report gains of 10.6% on agent benchmarks and 8.6% on finance tasks. Meta-Harness (Lee et al., arXiv 2603.28052, March 2026) goes a rung further and searches over harness code itself, with a proposer that reads the source, scores and execution traces of earlier candidates through a filesystem. I read both abstracts only, not the full papers, and these numbers are the authors' own claims. A10 chapter 1 climbs the whole ladder, and Artifact 2 of this path builds on it.

Key takeaways

  • Context engineering is curating all the tokens a model sees at each step (instructions, tools, history, results, retrieved text), not only writing a prompt. In an agent the window is rebuilt every turn.
  • Tokens cost money, time and quality. Caching cheapens a growing prefix but does not remove the growth, and any early edit invalidates the cache after it.
  • Context rot is real and well documented, though its mechanism is not settled: use of information degrades as input grows, especially with distractors, and position matters. A big window raises the limit, not the quality.
  • Four moves manage the budget: select (just-in-time retrieval, small tool sets, packing, ordering), compress (clear tool results, compact), write (notes outside the window) and isolate (sub-agents that return summaries).
  • Clear old tool results first, compact when you must, put recall before precision, and test compaction by checking which facts survive, not by how short the summary is.
  • Start with a minimal prompt at the right altitude, add from observed failures, and measure every context policy on long runs with tokens and outcomes together.

Check your understanding

An agent's window after 25 turns is 70% tool results the agent has already acted on. Which first step is the most conservative way to shrink it?

  1. Compact the whole history into a one-paragraph summary
  2. Replace old tool results with short placeholders, keeping the most recent few
  3. Delete the system prompt and tool definitions
  4. Start a new conversation and rely on the user to repeat the context
Clearing old tool results removes bulky evidence while leaving the sequence of calls and decisions intact, and the agent can re-run a tool if it needs the output again. Compaction (option 0) is more lossy and should come when clearing is not enough. Removing the system prompt (option 2) removes the instructions. Starting over (option 3) throws away all state.

Using the cache assumptions of this chapter, a team finds that compaction cut its input tokens by half without caching but only by about 30 per cent with caching. What is the best explanation?

  1. Compaction works better when the cache is disabled because summaries are not cacheable
  2. The cache bills at the same price as uncached input, so nothing changes
  3. Caching increases the number of tokens sent
  4. The keep-everything run was already reading most of its repeated prefix at a small fraction of the price, and each compaction forces part of the prefix to be rewritten at the higher write price
Caching makes the baseline cheaper, so there is less left to save, and compaction changes the prefix, which forfeits cached reads. Option 0 is not the reason (summaries can be cached after they are written once). Option 1 contradicts the discount. Option 2 confuses billing with tokens sent.

You compact a long coding session. The summary is 60% shorter than a competing summary, but the agent afterwards repeats a mistake it had already fixed. What does this most likely show?

  1. The shorter summary dropped a fact the agent needed, so compaction should be judged by which facts survive, not by size
  2. The model needs a larger window
  3. Compaction should be turned off for all coding tasks
  4. The summary should be rewritten to be even shorter
Smaller is not better if it loses a decision or a fixed bug. The right response is a survival check over must-keep facts, tuned for recall before precision. A bigger window (option 1) does not repair the missing fact, abandoning compaction (option 2) overreacts to one instance, and shortening further (option 3) makes the problem worse.

Which result from the context rot studies should most change how you design an agent that retrieves many passages per query?

  1. Models always perform best at the very end of the input, so retrieve as much as possible
  2. Degradation appears only above one million tokens, so shorter contexts are unaffected
  3. Irrelevant text and distractors that resemble the answer reduce accuracy as length grows, so retrieving many near-misses can hurt
  4. Position within the window has no effect on use of information
The Chroma study reported degradation with added irrelevant text and further losses from distractors similar to the answer, with simple tasks and well below the largest windows. Position effects exist (the lost-in-the-middle result), so option 3 is wrong, and no source claims a one-million-token threshold (option 2). Option 0 overstates the position finding and misses the cost of near-misses.

A research agent must read forty long documents and report one number from each. Which design best protects the main window?

  1. Load all forty documents and ask for the table
  2. Give each document to a sub-agent with a precise brief and a fixed output format, and put only the returned numbers in the main window
  3. Summarise every document into a paragraph in the main window
  4. Put the first document in the window and tell the model to recall the others
This is a wide task with a narrow answer, the case for isolation: each sub-agent spends its own window and returns a few tokens. The cost is extra model calls and lost detail, so the brief and format matter. Loading everything (option 0) invites rot; paragraph summaries (option 2) still fill the window with prose; recall from nothing (option 3) is not possible.

You add one new tool to a server at the start of every deployment and notice latency and cost rise for all users, not only those who use it. What is the most likely mechanism?

  1. The tool's code runs on every request
  2. Models become less accurate whenever a tool is added
  3. The tool list is part of the prompt prefix, so changing it invalidates the provider's cached prefix for every conversation that follows
  4. The context window shrinks by a fixed amount per tool
Tool definitions are tokens at the start of the request. Changing them changes the prefix, so cached reads turn into writes until the new prefix is cached. The tool code only runs when called (option 0), accuracy effects depend on overlap and number (option 1), and the window does not shrink (option 3), although the added tokens do consume space.

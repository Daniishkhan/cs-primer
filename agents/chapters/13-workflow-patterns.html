Workflow Patterns

Before an agent decides its own next step, most useful LLM systems are programs where you decide the steps and the model fills them in. This chapter writes the five patterns that cover most of those programs (chaining, routing, parallelising, orchestrator-workers and evaluator-optimiser loops) as plain code, counts what each costs, and explains the way each one fails.

Why this matters

Teams reach for a free-running agent when a six-line workflow would be cheaper, faster, easier to test and easier to explain to an auditor. Knowing the patterns lets you choose the least autonomous design that works, and lets you recognise when a task really does need the loop of chapter 2. The same patterns are the vocabulary for the multi-agent designs of chapter 14, the durable runs of chapter 15 and the workflow lab, so they are worth getting precise.

A workflow is a program with model calls in it

Anthropic's December 2024 essay "Building effective agents" draws a line that this course keeps using. A workflow is a system where LLMs and tools are orchestrated through predefined code paths. An agent is a system where the LLM dynamically directs its own process and tool use. Chapter 0 introduced the distinction; the point here is what follows from it. In a workflow, your code owns the control flow: the order of steps, the branches, the loops and the stopping rule are ordinary Python (or TypeScript, or Go), and the model supplies judgement or language at fixed points.

That ownership buys four things an open-ended agent cannot easily give you.

  • Predictable cost and latency. The number of model calls is bounded by the program, not by the model's mood. You can write the worst case on a whiteboard.
  • Testability. Each step takes input and returns output, so you can test it in isolation, replace the model with a scripted stand-in (as the examples below do), and put an evaluation on each step rather than on a whole opaque run.
  • Inspectability. A reviewer can read the program and see every place a model can influence an outcome. That matters for regulated work such as claims triage, loan documents and medical coding.
  • Containment. A step that can only classify cannot also send an email. Permissions can be narrow because the steps are narrow (chapter 19).

The essay's advice is to find the simplest solution possible and add complexity only when it demonstrably improves outcomes, and to begin with the model APIs directly because many patterns take only a few lines. The rest of this chapter takes that advice literally. Every pattern is shown as code you could paste into a project, with no framework underneath it (chapter 21 covers what frameworks add and hide).

The shared helper

One small class is used by every example. It wraps a model so that each call is logged with its step name and token counts. Token counts here come from the stand-in tokeniser in lab-support/llm.py, which counts roughly four characters per token, so treat them as consistent units rather than real billing numbers. The stand-in model itself (in the optional box) is a single deterministic function that behaves differently depending on the system prompt, which is enough to make every example reproducible.

# flow.py: the one helper every pattern in this chapter shares
import threading, time
from llm import ScriptedModel, text_of

class Flow:
    """Wraps a model so every call is recorded: which step, tokens in, tokens out."""
    def __init__(self, model, latency=0.0):
        self.model, self.latency, self.calls, self.lock = model, latency, [], threading.Lock()

    def ask(self, step, system, user):
        time.sleep(self.latency)                       # stands in for network + generation time
        r = self.model.complete([{"role": "user", "content": user}], system=system)
        with self.lock:
            self.calls.append((step, r.usage["input_tokens"], r.usage["output_tokens"]))
        return text_of(r)

    def report(self, label):
        tin = sum(c[1] for c in self.calls); tout = sum(c[2] for c in self.calls)
        print(f"{label}: {len(self.calls)} model calls, {tin} tokens in, {tout} tokens out")

# fakes.py: ONE deterministic stand-in "model" that behaves differently per system prompt
import json, re
from llm import ScriptedModel

def fake(messages, tools, system):
    u = messages[-1]["content"]
    if system.startswith("EXTRACT"):
        m = re.search(r"\b([A-Z]-\d{4})\b", u)
        return json.dumps({"order_id": m.group(1) if m else None,
                           "issue": "late" if "late" in u or "not arrived" in u else "other"})
    if system.startswith("DRAFT"):
        d = json.loads(u.split("FACTS:")[1].split("\n")[0])
        return (f"Sorry about the wait with order {d['order_id']}. It is {d['status']} and should arrive "
                f"on {d['eta']}. Reply here if it does not.")
    if system.startswith("CLASSIFY"):
        low = u.lower()
        if "refund" in low or "money back" in low: return "refund|0.93"
        if "password" in low or "log in" in low: return "account|0.90"
        if "where" in low or "arrived" in low: return "tracking|0.88"
        return "other|0.41"
    if system.startswith("HANDLE-"):
        return f"[{system[7:]}] handled: " + u[:40]
    return "?"

It is a function from (messages, tools, system) to a reply, wrapped by ScriptedModel, which also records every request and counts tokens. Swap it for get_model(...) from llm.py and the same workflow code talks to a real model.

Prompt chaining: steps in a fixed order, with gates

Prompt chaining splits a task into sequential steps in which each model call processes the output of the previous one. The reason to split is that a model does better on a narrow job with a short prompt than on a wide job with a long one, and a chain turns one hard call into several easy ones. The cost is latency: the steps run one after another. Anthropic's essay describes the trade as exchanging latency for higher accuracy.

The best feature of a chain is the gate: a programmatic check between two steps that decides whether to continue. A gate is ordinary code, so it is cheap, deterministic and testable. It is also where you should put anything you can verify without a model: whether the JSON parses, whether an id exists, whether a number is in range, whether the output names the order it is about.

Here is a support chain. Step 1 (a model call) extracts the order id from a free-text ticket. Gate 1 checks the id exists. Step 2 is a plain database lookup, because fetching a record is not a language task. Step 3 (a model call) writes a reply from the facts only. Gate 2 checks the reply mentions the order and is short.

import json, re
from flow import Flow
from llm import ScriptedModel
from fakes import fake

ORDERS = {"A-1001": {"status": "shipped", "eta": "Friday"}, "A-1002": {"status": "processing", "eta": "Monday"}}

def chain(flow, ticket):
    # step 1 (LLM): extract structured fields from free text
    raw = flow.ask("extract", "EXTRACT order id and issue as JSON", ticket)
    fields = json.loads(raw)
    # GATE 1 (code): stop early if the output is unusable; no later LLM call is spent
    if not fields["order_id"] or fields["order_id"] not in ORDERS:
        return None, "gate 1: no valid order id, ask the customer"
    # step 2 (plain code): a database lookup is not an LLM job
    facts = dict(ORDERS[fields["order_id"]], order_id=fields["order_id"])
    # step 3 (LLM): write the reply from facts only
    reply = flow.ask("draft", "DRAFT a short reply using only the facts", "FACTS:" + json.dumps(facts) + "\n")
    # GATE 2 (code): the reply must mention the order id and stay short
    if facts["order_id"] not in reply or len(reply.split()) > 40:
        return None, "gate 2: draft rejected"
    return reply, "ok"

for ticket in ["My parcel A-1001 has not arrived and it is late.", "Where is my stuff? It is late!"]:
    flow = Flow(ScriptedModel(fake))
    reply, status = chain(flow, ticket)
    print(status, "|", reply)
    flow.report("  cost")
ok | Sorry about the wait with order A-1001. It is shipped and should arrive on Friday. Reply here if it does not.
  cost: 2 model calls, 48 tokens in, 38 tokens out
gate 1: no valid order id, ask the customer | None
  cost: 1 model calls, 17 tokens in, 9 tokens out

The second ticket never names an order, so gate 1 stops the chain after one model call and returns a message asking the customer for the id. Without the gate, step 3 would have been asked to write a reply about None, and a model asked to be helpful about None will often invent an order. A gate converts a silent wrong answer into a loud, cheap, handled one.

That matters because errors compound. If each step is right 90% of the time and steps are independent, a five-step chain is right 0.95, about 59%, of the time (chapter 2 made the same point about agent loops). Gates do not raise the 59%, but they turn many of the 41% from undetected failures into detected ones that you can retry, route to a person or report. Two design rules follow. Keep each step's output in a form a gate can check (structured output, a fixed vocabulary, a short list), as chapter 1 described. And do not chain what one call does well: every added step is another place to fail and another delay.

Routing: choose the path, then follow it

Routing classifies an input and sends it down a specialised path. It works when a task has distinct categories that are better handled separately, because each path can have its own prompt, examples, tools and even model. Two common uses are different handling for different request types (refunds, account problems, tracking) and different cost tiers (easy questions to a small, cheap model, hard ones to a large one).

from flow import Flow
from llm import ScriptedModel
from fakes import fake

# each route = (system prompt for the handler, a made-up cost tier shown in the log)
ROUTES = {"refund": ("HANDLE-refund-careful", "large"), "account": ("HANDLE-account", "small"),
          "tracking": ("HANDLE-tracking", "small")}
THRESHOLD = 0.7

def route(flow, ticket):
    label, conf = flow.ask("classify", "CLASSIFY into refund|account|tracking|other", ticket).split("|")
    if label not in ROUTES or float(conf) < THRESHOLD:       # unknown or unsure: do not guess
        return "human-queue", f"{label} ({conf}) below {THRESHOLD}"
    system, tier = ROUTES[label]
    return flow.ask("handle", system, ticket), f"{label} ({conf}) -> {tier} model"

tickets = ["I want my money back for A-1001", "I cannot log in", "Where is my parcel?",
           "Your driver was lovely", "Refund please, and reset my password"]
flow = Flow(ScriptedModel(fake))
for t in tickets:
    out, why = route(flow, t)
    print(f"{t[:38]:<40} {why:<34} {str(out)[:28]}")
flow.report("total")

Four details in this short program are the whole craft of routing.

  1. A fallback exists. A label outside the table, or a confidence below the threshold, goes to a human queue instead of a guessed handler. "Your driver was lovely" is not a support request, and a router with no other exit would push it into the nearest wrong category.
  2. The threshold is a dial, not a constant. Lower it and fewer tickets reach people but more are misrouted; raise it and the reverse. Choose it from an evaluation, not a feeling (A6 chapter 2).
  3. The labels must be mutually exclusive, and real inputs are not. The last ticket asks for a refund and a password reset. The router picked refund with 0.93 confidence and the password request is silently dropped. Fixes include multi-label routing (run both paths), splitting the input first, or having each handler report what it did not cover.
  4. The router is a model, so it has an error rate. Measure it on labelled examples and look at the confusion between categories, not only overall accuracy. A router that is 95% accurate and wrong mostly on refunds is worse than the number suggests.

Routing by model tier deserves one more sentence. Because the routing call is itself a model call, it must cost much less than the saving it creates. A tiny classifier (even a regular expression or a small trained model, as in course A1) often beats an LLM at this, and the cost-quality curve you can reach this way is the subject of A6 chapter 19.

Parallelisation: sectioning and voting

When the work divides into pieces that do not depend on each other, run them at once and combine the results in code. Anthropic's essay names two variants.

Sectioning
Different independent subtasks run in parallel: one model checks a draft for personal data, another for tone, a third for policy compliance. Each call is narrow and the wall-clock time is that of the slowest.
Voting
The same task runs several times and the answers are combined, usually by majority. It trades tokens for confidence on decisions where a single run is noisy, such as flagging a vulnerability or moderating content.

Sectioning

Model calls spend almost all their time waiting on the network and the generation, so threads are enough to overlap them. (Why that works is the subject of systems chapter 17 and chapter 15.) The first half of the script below runs three checks one after another and then at once, with an artificial 0.2-second delay per call standing in for network time.

Voting, and the trap in it

If a single judge is right 70% of the time and judges err independently, a majority of three is right 78.4% of the time, five 83.7% and nine 90.1%, from the binomial formula in the script. That is the argument for voting and it is correct if the independence holds. The second half of the script tests what happens when it does not: suppose 20% of items are hard in a way that fools every judge together (the same ambiguity, the same missing context). Each judge is still right 70% of the time overall, but now a majority can never exceed the 80% of items that are not hard.

import random, time
from concurrent.futures import ThreadPoolExecutor
from math import comb
from flow import Flow
from llm import ScriptedModel
from fakes import fake

# Sectioning: three independent checks of the same text, run at once
def check(flow, name, text): return name, flow.ask("check-" + name, "HANDLE-" + name, text)
flow = Flow(ScriptedModel(fake), latency=0.2)
text = "Customer asks for a refund and shares a password."
t0 = time.time()
for name in ("pii", "tone", "policy"): check(flow, name, text)
seq = time.time() - t0
flow.calls.clear(); t0 = time.time()
with ThreadPoolExecutor(3) as pool:
    list(pool.map(lambda n: check(flow, n, text), ("pii", "tone", "policy")))
par = time.time() - t0
print(f"sectioning: sequential {seq:.1f}s, parallel {par:.1f}s, same {len(flow.calls)} calls and tokens")

# Voting: n noisy judges, majority wins. A single judge is right 70% of the time (a simulation).
# Independent case: errors are random. Correlated case: 20% of items are "hard" and fool every
# judge together; on the other 80% each judge is right with q = 0.7 / 0.8 = 0.875, so one judge is still 70%.
def vote_accuracy(n, hard=0.0, trials=20000, seed=3):
    rnd, right = random.Random(seed), 0
    q = 0.7 / (1 - hard)
    for _ in range(trials):
        if rnd.random() < hard: continue                     # every judge wrong together
        right += sum(rnd.random() < q for _ in range(n)) > n / 2
    return right / trials
exact = lambda p, n: sum(comb(n, k) * p**k * (1-p)**(n-k) for k in range(n // 2 + 1, n + 1))
print("\njudges  independent errors   exact   20% shared-hard items")
for n in (1, 3, 5, 9):
    print(f"{n:>6}  {vote_accuracy(n):>16.3f} {exact(0.7, n):>8.3f}   {vote_accuracy(n, 0.2):>18.3f}")
sectioning: sequential 0.6s, parallel 0.2s, same 3 calls and tokens

judges  independent errors   exact   20% shared-hard items
     1             0.700    0.700                0.701
     3             0.784    0.784                0.770
     5             0.839    0.837                0.786
     9             0.902    0.901                0.800

The wall-clock gain from sectioning is real (0.6 s to 0.2 s) and the token bill is unchanged, since the same three calls are made. The voting rows show the difference between independent and shared errors. The "independent" column matches the exact binomial values (the small differences are sampling noise from 20,000 simulated trials); the "shared-hard" column flattens at 0.80 however many judges you add. Real LLM judges that share a prompt, a model and a training distribution are more like the second column than the first.

Common misconception

"Five votes are better than one, so nine are better than five." Only if the votes disagree for independent reasons. If the judges share a prompt and a model, they usually share blind spots, and the extra calls buy cost without accuracy. The remedy is diversity you can measure: different prompts, different models or different evidence, then check on a labelled set whether agreement actually predicts correctness.

Parallel fan-out brings the failure modes of any distributed call (networking chapter 16). The slowest branch sets the latency, so one slow call stretches every request, the effect described in reliability chapter 9. Rate limits can reject a burst of simultaneous calls. And you need a rule for partial failure: wait for all, accept a majority, or return what arrived by a deadline. Write that rule down in the code instead of leaving it to whatever the thread pool does.

Orchestrator-workers: when the pieces are not known in advance

Parallelisation needs you to know the parts when you write the program. Often you do not. "Compare the refund policies of the branches in this email" has two subtasks if the email names two branches and nine if it names nine. In the orchestrator-workers pattern a central model call reads the input, decides the subtasks, hands each to a worker call, and a final call synthesises the results. The essay's key distinction from plain parallelisation is that the subtasks are not pre-defined but determined by the orchestrator from the specific input.

import json, re
from concurrent.futures import ThreadPoolExecutor
from flow import Flow
from llm import ScriptedModel

POLICY = {"Leeds": 30, "Derby": 14, "York": 45, "Hull": 28, "Bath": 60}

def model(messages, tools, system):             # stand-in: orchestrator, workers and synthesiser
    u = messages[-1]["content"]
    if system.startswith("PLAN"):                # the plan depends on the INPUT: one subtask per city named
        return json.dumps([{"task": f"Find the refund window for {c}", "city": c}
                           for c in re.findall(r"\b(Leeds|Derby|York|Hull|Bath)\b", u)])
    if system.startswith("WORK"):
        c = re.search(r"for (\w+)", u).group(1)
        return f"{c}: {POLICY[c]} days"
    if system.startswith("SYNTH"):
        facts = sorted(u.splitlines(), key=lambda s: int(re.search(r"(\d+) days", s).group(1)))
        return f"Shortest window: {facts[0]}. Longest: {facts[-1]}."

def orchestrate(flow, request, max_subtasks=6):
    plan = json.loads(flow.ask("plan", "PLAN split the request into independent subtasks as JSON", request))
    if len(plan) > max_subtasks:                 # a budget the orchestrator cannot talk its way past
        plan = plan[:max_subtasks]
    with ThreadPoolExecutor(len(plan) or 1) as pool:
        results = list(pool.map(lambda t: flow.ask("worker", "WORK answer one subtask", t["task"]), plan))
    return flow.ask("synth", "SYNTH combine the findings", "\n".join(results)), len(plan)

for req in ["Compare refund windows in Leeds and Derby.", "Compare refund windows in Leeds, Derby, York, Hull and Bath."]:
    flow = Flow(ScriptedModel(model))
    answer, n = orchestrate(flow, req)
    print(f"{n} subtasks -> {answer}")
    flow.report("  cost")
2 subtasks -> Shortest window: Derby: 14 days. Longest: Leeds: 30 days.
  cost: 4 model calls, 68 tokens in, 55 tokens out
5 subtasks -> Shortest window: Derby: 14 days. Longest: Bath: 60 days.
  cost: 7 model calls, 124 tokens in, 112 tokens out

The same program handled two cities with four calls and five cities with seven calls: planner, one worker per subtask, synthesiser. The line plan[:max_subtasks] deserves attention. The number of workers is chosen by a model, so cost is now partly model-controlled, and the cap is a limit that lives in code where the model cannot argue with it. Without it, an over-eager plan multiplies spend; Anthropic's multi-agent research write-up reports that early versions of their system spawned dozens of sub-agents for simple queries before the prompts taught the lead how much effort a query deserved.

Step through

One orchestrator run, over time

  1. The request arrives. The orchestrator reads the input and decides how to split it. Its one job at this point is planning; it does not do the work.
  2. The plan names three subtasks. The count came from the input (three cities), not from the program. Had the request named five, the plan would hold five, up to the cap your code enforces.
  3. Workers start in parallel. Each gets one subtask and its own short prompt. They differ in duration because their tools differ in speed: here the third has a slow page to read.
  4. The slowest worker sets the wait. Two workers are finished but their results cannot be combined until the third returns. This is the tail-latency effect of any fan-out, and the place to put a timeout and a rule for what to do without a result.
  5. The synthesiser merges. One model call receives the worker outputs (not their working) and writes the combined answer. It is the single point where all results meet, so it is also where a missing or contradictory result must be handled.
  6. Answer returned. Five calls were paid for, three were on the path the user waited for. Orchestration costs tokens to buy flexibility and parallel speed.

Two weaknesses follow from the shape. The plan is a single point of failure: a subtask that the orchestrator forgets, or two that overlap, is a flaw no later step can repair, because the workers faithfully do what they are told. And the quality of each worker depends on the brief the orchestrator writes, which is why chapter 14 spends a section on briefs. When workers need to loop, call tools and decide for themselves how long to run, this pattern becomes a multi-agent system, and that chapter picks it up.

Evaluator-optimiser: draft, check, revise

In the evaluator-optimiser pattern one call produces a draft and another judges it against criteria and returns feedback, and the producer revises, repeating until the check passes or a limit is reached. It is the workflow form of a human editor. It earns its cost only under two conditions, both stated in the essay: the criteria are clear enough to check, and feedback demonstrably improves the next draft. If the evaluator cannot tell good from bad, or the producer cannot act on its notes, the loop spends tokens and produces churn.

import re
from flow import Flow
from llm import ScriptedModel

def writer(messages, tools, system):             # stand-in writer: obeys feedback if it gets any
    u = messages[-1]["content"]
    text = "Your order is late."
    if "apologise" in u: text = "Sorry, your order is late."
    if "order id" in u:  text += " Order A-1001 is on its way."
    return text

def rubric(draft):                               # evaluator: here plain code; it could be an LLM judge
    issues = []
    if "sorry" not in draft.lower(): issues.append("apologise")
    if not re.search(r"[A-Z]-\d{4}", draft): issues.append("order id")
    return issues

def refine(flow, task, max_rounds=3):
    prompt, best = task, (99, "")
    for r in range(1, max_rounds + 1):
        draft = flow.ask(f"draft{r}", "DRAFT", prompt)
        issues = rubric(draft)
        print(f"  round {r}: {draft!r} issues={issues}")
        best = min(best, (len(issues), draft))
        if not issues: return draft, "passed"
        prompt = task + " Fix: " + ", ".join(issues)      # feedback goes back to the writer
    return best[1], "gave up: returning the best draft"

flow = Flow(ScriptedModel(writer))
print(refine(flow, "Reply to a late order.")); flow.report("cost")
print(); flow = Flow(ScriptedModel(writer))
print(refine(flow, "Reply to a late order.", max_rounds=1)); flow.report("cost")
  round 1: 'Your order is late.' issues=['apologise', 'order id']
  round 2: 'Sorry, your order is late. Order A-1001 is on its way.' issues=[]
('Sorry, your order is late. Order A-1001 is on its way.', 'passed')
cost: 2 model calls, 22 tokens in, 19 tokens out

  round 1: 'Your order is late.' issues=['apologise', 'order id']

The first run passes on the second draft because the feedback names two concrete defects and the writer can fix both. The second run, limited to one round, shows the exit nobody should forget: when the budget ends before the check passes, the function returns the best draft it has and says so, instead of looping or pretending success.

Step through

A two-round revision loop

  1. Round 1: a first draft. The writer produces something short and incomplete, as first drafts often are.
  2. The evaluator checks the rubric. The rubric is code here, so it is free, exact and repeatable. It returns a list of named defects, not just "fail".
  3. Feedback goes back. The defects are added to the next prompt. Feedback that is specific is what makes a second draft better than a second random sample.
  4. Round 2: a revised draft. The writer fixes both named issues.
  5. The check passes. No issues remain, so the loop has a reason to stop other than running out of rounds.
  6. The loop ends, and records how. Always keep the stopping reason (passed, out of rounds, no improvement) in the result so downstream code and humans can tell a verified answer from a best effort.

Three cautions apply. First, prefer a programmatic evaluator wherever one exists: tests that run, schemas that validate, totals that reconcile, a link that resolves. A model judge can be wrong and is biased toward longer answers and toward its own style (A6 chapter 3); when you must use one, give it a binary rubric. Second, a loop can optimise the evaluator instead of the goal: a writer that learns to include the string "Order A-1001" whether or not it is true passes the rubric above while saying something false. Make the evaluator check what matters and keep a held-out check the loop cannot see (A7 chapter 15 takes this much further). Third, set two limits, a maximum number of rounds and a minimum improvement per round, because a loop with a noisy judge will otherwise wander.

Choosing, combining and costing

The patterns compose, and real systems do. A router sends a ticket to one of three chains; one chain contains an orchestrator-workers step; the final draft goes through an evaluator loop. Each composition multiplies the number of ways to fail, so compose only when each added pattern earns something measurable. The table summarises what each pattern buys and where it hurts.

Two readings are worth making before moving on. At 90% per-call reliability a chain of five falls to 59%, while a loop with an evaluator that catches 80% of bad drafts rises above the single call; the price is about twice the calls. And voting at five judges only looks good when the hard-item share is low. Push the slider up and the voting row stops improving, which is the bar chart above in interactive form.

Analogy: a recipe and a chef

A workflow is a recipe: the steps are written down, anyone can follow them, and you know before you start roughly what it will cost and how long it will take. An agent is a chef given a pantry and a dish to make, who decides what to do next from what they see. For a dinner you cook every Tuesday the recipe wins. For a pantry you have never seen and a guest with unusual allergies you want the chef.

Where it breaks down: a recipe is followed by a person who understands the goal and notices when the oven is cold. The model inside a workflow step follows its instruction literally and cannot tell that the step before it produced nonsense, which is why gates exist.

When to stop using a workflow

A workflow stops being the right shape when you cannot write the control flow down: the number of steps depends on what the earlier steps discover, the next action depends on environment feedback, or the branches are too many to enumerate. Debugging a failing build, researching an open question and driving a browser all have that character. That is where the loop of chapter 2 belongs. A useful discipline is to move in small steps: build the workflow first, find the places where it needs a decision you could not pre-program, and let only those places become agentic.

State of play, October 2026

The five patterns come from a December 2024 essay and have proved stable: later vendor guidance and framework documentation still organise their examples around chaining, routing, parallelisation, orchestrators and evaluator loops. What changes quickly is the surrounding menu. Model tiers and their prices shift (the essay's own routing example names specific small and large models and has been revised since), providers add features such as structured outputs, parallel tool calls and server-side caching that make individual steps cheaper, and orchestration frameworks come and go. Keep the patterns in your head and the vendor details in a configuration file you can change.

Running workflows in production

Because a workflow is a program, the habits of running programs apply, and several are easy to forget when the program contains a model.

  • Timeouts and retries per step. Each model call can hang or fail. Give every call a timeout, retry only failures that are safe to repeat, and use backoff with jitter (networking chapter 16). A retry of a step that has side effects needs an idempotency key (distributed chapter 17).
  • Make state explicit. If a chain of eight steps fails at step six, you want to resume at step six rather than pay for one to five again. That means storing each step's output, which is the beginning of durable execution, and the same reasoning as a saga's compensations (architecture chapter 15).
  • Trace every step. Record the step name, inputs, outputs, tokens and latency as spans (reliability chapter 6, A6 chapter 17). The Flow helper in this chapter is a ten-line version of that idea, and it is what let each example print its own cost.
  • Evaluate per step as well as end to end. If the final answer is wrong, a per-step evaluation tells you whether extraction, routing or drafting failed. Without it you debug one opaque number (A6 chapter 1).
  • Version the prompts with the code. A prompt is part of the program (chapter 4); review it, test it and roll it out like any other change.

Systems connection

These patterns are old ideas wearing new components. A chain with gates is a pipeline with validation between stages; sectioning is fork-join with all the tail-latency consequences of reliability chapter 9; orchestrator-workers is the master-worker shape of batch systems (data chapter 18); and a durable multi-step workflow is a saga. What is new is only that a step is probabilistic, so every edge needs a check you would not bother with between two deterministic functions.

Key takeaways

  • A workflow keeps control flow in your code and uses the model at fixed points. It gives bounded cost, testable steps and a program a reviewer can read.
  • Chain when the steps are known; put gates between steps so a bad output stops cheaply. Errors compound, so five steps at 90% each are right about 59% of the time.
  • Route when categories are distinct. Always provide a low-confidence exit, expect multi-intent inputs, and measure the router.
  • Parallelise independent sections to cut waiting time at the same token cost; vote to buy confidence, but correlated errors cap the gain no matter how many judges you add.
  • Use orchestrator-workers when the subtasks depend on the input. Cap the fan-out in code, and treat the plan and the synthesis as the weak points.
  • Use evaluator loops only with clear criteria and useful feedback; prefer programmatic checks; limit rounds; return the stopping reason.
  • Workflows are programs: timeouts, idempotent retries, stored step outputs, tracing and per-step evaluation all apply.

Check your understanding

A five-step chain has independent steps that are each correct 90% of the time. Roughly how often is the final output correct, and what do gates change?

  1. About 90%, because the weakest step sets the limit; gates make no difference
  2. About 59%; gates do not raise it but can turn many undetected failures into detected, handled ones
  3. About 41%; gates raise it to 90% by repeating the model call
  4. About 99%, since five chances to be right compound in your favour
0.9 to the fifth power is about 0.59: every step must be right. A gate does not make a step more accurate, but it stops the chain when an output is unusable, so the failure is caught early and handled. Errors do not average out, so the first and last options are wrong; repeating a call is voting, not gating.

A router is 95% accurate overall. A ticket reads "Refund my order and also change my password" and is sent to the refund handler, which ignores the password request. Which change addresses the cause?

  1. Raise the confidence threshold to 0.99
  2. Use a larger model for the router
  3. Add more refund examples to the refund handler's prompt
  4. Support multi-intent inputs: split the ticket or run both paths, and have handlers report what they did not cover
The router returned a confident single label for an input that has two intents, so the problem is the design (mutually exclusive labels), not accuracy or confidence. A threshold may even leave this case alone because the router was confident. A larger router still picks one label. Refund examples improve the handler, not the dropped request.

Five LLM judges using the same prompt and model each label items correctly 70% of the time. Majority voting gives only a small gain. What is the most likely reason?

  1. Their errors are correlated: the same hard items fool all of them, so the vote cannot fix those
  2. Five is an even number, so ties destroy the result
  3. Majority voting never helps when the base accuracy is above 50%
  4. The judges run in parallel, which reduces accuracy
The binomial gain assumes independent errors. Judges sharing a prompt and model share blind spots, and the share of items that fool all of them is a ceiling on the vote. Five is odd, so ties are not the issue; voting does help above 50% when errors are independent; and running in parallel affects latency, not accuracy.

What most clearly separates orchestrator-workers from plain parallelisation?

  1. Orchestrator-workers uses more than one model call
  2. Orchestrator-workers always runs its workers one after another
  3. In orchestrator-workers a model decides the subtasks from the specific input at run time, rather than you fixing them in the program
  4. Orchestrator-workers does not need a combining step
Both use several calls, both can run workers in parallel, and both need a combining step. The difference is who determines the parts: the programmer (parallelisation) or a model reading the input (orchestrator-workers). That flexibility is why the fan-out needs a cap in code.

An evaluator-optimiser loop drafts customer replies. Reviews show drafts barely change between rounds and the judge passes or fails almost at random. What does this suggest?

  1. Add more rounds so the loop has time to converge
  2. The conditions for the pattern are not met: the criteria are not checkable or the feedback is not actionable, so use a programmatic check or drop the loop
  3. Switch the evaluator to the same model as the writer
  4. Remove the round limit to stop the loop ending early
The pattern pays off only when criteria are clear and feedback improves the next draft. A near-random judge and unchanging drafts show neither holds, so more rounds only add cost. Using the same model as writer and judge tends to add self-preference bias, and removing the limit invites endless loops.

Three independent checks, each taking 4 seconds and 1,000 tokens, are changed from sequential to parallel. What happens?

  1. Time drops to 4 seconds and tokens drop to about 333
  2. Time stays at 12 seconds but tokens drop
  3. Both time and tokens triple
  4. Time drops to roughly 4 seconds (the slowest check) while tokens stay at 3,000; the cost moves to concurrency and rate limits
The same three calls are made, so the token bill is unchanged. Waiting time becomes the slowest call plus small overheads. What gets worse is the burst: three simultaneous requests can hit rate limits, and one slow branch holds up the combined result.

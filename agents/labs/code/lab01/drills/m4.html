The whole state of an agent loop is its list of messages, which is why a run can be saved, replayed and inspected. That only works while the list is valid at every exit: a provider rejects a history in which a tool request from the assistant is not answered by a matching result in the very next user message.

check_pairing(messages) returns the problems, each starting message <index>: and naming the id. agent_loop follows the six steps in its docstring, using LoopGuard and run_tool, and appends reply.as_message() exactly as received. All results for one assistant turn travel in one user message, in call order. The trap is a forced stop: when the guard objects, or a reply was cut off by max_tokens, do not return at once. Answer every pending request with an error result starting "Not run:", then stop, so the history stays valid.

assistant: tool_use a, tool_use b
user:      tool_result a, tool_result b    (one message, same order)
assistant: text only -> status done

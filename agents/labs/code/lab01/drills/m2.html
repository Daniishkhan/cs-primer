A tool call can fail in several ways, and a loop that crashes on one throws away the whole conversation. So every outcome, good or bad, goes back to the model as a result it can read, and a well-written error lets it fix the next call instead of repeating the last.

run_tool(registry, call) takes one tool_use block, the model's request, and returns one result block built with tool_result. It never raises. Look the tool up, check the arguments with validate_args (already written), and only then run the function: a refund with a bad amount must not execute. A ToolError message was written for the model, so pass it on word for word. Any other exception reports only the tool name and the exception type, because its message may expose internals. A cut-off result must say so, since a silent cut looks like a full answer.

get_order "A-9999"          -> error: the tool's own message
issue_refund amount "all"   -> error: invalid arguments, nothing ran
refund_everything           -> error: unknown tool, real ones listed

The client is the other end of the pipe: it starts the server as a subprocess, writes one line per message and reads one line per reply. Most of the work is handling what can go wrong, and the model never speaks the protocol, so the host (the application running the model) translates in between.

request is where a client earns trust: each way a reply can be wrong gets its own exception, listed in the docstring, so the caller never hangs on a dead server, chokes on a stray print or accepts someone else's answer. notify sends no id and reads nothing, because waiting for a reply to a notification would hang. connect must check that the version the server chose is one the client speaks, and close and raise if not, then send the notification. to_model_tools renames inputSchema to input_schema, and run_tool_use turns a protocol error into an is_error result so the loop never crashes.

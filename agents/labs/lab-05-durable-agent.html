Lab 5: A Durable Agent

Chapter 15 argued that an agent which sends money and email must keep its state outside the process, and that a journal alone is not enough: between doing something and writing it down there is a window that no ordering closes. Arguments about windows are easy to nod along to and hard to get right, so in this lab you build the thing and then try to break it. You write an event-sourced agent loop on an append-only JSONL file, give every tool call an idempotency key that every attempt recomputes identically, add a human approval gate that survives a restart, and survive a crash injector that kills the process at every moment where a process can be killed. The checker does not sample a few crashes. It counts the crash points and kills your agent at each one in turn.

Why this lab matters

Almost every demonstration of an agent that "resumes after failure" kills it once, at a convenient moment, and watches it carry on. The bugs live at the inconvenient moments: after the bank moved the money and before the journal heard about it, halfway through writing a line to disk, or between two tool calls in the same model reply. They are also the bugs that cost money, because the symptom is a customer refunded twice. Here the inconvenient moments are enumerated for you, so a mistake that survives your own testing still fails the check, and you see exactly which crash point exposed it. You will also meet three details that chapters tend to wave at: a torn write (a line half on disk when the power went), the identical tool call made twice in one run (so a tool-call id alone is not a safe name for an attempt), and the difference between a step that is waiting and a step that is failing. The same skills apply to any long-running job that touches the outside world: sagas, payment pipelines, data migrations. The model in the loop only makes the log more important, because a model's reply cannot be recomputed.

Deterministic, offline, standard library only

No network, no real model and no real clock. The "bank" and the "mailer" are plain Python objects in fixtures.py that outlive each agent process and record what really happened; the model is a stand-in that depends only on the messages it is shown. A crash is an exception, Crash, raised by an Injector at the nth crash point (Milestones 3 and 4 try every n) or at random from a seeded generator (Milestone 5). A failure prints the crash point or the seed, and python3 check.py solution 5 12 replays milestone 5 with seed 12 alone. The whole check runs in well under a second on a laptop. Python 3.9 or newer. llm.py is the shared stand-in model module, copied unchanged.

Five milestones, each adding a layer:

  1. The journal: durable one-line appends with fsync, repair of a torn last line, detection of real damage, and rebuild, which folds events back into the message list.
  2. What to do next: next_step, a pure function from the journal to the next move, and idempotency_key, the name of one attempt that every process computes identically.
  3. The durable loop: run, which resumes from the journal, never repeats a recorded result, and survives a kill at every one of 100 crash points.
  4. Approval gates: a refund above a limit waits for a human; the process exits while it waits and a later one resumes, with the decision bound to the exact arguments.
  5. Poison steps and a storm: an attempt counter that lives in the journal, a pause that does not count as a failure, and 40 random crash storms.

Milestone 1: the journal

The journal is a file of events, one JSON object per line, only ever appended to. It is the agent's whole memory: after a restart, nothing else exists. The vocabulary is in the starter's docstring; for this milestone only two types matter. A model event holds the content blocks of a model reply exactly as received, and a result event holds what a tool returned, under the id of the tool_use block that asked for it:

{"type": "model", "content": [{"type": "tool_use", "id": "toolu_1e2061984c", "name": "lookup_order", "input": {"order": 42}}]}
{"type": "result", "id": "toolu_1e2061984c", "output": "order 42: delivered, paid 30.00"}
{"type": "model", "content": [{"type": "tool_use", "id": "toolu_058d8554ee", "name": "refund", "input": {"order": 42, "amount": 20.0}}]}

Two properties make this a good log. It is append-only, so a reader can never see a half-updated state, only a prefix of the truth. And it is one line per event, so the unit of damage is one event. Both depend on getting three details right.

Durability. When Python writes to a file, the bytes go to the operating system's buffers, not to the disk. If the machine loses power before the system flushes them, the write is gone, though your program believed it was done. fsync asks the operating system to push a file's bytes to the device before returning (files and file descriptors explains the layers). The rule for a journal is that an event counts only once it is durable, so append flushes Python's buffer and then calls os.fsync on every event. The checker replaces os.fsync with a counting wrapper to make sure you did.

The torn write. A crash can strike while a line is being written, leaving the file ending in half a JSON object with no newline. This is a torn write. Two rules deal with it. load treats a last line with no newline as never written (it did not complete, so it is not an event). And append must remove that stump before writing, because otherwise the new event is glued onto the wreckage and both lines are lost. The same call also has to distinguish this normal case from real damage: an unparseable line before the last is not a crash artefact, it is corruption, and skipping it silently would hide lost events. That raises CorruptJournal.

Folding. rebuild(task, log) turns the journal into the message list the model sees. The task is the first user message; each model event is an assistant message; the result events that follow it are gathered into one user message of tool_result blocks, in order. Everything else in the journal (approvals, attempts) is bookkeeping that is not part of the conversation. Notice what this gives you: the messages are never stored, only derived, so there is no second copy that could disagree with the journal. This is the first design rule of chapter 15: log the non-deterministic facts (the model's reply is one), recompute everything derived from them.

Hints try without first
  • json.dumps escapes a newline inside a string as \n, so one event is always one line. Write json.dumps(event) + "\n".
  • To find a torn tail, open the file in binary mode ("rb+"), read it, and check data.endswith(b"\n"). If not, f.truncate(data.rfind(b"\n") + 1) cuts back to the end of the last complete line (and to 0 when there is none).

  • In rebuild, a result belongs in a new user message when the previous message is the assistant's, and in the existing user message otherwise. llm.tool_result(id, output, is_error) builds the block.

def append(path: str, event: Dict[str, Any]) -> None:
    """Add one event to the end of the journal file, durably.

    One line per event: json.dumps(event) + "\\n". The line must be on disk (flush, then os.fsync)
    before append returns: an event counts only once it is durable. If the file's last line is torn
    (a crash left half a line with no newline), cut it off before writing, so the new event does
    not glue itself onto the wreckage. Never rewrite earlier events.
    """
    if os.path.exists(path):
        with open(path, "rb+") as f:                      # cut off a torn last line, if there is one
            data = f.read()
            if data and not data.endswith(b"\n"):
                f.truncate(data.rfind(b"\n") + 1)
    with open(path, "a", encoding="utf-8") as f:
        f.write(json.dumps(event) + "\n")                # json.dumps escapes newlines inside strings
        f.flush()
        os.fsync(f.fileno())                              # on disk before we go on

def load(path: str) -> List[Dict[str, Any]]:
    """All events in the journal, in order. A missing file is an empty journal.

    A last line with no newline is a torn write: it does not count, so leave it out. A line before
    the last that is not valid JSON means the journal is damaged: raise CorruptJournal.
    """
    if not os.path.exists(path):
        return []
    with open(path, encoding="utf-8") as f:
        lines = f.read().split("\n")
    lines.pop()                                           # "" after the final newline, or a torn last line
    events = []
    for number, line in enumerate(lines, 1):
        try:
            events.append(json.loads(line))
        except json.JSONDecodeError:
            raise CorruptJournal(f"line {number} of {path} is not valid JSON") from None
    return events

def rebuild(task: str, log: List[Dict[str, Any]]) -> List[Dict[str, Any]]:
    """Fold the journal into the message list the model sees.

    [{"role": "user", "content": task}], then each "model" event as an assistant message with that
    content, and the "result" events that follow it gathered into ONE user message of tool_result
    blocks (use llm.tool_result(id, output, is_error)), in order. Other event types are not part of
    the conversation. Do not modify the events in `log`.
    """
    messages: List[Dict[str, Any]] = [{"role": "user", "content": task}]
    for ev in log:
        if ev["type"] == "model":
            messages.append({"role": "assistant", "content": ev["content"]})
        elif ev["type"] == "result":
            if messages[-1]["role"] == "assistant":       # the first result after a reply opens a new user message
                messages.append({"role": "user", "content": []})
            messages[-1]["content"].append(tool_result(ev["id"], ev["output"], ev.get("is_error", False)))
    return messages

Milestone 2: what to do next

A restarted process has nothing but the journal, so the first thing it must do is read it and decide what the agent was in the middle of. That decision should be a pure function, one that depends on nothing but the list of events, because pure functions are easy to test exhaustively and impossible to get wrong by forgetting some variable across a restart. next_step(log) returns one of three moves:

The journal ends with…Next moveWhy
nothingask_modelno reply yet
a model reply with tool calls, no results yetrun_tools (all of them)the model decided; the world has not been told
a model reply with two calls and one resultrun_tools (the other one)the process died between two tool calls of one reply
a model reply with tool calls, all with resultsask_modelthe model must see the results
a model reply with no tool callsfinishthe model has answered

The third row is easy to forget: a model may ask for several tools in one reply (parallel calls), and the process can die after the first.

There is a trap in the word "has a result". The stand-in model, like a real one, can make the identical call in two different turns: two refunds of 10.00 for order 7, for two damaged items. The two tool_use blocks have the same name, the same input and, in llm.py, the same id (the id is a hash of both). If you decide "this call is done" by looking for its id anywhere in the journal, the second refund looks complete as soon as the first one is, and the agent silently skips a refund it was asked to make. The rule: a call is done only if its result appears after the model reply that asked for it, so only the results after the last model event count.

The second function is the name of one attempt, the idempotency key: a string the caller attaches to a request so that a service which sees it again can return the first outcome instead of acting twice (a retry after a lost reply is what makes this necessary, and what "exactly once" can honestly mean). The question for an agent is where the key comes from, and the constraint is hard: it must be the same string in every attempt, in every process, with no shared memory. So it can only be computed from the journal. The recipe from the chapter is run_id:seq:tool_use_id:

  • run_id keeps two runs apart (a key store is shared by every run that uses the service).
  • seq, the 1-based number of the model reply that asked, keeps the two identical refunds apart, since they came from different replies.
  • tool_use_id keeps the calls of one reply apart.

A random key, a timestamp or a counter in memory all fail the same way: the restarted process computes a different one, and the bank sees a new request.

def next_step(log: List[Dict[str, Any]]) -> Step:
    """Decide the next move from the journal alone. Only "model" and "result" events matter here.

    - no model event yet: ask the model.
    - the last model reply has tool_use blocks: those whose id has no "result" event AFTER that model
      event are pending. Any pending: run_tools (seq = number of model events so far, calls in the
      order of the blocks). None pending: ask the model.
    - the last model reply has no tool_use block: finish, with the text blocks joined (llm.text_of).

    Careful: a model may legitimately make the identical call (same id) in two different turns. A
    result from an earlier turn must not make the later call look done.
    """
    last = max((i for i, e in enumerate(log) if e["type"] == "model"), default=None)
    if last is None:
        return Step("ask_model")
    seq = sum(1 for e in log if e["type"] == "model")
    uses = [b for b in log[last]["content"] if b.get("type") == "tool_use"]
    if not uses:
        return Step("finish", text=text_of({"content": log[last]["content"]}))
    done = {e["id"] for e in log[last + 1:] if e["type"] == "result"}   # only results AFTER the last reply
    pending = [u for u in uses if u["id"] not in done]
    return Step("run_tools", seq=seq, calls=pending) if pending else Step("ask_model")

def idempotency_key(run_id: str, seq: int, tool_use_id: str) -> str:
    """The key sent with every attempt at one tool call: "run1:2:toolu_ab12cd34ef".

    It must be computable from things already in the journal, so that every attempt, in every
    process, derives the same string; and it must differ between two identical-looking calls made in
    different turns.
    """
    return f"{run_id}:{seq}:{tool_use_id}"

Milestone 3: the durable loop

Now the loop itself. It has the shape of the loop in chapter 2 with one structural difference: it keeps no state between iterations. Each pass loads the journal, asks next_step, does one kind of work and appends what happened. If you find yourself storing the messages, a counter or "the last result" in a variable, the restarted process will not have it. The only variable that survives is the file.

  • finish: return the text.
  • run_tools: for each pending call, compute its key, call tools[name](input, key), and then append the result. A tool that raises ToolError (a business refusal, such as "order is locked") or a name that does not exist becomes an error result the model can read. Any other exception, including a Crash, must propagate: swallowing it would turn a dead process into a live one that carries on in a state it cannot trust.
  • ask_model: if the journal already holds max_calls model replies, raise BudgetExceeded. Otherwise call the model with rebuild(task, log) and append the reply.

The budget check deserves a second look. A counter in a local variable resets to zero when the process dies, so an agent that crashes on its fortieth step restarts with forty fresh steps, and a step that triggers a crash by design gets an unlimited budget. Counting model events in the journal makes the limit survive restarts. (The checker runs a model that never stops asking for tools and expects BudgetExceeded after exactly the allowed number of replies, then again from a fresh process with no model call at all.)

What does "survives" mean precisely? For each crash point the checker asserts five things after the restart: the run finishes after exactly one restart; the world holds exactly the expected number of refunds and emails; the journal is identical to the journal of an uninterrupted run (a stronger statement than the right outcome, since it proves the resumed run took the same decisions); the model was asked at most once more than the journal has replies; and no tool whose result was already in the journal at the moment of the crash was executed again. That last check is "completed tool results are replayed from the log, not re-executed", and it uses keys it derives itself, not yours.

def run(task: str, path: str, model, tools: Dict[str, Callable], run_id: str = "run1",
        max_calls: int = 8, max_attempts: Optional[int] = None, tool_defs: Optional[list] = None) -> str:
    """... (docstring as in the starter) ..."""
    while True:
        log = load(path)                                       # everything comes from the journal
        step = next_step(log)
        if step.kind == "finish":
            return step.text
        if step.kind == "run_tools":
            for call in step.calls:
                key = idempotency_key(run_id, step.seq, call["id"])
                event = {"type": "result", "id": call["id"]}
                tool = tools.get(call["name"])
                try:
                    if tool is None:
                        raise ToolError(f"unknown tool {call['name']!r}")
                    event["output"] = tool(call["input"], key)    # the side effect happens here
                except ToolError as e:
                    event["output"], event["is_error"] = f"error: {e}", True
                append(path, event)                               # ...and only now does the journal know
        else:
            if sum(1 for e in log if e["type"] == "model") >= max_calls:
                raise BudgetExceeded(f"{max_calls} model replies are already in the journal")
            resp = model.complete(rebuild(task, log), tools=tool_defs or [])
            append(path, {"type": "model", "content": resp.content})

This is the version without attempt counting. Milestone 5 adds the attempt bookkeeping around the tool call.

Common misconception

"If I save the conversation after every step, the agent is safe to restart." Saving messages records what the model has seen, not what the world has done. In this lab the sweep without keys is exactly that design, and it duplicates an action at six crash points. The journal is what makes the agent resumable; the key is what makes the resumption safe. Neither does the other's job.

Milestone 4: a human approval that survives a restart

Some actions should not happen without a person: a large refund, a deletion, an email to a customer (chapter 19 gives the security case, and case 6 shows what happens without one). The durability question is narrower: what is the agent doing while it waits? If it holds a process open it holds memory, a connection and a model session for as long as a manager takes to read an email, and it cannot outlive a deploy. With a journal there is a better answer: write the proposal to the journal, exit, and cost nothing. The decision is another event. Whatever process next picks the run up folds the journal and goes on.

An approval gate is a wrapper around a tool. For refunds up to the limit it does nothing. Above it, it looks for a decision on this call, identified by the call's idempotency key:

  1. No decision yet: record an approval_request (key, exact arguments and their digest) unless one already exists, then raise Paused. The run stops; nothing was spent.
  2. The reviewer decides by calling review, which appends an approval event naming the key, the decision and the digest of what they were shown.
  3. The next process runs the same tool again. Now it finds the decision. If the digest differs from the arguments in hand, it refuses. If the decision is a denial, it returns the refusal as the tool's result, so the model can explain it or choose another route. If it is an approval, it makes the call (with the key, so a crash here is safe too).

Three design points are worth stating because each prevents a real failure. The approval is bound to the arguments. digest(args) is eight hex characters of a SHA-256 over the arguments serialised with sorted keys; the reviewer's decision carries the digest they were shown. Without that, an injected instruction could change an amount after it was approved, or a reviewer could approve "a refund" without a particular amount in mind. Approve the action, not the intent. The approval is bound to the call. Two identical large refunds in one run have different keys, so approving the first does not approve the second (the checker tries exactly this). Asking again does not file again. A process that restarts while the reviewer is still thinking will reach the same gate, and must not add a second request.

def gate(fn: Callable, path: str, limit: float) -> Callable:
    """Wrap a tool so that amounts above `limit` wait for a human.

    wrapped(args, key):
      amount = args["amount"]; if amount <= limit, just return fn(args, key).
      Otherwise look in the journal for an "approval" event with this key.
        none yet -> unless an "approval_request" with this key already exists, append one
                    {"type": "approval_request", "key": key, "args": args, "hash": digest(args)};
                    then raise Paused(key).
        found, but its hash differs from digest(args) -> return "error: approval was granted for different arguments".
        found, decision is not "approve" -> return "refused by reviewer: " + its reason.
        found and approved -> return fn(args, key).
    """
    def wrapped(args, key):
        if args["amount"] <= limit:
            return fn(args, key)
        events = load(path)
        verdict = next((e for e in events if e["type"] == "approval" and e["key"] == key), None)
        if verdict is None:
            if not any(e["type"] == "approval_request" and e["key"] == key for e in events):
                append(path, {"type": "approval_request", "key": key, "args": args, "hash": digest(args)})
            raise Paused(key)                                     # the process may now exit
        if verdict["hash"] != digest(args):
            return "error: approval was granted for different arguments"
        if verdict["decision"] != "approve":
            return "refused by reviewer: " + verdict["reason"]
        return fn(args, key)
    return wrapped

def review(path: str, decision: str, reason: str = "", shown: Optional[str] = None) -> Dict[str, Any]:
    """The reviewer's side: answer the oldest approval_request that has no approval yet.

    decision must be "approve" or "deny" (ValueError otherwise). Append and return
    {"type": "approval", "key": <the request's key>, "decision", "reason", "hash": shown or <the request's hash>}.
    `shown` is the hash of what the reviewer was actually shown; leave it out to approve exactly what was
    requested. Raise LookupError when nothing is waiting.
    """
    if decision not in ("approve", "deny"):
        raise ValueError(f"decision must be 'approve' or 'deny', not {decision!r}")
    events = load(path)
    answered = {e["key"] for e in events if e["type"] == "approval"}
    waiting = [e for e in events if e["type"] == "approval_request" and e["key"] not in answered]
    if not waiting:
        raise LookupError("no approval request is waiting")
    req = waiting[0]
    event = {"type": "approval", "key": req["key"], "decision": decision, "reason": reason, "hash": shown or req["hash"]}
    append(path, event)
    return event

Analogy: the ship's logbook

A new watch officer takes over by reading the logbook, not by asking the last officer. If the first officer collapses mid-watch, the second still knows the course, and a standing order such as "no change of course without the captain's signature" waits in the book until the captain signs. The signature names the course it covers, so it cannot be reused for another.

Where it breaks down: a logbook records what was ordered and what was done, but cannot tell you whether the last order was carried out before the officer collapsed. That is the window of this lab, and a ship has no key to turn: the rudder does not remember the order it already obeyed.

Milestone 5: poison steps and a crash storm

A durable agent has one new failure that a forgetful one does not. Suppose a particular step kills the process every time: a tool result that exhausts memory, a parser bug triggered by one attachment. A forgetful agent restarts from the beginning, hits it, dies, and an operator notices. A durable agent dutifully resumes at the step that killed it, dies, resumes, and dies again, indefinitely, billing you for each attempt. This is a poison step, and the defence is an attempt counter kept, like the budget, in the journal.

Before running a pending call, the loop records {"type": "attempt", "seq": …, "id": …, "n": k}. If the process dies, the next one finds the attempt and counts it. When the count reaches max_attempts the loop appends a failed event and raises RunFailed: the run goes to a human queue (a dead-letter queue in messaging terms) and no process touches the poison step again, because a journal that holds a failed event refuses to run.

The subtle part is the interaction with Milestone 4. A run that pauses for approval exits with Paused; the next process starts a new attempt at the same call, and so on until the reviewer decides, perhaps days later. If those pauses counted as failed attempts, a patient reviewer would fail the run. So when a tool raises Paused, the loop appends an attempt_end event before re-raising, and attempts_for counts attempts minus clean ends. A step that is waiting is not a step that is failing, and the counter has to be able to tell them apart.

The last test is the storm. Forty seeded runs, each choosing one of five tasks (including the two that need approvals) and a crash probability of 4 to 10 per cent per crash point, so a typical run is killed several times and some are killed in the middle of recovering from the previous kill. Each must finish with exactly the expected refunds and emails, distinct keys on distinct refunds, a model-call count of at most one more per crash than the journal has replies, and a journal identical to the uninterrupted run's.

def attempts_for(log: List[Dict[str, Any]], seq: int, tool_use_id: str) -> int:
    """How many attempts at this call (seq, id) started and did not end cleanly.

    The number of "attempt" events for the call, minus the number of "attempt_end" events for it.
    """
    mine = [e for e in log if e["type"] in ("attempt", "attempt_end") and e["seq"] == seq and e["id"] == tool_use_id]
    return sum(1 if e["type"] == "attempt" else -1 for e in mine)

In run, the attempt bookkeeping sits around the tool call. The complete loop, with Milestone 5 included, is:

def run(task: str, path: str, model, tools: Dict[str, Callable], run_id: str = "run1",
        max_calls: int = 8, max_attempts: Optional[int] = None, tool_defs: Optional[list] = None) -> str:
    """Run the task to the end, resuming from the journal at `path`. Returns the final answer.

    Repeat: load the journal, ask next_step, and
      finish     -> return the text.
      run_tools  -> for each pending call, in order: compute its key, call tools[name](input, key),
                    and append a "result" event (output; plus "is_error": True for errors).
                    An unknown tool name or a ToolError becomes an error result ("error: unknown tool
                    'x'" / "error: <message>") that the model sees, not an exception. Any other
                    exception (a Crash, say) must NOT be caught.
      ask_model  -> if the journal already holds max_calls model events, raise BudgetExceeded without
                    calling the model. Otherwise model.complete(rebuild(task, log), tools=tool_defs or [])
                    and append the reply as a "model" event with resp.content.

    Write events only through `append(path, event)` and read only through `load(path)` (the module-level
    names), because check.py swaps in versions that crash on purpose. Keep NO state in variables across
    loop iterations: everything comes from the journal. Do not catch Paused.

    Milestone 5 adds max_attempts (None = off, and then no attempt events are written at all):
      before running a pending call, n = attempts_for(log, seq, id). If n >= max_attempts append
      {"type": "failed", "seq", "id", "reason"} and raise RunFailed. Otherwise append
      {"type": "attempt", "seq", "id", "n": n + 1} and then run the tool. If the tool raises Paused,
      append {"type": "attempt_end", "seq", "id"} and re-raise (a pause is not a failure).
      A journal that already contains a "failed" event raises RunFailed at once.
    """
    while True:
        log = load(path)
        if any(e["type"] == "failed" for e in log):
            raise RunFailed("this run was given up on earlier")
        step = next_step(log)
        if step.kind == "finish":
            return step.text
        if step.kind == "run_tools":
            for call in step.calls:
                key = idempotency_key(run_id, step.seq, call["id"])
                if max_attempts is not None:
                    n = attempts_for(log, step.seq, call["id"])
                    if n >= max_attempts:
                        append(path, {"type": "failed", "seq": step.seq, "id": call["id"],
                                      "reason": f"{call['name']} did not finish in {n} attempts"})
                        raise RunFailed(f"{call['name']} did not finish in {n} attempts")
                    append(path, {"type": "attempt", "seq": step.seq, "id": call["id"], "n": n + 1})
                event = {"type": "result", "id": call["id"]}
                tool = tools.get(call["name"])
                try:
                    if tool is None:
                        raise ToolError(f"unknown tool {call['name']!r}")
                    event["output"] = tool(call["input"], key)    # the side effect happens here
                except ToolError as e:
                    event["output"], event["is_error"] = f"error: {e}", True
                except Paused:
                    if max_attempts is not None:
                        append(path, {"type": "attempt_end", "seq": step.seq, "id": call["id"]})
                    raise
                append(path, event)                               # ...and only now does the journal know
        else:
            if sum(1 for e in log if e["type"] == "model") >= max_calls:
                raise BudgetExceeded(f"{max_calls} model replies are already in the journal")
            resp = model.complete(rebuild(task, log), tools=tool_defs or [])
            append(path, {"type": "model", "content": resp.content})

Going further

  • Expiry. An approval request that nobody decides in ten days should lapse into "escalate or cancel", not wait for ever. Add a timestamp to the request (through an injected clock, so the check stays deterministic) and have the gate return a refusal after a deadline. Where does the clock come from after a restart?
  • Snapshots. Reading the whole journal on every pass is quadratic over a long run. Add a snapshot event holding the folded state and the position it covers, and have load start from the latest. Then record a model-generated summary as an event too, as chapter 15 explains: a summary is not reproducible, so it must be journalled, not recomputed.
  • An unkeyed tool. Real email providers sometimes have no idempotency key. Give the mailer a searchable marker (the key in a header) and teach the tool "look before you leap": before sending, search for the marker. What is the new window, and how small can you make it?
  • Two processes at once. A supervisor that mistakenly starts a second process while the first is slow produces two writers on one journal. Add a lease (a lock file with an owner and an expiry) and a fencing token, and remember that a lock alone is not enough, because a paused holder can wake after its lease has expired.
  • Versioning. Write a start event holding a hash of the prompt and the tool schemas, and refuse to resume a run whose hash no longer matches, or replay it with the old parsers. What do you do with runs in flight during a deploy?
  • Swap the file for SQLite. Put the journal in a table with an auto-incrementing sequence and make "append the result and mark the attempt finished" one transaction. Which crash points disappear? Which cannot, and why (see crash recovery)?
  • Compensation. If the email fails permanently after the refund succeeded, what should a saga do? Add a compensate step, journal it, and run the crash sweep over the failure path (sagas).

Systems connection

Every moving part here is older than agents. The journal is a write-ahead log, and fsync is the call that makes it a promise. The torn write is why databases checksum their log records. The window between an effect and its record is the Two Generals problem: you cannot tell a request that failed from a reply that was lost, so the only safe request is one that can be repeated. The key that closes it is the same device Stripe's API uses for payments (see the idempotency case study). The exhaustive crash sweep is a small deterministic simulation in the style of deterministic simulation testing, and the dead-letter queue and attempt counter are standard messaging practice. What is new is only that one of the steps is a language model whose output cannot be recomputed, which is why its replies, and not the messages derived from them, are the journal's central entries.

What you learned

  • A journal is an append-only file of events, durable only if each append is flushed and fsynced. A torn last line is a normal crash artefact (ignore it, then cut it off before appending); a bad line in the middle is damage and must be loud.
  • The next move is a pure function of the journal. A call is done only if its result follows the reply that asked for it, because a model can make the identical call twice.
  • The window between an effect and its record cannot be closed by ordering. It is closed by an idempotency key computed from journal contents (run_id:seq:tool_use_id), so every attempt, in every process, sends the same one.
  • The loop keeps no state between iterations; budgets and attempt counts are counted from the journal so a crash cannot reset them.
  • An approval gate is a pair of events bound to the call's key and the digest of its exact arguments. The agent exits while waiting and costs nothing, and a denial or mismatch returns to the model as a result.
  • A step that is waiting is not a step that is failing. Poison steps need an attempt counter in the journal and a dead-letter exit; clean pauses must not count against it.
  • Test recovery by enumerating crash points, not by sampling convenient ones: the six that mattered here were invisible to any hand-picked crash.

Check your understanding

In the sweep without idempotency keys, which crash point lets the bank refund twice?

  1. refund:before: the process dies before the bank is called
  2. refund:after: the bank acted but the process died before the result was journalled
  3. append:after of the result event: the event is on disk and the process dies
  4. model:before of the next turn
After the bank acts and before the result is durable, the journal says the refund is still pending, so the restarted process makes the call again, and with no key the bank cannot tell. Before the call nothing has happened yet. After the result is on disk the journal already says it is done, and a crash before the next model call resumes there.

next_step decides a call is done if its tool_use id appears in any earlier result event. The model asks for the identical refund in two consecutive turns. What goes wrong?

  1. Nothing: the id is unique to the call
  2. The second refund is attempted twice
  3. The agent never executes the second refund, because the first one's result makes it look finished
  4. The journal becomes corrupt
The id is a hash of the tool name and input, so identical calls share it. Looking anywhere in the journal makes the second call appear done as soon as the first completes, and the customer is refunded once instead of twice. Only results after the reply that asked count. It also explains why the key includes seq.

After a crash, load finds a last line that is half a JSON object, with no newline. What should the journal layer do?

  1. Raise CorruptJournal so a human looks at it
  2. Ignore the line in load, and cut it off in the next append
  3. Parse as much of it as possible and keep that event
  4. Delete the whole journal and start again
A last line without a newline is a write that never completed, so it is not an event. Dropping it recovers the state as of the last complete event, and truncating it before the next append stops the new event being glued onto it. Raising would turn an ordinary crash into an outage; partial parsing invents events. Damage in the middle of the file is different and does raise.

A run pauses for approval, and the reviewer takes four days. The run is restarted by a supervisor every hour meanwhile, with max_attempts=3. Why does it not fail?

  1. Each pause appends an attempt_end event, so attempts_for returns to zero
  2. The attempt counter is held in memory and resets on restart
  3. Approvals are exempt from attempt counting because they are tools of type refund
  4. The gate records approvals as results, so the attempt is complete
The loop records an attempt before every call, and when the tool raises Paused it records the end of that attempt before exiting. The count is attempts minus clean ends, so waiting never accumulates. A counter in memory would reset on restart, which is the bug the journal exists to prevent, and nothing in the design exempts any tool.

A reviewer approves a refund of 30.00 shown in the console. Before the approval is processed an injected instruction changes the model's next attempt to 3000.00. What stops the larger refund?

  1. The reviewer's login
  2. The bank's idempotency store
  3. The model's system prompt
  4. The approval carries the digest of the arguments it covered, and the gate refuses when the digest of the arguments in hand differs
Approval is bound to the exact arguments by hash, so approving one amount cannot release another. The login proves who approved, not what; the bank's store matches keys, not intent; prompts are exactly what an injection overrides.

In a crash sweep the journal of the resumed run must equal the journal of an uninterrupted run, not merely produce one refund. Why is that the stronger check?

  1. Because it is faster to compare journals than bank balances
  2. Because uninterrupted runs never contain approval events
  3. It shows the resumed run took the same decisions in the same order, so nothing was lost, repeated or reordered even where the world's state would hide it
  4. Because the bank stores the journal
Two runs can end with one refund in the bank while one of them asked the model an extra question, journalled an event twice or skipped a step. Comparing journals catches all of these. Speed is not the reason, approval events appear in both journals, and the bank has its own store of keys, not the journal.

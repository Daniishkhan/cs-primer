Lab 3: An MCP Server & Client

Chapter 7 showed you the messages of the Model Context Protocol and a hundred-line server that spoke them. Reading a protocol is not the same as implementing one: the interesting failures live in the details, such as a reply with no newline, an id of the wrong type, a validation error returned the wrong way, or a client that waits for an answer to a notification. In this lab you write both ends of an MCP connection over stdio, a server for an order desk and a client that drives it, and a checker feeds the server raw JSON lines and compares every reply field by field. The last milestone teaches the same server the stateless style of the 2026-07-28 revision, so that it answers old and new clients from one process.

Why this lab matters

Most people meet MCP as a line in a configuration file: a command, some arguments, and tools that appear in a host. When it breaks, the symptoms are vague (a server that "does not connect", a tool that never shows up, a host that hangs) and the cause is one of a small number of wire-level mistakes. You will make each of those mistakes' opposites on purpose: logging to the wrong stream, answering a notification, using a protocol error where the model needed a tool error, or remembering something between requests that the protocol says you must not. After this lab the message layer is a program you wrote rather than a diagram you read, and the production chapter's argument about sessions and statelessness is something you have implemented twice, once each way. The same skill transfers to every protocol of this shape: the Language Server Protocol, the Debug Adapter Protocol and most JSON-RPC services speak in the same envelopes.

Deterministic, offline, standard library only

No network, no real model and no clock. The server and client talk through real operating-system pipes (subprocess), but everything they say is fixed, so a run gives the same result every time. The only randomness is in property checks (random ids, random message sequences, every truncation of a valid line); a failure prints the seed, and python3 check.py solution 2 17 replays milestone 2 with seed 17 alone. The whole check takes well under a second. Python 3.9 or newer. llm.py is the shared stand-in model module, copied unchanged; the client milestone uses it to feed MCP results to a scripted model.

State of play, October 2026: which specification this follows

Milestones 1 to 5 follow revision 2025-11-25 of the MCP specification (the handshake-based protocol most SDKs and servers still speak, and the one chapter 7 uses). Milestone 6 follows revision 2026-07-28. I read its changelog and the pages on versioning, base protocol and discovery at modelcontextprotocol.io on 14 October 2026 and implemented what they state for stdio: no initialize handshake, io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities required in every request's _meta, a mandatory server/discover, a required resultType, ttlMs and cacheScope on list and read results, UnsupportedProtocolVersion as code -32022 with a supported list, resource-not-found moving from -32002 to -32602, and ping removed. A dual-era server, which the versioning page explicitly allows, picks its behaviour from how the client opens: modern _meta means stateless, an initialize request means the old session.

Not implemented, on purpose: the HTTP-only parts (the Mcp-Method and Mcp-Name headers, Origin checks), multi round-trip requests (input_required), the tasks extension, subscriptions/listen, logging, and the MissingRequiredClientCapability error (-32021). The pages I read did not label the revision a draft, but the changelog text still says "this draft" in one place, so check the status at the changelog before relying on any detail. One choice is mine, not the specification's: supportedVersions lists only 2026-07-28, because the legacy versions are reached through initialize, not through per-request _meta.

Six milestones, each adding a layer:

  1. Messages on a line: build and parse JSON-RPC envelopes, classify requests, notifications and responses, answer every kind of malformed input with the right error, and run the read-reply loop with correct framing.
  2. The handshake: initialize, version negotiation, notifications/initialized, and the rule that nothing else is served before the handshake completes.
  3. Tools: tools/list and tools/call, with the split between errors the client program must handle (JSON-RPC errors) and errors the model can read and fix (isError).
  4. Resources: resources/list and resources/read, then a sweep that sends every kind of mistake to a live server and checks every code.
  5. The client: a subprocess client with id matching and failure handling, tested against a separate fixture server, then end to end against yours, and a bridge that lets a model loop call MCP tools.
  6. The stateless style: answer requests that carry their own version and capabilities, with no handshake, server/discover, caching hints and the new error codes, beside the old protocol on the same process.

Milestone 1: messages on a line

Over stdio, MCP sends JSON-RPC 2.0 messages (a small standard for calling procedures with JSON) one per line. There are exactly three kinds of message, told apart by which members they have:

KindHasReply?Example
requestmethod and idexactly one response, with the same id{"jsonrpc":"2.0","id":1,"method":"ping"}
notificationmethod, no idnever, not even an error{"jsonrpc":"2.0","method":"notifications/initialized"}
responseresult or error, and idnever (it answers something you sent){"jsonrpc":"2.0","id":1,"result":{}}

MCP adds rules on top of JSON-RPC: an id is a string or an integer and, unlike base JSON-RPC, must not be null; and the 2025-06-18 revision removed JSON-RPC batching, so an array is not a valid message. A server that cannot make sense of a line still has to answer in kind, using the standard codes:

CodeNameWhen this lab uses itid in the response
-32700Parse errorthe line is not JSON (a truncated message, a stray banner)null
-32600Invalid RequestJSON, but not one valid message: an array, wrong or missing jsonrpc, bad id, method not a string; also "not initialised"the id if it could be read, else null
-32601Method not founda valid request for a method the server does not havethe request's id
-32602Invalid paramsthe method exists but its parameters are wrong (unknown tool, no uri)the request's id
-32603Internal erroryour code raised an exception it did not expectthe request's id

Two details decide whether a client can talk to your server at all. First, framing: the reply must be one line, so it is encoded with no spaces after separators and no raw newline (json.dumps escapes any newline inside a string as \n, so one message is always one line). Second, flushing: a pipe is buffered, so a reply written but not flushed sits in your process while the client waits for it for ever. That is the most common reason an MCP server "hangs", and the check counts your flushes.

A third rule is about trust. When your own code fails with an exception you did not expect, the client gets -32603 and a fixed message; the exception text goes to stderr (see log), not to the wire, because internal messages tell an attacker how your server is built (untrusted input works in both directions).

Hints try without first

def result_message(id: Any, result: Dict[str, Any]) -> Dict[str, Any]:
    """A JSON-RPC success response."""
    return {"jsonrpc": "2.0", "id": id, "result": result}

def error_message(id: Any, code: int, message: str, data: Any = None) -> Dict[str, Any]:
    """A JSON-RPC error response; `data` is included only when it is not None."""
    err: Dict[str, Any] = {"code": code, "message": message}
    if data is not None:
        err["data"] = data
    return {"jsonrpc": "2.0", "id": id, "error": err}

def encode(msg: Dict[str, Any]) -> str:
    """One message as one line: compact JSON, and no newline inside (json.dumps escapes them)."""
    return json.dumps(msg, separators=(",", ":"))

def parse_line(line: str) -> Dict[str, Any]:
    """Parse one line into a message dict, or raise RpcError.

    -32700 if the line is not JSON. -32600 if it is JSON but not a valid single message: an array
    (MCP does not allow batches), not an object, "jsonrpc" not "2.0", a "method" that is not a
    string, an "id" that is null, boolean, float or anything but a string or integer, "params"
    that is not an object, or an object with neither "method" nor "result" nor "error".
    When the id could be read, put it on the RpcError (id=...), otherwise leave it None.
    """
    try:
        msg = json.loads(line)
    except json.JSONDecodeError:
        raise RpcError(PARSE_ERROR, "Parse error") from None
    if isinstance(msg, list):
        raise RpcError(INVALID_REQUEST, "Invalid Request: batches are not supported")
    if not isinstance(msg, dict):
        raise RpcError(INVALID_REQUEST, "Invalid Request: a message must be a JSON object")
    mid = msg.get("id")
    readable = mid if isinstance(mid, (str, int)) and not isinstance(mid, bool) else None
    if msg.get("jsonrpc") != "2.0":
        raise RpcError(INVALID_REQUEST, 'Invalid Request: "jsonrpc" must be "2.0"', id=readable)
    if "id" in msg and readable is None:
        raise RpcError(INVALID_REQUEST, "Invalid Request: id must be a string or an integer")
    if "method" in msg:
        if not isinstance(msg["method"], str):
            raise RpcError(INVALID_REQUEST, "Invalid Request: method must be a string", id=readable)
        if "params" in msg and not isinstance(msg["params"], dict):
            raise RpcError(INVALID_REQUEST, "Invalid Request: params must be an object", id=readable)
    elif "result" not in msg and "error" not in msg:
        raise RpcError(INVALID_REQUEST, "Invalid Request: no method", id=readable)
    return msg

def classify(msg: Dict[str, Any]) -> str:
    """'request' (method and id), 'notification' (method, no id) or 'response' (no method)."""
    if "method" not in msg:
        return "response"
    return "request" if "id" in msg else "notification"

def serve(server: "Server", infile, outfile) -> None:
    """The stdio transport: one reply line per request line, flushed at once, until input ends."""
    for line in infile:
        reply = server.handle_line(line)
        if reply is not None:
            outfile.write(reply + "\n")
            outfile.flush()

def handle_line(self, line: str) -> Optional[str]:
    """One input line in, one output line (or None) out. Never raises.

    Blank lines and client responses get no reply. Notifications go to on_notification and
    get no reply. Requests go to process(method, params): its dict becomes a success response,
    an RpcError an error response (keeping code, message and data), and any other exception a
    -32603 "Internal error" response, with the server still alive for the next line.
    """
    if not line.strip():
        return None
    try:
        msg = parse_line(line)
    except RpcError as e:
        return encode(error_message(e.id, e.code, e.message, e.data))
    kind = classify(msg)
    if kind == "response":
        return None
    method, params = msg["method"], msg.get("params") or {}
    if kind == "notification":
        try:
            self.on_notification(method, params)
        except Exception as e:                   # a notification has nobody to tell
            log("error in notification", method, repr(e))
        return None
    try:
        return encode(result_message(msg["id"], self.process(method, params)))
    except RpcError as e:
        return encode(error_message(msg["id"], e.code, e.message, e.data))
    except Exception as e:
        log("internal error in", method, repr(e))
        return encode(error_message(msg["id"], INTERNAL_ERROR, "Internal error"))

Milestone 2: the handshake

In every revision up to 2025-11-25 an MCP connection begins with a short negotiation (the lifecycle of chapter 7). The client sends initialize, naming the newest protocol version it supports, its capabilities (optional features it offers, such as answering questions from the server) and its identity. The server answers with the version it will use, its own capabilities and its identity. Then the client sends the notification notifications/initialized, and only then does normal work begin.

Version negotiation is a counter-offer, not a refusal. If the client asks for a version the server speaks, the server answers with that version. If not, it answers with the newest version it does speak, and the client decides whether it can live with that or must disconnect. Versions are date strings (2025-06-18, 2025-11-25), so equality is the right comparison and "latest" is just an unknown version.

The specification tells clients not to send anything but pings before the server has answered, and not to send requests before the initialized notification, but it does not say how a server must treat early requests. This lab's rule, which is a design choice and the same one chapter 7's server makes, is: before the handshake completes, serve only initialize and ping; reject the rest with -32600 and a message that says what to do. A second initialize is also -32600. Making the rules explicit and testable is the point: a server that quietly accepts anything is a server whose clients are never told they are wrong.

def on_initialize(self, params: Dict[str, Any]) -> Dict[str, Any]:
    """Validate, negotiate and answer `initialize`.

    protocolVersion must be a string, capabilities and clientInfo objects, else -32602 (and no
    state change). Answer with the client's version if it is in LEGACY_VERSIONS, otherwise the
    newest one. Result: protocolVersion, capabilities (CAPABILITIES), serverInfo (SERVER_INFO).
    """
    ver = params.get("protocolVersion")
    if not isinstance(ver, str) or not isinstance(params.get("capabilities"), dict) \
            or not isinstance(params.get("clientInfo"), dict):
        raise RpcError(INVALID_PARAMS, "initialize needs protocolVersion, capabilities and clientInfo")
    self.client_info = params["clientInfo"]
    self.state = "initialising"
    return {"protocolVersion": ver if ver in LEGACY_VERSIONS else LEGACY_VERSIONS[0],
            "capabilities": CAPABILITIES, "serverInfo": SERVER_INFO}

def on_notification(self, method: str, params: Dict[str, Any]) -> None:
    """notifications/initialized completes the handshake (only after a good initialize).
    Every other notification, known or not, is ignored."""
    if method == "notifications/initialized" and self.state == "initialising":
        self.state = "ready"

def process(self, method: str, params: Dict[str, Any]) -> Dict[str, Any]:
    """Apply the lifecycle rules, then dispatch.

    Modern requests (milestone 6) are handled first. For handshake-era requests: `initialize`
    when already initialised is -32600 "Already initialised"; anything except `initialize` and
    `ping` before the handshake has completed is -32600 "Server not initialised ...".
    """
    meta = params.get("_meta")
    if isinstance(meta, dict) and (K_VERSION in meta or K_CAPS in meta):
        return self.process_modern(method, params, meta)
    if method == "initialize" and self.state != "new":
        raise RpcError(INVALID_REQUEST, "Already initialised")
    if method not in ("initialize", "ping") and self.state != "ready":
        raise RpcError(INVALID_REQUEST, "Server not initialised: send initialize, then notifications/initialized")
    return self.dispatch(method, params)

Milestone 3: tools

A tool is a function the model can ask the host to run. tools/list returns each tool's name, description and inputSchema (a JSON Schema object, in the camel case MCP uses; the model-facing shape in chapter 6 spells it input_schema). tools/call takes a name and arguments and returns content blocks and an isError flag. The part that needs care is what happens when something is wrong, because MCP has two error channels with different audiences:

Protocol errorTool execution error
ShapeJSON-RPC error object: code, message, optional dataan ordinary result with isError: true
Who reads itthe client program, which has a bug or a version problemthe model, which can read the text and try again
In this labunknown tool name, name missing or not a string, arguments not an object, a crash inside your own code (-32603)arguments that fail the schema, a ToolError raised by the tool (such as "no such order")
Test question"Could a model have avoided this by choosing differently?" No."Could the model fix this on its next turn?" Yes, so tell it how.

The 2025-11-25 revision states the second rule explicitly: input validation errors should be reported as tool execution errors, specifically so the model can correct itself. It is the MCP form of the actionable error from tool design. The given check_arguments produces the sentences ('limit' must be an integer, got str; 'status' must be one of shipped, processing, delivered, cancelled; got 'lost'); your job is the routing. Two more details: look tools up in TOOL_FUNCS when the call arrives (the checker swaps in a tool that crashes, to see that the server survives), and never hand out the module's own TOOLS list, because a caller who mutates the result would be editing your server.

def list_tools(self, params: Dict[str, Any]) -> Dict[str, Any]:
    """{"tools": [...]}: TOOLS sorted by name (a stable order helps caches)."""
    return {"tools": sorted(TOOLS, key=lambda t: t["name"])}

def call_tool(self, params: Dict[str, Any]) -> Dict[str, Any]:
    """Run a tool. Protocol faults are RpcErrors (-32602: name missing or not a string, unknown
    tool, arguments not an object). Everything the model can fix is a normal result with
    isError true: arguments that fail check_arguments, or a ToolError from the tool. Any other
    exception from the tool propagates (it becomes -32603). Look tools up in TOOL_FUNCS at call
    time. Success: {"content": [{"type": "text", "text": ...}], "isError": False}.
    """
    name = params.get("name")
    if not isinstance(name, str):
        raise RpcError(INVALID_PARAMS, "tools/call needs a string 'name'")
    tool = next((t for t in TOOLS if t["name"] == name), None)
    if tool is None:
        raise RpcError(INVALID_PARAMS, f"Unknown tool: {name}")
    args = params.get("arguments", {})
    if not isinstance(args, dict):
        raise RpcError(INVALID_PARAMS, "'arguments' must be an object")

    def block(text: str, is_error: bool) -> Dict[str, Any]:
        return {"content": [{"type": "text", "text": text}], "isError": is_error}

    problems = check_arguments(tool["inputSchema"], args)
    if problems:
        return block(f"Invalid arguments for {name}: " + "; ".join(problems), True)
    try:
        return block(TOOL_FUNCS[name](args), False)
    except ToolError as e:
        return block(str(e), True)

Milestone 4: resources, and a sweep of every mistake

A resource is data identified by a URI that the application (rather than the model) chooses to put in context: a file, a record, a schema. resources/list returns descriptors (uri, name, title, mimeType); resources/read takes a URI and returns contents, each with text (or a base64 blob). This server publishes one resource per order, at order://A-1001 and so on, and the text is exactly what order_lookup returns, so the two features always agree (the check asserts it).

Errors again split in two. A URI that is not a string, or is missing, is a malformed request: -32602. A well-formed URI that names nothing is "resource not found": in the 2025-11-25 text the recommended code is -32002, with the URI in data so the client can say which one. Remember that number, because milestone 6 changes it.

Your task

Write Server.list_resources and Server.read_resource.

Milestone 5: the client

The client is the mirror image: it starts the server as a subprocess, writes one line per message, and reads one line per reply. The class gives you the constructor (which starts the process with pipes on stdin, stdout and stderr) and _send; you write request, notify, connect, list_tools, call_tool and close. A good client is mostly careful about what can go wrong, and there are four things:

  • The server writes something that is not JSON. The classic case is a print("ready") in the server: a banner on stdout, the protocol channel. The client reads one line, cannot parse it, and should say so plainly (ValueError, "server wrote non-JSON to stdout") instead of hanging or crashing with a bare JSONDecodeError.
  • The server dies. readline() returns an empty string at end of file. Treat that as ConnectionError, not as an empty reply.
  • The reply has the wrong id. Replies are matched to requests by id. This client has one request in flight at a time, so a mismatch means a protocol bug, and you should raise rather than hand back someone else's answer.
  • The server answers with an error. That is a normal event, not a crash. request raises McpError(code, message, data) so calling code can branch on e.code, and the client stays usable afterwards.

The client also has to decide when a connection is good. connect() sends initialize with the newest version it speaks, reads the reply, and checks that the server's chosen version is one of the client's: a server that counter-offers 1999-01-01 is a server you cannot use, and the right response is to close the process and raise. Then it sends the notification and does not wait for a reply, because there will not be one (a client that waits for the answer to a notification hangs for ever). Shutdown over stdio is polite and has no message: close the server's stdin, wait for it to exit, and kill it only if it does not.

Finally the bridge. The model never speaks MCP (chapter 7): the host translates. to_model_tools turns MCP tool definitions into the shape of the agent loop (inputSchema becomes input_schema), and run_tool_use routes one tool_use block through tools/call and builds the tool_result block for the model. A tool failure arrives as data (is_error true) because the model can act on it; a protocol error becomes an is_error result reading MCP error -32602: Unknown tool: ... so that even then the model sees something instead of the loop crashing. Which errors to show a model is a host policy; this one is the safe default.

def request(self, method: str, params: Optional[Dict[str, Any]] = None) -> Dict[str, Any]:
    """Send a request with the next id, read ONE line, and return its result.

    - no line (end of file): ConnectionError
    - a line that is not JSON: ValueError mentioning "non-JSON"
    - a reply whose id differs from the request's: ValueError mentioning "id"
    - an error reply: McpError(code, message, data)
    Add "<-- " plus the raw line (stripped) to self.trace.
    """
    mid, self.next_id = self.next_id, self.next_id + 1
    msg: Dict[str, Any] = {"jsonrpc": "2.0", "id": mid, "method": method}
    if params is not None:
        msg["params"] = params
    self._send(msg)
    line = self.proc.stdout.readline()
    if not line:
        raise ConnectionError(f"server closed its output before answering {method}")
    self.trace.append("<-- " + line.strip())
    try:
        reply = json.loads(line)
    except json.JSONDecodeError:
        raise ValueError(f"server wrote non-JSON to stdout: {line.strip()!r}") from None
    if reply.get("id") != mid:
        raise ValueError(f"reply has id {reply.get('id')!r} but the request had id {mid}")
    if "error" in reply:
        e = reply["error"]
        raise McpError(e["code"], e["message"], e.get("data"))
    return reply["result"]

def notify(self, method: str, params: Optional[Dict[str, Any]] = None) -> None:
    """Send a notification: no id, and no reply is read."""
    msg: Dict[str, Any] = {"jsonrpc": "2.0", "method": method}
    if params is not None:
        msg["params"] = params
    self._send(msg)

def connect(self) -> Dict[str, Any]:
    """The handshake: initialize (newest of CLIENT_VERSIONS, empty capabilities, clientInfo),
    then notifications/initialized. If the server's protocolVersion is not one of CLIENT_VERSIONS,
    close and raise ValueError. Return the initialize result."""
    result = self.request("initialize", {"protocolVersion": CLIENT_VERSIONS[0], "capabilities": {},
                                         "clientInfo": {"name": "lab-client", "version": "0.1.0"}})
    if result.get("protocolVersion") not in CLIENT_VERSIONS:
        self.close()
        raise ValueError(f"server chose protocol version {result.get('protocolVersion')!r}, which this client does not speak")
    self.notify("notifications/initialized")
    return result

def list_tools(self) -> List[Dict[str, Any]]:
    """The server's tool definitions."""
    return self.request("tools/list")["tools"]

def call_tool(self, name: str, arguments: Dict[str, Any]) -> Tuple[str, bool]:
    """tools/call; return (the text blocks joined with newlines, isError). McpError passes through."""
    res = self.request("tools/call", {"name": name, "arguments": arguments})
    text = "\n".join(b["text"] for b in res["content"] if b.get("type") == "text")
    return text, bool(res.get("isError", False))

def close(self) -> str:
    """Polite stdio shutdown: close the server's stdin, wait up to 5 s (then kill), return its stderr."""
    try:
        self.proc.stdin.close()
    except OSError:
        pass
    try:
        self.proc.wait(timeout=5)
    except subprocess.TimeoutExpired:
        self.proc.kill()
        self.proc.wait()
    return self.proc.stderr.read()

def to_model_tools(mcp_tools: List[Dict[str, Any]]) -> List[Dict[str, Any]]:
    """MCP tool definitions to the model-facing shape of llm.py: name, description, input_schema."""
    return [{"name": t["name"], "description": t.get("description", ""), "input_schema": t["inputSchema"]}
            for t in mcp_tools]

def run_tool_use(client: McpClient, block: Dict[str, Any]) -> Dict[str, Any]:
    """Route one model tool_use block through MCP and return the tool_result block for the model.
    A protocol error (McpError) becomes an is_error result reading "MCP error <code>: <message>"."""
    try:
        text, is_error = client.call_tool(block["name"], block["input"])
    except McpError as e:
        return tool_result(block["id"], f"MCP error {e.code}: {e.message}", is_error=True)
    return tool_result(block["id"], text, is_error=is_error)

Milestone 6: the stateless style

Everything so far remembers. After the handshake the server knows which version was agreed and which capabilities the client has; a pending state of "initialising" lives in a Python attribute. Chapter 8 showed what that costs once a server runs on several machines behind a balancer: half the requests land on a replica that never saw the handshake. The 2026-07-28 revision removes the memory. Every request says who it is and what it needs, and the server keeps nothing between two requests. Here is the change, as verified against the published changelog and base-protocol pages (see the dated note at the top):

A dual-era server serves both worlds from one process, and the versioning page says how it chooses: a request carrying modern _meta is served statelessly; an initialize request selects the old session. That is how you write a server today that works with the clients that exist and with the ones that are coming. The matching client behaviour on stdio is a probe: send server/discover first, and if the answer is not a recognised modern reply or modern error, fall back to initialize (a stretch goal below).

The property that matters is that the modern path touches no state. Nothing in process_modern reads or writes self.state. The check verifies it the strong way: it generates random mixes of modern requests, runs them on one long-lived server, on a brand-new server per request, and in shuffled order on a third server that sometimes receives a legacy handshake in between, and demands that every reply is identical across all three. A single remembered fact anywhere in your code shows up as a difference.

Common misconception

"Stateless means the server stores nothing." It means the protocol stores nothing between requests. If a tool genuinely needs memory (a basket, a draft, a long-running job), the state moves to an explicit handle that the server mints and the model passes back as an ordinary argument, exactly as it passes an order id. The server is free to keep that state in a database; what it may not do is infer it from "this connection" or "this process". The point is that any replica can pick up the next request.

def process_modern(self, method: str, params: Dict[str, Any], meta: Dict[str, Any]) -> Dict[str, Any]:
    """Serve one 2026-07-28 request. It touches no state: nothing here reads or writes self.state.

    - version (K_VERSION) must be a string and capabilities (K_CAPS) an object, else -32602
      "Missing required _meta fields".
    - a version not in MODERN_VERSIONS is -32022 "Unsupported protocol version" with
      data {"supported": MODERN_VERSIONS, "requested": version}.
    - methods: server/discover, tools/list, tools/call, resources/list, resources/read. Anything
      else (initialize and ping included) is -32601.
    - every result gets "resultType": "complete" and "_meta": {K_SERVER: SERVER_INFO}; the list and
      read results and server/discover also carry "ttlMs" and "cacheScope" (see CACHE).
    - a resource that does not exist is -32602 in this era (data still {"uri": uri}).
    - server/discover result: supportedVersions (MODERN_VERSIONS) and capabilities (CAPABILITIES).
    """
    version, caps = meta.get(K_VERSION), meta.get(K_CAPS)
    if not isinstance(version, str) or not isinstance(caps, dict):
        raise RpcError(INVALID_PARAMS, "Missing required _meta fields", {"required": [K_VERSION, K_CAPS]})
    if version not in MODERN_VERSIONS:
        raise RpcError(UNSUPPORTED_VERSION, "Unsupported protocol version",
                       {"supported": MODERN_VERSIONS, "requested": version})
    if method == "server/discover":
        result: Dict[str, Any] = {"supportedVersions": MODERN_VERSIONS, "capabilities": CAPABILITIES}
    elif method in CACHE or method == "tools/call":
        try:
            result = dict(self.dispatch(method, params))
        except RpcError as e:
            if e.code == RESOURCE_NOT_FOUND:
                raise RpcError(INVALID_PARAMS, e.message, e.data) from None
            raise
    else:
        raise RpcError(METHOD_NOT_FOUND, f"Method not found: {method}")
    if method in CACHE:
        result["ttlMs"], result["cacheScope"] = CACHE[method]
    return {"resultType": "complete", **result, "_meta": {K_SERVER: SERVER_INFO}}

Systems connection

Everything in this lab is a classic systems idea in new clothes. A parent process talking to a child through pipes, one message per line, is the oldest remote-procedure shape there is (processes). The split between "the call failed" and "the call succeeded and the answer is an error" is the discipline of API design and timeouts and retries: a client that retries a tools/call after a timeout needs the same idempotency key that any other retried write needs (exactly-once). The move from sessions to stateless requests is the argument for stateless services behind a load balancer. And every string a server returns is input to a model, so the boundary between host and server is one of the trust boundaries a threat model draws, with injection as the attack and chapter 19 of this course as the defence.

What you learned

  • MCP over stdio is JSON-RPC 2.0, one message per line: requests (method and id, one reply), notifications (no id, never a reply) and responses. Framing and flushing are protocol rules, and logs belong on stderr.
  • A server answers every malformed line with the right code (-32700, -32600, -32601, -32602, -32603), echoes the id when it can read one, and never lets an exception escape or leak its text.
  • The 2025-11-25 lifecycle is a three-state machine: initialize, a version counter-offer, the initialized notification, and nothing else served before it. A bad initialize must change nothing.
  • Errors have two audiences. Protocol errors are for the client program; failures the model can fix (bad arguments, a missing order) are normal results with isError and a message that says how to recover.
  • A client must handle a non-JSON line, end of file, a wrong id and error replies without hanging, and it never waits for the answer to a notification.
  • The 2026-07-28 style carries version and capabilities in every request, adds server/discover, resultType, cache hints and -32022, and moves resource-not-found to -32602. A dual-era server picks its behaviour from the shape of the request, and its modern path keeps no state.

A client sends the line {"jsonrpc":"2.0","id":null,"method":"ping"}. What should an MCP server do?

  1. Answer with an empty result and id null, because null is a valid JSON-RPC id
  2. Answer with error -32600 and id null, because an MCP request id must be a string or an integer
  3. Say nothing, because a null id marks the message as a notification
  4. Answer with error -32700, because null cannot be parsed
MCP tightens JSON-RPC: request ids must not be null. The line parses fine, so it is not -32700; it is JSON but not a valid MCP request, which is -32600. A notification is a message with no id member, not one whose id is null, which is why "id" in msg and msg.get("id") is None must not be confused.

Which of these should be reported as a JSON-RPC error rather than as a tool result with isError: true?

  1. The model passed limit: "many" where an integer is required
  2. The model asked for order A-9999, which does not exist
  3. The model called a tool named refund_order, which the server does not have
  4. The model passed status: "lost", which is not in the enum
The test is whether the model can fix it on its next turn. A wrong type, a missing order and a value outside the enum all have a recovery the model can read in the message. Your client sends initialize and waits for ever. The server process is running and its stderr shows it received the message. What is the most likely cause?

  2. The server correctly answered the notification and the client is waiting for a second reply
  3. The server chose a different protocol version, which blocks the connection
  4. JSON-RPC requires the client to send its id as a string
The client reads one line per reply, and a pipe is buffered: an unflushed or newline-less reply never arrives. The second option is backwards (notifications must not be answered), a different version is a counter-offer that arrives as a normal reply, and ids may be integers or strings.

  3. Error -32602, because the version is not a string
  4. Error -32601, because tools/list does not exist in the modern era
The server does speak 2025-11-25, but through initialize, not through per-request metadata, so in the modern envelope that version is unsupported and the error says which versions would work. tools/list does exist in the modern era, and the version is a perfectly good string.

A client asks a 2026-07-28 server for resources/read of a URI that does not exist. Which error code does the revision specify?

  1. -32002, as in 2025-11-25
  2. -32601, method not found
  3. -32602, invalid params
  4. No error: a result with isError: true
The 2026-07-28 changelog moves resource-not-found from -32002 to the standard -32602, and tells implementations of that version not to emit -32002 (clients should still accept it from older servers). The method exists, so -32601 is wrong, and isError belongs to tools/call results, not to resource reads.

Lab 1: The Agent Loop from Scratch

Chapter 2 showed the whole agent loop in thirty lines. Those lines hide a dozen decisions: what counts as a valid call, what the model sees when a tool fails, which limit ends a run, how the history stays well-formed when a run is cut short, and what to record so you can explain a run afterwards. In this lab you write the loop yourself, one piece at a time, against a scripted model, until a checker can throw typos, runaway loops, parallel calls, truncated replies and a text-only model at it and the history stays valid every time.

Why this lab matters

Every agent you will meet, from a coding assistant to a framework's Agent.run, is this loop with more around it. The bugs that cost real money live here: a tool_use left without its tool_result (the provider rejects the next request), a retried side effect, a run that never stops, a log that cannot say why. A demo with a happy path never meets them. You meet them when you have written the loop and then try to break it, and a scripted model is what makes that practical: it does exactly what you tell it, including misbehaving, so every failure can be reproduced and every guard tested. The skills carry on. Lab 2 builds a measurement harness on top of this loop; the durable agent of chapter 15 resumes from the history you learn to keep valid here.

No model, no network, no clock: everything is scripted and seeded

Python 3.9 or newer and the standard library only. The "model" in every test is a ScriptedModel from llm.py with fixed replies, the time limits use a FakeClock that you wind by hand, and the random scenarios take a seed. A failure prints its seed, and python3 check.py solution 4 17 replays milestone 4 with seed 17 only. The whole check takes about a second. Nothing here calls a real model unless you choose to in the last section.

What you'll build

The scene is an order-support desk with four tools: get_order and track_shipment (read-only), issue_refund (moves money, so a wrong call costs something) and get_returns_policy (returns a long text, to exercise truncation). The Shop class holds the orders and records every refund and every tool function that actually ran, so a test can check not only what the loop said but what it did. Six milestones:

  1. Schemas and validation: validate_args, a small JSON Schema checker whose messages are written for the model, and Registry.definitions.
  2. Running a call: run_tool, which never raises, never runs a call it should not, and turns every failure into a result the model can read.
  3. Stopping rules: LoopGuard, with an iteration cap, a token budget, a deadline and repeated-call detection.
  4. The loop: agent_loop and check_pairing, keeping the history valid on every exit.
  5. Logging: structured events from the loop and summarise, the numbers you read first when a run goes wrong.
  6. A text-only model: parse_react, to_transcript and ReActModel, so the same loop drives a model that can only write text (chapter 3).

Milestone 1: tool schemas and argument validation

A tool schema is the contract between the model and your function: a name, a description and an input_schema written in JSON Schema, a standard vocabulary for the shape of a JSON document (which keys exist, their types, which are required, allowed values). The model reads the schema and writes arguments. It does not always follow it. It invents an extra key, sends "25" where an integer belongs, writes 1001 for A-1001, or picks a reason that is not in the list. Treat those arguments exactly as you would treat the body of an HTTP request from the internet: untrusted input, checked before anything runs (the same rule as in security chapter 9).

You will not implement the whole of JSON Schema, which is large. Six features cover almost every real tool: required, unexpected keys, type, enum, minimum and maximum, and pattern. Two details deserve care. In Python, True is an int, so a naive isinstance(value, int) accepts true as an amount of 1 cent. And a pattern must match the whole string: A-10012 is not an order id.

The other half of the milestone is quieter. The list your registry sends as tools= on every request has exactly three keys per tool (name, description, input_schema) and never the Python function. That list is part of every request you send, so its size is a cost you pay on every iteration, a theme of chapter 5 and of Lab 2.

The messages matter as much as the verdicts. A problem is a sentence the model will read and act on, so it names the argument and says what would be valid. Run the solution on a few bad calls (the demo imports from starter; once you have written your version it runs on yours):

Hints try without first
  • isinstance(True, int) is True in Python. Write a small _json_type(value) that tests bool before int and compare types with it.
  • A number accepts an int or a float; an integer accepts only an int (not a bool, not 25.0).
  • re.fullmatch(pattern, value), not re.search: A-10012 must not pass A-\d{4}.
  • After a type problem, continue to the next argument: a string where a number belongs should not also get a range complaint.

Solution spoiler 
def _json_type(value) -> str:
    if value is None:
        return "null"
    if isinstance(value, bool):
        return "boolean"
    if isinstance(value, int):
        return "integer"
    if isinstance(value, float):
        return "number"
    if isinstance(value, str):
        return "string"
    if isinstance(value, list):
        return "array"
    return "object"

def _type_ok(value, wanted: str) -> bool:
    actual = _json_type(value)
    if wanted == "number":
        return actual in ("integer", "number")      # an int is a valid number
    return actual == wanted                          # True is NOT an integer, 3.0 is NOT an integer here

def validate_args(schema: dict, args: Any) -> List[str]:
    """Check `args` against a (small subset of) JSON Schema; return a list of problems.

    An empty list means the arguments are acceptable. Each problem is one sentence the
    MODEL will read, so name the argument and say what would be valid.

    Supported: a top-level {"type": "object", "properties": {...}, "required": [...]}
    where each property may have type (string, integer, number, boolean, array, object),
    enum, minimum, maximum and pattern (a regex that must match the whole string).

    Order of the returned list: missing required arguments first (in the order of
    `required`), then one pass over `properties` in schema order for the arguments that
    were given, then unexpected arguments, sorted by name. A bool is not an integer and a
    float is not an integer. An argument with the wrong type gets ONE problem (no range or
    enum complaint on top of it). If `args` is not a dict, return a single problem.
    """
    if not isinstance(args, dict):
        return [f"arguments must be a JSON object, got {_json_type(args)}"]
    props = schema.get("properties", {})
    errors: List[str] = []
    for name in schema.get("required", []):
        if name not in args:
            errors.append(f"missing required argument '{name}'")
    for name, spec in props.items():
        if name not in args:
            continue
        value = args[name]
        wanted = spec.get("type")
        if wanted and not _type_ok(value, wanted):
            errors.append(f"argument '{name}' must be {wanted}, got {_json_type(value)} ({value!r})")
            continue
        if "enum" in spec and value not in spec["enum"]:
            errors.append(f"argument '{name}' must be one of {spec['enum']}, got {value!r}")
        if "pattern" in spec and isinstance(value, str) and not re.fullmatch(spec["pattern"], value):
            hint = f", for example {spec['examples'][0]!r}" if spec.get("examples") else ""
            errors.append(f"argument '{name}' = {value!r} does not match the pattern {spec['pattern']}{hint}")
        if "minimum" in spec and _json_type(value) in ("integer", "number") and value < spec["minimum"]:
            errors.append(f"argument '{name}' must be at least {spec['minimum']}, got {value!r}")
        if "maximum" in spec and _json_type(value) in ("integer", "number") and value > spec["maximum"]:
            errors.append(f"argument '{name}' must be at most {spec['maximum']}, got {value!r}")
    for name in sorted(set(args) - set(props)):
        errors.append(f"unexpected argument '{name}' (valid arguments: {', '.join(props) or 'none'})")
    return errors

class Registry:  # add, get and names are given
    def definitions(self) -> List[dict]:
        """The list sent as `tools=` on every model request.

        Each entry has exactly the keys name, description and input_schema (no
        function), in registration order. The result is a fresh list each call.
        """
        return [{"name": t.name, "description": t.description, "input_schema": t.input_schema}
                for t in self._tools.values()]

Milestone 2: running one tool call

A tool call can go wrong in five ways, and a harness that raises in any of them throws away the whole conversation so far. Chapter 2 made the point that the model is good at reading an error and often corrects itself on the next turn, so every failure should come back as a tool_result with is_error set. What you write in the message decides whether the next call is a fix or a repeat:

What happenedWhat the model should be toldDid the function run?
The tool name does not existWhich name was unknown and which tools are availableNo
The arguments are invalidEvery problem from validate_args, and that nothing ranNo
The tool raised ToolErrorThe tool's own message, verbatim: it was written for the modelYes
The tool raised anything elseThe tool name and the exception type, not its messageYes
The result is very longThe first part, plus a note saying it was cut, how much was shown and how to narrow itYes

The fourth row is a deliberate choice. A KeyError: 'secret_table' from a database layer tells an attacker who can steer the model something about your system and tells the model nothing useful; the type is enough for the trace, and the model needs a next step, not a stack. The fifth row comes from chapter 5: a silent cut looks to the model like a complete answer, so say that you truncated and what to do about it. Error messages are never truncated; they are the instructions.

Notice also what the invalid-arguments row protects. If the arguments are checked after the call, issue_refund with amount_cents: "all" has already run. The demo below sends five calls, one of them an invalid refund, and prints what ran:

def run_tool(registry: Registry, call: dict, max_result_chars: int = 2000) -> dict:
    """Run one tool_use block and return the matching tool_result block. NEVER raises.

    `call` is {"type": "tool_use", "id": ..., "name": ..., "input": {...}}.
    Use llm.tool_result(id, content, is_error) to build the block.

      * unknown tool name   -> error result naming the tool and listing the available ones
      * invalid arguments   -> error result starting "Invalid arguments for <name>:" with
                               every problem from validate_args; the function is NOT run
      * ToolError raised    -> error result whose content is str(error), verbatim
      * any other exception -> error result that names the tool and the exception TYPE
                               but not its message (internals stay out of the context)
      * a str result        -> used as is; anything else -> json.dumps(result, sort_keys=True)
      * a result longer than max_result_chars is cut to that length and a note is
        appended that contains the word "truncated" and both the shown and the total
        number of characters. Error messages are never truncated.
    """
    call_id = call.get("id", "")
    name = call.get("name", "")
    tool = registry.get(name)
    if tool is None:
        return tool_result(call_id, f"Unknown tool '{name}'. Available tools: {', '.join(registry.names())}. "
                                    "Nothing was run.", is_error=True)
    problems = validate_args(tool.input_schema, call.get("input", {}))
    if problems:
        return tool_result(call_id, f"Invalid arguments for {name}: " + "; ".join(problems) +
                           ". Nothing was run. Fix the arguments and call again.", is_error=True)
    try:
        value = tool.fn(**call.get("input", {}))
        content = value if isinstance(value, str) else json.dumps(value, sort_keys=True)
    except ToolError as e:
        return tool_result(call_id, str(e), is_error=True)
    except Exception as e:                                   # noqa: BLE001 (the loop must survive anything)
        return tool_result(call_id, f"{name} failed with an internal error ({type(e).__name__}). "
                                    "Try a different approach or tell the user.", is_error=True)
    if len(content) > max_result_chars:
        total = len(content)
        content = (content[:max_result_chars] +
                   f"\n[truncated: showing the first {max_result_chars} of {total} characters. "
                   "Ask for something narrower.]")
    return tool_result(call_id, content)

Milestone 3: stopping rules

Left alone, a model may call tools forever: it cannot find the answer, a tool keeps failing, two steps undo each other. The loop needs limits that your code enforces, because a limit the model is asked to respect is a request, not a barrier. LoopGuard holds four of them. It is pure bookkeeping: it never calls a model or a tool, which is what makes it easy to test exactly.

LimitCheckedStatusProtects against
max_input_tokensbefore each model calltoken_budgetThe quadratic cost of re-sending a growing history (chapter 2): call 20 costs far more than call 2
max_secondsbefore each model calltimeoutA user who has given up long before the budget runs out
max_iterationsbefore each model callmax_iterationsThe simplest backstop on cost and time
max_repeatswhen a reply asks for toolsrepeated_callA model stuck on one failing call, burning its budget for nothing

Three design choices are worth knowing, because they are the ones people get wrong. First, the token and time limits are strict (stop when the total is more than the limit) while the iteration limit is reached (the call after number max_iterations is refused); an off-by-one here is the classic bug, and the checker has a hand case for each. Second, when several limits are exceeded the guard reports one reason, in the order token budget, timeout, iterations, so a log line says the most informative thing first. Third, the repeat key is the tool name plus the input as canonical JSON (sort_keys=True), because a model may reorder the keys of an otherwise identical call.

A deadline needs a clock, and a test that sleeps is slow and flaky. The guard takes any zero-argument function that returns seconds, so tests pass a FakeClock they wind by hand. Step through a run that crosses the token line while time and iterations are still fine:

from starter import Budget, FakeClock, LoopGuard

clock = FakeClock()
guard = LoopGuard(Budget(max_iterations=4, max_input_tokens=3000, max_seconds=20), clock)
for step, (tokens, seconds) in enumerate([(800, 4), (1200, 5), (900, 8), (400, 1)], start=1):
    print(f"before call {step}: {guard.before_model_call()}   (tokens so far {guard.input_tokens}, seconds {clock():g})")
    guard.after_model_call({"input_tokens": tokens, "output_tokens": 50})
    clock.advance(seconds)
print(f"before call 5: {guard.before_model_call()}   (tokens so far {guard.input_tokens}, seconds {clock():g})")
call = {"name": "get_order", "input": {"order_id": "A-1001"}}
guard = LoopGuard(Budget(max_repeats=2), clock)
print([guard.check_calls([call]) for _ in range(3)])
before call 1: None   (tokens so far 0, seconds 0)
before call 2: None   (tokens so far 800, seconds 4)
before call 3: None   (tokens so far 2000, seconds 9)
before call 4: None   (tokens so far 2900, seconds 17)
before call 5: token_budget   (tokens so far 3300, seconds 18)
[None, None, 'repeated_call']

After four calls the guard has used 3,300 tokens against a limit of 3,000, so the fifth call is refused with token_budget even though only 18 of 20 seconds have passed and the iteration limit is also reached. Last line: the third identical call is the first to be reported (max_repeats=2 allows two).

Common misconception

"A repeated call is always a bug." Not always: polling a job's status is legitimate and repeats the same call. max_repeats is a number you tune per deployment, and a better rule for a polling tool is to exempt it by name. The point of the guard is that some rule exists in code, so that a stuck model costs three calls and not three hundred.

Hints try without first
  • The rule is more than for tokens and seconds and reached for iterations. The first two allow exactly the limit; the third refuses the call that would be number max_iterations + 1.
  • Elapsed time is self.clock() - self.started. The guard recorded started when it was created, so a clock that does not start at zero still works.
  • The repeat key is (call["name"], json.dumps(call["input"], sort_keys=True)). Count every call in the list before you return, even after you have found a repeat.

Solution spoiler 
class LoopGuard:  # __init__ is given
    def before_model_call(self) -> Optional[str]:
        """Return None if another model call is allowed, else the reason to stop.

        Checked in this order: "token_budget" when input_tokens so far is MORE than
        max_input_tokens; "timeout" when MORE than max_seconds have passed since the
        guard was created; "max_iterations" when iterations has reached max_iterations.
        """
        b = self.budget
        if self.input_tokens > b.max_input_tokens:
            return "token_budget"
        if self.clock() - self.started > b.max_seconds:
            return "timeout"
        if self.iterations >= b.max_iterations:
            return "max_iterations"
        return None

    def after_model_call(self, usage: Dict[str, int]) -> None:
        """Record one finished model call: one more iteration, plus its input tokens."""
        self.iterations += 1
        self.input_tokens += usage.get("input_tokens", 0)

    def check_calls(self, calls: List[dict]) -> Optional[str]:
        """Count every requested call and return "repeated_call" if any identical call
        (same tool name and same input, key order ignored) has now been requested MORE
        than max_repeats times in total; otherwise None. Every call is counted, in order,
        even after a repeat has been found."""
        verdict = None
        for c in calls:
            key = (c["name"], json.dumps(c["input"], sort_keys=True))
            self.seen[key] = self.seen.get(key, 0) + 1
            if self.seen[key] > self.budget.max_repeats:
                verdict = "repeated_call"
        return verdict

Milestone 4: the loop

Now the loop itself. Its whole state is the messages list (plus a few counters), which is why it can be checkpointed, replayed in a test and inspected after a failure. That is also why the history must be valid at every exit. A provider rejects a request in which an assistant tool_use is not followed by a user message with a matching tool_result, and a durable agent that resumes from a saved history cannot resume from an invalid one.

One iteration, in the order your code does it:

  1. Ask the guard whether another model call is allowed. If it names a reason, stop with that status.
  2. Call model.complete(messages, system=system, tools=registry.definitions()), tell the guard the usage, and append the reply exactly as received.
  3. No tool requests: the model has answered. Status done, or truncated if the reply was cut off by max_tokens.
  4. Tool requests, but the reply was cut off by max_tokens: the arguments may be incomplete JSON. Do not run them. Answer each with an error result and stop.
  5. Ask the guard about repeats. If it objects, answer every call with an error result ("Not run: ...") and stop with repeated_call.
  6. Otherwise run the calls in order and append one user message with all the results.

Steps 4 and 5 are the interesting ones. They stop the run, so the temptation is to break and return; but then the last assistant message holds tool requests nobody answered. Answering them with an error result costs two lines and keeps the history valid. Running calls in order, one after another, is the safe default for tools with side effects (chapter 2 explains why concurrency needs more thought than a thread pool). Here is the happy path from chapter 2, and then a model that never gives up on the same call:

from llm import ScriptedModel, tool_use
from starter import Shop, agent_loop, check_pairing, make_registry

model = ScriptedModel([
    [tool_use("get_order", {"order_id": "A-1001"}, id="t1")],
    [tool_use("track_shipment", {"carrier": "UPS"}, id="t2")],
    "Order A-1001 shipped with UPS and is out for delivery in Leeds.",
])
r = agent_loop(model, "Where is order A-1001?", make_registry(Shop()), system="You are a support agent.")
print(r.status, "| model calls:", r.iterations, "| input tokens:", r.input_tokens)
print(r.answer)
for i, m in enumerate(r.messages):
    kinds = [m["content"]] if isinstance(m["content"], str) else [b["type"] for b in m["content"]]
    print(f"  message {i}: {m['role']:9s} {kinds}")
print("pairing problems:", check_pairing(r.messages))

stuck = ScriptedModel(lambda messages, tools, system: [tool_use("get_order", {"order_id": "A-1001"})])
r = agent_loop(stuck, "Where is order A-1001?", make_registry(Shop()))
print("\nstuck model:", r.status, "after", r.iterations, "model calls")
print("answer:", r.answer)

Systems connection

The loop is an ordinary service handler, and the guard is its resilience layer: a deadline for the whole task (the budget idea of failure, timeouts and retries), a cap on retries, and a refusal to repeat what has not worked. The "Not run" results are the agent version of failing fast with a clear reason. And when a tool call times out in a real system, the harness cannot tell whether the side effect happened; chapter 5 and Lab 2 show the idempotency key that makes the retry safe.

def check_pairing(messages: List[dict]) -> List[str]:
    """Return the problems in a conversation history (an empty list when it is valid).

    Rules: roles alternate user, assistant, user, ... starting with user; every tool_use
    id in an assistant message is answered by exactly one tool_result with that id in the
    very next message (which must be a user message); every tool_result answers a
    tool_use from the message just before it. Each problem is a string that starts with
    "message <index>:" (0-based) and names the offending id.
    """
    problems: List[str] = []
    for i, m in enumerate(messages):
        want = "user" if i % 2 == 0 else "assistant"
        if m["role"] != want:
            problems.append(f"message {i}: expected role '{want}' but got '{m['role']}'")
        blocks = m["content"] if isinstance(m["content"], list) else []
        asked = [b["id"] for b in blocks if b.get("type") == "tool_use"]
        answered = [b["tool_use_id"] for b in blocks if b.get("type") == "tool_result"]
        previous = messages[i - 1]["content"] if i > 0 and isinstance(messages[i - 1]["content"], list) else []
        prev_ids = [b["id"] for b in previous if b.get("type") == "tool_use"] if i > 0 and messages[i - 1]["role"] == "assistant" else []
        for rid in sorted(set(answered)):
            if rid not in prev_ids:
                problems.append(f"message {i}: tool_result for '{rid}' does not answer a tool_use in the message before it")
            elif answered.count(rid) > 1:
                problems.append(f"message {i}: more than one tool_result for '{rid}'")
        if asked:
            nxt = messages[i + 1]["content"] if i + 1 < len(messages) and isinstance(messages[i + 1]["content"], list) else []
            got = {b["tool_use_id"] for b in nxt if b.get("type") == "tool_result"}
            for tid in asked:
                if tid not in got:
                    problems.append(f"message {i}: tool_use '{tid}' has no tool_result in the next message")
    return problems

def agent_loop(model: Model, question: str, registry: Registry, *, system: str = "",
               budget: Optional[Budget] = None, clock: Callable[[], float] = time.monotonic,
               max_result_chars: int = 2000, trace: Optional[Trace] = None) -> RunResult:
    """Run the tool-calling loop until the model answers or a limit stops it.

    History: starts as [{"role": "user", "content": question}]. Each iteration, in order:
      1. ask a LoopGuard (built from `budget`, default Budget(), and `clock`) whether
         another model call is allowed; if it names a reason, stop with that status;
      2. call model.complete(messages, system=system, tools=registry.definitions());
         tell the guard about its usage; append reply.as_message();
      3. no tool_use blocks in the reply -> stop: status "done" (or "truncated" when the
         stop_reason is "max_tokens");
      4. tool_use blocks but stop_reason "max_tokens" (the call was cut off): answer each
         with an error result "Not run: ...", append them, stop with "truncated";
      5. guard.check_calls(calls) names a reason ("repeated_call"): answer each call with
         an error result "Not run: ..." and stop with that reason (the history must stay valid);
      6. otherwise run every call IN ORDER with run_tool and append ONE user message whose
         content is the list of tool_result blocks.
    Whatever the exit, check_pairing(messages) must come back empty.

    The answer is the reply's text for "done" and "truncated", otherwise STOP_MESSAGES[status].
    RunResult.iterations is the number of model calls; input_tokens their summed input tokens.

    Milestone 5 adds logging: when `trace` is not None, call trace.add(...) for
      "model_call"  i, stop_reason, input_tokens, output_tokens, tools (list of requested names)
      "tool_call"   i, id, tool, input, is_error, result_chars, seconds (clock time the run took)
      "stop"        status, iterations
    in that order for each iteration, and exactly one "stop" event at the end.
    """
    guard = LoopGuard(budget or Budget(), clock)
    messages: List[dict] = [{"role": "user", "content": question}]
    tools = registry.definitions()
    status, reply = "done", None
    while True:
        reason = guard.before_model_call()
        if reason:
            status = reason
            break
        reply = model.complete(messages, system=system, tools=tools)
        guard.after_model_call(reply.usage)
        messages.append(reply.as_message())
        calls = tool_calls(reply)
        i = guard.iterations
        if trace is not None:
            trace.add("model_call", i=i, stop_reason=reply.stop_reason, input_tokens=reply.usage["input_tokens"],
                      output_tokens=reply.usage["output_tokens"], tools=[c["name"] for c in calls])
        if not calls:
            status = "truncated" if reply.stop_reason == "max_tokens" else "done"
            break
        if reply.stop_reason == "max_tokens":
            messages.append({"role": "user", "content": [
                tool_result(c["id"], "Not run: the reply was cut off by max_tokens. Ask again more briefly.", is_error=True)
                for c in calls]})
            status = "truncated"
            break
        reason = guard.check_calls(calls)
        if reason:
            messages.append({"role": "user", "content": [
                tool_result(c["id"], "Not run: this exact call has been made too many times. "
                                     "Change your approach or explain the problem to the user.", is_error=True)
                for c in calls]})
            status = reason
            break
        results = []
        for c in calls:
            t0 = clock()
            r = run_tool(registry, c, max_result_chars)
            if trace is not None:
                trace.add("tool_call", i=i, id=c["id"], tool=c["name"], input=c["input"], is_error=r["is_error"],
                          result_chars=len(r["content"]), seconds=round(clock() - t0, 6))
            results.append(r)
        messages.append({"role": "user", "content": results})
    answer = text_of(reply) if status in ("done", "truncated") and reply is not None else STOP_MESSAGES.get(status, "")
    if trace is not None:
        trace.add("stop", status=status, iterations=guard.iterations)
    return RunResult(messages, status, answer, guard.iterations, guard.input_tokens)

Milestone 5: logging and reading a trace

When an agent run goes wrong, the transcript is the fastest diagnosis, and the same records become your evaluation data later (tracing and observability for LLM systems). The loop already holds all the facts; the job is to record them as structured events, plain dictionaries that a program can count, instead of lines of prose that a person must read. Your loop writes three kinds:

EventWhenFields besides kind
model_callafter each model calli, stop_reason, input_tokens, output_tokens, tools (names requested)
tool_callafter each tool runi, id, tool, input, is_error, result_chars, seconds
stoponce, at the endstatus, iterations

Those are the leaf records of what distributed tracing calls spans: a model call and a tool call are the two kinds of span an agent run is made of. summarise reduces a list of events to the numbers you read first. The one with a definition worth stating is wasted_calls: a tool call that errored, or that repeats an earlier call of the same run with the same input. It is a blunt measure, but it is the first one that separates a model that is confused by your tools from one that is simply slow. def summarise(events: List[dict]) -> dict:
    """Condense a Trace's events into the numbers you read first when a run goes wrong.

    Returns a dict with exactly these keys:
      status         the status of the "stop" event ("" if there is none)
      iterations     number of "model_call" events
      input_tokens   sum of input_tokens over "model_call" events
      output_tokens  sum of output_tokens over "model_call" events
      tool_calls     number of "tool_call" events
      errors         tool_call events with is_error true
      calls_by_tool  {tool name: number of calls}
      wasted_calls   tool_call events that errored OR repeat an earlier call (same tool
                     and same input) of this run; each event counts once
      seconds        sum of "seconds" over tool_call events (rounded to 6 places)
    """
    out = {"status": "", "iterations": 0, "input_tokens": 0, "output_tokens": 0, "tool_calls": 0,
           "errors": 0, "calls_by_tool": {}, "wasted_calls": 0, "seconds": 0.0}
    seen = set()
    for e in events:
        if e["kind"] == "model_call":
            out["iterations"] += 1
            out["input_tokens"] += e["input_tokens"]
            out["output_tokens"] += e["output_tokens"]
        elif e["kind"] == "tool_call":
            out["tool_calls"] += 1
            out["calls_by_tool"][e["tool"]] = out["calls_by_tool"].get(e["tool"], 0) + 1
            key = (e["tool"], json.dumps(e["input"], sort_keys=True))
            if e["is_error"]:
                out["errors"] += 1
            if e["is_error"] or key in seen:
                out["wasted_calls"] += 1
            seen.add(key)
            out["seconds"] += e["seconds"]
        elif e["kind"] == "stop":
            out["status"] = e["status"]
    out["seconds"] = round(out["seconds"], 6)
    return out

Milestone 6: the same loop with a text-only model

Chapter 3 introduced ReAct in its original form: the model writes lines of text, Thought: then Action:, and the harness parses the action, runs it and appends an Observation:. Native tool calling replaced the parsing with structured blocks, but a text-only model (a small local model, a base model, a provider with no tool support) still needs the old form. The right way to support it is not a second loop. It is an adapter, so that guards, validation, error results and tracing all keep working.

Three rules make the text format safe, and they are all about who writes the observation. The format is Action: tool_name {"json": "arguments"} on one line. The model must stop after the action line (in a real API, a stop sequence of Observation:; the stand-in model cannot be told to stop, so your parser does it): anything from the first Observation: line on is the model inventing what the tool would have said, and it is discarded. A reply that invents an observation before it has acted has nothing valid left, which is an error, not a free answer. And when the reply cannot be parsed, the model is shown its mistake as a format error and asked again, a limited number of times.

def parse_react(reply: str) -> dict:
    """Parse one reply in the ReAct text format. NEVER raises, whatever the text.

    The format is:
        Thought: <free text>
        Action: <tool name> <JSON object>        (the JSON is optional: no JSON means {})
    or
        Thought: <free text>
        Final Answer: <free text>

    First cut the reply at the first line that starts with "Observation:" (a model that
    writes its own observation is inventing one; the harness supplies the real one).
    Then, whichever of "Action:" / "Final Answer:" starts a line first wins. Return one of
        {"kind": "final",  "thought": str, "answer": str}
        {"kind": "action", "thought": str, "tool": str, "input": dict}
        {"kind": "error",  "message": str}     neither found, JSON that does not parse, or
                                                JSON that is not an object
    `thought` is the text after "Thought:" up to the Action/Final Answer line, stripped
    ("" when absent). `answer` is everything after "Final Answer:", stripped.
    """
    cut = re.search(r"^Observation:", reply, re.M)
    body = reply[:cut.start()] if cut else reply
    act = re.search(r"^Action:[ \t]*([A-Za-z_][\w.-]*)[ \t]*(.*)$", body, re.M)
    fin = re.search(r"^Final Answer:[ \t]*", body, re.M)
    if not act and not fin:
        return {"kind": "error", "message": "Reply with 'Action: <tool> <JSON arguments>' or 'Final Answer: <text>'."}
    use_final = fin is not None and (act is None or fin.start() < act.start())
    first = fin if use_final else act
    th = re.search(r"Thought:[ \t]*", body[:first.start()])
    thought = body[th.end():first.start()].strip() if th else ""
    if use_final:
        return {"kind": "final", "thought": thought, "answer": body[fin.end():].strip()}
    raw_args = act.group(2).strip()
    if not raw_args:
        return {"kind": "action", "thought": thought, "tool": act.group(1), "input": {}}
    try:
        parsed = json.loads(raw_args)
    except ValueError as e:
        return {"kind": "error", "message": f"The arguments of Action {act.group(1)} are not valid JSON ({e.__class__.__name__}). "
                                            "Write one JSON object on the Action line."}
    if not isinstance(parsed, dict):
        return {"kind": "error", "message": "The arguments must be a JSON object, like {\"order_id\": \"A-1001\"}."}
    return {"kind": "action", "thought": thought, "tool": act.group(1), "input": parsed}

def to_transcript(messages: List[dict]) -> str:
    """Render a native content-block history as the text a ReAct model reads.

        Question: <first user message>
        Thought: <assistant text>            (only when an assistant message has text and a tool_use)
        Action: <tool name> <input as JSON>
        Observation: <tool_result content>   (one line per result, in order)

    An assistant message without a tool_use renders as "Final Answer: <text>". One line
    per item, each ending in a newline. Use json.dumps(input) for the arguments.
    """
    lines: List[str] = []
    for m in messages:
        c = m["content"]
        if isinstance(c, str):
            lines.append(f"Question: {c}")
            continue
        if m["role"] == "user":
            for b in c:
                if b.get("type") == "tool_result":
                    lines.append(f"Observation: {b['content']}")
            continue
        uses = [b for b in c if b.get("type") == "tool_use"]
        words = "".join(b.get("text", "") for b in c if b.get("type") == "text").strip()
        if not uses:
            lines.append(f"Final Answer: {words}")
            continue
        if words:
            lines.append(f"Thought: {words}")
        for b in uses:
            lines.append(f"Action: {b['name']} {json.dumps(b['input'])}")
    return "\n".join(lines) + "\n"

class ReActModel:  # __init__ is given
    def complete(self, messages, *, system=None, tools=None, max_tokens=1024, temperature=0.0):
        prompt = to_transcript(messages)
        n = 1 + sum(1 for m in messages if m["role"] == "assistant")
        usage = {"input_tokens": 0, "output_tokens": 0}
        raw_text = ""
        for attempt in range(self.max_format_retries + 1):
            raw = self.inner.complete([{"role": "user", "content": prompt}],
                                      system=react_system(tools or [], system or ""), max_tokens=max_tokens)
            for k in usage:
                usage[k] += raw.usage.get(k, 0)
            raw_text = text_of(raw)
            parsed = parse_react(raw_text)
            if parsed["kind"] == "final":
                return Response([text(parsed["answer"])], "end_turn", usage, self.name)
            if parsed["kind"] == "action":
                blocks = ([text(parsed["thought"])] if parsed["thought"] else []) + \
                         [tool_use(parsed["tool"], parsed["input"], id=f"react-{n}")]
                return Response(blocks, "tool_use", usage, self.name)
            prompt += raw_text.rstrip("\n") + f"\nObservation: Format error: {parsed['message']}\n"
        return Response([text(raw_text)], "end_turn", usage, self.name)

Going further

What you learned

  • Tool arguments are untrusted input. Validate before anything runs, and write the problems for the model: the argument, what is wrong, what would be valid.
  • A harness never raises on a tool failure. Every failure becomes an is_error result; internals stay out of the context; a long result is cut with a note that says so.
  • Limits live in code: strict token and time limits, a reached iteration limit, and a canonical key for repeated calls. A forced stop must return the reason and something useful.
  • The history is the state. Every exit, including forced ones and truncated replies, answers every tool_use, so the run can be inspected and resumed.
  • Structured events, and a few counts such as errors and wasted calls, are the first diagnostic. A text-only model needs an adapter in front, not a different loop, and the observation is always written by the harness.

Check your understanding

A model replies with two tool calls, and your harness notices the second is the third identical request of the run (max_repeats=2). What should the loop do with the history?

  1. Return at once: the run is over and the history is no longer needed.
  2. Answer both calls with error results such as "Not run: ...", append them, then stop with repeated_call.
  3. Run the first call, drop the second and continue.
  4. Delete the assistant message so the history looks as if the reply never happened.
The history must satisfy the pairing contract on every exit: each tool_use is answered by a tool_result in the next message. Returning at once leaves two unanswered requests, which a provider rejects and a resumed run cannot continue from. Dropping the message hides what the model actually did.

Budget(max_iterations=3) and a model that asks for one tool on every reply. How many model calls and how many tool functions run?

  1. 2 model calls and 2 tool runs
  2. 3 model calls and 2 tool runs
  3. 4 model calls and 3 tool runs
  4. 3 model calls and 3 tool runs
The guard is asked before each model call and refuses the call that would be number four. The third reply still asks for a tool and nothing forbids running it, so the loop runs it and appends the result; the next iteration's guard check then stops the run. That leaves a valid history ending on the tool results. The tempting “3 and 2” forgets that the third reply's tool call is honoured.

validate_args receives {"amount_cents": true} for an integer argument. Which result is right under the rules of this lab?

  1. One problem: a boolean is not an integer, even though Python's isinstance(True, int) says otherwise.
  2. No problem: true is 1 and 1 is a valid amount.
  3. Two problems: wrong type and below the minimum.
  4. A TypeError, because bools cannot be compared with ints.
JSON distinguishes booleans from numbers; Python's bool is a subclass of int and so slips through a naive check. Accepting it would refund one cent on a model's stray true. A type problem is reported once; range checks only run on values of the right type, so there is no second complaint.

A trace has four tool calls: get_order(A-1) succeeds, get_order(A-1) succeeds again, get_order(A-9) fails, get_order(A-9) fails again. What does summarise report for errors and wasted_calls?

  1. errors 2, wasted 2
  2. errors 2, wasted 4
  3. errors 2, wasted 3
  4. errors 4, wasted 3
Two calls errored, so errors is 2. A call is wasted if it errored or repeats an earlier one: the second A-1 repeats, the first A-9 errored, the second A-9 errored and repeats (counted once). That is 3. The first A-1 did useful work and is not wasted.

A text-only model writes Action: get_order {"order_id": "A-1001"} followed by a line Observation: it shipped via FedEx. What should parse_react and the loop do?

  1. Use the invented observation: it saves a tool call.
  2. Cut the reply at the Observation: line, run the real tool, and give the model the real observation.
  3. Reject the reply as malformed and stop the run.
  4. Run the tool but keep both observations in the transcript so the model can compare them.
Only the harness may write an observation: the model has no access to the order system and the invented text is a guess presented as fact (the failure chapter 3 describes). Cutting at the first Observation: line, acting on what comes before it, and supplying the real result is the stop-sequence behaviour done in the parser. Stopping the run throws away a usable action; keeping both would put a fabrication into the context.

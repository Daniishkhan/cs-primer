Lab 2: Tool Design, Measured

Chapter 5 argued that you cannot judge a toolset by reading it, and sketched how to measure one: realistic tasks, outcomes you can verify, runs you can count, transcripts you read, a held-out set. This lab does the measuring. Two designs of the same billing toolset (five wrappers around REST endpoints, and three tools built around what a support agent has to get done) face the same twenty tasks, three runs each. You write the linter, the task-shaped tools, the grader, the runner and the statistics, and the numbers pick a winner, or tell you honestly how far they can go.

Why this lab matters

Arguments about tool design are cheap to start and hard to end: one engineer likes many small tools, another likes few large ones. The only answer that ends the argument is a measurement, and measurements have traps that this lab makes you walk into on purpose. A pass rate over twenty tasks has wide error bars. An average can hide a regression on two tasks. A grader that reads the agent's final message rewards confident claims instead of results. A cheaper design might be cheaper because it did nothing. And the fix that makes a design better, such as a safe retry, may not show up in any metric until you grade the state of the world instead of the words. The same harness shape (tasks, end-state graders, per-run records, paired comparison, a held-out split) is what you will reuse for every agent in this path, and evaluating agents in A6 builds on it.

The agent is a stand-in: read the numbers as a method, not as a finding about models

Python 3.9 or newer and the standard library only; no network, no API key, no clock, and the same numbers on every run (the stand-in agent's few random choices are seeded by task and trial). The "model" that uses the tools is a small policy in standin.py that reads real tool results and does what chapter 5 says models tend to do with each design: try the id-only tool first with the only identifier it has, repeat an opaque error, guess a unit nobody stated, miss that a dump contains two customers, retry a call whose response was lost. Those behaviours are my assumptions, chosen to be representative and written down in the open. A real model would produce different numbers; what transfers is the harness, the grading and the statistics. The last section shows how to point the same harness at a real model.

What you'll build

The world is Northwind, the subscription company of chapter 5: six customers (two of them called Ana Silva), invoices, payments and refunds, behind an ordinary REST-style backend in fixtures.py. Design A wraps the backend endpoint by endpoint (get_customer, list_invoices, get_invoice, list_payments, create_refund). Design B has three tools, billing_find_customer, billing_get_account_summary and billing_issue_refund, whose definitions are given and whose behaviour you write. Five milestones:

  1. Lint and cost: lint and definition_tokens. A static review of both toolsets that reproduces chapter 5's findings and its token counts.
  2. Design B: find_customer, account_summary, issue_refund. Results that fit the next step, errors that teach, and a refund that is safe to retry.
  3. Grade by end state: grade. Did the right money move, and nothing else?
  4. Run and summarise: run_metrics, evaluate, aggregate. Twenty tasks, three trials, one record per run, one report per design.
  5. Decide: paired_bootstrap_ci, sign_test_p, decide. Intervals, a sign test, regressions and a held-out check.

Milestone 1: lint a toolset and count what it costs

The cheapest measurement needs no runs at all. A linter is a program that reads something and reports likely defects without executing it. Chapter 5 listed the defects a tool definition can have, and most of them can be checked mechanically: a description too short to say what, when, when not and what comes back; a description that only restates the name; generic argument names such as id; arguments with no description; and two tools whose descriptions overlap so much that a model has to guess between them. You write the linter that chapter 5 sketched, and a function that prices a toolset in tokens.

The token count matters because definitions are sent on every request, so their size is a per-call tax. A linter finding is a cheap proxy; it cannot tell you whether the extra words fix real mistakes. That is what the runs are for. Run the solution on both toolsets:

        print(f"   {tool:14s} {code:16s} {message}")

Whether it pays depends on what the extra words prevent, which the rest of the lab measures. Notice the asymmetry as well: a linter can tell you a description is short, but not that it is wrong. A description can pass every rule and still send the model to the wrong tool.

def lint(tools: List[dict]) -> List[Tuple[str, str, str]]:
    """Review tool definitions; return findings as (tool name, code, message).

    Codes, in the order they are reported for each tool:
      "thin"            the description has fewer than 15 words
      "restates"        words(description) is a subset of words(name with "_" as spaces)
      then for each property in schema order:
      "generic_arg"     the property name is in GENERIC
      "undescribed_arg" the property has neither a "description" nor an "enum"
    After every tool has been reviewed, one more kind of finding:
      "overlap"         for each PAIR of tools (a, b) in list order, the Jaccard similarity of
                        words(a description) and words(b description), |A & B| / |A | B|, is at
                        least 0.35. Report it against tool a; the message names both tools.
    Messages are sentences for a human; tests look at the tool name and the code.
    """
    out: List[Tuple[str, str, str]] = []
    for t in tools:
        d, n = t["description"], t["name"]
        if len(d.split()) < 15:
            out.append((n, "thin", f"description is {len(d.split())} words; say what, when, when not, and what comes back"))
        if words(d) <= words(n.replace("_", " ")):
            out.append((n, "restates", "description only restates the name"))
        for p, spec in t["input_schema"].get("properties", {}).items():
            if p in GENERIC:
                out.append((n, "generic_arg", f"argument '{p}' has a generic name; prefer customer_id, invoice_id ..."))
            if "description" not in spec and "enum" not in spec:
                out.append((n, "undescribed_arg", f"argument '{p}' has no description"))
    for a, b in itertools.combinations(tools, 2):
        wa, wb = words(a["description"]), words(b["description"])
        j = len(wa & wb) / max(1, len(wa | wb))
        if j >= 0.35:
            out.append((a["name"], "overlap", f"description overlaps {b['name']} by {j:.0%}; a model may confuse them"))
    return out

def definition_tokens(tools: List[dict]) -> int:
    """Tokens the definitions cost on EVERY request: the sum of count_tokens(json.dumps(tool))."""
    return sum(count_tokens(json.dumps(t)) for t in tools)

Milestone 2: design B, the task-shaped tools

Design A is what you get by wrapping a REST API one endpoint at a time: easy to build, complete on paper, and designed for a different user, a programmer who already holds a customer id and is happy to join four resources. A model holds an email address and nothing else. Design B starts from the tasks instead. Four moves from chapter 5 turn into code in this milestone:

  • Make the first step reachable. find_customer accepts the thing the user actually gave you (an email or a name) and returns candidate ids. When two customers share a name it returns both, because choosing between them is the model's job (and, in tasks 19 and 20, the right behaviour is to ask).
  • Send back what the next step needs. account_summary joins customer, open invoices and recent payments server-side and returns a small dictionary. For the customer with 60 invoices that is a few hundred tokens instead of more than ten thousand, and it includes the payment_id the refund tool needs.
  • Make errors teach. An unknown payment says what ids look like and where to get one; an impossible amount says the legal range and the unit; a refund above the cap says so, says a human decides, and says not to retry.
  • Enforce safety in code. The cap is a line of Python, not a sentence in the description, and the refund carries an idempotency key.

The last move deserves its own paragraph, because it is subtle and because it is the same mechanism as in failure, timeouts and retries. The backend's refund service in this lab is flaky in a realistic way: it applies the refund and then the response is lost, so the caller sees a timeout and does not know whether money moved. A caller that retries blindly refunds twice. An idempotency key is a caller-chosen token sent with a write so that repeating the same request has the effect of sending it once: the backend remembers the key and returns the first result. Your tool derives the key from the request itself (payment_id:amount:reason), so the model needs no new argument and the retry is recognised.

If your tool had checked the amount against the remaining balance before calling the backend, the retry would have been refused as out of range instead of being recognised as a repeat. That ordering is the trap this milestone sets; the checker has a case for it.

Common misconception

"The description says refunds above 10,000 cents must go to a human, so the model will not make one." The description is a request; the model, a prompt injection in a customer message, or a bug can ask anyway. The tool in this lab rejects the call whatever was said, and the rejection itself tells the model what to do next. Telling the model and enforcing in code are two layers, and you need both (authorisation belongs in the server).

def find_customer(db: Northwind, email_or_name: str):
    """billing_find_customer: up to 5 matches as [{"customer_id", "name", "email"}, ...].

    Use db.match_customers. When nothing matches, RETURN (do not raise) a sentence that
    starts "No customer found for" followed by the repr of the text, and tells the model
    what to try next (the email address on the account). A name shared by two customers
    returns both: it is the model's job to ask which one.
    """
    found = db.match_customers(email_or_name)
    if not found:
        return f"No customer found for {email_or_name!r}. Try the email address on the account."
    return [{"customer_id": c["customer_id"], "name": c["name"], "email": c["email"]} for c in found[:5]]

def account_summary(db: Northwind, customer_id: str, response_format: str = "concise"):
    """billing_get_account_summary: one dict that answers "what do they owe / what did they pay".

    Raises ToolError(f"No customer with id {customer_id!r}. Ids look like cus_1042; get one from
    billing_find_customer.") for an unknown id. Otherwise the dict has exactly these keys:
      customer_id, name, plan
      owed_cents          the sum of amount_cents over ALL invoices with status open or overdue
      open_invoices       the newest 5 of those invoices, newest first, each
                          {"invoice_id", "status", "amount_cents", "due"} (due = the invoice's due_at);
                          with response_format "detailed" each also has "line_items"
      latest_payment      the newest payment as {"payment_id", "invoice_id", "amount_cents", "paid_at"}, or None
      recent_payments     the newest 5 payments, same shape, newest first (latest_payment is the first)
    "Newest" payments sort by (paid_at, id) descending, which is what db.payments_of returns.
    Invoices come from db.invoices_of (newest first). Nothing else (no addresses, no audit trail).
    """
    c = db.customers.get(customer_id)
    if c is None:
        raise ToolError(f"No customer with id {customer_id!r}. Ids look like cus_1042; get one from billing_find_customer.")
    open_rows = [i for i in db.invoices_of(customer_id) if i["status"] in ("open", "overdue")]
    pays = [{"payment_id": p["id"], "invoice_id": p["invoice_id"], "amount_cents": p["amount_cents"], "paid_at": p["paid_at"]}
            for p in db.payments_of(customer_id)[:5]]
    listed = []
    for i in open_rows[:5]:
        row = {"invoice_id": i["id"], "status": i["status"], "amount_cents": i["amount_cents"], "due": i["due_at"]}
        if response_format == "detailed":
            row["line_items"] = i["line_items"]
        listed.append(row)
    return {"customer_id": customer_id, "name": c["name"], "plan": c["plan"], "owed_cents": sum(i["amount_cents"] for i in open_rows),
            "open_invoices": listed, "latest_payment": pays[0] if pays else None, "recent_payments": pays}

def issue_refund(db: Northwind, payment_id: str, amount_cents: int, reason: str):
    """billing_issue_refund: refund part or all of a payment, safely.

    1. If amount_cents is above REFUND_CAP_CENTS, raise ToolError whose text contains "human",
       says not to retry, and states the cap. (Enforce it in code, whatever the prompt said.)
    2. Otherwise call db.apply_refund(payment_id, amount_cents, idempotency_key=key) with
       key = f"{payment_id}:{amount_cents}:{reason}", so an identical request is never applied twice.
         KeyError          -> ToolError(f"Error: no payment {payment_id!r}. Payment ids look like
                              pay_88123; get one from billing_get_account_summary.")
         ValueError        -> ToolError naming the legal range "between 1 and N" (N = what is still
                              refundable on that payment) and reminding the model amounts are in cents
         RefundTimeout     -> ToolError saying the service timed out and the outcome is unknown, that
                              retrying the SAME call is safe because repeats are ignored
    3. On success return f"Refunded {amount_cents} cents of {payment_id} ({reason}); {left} cents still
       refundable." and, when the backend says replayed, append " (repeat of an earlier call: no money moved again)".

    Let the backend decide whether the amount is possible (do not pre-check it): after a lost response
    the retry must reach the backend with the same key, even if nothing is left to refund.
    """
    if amount_cents > REFUND_CAP_CENTS:
        raise ToolError(f"Error: refunds above {REFUND_CAP_CENTS} cents need a human. Do not retry. "
                        "Tell the customer a human colleague will review it.")
    key = f"{payment_id}:{amount_cents}:{reason}"
    try:
        res = db.apply_refund(payment_id, amount_cents, idempotency_key=key)
    except KeyError:
        raise ToolError(f"Error: no payment {payment_id!r}. Payment ids look like pay_88123; get one from billing_get_account_summary.")
    except ValueError:
        p = db.payments[payment_id]
        left = p["amount_cents"] - p["refunded_cents"]
        raise ToolError(f"Error: amount_cents must be between 1 and {left} for {payment_id}; got {amount_cents}. Amounts are in cents.")
    except RefundTimeout:
        raise ToolError("The refund service timed out and the outcome is unknown. Retry the same call: "
                        "repeats are ignored, so money cannot move twice.")
    msg = f"Refunded {amount_cents} cents of {payment_id} ({reason}); {res['remaining_cents']} cents still refundable."
    return msg + (" (repeat of an earlier call: no money moved again)" if res["replayed"] else "")

Milestone 3: grade by what happened

How do you decide whether a run succeeded? The tempting answer is to read the agent's last message. It is also the worst one, because an agent can say "I have refunded you £29.00" having refunded nothing, or having refunded 29 pence. Chapter 5 and A6 chapter 8 give the alternative: grade the end state, the condition of the world after the run. Here the world is the backend, and the question is which refunds really moved money.

The grader applies three rules to every run. The refunds that moved must equal the task's expected refunds as a multiset: the same payments and amounts, order ignored, repeats counted. Every phrase the task requires must appear in the answer (a customer wants to be told the amount, or that a human will decide). No forbidden phrase may appear. It also separates two outcomes that an average would blur. A run that failed did not do what was asked; a run that was harmful moved money that nobody asked to move: an extra refund, a doubled one, the wrong amount. A dashboard that shows only success rate hides the difference between "did nothing" and "did the wrong thing", and the second is the one that gets a support team into trouble.

def grade(task: dict, db: Northwind, answer: str) -> Grade:
    """Grade one finished run.

    * The refunds that really moved money (db.refunds, a list of (payment_id, amount_cents))
      must equal task["expected_refunds"] as multisets (order does not matter, repeats do).
    * Every phrase in task["must_include"] must appear in the answer, ignoring case.
    * No phrase in task["must_not_include"] may appear, ignoring case.
    success = none of those rules was broken. harmful = at least one refund moved money that
    the task did not expect (an extra, a double, a wrong amount); a MISSING refund is a failure
    but not harmful. reasons has one sentence per rule broken (empty on success).
    """
    reasons = []
    actual = Counter(tuple(r) for r in db.refunds)
    expected = Counter(tuple(r) for r in task["expected_refunds"])
    if actual != expected:
        reasons.append(f"refunds were {sorted(actual.elements())}, expected {sorted(expected.elements())}")
    low = answer.lower()
    for phrase in task["must_include"]:
        if phrase.lower() not in low:
            reasons.append(f"answer is missing {phrase!r}")
    for phrase in task["must_not_include"]:
        if phrase.lower() in low:
            reasons.append(f"answer contains {phrase!r}")
    return Grade(not reasons, bool(actual - expected), reasons)

def run_metrics(messages: List[dict]) -> Dict[str, int]:
    """Count what a finished conversation cost, from its messages alone.

    model_calls     assistant messages
    tool_calls      tool_use blocks
    tool_errors     tool_result blocks with is_error true
    result_tokens   sum of count_tokens(content) over all tool_result blocks
    repeated_calls  tool_use blocks whose (name, input) already appeared earlier in the run
    """
    m = {"model_calls": 0, "tool_calls": 0, "tool_errors": 0, "result_tokens": 0, "repeated_calls": 0}
    seen = set()
    for msg in messages:
        if msg["role"] == "assistant":
            m["model_calls"] += 1
        if isinstance(msg["content"], str):
            continue
        for b in msg["content"]:
            if b["type"] == "tool_use":
                m["tool_calls"] += 1
                key = (b["name"], json.dumps(b["input"], sort_keys=True))
                m["repeated_calls"] += key in seen
                seen.add(key)
            elif b["type"] == "tool_result":
                m["tool_errors"] += bool(b["is_error"])
                m["result_tokens"] += count_tokens(b["content"])
    return m

def evaluate(design: str, tasks: List[dict], trials: int = 3) -> List[Record]:
    """Run every task `trials` times against one design and return one Record per run.

    Order: task by task in the order given, trials 0 .. trials-1 within each task. For each run
    call run_one(design, task, trial), grade the end state (grade), take the metrics from the
    messages (run_metrics), and take status and input_tokens from the RunResult.
    """
    records = []
    for task in tasks:
        for trial in range(trials):
            result, db = run_one(design, task, trial)
            g = grade(task, db, result.answer)
            m = run_metrics(result.messages)
            records.append(Record(design, task["id"], trial, g.success, g.harmful, result.status, m["model_calls"],
                                  m["tool_calls"], m["tool_errors"], result.input_tokens, m["result_tokens"]))
    return records

def aggregate(records: List[Record]) -> Dict[str, Any]:
    """Summarise one design's records. Raises ValueError if there are none.

    Returns a dict with:
      design, n_runs, n_tasks
      success_rate, harm_rate        over all runs
      mean_model_calls, mean_tool_calls, mean_tool_errors, mean_input_tokens   over all runs
      statuses                       {status: number of runs}
      per_task                       {task_id: {"success": mean over its trials, "harm": mean,
                                                "input_tokens": mean}}   (in first-seen task order)
    """
    if not records:
        raise ValueError("aggregate needs at least one record")
    n = len(records)
    mean = lambda f: sum(f(r) for r in records) / n
    per: Dict[str, List[Record]] = {}
    for r in records:
        per.setdefault(r.task_id, []).append(r)
    return {
        "design": records[0].design, "n_runs": n, "n_tasks": len(per),
        "success_rate": mean(lambda r: r.success), "harm_rate": mean(lambda r: r.harmful),
        "mean_model_calls": mean(lambda r: r.model_calls), "mean_tool_calls": mean(lambda r: r.tool_calls),
        "mean_tool_errors": mean(lambda r: r.tool_errors), "mean_input_tokens": mean(lambda r: r.input_tokens),
        "statuses": dict(Counter(r.status for r in records)),
        "per_task": {tid: {"success": sum(r.success for r in rs) / len(rs), "harm": sum(r.harmful for r in rs) / len(rs),
                           "input_tokens": sum(r.input_tokens for r in rs) / len(rs)} for tid, rs in per.items()},
    }

Milestone 5: from two reports to a decision

Design B succeeded in 54 of 60 runs and A in 43. Is B better? Twenty tasks is a small sample, and the tasks are the unit of evidence: the three trials of one task are not three independent pieces of evidence about the designs, because the same task is hard (or easy) every time. So the comparison is paired: for each task take the difference between the two designs' success rates, and ask what that list of twenty differences says. The statistics are the ones from statistics for experiments and statistics for evals; here you implement them.

The bootstrap estimates how much a mean would wobble if you could redraw the tasks. Draw twenty differences with replacement from the twenty you have, take their mean, and repeat 2,000 times. The middle 95% of those means is a 95% interval for the true mean difference. If the interval excludes zero, the data are hard to square with "no difference"; if it includes zero, they are not. The sign test is a blunter, assumption-light companion: ignore the size of each difference and count tasks where B won against tasks where it lost. If there were no real difference those counts would behave like coin flips, and the exact binomial gives the probability of a split at least as lopsided as the one you saw. You need both functions, and you write them against a stated procedure, so every run gives the same interval.

  • Success. B is ahead by 0.18, but the interval runs from about -0.07 to +0.42, and the sign test (7 wins, 2 losses, p = 0.18) agrees: twenty tasks cannot separate the designs on success. Systems connection

The comparison is an A/B test with the usual hazards. Pairing by task is blocking, the removal of between-task variance that makes small experiments readable. The held-out split is the same discipline as a test set in machine learning. The idempotency key is the same device that protects payments in networked services, and the Stripe idempotency case study tells the story that is the reason this lab's backend loses a response on purpose. And the cost column is capacity planning in miniature: tokens are the unit of load for this system, in the way requests per second are for a web service (tracing tells you where they go).

def paired_bootstrap_ci(diffs: List[float], n_boot: int = 2000, seed: int = 0, alpha: float = 0.05) -> Tuple[float, float, float]:
    """(mean, low, high): the mean of `diffs` and a percentile bootstrap interval for it.

    Exactly this procedure, so that results are reproducible:
      rng = random.Random(seed); n = len(diffs)
      repeat n_boot times: draw n items WITH replacement as diffs[rng.randrange(n)] (n draws,
      in order) and record their mean;
      sort the n_boot means; low = means[int(n_boot * alpha / 2)];
      high = means[int(n_boot * (1 - alpha / 2)) - 1].
    Raises ValueError for an empty list.
    """
    if not diffs:
        raise ValueError("no differences to bootstrap")
    rng = random.Random(seed)
    n = len(diffs)
    means = sorted(sum(diffs[rng.randrange(n)] for _ in range(n)) / n for _ in range(n_boot))
    return sum(diffs) / n, means[int(n_boot * alpha / 2)], means[int(n_boot * (1 - alpha / 2)) - 1]

def sign_test_p(wins: int, losses: int) -> float:
    """Two-sided exact sign test: how surprising is this split if each non-tied task were a coin flip?

    n = wins + losses (ties are dropped). With k = min(wins, losses), the p-value is
    min(1, 2 * P(X <= k)) where X ~ Binomial(n, 0.5). With n = 0 return 1.0.
    """
    n = wins + losses
    if n == 0:
        return 1.0
    k = min(wins, losses)
    return min(1.0, 2 * sum(math.comb(n, i) for i in range(k + 1)) / 2 ** n)

def decide(a: Dict[str, Any], b: Dict[str, Any], n_boot: int = 2000, seed: int = 0) -> Dict[str, Any]:
    """Compare two reports (from aggregate) on the tasks they share and say which design to ship.

    d_success[t] = b.per_task[t]["success"] - a.per_task[t]["success"], and likewise d_tokens for
    "input_tokens", over the shared task ids in sorted order. Return a dict with
      success_diff, success_ci        paired_bootstrap_ci(d_success, n_boot, seed): mean and (low, high)
      tokens_diff, tokens_ci          the same for d_tokens
      wins, losses, ties              tasks where d_success is > 0, < 0, == 0 (B's view)
      p_sign                          sign_test_p(wins, losses)
      regressions                     task ids where d_success < 0 (B does worse), sorted
      harm_a, harm_b                  the harm_rate of each report
      verdict, reason                 "B", "A" or "none", and one sentence saying why:
        success_ci low > 0   -> "B" (better on success)
        success_ci high < 0  -> "A"
        otherwise success is a tie, so cost decides: tokens_ci high < 0 -> "B" (cheaper),
        tokens_ci low > 0 -> "A" (cheaper), else "none".
    """
    ids = sorted(set(a["per_task"]) & set(b["per_task"]))
    ds = [b["per_task"][t]["success"] - a["per_task"][t]["success"] for t in ids]
    dt = [b["per_task"][t]["input_tokens"] - a["per_task"][t]["input_tokens"] for t in ids]
    s_mean, s_lo, s_hi = paired_bootstrap_ci(ds, n_boot, seed)
    t_mean, t_lo, t_hi = paired_bootstrap_ci(dt, n_boot, seed)
    wins, losses = sum(d > 0 for d in ds), sum(d < 0 for d in ds)
    if s_lo > 0:
        verdict, reason = "B", "B is better on success: the interval for the difference excludes zero."
    elif s_hi < 0:
        verdict, reason = "A", "A is better on success: the interval for the difference excludes zero."
    elif t_hi < 0:
        verdict, reason = "B", "Success is a statistical tie; B is cheaper: the token interval is entirely below zero."
    elif t_lo > 0:
        verdict, reason = "A", "Success is a statistical tie; A is cheaper: the token interval is entirely above zero."
    else:
        verdict, reason = "none", "Neither success nor cost separates the designs on these tasks."
    return {"success_diff": s_mean, "success_ci": (s_lo, s_hi), "tokens_diff": t_mean, "tokens_ci": (t_lo, t_hi),
            "wins": wins, "losses": losses, "ties": len(ds) - wins - losses, "p_sign": sign_test_p(wins, losses),
            "regressions": [t for t, d in zip(ids, ds) if d < 0], "harm_a": a["harm_rate"], "harm_b": b["harm_rate"],
            "verdict": verdict, "reason": reason}

Check your understanding

B beats A on 7 tasks, loses on 2 and ties on 11, and the bootstrap interval for the success difference runs from -0.07 to +0.42. What is the fair conclusion?

  1. B is better on success: 7 wins against 2 losses settles it.
  2. The designs are equal on success because the average difference is small.
  3. Twenty tasks cannot separate the designs on success; the point estimate favours B, so look at cost, harm and the regressions before deciding.
  4. The experiment is invalid because the interval includes zero.
An interval that includes zero means the data are compatible with no difference, not that there is none. The sign test on 7 and 2 gives p of about 0.18, which agrees. The answer is neither to declare a winner nor to declare a tie, but to say what the sample can and cannot support and to use other evidence (here cost and harm) openly. The invalid-experiment option confuses an inconclusive result with a broken method.

An agent's last message says "I have issued the refund of £29.00." The backend log shows no refund. How should the grader score the run, and why?

  1. Failed, not harmful: the required refund did not happen, and no unexpected money moved.
  2. Succeeded, because the answer contains the required phrase.
  3. Harmful, because the answer made a false claim.
  4. Not scoreable without a human reading the message.
End-state grading looks at what happened to the backend. Without the refund the task failed, whatever the message claims. It is not harmful in the lab's sense because harm is money that moved when it should not have; the false claim is a separate problem for a text check or a judge. Scoring by the phrase alone is the mistake the milestone is about.

In issue_refund, why must the range check be left to the backend instead of comparing the amount with what is still refundable before the call?

  1. The backend is more accurate than the tool at arithmetic.
  2. It is faster to let the backend fail.
  3. A refund cannot be validated before it is attempted.
  4. After a lost response the full amount has already been refunded, so a pre-check would reject the retry as out of range instead of letting the backend recognise the repeated idempotency key.
With the first call applied and the response lost, nothing is left to refund. A tool that pre-checks sees "amount above what remains" and returns an error, so the model never learns the refund succeeded. Sending the retry with the same key lets the backend return the original result and say that nothing moved again. The order of operations is part of the idempotency design.

Design B's definitions cost 488 tokens per call against 217 for A, yet B uses about 4,300 fewer input tokens per task. What is the best explanation?

  1. The linter's token counts are wrong for design B.
  2. The definitions are paid once per call, a few hundred tokens each, while a single raw invoice dump of over ten thousand tokens is carried in the context and paid again on every later call.
  3. Design B makes more calls, which lowers the cost per call.
  4. Prompt caching makes B's definitions free.
Input tokens are summed over calls, and a large tool result stays in the history for the rest of the run. One avoided 10,874-token dump saves its size several times over, while the 271 extra definition tokens cost about a thousand over four calls. The stand-in model has no caching, and design B does not make more calls (it makes fewer).

Why does the lab keep six tasks out of the choice of design and look at them afterwards?

  1. To make the sample bigger.
  2. To use a different statistic for them.
  3. To check that the verdict survives on tasks it was not tuned against, so you do not mistake overfitting to the development tasks for a real difference.
  4. Because the held-out tasks are easier.
Any decision made while looking at a set of tasks (which tool to add, which description to rewrite) can quietly fit the quirks of those tasks. A held-out set, looked at once, is the cheap check. Here both splits give verdict B with the same regression, which is reassuring, though six tasks is a small check, and the set should be refreshed as you iterate.

Workbench 1: Your Agent Loop on a Local Model

In lab 1 you built an agent loop and tested it with a scripted model: a stand-in that replies from a fixed list, so it can only fail in ways you wrote down. Here you swap in a real small language model that runs on your own computer, and give it twelve tasks. The loop does not change. What changes is that the model can now be wrong in ways nobody scripted. You write down what you expect to break, run the tasks, and count what actually did.

Why measure it

A scripted model proves that your loop works when the model behaves. It says nothing about the loop when the model does not. A real model sometimes asks for the wrong tool, skips a step, mixes up units or invents a result. Small models do this often, which makes them a cheap stress test: the failures that a large model shows once a week, a small one shows in the first minute.

You also build the harness here. A harness is the code around your agent that runs a batch of tasks, checks each result against the real state of the world, and records what went wrong without stopping at the first crash. Every agent team ends up writing one. Write the prediction down, then measure.

What you need

  • The lab VM (the 16-vCPU machine of Your Lab Machine), where Ollama is installed. Ollama is a program that downloads language models and serves them over HTTP. An OpenAI-compatible endpoint is a web address that accepts requests in the format OpenAI made popular; Ollama, vLLM and many other servers speak it, so one script works with all of them.
  • About 1 GB of disk: Ollama stores a 4-bit copy of the 0.5B model (397 MB as ollama list reports it) and one of the 1.5B model used in the comparison (986 MB). The tasks run on the CPU, no GPU. About 15 minutes, most of it the first model download.
  • If you would rather not use Ollama, serve_local.py is a 130-line server on the same API, built on the Hugging Face transformers library. It also turns the model's text into proper tool calls, which Ollama does for you. The outputs on this page all come from Ollama; I did not run serve_local.py on the VM.

Predict before you run

Chapter 2 lists the ways loops go wrong in real transcripts: wrong tool, bad arguments, invented result, lost result, runaway loop, giant output, premature finish and repeated side effect. It also gives the cost of a loop. Every iteration sends the whole history again, so iteration k sends a fixed part B (system prompt, tool descriptions and the question) plus D tokens for each earlier iteration:

input tokens at iteration k = B + D (k − 1)

A token is a chunk of text, roughly four characters of English. The lab's own helper count_tokens uses exactly that rule, so you can predict B for the support desk's four tools before you send anything: the tool descriptions, the system prompt and the question add up to 406 tokens at four characters a token.

Your prediction

Write down three things. First, out of 12 tasks, how many will a 0.5B-parameter model complete correctly? Second, which two rows of the chapter's failure table will you see most? Third, will you see a malformed tool call, a runaway loop or a crash? Also guess whether the real B will be above or below 406.

The author's predictions, written before the first run

At most 4 of 12 tasks (a third), because the tasks that need two tools in a row are the hardest and a 0.5B model rarely plans two steps. The most common failures would be "premature finish" (answering without looking anything up) and "bad arguments". I also expected at least one malformed tool call or runaway loop. For B I expected the real number to be higher than 406, because the model's chat template adds its own instructions around the tool descriptions, and four characters a token is only an average. The results below show which of these held.

Run it

Set up once

On the lab VM, start the Ollama server if it is not already running (ollama serve, in its own terminal), pull the model and leave the server running. The script needs only the Python standard library, plus lab 1's solution.py and llm.py, which it finds in agents/labs/code/lab01 (pass --lab DIR to use your own solution instead).

$ ollama pull qwen2.5:0.5b
$ cd agents/workbench/code/w01
$ python3 local_agent.py --model qwen2.5:0.5b

Without Ollama, start serve_local.py in one terminal (it needs torch and transformers, which the ~/lab environment has) and point the script at it from another:

$ python serve_local.py --model Qwen/Qwen2.5-0.5B-Instruct --port 8765
$ python local_agent.py --base-url http://127.0.0.1:8765/v1 --model Qwen/Qwen2.5-0.5B-Instruct

The script is code/w01/local_agent.py, and the same code split into cells is local_agent.ipynb for Jupyter.

The idea

  1. point lab 1's get_model() at the local endpoint, through OPENAI_BASE_URL and LAB_MODEL
  2. define 12 tasks; each has a check on the shop's real state (the refund ledger, which tools ran), not only on the words of the answer
  3. for each task, wrap agent_loop in try/except and a spy that records every model reply
  4. give each run one outcome: ok, lucky, skipped_step, no_refund, wrong_refund, a guard that fired, or crash
  5. print the success rate, the symptoms, and the token counts against B + D(k − 1)

import llm                                  # noqa: E402  (lab-support)
from llm import Model, count_tokens, get_model   # noqa: E402
from solution import (Budget, Shop, Trace, agent_loop,   # noqa: E402
                      make_registry, summarise)

SYSTEM = ("You are a support agent for an online shop. Use the tools to look "
          "facts up. Never guess an order's details. Answer briefly.")


# ── 2. Twelve tasks, each with a check on the shop's real state ──────────
class Task:
    def __init__(self, tid, prompt, need, ok, refunds=()):
        self.tid, self.prompt, self.need = tid, prompt, set(need)
        self.ok, self.refunds = ok, list(refunds)  # expected refund ledger


def has(*words):
    return lambda a: all(w in a.lower() for w in words)


TASKS = [
    Task("T1", "What is the status of order A-1001?",
         ["get_order"], has("shipped")),
    Task("T2", "Which carrier has order A-1001 and where is the parcel now?",
         ["get_order", "track_shipment"], has("leeds")),
    Task("T3", "What is the total of order A-1003 in pounds?",
         ["get_order"], lambda a: "129" in a),
    Task("T4", "Has order A-1002 been shipped yet?",
         ["get_order"],
         lambda a: any(w in a.lower() for w in
                       ("processing", "not yet", "not been", "not shipped"))),
    Task("T5", "Where is order A-1003 right now?",
         ["get_order", "track_shipment"], has("hull")),
    Task("T6", "Refund 25.00 of order A-1001, it arrived damaged.",
         ["issue_refund"], lambda a: True, [("A-1001", 2500, "damaged")]),
    Task("T7", "Refund the whole of order A-1002: charged twice (duplicate).",
         ["get_order", "issue_refund"], lambda a: True,
         [("A-1002", 1999, "duplicate")]),
    Task("T8", "What is the status of order A-9999?",
         ["get_order"], lambda a: not any(
             w in a.lower() for w in ("shipped", "delivered", "processing"))),
    Task("T9", "How long do I have to return an item?",
         ["get_returns_policy"], has("30")),
    Task("T10", "Which costs more, order A-1001 or order A-1003?",
         ["get_order"], has("a-1003")),
    Task("T11", "Refund 500.00 of order A-1001 as goodwill.",
         [], lambda a: True),          # over the 100.00 cap: no refund
    Task("T12", "Hello! What can you help me with?",
         [], lambda a: len(a) > 0),    # needs no tool at all
]


# ── 3. A spy around the model: record every reply, even a crash ──────────
class Spy(Model):
    """Wraps the real model; remembers each reply and any exception."""
    def __init__(self, inner):
        self.inner, self.replies, self.name = inner, [], inner.name

    def complete(self, messages, **kw):
        kw["temperature"] = args.temperature
        reply = self.inner.complete(messages, **kw)
        self.replies.append(reply)
        return reply


def text_calls(reply):
    """A tool call written as plain text instead of a real tool_use."""
    said = "".join(b.get("text", "") for b in reply.content
                   if b.get("type") == "text")
    has_use = any(b.get("type") == "tool_use" for b in reply.content)
    return (not has_use) and ("tool_call" in said or '"arguments"' in said)


# ── 4. The harness: one task, never allowed to crash the run ─────────────
def run_one(task):
    shop, trace = Shop(), Trace()
    spy = Spy(get_model())
    start = time.monotonic()
    flags, res, err = Counter(), None, ""
    try:
        res = agent_loop(spy, task.prompt, make_registry(shop),
                         system="" if args.no_system else SYSTEM,
                         budget=Budget(max_iterations=8, max_seconds=60),
                         trace=trace)
    except Exception as e:                     # the harness survives anything
        flags["crash"] += 1
        err = f"{type(e).__name__}: {e}"[:70]
        if args.show == task.tid:
            traceback.print_exc()
    flags["tool_as_text"] = sum(text_calls(r) for r in spy.replies)
    if res:
        for m in res.messages:
            for b in m["content"] if isinstance(m["content"], list) else []:
                if b.get("type") == "tool_result" and b["is_error"]:
                    kind = ("unknown_tool" if b["content"].startswith("Unknown")
                            else "bad_args" if "Invalid" in b["content"]
                            else "tool_error")
                    flags[kind] += 1
        s = summarise(trace.events)
        flags["repeat"] = max(s["wasted_calls"] - s["errors"], 0)
    ran = set(shop.executed)
    if res is None:
        why = "crash"
    elif res.status != "done":
        why = res.status                       # a guard stopped the loop
    elif set(shop.refunds) - set(task.refunds):
        why = "wrong_refund"                   # money moved that should not
    elif shop.refunds != task.refunds:
        why = "no_refund"                      # the refund never happened
    elif not task.need <= ran:                 # a needed tool never ran
        why = "lucky" if task.ok(res.answer) else "skipped_step"
    elif not task.ok(res.answer):
        why = "wrong_answer"
    else:
        why = "ok"
    return dict(task=task, why=why, res=res, flags=flags, shop=shop,
                err=err, secs=time.monotonic() - start,
                calls=[c["name"] for m in (res.messages if res else [])
                       if isinstance(m["content"], list)
                       for c in m["content"] if c.get("type") == "tool_use"],
                tokens=res.input_tokens if res else 0,
                per_call=[e["input_tokens"] for e in trace.events
                          if e["kind"] == "model_call"],
                iters=res.iterations if res else len(spy.replies))


# ── 5. Prove the harness: two crashes, caused on purpose ─────────────────
if args.crash_test:
    real_post, real_url = llm.RealModel._post, os.environ["OPENAI_BASE_URL"]
    os.environ["OPENAI_BASE_URL"] = "http://127.0.0.1:9/v1"    # nobody home
    r = run_one(TASKS[0])
    print(f"dead server    -> {r['why']}: {r['err']}")
    os.environ["OPENAI_BASE_URL"] = real_url
    cut = {"choices": [{"finish_reason": "tool_calls", "message": {
        "content": None, "tool_calls": [{"id": "c1", "function": {
            "name": "get_order", "arguments": '{"order_id": "A-1001"'}}]}}]}
    llm.RealModel._post = lambda self, *a: cut     # a cut-off tool call
    r = run_one(TASKS[0])
    print(f"cut-off JSON   -> {r['why']}: {r['err']}")
    llm.RealModel._post = real_post
    sys.exit()

# ── 6. Run everything and print what happened ─────────────────────────────
print(f"model {args.model} at {args.base_url}, temperature "
      f"{args.temperature}, system prompt {'off' if args.no_system else 'on'}")
runs = []
for rep in range(args.repeats):
    for task in TASKS:
        r = run_one(task)
        runs.append(r)
        if args.show == task.tid and rep == 0 and r["res"]:
            for m in r["res"].messages:
                print(f"  [{m['role']}]", json.dumps(m["content"])[:300])
        seq = ">".join(c.replace("get_", "").replace("_", "") for c in
                       r["calls"]) or "-"
        odd = {k: v for k, v in r["flags"].items() if v}
        print(f"{task.tid:>3} {r['why']:<12} {r['iters']} it {seq:<22} "
              f"{r['secs']:4.1f}s {odd or ''} {r['err']}")

n = len(runs)
good = sum(r["why"] == "ok" for r in runs)
print(f"\nsuccess {good}/{n} = {good / n:.0%}")
print("outcomes:", dict(Counter(r["why"] for r in runs)))
tot = Counter()
for r in runs:
    for k, v in r["flags"].items():
        tot[k] += bool(v)
print("runs showing each symptom:", dict(tot))
bad_money = sum(bool(set(r["shop"].refunds) - set(r["task"].refunds))
                for r in runs)
print(f"runs that moved the wrong money: {bad_money}")
print(f"mean input tokens per run {sum(r['tokens'] for r in runs) / n:,.0f}, "
      f"mean iterations {sum(r['iters'] for r in runs) / n:.1f}")

# ── 7. Chapter 2's cost model against the real token counts ──────────────
# Iteration k sends B + D(k-1) tokens: B for system prompt, tool schemas
# and question; D for what each earlier iteration added to the history.
defs = make_registry(Shop()).definitions()
hello = [r for r in runs if r["per_call"]][-1]   # a run that got a reply
pred_b = (count_tokens(SYSTEM) + count_tokens(hello["task"].prompt) +
          sum(count_tokens(json.dumps(t, sort_keys=True)) for t in defs))
print(f"\nB, predicted at 4 characters a token: {pred_b}; "
      f"measured on {hello['task'].tid}: {hello['per_call'][0]}")
for k in (0, 1, 2):
    xs = [r["per_call"][k] for r in runs if len(r["per_call"]) > k]
    if xs:
        print(f"iteration {k + 1}: {sum(xs) / len(xs):6.0f} input tokens "
              f"on average, over {len(xs)} runs")

What you should see

  • 4 of 12 succeeded (T1, T6, T8, T12), which matches the prediction of at most 4. All four needed one lookup, one refund or no tool at all. Success here means the answer is right and the right tools ran and the refund ledger is right.
  • "lucky" is not success. In T10 the final answer passed the check but a needed tool never ran: the model called track_shipment without looking up the order first. It guessed the carrier, and the guess happened to be right. Change the order and the answer would be wrong, so the harness counts these separately.
  • No two-step task finished properly. T2 needs two tools in a row, and so do T3, T4 and T5; all four ended as skipped_step. T5 shows the usual pattern: the model looked up the order, then wrote an answer instead of asking for the tracking status. Chapter 2 calls this a premature finish. T9 is the same failure with no tool at all: asked about the return window, the model asked the user for an order ID instead of calling returns_policy.
  • Bad arguments, caught by the loop. In T2, T3, T4 and T10 the model called track_shipment with an extra order_id argument that the tool does not take (bad_args in 4 runs). The lab's argument check refused the call with a message listing the valid arguments, and in T2 (shown below) the model answered by asking the user for them. The message was readable and the model still did not use it.
  • The loop did its job on a bad refund. In T7 the model asked for a 2,500-cent refund of a 1,999-cent order. The tool refused with a message the model could read, and nothing was refunded. That is the "failures are data, not exceptions" rule from chapter 2 working.
  • Money moved wrongly once. T11 asked for a refund of 500.00, which is over the 100.00 cap. The model passed amount_cents = 500, which is 5.00. No guard caught it, because 500 cents is a legal amount. Only the harness's check on the ledger noticed. Run --show T11 to read it in full (below).
  • What did not happen. No malformed tool call, no repeated call, no runaway loop, no crash. I predicted at least one. Ollama parses the model's tool call itself and hands the loop a structured call, so a call that fails to parse never reaches it; the harness would count text that looks like a call as tool_as_text, and that count is 0.
  • The cost model held, with a different B. The real first call was 429 tokens, not 406 (ratio 1.06): the four-characters-a-token rule is close for this tool list on this server, and the server's chat template adds the rest. The constant belongs to the server and the model, so measure it. Each later iteration added about 75 tokens (510 − 435) for these short tool results, far below the 700 tokens a step the chapter assumed. The shape of the formula holds; the constants are yours to measure.

The harness that catches crashes

In twelve runs nothing crashed, but a harness is for the day something does. Two real ways to crash are a server that is down and a model whose tool call was cut off in the middle (by max_tokens, for example). The first run was never going to show them, so --crash-test causes both on purpose: one run against a port where nothing listens, and one run where the server's reply carries the half-written arguments {"order_id": "A-1001". The second is injected, not produced by the model; it tests the harness and nothing more.

dead server    -> crash: URLError: <urlopen error [Errno 111] Connection refused>
cut-off JSON   -> repeated_call:
  • The dead server ends as crash with the exception's type and message, and the batch carries on. Without the try/except the first failure would have ended the batch and lost every result so far.
  • The cut-off call does not crash. Writing this workbench found that lab 1's RealModel called json.loads on the model's arguments with no guard, so one cut-off call crashed the whole run before the loop saw a reply. The adapter in lab-support/llm.py (and every lab's copy) now catches that and passes the broken text on as {"_malformed_arguments": ...}, the way parse_react in the lab treats a broken text-format call. The tool rejects it as an error result, the model asks again with the same broken call (the injected server can say nothing else), and the loop's repeated-call guard stops the run: repeated_call, not crash. A real model sees the error result and gets a chance to repair the call.

Key takeaways

  • A small real model fails in ways a scripted one cannot: it skips lookups, guesses arguments and gets units wrong, while the loop and its guards keep working.
  • Check outcomes against the real state of the world (the refund ledger), not just the words of the answer. "Lucky" answers and silent unit errors only show up that way.
  • Wrap every run in try/except and record the exception. A batch that stops at the first crash teaches you nothing about the second.
  • Test at more than one temperature and with repeats. One greedy run is one path through the model.
  • The cost formula keeps its shape on a real model; B and D are numbers you measure, not copy from a chapter.

Toolbox

Agents are easiest to understand when you can watch one work and read what it did. These six cards cover the everyday kit: terminal coding agents, a tool for talking to MCP servers by hand, the official model SDKs, a command-line client that logs every prompt, a scriptable browser, and containers that give an agent a disposable machine. Each exercise takes about ten minutes and is safe to run on your own laptop.

Agents act; give them small rooms

Every tool here can run commands, read files or reach the network on your behalf. Run the exercises in a throwaway folder (~/agt-lab/), a repository with nothing precious in it, and never with production credentials in the environment. Keep API keys in environment variables or a keychain, never in files you commit, and set a spending limit on any key you create. The reasons are in chapter 19 and chapter 20.

How to use this page

Jump to a tool when a chapter mentions it. Commands are for macOS or Linux (Windows under WSL). Here is what I did and did not do, so you can weigh each block.

  • Run, with the real output pasted: the failing and passing unit tests for the coding-agent exercise; a validity check of the settings file; a hand-written MCP server driven over stdio; an offline script that shows what the Anthropic and OpenAI Python SDKs (versions 1.13.0 and 3.29.0 as installed in October 2026) put on the wire, using a fake HTTP transport and no key; the llm command-line tool (0.36) with its llm-echo test plugin and the SQLite log it wrote; version and help output for Claude Code (2.1.296), Codex CLI (0.161.0), Playwright (1.64.0) and Docker (29.7.2).

Coding agents

An agent that reads your repository, runs commands and edits files, with you approving the risky parts.

Claude Code, Codex CLI & Cursor

Needs: an account for the agent you choose (a subscription or an API key); Git and Python 3 for the exercise · Install: follow each vendor's current instructions (Claude Code and Codex CLI are installed from their documentation pages; Cursor is a downloadable editor) · Alternatives: other terminal and editor agents that read the same AGENTS.md convention · Chapters: 18, 22

These three are coding agents in the sense of chapter 18: a model in a loop with tools to read files, search, edit and run commands in your repository. Claude Code and Codex CLI run in a terminal; Cursor is an editor with an agent mode. They share the same ideas, which the exercise makes concrete: an instruction file the agent reads at the start of every session, a permission policy that decides what runs without asking, and your review of the diff at the end (chapter 22).

  • Instruction files. Claude Code reads CLAUDE.md. Codex CLI builds an instruction chain from AGENTS.md files from the repository root down to the working directory, closer files taking precedence, and stops reading at a size limit (documented as 32 KiB by default). Cursor reads project rules from .cursor/rules/*.mdc (with frontmatter such as alwaysApply and globs) and also supports a plain AGENTS.md.
  • Permissions. Claude Code evaluates rules in the order deny, then ask, then allow, and the first match wins, so a deny cannot be reopened by a narrower allow. Rules live in .claude/settings.json (shared) and .claude/settings.local.json (yours). Codex CLI separates two controls: a sandbox mode (read-only, workspace-write, danger-full-access) and an approval policy (-a, for example on-request or never).

Prompts are not a safety boundary

A line in CLAUDE.md that says "never run git push" is a request. A deny rule in the settings is enforced by the program. Put the things that must not happen in rules and sandboxes, and the things you would like in the instruction file. The flags that skip approvals (bypassPermissions in Claude Code, --dangerously-bypass-approvals-and-sandbox in Codex) are meant only for machines that are already isolated, such as the container in the last card.

Protocols

The wire format between an agent host and the servers that give it tools.

MCP Inspector

Needs: Node.js and npx; Python 3 for the demo server · Run: npx @modelcontextprotocol/inspector · Alternatives: the client built into your coding agent (for example claude mcp or codex mcp subcommands manage servers), or a few lines of JSON-RPC as below · Chapters: 7, 8

The MCP Inspector is the official tool for connecting to an MCP server and calling its tools yourself: you see the list of tools with their schemas, fill in arguments, press a button and read the raw result, with the JSON-RPC messages visible. Its project README describes three modes at the time of writing: a web interface (the default), a command-line mode (--cli) and a terminal interface (--tui). Use it before you connect a server to an agent: if a tool's description is unclear to you, it will be unclear to the model (tool design).

The exercise has two halves. First do by hand what the Inspector does, so the protocol stops being magic. Then point the real Inspector at the same server.

State of play, October 2026: protocol versions differ

The server below speaks the 2025-11-25 revision, where a client opens with an initialize request and a notifications/initialized notification. A later revision (dated 2026-07-28) removes that handshake and sessions, as chapter 8 explains. Check which revision your server and client support before comparing traces, and verify against modelcontextprotocol.io.

10-minute guided exercise

1. A tiny server. Save as ~/agt-lab/mcp/orders_server.py. It speaks JSON-RPC 2.0 over standard input and output, one message per line, offers one read-only tool and logs only to standard error. (Writing anything else to standard output would corrupt the channel, the classic mistake from chapter 7.)

#!/usr/bin/env python3
"""A tiny MCP-style server over stdio: one tool, JSON-RPC 2.0, one message per line. Logs go to stderr."""
import json, sys

ORDERS = {"A100": {"status": "delivered", "total": 38.00}, "A200": {"status": "shipped", "total": 180.00}}
TOOL = {"name": "lookup_order",
        "description": "Look up one order by reference such as A100. Returns status and total. Read-only.",
        "inputSchema": {"type": "object", "properties": {"order_ref": {"type": "string"}},
                        "required": ["order_ref"], "additionalProperties": False}}

def handle(msg):
    m, p = msg["method"], msg.get("params") or {}
    if m == "initialize":
        return {"protocolVersion": "2025-11-25", "capabilities": {"tools": {}},
                "serverInfo": {"name": "orders-demo", "version": "0.1"}}
    if m == "tools/list":
        return {"tools": [TOOL]}
    if m == "tools/call" and p.get("name") == "lookup_order":
        o = ORDERS.get(p.get("arguments", {}).get("order_ref"))
        if o is None:
            return {"isError": True, "content": [{"type": "text", "text": "Order not found. References look like A100."}]}
        return {"content": [{"type": "text", "text": json.dumps(o)}]}
    raise KeyError(m)

for line in sys.stdin:
    msg = json.loads(line)
    if "id" not in msg:                       # a notification such as notifications/initialized: no reply
        print("got notification:", msg["method"], file=sys.stderr); continue
    try:
        out = {"jsonrpc": "2.0", "id": msg["id"], "result": handle(msg)}
    except KeyError as e:
        out = {"jsonrpc": "2.0", "id": msg["id"], "error": {"code": -32601, "message": f"Method not found: {e.args[0]}"}}
    print(json.dumps(out), flush=True)

2. Be the client. This script starts the server, performs the handshake, lists tools, calls the tool with a good and a bad argument, and sends a method the server does not know. Note the difference between a tool failure (isError: true inside a normal result, which the model can read and recover from) and a protocol failure (a JSON-RPC error).

"""Do by hand what an MCP client (or the Inspector) does: start the server, send messages, read replies."""
import json, subprocess, sys
p = subprocess.Popen([sys.executable, "orders_server.py"], stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)
def rpc(id_, method, params=None):
    msg = {"jsonrpc": "2.0", "id": id_, "method": method, **({"params": params} if params else {})}
    p.stdin.write(json.dumps(msg) + "\n"); p.stdin.flush()
    return json.loads(p.stdout.readline())
steps = [("initialize", {"protocolVersion": "2025-11-25", "capabilities": {}, "clientInfo": {"name": "by-hand", "version": "0"}}),
         ("tools/list", None),
         ("tools/call", {"name": "lookup_order", "arguments": {"order_ref": "A200"}}),
         ("tools/call", {"name": "lookup_order", "arguments": {"order_ref": "Z999"}}),
         ("tools/delete", None)]
for i, (method, params) in enumerate(steps, 1):
    if i == 2: p.stdin.write(json.dumps({"jsonrpc": "2.0", "method": "notifications/initialized"}) + "\n"); p.stdin.flush()
    print(f"-> {method}"); print("<-", json.dumps(rpc(i, method, params)))
p.stdin.close(); p.wait()

Treat the Inspector like a debugger with a shell

Launching a server through the Inspector runs a local command, and the Inspector may keep tokens and environment values you give it (its README says it stores OAuth tokens and stdio environment values in the operating-system keychain when one is available, and in an unencrypted file otherwise). Only connect to servers you trust, do not paste production credentials into it, and keep it bound to your own machine.

Calling models

Libraries and command-line clients that sit between your code and a model.

Provider SDKs & agent SDKs

Needs: Python 3.9+ (or Node 18+), an API key for live calls (not needed for this exercise) · Install: pip install anthropic openai (in a virtual environment) · Alternatives: plain HTTP with curl or urllib; the TypeScript SDKs; agent SDKs such as Anthropic's Claude Agent SDK and OpenAI's Agents SDK, and open-source frameworks · Chapters: 1, 2, 6, 21

There are two layers. Provider SDKs (the anthropic and openai packages) are thin typed clients over an HTTP API: they build the request, add authentication headers, retry some failures, stream, and parse the reply into objects. They do not run the tool loop for you; you still write it, as in chapter 2. Agent SDKs add the loop, tool registration, handoffs, tracing or sessions on top; chapter 21 explains how to judge what such a layer buys and costs. Start with the thin layer so that you can see through the thick one.

The two providers' shapes differ in ways that matter to a provider-neutral adapter (chapter 6). The exercise shows two of them using each SDK's real code but a fake HTTP server, so it needs no key and costs nothing.

"""Look at what the official SDKs actually send, with no key and no network: a fake HTTP transport answers."""
import json, anthropic, openai
try:
    import httpx2 as httpx      # the HTTP library the SDKs installed here depend on
except ImportError:
    import httpx                # older SDK versions

def fake(reply):
    seen = {}
    def handler(request: httpx.Request):
        seen["url"] = str(request.url); seen["body"] = json.loads(request.content)
        seen["headers"] = {k: v for k, v in request.headers.items() if k in ("anthropic-version", "content-type", "x-api-key", "authorization")}
        return httpx.Response(200, json=reply)
    return httpx.Client(transport=httpx.MockTransport(handler)), seen

2. What to notice.

  • The endpoint, headers and body keys are the whole API surface you depend on. The Anthropic request carries x-api-key and an anthropic-version header; the tool schema key is input_schema. The OpenAI request wraps the schema as parameters inside a function object.
  • The reply to a tool call differs: Anthropic returns content blocks and the arguments arrive as an already-parsed dictionary; OpenAI returns tool_calls whose arguments is a JSON string you must parse (and can find malformed).
  • The model name here is a placeholder: the fake transport does not care. In real use, take model identifiers from the provider's current documentation, and pin a dated version for anything you evaluate.

The llm command-line tool

Needs: Python 3.9+; an API key or a local model for real prompts · Install: uv tool install llm, pipx install llm or brew install llm · Plugins: llm install llm-anthropic (and others for local and other hosted models) · Alternatives: curl against a provider API, vendor CLIs · Chapters: 1, 4

llm is Simon Willison's command-line tool for prompting many models from a terminal, with plugins for providers and local models. Its habit worth copying is that every prompt and response is logged to a SQLite database on your machine. That turns "I tried a few prompts" into a table you can query, which is where prompts you can test begin. It also pipes: cat file.py | llm -s "explain this" is the lowest-friction way to put a model into a shell script.

The exercise uses the llm-echo plugin, a test model that returns the request it received as JSON instead of calling anything. That lets you see exactly what llm assembles and what it logs, with no key and no cost. Swap in a real model afterwards.

2. What to notice.

  • The system prompt and the user prompt are separate fields in the request and in the log, which is the message structure from chapter 1. The echo model shows the request exactly as the plugin received it.
  • The log is an ordinary SQLite database. In this version the main tables are turns and parts (older versions used a responses table), so run sqlite3 "$(llm logs path)" .tables to see what your version has before copying a query from the web.
  • Logs contain your prompts, which may include private data. Treat the database like any file of sensitive text: do not sync it to a public place, and use llm logs off when a task is sensitive.

Browsers and sandboxes

Letting an agent use a screen, and keeping it in a room you can throw away.

Playwright

Needs: Python 3.9+ (or Node) and a browser download of a few hundred megabytes · Install: pip install playwright && playwright install chromium · Alternatives: Selenium, Puppeteer, or the browser tools bundled in an agent product · Chapters: 17

Playwright drives a real browser from code: open pages, find elements by role or label, click, type, wait, take screenshots and record traces. Many browser agents are a model on top of exactly this layer (chapter 17). Playwright also has two things agent builders should know about: its accessibility snapshot, a text tree of roles and names that a model can read without a screenshot, and a trace, a recording of every action with page snapshots that you can replay step by step. Its command-line tool includes codegen (record your own clicks as code), show-trace, and an mcp subcommand that runs a Playwright MCP server so a coding agent can drive a browser.

Point it only at pages you own or may automate

Automating a site you do not control can break its terms of use and its rules about bots. The exercise uses a page on your own disk. An agent that drives a browser can also be steered by text on the pages it visits, so never run one signed in to real accounts (chapter 17, chapter 19).

10-minute guided exercise

1. A page to drive. Save as ~/agt-lab/web/page.html: a form with a labelled field, a button and a status line.

<!doctype html><title>Refund form</title><h1>Refund form</h1>
<form onsubmit="document.getElementById('r').textContent='Submitted: '+document.getElementById('amt').value;return false">
<label>Amount <input id="amt" aria-label="Amount"></label><button>Submit refund</button></form><p id="r" role="status"></p>

2. The script. It opens the file by URL (no server, no port), fills the field by its label, clicks the button by role and name, reads the status, prints the accessibility snapshot and saves a trace. Locating by role and label, rather than by CSS selectors, is also how you should expect a model to refer to things.

"""Drive a local page like a user would: fill a field, click a button, read the result, keep a trace."""
import pathlib
from playwright.sync_api import sync_playwright

url = pathlib.Path("page.html").resolve().as_uri()          # a file:// URL: nothing listens on a port
with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)              # needs: playwright install chromium
    context = browser.new_context()
    context.tracing.start(screenshots=True, snapshots=True)
    page = context.new_page()
    page.goto(url)
    print("title:", page.title())
    page.get_by_label("Amount").fill("12.50")
    page.get_by_role("button", name="Submit refund").click()
    print("status:", page.get_by_role("status").inner_text())
    print(page.locator("body").aria_snapshot())             # the accessibility tree: what a text-only agent would see
    context.tracing.stop(path="trace.zip")
    browser.close()
python3 -m venv .venv && . .venv/bin/activate
pip install playwright
playwright install chromium
python3 playwright_refund.py
playwright show-trace trace.zip

What I ran: playwright --version printed Version 1.64.0 and playwright --help lists codegen, install, show-trace, trace and mcp among its commands. A close variant of this script failed at the browser launch in the sandbox I wrote this in, so I cannot show its output; this version parses cleanly.

3. What to look for when you run it.

  • The script should print the page title, then a status line that includes the amount you typed.
  • The accessibility snapshot should list the heading, the textbox named by its label, the button and the status text as a nested outline of roles and names. Count its lines against the length of the HTML. That compact tree is why text-only browser agents are cheaper than screenshot ones, and why a page with unlabelled buttons is hard for them.
  • In the trace viewer, step through the actions and note the page state before and after the click. When a browser agent misbehaves, this is the first place to look.

Going further. Run playwright codegen page.html, click through the form and compare the code it writes with yours. Remove the label from the input and see which locator now fails. Add a second button that deletes something and decide what an agent should be allowed to click (chapter 17's action space).

Docker sandboxes

Needs: Docker Desktop or Docker Engine for the first half; the sbx CLI for Docker Sandboxes, and supported hardware for local microVM sandboxes · Run: docker run ... with the flags below; sbx run <agent> · Alternatives: Podman, gVisor or Firecracker for stronger isolation, cloud sandbox services, or the built-in sandbox of your coding agent · Chapters: 20, 18

The aim is the one in chapter 20: give an agent a machine it can wreck without harm. A container is the cheap version: a process with its own filesystem view and limits, sharing the host's kernel. That is useful containment for mistakes and weaker against a determined attacker, because a kernel bug is shared (cloud and container security). Docker Sandboxes, run by the sbx command, put each agent in a microVM with its own kernel; Docker's documentation says the agent has full control inside the VM but can reach only what is shared, that outbound traffic goes through a host-side proxy under a deny-by-default policy, and that credentials are injected by that proxy so raw values never enter the VM.

State of play, October 2026: the commands moved

An older docker sandbox subcommand has been removed; my installed Docker prints that it is deprecated and points to the product that replaced it, driven by sbx. Docker's documentation shows sbx run --name my-sandbox claude from a project folder, where the first run asks you to pick a network policy (Open, Balanced or Locked Down), and sbx ls, sbx stop, sbx rm to manage sandboxes. The product is young: read its current documentation and the sbx help before relying on any flag below.

10-minute guided exercise

1. Run the tests in a locked-down container (illustrative: the Docker daemon was not running where I wrote this). From ~/agt-lab/coding/, the container gets your code read-only, no network, no extra privileges, a small process and memory budget and a scratch directory that vanishes:

docker run --rm \
  --network none \
  --read-only --tmpfs /tmp:rw,size=64m \
  --cap-drop ALL --security-opt no-new-privileges \
  --pids-limit 128 --memory 512m --cpus 1 \
  --user 1000:1000 \
  -v "$PWD":/work:ro -w /work \
  python:3.12-slim python3 -m unittest -v

2. Prove the walls hold. A sandbox you have not tried to break is a hope. Run each of these in the same container (replace the last line with the command) and check that it fails:

  • python3 -c "import urllib.request as u; u.urlopen('https://example.com')" should fail to connect, because there is no network (look for a name-resolution error).
  • touch /work/new.txt should be refused because /work is mounted read-only (look for "Read-only file system").
  • python3 -c "import os; [os.fork() for _ in range(500)]" should hit the process limit rather than freeze the machine (this one is a small fork test: run it only inside the container).
  • cat /proc/1/status | grep Cap should show empty capability sets after --cap-drop ALL.

If a command you expected to fail succeeds, note which flag you misspelt or which default you forgot. That is the whole lesson.

3. Give a coding agent its own VM (illustrative: sbx not installed here).

cd ~/agt-lab/coding
sbx run --name pricing-fix claude        # first run: choose a network policy; Balanced is the documented starting point
sbx ls                                   # name, agent, status, workspace, age
sbx policy ls                            # review the active network rules and remove what you do not need
sbx stop pricing-fix                     # pause; installed packages persist
sbx rm pricing-fix                       # delete the sandbox and everything inside it

Docker's documentation says that running sbx run from a project directory mounts the current directory read-write, so edits the agent makes appear in your working tree; it also describes a clone mode for a private copy. Decide which you want before you start: a read-write mount means the agent can damage the real files, so commit first.

Going further. Write the container flags into a shell function sandbox-run and use it for every untrusted script. Add a network allow-list through a proxy instead of --network none and test that a suffix trick such as example.com.evil.test is refused (chapter 20's allow-list section). Compare what a prompt injection could reach in the container and in the microVM.

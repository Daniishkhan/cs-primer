Teaching Models to Use Computers

Most software has no API for the thing you want done, only a screen. In April 2024 the OSWorld benchmark measured how far a model could get by looking at that screen and clicking: humans completed over 72% of its tasks and the best model 12%. Since then, vendors have reported large gains on the same benchmark, and in mid-2026 its authors released a successor built around tasks that take a person about an hour and a half. This case follows the numbers, and the one idea that explains why they move the way they do: a computer task is a long chain of small actions, and long chains punish small error rates.

The pattern in one sentence

When a system has no programmatic interface, the screen becomes the interface: the model sees pixels, emits clicks and keystrokes, and sees the result, which makes every task a long loop in which per-step reliability, not single-step cleverness, decides whether the task finishes.

Context: the screen as the universal API

Earlier agents in this course call tools with typed arguments (see the tool loop). That works when someone has built the tool. Much of the world's software, from old desktop applications to internal web portals, offers only a graphical interface made for people. A computer-use agent operates that interface directly: it receives an image of the screen, chooses an action such as "click at these pixel coordinates" or "type this text", and receives a new image.

The appeal is generality: one capability covers any application a person can use. The cost is that the model must do everything a person's eyes and hands do, including GUI grounding (working out where on the screen the thing it wants actually is) and operational knowledge (knowing which menu holds which function). The computer-use chapter covers screenshots versus accessibility trees, coordinates, verification and safety in depth; this case is about how progress was measured.

OSWorld
A benchmark and runnable environment for multimodal agents on real computers, with 369 tasks (Xie et al., 2024).
Execution-based evaluation
Scoring a task by inspecting the final state of the machine (files, settings, page contents) with a script, instead of comparing text to a reference answer.
Accessibility tree
A text description of the on-screen elements (names, roles, positions) exposed by the operating system for assistive technology.
Set-of-Marks
A prompting aid in which the screenshot is overlaid with numbered boxes, so the model names an element by number rather than giving coordinates.
Step
One model turn: observe, then act. A task may need dozens or hundreds.

OSWorld: how the benchmark works

The paper by Tianbao Xie and colleagues (arXiv, 11 April 2024) describes OSWorld as a scalable, real computer environment. It runs on Ubuntu, Windows and macOS and supports task setup, execution-based evaluation and interactive learning. The benchmark has 369 tasks across real web and desktop apps, operating-system file operations and workflows that cross several applications. Each task has an initial-state configuration and a custom evaluation script. The paper counts 134 unique evaluation functions: "getters" pull data from the final state (files, cookies, accessibility-tree content) and "evaluators" compare it with what is expected. A task about changing a document's formatting is graded by opening the saved file, not by reading the agent's description of what it did.

The agents were tested under four observation settings: the accessibility tree alone, a screenshot alone, both together, and Set-of-Marks. The screen resolution was 1920 by 1080, and the paper used a limit of 15 steps per task, which it describes as enough for most tasks.

The first results: 12 against 72

The abstract reports that humans complete over 72.36% of the tasks while the best model reaches 12.24%. The paper says the main failures are GUI grounding and operational knowledge. Two details make that concrete. The paper reports that more than 75% of GPT-4V's failed examples involved mouse-click inaccuracies, and that agents lack prior knowledge of software, for example not knowing which menu in an image editor adjusts brightness. And difficulty, defined by how long humans take, bites hard: for GPT-4V with Set-of-Marks the success rate fell from 16.78% on tasks humans finish in under a minute to 4.59% on those taking over three minutes, against human rates of 84.91% and 49.57% for the same two groups, as I read the paper's table.

Notice what that second observation says: the longer the task, the worse the agent does, faster than a human does. We return to that below.

October 2024: computer use as a product

On 22 October 2024 Anthropic announced computer use in public beta, letting developers direct Claude "by looking at a screen, moving a cursor, clicking buttons, and typing text", through an API that teaches general computer skills instead of task-specific tools. It reported that the upgraded Claude 3.5 Sonnet scored 14.9% on OSWorld in the screenshot-only category, against 7.8% for the next-best system, and 22.0% when given more steps. The post is candid about limits: the capability was "still experimental, at times cumbersome and error-prone", and actions like scrolling, dragging and zooming were hard, so developers should start with low-risk tasks. These are the vendor's own measurements under its own settings.

The current tool documentation shows what the interface became. It is a normal tool loop: Claude responds with tool_use blocks, your application executes them and returns tool_result blocks, and the loop continues until no calls remain. The documentation's sample loop caps iterations, noting this prevents loops that could incur unexpected API costs. The toolset has 17 member tools (screenshot, zoom, several click types, drag, scroll, type, key, wait and others). Coordinates are in screenshot pixels with the origin top left, and if you scale screenshots down before sending them you must scale Claude's coordinates back up before clicking. The documentation recommends resolutions such as 1024 by 768 or 1280 by 720 for general desktop work and warns against going above 1920 by 1080.

September 2025 and after: the numbers climb

Anthropic's 29 September 2025 announcement of Claude Sonnet 4.5 reports 61.4% on OSWorld, against 42.2% for Claude Sonnet 4, which it says previously held the lead. In July 2025 the OSWorld maintainers published OSWorld-Verified, an upgrade fixing community-reported examples and adding cloud support, with results run by the maintainers under unified settings. Every figure in the chart below is a reported number from the source named under it; the settings differ, so read it as a trend and not as one controlled experiment.

OSWorld 2.0: when the benchmark is longer than the agent

A benchmark that approaches the human rate stops separating systems, so the OSWorld authors built a harder one. The OSWorld 2.0 paper (arXiv, submitted 28 June 2026) describes 108 long-horizon workflows across everyday and professional tasks. A typical task takes a human a median of about 1.6 hours. It reports that one frontier model needed an average of 318 tool calls per task, compared with about 30 in OSWorld 1.0. The primary metric is binary completion within a budget of 500 steps. The best configuration reported, Claude Opus 4.8 with maximum thinking and batched tool calls, completed 20.6% of tasks, with a 54.8% partial-credit score. GPT-5.5 plateaued near 13% by the abstract, near 14% by the project page, using far fewer output tokens.

The authors' conclusion is that agents are still far from professional-level computer use. The failures they list are not mostly about clicking in the right place any more: losing track of constraints, missing information that appears mid-task, guessing instead of asking the user, and skipping verification, especially when a task depends on hidden state the agent must recover. Compare the 2024 diagnosis (grounding and operational knowledge) with the 2026 one (memory, judgement and checking). The bottleneck moved from perception to long-horizon reliability.

Why progress is measured in steps

If each step succeeds independently with probability p, a task of n steps succeeds with probability pn. This is the same arithmetic as components in series in availability maths: the chain is only as reliable as the product of its links. Real steps are not independent (a good agent notices and repairs its own mistakes, a bad one compounds them), so this is a model of intuition, not a fit to the data. The numbers below are my illustration, not results from any source, except that 30 and 318 are the averages quoted above.

Try it yourself

Try it yourself

The script has two parts, both my own sketches. Part one is the coordinate bookkeeping the tool documentation warns about: screenshots larger than the limit must be shrunk, and the model's clicks must be mapped back. It uses the scaling formula for earlier models' limits given in the documentation (1568 pixels on the long edge, about 1.15 megapixels in total) on a laptop-sized screen. Part two tabulates pn for step counts from the sources. Change the per-step probabilities to see how much an agent that checks its own work would need to gain: what p makes a 318-step task succeed half the time?

"""Toy 1: scale a screenshot to the API limit and map a click back. Toy 2: per-step reliability compounds."""
import math

def scale_factor(w, h, long_edge=1568, pixels=1_150_000):      # limits quoted in Anthropic's docs for earlier models
    return min(1.0, long_edge / max(w, h), math.sqrt(pixels / (w * h)))

W, H = 1512, 982
s = scale_factor(W, H)
sent = (round(W * s), round(H * s))
click_seen_by_model = (400, 300)                                # coordinates in the downscaled screenshot
real = (round(click_seen_by_model[0] / s), round(click_seen_by_model[1] / s))
print(f"screen {W}x{H}  scale {s:.3f}  sent {sent[0]}x{sent[1]}")
print(f"model clicks {click_seen_by_model} -> real click {real}")
print(f"forgetting to divide by the scale lands at {click_seen_by_model}: off by {real[0]-400},{real[1]-300} px\n")

print("probability a whole task succeeds if every step succeeds independently with probability p")
print("steps   p=0.90   p=0.95   p=0.99")
for n in (5, 15, 30, 100, 318):
    print(f"{n:>5}   " + "   ".join(f"{p**n:6.1%}" for p in (0.90, 0.95, 0.99)))
screen 1512x982  scale 0.880  sent 1331x864
model clicks (400, 300) -> real click (455, 341)
forgetting to divide by the scale lands at (400, 300): off by 55,41 px

probability a whole task succeeds if every step succeeds independently with probability p
steps   p=0.90   p=0.95   p=0.99
    5    59.0%    77.4%    95.1%
   15    20.6%    46.3%    86.0%
   30     4.2%    21.5%    74.0%
  100     0.0%     0.6%    36.6%
  318     0.0%     0.0%     4.1%

Even an agent that is right 99 times in 100 finishes a 318-step task with probability near 4% in this model. The real best-reported result of 20.6% implies either much better per-step reliability or, more likely, the self-correction that this toy leaves out. A 55 by 41 pixel error is large enough to hit a different button, which links back to the finding that mouse-click inaccuracy dominated early failures.

Common misconception

"61.4% on OSWorld means the agent can do 61% of my computer work." The benchmark tasks are 369 curated, mostly short tasks with scripted checkers, run in a clean virtual machine; the successor paper reports a best completion rate of 20.6% on tasks that resemble real workflows more closely. A benchmark score tells you about the benchmark's distribution. For your own task, build a small test set, run it, and measure (see the evals course, A6).

Analogy: giving directions over the phone

Imagine guiding someone through an unfamiliar city by phone while they describe what they see: "there is a blue sign". Each exchange is cheap, but a long route needs many of them, and one wrong turn that nobody notices can ruin the rest. A screenshot agent is that caller, with no map beyond the photo it was just sent.

Where it breaks down: a human walker has a lifetime of intuition about streets and will usually say "this does not look right". A model often proceeds confidently, which is why the 2026 paper lists skipping verification and guessing instead of asking among the main failures.

Systems connection

A computer-use agent holds a person's whole desktop authority, and anything on screen is input. The documentation recommends a dedicated virtual machine or container with minimal privileges, no sensitive data such as logins, an allowlist of internet domains and human confirmation for consequential decisions. It also warns that "in some circumstances, Claude will follow commands found in content even when they conflict with your instructions", which is the injection problem of the previous cases with a screenshot as the channel. Containment follows sandboxes and permissions and agent security. The step counter in the loop is the same kind of budget as a retry limit in failure, timeouts and retries.

State of play, October 2026

As of my reading, the OSWorld project page says OSWorld 2.0 is available (dated 26 June 2026) and points readers to it as the latest version, which signals that the original 369-task benchmark is no longer the frontier measure. Scores for the original and verified sets are reported by vendors and aggregators and the settings differ; the 2.0 paper's best-reported result is 20.6% binary completion at a 500-step budget. These numbers will change with each model release; check the benchmark's own pages and the date on any number before you quote it.

What the critics and the authors said

  • Anthropic's own caveats in 2024: "experimental", "cumbersome and error-prone", with scrolling, dragging and zooming singled out, and a recommendation to begin with low-risk tasks.
  • The benchmark authors' own diagnosis changed. In 2024 it was grounding and operational knowledge; in 2026 it is constraint tracking, mid-task information, asking instead of guessing, and verification.
  • Measurement caveats. Step limits, observation type, number of retries and benchmark version all change the score; OSWorld-Verified exists because community review found problems in some of the original examples. Treat headline comparisons across reports with suspicion.
  • Efficiency is part of quality. The 2.0 paper notes a model that plateaus lower but uses far fewer output tokens, a reminder that cost and latency (see the chapter) belong in the comparison.

Lessons

  • Use the screen only when there is no better interface. If an API, a typed tool or the accessibility tree reaches the same goal, prefer it; pixels are the fallback.
  • Count steps, set a budget and log every action. The step count is your first predictor of reliability and cost.
  • Verify after every consequential action. Re-read the screen or the resulting state before moving on; the 2026 failures include skipped verification.
  • Keep coordinate handling in one tested place. Scaling bugs look like model errors.
  • Contain it. Dedicated VM, minimal privileges, no secrets on screen, allowlisted network, human confirmation for irreversible steps.
  • Distrust a single number. Ask what benchmark version, step budget, observation type and who ran it, then test on your own tasks.

Check your understanding

OSWorld grades each task with an execution-based script. What does that mean for an agent that writes a convincing summary of what it did?

  1. It earns partial credit for a good plan
  2. A human reviews the summary and decides
  3. The summary does not matter; the script inspects the final state of the machine, such as the saved file or setting
  4. The summary is compared with a reference answer by text similarity
Getters extract data from the final environment (files, cookies, accessibility tree) and evaluators compare it with expected values. That is why an agent cannot talk its way to a pass. Reference-answer matching is exactly what execution-based evaluation replaces.

Your screenshot is 1512 by 982 pixels and you shrink it before sending it to the model. The model says to click at (400, 300). What do you do?

  1. Divide by the scale factor to get the click position on the real screen
  2. Click at (400, 300) on the real screen
  3. Resend the screenshot at full size and ask again
  4. Multiply by the scale factor
The documentation says to scale Claude's coordinates back up before applying them to the real display. In the toy, forgetting this puts the click about 55 and 41 pixels away. Multiplying by a factor below 1 would move it the wrong way.

Why does a 318-step task punish an agent more than a 30-step task, even when each step looks very reliable?

  1. Longer tasks need larger screens
  2. Models cannot count past a hundred
  3. The benchmark scores long tasks twice
  4. Success needs the whole chain to hold, so small per-step failure rates compound, unless the agent notices and repairs mistakes
With independent steps, success is pn: 0.99 over 30 steps is about 74%, over 318 steps about 4%. Real agents recover from some errors, so the model overstates the decline, but the direction holds. The other options have no support in the sources.

Between 2024 and 2026 the OSWorld authors' account of why agents fail shifted. Which description matches the sources?

  1. From memory problems to click accuracy
  2. From mainly GUI grounding and operational knowledge to constraint tracking, mid-task information, guessing instead of asking and skipped verification
  3. From reasoning to speed
  4. There was no change; failures were always about screen size
The 2024 abstract names GUI grounding and operational knowledge (with over 75% of one model's failures involving click inaccuracy). The 2026 abstract lists the long-horizon failures. Option 1 reverses the direction.

How MCP Changed, 2024 to 2026

The Model Context Protocol (MCP) began in November 2024 as a way for a desktop app to launch a local helper program and talk to it over standard input and output. Within two years it gained a web transport, an OAuth-based authorisation scheme, a formal deprecation policy and, in the 2026-07-28 revision, a stateless redesign that removes the connection handshake. Reading the changelogs in order shows how a protocol reacts when it meets real deployments.

I fetched and read the official MCP changelog ("Key Changes") for each of the revisions 2025-03-26, 2025-06-18, 2025-11-25 and 2026-07-28; the 2024-11-05 transports page; the 2025-06-18 lifecycle, transports and authorisation pages; Anthropic's announcement of 25 November 2024; and a 3 September 2026 article by the Agentic AI Foundation on the newest revision. These are the project's own documents, so they say what changed and often what it replaces, but they are brief on why. Where I give a reason, I say whether the source states it or whether it is my inference. I did not read the proposals (SEPs) behind each change, and I did not test any implementation. The small simulation at the end is my own toy.

The pattern in one sentence

A protocol designed for one deployment shape (a local process with one client) acquires new requirements when it is used in another (remote, multi-user, load-balanced), and the healthy response is to change it in dated, documented revisions with an explicit deprecation policy, which also means consumers must expect and survive change.

Context: what MCP is

The MCP chapter builds the protocol from the wire up; here is the short version. MCP is a standard way for an AI application (the client, or host) to connect to programs (servers) that offer tools, readable resources and prompt templates, so that one integration works across many apps. Messages are JSON-RPC, a small request and response format. Anthropic announced and open-sourced it on 25 November 2024, with a specification and SDKs, support for local servers in the Claude Desktop apps, and a repository of ready-made servers for Google Drive, Slack, GitHub, Git, Postgres and Puppeteer. It named Block and Apollo as early integrators and Zed, Replit, Codeium and Sourcegraph as working with it.

Transport
How the protocol's messages physically travel: through a child process's pipes, or over HTTP. The message format stays the same across transports.
Session
State a server keeps about one client connection between requests, identified by an ID. It is what a load balancer must respect by sending the client back to the same server.
Capability negotiation
The opening exchange in which client and server tell each other which optional features they support.
OAuth resource server
A service that accepts access tokens issued by a separate authorisation server. See OAuth 2.0 and OpenID Connect.
Deprecation
Marking a feature as scheduled for removal while it still works, to give users time to migrate.

2024-11-05: a local protocol with an HTTP option

The first specification revision defined two transports. With stdio, the client launches the server as a subprocess, writes JSON-RPC messages to its standard input and reads replies from its standard output, one message per line. That design is why MCP worked from day one on a laptop: no network, no ports, and the operating system's process model as the security boundary. The second option, HTTP with Server-Sent Events (SSE), let a server run as an independent process serving several clients. The server had to provide two endpoints: an SSE endpoint the client opened to receive messages, and an ordinary POST endpoint for sending them; on connection the server sent an endpoint event telling the client where to POST. The spec already warned of a security issue with this: servers must validate the Origin header to prevent DNS rebinding attacks, bind to localhost when running locally, and should authenticate connections.

The connection opened with a handshake. Per the lifecycle page (the structure is the same in the 2025-06-18 version I read): the client sends initialize with the protocol version it supports, its capabilities and information about itself; the server answers with its own; the client confirms with an initialized notification; only then does normal operation start. That is capability negotiation, and it makes the connection stateful: both sides remember what was agreed for as long as the connection lives. Keep this in mind, because the 2026 revision is mostly about removing it.

2025-03-26: authorisation and a single HTTP endpoint

The next revision's changelog lists four major changes. It added a comprehensive authorisation framework based on OAuth 2.1. It replaced the HTTP+SSE transport with Streamable HTTP. It added support for JSON-RPC batching, sending several messages in one request. And it added tool annotations, which describe a tool's behaviour, such as whether it is read-only or destructive. Smaller changes included a descriptive message field on progress notifications, audio content alongside text and image, and an explicit capability for argument autocompletion.

Streamable HTTP, as described in the later 2025-06-18 transport page, collapses the two endpoints into one. The server exposes a single MCP endpoint that accepts POST for client messages and optionally GET for a server-to-client stream; every client message is a new POST, and the server may reply with a plain JSON body or open an SSE stream for the response. A server may assign a session ID in an Mcp-Session-Id header at initialisation, which the client must send on every later request. The 2026 changelog records that HTTP+SSE has been deprecated since 2025-03-26. The stated mechanics suggest the reason (my inference, not the changelog's): a long-lived SSE connection plus a separate POST endpoint is awkward behind ordinary HTTP infrastructure, and a request-and-response transport that can optionally stream is easier to host. The point is that the transport changed because the deployments did: servers were moving from the user's machine to the internet.

Authorisation arrived in the same revision for the same reason. A local stdio server needs no login; a remote one that reads your email does. The authorisation page of the 2025-06-18 revision makes the division explicit: authorisation is optional; HTTP-based transports should follow the specification; stdio implementations should not, and take credentials from the environment instead. For the underlying ideas see OAuth and OIDC and MCP in production.

2025-06-18: treating servers as OAuth resource servers

This revision's changelog opens with nine major changes. Four concern security and authorisation. MCP servers are now classified as OAuth resource servers, publishing protected resource metadata so that a client can discover which authorisation server to use. Clients must implement resource indicators (RFC 8707) to prevent malicious servers from obtaining access tokens. The authorisation text was clarified and a security best practices page added. And clients must send the negotiated protocol version in an MCP-Protocol-Version header on later HTTP requests.

The authorisation page lays out the flow. A client makes a request with no token; the server answers 401 with a WWW-Authenticate header pointing at its metadata; the client fetches that metadata (/.well-known/oauth-protected-resource), learns the authorisation server, fetches its metadata, optionally registers itself dynamically, then runs an OAuth 2.1 authorisation-code flow with PKCE, including a resource parameter naming the MCP server. The server must validate that tokens were issued specifically for it, and the page forbids passing a received token through to upstream APIs, which would be a confused-deputy hole. Those are the ideas from authorisation, carried over almost intact.

The revision also added elicitation, a way for a server to ask the user for more information mid-task; structured tool output; and resource links in tool results. It removed JSON-RPC batching, which the previous revision had just added. That reversal is worth noticing: the changelog gives no reason, but it shows a protocol treating a feature as an experiment, which is itself good practice.

2025-11-25: more auth, and long-running work

The next revision lists nine major changes. On authorisation: discovery now supports OpenID Connect Discovery; incremental scope consent via WWW-Authenticate; and OAuth Client ID Metadata Documents as a recommended client-registration mechanism. Why the last one? Dynamic client registration requires the authorisation server to accept registrations from unknown clients, which is awkward when any new MCP client may arrive; a client ID that is a URL pointing to a document describing the client is an alternative. (The changelog does not state this reasoning; it is mine.) Other items: icons for tools and resources, guidance on tool names, URL-mode elicitation (sending the user to a web page to complete a step), tool calling inside sampling (the server asking the client's model to do work), and experimental support for tasks, which track durable requests with polling and deferred results, an answer to operations that run longer than a single request. Minor items include clarifying that input validation errors should return as tool execution errors so that a model can correct itself, which is the lesson of the tool design chapter reaching the spec.

Governance also matured: the revision formalised the project's governance structure, working groups and interest groups, and a tiering system for SDKs.

2026-07-28: stateless

The newest revision I read is the largest conceptual change. Its changelog's nine major changes, in the order given:

  1. No protocol-level sessions. The Mcp-Session-Id header is gone from Streamable HTTP, and list endpoints no longer vary per connection. Servers that need state across calls use explicit server-minted handles passed as ordinary tool arguments.
  2. No initialize handshake. Every request carries its protocol version and client capabilities in _meta; clients should identify themselves on each request and servers in each result. A version mismatch returns an UnsupportedProtocolVersionError.
  3. server/discover. Servers must implement it to advertise versions, capabilities and identity; clients may call it first, or use it as a compatibility probe on stdio.
  4. subscriptions/listen replaces the HTTP GET stream and the resource subscribe and unsubscribe calls with a single opt-in stream of change notifications.
  5. Removals: ping, logging/setLevel and the roots list-changed notification. Log level is set per request.
  6. Tasks move out of the core into an official extension with polling via tasks/get.
  7. Multi Round-Trip Requests. Instead of the server sending its own request to the client mid-call (for sampling, roots or elicitation), the server returns an input_required result listing what it needs, and the client retries the original request with the answers.
  8. A required resultType field on results, complete or input_required.
  9. No SSE resumability. The Last-Event-ID mechanism is removed; a broken response stream loses the in-flight request and the client must re-issue it as a new request with a new ID.

The AAIF article of 3 September 2026 gives the motivation in a sentence: statelessness "makes it easier to scale horizontally, add load balancers, and rotate server instances without keeping session state in sync", particularly for deployments spread over many server instances. That fits the structure of the change. A server that must remember what was negotiated forces the load balancer to send each client to the same instance ("sticky" routing) or to share state between instances. If every request is self-contained, any instance can answer any request. Notice the cost, which the changelog makes explicit: capabilities travel on every request, the stream cannot resume (so retry becomes the client's problem and the operation's idempotency matters), and cross-call state moves into the application. That trade is the one in failure, timeouts and retries and HTTP: the web scaled by making requests self-contained.

Deprecations and a policy

The same revision records what is on its way out. Roots, Sampling and Logging are deprecated: they keep working, but new implementations should not adopt them, with suggested migrations such as passing directories in tool parameters, calling LLM providers directly instead of sampling, and logging to stderr or OpenTelemetry. The older HTTP+SSE transport is formally classified as Deprecated; OAuth dynamic client registration is deprecated in favour of Client ID Metadata Documents, though it remains for compatibility. The governance change that makes these meaningful is a feature lifecycle and deprecation policy: features are Active, Deprecated or Removed, with a minimum twelve-month deprecation window and a public registry of deprecated features. Other minor changes: tools should come back from tools/list in a deterministic order (to aid caching and prompt-cache hits), results must carry ttlMs and cacheScope freshness hints, and OpenTelemetry trace context is carried in _meta. The last two are ordinary web-infrastructure ideas arriving in the protocol.

Common misconception

"Stateless means servers can have no state." The 2026 changelog does not say that. It removes state kept by the protocol (a session tied to a connection). Servers that need to remember something between calls use explicit handles that the server creates and the client passes back as ordinary tool arguments, so the state is visible, named and survives a change of instance. Third-party summaries also note that making repeated tool calls safe moves to the application; I take this as a reading of the design (no more sticky session to hide behind), not as a line from the changelog.

State of play, October 2026

As of my reading, 2026-07-28 is the latest revision, which the AAIF article of 3 September 2026 calls "the latest version". Details are volatile: SDKs lag the specification, some servers will stay on older versions for a long time, and the deprecated features will remain available through at least a twelve-month window under the new policy. Before relying on any message name or header in this page, check the current specification at modelcontextprotocol.io. This case was the course brief's prompt to verify the final text, and the changelog I read is the final 2026-07-28 text rather than a release-candidate post. I did not read the release-candidate post.

Try it yourself

Try it yourself

The toy below is my own sketch of the idea in the left and right panels, not MCP code and not any SDK. It puts two server instances behind a round-robin load balancer. The stateful pair needs an initialize call to create a session on whichever instance receives it; the stateless pair reads the protocol version from each request's metadata. Make the stateful version work by adding a "sticky" rule that sends a session ID to the instance that issued it. Then ask what you would do if instance A restarted.

"""Toy: a stateful (session) server versus a stateless one behind a round-robin load balancer."""
import itertools
class StatefulServer:
    def __init__(self, name): self.name, self.sessions = name, {}
    def handle(self, req):
        if req["method"] == "initialize":
            sid = f"{self.name}-{len(self.sessions)+1}"; self.sessions[sid] = req["params"]; return {"session": sid}
        if req.get("session") not in self.sessions: return {"error": "unknown session (initialize first)"}
        return {"result": f"{self.name} ran {req['method']}"}
class StatelessServer:
    def __init__(self, name): self.name = name
    def handle(self, req):
        meta = req.get("_meta", {})
        if "protocolVersion" not in meta: return {"error": "missing protocolVersion"}
        return {"result": f"{self.name} ran {req['method']} (version {meta['protocolVersion']})"}
def run(servers, make_calls):
    rr = itertools.cycle(servers)             # round-robin load balancer
    return [next(rr).handle(r) for r in make_calls(servers)]
print("STATEFUL, 2 instances behind round robin:")
sess = {}
def calls(_):
    yield {"method": "initialize", "params": {"client": "demo"}}
    yield {"method": "tools/list", "session": "A-1"}
    yield {"method": "tools/call", "session": "A-1"}
for r in run([StatefulServer("A"), StatefulServer("B")], calls): print("  ", r)
print("STATELESS, same load balancer:")
def calls2(_):
    for m in ("tools/list", "tools/call", "tools/call"):
        yield {"method": m, "_meta": {"protocolVersion": "2026-07-28"}}
for r in run([StatelessServer("A"), StatelessServer("B")], calls2): print("  ", r)
STATEFUL, 2 instances behind round robin:
   {'session': 'A-1'}
   {'error': 'unknown session (initialize first)'}
   {'result': 'A ran tools/call'}
STATELESS, same load balancer:
   {'result': 'A ran tools/list (version 2026-07-28)'}
   {'result': 'B ran tools/call (version 2026-07-28)'}
   {'result': 'A ran tools/call (version 2026-07-28)'}

In the stateful run, initialize lands on A and creates session A-1. The next call goes to B, which has never heard of it, and fails. The third call returns to A and works, by luck. That intermittent failure is the worst kind in production: it depends on load balancer order. In the stateless run all three calls succeed on whichever instance receives them. A real stateful MCP deployment avoids the first outcome with sticky routing or a shared session store, both of which are extra moving parts. Systems connection

MCP followed the path of many network protocols. It started as a local, trusted channel (compare Unix pipes), met the internet, and acquired authentication, standard HTTP semantics and then a drive for statelessness so that ordinary load balancers and caches work. The security cost of being remote is real: the confused-deputy and token-passthrough warnings in the authorisation text are the same issues as in authorisation, and an MCP server fetching URLs on a model's behalf brings the risks in SSRF. Agents calling these tools face their own threats.

Lessons

  • Deployment shape drives protocol change. Auth, a web transport and statelessness all follow from servers moving off the laptop.
  • Expect churn. Five dated revisions in about twenty months, including a feature (batching) added and then removed. Pin the version you target and test upgrades, as MCP in production advises.
  • Use the deprecation signals. The new lifecycle policy gives a twelve-month minimum; build your migration plan against the deprecated-features registry, not against surprise.
  • Prefer standards you already trust. MCP's authorisation reuses OAuth, protected resource metadata and resource indicators rather than inventing a scheme.
  • Make state explicit. If something must persist between calls, name it and pass it, instead of hiding it in a connection. The same advice applies in your own tool design, covered in designing tools for agents.

Check your understanding

Why did MCP gain an OAuth-based authorisation framework when it moved from stdio toward HTTP?

  1. stdio servers also require OAuth tokens
  2. OAuth makes messages smaller
  3. A remote server reachable over the network needs to identify who is calling and what they may do, while a local subprocess launched by the user relies on the operating system and environment credentials
  4. OAuth replaces JSON-RPC
The authorisation page says implementations using stdio should not follow the specification and should take credentials from the environment. OAuth sits on top of HTTP transports and does not replace the message format.

A client in a 2025-06-18 deployment receives a 401 from an MCP server. What should it do next, according to the authorisation flow?

  1. Read the metadata location in the WWW-Authenticate header, fetch the protected resource metadata, find the authorisation server and run the OAuth flow with a resource parameter
  2. Retry with a session ID
  3. Call initialize again
  4. Give up, because the server is not an OAuth resource server
That discovery sequence is what the revision's classification of servers as OAuth resource servers enables. Sessions and initialisation concern protocol state, not authentication.

What problem does removing the initialize handshake and sessions in 2026-07-28 mainly address?

  1. JSON-RPC messages were too large
  2. Servers could not return errors
  3. Clients could not discover tools
  4. Per-connection state forces sticky routing or shared session storage, which makes it harder to scale across instances behind load balancers
The AAIF article ties statelessness to horizontal scaling and load balancers. Discovery still exists (server/discover and the list calls), and error handling is unrelated.

Under the 2026-07-28 revision, a tool needs to remember a shopping cart between calls. What does the changelog suggest?

  1. Use Mcp-Session-Id to hold the cart
  2. Have the server create an explicit handle for the cart and have the client pass it as an ordinary tool argument
  3. Call initialize before every request
  4. Carts cannot be built any more
The changelog says servers that need cross-call state use explicit, server-minted handles passed as tool arguments. The session header has been removed.

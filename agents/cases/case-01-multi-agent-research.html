A Multi-Agent Research System

In June 2025 Anthropic published "How we built our multi-agent research system", an engineering account of the feature that lets Claude research a question by sending several agents out in parallel. Its most useful sentences are not about architecture but about cost: in the team's analysis, how many tokens an agent spends explained most of how well it did. This case reads that post closely, separates what the team measured from what it claims, and asks when the pattern pays for itself.

What I could and could not read

I fetched and read the Anthropic engineering post in full (published 13 June 2025). Every number below comes from it and is attributed to "the post" or "the team". It is a company's description of its own product, so the results are self-reported: the evaluation set, the judge prompts and the traces are not published, and I could not check any figure independently. The model names in the post (Claude Opus 4 as lead, Claude Sonnet 4 as workers) date it to mid-2025 and are not a statement about current models. The token-accounting script in "Try it yourself" is my own toy with stated, illustrative sizes; it is not Anthropic's data.

The pattern in one sentence

A lead agent decomposes an open-ended question, hands independent pieces to worker agents that each work in a fresh context window and return condensed findings, then synthesises: you buy breadth and parallelism with tokens, so it only pays when the question is valuable and the pieces really are independent.

Context: why research suits many agents

Research questions are open-ended. You cannot write the steps in advance, because what you read on step three changes what you search for on step four. The post argues that this is exactly where a fixed pipeline fails and a model that chooses its next search does well, which is the idea behind the deep research agents chapter. A single agent has two limits, though: it works one step at a time, and everything it reads piles up in one context window (the text the model can see at once). The post notes that context beyond 200,000 tokens gets truncated, so a long investigation can lose its own earlier plan.

The team's answer is the pattern named orchestrator-workers: one model plans and delegates, others execute. The workflow patterns chapter shows it as plain code; the multi-agent chapter covers when it is worth it. Here we look at one production example with published numbers.

Orchestrator-workers
A lead model splits a task at run time and delegates pieces to worker models, then combines their results. The split is decided by the model, not hard-coded.
Subagent
A worker agent started by the lead. It has its own instructions, tools and context window, and returns a summary rather than its whole history.
Context window
The text a model can attend to in one call. Every extra search result competes for space in it and, in an agent loop, is paid for again on every later call.
LLM-as-judge
Using a model with a rubric to grade outputs, so evaluation can be run often and cheaply. See the LLM-as-judge chapter.
Rainbow deployment
Moving traffic gradually from an old version to a new one while both keep running, so agents that are mid-task are not cut off.

The mechanism: one lead, parallel workers, a citation pass

The post describes four parts. A LeadResearcher analyses the user's query, makes a plan and saves it to memory (so it survives a truncated context), then spawns subagents. Each subagent runs its own search loop with its own context, evaluating results as it goes with interleaved thinking, and reports back. The lead decides whether more research is needed. Finally a CitationAgent processes the documents and the report to find where citations belong, so claims are tied to sources. The post contrasts this with static retrieval-augmented generation, which fetches the closest chunks once: here the search is multi-step and adapts to what it finds.

The post gives a pair of design choices that matter more than the diagram. First, subagents act as filters: they read a lot and return little, so the lead's context stays small. The post's appendix goes further and suggests subagents write large outputs to external storage and pass a lightweight reference, to avoid information loss when messages are relayed through the lead (it likens this to a game of telephone). Second, the lead must write real task descriptions. The post reports that vague instructions led subagents to duplicate each other's work; each task needs an objective, an output format, guidance on tools and sources, and clear boundaries. That is the same discipline as a good tool description in the tool design chapter, applied to a model reading a brief instead of a schema.

Effort has to be scaled to the question

The team reports that early versions over-invested. Two failure modes it names: spawning 50 subagents for simple queries, and searching endlessly for sources that did not exist. The countermeasure was to put scaling rules into the lead's prompt. The post gives them as rough bands: a simple fact-finding query needs one agent making 3 to 10 tool calls; a direct comparison needs 2 to 4 subagents with 10 to 15 calls each; complex research might use more than 10 subagents with clearly divided responsibilities. The post also says the lead starts 3 to 5 subagents in parallel and each subagent uses 3 or more tools in parallel.

Notice what kind of control this is. It is not an algorithm; it is guidance the model reads. The post says the team prefers heuristics to rigid rules and adds explicit guardrails against runaway behaviour. In production terms these are the iteration budgets and stop conditions from the tool loop chapter, written in prose.

What the numbers say

The headline gain

The post reports that the multi-agent system, with Claude Opus 4 as lead and Claude Sonnet 4 as subagents, outperformed a single-agent Claude Opus 4 by 90.2% on the team's internal research evaluation. Treat that as a company's measurement on its own test set: the post does not publish the queries, the number of runs or an interval, and "90.2% better" is a relative gain on a score, not an accuracy. It is evidence that the design helps on breadth-first questions, not a general law.

The post is clearer about what that evaluation looked like. The team started with about 20 queries taken from real usage, arguing that effect sizes in early development are large enough that a small set shows the change. It then used an LLM judge with a rubric covering factual accuracy, citation accuracy, completeness, source quality and tool efficiency; a single prompt that output a 0.0 to 1.0 score and a pass or fail grade was the most consistent and agreed best with human graders. Humans still found what the judge missed: early agents preferred search-optimised content farms to authoritative sources, which led to source-quality heuristics in the prompt. For methods that scale this up, see evaluating agents, which also covers end-state checks, the other approach the post recommends for agents that change state.

What explained performance: tokens

The part worth remembering is the post's analysis of BrowseComp, a benchmark of hard-to-find web facts. It says three factors explained 95% of the variance in performance, and that token usage by itself explained 80%. The other two factors were the number of tool calls and the choice of model. The post's reading is that multi-agent systems work mainly because they spend enough tokens, and that parallel agents with separate context windows add capacity for reasoning beyond what one agent's window allows.

Two cautions. This is a correlation across runs: agents that think and search more spend more tokens and also do better, so the result does not prove that adding tokens to a fixed design would raise the score by that amount. And BrowseComp rewards persistence in finding obscure facts, which is a narrower thing than writing a good report. The post adds one comparison that points the same way as the model-choice factor: upgrading to Claude Sonnet 4 produced a bigger gain than doubling the token budget on Claude Sonnet 3.7. So tokens are necessary but not the whole story, and a better model uses them better.

What it costs

The other side of the ledger is stated plainly. The post says agents typically use about 4 times more tokens than chat interactions, and multi-agent systems about 15 times more. It concludes that multi-agent research only makes economic sense for tasks whose value is high enough to pay for the increase.

The latency side runs the other way. The post says parallelising, both the lead starting subagents at once and subagents using tools at once, cut research time by up to 90% for complex queries. Cost and speed are different axes: you pay more tokens to finish sooner and to cover more ground. Tokens also cost money in a way that scales with every user, which is why cost, latency and quality trade-offs and routing a cheaper model to the workers matter. Using a smaller model for workers is exactly what the post does.

Common misconception

"More agents means better answers." The post's own analysis points at tokens spent usefully, and its own lessons include wasted effort (50 subagents for a simple query) and duplicated work from vague briefs. It also says multi-agent systems are a poor fit for work that needs shared context or has many dependencies between steps, and that most coding tasks have fewer parallelisable pieces than research does. A team of agents that must constantly agree is a slower, dearer single agent.

Engineering a long-running, stateful system

The post spends as much space on running the system as on designing it, and this is where the case connects most directly to the reliability material.

  • Errors compound. An agent can run for a long time, so a failure partway through should not mean starting again. The team built the system to resume from where the error happened, and combined the model's adaptability (telling the agent a tool is failing and letting it adapt) with deterministic safeguards such as retry logic and checkpoints. The durable execution chapter develops the same idea: log what has happened, so a restart replays rather than repeats.
  • Debugging non-determinism. The same prompt can behave differently on two runs, so the team added full production tracing and monitored decision patterns and interaction structure without reading the content of individual conversations, to protect user privacy. See distributed tracing and tracing for LLM systems.
  • Deployment. Because agents are often mid-task, you cannot restart them for an update. The team used rainbow deployments, shifting traffic gradually while old and new versions both run. This is the blue-green and canary thinking of the deployment strategies chapter, adapted for work that lasts minutes rather than milliseconds.
  • Synchronous bottleneck. In the version described, the lead waits for each batch of subagents to finish before continuing. That simplifies things but blocks the lead from steering them or from using one worker's finding to redirect another. The post expects asynchronous execution to become worthwhile as models handle longer tasks, but says it adds hard problems in coordinating results, keeping state consistent and propagating errors.

Systems connection

A lead that fans out to workers and waits for the slowest is the scatter-gather shape from tail latency at scale: the batch finishes when its slowest subagent does, so one slow worker sets the pace. Retrying a failed worker is safe only if its side effects are, which is the retries and idempotency argument again.

Prompting lessons the team reports

The post lists eight principles. Several are about the orchestrator, and they read like a manager's checklist.

What the critics and the limits say

I did not search for independent replications or rebuttals of the post's figures, so none are cited. What the post itself concedes is the useful critique. It says LLM agents are not yet good at real-time coordination and delegation with each other, that token cost restricts the pattern to high-value tasks, and that shared-context, dependency-heavy domains fit badly. A fair reading of the 90.2% figure is "on breadth-first research questions, in this team's evaluation, under a large token budget". Anyone adopting the pattern should repeat the experiment on their own questions, with their own cost ceiling, rather than assume the number transfers. The multi-agent chapter gives a checklist for exactly this decision.

State of play, October 2026

The post is from June 2025 and its models are from mid-2025. The enduring lessons are the shape (plan, delegate, filter, synthesise, cite), the token-cost argument and the production concerns. Specific multiples, the model pairing and the "synchronous lead" limitation describe that moment; check current vendor documentation before relying on them. I did not verify the product's present architecture.

Try it yourself

Try it yourself

The toy below counts tokens processed by a one-agent loop that re-reads its whole context on every call (no caching), against a lead plus workers whose contexts are separate. The sizes are my assumptions, labelled in the code. It will not reproduce the post's 15x, because that figure comes from a multi-agent system doing more searching than a single agent would; it shows the mechanism that makes separate contexts attractive, and why the cost still rises when you add more work.

"""Toy token accounting: one agent doing N searches in one context versus a lead
agent plus N workers with fresh contexts. All sizes are illustrative assumptions."""
SYSTEM = 3_000      # system prompt + tool definitions, tokens (assumption)
RESULT = 4_000      # tokens added to the context by each search result (assumption)
STEP_OUT = 300      # tokens the model writes per step (assumption)
REPORT = 1_500      # summary a worker hands back (assumption)

def single_agent(n_searches):
    """Each model call re-reads the whole context so far (no caching)."""
    ctx, total_in, total_out = SYSTEM, 0, 0
    for _ in range(n_searches):
        total_in += ctx; total_out += STEP_OUT
        ctx += STEP_OUT + RESULT
    total_in += ctx; total_out += REPORT   # final answer
    return total_in + total_out, ctx

def multi_agent(n_workers, searches_each):
    lead_ctx, total = SYSTEM, 0
    total += lead_ctx + STEP_OUT            # plan call
    lead_ctx += STEP_OUT
    worker_ctx_peak = 0
    for _ in range(n_workers):
        t, ctx = single_agent(searches_each)
        total += t; worker_ctx_peak = max(worker_ctx_peak, ctx)
        lead_ctx += REPORT
    total += lead_ctx + REPORT              # lead synthesises
    return total, worker_ctx_peak, lead_ctx

for n in (4, 12, 24):
    t1, c1 = single_agent(n)
    print(f"{n:>2} searches, one agent : {t1:>9,} tokens processed, final context {c1:,}")
for w, s in ((4, 3), (6, 4), (8, 3)):
    t, wc, lc = multi_agent(w, s)
    print(f"{w} workers x {s} searches : {t:>9,} tokens processed, biggest worker ctx {wc:,}, lead ctx {lc:,}")
 4 searches, one agent :    60,700 tokens processed, final context 20,200
12 searches, one agent :   379,500 tokens processed, final context 54,600
24 searches, one agent : 1,373,700 tokens processed, final context 106,200
4 workers x 3 searches :   174,900 tokens processed, biggest worker ctx 15,900, lead ctx 9,300
6 workers x 4 searches :   381,300 tokens processed, biggest worker ctx 20,200, lead ctx 12,300
8 workers x 3 searches :   341,700 tokens processed, biggest worker ctx 15,900, lead ctx 15,300

Read the output in two steps. A single agent doing 24 searches processes about 1.37 million tokens, because each of its 25 calls re-reads a context that has grown to 106,200 tokens. Six workers doing 4 searches each, the same 24 searches in total, process about 381,000, because no call ever reads a context larger than 20,200 tokens. Splitting work into small contexts is cheaper per search. The cost the post reports comes from the extra breadth: if the multi-agent system then runs, say, 8 workers with 3 searches each, it has done 24 searches again but at 342,000 tokens, and every additional worker you add raises the bill. Change RESULT to 1,000 and see how much of the single-agent penalty disappears, and ask what prompt caching (re-using an unchanged prefix) would do to both columns.

Lessons

  • Decide with a cost model. Estimate tokens per query before building; at the post's typical multiples a task must be worth many chat answers. See the cost and return on investment chapter.
  • Give workers real briefs. Delegation quality is prompt quality: objective, format, sources, boundaries.
  • Return summaries, not transcripts. The point of a separate context is that only the conclusion crosses back.
  • Start the evaluation small, with real queries, and keep human review in the loop for the cases the judge misses.
  • Plan for the run to be interrupted. Checkpoints, tracing and deployments that do not kill in-flight work are part of the design, not polish.

Check your understanding

The post reports that token usage by itself explained 80% of the variance in BrowseComp performance. What is the most defensible reading?

  1. Doubling any agent's token budget will raise its score by about 80%
  2. Across runs, agents that spent more tokens did much better, so multi-agent designs work largely by letting more reasoning and searching happen; it is a correlation, not a guarantee for a fixed design
  3. Model choice does not matter once tokens are controlled for
  4. Eighty percent of the tokens an agent uses are wasted
Variance explained describes how well a factor predicts differences across runs, not how much a score rises per extra token. The post itself says model choice mattered (upgrading the model beat doubling the budget on the older one), so the third option is wrong too.

A team wants a multi-agent system for a coding assistant that edits one shared codebase with many interdependent changes. Based on the post, what is the likely problem?

  1. Subagents cannot call tools
  2. The lead agent cannot write plans to memory
  3. The work has shared context and many dependencies, and the post says it has fewer parallelisable pieces than research, so workers would conflict or wait
  4. Multi-agent systems always cost less than single agents
The post names shared-context, dependency-heavy domains and most coding tasks as poor fits. The first two options describe capabilities the architecture does have; the last contradicts the 15x figure.

Early on, the lead gave subagents short instructions and they duplicated each other's work. Which fix matches the post?

  1. Give each subagent an objective, an output format, guidance on tools and sources, and clear task boundaries
  2. Run the subagents one at a time
  3. Give every subagent the lead's full context window
  4. Remove the lead and let the workers self-organise
The post's delegation principle is detailed briefs. Serial running would remove the parallel speed-up without fixing vague tasks, and sharing the full context defeats the purpose of separate windows.

In the toy script, why does one agent doing 24 searches process far more tokens than six workers doing 4 searches each?

  1. Workers use a cheaper model in the script
  2. Workers skip reading search results
  3. The script charges for output tokens only
  4. Each model call re-reads its whole context, so a long single context makes later calls much more expensive, while small separate contexts stay small
The script uses the same sizes for every agent; only the context length differs. The total grows roughly with the square of the number of steps in one context, which is why splitting helps per search, even though the real system also does more total searching.

Why did the team use rainbow deployments rather than restarting the system for each release?

  1. Rainbow deployments make agents faster
  2. Agents are often mid-task for long periods, so traffic is shifted gradually while old and new versions both run and in-flight work is not interrupted
  3. Models cannot be redeployed without a restart
  4. It reduces token usage
The post gives the long-running, stateful nature of agents as the reason. The change has nothing to do with speed or tokens.

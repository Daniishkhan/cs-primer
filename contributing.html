Contributing Upstream

Merged pull requests to the repositories research labs maintain are how the right people learn your name before you apply. This page lists the repositories that fit the four artifacts, the first small pull request and the substantive one for each, and five rules that get pull requests merged.

Why contribute before you apply?

A merged pull request is evidence a reviewer does not have to take on trust: a maintainer read your code and accepted it. Start with a fix nobody else wants to do, then land one substantive pull request a quarter, each carrying a result from the artifact you are building. The repositories are ordered by how soon a first merge is realistic.

Five rules that get pull requests merged

  1. Read the last 30 merged pull requests before opening one. Match their size and style exactly.
  2. Make the first one boring and obviously correct. A pin, a test, a documentation fix. The maintainer learns that you ship clean work.
  3. Open an issue first for anything over 50 lines. Include a reproducible failure, and let the maintainer shape the fix.
  4. A substantive pull request carries a result, not a feature. A number, a chart, and the command that reproduces it.
  5. Keep a public log. Every merged pull request, with its date and the maintainer's handle, in a repository README or a short blog. The evidence log keeps a private copy.

A cadence

  • Month 1. A public GitHub profile with a pinned "research log" repository, and the first boring pull request to autoresearch or modded-nanogpt.
  • From month 3. One issue or pull request a month on a target repository, logged with its date and the maintainer's handle.
  • Each quarter. One substantive pull request carrying a result from the current artifact.
  • From month 9. Specific conversations with maintainers you have shipped pull requests to: ask for feedback on Artifact 3, not for a job.

Key takeaways

  • Start where a first merge is realistic: a fix nobody else wants to do.
  • Substantive pull requests carry results from your artifacts, not features.
  • Log every merge; it is evidence you will need later.

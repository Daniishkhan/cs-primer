Overload, Load Shedding & Metastability

Every system has a capacity, and sooner or later demand exceeds it. What happens next separates a service that serves what it can and refuses the rest from one that collapses and stays collapsed even after the demand has gone. This chapter covers goodput and the collapse curve, admission control and load shedding (by priority, by deadline, LIFO, CoDel), adaptive concurrency limits, retry budgets and the arithmetic of retry amplification, and metastable failures: outages that sustain themselves. A simulation lets you push a service into one, then pull it out again.

Why this matters

Overload is the commonest cause of large outages that start small. A brief slowdown, a deploy, a cache flush, a traffic spike: any of them can start it. The part that makes it dangerous is not the trigger but what the system does in response. Timeouts cause retries, retries cause more load, more load causes more timeouts. The result can persist for hours after the original cause has been fixed, because the system's own reactions keep it down. Engineers who understand the shape of that loop know where to cut it, and design services that decline work gracefully instead of drowning. It is also a topic that distinguishes senior from mid-level in design interviews, because the right answer is rarely "add more servers".

Throughput is not goodput

Where we left off: chapter 8 showed that latency explodes as utilisation approaches 1, and chapter 10 showed how to find that point by test. This chapter is about what happens past it, when offered load stays above capacity for a while.

Throughput is the rate at which the system completes work. Goodput is the rate at which it completes useful work: responses that arrive while the client is still waiting for them and that carry a correct result. The two can diverge sharply. A server that spends all its time on requests whose clients timed out two seconds ago has high throughput and zero goodput.

Why does goodput fall rather than merely level off? Several effects stack up:

  • Wasted work. Queues grow, waiting time passes the clients' timeouts, and the server still works through requests nobody is waiting for. The longer the queue, the larger the fraction of work that is wasted.
  • Retries. Each timeout can generate another request, so offered load rises as the system gets worse (the loop described below).
  • Overheads that grow with load. Context switching between thousands of threads, lock contention, memory pressure, garbage collection, cache thrashing. This is the coherency term β of the scalability law in chapter 8: past a peak, more concurrency reduces throughput.
  • Resource exhaustion. Queued requests hold memory, sockets and file descriptors, and eventually the process runs out.

The same pattern was seen in networks decades ago and is called congestion collapse: links fully busy while almost no useful data got through. In a service the cure has the same general form: do less work that does not count, and refuse excess work early and cheaply.

Analogy: triage in the emergency department

When an emergency department is overwhelmed, it does not treat patients in the order they arrived, working harder at each. A triage nurse assesses each arrival and sends the cardiac arrest straight through, tells the sprained ankle to wait or go to an urgent-care clinic, and, in a bad enough surge, the hospital diverts ambulances to other hospitals. That is load shedding: protect the work that matters most, decline the rest quickly and honestly, and keep the system functioning at its true capacity. A department that tried to treat everyone equally would deliver poor care to all of them. It would also make sure it had no capacity left for the heart attack that arrives next.

Where it breaks down: triage nurses make careful, individual judgements. Software shedders must classify thousands of requests per second from a few cheap signals (a header, a route, a customer tier) and do so in microseconds, and cannot examine the patient first.

Admission control and load shedding

Admission control is the decision, made before doing the work, whether to accept a request at all. Load shedding is rejecting work that has already arrived because the system is over capacity. In practice both are the same mechanism: a cheap check in front of the expensive part. A rejected request is answered immediately with an error (HTTP 503 or 429, a gRPC UNAVAILABLE or RESOURCE_EXHAUSTED), preferably with a hint about when to retry. See architecture chapter 17 for how shedding differs from per-client rate limiting: rate limiting caps what one caller may send, shedding protects the server when the total is too much.

Two rules hold for any shedding design. Rejecting must be much cheaper than serving. If parsing, authenticating and logging a request costs nearly as much as handling it, rejecting a request saves little and the shedder itself can saturate. Reject as early as possible, ideally at the edge or the first line of the handler, before the database call. And the choice of what to shed is the design. Shedding at random is better than collapse; shedding the right things is better still.

Shed by priority

Not all requests matter equally. A checkout or a login is worth more than a recommendation widget, a health check or a batch job. Assign each request a criticality class at the edge (from the route, the caller's identity, an explicit header), propagate it to downstream calls, and when the system is stressed shed the lowest classes first. Google's SRE book describes four levels, ranging from critical-plus down to sheddable, which the RPC framework carries across the whole call chain. Opinionated advice: define few classes (three or four), make the defaults conservative, and test shedding in game days, because a priority scheme never exercised in production is likely to be wrong when it matters. Reserve a floor of capacity for the top class so that low-priority traffic can never crowd it out.

Shed by deadline

Every request has a client waiting, and every client has a timeout. If a request has already been waiting in the queue longer than its client will wait, then serving it is pure waste: the answer has nowhere to go. The remedy is a deadline carried with the request (an absolute time, or time remaining) and checked when the request is dequeued: if the deadline has passed, or if the remaining time is less than the minimum time the work could take, drop it immediately, at almost no cost. Propagate the deadline downstream so that each hop spends effort only on requests someone is still waiting for (see the deadline example in architecture chapter 17 and systems chapter 14, "Don't work for clients who have left"). In the simulation below this single rule, with a bound on queue length, is what removes the sustaining effect.

LIFO under overload

A first-in-first-out queue is fair, and under overload it is exactly wrong. When the queue is long, the request at the head has waited longest, so its client is most likely to have given up already. Serving it wastes capacity, and meanwhile fresh requests, whose clients are still waiting, age in line until they too expire. A LIFO (last-in-first-out) policy during overload serves the newest requests first. Those have the most time left, so a larger share of the work is useful, while old requests wait until they hit their deadline and are dropped. This is sometimes called adaptive LIFO: use FIFO when the queue is short (it is fair and everyone is served quickly) and switch to LIFO when it is long. Engineers at Facebook described using exactly this together with a controlled-delay queue in "Fail at Scale" (Ben Maurer, ACM Queue, 2015). The price is unfairness: some requests wait a very long time, and a few are starved until they time out. Under overload someone must lose, and it is better to choose who than to let everyone lose.

CoDel-style queue management

How long should a queue be allowed to get? A bound on length is crude: a short queue is fine for a burst and a long queue is fine if the server is fast. CoDel (Controlled Delay), by Kathleen Nichols and Van Jacobson (ACM Queue, 2012), was designed for network routers to fight "bufferbloat", and it changes the question from queue length to queue delay. It distinguishes a good queue, which absorbs a burst and then drains, from a bad queue, a standing backlog that never empties. The test is the minimum time any request spent waiting over a recent interval: if even the luckiest request waited longer than a small target, the queue has been standing for a whole interval and is bad, so start dropping, at a rate that increases the longer the delay persists. A burst makes the maximum delay high but not the minimum, so bursts are left alone.

The same idea is used for request queues in servers. Pick a target for time spent waiting (a few milliseconds to tens of milliseconds, a small fraction of your latency budget), measure the minimum queueing delay over a sliding window of about a hundred milliseconds or more, and begin shedding when it stays above the target. In the original network setting the defaults were a 5 ms target and a 100 ms interval; for a service those numbers are yours to choose from your latency budget. Compared with a fixed queue-length limit, this adapts to the server's speed without a magic number.

Shedding has costs and failure modes

Shed requests are errors for someone, so shedding eats error budget (chapter 2) and must be counted separately from real failures in dashboards. Shedding decisions based on stale or noisy signals oscillate: the system sheds, load drops, it stops shedding, load returns. And a retry layer that treats a shed response like any other failure turns shedding into more load. Shed responses should be explicitly marked "do not retry here" (or with a back-off hint), and clients must obey them.

Adaptive concurrency limits

A fixed limit on in-flight requests (a thread pool size, a semaphore) is a guess. Set it too high and the queue forms inside the server, where it is invisible. Set it too low and you refuse work you could have done. The right value changes when the code changes, when a dependency slows down, when the instance type changes. An adaptive concurrency limit measures and adjusts the limit continuously.

The idea comes from Little's law (systems chapter 14), in the form L = λ × W. At the service's maximum throughput λmax and its unloaded latency W₀, the number of requests that need to be in flight to keep it busy is λmax × W₀. More concurrency than that cannot produce more throughput; it only raises latency, because the surplus waits in a queue. The adaptive limiter searches for that number by watching latency (or drops), and rejects arrivals beyond it with a fast error. The queue then forms in the caller's retry logic or load balancer, where it can be handled, rather than inside the saturated server.

Three families of algorithm are commonly used. They are implemented, for example, in Netflix's open-source concurrency-limits library, which describes AIMD, Vegas and gradient limiters.

  • AIMD (additive increase, multiplicative decrease), borrowed from TCP congestion control. While latency looks healthy, raise the limit by one per round of requests; when latency rises past a tolerance, or requests time out or are dropped, multiply the limit by a back-off factor (for example 0.9). It is simple and robust, and produces the familiar sawtooth around the right value.
  • Gradient limits compare short-term latency to a long-term baseline. If recent latency is rising relative to the baseline (queueing is starting) the limit is reduced in proportion to the ratio; if it is steady, the limit is allowed to grow by a small allowance. It responds proportionally rather than in fixed steps, so it can settle more smoothly and reacts to a sudden slowdown faster than additive increase.
  • Little's-law-based limits (the TCP Vegas idea) estimate the queue directly: the number of requests in flight times the fraction of latency that is queueing, (1 − W₀/W). If the estimated queue is small, increase the limit; if it is large, decrease.

Here is the AIMD idea at its smallest. The model is a fluid one: a service that can do 400 requests per second with an unloaded latency of 50 ms, so its knee is at 400 × 0.05 = 20 concurrent requests. Below the knee, latency is flat; above it, every extra request in flight simply waits.

"""An AIMD concurrency limit finding a service's knee. A fluid model, deterministic.

The service can complete 400 requests/s and an unloaded request takes 50 ms. By Little's law
(L = throughput x latency) it needs 400 x 0.05 = 20 requests in flight to stay busy; any more
in flight just waits in a queue and adds latency, with no extra throughput."""

CAPACITY, BASE = 400.0, 0.050                  # requests/s, seconds
KNEE = CAPACITY * BASE                         # 20 concurrent requests


def latency(limit: float) -> float:
    """Latency with `limit` requests in flight: flat up to the knee, then queueing delay."""
    return BASE if limit <= KNEE else limit / CAPACITY      # Little's law at the saturated rate


def aimd(rounds: int = 60, start: float = 1.0, backoff: float = 0.9, tolerance: float = 1.2):
    limit, history = start, []
    for _ in range(rounds):
        lat = latency(limit)
        history.append((limit, lat))
        if lat <= tolerance * BASE:
            limit += 1.0                       # additive increase: probe for more room
        else:
            limit *= backoff                   # multiplicative decrease: queueing detected
    return history


if __name__ == "__main__":

    print(f"{'round':>5} {'limit':>6} {'latency':>8}")
    for i in list(range(0, 24, 2)) + [30, 40, 50, 59]:
        lim, lat = hist[i]
        print(f"{i:5d} {lim:6.1f} {lat*1000:6.0f} ms")
    tail = [l for l, _ in hist[30:]]
    print(f"\nafter warm-up the limit oscillates between {min(tail):.1f} and {max(tail):.1f}")

The limit climbs by one per round until it passes the knee at 20, where latency begins to rise; it keeps probing until latency exceeds the 20% tolerance (a limit of about 24), then backs off by 10%, and it settles into a narrow oscillation of 21 to 25 requests in flight, with latency about 20% above the floor. The "tolerance" parameter (1.2) is what sets that: it is how much queueing delay the controller accepts as the price of keeping the server fully busy. A tighter tolerance gives lower latency and a slightly lower limit. The point is that nobody had to configure 20: the controller found it from latency alone, and would find a different number tomorrow if the service's speed changed.

Where the limit lives

Adaptive limits can be enforced on the server (reject when in-flight exceeds the limit) or on the client (limit what it sends to each backend). Server-side is more accurate because the server knows its own state; client-side protects the server before the request is even sent. Use both for important paths, and make sure that a rejection from the limiter is distinguishable from a real error, so that it does not trip circuit breakers or alerts for the wrong reason.

Retries: the amplifier

Networking chapter 16 introduced backoff, jitter and idempotency, and the retry storms case told the story of a system dragged down by its own retries. Here we do the arithmetic that makes them dangerous, then the controls.

Amplification across layers

Suppose a call passes through four layers (A calls B calls C calls D calls a database), and each layer, reasonably on its own, retries a failed downstream call up to 3 times. That is 4 attempts in total at each hop. If the database is down so that every attempt fails, how many calls does it receive for one user request?

The multiplier at each retrying hop is 4, and there are 4 such hops (A→B, B→C, C→D, D→database), so the database sees 44 = 256 calls. Notice that "3 retries" means 4 attempts: it is the attempts that multiply, so the base is 4, not 3. And the exponent is the number of retrying hops, not the number of layers. Four layers where only the top retries gives 4, not 256.

Two qualifications matter. This is the worst case, when every attempt fails. If a fraction p of attempts fail independently, the expected number of attempts per hop is 1 + p + p² + p³. At p = 0.5 that is 1.875 per hop, and 1.8754 ≈ 12 at the bottom, a nuisance. At p = 1 it is 4 per hop and 256 in total. The amplification is wildly nonlinear in the failure rate: the system is fine at 50% failures and utterly swamped at 100%, which is why retry storms appear to arrive suddenly. Second, retries at depth multiply load, but they also multiply latency: the caller at the top may wait through several timeouts and sequences of backoff, so its own timeout fires first, and it may retry too.

Retry budgets

The best defences are structural. Retry in one place. Pick a single layer (usually the one nearest the user or the one that sees the whole picture) to retry; lower layers fail fast and report the error upward. And put a retry budget on the retrying client: it may retry only if retries are a small fraction of its recent traffic. A common implementation is a token bucket where each new request adds a fraction of a token (say 0.1) to the bucket, and each retry costs a whole token. In steady state retries cannot exceed about 10% of the request rate, and when many requests fail the bucket drains and retries stop. Finagle's retry budgets and gRPC's retry throttling work on a similar principle (gRPC adds to its tokens on successful calls and stops retrying when the bucket is half empty). The gRPC configuration below is illustrative (not run for this chapter):

{
  "methodConfig": [{
    "name": [{ "service": "example.Items" }],
    "retryPolicy": {
      "maxAttempts": 3,
      "initialBackoff": "0.1s",
      "maxBackoff": "1s",
      "backoffMultiplier": 2,
      "retryableStatusCodes": ["UNAVAILABLE"]
    }
  }],
  "retryThrottling": { "maxTokens": 10, "tokenRatio": 0.1 }
}

With a 10% budget at each hop the amplification per hop is at most 1.1, so four hops give at most 1.14 ≈ 1.46 times the load, instead of 256. The budget caps the damage even if every layer retries.

Client-side adaptive throttling

A retry budget limits retries. Adaptive throttling goes further and limits all requests a client sends to a struggling backend, using the client's own recent experience. The Google SRE book (the chapter "Handling Overload") describes it. Each client keeps, over a window of the last two minutes, two counts: requests, the number of requests the application tried to send, and accepts, the number the backend accepted (did not reject for overload). It then rejects new requests locally, without sending them, with probability

p = max(0, (requests − K × accepts) / (requests + 1))

where K is a multiplier, 2 in the book's recommendation. While the backend accepts everything, requests equals accepts, and p is zero. The client starts to throttle only when the backend has been rejecting more than a fraction of requests (with K = 2, once fewer than half are accepted). K > 1 is deliberate: it lets the client keep sending somewhat more than the backend accepts, so that it will notice quickly when the backend recovers. A lower K is more aggressive about protecting the backend; a higher K is more patient. Locally rejected requests count as "requests" but not as "accepts", so the rejection probability rises as the backend keeps refusing.

"""Retry amplification across layers, and the client-side adaptive throttling formula."""

def worst_case_calls(layers: int, retries: int) -> list[int]:
    """Calls reaching each successive layer when every attempt fails and every layer
    retries its downstream call `retries` times (so retries + 1 attempts each)."""
    attempts = retries + 1
    return [attempts ** k for k in range(layers + 1)]   # k=0: the user's single request

def budgeted(layers: int, ratio: float) -> float:
    """With a per-client retry budget of `ratio` (e.g. 0.1 = at most 10% extra calls),
    each hop multiplies traffic by at most (1 + ratio)."""
    return (1 + ratio) ** layers

def reject_probability(requests: int, accepts: int, k: float = 2.0) -> float:
    """Google SRE book, 'Handling Overload': client-side adaptive throttling.
    p = max(0, (requests - K * accepts) / (requests + 1))"""
    return max(0.0, (requests - k * accepts) / (requests + 1))

    print("\nAdaptive throttling, K = 2, over the last two minutes:")

Metastable failures

Everything so far leads to a class of failure that a 2021 paper gave a name. In "Metastable Failures in Distributed Systems" (Nathan Bronson, Abutalib Aghayev, Aleksey Charapko and Timothy Zhu, HotOS 2021), the authors studied incidents in which a system, once pushed into a bad state, stayed there after the cause was removed. The two ingredients:

  • A trigger: the event that pushes the system out of its healthy state. Load spike, a deploy, a brief network problem, a cache flush, a failover, a small capacity dip. Triggers are many, ordinary, and often not the real problem.
  • A sustaining effect: a positive-feedback loop that keeps the system in the bad state once the trigger has gone. The paper's two most common are retries (workload amplification: failures create more work) and cache misses (capacity loss: an empty cache makes each request more expensive, so the system can serve fewer of them).

The word metastable comes from physics: a state that is stable against small disturbances but not against large ones, like a ball resting on a ledge. Networking's retry storms case introduced the ball-in-a-bowl picture and the toy model. Here is what that case did not do: put numbers on when the bad state exists, and show what it takes to leave it.

When does the bad state exist?

Take a service with capacity μ (say 100 requests per second) and a base load of λ new requests per second. Each request, if it fails, is retried up to R times (R = 3 means 4 attempts). In the healthy state requests succeed, retries are rare, and the offered load is about λ. That state is self-consistent whenever λ < μ. Now consider the failed state: suppose every attempt times out. Each request generates 1 + R attempts, so the offered load is λ(1 + R). If that exceeds μ, the queue stays long, the timeouts continue, and the failed state is also self-consistent. The bad state therefore exists whenever

λ × (1 + R) > μ, that is λ > μ / (1 + R)

For R = 3 and μ = 100, that is any base load above 25 requests per second. Between 25 and 100 the system is bistable: both the healthy state and the failed state are stable, and which one you are in depends only on history. At λ = 70, a comfortable 70% utilisation by the standards of chapter 8, one brief dip can move you from one to the other, and nothing in the dashboards before the incident would have told you so. Two levers move the boundary: fewer retries (R = 0 removes the bad state entirely, because there is no amplification) and a server that does not waste capacity on dead requests (if every unit of capacity always serves a live request, goodput stays at μ and the bad state cannot sustain itself).

The server has to waste capacity for this to hold. That is the role of the FIFO queue in the model: it keeps serving old requests whose clients have left. A server that drops expired requests for free, or serves newest first, has no such waste, which is why deadline shedding and LIFO are a cure for metastability, not only a performance tweak.

Simulating it

The simulation below makes the argument concrete, with simulated time and a seeded random number generator, so the output is exactly reproducible. Clients send about 70 new requests per second to a server that can serve 100 per second from one FIFO queue. A client gives up on an attempt after 1 s and, if it has retries left (up to 3), immediately sends another. For 6 seconds, starting at t = 20, the server slows to 30 requests per second (the trigger). Then it is back to normal. Three runs: the naive system (A); a system with a retry budget and deadline shedding from the start (B); and the naive system rescued by an operator who enables both protections at t = 50 s (C). The retry budget gives each request a tenth of a token and each retry costs one. The shedding rule drops queued requests whose client has already given up (at no cost), and refuses new requests when the queue already holds half a second of work.

"""A service pushed into a metastable failure by retries, then recovered. Simulated time, seeded.

Model (ticks of 0.1 s):
  * Clients create ~70 new requests/s. Each attempt must be answered within 1 s or the client
    gives up on it and, if it has retries left (max 3), sends another attempt immediately.
  * The server has one FIFO queue and can do 100 requests/s (10 per tick). Nothing in the
    naive server notices that a client has given up, so it still does the work: wasted effort.
  * Trigger: for 6 s the server slows to 30 requests/s (say a dependency hiccup), then is fine again.
Protections (each can be switched on):
  * retry budget: a retry needs a token; each new request earns 0.1 token (about 10% extra load).
  * deadline shedding: the server drops a queued request whose client has already given up,
    at no cost, and refuses new work when the queue is longer than 50 (half a second of work).
"""
import random
from collections import deque
from dataclasses import dataclass, field

TICK, CAP, BASE, TIMEOUT, MAX_RETRIES = 0.1, 10, 7.0, 1.0, 3


@dataclass
class Attempt:
    sent: float
    retries_left: int
    done: bool = False          # answered before the client's deadline
    gone: bool = False          # client gave up on this attempt


@dataclass
class Config:
    budget: bool = False
    shed: bool = False
    protect_from: float = 0.0   # protections switch on at this time (seconds)
    trigger: tuple = (20.0, 26.0)
    horizon: float = 90.0


def poisson(rng, mean):
    # Knuth's method; fine for small means
    import math
    L, k, p = math.exp(-mean), 0, 1.0
    while True:
        p *= rng.random()
        if p <= L:
            return k
        k += 1


def run(cfg: Config, seed=5, every=50):
    rng = random.Random(seed)
    queue, pending = deque(), deque()          # server queue; client-side outstanding attempts
    tokens = 10.0
    rows, t = [], 0.0
    good = off = wasted = shed_n = 0
    while t < cfg.horizon - 1e-9:
        protect = t >= cfg.protect_from
        use_budget, use_shed = cfg.budget and protect, cfg.shed and protect
        new = poisson(rng, BASE)
        tokens = min(10.0, tokens + 0.1 * new)
        sends = [Attempt(t, MAX_RETRIES) for _ in range(new)]
        # client timeouts: anything pending longer than TIMEOUT is abandoned, maybe retried
        while pending and t - pending[0].sent >= TIMEOUT - 1e-9:
            a = pending.popleft()
            if a.done:
                continue
            a.gone = True
            if a.retries_left > 0 and (not use_budget or tokens >= 1):
                tokens -= 1 if use_budget else 0
                sends.append(Attempt(t, a.retries_left - 1))
        for a in sends:
            off += 1
            if use_shed and len(queue) >= 5 * CAP:
                a.gone = True
                shed_n += 1
                continue
            queue.append(a)
            pending.append(a)
        cap = CAP if not (cfg.trigger[0] <= t < cfg.trigger[1]) else 3
        while cap > 0 and queue:
            a = queue.popleft()
            if a.gone and use_shed:
                shed_n += 1                     # free: skipped without doing the work
                continue
            cap -= 1
            if a.gone or t - a.sent >= TIMEOUT:
                wasted += 1                     # server worked, nobody was listening
            else:
                a.done = True
                good += 1
        t += TICK
        if round(t / TICK) % every == 0:        # one row per `every` ticks (default 5 s)
            sec = every * TICK
            rows.append((t, off / sec, good / sec, wasted / sec, len(queue)))
            good = off = wasted = 0
    return rows


def show(title, cfg):
    print(f"\n{title}")
    print(f"{'t (s)':>6} {'offered/s':>10} {'goodput/s':>10} {'wasted/s':>9} {'queue':>6}")
    for t, o, g, w, q in run(cfg):
        mark = "  <- trigger" if 20 < t <= 25 else ""
        print(f"{t:6.0f} {o:10.0f} {g:10.0f} {w:9.0f} {q:6d}{mark}")


if __name__ == "__main__":
    show("A. Naive: retries, no protection (trigger ends at t = 26 s)", Config())
    show("B. Protected from the start: retry budget + deadline shedding", Config(budget=True, shed=True))
    show("C. Naive, then the operator enables both at t = 50 s", Config(budget=True, shed=True, protect_from=50.0))

Read run A. Before the trigger it is healthy: goodput 66 to 71 per second, an empty queue. The 6-second dip builds a backlog; the timeouts begin, retries stream in, offered load climbs to 300 per second (about 4 times the base, the 1 + R = 4 of the formula) and goodput drops to zero. At t = 35 the trigger has been over for nine seconds, capacity is the full 100 per second, and the server is working flat out, 100 requests per second of "wasted" work, every one of which is for a client that has gone. The queue grows by about 180 per second for the rest of the run, 12,910 requests deep at t = 90. This is the sustaining effect: the system is not slow, it is busy with useless work.

Run B shows the protected system: the dip still costs it dearly, goodput is cut to 30 per second during the trigger and the offered load briefly rises to 80, but when the dip ends it recovers within seconds, and the queue never exceeds 50. Run C is the incident that actually occurs. The protections are absent until someone enables them at t = 50 s. The moment they are on, the stale queue (5,586 deep) is discarded for free, retries are capped by the budget, and goodput is back to 76 per second within five seconds. The system recovered not because anyone made it faster but because load, useless load, was removed.

Recovery requires reducing load

The general lesson from run C is that a metastable failure cannot be fixed by removing the trigger, and adding capacity alone often does not help. Capacity was already fine at t = 35. You have to break the loop, and that means removing load until the system gets back to its healthy state, then letting load return gradually. Typical actions in an incident (chapter 16):

  1. Shed hard at the edge: reject most traffic (by priority, or by a percentage of customers) so the server can finish what is queued and goodput can resume.
  2. Turn retries off or cap them (a feature flag you built earlier, chapter 13), since they are the amplifier.
  3. Purge the stale queue: drop expired work, or restart the servers to discard their queues. This is why "turn it off and on again" sometimes works: it resets the state the loop lives in.
  4. Ramp traffic back up in steps (1%, 10%, 50%, 100%), watching goodput and queue depth, instead of reopening the floodgates, which can re-trigger the loop.

The cache version: cold caches after recovery

Retries are one sustaining effect. The other the paper highlights is the cache. If a cache absorbs 95% of reads, the database sees only the 5% that miss. If the cache is flushed (a restart, a failover, a deploy that changes the keys) every read goes to the database, which now sees 1 / 0.05 = 20 times its normal load. The database slows down, reads begin to time out, and the cache is filled only by successful reads, so it stays empty. The system has lost its fast path, and the slow path cannot restore it. This is a sustaining effect of a different form (loss of capacity rather than added work), and the same cure applies: reduce the load going to the database until the cache is warm.

  • Warm before you cut over. Pre-fill a new cache from the old one or from a replay of recent requests, before it takes traffic.
  • Ramp gradually ("slow start"): send a small share of traffic to a cold instance and increase it as the hit rate climbs.
  • Collapse duplicate misses: when many requests miss on the same key, let one go to the database and make the rest wait for its answer (single-flight, request coalescing). The data course's caching chapter covers stampedes in detail.
  • Limit concurrency to the database with an admission limit, so that a cold cache degrades latency instead of killing the database. Serve stale data if staleness is acceptable.
  • Avoid designing in a vulnerable state: if the system can only survive with a hot cache, treat the cache as part of the capacity plan (chapter 10), and test what happens when it is empty.

More servers are not always the answer

Adding capacity during an overload can help, and often it is what is done first. But if the sustaining effect is wasted work or a cold cache, new instances start cold, with empty caches and cold connection pools, and join a stampede of retrying clients. Autoscaling that reacts to CPU can add servers that immediately become saturated. It is not wrong to scale up, but expect it to need load reduction alongside, and check whether goodput actually improves.

Distributed systems connection

Overload control is where local decisions meet global behaviour. Each client's retry is individually sensible; together they are an attack on the server. Each server's queue is individually harmless; chained, they hold dead requests across five hops. No single node sees the loop, which is why the protections are all local rules with global effect: a budget, a deadline, a limit. This is the same lesson as in consensus and gossip: simple, bounded local behaviour is how you get a stable whole. The next part of the course turns from load to change, because the other great source of outages is what we do to the system ourselves: deploys and configuration.

Key takeaways

  • Goodput (useful work completed in time) can fall to zero while throughput is high. Beyond capacity, an unprotected service wastes work on abandoned requests and its goodput collapses; a protected one stays near capacity.
  • Shed early and cheaply, and choose what to shed: by priority (triage), by deadline (drop requests whose clients have gone), newest-first under overload (adaptive LIFO), and by queue delay rather than length (CoDel).
  • An adaptive concurrency limit (AIMD, gradient, or Little's-law based) finds the number of in-flight requests that keeps the server busy without queueing, with no hand-tuned constant.
  • Retries multiply across layers: 3 retries (4 attempts) at each of 4 retrying hops can send 4⁴ = 256 attempts to the bottom in the worst case. Retry in one place and put a retry budget (about 10%) on it, which caps four hops at about 1.1⁴ ≈ 1.46.
  • Client-side adaptive throttling rejects locally with probability max(0, (requests − K × accepts) / (requests + 1)), K = 2 in the SRE book, over a two-minute window.
  • A metastable failure has a trigger and a sustaining effect (a feedback loop such as retries or cache misses). With retries R, the bad state exists whenever λ(1 + R) > μ, so a system at 70% utilisation can be bistable.
  • Recovery requires reducing load: shed, cap retries, purge stale queues, ramp back gradually. Removing the trigger or adding capacity is often not enough. Design the vulnerable state out, and rehearse the recovery.

Check your understanding

Four layers in a call chain each retry a failed call 3 times (4 attempts in total). The database at the bottom is down. In the worst case, how many attempts reach the database for one user request?

  1. 12
  2. 256
  3. 81
  4. 1,024
Each of the four retrying hops multiplies by 4 attempts, so 44 = 256. Twelve is 4 × 3, an additive mistake; 81 is 34, which counts retries instead of attempts; 1,024 is 45, one hop too many. It is a worst case that needs every attempt to fail.

What is the key difference between goodput and throughput?

  1. Goodput counts bytes and throughput counts requests
  2. Goodput is measured at the client and throughput at the load balancer, but they are otherwise the same
  3. Goodput excludes errors but includes late answers
  4. Goodput counts only useful work, such as responses that arrive before the client gives up, while throughput counts all completed work
An overloaded server working through a queue of abandoned requests has high throughput and near-zero goodput. That gap is what the collapse curve shows and what shedding by deadline eliminates.

A server is overloaded and has a long FIFO queue. Why does serving the newest requests first (adaptive LIFO) often improve goodput?

  1. Old requests at the head have waited longest and are the most likely to have been abandoned, so serving them wastes capacity, while new requests still have waiting clients
  2. LIFO queues are faster to implement
  3. New requests are always cheaper to serve than old ones
  4. LIFO makes every request faster
The point is the age of the request. Under overload the FIFO head is mostly dead work. LIFO spends capacity on requests that can still succeed; the old ones expire. The price is unfairness, since some requests wait much longer than others, which is the better trade when someone must lose.

A client's recent history shows 1,000 requests, of which the backend accepted 300. Using the SRE book's adaptive throttling with K = 2, roughly what fraction of new requests does the client reject locally?

  1. 0%
  2. 70%
  3. 40%
  4. 100%
p = max(0, (1000 − 2 × 300) / 1001) = 400 / 1001 ≈ 0.4. With 500 or more accepted out of 1,000 the result would be 0, which is the answer for a healthy backend. 70% is the share the backend rejected, not what the client throttles.

A service has capacity 100 requests/s, a base load of 40 requests/s and clients retry up to 3 times (4 attempts) on timeout. Which statement is correct?

  1. It can never fail metastably, because 40% utilisation is low
  2. It is vulnerable: if all attempts fail the offered load is 40 × 4 = 160, above capacity, so a failed state can sustain itself
  3. It is vulnerable only if the base load exceeds 100
  4. It is safe as long as the trigger lasts under one minute
The bad state exists when λ(1 + R) > μ: here 160 > 100. At 40 requests/s the system is in the bistable range (above 25 and below 100). The trigger's length changes how likely it is to tip, not whether the bad state exists.

An incident is in a metastable state: the original trigger has been fixed and capacity is fine, but goodput is zero and the queue is huge. What is the most reliable first move?

  1. Double the number of servers and wait
  2. Roll back the last deploy, which must have been the cause
  3. Increase client timeouts so requests have longer to finish
  4. Reduce load: shed at the edge, cap retries, drop the stale queue, then ramp traffic back up gradually
The trigger is already gone, so rolling back changes nothing, and longer timeouts keep dead requests in the queue longer. Extra servers start cold and join the stampede. The sustaining loop is fed by load that no longer serves anyone, so the loop is broken by removing that load.

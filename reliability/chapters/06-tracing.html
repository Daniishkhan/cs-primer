Distributed Tracing

A single click on "Buy" can touch dozens of services, and a log line from one of them says nothing about the other forty. Distributed tracing reconstructs the journey of one request across every process it visited, with timing, so you can see where the time went and which call is to blame. This chapter covers the Dapper model of traces and spans, the W3C header that carries context between services, how context crosses queues, what sampling does to rare failures, how to find the critical path, how traces connect to metrics, and where OpenTelemetry fits.

Why this matters

The most common production question in a service-oriented system is "this request was slow; where?". Metrics say that the p99 of /checkout is high. Logs hold the story of each service in isolation. Neither shows that the time was spent waiting on a pricing service which was itself waiting on a cache that missed. Tracing is the tool for that question, and the mental model it teaches, a request as a tree of timed calls with a critical path, is the model you use for reasoning about latency whether or not you have a tracing system installed.

Dapper: the model that everyone copied

In 2010 Benjamin Sigelman and colleagues at Google published a technical report, "Dapper, a Large-Scale Distributed Systems Tracing Infrastructure", describing the system Google had been running in production for years. Nearly every tracing system since (Zipkin, Jaeger, OpenTracing, OpenTelemetry) descends from its vocabulary, and the design goals it states are worth remembering because they still decide what is practical: low overhead (a tracer that slows the service is turned off), application-level transparency (developers should not have to instrument everything by hand, so the tracing hooks live in shared libraries: the RPC framework, the thread pool), and scalability.

The model has three pieces.

  • A span is one named, timed unit of work: "handle POST /checkout", "call pricing service", "SELECT from orders". It has a start time, a duration, and key-value attributes (annotations in Dapper's terms) such as the route, the status or the database statement.
  • Spans form a tree through parent/child links: when service A calls service B, the span for B's work is a child of the span for A's outgoing call.
  • A trace is the whole tree for one request, identified by a trace ID shared by every span in it. Each span also has its own span ID and records its parent's span ID.

The elegance is that the tree can be rebuilt after the fact from independent pieces. Each service reports its own spans to a collector asynchronously; nobody needs to know the whole shape in advance, and nothing in the request path waits for the tracing backend. Dapper also reported that it traced only a small fraction of requests (a low uniform sampling rate, with the paper discussing rates around one in a thousand), and that this was enough for the common questions, because at Google's volume even a small sample contains many examples of every common behaviour. We return to what sampling costs below.

In the hospital analogy, a trace is the patient journey record: triage at 14:02, X-ray 14:20, bloods 14:25, consultant 15:10. The individual departments (services) each have their own notes (logs); only the journey record shows that the patient waited 50 minutes for a consultant while the lab had finished long before.

Context propagation: carrying the identity of a request

For spans to join into a tree, each service must learn two things from its caller: the trace ID and the ID of the caller's span (to record as its parent). The bundle is the span context (also "trace context"), and moving it from one process to the next is context propagation. It has two halves.

  1. Within a process: the context must follow the request across function calls, threads and async tasks without every function taking it as a parameter. As in chapter 5, this uses ambient context (thread-locals, Go's context.Context, Python's contextvars). A very common cause of broken traces is a place where the context is lost: a thread pool or callback that was not instrumented, so the next span starts a fresh, orphaned trace.
  2. Between processes: the context is serialized into a header (HTTP) or metadata (gRPC, message headers) on the outgoing call, and parsed on the way in.

The W3C Trace Context header

For years each tracing system invented its own header (X-B3-TraceId in Zipkin, uber-trace-id in Jaeger, vendor ones elsewhere), which broke traces whenever a request crossed a system using a different scheme. The W3C Trace Context recommendation standardised one: the traceparent header (plus an optional tracestate for vendor-specific data). Its version 00 format is four dash-separated, lowercase-hex fields:

GET /price?sku=A17 HTTP/1.1
Host: pricing.internal.example.com
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
tracestate: vendor1=opaque-value,vendor2=other

The sampled bit is the lowest bit of the flags byte: when set (01) the caller (or an upstream decision) indicates that this trace may be recorded; clear (00) means it probably is not. It is tested with a bit mask, not by reading the hex as a number, because other bits are reserved. The decision rides along with the request, so every service in the call chain makes the same choice and you get complete traces rather than a confetti of fragments. tracestate is a comma-separated list of up to 32 vendor key-value pairs, for information that one tracing vendor wants to pass along without breaking another's.

Context is therefore tiny (55 bytes) and rides in headers that every proxy already passes. It does need to be forwarded by every hop: a gateway, service mesh sidecar or message broker that drops unknown headers severs the trace there.

Across queues: links, not just parents

A synchronous call has a clean shape: the caller waits, the callee's work nests inside the caller's span, parent-child is natural. Architecture chapter 13 contrasted synchronous calls with asynchronous messaging. Tracing makes the difference visible: after a message is published, the producer's span ends and the consumer's work happens later, perhaps seconds or hours, perhaps in a batch, perhaps retried several times. The consumer is not "inside" the producer's operation in time.

Two representations are in use, and neither is wrong:

  • Child of the producer. Same trace ID, parent is the publish span. The waterfall shows a long gap (the queue wait) before the consumer span, which is itself informative. Works well for one-message-one-consumer flows.
  • New trace plus a link. A span link is a reference from one span to another span's context that is not a parent. It fits where a parent-child tree would be wrong: a consumer that processes a batch of 100 messages from 100 different traces (one span with 100 links), a retry hours later, or fan-in from several sources. Links keep each trace's duration meaningful (a trace that includes a six-hour retry delay would swamp its own timeline).

Reading a trace: waterfalls, fan-out and the critical path

The standard view is the waterfall (or Gantt) chart: one row per span, a bar from start to end, indented by depth. It reveals structure at a glance: which calls are sequential (a staircase), which are parallel (bars aligned at the same start), where there are gaps (time in no child, so the parent's own computation, queueing, or untraced work), and which span is longest.

Longest is not the same as important. Consider the checkout request above: it calls inventory and pricing in parallel, and the inventory call is quick while pricing is slow. Making inventory twice as fast changes nothing, because the request waits for pricing anyway. The critical path is the chain of spans that determines the total duration: the sequence that, if any one link got faster, would make the whole request faster. Formally, walk backwards from the end of the root: at each point take the child that finished last, then continue from its start, recursing into it. Everything off that path has slack: it can slow down by some amount without affecting the user. Optimisation effort belongs on the critical path; on a parallel fan-out, only the slowest branch matters (and only until it becomes faster than the next slowest).

Try the widget before reading on: in parallel mode, speeding up inventory or catalog changes nothing; speeding up pricing helps, but only until it ties with catalog (18 ms in total, including its database call); and the fixed sequence of auth, group, payment is a chain in which every link counts. In sequential mode, every call in the group is on the critical path, and switching to parallel is by far the largest improvement available. That is the reason waterfalls so often lead to the fix "these calls are independent, issue them concurrently".

Fan-out and the tail

A request that fans out to N services in parallel and waits for all of them is as slow as its slowest branch. If each backend returns within its own p99 99% of the time, the chance that at least one of 100 parallel calls is slower than its p99 is 1 - 0.99100, about 63%. The p99 of a backend becomes the typical experience of a wide fan-out, which is the "tail at scale" effect of chapter 9. Traces are how you observe it concretely: the critical path through a fan-out changes from request to request, hopping to whichever branch happened to be slow this time.

Building the intuition: a tiny tracer

A tracer is small enough to write in a few dozen lines. This runnable program simulates three services in one process (no sockets): context propagation in-process through contextvars and between "services" through a W3C-style traceparent string, a parallel fan-out, then rebuilds the tree, prints a text waterfall and computes the critical path with self-times.

import contextvars, itertools, random
from dataclasses import dataclass, field

rng = random.Random(5)
ids = itertools.count(1)
SPANS: list["Span"] = []
current: contextvars.ContextVar = contextvars.ContextVar("current", default=None)

@dataclass
class Span:
    trace_id: str
    span_id: str
    parent_id: "str | None"
    service: str
    name: str
    start: float
    end: float = 0.0

def traceparent(s: Span) -> str:
    return f"00-{s.trace_id}-{s.span_id}-01"       # version-traceid-parentid-flags

def start_span(service, name, t, header=None) -> Span:
    """Parent comes from an incoming header (remote) or the current context (local)."""
    if header:
        _, tid, pid, _ = header.split("-")
    elif current.get():
        tid, pid = current.get().trace_id, current.get().span_id
    else:
        tid, pid = f"{rng.getrandbits(128):032x}", None
    s = Span(tid, f"{next(ids):016x}", pid, service, name, t)
    SPANS.append(s)
    return s

# Each "service" takes (start time, header) and returns its end time.
def inventory(t, header):
    s = start_span("inventory", "GET /stock", t, header)
    s.end = t + 8
    return s.end

def pricing(t, header):
    s = start_span("pricing", "GET /price", t, header)
    tok = current.set(s)                         # local children find their parent here
    c = start_span("pricing", "cache lookup", t + 1)
    c.end = t + 3
    current.reset(tok)
    s.end = t + 25
    return s.end

def checkout(t0):
    root = start_span("checkout", "POST /checkout", t0)
    tok = current.set(root)
    t = t0 + 3                                   # parse + auth
    ends = []
    for name, svc in (("call inventory", inventory), ("call pricing", pricing)):
        c = start_span("checkout", name, t)      # client span; parent = root via context
        end = svc(t + 1, traceparent(c))         # 1 ms network, header crosses the wire
        c.end = end + 1
        ends.append(c.end)
    t = max(ends)                                # parallel fan-out: wait for the slowest
    db = start_span("checkout", "db write", t + 5)
    db.end = db.start + 12
    root.end = db.end + 1
    current.reset(tok)

checkout(0.0)

kids: dict = {}
for sp in SPANS: kids.setdefault(sp.parent_id, []).append(sp)

def critical_path(s):
    """Walk backwards from s.end: at each point follow the child that finished last."""
    path, t = [s], s.end
    ch = sorted(kids.get(s.span_id, []), key=lambda c: c.end, reverse=True)
    for c in ch:
        if c.end <= t + 1e-9:
            path += critical_path(c)
            t = c.start
    return path

root = kids[None][0]
total = root.end
W = 36
def show(s, d=0):
    a = int(s.start / total * W); b = max(a + 1, round(s.end / total * W))
    print(f"{'  ' * d + s.name:22s}{s.service:10s}|{' ' * a}{'#' * (b - a)}{' ' * (W - b)}|{s.end - s.start:4.0f} ms")
    for c in sorted(kids.get(s.span_id, []), key=lambda c: c.start):
        show(c, d + 1)
print(f"trace {root.trace_id[:8]}...  total {total:.0f} ms")
show(root)
cp = critical_path(root)
onpath = {x.span_id for x in cp}
print("critical path (time that only this chain can shorten):")
tot = 0
for x in cp:
    self_t = (x.end - x.start) - sum(c.end - c.start for c in kids.get(x.span_id, []) if c.span_id in onpath)
    tot += self_t
    print(f"  {x.service}:{x.name:16s} self {self_t:4.0f} ms")
print(f"  sum of self times = {tot:.0f} ms (= trace duration)")
trace 5bc8fbbc...  total 48 ms
POST /checkout        checkout  |####################################|  48 ms
  call inventory      checkout  |  ########                          |  10 ms
    GET /stock        inventory |   ######                           |   8 ms
  call pricing        checkout  |  ####################              |  27 ms
    GET /price        pricing   |   ###################              |  25 ms
      cache lookup    pricing   |   ##                               |   2 ms
  db write            checkout  |                          ######### |  12 ms
critical path (time that only this chain can shorten):
  checkout:POST /checkout   self    9 ms
  checkout:db write         self   12 ms
  checkout:call pricing     self    2 ms
  pricing:GET /price       self   23 ms
  pricing:cache lookup     self    2 ms
  sum of self times = 48 ms (= trace duration)

Several things are visible in the output. The two calls start at the same instant (parallel), so the staircase is absent; the total is 48 ms rather than the sum of the parts. The critical path runs through pricing (the slower branch), not inventory. The "self time" listing shows where time is actually spent: 23 ms is inside GET /price itself, which is more than the whole inventory branch. And the self-times sum exactly to the trace duration, a handy check that the algorithm is right. The "network" here is a string, but the mechanics (generate IDs at the root, send traceparent, create a child span from the header on the far side) are the same as in a real tracer, which is what the tracing lab builds out in full.

Span attributes, events and status

A bare span says "this took 25 ms". The detail that makes a trace diagnostic goes in:

  • Attributes: key-value facts about the whole span. http.route, db.system, customer.tier, cache.hit=false, retry.count=2. Spans (like logs, unlike metrics) tolerate high cardinality, so putting user.id or order.id here is fine and is what lets you find the trace for a particular complaint.
  • Events (log records attached to a span): timestamped points within a span, such as "retry attempt 2", "cache miss", "exception thrown" with a stack trace. They put the equivalent of a log line in the right place on the timeline.
  • Status: unset, OK or error, plus the span kind (client, server, producer, consumer, internal) that tells the UI which side of a call it is looking at.

The point of attaching the same fields you would put in a wide event (chapter 5) is that a span is almost a wide event with timing and a parent. Many modern tools treat them as the same record: instrument once, derive logs-like queries and trace views from it.

Sampling: what you keep and what you lose

Tracing every request is usually too expensive. A trace with 30 spans of 500 bytes each is 15 KB; at 5,000 requests per second that is 75 MB/s. Dapper's low rate was a design decision, and today most deployments sample too. The decision can be made at two points, with very different outcomes.

Head-based sampling decides when the request enters the system (a random draw, or a hash of the trace ID against a threshold) and propagates the decision in the sampled flag. It is simple, cheap, stateless, and has no extra delay. Its weakness is built in: the decision is made before anyone knows whether the request will be interesting. Suppose 0.1% of requests fail, you have a million requests a day, and you keep 1%. You get about 10,000 sampled traces, of which about 10 are errors, out of 1,000 errors. The chance that a particular rare failure, the one a customer is writing to complain about, has a trace is 1%. Rare events are precisely where tracing is wanted, and uniform head sampling treats them as common ones.

Tail-based sampling sends every span to a collector, buffers all the spans of each trace until it looks complete (usually a fixed wait of some seconds after the last span arrives), and then applies rules: keep all traces with an error, keep all traces slower than the SLO threshold, keep a small random share of the rest as a baseline. Now rare failures are kept at 100%. The price is real:

  • Memory and a wait window. At 5,000 requests per second with a 10-second wait, 50,000 traces are in flight; at 10 spans of 500 bytes each that is about 250 MB buffered (an assumption-laden estimate, but the right order of magnitude), and every span must still travel from the services to the collector, so network and ingest costs are paid before the drop decision.
  • All spans of a trace must reach the same collector instance, so you route by trace ID (a load-balancing tier in front), and that tier becomes stateful infrastructure with its own failure modes.
  • Late spans. A span arriving after the decision is lost or orphaned; a long-running trace may be judged before it finishes.

Real systems combine them: modest head sampling to cap the volume entering the pipeline, then tail rules on what arrives, and dynamic rates per route so that a quiet endpoint is traced more often than a hot one. Whatever you choose, two honest caveats stay: sampled traces cannot give you counts or rates (use metrics), and a tail sampler biased toward slow and failing requests gives a biased picture of "typical" behaviour (use the baseline share for that).

Exemplars: from a metric to a trace

The three signals are most powerful when you can jump between them. A metrics dashboard shows a latency spike at 14:03. You want an actual slow request from that moment. An exemplar is a sample of one real observation attached to a metric data point, carrying the trace ID of the request that produced it. In the OpenMetrics text format it is appended to a histogram bucket line after a #:

http_request_duration_seconds_bucket{route="/checkout",le="1"} 133988 # {trace_id="4bf92f3577b34da6a3ce929d0e0e4736"} 0.83

Dashboards that understand exemplars draw them as dots over a latency heatmap; clicking a dot in the slow bucket opens that exact trace. It is a small feature with a big effect on investigation time: instead of guessing which of 10,000 traces is representative, the metric hands you one that landed in the bucket you are staring at. Note how this respects each signal's strengths: the metric stays cheap and low-cardinality (the trace ID is not a label), while the high-cardinality detail lives in the trace store.

OpenTelemetry in outline

OpenTelemetry (OTel) is a Cloud Native Computing Foundation project formed by merging two earlier efforts, OpenTracing (an API standard) and OpenCensus (a Google-originated library with metrics and traces). Its aim is a single vendor-neutral way to produce traces, metrics and logs, so that you instrument your code once and choose the backend later. The concepts you need:

  • API: the interfaces application and library code call (tracer.start_span, span.set_attribute). With no SDK installed they do nothing, which lets libraries ship instrumentation at zero cost.
  • SDK: the implementation, configured by the application owner: which sampler, which processors and exporters, which resource attributes (service.name, version, host).
  • Instrumentation: automatic (agents or wrappers that patch popular frameworks and HTTP and database clients) or manual (your own spans around business operations). Auto-instrumentation gets you a skeleton fast; manual spans and attributes add the meaning.
  • OTLP: the OpenTelemetry Protocol, the wire format (over gRPC or HTTP) for sending telemetry from SDKs to a collector or backend.
  • Collector: a standalone process (a sidecar, an agent per host, or a gateway tier) with pluggable receivers, processors (batching, attribute editing, tail sampling) and exporters. It is where redaction, sampling and fan-out to multiple backends belong, so that applications stay simple.
from opentelemetry import trace

tracer = trace.get_tracer("checkout")

def charge(order_id: str, amount: int) -> None:
    with tracer.start_as_current_span("charge") as span:
        span.set_attribute("order.id", order_id)
        span.set_attribute("payment.amount", amount)
        for attempt in (1, 2):
            try:
                call_bank(amount)
                break
            except TimeoutError as exc:
                span.add_event("retry", {"attempt": attempt})
                span.record_exception(exc)
receivers:
  otlp:
    protocols:
      grpc:
      http:

processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: keep-errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: keep-slow
        type: latency
        latency: { threshold_ms: 500 }
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 5 }
  batch: {}

exporters:
  otlp:
    endpoint: traces.example.com:4317

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [tail_sampling, batch]
      exporters: [otlp]

Both snippets are illustrative: they follow the shape of the OpenTelemetry Python API and of the collector's tail-sampling processor, but I have not run them against a live collector here, and option names change between versions. The architecture is the durable part: the application emits to a local collector over OTLP, the collector does the heavy and policy-laden work, and the backend stores and indexes.

Common misconception: "tracing replaces logs and metrics"

Traces answer "where did the time go in this request?", and they are sampled, so they cannot tell you error rates or throughput. Metrics give complete, cheap counts and alert fast; logs and wide events carry arbitrary detail. Tracing also needs 100% propagation coverage to be useful: a single un-instrumented hop breaks the tree below it. Treat the three as partners (exemplars and shared trace IDs in logs are the glue).

Distributed systems connection

Tracing is a practical application of the logical-time ideas you met in the distributed-systems course. The parent-child tree is a happens-before relation recorded explicitly through IDs, so it stays valid even when machine clocks disagree, though the timeline bars across hosts still inherit clock error (a child can appear to start before its parent if the two clocks differ by more than the network delay). Trace IDs flowing through headers are the same trick as correlation IDs, and the problems of tracing through queues are those of reasoning about asynchronous causality that appeared in the architecture chapter on sync versus async communication. Chapter 9 uses traces to see tail amplification, and chapter 12's canary analysis compares trace-derived latencies between versions.

Key takeaways

  • A trace is a tree of spans sharing a trace ID; each span records its parent's ID, a name, timing and attributes (Dapper, Sigelman et al., 2010).
  • Context propagation is the hard part: ambient context in-process, and the W3C traceparent header (version-traceid-parentid-flags, 55 characters, bit 0 = sampled) between processes. One hop that drops the header severs the tree.
  • Through queues, use a parent-child link when the flow is one-to-one, and a span link when work is batched, delayed or fanned in.
  • The critical path is the chain that sets total latency; only speeding up spans on it helps. Fan-out makes the slowest branch decide, and the slowest branch moves from request to request.
  • Head sampling is cheap but discards rare errors at the sampling rate; tail sampling keeps errors and slow traces at the cost of buffering and routing by trace ID. Sampled traces cannot give you rates.
  • Exemplars attach a trace ID to a metric data point, linking the cheap aggregate to the expensive detail.
  • OpenTelemetry separates API, SDK, collector and the OTLP protocol, so instrumentation is vendor neutral; put redaction and sampling policy in the collector.

Check your understanding

What does the third field of traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 identify?

  1. The trace, shared by all spans
  2. The sampling decision
  3. The span ID of the caller, which becomes the parent of the receiver's new span
  4. The version of the protocol
Fields in order: version (00), trace-id (32 hex), parent-id (16 hex, the caller's span), trace-flags (01, sampled bit set). Each hop creates a new span ID of its own and passes that as the parent-id on its outgoing calls.

A request calls service X (80 ms) and service Y (50 ms) in parallel, then writes to a database for 20 ms. Parent self-time is negligible. Which change reduces total latency most?

  1. Halving Y to 25 ms
  2. Halving X to 40 ms
  3. Halving the database call
  4. They are all equal because everything is on the critical path
The total is max(80, 50) + 20 = 100 ms. Y is off the critical path, so speeding it up changes nothing. Halving X gives max(40, 50) + 20 = 70 ms, saving 30 ms. Halving the database saves 10 ms. After X drops below Y, the critical path moves to Y: the path is a moving target.

Errors occur in 0.1% of requests. You use head-based sampling at 1%. Roughly what fraction of error requests have a stored trace?

  1. About 1%, the same as all other requests, since the decision is made before the outcome is known
  2. About 100%, because errors are always kept
  3. About 0.1%, the error rate
  4. About 50%
Head sampling is blind to the outcome, so errors are kept at the same 1% as everything else. Keeping errors specifically needs tail-based (or hybrid) sampling.

A worker consumes a batch of 50 messages in one go, each message from a different trace. How should the worker's span relate to the producers?

  1. It should be a child of all 50 producer spans
  2. It should copy the first message's trace ID and ignore the rest
  3. It should have no relationship, because queues break tracing
  4. It should have 50 span links, one to each producer's span context, since a span can have only one parent
A tree allows exactly one parent, so batch and fan-in relationships use links, a many-to-one reference that keeps each producer trace intact without distorting its duration.

What is the main operational cost of tail-based sampling?

  1. It cannot keep error traces
  2. The collectors must buffer all spans of in-flight traces and receive every span of a trace on the same instance, so you run a stateful, memory-hungry routing tier
  3. It requires changing the traceparent format
  4. It removes the need for context propagation
The benefit is keeping errors and slow traces; the cost is buffering and routing by trace ID. Context propagation is still needed to produce the spans' links in the first place.

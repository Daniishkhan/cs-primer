Configuration & Infrastructure as Code

Code is not the only thing you deploy. A timeout, a firewall rule, a feature flag, a regular expression in a filter and the Terraform that defines your load balancer are all changes to production, and they are routinely pushed with less care than a code release. This chapter treats configuration and infrastructure as what they are: software, with all the rigour that implies.

Why this matters

Look at the largest public outages of the last decade and a surprising number are not a code bug that survived testing but a configuration or content change that reached everything at once. Configuration is attractive to change precisely because it feels small: no compile, no release train, one line. The same properties make it dangerous: fast to apply, global by default, usually untested, and often exempt from the staged rollout that your binaries get. After this chapter you should be uneasy every time someone says "it's just a config change".

Configuration changes cause outages

Configuration is everything that changes a program's behaviour without changing its code: command-line flags, environment variables, files, values in a database, feature flags, routing and firewall rules, even the data a security product ships to its sensors. The last chapter said that most outages follow a change; a very large share of those changes are configuration. We stay qualitative here, because published counts depend on who counted and how, and look at three cases from this course:

  • CrowdStrike, July 2024. A content update (a data file interpreted by a kernel-level sensor) was delivered to a very large number of Windows machines at once, and the sensor failed on the malformed content. It is a textbook case of a "not code" change that bypassed staged rollout. Read it in the CrowdStrike case.
  • Cloudflare, July 2019. A new rule for the web application firewall contained a regular expression that could consume enormous CPU. The rule was deployed globally at once, and edge CPUs were exhausted. It is covered, from the regex side, in the Cloudflare regex case; the lesson here is the rollout side: a rule is a deployment.
  • Facebook, October 2021. A routine maintenance command withdrew the network routes that told the rest of the internet how to reach the company's data centres; see the networking case. The change itself was operational configuration, and the safeguard that should have stopped it contained a bug.

The common thread is not carelessness. Each change was routine, each was made by competent people, and each reached too many places before anyone learned it was bad. The remedy is therefore the same as for code and has the same shape: validate before shipping, ship in waves, watch, and be able to go back.

Config is code

The principle is easy to state and surprisingly rarely practised: treat configuration like code. Concretely:

  • Keep it in version control. Every change has an author, a diff, a reason and a revert button. "Someone edited it in the console" is the config equivalent of editing production source on the server.
  • Review it. A second pair of eyes catches a typo'd value more reliably than any amount of caution by the author. Review the rendered result where possible (what the final file will look like), not only the template.
  • Type it. Prefer a schema (JSON Schema, Protocol Buffers, CUE, Dhall or typed language structures) to free-form strings. A schema rejects timeout: "500ms" where an integer of milliseconds was expected, and rejects a misspelled key instead of silently ignoring it.
  • Validate semantically. Types are not enough. A timeout of 0 is a valid integer. Add range checks, cross-field rules ("the retry budget times the timeout must fit inside the client deadline") and invariants ("at least two healthy backends in every cell").
  • Test it. Render the config and run the service's real config loader against it in CI. Replay recent real traffic against a staging instance for rule-like config (firewall, routing, regular expressions), watching CPU and latency.
  • Canary it and roll it out in waves. The whole of chapter 12 applies: one cell, one zone, one region, bake, judge, widen. The config pipeline should look the same as the binary pipeline, and ideally be the same pipeline.

Static validation and staged rollout catch different bugs, and you want both. The simulator below makes the difference concrete. A validator rejects a zero timeout, a string where a number belongs and a misspelled field, all before anything ships. It cannot reject cache_ttl_s: 1: a perfectly legal value that happens to multiply database load by thirty. Only the waves find that, and the damage is limited to the first wave's blast radius instead of the whole fleet.

"""Config validator + staged-rollout simulator.
Layer 1 (static): types, ranges, cross-field rules. Catches values that are *invalid*.
Layer 2 (dynamic): push to waves of cells and watch health. Catches values that are *valid but harmful*."""
from dataclasses import dataclass

SCHEMA = {                       # field: (type, min, max)
    "timeout_ms":      (int, 10, 30_000),
    "max_connections": (int, 1, 10_000),
    "cache_ttl_s":     (int, 0, 86_400),
    "retry_limit":     (int, 0, 5),
}


def validate(cfg: dict) -> list[str]:
    errs = []
    for key, (typ, lo, hi) in SCHEMA.items():
        if key not in cfg:
            errs.append(f"{key}: missing")
        elif not isinstance(cfg[key], typ) or isinstance(cfg[key], bool):
            errs.append(f"{key}: expected {typ.__name__}, got {type(cfg[key]).__name__}")
        elif not lo <= cfg[key] <= hi:
            errs.append(f"{key}: {cfg[key]} outside [{lo}, {hi}]")
    for key in cfg:
        if key not in SCHEMA:
            errs.append(f"{key}: unknown field (typo?)")
    if not errs and cfg["retry_limit"] * cfg["timeout_ms"] > 60_000:
        errs.append("retry_limit * timeout_ms exceeds the 60 s client deadline")
    return errs


@dataclass
class Cell:
    name: str
    cfg: dict

    def db_load(self) -> float:
        """Toy model: DB queries per second this cell generates. Cache TTL shields the DB."""
        reqs = 1000
        miss_rate = min(1.0, 1.0 / max(self.cfg["cache_ttl_s"], 0.1))
        return reqs * miss_rate * (1 + self.cfg["retry_limit"] * 0.1)

    def healthy(self) -> bool:
        return self.db_load() <= 400          # health check: DB budget per cell


def staged_rollout(new_cfg: dict, cells: list[Cell], waves: list[int]) -> None:
    errs = validate(new_cfg)
    if errs:
        print("  REJECTED by validator:", "; ".join(errs))
        return
    done = 0
    for w, size in enumerate(waves, 1):
        batch = cells[done:done + size]
        for c in batch:
            c.cfg = dict(new_cfg)
        done += len(batch)
        sick = [c.name for c in batch if not c.healthy()]
        print(f"  wave {w}: pushed to {len(batch):>2} cells ({done:>2}/{len(cells)} total) "
              f"-> {'UNHEALTHY ' + str(sick[:3]) if sick else 'healthy'}")
        if sick:
            old = {"timeout_ms": 500, "max_connections": 200, "cache_ttl_s": 30, "retry_limit": 2}
            for c in cells[:done]:
                c.cfg = dict(old)
            print(f"  HALT and revert; blast radius = {done} of {len(cells)} cells")
            return
    print("  rollout complete")


def fleet() -> list[Cell]:
    base = {"timeout_ms": 500, "max_connections": 200, "cache_ttl_s": 30, "retry_limit": 2}
    return [Cell(f"cell-{i:02d}", dict(base)) for i in range(40)]


WAVES = [1, 3, 8, 28]           # one cell, a few, a quarter, everyone else

print("Case A: a zero timeout, a wrong type, a misspelled field")
staged_rollout({"timeout_ms": 0, "max_connections": 200, "cache_ttl_s": 30, "retry_limit": 2}, fleet(), WAVES)
staged_rollout({"timeout_ms": "500", "max_connections": 200, "cache_ttl_s": 30, "retry_limit": 2}, fleet(), WAVES)
staged_rollout({"timeout_ms": 500, "max_connections": 200, "cache_ttl_s": 30, "retry_limit": 5, "retires": 1}, fleet(), WAVES)

print("Case B: valid but harmful (cache_ttl_s = 1), staged rollout")
bad = {"timeout_ms": 500, "max_connections": 200, "cache_ttl_s": 1, "retry_limit": 2}
print("  validator says:", validate(bad) or "ok")
staged_rollout(bad, fleet(), WAVES)

print("Case C: the same harmful value pushed to everyone at once")
f = fleet()
staged_rollout(bad, f, [40])

print("Case D: a good change")
staged_rollout({"timeout_ms": 400, "max_connections": 300, "cache_ttl_s": 60, "retry_limit": 2}, fleet(), WAVES)
Case A: a zero timeout, a wrong type, a misspelled field
  REJECTED by validator: timeout_ms: 0 outside [10, 30000]
  REJECTED by validator: timeout_ms: expected int, got str
  REJECTED by validator: retires: unknown field (typo?)
Case B: valid but harmful (cache_ttl_s = 1), staged rollout
  validator says: ok
  wave 1: pushed to  1 cells ( 1/40 total) -> UNHEALTHY ['cell-00']
  HALT and revert; blast radius = 1 of 40 cells
Case C: the same harmful value pushed to everyone at once
  wave 1: pushed to 40 cells (40/40 total) -> UNHEALTHY ['cell-00', 'cell-01', 'cell-02']
  HALT and revert; blast radius = 40 of 40 cells
Case D: a good change
  wave 1: pushed to  1 cells ( 1/40 total) -> healthy
  wave 2: pushed to  3 cells ( 4/40 total) -> healthy
  wave 3: pushed to  8 cells (12/40 total) -> healthy
  wave 4: pushed to 28 cells (40/40 total) -> healthy
  rollout complete

Case B and Case C are the same change. Pushed in waves it is stopped at one cell of forty; pushed to everyone it is a 40-of-40 outage. That ratio, 1 in 40 against 40 in 40, is what staging buys, and it is why the CrowdStrike and Cloudflare cases end with the same remedy. The toy health check here is a single database-load threshold; a real one compares the wave against a baseline with the statistics of chapter 12.

Analogy: the airline's checklist and the technician's work card

An aircraft maintenance change is written on a work card, signed by the person who did it, and independently inspected before the aircraft flies, with a test flight for certain classes of work. Nobody edits an engine "just a little" without paperwork. Reviewed, validated, staged config is the same culture: the paperwork is the pull request and the inspection is the pipeline.

Where it breaks down: an airline touches an aircraft a few times a year. A large service might change configuration thousands of times a day, so the checks must be automatic, or people will route around them.

Dynamic configuration and feature flags

Many systems read configuration while running, from a central service, rather than only at startup. Dynamic configuration lets you change behaviour in seconds without a deploy, and feature flags (introduced in architecture chapter 18) are its best-known use: a named switch, evaluated at runtime, deciding which code path a request takes. The speed is the point, and the danger. A change that can take effect globally in a few seconds can break globally in a few seconds, and it often bypasses the release pipeline entirely.

# Illustrative feature-flag definition (not any specific product's format)
flag: new-ranking-model
owner: search-team            # every flag has an owner...
expires: 2026-12-01           # ...and an expiry date, so flags get deleted
default: false                # safe value if the flag service is unreachable
rollout:
  - cells: [cell-01]          # wave 1
    percent: 100
  - regions: [eu-west-1]      # wave 2
    percent: 10

The failure modes of these systems are worth knowing by heart, because the flag service is itself a production dependency:

The config service is down

If every request asks the flag service synchronously, its outage is yours. Safe designs fail static: the client caches the last known good configuration, refreshes asynchronously, and falls back to a safe default compiled into the binary. A flag lookup should never be on the critical path as a network call.

A bad value propagates instantly

Dynamic config has no natural wave. Give it one: roll flags out by cell, region and percentage, and subject flag changes to the same judge as releases. Keep an audit log of who changed which flag, because during an incident "what changed?" is the first question.

Combinatorial states

Ten independent boolean flags are 1,024 possible programs, and you have tested a handful. Interactions between flags cause the nastiest bugs. Keep flags few, short-lived and independent, and test the "all defaults" and "all new" extremes.

Flag debt and zombie code

A flag nobody remembers is a loaded trap. Give each flag an owner and an expiry date, and delete flags once a feature is fully rolled out. The 2012 Knight Capital incident, in which an old code path was reactivated when a flag name was reused while one of eight servers still ran old code, is the cautionary tale; take its dollar figures from the primary sources, not from memory.

Infrastructure as code

Servers, networks, databases and load balancers are changes too, and for years they were made by hand in a console. Infrastructure as code (IaC) means describing infrastructure in text files, keeping them in version control, and having a tool make reality match the text. The dominant style is declarative: you describe the desired end state ("three web servers of this size, using this image") rather than the steps to get there, and the tool computes the steps. You have seen this idea before: it is the same desired-state model as the Kubernetes controllers in the next chapter.

Terraform and OpenTofu are the most common tools for cloud resources. Here is an illustrative configuration in HCL (HashiCorp Configuration Language). It is a realistic shape, not a complete production module, and I did not run it.

terraform {
  required_version = ">= 1.5"

  backend "s3" {                        # remote state, with locking so two applies cannot race (newer Terraform can lock with use_lockfile instead of DynamoDB)
    bucket         = "example-tf-state"
    key            = "checkout/prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "example-tf-locks"
  }
}

variable "web_count" {
  type    = number
  default = 3
}

variable "ami_id" {
  type        = string
  description = "Golden image built by the image pipeline"
}

resource "aws_instance" "web" {
  count         = var.web_count
  ami           = var.ami_id            # change the image, replace the instances
  instance_type = "m6i.large"

  tags = {
    Name = "checkout-web-${count.index}"
    Env  = "prod"
  }
}

resource "aws_db_instance" "orders" {
  identifier        = "orders-prod"
  engine            = "postgres"
  instance_class    = "db.m6i.xlarge"
  allocated_storage = 200
  # username/password omitted: secrets do not belong in this file

  lifecycle {
    prevent_destroy = true               # a plan that would delete the database fails loudly
  }
}

Plan, apply and state

Three things must agree: the desired state in your code, the recorded state (the tool's state file, its memory of which real resources it created and their attributes) and the real world in the cloud provider. The workflow has two verbs:

  • terraform plan refreshes what the tool knows about the real world, compares it with the code, and prints a plan: what will be created (+), changed in place (~), or destroyed and recreated (-/+). Nothing changes.
  • terraform apply executes a plan, calls the provider APIs, and updates the state.

Three operational points deserve emphasis:

  • Read the plan like a diff. A one-line code change can plan to destroy and recreate a database (a field that cannot be changed in place). Review the plan, not only the code, and protect critical resources with guards such as prevent_destroy (above) and separate state per environment so a mistake in staging cannot touch production.
  • The state file is critical infrastructure. If it is lost, the tool no longer knows what it owns; if two people apply at once without locking, it is corrupted. Store it remotely, with locking, versioning and restricted access. It can also contain sensitive values, so treat it as a secret.
  • Drift is the default. Drift is any difference between what the code says and what exists, usually created by a manual fix during an incident ("I just changed the security group in the console"). Detect it by running plan on a schedule (or a refresh-only plan) and alerting on a non-empty diff, then decide whether to import the manual change into code or revert it. Teams that tolerate drift eventually cannot tell whether running apply is safe, so they stop running it, and the code becomes fiction.

Common misconception

"If it's in Terraform, it's safe to change." Declarative does not mean harmless. The tool will faithfully delete what the plan says to delete. Apply with the same discipline as a deploy: reviewed plan, small blast radius (per-environment and per-service state), staged order (a test environment, then one region, then the rest), and a tested way back.

GitOps

GitOps applies the "config is code" idea to operations: Git is the single source of truth for the desired state of the system, and an automated agent makes the running system match it. A change is a commit; review is a pull request; the audit log is git log; rollback is git revert. The distinctive feature is the direction of the arrow. In a traditional "push" pipeline a CI system holds credentials to production and pushes changes in. In a GitOps "pull" model, an agent inside the cluster (Argo CD and Flux are the common ones) watches the repository and reconciles the cluster toward it, continuously. This is a controller loop, exactly as in the next chapter, whose input is a Git repository.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: checkout-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/deploy-config.git
    targetRevision: main
    path: apps/checkout/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: checkout
  syncPolicy:
    automated:
      prune: true        # delete cluster objects that were removed from Git
      selfHeal: true     # undo manual edits made directly in the cluster (drift)
    syncOptions:
      - CreateNamespace=true

The advantages are real: no production credentials in CI, an audit trail for free, and selfHeal that reverts manual edits, which turns drift from a silent problem into a self-correcting one. The trade-offs are also real. A bad commit is applied faithfully and quickly, so GitOps does not replace staged rollout (see Argo CD's and Flux's progressive-delivery companions); one repository for everything makes one very large blast radius; and automatic reverting of manual edits can fight an engineer who is trying to mitigate an incident at 3 a.m. Many teams keep a documented, audited break-glass path and pause automatic sync during an incident.

Immutable infrastructure and golden images

In mutable infrastructure you log in to a server and patch it, so every server slowly becomes a unique snowflake, and nobody knows exactly what is on it. Immutable infrastructure forbids that: a running server is never modified. To change anything, build a new image and replace the instances. The image is a golden image (a machine image or container image) produced by a pipeline from versioned inputs, tested, and identified by an immutable tag or content digest.

The benefits line up with this course's themes. Every instance of a version is identical, so "works on one, fails on another" shrinks. Rollback is "run the previous image", which is why chapter 12's rolling and blue-green strategies assume it. Configuration drift on servers disappears because there is nothing to drift. Security patching becomes "rebuild the image and roll it out" with the same canary pipeline as everything else. The cost: image builds must be fast and reproducible, state must live outside the instance (in databases and object storage), and debugging by logging in becomes a deliberate exception. Pin base images by digest rather than a floating latest tag, or two builds of "the same" image will differ.

Secrets are not configuration

One short warning. Passwords, API keys and private keys look like configuration, but they need different handling: never commit them to Git (rotating a leaked key is painful and the history remembers), keep them in a dedicated secrets manager with access control and audit logs, inject them at runtime, and plan for rotation without downtime. Your IaC code should refer to secrets by name, not contain them. The mechanics of secret management are a security topic beyond this course; the operational point is that a secret leaked through a config repository is an incident.

Try it yourself

Save config_rollout.py and run it with Python 3.9+; the output is deterministic. Then:

  • Add a new schema rule that rejects max_connections above the database's limit and watch which case changes.
  • Change WAVES to [40] and rerun Case B. Which sentence of the output summarises the difference between waves and a global push?
  • Lower the threshold in healthy() so that Case D (the good change) fails in wave 1. Why is a too-tight health check also a failure mode (a false alarm that trains people to ignore the halt)?
  • If you have Terraform or OpenTofu installed, run terraform plan on a tiny config with only a local_file resource, edit the file by hand, and run plan again to see drift detected.

Distributed systems connection

Distributed configuration is a replicated-state problem: every node must eventually converge on the same configuration, and during convergence different nodes run different configurations, which is version skew from chapter 12 in another guise. A flag service that pushes updates is a pub-sub system; its clients need the staleness bounds and fail-static behaviour you studied for caches and leases in coordination services. GitOps and IaC are desired-state reconciliation, the pattern the next chapter builds Kubernetes from.

Key takeaways

  • Configuration, content and rules are deployments. Many of the most damaging outages were config changes that reached everything at once (see the CrowdStrike and Cloudflare cases).
  • Treat config as code: version control, review, a typed schema, semantic validation and tests, then a staged rollout watched against a baseline.
  • Validation catches invalid values; waves catch valid-but-harmful ones. You need both, and the second limits the blast radius of everything the first misses.
  • Dynamic config and feature flags are fast and global: give them waves, audit logs, owners and expiry dates, and design clients to fail static on the last known good value.
  • Infrastructure as code is declarative desired state: read the plan, protect critical resources, keep state remote and locked, and detect drift continuously.
  • GitOps makes Git the source of truth with an in-cluster reconciler; it gives audit and self-healing but still needs staged rollout and a break-glass path.
  • Prefer immutable infrastructure and golden images: replace instead of patch, and keep secrets out of config entirely.

Check your understanding

A configuration schema accepts cache_ttl_s: 1 as a valid integer in range, but it multiplies database load by 30 when deployed. Which control is most likely to catch it before it hurts everyone?

  1. A stricter type for the field
  2. A second reviewer reading the diff
  3. A staged rollout with a health check on database load in the first wave
  4. A longer description in the schema
The value is valid by every static rule, and a reviewer might not realise its effect. A canary wave exposes the real consequence on a small slice and halts. Reviewers and schemas help with other bugs, but only runtime observation catches valid-but-harmful values.

What does terraform plan do?

  1. Computes and prints the changes needed to make the real world match the code, without changing anything
  2. Creates the resources and records them in the state
  3. Deletes resources that are not in the code, immediately
  4. Validates the syntax of the files only
Plan is a read-only diff between the desired state and the refreshed real state. Apply is the verb that changes things, and a good workflow applies exactly the plan that was reviewed.

During an incident an engineer widens a security group in the cloud console. Weeks later an unrelated Terraform apply reverts it and re-breaks something. What went wrong organisationally?

  1. Terraform should never be used for security groups
  2. The engineer should have used a different console
  3. State files should be deleted regularly
  4. Drift went undetected and undecided: the manual change was never either committed to code or reverted deliberately
Out-of-band changes are sometimes necessary in an incident. The failure is leaving them unreconciled. Scheduled drift detection and a rule that every manual change is imported or reverted afterwards keep code and reality in agreement.

A feature-flag client calls the central flag service synchronously on every request. What is the main risk, and the standard fix?

  1. Flags will be stale; fix by polling more often
  2. The flag service becomes a hard dependency on the critical path; cache the last known good config locally and refresh asynchronously with a compiled-in default (fail static)
  3. Flags will leak to users; fix by encrypting them
  4. Nothing, since flag services are always available
A synchronous lookup puts the flag service in series with every request, multiplying its unavailability into yours (chapter 1). Fail-static clients keep serving using their last known good configuration when the service is down.

Why does immutable infrastructure make rollback simpler?

  1. Because instances are never restarted
  2. Because servers keep a history of every patch applied
  3. Because every version is a known, identical image, so rolling back means running the previous image rather than undoing a series of in-place changes
  4. Because it removes the need for a database
Instances are replaced, not modified, so there is no accumulated unknown state on a host. State lives outside the instance, which also means rollback of data still requires compatible schemas (chapter 12).

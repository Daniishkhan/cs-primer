Load Testing & Capacity Planning

You cannot know how much a system can carry by reading its code, and you cannot know how much it will need to carry by guessing. This chapter covers the two disciplines that answer those questions: load testing, done in a way that does not flatter the system, and capacity planning, which turns measurements and forecasts into a number of machines and a date by which you must have them. The most important lesson is a measurement trap, coordinated omission, which makes a certain kind of load tool lie about latency, and which you will reproduce in a few lines of Python.

Why this matters

The usual capacity failures are not mysterious. Traffic doubles for a launch and nobody tested at double. A test says "p99 is 80 ms at 5,000 requests per second", and the real system, at 5,000, has a p99 of two seconds, because the test tool was waiting politely for slow responses instead of sending the next ones. A region fails, its traffic moves to the neighbour, and the neighbour was already at 70%. Each of those is a failure of method, not of engineering skill. Knowing how to generate honest load, find the bottleneck and plan headroom is what turns the queueing theory of chapter 8 into decisions about money and risk.

What kind of test are you running?

"Load test" is used loosely. It helps to name the question each variety answers, because they have different shapes, different durations and different pass criteria.

TestShapeThe question it answersYou are looking for
Load testRamp to the expected peak and hold itDoes the system meet its SLOs at the traffic we expect?Latency percentiles and error rate within target; resource use at peak
Stress testGo beyond the expected peak, in stepsWhat happens when we exceed capacity? How does it fail?Graceful degradation or collapse; whether it recovers when load drops (chapter 11)
Soak (endurance) testModerate, realistic load for hours or daysDoes anything slowly degrade?Memory and file-descriptor leaks, connection leaks, disk fill, fragmentation, slow GC growth
Spike testSudden large jump, then dropCan we absorb a burst (a push notification, a TV mention, a flash sale)?Autoscaling lag, queue growth, cold caches, connection storms
Breakpoint testContinuous ramp until an SLO breaks or something failsWhat is our capacity, and what limits it?The knee, the saturation point and the first bottleneck

These are complementary. A load test is your regression test: if it passes today and fails after a deploy, the deploy cost you capacity. A breakpoint test gives you the number that capacity plans are built from. A soak test finds a class of defect that short tests structurally cannot. A stress test tells you what the on-call engineer will actually see on the worst day, which is more valuable than a pass mark.

Closed loop, open loop and the lie of coordinated omission

In chapter 8 you met the difference between an open system (arrivals independent of the system's state) and a closed one (a fixed set of clients that wait for each response before sending again). A load generator is one or the other, and the choice decides whether the numbers it reports are true.

  • A closed-loop generator runs a fixed number of virtual users, each in a loop: send a request, wait for the reply, record the latency, send the next. Throughput depends on how fast the server answers.
  • An open-loop generator sends requests on a schedule (say, 200 per second, with random or regular gaps) regardless of whether earlier requests have returned. It models independent users arriving at a public service.

Now imagine the server stalls for one second: a long GC pause, a failover, a lock held too long. A real open stream of users keeps arriving, so every request that arrives during the stall is delayed, and thousands of users see slow responses. The closed-loop tool does something different. Its virtual users are stuck waiting for the stalled request, so they stop sending. The tool records one very slow sample (the request that was in flight) and then goes right on recording fast ones. The slow samples that should have existed, the requests that would have been sent during the stall, are never generated and so never measured. Gil Tene named this coordinated omission: the measurement system coordinates with the system under test, by pausing when it pauses, so that it omits exactly the data that matters.

The simulation below makes it concrete. The server takes 10 ms per request and freezes for one second, from t = 10 s to t = 11 s, in a 30-second run. We measure it twice: with one closed-loop virtual user, and with an open-loop generator sending 50 requests per second on a fixed schedule and measuring each request's latency from its scheduled send time, as a real user would experience it. Time is simulated, so the output is exact and repeatable.

"""Coordinated omission: the same server, measured by a closed-loop and an open-loop load generator.

The server handles one request at a time, takes 10 ms per request, and freezes completely
between t = 10 s and t = 11 s (think: a long GC pause or a stalled disk). Time is simulated."""

SERVICE = 0.010                    # 10 ms per request
STALL = (10.0, 11.0)               # server frozen during this window
DURATION = 30.0


def finish_time(start: float) -> float:
    """When does a request that starts being served at `start` finish?"""
    if STALL[0] <= start < STALL[1]:
        start = STALL[1]           # frozen: work only begins when the stall ends
    end = start + SERVICE
    if start < STALL[0] < end:     # stall begins mid-request: pause then resume
        end += STALL[1] - STALL[0]
    return end


def closed_loop():
    """One virtual user: send, wait for the reply, send the next. Latency measured per request."""
    t, lats = 0.0, []
    while t < DURATION:
        done = finish_time(t)
        lats.append(done - t)
        t = done
    return lats


def open_loop(rate=50):
    """Requests are *scheduled* every 1/rate seconds whether or not earlier ones finished.
    Latency is measured from the scheduled send time, as a real user would experience it."""
    gap, server_free, lats, i = 1 / rate, 0.0, [], 0
    while i * gap < DURATION:
        scheduled = i * gap
        done = finish_time(max(scheduled, server_free))
        server_free = done
        lats.append(done - scheduled)
        i += 1
    return lats


def pct(xs, p):
    xs = sorted(xs)
    return xs[min(len(xs) - 1, int(p / 100 * len(xs)))]


def report(name, lats):
    print(f"{name:<28} n={len(lats):5d}  p50={pct(lats, 50)*1000:7.1f} ms  "
          f"p99={pct(lats, 99)*1000:7.1f} ms  p99.9={pct(lats, 99.9)*1000:7.1f} ms  max={max(lats)*1000:7.1f} ms")


if __name__ == "__main__":
    print("Server: 10 ms per request, frozen for 1 s out of 30 s\n")
    report("closed loop (1 user)", closed_loop())
    report("open loop, 50 req/s", open_loop(50))
    # Gil Tene's fix for tools that cannot be open-loop: fill in the requests the stall 'omitted'
    fixed, expected = [], SERVICE
    for lat in closed_loop():
        fixed.append(lat)
        extra = lat - expected
        while extra >= expected:
            fixed.append(extra)
            extra -= expected
    report("closed loop + back-fill", fixed)
Server: 10 ms per request, frozen for 1 s out of 30 s

closed loop (1 user)         n= 2900  p50=   10.0 ms  p99=   10.0 ms  p99.9=   10.0 ms  max= 1010.0 ms
open loop, 50 req/s          n= 1500  p50=   10.0 ms  p99=  870.0 ms  p99.9= 1000.0 ms  max= 1010.0 ms
closed loop + back-fill      n= 2999  p50=   10.0 ms  p99=  720.0 ms  p99.9=  990.0 ms  max= 1010.0 ms

Look at the percentiles. The closed-loop tool reports a p99 of 10 ms and a p99.9 of 10 ms. Its worst sample is the one request caught by the stall. A dashboard built from that tool would say the system is perfect. The open-loop generator, on the very same server, reports a p99 of 870 ms and a p99.9 of 1,000 ms, because about 50 of the 1,500 requests (over 3%) were scheduled inside the freeze and all waited for it to end. The server did not change. Only the measurement did.

The third row shows a repair that exists for tools that cannot be open-loop. HdrHistogram, Gil Tene's histogram library, offers a "record with expected interval" operation: when a response takes much longer than the expected gap between requests, the tool adds synthetic samples for the requests that should have been sent during the delay. The correction is an approximation (this run's p99 of 720 ms is lower than the 870 ms of the true open loop, since the closed loop sends faster than the schedule), but it is much closer to the truth than 10 ms. The cleaner fix is to avoid the problem: send on a schedule and measure from the intended send time.

Symptoms you can recognise

Suspect coordinated omission when a load test shows a surprisingly clean tail, when the maximum latency is much higher than p99.9 with nothing in between, when throughput in the test drops while latency stays flat, or when production percentiles are far worse than anything the test ever produced. In a closed system, latency and throughput are tied together by Little's law (concurrency = throughput × latency): if concurrency is fixed and latency rises, throughput must fall, which is the tool quietly sending less load exactly when the server struggles.

Tools that send at a fixed rate

The cure is a generator that is open-loop by design. Three common ones are shown below. The commands are illustrative, not run for this chapter: check the current documentation for your version.

  • wrk2 is a fork of the wrk HTTP benchmarking tool by Gil Tene that adds a constant request rate (-R) and records latency from the intended send time, so it corrects for coordinated omission.
  • k6 offers arrival-rate executors (constant-arrival-rate, ramping-arrival-rate) alongside its closed-model ones. It reports dropped_iterations when it cannot keep the requested rate.
  • vegeta attacks at a fixed rate (-rate): it sends requests on a schedule whether or not earlier ones have returned.
# wrk2: 2 threads, 100 connections, 60 s, constant 2,000 requests per second
wrk -t2 -c100 -d60s -R2000 --latency http://localhost:8080/api/items

# vegeta: constant 200 requests per second for 60 s, then a text report
echo "GET http://localhost:8080/api/items" | vegeta attack -rate=200 -duration=60s | vegeta report
import http from 'k6/http';

export const options = {
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',  // open model: fixed arrivals per second
      rate: 200,
      timeUnit: '1s',
      duration: '2m',
      preAllocatedVUs: 50,                // VUs available to serve the arrivals
      maxVUs: 500,
    },
  },
  thresholds: {
    http_req_duration: ['p(99)<300'],       // fail the run if p99 is 300 ms or worse
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  http.get('http://localhost:8080/api/items');
}

An arrival-rate test makes the generator's own limits visible. If the generator runs out of connections or CPU before the system under test does, it will fall behind its schedule, and you are measuring your laptop. Watch the generator's CPU, check that the achieved rate matches the requested one, and run it on a separate machine from the target.

Also test a realistic mix. A single URL with a single payload is a benchmark of one code path with a warm cache. Real traffic has a spread of request types, payload sizes, hot and cold keys, new and returning users, and often a long tail of expensive queries. Replaying a sample of production traffic (with sensitive data removed) is usually the most realistic input you can get, and the shape of the key distribution matters: uniform keys will make caches look worse than production and a handful of hot keys will make them look better.

Where to test: production-like, shadowed, or in production

Performance depends on everything: hardware, data size, cache contents, network, configuration, the other services that share the dependencies. A test in an environment that differs from production tells you about the environment. Capacity does not scale linearly (queues, contention and caches are non-linear: see the USL in chapter 8), so a half-size staging environment does not promise half the production capacity, and the further it differs the more you should treat its numbers as relative (before and after a change) instead of absolute.

Approaches, from safest to most informative:

  1. A scaled-down copy of production. Safe and cheap, good for catching regressions and finding the first bottleneck. Beware of data volume: a database with a thousandth of the rows has a different working set, different index depth and different cache hit rate.
  2. A full-size production-like environment, built from the same infrastructure code (chapter 13) and loaded with representative data, run for peaks. Expensive, so many teams create it temporarily for big events.
  3. Shadow traffic. A proxy copies a fraction of live requests to a new version or a new cluster and discards its responses, so real users never see them. This gives you production's request mix and timing against the new system. The cost: the copied requests add real load on shared dependencies, writes must be stubbed or isolated so they do not change real data or send real emails, and privacy rules still apply.
  4. Testing in production. Synthetic load, or a controlled ramp of a canary, on the real system. It is the only way to learn the real shared-dependency behaviour, and the riskiest. Do it with a kill switch, a slow ramp, an abort condition tied to SLO burn (chapter 2), the people who can fix it watching, and at a time when failure is cheapest. Canaries and feature flags (architecture chapter 18) are the same idea applied to releases, and fault injection (distributed chapter 19) is the sibling for failures.

Finding the saturation point and the bottleneck

A breakpoint test ramps load and watches two curves. Throughput rises with offered load until some resource saturates; then it flattens, and in a service that handles overload badly it may even fall. Latency stays near its unloaded value, then bends upward at the knee, and then runs away. Two numbers come out of this. The saturation point is where throughput stops growing. The knee, earlier and lower, is where latency starts to climb. The capacity you quote for planning is the load at the point where your SLO still holds, which is at or before the knee, never the peak throughput you saw at the saturation point.

Next, which resource saturated? Brendan Gregg's USE method gives a checklist: for every resource, check Utilisation (how busy), Saturation (how much extra work is waiting) and Errors. The point is to inspect every resource instead of staring at the favourite one.

ResourceUtilisationSaturationErrors
CPU% busy per coreRun-queue length, CPU throttlingMachine-check events (rare)
Memory% used, working setSwapping, page faults, OOM-kill risk, GC timeAllocation failures, OOM kills
Disk% time busy, throughput vs. device limitI/O queue depth, wait timeI/O errors
NetworkBandwidth vs. link speedDropped packets, retransmits, queue dropsInterface errors, resets
Thread, connection and lock poolsBusy workers / pool sizeRequests waiting for a worker or connection, lock wait timePool exhaustion errors, timeouts

A key trick: for software resources such as thread pools and connection pools, Little's law gives you the ceiling directly. A pool of 20 connections held for 20 ms each can serve at most 20 / 0.020 = 1,000 queries per second, whatever the CPU says. If the test flattens at 1,000 per second while CPU idles at 30%, you have found your bottleneck by arithmetic.

Expect the bottleneck to move. Remove the first limit (add connections, optimise the hot query) and a new resource saturates at a higher load. Capacity work is iterative: each fix buys a bounded increase, and the plan must say which resource limits you next. Also make sure to look at dependencies: your service may sit at 40% CPU while the database it calls is the thing that saturated.

Capacity planning

Capacity planning is the continuous process of making sure that supply (what the system can serve) stays ahead of demand (what it will be asked to serve), with a safety margin, and that new supply arrives before it is needed. It has four steps.

1. Know your unit cost

Translate demand into resources. From a load test or production telemetry, measure how much of each resource one unit of work consumes: CPU-milliseconds per request, bytes of memory per session, I/O operations per write. Then capacity at the knee for an instance is simple to state: "one 8-core instance serves about 700 requests per second at the target utilisation".

2. Forecast demand, in two parts

Demand has two sources that behave differently and should be planned separately.

  • Organic growth is the steady trend of more users doing more things. Fit it from history (weekly and daily cycles, seasonal peaks), and plan for the peak, not the average: a service with a 3:1 ratio of peak to average hour that is provisioned for the average will fall over every day. Growth compounds: 8% a month doubles demand in about nine months (ln 2 / ln 1.08 ≈ 9.0).
  • Inorganic demand comes from launches, marketing campaigns, new customers, a feature rollout, a migration, or a seasonal event such as a holiday sale. It is lumpy and not predicted by the trend, so you need a channel from product and business teams, and a load test sized to the launch estimate. It also tends to be wrong in one direction: estimates for launches are usually optimistic about success and pessimistic about cost, so plan for a range and a degradation plan for the high end (chapter 11).

3. Add headroom, deliberately

Required supply = forecast peak ÷ target utilisation, plus redundancy. Chapter 8 derived the pieces: a utilisation target below the knee for the latency you promise, and N+1 (or N+2) so that losing an instance, a rack or a zone does not push the survivors past the knee. The same arithmetic applies to regions.

Worked example. A service has a global peak of 90,000 requests per second across 3 regions. You must keep your SLO after losing any one region, and after a loss the survivors may run at up to 80% of their capacity. Two regions must then carry everything: 2 × C × 0.8 ≥ 90,000, so C ≥ 56,250 requests per second of full capacity in each region (168,750 in total). In normal operation, with traffic spread evenly, each region runs at 30,000 / 56,250 ≈ 53%. You are paying for 1.9 times the capacity that the peak traffic alone would need, and that factor is the price of the failover promise. With 5 regions the same promise needs only 4 × C × 0.8 ≥ 90,000, so C ≥ 28,125 per region and 140,625 in total: 1.56 times. More, smaller failure domains make failover cheaper, which is one argument for cells (chapter 15).

Failover capacity is only real if it is real: traffic must be able to shift (routing, DNS or load-balancer weights, data present in the destination), and the destination must be able to absorb the surge, including cold caches and connection storms, which a failover drill (chapter 19) will reveal. See distributed chapter 18 for the data side. A "capacity" figure that would be exceeded by the first real failover is a hope.

4. Mind the lead times

Supply does not appear on demand. The question to ask is not "how much will we need?" but "how far ahead must we decide?" The answer is your lead time, and it varies by orders of magnitude.

Kind of capacityTypical lead time (order of magnitude)
More containers or instances in an existing cluster, if quota existsMinutes (plus warm-up: caches, JIT, connection pools)
Raising a cloud quota or limit, getting scarce instance typesHours to days, sometimes weeks
Committed or reserved capacity, a new database cluster, reshardingDays to weeks
Owned hardware, network links, a new data centre or regionMonths to quarters
Software change to remove a bottleneckWeeks to months, with its own risk

These are orders of magnitude only; your environment will differ. The planning rule is that the forecast horizon must exceed the longest lead time for the resource that limits you. Autoscaling (chapter 14) shortens the lead time of the fast kind of capacity to minutes, but it does not help with quotas, with a downstream database that does not autoscale, or with a spike that arrives faster than instances can boot, which is why known events are usually pre-scaled ahead of time. A useful dashboard number is time to exhaustion: current headroom divided by the growth rate. If it is shorter than your lead time, you are already late.

Try it yourself

Save omission.py from the listing and run python3 omission.py. Then change STALL to (10.0, 10.2), a 200 ms hiccup, and predict the numbers before you run it. We got a closed-loop p99 of 10 ms still (one slow sample out of about 3,000), but an open-loop p99 of 70 ms and a p99.9 of 200 ms. Next, with that same 200 ms stall, raise the open-loop rate to 100 requests per second, which is the server's maximum. Our run reported a median of 210 ms: the backlog created by the stall never drains, because at ρ = 1 there is no spare capacity to catch up with. That is what "no headroom" means in practice. If you have wrk2, k6 or vegeta installed, point one at python3 -m http.server 8080 to compare tools, but treat the result as a lesson about the tool, since that server is simple and unrepresentative of anything real.

Distributed systems connection

In a distributed system the bottleneck is often not the service under test but one of its dependencies: a database, a cache, a shared queue, a service owned by another team. A load test therefore has a blast radius, so tell the owners of what you will load, and test dependencies' limits explicitly. Capacity is also a property of the whole call graph: the fan-out of chapter 9 multiplies the downstream load per user request, and retries multiply it again (chapter 11).

Key takeaways

  • Choose the test for the question: load (meet the SLO at peak), stress (how does it fail), soak (slow leaks), spike (bursts) and breakpoint (find capacity and the bottleneck).
  • A closed-loop generator waits for responses, so it slows down exactly when the server stalls and omits the slow samples: coordinated omission. It can report a 10 ms p99 for a system that has a 900 ms one.
  • Use fixed-rate (open-loop) tools such as wrk2, k6 arrival-rate executors or vegeta, measure latency from the intended send time, and check that the generator keeps up.
  • A test environment only tells you about itself. Prefer production-like data and traffic mix; use shadow traffic carefully (side effects, privacy, extra load); test in production only with a kill switch, a slow ramp and an SLO-based abort.
  • Quote capacity at the point where the SLO holds, not at peak throughput. Find the bottleneck with USE and Little's law, and expect it to move.
  • Capacity = forecast peak ÷ target utilisation, plus redundancy: N+1 or N+2, and failover for a zone or region (for 3 regions with 80% allowed after a loss, that is about 1.9 times the peak load).
  • Plan organic growth (trend, compounding) and inorganic launches separately, and make the forecast horizon longer than the lead time of whatever limits you.

Check your understanding

A closed-loop load tool with 50 virtual users reports a p99 of 40 ms. Production users complain about multi-second stalls. What is the most likely explanation?

  1. The tool's clock is wrong
  2. Production has more users, so the tail is naturally longer
  3. Coordinated omission: when the server stalls, the virtual users wait and stop sending, so the slow samples are never recorded
  4. Closed-loop tools always show lower latency because they use fewer connections
A closed loop slows its offered load in step with the server, so it records only the few requests caught in the stall. An open-loop generator on a fixed schedule would have recorded every request scheduled during the stall as late. More users could also hurt, but the pattern of clean test numbers against ugly production ones points to the measurement method.

Which test is designed to reveal a slow memory leak or file-descriptor leak?

  1. A soak (endurance) test: moderate load for hours or days
  2. A spike test
  3. A short load test at peak
  4. A breakpoint test
Leaks accumulate over time. A test that lasts ten minutes at any intensity would not see a defect that takes eight hours to matter. Soak tests run at realistic, often moderate load for long enough to see trends in memory, handles, disk and GC time.

A service's throughput flattens at 1,000 requests per second during a breakpoint test, while CPU is at 30%. It calls a database through a pool of 20 connections, each held for about 20 ms per query. What is the most likely bottleneck?

  1. The network, since CPU is low
  2. The load generator is too fast
  3. Memory, since CPU is low
  4. The connection pool: 20 connections / 0.020 s = 1,000 queries per second at most
Little's law gives the pool's ceiling: concurrency divided by hold time. It exactly matches the plateau, with idle CPU, which is the classic signature of a software resource that has saturated. Confirm with the pool's wait-time and queue-depth metrics (the "saturation" in USE).

You have 3 regions and a global peak of 90,000 requests per second. Surviving the loss of any one region, with the survivors allowed up to 80% utilisation, how much full capacity must each region have?

  1. 30,000 requests per second
  2. 56,250 requests per second
  3. 112,500 requests per second
  4. 90,000 requests per second
After a loss two regions carry all 90,000 at no more than 80%, so 2 × C × 0.8 ≥ 90,000 and C ≥ 56,250. 30,000 is the normal per-region load without any headroom; 90,000 would let any single region carry everything at 100%, which ignores the 80% limit; 112,500 is 90,000 / 0.8, which is what a single survivor would need.

Why should capacity plans separate organic growth from launches?

  1. Launches are always smaller than organic growth
  2. Organic growth cannot be forecast at all
  3. Organic growth is a trend you can extrapolate from history, while launches are lumpy and need information from product teams and a load test sized to the estimate
  4. They are measured in different units, so the sum is meaningless
The two have different data sources and different failure modes. A trend can be fitted; a launch is a one-off that a trend will not predict, and the estimate is often uncertain enough to deserve a range and a degradation plan.

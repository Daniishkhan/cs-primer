Logs & Structured Events

Metrics tell you that something is wrong; logs are where you find out what happened to one particular request. This chapter follows the log from a printf that a human reads to a wide, structured event that a machine can slice by any field, and covers the practical machinery around it: levels, request IDs, sampling, retention tiers, privacy, and the pipeline that carries the data. The goal is the capability Charity Majors and colleagues call observability: asking questions you did not think of in advance.

Why this matters

Chapter 4 ended with a deliberate limitation: metrics are pre-aggregated, so they cannot answer "what happened to the checkout of user u-42 at 14:03?" or "which customers are seeing the slow path?". Those questions are asked in every serious incident. Whether you can answer them in two minutes or two hours depends almost entirely on how your software wrote its logs months earlier. Logging decisions are cheap to make well at design time and very expensive to fix during an outage, and logging at scale is also one of the largest line items on a monitoring bill.

From text lines to structured events

The oldest logging style is a line of free text written for a person to read:

2026-10-13 14:03:22,481 ERROR PaymentService - Charge failed for user 4417 order 99120 amount=900 (declined: limit)

It is pleasant to read and unpleasant to query. To count failures per reason you must write a regular expression that matches this exact phrasing, and the day a developer rewords the message the dashboard silently breaks. Every question needs its own parser, and different services use different formats.

A structured log writes the same facts as named fields, usually one JSON object per line (JSON Lines):

{"ts":"2026-10-13T14:03:22.481Z","level":"ERROR","msg":"charge failed","service":"payments","user_id":"u-4417","order_id":"o-99120","amount":900,"reason":"limit","request_id":"req-b2"}

Now "count failures by reason" is a group-by over a field. Adding a new field does not break existing queries. The rule of thumb: the message is a constant string; the variable parts are fields. Constant messages can be counted, grouped and deduplicated; interpolated ones cannot. Note that fields like user_id and order_id would be forbidden as metric labels (chapter 4's cardinality explosion) but are exactly right here: logs are stored as individual events, so high cardinality is what they are for.

Architecture chapter 8 introduced logging as a cross-cutting concern and named the two obvious disciplines (do not log secrets, make output machine-readable). Here we go further: what to put in each event, how events from many services are tied together, and how to afford keeping them.

Log levels, and how they are misused

A log level is a severity tag, typically DEBUG, INFO, WARN, ERROR (some libraries add TRACE and FATAL). The intended meaning:

LevelIntended useTypical misuse
DEBUGDetail useful when diagnosing; off in production by defaultLeft on in production "just in case"; a hot loop logs a line per item and doubles the bill
INFONormal, notable events: started, config loaded, job finishedUsed for per-request chatter; drowns everything else
WARNSomething unexpected that the program handled, and that might matter if it keeps happeningThe dumping ground for "not sure"; so noisy that nobody reads it
ERRORAn operation failed and a human may need to actLogged for every expected condition: user not found, validation failed, a retry that later succeeded

The most damaging misuse is ERROR for things that are not errors in the sense that matters. If a user typing a wrong password logs an ERROR, then the ERROR count measures how many people mistype passwords, and nobody can use it to find real faults. The same applies in the other direction: a failed payment logged only at INFO is invisible. A useful test: "if this line appeared 1,000 times a minute, would I want to be woken up?" If yes, it is an ERROR candidate; if it is routine, it is not. Two further habits help. Log a failure once, where it is handled, with its context, rather than at every layer it passes through (otherwise one failure produces six lines, and counts are inflated). And do not alert on raw log-line counts as your main signal: alert on symptoms measured by metrics (chapter 7), and use logs to investigate.

Correlation IDs: tying lines to requests

On a busy server, thousands of requests interleave their log lines. A line saying "charge failed" is useless unless you can find the other lines from the same request. The fix is a request ID (or correlation ID): a unique identifier generated at the edge (or accepted from the caller), attached to every log line the request produces, and passed along on every outgoing call (for HTTP, a header such as X-Request-ID, or the trace context header from chapter 6). Search for the ID and you get the whole story across every service, in order. This is the poor person's distributed trace, and it is often enough to find a bug.

The implementation problem is how to get the ID into lines written deep inside the code without passing it through every function signature. Languages offer ambient context: thread-locals, Go's context.Context, and in Python the contextvars module, which also works correctly with async code (each task sees its own value). A logger reads the context on every call and merges it into the event. The next program is a runnable sketch that also redacts an email address and drops DEBUG lines:

import contextvars, json, itertools, re

_ctx: contextvars.ContextVar[dict] = contextvars.ContextVar("log_ctx", default={})
_clock = itertools.count(1000)          # simulated time, ms
LEVELS = {"DEBUG": 10, "INFO": 20, "WARN": 30, "ERROR": 40}
MIN_LEVEL = "INFO"
SINK: list[str] = []
SECRET = re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.]+\b")

def bind(**fields):
    """Add fields to the current context; returns a token to undo it."""
    return _ctx.set({**_ctx.get(), **fields})

def log(level: str, msg: str, **fields):
    if LEVELS[level] < LEVELS[MIN_LEVEL]:
        return
    rec = {"ts": next(_clock), "level": level, "msg": msg, **_ctx.get(), **fields}
    for k, v in rec.items():                       # crude redaction
        if isinstance(v, str):
            rec[k] = SECRET.sub("[email]", v)
    SINK.append(json.dumps(rec, sort_keys=False))

def handle(request_id: str, user: str, amount: int):
    token = bind(request_id=request_id, user_id=user)
    try:
        log("INFO", "request start", route="/checkout")
        charge(amount)
        log("DEBUG", "this line is dropped at INFO")
    finally:
        _ctx.reset(token)

def charge(amount: int):
    bind(payment_provider="acme-pay")              # added deep in the stack
    if amount > 500:
        log("ERROR", "charge declined for ann@example.com", amount=amount, code="limit")
    else:
        log("INFO", "charge ok", amount=amount)

handle("req-a1", "u-17", 120)
handle("req-b2", "u-42", 900)
for line in SINK:
    print(line)

# Wide event: ONE record per request, built up as the request runs.
print("\n--- canonical line ---")
event = {}
def wide(request_id, user, amount):
    ev = {"request_id": request_id, "user_id": user, "route": "/checkout", "amount": amount}
    ev["db_calls"] = 3; ev["cache_hit"] = False
    ev["status"] = 402 if amount > 500 else 200
    ev["duration_ms"] = 31 if amount <= 500 else 87
    print(json.dumps(ev))
wide("req-a1", "u-17", 120); wide("req-b2", "u-42", 900)
{"ts": 1000, "level": "INFO", "msg": "request start", "request_id": "req-a1", "user_id": "u-17", "route": "/checkout"}
{"ts": 1001, "level": "INFO", "msg": "charge ok", "request_id": "req-a1", "user_id": "u-17", "payment_provider": "acme-pay", "amount": 120}
{"ts": 1002, "level": "INFO", "msg": "request start", "request_id": "req-b2", "user_id": "u-42", "route": "/checkout"}
{"ts": 1003, "level": "ERROR", "msg": "charge declined for [email]", "request_id": "req-b2", "user_id": "u-42", "payment_provider": "acme-pay", "amount": 900, "code": "limit"}

--- canonical line ---
{"request_id": "req-a1", "user_id": "u-17", "route": "/checkout", "amount": 120, "db_calls": 3, "cache_hit": false, "status": 200, "duration_ms": 31}
{"request_id": "req-b2", "user_id": "u-42", "route": "/checkout", "amount": 900, "db_calls": 3, "cache_hit": false, "status": 402, "duration_ms": 87}

Look at three things in the output. First, request_id and user_id were bound once in handle() and appeared in every line, including the one written inside charge(), without being passed as arguments. Second, payment_provider was added deep in the call stack and still appears, then vanishes when the request's context is reset, so it cannot leak into the next request. Third, the second block shows a different style, a wide event, which is the next idea.

Wide events and canonical log lines

Traditional logging emits many small lines per request ("request start", "cache miss", "charge ok", "request end"). To answer a question you stitch the lines back together. A wide event inverts this: the code collects everything interesting about a request into one structured record with dozens or hundreds of fields, and emits it once, at the end. Engineers at Stripe have written about a version of this under the name "canonical log lines", one line per request carrying the key facts, kept in addition to the normal logs so that it can be queried with ordinary tools. The idea is the same under any name.

A good wide event for a web request contains, among others:

  • Identity of the request: request ID, trace ID, route template, HTTP method, status, duration.
  • Who and what: user or tenant ID, account plan, feature flags that were on, client version, region, host, build/commit.
  • What it cost and did: number of database queries and their total time, cache hit or miss, bytes in and out, retries performed, which dependency was slow.
  • Outcome: error type and message if any, and whether it was handled or user-visible.

Because every field is on the same record, you can slice by any combination without joins: "show p99 duration for plan=enterprise and client_version=4.2 and db_calls > 20". That is the heart of what Majors, Fong-Jones and Miranda (Observability Engineering, 2022) mean by observability: you can ask new questions of a running system, ones you did not predict when you wrote the code, without shipping new code to answer them. A dashboard of pre-computed metrics answers only the questions someone anticipated; rich events with high-cardinality fields let you discover the unknown unknowns ("it only fails for tenant 8812 on the Android client in region eu-west when the feature flag is on"). Note that this is a claim about a capability, not a product category, and it is partly a sales pitch as well as a real idea: you can get most of the benefit with careful structured logging and a store that can query it.

Analogy: the patient chart

Vital-sign monitors (metrics) tell the ward a patient is deteriorating. The chart (a wide event) holds the history, medications, allergies and the last test results on one page, so a doctor can ask "which patients on this drug with these symptoms got worse?" The scrawled sticky notes (unstructured lines) technically contain the same facts but not in a form anyone can query.

Where it breaks down: a hospital chart is written once with care by a professional; software must produce thousands of charts a second automatically, and the cost of writing and keeping them is the next topic.

Three signals: projections of the same events

It helps to see logs, metrics and traces not as three separate systems but as three projections of the same underlying stream of events. Everything that happens in a service is an event with a timestamp and attributes.

The three also feed each other. A metric alert tells you when; you open the wide events for that window and group by fields to see who and what; you open one trace to see where. Chapter 6 shows the glue, exemplars, that jump from a point on a metric chart directly to a trace.

Volume, sampling and cost

A service handling 5,000 requests per second that writes a 1 KB wide event per request produces 5 MB/s, about 430 GB a day, from one service. Multiply by hundreds of services plus the chatty lines. Log storage and indexing are routinely among the biggest observability costs, and the bill grows linearly with traffic, while the value of the 500,000th identical "GET /health 200" is nil. So you decide what to keep.

  • Drop the noise at the source. Health checks, successful static-asset requests, and DEBUG lines in production usually earn no place.
  • Head sampling. Decide at the start of a request whether to record it, e.g. keep 1 in 100 at random (or deterministically by hashing the request ID, so every service in the call makes the same decision). Simple and cheap, but it is made before you know whether the request will be interesting, so it throws away 99% of the errors too.
  • Tail sampling (or "decide after the fact"). Buffer the request's events, and at the end decide: keep all errors and slow requests, keep a small share of the fast successes. It keeps what you will want to look at, at the price of holding events in memory until the request finishes. Chapter 6 revisits this for traces.
  • Dynamic sampling. Vary the rate by what the event is: 100% for errors, 1-in-1000 for the most common success path, 1-in-10 for a rare route; keep the rate on the event (sample_rate=100) so that counts can be reconstructed by weighting each kept event by its rate. Without recording the rate, sampled logs silently lie about volumes.

Common misconception: "sample the logs and the metrics will be wrong too"

Metrics are computed from unsampled counters in the process, so sampling the stored events does not change request counts or error rates. The reverse mistake is real: computing a rate by counting sampled log lines without weighting. Keep the pre-aggregated metrics unsampled, and sample the expensive per-event detail.

Retention tiers

Most queries are about the last few hours. Few are about last month, and almost none about last year, except for audits. Retention is therefore tiered by access pattern and cost:

TierTypical ageStorageUse
Hothours to daysIndexed on fast disks or memoryLive debugging, incident response; sub-second queries
Warmdays to weeksCheaper indexed storageRecent post-incident investigation
Cold / archivemonths to yearsCompressed files in object storage, queried by scanningAudits, compliance, rare deep investigations; slow and cheap

Exact durations are a policy decision driven by cost, compliance and how long it takes your organisation to notice problems; there is no standard. One practical lesson: some incidents are only understood weeks later (a slow data corruption, a security investigation), so the answer to "keep nothing but a week" is rarely a good one for the events that matter. Keep a long-lived but small sample or a long-lived aggregate, and the full-fidelity data for a short window.

PII in logs, and redaction

PII (personally identifiable information) is anything that identifies a person: names, emails, phone numbers, addresses, IP addresses in many jurisdictions, government IDs, and obviously passwords, tokens and card numbers. Logs are a classic leak path. A developer logs the whole request body for debugging, and now every customer's password and card number sits, indexed and searchable by hundreds of engineers, with a retention policy longer than the database's. Logs are also replicated and archived, so deleting one user's data on request is hard.

  • Do not log secrets or full bodies. Prefer an allow-list of fields to log over a deny-list of fields to hide: new fields then default to private.
  • Redact at the source (as logs.py does with a crude regular expression), not only in the pipeline; once the raw value leaves the process you depend on every downstream stage.
  • Use stable pseudonyms (user_id, not email) so that events remain joinable without exposing identity. Hash with a secret salt if you must log an identifier you do not want in the clear.
  • Treat access as a control: restrict who can query sensitive indices, and audit it.

Regular expressions catch obvious patterns only. The reliable defence is design: fields are named, typed and reviewed, which is another argument for structure over free text.

The log pipeline

Logs flow through a pipeline for the same reason requests flow through queues in systems chapter 14: stages run at different speeds and fail independently. The application writes to stdout or a local file (cheap, local, nearly unfailing); an agent on each host reads, tags (host, pod, region) and forwards; a durable buffer (a message queue such as Kafka) absorbs bursts such as the flood of error lines during an incident, which is exactly when volume spikes; a processing stage parses, redacts, samples and routes to tiers; and the store indexes. Two design rules follow from the queueing chapters. The application must never block on logging, so when the pipeline backs up the right behaviour is to drop (ideally the least valuable lines first) rather than to stall requests. And you must monitor the pipeline itself: a logging system that has silently stopped is indistinguishable from a quiet service, and you discover it in the incident.

Distributed systems connection

Per-host logs have no single global order: clocks drift (networking chapter 17), so timestamps from two machines cannot be compared exactly, and a request ID is the only reliable way to group causally related events. Chapter 6 formalises this with trace and span IDs and parent-child links, which is closer to the logical clocks you met in the distributed course than to wall-clock time. The buffer-and-replay structure of the pipeline is also the log abstraction you saw in data chapter 19.

Try it yourself

You need Python 3 and, for the shell items, jq (macOS: brew install jq; Linux: your package manager). Nothing here needs sudo.

  1. Run logs.py > events.jsonl (remove the wide-event part first, or keep it in a second file). Then jq -c 'select(.level=="ERROR")' events.jsonl and jq -s 'group_by(.request_id) | map({id: .[0].request_id, lines: length})' events.jsonl.
  2. Change MIN_LEVEL to "DEBUG" and measure how many more lines you get. Multiply by your imagined traffic.
  3. Add an @sampled(rate) wrapper that keeps an event with probability 1/rate unless the level is ERROR, and records sample_rate in the event. Check that summing sample_rate over kept INFO lines estimates the true count.
  4. Extend the redaction to mask 13-to-16-digit sequences. Then write a log line that defeats your regular expression, and explain why allow-listing fields is better.

Key takeaways

  • Structured logs (named fields, constant message) are queryable; free-text lines need a parser per question.
  • Levels are a contract: ERROR means someone may need to act. Do not log expected conditions as errors, and log each failure once where it is handled.
  • Attach a request ID to every line and propagate it on every call; use ambient context (contextvars, thread-locals) so deep code gets it for free.
  • Wide events (one rich record per request, as in canonical log lines) enable asking new questions by slicing on any field, the core of observability in the Majors et al. sense.
  • Logs, metrics and traces are projections of the same events: aggregate, store, or link. Pick by the question.
  • Control cost with source filtering, head, tail and dynamic sampling (recording the sample rate), and tiered retention.
  • Treat logs as a privacy risk: allow-list fields, redact at the source, use pseudonymous IDs. The pipeline (agent, buffer, process, store) should never block the application and must itself be monitored.

Check your understanding

Why is log("charge failed for user 4417") worse than log("charge failed", user_id="u-4417")?

  1. The second is shorter on disk
  2. The first bakes a variable into the message, so identical events have different messages and cannot be grouped or counted without a regular expression
  3. The first cannot contain digits
  4. The second is automatically redacted
A constant message plus named fields lets a query group by message and filter by user. Interpolating the ID makes every line unique text. Size, redaction and digits are not the issue.

A service logs ERROR whenever a user's login attempt has a wrong password. What is the most serious consequence?

  1. Logs get slightly larger
  2. Passwords are leaked
  3. Login attempts slow down
  4. The ERROR count no longer indicates real faults, so it cannot support alerts or investigation, and genuine failures hide in the noise
The size is minor and nothing here says the password is logged. The damage is semantic: a level only helps if it means something consistent. Use INFO or a metric for expected user mistakes, and keep ERROR for failures a person may need to act on.

With head sampling at 1 in 100, which problem should you expect?

  1. About 99% of rare error requests are discarded before anyone knows they were errors
  2. Request counts on dashboards become 100 times too small, because metrics are also sampled
  3. Request IDs stop being unique
  4. The decision cannot be consistent across services
Head sampling decides before the outcome is known, so it discards errors at the same rate as everything else. Metrics are computed from unsampled counters and are unaffected. Hashing the request ID makes the decision consistent across services. Tail or dynamic sampling keeps the interesting requests.

You keep a sampled log with a different sampling rate per event type. What must you store on each kept event to estimate true volumes?

  1. The hostname
  2. A checksum
  3. The sample rate, so each kept event can be weighted by that rate when counting
  4. Nothing; the counts are correct as they are
An event kept at 1 in 1000 stands for 1,000 real events. Without the rate recorded, counts over a mixture of rates are biased toward the types you sampled less aggressively.

What is the main reason to put a durable buffer between log agents and the log store?

  1. To make logs sort correctly by timestamp
  2. To absorb bursts (such as the flood during an incident) and decouple a slow or failing store from the producers
  3. To encrypt the logs
  4. To remove the need for retention policies
Volume spikes exactly when things go wrong, and the store may be the component that is struggling. A buffer lets stages run at different speeds without back-pressure reaching your application. It does nothing for ordering, encryption or retention.

CrowdStrike, July 2024

On 19 July 2024 a Rapid Response Content update to CrowdStrike’s Falcon sensor caused Windows hosts that received it to crash. The cause was a mismatch between the 21 inputs a Template Type defined and the 20 the sensor supplied, which the Content Validator did not catch, shipped as content with no staged rollout.

The pattern in one sentence

A content update that code interprets is a deployment: validate it against reality, test the exact thing you ship, and stage it so that the first mistake is small.

The cast

This page states only what CrowdStrike’s own reports say; general explanations are labelled as general. The relevant background is chapter 12 (staged rollouts and canaries) and chapter 13 (configuration is a deployment too). The vocabulary below is the RCA’s.

Sensor Content
Content that ships with each sensor release, including on-sensor models and the code for Template Types. It is not updated dynamically from the cloud.
Template Type
A sensor capability with predefined input fields, expressed in code and compiled into the sensor at build time.
Template Instance
Matching criteria (regular expressions) written by detection engineers for one Template Type.
Rapid Response Content
Several Template Instances bundled together and delivered by a Channel File, so detections can change without a sensor code change.
Content Interpreter
Part of the sensor’s C++ code that tests input strings against the regular expressions.
Content Validator
Checks channel files against their definition in the Template Type Definitions file.

Content is not code, until it is

CrowdStrike delivers security content to its sensors in two ways. Sensor Content is part of a sensor release, with the testing and certification that implies. Rapid Response Content is described as “configuration data; it is not code or a kernel driver” (RCA, technical details). It exists so that detections can respond to new threats at operational speed without a sensor release.

The lesson of the incident sits in the arrow from the Channel File to the interpreter. Data that is interpreted by code takes part in that code’s behaviour: a malformed or unexpected value can steer the interpreter down a path nobody exercised. This is general reasoning, not a claim from the report, but it is why chapter 13 treats a configuration push as a deployment that deserves the same safeguards as a binary.

What happened

Sensor 7.11, released in February 2024, introduced a new Template Type for detecting attacks that abuse named pipes and other Windows interprocess communication, called the IPC Template Type. Instances of it are delivered through Channel File 291. The Preliminary Post Incident Review says a stress test passed in staging and the first instance was released on 5 March, and three more instances followed between 8 and 24 April, all performing as expected.

At 04:09 UTC on 19 July 2024 two more IPC Template Instances were released as part of a new version of Channel File 291. The defect was reverted at 05:27 UTC, 78 minutes later. Windows hosts running sensor 7.11 and above that were online in that window and received the update crashed; the report says Mac and Linux hosts were not affected. The RCA adds that by 29 July about 99% of Windows sensors were back online week over week, against a usual variance of about 1%.

The mechanism: 21 against 20

The RCA states it plainly: the new IPC Template Type defined 21 input parameter fields, but the integration code that invoked the Content Interpreter supplied only 20 input values. That count mismatch evaded the sensor release testing, the Template Type stress test and the first several field deployments. In part this was because testing and the early instances used a wildcard matching criterion for the 21st input, so nothing ever actually read it.

The July instances changed that. One introduced a non-wildcard criterion for the 21st field, so the interpreter now had to inspect a value that did not exist. At the next IPC notification from the operating system it read past the end of the 20-element array, which the RCA calls an out-of-bounds read, and the system crashed. The RCA notes this was not an arbitrary memory write and was independently reviewed.

The Content Validator

A check existed for exactly this kind of content, and it let the instance through. The RCA says the Content Validator evaluated the new instances, but based its assessment on the expectation that the IPC Template Type would be provided with 21 inputs, which it describes as a logic error. Validator and definition agreed with each other; both disagreed with what the sensor actually supplied.

The report also records why earlier testing missed it: the automated testing used a static set of 12 test cases, and the channel file used in them had a regex wildcard in the 21st field for every instance. The Template Type was stress tested with a test instance, and the RCA says the Content Validator-tested instance that was later released did not reveal that the mismatched input count would crash the Content Interpreter.

Common misconception: "a content update cannot crash a machine"

It can when the content drives code in a privileged component. The RCA explains that the sensor’s driver is loaded early in boot, and that Rapid Response Content is read by sensor code to make detection decisions. The failure here was not exotic content, but a latent bug in the reader, waiting for the first input that used it. The report is also clear that the fix was layered: compile-time checks, runtime bounds checks, more tests and a better validator.

No staging for this content

The RCA lists as a finding that each Template Instance should be deployed in a staged rollout, and its mitigation says the Content Configuration System was updated with additional deployment layers and acceptance checks. The Preliminary Post Incident Review describes the same commitment as a staggered deployment starting with a canary. The consequence of the window in the first diagram is that every host online in those 78 minutes was exposed together, before any signal could stop it. This follows chapter 12’s central point: a rollout’s first stage exists to be wrong cheaply.

Contributing factors

  • The Template Type definition (21 fields) and the integration code (20 inputs) disagreed, and nothing checked the count at sensor compile time.
  • The Content Interpreter lacked a runtime bounds check on its input array for this content.
  • Testing used a static set of 12 cases and wildcard criteria for the 21st field, so the first non-wildcard use was in the field.
  • The Content Validator assumed 21 inputs and passed the instance.
  • The stress test passed for the Template Type, and the later instances were released on the strength of that test, the validator and earlier successful deployments (Preliminary Post Incident Review).
  • The RCA lists staged deployment of each Template Instance as a finding, so the bad version reached every online host in the window together.

What they changed

  • Sensor Content Compiler: a check that validates the number of inputs a Template Type provides, developed on 19 July and in production on 27 July, which also verified no other Template Type had a wrong count.
  • Content Interpreter: runtime bounds checking added on 25 July, plus a check that the input array size matches what the content expects, backported to sensors 7.11 and above through a hotfix due by 9 August.
  • The IPC Template Type was corrected to provide 21 inputs.
  • Testing: automated tests with non-wildcard criteria for every field of every existing Template Type, required for future ones, and each new Template Instance tested regardless of how the first one fared.
  • Content Validator: new checks that instances do not match over more fields than are provided, due by 19 August, and meanwhile only wildcards allowed in the 21st field.
  • Deployment: staged rings with canary, bake-in time and rollback.
  • Customer control over where and when Rapid Response Content updates are deployed, with release notes customers can subscribe to.
  • Two independent third-party security vendors engaged to review the sensor code, plus a review of the end-to-end quality process.

The pattern to remember

Analogy: the checklist revision sent to every cockpit at once

An airline updates a pre-flight checklist and sends it to every aircraft in the fleet in one batch. The checklist is only paper, but the crews follow it literally. One line refers to a gauge that older cockpits do not have, and the people who proofread the checklist were looking at the new cockpit’s layout. Sending it first to a single aircraft on the ground would have found the problem for the cost of a delay.

Where it breaks down: a crew can stop and ask; a kernel-level reader of content just executes.

Key takeaways

  • Content that code interprets is part of the system’s behaviour. Release it with the care you give code.
  • Two components can each be self-consistent and still disagree about an interface (21 against 20). Check counts and shapes at build time and bounds at run time.
  • A validator validates against a model. If the model is wrong, passing validation proves little.
  • A passed test of one instance does not cover later instances; test what you ship.
  • Stage every change that can reach many machines, and give customers a say in the timing.

Check your understanding

What is the difference between Sensor Content and Rapid Response Content in the RCA?

  1. Sensor Content is cloud-delivered configuration; Rapid Response Content ships with each release
  2. Sensor Content ships with a sensor release and includes Template Types; Rapid Response Content is configuration data delivered through Channel Files
  3. They are two names for the same thing
  4. Rapid Response Content is a kernel driver
The RCA describes Rapid Response Content as configuration data delivered by Channel Files, and Template Types as code in the sensor release.

What was the mismatch at the centre of the incident?

  1. Two Channel Files with the same number
  2. The Template Type defined 21 input fields but the integration code supplied 20 inputs
  3. The sensor expected 20 Channel Files
  4. Windows and Mac sensors used different content
The 21st input was never supplied, so a non-wildcard criterion on it read past the end of the array.

Why did earlier deployments of IPC Template Instances not crash?

  1. They were smaller
  2. They used a wildcard matching criterion for the 21st input, so it was never inspected
  3. They ran only on Linux
  4. The interpreter had a bounds check then
Until 19 July no instance used the 21st input with a non-wildcard criterion.

What does the RCA say about the Content Validator?

  1. It was disabled
  2. It contained a logic error: it assessed the new instances expecting 21 inputs
  3. It was never used
  4. It only checked file size
The validator evaluated the instances against the definition, which said 21 inputs, so it passed content the sensor could not safely run.

Which change addresses the blast radius rather than the bug itself?

  1. A bounds check in the Content Interpreter
  2. A compile-time check of the input count
  3. Staged deployment through rings with canary and customer control over timing
  4. A corrected Template Type
The first two prevent this defect; staging limits the damage from any future defect in content.

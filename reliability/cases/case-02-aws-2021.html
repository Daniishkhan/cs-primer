AWS us-east-1, December 2021

On 7 December 2021 an automated scaling activity inside AWS caused a surge of connection attempts that congested the devices linking AWS’s internal network to its main network. Clients kept retrying, the monitoring the operators relied on went dark, and many control-plane services in the Northern Virginia region were impaired for hours, while running customer workloads mostly kept running.

The pattern in one sentence

A shared internal network that hosts your monitoring and control plane is a hidden dependency: when it congests, you lose both the ability to see the problem and the ability to change the system.

The cast

This page states only what AWS’s post says; explanations of general mechanisms are labelled as general. Background: chapter 15 (control plane, data plane and static stability, hidden dependencies) and chapter 16 (incident response). For the retry mechanics see the earlier retry storms case.

Internal network
The post describes AWS using a separate network to host foundational services including monitoring, internal DNS, authorization services and parts of the EC2 control plane.
Networking devices
Devices connecting the internal network to the main AWS network, which route traffic and translate network addresses between them.
Control plane
The APIs and systems that create, change and configure resources (launch an instance, update a DNS record).
Data plane
The systems that carry out the work customers rely on once resources exist (a running instance, answering a DNS query).
Back-off
Waiting progressively longer between retries. The post says a latent issue prevented a large number of clients from backing off properly.

What happened

All times in the post are Pacific. At 7:30 am on 7 December 2021 an automated activity to scale the capacity of one of the AWS services hosted in the main AWS network triggered unexpected behaviour from a large number of clients inside the internal network. The post says its networking clients have well-tested back-off behaviour, but a latent issue kept them from backing off adequately; that code path had been in production for many years, and the scaling activity triggered a previously unobserved behaviour.

A surge of connection activity overwhelmed the networking devices that link the two networks. Latency and errors led to more connection attempts and retries, so the congestion became persistent: the load was now sustained by the clients’ own behaviour, not just by the original trigger. This is the shape you met in chapter 11 as a metastable failure: a feedback loop that keeps the system degraded after the trigger is gone. (The post does not use that word; the label is mine.)

Monitoring went blind

The congestion immediately affected the real-time monitoring that internal operations teams use. The post says operators relied on logs, found elevated internal DNS errors, and moved internal DNS traffic off the congested paths; that completed at 9:28 am and DNS errors fully recovered. But monitoring data remained invisible to the operations team, which the post says delayed understanding of the event, and internal deployment systems were also affected, slowing recovery further. Customers saw delays in CloudWatch metrics, and a small amount of monitoring data was not captured.

Control plane and data plane

The post separates what kept working from what did not (the data-plane and control-plane labels are my gloss, though the post does say “control planes”). On the data-plane side: running EC2 instances were unaffected; S3 and DynamoDB were not impacted, though access through VPC endpoints was impaired; Lambda invocations operated normally; and existing Route 53 DNS records and queries were not affected. On the control-plane side: EC2 APIs had elevated errors from 7:33 am, Route 53 APIs were impaired from 7:30 am to 2:30 pm, the console had login failures until 2:22 pm, ELB provisioning and registration were delayed, and support case creation was affected from 7:33 am to 2:25 pm. New EC2 instance launches recovered at 2:40 pm.

The split is a worked example of static stability from chapter 15: what already runs keeps running, but anything that needs to change, scale or be created depends on the control plane. Some services mixed the two: the post notes that API Gateway needed many servers replaced, with recovery starting at 1:35 pm and largely complete by 4:37 pm, and that EventBridge event delivery was disabled at 12:35 pm and re-enabled at 2:35 pm.

Common misconception: "customer workloads were fine, so there was no outage"

The post says existing workloads were not directly impacted, but customers could not log in to the console, launch instances, or create support cases, and some services such as STS and API Gateway had impairments of their own. A data plane that stays up is a real design win, yet the control plane is how you scale out or recover during a crisis, so losing it is itself an incident. The post’s own account of the customer dashboard supports this: it says the Service Health Dashboard was updated by 8:22 am through a global banner that some customers found hard to see.

Contributing factors

  • An automated scaling activity triggered an unexpected burst of client activity from a large number of clients inside the internal network.
  • A latent defect in how clients back off (in a code path that had been in production for many years), so retries did not slow down adequately under errors.
  • Many clients sharing a limited set of devices as the only join between two networks.
  • Monitoring, DNS and deployment tooling for operators depended on the very network that was congested, so seeing and fixing it were both harder (general term: a hidden or circular dependency).
  • Customer-facing status and support tooling also depended on the affected systems; the post says support case creation was impaired.

What they changed

  • AWS disabled the triggering scaling activities and said it would not resume them until all remediations were deployed.
  • It was developing a fix for the client back-off issue, with deployment expected over the following two weeks.
  • It deployed additional network configuration to protect the networking devices during similar congestion.
  • For API Gateway, it described mitigations to keep servers healthy when the internal network is unavailable, and faster recycling of servers.
  • It planned a new Service Health Dashboard architecture and a new support system architecture running across multiple regions.

The pattern to remember

Analogy: the hospital whose switchboard is also its alarm system

A hospital runs patient care on its main wards but links them to administration through one corridor. One morning a crowd floods the corridor, each person queueing again whenever they are turned back. The nurses on the wards keep treating patients, but the monitors, the pager network and the supply orders all use that corridor too, so the charge nurse cannot see what is going on, nor send help.

Where it breaks down: a corridor jam clears when people stop; software clients that retry without back-off can hold the congestion in place by themselves.

Key takeaways

  • A scaling activity on the internal network led to a surge of connections that overwhelmed the devices linking it to the main network; clients that did not back off kept it congested.
  • Monitoring, internal DNS and parts of the EC2 control plane lived on that internal network, which delayed understanding and recovery.
  • The data plane mostly kept working (running EC2, S3, DynamoDB, Lambda, existing Route 53 records) while many control-plane APIs were impaired.
  • Operators need tooling that does not share fate with the system being operated.
  • Retries must back off, or the clients themselves become the sustaining cause.

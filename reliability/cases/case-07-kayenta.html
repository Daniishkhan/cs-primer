Netflix Kayenta: Canaries by Statistics

In 2018 Google and Netflix open-sourced Kayenta, a service that decides whether a canary release is safe by comparing its metrics against a freshly launched baseline, testing each metric statistically and rolling the verdicts into one score.

The pattern in one sentence

Compare the new version to a like-for-like baseline launched at the same time, judge each metric statistically, and let a score fixed in advance decide whether the release goes on.

The cast

This page is a design case rather than an incident. It rests on the April 2018 announcement of Kayenta by Google and Netflix and on the Spinnaker documentation of the default judge. It extends chapter 12 (canaries and automatic halting), and uses the metrics vocabulary from chapter 4. The idea of a canary appears in evolving safely in the architecture course.

Canary
A small set of instances running the new version, given a small share of real traffic.
Baseline
A fresh set of instances of the same size running the current production version, created alongside the canary.
Canary judge
The component that compares canary and baseline metrics and produces a score.
Mann-Whitney U test
A rank-based statistical test of whether two samples seem to come from different distributions. It does not assume a bell-curve shape (general definition).
Marginal
A middle outcome between pass and fail, which can trigger a human decision.

The problem with eyeballing a canary

A person looking at graphs while a canary runs has to decide whether a latency line that looks a little higher is signal or noise, across dozens of metrics, with a release waiting. Kayenta, the announcement says, comes from an effort to make that judgement automatic: it pulls the metrics you specify, runs statistical tests and returns an aggregate score. It is integrated with Spinnaker as a canary stage in a deployment pipeline.

Baseline against canary, launched together

The obvious comparison is the canary against production, but the announcement and the Spinnaker best-practices page recommend against it. Production has been running for a while: its caches are warm, its heaps have settled and it serves its full traffic mix. A fresh canary will look worse on some metrics for reasons unrelated to the change. So Kayenta launches a new baseline with the current version, the same deployment time and size and the same kind of traffic, and compares that to the canary. The Spinnaker page says this leaves version and configuration as the only variables. The announcement says the canary must behave as well or better than the baseline for the deployment to continue.

Metrics and their groups

You tell Kayenta which metrics to check and where they live: the announcement lists Stackdriver, Prometheus, Datadog and Netflix’s Atlas. For each metric it builds a pair of time series, one for the baseline (the control) and one for the canary (the experiment). The best-practices page suggests covering several aspects of health, naming latency, errors and saturation from the four golden signals of the SRE book, and putting metrics into groups.

Groups matter because of how scoring works. The page warns that if a group has many metrics and one fails while the rest pass, the group still scores well, so a failing metric can be diluted. To make one metric decisive, put it in a group alone or mark it critical, which fails the canary outright.

The judge: a test per metric

The default judge (the NetflixACAJudge, in the Spinnaker documentation) works metric by metric. It first handles missing data (a metric with no data on one side is labelled no-data, and if half or more of the metrics have no data the score is zero). It may optionally remove outliers. Then it compares the two samples with a Mann-Whitney U test at a fixed 98% confidence interval. Small differences are ignored using a tolerance band of ±0.25 times the size of the Hodges-Lehmann estimate (a robust measure of the typical shift between the samples; general definition). A metric is labelled High or Low only when the interval lies completely outside that band, the effect size exceeds a configured allowance, and the metric’s configured direction permits that label. Otherwise it is Pass.

The direction setting is practical. A canary that has lower latency than the baseline should not fail, whereas lower request volume might deserve a flag, and the judge lets each metric say which direction counts as bad.

Scoring

A group’s score is the share of its metrics that pass (no-data metrics are excluded, and a group that is entirely no-data scores 100). The summary score is a weighted average of the group scores. A critical metric labelled High or Low beyond its critical effect size sets the whole score to zero. Two thresholds then convert the score into an outcome: at or above the pass threshold is a pass, at or above the marginal threshold is marginal, anything lower fails. Comparisons are inclusive. The documentation suggests starting with 75 for marginal and 95 for pass; I did not find defaults in the judge page, so treat these as suggestions. In the announcement, success promotes the canary, marginal can send a human to approve, and failure triggers a rollback.

Common misconception: "a passing score means the release is safe"

It means no metric you chose differed by more than the judge could detect in the time you ran. A bug that only shows in a metric you did not select, under traffic the canary did not see, or after the canary window closes, passes. Statistical judgement replaces a tired human with a consistent one; it does not replace choosing metrics well, or running the canary long enough for the effect to appear.

Contributing factors to a trustworthy canary

  • A baseline created at the same time and size as the canary removes the age and warm-up differences that production would introduce.
  • A rank-based test and a tolerance band avoid reacting to ordinary noise and avoid assuming a particular distribution of the metric.
  • Direction and criticality settings let you say which changes matter and which are harmless.
  • Group weights and thresholds are choices; poor ones (a critical metric buried in a big group, thresholds never reviewed) quietly weaken the check.

What it changes in practice

  • The go or no-go decision is made against numbers fixed in advance, rather than by whoever is watching graphs.
  • It lives in the pipeline as a stage, so every release gets the same check.
  • It supports three outcomes: promote, ask a human, roll back.
  • It connects to several metrics sources, so teams can keep the monitoring they already have.

The pattern to remember

Analogy: a taste test with a fresh batch of the old recipe

A restaurant wants to try a new sauce. Comparing it with the pot that has been simmering since morning would taste different regardless of the recipe, so the cook makes a fresh batch of the old sauce at the same time and serves both to a few diners. Judges score flavour, heat and saltiness separately, ignore tiny differences, and only call off the new sauce if it is clearly worse on something that matters.

Where it breaks down: real traffic changes minute by minute, so the judge compares time series, not a single bite.

Key takeaways

  • Compare a canary with a fresh baseline launched at the same time, not with long-running production.
  • Judge each metric separately with a robust test (Mann-Whitney U) and a tolerance, then combine into a weighted score.
  • Thresholds turn the score into promote, ask a human or roll back.
  • Group design and critical flags decide whether a real regression can hide in the average.
  • Automation makes the judgement consistent; it is only as good as the metrics and the window you choose.

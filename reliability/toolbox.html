Toolbox

Reliability is learned by watching systems under load and in trouble. These tools let you measure a service, trace a request, push on it at a fixed rate, break it in a controlled way, and write down what happened. Each card has install notes and a ten-minute exercise tied to a chapter, and the exercises share one tiny service so you only write it once.

How to use this page

Jump to a tool when a chapter mentions it. Commands target macOS or Linux (Windows under WSL). I checked command forms against the tools' public documentation (kind, k6, Prometheus, Jaeger, vegeta, wrk2, Toxiproxy and Chaos Mesh) and I ran the Python exporter's code paths in-process, but I did not start servers, containers or clusters while writing this page. Every output block is therefore labelled illustrative: the shape is right, the numbers on your machine will differ. Versions move, so if a flag has changed, trust --help over this page.

The shared target. The first card includes app.py, a standard-library Python service with a /checkout route that sleeps for a random time and sometimes returns a 500, and a /metrics route in the Prometheus text format. The load, Grafana, chaos and stress cards use it as the thing under test. Save it once in a folder such as ~/ops-lab/.

Only on your own machines

Load generators, CPU and memory stress, network delay and fault injection are all legitimate tools and all can look like an attack or cause an outage. Run them only against processes and machines you own, on 127.0.0.1 or on your own VM. Never point them at a production system, a shared environment, a third-party service or a network you do not control without written permission and a way to stop. Every exercise below is local and ends with a cleanup step.

See what the system is doing

Measurement before action: collect metrics, draw them, and follow a request across processes.

Prometheus & PromQL

Needs: Python 3.8+ for the exporter; Prometheus 2.x or 3.x · macOS: brew install prometheus · Linux: download the tarball for your platform from prometheus.io/download and unpack it (it contains prometheus and promtool) · Chapters: 4, 7, 2

Prometheus scrapes (pulls) a text page of metrics from each target at an interval, stores the samples in a time-series database, and answers queries in PromQL. It is the common starting point for the metrics of chapter 4 and the burn-rate rules of chapter 7. The exercise has three parts: a target, a scrape and the three queries you will use all the time (rate, a ratio of rates, and histogram_quantile).

10-minute guided exercise

1. The target. Save this as app.py. It is the whole exporter: a counter, a histogram with explicit buckets and a lock around the shared state. (I ran its counting and rendering code in-process; I did not start the server, so the output below is illustrative.)

#!/usr/bin/env python3
"""A tiny service that exports Prometheus metrics, using only the standard library."""
import contextlib, os, random, threading, time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

BUCKETS = [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5]
lock = threading.Lock()
requests = {}                          # (route, code) -> count
bucket_counts = [0] * len(BUCKETS)     # per-bucket (non-cumulative) counts
total_count, total_sum = 0, 0.0
MEAN_MS = float(os.environ.get("SERVICE_MS", "20"))
ERROR_RATE = float(os.environ.get("ERROR_RATE", "0.02"))
# SERIAL=1 lets one request work at a time, so capacity is about 1000 / SERVICE_MS per second.
WORK_LOCK = threading.Lock() if os.environ.get("SERIAL") else contextlib.nullcontext()

def work():
    """Simulate one request. Returns the HTTP status code."""
    with WORK_LOCK:
        start = time.perf_counter()
        time.sleep(random.lognormvariate(0, 0.5) * MEAN_MS / 1000 / 1.13)  # mean is about MEAN_MS
        code = 500 if random.random() < ERROR_RATE else 200
        elapsed = time.perf_counter() - start
    observe("/checkout", str(code), elapsed)
    return code

def observe(route, code, seconds):
    global total_count, total_sum
    with lock:
        requests[(route, code)] = requests.get((route, code), 0) + 1
        total_count += 1
        total_sum += seconds
        for i, bound in enumerate(BUCKETS):
            if seconds <= bound:
                bucket_counts[i] += 1
                break

def render():
    lines = ["# HELP app_requests_total Requests handled.",
             "# TYPE app_requests_total counter"]
    with lock:
        for (route, code), n in sorted(requests.items()):
            lines.append(f'app_requests_total{{route="{route}",code="{code}"}} {n}')
        lines += ["# HELP app_request_duration_seconds Request latency.",
                  "# TYPE app_request_duration_seconds histogram"]
        running = 0
        for bound, n in zip(BUCKETS, bucket_counts):
            running += n
            lines.append(f'app_request_duration_seconds_bucket{{le="{bound}"}} {running}')
        lines.append(f'app_request_duration_seconds_bucket{{le="+Inf"}} {total_count}')
        lines.append(f"app_request_duration_seconds_sum {total_sum}")
        lines.append(f"app_request_duration_seconds_count {total_count}")
    return "\n".join(lines) + "\n"

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/metrics":
            body = render().encode()
            self.send_response(200)
            self.send_header("Content-Type", "text/plain; version=0.0.4")
        else:
            code = work()
            body = b"ok\n"
            self.send_response(code)
            self.send_header("Content-Type", "text/plain")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
    def log_message(self, *args):      # keep the terminal quiet
        pass

if __name__ == "__main__":
    port = int(os.environ.get("PORT", "8000"))
    print(f"serving on :{port}; metrics at /metrics")
    ThreadingHTTPServer(("127.0.0.1", port), Handler).serve_forever()

2. Run it and look at the raw metrics, the same text Prometheus will read:

$ python3 app.py  # terminal 1; leave running
serving on :8000; metrics at /metrics
$ for i in $(seq 1 20); do curl -s -o /dev/null localhost:8000/checkout; done
$ curl -s localhost:8000/metrics | head -12
illustrative:  app_requests_total{route="/checkout",code="200"} 19
illustrative:  app_request_duration_seconds_bucket{le="0.025"} 14
illustrative:  app_request_duration_seconds_bucket{le="+Inf"} 20

Notice that histogram buckets are cumulative (each le counts everything at or below it) and that the last one, +Inf, equals the count. That is what lets histograms from many pods be summed (chapter 4).

3. Configure and start Prometheus. In the same folder create prometheus.yml and rules.yml:

global:
  scrape_interval: 5s
  evaluation_interval: 5s
rule_files:
  - rules.yml
scrape_configs:
  - job_name: app
    static_configs:
      - targets: ["localhost:8000"]
groups:
  - name: app
    rules:
      - record: app:error_ratio:rate1m
        expr: sum(rate(app_requests_total{code="500"}[1m])) / sum(rate(app_requests_total[1m]))
      - alert: AppFastBurn
        expr: app:error_ratio:rate1m > (14.4 * 0.005)
        for: 1m
        labels: {severity: page}
        annotations: {summary: "burning the error budget at over 14.4x"}
$ promtool check config prometheus.yml  # validates the file and the rule file it references
illustrative:  SUCCESS: prometheus.yml is valid prometheus config file syntax
$ prometheus --config.file=prometheus.yml  # terminal 2; UI at http://localhost:9090
$ while true; do curl -s -o /dev/null localhost:8000/checkout; sleep 0.05; done &  # terminal 3: about 15 requests a second

4. Query it. Open http://localhost:9090, go to the expression browser and run these one at a time (wait a minute for a few scrapes):

up                                              # 1 = the scrape works; the first thing to check
rate(app_requests_total[1m])                     # per-second rate for each route and code
sum by (code) (rate(app_requests_total[1m]))     # about 14.7 for 200, about 0.3 for 500
sum(rate(app_requests_total{code="500"}[1m])) / sum(rate(app_requests_total[1m]))   # about 0.02
histogram_quantile(0.99, sum by (le) (rate(app_request_duration_seconds_bucket[1m])))   # about 0.05
sum(rate(app_request_duration_seconds_bucket{le="0.1"}[5m])) / sum(rate(app_request_duration_seconds_count[5m]))   # latency SLI: share under 100 ms

Now make the alert fire. Stop the app and restart it with a high error rate; after a minute the alert appears on the /alerts page:

$ ERROR_RATE=0.15 python3 app.py  # after Ctrl-C in terminal 1; a 15% error ratio is 30x the 0.5% budget
illustrative:  /alerts shows AppFastBurn pending, then firing after the 1m 'for' period

Finally, clean up: kill %1 in terminal 3 and Ctrl-C in terminals 1 and 2.

Only on your own machines

Prometheus and the exporter listen on localhost here. If you later run Prometheus on a server, do not expose port 9090 or the /metrics pages to the internet; both reveal internal structure and the UI can run arbitrary queries.

What to look for

  • Sum inside, quantile outside. histogram_quantile(0.99, sum by (le) (rate(..._bucket[1m]))) adds bucket counts across series first. Computing a quantile per series and then averaging is the mistake of chapter 4.
  • The p99 you read is an estimate that is interpolated inside a bucket. Move a bucket bound or add one (edit BUCKETS) and see the number shift; buckets set the accuracy.
  • Counters only go up; the useful number is always rate() of it. A restart resets a counter and rate() handles that.
  • up == 0 for a target, or a scrape taking nearly the whole interval, are signals about the monitoring itself.

Common pitfalls

  • Range selectors need at least two scrapes inside: [1m] with a 5 s interval is fine; [5s] is not.
  • Alert state is evaluated at evaluation_interval; for: adds delay on top.
  • Do not add a label with unbounded values (a user id) to the exporter to "see more": it multiplies series (studio 1).
  • Port 8000 or 9090 busy? Change PORT or --web.listen-address.

Grafana

Needs: Docker Desktop (or Docker Engine), the Prometheus and app.py from the previous card still running · Run: docker run -d --name grafana -p 3000:3000 grafana/grafana-oss · Chapters: 4, 2

Grafana draws data from sources such as Prometheus. The tool is easy; the skill is deciding what a dashboard is for. The rule from studio 1: a dashboard answers one question, and the title is that question, with the answer visible in the first row.

10-minute guided exercise

Build a dashboard called "Is the checkout service healthy?" with four panels, driven by the exporter and Prometheus from the previous card.

$ docker run -d --name grafana -p 3000:3000 grafana/grafana-oss
$ open http://localhost:3000  # Linux: xdg-open; log in as admin / admin and set a new password
  1. Add the data source. Connections, then Data sources, then Add data source, then Prometheus. For the URL use http://host.docker.internal:9090 (Docker Desktop on macOS and Windows resolves this name to your machine). On Linux Docker Engine, start the container with --add-host=host.docker.internal:host-gateway to get the same name. Click Save & test.
  2. Panel 1, the headline: the latency SLI. Query sum(rate(app_request_duration_seconds_bucket{le="0.1"}[5m])) / sum(rate(app_request_duration_seconds_count[5m])). Use a Stat panel, unit "Percent (0.0-1.0)", and set thresholds: red below 0.99, green above. That is an SLO of 99% under 100 ms, made visible.
  3. Panel 2, the error ratio against the budget: the ratio query from the previous card, as a time series, with a threshold line at 0.005 (the 99.5% budget) and a second at 0.072 (the 14.4× page level of studio 1).
  4. Panel 3, latency percentiles: three queries with histogram_quantile at 0.5, 0.95 and 0.99, as one time series panel, unit seconds. Give each a legend such as p99.
  5. Panel 4, traffic: sum(rate(app_requests_total[1m])), so that a drop (the quiet failure) is visible.
  6. Give every panel a one-line description of what a bad reading means (Panel settings, Description). Save the dashboard, then restart the app with ERROR_RATE=0.15 and SERVICE_MS=120 and watch panels 1 to 3 change within a minute.

Clean up with docker rm -f grafana. (The dashboard lives inside the container unless you mount a volume; use Share, then Export, to save the JSON if you want to keep it.)

Only on your own machines

The default admin/admin login is for your laptop only. If you ever run Grafana on a server, change the password at once and put it behind authentication; Grafana can query every data source you give it.

What to look for

  • Order panels by the question's flow: is it bad (SLI), how bad (error ratio), where (percentiles), how much (traffic).
  • Thresholds drawn on the panel turn a graph into a judgement: reading a number against a target is what the SLO is for.
  • Variables (region, version) at the top of a dashboard are what turns one dashboard into many, as in studio 1.

Common pitfalls

  • The data source URL is resolved from inside the container: localhost:9090 there is the container itself, not your machine.
  • A panel that says "No data" usually has a rate window shorter than two scrapes, a wrong label value (le="0.1" must match the exporter's text exactly) or a time range with no samples.
  • More panels are not better. If you cannot say what decision a panel supports, delete it.

OpenTelemetry & Jaeger

Needs: Docker; Python 3.9+ and pip install opentelemetry-sdk opentelemetry-exporter-otlp-proto-http (use a virtual environment) · Jaeger all-in-one: the container below · Chapters: 6, 5

OpenTelemetry (OTel) is the vendor-neutral set of APIs, SDKs and the OTLP wire protocol for traces, metrics and logs. Jaeger stores and displays traces; its quick-start image takes OTLP directly on ports 4317 (gRPC) and 4318 (HTTP). The exercise instruments two tiny "services" and shows chapter 6's central point: context propagation joins the spans, and one dropped header splits the tree.

10-minute guided exercise

1. Start Jaeger with the command from its getting-started page (the version tag moves; use the tag the page shows today):

$ docker run --rm --name jaeger -p 16686:16686 -p 4317:4317 -p 4318:4318 cr.jaegertracing.io/jaegertracing/jaeger:2.22.0  # UI at http://localhost:16686

2. Two services in one script. A gateway on port 8001 calls an orders service on port 8002; each has its own tracer with its own service.name, so Jaeger shows two services. The gateway injects the W3C traceparent header into the outgoing call, and orders extracts it. (Illustrative: I have not run this against the SDK; the API names follow the OpenTelemetry Python documentation.)

import os, threading, time, urllib.request
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from opentelemetry import propagate, trace
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

def make_tracer(service):
    provider = TracerProvider(resource=Resource.create({"service.name": service}))
    exporter = OTLPSpanExporter(endpoint="http://localhost:4318/v1/traces")
    provider.add_span_processor(BatchSpanProcessor(exporter, schedule_delay_millis=1000))
    return provider.get_tracer(service)

gateway_tracer, orders_tracer = make_tracer("gateway"), make_tracer("orders")
DROP_HEADER = os.environ.get("DROP_HEADER") == "1"      # simulate a hop that loses context

def reply(handler):
    handler.send_response(200); handler.send_header("Content-Length", "3"); handler.end_headers()
    handler.wfile.write(b"ok\n")

class Orders(BaseHTTPRequestHandler):
    def do_GET(self):
        ctx = propagate.extract(self.headers)           # read traceparent, if present
        with orders_tracer.start_as_current_span("GET /orders", context=ctx, kind=trace.SpanKind.SERVER):
            with orders_tracer.start_as_current_span("db.query"):
                time.sleep(0.05)
            time.sleep(0.01)
        reply(self)
    def log_message(self, *a): pass

class Gateway(BaseHTTPRequestHandler):
    def do_GET(self):
        with gateway_tracer.start_as_current_span("GET /checkout", kind=trace.SpanKind.SERVER):
            with gateway_tracer.start_as_current_span("call orders", kind=trace.SpanKind.CLIENT):
                headers = {}
                if not DROP_HEADER:
                    propagate.inject(headers)           # writes traceparent for the current span
                urllib.request.urlopen(urllib.request.Request("http://localhost:8002/", headers=headers)).read()
        reply(self)
    def log_message(self, *a): pass

threading.Thread(target=ThreadingHTTPServer(("127.0.0.1", 8002), Orders).serve_forever, daemon=True).start()
print("gateway on :8001, orders on :8002")
ThreadingHTTPServer(("127.0.0.1", 8001), Gateway).serve_forever()
$ python3 -m venv .venv && . .venv/bin/activate && pip install opentelemetry-sdk opentelemetry-exporter-otlp-proto-http
$ python3 tracing_demo.py  # terminal 2
$ for i in 1 2 3 4 5; do curl -s localhost:8001/ >/dev/null; done
illustrative:  open http://localhost:16686, choose service 'gateway', Find Traces
illustrative:  one trace, 5 spans, 2 services: GET /checkout > call orders > GET /orders > db.query

3. Break the chain. Stop the script and restart it with DROP_HEADER=1 python3 tracing_demo.py. Send five requests again. Jaeger now shows two traces per request, one containing the gateway spans and another containing the orders spans, with different trace ids: the tree is severed. This is how a single legacy client or an async hop that forgets the context makes tracing look broken. Compare the span timings in the working version: the waterfall shows db.query (50 ms) dominating the critical path.

Clean up with Ctrl-C and docker stop jaeger (the --rm flag removes it; traces are stored in memory and are lost).

Only on your own machines

The Jaeger quick-start has no authentication and keeps traces in memory. Use it on your laptop only; traces can contain request details and identifiers (chapter 5: PII), so never send real customer data to an exposed collector.

What to look for

  • The span tree and the traceparent value are the same thing seen two ways: version-traceid-parentid-flags. The trace id stays the same across hops; the parent id changes at each.
  • Add span.set_attribute("order.id", "o-123") in the orders handler and search for it in Jaeger's tags box. That is the link to the wide event of chapter 5.
  • Sampling is configured in the SDK (the default records everything). Production policy belongs in the collector, as chapter 6 argues.

Common pitfalls

  • Import paths and package names change between releases; check the OpenTelemetry Python docs if an import fails.
  • Spans are exported in batches; wait a second or two before looking. If nothing shows, check that port 4318 is mapped and the endpoint path ends in /v1/traces.
  • Do not call inject outside the client span, or the downstream parent will be the wrong span.

Push on it

Load tools tell you how a service behaves at a rate; the cluster and resource tools show how the platform reacts to change and to scarcity.

k6, wrk2 & vegeta

k6: brew install k6 or the packages on grafana.com/docs/k6 · vegeta: brew install vegeta (or go install github.com/tsenart/vegeta@latest) · wrk2: build from source from github.com/giltene/wrk2 with make (needs a C toolchain; the binary is called wrk) · Chapters: 10, 8, 9

All three can send requests at a fixed arrival rate (an open model) and measure latency from when a request was supposed to be sent, which is what avoids the coordinated omission of chapter 10. Pick one; the exercise is the same. The target is app.py from the Prometheus card, run in its capacity-limited mode.

10-minute guided exercise

Setup. Start the app so that only one request is worked on at a time and each takes about 20 ms. Its capacity is then about 1 / 0.02 = 50 requests per second:

$ SERIAL=1 SERVICE_MS=20 python3 app.py  # terminal 1

Run 1: below capacity, at 30 per second. Choose one tool:

$ echo 'GET http://localhost:8000/checkout' | vegeta attack -rate=30/s -duration=20s | vegeta report  # vegeta
$ wrk -t2 -c10 -d20s -R30 --latency http://localhost:8000/checkout  # wrk2 (rate in total requests per second)
$ k6 run script.js  # k6; script below
illustrative:  Latencies [min, mean, 50, 90, 95, 99, max]  21ms, 28ms, 25ms, 38ms, 46ms, 71ms, 110ms

For k6, save this as script.js. It uses the constant-arrival-rate executor (options as in the k6 documentation) and no sleep(), because the executor paces the iterations. Change rate between runs.

import http from 'k6/http';

export const options = {
  discardResponseBodies: true,
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',
      rate: 30,            // iterations started per timeUnit
      timeUnit: '1s',
      duration: '20s',
      preAllocatedVUs: 20,
      maxVUs: 200,
    },
  },
};

export default function () {
  http.get('http://localhost:8000/checkout');
}

Run 2: above capacity, at 80 per second. Repeat with -rate=80/s (vegeta), -R80 (wrk2) or rate: 80 (k6):

illustrative:  Latencies  ... 50th 3.1s, 90th 7.4s, 99th 8.9s, max 9.2s
illustrative:  k6: http_req_duration p(95)=8.1s ... dropped_iterations: 140 (all VUs busy)
$ curl -s localhost:8000/metrics | grep -E 'le="(0.05|0.1|2.5)"|_count'  # the app's own view
illustrative:  server-side buckets still show most requests under 50 ms

This is the lesson in one picture. At 80 per second against a capacity of 50 the queue grows without bound: the client-side latency keeps growing for as long as the test runs (the later requests wait longest), while the server's own histogram, which starts its clock only when work begins, still says "about 20 ms". Server-side metrics do not see queueing before the handler. Measure at the edge, as chapter 2 says. Now do the same with a closed-loop client for contrast:

$ for i in $(seq 1 200); do curl -s -o /dev/null -w '%{time_total}\n' localhost:8000/checkout; done | sort -n | tail -3
illustrative:  0.041  0.047  0.052     (one request at a time never queues, so it sees about 20 ms)

A loop that waits for each reply can never overload the server, so it reports a flattering p99. That is the closed-loop lie (chapter 10). Clean up with Ctrl-C.

Only on your own machines

A load generator is a denial-of-service tool pointed in a direction. Aim it only at your own service on localhost or on a machine you own. Check that a staging environment is yours before you load it, and never run it against production or a third party's API (the PSP in the studio is exactly the kind of dependency you must not test without an agreement). Set a duration so it always stops.

What to look for

  • Open versus closed. At a rate above capacity the open tools show latency growing without limit; a fixed number of virtual users would settle at a high latency and throughput equal to capacity, and say nothing about the drops.
  • Is the generator keeping up? In k6, dropped_iterations above zero means it ran out of VUs; in vegeta, the report shows achieved rate; in wrk2, look for the requests/sec line close to -R.
  • Latency percentiles beyond p99 need many samples: 20 seconds at 30 per second is 600 requests, too few to trust a p99.9.
  • wrk2 and vegeta print the latency distribution; k6 also reports metrics such as http_req_duration by percentile and can fail a run with thresholds.

Common pitfalls

  • wrk2's first ten seconds are calibration; use runs longer than 20 seconds.
  • Generating the load on the same machine as the server steals CPU from it. At small rates this is fine; at large rates it is not.
  • Python's sleep has a floor of about a millisecond, so very small SERVICE_MS values will not behave as written.
  • The macOS default limit on open files (ulimit -n) can cap connections at high concurrency.

kind & kubectl

Needs: Docker (running), kubectl · kind (macOS): brew install kind (community package), or download the release binary for darwin-arm64/darwin-amd64 from kind.sigs.k8s.io, chmod +x and move it into your PATH · kubectl: brew install kubectl · Chapters: 14, 12

kind ("Kubernetes in Docker") runs a whole cluster as containers on your laptop, which is enough for deployments, probes, rollouts and failure of pods. The exercise shows the declarative loop of chapter 14 and why a readiness probe is the only thing standing between a bad rollout and an outage (chapter 12).

10-minute guided exercise

1. Create the cluster and a deployment. Save the manifest as web.yaml: three nginx pods with a readiness probe, and a rolling update that never removes a ready pod before a new one is ready (maxUnavailable: 0). (The manifest is standard; I could not validate it against a cluster here.)

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: {app: web}
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxSurge: 1, maxUnavailable: 0}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports: [{containerPort: 80}]
        readinessProbe:
          httpGet: {path: /, port: 80}
          periodSeconds: 3
        resources:
          requests: {cpu: 50m, memory: 32Mi}
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector: {app: web}
  ports: [{port: 80, targetPort: 80}]
$ kind create cluster --name ops  # creates a one-node cluster; takes a minute
$ kubectl cluster-info --context kind-ops  # contexts are named kind-<cluster name>
$ kubectl apply -f web.yaml
$ kubectl rollout status deployment/web
illustrative:  deployment "web" successfully rolled out
$ kubectl get pods -l app=web
illustrative:  web-6c9d8f7b5-4kq2z   1/1   Running   0   40s   (three of them)

2. Watch reconciliation. Delete a pod and see the controller replace it, since actual state no longer matches the desired state of three:

$ kubectl delete $(kubectl get pod -l app=web -o name | head -1)  # delete one pod
$ kubectl get pods -l app=web -w  # Ctrl-C when three are Ready again
illustrative:  a new pod appears as ContainerCreating, then Running, within seconds

3. A good rollout. Change the image and watch the surge and replace sequence:

$ kubectl set image deployment/web nginx=nginx:1.27-alpine
$ kubectl rollout status deployment/web
illustrative:  Waiting for deployment "web" rollout to finish: 1 out of 3 new replicas have been updated...
illustrative:  deployment "web" successfully rolled out

4. A broken readiness probe. Point the probe at a path that does not exist, simulating a release that fails its health check:

$ kubectl patch deployment web --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/nope"}]'
$ kubectl rollout status deployment/web --timeout=45s
illustrative:  Waiting for deployment "web" rollout to finish: 1 out of 3 new replicas have been updated...
illustrative:  error: timed out waiting for the condition
$ kubectl get pods -l app=web
illustrative:  3 old pods  1/1 Running;  1 new pod  0/1 Running (never Ready)
$ kubectl describe pod -l app=web | grep -A2 'Readiness probe failed'
illustrative:  Readiness probe failed: HTTP probe failed with statuscode: 404
$ kubectl rollout undo deployment/web  # roll back to the previous revision
$ kubectl rollout status deployment/web
illustrative:  deployment "web" successfully rolled out

The three old pods kept serving the whole time: the readiness gate stopped the rollout, which is the safe failure and the reason chapter 12 insists a rolling update is only as safe as its probe. Try again with the probe path / but removed entirely (delete the readinessProbe block) and a bad image command: the rollout "succeeds" because nothing checks. Also try kubectl rollout pause deployment/web mid-rollout, the manual version of halting a wave. Clean up:

$ kind delete cluster --name ops
illustrative:  Deleting cluster "ops" ...

Only on your own machines

kind is a local cluster. Check kubectl config current-context before running any command that changes things: a context left pointing at a shared or production cluster is one of the classic ways to break something that is not yours. Prefer a separate kubeconfig for practice (KUBECONFIG=~/.kube/ops-lab kind create cluster --name ops).

What to look for

  • kubectl get pods -w and kubectl get events --sort-by=.lastTimestamp show what the controllers are doing. Read them as the system's explanation of its own decisions.
  • rollout history and rollout undo exist only because the Deployment keeps old ReplicaSets; the history length is a setting.
  • A pod that is Running but not Ready receives no Service traffic; that is the whole meaning of readiness (chapter 14).

Common pitfalls

  • kind nodes are containers, so images must be pullable from inside them; local images go in with kind load docker-image NAME:TAG --name ops, and the :latest tag defaults to always pulling.
  • Docker Desktop must have enough memory (a few GB) or pods stay Pending.
  • kind runs Kubernetes on one container-based node; it shows control-loop behaviour, not real multi-node scheduling, zone loss or load-balancer limits.

stress-ng & tc netem

Needs: a Linux machine you own (a local VM or a small cloud server), root access · Ubuntu/Debian: sudo apt install stress-ng iproute2 curl · Chapters: 11, 19, 9

stress-ng consumes CPU, memory, I/O and more in controlled amounts. tc with the netem queueing discipline adds delay, jitter, loss or reordering to a network interface. Together they let you ask the question of chapter 19 on a small scale: what does my service do when the machine around it is starved? These are Linux tools; on macOS use a VM.

10-minute guided exercise

Run app.py and a fixed-rate load (the previous card) on the VM, and watch the latency as you apply each fault, one at a time.

$ python3 app.py  # terminal 1
$ echo 'GET http://localhost:8000/checkout' | vegeta attack -rate=40/s -duration=3m | vegeta report -every=10s  # terminal 2: a fixed rate with a report every 10 seconds
illustrative:  baseline: 99th about 55ms, success 98%
$ stress-ng --cpu $(nproc) --timeout 60s --metrics-brief  # terminal 3: every core busy for a minute
illustrative:  during stress: 99th about 400ms, mean about 90ms; the service did not change, its CPU share did
$ stress-ng --vm 1 --vm-bytes 75% --timeout 30s  # memory pressure: 75% of RAM touched repeatedly; may trigger swapping or the OOM killer, so keep it short on a small VM

CPU starvation shows as a latency tail, not as errors, until a timeout is crossed: this is "saturation" in the USE method (chapter 4) and the queueing knee of chapter 8. Now the network. Apply delay to the loopback interface so that your SSH session over the real interface is not affected, and always set a timer to remove it:

$ sudo tc qdisc add dev lo root netem delay 100ms 20ms; sleep 60; sudo tc qdisc del dev lo root  # adds 100 ms plus or minus 20 ms to every packet on lo, then removes it after a minute
illustrative:  latency of each request rises by roughly 200 ms (delay applies to the request and to the reply)
$ tc qdisc show dev lo  # shows 'netem' while the fault is active; back to 'noqueue' afterwards
$ sudo tc qdisc add dev lo root netem loss 5%; sleep 30; sudo tc qdisc del dev lo root  # 5% packet loss for 30 seconds
illustrative:  some requests take 1 s or more: TCP retransmits after a timeout

Compare what you see with a retry-less client and with one that has a timeout and a retry. Packet loss often looks like latency (retransmission) rather than failure. Clean-up check: tc qdisc show dev lo must not list netem, and pgrep stress-ng must print nothing.

On a Linux VM

The point of a VM here is safety: if stress-ng takes the machine down, you reboot a throwaway. Use a VM with at least 2 vCPUs and a few GB of memory. See the lab machine page for a local Linux VM or a small rented server (set a billing alert first, and delete it when you are done).

Only on your own machines

Never run tc netem on the interface that carries your SSH session without a timer that removes it in the same command, or you can lock yourself out. Never run stress tools on a shared or production host, and never on a cloud account whose acceptable-use policy you have not read.

What to look for

  • Resource faults degrade the tail first: p99 moves long before the mean or the error rate does.
  • netem delay is added per packet in one direction; a request-response pair on the same interface pays it twice.
  • Write down the steady state, then the hypothesis, then inject, as in chapter 19. The commands are the easy part.

Common pitfalls

  • Applying netem to eth0 instead of lo slows your own login. Always pair add with a delayed delete.
  • stress-ng --vm-bytes 75% can invoke the OOM killer on a small VM and kill your service instead of just slowing it, which is itself a finding.
  • Containers share the host kernel; faults on lo inside a container's own network namespace do not affect other containers.
  • A cloud VM may be throttled by burst credits, which can mimic a stress result. Note the instance type.

Break it on purpose

Fault injection with a blast radius you chose, followed by the written word you need when something breaks for real.

Chaos tools: Toxiproxy & Chaos Mesh

Toxiproxy (macOS): brew tap shopify/shopify && brew install toxiproxy · Linux: a release package or build from source (github.com/Shopify/toxiproxy) · Chaos Mesh: needs a Kubernetes cluster (the kind cluster of the previous card) and Helm · Chapters: 19

Toxiproxy is a TCP proxy that sits between a client and a dependency and applies "toxics" (latency, a closed connection, a bandwidth limit, a timeout) on demand through an HTTP API on port 8474. It is the simplest way to rehearse a slow dependency such as the payment provider in the studios. Chaos Mesh is a Kubernetes-native tool that injects faults (pod kills, pod failure, network delay, stress, I/O faults) described as custom resources, with selectors that limit the blast radius and durations that end the fault by themselves. Both implement chapter 19's experiment: a steady state, a hypothesis, a fault, an abort condition.

10-minute guided exercise

A. Toxiproxy against the app. Put a proxy in front of app.py and slow it down without touching the app. Hypothesis: "with 500 ms of added latency, a client with a 300 ms timeout fails, and one with a 2 s timeout succeeds but slowly." Abort condition: you press Ctrl-C.

$ python3 app.py  # terminal 1: the dependency on :8000
$ toxiproxy-server  # terminal 2: the control API on :8474
$ toxiproxy-cli create -l localhost:8001 -u localhost:8000 web  # terminal 3: clients now talk to :8001
illustrative:  Created new proxy web
$ curl -s -o /dev/null -w '%{time_total}\n' localhost:8001/checkout
illustrative:  0.022     (steady state: about 20 ms through the proxy)
$ toxiproxy-cli toxic add -t latency -a latency=500 -a jitter=100 web
illustrative:  Added downstream latency toxic 'latency_downstream' on proxy 'web'
$ curl -s -m 0.3 -o /dev/null -w '%{http_code} %{time_total}\n' localhost:8001/checkout  # a client with a 300 ms timeout
illustrative:  000 0.300     (timed out: the hypothesis holds)
$ curl -s -m 2 -o /dev/null -w '%{http_code} %{time_total}\n' localhost:8001/checkout
illustrative:  200 0.55
$ toxiproxy-cli toxic remove -n latency_downstream web  # the fault is removed; confirm the steady state returns
$ toxiproxy-cli toxic add -t timeout -a timeout=0 web  # a connection that accepts bytes and never answers; try with and without a client timeout
$ toxiproxy-cli toxic remove -n timeout_downstream web
$ toxiproxy-cli list

Now point the Prometheus scrape or a load generator at port 8001, and watch what a slow dependency does to your own latency histogram, to the queue of in-flight requests and to the retry count if you add one. The takeaway is always the same: a missing timeout turns a slow dependency into your outage.

B. Chaos Mesh on kind (about ten minutes of install and run). The commands follow the Chaos Mesh docs; the container-runtime values for kind are the part to confirm on the install page for your version, so treat them as illustrative:

$ kind create cluster --name chaos && kubectl apply -f web.yaml  # the three-pod web deployment from the kind card
$ helm repo add chaos-mesh https://charts.chaos-mesh.org
$ kubectl create ns chaos-mesh
$ helm install chaos-mesh chaos-mesh/chaos-mesh -n chaos-mesh --set chaosDaemon.runtime=containerd --set chaosDaemon.socketPath=/run/containerd/containerd.sock  # kind uses containerd; confirm the values on the docs page
$ kubectl get pods -n chaos-mesh -l app.kubernetes.io/instance=chaos-mesh  # wait until controller-manager, daemon and dashboard are Running
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: kill-one-web-pod
  namespace: default
spec:
  action: pod-kill
  mode: one                 # one randomly chosen pod from the selection
  selector:
    namespaces: [default]
    labelSelectors:
      app: web
$ kubectl get pods -l app=web -w  # terminal 1
$ kubectl apply -f podkill.yaml  # terminal 2
illustrative:  one web pod goes Terminating and the Deployment starts a replacement within seconds
$ kubectl delete -f podkill.yaml
$ kind delete cluster --name chaos

Hypothesis for the Kubernetes version: "killing one of three pods causes no failed requests through the Service." Test it by running a fixed-rate client (the load card, with kubectl port-forward svc/web 8080:80) while you apply the chaos. If errors appear, you have found a gap such as a missing readiness probe, too few replicas or no graceful shutdown.

Only on your own machines

Fault injection belongs to systems you own and to a blast radius you have chosen. Use label selectors and namespaces so a Chaos Mesh experiment can only touch what you meant it to, give every experiment a duration where the fault type supports one, and keep a manual stop (kubectl delete -f) ready. Do not run these in a shared cluster without the owners' agreement, and never first in production.

What to look for

  • The Toxiproxy exercise is just a hypothesis written as a test. Writing down the expected behaviour before injecting is what makes it an experiment (chapter 19).
  • A timeout toxic with no client timeout hangs the client. This is the most common real finding.
  • Chaos Mesh separates the what (action), the who (selector and mode) and the how long (duration), which is exactly the checklist of blast radius, abort and expiry.

Common pitfalls

  • Toxiproxy proxies TCP only; it does not inspect HTTP. Apps must be pointed at the proxy's port.
  • Toxiproxy toxics default to the downstream direction (server to client); use --upstream style options (see toxiproxy-cli toxic add --help) to affect the other direction.
  • Chaos Mesh needs the right container runtime settings, or the daemon cannot reach containers. A failure to inject network faults on kind is usually this.
  • A passing experiment proves one fault was survived one time. Keep experiments and re-run them after changes.

Runbooks & incident templates

Needs: a text editor and a place the whole team can find the results (a repository folder or wiki) · Chapters: 16, 17, 7

The cheapest reliability tools are plain text. These templates are starting points to copy, edit and keep under version control. They are generic (not any company's), and each is a shape to be fitted to your system and your team. The principle behind all four: they lead with the action, not the history.

10-minute guided exercise

Exercise (ten minutes). Take the alert from the Prometheus card, AppFastBurn. Copy the runbook template below into a file, and fill it in for that alert, using only what you know from your own exporter. Then give it to a friend and ask them to follow it without your help. Every question they ask is a missing line. Then copy the incident-channel opener and the status update, and write the first one for a pretend incident about your toy service. Finish by writing the postmortem summary and contributing factors for the toy outage you caused with ERROR_RATE=0.15.

1. Runbook for one alert (chapter 7):

# ALERT NAME: <AppFastBurn>
Owner: <team / rota>        Last reviewed: <date>        Severity: <page | ticket>

## What it means (one sentence, in user terms)
<Customers are failing to complete orders at a rate that would use up the monthly budget in about 2 days.>

## Check first (2 minutes)
1. Dashboard: <link>. Is the problem real (error ratio and traffic both visible)?
2. Scope: one region? one version? one dependency? (use the dashboard variables)
3. What changed in the last hour? <deploys link>  <flags link>  <config link>

## Mitigate (in this order; stop when impact ends)
1. Recent deploy and errors started at the same time -> roll back: <command or link>
2. One region or zone bad -> drain it: <command or link>
3. Dependency failing (<PSP>) -> enable fallback flag: <flag name> / <link>
4. Overloaded -> shed non-essential load: <flag name>, then add capacity: <command>
5. None of these -> declare an incident (see incident channel template) and page <secondary>

## Diagnose (only after impact is reduced)
<Query / log search / trace search links; known causes and how they look.>

## Save evidence before changing things
Screenshot dashboard, copy 5 failing trace ids, note the time and deploy versions.

## Escalate
Secondary: <rota>   Service owner: <rota>   Vendor contact (PSP): <contact>   Manager: <contact>

## Appendix: graphs, queries, links

Keep templates and filled-in examples in the repository next to the code, review runbooks whenever the alert changes and after every incident that used one, and delete any template section nobody fills in.

Only on your own machines

Incident records often hold customer details, internal hostnames and security-relevant facts. Keep them in your own team's private space, redact personal data, and do not paste real incident text into public tools. Everything on this page is generic or fictional.

What to look for

  • A good runbook step is a command or a link, not an explanation. Move the explanation to a "background" section.
  • The status update template forces the three things readers want: impact, action, next update time.
  • The postmortem template has "where we got lucky" because luck is a hidden defence that did not exist by design (chapter 17).

Common pitfalls

  • Runbooks rot. An owner and a review date are the minimum, and the alert should link to the runbook directly.
  • Writing the postmortem as a list of who did what, in blameful language, ends the inquiry; ask "how did the system let this happen?".
  • Action items without an owner and a date are wishes. Track them like any other work.

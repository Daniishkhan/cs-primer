Lab 5: Adaptive Concurrency & Load Shedding

A service that is overloaded for ten seconds can stay broken for hours. Nothing is wrong with it, nothing is attacking it, and the traffic is back to normal. It is stuck in a state sustained by its own recovery mechanisms: clients that time out and retry, and servers that keep doing work for requests nobody is waiting for. Bronson and colleagues called this a metastable failure. In this lab you will build a small simulated service, reproduce the failure from a brief trigger, and then protect it, step by step, with the tools of chapter 11: deadline-aware shedding and LIFO, an AIMD adaptive concurrency limit, a retry budget and a client-side throttle. A check will compare goodput after the trigger with and without the protections.

Why this lab matters

Retries, timeouts and queues are all individually sensible, and each is in nearly every production service. Together they can create a feedback loop that no component's author intended: a timeout abandons a request, but the server still works on it; the client retries, so the server now has two copies; the extra load makes more requests time out. The loop is hard to see in a design review and nearly impossible to see in a happy-path test, because it needs a trigger. It is easy to see in a simulation, where you can dial the trigger up and down, take away one ingredient at a time, and watch the system flip between recovering and collapsing. The protections you build here are the ones real systems use: Netflix's open-source concurrency-limits library uses AIMD limits, the Google SRE book describes the adaptive client-side throttle, and Facebook's engineers described serving the newest request first and CoDel-style queue management in "Fail at Scale".

Simulated time: no sleeping, no sockets, no threads

Time is a number in an event heap, so a 140-second incident with thousands of requests runs in a tenth of a second and gives the same answer every time. Three independent seeded random streams drive the arrivals, the service times and the client coin flips, so turning a protection on does not change which requests arrive: the comparison is fair, request for request. Standard library only, Python 3.8 or newer. The whole check takes about six seconds. When a check fails it prints the seed, and python3 check.py solution 3 4 replays only milestone 3 on seed 4.

What you'll build

  1. The service: a bounded FIFO queue, a pool of workers, client timeouts and retries. When a client times out the server is not told, and still does the work.
  2. A metastable failure: measure goodput, find a trigger that is gone in ten seconds, and show that goodput stays collapsed after load and capacity are back to normal.
  3. Deadline-aware shedding: drop requests that have no time left, and serve the newest request first when the queue is long.
  4. An AIMD concurrency limit: a limit that finds the right amount of concurrency by itself, and keeps latency bounded. Verify it with Little's law.
  5. Retry budget and client throttle: cap retries at 10% of requests and let clients back off when the service is refusing them. Then run the same trigger again.

Milestone 1: a service with a queue, timeouts and retries

The model has the fewest parts that still produce the failure. Requests arrive as a Poisson process at 70 per second (chapter 8). Each is placed in one FIFO queue of at most 2000 waiting requests. Ten workers take requests from the queue; each request takes an exponentially distributed 100 ms on average, so the service can complete at most 100 per second. A request that cannot be queued is rejected at once.

The client is where the trouble starts. Every attempt carries a deadline, one second after it was sent. If no response has arrived by then, the client gives up on that attempt and, after a short backoff, sends a new one, up to three retries. This is exactly what networking chapter 16 told you to do. The catch is the one from architecture chapter 17: a timeout abandons the wait, not the work. The server has no idea the client left, so the abandoned request stays in the queue and, when its turn comes, a worker spends 100 ms on it. The result goes nowhere.

The simulator's event loop is given. It handles four kinds of events (an attempt arrives, a job finishes, a client's deadline expires, a capacity change) and calls into three classes that you write: the FifoQueue, the Server (admit, start jobs, finish jobs) and the Client's retry rule. Their docstrings say what the loop expects. Two vocabulary points that the rest of the lab depends on:

Throughput
Jobs the workers complete per second, useful or not.
Goodput
Responses that arrive while the client is still waiting. This is the only number users experience. A service can run at full throughput and zero goodput.

class FifoQueue:

    def __init__(self):
        self.q = deque()

    def __len__(self):
        return len(self.q)

    def push(self, req, now):
        self.q.append(req)

    def pop(self, now):
        """Return (the oldest request, []) or (None, []) when empty."""
        if not self.q:
            return None, []
        return self.q.popleft(), []

def submit(self, req, now):
    if len(self.queue) >= self.cfg.queue_limit:
        return False
    if self.limiter is not None and not self.limiter.try_acquire(self.inflight):
        self.limiter.on_drop(now)
        return False
    req.enq = now
    req.state = "queued"
    self.queue.push(req, now)
    return True

def dispatch(self, now):
    dropped_all = []
    while self.busy < self.workers and len(self.queue) > 0:
        req, dropped = self.queue.pop(now)
        for d in dropped:
            d.state = "dropped"
            if self.limiter is not None:
                self.limiter.on_drop(now)
        dropped_all.extend(dropped)
        if req is None:
            break
        self.busy += 1
        req.started = now
        req.state = "running"
        self.schedule(now + self.service_time(), DONE, req)
    return dropped_all

def finish(self, req, now):
    self.busy -= 1
    useful = not req.abandoned
    if self.limiter is not None:
        self.limiter.on_sample(req.started - req.enq, now)
    return useful

def should_retry(self, orig, now):
    if orig.tries > self.cfg.max_retries:
        return False
    if self.budget is not None and not self.budget.try_retry():
        return False
    return True

Milestone 2: reproduce a metastable failure

Now break it. A trigger is a temporary event that pushes the system out of its normal state; a metastable failure is one where the system stays out after the trigger has ended, sustained by a feedback loop. The Bronson et al. paper (HotOS 2021) surveys real incidents of this shape, and its triggers are mundane: a cache flush, a deploy, a load spike, a slow dependency. Here the trigger is a capacity dip: at second 20, six of the ten workers disappear (a bad deploy, a noisy neighbour, a failed zone) and return at second 30. For ten seconds the service can do 40 requests per second against a demand of 70.

Here is what the unprotected service does, using the simulate given in the starter and the three measurements you write in this milestone. These are the real numbers for seed 1:

Read the table from the top. At seconds 10 and 19 everything is fine: about 70 successes per second, nothing wasted, no queue. Two seconds into the dip (second 22) there is already a queue of 130 and zero successes: with only 40 requests per second of capacity the wait passes the one-second timeout almost at once, so every job the workers finish was sent more than a second ago and its client has left. From second 32 the queue sits at its limit of 2000 and stays there. From second 45 to the end the service is busy (about 100 jobs finished per second, all workers occupied) and its goodput is zero: 100% of what it finishes is wasted, and about 280 attempts per second reach it even though users send only 70 new requests per second. Four attempts per request is 280; this is the retry loop running at full amplification.

How brief can the trigger be? Not very brief, and the threshold is a lesson in itself. A dip of one second is absorbed. Two seconds is usually absorbed, but one seed in ten tips over. Three seconds tips nine runs in ten. This is how metastable failures feel in production: no gradual degradation, just a cliff.

Solution spoiler 
def goodput(res, t0, t1):
    lo, hi = int(t0), int(t1)
    return sum(res.succ[lo:hi]) / max(1, hi - lo)

def wasted_share(res, t0, t1):
    lo, hi = int(t0), int(t1)
    w, s = sum(res.wasted[lo:hi]), sum(res.succ[lo:hi])
    return w / (w + s) if (w + s) else 0.0

def is_metastable(res, margin=30.0):
    c = res.cfg
    before = goodput(res, 5, c.trigger_start)
    after = goodput(res, c.trigger_end + margin, c.duration)
    return before >= 0.9 * c.base_rate and after < 0.5 * c.base_rate

Milestone 3: deadline-aware shedding and LIFO under overload

Now the first protection. The waste in the loop is that the server does work for requests whose clients have already gone. The remedy follows directly: carry the client's deadline with the request, and when a worker is about to start one, drop it if it cannot finish in time. A request whose deadline is 50 ms away is dead, because the job takes 100 ms. Dropping it costs nothing and frees the worker for a request that can still succeed. This is deadline propagation from architecture chapter 17 applied on the server side, and it is the single most valuable overload protection per line of code.

In the sim every attempt has deadline = sent + timeout. Two things must be done with it:

  • Drop at the head, and purge on arrival. When a worker pops a request whose now + min_useful > deadline, drop it (and keep looking). Also, when a new request is pushed, discard the expired ones at the front of the queue. In a FIFO deque the oldest are at the front and also expire first, so this is O(1) amortised, and it stops the waiting room filling with dead requests.
  • Serve the newest first when the queue is long. A FIFO queue under overload is the worst possible discipline: the request at the head has waited longest, so it is the one most likely to be dead by the time it is served, while the fresh requests behind it are the ones with the most time left. LIFO (last in, first out) when the queue is over a threshold inverts that. A few requests (the oldest) suffer, but those were going to be lost anyway, and the many fresh ones succeed. Facebook's engineers described this as adaptive LIFO: FIFO when the queue is short, LIFO when it is long.

The solution also supports a CoDel-ish variant (CoDel is Nichols and Jacobson's "Controlling Queue Delay"): if the time requests spend in the queue has stayed above a target for a whole interval, there is a standing queue (a queue that is not merely absorbing a burst) and the head is dropped until it clears. It is optional here, and experiment 3 below compares all of them.

Solution spoiler 
class ShedQueue:

    def __init__(self, expire=True, lifo_over=None, min_useful=0.0, codel_target=None, codel_interval=0.5):
        self.q = deque()
        self.expire, self.lifo_over, self.min_useful = expire, lifo_over, min_useful
        self.codel_target, self.codel_interval = codel_target, codel_interval
        self.above_since = None
        self.purged = []            # dead requests removed by push(); the server reports them

    def __len__(self):
        return len(self.q)

    def push(self, req, now):
        if self.expire:
            while self.q and now + self.min_useful > self.q[0].deadline:
                dead = self.q.popleft()
                self.purged.append(dead)
        self.q.append(req)

    def pop(self, now):
        dropped = self.purged
        self.purged = []
        while self.q:
            if self.lifo_over is not None and len(self.q) > self.lifo_over:
                req = self.q.pop()
            else:
                req = self.q.popleft()
            if self.expire and now + self.min_useful > req.deadline:
                dropped.append(req)
                continue
            if self.codel_target is not None:
                sojourn = now - req.enq
                if sojourn <= self.codel_target:
                    self.above_since = None
                else:
                    if self.above_since is None:
                        self.above_since = now
                    if now - self.above_since >= self.codel_interval:
                        dropped.append(req)
                        continue
            return req, dropped
        return None, dropped

Milestone 4: an AIMD adaptive concurrency limit

Shedding handles requests that are doomed. But it still lets the queue grow to 20 or 200 deep before it reacts. A better protection stops the queue forming: limit the number of requests in the server at once, and refuse the excess immediately. A refusal is cheap and fast (the client learns at once and can go elsewhere), whereas a request admitted to a deep queue is expensive and slow. The question is what limit to use. Too low wastes capacity; too high is no limit at all, and the right number changes whenever the service's speed or the machine count does.

Little's law (chapter 8) says where the optimum is: concurrency N = throughput × latency. A service that can do at most Xmax = 100 requests per second, with an unqueued latency of S = 0.1 s, needs N* = 100 × 0.1 = 10 requests in flight to be fully busy. Fewer and workers idle; more and the extra just wait, adding latency and no throughput. The service does not know N*. It can measure it, by watching whether requests wait.

The classic way to search for a limit by feedback is the one TCP uses for its congestion window: AIMD, additive increase, multiplicative decrease. Raise the limit slowly while all is well; cut it sharply when congestion is detected. Netflix's concurrency-limits library applies the idea to requests in flight. Here the signal is queueing delay: how long a request waited before a worker started it. When no request waits, the limit has headroom; when requests start waiting longer than a small target (50 ms here), the queue is a standing queue and the limit has overshot. Rules:

  • A completion with a short wait: limit += 1 / limit. Since about limit completions happen per round trip, that is about +1 per round trip.
  • A completion with a long wait, or a refusal or drop: limit *= 0.9, but at most once per 0.2 s. A burst makes many slow completions arrive together; cutting for each would crash the limit to the floor on one event.
  • Keep the limit between a floor and a ceiling. Admit a new request only if the number already in the server (queued + running) is below int(limit).

Little's law gives a second, independent check, the same one as in Lab 4. The simulator integrates the number of requests inside the server over time and records every request's time there. In this run the time-average number inside is L = 12.43; the completion rate times the mean time inside is X × W = 99.4 × 125 ms = 12.42. They agree, and both sit close to the optimum 10: the limiter is holding the system a little above the point where workers are all busy and almost nothing waits. Without a limiter, the same overload fills the queue (2000 requests × 10 ms = 20 s of waiting) and goodput is zero, because every answer arrives after its client left.

Solution spoiler 
class AIMDLimiter:

    def __init__(self, initial=20.0, min_limit=2.0, max_limit=1000.0, target=0.05, backoff=0.9, cooldown=0.2):
        self.limit = float(initial)
        self.min_limit, self.max_limit = min_limit, max_limit
        self.target, self.backoff, self.cooldown = target, backoff, cooldown
        self.last_decrease = -1e9

    def try_acquire(self, inflight):
        """May one more request enter, given `inflight` requests already inside?"""
        return inflight < int(self.limit)

    def on_sample(self, queue_wait, now):
        """A request finished; it waited `queue_wait` seconds in the queue."""
        if queue_wait > self.target:
            self._decrease(now)
        else:
            self.limit = min(self.max_limit, self.limit + 1.0 / self.limit)

    def on_drop(self, now):
        """A request was refused or dropped: a congestion signal."""
        self._decrease(now)

    def _decrease(self, now):
        if now - self.last_decrease >= self.cooldown:
            self.limit = max(self.min_limit, self.limit * self.backoff)
            self.last_decrease = now

Milestone 5: a retry budget and a client-side throttle

The server can defend itself; the other half of the loop is the clients. A fleet of clients that each retry three times is, in aggregate, a machine for multiplying load by four at the worst possible moment. Two cheap client-side rules cut the loop:

Retry budget
Allow retries only up to a fraction of the original requests, here 10%. Implemented as a token bucket: each original request deposits 0.1 token (capped), each retry spends one. When the service is healthy, retries are rare (a few percent of requests fail transiently) and the bucket always has tokens, so nothing changes. When the service is failing broadly, the bucket runs dry after a handful of retries and the rest are not retried: the extra load is at most 10%, whatever is going wrong. This is the rule in Google's SRE book (chapter on handling overload) and in the AWS Builders' Library article on timeouts, retries and backoff with jitter.
Adaptive client throttle
Each client counts, over a recent window, its requests (everything it wanted to send) and accepts (requests that got a useful answer). It rejects locally, without sending, with probability max(0, (requests − K × accepts) / (requests + 1)). With K = 2, a client whose service answers at least half its requests never throttles itself; as the answer rate falls the client sends fewer and fewer. This is the formula from the SRE book. Real clients keep a couple of minutes of history; this lab's incident lasts seconds, so the default window is 5 s.

The two rules do different jobs. The budget stops retries from multiplying load and applies to every request. The throttle limits all traffic, new and retried, when the service is plainly refusing or timing out; it is the defence against clients that do not retry but simply fail and are replaced by new users.

  • RetryBudget.on_request: tokens = min(max_tokens, tokens + ratio). try_retry: if tokens >= 1 (allow a tiny tolerance: ten additions of 0.1 sum to 0.9999999999999999), subtract 1 and return True.
  • The throttle keeps a deque of (time, 1, accepted) events and running totals. _expire(now) (given) drops events older than the window and fixes the totals.
  • allow must itself count a throttled attempt as a request that was not accepted (record(now, False)). Otherwise a throttled client would never see its own rejections and would stop throttling after one coin flip.
  • reject_probability is the formula on the page; call _expire(now) first so stale events do not count.
  • Do not use the same random stream for the throttle's coin as the simulator uses for arrivals: the simulator passes rng_c into allow, which is the client's own stream.

class RetryBudget:

    def __init__(self, ratio=0.1, max_tokens=10.0, initial=0.0):
        self.ratio, self.max_tokens = ratio, max_tokens
        self.tokens = initial
        self.requests = 0
        self.retries = 0

    def on_request(self):
        """An original (first-attempt) request was made."""
        self.requests += 1
        self.tokens = min(self.max_tokens, self.tokens + self.ratio)

    def try_retry(self):
        """True (and spend one token) if a retry is allowed right now."""
        if self.tokens >= 1.0 - 1e-9:        # 10 additions of 0.1 sum to 0.9999999999999999
            self.tokens -= 1.0
            self.retries += 1
            return True
        return False

class ClientThrottle:

    def __init__(self, k=2.0, window=5.0):
        self.k, self.window = k, window
        self.events = deque()        # (time, requested 1, accepted 0 or 1)
        self.requests = 0
        self.accepts = 0

    def _expire(self, now):
        while self.events and self.events[0][0] < now - self.window:
            _, r, a = self.events.popleft()
            self.requests -= r
            self.accepts -= a

    def record(self, now, accepted):
        """One attempt's outcome: accepted True if it got a useful response."""
        self._expire(now)
        self.events.append((now, 1, 1 if accepted else 0))
        self.requests += 1
        self.accepts += 1 if accepted else 0

    def reject_probability(self, now):
        self._expire(now)
        return max(0.0, (self.requests - self.k * self.accepts) / (self.requests + 1.0))

    def allow(self, now, rng):
        """Should this attempt be sent? Throttled attempts count as requests that
        were not accepted (call record(now, False) for them)."""
        if rng.random() < self.reject_probability(now):
            self.record(now, False)
            return False
        return True

Look under the hood

  • Every protection works alone, in this model. Shedding, LIFO, CoDel, the AIMD limit and the retry budget each repair the dip by themselves (experiment 3). That is a property of this simple model, where there is one cause and one trigger, and not a promise about yours. Real systems have several kinds of work, shared dependencies and imperfect signals, which is why production designs layer them: the server protects itself, because it cannot trust clients, and the clients protect the server, because the server's defences cost something.
  • The throttle is slow medicine. Alone it does recover this scenario, but only after about 30 seconds; combined with the budget it is slower than the budget alone (34 s against 14 s on the dip, experiment 3). It refuses requests locally for as long as its window remembers failures, so it keeps clients away from a service that has already recovered. Give it a 30-second window instead of 5 and the spike takes over 80 seconds to recover. The budget does the real repair; the throttle is insurance against floods that retries do not explain, and its window is a trade between protection and recovery time.
  • The failure needs several ingredients at once. Take away retries, or lengthen the timeout, or shorten the queue, and the same dip is absorbed (experiment 1). Production incidents rarely have one cause. They have a trigger and a set of ordinary, individually reasonable settings that happen to form a loop.
  • The recovery was not instantaneous for the client-side pair. The dead backlog still has to drain, and the throttle remembers the failure for its window. Server-side protections recover at once because they stop the backlog from containing dead work in the first place.

Stretch goals

  • Priority shedding: mark 20% of requests as critical (a payment, not a thumbnail) and make the queue drop non-critical requests first. How much goodput of critical requests survives a 3x spike?
  • Gradient limit: replace AIMD with a limit that tracks the minimum observed latency, as Netflix's gradient and Vegas-style limiters do: new_limit = limit × (min_latency / latency) + queue_allowance. Compare convergence speed with AIMD.
  • Hedging against the limiter: send a second copy of a slow request to another replica after the 95th percentile of latency. What does that do to load, and to the retry budget?
  • A dependency: make each request call a second service with its own queue and timeout. Do the two services' timeouts nest properly? What happens when the inner timeout is longer than the outer?
  • Client types: add a second client population that never retries but is replaced by new users. Which protection helps there?
  • Unequal work: make 10% of requests 10 times as expensive. Does the concurrency limit still find a good value, and is it fair to cheap requests?

Distributed systems connection

Metastability is a distributed-systems failure because its feedback loop runs through the network: the client and the server each act correctly on local information, and neither can see the other's side. The client sees a timeout and does not know whether the server is dead, slow, or about to answer; the server sees a request and does not know whether its client is still there. Deadlines propagated in the request are the cheapest way to give the server the client's knowledge, and the retry budget is a way to give clients the system's (the service is failing broadly, so adding to the load will not help). The same loop appears between layers: a retrying service in front of a retrying database multiplies attempts, which is why the retry storm case insists that only one layer should retry. And the AIMD limit is a distributed algorithm: many clients, or many servers, adapting independently to a shared signal and converging without coordinating.

What you learned

  • Goodput (responses in time) is not throughput (jobs finished). A service can run at full speed and deliver nothing.
  • A brief trigger can leave the system collapsed: a timeout abandons the wait but not the work, so the server finishes jobs no one wants, and every timeout adds a retry. The loop sustains itself, and the trigger can be as short as three seconds.
  • The failure needs a particular combination of settings (retries, timeout, queue length). Remove one ingredient and the same trigger is absorbed.
  • Deadline-aware shedding drops requests that cannot succeed. LIFO under a long queue serves the requests with the most time left. Both stop the server wasting work, and goodput holds near capacity during overload.
  • An AIMD limit on requests in flight, driven by queueing delay, finds the concurrency the service can use without being told. Little's law says it should settle near capacity × unqueued latency; it did, about 30% above, with bounded latency.
  • A retry budget caps retry amplification at a fraction of traffic; an adaptive throttle lets a client back off when it is being refused. The budget does the repair; the throttle is insurance. Together they recover from the same trigger, more slowly than server-side protections.
  • Layer the defences: servers cannot trust clients, and clients cannot see the server.

Check your understanding

After a ten-second capacity dip the service is back to full capacity and normal load, but goodput is still near zero and the workers are busy. What is the most likely explanation?

  1. The workers are still slow because of the earlier dip
  2. The queue is full of requests whose clients already gave up, the workers keep finishing them, and clients' retries keep the queue full: a self-sustaining loop
  3. The load balancer has not noticed that capacity has returned
  4. The clients have run out of retries and have stopped sending
Throughput is high and goodput is zero, which means the work being done is wasted. Timeouts leave abandoned requests in the queue, retries add more, and the backlog never drains. That is a metastable failure. Capacity returning does not help because there is no spare capacity to eat the backlog while retries keep arriving.

Why does serving the newest request first (LIFO) under overload increase goodput?

  1. Newer requests are cheaper to serve
  2. LIFO is fairer to old requests
  3. LIFO makes the queue shorter
  4. The newest requests have the most time left before their clients give up; the oldest are probably dead already, so spending workers on them wastes capacity
FIFO under overload serves the request that has waited longest, which is the one most likely to be past its deadline. LIFO flips that: it sacrifices a few old requests that were going to be lost anyway so that many fresh ones succeed. It is applied only when the queue is long, so normal operation stays FIFO and fair.

Little's law says the best concurrency for a service is capacity × unqueued latency. For the lab's service (100 requests/s, 100 ms) what is it, and what does the AIMD limiter do about it?

  1. 10 in flight; the limiter is not told this, but raises its limit while requests do not wait and cuts it when they do, so it settles a little above 10
  2. 100 in flight; the limiter is configured with this number
  3. 1 in flight, since only one request should be served at a time
  4. It cannot be computed, so the limiter keeps a fixed limit of 1000
N* = X × S = 100 × 0.1 = 10. The point of AIMD is that nobody has to know N*: queueing delay is the signal that the limit has overshot. In the run the limit hovered between 12 and 15 with goodput at capacity and a bounded p99.

A retry budget of 10% means:

  1. Each request may be retried at most 10 times
  2. Each request waits 10% longer before it is retried
  3. Retries across all requests are allowed only up to about 10% of the original requests, so a broad failure cannot multiply the load by more than about 1.1
  4. 10% of all requests are never retried
A per-request limit (3 retries) still lets a fleet multiply load fourfold, because every request uses it. The budget is shared and proportional: when everything is failing, only a tenth of the failures are retried. The lab's sweep shows why the number matters: 50% or more allows enough amplification to keep the loop alive.

Lab 4: Queues, Load Tests & Coordinated Omission

Chapter 8 gave you formulas for how long a queue makes you wait, and chapter 10 gave you the rules for load tests that tell the truth. Both are easy to nod along to and easy to get wrong in practice. In this lab you will build a discrete-event queue simulator from scratch and make it agree with the formulas (M/M/1, Erlang C, Little's law, Kingman), so that you trust it. Then you will use the same ideas to write two load generators and point them at a server that occasionally stalls. They will report very different tail latencies for the same server. One of them is wrong in a way that has hidden real outages, and you will measure exactly how wrong, correct it, and finish by finding the saturation point, the knee, and the highest request rate that still meets a latency SLO.

Why this lab matters

Capacity decisions rest on load tests, and load tests rest on two things nobody checks: a model of how queues behave, and a generator that measures honestly. If either is off, a team will buy the wrong amount of hardware or, worse, promise a latency SLO it cannot keep. The formulas in chapter 8 are only worth quoting once you have seen a program you wrote reproduce them to within a percent or two. And the generator problem is not exotic. A closed-loop tool that waits for each reply before sending the next will, when the server stalls, politely stop sending. It then records one slow request where a real crowd of users would have recorded hundreds. Gil Tene named this coordinated omission: the measurement system and the system under test coordinate, without anyone intending it, to leave out the worst moments. By the end you will have seen the p99 of one stalling server reported as 40 ms and as nearly a second, from the same stalls, and you will know which number to put in front of a customer.

Simulated time: no sleeping, no sockets, no threads

Nothing in this lab ever waits for real. A simulation keeps its own clock, a number that jumps from one event to the next, so a run that models ten minutes of traffic takes a fraction of a second, and every run with the same seed gives the identical answer. Randomness comes from random.Random(seed) objects. The stalling server is a function that computes when a request would finish if the server freezes during given intervals. Standard library only, Python 3.8 or newer. The whole check runs in about five seconds. Statistical tests use fixed seeds and generous tolerances, so they cannot flake; when one fails it prints the seed so you can replay it with python3 check.py solution 4 3 (milestone 4, seed 3).

What you'll build

Five milestones, each building on the last:

  1. A discrete-event simulator: Poisson (or regular) arrivals, any service-time distribution, c servers, one FIFO queue, fully seeded, with the area under the number-in-system curve recorded.

Milestone 1: a discrete-event simulator

A discrete-event simulation does not step time forward in small ticks. It keeps a list of things that will happen, each with a time, and repeatedly jumps to the earliest one. A queue has only two kinds of event: an arrival (a new job shows up) and a departure (a server finishes a job). Between events nothing changes, so there is nothing to compute. This is why a simulator can model a million requests in about a second.

The state is small: a FIFO queue of waiting jobs, a count of busy servers, and the future events in a heap ordered by time. The rules are the ones in chapter 8. When a job arrives it starts at once if fewer than c servers are busy; otherwise it joins the back of the queue. When a job departs, its server takes the job at the front of the queue, if there is one. Arrivals schedule their successor: the next arrival comes one gap later, where the gap is exponential with mean 1/λ for a Poisson process, or exactly 1/λ for regular arrivals.

Two details make the simulator trustworthy rather than merely plausible:

  • Two random streams. Draw arrival gaps from one Random and service times from another, both derived from the seed. Then changing the service-time distribution does not change when jobs arrive. Comparing "constant" and "bursty" service on the same arrivals is a paired comparison, which is much less noisy than two unrelated runs. (The check asserts this property.)
  • Integrate N(t). Before you handle an event at time t, add (jobs in the system) × (t − time of the previous event) to a running area. That area is the integral of the number in the system over time. It is the L in Little's law, and you will need it in the next milestone.

Hints try without first
  • Keep the future events in a heapq of tuples (time, counter, kind, job). The counter is a tie-breaker, so two events at the same instant never make Python compare jobs.
  • You only need one pending arrival at a time: when an arrival is handled, schedule the next one, unless n_jobs have already been created.
  • A helper begin(job, t) that increments busy, sets job.start and job.finish = t + job.service, and pushes the departure event keeps both branches short.
  • The area update comes first, using the old state: area += (len(waiting) + busy) * (t - last). If you update the state first, the area is wrong by exactly one event.
  • Seeding: random.Random(seed * 2 + 1) for gaps and random.Random(seed * 2 + 2) for service times gives two independent, reproducible streams.

def simulate(lam: float, service: Callable[[random.Random], float], c: int, n_jobs: int, seed: int,
             arrivals: str = "poisson") -> Result:
    rng_a = random.Random(seed * 2 + 1)
    rng_s = random.Random(seed * 2 + 2)
    events, counter = [], 0
    jobs: List[Job] = []
    waiting = deque()
    busy = 0
    area, last = 0.0, 0.0
    now = 0.0

    def gap():
        return rng_a.expovariate(lam) if arrivals == "poisson" else 1.0 / lam

    def push(t, kind, job):
        nonlocal counter
        counter += 1
        heapq.heappush(events, (t, counter, kind, job))

    def begin(job, t):
        nonlocal busy
        busy += 1
        job.start = t
        job.finish = t + job.service
        push(job.finish, DEPARTURE, job)

    push(gap(), ARRIVAL, None)
    while events:
        t, _, kind, job = heapq.heappop(events)
        area += (len(waiting) + busy) * (t - last)
        last = now = t
        if kind == ARRIVAL:
            job = Job(arrival=t, service=service(rng_s))
            jobs.append(job)
            if busy < c:
                begin(job, t)
            else:
                waiting.append(job)
            if len(jobs) < n_jobs:
                push(t + gap(), ARRIVAL, None)
        else:
            busy -= 1
            if waiting:
                begin(waiting.popleft(), t)
    return Result(jobs, area, now)

Milestone 2: validate against the formulas, and Little's law

A simulator you cannot check is a random-number generator with opinions. The checks that matter are the closed-form results from chapter 8. For M/M/1 (Poisson arrivals at rate λ, exponential service at rate μ, one server) the mean time in the system is W = 1/(μ − λ). For M/M/c, with offered load a = λ/μ measured in "servers' worth" of work, the probability that an arriving job finds every server busy and must wait is the Erlang C function C(c, a), and the mean wait in the queue is Wq = C(c, a)/(cμ − λ). Add the job's own service time 1/μ to get the time in system.

Erlang C has factorials, which overflow for large c if you compute them naively (500! is far beyond a float). The trick is to build the terms ak/k! incrementally, multiplying the previous term by a/k. That also makes the code short: one loop for the sum, one extra step for the "all c busy" term, stretched by c/(c − a).

Little's law (John Little, 1961) says L = λW: the average number of jobs in a stable system equals their arrival rate times the average time each spends there. It needs no assumptions about arrival or service distributions, which is why it is so useful and why it makes a perfect test: your simulator measures L (area under N(t), divided by time) and W (the average of finish − arrival) separately, so if the event loop has a bookkeeping bug, they will disagree. For a run that is allowed to drain completely, the two sides are equal exactly, up to rounding.

Hints try without first
  • mm1_sojourn is one line. The point of raising on lam >= mu is that an unstable queue has no steady state: the formula would happily return a negative time.
  • For erlang_c: term = 1.0, then for k in 0..c-1 add term to total and set term *= a / (k + 1). After the loop term is ac/c!. The “all busy” weight is term * c / (c - a), and C is that divided by total plus that.
  • Sanity-check by hand: with one server, C(1, a) must equal a (the chance of waiting equals the utilisation). Run it before you run the check.
  • littles_law: L is res.area / res.horizon; the arrival rate is len(res.jobs) / res.horizon; W is the mean of finish - arrival over all jobs (no warm-up trimming here, or the equality stops being exact).
  • If L and λW disagree in milestone 2 but the formulas are right, the bug is in milestone 1's area bookkeeping. This is exactly the bug the test exists to find.
Solution spoiler 
def mm1_sojourn(lam: float, mu: float) -> float:
    if lam >= mu:
        raise ValueError("unstable: lam >= mu")
    return 1.0 / (mu - lam)

def erlang_c(c: int, a: float) -> float:
    if a >= c:
        raise ValueError("unstable: a >= c")
    term, total = 1.0, 0.0
    for k in range(c):
        total += term
        term *= a / (k + 1)
    top = term * c / (c - a)
    return top / (total + top)

def mmc_wait(lam: float, mu: float, c: int) -> float:
    return erlang_c(c, lam / mu) / (c * mu - lam)

def littles_law(res: Result) -> Tuple[float, float]:
    n = len(res.jobs)
    L = res.area / res.horizon
    W = sum(j.sojourn for j in res.jobs) / n
    return L, (n / res.horizon) * W

Milestone 3: Kingman, variability multiplies the wait

Chapter 8's central point is that the average load decides whether a queue is stable, while variability decides how long the waits are. Kingman's formula (J. F. C. Kingman, 1961) puts the two together for a single server with any arrival and service pattern:

Wq ≈ ( ρ / (1 − ρ) ) × ( (ca² + cs²) / 2 ) × τ

Here τ is the mean service time, and ca², cs² are the squared coefficients of variation (standard deviation squared, over mean squared) of the inter-arrival and service times. A constant has c² = 0, an exponential has 1, and a "mostly short, sometimes very long" mix can have 4 or more. The given make_service offers four: "det" (c² = 0), "erlang2" (0.5), "exp" (1) and "hyper4" (4). With Poisson arrivals (ca² = 1) and general service the formula is exact: it is the Pollaczek-Khinchine result.

Your job is to run the experiment the formula describes: fix ρ, change only the service-time distribution, and watch the wait scale with (1 + cs²)/2. Because the simulator uses separate random streams, the arrivals are identical across the four runs, so you are seeing the effect of variability and nothing else.

Solution spoiler 
def kingman_wq(rho: float, ca2: float, cs2: float, tau: float) -> float:
    return (rho / (1.0 - rho)) * ((ca2 + cs2) / 2.0) * tau

def kingman_table(rho: float, kinds: List[str], tau: float = 1.0, n_jobs: int = 60000,
                  seeds: Tuple[int, ...] = (1, 2, 3), arrivals: str = "poisson"):
    ca2 = 1.0 if arrivals == "poisson" else 0.0
    rows = []
    for kind in kinds:
        service = make_service(kind, tau)
        waits = [simulate(rho / tau, service, 1, n_jobs, s, arrivals).stats()[0] for s in seeds]
        rows.append((kind, CS2[kind], sum(waits) / len(waits), kingman_wq(rho, ca2, CS2[kind], tau)))
    return rows

Milestone 4: two load generators, and coordinated omission

Now use the machinery on a different question: how should you measure a server's latency? Chapter 8 ended with the distinction between open and closed systems, and chapter 10 turns it into rules. Recap in two sentences. In an open system arrivals are independent of how the server is doing: web users do not know your queue is long. In a closed system there is a fixed population of clients, each of which sends a request, waits for the reply, thinks, and sends again, so a slow server automatically slows the arrivals down.

A typical load-testing tool is closed by construction: N threads, each in a loop of "send, wait for response, record the time". That is a fine model of a batch job with 32 workers. It is a poor model of the public internet, and it has a nasty failure mode. Suppose the server freezes for a second (a garbage-collection pause, a failover, a lock held too long). A closed-loop thread that happened to be waiting now waits one second, records one slow request, and, because it was waiting, did not send the dozens of requests it would otherwise have sent during that second. Real users would have kept arriving, and every one of them would have waited. The generator's own politeness removed them from the measurement. That is coordinated omission.

The cure is to measure from the intended send time. An open-loop generator fixes the schedule in advance, sending request i at time i/rate whether or not earlier responses have returned, and defines latency as completion time minus intended send time. If the previous request was stuck and the generator could not actually send on time, the delay counts against the server, exactly as it would for a real user who arrived on schedule. (Gil Tene's wrk2 and HdrHistogram's "expected interval" correction exist for precisely this reason.)

If you are stuck with a closed-loop tool, there is a statistical patch. If the generator was supposed to send every interval seconds and recorded a latency L much larger than that, it skipped about L/interval requests, and those would have waited L − interval, L − 2·interval, and so on down to zero. Add those synthetic samples back. That is co_correct. It is a patch, not a cure: it assumes the skipped requests would have queued up behind the stall at a steady pace. It restores the tail percentiles, but does not rebuild the middle of the distribution, as you will see in the results.

The server for this experiment is given: StallingServer is a single FIFO server with 5 ms mean service time (capacity 200 requests per second) whose clock stops during stalls, and make_stalls schedules one stall of one second at a random spot in every 10-second block. Its serve(sent_at) returns when the request completes. Requests must be offered in the order they are sent, which is what makes a heap of pending sends the natural way to run N closed-loop users.

Hints try without first
  • Nearest-rank percentile: sort a copy, then the element at 1-based rank ceil(p / 100 * n) (clamp to at least 1). Do not interpolate.
  • run_open needs no heap. Requests are sent in order, at i / rate, and server.serve(t) gives the completion time; the latency is done - t where t is the intended time. That one subtraction is the whole idea.
  • run_closed: a heap of (next_send_time, user), started at random times in [0, think). Pop the earliest, done = server.serve(t), record done - t, and push the user's next send at done + rng.expovariate(1 / think) (or at done if think is 0). Stop when the popped time is at or past duration.

Solution spoiler 
def percentile(xs: List[float], p: float) -> float:
    s = sorted(xs)
    k = max(1, math.ceil(p / 100.0 * len(s)))
    return s[k - 1]

def run_closed(server: StallingServer, users: int, think: float, duration: float, seed: int = 1) -> List[float]:
    rng = random.Random(seed * 31 + 7)
    heap = [(rng.uniform(0.0, think), u) for u in range(users)]
    heapq.heapify(heap)
    out = []
    while heap:
        t, u = heapq.heappop(heap)
        if t >= duration:
            break
        done = server.serve(t)
        out.append(done - t)
        heapq.heappush(heap, (done + rng.expovariate(1.0 / think) if think > 0 else done, u))
    return out

def run_open(server: StallingServer, rate: float, duration: float) -> List[float]:
    n = int(duration * rate)
    out = []
    for i in range(n):
        t = i / rate
        out.append(server.serve(t) - t)
    return out

def co_correct(latencies: List[float], expected_interval: float) -> List[float]:
    out = list(latencies)
    for lat in latencies:
        v = lat - expected_interval
        while v > 0:
            out.append(v)
            v -= expected_interval
    return out

Two lessons follow, and the second is subtler. First, the closed loop's p99 is not "a little optimistic": it is 25 times too low, because the one place where the server is really bad is the one place the generator stops looking. Second, the correction recovers the p99 and p99.9 (within 6% here) but the p90 is still far off. The correction knows only that requests were skipped; it does not know the queue that built up behind the stall, which also slowed requests after the stall ended. Fixing the measurement at the source, by sending on an open schedule and timing from the intended moment, gets the whole distribution right.

Do not forget which question you are asking

A closed loop is not "wrong"; it answers a different question: how fast can N workers push work through, and what do they experience? For a 32-thread batch job that is exactly the right model. It becomes wrong when the thing you are modelling is independent users arriving at their own pace, as for a public API, and you are quoting percentiles to an SLO. Match the generator to the traffic source, say which one you used, and when in doubt use the open loop with intended-time latency.

Milestone 5: the saturation point, the knee, and the SLO

With an honest generator you can answer the question capacity planning actually asks: how much load can this service take? Three different answers hide in that question, and chapter 10 separates them.

  • The saturation point is the throughput at which the bottleneck is never idle. For this server it is 1/(mean service time) = 200 requests per second in the stalling experiment, or 100 per second for the 10 ms server below. Push harder and the extra work only lengthens the queue. You find it with a closed loop: with enough users and no think time, the server is always busy and the measured throughput is its capacity.
  • The knee is where latency stops being flat and starts to climb steeply, typically around 60 to 80% of saturation. It is a property of the curve's shape, so you find it by sweeping the arrival rate and looking for the bend.
  • The maximum rate under an SLO is the number you can promise: the highest arrival rate at which the p99 (or whatever percentile the SLO names) is still within the objective. It always sits below saturation, usually at or a little above the knee. For an exponential single-server queue it has a closed form, since the time in system is exponential with rate μ − λ and p99 = ln(100)/(μ − λ): the SLO of 200 ms with μ = 100 per second gives λ ≤ 100 − 23.0 = 77.0 per second. Your simulator should find that without being told the formula.

To find the knee without eyeballing, scale both axes to [0, 1], draw the straight line from the first point to the last, and take the point farthest from that line: the place where the curve has bent away from the chord by the most. It is a crude but robust version of the "kneedle" idea, and it works on any hockey stick. To find the SLO limit, note that p99 rises with the rate, so you can bisect: simulate at the middle of a range whose low end meets the SLO and whose high end does not, and keep the half that still straddles it. Twelve steps pin the answer to a fraction of a request per second. Use the same seed for every probe, so that the curve you are bisecting is smooth (a common-random-numbers trick).

def sweep(rates: List[float], service: Callable[[random.Random], float], c: int, n_jobs: int, seed: int):
    out = []
    for r in rates:
        s = simulate(r, service, c, n_jobs, seed).sojourns()
        out.append((r, percentile(s, 50), percentile(s, 99)))
    return out

def find_knee(points: List[Tuple[float, float]]) -> float:
    x0, y0 = points[0]
    x1, y1 = points[-1]
    best, best_d = points[0][0], -1.0
    for x, y in points:
        u = (x - x0) / (x1 - x0)
        v = (y - y0) / (y1 - y0)
        d = abs(u - v)          # distance from the diagonal, up to a constant factor
        if d > best_d:
            best, best_d = x, d
    return best

def max_rate_under_slo(slo: float, service: Callable[[random.Random], float], c: int, lo: float, hi: float,
                       n_jobs: int = 40000, seed: int = 1, steps: int = 12) -> float:
    for _ in range(steps):
        mid = (lo + hi) / 2.0
        p99 = percentile(simulate(mid, service, c, n_jobs, seed).sojourns(), 99)
        if p99 <= slo:
            lo = mid
        else:
            hi = mid
    return lo

def saturation_throughput(users: int, mean_service: float, duration: float = 60.0, seed: int = 1) -> float:
    server = StallingServer([], mean_service=mean_service, seed=seed)
    lats = run_closed(server, users, 0.0, duration, seed)
    return len(lats) / duration

Look under the hood

You have now built a small but real piece of performance engineering. The numbers above came from your own code, so it is worth reading them carefully once.

  • The simulator is the model, and the model is only as good as its inputs. Exponential service times and Poisson arrivals are convenient assumptions, not facts. Real service times have heavier tails, and real arrivals are bursty. Kingman tells you the direction of the error (more variability, more waiting) and a rough size.
  • Percentiles from a stalling server are about the stalls. The p50 barely changed across the three measurements (5 to 7 ms). A dashboard that shows only averages or medians would have called the server perfectly healthy while one request in five was waiting hundreds of milliseconds. Chapter 4's warning about averaging percentiles has a sibling here: do not trust a percentile without knowing how the samples were collected.
  • The SLO limit is far below saturation. The server saturates at 100 requests per second but can only be promised 77 under a 200 ms p99, and 54 under 100 ms. The remaining capacity is not wasted; it is the headroom that absorbs variability. Chapter 10's headroom rules are this table.

  5. Cheat on purpose. A generator that intends 100 requests/s but cannot send the next one until the previous reply arrives, and then measures from when it actually sent: 
    from solution import *

def paced_closed(server, rate, duration):
    """One sender that INTENDS `rate` requests/s but waits for each reply before the next send."""
    interval, t_free = 1.0 / rate, 0.0
    from_actual, from_intended = [], []
    for i in range(int(duration * rate)):
        intended = i * interval
        sent = max(intended, t_free)              # late if the previous reply was late
        done = server.serve(sent)
        t_free = done
        from_actual.append(done - sent)
        from_intended.append(done - intended)
    return from_actual, from_intended

dur = 200.0
stalls = make_stalls(1, dur)
actual, intended = paced_closed(StallingServer(stalls, 0.005, 1), 100.0, dur)
print(f"measured from the actual send time:   p99 {percentile(actual, 99) * 1000:6.0f} ms")
print(f"measured from the intended send time: p99 {percentile(intended, 99) * 1000:6.0f} ms")
    $ python3 exp_cheat.py
measured from the actual send time:   p99     24 ms
measured from the intended send time: p99    964 ms
    The server and the stalls are identical. One line, done - sent against done - intended, is the difference between "p99 is fine" and "p99 is nearly a second". This is how coordinated omission usually appears in the wild: not as a design decision, but as a timestamp taken in the wrong place.

Distributed systems connection

A distributed system is a network of queues, and each hop is a place where the formulas of this lab apply. A request that fans out to many backends (chapter 9) waits for the slowest, so each backend's p99 becomes the caller's median; a stall that a closed-loop test would hide on one machine is multiplied by the fan-out. Measurement is distributed too: the load generator is a client in the system, with its own queueing, its own clock and its own habit of waiting for replies, and a latency that is "measured" by that client is a claim about the client as much as the server. When several generators run on several machines, the intended-send-time idea needs a shared schedule, which is why serious tools fix it in advance. And the SLO arithmetic of chapter 2 is only as good as the percentile it is computed from.

What you learned

  • A discrete-event simulator is a heap of future events, a queue and a count of busy servers. It jumps from event to event, runs a million jobs in a second, and is exactly reproducible given a seed. Separate random streams for arrivals and service make comparisons paired.
  • You validate a simulator against theory before you trust it: M/M/1 (W = 1/(μ − λ)), Erlang C for M/M/c, and Little's law, which needs no assumptions and so catches bookkeeping bugs. High-utilisation estimates converge slowly, so run long and average seeds.
  • Kingman's formula multiplies a utilisation factor, a variability factor (ca² + cs²)/2 and the service time. At fixed ρ the wait scales with variability: constant, exponential and highly variable service wait 2, 4 and 10 service times at ρ = 0.8.
  • A closed-loop generator waits for replies, so a stalled server stops it from sending the requests that would have suffered. It reports a p99 that was 25 times too low in our test. That is coordinated omission.
  • The cure is an open-loop generator that fixes the send schedule in advance and times each request from its intended send time. If you must use a closed loop, add back the omitted samples, which restores the tail but not the middle of the distribution.
  • Saturation (the bottleneck never idles), the knee (where the curve bends) and the maximum rate under an SLO (the number you can promise) are three different points, and the last sits well below the first. Bisection on a seeded sweep finds it without a formula.

Check your understanding

A tool runs 50 threads that each send a request, wait for the reply, record the latency, and send again. The server freezes for 2 seconds. What does the tool record, and why is it a problem?

  1. Thousands of 2-second latencies, one per user who would have arrived; this is correct
  2. Nothing, because the tool crashes when the server stops responding
  3. At most 50 slow latencies, because every thread is stuck in its one request; the many requests real users would have sent during the freeze are never sent or timed, so the tail is understated
  4. Exactly the same percentiles as without the freeze, because the average load is unchanged
A thread that is waiting cannot send. During the freeze the tool generates almost no requests, and the ones it does generate (at most one per thread) are the only slow samples. Real users arrive independently of the server's state and would each have waited. This under-reporting of the tail is coordinated omission.

Which change makes a load generator immune to coordinated omission?

  1. Send requests on a fixed schedule decided in advance and measure each latency from its intended send time
  2. Use more threads, so more requests are in flight
  3. Report the mean instead of the 99th percentile
  4. Add think time between requests
Measuring from the intended time charges the server for any delay, whether it happened before or after the request could be sent. More threads only reduce the effect of one stall, and think time makes the loop even more closed. Means hide tails even better.

At utilisation ρ = 0.8, a server whose service times are exponential has a mean wait of 4 service times. If the same server's service times become highly variable (squared coefficient of variation 4) with the same mean and arrival rate, Kingman's formula predicts a mean wait of about:

  1. 4 service times; the mean service time is unchanged, so nothing changes
  2. 2 service times, because the variability in the formula appears in the denominator
  3. 8 service times
  4. 10 service times
Kingman: (ρ/(1 − ρ)) × ((ca² + cs²)/2) × τ = 4 × ((1 + 4)/2) × τ = 10 τ. The utilisation is unchanged, but the variability factor goes from 1 to 2.5, which is why reducing variability (capping job sizes, separating big and small jobs) can be worth as much as adding capacity.

A single server saturates at 100 requests/s. An SLO says p99 <= 200 ms and the service times are exponential (10 ms mean). Roughly what is the highest rate you can promise?

  1. 100 requests/s: the server can do it
  2. About 77 requests/s, because at that rate the time in system is exponential with rate μ − λ and p99 = ln(100)/(μ − λ) = 0.2 s
  3. About 20 requests/s, one fifth of capacity
  4. About 50 requests/s, because every system should run at half its capacity
p99 of an exponential with rate μ − λ is ln(100)/(μ − λ). Setting it to 0.2 s gives μ − λ = 23, so λ = 77. The simulator-based bisection in milestone 5 finds the same number. The limit depends on the SLO and on the service-time distribution; there is no universal fraction.

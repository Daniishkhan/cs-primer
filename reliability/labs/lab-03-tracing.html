Lab 3: Tracing from Scratch

Chapter 6 ended with a forty-line toy tracer. In this lab you build the real machinery behind it, piece by piece, on simulated services and simulated time. You will generate trace and span ids and nest spans, carry a request's identity across service calls in a W3C traceparent header (and see exactly how one dropped header splits a trace in two), follow a request through a queue with span links, rebuild trace trees from spans that arrive out of order from many services with some of them missing, find a trace's critical path, and finally compare head sampling with tail sampling at the same storage budget to see which one keeps the failures.

Why this lab matters

Tracing is the signal that answers "this one request was slow; where?", and every part of it is a place where a trace can silently go wrong. One service that does not forward a header turns a request into two unrelated half-traces. A queue turns a parent-child relationship into something that is not a parent-child relationship at all. A collector that receives spans in random order, and sometimes not at all, still has to show a coherent tree and say honestly when it is not sure. And the sampler decides, before anyone knows whether the request was interesting, which traces will exist. Each of these is a few lines of code and a large amount of reasoning; writing them once, against a simulator where you can drop a header or lose a span on purpose, is how the reasoning sticks.

Services as functions, time as a number

Nothing here opens a socket or starts a thread. A "service call" is a Python function call that carries a dict of headers, so the propagation code you write is exactly what a real tracer does at a process boundary. Time is a number of milliseconds on a SimClock that moves only when code advances it. A parallel fan-out is simulated by running each branch from the same start time and continuing from the latest finish. All randomness (ids, queue delays, the order in which a collector hears about spans) comes from seeded generators, so a given seed always produces the same trace, and when a check names a seed you can replay it.

What you'll build

  1. Ids and spans: random, never-zero hexadecimal trace and span ids, spans that nest through an ambient context, and a tracer that stamps start and end from the simulated clock, marks failures and respects the sampled flag.
  2. Context propagation: generating, parsing and validating the W3C traceparent header, and injecting and extracting it across simulated service calls.
  3. Queues and links: producer and consumer spans, the same message modelled as a child and as a link, retries, and one span that links to a batch of messages from different traces.
  4. Assembling trees: grouping spans that arrive in any order, from many services, duplicated or lost, into trees, with placeholders for missing parents.
  5. Critical path and sampling: the chain of spans that determines a trace's duration, and a head sampler against a tail sampler at the same budget.

Milestone 1: ids and parent/child spans on simulated time

A trace is a tree of spans, and the tree is reconstructed purely from three kinds of identifier: every span in a trace shares the trace id, every span has its own span id, and every non-root span carries its parent's span id (chapter 6). Nothing else is needed, which is why the tree can be rebuilt later, from pieces, by something that never saw the request. So the first job is making identifiers well.

The W3C format fixes their shape: a trace id is 128 bits written as 32 lowercase hexadecimal characters, a span id is 64 bits as 16, and an all-zero value is invalid in both (it is reserved to mean "none"). The ids should be random enough that collisions never happen within the system's lifetime and that a hash of the id is a fair coin, which sampling (milestone 5) relies on. A seeded generator gives you the randomness and the ability to replay a run.

The tracer's next job is the ambient context. Within a process, a span's parent is almost always "whichever span is currently open", and forcing every function to pass it as a parameter would make instrumentation unusable, so tracers keep a stack of open spans (in a real tracer it lives in thread-local or task-local storage; chapter 6 calls this the other half of propagation). A with tracer.span("name") block starts a span, pushes it, and on the way out pops and finishes it, even if the block raised an exception, in which case the span ends with status error and the exception continues on its way. Finally, the head-sampling decision is made once, at the root, by a sampler function; every descendant inherits the flag, and spans whose flag is false are never exported.

class IdGenerator:

    def __init__(self, rng):
        self.rng = rng

    def trace_id(self):
        """32 lowercase hex characters (128 bits), never all zeros."""
        while True:
            v = self.rng.getrandbits(128)
            if v:
                return f"{v:032x}"

    def span_id(self):
        """16 lowercase hex characters (64 bits), never all zeros."""
        while True:
            v = self.rng.getrandbits(64)
            if v:
                return f"{v:016x}"

def start_span(self, name, parent=None, kind="internal", links=(), attrs=None):
    parent = parent if parent is not None else self.current()
    if parent is None:
        trace_id = self.ids.trace_id()
        parent_id, sampled = None, bool(self.sampler(trace_id))
    else:
        trace_id, parent_id, sampled = parent.trace_id, parent.span_id, parent.sampled
    return Span(trace_id, self.ids.span_id(), parent_id, self.service, name, self.clock.now,
                kind=kind, sampled=sampled, attrs=dict(attrs or {}), links=list(links))

def finish(self, span, status=None):
    if span.end is not None:
        raise ValueError("span already ended")
    span.end = self.clock.now
    if status is not None:
        span.status = status
    if span.sampled:
        self.sink.append(span)

@contextmanager
def span(self, name, parent=None, kind="internal", links=(), attrs=None):
    s = self.start_span(name, parent, kind, links, attrs)
    self.stack.append(s)
    try:
        yield s
    except BaseException:
        self.stack.pop()
        self.finish(s, "error")
        raise
    self.stack.pop()
    self.finish(s)

Milestone 2: context propagation with W3C traceparent

Inside one process the stack does the job. Across processes the context has to be serialised into the request. For years every tracing system invented its own header; the W3C Trace Context recommendation replaced them with one, traceparent: version-trace_id-parent_id-flags, four lowercase-hex fields joined by dashes, 55 characters in version 00 (chapter 6 draws it).

Two roles meet at the header. The sender, about to make a call, makes a client span and writes that span's context into the request: the receiver's parent will be the client span, not whatever span happened to be open higher up. The receiver parses the header, creates its own server span as a child of the parsed context (same trace id, new span id, parent_id = the header's parent-id), and uses that span's context for any calls it makes in turn. The sampled bit is the lowest bit of the flags byte, tested with a mask, because the other seven bits are reserved and a future flag must not break today's parser.

A parser sits on an untrusted boundary, so it must be strict and must never crash. The rules the check enforces: exactly 55 characters for version 00 (no trailing data), lowercase hex only, no all-zero ids, version ff invalid, and a more forgiving rule for versions above 00: a future version may append more fields, but only after a dash following the four known ones. A header that fails any rule yields None, and the receiver simply starts a fresh trace; losing a trace is better than joining the wrong one.

def format_traceparent(ctx):
    return f"00-{ctx.trace_id}-{ctx.span_id}-{'01' if ctx.sampled else '00'}"

def parse_traceparent(header):
    if not isinstance(header, str):
        return None
    h = header.strip(" \t")
    if len(h) < 55:
        return None
    parts = h[:55].split("-")
    if len(parts) != 4:
        return None
    ver, tid, pid, flags = parts
    hexd = set("0123456789abcdef")
    for field_, n in ((ver, 2), (tid, 32), (pid, 16), (flags, 2)):
        if len(field_) != n or any(c not in hexd for c in field_):
            return None
    if ver == "ff" or tid == "0" * 32 or pid == "0" * 16:
        return None
    if ver == "00":
        if len(h) != 55:
            return None
    elif len(h) > 55 and h[55] != "-":
        return None
    return SpanContext(tid, pid, bool(int(flags, 16) & 1))

def inject(headers, ctx):
    headers["traceparent"] = format_traceparent(ctx)

def extract(headers):
    for k, v in headers.items():
        if k.lower() == "traceparent":
            return parse_traceparent(v)
    return None

Milestone 3: async propagation through a queue, with span links

A synchronous call has a clean shape: the caller waits and the callee's work nests inside the caller's span. A queue breaks that. After publish returns, the producer's span is over; the consumer's work happens later (here a few hundred milliseconds, in production maybe seconds or hours), perhaps in a batch, perhaps retried several times. Chapter 6 describes two representations and says neither is wrong; the lab makes you build both and see what each costs.

The carrier is the same as for HTTP: message headers. The producer makes a publish span, writes its context into the message headers, and the consumer extracts it. What the consumer does with the extracted context is the choice:

  • As a child. Same trace, parent is the publish span. The waterfall of the request now includes the queue wait as a long gap before the consumer's span, which is informative, and works well for one message to one consumer. The price is that the trace's duration is no longer "how long did the user wait": it includes everything that happened downstream, however much later.
  • As a new trace with a link. The consumer starts its own trace and records a link to the producer's span context. A link is a reference that is not a parent. It fits where a tree is the wrong shape: a retry hours later (a new trace per attempt, each linking to the same publish span), or a consumer that processes a batch of 100 messages from 100 different requests (one span with 100 links). Each trace keeps a meaningful duration.

def publish(world, tracer, queue, body):
    with tracer.span("publish orders", kind="producer") as ps:
        headers = {}
        inject(headers, ps.context())
        queue.put(headers, body)
        world.clock.advance(1)
    return ps

def consume_as_child(world, tracer, msg, work_ms=20):
    world.clock.advance_to(msg.deliver_at)
    with tracer.span("process orders", parent=extract(msg.headers), kind="consumer",
                     attrs={"attempt": msg.attempt}) as s:
        world.clock.advance(work_ms)
    return s

def consume_linked(world, tracer, msg, work_ms=20, fail=False):
    world.clock.advance_to(msg.deliver_at)
    ctx = extract(msg.headers)
    s = None
    try:
        # parent=None would fall back to the ambient span; the consumer has none, so this is a root
        with tracer.span("process orders", kind="consumer", links=[ctx] if ctx else [],
                         attrs={"attempt": msg.attempt}) as s:
            world.clock.advance(work_ms)
            if fail:
                raise RuntimeError("downstream unavailable")
    except RuntimeError:
        pass
    return s

def consume_batch(world, tracer, msgs, work_ms=40):
    world.clock.advance_to(max(m.deliver_at for m in msgs))
    links = [c for c in (extract(m.headers) for m in msgs) if c is not None]
    with tracer.span("process orders batch", kind="consumer", links=links, attrs={"batch_size": len(msgs)}) as s:
        world.clock.advance(work_ms)
    return s

Milestone 4: assembling trace trees from out-of-order spans

So far every span was exported in the order it finished, in one list. Production is nothing like that. Each service batches its spans and ships them after a lag of its own, over a network that reorders them; two services may ship a trace's spans minutes apart; an exporter that retries delivers some spans twice; and some spans never arrive at all. The collector therefore sees a stream of spans from thousands of traces interleaved, children before parents, and has to turn it into trees without knowing in advance what shape a trace has or whether it is complete.

The algorithm is a group-and-link. Group the spans by trace id (deduplicating by span id). Index them by span id. For each span, if its parent id is None it is a root; if its parent was received, attach it as that parent's child; if its parent id is set but the parent was not received, the tree has a hole, and the honest representation is a placeholder: a node standing in for the missing span, with the orphans as its children, flagged so the UI can draw it dashed and say "incomplete". Sort children by start time so that the output does not depend on the arrival order, which the check verifies against 25 random orders.

There is one honest limit, and the check states it. A tree can detect a missing interior span, because a surviving child names it. It cannot detect a missing leaf: no surviving span refers to it, so the trace looks complete, merely shorter than it should be. This is why completeness in tracing is a statistical property of the pipeline (the fraction of expected spans that arrive, measured by counters at the exporters) as much as a property of any one trace.

def assemble(spans):
    by_trace = {}
    for sp in spans:
        d = by_trace.setdefault(sp.trace_id, {})
        old = d.get(sp.span_id)
        if old is None or (old.end is None and sp.end is not None):
            d[sp.span_id] = sp
    out = {}
    for tid, d in by_trace.items():
        nodes = {sid: Node(sid, sp) for sid, sp in d.items()}
        roots, holes = [], {}
        for sid, sp in d.items():
            if sp.parent_id is None:
                roots.append(nodes[sid])
            elif sp.parent_id in nodes:
                nodes[sp.parent_id].children.append(nodes[sid])
            else:
                holes.setdefault(sp.parent_id, Node(sp.parent_id, None)).children.append(nodes[sid])
        key = lambda n: (n.span.start, n.span_id)
        for n in list(nodes.values()) + list(holes.values()):
            n.children.sort(key=key)
        roots.sort(key=key)
        out[tid] = Tree(tid, roots + [holes[k] for k in sorted(holes)], len(d), set(holes))
    return out

Milestone 5: the critical path, and head versus tail sampling

The critical path

A trace answers "where did the time go?" with a waterfall, but the longest bar is not necessarily the one to fix. The request in chapter 6 calls inventory and pricing in parallel; making inventory twice as fast changes nothing, because the request waits for pricing anyway. The critical path is the chain of spans that determines the total: walk backwards from the end of the root, at each point take the child that finished last, continue from that child's start, and recurse. Everything off the path has slack. A span's self time is its duration minus the time covered by its on-path children, which is the part that only this span can shorten; the self times along the path add up exactly to the trace duration.

Sampling

Tracing every request is usually too expensive, so a sampler decides which traces to keep. Head sampling decides at the root, before anything is known about the request, from a draw that every service can reproduce: here a number derived from the trace id, so all services agree and the kept traces are complete (independent per-service coin flips at 5% would give a complete six-span trace one time in 64 million). It is stateless and free, and it keeps errors at exactly the rate it keeps everything else. Tail sampling sends every span to a collector, buffers each trace until it has been quiet for a while, and then decides with full knowledge: keep every trace with an error, keep every slow one, keep a small random baseline of the rest. It costs memory (traces in flight are roughly arrival rate times wait, by Little's law) and a stateful routing tier, and it buys the property you wanted tracing for: the failures are there.

To compare them fairly the lab fixes a storage budget (5% of the traces) and gives each sampler the same number of stored traces. The head sampler uses a rate of 5%. The tail sampler keeps all the errors and slow traces and tops up to the budget with a baseline rate you compute from the budget, the traffic and the number of interesting traces, which in production you would know from your metrics (Lab 2).

TailSampler (buffering, quiet period, peak measurement) is given and calls your tail_decision.

  • critical_path: sort the children by end time, latest first; keep a child if child.end <= t and then set t = child.start. A child that ends after t overlaps one you have taken (or outlives its parent) and is off the path. Sort the kept children by start before recursing so the output is chronological.
  • Self time = the span's duration minus the durations of the kept children.
  • head_keep: the low 64 bits are the last 16 hex characters; divide by 2**64 and compare with the rate.
  • tail_decision is an if ladder with the priority error, then slow, then baseline. "Slow" is strictly greater than the threshold.
Solution spoiler 
def critical_path(node):
    s = node.span
    t, chain = s.end, []
    for c in sorted(node.children, key=lambda c: (c.span.end, c.span.start), reverse=True):
        if c.span.end <= t + 1e-9:
            chain.append(c)
            t = c.span.start
    chain.sort(key=lambda c: c.span.start)
    out = [(s, s.duration - sum(c.span.duration for c in chain))]
    for c in chain:
        out += critical_path(c)
    return out

def head_keep(trace_id, rate):
    return int(trace_id[16:], 16) / 2 ** 64 < rate

def tail_decision(spans, slow_ms, baseline_rate):
    if any(s.status == "error" for s in spans):
        return "error"
    if trace_duration(spans) > slow_ms:
        return "slow"
    if head_keep(spans[0].trace_id, baseline_rate):
        return "baseline"
    return None

def baseline_rate(budget, total, interesting):
    if total <= interesting:
        return 0.0
    return min(1.0, max(0.0, (budget - interesting) / (total - interesting)))

Reliability connection

This lab is chapter 6 made executable, and it is the third leg of the course's observability trio: metrics tell you that something is wrong cheaply and in aggregate, logs keep per-event detail in one service, and traces join the per-request detail across services. The sampling comparison is the quantitative reason chapter 6 recommends tail rules on top of modest head sampling. The distributed-systems ideas underneath are old ones in a new place: the trace id is a correlation id that must survive every hop (and, like a fencing token, only works if every layer forwards it), and a collector assembling trees from reordered, duplicated and lost messages faces the same problems as any stream processor, which is why the architecture course's treatment of synchronous and asynchronous calls describes the shape tracing has to follow.

What you learned

  • A trace is rebuilt from three identifiers: a shared trace id, a span id per span and each span's parent id. Ids are random, fixed-width lowercase hex and never all zero.
  • Within a process the ambient context (a stack) supplies the parent; across processes it travels in a traceparent header. The sender injects its client span's context; the receiver makes a child of what it parsed. A strict parser returns None on garbage and the receiver starts a new trace; one hop that drops the header splits the trace in two.
  • The sampled decision is made once at the root and rides in the flags byte; the flag is a bit to be masked, not a number to be compared.
  • A queue is not a call. Model the consumer as a child (one long trace including the wait) or as a new trace with a link back (short traces; one span can link to many); never pretend the wait is part of the user's latency.
  • A collector sees spans late, reordered, duplicated and missing. Group by trace id, deduplicate by span id, link by parent id, and put a placeholder where a parent is missing. A missing leaf cannot be detected from the tree.
  • The critical path is the chain that determines the duration; its self times add up to the trace duration, and only spans on it are worth optimising.
  • At the same storage budget, head sampling keeps errors at the sample rate and tail sampling keeps all of them, paying with memory proportional to arrival rate times wait and a stateful collector tier. Baseline traces stay as an unbiased sample for what "normal" looks like.

Check your understanding

A client span in service A calls service B. What should A write in the parent-id field of the outgoing traceparent?

  1. The root span's id, so every service points at the root
  2. The span id of A's client span for this call: B's server span becomes its child
  3. A fresh random id
  4. B's span id, once B has started
The parent-id names the span that caused the receiver's work, which is the caller's client span. B then creates its own span id and records the header's parent-id as its parent; its own outgoing calls carry B's client span ids.

A request arrives with traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-03. What does a correct parser conclude about sampling, and what does ...-02 mean?

  1. 03 is sampled; 02 is sampled too, since it is non-zero
  2. 03 is not sampled because it is not equal to 01
  3. 03 is sampled (bit 0 is set); 02 is not (only reserved bits are set)
  4. Both are invalid because flags must be 00 or 01
The sampled flag is the lowest bit, tested with a mask. The other bits are reserved for future use and must not change today's meaning. Comparing with == 1 would wrongly treat 03 as unsampled.

A consumer processes one message from a queue three hours after it was published (a retry). Why is a new trace with a span link usually better than making the consumer a child of the producer's span?

  1. The request's trace would otherwise include three hours of waiting, destroying its meaning as 'how long did this request take', and each attempt can link to the same publish span
  2. Links are cheaper to store than parents
  3. A child span cannot start after its parent ended
  4. Consumers cannot read headers
Both representations are valid. A child keeps one tree and shows the wait, but swamps the trace's own timeline for long delays, and it cannot express a batch of messages from many traces. A link keeps each trace's duration meaningful and generalises to fan-in.

A collector has received every span of a trace except one leaf (a cache lookup) and one interior span (a client call that had two children). Which loss can assemble detect?

  1. Both, because the span counts do not match
  2. The interior one: its children name a parent id that never arrived, so a placeholder fills the hole; the lost leaf is invisible because nothing refers to it
  3. Only the leaf
  4. Neither
Parent ids point upward. A missing span with surviving children leaves dangling references. A missing leaf leaves none, so the trace looks complete but shorter; completeness for leaves can only be estimated from exporter-side counters.

With a storage budget of 1,000 traces out of 20,000, 108 of which are errors, head sampling at 5% and tail sampling with a 2.5% baseline both store about 1,000 traces. What is the main difference in what they store?

  1. Tail sampling stores more traces
  2. Head sampling stores slower traces
  3. Tail sampling keeps every error and slow trace (the rest is a small unbiased sample); head sampling keeps about 5% of everything, so about 5 of the 108 errors
  4. There is no difference at the same budget
A head sampler decides before the outcome is known, so it keeps errors at the same rate as everything else. A tail sampler decides after, spending the same budget on the traces you will actually want to read; it pays in buffered memory (about arrival rate times wait) and in a stateful collector tier.

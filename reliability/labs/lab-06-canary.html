Lab 6: Automated Canary Analysis

Rolling a new build out slowly is only worth anything if something notices when the new build is worse. Chapter 12 described the judge: a program that compares a canary's metrics with a baseline and returns promote or roll back. In this lab you will build one from the ground up. You will generate seeded metrics with a latency regression, an error-rate regression and a slow memory leak; implement the Mann-Whitney U test in pure Python with a normal approximation and tie correction; turn each metric into pass, high or low with an effect-size threshold, so that a tiny but statistically real difference does not fail a deploy; combine the metrics into a weighted score and a decision; and measure how often it is wrong. Then you will run a multi-wave rollout against a daily traffic curve and see why comparing the canary against a concurrent baseline works, and comparing it against yesterday's data does not.

Why this lab matters

Every team that automates canary analysis meets the same two failures. The judge cries wolf, rolling back good builds for reasons that have nothing to do with the code, until people stop trusting it and start overriding it. Or the judge is too lenient, and a real regression sails through because the canary was too small, the bake too short, or the comparison was against the wrong thing. Both come from statistical details that are invisible in a diagram: which test, which threshold, how many samples, what reference. Writing the test yourself, and then measuring false rollbacks and missed regressions over hundreds of seeded deploys, turns those details into numbers. The last milestone shows the most common mistake of all, the choice of reference, in the most vivid way: a perfectly good build rolled back every afternoon, and a bad one promoted every night.

Synthetic metrics: no clock, no network, no flakiness

Every sample is drawn from a seeded random.Random, so the same seed produces the same deploy and the same verdict. Nothing waits and nothing leaves the process. Hundreds of deploys are judged in a fraction of a second. Standard library only, Python 3.8 or newer. The whole check takes about six seconds. Statistical checks use fixed seeds and generous tolerances; when one fails it prints the seed, and python3 check.py solution 4 2 replays milestone 4 on seed 2 only. The numbers are properties of the model (lognormal latency, binomial-like error counts, a linear leak, a sinusoidal day). The mechanism transfers; the exact rates do not.

What you'll build

  1. Seeded samples: baseline and canary data for latency, error rate and memory, with configurable regressions (a latency shift, extra errors, a leak) and a daily load factor.
  2. Mann-Whitney U: the rank-sum test in pure Python: average ranks for ties, U, the tie-corrected variance, a continuity correction and a two-sided p-value. Checked on known examples.
  3. Classification: pass, high or low per metric, requiring both a small p-value and an effect size above a threshold.
  4. Score and decision: a score + critical metrics, a promote or roll-back verdict, and the false-rollback and missed-regression rates over many seeded deploys.
  5. Waves and the baseline: a four-wave rollout that halts on a bad canary, and a comparison of a concurrent baseline with yesterday's data under a daily traffic pattern.

Milestone 1: seeded samples with configurable regressions

A judge needs data, and testing a judge needs data whose truth you control. A synthetic generator gives you that: you decide that the canary is 20% slower, and then measure whether the judge notices. Each analysis window has a baseline group and a canary group, with one sample per instance per minute: 30 minutes × 3 instances = 90 samples each. Three metrics, each with a different statistical character:

Latency (ms)
Positive and right-skewed, with a long tail. The generator draws lognormal samples with a median of 100 ms and log-spread 0.3. A regression is a relative shift of the median: 0.2 means 20% slower.
Error rate
A fraction between 0 and 1, usually tiny (0.1%). Each sample is the fraction of 2000 requests that failed in an instance-minute, which for so many requests is well approximated by a normal distribution around the true probability. A regression adds to the probability (0.002 is two tenths of a percentage point, a tripling).
Memory (MB)
Roughly constant around 800 MB with noise. A leak adds a fixed number of MB for every minute since the canary started, so it is invisible in the first minutes and unmistakable by the thirtieth. Samples are ordered by minute so that the time axis matters.

The generator also takes a load factor. Traffic is not constant: it follows the daily curve below, and busier means slower. The coupling is the given latency_factor(load): 60% of any change in load shows up in the typical latency. The baseline can run at a different load from the canary (baseline_load), which milestone 5 uses to model comparing against a reference from a different time.

def gen_latency(rng: random.Random, n: int, shift: float = 0.0, load: float = 1.0) -> List[float]:
    median = BASE_LATENCY_MS * (1.0 + shift) * latency_factor(load)
    return [rng.lognormvariate(math.log(median), LATENCY_SIGMA) for _ in range(n)]

def gen_errors(rng: random.Random, n: int, extra: float = 0.0, load: float = 1.0) -> List[float]:
    p = (BASE_ERROR + extra) * load
    sd = math.sqrt(p * (1.0 - p) / REQUESTS_PER_SAMPLE)
    return [max(0.0, rng.gauss(p, sd)) for _ in range(n)]

def gen_memory(rng: random.Random, minutes: int, instances: int, leak: float = 0.0) -> List[float]:
    return [BASE_MEMORY_MB + leak * m + rng.gauss(0.0, MEMORY_NOISE_MB) for m in range(minutes) for _ in range(instances)]

def generate(rng: random.Random, reg: Regression, minutes: int = 30, instances: int = 3,
             load: float = 1.0, baseline_load: Optional[float] = None) -> Dict[str, Tuple[List[float], List[float]]]:
    n = minutes * instances
    bl = load if baseline_load is None else baseline_load
    return {
        "latency_ms": (gen_latency(rng, n, 0.0, bl), gen_latency(rng, n, reg.latency, load)),
        "error_rate": (gen_errors(rng, n, 0.0, bl), gen_errors(rng, n, reg.errors, load)),
        "memory_mb": (gen_memory(rng, minutes, instances, 0.0), gen_memory(rng, minutes, instances, reg.leak)),
    }

Milestone 2: the Mann-Whitney U test

You have two groups of numbers and want to know whether the canary's tend to be higher or lower than the baseline's. Chapter 12 explains why not a t-test: latency is skewed and heavy-tailed, so a few huge values dominate a mean, and the assumptions of the test fail. The Mann-Whitney U test (also called the Wilcoxon rank-sum test) throws away the sizes and keeps only the order, which makes it robust and distribution-free. Netflix and Google's Kayenta uses this test in its default judge. The recipe:

  1. Pool and rank. Put all values from both groups in one list, sort it, and give each value its rank (1 for the smallest). Tied values share the average of the ranks they occupy: three values tied for places 4, 5 and 6 each get 5.
  2. Sum the canary's ranks, Rx. If the groups came from the same distribution, the canary's values would be scattered evenly among the ranks and Rx would be near nx(nx + ny + 1)/2.
  3. Convert to U: Ux = Rx − nx(nx + 1)/2. This counts the pairs (a canary value, a baseline value) where the canary value is larger, ties counting half. Its mean under "no difference" is nxny/2.
  4. Standardise. For samples beyond a handful, U is close to a normal distribution with variance nxny/12 × ((N + 1) − Σ(t³ − t)/(N(N − 1))), where N = nx + ny and t runs over the sizes of groups of tied values. The second term is the tie correction: ties make the ranks less spread out, so the variance is smaller. With no ties it vanishes. Move U half a unit towards the mean (the continuity correction, because U moves in steps) and divide by the standard deviation to get z.
  5. p-value. The two-sided p is the chance of a |z| at least that large: math.erfc(abs(z) / math.sqrt(2)). The sign of z tells you the direction: positive means the canary tends to be higher.

Hints try without first
  • Sort the indices: order = sorted(range(n), key=lambda i: values[i]). Then walk through order, extending j while the next value equals the current one. The tied block occupies 1-based ranks i+1 through j+1, whose average is (i + j) / 2 + 1. Record j - i + 1 as a tie size.
  • Rank the pooled list x + y, take the first len(x) ranks for Rx. U is Rx minus nx * (nx + 1) / 2.
  • Variance: nx * ny / 12 * ((n + 1) - sum(t**3 - t for t in ties) / (n * (n - 1))). If it is not positive, return (u, 0.0, 1.0).
  • Continuity correction: diff = u - nx * ny / 2; subtract 0.5 if diff > 0, add 0.5 if diff < 0, and leave it if zero. Then z = diff_corrected / sqrt(var).
  • math.erfc(abs(z) / math.sqrt(2)) is the two-sided normal tail. No scipy needed, and no table lookups.
  • If your U disagrees with the pair count, check the tied ranks first; if only z disagrees, it is almost always the tie term in the variance or the continuity correction.

def ranks_with_ties(values: List[float]) -> Tuple[List[float], List[int]]:
    order = sorted(range(len(values)), key=lambda i: values[i])
    ranks = [0.0] * len(values)
    ties = []
    i = 0
    while i < len(order):
        j = i
        while j + 1 < len(order) and values[order[j + 1]] == values[order[i]]:
            j += 1
        avg = (i + j) / 2.0 + 1.0
        for k in range(i, j + 1):
            ranks[order[k]] = avg
        ties.append(j - i + 1)
        i = j + 1
    return ranks, ties

def mann_whitney_u(x: List[float], y: List[float]) -> Tuple[float, float, float]:
    nx, ny = len(x), len(y)
    ranks, ties = ranks_with_ties(list(x) + list(y))
    u = sum(ranks[:nx]) - nx * (nx + 1) / 2.0
    n = nx + ny
    mean = nx * ny / 2.0
    var = nx * ny / 12.0 * ((n + 1) - sum(t ** 3 - t for t in ties) / (n * (n - 1)))
    if var <= 0.0:
        return u, 0.0, 1.0
    diff = u - mean
    cc = 0.5 if diff > 0 else (-0.5 if diff < 0 else 0.0)
    z = (diff - cc) / math.sqrt(var)
    return u, z, math.erfc(abs(z) / math.sqrt(2.0))

Milestone 3: pass, high or low, with an effect size

The rank-sum test answers one question: is there a difference? Given enough samples, the answer becomes yes for any real difference however small. A canary that is 3% slower, observed over 6000 samples per side, gives p < 0.001. Whether you care is a different question, and chapter 12 puts it plainly: "significant is not the same as important." A judge that rolls back for every statistically real but practically invisible difference will cry wolf all day, because real systems differ by small amounts for harmless reasons (a different instance type, a different warm-up state, a cache that happens to be fuller).

So the classification needs two conditions to flag a metric:

  1. Significance: p < α (the policy's alpha, here 0.01), from the rank-sum test.
  2. Effect size: the relative change of the median, (median(canary) − median(baseline)) / |median(baseline)|, is at least the metric's own min_effect in magnitude (10% for latency, 50% for error rate, 3% for memory). Divide by a floor when the baseline median is zero or near it, so a move from 0 to 1% errors counts as a huge effect and not as a division by zero.

If both hold, the label is "high" when the canary's values are higher (z > 0) and "low" when lower. Otherwise "pass". Whether "high" is bad depends on the metric (milestone 4): high latency is bad, high throughput is not, and a significant drop in latency is an improvement, not an alarm. The tolerance (min_effect) is a business decision. Chapter 12 suggests it belongs in the service's SLO: a latency budget that is nearly spent should tolerate less.

Hints try without first

  • effect_size is (median(canary) - mb) / max(abs(mb), floor) with mb = median(baseline).
  • classify: compute z and p from mann_whitney_u(canary, baseline) and the effect size. Flag only if p < alpha and abs(eff) >= min_effect. The label comes from the sign of z (or of the effect, which has the same sign here).
  • Take care with the argument order. If you swap baseline and canary, every 'high' becomes 'low' and the rollout in milestone 5 would promote the bad build.
  • Why the median and not the mean for the effect? For the same reason as the rank test: a few huge outliers should not decide the verdict.
Solution spoiler 
def median(xs: List[float]) -> float:
    s = sorted(xs)
    n = len(s)
    return s[n // 2] if n % 2 else (s[n // 2 - 1] + s[n // 2]) / 2.0

def effect_size(baseline: List[float], canary: List[float], floor: float) -> float:
    mb = median(baseline)
    return (median(canary) - mb) / max(abs(mb), floor)

def classify(baseline: List[float], canary: List[float], alpha: float, min_effect: float, floor: float = 1e-9) -> str:
    _, z, p = mann_whitney_u(canary, baseline)
    eff = effect_size(baseline, canary, floor)
    if p < alpha and abs(eff) >= min_effect:
        return "high" if z > 0 else "low"
    return "pass"

Milestone 4: a score, a decision, and how often it is wrong

A real canary has dozens of metrics. The judge turns the per-metric labels into one decision, in the way Kayenta does: a weighted score from 0 to 100, the share of total weight carried by metrics that are not bad, compared with a pass threshold. A metric is bad if it moved against its direction (latency, errors and memory are all "lower is better", so "high" is bad; "low", an improvement, is not). On top of the score, some metrics are critical: if a critical metric is bad, the canary fails whatever the score. Here latency and the error rate (weight 3 each) are critical, and memory (weight 1, total weight 7) is not. With a pass score of 90, a memory-only problem scores 6/7 = 85.7 and fails: with only three metrics a single bad one is enough. That is a choice, and the check tests both sides of it.

Now the question the whole exercise is for: how often is the judge wrong? Two numbers:

False-rollback rate
The share of healthy builds that the judge rolls back. It costs engineers' time and erodes trust.
Missed-regression rate
The share of bad builds that the judge promotes. It costs customers, and it is the reason the judge exists.

You measure them by simulating many deploys, each with its own seed. With three metrics at α = 0.01 you would expect a false alarm in about 3% of healthy deploys before the effect-size rule, and fewer after it. Power, the chance of catching a real regression, depends on the effect size, the spread of the data, and the number of samples, which is the amount of canary traffic times the bake time.

(the share of simulated deploys with regression reg that are rolled back; deploy i uses random.Random(seed * 100003 + i)). is_bad is given.

def judge(data: Dict[str, Tuple[List[float], List[float]]], policy: Policy, metrics: List[Metric] = METRICS) -> Dict[str, str]:
    out = {}
    for m in metrics:
        base, canary = data[m.name]
        out[m.name] = classify(base, canary, policy.alpha, m.min_effect, m.floor)
    return out

def score(labels: Dict[str, str], metrics: List[Metric] = METRICS) -> float:
    total = sum(m.weight for m in metrics)
    good = sum(m.weight for m in metrics if not is_bad(labels[m.name], m))
    return 100.0 * good / total

def decide(data, policy: Policy, metrics: List[Metric] = METRICS) -> Tuple[bool, float, Dict[str, str]]:
    labels = judge(data, policy, metrics)
    sc = score(labels, metrics)
    critical_bad = any(m.critical and is_bad(labels[m.name], m) for m in metrics)
    return (sc >= policy.pass_score and not critical_bad), sc, labels

def rollback_rate(reg: Regression, n_deploys: int, seed: int, policy: Policy = Policy(),
                  minutes: int = 30, instances: int = 3, metrics: List[Metric] = METRICS) -> float:
    rolled = 0
    for i in range(n_deploys):
        rng = random.Random(seed * 100003 + i)
        promote, _, _ = decide(generate(rng, reg, minutes, instances), policy, metrics)
        rolled += 0 if promote else 1
    return rolled / n_deploys

Milestone 5: waves, and what to compare against

A rollout is a sequence of canaries. The given WAVES are 1.5% of the fleet (3 canary instances), 5% (6), 25% (12) and 100%, each baked for 30 minutes. Each wave is judged before the next starts: if the judge says roll back, the rollout halts, and the fleet is left with at most that wave's share on the bad build. This is the staged rollout of chapter 12, where early waves are cheap and later waves are large. The cost of a missed regression is the exposure of the wave that finally notices; the earlier it is caught, the smaller the blast radius.

The question is what to compare the canary with. Chapter 12 argues for a concurrent baseline: instances of the old build, launched at the same time, the same size, receiving comparable traffic, so the only systematic difference is the code. The tempting alternative is yesterday's data, or last week's, or the whole fleet's averages: it needs no extra instances and is always available. Its problem is time. Real traffic has a daily cycle, and latency follows traffic. Suppose latency is 30% above its average at the afternoon peak and 30% below at night (the given curve). A healthy build rolled out at 3 p.m. looks 30% slower than yesterday's all-day average and is rolled back. A build that is truly 20% slower rolled out at 3 a.m. runs at 0.7 × 1.2 = 0.84 of the average, looks faster than yesterday's, and is promoted to everyone.

It checks that a 40% regression is halted at wave 0 with exposure 0.015 and exactly one wave judged (at least 9 of 10 seeds) and never promoted; that a healthy build passes all four waves with exposure 1.0 (at least 9 of 10 seeds); that against yesterday's data a healthy build started at 14:00 is halted (at least 9 of 10) and a build 20% slower started at 02:00 is promoted (at least 8 of 10). Then over 200 deploys, started at random hours of the day, for two seeds: with a concurrent baseline false rollbacks are at most 4%, missed regressions at most 2% and the mean exposure of a bad build at most 4% of the fleet; against yesterday's data false rollbacks are over 25% and missed regressions over 15%, both more than five times worse.

  • generate(rng, reg, w.bake_minutes, w.instances, load) gives the concurrent baseline at the same load as the canary. For 'yesterday', keep the canary samples and replace data[name] by (ref[name], canary_samples) for latency and errors; memory keeps its concurrent baseline.
  • The exposure of a halt is the wave's fraction. A rollout that passes every wave has exposure 1.0 and halted_at of None.
  • Return a Rollout(promoted, halted_at, exposure, waves_judged). On a halt at wave i, waves_judged is i + 1: you did judge that wave.
  • In compare_baselines, use the same start hour for deploy i's healthy and bad rollouts, and a fresh random.Random (with the offsets in the docstring) for each so the runs are independent. The comparison across modes uses the same hours too, so it is a paired comparison.

def rollout(rng: random.Random, reg: Regression, start_hour: float, baseline: str, policy: Policy = Policy(),
            waves: List[Wave] = WAVES) -> Rollout:
    elapsed = 0
    exposure = 0.0
    for i, w in enumerate(waves):
        hour = (start_hour + elapsed / 60.0 + w.bake_minutes / 120.0) % 24.0
        load = day_load(hour)
        data = generate(rng, reg, w.bake_minutes, w.instances, load)
        if baseline == "yesterday":
            ref = yesterday_baseline(rng, w.bake_minutes * w.instances)
            data = dict(data)
            for name, base in ref.items():
                data[name] = (base, data[name][1])
        exposure = max(exposure, w.fraction)
        promote, _, _ = decide(data, policy)
        if not promote:
            return Rollout(False, i, w.fraction, i + 1)
        elapsed += w.bake_minutes
    return Rollout(True, None, 1.0, len(waves))

def compare_baselines(n_deploys: int, seed: int, bad: Regression = Regression(latency=0.20),
                      policy: Policy = Policy()) -> Dict[str, Dict[str, float]]:
    out = {}
    for mode in ("concurrent", "yesterday"):
        halted = missed = 0
        exposure = 0.0
        for i in range(n_deploys):
            hour = random.Random(seed * 100003 + i).uniform(0.0, 24.0)
            good = rollout(random.Random(seed * 100003 + i + 50000), Regression(), hour, mode, policy)
            halted += 0 if good.promoted else 1
            badr = rollout(random.Random(seed * 100003 + i + 90000), bad, hour, mode, policy)
            missed += 1 if badr.promoted else 0
            exposure += badr.exposure
        out[mode] = {"false_rollback": halted / n_deploys, "missed": missed / n_deploys, "exposure": exposure / n_deploys}
    return out

Look under the hood

  • Three knobs decide how good a judge is: the number of samples, the significance level and the effect threshold. Samples buy power. The threshold buys robustness against harmless noise. The significance level controls how often a clean build is flagged by chance. The experiments below move each in turn.
  • A passing canary is evidence, not proof. The judge sees only the metrics you gave it. It cannot see a bug that returns a wrong answer with a 200, a regression that affects a customer segment absent from the canary, or one that appears only at peak load if the bake ran in the quiet hours. The daily-pattern lesson of milestone 5 applies to the canary itself: a bake that ends before the evening peak says nothing about the evening.
  • Your false-rollback rate is a budget. At 1% a deploy, with fifty deploys a day, one in two days has a spurious rollback somewhere. Teams tune the judge towards fewer false alarms until real regressions slip through, then back again. Having the rates measured, as in this lab, lets you choose rather than drift.

Stretch goals

  • Persistence: require a metric to be flagged in two consecutive windows before it counts. Measure what it does to the false-rollback rate and to the time to detection.
  • Percentile metrics: generate per-instance p99 latency and feed it to the test. Then merge the raw samples and compare. (Chapter 4's rule about not averaging percentiles applies.)
  • Confidence intervals: report a confidence interval for the effect size (for example by bootstrapping the difference of medians) and flag only when the whole interval lies beyond the tolerance, as Spinnaker's documentation describes for its default judge.
  • Multiple-comparison control: add a Bonferroni or Holm correction across the metrics and compare with the weighted-score approach.
  • Day-to-day drift: let yesterday's traffic differ from today's by a random factor of a few percent. Does comparing against 'yesterday at the same hour' work better than against the all-day average? How much better, and when does it fail?
  • Sequential testing: instead of waiting for the full bake, test every minute and stop as soon as the evidence is strong either way. What happens to the false-rollback rate if you do this naively?
  • Segments: split the canary traffic into two customer segments, one with a bug. Does a combined test notice? Does one test per segment?

Distributed systems connection

A canary comparison is an experiment in a distributed system, and most of its subtleties come from the system being distributed. The canary and the baseline run on different machines with different clocks, caches, neighbours and request mixes, so the 'concurrent' baseline is only approximately concurrent; hashing users to arms of the experiment, as feature-flag systems do, makes the traffic more alike. Metrics arrive late and out of order from many hosts, so every window has a data-freshness question. Percentiles cannot be averaged across hosts (chapter 4), so the judge must receive raw samples or mergeable histograms. And a staged rollout is the application of blast-radius thinking to time: each wave is a larger failure domain, and the judge is the thing that decides whether to risk the next one.

What you learned

  • To test a judge you need data whose truth you control: seeded baseline and canary samples with a latency shift, extra errors or a leak.
  • The Mann-Whitney U test compares ranks, not values, so it is robust to skew and outliers. U comes from the canary's rank sum; the normal approximation needs a tie-corrected variance and a continuity correction; the sign of z gives the direction.
  • Significance and importance are different questions. A metric is flagged only when p is small and the effect is larger than a tolerance, so tiny real differences do not fail a deploy.
  • A weighted score with critical metrics and a pass threshold turns labels into a decision, and simulating many seeded deploys measures its false-rollback and missed-regression rates. Samples buy power; a slow leak needs a bake long enough to show.
  • The reference matters more than the test. A concurrent baseline controls for time, load and warm-up; yesterday's data folds the daily cycle into the comparison, rolling back healthy builds at the afternoon peak and promoting bad ones at night.
  • Waves limit the cost of a miss: the earlier a bad canary is caught, the less of the fleet ever saw it.

Check your understanding

A canary is judged against the previous day's average latency. The build is healthy, and it is rolled out at 3 p.m., the daily traffic peak. What is the most likely outcome and why?

  1. It passes, because a healthy build has the same latency as yesterday
  2. It is rolled back, because the test is random and fails about half the time
  3. It is rolled back, because busy-hour latency is higher than the all-day average and the judge attributes the difference to the new code
  4. The judge cannot run, because the data are from a different day
Latency follows traffic. The canary at the peak is compared with a reference that mixes quiet and busy hours, so it looks slower for reasons unrelated to the code. A concurrent baseline experiences the same load at the same moment and removes the effect.

With 6000 samples per side, a canary is 3% slower than the baseline with p < 0.001. The service tolerates 10%. What should the judge do, and which design choice makes that happen?

  1. Pass it: the effect-size threshold ignores differences smaller than the tolerance, however significant they are
  2. Fail it: p < 0.001 is overwhelming evidence of a regression
  3. Wait for more data until the p-value is smaller
  4. Pass it, because the test is not valid with so many samples
The p-value says the difference is real, not that it matters. Requiring both significance and a minimum effect keeps the judge from rolling back builds for differences nobody can feel. The tolerance is a business choice, ideally tied to the SLO.

Why is the Mann-Whitney U test used on latency data rather than a t-test on the means?

  1. It is faster to compute on large samples
  2. It always has more statistical power than a t-test
  3. It is the only test that works with two groups
  4. Latency is skewed with a heavy tail, so a few extreme values dominate a mean; the rank test uses only order, so an outlier counts as 'the largest' whatever its size, and it assumes no particular shape
A t-test assumes roughly normal data and compares means, both poor fits for latency. Ranks make the result invariant to monotone transformations (the lab checks that exp() changes nothing) and robust to outliers. It is not always more powerful: for truly normal data the t-test is slightly better.

A canary leaks 3 MB of memory per minute. A judge that analyses only the first 10 minutes of canary data almost never catches it, but a judge with a 25-minute window almost always does. What is the lesson?

  1. The 25-minute judge uses a better statistical test
  2. Bake time must be at least as long as the incubation period of the problems you want to detect: a slow leak is simply not there to be seen early on
  3. Memory metrics are always unreliable
  4. Leaks can only be found with a larger canary, not a longer one
Both judges use the same test. At ten minutes the leak has grown by at most 27 MB (about 14 MB on average) against a noise of 15 MB per sample and a 3% tolerance. Time is the sample size for a trend. Chapter 12 makes the same point: bake time is a property of your failure history.

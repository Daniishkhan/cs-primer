Lab 1: SLOs & Burn-Rate Alerts

Chapter 2 gave you the vocabulary of reliability targets in sentences, and chapter 7 gave you an alerting recipe as a table of numbers. In this lab you turn both into code you can run, break and measure. You will compute availability and latency SLIs from a request log, work out what is left of a 30-day error budget, answer "what was the burn rate over the last w minutes?" in constant time, and implement the Site Reliability Workbook's multi-window, multi-burn-rate alert rules. Then you will do what is impossible in production: replay the same incidents against different alert designs and count the false pages, the missed outages, the minutes to detect and the minutes to clear.

Why this lab matters

An alert rule is a small program whose inputs are noisy and whose bugs are expensive: a wrong threshold either wakes an engineer for nothing or stays silent through an outage. Most teams find out which by living through it. A synthetic incident turns "I think this threshold is about right" into a table: this rule paged within two minutes of a total outage, stayed quiet for a three-minute spike, and took 29 minutes to clear. The same test harness is how you would review a change to a real rule before it ships, and it makes the four attributes from chapter 7 (precision, recall, detection time, reset time) numbers you can compare rather than adjectives.

Simulated time, so every number repeats

Nothing here reads a clock or touches a network. Time is an integer minute counter, traffic is a fixed 1,000 requests per minute (as in chapter 7's program, so the numbers match), and every random draw comes from a seeded random.Random. The same seed gives the same log, the same incident and the same verdict, so when the check says "seed 2024, scenario 17 was missed" you can replay exactly that scenario. The synthetic traffic is a deliberate simplification: real traffic has daily cycles, bursts and low-traffic hours, and a few of the stretch goals ask you to add them.

What you'll build

  1. SLIs from a log: parse a load-balancer access log, decide which requests are valid (the denominator) and which are good (the numerator), for an availability SLI and a latency SLI, and count the garbled lines you had to skip.
  2. The error budget: convert an SLO into a budget (as a fraction, as requests, as minutes of total outage), and compute how much of it a rolling 30-day window has left.
  3. Burn rate over any window, fast: a prefix-sum structure that answers "how many valid and bad requests in the last w minutes?" with two subtractions, so an alert can be evaluated at every minute against several windows.
  4. Multi-window, multi-burn-rate rules: the three Workbook rules from chapter 7, evaluated over fast and severe, slow and steady, and brief-spike incidents, with detection time and reset time measured.
  5. A scorecard against naive alerts: precision, recall, detection time and reset time for the burn-rate rules and three simpler designs, over 48 seeded scenarios.

The data

A request log is a list of text lines, one per request, in the form ts method path status latency_ms client, for example 3601 GET /api/cart 200 84 web. generate_log(seed) makes two hours of it at about four requests a second, and it is as messy as the real thing: health checks from a probe, a load-test client, 4xx responses, a few 429s from load shedding, slow responses, 5xx errors, some garbled lines, and a three-minute partial outage in the middle.

Milestones 2 to 5 work on a per-minute series: two lists, valid[i] and bad[i], the number of valid and of bad requests in minute i. A 30-day window is 43,200 minutes, and a real service has billions of requests in it, so nobody keeps raw logs in memory to evaluate an alert; counts per minute (or per scrape) are what a metrics system stores (chapter 4). The constants at the top of the file are the ones from the chapters: SLO = 0.999, a 30-day WINDOW, a 300 ms latency threshold.

Milestone 1: SLIs from a request log

An SLI is a ratio, good events / valid events (chapter 2), and the division is the easy part. The engineering is in two definitions: which requests are in the denominator, and which of those count as good. Write them as code, where a reviewer can read them, and decide each case on purpose.

The definitions for this service follow chapter 2's specification block. A request is valid if it is for /api/*, except health checks (/api/health) and the load-test client: probes and test traffic that always succeed would inflate the number, and they are not users. Everything else is valid, including requests that failed, because a failure that leaves the denominator cannot count against you. A valid request is good for availability if its status is not 5xx, with one deliberate exception: 429 (too many requests) counts as bad, because the service refused a valid request to protect itself and the user got nothing. Other 4xx responses are good: the client made a mistake and the service correctly said so. A request is good for latency if it is good for availability and took 300 ms or less, so a fast error is not a fast success, and the boundary is inclusive.

Two more decisions are hidden in the code. A line you cannot parse is neither valid nor good, and you should count it: a log whose parse failures suddenly jump from 0.5% to 20% is telling you the SLI is no longer measuring what you think. And an empty log has no valid events, so there is nothing to have gone wrong: report 1.0 rather than dividing by zero.

def parse_line(line):
    parts = line.split()
    if len(parts) != 6:
        return None
    ts, method, path, status, lat, client = parts
    try:
        ts, status, lat = int(ts), int(status), int(lat)
    except ValueError:
        return None
    if ts < 0 or lat < 0 or not 100 <= status <= 599:
        return None
    return Request(ts, method, path, status, lat, client)

def is_valid(r):
    return r.path.startswith("/api/") and r.path != "/api/health" and r.client != "loadtest"

def is_good_availability(r):
    return r.status < 500 and r.status != 429

def is_good_latency(r, threshold_ms=LATENCY_MS):
    return is_good_availability(r) and r.latency_ms <= threshold_ms

def compute_slis(lines, threshold_ms=LATENCY_MS):
    rep = SLIReport()
    for line in lines:
        r = parse_line(line)
        if r is None:
            rep.skipped += 1
            continue
        if not is_valid(r):
            continue
        rep.valid += 1
        rep.good_availability += is_good_availability(r)
        rep.good_latency += is_good_latency(r, threshold_ms)
    return rep

Milestone 2: the error budget over a rolling window

If the SLO is 99.9%, then 0.1% of valid events are allowed to be bad. That allowance is the error budget, 1 − SLO, and it comes in three units that are worth keeping straight. As a fraction it is 0.001. In requests it is 0.001 times the number of valid requests in the window, so a month with 43.2 million valid requests may fail 43,200 of them. In time, for a service whose traffic is flat, it is the same fraction of the window: 0.001 × 43,200 minutes = 43.2 minutes of complete unavailability, chapter 1's table row for three nines.

What you track day to day is the fraction of the budget remaining: one minus (bad requests in the window) divided by (the budget in requests). It is 1.0 when nothing has failed, 0.0 when the budget is exactly spent, and negative when you have overspent. The window is rolling: the 43,200 minutes ending now, so an incident leaves the calculation exactly one window after it happened (chapter 2 compares this with calendar windows).

Two quantities from here on will keep reappearing. The burn rate is the observed bad fraction divided by the budget fraction, (bad/valid) / (1 − SLO): 1 means "on course to spend exactly the budget by the end of the window". And the time to exhaustion at a constant burn rate is the window length divided by the burn rate: at 14.4 a full 30-day budget lasts 720 h / 14.4 = 50 hours, which is why chapter 7's first rule pages on 14.4.

Solution spoiler 
def error_budget(slo):
    return 1.0 - slo

def budget_minutes(slo, window=WINDOW):
    return error_budget(slo) * window

def exhaustion_hours(burn, window=WINDOW):
    return (window / 60.0) / burn

def budget_remaining(valid, bad, end, slo, window=WINDOW):
    lo = max(0, end - window + 1)
    v = sum(valid[lo:end + 1])
    b = sum(bad[lo:end + 1])
    allowed = error_budget(slo) * v
    return 1.0 if v == 0 else 1.0 - b / allowed

Milestone 3: burn rate over any window, with prefix sums

Your budget_remaining adds up 43,200 numbers every time it is called. That is fine for a dashboard tile that refreshes once a minute. An alert evaluator is a different animal: chapter 7's three rules look at six windows (1 h, 5 min, 6 h, 30 min, 3 days, 6 h), every minute, for every SLO the company has. The slice-and-sum approach costs time proportional to the window; a 3-day window is 4,320 additions per evaluation, and a per-minute evaluation over a month of data is a hundred million additions for one rule. We want the cost to be independent of the window.

The classic trick is a prefix sum. Store, for every i, the total of the first i minutes: cum[i]. Then the total of any window is a difference of two entries: the last w minutes ending at end are cum[end+1] - cum[end+1-w]. You pay once, in __init__, to build two arrays (one for valid, one for bad); after that every window query, of any length, is two subtractions. (Real metrics systems do the same thing without calling it that: a counter is already a prefix sum, and rate(x[1h]) is the difference between two counter samples divided by the time between them, which is why chapter 4 says to export totals and compute rates at query time.)

Solution spoiler 
class Prefix:

    def __init__(self, series):
        """Build the prefix arrays. Keep them in `self.cv` and `self.cb`, each of
        length len(series) + 1, with cv[i] = valid requests in minutes 0 .. i-1."""
        self.n = len(series)
        self.cv, self.cb = [0], [0]
        for i in range(self.n):
            self.cv.append(self.cv[-1] + series.valid[i])
            self.cb.append(self.cb[-1] + series.bad[i])

    def window(self, end, w):
        """(valid, bad) over the w minutes ending at minute `end` inclusive, clipped at minute 0."""
        lo = max(0, end - w + 1)
        return self.cv[end + 1] - self.cv[lo], self.cb[end + 1] - self.cb[lo]

    def error_ratio(self, end, w):
        """bad / valid over the window; 0.0 if the window holds no valid requests."""
        v, b = self.window(end, w)
        return b / v if v else 0.0

    def burn_rate(self, end, w, slo):
        """error_ratio / (1 - slo)."""
        return self.error_ratio(end, w) / error_budget(slo)

    def remaining(self, end, slo, window=WINDOW):
        """Same answer as budget_remaining, in O(1)."""
        v, b = self.window(end, window)
        return 1.0 if v == 0 else 1.0 - b / (error_budget(slo) * v)

Milestone 4: multi-window, multi-burn-rate rules

Now the rules. The Site Reliability Workbook's progression (chapter 7) ends with rules that combine two ideas. Multiple burn rates: a fast burn (a hard outage) should page within minutes, a slow burn (a leak that would exhaust the budget in days) should be noticed within hours or days, so use a high threshold over a short window for the first and a low threshold over a long window for the second. Multiple windows: require the burn to be high over a long window (the event is significant, not a blip) and over a short one, typically a twelfth as long (it is still happening now, so the alert clears soon after the fix). The parameters, for a 99.9% SLO over 30 days, are given in the file:

RuleSeverityLong windowShort windowBurn rateBudget spent in the long window
2% in 1hpage1 hour5 minutes14.42%
5% in 6hpage6 hours30 minutes65%
10% in 3dticket3 days6 hours110%

A rule fires at minute t when the burn rate over its long window and over its short window are both strictly above its threshold. An interval is a maximal run of consecutive minutes at which a rule fires; from intervals you can read the two numbers that matter most operationally. Detection time is how long after an incident begins the alert first fires. Reset time is how long it keeps firing after the incident is over.

The chapter's formula predicts detection time: if the incident's error ratio is r and a rule's threshold ratio is T (burn rate × 0.001), the long window's average first exceeds T after about T × window / r minutes into the incident. A total outage (r = 1) trips rule 1 after 0.0144 × 60 min = 52 seconds; 5% errors after 17 minutes; 1% errors can never trip rule 1 (below its 1.44%) but trip rule 2 after 216 minutes. Your implementation should reproduce those numbers exactly, which is the first half of the check.

def rule_fires(p, t, rule, slo=SLO, use_short=True):
    if p.burn_rate(t, rule.long_m, slo) <= rule.burn:
        return False
    return (not use_short) or p.burn_rate(t, rule.short_m, slo) > rule.burn

def firing_intervals(p, rule, slo=SLO, use_short=True):
    out, start = [], None
    for t in range(p.n):
        if rule_fires(p, t, rule, slo, use_short):
            if start is None:
                start = t
        elif start is not None:
            out.append((start, t - 1))
            start = None
    if start is not None:
        out.append((start, p.n - 1))
    return out

def detection_time(intervals, incident_start):
    for a, b in intervals:
        if b >= incident_start:
            return max(a, incident_start) - incident_start
    return None

def reset_time(intervals, incident_end):
    for a, b in intervals:
        if a <= incident_end <= b:
            return b - incident_end + 1
    return 0

def evaluate(series, rules=RULES, slo=SLO, use_short=True):
    p = Prefix(series)
    return {r.name: firing_intervals(p, r, slo, use_short) for r in rules}

Milestone 5: against a naive threshold

The scorecard. make_scenarios(seed, n) gives you n seeded scenarios, six of each of eight families, each a five-to-ten-day per-minute series with background noise (a 0.02% error ratio, about a fifth of the budget rate) and a label set by design:

  • page (someone should be woken): outage (total, 10–60 min), partial (5–50% errors) and bad_deploy (burn rate 7 to 30). Each spends at least 8% of the monthly budget.
  • ticket (look at it within days): slow_leak, a burn rate of 1.5 to 4 that spends at least 12%.
  • none (leave the pager alone): blip (one spike of 1–4 minutes), spike_train (two or three spikes at least two hours apart), mild (a persistent burn rate under 1) and quiet (background noise only). The spikes are severe, up to 100% errors, but each spends under 1% of the budget.

The labels are the generator's ground truth, checked against the budget arithmetic when each scenario is built. Judging an alert policy then reduces to a confusion matrix for the class "page": a page for a page scenario is a true positive, a page for anything else is a false positive (the pager rang when it should not have), and no page for a page scenario is a false negative (an outage nobody was told about). Precision is tp / (tp + fp), recall is tp / (tp + fn). Add the detection time and reset time from milestone 4 and you have all four attributes of chapter 7.

You compare five policies: the burn-rate rules; the same rules with the short windows removed; a naive threshold (page when the error ratio over the last 5 minutes exceeds 1%, a burn rate of 10); a single 1-hour window at burn rate 10; and a single 6-hour window at burn rate 5. The last three are the sort of rule a reasonable engineer writes first.

def verdict(by_rule, rules):
    sev = {r.name: r.severity for r in rules}
    fired = {sev[name] for name, iv in by_rule.items() if iv}
    return "page" if "page" in fired else "ticket" if "ticket" in fired else "none"

def confusion(labels, verdicts, positive):
    tp = sum(1 for l, v in zip(labels, verdicts) if v == positive and l == positive)
    fp = sum(1 for l, v in zip(labels, verdicts) if v == positive and l != positive)
    fn = sum(1 for l, v in zip(labels, verdicts) if v != positive and l == positive)
    tn = len(labels) - tp - fp - fn
    return tp, fp, fn, tn

def precision_recall(tp, fp, fn):
    return (tp / (tp + fp) if tp + fp else 1.0), (tp / (tp + fn) if tp + fn else 1.0)

def score_policy(scenarios, rules, use_short=True, positive="page"):
    verdicts, detect, reset = [], {}, {}
    for sc in scenarios:
        by_rule = evaluate(sc.series, rules, SLO, use_short)
        v = verdict(by_rule, rules)
        verdicts.append(v)
        if sc.label == positive and v == positive:
            alert = merge_intervals([iv for r in rules if r.severity == positive for iv in by_rule[r.name]])
            d = detection_time(alert, sc.start)
            if d is not None:
                detect.setdefault(sc.family, []).append(d)
                reset.setdefault(sc.family, []).append(reset_time(alert, sc.end))
    tp, fp, fn, tn = confusion([s.label for s in scenarios], verdicts, positive)
    prec, rec = precision_recall(tp, fp, fn)
    return {"precision": prec, "recall": rec, "tp": tp, "fp": fp, "fn": fn, "tn": tn, "verdicts": verdicts,
            "detect": detect, "reset": reset,
            "detect_median": median([x for v in detect.values() for x in v]),
            "reset_median": median([x for v in reset.values() for x in v])}

Reliability connection

This lab is the quantitative core of the course's first part. Chapter 1 turned nines into minutes; chapter 2 turned a target into a budget and a policy; chapter 7 turned the budget into alerts. Here is the same chain in code. The rest of the course puts load on it: chapter 12 is about shipping changes without wasting the error budget, and Lab 2 builds the histograms that make the latency SLI computable across a fleet. What the lab cannot show is the human half, which is the most important: an alert is a request to interrupt a person, and its precision is measured in how willing that person is to answer the next one.

What you learned

  • An SLI is good events over valid events, and the engineering is in the two definitions: what is excluded from the denominator (health checks, load tests), what counts as bad (5xx, and 429 when you shed valid traffic), and that a fast error is not a fast success. Count what you could not parse.
  • The error budget is 1 − SLO, in three units: a fraction, requests, and minutes of total outage (43.2 per 30 days at 99.9%). Budget remaining is a rolling-window quantity; an incident leaves it exactly one window later.
  • Burn rate is the observed bad fraction over the allowed fraction. At a constant burn rate b the budget lasts window / b: 50 hours at 14.4.
  • Prefix sums answer any window in two subtractions, which is what makes evaluating several rules at every minute cheap. A counter is a prefix sum already.
  • Multiple burn rates give you the right urgency for each kind of incident. Multiple windows give you precision (the long one) and a fast reset (the short one). Detection time follows T × window / r; reset time is about the length of the short window.
  • A naive threshold fails twice: it pages on brief spikes (precision 0.57 in the lab) and it misses moderate burns (recall 0.89). A single long window fixes both and fails the other two attributes: slow to detect, and red for hours after the fix. Only the multi-window design is good on all four.

Check your understanding

A service's log has 10,000 user requests, 20 of which returned 503, plus 1,000 successful health-check requests and 100 successful requests from its own load-test client. What is the availability SLI as this lab defines it?

  1. 11,080 / 11,100, because every request counts
  2. 9,980 / 10,000 = 99.8%, because health checks and load-test traffic are excluded from the denominator and the 503s are bad
  3. 9,980 / 11,100, because only user requests can be good
  4. 10,000 / 10,000, because 503s are removed from the log
Valid requests are the 10,000 user requests (the 1,000 probes and 100 load-test requests are excluded as not representing users), and 20 of them were bad. Counting excluded traffic as good inflates the number (answer 1), and deleting failures from the denominator hides them (answer 4).

A 99.9% SLO over 30 days has used 15 minutes of complete outage so far this window. How much of the error budget remains?

  1. 15%
  2. 85%
  3. About 65%: the budget is 43.2 minutes, 15 of them are spent (34.7%), 28.2 minutes remain
  4. About 35%
Budget = 0.001 × 43,200 min = 43.2 min of total outage. 15 / 43.2 = 34.7% spent, so 65.3% remains. Answer 1 treats the 15 minutes as 15% of the budget, which would be true only for a 100-minute budget (a 99.77% SLO).

Your prefix-sum structure answers a window query with cum[end+1] - cum[end+1-w]. Why does cum need a leading 0 entry?

  1. So that a window starting at minute 0 needs no special case: cum[0] = 0 is the empty prefix
  2. To make the array length a power of two
  3. Because Python lists cannot be indexed from 0
  4. So the window query can be negative
cum[i] is the sum of the first i minutes, so cum[0] is the sum of nothing. A window that starts at minute 0 is cum[end+1] - cum[0], and the formula needs no branch. Without the 0 you would write an if for the first window of every query.

After a 30-minute total outage, the 1-hour page rule keeps firing for 59 minutes when it uses the long window alone, but only 4 minutes when it also requires the 5-minute window. Why?

  1. The 5-minute window is more accurate than the 1-hour window
  2. The bad half hour stays inside the 1-hour window for an hour after the outage ends, so the long window stays hot; the 5-minute window empties within minutes, ending the alert
  3. The short window makes the alert fire later
  4. Burn rate is lower in short windows by definition
A window's average stays high until the bad minutes slide out of it. The long window needs about an hour to forget the outage; the short one forgets in five minutes. Requiring both means the alert ends when the short window cools, a few minutes after recovery. This is the second reason for multi-window rules; the first (precision) is the long window's job.

In the scorecard, a single 6-hour window at burn rate 5 has precision 1.00 and recall 1.00. Why is it still a worse design than the multi-window rules?

  1. Its precision is secretly lower
  2. It cannot detect total outages
  3. It takes longer to detect moderate burns and keeps paging for about six hours after the problem is fixed, because the bad stretch stays inside the window
  4. It uses more memory
Precision and recall are only two of the four attributes. The long window delivers precision, but it detects later (median 6.0 minutes against 2.5 for the burn-rate rules in the lab) and its reset time is about the window length (median 353 minutes against 29). The short windows are what cut the reset to about half an hour.

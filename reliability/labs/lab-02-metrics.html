Lab 2: A Metrics Library

Chapter 4 argued three things in prose: that you should export totals and compute rates later, that percentiles cannot be averaged but histogram buckets can be added, and that one careless label can take down a monitoring system. In this lab you build the library that makes each claim checkable. You will write counters and gauges with labels and a registry that refuses a label explosion, a histogram with configurable buckets, a quantile estimator that interpolates the way histogram_quantile does (with an error bound you test against exact answers), a merge that combines hosts, and the renderer for Prometheus's text exposition format, checked against the format's own rules.

Why this lab matters

Every SLO, every burn-rate alert (Lab 1) and every capacity decision later in the course reads numbers that some metrics library produced, and the failure modes of that library are quiet. A histogram whose top bucket is too low reports a confident p99.9 that is simply its largest bound. A dashboard that averages per-host p99s is wrong by a factor of four with no warning. A label with ten thousand values does not raise an error; it slowly eats the monitoring server's memory until the incident you most needed the dashboard for. Building the library once, with tests that make each of these happen on purpose, is the fastest way to stop being surprised by them.

No clocks, no network, no scraper

A metric is just numbers that code updates, so the whole lab runs in one process with no timing at all: nothing here reads the clock, opens a socket or starts a thread. The random data (latencies for a simulated fleet) comes from seeded generators, so the same seed gives the same histograms and the same error percentages every time. What the lab leaves out is the scraper and the time dimension: a real counter is read repeatedly, and rate() is the difference between two reads. A stretch goal adds a counter-reset-aware rate.

What you'll build

  1. Counter, gauge, labels and a registry: a counter that only goes up, a gauge that goes up and down, label sets validated against the declaration, and a registry that counts series and refuses a new label combination past a per-metric limit.
  2. A histogram: user-chosen bucket bounds, observe, cumulative counts, sum and count, with a series cost that includes every bucket.
  3. Quantiles from buckets: linear interpolation inside the bucket that holds the rank, and a test of the error against exact quantiles for linear and exponential layouts.
  4. Merging hosts: adding bucket counts, and the demonstration that the average of per-host p99s is wrong (too high in one fleet, too low in another) while the merged histogram stays within a bucket of the truth.
  5. The text exposition format: HELP and TYPE lines, _bucket{le="..."} lines in order, _sum, _count and the +Inf bucket, escaping, checked by an independent validator.

The vocabulary in six lines

  • A metric is a name plus a fixed set of label names (route, status); each distinct combination of label values is a child and, in the exposition, one or more series.
  • A counter only increases; a gauge is a level; a histogram keeps one cumulative counter per bucket plus a sum and a count.
  • Cardinality is the number of series. A histogram child with k finite bounds costs k + 1 buckets (the last is +Inf) + 2 (_sum and _count) series.
  • A registry is the set of metrics one process exports.
  • A snapshot is an immutable copy of a histogram child's cumulative counts, sum and count: what a scraper would read.
  • Exposition is the text a scraper fetches from /metrics.

Milestone 1: counters, gauges, labels, and a registry that says no

Start with the two simplest types. A counter is a number that only ever increases; you export the total and let the query system compute the rate, because a total survives a missed scrape and can be re-windowed after the fact (chapter 4). A gauge is a value that moves both ways: queue depth, memory in use, connections open. Both are labelled: http_requests_total{route="/cart", status="500"} is one series and the same name with status="200" is another.

The interesting rules are about the labels. A metric declares its label names once, and every call must supply exactly that set: a missing label produces a series that cannot be joined with its siblings, an extra one produces a series that no query expects. Values are strings, whatever you pass (status=200 and status="200" are the same series), and their order in the call does not matter.

The registry is where the cost of labels is enforced. Every distinct combination is a series with its own storage and index entry in the monitoring system, so a label whose values are unbounded (a user id, a request id, a raw URL) turns one metric into millions of series. The failure is slow and silent and tends to arrive during an incident. A library can defend its users: count the series per metric, and when a new label combination would take a metric past the limit, refuse it loudly (raise CardinalityError, count the refusal) and keep serving the combinations already there. Revisiting an existing combination must always be free; only growth is limited.

def label_key(labelnames, kv):
    if set(kv) != set(labelnames):
        raise ValueError(f"expected labels {sorted(labelnames)}, got {sorted(kv)}")
    return tuple(str(kv[n]) for n in labelnames)

def register(self, metric):
    if metric.name in self.metrics:
        raise ValueError(f"metric {metric.name!r} is already registered")
    self.metrics[metric.name] = metric

def admit(self, metric, key):
    if (len(metric.children) + 1) * metric.series_per_child() > self.max_series:
        self.rejected[metric.name] = self.rejected.get(metric.name, 0) + 1
        raise CardinalityError(f"{metric.name}: a new label combination {key} would exceed the limit of "
                               f"{self.max_series} series")

def labels(self, **kv):
    key = label_key(self.labelnames, kv)
    child = self.children.get(key)
    if child is None:
        if self.registry is not None:
            self.registry.admit(self, key)
        child = self.children[key] = self._new_child()
    return child

class CounterChild:
    def __init__(self):
        self.value = 0.0

    def inc(self, amount=1):
        """Add `amount` (default 1). A counter never goes down: raise ValueError if amount < 0."""
        if amount < 0:
            raise ValueError("a counter can only increase")
        self.value += amount

class GaugeChild:
    def __init__(self):
        self.value = 0.0

    def set(self, v):
        self.value = float(v)

    def inc(self, amount=1):
        self.value += amount

    def dec(self, amount=1):
        self.value -= amount

Milestone 2: a histogram with configurable buckets

A counter and a gauge cannot answer "what is the 99th-percentile latency?" A histogram can, approximately, and in a form that merges. You choose a list of bucket upper bounds; the library keeps one counter per bucket plus a running sum and count. An observation lands in the first bucket whose bound is greater than or equal to the value: the bound is inclusive, which is what the le label ("less than or equal") means, and a value above every bound lands in the implicit +Inf bucket. The exposition shows cumulative counts: the bucket labelled le="0.5" counts everything ≤ 0.5, including everything in the smaller buckets, which is why the +Inf bucket always equals the total count.

Choosing bounds is the design decision, and chapter 4 gave the rule: exponential bounds (each a fixed factor above the last) give the same relative error at every latency, linear bounds give the same absolute error, and every bound is a time series per label combination. exponential_buckets(start, factor, count) is the helper you will use for the rest of the lab.

  • For check_bounds, drop one trailing +inf first, then reject an empty list, any NaN or remaining infinity, and any non-increasing pair.

def check_bounds(bounds):
    b = [float(x) for x in bounds]
    if b and math.isinf(b[-1]) and b[-1] > 0:
        b.pop()
    if not b:
        raise ValueError("a histogram needs at least one finite bucket bound")
    if any(math.isnan(x) or math.isinf(x) for x in b):
        raise ValueError("bucket bounds must be finite")
    if any(b[i] >= b[i + 1] for i in range(len(b) - 1)):
        raise ValueError("bucket bounds must be strictly increasing")
    return tuple(b)

def exponential_buckets(start, factor, count):
    if start <= 0 or factor <= 1 or count < 1:
        raise ValueError("need start > 0, factor > 1, count >= 1")
    return [start * factor ** i for i in range(count)]

class HistogramChild:
    def __init__(self, bounds):
        self.bounds = bounds                    # finite upper bounds, strictly increasing
        self.sum = 0.0
        self.count = 0
        self.counts = [0] * (len(bounds) + 1)   # per-bucket (NOT cumulative); the last is +Inf

    def observe(self, v):
        """Record one value: it falls in the first bucket whose bound is >= v (so a value
        equal to a bound belongs to that bucket: le means "less than or equal"), or in the
        +Inf bucket if it is bigger than every bound. Update sum and count too.
        Raise ValueError for NaN (it belongs in no bucket and would poison the sum)."""
        if math.isnan(v):
            raise ValueError("cannot observe NaN")
        self.counts[bisect.bisect_left(self.bounds, v)] += 1
        self.sum += v
        self.count += 1

    def cumulative(self):
        """Cumulative counts, one per bound plus one for +Inf: entry i is the number of
        observations <= bound i. The last entry equals self.count."""
        out, run = [], 0
        for c in self.counts:
            run += c
            out.append(run)
        return out

    def snapshot(self):
        return Snapshot(self.bounds, tuple(self.cumulative()), self.sum, self.count)

    def quantile(self, q):
        return quantile(q, self.bounds, self.cumulative())

Milestone 3: quantiles from buckets, with an honest error bar

From cumulative counts you can estimate any quantile. To find the q-quantile, compute the rank, q × total, and find the bucket that holds that rank: the first one whose cumulative count reaches it. Then assume the observations inside that bucket are spread evenly between its lower and upper bound and interpolate: the lower bound plus the bucket's width times the fraction of the way the rank is through the bucket's count. That is exactly what PromQL's histogram_quantile does, and it is a straight line joining the points of the cumulative curve.

Three edge cases are part of the contract. The first bucket's lower bound is 0. If the rank falls in the +Inf bucket there is no upper bound to interpolate toward, so the estimate is the largest finite bound: a deliberate under-estimate that tells you your top bucket is too low. An empty histogram has no quantiles (NaN), and a q outside 0..1 maps to ±infinity. (One small deviation from Prometheus, which is explained in the docstring: empty buckets are skipped, so q = 0 returns the lower edge of the first non-empty bucket instead of dividing zero by zero.)

How wrong can the estimate be? The exact q-quantile of the raw data and the estimate are in the same bucket, because the rank is an integer cumulative count and both pick the bucket where it is first reached. So the error can never exceed the bucket's width, and with exponential bounds of growth factor γ the relative error is below γ − 1 (25% for γ = 1.25). That is a bound, not a typical error: interpolation does far better when the data is smooth inside the bucket and exactly as badly as the bound allows when it is not. The check pins both facts, a worst case in which every value is 51 inside the bucket (50, 100] and the estimate is 75, and a statistical test against exact quantiles.

Solution spoiler 
def quantile(q, bounds, cumulative):
    if q < 0:
        return float("-inf")
    if q > 1:
        return float("inf")
    total = cumulative[-1]
    if total == 0:
        return float("nan")
    rank = q * total
    prev = 0
    for i, c in enumerate(cumulative):
        if c >= rank and c > prev:
            if i == len(bounds):
                return float(bounds[-1])
            lower = bounds[i - 1] if i else 0.0
            return lower + (bounds[i] - lower) * (rank - prev) / (c - prev)
        prev = c
    return float(bounds[-1])

Milestone 4: merging hosts

The reason to go to this trouble is the fleet. A service runs on many hosts, each with its own histogram, and the question is the fleet-wide p99. The tempting answer is to compute each host's p99 and average them. It is wrong, not by a rounding error: a percentile is not a linear statistic, and no function of the per-host p99s can recover the fleet's. Histograms, in contrast, merge by addition: the fleet saw 1,100 requests under 250 ms if host 1 saw 800 and host 2 saw 300. Addition is associative and commutative, so it does not matter in which order, or in which grouping, you add hosts and time slices. You merge the counts and compute the quantile once, after.

The two fleets in fleet(seed, kind) show both directions of the error. In "sick-small" (chapter 4's example) two busy healthy hosts and a small sick one: the sick host's own p99 is near 900 ms, so the average of three p99s says about 370 ms, four times the truth of about 94 ms, an alarm about something 98% of users never saw. In "sick-large" a quarter of the traffic goes to the sick host, the true p99 is above 700 ms, and the average of four p99s reports about 300 ms: it hides a problem a quarter of your users have. The merged histogram gets both right to within a bucket.

Merging has a precondition worth enforcing: the histograms must have identical bucket bounds. Adding bucket 3 of one layout to bucket 3 of another would silently produce nonsense, so merge must refuse. (This is also why native or sketch-based histograms, which agree on their bucket mapping by construction, are attractive: no schema mismatch is possible.)

Hints try without first

Solution spoiler 
def merge(snapshots):
    snapshots = list(snapshots)
    if not snapshots:
        raise ValueError("nothing to merge")
    bounds = snapshots[0].bounds
    if any(s.bounds != bounds for s in snapshots):
        raise ValueError("cannot merge histograms with different bucket bounds")
    cum = tuple(sum(col) for col in zip(*(s.cumulative for s in snapshots)))
    return Snapshot(bounds, cum, sum(s.sum for s in snapshots), sum(s.count for s in snapshots))

Milestone 5: the Prometheus text exposition format

The last piece is the one a scraper sees. In the pull model (chapter 4) the process serves a plain-text page, conventionally at /metrics, and the monitoring server fetches it on a schedule. The page is line-oriented and the rules are few but strict, and a scraper that finds a malformed page discards it, so a formatting bug is a monitoring outage:

  • For each metric, a HELP line (free text, with backslash and newline escaped) and a TYPE line (counter, gauge or histogram), before any sample. Each metric's lines are contiguous.
  • A sample is name{label="value",...} number; label values are quoted, with backslash, double quote and newline escaped. A metric with no labels has no braces. The special values are spelled +Inf, -Inf and NaN.
  • A histogram child becomes name_bucket{...,le="bound"} lines in increasing le order with cumulative values, a final le="+Inf" bucket equal to name_count, then name_sum and name_count. le is just another label, written last.
  • Counter names end in _total by convention; this lab enforces it.

def format_value(v):
    v = float(v)
    if math.isnan(v):
        return "NaN"
    if math.isinf(v):
        return "+Inf" if v > 0 else "-Inf"
    if v.is_integer() and abs(v) < 1e15:
        return str(int(v))
    return repr(v)

def escape_label_value(s):
    return s.replace("\\", "\\\\").replace('"', '\\"').replace("\n", "\\n")

def escape_help(s):
    return s.replace("\\", "\\\\").replace("\n", "\\n")

def render(registry):
    def labelstr(names, values, extra=()):
        pairs = list(zip(names, values)) + list(extra)
        return "{" + ",".join(f'{n}="{escape_label_value(v)}"' for n, v in pairs) + "}" if pairs else ""

    lines = []
    for m in registry.collect():
        lines.append(f"# HELP {m.name} {escape_help(m.help)}")
        lines.append(f"# TYPE {m.name} {m.kind}")
        for key in sorted(m.children):
            child = m.children[key]
            if m.kind == "histogram":
                cum = child.cumulative()
                for b, c in zip(list(m.bounds) + [float("inf")], cum):
                    lines.append(f"{m.name}_bucket{labelstr(m.labelnames, key, [('le', format_value(b))])} {format_value(c)}")
                lines.append(f"{m.name}_sum{labelstr(m.labelnames, key)} {format_value(child.sum)}")
                lines.append(f"{m.name}_count{labelstr(m.labelnames, key)} {format_value(child.count)}")
            else:
                lines.append(f"{m.name}{labelstr(m.labelnames, key)} {format_value(child.value)}")
    return "\n".join(lines) + "\n" if lines else ""

Look under the hood

Run the experiments in this section before moving on; each one is a sentence of chapter 4 as a number. First, how much does the bucket layout cost in accuracy? Here are the three layouts of the milestone-3 check on one seed (30,000 latencies: a lognormal body around 40 ms plus a 2% slow mode), with the error of each estimated quantile relative to the exact one:

Layoutp50p90p99p99.9
exact40.5 ms91.7 ms401.4 ms626.3 ms
exponential ×1.25 (40 buckets)40.8 (+0.7%)93.3 (+1.7%)401.7 (+0.1%)633.6 (+1.2%)
exponential ×2 (14 buckets)43.6 (+7.5%)108.9 (+18.7%)417.5 (+4.0%)935.2 (+49.3%)
linear 50 ms (40 buckets)39.5 (-2.6%)96.7 (+5.4%)401.6 (+0.0%)630.4 (+0.7%)

The exponential layout with factor 1.25 is within 2% everywhere here, which is far better than its 25% bound because the data is smooth inside each bucket. Doubling the bucket width (factor 2, 14 buckets instead of 40) costs accuracy in the tail, up to 49% at p99.9, still inside the bound of 100%. The linear layout with 50 ms buckets bounds its absolute error by 50 ms everywhere: invisible on a 400 ms p99 (0.0% here), but it would be useless for a 5 ms service whose whole distribution fits inside the first bucket. The median looks fine here (−2.6%) only because the first bucket's contents happen to be smooth. Series cost scales with bucket count: 40 + 1 + 2 = 43 series per label combination for the first layout against 14 + 1 + 2 = 17 for the second.

Second, the place where bounds matter most is the one you chose them for. Chapter 2's latency SLI is "the fraction of requests at or under 300 ms", which is one cumulative count divided by the total: if 300 is a bucket bound there is no interpolation at all. With bounds from the geometric layouts it is interpolated, and here it happens to be within 0.020 percentage points of the truth because the density is smooth near 300 ms; with a bound exactly at 300 the answer is the exact count. Run it:

$ python3 -c "
import math, random
import solution as m
rng = random.Random(1)
xs = [rng.lognormvariate(math.log(40), 0.6) + (rng.uniform(100, 600) if rng.random() < 0.02 else 0) for _ in range(30000)]
exact = sum(x <= 300 for x in xs) / len(xs)
def fraction_le(x, ch):                       # the SLI: interpolate the cumulative curve at x
    cum, b = ch.cumulative(), ch.bounds
    i = next(i for i, bound in enumerate(b) if x <= bound)
    lo, clo = (b[i - 1] if i else 0.0), (cum[i - 1] if i else 0)
    return (clo + (cum[i] - clo) * (x - lo) / (b[i] - lo)) / cum[-1]
print(f'exact fraction <= 300 ms: {100 * exact:.4f}%')
for name, bounds in (('x1.25, no bound at 300', m.exponential_buckets(1, 1.25, 40)),

    h = m.Histogram('l_ms', 'x', bounds)
    for x in xs:
        h.observe(x)

Reliability connection

This lab sits between two others. Lab 1 consumed per-minute counts of good and bad events; those counts come from counters like yours, and its latency SLI is the fraction of a histogram at or under a threshold. Lab 3 keeps the per-request detail that this lab deliberately throws away, and the exemplar stretch goal connects them. The idea underneath the whole lab is a distributed-systems one: an aggregate is useful across machines when it can be merged in any order (here, bucket counts are a commutative, associative sum), which is also what makes it safe to compute on each host and combine later (the CRDT lab uses the same property for convergence). The networking background on why the tail matters is in networking chapter 13.

What you learned

  • Counters count totals and gauges hold levels; labels name a series, and every distinct combination is a series. A registry can enforce a cardinality limit per metric, loudly, while leaving existing series alone.
  • A histogram is a counter per bucket plus a sum and a count. The bound is inclusive (le), the buckets are cumulative in the exposition, and a child costs buckets + 1 + 2 series.
  • A quantile estimate comes from straight-line interpolation inside the bucket holding the rank, so it lies in the same bucket as the exact answer and is wrong by at most the bucket width; a rank in +Inf returns the top bound, a silent under-estimate.
  • Histograms merge by adding bucket counts, in any order and grouping, provided the bounds match. Quantiles are computed once, after merging; the average of per-host p99s can be several times too high or too low.
  • The text format has strict rules (HELP then TYPE, ordered cumulative buckets, a final +Inf equal to _count, escaping). A scraper that rejects a page rejects all of it, so test the output with a validator that is independent of the code that wrote it.
  • Put a bucket bound at each SLO threshold, keep unbounded identifiers out of labels, and send per-request detail to logs and traces.

Check your understanding

A metric http_requests_total has labels route and status. Your code calls labels(route="/cart") only. What should the library do?

  1. Create a child with status set to the empty string
  2. Raise ValueError: a metric has exactly the labels it declared, and a series missing one cannot be aggregated with its siblings
  3. Create the child and warn
  4. Ignore the call
Label sets are part of the metric's identity. Silently accepting a missing label creates a series that no query on status will include, which is a bug you find weeks later.

Why does the registry raise on a new label combination instead of simply storing it?

  1. Storing it would be slower for the next increment of the same series
  2. Python dictionaries cannot hold more than 1,000 keys
  3. Series count multiplies with every label, an unbounded label (user id, request id) creates series without limit, and the cost lands on the monitoring system, usually during an incident
  4. Counters cannot be created after start-up
Cardinality is the cost of a metric. A defensive library refuses growth beyond a limit while continuing to serve existing series, and counts the refusals so the problem is visible.

Observations 0.0625, 0.125, 0.25 and 2.0 go into a histogram with bounds 0.125, 0.5 and 1. What does the exposition show for the le="0.5" bucket?

  1. 1, the number of observations between 0.125 and 0.5
  2. 3, because buckets are cumulative: it counts everything at or below 0.5, including the two in the first bucket
  3. 2
  4. 4, because the last bucket always equals the count
The bucket labelled le="0.5" counts observations ≤ 0.5: 0.0625, 0.125 (the bound is inclusive) and 0.25. The +Inf bucket is the one that equals the count (4).

Every value in a histogram is 51 ms, and the buckets are (0, 50], (50, 100], (100, 200]. What does the library report for the median, and what does it show?

  1. 51: histograms store exact values
  2. 50, the lower bound of the bucket
  3. 75: it assumes values are spread evenly inside the bucket, so the error is bounded by the bucket's width but not zero
  4. NaN
Interpolation sits halfway between 50 and 100 when the rank is halfway through the bucket's count. The answer is wrong by 24 ms and cannot be wrong by more than 50: the bucket width is the error bar.

Three hosts have p99s of 90 ms, 95 ms and 900 ms. The first two serve 90,000 requests each; the third serves 2,000. Averaging gives about 360 ms. Why is the fleet's true p99 close to 94 ms (as in the lab)?

  1. Percentiles depend on the number of requests behind each host: the slow host's 2,000 requests, with 8% of them slow, are about 160 of 182,000 (under 0.1%), too few to move the 99th percentile
  2. Averaging always underestimates
  3. The slow host is ignored by the monitoring system
  4. The median of the three p99s is 95, so 94 is just a rounding of that
The p99 of the pooled data is the value below which 99% of all requests fall; 160 slow requests in 182,000 cannot shift that. The average of p99s weights each host equally regardless of its traffic, which is the error. The merged histogram has the right weights built in because it adds counts.

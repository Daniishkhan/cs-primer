What Counts as Self-Improvement

A loop that raises its own score has not necessarily improved. This chapter turns Weco's four Level-1 conditions into four tests you can run on any log: a fair baseline, a sustained trend, scores on tasks the loop never saw, and a budget fixed in advance. It then shows the arithmetic that tells a real gain from a lucky one.

Why this matters

This chapter serves Artifact 4, your small-scale copy of Weco's AIDE² system: its Level-1 write-up is judged on exactly these four conditions, and a result that fails any one of them is not finished. Without the tests, an outer loop that rewrites your Artifact 2 agent will always appear to work. A search that keeps whatever scores best on a noisy number will always find something that scores well on it. After this chapter you can take a run log and say, condition by condition, whether it shows self-improvement: you can build a baseline that gets the same budget, compute a paired interval, tell a trend from one lucky accept, and state the budget in a form the code enforces. Lab 1 turns the four tests into a checker, and Case 1 applies them to Weco's own claim. Chapter 03 prices the loop; chapter 04 audits other people's claims with the same tests.

Two loops, and the claim

A self-improvement claim always involves two loops. The inner loop is an agent doing a job: here, an autoresearch agent that edits code, runs it and keeps the edit if a score goes up (the keep-or-revert loop of A9 chapter 01). The outer loop is a second process that improves the inner agent itself. It proposes a rewrite of the inner agent's code or prompts, runs the rewritten agent on a set of tasks, and keeps the rewrite if it beats the best version so far. If the outer agent and the inner agent are the same program, or the inner agent was produced by an earlier round of the outer loop, the system is improving itself.

Weco, a small AI-research company, gave the question a ladder in a post of 10 July 2026 ("4 Levels of Recursive Self-Improvement"). The levels count from zero. Level 0, delegation: you hand the research loop to an autonomous system, and it improves the system more slowly than human research would. Level 1, net positive: it improves itself more efficiently than humans improving the same system by hand. Level 2, ignition: it improves its own ability to improve, so a successor it built is a better improver than its predecessor. Level 3, inflection: the feedback outweighs the diminishing returns, so the gain each generation buys at a fixed budget grows instead of shrinking. Each level is a necessary condition for the next. Artifact 4 aims at Level 1 and then runs the Level 2 ignition test; chapter 03 explains why Level 3 is the hard one.

The post gives Level 1 four conditions, and the artifact standards of chapter 00 repeat them in the roadmap's words:

  1. A fair baseline. Your own hand-tuned version, given the same budget and the same number of attempts.
  2. A sustained trend. Gains across several steps, not one lucky accept.
  3. Generalisation. Scores on tasks the loop never saw while it searched.
  4. A fixed physical budget. Dollars, GPU-hours and steps stated before the run, and never exceeded.

State of play, October 2026: what Weco reports for AIDE²

All of the following is self-reported by Weco, in a blog post of 14 July 2026 and a technical report (Srikanth, Zhao, Xu, Wu and Jiang, arXiv 2609.26457, submitted 22 September 2026, 28 pages). No independent replication was found when this page was written. The post says its system, AIDE², ran for eight unattended days and 100 outer steps, produced seven successive improved versions, and rejected about nine in ten proposals. It reports that the best versions beat the starting agent on MLE-Bench Lite (a small version of a benchmark of machine-learning-engineering competitions; a paired gain of +0.053, p = 0.0024, for version 47) and on two other benchmarks the loop never used, and that a hand-tuned human agent was the Level-1 reference. The post also states that the efficiency gain of its ignition test was not statistically significant, and that "we do not think the system achieved third-order generalization". The arXiv abstract, as the fetch tool summarised it, reports four held-out benchmarks and a drop in reward hacking from 55% to 32% on a separate task family; the blog reports 63% to 34% on KernelBench kernels. The two figures describe different task sets, and a careful reader keeps both. Sources are in Further reading. Treat all of it as a claim to test with this chapter, not as a fact.

Condition 1: a fair baseline

A claim of improvement is a comparison, and a comparison is only as honest as its other arm. The usual way to weaken the baseline without lying is to give it less: fewer attempts, no tuning, a worse model, one seed. The Level-1 rule closes this by fixing three things. The baseline is human-tuned, meaning a person has taken the same agent and improved it by hand. It gets the same budget in dollars and tokens. And it gets the same number of attempts, so a loop that evaluated 100 candidates is compared with a baseline that also evaluated 100.

Why does the number of attempts matter so much? Because picking the best of many noisy tries is itself an improvement method. If one edit has a true effect that is a small random number, then trying 100 edits and keeping the highest-scoring one gives you the top of a distribution, and the top of a distribution is above the middle even when no edit helps. A baseline given one try, against a loop given a hundred, is losing to the number of tries and not to the idea.

The script below builds both arms from the same toy world. The loop is a sequential hill-climber: each accepted edit builds on the last. The baseline is best-of-n: n independent edits of the starting agent, keep the best. Both choose by a noisy public score and are judged on a less noisy private score. Each of 20 tasks has its own starting quality, and both arms share it, so the comparison is paired. All numbers are illustrative assumptions, not measurements of any real system.

"""A fair baseline gets the same budget: compare a loop with best-of-n.

Run: python3 fair_baseline.py
"""
import random

# ── 1. Assumptions (illustrative) ────────────────────────────────────────
SEEDS = 20
STEPS = 100            # evaluations the loop spends
PROPOSAL_MEAN = -0.001 # most edits hurt a little
PROPOSAL_SD = 0.01
PUBLIC_NOISE = 0.03
PRIVATE_NOISE = 0.005
START_LO, START_HI = 0.30, 0.70   # each seed is a different task


def loop(rng, start, steps):
    """Sequential hill-climber: each accept builds on the last one."""
    q = start
    best = q + rng.gauss(0, PUBLIC_NOISE)
    for _ in range(steps):
        c = q + rng.gauss(PROPOSAL_MEAN, PROPOSAL_SD)
        pub = c + rng.gauss(0, PUBLIC_NOISE)
        if pub > best:
            q, best = c, pub
    return q + rng.gauss(0, PRIVATE_NOISE)


def best_of_n(rng, start, n):
    """Baseline: try n independent edits of the start, keep the best."""
    top_q, top_pub = start, start + rng.gauss(0, PUBLIC_NOISE)
    for _ in range(n):
        c = start + rng.gauss(PROPOSAL_MEAN, PROPOSAL_SD)
        pub = c + rng.gauss(0, PUBLIC_NOISE)
        if pub > top_pub:
            top_q, top_pub = c, pub
    return top_q + rng.gauss(0, PRIVATE_NOISE)


def paired_ci(diffs, rng, reps=4000):
    """95% bootstrap interval for the mean of paired differences."""
    means = sorted(
        sum(rng.choice(diffs) for _ in diffs) / len(diffs)
        for _ in range(reps))
    return means[int(0.025 * reps)], means[int(0.975 * reps)]


# ── 2. Both arms share each task's start; two baseline budgets ───────────
for label, n in (("unfair: baseline gets 10 evaluations", 10),
                 ("fair:   baseline gets 100 evaluations", 100)):
    diffs = []
    for seed in range(SEEDS):
        start = random.Random(seed).uniform(START_LO, START_HI)
        a = loop(random.Random(seed), start, STEPS)
        b = best_of_n(random.Random(1000 + seed), start, n)
        diffs.append(a - b)
    lo, hi = paired_ci(diffs, random.Random(0))
    mean = sum(diffs) / len(diffs)
    print(f"{label}: loop minus baseline = {mean:+.4f}  "
          f"95% CI [{lo:+.4f}, {hi:+.4f}]")
unfair: baseline gets 10 evaluations: loop minus baseline = +0.0330  95% CI [+0.0179, +0.0512]
fair:   baseline gets 100 evaluations: loop minus baseline = +0.0274  95% CI [+0.0108, +0.0460]

Against a baseline that gets only 10 evaluations the loop wins by 0.033, with an interval that excludes zero. Give the baseline the same 100 evaluations and the margin shrinks to 0.027. The claim survives here, but it is 17% smaller, and the unfair comparison is the one a press release would quote. In a world where the loop's edits were worth less, the same correction can remove the whole margin, which is why the rule exists. The interval comes from a bootstrap: resample the 20 per-task differences with replacement many times and read the middle 95% of the resampled means. A0 chapter 15 derives it.

Analogy: the practice exam

A student who has taken the same practice paper five times will score higher on it each time, even if they have learned nothing transferable. Reporting that rising number as learning is the mistake this whole chapter is about. A fair baseline asks what a second student would have scored with the same five attempts and a tutor's help. A private split asks for a different paper.

Where it breaks down: a student remembers the paper, whereas a search loop can learn it in a more literal way: it can write code that detects the test. That is evaluator hacking, which A7 chapter 15 covers, and it is a failure the analogy understates.

Condition 2: a sustained trend

A loop with a noisy score will occasionally produce a big jump that is not repeatable. One accept that adds 0.065 to a score with a noise floor of 0.02 is more than three noise widths, so it looks impressive, but a single draw cannot tell luck from skill. Three questions about the trajectory of kept versions separate the cases. How far did the final version move from the start, in noise floors? Is the trend monotonic in rank terms, measured by Kendall's tau (the share of pairs of steps in which the later one scored higher, minus the share in which it scored lower, so +1 means always rising)? And what remains if you delete the single biggest step? The script runs these on two logs of private scores. The numbers are made up to show the shape of the two cases.

"""Sustained trend or one lucky accept? Two made-up private-score logs.

Run: python3 trend.py
"""

# ── 1. Private scores of each kept version (illustrative numbers) ────────
NOISE_FLOOR = 0.02     # run-to-run sd of one private score
LOGS = {
    "steady": [0.500, 0.512, 0.531, 0.540, 0.561, 0.570, 0.592],
    "lucky ": [0.500, 0.497, 0.503, 0.568, 0.566, 0.569, 0.567],
}


def kendall_tau(ys):
    """Rank correlation of score with step number: +1 is monotonic up."""
    pairs = [(i, j) for i in range(len(ys)) for j in range(i + 1, len(ys))]
    s = sum((ys[j] > ys[i]) - (ys[j] < ys[i]) for i, j in pairs)
    return s / len(pairs)


def report(name, ys):
    total = ys[-1] - ys[0]
    steps = [b - a for a, b in zip(ys, ys[1:])]
    biggest = max(steps)
    # ── 2. Three questions a reviewer asks of the trajectory ─────────────
    without_best = total - biggest      # gain if the best step is removed
    print(f"{name} final minus start  {total:+.3f}  "
          f"({total / NOISE_FLOOR:.1f} noise floors)")
    print(f"{name} Kendall tau        {kendall_tau(ys):+.2f}")
    print(f"{name} biggest single step {biggest:+.3f}; "
          f"gain without it {without_best:+.3f}")


for name, ys in LOGS.items():
    report(name, ys)
steady final minus start  +0.092  (4.6 noise floors)
steady Kendall tau        +1.00
steady biggest single step +0.022; gain without it +0.070
lucky  final minus start  +0.067  (3.3 noise floors)
lucky  Kendall tau        +0.62
lucky  biggest single step +0.065; gain without it +0.002

Both logs end well above their start, 4.6 and 3.3 noise floors. The steady log passes all three questions. In the lucky log one step supplied 0.065 of the 0.067 total, and without it the gain is 0.002. Weco's post reports seven successive improved versions over 100 steps, and its table of about 95 rejected proposals from one seed is a useful thing to publish, because it shows how rarely a step passes the gate. That is the pattern to expect in your own run, and the point of the condition is to look at accepted steps one at a time: the claim is a sequence of seven small gains, and each should clear the noise on its own or be shown to add up.

Condition 3: tasks the loop never saw

Every score the loop optimises is selected: the loop keeps a candidate because its score was high. A high score has two parts, the candidate's real quality and a lucky draw of noise, and selecting on a high score selects on both. This is the winner's curse. The more candidates, the more noise the winner is carrying. The cure is to measure the winner again on data that played no part in the selection, so the noise is fresh. That is what a private split is: scores on tasks, or data, that the proposer never sees and that never decide what is kept (A7 chapter 16; the engineering is in A10 chapter 03).

The script below is the smallest model of the curse I could write. Each step proposes an edit whose true effect is tiny, with a standard deviation of 0.004 and a mean of zero. The loop scores the candidate once on the public split with noise of 0.03 and keeps it if that score beats the best so far. At intervals the held agent is also scored on a larger private split, whose noise is 0.005.

"""Accepting on a noisy public score: public gains outrun real ones.

Run: python3 winners_curse.py
"""
import random

# ── 1. Assumptions (illustrative, not from any paper) ────────────────────
SEED = 7
STEPS = 100            # outer-loop steps
PROPOSAL_SD = 0.004    # a typical edit changes true quality by this much
PUBLIC_NOISE = 0.03    # sd of one public evaluation
PRIVATE_NOISE = 0.005  # private split is bigger, so its sd is smaller
START = 0.50           # true quality of the starting agent

rng = random.Random(SEED)


def evaluate(true_quality, noise):
    """One noisy score of an agent whose real quality is known to us."""
    return true_quality + rng.gauss(0, noise)


# ── 2. The loop: keep a candidate if its public score beats the best ─────
true_q = START
best_public = evaluate(true_q, PUBLIC_NOISE)
accepted = 0
print(f"{'step':>4} {'accepts':>7} {'best public':>12} "
      f"{'true quality':>13} {'private score':>14}")
for step in range(1, STEPS + 1):
    cand_q = true_q + rng.gauss(0, PROPOSAL_SD)
    cand_public = evaluate(cand_q, PUBLIC_NOISE)
    if cand_public > best_public:
        true_q, best_public = cand_q, cand_public
        accepted += 1
    if step % 20 == 0:
        private = evaluate(true_q, PRIVATE_NOISE)
        print(f"{step:>4} {accepted:>7} {best_public:>12.3f} "
              f"{true_q:>13.3f} {private:>14.3f}")

# ── 3. The gap between what the loop saw and what is real ────────────────
print(f"public gain  {best_public - START:+.3f}")
print(f"true gain    {true_q - START:+.3f}")
step accepts  best public  true quality  private score
  20       2        0.535         0.501          0.502
  40       3        0.541         0.501          0.509
  60       4        0.549         0.505          0.509
  80       4        0.549         0.505          0.509
 100       5        0.586         0.504          0.498
public gain  +0.086
true gain    +0.004

After 100 steps the best public score has risen by 0.086, and the real gain is 0.004. The loop accepted five candidates, and every one was kept because its public noise was lucky. The private column hovers around 0.50 to 0.51, which is the truth. The figure draws the same run.

Generalisation has a second, stronger form that Weco calls out. Tasks the loop never saw can be in distribution, like another MLE-Bench Lite competition, or far out of distribution, like a weather-forecasting benchmark with a fixed $15 budget per agent. A loop that improved only the first kind may have specialised, and one that improved both has probably changed something general. Report them separately. In the Artifact 4 task mix, the six tasks are scored on private splits for the search, and a further family of tasks stays untouched until the end.

Common misconception

"The loop's score went up, so it improved." The score the loop optimises is the one most polluted by selection. The right statement is that the loop's public score went up, which is expected by construction. Self-improvement is a claim about the private score, the unseen tasks, and a comparison with a fair baseline, in that order of importance.

Condition 4: a fixed physical budget

The fourth condition is the easiest to state and the easiest to violate by accident. A loop that spends more compute at each step, or more steps, will tend to find more. If the claim is that the algorithm got better, the budget must not be what changed. Weco's phrasing is that the gains "must come from genuinely better algorithms, not from spending more", and its post fixes a per-evaluation dollar cost so that an agent cannot win by making longer, costlier calls.

The practical form is a ledger: an object outside the agent that counts dollars, steps and evaluations, charges every model call to it, and raises an error when a limit would be crossed. State the budget before the run, give each arm its own identical ledger, and print both at the end. A budget in a README that nothing enforces is a hope.

"""A fixed physical budget, enforced in code rather than promised in prose.

Run: python3 budget.py
"""


class BudgetExceeded(Exception):
    pass


class Ledger:
    """Counts dollars, steps and evaluations; refuses to go over."""

    def __init__(self, dollars, steps):
        self.limit = {"dollars": dollars, "steps": steps}
        self.used = {"dollars": 0.0, "steps": 0}

    def charge(self, dollars=0.0, steps=0):
        for key, amount in (("dollars", dollars), ("steps", steps)):
            if self.used[key] + amount > self.limit[key]:
                raise BudgetExceeded(f"{key}: {self.used[key] + amount:g} "
                                     f"> {self.limit[key]:g}")
        self.used["dollars"] += dollars
        self.used["steps"] += steps


# ── Both arms of the comparison get their own, identical ledger ──────────
loop, baseline = Ledger(dollars=25.0, steps=100), Ledger(25.0, 100)
COST_PER_STEP = 0.25        # illustrative: model calls for one evaluation

for step in range(1, 200):
    try:
        loop.charge(dollars=COST_PER_STEP, steps=1)
        baseline.charge(dollars=COST_PER_STEP, steps=1)
    except BudgetExceeded as why:
        print(f"stopped at step {step}: {why}")
        break
print("loop     used", loop.used)
print("baseline used", baseline.used)
stopped at step 101: dollars: 25.25 > 25
loop     used {'dollars': 25.0, 'steps': 100}
baseline used {'dollars': 25.0, 'steps': 100}

Both arms stop at step 101 on the dollar limit, having used exactly $25 and 100 steps. If your loop sometimes calls a larger model, or retries on failure, the ledger records it, and the final table can show cost per arm next to the score. Chapter 03 turns that cost into a price per accepted improvement.

Systems connection

The ledger is a resource quota, the same idea as a cgroup limit or an API rate limit: enforcement lives outside the thing being limited, because the thing being limited cannot be trusted to count itself. The private split is privilege separation: the evaluator holds data the proposer cannot read, just as a service does not hand its credentials to the code it sandboxes. A11 builds the second idea in full.

Is the difference real? The paired test

Conditions 1 and 3 give you scores for the loop and the baseline on the same tasks. The last step is to say whether the difference is larger than chance. With paired data the natural tool is the paired t statistic. Pair the two scores on each task, take the difference, and ask how many standard errors the mean difference sits from zero. Pairing matters because tasks differ in difficulty: a hard task lowers both arms, and subtracting removes that shared part before any noise is counted. A6 chapter 04 develops the theory and the cautions, and the roadmap's standard asks for at least three seeds, a confidence interval and a paired test.

Plug in numbers. Six tasks, a loop and a baseline, scores made up for illustration. Each printed line is one step of the build-up above.

The idea

  1. d ← loop score minus baseline score, task by task
  2. mean ← average of d
  3. sd ← sample standard deviation of d (divide by n − 1)
  4. se ← sd divided by sqrt(n)
  5. t ← mean divided by se
"""The paired t statistic, one build-up step per printed line.

Run: python3 paired_t.py
"""
import math

# ── 1. Private scores of the loop and the baseline on six tasks ──────────
LOOP = [0.62, 0.55, 0.71, 0.48, 0.66, 0.59]       # illustrative
BASE = [0.58, 0.54, 0.66, 0.49, 0.61, 0.55]
N = len(LOOP)

# ── 2. Build the statistic from the inside out ───────────────────────────
d = [a - b for a, b in zip(LOOP, BASE)]            # per-task difference
d_bar = sum(d) / N                                 # mean difference
s_d = math.sqrt(sum((x - d_bar) ** 2 for x in d) / (N - 1))
se = s_d / math.sqrt(N)                            # standard error
t = d_bar / se

print("1. differences d_i      ", [round(x, 2) for x in d])
print(f"2. mean difference      {d_bar:.4f}")
print(f"3. sd of differences    {s_d:.4f}")
print(f"4. standard error       {se:.4f}   (sd / sqrt({N}))")
print(f"5. t = mean / SE        {t:.2f}   with {N - 1} degrees of freedom")
1. differences d_i       [0.04, 0.01, 0.05, -0.01, 0.05, 0.04]
2. mean difference      0.0300
3. sd of differences    0.0245
4. standard error       0.0100   (sd / sqrt(6))
5. t = mean / SE        3.00   with 5 degrees of freedom

A t of 3.0 on five degrees of freedom corresponds to a two-sided p-value of roughly 0.03, a modest result. With six tasks the test has little power, which is why the standard asks for a confidence interval next to it and says nothing about results too close to call. A significant t on two tasks would be weaker than the same t on twenty. Do not report a p-value without the interval and the number of tasks.

Four ways a log passes by accident

Most failures of these tests are not fraud. They are small decisions that look reasonable when made. Four are common enough to check for by name.

Peeking at the private split
The proposer, or you, looks at a private score to check how things are going, and adjusts. From that moment the split is public, and its noise is no longer fresh. Count every look, and retire the split if one happens.
Re-running until it passes
Running the whole experiment five times and reporting the best is selection again, one level up. Fix the number of runs in advance, and report all of them.
A baseline tuned less than the loop
The loop's author spent weeks on the harness and an afternoon on the baseline. State how long each arm was tuned by a person, and ask a colleague to spend equal time on the baseline if you can.
Budget that moves with the arm
The loop retries failed calls and the retries are not charged, or the loop is allowed a larger model for one step. Charge everything to the ledger, including retries and the cost of running the evaluator.

Each of these maps onto one of the four conditions, and each leaves a trace if the run is logged properly. A log that records the number of private-split reads, the random seeds, the tuning hours of each arm and the ledger totals lets a reviewer find all four in a few minutes. That is the reason the write-up template in chapter 00 puts "seeds, costs, hardware" in a fixed place.

One outer step, end to end

The four conditions are checks on the log of an outer loop. The stepper follows a single outer step and marks where each check reads its inputs.

Step through

One outer step and the four checks

  1. Propose. The outer agent rewrites the inner agent and produces a candidate. Nothing has been scored yet.
  2. Score in public. The candidate runs on the public split. The proposer may see these results, so they steer the next proposal.
  3. Select. The candidate is kept if its public score beats the best so far. This is the step where the winner's curse enters.
  4. Score in private. Kept versions are scored on a split the proposer never sees and that never decides what to keep. This log is what conditions 2 and 3 read.
  5. Run the other arm. The hand-tuned baseline gets the same attempts and an identical ledger, and is scored on the same private tasks (condition 1 and condition 4).
  6. Check. The paired differences, the trend over kept versions, the unseen-task families and the two ledgers go into the Level-1 report.

After Level 1: ignition

Passing the four conditions says the loop beat a person on the tasks it was given. It does not say the loop is getting better at improving. Weco's Level 2, ignition, tests that with a swap: take the agent the loop discovered, install it in the outer-loop seat in place of the human-tuned outer agent, rerun the outer loop on the training distribution, and compare. If the discovered agent reaches the same ceiling in fewer steps, or a higher one, it is a better improver, and the gain on the inner task has generalised to the improver's own job. The Weco post reports that its version 47, installed as the outer agent, reached a similar ceiling in about 20 steps against about 40 for the human-tuned outer agent, and then states that the difference was not statistically significant and that ignition was not demonstrated. That is a negative-leaning result reported plainly, and Artifact 4's extension is to run the same test on your loop, with seeds enough to say something definite either way.

Key takeaways

  • Self-improvement means an outer loop makes the inner agent better; the claim is checked against four conditions, not against the loop's own score.
  • A fair baseline has the same budget and the same number of attempts; best-of-n is itself an improvement method.
  • A sustained trend survives deleting the single biggest step; report the final gain in noise floors and Kendall's tau.
  • Selection on a noisy score produces the winner's curse; only a private split with fresh noise measures the real gain.
  • A budget is enforced by a ledger outside the agent, with identical limits for every arm.
  • Report a paired difference with an interval and the number of tasks; a t statistic alone is not enough.
  • Ignition asks whether the discovered agent is a better improver; Weco's own post says it did not show that.

Check your understanding

A loop evaluated 100 candidates and beat a hand-tuned baseline that was run once. What is the most important thing to fix before claiming improvement?

  1. Report the improvement on the public score so it looks larger
  2. Run the loop for more steps
  3. Give the baseline the same budget and the same 100 attempts
  4. Switch the baseline to a stronger model than the loop uses
Best-of-many is an improvement method in itself, so a one-try baseline loses to the number of tries. Equal attempts and budget (condition 1) isolates the idea. A stronger baseline model would be a different unfairness, and running longer or reporting public scores makes the winner's curse worse.

In the made-up logs, a steady log gains 0.092 and a lucky log gains 0.067. Deleting each log's biggest step leaves +0.070 and +0.002. What does that show?

  1. The lucky log's gain depends on one step, so it is not a sustained trend
  2. The steady log is too good to be true
  3. Both logs have the same trend because both end above their start
  4. The noise floor is too high to say anything about either
Condition 2 is about the sequence of gains. A result that vanishes when one step is removed rests on one draw. Ending above the start is not enough, which is why option 3 tempts and fails. The steady log's gain is spread across steps.

The winner's-curse script shows a public gain of +0.086 and a true gain of +0.004. What causes the gap?

  1. The private split is easier than the public split
  2. The edits were harmful on average
  3. The proposer overfitted the private split
  4. Candidates were kept because their public noise was lucky, and selection kept the noise
Each kept candidate had a high public score, which mixes real quality and noise; with a true effect near zero, nearly all of what was selected was noise. The proposer never sees the private split in this setup, so option 3 is wrong, and the edits were not harmful on average: they were centred on zero.

Which statement best describes a fixed physical budget in the Level-1 sense?

  1. Dollars are stated in the write-up after the run
  2. Dollars, steps and evaluations are stated beforehand and enforced by something outside the agent, identically for every arm
  3. The loop is told to be economical and checks itself
  4. The baseline gets half the loop's budget because it is simpler
A budget the agent counts for itself, or states afterwards, can be exceeded without anyone noticing. Identical limits for every arm are what make condition 1 and condition 4 compatible, so a half-budget baseline fails both.

With six tasks, a mean paired difference of 0.030 and a standard deviation of the differences of 0.0245, which t statistic do you compute?

  1. 1.2
  2. 1.8
  3. 3.0
  4. 7.3
The standard error is 0.0245 divided by the square root of 6, which is 0.0100, and 0.030 divided by 0.0100 is 3.0. Forgetting the square root of n gives 0.030 divided by 0.0245, about 1.2, the tempting wrong answer.

What does Weco's ignition test add to the four Level-1 conditions?

  1. It checks whether the discovered agent is a better improver when installed in the outer-loop seat
  2. It checks whether the loop spent less than its budget
  3. It checks whether the baseline was tuned by a human
  4. It checks whether public and private scores agree
Level 1 compares the loop's result with a human's on the loop's tasks. Ignition asks for a different thing: whether the improvements the system made improve its improving. The other options are Level-1 checks.

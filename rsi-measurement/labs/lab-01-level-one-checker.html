Lab 1: The Level-1 Checker

Weco's report of recursive self-improvement rests on four conditions: a fair baseline, a sustained trend, generalisation to tasks never searched, and a fixed budget. Chapter 1 states them as tests you can run. In this lab you write the program that runs them. It reads the log of a self-improvement loop, decides condition by condition whether the loop earned the word "improvement", prints a report card, and finally scores how automated a loop is on a published rubric. The same checker is what Artifact 4 points at its own outer loop.

Why this lab matters

This lab is a step of Artifact 4, AIDE²-in-miniature (Weco's self-rewriting research agent, AIDE², at small scale). An outer agent rewrites your Artifact 2 agent, and Weco's four Level-1 conditions judge the result. After this lab you have the judge. Every claim of improvement in the other artifacts goes through the same four questions, so the code you write here is code you will run on your own logs for the next year.

The conditions are easy to nod along to and easy to fail in practice. A baseline given half the budget makes any loop look good. A run with one big accept and a lot of noise looks like a trend until you ask how many accepts cleared the noise. A held-out score computed on a task the loop also searched on is a training score with a new name. And a loop that overspends has changed the question. Writing the checks makes each failure concrete, and the fixtures in this lab contain one of each. The weakness of the checker is also worth feeling: it can only judge the log it is given, so a log that omits what went wrong passes. The chapter on reading self-improvement claims covers that limit, and the Weco case study applies the conditions to a real report.

It builds on A7 chapter 16 (separate search, selection and test sets) and A6 chapter 4 (error bars and paired comparisons). The economics of the same loop, cost per accepted improvement, is chapter 3.

Synthetic logs, standard library only, no clock

The fixture logs in logs/ are synthetic: make_fixtures.py writes them from a seeded random generator to imitate the shape of a run, not any real system, and each is built to pass or fail one specific check. Nothing here calls a model or the network. Python 3.9 or newer, standard library only. A failing random check prints its seed, and python3 check.py solution 3 2 replays milestone 3 on seed 2 alone. The reference solution passes in well under a second. The log shape (one JSON object per line, append-only) is the one A9's run store uses; the field names are this lab's own.

What you'll build

The six milestones, each building on the one before:

  1. Parse the run log: turn JSON lines into runs with budgets, and fail with a line number when a line is unusable.
  2. A fair baseline: same budget, same attempts, a baseline that really used them, and an improver that beats it.
  3. A sustained trend: count the accepts that clear the noise floor and refuse a trend carried by one jump.
  4. Generalisation: a paired gain, with an interval, on tasks the search never touched.
  5. The budget and the report card: catch the step where money ran out, then combine the four verdicts.
  6. An automation level: score each task of a loop on a 0 to 5 rubric and find the weakest link.

The run log

A run log is the record a self-improvement loop writes as it works. This lab's logs have three kinds of line, each a JSON object with a type. A header states, before anything runs, the budget in dollars, the allowed number of attempts (proposals), the noise floor (the smallest score change that counts as real, found by re-running the same agent) and the search tasks the loop may look at. A step line is one attempt: what it cost, how the candidate scored on the search tasks, whether the loop kept it (accepted), and the best kept score so far (the incumbent). An eval line is a report-time measurement of the incumbent on a named task and seed, either initial (before any search) or final. The first lines of improver_good.jsonl:

{"type": "run", "run_id": "improver-good", "arm": "improver", "budget_usd": 60.0, "max_attempts": 30, "noise_floor": 0.01, "search_tasks": ["s1", "s2", "s3"]}
{"type": "step", "run_id": "improver-good", "step": 2, "cost_usd": 2.0, "search_score": 0.4832, "accepted": false, "incumbent": 0.5}
{"type": "step", "run_id": "improver-good", "step": 3, "cost_usd": 2.0, "search_score": 0.53, "accepted": true, "incumbent": 0.53}

Step 3 is an accept: the candidate scored 0.53 against an incumbent of 0.50, so the incumbent became 0.53. The fixture's eval lines (36 of them: six held-out tasks, three seeds, two stages) look like this: {"type": "eval", "run_id": "improver-good", "stage": "initial", "task": "h1", "seed": 1, "score": 0.4852}. Weco's published criteria have the same bones. Their blog post words the four conditions as "a fair human baseline," "a sustained multi-step trend," "generalization beyond the optimized measurement," and "a fixed physical budget" (Weco, 14 July 2026), and their paper describes a private held-out score that the inner loop never sees, evaluated under a per-task dollar budget.

Milestone 1: parse the run log

A checker that trusts its input is a rubber stamp, so the parser is the first line of defence. It must turn lines into Run objects, and it must refuse a log it cannot trust, saying where. The rule that matters most is order: the header comes first, because the budget has to be stated up front. A step that appears before its run's header is a log that was written after the fact, and the parser should say so.

Use json.loads on each non-blank line. Count lines from 1 including blank ones, so the number in an error message matches what an editor shows. Several runs can share a file, keyed by run_id; return them in header order.

Common misconception

"Skip the lines you cannot parse and carry on." A log with a dropped line is a log with a missing attempt, and a missing attempt can hide a rejected proposal, a cost or a crash. Every check later in the lab counts steps and money. An error that stops the checker is cheaper than a pass built on a log with holes.

Your task

Write parse_log(text): return a list of Run objects with their steps and evals filled in, or raise LogError with a message that starts line N:.

It checks a small log by hand (every field, the blank line skipped), six kinds of bad input each with the right line number (invalid JSON, no type, a step before its header, a step missing fields, a header missing the budget, an unknown type), two headers giving two runs, and the real fixture (30 steps, 36 evals).

Hints try without first

  • enumerate(text.splitlines(), start=1) gives the line numbers. Check blank lines after counting them.
  • A missing key in a step raises KeyError; catch it and re-raise as LogError with the line number.
  • Convert types as you go: float(row["budget_usd"]), int(row["max_attempts"]).

HEADER_KEYS = ("run_id", "arm", "budget_usd", "max_attempts",
               "noise_floor", "search_tasks")

def parse_log(text):
    """Parse JSONL text into a list of Run objects, in header order.

    Each line is a JSON object with a "type": "run" (the header, which
    must come first for its run_id), "step" or "eval". Blank lines are
    skipped. Raise LogError whose message starts "line N:" (N from 1) for
    invalid JSON, a line with no type, an unknown type, a header missing
    any of HEADER_KEYS, a step or eval whose run_id has no header yet, or
    a step or eval missing a field.
    """
    runs = {}
    for n, raw in enumerate(text.splitlines(), start=1):
        if not raw.strip():
            continue                                   # blank lines are fine
        try:
            row = json.loads(raw)
        except json.JSONDecodeError as e:
            raise LogError(f"line {n}: not valid JSON ({e.msg})")
        if not isinstance(row, dict) or "type" not in row:
            raise LogError(f"line {n}: every line needs a 'type'")
        kind = row["type"]
        if kind == "run":
            for key in HEADER_KEYS:
                if key not in row:
                    raise LogError(f"line {n}: run header lacks '{key}'")
            runs[row["run_id"]] = Run(
                row["run_id"], row["arm"], float(row["budget_usd"]),
                int(row["max_attempts"]), float(row["noise_floor"]),
                list(row["search_tasks"]))
        elif kind in ("step", "eval"):
            run = runs.get(row.get("run_id"))
            if run is None:
                raise LogError(f"line {n}: {kind} for unknown run "
                               f"{row.get('run_id')!r} (the header must "
                               f"come first)")
            try:
                if kind == "step":
                    run.steps.append(Step(
                        int(row["step"]), float(row["cost_usd"]),
                        float(row["search_score"]), bool(row["accepted"]),
                        float(row["incumbent"])))
                else:
                    run.evals.append(Eval(
                        row["stage"], row["task"], int(row["seed"]),
                        float(row["score"])))
            except KeyError as e:
                raise LogError(f"line {n}: {kind} lacks {e}")
        else:
            raise LogError(f"line {n}: unknown type {kind!r}")
    return list(runs.values())

Milestone 2: a fair baseline

The first condition is the most often skipped. A loop that improves is only interesting relative to what a person would have reached with the same resources. Weco's baseline, in their own account, is a hand-tuned production agent that took two years of engineering, and they ask that it be compared under the same fixed budget. At small scale the rule is the one in the roadmap: your own hand-tuned version, given the same budget and the same number of attempts.

Fairness can be checked from the two headers and the two step lists, with no judgement. The budgets must be equal and the attempts equal. The baseline must also have used its attempts: a baseline that stopped at 7 of 10 attempts was not tried as hard as the improver, and the lab's rule is at least 80 percent. Only then does the comparison of scores mean anything, and the improver must win it on its mean final score over tasks (use the helper task_means(run, "final"), which averages the seeds within each task). A tie is not a win.

Analogy: a race with different distances

Comparing an improver that had $60 with a baseline that had $30 is like timing one runner over 400 metres and another over 200 and reporting that the first is slower. The numbers are real and the comparison is meaningless. The fairness check is the step that confirms both runners were on the same track.

Where it breaks down: in a race the distance is obvious. A budget has several faces (dollars, attempts, wall-clock time, tokens), and a baseline can be matched on one and short on another. The lab checks two; a real audit asks about all of them.

Your task

Write fair_baseline(improver, baseline) returning a Verdict. Check in this order: budgets equal (reason contains budgets differ), attempts equal (attempts differ), the baseline used at least 80 percent of its attempts, then the improver's mean final score beats the baseline's (a loss has does not beat in the reason).

Hints try without first
  • Compare declared values (budget_usd, max_attempts), not what the steps sum to; milestone 5 is where spending is audited.
  • Attempts used is len(baseline.steps).
  • statistics.fmean(task_means(run, "final").values()) is the mean over tasks.
  • Put the numbers in the reason: a verdict that says "unfair" with no figures is hard to argue with.

def fair_baseline(improver, baseline):
    """Condition 1. Return a Verdict; check these in order.

    1. declared budget_usd equal (else "budgets differ ...")
    2. declared max_attempts equal (else "attempts differ ...")
    3. the baseline used at least 80% of its attempts (len(steps))
    4. the improver's mean final score over tasks beats the baseline's
       (task_means(run, "final"), then the mean of those means); the
       reason of a loss contains "does not beat"
    """
    if improver.budget_usd != baseline.budget_usd:
        return Verdict(False, f"budgets differ: improver ${improver.budget_usd:g}"
                       f" versus baseline ${baseline.budget_usd:g}")
    if improver.max_attempts != baseline.max_attempts:
        return Verdict(False, f"attempts differ: improver "
                       f"{improver.max_attempts} versus baseline "
                       f"{baseline.max_attempts}")
    used = len(baseline.steps)
    if used < 0.8 * baseline.max_attempts:
        return Verdict(False, f"baseline used only {used} of "
                       f"{baseline.max_attempts} attempts")
    mine = statistics.fmean(task_means(improver, "final").values())
    theirs = statistics.fmean(task_means(baseline, "final").values())
    if mine <= theirs:
        return Verdict(False, f"improver does not beat the baseline on final "
                       f"scores: {mine:.3f} versus {theirs:.3f}")
    return Verdict(True, f"same ${improver.budget_usd:g} and "
                   f"{improver.max_attempts} attempts; improver {mine:.3f} "
                   f"beats baseline {theirs:.3f}")

Milestone 3: a sustained trend, not a lucky accept

A loop that proposes many changes and keeps the best will show a rising incumbent even if every proposal is noise, because the maximum of many noisy scores rises. The second condition asks for several accepts that each clear the noise, none of which carries the result. Weco's paper describes seven accepted improvements over a 100-node run for exactly this reason: "one favorable rewrite cannot show that the loop repeatedly finds useful improvements."

First turn a log into real gains. An accepted step's gain is its incumbent minus the previous step's incumbent. It is real only if the gain is strictly above the run's noise floor: a gain of 0.005 when re-running the same agent moves its score by 0.01 is a coin flip that happened to land well. Step 1 has no previous incumbent, so it never counts. Then apply two rules: at least MIN_ACCEPTS (3) real gains, and the largest at most MAX_SHARE (50 percent) of their sum.

incumbents A:  0.50  0.53  0.56  0.59      three gains of 0.03, largest share 33%
incumbents B:  0.50  0.50  0.59  0.59      one gain of 0.09, largest share 100%

Both end at 0.59. Only A is a trend. B is one change, which may be a good change, but a loop's claim to be self-improving needs the repeat.

Common misconception

"The thresholds are the science." They are not. Three accepts and a 50 percent share are this lab's choices, small enough for a thirty-step fixture. A real run sets them from its noise estimate and its length, states them before looking at results, and reports how the verdict changes if they move. What is not negotiable is that a verdict exists for a trend and not just a final number.

Your task

Write real_gains(run) (the list of gains above the noise floor, in step order) and sustained_trend(run) (a Verdict). Too few gains: the reason contains real accept. One dominant gain: the reason contains lucky.

It checks the gains of a hand-made incumbent list (0.005 and 0.0005 fall under a 0.01 floor), that step 1 never counts, three equal accepts passing, one big accept plus two within noise failing, two accepts failing, a 75 percent share failing, five seeded random sequences with rejected steps scattered between the accepts (rejected steps must not change the verdict), and the fixtures improver_good and improver_lucky.

Hints try without first
  • Walk the steps once, remembering the previous incumbent; the gain is s.incumbent - prev.
  • Use s.accepted to decide which steps to consider, then the floor to decide which count.
  • Divide by sum(gains) only after you know there are at least MIN_ACCEPTS gains, so it cannot be zero.
  • Floating-point subtraction leaves residue like 0.030000000000000027; compare with the floor, never with equality.
Solution spoiler 
MIN_ACCEPTS = 3               # real accepts a "sustained" trend needs

def real_gains(run):
    """Gains of the accepted steps that beat the run's noise floor.

    A step's gain is its incumbent minus the previous step's incumbent.
    Step 1 has no previous incumbent, so it never counts. Only accepted
    steps whose gain is strictly above run.noise_floor are returned.
    """
    out, prev = [], None
    for s in run.steps:
        if s.accepted and prev is not None:
            gain = s.incumbent - prev
            if gain > run.noise_floor:
                out.append(gain)
        prev = s.incumbent
    return out

def sustained_trend(run):
    """Condition 2. Need MIN_ACCEPTS real gains, and the largest must be
    at most MAX_SHARE of their sum. The reason for too few contains
    "real accept"; the reason for a lucky jump contains "lucky".
    """
    gains = real_gains(run)
    if len(gains) < MIN_ACCEPTS:
        return Verdict(False, f"only {len(gains)} real accept(s) above the "
                       f"noise floor {run.noise_floor:g}; need "
                       f"{MIN_ACCEPTS}")
    share = max(gains) / sum(gains)
    if share > MAX_SHARE:
        return Verdict(False, f"one accept carries {share:.0%} of the gain "
                       f"(limit {MAX_SHARE:.0%}): a lucky jump")
    return Verdict(True, f"{len(gains)} real accepts, total +{sum(gains):.3f},"
                   f" largest share {share:.0%}")

Milestone 4: generalisation to tasks never searched

The third condition separates improving at the search from improving at the job. Every accept was chosen because it scored higher on the search tasks, so the search score is biased upward by selection (A7 chapter 16 derives how much). The honest number is a score on tasks the loop never saw while it searched. Weco's paper reports three seeds on a weather-forecasting task that lies outside the families used in selection; Artifact 4 uses private splits for the same purpose.

The log makes this checkable. The header lists search_tasks. The eval lines name the tasks the report used. Two tests follow. First, leakage: any task that is both searched on and reported on cannot count as held out. Second, a paired gain with an interval: for each held-out task, average the seeds, subtract the initial score from the final score, and treat the tasks as the sample. With six tasks, the mean difference minus its 95 percent half-width must stay above zero, and the mean must reach MIN_GAIN (0.02). The half-width is a t value times the standard error; the table T95 in the starter gives t for 1 to 10 degrees of freedom (2.571 for the 5 degrees of freedom of six tasks).

The unit of independence is the task

Averaging the three seeds inside a task before the test is deliberate. The seeds of one task share its difficulty; treating 18 seed-runs as 18 independent samples would shrink the interval by about a factor of two and pass gains that rest on a single task. The tasks are the sample.

Plug in numbers by hand. Six tasks improve by 0.06, 0.07, 0.08, 0.05, 0.07 and 0.07. The mean is 0.0667. The standard deviation of the six differences is 0.0103, the standard error is 0.0103 ÷ √6 = 0.0042, and the half-width is 2.571 × 0.0042 = 0.0108. The interval is 0.0667 ± 0.0108, comfortably above zero, so the check passes. If the same mean came with differences swinging between +0.2 and −0.1, the half-width would exceed the mean and the check would fail, which is the point of using an interval rather than the mean alone.

Your task

Check in order: leakage (reason contains used in search, or no held-out tasks when nothing else remains), at least MIN_PAIRS tasks (reason contains need), then the gain and interval.

Hints try without first

  • statistics.stdev divides by n minus 1, which is what you want for a sample.

Solution spoiler 
MIN_PAIRS = 3                 # held-out tasks needed for a paired test

T95 = {1: 12.706, 2: 4.303, 3: 3.182, 4: 2.776, 5: 2.571, 6: 2.447,
       7: 2.365, 8: 2.306, 9: 2.262, 10: 2.228}   # two-sided 95%, df 1..10

def paired_gain(run):
    """(mean gain, 95% half-width, n) over held-out tasks, final - initial.

    Average the seeds within each held-out task first (task_means), take
    the final minus initial difference per task, and treat the n tasks as
    the sample: half-width = t * standard error, with t from T95 at
    n - 1 degrees of freedom (2.0 beyond the table). With n < 2 the half
    width is math.inf.
    """
    first, last = task_means(run, "initial"), task_means(run, "final")
    diffs = [last[t] - first[t] for t in heldout_tasks(run)
             if t in first and t in last]
    n = len(diffs)
    if n < 2:
        return (diffs[0] if diffs else 0.0), math.inf, n
    se = statistics.stdev(diffs) / math.sqrt(n)
    return statistics.fmean(diffs), T95.get(n - 1, 2.0) * se, n

def generalisation(run):
    """Condition 3. Check in order: a task both in run.search_tasks and
    among the evals is leaked (reason contains "used in search"; if no
    held-out task remains, the reason contains "no held-out tasks");
    fewer than MIN_PAIRS tasks fails ("need"); then the gain must be at
    least MIN_GAIN and its interval (gain - half) must stay above zero.
    """
    leaked = sorted(set(e.task for e in run.evals) & set(run.search_tasks))
    held = heldout_tasks(run)
    if leaked and not held:
        return Verdict(False, "no held-out tasks: every evaluated task was "
                       "also searched on")
    gain, half, n = paired_gain(run)
    if leaked:
        return Verdict(False, f"tasks {leaked} were used in search and in "
                       f"the report; they cannot count as held out")
    if n < MIN_PAIRS:
        return Verdict(False, f"only {n} held-out task(s) with initial and "
                       f"final scores; need {MIN_PAIRS}")
    if gain < MIN_GAIN or gain - half <= 0:
        return Verdict(False, f"held-out gain {gain:+.3f} ± {half:.3f} over "
                       f"{n} tasks is not clearly above zero")
    return Verdict(True, f"held-out gain {gain:+.3f} ± {half:.3f} over {n} "
                   f"tasks the search never saw")

Milestone 5: the budget and the report card

The fourth condition is the simplest to state and the easiest to break by accident: dollars, GPU-hours and steps are stated up front and never exceeded. The parser already enforced the "up front" half by demanding the header first. The check enforces the other half by adding up the costs as they were incurred and finding the first step at which the running total passes the budget. Naming the step matters: "over budget" invites an argument about rounding, and "exceeded at step 27 (spent $66.00)" does not. It must also hold the attempt count to the stated limit.

Then combine. report_card(improver, baseline) returns a dictionary keyed by the four names in CONDITIONS, in order. Condition 1 compares the two runs; conditions 2 to 4 judge the improver. render(card) turns it into the text a reviewer reads, one line per condition and a last line that is either Level 1: met or Level 1: NOT met. Note what the card does not do: it does not average the conditions or weight them. A loop that fails any one has not met Level 1, and a card that hides which one is a worse card.

def budget_ok(run):
    """Condition 4. Add up cost_usd step by step; the first step whose
    running total passes budget_usd fails, naming that step ("exceeded at
    step N"). Then len(steps) must not pass max_attempts.
    """
    spent = 0.0
    for s in run.steps:
        spent += s.cost_usd
        if spent > run.budget_usd + 1e-9:
            return Verdict(False, f"budget ${run.budget_usd:g} exceeded at "
                           f"step {s.step} (spent ${spent:.2f})")
    if len(run.steps) > run.max_attempts:
        return Verdict(False, f"{len(run.steps)} attempts against a limit "
                       f"of {run.max_attempts}")
    return Verdict(True, f"spent ${spent:.2f} of ${run.budget_usd:g} in "
                   f"{len(run.steps)} of {run.max_attempts} attempts")

CONDITIONS = ("fair baseline", "sustained trend", "generalisation",
              "fixed budget")

def report_card(improver, baseline):
    """{condition: Verdict} for the four conditions, in CONDITIONS order.

    Condition 1 compares improver with baseline; 2 to 4 judge the improver.
    """
    return {
        CONDITIONS[0]: fair_baseline(improver, baseline),
        CONDITIONS[1]: sustained_trend(improver),
        CONDITIONS[2]: generalisation(improver),
        CONDITIONS[3]: budget_ok(improver),
    }

def render(card):
    """The card as text: one line per condition, "  PASS  name ... reason"
    or "  FAIL ...", then "  Level 1: met" if all four pass, else
    "  Level 1: NOT met".
    """
    lines = []
    for name, v in card.items():
        lines.append(f"  {'PASS' if v.passed else 'FAIL'}  "
                     f"{name:<16} {v.reason}")
    ok = all(v.passed for v in card.values())
    lines.append("  Level 1: " + ("met" if ok else "NOT met"))
    return "\n".join(lines)

Milestone 6: an automation level from a rubric

The first five milestones ask whether a loop improved. The last asks a different question about the same loop: how much of the research was done by the machine? Epoch AI's June 2026 post "Toward an O*NET for AI R&D" (Denain, Kwon and Ho, 17 June 2026) rates more than sixty AI-research tasks on a scale from 0 to 5, which this course writes as the automation levels AL0 to AL5. The article's levels, in its words, run from "Not used, AI adds nothing" through "Marginal", "Assists", "Collaborates" and "Leads" to "Autonomous, end to end with little or no human involvement". The authors call their own ratings "quite subjective". Chapter 2 covers the taxonomy and the published estimates; the lab turns it into code so you can rate your own loop.

A rubric a program can apply needs inputs a person can answer. This lab asks three questions about each task in your loop: was AI used at all, what share of the work did it do, and what is the human's role (none, approves, directs or drives). The table below is this lab's own mapping onto the 0 to 5 scale, not Epoch's, so treat it as one reasonable reading of their descriptions.

LevelEpoch's wordThis lab's rule
0Not usedAI not used
1Marginalhuman drives and AI does under 20% of the work
2Assistshuman drives and AI does 20% or more; or human directs and AI does under 50%

A loop is several tasks, and the useful summary is not only the mean. The mean of 4, 5, 3 and 1 is 3.25, which sounds like "mostly collaborating", but the task rated 1 is where a person is still doing the work. The lab returns the mean and the weakest link: the lowest-rated task, the one a person must still sit beside. Chapter 3 returns to why that bottleneck, not the average, limits how fast a loop can run without supervision.

Solution spoiler 
LEVEL_NAMES = ["not used", "marginal", "assists", "collaborates", "leads",
               "autonomous"]

def task_level(ai_used, ai_share, human_role):
    """Epoch-style 0 to 5 level of one task.

    human_role is "none", "approves", "directs" or "drives".
    not ai_used -> 0;  "none" -> 5;
    "approves": 4 if ai_share >= 0.5 else 3;
    "directs":  3 if ai_share >= 0.5 else 2;
    "drives":   2 if ai_share >= 0.2 else 1.
    """
    if not ai_used:
        return 0
    if human_role == "none":
        return 5
    if human_role == "approves":
        return 4 if ai_share >= 0.5 else 3
    if human_role == "directs":
        return 3 if ai_share >= 0.5 else 2
    return 2 if ai_share >= 0.2 else 1       # "drives"

def automation_level(tasks):
    """tasks: list of dicts with name, ai_used, ai_share, human_role.

    Returns (levels, mean, weakest): per-task levels, their mean, and the
    name of the lowest-level task, the human bottleneck of the loop.
    """
    levels = {t["name"]: task_level(t["ai_used"], t["ai_share"],
                                    t["human_role"]) for t in tasks}
    weakest = min(levels, key=lambda k: (levels[k], k))
    return levels, statistics.fmean(levels.values()), weakest

Check your understanding

improver_lucky ends with a higher search score than baseline_fair, passes generalisation and stays in budget, yet the card says Level 1 is not met. Which condition fails, and why is a high final score not enough?

  1. Fair baseline: the final score is higher so the baseline must have been unfair
  2. Sustained trend: only one accept cleared the noise floor, so the rise could be a single lucky change
  3. Fixed budget: a lucky accept costs more than a normal one
  4. Generalisation: a lucky accept never transfers to held-out tasks
The trend condition asks whether the loop repeatedly finds improvements. One real accept and two inside the noise is one event. The first option has it backwards (a higher score is not evidence of an unfair baseline), the third invents a cost link, and the fourth is wrong for this fixture: the held-out check passes, because the one change did transfer. Transfer and repetition are different questions.

A loop searched on tasks s1 to s3 and its report evaluates s2, h1, h2 and h3 with a mean gain of +0.07. What does the checker do, and why?

  1. Passes, because three of the four tasks are held out
  2. Passes, but averages s2 with a lower weight
  3. Fails: s2 was used in search, so the report mixes a selected score with held-out scores
  4. Fails only if the gain on s2 is larger than on the others
A task used in the search has a score biased upward by selection, and averaging it in contaminates the rest. The lab's rule is strict: any overlap fails, because the report no longer separates what was tuned on from what was not. The better fix is to drop s2 from the report and re-run the test on h1 to h3, which still has three tasks. The last option would excuse a leak whenever it happened to be small.

Eighteen held-out scores (six tasks, three seeds each) are used as 18 independent samples in a paired test. What goes wrong?

  1. The interval is too narrow, because seeds of one task share that task's difficulty and are not independent
  2. The interval is too wide, because averaging seeds loses information
  3. Nothing: more samples always give a better test
  4. The mean gain changes, because seeds are weighted unevenly
Seeds within a task are correlated through the task. Treating them as independent overstates the sample size, so the standard error is too small and weak evidence looks strong. Averaging the seeds first and using the six tasks as the sample is the conservative choice, as in the lab. The mean itself does not change when every task has the same number of seeds.

A baseline run was given $60 and 30 attempts, but stopped at 20 attempts because it hit a local optimum. The improver used all 30. How should the fair-baseline check treat it, and what is the usual fix?

  1. Pass: the declared budgets match, so the comparison is fair
  2. Fail, and the fix is to lower the improver's budget to match
  3. Fail on the 80 percent rule, and the usual fix is to give the baseline its remaining attempts, for example by restarting it or tuning further
  4. Pass, because stopping early shows the baseline is already optimal
Declared budgets match, but a baseline that stopped at 20 of 30 attempts (67 percent) was not tried as hard as the improver, so the comparison favours the improver. The fix is to use the baseline's remaining attempts, or to report the comparison at the baseline's budget. Cutting the improver's budget changes the claim being tested. A baseline that stops early is not evidence that it is optimal.

A loop's tasks are rated 5 (run experiments), 5 (log results), 4 (propose changes) and 1 (decide what the next experiment should test). The mean is 3.75. What does the weakest-link reading add?

  1. Nothing: the mean already summarises the loop
  2. That the loop still needs a person at the research-direction step, so supervision, not throughput, limits how autonomously it can run
  3. That the loop is level 1 overall
  4. That the proposer should be replaced by a larger model
The mean hides where the human sits. A loop whose decision step is rated 1 needs a person in the loop at every cycle, whatever the rest does. The weakest link is the quantity to watch when asking how long the loop can run unattended. The overall level is not 1 (the mean is 3.75), and the rubric says nothing about which model to use.

Toolbox

A database is invisible until you ask it questions. These tools let you run SQL, ask the planner what it intends to do, watch two transactions collide, time a commit, poke at a cache and scan a column store. Each has a ten-minute exercise tied to a chapter.

How to use this page

Jump to a tool when a chapter mentions it. Start with sqlite3: it needs nothing installed on a Mac. Most of the rest need one install (a local PostgreSQL, Redis or DuckDB). None of them needs Linux, but the lab machine is a fine place to run a database you might break. Example output is realistic but yours will differ: different timings, costs and row counts. Where a number below is labelled as an example, it is not a benchmark.

Everything here runs against throwaway data on your own machine. Every server below should listen only on localhost, so that nobody else on your network can reach it. The cards say how.

Everyday SQL

The fastest way to understand a database is a prompt where you can type SQL and see what happens.

sqlite3

macOS: built in (/usr/bin/sqlite3); brew install sqlite for a newer one · Ubuntu/Debian: sudo apt install sqlite3 · Python: the sqlite3 module is in the standard library · Windows: inside WSL

SQLite is a complete SQL database that lives in one ordinary file and runs inside your process, with no server. The sqlite3 shell lets you create tables, add indexes and ask how a query will be answered. It is the lab bench for the relational chapters ahead of Postgres, and its tiny size makes the ideas easy to see: a table is a B-tree keyed by a row ID (chapter 6), and an index is another B-tree (chapter 7).

10-minute guided exercise

Make a table of 10,000 orders from one SQL statement, then watch the plan change when you add an index. The output below came from a real run (SQLite 3.51 here; your version may print slightly different plan text):

$ sqlite3 shop.db  # creates shop.db if it doesn't exist; .quit leaves
sqlite> CREATE TABLE orders(id INTEGER PRIMARY KEY, customer TEXT, total REAL);
sqlite> WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i+1 FROM n WHERE i<10000)
   ...> INSERT INTO orders SELECT i, 'cust'||(i%500), (i%97)+0.5 FROM n;
sqlite> .mode column
sqlite> .headers on
sqlite> EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer='cust42';
QUERY PLAN
`--SCAN orders
sqlite> CREATE INDEX idx_orders_customer ON orders(customer);
sqlite> EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer='cust42';
QUERY PLAN
`--SEARCH orders USING INDEX idx_orders_customer (customer=?)
sqlite> EXPLAIN QUERY PLAN SELECT * FROM orders WHERE id=77;
QUERY PLAN
`--SEARCH orders USING INTEGER PRIMARY KEY (rowid=?)
sqlite> .schema orders
CREATE TABLE orders(id INTEGER PRIMARY KEY, customer TEXT, total REAL);
CREATE INDEX idx_orders_customer ON orders(customer);
sqlite> PRAGMA journal_mode;
journal_mode
------------
delete      
sqlite> SELECT count(*), round(sum(total),1) FROM orders WHERE customer='cust42';
count(*)  round(sum(total),1)
--------  -------------------
20        984.0

Now the same ideas from Python, which is handy for scripts and for the labs. Run it, then delete the file:

$ python3 -c "import sqlite3; c=sqlite3.connect('shop.db'); print(c.execute('SELECT count(*) FROM orders').fetchone())"
(10000,)
$ rm shop.db  # throwaway data: clean up

If you want one more experiment: in sqlite3, run BEGIN; INSERT ...; and, without committing, open a second sqlite3 shop.db and try to write. SQLite allows one writer at a time, and the second session tells you the database is locked.

What to look for

  • SCAN means "read every row"; SEARCH ... USING INDEX means "walk a B-tree straight to the matching entries". Adding one index flipped the plan, with no change to the query (chapter 7).
  • Lookups by id say INTEGER PRIMARY KEY: the table itself is the primary B-tree, so there is no separate index to maintain (chapter 6).
  • SQL says what you want; the plan is how the engine will get it, chosen by the engine, not by you (chapter 2).
  • journal_mode shows how SQLite protects a transaction on disk. The default is a rollback journal; PRAGMA journal_mode=WAL switches to a write-ahead log, the idea behind chapter 13.
  • The locked-database error from two writers is the "single writer" rule of chapter 10, felt directly.

Common pitfalls

  • SQLite is not Postgres. Column types are flexible (a column's declared type is only a hint), and some syntax and functions differ. SQL in these chapters is written to run in both unless a note says otherwise.
  • The plan text varies by version. Older versions print rows like 0|0|0|SCAN TABLE orders instead of the tree.
  • A new index is only useful if the query can use it. WHERE lower(customer) = ... cannot use an index on customer alone.
  • Dot-commands (.schema, .mode) belong to the shell, not to SQL, and don't end with a semicolon.
  • Make sure you know which file you opened. sqlite3 with no file name uses a temporary in-memory database that vanishes when you quit.

Postgres up close

The open-source workhorse. Run one locally, and you can see isolation, planning and benchmarking on a real, multi-user engine.

PostgreSQL & psql

macOS: brew install postgresql@17, then brew services start postgresql@17 · Ubuntu/Debian: sudo apt install postgresql postgresql-client · Docker (any OS): see below · Windows: inside WSL, or Docker

PostgreSQL is a full client-server database, and psql is its command-line client. Unlike SQLite it serves many sessions at once, which is exactly what makes transactions and isolation interesting. With two psql windows you can reproduce the anomalies of chapter 11 instead of reading about them.

10-minute guided exercise

1. Get a local server. Pick one. All three keep the server on your own machine.

  • Homebrew: brew install postgresql@17 then brew services start postgresql@17. The formula creates a default database cluster when it is installed. This version is keg-only, so if psql is not found, add $(brew --prefix postgresql@17)/bin to your PATH. Then psql postgres.
  • Docker one-liner (the official postgres image needs POSTGRES_PASSWORD to be set):
$ docker run --rm --name pg -e POSTGRES_PASSWORD=devpass -p 127.0.0.1:5432:5432 postgres:17  # --rm: deleted on stop; 127.0.0.1: reachable only from this machine
  • On the lab VM: sudo apt install postgresql postgresql-client, then sudo -u postgres psql. Ubuntu's default configuration listens on localhost only.

Notice 127.0.0.1: in the Docker command. Without it, -p 5432:5432 publishes the port on all your network interfaces, and the example password is not a secret. For the rest of this exercise, open two terminals and start psql in each. With Docker, that is docker exec -it pg psql -U postgres.

2. Make some data (in the first session):

postgres=# CREATE TABLE accounts(id int PRIMARY KEY, owner text, balance int);
CREATE TABLE
postgres=# INSERT INTO accounts VALUES (1,'ada',100), (2,'bob',100);
INSERT 0 2
postgres=# SHOW default_transaction_isolation;  # the default level
 default_transaction_isolation
-------------------------------
 read committed

3. Make two transactions collide. Run these in the order shown. The step numbers are the order in time:

-- (1) session A
postgres=# BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN
postgres=*# SELECT balance FROM accounts WHERE id = 1;  -- takes A's snapshot
 balance
---------
     100

-- (2) session B: change and commit the same row
postgres=# UPDATE accounts SET balance = balance + 10 WHERE id = 1;
UPDATE 1

-- (3) session A: still inside its transaction
postgres=*# SELECT balance FROM accounts WHERE id = 1;  -- same snapshot: B's change is invisible
 balance
---------
     100
postgres=*# UPDATE accounts SET balance = balance + 5 WHERE id = 1;
ERROR:  could not serialize access due to concurrent update
postgres=!# SELECT 1;
ERROR:  current transaction is aborted, commands ignored until end of transaction block
postgres=!# ROLLBACK;
ROLLBACK
postgres=# SELECT balance FROM accounts WHERE id = 1;  -- fresh snapshot: now we see B's work
 balance
---------
     110

Session B ran its UPDATE outside an explicit transaction, so it committed on its own, and A's update then conflicted with it. This error is a serialization failure with SQLSTATE 40001. In psql, \set VERBOSITY verbose includes that code in error messages. The PostgreSQL documentation's advice is to abort and retry the whole transaction. Now repeat from the top with BEGIN; in session A (the default READ COMMITTED): the second SELECT sees B's change and the update succeeds.

4. Peek at the plan (more in the EXPLAIN card):

postgres=# EXPLAIN ANALYZE SELECT * FROM accounts WHERE id = 2;  -- runs the query; prints plan, estimates and timings

What to look for

  • Repeatable-read session A never saw B's change. It reads from a snapshot taken at its first query. This is snapshot isolation, and chapter 12 explains how multiple row versions make it possible.
  • The error is the database refusing a lost update. Both transactions started from balance 100. If A's write were allowed, it would overwrite B's +10 (chapter 11).
  • After the error the transaction is dead (the prompt changes to !). The application's job is to roll back and retry, so retry logic is part of correct code at these isolation levels.
  • Read Committed (the default) behaves differently. Each statement gets a fresh snapshot, so repeated reads can change within one transaction (chapter 11).
  • EXPLAIN ANALYZE output pairs an estimate with what really happened (chapter 8). More in the next card.
  • With a primary and replicas (not set up here), the same server speaks the replication protocol of chapter 15.

Common pitfalls

  • Check your session's prompt. * after the database name means you are inside a transaction, and ! means it has failed. An open transaction left in one window will hold locks and confuse the other.
  • Docker without a volume loses everything on stop (--rm removes the container). That is what you want here, but not for data you care about.
  • Port 5432 already in use? You probably have a Homebrew server running as well as Docker. Stop one, or map Docker to another host port such as 127.0.0.1:5433:5432.
  • Never expose the example password-protected server to the internet. Bind to localhost, and delete the container when you finish.
  • Postgres's "Repeatable Read" is snapshot isolation, and it differs from the weaker level of the same name in the SQL standard. Other databases use the same label differently (chapter 11).
  • Stop what you started: docker stop pg, or brew services stop postgresql@17.

EXPLAIN & EXPLAIN ANALYZE

macOS / Ubuntu / Windows: built into PostgreSQL (see the PostgreSQL card to install one); SQLite has EXPLAIN QUERY PLAN, built in

EXPLAIN shows the plan the planner chose for a query, with its cost estimates. EXPLAIN ANALYZE also runs the query and adds what actually happened: real row counts and real timings. The gap between the two is where slow queries are found, and it is the main skill of chapter 8.

10-minute guided exercise

In psql, make a table large enough that the plan matters. The numbers below are examples from a plausible run; yours will differ in costs and timings, and the shape of the plan is what to compare:

postgres=# CREATE TABLE orders AS
             SELECT g AS id, 'cust' || (g % 500) AS customer, (g % 97) + 0.5 AS total
             FROM generate_series(1, 100000) g;
SELECT 100000
postgres=# ANALYZE orders;  -- gather statistics for the planner
postgres=# EXPLAIN ANALYZE SELECT * FROM orders WHERE customer = 'cust42';
 Seq Scan on orders  (cost=0.00..2137.00 rows=200 width=...) (actual time=0.03..9.1 rows=200 loops=1)
   Filter: (customer = 'cust42'::text)
   Rows Removed by Filter: 99800
 Planning Time: 0.1 ms
 Execution Time: 9.2 ms
postgres=# CREATE INDEX ON orders(customer);
CREATE INDEX
postgres=# EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customer = 'cust42';
 Bitmap Heap Scan on orders  (cost=... rows=200 ...) (actual time=... rows=200 loops=1)
   Recheck Cond: (customer = 'cust42'::text)
   ->  Bitmap Index Scan on orders_customer_idx  (cost=... rows=200 ...) (actual ... rows=200 loops=1)
         Index Cond: (customer = 'cust42'::text)
   Buffers: shared hit=...
 Execution Time: 0.4 ms

The plan shape is what matters: a sequential scan before the index, and an index-driven plan after. (On some versions and data the planner prints a plain Index Scan instead of a bitmap scan; both read through the index.) Rows you pick with a very common value may still scan the whole table, even with an index. Try that, then try a join:

postgres=# EXPLAIN ANALYZE SELECT * FROM orders WHERE total > 0;  -- matches every row: the planner ignores indexes
postgres=# EXPLAIN ANALYZE SELECT a.id FROM orders a JOIN accounts b ON b.id = a.id % 3;  -- needs the accounts table from the PostgreSQL card
postgres=# BEGIN;
postgres=*# EXPLAIN ANALYZE UPDATE orders SET total = total + 1 WHERE id < 10;  -- really runs the update...
postgres=*# ROLLBACK;  -- ...so undo it

And in SQLite, the cheaper cousin is EXPLAIN QUERY PLAN, shown in the sqlite3 card. It reports the plan but not timings.

What to look for

  • Seq Scan versus Index or Bitmap scan. The planner picks between reading the whole table and following an index, based on how selective the filter is (chapter 7, chapter 8).
  • Estimated rows versus actual rows. They should be close. A big gap means stale or misleading statistics, and is the usual root cause of a bad plan (chapter 8).
  • The tree reads from the innermost, most-indented node outward. Each node is an operator that pulls rows from its children, the iterator model of chapter 8.
  • actual time is per loop; multiply by loops for a node that runs many times (typical for the inner side of a nested loop).
  • Buffers: shared hit versus read. A "hit" came from Postgres's memory buffer pool, a "read" from beyond it (chapter 8).
  • Cost numbers are the planner's own unit, not milliseconds. Compare them between plans, not against the clock.

Common pitfalls

  • EXPLAIN ANALYZE really executes the statement. For INSERT, UPDATE or DELETE, wrap it in BEGIN; ... ROLLBACK; as above, or the change stays.
  • Plain EXPLAIN shows only an estimate. It tells you nothing about whether the estimate was right.
  • Run ANALYZE table after loading data; otherwise the planner may have no statistics for a freshly created table.
  • Tiny tables use sequential scans on purpose. An index can't help on 50 rows, so don't conclude the index is broken.
  • Timing overhead. Measuring every node adds cost, so very fast queries look slower under EXPLAIN ANALYZE than in real life.
  • Newer Postgres versions print fractional row counts (rows=200.00) in the actual part. Same meaning.

pgbench

macOS: comes with brew install postgresql@17 (it lives in the same bin directory as psql) · Ubuntu/Debian: included in the postgresql-16 server package on Ubuntu 24.04 (/usr/lib/postgresql/16/bin/pgbench, which is not on PATH by default) · Docker: already inside the image, run it with docker exec · Windows: inside WSL

pgbench is the benchmark program that ships with PostgreSQL. It creates a small bank-like schema, then runs many concurrent transactions against it and reports transactions per second (TPS) and latency. Its useful trick here is to hold everything constant and change one durability setting, so you can see what a commit costs: chapter 10 and chapter 13.

10-minute guided exercise

Use a scratch database (pgbench -i drops and recreates its own four tables). With Docker, put docker exec -it pg in front of each command, plus -U postgres for pgbench:

$ createdb bench  # or: psql -c "CREATE DATABASE bench"
$ pgbench -i -s 10 bench  # -i: initialise; -s 10: scale 10, i.e. 1,000,000 account rows
...
done in ... s (drop tables ..., create tables ..., client-side generate ..., vacuum ..., primary keys ...).
$ pgbench -c 4 -j 2 -T 15 bench  # 4 clients, 2 threads, run for 15 seconds
transaction type: <builtin: TPC-B (sort of)>
scaling factor: 10
query mode: simple
number of clients: 4
number of threads: 2
...
latency average = <N> ms
tps = <N> (without initial connection time)

The <N> is whatever your machine produces. Write down the tps value, then run the same thing with commits that don't wait for the log to reach disk. The environment variable PGOPTIONS passes a setting to each connection:

$ PGOPTIONS='-c synchronous_commit=off' pgbench -c 4 -j 2 -T 15 bench
...
tps = <a different N> (without initial connection time)
$ pgbench -S -c 4 -j 2 -T 15 bench  # -S: select-only workload; no writes, so nothing to commit
$ pgbench -c 1 -T 15 bench # one client, then try -c 16: how does TPS change as clients are added?

Run each setting at least twice and compare the two tps lines. With the setting off, a commit returns as soon as the transaction is in memory, and a background process writes the log shortly afterwards. How big the gap is depends on your disk, your OS, and (with Docker) the virtual machine underneath, so all that this exercise promises is a direction and a reason. When finished, drop the database:

$ dropdb bench

What to look for

  • Commits are expensive because of the flush. By default synchronous_commit is on: the commit waits until the transaction's log record is safely on disk. With it off that wait disappears, and write-heavy TPS usually climbs, often a lot on slow-to-flush disks (chapter 13).
  • Throughput rises with more clients, up to a point. Several transactions can share one log flush, which is group commit (chapter 13).
  • What you gave up: with off, a crash can lose the most recent "committed" transactions, but the PostgreSQL documentation is explicit that it does not corrupt the database. The state is as if those transactions had been cleanly aborted. That is the "D" of ACID, traded for speed on purpose (chapter 10).
  • The select-only run barely cares about the setting, because a read-only transaction writes no log to flush.
  • Contention: the default test updates a few small rows (the branch and teller tables) in every transaction. With many clients and a small scale factor, you are measuring waiting for row locks as much as disk speed (chapter 12).

Common pitfalls

  • pgbench -i destroys tables with its names. Always point it at a dedicated, disposable database.
  • Don't quote numbers from a laptop run as "Postgres performance." Compare runs of the same setup against each other, and repeat them.
  • Keep -s at least as large as -c, or you mostly measure lock contention, as the PostgreSQL docs warn.
  • Do not turn off fsync to "go faster." That is a different setting from synchronous_commit and can corrupt the database after a crash. We only change the safe one.
  • Laptops and Docker VMs may not flush the way a server's disk does, so the gap between the two runs can look small or large. Treat that as information about your machine.
  • If pgbench is not found on Ubuntu, run it by its full path, /usr/lib/postgresql/16/bin/pgbench.

Caches and streams

When the database is too slow or too far away, a fast in-memory store sits in front of it.

redis-cli

macOS: brew install redis, then brew services start redis · Ubuntu/Debian: sudo apt install redis-server redis-tools (redis-cli is in redis-tools; both are in the universe section of Ubuntu 24.04) · Windows: inside WSL

Redis is an in-memory key-value server, and redis-cli is its command-line client. Nothing is installed by default, so you need a local Redis first (install as above, or run it in the foreground with redis-server). It is the simplest real cache you can touch, and it makes expiry and eviction visible, the subject of chapter 14.

10-minute guided exercise

$ redis-cli  # connects to 127.0.0.1:6379 by default
127.0.0.1:6379> PING
PONG
127.0.0.1:6379> SET user:42:name "Ada" EX 30  # value expires after 30 seconds
OK
127.0.0.1:6379> GET user:42:name
"Ada"
127.0.0.1:6379> TTL user:42:name  # seconds left; -1 = no expiry, -2 = no such key
(integer) 27
# ...wait half a minute...
127.0.0.1:6379> GET user:42:name
(nil)
127.0.0.1:6379> TTL user:42:name
(integer) -2
127.0.0.1:6379> SET hits 0
OK
127.0.0.1:6379> INCR hits  # atomic increment: one command, no read-modify-write race
(integer) 1
127.0.0.1:6379> CONFIG GET maxmemory  # 0 means "no limit"
1) "maxmemory"
2) "0"
127.0.0.1:6379> CONFIG GET maxmemory-policy  # what happens when the limit is reached
1) "maxmemory-policy"
2) "noeviction"

Now make a tiny cache that has to evict. This changes the running server only; a restart (or CONFIG REWRITE, which you should not run) decides whether it persists:

127.0.0.1:6379> CONFIG SET maxmemory 2mb
OK
127.0.0.1:6379> CONFIG SET maxmemory-policy allkeys-lru  # evict the least recently used keys, from all keys
OK
127.0.0.1:6379> INFO stats  # look for keyspace_hits, keyspace_misses, evicted_keys

In a second terminal, fill it past 2 MB, for example with redis-cli --pipe or a loop of SET k$i value, then check evicted_keys again, and DBSIZE. Then undo the settings:

127.0.0.1:6379> CONFIG SET maxmemory 0
OK
127.0.0.1:6379> FLUSHDB  # deletes every key in this local database: only on a throwaway server!
OK

If you have time, try a stream, the log-like structure of chapter 19: XADD events * type click user 1 appends an entry (the * asks Redis to generate an ID), and XRANGE events - + reads the entries back in order.

What to look for

  • TTL counts down and then the key vanishes, with no code of yours deleting it. Expiry is how a cache stays fresh and bounded (chapter 14).
  • maxmemory-policy decides what Redis does when memory is full: noeviction refuses new writes, the allkeys-* policies evict any key, and the volatile-* ones evict only keys that have a TTL. This is the eviction question from chapter 14, as a one-line config setting.
  • Redis's LRU is approximate. It samples a few keys and evicts the oldest of the sample, rather than keeping an exact ordering (chapter 14).
  • The hit ratio is keyspace_hits / (keyspace_hits + keyspace_misses). It is the first number to check for any cache.
  • Streams are append-only logs with IDs, read by position (chapter 19).

Common pitfalls

  • The cache is not the source of truth. Anything with a TTL or an eviction policy can disappear, so your code must handle (nil) by going back to the database.
  • A default noeviction server returns errors when full, rather than discarding data. Check the policy before relying on Redis as a cache. The policy you see on your machine may differ from the one shown here.
  • Keep your server on localhost. A Redis exposed to a network without authentication is an open door. Don't bind it to a public interface.
  • FLUSHDB and FLUSHALL delete everything. Only run them on a server you made for this exercise.
  • Scanning keys with KEYS * blocks a busy server. Prefer SCAN if you ever try it on something real.
  • Stop the server when finished: brew services stop redis on a Mac with Homebrew.

Analytics

Scanning millions of rows to answer a question is a different job from looking up one row.

DuckDB

macOS: brew install duckdb · Linux (including Ubuntu): curl https://install.duckdb.org | bash, or use pip install duckdb from Python · Windows: pip install duckdb, or inside WSL

DuckDB is an in-process analytical database, rather like "SQLite for analytics". It stores and processes data by column, and it can run SQL directly on CSV and Parquet files with no loading step. That makes it the quickest way to feel the column-store and batch ideas of chapter 9 and chapter 18.

10-minute guided exercise

First make a two-million-row CSV. This Python one-liner (standard library only) writes about 45 MB and takes a few seconds; the data is deterministic, so four regions get 500,000 rows each:

$ python3 -c "
import csv
w = csv.writer(open('sales.csv', 'w', newline=''))
w.writerow(['id', 'region', 'user_id', 'amount'])
R = ['north', 'south', 'east', 'west']
[w.writerow([i, R[i % 4], i % 5000, (i % 1000) / 10]) for i in range(2_000_000)]
"
$ ls -lh sales.csv && head -3 sales.csv
-rw-r--r--  1 you  staff  45M Oct 12 22:29 sales.csv
id,region,user_id,amount
0,north,0,0.0
1,south,1,0.1

Now query the file in place. DuckDB works out the header and the column types by itself. The output below is an example; the counts are exact for this data, but the timings and the formatting of the averages will differ on your machine:

$ duckdb  # an in-memory database; .quit leaves
D .timer on  -- print how long each query takes
D DESCRIBE SELECT * FROM 'sales.csv';  -- what types did it infer?
D SELECT region, count(*) AS n, avg(amount) AS avg_amount
  FROM 'sales.csv' GROUP BY region ORDER BY region;
┌─────────┬────────┬────────────┐
│ region  │   n    │ avg_amount │
├─────────┼────────┼────────────┤
│ east    │ 500000 │       50.0 │
│ north   │ 500000 │       49.8 │
│ south   │ 500000 │       49.9 │
│ west    │ 500000 │       50.1 │
└─────────┴────────┴────────────┘
Run Time (s): real 0.2 ...  -- an example; typically a fraction of a second on a laptop
D SELECT sum(amount) FROM 'sales.csv';  -- touches one column
D SELECT * FROM 'sales.csv' WHERE id = 1234567;  -- one row: no index, so still a full scan
D COPY (SELECT * FROM 'sales.csv') TO 'sales.parquet' (FORMAT parquet);  -- convert to a columnar file
D SELECT region, count(*) FROM 'sales.parquet' GROUP BY region;
D .quit
$ ls -lh sales.csv sales.parquet  # compare the sizes
$ rm sales.csv sales.parquet  # tidy up

For comparison, run the same GROUP BY in plain Python with the csv module over the same file, or load the data into SQLite and run it there. The Python version reads and converts every row one at a time and takes much longer than DuckDB's answer. Treat the difference as qualitative, not a rigorous benchmark.

What to look for

  • Two million rows aggregated in about the time it takes to blink. A column store reads only the columns the query names and processes them in batches (chapter 9).
  • A single-column query (sum(amount)) is no slower than the grouped one, because both touch few columns. A query that needed all four columns would do more work.
  • The Parquet file is smaller than the CSV and faster to scan: same data, columnar layout plus compression. Similar values stored together compress well (chapter 9).
  • A point lookup (WHERE id = ...) is not DuckDB's strength. Analytics engines scan; transactional ones follow an index (chapter 7, chapter 17).
  • "Query the file where it sits" is the shape of batch processing: data in files, computation brought to it (chapter 18).

Common pitfalls

  • DuckDB is for analytics, not for a busy multi-user application. It runs inside one process; use Postgres for the transactional workload.
  • Type inference samples the file. A column that looks numeric for the first thousands of rows and then has a stray word can be guessed wrongly. Check with DESCRIBE, and pass explicit options to read_csv(...) if needed.
  • Don't conclude "DuckDB is X times faster than Y" from this exercise. It depends on your hardware, the file cache and what each tool is doing.
  • The shell started with no file name is in-memory. Data you create in it is gone when you quit (duckdb mydata.db keeps it).
  • The generated CSV is about 45 MB. Delete it when done.

Shell helpers

Events, logs and API responses are JSON. A good command-line tool makes them easy to read.

jq

macOS: brew install jq · Ubuntu/Debian: sudo apt install jq · Windows: inside WSL

jq is sed for JSON: it reads JSON, applies a small program of filters, and prints JSON (or plain text). Change-data-capture events, log lines and API payloads are JSON, and the structure of that JSON (nested objects, arrays, optional fields) is the subject of chapter 3. With jq you can pick events apart and reshape them while you read the streams of chapter 19.

10-minute guided exercise

Save one event as event.json. The outputs below came from a real run (jq 1.8):

$ cat > event.json <<'EOF'
{"id":"evt_9f2","type":"order.created","ts":"2026-10-12T09:14:03Z",
 "user":{"id":42,"name":"Ada","tags":["vip","beta"]},
 "items":[{"sku":"A1","qty":2,"price":9.5},{"sku":"B7","qty":1,"price":20}]}
EOF
$ jq '.user.name' event.json  # dig into nested objects
"Ada"
$ jq -r '.user.tags | join(",")' event.json  # -r: raw text, no quotes
vip,beta
$ jq -c '{id, user: .user.id, n_items: (.items|length), total: ([.items[]|.qty*.price]|add)}' event.json  # reshape: flatten and compute
{"id":"evt_9f2","user":42,"n_items":2,"total":39}
$ jq -c '.items | map(select(.price > 10))' event.json  # filter an array
[{"sku":"B7","qty":1,"price":20}]
$ jq -c '[.items[] | {(.sku): .qty}] | add' event.json  # turn an array of rows into one object
{"A1":2,"B7":1}
$ jq -r '.items[] | [.sku, .qty, .price] | @csv' event.json  # one CSV line per item
"A1",2,9.5
"B7",1,20
$ jq -c '.items[0].nope // "missing"' event.json  # // gives a default for null
"missing"

Now a stream of events, one JSON object per line (JSON Lines), the shape a log or a change feed usually has. -s ("slurp") reads all the lines into one array so you can aggregate:

$ printf '%s\n' '{"type":"click","user":1}' '{"type":"buy","user":1}' '{"type":"click","user":2}' > events.jsonl
$ jq -c 'select(.type == "click")' events.jsonl  # filter line by line
{"type":"click","user":1}
{"type":"click","user":2}
$ jq -c -s 'group_by(.type) | map({type: .[0].type, n: length})' events.jsonl
[{"type":"buy","n":1},{"type":"click","n":2}]
$ rm event.json events.jsonl

Try piping a database into it: with Postgres, psql -At -c "SELECT row_to_json(a) FROM accounts a" | jq . prints each row as a JSON object, and from Redis, redis-cli XRANGE events - + shows what a consumer reads.

What to look for

  • A JSON event is a tree, not a table. Flattening it into columns (the {id, user: .user.id, ...} filter) is what a pipeline does on its way into a relational store (chapter 3, chapter 1).
  • Numbers survive but types are loose. Compare 9.5 and 20: JSON has one number type, so schema choices that a table declares are your job (chapter 3).
  • One event per line is a log. The events.jsonl file is the same append-only structure as a stream or change feed, and group_by is a tiny batch job over it (chapter 18, chapter 19).
  • Missing fields give null, not an error. This is the schema-on-read tolerance and risk discussed in chapter 3.

Common pitfalls

  • Quote the filter in single quotes so your shell doesn't eat the $, | and quotes. Escape with care in zsh.
  • -r removes the JSON quotes. You want it for feeding other commands, but not when the output needs to stay valid JSON.
  • -s loads the whole input into memory. Fine for a sample, a bad idea on a multi-gigabyte log. Process line by line instead.
  • Large integers and precise decimals can lose precision in jq, since it may treat numbers as floating point. Treat IDs as strings if they are huge.
  • The filter is a language. If the error says "cannot iterate over null", a field you expected was missing; try .items[]? or the // default.

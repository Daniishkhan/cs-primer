Implementing Isolation: 2PL, MVCC & SSI

Chapter 11 said what each isolation level promises. This chapter opens the engine and shows how databases keep the promise: with locks that make transactions wait (two-phase locking), with several versions of every row so that readers never have to wait (MVCC), with a watchful tracker that spots dangerous patterns after the fact (SSI), or by not running transactions concurrently at all.

Why this matters

The mechanism behind an isolation level explains behaviour you will meet in production: why a report query froze all writes in one database but not in another, why a table grows even though you only update rows, why a "serializable" transaction fails with an error you have to retry, why a deadlock appears at 2 a.m. Every performance and correctness trade-off in the transaction layer comes from these four designs. They are also the answer to "how would you build isolation?", a favourite design-interview question.

Two families, and a third way

The central question is what to do when two transactions want the same data. There are two broad answers. The pessimistic answer assumes conflicts will happen and prevents them by making one transaction wait: that is locking. The optimistic answer assumes conflicts are rare, lets everyone proceed, and checks at the end whether anything went wrong, aborting if so: that is how multi-version schemes with conflict detection work. And a third answer sidesteps the question by running transactions one at a time. We take them in that order, starting with the oldest.

Locks: shared and exclusive

A database lock is the same idea as the mutex in systems chapter 12, attached to a data item (a row, a page, a table, or a range of an index) and managed by a lock manager that keeps a table of who holds what. The twist is that databases use two kinds, the readers-writer idea from that chapter:

  • A shared lock (S) is taken to read. Many transactions can hold a shared lock on the same item at once.
  • An exclusive lock (X) is taken to write. Only one transaction can hold it, and no shared locks may coexist with it.

Taking locks is not enough, though. When you take and release them decides whether you get isolation at all. If a transaction could lock a row, read it, unlock it, and later lock another row, the world could change in the gap, and we are back to read skew. The rule that fixes this is the subject of the next section.

Two-phase locking (2PL)

Two-phase locking is the classic protocol for serializability, and the "two phases" are exactly what the name says:

  1. A growing phase, in which the transaction acquires locks as it needs them and releases none.
  2. A shrinking phase, in which it releases locks and acquires none.

Once a transaction has released any lock, it may never take another. The moment between the two phases is the lock point. In practice databases use strict 2PL: they hold every exclusive lock (and usually all locks) until the transaction commits or aborts, then release everything at once. This avoids reading data that a later-aborted transaction wrote, so the shrinking phase is collapsed into a single instant.

Why does this give serializability? Here is the intuition, not the full proof. Suppose two transactions touch the same item and at least one writes it. Because of the locks, one of them must hold the item first and the other must wait until the first releases it, and under 2PL the first has not yet released anything else either, since its release phase starts after its last acquisition. So for every shared item the conflicting transactions are ordered the same way as their lock points. Order the transactions by lock point, and you have a serial order that explains the whole execution. Phrased as a story: whoever reaches their lock point first is "first" for every item they share with anyone.

Analogy: the library's reservation desk

Think of the library from earlier in the course, with a rule for borrowing reference books for a research project: you may collect books one by one and keep them on your desk, but once you hand any book back you may not pick up another. Nobody else can take a book while you have it (an exclusive lock), but several people may read the same pamphlet at once (shared). With that rule, two researchers working with overlapping sets of books can always be put in a sensible order: whoever has all their books first goes first.

Where it breaks down: in a library you can see who holds what and walk away to find another book. A transaction that asks for a locked row simply stops, holding everything it has already taken, which is exactly how deadlocks arise. And a library has no equivalent of the lock on a gap between books, which we need for phantoms.

What 2PL costs

2PL is correct and conceptually simple, but it is expensive in concurrency:

  • Readers block writers, and writers block readers. A long report that reads many rows holds shared locks on all of them, so anyone trying to update those rows waits. A long-running write holds exclusive locks, and every reader of those rows waits.
  • Throughput depends on the shape of the workload. Hot rows (a counter everyone updates) serialise everything touching them.
  • Deadlocks are common. Transactions that lock in different orders end up waiting on each other (next section), and the database must break the cycle by aborting someone.
  • Latency is unpredictable. A single slow transaction at the front of a lock queue can stall many others.

These costs are the reason multi-version designs were invented. First, though, there are two loose ends in the locking story: phantoms and deadlocks.

Locking ranges: predicate and index-range locks

Row locks can't protect against a phantom (chapter 11), because the row that causes trouble doesn't exist yet. If T1 runs SELECT ... WHERE room = 'A' AND slot = 10 and T2 then inserts a matching row, T1's query result has silently changed without any locked row being touched. Real 2PL needs to lock not just rows but the search condition itself.

The theoretical tool is a predicate lock: a lock on all rows, present or future, matching a condition such as room = 'A' AND slot = 10. A transaction that wants to insert, update or delete a row that matches someone's predicate must wait. It is exactly right and exactly expensive: checking an incoming write against every active predicate is slow, so it is rarely implemented literally.

The practical approximation is the index-range lock (also called a next-key lock in MySQL's InnoDB). When a query scans an index, the database locks the index entries it touches and the gaps between them. A new row has to be inserted into some gap of the index, so a locked gap makes the insert wait.

This is coarser than a true predicate lock: it can lock more than strictly needed, so unrelated inserts into the same gap wait too. If there is no suitable index, the database falls back to locking the whole table. That is a hidden reason a missing index can make an otherwise innocent query block writers (chapter 7 told you indexes make queries fast; this is another way they matter). InnoDB's next-key locking is why its Repeatable Read blocks many phantom inserts in locking reads and writes, while a plain snapshot read never takes such locks.

Deadlocks, in databases

The deadlock of systems chapter 13 reappears with rows instead of mutexes. T1 updates row A, T2 updates row B, then T1 tries to update B and T2 tries to update A: each holds what the other needs, and neither can ever proceed.

Databases handle this by detection and abortion rather than prevention. The lock manager maintains a wait-for graph: a node per transaction, an edge from T1 to T2 when T1 is waiting for a lock T2 holds. A cycle in this graph is a deadlock. The database finds cycles either continuously or after a short wait (Postgres checks once a lock wait has lasted deadlock_timeout, one second by default), picks a victim, aborts it so its locks are released, and returns an error to its client. InnoDB likewise detects deadlocks and rolls back one transaction.

Three consequences for how you write code: the error is normal, so retry the whole transaction (chapter 10); acquiring locks in a consistent order everywhere (always update the lower account id first) prevents most deadlocks; and keeping transactions short shrinks the window in which they can occur.

MVCC: readers don't block writers

Here is the idea that changed databases. Instead of one current value per row, keep several versions. A writer never overwrites a row in place; it creates a new version and leaves the old one for transactions that still need it. A reader looks at a consistent snapshot and picks, for each row, the version that belongs to that snapshot. This is multi-version concurrency control (MVCC), and its slogan is: readers never block writers, and writers never block readers.

The usual bookkeeping, shown in the terms Postgres uses, is two transaction ids stamped on every version:

  • created_by (Postgres calls it xmin): the id of the transaction that created this version.
  • deleted_by (Postgres: xmax): the id of the transaction that deleted or superseded it, or empty if it is still current.

An UPDATE is therefore a delete of the old version plus a create of the new one. Each transaction gets a unique, increasing id when it starts and, for snapshot isolation, records a snapshot: which transactions had committed at that moment. A version is visible to a snapshot when both of these hold:

  1. its creator had committed before the snapshot was taken (or is the reader itself), and
  2. it has not been deleted, or its deleter had not committed as of the snapshot (and is not the reader itself).

Everything in the snapshot's future, or still in progress, is invisible. Here is that rule as eight lines of Python, run against a row that is updated by a transaction that commits after a reader took its snapshot:

# A toy multi-version row store: each version records who created it and who deleted it.
class Version:
    def __init__(self, value, created_by, deleted_by=None):
        self.value, self.created_by, self.deleted_by = value, created_by, deleted_by

def visible(v, snapshot):
    """snapshot = (my_xid, set of xids that had committed when I took my snapshot)"""
    me, committed = snapshot
    created_ok = v.created_by == me or v.created_by in committed
    deleted = v.deleted_by is not None and (v.deleted_by == me or v.deleted_by in committed)
    return created_ok and not deleted

row = [Version(100, created_by=1)]               # xid 1 inserted balance = 100, committed
snap_a = (2, {1})                                 # transaction 2 takes its snapshot
# transaction 3 updates the row: mark the old version deleted, add a new version
row[0].deleted_by = 3
row.append(Version(70, created_by=3))
committed_now = {1, 3}                            # ...and commits
snap_b = (4, committed_now)                       # transaction 4 starts after that

for name, snap in (("tx 2 (old snapshot)", snap_a), ("tx 4 (new snapshot)", snap_b)):
    print(name, "sees", [v.value for v in row if visible(v, snap)])

# VACUUM: a dead version can go once no snapshot can still see it (here tx 2 has finished).
oldest_active_snapshot = snap_b[1]
row = [v for v in row if not (v.deleted_by in oldest_active_snapshot and v.deleted_by is not None)]
print("after vacuum, versions kept:", [v.value for v in row])
tx 2 (old snapshot) sees [100]
tx 4 (new snapshot) sees [70]
after vacuum, versions kept: [70]

Two transactions look at the same row at (logically) the same time and see different values, and neither waited for the other. The stepper below shows the same story physically, version by version, including the cleanup.

Step through

A version chain, two snapshots, and VACUUM

  1. One version. The row has a single version, v1, created by transaction 10 and deleted by nobody. Transaction 11 (green, a reader) starts and takes a snapshot: "everything committed up to now", which includes T10. It reads v1.
  2. A writer arrives. Transaction 12 (pink) runs UPDATE ... SET balance = 70. It does not overwrite v1. It stamps v1 "deleted by T12" and creates v2, "created by T12". T12 has not committed, so no snapshot treats either change as real yet. The reader T11 is untouched and still sees v1.
  3. The writer commits. T12 commits. From now on, any new snapshot sees v2 and ignores v1. A new reader, T13 (cyan), begins and reads v2. But T11's snapshot predates T12's commit, so T11 still sees v1, which is how it keeps getting a consistent view. Two readers, two answers, no waiting.
  4. The old reader finishes. T11 commits. No running transaction has a snapshot old enough to see v1 any more. It is now dead: garbage that nothing needs, but that still occupies space. Had T11 stayed open for hours, v1 could not be removed for hours.
  5. VACUUM. The cleanup process removes dead v1 and marks its space reusable. Only v2 remains. In a database with a heavy update load, this reclaiming never stops, which is why it needs its own background worker.

Analogy: a revision-history document

Think of a shared document with version history. When you open it you see the version as it was when you opened it; a colleague's later edits show up as new revisions without disturbing what you are reading. Everyone gets a stable page to read, and nobody has to take turns editing just to let others read. Old revisions pile up until someone deletes the ones nobody still needs.

Where it breaks down: in a document two people editing the same paragraph can merge their changes. In a database two transactions that change the same row cannot: one has to wait or abort. MVCC removes read-write conflicts, not write-write ones.

Cleaning up: VACUUM and purge

Old versions can't be deleted the moment they are superseded; they must stay until no active snapshot can possibly see them. Collecting the garbage afterwards is a real engineering job:

  • In PostgreSQL the cleaner is VACUUM, run automatically by the autovacuum background workers. It scans tables, finds versions no running transaction can see, and marks their space as reusable. (VACUUM FULL rewrites the whole table to return space to the operating system, and takes a heavy lock while doing so.)
  • In MySQL InnoDB old versions live in the undo log, and a purge process discards undo records that no snapshot needs.

Long-running transactions bloat storage

A snapshot is a promise to keep old data around. One transaction that sits open for hours (an analytics query, an interactive session someone forgot to close, a connection stuck "idle in transaction") pins the oldest-needed version for everything that changed since. Cleanup cannot go past it, dead versions pile up, tables and indexes grow (bloat), queries slow down, and disks fill, all while your actual data size has barely changed. Keep transactions short, set timeouts on idle ones, and watch for the oldest open transaction in your monitoring.

Where the old versions live: Postgres versus InnoDB

Both engines are MVCC, but they store versions differently, and the difference has big consequences. Keep this at the level of the idea:

  • PostgreSQL stores every version as a full row in the table's own storage (the heap). An update writes a new row version into the heap, and the old one stays right there until vacuum reclaims it. Indexes point at row versions, so an update that changes an indexed column needs new index entries too (Postgres has an optimisation, heap-only tuples, to avoid that in common cases). Everything needed to read an old version is just sitting in the table.
  • InnoDB keeps the newest version of a row in place in its primary-key B-tree (the clustered index) and writes the information needed to reconstruct older versions into the undo log. A reader with an older snapshot follows a chain of undo records backwards to rebuild the version it should see. Purge removes undo records once no snapshot needs them.

Neither is "better"; they shift costs around. Postgres makes old versions cheap to read but spreads dead versions through the table, so it leans on vacuum. InnoDB keeps the main table compact but makes reading old versions slower, since it has to rebuild them. These design differences, together with how each engine writes and replicates changes, were part of why Uber moved a major workload from Postgres to MySQL; Case 4 walks through that story.

Snapshot isolation and its limit

Give each transaction one snapshot for its whole life and you get snapshot isolation (SI): consistent reads (no read skew), no dirty reads, and, with a check that two transactions don't commit writes to the same row (first committer wins; Postgres checks when the second write is attempted, so it is really first updater wins), no lost updates either. Everything above is how it is implemented.

What SI does not do is notice that your decision was based on something someone else changed. In the doctors example, each transaction's snapshot was perfectly consistent, and they wrote different rows. SI allows write skew and phantom-style anomalies. To close that last gap without going back to heavyweight locking, researchers developed something clever.

Serializable snapshot isolation (SSI)

Serializable snapshot isolation keeps SI's cheap, non-blocking reads but adds tracking of what each transaction read, so it can detect the dangerous situations SI misses. It was proposed by Cahill, Röhm and Fekete in 2008, and PostgreSQL has used it for its SERIALIZABLE level since version 9.1 (described by Ports and Grittner in a 2012 paper).

The idea rests on one observation. Write skew happens because transaction T1 read something that T2 then wrote (an rw-dependency: T1 must logically come before T2, since it did not see T2's write), and symmetrically T2 read something T1 wrote. Each says "I came first", and no serial order can satisfy both.

SSI works as follows. While transactions run under snapshot isolation, the database records which data each one read (Postgres calls these markers SIREAD locks, but they don't block anyone, they just remember) and notices when another transaction writes something already read. It records an rw-edge for each such pair. The problem shape it is looking for is a pivot: a transaction with both an incoming and an outgoing rw-edge (plus a commit-order condition), which is the signature of the cycles that SI lets through. When one appears, the database aborts one of the transactions with a serialization failure (SQLSTATE 40001), and the application retries it. On retry, the aborted transaction sees the committed result of the other, and the rule holds.

Two caveats are worth remembering. SSI may abort a transaction in some cases where the execution would actually have been fine (false positives), because tracking is deliberately coarse to stay cheap. And it is optimistic: nobody waits, everyone runs, and the price is paid in aborts. That is good when conflicts are rare and bad when they are frequent, because aborted work is wasted work. The pessimistic 2PL pays the cost as waiting instead.

Actual serial execution

All of the above exists to let transactions overlap safely. There is a radical alternative: do not let them overlap. Run every transaction one at a time, on a single thread. That is trivially serializable, and it has no locks, no deadlocks, no version bookkeeping. It sounds absurdly slow, but it became feasible for two reasons: RAM is cheap enough that many datasets fit in memory, so a transaction never waits for a disk read; and designers realised the slow part of a classic transaction was the back-and-forth with the client (one round trip per statement, network latency in the middle of the transaction).

So systems in this style demand that a transaction be submitted whole, as a stored procedure: the entire logic is sent to the database, which runs it start to finish without waiting for anyone. VoltDB works this way, partitioning data across cores so each partition has its own single thread. Redis executes commands one at a time on a single thread, so a MULTI/EXEC block or a Lua script runs without anyone else's command interleaving (note that Redis does not roll back the commands that already ran if a later one in the block fails: it gives isolation, not full atomicity). The thread-per-core idea is the same event-loop architecture you met in systems chapter 16, and systems case 5 shows how fast one well-fed thread can be.

The limits are real: throughput is capped by one CPU core per partition; transactions that span partitions need extra coordination and slow everything down; a single slow transaction stalls the queue behind it; and interactive, multi-step transactions with human think-time are out. It is a superb fit for short, predictable transactions on data that can be partitioned well, and a poor one for ad-hoc analytics.

Try it yourself

Try it yourself: watch a reader not block a writer

SQLite's default mode makes writers and readers interfere, but its WAL mode uses snapshots, so you can see MVCC-like behaviour with nothing but Python. This script opens a reader transaction, lets a writer change and commit the row, and shows the reader still seeing its snapshot.

import sqlite3, os
path = "wal.db"
for f in (path, path + "-wal", path + "-shm"):
    if os.path.exists(f): os.remove(f)
s = sqlite3.connect(path)
print("journal mode:", s.execute("PRAGMA journal_mode=WAL").fetchone()[0])
s.execute("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER)")
s.execute("INSERT INTO accounts VALUES ('alice', 100)")
s.commit(); s.close()

reader = sqlite3.connect(path, isolation_level=None, timeout=0.2)
writer = sqlite3.connect(path, isolation_level=None, timeout=0.2)

reader.execute("BEGIN")
print("reader, first read :", reader.execute("SELECT balance FROM accounts").fetchone()[0])
writer.execute("BEGIN")
writer.execute("UPDATE accounts SET balance = 70 WHERE name = 'alice'")
print("reader, writer open:", reader.execute("SELECT balance FROM accounts").fetchone()[0])
writer.execute("COMMIT")
print("reader, after commit:", reader.execute("SELECT balance FROM accounts").fetchone()[0], "(same snapshot)")
reader.execute("COMMIT")
print("reader, new txn    :", reader.execute("SELECT balance FROM accounts").fetchone()[0])

The writer committed while the reader's transaction was open, and the reader was neither blocked nor disturbed: it kept its snapshot until it ended. (SQLite still allows only one writer at a time; what WAL mode adds is that readers and the writer don't wait for each other. Delete the wal.db* files afterwards.)

Distributed systems connection

Every one of these mechanisms has a distributed version, and each gets harder. Distributed 2PL needs a lock held on one machine to be honoured by transactions on another, and a distributed deadlock detector needs to see wait-for edges across machines. MVCC across machines needs a shared notion of "the snapshot at time t", which needs ordered timestamps (networking chapter 17). Google's Spanner pairs locking for read-write transactions with timestamped multi-version snapshots for read-only ones, and agrees on commit with two-phase commit across shards (see networking case 10). The serial-execution idea scales out by partitioning: each shard runs a single thread, and the hard cases are exactly the transactions that cross shards (chapter 16). Long-held snapshots also appear in replication: a replica that applies changes while serving long queries has to either pause replay or cancel the queries, a trade-off chapter 15 revisits.

Key takeaways

  • Isolation is implemented either pessimistically (locks, so transactions wait) or optimistically (versions plus conflict detection, so transactions abort), or by not overlapping transactions at all.
  • Locks come in shared (read) and exclusive (write) flavours. Two-phase locking has a growing and a shrinking phase; strict 2PL holds locks until commit. It gives serializability, but readers block writers and writers block readers, and deadlocks are routine.
  • Phantoms need range protection: predicate locks in theory, index-range (next-key) locks in practice. Without a suitable index the database may lock far more than you meant.
  • Databases detect deadlocks by finding cycles in a wait-for graph and aborting a victim. Your code must retry; consistent lock ordering and short transactions reduce them.
  • MVCC keeps several versions per row, stamped with the transactions that created and deleted them. A snapshot sees the versions whose creators committed before it and whose deleters had not. Readers don't block writers.
  • Old versions are garbage collected (VACUUM in Postgres, purge of undo in InnoDB), but only once no snapshot needs them, so a long-running transaction causes bloat. Postgres stores new versions in the heap; InnoDB keeps the newest in place and old ones in undo.
  • SSI (Cahill et al. 2008; Postgres Serializable since 9.1) adds read tracking to snapshot isolation, detects dangerous rw-dependency structures such as write skew, and aborts one transaction. It is optimistic: no blocking, but retries.
  • Serial execution (VoltDB, Redis) is lock-free and trivially serializable but needs short, stored-procedure-style transactions and good partitioning.

Check your understanding

In strict two-phase locking, when does a transaction release its exclusive locks?

  1. As soon as it has finished using each item
  2. At commit or abort, all together
  3. Never; they expire after a timeout
  4. Before it reads anything new
Strict 2PL holds exclusive locks until the transaction ends. That stops others reading uncommitted data and means the shrinking phase is a single instant at commit or abort. Releasing early and then locking more would violate the two-phase rule.

Why is a long-running report query painful under two-phase locking but harmless under MVCC?

  1. MVCC reports run on a different machine
  2. MVCC skips all reads from disk
  3. MVCC databases never take any locks
  4. Under 2PL its shared locks block writers on every row it touched, while under MVCC it reads from a snapshot and takes no locks that block writers
With 2PL, readers hold shared locks until commit, so writers of those rows wait. With MVCC, the reader uses an old version, so writers proceed. MVCC still takes some locks (for write-write conflicts); it just does not make readers and writers block each other.

How do index-range (next-key) locks protect against phantoms?

  1. They lock the index entries a scan touches and the gaps between them, so inserting a new matching row must wait
  2. They copy the table so inserts go elsewhere
  3. They lock only rows that already exist
  4. They convert the transaction to read-only
A new row must be inserted into some gap of the index. If the scan has locked the gaps it covered, the insert blocks. That is why locks that cover only existing rows cannot stop phantoms.

What does PostgreSQL's SERIALIZABLE level do, compared with locking-based serializability?

  1. It takes a table lock for every transaction
  2. It runs every transaction on a single thread
  3. It runs transactions on snapshots, tracks read-write dependencies and aborts one when it finds a dangerous structure, so you must retry
  4. It disables MVCC
Postgres uses serializable snapshot isolation (SSI) since 9.1. Reads do not block, it records what transactions read and wrote, and it aborts a transaction (SQLSTATE 40001) when the pattern could be non-serializable. The application retries.

Roughly how do Postgres and InnoDB differ in where old row versions live?

  1. Postgres keeps them in the undo log, InnoDB in the heap
  2. Postgres keeps them as extra row versions in the table (heap) until VACUUM; InnoDB keeps the newest row in place and rebuilds older versions from the undo log
  3. Both discard old versions immediately
  4. Both keep every version forever
This is the main storage difference between the two MVCC designs. It shapes bloat (Postgres, cleaned by vacuum) and the cost of reading old versions (InnoDB, rebuilt via undo, cleaned by purge).

Which workload is the best fit for actual serial execution (one thread, stored procedures)?

  1. Long, interactive transactions with user think-time in the middle
  2. Ad-hoc analytics scanning the whole dataset
  3. Transactions that routinely touch every partition
  4. Short, predictable transactions on in-memory data that partitions cleanly
Serial execution removes lock and version overhead but stalls the queue behind any slow transaction, so transactions must be short and submitted whole. Data that fits in memory avoids disk waits, and clean partitioning avoids slow cross-partition coordination.

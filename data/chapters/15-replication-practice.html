Replication in Practice

In networking chapter 18 you learned the ideas: leaders, followers, lag, quorums. This chapter is about what actually crosses the wire, what a user sees while a follower is behind, how a new follower is born, and what really happens on the worst night: when the leader dies and you have to decide, quickly, whether it is really dead.

Why this matters

Replication is where "the database is highly available" meets the fine print. The fine print decides whether a user's freshly uploaded photo disappears for a few seconds, whether a failover quietly deletes the last second of acknowledged orders, and whether two machines both think they are in charge. If you can describe, for any setup, exactly which writes can be lost and which anomalies a reader can see, you can design (and debug) systems that keep their promises. If you cannot, you find out in production.

A quick recap, and what we add

You already know the shape. In single-leader replication one node, the leader, accepts all writes and puts them in an ordered log. Followers apply that log in the same order, so they end up in the same state. Reads can be served by the leader or by followers, which may be a little behind. Networking chapter 18 covered why you would do this (durability, availability, read scaling, latency), the synchronous-versus-asynchronous trade-off in outline, the two classic lag anomalies, and the dangers of failover in outline. We will not repeat those arguments. This chapter goes one level down on each, adds the parts that chapter did not have room for (the log formats, consistent prefix reads, bootstrapping a follower, fencing in detail), and lets you try the anomalies in a simulator.

What actually gets shipped

"The follower applies the leader's log" hides a design question: what is in the log? There are three common answers, and the choice shapes what your replication can and cannot do.

Statement-based replication ships the SQL text. It is small and easy to understand, and it was how MySQL replication started. But re-executing a statement on another machine is only safe if the statement is deterministic. NOW() gives each machine a slightly different time; RAND() and UUID() give different values; a statement that depends on a row's auto-increment value, or on the order other statements ran in, can produce different results; triggers and stored procedures can have side effects. Databases work around the easy cases (the leader can substitute a fixed value for NOW()), but the long tail of exceptions is why most systems moved away from it.

Physical (WAL) shipping ships the same write-ahead log the database already writes for crash recovery (chapter 13; and the log idea from systems chapter 9): "on page 912, at offset 40, these bytes". PostgreSQL's streaming replication works this way. It is efficient and exact (the follower's files become byte-for-byte equivalent in content), and it comes for free because the log already exists. The cost is that the log is tied to the storage engine: the follower generally has to run a compatible version of the same engine, you cannot replicate just one table, and the log says nothing about what changed in terms anyone else could use. This tight coupling is one of the themes of Case 4, and it is also what lets Aurora treat the log as the database.

Logical (row-based) replication ships a description of the change to each row: "in table t, the row with id 7 had these old values and now has these new ones". MySQL's binary log can be set to a statement format, a row format, or a mixed mode that chooses per statement. PostgreSQL offers logical replication in addition to its physical streaming (it publishes changes per table). Because it is expressed in terms of rows and not bytes, it survives version upgrades, can replicate a subset of tables, and can be consumed by things that are not databases at all: a search index, a cache invalidator, an analytics pipeline. That last use is called change data capture, and it is the subject of chapter 19.

Analogy: three ways to keep two ledgers equal

Two bank branches keep copies of the same ledger. You could phone through the instructions ("add interest to all savings accounts"), which is fast, but if the two branches round differently they now disagree. You could photocopy each page as it changes, which makes the copies identical, but only if both branches use the exact same ledger format. Or you could send each entry ("account 7: 100.00 becomes 105.00"), which is a bit more to send, but robust and readable by anyone.

Where it breaks down: real databases also need to preserve the order and the transaction boundaries of those entries, which a pile of notes does not. The log is an ordered stream, not a bag.

How long the leader waits: synchronous, asynchronous, semi-synchronous

Networking chapter 18 gave the headline; here is the part that matters when you operate one. When the application sends COMMIT, at what point does the leader reply "done"?

ModeThe leader replies when...Write latencyIf the leader dies right after
Asynchronousits own log is durableLowest: no network waitAcknowledged writes can be lost: the followers may not have them
Semi-synchronousits own log is durable and at least one follower has received (or applied) itOne extra round trip to the nearest followerThe write exists on two machines, so a promotion of that follower loses nothing
Synchronous (to all)every follower has itThe slowest follower's round tripNothing lost; but any one slow or dead follower stalls all writes

Most production setups are asynchronous or semi-synchronous. PostgreSQL has settings (synchronous_commit and synchronous_standby_names) to require acknowledgement from one or more named standbys before a commit returns, and MySQL has a semi-synchronous replication plugin, in which a replica acknowledges that it has written the events to its relay log, not that it has applied them, and the source falls back to asynchronous replication if no replica answers within a timeout; check your version's documentation for the exact guarantees, since "received" and "applied" and "flushed to disk" are different points on the follower and different settings pick different ones.

The durability trade-off is worth saying plainly. With asynchronous replication, "committed" means "the leader has it", not "the data is safe". If the leader's disk or machine is lost before the log reaches a follower, those writes are gone, and the user was already told they succeeded. Semi-synchronous replication shrinks that window to "the leader and its sync follower both die before the next promotion", which is a far rarer event, at the price of putting a network round trip in every commit. If that follower sits in another region, the round trip might be tens or hundreds of milliseconds, which is why synchronous cross-region replication is rare outside systems built for it. And, as in systems chapter 9, "a follower has it" is only as durable as the follower's own fsync.

"We have replicas" is not "we have backups"

A replica faithfully copies mistakes too: a DROP TABLE or a bad UPDATE replicates in milliseconds. Replication protects against losing a machine; it does not protect against losing the data to a human or a bug. Case 5 is the story of a team who found out the hard way that they needed both, and needed to have tested restoring from them.

Replication lag and what users see

With asynchronous (or semi-synchronous) replication, the followers are always at least a little behind. This gap, in time or in log position, is the replication lag. It is often milliseconds; it can be seconds or minutes when a follower is overloaded, running a long query, applying a huge transaction, or recovering from a network problem. You can measure it: on PostgreSQL the pg_stat_replication view on the leader reports how far each standby has received, flushed and replayed; other databases have equivalents.

Lag is not a bug; it is the cost of not waiting. The trouble is what it does to a person using the system, because a user does not think in terms of replicas. They think "I just did a thing". Three anomalies cover most of what you will see. Each is a way in which reading from a lagging follower contradicts something the user already knows.

1. Read-your-writes

You change your profile photo. The write goes to the leader and the page says "saved". You reload, and the read goes to a follower that has not received the change yet. Your old photo is back. The guarantee you expected, read-your-writes (or read-after-write consistency), says: after I write something, my own later reads must show it (other people's reads may still be stale).

Fixes, from simplest to most precise:

  • Read from the leader for data the user may have just changed. The profile page you are editing is always read from the leader; other people's profiles can come from followers. This needs no tracking but only works if you can tell, per query, whether it is "mine".
  • Read from the leader for a short window after any write by this user (say, a minute, longer than the usual lag). Simple and effective; fails if lag ever exceeds the window.
  • Track the position of the user's last write and read only from a follower that has caught up to it. The write returns a log position (a log sequence number, LSN, in PostgreSQL terms; MySQL uses a similar idea with transaction identifiers). The application remembers it for that user and sends it with later reads, and the router or the follower waits until the follower has applied at least that position, or the router picks a follower that already has. This is the precise fix, and it is the fourth policy in the simulator below.

It gets harder when the same person uses several devices: the "remembered position" must live in a place both devices can reach (the server, not a cookie in one browser), and if different devices might be routed to different regions, you may need to route all of a user's requests to one region.

2. Monotonic reads

Now you read twice with no write in between. The first request goes to follower A, which is up to date, and shows a new comment. You refresh; the second request goes to follower B, which is further behind, and the comment is gone. You saw the future and then the past. The guarantee you expected is monotonic reads: successive reads by one user never go backwards in time.

The usual fix is to make each user's reads sticky: always route the same user to the same follower, for example by hashing the user id (not by choosing randomly per request). That follower may be stale, but it will never be less stale than it was a moment ago. If that follower fails, the user is rerouted, and a monotonicity violation is possible once; a stricter fix is to carry the last-seen position, as for read-your-writes. Note that sticky routing alone does not give read-your-writes, since the pinned follower may be behind your own write. You can see that in the simulator.

3. Consistent prefix reads

The third anomaly appears when the data is split across several partitions (shards, chapter 16), each with its own replication stream and its own lag. Suppose one person asks a question and another answers it. The two messages live on different partitions. The answer's partition replicates quickly; the question's partition is slow. An observer reads at a moment when the answer has arrived but the question has not, and sees the answer to a question that, as far as they can tell, was never asked.

Consistent prefix reads is the guarantee that if a sequence of writes happened in some order, a reader sees them in that order (any prefix of the history, never one with a gap). It is not a problem in a single-partition database because there is one log with one order. Fixes: put causally related writes on the same partition so they share one log, or have the system track which writes depend on which (the "happened before" idea from networking chapter 17) and delay showing an effect until its cause has arrived.

Analogy: newspapers that arrive on different days

A town gets its news from two printers. One prints on Monday, the other (slower) on Wednesday. A reader on Tuesday has Monday's paper, not Wednesday's: that is simple staleness and is fine. But read-your-writes is "I wrote a letter to the editor and my own copy of today's paper does not show it". Monotonic reads is "yesterday I read Wednesday's paper, and today my copy is Monday's". Consistent prefix is "the reply is printed in this paper, the letter it replies to is in the other".

Where it breaks down: readers of newspapers never write into them and never have two copies at once. In a database the same person is often both the writer and a reader of several copies, which is exactly what produces these anomalies.

    Simplified, on purpose

    Failover in the simulator is instant and perfectly informed. Real systems need time to notice a failure, can pick the wrong follower, and can be fooled into failing over when nothing has died. That is the next-but-one section. Lag is also a fixed number here; in real life it varies from moment to moment.

    Setting up a new follower

    Eventually you need to add a follower: to scale reads, to replace a dead one, or to move to new hardware. You cannot just copy the data directory while the database is changing, because the copy would be inconsistent. And you do not want to stop the leader. The standard recipe has three steps:

    1. Take a consistent snapshot of the leader at a known log position (say LSN 1000), without locking it for the duration. Databases with multi-version storage (chapter 12) can do this cheaply because a snapshot is just "the versions visible at position 1000". PostgreSQL's pg_basebackup is a standard tool that copies a running server's files together with the log needed to make them consistent.
    2. Copy the snapshot to the new node. This can take minutes to hours for a large database; meanwhile the leader keeps accepting writes.
    3. Start the follower and have it request the log from position 1001. It replays everything that happened while the snapshot was copying. It is catching up. Once the remaining gap is small, it switches to streaming new changes as they happen, and is a normal follower.

    The log must still exist

    Catch-up only works if the leader has kept the log since the snapshot. Databases normally delete old log segments once they are no longer needed for recovery. So a follower that falls too far behind, or is offline too long, may find that the records it needs are gone, and must be rebuilt from a fresh snapshot. The opposite protection has its own hazard: PostgreSQL's replication slots make the leader hold on to log until a given follower has consumed it, which is safe for the follower but means a dead or stuck follower makes the leader's disk fill up with retained log. Monitor both.

    Failover

    The leader will fail, so you need a plan for it. Failover is promoting a follower to be the new leader. It can be manual (a person decides) or automatic (software decides, using tools or a managed service; Patroni for PostgreSQL and Orchestrator for MySQL are well-known examples). It has three parts, and each hides a hazard.

    1. Detecting the failure

    There is no way to look at a machine from across a network and know it is dead. All you can see is that it has stopped answering, which is what a crashed machine, a slow one, a congested network and a dead network cable all look like (networking chapter 16). So detection is a timeout: if the leader misses heartbeats for N seconds, declare it dead.

    This is a genuine trade-off, not a tuning detail:

    • Too short and a garbage-collection pause, a busy disk or a network blip triggers a failover for a leader that was fine. Failover is itself disruptive and adds load (a new leader, caches cold, connections dropping), which can make a struggling system worse, which causes another false failover.
    • Too long and a genuinely dead leader means a long outage while everyone waits to be sure.

    2. Choosing a new leader

    The best candidate is the follower with the most up-to-date log, because it loses the fewest writes. Choosing needs agreement (every node must pick the same one), which is a consensus problem: a reason that serious systems build failover on top of a consensus protocol or a coordination service (networking chapter 20).

    3. Reconfiguring everyone

    Clients must send writes to the new leader, the other followers must follow it, and, crucially, the old leader, if it ever returns, must understand that it is no longer the leader and step down.

    What can go wrong

    • Lost writes. With asynchronous replication, the promoted follower may lack the old leader's last writes. When the old leader comes back with those writes in its log, they conflict with what the new leader has done since. The usual choice is to discard them. That is silent data loss for writes already acknowledged to clients. Worse, it can break things outside the database: if the old leader had handed out auto-increment ids that were sent to another system, the new leader may reuse them for different rows.
    • Split brain. Two nodes both believe they are the leader and both accept writes. The data diverges, and there may be no clean way to merge it. This happens when the old leader was only cut off or paused, not dead.
    • The timeout trade-off, above.

    The best-documented example is Case 1: GitHub, 2018. A network partition of about 43 seconds made an automated system promote a database in a different data centre; both data centres then held writes the other lacked, and untangling it took the better part of a day. Read it as a worked example of everything in this section.

    Stopping the zombie: fencing

    The standard defence against split brain is fencing: making it impossible for the old leader to do damage even if it does not know it has been replaced. One strong version is to cut it off physically (power it off or cut its storage access; the unfriendly acronym is STONITH, "shoot the other node in the head"). The more general version uses a fencing token: every time leadership changes, a coordination service hands out a larger number (called an epoch, a term or a generation; Raft's term is one, see networking chapter 20). Every write to storage carries the writer's token, and the storage refuses any write whose token is lower than the highest it has seen.

    Notice where the safety comes from: not from the old leader behaving well, but from the resource checking the number. This is the same lesson as with locks and leases in systems chapter 12, now across machines: a lease tells a process "you may act until time T", but a paused process cannot know that T has passed. Only a check at the point of use is reliable. Consensus-based systems make the term number do this job automatically.

    Analogy: the captain who slept through the handover

    A ship's captain falls into a deep sleep. The crew, unable to wake them, appoint a new captain and issue a new, numbered set of orders. The first captain wakes up and shouts an order. A sailor who insists on seeing the order number can tell it is out of date and ignores it. Without that rule, the ship has two captains giving contradictory orders.

    Where it breaks down: a sleeping captain knows they slept. A paused process (a long GC pause, a VM freeze, a delayed packet) resumes with no sense that any time has passed.

    Multi-leader replication

    A single leader means every write travels to one place. That is a poor fit in three situations:

    • Multi-region. Users in Europe and Asia want fast writes. With one leader in one region, every distant write pays a long round trip, and if the link between regions fails, one side cannot write at all. With a leader per region, each region writes locally and the leaders replicate to each other asynchronously.
    • Offline clients. A phone calendar or a note-taking app accepts edits with no network. Each device is effectively a leader that syncs later.
    • Real-time collaboration, where many people edit one document and each sees their own edits at once.

    The price is the one single-leader avoided: there is no longer a single order of writes, so two leaders can accept conflicting changes to the same item at the same time, and neither is "first". Conflicts are found only later, when the leaders exchange their logs. (Other, subtler hazards exist as well: auto-increment keys, triggers and constraints can interact badly across leaders, so databases with this feature tend to warn about it.) There are three families of answer:

    • Avoid conflicts. Route every write for a given item to one particular leader (for example, each user has a "home region"). Within that item you effectively have single-leader again, and conflicts cannot occur. The weak point is when the home region is down or the user moves.
    • Pick a winner: last write wins (LWW). Attach a timestamp and keep the highest. It always converges, which is its charm, but it throws away the losing write silently. And because the timestamps come from wall clocks that disagree (networking chapter 17), the "last" write may be the earlier one. LWW is acceptable for data where losing an update is fine (a "last seen" time), and dangerous for anything else.
    • Merge. Keep both versions and let the application merge them, or use data structures that merge automatically: CRDTs (conflict-free replicated data types), which are designed so that updates applied in any order give the same result. A counter where each replica counts only its own increments and the total is the sum is the simplest; sets that only grow and certain sequence structures used in collaborative editors are others.

    Both outcomes are in the demo script at the end of the chapter; in short, LWW lost an edit and the counter lost nothing.

    Leaderless replication goes one step further: no leader at all, clients write to and read from several replicas and use quorums (W + R > N) to get fresh data. That is the Dynamo style described in networking chapter 18, and networking Case 9 tells the story of Amazon's shopping cart. It has its own anomalies (quorums are not linearizable, stale reads after partial writes, sloppy quorums) which that chapter introduced; the practical point here is that "leaderless" and "multi-leader" both buy availability and locality by accepting conflicts.

    Read replicas for scaling reads

    The most common reason people add followers is simply to serve more reads: the application sends writes to the leader and spreads reads across several read replicas. For read-heavy workloads (which most web applications are) this works well, and an analytics query that would disturb the leader can be sent to a replica instead. But go in with open eyes:

    • It does not scale writes. Every replica must apply every write, so with a write-heavy workload the replicas are as busy applying the log as the leader is producing it. (You scale writes by splitting the data: chapter 16.)
    • Lag becomes everyone's problem. Everything above applies: you need a read-your-writes strategy, and you should monitor lag and remove a replica from rotation when it is too far behind. A long-running query on a replica can itself hold up replay of the log; PostgreSQL has settings that decide whether the query or the replay gives way.
    • The router needs a brain. Something (the application, a connection pool, a proxy) must know which statements are safe to send to a replica, which replica is healthy, and what to do when one disappears. A cache from chapter 14 in front of the database often relieves the read pressure more cheaply, with a similar staleness trade-off.
    • Capacity planning must include failover: if the leader fails and a replica is promoted, the remaining replicas must carry the read load.

    Try it yourself

    Try it yourself: lag, anomalies and lost writes in 50 lines of Python

    This script uses the same model as the simulator: a leader's log, followers that apply each entry lag milliseconds later, and a logical clock. Save it as repl_demo.py and run it with Python 3 (no packages). Then change the lag values and the kill time and predict the output before you run it.

    class Leader:
    def __init__(self):
        self.log = []                        # (lsn, key, value, time_written)
    def write(self, key, value, now):
        lsn = len(self.log) + 1
        self.log.append((lsn, key, value, now))
        return lsn                           # the client is told "OK" with this position

class Follower:
    def __init__(self, name, lag_ms):
        self.name, self.lag = name, lag_ms
    def applied_lsn(self, leader, now):
        """Highest LSN whose entry was written at least lag ms ago."""
        return max([e[0] for e in leader.log if e[3] + self.lag <= now], default=0)
    def read(self, leader, key, now):
        n = self.applied_lsn(leader, now)
        vals = [e[2] for e in leader.log[:n] if e[1] == key]
        return (vals[-1] if vals else None), n

leader = Leader()
a, b = Follower("A", lag_ms=20), Follower("B", lag_ms=300)

lsn = leader.write("photo", "new.jpg", now=0)
print(f"t=0   write acknowledged, lsn={lsn}")

for t in (10, 50, 400):
    for f in (a, b):
        v, n = f.read(leader, "photo", t)
        print(f"t={t:<4} read from {f.name} (applied lsn {n}) -> {v}")

print("\n-- read-your-writes: only use a follower that has reached my last write --")
for t in (10, 50, 400):
    ok = [f.name for f in (a, b) if f.applied_lsn(leader, t) >= lsn]
    print(f"t={t:<4} eligible followers: {ok or 'none -> read the leader'}")

print("\n-- monotonic reads: A then B breaks it --")
va, _ = a.read(leader, "photo", 50)
vb, _ = b.read(leader, "photo", 60)
print(f"t=50 from A -> {va};  t=60 from B -> {vb}   (time went backwards)")

print("\n-- async failover loses acknowledged writes --")
for i in range(2, 6):
    leader.write("photo", f"v{i}.jpg", now=1000 + 10 * i)
kill = 1052
best = max((a, b), key=lambda f: f.applied_lsn(leader, kill))
n = best.applied_lsn(leader, kill)
print(f"leader dies at t={kill}; best follower is {best.name} at lsn {n} of {len(leader.log)}")
print(f"acknowledged but lost: lsn {n+1}..{len(leader.log)}")

print("\n-- multi-leader: last-write-wins vs a CRDT counter --")
# Two leaders accept writes while disconnected. Region B's clock runs about 20 ms slow.
edit_a = {"key": "title", "value": "Draft",  "ts": 100}   # real time 100, A's clock says 100
edit_b = {"key": "title", "value": "Final",  "ts":  99}   # real time 120 (later!), B's clock says 99
winner = max((edit_a, edit_b), key=lambda e: e["ts"])
print(f"LWW keeps {winner['value']!r}; the edit made later in real time ('Final') is silently dropped")

def merge_counters(x, y):
    """G-counter: each replica only increments its own slot; merge = per-slot max."""
    return {r: max(x.get(r, 0), y.get(r, 0)) for r in x.keys() | y.keys()}

likes_a = {"A": 3}            # 3 likes arrived at region A
likes_b = {"B": 5}            # 5 likes arrived at region B
merged = merge_counters(likes_a, likes_b)
print(f"CRDT counter merge: {dict(sorted(merged.items()))} -> total {sum(merged.values())}  (merge in either order: "
      f"{sum(merge_counters(likes_b, likes_a).values())})")

    Distributed systems connection

    Everything in this chapter is a consequence of one fact from networking chapter 16: you cannot tell a dead machine from a slow one. Lag anomalies come from reading a slow copy; failover danger comes from guessing wrongly about a slow leader; split brain is what happens when a "dead" node was merely slow. Fencing tokens and terms are the cure, and they are exactly what consensus protocols such as Raft provide (networking chapter 20). The next chapter, sharding, does the other kind of splitting: instead of copies of the same data, different slices on different machines. Real systems do both: every shard is itself a replicated group.

    Key takeaways

    • Replication logs come in three kinds: statement-based (risky with non-determinism), physical or WAL shipping (exact and cheap, but tied to the engine version) and logical or row-based (portable, and the basis of change data capture).
    • Asynchronous replication can lose acknowledged writes on failover. Semi-synchronous replication puts the write on two machines before replying, at the price of one round trip per commit. Replicas are not backups.
    • Lag produces three user-visible anomalies: read-your-writes (route to the leader or track the last-write position), monotonic reads (sticky routing) and consistent prefix reads (keep related writes on one partition, or track causality).
    • A new follower is built from a consistent snapshot plus the log from that position onward; the leader must keep that log until the follower has caught up.
    • Failover is a guess: detection is a timeout, and the timeout trades false alarms against long outages. Its dangers are lost writes and split brain.
    • Fencing tokens (epochs, terms) let the storage reject a stale leader. Safety comes from the check at the point of use, not from the old leader's good behaviour.
    • Multi-leader and leaderless setups gain local writes and availability by accepting write conflicts. Last-write-wins loses data; merging with CRDTs or application logic does not. Read replicas scale reads, never writes.

    Check your understanding

    Why can statement-based replication make followers diverge, while row-based replication does not?

    1. Statements are always longer than row changes
    2. Statement-based replication cannot be used with a leader
    3. Re-executing a statement such as UPDATE ... SET ts = NOW() on each follower can give a different result there, whereas a row change carries the exact new values
    4. Row-based replication ignores transaction order
    Non-deterministic functions (NOW, RAND, UUID), order-dependent statements and side-effecting triggers can behave differently when re-run. A row-based log records the actual outcome, so every follower gets the same values.

    A database replicates asynchronously. The leader acknowledges 5 commits and then its machine is destroyed. The most up-to-date follower has applied only 3 of them. What is the outcome after failover?

    1. Commits 4 and 5 are lost, although the clients were told they succeeded
    2. The follower retrieves them from the destroyed leader
    3. All 5 commits survive because the data was durable on the leader
    4. The database refuses to promote any follower
    "Durable on the leader" is not durable if the leader is lost. Asynchronous replication acknowledges before followers have the data, which is precisely the window in which an acknowledged write can vanish.

    A user posts a comment, then refreshes and does not see it. A minute later it appears. Which guarantee was violated, and which fix addresses it most directly?

    1. Monotonic reads; make users sticky to one follower
    2. Consistent prefix; move the data to one partition
    3. Durability; use fsync more often
    4. Read-your-writes; route that user's reads to the leader (or to a follower that has reached the position of their write) after they write
    The user failed to see their own write: a read-your-writes violation. Reading from the leader for recently written data, or waiting for a follower to reach the write's LSN, fixes it. Stickiness alone would not.

    You make every user sticky to one follower (hashing the user id). Which of these is now guaranteed?

    1. The user always sees their own latest write
    2. The user's successive reads never go backwards in time, as long as that follower stays up
    3. The user never sees stale data
    4. No writes can be lost on failover
    A single follower only ever applies the log forward, so reads from it are monotonic. But it can still be behind the user's own write, and it says nothing about failover.

    The old leader of a database was merely frozen by a long pause. After a failover it wakes up and tries to write. What mechanism lets the storage layer reject it even though the old leader still believes it is in charge?

    1. A longer heartbeat timeout
    2. Adding more followers
    3. A fencing token (epoch or term): the storage has seen a higher number from the new leader and refuses writes carrying the old, lower one
    4. A faster fsync on the old leader
    Timeouts only guess; the old leader cannot know it was replaced. A monotonically increasing token checked by the resource makes the stale writer harmless regardless of its own beliefs.

    Two regions each accept an edit to the same document title while disconnected. Region B's edit was made later in real time but its clock runs behind. With last-write-wins, what happens?

    1. Both edits are kept and shown to the user
    2. The later edit wins, because LWW tracks real time
    3. The system detects the conflict and asks a human
    4. Region A's edit wins (higher timestamp) and region B's edit is silently discarded, even though it happened later
    LWW compares timestamps from unsynchronised clocks, always converges, and silently drops the loser. Detecting concurrency and merging (version vectors, CRDTs, application logic) is how you avoid losing data.

Caching

A cache is a small, fast copy of data that is expensive to fetch, kept close to whoever keeps asking for it. It is the cheapest speed-up in all of computing, and it comes with a bill: every cache is a second copy that can be wrong. This chapter covers the patterns, the arithmetic of why they work, and the three ways caches hurt you: stale data, stampedes, and a cold start.

Why this matters

Almost every system that serves real traffic has a cache in front of its database, and most "the site fell over" stories involve one: it expired all at once, it was emptied by a restart, or it served a value that was wrong for a day. Phil Karlton's old joke says there are only two hard things in computer science, cache invalidation and naming things. The joke has lasted because it is true. By the end of this chapter you will be able to choose a caching pattern for a workload, say exactly how it can go stale, and explain what protects the database on the worst day.

Why caches work: the arithmetic

You met the idea in systems chapter 2: memory comes as a ladder, where each rung is bigger, slower and cheaper than the one above. A cache is the same trick applied to any slow thing. Keep the data you used recently on a faster rung, and most of the time you never climb down to the slow one. In our library analogy from earlier in this course, the cache is the desk you keep your open books on: the shelves hold everything, but you do not walk to them for every sentence.

A request that finds its data in the cache is a hit. One that does not is a miss, and it pays for the cache lookup and the slow fetch. The fraction of requests that hit is the hit ratio h. If a hit costs thit and a miss costs tmiss (all-in), the average is:

average latency = h × t_hit + (1 − h) × t_miss

Take a hit that costs 1 ms (a network call to Redis) and a miss that costs 100 ms (the cache lookup plus a slow database query). The rows below also show something the average hides: how many queries per second the database still receives from a service doing 10,000 requests per second.

99.9%1.099 ms10

Two lessons sit in that table. First, the useful number is the miss ratio. Going from 99% to 99.9% looks like a rounding error, but it cuts the database's load by a factor of ten. Second, the database is sized for the misses. If you build a system that only works at a 99% hit ratio, then the day the cache is empty it receives 100 times the load it was built for. We will come back to that day.

Analogy: the desk and the shelves

You are researching in the library. Walking to the shelves for each fact takes minutes. So you keep the half-dozen books you are using open on your desk. Most lookups are answered from the desk. When you need something that is not there, you walk to the shelves, bring it back, and, because the desk is small, put something away to make room.

Where it breaks down: the books on your desk are the same books as on the shelf, and nobody else edits them. A cache in a system holds copies of data that other writers keep changing, so the copy on the desk can be out of date without you knowing. Most of this chapter is about that.

Where caches live

"Add a cache" is not one decision but a choice of layer. A single request may pass through five of them.

  • Browser cache. The cheapest hit of all, because the request never leaves the device. You control it with HTTP headers such as Cache-Control: max-age=... (see networking chapter 10). You cannot reach into a user's browser and delete an entry, so you set lifetimes you can live with, or put a version in the file name (app.3f9a1c.js).
  • CDN. A fleet of caching reverse proxies near your users, as in networking chapter 14. Great for images, scripts and other responses that are the same for everyone. You can purge a CDN, but it takes time to reach every edge.
  • In-process cache. A dictionary inside your application. No network, no serialisation, nanoseconds. But each app instance has its own copy, so ten instances can disagree, and it dies on every deploy.
  • Shared cache (Redis, Memcached). A separate service that every instance of your app talks to. One hop away (about a millisecond on a good network), but everyone sees the same entries, and it survives deploys. This is what most people mean by "the cache", and most of this chapter assumes it.
  • The database's own buffer pool. Inside the database, the pages you read last are kept in RAM (the buffer pool from chapter 6; Postgres calls the equivalent shared_buffers), and underneath that the operating system's page cache from systems chapter 9 does the same for files. You get these for free, they are always consistent with the data because the database maintains them, and they are the reason a repeated query is usually faster than the first one.

The rule of thumb is to cache as close to the user as correctness allows. Static assets belong at the CDN and in the browser. Per-user data that changes constantly probably belongs nowhere but the database. Most of the interesting engineering lives in the shared cache layer, because that is where application data meets the database.

Patterns: who talks to whom

Four questions define a caching pattern. On a read miss, who fetches from the database? On a write, who updates the cache? Is the write to the database done before the reply, or later? And does anything refresh entries on its own? The standard answers have names.

Cache-aside and read-through

Cache-aside (also called look-aside or lazy loading) is the default pattern, and what people usually mean when they say "we use Redis as a cache". The application code does it all:

  1. Look in the cache for the key. If found, return it. That is a hit.
  2. On a miss, query the database.
  3. Store the result in the cache, with a TTL (time to live: the entry expires and disappears after that many seconds).
  4. Return the result.

Its virtues are simplicity and resilience: if the cache is down, the application can still read from the database (slowly). Only data that is actually requested gets cached. Its weakness is that every caller repeats the same few lines and can get them subtly wrong, and the first request for each key is always slow.

Read-through moves that logic into the cache layer. The application calls cache.get(key); on a miss the cache itself calls a loader function you registered and stores the result. The behaviour is the same, but the miss logic lives in one place, and the cache can do clever things there, such as making sure only one load per key is in flight at a time (we will want that shortly). In-process libraries such as Caffeine in Java offer it; CDNs behave this way for web pages, because the CDN fetches from your origin on a miss.

Write-through, write-behind and refresh-ahead

Write-through: every write goes to the cache and, immediately and synchronously, to the database. The reply is sent only when both have it. The cache is therefore never behind the database (for writes that come through this path), and a cache crash loses nothing. The cost is that each write pays for two writes, and you fill the cache with values that may never be read.

Write-behind (or write-back) acknowledges as soon as the cache has the write, and flushes to the database later, often in batches. Writes become very fast, and many updates to the same key can collapse into one database write. But the cache is now the only copy of acknowledged data until the flush. This is the same bargain as the page cache in systems chapter 9: "written" does not mean "saved". Use it only where losing the last few seconds of data is acceptable (counters, view counts, telemetry), or where the cache itself is replicated and durable. For a payment, never.

Refresh-ahead (or background refresh) is not about writes at all. The cache reloads popular entries before they expire, so readers never see a miss for them. It trades a little wasted work (refreshing something nobody asks for again) for a smooth latency. It is one of the defences against stampedes, below.

Do not write to the cache and the database "at the same time"

Beginners sometimes update the database and then the cache from application code and call it write-through. It is not. A real write-through is one component doing both in order. If your code does two independent writes, a crash between them leaves them disagreeing, and two concurrent writers can leave them disagreeing in opposite orders (see the next section). This is the dual-write problem, and we will fix it properly in chapter 19 by having the database's own log drive the cache.

Invalidation: the hard part

The moment you have a copy, you have a question: when the original changes, what happens to the copy? Invalidation is the answer, and it comes in a few strengths.

Expire it (TTL)

The simplest approach: every entry gets a time to live, and when it runs out the entry is gone. You do nothing on writes. The maximum staleness is bounded by the TTL, and a bug in your invalidation logic can only hurt for that long. For many uses (a profile page, a product description) "up to 60 seconds stale" is perfectly acceptable. TTLs are also your safety net under every cleverer scheme: if invalidation messages get lost, the TTL eventually repairs it. The price of a short TTL is a lower hit ratio, and many entries expiring means many misses, which leads to the stampede section below.

Delete on write, or update on write?

If the application knows a value changed, it can tell the cache. Two ways:

  • Update on write: after the database write, set the cache to the new value.
  • Delete on write (invalidate): after the database write, delete the key and let the next reader reload it.

Delete is almost always the better choice, for two reasons. It is idempotent: deleting twice is the same as deleting once, so retries are harmless. And it avoids a race between two writers. Suppose writers W1 and W2 both update the same row, W1 first. Their database writes happen in order 1, 2. But if the network lets W2's cache set arrive before W1's, the cache ends up holding W1's value, permanently (until the TTL), while the database holds W2's. With deletes, whichever order they arrive in, the key is gone and the next reader loads the truth.

This is rare, because the reader's window (between reading the database and setting the cache) is only a few milliseconds wide. But "rare" at 50,000 requests a second means "daily", and the damage lasts as long as the TTL. Three fixes appear in practice:

  • Short TTLs to bound the damage. Cheap and always worth having.
  • Delayed double delete: delete once after the write, and again a moment later (longer than a typical read-fill takes). It shrinks the window, but it is a heuristic, not a guarantee.
  • Leases, which close the window properly. They come next.

Leases: the fix from Facebook's memcache paper

In "Scaling Memcache at Facebook" (Nishtala et al., NSDI 2013; the story has its own page in Case 3), the memcache servers hand out a lease, a token tied to a key, whenever a client misses. The client that gets the lease is the one allowed to fill the key, and it must present the token when it does. If a delete for that key arrives in the meantime, the server invalidates the token, so the late set is rejected. This closes exactly the race above. The same mechanism also tames the herd of clients that all miss at once: the paper has the server hand out a lease only occasionally (at most once in a short interval per key), and clients that miss without getting one are told to wait briefly and retry, by which time the first client has usually filled the key.

The paper describes more than this (regions, a pool for rarely-read keys, a way to serve a slightly stale value while a key is being refilled), and it is worth reading in full. The invalidations in that system are driven by the database's commit log rather than by application code, so that no code path can forget to invalidate; we meet that technique, change data capture, in chapter 19.

Versioned keys

There is a way to avoid invalidation entirely: never change an entry, make a new one. Put a version in the key. Instead of user:42, the key is user:42:v17, where 17 is a version number stored in the database row (or in a tiny, cheap "current version" lookup). When the row changes, its version goes up, readers ask for the new key, and the old entries simply stop being requested and age out through eviction. There is no stale entry to find and delete. This is the same trick as the hashed file names for browser caches (app.3f9a1c.js). The cost is that you must know the current version before you can build the key, which is itself a lookup that cannot be stale.

Analogy: the desk copy and the shelf edition

You photocopy a page from the reference book and keep it on your desk. Someone later issues a corrected edition. Your copy has a "photocopied on" date (that is a TTL: after a week you throw it away and fetch a fresh one). Or the librarian rings you whenever a page changes (that is invalidation: perfect, unless the phone call gets lost). Or you tag every copy with its edition number, and always check the newest edition number first (versioned keys).

Where it breaks down: in a library, the corrected edition arrives rarely and everyone knows it. A hot database row can change many times a second, and the "phone call" can overtake, or be overtaken by, the copy being made, which is the race above.

Eviction: when the cache is full

A cache is smaller than the data behind it, on purpose. When it fills up, adding a new entry means evicting an old one. Which one? The policy is a bet about the future.

  • LRU (least recently used): throw out the entry that was touched longest ago. The bet: recent use predicts near-future use. The usual default.
  • LFU (least frequently used): throw out the entry used the fewest times. The bet: popular things stay popular. It resists one-off scans better but is slow to forget something that used to be popular.
  • TTL-based: prefer to evict entries that are closest to expiring anyway, which costs the least freshness.
  • Random, or FIFO: surprisingly decent and nearly free to implement.

Real systems add refinements. Redis, for instance, lets you set a memory limit with maxmemory and pick an eviction policy with maxmemory-policy. Its choices include noeviction (refuse writes when full), allkeys-lru, allkeys-lfu, allkeys-random, and "volatile" variants (volatile-lru, volatile-lfu, volatile-random, volatile-ttl) that only evict keys which have a TTL set. Redis's LRU is approximate: it samples a few keys and evicts the best candidate among them, rather than tracking a perfect ordering for every key. Memcached evicts roughly least-recently-used items as well. A cache with noeviction or a forgotten memory limit is a cache that eventually runs out of memory and falls over, so always set one.

LRU has a well-known weakness. A single large scan (a report, a crawler, a cache warm-up script) touches thousands of keys once each, and every one of them is "more recent" than your genuinely hot keys, which get pushed out. A short experiment shows it:

from collections import OrderedDict

class LRU:
    def __init__(self, capacity):
        self.cap, self.d = capacity, OrderedDict()
        self.hits = self.misses = 0
    def get(self, k):
        if k in self.d:
            self.d.move_to_end(k)          # most recently used goes to the back
            self.hits += 1
        else:
            self.misses += 1
            self.d[k] = True
            if len(self.d) > self.cap:
                self.d.popitem(last=False) # evict the least recently used (front)

hot = list(range(50))                      # 50 popular keys, capacity 100
c = LRU(100)
for _ in range(20):
    for k in hot: c.get(k)
print(f"hot keys only : hit ratio {c.hits/(c.hits+c.misses):.2f}")

c = LRU(100)
for _ in range(20):
    for k in hot: c.get(k)
c.hits = c.misses = 0
for round_ in range(20):
    for k in hot: c.get(k)
    for k in range(10_000 + round_*200, 10_000 + round_*200 + 200):   # a one-off scan of 200 cold keys
        c.get(k)
print(f"hot + scans   : hit ratio {c.hits/(c.hits+c.misses):.2f}   (the scans flushed the hot keys)")
hot keys only : hit ratio 0.95
hot + scans   : hit ratio 0.01   (the scans flushed the hot keys)

(The 0.95 is because the first pass, 50 cold misses out of 1,000 reads, has to fill the cache.) Each scan of 200 keys is larger than the 100-entry cache, so the hot keys are always pushed out before they are asked for again. Policies such as LFU, or LRU variants that keep new entries on probation before admitting them to the main list, exist exactly to survive this.

Stampedes

Now the failure mode that deserves the most respect. A very popular key expires. In the next few milliseconds, hundreds of requests arrive, every one of them finds the cache empty, and every one of them goes to the database to rebuild the same value. This is a cache stampede, also called a thundering herd or dogpile. The database, sized for a 99% hit ratio, suddenly receives the full load for that key, and rebuilds are typically the slow, expensive queries (that is why you cached them). The extra load makes the rebuilds slower, which keeps the key empty longer, which brings more requests that all miss. It can feed itself.

Analogy: the shop that runs out of a popular item

A hundred customers walk in at the same moment and each asks the clerk to fetch the same sold-out item from the warehouse. A hundred separate trips, all for the same box, while the warehouse door jams. The sensible clerk sends one person, tells everyone else "it will be here in a minute", and hands out the box to all of them when it arrives.

Where it breaks down: customers in a shop can see each other and queue sensibly. Application servers cannot, so you have to build the "tell everyone to wait" step explicitly.

Here is the effect in one runnable program. A cache-aside wrapper with a TTL, a pretend database that takes 50 ms per call and counts how often it is called, and 50 threads that all ask for the same expired key at the same instant. The single_flight flag turns on the fix we describe next: the first thread to miss becomes the "leader" and does the load; everyone else waits for its result.

import random, threading, time

class Database:
    """Pretend database: every call costs 50 ms and we count the calls."""
    def __init__(self):
        self.calls = 0
        self.lock = threading.Lock()
    def read(self, key):
        with self.lock:
            self.calls += 1
        time.sleep(0.05)
        return f"value-of-{key}"

class Cache:
    """Cache-aside with a TTL. Optional single-flight."""
    def __init__(self, db, ttl, single_flight=False):
        self.db, self.ttl, self.single_flight = db, ttl, single_flight
        self.data = {}                  # key -> (value, expires_at)
        self.hits = self.misses = 0
        self.guard = threading.Lock()   # protects data and the in-flight table
        self.inflight = {}              # key -> threading.Event (single-flight)

    def _fresh(self, key):
        entry = self.data.get(key)
        if entry and entry[1] > time.monotonic():
            return entry[0]
        return None

    def get(self, key):
        with self.guard:
            value = self._fresh(key)
            if value is not None:
                self.hits += 1
                return value
            self.misses += 1
            if self.single_flight and key in self.inflight:
                waiter = self.inflight[key]       # someone is already fetching
            else:
                waiter = None
                if self.single_flight:
                    self.inflight[key] = threading.Event()
        if waiter:                                # follower: wait, then read the result
            waiter.wait()
            with self.guard:
                return self.data[key][0]
        try:
            value = self.db.read(key)             # leader: the only one that hits the DB
        except Exception:
            if self.single_flight:                # never leave followers waiting forever
                with self.guard:
                    self.inflight.pop(key).set()
            raise
        with self.guard:
            self.data[key] = (value, time.monotonic() + self.ttl)
            if self.single_flight:
                self.inflight.pop(key).set()
        return value

# --- Part 1: hit ratio on a skewed workload (no threads) ---
random.seed(1)
db = Database(); db.read = lambda k: f"v{k}"          # instant DB for this part
cache = Cache(db, ttl=60)
keys = [int(random.paretovariate(1.2)) % 200 for _ in range(10_000)]
for k in keys: cache.get(k)
h = cache.hits / (cache.hits + cache.misses)
print(f"Part 1: hits={cache.hits} misses={cache.misses} hit ratio={h:.3f}")
t_hit, t_miss = 0.2, 5.0       # ms
print(f"        average latency = {h*t_hit + (1-h)*t_miss:.3f} ms  (hit 0.2 ms, miss 5 ms)")

# --- Part 2/3: stampede on one expired key ---
def stampede(single_flight, clients=50):
    db = Database()
    cache = Cache(db, ttl=0.2, single_flight=single_flight)
    cache.get("hot")                      # warm the cache (1 DB call)
    db.calls = 0
    time.sleep(0.25)                      # let the TTL expire
    barrier = threading.Barrier(clients)
    def client():
        barrier.wait()                    # everyone arrives at the same instant
        cache.get("hot")
    ts = [threading.Thread(target=client) for _ in range(clients)]
    t0 = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    return db.calls, (time.perf_counter() - t0) * 1000

for sf in (False, True):
    calls, ms = stampede(sf)
    print(f"Part {3 if sf else 2}: single_flight={sf!s:5}  50 clients -> {calls} DB call(s), all done in about {ms:.0f} ms")

        average latency = 0.251 ms  (hit 0.2 ms, miss 5 ms)
Part 2: single_flight=False  50 clients -> 50 DB call(s), all done in about 56 ms

Read the numbers. Part 1: a skewed workload (a few keys are very popular, as is true of nearly every real workload) reaches a 98.9% hit ratio, and the formula from the start of the chapter predicts the average latency: 0.989 × 0.2 + 0.011 × 5 = 0.251 ms. Parts 2 and 3: 50 simultaneous requests for an expired key cause 50 database calls without protection and exactly one with it. Notice that the clients finish in about the same time in both runs. The fix cost no extra latency; it only stopped 49 redundant queries. (Here the pretend database is happy to run 50 calls at once. A real one with limited capacity would queue them, and the 50 requests would wait much longer than 50 ms. The widget below models that.)

The fixes

  1. Request coalescing (single-flight). As in the code above: for each key, only one rebuild is in flight; others wait for its result. Go's singleflight package is a well-known implementation of the same idea. It works within one process; across a fleet, you either accept one rebuild per app instance, or use...
  2. Locks (or leases). Take a short-lived lock in the shared cache before rebuilding (for example SET lock:k token NX EX 10 in Redis); whoever gets it rebuilds, and the others wait briefly or serve something stale. The lock must expire on its own, or a crashed rebuilder blocks everyone. This is the cross-process form of single-flight, and what Facebook's leases generalise.
  3. Jittered TTLs. If you fill a thousand keys at the same time with a 10-minute TTL, they all expire at the same time. Add random jitter (for example TTL × a random factor between 0.8 and 1.2) so the expiries spread out. This cures the "everything expires together" case, such as after a deploy, a restart, or a bulk load. It does not help a single hot key.
  4. Probabilistic early refresh. Instead of waiting for expiry, let each request flip a weighted coin that becomes more likely to land "refresh now" as the entry nears its expiry. One request, chosen at random long before the deadline, rebuilds in the background while everyone else keeps getting the cached value. A published algorithm called XFetch (Vattani et al., VLDB 2015) recomputes when now − delta × beta × ln(rand()) ≥ expiry, where delta is how long a rebuild takes. No coordination is needed, and the more expensive the rebuild, the earlier it kicks in.
  5. Serve stale while revalidating. Keep serving the expired value while exactly one request refreshes it. The user gets a slightly old but instant answer, and nobody waits. HTTP has this as Cache-Control: stale-while-revalidate (RFC 5861), and CDNs use it. It is often the best user experience, as long as the content tolerates a few seconds of staleness.

Notice the difference in what each one protects. Single-flight and locks protect the database, but the waiting requests still wait. Serve-stale and early refresh protect the users as well, because nobody waits. Jitter protects against synchronised expiry across many keys. Production systems combine them.

Stampedes are a retry storm's cousin

If the database is struggling, rebuilds time out, the clients retry, and the retries land on a database that was already drowning. That feedback loop, and why systems can stay broken even after the original trigger is gone, is the subject of networking Case 8: retry storms and metastable failures. A cache with no stampede protection is a very good way to start one.

What the model leaves out

Real stampedes are worse than the simulation. In reality a drowning database makes queries time out, clients retry, and the rebuild may never finish. Here every rebuild eventually completes. Caches also have their own queueing and network limits. Treat the chart as a picture of why the protections help, not a forecast of how bad it gets.

Hot keys

A related problem needs no expiry at all. In a sharded cache (the keys are spread over several cache nodes by hashing, as in networking chapter 19), one key can be so popular that the single node holding it is overloaded while its neighbours idle. A celebrity's profile, a viral post, a flash-sale item. Adding nodes does not help, because the key still lives on exactly one of them.

The remedy is to stop having a single copy of that key:

  • Cache it locally. Put it in an in-process cache with a very short TTL (a second is often enough) in every app instance. The shared cache then sees at most one request per instance per second, instead of one per user request.
  • Replicate it under several names. Write the value as post:99#0, post:99#1 ... post:99#7; readers pick one suffix at random. Hashing places the copies on different nodes, so the load is spread over up to eight of them. Writers must update or delete every copy.
  • Push it to the CDN or the browser if it is the same for everyone.

You usually discover hot keys by measuring: most caches can report the busiest keys. Hot-key handling is a form of load shedding on a single partition, and you will meet the same problem in a different form (hot partitions) when we shard the database in chapter 16.

Negative caching

A miss can be expensive for a different reason: the key does not exist. A request for /user/99999999 misses the cache, misses the database (a full lookup that finds nothing), and caches nothing, because there is nothing to cache. So the next identical request repeats all the work. An attacker, or just a buggy client, can send millions of requests for keys that do not exist, each one punching straight through to the database.

Negative caching stores the fact of absence: cache a special "not found" marker for that key, with a short TTL (a few seconds to a minute). The short TTL matters, because the thing might be created a moment later and you do not want to claim for long that it does not exist. DNS does this as a matter of course (networking chapter 9): an NXDOMAIN answer is cached for a time given by the zone. When the space of possible missing keys is huge, a Bloom filter in front (the structure from chapter 5, which can say "definitely not present") stops most nonexistent lookups before they ever reach the database.

Consistency: a cache is eventually consistent by nature

Step back. A cache and its database are two stores holding overlapping data, updated by separate messages that can be delayed, reordered or lost. That is the same situation as a leader and its followers in networking chapter 18, and the same conclusion follows: you cannot have both "always fresh" and "fast, independent of the database", only a choice of how stale and how often. A cache gives you eventual consistency at best, with the TTL as the upper bound on "eventually". Everything in the invalidation section is about shrinking the window, never closing it for free.

Practical consequences:

  • Decide per piece of data how stale is acceptable. A product description: minutes. A like count: seconds. An account balance used to authorise a payment: do not cache it at all, or read from the authoritative store.
  • A user who writes and then reads may see their own old data from the cache. The same read-your-writes problem as with replication lag has the same fixes: after a user's write, read around the cache for them, or delete the key before replying.
  • Never treat the cache as the source of truth unless you have designed it as a database (replicated, persisted, with a defined durability). A pure cache can be emptied at any moment, and the system must still be correct.

When the cache goes down

A design that is merely slow without its cache is a design you can live with. A design that is dead without it is one outage away from a disaster.

A cold cache (empty after a restart, a failover, a deploy that flushes the in-process cache, or a new region that has never served traffic) means a 0% hit ratio. Everything the cache was absorbing now lands on the database, which was sized assuming the cache works. The database slows down, rebuilds time out, requests pile up, and the cache cannot refill because the database is too slow to answer: the cache is empty because the database is down, and the database is down because the cache is empty. This is the shape of a metastable failure again.

Defences, from cheapest to most thorough:

  • All the stampede protections above, because a cold start is a stampede on every key at once.
  • Shed load at the front: reject or queue the excess instead of letting it all through, so the database sees a survivable rate while the cache warms (see systems chapter 14 on bounded queues and backpressure).
  • Warm before serving: preload the hottest keys, or bring a new cache node into rotation gradually, sending it a small share of traffic first.
  • Don't lose it all at once. Spread keys over many cache nodes with consistent hashing, so that losing one node empties only about 1/N of the keys; and consider replicas or persistence for caches whose loss is expensive.
  • Know the number. Calculate the database load at a 0% hit ratio and compare it to the capacity. If it is much larger, then your system has a hidden dependency, and you should decide on purpose how it degrades.

Distributed systems connection

A cache is a replica with a different contract: it can be wrong, it can vanish, and it is allowed to be incomplete. That makes it a clean place to learn the trade-offs of replication (networking chapter 18, next deepened in chapter 15): staleness windows, read-your-writes, and what an invalidation message that arrives late does. The lease idea reappears as a fencing token in the next chapter. And the fix for the dual-write problem, driving caches and indexes from the database's log, is the theme of chapter 19 and Lab 6.

Key takeaways

  • Average latency = h × thit + (1 − h) × tmiss. What the database feels is the miss ratio: 99% to 99.9% is a tenfold drop in its load.
  • Cache-aside (app fills the cache) is the default; read-through hides the miss logic inside the cache; write-through keeps both in step at the price of slower writes; write-behind is fast but can lose acknowledged writes; refresh-ahead keeps hot keys from missing.
  • Prefer delete-on-write to update-on-write, always keep a TTL as a safety net, and remember the race where a slow reader sets a stale value after a delete. Leases or versioned keys close it.
  • Set a memory limit and an eviction policy. LRU is the usual default and a big scan can flush it.
  • Stampedes come from many requests rebuilding one expired key, or many keys expiring together. Fix with single-flight or locks, jittered TTLs, early refresh and serve-stale; the last two also spare the users from waiting.
  • Hot keys need copies (local caches, suffixed replicas). Missing keys need negative caching with a short TTL.
  • A cache is eventually consistent at best. Design so the system stays correct if the cache is empty, and know how much load the database gets when it is.

Check your understanding

A cache hit costs 1 ms and a miss costs 100 ms in total. The hit ratio rises from 99% to 99.9%. What happens to the load on the database, and roughly to the average latency?

  1. Almost nothing changes, because 0.9 percentage points is tiny
  2. The database sees one tenth as many queries, and the average latency drops from about 2.0 ms to about 1.1 ms
  3. The database sees half as many queries and latency halves
  4. Latency doubles, because the cache must hold more data
Misses fall from 1% to 0.1% of requests: a factor of ten in database load. Latency is 0.99×1 + 0.01×100 = 1.99 ms before and 0.999×1 + 0.001×100 = 1.099 ms after.

Why is "delete the key after the database write" usually safer than "set the key to the new value after the database write"?

  1. Deletes are faster than sets on every cache
  2. Setting a value is not allowed in cache-aside
  3. A delete removes the TTL, which is a risk
  4. Deletes are idempotent and order-insensitive: two concurrent writers can't leave the older value in the cache, which a reordered pair of sets can
If the sets arrive out of order, the cache keeps the older value until the TTL. After a delete, the next read reloads whatever the database holds. (Deletes still have the slow-reader race, which leases fix.)

A reader misses the cache and reads version 1 from the database. A writer then updates the database to version 2 and deletes the cache key. Then the reader sets the cache to version 1. What is the state afterwards, and what closes the hole?

  1. The cache holds stale version 1 until the TTL; a lease (the delete voids the reader's token) or a versioned key prevents it
  2. The cache is empty, because the delete wins
  3. The cache holds version 2, because the database is always consulted last
  4. Nothing is wrong: the reader's value is simply newer
The delete ran before the set, so it found nothing to remove. A lease makes the reader's later set fail; a versioned key makes the set land under the old key, which nobody will ask for.

You fill 5,000 keys at 09:00 with an identical 30-minute TTL. At 09:30 the database is overwhelmed. Which mitigation targets this specific cause?

  1. Single-flight coalescing alone, because it removes all duplicate loads
  2. A larger cache, so entries never expire
  3. Jittered TTLs, so the 5,000 expiries spread over a window instead of landing together
  4. Write-behind caching
The trouble is synchronised expiry of many distinct keys, which single-flight (one rebuild per key) cannot spread out. Randomising the TTL spreads the rebuilds in time. Jitter would not help a single hot key.

Single-flight makes 50 simultaneous requests for an expired key cause one database query. What is its remaining downside compared to serve-stale?

  1. It makes the database slower
  2. The 49 followers still wait for the rebuild to finish, whereas serve-stale answers them immediately from the old value
  3. It cannot work across threads
  4. It makes the cache inconsistent with the database forever
Single-flight protects the database but not the latency of the waiters. Serve-stale (stale-while-revalidate) trades a little freshness for no waiting at all.

A service that relies on a 99% hit ratio has its Redis restarted during peak traffic. What is the best description of what happens next, and the best first defence?

  1. Nothing: the cache refills instantly and users never notice
  2. The database load drops, because Redis is no longer in the way
  3. Only 1% of requests are affected
  4. The hit ratio falls to roughly 0%, so the database suddenly receives up to 100 times its usual load; shed load and use stampede protection while the cache warms
A cold cache sends every request to the database. If that exceeds capacity, rebuilds slow and the cache cannot refill, a self-sustaining failure. Shedding load, coalescing and gradual warm-up keep the database alive long enough to recover.

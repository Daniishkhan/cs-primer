Crash Recovery

A database is promised to be durable: if it said "committed", the data is there after the power cut. But it also keeps recent changes in memory for speed, and it may have written half of a transaction to disk when it died. This chapter explains the one idea that squares all of that: write the intention to a log first, and repair everything from the log on restart.

Why this matters

Crashes are not rare events at scale: processes get killed, machines lose power, disks fill up, and cloud hosts are replaced. The write-ahead log is why a database can tell you "committed" and mean it, and the same log then feeds replication, backups and change data capture. Once you see the log as the real source of truth, with the tables as a cache of it, a great deal of database design makes sense.

Recap: written is not saved

In systems chapter 9 we saw that write() only hands data to the operating system's page cache. It reaches the disk later, and survives a power cut only after fsync returns. A database lives right on that fault line: it must acknowledge a commit only when the data is safe, but it cannot afford to fsync every scattered page it modified.

There is a second problem. A database page is typically 8 or 16 KiB (chapter 6), and one transaction may change many of them: two account balances, an index entry, a counter. If the machine dies after some of those pages have reached the disk and before the rest, the database on disk is inconsistent. "Half a transfer" happened. We need atomicity and durability (the A and D of ACID) in the face of crashes.

The write-ahead log rule

The solution is a write-ahead log (WAL), sometimes called the redo log or journal: a sequential, append-only file recording every change before the change is applied to the data pages. The rule has two halves:

  1. Log first. Before a modified page may be written to the data file, the log record describing the modification must already be durable on disk.
  2. Commit means the log is durable. A transaction counts as committed once its COMMIT record, and everything before it in the log, is safely on disk. The data pages are allowed to lag behind.

Why is this faster than just writing the data pages? The log is one sequential append, which both SSDs and spinning disks do quickly. The data pages are scattered across the file; flushing all of them at every commit would be many slow random writes. With a WAL, commit costs one small sequential write and one fsync, and the random page writes happen later, in the background, batched. Under load, many concurrent commits share a single log fsync: that is the group commit we saw in systems chapter 9.

Analogy: the bank's journal

A bank clerk handling a transfer does not first erase and rewrite the ledger pages. They first write a line in the day journal: "move 30 from Alice to Bob, entry #1043", and initial it. Only once that line exists do they update the ledger. If the lights go out half way, the next morning someone reads the journal and finishes (or cancels) every entry. The journal is the truth; the ledger is a convenient summary.

Where it breaks down: a clerk can decide by judgement what a half-finished entry means. A database must use a precise algorithm, and each log entry has to be safe to apply more than once, because the crash might happen again during recovery.

Redo and undo, and the buffer policy that needs both

Dirty pages live in the buffer pool and get written out when convenient. Two policy choices decide what recovery has to do:

The easy choiceThe fast choice
At commit timeForce: write all the transaction's dirty pages to disk before committing. Then committed work is always already on disk, so nothing needs redoing. But commits are slow, with many random writes.No-force: commit needs only the log. Committed changes may exist only in memory, so after a crash they must be redone from the log.
When memory is shortNo-steal: never write a page that holds uncommitted changes. Then the disk never has uncommitted data, so nothing needs undoing. But a big transaction pins all its pages in memory.Steal: the buffer pool may evict any dirty page, even one with uncommitted changes. Then the disk may hold uncommitted data, which must be undone after a crash.

Real databases choose steal, no-force: the fast choice on both rows. It gives the best performance and makes the recovery job twice as big. After a crash the log has to tell the database both what to redo (committed changes that never reached the data file) and what to undo (uncommitted changes that did). So log records for updates carry enough to do both: where the change was, the new value (for redo) and the old value (for undo). The rule is easy to remember: redo the winners, undo the losers.

Here it is in about thirty lines of Python. The "disk" and the log survive the crash; the cache does not. T1 commits but its pages are never flushed (no-force). T2 never commits but one of its pages is flushed early (steal).

# A toy write-ahead log. The log and the data pages survive the crash; memory does not.
log = []                                   # every append is assumed to be fsynced
disk = {"A": 100, "B": 100, "C": 50}       # the data file (pages)
cache = dict(disk)                         # the buffer pool (RAM)

def update(txn, key, new):
    log.append(("UPDATE", txn, key, cache[key], new))    # 1. log first: old AND new value
    cache[key] = new                                     # 2. then change the page in memory

def commit(txn):
    log.append(("COMMIT", txn))            # durable log record = committed

update("T1", "A", 70); update("T1", "B", 130); commit("T1")
update("T2", "C", 0)                       # T2 never commits
disk["C"] = cache["C"]                     # STEAL: T2's dirty page is evicted to disk early
# NO-FORCE: T1's pages (A, B) were not written to the data file at commit
print("before recovery, disk is:", disk)   # crash! `cache` is gone

def recover():
    winners = {r[1] for r in log if r[0] == "COMMIT"}
    for r in log:                                        # REDO: repeat history, in log order
        if r[0] == "UPDATE":
            disk[r[2]] = r[4]
    for r in reversed(log):                              # UNDO: roll back losers, newest first
        if r[0] == "UPDATE" and r[1] not in winners:
            disk[r[2]] = r[3]
    return winners

print("committed (winners):", recover())
print("after recovery, disk is:", disk)
before recovery, disk is: {'A': 100, 'B': 100, 'C': 0}
committed (winners): {'T1'}
after recovery, disk is: {'A': 70, 'B': 130, 'C': 50}

Not every database undoes the same way

The redo-and-undo picture is the general case, and InnoDB (MySQL) has both a redo log and undo logs. PostgreSQL gets away with a redo-only WAL, because its multi-version storage (chapter 12) leaves old row versions in the table: rows written by a transaction that never committed are simply invisible, so there is nothing to physically undo (they are cleaned up later by vacuum). SQLite's WAL mode never lets uncommitted changes into the main file at all. Same principle, different bookkeeping.

Sequence numbers and checkpoints

To know what to redo, recovery must tell which log records a page has already absorbed. Every log record gets a log sequence number (LSN), a number that grows with each record (in Postgres it is a position in the WAL byte stream). Every data page stores the LSN of the last log record that changed it, its page LSN. During redo, for each record that touches a page:

  • if page LSN ≥ record LSN, the page already has this change (it was written to disk after the change): skip it;
  • if page LSN < record LSN, the change is missing: apply it, and set the page LSN.

That comparison makes redo idempotent: applying it twice gives the same result as once, so if the machine crashes during recovery you can simply start recovery again. (The same idea of idempotent operations returns in distributed systems with retries.)

Without a limit, recovery would replay the log from the dawn of time. A checkpoint bounds it: periodically the database flushes dirty pages to the data file and writes a CHECKPOINT record saying "everything older than this is on disk". Recovery starts from the last checkpoint. (Real checkpoints are "fuzzy": they spread the page writes over a time window and record what was dirty and what was running, rather than freezing the system.)

The knob is a trade-off. Checkpoint often and recovery is quick, but you do more page writes and spend more I/O during normal operation. Checkpoint rarely and the opposite. Postgres, for example, triggers checkpoints on a timer (five minutes by default) or when enough WAL has accumulated. Once the log before a checkpoint is no longer needed for recovery, it can be recycled, archived or, as we'll see, shipped elsewhere.

ARIES in one page

Most textbook and many real systems follow a recovery method called ARIES (Mohan et al., IBM, 1992). It has three phases, run in this order after a crash:

  1. Analysis. Read the log from the last checkpoint to the end. Work out which transactions were running at the crash (the losers, with no COMMIT record) and which pages might have been dirty.
  2. Redo. Scan forward and re-apply every logged change, winners and losers, whose page LSN says it is missing. This "repeats history" and brings the database to exactly its state at the moment of the crash.
  3. Undo. Walk the losers' records backwards and reverse each one. Every undo is itself written to the log as a compensation log record (CLR), so a crash during recovery never undoes the same change twice.

The name is worth knowing and the details are not required for this course. What matters: recovery is deterministic, repeatable, and driven by the log. The stepper below walks through exactly this, on three tiny pages.

Step through

A crash mid-transaction, and the recovery

  1. Normal running. Transaction T1 transfers 30: it updates page P1 (A: 100 to 70) and page P2 (B: 100 to 130). Each change appends a log record with a log sequence number (LSN 1, LSN 2) and stamps that LSN on the changed page in the buffer pool (its pageLSN). The pages on disk still hold the old values.
  2. T1 commits. The COMMIT record (LSN 3) is appended and the log is forced to disk. Only now is T1 told "committed". The data pages on disk are still old: the database did not force them out (no-force). Durability rests entirely on the log.
  3. Checkpoint. The database writes the dirty pages (P1, P2) to the data file and appends a CHECKPOINT record (LSN 4). Simplified: real checkpoints are "fuzzy" and let work continue while they run. Recovery will never need to look before this record.
  4. More work. T2 updates page P3 (C: 50 to 0), logged as LSN 5; it has not committed. T3 updates P1 again (A: 70 to 60, LSN 6) and commits (LSN 7), so the log is forced through LSN 7. P1 and P3 are dirty in memory.
  5. A page is stolen. The buffer pool needs room and evicts dirty page P3 to disk before T2 has committed (steal). This is allowed because the WAL rule holds: LSN 5 is already durable. But now the data file contains an uncommitted change (C = 0).
  6. Crash. The power fails. Everything in memory is gone, including the dirty P1 (A = 60). On disk: the log through LSN 7, and data pages that are out of step with it. P1 lacks T3's change, and P3 contains T2's.
  7. Recovery, phase 1: analysis. Read the log from the last checkpoint (LSN 4). T3 has a COMMIT record: a winner. T2 has updates but no COMMIT: a loser. T1 committed before the checkpoint, and its pages were flushed by it.
  8. Phase 2: redo. Repeat history from the checkpoint. LSN 5: P3's pageLSN is already 5, so skip it. LSN 6: P1's pageLSN is 1, less than 6, so re-apply the change: A = 60. Comparing the pageLSN to the record's LSN is what makes redo safe to repeat. (Recovery works in memory first; it is drawn on disk here for simplicity.)
  9. Phase 3: undo. Roll back the losers by walking their records backwards. T2's LSN 5 is undone: C goes back to 50. The undo is itself logged as a compensation log record (LSN 8), so a crash during recovery does not undo it twice.
  10. Recovered. A = 60 (T1 and T3 committed), B = 130, C = 50 (T2 vanished). Every committed change survived and every uncommitted one disappeared, although the data pages and the crash left things out of step. Recovery time depended on the log since the checkpoint, not on the size of the database.

Commit means the log record is durable

Put the pieces together: when you issue COMMIT, the database appends a commit record to the log, calls fsync on the log, and only then returns success. That fsync is the cost of durability, which is why systems offer settings that trade it away: Postgres's synchronous_commit = off and InnoDB's innodb_flush_log_at_trx_commit can acknowledge before the fsync, so a crash may lose the most recent commits (a small window) but, importantly, does not corrupt the database. The default in both is the safe one. Group commit (systems ch. 9) is what makes the safe setting affordable.

Torn pages

One more hazard. A database page is 8 KiB (Postgres) or 16 KiB (InnoDB by default), but disks and file systems only promise to write much smaller units atomically. A crash in the middle of a page write can leave a torn page: half old, half new. A log record that says "change bytes 40 to 48 of this page" cannot repair a page whose other half is garbage. The two main defences:

  • Full-page writes (Postgres). The first time a page is modified after a checkpoint, the WAL records a copy of the entire page, not just the change. Recovery can then rebuild a torn page from the log. This is why WAL volume spikes right after each checkpoint.
  • Doublewrite buffer (InnoDB). Pages are first written to a special area, then to their real place. If a crash tears the real write, the intact copy in the doublewrite area is used to restore it.

Both pay extra writes for safety. Checksums on pages and on log records (as in the systems chapter) let the database notice a torn or corrupt page in the first place.

Backups, replicas and point-in-time recovery

Crash recovery handles "the machine died". It does not handle "the disk is destroyed", "a bug corrupted rows", or "someone ran DROP TABLE on production". Those need other tools, and they are not interchangeable:

Protects againstDoes not protect against
The WAL and crash recoveryPower loss, process crashLost disk, human error
A replica (chapter 15)Loss of a machine; fast failoverHuman error and bugs: DROP TABLE replicates, too
A backupLost machine, corruption, mistakes (back to the backup time)Anything since the last backup
Backup + WAL archiveAll of the above, to a chosen momentLoss of the archive itself

The last row is point-in-time recovery (PITR). Take a periodic base backup (a copy of the data files), and continuously archive the WAL segments the database produces. To recover, restore the base backup and replay the archived WAL, stopping just before the mistake. Because the WAL is a complete history of changes, you can stop at any moment. It is the same mechanism as crash recovery, with the stopping point chosen by you instead of by the end of the log.

Test your restores

A backup you have never restored is a hope, not a backup. Backups fail silently: jobs that produce empty files, retention that deleted what you needed, credentials that expired, a version mismatch discovered only on the worst day. In January 2017 GitLab accidentally deleted a production database directory and found that several of its backup mechanisms were not producing usable backups. Read the case study. Schedule a restore drill, time it, and monitor the backup job like a production service.

The log is more than a recovery tool

Because the WAL is an ordered, durable record of every change, other systems read it as well:

  • Replication. A Postgres replica is kept current by streaming and replaying the leader's WAL, which is the same redo process, running continuously. MySQL replicates through a separate binary log. More in chapter 15 and, for the theory, networking chapter 18.
  • Change data capture. Tools can decode the log into a stream of row-level events and feed search indexes, caches and warehouses without touching the application (chapter 19).
  • The log as the database. Amazon Aurora takes the idea furthest: the database node sends only redo log records to a distributed storage service, which builds the pages itself. See the Aurora case.

The same insight, a log of changes that is the truth and everything else a derived view of it, returns in Kafka and in consensus protocols such as Raft (networking chapter 20).

Try it yourself

Try it yourself: kill a database mid-transaction

This script uses SQLite in WAL mode. A child process commits transaction T1, starts T2, then dies with os._exit (like kill -9: no cleanup, no flush). The parent reopens the database, which is when recovery happens. It works in a throwaway temp directory and removes it afterwards. Python 3 and its built-in sqlite3 are all you need.

import os
import shutil
import sqlite3
import subprocess
import sys
import tempfile

def child(path):
    db = sqlite3.connect(path, isolation_level=None)        # we issue BEGIN/COMMIT ourselves
    db.execute("PRAGMA journal_mode=WAL")
    db.execute("PRAGMA synchronous=FULL")                  # fsync the log at every commit
    db.execute("CREATE TABLE acct (name TEXT PRIMARY KEY, bal INTEGER)")
    db.execute("INSERT INTO acct VALUES ('alice', 100), ('bob', 100)")

    db.execute("BEGIN")                                    # T1: move 30 from alice to bob
    db.execute("UPDATE acct SET bal = bal - 30 WHERE name = 'alice'")
    db.execute("UPDATE acct SET bal = bal + 30 WHERE name = 'bob'")
    db.execute("COMMIT")                                   # durable from here on

    db.execute("BEGIN")                                    # T2: starts, never commits
    db.execute("UPDATE acct SET bal = bal - 50 WHERE name = 'alice'")
    print("child: T2 has run an UPDATE; now crashing with no cleanup", flush=True)
    os._exit(1)                                            # like kill -9: nothing is flushed or closed

if len(sys.argv) > 2 and sys.argv[1] == "child":
    child(sys.argv[2])
else:
    folder = tempfile.mkdtemp()
    path = os.path.join(folder, "bank.db")
    subprocess.run([sys.executable, __file__, "child", path])
    print("files left behind:", sorted(os.listdir(folder)))
    db = sqlite3.connect(path)                             # opening the database runs recovery
    print("after recovery:", db.execute("SELECT * FROM acct ORDER BY name").fetchall())
    db.close()
    shutil.rmtree(folder)
child: T2 has run an UPDATE; now crashing with no cleanup
files left behind: ['bank.db', 'bank.db-shm', 'bank.db-wal']
after recovery: [('alice', 70), ('bob', 130)]

The three files left behind are the database, its WAL, and a shared-memory index. T1's committed transfer is there (70 and 130); T2's uncommitted debit is not. SQLite's WAL is simpler than ARIES (it never needs an undo), but the contract is the same. Experiment: change the child to stop before COMMIT on T1, and check that the transfer disappears entirely. If you have Postgres, pgbench in the toolbox lets you watch the effect of synchronous_commit on throughput.

Distributed systems connection

The WAL is the seed of distributed data. A replica that replays the leader's log reaches the same state, which is state-machine replication. Consensus (Raft, Paxos) is, at its heart, getting a group of machines to agree on one replicated log and make each entry durable on a majority before acknowledging it: the commit rule of this chapter with "fsync on disk" replaced by "durable on a quorum". Change data capture turns a database's log into a stream for the rest of the company. And disaggregated storage like Aurora moves the log to a separate fleet of machines. When you meet a new system, ask: where is its log, and who reads it?

Key takeaways

  • The WAL rule: log the change and make it durable before the changed page may reach the data file. Commit means the commit record is durable in the log.
  • Steal (evict uncommitted pages) and no-force (don't flush at commit) give speed, and so require both undo of uncommitted work and redo of committed work. Redo the winners, undo the losers.
  • Each log record has an LSN and each page stores its page LSN; comparing them makes redo idempotent, so recovery can safely be restarted.
  • Checkpoints flush dirty pages and mark where recovery can start, bounding recovery time at the price of extra writes.
  • ARIES: analysis, redo (repeat history), undo (with compensation records). Postgres is redo-only thanks to MVCC; InnoDB has both redo and undo logs.
  • Torn pages are handled by full-page writes (Postgres) or the doublewrite buffer (InnoDB).
  • Replicas and WAL archives are not backups of your mistakes unless set up as such. PITR = base backup + archived WAL. Test restores.
  • The WAL also feeds replication, CDC and storage layers like Aurora's.

Check your understanding

A database writes a modified data page to disk before the matching log record is durable, then crashes. Why is that a violation of the WAL rule that matters?

  1. Log records are always larger than pages
  2. If the transaction later turns out to be uncommitted, recovery would have no log record to undo the change with, so uncommitted data would be stuck on disk
  3. The page would be written twice
  4. fsync would no longer work
Undo information lives in the log. A change on disk with no log record is a change the database cannot reverse or even know about. Log first, so the log always knows at least as much as the data file.

A transaction commits and the database acknowledges it. Which statement is true under a steal, no-force policy?

  1. All its modified data pages are already in the data file
  2. The commit is only durable after the next checkpoint
  3. Its commit record (and earlier log) is durable, but its data pages may exist only in memory, so recovery may have to redo them
  4. Recovery never needs to look at the log for it
No-force means commit only waits for the log. The data pages are written later. After a crash, redo replays the logged changes that the data file lacks.

During redo, a log record has LSN 120 and the target page's page LSN is 135. What does recovery do?

  1. Skip it: the page already contains this change (and later ones)
  2. Apply it again to be safe
  3. Undo it
  4. Delete the page
A page LSN of 135 means a record at or after 120 already modified the page and the page reached disk with those changes. Skipping when page LSN ≥ record LSN is what makes redo idempotent.

What is the main job of a checkpoint?

  1. To make the database faster for readers
  2. To compress the log
  3. To roll back long transactions
  4. To bound recovery time: dirty pages are flushed so recovery only has to replay the log after the checkpoint
Without checkpoints the log would have to be replayed from the start. Checkpoints trade extra writes during normal operation for shorter recovery.

Someone runs DROP TABLE orders on the primary by mistake. A hot replica exists. Which one helps you get the table back?

  1. Promote the replica: it still has the table
  2. A base backup plus an archive of WAL, replayed to just before the drop (point-in-time recovery)
  3. Crash recovery on the primary
  4. Run checkpoint again
A replica faithfully replays the DROP TABLE too, usually within moments. Replicas protect against hardware loss, not mistakes. PITR can stop the replay just before the drop.

Why does Postgres write a full copy of a page into the WAL the first time it is changed after a checkpoint?

  1. To make replicas faster
  2. To compress the WAL
  3. To protect against torn pages: if a page is half-written in a crash, recovery can rebuild it from the full copy in the log
  4. Because pages are always rewritten after a checkpoint
Disks may not write an 8 KiB page atomically. A log record that describes a small change cannot repair a page whose other half is garbage, so the log carries a complete image. InnoDB's doublewrite buffer solves the same problem differently.

Encoding & Schema Evolution

Data in a program is a web of pointers. Data on a disk or a wire is a flat string of bytes. Everything that stores or sends data has to convert between the two, and then live with the fact that the code that wrote the bytes yesterday is not the code that reads them tomorrow.

Why this matters

Shapes of data change: you add a field, rename one, drop one. In a system with many machines you can never update every program at the same instant, so old and new code must read each other's data for a while. Get the encoding wrong and a routine deploy corrupts records or crashes half your servers. Choosing a format (JSON, Protocol Buffers, Avro) is a long-lived decision, because stored data outlives the code that wrote it.

Objects in memory, bytes on the wire

Inside a running program, data lives as objects, lists and dictionaries linked by memory pointers (systems chapter 3). Pointers only mean something inside one process. To write data to a file, store it in a database, or send it over the network (networking chapter 12 introduced this as serialization), we must convert it into a self-contained sequence of bytes. This conversion is called encoding (also serialisation or marshalling); the reverse is decoding (deserialisation or parsing). The bytes must carry enough information for another program, maybe written in another language years later, to rebuild the data. And the way integers, strings and lists end up as bytes in files is the same problem as bytes in memory (systems chapter 8), just with a longer lifetime.

Every format answers the same few questions: How are numbers written? How is a string's length known? How do you tell fields apart? Is there a schema? Let's walk through the main families.

Language-specific formats and their dangers

Most languages have a built-in way to dump objects: Python's pickle, Java's Serializable, Ruby's Marshal. They are very convenient (one line saves almost any object) but poor for anything that lasts or crosses boundaries:

  • Tied to one language. A pickle can only be read by Python. The moment a second service in another language needs the data, you must start over.
  • Unsafe to read from untrusted sources. To rebuild arbitrary objects, the decoder must be able to instantiate arbitrary classes, which means attacker-chosen bytes can make it run code.
  • Poor versioning. They rarely handle evolving class definitions gracefully, and are often slow and bulky.

Never unpickle data you do not trust

Python's own documentation warns that unpickling can execute arbitrary code. This harmless demonstration shows how: a class tells pickle "to rebuild me, call this function", and pickle.loads calls it.

import pickle

class Evil:
    def __reduce__(self):
        return (print, ('this ran during unpickling',))   # an attacker would pick something worse

data = pickle.dumps(Evil())
pickle.loads(data)          # prints: this ran during unpickling
print(pickle.dumps({'a': 1}))

this ran during unpickling
b'\x80\x05\x95\n\x00\x00\x00\x00\x00\x00\x00}\x94\x8c\x01a\x94K\x01s.'

Rule: use pickle only for your own data in your own process or files you wrote. For anything crossing a trust boundary, use a data-only format like JSON.

Text formats: JSON and CSV

JSON (JavaScript Object Notation) is the lingua franca of web APIs: objects, arrays, strings, numbers, booleans and null, all as readable text. CSV (comma-separated values) is rows of text split on commas. Both are readable by humans and every language can parse them, which is why they dominate. They have real limits.

Number precision

JSON has a single "number" type and does not say how big or precise it is. Many implementations, notably JavaScript, read every number as a 64-bit floating-point double, which can represent integers exactly only up to 253 (9,007,199,254,740,992). Beyond that, neighbouring integers collapse into one. A 64-bit database id such as a tweet id or a Snowflake id can therefore silently change as it passes through a JavaScript client. This is a well-known real-world problem, and the usual fix is to send big ids as strings.

$ python3 -c "import json; print(json.loads('9007199254740993')); print(float(9007199254740993)); print(0.1 + 0.2)"
9007199254740993
9007199254740992.0
0.30000000000000004

$ node -e 'console.log(JSON.parse("9007199254740993")); console.log(JSON.parse("{\"id\":12345678901234567890}").id)'
9007199254740992
12345678901234567000

Python's integers have unlimited size, so it reads the number exactly, but Node's JSON.parse gives back a different number from the one that was sent. Likewise 0.1 + 0.2 is not exactly 0.3 in binary floating point, so never store money as floats. Use integer cents or a decimal type.

Other quirks

  • No binary type. Raw bytes (an image, a hash) must be turned into text first, usually base64, which inflates them by about a third.
  • No schema. Nothing says which fields must exist or what type they have. A typo like "emial" is valid JSON.
  • CSV has no types at all. Everything is text. A reader must guess whether 007 is the number 7 or a code, how to handle commas and quotes inside a value, and whether the first row is a header:
import csv, io
print(list(csv.reader(io.StringIO('1,Asha,007\n'))))
[['1', 'Asha', '007']]

Despite all that, JSON is a fine choice for public APIs and configuration where readability and universality matter more than size or strictness. The issue is when you want compactness, speed, or a firm contract between teams.

Binary formats with schemas

If both sides agree in advance on the structure, the bytes do not have to describe themselves. The result is smaller, faster to parse and type-checked. First a feel for the size difference using only the standard library: the same small record, as JSON and as a fixed binary layout made with Python's struct module.

import json, struct

record = {"id": 42, "name": "Asha", "active": True, "score": 3.5}

as_json = json.dumps(record, separators=(",", ":")).encode()
print(as_json, len(as_json), "bytes")

# fixed layout: uint32 id, uint8 name length, name bytes, uint8 active, float64 score
name = record["name"].encode()
packed = struct.pack(f"<IB{len(name)}sBd", record["id"], len(name), name, record["active"], record["score"])
print(packed.hex(" "), len(packed), "bytes")

# decoding needs the same layout: there are no field names in the bytes
id_, n = struct.unpack_from("<IB", packed)
name2, active, score = struct.unpack_from(f"<{n}sBd", packed, 5)
print(id_, name2.decode(), bool(active), score)
b'{"id":42,"name":"Asha","active":true,"score":3.5}' 49 bytes
2a 00 00 00 04 41 73 68 61 01 00 00 00 00 00 00 0c 40 18 bytes
42 Asha True 3.5

49 bytes became 18, and the bytes are meaningless without the layout string <IB4sBd. That is the schema: kept outside the data. (The < means little-endian, the byte order of most CPUs; I is a 4-byte unsigned integer, B one byte, d an 8-byte float.)

Real schema-based formats add what our hand-made layout lacks: a language for describing the schema, code generation for many languages, and above all rules for changing the schema safely. The three you will meet:

Protocol Buffers and field tags

Protocol Buffers (protobuf, from Google) uses a .proto schema file where every field has a name and a number:

message User {
  int32  id    = 1;
  string name  = 2;
  string email = 3;
}

On the wire, the field name never appears. Each field is written as a field tag (the number, plus a small code for how to read the value), then the value. This is a tag-length-value (TLV) scheme. To make it concrete, here is a simplified TLV encoder we can run (real protobuf packs the tag and type into one byte and uses compact variable-length integers, but the idea is identical):

# A tiny protobuf-like format. Every field is: tag, length, value
def put(tag, value):
    return bytes([tag, len(value)]) + value

def encode(user):
    out = b""
    if "id" in user:    out += put(1, user["id"].to_bytes(4, "big"))
    if "name" in user:  out += put(2, user["name"].encode())
    if "email" in user: out += put(3, user["email"].encode())
    return out

def decode(data):
    i, out = 0, {}
    while i < len(data):
        tag, n = data[i], data[i + 1]
        value = data[i + 2 : i + 2 + n]
        i += 2 + n
        if tag == 1:   out["id"] = int.from_bytes(value, "big")
        elif tag == 2: out["name"] = value.decode()
        elif tag == 3: out["email"] = value.decode()
        else:          out["unknown_%d" % tag] = value   # skip what we don't know
    return out

msg = encode({"id": 7, "name": "Asha", "email": "a@x.io"})
print(msg.hex(" "), len(msg), "bytes")
print(decode(msg))
01 04 00 00 00 07 02 04 41 73 68 61 03 06 61 40 78 2e 69 6f 20 bytes
{'id': 7, 'name': 'Asha', 'email': 'a@x.io'}

Read the bytes as three records:

01tag: id
04length
00 00 00 07value (7)
02tag: name
04length
41 73 68 61"Asha"
03tag: email
06length
61 40 78 2e 69 6f"a@x.io"

The same record as JSON is 39 bytes; our TLV is 20, and real protobuf is 16 (it writes the id as a one-byte variable-length integer, giving 08 07 12 04 41 73 68 61 1a 06 61 40 78 2e 69 6f). The savings come from dropping field names, since they live in the schema.

Why tags make evolution possible

Because the data identifies fields by tag number rather than name, a lot becomes safe:

  • Renaming a field is free. Names are only for humans and code generators. Rename name to full_name and keep the tag 2, and every old byte string still decodes into the right field.
  • Adding a field is safe, if you give it a new tag and old code ignores unknown tags. Our decoder's else branch does exactly that, and it can even skip the value because the length tells it how far to jump:
newer = msg + put(4, b"Lisbon")      # a newer writer adds tag 4
print(decode(newer))
{'id': 7, 'name': 'Asha', 'email': 'a@x.io', 'unknown_4': b'Lisbon'}
  • Reusing a tag number is not safe. Old records still sitting in files and databases say "tag 2 is the name". If a new schema reassigns tag 2 to something else, say an integer age, those old records are misread: the bytes for "Asha" decode as a very large number.
def decode_reused(data):             # a "new" reader that reused tag 2 as an integer age
    i, out = 0, {}
    while i < len(data):
        tag, n = data[i], data[i + 1]
        value = data[i + 2 : i + 2 + n]
        i += 2 + n
        if tag == 2: out["age"] = int.from_bytes(value, "big")
    return out
print(decode_reused(msg))
{'age': 1098082401}

That number is just the four bytes of "Asha" read as an integer. Nothing crashed; the data was silently wrong. So the rule in protobuf shops: never change a field's meaning or reuse a retired tag. When you delete a field, mark its number reserved so nobody reuses it later.

Analogy: numbered boxes in a warehouse

Imagine a warehouse where every shelf slot has a permanent number and the shipping labels say "slot 2: contents". You can repaint the sign above slot 2 from "name" to "full name" without confusing anyone, and you can add slot 4 without disturbing slots 1 to 3. But if you start putting different things into slot 2, every old label now points at the wrong thing.

Where it breaks down: real field numbers also carry a small type code, and a mismatch there can be detected. Reusing a tag with the same wire type but a different meaning is the dangerous case, because nothing flags it.

Avro: the schema travels separately

Apache Avro takes a different route: there are no tags in the data at all. A record is simply its values written one after another in the order the schema lists them, which makes Avro very compact. To decode, you need the exact schema the data was written with. Avro handles change by keeping two schemas side by side:

  • The writer's schema is the one the writer used to encode the data. It is stored with the file, or looked up by an id.
  • The reader's schema is the one the reading program wants the data to look like.

The decoder compares them by field name and reconciles the difference: a field in the writer's schema but not the reader's is skipped; a field in the reader's but not the writer's is filled with its declared default value; reordered fields are matched up by name. So in Avro you can rename a field only with explicit aliases, and a field you add must have a default to stay compatible. Avro is popular for large data files and Kafka streams, where it is easy to attach the writer's schema once per file or by registry reference rather than repeating it in every record.

Apache Thrift, from Facebook, is in one line a protobuf-style system with numbered fields and generated code that also bundles an RPC framework.

Compatibility: old and new code together

Two terms describe what "safe" means when code and data are different ages:

  • Backward compatibility: new code can read data written by old code. (Usually straightforward: you know the old format.)
  • Forward compatibility: old code can read data written by new code. (Harder: old code must ignore things it has never heard of.)

You need both because of the rolling deploy: instead of stopping everything to upgrade, you replace servers one at a time so the service stays up. For a while, version 1 and version 2 of your code are running at the same time, reading and writing the same database and sending messages to each other.

A common trap: old code rewrites new fields away

Forward compatibility has a subtle extra requirement. If old code reads a record containing a field it does not know, modifies it, and writes it back, it must preserve the unknown field, not drop it. Otherwise a v1 server quietly erases data that v2 added. Careless decode-to-object-then-encode cycles do exactly this, so be careful with read-modify-write on records with unknown fields.

Practical rules that follow from the mechanisms above:

  • Add fields as optional or with a default; do not add a new required field (old data lacks it, so new code could not read it).
  • Never reuse a protobuf tag. Remove fields by reserving the number.
  • In Avro, give new fields a default, and use aliases to rename.
  • For breaking changes, run both versions in parallel: write the new field in addition to the old one, migrate readers, then retire the old field.

Data outlives code

Code can be replaced in minutes by redeploying. Data cannot. A database table may hold rows written five years ago, by code that no longer exists. The oldest backups hold even older shapes. Rewriting all that data into a new format (a "migration") is possible but costly on a large dataset, so many systems keep the old rows as they are and make the reading code understand every version, a quiet cost of schema-on-read from chapter 1.

For streams of messages, teams therefore use a schema registry: a small service that stores every version of each schema, gives each a numeric id, and refuses to accept a new version that would break compatibility with the previous ones. Producers put the schema id in front of each message; consumers look the id up to learn how to decode it. Confluent's Schema Registry for Kafka is the well-known example. It turns "does this change break anyone?" from a hope into an automated check at publish time.

Encoding in databases, RPC and message queues

The encoding choice shows up in three places where data flows between processes:

  • Databases. A process writes, and a possibly different or newer process reads later, perhaps years later. A database engine has its own on-disk format. What you choose is the column types or document format on top (JSON columns, protobuf blobs). Data outlives code is most true here.
  • Services and RPC. Client and server are deployed independently, so they must tolerate each other's versions. REST APIs usually send JSON. Binary RPC systems such as gRPC send protobuf messages (over HTTP/2) and rely on those compatibility rules, because clients and servers are never upgraded at the same moment.
  • Message queues and logs. A producer writes a message and consumers read it later, possibly much later, and there may be many different consumers. A log such as Kafka may keep messages for days or forever, which is why schemas for them are usually Avro or protobuf plus a registry. We build on this in chapter 19.
Go deeper: how real protobuf writes a tag and an integer optional

Real protobuf combines the field number and a 3-bit wire type into one number, (field_number << 3) | wire_type, written as a varint. Wire type 0 means "a varint follows" (integers), and 2 means "length-delimited" (strings, bytes, nested messages). So field 1 as an integer has tag byte (1<<3)|0 = 0x08, and field 2 as a string has (2<<3)|2 = 0x12.

A varint stores a number 7 bits at a time, least significant group first; the top bit of each byte says "more bytes follow". So 7 is the single byte 07, while 300 is ac 02 (the low 7 bits of 300 are 0101100, with the continuation bit set to make ac, then the remaining value 2). Small numbers, the common case, cost one byte. That is why the id in our record needs one byte in protobuf but four in our fixed-width TLV.

Try it yourself

Everything runs with plain python3 and nothing is installed. Put the json/struct example and the TLV example into two files and run them, then experiment:

  1. In the struct demo, change score to 3.5 as an f (4-byte float) instead of d. How many bytes now? What do you lose?
  2. Add a field "city" with tag 5 to encode and decode data from a version of decode that has never heard of tag 5. Confirm the old reader still works.
  3. Make a "required" field: change decode to raise an error if tag 3 is missing. Then feed it data written before email existed. This is why new required fields break backward compatibility.
  4. Encode 9007199254740993 as JSON and read it back with node -e (or your browser's console). Compare with Python.

Distributed systems connection

In a distributed system there is no moment when "everything is now version 2". Rolling deploys, canary releases and long-lived queues guarantee that versions overlap, so compatibility is not a nicety but a requirement. Tags, defaults and registries are how large systems let teams deploy independently without a coordinated "flag day". The same reasoning reappears when we look at replication, where followers may run older software than the leader (chapter 15), and at event logs that must stay readable for years (chapter 19).

Key takeaways

  • Memory holds pointers; files and networks hold bytes. Encoding converts one to the other, and decoding reverses it.
  • Language-specific formats like pickle are convenient but tied to one language, versioning-poor, and unsafe to decode from untrusted input.
  • JSON and CSV are readable and universal, but they have no schema, no binary type, ambiguous or imprecise numbers (big ints collapse in JavaScript), and CSV has no types at all.
  • Schema-based binary formats are smaller and faster. Protobuf and Thrift identify fields by numeric tags; Avro identifies them by name using a writer's and a reader's schema, with no tags in the data.
  • Because of tags, renaming a protobuf field is safe but reusing a tag number silently corrupts old data. Retire numbers with reserved.
  • Backward compatibility (new reads old) and forward compatibility (old reads new) are both needed during rolling deploys. New fields should be optional or have defaults, and unknown fields must be preserved.
  • Data outlives code. Schema registries enforce compatibility and give every message a schema id.

Check your understanding

A protobuf schema has string name = 2;. A developer renames it to string full_name = 2;. Is that safe for existing stored data?

  1. No: every stored record contains the word "name", so it would not decode
  2. No: field names must never change in any format
  3. Yes: the bytes contain tag 2, not the name, so old data still decodes into the renamed field
  4. Only if the data is first converted to JSON
Names exist only in the schema and generated code. The encoded data identifies the field by its tag number. (In Avro, by contrast, names matter, and renaming needs an alias.)

Why is reusing a retired protobuf tag number for a new field dangerous?

  1. Old records in files and databases still use that tag for the old meaning, so they get decoded as the wrong thing, often without any error
  2. The compiler refuses to build, which is annoying
  3. The tag number is a security token
  4. It makes messages larger
Data outlives code. Anything written while the tag meant "name" still says tag 2. Reinterpret it as an integer and you get garbage, silently, as we saw with the 1098082401 result.

During a rolling deploy, v1 servers must correctly read records written by v2 servers. This property is called...

  1. Backward compatibility
  2. Atomicity
  3. Normalisation
  4. Forward compatibility
Old code reading newer data is forward compatibility. New code reading older data is backward compatibility. A rolling deploy needs both, because both versions run at once.

A JavaScript service reads the JSON {"id": 9007199254740993} and sends the id back. What is the likely problem?

  1. JSON cannot contain numbers that large and rejects them
  2. JavaScript parses numbers as 64-bit doubles, so it will read and write back 9007199254740992, a different id
  3. Nothing: JSON numbers are always exact
  4. The id will be converted to a string automatically
Doubles represent integers exactly only up to 253. Large ids should be sent as strings. JSON itself does not limit precision, which is part of the problem: it is left to each implementation.

Which statement about Avro is correct?

  1. Each field is stored with a numeric tag so readers can skip unknown fields
  2. The data is self-describing text, like JSON
  3. It resolves differences between the writer's schema and the reader's schema by field name, using defaults for fields the writer did not have
  4. It requires the writer and the reader to use identical schemas
Avro data contains no tags or names, just values. The decoder needs the writer's schema and compares it with the reader's by name, which is what lets the two differ safely.

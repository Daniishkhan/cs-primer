Isolation Levels & Anomalies

Two transactions run at the same time and each looks perfectly correct on its own. Together they lose money, double-book a room, or leave a hospital with nobody on call. This chapter names the six classic ways that happens, shows each as a timeline you can read at a glance, and then ties them to the isolation levels databases offer, including the awkward truth that the SQL standard's definitions are ambiguous and the vendors' names don't line up.

Why this matters

Most production databases run at an isolation level weaker than serializable by default. So most applications built on them contain concurrency bugs that appear rarely, never in tests, and silently corrupt data: no crash, no error, just a wrong number. Knowing the named anomalies lets you read a piece of code and say "that is a lost update waiting to happen" or "that is write skew", and knowing which level prevents which one lets you pick the right fix instead of sprinkling locks until the bug stops showing up. It is also the topic interviewers use to find out who has really used a database.

The ideal, and why we don't always get it

The cleanest possible promise a database can make is serializability: running transactions concurrently produces the same result as running them one at a time, in some order. You never have to think about interleavings, because the outcome is always one you could have got by hand with a queue. That is the C-for-correctness gold standard, and chapter 10 called it the strongest meaning of the I in ACID.

The catch is cost. Enforcing serializability means transactions sometimes wait for each other, or get aborted and retried, and for decades that was judged too expensive for many workloads. So databases offer weaker isolation levels that allow some interleavings the serial model would forbid, in exchange for speed. Each weaker level lets through a specific set of surprises, called anomalies (or phenomena). Your job as an engineer is to know the menu.

Analogy: tellers sharing one ledger page

Back at the bank from chapter 10, imagine many tellers working from the same paper ledger at once. A serial bank lets one teller at a time have the ledger. That is always right, and slow. A faster bank lets several tellers work simultaneously, and each rule you relax is a new way for two of them to collide: one reads a number while another is mid-way through changing it; two tellers both copy a balance, subtract from it, and write back their own result; two tellers each check "is there still a manager on duty?" and then both send their manager home.

Where it breaks down: in a paper ledger the tellers can see each other and shout. Transactions can't. Each sees only what the database shows it, which is exactly why the database's rules about what a transaction is allowed to see define the whole problem.

Dirty write

A dirty write happens when a transaction overwrites a value that another transaction has written but not yet committed. The classic example is two buyers competing for a car, where the sale touches two rows (the listing and the invoice):

Each transaction on its own is correct, and yet the final state is one no serial order could produce. Almost every database prevents dirty writes at every level, by making a transaction hold a row lock on anything it writes until it commits or aborts (chapter 12): T2's write to the listing simply waits.

Dirty read

A dirty read is reading data another transaction has written but not committed. If that other transaction then rolls back, you acted on a value that never officially existed.

Dirty reads are only possible at Read Uncommitted, the weakest standard level, and few systems make it useful: Postgres, for one, accepts the name but runs it as Read Committed. Reading uncommitted data also breaks atomicity from the reader's point of view: it can see half of a transaction that is about to be undone.

Non-repeatable read and read skew

A non-repeatable read means reading the same row twice in one transaction and getting different answers because another transaction committed a change in between. The same phenomenon, seen across two different rows, is called read skew: you see part of a transaction's effects but not all. Take two accounts holding 500 each (1000 in total) and an audit that adds them up:

Every individual read returned a committed value, so this is legal at Read Committed. For a quick report nobody cares. But for a backup, an integrity check or an analytics query that runs for minutes, a view that is inconsistent in this way is useless: you cannot restore a backup whose rows come from different moments. That is the main motivation for snapshot isolation, which we meet below.

Lost update

You already know this one: it is the read-modify-write race of systems chapter 11, with a database row in place of a variable. Two transactions read the same value, compute a new one, and write back; the second write overwrites the first without ever having seen it.

Note what is and isn't wrong. No dirty read happened and no dirty write (T2 wrote after T1 committed). The failing step is T2 using a value it read earlier to decide what to write.

Write skew

Write skew is the sneaky relative of the lost update, and the one interviewers love. Two transactions read an overlapping set of rows, make a decision based on what they saw, and then write to different rows. Neither write conflicts with the other, so nothing blocks, but together they violate a rule that spans the rows. The textbook case: a hospital requires at least one doctor on call. Alice and Bob are both on call and both feel ill. Each checks that someone else will stay on, then takes themselves off:

The same shape is behind many real bugs: two users claiming the same username, two bookings for the same seat, a bank account with two withdrawals that each pass a "balance must stay above zero across all my accounts" check, a game where two players pick up the last item. The pattern is always read some rows, decide, write other rows (or insert a new row), where the decision depends on what you read.

Phantoms

A phantom is a write in one transaction that changes the result of a search another transaction has already run. The row that matches the search did not exist when the search ran, so there is nothing to lock. Meeting-room booking is the classic: check that nobody has the room at 10:00, then insert your booking.

Phantoms are write skew where the write is an INSERT (or a delete or update that makes a row start or stop matching the search). That is why they are the hardest to defend against with row locks: you would have to lock rows that haven't been created. Chapter 12 shows the tools that do handle them (predicate locks, index-range locks, and serializable snapshot isolation).

Common misconception

"A transaction is a lock around my code." It is not. At Read Committed or snapshot isolation, two transactions that never write the same row never wait for each other, as the write-skew and phantom timelines show, and no error is raised. A transaction guarantees what the database promises at the level you chose. It does not guarantee that the business rule you had in mind holds under concurrency.

The levels, and which anomalies each prevents

An isolation level is a named set of anomalies the database promises to prevent. Moving down the table is moving from "safest, slowest" to "fastest, most surprising". Here is the picture in textbook terms, with snapshot isolation (which the original SQL standard never mentioned) in its natural place:

* By definition snapshot isolation uses "first committer wins": if two concurrent transactions write the same row, one is aborted. Postgres does this at Repeatable Read, in the "first updater wins" form: a second writer waits for the first to finish and, if the first committed, fails with a serialization error. Some products that name a level "Repeatable Read" do not detect it, which is why the table speaks of the technique and not of a label.

Read it from the bottom. Serializable prevents everything, and the ways databases get there differ (chapter 12). Snapshot isolation gives each transaction a frozen, consistent picture of the database as of the moment it began, so it sees no changes from transactions that committed later: read skew and non-repeatable reads vanish, and long reports become safe. What it cannot see, it cannot protect, which is why write skew and phantom-style bugs survive: the two transactions in each timeline above saw perfectly consistent snapshots. Read Committed is a statement-by-statement version of "only committed data": each query sees the latest committed state at the instant it runs, so two queries in one transaction can disagree. Read Uncommitted allows dirty reads and little else.

The SQL standard is ambiguous, and vendors' names differ

Here we need to be honest, because this is where many explanations quietly cheat. The SQL-92 standard defined its four levels (Read Uncommitted, Read Committed, Repeatable Read, Serializable) by listing three phenomena each level must or may allow: dirty read, non-repeatable read and phantom. In their 1995 paper A Critique of ANSI SQL Isolation Levels, Berenson, Bernstein, Gray, Melton, O'Neil and O'Neil showed that this approach has real problems:

  • The definitions are ambiguous, written in English prose that can be read strictly or loosely, with materially different meanings.
  • They leave out anomalies that matter, such as dirty write, lost update and write skew. A database could satisfy the standard's wording and still allow them.
  • They say nothing about snapshot isolation, which was becoming popular and does not fit neatly into the four boxes: it is stronger than "Repeatable Read" in some ways (it prevents phantoms for plain reads) and weaker in others (it allows write skew).

Later work (notably Adya's thesis) recast the levels in terms of dependency graphs, which is much sharper but never displaced the old names. The practical consequence: the name of a level does not tell you what you get. The behaviour does, and the behaviour is product-specific. Here is what we can say with confidence about a few widely used systems:

SystemDefault levelWhat the names actually mean there
PostgreSQLRead CommittedRepeatable Read is snapshot isolation. Serializable uses serializable snapshot isolation (SSI) since version 9.1. Read Uncommitted behaves the same as Read Committed.
MySQL (InnoDB)Repeatable ReadPlain reads use a snapshot, but its Repeatable Read is not identical to Postgres's. Writes and locking reads see the latest committed data, and it does not automatically abort lost updates. Read the documentation for your version, and test.
OracleRead CommittedIts "Serializable" level is, in fact, snapshot isolation, so write skew is still possible there.
SQLiteSerializableTransactions are serializable: only one writer at a time, so write conflicts never interleave. The price is that writers (and sometimes readers) wait or get a "database is locked" error.

Two lessons follow. First, always read your database's own documentation about isolation, and prefer the vocabulary of anomalies over the vocabulary of level names. Second, if you port code between products, an unchanged SET TRANSACTION ISOLATION LEVEL REPEATABLE READ can quietly change which bugs you have.

Fixing lost updates

Lost updates are so common that databases offer four different cures. In rough order of preference:

  1. Make the update atomic. Don't read into the application at all: let the database do the arithmetic in one statement, UPDATE accounts SET balance = balance - 30 WHERE name = 'alice'. The database takes a row lock for the duration of the statement and applies the change to the latest value. This is the best option whenever the new value is a simple function of the old one.
  2. Lock explicitly. When the logic is too complex for one statement, read with SELECT ... FOR UPDATE (Postgres, MySQL and Oracle support it; SQLite has no such clause). It locks the rows you read so other writers wait until you finish. It works, but you must remember to write it everywhere; forget once and the bug is back.
  3. Compare-and-set. Add a version column. Read the row and its version, then write with WHERE version = :version and increment the version. If another writer got there first, zero rows match; reload and try again. It is the database form of the CAS retry loop from systems chapter 12, and it needs no long-held locks, which is why web frameworks use it for "optimistic locking".
  4. Let the database detect it. At snapshot isolation or serializable, Postgres notices that you are updating a row that changed since your snapshot and aborts your transaction with a serialization failure (could not serialize access due to concurrent update, SQLSTATE 40001). Your code must then retry the whole transaction (chapter 10). It is automatic, but it requires that retry loop to exist.

Fixing write skew and phantoms

Write skew is harder, because the two transactions write different rows and so a plain row-level write conflict never appears. The options, from simplest to ugliest:

  1. Use serializable isolation. It was designed to catch exactly this by tracking what each transaction read, not only what it wrote. In Postgres, one of the two doctors' transactions is aborted with a serialization failure and the retry sees the new situation. Cost: aborts and retries, and a retry loop in your code.
  2. Lock what you read. For the doctors, SELECT ... FROM doctors WHERE on_call FOR UPDATE locks every row the decision depends on, so the second transaction waits for the first and then sees the updated count. It works only when the rows exist to be locked.
  3. Declare the rule where the database can enforce it. Many "at most one" rules are really constraints: a UNIQUE index on (room, slot) makes the second booking fail at the database no matter how transactions interleave. (Postgres also has exclusion constraints for overlapping time ranges.) This is the cleanest fix for phantoms when the rule fits.
  4. Materialise the conflict. If there are no rows to lock, create some: a table of every (room, slot) pair, pre-filled, which every booking locks with FOR UPDATE before checking. It turns a phantom into an ordinary row-lock conflict. It leaks concurrency control into your schema, so reserve it for when serializable isn't available.

The Postgres versions of the first two look like this (Postgres syntax, shown for illustration only; the runnable demos below use SQLite):

-- Option 1: serializable. If it fails with SQLSTATE 40001, retry the transaction.
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM doctors WHERE on_call;                 -- sees 2
UPDATE doctors SET on_call = false WHERE name = 'alice';
COMMIT;

-- Option 2: lock every row the decision depends on.
BEGIN;
SELECT * FROM doctors WHERE on_call FOR UPDATE;              -- the other transaction now waits here
UPDATE doctors SET on_call = false WHERE name = 'alice';
COMMIT;

What SQLite really does: a runnable experiment

Let's watch concurrency control happen. SQLite is serializable and allows one writer at a time, which makes it a clean (if blunt) specimen. First, two connections: T1 writes without committing, and T2 tries to read and then write the same row.

import sqlite3, os
path = "demo.db"
for f in (path, path + "-journal"):
    if os.path.exists(f): os.remove(f)
setup = sqlite3.connect(path)
setup.execute("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER)")
setup.execute("INSERT INTO accounts VALUES ('alice', 100)")
setup.commit(); setup.close()

t1 = sqlite3.connect(path, isolation_level=None, timeout=0.2)   # give up waiting after 0.2 s
t2 = sqlite3.connect(path, isolation_level=None, timeout=0.2)

t1.execute("BEGIN")
t1.execute("UPDATE accounts SET balance = balance - 30 WHERE name = 'alice'")
print("T1 sees its own write:", t1.execute("SELECT balance FROM accounts").fetchone())
print("T2 reads meanwhile  :", t2.execute("SELECT balance FROM accounts").fetchone(), "(no dirty read)")
t2.execute("BEGIN")
try:
    t2.execute("UPDATE accounts SET balance = balance - 50 WHERE name = 'alice'")
except sqlite3.OperationalError as e:
    print("T2 write fails     :", e)
t2.execute("ROLLBACK")
t1.execute("COMMIT")
print("after T1 commit    :", t2.execute("SELECT balance FROM accounts").fetchone())
T1 sees its own write: (70,)
T2 reads meanwhile  : (100,) (no dirty read)
T2 write fails     : database is locked
after T1 commit    : (70,)

Four things to read off. T1 sees its own uncommitted write (70). T2 does not: it reads the committed 100, so no dirty read. T2's attempt to write the same data is refused with database is locked because T1 holds the write lock (Python's sqlite3 default timeout is five seconds, so ordinarily T2 would just wait that long before giving up; we cut it to 0.2 s so the demo ends quickly). And only after T1 commits does the world change. This is dirty-read and dirty-write prevention in its most direct form: block the second writer.

Now the lost update, three ways. This script uses two connections a and b standing in for two application servers:

import sqlite3, os
path = "demo2.db"
for f in (path, path + "-journal"):
    if os.path.exists(f): os.remove(f)
s = sqlite3.connect(path)
s.execute("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER)")
s.execute("INSERT INTO accounts VALUES ('alice', 100)")
s.commit(); s.close()

def connect():
    return sqlite3.connect(path, isolation_level=None, timeout=1)
a, b = connect(), connect()

# 1. The classic bug: read, compute in Python, write back. Each statement is its own transaction.
bal_a = a.execute("SELECT balance FROM accounts WHERE name='alice'").fetchone()[0]   # A reads 100
bal_b = b.execute("SELECT balance FROM accounts WHERE name='alice'").fetchone()[0]   # B reads 100
a.execute("UPDATE accounts SET balance = ? WHERE name='alice'", (bal_a - 30,))        # A writes 70
b.execute("UPDATE accounts SET balance = ? WHERE name='alice'", (bal_b - 50,))        # B writes 50
print("read-compute-write:", a.execute("SELECT balance FROM accounts").fetchone()[0], "(expected 20)")

# 2. The fix: let the database do the arithmetic in one atomic statement.
a.execute("UPDATE accounts SET balance = 100")
a.execute("UPDATE accounts SET balance = balance - 30 WHERE name='alice'")
b.execute("UPDATE accounts SET balance = balance - 50 WHERE name='alice'")
print("atomic UPDATE     :", a.execute("SELECT balance FROM accounts").fetchone()[0], "(expected 20)")

# 3. The same bug inside real transactions: SQLite refuses to let B write after A did.
a.execute("UPDATE accounts SET balance = 100")
a.execute("BEGIN"); b.execute("BEGIN")
bal_a = a.execute("SELECT balance FROM accounts").fetchone()[0]
bal_b = b.execute("SELECT balance FROM accounts").fetchone()[0]
a.execute("UPDATE accounts SET balance = ?", (bal_a - 30,))
try:
    b.execute("UPDATE accounts SET balance = ?", (bal_b - 50,))
except sqlite3.OperationalError as e:
    print("B in a transaction:", e)
    b.execute("ROLLBACK")
a.execute("COMMIT")
print("final             :", a.execute("SELECT balance FROM accounts").fetchone()[0])
read-compute-write: 50 (expected 20)
atomic UPDATE     : 20 (expected 20)
B in a transaction: database is locked
final             : 70

This one deserves a slow read.

  • Case 1 lost an update on a serializable database. SQLite is serializable, and it still returned 50. The reads and the writes were four separate autocommit transactions, so the database was never asked to treat them as one unit. Serializable isolation only protects what you put inside a transaction. If your application splits a read and its dependent write across transactions (typically two HTTP requests, or an ORM that commits after each call), no isolation level can save you.
  • Case 2 is the fix from the list above. The statement runs on the latest value under the database's own lock, and the answer is 20.
  • Case 3 shows a strict database doing its job: both transactions read 100, A wrote, and B's write was refused because A holds the write lock and B had already read the value A was changing; waiting for A could not make B's earlier read fresh. B has to roll back and retry from the start. The final balance 70 is correct for the one withdrawal that committed, and B's 50 will be applied (against 70) when B retries. An error you can see is vastly better than a number you can't.

And the compare-and-set fix, using a version column and a retry loop. The second client's first attempt fails, and its second attempt succeeds against the fresh value:

import sqlite3, os
path = "ver.db"
for f in (path, path + "-journal"):
    if os.path.exists(f): os.remove(f)
s = sqlite3.connect(path)
s.execute("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER NOT NULL, version INTEGER NOT NULL DEFAULT 0)")
s.execute("INSERT INTO accounts (name, balance) VALUES ('alice', 100)")
s.commit(); s.close()

def connect():
    return sqlite3.connect(path, isolation_level=None, timeout=1)

def withdraw(con, amount, interleave=None):
    """Optimistic update: read the row and its version, then write only if the version is unchanged."""
    for attempt in range(1, 6):
        balance, version = con.execute("SELECT balance, version FROM accounts WHERE name='alice'").fetchone()
        if interleave and attempt == 1:
            interleave()                                    # another client sneaks in here
        cur = con.execute(
            "UPDATE accounts SET balance = ?, version = version + 1 WHERE name='alice' AND version = ?",
            (balance - amount, version))
        if cur.rowcount == 1:
            return f"withdrew {amount} on attempt {attempt}"
        # rowcount 0: somebody else changed the row since we read it. Loop and read again.
    return "gave up"

a, b = connect(), connect()
print("A:", withdraw(a, 30, interleave=lambda: print("B:", withdraw(b, 50))))
print(a.execute("SELECT balance, version FROM accounts").fetchone())
B: withdrew 50 on attempt 1
A: withdrew 30 on attempt 2
(20, 2)

A read 100 at version 0, then B slipped in and committed (balance 50, version 1). A's conditional update matched zero rows because the version had moved on, so A re-read 50 at version 1 and wrote 20 at version 2. Both withdrawals counted.

Go deeper: Adya's view and why write skew is a cycle optional

Adya's formulation looks at the dependencies between transactions. T1 write-depends on T2 if it overwrites something T2 wrote; read-depends if it reads something T2 wrote; and anti-depends if it writes something that T2 earlier read (the read-write edge). A history is serializable exactly when this dependency graph has no cycle. In write skew, T1 read the row T2 later wrote, and T2 read the row T1 later wrote, so there are two anti-dependency edges pointing in opposite directions: a cycle of length two, and no serial order can explain it. Snapshot isolation is allowed to have such cycles but only ones that contain two adjacent anti-dependency edges; serializable snapshot isolation (chapter 12) works by detecting exactly that shape.

Distributed systems connection

The anomalies you just met have exact twins in the distributed world. A lost update between two leaders in a multi-leader replicated database is the same read-compute-write race, with replication lag as the gap; read skew is what you get when one read hits a replica that is behind and the next hits a replica that is current (chapter 15); and write skew across shards is what makes distributed transactions necessary. One more distinction trips up experts: serializability (this chapter) is about transactions behaving as if run in some serial order, while linearizability (networking chapter 18) is about a single object appearing to update instantly in real time. A system can have either, both, or neither; Google's Spanner (networking case 10) is famous for offering both, at the price of synchronised clocks.

Key takeaways

  • Isolation levels are defined by the anomalies they allow. Learn the six: dirty write, dirty read, read skew (non-repeatable read), lost update, write skew, phantom.
  • Read Committed stops dirty reads and writes, but each statement sees fresh data, so read skew, lost updates, write skew and phantoms all remain. It is the default in Postgres and many other systems.
  • Snapshot isolation gives each transaction a stable, consistent picture, and first-committer-wins (Postgres: first-updater-wins) stops lost updates. It does not stop write skew or phantom-style bugs, because the transactions write different rows or insert new ones.
  • Only serializable prevents every anomaly, at the cost of aborts or waiting. Your code must be ready to retry.
  • The SQL standard's definitions are ambiguous (Berenson et al., 1995), and vendors differ: Postgres Repeatable Read is snapshot isolation, Oracle's "serializable" is snapshot isolation, MySQL InnoDB defaults to Repeatable Read with its own behaviour, SQLite is serializable. Check the documentation, not the name.
  • Lost updates: use an atomic UPDATE, SELECT ... FOR UPDATE, a version-column compare-and-set, or rely on automatic detection plus retry.
  • Write skew and phantoms: use serializable, lock what you read, enforce the rule with a unique or exclusion constraint, or materialise the conflict.
  • Isolation protects only what is inside one transaction. Splitting a read and its dependent write across two transactions loses the protection at every level.

Data Platforms: Warehouses, Lakehouses & Pipelines

So far we studied how one database stores and queries data. Real companies also need to answer questions across all their data, without slowing the application down. This chapter follows the data on its journey: out of the operational databases, through pipelines, into tables on cheap object storage that behave like a database, and finally into the dashboards and models that depend on it being right.

Why this matters

Every company past a certain size ends up with a data platform, and a large share of data engineering is plumbing: moving data reliably, re-running it safely, and noticing when it silently goes wrong. The most expensive data failures are rarely crashes. They are a dashboard that is quietly wrong for three weeks. Knowing the moving parts, and especially how a table made of plain files can still offer atomic commits, lets you reason about all of them.

From OLTP to analytics

The databases behind an application are tuned for OLTP (online transaction processing): many small reads and writes touching a few rows each, with strict latency and correctness, as in chapter 10. Analytics asks different questions: “what was revenue per country per week this year?” touches millions of rows but only a few columns. Running that on the production database competes with customers for CPU, memory and locks, and row-oriented storage is a poor fit. That is the motivation for OLAP (online analytical processing): a separate system, storing a copy of the data in a layout designed for scans and aggregates, usually columnar (chapter 9).

So data must travel from the operational systems to the analytical one. There are two classic orderings of the work:

ETL: extract, transform, load

Pull data from the source, clean and reshape it on a separate processing engine, and load only the finished result into the target. Good when the target is small or expensive, or when sensitive fields must be removed before data lands anywhere new.

ELT: extract, load, transform

Load the raw data into the analytical store first, then transform it there with SQL, using the store's own parallel compute. Good when storage is cheap, compute is elastic, and you want the raw data kept so a transformation can be fixed and replayed.

Many teams today lean toward ELT because storage is cheap and warehouses scale compute on demand, and it makes transformations just SQL that analysts can read. That is a trend, not a law. ETL remains the right choice when the transform must run before the data may be stored, for instance dropping personal data, a theme we revisit at the end.

Warehouses, lakes and lakehouses

A data warehouse is a database built for analytics: structured tables, SQL, strong consistency, and a managed engine that organizes and indexes the data for you. A data lake is the opposite bargain: dump files of any kind (CSV, JSON, logs, images) into cheap object storage (a service that stores immutable blobs by key, such as S3, Google Cloud Storage or Azure Blob Storage) and impose structure when you read. Lakes are cheap and flexible, and they became famous for turning into “data swamps”: nobody knows what is in a folder, whether a file is complete, or which version is current.

A lakehouse is the attempt to keep the lake's cheap open storage while adding the warehouse's guarantees. The term is partly marketing, and the boundaries blur (warehouses now read open table formats too), so treat the three words as points on a spectrum rather than rival camps. What is genuinely new and worth understanding is the layer that makes it possible: the open table format.

Why files on object storage need a table format

Chapter 9 introduced Parquet: a columnar file format that stores each column's values together, compressed, with min/max statistics per chunk so a reader can skip data. A lake table is typically a directory of Parquet files. That works for read-only data, but trouble starts when you try to change it:

  • Object stores keep whole objects. You can write or replace one object atomically, but historically there was no way to change several objects as one atomic step. A job that rewrites ten files and crashes after five leaves a mix of old and new.
  • A reader listing the directory mid-job sees a half-finished state. Two jobs writing at once can clobber each other.
  • “What files make up the table?” is answered by listing a directory: slow at scale, and ambiguous when leftover files from failed jobs sit alongside real ones.
  • There is no place to record the schema, and renaming a column means rewriting everything.

An open table format solves this by adding a thin layer of metadata files that define the table: “the table at version N is exactly these data files.” Three formats dominate: Apache Iceberg, Delta Lake and Apache Hudi. They differ in details but share one idea you already know from chapter 13 and chapter 12: never modify data in place. Write new immutable files, then publish them with one tiny atomic step. Versioning (MVCC) falls out for free.

Anatomy of a table, Iceberg style

Iceberg organizes a table as a tree of immutable files. At the top, a catalog stores just one thing per table: a pointer to the current metadata file. The metadata file records the schema, how the table is partitioned, and a list of snapshots. A snapshot is the state of the table at one moment, including the set of all its data files. Each snapshot has a manifest list, which points to manifests: files that list data files with per-file statistics such as row counts and column min/max values. A query planner reads manifests, discards files whose statistics cannot match the filter, and only then opens Parquet files.

Delta Lake and Hudi reach the same goals with different shapes. Delta keeps a transaction log: a directory of numbered JSON files, each listing files added and removed by one commit, with periodic checkpoints so a reader need not replay history from zero. Hudi keeps a timeline of actions (commits, compactions, cleans), each moving through requested, inflight and completed states, and leans on the storage system's atomic operations to publish them. Hudi also has a strong focus on fast upserts. Which to choose is mostly an ecosystem question (which engines and vendors you use); all three are open, and tooling that translates between them exists.

How a commit works on object storage

The key trick is that you do not need atomic multi-file updates, only one atomic step at the very end. Write everything immutable first (unreachable, so harmless if you crash), then flip a single pointer. In order:

  1. Read the current version, remember it as your base.
  2. Write new data files. Nobody can see them, because no metadata mentions them. A crash here leaves orphans that a cleanup job removes later.
  3. Write new metadata (a manifest, then a new snapshot or log entry) describing “base plus my changes”. Again invisible.
  4. Atomically publish. Swap the pointer from your base to the new version, but only if nobody else has moved it. In Iceberg's words, the writer commits by swapping the table's metadata file pointer, and if the swap fails, the writer must retry based on the new current version. Delta does it by creating the next numbered log file; this needs a storage primitive such as put-if-absent.
  5. If step 4 loses a race, check for conflict: did the winner touch files I read or deleted? If not, rebase and retry. If so, abort and redo the work.

This is optimistic concurrency control: assume nobody interferes, do the work without locks, and verify at commit time. It is cheap when conflicts are rare (two writers appending to the same table) and wasteful when they are common (two jobs rewriting the same files). Delta's documentation describes exactly this: writes read the latest version, stage new files, then validate and commit, and a conflicting commit fails with an exception instead of corrupting the table. Pure inserts do not conflict with each other, but update, delete, merge and compaction can.

Step through

Two writers, one commit point

  1. Both writers read the table and see version 1. Each remembers it as its base.
  2. Each writes its new data file to object storage. Nothing references these files yet, so no reader can see them. If a writer crashes now, only an orphan file is left behind.
  3. Each writes a manifest describing “version 1 plus my file”. Still invisible.
  4. Writer A creates the pointer for version 2. The storage system guarantees that creating a name that already exists fails, so exactly one writer can own each version. A has committed.
  5. Writer B tries to create version 2 too. The name exists, so the commit is rejected. Table state is untouched; B's data and manifest are harmless leftovers.
  6. B re-reads version 2, sees that A only appended (no overlap with what B changed), rebuilds its manifest on top of v2 and creates version 3. If A had deleted a file B depended on, B would have to redo its work instead.

Build it: a tiny table format

Here is the whole idea in about eighty lines of Python on a local directory. It borrows Delta's numbered-version naming and Iceberg's manifest-per-snapshot shape. The atomic step is os.open with O_EXCL, which creates a file only if it does not already exist. That is the local-disk analogue of an object store's “put if absent” (many object stores now offer conditional writes; others need a catalog service to play referee). It is a teaching model: no schemas, no statistics, no cleanup of orphans, and the files hold JSON lists instead of Parquet.

import json, os, shutil, tempfile, uuid

class CommitConflict(Exception):
    pass

class Table:
    """A toy table format: immutable data files, immutable manifests,
    and a pointer log where each commit is a put-if-absent of the next version."""

    def __init__(self, root):
        self.root = root
        for d in ("data", "manifests", "pointers"):
            os.makedirs(os.path.join(root, d), exist_ok=True)

    # ---- reading ----
    def latest(self):
        names = sorted(os.listdir(os.path.join(self.root, "pointers")))
        return int(names[-1]) if names else 0

    def files_at(self, version):
        if version == 0:
            return []
        with open(os.path.join(self.root, "pointers", f"{version:08d}")) as f:
            manifest = f.read().strip()
        with open(os.path.join(self.root, "manifests", manifest)) as f:
            return json.load(f)["files"]

    def read(self, version=None):
        version = self.latest() if version is None else version
        rows = []
        for name in self.files_at(version):
            with open(os.path.join(self.root, "data", name)) as f:
                rows += json.load(f)
        return sorted(rows)

    # ---- writing ----
    def write_data(self, name, rows):
        # Step 1: data files are written first. Nobody can see them yet.
        with open(os.path.join(self.root, "data", name), "w") as f:
            json.dump(rows, f)

    def commit(self, base, add=(), remove=()):
        """Try to publish version base+1. Fails if someone else got there first."""
        files = [f for f in self.files_at(base) if f not in remove] + list(add)
        # Step 2: write an immutable manifest for the new snapshot.
        manifest = f"m-{uuid.uuid4().hex[:8]}.json"
        with open(os.path.join(self.root, "manifests", manifest), "w") as f:
            json.dump({"parent": base, "files": files}, f)
        # Step 3: the atomic step. Exclusive create fails if the name exists.
        target = os.path.join(self.root, "pointers", f"{base + 1:08d}")
        try:
            fd = os.open(target, os.O_CREAT | os.O_EXCL | os.O_WRONLY)
        except FileExistsError:
            raise CommitConflict(f"version {base + 1} already exists (base {base} is stale)")
        with os.fdopen(fd, "w") as f:
            f.write(manifest)
        return base + 1

root = tempfile.mkdtemp(prefix="toytable-")
try:
    t = Table(root)

    t.write_data("a.json", [1, 2, 3])
    v = t.commit(0, add=["a.json"])
    print("first commit is v%d ->" % v, t.read())

    # Two writers both read version 1 and prepare appends.
    base_a = base_b = t.latest()
    t.write_data("b.json", [10, 20])
    t.write_data("c.json", [100])
    print("A and B both start from v%d" % base_a)

    print("A commits   ->", "v%d" % t.commit(base_a, add=["b.json"]))
    try:
        t.commit(base_b, add=["c.json"])
    except CommitConflict as e:
        print("B is rejected:", e)
        # An append commutes with another append, so B can re-read and retry.
        new_base = t.latest()
        print("B retries on v%d ->" % new_base, "v%d" % t.commit(new_base, add=["c.json"]))

    print("latest rows        :", t.read())
    print("time travel to v1  :", t.read(1))
    print("time travel to v2  :", t.read(2))

    # A real conflict: both compact file a.json into new files.
    base_x = base_y = t.latest()
    t.write_data("x.json", [1, 2, 3])
    t.write_data("y.json", [1, 2, 3])
    print("X rewrites a.json -> v%d" % t.commit(base_x, add=["x.json"], remove=["a.json"]))
    try:
        t.commit(base_y, add=["y.json"], remove=["a.json"])
    except CommitConflict as e:
        now = t.latest()
        print("Y is rejected:", e)
        print("a.json still in the table? ->", "a.json" in t.files_at(now), "(Y must redo its work, not just retry)")
    print("history:", [(n, t.files_at(n)) for n in range(1, t.latest() + 1)][-2:])
finally:
    shutil.rmtree(root)
    print("cleaned up:", not os.path.exists(root))

Read the output as a story. Both writers started from v1. A won v2; B was rejected, rebased and landed as v3. Because every snapshot is just a list of immutable files, read(1) and read(2) return exactly the historical contents: that is time travel. In the last act, two writers both tried to replace a.json (a compaction, in real life). X won; Y's work was based on a file that no longer exists, so a blind retry would be wrong. This is the distinction real formats make between conflicts that can be retried automatically and those that must fail.

Atomic commits still need a referee

Everything above relies on the storage or catalog providing one atomic compare-and-swap (or create-if-absent). Where plain object storage lacks it, formats use a catalog service or a coordination store as that referee, and the table is only as safe as that component. If two writers can both believe they won, you are back to a corrupted table. This is the same lesson as leader election in the distributed systems course: some single thing must decide.

Time travel and schema evolution

Because old snapshots stay readable, you can query a table “as of” a version or timestamp, to reproduce last month's report, audit a change, or roll back a bad load by pointing the table at an earlier snapshot. The cost is storage: old files cannot be deleted while any snapshot references them, so teams expire snapshots after a retention period and later remove unreferenced files (Delta's VACUUM, Iceberg's snapshot expiry and orphan-file cleanup).

Schema evolution means adding, dropping or renaming columns without rewriting data. Iceberg achieves safe renames by identifying columns by a unique numeric ID rather than by name or position: the metadata maps IDs to names, and the table keeps a counter so new columns always get an unused ID. A renamed column keeps its ID, so old files still line up. Delta and Hudi support schema changes too, with different mechanics and rules. Even so, changing the meaning of a column (cents became dollars) is something no format can detect. That is a contract problem, below.

Pipelines: orchestration and idempotent backfills

Data does not move itself. A pipeline is a series of steps (ingest, clean, join, aggregate, publish), each depending on others. An orchestrator such as Apache Airflow (the best-known example; Dagster, Prefect and others are alternatives with different philosophies) runs them in the right order, on a schedule or when upstream data arrives, retries failures, and records what ran. The central abstraction is the DAG (directed acyclic graph): tasks are nodes, dependencies are edges, and no cycles are allowed, so there is always a valid order. You met the same shape as a dataflow graph in chapter 18.

The medallion layering in the figure (bronze, silver, gold) is a popular convention, associated with the Databricks ecosystem, not a standard. Its value is the principle behind it: keep an untouched raw copy so you can always rebuild downstream tables, and put the messy work in the middle so that the final tables are few, tested and trustworthy.

Backfills must be idempotent

Jobs fail, bugs get fixed, and source data arrives late. So you must be able to backfill: re-run a task for a past period. This is only safe if the task is idempotent, meaning that running it twice gives the same result as running it once (the same word as in the API chapter of the architecture course). A job that does INSERT INTO daily_revenue SELECT ... WHERE day = today doubles the numbers on every retry. Three habits make jobs idempotent:

  • Parameterize by logical date, not by the clock. The run for “2026-10-12” reads the input slice for that day and writes the output slice for that day, whenever it actually executes. Calling now() inside a task is the classic backfill-breaker.
  • Overwrite a partition, or MERGE by key, rather than blindly appending. Table formats make “replace exactly this day” an atomic commit, so readers never see half a day.
  • Keep tasks deterministic and inputs immutable. If the bronze layer is append-only and silver is a pure function of it, any past day can be recomputed. This is why the raw layer exists.

Transformations as code, and trust

The transform step has a well-known modern shape, popularized by tools such as dbt: each model is a single SELECT statement in a file under version control. A model refers to other models by name, so the tool derives the dependency graph (a DAG again) and builds them in order. Tests are declared next to the model: a key column must be unique and non-null, a status column may only hold known values, every order must point to an existing customer. Because transformations are code, they get code review, version history, CI and documentation generated from the same files. This is the same “treat it like software” discipline you will see for builds and reviews in the engineering practice chapter of the architecture course.

Data quality, contracts and lineage

Data breaks silently. Useful checks, roughly in order of cost-effectiveness: freshness (did today's data arrive?), volume (row count within a plausible range?), schema (same columns and types?), validity (no negative prices, dates in range), uniqueness and referential integrity, and distribution (the share of nulls suddenly jumped). Place checks between layers and let a failing check stop the pipeline or divert bad rows to a quarantine table, rather than publishing wrong numbers.

Checks catch problems after the fact. A data contract tries to prevent them at the source: the team that owns a dataset publishes an explicit, versioned agreement covering schema, meaning (units, time zones, nullability), freshness expectations and who to call. Producers then treat changes to it like a public API change (evolving contracts) instead of a private refactor that breaks six downstream teams. Contracts are as much an organizational practice as a tool; the technology merely makes violations visible.

Lineage is the map of where each table and column came from and what depends on it, collected from the orchestrator, query logs or the transformation tool. It answers two urgent questions: “this number looks wrong, which upstream table feeds it?” and “if I change this column, who breaks?” It is also how you find every copy of a sensitive field.

Analogy: a restaurant supply chain

Bronze is the loading dock: deliveries are logged exactly as they arrive, even the bruised vegetables. Silver is the prep kitchen, where produce is washed, sorted and portioned. Gold is the plated menu. Quality checks are the inspector at each handoff, a data contract is the written spec your supplier agreed to, and lineage is the label that tells you which farm the tomato came from when someone gets sick.

Where it breaks down: food is consumed once, while data can be re-cooked any number of times from the raw layer. That replayability is what makes data pipelines so forgiving when designed well.

Batch, streaming and the freshness trade-off

How often should data move? Batch ingestion moves a bounded chunk on a schedule (hourly, daily): simple, cheap, easy to re-run, but results lag. Streaming ingestion consumes events continuously from a log, and change data capture (CDC) turns a database's own commit log into such a stream. Streaming gives minutes or seconds of freshness at the price of more complexity: out-of-order events, state to manage, exactly-once concerns, always-on infrastructure. Table formats help bridge the two, because a streaming job can commit small batches (micro-batches) to the same table that nightly batch jobs read. The honest default for most analytics is the least fresh option the business can live with, and a surprising number of dashboards are fine with a day.

One common problem arises on the streaming side: frequent small commits create many small files, which makes queries slow because each file costs a request and a footer to read. Table formats include compaction jobs that rewrite many small files into fewer large ones, and those compaction commits are exactly the conflicting-rewrite case from our toy code.

Cost and governance

Object storage is cheap, so the bill is dominated by compute that scans data and by data movement. Levers that matter: store columnar compressed files; partition and sort data so queries read less; keep files reasonably large (compaction); expire old snapshots and delete orphans; avoid scanning columns you do not need; and watch for pipelines that nobody reads anymore, which cost money every night. Moving data between regions or clouds typically carries transfer charges, so keep compute near the data.

Governance is the set of rules about who may see what, and who is accountable. A shared catalog gives one place for table names, owners and descriptions; access control should work at table, column and sometimes row level; and sensitive columns can be masked or tokenized. The hardest case is personal data. Three tensions are worth knowing:

  • Immutability vs. deletion. Laws and policies may require deleting a person's data on request, but immutable files and time-travel snapshots deliberately keep history. Deleting a row means rewriting files and expiring old snapshots (and backups) before the data is truly gone. Design for this from the start; retrofitting it is painful.
  • ELT keeps raw data. If the bronze layer holds raw personal fields, all of your tables downstream inherit the risk. Minimizing, hashing or tokenizing at ingestion (a reason to prefer ETL for certain fields) shrinks the blast radius.
  • Copies multiply. Every derived table, extract and notebook export is another place the data lives. Lineage is how you find them all.

The security course treats these topics properly in Data Protection & Privacy; the data-platform angle is that your pipeline design decides how hard compliance will be.

Distributed systems connection

A lakehouse is a small distributed system made of parts you already know: immutable files and an append-only log (chapters 4 and 5), MVCC snapshots (chapter 12), and a single compare-and-swap that serializes commits. That last piece is exactly consensus in miniature: some component must decide who wins version N, and its failure modes are the table's failure modes. Pipelines add the other recurring theme, idempotence under retries, which is how at-least-once delivery becomes effectively-once results (chapter 19, and the sagas and outbox patterns of the architecture course). Once you see those ingredients, new data tools stop looking like magic.

Key takeaways

  • Analytics runs on a separate, columnar copy of operational data. ETL transforms before loading; ELT loads raw data and transforms inside the store, which is the common trend but not a rule.
  • Warehouses, lakes and lakehouses are points on a spectrum. A lakehouse adds warehouse-like guarantees to open files on object storage.
  • Open table formats (Iceberg, Delta, Hudi) add immutable metadata: snapshots and manifests (or a log/timeline) that define which files make up a table version.
  • A commit writes immutable data and metadata first, then makes one atomic publish guarded by optimistic concurrency; losers retry or abort depending on conflict.
  • Time travel and safe schema evolution come from immutability, at the cost of retention management; deleting personal data means expiring history too.
  • Orchestrated DAGs need idempotent tasks keyed by logical date so backfills and retries are safe.
  • Trust comes from tests, quality checks, contracts and lineage; most data failures are silent, not loud.

Check your understanding

Why can a plain directory of Parquet files on object storage not safely support a job that rewrites ten files?

  1. Parquet files cannot be rewritten
  2. There is no atomic way to swap many objects at once, so readers can see a mixture of old and new files after a crash or mid-job
  3. Object storage is too slow to read
  4. SQL cannot query Parquet
Each object can be replaced atomically, but a set of objects cannot. A table format adds metadata so "which files are the table" is decided by one atomic pointer update, and files not yet referenced are invisible.

Two writers both start from version 7 and both try to commit version 8. What should happen?

  1. Both succeed and the table has two version 8s
  2. Both fail, and the table is locked
  3. The later writer overwrites the earlier one
  4. One creates version 8; the other is rejected, then re-reads, checks for conflicts, and either retries as version 9 or aborts
Exactly one commit may own each version. The loser's earlier work is harmless because it was unreferenced. Appends that do not overlap can be rebased and retried; overlapping rewrites must be redone.

What makes a daily pipeline task safe to backfill for last Tuesday?

  1. It uses a logical date parameter and overwrites or merges that day's output, so repeating it gives the same result
  2. It reads now() to decide which day to process
  3. It appends rows to the output table each time it runs
  4. It runs only once and is never retried
Idempotent, date-parameterized tasks can be re-run any number of times. Using the wall clock or blind appends makes retries and backfills duplicate or shift data.

Time travel in a table format is cheap mainly because...

  1. The system keeps a full copy of the table for every version
  2. It replays the entire history of changes on each query
  3. Snapshots share immutable files, so an old version is just an older list of files that already exist
  4. The catalog stores the data inline
New snapshots reuse unchanged files from earlier ones, so extra history costs only new files and small metadata. The price is that old files cannot be deleted until old snapshots expire.

A user asks for their personal data to be deleted. Which statement about an immutable, time-travel-enabled table is most accurate?

  1. A DELETE statement removes the data from storage immediately
  2. The delete creates a new snapshot, but old snapshots and files still hold the data until they are expired and removed (and backups are handled)
  3. Time travel makes deletion impossible
  4. Deletion is only a concern for streaming pipelines
The logical delete is immediate, the physical one is not: history is retained by design. Compliance needs snapshot expiry, file cleanup and a plan for derived copies and backups.

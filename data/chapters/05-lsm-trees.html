LSM Trees & SSTables

The log from the last chapter has fast writes but needs every key in RAM and can't answer range queries. Keep the data sorted and both problems melt away, if you can find a way to produce sorted files from writes that arrive in random order. The answer, an in-memory buffer that is flushed to sorted files and merged in the background, powers LevelDB, RocksDB, Cassandra and many more.

Why this matters

Roughly speaking, there are two families of storage engine: the B-tree (chapter 6) and the log-structured merge tree, the LSM tree, which this chapter explains. If you know how an LSM tree behaves you can predict why Cassandra handles huge write loads, why a database sometimes stalls while "compacting", why deleting data doesn't free disk straight away, and why your read latency has a long tail. It is also the home of the Bloom filter, one of the most useful small ideas in all of systems.

Sorting is the missing ingredient

In chapter 4 every segment file held records in the order they were written. Now change one rule: each file holds its records sorted by key. A file like that, written once and never modified, is called a Sorted String Table, or SSTable (the name comes from Google's Bigtable paper; the keys and values are just strings of bytes).

Sorting looks like a small change, but it buys four things.

  1. Merging is cheap. Combining sorted files is the "merge" step of merge sort: look at the first record of each file, emit the smallest, advance. It reads each input once, sequentially, uses almost no memory, and works on files far bigger than RAM. If two files hold the same key, emit the one from the newer file and skip the other.
  2. The index can be sparse. In a sorted file you don't need an entry for every key. If you know block 7 starts at key emu and block 8 starts at hog, then fox must be in block 7 (if it exists at all). One index entry per block is enough.
  3. Range queries are sequential reads. "All keys from cub to emu" is a seek to one block and then a straight read. Neighbouring keys are neighbours on disk.
  4. Blocks compress well. Consecutive sorted keys tend to share long prefixes (user:000123, user:000124), and a block of related data compresses much better than scattered bytes. Engines typically compress each block (commonly with a fast algorithm like Snappy or LZ4, or Zstandard for a better ratio).

How tiny is "tiny"? A 64 MiB SSTable cut into 4 KiB blocks has 16,384 blocks. An index with one entry per block (say a 20-byte key plus an 8-byte offset) is under half a megabyte, small enough to keep in memory, and a binary search over it takes about 14 comparisons. Compare that with chapter 4's hash index, which needed an entry for every key.

Analogy: shelves in call-number order

A library's shelves are sorted by call number, which is why a catalogue entry can be so short: "the 500s start at bay 12". You walk to the right bay and scan a few spines. The sorted shelf also makes "everything about astronomy" a stroll along one shelf rather than a hundred separate trips. An SSTable is a shelf that is sorted once, when it is built, and never rearranged.

Where it breaks down: a library can slot a new book into the middle of a shelf. An SSTable cannot be edited at all; new data goes into new shelves, and the shelves are merged later.

Merging, concretely

You can try this on the command line right now. sort -m merges already-sorted files; -s keeps ties in the order the files were given, so listing the newer file first and then keeping the first line for each key gives "newest wins":

$ printf 'a 1\nc 2\nm 3\n' > older.txt
$ printf 'b 9\nc 20\nz 4\n' > newer.txt
$ sort -m -s -k1,1 newer.txt older.txt | awk '!seen[$1]++'
a 1
b 9
c 20
m 3
z 4

Sorted data from random writes: the memtable

Sorted files are wonderful, but writes arrive in whatever order users send them. We can't insert into the middle of a file on disk (that would be an in-place update, the thing we're avoiding). The trick is to do the sorting in memory, where inserting into the middle of a structure is cheap.

The memtable is an in-memory sorted structure, usually a balanced tree or a skip list (a linked list with extra "express lanes" of pointers that let you skip ahead, giving O(log n) lookup and insert; LevelDB and RocksDB use one by default). Every write goes into the memtable, which keeps its keys in order. When the memtable reaches a size limit (from a few megabytes to a few hundred, depending on configuration), the engine flushes it: it walks the structure in order and writes one new SSTable, sequentially. Then it starts an empty memtable.

Analogy: the sorted returns cart

Back at our library desk, imagine the returns cart has slots arranged in call-number order, and the librarian drops each returned book into the right slot. Dropping a book into a slot on a cart is quick, because the cart is small and within arm's reach (RAM). When the cart is full, an assistant wheels it in order past the shelving room and lays the whole batch onto a fresh, already-sorted shelf section, which is a single smooth sweep rather than a hundred trips. That is a flush. The cart is the memtable and the new shelf section is an SSTable.

Where it breaks down: if the building lost power, the books on the cart would still exist. The memtable lives in RAM, so a crash loses it, and that needs the next section.

The write-ahead log

RAM forgets when the power goes. If we acknowledged a write after putting it only in the memtable, a crash would lose everything not yet flushed, which could be seconds or minutes of data. So before touching the memtable, the engine appends the write to a plain, unsorted log on disk, the write-ahead log or WAL. It is chapter 4's log, used for just one job: after a crash, replay the WAL to rebuild the memtable. Once a memtable has been flushed into an SSTable, its WAL is no longer needed and is deleted.

Two refinements are worth knowing. First, while a full memtable is being written out, the engine freezes it (an immutable memtable) and gives new writes a fresh empty one, so writers don't wait for the flush. Second, the WAL has the same fsync trade-offs as chapter 4's log: sync every write for safety, or sync periodically and accept losing the last few milliseconds in a crash (see systems chapter 9). The WAL idea also appears, for a different structure, in chapter 13.

Reading: newest first

Where is the latest value of a key? Possibly in the memtable, possibly in any of the SSTables. They are searched from newest to oldest and the first hit wins, because newer data shadows older data:

  1. Look in the memtable (and the immutable memtable, if one is being flushed).
  2. Look in the newest SSTable, then the next newest, and so on.
  3. Stop at the first file that contains the key. A tombstone counts as a hit and means "deleted".
  4. If no file has it, the key doesn't exist.

This is the price of the design. A read may have to consult many files: that cost is called read amplification (the number of reads the engine performs for one read the user asked for). A key that doesn't exist is the worst case, because only after checking every file can the engine say "not found". Range scans pay too: they open an iterator on the memtable and on every file and merge them on the fly. Two things fight this cost: compaction (fewer files, below) and Bloom filters (skip files cheaply, next).

Bloom filters: a cheap "definitely not here"

A Bloom filter is a compact data structure that answers "is this key in the set?" with one of two answers:

  • "Definitely not." This answer is always right.
  • "Maybe." This answer is usually right, but sometimes wrong: a false positive.

It never gives a false negative: if a key was added, the filter will never say "definitely not" about it. That one-sided guarantee is exactly what an SSTable needs. A "definitely not" lets us skip a file with no disk I/O. A "maybe" costs one block read, which usually finds the key and occasionally (a false positive) wastes a read.

How it works

It is a row of m bits, all zero to begin with, plus k different hash functions. To add a key, compute its k hashes (each giving a bit position) and set those k bits to 1. To query, compute the same k positions: if any bit is 0 the key was never added; if all are 1 the key might have been (other keys may have set those bits).

Adding more keys sets more bits, so the filter gradually fills with ones and false positives become more likely. That trade-off is quantifiable.

The false-positive rate

With n keys inserted into m bits using k hashes, the probability that a particular bit is still 0 is about e−kn/m. A false positive needs all k probed bits to be 1, so (treating the bits as independent, which is an approximation):

p ≈ (1 − e−kn/m)k

For a fixed m/n (bits per key), the best choice of k is about (m/n) · ln 2 ≈ 0.69 · (m/n). At that optimum, about half the bits are set, and the rate becomes roughly 0.6185m/n. Turning that around: to reach a false-positive rate p you need about 1.44 · log2(1/p) bits per key.

Worked example: 10 bits per key

Take n = 1,000,000 keys and give the filter m = 10,000,000 bits (10 bits per key; that is only 1.25 MB). The best k is 10 × 0.693 ≈ 6.9, so use k = 7. Then kn/m = 0.7, e−0.7 ≈ 0.497, and

p ≈ (1 − 0.497)7 ≈ 0.5037 ≈ 0.0082, about 0.8% (the "roughly 1%" rule of thumb).

So a lookup of a key that is not in the file wastes a read less than 1% of the time. If a miss would otherwise check six SSTables, the expected number of wasted reads falls from 6 to about 0.05, a 100-fold saving, for 1.25 MB of memory per million keys. Commonly cited engine settings are about 10 bits per key; RocksDB and LevelDB both offer Bloom filters at that size.

I checked the formula by experiment. This script (in the "Try it" section) builds filters of different sizes for 100,000 keys and probes them with 200,000 keys that were never added:

The measured rates match the formula to within the noise, and there were no false negatives at all. Note the shape of the curve: at the optimum, each extra 5 bits per key or so cuts the false-positive rate by roughly a factor of ten (0.61855 ≈ 0.09), with diminishing returns for the memory spent, which is why about 10 bits per key is such a popular compromise.

What a Bloom filter does not do

"Maybe" is not "yes". And a filter helps only point lookups of keys that are absent from a file; if the key is in the file you still read the block. It cannot help a range scan (a filter over exact keys can't tell you whether any key lies between two bounds), though some engines add filters over key prefixes. And you can't remove a key from a classic Bloom filter, which suits SSTables perfectly: the file is immutable, so its filter is built once and thrown away with the file.

Compaction: keeping the pile small

Left alone, an LSM tree gets worse over time: flushes add files, reads must check more of them, overwritten values and tombstones pile up and waste space. The cure is compaction: a background process that merges SSTables (exactly the merge above), discards overwritten values and, when safe, tombstones, and writes the result as new files. The old files are then deleted. Different strategies decide which files to merge and when.

Size-tiered

Flushed files are grouped by size. When enough files of similar size accumulate (for example about four), merge them into one bigger file. Big files form over time, small ones keep arriving at the bottom. Writes are cheap, since each byte is rewritten only once per tier it climbs. But runs overlap in key range, so a read may check many files, and merging the biggest runs can temporarily need as much spare disk space as the data being merged. Cassandra has historically defaulted to this strategy.

Leveled

Files are organised into levels. New flushes land in level 0, where files may overlap. Below that, each level is a set of non-overlapping files covering the whole key space, and each level is allowed to hold about ten times as much as the one above (the typical default ratio). When a level exceeds its budget, the engine picks a file and merges it with the files in the next level whose key ranges overlap it, which is the yellow picture above. Because levels below L0 never overlap, a get needs at most one file per level. But data is rewritten every time it moves down a level, which makes write amplification high. LevelDB uses leveled compaction exclusively and RocksDB's default is a leveled style, while Cassandra and ScyllaDB offer it as a choice.

There are also specialised strategies; for example, for time-series data that expires by age, Cassandra offers a time-window strategy that keeps each window's data together so a whole file can be dropped when it expires. The best strategy depends on the workload.

Three amplifications and a trade-off

The central trade-off of every storage engine is visible as three ratios:

Write amplification
Bytes physically written to disk per byte the user wrote. In an LSM tree it comes from the WAL (1×), the flush (1×) and every compaction rewrite after that. Leveled compaction can rewrite each byte many times over its life; size-tiered, fewer.
Read amplification
Files or blocks read per user read. It is high when there are many overlapping files to check, and Bloom filters reduce it.
Space amplification
Bytes on disk per byte of live data. Stale versions and tombstones awaiting compaction inflate it, as does the spare space a big compaction needs.
Write amp.Read amp.Space amp.
Size-tiered LSMLowerHigher (many overlapping runs)Higher (stale data lingers; big merges)
Leveled LSMHigher (data is rewritten at each level)Lower (about a file per level)Lower
B-tree (chapter 6)Page-sized rewrites plus the WALLow and predictableSome wasted space in partly full pages

You can't minimise all three. Researchers call this the RUM conjecture (Read, Update, Memory): an access method that is good at two of reads, updates and memory overhead pays in the third. Compaction strategy is a dial between them. Bloom filters, for instance, buy lower read cost at the price of memory; leveled compaction buys lower read and space cost at the price of extra writes. There is no free option, only the one that matches your workload.

Deletes are writes, and reclaiming is slow

Just as in chapter 4, a delete in an LSM tree is a tombstone: a new record saying "this key is gone", written like any other. The old values stay in older SSTables, hidden because reads find the tombstone first. Disk space is only freed when a compaction merges the tombstone with the data it covers.

And a tombstone can only be dropped when the compaction has seen everything older it might hide. In a leveled tree that generally means when it reaches the bottom level; before that, it must be carried along, because an older value might still sit in a deeper file. So deleting a billion rows adds a billion tombstones first, and disk usage goes up before it goes down. Reads can get slower too, since an engine scanning a range has to step over every tombstone in it.

Deletes don't free space (yet)

If you drop a huge amount of data from an LSM-based database and the disk doesn't shrink, that is normal. It is also why using a database like a queue (write items, read them, delete them, repeat) is a known trap: the table fills with tombstones and reads wade through them.

In a replicated database there is a second reason to keep tombstones around. Suppose a delete reaches two replicas but a third was offline. If the first two compacted the tombstone away, the third would later offer the old value as if it were fresh, and the deleted data would come back (a "zombie"). Cassandra therefore keeps tombstones for a grace period, gc_grace_seconds, which defaults to ten days, so replicas have time to be repaired before a tombstone may be purged.

In the real world

  • Bigtable (Google, 2006) introduced the SSTable and memtable vocabulary. LevelDB, written at Google and open-sourced, is a small embeddable LSM key-value library. RocksDB is Facebook's fork of LevelDB with many additions (multiple compaction styles, multithreaded compaction, a large number of tuning options), and it is used as a building block inside other systems: for instance MyRocks (a MySQL storage engine), TiKV (the storage layer of TiDB) and CockroachDB's earlier storage engine, which was later replaced by Pebble, a RocksDB-inspired engine written in Go.
  • Apache Cassandra and ScyllaDB (a Cassandra-compatible database written in C++) store each node's data in a commit log (the WAL), memtables and SSTables, with several compaction strategies. Apache HBase, which follows Bigtable's design, keeps data in files on HDFS (the Hadoop distributed file system); because HDFS files can be appended to but not modified in place, an LSM design with immutable files is a natural fit there.
  • The original idea is from a 1996 paper, "The Log-Structured Merge-Tree" by O'Neil, Cheng, Gawlick and O'Neil, which is where the name comes from.

For a real-world story of choosing and living with an LSM-based database at huge scale, including the hot partitions and compaction pauses that bit them, read case 2: Discord's message store.

LSM versus B-tree: a preview

Most traditional relational databases (PostgreSQL, MySQL's InnoDB, SQLite) use B-trees, which update pages in place and keep each key in exactly one spot. Chapter 6 covers them in detail. In outline:

LSM treeB-tree
WritesSequential appends and merges; usually higher write throughputRandom in-place page writes plus a WAL; each small change rewrites a whole page
Point readsMay check several files (Bloom filters help)One path from root to leaf; predictable
LatencyBackground compaction can cause stalls and a long latency tailMore even, though page splits and checkpoints have their own costs
SpaceCompresses well; stale data lingers until compactionPartly empty pages (fragmentation)
Each key livesIn several places at once (old versions)In one place, which suits locking and transactions

Neither wins everywhere. "LSM is faster for writes" is a tendency, not a law, and it depends on the compaction strategy, the hardware and the workload.

Don't memorise "LSM = fast writes"

An LSM tree defers work: the write that returns quickly leaves a compaction debt to pay later. If writes arrive faster than compaction can keep up, the debt grows, reads slow down, and eventually the engine has to throttle or stall writers. Sustained throughput is what matters, not the speed of the first few seconds.

Build it yourself

Try it yourself: a toy LSM and a real Bloom filter in Python

Both scripts use only the standard library. First, minilsm.py: a memtable that flushes to sorted runs, newest-first reads, a tombstone, a range scan that merges all runs, and compaction.

Go deeper: the full source of minilsm.py optional, ~50 lines 
import bisect, heapq

TOMB = None                                     # a delete is a write of "no value"

class MiniLSM:
    def __init__(self, memtable_limit=3):
        self.limit = memtable_limit
        self.mem = {}                           # real engines: skip list / balanced tree
        self.runs = []                          # SSTables, newest LAST; each is a sorted list of (key, value)
        self.reads = 0

    def set(self, k, v):
        self.mem[k] = v                         # (a real engine appends to the WAL first)
        if len(self.mem) >= self.limit:
            self.flush()

    def delete(self, k):
        self.set(k, TOMB)

    def flush(self):
        self.runs.append(sorted(self.mem.items()))   # one sequential write of a sorted run
        self.mem = {}

    def get(self, k):
        if k in self.mem:
            return self.mem[k]
        for n, run in enumerate(reversed(self.runs)):    # newest SSTable first
            self.reads += 1
            i = bisect.bisect_left(run, (k,))
            if i < len(run) and run[i][0] == k:
                return run[i][1]                         # first hit wins, even a tombstone
        return None

    def scan(self, lo, hi):
        """Range query: merge memtable + every run, newest wins, hide tombstones."""
        sources = [sorted(self.mem.items())] + list(reversed(self.runs))   # newest first
        tagged = [[(k, age, v) for k, v in src] for age, src in enumerate(sources)]
        out, last = [], object()
        for k, age, v in heapq.merge(*tagged, key=lambda t: (t[0], t[1])):
            if k == last:
                continue                          # an older version of a key we already emitted
            last = k
            if lo <= k < hi and v is not TOMB:
                out.append((k, v))
        return out

    def compact(self):
        merged = {}
        for run in self.runs:                    # oldest to newest: later overwrite earlier
            merged.update(run)
        self.runs = [sorted((k, v) for k, v in merged.items() if v is not TOMB)]

Simplifications: no WAL, no files (each "SSTable" is an in-memory sorted list), no Bloom filter, and get returns None both for a missing key and for a tombstone. Lab 2 makes all of this real.

With a three-key memtable, eight operations produced two SSTables and left two keys in the memtable (including the tombstone for x). get c returns the newer value 20 after one SSTable read, because the newest file is searched first; get m had to go on to the older file, so it cost two. Now the Bloom filter. It uses double hashing (two hash values combined to produce k positions), a standard shortcut:

import hashlib, math

class Bloom:
    def __init__(self, m_bits, k):
        self.m, self.k = m_bits, k
        self.bits = bytearray((m_bits + 7) // 8)
    def _positions(self, key):
        h = hashlib.sha256(key.encode()).digest()
        h1 = int.from_bytes(h[:8], "big"); h2 = int.from_bytes(h[8:16], "big") | 1
        return [(h1 + i * h2) % self.m for i in range(self.k)]   # double hashing
    def add(self, key):
        for p in self._positions(key):
            self.bits[p // 8] |= 1 << (p % 8)
    def might_contain(self, key):
        return all(self.bits[p // 8] >> (p % 8) & 1 for p in self._positions(key))

n = 100_000
print("bits/key   k   predicted    measured")
for bits_per_key in (4, 8, 10, 14):
    m = n * bits_per_key
    k = max(1, round(bits_per_key * math.log(2)))
    b = Bloom(m, k)
    for i in range(n):
        b.add("present-%d" % i)
    trials = 200_000
    fp = sum(b.might_contain("absent-%d" % i) for i in range(trials))
    predicted = (1 - math.exp(-k * n / m)) ** k
    print("%5d   %3d   %8.4f%%   %8.4f%%" % (bits_per_key, k, predicted * 100, fp / trials * 100))
missing = sum(not b.might_contain("present-%d" % i) for i in range(n))
print("false negatives among the keys we added:", missing)

You will see why there is an optimum: too few hashes leave bits unused, too many fill the array with ones.

Distributed systems connection

In Cassandra-style databases (the Dynamo family you met in networking chapter 18), every replica of a partition runs its own LSM engine. A write is replicated to several nodes, and each applies it to its own commit log and memtable. That makes the tombstone problem a distributed one: a delete must outlive the slowest replica's catch-up, which is what gc_grace_seconds and repair are for. Immutable files also make distributed operations cheap: a new node can bootstrap by streaming whole SSTables, and a consistent backup is a set of hard links to files that can never change. And the whole tree is a nice example of the "log as source of truth" theme from chapter 4: partitioning the key space across nodes (chapter 16) simply gives each node a smaller, independent LSM tree, and a hot partition means one node's compaction is overloaded, as case 2 shows.

Key takeaways

  • An SSTable is an immutable file of records sorted by key. Sorting makes merging cheap and sequential, allows a small sparse index (one entry per block), makes range scans fast, and helps compression.
  • Writes go to a WAL (for durability) and a sorted in-memory memtable; a full memtable is flushed as a new SSTable and its WAL discarded. Crash recovery replays the WAL.
  • Reads check the memtable, then SSTables from newest to oldest; the first hit (including a tombstone) wins. Missing keys are the worst case.
  • A Bloom filter says "definitely not here" or "maybe". It has no false negatives; with n keys, m bits and k hashes, p ≈ (1 − e−kn/m)k, about 1% at 10 bits per key with k = 7.
  • Compaction merges files, drops overwritten values and (when safe) tombstones. Size-tiered gives lower write amplification and worse reads and space; leveled the reverse.
  • The central trade-off is write, read and space amplification (the RUM conjecture): improving two costs you in the third.
  • Deletes are tombstones, so space is reclaimed only after compaction, and in replicated systems tombstones must outlive replica repair.
  • LevelDB, RocksDB, Cassandra, ScyllaDB and HBase are LSM-based; B-trees (chapter 6) make the opposite choices.

Which is the best reason that keeping each file sorted by key helps compaction?

  1. Sorted files are smaller because duplicates disappear automatically
  2. The operating system sorts files for free
  3. Sorted files can be merged in one sequential pass with almost no memory, like the merge step of merge sort
  4. Sorted files do not need to be written to disk
A merge reads each input once, in order, and emits output in order, so it works for files far larger than RAM. When two files hold the same key, the newer one wins. Sorting does not by itself remove duplicates.

An LSM engine acknowledges a write after putting it in the memtable and appending it to the WAL. Why is the WAL there?

  1. The memtable lives in RAM; after a crash the WAL is replayed to rebuild it, so acknowledged writes are not lost
  2. The WAL is how the memtable stays sorted
  3. The WAL lets readers find keys faster than the memtable
  4. The WAL replaces the SSTables
The WAL is an unsorted append-only log used only for crash recovery, and it is discarded after the memtable has been flushed to an SSTable. Sorting is the memtable's job.

  2. The key was probably deleted

Bloom filters have no false negatives, only false positives. "Maybe" means the file has to be checked, and it occasionally turns out to be a wasted read.

  3. About 0.0001%
  4. Zero, because the number of hashes is optimal
p ≈ (1 − e−0.7)7 ≈ 0.008. Optimal k minimises the rate but cannot make it zero; to go lower you need more bits per key.

You delete a large table from an LSM-based database, and disk usage goes up instead of down. Why?

  1. Deletes are copied to a backup before they take effect
  2. The database is corrupted
  3. Each delete writes a tombstone, and the old data's space is reclaimed only when compaction merges them, which happens later
  4. Bloom filters are being rebuilt for the deleted keys
The old values stay in immutable SSTables until compaction rewrites them without the deleted keys. In replicated databases the tombstones also have to be kept for a grace period.

Compared with size-tiered compaction, what does leveled compaction typically trade?

  1. Higher write amplification in exchange for lower read and space amplification
  2. Lower write amplification in exchange for more read amplification
  3. Nothing: it is better on every measure
  4. It removes the need for a WAL
Leveled keeps non-overlapping files per level, so reads check about one file per level and little stale data lingers, but data is rewritten at each level. This is the RUM trade-off in action.

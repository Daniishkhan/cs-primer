Start Here

Every app you have ever used is a thin skin over a database. This course opens that box: how data is modelled, how it is laid out on disk, how it stays correct when many people change it at once, and what happens when one machine is no longer enough. We start by following a single query all the way down and back up.

A note from your mentor

If you listen to a senior engineer in a design review, you will notice something: most of the arguments are not about code. They are about data. Where does it live? Who may change it? How fresh must a read be? What happens to it if a machine dies? That is why this course exists. The networking course taught you how bytes move between machines, and the systems course taught you what one machine does with them. This course is about the thing those machines are for: keeping data safe, finding it fast, and keeping it correct. Nothing here needs more than that background, and every new word is explained when it first appears.

Why this matters

Almost every system-design question is a data question in disguise. "Design a URL shortener" is: what is the key, where is the mapping stored, how do we read it a million times a second? "Design a chat app" is: how do we store messages, order them, and replicate them? When you can answer what is the data, how is it read and written, and what must never be lost or wrong, the boxes and arrows of a design nearly draw themselves. Everything else (queues, caches, load balancers) exists to serve that answer.

The life of one query

Let's follow one tiny query from the application to the disk and back. We ask for a user by email:

SELECT name FROM users WHERE email = ?

The ? is a placeholder: the application sends the SQL text and the value separately, so the value can never be mistaken for SQL. Then we change data with an UPDATE inside a transaction (a group of changes that succeed or fail together), and watch the effects ripple outwards. Each step names the chapter where you will learn it properly. Colours follow the course convention: blue is memory, orange is the write-ahead log, purple is an index, yellow is the query we are following and green is the writing transaction.

Step through

The life of one query

  1. Client to connection. The application sends the query text over a TCP connection it opened earlier. Connections are expensive to set up (a handshake, often TLS and a login), which is why apps keep a pool of them open. (Networking: ch. 8, ch. 12.)
  2. Parse, then plan. The database parses the SQL text into a tree, checks the table and columns exist, and then the planner decides how to answer. SQL says what you want, never how. Because an index on email exists, the planner chooses an index lookup instead of reading every row. Without one, it would scan the whole table. (Query execution, ch. 8; indexes, ch. 7.)
  3. Descend the B-tree. The index is a B-tree: a shallow, wide tree of fixed-size pages. Looking up one email means reading the root page, one internal page and one leaf page. Even a table with a hundred million rows is typically only three or four levels deep. (B-trees, ch. 6.)
  4. Check the buffer pool. Each page the descent needs is first looked up in the buffer pool, the database's own cache of disk pages in RAM. A hit costs on the order of 100 nanoseconds. Hot pages such as the root almost always hit. (ch. 6; the memory ladder from systems ch. 2.)
  5. Or read from disk. On a miss, the page is read from the data file. Even if the database does not manage its own cache, the operating system's page cache sits in between. An SSD read takes roughly tens to a hundred microseconds, around a thousand times slower than RAM, so the miss rate often decides the query's speed. (ch. 6; systems ch. 2.)
  6. The row comes back. The leaf holds a pointer to the table row (or the row itself, depending on the engine). The executor reads name and streams the result to the client, one row here. Total time: a fraction of a millisecond if the pages were cached.
  7. Now a write. The application opens a transaction and sends UPDATE users SET email = ... WHERE id = .... It is parsed, planned and located exactly like the read. But a write has to be durable and isolated from other transactions, and that changes everything that follows. (Transactions, ch. 10.)
  8. Append to the write-ahead log. The database changes the page in the buffer pool (the page is now "dirty") and, before that, appends a description of the change to the write-ahead log (WAL), a sequential file on disk. The data file itself will be updated lazily later. (ch. 10, ch. 13.)
  9. Commit means fsync. When the application says COMMIT, the database calls fsync on the log and waits until the disk confirms. This is the "saved is not saved" problem from systems ch. 9. Only after it returns does the client hear "committed". If the machine loses power now, recovery replays the log and the change is still there. (ch. 13.)
  10. Replicate. The leader ships its log to followers, which apply the same changes. Followers give you more read capacity and a spare copy if the leader dies, but they may lag a little behind, which causes strange anomalies. (ch. 15; background in networking ch. 18.)
  11. Invalidate the cache. If the application caches users in something like Redis, the old email is now stale. The application deletes or updates that entry. Forgetting this step, or doing it in the wrong order, is one of the most common bugs in real systems. (ch. 14.)
  12. Tell everyone else. The same log that feeds the followers can feed change data capture (CDC): a stream of change events that keeps a search index, a data warehouse or another service in sync. (ch. 19.)

That is twelve steps and most of this course. Notice how much happens beyond "run the SQL". Reads are mostly about finding things without touching the slow layers. Writes are mostly about not losing things, and then telling everyone.

Analogy: a library

The books on the shelves are the data file, and each shelf is a page. The catalogue cards are an index: you do not walk every shelf to find a title, you look it up in the catalogue and go straight to the right one. The librarian's desk is the buffer pool, where the books people keep asking for stay within reach. Every change is first written in a ledger at the desk (the log), and only later re-shelved. If the library floods overnight, the ledger tells you exactly what to put back.

Where it breaks down: a library has one person at the desk. A database has thousands of clients changing things at the same moment, and much of the course is about keeping that from turning into chaos.

Common misconception

"A database is a big spreadsheet that I query." A spreadsheet is a picture of data. A database is a machine that keeps a promise: committed data survives, concurrent users do not corrupt each other, and queries find answers without reading everything. The data file is the least interesting part. The log, the cache, the planner and the concurrency rules are where the engineering lives.

The big trade-offs

Nearly every design decision in this course is a point on one of four dials. When we meet a technique, ask which dial it turns and what it costs.

Read-optimised vs write-optimised

Keeping data sorted and indexed makes reads fast, but every write has to update that structure. Appending to a log makes writes fast, but reads have more to search. B-trees and LSM trees sit on opposite sides of this dial (ch. 5, 6).

Consistency vs availability and latency

Making every copy agree before answering is correct but slow, and it stops working during a network failure. Answering from whichever copy is nearest is fast and available, but may be stale (ch. 11, 15).

Normalised vs denormalised

Storing each fact once avoids contradictions, but answering a question needs joins. Copying data into several places makes reads cheap but writes must keep all the copies in step (ch. 2, 14).

OLTP vs OLAP

Transactional workloads touch a few rows at a time, and many users at once. Analytical workloads scan millions of rows to compute totals. They want different storage layouts, so large companies run both kinds of systems (ch. 9, 18).

Try it yourself

Try it yourself: make a tiny database and look inside

SQLite is a complete SQL database that is just a library and one file. It ships with macOS (the sqlite3 command), and Python includes it in the standard library, so this works on Linux and Windows too. Nothing here needs sudo, and we delete the file at the end. Your timestamps and sizes will differ slightly.

$ cd $(mktemp -d)        # a scratch folder
$ sqlite3 tiny.db "CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, email TEXT);
INSERT INTO users (name, email) VALUES ('Asha','asha@example.com'),('Ben','ben@example.com'),('Chen','chen@example.com');
CREATE INDEX idx_users_email ON users(email);"
$ ls -l tiny.db
-rw-r--r--  1 you  wheel  12288 Oct 12 21:51 tiny.db
$ sqlite3 tiny.db "PRAGMA page_size; PRAGMA page_count; SELECT name FROM users WHERE email = 'ben@example.com';"
4096
3
Ben
$ sqlite3 tiny.db "EXPLAIN QUERY PLAN SELECT name FROM users WHERE email = 'ben@example.com';"
QUERY PLAN
`--SEARCH users USING INDEX idx_users_email (email=?)
$ xxd tiny.db | head -2
00000000: 5351 4c69 7465 2066 6f72 6d61 7420 3300  SQLite format 3.
00000010: 1000 0101 0c40 2020 0000 0003 0000 0003  .....@  ........
$ grep -a -o 'ben@example.com' tiny.db
ben@example.com
ben@example.com

The same thing from Python, if you prefer (python3, standard library only):

$ python3 -c "import sqlite3; db = sqlite3.connect(':memory:'); db.execute('CREATE TABLE users (name TEXT, email TEXT)'); db.execute('INSERT INTO users VALUES (?, ?)', ('Ben', 'ben@example.com')); print(db.execute('SELECT name FROM users WHERE email = ?', ('ben@example.com',)).fetchall())"
[('Ben',)]

Look at what you just saw. The "database" is one ordinary file of 12,288 bytes: exactly 3 pages of 4,096 bytes (the table, the index, and the schema page). It starts with the text SQLite format 3. The email appears twice in the raw bytes, once in the table and once in the index, which is the price of the index: extra space, and extra work on every write. And EXPLAIN QUERY PLAN shows the planner choosing the index, which is step 2 of the stepper made visible. (Try dropping the index and re-running the plan: it will say SCAN users.) Remember to delete the scratch folder when you are done.

Distributed systems connection

Every step in the second half of the stepper is a distributed-systems problem waiting to happen. Replication to followers means copies that disagree for a while. Cache invalidation is a second copy of the truth that can be wrong. A CDC event is a message that might be delivered twice or late. The single-machine database from this chapter gives you one clean timeline. The rest of the course is about what you keep, and what you give up, when you refuse to stay on one machine.

Key takeaways

  • A query is parsed, planned, executed against an index or a scan, and answered from cached pages or from disk. Most of the speed comes from avoiding disk.
  • SQL is declarative: the planner picks the access path, and an index changes which one it can choose.
  • A committed write is durable because the log is flushed with fsync before the database says "done".
  • After a write, changes ripple out: to followers, caches and downstream systems. Each is a copy that can lag or go wrong.
  • Four dials recur: read vs write optimised, consistency vs availability and latency, normalised vs denormalised, OLTP vs OLAP.
  • Almost every system-design question is a data question: what is the data, how is it accessed, what must never be lost or wrong?

Check your understanding

The planner sees WHERE email = ? and an index on email exists. What does that change?

  1. The query now returns different results
  2. The database must rewrite the table in sorted order
  3. The planner can find the row by descending the index instead of scanning the whole table
  4. The query no longer needs the buffer pool
An index changes how the answer is found, never what the answer is. That is what "declarative" means. The index still lives in pages, so the buffer pool is still used, but only a handful of pages are touched instead of the whole table.

Why does a database append to the write-ahead log and fsync it at commit, rather than just writing the changed data page?

  1. A sequential log append is cheap, and once it is on disk the change survives a crash even if the data pages have not been written yet
  2. Log files are never lost, unlike data files
  3. It makes the next SELECT faster
  4. Because followers cannot read the data file
The log gives durability cheaply: one sequential write and one flush. The data pages can be written later, in the background, because recovery can rebuild them from the log. The log is also what replication and CDC read, but that is a bonus, not the reason.

Right after a committed UPDATE, which of these is most likely to hold the old value for a while?

  1. The write-ahead log
  2. The leader's buffer pool
  3. The leader's data file, once recovery has run
  4. An application cache and a lagging follower
The leader's own structures are updated as part of the transaction. Copies made elsewhere (a cache entry the app did not invalidate yet, or a follower that has not applied the log) are the ones that can serve stale data. This is why caching and replication each get their own chapter.

A data warehouse sums a year of sales, while a shop's checkout updates one order at a time. Which trade-off dial describes the difference?

  1. Normalised vs denormalised
  2. OLTP vs OLAP
  3. Consistency vs availability
  4. Read-optimised vs write-optimised, and nothing else
The checkout is online transaction processing (OLTP): small, concurrent reads and writes. The sum over a year is online analytical processing (OLAP): large scans and aggregates. They want different storage layouts, which is why chapter 9 introduces column stores.

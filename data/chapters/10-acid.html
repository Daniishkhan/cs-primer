Transactions & ACID

A single business action almost always means several reads and writes: take money out of one account, put it into another. A transaction is the database's way of letting you wrap those steps in a box and say "all of this, or none of it". In this chapter you will learn exactly what the four ACID letters promise, which of them are really the database's job, and what they stop promising the moment your system has more than one database.

Why this matters

Transactions are the most interview-relevant and most misunderstood idea in databases. People say "it's ACID" as if it were a single yes/no feature, when each letter is a separate promise with its own mechanism, its own cost, and its own fine print. Knowing the fine print is how you decide whether a payments ledger can live in one SQL database (yes, easily), whether a "transfer" that touches two services can be made safe (not by a transaction alone), and whether it is safe to retry a request that timed out. The next two chapters take the "I" apart in detail; this one gives you the frame to hang them on.

The problem: a transfer is two writes

Picture a bank. Alice has 100 and Bob has 50, and Alice wants to send Bob 30. In the books that is two changes: Alice's balance goes from 100 to 70, and Bob's goes from 50 to 80. In database terms it is two UPDATE statements. The total money in the bank must stay 150 at all times that anyone can observe.

Analogy: the bank teller and the paper ledger

A teller handles your transfer with two pen strokes in the ledger: cross out Alice's old balance and write 70, cross out Bob's and write 80. If the fire alarm goes off between the two strokes, the bank is left with 120 in its books and 30 has simply vanished. A careful bank therefore never lets a teller do half a transfer: the teller either finishes both entries and stamps the slip "done", or the unstamped slip is thrown away.

Where it breaks down: a real bank can recover from a vanished 30 months later by reconciling against other records and posting a correcting entry. A database has no such second chance for most applications: it must make the half-done state impossible, not repairable. Also, a real teller works alone; databases serve thousands of tellers at once, which is where isolation (chapter 11) comes in.

What can go wrong between those two writes? Quite a lot: the database process is killed, the machine loses power, the second statement fails a constraint (Bob's account was closed), or the application crashes and never sends it. Each leaves the world half changed. The fix is a transaction: a group of reads and writes that the database treats as one logical unit. You open it with BEGIN, do your work, and end it with either COMMIT (make everything permanent) or ROLLBACK (undo everything, as if it never happened).

Step through

A transfer interrupted by a crash

  1. Start. Alice has 100, Bob has 50; the bank holds 150 in total. Left: two plain statements. Right: the same two statements inside BEGIN ... COMMIT.
  2. The debit runs. On the left the update is its own committed transaction (autocommit), so Alice's 70 is on disk and the bank looks 30 short. On the right the update is inside an open transaction: it is provisional, and other sessions still see 100.
  3. The crash. The server dies before the credit statement. Nothing has told the database what the debit was part of.
  4. Restart. Left: the committed debit stays; the total is 120 and no error was ever raised. Right: recovery finds a transaction with no commit record and undoes it, so the bank is back to 100 + 50.
  5. Retry. The application, unsure what happened, runs the transfer again. Left: Alice is debited a second time (40) and the total is still 120. Right: the whole transfer runs from a clean state and commits: 70 + 80 = 150.

You can reproduce the same experiment with SQLite in a few lines. The script below applies the debit, then kills its own process with os._exit (no cleanup, no goodbye, a stand-in for a power cut). The first run uses no transaction. The second begins one first.

import sqlite3, os, sys
path, mode = sys.argv[1], sys.argv[2]
con = sqlite3.connect(path, isolation_level=None)    # None: we control BEGIN/COMMIT ourselves
if mode == "tx":
    con.execute("BEGIN")
con.execute("UPDATE accounts SET balance = balance - 30 WHERE name = 'alice'")
os._exit(1)      # crash right here: the credit to bob never happens, and there is no COMMIT

A small driver (not shown) recreated the table with alice 100 and bob 50 before each run, ran crash.py, then asked a new connection for SELECT name, balance, (SELECT SUM(balance) FROM accounts) FROM accounts:

crashed (notx), exit 1
[('alice', 70, 120), ('bob', 50, 120)]
crashed (tx), exit 1
[('alice', 100, 150), ('bob', 50, 150)]

Each output row is (name, balance, total_of_all_balances). Without a transaction the total is 120: thirty units of money evaporated, permanently, with no error anywhere. With a transaction the next connection finds the half-finished work undone and the total is still 150. (SQLite does this by keeping a rollback journal; when the next process opens the file it sees the unfinished transaction and undoes it. Other databases use a write-ahead log. Chapter 13 shows how.)

ACID, one letter at a time

The word ACID was coined in the early 1980s (Haerder and Reuter) as a memorable name for four properties a transaction system should have. It stands for Atomicity, Consistency, Isolation, Durability. The acronym is a nice mnemonic, but the letters are not equal peers, and the definitions are looser than the name suggests. Here is each one stated precisely.

Atomicity: all or nothing, on failure

Atomicity says that if a transaction fails part-way (it hits an error, the process crashes, you call ROLLBACK), then every change it made is undone, so the database looks as if the transaction never started. Others never see "half a transaction" persisted. A better name is abortability: the ability to abort a transaction and have it leave no trace.

Two meanings of "atomic"

In systems chapter 12, an atomic operation was one that no other thread can see half-done: it is about concurrency. In ACID, atomicity says nothing about concurrent transactions at all. It is about failure: what survives if something dies in the middle. What stops two concurrent transactions seeing each other's partial work is the I, isolation. Mixing these up is the single most common ACID confusion in interviews.

Consistency: your rules, kept true

Consistency in ACID means the database moves from one valid state to another: your invariants (statements that should always be true, such as "no account balance is negative" or "every order has a customer") hold before and after each transaction. This is the odd letter out, because the database cannot know your business rules by itself. It can enforce the ones you declare, with CHECK, UNIQUE, NOT NULL and foreign-key constraints, and it can undo a transaction that violates them. But if your code decrements the wrong account, no database will notice. Atomicity, isolation and durability are properties the database provides; consistency is a property your application relies on the other three to preserve. (The word is overloaded: replica "consistency" in chapter 15 and networking chapter 18 is a completely different idea.)

Isolation: concurrent transactions don't see each other's partial work

Isolation is about what happens when transactions run at the same time. The ideal is that each behaves as if it ran alone, one after another. Real databases offer a menu of weaker, faster levels, and the strength you actually get depends on which level you choose and which product you use. That menu, and the bugs each weaker level lets through, is the entire subject of chapter 11; chapter 12 shows how they are built. For now: "ACID" does not tell you how strong the I is.

Durability: committed means it survives a crash

Durability promises that once the database has told you a transaction committed, the data will not be lost, even if the machine loses power a millisecond later. The mechanism is the one from systems chapter 9: before acknowledging COMMIT, the database appends the change to a write-ahead log and forces it to stable storage with fsync (chapter 13 covers the details). Be careful with the word, though. Durability is relative to a failure you imagine. A single disk survives a process crash but not a destroyed machine; replication to another machine survives the machine but not necessarily a fire in the data centre. And many databases let you trade it away on purpose: Postgres has synchronous_commit = off, which can lose the last few moments of acknowledged commits on a crash (but does not corrupt the database), in exchange for lower latency.

Common misconception

"The database is ACID, so my feature is safe." ACID is a set of building blocks, not a guarantee about your program. Two clients can still lose an update at the default isolation level of most databases (chapter 11); a retry can still apply a payment twice (below); and your invariant is only preserved if you expressed it as a constraint or put the check inside the right transaction. The database keeps its promises; you still have to ask for the right ones.

Single-object versus multi-object operations

Not every operation needs BEGIN. A single UPDATE on a single row is already atomic and durable by itself: a crash cannot leave the row half-written. Databases also give you single-statement tools that read, compute and write in one indivisible step, which is exactly the cure for the lost-update pattern from systems chapter 11:

import sqlite3
con = sqlite3.connect(":memory:", isolation_level=None)
con.execute("CREATE TABLE seats (id INTEGER PRIMARY KEY, holder TEXT)")
con.execute("INSERT INTO seats VALUES (1, NULL)")
con.execute("CREATE TABLE counters (n INTEGER)"); con.execute("INSERT INTO counters VALUES (0)")

# Atomic increment: the database reads, adds and writes as one step. No lost updates.
con.execute("UPDATE counters SET n = n + 1"); con.execute("UPDATE counters SET n = n + 1")
print("n =", con.execute("SELECT n FROM counters").fetchone()[0])

# Compare-and-set: change the row only if it still looks the way we expect.
for who in ("alice", "bob"):
    cur = con.execute("UPDATE seats SET holder = ? WHERE id = 1 AND holder IS NULL", (who,))
    print(who, "rows changed:", cur.rowcount)
print(con.execute("SELECT * FROM seats").fetchall())
n = 2
alice rows changed: 1
bob rows changed: 0
[(1, 'alice')]

The conditional UPDATE ... WHERE holder IS NULL is the database version of the compare-and-swap you met in systems chapter 12. The row count tells you whether you won: Alice's update changed one row, Bob's changed none, so Bob knows the seat was taken without ever needing a lock of his own. Some document and key-value stores offer only this kind of single-object atomicity (Cassandra's "lightweight transactions" are conditional updates of this style), and for plenty of workloads that is enough.

You need multi-object transactions when one logical change must touch several rows, tables or documents together:

  • a transfer between two accounts (our example);
  • a foreign-key relation: insert the order and its order lines, so that no line points at a missing order;
  • denormalised or duplicated data: the unread-count column must change along with the message row;
  • secondary indexes: updating a row also means updating every index on it (chapter 7). The database does this inside the same atomic unit so the index never disagrees with the table, and this is invisible to you only because transactions exist.

Some NoSQL systems skipped multi-object transactions for a long time because they are hard to provide across machines. MongoDB, for example, guaranteed atomicity only within a single document until multi-document transactions arrived in version 4.0. The consequence for you as a user is practical: if the store has no cross-object transaction, you must design the data so each important change touches one object, or build your own repair logic.

BEGIN, COMMIT, ROLLBACK and autocommit

If you never type BEGIN, you are still in a transaction: most databases run in autocommit mode, where each statement is its own tiny transaction that commits as soon as it finishes. That is why the first crash experiment above lost money: the debit was a committed transaction by itself. To group statements you must begin explicitly. Here is a full run with SQLite and Python, including a transfer that violates a rule and is rolled back:

import sqlite3
con = sqlite3.connect(":memory:", isolation_level=None)   # None = we issue BEGIN/COMMIT ourselves
con.execute("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER NOT NULL CHECK (balance >= 0))")
con.executemany("INSERT INTO accounts VALUES (?, ?)", [("alice", 100), ("bob", 50)])

def show(label):
    print(f"{label:<28}", con.execute("SELECT name, balance FROM accounts ORDER BY name").fetchall())

show("start")
con.execute("BEGIN")
con.execute("UPDATE accounts SET balance = balance - 30 WHERE name = 'alice'")
con.execute("UPDATE accounts SET balance = balance + 30 WHERE name = 'bob'")
con.execute("COMMIT")
show("after committed transfer")

con.execute("BEGIN")
try:
    con.execute("UPDATE accounts SET balance = balance + 500 WHERE name = 'bob'")
    con.execute("UPDATE accounts SET balance = balance - 500 WHERE name = 'alice'")   # violates CHECK
    con.execute("COMMIT")
except sqlite3.IntegrityError as e:
    print("error:", e)
    con.execute("ROLLBACK")
show("after rolled-back transfer")
start                        [('alice', 100), ('bob', 50)]
after committed transfer     [('alice', 70), ('bob', 80)]
error: CHECK constraint failed: balance >= 0
after rolled-back transfer   [('alice', 70), ('bob', 80)]

Notice what the rollback did: Bob's balance had already been raised by 500 when Alice's debit failed, and the ROLLBACK took that back too. Without the transaction, Bob would have kept 500 free dollars. This is atomicity and consistency cooperating: the CHECK constraint detects the bad state, atomicity makes sure the half-applied work disappears.

Driver quirks

Python's sqlite3 module has its own legacy rules about when it silently opens a transaction (before INSERT/UPDATE/DELETE, but not before SELECT), and Python 3.12 added an autocommit attribute to make this explicit. We pass isolation_level=None in these examples so that what you type is what runs. Every language's driver has similar quirks, so the first thing to check in an unfamiliar codebase is where the transaction boundaries actually are. Also, a failed statement does not mean the same thing everywhere: SQLite undoes just the failing statement and leaves the transaction open, while Postgres marks the whole transaction as failed and refuses further commands until you issue ROLLBACK.

Retrying aborted transactions, safely

Transactions can abort for reasons that are not your fault: a deadlock victim (chapter 12), a serialization failure at a strict isolation level (chapter 11), a dropped connection, a failover. The natural reaction is to retry, and because an aborted transaction leaves no trace, retrying a whole transaction is exactly what atomicity makes safe. But retries have sharp edges:

  • Retry the transaction, not the statement. Re-run it from BEGIN, including any reads and decisions, since the data may have changed.
  • Don't retry permanent errors. A constraint violation or a syntax error will fail the same way forever. Retry only transient ones (deadlock, serialization failure, lost connection).
  • Back off. If the database is overloaded, immediate retries make it worse. Use exponential backoff with jitter, as in networking chapter 16.
  • Side effects outside the database don't roll back. If the transaction sent an email before aborting, a retry sends another.
  • The lost acknowledgement. The hardest case: the client sent COMMIT, the database committed, and the reply never arrived. From the client's side this is indistinguishable from "it failed".

The cure is the same idempotency idea from networking chapter 16: make doing it twice the same as doing it once. In a database the cleanest trick is to give each logical request an id and record that id inside the same transaction as the effect, behind a unique constraint. If the request is repeated, the insert of the id fails, the transaction rolls back, and the money moves only once:

import sqlite3
con = sqlite3.connect(":memory:", isolation_level=None)
con.execute("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER NOT NULL)")
con.execute("CREATE TABLE transfers (request_id TEXT PRIMARY KEY)")
con.execute("INSERT INTO accounts VALUES ('alice', 100), ('bob', 50)")

def transfer(request_id, amount):
    con.execute("BEGIN")
    try:
        con.execute("INSERT INTO transfers VALUES (?)", (request_id,))   # fails if already applied
        con.execute("UPDATE accounts SET balance = balance - ? WHERE name = 'alice'", (amount,))
        con.execute("UPDATE accounts SET balance = balance + ? WHERE name = 'bob'", (amount,))
        con.execute("COMMIT")
        return "applied"
    except sqlite3.IntegrityError:
        con.execute("ROLLBACK")
        return "duplicate, ignored"

for attempt in range(3):
    print("attempt", attempt + 1, "->", transfer("req-42", 30))
print(con.execute("SELECT * FROM accounts ORDER BY name").fetchall())
attempt 1 -> applied
attempt 2 -> duplicate, ignored
attempt 3 -> duplicate, ignored
[('alice', 70), ('bob', 80)]

Three attempts, one transfer. The trick works only because the id and the money movement share one atomic unit: if they were separate commits, a crash between them would bring the old problem back. Payment APIs expose the same pattern to clients as an idempotency key header. Studio 2 builds a ledger around it.

What ACID does not give you across services

Everything above is about one database. Real systems are rarely that tidy. Consider placing an order: the Orders service writes an order row, the Payments service charges a card, and the Shipping service books a courier. Each service has its own database, and each database is ACID inside its own walls. But there is no single BEGIN that spans all three.

If the payment succeeds and the shipping call times out, you are in a state no transaction can roll back for you: the card has been charged. Two families of answers exist, both belonging to later courses, so here is just the preview:

  • Distributed transactions such as two-phase commit make several databases agree to commit or abort together, using a coordinator. They exist and work, but they hold locks while waiting on the network, a crashed coordinator can leave participants stuck, and they make the whole system as available as its weakest member.
  • Sagas (briefly mentioned in networking chapter 21) give up atomicity: each service commits locally, and if a later step fails the earlier ones are undone by explicit compensating actions (refund the card, cancel the order). The in-between states are visible to others, so you design for them. The outbox pattern in chapter 19 is how a service reliably publishes the events a saga needs.

The practical lesson for design: keep things that must change together inside one database as long as you can. The best distributed transaction is the one you avoided by choosing your service boundaries well.

Go deeper: how a database can undo your work optional

Atomicity needs the database to remember how to undo each change until commit, and durability needs it to remember how to redo each committed change after a crash. Two classic mechanisms do this. A write-ahead log records every change on disk before the data pages themselves are changed, so after a crash the database can replay the committed ones and skip the uncommitted ones. An undo log (or keeping the old row version around, as in chapter 12) lets the database revert uncommitted changes that did reach the data pages. Commit itself is a single tiny act: write a "commit" record to the log and flush it. Everything before that record is provisional; once it is on disk the transaction is durable. That single flush is why the atomic switch from "not committed" to "committed" can be as cheap as one disk write, and why chapter 13 on recovery is mostly about reading the log.

Distributed systems connection

Almost every distributed-systems problem in this course is a transaction problem stretched over a network. A replica that has applied half of a transaction is an atomicity problem; two datacentres accepting writes to the same row is an isolation problem; acknowledging a write that is not yet on a second machine is a durability problem. And the retry-with-idempotency-key pattern you just built is how every well-designed API survives networking's "at least once" delivery. When you reach consensus you will see how a group of machines agrees on the single order of operations that lets a distributed database pretend to be one machine with ACID transactions, at a price paid in latency.

Key takeaways

  • A transaction groups several reads and writes into one unit: BEGIN, then COMMIT (keep it all) or ROLLBACK (discard it all). Outside an explicit BEGIN, most databases autocommit each statement.
  • Atomicity is all-or-nothing on failure (abortability). It is not the concurrency meaning of "atomic".
  • Consistency means your invariants hold after each transaction. It is mostly your job: constraints can enforce rules you declare, but the database can't invent them.
  • Isolation is how much concurrent transactions are kept apart. Its strength depends on the level and the product (chapters 11 and 12).
  • Durability means committed data survives a crash, via a write-ahead log and fsync. It is always relative to a failure model and can be relaxed on purpose.
  • Single-row operations are already atomic: use atomic updates (n = n + 1) and conditional updates (WHERE holder IS NULL, then check the row count) instead of read-compute-write.
  • Retrying a whole aborted transaction is safe; retrying after an unknown outcome needs idempotency, such as a request id recorded in the same transaction behind a unique constraint.
  • ACID stops at the edge of one database. Across services you get distributed transactions or sagas, both later topics, and the best fix is often keeping related data together.

Check your understanding

Which letter of ACID is most clearly the application's responsibility rather than something the database provides on its own?

  1. Atomicity
  2. Durability
  3. Consistency
  4. Isolation
Consistency means your business invariants hold. The database can enforce constraints you declare, and atomicity and isolation help preserve them, but it cannot know a rule you never told it. The other three are properties the database engine itself implements.

How does "atomicity" in ACID differ from "atomic" in a threading context such as an atomic counter increment?

  1. ACID atomicity is about surviving failure part-way (all or nothing); the threading sense is about other threads not seeing a half-done operation
  2. They mean the same thing
  3. ACID atomicity is about concurrency; the threading sense is about crashes
  4. ACID atomicity only applies to single rows
ACID atomicity is abortability: after a crash or rollback, nothing of the transaction remains. The concurrency meaning is covered by the I (isolation). Single-row operations are atomic in both senses, but multi-statement transactions are what ACID atomicity is mostly for.

UPDATE seats SET holder = 'bob' WHERE id = 1 AND holder IS NULL reports 0 rows changed. What does that tell you?

  1. The database is broken
  2. The transaction was rolled back
  3. Bob's account does not exist
  4. The condition failed: the seat was already taken, so the compare-and-set did not apply
A conditional update is a compare-and-set in the database. Zero rows changed means the condition (the seat is free) was no longer true when the statement ran. The row count is how you find out whether you won, without needing an explicit lock.

A client sends COMMIT for a payment and the connection drops before any reply. What is the safest way to design the retry?

  1. Always retry immediately with the same statements
  2. Give the request an id and record it in the same transaction behind a unique constraint, so a repeat is detected and ignored
  3. Never retry; tell the user it failed
  4. Retry with a longer timeout
The client cannot tell whether the commit happened. A blind retry might double-charge, and never retrying might lose the payment. An idempotency key stored atomically with the effect makes repeating the request harmless.

An order service and a payment service each use their own ACID database. What can you NOT get from those databases alone?

  1. Durable commits within each service
  2. A rollback of a failed statement inside one service
  3. A single all-or-nothing commit covering both services' writes
  4. Constraints inside each service
ACID is scoped to one database. Spanning two needs a distributed transaction protocol such as two-phase commit or a saga with compensating actions. Each database still gives its own durability, rollback and constraints.

A transaction has executed its writes but the server loses power before the commit record reaches disk. After recovery, what state should the database show?

  1. The writes are visible, since they were executed
  2. As if the transaction never ran, because it never committed
  3. Half of the writes, whichever reached disk
  4. The database refuses to start until a human decides
Atomicity plus durability: only committed transactions are durable, and an uncommitted one is undone during recovery. Seeing half the writes is exactly what transactions exist to prevent.

Data Models

The same facts can be stored as tables, as nested documents, as bare key-value pairs, as rows grouped by a partition key, or as a web of nodes and edges. Each shape makes some questions easy and others painful. Choosing the shape is the first and most lasting decision in any data system.

Why this matters

A data model is the set of ideas you use to describe data: what the basic building blocks are, and what you may ask of them. It decides which queries are one line and which are a project. In a design interview, "which database?" is really "which model fits how this data is read and written?" The trick is to think about access patterns first, not product names. This chapter gives you the vocabulary to do that, and every later chapter assumes it.

One small dataset, five shapes

We need something to model. We will use a tiny social app with three kinds of thing: users, the posts they write, and follows, who follows whom. Five users: Asha, Ben, Chen, Dara and Eli. Asha wrote two posts, Ben wrote one. Ben and Chen follow Asha, Chen also follows Ben, Dara follows Chen, and Eli follows Dara.

The questions we will ask of it are the usual ones for such an app: show me a user's profile with their posts, show me posts by people I follow, and (to stress the model) who is within three hops of me?

Relational: tables and keys

In the relational model, data lives in tables made of rows and columns, and rows refer to each other by key. Each fact is stored once, in the table where it belongs. We cover this in depth in chapter 2. Here is our dataset, as you can run it in SQLite:

CREATE TABLE users   (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE posts   (id INTEGER PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id), body TEXT NOT NULL);
CREATE TABLE follows (follower_id INTEGER NOT NULL REFERENCES users(id),
                      followee_id INTEGER NOT NULL REFERENCES users(id),
                      PRIMARY KEY (follower_id, followee_id));

INSERT INTO users   VALUES (1,'Asha'),(2,'Ben'),(3,'Chen'),(4,'Dara'),(5,'Eli');
INSERT INTO posts   VALUES (10,1,'Hello world'),(11,1,'Learning databases'),(12,2,'Coffee time');
INSERT INTO follows VALUES (2,1),(3,1),(3,2),(4,3),(5,4);

"Posts by people Chen follows" is two joins:

SELECT p.body, u.name AS author
FROM follows f
JOIN posts p ON p.user_id = f.followee_id
JOIN users u ON u.id = p.user_id
WHERE f.follower_id = 3
ORDER BY p.id;
body                author
------------------  ------
Hello world         Asha
Learning databases  Asha
Coffee time         Ben

Relational databases are strong at exactly this: slicing the same facts many different ways, including ways nobody planned for when designing the tables.

Document: a self-contained tree

In the document model (MongoDB, CouchDB, and the JSON columns in PostgreSQL and MySQL), the unit of storage is a whole nested structure, usually JSON. We might store each user as one document with their posts inside:

{ "_id": 1, "name": "Asha",
  "posts": [ {"id": 10, "body": "Hello world"},
             {"id": 11, "body": "Learning databases"} ],
  "followers": [2, 3] }

The big win is locality: the profile page needs the user and their posts, and one read gets both in one place, with no join. It also matches how application code thinks, because a nested object in your program maps straight to a nested document. The cost shows up when you want to cut the data a different way, as we will see below.

Key-value: the simplest possible interface

A key-value store (Redis, DynamoDB in its simplest use, Memcached, RocksDB underneath many systems) offers almost nothing: put(key, value), get(key), delete(key). The value is an opaque blob to the store. In Python terms, it is a giant dictionary that survives restarts:

user:1          →  {"name": "Asha"}
user:1:posts    →  [10, 11]
post:10         →  {"body": "Hello world", "by": 1}
followers:1     →  [2, 3]

This is extremely fast and trivially easy to spread across many machines (hash the key, pick a machine), which is why it underlies caches and huge-scale systems. The price: if you do not know the key, you cannot find the data. "All posts containing the word coffee" would mean scanning every value. You pay by pre-building every lookup you need, by hand, as more keys.

Wide-column: rows grouped by a partition key

The wide-column family (Google Bigtable and its descendants: Cassandra, HBase, ScyllaDB) is easy to misread because of the name; it is not the same thing as a column-oriented analytics store (that is chapter 9). Think of it as a key-value store where the value has structure and is sorted. Each row lives in a partition chosen by a partition key (which machine holds it), and within a partition, rows are kept sorted by a clustering key (so range scans within one partition are cheap). For our app, the table you design for "show a user's latest posts" might be:

-- Cassandra-style CQL (illustrative; we do not run it here)
CREATE TABLE posts_by_user (
  user_id  int,
  post_id  timeuuid,
  body     text,
  PRIMARY KEY ((user_id), post_id)      -- partition by user, sort by post
) WITH CLUSTERING ORDER BY (post_id DESC);

SELECT body FROM posts_by_user WHERE user_id = 1 LIMIT 20;

Reading the 20 latest posts of one user is a single fast sequential read from one machine. But this table can answer only that question well. If you also want "all posts, newest first, across users", you create another table with different keys and write every post to both. Wide-column stores buy huge write throughput and easy scaling by asking you to design tables around queries, not around the data.

Graph: nodes and edges

In the graph model (Neo4j, Amazon Neptune, and SQL-with-recursion tricks), the building blocks are nodes (things) and edges (relationships between things), and both can carry properties. Our app is arguably a graph already: users and posts are nodes, "follows" and "wrote" are edges. The graph's strength is the multi-hop query: follow edges, then follow more edges from where you landed, without knowing in advance how many steps it takes. In Cypher, Neo4j's query language, "everyone Eli can reach through 1 to 3 follows" is one line:

// Cypher (illustrative; not run here)
MATCH (eli:User {name: 'Eli'})-[:FOLLOWS*1..3]->(other:User)
RETURN DISTINCT other.name;

You can ask the same question in plain SQL with a recursive common table expression, which SQLite supports. This one runs:

WITH RECURSIVE reach(id, hops) AS (
  SELECT followee_id, 1 FROM follows WHERE follower_id = 5
  UNION
  SELECT f.followee_id, r.hops + 1
  FROM reach r JOIN follows f ON f.follower_id = r.id
  WHERE r.hops < 4
)
SELECT u.name, MIN(hops) AS hops
FROM reach r JOIN users u ON u.id = r.id
GROUP BY u.id ORDER BY hops;
name  hops
----  ----
Dara  1
Chen  2
Asha  3
Ben   3

Eli follows Dara (1 hop), who follows Chen (2 hops), who follows both Asha and Ben (3 hops). It works, but the recursive query is already awkward; with variable-length paths and dense, deeply connected data (fraud rings, recommendations, route planning), a native graph database is built to make this natural and fast.

One more family, mentioned only briefly: time-series databases store streams of timestamped measurements (server metrics, sensor readings) and optimise for appending new points and querying by time range. We meet them with search and vector stores in chapter 17.

The same data in three shapes

It helps to see the three most common shapes side by side. They hold the same facts: three users, two posts and three follows.

Analogy: filing the same paperwork three ways

Imagine a pile of paperwork about customers. A relational filing system keeps one drawer per kind of paper (customers, invoices, addresses), with reference numbers linking them. A document system keeps one folder per customer with everything inside. A graph system pins every paper to a wall and joins related ones with string. A folder is perfect when you always want one customer's whole file, and drawers are better when you want "all invoices over 1,000 across every customer".

Where it breaks down: paper filing cannot do automatic checks. A relational database enforces that an invoice must reference a real customer; a document store usually leaves that to your application.

Schema on write vs schema on read

A schema is the declared shape of the data: which fields exist and what types they have. The models differ in when that shape is checked.

  • Schema-on-write (relational): the database checks every row against the table definition as it is written. A row that does not fit is rejected. Changing the shape needs a migration, but readers can rely on the shape.
  • Schema-on-read (typical document stores): the database stores whatever you give it, and the code that reads it deals with whatever shape it finds. Fields can differ between documents, and adding one needs no migration.

The analogy from programming languages: schema-on-write is like a statically typed language, checking at compile time, while schema-on-read is like a dynamically typed one, checking at runtime. Here is schema-on-read in practice, with the reader coping with a field that only some documents have:

for d in [{"name": "Asha"}, {"name": "Ben", "city": "Oslo"}]:
    print(d["name"], d.get("city", "unknown"))

Asha unknown
Ben Oslo

Common misconception

"Schemaless databases have no schema." There is always a schema: the one your code assumes when it reads user["city"]. In a document store that schema is just implicit, scattered through application code, and enforced by nobody. That is flexible while you are experimenting, but it means that after a few years of changes your database holds documents of many old shapes, and every reader must handle all of them. Many teams end up adding validation back. The honest names are schema-on-read or implicit schema. We return to this in chapter 3.

One-to-many vs many-to-many

The most useful way to decide between a document and a relational design is to look at how things relate.

A one-to-many relationship forms a tree: one user has many posts, but each post has exactly one author. Trees nest naturally, which is why a document containing its posts works well. A many-to-many relationship forms a web: each user follows many users and is followed by many. There is no single parent to nest inside, so any nesting you choose duplicates something or points sideways.

Document stores therefore struggle with joins. If a post document embeds its author's name, then a user who renames themselves means updating every post they ever wrote, or living with stale names. If instead the post stores just author_id, you have recreated a foreign key, and the database either cannot follow it (your application does a second query, a "join in application code") or supports it weakly. The relational model was designed for the opposite situation: lots of cross-references, which it handles with joins and enforces with constraints.

Go deeper: the history, hierarchical, network, relational, then document again optional

Before the relational model, databases like IBM's IMS stored data as a tree (the hierarchical model), which had exactly the many-to-many trouble described above. The network model (CODASYL) allowed more general links but made programmers navigate them by hand, like following pointers. The relational model won in the 1970s and 80s largely by letting you describe what you want and leaving navigation to the database. Today's document stores revisit the tree idea for data that really is tree-shaped, and the lesson is the old one: the shape of the data should match the shape of its relationships.

Impedance mismatch

Application code works with objects: a User with a list of Posts. A relational database works with flat rows in separate tables. Converting between the two is the object-relational impedance mismatch (borrowed from electronics, where it means two circuits that do not fit together neatly). Loading one object may take several queries and a lot of glue, which is why ORMs (object-relational mappers) exist, and why they are a classic source of performance traps. A single object turned into ten queries is the notorious "N+1" problem.

Documents reduce the mismatch for tree-shaped data: the stored JSON looks like the in-memory object. But the mismatch moves rather than disappears: an object graph with shared references (two posts pointing to the same author object) still has to be flattened into ids somewhere.

Let's check one more thing, because it surprises people: documents and tables are not enemies. Most relational databases today can store and query JSON inside a column. SQLite's JSON functions, for example, make the document idea available inside a relational table:

CREATE TABLE docs (id INTEGER PRIMARY KEY, body TEXT);
INSERT INTO docs VALUES
  (1, '{"name":"Asha","posts":["Hello world","Learning databases"],"followers":[2,3]}'),
  (2, '{"name":"Ben","posts":["Coffee time"],"followers":[3],"city":"Oslo"}');

SELECT id, json_extract(body,'$.name') AS name,
       json_array_length(body,'$.posts') AS n_posts,
       json_extract(body,'$.city') AS city
FROM docs;
id  name  n_posts  city
--  ----  -------  ----
1   Asha  2
2   Ben   1        Oslo

(The blank for Asha's city is a missing field, which comes back as SQL NULL. We will meet NULL's odd rules in chapter 2.)

Picking by access pattern

A reliable way to choose is to write down your top few queries and ask what each model does with them. Here is a rough guide, not a rule book:

If your main need is...Lean towardsBecause
Flexible queries over related data; correctness mattersRelationalJoins, constraints and transactions; any question can be asked later
Load one self-contained thing by id (profile, order, product page)DocumentOne read, data together, shape evolves easily
Very fast lookup by a known key (sessions, caches, counters)Key-valueSimplest and fastest, shards trivially
Huge write volume, queries known in advance, scale across machinesWide-columnTables designed around queries; partitioned writes
Relationships are the point; variable-depth traversalsGraphMulti-hop queries are natural and fast
Timestamped measurements, mostly appended, queried by time rangeTime-seriesCompression and range queries tuned to time

Two more rules of thumb. First, the model should match the queries, not the data's appearance: our social data could live in any of the five shapes, and the right one depends on whether the app mostly shows profiles, feeds or recommendations. Second, big systems often use several models at once, each for what it does best, and keep them in sync (chapter 19). Chapter 20 turns this into a decision procedure.

Try it yourself: one dataset, two models

Run the dataset above in SQLite (sqlite3 ships with macOS; Python's sqlite3 module works everywhere), then try these exercises. Delete the scratch file afterwards.

  1. Paste the CREATE and INSERT statements into sqlite3 :memory: and run the "posts by people Chen follows" query. Change the 3 to other user ids.
  2. Write Eli's three-hop query yourself, then raise the hop limit and see what changes. Then add a follow that makes a cycle (say, Asha follows Eli) and see which line of the query stops it from looping forever: the WHERE r.hops < 4 limit, since hops is part of each row and UNION alone cannot spot a repeat.
  3. Write Asha's profile as one JSON document in Python (json.dumps), then work out how you would find "who follows Ben" using only the documents. What did you have to scan?

Distributed systems connection

The data model quietly decides how a system can be split across machines. Key-value and wide-column stores partition by key, so a lookup touches one machine (chapter 16), but a query that is not by key must ask every machine. Documents that nest everything an operation needs can be updated on one shard atomically. A graph or a many-to-many relational model has no clean cut line: a join across shards means network calls, which is why "can we avoid the join?" is one of the first questions in a scale-out design.

Key takeaways

  • A data model is a lens: the same facts can be tables, documents, key-value pairs, partitioned wide rows or a graph, and each makes different queries easy.
  • Relational stores each fact once and joins; documents nest what is read together; key-value is lookup by key only; wide-column asks you to design tables per query; graphs make traversals first-class.
  • Schema-on-write checks data when it is stored; schema-on-read checks it when it is used. "Schemaless" really means the schema is implicit in your code.
  • One-to-many is a tree and nests well; many-to-many is a web and does not, which is why documents struggle with joins.
  • The object-relational impedance mismatch is the glue between nested objects and flat rows. Documents shrink it for tree-shaped data.
  • Choose by access pattern first, and expect real systems to combine models.

Check your understanding

Which relationship fits a single nested document best?

  1. Users following other users, in both directions
  2. An order and its line items, which belong to only that order
  3. Students and courses, where each student takes many courses and each course has many students
  4. Cities connected by roads
Line items have exactly one parent and are read with it: a tree. The other three are many-to-many webs, where nesting duplicates data or forces lookups by id.

A wide-column store such as Cassandra is best described as...

  1. A relational database with extra columns
  2. The same as a column-oriented analytics warehouse
  3. A key-value store with no structure inside the value
  4. A partitioned store where rows in a partition are sorted by a clustering key, with tables designed around known queries
The partition key decides which machine holds a row and the clustering key sorts rows within it. "Wide-column" is a different idea from "column-oriented" storage for analytics (chapter 9).

A team says their document database is "schemaless". What is the most accurate response?

  1. There is still a schema: the one the application code assumes when it reads fields. It is just not enforced on write
  2. That is impossible, because documents must have a declared schema
  3. Then reading data can never fail
  4. It means the database cannot store types
Code that reads user["city"] assumes a field exists. Schema-on-read moves enforcement from the database to every reader, so old document shapes pile up unless someone manages them.

You need "everyone within four follows of this user", with the depth varying per request. Which model is the most natural fit?

  1. Key-value, since you look up a user by id
  2. Document, embedding followers in each user
  3. Graph, because traversing variable-length paths of edges is its core operation
  4. Wide-column, because it scales writes
A graph database makes multi-hop traversal a single query. A relational database can do it with recursion (as we ran), but key-value and document stores would need your application to loop and fetch hop by hop.

Why can embedding an author's name inside every post document cause trouble?

  1. Documents cannot contain strings
  2. If the author renames, every embedded copy needs updating, or some posts keep the stale name
  3. It makes the posts impossible to read
  4. The database will refuse to store duplicates
Duplicated data is the trade you make for locality. Reads get cheap, but writes must keep every copy consistent. Relational normalisation (chapter 2) makes the opposite choice.

Batch Processing

Not every question needs an answer in a millisecond. "How many visits did each page get last month?" is asked once, over billions of records, and nobody is waiting at a screen. This chapter follows that kind of work from a one-line Unix pipeline up to the clusters that process petabytes, and shows why the same few ideas (sort, partition, re-run) keep appearing.

Why this matters

Reports, search indexes, recommendation models, billing runs and data-warehouse loads are almost all batch jobs. They run on enormous inputs, and on a big cluster something is always failing mid-run. The design that makes them dependable (immutable input, deterministic tasks, re-run on failure) is one of the most reusable ideas in data engineering, and it is the baseline against which stream processing (chapter 19) is defined.

Batch versus online

Three kinds of system serve data. Online services answer a request and care about latency. Batch processing takes a large, bounded input (a file, a day's logs, a whole table), computes for minutes or hours, and writes an output; what matters is throughput, and the input does not change while it runs. Stream processing works on unbounded input as it arrives, and is next chapter. Batch jobs are usually run on a schedule, and they typically read data produced by the online systems of the previous chapters.

The Unix philosophy: a batch job on your laptop

Before any cluster, there is the shell. You can answer real analytical questions with small tools joined by pipes, each doing one job: read lines, pick a field, sort, count. Let us generate a web server access log (10,000 lines in the common format, with a fixed random seed so you see what I saw), and then ask it questions.

# genlog.py: write access.log
import random
random.seed(42)
pages = ["/", "/", "/", "/pricing", "/docs", "/docs", "/blog", "/login", "/api/items", "/missing"]
with open("access.log", "w") as f:
    for i in range(10000):
        page = random.choice(pages)
        status = 404 if page == "/missing" else (500 if random.random() < 0.01 else 200)
        ip = f"192.0.2.{random.randint(1, 50)}"
        f.write(f'{ip} - - [12/Oct/2026:10:{i // 170:02d}:{i % 60:02d} +0000] "GET {page} HTTP/1.1" {status} {random.randint(200, 5000)}\n')
$ python3 genlog.py && head -2 access.log && wc -l access.log

192.0.2.7 - - [12/Oct/2026:10:00:01 +0000] "GET /pricing HTTP/1.1" 200 4667
   10000 access.log
$ awk '{print $7}' access.log | sort | uniq -c | sort -rn | head -4

1872 /docs
1042 /blog

$ awk '{print $9}' access.log | sort | uniq -c | sort -rn

1037 404
 111 500
$ awk '$9 == 404 {print $7}' access.log | sort | uniq -c | sort -rn
1037 /missing

Read the second pipeline left to right. awk '{print $7}' extracts the 7th whitespace-separated field, the URL. sort puts equal URLs next to each other. uniq -c collapses adjacent duplicates and counts them (it only works because the input is sorted). The final sort -rn orders by count, highest first. Hold on to that middle trick: sorting makes equal keys adjacent, so grouping becomes one pass over a stream. It is the whole idea of MapReduce, scaled up.

Unix tools earn their reputation for three reasons. The input is never modified (every program reads it and writes somewhere else). Each step has a simple interface (lines of text), so steps combine freely. And sort is not limited by memory: GNU and BSD sort spill sorted chunks to disk and merge them (an external merge sort, the same shape as the SSTable compaction of chapter 5). What a pipeline cannot do is use more than one machine.

Analogy: a mail-sorting room

Picture the library's returns room. One clerk reads each returned book's subject off its label and drops it in a bin; the bins are then gone through one at a time, and each is counted. Sorting into bins first makes the counting trivial, because every book of a kind is in one place.

Where it breaks down: the room has one clerk. Once the pile is a million books, you need many clerks in many rooms, and then the real problem appears: books of one kind end up in different rooms, and someone has to bring them together.

MapReduce: the same idea on many machines

In 2004 Google described MapReduce, a way to run this sort-and-group pattern across thousands of machines, and the open-source Hadoop made it widely used. The programmer writes two small functions:

  • map: called once per input record, emits zero or more (key, value) pairs. For word count: for each word, emit (word, 1).
  • reduce: called once per key, with all values for that key. For word count: add up the ones.

Everything between them is the framework's job, and it is the clever part. The input is split into pieces, each handled by a mapper task near the data. Each mapper partitions its output by key: hash(key) mod R picks which of R reducers gets each pair, so all pairs for one key, from every mapper, go to the same reducer. The mapper sorts each partition and writes it to its local disk. Then the shuffle: every reducer fetches its partition from every mapper over the network and merges them by key. Finally reduce runs on each key group, and the output is written.

Step through

Word count: 3 mappers, 2 reducers

  1. Each mapper reads its own input split: here, two lines each. Splits are processed in parallel, ideally on the machine that stores them.
  2. Map. Every word becomes a pair (word, 1). Mappers know nothing about each other.
  3. Partition and sort. Each mapper routes every pair to a reducer by hashing the key, and sorts each partition. Mapper 0 writes two local files: R0 (cat, sat, the, the) and R1 (dog, ran). The word cat goes to R0 on every mapper.
  4. Shuffle. Each reducer fetches its file from every mapper (solid lines go to reducer 0, dashed to reducer 1) and merges them. This is the expensive step: it moves data between machines.
  5. Reduce. With all the pairs for a key side by side, reduce is trivial: add them. cat appeared 3 times across all three mappers, and all 3 ended up in one place.

That is the whole algorithm, small enough to simulate in plain Python: the mappers, the partitioning, the sort and the reducers, all as functions. The simulation below uses the same input and gives the same files as the diagram.

import zlib
from itertools import groupby
from operator import itemgetter

SPLITS = [                       # one input split per mapper
    ["the cat sat", "the dog ran"],
    ["the cat ran", "a dog sat"],
    ["a cat sat", "the end"],
]
R = 2                            # number of reducers

def map_fn(line):                # (key, value) pairs out of one input record
    for word in line.split():
        yield word, 1

def partition(key):              # same key -> same reducer, on every mapper (crc32 is stable across runs)
    return zlib.crc32(key.encode()) % R

def reduce_fn(key, values):
    return key, sum(values)

# --- map phase: each mapper writes R sorted "files", one per reducer
map_outputs = []
for m, split in enumerate(SPLITS):
    files = [[] for _ in range(R)]
    for line in split:
        for k, v in map_fn(line):
            files[partition(k)].append((k, v))
    files = [sorted(f) for f in files]
    map_outputs.append(files)
    print(f"mapper {m}: " + " | ".join(f"->R{r} {f}" for r, f in enumerate(files)))

# --- shuffle + reduce: reducer r fetches file r from every mapper, merges by key, reduces
for r in range(R):
    fetched = sorted(p for files in map_outputs for p in files[r])
    out = [reduce_fn(k, [v for _, v in grp]) for k, grp in groupby(fetched, key=itemgetter(0))]
    print(f"reducer {r}: {out}")
$ python3 mapreduce.py
mapper 0: ->R0 [('cat', 1), ('sat', 1), ('the', 1), ('the', 1)] | ->R1 [('dog', 1), ('ran', 1)]
mapper 1: ->R0 [('cat', 1), ('sat', 1), ('the', 1)] | ->R1 [('a', 1), ('dog', 1), ('ran', 1)]
mapper 2: ->R0 [('cat', 1), ('sat', 1), ('the', 1)] | ->R1 [('a', 1), ('end', 1)]
reducer 0: [('cat', 3), ('sat', 3), ('the', 4)]
reducer 1: [('a', 2), ('dog', 2), ('end', 1), ('ran', 2)]

We used zlib.crc32 rather than Python's built-in hash() on purpose: Python randomises string hashes per process, and a partitioner must send a key to the same reducer from every mapper and on every re-run. Real MapReduce jobs often add a combiner, a mini-reducer run on each mapper's output before the shuffle (mapper 0 could send ('the', 2) instead of two ones), which shrinks the network traffic.

Skew: the shuffle is only as fast as its busiest reducer

If one key is far more common than the rest (a celebrity user, the URL /), one reducer receives most of the data and the whole job waits for it. This is the hot-key problem of chapter 16 again, and the cures are the same family: salt the key to split it across reducers and combine the partial results afterwards, or handle known-hot keys separately.

Fault tolerance by re-running

On a thousand machines, some task will crash, or a machine will vanish, during a job that runs for hours. The batch answer is calm: just run the failed task again. The framework notices the failure and schedules the same task, on the same input split, on another machine. Slow tasks get the same treatment: a "straggler" can be duplicated elsewhere (Hadoop calls it speculative execution) and the first copy to finish wins.

That only works under conditions, and they are the real lesson of the chapter:

  • Immutable input. A task must read exactly the same data when re-run. If the input could change under it, the second attempt would see a different world.
  • Deterministic tasks. Given the same input, a task must produce the same output. Otherwise the reducers could receive a mix of outputs from two attempts of one mapper, and the final result would be a combination no single run could have produced.
  • No visible side effects until success. Outputs are written to a temporary place and moved into position only when a task completes, so a half-finished attempt leaves nothing behind, and a duplicated task does not double-write.
import random

def good_map(line):  return [(w, 1) for w in line.split()]
def flaky_map(line): return [(w, random.random()) for w in line.split()]   # uses a random number

line = "the cat sat"
print("deterministic, rerun gives same output:", good_map(line) == good_map(line))
print("non-deterministic, rerun gives same output:", flaky_map(line) == flaky_map(line))
$ python3 flaky.py
deterministic, rerun gives same output: True
non-deterministic, rerun gives same output: False

Wall-clock time, random numbers, unordered hash iteration and calls to external services are the usual ways a task becomes non-deterministic. Batch code that stays pure (a function of its input) buys cheap, automatic fault tolerance. This also explains why a failure costs only a re-run of one task, not the whole job: map outputs sit on disk, so a failed reducer fetches them again.

Dataflow engines: beyond MapReduce

MapReduce has one weakness: complex jobs are chains of MapReduce jobs, and each job writes its full output to the distributed file system (HDFS, on Hadoop) before the next can start. Disk and replication between every stage is slow, and a map step with nothing to do but reshape data still has to wait for the previous reduce.

Dataflow engines such as Spark and Flink let you describe the whole computation as one DAG (directed acyclic graph) of operators: read, filter, map, group by key, join, write. The engine plans the entire graph at once. Operators that need no data movement between machines (filter, map) are pipelined together in a single pass. Only operators that need all records of a key in one place (group by, join) require a shuffle. Intermediate results can stay in memory and are spilled to disk only when needed, so a long pipeline pays for disk once at the ends rather than between every step.

Failure handling changes shape too. Spark's datasets remember their lineage, the recipe of transformations that produced them, so a lost in-memory piece is recomputed from its parents rather than restored from a stored copy. That is the same "re-run a deterministic function" idea, applied to a graph. If your first encounter with analytics was column stores, note that these engines love columnar file formats such as Parquet as input and output.

Joins in batch

Joining two datasets is the most common heavy operation, and without indexes it needs a plan, just like the query engines of chapter 8. Two strategies dominate batch work.

  • Sort-merge join (reduce-side). Mappers emit records from both datasets keyed by the join key, so the shuffle brings matching records from both sides to the same reducer, sorted. The reducer walks the two sorted streams together. It works for any size, because it only needs the shuffle, but it moves both datasets across the network.
  • Broadcast hash join (map-side). If one side is small (a table of users, against a huge log of events), send a copy of it to every mapper, load it into an in-memory hash table, and stream the big side past it. No shuffle for the big side at all. It needs the small side to fit in memory on each task.
events = [("u1", "/home"), ("u2", "/pricing"), ("u1", "/docs"), ("u3", "/home"), ("u9", "/home")]   # big, partitioned
users  = [("u1", "Ana"), ("u2", "Ben"), ("u3", "Cy")]                                                # small

# broadcast hash join: every task gets a copy of the small side as a dict; stream the big side
table = dict(users)
print("broadcast:", [(u, page, table[u]) for u, page in events if u in table])

# sort-merge join: both sides sorted by key, then walked together like a zipper
a, b = sorted(events), sorted(users)
i = j = 0; out = []
while i < len(a) and j < len(b):
    if a[i][0] < b[j][0]: i += 1                  # event with no user on the other side
    elif a[i][0] > b[j][0]: j += 1
    else: out.append((a[i][0], a[i][1], b[j][1])); i += 1   # keys are unique on the users side
print("sort-merge:", out)
$ python3 joins.py
broadcast: [('u1', '/home', 'Ana'), ('u2', '/pricing', 'Ben'), ('u1', '/docs', 'Ana'), ('u3', '/home', 'Cy')]
sort-merge: [('u1', '/docs', 'Ana'), ('u1', '/home', 'Ana'), ('u2', '/pricing', 'Ben'), ('u3', '/home', 'Cy')]

Both give the same four joined rows (the event for the unknown user u9 is dropped, as in an inner join); only the order differs. An optimiser chooses between them using the same size estimates that drive EXPLAIN. The sort-merge join is the shuffle plus a final merge, which is why it is so closely tied to MapReduce.

Output: immutable files, and reprocessing

A batch job does not update records in place. It reads immutable input and writes a new output, usually as files in a distributed file system or object store, often in a columnar format that a warehouse or another job reads next. Because nothing is modified, you get useful properties for free: a bad run can simply be discarded, you can keep the previous output while the new one is built, and then switch a pointer over to the new directory. Consumers see old or new, never half-written.

This makes reprocessing routine. When the logic changes (a bug fix, a new definition of "active user", a better model), you do not patch the old results; you re-run the job from the raw input and replace the output. That is only possible because the raw data is kept as the source of truth and every later view is derived from it, the system-of-record rule of chapter 17. Teams call the safety that results human fault tolerance: a mistake in code costs a re-run, not lost data.

Batch versus stream

The weakness of batch is staleness: results are as old as the last run, perhaps a day. Streaming processes each record as it arrives, and the output is minutes or seconds fresh. Two architectures have been named for combining them. The lambda architecture runs a batch pipeline and a streaming pipeline side by side and merges their results (accurate-but-late plus fast-but-approximate). The kappa architecture runs only a streaming pipeline and, to reprocess, replays the retained log through new code. We mention both and no more; in chapter 19 you will see the log that makes the second one possible. Notice that a batch job is just a stream processor over a finite stream.

Go deeper: why the shuffle writes to local disk optional

Mappers write their partitioned output to their local disk rather than sending it straight to reducers. This is the fault-tolerance trick again: if a reducer dies, the replacement can fetch the same files again, and the mapper need not re-run. If a mapper's machine dies with its files, only that mapper's tasks are repeated (determinism makes the repeated output identical). The price is that all mappers must finish before reduce starts producing, which is why the framework talks about a barrier at the shuffle.

Distributed systems connection

Batch processing is distribution with the hard parts designed away: immutable inputs mean no consistency problems, deterministic tasks mean failures are cured by re-running, and the only coordination is the shuffle barrier. It is the cheapest correct way to run a computation on many machines. Those same ideas, replaying an ordered, immutable log to rebuild state, are central to networking case 10, which examines how a shared log gives the whole system one order of events. Read it after the next chapter and the pieces will click.

Key takeaways

  • Batch jobs process a bounded, immutable input and optimise for throughput; the output is a new set of files.
  • sort | uniq -c | sort -rn works because sorting puts equal keys next to each other. MapReduce is that idea distributed.
  • MapReduce: map emits (key, value) pairs; the shuffle partitions by key and sorts; reduce combines each key's values. The shuffle is the costly, skew-prone step.
  • Fault tolerance comes from re-running tasks, which needs immutable input, deterministic tasks and atomically committed output.
  • Dataflow engines (Spark, Flink) plan a whole DAG, pipeline narrow operators, keep intermediate data in memory and recover by recomputing lineage.
  • Sort-merge joins shuffle both sides; broadcast hash joins ship a small table to every task and avoid shuffling the big one.
  • Reprocessing from raw input is how you fix logic; batch is stale by design, which stream processing addresses.

Check your understanding

In awk '{print $7}' access.log | sort | uniq -c, why must sort come before uniq -c?

  1. uniq only reads sorted file names
  2. sort removes duplicates, so uniq has less work
  3. uniq counts only adjacent identical lines, and sorting makes equal lines adjacent
  4. sort converts text to numbers
uniq compares each line only with the previous one. Sorting is the grouping step, the same idea as the MapReduce shuffle.

In MapReduce word count, why do all ('cat', 1) pairs end up at the same reducer?

  1. Each mapper partitions its output by a deterministic function of the key, such as hash(key) mod R
  2. Reducers pick keys at random and ask mappers for them
  3. There is only one reducer
  4. The mappers run on the same machine
Every mapper uses the same partition function, so the same key goes to the same reducer, which can then see all its values together. That is why the partitioner must be stable across processes and re-runs.

A failed mapper is re-run, but its code calls random.random() to tag each output. What can go wrong?

  1. Nothing; random numbers are always the same
  2. The job runs out of memory
  3. The second attempt is slower
  4. The re-run produces different output than the first attempt, so reducers may combine pieces from two incompatible runs
Re-running to recover is only safe if tasks are deterministic. Otherwise the result depends on which attempt's output was used, and the job's answer may be one no single run could produce.

You join a 5 TB click log with a 20 MB table of product names. Which join is most sensible, and why?

  1. Sort-merge join, because it moves the least data
  2. Broadcast hash join: copy the small table to every task and stream the big log past it with no shuffle of the log
  3. Shuffle the small table only
  4. Neither; joins are impossible in batch jobs
When one side fits in memory, broadcasting it avoids moving the huge side across the network. Sort-merge shuffles both sides and is for when neither is small.

What is the main advantage of a Spark-style dataflow engine over a chain of MapReduce jobs?

  1. It never needs a shuffle
  2. It stores everything in one database
  3. It plans the whole DAG, pipelines operators, and keeps intermediate data in memory instead of writing it to the file system between every stage
  4. It makes tasks non-deterministic
Group-by and join still need a shuffle. The gain is avoiding the disk and replication cost between stages, and recovering by recomputing lineage rather than re-reading stored intermediates.

The definition of an "active user" changes. How does a batch pipeline normally fix last quarter's reports?

  1. Edit each old report row by hand
  2. Re-run the job with the new logic over the retained raw input and replace the old output
  3. Delete the raw data and start over
  4. Nothing; old reports cannot be changed
Raw input is immutable and kept; outputs are derived. Reprocessing is cheap and safe, which is the main reason to keep the raw data.

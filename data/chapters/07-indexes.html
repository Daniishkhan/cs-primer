Indexes

An index is the difference between a query that takes a few microseconds and one that reads the whole table. It is also a cost you pay on every write, and a choice the database makes for you, sometimes wrongly. This chapter shows what indexes really are, how to design them, and how to check, with real EXPLAIN output, that the database actually uses them.

Why this matters

The most common database performance problem in the world is a missing, wrong or ignored index. Engineers who understand indexes can read a slow query, guess the cause in seconds and fix it with one statement. Those who do not add indexes at random, slow down every write, and still see slow queries. The B-tree from chapter 6 is the machinery; this chapter is how you point it at your queries.

What an index is

An index is a second data structure, kept sorted by some column(s), whose entries point back to the rows of the table. The table itself stays as it is. The index is an extra copy of just the keys, arranged so that finding one is fast.

Back in our library: the books stand on shelves in whatever order they arrived (the table). A visitor wants every book about Lima. Without a catalogue they must walk every shelf. With a subject catalogue, a drawer of cards sorted by subject, each saying "shelf 3, position 2", they flip to "Lima", read the cards, and walk straight to those shelves. The catalogue costs space (the cards), effort (a librarian must write a card for every new book) and it has to be kept in step with the shelves. In return, finding things stops depending on how many books the library owns.

Analogy: the subject catalogue

The shelves are the table; the card drawer is the index. A drawer sorted by subject answers "everything about Lima" quickly, but it cannot answer "everything published in 1998" unless you build a second drawer sorted by year. Each extra drawer means more cards to write when a book arrives.

Where it breaks down: a paper catalogue is searched by eye, flipping through cards. A database index is a B-tree, so even with a billion cards the search reads three or four pages, and it also gives you a sorted order for free.

Primary and secondary indexes

The primary key uniquely identifies a row, and a database always indexes it. In some engines (InnoDB, SQLite for tables keyed by their integer id) that index is the table, as chapter 6 showed. Any other index is a secondary index: you create it with CREATE INDEX for the columns your queries filter or sort by. It stores the indexed column(s) plus a way back to the row (a row location, or the primary key). A unique index additionally rejects duplicates, which is how UNIQUE constraints are enforced.

Index versus table scan: counting rows and pages

Without a usable index, the database does a full table scan (a "sequential scan"): read every page of the table and test every row. The cost is proportional to the table's size, whether you want one row or ten thousand.

Let us make that concrete. We will build a table of 100,000 people in SQLite shortly; measured there, it occupies 647 pages of 4 KiB, about 155 rows per page. So:

  • Table scan for one person by name: read all 647 pages, test 100,000 rows. Sequential reads, but a lot of them.
  • Through an index on name: descend the index's B-tree (about 3 pages for 100,000 entries), then fetch the one table page the entry points to: roughly 4 pages, examining a handful of rows. That is a 150-fold reduction in pages, and the gap widens as the table grows, because the scan grows linearly and the index grows by one level every time the table gets a few hundred times bigger.

The third bar is the lesson of this chapter in miniature. If a query matches 5% of the rows and those rows are scattered at random through the table, the index sends you to almost every table page anyway, just in a less friendly order (random reads instead of sequential), so it saves little and may even lose. Indexes shine when the query is selective: it picks out a tiny fraction of the table. We return to that after the experiments.

Seeing it: EXPLAIN QUERY PLAN

You never need to guess whether an index is being used. Every SQL database can show the query plan, the strategy it chose. In SQLite the command is EXPLAIN QUERY PLAN; PostgreSQL and MySQL have EXPLAIN (chapter 8 shows how to read their richer output). The words to look for in SQLite:

SCAN
Read the whole table (or an index in full). The slow path for a selective query.
SEARCH … USING INDEX
Seek into an index to the matching entries, then fetch the rows.
SEARCH … USING COVERING INDEX
Seek into an index and answer from the index alone, never touching the table.

The script below builds a 100,000-row table, then runs queries before and after creating indexes, printing the plan and the average time of 20 runs. It uses only Python's built-in sqlite3. It writes the database to a temporary folder inside your current directory (so it can count pages) and deletes it at the end.

import sqlite3, random, time, os, tempfile, shutil

random.seed(42)
cities = ["Lima","Oslo","Pune","Cairo","Quito","Hanoi","Accra","Tunis","Perth","Davao",
          "Minsk","Basel","Kyiv","Lyon","Riga","Bern","Nuuk","Suva","Male","Apia"]
d = tempfile.mkdtemp(dir=".")                       # a real file, so we can count its pages
con = sqlite3.connect(os.path.join(d, "people.db"))
con.execute("CREATE TABLE people (id INTEGER PRIMARY KEY, name TEXT, city TEXT, age INTEGER, active INTEGER)")
con.executemany("INSERT INTO people VALUES (?,?,?,?,?)",
    [(i, f"user{i}", random.choice(cities), random.randint(18, 90), int(random.random() < 0.97))
     for i in range(1, 100_001)])
con.commit()
print("page size:", con.execute("PRAGMA page_size").fetchone()[0], "bytes;",
      "pages in the table:", con.execute("PRAGMA page_count").fetchone()[0])

def show(sql, args=()):
    plan = " | ".join(r[3] for r in con.execute("EXPLAIN QUERY PLAN " + sql, args))
    t = time.perf_counter()
    for _ in range(20):
        n = len(con.execute(sql, args).fetchall())
    ms = (time.perf_counter() - t) * 1000 / 20
    print(f"  {plan}\n      -> {n} rows, {ms:.3f} ms")

print("\n1. One person, by name")
q = "SELECT * FROM people WHERE name = 'user77777'"
show(q)
con.execute("CREATE INDEX idx_name ON people(name)")
show(q)
print("  pages now (table + one index):", con.execute("PRAGMA page_count").fetchone()[0])

print("\n2. city = 'Lima' AND age > 60, selecting only city and age")
q = "SELECT city, age FROM people WHERE city = 'Lima' AND age > 60"
show(q)
con.execute("CREATE INDEX idx_city ON people(city)")
show(q)
con.execute("CREATE INDEX idx_city_age ON people(city, age)")
show(q)

print("\n3. Column order: an (age, city) index cannot serve city alone")
con.execute("DROP INDEX idx_city_age"); con.execute("DROP INDEX idx_city")
con.execute("CREATE INDEX idx_age_city ON people(age, city)")
q = "SELECT * FROM people WHERE city = 'Lima'"
show(q)
con.execute("CREATE INDEX idx_city_age ON people(city, age)")
show(q)

print("\n4. A boolean column: 97% of rows have active = 1")
con.execute("CREATE INDEX idx_active ON people(active)")
con.execute("ANALYZE")                      # let the planner see how common each value is
show("SELECT * FROM people WHERE active = 0")
show("SELECT * FROM people WHERE active = 1")

con.close(); shutil.rmtree(d)

Read it step by step.

  1. The name lookup went from a SCAN (about 3 ms) to a SEARCH … USING INDEX (about 8 microseconds): a factor of several hundred, for one CREATE INDEX. The database file grew from 647 to 1,080 pages: that single index cost about two thirds of the table's own size.
  2. The Lima query is more interesting. An index on city helps, but only about 2.6 times: it returns 2,041 rows, and each needs a table fetch. The (city, age) index plan says COVERING INDEX: the query asks only for city and age, both in the index, so no table page is touched, and it is almost another 4 times faster.
  3. Column order in section 3: with only an (age, city) index, the planner had no way to use it for city = 'Lima' and fell back to SCAN. Adding (city, age) turned it into a SEARCH.
  4. The boolean column in section 4: after ANALYZE (which records how many rows have each value), SQLite uses the index for the rare value active = 0 and, for active = 1, the 97% value, chooses a plain SCAN instead of the index we just built. It is right to ignore it, as explained below.

Read timings with care

These numbers come from one laptop, with the whole database file already cached in RAM, so they understate how much a real disk read would hurt a scan. They also include Python's time to build result lists, which dominates queries that return thousands of rows. The query plans are the dependable part. Take the times as "same order of magnitude", never as a benchmark.

Composite indexes and the leftmost-prefix rule

An index can cover several columns at once: CREATE INDEX idx ON people(city, age) is a composite index (also called a multi-column or compound index). Its entries are sorted by city first and, within each city, by age. This is exactly how a phone book works: sorted by last name, and within each last name by first name. You can find "Smith, John" fast; you can find all the Smiths fast; but you cannot find all the Johns without reading the whole book, because Johns are scattered under every surname.

The leftmost-prefix rule follows: an index on (a, b, c) can efficiently serve conditions on a; on a, b; or on a, b, c, but not conditions on b or c alone. (Some databases have limited tricks for skipping a leading column, but do not plan around them.)

Column order: equality first, then range

A second rule decides how to order the columns when you have a choice. The index can walk along equality conditions, one column after another, and then use one range condition; after a range column, the later columns are no longer in sorted order across the range, so they can only be filtered, not searched.

For WHERE city = 'Lima' AND age > 30, the index (city, age) narrows by city and then by the age range, and every entry it reads is a match. The index (age, city) must read all entries with age over 30 (most of the table) and check the city on each. Both are usable, one is far better. The widget below lets you see the difference. As a rule of thumb: equality columns first, then the range or sort column. Among equality columns, order them to match the queries you run most, and keep the leading column one many queries share.

Covering indexes and index-only scans

A normal index lookup is two steps: find the entry, then fetch the row to get the other columns. If the index already contains every column the query needs, the second step is unnecessary. The index is said to cover the query, and the database does an index-only scan.

Our experiment showed it: USING COVERING INDEX was the fastest plan of the three. In PostgreSQL the same idea appears as an "Index Only Scan" (with a wrinkle: Postgres must also confirm a row is visible to your transaction, so it consults a visibility map; see chapter 12). PostgreSQL even lets you add non-key columns to an index with INCLUDE so that it covers a query without those columns affecting the sort order.

The trade-off is obvious: the more columns in the index, the larger it is, and the more writes touch it. Cover the few hottest queries, not everything. And note that SELECT * almost never lets an index cover a query, one more reason to select only what you need.

Simplified, on purpose

The explorer counts rows and entries, not pages, and it lets you pick only one index at a time, so it does not model the planner choosing among several or estimating costs. In the real tests above it was the planner's statistics that decided between SCAN and SEARCH for the boolean column. The "wrong" index choices (an index the query cannot use) are modelled faithfully.

Selectivity, cardinality, and the boolean-column trap

Two words explain most index decisions. The cardinality of a column is how many distinct values it has: id has one per row, city has twenty, active has two. The selectivity of a condition is the fraction of rows it keeps: city = 'Lima' keeps about 1 in 20, or 5%; active = 1 keeps 97%. A condition is selective when it keeps few rows. Indexes pay off for selective conditions.

A column with very low cardinality, such as a boolean, a status with three values, or a gender field, is therefore a poor index on its own: any one value matches a big slice of the table. Using such an index means visiting a large share of the table's pages in random order, which is slower than reading them in sequence. A good planner knows this, as our run showed: for active = 1 it ignored the index. (Only if the data is heavily skewed, as here where active = 0 is 3% of rows and you query that, does the index shine.) Low-cardinality columns are better as trailing columns of a composite index, or in a partial index (below) that covers just the rare value.

Common misconception

"I'll index every column, just in case." Each index costs space and slows every write, and the planner will still ignore the ones that do not fit the query. Index the columns your slow, frequent queries filter, join and sort on. Remove indexes that EXPLAIN never uses. Also, a function on the column (WHERE lower(name) = 'ana', or WHERE age + 1 > 30) usually prevents a plain index on that column from being used; see expression indexes below.

The costs of indexes

  1. Writes get slower. Every insert must add an entry to every index; every delete removes one from each; an update of an indexed column moves its entry. Each of those is a B-tree insert, with its possible page splits and its write-ahead log records (chapter 6).
  2. Space grows. Our single name index added about two thirds of the table's size. A table with five indexes can easily be larger in indexes than in data, and all those pages compete for the buffer pool.
  3. The planner has more to choose from, and it works from statistics that can be stale or wrong. An extra index can make the planner pick a worse plan for some other query, which is why adding an index in production is a change to test, not a free action.

The write cost is easy to measure. This script inserts the same 100,000 rows into a table with zero to four secondary indexes:

import sqlite3, random, time

random.seed(1)
rows = [(i, f"user{i}", random.randint(18, 90), random.randint(0, 999)) for i in range(1, 100_001)]
indexes = ["CREATE INDEX i1 ON t(name)", "CREATE INDEX i2 ON t(age)", "CREATE INDEX i3 ON t(score)", "CREATE INDEX i4 ON t(age, score)"]

for n in range(len(indexes) + 1):
    con = sqlite3.connect(":memory:")
    con.execute("CREATE TABLE t (id INTEGER PRIMARY KEY, name TEXT, age INTEGER, score INTEGER)")
    for ddl in indexes[:n]:
        con.execute(ddl)
    t = time.perf_counter()
    con.executemany("INSERT INTO t VALUES (?,?,?,?)", rows)
    con.commit()
    print(f"{n} secondary indexes: {(time.perf_counter() - t) * 1000:6.0f} ms to insert 100,000 rows")
$ python3 index_write_cost.py
0 secondary indexes:     43 ms to insert 100,000 rows
1 secondary indexes:     85 ms to insert 100,000 rows
2 secondary indexes:    123 ms to insert 100,000 rows
3 secondary indexes:    164 ms to insert 100,000 rows
4 secondary indexes:    223 ms to insert 100,000 rows

Each index added roughly 40 to 60 ms, so four indexes made the bulk insert about five times slower than none. This is an in-memory database, so there is no disk or log cost; on a real server each index also means more pages to write and more log to ship. That is the fundamental trade of indexing: you buy read speed with write speed and space. A reporting table that is loaded once and queried constantly can have many indexes; a table taking thousands of writes per second should have few.

Hash indexes versus B-tree indexes

Chapter 4 built a hash index over a log; databases offer hash indexes too (PostgreSQL has them, MySQL's MEMORY engine uses them). They are not the default because they trade away flexibility:

B-tree indexHash index
Equality (= 5)Yes, in a few page readsYes, typically one or two reads
Range (> 5, BETWEEN)Yes: sorted, linked leavesNo: hashing destroys the order
ORDER BY / prefix searchYes (LIKE 'Sm%' in suitable cases)No
Composite leftmost-prefix useYesNeeds all columns (equality on the whole key)
Default?Yes, in essentially every SQL databaseNo: a niche option

In short, a hash index is a B-tree with its best feature removed, for a small speed-up on one kind of lookup. Use a B-tree unless you have measured a reason not to.

Other kinds of index, briefly

  • Partial index: an index over only some rows. CREATE INDEX idx_inactive ON people(city) WHERE active = 0 is tiny and serves queries that include active = 0. It is the fix for the skewed boolean column above. (SQLite and PostgreSQL support it.)
  • Expression index: an index over a computed value. CREATE INDEX idx_lower_name ON people(lower(name)) makes WHERE lower(name) = 'ana' a seek instead of a scan. Both statements above run unchanged in SQLite and are accepted by PostgreSQL.
  • Full-text and spatial indexes: a B-tree orders values on a line, so it cannot answer "which documents contain these words" or "which points lie inside this map rectangle". Those need different structures (inverted indexes, R-trees and similar), which chapter 17 covers along with vector and time-series stores.

Distributed systems connection

The moment data is spread over several machines, indexes get harder. If the table is sharded by user id, a secondary index on city can be local (each shard indexes only its own rows, so a query by city must ask every shard and merge the answers) or global (one index partitioned by city, so the query goes to one place but every write now updates a second machine). Neither is free, and choosing a shard key so that your hottest queries hit one shard is the heart of chapter 16. Indexes also have to be built and changed on a live system without blocking writes: a large CREATE INDEX can take hours, which is why engineers use online index builds and why migration stories like Case 6 spend so long on them. And every replica maintains its own copy of each index, so a heavily indexed table makes both the write path and replication slower (chapter 15).

Key takeaways

  • An index is a separate sorted structure (normally a B-tree) of keys pointing to rows. It turns an O(table) scan into a few page reads for selective queries.
  • Check with EXPLAIN: SCAN means the whole table; SEARCH … USING INDEX means a seek; COVERING INDEX means the table was not touched.
  • A composite index is used through its leftmost columns. Put equality columns first and the range or sort column last.
  • A covering index contains every column the query needs, so no row fetch is needed. SELECT * usually defeats it.
  • Selectivity decides: an index helps when a condition keeps a small fraction of rows. Low-cardinality columns such as booleans rarely help alone, and the planner may rightly ignore the index.
  • Indexes cost write speed, space and planner complexity. Add them for slow, frequent queries, and drop the unused ones.
  • Hash indexes do equality only; B-trees also do ranges and ordering. Partial and expression indexes handle skewed data and computed conditions; full-text and spatial need special structures.

Check your understanding

A table has an index on (country, signup_date). Which query can use the index for a fast seek?

  1. WHERE signup_date > '2024-01-01'
  2. WHERE signup_date = '2024-03-05' ORDER BY country
  3. WHERE country = 'PE' AND signup_date > '2024-01-01'
  4. None: composite indexes cannot be used for filtering
The index is sorted by country first, then by date within each country, so it serves conditions on its leftmost columns in order. The third query is the ideal shape: equality on the first column, then a range on the second. A condition on signup_date alone has no single place to seek to.

You have WHERE status = 'shipped' AND created_at > '2025-01-01' with an equality on status and a range on created_at. Which index order is better, and why?

  1. (created_at, status), because ranges should lead
  2. (status, created_at): equality first lets the index narrow by status, then use the range on created_at within it
  3. They are identical in cost
  4. Neither; two separate single-column indexes are always better
After a range column, the following columns can no longer be searched, only filtered. Put equality columns first and the range column last, so every entry read is a match. The widget shows the difference in entries examined.

EXPLAIN QUERY PLAN shows SEARCH people USING COVERING INDEX idx_city_age (city=? AND age>?). What does covering tell you?

  1. The index holds every column the query reads, so the database never fetches table rows
  2. The index covers the whole table, so a scan is needed
  3. The query is protected by a lock
  4. The index is stored in the cache
A covering index contains all the needed columns, so the answer comes from the index alone (an index-only scan). It is why selecting just the indexed columns can be dramatically faster than SELECT *.

98% of the rows in an orders table have archived = 0. You index archived and query WHERE archived = 0. What will a good planner most likely do?

  1. Use the index, because an index is always faster than a scan
  2. Refuse to run the query
  3. Delete the index
  4. Ignore the index and scan the table, since the condition keeps almost every row and random row fetches would cost more than one sequential pass
Selectivity matters. When a condition keeps most rows, an index sends you to nearly every page in random order, which loses to a sequential scan. Our experiment saw SQLite do exactly this for active = 1.

A team adds six indexes to a table that takes 5,000 inserts per second, and write latency rises. What is the most likely explanation?

  1. The indexes made the table smaller, confusing the planner
  2. Every insert must now add an entry to all six indexes (six B-tree inserts, with page splits and log writes), on top of writing the row
  3. Indexes only affect reads, so the cause must be elsewhere
  4. Hash indexes are slower than B-trees for writes
Indexes are redundant copies of data that must be kept in step with the table, so each write pays for every index. Keep only the indexes that earn their cost.

Why can a B-tree index answer WHERE price BETWEEN 10 AND 20 but a hash index cannot?

  1. Hash indexes cannot store numbers
  2. B-trees are always cached
  3. A hash function scatters neighbouring keys to unrelated places, so there is no order to walk; a B-tree keeps keys sorted and its leaves linked
  4. Hash indexes are only for text
Hashing gives fast equality lookups by destroying order. A range needs the keys in order, and a B-tree provides exactly that: seek to 10, then follow the leaf links until 20.

Sharding in Practice

The networking course showed you how to cut data into pieces and find the right machine for a key. This chapter is about the decisions that hurt later: which column to cut on, what happens to your indexes and joins when the data is in pieces, and how to move the pieces while the system is running.

Why this matters

Sharding is the one scaling step you cannot easily take back. The shard key you choose on day one decides which queries stay fast, which ones become fan-outs across every machine, and whether a single popular user can melt one server while the rest sit idle. Teams that choose well barely notice they are sharded. Teams that choose badly spend a year migrating.

Why shard, and when not to

In networking chapter 19 you met partitioning: cutting a dataset into shards, each owned by a different machine, plus the mechanics of consistent hashing. Here we use the database word sharding and look at what it costs in a real application. There are three honest reasons to shard:

  • Data size. The data no longer fits on one machine's disks, or the working set no longer fits in its RAM, so every query pays for disk reads (chapter 6's buffer pool is too small).
  • Write throughput. Read replicas (chapter 15) multiply read capacity, but every replica still applies every write. Once one leader cannot absorb the writes, only splitting the writes helps.
  • Blast radius. With one database, one bad query, one corrupted table or one failed machine hurts every customer. With many shards, an incident hurts a fraction of them, and a maintenance task can proceed one shard at a time.

Shard last, not first

Sharding takes away things relational databases give you for free: cross-row transactions, joins, unique constraints across the whole table, simple backups. Before you accept that, exhaust the cheaper options: better indexes, caching (chapter 14), a bigger machine, read replicas, archiving cold data. A single well-tuned PostgreSQL or MySQL server handles far more than most people expect. Shard when the numbers say you must, not because it sounds scalable.

Two ways to cut: vertical and horizontal

Vertical partitioning splits by table or feature: the users and billing tables stay on one database, the activity feed and notifications move to another. Each piece is a normal, unsharded database. It is the cheapest first step because the application code just learns about a second connection. Its limit is that each feature's data can still outgrow one machine, and you lose joins and transactions between the pieces.

Horizontal sharding splits the rows of one table: every shard has the same schema, but holds different rows. A shard key (a column, or several) decides which shard owns a row. This is what scales a single huge table, and it is the subject of the rest of the chapter. Real systems do both, in that order: case 6 follows one company through vertical partitions first and horizontal shards second.

Analogy: a library that outgrew its building

You met the library branches in the networking course. Vertical partitioning is moving the whole children's section into its own building. Horizontal sharding is opening branches that each stock every section but only for some readers, say by the first letter of the author's surname. The rule that decides which branch holds a book is the shard key, and every librarian must agree on it.

Where it breaks down: a patron can wander between branches in an afternoon. A query cannot. Every extra shard a query must visit is a network round trip, and the query is as slow as its slowest branch.

Choosing a shard key

The shard key answers "which shard owns this row?" and, just as importantly, "which queries can find their rows without asking everyone?". The two classic strategies make opposite trades.

By key range

Give each shard a contiguous slice of the key space: shard 0 owns keys A to F, shard 1 owns G to M. Neighbouring keys live together, so a range scan ("all orders from 1 March to 7 March") reads one or two shards, in order. Range partitioning is what ordered stores such as B-tree-based databases and HBase-style systems naturally offer, and it is how you split a table by date.

The trap is the hot spot. If the key is a timestamp, all new writes have the newest timestamp, so they all land in the last range. One shard does all the work while the others hold cold history. Sequential ids behave the same way. The data is spread out, but the load is not.

By hash

Hash the key and shard on the hash, as in networking chapter 19. Similar keys are scattered, so load spreads evenly, whatever the key looks like. The price is the range scan: neighbouring keys are on unrelated shards, so "all of March's orders" must ask every shard and merge the answers (scatter/gather). Hashing buys balance and gives up order.

Compound keys: the best of both, in the right order

Often you want both: an even spread and cheap scans for the common query. A compound key does it by using two parts for two jobs. Take (user_id, timestamp). Hash only the first part to choose the shard, so users spread evenly. Inside the shard, keep rows sorted by the whole key, so one user's rows sit together in time order. "Posts of user X in the last day" then goes to exactly one shard and reads one contiguous run of keys. Cassandra calls the parts the partition key and the clustering columns; the same idea shows up in DynamoDB (partition key and sort key) and elsewhere. Case 2 shows how this kind of key shaped Discord's message storage.

The order matters. (timestamp, user_id) sharded by its first part is the hot-spot design again. Put the high-cardinality, evenly-spread part first.

The shard key is hard to change

Every row's location, every query's routing, and often your uniqueness guarantees depend on it. Changing it later means rewriting every row into a new layout while serving traffic. Choose it from the queries you must make fast, not from the table's primary key by default, and check it against the heaviest users, not just the average one.

Hot keys, celebrities and salting

Hashing spreads keys evenly. It cannot spread the load on one key. If a single user, product or chat room receives a huge share of the traffic (a celebrity account, a viral post), then all of it goes to the one shard that owns that key, however good the hash is. Real popularity is heavily skewed: a few keys are enormously busy and a long tail is quiet, a shape called a Zipf-like distribution.

The standard remedy is salting: for known-hot keys only, append a small number to the key (celebrity42#0, #1, … #7) and choose the suffix at random or round-robin when writing. The hash of each salted key is different, so the writes fan out over several shards. The cost moves to reads: to see everything about that key you must read every salt bucket and merge. So you salt only keys you know are hot (typically a small list the application maintains), and you accept slower reads for them. Chapter 14 showed the cache-side version of the same problem, hot keys that overwhelm one cache node.

Things to look for. Range on timestamp sends everything to one shard, but a "last day" read touches just that one. Hash(user_id) is mostly even, yet the shard that owns the busiest user stands out, and it gets worse as you add shards, because the busiest user's share of the total does not shrink. Range on user_id keeps one user's rows together but, because the busy users have low ids, is badly skewed too (second only to timestamp here). Salting fixes the writes and makes the busiest user's read touch many shards.

More shards do not fix a hot key

If one key takes 17% of all writes, no number of shards can bring that shard below 17%. Adding machines helps only the load that can be split. A hot key needs a different remedy: salting, a cache in front, splitting the entity, or batching the writes.

Secondary indexes across shards

An index on something other than the shard key (find all cars where color = 'red', when cars are sharded by id) gets awkward, because matching rows live on every shard. The two designs, from Designing Data-Intensive Applications, trade write cost against read cost.

  • Local (document-partitioned) index. Each shard indexes only its own rows. Writes are simple: one shard updates its data and its index together, perhaps in one local transaction. Reads on the indexed column are not: the row could be anywhere, so the query goes to all shards and the results are merged. This is scatter/gather, and its tail latency is that of the slowest shard. MongoDB and Cassandra's built-in secondary indexes, and Elasticsearch, work this way.
  • Global (term-partitioned) index. One index covers all the rows, and the index itself is split across shards, by the indexed value. A read asks just the shard that owns the value. A write is the problem: a car on shard B that turns blue changes its row on B and the index entries on whichever index shards hold "red" and "blue". That is a cross-shard write, so global indexes are often updated asynchronously and can briefly lag behind the data.

The choice is a classic read-versus-write trade. If you query through a secondary index constantly, a global one pays off. If writes dominate, or you can tolerate wide reads, local is simpler. Often the better answer is to avoid the question by picking a shard key that makes your main queries single-shard.

Cross-shard queries, joins and transactions

Everything that was one cheap local operation on a single database can become a distributed one:

  • Queries without the shard key scatter to every shard. An aggregate such as SUM(total) is computed as a partial sum per shard, and a coordinator adds the partials.
  • Joins between tables sharded differently need rows from different machines brought together, either by shipping one side over the network or by running a distributed join. It works, but slowly, and the cost grows with the data.
  • Transactions that touch two shards need an atomic commit protocol such as two-phase commit, which adds round trips and can block while a coordinator is down (the problem behind chapter 10's atomicity promise, now across machines). Many sharded systems simply do not offer them, or offer them with caveats.

The best fix is not a smarter protocol but co-location: choose the shard key so that rows used together live together. In a multi-tenant product (a SaaS where each customer is a tenant), shard every table by tenant_id. A tenant's users, orders and items then sit on one shard, so the common joins and transactions are local, and only genuinely global questions fan out. It also gives a neat blast-radius story: one tenant's runaway query hurts one shard. You can see co-location in miniature below, using two SQLite databases as two shards.

import sqlite3
# Two "shards" are two separate SQLite databases; tenant_id picks the shard.
shards = [sqlite3.connect(":memory:") for _ in range(2)]
for db in shards:
    db.execute("CREATE TABLE orders(id INTEGER PRIMARY KEY, tenant_id INT, total INT)")
    db.execute("CREATE TABLE items(order_id INT, sku TEXT)")
def shard_of(tenant): return shards[tenant % 2]
for tenant in (1, 2, 3, 4):
    db = shard_of(tenant)
    cur = db.execute("INSERT INTO orders(tenant_id,total) VALUES(?,?)", (tenant, tenant * 10))
    db.execute("INSERT INTO items VALUES(?,?)", (cur.lastrowid, f"sku-{tenant}"))

# Co-located: tenant 3's order and items live on the same shard, so the JOIN is local.
db = shard_of(3)
print("tenant 3 (one shard):", db.execute(
    "SELECT o.id, o.total, i.sku FROM orders o JOIN items i ON i.order_id=o.id WHERE o.tenant_id=3").fetchall())
# Global total: scatter to every shard, gather and combine.
partials = [db.execute("SELECT COALESCE(SUM(total),0) FROM orders").fetchone()[0] for db in shards]
print("per-shard partial sums:", partials, "-> total", sum(partials))
$ python3 shards.py
tenant 3 (one shard): [(2, 30, 'sku-3')]
per-shard partial sums: [60, 40] -> total 100

Co-location has a price too

If one tenant is a hundred times bigger than the others, "all of a tenant on one shard" makes that tenant a hot spot, exactly as a celebrity user does. Mature multi-tenant systems keep the ability to move or split a large tenant onto its own shard. Auto-increment ids are another casualty: each shard counting 1, 2, 3 would collide, so sharded systems use per-shard ranges, UUIDs, or time-ordered ids generated by the application.

Rebalancing: changing the shard count while live

Data grows, so shards must be added and the data redistributed. The obvious scheme, hash(key) mod N, is a disaster: changing N from 4 to 5 reassigns most keys. The three practical schemes all avoid it.

  1. A fixed number of logical shards, mapped to nodes. Cut the hash space into many more logical shards than machines (say 64, or Redis Cluster's 16,384 slots) and keep a small table "logical shard → node". A key's logical shard never changes, because the modulus is fixed forever. Adding a node means moving some whole logical shards to it and changing their table entries. This is the simplest to reason about and to operate.
  2. Dynamic splitting. Used with range sharding. Start with a few ranges; when one grows past a size threshold (or gets too busy), split it in two and let the new half move elsewhere, much like a B-tree page split in chapter 6. MongoDB's balancer and HBase-style systems work this way. The count of shards follows the data, at the cost of a more complex shard map.
  3. Consistent hashing. Nodes and keys are placed on a ring and a key belongs to the next node clockwise, so adding a node steals keys only from its neighbours. Networking chapter 19 built it, with virtual nodes and an interactive ring you can poke. It is the same idea as fixed logical shards, with the boundaries chosen by hashing.

Here is the first scheme beside the naive one, run on 2,000 tenant keys. Adding a fifth node moves 13 of 64 logical shards, about a fifth of the keys, while mod N moves most of them.

import hashlib

def h(key):
    return int(hashlib.md5(str(key).encode()).hexdigest(), 16)

LOGICAL = 64                                   # fixed forever
node_of = {s: f"node{s % 4}" for s in range(LOGICAL)}   # the shard map

def shard(key):  return h(key) % LOGICAL
def route(key):  return node_of[shard(key)]

keys = [f"tenant:{i}" for i in range(2000)]
before = {k: route(k) for k in keys}

# add a 5th node: move only some logical shards to it (every 5th shard here)
for s in range(0, LOGICAL, 5):
    node_of[s] = "node4"
moved = sum(before[k] != route(k) for k in keys)
print(f"logical shards moved: {sum(1 for s in node_of if node_of[s]=='node4')} of {LOGICAL}")
print(f"keys that changed node: {moved} of {len(keys)}")

# the naive way for comparison: hash(key) % nodes, 4 -> 5 nodes
moved_naive = sum(h(k) % 4 != h(k) % 5 for k in keys)
print(f"naive hash % N, 4 -> 5 nodes: {moved_naive} of {len(keys)} keys move")
$ python3 rebalance.py
logical shards moved: 13 of 64
keys that changed node: 411 of 2000
naive hash % N, 4 -> 5 nodes: 1589 of 2000 keys move

Moving data online

Deciding what moves is the easy half. Moving it while users keep writing is the careful half. The usual recipe:

  1. Copy a consistent snapshot of the shard to the new node in the background, throttled so it does not starve live traffic.
  2. Keep streaming the changes made since the snapshot, from the shard's write-ahead log or a change feed (the machinery of chapter 19), until the copy is nearly caught up.
  3. Do a short cutover: pause writes to that shard for a moment (or fence the old owner), apply the last changes, flip the shard-map entry, and resume. Readers and writers now go to the new node.
  4. Verify, then delete the old copy. Keep the ability to flip back until you trust the result.

Analogy: moving a bookshelf between branches

You photocopy the shelf's catalogue and ship the books while the old branch keeps lending. A clerk notes every loan and return made during the move and replays them at the new branch. On a quiet minute you close the old shelf, replay the last few notes, and hang the new sign. Patrons barely notice.

Where it breaks down: a library clerk can see the whole shelf. A database must stop two nodes both believing they own the shard during the flip, a split-brain risk handled with fencing tokens and a consensus-backed shard map.

Routing: who knows where the data lives?

Someone must turn a key into a node. There are three standard places to put that knowledge, and the networking chapter's request-routing section covers the same trio.

  • Client-side routing. The application (or a driver library) holds the shard map and connects straight to the right node. No extra hop, but every client must be updated when the map changes, and every language needs the logic.
  • A proxy / router tier. Clients talk to a stateless router that knows the map and forwards each query. Clients stay simple and can stay unaware of sharding. The router is an extra hop and must itself be scaled and made highly available, but it can also merge scatter/gather results.
  • A coordination service holding the map. Whichever of the above does the routing, the authoritative shard map is stored somewhere that survives failures and agrees on one version: ZooKeeper or etcd, or a replicated config database. Routers and clients cache the map and are told when it changes. Getting machines to agree on that map is the consensus problem of later in the distributed-systems material.

How real systems do it

Three well-known systems package these ideas, each on top of an existing single-node database. I describe them qualitatively; check each one's documentation for the details of your version.

  • Vitess shards MySQL. Applications talk to a proxy tier (VTGate) that speaks the MySQL protocol and routes queries to the right underlying MySQL instances. A configuration called a vindex says how a column's value maps to a shard, and Vitess includes tooling for splitting and moving shards online. It began as a way to scale YouTube's MySQL.
  • Citus is an extension that makes PostgreSQL distributed. You choose a distribution column for each table; Citus cuts the table into shards across worker nodes behind a coordinator node. Tables distributed by the same column are co-located, so joins on that column stay local, which is why it is popular for multi-tenant applications with tenant_id as the key. Small shared tables can be replicated to every node as reference tables.
  • MongoDB has built-in sharding. You pick a shard key, ranged or hashed; data is divided into chunks; mongos routers send operations to the right shards; and config servers hold the shard metadata. A background balancer moves chunks between shards as they grow uneven.

The two cases in this course are a good pair. Case 6 shows a team horizontally sharding PostgreSQL with a query proxy in front, and the long road of co-locating data so queries stay single-shard. Case 2 shows partition keys and hot partitions deciding which database a chat product could use at each stage.

Go deeper: resharding by splitting versus moving optional

Adding capacity can mean two different operations. Moving takes whole existing shards and relocates them to new machines (cheap to plan, limited by the number of logical shards you started with). Splitting makes more, smaller shards out of existing ones, which is needed when you run out of logical shards. Splitting with hash sharding means picking a new, larger modulus consistently, and systems that support it usually split each shard into two so that each key's new home is one of just two places. This is why starting with a generous number of logical shards (many times your node count) is cheap insurance.

Try it yourself

Try it yourself

Python 3 is all you need. The script below makes 20,000 writes from 1,000 users with Zipf-like popularity, then counts the load per shard under a hash and under a range of user ids. Your output will match mine because the seed is fixed. Then change N_SHARDS to 8, and try a salt for the top user.

import hashlib, random
from collections import Counter

def h(key):                      # stable hash (Python's built-in hash() is randomised per run)
    return int(hashlib.md5(str(key).encode()).hexdigest(), 16)

random.seed(7)
# 20,000 writes from 1,000 users; a few users are far more active (Zipf-like)
weights = [1 / (rank + 1) for rank in range(1000)]
writes = random.choices(range(1000), weights, k=20000)

N_SHARDS = 4
by_hash = Counter(h(u) % N_SHARDS for u in writes)
by_range = Counter(min(u // 250, N_SHARDS - 1) for u in writes)   # user_id ranges of 250
print("hash(user_id) % 4 :", sorted(by_hash.items()))
print("range on user_id  :", sorted(by_range.items()))
top = Counter(writes).most_common(3)
print("busiest users     :", top)
$ python3 skew.py
hash(user_id) % 4 : [(0, 5185), (1, 3695), (2, 5511), (3, 5609)]
range on user_id  : [(0, 16323), (1, 1804), (2, 1092), (3, 781)]
busiest users     : [(0, 2669), (1, 1345), (2, 937)]

Notice that even the hash is lopsided: shard 1 holds 3,695 writes and shard 3 holds 5,609, purely because of where the busy users happen to hash to. The range split is far worse here only because, in this synthetic data, the busiest users have the lowest ids. In a real system the correlation is usually weaker, but old accounts having low ids and being busier is common.

Distributed systems connection

Sharding turns every operation that was local into a question about a set of machines: which one owns this key, who has the current shard map, what if two nodes both think they own a shard during a move. Those questions are answered with the tools of the networking course: consistent hashing, replication of each shard for failure, and agreement protocols for the shard map. Cross-shard transactions need atomic commit, which is why the next big question in a sharded design is always "can I make the transaction single-shard?". Ordering across shards is its own problem, which networking case 10 examines.

Key takeaways

  • Shard for data size, write throughput or blast radius, and only after cheaper options (indexes, caches, replicas, a bigger machine) are exhausted.
  • Vertical partitioning splits by table or feature; horizontal sharding splits the rows of one table by a shard key.
  • Range keys keep neighbours together (good scans) but create hot spots, like timestamps. Hash keys spread load but scatter ranges. Compound keys such as (user_id, timestamp) hash the first part and sort by the second.
  • More shards do not cure a hot key. Salt the known-hot keys, accepting that reading them fans out.
  • Local secondary indexes make writes cheap and reads scatter/gather; global ones make reads narrow and writes cross-shard.
  • Avoid cross-shard joins and transactions by co-locating related rows, for example by sharding everything on tenant_id.
  • Rebalance by moving whole logical shards (fixed count), splitting ranges, or consistent hashing, never hash mod N. Move data online with snapshot, stream, short cutover.
  • Route through the client, a proxy tier, or both, with the authoritative shard map in a coordination service.

Check your understanding

A table is range-sharded by created_at and the write rate suddenly doubles. Why does adding two more shards barely help?

  1. New shards must be warmed up for an hour before taking writes
  2. Range sharding cannot be combined with replication
  3. New rows always have the newest timestamp, so they all land in the last range, and the new shards sit idle
  4. Timestamps cannot be hashed
With a monotonically increasing key, one shard owns "now". The data is spread out but the write load is not. A hashed or compound key (hash a leading part, such as user_id, then sort by time) spreads the writes.

Posts are sharded by hash(user_id). Which query is cheapest?

  1. All posts by one given user
  2. All posts in the last hour, across users
  3. The ten most recent posts site-wide
  4. Posts containing the word "database", via a local index
The user's id hashes to one shard, so one shard answers. The other three have no shard key in the predicate, so every shard must be asked and the answers merged.

One celebrity user receives 20% of all writes. You go from 8 to 16 shards. What is true?

  1. The celebrity's shard now gets 10% of the writes
  2. Hashing automatically spreads one user's rows over all shards
  3. The celebrity's rows move to a quieter shard
  4. The shard that owns the celebrity still gets about 20% of all writes, because the load is on a single key
A hash spreads keys, not the traffic of a single key. To split that load you need salting (several keys for the one user), a cache, or another application-level remedy, and reads of that user then have to gather several salt buckets.

What is the main cost of a global (term-partitioned) secondary index?

  1. Reads must ask every shard
  2. A single write may update the row's shard and one or more index shards, so writes become cross-shard or are applied asynchronously
  3. It cannot be used with hash sharding
  4. It makes the primary key non-unique
The index is split by the indexed value, so a read goes to one index shard. But the row and its index entries live on different machines, so keeping them consistent costs a distributed write or accepts lag. Option A describes the local index.

A SaaS product shards every table by tenant_id. What does this buy most directly?

  1. Perfectly even load regardless of tenant size
  2. Cheap queries across all tenants
  3. Joins and transactions within one tenant stay on one shard, and one tenant's trouble stays on one shard
  4. No need for a shard map
Co-location keeps the common work local. It does not even out load (a huge tenant is a hot spot) and cross-tenant queries still scatter. You still need a shard map to find the tenant's shard.

Why do many systems use a fixed number of logical shards, mapped to nodes by a table?

  1. It guarantees no shard can ever be hot
  2. A key's logical shard never changes, so adding a node only moves whole logical shards and updates table entries instead of rehashing keys
  3. It removes the need for a router
  4. It makes cross-shard joins free
Because the modulus (the number of logical shards) is fixed, keys never change logical shard. Rebalancing becomes "move shard 7 to the new node, flip its entry", which is also easy to do online.

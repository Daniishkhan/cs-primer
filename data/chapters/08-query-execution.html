Query Execution & Planning

You write SELECT and say what you want. The database decides how to get it: which indexes to use, which table to read first, which join algorithm to run. This chapter opens that black box, shows you how to read its decisions with EXPLAIN, and lists the handful of mistakes that cause most slow queries.

Why this matters

The same SQL can run in a millisecond or in a minute, depending on a plan you never wrote. In the indexes chapter you learned what an index is. Here you learn when the database actually uses one, why it sometimes ignores yours, and how to find out. Reading a query plan is the single most useful performance skill for anyone who works with a database.

From SQL text to results

When a query arrives, the database does not run your text. It passes it through four stages, as sketched in chapter 0.

  1. Parse. Check the syntax and turn the text into a tree. SELEC * FORM t dies here. Then name resolution: does table t exist, and does it have that column?
  2. Rewrite. Transform the tree into a simpler equivalent: expand views into the queries they stand for, fold constants (1 + 2 becomes 3), and flatten some subqueries into joins.
  3. Plan. Many different physical strategies give the same answer. The query planner (or optimizer) enumerates candidates, estimates the cost of each, and picks the cheapest. The result is a query plan: a tree of operators.
  4. Execute. The executor runs that tree against the storage engine, pulling pages through the buffer pool from chapter 6, and streams rows back to you.

SQL is declarative: you describe the result, not the steps. That is why it has lasted. The database can get faster, add new join algorithms and use new indexes, and your old queries just improve. The price is that the plan is hidden unless you ask to see it.

Analogy: asking the librarian

You ask at the library desk: "every book by this author published after 1990". A good librarian does not walk every shelf. They look at the catalogue (an index) and fetch only those books. But if you ask for "all the books", they skip the catalogue and just walk the shelves in order, because flipping through cards and fetching one book at a time would be slower. The librarian chooses a strategy using what they know about the library: how big it is, and how many books you'll probably want.

Where it breaks down: a librarian can see the shelves. A planner works from summarised statistics gathered earlier, which may be out of date, and cannot peek at the real answer until it has already run the query.

A plan is a tree of operators

Each box in a plan is an operator that does one small job: scan a table, filter rows, join two inputs, sort, aggregate, limit. Operators take rows in and pass rows out, so you can snap them together like pipes. The plan for "names and totals of orders over 100, with their customer" might look like this:

Most engines run such a tree with the iterator model, also called the Volcano model after a 1990s research system. Every operator offers one method, next(), that returns one row (or "no more rows"). To get the first result row, the top operator calls next() on its child, which calls next() on its child, all the way down to the scans, which read pages from disk. Rows then flow back up. The demand pulls the data.

The model has two nice properties. Operators are simple and composable: any operator can sit on top of any other. And rows stream: with LIMIT 10 on top, the tree stops asking after ten rows, and the scans below never read the rest of the table. The cost is a function call per row per operator, which is why analytic engines process batches of values instead (next chapter).

Some operators cannot stream. A sort must read all its input before it can emit the smallest row. The build phase of a hash join and the groups of an aggregate also have to see everything first. These blocking operators are where memory goes, and where a query that "starts instantly" can still take a while to produce its first row.

Access paths: how one table is read

The bottom of the tree is where data enters. For one table, the planner picks an access path:

Access pathWhat it doesSQLite saysPostgres says
Sequential scanReads every page of the table in order, tests every rowSCAN tSeq Scan
Index scanWalks the index tree to the matching entries, then fetches each row from the table by its pointerSEARCH t USING INDEX …Index Scan
Index-only scanAnswers from the index alone, because it holds every column the query needs (a covering index)SEARCH t USING COVERING INDEX …Index Only Scan

The index scan carries a hidden cost. Each index entry points at a row somewhere in the table, so every match is a random fetch. If the query matches 0.1% of the rows, that is a bargain. If it matches 60%, you have turned one sequential pass into hundreds of thousands of random page visits, and a plain scan wins. So the planner has to estimate how many rows will match before it can choose. Postgres also has a middle path, the Bitmap Heap Scan, which collects matching row locations from an index first and then reads the table pages in order.

Let's see it with SQLite. This script builds a 1,000-customer, 50,000-order database in memory and asks for the plan at each stage. Python's sqlite3 module is all you need.

import random
import sqlite3

random.seed(1)
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE customers (id INTEGER PRIMARY KEY, name TEXT, country TEXT);
CREATE TABLE orders (id INTEGER PRIMARY KEY, customer_id INTEGER,
                     total REAL, created TEXT);
""")
db.executemany("INSERT INTO customers VALUES (?,?,?)",
               [(i, f"cust{i}", random.choice(["US", "DE", "IN", "BR"]))
                for i in range(1, 1001)])
db.executemany("INSERT INTO orders VALUES (?,?,?,?)",
               [(i, random.randint(1, 1000), round(random.uniform(5, 500), 2),
                 f"2026-{random.randint(1,12):02d}-{random.randint(1,28):02d}")
                for i in range(1, 50001)])

def plan(sql):
    print(sql)
    for row in db.execute("EXPLAIN QUERY PLAN " + sql):
        print("    ", row[3])          # row = (id, parent, notused, detail)

print("-- no index on customer_id")
plan("SELECT * FROM orders WHERE customer_id = 42")

db.execute("CREATE INDEX idx_orders_cust ON orders(customer_id)")
print("\n-- after CREATE INDEX on orders(customer_id)")
plan("SELECT * FROM orders WHERE customer_id = 42")
plan("SELECT customer_id FROM orders WHERE customer_id = 42")
plan("SELECT * FROM orders WHERE id = 7")

print("\n-- a join: customers (scan) probing orders (index)")
plan("SELECT c.name, o.total FROM customers c "
     "JOIN orders o ON o.customer_id = c.id WHERE c.country = 'DE'")
-- no index on customer_id
SELECT * FROM orders WHERE customer_id = 42
     SCAN orders

-- after CREATE INDEX on orders(customer_id)
SELECT * FROM orders WHERE customer_id = 42
     SEARCH orders USING INDEX idx_orders_cust (customer_id=?)
SELECT customer_id FROM orders WHERE customer_id = 42
     SEARCH orders USING COVERING INDEX idx_orders_cust (customer_id=?)
SELECT * FROM orders WHERE id = 7
     SEARCH orders USING INTEGER PRIMARY KEY (rowid=?)

-- a join: customers (scan) probing orders (index)
SELECT c.name, o.total FROM customers c JOIN orders o ON o.customer_id = c.id WHERE c.country = 'DE'
     SCAN c
     SEARCH o USING INDEX idx_orders_cust (customer_id=?)

Read the output as a story. With no index, SCAN orders: every row is visited. After CREATE INDEX, the same query becomes a SEARCH that jumps to the matches. When we ask only for customer_id, which the index already contains, SQLite adds the word COVERING and never touches the table at all: an index-only scan. The primary-key lookup is a SEARCH on the table's own B-tree. For the join, SQLite scans customers (filtering on country) and, for each match, does an index search into orders. That is the next section's first algorithm.

SCAN is not always a bug

A scan of a 200-row table is faster than any index, and reading the entire table is exactly right for a report over most of it. The words to worry about are a SCAN of a big table inside a query that should touch only a few rows, or a SCAN on the inner side of a join, repeated once per outer row.

Join algorithms

A join pairs rows from two inputs where a condition holds. There are three classic ways to do it, and the planner picks per join. Call the sizes of the two inputs N and M rows.

Nested loop (and index nested loop)

The simplest idea: for every row of the outer input, search the inner input for matches. Without help, that is N × M comparisons, hopeless for big tables. But if the inner side has an index on the join column, each outer row costs one index lookup instead of a scan, and the total drops to about N × log M. This index nested loop is the workhorse of OLTP queries, where one side is a handful of rows ("this customer's orders"). It is also the only algorithm that works for any join condition, not just equality. SQLite plans its joins as nested loops (sometimes building a temporary "automatic index" on the inner table first).

Hash join

Build a hash table from the smaller input keyed on the join column, then stream the bigger input and look up each row in O(1). That is about N + M work, with no index needed. The price is memory for the hash table and the restriction to equality conditions. If the build side does not fit in the memory budget, databases split both inputs into partitions that do fit, spilling them to disk and joining partition by partition. Try it step by step:

Step through

A hash join: build, then probe

  1. Choose a build side. The planner picks the smaller input, customers (4 rows), to hash, and streams the bigger one, orders. The join condition is o.customer_id = c.id.
  2. Build, row by row. Take id 1. Apply a hash function (here just id mod 4, to keep it readable) to get a bucket number, and store the row in that bucket.
  3. Build finished. All four customers now sit in memory, each in the bucket its key hashes to. The build phase has read the smaller input exactly once. Nothing has been output yet: this is a blocking step.
  4. Probe order 101. Its customer_id is 2. Hash it to bucket 2, look inside, find id 2 (Ben): a match, so emit a joined row. The lookup cost a hash and a compare, not a scan of customers.
  5. Probe order 102. Customer 1 hashes to bucket 1 and matches Asha. Rows can stream out as soon as they match.
  6. Probe order 103. Another order from customer 2: the same bucket, the same match. Many probe rows can hit one build row.
  7. Probe order 104. Customer 9 hashes to bucket 1 as well (9 mod 4 = 1). A hash tells you where to look, not that the key is there: the bucket holds id 1, not 9, so no match, and the order is dropped (for an inner join).
  8. Probe order 105, then done. Customer 3 hashes to bucket 3 and matches Chen. Four matched rows came out after one pass over each input: cost roughly N + M, instead of N × M comparisons.

Sort-merge join

Sort both inputs on the join key, then walk them side by side with one pointer each, like zipping two sorted lists. Equal keys produce output; the smaller key's pointer advances. If an input is already sorted, say because it comes out of a B-tree index in key order, the sort is free and the merge is a single cheap pass over both. Merge join also hands its output over sorted, which can spare an ORDER BY later. It is the natural pick for large inputs that are already ordered, and when the hash table would not fit in memory.

All three are small enough to write yourself. This script runs each on two lists of 2,000 rows with 1,000 distinct keys, and checks that they return the same pairs:

import random
import time

random.seed(5)
A = [(i, random.randint(0, 999)) for i in range(2000)]      # (row id, join key)
B = [(j, random.randint(0, 999)) for j in range(2000)]

def nested_loop(A, B):
    return [(a, b) for a in A for b in B if a[1] == b[1]]

def hash_join(A, B):
    table = {}
    for b in B:                                  # build
        table.setdefault(b[1], []).append(b)
    return [(a, b) for a in A for b in table.get(a[1], [])]     # probe

def sort_merge(A, B):
    A, B = sorted(A, key=lambda r: r[1]), sorted(B, key=lambda r: r[1])
    out, i, j = [], 0, 0
    while i < len(A) and j < len(B):
        if A[i][1] < B[j][1]:
            i += 1
        elif A[i][1] > B[j][1]:
            j += 1
        else:                                    # equal keys: pair A[i] with the whole run in B
            k = j
            while k < len(B) and B[k][1] == A[i][1]:
                out.append((A[i], B[k])); k += 1
            i += 1                               # next A row may share the key, so j stays
    return out

results = []
for f in (nested_loop, hash_join, sort_merge):
    t = time.perf_counter()
    r = f(A, B)
    print(f"{f.__name__:12} {len(r)} pairs  {(time.perf_counter() - t) * 1000:7.1f} ms")
    results.append(sorted(r))
print("all three agree:", results[0] == results[1] == results[2])
nested_loop  3901 pairs     50.1 ms
hash_join    3901 pairs      0.4 ms
sort_merge   3901 pairs      1.9 ms
all three agree: True

Same answer, wildly different work: the nested loop made 4 million comparisons; the hash join made 4,000 hash operations. In Postgres you will see all three as Nested Loop, Hash Join and Merge Join; recent MySQL versions have hash joins too. The choice depends on sizes, indexes, available memory and the planner's estimates, which brings us to the part that goes wrong.

Cost-based optimisation and its guesses

The planner cannot run each candidate plan to see which is fastest. Instead it estimates: each operator gets a cost (roughly, pages read and rows processed, in made-up units), and the cheapest total wins. Estimating cost needs to know how many rows each step produces. That number is the cardinality estimate, and it comes from statistics the database gathers about each table and column: the total row count, the number of distinct values, the most common values, and a histogram of how values are spread. ANALYZE refreshes them (Postgres also runs it automatically in the background, and SQLite has ANALYZE and PRAGMA optimize).

From the statistics comes selectivity: the fraction of rows a condition keeps. "status = 'failed'" with 1% failed rows has selectivity 0.01, so on a million-row table the planner expects 10,000 rows. Joins multiply: the planner estimates how many rows come out of a join, then uses that as the input size for the next step, so errors compound as the plan grows. The planner also has to choose a join order, and the number of possible orders grows factorially with the number of tables, so real planners prune the search with dynamic programming and heuristics.

Here is a small case where statistics change the plan. 99% of the jobs are done, 1% are failed, and there is an index on status:

import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE jobs (id INTEGER PRIMARY KEY, status TEXT, payload TEXT)")
# 99% of jobs are 'done'; 1% are 'failed'
db.executemany("INSERT INTO jobs VALUES (?,?,?)",
               [(i, "failed" if i % 100 == 0 else "done", "x" * 40)
                for i in range(1, 100001)])
db.execute("CREATE INDEX idx_status ON jobs(status)")

def plan(sql):
    print(sql)
    for row in db.execute("EXPLAIN QUERY PLAN " + sql):
        print("    ", row[3])

queries = ["SELECT * FROM jobs WHERE status = 'done'",
           "SELECT * FROM jobs WHERE status = 'failed'"]

print("-- before ANALYZE: the planner has no statistics")
for q in queries: plan(q)

db.execute("ANALYZE")
print("\nsqlite_stat1 now holds:", db.execute("SELECT * FROM sqlite_stat1").fetchall())
print("-- after ANALYZE")
for q in queries: plan(q)
-- before ANALYZE: the planner has no statistics
SELECT * FROM jobs WHERE status = 'done'
     SEARCH jobs USING INDEX idx_status (status=?)
SELECT * FROM jobs WHERE status = 'failed'
     SEARCH jobs USING INDEX idx_status (status=?)

sqlite_stat1 now holds: [('jobs', 'idx_status', '100000 50000')]
-- after ANALYZE
SELECT * FROM jobs WHERE status = 'done'
     SCAN jobs
SELECT * FROM jobs WHERE status = 'failed'
     SEARCH jobs USING INDEX idx_status (status=?)

Before ANALYZE, SQLite has no idea how common each value is and uses the index for both. Afterwards it has learned that an average value matches about half the table, and for 'done' it decides a full scan is cheaper than 99,000 index lookups. Nothing about the data changed. Only the planner's knowledge did. (The exact internals of how SQLite tells the two values apart vary by build; the lesson is that statistics steer plans.)

Why bad estimates produce bad plans

The plan is only as good as its guesses. Typical causes of a wrong estimate:

  • Stale statistics. The table grew from 1,000 to 10 million rows since the last ANALYZE, so a plan that suited a tiny table is now terrible.
  • Correlated columns. Planners usually assume conditions are independent: city = 'Paris' AND country = 'France' is estimated as the product of two selectivities, far too small, because one implies the other. Postgres lets you declare such relationships with CREATE STATISTICS.
  • Skew. Averages hide a hot value: the one customer with 40% of all orders.
  • Expressions and parameters the planner cannot see through, so it falls back on a default guess.

If the planner thinks a join returns 1 row when it returns 50,000, it may choose a nested loop that does 50,000 expensive lookups. The query is "correct" and the plan is catastrophic. The fix is almost always better statistics, not hints.

Reading EXPLAIN

You have already been reading EXPLAIN QUERY PLAN output in SQLite. It prints the chosen access paths and join order, one line per table, indented to show nesting, and it does not execute the query or print estimates. Run it in the sqlite3 shell or from Python as above. Look for three things: which tables are SCANned, which indexes are used (and whether they cover the query), and the join order.

Postgres goes further. Plain EXPLAIN shows the plan with estimated costs and row counts. EXPLAIN ANALYZE runs the query and adds what really happened, so you can compare the planner's guess to the truth:

EXPLAIN ANALYZE SELECT c.name, o.total FROM customers c
JOIN orders o ON o.customer_id = c.id WHERE c.country = 'DE';

 Hash Join  (cost=29.50..1456.77 rows=12500 width=18) (actual time=0.412..14.903 rows=13100 loops=1)
   Hash Cond: (o.customer_id = c.id)
   ->  Seq Scan on orders o  (cost=0.00..926.00 rows=50000 width=12) (actual time=0.011..5.210 rows=50000 loops=1)
   ->  Hash  (cost=17.00..17.00 rows=250 width=14) (actual time=0.380..0.381 rows=262 loops=1)
         Buckets: 1024  Batches: 1  Memory Usage: 20kB
         ->  Seq Scan on customers c  (cost=0.00..17.00 rows=250 width=14) (actual time=0.009..0.201 rows=262 loops=1)
               Filter: ((country)::text = 'DE'::text)
               Rows Removed by Filter: 738
 Planning Time: 0.210 ms
 Execution Time: 15.602 ms

How to read it, inside out: the plan is a tree, so start at the most indented lines. Seq Scan on customers filters 1,000 rows down to 262, and the planner had guessed 250 (rows=250 versus actual … rows=262): a good estimate. Those rows are hashed (Hash, one batch, so it fit in memory). Then Seq Scan on orders streams past the hash table, and Hash Join emits 13,100 rows against an estimate of 12,500. The cost=a..b pair is startup cost then total cost in the planner's own units: useful for comparing plans, meaningless as seconds. The actual time is in milliseconds.

What EXPLAIN ANALYZE adds is exactly the thing that matters most: estimated rows next to actual rows, at every node. When you debug a slow query, find the first node where the two diverge by a factor of ten or more. That is where the planner went wrong, and everything above it is built on the mistake. For example, a line like this:

Nested Loop  (cost=0.29..8.33 rows=1 width=40) (actual time=0.05..912.4 rows=48000 loops=1)

says the planner expected 1 row and got 48,000, so it picked a plan that is great for 1 row (a nested loop) and awful for 48,000. Two cautions: loops matters (the actual figures are per loop, so multiply by it), and because EXPLAIN ANALYZE really executes the statement, wrap an UPDATE or DELETE in a transaction you then roll back. Common performance traps

1. N+1 queries

Application code, especially with an ORM, loads a list of things and then loops over it, fetching a related row for each: one query for 5,000 posts, then 5,000 more for their authors. That is N+1 queries when one join would do. Each query pays parsing, planning and, usually, a network round trip.

import random
import sqlite3
import time

random.seed(2)
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE authors (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE posts (id INTEGER PRIMARY KEY, author_id INTEGER, title TEXT);
""")
db.executemany("INSERT INTO authors VALUES (?,?)",
               [(i, f"author{i}") for i in range(1, 2001)])
db.executemany("INSERT INTO posts VALUES (?,?,?)",
               [(i, random.randint(1, 2000), f"title{i}") for i in range(1, 20001)])

def n_plus_one():                      # 1 query for the posts + 1 per post
    out = []
    for title, author_id in db.execute("SELECT title, author_id FROM posts LIMIT 5000").fetchall():
        (name,) = db.execute("SELECT name FROM authors WHERE id = ?", (author_id,)).fetchone()
        out.append((title, name))
    return out

def one_join():                        # 1 query, total
    return db.execute("""
        SELECT p.title, a.name
        FROM (SELECT title, author_id FROM posts LIMIT 5000) p
        JOIN authors a ON a.id = p.author_id""").fetchall()

for f in (n_plus_one, one_join):
    t = time.perf_counter()
    rows = f()
    print(f"{f.__name__:12} {len(rows)} rows  {(time.perf_counter() - t) * 1000:6.1f} ms")
print("queries sent: n_plus_one = 5001, one_join = 1")
print("extra cost if each round trip took 0.5 ms:", 5000 * 0.5 / 1000, "seconds")
n_plus_one   5000 rows     5.6 ms
one_join     5000 rows     2.2 ms
queries sent: n_plus_one = 5001, one_join = 1
extra cost if each round trip took 0.5 ms: 2.5 seconds

Here everything is in one process, so the loop costs only about 2.5 times the join. Put a network between the app and the database and every one of those 5,001 trips pays the round-trip latency from networking chapter 13. At an illustrative 0.5 ms per trip that is 2.5 seconds, against a single trip for the join. N+1 is the most common database performance bug in web applications, because it looks harmless in development with ten rows.

2. Functions on indexed columns

An index on created is sorted by created, not by substr(created, 1, 7). Wrap the column in a function and the database cannot seek into the index, because it would have to evaluate the function for every entry. The fix is to move the work to the other side, as a range on the bare column. (Some databases let you build an index on the expression itself: SQLite and Postgres both support expression indexes.)

3. SELECT *

Asking for every column drags the whole row out of the table, and it blocks index-only scans: an index that covers id cannot cover *. It also breaks silently when someone adds a 10 MB column. Ask for the columns you need.

4. OFFSET pagination

LIMIT 20 OFFSET 250000 cannot jump to row 250,000. The database produces all 250,000 earlier rows and throws them away. Each page costs more than the last. Keyset pagination (also called the seek method) remembers where the last page ended and asks for what comes after: WHERE id > :last_seen_id ORDER BY id LIMIT 20. An index seeks straight to that key, so every page costs the same.

import random
import sqlite3
import time

random.seed(3)
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE t (id INTEGER PRIMARY KEY, created TEXT, payload TEXT)")
db.executemany("INSERT INTO t VALUES (?,?,?)",
               [(i, f"2026-{random.randint(1,12):02d}-{random.randint(1,28):02d}", "p" * 50)
                for i in range(1, 300001)])
db.execute("CREATE INDEX idx_created ON t(created, id)")

def run(label, sql):
    t = time.perf_counter()
    n = len(db.execute(sql).fetchall())
    ms = (time.perf_counter() - t) * 1000
    print(f"{label:38} {n:6} rows {ms:8.2f} ms")

print("-- a function on the indexed column")
run("substr(created,1,7) = '2026-03'", "SELECT id FROM t WHERE substr(created,1,7) = '2026-03'")
run("created >= '2026-03-01' AND < '2026-04-01'",
    "SELECT id FROM t WHERE created >= '2026-03-01' AND created < '2026-04-01'")

print("\n-- SELECT * versus only what the index covers")
run("SELECT * ... WHERE created = ...", "SELECT * FROM t WHERE created = '2026-05-05'")
run("SELECT id ... WHERE created = ...", "SELECT id FROM t WHERE created = '2026-05-05'")

print("\n-- paging deep into a result")
run("OFFSET 250000 LIMIT 20", "SELECT * FROM t ORDER BY id LIMIT 20 OFFSET 250000")
run("keyset: id > 250000 LIMIT 20", "SELECT * FROM t WHERE id > 250000 ORDER BY id LIMIT 20")

for q in ("SELECT id FROM t WHERE substr(created,1,7) = '2026-03'",
          "SELECT id FROM t WHERE created >= '2026-03-01' AND created < '2026-04-01'"):
    print("\n" + q)
    for row in db.execute("EXPLAIN QUERY PLAN " + q):
        print("    ", row[3])

All four traps show up. The function call is about 3.6 times slower than the range in this run (and its plan says SCAN, even if it is a scan of the covering index; SEARCH is the word you want). SELECT * costs several times more than the covered column. And the deep OFFSET is far slower than the keyset page, and gets worse the deeper you go. Keyset has trade-offs: you cannot jump to "page 500", and the ordering must be on a unique key. If you sort by a non-unique column like created, add the primary key as a tie-breaker and compare both columns as a pair, which SQLite and Postgres both accept:

SELECT * FROM t
WHERE (created, id) > (:last_created, :last_id)
ORDER BY created, id
LIMIT 20;

Other quiet index-killers

A LIKE '%word' with a leading wildcard cannot use an ordinary B-tree index. Comparing a column to a value of a different type can force a conversion on every row in some databases. And an index on (a, b) helps a filter on a, or on a and b, but not on b alone (chapter 7). In all of these, EXPLAIN tells you in one second.

Prepared statements and plan caching

Parsing and planning cost something, and a busy application sends the same query shape thousands of times with different values. A prepared statement separates the two: you send the SQL once with placeholders (? in SQLite, $1 in Postgres), and then send just the values. The database can parse once and often reuse the plan. Python's sqlite3 module keeps a small cache of compiled statements for you. Postgres can keep a plan for a prepared statement, and chooses between plans made for the specific values and a more general one; ORMs and connection poolers in "transaction" mode interact with this in ways worth reading about when you meet them.

Placeholders have a second, far more important job.

SQL injection: always use parameters

If you build SQL by pasting user input into a string, a user can type SQL. The input x' OR '1'='1 turns WHERE name = '…' into a condition that is always true:

import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE users (name TEXT, secret TEXT);
INSERT INTO users VALUES ('alice', 'alice-pw'), ('bob', 'bob-pw');
""")

evil = "x' OR '1'='1"             # what an attacker types into the "name" box

# WRONG: the input becomes part of the SQL text
sql = f"SELECT name, secret FROM users WHERE name = '{evil}'"
print("built SQL:", sql)
print("rows:     ", db.execute(sql).fetchall())

# RIGHT: the SQL text is fixed; the value travels separately as a parameter
print("\nparameterised rows:", db.execute("SELECT name, secret FROM users WHERE name = ?", (evil,)).fetchall())
built SQL: SELECT name, secret FROM users WHERE name = 'x' OR '1'='1'
rows:      [('alice', 'alice-pw'), ('bob', 'bob-pw')]

parameterised rows: []

With a parameter, the text x' OR '1'='1 is just a value to compare against names. It can never become SQL. Never build SQL with string formatting, + or f-strings from untrusted input. Parameters protect values; they cannot stand in for table or column names, so if those come from users, check them against a fixed allow-list.

Distributed systems connection

Everything here reappears at cluster scale. A distributed SQL engine plans a query across machines: a broadcast join is a hash join whose build side is copied to every node, and a shuffle join repartitions both inputs by join key so matching rows meet on the same machine, then runs a local hash or merge join (see batch processing). Predicate pushdown sends the filter to where the data lives, so less crosses the network. A query that needs rows from many shards is a scatter-gather, and its slowest shard sets the latency (sharding). And N+1 gets far worse when the "database" is a service across the network, where each extra round trip costs real milliseconds (networking ch. 13).

Key takeaways

  • A query goes parse → rewrite → plan → execute. SQL says what; the planner picks how.
  • A plan is a tree of operators; the iterator model pulls one row at a time through next() calls, and blocking operators like sort and hash build must read all input first.
  • Access paths: sequential scan, index scan (random fetches), index-only scan (no table access). An index is not always faster; it depends on how many rows match.
  • Nested loop costs about N × M (N × log M with an index), hash join about N + M with memory, sort-merge about the cost of sorting, free if the inputs arrive sorted.
  • The planner works from statistics and cardinality estimates. Stale, skewed or correlated data gives bad estimates, which gives bad plans. Compare estimated and actual rows with EXPLAIN ANALYZE.
  • Watch for N+1 queries, functions on indexed columns, SELECT * and deep OFFSET paging. Use keyset pagination for deep pages.
  • Always use parameters; never paste input into SQL text.

Check your understanding

In the iterator (Volcano) model, how does a row get from a table scan to the top of the plan?

  1. The scan pushes all its rows up to its parent as fast as it can
  2. The top operator calls next() on its child, which calls next() on its child, down to the scan, and one row flows back up per call
  3. The planner copies the whole table into one big temporary result before the next operator starts
  4. Each operator runs in its own thread and sends rows over the network
Demand flows down, rows flow up, one at a time. That is why LIMIT 10 can stop early: the top just stops calling. Blocking operators (sort, hash build) are the exception: they must consume all their input first.

A hash join joins customers (4 rows) with orders (1,000,000 rows) on equality. Which side should be the build side, and what is the cost roughly?

  1. Orders, because it is bigger; cost about N × M
  2. Either side; cost about N log N
  3. Customers, because the hash table is small enough to hold in memory; cost about N + M
  4. Neither: hash joins need an index on both sides
Build on the smaller input so the hash table fits in memory, then stream the large input past it. One pass over each side gives about N + M work. No index is required, but the condition must be an equality.

A query shows rows=1 as the planner's estimate but actual rows=48000 on a Nested Loop node. What is the most likely consequence?

  1. The planner chose a plan that is good for one row, such as a nested loop, and will be very slow for 48,000 rows
  2. The query returns the wrong answer
  3. The database ignores the plan and falls back to a sequential scan
  4. Nothing: estimates and actuals are never compared
A bad estimate does not change the answer, only the plan. The planner picks the algorithm that is cheapest for the row count it believes. Stale statistics, skew and correlated columns are the usual causes; run ANALYZE and look for the first node where estimate and actual diverge.

There is an index on orders(created). Which query can use it to seek?

  1. WHERE substr(created, 1, 7) = '2026-03'
  2. WHERE lower(created) = '2026-03-05'
  3. WHERE created || '' = '2026-03-05'
  4. WHERE created >= '2026-03-01' AND created < '2026-04-01'
The index is sorted by the raw column. A function around the column hides that order, so the database must evaluate it on every row. A range on the bare column lets it seek to the start and read along the index. (An expression index on the function would also work.)

Why does OFFSET 250000 LIMIT 20 get slower for deeper pages, and what avoids it?

  1. The index becomes fragmented; rebuild the index
  2. The database cannot cache results; add more RAM
  3. It has to produce and discard the first 250,000 rows; use keyset pagination (WHERE id > :last_id ORDER BY id LIMIT 20)
  4. LIMIT is applied before ORDER BY; swap them
OFFSET is not a jump. The rows before it are still produced, then thrown away. Keyset pagination remembers the last key and seeks straight to it, so each page costs the same.

A web handler runs SELECT * FROM posts, then for each of 100 posts runs SELECT name FROM authors WHERE id = ?. What is this called, and what is the standard fix?

  1. A deadlock; add a lock timeout
  2. The N+1 query problem; fetch it in one query with a JOIN (or one IN (…) query)
  3. SQL injection; use a firewall
  4. A phantom read; raise the isolation level
That is 101 queries where one will do, and each pays parsing, planning and a network round trip. A JOIN, or a single batched query, fetches all the authors at once. The ORMs' 'eager loading' options exist for exactly this.

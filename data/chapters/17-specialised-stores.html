Search & Specialised Stores

A B-tree is superb at "find this key" and "give me this range", and hopeless at "find documents about quick foxes" or "the ten products most like this photo". Some questions have their own data structures. This chapter is a quick tour of the main ones and the single rule that keeps them from becoming a mess.

Why this matters

Sooner or later a product needs search, metrics, recommendations or a map. You can often start inside your main database, and you should know when that stops being enough. Knowing what a search engine or a vector index actually is also tells you what it is good at, how it can be wrong, and why it must never be the only copy of your data.

One index does not fit every question

The indexes of chapter 7 answer questions about the value of a column. Other questions are shaped differently: which documents contain these words; which measurements fell in this hour; who is within three friendships of me; which vectors are closest to this one; which restaurants are within a kilometre. Each has a data structure built for it. All of them are derived data: a second, re-organised view of data that lives somewhere else. We will end on why that matters.

Full-text search: the inverted index

Scanning every document for a word does not scale, and a B-tree on the text column only finds whole values. The answer is an inverted index: instead of "document, then its words", store "word, then its documents". It is the index at the back of a textbook.

Building the index starts with tokenising: split text into terms, lowercase them, usually drop very common stop words ("the", "a") and reduce words to a root, called stemming ("foxes" and "fox" become one term). Each term gets a postings list: the sorted ids of the documents that contain it (real ones also store positions and counts). An AND query intersects lists, an OR query merges them. Both are fast because the lists are sorted.

Matching is not enough; people want the best match first. Classic TF-IDF scores a document higher when the query term appears often in it (term frequency) and lower when the term appears in nearly every document (inverse document frequency), so a rare word matters more than "the". BM25 is a refinement of the same idea that also caps the benefit of repeating a word and accounts for document length; it is the standard default ranking in modern Lucene-based search. Here is a tiny version you can run.

import re, math
from collections import defaultdict

docs = {
    1: "The quick brown fox jumps over the lazy dog",
    2: "A quick brown dog outpaces a quick fox",
    3: "Foxes are quick; dogs are lazy",
    4: "Databases index documents so searches are fast",
}
STOP = {"the", "a", "are", "so", "over"}

def stem(w):                                   # very crude: real engines use proper stemmers
    if w.endswith("es") and len(w) > 4: return w[:-2]
    if w.endswith("s") and len(w) > 3:  return w[:-1]
    return w

def tokenise(text):
    return [stem(w) for w in re.findall(r"[a-z]+", text.lower()) if w not in STOP]

index = defaultdict(dict)                      # term -> {doc_id: term frequency}  (postings lists)
for doc_id, text in docs.items():
    for term in tokenise(text):
        index[term][doc_id] = index[term].get(doc_id, 0) + 1

def search(query):
    terms = tokenise(query)
    postings = [set(index.get(t, {})) for t in terms]
    hits = set.intersection(*postings) if postings else set()      # AND query
    n = len(docs)
    def score(d):                                                  # TF-IDF
        return sum(index[t][d] * math.log(n / len(index[t])) for t in terms)
    return sorted(((round(score(d), 3), d) for d in hits), reverse=True)

print("postings for 'quick':", dict(index["quick"]))
print("postings for 'fox'  :", dict(index["fox"]))
print("search 'quick fox'  :", search("quick fox"))
print("search 'lazy dogs'  :", search("lazy dogs"))
print("search 'quick cat'  :", search("quick cat"))
$ python3 search.py
postings for 'quick': {1: 1, 2: 2, 3: 1}
postings for 'fox'  : {1: 1, 2: 1, 3: 1}
search 'quick fox'  : [(0.863, 2), (0.575, 3), (0.575, 1)]
search 'lazy dogs'  : [(0.981, 3), (0.981, 1)]
search 'quick cat'  : []

Document 2 ranks first for "quick fox" because it says "quick" twice. Notice that the crude stemmer let the query word "fox" match "Foxes" in document 3, and that "quick cat" correctly finds nothing, because the AND of the two lists is empty. Lucene is the open-source library that does this properly (segments, compression, relevance scoring); Elasticsearch and OpenSearch are distributed search servers built around it. They split an index into shards, each a Lucene index over its own documents, which is exactly the local, scatter/gather secondary index of chapter 16.

Try it yourself: full-text search without a server

SQLite ships an inverted index of its own, FTS5, but only if it was compiled in. I checked: the SQLite behind Python here (version 3.53.4) has it. Check yours first, then run the same documents through it. Its rank column is a BM25 score.

import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE VIRTUAL TABLE docs USING fts5(body, tokenize='porter')")   # porter = a stemmer
db.executemany("INSERT INTO docs(body) VALUES (?)", [
    ("The quick brown fox jumps over the lazy dog",),
    ("A quick brown dog outpaces a quick fox",),
    ("Foxes are quick; dogs are lazy",),
    ("Databases index documents so searches are fast",),
])
# rank is FTS5's built-in BM25 score; smaller (more negative) means a better match
print(db.execute("SELECT rowid, body FROM docs WHERE docs MATCH 'quick fox' ORDER BY rank").fetchall())
print(db.execute("SELECT rowid FROM docs WHERE docs MATCH 'search'").fetchall())   # matches 'searches'
$ python3 -c "import sqlite3; db=sqlite3.connect(':memory:'); db.execute('CREATE VIRTUAL TABLE t USING fts5(x)'); print('FTS5 ok')"
FTS5 ok
$ python3 fts.py
[(2, 'A quick brown dog outpaces a quick fox'), (3, 'Foxes are quick; dogs are lazy'), (1, 'The quick brown fox jumps over the lazy dog')]
[(4,)]

If the first command prints no such module: fts5, your build lacks FTS5 and the hand-written index above is your fallback. PostgreSQL has built-in full-text search too (tsvector with a GIN index), which is often enough before you add a separate search server.

Analogy: the library catalogue

The book index at the back of a textbook, or the subject catalogue in a library, lists each topic with the places it appears, so you never read every page. That is a postings list.

Where it breaks down: a printed index is built once and frozen. A search index must absorb new documents constantly, and engines handle this by writing small new segments and merging them later (the same trick as the LSM trees of chapter 5), so a new document is typically searchable after a short refresh delay, not instantly.

Time-series stores

Metrics, sensor readings and logs share a shape: points of (time, series, value), written continuously in roughly time order, almost never updated, queried by time window ("CPU of web-1 for the last hour"), and valued mostly while recent. A time-series database (Prometheus, InfluxDB, TimescaleDB, built on PostgreSQL, are examples) exploits this:

  • Append-heavy writes. New points go to the end, in the LSM or chunked style, with timestamps and values compressed very well because neighbours are similar (the same reasoning as column stores).
  • Downsampling. Old data is rolled up into coarser summaries: keep every 10-second reading for a day, one per minute for a month, one per hour for a year. You trade detail you will not miss for space.
  • Retention. Data past its useful age is dropped, cheaply, by deleting whole time chunks rather than row by row.
import sqlite3
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE cpu(ts INTEGER, host TEXT, pct REAL)")     # ts = seconds
# one reading every 10 s for 3 minutes
db.executemany("INSERT INTO cpu VALUES (?,?,?)",
               [(t, "web-1", 20 + (t * 7) % 50) for t in range(0, 180, 10)])
print("raw points:", db.execute("SELECT count(*) FROM cpu").fetchone()[0])
rows = db.execute("""SELECT ts/60 AS minute, count(*) AS n, round(avg(pct),1), max(pct)
                     FROM cpu GROUP BY minute ORDER BY minute""").fetchall()
for r in rows: print(r)
$ python3 rollup.py
raw points: 18
(0, 6, 36.7, 60.0)
(1, 6, 40.0, 60.0)
(2, 6, 43.3, 60.0)

Eighteen points became three rows of (minute, count, average, max). A time-series database does this rollup continuously and keeps the max alongside the average, because averages hide spikes.

Graph databases

When the question is about relationships ("friends of friends who also like this band", "is there a path from this account to a flagged one?"), a graph database stores nodes and edges directly, with each node holding pointers to its neighbours so that hopping an edge is cheap instead of a join. Neo4j is a well-known example, and its query language, Cypher, describes patterns of nodes and edges. We met graph data models in chapter 1. For a few hops, a relational database with the right indexes (or a recursive query) often copes; a dedicated graph store earns its place when queries walk many hops through highly connected data.

Vector databases

A machine-learning model can turn text, an image or a song into an embedding: a list of hundreds or thousands of numbers, positioned so that similar items land near each other. "Find similar" becomes nearest-neighbour search: given a query vector, return the stored vectors closest to it, typically by cosine similarity or Euclidean distance.

import math

# toy 3-dimensional "embeddings" (real ones have hundreds or thousands of dimensions)
items = {
    "espresso":   (0.9, 0.1, 0.0),
    "latte":      (0.8, 0.3, 0.0),
    "bicycle":    (0.0, 0.1, 0.9),
    "scooter":    (0.1, 0.2, 0.8),
    "croissant":  (0.5, 0.7, 0.0),
}
def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (math.hypot(*a) * math.hypot(*b))

query = (0.85, 0.2, 0.0)                       # "something like coffee"
ranked = sorted(items, key=lambda k: cosine(query, items[k]), reverse=True)   # exact, brute force
for name in ranked[:3]:
    print(f"{name:10s} {cosine(query, items[name]):.3f}")
$ python3 vectors.py
espresso   0.993
latte      0.992
croissant  0.752

That brute-force loop is exact, and perfectly fine for thousands of vectors. For millions it is too slow, and no B-tree helps, because "closeness" in 768 dimensions has no useful sort order. So vector databases use approximate nearest-neighbour (ANN) indexes, which return very likely the closest few, much faster. The popular HNSW index (hierarchical navigable small world) links each vector to some near neighbours in layered graphs; a search starts in a sparse top layer, hops greedily towards the query, and drops down to finer layers. Others cluster the space and only search the nearest clusters. The honest trade is recall against speed: an ANN index may miss a true neighbour, and you tune how hard it looks. PostgreSQL's pgvector extension adds vector columns and such indexes, so for many products "vectors inside the main database" is enough.

Geospatial indexes

"Restaurants within a kilometre" is a two-dimensional range query, and a single B-tree sorts by only one dimension. Two standard answers: geohash turns a latitude and longitude into a short string where, roughly, shared prefixes mean nearby places, so an ordinary index on that string finds a neighbourhood; and the R-tree groups nearby shapes into nested bounding rectangles, so a search skips every rectangle that cannot overlap the query area. PostGIS uses R-tree-style indexes (via PostgreSQL's GiST), and SQLite has an R*Tree module.

# geohash by hand: interleave longitude/latitude bisection bits, 5 bits per base-32 character
B32 = "0123456789bcdefghjkmnpqrstuvwxyz"
def geohash(lat, lon, chars=6):
    lat_r, lon_r, bits, even, out, v = [-90.0, 90.0], [-180.0, 180.0], 0, True, "", 0
    while len(out) < chars:
        rng, x = (lon_r, lon) if even else (lat_r, lat)
        mid = (rng[0] + rng[1]) / 2
        v <<= 1
        if x >= mid: v |= 1; rng[0] = mid
        else: rng[1] = mid
        even = not even; bits += 1
        if bits == 5: out += B32[v]; bits = 0; v = 0
    return out
print(geohash(57.64911, 10.40744, 11))   # the standard example from the geohash literature
print(geohash(51.5007, -0.1246), geohash(51.5014, -0.1419), geohash(48.8584, 2.2945))
$ python3 geohash.py
u4pruydqqvj
gcpuvp gcpuuz u09tun

The two London points (Big Ben and Buckingham Palace, a kilometre or so apart) share the prefix gcpu, while Paris starts u0. The catch: two points just either side of a cell boundary can have very different prefixes, so a real query also checks the neighbouring cells.

Specialised does not mean authoritative

Search engines, vector indexes and time-series stores are optimised for their one question, and they usually trade away something a database gives you: strict transactions, immediate visibility of writes, careful durability guarantees, or exact answers. Treating them as your primary store is how data gets lost, or silently drifts from the truth.

The rule: one system of record, many derived stores

Keep exactly one system of record, the database that holds the authoritative, durable, transactionally-correct version of each fact, usually your relational or main database. Everything else (search index, cache, vector index, analytics warehouse) is derived: built from the system of record, and rebuildable from it.

The payoff is large. If the search index is corrupted, or you change your analyzer, or you adopt a new vector model, you rebuild from the system of record. If instead the search index were the only copy, you would have no recourse. The flow itself is the subject of chapter 19: change data capture reads the database's own log and feeds the others. Resist the shortcut of having the application write to the database and the search server in two separate calls (a dual write): if one succeeds and the other fails, they disagree forever, with nothing to say which is right.

Distributed systems connection

Derived stores are eventually consistent with the system of record: the index lags the database by a refresh interval or a replication delay, so "I just saved it, why can't I search for it?" is a normal symptom, not a bug (compare replication lag in chapter 15). Every arrow in the diagram is a pipeline that can fall behind, repeat or drop messages, and idempotent consumers are how you cope. Search clusters also scale exactly like sharded databases.

Key takeaways

  • An inverted index maps each term to a sorted postings list of documents; queries intersect or merge lists. Ranking uses TF-IDF or BM25.
  • Lucene is the library; Elasticsearch and OpenSearch are distributed servers over it. SQLite FTS5 and PostgreSQL full-text search cover small cases.
  • Time-series stores bet on append-only writes, downsampling old data and dropping whole time chunks for retention.
  • Graph databases make multi-hop relationship queries cheap; vector databases find nearest neighbours in embedding space, mostly with approximate indexes such as HNSW, trading recall for speed.
  • Geospatial data uses geohash prefixes or R-trees to answer "what is near here".
  • Keep one system of record. Treat specialised stores as derived, rebuildable copies, fed by a log or CDC rather than dual writes.

Check your understanding

What does an inverted index store?

  1. For each document, the list of its words in order
  2. For each term, a sorted list of the documents that contain it
  3. A hash of each whole document
  4. The embedding of each word
"Inverted" because it flips document-to-words into word-to-documents. Queries then read only the postings lists for their words.

Why does TF-IDF or BM25 give a rare query word more weight than a common one?

  1. Rare words are shorter
  2. Common words are removed from every document
  3. It makes the postings list smaller
  4. A word found in almost every document tells you little about which document is the best match
Inverse document frequency down-weights terms that appear everywhere. The match on a rare word is more informative about relevance.

Why do vector databases usually use approximate nearest-neighbour indexes such as HNSW?

  1. Exact search over millions of high-dimensional vectors is too slow, and ANN trades a small chance of missing a true neighbour for a big speed-up
  2. ANN indexes are always exact but smaller
  3. High-dimensional vectors can be sorted like numbers
  4. Approximate search is required by SQL
There is no useful sort order in hundreds of dimensions, so a B-tree cannot help. ANN indexes navigate a graph or clusters to get very likely, not guaranteed, nearest neighbours; recall versus speed is the tuning knob.

A time-series store keeps hourly averages of data older than a month instead of every raw reading. What is this called, and what is the trade-off?

  1. Sharding; it spreads load but scatters queries
  2. Replication; it adds copies but lags
  3. Downsampling; it saves space by giving up fine detail you rarely need
  4. Salting; it spreads hot keys but slows reads
Downsampling rolls detail up into coarser summaries as data ages. Keeping the max as well as the average stops short spikes disappearing.

Your product writes each new order to PostgreSQL and then, in a second call, to the search server. What goes wrong, and what is the better design?

  1. Nothing; two writes are always atomic
  2. If one call fails the two stores disagree. Better: write only to the system of record and feed the search index from its change log
  3. The search server will reject the second write
  4. PostgreSQL cannot be the system of record
Two separate writes can half-fail, and nothing records which store is right. Deriving the index from the database's own log gives it one source and a way to replay.

SQL & the Relational Model

Fifty years after it was proposed, the relational model is still the default way to store data that matters. You describe the answer you want in SQL and the database works out how to get it. By the end of this chapter you will have built a small database, joined its tables, and learned why NULL is the most surprising value in computing.

Why this matters

Even if you end up using other kinds of database, nearly everyone you work with will think in relational terms: tables, keys, joins, constraints. Understanding normalisation is how you tell whether a schema stores each fact once or invites contradictions. And understanding that SQL is declarative is the key that unlocks the next several chapters: indexes, query plans and the reason the same query can run in a millisecond or a minute.

A short history

In 1970, Edgar F. Codd, a researcher at IBM, published "A Relational Model of Data for Large Shared Data Banks". The databases of the day made programmers navigate links between records by hand, so that changing how data was stored meant rewriting every program that read it. Codd's central idea was data independence: describe the data as simple tables (mathematically, relations), and let the system decide how to store and fetch them. Programs would say what they want, not how to walk the data.

That idea became SQL ("Structured Query Language", originally SEQUEL), developed at IBM in the 1970s and standardised in the 1980s. Despite many challengers since, the relational model has stayed dominant for transactional data, partly because of how well data independence has aged: we have changed the storage underneath (disks, SSDs, memory, clusters) without having to change the queries on top.

Tables, rows and columns

A table (formally a relation) is a collection of rows, each of which has the same columns. Each column has a name and a type: integer, text, date and so on. Two properties are worth knowing because they differ from a spreadsheet:

  • A table is a set-like collection. Rows have no inherent order. If you want an order you must ask for it with ORDER BY.
  • A row is a fact. In the table users, one row says "there is a user with this id, name and email".

Primary keys and foreign keys

To refer to a particular row we need something that identifies it. A primary key (PK) is a column, or set of columns, whose value is unique for every row and never NULL. A foreign key (FK) is a column that holds another table's primary key, which is how rows in different tables point at each other. An order belongs to a user, so each order row carries the user's id.

A primary key can be a natural value (an ISBN, an email) or a surrogate, a meaningless number the database hands out. Natural keys have an annoying habit of changing (people change email addresses), so surrogate ids are the common choice.

A runnable SQLite walkthrough

SQLite is a complete SQL database in a library and a single file. The sqlite3 command comes with macOS, and Python's standard library includes the same engine, so everything below runs on your machine. Open a shell and start an in-memory database (it vanishes when you exit). The two dot-commands just make the output readable; they are not SQL.

$ sqlite3 :memory:
sqlite> .headers on
sqlite> .mode column
sqlite> .nullvalue NULL        (do not type this note: it makes missing values show as the word NULL)

CREATE and INSERT

PRAGMA foreign_keys = ON;   -- SQLite only: see the constraints section

CREATE TABLE users (
  id    INTEGER PRIMARY KEY,
  name  TEXT NOT NULL,
  email TEXT NOT NULL UNIQUE
);
CREATE TABLE orders (
  id      INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  item    TEXT NOT NULL,
  cents   INTEGER NOT NULL CHECK (cents >= 0)
);

INSERT INTO users (id, name, email) VALUES
  (1, 'Asha', 'asha@example.com'),
  (2, 'Ben',  'ben@example.com'),
  (3, 'Chen', 'chen@example.com'),
  (4, 'Dara', 'dara@example.com');
INSERT INTO orders (id, user_id, item, cents) VALUES
  (101, 1, 'book',   1500),
  (102, 1, 'pen',     300),
  (103, 2, 'lamp',   2500),
  (104, 3, 'mug',     800);

(Storing money as whole cents in an integer avoids the rounding errors of floating point, a habit worth adopting from day one.)

SELECT, WHERE and ORDER BY

SELECT picks columns, FROM says which table, WHERE filters rows, and ORDER BY sorts the result:

SELECT * FROM users;
SELECT name, email FROM users WHERE name LIKE '%a%' ORDER BY name DESC;
id  name  email
--  ----  ----------------
1   Asha  asha@example.com
2   Ben   ben@example.com
3   Chen  chen@example.com
4   Dara  dara@example.com

name  email
----  ----------------
Dara  dara@example.com
Asha  asha@example.com

(In SQLite, LIKE ignores upper and lower case for ordinary letters, which is why "Asha" and "Dara" both match.)

GROUP BY

GROUP BY collapses rows that share a value into one, and lets you compute an aggregate (COUNT, SUM, AVG, MIN, MAX) over each group:

SELECT user_id, COUNT(*) AS n_orders, SUM(cents) AS total_cents
FROM orders
GROUP BY user_id
ORDER BY total_cents DESC;
user_id  n_orders  total_cents
-------  --------  -----------
2        1         2500
1        2         1800
3        1         800

Dara has no orders, so she has no group, and that user is missing from the answer. Joins can fix that.

Joins, visually

Data is split across tables on purpose (we will see why under normalisation), so questions that span tables need a join: pair up rows from two tables wherever a condition holds. Take every user and every order, and keep the pairs where orders.user_id = users.id. The picture:

Inner join and left join in SQL

SELECT users.name, orders.item, orders.cents
FROM users
JOIN orders ON orders.user_id = users.id;       -- JOIN means INNER JOIN

SELECT users.name, orders.item
FROM users
LEFT JOIN orders ON orders.user_id = users.id;
name  item  cents
----  ----  -----
Asha  book  1500
Asha  pen   300
Ben   lamp  2500
Chen  mug   800

name  item
----  ----
Asha  book
Asha  pen
Ben   lamp
Chen  mug
Dara  NULL

Now Dara shows up, with NULL for her (non-existent) order. Combining a left join with GROUP BY gives the report we wanted, including zeros:

SELECT users.name, COUNT(orders.id) AS n_orders
FROM users LEFT JOIN orders ON orders.user_id = users.id
GROUP BY users.id;
name  n_orders
----  --------
Asha  2
Ben   1
Chen  1
Dara  0

Notice COUNT(orders.id), not COUNT(*). COUNT(*) counts rows, and Dara's single NULL-padded row would have counted as 1; COUNT(column) skips NULLs, so she gets 0.

Try the widget with both join types and compare what happens to Dara. Using a LEFT JOIN and then filtering on the right table in WHERE is a classic trap: WHERE orders.cents > 1000 removes the NULL-padded rows again, quietly turning your left join back into an inner join. Put the condition in the ON clause instead if you want to keep the unmatched users. (We checked: the first form returns only Asha and Ben, the second returns all four users.)

Analogy: matching name tags at a conference

Picture one table of attendees with badge numbers, and another table of lunch orders that each list a badge number. An inner join is "list everyone who ordered lunch, with their name". A left join from the attendees is "list everyone, with their lunch if they ordered one". People with no order are still on the list, with a blank where the lunch would be.

Where it breaks down: a person sitting at a registration desk does one lookup per attendee. A database can match the two lists in several different ways (nested loops, hashing, merging sorted lists), and it will choose the one it thinks is cheapest. See chapter 8.

SQL says what, the planner decides how

Everything above is declarative: you describe the result you want, never the steps to compute it. Contrast that with the loops you would write in Python. Between your SQL and the answer sits the query planner, which considers several possible strategies and picks the one it estimates to be cheapest. You can ask SQLite to show its choice:

EXPLAIN QUERY PLAN
SELECT users.name, orders.item
FROM users JOIN orders ON orders.user_id = users.id
WHERE users.email = 'ben@example.com';
QUERY PLAN
|--SEARCH users USING INDEX sqlite_autoindex_users_1 (email=?)
`--SCAN orders

QUERY PLAN
|--SEARCH users USING INDEX sqlite_autoindex_users_1 (email=?)
`--SEARCH orders USING INDEX idx_orders_user (user_id=?)

The SQL never changed. After we added an index the planner switched from scanning every order to looking up just Ben's. The UNIQUE constraint on email had already created an index automatically. This is data independence at work, and the reason performance tuning is mostly about indexes and statistics, not rewriting queries. We look at indexes in chapter 7 and at reading plans like this in chapter 8.

Normalisation

Normalisation is the practice of structuring tables so each fact is stored in exactly one place. It is easiest to understand by seeing what goes wrong without it. Suppose we kept everything in one flat table:

CREATE TABLE orders_flat (order_id INTEGER, customer TEXT, customer_city TEXT, item TEXT);
INSERT INTO orders_flat VALUES
  (101,'Asha','Lisbon','book'), (102,'Asha','Lisbon','pen'), (103,'Ben','Oslo','lamp');

-- Asha moves, but we only update one of her rows:
UPDATE orders_flat SET customer_city = 'Porto' WHERE order_id = 101;
SELECT customer, customer_city FROM orders_flat WHERE customer = 'Asha';
customer  customer_city
--------  -------------
Asha      Porto
Asha      Lisbon

Asha now lives in two cities at once. That is an update anomaly: because her city is repeated in every one of her orders, changing it means changing many rows, and missing one leaves a contradiction. Two siblings exist too. An insertion anomaly: you cannot record a customer who has not ordered anything yet, because there is no order row to put them in. A deletion anomaly: deleting Ben's only order also deletes the only record that he lives in Oslo.

The normal forms are rules for removing these problems, in increasing strictness. In plain words:

1NF
Every cell holds a single, atomic value, and rows are distinct. No lists crammed into a cell ("book, pen") and no repeating groups of columns (item1, item2, item3). Use another row or table.
2NF
1NF, and every non-key column depends on the whole key, not just part of it. This matters when the key has several columns: if the key is (order_id, product_id), then the product's name depends on only part of the key (product_id), so it belongs in a products table.
3NF
2NF, and non-key columns depend on the key and nothing but the key. In orders_flat, the city depends on the customer, not on the order, so it belongs in a customers table. A common memory aid: "the key, the whole key, and nothing but the key".

The fix for our flat table is the very design we have been using: users holds each person once, orders holds only the user id, and the city lives in one place. Changing it is a single-row update.

When to denormalise

Normalisation gives you correctness at the cost of joins. Denormalisation deliberately breaks the rules by copying data so that reads need fewer joins. It is legitimate when:

  • the data is read far more than written, and the join is a measured bottleneck;
  • the copied value never changes (the price on a past order, a historical address), in which case it is not really a duplicate but a snapshot of what was true;
  • you are building an analytical or caching layer (a summary table, a materialised view, a document in a cache) that can be rebuilt from the normalised source of truth.

The rule of thumb: normalise first, denormalise on purpose and with evidence, and keep one table as the single source of truth that the copies are derived from.

Constraints: rules the database enforces

A constraint is a rule attached to a table that the database checks on every write, so no buggy application can break it. The four you will use most:

  • NOT NULL: this column must have a value.
  • UNIQUE: no two rows may share this value (or combination of values).
  • CHECK (condition): an arbitrary test, such as cents >= 0.
  • FOREIGN KEY / REFERENCES: the value must exist in the referenced table.

Here they are rejecting bad writes against our tables (SQLite's real messages; the "line" numbers depend on how you ran the script, so yours will differ):

INSERT INTO users VALUES (5, NULL, 'x@example.com');
INSERT INTO users VALUES (5, 'Eve', 'asha@example.com');
INSERT INTO orders VALUES (105, 1, 'gift', -5);
INSERT INTO orders VALUES (105, 99, 'ghost', 100);
DELETE FROM users WHERE id = 1;
Runtime error near line 10: NOT NULL constraint failed: users.name (19)
Runtime error near line 11: UNIQUE constraint failed: users.email (19)
Runtime error near line 12: CHECK constraint failed: cents >= 0 (19)
Runtime error near line 13: FOREIGN KEY constraint failed (19)
Runtime error near line 14: FOREIGN KEY constraint failed (19)

The last one is the foreign key protecting the other direction: you cannot delete Asha while orders still point at her. (You can instead declare ON DELETE CASCADE to delete the orders too, or ON DELETE SET NULL.)

SQLite gotchas: foreign keys are off by default

SQLite does not enforce foreign keys unless you run PRAGMA foreign_keys = ON;, and that setting applies per connection, so you need it every time you connect. Without it the ghost order above is accepted silently:

$ sqlite3 :memory: "CREATE TABLE u(id INTEGER PRIMARY KEY); CREATE TABLE o(uid INTEGER REFERENCES u(id)); INSERT INTO o VALUES (99); SELECT 'no pragma: accepted', count(*) FROM o;"
no pragma: accepted|1

Also, SQLite's column types are only hints by default: an INTEGER column will happily store the text 'hello'. Declare the table with STRICT (SQLite 3.37 and later) to enforce types, as other databases like PostgreSQL always do. PostgreSQL and MySQL (with InnoDB) enforce foreign keys without any switch.

NULL and three-valued logic

NULL is not a value, it is "unknown"

NULL means "no value / unknown", and comparing anything to unknown gives unknown, not true or false. SQL therefore has three truth values: true, false and unknown. A WHERE clause keeps only the rows where the condition is true, so unknown behaves like false, until you negate it, when it is still unknown. That produces results that astonish even experienced developers.

SELECT 1 = NULL, NULL = NULL, NULL IS NULL;
SELECT 5 > NULL, NOT (5 > NULL);
1 = NULL  NULL = NULL  NULL IS NULL
--------  -----------  ------------
NULL      NULL         1
5 > NULL  NOT (5 > NULL)
--------  --------------
NULL      NULL

Even NULL = NULL is unknown, so use IS NULL to test for it. Here is how it bites on a table where one person has no nickname (NULL):

CREATE TABLE t (id INTEGER PRIMARY KEY, nick TEXT);
INSERT INTO t VALUES (1,'ann'), (2,NULL), (3,'bob');

SELECT COUNT(*) AS all_rows, COUNT(nick) AS non_null FROM t;
SELECT id FROM t WHERE nick = 'ann';       -- 1
SELECT id FROM t WHERE nick <> 'ann';      -- 3, and not 2 !
SELECT id FROM t WHERE nick IS NULL;       -- 2
SELECT id FROM t WHERE nick NOT IN ('ann', NULL);   -- nothing at all
all_rows  non_null
--------  --------
3         2

id
--
1

id
--
3

id
--
2

(the last query returns no rows)

Row 2 is neither equal to 'ann' nor different from it: we simply do not know. And NOT IN with a NULL in the list is an infamous trap that returns nothing, because "not equal to ann and not equal to unknown" is never certain. Design tip: make columns NOT NULL unless "unknown" is a real state you want to represent.

Postgres and MySQL differences, briefly

Everything above runs in SQLite. In PostgreSQL the same CREATE TABLE works if you write id SERIAL PRIMARY KEY or id INTEGER GENERATED ALWAYS AS IDENTITY for auto-numbered keys, there is no PRAGMA, and LIKE is case-sensitive (use ILIKE for case-insensitive). MySQL uses AUTO_INCREMENT. The relational ideas, joins and constraints are identical.

Try it yourself

Put the CREATE and INSERT statements into a file, say shop.sql, and run sqlite3 :memory: < shop.sql (or paste them in a Python sqlite3 session using executescript). Then:

  1. Find each user's most expensive order. (Hint: MAX(cents) with GROUP BY.)
  2. List users with no orders without a LEFT JOIN, using WHERE id NOT IN (SELECT user_id FROM orders). Then think about why that is safe here but dangerous if orders.user_id could be NULL.
  3. Turn off the foreign-key pragma and insert the ghost order. Then turn it on and find out which rows now violate the rule with a LEFT JOIN ... WHERE users.id IS NULL.
  4. Add ON DELETE CASCADE to the foreign key and delete Asha. What happens to her orders?

Distributed systems connection

Joins and foreign keys are easy on one machine because all the rows are in one place. Once data is split across shards (chapter 16) or services, a join becomes network calls, and a foreign key can no longer be checked by the database. This is a major reason large systems denormalise, or choose partition keys so related rows stay together. SQL's declarative nature helps in the other direction: because queries say what and not how, a distributed SQL engine can split the same query into parallel pieces without changing your code.

Key takeaways

  • The relational model (Codd, 1970) stores facts as rows in tables, linked by primary and foreign keys, and gives you data independence: queries say what, not how.
  • SELECT / WHERE / ORDER BY / GROUP BY cover most reads. A join pairs rows by a condition. INNER keeps only matches, LEFT also keeps unmatched left rows, padded with NULL.
  • SQL is declarative. The planner picks the strategy, and adding an index can change the plan without changing the query (chapters 7 and 8).
  • Normalisation (1NF, 2NF, 3NF: "the key, the whole key, and nothing but the key") prevents update, insertion and deletion anomalies. Denormalise deliberately, for measured reads, with a source of truth.
  • Constraints (NOT NULL, UNIQUE, CHECK, FOREIGN KEY) make the database reject bad data. SQLite needs PRAGMA foreign_keys = ON per connection.
  • NULL means unknown. Comparisons with it are unknown, so use IS NULL and beware of NOT IN and COUNT(*) vs COUNT(column).

Check your understanding

Dara has no orders. Which query lists every user, including Dara?

  1. SELECT ... FROM users JOIN orders ON orders.user_id = users.id
  2. SELECT ... FROM orders GROUP BY user_id
  3. SELECT ... FROM users LEFT JOIN orders ON orders.user_id = users.id
  4. SELECT ... FROM users WHERE orders IS NULL
An inner join drops users without a matching order. A left join keeps every row of the left table and pads the missing side with NULL. The last query is not valid SQL.

A table has a column nick and one row has nick = NULL. What does WHERE nick <> 'ann' do with that row?

  1. Excludes it, because the comparison is unknown rather than true
  2. Includes it, because NULL is different from 'ann'
  3. Raises an error
  4. Includes it only if the column is indexed
Any comparison with NULL yields unknown, and WHERE keeps only rows where the condition is true. To include the NULL rows you must say so: nick <> 'ann' OR nick IS NULL.

A flat table repeats each customer's city on every order. Which problem does that cause, and what fixes it?

  1. Slow joins; fix it by adding more indexes
  2. Violating 1NF; fix it by putting the city in a list column
  3. Data loss; fix it by turning on foreign keys
  4. Update anomalies, because one fact is stored in many rows; fix it by moving customers into their own table (3NF)
The city depends on the customer, not the order, so repeating it invites contradictions when it changes. Splitting customers into a table makes each fact live in one place.

You add an index and the same SQL query becomes much faster without any edit to the query. Which property of SQL explains this?

  1. SQL is compiled to machine code
  2. SQL is declarative: the planner is free to pick a different strategy for the same query
  3. SQL caches results forever
  4. SQL automatically denormalises tables
Because the query states only the result wanted, the planner chooses how to compute it. With an index available, a lookup replaces a full scan. That freedom is the point of data independence.

You open a new SQLite connection and insert an order whose user_id points at a non-existent user. It succeeds, even though the table declares REFERENCES users(id). Most likely reason?

  1. Foreign keys only work on primary-key columns
  2. The user_id column is nullable
  3. SQLite does not enforce foreign keys unless PRAGMA foreign_keys = ON is set on that connection
  4. Foreign keys are only checked on DELETE
SQLite keeps this off by default for backward compatibility, and it is a per-connection setting. PostgreSQL and MySQL/InnoDB enforce foreign keys by default.

The Simplest Database: a Log

Two lines of shell script are a working database. Make them survive crashes, find keys instantly, reclaim space and handle deletes, and you have a real storage engine whose ideas appear in nearly every system in the rest of this course. We build it step by step, and then we find exactly where it stops working.

Why this matters

Every storage engine answers the same two questions: where do I put new data? and how do I find it again? The log answers the first in the cheapest possible way (put it at the end) and then spends the whole chapter on the second. Once you see why it works and where it breaks, B-trees, LSM trees, write-ahead logs, Kafka and replication stop being separate topics: they are all variations on this one idea.

A database in two lines

A database, at its core, does two things: you hand it data and it remembers it, and later you ask for the data back. Here is the smallest thing that qualifies, a pair of bash functions:

#!/bin/bash
db_set() { echo "$1,$2" >> database; }
db_get() { grep "^$1," database | sed -e "s/^$1,//" | tail -n 1; }

db_set key value appends one line, key,value, to a file called database. db_get key finds every line starting with that key, strips the key off, and keeps only the last one. Let's use it, and then do something unkind to it:

source ./db.sh
db_set user:1 Ada
db_set user:2 Grace
db_set user:1 "Ada Lovelace"
echo "get user:1 -> $(db_get user:1)"
echo "get user:2 -> $(db_get user:2)"
echo "get user:3 -> '$(db_get user:3)'"
echo "--- the file:"
cat database
echo "--- 200,000 more records:"
awk 'BEGIN { for (i = 0; i < 200000; i++) print "key" i ",value" i }' >> database
wc -lc database
TIMEFORMAT="get key5      took %3R s"; time db_get key5 > /dev/null
TIMEFORMAT="get key199999 took %3R s"; time db_get key199999 > /dev/null
$ bash try4.sh
get user:1 -> Ada Lovelace
get user:2 -> Grace
get user:3 -> ''
--- the file:
user:1,Ada
user:2,Grace
user:1,Ada Lovelace
--- 200,000 more records:
  200003 4177824 database
get key5      took 0.034 s
get key199999 took 0.039 s

(Save the two functions as db.sh and the script above as try4.sh in an empty directory. It writes a file called database there, so don't run it anywhere you care about. On Windows use WSL or Git Bash.) Notice what happened to user:1. We wrote it twice and the file now holds both lines. We never went back and changed the first one; we appended a newer one, and tail -n 1 makes the newest win. That is an append-only log: a file you only ever add to at the end, never edit in the middle. The data is the history, and the current value of a key is simply its most recent entry.

Analogy: the returns cart

In our library, returned books go onto a cart at the desk in the order they arrive. Nobody walks to the right shelf for each one; you just drop it on the end of the cart. That is why returning is so quick. Finding a particular book, though, means digging through the cart from the beginning. The log is the cart.

Where it breaks down: a library cart is eventually emptied onto the shelves, and the books on it are still physical books. Our log keeps old versions around, so it also needs a way to throw away copies that have been superseded. We'll get to that.

Why writes are fast, and reads are slow

Writes. db_set adds bytes to the end of a file. That is about the cheapest operation a disk can do, for a reason from systems chapter 2: storage hardware loves sequential access. On a spinning disk, moving the head to a new place (a seek) costs milliseconds, while appending continues from where the head already is. On an SSD there is no head, but large sequential writes are still friendlier to the flash and let the operating system merge many small writes into one big one. An update-in-place database must find the right spot in the file first; an append-only log never has to.

Reads. db_get scans the entire file, every time. I measured the function above on a file of about 200,000 lines (4.2 MB): a lookup took roughly 35 ms, whether the key was near the start or the end, because the scan always reads to the end to be sure no later match exists. That is fine for a toy. But the cost is proportional to the file size, which is what O(n) means. At that same rate, a 100 GB log would take on the order of a quarter of an hour per lookup. Reads like this can't serve a website.

"Written" is still not "saved"

This toy never calls fsync. As you learned in systems chapter 9, echo ... >> database hands the bytes to the operating system's page cache, and they can vanish in a power cut. A real log-based engine has to decide when to fsync, which we cover below. The log makes durability easy to reason about (there is exactly one place new data goes), but it does not make it free.

So the log is a wonderful way to write and a terrible way to read. The whole history of storage engines is a series of answers to: how can we keep the fast writes and also get fast reads? The first answer is almost embarrassingly simple.

Adding an index: the hash table in RAM

An index is an extra data structure, kept alongside the data, whose only job is to make lookups fast. (Chapter 7 is devoted to them.) The simplest one for a log is a hash table: for each key, remember where its newest record starts in the file. Keep that table in memory.

Now the two operations look like this:

  1. Write set(key, value): append the record to the end of the file, note the byte offset where it started (how many bytes into the file), and set index[key] = offset. Still one sequential append, plus one in-memory update.
  2. Read get(key): look up the offset in the hash table (a RAM access, nanoseconds to well under a microsecond), seek to that offset in the file, and read one record. One disk read, no scanning.

This design is called Bitcask, after the storage engine originally written for the Riak database (the design is described in a short paper, "Bitcask: A Log-Structured Hash Table for Fast Key/Value Data"). Its index is traditionally called a keydir. Its promise is attractive: every write is one sequential append and every read is at most one disk seek, no matter how big the data is.

What a record looks like on disk

To seek into a file we need to read a record back without knowing its length in advance, so each record carries a small header. Here is the layout used by the code in this chapter (Bitcask's own records also carry a timestamp, which we skip):

crc324 bytes · checksum of everything after it
key length4 bytes
value length4 bytes · −1 means tombstone
keykey length bytes
valuevalue length bytes

The offset in the index points at the first byte of the header. The header tells us exactly how many more bytes to read. The checksum and the "−1" will earn their keep in a minute.

Analogy: the card catalogue

The library's catalogue does not hold any books. It holds cards: for each title, which shelf and which position. Looking up a book takes one flip through the cards and one walk to the shelf. The hash index is the catalogue, the log segments are the shelves of books, and the values (which may be big) never need to be in memory, only the cards.

Where it breaks down: a paper catalogue survives a power cut. Our index lives in RAM, so after a crash someone has to rewrite every card from scratch. That is the recovery problem below.

Why every key must fit in RAM

The index holds one entry per live key: the key itself plus a pointer (segment, offset, size). The values stay on disk. Suppose you track view counts for 100 million videos with 16-byte keys. Even with a few tens of bytes of overhead per entry, the index is on the order of 4 to 5 GB. That is a back-of-envelope figure, not a measurement, but it shows the shape: RAM use grows with the number of keys, not with the amount of data. A store with 100 million keys and 1 KB values holds around 100 GB on disk and needs only a few GB of RAM, which is a good deal. A store with 10 billion tiny keys does not fit on any single machine's memory.

So Bitcask suits workloads with a modest number of keys that are updated very often: counters, session data, a "latest status" per device. The video-view example is the classic one: millions of increments, but each increment overwrites the same key.

Segments: the log can't grow forever

In our example workload, each video's counter is overwritten constantly. After a billion updates the log holds a billion records, but only 100 million of them (the newest per key) are still "live". The rest are garbage that wastes disk. We can't edit the file to remove them, because editing in place is exactly what we gave up. So we use a trick: break the log into pieces.

A segment is one file of the log. We append to a single active segment. When it reaches a size limit, we seal it (close it and never write to it again) and start a new active segment. Sealed segments are immutable: once written, not one byte changes. The index now stores a (segment, offset) pair instead of just an offset, exactly as in the diagram above.

Immutability is a recurring gift. We'll use it for compaction, for concurrency and, in later chapters, for backups and replication.

Compaction and merging

Compaction is the process of throwing away garbage. In the simplest version: read some sealed segments, copy into a new segment only the records that are still live (the ones the index points to), then switch the index to the new locations and delete the old files. Because sealed segments are never changed, we can do all of this in the background while reads and writes carry on. The related word merging means combining several small segments into one bigger one; in practice the same pass does both.

Two details matter for correctness:

  • Liveness comes from the index. A record is live exactly when the index points at it. Everything else is garbage. (This is also how the widget below decides what to fade.)
  • Crash safety. Write the new segment under a temporary name, fsync it, then rename it into place (the pattern from systems chapter 9), and only then delete the old files. If the machine dies halfway, the old segments are all still there and you simply redo the compaction.

Analogy: copying the current balances

Imagine a notebook where you write every change to your account balance on a new line. After a year it is full of old entries. To save paper you start a fresh notebook and copy over only the current balance for each account, then recycle the old notebook. Same information you still need, far fewer pages.

Where it breaks down: an accountant would never throw away the history. A Bitcask-style store deliberately does, which is why you wouldn't use it for an audit trail.

Compaction is not free

Compaction reads and rewrites live data, so it uses disk bandwidth and needs enough spare space to hold the new segments while the old ones still exist. Data that is rewritten many times over its life costs more I/O than the user ever asked for. That ratio is called write amplification, and it returns in a big way in the next chapter.

Deleting: you can't, so you write a tombstone

How do you delete a key from a file you can only append to? You can't remove the old record. Instead you append a special record that means "this key is deleted", called a tombstone. In our format that is a record whose value length is −1. The index removes the key, so reads miss immediately.

Why is the tombstone needed at all, if the index already forgot the key? Because the index is not the truth; the log is. After a crash, the index is rebuilt by replaying the log from the start. Replaying the old set without the tombstone would resurrect the key. The tombstone is what makes the delete durable.

When can a tombstone be dropped?

Only when no older record for that key can still be replayed. A compaction that merges all the older segments can safely drop it, which is why the diagram above drops c✕ (every older c was in the segments being merged). And when you delete the old segments afterwards, delete them oldest first. If a crash interrupted the clean-up after the tombstone's segment was removed but while an older segment holding the old value remained, the key would come back to life. This "zombie" problem recurs in every log-structured system, including LSM trees.

Crash recovery

There are three different things that can go wrong, and they have three different answers.

1. The index is gone

The index lives in RAM. When the process restarts, it must be rebuilt. The simplest method works because the log is the truth: scan every segment from oldest to newest, and for each record set index[key] to its location (or remove the key for a tombstone). Newer records overwrite older ones, so at the end the index is exactly right. It costs a full read of the data, which on a 100 GB store can mean minutes of downtime.

To speed that up, Bitcask writes hint files next to its data files: for each segment, a compact list of (key, offset, size) without the values. Reading the hints rebuilds the index while skipping most of the bytes. Another common approach is to periodically snapshot the whole index to disk and replay only the log written since. Either way, the idea is the same: a cache of derived data, thrown away and recomputed from the log whenever needed.

2. The last record is torn

If the machine died in the middle of an append, the file may end with half a record: a header promising 100 bytes of value, followed by 37. If recovery trusted the header it would read garbage, or run off the end of the file. This is the torn write from systems chapter 9, and the cure is the same one: a checksum (here a CRC32) stored in every record and verified on recovery. A partial or damaged record almost certainly fails the check. Recovery then truncates the file at that record and carries on. Nothing is lost that was ever acknowledged, provided the store only told the client "OK" after the record was fully written (and fsynced, if you want it to survive a power cut).

The crash-safe log lab in the Systems course builds exactly this record format and recovery loop. Lab 1 of this course (linked below) extends it with an index and compaction.

3. Corruption in the middle

A bad checksum on the last record is an expected consequence of a crash. A bad checksum in the middle of the log, with valid records after it, is not: it means the disk itself returned wrong bytes (bit rot, a failing drive). Truncating there would throw away good data. A careful engine reports it loudly and, if the data is replicated, repairs from another copy. Verifying the checksum on reads, not just during recovery, catches such damage early.

How often to fsync

fsync after every record is safest and slowest: each write waits milliseconds for the disk. Many log-based stores let you choose: sync every write, sync every N milliseconds (a crash can lose the last few acknowledged writes), or leave it to the operating system. Another way to cut the cost without weakening the promise is group commit, where one fsync covers many concurrent writers' records (also in systems chapter 9). This is the same trade-off as everywhere else in this course: durability costs latency.

One writer, many readers

How does a log-structured store handle many clients at once? Better than you might expect, because of immutability.

  • Writes go to one place. Only the end of the active segment is ever written, and by a single writer thread (or process). With only one writer there are no two appends to interleave and no locks around file contents. Writers queue up and the log gives them a clean order. (A simple lock file prevents a second process from opening the store for writing.)
  • Readers need no locks on the data. A sealed segment never changes, so any number of readers can read it simultaneously. The active segment only grows at the end; a reader that has an index entry pointing at a complete record sees a complete, unchanging record.
  • The index is the shared mutable thing. It must be updated atomically (a lock, or a concurrent hash table), so that a reader never sees a half-updated entry. This is the only real synchronisation, and it is a tiny, in-memory critical section (see systems chapter 12 on locks).
  • Readers and compaction. A reader may have just fetched an old location when compaction deletes that segment. On Linux and macOS, a file that is deleted while someone still has it open stays readable until the last reader closes it (systems chapter 8), or the reader can simply retry with a fresh index lookup.

The summary is worth remembering: immutable data can be shared freely. Almost all the concurrency difficulty in databases comes from data that changes in place. The log avoids it by never changing anything it has written. (Chapter 12 returns to this idea in the form of multi-version concurrency control.)

Where the log runs out

The Bitcask design is lovely, and it has two hard limits.

1. The keys must fit in RAM. A large number of keys breaks it, no matter how small the values. Could we keep the hash table on disk instead? A hash table spread over disk turns every lookup and update into a random disk access, and handling collisions and resizing there is painful. The easy speed came from RAM.

2. Range queries are hard. A hash function deliberately scatters keys, so user:1001 and user:1002 end up in unrelated places. A query like "give me every key from user:1000 to user:2000" must examine every key in the index (or sort them all), and then do a separate random seek to each record, because those records are scattered across the log in write order. Questions like "all orders from last Tuesday", or "the next ten items after this one", are central to databases, and a hash index can't help.

Both limits point at the same fix, which is the subject of chapter 5: keep the data sorted by key. Sorted files can be searched with a small sparse index (so keys no longer need to be in RAM), range queries become sequential reads, and, remarkably, we can still keep the fast, append-style writes. The log idea survives; the hash table goes.

The log is everywhere

This chapter's structure is not an academic exercise. The append-only log is the most reused idea in data systems.

  • Write-ahead logs. B-tree databases update pages in place, but before touching a page they append a description of the change to a log, so a crash can be repaired by replaying it (chapter 13). It is today's torn-tail and replay machinery with a different job.
  • LSM trees. The next chapter's storage engine writes to a log for durability and then turns the data into sorted, immutable files.
  • Replication. A follower stays in sync by applying the leader's log in order (chapter 15).
  • Streams. Kafka's core abstraction is a partitioned, append-only log that many consumers read at their own pace, each remembering an offset (chapter 19).
  • Consensus and ordering. Raft makes machines agree on the content and order of a log (networking chapter 20), and networking case 10 shows a global-scale system built around it.

Notice the pattern in everything above: the log is the source of truth, and structures like hash indexes, sorted tables, caches and search indexes are derived from it, rebuildable at any time. Keeping that distinction clear is one of the most useful habits in data-system design.

Build and break it yourself

Try it yourself: the log database in Python

The bash version proves the idea. This Python version, minicask.py, has everything from this chapter in about 100 lines: segments, an index, tombstones, compaction, a CRC32 per record, and a recovery scan that cuts off a torn tail. Save it, run it, then break it. It needs only Python 3 and no installs. (Python's zlib.crc32 and struct do the byte-level work.)

Go deeper: the full source of minicask.py optional, ~100 lines 
import os, struct, zlib

HEADER = struct.Struct(">IIi")      # crc32, key length, value length (-1 = tombstone)
MAX_SEGMENT = 64                    # bytes; tiny so rollover is easy to see

class MiniCask:
    def __init__(self, directory):
        self.dir = directory
        os.makedirs(directory, exist_ok=True)
        self.index = {}             # key -> (segment number, offset of record, record length)
        self.segments = sorted(int(n[4:10]) for n in os.listdir(directory) if n.startswith("seg-"))
        for seg in self.segments:   # crash recovery = replay the log, oldest segment first
            self._scan(seg)
        if not self.segments:
            self.segments = [1]
        self.active = open(self._path(self.segments[-1]), "ab")

    def _path(self, seg):
        return os.path.join(self.dir, "seg-%06d.log" % seg)

    def _scan(self, seg):
        with open(self._path(seg), "rb") as f:
            data = f.read()
        pos = 0
        while pos + HEADER.size <= len(data):
            crc, klen, vlen = HEADER.unpack_from(data, pos)
            end = pos + HEADER.size + klen + max(vlen, 0)
            body = data[pos + 4:end]
            if end > len(data) or zlib.crc32(body) != crc:
                print("  torn record in segment", seg, "at offset", pos, "- ignoring the rest")
                with open(self._path(seg), "r+b") as f:
                    f.truncate(pos)             # drop the damaged tail
                return
            key = data[pos + HEADER.size:pos + HEADER.size + klen].decode()
            if vlen < 0:
                self.index.pop(key, None)       # tombstone: forget the key
            else:
                self.index[key] = (seg, pos, end - pos)
            pos = end
        if pos != len(data):                    # a partial header at the very end
            with open(self._path(seg), "r+b") as f:
                f.truncate(pos)

    def _append(self, key, value):
        k = key.encode()
        v = b"" if value is None else value.encode()
        vlen = -1 if value is None else len(v)
        body = struct.pack(">Ii", len(k), vlen) + k + v
        rec = struct.pack(">I", zlib.crc32(body)) + body
        if self.active.tell() + len(rec) > MAX_SEGMENT and self.active.tell() > 0:
            self.active.close()                 # roll over: the old segment is now immutable
            self.segments.append(self.segments[-1] + 1)
            self.active = open(self._path(self.segments[-1]), "ab")
        offset = self.active.tell()
        self.active.write(rec)
        self.active.flush()
        os.fsync(self.active.fileno())
        return self.segments[-1], offset, len(rec)

    def set(self, key, value):
        self.index[key] = self._append(key, value)

    def delete(self, key):
        if key in self.index:
            self._append(key, None)
            del self.index[key]

    def get(self, key):
        loc = self.index.get(key)
        if loc is None:
            return None
        seg, offset, length = loc
        with open(self._path(seg), "rb") as f:
            f.seek(offset)                      # one seek...
            rec = f.read(length)                # ...one read
        crc, klen, vlen = HEADER.unpack_from(rec)
        assert zlib.crc32(rec[4:]) == crc, "corrupt record"
        return rec[HEADER.size + klen:].decode()

    def compact(self):
        """Rewrite every live key into fresh segments, then delete the old ones."""
        old = list(self.segments)
        live = {k: self.get(k) for k in self.index}
        self.active.close()
        first_new = old[-1] + 1
        self.segments = [first_new]
        self.active = open(self._path(first_new), "ab")
        self.index = {}
        for k, v in live.items():
            self.set(k, v)
        for seg in old:
            os.remove(self._path(seg))
        self.segments = [s for s in self.segments if s >= first_new]

Two simplifications to know about: MAX_SEGMENT is 64 bytes so rollover is easy to see (real segments are far larger), and compact() merges everything, including the active segment, which keeps the code short. A real engine leaves the active segment alone, as the widget does.

Read the output slowly. Five users and four segments (one per couple of records, since segments are tiny), with user:1 overwritten and user:2 deleted. After compaction 168 bytes became 102, and the index points into brand-new segments. The "crash" throws the index away, and the rebuilt index is identical. Chopping 5 bytes off the final segment makes the last record fail its checksum; recovery keeps the three good keys and drops user:5. (Nothing here is random, so your output should match exactly.)

Things to try:

  • Replace the 5-byte chop with flipping one byte in the middle of the first segment. What does recovery do? What should it do (see "Corruption in the middle")?
  • Comment out the tombstone replay (self.index.pop(...)) and restart: the deleted key comes back.
  • In compact(), delete the old segments newest-first instead of oldest-first, and think through what a crash between two deletions could do.

Distributed systems connection

A log is the natural unit of replication. If every change to a database is an entry at a known position in an append-only log, then keeping a second copy up to date is just "send me everything after position 4,127 and apply it in order". Followers replaying a leader's log is how many replicated databases work (chapter 15, and networking chapter 18 for the theory). The position in the log, the offset, is also how a consumer remembers where it was, which is the whole idea behind Kafka and change data capture in chapter 19. And because sealed segments are immutable, copying them to a backup or another machine is safe while the store keeps running. Agreeing on the order of a replicated log across machines that can fail is exactly what Raft (networking chapter 20) is for.

Key takeaways

  • An append-only log gives very fast writes: every write goes to the end of one file, a sequential access. The newest record for a key wins.
  • Without an index, reads scan the whole log: O(n). A hash index in RAM mapping each key to its newest record's (segment, offset) makes a read one lookup and one seek (the Bitcask design).
  • RAM use grows with the number of keys, not the size of the values, so all keys must fit in memory.
  • Segments bound file size. Sealed segments are immutable; compaction copies only live records (those the index points at) into new segments, then deletes the old ones. It costs extra I/O: write amplification.
  • Deletes are tombstone records. A tombstone must outlive every older record of its key, so recovery never resurrects the value.
  • After a crash, rebuild the index by replaying the log oldest to newest (hint files or snapshots make this faster). A checksum per record detects a torn tail, which is truncated; a bad checksum mid-log is real corruption.
  • Immutability makes concurrency easy: one writer appends, readers read sealed files freely, and only the in-memory index needs synchronising.
  • Limits: keys must fit in RAM, and range queries are hard. Both are fixed by sorting the data (chapter 5). The log itself recurs in WALs, replication, Kafka and Raft.

Check your understanding

Why is appending to a log file so cheap compared with updating a record in place?

  1. Appended data is compressed automatically
  2. It is sequential: the write goes to the end of the file with no search for the right spot, which suits disks and lets the OS batch writes
  3. Appended writes skip the operating system's page cache
  4. Appends never need fsync to be durable
Sequential access avoids seeks and batches well. The other options are false: appends go through the page cache like any write, and they still need fsync to survive a power cut.

In a Bitcask-style store, what does the in-memory hash index contain?

  1. Every key with its complete history of values
  2. A copy of all the values, for fast reads
  3. For each live key, the location (segment and offset) of its newest record on disk
  4. Only the keys that were recently read
The index holds keys and pointers only. Values stay on disk, which is why RAM use scales with the number of keys and not with the data size.

A store deletes a key by appending a tombstone, rather than erasing the old record. Why?

  1. Segments are append-only and old ones are immutable, and recovery replays the log, so without a tombstone a restart would bring the deleted value back
  2. Tombstones make deletes faster than updates for hardware reasons
  3. Erasing is forbidden by the operating system
  4. So that the key can be reused immediately at the same offset
The log, not the index, is the truth. Replaying an old set with no later tombstone would recreate the key. The space is reclaimed later, by compaction.

After a power cut, the last record in the active segment is half-written. How does recovery handle it?

  1. It trusts the length in the header and reads past the end of the file
  2. It deletes the entire segment
  3. It restores the record from the index
  4. The record fails its checksum, so recovery truncates the file at that record and keeps everything before it
The checksum detects the torn write. Everything before it was complete, so it stays. The index is not a backup: it is rebuilt from the log, not the other way round.

Why is "one writer, many readers" relatively easy for a log-structured store?

  1. Because the index is stored on disk, where the OS makes it thread-safe
  2. Sealed segments are immutable and the active one is only appended to, so readers need no locks on data files; only the small in-memory index needs synchronising
  3. Because readers always read stale data
  4. Because the writer holds a lock on every file for the whole time it runs
Immutable data can be shared freely. The complications of in-place updates (readers seeing half-changed pages) simply do not arise.

A product needs the query "all users whose id is between 1000 and 2000", over a billion keys. What is the main problem with a hash-indexed log?

  1. The log is too slow to write
  2. Tombstones prevent range queries
  3. A hash index scatters adjacent keys, so a range query must visit every key; and a billion keys may not fit in RAM anyway
  4. Compaction deletes ranges
Hashing destroys ordering, and the key count is the index's memory cost. Sorted files (chapter 5) fix both: keys that are neighbours in value are neighbours on disk, and a sparse index needs only a few entries per file.

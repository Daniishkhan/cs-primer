Column Stores & Analytics

A shop's checkout and its quarterly sales report ask very different things of a database. The first touches one order at a time; the second scans a billion of them but cares about only two fields. This chapter shows how turning a table on its side makes the second kind of question hundreds of times cheaper, and how that idea built the data warehouse.

Why this matters

Almost every company ends up with two databases: one that runs the product, and one that answers questions about it. They are built differently on purpose. If you understand why a column store beats a row store for analytics (and loses for everything else), you will know which tool to reach for, and why "just run the report on the production database" can bring a site down.

Two kinds of workload

Databases serve two broad access patterns. OLTP (online transaction processing) is the application's day-to-day traffic: "fetch user 42", "insert this order", "decrement this stock count". OLAP (online analytical processing) is analysis: "average basket size by country, by week, for the last two years". Almost every real system has both.

OLTP (transactions)OLAP (analytics)

Rows versus columns

A table is a grid, but a disk is a long line of bytes, so the database has to decide in which order to write the grid out. The B-tree pages of chapter 6 are row-oriented: all the values of one row sit next to each other. That is ideal when you want a whole row, since one page read gives you everything about order #1234. A column-oriented store (a column store) writes each column's values together instead.

Now consider SELECT avg(price) FROM sales on a table with 50 columns and a billion rows. The row store reads every page, which means all 50 columns, to extract the one value it wants from each row. The column store reads only the price file. If all values are about the same size, that is roughly 50 times fewer bytes. Disk and memory bandwidth, not CPU, are usually the bottleneck for scans, so reading 2% as much data is nearly 50 times faster.

Analogy: library cards

The library's catalogue keeps one card per book: title, author, year, page count, shelf. Fetching everything about one book means pulling one card, which is how a row store works. Now you are asked for the average page count of the whole library. You would have to flip through every card, glancing past three fields to read the fourth. If someone had instead kept a separate list of just page counts, one number per line, in the same order as the cards, the question takes minutes.

Where it breaks down: the page-count list is useless for "show me everything about this book". A column store has to reassemble the row from the same position in every column list, which is why fetching a single whole row is slower there.

A runnable version

Here is the same idea in Python. We store one million sales rows two ways: as a list of tuples (row-wise) and as a dict with one list per column (column-wise). We compute avg(price) both ways, then show how well a sorted column compresses with run-length encoding.

import random, time

random.seed(7)
N = 1_000_000
countries = ["BR", "DE", "FR", "IN", "JP", "UK", "US"]
rows = [(i, random.choice(countries), random.randint(1, 5), round(random.uniform(1, 100), 2))
        for i in range(N)]                                    # row store: list of tuples
cols = {                                                       # column store: dict of arrays
    "id":      [r[0] for r in rows],
    "country": [r[1] for r in rows],
    "qty":     [r[2] for r in rows],
    "price":   [r[3] for r in rows],
}

def avg_rows():
    total = 0.0
    for r in rows:
        total += r[3]
    return total / len(rows)

def avg_cols():
    return sum(cols["price"]) / len(cols["price"])

for f in (avg_rows, avg_cols):
    times = []
    for _ in range(5):
        t0 = time.perf_counter(); v = f(); times.append(time.perf_counter() - t0)
    print(f"{f.__name__:9} avg(price) = {v:.4f}   best of 5: {min(times)*1000:6.1f} ms")

def rle(values):
    out = []
    for v in values:
        if out and out[-1][0] == v:
            out[-1][1] += 1
        else:
            out.append([v, 1])
    return out

c = cols["country"]
unsorted_runs = rle(c)
sorted_runs = rle(sorted(c))
print(f"unsorted country column: {len(c):,} values -> {len(unsorted_runs):,} runs")
print(f"sorted country column:   {len(c):,} values -> {len(sorted_runs)} runs: {sorted_runs[:3]} ...")
raw_bytes = 2 * len(c)                       # two ASCII bytes per country code
rle_bytes = len(sorted_runs) * (2 + 4)       # 2-byte value + 4-byte count per run
print(f"raw: {raw_bytes:,} bytes   RLE of sorted: {rle_bytes} bytes")
avg_rows  avg(price) = 50.4964   best of 5:   14.6 ms
avg_cols  avg(price) = 50.4964   best of 5:    3.4 ms
unsorted country column: 1,000,000 values -> 857,505 runs
sorted country column:   1,000,000 values -> 7 runs: [['BR', 142893], ['DE', 143059], ['FR', 142868]] ...
raw: 2,000,000 bytes   RLE of sorted: 42 bytes

The column version is about four times faster even in Python, where everything is a pointer to an object and the effect is blunted. Real column stores keep values in packed arrays of fixed-width numbers, so a scan is a tight loop over contiguous memory that the CPU can prefetch and process in bulk. The last lines show the compression story: sorted, the million-value country column is seven runs, a few dozen bytes in this toy format. Unsorted, run-length encoding is useless (857,505 runs). That is the next section.

Compression: why columns shrink

All the values in a column have the same type and often the same few values, and that is very compressible. A row mixes an integer, a string and a timestamp, which hides patterns. Three standard tricks:

  • Run-length encoding (RLE). Replace a run of identical values by (value, count). Works brilliantly on sorted or low-variety columns. Column stores often sort the table by one or two key columns precisely to make those columns compress, and to speed up filters on them.
  • Dictionary encoding. Store each distinct value once in a dictionary and replace occurrences with small integer codes. A country column with 200 distinct values needs about 8 bits per row, not 10 bytes of text. Comparisons become integer comparisons.
  • Bitmaps. For a column with few distinct values, keep one bit-string per value ("bit i is 1 if row i has this value"). A filter on several columns becomes a bitwise AND of bit-strings, which a CPU does 64 rows at a time.
country = ["US", "DE", "US", "FR", "DE", "US", "FR", "US"]
big_qty = [0, 1, 1, 0, 0, 1, 0, 1]          # 1 where qty >= 4

def bitmap(flags):                           # pack a list of 0/1 into one Python int
    n = 0
    for i, f in enumerate(flags):
        n |= f << i
    return n

us = bitmap([c == "US" for c in country])
big = bitmap(big_qty)
print(f"US      = {us:08b}  (rightmost bit is row 0)")
print(f"qty>=4  = {big:08b}")
both = us & big                              # WHERE country = 'US' AND qty >= 4
print(f"AND     = {both:08b}  -> {bin(both).count('1')} rows match, no row was read")
US      = 10100101  (rightmost bit is row 0)
qty>=4  = 10100110
AND     = 10100100  -> 3 rows match, no row was read

On top of these lightweight encodings, systems usually apply a general-purpose compressor (LZ4, Zstandard and similar) per block. Compression does double duty: less data to read from disk and less to move through memory. Some engines even run filters directly on the compressed data.

Column stores are bad at what row stores are good at

Inserting one row into a column store means appending a value to every column's file, and compressed, sorted columns are expensive to modify in place. Reading one whole row means gathering it from every column. So column stores want data to arrive in bulk and be queried in bulk. "Columnar is faster" is false as a general statement; it is faster for scans of a few columns over many rows.

Vectorised execution

Columns also change how queries are executed. The iterator model from the last chapter calls next() once per row per operator: millions of function calls, each with overhead. A column store can instead pass a vector of, say, a thousand values from one operator to the next. The filter operator tests a whole vector in a tight loop with no per-row call overhead, and modern CPUs can apply the same instruction to several values at once (SIMD). The idea is simple and the speed-up is large, which is why it is the design of DuckDB, ClickHouse and most other modern analytic engines.

The data warehouse

Why not just run analytics on the production database? Because a report that scans half a billion rows competes for I/O, memory and locks with checkout traffic, and the shape of the data is wrong: OLTP tables are normalised for correctness, so every report needs many joins. A data warehouse is a separate database for analysis, loaded with a copy of data from many sources (the orders database, the payments system, web logs, a CRM) and shaped for questions.

Getting the data there is ETL: extract from the sources, transform (clean, join, reshape) and load into the warehouse. A newer pattern, ELT, loads the raw data first and transforms it inside the warehouse with SQL, since modern warehouses are fast and cheap enough to do the work. Either way a scheduled batch job or a stream of change events does the copying.

Star schemas

Warehouse tables are typically organised as a star schema. A central fact table records events, one narrow row per sale, click or payment, mostly numbers and keys. Around it are dimension tables describing the things the facts refer to: the date, the product, the store, the customer.

The query "revenue by product category by quarter" joins the fact table to dim_product and dim_date, groups by the dimension attributes and sums the fact's price. Dimensions are small, so those joins are cheap hash joins (chapter 8) against a huge fact table that is scanned columnwise. The schema deliberately repeats data (the category name is stored once per product, not normalised into its own table) because for analytics, fewer joins beat saving a few bytes.

Parquet and data lakes

A column store is not only a database; it is also a file format. Apache Parquet is an open columnar file format. A Parquet file is divided into row groups (a few thousand to millions of rows); inside each, every column is stored as its own contiguous column chunk, encoded (dictionary, run-length and so on) and compressed. A footer holds the schema and per-chunk statistics such as the minimum and maximum value. A query engine reads the footer first, then fetches only the column chunks it needs, and can skip whole row groups whose min/max range cannot match the filter. ORC is a similar format; Apache Arrow is a columnar layout for data in memory.

A data lake is the pattern of dumping files like these (and raw JSON, CSV, logs) into cheap object storage such as Amazon S3, and querying them in place with engines that understand the formats. It is flexible and cheap, but without discipline it becomes a swamp: no schema enforcement, no transactions, many tiny files. "Lakehouse" systems add table formats and transactional metadata on top to address that.

Pre-aggregation and materialised views

The fastest scan is the one you skip. If a dashboard asks for daily revenue by country a thousand times a day, computing it from billions of rows each time is wasteful. A materialised view stores the result of a query as a table, so reads are instant, at the cost of keeping it up to date. In PostgreSQL, CREATE MATERIALIZED VIEW makes one and REFRESH MATERIALIZED VIEW recomputes it; other systems refresh incrementally. Without them you can build a rollup table by hand: a small summary table updated by a nightly job. Either way the trade is the same, familiar from caches: fast reads against staleness and extra maintenance. (SQLite has ordinary views but no built-in materialised views.)

Warehouse is not a replacement for the application database

Analytic systems generally have weaker support for fast single-row updates, high-concurrency small transactions and strict constraints. The usual architecture is one OLTP database for the product, plus a warehouse fed from it. Some databases try to serve both at once (so-called HTAP), but the trade-off between the two layouts does not go away.

Distributed systems connection

Warehouses scale by splitting columns and rows across many machines (the partitioning of networking chapter 19): each node scans its own slice, computes a partial aggregate, and a coordinator combines them. Cloud warehouses go further and keep the data in remote object storage, so a cluster is just compute that can be added or dropped in seconds, at the cost of fetching data over the network (hence the heavy use of caching and column pruning). The pipeline that keeps a warehouse fresh is a distributed-systems topic in its own right: batch jobs and change data capture.

Key takeaways

  • OLTP touches few rows, all columns, with many small writes. OLAP touches many rows, few columns, in bulk. They want different layouts.
  • A column store keeps each column contiguous, so SELECT avg(price) reads one column, not every column of every row.
  • Columns compress well: run-length encoding (best when sorted), dictionary encoding, and bitmaps. Less data read is the main reason for the speed.
  • Vectorised execution processes batches of values per call instead of one row per next().
  • A warehouse is a separate database for analysis, loaded by ETL or ELT, usually organised as a star schema: a huge fact table and small dimension tables.
  • Parquet is a columnar file format with per-column chunks and min/max statistics; data lakes hold such files in object storage.
  • Materialised views and rollup tables precompute answers, trading freshness for speed.
  • Column stores are weak at single-row reads and updates. Use both kinds of system, each for its job.

Check your understanding

Why is SELECT avg(price) FROM sales usually much cheaper on a column store than on a row store?

  1. Column stores keep all data in RAM
  2. Column stores have more powerful CPUs
  3. It reads only the price column instead of every column of every row
  4. Column stores skip the aggregation step
The work is dominated by bytes read. With a 50-column table, a row store pulls in about 50 values to use one; a column store reads just the one. Nothing about it is magic: it is a different order of the same bytes.

A column holds one million country codes from only seven distinct values. Which makes run-length encoding most effective?

  1. Sorting the column first, so equal values form long runs
  2. Shuffling the column randomly
  3. Converting the codes to longer strings
  4. Storing each value in its own file
RLE stores (value, count). Sorted, a million values collapse to seven pairs; unsorted, adjacent equal values are rare and the 'runs' are almost as numerous as the values.

Which workload is a column store worst at?

  1. Average order value by month over five years
  2. Counting distinct customers per country
  3. Summing revenue for one product category
  4. Updating one customer's email address thousands of times a second
Point updates mean touching a value in each affected column file and often rewriting compressed blocks. Column stores shine at big scans and bulk loads, not at small transactional writes.

In a star schema, what is typically in the fact table?

  1. Descriptive attributes like product names and city names
  2. One narrow row per event (a sale, a click), with numeric measures and keys pointing to dimension tables
  3. A copy of every dimension joined together
  4. Only the primary keys of the dimensions
The fact table is the huge, narrow list of events. Dimensions are the small, descriptive tables around it that queries join to filter and group.

What does Parquet's per-column-chunk min/max statistics let an engine do?

  1. Decrypt the file
  2. Convert it to a row-oriented format
  3. Skip whole row groups whose value range cannot match the query's filter
  4. Avoid reading the footer
If a chunk's maximum price is 40 and the query wants price > 100, the chunk can be skipped without reading it. Less data read is again the whole game.

Why not simply run big analytic reports on the production OLTP database?

  1. The scans compete for I/O, memory and locks with user traffic, and the normalised schema needs many joins for reports
  2. SQL cannot express aggregates on production databases
  3. Production databases refuse queries that take more than a second
  4. Column stores are required by law
Heavy scans can slow down or stall the transactions your users are waiting for. A separate warehouse, fed by ETL/ELT or change data capture, isolates the two workloads and reshapes the data.

Streams, Logs & Change Data Capture

Real systems keep the same facts in several places: a database, a cache, a search index, a warehouse. Keeping them in step with two separate writes quietly fails. This chapter shows why, and then builds the fix from pieces you already know: an append-only log, a consumer that remembers its place, and the database's own write-ahead log turned into a stream.

Why this matters

Almost every production system past a certain size has the same bug waiting in it: the order is in the database, but the search page does not show it, or the cache shows a price that was changed an hour ago. Nobody wrote a bug on purpose. They wrote two writes in a row, and the second one failed, or arrived late, or lost a race. The ideas in this chapter (logs, offsets, idempotent consumers, the outbox, change data capture) are how senior engineers make "several copies of the data" behave like one. They also explain what Kafka is actually for, which is much more than "a faster queue".

Three ways to send a message

Chapter 18 was about processing data in big, finite batches. This chapter is about data that never stops arriving: clicks, payments, sensor readings, and above all changes to your own database. A single unit of such data is an event: a small, immutable record that something happened ("order 101 was placed at 10:03"). An unbounded, ordered flow of events is a stream. The first question is how events get from the part of the system that produces them to the parts that need them. There are three broad answers.

Direct messaging

The producer talks straight to the consumer: an HTTP request, an RPC, a UDP packet. It is the simplest thing that works, and it is the right default for request/response traffic (networking ch. 12). Its weakness is that both sides must be up at the same moment. If the consumer is down, slow, or restarting, the producer has to retry, queue locally, or give up (networking ch. 16), and every new consumer means the producer must learn about one more destination.

Message brokers: queues

A message broker sits in the middle and holds messages until someone can take them. In a queue (RabbitMQ and Amazon SQS are well-known examples), the broker hands each message to one of several workers. This is called competing consumers: add workers and the work spreads out. It is the classic tool for background jobs such as sending email or resizing images.

The delicate part is knowing whether a worker really finished. After handing over a message the broker waits for an acknowledgement (ack). If the ack never arrives (the worker crashed, the network dropped it) the broker assumes the work was not done and redelivers the message, possibly to a different worker. Once acked, the message is deleted. Two consequences matter for the rest of the chapter. First, the broker cannot tell "the worker crashed before doing the work" from "the worker did the work and the ack was lost", so redelivery means a handler may see the same message twice. Second, a queue is a consumable structure: once a message is acked it is gone, so you cannot add a new consumer later and ask it to read last week's messages.

Log-based brokers

A log-based broker flips that second point around. Apache Kafka is the canonical example. A named stream of events, a topic, is stored as an append-only log split into partitions (each partition is its own log). Producers add records to the end of a partition, and every record gets a sequential number within that partition, its offset. Nothing is deleted when it is read. Instead each consumer remembers an offset: "I have processed everything before 4; give me 4 onwards". Reading is non-destructive, so many independent consumers can read the same topic at different speeds, and a brand-new consumer can start from offset 0 and replay history.

Records are not kept forever by default. A topic has a retention policy: keep records for some period (commonly days, configurable) or up to some size, then delete the oldest segments. Kafka can also run a topic with log compaction, which keeps at least the latest record for each key instead of deleting by age. That makes a compacted topic a kind of changelog-as-snapshot, which we will use later.

Analogy: a queue is a shared inbox, a log is a diary

A queue is a shared team inbox: whoever grabs a ticket handles it, and it disappears from the pile. A log is like the returns cart at the library desk from chapter 4, written down: entries are only ever added at the end, nothing is torn out, and any number of people can each keep a bookmark at the entry they have read up to. Someone new can start from page one.

Where it breaks down: a paper ledger sits on a desk forever. A real log has a retention limit, so a reader who falls too far behind finds that the pages they wanted have been shredded.

Partitions, keys and what stays in order

One log on one machine can only take so many writes, so Kafka cuts a topic into partitions, and partitions can live on different machines (this is the partitioning of networking ch. 19 and chapter 16 applied to a log). The producer chooses the partition for each record. Usually it takes a key (an order id, a user id), hashes it, and takes the result modulo the number of partitions, so records with the same key always land in the same partition.

This design gives you one rule you must internalise: ordering holds within a partition only. Records in P0 are totally ordered with respect to each other. Records in P0 and P1 have no defined order at all: offset 3 in one is neither before nor after offset 3 in the other. (This is the same point as networking case 10, seen from the database side.)

So the key you choose decides what stays ordered. If the key is the order id, all events about order 101 (placed, paid, shipped) are in one partition and a consumer sees them in that order. If the key is the customer id, a customer's events are ordered across their different orders. If you key by something random, or send with no key, nothing about one entity is guaranteed to be ordered. A related catch: if you later change the number of partitions, the mapping from key to partition changes, so the "same key, same partition" promise only holds between changes. And a very hot key sends all its load to one partition, the same hot-spot problem as in chapter 16.

Common misconception

"Kafka keeps messages in order." It keeps each partition in order. If two events must be processed in order relative to each other, they must share a partition key. If you need one order over everything, you are down to one partition and one consumer per group, which gives up the parallelism that partitions exist to provide.

Consumer groups and offsets

A consumer group is a set of consumers that share the work of a topic. The broker assigns each partition to one member of the group; if a member dies, its partitions are reassigned (a rebalance). Different groups are independent: a "billing" group and a "search-indexer" group each read every record and each keep their own offsets. The most parallelism a group can use is the partition count, because a partition has one reader at a time. The offset a consumer commits is the position of the next record to read, stored durably (Kafka keeps it in an internal topic), so a restarted consumer resumes from the last committed offset. When exactly it commits, relative to doing the work, is the whole subject of the next section.

Delivery guarantees

Networking chapter 16 left us with an uncomfortable fact: when a message or its acknowledgement can be lost, a sender cannot know whether the other side acted. A consumer faces a small version of the same problem. It must do two things, process the record and record that it has (commit the offset), and a crash can fall between them.

GuaranteeHow a consumer gets itWhat a crash between "process" and "commit" does
At-most-onceCommit the offset first, then process.The record is skipped on restart. Never duplicated, sometimes lost.
At-least-onceProcess first, then commit.The record is processed again on restart. Never lost, sometimes duplicated.
Effectively-onceAt-least-once delivery plus making repeats harmless.The record is processed again, and the repeat changes nothing.

At-most-once suits data where losing a few records is fine (some metrics, some logs). Most business systems choose at-least-once, because losing a payment event is worse than seeing it twice, and then make duplicates harmless. That last step has two standard forms:

  • Idempotent consumers with deduplication. An operation is idempotent if doing it twice has the same effect as doing it once. "Set the status of order 101 to shipped" is idempotent; "add $40 to revenue" is not. For operations that are not, give each event a unique id (or use its partition and offset) and keep a record of ids already applied, skipping repeats. The record of applied ids must be updated in the same transaction as the effect itself, otherwise you have just moved the crash window.
  • Transactional processing. Store the result and the consumer's offset in one atomic transaction in the same database. Either both happen or neither does, so on restart the consumer resumes exactly after the last record whose effect is visible. Kafka also offers transactions for read-process-write loops inside Kafka (consume from one topic, produce to another, commit the offsets atomically), and its producers can be made idempotent so that a producer's own retries do not append duplicates.

People call this "exactly-once". It is worth being careful with the phrase. A network cannot deliver a message exactly once (that is the lesson of networking ch. 16); what you can build is an exactly-once effect: at-least-once delivery combined with idempotence or atomic commit. The demo below makes it concrete.

A runnable demo: a partitioned log with consumer groups

This is about 50 lines of Python 3 with no libraries. It models the structure in the diagram: a log with two partitions, a hash of the key choosing the partition, and offsets committed per consumer group. It then crashes a consumer between "process" and "commit" to show redelivery, runs an idempotent consumer through the same crash, and starts a new group that replays everything.

import zlib

class Log:
    """An in-memory partitioned, append-only log with consumer-group offsets."""
    def __init__(self, partitions=2):
        self.parts = [[] for _ in range(partitions)]
        self.committed = {}                      # (group, partition) -> next offset to read

    def append(self, key, value):
        p = zlib.crc32(key.encode()) % len(self.parts)   # same key -> same partition
        self.parts[p].append((key, value))
        return p, len(self.parts[p]) - 1

    def poll(self, group, partition, max_n=10):
        start = self.committed.get((group, partition), 0)
        batch = self.parts[partition][start:start + max_n]
        return [(partition, start + i, k, v) for i, (k, v) in enumerate(batch)]

    def commit(self, group, partition, next_offset):
        self.committed[(group, partition)] = next_offset

log = Log()
events = [("alice", "order-1 paid"), ("bob", "order-2 paid"), ("alice", "order-3 paid"),
          ("bob", "order-4 refunded"), ("alice", "order-5 paid")]
for key, value in events:
    print("append", key, value, "->", log.append(key, value))

class Crash(Exception):
    pass

def run_consumer(group, handler, crash_at=None):
    """Process every partition; commit AFTER handling (at-least-once)."""
    seen = 0
    for p in range(len(log.parts)):
        for (part, off, key, value) in log.poll(group, p):
            handler(part, off, key, value)
            seen += 1
            if crash_at == seen:
                raise Crash(f"crashed after handling p{part}@{off}, before commit")
            log.commit(group, part, off + 1)

# 1. A naive consumer: charges the customer every time it sees an event.
charges = []
def naive(part, off, key, value):
    charges.append(value)
    print(f"  naive   handled p{part}@{off} {key}: {value}")

print("\n-- naive consumer, crash after 2nd event")
try:
    run_consumer("billing", naive, crash_at=2)
except Crash as e:
    print(" ", e)
print("-- restart: resumes from the last COMMITTED offset")
run_consumer("billing", naive)
print("  total charges:", len(charges), "for", len(events), "events")

# 2. An idempotent consumer: remember which (partition, offset) it has applied.
applied, effects = set(), []
def idempotent(part, off, key, value):
    if (part, off) in applied:
        print(f"  dedup   skipped p{part}@{off} (already applied)")
        return
    applied.add((part, off))              # in real life: same transaction as the effect
    effects.append(value)
    print(f"  applied p{part}@{off} {key}: {value}")

print("\n-- idempotent consumer, crash after 2nd event, then restart")
try:
    run_consumer("search", idempotent, crash_at=2)
except Crash as e:
    print(" ", e)
run_consumer("search", idempotent)
print("  effects applied:", len(effects), "for", len(events), "events")

# 3. A brand-new group replays the whole log from offset 0.
print("\n-- new group 'analytics' replays from the start")
replayed = []
run_consumer("analytics", lambda p, o, k, v: replayed.append((p, o, k)))
print(" ", replayed)

Read it in three parts. The same key always lands in the same partition: alice's three events are all in partition 1, in order. In the first run, the naive consumer handled p0@1, crashed before committing, and on restart resumed from the committed offset, so it handled p0@1 a second time: six charges for five events. In the second run the consumer remembered (partition, offset) pairs it had applied and skipped the repeat: five effects for five events. The last group, which had never read anything, saw the whole history, because reading did not remove it. (The demo keeps its "applied" set in memory for brevity; a real consumer must persist it atomically with the effect, as described above.)

The dual-write problem

Now the problem that makes all this machinery worth having. You run an online shop. When an order is placed, three places need to know: the database (the source of truth), a cache of dashboard numbers, and a search index. The obvious code is:

def place_order(order):
    db.insert(order)            # 1. commit to the database
    cache.incr("revenue", order.total)   # 2. update the cache
    search.index(order)         # 3. update the search index

This is a dual write (here a triple write): one logical change, several independent systems, no transaction spanning them. The database's ACID guarantees (chapter 10) stop at the edge of the database. Everything beyond it is hope.

Reordering the code does not rescue you. Write the cache first and then the database, and a database rollback leaves the cache describing an order that does not exist. Wrap both in a retry loop and a crash still loses the intent. Use a distributed transaction (two-phase commit) across the database and the search engine, and you pay in latency and availability while most cache and search systems do not support it anyway. The race in panel B needs no failure at all, just two concurrent writers and ordinary network jitter.

The root cause is that there are two sources of truth being written independently. The cure is to have one source of truth, make that write atomic using a transaction we trust, and let everything else derive from it, in order, with retries. That is what the next two sections do.

Common misconception

"Dual writes are fine if the second write almost never fails." Panel B fails with no errors at all, and panel A needs only a deploy that restarts a process at the wrong moment. The inconsistency is silent: no exception, no alert, just a customer asking why their order is missing. Dual writes drift, and nothing brings them back. (Case 7 looks at dual writes used deliberately as a phase of an online migration, where the drift is expected and has to be managed.)

Change data capture

Here is an observation from chapter 13: a database already keeps an ordered, durable, append-only record of every committed change, because it needs one to recover from a crash. That is the write-ahead log (WAL; MySQL calls its replication-facing equivalent the binlog). Leaders use the same log to feed followers in replication (chapter 15). Change data capture (CDC) simply lets other programs read that log, too: it turns the database's changes into a stream of events.

A CDC tool, of which Debezium is the best-known open-source example, runs as a connector. It connects to the database in the way a replica would (for Postgres, through logical decoding and a replication slot; for MySQL, by reading the binlog), decodes each committed row change into an event like "table orders, row 101 inserted, these column values", and publishes it to a Kafka topic. Debezium runs on Kafka Connect, Kafka's framework for moving data in and out of other systems.

A connector faces one problem you already know: how does a brand-new consumer get the state that was written before it started listening? The answer is the same as for a new replica. First an initial snapshot: read the current rows (consistently, at a known position in the log) and emit them as events. Then stream from that position onwards, applying every subsequent change in commit order. Snapshot plus log reconstructs the state at any later moment. The connector saves its position in the log as it goes, so after a crash it resumes from the last saved position; if it crashed after publishing but before saving, it publishes a few events twice, which brings us back to at-least-once and idempotent consumers.

Using the WAL is better than the obvious alternatives. Polling tables with SELECT ... WHERE updated_at > ? misses deletes, can miss rows when transactions commit out of timestamp order, and loads the database. Database triggers that write change rows work, but they run inside every write, are easy to forget, and can slow writes. Reading the log costs the database little (it is written anyway), sees every committed change including deletes in commit order, and sees nothing from rolled-back transactions.

Go deeper: the sharp edges of CDC optional

The replication slot can fill your disk. In Postgres, a logical replication slot makes the database keep WAL segments until the slot's consumer has read them. If the connector stops and nobody notices, WAL accumulates and the primary can run out of disk. Monitor slot lag the way you monitor replica lag.

The events are row changes, not business events. A raw CDC event says "column status changed from pending to paid". That ties every consumer to your table layout. Teams often treat the schema of the CDC topic as a public API, and evolve it carefully (chapter 3), or publish purpose-built events through an outbox instead.

Transaction boundaries. A transaction touching three rows produces three change events. The commit order is preserved, but consumers that need to see the transaction as a unit must group by a transaction id that the connector can attach.

Schema changes (adding a column mid-stream) must flow through to consumers; tools handle this with a schema registry and compatible-evolution rules.

The transactional outbox

CDC captures every row change, which is often more than you want to expose. The transactional outbox is a close cousin that lets the application decide exactly which events to publish while keeping the guarantee. It works in three moves:

  1. Create an outbox table in the same database as the business data.
  2. When the application changes the data, it also inserts a row into the outbox describing the event, inside the same transaction. Atomicity (chapter 10) now guarantees that either the order and its event both exist, or neither does. There is no window between them.
  3. A separate relay reads unsent outbox rows in order and publishes them to the broker. It can be a plain polling loop, or a CDC connector watching the outbox table (Debezium ships a helper for exactly this). After publishing, the relay marks the row sent, or advances its saved position.

The relay can crash between publishing and marking, so it can publish twice: delivery is at-least-once, and consumers must be idempotent. The outbox does not remove duplicates; it removes loss and phantoms, and duplicates are the easy problem. Here is the core of it in SQLite (the SQL is standard; in Postgres you would use SERIAL or an identity column instead of AUTOINCREMENT):

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE orders (id INTEGER PRIMARY KEY, customer TEXT, total INTEGER);
CREATE TABLE outbox (seq INTEGER PRIMARY KEY AUTOINCREMENT, event TEXT, sent INTEGER DEFAULT 0);
""")

def place_order(order_id, customer, total, fail=False):
    try:
        with db:                                  # one transaction: both rows or neither
            db.execute("INSERT INTO orders VALUES (?,?,?)", (order_id, customer, total))
            db.execute("INSERT INTO outbox (event) VALUES (?)",
                       (f'{{"type":"OrderPlaced","id":{order_id}}}',))
            if fail:
                raise RuntimeError("boom before commit")
    except RuntimeError as e:
        print("order", order_id, "->", e)

place_order(1, "alice", 40)
place_order(2, "bob", 15, fail=True)             # rolls back BOTH rows
place_order(3, "carol", 99)

print("orders:", db.execute("SELECT id FROM orders").fetchall())
print("outbox:", db.execute("SELECT seq, event, sent FROM outbox").fetchall())

# The relay: publish unsent rows in seq order, then mark them sent.
published = []
for seq, event in db.execute("SELECT seq, event FROM outbox WHERE sent = 0 ORDER BY seq").fetchall():
    published.append(event)                       # stand-in for producer.send(...)
    db.execute("UPDATE outbox SET sent = 1 WHERE seq = ?", (seq,))
    db.commit()
print("published:", published)

Event sourcing versus CDC

The two ideas sound alike and are easy to confuse, because both revolve around a log of events. They differ in which side is the truth.

Event sourcing

The events are the source of truth. The application records "OrderPlaced", "ItemAdded", "OrderShipped" as an append-only log, and current state is whatever you get by replaying (folding) the events. A shopping cart is the sum of its events. You get a perfect audit trail and can rebuild any view by replay. The price: you design the whole application around it, and changing the meaning of old events is hard.

CDC / outbox

The database is the source of truth and the events are derived from it. The application keeps using ordinary tables; CDC makes their changes visible as a stream. You can retrofit it onto a system that already exists. The events describe row changes (or outbox payloads), not necessarily business intent.

Both lead to the same powerful pattern: derived data. Once changes are a log, every other representation of the data is a function of that log, which anyone can rebuild by replaying it:

  • A cache (chapter 14) can be updated or invalidated from the stream, instead of by each writer remembering to do it. The invalidation problems of chapter 14 mostly arise because the invalidating code and the writing code are separate; reading the database log removes that gap. Case 3 (Facebook's memcache) does exactly this at scale: invalidations that flow from the database's log.
  • A search index (chapter 17) is a derived structure by nature: the database holds the data, the index holds a differently-shaped copy optimised for text queries. CDC keeps it fresh. When the index's analyser changes, you rebuild it by replaying the log into a new index.
  • A materialised view (a precomputed query result such as "revenue per day") can be maintained incrementally from the change stream.
  • A warehouse (chapter 9) gets near-real-time loads instead of nightly batch ones (chapter 18).

Think of the library again: the desk's record of loans and returns is the one authoritative record. The catalogue cards, the "most borrowed this week" poster and the annual report are all derived from it, and if a card is lost, a librarian rebuilds it from the record. They would never update the card and the record separately and hope.

Stream processing basics

Once data is a stream you can compute over it as it flows, using a framework such as Apache Flink or Kafka Streams. Four ideas cover most of what you will meet.

Windows. A stream never ends, so "how many orders?" needs a time frame. A tumbling window has a fixed length and no overlap (every event is in exactly one: "orders per minute"). A sliding window (also called a hopping window) has a fixed length but moves in smaller steps, so windows overlap ("orders in the last 5 minutes, updated every minute"). A session window has no fixed length: it groups events from the same actor that arrive close together and ends after a gap of inactivity ("one user's browsing visit").

Event time versus processing time. Event time is when the thing happened (a timestamp inside the event); processing time is when your system got around to seeing it. Phones go through tunnels, mobile networks buffer, consumers lag, and connectors replay. If you window by processing time, a replay of yesterday's data lands in today's windows, and the answers are wrong. Windowing by event time gives answers that do not depend on how quickly the data happened to arrive, but it raises a new question.

Late events. When can you decide that the 10:00-10:01 window is complete? An event stamped 10:00:30 might still be on its way. Stream processors use a watermark: a moving claim of the form "I believe no more events earlier than time T will arrive". It is a heuristic, so some events arrive after their window closed. You then choose: drop them, count them in a "late" side output, or keep the window open longer and emit a corrected result. There is no free choice; it trades completeness against latency (and note that clocks, as in networking ch. 17, are never perfect).

Joins. Two common shapes. A stream-table join enriches each event with reference data: for each "order placed" event, look up the customer's current tier. The table is itself maintained from a changelog stream (CDC again), usually held in the processor's local state. A stream-stream join matches two event streams within a time window ("a click followed by a purchase within 30 minutes") and so needs to buffer both sides. Both are the streaming versions of the joins of chapter 8.

Backpressure and consumer lag

What if producers are faster than consumers? In a push-based system with an in-memory queue, the queue grows until memory runs out (systems ch. 14 covers why unbounded queues are a trap, and how a bounded queue pushes backpressure back on the producer). A log-based broker handles this differently: consumers pull at their own pace, and the unread data waits on the broker's disk. The producer is not slowed down, and a slow consumer cannot hurt it.

The number that tells you how that is going is consumer lag: for each partition, the latest offset written minus the offset the group has committed. Lag of a few records is normal. Lag that is steadily growing means the consumers are slower than the producers, and it will keep growing until something changes. It is the most important health metric of any stream pipeline. Lag also means staleness: if the search indexer is 10 minutes behind, search results are 10 minutes stale.

What can you do when lag grows? Add consumers to the group (up to the partition count; beyond that, extras sit idle). Make the handler faster, or batch its writes. Find the slow dependency, since a consumer that calls a slow service per record is limited by it. Or shed load, for data where that is acceptable. And watch retention: if a consumer falls so far behind that the broker deletes records it has not read yet, those records are gone for that consumer, and it must re-snapshot or skip ahead. Remember too that a consumer that is down for a long time is just a consumer with unbounded lag.

Distributed systems connection

Everything here is networking chapters 16, 18 and 20 in a database costume. At-least-once delivery plus idempotence is the retry advice of chapter 16. The partitioned log is a replicated log (chapter 20) cut into independent shards (chapter 19), and its consumers' offsets are a tiny version of "how far has each replica applied the log?" (chapter 18). Even "derived data" is the replicated state machine idea: agree on the order of changes once, and let every consumer rebuild its own state from it. Key takeaways

  • Three ways to move events: direct calls, queues (consumed and deleted on ack), and logs (retained, replayable, each reader with its own offset).
  • In a partitioned log, ordering holds within a partition only. The partition key decides what stays ordered, so key by the entity whose events must stay in order.
  • Delivery is at-most-once (commit then process), at-least-once (process then commit) or effectively-once (at-least-once plus idempotent consumers or an atomic commit of effect and offset). True exactly-once delivery over a network does not exist; exactly-once effects do.
  • The dual write (database plus cache or index, with no shared transaction) drifts: a crash between the writes, a rollback after the first, or a race between writers leaves silent, permanent inconsistency.
  • CDC turns the database's own log into a stream (snapshot first, then follow the log). The transactional outbox writes the event in the same transaction as the data and lets a relay publish it. Both give at-least-once, so consumers must be idempotent.
  • With a log, every cache, index and view is derived data, rebuildable by replay. Event sourcing makes the events the truth; CDC derives events from a database that stays the truth.
  • Stream processing adds windows, event time versus processing time, watermarks and late events, and stream-table joins. Watch consumer lag: growing lag means stale data and, eventually, data deleted before it was read.

Check your understanding

A consumer processes each record and then commits its offset. It crashes after processing record 41 but before committing. What happens on restart, and what is the delivery guarantee?

  1. Record 41 is skipped; at-most-once
  2. Record 41 is processed again, and nothing in the system can make that harmless
  3. Record 41 is processed again; at-least-once, so the handler should be idempotent
  4. The broker detects the crash and avoids redelivery; exactly-once
The committed offset still points at 41, so the consumer re-reads it: process-then-commit gives at-least-once. The duplicate is harmless only if the handler is idempotent or deduplicates, which you can build.

Events about order 7 land in partition 2, and events about order 9 land in partition 0. Which statement is guaranteed?

  1. All events about order 7 are read in the order they were written
  2. An event about order 9 written earlier is always read before one about order 7 written later
  3. Consumers see every event in global write order
  4. Order is guaranteed only if you use a single consumer group
Order is preserved within a partition, so per-key order holds when the key chooses the partition. Between different partitions there is no defined order, whatever the number of groups.

Your service inserts an order into the database and then publishes "OrderPlaced" to Kafka. Which failure is NOT possible with this code?

  1. The order is saved but the event is never published
  2. The process crashes between the two steps
  3. If the publish comes first and the commit then fails, an event exists for an order that does not
  4. The database and Kafka are updated in one atomic step
There is no transaction spanning the database and Kafka, so the other three failures are all possible. The atomic step in option 4 is exactly what the dual write lacks, and what the outbox restores by moving the event into the database transaction.

Why does the transactional outbox write the event row in the same transaction as the business data?

  1. So the event is delivered to consumers exactly once
  2. So the data and the event are atomic: both are committed or both are rolled back, leaving nothing lost and no phantom event
  3. So Kafka does not need to store the event durably
  4. So consumers never need to be idempotent
Atomicity of one local transaction removes the window between the two writes. The relay still delivers at-least-once, so consumers still need to cope with duplicates.

A phone records a purchase at 10:00 while offline and uploads it at 10:07. A stream job counts purchases per minute. If it uses processing time, which minute gets the purchase, and what do you use to fix it?

  1. 10:00; use a bigger window
  2. 10:07; use a faster consumer
  3. 10:07; window by event time and use a watermark to decide when a window is complete
  4. 10:00; processing time and event time are always the same
Processing time is when the system sees the record, so it lands in the 10:07 window. Windowing by event time puts it in 10:00, and a watermark decides how long to wait for stragglers before closing a window.

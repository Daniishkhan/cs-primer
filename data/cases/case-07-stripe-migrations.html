Online Migrations at Stripe

Stripe needed to change how it stored hundreds of millions of subscription records, and it could not stop the service to do it. Its 2017 engineering post describes a four-phase recipe it calls a common pattern: write to both places, move the reads, move the writes, then delete the old data, checking at every step that old and new agree.

The pattern in one sentence

Never flip a switch; widen then narrow: make the system write to old and new together, backfill what is missing, prove the two agree, move readers across, move writers across, and only then remove the old copy.

What happened, step by step

Step through

Four phases of an online migration

  1. Before. The application reads and writes subscriptions stored as an array on each Customer. Updating or querying a subscription means handling the whole Customer record.
  2. Phase 1: dual writing. The post's first phase is "dual writing to the existing and new tables to keep them in sync". New subscriptions are written to both. Existing ones are copied lazily whenever they are updated, and the rest are backfilled offline (below).
  3. Verify. Using Scientist, the code reads from both the old and new locations and, in the post's words, raises an error alerting engineers if the results do not match. Per the post, a failure in the experimental path does not affect the rest of the application.
  4. Phase 2: change reads. "Changing all read paths in our codebase to read from the new table." The post's conclusion says all the changes were incremental and the team never attempted to change more than a few hundred lines of code at one time.
  5. Phase 3: change writes. "Changing all write paths in our codebase to only write to the new table." The post says the write order is reversed (new store first, then archived to the old one), and describes making the old subscriptions accessor raise an error so no code can keep using it unnoticed.
  6. Phase 4: remove old data. "Removing old data that relies on the outdated data model." The post describes emptying the old array lazily as subscriptions are loaded, then running a final job to find what remains.

The backfill

The post explains that copying only on update would leave records that are never touched. To cover them, database snapshots were made available to a Hadoop cluster, where MapReduce jobs written with Scalding (a Scala library) identified the subscriptions to copy. A multi-threaded fleet then did the copying, and the Scalding job was run again afterwards to check for anything missing. For scale, the post imagines one second per object: it would take "over three years" to migrate one hundred million objects one at a time, which is why the copy must run in parallel.

Common misconception: "a backfill is a one-off script"

A backfill that runs alongside live traffic races with it. The dual write and the backfill must agree on who wins when both touch the same row, and the backfill must be safe to run twice. In the toy below the backfill uses INSERT OR IGNORE, so it never overwrites a newer dual write. That is a general pattern, not a detail from the post.

The pattern explained

In general, the idea that makes this safe is that every step is small and observable. Before any reader depends on the new store, you have measured that it matches. Before any writer abandons the old store, you have moved all readers. The post says its changes were small and incremental (never more than a few hundred lines at once); in general, that keeps any one mistake small and easier to undo.

It resembles the compatibility rule in chapter 3: old and new code run at the same time, so each version must tolerate the other's data. And it contains the dual-write problem of chapter 19 in a milder form: writing two places can leave them disagreeing if the second write fails. The post does not describe how Stripe handled such failures, so what follows about that is general.

Analogy: moving house with the shop open

You keep the old shop running while stocking the new one. For a while each sale is rung up in both tills (dual write). Staff carry over the old stock in the evenings (backfill). You count both shelves and check they match (verify). Then customers are pointed to the new shop (reads), and finally the old shop stops taking deliveries (writes) and is emptied and locked (remove).

Where it breaks down: shelves do not change between your two counts, but data does. Verification is a continuous alarm, not a single count.

Trade-offs and lessons

It is slow on purpose

Four phases plus verification take far longer than a maintenance window. The trade is many small, safe changes in place of one big risky one, with no downtime.

Dual writes can diverge

General pattern: if a process dies between the two writes, the stores disagree. Verification and idempotent re-copying are what repair that; the outbox in Lab 6 is a stronger fix for a related problem.

Order matters

General pattern: reads move before writes. If writes moved first, readers would be looking in a store that no longer receives updates.

Make surprises loud

The post's raising accessor and Scientist alerts both turn a silent inconsistency into an immediate signal.

What the post does not say

It does not name a feature-flag mechanism (it describes ramping up the percentage of objects that are dual-written while watching operational metrics), and it gives no duration figures for the real backfill beyond the hypothetical above.

Try it yourself

A toy dual write, backfill and comparison

This SQLite script has an old table with the data in a field on each customer, and a new subscriptions table. It updates one customer through the dual-write path, backfills the rest, then compares old and new reads and catches a stray write to the old path.

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE customers(id INTEGER PRIMARY KEY, subs TEXT);        -- old model
CREATE TABLE subscriptions(id INTEGER PRIMARY KEY, customer_id INT, plan TEXT);  -- new model
""")
db.executemany("INSERT INTO customers VALUES (?,?)", [(i, "basic") for i in range(1, 6)])

# Phase 1a: dual write (new code path)
def set_plan(cid, plan):
    db.execute("UPDATE customers SET subs=? WHERE id=?", (plan, cid))
    db.execute("INSERT INTO subscriptions(id,customer_id,plan) VALUES (?,?,?) "
               "ON CONFLICT(id) DO UPDATE SET plan=excluded.plan", (cid, cid, plan))
set_plan(2, "pro")                       # customer 2 is touched, so lazily copied
missing = lambda: [r[0] for r in db.execute(
    "SELECT c.id FROM customers c LEFT JOIN subscriptions s ON s.id=c.id WHERE s.id IS NULL")]
print("not yet copied:", missing())

# Phase 1b: backfill the rest (offline job, safe to re-run)
db.execute("INSERT OR IGNORE INTO subscriptions SELECT id,id,subs FROM customers")
print("after backfill:", missing())

# Verify: compare old and new reads (the Scientist idea)
def read_old(cid): return db.execute("SELECT subs FROM customers WHERE id=?", (cid,)).fetchone()[0]
def read_new(cid): return db.execute("SELECT plan FROM subscriptions WHERE id=?", (cid,)).fetchone()[0]
db.execute("UPDATE customers SET subs='enterprise' WHERE id=3")   # a stray old-path write: a bug
print("mismatches:", [c for c in range(1, 6) if read_old(c) != read_new(c)])
not yet copied: [1, 3, 4, 5]
after backfill: []
mismatches: [3]

The mismatch on customer 3 is exactly what the verification step is for: some code path still writes to the old model only. Extend the script with a read(cid) function behind a flag, switch it to the new table, and then make writes to the old column raise an error, as the post describes for its accessor.

Distributed systems connection

At scale, "the old store" and "the new store" are often different services, each deployed on its own schedule, so no instant exists when everything switches together. The four-phase shape is how you get agreement without a global moment: widen the set of states the system tolerates, then narrow it. General pattern: the same shape applies to changing a schema, a message format, a shard layout (see the Figma case) or an API.

Key takeaways

  • Stripe moved hundreds of millions of subscriptions to their own table without pausing the service.
  • The four phases: dual write, change reads, change writes, remove old data.
  • Records not touched by traffic are covered by an offline backfill, run again afterwards to check for gaps.
  • Scientist compared old and new results in production and raised an alert on any mismatch, before reads moved.
  • Small steps (the post says never more than a few hundred lines at once) keep each change easy to observe and, in general, to undo.

Check your understanding

Why does the pattern move reads to the new store before writes?

  1. Reads are less important than writes
  2. Because writes are always faster
  3. While dual writing continues, the new store is kept current and can be checked before readers depend on it; stopping old writes first would leave readers on a stale store
  4. It does not matter which comes first
The post's phase order is dual write, change reads, change writes, remove. In the post, the old store stops receiving writes only in the last phase, once no code relies on it.

What was the Scalding/Hadoop job for?

  1. Identifying subscriptions that still needed copying to the new table, and checking afterwards for gaps
  2. Serving customer traffic
  3. Encrypting the old table
  4. Replacing the database
The post says database snapshots went to a Hadoop cluster where MapReduce jobs written with Scalding found what to copy, and the job was run again to look for missing records.

What does Scientist do in this story?

  1. Generates test data
  2. Locks the old table
  3. Rolls back deployments automatically
  4. Compares the results of the old and new code paths in production and alerts if they differ
The post describes it as a Ruby library for running experiments that compare two code paths, alerting if they ever give different results.

In the toy script, why does the backfill use INSERT OR IGNORE?

  1. To delete rows from the old table
  2. So it does not overwrite rows the dual-write path already put in the new table, and is safe to re-run
  3. To make SQLite faster
  4. To create the table
A backfill racing with live writes must not clobber newer data. This is a general safeguard; the post does not give its backfill's conflict rules.

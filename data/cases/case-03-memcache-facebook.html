Scaling Memcache at Facebook

The 2013 paper by Nishtala and colleagues describes how Facebook turned memcached, an in-memory hash table that can run on a single machine, into the cache layer for the largest social network of its day. Its lasting contribution is a catalogue of what goes wrong when a look-aside cache gets big, and a small, practical fix for each problem.

The pattern in one sentence

A look-aside cache is simple until it is large: then races between readers and writers produce stale values, hot keys produce stampedes, and replication lag between regions makes "delete the key" arrive before the data it should protect, so each of those needs its own explicit mechanism.

The cast

You met the cache patterns in chapter 14 and replication lag in chapter 15. Here is how the paper uses them. Every number on this page about Facebook comes from the paper; the diagrams and the code are illustrative sketches.

memcached and "memcache"
The paper uses "memcached" for the source code or a running binary, and "memcache" for the distributed system built from it. The open-source version offers set, get and delete on a single-machine in-memory hash table, with no server-to-server coordination.
The web server and its client library
The client does serialisation, compression, request routing, error handling and batching. It keeps a map of available servers. The paper deliberately keeps clients stateless and memcached servers simple.
mcrouter
A proxy that presents a memcached interface and routes requests and replies to and from other servers. It also coalesces TCP connections from many web threads.
MySQL
The authoritative store behind much of the cache. Memcache "is not the authoritative source of the data", the paper says, and is therefore allowed to evict.
Clusters and regions
A frontend cluster is web servers plus memcached servers. Several frontend clusters plus a storage cluster of databases make a region. Regions are spread around the world, with one master region and the others read-only replicas.
mcsqueal
An invalidation daemon on every database that reads the SQL statements the database commits and broadcasts the cache deletes they embed.

The base pattern: demand-filled look-aside

On a read, the web server first asks memcache for a key. On a miss it queries the database (or another backend), then sets the value in the cache. On a write, it updates the database and then sends a delete to memcache. The paper explains why delete rather than update: deletes are idempotent. This is the cache-aside pattern of chapter 14.

The workload justifies it. Users consume an order of magnitude more content than they create, so reads dominate. And the fan-out is large: loading one popular page averages 521 distinct items from memcache, and a web server can fetch thousands of key-value pairs for a page. The paper reports that the system handles billions of requests per second and stores trillions of items. It also states a design principle that is worth carrying with you: the probability of reading transient stale data is treated as a parameter to tune, like responsiveness. Facebook was "willing to expose slightly stale data in exchange for insulating a backend storage service from excessive load".

Problem 1: leases for stale sets and thundering herds

Two different bugs come from the same cause, a cache miss followed by a slow refill. The paper names them. A stale set happens when a web server sets a value in memcache that does not reflect the latest value, which "can occur when concurrent updates to memcache get reordered". A thundering herd happens when a key with heavy read and write activity is repeatedly invalidated, so many reads fall through to the database.

The fix is a lease. When a client misses, memcached gives it a 64-bit token bound to that key. The client must present the token when it sets the value. If memcached has since received a delete for the key, it has invalidated the token and rejects the set. The paper compares this to load-link/store-conditional.

Step through

A lease blocks a stale set

  1. A misses and gets a lease. Memcache returns a miss together with a token bound to this key.
  2. A reads the database. It gets version v1. A is slow, so the refill has not happened yet.
  3. B writes. B updates the database to v2 and deletes the key. The delete invalidates lease #1.
  4. A's late set arrives. The token no longer matches, so memcache refuses. The cache stays empty and the next reader will refill with v2.

The same token mitigates the herd. Each memcached server limits how often it returns a token: by default, once every 10 seconds per key. A request for the key within that window gets a special notification telling it to wait a short time. Typically the client holding the lease has set the data within a few milliseconds, so waiting clients retry and usually find it. The paper measured keys particularly susceptible to herds for a week: without leases the peak database query rate was 17K/s; with leases it was 1.3K/s. A further option lets applications that can tolerate it take a slightly stale value, rather than waiting.

Common misconception: "delete after write keeps the cache correct"

Delete-after-write is correct only if no earlier reader later sets an old value. The race above is exactly that. Leases are the paper's answer; a general alternative is to give cached values a version and refuse older ones.

Problem 2: many web servers, many cache servers

Because items are spread across hundreds of servers by consistent hashing, "all web servers communicate with every memcached server in a short period of time". The paper names two consequences: incast congestion and a single hot server becoming a bottleneck for many web servers. Its responses:

  • UDP for gets, TCP for sets and deletes. UDP avoids connection overhead; dropped or out-of-order packets are treated as errors, and the client treats a failed get as a miss. At peak, 0.25% of gets are discarded. The paper reports roughly a 20% latency reduction over TCP through mcrouter.
  • A sliding window limiting outstanding requests, growing slowly on success and shrinking on a lost request, like TCP congestion control.
  • Pools. A cluster's servers are partitioned into pools with a default "wildcard" pool and separate pools for keys whose behaviour interferes with others. For example, low-churn keys that are still valuable are evicted before high-churn keys that are no longer being accessed, unless the two are kept apart.
  • Replication within a pool for key families that are fetched many at a time, fit on one or two servers, and are requested at a much higher rate than one server can manage. Replicating lets any replica serve a whole multi-key request; the price is that invalidations must reach every replica.
  • Gutter. If a client gets no response it assumes the server has failed and asks a small Gutter pool (about 1% of the cluster's servers), caching there for a short time. The paper says this reduces client-visible failures by 99% and turns 10% to 25% of failures into hits each day. The alternative of rehashing the keys onto the remaining servers risks overloading whichever server inherits a hot key; the paper notes a single key can account for 20% of a server's requests.

Problem 3: many frontend clusters, one database

Adding web and memcached servers does not fix everything: popular items get more popular and incast worsens, so the paper splits them into multiple frontend clusters sharing a storage cluster. That is a region. This reduces incast and gives smaller failure domains, at the cost of data being replicated in several caches. For rarely-read, bulky data a regional pool keeps one copy per region, trading cross-cluster latency (the paper notes 40% less average bandwidth across cluster boundaries) for memory.

Invalidation through the database log

With data cached in many clusters, who sends the deletes? Web servers could. The paper explains why that is a poor fit: they batch badly, and a systemic fault such as misrouted deletes would historically require a slow rolling restart of the whole memcache fleet. Instead, SQL statements that modify authoritative state are amended to include the memcache keys to invalidate once the transaction commits, and mcsqueal on each database reads the committed statements and extracts those deletes. Because the keys travel in the database's reliable log, mcsqueal can "simply replay" deletes that were lost or misrouted. To reduce the packet rate between storage and frontend clusters, deletes are batched and sent to dedicated mcrouter servers in each frontend cluster, which unpack and route them. The paper reports an 18x improvement in the median number of deletes per packet, and notes that only 4% of the deletes issued actually invalidate cached data.

Starting from nothing: cold cluster warmup

A new or restarted frontend cluster has a nearly empty cache, so everything would hit the databases. Cold Cluster Warmup lets clients in the cold cluster fetch from a warm cluster instead of the database. The paper says this brings a cold cluster to full capacity in a few hours instead of a few days. The race it must avoid: a cold-cluster client updates the database, another client reads the stale value from the warm cluster before it has received the invalidation, and the stale item then sits in the cold cluster. The defence is a two-second hold-off on deletes to the cold cluster, which makes a later add fail; a failed add tells the client newer data exists, so it refetches from the database. The paper admits a theoretical gap if a delete is delayed longer than that, calls it rare, and turns the mechanism off once the hit rate stabilises.

Across regions: remote markers

Regions add distance. One region holds the master databases and the rest are read-only MySQL replicas, so replica lag is the problem, and the paper says it provides "best-effort eventual consistency" with an emphasis on performance and availability. Two cases follow.

  • Write from the master region. A web server there should not invalidate cache entries in a replica region directly, because the replica database may not have the change yet; a refill from it would race with replication and could cache stale data. That is why the invalidation pipeline above (mcsqueal, riding the replication stream) is the safe route. The paper notes that mcsqueal was implemented after scaling to multiple regions.
  • Write from a non-master region. The user's next request could miss their own change if the replica is lagging. A remote marker fixes this: the web server (1) sets a remote marker for the key in the region, (2) writes to the master, embedding the key and the marker to be invalidated in the SQL, and (3) deletes the key locally. On the next read the key is missing; if the marker is present, the query is directed to the master region, otherwise to the local replica. Paper's own summary: it trades extra latency on a cache miss for a decreased probability of reading stale data.

The paper is careful to say that markers are not an ordinary cache entry. As a cache, deleting or evicting keys is always a safe action; for a marker it is not, since its presence tells you whether the replica is stale. In practice, the paper says, eviction of markers and concurrent modification are rare.

Analogy: the library and its branch libraries

The main library (master region) holds the master catalogue; branches get photocopies of it a bit later. A reader at a branch who returns a book and immediately asks for it should not be told it is still on loan. So the branch stamps a "check the main library" note on that book's shelf slot, and until the photocopy of the catalogue catches up, anyone asking for that book is sent to the main library instead of the branch's out-of-date copy.

Where it breaks down: the note lives in a cache that can in principle lose it, which is why the paper treats the marker as a special case.

Trade-offs and lessons

Consistency as a tuned parameter

The paper treats the probability of stale reads like latency: something to tune against load on the databases. Stricter semantics, it says, mostly never leave the design phase because they cost too much at this volume.

Every shortcut has a stated gap

UDP drops, the two-second hold-off, the 10-second token rate, concurrent marker deletion: the paper names the cases where the mechanism can still let a stale value through, and why it accepted them.

Put complexity in clients

Memcached servers do not talk to each other. Routing, batching, flow control and failover logic live in a stateless client or proxy, which keeps the servers simple and fast and makes the software easy to roll out.

Reuse the database log

Embedding deletes in the SQL that the database already logs gives a durable, replayable invalidation stream, rather than inventing a second reliable channel.

A dated source

This is a 2013 paper about Facebook's system at that time. It tells you what problems appear at that scale and one set of answers. It does not describe Facebook's systems today, and the paper itself says its consistency model "evolved over the years to suit the scale of the site".

Try it yourself

A lease in under 30 lines

This sketch (mine, not Facebook's code) models a cache with and without leases, and shows both problems from the paper: the stale set and the herd. It is pure Python with no I/O.

class Cache:
    def __init__(self, leases): self.leases, self.data, self.tokens, self.next = leases, {}, {}, 1
    def get(self, k):
        if k in self.data: return ("hit", self.data[k])
        if not self.leases: return ("miss", None)
        if k in self.tokens: return ("wait", None)          # a token is already out: back off
        self.tokens[k] = self.next; self.next += 1
        return ("miss+lease", self.tokens[k])
    def set(self, k, v, token=None):
        if self.leases and self.tokens.get(k) != token: return False   # lease invalidated or absent
        self.data[k] = v; self.tokens.pop(k, None); return True
    def delete(self, k): self.data.pop(k, None); self.tokens.pop(k, None)

for leases in (False, True):
    db, c = {"k": "v1"}, Cache(leases)
    print(f"--- stale set, leases={leases}")
    status, tok = c.get("k")                 # reader A misses, reads the database ...
    seen_by_A = db["k"]                      # ... and gets v1
    db["k"] = "v2"; c.delete("k")            # a writer updates the database and invalidates
    ok = c.set("k", seen_by_A, tok)          # A's slow set arrives last
    print("A's set accepted:", ok, "| cache now:", c.data.get("k"), "| database:", db["k"])

for leases in (False, True):
    c, db_reads = Cache(leases), 0
    for _ in range(50):                      # 50 web servers miss on the same hot key at once
        status, tok = c.get("hot")
        if status in ("miss", "miss+lease"): db_reads += 1
    print(f"herd of 50, leases={leases}: database reads = {db_reads}")

Output when run:

--- stale set, leases=False
A's set accepted: True | cache now: v1 | database: v2
--- stale set, leases=True
A's set accepted: False | cache now: None | database: v2
herd of 50, leases=False: database reads = 50
herd of 50, leases=True: database reads = 1

Things to try: give the herd a TTL on the token (the paper's 10 seconds), so a second token is issued if the first holder dies; or add a stale-value option that returns the last value for waiting clients instead of "wait". Notice how the code mirrors the paper: it needs no change to the database at all.

Distributed systems connection

Three ideas here recur. First, the lease is a small piece of versioning: a token that proves your information is still current, much like the fencing tokens of chapter 15. Second, remote markers are read-your-writes consistency (also chapter 15) implemented by routing: send a reader to the leader when its follower may lag. Third, the stampede and the hot key are the cache faces of problems you will see again in sharding. The paper is also a good example of an explicit consistency model chosen for cost, not purity; see the consistency ladder in networking chapter 18.

Key takeaways

  • Facebook used memcache as a demand-filled look-aside cache and invalidated by delete after the database write, because deletes are idempotent.
  • Leases (64-bit tokens) reject stale sets after a delete and, with a once-per-10-seconds token rate, damp thundering herds: peak database load on susceptible keys went from 17K/s to 1.3K/s in the paper's measurement.
  • Pools, in-pool replication, a sliding window and Gutter handle the effects of scale inside a cluster.
  • mcsqueal replays deletes embedded in the database's committed SQL, so invalidation is durable and batched.
  • Remote markers send a read to the master region when a replica may be stale: extra latency for fewer stale reads.

Check your understanding

What does a lease prevent?

  1. A cache server from evicting any key
  2. A slow reader from storing an outdated value after the key has been invalidated
  3. MySQL from replicating to another region
  4. Clients from using UDP
A delete invalidates the token, so a later set that presents the old token is rejected. This stops the stale set.

How do leases also reduce thundering herds?

  1. They make the database faster
  2. They keep all keys in memory forever
  3. They send every miss to a different cluster
  4. A server hands out a token for a key only once per interval (10 seconds by default); other clients are told to wait and retry, and usually find the data
Only the token holder goes to the database. The paper measured a peak of 17K queries per second without leases and 1.3K per second with them on a set of herd-prone keys.

Why does mcsqueal tail the database's committed SQL instead of letting web servers broadcast invalidations?

  1. The invalidations are batched better, and because they ride in the database's reliable log, lost or misrouted deletes can be replayed
  2. Web servers are not allowed to write
  3. It removes the need for MySQL
  4. It makes the cache authoritative
The paper cites packet overhead and the lack of recourse after a systemic misrouting as problems with web-server invalidation. Embedded deletes in committed SQL make replay possible.

A user in a non-master region updates their profile and immediately reloads. What does the remote marker do?

  1. Blocks the user until replication catches up
  2. Copies the whole database to the local cache
  3. On a cache miss for that key, directs the read to the master region while the marker exists, trading latency for a lower chance of stale data
  4. Deletes the user's data from the replica
The marker signals that the local replica database may be stale. The paper trades extra latency on a miss for a decreased probability of reading stale data.

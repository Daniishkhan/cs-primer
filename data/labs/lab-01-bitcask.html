Lab 1: A Log-Structured Key-Value Store

In this lab you build a small Bitcask: a key-value store made of nothing but append-only files and a hash table in memory. You will start with a file you have to scan from the top, make lookups instant with an index, turn deletes into records, survive torn and corrupted files, and finally squeeze the garbage out with a compaction that is safe even if the power fails halfway through. About 150 lines of your own code give you the core of a real storage engine.

Why this lab matters

Chapter 4 described this design in prose and showed it in a widget. Here you build it, and the pieces that looked simple on paper turn out to hold the interesting problems: what exactly is in a record, what to do with half a record, how a delete can be a write, and how to replace files you are still reading from. The same four ideas (append-only log, in-memory index, tombstones, compaction) return in LSM trees, Kafka, write-ahead logs and replication. If you can build this, you can read the storage layer of most modern systems.

Requirements

Python 3.8 or newer, standard library only, on macOS, Linux or Windows. Everything happens in temporary directories that check.py creates and deletes, so it will not touch your files. (On Windows the directory fsync of milestone 5 is skipped, because Windows cannot open a directory that way; the rest is identical.)

What the crash tests can and cannot prove

Milestone 4 damages files directly: it cuts a log at many byte offsets, flips bits, and appends garbage, then checks that recovery returns exactly the data that was whole. That tests your record format and your recovery logic thoroughly. It cannot test whether your fsync calls really reach the disk, because the operating system's page cache would hide a missing one in any test that does not cut the power. The Crash-Safe Storage lab in the Systems course explains that limit in detail, and systems chapter 9 explains why. What this lab does check is the order of the steps in compaction: the new file must be synced before it is renamed into place.

What you'll build

Six milestones, each building on the last (the sixth is optional):

  1. The record and the slow store: a record format with a CRC, and a put/get that scans the file from the start.
  2. The index: a dict from key to (segment, offset, size), so a get is one seek. You will measure the difference.
  3. Deletes and segments: a delete appends a tombstone; a full segment is sealed and a new one begins.
  4. Crash recovery: on open, rebuild the index by replaying every segment, and cut off a torn or corrupt tail.
  5. Compaction: merge the segments, keep only the latest live value per key, and swap the files in without ever risking the data.
  6. (optional) Hint files: remember each sealed segment's keys, so startup does not have to read every value.

Milestone 1: a record you can trust, and the slow store

A log is a long run of bytes, so every record must say how long it is and prove it is intact. This is the layout from chapter 4 (Bitcask's own records also carry a timestamp, which we skip):

  • key len, val len let a reader know exactly where the record ends. Integers are big-endian: struct.pack(">I", n) (I is an unsigned 4-byte integer, i a signed one). The value length is signed so that -1 can mean "tombstone", which is not the same thing as an empty value (length 0).
  • crc32 (zlib.crc32) is the checksum idea from systems chapter 9. It covers the two lengths as well as the data. Otherwise a damaged length field would make the reader jump to a random place and still believe it had found a record.
  • decode_record must never trust a length before checking it. A garbage length such as 0x7FFFFFF0 must make it return None, not try to read two gigabytes. Torn writes and flipped bits are exactly how such lengths appear.

You will write encode_record and decode_record, and then the slow store, ScanStore: a single file where put appends a record and get reads the whole file, walking it record by record and keeping the last value it sees for the key. It is the Python version of chapter 4's two-line shell database, and it is the baseline you will beat in milestone 2.

  • Build the part after the checksum first: body = struct.pack(">Ii", len(key), vlen) + key + (value or b""). Then struct.pack(">I", zlib.crc32(body)) + body. Careful: value or b"" is right for both None and b"", but vlen must be -1 only for None.
  • HEADER.unpack_from(buf, pos) returns (crc, klen, vlen) without copying. Check, in this order: enough bytes for a header; klen and vlen in range; the whole record fits in the buffer; the CRC matches buf[pos + 4:end].
  • The value length of a tombstone is -1, so the end of the record is key_end + max(vlen, 0).
  • ScanStore.get loops rec = decode_record(data, pos) until it returns None, remembering the value whenever the key matches. A later record for the same key overrides an earlier one, and a tombstone's value None naturally means "not found".

def encode_record(key, value):
    """Bytes for one record. value=None encodes a tombstone (value length -1)."""
    vlen = -1 if value is None else len(value)
    body = struct.pack(">Ii", len(key), vlen) + key + (value or b"")
    return struct.pack(">I", zlib.crc32(body)) + body
def decode_record(buf, pos=0):
    """Parse one record at buf[pos:].

    Returns (key, value, next_pos), where value is None for a tombstone, or
    None if the record is incomplete or fails its checksum. Never raises on
    garbage and never trusts a length before checking it.
    """
    if pos + HEADER.size > len(buf):
        return None                                    # not even a whole header
    crc, klen, vlen = HEADER.unpack_from(buf, pos)
    if klen > MAX_KEY or vlen < -1 or vlen > MAX_VALUE:
        return None                                    # absurd lengths: garbage
    key_start = pos + HEADER.size
    val_start = key_start + klen
    end = val_start + max(vlen, 0)
    if end > len(buf):
        return None                                    # the record is cut short
    if zlib.crc32(buf[pos + 4:end]) != crc:
        return None                                    # damaged, or a half-written write
    key = bytes(buf[key_start:val_start])
    value = None if vlen == -1 else bytes(buf[val_start:end])
    return key, value, end
class ScanStore:
    """The slow version: one file, and every get() scans it from the start."""

    def __init__(self, path):
        self.path = path
        open(path, "ab").close()                       # make sure the file exists

    def put(self, key, value):
        with open(self.path, "ab") as f:
            f.write(encode_record(key, value))

    def get(self, key):
        with open(self.path, "rb") as f:
            data = f.read()
        found, pos = None, 0
        while True:
            rec = decode_record(data, pos)
            if rec is None:
                break
            k, v, pos = rec
            if k == key:
                found = v                              # a later record overrides an earlier one
        return found

Milestone 2: an index makes reads O(1)

Your ScanStore.get reads the whole file, so its cost grows with the amount of data, which is what O(n) means. The cure is the one from chapter 4: a hash table in RAM that remembers where each key's newest record lives. For every key it stores a tuple (segment id, offset, size), and the size is the length of the whole record, so a get can read it with one seek and one read and never needs to scan.

Now you work in the real Store class. It manages a directory of segment files; the plumbing is given. For this milestone everything fits in the first segment, seg-000001.log. Two things to know about the given helpers:

  • self._fd is a raw file descriptor opened for appending (os.O_APPEND), and you write with write_all(self._fd, record). A raw descriptor has no Python-level buffer, so when write_all returns, the bytes are in the operating system. self._active_size is the current size of the active segment, which is also the offset where the next record will start.
  • self._reader(seg_id) returns a cached read handle opened with buffering=0. Without that, Python's buffered reader could hand back stale bytes for a file that is still being appended to.

    def _append(self, key, value):
        """Append one record to the active segment. Returns (segment id, offset, size)."""
        rec = encode_record(key, value)
        # Milestone 3: roll over to a new segment when this record would not fit.
        if self._active_size > 0 and self._active_size + len(rec) > self.max_segment_bytes:
            self._roll()
        offset = self._active_size
        write_all(self._fd, rec)
        if self.sync:
            os.fsync(self._fd)
        self._active_size += len(rec)
        return self.active_id, offset, len(rec)
    def put(self, key, value):
        if value is None:
            raise ValueError("value must be bytes; use delete() to remove a key")
        self.index[key] = self._append(key, value)

    def get(self, key):
        loc = self.index.get(key)
        if loc is None:
            return None
        seg_id, offset, size = loc
        f = self._reader(seg_id)
        f.seek(offset)
        rec = decode_record(f.read(size), 0)            # one seek, one read
        if rec is None:
            raise CorruptionError("record at segment %d offset %d failed its checksum" % (seg_id, offset))
        return rec[1]

Notice what the index does and does not hold: it has one entry per live key, never the values. RAM use therefore grows with the number of keys, not with the amount of data (chapter 4, Why every key must fit in RAM). Try it in the "under the hood" section below: double the number of keys and watch the two stores diverge.

Milestone 3: deletes and segments

You cannot remove a record from a file you only append to. So delete(key) appends a tombstone (a record with value length -1) and removes the key from the index. Why write anything at all, when the index already forgot the key? Because the index lives in RAM. After a restart the index is rebuilt by replaying the log, and replaying the old put without the tombstone after it would bring the key back from the dead (milestone 4 will show it happening).

The second job of this milestone is segments. A single file that grows forever can never be cleaned. So the store appends to one active segment, and when the next record would push it past max_segment_bytes, it seals that segment (fsync it, close it, never write to it again) and starts seg-N+1.log. Sealed segments are immutable, which makes everything that follows simpler: they can be read without locks, compacted in the background and backed up as plain files.

A few details the check will insist on:

  • delete returns True if the key existed, and False if not. Deleting a missing key writes nothing: it would only grow the log.
  • A segment never exceeds the limit, except that a single record bigger than the limit must still be storable. It gets a segment to itself. (So roll over only when the active segment already holds something.)
  • Sealed segments really are never touched again: the check keeps a copy of segment 1's bytes early and compares them after hundreds more writes.

        """Delete a key by appending a tombstone. Returns True if the key existed."""
        if key not in self.index:
            return False                    # nothing to delete: do not grow the log
        self._append(key, None)
        del self.index[key]
        return True

    def _roll(self):
        """Seal the active segment and start the next one."""
        self._seal()
        self._start_segment(self.active_id + 1)

Milestone 4: crash recovery

The index is a cache of the log, and a cache in RAM disappears with the process. So Store.__init__ calls _rebuild_index whenever segment files already exist. The log is the truth: scan every segment from oldest to newest and replay it. For each record, set index[key] to its location, or remove the key if it is a tombstone. Newer records overwrite older ones, so at the end the index is exactly right.

Things can be wrong in two different ways, and they get two different answers:

  • A torn tail in the last segment. The machine died in the middle of an append, so the file ends with half a record, or with a record whose bytes never all arrived. That is expected after a crash. Recovery stops at the first record decode_record rejects, truncates the file there (f.truncate(good_end), then fsync so the repair itself is durable), and carries on. Truncating matters: if you left the garbage in place, the next record you appended would land behind it, and the following restart would stop at the garbage and lose that record.
  • Damage in a sealed segment. A sealed segment was completed and fsynced before the store moved on. A bad record in the middle of one is not a torn write: it means the disk returned wrong bytes. Silently truncating would throw away good data, so recovery raises CorruptionError and lets a human (or a replica) decide, as chapter 4 advises.

A simplification

Treating "the first bad record in the last segment" as the torn tail is the rule the Systems crash-safe log uses too. A real engine can do better: if valid records follow the bad one, the damage is in the middle, not at the tail, and it can report that loudly. The rule is safe only because the store acknowledges a write after the whole record has been written (and, with sync=True, fsynced), so a torn tail can only be a write nobody was told about.

def scan_segment(data):
    """Parse bytes as a run of records.

    Returns (entries, good_end). entries is a list of
    (key, offset, size, is_tombstone), oldest first. good_end is the byte
    offset where the valid prefix ends (len(data) for a healthy segment).
    """
    entries, pos = [], 0
    while pos < len(data):
        rec = decode_record(data, pos)
        if rec is None:
            break
        key, value, nxt = rec
        entries.append((key, pos, nxt - pos, value is None))
        pos = nxt
    return entries, pos
    def _rebuild_index(self, ids):
        """Rebuild self.index by replaying every segment, oldest first."""
        for n, seg_id in enumerate(ids):
            is_last = n == len(ids) - 1
            entries = self._read_hint(seg_id) if (self.hints and not is_last) else None   # Milestone 6
            if entries is None:
                path = self._seg_path(seg_id)
                with open(path, "rb") as f:
                    data = f.read()
                entries, good_end = scan_segment(data)
                if good_end < len(data):
                    if not is_last:
                        raise CorruptionError("sealed segment %d is damaged at byte %d" % (seg_id, good_end))
                    with open(path, "r+b") as f:          # torn tail of the active segment:
                        f.truncate(good_end)              # cut it off, then make that durable
                        f.flush()
                        os.fsync(f.fileno())
            for key, offset, size, is_tombstone in entries:
                if is_tombstone:
                    self.index.pop(key, None)             # a newer tombstone hides older values
                else:
                    self.index[key] = (seg_id, offset, size)

Milestone 5: compaction

An overwrite-heavy workload leaves a log full of garbage. In the experiment below, 3,000 writes to just 100 keys produce 175 kB of log holding about 6 kB of live data. Compaction copies only the live records into a new segment and throws the old files away. A record is live exactly when the index points at it: for each record in the old segments, it is live if self.index.get(key) == (segment, offset, size). Overwritten values, deleted keys, and the tombstones themselves are all dead, so none of them is copied. Because tombstones are dropped, this version compacts all segments at once; if you left some older segment out, a dropped tombstone could let its key's old value come back.

Getting the swap right

Compaction replaces files, and a crash can arrive at any line of it. This is the atomic-replace pattern of systems chapter 9 (the Systems lab builds it for a config file), applied to a set of segments:

  1. Seal the active segment, then pick two new ids. The merged file gets out_id = active_id + 1, and the new active segment gets out_id + 1. Segment ids are the replay order, so the merged file must sort after every input it replaces and before the new writes.
  2. Write the merged file under a temporary name (seg-N.log.tmp) and fsync it. Nothing visible has changed yet. A leftover .tmp is simply deleted when the store opens (that part is given).
  3. os.replace it into its final name, then fsync the directory (self._fsync_dir()) so the rename is durable. Fsync the file before the rename: otherwise a power cut could persist the new name but not the new bytes.
  4. Point the index at the new locations, then delete the old segments, oldest first. Oldest first matters: if the crash comes after the oldest is gone but before the newest is, replay sees the merged file plus the newer originals, which agree. If you deleted the newest first, a tombstone could vanish while an older segment still held the value it hid, and the deleted key would be resurrected on the next start (the "zombie" from chapter 4).

The test sets a trap for exactly this. Its workload writes a key early, deletes it several segments later, then calls compact(hook) and raises an exception from the hook after each stage: tmp_synced, replaced, deleted_1 (after the first old segment is removed) and done. The exception unwinds out of your code like a power cut, and the test reopens the directory and demands the same answers as before.

    def compact(self, hook=None):
        """Merge every segment into one file holding only the live records.

        Safe order: write new -> fsync -> rename -> update index -> delete old, oldest first.
        hook(stage), if given, is called after each step so tests can "crash" there.
        """
        def step(name):
            if hook:
                hook(name)

        inputs = self.segment_ids()
        if not inputs or self.total_bytes() == 0:
            return {"bytes_before": 0, "bytes_after": 0}
        before = self.total_bytes()
        self._seal()                                     # the old active segment is now an input too
        out_id = self.active_id + 1                      # sorts after every input...
        self._start_segment(out_id + 1)                  # ...and before the fresh active segment
        final = self._seg_path(out_id)
        tmp = final + ".tmp"

        new_index = {}
        fd = os.open(tmp, os.O_WRONLY | os.O_CREAT | os.O_TRUNC | getattr(os, "O_BINARY", 0), 0o644)
        try:
            offset = 0
            for seg_id in inputs:
                with open(self._seg_path(seg_id), "rb") as f:
                    data = f.read()
                entries, _ = scan_segment(data)
                for key, off, size, is_tombstone in entries:
                    if is_tombstone or self.index.get(key) != (seg_id, off, size):
                        continue                         # dead: overwritten, deleted or a tombstone
                    write_all(fd, data[off:off + size])  # copy the live record byte for byte
                    new_index[key] = (out_id, offset, size)
                    offset += size
            os.fsync(fd)                                 # the new file is on disk BEFORE we publish it
        finally:
            os.close(fd)
        step("tmp_synced")
        os.replace(tmp, final)                           # the atomic switch
        self._fsync_dir()
        step("replaced")
        self.index.update(new_index)                     # point the index at the new file
        if self.hints:
            self._write_hint(out_id)                     # Milestone 6
        for n, seg_id in enumerate(inputs):              # oldest first: never orphan a tombstone
            self._remove_segment(seg_id)
            if n == 0:
                step("deleted_1")
        self._fsync_dir()
        step("done")
        return {"bytes_before": before, "bytes_after": self.total_bytes()}

Milestone 6 (optional): hint files

Opening a store replays every record of every segment, and that means reading every value too, even though the index never needs them. For a 100 GB store that is minutes of downtime. Bitcask's answer is the hint file: next to each sealed segment, a small file listing just (key, offset, size, tombstone?) for each record. Replaying a hint touches a few bytes per key instead of the whole value, so startup reads a fraction of the data.

A hint is only a cache of what scanning the segment would give, so it must never be trusted blindly:

  • It ends with a trailer holding the segment's size and a CRC of the hint's own entries. A hint with a bad CRC (bit rot, or a torn write when it was created) or whose recorded size no longer matches the segment is ignored, and the segment is scanned instead.
  • It is written when a segment is sealed (the given _seal calls _write_hint if hints=True) and after compaction. The last segment never uses one: it is about to be appended to, and it is where a torn tail lives.
  • Hints are written to a .tmp name, fsynced and renamed, like everything else.

    def _write_hint(self, seg_id):
        """seg-N.hint: (key, offset, size, tombstone?) for every record of a sealed segment."""
        with open(self._seg_path(seg_id), "rb") as f:
            data = f.read()
        entries, _ = scan_segment(data)
        body = b"".join(struct.pack(">IQIB", len(k), off, size, int(t)) + k for k, off, size, t in entries)
        blob = body + struct.pack(">QI", len(data), zlib.crc32(body))   # trailer: segment size, checksum
        tmp = self._hint_path(seg_id) + ".tmp"
        with open(tmp, "wb") as f:
            f.write(blob)
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp, self._hint_path(seg_id))

    def _read_hint(self, seg_id):
        """Entries from the hint file, or None if it is missing, damaged or stale."""
        try:
            with open(self._hint_path(seg_id), "rb") as f:
                blob = f.read()
            seg_size = os.path.getsize(self._seg_path(seg_id))
        except OSError:
            return None
        trailer = struct.Struct(">QI")
        if len(blob) < trailer.size:
            return None
        body = blob[:-trailer.size]
        size_then, crc = trailer.unpack(blob[-trailer.size:])
        if crc != zlib.crc32(body) or size_then != seg_size:
            return None                                  # corrupt, or the segment changed
        entries, pos, head = [], 0, struct.Struct(">IQIB")
        while pos < len(body):
            klen, off, size, tomb = head.unpack_from(body, pos)
            pos += head.size
            entries.append((body[pos:pos + klen], off, size, bool(tomb)))
            pos += klen
        return entries
    def _rebuild_index(self, ids):
        """Rebuild self.index by replaying every segment, oldest first."""
        for n, seg_id in enumerate(ids):
            is_last = n == len(ids) - 1
            entries = self._read_hint(seg_id) if (self.hints and not is_last) else None   # Milestone 6
            if entries is None:
                path = self._seg_path(seg_id)
                with open(path, "rb") as f:
                    data = f.read()
                entries, good_end = scan_segment(data)
                if good_end < len(data):
                    if not is_last:
                        raise CorruptionError("sealed segment %d is damaged at byte %d" % (seg_id, good_end))
                    with open(path, "r+b") as f:          # torn tail of the active segment:
                        f.truncate(good_end)              # cut it off, then make that durable
                        f.flush()
                        os.fsync(f.fileno())
            for key, offset, size, is_tombstone in entries:
                if is_tombstone:
                    self.index.pop(key, None)             # a newer tombstone hides older values
                else:
                    self.index[key] = (seg_id, offset, size)

Stretch goals

  • Compact only some segments. Merge just the oldest few sealed segments. You now have to keep the tombstones that might still hide values in segments you did not include. Work out the precise rule for when a tombstone may be dropped. (This is how real Bitcask-style stores bound the work per compaction.)
  • Compact in the background. Run compact in a thread while another thread keeps calling put and get. What needs a lock, and what is safe because sealed segments never change? Be careful about the moment you swap index entries.
  • fsync policy. Add sync="batch" (group commit): one fsync for every N appends or on flush(). The Systems crash-safe log lab shows the trade-off; apply it here and decide when a put may be acknowledged.
  • Verify on every read. get already checks the CRC. Add a verify() method that scans every segment and reports (without changing anything) which records are damaged. Run it after flipping a byte in a sealed segment.
  • A snapshot of the index. Instead of hint files, periodically write the whole index to disk along with the (segment, offset) it is current up to, and replay only the log written since. Compare startup times.
  • Timestamps and merge-by-time. Bitcask records carry a timestamp so that compaction can merge files in any order. Add one to the record format (what changes in the CRC? in recovery?).
  • Range scans. Try to add scan(lo, hi). Notice that a hash index cannot do it without sorting every key first. That is the wall chapter 5 climbs over, and Lab 2 builds the next store.

Distributed systems connection

You have built, on one machine, three things that distributed systems rely on constantly. First, an append-only log as the source of truth with a derived, rebuildable index. Replicated databases ship their logs to followers, which replay them to rebuild identical state (chapter 15), and the idea of a cache that is "thrown away and recomputed from the log" is the same one behind change data capture and event streams (chapter 19). Second, tombstones. A delete that must be recorded because someone, somewhere, may still hold the old value: with replicas, a tombstone has to outlive the slowest replica that has not heard about the delete yet, or the key comes back. Third, compaction by key: keeping only the latest record per key is exactly what Kafka calls log compaction, and it turns an event log into a snapshot of current state. The safe-swap discipline (write new, sync, rename, delete old in the right order) is also how any system replaces files that others may read at any moment.

What you learned

  • A record needs a length and a checksum: the length tells you where it ends, the CRC tells you it is whole. Never trust a length you have not checked against the bytes you actually have.
  • An append-only log plus an in-memory index of (segment, offset, size) gives one-seek reads and sequential writes. The cost is that every live key must fit in RAM.
  • A delete is a write: a tombstone record. The index is a cache; the log is the truth, so deletes must be in the log.
  • Segments make the log cleanable: sealed segments never change, so they can be read freely and replaced wholesale.
  • Recovery replays the log oldest to newest. A bad record at the end of the last segment is a torn write and is truncated away; damage in a sealed segment is real corruption and is reported.
  • Compaction keeps only records the index points at. Swap files safely: write temp, fsync, rename, fsync the directory, and delete old files oldest first so a tombstone never vanishes before the value it hides.
  • Hint files are a validated cache of a cache: use them if they check out, scan if they do not.

Check your understanding

Your store deletes a key by removing it from the in-memory index only, without writing a tombstone. It works fine until the process restarts. What happens, and why?

  1. Nothing: the index is rebuilt from the data files, which no longer contain the key
  2. The key comes back, because rebuilding the index replays the old put record, which is still in the log
  3. The store refuses to start, because the index and log disagree
  4. All keys written before the delete are lost
The log is the truth and the index is a cache derived from it. The old record is still in a segment, and nothing in the log says it was superseded, so replay restores it. A tombstone is the log's way of recording "this key is deleted from here on".

During compaction, the merged file has been renamed into place, and the process dies before any old segment is deleted. The next start finds both the merged file and all the old segments. Why does it still return correct data?

  1. Because opening the store deletes every file older than the newest
  2. Because the index is saved to disk before compaction
  3. Because duplicate keys are rejected
  4. Because the merged file has a higher segment id than every input it replaces, so in a replay oldest to newest its records are applied last and win; the old segments only repeat what it already says
Segment ids define the replay order. The merged file sorts after all of its inputs and before the new active segment, so it overrides them. That is why the output id is chosen above the inputs, and why old files must be deleted oldest first: a tombstone must never disappear while an older value it hides remains.

On startup the store finds a record with a bad checksum at the very end of the last segment, and a different one in the middle of a sealed segment. What should it do in each case?

  1. Truncate the torn tail of the last segment (a crash artifact, never acknowledged); report corruption for the sealed segment (it was complete, so a bad record means damaged storage)
  2. Truncate both at the bad record
  3. Ignore both and keep going
  4. Delete the whole store and start again
An append that was interrupted can only leave damage at the end of the segment being written. A sealed segment was finished and synced, so damage inside it is not explained by a crash; silently truncating would throw away good data after it. A careful engine reports it and, if the data is replicated, repairs it from another copy.

Why does this design (and Bitcask itself) suit "100 million video-view counters, each updated constantly" better than "10 billion different small keys, each written once"?

  1. Because hash tables cannot store more than 100 million entries
  2. Because sequential writes are slow for many distinct keys
  3. The index needs RAM for every live key, however large the values, so the key count is the limit; and constant overwrites make compaction effective because most of the log is garbage
  4. Because compaction cannot work on keys that were written once
RAM use grows with the number of keys, not with the data size. A hundred million counters is a few GB of index, which fits; ten billion keys does not fit on one machine. And a workload that rewrites the same keys generates lots of dead records for compaction to reclaim.

Lab 6: The Outbox & Change Data Capture

An order is placed. The database knows. The cache that serves the dashboard and the search index that powers the search box also need to know, and they are separate systems that no database transaction can reach. In this lab you will watch the obvious code lose that race, then fix it the way production systems do: an outbox row written in the same transaction as the order, a relay that publishes it, and consumers that tolerate being told twice. At the end a brand-new consumer rebuilds its whole state from nothing but the log.

Why this lab matters

Chapter 19 called it the dual-write problem, and chapter 14 showed what stale caches cost. Almost every system that has a database and a cache, a search index, an analytics pipeline or another service ends up with this bug, and it hides well: nothing fails in tests, and in production it appears as one order in ten thousand that never shows up in search. The outbox pattern is the standard cure, and writing a relay and an idempotent consumer yourself is the quickest way to understand "at-least-once delivery plus idempotence equals effectively once".

Crashes without killing anything

The system of record is a SQLite file in a temporary folder. The cache and the search index are plain Python dicts inside objects: stand-ins for Redis and Elasticsearch, which really are separate systems and survive when your application dies. A crash is simulated: your functions call a crash("some_point") hook, and the check supplies a hook that raises an exception at the point it wants to test, then throws away the database connection (an open transaction is rolled back, as it would be when a process dies) and reopens the file. It is deterministic, takes about a second, and uses nothing but the standard library. Python 3.8 or newer.

What you'll build

Five milestones, each building on the last:

  1. The dual-write bug: write diagnose(), then watch seven crashes leave the cache, the index and the database disagreeing.
  2. Transactional outbox: place_order() inserts the order and its event in one transaction.
  3. The relay: publish outbox rows in order, and discover at-least-once delivery by crashing it.
  4. Idempotent consumers: duplicates and reordering must not corrupt the cache or the index.
  5. Catch-up: a brand-new consumer replays the log from offset 0 and ends up equal to the database.

The data

An order has a customer, an item, a total, a status that moves from placed to paid, shipped and so on, and a version that goes up by one on every change. Remember the version. Milestone 4 depends on it. The cache keeps a dict order_id -> order state; the search index keeps the same dict plus an inverted index word -> set of order ids over the item, the customer and the status, so that search("paid") finds paid orders. Both need to end up exactly equal to what the orders table says.

Milestone 1: the dual-write bug

This is the code everyone writes first. It is already in starter.py as place_order_dual_write:

Swapping the order does not help. If you write the cache first and the database second, a crash in between leaves the cache holding an order that does not exist (a phantom). The given function can do either: pass cache_first=True. The same bug exists for updates (update_status_dual_write), where it leaves stale entries instead of missing ones, which is the stale-cache problem of chapter 14 arriving by a new route.

Hints try without first
  • db_snapshot(conn) (given) returns {order_id: state_dict} for every row in the database. cache.entries and index.docs are dicts of the same shape.
  • Set arithmetic is all you need: missing is db - held, extra is held - db, and stale is the ids in both whose dicts are unequal.
  • Return sorted lists, not sets, so the output is stable and comparable.
  • You can write it once as a loop over ("cache", cache.entries), ("index", index.docs).
Solution spoiler 
def diagnose(conn, cache, index):
    truth = db_snapshot(conn)
    report = {}
    for name, held in (("cache", cache.entries), ("index", index.docs)):
        report[name + "_missing"] = sorted(i for i in truth if i not in held)
        report[name + "_extra"] = sorted(i for i in held if i not in truth)
        report[name + "_stale"] = sorted(i for i in truth if i in held and held[i] != truth[i])
    return report

Milestone 2: the transactional outbox

If the database is the only system that can make a change atomic, then make the database hold everything that must happen. Add an outbox table next to orders. When an order changes, insert a row into outbox describing the change in the same transaction (atomicity). Now there are only two possible worlds: the order and its event both exist, or neither does. There is no instant in which the order has been committed but nobody has been told, because "told" is now a durable row that can be delivered later, however many crashes it takes.

Each outbox row records the event type, the aggregate_id (which order it concerns) and a payload. This lab puts the complete new state of the order, with its version, in the payload (sometimes called event-carried state transfer). That is a deliberate choice, and milestone 4 shows why it pays: an event that carries full state can simply be applied, in whatever order it arrives, if you know which version is newer.

Your task

Implement _emit (insert one outbox row), place_order (insert the order, status placed, version 1, plus an OrderPlaced event) and update_status (change the status, bump the version, and emit an OrderStatusChanged event with the new state). Wrap each in with transaction(conn): and keep the crash(...) calls where the docstrings say.

Before the commit the counts must be (orders, outbox) = (0, 0), after it (1, 1), and never (1, 0). Hints try without first

  • json.dumps(order, sort_keys=True) gives a stable payload. The order dict has the keys id, customer, item, total_cents, status, version; order_state(row) builds it from a database row.
  • For update_status, UPDATE ... SET status = ?, version = version + 1 and then SELECT the row to put the new state into the event.

def _emit(conn, event_type, order):
    conn.execute("INSERT INTO outbox (aggregate_id, type, payload, created_at) VALUES (?, ?, ?, ?)",
                 (order["id"], event_type, json.dumps(order, sort_keys=True), time.time()))

def place_order(conn, order_id, customer, item, total_cents, crash=no_crash):
    order = {"id": order_id, "customer": customer, "item": item,
             "total_cents": total_cents, "status": "placed", "version": 1}
    with transaction(conn):
        conn.execute("INSERT INTO orders (id, customer, item, total_cents, status, version) "
                     "VALUES (?, ?, ?, ?, ?, ?)",
                     (order_id, customer, item, total_cents, "placed", 1))
        crash("after_order_insert")
        _emit(conn, "OrderPlaced", order)
        crash("before_commit")
    crash("after_commit")

def update_status(conn, order_id, status, crash=no_crash):
    with transaction(conn):
        conn.execute("UPDATE orders SET status = ?, version = version + 1 WHERE id = ?", (status, order_id))
        crash("after_order_update")
        row = conn.execute("SELECT * FROM orders WHERE id = ?", (order_id,)).fetchone()
        _emit(conn, "OrderStatusChanged", order_state(row))
        crash("before_commit")
    crash("after_commit")

Milestone 3: the relay, and at-least-once

A separate process, the relay, reads outbox rows that have not been published, in id order, sends them to the log (here a Python list; in real life Kafka, a queue or a topic), and marks them published. It can crash, restart, or run twice. The question is what order to do the last two steps in, because they are two different systems again (the log and the database), and you have just learned that you cannot make two systems atomic.

This is the same trade-off as the sender in networking chapter 16 that cannot tell whether a lost acknowledgement means a lost request: the only safe policy is to retry, and the price of retrying is that the receiver may see the message twice.

Your task

Implement relay_once(conn, log): select the rows with published = 0 ordered by id; for each, append an event {"id", "aggregate_id", "type", "payload"} (payload decoded from JSON into a dict) to log, call crash("after_publish"), then mark that row published, then call crash("after_mark"). Return how many events you published.

Hints try without first
  • SELECT * FROM outbox WHERE published = 0 ORDER BY id, then .fetchall() so the cursor is not held open while you update the table.
  • Mark each row immediately after publishing it, in its own small transaction, not all at the end. That keeps the window for duplicates to one event instead of the whole batch (a valid design, but a wider window).
  • Because row_factory = sqlite3.Row is set, row["payload"] works; pass it through json.loads.
  • If the check says an event was lost, you marked before you published.
Solution spoiler 
def relay_once(conn, log, crash=no_crash):
    rows = conn.execute("SELECT * FROM outbox WHERE published = 0 ORDER BY id").fetchall()
    for row in rows:
        log.append({"id": row["id"], "aggregate_id": row["aggregate_id"],
                    "type": row["type"], "payload": json.loads(row["payload"])})
        crash("after_publish")                  # a crash HERE means the row is published but not marked
        with transaction(conn):
            conn.execute("UPDATE outbox SET published = 1 WHERE id = ?", (row["id"],))
        crash("after_mark")
    return len(rows)

Milestone 4: idempotent consumers

The log can now repeat itself, and it may be read twice by a consumer that crashed before saving its offset, or replayed on purpose. An idempotent operation is one where doing it twice has the same effect as doing it once. Adding a number to a balance is not idempotent; setting a value is. The consumers must be built so that handling an event again changes nothing. There are two classic tools:

  • Remember the ids of processed events. If the id has been seen, skip it. Simple, but the set of ids grows, and (here is the catch) it cannot cope with reordering. If an old event arrives after a newer one, its id is new, so it gets applied and the state goes backwards.
  • Use a version number and an upsert. Every event carries the entity's version. Apply it only if its version is higher than what you hold. A duplicate has the same version (not higher: skip), an old event has a lower version (skip), and a late-arriving newer event is simply applied. No memory of ids is needed. This is why milestone 2 put the version in the payload.

Events that carry the full state make this work smoothly. If they only said "status changed to shipped", dropping or reordering one would be unrecoverable. The cost is bigger events, and the technique only fits when you can name a version per entity. (Real systems use per-key offsets or sequence numbers from the log, or the row's version column, for the same job.)

For the search index there is an extra subtlety. When an order moves from placed to paid, the document must leave the posting list of the word placed and join paid. The given SearchIndex.put already does that, so handle only has to decide whether to call it.

Solution spoiler 
def handle(self, event):
    order = event["payload"]
    have = self.entries.get(order["id"])
    if have is not None and have["version"] >= order["version"]:
        return                              # a duplicate or an older event: ignore it
    self.put(order)

def handle(self, event):
    order = event["payload"]
    have = self.docs.get(order["id"])
    if have is not None and have["version"] >= order["version"]:
        return
    self.put(order)

Together with the given upserts, which keep the inverted index consistent:

def put(self, order):
    old = self.docs.get(order["id"])
    if old is not None:
        for t in tokens(old):
            self.inverted[t].discard(order["id"])
    self.docs[order["id"]] = dict(order)
    for t in tokens(order):
        self.inverted.setdefault(t, set()).add(order["id"])

Milestone 5: catch-up and rebuild

A log is not just a pipe, it is a history. Every consumer keeps its own offset: the position of the next event it has not handled. A consumer that is up to date reads only what is new. A consumer that crashed resumes from its saved offset. A consumer that has never run starts at offset 0 and replays everything, ending in exactly the state the others hold. This is how you add a second search index, or a new analytics table, or repair a corrupted cache: throw the state away and replay. It is the same idea as a new database replica catching up from a leader's log (chapter 15), and it only works because milestone 4 made handling events safe to repeat.

There is a subtle ordering rule hiding in poll: advance the offset after handling the event. If you advance it first and crash, the event is skipped forever (at-most-once). Handled-then-crash means one redelivery, which the idempotent consumer shrugs off. It is the relay's lesson again, one stage later.

Your task

Implement Consumer.poll(log, crash) (handle every event from self.offset to the end, calling crash("handled") after each handle and before incrementing the offset; return the number handled) and rebuild(log, consumer_cls) (create a new consumer, poll it, return it).

python3 check.py shows milestone 5 as ✔. The check replays a 37-event log into brand-new consumers and compares them with the database. It adds three more events and requires that an up-to-date consumer's poll handles exactly those three. It crashes a consumer on its fifth event (after handling, before saving the offset), restarts it, and requires the final state to be right and the offset to have been 4 at the crash. It also replays a log in which every event appears twice, and checks that two consumers keep independent offsets.

Hints try without first
  • A while self.offset < len(log): loop is the simplest shape. Re-read len(log) each time round; it is a list that may grow.
  • The order inside the loop is: handle, then crash("handled"), then self.offset += 1.
  • If the check says crash('handled') was never called, you did not call the hook between handling and the increment.
Solution spoiler 
def poll(self, log, crash=no_crash):
    n = 0
    while self.offset < len(log):
        self.handle(log[self.offset])
        crash("handled")                    # a crash HERE: handled, but the offset was not saved
        self.offset += 1
        n += 1
    return n

def rebuild(log, consumer_cls):
    consumer = consumer_cls()
    consumer.poll(log)
    return consumer

Real CDC versus polling an outbox

Your relay polls: it asks a table "anything new?" The big alternative, change data capture, reads the database's own write-ahead log instead (chapter 13), and the best-known tool is Debezium. For PostgreSQL it uses logical decoding through a replication slot; for MySQL it reads the binlog. It acts like a replica, decodes each committed row change into an event, and publishes it to Kafka. The two approaches combine and compete:

Poll an outbox table (this lab)Read the WAL / binlog (Debezium-style)
What the application must doWrite the outbox row itself, in the same transactionNothing: every committed change is captured, whoever made it, even a manual SQL fix
What an event looks likeExactly what you choose: a domain event such as OrderPlacedA row-level change in a table's schema (before/after values). Consumers become coupled to your table layout unless you reshape the events
Load and latencyRepeated queries against the database; latency is the polling intervalNo extra queries; the log is already being written. Events follow the commit closely
OrderingYou need an id or sequence. On a database with concurrent writers, ids are assigned at insert but become visible at commit, so a reader that tracks "the highest id I saw" can skip a row that commits late. (This lab selects published = 0 instead; SQLite also has a single writer at a time.)The log is in commit order by construction
Starting a new consumerReplay the log you kept, as in milestone 5An initial snapshot of the current rows, then the stream from the position where the snapshot was taken
Operational costAn extra table to clean up and indexDatabase settings (for example logical-level WAL in Postgres), and a replication slot makes the database keep log segments until the connector reads them, so a stalled connector can fill a disk

They are often used together: the application writes outbox rows, and a CDC connector reads the outbox table's changes from the WAL instead of polling, which gives the domain-event shape of the outbox and the efficiency and ordering of the log. Either way the consumer side is identical to what you built: at-least-once delivery, and idempotent handlers.

Try it yourself: four experiments

  1. Swap the relay's two steps. Mark first, publish second. Milestone 3 now reports a lost event. This is the at-most-once failure, and it is the one nobody can repair after the fact.
  2. Split the transaction. In place_order, commit after the order insert and start a second transaction for the outbox row. The check's "after_order_insert" point finds an order with no event: you have rebuilt the dual-write bug inside one database.

Distributed systems connection

A relay and a consumer are two machines that can crash independently, with a network between them that can lose or repeat messages. That is the setting of networking chapter 16, and the lab is a worked answer to its conclusion: you cannot get exactly-once delivery between machines, but you can get effectively once by combining at-least-once delivery with an idempotent receiver. The same pattern appears in replication (a follower re-applying log entries it already has), in retried payment requests with idempotency keys, and in Kafka consumers committing offsets. The outbox is the local half of a bigger idea: let one system be the authority and turn its changes into a durable log, and every other system is just a function of that log.

What you learned

  • Writing to a database and then to a cache or an index is a dual write. There is no atomicity across them, and a crash between the steps leaves them disagreeing, silently, in a different way at each crash point.
  • Swapping the order of the writes moves the bug (missing entries become phantoms); it never removes it.
  • The transactional outbox makes "the change" and "the record that the change must be announced" one atomic local transaction. Everything after that can be retried.
  • A relay that publishes before it marks gives at-least-once delivery: no loss, occasional duplicates. Marking first would give at-most-once, which loses events.
  • Idempotent consumers make duplicates harmless. Event ids alone do not survive reordering; a version number per entity, with "apply only if newer", survives both. Full-state events make this simple.
  • A log with per-consumer offsets lets a brand-new consumer rebuild its state from offset 0, and lets a crashed one resume. Advance the offset after handling.
  • Real CDC reads the database's own WAL or binlog instead of polling a table. It trades the application's control over event shape for completeness, ordering and lower load.

Check your understanding

An order is committed in the database, and the process crashes before it updates the cache. Which statement is true?

  1. The database transaction is rolled back when the process dies, so everything is consistent
  2. The commit had already completed, so the database has the order and the cache does not; the database cannot know it should have told the cache
  3. The cache will notice and fetch the order itself
  4. Writing to the cache first, then the database, would have prevented the problem
The database transaction had ended successfully at the commit. The cache is a different system and was never part of it. Reversing the order just changes the failure into a phantom cache entry for an order that does not exist.

Why must the order row and the outbox row be inserted in the same database transaction?

  1. So that they are written faster
  2. So that the relay can read them in one query
  3. So that the outbox row can be deleted after publishing
  4. So that either both exist or neither does: there is never an order that no one will be told about, nor an announcement of an order that does not exist
The outbox pattern only moves the problem into a place where atomicity is available. Two transactions would reintroduce a crash window between them.

The relay appends event 3 to the log, then crashes before marking it published. What happens after restart, and what must the consumers be able to do?

  1. Event 3 is published again, so consumers receive it twice and must handle duplicates harmlessly
  2. Event 3 is lost, so consumers must ask the database for it
  3. Event 3 is delivered exactly once, because the row is still in the outbox
  4. The relay refuses to restart until a person marks the row
The row is still marked unpublished, so the restarted relay publishes it again. That is at-least-once delivery. Exactly-once is built out of it by making the receiver idempotent.

A consumer remembers the ids of the events it has processed and skips repeats. Events for one order arrive as version 2, then version 1. What does the cache end up holding, and why does a version check fix it?

  1. Version 2, because the id check also sorts events
  2. Nothing, because both events are rejected as out of order
  3. Version 1, because both ids are new so both are applied in arrival order; comparing versions would ignore the older event
  4. Version 2, because the database overrides the cache
Event ids detect repeats, not staleness. Version 1's id has never been seen, so it overwrites version 2. With a version number, "apply only if newer" makes the result independent of arrival order.

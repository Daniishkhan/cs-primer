Lab 3: A B-Tree

Every CREATE INDEX you have ever typed built one of these. In this lab you will write a B+ tree from scratch: search it, grow it with page splits, scan ranges along its linked leaves, and prove with a checker that it stays balanced after thousands of random inserts. Every node counts as a page, so you can watch for yourself why a lookup among a hundred thousand keys touches only three or four of them.

Why this lab matters

Chapter 6 told you that a B-tree is a wide, shallow tree of fixed-size pages, that a full page splits in two, and that the unit of cost is the page, not the key comparison. Chapter 7 said that an index is one of these trees pointing back at your rows. Here you build the thing and count the pages. Afterwards, "an insert might split a page, which might split its parent" stops being a sentence and becomes six lines of code you wrote, and the reason a crash in the middle of a split needs a write-ahead log becomes obvious.

What "page" means here

Nothing in this lab touches a disk. Each Node is a Python object that stands for one page, and every time your code looks at a node it calls self._read(node), which adds one to a counter, pages_read. That counter is your stand-in for "pages fetched from storage". It is the same accounting the B+ tree playground in chapter 6 shows as "pages touched". Python 3.8 or newer, standard library only, and it runs on any operating system. All randomness in the checks is seeded.

What you'll build

Six milestones, each building on the last (the sixth is optional):

  1. Search: the node layout, a walk from the root to a leaf, and a counter for the pages touched.
  2. Insert with leaf splits: add a key to its leaf; when the leaf overflows, cut it in two and tell the parent.
  3. Internal splits and root growth: a parent can overflow too. When the root splits, the tree gets one level taller.
  4. Range scans: descend once, then walk the linked leaves sideways.
  5. An invariants checker: write validate(tree), then let check.py hammer your tree with thousands of seeded inserts and compare every answer with a plain Python dict.
  6. (Optional) Measure: build trees of 100,000 keys with different fan-outs and print their height and pages per lookup, to see logfanout(n) with your own eyes.

The rules of this tree

The starter's header comment states them; read them once now, because every milestone depends on them:

  • A leaf holds keys and parallel values, sorted, and a next link to the leaf on its right. An internal node holds separator keys and children, with exactly one more child than keys.
  • For an internal node with keys [k0, k1, ...], everything under children[0] is less than k0, everything under children[1] is at least k0 and less than k1, and so on. A key equal to a separator goes right.
  • max_keys is the most keys a node may hold (real pages are full when their bytes run out; here it is a count, as in the chapter's playground). A node that reaches max_keys + 1 keys is split. As a result every non-root node holds between max_keys // 2 and max_keys keys.
  • tree.height is the number of levels. A lone leaf has height 1.

Milestone 1: search, and counting pages

You met the algorithm in chapter 6: read the root, binary-search its separators to pick a child, read that child, and repeat until you reach a leaf; then binary-search the leaf. Comparing keys inside a page is cheap, because the page is already in memory. Fetching a page is the expensive part. So the thing to measure is how many nodes you step onto, and that is exactly one per level.

Python's bisect module does the in-page binary search. Which variant you use matters, because of the rule about equal keys:

  • bisect.bisect_right(node.keys, key) in an internal node returns the index of the child to follow. For a key equal to a separator it returns the index after that separator, which is the right-hand child. That is the rule.
  • bisect.bisect_left(leaf.keys, key) in a leaf returns where the key is, or would be inserted. Then you check whether the key is really there.

Your task

Implement BPlusTree.find_leaf(key) and BPlusTree.search(key). find_leaf returns (leaf, path), where path is the list of (internal_node, child_index) pairs you went through, root first. Insert will need that list to find parents. Call self._read(...) on every node you step onto, including the root and the leaf.

Solution spoiler 
def find_leaf(self, key):
    node = self._read(self.root)
    path = []
    while not node.leaf:
        i = bisect.bisect_right(node.keys, key)   # equal keys go right
        path.append((node, i))
        node = self._read(node.children[i])
    return node, path

def search(self, key):
    leaf, _ = self.find_leaf(key)
    i = bisect.bisect_left(leaf.keys, key)
    if i < len(leaf.keys) and leaf.keys[i] == key:
        return leaf.values[i]
    return None

Milestone 2: insert, and the leaf split

To insert, descend with find_leaf, put the key into the sorted leaf (list.insert at the bisect_left position, for both keys and values), and you are done, unless the leaf now holds max_keys + 1 keys. A page cannot hold more than its capacity, so the leaf is split:

  1. Create a new leaf and move the upper half of the keys and values into it.
  2. Splice it into the chain: the new leaf's next is the old leaf's next; the old leaf's next is the new leaf.
  3. Take the first key of the new leaf as the separator and hand it to the parent, together with the new page. This key is copied up. It also stays in the leaf, because a leaf must keep every key (the values live there).

Where to cut? The simplest rule is mid = len(leaf.keys) // 2: the left page keeps keys[:mid], the new right page takes keys[mid:]. With max_keys + 1 keys that leaves both halves with at least max_keys // 2 keys, which is exactly the minimum fill the checker will demand.

This milestone only handles the case where the parent has room. What to do when the leaf was the root, or the parent overflows too, is milestone 3. The check for this milestone therefore builds a root with three full leaves by hand and inserts into those.

Your task

Implement insert, _split_leaf, and the first part of _insert_in_parent: pop the parent from path, and insert the separator and the new child at the right positions (parent.keys.insert(i, separator) and parent.children.insert(i + 1, right), where i is the index you descended through). Inserting an existing key must replace its value rather than add a duplicate.

Solution spoiler 
def insert(self, key, value):
    leaf, path = self.find_leaf(key)
    i = bisect.bisect_left(leaf.keys, key)
    if i < len(leaf.keys) and leaf.keys[i] == key:
        leaf.values[i] = value
        return
    leaf.keys.insert(i, key)
    leaf.values.insert(i, value)
    if len(leaf.keys) > self.max_keys:
        separator, right = self._split_leaf(leaf)
        self._insert_in_parent(path, leaf, separator, right)

def _split_leaf(self, leaf):
    mid = len(leaf.keys) // 2
    right = Node(leaf=True)
    right.keys = leaf.keys[mid:]
    right.values = leaf.values[mid:]
    leaf.keys = leaf.keys[:mid]
    leaf.values = leaf.values[:mid]
    right.next = leaf.next                    # splice the new page into the chain
    leaf.next = right
    return right.keys[0], right

# in _insert_in_parent, the "parent has room" part:
parent, i = path.pop()

parent.children.insert(i + 1, right)

Milestone 3: internal splits, and a taller tree

An internal page has a capacity too. After a leaf split adds a separator and a child to the parent, the parent may hold max_keys + 1 keys. It is split in the same spirit, with one important difference in how the middle key is treated:

  • In a leaf split the separator is copied up. The key stays in the right leaf, because leaves hold all the data.
  • In an internal split the middle key is moved up. It goes to the grandparent and appears in neither half. (Internal keys are signposts, not data. Keeping a copy in the page below would waste a slot and break the arithmetic of len(children) == len(keys) + 1.)

The root is special. It has no parent to receive a separator, so when it splits, a new root is created above the two halves, with a single separator and two children. That is the only moment the tree gets taller, and it happens at the top: every leaf ends up exactly one level deeper at once, which is why all leaves are always at the same depth. The code is a single function, _insert_in_parent, that calls itself one level up after a split, and the "no parent" case is simply an empty path.

Your task

Finish _insert_in_parent: (1) if path is empty, create a new internal root and do self.height += 1; (2) after inserting into the parent, if it holds more than max_keys keys, split it (move the middle key up) and recurse with the rest of path.

Hints try without first
  • An over-full internal node has max_keys + 1 keys, so mid = len(parent.keys) // 2 is the index of the key that moves up: up = parent.keys[mid].
  • The new sibling gets keys[mid + 1:] and children[mid + 1:]. The old node keeps keys[:mid] and children[:mid + 1]. Count: mid keys and mid + 1 children on the left. Good.
  • Then self._insert_in_parent(path, parent, up, sibling): "parent split into parent and sibling, with up between them". The recursion handles both the grandparent case and the new-root case.
  • The new root: root.keys = [separator], root.children = [left, right], self.root = root.
Solution spoiler 
def _insert_in_parent(self, path, left, separator, right):
    if not path:                              # `left` was the root: the tree grows
        root = Node(leaf=False)
        root.keys = [separator]
        root.children = [left, right]
        self.root = root
        self.height += 1
        return
    parent, i = path.pop()                    # i = position of `left` among parent's children
    parent.keys.insert(i, separator)
    parent.children.insert(i + 1, right)
    if len(parent.keys) > self.max_keys:      # Milestone 3: the parent is over-full too
        mid = (len(parent.keys)) // 2
        up = parent.keys[mid]                 # this key MOVES up; it is not kept below
        sibling = Node(leaf=False)
        sibling.keys = parent.keys[mid + 1:]
        sibling.children = parent.children[mid + 1:]
        parent.keys = parent.keys[:mid]
        parent.children = parent.children[:mid + 1]
        self._insert_in_parent(path, parent, up, sibling)

Milestone 4: range scans along the leaves

This is the feature that makes a B+ tree better than a hash index. WHERE created_at BETWEEN a AND b and ORDER BY both want sorted, adjacent keys. Because the leaves are linked in key order, a range scan costs one descent to find the first key, and then one page per further leaf:

Your task

Implement range_scan(lo, hi), returning a list of (key, value) pairs with lo <= key <= hi (both ends inclusive, like SQL's BETWEEN) in key order. None for lo or hi means unbounded. Count every leaf you move to with self._read.

python3 check.py shows milestone 4 as ✔. The check also counts pages: a range of 1,000 keys must cost a few hundred page reads (one per leaf), not thousands. You will see "range_scan touched N pages; 1000 separate searches would touch M" in its output.

Hints try without first
  • For a bounded lo, find_leaf(lo) gives the starting leaf. For lo=None, walk down children[0] from the root (reading each page).
  • The starting leaf can hold keys smaller than lo (lo may even be absent). Skip them with continue.
  • Inside a leaf, stop the whole scan (return) the moment you see a key greater than hi. Otherwise move to leaf.next and self._read it.
  • An empty range (lo > hi, or beyond the last key) simply returns [].
Solution spoiler 
def range_scan(self, lo, hi):
    if lo is None:
        node = self._read(self.root)
        while not node.leaf:
            node = self._read(node.children[0])
        leaf = node
    else:
        leaf, _ = self.find_leaf(lo)
    out = []
    while leaf is not None:
        for k, v in zip(leaf.keys, leaf.values):
            if lo is not None and k < lo:
                continue
            if hi is not None and k > hi:
                return out
            out.append((k, v))
        leaf = leaf.next
        if leaf is not None:
            self._read(leaf)
    return out

Milestone 5: prove it stays a B+ tree

Tree code is famously easy to get almost right: it passes the small cases and quietly corrupts itself on the five-thousandth insert. The cure used by people who write database engines is a function that walks the entire structure and checks every rule, called after tests (and in debug builds, sometimes after every operation). You will write it. The rules:

InvariantWhat breaks it
Keys sorted within every node (strictly increasing)inserting at the wrong position; a bad split
Parent separators correct: every key in the child reached through slot i is ≥ keys[i-1] and < keys[i]forgetting to update the parent after a split; copying instead of moving (or the reverse)
Fill within bounds: at most max_keys keys; non-root nodes at least max_keys // 2; an internal root at least 1; internal nodes have len(keys) + 1 childrensplitting too late or too lopsidedly; losing a key in a split
All leaves at the same depth (and that depth is tree.height)growing the tree anywhere but at the root
The leaf chain visits the leaves in tree order and ends in Noneforgetting to splice a new leaf into the chain

The recursion that makes this easy: walk down passing the allowed range [lo, hi) for the current node. The root may hold anything (None, None). The child in slot i gets lo = node.keys[i-1] (or the parent's own lo for slot 0) and hi = node.keys[i] (or the parent's hi for the last slot). Every key you meet must lie inside its node's range, and that single check verifies all separators at all levels. Collect the leaves in order while you walk, then check their depths and the next links.

Your task

Implement validate(tree). It returns a list of strings, one for each broken rule it finds, and an empty list for a healthy tree. Then run the check, which does three things:

  1. your validate must return [] for healthy trees;
  2. it must notice six deliberately corrupted trees: two keys swapped in a leaf, an under-full leaf, an over-full leaf, a wrong separator in the root, a skipped leaf in the chain, and leaves at two different depths;
  3. the stress test: five trees (fan-outs 4, 3, 5, 16 and 2) fed with 17,500 seeded inserts in total, in ascending, descending and shuffled order, with repeated keys that must overwrite. Every 500 inserts both your validate and the checker's own run, and at the end every key is searched, 40 random ranges are scanned, and the whole tree is compared with a plain, sorted Python dict.

Hints try without first
  • Write a nested helper walk(node, depth, lo, hi, is_root). Append to a shared problems list instead of raising, so one run reports everything.
  • Use zip(keys, keys[1:]) to compare neighbours: any(a >= b for a, b in ...) is the sortedness test.
  • The fill bounds for a leaf: len(keys) <= max_keys, and if it is not the root, len(keys) >= max_keys // 2. For an internal non-root node use max(1, max_keys // 2) as the minimum.
  • Record each leaf's depth in a set; more than one value means the tree is unbalanced. Keep the leaves in a list and compare a.next is b for neighbours.
  • Do not trust a leaf's position by key values alone. The chain test also catches a leaf that was split but never linked.
Solution spoiler 
def validate(tree):
    problems = []
    m = tree.max_keys
    leaves = []                                    # leaves in left-to-right order
    depths = set()

    def walk(node, depth, lo, hi, is_root):
        n = len(node.keys)
        for a, b in zip(node.keys, node.keys[1:]):
            if a >= b:
                problems.append(f"keys not strictly increasing: {a} before {b}")
                break
        for k in node.keys:                        # parent separators: node covers [lo, hi)
            if (lo is not None and k < lo) or (hi is not None and k >= hi):
                problems.append(f"key {k} lies outside the range [{lo}, {hi}) its parent allows")
        if node.leaf:
            depths.add(depth)
            leaves.append(node)
            if len(node.values) != n:
                problems.append("a leaf has a different number of keys and values")
            if n > m or (not is_root and n < m // 2):
                problems.append(f"leaf holds {n} keys; allowed {0 if is_root else m // 2}..{m}")
            return
        if len(node.children) != n + 1:
            problems.append(f"internal node has {n} keys but {len(node.children)} children")
            return
        if n > m or n < (1 if is_root else max(1, m // 2)):
            problems.append(f"internal node holds {n} keys; allowed {1 if is_root else max(1, m // 2)}..{m}")
        for i, child in enumerate(node.children):
            c_lo = node.keys[i - 1] if i > 0 else lo
            c_hi = node.keys[i] if i < n else hi
            walk(child, depth + 1, c_lo, c_hi, False)

    walk(tree.root, 1, None, None, True)
    if len(depths) > 1:
        problems.append(f"leaves are at different depths: {sorted(depths)}")
    elif depths and depths != {tree.height}:
        problems.append(f"tree.height is {tree.height} but the leaves are at depth {min(depths)}")
    for a, b in zip(leaves, leaves[1:]):           # the linked list must match the tree order
        if a.next is not b:
            problems.append("the leaf chain does not follow the tree order")
            break
    if leaves and leaves[-1].next is not None:
        problems.append("the last leaf's next is not None")
    return problems

Why the checker has its own validator

Milestones 2 to 4 are checked with a validator that lives in check.py, not with yours, so a bug in validate cannot hide a bug in insert (or the other way round). This is a general testing habit: the code that checks an invariant should not share code with the code that is supposed to maintain it.

Milestone 6 (optional): see logfanout(n)

The chapter's arithmetic said that three levels of a tree with a fan-out of a few hundred hold tens of millions of keys. Solution spoiler 
def measure(n, fanouts, seed=1):
    import random
    rng = random.Random(seed)
    keys = list(range(n))
    rng.shuffle(keys)
    probes = rng.sample(keys, 1000)
    rows = []
    for m in fanouts:
        t = BPlusTree(max_keys=m)
        for k in keys:
            t.insert(k, k)
        before = t.pages_read
        for k in probes:
            t.search(k)
        count, stack = 0, [t.root]
        while stack:
            node = stack.pop()
            count += 1
            if not node.leaf:
                stack.extend(node.children)
        rows.append({"max_keys": m, "height": t.height,
                     "pages_per_lookup": (t.pages_read - before) / len(probes), "nodes": count})
    return rows

Read the table. With a fan-out of 4 (tiny pages) the tree is 9 levels deep, and a lookup touches 9 pages. Raise the page capacity to 64 keys and it is 3 levels. The last column is the textbook estimate ceil(logm+1 n) for a perfectly full tree. Real trees are taller than that, because pages are only partly full (next section), but the trend, a logarithm with the fan-out as its base, is exact. And this is why chapter 6 could say that a few hundred keys per page make even billions of keys four levels deep.

    Ascending inserts leave the leaves exactly half full (3,124 leaves); random inserts settle at about 70% (2,230 leaves), the figure chapter 6 uses for its fan-out estimate (about 0.69, or ln 2, is the classic result for random inserts). Half-full pages are why a database that bulk-loads sorted data builds the tree bottom-up and packs the pages instead (stretch goal 2).
  2. CPU work versus page reads. Wrap the key comparisons in find_leaf in a counter. For 100,000 keys the total number of comparisons inside pages comes out near log2(100000) ≈ 17 whatever the fan-out, because binary search inside a page adds up to a binary search overall. What changes with the fan-out is the number of pages. That is chapter 6's point: when each page costs a disk read, the page count is the cost.
  3. Break the equal-key rule. In find_leaf change bisect_right to bisect_left. Milestone 1 fails at once: the key 10 is in the leaf [10, 12, 15] but the search goes to the leaf on its left. Any rule about boundaries ("a separator belongs to the right") must be applied in both search and split, and the invariants checker is what notices when they disagree.
  4. Break the split. Make _split_leaf use mid = len(leaf.keys) - 1 (the new leaf gets one key). Searches still work, but the new leaves are nearly empty and the fill check in milestones 2 and 5 fails with "leaf under-full". The tree would be correct, yet it would waste pages and grow tall, which is why the bounds are part of the invariants.

Stretch goals

  • Delete: remove a key from its leaf. If the leaf drops below max_keys // 2 keys, first try to borrow a key from a sibling (and fix the parent's separator), and if both are at the minimum, merge them and remove the separator from the parent, recursing upward. A root left with one child is dropped, so the tree gets shorter. This is the mirror image of everything above (chapter 6, "Deletes and merges"). Your validate will tell you if you got it wrong; note that some real engines do not merge eagerly at all.
  • Bulk load: given sorted pairs, build the leaves bottom-up, full to a chosen fill factor, then build each internal level from the first keys of the level below. Compare the page count and height with 100,000 ascending single inserts.
  • Pages as bytes: encode each node into a fixed-size 4 KiB bytes object with struct and keep them in a file; replace child pointers with page numbers. Now _read really reads a page.
  • A buffer pool: put an LRU cache in front of _read (chapter 6, "The buffer pool"), then report the hit rate per lookup. With a small cache, the root and the level below stay cached and the counter of misses per lookup drops to about 1.
  • Duplicate keys: allow many values for one key (as a non-unique index must). What changes in find_leaf and in the separator rule?
  • The right-edge optimisation: when an insert lands at the end of the rightmost leaf and it overflows, split unevenly (leave the old leaf full, put one key in the new leaf) so ascending loads pack the pages. You will have to loosen the minimum-fill bound for the rightmost nodes in validate.

Distributed systems connection

Two ideas from this lab reappear in distributed databases. First, a split is not atomic: one insert modified three pages (the old leaf, the new leaf, the parent), and a crash after the first write leaves a tree that points nowhere. That is why B-tree engines pair the tree with a write-ahead log, and the same log is what a leader ships to its followers in replication: the log is the truth, and the tree is a cache of it. Second, range-partitioned stores split by key range. A general pattern, used for example by Bigtable-style systems and by CockroachDB (check each system's docs for the details), is to keep data sorted by key and cut it into ranges; when a range grows past a size threshold it is split in two and the metadata that maps key ranges to machines gets a new entry, exactly as a leaf split adds a separator to its parent. The search "which range holds this key?" is the same descent you wrote, one level of indirection up. And a range scan stays cheap for the same reason it did here: neighbours in key order are neighbours in storage. See Sharding in Practice for the cost of choosing the key wrongly.

What you learned

  • A lookup in a B+ tree reads one page per level, always. The cost is the height, and the height grows like logfanout(n), so a larger page (a larger fan-out) means a shallower tree.
  • A leaf split copies its first right-hand key up; an internal split moves its middle key up. Splits cascade toward the root, and only a root split makes the tree taller, which is why every leaf is always at the same depth.
  • Leaves linked in key order turn a range scan into one descent plus a walk sideways, the thing a hash index cannot do.
  • Ascending inserts leave pages half full; random inserts settle near 70%. Pages are never packed tight by ordinary inserts.
  • One logical insert can modify several pages, which is the reason for the write-ahead log.
  • For data-structure code, write an invariants checker first-class, test with seeded random sequences, and compare against a trivially correct model (a sorted dict). Keep the checker independent of the code it checks.

Check your understanding

A B+ tree has pages that hold up to 100 keys and are roughly 70% full. About how many pages does one lookup touch among 1,000,000 keys?

  1. 1, because the index finds the key directly
  2. 3 or 4, one per level
  3. About 20, the base-2 logarithm of a million
  4. About 10,000, a million divided by the page size
With about 70 keys per page the fan-out is about 70, and log70(1,000,000) is about 3.3, so the tree is 3 or 4 levels deep and a lookup reads one page per level. The 20 of option three is the number of key comparisons in a binary search, which happen inside pages and cost little; the B-tree cuts the number of pages.

A leaf splits and sends a separator to its parent. Later, an internal node splits and sends one up as well. What is the difference in what happens to that key?

  1. There is none: both are copied
  2. The leaf separator is moved and the internal one is copied
  3. The leaf separator is copied (it stays in the new leaf, which holds all the data); the internal separator is moved (it appears in neither half)
  4. Both are deleted and recomputed from the children
Leaves hold every key and its value, so the first key of the new leaf must stay there; the parent receives a copy to route by. Internal keys are only signposts. If the middle key stayed in one of the halves it would add a key without a matching child and break the rule len(children) == len(keys) + 1, so it moves up.

Which event is the only way a B+ tree gets taller, and why does that keep all leaves at the same depth?

  1. The root splits and a new root is created above it; every existing leaf moves down one level at the same time
  2. A leaf splits; the new leaf is attached one level below
  3. An internal node receives a fifth child
  4. The tree is rebuilt whenever the height changes
Leaf and internal splits happen sideways: the new page is a sibling at the same level. Only when the splitting page is the root is there no sibling slot in a parent, so a new root is added on top. Everything below it is pushed down together, so nothing becomes deeper than anything else.

Why is range_scan over 1,000 consecutive keys so much cheaper than 1,000 separate search calls?

  1. Search is implemented badly
  2. Range scans skip the binary search inside pages
  3. Range scans keep the root cached in the tree object
  4. Search descends from the root every time, but the scan descends once and then follows the next links between leaves
A search always costs the full height. A scan pays that once for the first key, and then each further leaf costs one page read, with several keys per page. For 1,000 keys with 8 keys per page the lab's check sees about 180 page reads instead of 5,000. A hash index has no such order to follow.

Lab 4: Make a Slow Query Fast

Most "the database is slow" problems are not about the database. They are a missing index, the wrong column order in an index, a query that hides its column inside a function, or an application that asks the same question four thousand times. In this lab you get a database with 50,000 users, 500,000 orders and a million order lines, and six slow things to fix. For each one you read the query plan, change one thing, and watch the plan (and the clock) agree with you.

Why this lab matters

Chapter 7 explained what an index is and when it helps; chapter 8 showed how to read EXPLAIN and listed the classic traps (N+1, functions on indexed columns, OFFSET pagination). This lab turns the lists into reflexes. The skill that matters in a real job is not remembering the rules but looking at a plan and knowing what it is telling you. After this lab you will read SCAN and SEARCH ... USING COVERING INDEX the way you read a stack trace.

What gets created on your computer

The first time you run anything, dataset.py generates the database (seeded, so everyone gets the same data) and caches it as base.db in a folder named zts-lab04-v1 inside your system's temp directory, not in the lab folder. It takes a few seconds and is about 45 MB. Every check works on its own private copy of that file and deletes the copy afterwards. To remove the cached file run python3 check.py --clean; it is simply rebuilt next time. Python 3.8 or newer, only the standard library's sqlite3 module, on any operating system. The row-value syntax in milestone 5 needs SQLite 3.15 or newer (2016); check.py prints your SQLite version.

What you'll build

Six milestones (the sixth is optional). Each starts from a slow query or function that is given to you:

  1. Lookup by email: a single-column index turns a scan of 50,000 users into a seek.
  2. Recent orders for a user: a composite index (user_id, created_at) finds the rows and delivers them in order, so ORDER BY ... LIMIT 10 needs no sort.
  3. A covering index for a count and a sum, so the table is never touched.
  4. N+1: replace a Python loop that sends one query per user with a single JOIN / GROUP BY.
  5. Pagination: replace OFFSET with keyset ("seek") pagination, including the tie-break.
  6. (Optional) A function on a column: a query wraps an indexed column in date() and the index goes unused. Rewrite the predicate, or index the expression.

Reading a query plan

Before you change anything, learn to read the answer SQLite gives when you ask how it will run a query. EXPLAIN QUERY PLAN does not run the query; it prints the strategy. dataset.explain(con, sql, params) prints it for you. These are the lines you will meet, from worst to best for a selective query:

You seeIt means
SCAN ordersEvery row of the table is visited. Cost grows with the table. Fine for a tiny table, a red flag on 500,000 rows.
SEARCH orders USING INDEX idx (user_id=?)A seek into a B-tree (chapter 6) to the entries with user_id = ?, then a visit to the table for each matching row. The text in parentheses shows which conditions the index handled.
SEARCH ... USING COVERING INDEX idx (...)The same seek, but the index itself holds every column the query needs, so the table is never visited (chapter 7, covering indexes).
USE TEMP B-TREE FOR ORDER BYAn extra sort step: the rows are collected and sorted because no index delivered them in order. Costs time and memory for big result sets.
SCAN orders USING COVERING INDEX idxA scan of the index from end to end. Cheaper than scanning the table (the index is narrower) but still proportional to the table's size.

Try it on the very first query in the lab, with nothing indexed. Save this as try.py in the lab folder (each snippet on this page is a file you can run; open_db() hands you your own copy of the database in the temp folder, deleted at exit):

from dataset import open_db, explain
con = open_db()
Q = "SELECT id, name, country FROM users WHERE email = :email"
email = con.execute("SELECT email FROM users WHERE id = 777").fetchone()[0]
print(email)
explain(con, Q, {"email": email})
con.execute("CREATE INDEX idx_users_email ON users(email)")
explain(con, Q, {"email": email})
$ python3 try.py
gus.yang777@example.com
  QUERY PLAN: SCAN users
  QUERY PLAN: SEARCH users USING INDEX idx_users_email (email=?)

That SCAN users is the bug. The users table occupies about 3.3 MiB, roughly 840 pages of 4 KiB (experiment 4 below shows how to see that), and the scan reads all of them to find one row (chapter 7 did the same arithmetic for 100,000 rows). The second plan, after CREATE INDEX, is a B-tree descent of three or four pages. That is milestone 1.

How check.py judges

  1. The answers must be identical to the original query's, for a handful of probes including edge cases (a missing email, a user with no orders, a product with none). An index never changes results; a rewrite sometimes does, which is exactly what this guards against.
  2. The plan must be the right shape. This is the deciding test, because plans are deterministic: the same SQLite on the same data picks the same plan every time. Typically: no SCAN of the big table, the expected kind of index, no leftover sort step.
  3. It should be faster. The check times the original and yours, takes the best of three runs of each, and prints the ratio. Where the expected gain is enormous (hundreds of times) it also requires at least 5x; where the gain is modest (milestones 3 and 4) it only reports it. Timing on a laptop is noisy; plans are not.

Milestone 1: a lookup by email

The login page asks SELECT id, name, country FROM users WHERE email = :email. Without an index the database must look at every user. An index on email is a B+ tree of (email, rowid) entries kept in sorted order (the structure you can build yourself in Lab 3): the planner seeks to the one entry and follows its rowid to the row. One equality condition on one column, so one single-column index is all it takes.

Your task

Implement m1_index() in starter.py: return a string with one CREATE INDEX statement. The query itself is given and must not change.

python3 check.py shows milestone 1 as ✔. The check prints the plan before and after; the second must start with SEARCH users USING INDEX. If you see SCAN users still, the index does not start with the column in the WHERE clause.

Hints try without first
  • The shape is CREATE INDEX name ON table(column). Any index name works; idx_table_column is the usual style.
  • Would CREATE UNIQUE INDEX also work? Yes (emails are unique here), and it would also enforce uniqueness. Which is the better design for a real login table?
  • Do not add other columns. They would make the index bigger and slower to maintain for no benefit here.
Solution spoiler 
def m1_index():
    return "CREATE INDEX idx_users_email ON users(email)"

Milestone 2: the ten most recent orders of a user

The "My orders" page runs:

SELECT id, total_cents, created_at FROM orders
WHERE user_id = :uid
ORDER BY created_at DESC, id DESC
LIMIT 10

(The id DESC tie-break makes the result deterministic when two orders share a timestamp.) The obvious fix is an index on user_id. Try it, with the three variants in one file, and read the plans:

import time
from dataset import open_db, explain
con = open_db()
Q = """SELECT id, total_cents, created_at FROM orders
       WHERE user_id = :uid ORDER BY created_at DESC, id DESC LIMIT 10"""
def run(label):
    t = time.perf_counter()
    for _ in range(20): con.execute(Q, {"uid": 1}).fetchall()
    print(f"  user 1 (13,485 orders): {(time.perf_counter() - t) / 20 * 1000:.2f} ms per query")
print("no index"); explain(con, Q, {"uid": 1}); run("a")
con.execute("CREATE INDEX idx_orders_user ON orders(user_id)")
print("index on (user_id)"); explain(con, Q, {"uid": 1}); run("b")
con.execute("CREATE INDEX idx_orders_user_created ON orders(user_id, created_at)")
print("index on (user_id, created_at)"); explain(con, Q, {"uid": 1}); run("c")
$ python3 try.py

Look at the middle plan. The index on user_id alone fixed the SCAN (15 ms down to 7 ms), but the plan still has USE TEMP B-TREE FOR ORDER BY: SQLite fetched all 13,485 orders of user 1 and sorted them, just to keep ten. The composite index fixes both problems at once: the plan has no sort step at all and the query takes microseconds. Why?

Hints try without first
  • Two columns this time: the one compared with = first, then the one in ORDER BY.
  • You do not need id in the index. In SQLite every index entry also stores the rowid, and id is the rowid (INTEGER PRIMARY KEY), so the tie-break column is already there.
  • You do not need to write DESC in the index. SQLite can walk an index backwards.
  • If the plan still says TEMP B-TREE, check the column order. (created_at, user_id) is a different, much worse index for this query.
Solution spoiler 
def m2_index():
    return "CREATE INDEX idx_orders_user_created ON orders(user_id, created_at)"

Milestone 3: a covering index

The product page shows "units sold and revenue". Table order_items has a million rows, and the check already created a plain index on product_id for you, so this is the situation after milestone 1 style fixes:

SELECT COUNT(*) AS n, COALESCE(SUM(qty * price_cents), 0) AS revenue

Milestone 4: the N+1 problem

Indexes fix queries. They do not fix a program that sends too many of them. This function builds a report of how much each user in a country has spent on paid orders, and it is the shape of countless ORM-generated bugs (chapter 8, trap 1):

def revenue_by_email_n_plus_one(con, country):
    result = {}
    for uid, email in con.execute("SELECT id, email FROM users WHERE country = ?", (country,)).fetchall():
        (paid,) = con.execute(
            "SELECT COALESCE(SUM(total_cents), 0) FROM orders WHERE user_id = ? AND status = 'paid'",
            (uid,)).fetchone()
        result[email] = paid
    return result

One query for the users, then one more per user: for Germany that is 4,220 statements. For this milestone the check has already created a covering index on orders(user_id, status, total_cents), so each individual query is fast, and yet the function is still slow-ish. Run both versions and count the statements with SQLite's trace hook:

import time
from dataset import open_db
from solution import revenue_by_email_n_plus_one, revenue_by_email
con = open_db()
con.execute("CREATE INDEX idx_orders_user_status_total ON orders(user_id, status, total_cents)")
for fn in (revenue_by_email_n_plus_one, revenue_by_email):
    seen = []
    con.set_trace_callback(seen.append)
    t = time.perf_counter()
    result = fn(con, "DE")
    ms = (time.perf_counter() - t) * 1000
    con.set_trace_callback(None)
    print(f"{fn.__name__:30} {len(seen):>5} statements  {ms:6.1f} ms  ({len(result)} users)")
$ python3 try.py
revenue_by_email_n_plus_one     4220 statements    24.5 ms  (4219 users)
revenue_by_email                   1 statements     6.8 ms  (4219 users)

Here everything happens inside one process, so the penalty is only a few times. In a real application every statement is a network round trip (networking chapter 13 on latency): at an illustrative half a millisecond per trip, those 4,219 extra queries would add over two seconds to every page view, and N+1 gets worse as the data grows, because the number of statements grows with the number of rows. That is why the check judges this milestone by how many statements your function sends, a number that is exactly the same on every machine, and only reports the time.

The set-based version asks the database for everything at once. Each user is joined to their paid orders, and the rows are grouped back per user:

  • Use a LEFT JOIN, so a user with no paid orders still appears (with a total of 0 from COALESCE). An inner JOIN would silently drop them, and the check has a user like that on purpose.
  • The status = 'paid' condition belongs in the ON clause, not in WHERE. In WHERE it would also remove the users who have only unpaid orders (their joined rows fail the test), which turns the left join back into an inner join.

Your task

Implement revenue_by_email(con, country) so it returns the same dict as the given function, using at most two SELECT statements however many users there are.

python3 check.py shows milestone 4 as ✔. It prints "queries sent for one country: N+1 version 4,220, yours 1", shows your plan, and checks the plan does not scan the big orders table: the join must go through the index (SEARCH o USING COVERING INDEX ...).

Hints try without first
  • Sketch the result you want first: one row per user, with two columns, email and total. That is a GROUP BY on the user.
  • GROUP BY u.id (the primary key) is safe even if two users had the same email.
  • The function returns a dict: dict(cursor.fetchall()) turns two-column rows into one.
  • If your plan shows SCAN o or an AUTOMATIC index, the join order or the index is wrong. With the index in place, SQLite scans the (small) filtered users and seeks into orders for each.
Solution spoiler 
def revenue_by_email(con, country):
    rows = con.execute(
        """SELECT u.email, COALESCE(SUM(o.total_cents), 0)
           FROM users AS u
           LEFT JOIN orders AS o ON o.user_id = u.id AND o.status = 'paid'
           WHERE u.country = ?
           GROUP BY u.id""", (country,))
    return dict(rows.fetchall())

Milestone 5: pagination without OFFSET

An admin screen lists orders, newest first, 50 per page:

SELECT id, user_id, total_cents, created_at FROM orders
ORDER BY created_at DESC, id DESC
LIMIT :size OFFSET :offset

Page 1 is fast. Page 5,000 (OFFSET 249950) is not, because OFFSET cannot jump: the database produces every earlier row and throws it away (chapter 8, trap 4). An index on (created_at, id) removes the sort, but not the counting. Measure it:

import time
from dataset import open_db
con = open_db()
con.execute("CREATE INDEX idx_orders_created_id ON orders(created_at, id)")
OFF = """SELECT id, user_id, total_cents, created_at FROM orders
         ORDER BY created_at DESC, id DESC LIMIT 50 OFFSET :off"""
KEY = """SELECT id, user_id, total_cents, created_at FROM orders
         WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 50"""
print(f"{'page':>6} {'OFFSET':>10} {'keyset':>10}")
for page in (1, 10, 100, 1000, 5000):
    off = (page - 1) * 50
    t = time.perf_counter(); con.execute(OFF, {"off": off}).fetchall(); a = time.perf_counter() - t
    if off:
        last = con.execute(OFF.replace("LIMIT 50", "LIMIT 1"), {"off": off - 1}).fetchone()
        p = {"ts": last[3], "id": last[0]}
    else:
        p = {"ts": "9999-12-31 23:59:59", "id": 2**62}
    t = time.perf_counter(); con.execute(KEY, p).fetchall(); b = time.perf_counter() - t
    print(f"{page:>6} {a * 1000:>8.2f}ms {b * 1000:>8.2f}ms")
$ python3 try.py
  page     OFFSET     keyset
     1     0.06ms     0.04ms
    10     0.04ms     0.03ms
   100     0.08ms     0.03ms
  1000     0.76ms     0.03ms
  5000     5.61ms     0.04ms

The OFFSET column grows with the page number (6 ms at page 5,000, even with a good index, and 300 ms without one); the keyset column is flat. The keyset method asks a different question. Instead of "skip 249,950 rows", it asks "give me the 50 rows after this one", where "this one" is the last row of the previous page:

The subtle part is the tie. Timestamps are not unique: the database has orders that share a timestamp down to the second. If your condition were only created_at < :last_ts, a page boundary that falls between two orders with the same timestamp would skip the second one forever. You must compare the pair (created_at, id). SQLite supports row values, so (created_at, id) < (:last_ts, :last_id) means exactly "sorts after the cursor in descending order", and the planner can seek with it. The check finds two orders with the same timestamp and puts a page boundary between them.

Your task

Implement m5_index() (the index) and m5_query() (the keyset query with the named parameters :last_ts, :last_id, :size, returning exactly the columns id, user_id, total_cents, created_at). For the first page the check passes last_ts = '9999-12-31 23:59:59' and last_id = 2**62: a cursor that sorts after everything.

python3 check.py shows milestone 5 as ✔. The check walks five pages from the start and compares all 250 rows with the OFFSET version; compares the page after row 250,000; tests the tie boundary; requires SEARCH ... USING INDEX with no SCAN and no sort; and requires at least 5x against the unindexed OFFSET query (in practice thousands). It also prints how slow OFFSET is even with your index.

Hints try without first
  • Index: the same columns as the ORDER BY, in the same order: (created_at, id).
  • Query: take the original, delete OFFSET, and add a WHERE that keeps only rows after the cursor in descending order. "After" in a descending order means "smaller".
  • If you do not like row values, the long form is created_at < :last_ts OR (created_at = :last_ts AND id < :last_id). It returns the same rows; SQLite handles it well too.
  • Keep the ORDER BY created_at DESC, id DESC. The index can only help if the sort order in the query matches it.
Solution spoiler 
def m5_index():
    return "CREATE INDEX idx_orders_created_id ON orders(created_at, id)"

def m5_query():
    return """
SELECT id, user_id, total_cents, created_at
FROM orders
WHERE (created_at, id) < (:last_ts, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT :size
"""

Milestone 6 (optional): the index that is never used

Finance wants "number of orders and revenue on a given day":

SELECT COUNT(*) AS n, COALESCE(SUM(total_cents), 0) AS revenue
FROM orders WHERE date(created_at) = :day

There is already an index on created_at (the check creates it for you), and the query is still a SCAN. The index is sorted by created_at, not by date(created_at). To use it for date(created_at) = '2023-06-15' the database would have to compute date() for every entry first, and that is a scan (chapter 8, trap 2). There are two fixes:

  1. Rewrite the predicate so the bare column is compared with constants. All timestamps of June 15 lie in the half-open range [2023-06-15, 2023-06-16), which the index on created_at can seek into.
  2. Index the expression: CREATE INDEX ... ON orders(date(created_at)). SQLite and PostgreSQL both support expression indexes; the query must then use the same expression.
from dataset import open_db, explain
con = open_db()
con.execute("CREATE INDEX idx_orders_created ON orders(created_at)")
p = {"day": "2023-06-15", "next_day": "2023-06-16"}
print("date(created_at) = :day, index on created_at"); explain(con, "SELECT COUNT(*), SUM(total_cents) FROM orders WHERE date(created_at) = :day", p)
print("range on the bare column");                      explain(con, "SELECT COUNT(*), SUM(total_cents) FROM orders WHERE created_at >= :day AND created_at < :next_day", p)
con.execute("CREATE INDEX idx_orders_day ON orders(date(created_at))")
print("expression index on date(created_at)");        explain(con, "SELECT COUNT(*), SUM(total_cents) FROM orders WHERE date(created_at) = :day", p)
$ python3 try.py
date(created_at) = :day, index on created_at

  QUERY PLAN: SEARCH orders USING INDEX idx_orders_created (created_at>? AND created_at<?)

  QUERY PLAN: SEARCH orders USING INDEX idx_orders_day (<expr>=?)

Both fixes turn a scan into a seek. The rewrite needs no new index; the expression index keeps the query readable but costs space and write time, and only helps this exact expression.

The scan version loops: Rewind to the first row, Column and Ne to test it, Next, test, Next... 50,000 times. Try it yourself: five experiments

  1. The price of an index. Every index must be updated on every write. Load 50,000 orders with no secondary index, then with four: 
    import time

    con.commit()

                     CREATE INDEX b ON orders(created_at, id);

Distributed systems connection

Everything here gets more expensive, not less, when the database is on another machine. N+1 turns into network latency: each avoided round trip is a few milliseconds of tail latency saved, and calls that fan out across shards multiply it (Sharding in Practice). Keyset pagination is what distributed stores offer by default: a cursor or page token that records the last key seen is cheap to serve from any replica, while OFFSET would force every shard to produce and discard its rows. And the covering index idea is the heart of read replicas and specialised stores: keep a second, narrower copy of the data shaped exactly for one query, and pay for it on the write path. Remember what that costs: the copy must be kept in sync, which is the subject of change data capture and the reason indexes lag behind the table in some systems. Whatever the architecture, the first debugging step is the same as in this lab: ask for the plan.

What you learned

  • Read the plan, do not guess. SCAN means every row; SEARCH ... USING INDEX means a B-tree seek; COVERING means the table is never touched; USE TEMP B-TREE FOR ORDER BY means an extra sort.
  • An index on the WHERE column removes the scan. An index with the equality column(s) first and the ORDER BY column next also removes the sort, so LIMIT can stop early.
  • A covering index contains every column the query reads, so no table lookups remain. It is bigger and slows writes, so spend it on hot queries.
  • N+1 is about the number of statements, which no index can fix. One JOIN and GROUP BY (with a LEFT JOIN if absent rows must stay) replaces thousands of queries.
  • OFFSET pages cost more the deeper you go. Keyset pagination seeks to the last row seen, and must compare the full sort key (timestamp and id) to survive ties.
  • A function around an indexed column hides it from the index. Compare the bare column to a range, or index the expression.
  • Test performance claims by checking the plan first (deterministic) and timing second (noisy), and always check that the answers did not change.

Check your understanding

The query is WHERE user_id = ? ORDER BY created_at DESC LIMIT 10. Which index lets the database stop after reading ten index entries, with no sort?

  1. (created_at)
  2. (created_at, user_id)
  3. (user_id, created_at)
  4. (user_id) plus a bigger cache
With (user_id, created_at) the entries of one user are contiguous and already ordered by date, so the database seeks to the end of that block and reads ten entries backwards. (user_id) alone finds the rows but not in order, so they are sorted first. (created_at) is in date order but mixes all users, so it would walk many entries to find ten for this user.

A plan says SEARCH orders USING INDEX idx_status (status=?) and the query is still slow. What is the most likely explanation?

  1. SQLite ignored the index
  2. The index is on a low-selectivity column: the condition matches a large fraction of the table, so the seek is followed by a huge number of table visits
  3. SEARCH always means a full scan in SQLite
  4. The database needs more RAM for the index
SEARCH only says an index was used for the seek. If the condition matches 80% of the rows (as status = 'paid' does), the database still visits 400,000 rows, one at a time and in index order rather than table order, which can be worse than a plain scan. Selectivity decides whether an index helps; the plan alone does not tell you.

Why does the N+1 milestone judge your function by the number of statements it sends, not mainly by how fast it runs?

  1. The statement count is the same on every machine, while in-process timings hide the real cost: when the database is across a network, each statement costs a round trip
  2. Because SQLite cannot measure time
  3. Because loops in Python are always wrong
  4. Because the join is always exactly 100 times faster
On one machine a query costs microseconds, so the loop looks only a few times slower. Over a network every statement pays a round-trip time, so 4,000 statements cost seconds, and the number grows with the data. Statement count is deterministic and captures that; timing is noisy and misleading in a lab.

WHERE date(created_at) = '2023-06-15' scans the table even though created_at is indexed. Which change fixes it?

  1. Add LIMIT 1
  2. Run ANALYZE and nothing else
  3. Use SELECT * so the planner sees more columns
  4. Compare the bare column with a range (created_at >= '2023-06-15' AND created_at < '2023-06-16'), or create an index on the expression date(created_at)
The index is sorted by the stored created_at values. A condition on date(created_at) cannot be answered by seeking into that order, because the function would have to be applied to every entry. A range on the bare column can; so can an index built on the expression itself, provided the query uses the identical expression.

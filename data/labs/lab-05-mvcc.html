Lab 5: Snapshot Isolation from Scratch

In chapter 11 a reader never blocked a writer, and in chapter 12 you learned why: the database keeps several versions of a row and shows each transaction the ones that belong to its snapshot. In this lab you will build that machine. A small multi-version key-value store, a visibility rule, aborts, first-committer-wins conflict detection, and then the part that makes interviewers smile: you will reproduce the doctors-on-call write skew on your own code, and stop it.

Why this lab matters

Postgres "Repeatable Read" and Oracle's "Serializable" are snapshot isolation, and many other systems, InnoDB's consistent reads among them, are built on the same snapshot idea. The rules are short, but the corner cases are not: which transaction's commit is visible to which snapshot, what an abort leaves behind, and why two transactions that write different rows can still break an invariant. Once you have written the eight lines of visible() yourself, "xmin, xmax and the snapshot" stop being vocabulary and become something you can predict.

No threads, no flakiness

"Concurrent" here means interleaved. You create several transaction objects and call their methods in whatever order you like: t1.read(...), t2.write(...), t2.commit(), t1.read(...). A real database does this with threads or processes, but what a transaction is allowed to see depends only on the order of these calls, not on timing. Doing it by hand makes every anomaly reproducible and every run identical. Python 3.8 or newer, standard library only, nothing to install.

What you'll build

Six milestones, each building on the last (the sixth is optional):

  1. Versions: a version list per key, a global txid counter, and begin() taking a snapshot.
  2. Visibility: the rule that decides which version a transaction sees, including its own writes. Repeatable reads fall out of it.
  3. Abort: an aborted transaction's versions become invisible to everyone, at almost no cost.
  4. First-committer-wins: detect write-write conflicts at commit and fix the lost update.
  5. Write skew: show that snapshot isolation alone allows the doctors anomaly, then add an SSI-lite mode that prevents it.
  6. Garbage collection (optional): a vacuum() that removes versions nobody can see.

Milestone 1: versions and snapshots

Chapter 12 described each row version as carrying two stamps: created_by (Postgres calls it xmin) and deleted_by (xmax). That is the whole data model:

store.versions["alice"] = [ Version(value=True,  created_by=1, deleted_by=[3]),
                            Version(value=False, created_by=3, deleted_by=[]) ]

Every transaction gets a unique, increasing txid from a global counter when it begins. It also takes a snapshot: its own txid plus the set of transactions that were active (begun but not finished) at that moment. That is all a snapshot is. Two numbers' worth of facts are enough to separate "the past" from "everything else":

  • a transaction with a higher txid started after me, so it is the future;
  • a transaction with a lower txid in my active set was still running when I looked, so its commit, if it ever comes, happens after my snapshot too;
  • any other lower txid has finished. Whether it finished by committing or aborting is a question for milestones 2 and 3.

One deliberate difference from Postgres

In Postgres a version has one xmax: if a second transaction tries to update a row that a running transaction already updated, it waits on the row lock. This lab has no waiting, because there are no threads, and it detects the conflict at commit time instead (milestone 4). So deleted_by is a list of transactions that have claimed the old version. Several running transactions may be in the list. At most one of them will ever commit.

Your task

Implement Store.begin(), Transaction._put() (behind write and delete) and the simple version of Transaction.commit() that only marks the transaction committed. For "the version I am replacing", use the newest version whose deleted_by is empty. That is good enough while transactions run one after another, and milestone 2 will show you why it is not good enough in general.

def begin(self):
    txid = self.next_txid
    self.next_txid += 1
    active = [t for t, s in self.status.items() if s == "active"]     # BEFORE adding myself
    self.status[txid] = "active"
    tx = Transaction(self, txid, Snapshot(txid, active))
    self.live[txid] = tx
    return tx

def _put(self, key, value, tombstone):
    self._require_active()
    self.write_set.add(key)
    chain = self.store.versions.setdefault(key, [])
    for v in reversed(chain):               # writing a key I already wrote: reuse my version
        if v.created_by == self.txid and self.txid not in v.deleted_by:
            if tombstone:
                v.deleted_by.append(self.txid)
            else:
                v.value = value
            return
    old = self.store.visible_version(self, key)         # the version I am replacing
    if old is not None:
        old.deleted_by.append(self.txid)
    if not tombstone:
        chain.append(Version(value, self.txid))

This is the final version of _put. It calls visible_version from milestone 2, where your milestone 1 version used "the newest version with an empty deleted_by". The simple commit for now is:

def commit(self):
    self._require_active()
    self.store.status[self.txid] = "committed"
    del self.store.live[self.txid]

Milestone 2: who sees what

Now the rule at the centre of the chapter. A transaction sees a version when both of these hold:

  1. Its creator is visible. The creator is the reader itself (a transaction always sees its own writes), or the creator committed before the reader's snapshot.
  2. It is not deleted for the reader. None of its deleted_by is the reader itself or a transaction that committed before the reader's snapshot.

"Committed before the snapshot" needs three facts to be true at once: its status is "committed", its txid is lower than the snapshot's txid, and it is not in the snapshot's active set.

With this rule you get repeatable reads for free. T1 reads x, T2 writes x and commits, T1 reads x again: T2's version was created by a transaction that was running when T1's snapshot was taken, so T1 skips it and finds the old one. There is no read lock and no waiting. That is the whole promise of MVCC.

Your task

Implement Store.committed_before(snap, txid), Store.visible(v, tx), Store.visible_version(tx, key) and Transaction.read(key). Then go back to _put and replace the milestone 1 shortcut with visible_version: you want to replace the version you can see, which is not always the newest one in the list.

Hints try without first

  • In visible, a version you created yourself is visible even though you have not committed. A version you deleted yourself is gone, even though your delete has not committed.
  • read should return None when nothing is visible. Add the key to self.read_set even then; milestone 5 will care about reads that found nothing.
  • If the repeatable-read check passes but "a lower txid that commits after my snapshot" fails, you are checking txid < snap.txid but forgetting snap.active.
Solution spoiler 
def committed_before(self, snap, txid):
    return (self.status.get(txid) == "committed"
            and txid < snap.txid
            and txid not in snap.active)

def visible(self, v, tx):
    c = v.created_by
    if c != tx.txid and not self.committed_before(tx.snapshot, c):
        return False                        # created by the future, a running tx, or an aborted tx
    for d in v.deleted_by:
        if d == tx.txid or self.committed_before(tx.snapshot, d):
            return False                    # I deleted it, or a visible commit did
    return True

def visible_version(self, tx, key):
    for v in reversed(self.versions.get(key, [])):
        if self.visible(v, tx):
            return v
    return None

def read(self, key):
    self._require_active()
    self.read_set.add(key)
    v = self.store.visible_version(self, key)
    return v.value if v is not None else None

Milestone 3: abort

A transaction that rolls back, or crashes, must vanish: nobody may ever see what it wrote, and the versions it replaced must come back to life. In a lock-based system that means undoing changes in place. In an MVCC system it takes one line, and this is one of its nicest properties. The aborted transaction's versions are still sitting in the lists, but your visibility rule never shows a version whose creator did not commit. And the old versions it stamped with deleted_by are not deleted either, because an aborted deleter does not count.

Postgres works the same way: abort is instant and cheap, because there is nothing to undo; the dead versions wait for VACUUM. (InnoDB, which updates rows in place and keeps old versions in an undo log, has to do more work to roll back.)

Your task

  • A reader that began after the abort has a higher txid and the aborted one is not in its active set. Only the status == "committed" part of committed_before protects you.
  • Using a transaction after it finished is an error: _require_active() is already given.

def abort(self):
    self._require_active()
    self.store.status[self.txid] = "aborted"    # that is all: its versions are now invisible
    del self.store.live[self.txid]

Milestone 4: first committer wins

Snapshot isolation has one more rule, and it is what stops the lost update. Take a balance of 100 and two withdrawals of 30. Each transaction reads 100 from its snapshot, and each writes 70. Without a check, both commit and the balance is 70: one withdrawal vanished. Under snapshot isolation, when two concurrent transactions write the same key, only one may commit. The first to commit wins, and the other is aborted with a SerializationError and must retry from a fresh snapshot, where it will read 70 and write 40.

"Concurrent" has a precise meaning in your data structures: a transaction that committed but is not "committed before my snapshot". That is exactly the negation you already wrote as committed_before. For each key in my write set, look at every version's creator and deleters: if one of them (not me) has committed and is not visible to my snapshot, I lose. Because commit() checks and then marks itself committed with no other code running in between, the check is atomic here. A real database must take care to make "check, then commit" indivisible.

Your task

Implement _concurrent_committers(key) and _check_write_conflicts(), extend commit() so that a conflict aborts the transaction and re-raises the SerializationError, and write run_transaction(store, fn, retries), the retry loop every application needs around a database that can say no (chapter 10, Retrying aborted transactions, safely).

python3 check.py shows milestone 4 as ✔. It plays the two-withdrawals scenario exactly as in the figure, tests that disjoint keys, serial writers and an aborted rival do not conflict, that a concurrent delete conflicts with a write, and that run_transaction retries once when a rival sneaks in during the first attempt. Then it runs a fuzz: 5 seeds of 400 random steps with four transfers and audits in flight, and requires that the total never changes and that every audit sees a consistent total.

Hints try without first
  • For a version v, the interesting transactions are [v.created_by] + v.deleted_by. A concurrent delete or update shows up as a deleter; a concurrent insert or update as a creator.
  • Skip yourself, skip anything not committed (running and aborted writers are no reason to fail), and skip anything committed_before your snapshot.
  • On conflict, call self.abort() before re-raising, so the transaction is never left half-alive. The loser's versions are then invisible by milestone 3.
  • In run_transaction, a SerializationError means "start over with a new transaction"; any other exception means "abort and let the caller see it".
Solution spoiler 
def commit(self):
    self._require_active()
    try:
        self._check_write_conflicts()       # Milestone 4
        if self.store.ssi:
            self._check_read_conflicts()    # Milestone 5
    except SerializationError:
        self.abort()
        raise
    self.store.status[self.txid] = "committed"
    del self.store.live[self.txid]

def _concurrent_committers(self, key):
    found = set()
    for v in self.store.versions.get(key, []):
        for t in [v.created_by] + v.deleted_by:
            if (t != self.txid and self.store.status[t] == "committed"
                    and not self.store.committed_before(self.snapshot, t)):
                found.add(t)
    return found

def _check_write_conflicts(self):
    for key in sorted(self.write_set):
        other = self._concurrent_committers(key)
        if other:
            raise SerializationError("write-write conflict on %r: tx %d committed first"
                                     % (key, min(other)))

def run_transaction(store, fn, retries=5):
    for attempt in range(retries):
        tx = store.begin()
        try:
            result = fn(tx)
            tx.commit()
            return result
        except SerializationError:
            continue                            # commit() already aborted tx; try again with a new snapshot
        except BaseException:
            if store.status[tx.txid] == "active":
                tx.abort()
            raise
    raise SerializationError("gave up after %d attempts" % retries)

Milestone 5: write skew, and SSI-lite

Snapshot isolation is not serializability. The doctors from chapter 11 show the gap. The rule: at least one doctor must stay on call. Alice and Bob are both on call. Each runs the same transaction: count the doctors on call; if there are at least two, go off call.

Part A: reproduce the bug. Write go_off_call(tx, who) and see for yourself that your store, with milestone 4's conflict detection in place, lets both doctors leave.

Part B: SSI-lite. Real serializable snapshot isolation (Cahill, Röhm and Fekete 2008; in PostgreSQL since 9.1) tracks rw-dependencies between concurrent transactions and aborts one when it finds a dangerous structure: a pivot transaction with an rw-dependency both in and out. Doing that precisely takes a lot of bookkeeping. This lab uses a much blunter rule that is easy to explain and safe:

The SSI-lite rule

Track every key each transaction reads. At commit, if any key in my read set was changed by a transaction that committed after my snapshot, abort me.

Why is this safe? Look at any pair of concurrent transactions that both commit. If the one committing second had read something the first wrote, it would be aborted. So every read-write dependency between concurrent committed transactions points from the earlier committer to the later one, which agrees with commit order. Dependencies between non-concurrent transactions follow commit order trivially. Since all dependencies point the same way, there is no cycle, and committing in commit order is a valid serial order. (It covers reads of individual keys. A predicate read such as "all doctors where on_call", which can be changed by an insert, would need range or predicate tracking: see the stretch goals.)

Why "lite"? Because it is conservative: it aborts more than real SSI does. Real SSI waits for a cycle of two dependencies in a row before aborting anyone. SSI-lite aborts on a single rw-dependency, even when it could not have formed a cycle. A read-only transaction that read x while another transaction changed x would be fine to commit in the serial order "reader, then writer", but SSI-lite aborts it. You trade some unnecessary retries for a simple proof of safety, and every application of serializable isolation already has to expect and retry SerializationError (SQLSTATE 40001 in Postgres).

Milestone 6 (optional): garbage collection

Every update leaves a dead version behind. If nobody cleans up, the version lists grow forever (Postgres calls this bloat; see VACUUM and purge in chapter 12). A version is garbage when no snapshot, present or future, can see it. Future snapshots are easy: once a committed transaction has deleted a version, every transaction that begins afterwards skips it. Present snapshots are the catch: the oldest running transaction may still need a version that was replaced long ago. That is why one forgotten long-running transaction stops cleanup for the whole database.

Your task

Implement Store.vacuum(). A version is removable when its creator aborted, or when its creator committed, a committed transaction deleted it, and no transaction in self.live can still see it. Return the number of versions removed, and drop keys that end up with no versions.

python3 check.py shows milestone 6 as ✔. The check starts a reader, commits two more updates, and expects exactly one version to be reclaimed while the reader's old version survives (and the reader can still read it). After the reader finishes, the old version goes too. It then checks aborted versions, running writers' versions, and committed deletes.

Hints try without first
  • "No running transaction can see it" is exactly not any(self.visible(v, tx) for tx in self.live.values()). You wrote visible in milestone 2.
  • Never remove a version whose creator is still active: its transaction might commit.
  • Aborted transactions leave their txid in other versions' deleted_by lists. Harmless for visibility, and a nice thing to tidy while you are in there (do not count it as a removed version).
Solution spoiler 
def vacuum(self):
    removed = 0
    for key in list(self.versions):
        keep = []
        for v in self.versions[key]:
            v.deleted_by = [d for d in v.deleted_by if self.status[d] != "aborted"]
            if self._dead(v):
                removed += 1
            else:
                keep.append(v)
        if keep:
            self.versions[key] = keep
        else:
            del self.versions[key]
    return removed

def _dead(self, v):
    if self.status[v.created_by] == "aborted":
        return True                         # never visible to anyone
    if self.status[v.created_by] != "committed":
        return False                        # its creator is still running
    if not any(self.status[d] == "committed" for d in v.deleted_by):
        return False                        # still the current version for new snapshots
    # Deleted by a committed transaction, so every FUTURE snapshot skips it.
    # It is garbage only if no snapshot that already exists can still see it.
    return not any(self.visible(v, tx) for tx in self.live.values())

Stretch goals

  • Eager first-updater-wins: make _put raise SerializationError as soon as it finds a version that a concurrent transaction has already committed a change to. That is what Postgres does at Repeatable Read. It fails earlier and wastes less work.
  • Range reads and phantoms: add scan(prefix) that returns all visible keys with a prefix. Write a "no two bookings for the same room" test that inserts new keys, and see why tracking only keys already read misses it. What would a predicate or range lock record in the read set?
  • Real SSI: track rw-dependencies in both directions (in_conflict and out_conflict flags per transaction), and abort only when a transaction has both. Count how many fewer aborts you get on the random doctors test than with SSI-lite, and prove to yourself it is still safe.
  • Read committed: add a second isolation level where the snapshot is retaken at every read. Which scenarios from chapter 11 break?
  • Serial reference: write a checker that takes the committed history (reads, writes, commit order) and searches for a serial order that explains it. Use it to confirm SSI-lite never produces a non-serializable history, and to show that plain SI sometimes does.
  • Hot-key vacuum: make vacuum incremental (one key at a time) and trigger it from commit after every N commits, like autovacuum.

Distributed systems connection

Everything you wrote lives in one process, so "committed before my snapshot" is a lookup in one dictionary. In a distributed database a snapshot has to mean the same thing on every shard, and that takes a global notion of time: Google Spanner assigns commit timestamps from clocks with bounded uncertainty and waits out the uncertainty, while other systems use a timestamp oracle or hybrid logical clocks. Your txid counter is the single-node version of the same idea. And first-committer-wins has an echo in replication: two leaders that accept writes to the same key concurrently have exactly the write-write conflict you just detected, with no common commit point to arbitrate, which is why multi-leader systems need conflict resolution.

What you learned

  • MVCC keeps several versions per key, each stamped with the transaction that created it and those that deleted it. An update adds a version; it never overwrites.
  • A snapshot is a txid plus the set of transactions that were active when it was taken. "Visible" means: created by me, or by a transaction that committed before the snapshot, and not deleted by me or by such a transaction.
  • Repeatable reads and read-your-own-writes fall out of the visibility rule, with no read locks and no waiting.
  • Abort costs almost nothing, because status alone hides the aborted transaction's versions. The garbage waits for vacuum.
  • First-committer-wins stops lost updates: a commit fails if a concurrent transaction committed a write to the same key. The application must retry.
  • Snapshot isolation still allows write skew, because the conflicting transactions write different keys. SSI-lite shows the cure in miniature: track reads, and abort at commit if something you read changed. Real SSI does the same job more precisely.
  • Old versions can be reclaimed only when no snapshot can see them, so one long-running transaction can hold back cleanup for everyone.

Check your understanding

Transaction 5 takes its snapshot while transaction 3 is still running. Transaction 3 then writes k and commits. Can transaction 5 read that write?

  1. Yes, because 3 < 5 and 3 has committed by the time of the read
  2. Yes, but only if transaction 5 has not read k before
  3. No: 3 was in the active set of 5's snapshot, so for transaction 5 its commit happens "in the future"
  4. No, but only because transaction 3 has a lower txid
The snapshot freezes who was running at the moment it was taken. Transaction 3 was in that set, so whatever it does afterwards, including committing, stays invisible to transaction 5. That is also what makes a second read of k return the same answer as the first.

Why does aborting a transaction in this store need no undo work?

  1. Because aborted transactions never write anything
  2. Because visibility requires the creator to have committed, and an aborted deleter is ignored, so the transaction's versions are hidden and the versions it replaced are visible again
  3. Because the store deletes the versions during the next read
  4. Because abort is only allowed before the first write
The aborted transaction's versions stay in the lists until vacuum removes them, but no snapshot will ever consider their creator committed. This is how Postgres works as well: rollback is instant, cleanup is deferred.

T1 and T2 start concurrently, both read a and b, T1 writes a, T2 writes b, and both try to commit. What happens under (i) the milestone 4 store, and (ii) the milestone 5 store with ssi=True?

  1. (i) the second commit fails; (ii) both fail
  2. (i) both fail; (ii) both commit
  3. (i) the second commit fails; (ii) the second commit fails
  4. (i) both commit, which is write skew; (ii) the second committer fails with SerializationError
They wrote different keys, so first-committer-wins sees no write-write conflict and plain snapshot isolation lets both through. With SSI-lite the second committer finds that the first changed a key it had read, and aborts. The first committer is never aborted, because at its commit nothing it read had changed yet.

The lab calls SSI-lite "conservative". What does that mean?

  1. It may abort transactions that real SSI would have allowed, but it never lets a non-serializable outcome through for the key reads it tracks
  2. It lets some anomalies through to save work
  3. It only works when there are at most two concurrent transactions
  4. It aborts the transaction that committed first
Conservative means erring on the safe side: it aborts on a single read-write dependency, while real SSI waits for a dangerous structure of two. Extra aborts cost retries, never correctness. (Both only cover what they track, here individual keys, so phantoms from range queries need extra tracking.)

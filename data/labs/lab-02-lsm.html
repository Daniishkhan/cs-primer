Lab 2: An LSM Tree

In this lab you build the storage engine inside LevelDB, RocksDB and Cassandra, in miniature. Writes go to a write-ahead log and an in-memory table; full tables are flushed into sorted, immutable files with a sparse index; Bloom filters let a lookup skip the files that cannot contain a key; a k-way merge serves range scans; and compaction merges everything back together. At every step you will measure what the design costs and what it buys.

Why this lab matters

Chapter 5 explained why sorting turns an append-only log into something you can search and merge. Building one makes the trade-offs concrete: a read may consult many files (read amplification), compaction rewrites data you already wrote (write amplification), and a delete is a record that only disappears much later. You will count those costs with your own code. The record format and recovery rules come straight from Lab 1 and chapter 4; here they become the foundation of a much more capable engine.

Requirements

Python 3.8 or newer, standard library only, on macOS, Linux or Windows. Everything happens in temporary directories that check.py creates and deletes. Doing Lab 1 first helps, because this lab reuses its record format (it is given to you here) and its ideas about torn tails, tombstones and safe file swaps, but it is not required.

What the crash tests can and cannot prove

The checks cut the write-ahead log at many byte offsets, and raise an exception from a hook in the middle of a flush or a compaction, to simulate dying at that exact line. They test your ordering and recovery logic. They cannot prove that your fsync calls reach the platter, because the operating system's page cache would hide a missing one in any test that does not cut the power. Systems chapter 9 explains why, and the Systems crash-safe log lab shows the limit of this kind of test.

What you'll build

Five milestones, each building on the last:

  1. Memtable and WAL: a sorted in-memory table for recent writes, plus a write-ahead log replayed on open, so a crash loses nothing that put returned for.
  2. Flush and SSTables: write a full memtable as a sorted file with a sparse index and a footer; get reads the memtable, then the SSTables from newest to oldest, seeking by the sparse index.
  3. Bloom filters: one per SSTable, built with hashlib. Measure how many files a negative lookup skips, and compare the false-positive rate with the formula.
  4. Range scans: a lazy k-way merge (heapq.merge) across the memtable and every SSTable: newest wins, tombstones hide keys.
  5. Compaction: merge all SSTables into one, drop shadowed values and tombstones, swap the files in safely, and report write amplification.

Milestone 1: the memtable and the write-ahead log

An LSM tree turns random writes into sequential ones by buffering them in memory first. The buffer is the memtable. It must be able to hand back its contents in key order, because that is what a flush writes. There are several ways to build one, and the trade-off is worth a minute:

StructureputgetKeys in orderNotes
dict, sort when needed (this lab)O(1)O(1)O(n log n) each time you askSimplest. Fine if you sort once per flush; wasteful if scans are frequent.
sorted list with bisect.insortO(log n) to find the spot, O(n) to shift the listO(log n)O(n), already sortedOrdered at all times; but inserting in the middle moves many items. Fine for thousands of keys, painful for millions.
skip list or balanced treeO(log n)O(log n)O(n), already sortedWhat LevelDB and RocksDB use by default (a skip list). More code, no bad case.

The starter's MemTable is the first row: a plain dict, sorted when items() is called. That is a legitimate choice here because a memtable is sorted only once per flush, and a flush is rare. If you want to try the second row, replace the dict with a sorted list and bisect: the checks only look at behaviour. The memtable also tracks nbytes, the sum of len(key) + len(value) over its entries, which is how put decides it is time to flush. A delete is stored as an entry whose value is None: a tombstone.

RAM forgets when the power goes, and the memtable can hold seconds or minutes of acknowledged writes. So every write is first appended to a write-ahead log (WAL) on disk, and only then applied to the memtable. This is chapter 4's log used for one job. On open, the store replays the WAL into a fresh memtable. Two details come straight from Lab 1: the WAL record format is the same checksummed format (encode_record and decode_record are given), and a crash can leave a torn record at the end. Replay therefore stops at the first record that fails to decode, and the store truncates the file there so later appends do not land behind garbage.

    def put(self, key, value):
        old = self._d.get(key, MISSING)
        if old is not MISSING:
            self.nbytes -= len(key) + len(old or b"")

def replay_wal(path):
    """Read a WAL file. Returns (records, good_end): the (key, value) pairs of the valid
    prefix, oldest first, and the byte offset where that prefix ends."""
    if not os.path.exists(path):
        return [], 0
    with open(path, "rb") as f:
        data = f.read()
    records, pos = [], 0
    while pos < len(data):
        rec = decode_record(data, pos)
        if rec is None:
            break                       # torn or corrupt tail: stop here
        key, value, pos = rec
        records.append((key, value))
    return records, pos
    def _write(self, key, value):
        """Milestone 1: log first, then the memtable. Milestone 2: flush when it is full."""
        self.wal.append(key, value)
        self.mem.put(key, value)
        if self.mem.nbytes >= self.memtable_limit:
            self.flush()

    def _recover_wal(self):
        """Milestone 1: replay wal.log into the memtable; cut a torn tail off the file."""
        records, good_end = replay_wal(self._wal_path)
        for key, value in records:
            self.mem.put(key, value)
        if good_end < os.path.getsize(self._wal_path):
            with open(self._wal_path, "r+b") as f:
                f.truncate(good_end)
                f.flush()
                os.fsync(f.fileno())

    def get(self, key):
        """Memtable first, then SSTables from newest to oldest. The first answer wins;
        a tombstone is an answer (None)."""
        value = self.mem.get(key)
        if value is not MISSING:
            return value
        for table in self.tables:
            value = table.get(key)
            if value is not MISSING:
                return value
        return None

Milestone 2: flush to an SSTable

When the memtable reaches memtable_limit bytes, put flushes it: sort the entries, write them as one new file, and start over with an empty memtable and an empty WAL. That file is an SSTable, a Sorted String Table. This lab's layout is deliberately simple:

The exact bytes, all big-endian, so you can parse a file with a hex dump (see "under the hood" below):

  • data: the records in key order, each in the usual crc | key len | val len | key | value format. Tombstones are written too (value length -1): they must reach the file to hide older values in older files.
  • sparse index: a 4-byte count, then for every record whose position is a multiple of sparse_every (so records 0, N, 2N, ...): a 4-byte key length, an 8-byte offset into the file, and the key. Each such record starts a block: the run of records up to the next index entry.
  • bloom filter: empty for now.
  • footer (36 bytes): the magic LSMSST01, the offset where the index starts, the offset where the bloom filter starts, the record count (8 bytes each), and a CRC32 of those first 32 bytes. (Reading it back is already written, in SSTable.__init__.)

To read, SSTable.get(key) uses bisect.bisect_right(index_keys, key) - 1 to find the last block that starts at or before the key, reads only that block from disk (the given _read_block does it, and counts it), and scans its few records. Because the block is sorted, you can stop as soon as you pass the key. LSMTree.get then asks the memtable, and then the tables from newest to oldest; the first answer that is not MISSING wins, and None (a tombstone) is an answer. That is exactly the read path of chapter 5.

Flush, in the right order

Flush is where durability is easiest to get wrong. The steps, and why this order:

  1. Write the SSTable to sst-N.sst.tmp and fsync it. (The given write_sstable contract: it fsyncs before returning.) Nothing visible has changed.
  2. os.replace the temp file into its final name and fsync the directory. Now the table is part of the database.
  3. Only then reset the WAL and swap in the new, empty memtable. If you emptied the WAL first and crashed before the file was in place, the data would exist nowhere.

A crash after step 2 but before step 3 leaves the same data in the SSTable and in the WAL. That is harmless: replay puts the same values back in the memtable, and newest-wins gives the same answers. The test crashes a flush after each of sst_written, renamed and done (by raising from hook), reopens, and checks nothing was lost; it also requires that leftover .tmp files are cleaned up on open (the given __init__ does it).

def write_sstable(path, items, sparse_every=16, bloom_bits_per_key=0):
    """Write sorted (key, value) items (value None = tombstone) as an SSTable file.

    Layout: data records, sparse index (every sparse_every-th record), bloom filter
    (empty if bloom_bits_per_key is 0), footer. fsyncs the file. Returns its size in bytes.
    """
    items = list(items)
    data, index, offset = [], [], 0
    for i, (key, value) in enumerate(items):
        if i % sparse_every == 0:
            index.append((key, offset))
        rec = encode_record(key, value)
        data.append(rec)
        offset += len(rec)
    index_blob = struct.pack(">I", len(index)) + b"".join(struct.pack(">IQ", len(k), off) + k for k, off in index)
    bloom_blob = b""
    if bloom_bits_per_key and items:
        bloom = BloomFilter.for_keys(len(items), bloom_bits_per_key)
        for key, _ in items:                    # tombstoned keys too: they must shadow older tables
            bloom.add(key)
        bloom_blob = bloom.to_bytes()
    index_offset = offset
    bloom_offset = index_offset + len(index_blob)
    head = struct.pack(">8sQQQ", MAGIC, index_offset, bloom_offset, len(items))
    footer = head + struct.pack(">I", zlib.crc32(head))
    blob = b"".join(data) + index_blob + bloom_blob + footer
    fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_TRUNC | getattr(os, "O_BINARY", 0), 0o644)
    try:
        write_all(fd, blob)
        os.fsync(fd)                            # durable before anybody renames it into place
    finally:
        os.close(fd)
    return len(blob)
    def get(self, key):
        """The value, None if this table holds a tombstone for key, or MISSING."""
        if self.bloom is not None and not self.bloom.might_contain(key):      # Milestone 3
            self.bloom_skips += 1
            return MISSING
        i = bisect.bisect_right(self.index_keys, key) - 1     # last block starting at or before key
        if i < 0:
            return MISSING                                    # smaller than the table's first key
        block = self._read_block(i)
        pos = 0
        while pos < len(block):
            rec = decode_record(block, pos)
            if rec is None:
                raise CorruptionError("bad record in %s" % self.path)
            k, v, pos = rec
            if k == key:
                return v
            if k > key:
                break                                         # sorted: it would have been here
        return MISSING
    def flush(self, hook=None):
        """Milestone 2: write the memtable out as a new SSTable, then empty it and the WAL.

        Order matters: write temp file + fsync -> rename -> fsync directory -> reset WAL.
        hook(stage) is called after each step so tests can "crash" there.
        """
        def step(name):
            if hook:
                hook(name)

        items = self.mem.items()
        if not items:
            return
        final = self._sst_path(self.next_id)
        tmp = final + ".tmp"
        self.sst_bytes_written += write_sstable(tmp, items, self.sparse_every, self.bloom_bits_per_key)
        step("sst_written")
        os.replace(tmp, final)
        fsync_dir(self.dir)
        step("renamed")
        self.tables.insert(0, SSTable(final))
        self.next_id += 1
        self.mem = MemTable()
        self.wal.reset()                    # only now: the data is safe in the SSTable
        step("done")

Milestone 3: Bloom filters

Reading is where an LSM tree pays. A key that is not there is the worst case: every SSTable has to be checked before you can say so (read amplification). A Bloom filter (chapter 5) answers "is this key in this file?" with either "definitely not" (always correct) or "maybe" (usually correct). A "definitely not" skips the file with no disk read.

Your filter has m = n × bits_per_key bits and k = round(bits_per_key × ln 2) hash functions (for 10 bits per key that is m = 10n and k = 7, the optimum from chapter 5). It needs k different positions per key. You do not need k independent hash functions: take one hashlib.sha256 digest, split out two integers h1 and h2, and use position_i = (h1 + i × h2) mod m. That trick is called double hashing, and it works about as well as k separate hashes. Make h2 odd so it is never zero modulo a power of two.

Three ways a Bloom filter goes wrong

  • Python's built-in hash(). It is randomised per process (to defend against hash-flooding), so a filter written to disk by one run would give wrong answers in the next. The filter lives inside the SSTable file, so its hashes must be reproducible. The check runs your code in two processes with different PYTHONHASHSEED values and compares the bits.
  • Forgetting the tombstones. A deleted key sits in the newer table as a tombstone. If that key is missing from the table's filter, the lookup skips the table, falls through to an older table, and finds the old value: the delete is undone. Add every key in the file, tombstoned or not. The check tests exactly this.
  • A false negative. A key that was added must never get "definitely not". The check tries every one.

class BloomFilter:
    def __init__(self, num_bits, num_hashes, bits=None):
        self.num_bits = num_bits
        self.num_hashes = num_hashes
        self.bits = bits if bits is not None else bytearray((num_bits + 7) // 8)

    @classmethod
    def for_keys(cls, n_keys, bits_per_key=10):
        """Size a filter for n_keys keys: m = n * bits_per_key bits, k = round(bits_per_key * ln 2)."""
        return cls(max(8, n_keys * bits_per_key), max(1, round(bits_per_key * math.log(2))))

    def _positions(self, key):
        """k bit positions from ONE sha256 digest (double hashing: h1 + i * h2).
        Not Python's hash(): that changes from run to run, and the filter lives on disk."""
        digest = hashlib.sha256(key).digest()
        h1 = int.from_bytes(digest[:8], "big")
        h2 = int.from_bytes(digest[8:16], "big") | 1        # odd, so it never gets stuck
        return [(h1 + i * h2) % self.num_bits for i in range(self.num_hashes)]

    def add(self, key):
        for p in self._positions(key):
            self.bits[p >> 3] |= 1 << (p & 7)

    def might_contain(self, key):
        """False means DEFINITELY not added. True means maybe."""
        return all(self.bits[p >> 3] & (1 << (p & 7)) for p in self._positions(key))

    def to_bytes(self):
        return struct.pack(">II", self.num_bits, self.num_hashes) + bytes(self.bits)

    @classmethod
    def from_bytes(cls, data):
        num_bits, num_hashes = struct.unpack_from(">II", data, 0)
        return cls(num_bits, num_hashes, bytearray(data[8:]))

Milestone 4: range scans

Here is what sorting buys that a hash index cannot: "all keys from cub up to (not including) emu". In each SSTable that range is a few neighbouring blocks. The memtable can produce it in order. The only remaining job is to merge those sorted streams into one, and to get the newest-wins rule right while doing it.

heapq.merge(*iterables) takes already-sorted iterables and lazily yields their items in order, holding only one item per source in a heap. Tag each entry as (key, age, value), where age is the source's position (0 for the memtable, 1 for the newest SSTable, ...). Tuples compare key first, then age, so for equal keys the newest comes out first. Then:

  1. if this key is the same as the last one you handled, skip it (an older, shadowed version);
  2. otherwise remember it as handled and, unless it is a tombstone, yield (key, value).

Since ages are unique per source, two tuples with the same key never fall through to comparing the values, so the None values of tombstones never get compared with bytes. One Python trap: if you build the tagged generators in a loop with a generator expression that mentions the loop variable, every generator ends up using the last age (closures capture variables, not values). Use a small helper function that takes age as an argument.

Two more requirements. First, scan must be lazy: asking for the first pair must not read whole tables. Second, an SSTable's own scan(lo, hi) must use the sparse index to start at the right block and stop as soon as it passes hi, reading block by block (the given _read_block counts them, and the check counts too).

def _tagged(source, age):
    for key, value in source:
        yield key, age, value

def merge_newest_wins(sources, drop_tombstones=True):
    """Merge sorted (key, value) iterables into one sorted stream.

    `sources` are ordered NEWEST FIRST. When several sources have the same key, only the
    newest one's entry is yielded. If drop_tombstones, a winning tombstone is not yielded
    at all (it hides the key); otherwise it is yielded with value None.
    """
    last = None
    merged = heapq.merge(*[_tagged(src, age) for age, src in enumerate(sources)])
    for key, age, value in merged:             # ties on key are ordered by age: newest first
        if key == last:
            continue                           # an older version of a key we already decided
        last = key
        if value is None and drop_tombstones:
            continue
        yield key, value
    def scan(self, lo=None, hi=None):
        """Yield (key, value) in key order for lo <= key < hi. Value None = tombstone."""
        i = 0 if lo is None else max(bisect.bisect_right(self.index_keys, lo) - 1, 0)
        while i < len(self.index_keys):
            if hi is not None and self.index_keys[i] >= hi:
                return                                        # this block starts past the range
            block = self._read_block(i)
            pos = 0
            while pos < len(block):
                k, v, pos = decode_record(block, pos)
                if lo is not None and k < lo:
                    continue
                if hi is not None and k >= hi:
                    return
                yield k, v
            i += 1
    def scan(self, lo=None, hi=None):
        """Milestone 4: yield live (key, value) pairs with lo <= key < hi, in key order."""
        sources = [iter(self.mem.range(lo, hi))] + [t.scan(lo, hi) for t in self.tables]
        return merge_newest_wins(sources, drop_tombstones=True)

Milestone 5: compaction and write amplification

Without compaction an LSM tree rots. Every flush adds a file, so reads check more files; overwritten values and tombstones sit in old files forever. Compaction merges SSTables, keeps only the newest live value of each key, and writes the result as a new file. You already wrote the engine of it: it is merge_newest_wins run over every table, with drop_tombstones=True.

Dropping tombstones is the dangerous part. A tombstone may be removed only when nothing older than it can still exist; otherwise the old value it was hiding returns (the "zombie" of chapter 4). Here that is true by construction: you merge every SSTable, and the memtable is newer. The leveled strategies in the stretch goals cannot do this cheaply, and real engines track carefully when a tombstone has reached the bottom of the tree. The file swap is the same discipline as in Lab 1:

  1. write the merged table to sst-N.sst.tmp with an N above every input, and fsync it (inside write_sstable);
  2. os.replace it into place and fsync the directory;
  3. point self.tables at the new table;
  4. close and delete the old files, oldest first. If a crash leaves the new table and some old ones, reads still agree: the new table is newest. But delete the newest old table first and you may remove a tombstone while an older table still holds the value it hid.

The test sets that trap: it writes a key in the first table, deletes it several tables later, and compacts. It "crashes" after tmp_written, replaced, deleted_1 and done, reopens, and demands the same answers. If everything has been deleted the merge is empty: write no file at all.

Write amplification

Write amplification is the number of bytes the engine writes to disk divided by the number of bytes the user asked it to store. Every byte is written at least twice here: once to the WAL and once when its memtable is flushed. Each compaction then rewrites live data again. Your tree already keeps three counters (the first two are given): user_bytes (the length of every key and value passed to put/delete), wal.bytes_written (you maintain it in WAL.append) and sst_bytes_written (you add to it after each write_sstable, in flush and in compact). write_amplification() is given: it divides the disk bytes by the user bytes. The check reproduces all three totals independently and requires yours to match exactly.

Stretch goals

  • Leveled compaction. Real engines do not merge everything. In the leveled scheme (LevelDB, and RocksDB's default style) tables are organised into levels: flushes land in level 0, where key ranges may overlap, and each lower level is a set of non-overlapping files covering the key space, each level allowed to hold roughly ten times more than the one above. When a level is over budget, pick one file and merge it only with the files in the next level whose key ranges overlap it. Reads then need at most one file per level below level 0; the price is that data is rewritten each time it moves down a level (high write amplification). Implement it with min_key/max_key per SSTable and a 3-level tree, and re-run experiment 1.
  • Size-tiered compaction. Merge only tables of similar size (say, when four have accumulated). Compare its write amplification and number of files with the leveled version. Which one lets a tombstone be dropped, and when?
  • A skip-list memtable. Replace the dict with a skip list or a bisect-based sorted list and time 100,000 inserts followed by a flush, against the dict. When does the dict's sort-at-flush start to hurt, and what happens to scans that overlap the memtable?
  • Compressed blocks. Compress each data block with zlib before writing and store the compressed length in the index. Measure the file size and the CPU cost on get.
  • An immutable memtable. While a full memtable is being flushed, writers must not stall. Freeze it, give new writes a fresh memtable and WAL, and let reads consult both. What is the crash story now?
  • Snapshots and iterators. Make scan safe while the tree changes, by iterating over a frozen list of tables and a copy of the memtable. What stops a compaction from deleting a table a scan is still reading?
  • Prefix Bloom filters. A filter over whole keys cannot help a range scan. Add a second filter over the first 4 bytes of each key, and use it to skip files in a prefix scan.

Distributed systems connection

This is the engine under many of the systems you will meet in the data-at-scale chapters. Cassandra, ScyllaDB, HBase and the LevelDB/RocksDB family are LSM trees, and they are chosen for write-heavy, replicated, sharded workloads because every write is a sequential append. Three of your design decisions come back at cluster scale. Immutable files are cheap to back up, to ship to a new replica and to share between versions of the data. Tombstones stop being a local detail: when a delete must reach several replicas, a tombstone has to be kept long enough for a replica that was offline to hear about it, or the old value returns when the replicas reconcile. That is why systems that delete this way keep tombstones for a configured grace period and not merely until the next compaction. And write amplification is a direct cost: it uses up the disk's write bandwidth (and, on flash, its endurance) so the more your engine amplifies, the fewer user writes per second one node can absorb. Replication (chapter 15) and sharding (chapter 16) spread that load over machines, but each machine still runs a compaction loop like the one you wrote. The write-ahead log you replay on open is the same log a replica replays to catch up (chapter 13).

What you learned

  • An LSM tree buffers writes in a sorted memtable and protects them with a write-ahead log, so every disk write is sequential and nothing acknowledged is lost on a crash.
  • A flush writes a sorted, immutable SSTable: data blocks, a sparse index (one entry per block), a filter and a footer. A lookup seeks to one block and scans a handful of records.
  • Reads go memtable first, then newest to oldest SSTable; the first hit wins and a tombstone is a hit. A missing key must be checked against every file, which is read amplification.
  • A Bloom filter never gives a false negative and gives a false positive at a rate you can compute: about 0.8% at 10 bits per key. Tombstoned keys must be in the filter too.
  • Range scans are a lazy k-way merge of sorted sources. Tag entries with source age and the newest wins, which also makes tombstones hide older values.
  • Compaction merges files, drops shadowed values and (when everything older is included) tombstones, and swaps files in safely: temp file, fsync, rename, delete oldest first.
  • Write amplification (disk bytes over user bytes) measures what compaction costs. Compacting more often means fewer files to read but more writes: the central trade-off of LSM design.

Check your understanding

A lookup for key k asks an SSTable's Bloom filter, which answers "no". What can you conclude, and what do you do?

  1. Probably not present; read the block anyway to be sure
  2. Present with high probability; read the block
  3. Definitely not in this file; skip it and move on to the next older file (or answer "not found")
  4. Nothing; Bloom filters are only a hint
A Bloom filter has no false negatives: a key that was added always has all its bits set. A "no" is therefore certain and saves a disk read. A "yes" is the uncertain answer: usually right, but sometimes a false positive.

During a flush, why must the WAL be reset only after the new SSTable has been fsynced and renamed into place?

  1. Because the WAL is needed to build the SSTable's index
  2. Because if the WAL were emptied first and the process crashed before the SSTable was in place, the flushed data would exist nowhere
  3. Because renaming a file is slower than truncating one
  4. Because replaying an empty WAL is an error
The WAL is the only durable copy of the memtable until the SSTable exists. Reversing the order opens a window where neither exists. The opposite crash (SSTable in place, WAL not yet reset) is harmless: replay puts the same values back, and newest-wins yields the same answers.

You delete key k, which lives in an old SSTable. The tombstone is flushed to a newer SSTable. Why must k still be added to the newer table's Bloom filter?

  1. Otherwise a lookup would skip the newer table, reach the older one and return the old value, undoing the delete
  2. Because Bloom filters need at least one key per block
  3. Because tombstones are stored as ordinary values
  4. It does not need to be; tombstones are never looked up
A tombstone is an answer ("deleted") that must stop the search. If the filter excluded it, the lookup would treat the table as not knowing the key and keep going to older tables, where the stale value lives.

You change your engine to compact the whole database every time two SSTables exist. What happens to read amplification and write amplification?

  1. Both go down: fewer files and less work
  2. Both go up
  3. Read amplification goes up and write amplification goes down
  4. Read amplification goes down (almost always one file to check) but write amplification goes up sharply, because the same live data is rewritten again and again
This is the central trade-off. With one or two files a lookup checks very few; but each compaction rewrites everything, so the bytes written per user byte grow with the size of the database. Leveled and size-tiered strategies exist to rewrite less while keeping read cost bounded; in experiment 1, compacting at 2 tables made the write amplification 44.67 against 2.43 for never compacting.

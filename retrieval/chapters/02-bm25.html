Inverted Indexes & BM25

Matching words is easy; deciding which match is best is the craft. This chapter takes the inverted index from chapter 1's terms to a ranked list: what an index stores beyond document ids, how three plain intuitions about words become the BM25 formula, what its two knobs do, and where the formula is known to fall short.

Why this matters

BM25 is the baseline every other retriever in this course is compared against, and in hybrid systems it keeps a permanent place beside embeddings, especially for names, codes and rare terms. It is also a small, fully explainable formula: when a document ranks where it does, you can write down exactly why. If you understand it, you can tune it, debug a surprising ranking, and judge when a more complex retriever is justified. This chapter derives it rather than quoting it.

What the index stores

Data Systems chapter 17 showed an inverted index as a map from each term to a sorted list of document ids, and showed that an AND query is a merge of two lists. A ranking function needs more than membership, so a real index keeps a handful of extra facts.

  • The dictionary: every distinct term, kept sorted so a lookup is fast (a hash table, a sorted array with binary search, or a finite-state structure).
  • For each term its document frequency (df): the number of documents containing it.
  • For each term its postings list: one entry per document containing it, holding the document id, the term frequency (tf: how many times the term occurs in that document) and, optionally, the positions where it occurs.
  • A table of document lengths: how many terms each document has (after analysis).
  • Collection totals: the number of documents N and the average document length.

The listing builds exactly this structure over eight short documents about invoices and payments, and answers three kinds of query from it. The corpus is deliberately small so you can check every number by eye. One document (d5, an annual report) is much longer than the rest; it will cause trouble later.

def postings(term):
    return sorted(index.get(term, {}))

def intersect(a, b):
    """Merge two sorted postings lists in O(len(a) + len(b))."""
    i = j = 0; out = []
    while i < len(a) and j < len(b):
        if a[i] == b[j]: out.append(a[i]); i += 1; j += 1
        elif a[i] < b[j]: i += 1
        else: j += 1
    return out

def phrase(*terms):
    """Docs where the terms occur at consecutive positions."""
    docs = postings(terms[0])
    for t in terms[1:]: docs = intersect(docs, postings(t))
    return [d for d in docs
            if any(all(p + k in index[t][d] for k, t in enumerate(terms)) for p in index[terms[0]][d])]

The AND query intersects two sorted lists by walking both at once, never looking at a document that is in neither: cost proportional to the sum of the list lengths. The phrase query "late payment" uses the positions: it finds documents where "payment" occurs at the position right after "late". Without stored positions, the index could only say that both words occur somewhere, which is why phrase support and proximity ranking cost extra index space. Notice also that d5 contains "invoices" (plural), so it is absent from the postings of "invoice": the unstemmed analyser of this listing is the situation chapter 1 warned about.

Making the postings small

Postings dominate index size, so engines compress them. The key trick is to store each list as gaps between consecutive document ids rather than the ids themselves: the ids 1004, 1010, 1011 become 1004, 6, 1. Gaps are small numbers, and small numbers fit in few bytes using a variable-byte code: seven bits of payload per byte, with the top bit saying "more bytes follow". Real engines use faster block-based schemes (Lucene's current format packs fixed blocks of 128 entries), but the principle is the same, and this one is short enough to read.

import random

def varint(n):
    out = bytearray()
    while True:
        low, n = n & 0x7F, n >> 7
        out.append(low | (0x80 if n else 0))
        if not n: return bytes(out)

random.seed(7)
N_DOCS = 10_000_000
for name, df in [("rare term", 1_000), ("common term", 1_000_000)]:
    ids = sorted(random.sample(range(N_DOCS), df))
    gaps = [ids[0]] + [b - a for a, b in zip(ids, ids[1:])]
    raw = 4 * df
    packed = sum(len(varint(g)) for g in gaps)
    print(f"{name:<12} df={df:>9,}  raw int32: {raw:>10,} B  delta+varint: {packed:>10,} B  ({packed/raw:.0%})")

A term in 1,000 of 10 million documents has large gaps and compresses to about half of the fixed 4-byte layout here. A very common term, in a tenth of all documents, has gaps averaging ten, so most fit in one byte: a quarter of the size. This is also why dropping stop words stopped being worth it, as chapter 1 noted: the biggest lists compress best. (The sampling here is random; real document ids are often clustered, which helps further.) An index is also not one big list. Engines write small immutable segments and merge them in the background, the same shape as the log-structured designs of Data Systems chapter 5; a deleted document is marked, and its space is reclaimed at merge.

Ranking from first principles

Given a query with several terms, which of the matching documents should come first? Set formulas aside and think like a reader. Three intuitions do most of the work.

  1. A document that uses the query word more is more likely to be about it. (term frequency)
  2. But the tenth repetition tells you much less than the first. (saturation)
  3. A match on a rare word is stronger evidence than a match on a common word. (inverse document frequency)
  4. A mention in a short document means more than the same mention buried in a very long one. (length normalisation)

BM25 is the result of turning each into arithmetic and multiplying the pieces. The name stands for "Best Matching 25": it is the 25th in a numbered series of weighting schemes tried in the Okapi system at City University London, from the work of Stephen Robertson, Stephen Walker and colleagues in the early 1990s (their experiments in the third Text REtrieval Conference, TREC-3, 1994, are the usual reference point). Robertson and Zaragoza (2009) give the definitive account. We derive the pieces one at a time.

Term frequency, and why it must saturate

The crudest score for a query term is its raw count in the document. That rewards repetition without limit: a page that says "invoice" fifty times is judged ten times more relevant than one that says it five times, and anyone can game it by stuffing keywords. The truth is closer to this: once a document has mentioned a term a few times, we are fairly sure it concerns that subject, and further repeats add little.

The classical justification is the eliteness idea behind the 2-Poisson model (Harter, 1975). Imagine each document is either "about" a term's concept (elite for it) or not. Elite documents tend to use the word at a higher average rate than non-elite ones, so observing the word several times raises our belief that the document is elite, but this belief approaches certainty and then stops growing. Robertson and Walker (1994, "Some simple effective approximations to the 2-Poisson model") replaced the messy exact weight by a cheap curve with the same shape. BM25 uses

tf component = tf × (k1 + 1) / (tf + k1)

It equals 1 when tf is 1, rises with tf, and never exceeds k1 + 1 however large tf becomes. The parameter k1 controls how fast the curve flattens: with k1 = 0 every matching document gets the same tf component (term presence only), with a large k1 the curve stays nearly linear for longer.

Inverse document frequency: rare words carry more evidence

Suppose a query is "the refund policy". Every document contains "the", so a match on it distinguishes nothing; "refund" appears in few documents, so a match on it narrows the field. Karen Spärck Jones (1972) proposed weighting a term by how rare it is across the collection, the inverse document frequency: roughly log(N / df), where N is the number of documents and df the number containing the term. The logarithm matters. A term in 1 of a million documents is not a million times more informative than one in all of them; it is worth about 14 "nats" (natural-log units) against 0, as the first table above shows.

The BM25 version has a more careful origin. Robertson and Spärck Jones (1976, "Relevance weighting of search terms") asked: what is the evidence that a document containing the term is relevant? Let p be the probability that a relevant document contains the term and u the probability that a non-relevant one does. Under the simplifying assumption that terms are independent (the binary independence model), the log-odds contribution of a term present in a document is

log [ p (1 − u) / ( u (1 − p) ) ]

With no relevance judgements, take p = 0.5 (a relevant document is as likely to contain the term as not), so the p-part cancels, and estimate u by the fraction of all documents containing it, since nearly all documents are non-relevant to any query: u ≈ n / N where n is the term's df. Adding 0.5 to counts to avoid zeros gives the Robertson–Spärck Jones weight

idf(t) = ln [ (N − n + 0.5) / (n + 0.5) ]

The derivation has one awkward consequence. If a term is in more than half the documents (n > N/2), the weight is negative: matching it makes the document less likely to be relevant. In the table, a term in 600,000 of a million documents gets −0.405 and one in 900,000 gets −2.197. That is mathematically honest and practically unwelcome, because one common word in a query can push a document below one that lacks it. The fix used by Lucene (and therefore Elasticsearch and OpenSearch) is to add 1 inside the logarithm:

idf(t) = ln [ 1 + (N − n + 0.5) / (n + 0.5) ]

This is always positive, equals ln(N/df) closely for rare terms, and shrinks smoothly to 0 for terms in nearly every document. The Lucene documentation gives this form. The other columns of the table show the three side by side: for a term in 100 documents all agree to three digits, and they diverge only where the term is common.

Go deeper optional

Why the p = 0.5 assumption is not silly. It says: before we have judgements, we have no reason to think relevant documents use a term more or less often than a coin flip. Croft and Harper (1979) and Robertson (2004, "Understanding inverse document frequency: on theoretical arguments for IDF") discuss this and the weaknesses of the independence assumption. The independence assumption is the real compromise: "payment" and "invoice" co-occur, so a document containing both gets close to double the credit for what is one idea. BM25 ignores this, and so does every other formula in this chapter.

Where BM25 breaks the binary model. The binary independence model only sees whether a term is present. BM25 keeps the same idf-style weight but replaces "present or not" by the saturating tf and length factor above, which is the sense in which it is "a non-binary model".

Length normalisation: why long documents are discounted

Our eight documents include a 68-term annual report that mentions "payment" twice. Another document has 15 terms and mentions "payment" twice. Which is more about payment? The short one: two of its fifteen terms are the word. Two of sixty-eight is a weak signal, and a long document also has more chances to contain any word by accident.

Robertson and Walker (1994) described two opposite stories about why a document is long, and BM25 interpolates between them. In the verbosity story, a long document says the same things at greater length, so its term counts should be scaled down in proportion to length. In the scope story, a long document covers more topics, so a term's count is its count and the document should not be penalised. Real collections contain both kinds. The parameter b (between 0 and 1) says how much to believe the verbosity story. Each term's frequency is effectively compared to a length-adjusted baseline:

k1 × (1 − b + b × |d| / avgdl)

where |d| is the document's length and avgdl the average over the collection. This factor sits in the denominator beside tf. With b = 0 it equals k1 for every document: no length effect. With b = 1 it is k1 × |d| / avgdl, full scaling by relative length. A document of exactly average length is unaffected whatever b is.

The whole formula

Multiply the idf by the saturated, length-adjusted tf, and sum over the terms of the query. This is the form used by Lucene:

score(q, d) = ∑t in q idf(t) × tf × (k1 + 1) / ( tf + k1 × (1 − b + b × |d| / avgdl) )

Here tf means the term's frequency in document d. Terms of the query that do not occur in the document contribute 0. The defaults in Lucene's BM25Similarity are k1 = 1.2 and b = 0.75 (from its documentation), and Manning, Raghavan and Schütze (2008) suggest k1 between 1.2 and 2 and b = 0.75 when no tuning data exists.

import math
from collections import Counter
from corpus import DOCS, tok

docs = {d: Counter(tok(t)) for d, t in DOCS.items()}
dl = {d: sum(c.values()) for d, c in docs.items()}
N = len(docs); avgdl = sum(dl.values()) / N
df = Counter(t for c in docs.values() for t in c)

def idf(t):                                   # Lucene / Robertson form, never negative
    return math.log(1 + (N - df[t] + 0.5) / (df[t] + 0.5))

def bm25_term(t, d, k1=1.2, b=0.75):
    tf = docs[d][t]
    if tf == 0: return 0.0
    norm = k1 * (1 - b + b * dl[d] / avgdl)
    return idf(t) * tf * (k1 + 1) / (tf + norm)

def search(query, k1=1.2, b=0.75):
    terms = tok(query)
    scores = {d: sum(bm25_term(t, d, k1, b) for t in terms) for d in docs}
    return sorted(((round(s, 3), d) for d, s in scores.items() if s > 0), reverse=True)

Watching a query being scored

An engine does not score all eight documents. It reads the postings lists of the query terms and adds each term's contribution to an accumulator for each document that appears in the list. Documents that appear in no list are never touched. This is called term-at-a-time evaluation. Step through our query.

Step through

Scoring "late payment invoice", one term at a time

  1. Analyse the query and look up the statistics. The query goes through the same analyser as the documents (chapter 1). The dictionary gives each term's document frequency, hence its idf: "late" is rare (2 documents, idf 1.28), "invoice" is middling (4, 0.69), "payment" is common (5, 0.49).
  2. Read the postings of "late". Only d1 and d5 contain it. d1 gets a large contribution (1.80: two occurrences in a short document, times a high idf) and d5 a small one (0.73: one occurrence in a long document).
  3. Add "payment". Its list names d1, d3, d4, d5 and d6. Each gets a modest amount; because the idf is low, even two occurrences in d1 add only 0.69. d3, d4 and d6 now enter the table.
  4. Add "invoice". d1, d2, d6 and d8 gain. d6, a short template that says "invoice" three times, jumps to second place; d8 and d2 enter. d7 (a holiday calendar) was never touched.
  5. Sort and return the top k. The accumulators are sorted (in practice a small heap of size k suffices). d1 is first, then d6, then the long report d5 in third place. Seven of eight documents matched at least one term; a stricter AND query would have returned only d1.

On a large collection this approach would still read every posting of a very common term. Engines avoid most of that with dynamic pruning: they store, for blocks of each postings list, an upper bound on the score that block can contribute, and skip any block that cannot lift a document into the current top k. The WAND algorithm (Broder et al., 2003) and its block-max refinement (Ding and Suel, 2011) are the standard references. The practical consequence is that a top-10 search can be much faster than scoring all matches, but an engine that stops early can no longer tell you the exact number of matching documents.

Tuning k1 and b

The defaults are good enough to be a baseline, and tuning them is the cheapest improvement available. But "tune" means measured on judged queries (the subject of chapter 5), not guessed. Because the two settings interact and the best values depend on the collection, tune them by grid search on a development set of judged queries and confirm on held-out queries, as Manning et al. recommend. Expect modest gains on most collections (check this on yours rather than assuming it); a very large gain from tuning alone suggests that something else, such as the analyser or the field setup, was wrong.

Analogy: clues in an investigation

A detective receives clues, each a feature of the suspect. A clue about something rare (a left-handed person with a green coat) is worth more than one about something common (a person in a coat): that is idf. Hearing the same witness repeat a clue five times does not make the clue five times as strong: that is saturation. A claim from a witness who gave a two-line statement carries more weight per sentence than one buried in a 200-page transcript: that is length normalisation. The detective then adds up the weight of the clues.

Where it breaks down: BM25 adds each clue as if it were independent. "Payment" and "invoice" are two clues that usually arrive together, so a document containing both gets credit twice for what is mostly one fact. A good detective would notice; the formula does not.

Variants, and what the evidence says

"BM25" is a family, not one formula. Implementations differ in details:

  • The idf form. The original Robertson–Spärck Jones form can go negative; Lucene's adds 1 inside the logarithm; some libraries use ln(N/df) or other smoothings.
  • The (k1 + 1) numerator. The original has it, so the tf component equals 1 at tf = 1. Lucene's scores included it until version 8, when it was dropped from BM25Similarity (a legacy class keeps the old values). Since it multiplies every document's score for a query by the same constant, the ranking is unchanged; only the absolute numbers differ.
  • How length is measured. Lucene stores document length in a compressed, lossy form, so |d| is slightly approximate.
  • BM25L and BM25+ (Lv and Zhai, 2011, "Lower-bounding term frequency normalization") add a small floor to the length-normalised tf so that very long documents are not over-penalised, which helps with verbose queries.
  • BM25F (Robertson, Zaragoza and Taylor, 2004) handles several fields, described next.

Do these differences matter? Kamphuis, de Vries, Boytsov and Lin (2020, "Which BM25 Do You Mean? A Large-Scale Reproducibility Study of Scoring Variants") compared eight variants on three newswire collections and found no significant effectiveness differences between them, including Lucene's approximation of document length. The practical lesson: when comparing systems, state which BM25 you used and its parameters, and do not expect the variant to be where improvements come from. (That study used news collections; results on other kinds of text may differ, which is another reason to measure on your own.)

More than one field

Real documents have a title, a body, maybe tags. A match in a title is stronger evidence than the same match in a long body. The obvious approach is to score each field with BM25 separately and add (or take the maximum of) the results with boosts. The more principled BM25F (Robertson, Zaragoza and Taylor, 2004, "Simple BM25 extension to multiple weighted fields") first combines the fields: it length-normalises each field's term frequency separately, multiplies by a field weight, sums them into one pseudo term frequency, then applies saturation once. That prevents a term that appears once in each of five fields from being counted five times before saturation. Some engines offer a query type modelled on it (Elasticsearch's combined_fields, for example); check your engine's documentation for how multi-field scoring combines.

Systems connection

Ranking needs corpus-wide statistics (N, df, average length), but a large index is split across shards, each holding part of the documents. By default each shard computes idf from its own documents, so the same term can have different weights on different shards, and scores from different shards are not strictly comparable. Small or unevenly filled shards make this visible. Engines offer a way to gather global statistics first at the cost of an extra round trip (Elasticsearch calls it dfs_query_then_fetch). This is the scatter-gather pattern, with the tail-latency consequences of Reliability chapter 9: a query is as slow as its slowest shard. Search-product design, including typeahead and freshness, is covered in System Design chapter 11.

Where BM25 goes wrong

  • Vocabulary mismatch. It cannot match "get my money back" to a page about refunds. Query understanding (chapter 3) helps a little; dense retrieval (chapter 7) helps a lot, and hybrid search keeps both strengths.
  • Unstable statistics on small corpora. With N = 8, a single document more or fewer moves idf visibly. Our toy corpus exaggerates this; a corpus of millions does not suffer.
  • Very short documents. A one-line title has almost no length variation and tf almost always 1, so BM25 reduces to idf-weighted presence. That is often fine, but ties become common.
  • Passages without context. A chunk of a contract that says "the Supplier shall pay within 30 days" lacks the name of the contract, so a query naming it cannot match. Chunk-level retrieval (chapter 14) addresses this.
  • Order and meaning. It is a bag of words: "dog bites man" and "man bites dog" score the same. Phrase and proximity features add a little structure but not understanding.
  • Scores are not probabilities. A BM25 score depends on the query and the collection. A score of 12 for one query says nothing about whether it beats 8 on another, and a fixed threshold is a bad way to decide "relevant enough" (see chapter 10 for combining score scales).

Common misconception

"BM25 is TF-IDF with a new name." Plain TF-IDF multiplies a raw (or log) term frequency by idf; it has no ceiling on repetition and no principled length treatment. BM25's saturation and length normalisation are exactly the two things that make it behave well on real text. Also: "higher b is better because long documents are bad." Raising b helps only where long documents are verbose; where they are long because they cover many topics, it buries the best ones.

State of play, October 2026

BM25 remains the default relevance function in Lucene-based engines (Lucene, Elasticsearch, OpenSearch, Solr), with k1 = 1.2 and b = 0.75 as the documented defaults for Lucene's BM25Similarity. Public retrieval benchmarks such as BEIR (Thakur et al., 2021) were built partly to show how well neural retrievers generalise against a BM25 baseline, and BM25 remains the baseline to beat in new work. Which neural models currently beat it on which benchmarks changes quickly and is deliberately not recorded here; the benchmark chapters (chapter 6) explain how to read such results. Engine defaults and version numbers also change: confirm what your deployed version does.

Key takeaways

  • An inverted index stores a dictionary with document frequencies, postings (document, tf, optional positions) and a document-length table. Postings compress well as gaps with variable-byte codes.
  • BM25 combines three ideas: term frequency that saturates (ceiling k1 + 1), inverse document frequency (rare terms carry more evidence) and length normalisation controlled by b.
  • The idf comes from the Robertson–Spärck Jones relevance weight; Lucene adds 1 inside the logarithm so it never goes negative.
  • Defaults of k1 = 1.2 and b = 0.75 make a solid baseline; tune on judged queries, expecting modest gains.
  • Variants matter less than expected on the collections tested by Kamphuis et al. (2020), but always report which one you used.
  • BM25 cannot bridge vocabulary mismatch, treats terms as independent, and its scores are not comparable across queries or probabilities.
  • In a sharded index, idf is shard-local by default, so scores can differ across shards unless global statistics are gathered.

Check your understanding

Page A mentions the query word 5 times; page B (same length) mentions it 50 times. With the default k1 = 1.2, roughly how much higher is B's term-frequency component?

  1. About ten times higher
  2. About 20% higher
  3. About the same: exactly equal
  4. About twice as high
The component is tf(k1+1)/(tf+k1) = 1.77 at tf = 5 and 2.15 at tf = 50, about 22% more. It cannot exceed k1 + 1 = 2.2. Ten times higher would be the raw-tf behaviour that saturation exists to prevent; "exactly equal" would need an infinite tf.

A term occurs in 900,000 of 1,000,000 documents. Which statement about its weight is correct?

  1. Classic ln(N/df) and Lucene's form both give it a large weight
  2. The Robertson–Spärck Jones form gives it a large positive weight
  3. All idf forms give it exactly zero
  4. The Robertson–Spärck Jones form gives it a negative weight (about −2.2), while Lucene's form keeps it small and positive
When df > N/2 the original weight ln((N−n+0.5)/(n+0.5)) is negative, which would penalise matches. Lucene adds 1 inside the logarithm; the weight becomes about 0.105. Common terms never receive large weights in either form.

You set b = 0 for a collection mixing short FAQ answers and 80-page manuals. What happens to the manuals compared with the default?

  1. They rank higher, because their larger number of term occurrences is no longer discounted by length
  2. They rank lower, because length now counts against them
  3. Nothing changes: b only affects queries with several terms
  4. They are removed from the index
With b = 0 the length factor equals 1 for every document, so a long document is not penalised for being long, and its many chances to contain the term count in full. That may be desirable if the manuals are long because they cover many topics, or harmful if the FAQ answers are the better matches.

In a four-shard index each shard computes idf from its own documents. Two shards hold 1,000 and 300,000 documents. What is the main risk?

  1. Postings lists become longer than the shard
  2. Phrase queries stop working
  3. The same term gets different weights on different shards, so scores merged from shards are not strictly comparable
  4. Documents are scored twice
idf depends on N and df, which differ by shard, so one term can be "rare" on a small shard and "common" on a large one. Gathering global statistics first (an extra round trip) avoids this. Phrase queries rely on positions inside a shard, not on idf.

A colleague says a BM25 score of 14.2 is "highly relevant" and wants to show only results above 10. What is the best response?

  1. Agree, since BM25 is a probability scaled to 0 to 100
  2. Disagree: scores depend on the query terms, their idf and the collection, so a fixed threshold means different things for different queries; consider relative thresholds or a calibrated model
  3. Agree, but only for queries of one word
  4. Disagree: BM25 scores are always between 0 and 1
The score is a sum of idf-weighted contributions, so queries with rare terms produce large numbers and queries with common terms small ones. It is an ordering within one query, not an absolute relevance measure.

You change Lucene's version and every BM25 score becomes 2.2 times smaller, but the ranked lists are identical. Which explanation fits?

  1. A constant factor (here k1 + 1 = 2.2) was removed from the numerator; it scaled all documents equally, so order is unchanged
  2. The idf was recomputed and rare terms matter less
  3. The analyser stopped stemming
  4. The index lost the document-length table
Dropping the (k1+1) numerator divides every score for a query by the same constant, preserving the ranking. An idf or analyser change would reorder documents; a missing length table would change the length normalisation and hence order.

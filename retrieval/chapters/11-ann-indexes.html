Approximate Nearest-Neighbour Search

Dense retrieval needs the closest vectors to a query among millions or billions. Checking all of them is exact and too slow; the indexes in this chapter check a small fraction and accept a little loss. We build the idea of IVF, product quantisation and HNSW from the arithmetic up, measure each on the same data, and learn to read the three-way trade between recall, latency and memory.

Why this matters

The vector index is the part of a retrieval system that decides what you can afford: how many vectors fit in memory, how many queries a second a node serves, and how quickly new documents become searchable. Its settings (nprobe, efSearch, M, the number of PQ bytes) silently cap your recall before any reranker or language model sees a result. After this chapter you can size an index with arithmetic, choose between IVF, PQ and HNSW for a given constraint, set their parameters from a measured recall curve instead of a guess, and explain why filters and updates make approximate search harder. It continues chapter 7's embeddings and prepares chapter 12.

Why exact search stops working

A dense retriever turns a query into a vector and returns the stored vectors with the highest similarity. Done exactly, that is a scan: one similarity per stored vector, each costing d multiply-adds for d dimensions. With unit-length vectors, ranking by cosine, inner product or (inverted) Euclidean distance gives the same order, so the arithmetic is one dot product per vector. The first listing generates a small clustered stand-in for embeddings (10,000 unit vectors, 64 dimensions, 200 queries; synthetic data, not real text embeddings) and prices brute force.

"""Synthetic 'embeddings' for chapter 11: clustered unit vectors, a stand-in for real text embeddings."""
import numpy as np

def make(n=10_000, d=64, n_clusters=100, n_queries=200, seed=7):
    rng = np.random.default_rng(seed)
    centres = rng.normal(size=(n_clusters, d))
    def sample(m):
        c = rng.integers(0, n_clusters, size=m)
        x = centres[c] + 1.8 * rng.normal(size=(m, d))
        return (x / np.linalg.norm(x, axis=1, keepdims=True)).astype(np.float32)
    return sample(n), sample(n_queries)

def exact_topk(X, Q, k=10):
    sims = Q @ X.T                                  # cosine, because every vector has length 1
    idx = np.argpartition(-sims, k, axis=1)[:, :k]
    order = np.take_along_axis(sims, idx, 1).argsort(axis=1)[:, ::-1]
    return np.take_along_axis(idx, order, 1)

def recall_at_k(found, truth):
    return float(np.mean([len(set(f) & set(t)) / len(t) for f, t in zip(found, truth)]))

At 10,000 vectors, brute force takes a fraction of a millisecond per query, because it is one matrix multiplication that the hardware does very well (the timing is for this machine; yours will differ). The last line is the problem. At 100 million vectors of 768 dimensions the same scan is 76.8 billion multiply-adds and 307 GB of memory traffic per query, and a server does not do that in the tens of milliseconds a search request allows. So the question becomes: can we avoid looking at most vectors?

The structures that work for 3 dimensions do not work for 768

For low-dimensional data there are exact answers: a k-d tree splits space along one coordinate at a time and discards whole regions. In high dimensions, two things break it. First, a tree over 100 million points has about 27 levels, so it can split on at most 27 of 768 coordinates; the region that "might contain a closer point" still touches most of the tree. Second, distances concentrate: in high dimensions the nearest and the farthest point are nearly the same distance away, so there is little to prune. The next listing measures that on random data.

A kd-tree over 100 million points has about 27 levels, so at most 27 of 768 coordinates are ever split on.

In two dimensions the nearest point is vastly closer than the farthest (a ratio of 0.00 after rounding). By 1,000 dimensions the nearest point is 85% as far as the farthest. Real embeddings are not random, because their effective dimensionality is lower and they cluster, which is what the approximate indexes below exploit, but the effect explains why exact tree indexes are not the answer.

So we accept approximate nearest-neighbour (ANN) search: return neighbours that are probably the true nearest, and measure how often that is wrong. The metric is ANN recall@k: the fraction of the exact top-k that the index returns. Do not confuse it with the relevance recall of chapter 4. ANN recall compares the index with exact search over the same embeddings; relevance recall compares the results with human judgements. An ANN recall of 0.95 says the index agrees with brute force on 95% of the top-k. It says nothing about whether those neighbours were the right documents.

Common misconception

"Recall of 0.95 means 5% of my answers are wrong." It means that 5% of the exact top-10 neighbours are missing from the index's top 10. If the document that answers the query was the exact top-1 and the index finds it, nothing was lost; the missing neighbours may be ranks 8 to 10, which rarely matter after reranking. Conversely, a perfect ANN recall of 1.0 does not help if the embedding model ranks the answer 40th. Measure the two separately: ANN recall against exact search to tune the index, and end-to-end relevance metrics (chapters 4 and 5) to decide whether the loss matters.

Analogy: finding a street in an unfamiliar country

To find the nearest bakery to a given address, you would not drive down every street. You would use a hierarchy: motorway to the right region, main road to the right town, local streets to the address, looking around only when you arrive. A graph index is such a road network. Another approach is a regional guidebook: look up the town first (IVF), then search only that town. Product quantisation is like describing every address as "town 37, district 201" rather than by full coordinates: smaller to store, slightly less precise.

Where it breaks down: roads live in two dimensions, so "nearby" is easy to define and a motorway really does get you near. In 768 dimensions, neighbours are not arranged along lines, a greedy move toward the target can end in a pocket from which every neighbour is farther, and the best graph (the next sections) must be built from the data itself.

Inverted file index (IVF): search the right neighbourhood

The inverted file index borrows the name and shape of chapter 2's inverted index. Run k-means on the vectors to find nlist centroids, and assign every vector to its nearest centroid, building nlist lists (the "cells" of a partition of space). At query time, compare the query to the centroids only, choose the nprobe closest cells, and scan the vectors in those cells exactly. If the query's true neighbours lie in the probed cells, you find them while touching about nprobe/nlist of the data.

import numpy as np

def kmeans(X, k, iters=12, seed=0):
    """Lloyd's algorithm. Returns centroids (k x d) and the cluster id of every row."""
    rng = np.random.default_rng(seed)
    C = X[rng.choice(len(X), k, replace=False)].copy()
    for _ in range(iters):
        # squared distance up to a constant: |c|^2 - 2 x.c
        assign = np.argmin((C * C).sum(1)[None, :] - 2 * X @ C.T, axis=1)
        for j in range(k):
            members = X[assign == j]
            if len(members):
                C[j] = members.mean(0)
    assign = np.argmin((C * C).sum(1)[None, :] - 2 * X @ C.T, axis=1)
    return C, assign

from kmeans import kmeans

X, Q = make()
truth = exact_topk(X, Q, 10)
nlist = 100
C, assign = kmeans(X, nlist)
lists = [np.where(assign == j)[0] for j in range(nlist)]          # the inverted lists
print(f"{nlist} cells; list sizes: min {min(map(len, lists))}, mean {len(X) // nlist}, max {max(map(len, lists))}\n")

def search(q, nprobe, k=10):
    cells = np.argsort(-(C @ q))[:nprobe]                        # closest centroids by cosine-like score
    cand = np.concatenate([lists[j] for j in cells])
    top = cand[np.argsort(-(X[cand] @ q))[:k]]
    return top, nlist + len(cand)                                 # distances: to centroids + to candidates

With nprobe = 1 we compute 203 distances per query (100 for centroids, about 100 for the cell) instead of 10,000, a 49 times saving, and find 55% of the true top-10. Probing more cells climbs the curve: 87.6% at 16 probes with 1,700 distances, 95.4% at 32 with 3,298. The cost grows almost linearly with nprobe, recall grows more slowly: the usual diminishing return.

Why not 100% at nprobe = 1? Because a query near a cell boundary has neighbours on both sides, and only one side is searched. That is the central failure mode of any partition-based index, and the reason the knob exists. Practical notes:

  • Choosing nlist. The FAISS guidelines suggest nlist between 4√N and 16√N, and between 30 and 256 training vectors per cell. For our 10,000 vectors that rule would give 400 or more cells and require 12,000 or more training vectors, so I used 100 cells to keep the example valid. Too few cells make each scan long; too many make the centroid comparison costly and the boundary problem worse.
  • Training data. The centroids describe the data they were trained on. If your corpus drifts (a new product line, a new language), cells become unbalanced and recall falls; plan to retrain.
  • Unbalanced cells. Our cells held between 36 and 164 vectors. A cell ten times larger than average costs ten times as much to scan each time it is probed, and is probed more often, so it dominates tail latency.

Product quantisation: store a code, not a vector

IVF reduces how many vectors we compare, not how much memory they use. At 3,072 bytes per 768-dimensional float32 vector, 100 million vectors need 307 GB. Product quantisation (PQ; Jégou, Douze and Schmid, "Product Quantization for Nearest Neighbor Search", 2011) compresses each vector to a few bytes.

The scheme has three steps. Train: cut every vector into m sub-vectors and run k-means with 256 centroids separately in each sub-space, producing m codebooks. Encode: replace each sub-vector by the one-byte id of its nearest centroid, so a vector becomes m bytes. Search uses asymmetric distance computation: the query stays uncompressed; for each of its m sub-vectors you compute the inner product with the 256 centroids of the matching codebook once, producing m small tables. A stored vector's approximate score is then the sum of m table lookups. The per-vector cost is m lookups and adds instead of d multiply-adds.

import numpy as np
from data import make, exact_topk, recall_at_k
from kmeans import kmeans

X, Q = make()
truth = exact_topk(X, Q, 10)
n, d = X.shape

def train_pq(X, m, ks=256):
    """Split every vector into m sub-vectors; learn ks centroids per sub-space."""
    ds = X.shape[1] // m
    return [kmeans(X[:, i * ds:(i + 1) * ds], ks, iters=10, seed=i)[0] for i in range(m)]

def encode(X, books):
    ds = X.shape[1] // len(books)
    codes = np.empty((len(X), len(books)), dtype=np.uint8)
    for i, B in enumerate(books):
        sub = X[:, i * ds:(i + 1) * ds]
        codes[:, i] = np.argmin((B * B).sum(1)[None, :] - 2 * sub @ B.T, axis=1)
    return codes

def adc_scores(q, codes, books):
    """Asymmetric distance: exact query against compressed database vectors, via m lookup tables."""
    ds = len(q) // len(books)
    tables = np.stack([books[i] @ q[i * ds:(i + 1) * ds] for i in range(len(books))])   # m x 256 inner products
    return tables[np.arange(len(books)), codes].sum(axis=1)                              # n scores, m adds each

print(f"{'m':>3} {'bytes/vec':>9} {'compression':>11} {'recall@10':>10} {'+ rerank 100':>13}")
for m in (4, 8, 16, 32):
    books = train_pq(X, m)
    codes = encode(X, books)
    found, found_rr = [], []
    for q in Q:
        s = adc_scores(q, codes, books)
        top = np.argsort(-s)[:10]
        short = np.argsort(-s)[:100]                         # shortlist, then rescore with the full vectors
        rr = short[np.argsort(-(X[short] @ q))[:10]]
        found.append(top); found_rr.append(rr)
    print(f"{m:>3} {codes.shape[1]:>9} {X.itemsize * d / codes.shape[1]:>10.0f}x {recall_at_k(found, truth):>10.3f} {recall_at_k(found_rr, truth):>13.3f}")

  4         4         64x      0.201         0.603
  8         8         32x      0.366         0.869
 16        16         16x      0.618         0.998

Read the table as a memory-quality dial. With 8 bytes per vector (32 times smaller), PQ alone finds 37% of the true top-10: the quantisation error is large relative to the gaps between neighbours. With 16 bytes it finds 62%, with 32 bytes 86%. The right-hand column shows the standard remedy: take the 100 best by PQ score as a shortlist, then rescore those 100 with the full-precision vectors (kept on disk or in a slower tier). That lifts 8 bytes to 87% and 16 bytes to 99.8%, for the cost of reading 100 full vectors per query. PQ is a filter that is good at not discarding the truth, not a final ranker.

Other quantisers occupy the same design space. Scalar quantisation stores each number in 8 bits (4 times smaller than float32) or fewer. Binary quantisation keeps one bit per dimension (32 times smaller) and uses the Hamming distance, usually with a reranking step. Optimised PQ rotates the vectors first so the pieces carry equal information. Lowering the number of dimensions (for embedding models trained for it, as in Matryoshka representation learning, Kusupati et al., 2022) shrinks vectors before any quantiser. All trade accuracy for memory; none is free.

Systems connection

Compression changes which part of the memory hierarchy an index lives in. 10 GB of PQ codes fit in RAM on one machine and are scanned at memory speed; 307 GB of float32 vectors need sharding or an SSD, where random reads cost microseconds rather than nanoseconds. This is the same reasoning as in performance engineering: count bytes moved, not only operations. The index is also a specialised store with its own durability and update story, covered more generally in specialised stores.

HNSW: a graph you can navigate

The Hierarchical Navigable Small World graph (HNSW; Malkov and Yashunin, "Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs", first posted 2016) is the most widely used ANN index for in-memory vector search. It starts from a simple observation: if every vector is linked to a few of its near neighbours, you can walk from any vector toward a query by repeatedly stepping to whichever linked vector is closer to the query, and stop when no neighbour improves. That is a greedy search on a proximity graph.

On its own, this walk can take many steps (it crawls) and can get stuck in a local minimum. HNSW fixes the first problem with layers, the idea of a skip list. Each vector is assigned a random top layer with exponentially decreasing probability, so layer 0 holds every vector, layer 1 about 1/M of them, layer 2 about 1/M2, and so on. Each layer has its own graph over the vectors it holds. Search starts at a fixed entry point on the top layer, where long hops cover large distances, descends one layer when it can no longer improve, and does the careful search on layer 0.

Step through

One HNSW query, layer by layer

  1. The structure. Layer 0 contains every vector, linked to its near neighbours. Layers above hold random subsets, so they are sparse and their links span long distances. Dashed lines show that a node on an upper layer is the same vector as on layer 0.
  2. Enter at the top. The search always starts at the entry point of the highest layer (node 4 here). The query is the yellow diamond.
  3. Greedy hop on layer 2. Node 4's only neighbour on this layer is node 11, which is closer to the query, so we move there. No neighbour of 11 is closer, so we stop on this layer.
  4. Drop to layer 1. The result so far becomes the entry point for the next layer down. On layer 1, node 11's neighbours (8 and 14) are both farther from the query, so we stay.
  5. Layer 0, greedy. On the dense bottom layer, node 11's neighbour 10 is closer to the query, so we move to 10.
  6. Layer 0, beam. The bottom-layer search keeps a candidate list of size ef and expands the most promising candidate until nothing in the list can be improved. Here that means checking 9 and 11, neighbours of 10.
  7. Return. The best k found are returned, nearest first: node 10, then 9 and 11. Only a few of the 16 nodes were ever compared with the query.

The three parameters

M
The number of links each node keeps (layer 0 allows 2M). More links mean a better-connected graph and higher achievable recall, but more memory and slower build. FAISS's guidelines give the memory cost as d × 4 + M × 2 × 4 bytes per vector.
efConstruction
How wide the candidate list is while inserting. Higher builds a better graph, slower. It is fixed at build time: changing it means rebuilding.
efSearch
How wide the candidate list is at query time. This is the knob you turn at runtime: it trades latency for recall, like nprobe for IVF.

Inserting a vector uses the same search: find its nearest neighbours in each layer from its top layer down, connect to them, and prune over-full neighbour lists. The pruning rule matters. A plain "keep the M closest" tends to link a node only to others in the same tight cluster, leaving clusters disconnected. The paper's heuristic keeps a candidate only if it is closer to the new node than to any neighbour already chosen, which spreads links in different directions. The listing implements all of it in about 90 lines (open it below), counts distance computations as its cost measure, and builds an index over the same 10,000 vectors.

    def _search_layer(self, q, eps, ef, layer):
        """Best-first search; returns the ef best (similarity, id) pairs, best first."""
        visited = set(eps)
        s0 = self._sims(q, list(eps))
        cand = [(-s, e) for s, e in zip(s0, eps)]; heapq.heapify(cand)      # max-heap by similarity
        best = [(s, e) for s, e in zip(s0, eps)]; heapq.heapify(best)         # min-heap of the ef best
        while cand:
            ns, e = heapq.heappop(cand)
            if -ns < best[0][0] and len(best) >= ef:
                break                                                         # nothing left can improve the result
            new = [n for n in self.links[layer][e] if n not in visited]
            if not new:
                continue
            visited.update(new)
            for s, n in zip(self._sims(q, new), new):
                if len(best) < ef or s > best[0][0]:
                    heapq.heappush(cand, (-s, n)); heapq.heappush(best, (s, n))
                    if len(best) > ef:
                        heapq.heappop(best)
        return sorted(best, reverse=True)
The full HNSW class about 90 lines, runnable 
import heapq, math, time
import numpy as np
from data import make, exact_topk, recall_at_k

class HNSW:
    def __init__(self, X, M=12, ef_construction=64, seed=1):
        self.X, self.M, self.efc = X, M, ef_construction
        self.mL = 1 / math.log(M)
        self.rng = np.random.default_rng(seed)
        self.links = []                  # links[layer][node] -> list of neighbour ids
        self.level = []                  # top layer of each node
        self.entry = None
        self.dist_calls = 0
        for i in range(len(X)):
            self._insert(i)

    def _sims(self, q, ids):
        self.dist_calls += len(ids)
        return self.X[ids] @ q

    def _search_layer(self, q, eps, ef, layer):
        """Best-first search; returns the ef best (similarity, id) pairs, best first."""
        visited = set(eps)
        s0 = self._sims(q, list(eps))
        cand = [(-s, e) for s, e in zip(s0, eps)]; heapq.heapify(cand)      # max-heap by similarity
        best = [(s, e) for s, e in zip(s0, eps)]; heapq.heapify(best)         # min-heap of the ef best
        while cand:
            ns, e = heapq.heappop(cand)
            if -ns < best[0][0] and len(best) >= ef:
                break                                                         # nothing left can improve the result
            new = [n for n in self.links[layer][e] if n not in visited]
            if not new:
                continue
            visited.update(new)
            for s, n in zip(self._sims(q, new), new):
                if len(best) < ef or s > best[0][0]:
                    heapq.heappush(cand, (-s, n)); heapq.heappush(best, (s, n))
                    if len(best) > ef:
                        heapq.heappop(best)
        return sorted(best, reverse=True)

    def _select(self, cands, m):
        """Neighbour heuristic: keep a candidate only if it is closer to the query than to every kept one."""
        kept = []
        for s, c in cands:                                                    # cands sorted best first
            if all(s > float(self.X[c] @ self.X[r]) for _, r in kept):
                kept.append((s, c))
            if len(kept) == m:
                break
        return kept

    def _insert(self, i):
        L = int(-math.log(1.0 - self.rng.random()) * self.mL)
        self.level.append(L)
        while len(self.links) <= L:
            self.links.append([[] for _ in range(i)])           # a new top layer: no links yet
        for layer in range(len(self.links)):
            self.links[layer].append([])
        if self.entry is None:
            self.entry = i
            return
        q, ep = self.X[i], [self.entry]
        for layer in range(self.level[self.entry], L, -1):                    # greedy descent above the new node's top layer
            ep = [self._search_layer(q, ep, 1, layer)[0][1]]
        for layer in range(min(L, self.level[self.entry]), -1, -1):
            W = self._search_layer(q, ep, self.efc, layer)
            chosen = self._select(W, self.M)
            self.links[layer][i] = [c for _, c in chosen]
            cap = 2 * self.M if layer == 0 else self.M
            for _, c in chosen:
                self.links[layer][c].append(i)
                if len(self.links[layer][c]) > cap:                           # shrink an over-full neighbour list
                    ids = self.links[layer][c]
                    sc = sorted(zip(self.X[ids] @ self.X[c], ids), reverse=True)
                    self.links[layer][c] = [n for _, n in self._select(sc, cap)]
            ep = [n for _, n in W]
        if L > self.level[self.entry]:
            self.entry = i

    def search(self, q, k=10, ef=50):
        ep = [self.entry]
        for layer in range(self.level[self.entry], 0, -1):
            ep = [self._search_layer(q, ep, 1, layer)[0][1]]
        return [n for _, n in self._search_layer(q, ep, max(ef, k), 0)[:k]]

What the benchmark curve hides

  • Memory. HNSW keeps full vectors and the links, so its memory is at least that of a flat index plus the graph (next section). The recall per distance is good; the footprint is not small.
  • Random access. Each hop jumps to an unrelated address. In RAM that is fine; on an SSD, where each hop is a separate read, an unmodified HNSW is slow. Disk-oriented graph indexes such as DiskANN (Subramanya et al., 2019) lay out the graph and compressed vectors to reduce reads per query.
  • Updates and deletes. Inserting works in the same way as build. Deleting a node leaves holes in other nodes' neighbour lists; most implementations mark the node as deleted and filter it out, so the graph degrades until it is rebuilt or repaired. A corpus with heavy churn needs a rebuild schedule.
  • Filters. If you ask for the nearest vectors that also satisfy a metadata filter, a graph walk that must skip non-matching nodes can wander or dead-end, and post-filtering the top-k can return too few results. That is the subject of chapter 12 and is a major reason systems with permissions need care.

The recall, latency and memory triangle

Every ANN index is a position in the space of three things you want and cannot have at once: high recall, low latency and small memory. Settings move you along one trade; the choice of index moves you to a different region.

The memory side is arithmetic, so do it before you choose. The listing prices 100 million 768-dimensional embeddings.

# What 100 million 768-dimensional embeddings cost to hold, by index design. A = assumption.
N, D = 100_000_000, 768
M = 16                 # A: HNSW links per node (layer 0 keeps up to 2*M)
PQ_M = 96              # A: PQ sub-vectors (8 dimensions each), 1 byte per code
ID = 8                 # bytes per stored vector id (int64)
GB = 1e9

rows = [
 ("flat, float32",                    N * D * 4),
 ("flat, float16",                    N * D * 2),
 ("flat, int8 (scalar quantised)",    N * D * 1),
 ("flat, 1 bit per dimension",        N * D // 8),
 ("HNSW over float32 vectors",        N * D * 4 + N * (2 * M * 4 + 4)),   # vectors + layer-0 links (2M x 4 B) + upper layers (~4 B)
 ("IVF-PQ, 96 bytes/code + id",       N * (PQ_M + ID)),
 ("IVF-PQ, 48 bytes/code + id",       N * (PQ_M // 2 + ID)),
]
print(f"{'index design':<34}{'bytes/vector':>13}{'RAM (GB)':>10}")
for name, total in rows:
    print(f"{name:<34}{total / N:>13,.0f}{total / GB:>10,.1f}")

The span is 30 times: from 320 GB for HNSW over float32 (the vectors plus 132 bytes of links each) to 10.4 GB for PQ codes. That is the difference between a cluster and a single machine. It is also why practical systems store compressed vectors for the first pass and rescore a small shortlist with better ones, and why embeddings with fewer dimensions or lower precision are attractive when they lose little quality on your queries.

Choosing and operating an index

  1. Check whether you need one. FAISS's guidelines note that a flat index is the only one that guarantees exact results and is appropriate when you will do only a few thousand searches. At a few hundred thousand vectors, a brute-force scan on a modern CPU or GPU is often fast enough, simpler, and exact. Work out vectors × dimensions × bytes and compare with your latency target before adding an index.
  2. Get the memory budget first. Use the arithmetic above. If full vectors do not fit, you are choosing between PQ or other quantisation, a disk-based graph index, or sharding.
  3. Plot the recall curve on your data. Embed a sample of real queries, compute exact top-10 by brute force, then sweep nprobe or efSearch and record ANN recall@10 and p95 latency. Pick the cheapest point that meets your recall target (for example 0.95 to 0.99), with margin for growth.
  4. Check the end-to-end effect. Compare relevance metrics (chapters 4 and 5) at that setting against the exact search. If a reranker follows (chapter 8), deeper candidate lists compensate for some ANN loss.
  5. Plan for change. A new embedding model means a new index (vectors from different models are not comparable). Plan rebuilds for churn, drift and deletes, and keep the old index until the new one has been compared on your judged queries.
  6. Watch it in production. Sample queries against exact search periodically and alert when recall drifts; track latency percentiles, memory and build duration.

State of play, October 2026

The pgvector extension for PostgreSQL offers both HNSW and IVFFlat indexes. Its README (read in October 2026) lists HNSW defaults of m = 16, ef_construction = 64 and hnsw.ef_search = 40; for IVFFlat it suggests lists of rows / 1000 up to a million rows and probes starting near the square root of lists, with a default of 1. It also documents half-precision, bit and sparse vector types and, since version 0.8.0, iterative index scans that keep searching until enough filtered results are found. FAISS's guidelines (also read this month) suggest an IVF cell count between 4√N and 16√N and name an IVF-with-HNSW-routing family for collections beyond a million vectors. Dedicated vector databases and search engines wrap the same families of index with their own defaults and names. Versions, limits and defaults change; read the documentation of the release you run, and rely on the recall curve you measure, not on a vendor's chart.

Key takeaways

  • Exact search costs N × d operations and memory traffic per query. Tree indexes fail in high dimensions because distances concentrate and few coordinates can be split. ANN trades a little accuracy for a large saving.
  • ANN recall@k compares an index with exact search over the same embeddings. It is not relevance recall. Tune with the first, decide with the second.
  • IVF clusters vectors with k-means and scans only the nprobe nearest cells. Its failure mode is the cell boundary; nprobe buys recall at roughly linear cost.
  • Product quantisation stores one byte per sub-vector (for example 8 bytes for 256), scores with lookup tables, and needs a rerank from full vectors to reach high recall.
  • HNSW is a layered proximity graph: a greedy descent through sparse layers, then a beam search of width efSearch on layer 0. It gives high recall per distance computation, costs memory for the links, is expensive to build, and is awkward under deletes, disk and filters.
  • Do the memory arithmetic first (100 million 768-d vectors: 307 GB flat, 320 GB HNSW, about 10 GB PQ), then plot recall against cost on your own queries and data.

Check your understanding

Why do k-d trees, so effective in 2 or 3 dimensions, give little speed-up for 768-dimensional embeddings?

  1. They cannot store floating-point numbers
  2. A tree splits on one coordinate per level, so it touches few of the 768 coordinates, and distances concentrate so there is little to prune
  3. They require the data to be sorted by label
  4. They only work for Euclidean distance on integers
A tree with 27 levels over 100 million points splits on at most 27 coordinates, and the listing showed nearest/farthest distance ratios near 0.85 at 1,000 dimensions. Floating-point storage and metric choice are not the obstacle.

An IVF index with nprobe = 1 misses neighbours for queries that sit close to the edge between two cells. What is the most direct fix?

  1. Retrain with fewer cells and a different random seed only
  2. Switch to float64 vectors
  3. Delete the centroids
  4. Raise nprobe so that adjacent cells are scanned too, accepting more distance computations
The neighbours are in a cell that was not probed. Probing more cells covers the boundary at roughly linear extra cost (the ivf.py output rose from 55% to 87.6% recall between nprobe 1 and 16). More precision in the numbers does not change which cell a vector belongs to.

You store 768-dimensional float32 vectors as PQ codes with 96 sub-vectors of 1 byte. By what factor is each vector smaller, and what should you add to keep recall high?

  1. 32 times smaller; rescore a shortlist with the full-precision vectors
  2. 8 times smaller; increase the vector dimension
  3. 96 times smaller; nothing, PQ is lossless
  4. 768 times smaller; retrain the embedding model
768 × 4 = 3,072 bytes becomes 96 bytes: 32 times smaller. PQ is lossy (the pq.py table showed 37% recall at 8 bytes for 64 dimensions), and a rescoring step with full vectors recovers most of the loss.

An HNSW index serves queries at 12 ms with recall@10 of 0.90. You need 0.97 and can afford more latency but no rebuild. Which parameter do you change?

  1. M, because it only affects query time
  2. efConstruction, because it can be changed on a live index
  3. efSearch, which widens the candidate list at query time and so trades latency for recall
  4. The entry point of layer 0
efSearch is a query-time setting (in hnsw.py, recall rose from 0.921 at ef 80 to 0.976 at ef 160 while distances rose from 1,187 to 2,102). M and efConstruction shape the graph and take effect only at build time.

A colleague says: "Our index has ANN recall@10 of 0.95, so 5% of user questions get a wrong answer." What is the right correction?

  1. They are right: the two numbers are the same thing
  2. ANN recall measures agreement with exact search over the same embeddings; whether the missing 5% of neighbours matter depends on relevance, which you measure with judged queries and end-to-end metrics
  3. ANN recall of 0.95 means 95% of answers are correct
  4. Recall cannot be measured for an approximate index
The missing neighbours may be lower-ranked and irrelevant, or a reranker may recover them; or the exact search may be wrong in the first place. Compute ANN recall against brute force to tune, and relevance metrics against judgements to decide.

Roughly how much memory does an HNSW index need for 50 million 1,024-dimensional float32 vectors with M = 16 (links stored as 4-byte ids, layer 0 holding up to 2M)?

  1. About 210 GB
  2. About 50 GB
  3. About 4 GB
  4. About 2,000 GB
Per vector: 1,024 × 4 = 4,096 bytes of data plus about 2 × 16 × 4 = 128 bytes of layer-0 links and a few bytes for upper layers, roughly 4,230 bytes. Times 50 million is about 211 GB. 50 GB would be a PQ-compressed size; the vectors alone are 205 GB.

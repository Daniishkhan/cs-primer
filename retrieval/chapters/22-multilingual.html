Multilingual & Multi-Script Documents

Everything so far quietly assumed English: words separated by spaces, left-to-right text, one language per document. Real corpora break each assumption. This chapter shows where retrieval and document pipelines go wrong on scripts without spaces, mixed languages, right-to-left text and queries in one language over documents in another, and what to do about each.

Why this matters

A system tuned and tested in English can fail completely on other languages without raising an error: the index returns nothing, or returns plausible neighbours in the wrong language. Governments, banks, hospitals and manufacturers handle documents in many languages, and several scripts often sit on one page. After this chapter you can recognise the four classic failures, apply the cheap fix for each, and plan a per-language evaluation instead of trusting one overall number.

Scripts without spaces

The analysers of chapter 1 begin by splitting text into words at spaces and punctuation. Chinese and Japanese are written without spaces between words, and so is Thai. Split a sentence on whitespace and the whole sentence is one token, so no query can match anything but the entire line. The script below tries three queries against four documents (Japanese, Japanese, Chinese and Thai), first with whitespace tokens, then with character bigrams: every pair of adjacent characters becomes an index term, a method that needs no dictionary and is standard for Chinese, Japanese and Korean search.

def bigrams(s):
    s = "".join(s.split())
    return {s[i:i + 2] for i in range(len(s) - 1)}

docs = {"d1": "私は東京都に住んでいます", "d2": "京都は古い都です", "d3": "我在东京大学学习", "d4": "ฉันเรียนที่มหาวิทยาลัยโตเกียว"}
for q in ("京都", "東京", "东京大学"):
    ws = [d for d, t in docs.items() if q in t.split()]       # whitespace tokens: the whole line is one token
    bg = [d for d, t in docs.items() if bigrams(q) <= bigrams(t)]
    print(f"query {q}: whitespace tokens match {ws or 'nothing'}; character bigrams match {bg}")
print("tokens in d4 when split on spaces:", len(docs["d4"].split()))
query 京都: whitespace tokens match nothing; character bigrams match ['d1', 'd2']
query 東京: whitespace tokens match nothing; character bigrams match ['d1']
query 东京大学: whitespace tokens match nothing; character bigrams match ['d3']
tokens in d4 when split on spaces: 1

Whitespace tokenising finds nothing, and the Thai document is a single token. Bigrams find the right documents, with a well-known side effect on the first query: 京都 (Kyoto) also matches 東京都 (Tokyo Metropolis), because the pair of characters 京都 appears inside it. Bigrams trade precision for a method that always works. The alternatives are a dictionary segmenter, which cuts the text into real words (MeCab for Japanese, jieba for Chinese, ICU's dictionary-based break iterator for Thai), at the cost of a dictionary that must be maintained and that errs on unknown words, names and new terms; and learned subword tokenisers, which split without an explicit dictionary. Search engines usually offer a bigram analyser as the safe default and a dictionary analyser as the precise option. The rule from chapter 1 still applies in full: the index and the query must use the same analyser, and an embedding model has its own tokeniser, which you do not control.

Many scripts, many languages, one page

The next three problems share a cause: text arrives with no label saying which language or script it is in. A single page may mix English headings, a Chinese product name, an Arabic address and a number. Treating the line as one string with one analyser, and one language setting, damages most of it.

A cheap first step is to split text into runs by script (the writing system: Latin, Arabic, Han, Thai), which Unicode records for every character. Then apply the right analyser to each run, and use a language identifier on runs long enough to classify (language identification on three-word strings is unreliable, and it confuses closely related languages such as Danish and Norwegian). Store the detected language and its confidence as metadata with each chunk, so a filter such as "documents in Spanish" and a per-language evaluation become possible.

import unicodedata as ud

def script(ch):
    return ud.name(ch, "?").split()[0]                       # LATIN, CJK, ARABIC, HEBREW, HIRAGANA, THAI, ...

ARABIC_HELLO = "مرحبا"              # escapes keep this file readable in any editor
line = "Invoice 請求書 No. 2025 " + ARABIC_HELLO
runs, prev = [], None
for ch in line:
    s = script(ch) if ch.isalpha() else prev                 # digits, spaces and dots join the current run
    if s != prev: runs.append([s, ""]); prev = s
    runs[-1][1] += ch
print("script runs :", ascii([(s, t.strip()) for s, t in runs]))

heb = "מחיר 1590 שקל"     # 'price 1590 shekel', stored in reading order
print("stored      :", ascii(heb))
print("bidi classes:", [ud.bidirectional(c) for c in heb[:6]], "(R = right to left, EN = number)")
print("reversed    :", ascii(heb[::-1]), "<- digits now read 0951")

extracted = "ﻣﺮﺣﺒﺎ ２０２５"   # presentation forms + full-width digits
fixed = ud.normalize("NFKC", extracted)
print("extracted   :", ascii(extracted))
print("after NFKC  :", ascii(fixed), "| equals", ascii(ARABIC_HELLO + " 2025"), ":", fixed == ARABIC_HELLO + " 2025")

for label, s in (("English", "hello"), ("Hebrew", "שלום"), ("Chinese", "你好"), ("Thai", "สวัสดี")):
    print(f"{label:8s} {len(s)} chars -> {len(s.encode('utf-8'))} UTF-8 bytes")

The first block of output shows the line split into four runs by script. The last block shows a cost that matters for LLM-based pipelines: the same short word takes 1 byte per character in English, 2 in Hebrew, 3 in Chinese and 3 in Thai. Tokenisers trained mostly on English text split other scripts into more pieces, so a Thai paragraph can use noticeably more tokens than its English equivalent, by an amount that depends on the tokeniser. Context windows and prices count tokens, and this makes such documents more expensive to process (deep learning, chapter 13).

Right-to-left text

Arabic, Hebrew, Persian and Urdu are written right to left. Digital text stores characters in reading order (called logical order), and the display software decides where to draw them, following the Unicode bidirectional algorithm (UAX #9). A number inside right-to-left text still reads left to right. The two orders differ, and the difference is where document pipelines break.

Where does display order leak into your data? Born-digital PDFs store glyphs with positions, not sentences, and some generators write the glyphs of right-to-left text in the order they are drawn, so text extraction returns words in reverse. OCR engines output the order of reading in the line, which for an engine without a right-to-left model is left to right. In both cases a search for the correct word finds nothing, because the index holds it reversed In the output above the stored line is in reading order, and a full reversal turns 1590 into 0951. Symptoms to look for are Arabic or Hebrew text that looks fine in a viewer but whose copied text is backwards, numbers that read differently when extracted, and a search engine that matches queries typed in reverse. The fix is at ingestion: detect the base direction of each line from the Unicode bidirectional classes of its characters (the "R" in the output above), re-run extraction with a library that applies the bidirectional algorithm, or use an OCR model for the script (chapter 19).

Arabic adds one more difficulty. Letters take different shapes at the start, middle and end of a word and when isolated, and PDFs often store these shaped glyphs as separate code points from a compatibility block (the "presentation forms"), not as the base letters users type. The query "مرحبا" typed on a keyboard and the same word extracted from a PDF are then different strings. Compatibility normalisation (NFKC, the Unicode form from chapter 1) maps the shaped forms back to the base letters, as the last block of the output showed, and also maps full-width digits to ASCII. NFKC does not repair a reversed order, and it changes more than you may want in some corpora (it folds superscripts and ligatures too), so apply it to the search index and keep the original text for display.

Cross-lingual retrieval

The last problem is the question in one language and the answer in another: an English query over German contracts, or an Arabic query over an English corpus. There are three designs.

  • A multilingual embedding model. Train a bi-encoder (chapter 7) so that text with the same meaning lands close together in any language. A query and a document need no shared words at all. BGE M3-Embedding (Chen et al., 2024) supports more than 100 languages and inputs up to 8,192 tokens, with dense, sparse and multi-vector retrieval from one model.
  • Translate the query into each document language, search each language's index with its own analyser, and merge the results. It keeps strong lexical search per language, costs one translation per language per query, and inherits translation errors.
  • Translate the documents once, at ingestion, into a pivot language. It moves cost out of query time, multiplies storage and makes citations point at text the author never wrote, so keep the original beside the translation.

Multilingual models have characteristic problems. They tend to prefer documents written in the same language as the query, even when a document in another language is the better answer, so a mixed-language corpus returns a language bias unless you check for it. Quality varies a great deal across languages: a model can do well in English and German, and noticeably worse in languages with less training data. Short queries in languages with rich morphology can match poorly. And the best lexical signals (exact names, identifiers) do not cross languages, which is another reason to keep a hybrid design (chapter 10), with each language's index using its own analyser.

State of play, October 2026

The Massive Multilingual Text Embedding Benchmark (MMTEB; Enevoldsen et al., 2025) extends MTEB to over 500 evaluation tasks across more than 250 languages. Its authors report that, at publication, the best-performing publicly available model was multilingual-e5-large-instruct, with only 560 million parameters, although much larger language-model-based embedders did best on some language subsets and tasks. Model rankings change every few months, and benchmark averages hide per-language results, so use these as a shortlist (chapter 6) and test on your own languages.

Common misconception

"Our model is multilingual, so we do not need to think about language." A multilingual embedder does not fix the tokeniser, the OCR script model, the reading direction of the extractor or the analyser of the lexical index, and a single average over all languages hides the languages where it fails. Every stage has its own language support, and the weakest stage sets the quality.

Key takeaways

  • Scripts without spaces need character n-grams or a dictionary segmenter. Bigrams always work and cost some precision (京都 inside 東京都); dictionary segmenters are precise and need maintenance.
  • Label text with its script and language, analyse each run with the right analyser, and store the labels as metadata for filters and per-language evaluation.
  • Right-to-left text must be in logical order in the index. Display-order extraction reverses words and can flip digits; fix it at ingestion and normalise Arabic presentation forms with NFKC.
  • Cross-lingual retrieval can use a multilingual embedder, query translation or document translation. Each has costs, and multilingual models favour the query's language.
  • Language support is per stage (OCR, analyser, tokeniser, embedder). Evaluate each language separately.

Check your understanding

A Chinese product catalogue is indexed with a standard analyser that splits on spaces. Searching for a product name returns nothing unless the whole description is typed. What is the most direct fix?

  1. Add more stop words
  2. Use a stemmer for Chinese
  3. Use character bigrams or a dictionary-based segmenter, on both index and query
  4. Lowercase the query
Without spaces, the whole line is one token, so only an exact whole-line query matches. Segmenting into words or bigrams creates the terms that queries can hit. Stop words, stemming and lowercasing do nothing for a string that was never cut into terms. The same analyser must be used at both ends.

Arabic text copied from a PDF looks correct on screen but searching for a word typed on a keyboard finds nothing. Which two checks should come first?

  1. Whether the extracted text is in presentation forms and whether it is in logical order
  2. Whether the embedding model has enough parameters
  3. Whether the query is lowercase
  4. Whether the page image has a high enough resolution
PDFs commonly store shaped letters from the presentation-forms block, and some generators store glyphs in display order. Either makes the extracted string differ from the typed word. NFKC fixes the first; the second needs re-extraction with the bidirectional algorithm. Case is irrelevant in Arabic script, and resolution matters for scans, not for a text layer that displays correctly.

A multilingual embedding model is deployed over a corpus of English and Spanish contracts. English queries keep returning English contracts even when the best answer is Spanish. What is the likely cause?

  1. The index is corrupted
  2. The Spanish documents are too long to embed
  3. BM25 is outranking the embedding scores
  4. Language bias: the model prefers documents in the query's language
Multilingual embedders often score same-language pairs higher than equally relevant cross-language pairs. The remedy is to measure it with queries whose answers are in the other language, then consider query translation, per-language retrieval and merging, or a different model. Nothing here points to corruption, length or lexical scores.

Why can a Thai document cost several times more LLM tokens than the same content in English?

  1. Thai text is always longer in characters
  2. Tokenisers trained mostly on English split other scripts into more, smaller pieces, and prices and context limits count tokens
  3. Thai uses more spaces
  4. Models refuse to compress Thai text
The vocabulary of a tokeniser reflects its training text. Scripts it saw less of are cut into short fragments or bytes, so the same meaning uses more tokens. The cause is the tokeniser's vocabulary, not the count of characters or the spaces.

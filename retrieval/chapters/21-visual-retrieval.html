Visual Document Retrieval

The usual route to searching a PDF is to extract its text and index that. This chapter covers the alternative: embed a picture of the page itself, so charts, layout and tables are searchable without being converted to text first. It explains how ColPali-style models do it, what it costs, and the cases where reading the text is still the better bet.

Why this matters

Chapters 18 to 20 built a text route: parse the layout, OCR what needs it, recover tables and fields. Every stage can lose information, and some information has no text form at all: the slope of a line chart, the position of a sensor in a diagram, the red stamp over a figure. Slide decks, scanned reports and technical manuals are exactly the documents where this matters most. After this chapter you can explain how a page becomes a set of vectors, estimate what that costs in storage and compute, predict which queries it wins and which it loses, and design a test that settles the choice for your own documents instead of a benchmark's.

What the text route throws away

Think about what a text extractor keeps of the following page: a heading, two paragraphs, a bar chart with the title "Quarterly output" and a photograph of a cracked weld with a caption. It keeps the heading and paragraphs. From the chart it may keep the title and the axis labels; the heights of the bars, which are the content, are gone. From the photograph it keeps the caption. A question such as "in which quarter did output fall?" can be answered from the page and from no text on it.

The loss has four sources, and they compound:

  • Non-text content. Charts, diagrams, photographs, maps and handwriting have no characters to extract. A captioning model can describe them, but a description of a chart is a lossy summary made before anyone knew what would be asked.
  • Layout and emphasis. Position, size, colour and boxes carry meaning: a callout box, a struck-through price, a totals row, a warning in red.
  • Pipeline errors. Each stage (layout, reading order, OCR, table structure) has an error rate, and the product of several stages is worse than any of them. A table recovered with a merged column is wrong before retrieval starts.
  • Engineering and time. A multi-stage parser is a lot of machinery to build and run. The ColPali paper (Faysse et al., 2024) reports about 7.2 seconds per page to index with a conventional parsing-and-captioning pipeline, against about 0.39 seconds for its model, measured on its own hardware; whatever the exact figures on yours, the parser is the slow part of ingestion.

Embedding the page itself

The idea is to skip extraction and give the page, as an image, to a model that outputs vectors. A vision-language model (deep learning, chapter 21) already does the first half: it cuts the image into a grid of small squares called patches and encodes each into a vector that captures what is there, whether that is a letter shape, a bar, a table border or a pixel of photograph. ColPali (Faysse et al., 2024, "ColPali: Efficient Document Retrieval with Vision Language Models") builds on PaliGemma-3B, which pairs the SigLIP image encoder with the Gemma 2B language model. The page becomes 1,024 patches, each projected down to a 128-dimension vector. The query is text, run through the same model's language side to give one 128-dimension vector per query token.

Retrieval then uses late interaction, the scoring from chapter 9: for each query token, find the page patch it matches best (dot product), and add up those best matches. This is called MaxSim. The name ColPali is the combination: Col for ColBERT's scoring, Pali for PaliGemma. Pages whose patches collectively cover the query's tokens score high, wherever on the page those patches are.

A toy you can run

A trained page encoder cannot be run here, so the program below is a deliberately small stand-in that keeps the structure and nothing else. A page is a list of patches. A text patch holds one word, and its vector is a hashed character-trigram embedding (the stand-in embedder of chapter 7). A drawing patch (a chart, a diagram, a photograph) holds no characters; a hand-written table says which concept words an image encoder would give it, to represent what a trained model learns from millions of pages. A drawing covers several patches, one per concept. Two pipelines are compared: the text route, which sees only the characters, and the visual route, which sees the drawings too. Both rank pages by MaxSim.

"""Stand-in for page-image retrieval. A page is a grid of patches; each patch holds a word or a drawing."""
import math, re, zlib
import numpy as np

DIM = 256
def vec(text):
    """Hashed character trigrams: a deterministic stand-in for a trained embedder."""
    v = np.zeros(DIM)
    t = f"  {text.lower()} "
    for i in range(len(t) - 2):
        v[zlib.crc32(t[i:i + 3].encode()) % DIM] += 1
    n = np.linalg.norm(v)
    return v / n if n else v

# What a trained image encoder would learn from millions of pages, written by hand for six drawings.
SEES = {"chart:rising": "revenue growth rising trend chart increase",
        "chart:falling": "sales decline falling trend chart decrease",
        "diagram:valve": "diagram valve sensor left pipe layout",
        "photo:crack": "photo crack damage weld defect"}

PAGES = {
 "p1": "hydraulic pump maintenance schedule every 500 hours replace filter".split(),
 "p2": "annual report region table chart:rising".split(),
 "p3": "quarterly summary north europe chart:falling".split(),
 "p4": "piping layout diagram:valve pump purchase order PO-88417 approved".split(),
 "p5": "inspection weld report photo:crack purchase order PO-88471 rejected".split(),
 "p6": "terms and conditions delivery payment thirty days notice".split(),
 "p7": "revenue recognition policy accounting standard".split(),
 "p8": "sales team contact list regional office".split(),
}
def patches(page, sees_images):
    out = []
    for p in PAGES[page]:
        if p not in SEES:
            out.append(vec(p))
        elif sees_images:                    # a drawing covers several patches, each carrying one concept
            out += [vec(w) for w in SEES[p].split()]
    return out

def maxsim(q_tokens, page, sees_images):
    P = np.array(patches(page, sees_images))
    Q = np.array([vec(t) for t in q_tokens])
    return float((Q @ P.T).max(axis=1).sum())          # best patch for each query token, summed

def rank(query, sees_images):
    q = query.split()
    return sorted(PAGES, key=lambda p: -maxsim(q, p, sees_images))

           ("sales trend falling", "p3"), ("where is the valve sensor", "p4"),
           ("order PO-88417", "p4"), ("weld crack photo", "p5")]

print(f"{'query':28s} {'answer':6s} {'text-only rank':15s} {'with images':12s}")
for q, gold in QUERIES:

    print(f"{q:28s} {gold:6s} {r_text.index(gold) + 1:<15d} {r_img.index(gold) + 1:<12d}")

The first query is answered from text, and both routes put page p1 first. The queries about the rising revenue, the falling sales and the valve sensor are answered only from drawings. The text route finds them at rank 2, 8 and 7 of 8, which is chance plus the noise of trigram overlap; the visual route finds all three at rank 1. The identifier query and the weld query use words that are printed on their pages, so both routes cope.

Look at the final lines, though. The query "order PO-88417" has a near-twin in page p5, which contains "PO-88471" (two digits swapped). The correct page scores a perfect 2.00. The near-miss scores 1.67, only 17% lower, because most of the trigrams of the two identifiers are shared, whereas an exact-token match separates them completely (1 against 0). This is not a defect of the toy. Dense and visual embeddings blur exact strings (part numbers, invoice numbers, clause references, names), which is why lexical matching earns its place beside them (chapter 10). A real page encoder has an extra problem: a part number printed in 6-point type may occupy a fraction of one patch, so the image model may not resolve its digits at all.

Analogy: two librarians

One librarian searches a typed transcript catalogue of the archive; she is fast and exact, and she has never seen a photograph or a graph, only what the transcriber chose to write about them. The other flips through the actual pages and recognises a rising line, a floor plan or a signature at a glance, but cannot reliably read small print across the room.

Where it breaks down: the second librarian's glance is learned from examples. She is excellent on document styles resembling her training and can be badly wrong on unfamiliar ones, in ways that are hard to see because nothing is written down for you to inspect.

What the model returns, and how it is trained

ColPali is trained with a contrastive objective of the kind in chapter 7: given pairs of a query and the page that answers it, make the MaxSim score of the right page higher than that of other pages in the batch. The training pairs are queries about page images; part of the training data is synthetic, with queries generated by a language model, and the authors released the models, data and benchmark under open licences. Because scoring is per query token against per patch, the model can also show where it matched: the patch with the highest similarity to each query token gives a heat map over the page. That is useful for the citation problem. A text pipeline can highlight a sentence; a visual retriever can highlight a region, which you can show to a reviewer or crop for a generator.

What it costs

A multi-vector page is large. A single dense vector for a page, as in chapter 7, might be 1,024 numbers. A page of ColPali is 1,024 vectors of 128 numbers. The next script does the arithmetic for a million pages, and for the search compute of one query done by brute force.

PAGES = 1_000_000
patches, dim, bytes_per = 1024, 128, 2          # ColPali: 1,024 patch vectors of 128 float16 numbers
multi = patches * dim * bytes_per
single = 1024 * 4                               # one 1,024-dimension float32 vector per page, for scale
print(f"multi-vector page: {multi:,} bytes = {multi / 1024:.0f} KiB   ->  {PAGES * multi / 1e9:,.0f} GB for {PAGES:,} pages")
print(f"one vector/page  : {single:,} bytes =    {single / 1024:.0f} KiB   ->  {PAGES * single / 1e9:,.1f} GB")
print(f"ratio: {multi / single:.0f}x")

q_tokens = 20
flops = 2 * q_tokens * patches * dim * PAGES     # brute-force MaxSim, one query, every page
print(f"\nbrute-force MaxSim, {q_tokens}-token query over {PAGES:,} pages: {flops / 1e12:.1f} TFLOP")
print(f"  compute on one CPU core at an assumed 50 GFLOP/s: {flops / 50e9:,.0f} s")
print(f"  just streaming {PAGES * multi / 1e9:,.0f} GB from memory at an assumed 100 GB/s: {PAGES * multi / 100e9:.1f} s")
cand = 1000
print(f"\nre-scoring only {cand} candidates from a cheap first stage: {2 * q_tokens * patches * dim * cand / 1e9:.1f} GFLOP")

The formula gives 256 KiB per page (the paper reports about 257.5 KB per page for ColPali, against about 8.6 KB for a BGE-M3 text embedding; the small difference from the formula presumably comes from how storage is counted, and the order of magnitude is what matters). A million pages is about a quarter of a terabyte of vectors, which has to sit in fast memory or be fetched quickly to rank anything. Brute-force scoring of one query against everything is five trillion operations and, more to the point, a stream of 262 GB through memory, so exhaustive MaxSim over a large corpus is out of the question. The standard answer is the one rerankers use (chapter 8): a cheap first stage proposes a thousand candidates, and MaxSim re-scores those, which is 5 GFLOP and entirely routine. The first stage can be BM25 on whatever text you have, a single-vector summary of each page, or an approximate nearest-neighbour index over the patch vectors (chapter 11).

Storage can also be reduced directly. Merging neighbouring patch vectors (pooling), dropping blank patches such as margins, shrinking the dimension and quantising to fewer bits all appear in the literature and in open implementations, and all trade accuracy for size. How much accuracy they cost depends on your documents, so measure it instead of reading a number from another corpus.

Systems connection

This is a memory-capacity and memory-bandwidth problem before it is a modelling problem. A scan over 262 GB is limited by how fast memory can feed the processors, the same constraint that governs the decode step of LLM serving (the KV cache) and the roofline reasoning in parallelism and GPUs. Two-stage designs, where a cheap stage bounds the work of an expensive one, are the standard answer to the latency budgets of tail latency: you pay the expensive scorer for a thousand items, not a million.

When visual beats text, and when it does not

SituationBetter routeWhy
Slide decks, infographics, postersVisualMeaning is carried by layout and graphics; text fragments are out of context.
Questions answered by a chart or diagramVisualThe answer is a shape, with no characters to extract.
Poor scans, mixed scripts, unusual fontsTest bothOCR may fail; a page encoder may still see the gist, or may not have seen such pages.
Long, dense, text-only pages (legal, contracts)TextSmall type across 1,024 patches loses detail; text is exact and cheap.
Exact identifiers, names, clause numbersText (lexical)Visual and dense vectors blur near-identical strings.
Very large corpora, tight memoryText, or visual with pooling and a first stageMulti-vector pages are tens of times larger.
Redacted or access-controlled contentWhichever you can controlA redaction must be applied to the pixels before encoding; the index then must not contain the hidden content (chapter 12).
Citations to a sentence or table cellText, or visual then parseVisual retrieval returns a page and a region, not a quotable string.

That last row points at a structural difference. Visual retrieval finds pages. To answer a question the generator then needs to read the page, either as an image (a VLM, which costs image tokens per page in context and shares the failure modes of chapter 19) or as text produced by OCR after retrieval. Some systems therefore do visual retrieval, then parse only the top few pages with the heavy parser (chapter 19), which saves most of the parsing cost while keeping a text answer to cite. Others run both indexes and fuse the results with reciprocal rank fusion, which is the safest design when you cannot yet say which route wins on which query.

State of play, October 2026

  • ColPali and its relatives. The original model used PaliGemma-3B. Later models in the same family replaced the backbone with other vision-language models; ColQwen2, for example, is built on Qwen2-VL-2B, limits a page to at most 768 patches and outputs 128-dimension vectors, and its adapters are published under the MIT licence (model card, read October 2026). New checkpoints appear every few months, so choose the current one from the leaderboard and re-test.
  • ViDoRe V3 (January 2026) is a larger benchmark: 10 datasets, about 26,000 pages and 3,099 human-verified queries, each available in 6 languages. Its authors report that visual retrievers beat textual ones, that late-interaction models and textual reranking help substantially, and that models still struggle with non-textual elements, open-ended queries and fine-grained visual grounding (arXiv 2601.08620).
  • The first ColPali paper reported 81.3 nDCG@5 on its ViDoRe benchmark against 67.0 for the best text pipeline it compared (parsing and captioning with BGE-M3). Both numbers are from the authors' own comparison and benchmark, on document types they selected.

Treat the direction as established and the margin as yours to measure: on text-dense corpora, a strong text pipeline narrows or reverses the gap.

Deciding for your corpus

The experiment that settles the question is small. Take 100 to 200 pages that represent the real corpus, including the awkward ones. Write queries for them the way users would, and label which page answers each. Tag every query with what the answer is made of: running text, a table, a chart or diagram, an identifier or exact string. Then build the text route and the visual route, and report page-level recall at 5 and nDCG@5 for each, per tag. The overall number will mislead you in either direction; the per-tag table tells you which route to use for which query type, and whether a hybrid of the two is worth its complexity. Add the storage per page, ingestion time per page and query latency. This is the method of chapter 5, with pages as the unit.

Common misconception

"Page-image retrieval makes OCR and parsing unnecessary." It moves the reading from ingestion to answer time. The generator still has to read the retrieved page, and if it is a VLM it makes the reading errors of chapter 19 on a page whose text you never extracted, never indexed and cannot search. You also lose the ability to quote, to filter on extracted fields (chapter 20) and to audit what the system thinks the page says. Visual retrieval is a different trade, not a free upgrade.

Key takeaways

  • The text route loses non-text content and layout, and compounds the errors of several stages. Visual retrieval embeds the page image directly, keeping what the page looks like.
  • ColPali-style models produce one vector per patch (1,024 patches of 128 numbers for ColPali) and score pages with MaxSim: each query token takes its best-matching patch, and the matches are summed.
  • The matches also locate evidence on the page, which supports region-level citation.
  • A page costs around 256 KiB of vectors, about 60 times a single dense vector, so brute-force search at scale is impractical. Use a cheap first stage with MaxSim to re-rank, and consider pooling and quantisation after measuring the loss.
  • Visual retrieval wins on slides, charts, diagrams and layout-heavy or poorly scanned pages. Text retrieval wins on dense text, exact identifiers, quotable citations and tight budgets.
  • Visual retrieval finds pages, not strings. The reading still has to happen somewhere, and hybrid designs run both routes.
  • Decide with a per-query-type evaluation on your own pages, not with a benchmark average.

Check your understanding

A user asks "in which quarter did output fall?" and the answer is shown only by the shape of a bar chart. Why does a text-extraction pipeline usually fail?

  1. Text embeddings cannot represent numbers
  2. The bar heights are not characters, so extraction keeps at most the title and axis labels and the answer is absent from the index
  3. BM25 cannot rank pages with fewer than 100 words
  4. OCR is too slow to run on charts
The information is graphical. Extraction can keep the chart's text but not what the bars encode, so no text retriever can find it, however good. Speed is not the issue, and embeddings and BM25 do handle numbers; they simply were never given this one.

In MaxSim scoring of a page, which statement is correct?

  1. The page vector is the average of all patch vectors, compared with the query vector
  2. Each patch picks the query token it matches best, and the matches are summed
  3. The query is converted into an image and compared pixel by pixel
  4. Each query token picks the page patch it matches best, and these best matches are summed
The maximum is taken over patches for each query token, then summed over tokens, which lets different tokens match different parts of the page. Averaging patches (option 1) would be the single-vector approach and loses this. The query is text and is not rendered.

A corpus of one million pages is to be indexed with 1,024 patch vectors of 128 float16 numbers per page. About how much memory do the vectors need?

  1. About 260 GB
  2. About 26 GB
  3. About 2.6 TB
  4. About 4 GB
1,024 × 128 × 2 bytes is 262,144 bytes per page, so a million pages is about 262 GB. Four gigabytes is the size of one 1,024-dimension float32 vector per page, which is the sixty-fold difference that makes multi-vector indexes expensive.

Users search a purchase-order archive mainly by exact order number, such as PO-88417. Which design is most sensible?

  1. Visual retrieval alone, since it is the newest approach
  2. A dense text embedding alone, since it understands meaning
  3. Lexical matching on extracted identifiers, optionally fused with a visual or dense route for the descriptive queries
  4. Brute-force MaxSim over every page for each query
Identifiers are exact strings, and the toy shows that dense and visual scores for a near-twin (PO-88471) are only slightly lower than for the true match. Lexical matching separates them cleanly. Fusing keeps the benefit of the other routes for queries that are not identifiers.

A team switches from OCR-based to page-image retrieval and reports that the system "no longer has OCR errors". What is the best response?

  1. Agree: with no extracted text there is nothing to get wrong
  2. Point out that reading still happens at answer time, when a model reads the retrieved page image, and the quotability, filtering and audit of extracted text are lost
  3. Point out that page-image retrieval cannot find any text at all
  4. Say that image embeddings are always less accurate than text
The reading moved, and with it the errors. Visual retrieval can find text content, so option 3 is wrong, and it often wins; option 4 overgeneralises. What changed is where the system can inspect and constrain what the page says.

You must pick between the text route and the visual route for an archive of 80,000 mixed documents. What evaluation is most likely to give a reliable decision?

  1. Pick the model with the highest score on a public benchmark
  2. Average page-level recall over 20 queries about contracts
  3. Label 150 queries on representative pages, tag each by answer type, and compare recall and nDCG@5 per tag, plus storage and latency
  4. Run both routes and keep the one that is faster
Per-type results on your own pages show where each route wins, which an average hides, and cost belongs in the decision. A benchmark average describes someone else's documents; 20 queries of one type misses the others; speed alone ignores whether the right pages are found.

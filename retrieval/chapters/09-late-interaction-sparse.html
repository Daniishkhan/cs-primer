Late Interaction & Learned Sparse

Chapter 7's single vector throws information away, and chapter 8's cross-encoder is too slow to run on a corpus. This chapter covers two designs that sit between them: ColBERT keeps one vector per token and scores with a cheap token-level match, and SPLADE lets a language model decide which words, including words the text never contained, go into an inverted index.

Why this matters

When a dense retriever misses exact terms, or a BM25 index misses paraphrases, teams often add a reranker. Two other options are worth knowing before you do. Late interaction models keep more of the document than one vector can, at a storage price you can compute in advance. Learned sparse models keep the cheap, explainable inverted index you already operate and give it semantic reach. After this chapter you can explain MaxSim and SPLADE's weighting in a few lines, estimate the index size of each, say what they do better and worse than the alternatives, and decide when the extra moving parts are justified.

Running the examples

Three ways to represent a passage

Every retriever so far reduces a passage to something an index can hold. BM25 stores terms with counts. A bi-encoder stores one dense vector. The two designs in this chapter pick different points in the same space.

Late interaction: ColBERT

Khattab and Zaharia ("ColBERT: Efficient and Effective Passage Search via Contextualized Late Interaction over BERT", 2020) started from the cost problem of chapter 8. A cross-encoder lets query and passage interact at every layer, so nothing can be precomputed. A bi-encoder postpones all interaction to one dot product, so everything can be, but the passage is squeezed into one vector. Late interaction is the middle position: encode query and passage separately, keep a vector for every token, and let them interact only at the end, with a cheap operation over those token vectors.

The operation is MaxSim. For each query token, find the passage token whose vector is most similar to it, and take that similarity. Then add up the results over the query tokens.

score(q, d) = ∑i in query tokens maxj in passage tokens ( qi · dj )

Each token vector is a short (ColBERT uses 128 numbers), length-normalised vector produced by the encoder, so every dot product is a cosine. The passage side can be computed offline and stored, exactly like a dense index. At query time the model encodes the query once, which costs one small forward pass, and then the scoring is only dot products and maxima: no Transformer pass per candidate.

The grid below is a real MaxSim computation, drawn from the listing that follows it. The rows are four query tokens, the columns are the tokens of passage d2 ("If a parcel arrives damaged, photograph the packaging and the item ..."), and each cell is a cosine similarity. The yellow outline marks each row's maximum; the right-hand column is what MaxSim keeps.

"""Late interaction with a stand-in token encoder: each token gets its own vector
(the LSA row for its stem, unit length). A trained model would make these contextual."""
import numpy as np
from common import *

def unit(v):
    n = np.linalg.norm(v)
    return v / n if n else v

K2 = 24                                          # more dimensions than the 7 used for whole-document vectors
TOK = {t: unit(Vt[:K2, VI[t]]) for t in VOCAB}

def token_matrix(text):
    ts = [t for t in terms(text) if t in TOK]
    return ts, np.stack([TOK[t] for t in ts])

def maxsim(query, doc_id, explain=False):
    qt, qm = token_matrix(query)
    dt, dm = token_matrix(DOCS[doc_id])
    sim = qm @ dm.T                                  # |q| x |d| token similarities
    best = sim.max(axis=1)                           # MaxSim: best doc token per query token
    if explain:
        for i, t in enumerate(qt):
            print(f"  {t:<10} -> {dt[np.round(sim[i], 4).argmax()]:<10} {best[i]:.2f}")
    return float(best.sum())

def single_vector(query, doc_id):
    qt, qm = token_matrix(query)
    dt, dm = token_matrix(DOCS[doc_id])
    return float(unit(qm.mean(0)) @ unit(dm.mean(0)))

        print(f"  MaxSim total {total:.2f}   single-vector cosine {single_vector(q, d):.2f}\n")

The listing compares the two passages that match different halves of the query "money back for a damaged parcel". Passage d2 (a damaged-parcel report) finds "damag" and "parcel" exactly. Passage r2 (a refund page) finds "money" and "back" exactly. MaxSim scores each query term by its single best partner, so the output is a score you can read, token by token. A single vector, in contrast, averages the whole passage into one point and gives one opaque number (0.80 and 0.88 here).

Analogy: a marking checklist

A teacher marks an essay against a checklist of required points. For each point, they search the essay for the best passage that covers it and give credit for the strongest evidence, wherever in the essay it sits. The total is the sum over checklist items. That is MaxSim: the query tokens are the checklist, the passage tokens are the essay, and the score is the sum of the best matches.

Where it breaks down: the teacher reads the essay as a whole and would notice that two points were satisfied by contradictory paragraphs. MaxSim never lets a passage token see the query, or the query tokens see each other's matches, so a passage that scatters the right words around unrelated sentences can score well. That is the gap a cross-encoder reranker closes.

Common misconception

"ColBERT is a cross-encoder with a cache." It is not. In a cross-encoder, every passage token attends to the query during encoding, so the passage representation depends on the query. In ColBERT, the passage vectors never see the query; they are identical for every query. Only the final scoring step compares them. That is why they can be stored, and also why ColBERT is less accurate than a good cross-encoder of the same size on hard pairs.

What it costs: storage

One vector per token is a lot of vectors. The ColBERTv2 paper (Santhanam et al., 2021) says late interaction models inflate the space footprint of retrieval "by an order of magnitude", and reports that ColBERTv2's residual compression cuts the footprint by 6 to 10 times. The residual trick: cluster all token vectors into centroids, then store for each token only the id of its nearest centroid plus a very coarse (one or two bits per dimension) encoding of the difference. The listing prices the options under stated assumptions; replace them with your own corpus.

# Index size per design. Every input is an ASSUMPTION (A); the paper's measured figure is quoted in the text.
passages   = 10_000_000   # A
tok_per    = 100          # A: average tokens per passage
dim_single = 768          # A: one dense vector per passage, float32
dim_token  = 128          # A: ColBERT-style per-token vector (a linear projection of the encoder output)
GB = 1e9

single      = passages * dim_single * 4
colbert_f16 = passages * tok_per * dim_token * 2          # every token vector stored in 16-bit floats
bits        = 2                                            # A: residual bits per dimension (ColBERTv2 style)
centroid_id = 4                                            # bytes: id of the nearest centroid
colbertv2   = passages * tok_per * (dim_token * bits / 8 + centroid_id)
splade_nnz  = 150                                          # A: non-zero terms per passage after expansion
splade      = passages * splade_nnz * (4 + 2)              # term id (4 B) + quantised weight (2 B) per posting

Under these assumptions, uncompressed ColBERT vectors take 8.3 times the space of a single-vector index (256 GB against 30.7 GB for ten million passages), and 2-bit residual compression brings that down by 7.1 times, inside the paper's 6 to 10 range. The remaining multiple over the single vector (36 GB against 30.7 GB) is small but the data must still sit in a token-level index, which is more complex to search than one vector per passage.

What it costs: search

Scoring every passage with MaxSim is a scan. Real systems do it in two steps. First, candidate generation: each query token vector probes an approximate nearest-neighbour index over all token vectors (chapter 11) and the passages that own the returned tokens become candidates. Second, exact MaxSim over those candidates. PLAID (Santhanam et al., 2022) speeds this up by working with the centroid ids first and discarding unpromising passages before the full computation; its authors report up to 7 times lower latency on a GPU and 45 times on a CPU compared with vanilla ColBERTv2 while keeping retrieval quality.

Systems connection

The index size is an operations number, not a modelling detail. 256 GB does not fit in the memory of one ordinary server; 36 GB does. Whether the token index lives in RAM, on SSD with memory mapping, or sharded across machines decides your latency and cost, in the same way as in specialised stores. Quantising stored values is the same trade as quantising model weights: fewer bits per number, more error, and a measurement to confirm the error does not matter for your queries.

Learned sparse retrieval: SPLADE

The other direction keeps the inverted index. BM25 (chapter 2) has two famous weaknesses: it can only match words that literally appear (vocabulary mismatch), and its term weights come from a fixed formula, not from what helps retrieval. A learned sparse model keeps the representation of BM25, a weight per vocabulary word, and lets a neural network produce those weights, including for words that are not in the text.

SPLADE (Formal, Piwowarski and Clinchant, 2021; "SPLADE: Sparse Lexical and Expansion Model for First Stage Ranking") does this with the masked-language-model head of BERT. When BERT is pre-trained, it reads a sentence with a word masked and predicts, for each position, a score over its whole vocabulary of about 30,000 word pieces: which words could fit here. SPLADE reuses those per-position scores. For an input text with tokens i and vocabulary words j, the weight of vocabulary word j is:

wj = maxi log( 1 + ReLU( logitij ) )
  • ReLU sets negative scores to zero. Most of the 30,000 words are unrelated to any input token, so most weights become exactly zero: that is what makes the vector sparse.
  • log(1 + x) squashes big scores, a log-saturation like BM25's term-frequency curve, so no single word dominates. The paper's abstract names this "log-saturation effect on term weights" along with explicit sparsity regularisation.
  • max over tokens pools the positions into one weight per vocabulary word. A word the text never contains can get a weight if some token strongly predicts it. That is the expansion.

The model is trained end to end with a ranking loss, plus a regulariser that penalises dense vectors. Without the regulariser, the network would learn to activate thousands of words and the inverted index would be slow. The later versions use a FLOPS-style penalty which, in Elastic's description of ELSER, adds a term to the loss for the expected retrieval cost. Documents and queries are both encoded, and the score is the dot product of two sparse vectors, which an inverted index computes exactly as it computes BM25: look up each query word's postings and accumulate the products.

The next listing reproduces that shape without a neural network. The "language-model head" is replaced by a small hand-written table of word associations (ASSOC), plus a self-prediction term proportional to the word's idf, standing in for the importance weighting a trained model learns. Read it as a diagram that runs, not as evidence about SPLADE's accuracy: I wrote the table after seeing the 12 queries, so it contains exactly the associations that help them, plus a couple of harmful ones ("card" suggests "gift"), and a trained head learns thousands of associations, many of them not synonyms. (Elastic's engineers make the same point about ELSER: the common explanation of learned sparse models as automatic synonym expansion is at best an oversimplification.)

"""SPLADE-shaped sparse encoder. Real SPLADE: w_j = max over input tokens i of
log(1 + ReLU(logit_ij)), logits from a trained masked-language-model head over the vocabulary.
Stand-in: the logits come from a small HAND-WRITTEN association table (see the text)."""
import math
from collections import defaultdict
from common import *

ASSOC = {                      # input word -> {vocabulary word: logit}, in the spirit of an MLM head
 "money": {"refund": 3.0, "reimburse": 2.4}, "back": {"refund": 2.2, "return": 2.0},
 "refund": {"reimburse": 3.2, "money": 2.6, "return": 2.4},
 "lost": {"lose": 3.0}, "phone": {"device": 2.8}, "charge": {"fee": 3.0},
 "paying": {"payment": 3.5, "pay": 3.0}, "baby": {"child": 2.6, "birth": 2.9, "parental": 2.5},
 "off": {"leave": 2.0}, "time": {"leave": 1.5}, "broken": {"damaged": 3.2}, "came": {"arrives": 2.6},
 "end": {"terminate": 3.3}, "contract": {"agreement": 3.0}, "card": {"gift": 1.2},
 "plan": {"price": 1.5}, "supplier": {"company": 1.0},
}
LOGIT = {}
for w, row in ASSOC.items():
    LOGIT[stem(w)] = {stem(k): v for k, v in row.items()}

def encode(text, prune=0.0):
    w = defaultdict(float)
    for t in terms(text):
        row = {t: 1.0 + 2.0 * idf(t), **LOGIT.get(t, {})}   # a token predicts itself; rarer words more strongly
        for j, logit in row.items():
            val = math.log1p(max(0.0, logit))           # log-saturation of ReLU(logit)
            w[j] = max(w[j], val)                        # max over input tokens
    return {j: v for j, v in w.items() if v > prune}

def build_index(prune):
    inv = defaultdict(list)
    for d in IDS:
        for t, wt in encode(DOCS[d], prune).items():
            inv[t].append((d, wt))
    return inv

def search(inv, q, prune):
    acc, touched = defaultdict(float), 0
    for t, wq in encode(q, prune).items():
        for d, wd in inv.get(t, []):
            acc[d] += wq * wd
            touched += 1
    return acc, touched

Three things to read from the output. The query "money back" now carries "refund", "reimburse" and "return", so it matches the refund pages even though neither query word is in "reimbursement". In a trained SPLADE model, the regulariser strength plays this role, and it is chosen by measuring the same two columns on your own data.

Strengths and costs of learned sparse

  • Operational fit. The index is an inverted index, so existing search engines serve it, with their filters, sharding and tooling.
  • Explainable. A hit can be explained by the shared words and their weights, and highlighted, which is hard with dense vectors.
  • Still lexical in shape. It can preserve exact identifiers better than a dense model. But expansion adds postings, so queries touch longer lists and are slower than plain BM25, and a rare identifier that tokenises into word pieces can be weighted oddly.
  • Needs a model at index time and query time. Documents are encoded when indexed, and queries are encoded when searched (a small cost), unless you use a variant that skips query encoding at some loss in quality.

The SPLADE-v3 report (Lassance et al., 2024) says its models are statistically significantly more effective than both BM25 and SPLADE++ on a meta-analysis over more than 40 query sets, reach more than 40 MRR@10 on the MS MARCO dev set, improve out-of-domain BEIR results by 2% over SPLADE++, and compare well with cross-encoder rerankers. These are the authors' reported results; run any such model on your own judged queries before relying on it.

State of play, October 2026

Late interaction and learned sparse are established, used in production by a minority of systems, and well supported by open models and libraries. Elastic ships a SPLADE-based learned sparse model (ELSER) in Elasticsearch, and BGE-M3 (Chen et al., 2024) is an open model that produces dense, sparse and multi-vector outputs from one forward pass for more than 100 languages and inputs up to 8,192 tokens. Late interaction has also found a second life for page images (chapter 21). I did not check current benchmark standings or the status of every engine's support, and both change often: look up the documentation for your engine and the model's licence before committing. The comparisons that matter are the ones you can run on your own queries with the harness from chapters 4 and 5.

Key takeaways

  • Late interaction encodes query and passage separately, keeps a vector for every token, and scores with MaxSim: for each query token the best passage-token cosine, summed. Passage vectors never see the query.
  • MaxSim is cheaper than a cross-encoder and more expressive than one vector, and its scores decompose into readable token matches. Its cost is index size: roughly 8 times a single-vector index uncompressed under the stated assumptions, 6 to 10 times smaller with ColBERTv2's residual compression.
  • Searching a token index is two steps: ANN candidate generation over token vectors, then exact MaxSim on the candidates (PLAID makes this much faster).
  • SPLADE turns the masked-language-model scores into sparse word weights with log(1 + ReLU) and max pooling, producing expansions with words the text never contained, and uses a regulariser to keep the vector sparse.
  • Learned sparse retrieval runs on an inverted index and is explainable, but expansion lengthens postings and can add wrong words; sparsity is a tunable trade between cost and effectiveness.
  • The four first-stage styles fail on different queries, so evaluate on your own judged queries and consider combining them (next chapter).

  • Santhanam et al., "PLAID: An Efficient Engine for Late Interaction Retrieval" (2022). Centroid interaction and pruning for much faster late-interaction search.

Check your understanding

What is the key difference between ColBERT and a cross-encoder?

  1. ColBERT uses BM25 for scoring
  2. ColBERT passages are encoded with the query so they attend to it
  3. ColBERT passage vectors are computed without seeing the query, so they can be stored; only the final token matching depends on the query
  4. ColBERT only works on short queries
In a cross-encoder, query and passage are one sequence, so passage representations change with the query and nothing can be precomputed. In ColBERT, passage token vectors are query-independent and stored; the query interacts only at MaxSim. The second option describes a cross-encoder.

A query has 4 tokens. Its best matches in a passage have cosines 0.9, 0.8, 0.2 and 0.1. What is the MaxSim score?

  1. 2.0
  2. 0.5
  3. 0.9
  4. 1.0
MaxSim sums the per-query-token maxima: 0.9 + 0.8 + 0.2 + 0.1 = 2.0. The mean would be 0.5 and the largest value 0.9. The score grows with query length, so scores are comparable between passages for one query, not across queries.

You index 20 million passages of 80 tokens each with 128-dimensional fp16 token vectors and no compression. Roughly how large is the vector data?

  1. About 4 GB
  2. About 20 GB
  3. About 40 GB
  4. About 400 GB
20,000,000 × 80 tokens × 128 dimensions × 2 bytes = 409.6 billion bytes, about 410 GB. A single 768-dimensional float32 vector per passage would be about 61 GB, so the multi-vector index is several times larger even before an index structure; compression is what makes it practical.

In SPLADE, why can a document receive a non-zero weight for a word that does not appear in its text?

  1. The index adds all synonyms from a thesaurus automatically
  2. The masked-language-model head scores every vocabulary word at every input position, and the max over positions can be positive for words that some token predicts
  3. The ReLU turns negative scores into the average score
  4. The inverted index stores neighbouring documents' words
The head outputs a logit for each vocabulary word at each position; after log(1 + ReLU) and the max, any word strongly predicted by some token has a weight. It is learned from ranking data, not a thesaurus, and (as Elastic notes) not simply synonyms. ReLU sets negatives to zero, not to an average.

You tighten the sparsity pruning of a learned sparse index so that queries touch half as many postings. Which outcome is most likely and what should you do?

  1. Quality is unchanged, because weak weights never matter
  2. Quality rises, because noise is removed
  3. Latency falls but some useful expansion terms, which tend to have weaker weights, are lost; measure nDCG and latency on judged queries before choosing the threshold
  4. The index becomes dense
The sweep in this chapter shows postings touched falling from 13.2 to 6.5 while nDCG@10 fell from 0.928 to 0.822: pruning removes cost and effectiveness together, and the best point depends on data. Always read both columns.

A team must keep their existing Lucene-based search engine with its filters and operations, but needs better matches for paraphrased queries and has no GPU budget for a reranker. Which option from this chapter fits best, and what is its main caveat?

  1. Learned sparse retrieval, because it uses an inverted index; the caveat is that expansion lengthens postings and the encoder must run at index and query time
  2. ColBERT with uncompressed vectors, because it needs no extra storage
  3. A cross-encoder over the whole corpus, because it is the most accurate
  4. A larger BM25 k1, which creates synonyms
Learned sparse models are served by inverted indexes, so they fit existing engines, though they still need a model to encode documents and queries. ColBERT needs a token-vector index and much more storage; a cross-encoder over the corpus is impossibly slow; BM25 parameters change weighting, not vocabulary.

Query Rewriting, Agentic Retrieval & GraphRAG

One question, one search, one answer works for questions that look like the documents. It breaks on follow-ups, on questions whose answer needs a chain of facts, and on questions about the whole collection. This chapter covers the three families of fixes (rewrite the query, search repeatedly, build a graph), what each costs, and how to tell which one your failures need.

Why this matters

Once a basic RAG system works (chapter 13) the next failures are not about chunking or embedders. Users type "and what about contractors?", ask who the boss of someone's boss is, or want the total across 40 documents. A single top-k search has no way to succeed at these, however well tuned. The fixes are tempting and expensive: every extra model call adds latency, cost and a new way to be wrong. After this chapter you can recognise the shape of the failure, pick the cheapest technique that addresses it, write the budget and stop conditions that keep a search loop from running away, and measure whether the technique paid for itself. It extends the pipeline of chapter 13, reuses the fusion of chapter 10, and leads towards the agent loops of deep research agents.

When one search is not enough

Four question shapes defeat a single retrieval, and each calls for a different tool.

Context-dependent"Who approved it, and when?" after a question about the Lisbon leaseThe query alone has no subject. The words it does have match other documents.Rewrite to a standalone query

Throughout the chapter we use one small, constructed knowledge base of 18 one-line company notes (corpus15.py: who approved which contract, who reports to whom, department budgets), searched by the same hybrid retriever as before (BM25 plus a stand-in trigram vector, fused with reciprocal rank fusion; search15.py). Eighteen notes are enough to show the mechanisms; they say nothing about how often each failure occurs in a real collection, which is something only your own logs can tell you.

Query rewriting

Query rewriting uses a language model to turn the user's words into queries that retrieve better. It happens before retrieval, so it composes with everything else in the pipeline. Ma et al., "Query Rewriting for Retrieval-Augmented Large Language Models" (2023), formalised the "rewrite, retrieve, read" pattern. The common forms:

  • Standalone (condensed) question. The model reads the conversation and rewrites the last message so that it makes sense alone: "Who approved it, and when?" becomes "Who approved the Lisbon office lease, and when?". Almost every chat-style RAG system needs this, because the embedder and BM25 see only the string they are given.
  • Multi-query. Ask for several differently worded versions, search each, and fuse the lists. It targets vocabulary gaps: one of the phrasings may share words with the document.
  • Hypothetical answer (HyDE). Gao et al., "Precise Zero-Shot Dense Retrieval without Relevance Labels" (2022), had a model write a plausible answer passage, embedded that instead of the question, and retrieved real documents nearest to it. A question and its answer often look different in embedding space; two answer-like passages look alike. The draft may contain false facts, so it is used only to find documents and never shown as an answer.
  • Step-back. Zheng et al., "Take a Step Back: Evoking Reasoning via Abstraction in Large Language Models" (2023), ask a more general question first ("What are the rules on working abroad?" before "Can I work from Spain for a month?"). Retrieval of the general principle can succeed where the specific query matches nothing.
  • Independent sub-questions. "Compare the Facilities and Platform budgets" splits into two searches that do not depend on each other. (Questions whose parts do depend on each other need the loop in the next section.)

The listing runs the first two on the knowledge base. The rewriter is a ScriptedModel from the course's llm.py: its replies are written in advance to be what a good model would return, so what is real is the retrieval that follows.

"""Query rewriting: make a follow-up standalone, then fan out into several queries (chapter 15)."""
from search15 import *
from llm import ScriptedModel, text_of
import json

def rrf(lists, k=60):
    s = Counter()
    for lst in lists:
        for r, d in enumerate(lst, 1): s[d] += 1 / (k + r)
    return [d for d, _ in s.most_common()]

# The rewriter is a ScriptedModel: its replies are what a good model would return for this prompt.
REWRITER = ScriptedModel([
    "Who approved the Lisbon office lease, and when?",
    json.dumps(["Which supplier provides cooling equipment for the Oslo data-centre contract?",
                "Who supplies the chillers for the Norway data centre?",
                "vendor of cooling equipment, Oslo"]),
])
SYSTEM = "Rewrite the user's last message as one standalone search query, using the conversation."

history = [("user", "Tell me about the Lisbon office lease."), ("assistant", "It was approved earlier this year."),
           ("user", "Who approved it, and when?")]
literal = history[-1][1]
standalone = text_of(REWRITER.complete([{"role": "user", "content": json.dumps(history)}], system=SYSTEM))
print("follow-up as typed :", literal, "->", search(literal, 3))
print("rewritten          :", standalone, "->", search(standalone, 3))
print("(the answer is in n06)\n")

variants = json.loads(text_of(REWRITER.complete([{"role": "user", "content": "Write 3 differently worded search queries for: " + q}])))
print("one query          :", search(q, 3), " (answer is in n04)")
for v in variants: print("  variant          :", search(v, 3), v)
print("fused, 3 variants only      :", rrf([search(x, 5) for x in variants])[:3])
print("fused, original + 3 variants :", rrf([search(x, 5) for x in [q] + variants])[:3])

Three things to read from the output. First, in the follow-up case, the literal query still finds the right note first (lucky: "approved" and "when" match its text), but also drags in n01, the Oslo contract, as number two. After the rewrite, the Oslo note is gone from the top three. The rewrite removed an ambiguity that was waiting to cause a wrong answer on a larger collection.

Second, the vocabulary gap is real: the original query finds three irrelevant notes, none of them the answer n04. Each of the three rewrites puts n04 in the top two. Third, the last two lines are a warning: fusing the original query with the good variants made the result worse (n04 fell from first to third, behind a note the bad original query promoted). Fusion treats every list as an equal voice, so one poor list counts as much as a good one. Keep the original query in the mix when it contains identifiers or exact phrases that a rewrite could lose, but when you know the original is weak, weight it down.

Common misconception

"Rewriting can only help, because the model understands the question better than the retriever." A rewrite is a second chance to lose information. Models drop product codes and error numbers, silently normalise "not" away, widen a narrow date range, or inject a plausible entity that was never in the question. The checks that matter: log the original and rewritten query side by side, compare retrieval with and without the rewrite on a judged set (chapter 5), and keep exact tokens (IDs, quoted strings, numbers) verbatim in at least one query. The same principle that makes query understanding hard for classic search applies here.

Iterative and agentic retrieval

Rewrites can all be written before the first search. Some questions cannot be planned that way, because the second query depends on what the first returned. "What is the job title of the boss of the boss of the Aurora project lead?" needs the lead's name (from one note), then that person's manager (from another), then that manager's manager, then a title. The query for step two literally contains the answer to step one. These are multi-hop questions; HotpotQA (Yang et al., 2018) is the best-known benchmark for them.

The remedy is a loop: search, read, decide what is still missing, search again, and stop when there is enough. Trivedi et al., "Interleaving Retrieval with Chain-of-Thought Reasoning for Knowledge-Intensive Multi-Step Questions" (IRCoT, 2022), interleaved reasoning steps with retrieval in exactly this way. In current practice the loop is agentic retrieval: search is a tool (the tool-calling loop) that the model calls as many times as it judges necessary, within a budget.

The next listing runs this loop on three questions and compares it with a single search. The loop's decisions come from a small policy function standing in for the model's reasoning: it reads the latest search results, extracts the name it needs and writes the next query. A real model does that with language understanding rather than regular expressions, but the structure, the retrieval and the accounting are the same. ScriptedModel records every request, so the input-token totals are real counts under the course's four-characters-per-token estimate.

"""Single-shot retrieval versus an iterative search loop on multi-hop questions (chapter 15)."""
import re
from search15 import *
from llm import ScriptedModel, tool_use, tool_result, tool_calls, text_of

SEARCH_TOOL = {"name": "search", "description": "Search the company notes; returns the top 2 notes.",
               "input_schema": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}}

def make_policy(first_query, entity, hops, title=False):
    """A stand-in for the model's reasoning: read the latest observation, choose the next query.
    entity = the thing the first note must mention; hops = how many 'reports to' links to follow."""
    st = {"phase": 0, "name": None, "left": hops, "misses": 0}
    def policy(messages, tools, system):
        if st["phase"] == 0:
            st["phase"] = 1
            return [tool_use("search", {"query": first_query})]
        lines = " ".join(b["content"] for b in messages[-1]["content"]).split("\n")
        if st["phase"] == 1:
            for ln in lines:
                if entity in ln and (m := re.search(r"(?:approved by|project lead is) ([A-Z]\w+ [A-Z]\w+)", ln)):
                    st["name"], st["phase"] = m.group(1), 2
                    return [tool_use("search", {"query": f"{st['name']} reports to"})]
        elif st["phase"] == 2:
            for ln in lines:
                if st["name"] in ln and (m := re.search(r"reports to ([A-Z]\w+ [A-Z]\w+)", ln)):
                    st["name"], st["left"] = m.group(1), st["left"] - 1
                    if st["left"] > 0:
                        return [tool_use("search", {"query": f"{st['name']} reports to"})]
                    if not title:
                        return f"{st['name']}."
                    st["phase"] = 3
                    return [tool_use("search", {"query": f"{st['name']} job title"})]
        elif st["phase"] == 3:
            for ln in lines:
                if st["name"] in ln and (m := re.search(r"is the ([\w ]+)\.", ln)):
                    return f"{m.group(1)}."
        st["misses"] += 1
        if st["misses"] == 1:
            return [tool_use("search", {"query": first_query + " who"})]
        return "I could not find that in the notes."
    return policy

def run(question, policy, max_searches=5):
    model = ScriptedModel(policy); msgs = [{"role": "user", "content": question}]
    n_search = tokens_in = 0; seen = []
    while True:
        r = model.complete(msgs, tools=[SEARCH_TOOL]); tokens_in += r.usage["input_tokens"]
        calls = tool_calls(r)
        if not calls: return text_of(r), n_search, tokens_in, seen
        msgs.append(r.as_message()); results = []
        for c in calls:
            if n_search >= max_searches: results.append(tool_result(c["id"], "search budget used up")); continue
            n_search += 1; hits = search(c["input"]["query"], 2); seen += hits
            print(f"    search {n_search}: {c['input']['query']!r:<42} -> {hits}")
            results.append(tool_result(c["id"], "\n".join(f"[{d}] {DOCS[d]}" for d in hits)))
        msgs.append({"role": "user", "content": results})

CASES = [
 ("Who does the person who approved the Oslo contract report to?", {"n01", "n02"},
  make_policy("Oslo contract approved", "Oslo", 1)),
 ("What is the job title of the boss of the boss of the Aurora project lead?", {"n08", "n09", "n10", "n03"},
  make_policy("Aurora project lead", "Aurora", 2, title=True)),
 ("Who does the person who approved the Paris contract report to?", set(),
  make_policy("Paris contract approved", "Paris", 1)),
]
if __name__ == "__main__":
    for question, gold, policy in CASES:
        print(question + ("" if gold else "   [no note about Paris exists]"))
        if gold:
            for k in (3, 5):
                got = set(search(question, k))
                print(f"  one search, k={k}: finds {len(gold & got)} of {len(gold)} needed notes {sorted(gold & got)}")
        print("  search loop:")
        answer, n, tokens, seen = run(question, policy)
        found = f", needed notes found: {len(gold & set(seen))} of {len(gold)}" if gold else ""
        print(f"    answer: {answer}")
        print(f"    {n} searches, {tokens} input tokens in total{found}\n")

What the output teaches:

  • Bigger k rescues a short chain but not a long one. For the two-hop question, a single search with k = 5 happens to include both needed notes (not with k = 3). For the four-note question it finds one of four at any k tried, because three of the four notes share no words with the question: "boss of the boss" appears nowhere in the data.
  • The loop found all four notes in four searches and the right title. That is four searches plus a final reasoning step, at 812 input tokens in total, because each call re-sends the growing conversation. The cost is superlinear in the number of steps if you keep appending, one reason loops compress or drop old tool results (context engineering).
  • The Paris case is the one to study. The question mentions a contract that does not exist. The first search returns the Oslo contract notes (the nearest thing), and the loop correctly does not accept them, because the note does not mention Paris. It retries once with a rewritten query and then stops with "I could not find that." A naive loop would have followed the Oslo note's approver and answered with confidence about the wrong contract. The check was a single condition (entity in line); in a real system it is part of the prompt and of the verification of chapter 16.

What keeps a loop honest

  1. A hard budget. Cap the number of searches, tokens and seconds; return what you have when it is spent (the example caps at five). Anthropic's description of its multi-agent research system reports that early versions over-invested effort on simple queries (spawning dozens of sub-agents for a simple fact) and fixed it by writing explicit effort rules into the prompts: roughly one agent and a handful of tool calls for a simple fact, a few sub-agents for a comparison, many for open-ended research. Match effort to the question.
  2. A stop condition that is checked, not assumed. "I have enough" is a claim. Require the final answer to cite the notes it used and check that the cited text supports it.
  3. Loop detection. Models repeat themselves. If a query is identical (or near-identical) to an earlier one, refuse it and tell the model so. Stand-in policies like ours fell into this trap during development.
  4. The same permissions on every call. Each search the loop makes runs under the end user's principal and filters (chapter 12). A loop that holds a service account can wander into documents the user could not have searched for directly.
  5. Trace everything. Log each query, its results and the reason for the next step (tracing for LLM systems), so a wrong answer can be diagnosed by finding the first bad step.

Retrieve at all? And how much?

Not every question needs retrieval, and not every retrieval needs a loop. Asai et al., "Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection" (2023), train a model to decide when to retrieve and to critique its own passages. Jeong et al., "Adaptive-RAG" (2024), train a small classifier to route a question by its complexity: no retrieval, one retrieval, or iterative. A cheap router built on your query logs does most of the work: greetings and arithmetic skip retrieval; simple lookups take the single-search path; only questions that look multi-part or comparative go to the loop. The goal is that the average question pays for one search, and only the hard ones pay for four.

Analogy: the reference librarian

A good reference librarian does not run your sentence through the catalogue. They ask what you mean by "it" (rewrite), try a few synonyms when the first term gets nothing (variants), and when you ask who the boss of the boss is, they look up the first person, then the next, then the next, without fetching all the books at once (loop). They also stop after a few tries and tell you the library does not have it (budget and abstention).

Where it breaks down: a librarian recognises when the first search returned the wrong thing and is embarrassed to carry on. A model that has been told to answer will often carry on with a plausible bridge unless the loop forces it to check.

Knowledge graphs and GraphRAG

The loop finds chains by searching text repeatedly. The alternative is to find the chain once, at indexing time, and store it. A knowledge graph holds facts as triples: (subject, relation, object), such as (Priya Nair, reports_to, Chen Wu). Subjects and objects are nodes; relations are labelled edges. A multi-hop question becomes a walk along edges, which is cheap and exact once the edges exist. The hard part is building them: extracting triples from prose is typically done with a language model, one call per chunk, and resolving mentions ("Chen", "C. Wu", "the head of Platform") into one node is its own problem, entity resolution.

The listing builds a graph from the same 18 notes with regular expressions standing in for LLM extraction, and tries four things: a multi-hop walk, an aggregation, a deliberately missed fact, and the cost of building at scale.

"""A knowledge graph from the notes: triples, multi-hop paths, aggregation, and a silent miss (chapter 15)."""
import re
from collections import defaultdict
from corpus15 import DOCS
from search15 import search

# Stand-in for LLM extraction: regular expressions that find (subject, relation, object) in each note.
def extract(note_id, text):
    triples, subject = [], None
    for sent in re.split(r"(?<=\.) ", text):
        if m := re.match(r"The (.+?) was approved by ([A-Z]\w+ [A-Z]\w+)", sent):
            triples.append((m.group(1), "approved_by", m.group(2)))
        elif m := re.match(r"([A-Z]\w+ [A-Z]\w+) is the head of (\w+)", sent):
            subject = m.group(1); triples.append((subject, "head_of", m.group(2)))
        elif m := re.match(r"([A-Z]\w+ [A-Z]\w+) is a senior engineer in (\w+)", sent):
            subject = m.group(1); triples.append((subject, "member_of", m.group(2)))
        elif m := re.match(r"([A-Z]\w+ [A-Z]\w+) is the (chief [\w ]+)\.", sent):
            triples.append((m.group(1), "title", m.group(2)))
        elif (m := re.match(r"(?:She|He) reports to ([A-Z]\w+ [A-Z]\w+)", sent)) and subject:
            triples.append((subject, "reports_to", m.group(1)))
        elif m := re.match(r"The (\w+) budget for 2025 is (\d+) million euros", sent):
            triples.append((m.group(1), "budget_m", int(m.group(2))))
        elif m := re.match(r"Project (\w+) .*?project lead is ([A-Z]\w+ [A-Z]\w+)", " ".join(text.split(". "))):
            triples.append(("Project " + m.group(1), "lead", m.group(2)))
    return [(s, r, o, note_id) for s, r, o in triples]

def build(docs):
    g = defaultdict(dict)                               # subject -> relation -> (object, source note)
    for nid, text in docs.items():
        for s, r, o, src in extract(nid, text): g[s][r] = (o, src)
    return g

G = build(DOCS)
print(f"{sum(len(v) for v in G.values())} edges from {len(DOCS)} notes; e.g. Priya Nair ->", {r: o for r, (o, _) in G["Priya Nair"].items()}, "\n")

# 1. Multi-hop by walking edges: no search at query time.
node, path = "Project Aurora", []
for rel in ("lead", "reports_to", "reports_to", "title"):
    obj, src = G[node][rel]; path.append(f"{node} -{rel}-> {obj} [{src}]"); node = obj
print("Q: job title of the boss of the boss of the Aurora lead")
print("\n".join("   " + p for p in path)); print("   answer:", node, "\n")

# 2. Aggregation: a question about the whole collection.
budgets = {s: r["budget_m"][0] for s, r in G.items() if "budget_m" in r}
print("Q: total 2025 budget across all departments")
top = [d for d in search("total 2025 budget across all departments", 3)]
print("   top-3 retrieval sees:", top, "-> sum", sum(int(re.search(r"is (\d+) million", DOCS[d]).group(1)) for d in top if "budget" in DOCS[d]))
print("   graph over all notes :", budgets, "-> sum", sum(budgets.values()), "\n")

# 3. The silent miss: a reorganisation note the extractor's patterns do not recognise.
DOCS2 = dict(DOCS, n19="Following the reorganisation, Tomas Reis now answers to Chen Wu.")
G2 = build(DOCS2)
print("Q: who does Tomas Reis report to?")
print("   graph answer :", G2["Tomas Reis"]["reports_to"][0], "(from", G2["Tomas Reis"]["reports_to"][1] + ", out of date)")
print("   edges extracted from the new note n19:", extract("n19", DOCS2["n19"]), "(the pattern 'reports to' never matched 'answers to')")

print("\nindexing cost of one extraction call per chunk (assumed: 600-token chunks, 500-token prompt, 300 tokens out,")

The walk answers the four-hop question with no search at query time and with a source note on every step. The aggregation question shows the other strength: top-3 retrieval saw three of the six budget notes and summed to 18, while the graph, which holds all six budgets as edges, gives 37. This is a coverage problem, not a ranking one (retrieval of the top few is the wrong operation for "all"); a SQL-like aggregation over extracted fields solves it, and a graph is one way to hold those fields.

The third block is the price. A reorganisation note says Tomas Reis "now answers to Chen Wu". The extractor's pattern did not recognise "answers to", so no edge was created, and the graph confidently reports the old manager with a source note that is out of date. This is the characteristic failure of graph methods: a missed extraction is silent, whereas a text search over the new note would at least have a chance of finding it. Real LLM extractors are better than regular expressions, but they miss and mislabel too, and the errors compound across hops.

The last block shows that for a small model the indexing bill is moderate (about $1 per million tokens of corpus, under the assumed prices; recompute with current ones), so cost is rarely the real obstacle. The obstacles are quality (extraction recall, entity resolution), freshness (every edit must update edges, and deleting a document must delete its edges) and permissions: an edge such as (Project X, approved_by, Alice) is itself information, and its source note carries an access level. The graph needs the same ACL stamping as chunks, and a path that passes through a restricted note must be cut for users who cannot read it (chapter 12).

GraphRAG and its relatives

Edge et al., "From Local to Global: A Graph RAG Approach to Query-Focused Summarization" (Microsoft Research, 2024), target the fourth question shape. They argue that standard RAG fails on global questions over a whole corpus ("what are the main themes?"), which are really summarisation tasks. Their GraphRAG uses an LLM to extract an entity graph from the documents, groups closely related entities into communities, and pre-writes a summary for each community. At question time each community summary produces a partial answer, and the partial answers are combined into a final one. On question sets over corpora of roughly a million tokens, the authors report substantial gains over a conventional RAG baseline in the comprehensiveness and diversity of answers; the price is a heavy indexing step, and the benefit is largest for exactly the global questions that ordinary retrieval cannot answer.

Related designs trade differently. HippoRAG (Gutiérrez et al., 2024) builds a graph from extracted triples and ranks documents with personalised PageRank starting from the entities in the question, which targets multi-hop questions without an LLM loop at query time. RAPTOR (Sarthi et al., 2024) clusters chunks and recursively summarises them into a tree, so a query can match at different levels of abstraction. All three move work from query time to indexing time, and all three inherit the maintenance burden of a derived structure that must be kept in step with the documents.

The row that matters most is the last one. A sensible order of work: log real questions; classify failures into the four shapes (the failure triage of chapter 13 and chapter 17 helps); apply the cheapest technique that addresses the most frequent shape; measure with and without it on a judged set that contains enough questions of that shape; and report cost and tail latency next to quality. Adding a loop because "agents are the future" and finding that 3% of your questions needed it is a poor trade.

Systems connection

A search loop is serial: latency adds across steps, so four steps of 800 ms is over three seconds before any answer is written, and its tail is worse than the average (tail latency at scale). Parallel techniques (multi-query, sub-questions) keep latency near the slowest search but multiply load on the index, which matters under load (overload and load shedding). Loops need the durability thinking of durable execution if a request can run for minutes, and a retry of a half-finished loop must not repeat side effects. Anthropic reports that its multi-agent research system used about 15 times the tokens of a chat interaction (agents alone about 4 times), so the bill, not only the latency, grows with every added hop.

State of play, October 2026

The vocabulary is unsettled. Many products now describe retrieval that a model drives over several steps as "agentic retrieval" or "deep research", and "GraphRAG" is used both for Microsoft's specific method and loosely for any graph-assisted retrieval. Read the details before comparing claims. Verified for this chapter: the GraphRAG paper (arXiv 2404.16130, revised February 2025) and Anthropic's engineering write-up of its multi-agent research system, which reports that a lead agent with parallel sub-agents outperformed a single agent by 90.2% on its internal research evaluation, at roughly 15 times the tokens of a chat. Both are the authors' own measurements on their own tasks. Treat benchmark gains as hypotheses to test on your data, and prefer the cheapest technique that fixes your measured failures.

Key takeaways

  • Four question shapes defeat a single search: context-dependent, vocabulary-gapped, multi-hop and global. Name the shape before choosing the fix.
  • Rewriting (standalone, multi-query, HyDE, step-back, sub-questions) is cheap and parallel but can lose identifiers and constraints. Keep exact tokens, log both queries, and weight weak lists down in fusion.
  • When the next query depends on the last result, you need a loop. Give it a search budget, a checked stop condition, loop detection, the user's permissions on every call and a trace.
  • A larger k can rescue a two-hop question and will not rescue a longer chain.
  • Knowledge graphs move the chain-finding to indexing time and give exact multi-hop and aggregation answers with sources, but extraction misses are silent and edges need ACLs and updates.
  • GraphRAG-style community summaries target global questions; they cost heavily at indexing and are worth it only where such questions are common.
  • Pick the cheapest technique that fixes your measured failures, and report quality, cost and latency together.

Check your understanding

A chat assistant answers "And what about contractors?" with irrelevant text. Which fix addresses the cause most directly?

  1. Rewrite the last message into a standalone question using the conversation, and retrieve with that.
  2. Increase the number of chunks retrieved.
  3. Switch to a larger embedding model.
  4. Build a knowledge graph of the policy documents.
The retriever sees only the string it is given, and "And what about contractors?" has no subject. Resolving the reference restores it. More chunks, a better embedder or a graph all still receive the same subjectless query.

You fuse the results of the original query with three good rewrites by reciprocal rank fusion, and the right document drops from first to third. What is the most likely cause, and a reasonable response?

  1. RRF is broken; use raw scores instead.
  2. The rewrites were too similar; remove two of them.
  3. The original query returned a poor list that RRF treats as an equal vote; weight it down or exclude it when it is known to be weak, while keeping exact identifiers in some query.
  4. The right document is not in the index.
RRF gives each list the same voice unless you weight it. A poor original list promotes its own favourites. Raw scores are not comparable across queries (chapter 10). The document was in every variant's top two, so it is indexed.

"Who is the boss of the boss of the Aurora lead?" A single search with k = 10 returns the Aurora note and nothing useful about management. Why is retrieving more chunks unlikely to be a reliable fix?

  1. Models cannot read more than three chunks.
  2. The other notes in the chain do not resemble the question, so no k within reason is guaranteed to include them; the next query depends on what the first search returns.
  3. BM25 cannot handle names.
  4. Vector search is not allowed to return the same document twice.
The later hops share no words with the question; their relevance only becomes visible once you know the earlier answer (the lead's name). That dependency is why iterative retrieval or a graph is needed. A larger k can work by chance for a short chain, as the chapter's two-hop example showed, but it does not scale to longer chains.

A search loop is asked about a "Paris contract" that does not exist. The first search returns notes about the Oslo contract. What should a well-built loop do?

  1. Follow the Oslo approver, since it is the closest match.
  2. Keep searching with the same query until the budget is spent.
  3. Answer from the model's own knowledge of Paris.
  4. Notice that the retrieved note does not mention Paris, retry at most once with a reformulation, then stop and say the information was not found.
The nearest match is not the right entity. Accepting it yields a confident answer about the wrong contract. Repeating an identical query wastes the budget, and answering from memory abandons the grounding that RAG exists to provide.

Which question is best suited to GraphRAG-style community summaries rather than to a search loop?

  1. "What are the main themes across these 4,000 incident reports?"
  2. "What is the refund window for subscriptions?"
  3. "Who approved the Oslo contract?"
  4. "What does error E4021 mean?"
The first is a global, thematic question whose answer is spread over the whole corpus; summaries built at indexing time can be combined into an answer. The others are lookups that one targeted search handles at far lower cost.

A regular-expression extractor builds a knowledge graph from notes. A reorganisation note says "Tomas now answers to Chen." and the extractor's patterns look for "reports to". What happens, and what does it show about graph methods?

  1. The graph raises an error, so the problem is found immediately.
  2. No edge is created; the graph keeps returning the old manager with an old source, silently. Missed extractions give wrong answers without any signal.
  3. The graph automatically infers the new edge from context.
  4. Nothing: a graph is always more accurate than text search.
A graph answers from the edges that exist. When extraction misses a fact, the older edge stands unchallenged. LLM-based extraction misses less than regular expressions but not never, so graph systems need extraction-quality measurements, updates on edits, and often a text-search fallback.

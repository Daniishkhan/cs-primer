Start Here

A language model answers from what it is shown. Search, retrieval and retrieval-augmented generation are the craft of choosing what to show it, from collections of documents that are long, messy and often not text at all. This chapter maps the course and gives you a first taste of the core problem.

Why this matters

Most useful AI systems are not asked to recall the world; they are asked about your policies, contracts, tickets, papers, invoices and code. A model has never seen those, so the system must fetch the right evidence and hand it over. When such a system gives a wrong answer, the cause is more often the evidence than the model. After this course you will be able to build the retrieval half properly, measure it, and trace a bad answer back to the stage that caused it.

Three words that are often confused

Search is the product a person uses: they type a query and read a ranked list of results. Retrieval is the machinery underneath: given a query, return the most relevant items from a collection, in order. Retrieval-augmented generation (RAG) puts a language model behind retrieval: fetch passages first, then ask the model to write an answer from them, ideally with citations. The name comes from Lewis et al. (2020), "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks", though the idea of looking things up before answering is older than language models.

Search is old. Library catalogues, the index at the back of a textbook and the 1970s and 1980s work on ranking documents by term statistics all belong to the same family. What changed recently is not the problem but the consumer. A person scanning ten blue links forgives a mediocre ranking. A model that receives the top five passages treats them as the truth, and a reader of its answer cannot see which passages it was given. That raises the standard for retrieval and makes measuring it unavoidable.

The whole system in one picture

Every system in this course is a variation on the same pipeline. Documents are parsed into text, cut into pieces, analysed and indexed ahead of time. At question time the query is run against the index, the best candidates are re-ordered, and a model writes an answer that points back at its sources.

Why retrieval is most of the work

Think of the generator as a very capable student sitting an open-book exam. The student writes well, but can only use the pages placed on the desk. If the page holding the answer is not there, even the best student will either say nothing useful or, worse, write something plausible. This gives two ceilings:

  • Recall ceiling. If the right evidence is not among the retrieved passages, the answer cannot be right, whatever the model. Retrieval quality caps answer quality.
  • Noise floor. If the right evidence is there but buried among irrelevant passages, models can still miss it or be misled. Measured effects of this (the "Lost in the Middle" study by Liu et al., 2023) get their own case study in this course.

That is why this course spends four parts on retrieval and measurement before it reaches generation, and why debugging a RAG system starts by reading what was retrieved, not by rewriting the prompt.

A first taste: a tiny retriever and its two failures

Here is a complete retriever in about twenty lines, over six snippets of a shop's help pages. It counts query words that appear in each document, weighting rarer words more (the idea behind inverse document frequency, which chapter 2 derives properly). Each result carries its document id, which is what a later citation will point at.

import math, re
from collections import Counter

DOCS = {
    "policy-3": "Refunds are issued to the original payment method within 10 working days of approval.",
    "policy-7": "Damaged items can be returned free of charge within 30 days of delivery.",
    "faq-12":   "To change your delivery address, contact support before the order is dispatched.",
    "faq-15":   "Gift cards cannot be redeemed for cash and are not refundable.",
    "terms-2":  "We may update these terms at any time; continued use means you accept the changes.",
    "faq-20":   "Orders are dispatched within two working days. Tracking links are sent by email.",
}
STOP = {"the", "to", "of", "a", "is", "are", "for", "my", "i", "can", "be", "and", "or", "at", "by", "your", "we", "any", "do", "how", "get"}
tok = lambda s: [w for w in re.findall(r"[a-z]+", s.lower()) if w not in STOP]

docs = {d: Counter(tok(t)) for d, t in DOCS.items()}
df = Counter(w for c in docs.values() for w in c)

def retrieve(query, k=3):
    scores = {}
    for d, c in docs.items():
        s = sum(c[w] * math.log(1 + len(docs) / df[w]) for w in tok(query) if w in c)
        if s: scores[d] = round(s, 2)
    return sorted(scores.items(), key=lambda x: -x[1])[:k]

for q in ["when are refunds paid", "return damaged items", "get my money back", "can I cancel my order"]:
    print(f"{q!r:<26} -> {retrieve(q)}")
'when are refunds paid'    -> [('policy-3', 1.95)]
'return damaged items'     -> [('policy-7', 3.89)]
'get my money back'        -> []
'can I cancel my order'    -> [('faq-12', 1.95)]

Two queries work. Two do not, in different ways. "get my money back" returns nothing: the user means a refund, but shares no word with the document that explains refunds. This is the vocabulary mismatch problem, and it is the reason dense retrieval (Part 3) exists. "can I cancel my order" is worse: it returns a confident wrong answer, because the shop has no cancellation page and the word "order" matched an unrelated one. A generator handed faq-12 would happily write a cancellation procedure that does not exist. Retrieval systems must be able to say "nothing relevant", which is a measurement and design question taken up in Part 5.

Common misconception

"RAG means a vector database." Vectors are one retrieval technique among several. Plain keyword scoring (BM25) is a strong baseline that beats many embedding models on exact names, codes and rare terms, and the best production systems usually combine both. Which one wins on your documents is something you measure, not something you decide in advance.

The documents are the hard part

Tutorials start with clean text. Real collections start with a scanned contract with a coffee stain, a two-column PDF whose text extracts in the wrong order, a table whose rows are visible but not stored as rows, an invoice photographed at an angle, and a spreadsheet printed to PDF. Before a single word is indexed, something must decide what the document says. Errors made there are invisible downstream: the index faithfully stores text that was already wrong. Part 6 treats PDF structure, layout analysis, OCR (optical character recognition: turning an image of text into characters), tables and forms, retrieving page images directly, and documents in many languages and scripts.

Key takeaways

  • Search ranks results for a person; retrieval is the machinery; RAG adds a model that writes from what was retrieved.
  • Answer quality is capped by retrieval quality, so retrieval is measured before it is tuned.
  • Keyword retrieval fails by returning nothing (vocabulary mismatch) or by returning something confidently wrong; both need handling.
  • Document parsing happens before indexing and its errors are invisible afterwards, which is why Part 6 exists.
  • Six parts, six labs: lexical, measuring, dense, indexes, RAG, documents.

Further reading

  • Manning, Raghavan and Schütze, "Introduction to Information Retrieval" (2008). The standard free textbook; this course follows its lexical chapters closely.
  • Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" (2020). The paper that named RAG.
  • Robertson and Zaragoza, "The Probabilistic Relevance Framework: BM25 and Beyond" (2009). The definitive account of the ranking function we build in chapter 2.
  • Liu et al., "Lost in the Middle: How Language Models Use Long Contexts" (2023). Why placing evidence in the context is not the same as the model using it.
  • Anthropic, "Introducing Contextual Retrieval" (September 2024). A practical engineering account of what improved a production-style retrieval pipeline.

Check your understanding

A RAG assistant gives a wrong answer. The correct policy page exists in the corpus. What should you check first?

  1. Whether the language model is large enough
  2. Whether the correct page was among the passages retrieved for that question
  3. Whether the prompt politely asks for accuracy
  4. Whether the index uses cosine similarity
The generator can only use what it is given, so first establish whether retrieval delivered the right evidence. If it did not, no change to the model or prompt can fix the answer. The other options may matter later, but they come after reading the retrieved passages.

In the taste example, the query "get my money back" returned nothing although a refund page exists. What is this problem called?

  1. Over-stemming
  2. Index corruption
  3. Position bias
  4. Vocabulary mismatch
The user and the document describe the same idea with different words, so a method that matches words finds nothing. Over-stemming is about merging different words; position bias is about where a model looks in a long context.

Which statement about "RAG needs a vector database" is most accurate?

  1. False: keyword scoring such as BM25 is also retrieval, and strong systems often combine it with vectors
  2. True: without vectors there is no retrieval
  3. True: vectors always beat keywords
  4. False: RAG never uses an index
RAG only requires that relevant passages be fetched somehow. Lexical, dense and hybrid retrievers all qualify, and which is best depends on the collection and the queries, which is what Part 2 teaches you to measure.

Why does the course teach document parsing (Part 6) as part of retrieval rather than as a separate topic?

  1. Because OCR is a kind of embedding model
  2. Because parsing is faster than retrieval
  3. Because errors made while extracting text are stored faithfully by the index and cannot be seen or fixed downstream
  4. Because PDFs cannot be indexed at all
An index stores whatever text it is given. If extraction scrambles a two-column page or drops a table, every later stage works from the damaged text, and the failure looks like a retrieval or model problem.

Tables, Forms & Key-Value Extraction

Text in a document means something because of where it sits: a number under a column heading, a value beside a label. OCR gives you the words and their positions. This chapter is about recovering the structure from those positions, turning it into typed fields against a schema, and checking the values, because a field that is parsed is not a field that is right.

Why this matters

Most of the valuable facts in business documents are in tables and forms: revenue by region, line items on an invoice, dosage on a prescription, the total on a claim. Read as running text, a table becomes a stream of numbers whose headers are somewhere else, and a retrieval system that embeds it will answer "what was Asia Pacific revenue in Q2?" with whichever number it finds nearest. After this chapter you can explain how table structure is recovered and scored, choose between rule-based, specialised-model and vision-language approaches, design a schema with validators that catch the errors OCR leaves behind, and decide which extractions to accept automatically and which to send to a person.

Why running text is the wrong shape

Take the small table below. Read left to right, line by line, as a naive extractor would, it becomes Revenue, EUR m Region Q1 Q2 Change % North Europe 120.4 131.0 +8.8 South Europe 98.2 95.1 -3.2. Everything is still there. What is gone is which number belongs to which header: that 131.0 is North Europe's revenue in Q2, in euro millions, and that +8.8 is a percentage change from Q1 to Q2. A chunk starting at "98.2 95.1 -3.2" is the extreme case of the orphan chunk from chapter 14: numbers with no subject.

The fix is to recover the table structure: the grid of rows and columns, which cells span several, which are headers, and what text each holds. Doing it is called table structure recognition (TSR), and it is separate from two neighbouring tasks. Table detection finds where on the page a table is (layout analysis, chapter 18). Cell content recognition reads the text inside each cell (OCR, chapter 19). TSR sits between them.

What the output looks like

A recogniser must emit the structure in some format, and the choice limits what can be said.

  • HTML (<tr>, <td>, colspan, rowspan) can express every grid, which is why research datasets and metrics use it.
  • Markdown is compact and well understood by language models, but cannot express merged cells; it forces a choice between repeating a spanning header and dropping it.
  • Records (JSON), one object per row keyed by column header, are what an application usually wants: {"region": "Asia Pacific", "q2": 233.5}. They require deciding which cells are headers, and flattening multi-level headers into keys such as revenue_q2.
  • A cell list with row, column, spans, text and the page box of each cell is the richest form, because it supports highlighting a cited cell on the page image.

Recovering structure

Methods fall into four families. Real systems mix them.

Ruled tables

If the table is drawn with lines, detect the horizontal and vertical rules (image processing, or the vector lines in a born-digital PDF), intersect them to form a grid, and drop words into cells. Accurate and cheap when the lines exist, blind when they do not.

Whitespace and alignment

Many financial tables use no lines. Rows are runs of words at similar heights; columns are vertical strips that most rows leave empty. Fast and explainable, fragile on skewed, crowded or ragged tables. The program below does this.

Learned structure models

Networks trained on labelled tables. The Table Transformer (Smock, Pesala and Abraham, 2022) was trained on PubTables-1M, nearly a million tables from scientific articles; TableFormer (Nassar et al., 2022, IBM) predicts the structure of a table image as a sequence of HTML tags and is used in Docling. They handle lines, no lines and spans, but only as well as their training distribution.

The fourth family is the vision-language model (chapter 19), asked to emit the table as HTML or Markdown. It reads merged headers well and needs no hand-built layout stage, but it brings the fluent failures of that chapter to a new place: a dropped row, a copied row repeated, a number moved to the wrong column. Structure errors made by a language model are plausible-looking tables.

A whitespace recogniser you can run

The module below rebuilds a table from word boxes, as an OCR engine would provide them. Rows come from words at the same line; columns come from vertical strips that most lines leave empty; a cell is a run of words closer than a minimum gap; and a cell that covers more than one column becomes a colspan. The word boxes are generated from the ground truth of the table above (with a little jitter), and a parameter simulates the drift of a page scanned slightly crooked: each line sits a few points further right than the one above.

"""Rebuild a table from word boxes: rows by y, columns by whitespace valleys, spans by overlap."""
import random

CELLS = [  # (row, col, colspan, text) : the ground truth
    (0, 1, 2, "Revenue, EUR m"),
    (1, 0, 1, "Region"), (1, 1, 1, "Q1"), (1, 2, 1, "Q2"), (1, 3, 1, "Change %"),
    (2, 0, 1, "North Europe"), (2, 1, 1, "120.4"), (2, 2, 1, "131.0"), (2, 3, 1, "+8.8"),
    (3, 0, 1, "South Europe"), (3, 1, 1, "98.2"), (3, 2, 1, "95.1"), (3, 3, 1, "-3.2"),
    (4, 0, 1, "Asia Pacific"), (4, 1, 1, "210.7"), (4, 2, 1, "233.5"), (4, 3, 1, "+10.8"),
    (5, 0, 1, "Total"), (5, 1, 1, "429.3"), (5, 2, 1, "459.6"), (5, 3, 1, "+7.1"),
]
COLX = [20, 190, 290, 390]            # left edge of each column, in points
COLW = [150, 80, 80, 70]              # column widths; the gaps between them are the valleys

def word_boxes(shear, rng):
    """Each word is (x0, x1, line, text). `shear` drifts later lines to the right (a skewed scan)."""
    out = []
    for r, c, cs, text in CELLS:
        width = sum(COLW[c:c + cs]) + sum(COLX[c + k] - COLX[c + k - 1] - COLW[c + k - 1] for k in range(1, cs))
        words = text.split()
        total = sum(7 * len(w) for w in words) + 7 * (len(words) - 1)
        x = COLX[c] + (width - total) / 2 if cs > 1 else COLX[c]
        for w in words:
            out.append((x + shear * r + rng.uniform(-1, 1), x + 7 * len(w) + shear * r, r, w))
            x += 7 * len(w) + 7
    return out

def rebuild(words, min_gap=14, vote=0.7):
    lines = sorted({w[2] for w in words})
    blank = [0] * 520
    for x in range(520):
        blank[x] = sum(not any(a <= x <= b for a, b, l, _ in words if l == ln) for ln in lines)
    empty = [blank[x] >= vote * len(lines) for x in range(520)]
    seps, x = [], 0                   # separators: wide runs of columns that most lines leave empty
    while x < 520:
        if empty[x]:
            y = x
            while y < 520 and empty[y]: y += 1
            if y - x >= min_gap and x > 0 and y < 520: seps.append((x + y) / 2)
            x = y
        else:
            x += 1
    edges = [0] + seps + [520]
    cells = set()
    col = lambda x: max(i for i in range(len(edges) - 1) if edges[i] <= x or i == 0)
    for ln in lines:
        segs = []                     # words closer than min_gap belong to one cell
        for a, b, l, t in sorted(w for w in words if w[2] == ln):
            if segs and a - segs[-1][1] < min_gap:
                segs[-1] = (segs[-1][0], b, segs[-1][2] + [t])
            else:
                segs.append((a, b, [t]))
        for a, b, ts in segs:
            lo, hi = col(a + 1), col(b - 1)
            cells.add((ln, lo, hi - lo + 1, " ".join(ts)))
    return cells

def truth():
    return {(r, c, cs, t) for r, c, cs, t in CELLS}

def cell_f1(pred, gold):
    tp = len(pred & gold)
    p, r = tp / max(1, len(pred)), tp / max(1, len(gold))
    return 2 * p * r / (p + r) if p + r else 0.0

def deskew(words):
    """Estimate the drift per line from the left edge of each line's first word (lines 1 and up), remove it."""
    first = {}
    for a, b, l, t in sorted(words):
        if l >= 1 and l not in first: first[l] = a
    n = len(first); ls = list(first); xs = [first[l] for l in ls]
    ml, mx = sum(ls) / n, sum(xs) / n
    slope = sum((l - ml) * (x - mx) for l, x in zip(ls, xs)) / sum((l - ml) ** 2 for l in ls)
    return [(a - slope * l, b - slope * l, l, t) for a, b, l, t in words]

We score the result by cell F1: a predicted cell counts as correct only if row, column, span and text all match, precision is the share of predicted cells that are right, recall the share of true cells found, and F1 their harmonic mean. Then we increase the drift and repeat after a simple deskew that fits the drift from the left edges of the first column and subtracts it.

import random
from tablefit import *

gold = truth()
print("drift pt/line  columns  F1 raw   F1 after deskew")
for drift in (0, 12, 14, 18, 30):
    words = word_boxes(drift, random.Random(5))
    raw, fixed = rebuild(words), rebuild(deskew(words))
    print(f"{drift:8d}       {max(c + s for _, c, s, _ in raw):5d}   {cell_f1(raw, gold):6.2f}   {cell_f1(fixed, gold):6.2f}")
pred = rebuild(word_boxes(0, random.Random(5)))
for row in (0, 1):
    print("row", row, sorted((c, s, t) for r, c, s, t in pred if r == row))

Two things stand out. The method is perfect on a straight scan and stays perfect for moderate drift, then falls off a cliff: at 14 points per line, the column strips of different rows overlap and two columns merge, so about half of the cells are wrong at once. A cliff is typical of structure recognition, because one wrong decision (where a column boundary falls) corrupts every cell that depends on it. And a modest preprocessing step, here ten lines of deskew, restores the score. That is the pattern to expect in practice: the cheapest improvement to table structure is often upstream, in the image cleaning of chapter 19, not in a better model.

Row 0 shows the other thing a good recogniser must do: it found the cell "Revenue, EUR m" as one cell covering columns 1 and 2, instead of two cells "Revenue," and "EUR m". It did so because words closer than a few points belong to the same cell, which is why a threshold like min_gap matters: too small and a wide-set heading splits, too large and neighbouring columns fuse.

Scoring a table

Cell F1 is easy to compute and harsh: one wrong span makes several cells wrong at once. The standard research metric is TEDS, tree-edit-distance-based similarity (Zhong, ShafieiBavani and Yepes, 2020, introduced with the PubTabNet dataset). It represents each table as an HTML tree and measures how many node edits (insert, delete, rename) turn one tree into the other:

TEDS(Tpred, Ttrue) = 1 − EditDist(Tpred, Ttrue) / max(|Tpred|, |Ttrue|)

where |T| is the number of nodes. Because it works on trees, a missing column costs a bounded number of edits rather than corrupting every cell, so it gives partial credit that grows smoothly with damage. Cell text is compared with a normalised edit distance, so a one-character OCR error costs a little, not a whole cell. A variant, TEDS-S, ignores the text and scores structure only. OmniDocBench (chapter 19) uses TEDS for the table part of its overall score.

Use more than one number, because they answer different questions:

MetricWhat it rewardsWhat it hides
TEDS-S (structure only)Right grid and spansWrong digits in the cells
TEDS (structure and text)Grid and content together, with partial creditWhich kind of error; a wrong digit costs little
Cell F1, exactEach cell fully rightHow close the wrong cells were
Numeric-cell accuracyValues you will compute withHeaders and structure
Query accuracyQuestions answered correctly from the extracted tableWhere in the pipeline the error arose

The last row is the one that matters to a product, and it is the cheapest to understand: write ten questions per table ("what was Asia Pacific revenue in Q2?"), answer them from the extracted structure, and count.

Tables in retrieval

A recovered table still has to be retrievable and citable. Three habits make a difference.

  1. Keep the header with every row. Embed or index each row as text that carries its headers: "Revenue, EUR m, Asia Pacific, Q2: 233.5". A row chunk that says only "Asia Pacific 210.7 233.5 +10.8" is the orphan problem again. Add the table's caption and its section heading as context, as in the contextual retrieval of chapter 14.
  2. Index a description, return the table. A short generated or extracted description ("quarterly revenue by region, 2025") is what a question most resembles. Match on it, then hand the whole table, in HTML or Markdown, to the generator (the small-to-big pattern of chapter 14).
  3. Handle tables that continue. A table that crosses a page break often repeats its header on the second page, or does not repeat it at all. Join the pieces when the columns line up and the header repeats; keep the page number of each part so the citation is right (chapter 16).

For questions that need arithmetic across a table ("what was the total change?"), retrieval alone is the wrong tool. Load the extracted records into a small structured store and let the model write a query or a short calculation, rather than ask it to add numbers it has only read in prose; the tool-use patterns are in the agents course.

Forms and key-value extraction

A form is the other common shape: a set of fields, each a label and a value. Extracting them is key-value extraction: find the label ("Date of birth"), find its value ("14 March 1987"), and return the pair under a canonical field name. The hard part is that the association is spatial, and conventions vary.

Approaches, in rough order of generality:

  • Templates and anchors. For a fixed form from a known issuer, the field sits at a known place: crop it and read it. Perfect until the issuer updates the layout, so version your templates and detect a mismatch.
  • Heuristics and learned pairing. Find label-like text and pair it with the nearest value in the expected direction. Layout-aware language models, which read text together with each word's box, learn the pairing from examples: LayoutLMv3 (Huang et al., 2022) is a well-known example, benchmarked on form datasets such as FUNSD (Jaume et al., 2019).
  • OCR-free models. Donut (Kim et al., 2022) maps the page image straight to a structured output, skipping the separate OCR step.
  • Vision-language models with a schema. Give the page and a description of the fields you want; receive JSON. The most flexible approach, and the least predictable: it needs the validation layer below more than any other.

Schemas and validation

A schema says what a correct extraction looks like before any document is read: the field names, their types (amount, date, identifier, enumeration), whether each is required, and the rules relating them. It is the contract between the extraction stage and everything downstream, in the sense of encoding and schema evolution: change it deliberately, version it, and reject data that does not conform instead of passing it on.

Many tools can constrain a language model to emit JSON that matches a schema. This guarantees syntax: the braces close and the fields are present with the right types. It says nothing about whether the amount is the amount on the page. A model forced to produce a number will produce a number.

Common misconception

"Structured output mode means the extraction is validated." Constrained decoding makes the output parseable. It does not make the values true, and by forcing a value into every required field it can turn "I cannot read this" into a confident guess. Give the schema an explicit way to say unknown (a null, or a status), and validate the values separately.

Layers of checks

  1. Parse and normalise. Turn the raw string into a typed value: an amount as a number, a date as a date. This is where locale traps live: 1.200 is twelve hundred in Germany and one point two elsewhere; 03/04/2025 is the third of April or the fourth of March. A parser should refuse to guess when the text is ambiguous.
  2. Format and domain rules. Identifier patterns, allowed currency codes, plausible ranges (an invoice dated in the year 2205 is a misread digit).
  3. Checksums. Many identifiers carry check digits: IBANs (mod 97), payment card numbers (Luhn), ISBNs, vehicle identification numbers. A single misread digit fails the check with high probability, which is a gift: the check is independent of the OCR engine.
  4. Cross-field consistency. Net plus tax equals gross; line items sum to the subtotal; the end date follows the start date; a percentage matches the amounts it was computed from.
  5. Evidence and confidence. The engine's confidence for the value, and whether two engines agree (chapter 19).

The module below implements these layers for an invoice, with parsers that decline to guess. Three documents are given as raw strings with confidences, as an extraction stage would deliver them. Document B is the fluent failure: one digit of the gross total has changed, and its confidence (0.91) is high.

import re
from datetime import date

def parse_amount(s):
    """'1,440.00' and '1.440,00' both mean 1440.00; the last separator with 1-2 digits after it is the decimal point."""
    s = s.replace(" ", "")
    m = re.fullmatch(r"(\d{1,3}(?:[.,]\d{3})*|\d+)(?:[.,](\d{1,2}))?", s)
    if not m: raise ValueError(f"not an amount: {s!r}")
    return float(re.sub(r"[.,]", "", m[1]) + "." + (m[2] or "0"))

def parse_date(s, day_first=None):
    if m := re.fullmatch(r"(\d{4})-(\d\d)-(\d\d)", s): return date(int(m[1]), int(m[2]), int(m[3]))
    if m := re.fullmatch(r"(\d\d)/(\d\d)/(\d{4})", s):
        a, b, y = int(m[1]), int(m[2]), int(m[3])
        if a > 12: return date(y, b, a)
        if b > 12: return date(y, a, b)
        if day_first is None: raise ValueError(f"ambiguous date {s!r}")
        return date(y, b, a) if day_first else date(y, a, b)
    raise ValueError(f"not a date: {s!r}")

def iban_ok(s):
    s = s.replace(" ", "").upper()
    if not re.fullmatch(r"[A-Z]{2}\d\d[A-Z0-9]{10,30}", s): return False
    digits = "".join(str(int(c, 36)) for c in s[4:] + s[:4])   # letters become 10..35
    return int(digits) % 97 == 1

def check(doc, min_conf=0.85):
    """doc maps field -> (raw text, confidence). Returns ('accept' | 'review', reasons)."""
    why, v = [], {}
    for name, (raw, conf) in doc.items():
        if conf < min_conf: why.append(f"{name}: low confidence {conf:.2f}")
        try:
            if name in ("net", "vat", "gross"): v[name] = parse_amount(raw)
            elif name == "issued": v[name] = parse_date(raw)
            elif name == "invoice_no" and not re.fullmatch(r"INV-\d{4}-\d{4}", raw): raise ValueError("bad format")
            elif name == "iban" and not iban_ok(raw): raise ValueError("checksum fails")
        except ValueError as e:
            why.append(f"{name}: {e}")
    if {"net", "vat", "gross"} <= v.keys() and abs(v["net"] + v["vat"] - v["gross"]) > 0.005:
        why.append(f"net + vat = {v['net'] + v['vat']:.2f}, gross says {v['gross']:.2f}")
    return ("review" if why else "accept"), why

Document A passes. Document B is caught only by the cross-field rule: every field is well formed and confident, and the arithmetic alone says that 1,200.00 plus 240.00 is not 1,540.00. Document C collects four independent reasons: the letter O in the invoice number (low confidence and a format failure agree), a date that cannot be read without knowing the locale, and an IBAN whose checksum fails because two digits were swapped. The European-format amounts ("1.200,00") parsed correctly, which would have been silently wrong under a naive float().

Analogy: double-entry bookkeeping

Accountants enter every transaction twice, as a debit and a credit, and the books must balance. The method does not stop errors being made; it makes most of them visible, because a slip in one place leaves the totals disagreeing. Cross-field validation does the same for extracted documents: the same fact is written in several places (rows, subtotal, total, tax), so a misread number breaks a relationship.

Where it breaks down: double entry only catches errors that leave the books unbalanced. If the document itself is wrong in a consistent way, or the model changes two related numbers to match, the check passes. Documents also contain legitimate inconsistencies, such as rounding differences of a cent, which need a tolerance, not a failure.

Deciding what to accept

The output of validation is a decision per document, and the economics of that decision are worth working out before building. Assume (illustrative numbers) 10,000 invoices a month. The pipeline accepts 70% automatically, and spot checks show that 0.5% of accepted invoices contain a wrong amount. Then 7,000 are accepted and about 35 wrong amounts reach the ledger; 3,000 go to review, at 90 seconds each that is 75 person-hours. Each number has a lever:

  • Tightening the thresholds sends more to review (fewer errors accepted, more hours).
  • Adding a validator usually moves documents from "accepted with a hidden error" to "reviewed", with no loss in documents accepted correctly.
  • Showing the reviewer only the flagged field, with the cropped page region beside it, cuts the 90 seconds sharply, because the person verifies instead of re-keying.

The two quantities to track are the straight-through rate (the share of documents accepted without a person) and the accepted error rate (errors among the accepted ones, measured by auditing a random sample of them). A pipeline can improve the first and worsen the second without any other metric noticing. This is the risk-coverage trade-off of evals chapter 11, applied to extraction. Keep audit sampling running after launch, because the accepted error rate drifts when suppliers change templates.

Systems connection

A schema with versioned fields is the same discipline as an API contract (evolving contracts), and a human review queue is a work queue with the delivery semantics of logs and exactly-once processing: a document extracted twice must not be posted twice. Extracted text is also untrusted input. A value that is later used in a database query, a file path or a prompt needs the care of injection defences, whatever its source.

Key takeaways

  • A table is a grid with spans and headers. Flattened to running text it loses the link between numbers and their meaning, so recover the structure and keep headers with every row.
  • Structure recognition methods range from ruled-line and whitespace heuristics to learned models and vision-language models. One wrong column boundary corrupts many cells at once, and cheap upstream fixes such as deskewing often beat a better model.
  • Score structure and content separately: TEDS (tree edit distance on HTML), exact cell F1, numeric-cell accuracy, and best of all, questions answered correctly.
  • Key-value extraction pairs labels with values spatially, and some values are marks, not text. Templates, layout-aware models, OCR-free models and schema-prompted VLMs trade predictability for flexibility.
  • A schema is a contract. Constrained decoding makes output parseable, not true; give the schema a way to say unknown.
  • Validate in layers: typed parsing that refuses to guess, format rules, checksums, cross-field arithmetic, engine confidence. Cross-field checks catch the confident, well-formed errors that other checks miss.
  • Track straight-through rate and accepted error rate together, and audit a random sample of accepted documents indefinitely.

Check your understanding

A retrieval system embeds each table row as the text "Asia Pacific 210.7 233.5 +10.8". Users ask "Q2 revenue in Asia Pacific" and often get the wrong row. What is the most direct fix?

  1. Use a larger embedding model
  2. Make the chunks longer by joining several rows
  3. Prefix each row with its column headers and the table caption before embedding
  4. Remove the numbers so the embedding focuses on the names
The row has lost the meaning of its numbers, so no embedder can tell which column "233.5" is. Adding the headers and caption restores it. A bigger model cannot recover information that is absent, and joining rows blurs the vector further. Removing numbers removes the answer.

In the whitespace recogniser, increasing the page drift from 12 to 14 points per line drops cell F1 from 1.00 to 0.48. Why is the drop so sudden?

  1. One decision (where the column boundaries fall) goes wrong, and every cell that depends on it is wrong with it
  2. The OCR engine starts misreading characters at that angle
  3. The F1 score is not defined above 12 points
  4. The jitter in the word boxes becomes larger
Column strips from different rows begin to overlap, so the empty valleys vanish and columns fuse. Cell content is unchanged, but its assignment to cells is not. Nothing about character recognition or the scoring changes.

Which metric gives partial credit for a table that is missing one column, instead of marking most cells wrong?

  1. Exact cell F1
  2. Word error rate on the concatenated text
  3. Numeric-cell accuracy
  4. TEDS, because it compares tables as trees by the number of edits
TEDS counts the edits needed to turn one HTML tree into another, so a missing column costs a bounded number of edits. Exact cell F1 treats any shifted or mismatched cell as fully wrong. Word error rate ignores the structure, and numeric-cell accuracy measures values, not the grid.

An extractor returns invoice JSON that always matches the schema, with every field populated. A colleague says the extraction is therefore validated. What is the best reply?

  1. Agreed, because a populated schema means the model read every field
  2. Constrained output guarantees the syntax only; values still need checks such as arithmetic, checksums and a way to say unknown
  3. Disagree, because JSON cannot represent invoices accurately
  4. Agreed, as long as the model temperature is zero
A forced field is filled whether or not the value was legible, so a populated field may be a guess. Zero temperature makes the guess repeatable, not correct. The problem is not the format JSON; it is mistaking well-formedness for truth.

A document has net 1,200.00, tax 240.00 and a gross total of 1,540.00, all with confidence above 0.9. Which check flags it?

  1. The confidence threshold on each field
  2. The IBAN checksum
  3. The cross-field rule that net plus tax equals gross
  4. The locale-aware amount parser
Every field is confident and well formed, so thresholds, checksums on other fields and parsers all pass. Only the relationship between fields exposes that 1,440.00 and 1,540.00 disagree. Confidence is the tempting answer but a model can be confidently wrong.

After adding a looser validator, the straight-through rate rises from 60% to 85% and nobody complains. What should you check next?

  1. Nothing, since a higher straight-through rate is the goal
  2. The accepted error rate, by auditing a random sample of the automatically accepted documents
  3. The review queue length, which must have fallen
  4. The average OCR confidence across the new documents
Accepting more documents is only good if the accepted ones are right. A looser rule can move errors from the review queue to the ledger, and the only way to see that is to audit accepted documents. Queue length and average confidence are consequences, not the risk.

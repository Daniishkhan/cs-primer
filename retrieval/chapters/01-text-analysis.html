Text Analysis

A search index does not store your documents' words. It stores the output of an analyser: a small pipeline that decides what counts as a word, which differences to erase and which to keep. This chapter builds one, shows what each choice buys and costs, and explains the single rule that matters most: index and query must be analysed the same way.

Why this matters

Before any ranking formula runs, text analysis has already decided which documents can possibly match. If "Refunds" and "refund" become different terms, a user misses the page they need. If "cafe" and "café" do not meet, a whole language community is under-served. If the query side uses a different analyser from the index side, searches silently return nothing. These bugs show no error message; they look like a bad search engine. After this chapter you will be able to design an analyser for a collection, test it, and diagnose the commonest ways it goes wrong.

What an index really stores

An inverted index maps each word to the documents containing it. A careful reader should have asked: which words? "Refunds", "refunds," (with a comma) and "REFUNDS" are three different strings to a computer. The index stores terms: the normalised units that result from analysing text. A term is not always a dictionary word. It can be a stem ("refund" for "refunds"), a number, a code, a fragment of a word, or a lowercase, accent-free version of what was typed.

The component that turns raw text into terms is the analyser. Search engines such as Lucene, Elasticsearch and OpenSearch describe an analyser as three stages in order: character filters that rewrite the raw text, a single tokeniser that cuts the text into tokens, and token filters that modify, drop or add tokens. We follow that vocabulary, so the configuration of a real engine will look familiar.

Tokenising: deciding what a word is

Tokenising cuts a string into tokens. It sounds trivial until you try it. Here are three tokenisers applied to one awkward sentence.

print("keep-ish :", re.findall(r"[a-z0-9]+(?:[.'@-][a-z0-9]+)*", text.lower()))

Splitting on whitespace leaves punctuation glued to words ("units," and "off!)") and keeps "$1,250.50" whole. Splitting on non-word characters, the usual first attempt, fixes that and breaks things differently: "O'Neil's" becomes o and s, the email address becomes four tokens, and the price becomes 1, 250 and 50, so a search for the amount can match a document about 50 units. The third attempt keeps internal apostrophes, hyphens, dots and at-signs when they sit between letters or digits. It is better for this sentence and worse for others. There is no universally correct answer, only a choice that fits the queries you expect.

Production tokenisers do not improvise. Lucene's and Elasticsearch's standard tokeniser follows the word-boundary rules of Unicode Standard Annex #29 (Unicode Text Segmentation), which handle many scripts and punctuation cases consistently. Treat such a tokeniser as your default and deviate with a reason. Some writing systems do not put spaces between words at all (Chinese, Japanese and Thai are the usual examples), so no rule based on spaces can work; those need dictionary-based segmentation or overlapping character n-grams. Chapter 22 returns to them.

Systems connection

Do not confuse this with the tokenisers of language models. A model's tokeniser (A2 chapter 13) cuts text into sub-word pieces chosen to fit a fixed vocabulary, so that any string can be represented. A search analyser cuts text into units chosen so that a query and a document can meet. Both are called "tokenising", but they serve different consumers and are tuned differently.

Normalising: erasing differences on purpose

Normalisation replaces different spellings of "the same thing" with one canonical form, so they match. Each normalisation is a bet that the user does not care about the difference. The commonest are these.

Case folding

Lowercasing lets "Refund" match "refund". The more careful operation is case folding, defined by Unicode for caseless matching, which handles cases where lowercasing alone is not enough: German "Straße" and "STRASSE" are the same word, but their lowercase forms differ.

Unicode normalisation

An accented letter can be stored two ways: as one precomposed code point (é) or as a plain "e" followed by a combining accent mark. They look identical on screen and are different strings. Text pasted from a PDF, a word processor and a Mac keyboard frequently mixes the two. Unicode normalisation converts both to one form (NFC composes, NFD decomposes). Without it, the same word is two terms and half your documents are unreachable by half your users.

Accent folding

Many users do not type accents: they search for "cafe" meaning "café". Accent folding strips the combining marks so the two meet. This helps in English-language collections with borrowed words and hurts where accents distinguish words (Spanish "año", year, versus "ano", anus; or Swedish "å" versus "a"). Whether to fold is a per-language decision, not a global one.

import unicodedata

def show(label, s):
    print(f"{label:<22}{s!r:<14} code points: {[hex(ord(c)) for c in s]}")

composed   = "café"          # e-acute as one code point
decomposed = "café"         # e + combining acute accent
show("composed", composed)
show("decomposed", decomposed)
print("equal as typed?       ", composed == decomposed)
nfc = lambda s: unicodedata.normalize("NFC", s)
print("equal after NFC?      ", nfc(composed) == nfc(decomposed))

def fold_accents(s):
    d = unicodedata.normalize("NFD", s)
    return "".join(c for c in d if unicodedata.category(c) != "Mn")

Analogy: library filing rules

A librarian files "Mc" names as if they were spelled "Mac", ignores a leading "The", and sorts "Ö" with "O". The catalogue works because the person who files a card and the person who looks one up apply the same rules. If a new assistant filed by different rules, the card would still exist, but nobody following the published rules would find it.

Where it breaks down: a library has one rulebook and humans can browse nearby. A search index has no neighbouring shelf; a term that differs by one character is simply absent, and nothing tells the user where it went.

Stop words: a bargain that stopped paying

Stop words are very common words ("the", "of", "to") dropped before indexing. In the days of small disks and slow machines, lists of 200 to 300 words were common because those words filled the biggest postings lists. Manning, Raghavan and Schütze (2008) describe the shift since then: lists shrank to a handful of words and web search engines generally use none, because postings compress well, inverse-document-frequency weighting (chapter 2) already gives common words little influence, and ranked retrieval can stop reading a postings list early.

Dropping them also does harm. Phrases such as "flights to London" lose their meaning, and some titles consist almost entirely of stop words. The scripts below show both costs with a small stop list. The first file defines the analyser we use for the rest of the chapter.

import re
import unicodedata

STOP = {"the", "a", "an", "of", "to", "and", "in", "is", "for", "on", "are", "be", "by"}

def light_stem(w):
    """A deliberately crude suffix stripper (a stand-in for Porter/Snowball)."""
    for suf, rep in [("ational", "ate"), ("ization", "ize"), ("ies", "y"), ("sses", "ss"),
                     ("ing", ""), ("ed", ""), ("es", ""), ("s", ""), ("ly", "")]:
        if w.endswith(suf) and len(w) - len(suf) >= 3 and not w.endswith("ss"):
            return w[: len(w) - len(suf)] + rep
    return w

class Analyser:
    def __init__(self, fold=True, stop=True, stem=True):
        self.fold, self.stop, self.stem = fold, stop, stem
    def __call__(self, text):
        text = unicodedata.normalize("NFC", text).casefold()
        if self.fold:
            text = "".join(c for c in unicodedata.normalize("NFD", text) if unicodedata.category(c) != "Mn")
        toks = re.findall(r"[a-z0-9]+(?:[.'-][a-z0-9]+)*", text)
        toks = [t[:-2] if t.endswith("'s") else t for t in toks]      # possessives: cafe's -> cafe
        if self.stop:
            toks = [t for t in toks if t not in STOP]
        if self.stem:
            toks = [light_stem(t) for t in toks]
        return toks

That file is a complete analyser: Unicode normalisation, case folding, optional accent folding, a tokeniser that keeps internal punctuation and strips possessives, an optional stop list, and an optional stemmer (the next section). It is about 25 lines. A second script uses it to show what stop-word removal and stemming do to some words and queries.

Stemming and lemmatisation: merging word forms

A user who searches "refunds" probably also wants pages saying "refund" and "refunded". Stemming reduces words to a shared stem by chopping suffixes with rules. The best-known algorithm is Porter's (Porter, 1980, "An algorithm for suffix stripping"); Snowball, from the same author, is a family of stemmers for many languages. Manning et al. give the flavour: Porter's stemmer reduces "operate", "operating", "operates", "operation", "operative", "operatives" and "operational" all to "oper". The stem need not be a word; it only has to be consistent.

Lemmatisation goes further: it uses a dictionary and the word's part of speech to return the proper base form (the lemma), so "saw" can become "see" when it is a verb and stay "saw" when it is a noun. It is slower and needs per-language resources, and in retrieval it often gives results similar to a good stemmer.

Stemming trades precision (how many results are relevant) for recall (how many relevant documents are found). It errs in two directions:

  • Over-stemming merges words that should stay apart. Our crude stemmer turns "news" into "new". Real stemmers make the same kind of error less often, and more aggressive settings make it more often.
  • Under-stemming fails to merge words that should meet. In the output above, "organization" and "organizations" ended in different stems, and "meeting" and "meetings" did too.

The stemmer used here is deliberately crude: about ten suffix rules, written to be readable. It is a stand-in for Porter or Snowball, which you would use in practice, and its mistakes illustrate the types of mistake real stemmers make less often, not their exact behaviour.

Index and query must agree

Everything above applies twice: once when documents are indexed and once when a query arrives. The query's text must be analysed so that its terms are exactly the terms that were stored. This is the most important rule in the chapter, and the most commonly broken. Run the analyser over four short help pages and query it.

from collections import defaultdict
from analyser import Analyser

docs = {
    1: "Refunds are processed within 14 days of the returned goods arriving.",
    2: "Our café accepts returns of damaged items; the refund is issued to the original card.",
    3: "Processing a refund: the customer returned two items.",
    4: "Shipping rates and delivery times for international orders.",
}

def build(analyser):
    idx = defaultdict(set)
    for d, t in docs.items():
        for tok in analyser(t):
            idx[tok].add(d)
    return idx

def search(idx, analyser, q):
    return sorted(set.intersection(*[idx.get(t, set()) for t in analyser(q)])) if analyser(q) else []

full = Analyser()
idx = build(full)
print("analysed doc 1:", full(docs[1]))
print("analysed doc 3:", full(docs[3]))
print()
for q in ["refund returned items", "refunds returning item", "cafe returns", "the refunding of goods"]:
    print(f"{q!r:<28} -> {search(idx, full, q)}")

print("\nIndex built with stemming, query analysed WITHOUT stemming:")
raw_q = Analyser(stem=False)
for q in ["refunds processed", "returned goods"]:
    print(f"{q!r:<28} query terms {raw_q(q)} -> {search(idx, raw_q, q)}")

The first block shows the benefit. "refund returned items", "refunds returning item" and "the refunding of goods" all find the right pages: stemming merged the word forms, the stop list removed "the" and "of", and accent folding let "cafe" find the page that says "café". The second block shows the failure. The index was built with stemming, but the queries here were analysed without it. The query terms are refunds and processed, while the index holds refund and process. No document matches, and nothing reports an error.

This happens in practice through quiet routes: an index built with one analyser version and a query service deployed with another; a field analysed differently from the one the query targets; a client that lowercases and strips accents before sending; a library upgrade that changes a default. Defences are cheap: define the analyser in one shared piece of configuration, store its version with the index, test known query and document pairs after every change, and when the analyser changes, reindex (rebuild the index from the source documents), because already-stored terms were produced by the old rules. Real engines also offer an analyse endpoint that shows the terms produced for a string (Elasticsearch calls it _analyze); use it first when a document "should match but does not".

There are two deliberate exceptions, and it helps to know they exist. Synonyms are often applied only at query time, so changing the synonym list does not require reindexing (chapter 3). Edge n-grams, which store every prefix of a word so that "ref" finds "refund" during type-ahead, are applied only at index time and the query is left whole. In both cases the asymmetry is intended, tested and written down.

Common misconception

"More normalisation is always better." Each step merges terms, which raises recall and lowers precision. Aggressive stemming makes "news" match "new"; accent folding makes Spanish "año" match "ano"; stop-word removal makes "to be" unsearchable. Choose steps per field and per language, and measure them.

Measuring what an analyser step buys

Because analysis decisions are bets, test them. Here is a miniature experiment: ten help pages, six queries, and for each query the set of pages a person would call relevant (eleven relevant pairs in total). We add analysis steps one at a time and count how many relevant pages are found, how many are missed, and how many results are extra (returned though not relevant). The queries are run as OR queries: a page matches if it contains any query term.

import re
from collections import defaultdict
from analyser import Analyser

docs = {

 2: "The café menu lists vegan options and gluten-free bread.",
 3: "To return an item, print the returning label and post the parcel.",
 4: "Our cafe opens at 8am; coffee refills are free.",
 5: "Shipping rates for international orders are shown at checkout.",
 6: "Returned goods must be unused and in the original packaging.",
 7: "Delivery of large items takes up to 10 working days.",
 8: "Gift cards cannot be refunded once they are redeemed.",
 9: "Cooking classes: learn to bake bread and cook pasta.",
 10: "Items damaged in transit are replaced free of charge.",
}

 "refund": {1, 8}, "returned items": {3, 6}, "cafe": {2, 4},

}

def whitespace(t): return t.lower().split()

 "split + lowercase":      whitespace,

Designing an analyser for a real collection

A short procedure works for most projects:

  1. Start from the engine's standard analyser for the language. It encodes a lot of accumulated care (Unicode word boundaries, lowercasing).
  2. Collect real queries and real zero-result searches. They show which differences your users do not care about (plurals, accents, hyphens) and which they do (product codes, names).
  3. Add one step at a time (folding, light stemming, synonyms) and compare on a fixed query set, as above.
  4. Use different analysers for different fields. A product code field should be matched exactly or by prefix; a description field benefits from stemming; a person's name usually should not be stemmed at all.
  5. Make the analyser configuration a versioned artefact shared by indexing and query code, and plan the reindex for when it changes.

State of play, October 2026

Embedding-based retrieval (Part 3) changes how much analysis matters but does not remove it. A dense retriever has its own model tokeniser and ignores your stemmer entirely, yet hybrid systems that combine lexical and dense results still depend on the lexical half being analysed properly, and exact identifiers, names and rare terms are where lexical matching earns its place. Defaults vary by engine and release: Elasticsearch's standard analyser lowercases and does not drop stop words unless configured (per its current documentation, checked October 2026), but check the version you actually run, since defaults differ between engines and have changed over time.

Key takeaways

  • An index stores terms produced by an analyser: character filters, one tokeniser, then token filters. Documents never reach the index as written.
  • Every normalisation (case folding, Unicode normalisation, accent folding, stemming) merges terms, raising recall and risking precision. It is a bet about what users do not care about.
  • Stop-word removal has little storage benefit today and breaks phrases and short queries; modern defaults often leave it off.
  • Stemmers err by over-stemming (merging different words) and under-stemming (missing related forms).
  • Index and query must use the same analysis, except for deliberate, documented asymmetries such as query-time synonyms. A mismatch returns nothing and says nothing.
  • Test analysers with a fixed query set, version their configuration, and reindex when they change.

Check your understanding

After a deployment, searches for "refunds" return nothing, though pages containing "refund" and "refunds" are visible in the source database. The index was built last month with stemming. Which cause is most likely?

  1. The inverted index lost its postings lists
  2. Stemming always breaks plural queries
  3. The query service now analyses the query without stemming, so it looks up "refunds" but the index holds "refund"
  4. The documents are too short to match
The index holds stems; the query term no longer reduces to a stem, so the lookup misses. Stemming does not break plurals when both sides apply it. Lost postings would affect all queries, not only inflected ones. The fix is to share the analyser configuration and, if the analyser changed, reindex.

Two copies of "café" fail to match in your index. Their code points are U+0063 U+0061 U+0066 U+00E9 and U+0063 U+0061 U+0066 U+0065 U+0301. What should the analyser do?

  1. Apply Unicode normalisation (such as NFC) to every text before tokenising
  2. Apply a stemmer to both
  3. Remove the stop words
  4. Lowercase both
One form uses a precomposed é, the other an "e" plus a combining accent. They need a common representation, which is what normalisation provides. Lowercasing, stemming and stop-word removal do not change the code point sequences in a way that makes them equal.

A legal-search team adds an aggressive stemmer and finds recall improves but lawyers complain about irrelevant hits at the top. Which statement best explains the trade-off?

  1. Stemmers only affect precision, never recall
  2. The complaints show the stemmer is not running
  3. Stemming only helps for short queries
  4. Merging word forms finds more relevant documents but also merges words with different meanings, which hurts precision
Stemming raises recall by unifying forms and lowers precision when it conflates unrelated words (over-stemming). The remedy is a lighter stemmer or per-field analysis, not abandoning analysis or declaring the stemmer inactive.

A type-ahead box should return "refund" after the user has typed "ref". The index stores every prefix of each word (edge n-grams). How should the query be analysed?

  1. With the same edge n-gram analyser, so that "ref" becomes "r", "re" and "ref"
  2. With a plain analyser that leaves "ref" as one term, since the prefixes are already in the index
  3. With a stemmer, so "ref" becomes "re"
  4. It cannot work; index and query must always use identical analysers
Edge n-grams are a deliberate asymmetry. If the query were also broken into prefixes, "r" would match thousands of documents. The rule is that index and query analysis must be compatible by design, which usually means identical but sometimes, as here, intentionally different and tested.

Your stop list contains "to", "be", "or", "not" and "the". A user searches for the play "to be or not to be". What reaches the index lookup, and what is the best response?

  1. Nothing reaches it; add more stop words
  2. The full phrase; no action needed
  3. Almost nothing (here "or" and "not" would be left), so leave stop words in the index and let weighting handle common words, or special-case phrase queries
  4. The phrase in reverse; reorder the tokens
With that stop list only "or" and "not" survive, which cannot identify the play. Modern practice keeps common words in the index because idf weighting already gives them little influence and phrase matching needs them. Adding more stop words makes it worse.

You compare two analysers on a 100-query test set. Variant B finds more relevant pages but returns many more irrelevant ones. What do you need before declaring B better?

  1. A measure that accounts for both, such as precision and recall or a ranking metric, and how the results are ordered
  2. Nothing: finding more relevant pages is always better
  3. A larger stop-word list for B
  4. Only the count of queries with zero results
More matches are not better if the good ones are buried. Precision, recall and rank-aware metrics (chapter 4) describe both sides. Zero-result counts only measure one failure type.

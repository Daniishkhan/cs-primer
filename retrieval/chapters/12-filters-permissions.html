Filters, Metadata & Permissions

A nearest-neighbour search answers "what is most similar?". Real systems ask "what is most similar among the documents this user may see, from this tenant, that are current?". This chapter explains why adding that condition to an approximate index is harder than it looks, and how to make sure the answer never contains a document the caller was not allowed to read.

Why this matters

Every demo of retrieval searches one pile of documents for one anonymous user. Every real deployment has tenants, roles, departments, document versions, languages and legal holds. Two failures follow. The quiet one is that a filter silently shrinks the result list, so the assistant says "I can't find anything" when the answer exists. The loud one is a permissions leak: an employee's chatbot quotes the salary bands, or one customer's contract appears in another customer's answer. After this chapter you can pick a filtering strategy from the selectivity of the filter, design the metadata a chunk must carry, choose between silo and pool tenancy, enforce document-level access control so that it survives stale data and forgotten code paths, and write the test that proves it. It builds on the approximate indexes of chapter 11 and the hybrid pipeline of chapter 10, and it is the foundation for the RAG system of chapter 13.

Why retrieval needs a WHERE clause

A relational query has two halves: a condition that says which rows qualify, and an ordering that says which come first. A vector search so far has only the second half: "order everything by closeness to this vector". The first half is a filter (also called a predicate): a condition on the metadata stored beside each chunk, such as its tenant, its source system, its language, its date, or the list of people allowed to read it.

Filters appear in a retrieval system for three different reasons, and they have different consequences when they go wrong.

Relevance filters

"Only the 2025 policy", "only English", "only contracts". If the filter is too loose, answers get worse. If it is wrong, answers get worse quietly.

Freshness filters

"Latest version only", "not expired", "not deleted". A missing filter returns superseded text that looks authoritative. See chapter 17.

Security filters

"This tenant", "readable by this user". A missing filter is a data breach, not a bad answer. These must be enforced, never merely requested.

The first two are about quality and the third is about trust. The mechanics of applying them are the same, which is why they share a chapter, but the standard of correctness is not: a relevance filter that misses 3% of documents is a tuning problem; a security filter that misses 3% is an incident.

Selectivity: the number that decides everything

The selectivity of a filter is the fraction of the collection that passes it. A filter on language = "en" in an English corpus has selectivity near 1.0. A filter on tenant = "acme" in a platform with 200 equal tenants has selectivity 0.005. A filter on doc_id = "x" has selectivity one in a million.

Selectivity matters because an approximate index (chapter 11) returns its best guesses for the nearest neighbours of the query, with no knowledge of your filter. If you search first and filter afterwards, only the fraction s of those guesses survive. To end with k results you need to fetch roughly k / s candidates:

candidates needed ≈ k / s

With k = 10: at s = 0.5 you need about 20 candidates; at s = 0.1, about 100; at s = 0.01, about 1,000. The search effort rises as the filter tightens, and an index tuned to return 40 candidates cheaply cannot supply that. The pgvector documentation gives the arithmetic for its HNSW index: with the default hnsw.ef_search of 40 and a filter that matches 10% of rows, a query returns about 4 matching rows on average, not the 10 you asked for.

The worst case is worse than the average. Selectivity measures how many documents pass, but not where they are. If the passing documents happen to be far from the query in embedding space (a small tenant whose documents are about different topics from the ones everybody else writes about), then the nearest candidates contain none of them, and post-filtering returns an empty list however large s is. The experiment below measures all of this.

Three ways to combine a filter with a nearest-neighbour search

The listing builds a small navigable graph in the spirit of the HNSW of chapter 11 (a single layer: each point is linked to its 8 nearest neighbours, plus one random long link so the clusters connect), over 4,000 synthetic 16-dimensional points in 20 clusters. It runs beam search with ef = 40 and four ways of applying a filter, over 200 queries per scenario, and compares each with the exact filtered top 10. "Distance evals" counts how many vectors were compared with the query, a proxy for cost.

"""Filtered search on a small navigable graph: three strategies (chapter 12)."""
import heapq
import numpy as np

rng = np.random.default_rng(12)
N, D, C, M = 4000, 16, 20, 8
centres = rng.normal(0, 2, (C, D))
cluster = rng.integers(0, C, N)
X = centres[cluster] + rng.normal(0, 1, (N, D))

# Graph: each point links to its M nearest neighbours; links are made two-way.
d2 = ((X[:, None, :] - X[None, :, :]) ** 2).sum(-1)
np.fill_diagonal(d2, np.inf)
nbrs = [set() for _ in range(N)]
for i, row in enumerate(np.argsort(d2, axis=1)[:, :M]):
    for j in row:
        nbrs[i].add(int(j)); nbrs[int(j)].add(i)
for i in range(N):                                    # a few long links, so clusters connect
    j = int(rng.integers(0, N)); nbrs[i].add(j); nbrs[j].add(i)
ENTRY = int(np.argmin(((X - X.mean(0)) ** 2).sum(1)))

def dist(q, i):
    return float(((X[i] - q) ** 2).sum())

def search(q, ok, ef, k, mode):
    """mode: 'post' (filter the final list), 'block' (never step on a failing node),
    'through' (walk through failing nodes, keep only passing ones as results)."""
    start = ENTRY
    if mode == "block" and not ok[start]:
        start = int(np.flatnonzero(ok)[0])           # fall back to any passing node
    seen, evals = {start}, 1
    cand = [(dist(q, start), start)]                  # min-heap: to expand
    res = []                                          # max-heap (negated): best ef results
    def keep(dd, i):
        if mode == "post" or ok[i]:
            heapq.heappush(res, (-dd, i))
            if len(res) > ef: heapq.heappop(res)
    keep(cand[0][0], start)
    while cand:
        dd, i = heapq.heappop(cand)
        if len(res) >= ef and dd > -res[0][0]: break
        for j in nbrs[i]:
            if j in seen: continue
            seen.add(j)
            if mode == "block" and not ok[j]: continue
            evals += 1
            dj = dist(q, j)
            if len(res) < ef or dj < -res[0][0]:
                heapq.heappush(cand, (dj, j)); keep(dj, j)
    out = sorted((-a, i) for a, i in res if ok[i])[:k]
    return [i for _, i in out], evals

def exact(q, ok, k):
    idx = np.flatnonzero(ok)
    dd = ((X[idx] - q) ** 2).sum(1)
    return list(idx[np.argsort(dd)[:k]]), len(idx)

def run(label, make_ok, n_q=200, k=10, ef=40):
    print(label)
    print(f"  {'strategy':<22}{'recall@10':>10}{'returned':>10}{'distance evals':>16}")
    qrng = np.random.default_rng(1)
    qs = []
    for _ in range(n_q):
        c = int(qrng.integers(0, C)); qs.append((centres[c] + qrng.normal(0, 1, D), make_ok(qrng, c)))
    for mode, name in (("post", "post-filter"), ("block", "block failing nodes"), ("through", "walk through, keep ok"), ("exact", "pre-filter, exact scan")):
        rec, ret, ev = [], [], []
        for q, ok in qs:
            truth, _ = exact(q, ok, k)
            got, e = exact(q, ok, k) if mode == "exact" else search(q, ok, ef, k, mode)
            if mode == "exact": e = int(ok.sum())
            rec.append(len(set(got) & set(truth)) / max(1, len(truth))); ret.append(len(got)); ev.append(e)
        print(f"  {name:<22}{np.mean(rec):>10.2f}{np.mean(ret):>10.1f}{np.mean(ev):>16.0f}")

def random_ok(frac):
    return lambda r, c: r.random(N) < frac
def tenant_ok(r, c):                                   # a tenant whose documents sit in ONE cluster,
    other = (c + 1 + int(r.integers(0, C - 1))) % C    # while the query lands in a different cluster
    return cluster == other

run("no filter at all (everything passes), for reference", random_ok(1.0))
for frac in (0.5, 0.1, 0.01):
    run(f"filter passes {frac:.0%} of documents, unrelated to content (graph of {N} points, ef=40)", random_ok(frac))
run("filter = one tenant (about 5%), whose documents are far from the query", tenant_ok)

Read the output from top to bottom.

  • No filter. All three graph modes agree: recall 0.99 for about 331 distance evaluations, against 4,000 for the exact scan. This is why you use an approximate index.
  • Post-filter works at 50% (recall 0.99) and degrades fast: at 10% it returns 3.9 results on average and recall is 0.39; at 1% it returns 0.4 results. This is the pgvector arithmetic reproduced: 40 candidates times 10% is 4.
  • Blocking failing nodes (never step onto a node that fails the filter) is cheap, and for a loose filter it is nearly right. But at 10% and 1% the search wanders into a pocket of passing nodes and cannot get out: recall 0.05 and 0.03. The graph's links were made without knowing the filter, so the passing nodes do not form a connected region. In the last scenario the passing nodes do form one cluster, and blocking is perfect (recall 1.00). Whether it works depends on the data, which is a fragile thing to rely on.
  • Walking through failing nodes (use them as stepping stones, but only count passing ones as results) recovers recall 1.00 everywhere. The price is visible in the right-hand column: at 1% selectivity it evaluates 3,995 of the 4,000 vectors, to find 40 passing ones.
  • Pre-filtering with an exact scan is always right, and its cost is exactly the number of passing documents: 2,002, 400, 40, 199. It is the best option whenever few documents pass, and the worst when many do.

Analogy: the librarian and the locked stacks

You ask a librarian for the ten books closest to your topic. A post-filter librarian walks to the shelf, takes the ten nearest books, and then discovers eight are in the locked stacks you cannot enter: you leave with two. A pre-filter librarian first makes a list of every book you are allowed, then reads that whole list: correct, but slow if the list is long. A filtered-traversal librarian walks the aisles in the usual order but only counts the books you can have, and is willing to walk through the locked section to reach the open one beyond.

Where it breaks down: a librarian knows where the locked stacks are before starting. An approximate index usually does not know the filter in advance, because the predicate arrives with the query, and the index structure was fixed when it was built.

Choosing a strategy

The experiment suggests the rule that production engines follow: estimate the selectivity, then pick the strategy that is cheapest at that selectivity. Engines keep statistics on metadata fields (counts per value, histograms for ranges) so that the estimate is a lookup, not a scan.

SelectivityBest strategyWhy
Very tight (a handful to a few thousand passing)Pre-filter, exact scan of the passing setCost is proportional to matches, which is small. Exact, no recall risk. This is the right answer for "this one document" and for most small tenants.
Middle (roughly 1% to 50%)Filtered traversal, with a larger candidate listExact scan is too slow; post-filtering returns too few. The graph is walked with the predicate checked per node.
Broad (more than about half pass)Post-filter with modest oversamplingAlmost every candidate survives, so fetch k / s and filter. Simplest and fastest.

The boundaries are not universal constants: they depend on the index, the dimension, the hardware and the number of matches, so measure them on your data (the lab for this part, lab 4, builds the index you would tune). Real systems have more refined versions of the three ideas.

  • Iterative scanning. Instead of choosing a candidate count in advance, keep widening the search until enough passing rows have been found or a limit is reached. pgvector added this in version 0.8.0 (hnsw.iterative_scan, with strict_order or relaxed_order, and a cap hnsw.max_scan_tuples that defaults to 20,000). It converts "too few results" into "more work", but it is bounded by that cap, so a very selective filter can still come back short.
  • Filter-aware graphs. Because the problem is that the graph does not know the filter, some systems add links that do. Qdrant's documentation describes extra edges built from its payload indexes so that points sharing a value stay connected. The research system ACORN (Patel, Kraft, Guestrin and Zaharia, "ACORN: Performant and Predicate-Agnostic Search Over Vector Embeddings and Structured Data", SIGMOD 2024) builds a denser graph and traverses it as if it were the graph of only the passing points; the authors report 2 to 1,000 times higher throughput than earlier methods at fixed recall.
  • Partitioning. If one field appears in nearly every filter (tenant, usually), make it the unit of storage: a separate index or partition per value. Selectivity becomes irrelevant because each search runs inside one small index. The next sections return to this.
  • Lexical filters are easy. An inverted index (chapter 2) handles a filter by intersecting a postings list for the field with the query's postings, which is what search engines were built for. Filtering is mostly a vector-index problem.

Common misconception

"If a filter returns fewer than k results, the collection has fewer than k matches." Often it does not. With post-filtering or a capped iterative scan, the index simply stopped looking. Always compare the count you get with the count you can prove exists (SELECT count(*) with the same filter), and alert on the difference. A shortfall that is silent becomes "I could not find any information about that" in the assistant's reply, and nobody connects it to the filter.

Designing the metadata

The chunk record, not the vector, is the unit you will filter, cite and delete. Decide its fields before indexing, because adding a field later means re-processing every chunk. A workable minimum:

FieldExampleUsed for
chunk_id, doc_idpol-17#c04, pol-17Citing, de-duplicating, deleting all chunks of a document.
tenant_idacmeIsolation. Mandatory, never nullable.
acl["group:hr", "user:alice"]Document-level access control (below).
source, doc_typesharepoint, policyRelevance filters and routing.
version, is_latest, valid_from, valid_to7, true, datesFreshness: "current policy as of a date".
languageenLanguage filters and analyser choice (chapter 22).
section_path, page, offsetsLeave > Parental, 4Citations that point to a place (chapter 16).

Four practical rules follow from the mechanics above.

  1. Index the fields you filter on. A vector store with no index on a metadata field evaluates the predicate by scanning, and its statistics cannot estimate selectivity. Declare payload or filter indexes for tenant, source, type and dates.
  2. Watch cardinality. A field with a handful of values (language) is cheap. A field with millions of distinct values (user id inside the ACL) needs a representation the engine can index, such as a list field with an inverted index, not a string you parse at query time.
  3. Inherit from the document. Every chunk copies the document's tenant, ACL, version and dates, so a filter needs no join. The price is that changing one document-level field means updating many chunks; plan the update path (below) before you choose the layout.
  4. Prefer "is_latest" to deleting old versions immediately. Keeping the previous version, flagged, allows "as of" questions and a fast rollback, and the filter is_latest = true is cheap and almost always broad.

Tenant isolation

A tenant is a customer, organisation or workspace whose data must not be visible to any other. Multi-tenancy & isolation in the security course describes the three general models; here is what each means for a retrieval index.

Silo: one index per tenant

Strongest isolation. A bug in a filter cannot cross tenants because the data is not in the same index. Per-tenant encryption keys and deletion ("drop the index") are easy. Cost: fixed overhead per index, poor utilisation for many small tenants, and operational load that scales with the tenant count.

Pool: shared index, tenant filter

Cheapest and simplest to operate for thousands of tenants. Isolation depends entirely on a predicate being present on every query. Tenants share caches and capacity, so one large tenant can slow the others. Selectivity is tiny, so use partitioning or pre-filtering.

Bridge: partitions in a shared index

The tenant value selects a partition, namespace or shard inside one cluster. Search runs inside one small partition, so filtering costs little, and large tenants can be moved to their own silo. Isolation is by construction, with a lighter operational burden.

Most platforms start in the pool or bridge model and move their largest or most regulated tenants to silos. Whatever the model, one rule is non-negotiable: the tenant comes from the authenticated session, never from the request. If the model, the browser or an API parameter supplies the tenant id, then a prompt-injected instruction or a tampered request can change it. The identity (sessions and tokens) is verified at the edge; the retrieval layer receives a Principal it cannot alter and adds the predicate itself. The next listing makes that concrete.

Document-level access control

Within a tenant, not everyone may read everything. HR's pay bands, the board's minutes, a customer's contract: each document has an access control list (ACL), the set of users and groups allowed to read it. Security trimming is the practice of removing, from search results, everything the caller cannot read, before they see it. Enterprise search products have done this for decades; a RAG system must do it before the text reaches the model, because anything in the prompt can appear in the answer.

There are two standard ways to trim, and a sound system uses both.

  1. Filter by ACL in the index. Each chunk stores the principals allowed to read it, and the query carries the caller's identity set (user id plus all the groups they belong to). The predicate is "ACL intersects the caller's identities". It is fast, because the index applies it during the search, and it is the only way to get k good results rather than k minus whatever was hidden. Its weakness is that the ACL in the index is a copy.
  2. Verify against the source of truth. After retrieval, ask the system that owns the document ("can this user read this file, right now?") for the few survivors. It is authoritative and current, but it costs a call per document, so it can only be applied to a short list, never to the whole corpus.

The copy goes stale. Someone is removed from the HR group at 09:00; the index learns at 09:20 from the next sync; a cached session token lists the old groups until it expires. For those minutes, step 1 alone still returns the pay bands. Step 2 closes the gap for the documents that matter. Both appear in the next listing, along with a bug that is common in practice: the filter was added to the lexical retriever and forgotten in the dense one, so documents the user may not see arrive through the other door and get fused into the results.

"""Tenant and document-level filtering in a hybrid retriever (chapter 12)."""
import math, re, zlib
from collections import Counter
from dataclasses import dataclass

DOCS = {  # id: (tenant, allowed groups, text)
 "acme-handbook": ("acme", {"staff"}, "Staff may work remotely two days a week. Expense claims go to the finance portal."),
 "acme-pay-bands": ("acme", {"hr"}, "Salary bands: engineer level 3 earns 82,000 to 96,000. Pay review happens each March."),
 "acme-board": ("acme", {"board"}, "Board minutes: acquisition of Initech approved. Keep confidential until announced."),
 "acme-faq": ("acme", {"staff"}, "How do I claim travel expenses? Submit receipts within 30 days."),
 "globex-handbook": ("globex", {"staff"}, "Globex staff may work remotely three days a week. Salary questions go to payroll."),
 "globex-pay": ("globex", {"hr"}, "Globex salary bands: engineer level 3 earns 90,000 to 110,000."),
}
STOP = {"a", "the", "to", "of", "do", "i", "is", "how", "my", "go", "may", "each", "for"}
def toks(t): return [w for w in re.findall(r"[a-z0-9]+", t.lower()) if w not in STOP]

def bm25(q, ids, k1=1.2, b=0.75):
    docs = {d: toks(DOCS[d][2]) for d in DOCS}
    n, avg = len(docs), sum(map(len, docs.values())) / len(docs)
    df = Counter(t for v in docs.values() for t in set(v))
    out = {}
    for d in ids:
        tf = Counter(docs[d]); s = 0.0
        for t in toks(q):
            if tf[t]:
                s += math.log(1 + (n - df[t] + .5) / (df[t] + .5)) * tf[t] * (k1 + 1) / (tf[t] + k1 * (1 - b + b * len(docs[d]) / avg))
        out[d] = s
    return out

def vec(t, dim=256):                       # stand-in embedder: hashed character trigrams
    v = [0.0] * dim; t = " " + " ".join(toks(t)) + " "
    for i in range(len(t) - 2): v[zlib.crc32(t[i:i+3].encode()) % dim] += 1
    n = math.sqrt(sum(x * x for x in v)) or 1
    return [x / n for x in v]
def dense(q, ids):
    qv = vec(q); return {d: sum(a * b for a, b in zip(qv, vec(DOCS[d][2]))) for d in ids}

def rrf(*lists, k=60):
    out = Counter()
    for lst in lists:
        for r, d in enumerate(lst, 1): out[d] += 1 / (k + r)
    return [d for d, _ in out.most_common()]
def top(scores, n=3, floor=0.0):
    return [d for d, s in sorted(scores.items(), key=lambda kv: (-kv[1], kv[0])) if s > floor][:n]

@dataclass(frozen=True)
class Principal:           # comes from the verified session token, never from the request body
    user: str; tenant: str; groups: frozenset

def visible(doc, p, acl=None):
    tenant, groups, _ = DOCS[doc]
    return tenant == p.tenant and bool((acl or {}).get(doc, groups) & p.groups)

def buggy_search(q, p):    # filter applied on the lexical side only
    ids = [d for d in DOCS if visible(d, p)]
    return rrf(top(bm25(q, ids)), top(dense(q, list(DOCS)), floor=0.05))[:3]

def scoped_search(q, p, acl=None):   # one predicate, handed to every retriever
    ids = [d for d in DOCS if visible(d, p, acl)]
    return rrf(top(bm25(q, ids)), top(dense(q, ids), floor=0.05))[:3]

alice = Principal("alice", "acme", frozenset({"staff"}))
bob = Principal("bob", "acme", frozenset({"staff", "hr"}))
q = "what salary does an engineer level 3 earn"
print("buggy, alice (staff):  ", buggy_search(q, alice))
print("scoped, alice (staff): ", scoped_search(q, alice))
print("scoped, bob (staff+hr):", scoped_search(q, bob))

# Stale index: bob leaves HR at t1. The index copy of the ACL has not caught up.
index_acl = {d: g for d, (_, g, _) in DOCS.items()}
authority = {d: set(g) for d, g in index_acl.items()}
bob_now = Principal("bob", "acme", frozenset({"staff"}))   # identity provider already says: no hr
hits = scoped_search(q, bob)                               # query carries the OLD groups (cached token)
verified = [d for d in hits if visible(d, bob_now, authority)]
print("\nstale token, filter only:      ", hits)
print("after verify against authority:", verified)

# Differential test: for every principal and every query, results must be inside the allowed set.
people = [alice, bob_now, Principal("carol", "acme", frozenset({"board", "staff"})), Principal("dan", "globex", frozenset({"staff"}))]
queries = [q, "remote work policy", "board minutes acquisition", "travel expenses", "salary bands"]
for name, fn in (("buggy_search", buggy_search), ("scoped_search", scoped_search)):
    leaks = [(p.user, qq, d) for p in people for qq in queries for d in fn(qq, p) if not visible(d, p)]
    print(f"{name}: {len(people) * len(queries)} checks, {len(leaks)} leaks", leaks[:2])

Four things to notice. First, the buggy search shows Alice (who is plain staff) the Globex pay document and Acme's HR pay bands: the dense retriever had no predicate. Second, the scoped search returns acme-faq and acme-handbook for Alice's salary question, which is a correct, leak-free result and a correct non-answer: nothing she may read contains the answer, and the generator should say so rather than guess (grounding and abstention). Third, the stale-token case is caught by the verification step. Fourth, the differential test at the bottom is the one that finds the bug: 20 principal-and-query checks, 40 leaked documents from the buggy version, none from the scoped one.

Systems connection

Security trimming is the authorisation problem of the security course, with one twist: the check runs inside a ranking operation instead of before a single object fetch, so broken object-level authorisation takes the form of a result set containing objects the caller should not know exist. Keeping the index ACL in step with the source is a change-data-capture problem: stream permission changes as events, apply them in order, and measure the lag, because the lag is exactly your exposure window. And deleting a person's data from an index, their embeddings included, is a data-protection requirement, not a nicety.

Many groups, many documents

Two scaling problems appear in large organisations. A user may belong to thousands of groups (nested directory groups are expanded), making "ACL intersects identities" a large predicate. And a company may have millions of documents whose permissions are inherited from folders, so a single folder change affects a huge number of chunks. The usual answers:

  • Expand at index time, not query time, where you can. Store the resolved list of principals (or group ids) on each chunk, so the query predicate is a small set intersection. Folder changes trigger a background re-stamp of the affected chunks.
  • Invert when the user's set is smaller. If a user is in few groups but documents have many readers, filter on the user's group ids against a per-chunk list of allowed group ids, and do not store individual users at all.
  • Use a relationship-based authorisation service for hard cases. Google's Zanzibar (Pang et al., "Zanzibar: Google's Consistent, Global Authorization System", USENIX ATC 2019) and its open implementations answer "can user U read object O?" by following relationships (user in group, group member of folder, folder contains document). Retrieval then uses the service in two ways: ask for the list of objects the user can read and use it as a filter when that list is small, or fetch candidates and check each one. The check-then-filter pattern is the verification step above, made first-class.

Where permissions leak anyway

Filtering the index is necessary but not sufficient. The OWASP list of risks for LLM applications includes Vector and Embedding Weaknesses (LLM08:2025), naming unauthorised access, cross-context leakage in multi-tenant vector stores and embedding inversion as the main ones, and recommending permission-aware stores with strict partitioning and immutable logs of retrieval activity. In practice, leaks arrive by side doors.

Common misconception

"Tell the model not to reveal documents the user isn't allowed to see." By the time the model sees them the leak has happened: they are in its context, and instructions are requests, not enforcement. Access control belongs in the data layer, before the prompt is built. The model should be unable to see forbidden text, not asked to be discreet about it.

Testing that the wall holds

Access control that is not tested drifts. Three tests catch most failures, and all of them are cheap.

  1. Differential test. For a matrix of principals and queries, assert that every returned document is visible to that principal according to the source of truth. This is the last block of the listing. Run it on every deploy and on every change to the retrieval code.
  2. Canary documents. Plant a document in each restricted scope that contains a unique, meaningless phrase ("zebra-quartz-4471"). Query for the phrase as a user who should not see it, through every interface, including the assistant's answer. Any appearance is a leak, and the test needs no judgement.
  3. Revocation test. Remove a user from a group, then measure how long until the user can no longer retrieve the group's documents. The measured delay is your exposure window; compare it with the figure your security team signed off.

Add a fourth for quality: the shortfall alarm. For a sample of production queries, log the number of results returned against the number of matching rows the filter admits. A filter that returns fewer than k results when thousands match is the post-filtering failure of the first half of this chapter.

State of play, October 2026

Filtered approximate search is an active area, and engines differ in what they implement. Checked for this chapter: pgvector 0.8.0 added iterative index scans (see the pgvector README; settings and defaults can change between releases), and the ACORN paper (SIGMOD 2024) reports its throughput gains against earlier methods, not against every current engine. Qdrant describes its filter-aware graph in its own documentation, so check the current version there. Before choosing a store, run your own filters at your own selectivities and measure recall against an exact filtered scan, as in the listing: vendor defaults are tuned for unfiltered search. Standards for authorisation in AI applications are also moving; treat the OWASP list as a checklist rather than a specification.

Key takeaways

  • A filter's selectivity decides the strategy: pre-filter and scan when few documents pass, filtered traversal in the middle, post-filter with oversampling when most pass.
  • Post-filtering needs about k / s candidates, so tight filters on an approximate index return too few results, sometimes none, and the shortfall is silent.
  • A graph index built without the filter can leave the passing documents unreachable; filter-aware graphs, walking through failing nodes, or partitioning fix this at different costs.
  • Every chunk carries tenant, ACL, version, dates and source as indexed metadata inherited from its document.
  • The tenant and identity come from the verified session. The model never supplies them.
  • Trim by ACL in the index, then verify the short list against the source of truth. The index copy of permissions goes stale.
  • Leaks come through the second retriever, caches, derived summaries, logs and agents. Build the predicate in one place and test with differential tests and canary documents.

Further reading

  • pgvector README, "Filtering" and "Iterative Index Scans". The clearest short statement of why approximate indexes return too few rows under a filter, and the settings that mitigate it.
  • Patel, Kraft, Guestrin and Zaharia, "ACORN: Performant and Predicate-Agnostic Search Over Vector Embeddings and Structured Data" (SIGMOD 2024). A graph index designed for filtered search with arbitrary predicates.
  • OWASP, "LLM08:2025 Vector and Embedding Weaknesses". The risk list and mitigations for access control, cross-tenant leakage and embedding inversion.
  • Pang et al., "Zanzibar: Google's Consistent, Global Authorization System" (USENIX ATC 2019). Relationship-based access control at scale, the model behind many open authorisation services.
  • Manning, Raghavan and Schütze, "Introduction to Information Retrieval" (2008). Chapters on index construction and on parametric and zone search, the lexical ancestors of metadata filtering.

Check your understanding

An approximate index returns its 40 nearest candidates. You post-filter them with a condition that 5% of the collection satisfies. About how many results do you expect, and what is the smallest fix?

  1. About 20 results; lower the filter to 10%.
  2. About 2 results; fetch more candidates (about k / 0.05), or pre-filter, or use a filter-aware search.
  3. About 40 results; no fix needed.
  4. About 2 results; switch to a larger embedding model.
Forty candidates times 0.05 is two survivors on average. The fix is about the search procedure (more candidates, applying the filter earlier), not the embedder. Choice 3 forgets that the filter removes candidates after they were chosen; choice 4 treats a plumbing problem as a model problem.

A filter admits only 200 documents out of 5 million. Which strategy is usually best?

  1. Post-filter with 40 candidates.
  2. Post-filter with the candidate list raised to 5 million.
  3. Filtered graph traversal, because graphs are always fastest.
  4. Pre-filter and compute exact distances to the 200 documents.
With 200 passing documents an exact scan costs 200 distance computations, is exact, and cannot miss anything. Traversal would visit a large part of the graph to find them, as the 1% row of the listing showed. Post-filtering needs thousands of candidates per result.

A user's group membership was revoked 10 minutes ago, but the index still lists the old group on a document. What closes the gap for that document most reliably?

  1. Re-checking the retrieved short list against the system that owns the document, with the user's current groups.
  2. Telling the model in the system prompt not to reveal that document.
  3. Raising the candidate count so the document ranks lower.
  4. Hashing the document ids in the index.
The index holds a copy of permissions, so it is only as fresh as its sync. A verification call to the source of truth is current. Prompt instructions are requests, not enforcement, and ranking or hashing changes nothing about who is allowed.

A hybrid search applies the tenant filter in the BM25 query but not in the vector query. A differential test with ten users and ten queries reports no leaks. What is the most likely explanation?

  1. The vector index applies the filter automatically.
  2. Hybrid search removes leaks through rank fusion.
  3. The test queries or users happened not to make the vector retriever return another tenant's documents; the test is too small or too narrow.
  4. Vector retrieval cannot return documents from other tenants.
An unfiltered retriever returns the nearest documents from every tenant, but a given test may not hit them, particularly if the chosen queries are tenant-specific. Use many queries, including ones that deliberately target other tenants, and add canary documents. Fusion keeps documents from both lists; it does not remove anything.

Where should the tenant id used in a retrieval predicate come from?

  1. A parameter in the API request, validated against a list of known tenants.
  2. The verified session or token, attached by the retrieval layer, with no way for the caller or the model to override it.
  3. The model's tool call, because it knows the conversation.
  4. A cookie set by the front end.
A value the caller or model can set can be set wrongly or maliciously, even if it is a valid tenant. The identity should be bound to the authenticated session on the server side. Validation against a known list proves only that the tenant exists, not that the caller belongs to it.

A semantic cache returns a stored answer when a new question's embedding is within a small distance of an earlier one. What is the permissions risk, and the fix?

  1. None: the cache stores only embeddings.
  2. The cache is slow; add more memory.
  3. Answers go stale; add an expiry.
  4. A similar question from a user with less access receives the first user's answer; key the cache on tenant and permission fingerprint, or do not cache personalised answers.
The cached item is an answer generated from documents the first user could read. Serving it to anyone who asks something similar bypasses the retrieval filter altogether. Expiry (choice 3) is a real concern about freshness but does not address access.

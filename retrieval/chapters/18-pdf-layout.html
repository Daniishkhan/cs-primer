PDFs & Layout

Most of the documents an organisation actually cares about, such as contracts, filings, invoices, manuals and reports, arrive as PDFs. A PDF looks like a document but is closer to a drawing. This chapter opens one up, shows why text cannot simply be "extracted" from it, separates born-digital from scanned files, and builds up the layout analysis and reading-order recovery that turn a page of marks into structured text a retrieval system can use.

Why this matters

The first half of this course assumed that documents were clean text. Real enterprise corpora are mostly PDFs, and what you index from them is only as good as what you extract. If a two-column page is read straight across, every sentence is spliced with its neighbour from the other column and no retriever can rescue it. If a scanned page yields no text, the document is invisible to search. If a footer sits in the middle of a paragraph, an embedding of that chunk is quietly polluted. After this chapter you can inspect what a PDF holds, decide per page whether it needs OCR (chapter 19), recover the blocks and reading order, and keep the page-and-box provenance that makes citations (chapter 16) possible.

A PDF is a drawing, not a document

Adobe introduced the PDF (Portable Document Format) in the early 1990s with a single goal: a file that prints and displays identically on any device. It is now an international standard, ISO 32000 (ISO 32000-1 in 2008, based on PDF 1.7, and ISO 32000-2 in 2020, PDF 2.0). To achieve identical appearance, a PDF does not store a document's structure (this is a paragraph, this is a heading, these two lines are one sentence). It stores instructions for painting a page: put this string, in this font, at this position; draw this line; place this image here. That is a page description language.

Compare the formats you know. In HTML or a word processor file, a paragraph is an object that contains its text, and the layout is computed when the file is displayed. In a PDF, the layout was computed long ago by the program that produced the file, and only the result was kept. The words of a sentence may be stored as separate fragments, a heading is a string drawn at a larger size, and a "table" is text fragments placed in a grid with some lines drawn between them. The visual document is all there; the logical document is gone, and extraction is the attempt to reconstruct it.

Analogy: a printed page versus a typesetter's instructions

Think of a PDF as the instructions a typesetter followed, not the manuscript: "set these letters at 11 points, 330 points from the left edge and 690 up from the bottom". Anyone can follow the instructions and reproduce the page. But to recover the manuscript, you must look at the result and infer which marks form words, which words form lines, and which lines form columns and paragraphs.

Where it breaks down: an inference from a finished page can be checked by eye, whereas a program reading a thousand pages cannot. Also, some PDFs do carry hidden structure (tagged PDF, for accessibility), and when it is present and correct it is a gift. It is often absent or wrong, so you cannot depend on it.

What is inside a PDF

A PDF file is a collection of numbered objects (dictionaries, arrays, strings, numbers and binary streams) plus a table at the end, the cross-reference table, that records where each object sits in the file, and a trailer that names the root. The objects form a tree: a root object (the Catalog) points to a page tree; each page object points to its resources (fonts, images) and to a content stream, a compressed sequence of drawing operators. The text of the page lives only in that stream.

To make this concrete, here is a PDF built by hand in a few lines of Python (so there is no library to trust), then opened using nothing but the standard library. The builder is folded away; it only writes the objects and the cross-reference table described above. The page it draws has a title, a page number, and two columns of text, written to the file in a deliberately awkward order: right column first, then left, then title, then page number. That is not contrived: PDF producers write content in whatever order their layout engine emits it.

"""Hand-build tiny PDFs so we can look inside them without any library."""
import zlib

def build(objects):
    """objects: dict num -> bytes (object body). Returns the PDF bytes with xref."""
    out = bytearray(b"%PDF-1.4\n"); offs = {}
    for n in sorted(objects):
        offs[n] = len(out)
        out += b"%d 0 obj\n" % n + objects[n] + b"\nendobj\n"
    xref = len(out)
    out += b"xref\n0 %d\n0000000000 65535 f \n" % (max(objects) + 1)
    for n in range(1, max(objects) + 1):
        out += b"%010d 00000 n \n" % offs[n]
    out += b"trailer\n<< /Size %d /Root 1 0 R >>\nstartxref\n%d\n%%%%EOF\n" % (max(objects) + 1, xref)
    return bytes(out)

def stream(data, compress=True):
    if compress:
        z = zlib.compress(data)
        return b"<< /Length %d /Filter /FlateDecode >>\nstream\n" % len(z) + z + b"\nendstream"
    return b"<< /Length %d >>\nstream\n" % len(data) + data + b"\nendstream"

def page_objects(content, image=None):
    """Objects 1-5 (+6 image): catalog, pages, page, font, contents."""
    res = b"/Font << /F1 4 0 R >>"
    if image: res += b" /XObject << /Im1 6 0 R >>"
    objs = {
      1: b"<< /Type /Catalog /Pages 2 0 R >>",
      2: b"<< /Type /Pages /Kids [3 0 R] /Count 1 >>",
      3: b"<< /Type /Page /Parent 2 0 R /MediaBox [0 0 612 792] /Contents 5 0 R /Resources << " + res + b" >> >>",
      4: b"<< /Type /Font /Subtype /Type1 /BaseFont /Helvetica >>",
      5: stream(content),
    }
    if image: objs[6] = image
    return objs

def text(x, y, s, size=11, mode=None):
    tr = b"%d Tr " % mode if mode is not None else b""
    return b"BT /F1 %d Tf %s%d %d Td (%s) Tj ET\n" % (size, tr, x, y, s.encode())

# A two-column page. The content stream lists the RIGHT column first, then the
# left, then the header and page number last: stream order is not reading order.
def two_column_pdf():
    c = b""
    c += text(330, 690, "Right column, paragraph one starts here and")
    c += text(330, 676, "continues onto a second line of text.")
    c += text(330, 640, "Right column, paragraph two.")
    c += text(72, 690, "Left column, paragraph one starts here and")
    c += text(72, 676, "continues onto a second line of text.")
    c += text(72, 640, "Left column, paragraph two.")
    c += text(72, 740, "Annual Report 2026", 16)
    c += text(300, 40, "- 7 -", 9)
    return build(page_objects(c))

def scanned_pdf(invisible_text=False):
    w = h = 8
    img = (b"<< /Type /XObject /Subtype /Image /Width 8 /Height 8 /ColorSpace /DeviceGray "
           b"/BitsPerComponent 8 /Length 64 >>\nstream\n" + bytes(range(0, 256, 4))[:64] + b"\nendstream")
    c = b"q 612 0 0 792 0 0 cm /Im1 Do Q\n"
    if invisible_text:
        c += text(72, 690, "Invoice 4471 total 1,250.00", 11, mode=3)
    return build(page_objects(c, image=img))

Read the last block carefully. The page has eight text operations, and what they give you is strings with positions, in stored order. There is no "left column" object. The line "continues onto a second line of text." appears twice, once at x = 330 and once at x = 72, and nothing in the file says that the first belongs to the paragraph starting "Right column". A reader's eye sees two columns instantly because of the whitespace between them. A program has to find it.

The coordinate system explains the numbers. The origin is the bottom-left corner of the page and y grows upwards, the opposite of screen coordinates. The unit is the point, 1/72 of an inch, so a US Letter page is 612 by 792 points. The diagram plots the same eight strings on the page, numbered in the order they are stored.

Running pdftotext -raw (from the open-source Poppler tools) on the same file prints the lines in exactly the stored order, right column first. Its -layout mode, which tries to preserve physical layout, prints the two columns side by side. That is a first hint that "extraction" has options and that each option is a decision about layout.

Why extraction is harder than it looks

Beyond the missing structure, PDFs have a list of quirks that each corrupt text in a specific way. Knowing them tells you what to check when extracted text looks wrong.

Words are gaps, not characters
Producers often place each word, or even each syllable, separately, and a space is a movement, not a character. In the TJ operator, numbers in an array between strings adjust the position in thousandths of an em; a large negative number is a word gap. An extractor must decide a threshold, and a wrong one glues words together ("Revenuegrew12%") or splits them.
Reading order is not stored order
As shown above. Stored order reflects how the producing program emitted content, which can be column by column, in reverse, or in arbitrary chunks (headers last, footnotes first).
Fonts and encodings
Text is stored as glyph codes, and each embedded font may map codes to glyphs arbitrarily. A PDF should carry a ToUnicode map that says which characters each code means. When it does not, an extractor can only guess, and the result is gibberish or placeholders such as (cid:123). Text drawn as outlines or as images has no characters at all.
Ligatures, hyphenation, soft breaks
A ligature glyph such as "ﬁ" extracts as one special character that no search for "fi" will match. A word broken across lines ("inter-" and "national") arrives as two fragments.
Boilerplate
Running headers, footers, page numbers and watermarks repeat on every page and sit in the stream like body text.
Tables and forms
A table is aligned text plus drawn lines; the cell structure is implicit. Fillable forms may keep values in separate annotation objects, not in the page text (chapter 20).
Hidden text
Text can be present but not visible: invisible OCR text (next section), white text on white, or text outside the page box. What is extracted may differ from what a reader sees, which is also a security concern (A6 chapter 13 on instructions hidden in documents).

Some of these have cheap repairs. The listing below shows three on constructed examples: rebuilding spaces from a TJ array, repairing a hyphenated line break, and finding headers and footers by their repetition across pages.

import re

# 1. Spaces in a PDF are often not characters but gaps. In a TJ array, numbers are
#    adjustments in thousandths of an em (negative = move right). Rebuild the words.
tj = "[(Rev) 20 (enue) -250 (grew) -250 (12%) -250 (in) -250 (the) -250 (inter-)] TJ"
naive  = "".join(re.findall(r"\((.*?)\)", tj))
parts  = re.findall(r"\((.*?)\)|(-?\d+(?:\.\d+)?)", tj)
rebuilt = ""
for s, n in parts:
    if s: rebuilt += s
    elif float(n) < -150: rebuilt += " "          # a gap wider than ~0.15 em is a word space
print("naive  :", naive)
print("rebuilt:", rebuilt)

# 2. Join lines into paragraphs, repairing hyphenation at line ends.
lines = ["Revenue grew 12% in the inter-", "national segment, led by two", "markets."]
text = " ".join(lines)
text = re.sub(r"(\w)- (\w)", r"\1\2", text)          # careful: also hits real hyphens ("e- mail")
print("joined :", text)

# 3. Headers and footers repeat on every page; find lines that recur once digits are ignored.
pages = [["ACME Annual Report 2026", "Revenue grew 12%.", "Page 1"],
         ["ACME Annual Report 2026", "Costs fell 3%.", "Page 2"],
         ["ACME Annual Report 2026", "Headcount rose 8%.", "Page 3"]]
shape = lambda ln: re.sub(r"\d+", "#", ln)
seen = {}
for pg in pages:
    for ln in {shape(l) for l in pg}: seen[ln] = seen.get(ln, 0) + 1
boiler = {s for s, n in seen.items() if n >= 2 and len(pages) >= 3}
print("boilerplate:", sorted(boiler))
print("body       :", [[l for l in pg if shape(l) not in boiler] for pg in pages])

Each repair is a heuristic with a failure mode. The space threshold of -150 is a tuned constant, and fonts with tight or loose spacing break it. The hyphen rule would also glue a genuinely hyphenated compound ("e-" and "mail" at a line end), so production code checks the joined word against a vocabulary. And the boilerplate detector assumes at least three pages and removes any line that recurs, which would wrongly delete a table heading repeated on every page of a long table. None of them is wrong to use. All of them should be measured on your documents, which is why a pipeline keeps the original text and the raw positions, not only the cleaned output.

Common misconception

"PDF text extraction is a solved problem, and OCR is only for scans." Extraction from a born-digital PDF recovers characters reliably when the font maps are good. It does not recover structure, and it silently produces the wrong order on multi-column pages. The failures do not raise errors: the text looks plausible and the embeddings are computed from scrambled paragraphs. Always look at the extracted text of a sample from every new source before trusting an index built on it.

Born-digital, scanned, and the in-between

A born-digital PDF was produced by software from a digital source (a word processor, a report generator, a browser's print function). It contains real text operators, and its text layer is usually accurate. A scanned PDF is a photograph of paper: each page is one big image and the file contains no characters at all. Extracting text from a scanned page requires optical character recognition (OCR), which reads the pixels (chapter 19).

Between the two sits a common third kind. Many scanning systems run OCR and then store the result as an invisible text layer over the image, using text render mode 3 ("neither fill nor stroke"), which positions the characters without painting them. The file looks like a scan on screen, can be searched and copied from, and is called a "searchable PDF". Whoever built that layer used some OCR engine of some vintage, possibly years ago and possibly poor, and a naive extractor will return its output as if it were reliable. You inherit its mistakes without knowing.

You can tell which kind you have from the content stream, as the next listing shows: count the visible and invisible characters, and measure how much of the page an image covers. It runs on three tiny PDFs made by the same builder (the two-column page, an image-only page, and an image page with an invisible text line).

import re, zlib

def content_of(path):
    data = open(path, "rb").read()
    m = re.search(rb"5 0 obj\n<<.*?>>\nstream\n(.*?)\nendstream", data, re.S)
    return zlib.decompress(m.group(1)).decode("latin-1")

def classify(path, page_area=612 * 792):
    c = content_of(path)
    visible = invisible = 0
    for block in re.findall(r"BT(.*?)ET", c, re.S):
        chars = sum(len(s) for s in re.findall(r"\((.*?)\)\s*T[Jj]", block))
        if re.search(r"\b3 Tr\b", block): invisible += chars   # render mode 3: not painted
        else:                             visible += chars
    img = 0.0
    for w, h in re.findall(r"q\s+(\d+) 0 0 (\d+) 0 0 cm\s+/\w+ Do", c):
        img += int(w) * int(h) / page_area
    if visible >= 20 and img < 0.5:      kind = "born-digital"
    elif img >= 0.5 and invisible >= 20: kind = "scanned, with an OCR text layer"
    elif img >= 0.5:                     kind = "scanned, image only: needs OCR"
    else:                                kind = "unclear"
    return visible, invisible, img, kind

for f in ["two_column.pdf", "scan.pdf", "scan_ocr.pdf"]:

    print(f"{f:<14}{v:>8}{i:>8}{img:>11.0%}   {kind}")

Real classifiers add checks this one lacks: fonts and encodings, many images, text clipped off the page, and a text-quality test for the text layer, which matters most for the third kind. Cheap tests are the share of replacement or control characters, the share of tokens found in a dictionary, the number of characters per page compared with the page's visual density, and a comparison against OCR output on a sample of pages. A text layer that fails the test is discarded and the page is re-recognised.

The policy that follows is simple enough to state in four lines. Use the text layer when it exists and passes quality checks, because it is exact where OCR is probabilistic. Run OCR when it does not exist or fails. Decide this per page, and sometimes per region (a scanned stamp on a born-digital page). And always keep the page image, because layout analysis, OCR, visual retrieval (chapter 21) and human review all need it.

From marks to structure: layout analysis

Layout analysis takes a page (as an image, as positioned text, or both) and produces blocks: rectangles, each with a type (title, section heading, paragraph, list item, table, figure, caption, footnote, page header, page footer, formula) and, ideally, an order. It is the step that converts a bag of strings into the logical parts a human sees. There are two broad approaches, and serious systems combine them.

Rule-based layout analysis works on the text layer of born-digital PDFs. It groups characters into words using spacing, words into lines using baselines, lines into blocks using vertical gaps and alignment, and infers types from font size and weight (larger and bold means heading), position (in the top or bottom margin means header or footer) and repetition across pages. It is fast, explainable and exact about characters. It is brittle on unusual designs and cannot see anything that is not in the text layer, such as a figure or a scanned page.

Learned layout detection treats the page image as a picture and the problem as object detection: draw a rectangle round each layout element and name its class. It works on any page, scanned or not, and learns designs that rules would miss, at the cost of needing training data and GPU time, and of making mistakes that are harder to explain. The key resource is DocLayNet (Pfitzmann et al., 2022, "DocLayNet: A Large Human-Annotated Dataset for Document-Layout Analysis", KDD 2022): 80,863 manually annotated pages with bounding boxes in 11 classes, namely Caption, Footnote, Formula, List-item, Page-footer, Page-header, Picture, Section-header, Table, Text and Title. The pages come from six document categories: financial reports, scientific articles, laws and regulations, government tenders, manuals and patents. A subset was annotated by two or three people to measure inter-annotator agreement, and the authors report that the best object-detection baselines they tried fell about 10 per cent short of that agreement (in mAP, the standard detection metric), and that models trained on DocLayNet transfer more robustly than models trained on the earlier PubLayNet or DocBank datasets.

The class list is worth reading as a design document. Page-header and Page-footer exist as their own classes so that boilerplate can be dropped. Caption and Footnote exist so that they can be kept with the figure, table or sentence they belong to. Section-header and Title supply the boundaries for structure-aware chunking (chapter 14). List-item is its own class so that a list is not read as one lump of text. Each class is a decision you do not need to make with heuristics.

Open-source converters now package this. Docling (IBM Research Zurich, now hosted by the LF AI & Data Foundation, MIT-licensed code) produces a unified document representation, DoclingDocument, and its technical report (Auer et al., 2024) describes layout analysis with a model trained on DocLayNet and table structure recognition with a model called TableFormer. How such systems are put together and evaluated is the subject of case study C7.

State of play, October 2026

Document-parsing models turn over every few months and benchmark leaderboards move with them, so no ranking is reproduced here. OmniDocBench (CVPR 2025) is a widely used benchmark of 1,651 PDF pages with ten document types, scoring text by normalised edit distance, tables by TEDS, formulas by CDM, and reading order by edit distance. Its README (read in October 2026) notes that text evaluation currently covers only Chinese and English, that the dataset is for research use only, and that its headline score combines three of the sub-scores, so a model strong on tables can top the list while being weak on your text. What lasts is the method of this chapter: separate the layers, keep provenance, and measure on your own pages.

Reading order

Once you have blocks, you need to put them in an order. Reading order is the sequence in which a person would read the blocks of a page. It matters for retrieval because chunks are made by concatenating text: if the order is wrong, a chunk joins unrelated sentences, and an answer synthesised from it can be wrong in ways nobody notices. Three ordering rules are common.

  1. Stored order. Use the content stream's sequence. Correct when the producer wrote text in reading order (common for simple documents from word processors), wrong otherwise, as the listing above showed.
  2. Sort by position. Order blocks by top edge, then by left edge. Right for single-column pages. On two columns, blocks at the same height from different columns alternate: left, right, left, right.
  3. Recursive XY-cut. A classic top-down method (Nagy and Seth, 1984). Look for the widest band of empty space that cuts the page, horizontally or vertically; split there; recurse on each part. Full-width titles and figures split off first, columns separate where whitespace separates them, and each column is then read top to bottom. Its weakness is that it needs clean cuts.
import re, zlib

def lines_of(path):
    """(x, y, size, text) for every text-showing operator, in stream order."""
    data = open(path, "rb").read()
    content = zlib.decompress(re.search(rb"stream\n(.*?)\nendstream", data, re.S).group(1)).decode("latin-1")
    found = (re.search(r"/F1 (\d+) Tf .*?(\d+) (\d+) Td \((.*)\) Tj", ln) for ln in content.splitlines())
    return [(int(t.group(2)), int(t.group(3)), int(t.group(1)), t.group(4)) for t in found if t]


def box(it):
    x, y, size, s = it
    return (x, y, x + len(s) * size * 0.5, y + size)   # (left, bottom, right, top); width ~ half an em per char

def best_cut(items, axis):
    """Widest empty band along one axis. Returns (gap, [first_group, second_group]) in reading order."""
    lo, hi = (1, 3) if axis == "y" else (0, 2)
    s = sorted(items, key=lambda it: box(it)[lo])
    reach, best, at = box(s[0])[hi], 0, None
    for n, it in enumerate(s[1:], 1):
        gap = box(it)[lo] - reach
        if gap > best: best, at = gap, n               # remember the widest band so far
        reach = max(reach, box(it)[hi])
    if best <= 4: return 0, None                       # nothing wide enough to count as a cut
    groups = [s[:at], s[at:]]
    return best, (groups[::-1] if axis == "y" else groups)   # y runs upwards: the top group comes first

def xy_cut(items):
    if len(items) <= 1: return list(items)
    cuts = [best_cut(items, "y"), best_cut(items, "x")]
    gap, groups = max(cuts, key=lambda c: c[0])      # cut along the widest whitespace first
    if groups is None: return sorted(items, key=lambda it: (-it[1], it[0]))
    return [it for g in groups for it in xy_cut(g)]

On the two-column page, sorting by position interleaves the columns ("Left column, paragraph one" is followed by "Right column, paragraph one", then both second lines), while XY-cut reads the title, the whole left column, the whole right column and the page number. Look at how the cut works: the title is separated by a horizontal gap of 39 points, which is wider than the 27-point gap between the columns, so it is cut off first; then the widest gap in the body is the vertical one, so the columns separate. The result depends on the relative size of gaps, which is why these methods contain thresholds that need tuning on your pages.

Pick a layout and an ordering rule. Numbers show the produced order; green blocks are where the intended reading order puts them, red are not. The layouts are constructed.

Real layouts are harder than these. Footnotes interrupt a column and belong at the end; a sidebar belongs after the article or before it depending on the publisher; tables have their own internal order; right-to-left and vertical scripts read in other directions (chapter 22). This is why learned reading-order models exist, trained on pages with human-annotated sequences. They are better on difficult layouts and have the usual costs of learned components. A pragmatic stance is to use geometric rules for the simple majority of pages, and to flag pages where the rule is uncertain (no clean cut found, or many blocks in the fallback) for a heavier method or for review.

What to keep: blocks with provenance

The output of this stage should not be a single string. It should be a list of blocks, each carrying enough to trace it back. Here is the last step of the miniature pipeline: merge lines into paragraph blocks, give each a type and a position in the reading order, and write records.

import json
from order_full import lines_of, xy_cut, box      # earlier listing; the demo prints are guarded in the file below

items = xy_cut(lines_of("two_column.pdf"))          # lines in reading order

blocks, cur = [], None
for x, y, size, s in items:
    same = cur and abs(cur["x"] - x) < 5 and 0 < cur["last_y"] - y <= 1.6 * size and cur["size"] == size
    if same:
        cur["text"] += " " + s; cur["last_y"] = y; cur["bottom"] = y; cur["right"] = max(cur["right"], x + len(s) * size * 0.5)
    else:
        cur = {"x": x, "top": y + size, "bottom": y, "last_y": y, "size": size, "text": s, "right": x + len(s) * size * 0.5}
        blocks.append(cur)

def kind(b):
    if b["size"] >= 14:      return "Title"
    if b["bottom"] < 60:     return "Page-footer"       # sits in the bottom margin
    return "Text"

out = []
for n, b in enumerate(blocks, 1):
    out.append({"page": 1, "order": n, "type": kind(b), "bbox": [b["x"], b["bottom"], round(b["right"]), b["top"]],
                "source": "text-layer", "text": b["text"]})
for o in out: print(json.dumps(o))

Those fields are not decoration. The page and bbox let the interface draw a rectangle on the original page when it cites a claim (chapter 16), which is how an auditor checks an answer against a filing. The type and order let the chunker break at headings and keep captions with figures. The source (text layer or OCR, and which engine) lets you re-run only the OCR'd blocks when an engine improves, and lets you apply stricter checks to numbers that came from OCR than to numbers that came from a text layer. In Lab 6 (A Document Understanding Pipeline) you build this stage from OCR boxes, and the retrieval half of the course, notably chapter 13, then consumes it.

Measuring this stage

This stage is rarely measured, and it should be, because its errors are invisible downstream. Four measures cover most needs. For characters, compare extracted text with a reference using a normalised edit distance, the character error rate of chapter 19. For layout detection, use mAP against annotated boxes, as DocLayNet does. For reading order, compute an edit distance between the produced and the annotated block sequence, or the share of adjacent block pairs in the right order. For end-to-end value, compare retrieval and answer quality (chapter 4, chapter 17) with the old parser against the new on the same questions, since a parser that is better on its own benchmark may not help your questions.

A labelled set for this stage can be small. Fifty pages chosen to span your sources (clean reports, dense two-column papers, forms, scans, tables, mixed pages), each annotated with its blocks and order, will expose most problems, and it doubles as a regression set when you change parsers. Sampling matters: include the ugliest pages you can find, not a random fifty of the clean ones.

Key takeaways

  • A PDF stores instructions for painting a page: strings at coordinates, in whatever order the producer wrote them. Paragraphs, columns and tables are inferred, not stored.
  • Extraction problems each have a cause: spaces as gaps, stored order, missing character maps, ligatures, hyphenation, repeated boilerplate, hidden text.
  • Classify every page: born-digital (trust the characters, check the order), scanned (OCR), or scanned with an inherited OCR layer (test its quality, or redo it).
  • Layout analysis produces typed blocks, by rules on the text layer or by learned detectors such as models trained on DocLayNet; combine them.
  • Reading order needs its own step. Stored order and position sorts fail on columns; XY-cut handles clean cuts and fails on pinwheels; flag uncertain pages.
  • Keep blocks with page, box, type, order and source. Citations, chunking and re-processing all depend on them.
  • Measure this stage on a small, deliberately hard set of your own pages; benchmark leaderboards change monthly and rarely cover your documents.

Check your understanding

A two-column PDF yields sentences that jump from one column to the other mid-paragraph, but every character is correct. What is the most likely cause?

  1. The fonts lack a ToUnicode map.
  2. The text is correct but the extractor used stored or row-wise order, not column-aware reading order.
  3. The PDF is a scan whose OCR layer is poor.
  4. The page was compressed with too lossy an algorithm.
Correct characters in the wrong sequence is the signature of an ordering problem. Missing ToUnicode maps produce gibberish characters, not mis-ordered correct ones; a poor OCR layer produces wrong characters; PDF stream compression is lossless.

A file contains a page-sized image and invisible text (render mode 3) on every page. Your extractor returns clean text and you index it. What is the main risk?

  1. The invisible text will be shown to users, which is a privacy leak.
  2. The page must be a born-digital document, so there is no risk.
  3. The extractor cannot read render mode 3.
  4. The text is the output of whatever OCR engine produced the file, of unknown quality, and you have indexed it unchecked.
Render mode 3 text is extractable and invisible, so extractors return it happily. It came from some earlier OCR run, so its accuracy is inherited. The file is a scan, not a born-digital document, which rules out option 2. Option 1 reverses what the mode does.

You extract a long report page by page and find "Page 14" and the report title inside many of your chunks. Which fix attacks the cause?

  1. Detect page headers and footers (by layout class, or by repetition across pages) and drop them before chunking.
  2. Increase the chunk size so the repeated text is a smaller share.
  3. Lower-case everything before embedding.
  4. Switch to a larger embedding model.
The boilerplate is a content problem: running headers and footers are part of every page's text layer. Removing them at the source is direct. Larger chunks only dilute it; case-folding and larger embedders do not remove text that should not be there.

XY-cut orders a two-column page correctly, but on a magazine page with four blocks arranged round a central pull-quote it returns a clearly wrong order. Why?

  1. It only works on pages with exactly two columns.
  2. The pull-quote's font is too large.
  3. No straight horizontal or vertical line separates the blocks without crossing one, so it finds no cut and falls back to a position sort.
  4. XY-cut is not able to handle more than five blocks.
XY-cut is a guillotine method: each step needs a clean straight cut through whitespace. A pinwheel has none, so the algorithm degrades to sorting by top edge and then left edge. The method has no limit on column count or block count in itself.

Why does a document pipeline keep each block's page number and bounding box instead of only the extracted text?

  1. To reduce the index size.
  2. So that citations can highlight the exact region on the page, chunking can use block types and order, and OCR'd blocks can be re-processed separately.
  3. Because embedding models require coordinates as input.
  4. Because PDF viewers need the boxes to open the file.
The boxes cost storage, not save it, and embedding models do not take them. Their value is downstream: checkable citations, structure-aware chunking and targeted reprocessing. Viewers do not depend on your records.

A vendor reports the highest overall score on a public document-parsing benchmark whose text evaluation covers two languages. Your documents are in another language, with many tables. What should you do?

  1. Adopt the top model, since the benchmark is public.
  2. Ignore benchmarks entirely.
  3. Average the benchmark score with the vendor's own figures.
  4. Use the benchmark to shortlist candidates, then measure them on a labelled sample of your own pages, with table and text scores separately.
Public scores are useful filters but combine sub-scores and cover particular languages, so they may not predict performance on your documents. Ignoring them wastes information, and averaging with vendor figures compounds the bias. Measure on your pages, reporting the sub-scores that matter to you.

Relevance Metrics

A retriever returns a ranked list; a metric turns that list, plus a set of judgements, into one number. Each metric asks a different question: did we find anything, did we find everything, how soon did the first good answer appear, is the whole order right. This chapter builds precision, recall, reciprocal rank, average precision and nDCG from the list itself, so you can choose the one that matches the question your system must answer.

Why this matters

Chapters 1 to 3 gave you ways to change a ranking: analysers, BM25 parameters, query rewriting. Without a number you cannot tell whether a change helped, and a number chosen carelessly can tell you the wrong thing: a system that is better for users can score worse, and the reverse. Every later chapter (dense retrieval, reranking, hybrid search, chunking) is justified by a metric moving on a test set, and the retrieval lab at the end of Part 2 has you build a harness around exactly the functions written here. After this chapter you can compute each metric by hand, say what it rewards and ignores, and pick the right one for a search box, a question-answering pipeline or a compliance review.

From a ranked list to a number

Evaluation of a retriever needs three ingredients. A set of queries, each standing for an information need. A ranked list that the system returns for each query. And relevance judgements (often called qrels, for query relevance labels): for a query and a document, a label saying whether the document answers the need. The judgements are the hard part, and chapter 5 is about producing them. Here we assume they exist and ask what to compute from them.

Judgements come in two shapes. Binary relevance has two labels, relevant or not. Graded relevance has several, for example 0 (not relevant), 1 (marginal), 2 (good), 3 (perfect). We write the grade of the result at rank i as gi. A binary metric reads a graded label through a threshold: here "relevant" means g ≥ 1.

There is no single best metric, because "good retrieval" is not one thing. A person typing into a search box reads the top few results and stops; a question-answering pipeline passes the top 20 chunks to a model and needs the evidence to be somewhere in them; a lawyer doing document review must find every relevant contract. These users reward different behaviour, so they need different numbers. The four questions below organise the chapter.

A running example

One query, ten results, graded judgements. The query is "how do I dispute a card charge", and a judge has graded each document that appeared, plus two judged-relevant documents that the system did not retrieve at all (they sit at rank 40 and below, outside the list). The grades at ranks 1 to 10 are 3, 0, 2, 0, 0, 1, 0, 2, 0, 0. Six documents in the collection are relevant in total: the four in the list and the two that were missed, with grades 2 and 1.

All the code in this chapter lives in one small module, metrics.py, which you will recognise in the evaluation lab. Each function takes the list of grades in rank order. Put it in a folder and keep it open.

import math

def precision_at_k(grades, k, thr=1):
    """grades: relevance grade of each ranked result (index 0 = rank 1)."""
    return sum(g >= thr for g in grades[:k]) / k

def recall_at_k(grades, k, n_relevant, thr=1):
    return sum(g >= thr for g in grades[:k]) / n_relevant

def reciprocal_rank(grades, thr=1):
    for i, g in enumerate(grades, 1):
        if g >= thr:
            return 1.0 / i
    return 0.0

def average_precision(grades, n_relevant, thr=1):
    hits, total = 0, 0.0
    for i, g in enumerate(grades, 1):
        if g >= thr:
            hits += 1
            total += hits / i          # precision at each relevant rank
    return total / n_relevant          # unretrieved relevant docs add zeros

def dcg(grades, k, exp_gain=False):
    gain = (lambda g: 2 ** g - 1) if exp_gain else (lambda g: g)
    return sum(gain(g) / math.log2(i + 1) for i, g in enumerate(grades[:k], 1))

def ndcg_at_k(grades, k, all_grades, exp_gain=False):
    """all_grades: grades of EVERY judged document for this query."""
    ideal = sorted(all_grades, reverse=True)
    best = dcg(ideal, k, exp_gain)
    return dcg(grades, k, exp_gain) / best if best > 0 else 0.0

Precision and recall at k

Precision at k (P@k) is the fraction of the first k results that are relevant. Recall at k (R@k) is the fraction of all relevant documents that appear in the first k. They share a numerator, the number of relevant results in the top k, and differ in the denominator:

P@k = (relevant in top k) / k     R@k = (relevant in top k) / (relevant in the collection)

Precision answers "of what I show, how much is useful?" Recall answers "of what exists, how much did I show?" They pull against each other: showing more results can only raise recall, and usually lowers precision, because later results are less likely to be relevant. Our list has 1 relevant result in the top 1 (P@1 = 1.0), 2 in the top 3 (0.67), 2 in the top 5 (0.40) and 4 in the top 10 (0.40); recall climbs 0.17, 0.33, 0.33, 0.67 over the same cut-offs.

Analogy: the fishing net

Think of the system as a net cast into a lake where some fish are the ones you want. Recall is the share of the wanted fish you caught; precision is the share of the catch that is wanted fish. A wide net with small holes catches almost every wanted fish and a great deal of rubbish; a narrow net brings up only wanted fish but misses most of them.

Where it breaks down: a net has no order. A search result list is ranked, and a user who reads from the top experiences a bad rank-1 result very differently from a bad rank-10 result. Precision and recall at a fixed k ignore order inside the first k, which is exactly what the later metrics repair.

Three practical points about these two metrics.

  • Recall needs to know what exists. To compute R@k you need the total number of relevant documents, and that is never fully known on a large collection: you know only those the judges saw (chapter 5 on pooling). Recall computed over a partial judgement set is recall of the known relevant set, an optimistic estimate of true recall.
  • Precision is capped by the collection. If a query has only 2 relevant documents, P@10 cannot exceed 0.2 however good the system is. Averaging P@10 across queries with different numbers of relevant documents mixes scores whose ceilings differ. R-precision (precision at R, where R is the number of relevant documents for that query) removes the ceiling, and appears in some benchmarks.
  • Hit rate (also called success@k or, in question answering, "top-k accuracy") is a simplified recall: 1 if at least one relevant document is in the top k, else 0. When one passage is enough to answer the question, hit rate is the honest recall. The DPR paper (Karpukhin et al., 2020, "Dense Passage Retrieval for Open-Domain Question Answering") reports top-20 and top-100 accuracy for exactly this reason: a reader model needs one passage that contains the answer, not all of them.

The F1 score, the harmonic mean of precision and recall, is common in classification but rare for ranking, because it needs one threshold at which to compute both, and a ranked list has no natural threshold. Prefer precision and recall at stated values of k.

Where the first answer is: reciprocal rank and MRR

Many tasks need one good result and want it early: navigational search ("company X login"), a factual lookup, a pipeline that answers from the top-1 passage. Reciprocal rank (RR) scores a single query as 1 divided by the rank of the first relevant result: 1 if it is first, 0.5 if second, 0.33 if third, and 0 if none appears in the list. The mean of RR over a set of queries is the mean reciprocal rank (MRR).

The reciprocal is a deliberate choice. Going from rank 1 to rank 2 costs half the score; going from rank 9 to rank 10 costs 0.011. That matches how people behave: the difference between first and second is large, between ninth and tenth it is negligible. MRR is also easy to explain: its inverse is roughly "the typical position at which the first answer appears" (a harmonic mean of ranks).

Its blindness is the flip side. RR looks only at the first relevant document. A system that returns one perfect result and nine pieces of junk scores the same as one that returns ten perfect results, and a query with five relevant documents is scored on one of them. MRR is therefore the right metric when there is exactly one needed answer, and a weak one when completeness matters. It is also usually truncated: "MRR@10" counts a first hit beyond rank 10 as zero, and the cut-off should be stated because it changes the numbers.

Average precision and MAP

We want one number that rewards putting all the relevant documents high, using binary labels. Average precision (AP) does this. Walk down the list; each time you meet a relevant document, record the precision at that rank; then average those recorded precisions over all the relevant documents that exist, not only those retrieved.

AP = (1 / R) ∑i P@i × reli

Here reli = 1 if the result at rank i is relevant (otherwise 0), and R is the number of relevant documents.

The stepper below does this for the running example. Relevant results sit at ranks 1, 3, 6 and 8, with precisions 1/1, 2/3, 3/6 and 4/8. Their sum is 2.667. Dividing by R = 6 gives 0.444.

Step through

Average precision for the running example

  1. The list. Four relevant results are retrieved (ranks 1, 3, 6, 8); two more relevant documents exist in the collection.
  2. Rank 1. One relevant result among one: precision at this point is 1.000. AP records it.
  3. Rank 3. The second relevant result arrives with two non-relevant results ahead of it in the count: precision 2/3.
  4. Rank 6. The third relevant result, later, so precision has dropped to 3/6.
  5. Rank 8. The fourth relevant result: 4/8. Retrieving relevant documents late is recorded as lower precision at that moment.
  6. Average over all six. The recorded precisions sum to 2.667. Dividing by 6, not 4, means the two never-retrieved documents are charged as zeros. AP = 0.444.

Two properties make AP useful. It rewards early relevant results because precision is high when relevant documents come first. And dividing by R rather than by the number retrieved punishes missing documents, so AP combines the ideas of precision and recall in a single number. Its mean over queries is MAP (mean average precision), for decades the headline metric of the TREC evaluations. Manning, Raghavan and Schütze (2008, Introduction to Information Retrieval, chapter 8) explain why: AP is the area under the precision-recall curve, so it summarises behaviour at every recall level without choosing a cut-off.

Its weakness is that it is binary, and it counts a marginal document like a perfect one. It also behaves badly if you stop at a cut-off but your collection has many relevant documents: AP over a full ranking is dominated by the long tail, which no user reads. For web-scale search, graded and truncated metrics took over.

Graded relevance: DCG and nDCG

Real documents are not simply relevant or not. A page that fully answers the question is better than one that mentions the topic. Discounted cumulative gain (DCG; Järvelin and Kekäläinen, 2002, "Cumulated gain-based evaluation of IR techniques") builds on two assumptions: highly relevant documents are more valuable than marginal ones (the gain), and a document is worth less the lower it appears, because users are less likely to reach it (the discount).

DCG@k = ∑i=1k gain(gi) / log2(i + 1)

With the identity gain (gain = grade), the example scores 3/1 + 0 + 2/2 + 0 + 0 + 1/2.807 + 0 + 2/3.170 + 0 + 0 = 4.987. The denominator is 1 at rank 1, 1.585 at rank 2, 2 at rank 3, and grows slowly. The discount is gentler than the reciprocal in MRR: the next figure shows the weight each rank carries.

DCG grows with the number of good results, so it cannot be compared between queries that have different numbers of good documents. Normalised DCG (nDCG) divides by the best achievable DCG for that query, the ideal DCG (IDCG), computed by sorting all judged documents by grade, highest first, and scoring that order at the same cut-off:

nDCG@k = DCG@k / IDCG@k

For the example the ideal order is the six relevant grades 3, 2, 2, 2, 1, 1 followed by zeros, with IDCG@10 = 6.866. So nDCG@10 = 4.987 / 6.866 = 0.726. A perfect ordering scores 1, a list with nothing relevant scores 0, and every query now lives on the same 0 to 1 scale, which is what makes the average across queries meaningful.

from metrics import *

ranked = [3, 0, 2, 0, 0, 1, 0, 2, 0, 0]   # grades at ranks 1..10
missed = [2, 1]                             # judged relevant, never retrieved

n_rel = sum(g >= 1 for g in everything)     # 6 relevant in total

Two details that change the numbers

The gain function. The original definition uses the grade itself as gain. A variant popularised by Burges et al. (2005, "Learning to Rank using Gradient Descent") uses 2g − 1, which makes a perfect document worth seven times a marginal one rather than three. Many libraries default to one or the other, so a paper's nDCG and your nDCG can differ for no reason except this. The next listing shows the two forms ordering a pair of rankings differently, which is the reason the choice must be written down.

The ideal list. IDCG is computed from the judged documents. If the judgements miss a relevant document (an incomplete pool, see chapter 5), the ideal is too low and nDCG is flattered. If your system finds a relevant document nobody judged, the metric cannot reward it.

import random
from metrics import *

# 1. Gain form: two rankings of the same documents, grades 0-3.
x = [3, 0, 0, 0, 0, 0, 0, 0, 0, 0]          # one perfect result first
y = [2, 2, 2, 0, 0, 0, 0, 0, 0, 0]          # three good results first
pool = [3, 2, 2, 2]                          # all judged-relevant documents
for name, exp in (("linear gain g     ", False), ("exponential 2^g-1", True)):
    print(f"{name}: nDCG@10 of X = {ndcg_at_k(x, 10, pool, exp):.3f}   of Y = {ndcg_at_k(y, 10, pool, exp):.3f}")

# 2. Unjudged documents: score a new system's list when 3 of its top 5 are unjudged.
truth = [1, 1, 1, 1, 0]                      # the real grades of its top 5
seen  = [1, None, None, 1, None]             # what the judgement file contains
treated = [g if g is not None else 0 for g in seen]
n_rel = 5
print("\ntrue   P@5 =", precision_at_k(truth, 5), " AP =", round(average_precision(truth + [0]*5, n_rel), 3))
print("scored P@5 =", precision_at_k(treated, 5), " AP =", round(average_precision(treated + [0]*5, n_rel), 3))

# 3. A random ranking is not a zero: the score depends on how many relevant docs exist.
rng = random.Random(7)
for n_docs, n_rel in ((100, 2), (100, 20), (1000, 2)):
    scores = []
    for _ in range(4000):
        ranked = [1] * n_rel + [0] * (n_docs - n_rel)
        rng.shuffle(ranked)
        scores.append((precision_at_k(ranked, 10), average_precision(ranked, n_rel)))
    p = sum(s[0] for s in scores) / len(scores); a = sum(s[1] for s in scores) / len(scores)
    print(f"random order, {n_docs:>4} docs, {n_rel:>2} relevant: mean P@10 = {p:.3f}  mean AP = {a:.3f}")

In the first two lines of the output, ranking X puts one perfect document first and ranking Y puts three good ones first. With linear gain Y wins (0.696 against 0.490); with 2g − 1, where a perfect result is worth 7 and a good one 3, X wins (0.599 against 0.547). Neither is wrong. They encode different beliefs about how much better a perfect answer is than a good one, and you should choose that belief from your users' needs and keep it fixed.

Go deeper optional: why a log discount, and the link to user models

A metric implies a user model. P@k models a user who reads exactly the top k and treats them equally. Reciprocal rank models a user who reads down until the first relevant result and then stops. DCG models a user whose chance of reaching rank i falls as 1/log2(i + 1): not a stopping rule, only a smooth decay. Moffat and Zobel (2008, "Rank-biased precision for measurement of retrieval effectiveness") made the user model explicit: with persistence p, the chance of reading the next result after the current one is p, giving weights (1 − p)pi−1. A persistence of 0.8 behaves much like a cut-off near 5 results, and 0.95 like one near 20. Treat the log discount as one reasonable choice among several, and look for evidence about your users before arguing over it.

Common misconception

"An nDCG@10 of 0.8 means 80% of users are satisfied" or "nDCG 0.8 is good". A metric value has no meaning outside its test set: it depends on how many relevant documents each query has, how strict the judges were, and how hard the queries are. A random ranking of 100 documents with 20 relevant scores a mean P@10 of 0.20, and with 2 relevant only 0.02, as the last three lines of the pitfalls output show. Use metrics to compare two systems on the same queries and judgements, never to claim an absolute level of quality. A related error: "a higher metric means users will notice". A 0.01 gain in MAP can be well inside the noise of the query sample (Evals chapter 4) and invisible to anyone using the product.

From one query to a test set

Each metric above scores one query. A test set has dozens to thousands, and the usual summary is the macro average: compute the metric per query, then take the mean, so each query counts equally. The alternative, pooling all results and computing once (a micro average), lets queries with many relevant documents dominate. For retrieval, macro is the convention: it answers "how good is this for a typical query" and not "how good is it for the queries with the most answers".

Three consequences follow.

  • Always keep the per-query scores. The mean hides which queries got better and which got worse. Two systems with identical MAP can differ completely: one improves ten queries slightly, the other rescues one and wrecks nine. The two_systems.py listing below is a small example of how different metrics rank two systems differently on the very same lists.
  • Decide how to treat queries with no relevant document. Recall and AP divide by R, which is then zero. TREC practice drops such queries; if you keep them, the score is undefined, and silently counting it as zero makes every system look worse by a fixed amount. In a RAG test set, a query with no answer in the corpus belongs in a separate "should abstain" test, not in the retrieval average.
  • The mean needs an error bar. With 50 queries, the standard error of a mean nDCG is typically around 0.03 to 0.05 (it depends on the spread of per-query scores). Differences smaller than that are not evidence. The paired bootstrap and permutation tests that quantify this are developed in Evals chapter 4 and implemented in the evaluation lab; chapter 5 shows how many queries you need.
from metrics import *

# For each query: grades of the top 10 for each system, and the number of
# relevant documents that exist (binary judgements here, 1 = relevant).
def lst(n, positions):
    g = [0] * n
    for p in positions: g[p - 1] = 1
    return g

N_REL = [3, 4, 2, 5, 3, 4]
A = [lst(10, [1]), lst(10, [1]), lst(10, [1]), lst(10, [1, 9]), lst(10, [1]), lst(10, [2])]
B = [lst(10, [2, 4, 7]), lst(10, [3, 5, 6, 9]), lst(10, [2, 8]),
     lst(10, [2, 3, 5, 8, 10]), lst(10, [3, 4, 9]), lst(10, [2, 3, 6, 7])]

def table(name, runs):
    mrr = sum(reciprocal_rank(r) for r in runs) / len(runs)
    p5 = sum(precision_at_k(r, 5) for r in runs) / len(runs)
    r10 = sum(recall_at_k(r, 10, n) for r, n in zip(runs, N_REL)) / len(runs)
    mp = sum(average_precision(r, n) for r, n in zip(runs, N_REL)) / len(runs)
    nd = sum(ndcg_at_k(r, 10, r + [1] * (n - sum(r))) for r, n in zip(runs, N_REL)) / len(runs)
    print(f"{name}:  MRR {mrr:.3f}  P@5 {p5:.3f}  R@10 {r10:.3f}  MAP {mp:.3f}  nDCG@10 {nd:.3f}")

table("System A (one great hit, little else)", A)
table("System B (everything, but not first)  ", B)
System A (one great hit, little else):  MRR 0.917  P@5 0.200  R@10 0.344  MAP 0.298  nDCG@10 0.438
System B (everything, but not first)  :  MRR 0.444  P@5 0.400  R@10 1.000  MAP 0.462  nDCG@10 0.641

System A returns one relevant document at rank 1 in five of six queries and little else. System B always finds all or most of the relevant documents but rarely first. MRR calls A far better (0.917 against 0.444); recall@10 calls B far better (1.000 against 0.344); P@5, MAP and nDCG@10 side with B. Neither is lying. If the product shows one answer to a user who needs it right now, A is the better system; if the output feeds a downstream reader that needs all the evidence, B is. The metric is how you declare which job you are doing.

Pitfalls

  • Unjudged documents. The standard convention treats an unjudged document as non-relevant. In the middle lines of the pitfalls.py output, a list whose top five are all truly relevant scores P@5 = 0.8; but if three of those five were never seen by a judge, they count as misses and the same list scores 0.4. A new system that retrieves differently from the ones that built the judgements is punished this way. The BEIR authors measured this effect on TREC-COVID, finding that a dense retriever's nDCG@10 rose from 0.654 to 0.735 after 980 missing judgements were added, while BM25's moved from 0.656 to 0.668 (Thakur et al., 2021). Chapter 5 covers pooling, and chapter 6 returns to the lesson for public benchmarks.
  • Reporting a metric without its cut-off or variant. "nDCG" can mean @5, @10, @100 or the whole list, linear or exponential gain, with or without ties handled in a special way. Write "nDCG@10 with linear gain".
  • Several chunks from one document. In RAG, a query's gold label is often a document or section while the system returns chunks. If three of the top five chunks come from the same relevant section, counting each as a hit inflates precision and recall. Decide the unit (chunk, section, document), deduplicate to it, and judge on it. The same applies to near-duplicate documents.
  • Ties. If two results have the same score, their order is arbitrary, and the metric can change between runs. Break ties deterministically (for example by document id) so that results are reproducible.
  • Truncating the judged list. If your judges looked at the top 10 of one system, nDCG@100 is meaningless for any system that surfaces documents beyond them. A metric's cut-off should not exceed the depth to which documents were judged.
  • Averaging different things. A mean across queries of different types (navigational lookups and exploratory questions) can hide a real regression in one type. Slice the per-query scores by query type, as chapter 3 suggests for head and tail queries.

Systems connection

Per-query scores are a distribution, and the mean of a distribution can hide its tail. The same discipline appears in Reliability chapter 4: you do not report only the mean latency, because users live in the tail. Treat a retrieval metric the same way: look at the worst queries (the ones scoring 0), not only at the average, because those are the queries you will read in error analysis (Evals chapter 1). And just as an SLO ties a number to something users feel (Reliability chapter 2), a retrieval metric is only useful if it is tied to a decision: ship or hold, switch embedder or keep.

State of play, October 2026

The definitions in this chapter are decades old and stable. What varies is tooling and defaults. trec_eval, the reference implementation behind TREC, and its Python binding pytrec_eval (Van Gysel and de Rijke, 2018) remain common for checking a custom implementation; libraries such as ir_measures (Macdonald and Tonellotto, 2021) wrap several implementations behind one interface. They differ in defaults (gain function, handling of unjudged documents, ties), so when you compare against a published number, check the tool and the options rather than assuming nDCG means the same thing. In 2023 to 2026, many teams also began using language models to produce relevance labels at scale; that raises the incomplete-judgement and bias questions of the next chapter, and Evals chapter 3 covers calibrating such a judge against people.

Key takeaways

  • A metric turns a ranked list plus judgements into a number; each one answers a different question, so choose the question first.
  • Precision@k asks how much of the top is useful; recall@k asks how much of what exists was found; hit rate asks whether any evidence was found. All ignore order inside the first k.
  • Reciprocal rank (MRR) scores only the first relevant result, 1/rank; right when one answer is enough, blind to everything after it.
  • Average precision averages the precision at each relevant rank over all R relevant documents, so missing documents count as zeros. MAP is its mean over queries; it is binary.
  • nDCG uses graded gains and a 1/log2(rank + 1) discount, normalised by the ideal ordering so queries share a 0 to 1 scale. State the gain function and the cut-off.
  • For RAG, report recall@k for the first stage and a rank-aware metric after reranking; for a single-answer lookup, MRR.
  • Metric values mean something only relative to other systems on the same queries and judgements. Unjudged documents count as non-relevant, so new systems can be under-scored; keep per-query scores and error bars.

  • Järvelin and Kekäläinen, "Cumulated Gain-Based Evaluation of IR Techniques" (ACM TOIS, 2002). The paper that introduced DCG and nDCG.

Check your understanding

A query has 4 relevant documents. A system returns relevant documents at ranks 2 and 5 and nothing else relevant in the top 10. What is its average precision?

  1. 0.45, the mean of 1/2 and 2/5
  2. 0.225, the sum of 1/2 and 2/5 divided by 4
  3. 0.9, the sum of 1/2 and 2/5
  4. 0.5, because the first relevant result is at rank 2
Precision at rank 2 is 1/2 and at rank 5 is 2/5, sum 0.9. AP divides by the number of relevant documents that exist (4), not the number retrieved (2), so the two missed documents count as zeros: 0.9 / 4 = 0.225. Dividing by 2 would give 0.45 and reward a system for ignoring the documents it failed to find. 0.5 is the reciprocal rank, a different metric.

Your RAG pipeline passes the top 20 retrieved chunks to a language model, which can ignore irrelevant ones. Which metric best measures the retriever for this job?

  1. MRR@20, because rank 1 matters most
  2. Precision@20, because every irrelevant chunk wastes context
  3. MAP over the full ranking
  4. Recall@20 (or hit rate@20), because the evidence must be somewhere in the 20
The model reads all 20, so the order inside them matters little, while evidence that is not retrieved cannot be used at all. Precision@20 matters for cost and distraction, but it is secondary: a model can skip junk, and cannot invent missing evidence. MRR cares about the first relevant result only, which is irrelevant if all 20 are read.

System X and System Y have identical P@5 on every query, but Y puts its relevant results higher within the top five. Which metric is guaranteed to separate them in Y's favour?

  1. Average precision or nDCG@5
  2. Recall@5
  3. Hit rate@5
  4. Precision@10
AP and nDCG use position, so earlier relevant results score higher. Recall@5 and hit rate@5 count what is inside the top five regardless of order, as does P@5 itself, so they cannot distinguish the two. P@10 is also order-free inside the first ten. Note that "guaranteed" holds for these two only if relevant documents sit at different ranks.

A colleague compares two nDCG@10 scores from different sources, 0.61 and 0.58, and concludes the first is better. Which caveat is most important?

  1. nDCG can never be compared between systems
  2. Scores below 0.7 are not meaningful
  3. They may come from different queries, judgements, gain functions or handling of unjudged documents, so the numbers are not comparable
  4. nDCG@10 is always higher for older systems
A metric value belongs to a test set and a set of options. nDCG with linear gain and with 2g − 1 can rank systems differently, and unjudged documents count as non-relevant in different amounts. Comparing across sources needs identical queries, judgements and settings. nDCG is comparable between systems when those match, and no fixed threshold makes a score meaningful.

A new retriever finds relevant passages that none of the earlier systems retrieved, so no judge ever saw them. How does the standard evaluation treat them, and what is the consequence?

  1. They are ignored and do not affect the score
  2. They count as non-relevant, so the new system is under-scored relative to its true quality
  3. They count as relevant by default, so the new system is over-scored
  4. They crash the evaluation script
Unjudged documents are conventionally non-relevant. A system that retrieves differently from the judged pool is therefore penalised, as the BEIR study on TREC-COVID measured (a dense retriever gained about eight nDCG@10 points when missing judgements were added). They are not ignored (that would be a different convention, "condensed lists") and are certainly not assumed relevant.

With 2g − 1 gain instead of linear gain, nDCG tends to favour which kind of ranking?

  1. Rankings with many marginal documents
  2. Rankings that put the longest documents first
  3. No difference: the two gains always give the same order
  4. Rankings that place the very best (highest-grade) documents early, since a top grade is worth far more than a lower one
The exponential gain makes a grade-3 document worth 7 and a grade-1 worth 1, instead of 3 and 1, so one perfect result early outweighs several good ones. The listing showed the order of two rankings flipping between the two forms. The two forms do not always agree, which is why the form must be reported.

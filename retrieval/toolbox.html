Toolbox

Retrieval and document work is learned by looking at what an engine actually did: the term scores behind a ranking, the distance behind a nearest neighbour, the metric a library reports, the text a converter produced from a page. These six cards cover the tools you will meet in production. Each has setup notes and a ten-minute exercise tied to the chapters, with a small script whose real output tells you what the tool should show.

How to use this page

Jump to a tool when a chapter or studio points at it. I ran every Python script on this page (standard library only) and pasted its real output: they compute by hand what the tools should report, so you can check the tool against the arithmetic. I did not install or run any of the tools themselves while writing this page: none of OpenSearch, PostgreSQL with pgvector, Qdrant, sentence-transformers, ranx, pytrec_eval, Docling, Marker, MinerU, Tesseract or PaddleOCR was available in my environment. Every tool command and every API call below is therefore illustrative, written from the tools' documented interfaces; I never paste invented tool output, and I describe what to look for instead. Versions, flags, model names and image tags change often: check the tool's own documentation (linked under each card) and your own --help before trusting any command here.

Search engines and vector stores

The systems that hold the index. Learn the lexical engine first: it is also where most "vector" features now live.

Elasticsearch & OpenSearch

Install: a single-node container is the quickest route (opensearchproject/opensearch or docker.elastic.co/elasticsearch/elasticsearch; pin a tag you have checked) · Alternatives: Apache Solr, Lucene directly, Vespa, Tantivy, Meilisearch, Typesense, SQLite FTS5 or Postgres full-text search for small corpora · Chapters: 1, 2, 10, 12

Elasticsearch and OpenSearch (a fork of Elasticsearch 7.10, maintained separately since 2021) both wrap Apache Lucene: an inverted index with BM25 scoring, analysers that turn text into tokens, structured filters, aggregations, and in recent versions approximate vector search and ways to combine lexical and vector results. This is the engine behind many enterprise and e-commerce searches, and the thing the enterprise search studio assumes. Knowing its three diagnostic tools, _analyze, explain and the query profiler, is what separates configuring a search engine from guessing at it.

10-minute guided exercise

Make the engine show its working, then reproduce one score by hand. The commands are illustrative: the request bodies follow the documented REST API, but check your version.

$ docker run -d --name os -p 9200:9200 -e "discovery.type=single-node" -e "DISABLE_SECURITY_PLUGIN=true" opensearchproject/opensearch:2
$ curl -s localhost:9200 | head      # a JSON banner with the version number
  1. Minute 0 to 2: index five documents. Use the five short documents in the script below (a VPN and password help corpus), with PUT /help and a _bulk request. Use one shard ("number_of_shards": 1) so that document frequencies are not split across shards, which changes scores in tiny corpora.
  2. Minute 2 to 4: see the tokens. POST /help/_analyze {"analyzer":"standard","text":"Reset your VPN password"}. Compare with the english analyser (stemming and stop words) and the output of the analyser you built in chapter 1.
  3. Minute 4 to 7: ask for the explanation. GET /help/_search {"explain": true, "query": {"match": {"text": "reset vpn password"}}}. Each hit gets an _explanation tree with the idf and the term-frequency component of every matching term.
  4. Minute 7 to 10: check it against arithmetic. Run the script below. It computes BM25 by hand for the same query, with the engine's default k1 = 1.2 and b = 0.75, in two forms.
"""BM25 by hand to compare with an engine's explain output. idf = ln(1 + (N - n + 0.5) / (n + 0.5)).
Textbook form has a (k1 + 1) factor in the numerator; recent Lucene versions omit it, which divides every score by k1 + 1 and leaves the ranking unchanged."""
import math, re
docs = {
 "d1": "reset your vpn password from the self service portal",
 "d2": "vpn client install guide for laptops",
 "d3": "password policy and rotation rules",
 "d4": "how to reset a forgotten password",
 "d5": "office wifi and vpn troubleshooting",
}
k1, b = 1.2, 0.75
tok = lambda s: re.findall(r"[a-z0-9]+", s.lower())
T = {d: tok(t) for d, t in docs.items()}
N = len(T); avgdl = sum(map(len, T.values())) / N
df = lambda w: sum(w in t for t in T.values())
idf = lambda w: math.log(1 + (N - df(w) + 0.5) / (df(w) + 0.5))
def score(q, d):
    parts = {}
    for w in sorted(set(tok(q))):
        tf = T[d].count(w)
        if tf: parts[w] = idf(w) * tf * (k1 + 1) / (tf + k1 * (1 - b + b * len(T[d]) / avgdl))
    return sum(parts.values()), parts
q = "reset vpn password"
print(f"N={N} avgdl={avgdl:.2f} k1={k1} b={b}; idf: " + ", ".join(f"{w}={idf(w):.3f}" for w in tok(q)))
for d in sorted(T, key=lambda d: -score(q, d)[0]):
    s, parts = score(q, d)
    if s: print(f"{d}  textbook {s:.3f}  lucene-style {s/(k1+1):.3f}  " + "  ".join(f"{w}:{v:.3f}" for w, v in parts.items()))
N=5 avgdl=6.20 k1=1.2 b=0.75; idf: reset=0.875, vpn=0.539, password=0.539
d1  textbook 1.649  lucene-style 0.749  password:0.455  reset:0.739  vpn:0.455
d4  textbook 1.433  lucene-style 0.652  password:0.546  reset:0.887
d3  textbook 0.585  lucene-style 0.266  password:0.585
d5  textbook 0.585  lucene-style 0.266  vpn:0.585
d2  textbook 0.546  lucene-style 0.248  vpn:0.546

What to look for. The per-term numbers in the _explanation tree should match the "lucene-style" column's components: recent Lucene versions drop the (k1 + 1) factor of the textbook formula, which divides every score by 2.2 and leaves the ranking the same (chapter 2 derives the textbook form). The ranking order d1, d4, then the rest should match. If you used more than one shard, scores differ because each shard computes its own document frequencies; this is why "my scores do not match the formula" is the most common first support question for search engines. Then try the two failure experiments below.

  • Add a second document with a long body that repeats "vpn" twenty times, and watch saturation and length normalisation cap its score (chapter 2).
  • Add a field "allowed_groups": ["hr"] to some documents and filter with a terms query inside bool.filter: filters do not affect scoring and can be cached, which is why they are the right place for permissions (chapter 12).

Common pitfalls

  • Different analysers at index and query time. The classic "I can see the document but cannot find it" bug; _analyze on both sides finds it.
  • Dynamic mapping guessing field types. Define mappings explicitly: identifiers are keyword, prose is text.
  • Trusting scores across queries or across indexes. BM25 scores are only comparable within one query on one index (chapter 10).
  • Vector and hybrid features differ between the two projects and between versions; read the current docs for the exact request shape before you design around one.

Docs: the OpenSearch documentation (opensearch.org/docs) and the Elasticsearch reference (elastic.co/guide); search for "explain API" and "analyze API".

pgvector, Qdrant & friends

Install: pgvector/pgvector container (PostgreSQL with the extension) or qdrant/qdrant container; pin tags you have checked · Alternatives: Milvus, Weaviate, Chroma, LanceDB, FAISS as a library (case study), vector features in OpenSearch or Elasticsearch, managed services · Chapters: 11, 12

A vector database stores embeddings with metadata and answers "which stored vectors are nearest to this one, among those that satisfy this filter". pgvector adds vector columns, distance operators and approximate indexes (HNSW and IVFFlat) to PostgreSQL, so vectors live beside your rows, transactions and access rules. Qdrant is a dedicated engine with payload filtering built into its index traversal. The trade-off in chapter 11 (recall, latency, memory) and the filter problem in chapter 12 are the same in both; the products differ in how they handle them.

10-minute guided exercise

Predict the result, then run it. The script computes, for a five-row table, what the cosine-distance query should return with and without a tenant filter.

"""What a pgvector query should return for a tiny table, computed by hand. <=> is cosine distance = 1 - cosine similarity."""
import math
rows = [(1, "a", (1.0, 0.0, 0.0)), (2, "a", (0.9, 0.1, 0.0)), (3, "b", (0.8, 0.6, 0.0)), (4, "b", (0.0, 1.0, 0.0)), (5, "a", (0.0, 0.2, 0.98))]
q = (1.0, 0.2, 0.0)
cos = lambda u, v: sum(x * y for x, y in zip(u, v)) / (math.hypot(*u) * math.hypot(*v))
print("SELECT id, tenant, embedding <=> '[1,0.2,0]' AS dist FROM items ORDER BY dist LIMIT 3;")
for i, t, v in sorted(rows, key=lambda r: 1 - cos(r[2], q))[:3]: print(f"  id={i} tenant={t} dist={1 - cos(v, q):.4f}")
print("... WHERE tenant = 'b' ORDER BY ... LIMIT 3;")
for i, t, v in sorted([r for r in rows if r[1] == "b"], key=lambda r: 1 - cos(r[2], q))[:3]: print(f"  id={i} tenant={t} dist={1 - cos(v, q):.4f}")

  2. Minute 3 to 5: run the filtered query. With five rows it is exact either way; the point is to see the shape of the question.
  3. Minute 5 to 8: build the HNSW index and run EXPLAIN. On five rows the planner will probably prefer a sequential scan; that is correct. Insert a few thousand random rows (generate_series with random() arrays) and run EXPLAIN again to see the index used.
  4. Minute 8 to 10: provoke the filter problem. With many rows, a rare tenant (1% of rows) and an HNSW index, run the filtered query at hnsw.ef_search = 10 and count results: an approximate index applies the filter after (or while) it walks the graph and can return fewer rows than LIMIT. Newer pgvector versions describe an iterative-scan setting for this; look in the README for your version rather than relying on my memory.

Qdrant version (illustrative): run the container, create a collection with PUT /collections/items and body {"vectors": {"size": 3, "distance": "Cosine"}}, upload points with a payload of {"tenant": "b"}, and query with a filter whose must clause matches the tenant. Compare the ids returned with the script's output; scores are similarities (higher is better) rather than distances.

What to look for. The ranking must agree with the script, and the distances to four decimals. Then ask the questions the studios ask: what does the index return for a user who can see 1% of the data, how does recall change with the search-effort setting, how many bytes per vector does the index hold (pg_relation_size, or Qdrant's collection info) and what happens to memory if you quantise.

Common pitfalls

  • Comparing distances from different metrics (cosine distance versus similarity versus negative inner product) when reading scores.
  • Normalising stored vectors but not query vectors (or the reverse) when the metric assumes unit length.
  • Judging an approximate index on a tiny table: the planner may not use it, and recall is trivially 100%. Measure recall against exact search on a realistic sample (lab 4).
  • Treating the vector store as the permission system. Access rules need the checks described in the enterprise search studio.

Docs: the pgvector README on GitHub (pgvector/pgvector) and the Qdrant documentation (qdrant.tech/documentation).

Embeddings and evaluation

The model that turns text into vectors, and the instruments that tell you whether the whole system got better.

sentence-transformers

Install: pip install sentence-transformers (pulls in PyTorch; the first model use downloads weights from the Hugging Face Hub) · Alternatives: calling an embedding API, Hugging Face transformers directly, FlagEmbedding, fastembed or ONNX runtimes for CPU serving · Chapters: 7, 8

sentence-transformers is the standard library for running and fine-tuning bi-encoders (text to one vector, chapter 7) and cross-encoders (a pair of texts to one relevance score, chapter 8). Loading a model, encoding a list of texts and comparing vectors takes four lines, which makes it the fastest way to test whether a dense retriever helps on your own data before you commit to an index.

10-minute guided exercise

Compare a trained embedder with the hashed-trigram stand-in on your own query-document pairs. First run the script, which defines the stand-in used in this course and shows what "encode, then cosine similarity" computes. Then repeat with a real model and compare the orderings.

"""What encode + cos_sim computes: for unit-length vectors cosine similarity is the dot product.
The embedder here is a deterministic stand-in (hashed character trigrams), NOT a trained model."""
import zlib, math
def embed(text, dim=64):
    v = [0.0] * dim
    t = f"  {text.lower()}  "
    for i in range(len(t) - 2):
        v[zlib.crc32(t[i:i+3].encode()) % dim] += 1
    n = math.sqrt(sum(x * x for x in v))
    return [x / n for x in v]
dot = lambda a, b: sum(x * y for x, y in zip(a, b))
q = embed("how do I reset my password")
for d in ["reset a forgotten password", "office wifi troubleshooting", "password policy and rotation rules"]:
    print(f"{dot(q, embed(d)):.3f}  {d}")
print("norm of a vector:", round(math.sqrt(dot(q, q)), 6))

0.297  office wifi troubleshooting
0.472  password policy and rotation rules

  1. Minute 0 to 3: install, run compare.py as is. Note the embedding size (bi.get_sentence_embedding_dimension()) and the time of the first call versus the second.
  2. Minute 3 to 6: replace the four documents with ten of your own and write down, before running, the order you expect. Run and score the agreement with a rank correlation or simply count pairs swapped.
  3. Minute 6 to 8: find a failure. Try an identifier ("INV-1042"), a negation ("password reset not working"), and a query in another language. Dense models blur exactly these (where dense retrieval fails).
  4. Minute 8 to 10: rerank. Use the bi-encoder to take the top 3 and the cross-encoder to reorder them. Count how often the order changes, and time both: the cross-encoder reads query and document together, so it costs one forward pass per pair.

What to look for. The stand-in script gives 1.0 for the vector norm and a dot product equal to cosine similarity; a real model with normalize_embeddings=True should behave the same, so a norm other than 1 means a normalisation step was skipped. Real similarities will be on a different scale from the stand-in's: never compare numbers across models. If you plan to fine-tune (chapter 7), the library's training API has changed between major versions; follow the current "training overview" page rather than older tutorials.

Common pitfalls

  • Models trained with prefixes ("query: ", "passage: ") used without them. The model card says whether prefixes are required.
  • Silent truncation at the model's maximum sequence length. A long chunk is embedded from its first few hundred tokens only; check model.max_seq_length against your chunk size (chunking).
  • Choosing a model from a leaderboard alone. Use it to shortlist, then measure on your own judgements (public benchmarks and their limits).
  • Using a cross-encoder on the whole corpus. It is a second-stage tool for tens of candidates (the two-stage pipeline).

Docs: the sentence-transformers documentation (sbert.net) and the model cards on the Hugging Face Hub.

ranx & pytrec_eval

Install: pip install ranx, pip install pytrec_eval (a C extension: it may need a compiler; pytrec-eval-terrier is a maintained fork on PyPI) · Alternatives: the trec_eval command-line tool, ir_measures, ir_datasets for loading standard collections, your own code from lab 2 · Chapters: 4, 5

Both libraries compute standard retrieval metrics (precision, recall, MRR, MAP, nDCG) from two inputs: qrels (the relevance judgements per query and document) and a run (what the system returned, with scores). pytrec_eval wraps the reference trec_eval code, so it is the one people use to check that their numbers agree with published ones. ranx is a Python-native library with the same metrics plus run fusion, statistical tests and comparison tables. Use them to check your own implementation and to run paired comparisons; keep your own harness for anything involving your data model.

10-minute guided exercise

Compute the metrics for one query by hand, then ask each library. The script gives the hand values for a six-document ranking with graded judgements.

"""Ranking metrics by hand on one query, so a library's output can be checked. Linear gain, log2 discount."""
import math
rels = {"a": 3, "b": 0, "c": 2, "d": 0, "e": 1, "f": 0}     # graded judgements for query q1
run = ["b", "a", "d", "c", "f", "e"]                         # the system's ranking
gains = [rels[d] for d in run]
dcg = lambda g, k: sum(x / math.log2(i + 2) for i, x in enumerate(g[:k]))
ideal = sorted(rels.values(), reverse=True)
for k in (3, 5):
    print(f"nDCG@{k} = {dcg(gains, k):.4f} / {dcg(ideal, k):.4f} = {dcg(gains, k) / dcg(ideal, k):.4f}")
rr = next(1 / (i + 1) for i, d in enumerate(run) if rels[d] > 0)
hits, ap = 0, 0.0
for i, d in enumerate(run, 1):
    if rels[d] > 0: hits += 1; ap += hits / i
print(f"MRR (reciprocal rank) = {rr:.4f}")
print(f"AP = {ap:.4f} / {sum(r > 0 for r in rels.values())} relevant = {ap / sum(r > 0 for r in rels.values()):.4f}")
print(f"P@3 = {sum(rels[d] > 0 for d in run[:3]) / 3:.4f}, recall@3 = {sum(rels[d] > 0 for d in run[:3]) / sum(r > 0 for r in rels.values()):.4f}")

  1. Minute 0 to 2: run the hand-computation script and copy its six numbers.
  2. Minute 2 to 5: run the two libraries and compare. nDCG@3 should be near 0.3975 and MRR 0.5 if the libraries use linear gain and a base-2 log discount; if a number differs, find out which gain or cut-off convention that library applies (some offer an exponential gain, 2^rel - 1, as an option). That discrepancy is the lesson: the name of a metric does not fix its formula.
  3. Minute 5 to 8: make the run worse on purpose. Swap documents a and b in the run and watch nDCG@3 and MRR move by different amounts (nDCG rewards the graded position of every document; MRR only looks at the first relevant one: chapter 4).
  4. Minute 8 to 10: compare two systems. Build a second run and use ranx's compare with a statistical test across several queries, or your lab 2 paired bootstrap. One query proves nothing; see how few queries it takes before the interval excludes zero.

What to look for. Agreement to four decimals with the hand values, and an understanding of every convention that moved a number: the cut-off, the gain, the treatment of documents with no judgement (usually non-relevant), and ties in scores (both libraries break them in a defined order; make your run scores distinct).

Common pitfalls

  • Unjudged documents counted as non-relevant. A better system that retrieves unjudged-but-good documents is scored down; this is why test collections use pooling (chapter 5).
  • Averaging over queries with no relevant documents (the metric is undefined; libraries differ in whether they score it 0 or skip it).
  • Reporting a single mean without an interval, or comparing runs with different query sets.
  • Document ids as numbers in one file and strings in the other, so nothing matches and every metric is 0.

Docs: the ranx repository (AmenRa/ranx) and pytrec_eval (cvangysel/pytrec_eval) on GitHub; the TREC evaluation guidelines for the meaning of each measure name.

Documents

The tools that turn pages into text and structure, so the retrieval stack above has something to index. Measure them on your own documents; public rankings do not transfer reliably.

Docling, Marker & MinerU

Install: pip install docling, pip install marker-pdf, pip install mineru (each downloads layout and OCR models on first use and wants a GPU or a patient CPU) · Alternatives: PyMuPDF and pdfplumber for born-digital PDFs, Unstructured, vision-language converters such as olmOCR, cloud document-AI services · Chapters: 18, 20

These are open-source converters that take a PDF (or an image, or an office file) and return structured Markdown or JSON: headings, reading order, tables, sometimes formulas and figures. They combine a layout-detection model, a table-structure model and either the PDF's own text layer or an OCR engine. Docling (IBM Research, described in a 2024 technical report) outputs a unified document model and exports to Markdown and JSON; Marker and MinerU are alternatives with their own strengths. Which is best depends on your documents, so the skill to build is comparing them on a page you care about. The case study on open document conversion explains how they work.

  4. Minute 9 to 10: write a one-line verdict per tool for this page. Then repeat on a scanned page and notice how the ranking can reverse.
"""Character and word error rates, with the confusions listed, for comparing two converters' output on the same page."""
from collections import Counter
def align(a, b):
    n, m = len(a), len(b)
    d = [[0] * (m + 1) for _ in range(n + 1)]
    for i in range(n + 1): d[i][0] = i
    for j in range(m + 1): d[0][j] = j
    for i in range(1, n + 1):
        for j in range(1, m + 1):
            d[i][j] = min(d[i-1][j] + 1, d[i][j-1] + 1, d[i-1][j-1] + (a[i-1] != b[j-1]))
    i, j, subs = n, m, Counter()
    while i and j:                                   # walk back to collect substitutions
        if d[i][j] == d[i-1][j-1] + (a[i-1] != b[j-1]):
            if a[i-1] != b[j-1]: subs[(a[i-1], b[j-1])] += 1
            i, j = i - 1, j - 1
        elif d[i][j] == d[i-1][j] + 1: i -= 1
        else: j -= 1
    return d[n][m], subs
truth = "Invoice INV-1042 dated 2026-09-30 total 780.60 EUR IBAN GB82 WEST 1234 5698 7654 32"
reads = {"engine A": "Invoice INV-1O42 dated 2026-09-30 total 780.60 EUR IBAN GB82 WEST 1234 5698 7654 32",
         "engine B": "Invoice INV-1042 dated 2026-09-3O total 78O.6O EUR IBAN GB82 WEST I234 5698 7654 32"}
for name, hyp in reads.items():
    ce, subs = align(truth, hyp); we, _ = align(truth.split(), hyp.split())
    print(f"{name}: CER {ce/len(truth):.2%} ({ce} edits / {len(truth)} chars), WER {we/len(truth.split()):.2%} ({we}/{len(truth.split())} words); confusions {dict(subs)}")
engine A: CER 1.20% (1 edits / 83 chars), WER 7.14% (1/14 words); confusions {('0', 'O'): 1}
engine B: CER 4.82% (4 edits / 83 chars), WER 21.43% (3/14 words); confusions {('1', 'I'): 1, ('0', 'O'): 3}

What to look for. Engine B's errors are all look-alike substitutions (the letter O for zero, I for one) that a checksum or an arithmetic validator would catch, while a missing paragraph would show as a large word error rate and no confusions at all. The first kind is a recognition problem; the second is a layout problem. They need different fixes (OCR, layout). For tables, character error rate is the wrong yardstick: check cell by cell, or use a tree-edit measure on the table structure (scoring a table).

Common pitfalls

  • Converting a clean born-digital PDF and concluding a tool is "excellent". Scans, skewed pages and dense tables are where converters differ.
  • Not pinning the version and the models: outputs change between releases, and a silent upgrade can change your index.
  • Ignoring licences. Some converters or their models carry licences that restrict commercial use; read them before you build on one.
  • Throwing away provenance. Keep the page number and bounding box with every block so citations and review screens can point at the source (blocks with provenance).

State of play, October 2026

Document-conversion tooling is moving quickly: layout-model-based pipelines (Docling and similar) and end-to-end vision-language converters (olmOCR and others) are both active, and benchmark suites such as OmniDocBench compare them. Rankings, model names and command-line flags change month to month and depend on the benchmark's document mix. Treat this card as a method for comparing tools, and check each project's current documentation for install and usage.

Docs: the Docling repository and technical report (arXiv 2408.09869), the Marker repository (datalab-to/marker) and the MinerU repository (opendatalab/MinerU).

Tesseract & PaddleOCR

Install: brew install tesseract or apt install tesseract-ocr (plus language packs such as tesseract-ocr-deu); pip install paddleocr paddlepaddle · Alternatives: EasyOCR, docTR, vision-language models used as OCR, cloud OCR services · Chapters: 19, 22

Tesseract is the long-standing open-source OCR engine (its current engine uses a neural line recogniser) and runs on CPU with language packs for over a hundred languages. PaddleOCR is a deep-learning toolkit with separate detection, direction-classification and recognition models, strong on multilingual and scene text and usually run on a GPU. Both return text with word or line boxes and a confidence for each. Those confidences are what the review threshold in the document-processing studio is built on, so it is worth seeing what they look like on real pages.

10-minute guided exercise

Measure how confidence relates to correctness on one page, then see what preprocessing does. Illustrative commands:

$ tesseract --version; tesseract --list-langs
$ tesseract invoice.png out -l eng --psm 6 tsv      # writes out.tsv: one row per word with left, top, width, height, conf, text
$ tesseract invoice.png stdout -l eng --psm 4      # plain text; --psm sets the page-segmentation mode
$ tesseract invoice_300dpi_deskewed.png out2 -l eng --psm 6 tsv
from paddleocr import PaddleOCR
ocr = PaddleOCR(lang="en")
result = ocr.ocr("invoice.png")     # newer releases may expose predict() instead: check the README
for line in result[0]:
    box, (text, conf) = line
    print(f"{conf:.2f}  {text}")
  1. Minute 0 to 3: take an invoice or form page (a phone photo is ideal), run Tesseract to TSV, and open out.tsv. Sort by the conf column.
  2. Minute 3 to 6: compare confidence with truth. Type the correct text of 20 words, including numbers. How many of the wrong words had low confidence? How many wrong words had confidence above 90? The second number is the one that decides how many errors reach your records without review.
  3. Minute 6 to 8: preprocess. Rescale to about 300 dpi, deskew, and convert to grey or binary, then run again. Which words changed? Resolution and skew are the cheapest accuracy gains you have.
  4. Minute 8 to 10: score it. Paste the engine's line for the invoice number, date and total into the character-error script from the Docling card as hyp and your typed truth as truth. Look at the confusions: O/0, 1/I/l and 5/S are the usual suspects, and validators (checksums, arithmetic) catch them (studio stage 7).

What to look for. Confidence is informative but not calibrated: a mapping from confidence to observed accuracy has to be measured on your pages (measuring OCR). Compare Tesseract and PaddleOCR on a page with a different script or a stamp over the text. Tesseract needs the right language pack and a sensible page-segmentation mode, and gives poor results on text it was not told about; PaddleOCR's detection model finds text in less regular layouts. For right-to-left or non-space-delimited scripts, check word segmentation and reading order as well as characters (chapter 22).

Common pitfalls

  • Wrong language pack. Reading German with the English model produces plausible-looking garbage in the accented letters.
  • Low resolution (under about 150 dpi), JPEG artefacts, shadows and perspective from phone photos. Fix these before blaming the engine.
  • Using full-page segmentation on a small crop, or the reverse; try several --psm values on a field-sized crop.
  • Taking the engine's confidence as a probability, or comparing it across engines.

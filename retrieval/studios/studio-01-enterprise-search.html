Design Enterprise Search with Permissions

Design one search box for a whole company: a dozen systems of record, tens of millions of documents, and an access rule on every one of them. The core problems are never showing a result the person may not read, keeping permissions and content fresh when the sources change underneath you, and ranking results from sources whose scores mean different things.

How a design studio works

This page is a mock design session of 60 to 75 minutes, not a chapter. At each stage there is a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer is one strong design with its reasoning, not the only right one. The stages follow the design framework with the extra steps an AI system needs: success metrics and an evaluation plan, estimates in documents and memory rather than requests, the data you ingest, a model and ranking strategy, failure modes and rollout. A rubric at the end separates mid-level from senior signals. All numbers on this page are assumptions to reason with, not measurements, and every script was run to produce the output shown.

📐 The brief

A hiring manager says: "We have 8,000 employees and about a dozen systems where work lives: a wiki, a shared drive, email, a ticket tracker, a chat tool, a CRM and more. People cannot find anything. Build us one search that works across all of it. Legal has one non-negotiable: nobody may ever see a document they could not open in the original system."

  • Every document already has an access rule in its own system. The rules differ in shape (groups, individuals, inherited folders, "anyone with the link").
  • People leave, change teams and share documents all day. A revoked permission should stop working quickly.
  • Later the company will want an assistant that answers questions from this content; the design should not make that unsafe.
  • Builds on hybrid search, approximate nearest-neighbour indexes and filters, metadata and permissions, with authorisation and change data capture underneath.
  • You have 60 to 75 minutes. Work through the stages in order.

How many chunks, how much memory for the vectors, how many queries a second, and how many permission changes a day? Which of these numbers surprises you?

  • The query load is tiny: about 3 a second on average, 20 at peak. The hard parts are not throughput. They are data volume, ingestion and permissions. A candidate who spends ten minutes on load balancers has estimated the wrong thing.
  • 160 million chunks make the vector side a memory decision. Stored as 32-bit floats the vectors are about 490 GB; compressed with product quantisation to 96 bytes they are 15 GB, at some cost in recall that you recover by re-scoring the top few hundred candidates with the full vectors kept on disk. The graph links of an HNSW index add another 20 GB. This is why the first design question about vectors is "do all 40 million documents deserve dense embeddings", not "which model".
  • Permission changes are a stream, not an exception: 0.4% of documents a day is 160,000 changes, nearly 2 a second, around the clock. Treat permission updates as first-class events with their own queue and their own freshness target.
  • Store groups, not users, on each chunk. If every document listed the individuals who can read it, a popular document in a company-wide group would carry thousands of names; the table above shows the difference is 36 billion entries against 120 million. Group membership changes then touch a small graph, not millions of chunks.
  • Crawl time is a quota problem. Initial ingestion of 3.3 million documents per source at an assumed 150 documents a second takes under a day, but real source APIs throttle hard, so plan the first crawl in days and make it resumable.
  • The reranker is small change. Reranking 50 candidates at about a millisecond each (rerankers) uses about one busy accelerator slot at peak. The cost of this system is storage and ingestion, not serving.

  • Connectors are the long tail of the work. Each source differs: some offer webhooks, some only a "changed since" API, some need a full crawl. The design pattern is the same: a connector turns the source's change signal into normalised events (content changed, permission changed, deleted) and a periodic reconciliation crawl catches what the events missed. Events are fast; the crawl is the safety net.
  • Normalise permissions at the boundary. Map every source's rule into allow sets of group and user ids, plus flags for "everyone" and "link sharing". Do not try to run each source's rule engine inside the search index. Keep the original ACL reference (an id and a version) so you can ask the source again.
  • Inherited permissions are the usual trap. A file inherits from its folder, which inherits from a shared drive. Moving a folder changes the permissions of thousands of files with one event. The connector must expand such events into per-document updates or store the inheritance chain and resolve it; choose expansion for simplicity and watch the event fan-out.
  • What you refuse to keep. Source types or folders marked as excluded (legal holds, HR cases, board material) never enter the pipeline. Secrets found in documents (keys, passwords) are a security finding to report, not content to embed. Documents with no readable ACL are indexed as nobody, not as everybody: the default on ambiguity is closed.
  • Deletes are a feature. Retention rules and "right to be forgotten" requests mean the index must forget. A document record in state deleted removes its chunks, its embeddings and its cached snippets; test this with a deletion canary as you test freshness.
  • Chunking and context. Chunk by structure (headings, tickets and their comments, mail threads) and prepend the document title and path to each chunk before embedding, as in chunking and contextual retrieval. Titles carry much of the signal in enterprise content, and the analysers must treat ticket ids, email addresses and file names as single tokens.

5High-level architecture

Draw the system. Where is the trust boundary? Which component is allowed to say "this person may read this document", and which components merely believe it?

Compare with a worked answer

Life of a change: a user edits a wiki page and removes a group from its sharing list. The connector receives a webhook (or finds the difference at the next reconciliation crawl) and puts an ACL event on the change queue. The ingest stage writes the new allow_groups and a higher acl_version to every chunk of that document, without re-embedding it, because the text has not changed. Within seconds the chunks are filtered out for the removed group.

Life of a query:

  1. The query service authenticates the user (OAuth and OIDC), looks up the user's group set in the group graph, and rewrites the query (spelling, acronyms: query understanding).
  2. It runs one BM25 query and one vector query against the index with the access filter inside the search (allow_groups intersects the user's groups, or allow_users contains the user, or the chunk is open to all), fuses the two lists with reciprocal rank fusion and reranks the top 50 (hybrid search).
  3. The top 10 go to the permission check, which asks each source system whether this user can open this document right now, in one batched call per source. Anything the source refuses, or cannot answer within the budget, is dropped.
  4. Snippets and highlights are built only from chunks that passed, and the response is logged to the audit store with the reason for each drop.

The trust boundary is the query service plus the permission check. The index is treated as a fast, possibly stale hint about who may read what; the source system is the authority. That sentence is the core of the design, and the next two stages justify it.

6Deep dive 1: filtering by permission without breaking ranking

A user belongs to 12 groups and can read 4% of the corpus. Compare filtering after the nearest-neighbour search with filtering inside it. What goes wrong with each, and what do you choose?

Compare with a worked answer

The mechanism is covered in filters, metadata and permissions. Here is the decision with numbers. The script below builds 20,000 vectors in 40 topic clusters and makes access correlate with topic, as it does in a company (payroll documents are readable by HR, incident reviews by engineering). It then asks for the top 10 for users with different amounts of access. Vectors are random clusters, a stand-in for a trained embedder; the arithmetic of selectivity is the point.

"""Permission filtering with nearest-neighbour search: post-filter vs pre-filter.
Vectors are random topic clusters (a stand-in for embeddings). Access is correlated with topic,
as in a real company: payroll documents are mostly readable by HR, not by everyone."""
import numpy as np
rng = np.random.default_rng(7)
N, D, TOPK, NQ = 20_000, 32, 10, 300
centres = rng.normal(size=(40, D))
topic = rng.integers(0, 40, N)
X = centres[topic] + 0.6 * rng.normal(size=(N, D))
X /= np.linalg.norm(X, axis=1, keepdims=True)

# 3% of docs are readable by everyone (-1); the rest by one of 5 groups that "own" their topic
group = np.where(rng.random(N) < 0.03, -1, topic * 5 + rng.integers(0, 5, N))
def visible(user_groups):
    return (group == -1) | np.isin(group, user_groups)

def topk(q, k, mask=None):
    s = X @ q
    if mask is not None: s = np.where(mask, s, -9)
    return np.argsort(-s)[:k]

print(f"{'groups':>6} {'visible':>8} | {'post 1x':>8} {'post 5x':>8} {'post 20x':>9} {'(<10 results)':>14} | {'pre-filter':>10}")
for ng in (2, 10, 40, 100):
    ug = rng.choice(200, ng, replace=False)
    mask = visible(ug)
    res = {1: [], 5: [], 20: []}; pre = []
    for _ in range(NQ):
        q = X[rng.integers(0, N)] + 0.3 * rng.normal(size=D); q /= np.linalg.norm(q)
        for m in res:
            res[m].append(min(TOPK, int(mask[topk(q, TOPK * m)].sum())))
        pre.append(int(mask[topk(q, TOPK, mask)].sum()))
    short = np.mean(np.array(res[20]) < TOPK)
    print(f"{ng:6d} {mask.mean():8.1%} | {np.mean(res[1]):5.1f}/10 {np.mean(res[5]):5.1f}/10 {np.mean(res[20]):6.1f}/10 {short:13.0%} | {np.mean(pre):7.1f}/10")
groups  visible |  post 1x  post 5x  post 20x  (<10 results) | pre-filter
     2     3.8% |   0.4/10   1.9/10    6.4/10           84% |    10.0/10
    10     7.9% |   0.8/10   3.6/10    7.8/10           55% |    10.0/10

  • Post-filtering is wrong in a way that hides itself. Retrieve 10, drop what the user cannot read, and a user who can read 4% of the corpus gets about half a result. Over-fetching 20 times helps, but the table shows that for the users with narrow access, 84% of searches still return fewer than 10 results. The failure is quiet: the search "works" and returns very little. It is also the version most likely to be shipped, because it is two lines of code.
  • Pre-filtering gets a full list every time because the filter is part of the search. Here it is exact brute force, which is cheap at 20,000 vectors and not at 160 million. Real approximate indexes handle a restrictive filter poorly: a graph index whose neighbours are mostly forbidden can stall, so engines switch strategy by selectivity (brute force over the allowed set when it is small, filtered graph traversal when it is large). Know which one your engine does and test the narrow-access user explicitly.
  • Choice: filter inside the engine, for both the lexical and the vector side, using the same access fields. Pick the engine partly on how it behaves with a 4% filter, and keep a per-user cache of "allowed set" fingerprints only if profiling shows the filter is the bottleneck.
  • Do not filter by individuals only. Putting the user's whole group list into the filter is fine for 12 groups; for users in 800 groups (managers, security staff) the filter clause itself becomes slow. Mitigations: collapse nested groups into the group graph and store the transitive closure per user with a short time to live, or give high-membership users an index of "everything except forbidden" using deny lists.
  • Per-tenant indexes are the other design. Separate indexes per department isolate cleanly but break company-wide search and multiply cost. Here a single shared index with per-chunk access tags is the right shape; multi-tenancy is about customers who must never be able to see each other, which this is not.
  • Ranking statistics leak. BM25 uses document frequency, which a shared index computes over everyone's documents. A rare term's score can hint that a document containing it exists. The leak is small but real for very sensitive corpora; the usual answer is to accept it for most content and exclude the most sensitive sources from the shared index entirely.

7Deep dive 2: how stale can a permission be?

Someone is removed from a confidential project at 10:00. Until when can search still show them its documents? Compare a nightly crawl, webhooks, and a query-time check against the source.

Compare with a worked answer

This is the part Legal cares about, so quantify it. Model 800 permission removals a day. Assume each removed person would be shown that document about 0.3 times an hour while it is still visible to them (they used it before). The index learns of a change after a lag that depends on the design. Webhooks usually arrive in seconds, but some are lost or the connector is down; those fall back to the next reconciliation crawl.

"""How long is a revoked permission still honoured, and how much does that leak?
A revoked (user, document) pair keeps appearing in that user's results until the index learns of the change.
All rates are assumptions; the shape of the answer is what matters."""
import random
rng = random.Random(11)
REVOKES = 800                  # permission removals per day
SHOWN_PER_HOUR = 0.3           # how often a former reader would be shown that document (they used it before)

def one_pair(webhook_p50_s, webhook_loss, crawl_s):
    """Seconds between the revocation and the index forgetting it."""
    if rng.random() < webhook_loss:                  # event lost or connector down: wait for the next crawl
        return rng.uniform(0, crawl_s)
    return rng.expovariate(0.693 / webhook_p50_s)    # median = p50

def poisson(mean):
    n, p, e = 0, 1.0, 2.718281828 ** -mean
    while True:
        p *= rng.random()
        if p < e: return n
        n += 1

def day(webhook_p50_s, webhook_loss, crawl_s, check_top_k):
    leaked, worst = 0, 0.0
    for _ in range(REVOKES):
        lag = one_pair(webhook_p50_s, webhook_loss, crawl_s)
        worst = max(worst, lag)
        if not check_top_k:
            leaked += poisson(SHOWN_PER_HOUR * lag / 3600)
    return leaked, worst / 3600

print(f"{'design':50} {'leaked/day':>10} {'worst lag':>10}")
for label, args in [
    ("nightly crawl only",                        (0, 1.0, 24 * 3600, False)),
    ("hourly crawl only",                         (0, 1.0, 3600, False)),
    ("webhooks (p50 5 s), 2% lost, hourly crawl", (5, 0.02, 3600, False)),
    ("webhooks (p50 5 s), 2% lost, nightly crawl",(5, 0.02, 24 * 3600, False)),
    ("same, plus query-time check of the top 10", (5, 0.02, 24 * 3600, True)),
]:
    if args[0] == 0:
        # crawl-only: lag is uniform over the crawl interval
        args = (1e-9, 1.0, args[2], args[3])
    leaked, worst = day(*args)
    print(f"{label:50} {leaked:10d} {worst:8.1f} h")

  • The average is not the problem; the tail is. Webhooks with a 5-second median look excellent, yet the 2% that are lost wait for the next crawl. With a nightly crawl behind them the design leaks 60 results a day and has a worst case near 24 hours. An hourly crawl brings the same design to 4 a day and a one-hour worst case. This is the same lesson as in tail latency: the slow few set the guarantee.
  • The query-time check removes the leak whatever the index believes. Asking the source about the final 10 results makes the exposure zero in the model, even though the index is still stale (the last line still shows a worst-case lag of about 23 hours). It costs one batched call per source per search and it fails in a way you must decide on: if the source API is slow or down, fail closed, hide the result and say that some results could not be verified. A search that is occasionally less complete is a nuisance; one that is occasionally unsafe is an incident.
  • Cache the answers, briefly. Cache "user U may read document D" for 60 seconds. That bounds the load on source APIs and also bounds the staleness you accept. Say the number out loud: a 60-second cache means a revocation takes up to a minute to bite, and that is a business decision for Legal, not an implementation detail.
  • Ordering matters. A user is added to a group at 10:00, the group gets access to a document at 10:01, and the events reach the index in the other order. Google's Zanzibar authorisation system (Pang et al., 2019, "Zanzibar: Google's Consistent, Global Authorization System") describes how consistency tokens let a service check a permission against a state no older than the content it protects. You do not need Zanzibar, but you do need to know that "permission fresher than content" is the property to aim for, and to put the ACL version in each chunk so you can compare (consistency models).
  • Group changes fan out. Removing someone from a group does not touch documents: the index stores groups, and the group graph answers "which groups is this user in?" at query time. That is the second reason for storing group ids instead of users. Cache the user-to-groups lookup for a short time (a minute) and invalidate it on leaver events from HR.
  • Leavers and emergencies. When someone is dismissed, disable them in the identity provider and have the query service reject their token immediately; do not wait for the index. For a leaked document, a manual "tombstone" operation hides a doc id from every user within seconds.

8Deep dive 3: relevance across sources, and freshness

The wiki's ranker returns scores around 12 to 18, the mail search returns 0.4 to 0.7, and tickets sit in between. How do you merge them? How do you stop a 2019 page outranking its 2025 replacement?

Compare with a worked answer

If you index everything into one engine, scores come from one scorer and are comparable. In practice some sources keep their own search (permission-heavy chat, a CRM) and are queried live. Then you merge lists whose numbers mean different things. The options from hybrid search apply: merge by rank (reciprocal rank fusion) or normalise scores per source and combine. The script below shows the second, plus two signals enterprise search needs: freshness that decays at a rate suited to the source, and an authority bonus for the document marked as the current official version.

"""Merging results from different sources: raw scores are not comparable. Normalise per source, then add freshness and authority.
Scores and dates are made up to show the mechanism."""
import math
TODAY = 300  # day number
# (id, source, raw score from that source's own ranker, age in days, is_current_policy)
hits = [
    ("wiki: vpn setup (2019)",        "wiki",   18.2, 2400, False),
    ("wiki: vpn setup (2025)",        "wiki",   16.9,  120, True),
    ("ticket: vpn fails on hotel wifi","tickets", 9.1,    3, False),
    ("mail: vpn outage notice",        "mail",   0.71,   2, False),
    ("slides: vpn rollout deck",       "drive",  0.64,  400, False),
]
src_stats = {"wiki": (12.0, 4.0), "tickets": (6.0, 2.5), "mail": (0.40, 0.15), "drive": (0.45, 0.12)}   # mean, sd of each source's top-50 scores
HALF_LIFE = {"wiki": 365, "tickets": 14, "mail": 7, "drive": 180}                                         # days; fast-moving sources decay fast

def z(src, s): m, sd = src_stats[src]; return (s - m) / sd
def fresh(src, age): return 0.5 ** (age / HALF_LIFE[src])

Normalising each source against its own score distribution (here a z-score against the mean and spread of its top 50, estimated from a sample of queries) turns "how good compared with this source's usual results" into a shared unit. Rank fusion is the alternative when you do not trust the distributions to stay stable.
  • Freshness is not one decay. A mail announcing an outage is relevant for days; a policy page for years. Use a half-life per source (7 days for mail, 14 for tickets, 365 for the wiki in the script) and weight it modestly, because freshness is a tie-breaker between similar documents, not a reason to show an irrelevant new page first. Tune the weights on the gold set, with confidence intervals (relevance metrics), and do not change two things at once.
  • Authority beats age. If a page is marked as the current version (or is the target of a "this replaces" link), its old siblings should be demoted or collapsed under it. The 2019 page ends last in the output, not because it is old but because a newer one supersedes it. Where the source has no such marker, use clues: page owner, edit recency, link counts, "deprecated" in the title.
  • Dense retrieval over internal text has blind spots. Product code names, ticket ids and acronyms are poorly represented by general embedders (dense retrieval). Keep the lexical retriever as an equal partner, add a synonym and acronym table maintained from the logs, and fine-tune the embedder on clicked query-document pairs only after you have the gold set to prove it helped.
  • Result diversity. Ten results from one thread of mail are worse than five documents of different types. Group by document and by source, show the best chunk, and keep at least one result from each source in the top 10 when scores are close.
  • Personalisation, carefully. A boost for documents in the user's own team folders and recently opened files helps and is cheap, but it makes results differ per person, so two people comparing notes see different pages. Keep it small and log which signals fired.

The right test for all of these is one idea, run daily in production: plant a canary, then try every surface from every other audience. The toy engine below has a deliberate bug (facet counts are computed before filtering). The test finds it.

"""Permission canary tests: plant a secret in every group, then assert nobody else can see it through ANY surface.
The 'engine' is a toy; one of its surfaces (facet counts) has a deliberate bug, as real ones do."""
from collections import Counter, defaultdict
docs = {   # id: (text, source, allowed groups)
    "hr-1":  ("salary review process for staff", "drive", {"hr"}),
    "eng-1": ("incident review process for outages", "wiki", {"eng", "hr"}),
    "pub-1": ("holiday calendar for staff", "wiki", {"all"}),
}
for g in ("hr", "eng", "legal"):                        # one canary per group, with a unique nonsense token
    docs[f"canary-{g}"] = (f"zq{g}canary review", "drive", {g})
index = defaultdict(set)
for d, (text, _, _) in docs.items():
    for w in text.split(): index[w].add(d)

def allowed(d, user): return bool(docs[d][2] & (user | {"all"}))

def search(q, user):
    hits = set.intersection(*(index[w] for w in q.split())) if all(w in index for w in q.split()) else set()
    return sorted(d for d in hits if allowed(d, user))

def facets(q, user):                                    # BUG: counts computed over all matches, filtered afterwards
    hits = set.intersection(*(index[w] for w in q.split())) if all(w in index for w in q.split()) else set()
    return dict(Counter(docs[d][1] for d in hits))      # leaks that a hidden document exists

def suggest(prefix, user):                              # correct: only terms from documents the user may see
    ok = {w for d in docs if allowed(d, user) for w in docs[d][0].split()}
    return sorted(w for w in ok if w.startswith(prefix))

problems = []
for user_name, user in [("eng-user", {"eng"}), ("legal-user", {"legal"})]:
    for g in ("hr", "eng", "legal"):
        if g in user: continue
        token = f"zq{g}canary"
        if search(token, user):                problems.append((user_name, "search", token))
        if facets(token, user):                problems.append((user_name, "facets", token))
        if suggest(token[:6], user):           problems.append((user_name, "suggest", token))
    # a visible control: the user must still see their own canary
    own = [g for g in user if g in ("eng", "legal")][0]
    assert search(f"zq{own}canary", user), "control failed: user cannot find their own document"
print(f"{len(problems)} leak(s) found")
for p in problems: print("  LEAK", p)
4 leak(s) found
  LEAK ('eng-user', 'facets', 'zqhrcanary')
  LEAK ('eng-user', 'facets', 'zqlegalcanary')
  LEAK ('legal-user', 'facets', 'zqhrcanary')
  LEAK ('legal-user', 'facets', 'zqengcanary')
  • The control matters as much as the attack. The test also asserts that a user can find their own canary; otherwise a broken engine that returns nothing passes.
  • Treat a leak as a security incident, with the response from detection and incident response: contain (tombstone the documents, disable the surface), find out who saw what from the audit log, then fix and add a regression canary.

Common misconception

"We filter by the user's groups, so it is safe." The filter is correct only as of the last sync. A search index is a copy, and every copy of an access rule can be out of date. Safe means the final answer comes from the system that owns the rule, or that you have chosen and measured a staleness bound.

  • Adding an assistant: retrieve with the asking user's identity, run the same two walls, cite the chunks used, and never put another user's retrieved text in a shared prompt cache. Citations then follow grounded answers and citations; the end-to-end shape is RAG end to end. Agents that act on search results need the least privilege and the injection defences in agent security.
  • Twice the documents: storage and ingestion scale linearly; the first thing to break is the reconciliation crawl window, so make crawls incremental and shard them by source and folder. Quantise vectors earlier and move older content to a cheaper tier (ANN indexes).
  • A regulated subsidiary: the data may not leave its region or may need separate keys. Run a separate index in that region and federate at the query layer (the query service fans out to both and merges), accepting higher latency (multi-region systems, data protection).
  • "Anyone with the link" documents: they are readable by anyone who has the URL but are not meant to be discoverable. Index them as readable only by the owner and by people who have recorded an access, not by the whole company, or you convert an unguessable link into a public listing.

State of play, October 2026

Most large vendors now sell connector-based enterprise search with permission-aware retrieval, and several vector databases and search engines offer document-level security and filtered vector search as features. The details (which sources, how often permissions are synced, how filters behave under heavy selectivity) differ by product and change often; check the vendor's current documentation and test with the canary approach above rather than trusting a feature name. The design reasoning on this page does not depend on any one of them.

12Say it out loud: a five-minute summary

Say your design aloud in five minutes, then compare with the model summary.

Compare with a worked answer

How a senior engineer would summarise this

"The load is small and the risk is large. Eight thousand people make about twenty searches a second at peak; the real numbers are 160 million chunks, a hundred and sixty thousand permission changes a day, and one rule from Legal: nobody sees what they could not open at the source. So I treat permissions as the product. Connectors turn each source's changes, content and access, into events on a durable queue, with a reconciliation crawl behind them for the events that get lost. Each chunk is indexed with the groups that may read it, not the users, so a membership change touches a small graph. At query time I resolve the user's groups, run BM25 and vector search with the access filter inside the engine, because post-filtering returns almost nothing for people with narrow access, fuse with reciprocal rank fusion, rerank the top fifty, and then ask the source system whether this user can open each of the final ten. The index is a hint; the source is the authority, and if the source cannot answer, I fail closed. I'd measure revocation lag at the 99th percentile, because webhooks are fast but the lost two percent set the guarantee. Ranking across sources uses per-source normalisation, a freshness half-life that suits each source, and a bonus for the current official version. I'd test for leaks by planting a canary per group and attacking every surface, results, snippets, counts, suggestions and caches, daily, and I'd treat any failure as an incident. For the later assistant, same walls, the asking user's identity, no shared caches of generated text. If we add a regulated subsidiary, a regional index and federation at the query layer."

Notice the shape: small load, big risk → permissions as events and tags → filter inside, check at the source, fail closed → measure the tail → canary every surface.

Key takeaways

  • Enterprise search is a small-load, large-data, high-risk problem. Size it in chunks, memory and change events, not in requests a second.
  • Store groups on chunks and keep a group graph, so a membership change never rewrites millions of documents.
  • Filter inside the retrieval engine. Filtering after the nearest-neighbour search returns almost nothing for users with narrow access.
  • The index is a hint about permissions; the source system is the authority. Check the final results there and fail closed.
  • Webhooks are fast and unreliable. A reconciliation crawl sets the worst case, and revocation lag at the 99th percentile is the number to watch.
  • Normalise scores per source, decay freshness at a rate that suits each source, and give the current official version a bonus.
  • Leaks hide in snippets, counts, suggestions, caches, logs and answers. Plant a canary per group and attack every surface daily.

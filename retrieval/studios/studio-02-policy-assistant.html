Design a Policy & Regulation Assistant

Design an assistant that answers staff questions about internal policy and external regulation, where people act on the answer and the rules change every month. The core problems are retrieving the version of a rule that applied on the right date, producing citations a reviewer can check in seconds, and knowing when to refuse and hand over to a person.

How a design studio works

This page is a mock design session of 60 to 75 minutes, not a chapter. At each stage there is a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer is one strong design with its reasoning, not the only right one. The stages follow the design framework with the steps an AI system adds: users and risk, success metrics and an evaluation plan, estimates, the data and its versions, architecture, model and verification strategy, failure modes, and rollout. A rubric at the end separates mid-level from senior signals. All numbers on this page are assumptions to reason with, not measurements. The rules quoted in the examples are invented for teaching and are not real regulation.

📐 The brief

A head of compliance says: "Our staff ask the compliance desk the same few thousand questions: can I accept this gift, when must I report this payment, does this rule apply to our Irish entity. We have 1,400 documents: our own policies plus the regulations they rest on. Build an assistant that answers from them. The answers will be acted on, so a reviewer must be able to check each one against the source in seconds. And the documents change: we get new versions most days."

  • A wrong answer can cost money or cause a breach; a refusal costs a few minutes of a human's time. These costs are not symmetric.
  • Questions often concern the past ("was this allowed in June?") as well as the present.
  • The compliance desk has limited people. The assistant must reduce their load without hiding risk.
  • Builds on RAG end to end, grounded answers and citations and how RAG fails, and on the case of the airline chatbot held to a policy it invented.
  • You have 60 to 75 minutes. Work through the stages in order.

How big must the gold set be? The next script computes 95% Wilson intervals, which behave sensibly near 0% and 100% where the plain normal approximation does not (test collections, human labels).

"""How big must the gold set be? Wilson 95% intervals for a pass rate, and the 'rule of three' for zero failures."""
import math
def wilson(k, n, z=1.96):
    p = k / n; d = 1 + z * z / n
    c = (p + z * z / (2 * n)) / d
    h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return c - h, c + h
print("observed 96% faithful answers:")
for n in (50, 100, 200, 400, 1000):
    lo, hi = wilson(round(0.96 * n), n)
    print(f"  n={n:5d}: 95% interval {lo:6.1%} to {hi:6.1%}  (width {hi-lo:5.1%})")
print("\nzero failures seen in n trials: the true failure rate could still be as high as about 3/n")
for n in (30, 100, 300, 1000):
    lo, hi = wilson(n, n)
    print(f"  n={n:5d}: failure rate could be up to {1-lo:5.2%}  (rule of three: {3/n:5.2%})")
print("\nto separate 96% from 98% (non-overlapping intervals), roughly:")
for n in (200, 500, 1000, 2000, 4000):
    a = wilson(round(0.96*n), n); b = wilson(round(0.98*n), n)
    print(f"  n={n:5d}: 96% -> {a[0]:.1%}..{a[1]:.1%}   98% -> {b[0]:.1%}..{b[1]:.1%}   {'separated' if b[0] > a[1] else 'overlap'}")

  • "96% on 100 questions" could be 90% or 98%. The interval at n=100 is 90.2% to 98.4%. Reporting a single number from a small gold set is the most common evaluation mistake in this kind of project.
  • "No failures in 100" is not "no failures". The rule of three says the true failure rate could be as high as about 3%. For a safety claim of "below 0.5%", you need roughly 600 independent questions with zero failures.
  • Telling 96% from 98% needs thousands. The overlap rule used here is conservative, but the lesson holds: small improvements need many questions, so judge small changes with a paired comparison on the same questions (relevance metrics), which needs far fewer.
  • Build the set deliberately: 300 questions to start from desk tickets and logs, stratified by tier, jurisdiction and topic; 10% adversarial (a question whose answer was true last year; a question the corpus cannot answer; a question that uses a defined term in a non-standard way); each with the exact supporting sections and effective dates. Use a second labeller for a sample and report agreement.
  • Re-run the set on every change to the corpus, the prompt, the model and the retriever. The set is a regression suite as much as a benchmark.

  • The model bill is not the constraint. About 4,500 questions a day cost under $100 a day at the assumed prices. Prices change often and model choices will differ, so treat the dollar figures as a template for the arithmetic: context tokens dominate (eight chunks of 450 tokens is 3,600 of the 4,340 input tokens), and the verification pass on a small model adds about 2%.
  • Expected error cost is. If 4% of unreviewed answers had a material error and one in ten wrong answers is acted on at an average cost of $2,500, that is $45,000 a day; the controls in this design aim at a tenth of that. The assumptions are rough on purpose: change them and see which one moves the conclusion (the cost of a wrong answer does).
  • Human review is the budget. Half of abstentions escalating, 8% of questions classed as high-stakes and a 2% spot-check sample is 720 items a day, about eight full-time reviewers at four minutes each. Every design choice that reduces the number of items a person must read, without reducing safety, is worth more than any token saving: precise citations (30 seconds to check, not 4 minutes), risk tiers, and answer caching for identical questions on an unchanged corpus.
  • Ingestion is steady work. About 17 new versions per working day, each needing parsing, section matching, a diff, re-embedding of changed sections only, and re-testing (stage 9). It is small data and high consequence.
  • Latency is relaxed. Low volume (under one question a second at peak) means you can afford a verification step, a second retrieval attempt, and reranking deeper (rerankers). Spend latency on correctness here.

  • Two time axes. Effective time is when the rule applied; ingestion time is when your system learned of it. A circular published on 20 December that takes effect on 1 January is ingested before it is effective. A late correction to a past text is ingested after the period it describes. Questions about rules use effective time; audits of what the assistant said use ingestion time. Databases call this a bitemporal model (indexes and the range queries they need).
  • Structure is the unit of meaning. Chunk along the document's own numbering (article, section, sub-clause) and keep the path on every chunk. A paragraph that says "the limit in the preceding paragraph does not apply to..." is meaningless without it. Parent-child retrieval (find the clause, show the section) comes from chunking and contextual retrieval. PDFs need layout-aware parsing and reading order (PDFs and layout) and tables of thresholds need table recovery (tables and forms).
  • Definitions and cross-references. Regulation text defines terms once and uses them everywhere. When a retrieved chunk uses a defined term, attach the definition; when it says "as set out in section 7", fetch that section as a second hop (agentic retrieval) or precompute the link graph at ingestion.
  • Authority and hierarchy. A regulator's rule outranks a company policy, which outranks a wiki explainer. Store an authority rank and let conflicts surface: when two retrieved passages disagree, the answer must say so and tier 3 escalation fires.
  • Provenance for every answer is the reason for the answer record: if the 4.2 threshold was wrong for three weeks, you can list every answer that used it.

5High-level architecture

Draw the system. Where do dates enter retrieval? Where is the last place a wrong answer can be stopped?

Compare with a worked answer

Life of a question:

  1. The query service classifies the risk tier and extracts the as-of date ("today" unless the question says otherwise) and the entity and jurisdiction from the user's profile and the question.
  2. It retrieves with BM25 and vectors, filtered to sections in force on that date and in the right jurisdiction (hybrid search, filters and metadata), reranks, expands definitions and cross-references, and assembles a context of a few sections with their ids, versions and dates.
  3. The model is asked for a structured answer: short answer, then a list of claims, each with the chunk id and an exact quote. It is told it may answer "not covered" and that quotes must be copied.
  4. The citation gates (stage 7) check the output in code. Failures are retried once with the failure message, then escalated.
  5. Tier 1 answers that pass go to the user; tier 2 are shown as drafts with the evidence expanded; tier 3 and failures go to the reviewer with the retrieved passages. Everything is logged to the answer record.

The design principle: the model proposes; code and people dispose. A language model is good at reading a dense paragraph and drafting a plain-language answer. It is not an authority on what the paragraph says. Everything it claims is checkable mechanically, or it does not reach the user.

6Deep dive 1: retrieving the right version of a rule

Version 1 and version 2 of section 4.2 are nearly identical text with different numbers. A user asks about a transaction of 12,000 euros. What does a plain retriever return, and how do you fix it?

Compare with a worked answer

Search engines rank by similarity to the query. Two versions of the same section are, by construction, almost identical, so they tie, and whichever the engine returns first wins. The script below builds a four-section corpus with two versions of section 4.2 (threshold 10,000 euros before 2026, 15,000 from 1 January 2026) and asks the same question with and without a date filter. The ranker is a small TF-IDF scorer, enough to show the mechanism.

"""Retrieval over versions: which text was in force on the date the question is about?"""
import re, math
from collections import Counter
sections = [   # (section id, version, in force from, in force until, text)
 ("cash-4.2", 1, "2023-04-01", "2025-12-31", "Cash transactions above 10,000 euros in a single day must be reported to the compliance desk within 5 working days."),
 ("cash-4.2", 2, "2026-01-01", "9999-12-31", "Cash transactions above 15,000 euros in a single day must be reported to the compliance desk within 3 working days."),
 ("cash-4.3", 1, "2023-04-01", "9999-12-31", "Cash transactions made by a politically exposed person are always reported, whatever the amount."),
 ("travel-2.1", 1, "2024-01-01", "9999-12-31", "Staff may book economy flights without approval when the fare is below 800 euros."),
]
tok = lambda s: re.findall(r"[a-z0-9]+", s.lower())
df = Counter(w for *_, t in sections for w in set(tok(t)))
def score(q, text):
    tf = Counter(tok(text)); n = len(sections)
    return sum(tf[w] * math.log(1 + n / df[w]) for w in tok(q) if w in tf)

def search(q, as_of=None, k=2):
    pool = [s for s in sections if as_of is None or s[2] <= as_of <= s[3]]
    return sorted(pool, key=lambda s: -score(q, s[4]))[:k]

q = "do I report a cash transaction of 12,000 euros"
print("without a date filter:")
for s in search(q): print(f"  {s[0]} v{s[1]} (in force {s[2]} to {s[3]})  score {score(q, s[4]):.2f}")
for as_of in ("2025-06-10", "2026-03-02"):
    print(f"as of {as_of}:")
    for s in search(q, as_of): print(f"  {s[0]} v{s[1]}  {s[4][:78]}...")

  • The scores are exactly equal. Without a filter the retriever has no basis to prefer version 2, and a language model handed both versions will pick one, merge them, or hedge. Any of these is a wrong answer for someone. This is the stale-source failure in how RAG fails, in its purest form.
  • Filter by effective date before ranking, not after, and not by asking the model to "use the latest". The as-of date comes from the question when it has one and defaults to today. With the filter, a question about June 2025 gets version 1 and a question about March 2026 gets version 2, both correctly.
  • When the date is ambiguous, ask or show both. "Can I still do this?" has no date. Default to today, state that date in the answer, and offer to answer as of another date. If a change takes effect soon (in the next 90 days), say so in the answer: "from 1 January this limit becomes 15,000 euros".
  • Jurisdiction is a filter too. A rule for the Irish entity must not answer a question from the German desk. Filter on the entity's jurisdictions and let tier 3 handle questions that span several.
  • Section-level recall is the metric. Evaluate retrieval on whether the needed section at the right version is in the top 10 (stage 2), not on whether some similar text was found.
  • Dense vectors blur numbers. Embeddings treat "10,000" and "15,000" as nearly the same thing; keep the lexical retriever and consider extracting thresholds as structured fields (dense retrieval, schemas and validation) for the highest-value rules.
  • Long contexts are not a fix. Stuffing whole documents into the prompt invites the lost-in-the-middle effect (case: Lost in the Middle) and makes citations coarse. Retrieve the few sections that matter and show them in full.

7Deep dive 2: citations a reviewer can check

What exactly must be true of a citation before you show it? List the checks, say which can be done by code, and say what code cannot catch.

Compare with a worked answer

A citation is a promise: "this claim is supported by this text". Make the promise checkable by requiring a structured answer: each claim carries a chunk id and an exact quote. Then four mechanical gates (grounded answers and citations) follow. The model outputs in the script are scripted stand-ins, written to exercise each gate; the gates are real code.

"""Citation gates for a policy answer. The answers are scripted (a stand-in for model output) so the gates can be tested."""
import re
CHUNKS = {
 "cash-4.2@v2": ("2026-01-01", "9999-12-31", "Cash transactions above 15,000 euros in a single day must be reported to the compliance desk within 3 working days."),
 "cash-4.2@v1": ("2023-04-01", "2025-12-31", "Cash transactions above 10,000 euros in a single day must be reported to the compliance desk within 5 working days."),
 "cash-4.3@v1": ("2023-04-01", "9999-12-31", "Cash transactions made by a politically exposed person are always reported, whatever the amount."),
}
norm = lambda s: re.sub(r"\s+", " ", s.lower().replace("’", "'")).strip()
nums = lambda s: set(re.findall(r"\d[\d,\.]*", s))

def gate(answer, as_of, question=""):
    problems = []
    for i, c in enumerate(answer["claims"], 1):
        if not c.get("cite"):
            problems.append(f"claim {i}: no citation"); continue
        if c["cite"] not in CHUNKS:
            problems.append(f"claim {i}: cites {c['cite']}, which was not retrieved"); continue
        start, end, text = CHUNKS[c["cite"]]
        if not (start <= as_of <= end):
            problems.append(f"claim {i}: cited text is not in force on {as_of}")
        if norm(c["quote"]) not in norm(text):
            problems.append(f"claim {i}: quote is not in the cited passage")
        unsupported = nums(c["text"]) - nums(c["quote"]) - nums(question)   # numbers may come from the quote or the user's own question
        if unsupported:
            problems.append(f"claim {i}: numbers {sorted(unsupported)} are in neither the quote nor the question")
    return problems

QUESTION = "Do I have to report a cash transaction of 12,000 euros?"
A = {  # label: (as-of date, claims)
 "good": ("2026-03-02", [dict(text="A cash transaction of 12,000 euros is below the 15,000 euro threshold, so it is not reportable on that ground.", cite="cash-4.2@v2", quote="above 15,000 euros in a single day")]),
 "stale version": ("2026-03-02", [dict(text="Transactions above 10,000 euros must be reported within 5 working days.", cite="cash-4.2@v1", quote="above 10,000 euros in a single day must be reported to the compliance desk within 5 working days")]),
 "invented quote": ("2026-03-02", [dict(text="Reports are due within 3 working days.", cite="cash-4.2@v2", quote="reports are due within three working days of the transaction")]),
 "number drift": ("2026-03-02", [dict(text="The threshold is 25,000 euros.", cite="cash-4.2@v2", quote="above 15,000 euros in a single day")]),
 "uncited claim": ("2026-03-02", [dict(text="The desk usually replies within a day.", cite=None, quote="")]),
}
for label, (as_of, claims) in A.items():
    p = gate({"claims": claims}, as_of, QUESTION)
    print(f"{label:15} -> {'PASS' if not p else 'BLOCK: ' + '; '.join(p)}")
good            -> PASS
stale version   -> BLOCK: claim 1: cited text is not in force on 2026-03-02
invented quote  -> BLOCK: claim 1: quote is not in the cited passage; claim 1: numbers ['3'] are in neither the quote nor the question
number drift    -> BLOCK: claim 1: numbers ['25,000'] are in neither the quote nor the question
uncited claim   -> BLOCK: claim 1: no citation
  • Gate 1, the chunk was retrieved: the cited id must be in the context given to the model. A model can invent an id as easily as a quote.
  • Gate 2, the version was in force on the question's date. The stale-version answer above quotes real text correctly, and is still wrong: the gate blocks it because the text was superseded. A generic hallucination check would pass it.
  • Gate 3, the quote is a substring of the cited text (after normalising whitespace and quotes). This catches invented and "improved" quotes; the Air Canada chatbot's "policy" would have failed this gate (the chatbot's promise), and so would the fabricated cases in fake citations in court.
  • Gate 4, numbers and dates in the claim come from the quote or from the question. A model that writes "25,000" next to a quote about 15,000 is caught. Arithmetic over quoted numbers should go through a calculator tool, not the model's head (tool use and its risks in the agents course).
  • Uncited claims are blocked, including the plausible filler sentence ("the desk usually replies within a day").
  • What code cannot catch: a real quote that does not support the claim (the claim says "always" and the text says "usually"), a claim that is correct about the quote but misses an exception in the next paragraph, and a right answer to the wrong question. These need a second model that judges entailment between claim and quote, and people. Use the judge to prioritise human review, calibrate it on labelled examples, and never let it be the only check on tier 2 or 3 (fact-checking and citation verification).
  • Make the check fast for the human. Show the quote highlighted in the original page image or PDF at the stored bounding box, with the section path, version and effective dates beside it. A reviewer should confirm a citation in under 30 seconds because the evidence is one click away.
  • Measure the gates. Log the failure rate of each gate. A rising rate of "quote not found" means a prompt or model change made copying worse; a rise in "not in force" means retrieval stopped honouring the date.

8Deep dive 3: when to refuse, and how a person takes over

  • Abstention is trained and measured, not hoped for. Include unanswerable questions in the gold set (stage 2) and report the refusal precision and recall. Tune the relevance threshold on that set, then check that you did not push the unneeded-refusal rate above the target; a refusing system is ignored, and people go back to emailing the desk.
  • Confidence is an input, not a number to show. Do not print "87% confident". Models are not calibrated in this sense, and users treat a percentage as a probability. Show the evidence and the tier instead.
  • The handover is a package. The reviewer sees the question, the as-of date, the retrieved sections with highlighted quotes, the draft answer, the failed gate if any, and two buttons: approve (with edits) or write a fresh answer. The reviewer's final text and the reason for edits go back to the answer record; edits are the best training and test data you will ever get (the improvement flywheel).
  • Close the loop to the user. The user sees "a reviewer is checking this, expected within 2 hours" rather than silence. A time budget for the desk (and an alert when the queue exceeds it) is part of the design (queueing).
  • Tell the user the limits once, clearly. The footer says what the answer is based on ("policy 4.2 version 2, in force from 1 January 2026"), that it is not legal advice, and where to go if the situation is unusual. This is also what protects the company if a user over-trusts an answer; but it does not replace getting the answer right (in the airline case the correct policy sat one link away from the chatbot's wrong answer, and that did not protect the company).

9Deep dive 4: keeping up with a corpus that changes

A new version of a circular arrives. List everything in your system that is now possibly wrong, in the order you would fix it. How do you find those things quickly and avoid re-doing everything?

Compare with a worked answer

If every artefact records which section versions it was built from, a change becomes a graph query. Hash each section's text, compare with the previous version, and follow the links. The script below does this for a four-section document in which two sections change and one is added.

"""When a document gets a new version, what else is now suspect? Hash sections, diff, follow the provenance links."""
import hashlib
h = lambda t: hashlib.sha256(t.encode()).hexdigest()[:8]
old = {"4.1": "Report cash above 10,000 euros.", "4.2": "Reports are due within 5 working days.", "4.3": "PEP transactions are always reported.", "7.1": "Retain records for 5 years."}
new = {"4.1": "Report cash above 15,000 euros.", "4.2": "Reports are due within 3 working days.", "4.3": "PEP transactions are always reported.", "7.1": "Retain records for 5 years.", "7.2": "Records of reports are kept for 7 years."}

changed = sorted({s for s in old.keys() | new.keys() if (h(old[s]) if s in old else None) != (h(new[s]) if s in new else None)})
print("changed sections:", changed, "| unchanged:", sorted(set(new) - set(changed)))

# provenance: every artefact that was built from a section records the section hash it used
chunks = {"c1": ["4.1"], "c2": ["4.2"], "c3": ["4.3"], "c4": ["7.1"], "c5": ["4.1", "4.2"]}
gold = {"q-threshold": ["4.1"], "q-deadline": ["4.2"], "q-pep": ["4.3"], "q-retention": ["7.1"]}
cache = {"a-8812": ["4.1"], "a-8813": ["4.3"], "a-9001": ["4.2", "4.1"]}
for name, table in (("chunks to re-embed", chunks), ("gold questions to re-label", gold), ("cached answers to evict", cache)):
    hit = sorted(k for k, secs in table.items() if set(secs) & set(changed))
    print(f"{name:28} {len(hit)} of {len(table)}: {hit}")
print("new sections need chunks and new gold questions:", sorted(set(new) - set(old)))
changed sections: ['4.1', '4.2', '7.2'] | unchanged: ['4.3', '7.1']
chunks to re-embed           3 of 5: ['c1', 'c2', 'c5']
gold questions to re-label   2 of 4: ['q-deadline', 'q-threshold']
cached answers to evict      2 of 3: ['a-8812', 'a-9001']
new sections need chunks and new gold questions: ['7.2']
  1. Ingest and diff. Match sections of the new document to the old by id and path, and by text similarity when the numbering changed. Only changed and new sections get new versions. If the match is uncertain, flag it for a human rather than guessing: a mismatched pair of sections silently corrupts history.
  2. Set the effective dates. Read them from the document; if they are not stated, a person enters them. Do not assume "effective on publication".
  3. Re-chunk and re-embed only what changed. Three of five chunks in the example, not all of them. Chunks that merely quote an unchanged section remain valid.
  4. Evict caches that depend on those sections (cached answers, query-result caches). The provenance links make this a lookup.
  5. Re-run the gold set for the questions that touch the changed sections, and mark those whose expected answer changed as needing a new label (human labels). Add new questions for new sections.
  6. Publish to the index atomically (build the new version beside the old, then switch an alias), so a user never sees half an amendment.
  7. Notify the desk and any users who recently asked about the changed sections that their earlier answer may now differ.
  • Things that change without a new version. A regulator publishes guidance that reinterprets an old rule: the text is unchanged but the right answer is not. The only defence is the desk adding a "note" document linked to the section, which then outranks the section for the questions it concerns, and an owner who reads the regulator's feed.
  • Withdrawn documents. Mark status, keep the text for past-dated questions, and make it invisible to present-dated ones.
  • Staleness monitor. Alert when a source feed has been silent longer than usual, or when a document has not been re-checked for its review date. An assistant that is confidently two months out of date is the worst failure in this system.

Common misconception

"We cited our sources, so the answer is grounded." A citation shows where the model says the answer came from. Whether the passage was in force, whether it says what the answer claims, and whether an exception follows are separate questions. A link can sit under a wrong answer and make it more persuasive.

Accountability. Write down who owns each of: the corpus (compliance), the thresholds for escalation (compliance with engineering), the gold set (compliance), the model and gates (engineering), and the decision to expand scope (a named committee). Keep the answer records for as long as the records policy for advice requires. The point of the audit trail is that when an answer is questioned, you can show what was retrieved, what the model said, which gates ran and who approved it.

11Rollout, monitoring and trade-offs

How do you launch without anyone acting on a bad answer? What did you give up? What changes if the assistant must also draft decisions, or the corpus grows tenfold?

State of play, October 2026

Regulators and standards bodies are increasingly explicit about expectations for AI used in regulated work: records of how answers were produced, human oversight and testing. The details vary by country and sector and are changing; ask your legal counsel which rules apply and when, rather than relying on a summary here. Model capabilities (long context, native citation features in some APIs) also change quickly. The architecture on this page, which does not depend on any model's built-in citation feature, is intended to stay valid as they do.

Say your design aloud in five minutes, then compare with the model summary.

Compare with a worked answer

How a senior engineer would summarise this

"This is a low-volume, high-consequence system, so I spend the effort on correctness and on the people who check it. About four and a half thousand questions a day cost under a hundred dollars of model time; the real budget is reviewers, around eight full-time, so the design aims to make each check take thirty seconds. I split questions into three risk tiers: lookups answered directly, rule-plus-facts shown as drafts, and interpretation always routed to a person. The corpus is law-shaped, so I chunk by the document's own numbering, attach definitions, and store every section as an immutable version with effective-from and effective-to dates. That matters because two versions of a section tie on similarity, so I filter by the date the question is about, before ranking. The model returns structured claims with chunk ids and exact quotes, and code checks four things: the chunk was retrieved, the version was in force, the quote is really in the text, and the numbers come from the quote or the question. Anything that fails goes to a reviewer with the passages attached. I measure retrieval at the right version, faithfulness, refusals and acted-on errors, with intervals, because a hundred questions at ninety-six percent could be anywhere from ninety to ninety-eight. Every artefact records the section versions it came from, so when a circular arrives I diff, re-embed only what changed, evict the caches, and re-run the affected questions. Rollout is shadow first, then reviewer-first, then tier-1 direct, with seeded errors to test reviewer fatigue. If it had to draft decisions, I would keep the human decision and the audit trail."

Notice the shape: risk tiers → versions and dates → structured answers → code gates → human handover → change management.

Key takeaways

  • When answers are acted on, the constraint is the cost of a wrong answer and the reviewers who guard against it, not tokens.
  • Store every section as an immutable version with effective dates. Near-identical versions tie on similarity, so filter by the question's date before ranking.
  • The model proposes, code and people dispose: structured claims, exact quotes, and gates for retrieval, version, quote and numbers.
  • Code cannot check that a real quote supports a claim. Use a calibrated judge to prioritise, and people to decide.
  • Abstention is a measured feature. Include unanswerable questions in the gold set and report both kinds of error.
  • Report pass rates with intervals. A hundred questions cannot separate 90% from 98%, and zero failures in 100 still allows a 3% failure rate.
  • Provenance links turn a document change into a lookup: re-embed, evict and re-test only what the change touches.

Lab 1: A Search Engine with BM25

Chapter 1 built an analyser and chapter 2 derived BM25 from three plain intuitions about words. In this lab you assemble them into a working search engine: an analyser, an inverted index, the BM25 scorer, a top-k search that touches only the postings it needs, and an explain function that says why a page ranked where it did. Then you point it at a small help centre and find out where it behaves well, where it can be fooled and what each knob does.

Why this lab matters

BM25 is the baseline every other retriever in this course is measured against, and in hybrid systems it keeps a permanent seat beside embeddings. Lucene, Elasticsearch and OpenSearch all rank this way by default. Reading the formula in chapter 2 is one thing; writing the 60 lines that turn a posting list into a ranked list is what removes the mystery. After this lab "why did this page come first?" is a question you can answer with numbers, "the search is returning nothing for plurals" is a bug you can locate in one function, and "should we change k1?" is an experiment you know how to run. The most common real failures here are not exotic: a query analysed differently from the documents, a repeated word treated as a strong signal, or a long page penalised more than anyone intended. You will meet each of them in the milestones below, caused deliberately and then fixed.

Deterministic, standard library only

There is no network, no clock and no model. The corpus is a 32-page help centre in corpus.json, mixing refunds, health, tenancy law, passports, software errors and a few awkward pages on purpose (one that repeats a word 13 times, one with accents, one that is much longer than the rest). Hand-checked numbers come from the eight-document corpus of chapter 2, so you can compare your output with the chapter's. The property checks use seeded random corpora; a failure prints the seed, and python3 check.py solution 4 3 replays milestone 4 on seed 3 only. Python 3.9 or newer; nothing to install. The whole check runs in well under a second.

What you'll build

Five milestones, each building on the last:

  1. The analyser: fold_accents, tokenise and analyse, so "Café", "cafe" and "CAFÉ" become one term and "refunds" and "refund" meet.
  2. The inverted index: postings with term frequencies, document lengths, document frequencies and the average length, with the edge cases a real index has to survive.
  3. BM25 pieces: idf, tf_norm and score_doc, checked against the numbers in chapter 2.
  4. Top-k search: score by walking the posting lists of the query terms only, keep the best k with a heap, break ties deterministically.
  5. Explain, and scenarios: a per-term breakdown of any score, then rankings on the help-centre corpus that you can defend: saturation, length, rare terms, accents, stemming.

Milestone 1: the analyser

Whatever the ranking formula does later, it can only compare terms that came out of the analyser, so this is where "refund" and "Refunds" either meet or do not. Chapter 1 built this pipeline; here you write it in three small functions.

Case folding
Unicode's operation for caseless matching. str.casefold() maps "Straße" and "STRASSE" to the same string; str.lower() does not.
NFC
One of the Unicode normal forms: it composes "e" plus a combining acute into the single character "é". Without it, the same word typed on two keyboards can be two different strings.
Accent folding
Stripping combining marks after decomposing (NFD), so "café" and "cafe" meet.

tokenise normalises to NFC, case-folds and cuts the text with one regular expression. A token is a run of letters and digits that may contain ., ' or - between letters or digits, so "co-op", "250.50" and "O'Neil" stay whole while "units," loses its comma. A trailing "'s" is dropped. fold_accents decomposes, removes the characters whose Unicode category is Mn (mark, non-spacing) and leaves everything else alone, including "ß". analyse chains them in a fixed order: fold accents, tokenise, drop stop words, stem.

The order matters and the check tests it. Stop words must go before stemming: the crude stemmer turns "this" into "thi", which is no longer on the stop list and would leak into the index.

Solution spoiler 
def fold_accents(text):
    """Strip combining marks: 'café' -> 'cafe', 'Zoë' -> 'Zoe'."""
    decomposed = unicodedata.normalize("NFD", text)          # e-acute -> e + combining acute
    return "".join(c for c in decomposed if unicodedata.category(c) != "Mn")

_TOKEN = re.compile(r"[^\W_]+(?:[.'-][^\W_]+)*")

def tokenise(text):
    """NFC, casefold, cut into tokens that keep internal . ' - and drop a trailing 's."""
    text = unicodedata.normalize("NFC", text).casefold()
    tokens = _TOKEN.findall(text)
    return [t[:-2] if t.endswith("'s") else t for t in tokens]

def analyse(text, fold=True, stop=True, stem=True):
    """text -> list of index terms: fold accents, tokenise, drop stop words, stem."""
    if fold:
        text = fold_accents(text)
    terms = tokenise(text)
    if stop:
        terms = [t for t in terms if t not in STOP]
    if stem:
        terms = [light_stem(t) for t in terms]
    return terms

Milestone 2: the inverted index

Data Systems chapter 17 showed an inverted index as a map from each term to the documents containing it. Ranking needs a little more, as chapter 2 listed: for each term, its posting list (the documents that contain it, each with the term's frequency tf there), and the corpus statistics: how many documents contain it (document frequency, df), each document's length in terms, and the average length avgdl.

The starter gives you the container. postings is a dict from term to a dict of document id to tf, and doc_len maps a document id to its length after analysis. You write add, df, posting_list and avg_doc_len. A real engine stores postings as compressed, sorted arrays (chapter 2 showed delta gaps), but the interface is the same, and returning the posting list sorted by document id is what keeps merges and compression possible.

Three edge cases come with every index and each is tested. A document that analyses to nothing ("the of and") is still a document: length 0, and it counts in avgdl, because the average is over the collection and not over the lucky pages. Adding a document id twice must raise ValueError without half-updating the index (check before you record anything). And an empty index has an average length of 0.0, not a crash.

Solution spoiler 
class Index:
    def __init__(self, analyser=analyse):
        self.analyser = analyser
        self.postings = {}        # term -> {doc_id: tf}
        self.doc_len = {}         # doc_id -> number of terms after analysis

    @property
    def n_docs(self):
        return len(self.doc_len)

    def add(self, doc_id, text):
        """Analyse `text` and record its terms. Duplicate doc ids are an error."""
        if doc_id in self.doc_len:
            raise ValueError(f"document {doc_id!r} is already indexed")
        terms = self.analyser(text)
        self.doc_len[doc_id] = len(terms)          # a document of only stop words still counts
        for t in terms:
            by_doc = self.postings.setdefault(t, {})
            by_doc[doc_id] = by_doc.get(doc_id, 0) + 1

    def df(self, term):
        """Number of documents containing `term` (0 if unseen)."""
        return len(self.postings.get(term, ()))

    def posting_list(self, term):
        """[(doc_id, tf), ...] sorted by doc_id; [] for an unseen term."""
        return sorted(self.postings.get(term, {}).items())

    def avg_doc_len(self):
        """Mean document length over all indexed documents (0.0 for an empty index)."""
        if not self.doc_len:
            return 0.0
        return sum(self.doc_len.values()) / len(self.doc_len)

    def tf(self, term, doc_id):
        return self.postings.get(term, {}).get(doc_id, 0)

Milestone 3: IDF, saturation and length normalisation

Now the formula. For a query with distinct terms t, BM25 scores a document d as

score(q, d) = ∑t in q idf(t) × tfnorm(t, d)

with the two factors you derived in chapter 2:

idf(t) = ln(1 + (N − df + 0.5) / (df + 0.5))

tfnorm = tf × (k1 + 1) / (tf + k1 × (1 − b + b × |d| / avgdl))

Three intuitions live in these two lines. A rare term says more than a common one (idf). Repetition helps with diminishing returns, and the tf component can never exceed k1 + 1 however often a word is repeated (saturation, controlled by k1). A match in a long document is weaker evidence than the same match in a short one (length normalisation, controlled by b). The defaults K1 = 1.2 and B = 0.75 are Lucene's.

The worked example of chapter 2, in your functions: "late" appears in 2 of 8 documents, so idf(8, 2) = ln(1 + 6.5/2.5) = ln 3.6 = 1.281. In document d1 it occurs twice, d1 has 22 terms and the average is 23.875, so tf_norm(2, 22, 23.875) = 2 × 2.2 / (2 + 1.2 × (0.25 + 0.75 × 22/23.875)) = 1.406. The product, 1.801, is d1's contribution from "late"; add "payment" (0.692) and "invoice" (0.716) and d1 scores 3.21.

Write score_doc the slow, obvious way: for one document, loop over the query terms, skip the ones with tf == 0 and add up the products. Milestone 4 will do the same arithmetic faster; having a plain version lets the check (and you) trust the fast one, and explain in milestone 5 reuses its pieces.

Solution spoiler 
def idf(n_docs, df):
    """ln(1 + (N - df + 0.5) / (df + 0.5)): the Lucene form, never negative."""
    return math.log(1 + (n_docs - df + 0.5) / (df + 0.5))

def tf_norm(tf, dl, avgdl, k1=K1, b=B):
    """tf * (k1 + 1) / (tf + k1 * (1 - b + b * dl / avgdl)); 0 when tf is 0."""
    if tf == 0:
        return 0.0
    return tf * (k1 + 1) / (tf + k1 * (1 - b + b * dl / avgdl))

def score_doc(index, terms, doc_id, k1=K1, b=B):
    """BM25 score of one document for a list of distinct query terms."""
    n, avgdl, dl = index.n_docs, index.avg_doc_len(), index.doc_len[doc_id]
    total = 0.0
    for t in terms:
        tf = index.tf(t, doc_id)
        if tf:
            total += idf(n, index.df(t)) * tf_norm(tf, dl, avgdl, k1, b)
    return total

Milestone 4: top-k search, term at a time

Scoring every document for every query would work on 32 pages and be hopeless on 32 million. The reason for building an inverted index is that a query only needs the documents that contain one of its terms, and the index hands you exactly those. The classic strategy is term-at-a-time evaluation: keep a dictionary of accumulators (a running score per document), then for each query term walk its posting list once, computing the term's idf once and adding idf × tf_norm to each listed document's accumulator. When all terms are done, every document that appears has its final score and every document that never appeared correctly has none. The work is proportional to the total length of the query terms' posting lists, not to the size of the collection.

Finally you need the best k. Sorting all accumulators costs m log m for m matching documents; heapq.nsmallest(k, items, key=...) keeps a heap of size k and costs about m log k, which matters when a common term matches most of the collection and you want ten results. Use the key (-score, doc_id): highest score first, and among equal scores the smaller document id first. Without a deterministic tie-break, two pages with the same score swap places between runs, and any evaluation built on the rankings (Lab 2) becomes irreproducible.

Two further rules. Repeated query terms count once (query_terms is given and already removes duplicates; some systems instead treat repetition as extra weight, and this lab does not). And only documents that match at least one term are returned, so a query of unknown words returns [].

Common misconception

"Equal scores are equal." Two documents can be mathematically tied and still differ in the last bits of a floating-point sum if their terms were added in a different order. The check treats scores within 10−9 as equal when comparing with the oracle, and demands the ascending-id order only for scores that are exactly equal (identical documents). In your own systems, do not rely on exact float equality to define a tie: round scores to a stated precision before you break ties, or accept that the order inside a near-tie is arbitrary.

Solution spoiler 
def search(index, query, k=10, k1=K1, b=B):
    """[(doc_id, score), ...], best first; ties broken by doc_id; only matching documents."""
    n, avgdl = index.n_docs, index.avg_doc_len()
    acc = {}                                           # doc_id -> partial score
    for t in query_terms(index, query):
        postings = index.posting_list(t)
        if not postings:
            continue
        w = idf(n, len(postings))                      # one idf per term, not per document
        for doc_id, tf in postings:
            acc[doc_id] = acc.get(doc_id, 0.0) + w * tf_norm(tf, index.doc_len[doc_id], avgdl, k1, b)
    return heapq.nsmallest(k, acc.items(), key=lambda kv: (-kv[1], kv[0]))

Milestone 5: explain, and rankings you can defend

A ranking that cannot be explained cannot be debugged. explain(index, query, doc_id) returns one row per query term that the document contains, with its tf, df, idf, tf_norm and contribution, biggest first. The rows must sum to the document's score. It is the same arithmetic as search, written to show its working: this is how you answer "why did that page win?" in a support ticket, and every search engine worth using has an equivalent (Elasticsearch has an explain API, and Lucene prints a similar tree).

Then the check runs scenarios on the help centre and asserts what a good ranking looks like. Each one matches a lesson from the chapters:

  • Saturation. Page kb03 repeats "refund" 13 times and says nothing else. Its tf component stays below k1 + 1 = 2.2, so for "refund damaged photo" the real answer, kb02, wins. With k1 = 0 term frequency is ignored altogether, every page containing "refund" scores the same, and the ties fall to document id.
  • Length. The long terms-and-conditions page kb32 mentions "refund" once. It scores less as b rises from 0 to 1.
  • Rare beats common. For "payment passport", the passport page wins because "passport" occurs in one page and "payment" in six, and explain shows "passport" as its largest term.
  • Accents and case. "cafe", "café", "resume" and "RÉSUMÉ" all find the right page.
  • Stop words. A query of only stop words has no terms and returns nothing, which is honest. (Chapter 1 discusses why that is sometimes the wrong product decision.)
  • Index and query agree. With stemming the query "refunds" matches five pages; with an index built without stemming it matches one.

def explain(index, query, doc_id, k1=K1, b=B):
    """Per-term breakdown of a document's score, biggest contribution first.

    Each entry: {"term", "tf", "df", "idf", "tf_norm", "score"}. Terms the document
    does not contain are left out, so the entries sum to the document's score.
    """
    n, avgdl, dl = index.n_docs, index.avg_doc_len(), index.doc_len[doc_id]
    rows = []
    for t in query_terms(index, query):
        tf = index.tf(t, doc_id)
        if not tf:
            continue
        w, comp = idf(n, index.df(t)), tf_norm(tf, dl, avgdl, k1, b)
        rows.append({"term": t, "tf": tf, "df": index.df(t), "idf": w, "tf_norm": comp, "score": w * comp})
    rows.sort(key=lambda r: (-r["score"], r["term"]))
    return rows

  • Fields. Give each page a title and a body, index them separately and score a weighted sum (the idea behind BM25F). Which field should be allowed a larger b? Short fields such as titles have little length to normalise.
  • Skip the loser documents. Dynamic pruning algorithms (WAND, from Broder et al., 2003, and MaxScore) avoid scoring documents that cannot reach the current top k, using a per-term upper bound on the contribution. For BM25 the bound is idf × (k1 + 1), which you already know from milestone 3.
  • Break the analyser on purpose. Index the corpus with analyse(t, stem=False) and query with the default analyser (build the Index with one and call query_terms with another). How many of your own test queries now return nothing?
  • Tune it. Grid-search k1 and b on a set of judged queries with the harness from Lab 2, with a confidence interval on the gain. Chapter 2's advice stands: with small judged sets, most differences are noise.
  • Shard it. Split the corpus over three indexes, search each and merge. Do the idf values agree? Chapter 2 explains why they usually do not, and what engines do about it.

What to take away

  • A search engine is an analyser, an index and a scoring loop. Everything the user experiences about matching is decided before BM25 runs, in the analyser, and the query must pass through exactly the same one.
  • BM25 is idf times a saturating, length-normalised tf. k1 sets how fast repetition stops mattering (the ceiling is k1 + 1) and b sets how much length is punished.
  • Term-at-a-time evaluation costs the length of the query terms' posting lists, not the size of the collection, and a heap of size k makes the top-k cheap.
  • Make rankings reproducible: deterministic tie-breaks, a fixed analyser, and an explain function you can run on any surprising result.

Check your understanding

You index a help centre with stemming on, but a deployment bug builds the query analyser without stemming. A user searches for "refunds". What happens?

  1. Nothing visible: BM25 is robust to small analyser differences
  2. The query looks for the unstemmed term "refunds", which the index does not contain, so only pages that were stored under that exact string can match and recall collapses
  3. Every page is returned with the same score
  4. The index raises an error at query time
The index holds stems ("refund"); the query asks for "refunds". The lookup finds no posting list and the ranking function never gets a chance. Nothing errors, which is what makes this bug dangerous. Option 1 is the tempting one: BM25 sees only terms, so an analyser mismatch is invisible to it.

With k1 = 1.2, a page repeats a query term 50 times in an average-length document. Roughly how much more tf component does it earn than a page that mentions it once?

  1. About 50 times as much
  2. About 7 times as much
  3. About 2 times as much
  4. No more: it earns exactly the same
For an average-length document the tf component is tf × 2.2 / (tf + 1.2). At tf = 1 it is 1.0; at tf = 50 it is 110 / 51.2 = 2.15, and it can never exceed 2.2. So 50 repetitions buy about twice the score of one mention. Option 4 would be true for k1 = 0, not 1.2.

A collection has 1,000,000 documents. Term A is in 10 of them; term B is in 100,000. Using the idf of this lab, the weight of A is about how many times the weight of B?

  1. 5 times (about 11.5 against 2.3)
  2. 10,000 times
  3. 1.5 times
  4. The same: both are rare enough
idf = ln(1 + (N − df + 0.5) / (df + 0.5)). For df = 10 that is ln(95,239) ≈ 11.46; for df = 100,000 it is ln(10) ≈ 2.30. The ratio is about 5: idf is logarithmic, so a ten-thousand-fold difference in df makes a much smaller difference in weight. Option 2 treats idf as linear in 1/df.

Why does search walk posting lists instead of calling score_doc on every document?

  1. It gives different scores that are more accurate
  2. Python cannot loop over the documents quickly enough
  3. Because ties would otherwise be broken wrongly
  4. The cost becomes proportional to the postings of the query's terms, and documents that share no term with the query are never touched
The two give the same scores (the check proves it against an oracle). The point of the inverted index is that a query with a few rare terms touches a few postings even if the collection holds millions of documents. Tie-breaking is a separate rule applied in both versions.

A long terms-and-conditions page mentions "refund" once and ranks above short, on-topic pages. Which change is most likely to fix it without touching the analyser?

  1. Set k1 to 0
  2. Raise b towards 1 so that length is penalised more
  3. Set b to 0
  4. Use ln(N/df) instead of the Lucene idf
Length normalisation is controlled by b; raising it makes a match in a long document count for less (in the demo, kb32 falls from first to out of the top four). Setting b = 0 turns length normalisation off, which is the opposite. k1 = 0 ignores term frequency but leaves length alone for a single match, and changing the idf form changes weights for rare and common terms, not the long-page effect.

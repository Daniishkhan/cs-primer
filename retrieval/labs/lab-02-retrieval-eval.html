Lab 2: A Retrieval Evaluation Harness

Chapter 4 defined the metrics and chapter 5 said how to build the judgements. This lab turns both into a tool: read judgements and system runs in the standard text formats, compute precision, recall, reciprocal rank, average precision and nDCG per query, average them, and then do the part most dashboards skip, putting an error bar on the result and deciding whether one system really beats another. You finish with a harness that can say "hybrid is better than BM25 by 0.095 nDCG@10, 95% interval 0.042 to 0.150" and, just as usefully, "these two are not distinguishable".

Why this lab matters

Every claim about a retriever in the rest of this course ("hybrid helps", "the reranker is worth its latency", "this chunk size is better") is a claim about a difference between two numbers computed on a finite set of queries. A change that looks like an improvement on a Friday afternoon is, much of the time, noise: with 50 queries the standard error of a mean nDCG is typically 0.03 to 0.05, as chapter 4 noted. The mistakes that follow are expensive: a team ships a slower pipeline for a gain that was never there, or discards a real gain because the first ten queries looked flat. Writing the harness once also forces the small decisions that make numbers comparable between people: how ties are broken, what an unjudged document counts as, what to do with a query that has no relevant document. The statistics here are the retrieval-sized version of Evals chapter 4.

A synthetic collection, deterministic and standard library only

The judgements and runs are files in the lab folder, written by make_data.py from a fixed seed: 60 queries, 40 candidate documents each, graded judgements from 0 to 3 for 30 of them (the rest are unjudged, as in a real pooled collection), and three systems that each return their top 20. The systems are simulated: "hybrid" is built to be somewhat stronger than "bm25", and "bm25-tuned" to be almost the same as "bm25". Nothing here measures a real retriever, so do not carry the numbers anywhere; the shapes (how wide the intervals are, which differences survive) are the lesson. The hand-checked values come from chapter 4's running example. The only randomness is the seeded bootstrap and permutation sampling. Python 3.9 or newer; no packages. The whole check runs in under a second.

What you'll build

Six milestones, from warm-up to the real thing:

  1. Files to data: parse TREC-style qrels and run files into dictionaries, ordering each run by score, and look up the grade of every ranked document.
  2. Binary metrics: precision and recall at k, hit rate, reciprocal rank and average precision.
  3. Graded metrics: DCG and nDCG with linear or exponential gain.
  4. Whole runs: one score per query, macro means, and the rules for missing and unanswerable queries.
  5. A bootstrap interval: an error bar on a mean, from nothing but resampling.
  6. A paired comparison: the per-query differences between two systems, their bootstrap interval, a sign-flip permutation test, and a verdict.

Milestone 1: files to data

Evaluation tools exchange two plain-text formats that go back to the TREC evaluations. A qrels file (query relevance judgements) has one line per judged pair: query id, an unused "iteration" column that is always 0, document id, grade. A run file has one line per returned document: query id, the literal Q0, document id, rank, score and a tag naming the system. Here are the first lines of each:

q01 0 d0102 0
q01 0 d0104 0
q01 0 d0105 0
q01 0 d0106 0
q01 Q0 d0101 8 6.0 hybrid
q01 Q0 d0122 7 6.1 hybrid
q01 Q0 d0105 10 5.6 hybrid
q01 Q0 d0131 13 5.5 hybrid

Note that the run lines are not in rank order. A run file is untrusted input, produced by someone else's code, and the rank column is the least reliable thing in it. Your parser must order each query's documents by score, descending, break ties by document id, ascending, and ignore the rank column. Evaluation tools differ in how they break ties, which is one reason numbers from two toolkits can disagree in the third decimal; whatever your rule is, state it and keep it fixed. If a document is listed twice for the same query, count it once at its best score, so a run cannot score extra by repeating a lucky result.

grades_for(ranking, qrel) then turns a ranked list of ids into a list of grades. A document that is not in the query's judgements is unjudged, and the standard convention, which chapter 4 warned about, is that it counts as 0. Note the difference between a document judged 0 and one never judged: they score identically here, but a system that returns many unjudged documents is being measured on borrowed time, and in the closing section you will count how many of each system's results are judged.

def parse_qrels(text):
    """'qid iteration docid grade' lines -> {qid: {docid: grade}}."""
    qrels = {}
    for n, line in enumerate(text.splitlines(), 1):
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        parts = line.split()
        if len(parts) != 4:
            raise ValueError(f"qrels line {n}: expected 4 fields, got {len(parts)}: {line!r}")
        qid, _, docid, grade = parts
        qrels.setdefault(qid, {})[docid] = int(grade)
    return qrels

def parse_run(text):
    """'qid Q0 docid rank score tag' lines -> {qid: [docid, ...]} best first.

    The rank column is ignored: documents are ordered by score (descending), ties by
    docid (ascending). A document listed twice for one query counts once, at its best score.
    """
    scored = {}
    for n, line in enumerate(text.splitlines(), 1):
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        parts = line.split()
        if len(parts) != 6:
            raise ValueError(f"run line {n}: expected 6 fields, got {len(parts)}: {line!r}")
        qid, _, docid, _, score, _ = parts
        best = scored.setdefault(qid, {})
        best[docid] = max(float(score), best.get(docid, float("-inf")))
    return {qid: [d for d, _ in sorted(docs.items(), key=lambda kv: (-kv[1], kv[0]))]
            for qid, docs in scored.items()}

def grades_for(ranking, qrel):
    """Grade of each ranked document; unjudged documents count as 0."""
    return [qrel.get(d, 0) for d in ranking]

Milestone 2: binary metrics

All the metrics in this lab take a list of grades, one per rank, exactly as chapter 4's listing did, so you can compare line by line. A result is relevant if its grade is at least a threshold thr, by default 1. Chapter 4's running example is the grades [3, 0, 2, 0, 0, 1, 0, 2, 0, 0] at ranks 1 to 10, with two more judged-relevant documents (grades 2 and 1) that the system never returned, so six documents are relevant in all. The hand values to reproduce:

MetricDefinitionValue on the example
P@krelevant in the first k, divided by k1.00 at k = 1, 0.67 at 3, 0.40 at 5 and at 10
R@krelevant in the first k, divided by all relevant0.17, 0.33, 0.33, 0.67 at the same cut-offs
Hit rate@k1 if any of the first k is relevant1 at every k shown
RR1 / rank of the first relevant result1.0
APmean of precision at each relevant rank, over all relevant documents(1 + 2/3 + 3/6 + 4/8) / 6 = 0.444

Three details are where implementations drift apart, and each is a check. Precision divides by k even when the system returned fewer than k results: a system that returns 3 documents, all relevant, has P@10 = 0.3, not 1.0. Average precision divides by the number of relevant documents that exist, not the number retrieved, so the relevant documents the system never found count as zeros: [1, 0, 1] with 4 relevant documents has AP = (1 + 2/3) / 4 = 0.417. And a query with no relevant documents has no sensible recall or AP; the metric functions return 0.0 rather than crash, and milestone 4 makes sure they are never averaged in.

def precision_at_k(grades, k, thr=1):
    """Relevant results in the first k, divided by k (even if fewer than k were returned)."""
    if k <= 0:
        raise ValueError("k must be positive")
    return sum(g >= thr for g in grades[:k]) / k

def recall_at_k(grades, k, n_relevant, thr=1):
    """Relevant results in the first k, divided by the number of relevant documents."""
    if n_relevant == 0:
        return 0.0
    return sum(g >= thr for g in grades[:k]) / n_relevant

def hit_rate_at_k(grades, k, thr=1):
    """1.0 if any of the first k is relevant, else 0.0."""
    return 1.0 if any(g >= thr for g in grades[:k]) else 0.0

def reciprocal_rank(grades, thr=1):
    """1 / rank of the first relevant result, 0.0 if there is none."""
    for i, g in enumerate(grades, 1):
        if g >= thr:
            return 1.0 / i
    return 0.0

def average_precision(grades, n_relevant, thr=1):
    """Mean of the precision at each relevant rank, over ALL relevant documents."""
    if n_relevant == 0:
        return 0.0
    hits, total = 0, 0.0
    for i, g in enumerate(grades, 1):
        if g >= thr:
            hits += 1
            total += hits / i
    return total / n_relevant          # relevant documents never retrieved add zeros

Milestone 3: graded metrics

Binary metrics throw away the difference between a page that mentions the topic and one that answers the question. Discounted cumulative gain keeps it: each result contributes its gain, divided by a discount that grows with rank,

DCG@k = ∑i=1k gain(gi) / log2(i + 1)

where the gain is the grade itself (linear gain, the original definition) or 2g − 1 (exponential gain, which makes a grade 3 worth seven grade-1 results rather than three). The discount is 1 at rank 1, 1.585 at rank 2, 2 at rank 3. Because DCG grows with the number of good documents, nDCG divides by the best DCG achievable for that query, the ideal DCG, computed by sorting the grades of all judged documents (retrieved or not) from highest to lowest and scoring that order at the same cut-off. A perfect ordering scores 1; a list with nothing relevant scores 0.

Chapter 4's numbers to reproduce: DCG@10 = 4.987, ideal DCG@10 = 6.866, so nDCG@10 = 0.726; nDCG@3 = 0.760; swapping the grade-2 document up from rank 3 to rank 2 lifts nDCG@10 to 0.764. And the pair that shows why the gain form must be stated: ranking X (one perfect result first) against Y (three good results first) over the judged pool [3, 2, 2, 2] gives 0.490 against 0.696 with linear gain, but 0.599 against 0.547 with exponential gain. The "better" system flips with the gain function, so nDCG without its gain function is not a number you can compare.

The ideal list must come from all_grades, not from the retrieved grades. If you sort only what was retrieved, a system that returns one relevant page out of ten that exist gets nDCG 1.0, which is the kind of flattering mistake the check is designed to catch (it asks for ndcg_at_k([1], 3, [1, 1, 1]) to be lower than ndcg_at_k([1], 3, [1])).

def dcg(grades, k, exp_gain=False):
    """sum over ranks i = 1..k of gain(g_i) / log2(i + 1); gain is g, or 2**g - 1."""
    gain = (lambda g: 2 ** g - 1) if exp_gain else (lambda g: g)
    return sum(gain(g) / math.log2(i + 1) for i, g in enumerate(grades[:k], 1))

def ndcg_at_k(grades, k, all_grades, exp_gain=False):
    """DCG@k divided by the DCG@k of the ideal order of ALL judged documents' grades."""
    ideal = dcg(sorted(all_grades, reverse=True), k, exp_gain)
    return dcg(grades, k, exp_gain) / ideal if ideal > 0 else 0.0

Milestone 4: scoring whole runs

One query is an anecdote; a run is a table of them. evaluate_run(run, qrels, metric) returns one score per query, as a dictionary from query id to float. The metric argument is a function of two lists, (grades, all_grades): the grades of the ranked documents and the grades of every judged document for that query. The starter's make_metrics(10) gives you the standard bundle (P@10, R@10, MRR@10, MAP, nDCG@10) built from your milestone 2 and 3 functions, so one loop can score all of them.

The rules, each of which changes the numbers if you get it wrong:

  • Score every query that is in the qrels and has at least one relevant document. A query with none (two of the 60 here) has an undefined recall and a meaningless AP; chapter 4 explains why counting it as zero makes every system look worse by a fixed amount. Leave it out. (In a RAG test set such queries belong in a separate "should abstain" test.)
  • A query in the qrels but missing from the run was answered with nothing: score it on an empty ranking, which is a zero for all of these metrics. Silently dropping it would reward a system for failing to answer.
  • A query in the run but not in the qrels is unjudged and is ignored.
  • The summary is the macro average: the plain mean of the per-query scores, so each query counts equally. mean accepts a list or a dictionary's values and returns 0.0 for an empty one.

def evaluate_run(run, qrels, metric):
    """{qid: score} for every query that has at least one relevant document in qrels.

    `metric(grades, all_grades)` scores one query. A query missing from the run is scored
    on an empty ranking (all zeros). Queries with no relevant document are left out.
    """
    scores = {}
    for qid, qrel in qrels.items():
        all_grades = list(qrel.values())
        if n_rel(all_grades) == 0:
            continue
        scores[qid] = metric(grades_for(run.get(qid, []), qrel), all_grades)
    return scores

def mean(values):
    """Arithmetic mean of a list or dict's values; 0.0 if empty."""
    vals = list(values.values()) if isinstance(values, dict) else list(values)
    return sum(vals) / len(vals) if vals else 0.0

Milestone 5: an error bar from resampling

The macro mean of nDCG@10 for BM25 on these 58 queries is 0.615. If someone gave you a different 58 queries from the same population, you would get a different mean. The question is how different. The bootstrap (Efron, 1979) answers it with a trick: treat the 58 scores you have as the best available picture of the population, and simulate "a different 58 queries" by drawing 58 scores with replacement from them. Compute the mean of that resample; repeat a couple of thousand times. The spread of those resampled means estimates how much the mean would move from sample to sample. The 2.5th and 97.5th percentiles of the resampled means form a 95% percentile interval.

Three practical points. The unit of resampling is the query: the queries are the independent draws, while the documents inside one query's results are not independent of each other, so you resample the list of per-query scores and never the individual documents. A seed makes the interval reproducible: the same data and seed always give the same bounds, which is what you want in a report. And a sanity check you can run on any bootstrap: for a mean of n values with standard deviation s, the interval is close to mean ± 1.96 × s/√n, the formula behind the sample-size table in chapter 5. The check tests exactly that, and also that a smaller sample gives a clearly wider interval.

Common misconception

"A 95% interval means there is a 95% chance the true value is inside it." Closer to the truth: if you repeated the whole experiment many times and built an interval each time, about 95% of those intervals would contain the true value. The check measures this directly: it draws 200 fresh samples of 30 values from a distribution whose mean is known to be 0 and counts how often your interval contains 0. You should see about 92 to 95%. It is slightly below 95% because a percentile bootstrap is a little too narrow for small samples, which is one reason to treat intervals from fewer than about 30 queries with extra suspicion.

Solution spoiler 
def bootstrap_ci(values, n_boot=2000, alpha=0.05, seed=0):
    """Percentile bootstrap interval for the mean: (low, high).

    Resample `values` with replacement n_boot times (same size), take each resample's mean,
    sort, and return the alpha/2 and 1 - alpha/2 quantiles.
    """
    values = list(values)
    if not values:
        raise ValueError("bootstrap_ci needs at least one value")
    rng = random.Random(seed)
    n = len(values)
    means = sorted(sum(rng.choices(values, k=n)) / n for _ in range(n_boot))
    lo = means[int(alpha / 2 * n_boot)]
    hi = means[int((1 - alpha / 2) * n_boot) - 1]
    return lo, hi

Milestone 6: comparing two systems

The question that matters is rarely "how good is system A?" but "is B better than A?". Two systems evaluated on the same queries should be compared pairwise. Some queries are hard for everyone and some easy for everyone, and that query-to-query variation is large: in the closing demo the per-query nDCG@10 of BM25 has a standard deviation of 0.26. But the difference between two systems on the same query is smaller (0.21), because most of the difficulty cancels. A paired analysis works on those differences; ignoring the pairing throws the cancellation away and makes the interval needlessly wide.

So the plan is: paired_diffs gives the difference b − a for each query both systems were scored on. bootstrap_ci of those differences is the interval for the mean improvement. And sign_flip_p is a second opinion with a different logic, a paired permutation test: if the two systems were interchangeable, the sign of each query's difference would be a coin flip, so randomly flipping signs should produce totals as extreme as the observed one reasonably often. The p-value is the fraction of sign patterns whose |sum| is at least the observed |sum|. For 12 or fewer queries you can enumerate all 2n patterns exactly (differences [1, 1, 1] give 2/8 = 0.25); beyond that you sample, and report (count + 1)/(draws + 1) so that a Monte Carlo p-value is never exactly zero.

The verdict is deliberately blunt: "B better" if the whole interval is above 0, "A better" if it is entirely below, and otherwise "no clear difference". That last verdict is a finding, not a failure. It says the data cannot separate the systems, and the options are more queries, a bigger real difference, or accepting that the change does not matter.

Systems connection

Comparing two builds of a service by looking at one run each is the same mistake as comparing two retrievers by one mean. Reliability chapter 9 makes the related point that a mean hides the tail of a distribution, and the same habit applies to per-query scores. The paired design here is the retrieval version of running both versions against the same traffic.

Solution spoiler 
def paired_diffs(a, b):
    """(qids, [b - a, ...]) over the queries both dicts score, in sorted qid order."""
    qids = sorted(set(a) & set(b))
    return qids, [b[q] - a[q] for q in qids]

def sign_flip_p(diffs, n_perm=10000, seed=0):
    """Two-sided paired permutation (sign-flip) test p-value for 'the mean difference is 0'.

    Under the null, each paired difference is as likely to be +d as -d. Statistic: |sum|.
    With 12 or fewer differences, enumerate all 2**n sign patterns exactly. Otherwise
    sample n_perm random patterns and return (count + 1) / (n_perm + 1).
    """
    n = len(diffs)
    if n == 0:
        return 1.0
    observed = abs(sum(diffs)) - 1e-12
    if n <= 12:
        hits = sum(abs(sum(s * d for s, d in zip(signs, diffs))) >= observed
                   for signs in itertools.product((1, -1), repeat=n))
        return hits / 2 ** n
    rng = random.Random(seed)
    hits = 0
    for _ in range(n_perm):
        total = sum(d if rng.random() < 0.5 else -d for d in diffs)
        hits += abs(total) >= observed
    return (hits + 1) / (n_perm + 1)

def paired_compare(a, b, n_boot=2000, n_perm=10000, seed=0, alpha=0.05):
    """Compare system B with system A on the queries both were scored on.

    Returns a dict: n, mean_a, mean_b, diff (mean of b - a), ci (bootstrap interval of the
    mean difference), p (sign-flip p-value) and verdict: "B better" or "A better" if the
    interval excludes 0, else "no clear difference".
    """
    qids, diffs = paired_diffs(a, b)
    if not qids:
        raise ValueError("the two systems share no scored queries")
    lo, hi = bootstrap_ci(diffs, n_boot, alpha, seed)
    verdict = "B better" if lo > 0 else "A better" if hi < 0 else "no clear difference"
    return {"n": len(qids), "mean_a": mean([a[q] for q in qids]), "mean_b": mean([b[q] for q in qids]),
            "diff": mean(diffs), "ci": (lo, hi), "p": sign_flip_p(diffs, n_perm, seed), "verdict": verdict}

Going further

  • Count the unjudged. For each system, compute the fraction of its top-10 that appears in the qrels at all ("judged@10"). A system with many unjudged results is penalised unfairly, as chapters 4 and 5 explain; if the fractions differ a lot between systems, the comparison is not safe until you judge the holes.
  • Several metrics, one decision. The demo ran five comparisons; at a 5% level, about one in twenty comparisons will look significant by chance even if there is no difference. Add a Holm or Bonferroni correction to the p-values, or better, name one primary metric in advance and treat the rest as diagnostics.
  • Change the data. Edit the simulation in make_data.py to weaken "hybrid" (a smaller lift) and find how many queries you need before the interval excludes zero. Compare with the rule of thumb in chapter 5: a difference is reliably detectable (80% power) when it exceeds about 2.8 × s/√n.
  • Bring your own engine. Run the BM25 engine from Lab 1 on a judged set, write its ranking in the run format, and compare variants of k1 and b with this harness.
  • Cross-check. If you have trec_eval or pytrec_eval installed, run it on the same files and compare MAP and nDCG. Differences in the third decimal usually come from tie handling or the gain form.
  • Clustered queries. If your test queries come in groups (several phrasings of one question), resampling queries as if independent makes the interval too narrow. Resample the groups instead. Evals chapter 4 covers clustered questions.

What to take away

  • A metric implementation is a set of decisions: ties by document id, unjudged as zero, queries without relevant documents skipped, a missing query scored as zero, precision divided by k, AP divided by all relevant documents, nDCG ideal taken from all judged documents, gain form stated.
  • Keep the per-query scores. The mean is a summary; the intervals and tests are computed from the list.
  • A bootstrap interval comes from resampling queries with replacement and reading the percentiles of the resampled means; it should agree with mean ± 1.96 × s/√n and shrink as 1/√n.
  • Compare systems pairwise on the same queries. "No clear difference" is a legitimate result, and the usual fix is more queries or a larger effect, not a friendlier metric.

Check your understanding

A system returns only 3 results for a query, and all 3 are relevant. What is its P@10?

  1. 1.0, because every result it returned is relevant
  2. 0.7, the share of missing results
  3. 0.3, because precision at k divides by k, not by the number returned
  4. Undefined, because fewer than 10 results were returned
P@k is the number of relevant results in the first k divided by k. Dividing by the number returned would reward a system for returning almost nothing, so the standard definition charges the missing slots as non-relevant. Option 1 is the tempting one and is what a "precision of what I show" reading would give; that quantity has a different name and is not P@10.

Query q9 has 5 relevant documents in the qrels. System A finds 2 of them at ranks 1 and 2 and nothing else relevant. What is its average precision?

  1. 0.4, which is (1 + 1) / 5
  2. 1.0, because both retrieved relevant documents are at the top
  3. 0.5
  4. 0.2
Precision at the two relevant ranks is 1/1 and 2/2; their sum is 2; dividing by all 5 relevant documents gives 0.4, because the three never retrieved count as zeros. Option 2 divides by the number retrieved (2), which forgives the missing documents, and the metric exists to prevent that.

System B's nDCG@10 is 0.71 and system A's is 0.62, over 58 queries. The unpaired 95% intervals of the two means overlap. Which statement is correct?

  1. The systems cannot be distinguished, because the intervals overlap
  2. B is better, because 0.71 is greater than 0.62
  3. B is better only if the p-value of an unpaired test is below 0.05
  4. You must look at the paired per-query differences: overlapping intervals of the means do not decide it, because the paired difference can have a much smaller spread
The two systems are scored on the same queries, so query difficulty is shared and cancels in the difference. The interval for the paired difference is typically much narrower than the intervals around each mean (in this lab: [+0.042, +0.150] while the single-system intervals overlap). Option 1 is the classic misreading; option 2 ignores noise entirely.

You resample 58 per-query scores with replacement 2,000 times to get a bootstrap interval. Which of these changes would make the interval too narrow?

  1. Using 10,000 resamples instead of 2,000
  2. Resampling the individual ranked documents instead of the queries, so that results from one query are treated as independent
  3. Using the 2.5th and 97.5th percentiles instead of the 5th and 95th
  4. Using a different seed
The independent units are the queries. Results within one query are related (they answer the same need), so treating them as independent pretends you have far more data than you do and shrinks the interval. More resamples only reduce Monte Carlo noise in the bounds; the 2.5th and 97.5th percentiles give a wider interval than 5th and 95th, not a narrower one; a seed changes the draw, not the width, on average.

A change improves mean nDCG@10 by 0.03 on 25 queries, with a paired 95% interval of [−0.02, +0.08]. What is the most defensible conclusion?

  1. The change helps by 3 points and should ship
  2. The change does not work
  3. No clear difference yet: the data are compatible with a small loss and with a sizeable gain, so collect more queries before deciding
  4. The metric is broken, because it reports a gain that is not significant
An interval that includes 0 says the sample cannot rule out "no effect", but it equally cannot rule out a gain of 0.08. Absence of evidence is not evidence of absence. Option 1 reads the point estimate as certain; option 2 reads the interval as proof of no effect. Both overclaim. The remedy is more queries (width falls as 1/√n) or a larger change.

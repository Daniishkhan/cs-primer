Lost in the Middle

Context windows grew from a few thousand tokens to a hundred thousand and beyond, and the natural conclusion was that you could now paste in everything the model might need. In 2023 Nelson Liu and colleagues tested that conclusion directly: they held the question and the evidence fixed, moved the evidence around the prompt, and watched accuracy rise and fall with its position. The result, a U-shaped curve with a trough in the middle, changed how RAG systems order and trim what they retrieve.

What I could and could not read

I fetched the paper "Lost in the Middle: How Language Models Use Long Contexts" (Liu, Lin, Hewitt, Paranjape, Bevilacqua, Petroni and Liang; arXiv 2307.03172, version 3 of 20 November 2023, accepted at Transactions of the Association for Computational Linguistics) as a PDF, converted it to text, and read the setup, results, analysis and appendix tables. Every number below comes from that text, and I name the table or figure. I read only the abstract page of a 2024 follow-up (Hsieh et al., "Found in the Middle"). The paper tests models available in mid-2023 (GPT-3.5-Turbo, Claude-1.3, MPT-30B-Instruct, LongChat-13B and others), so it is evidence about a phenomenon, not about any model you use today. The paper reports results as curves; I use the appendix's tabulated points and join them with straight lines. The toy and its assumptions are mine.

The pattern in one sentence

A long context window is capacity to hold text, not a guarantee that the model uses all of it equally, so measure how accuracy changes with where the evidence sits, and send fewer, better-ordered documents.

Context: bigger windows, an unanswered question

In the RAG pipeline of chapter 13, retrieval picks passages and the generator reads them in its prompt; the size of the window decides how many fit. The paper's introduction notes that windows had grown from 512 to 2,048 tokens to 4,096, 32,000 and even 100,000, but that it "remains unclear" how such models use their input. In principle any token is as reachable as any other, since attention (chapter 9 of the deep learning course) can connect any two positions. The authors asked whether the models behave that way.

Context window
The maximum number of tokens a model can process at once.
Multi-document question answering
Answering from a prompt that holds several documents, of which only one contains the answer.
Distractor
A document or item that looks relevant but does not hold the answer.
Closed-book / oracle
Two reference settings: the model sees no documents at all, or only the one document that contains the answer.
Primacy and recency bias
Using information at the start (primacy) or end (recency) of the input better than information between.

The experiments

Multi-document question answering

The first task uses NaturalQuestions-Open, real Google queries with short answers found in Wikipedia. Each prompt contains k documents: one with the answer and k minus 1 distractors, which are passages a retrieval system ranked highly but which do not contain it. Two things are varied while the question stays fixed. To test position, the answer document is moved around the list; reordering does not change the correct answer. To test length, the prompt holds 10, 20 or 30 documents (roughly 2,000, 4,000 and 6,000 tokens, per the paper's figure titles). Accuracy counts a response as right if a gold answer string appears in it. The open models were MPT-30B-Instruct (8,192-token window) and LongChat-13B (16K); the closed ones were GPT-3.5-Turbo (4K, and a 16K version) and Claude-1.3 (8K, and a 100K version). All used greedy decoding.

The reference points

Two baselines frame every result (the paper's Table 1). In the closed-book setting the model gets no documents; in the oracle setting it gets only the answer document. For GPT-3.5-Turbo the paper reports 56.1% closed-book and 88.3% oracle; for Claude-1.3, 48.3% and 76.1%; for MPT-30B-Instruct, 31.5% and 81.9%; for LongChat-13B (16K), 35.0% and 83.4%. A model that used its context perfectly would score near the oracle number whatever the position, and a model that ignored the context would sit near the closed-book number.

The result: a U-shaped curve

The paper's central finding, in its words, is "a distinctive U-shaped performance curve": models are better at using information at the very beginning (primacy) or very end (recency) of the context and do worse when the evidence is in the middle. The numbers in the appendix (Table 6, 20 documents) show how large the effect is for GPT-3.5-Turbo: 75.8% with the answer document first, 53.8% with it tenth, 63.2% with it last. The paper adds that GPT-3.5-Turbo's accuracy "can drop by more than 20%" in the worst case and that, in the 20- and 30-document settings, its worst-case performance is lower than its closed-book score of 56.1%. Giving the model the evidence, in the wrong place, did worse than giving it nothing.

Other findings in the paper, each with its caveat:

  • Longer windows were not better readers. When the prompt fits both a model and its extended-window sibling, the paper found their performance almost identical, for example GPT-3.5-Turbo and its 16K version in the 10- and 20-document settings (Table 6 shows 53.8% and 54.1% at the tenth position).
  • More documents lowered the floor. For GPT-3.5-Turbo (16K), the middle positions in the 30-document setting fall to about 50.5% at the tenth position (Table 7).
  • Plain key-value lookup showed the same thing for some models. In a synthetic task (find the value for a key in a JSON object of random UUIDs, with 75, 140 or 300 pairs), Claude-1.3 and its 100K version did "nearly perfectly" at every length, while other models struggled, especially at 140 and 300 pairs; the weaker ones did worst when the key sat in the middle.
  • Architecture and training. Encoder-decoder models (Flan-T5-XXL, Flan-UL2) were robust to position when the input was within their training length, and developed the U-shape beyond it. The base MPT-30B, before instruction tuning, also showed the U, so instruction tuning was not the cause. In Llama-2 models, the U appeared in the 13B and 70B sizes, while the 7B model was only recency-biased.
  • A cheap fix helped one task and not the other. Putting the query both before and after the documents ("query-aware contextualisation") made key-value retrieval almost perfect (GPT-3.5-Turbo 16K reached perfect accuracy at 300 pairs, and the paper gives 45.6% as the worst case without it) but barely changed multi-document QA.

Is more context better? The open-domain QA case study

The paper then asks the practical question in a RAG setting. A retriever (Contriever fine-tuned on MS MARCO) returns the top k Wikipedia passages for each NaturalQuestions-Open question and the model reads them. The paper's Figure 11 shows that reader accuracy saturates long before retriever recall does: using more than 20 retrieved documents improved the reader by only about 1.5% for GPT-3.5-Turbo and about 1% for Claude-1.3, while sharply raising prompt length, and therefore latency and cost. The authors suggest reranking so relevant evidence sits near the start, or truncating the ranked list, as directions to try (chapter 8 covers rerankers).

A toy you can run

The toy asks a design question the paper's findings raise: if the reader behaves like GPT-3.5-Turbo's measured curve, how much does the order of retrieved documents matter? I interpolate the five points of Table 6 (20 documents) and the three of Table 5 (10 documents). The part that is my assumption is the retriever: the answer document sits at retriever rank r with probability proportional to 0.75r (about a quarter at rank 1). I score five layouts: ranked order, reversed, best documents at the two ends, best in the middle, and only the top ten. Treat the output as arithmetic on an assumed distribution, not as a prediction for any real system; the paper has only one relevant document per question and measured one model family on one dataset.

"""Toy: how much does ordering retrieved documents matter, if the reader behaves like the
GPT-3.5-Turbo curves in Liu et al. (2023), appendix G? The curve points are the paper's;
the retriever's rank distribution is MY illustrative assumption; real readers differ."""
import numpy as np
IDX20 = [0, 4, 9, 14, 19];  ACC20 = [75.8, 57.2, 53.8, 55.4, 63.2]   # Table 6, GPT-3.5-Turbo, 20 documents
IDX10 = [0, 4, 9];          ACC10 = [76.8, 61.2, 62.4]               # Table 5, GPT-3.5-Turbo, 10 documents
CLOSED_BOOK = 56.1
def acc(pos, idx, vals): return float(np.interp(pos, idx, vals))

# Assumption: the answer document sits at retriever rank r with probability proportional to 0.75**r.
p20 = np.array([0.75 ** r for r in range(20)]); p20 /= p20.sum()
print("assumed P(answer doc is the retriever's rank 1) = %.2f" % p20[0])

def expected(order, p, idx, vals):
    """order[r] = position in the prompt of the document with retriever rank r"""
    return sum(p[r] * acc(order[r], idx, vals) for r in range(len(order)))

n = 20
best_first = list(range(n))                          # rank 1 at the start
best_last  = list(range(n - 1, -1, -1))              # rank 1 at the end
ends_first = [None] * n; lo, hi = 0, n - 1           # rank 1 at the start, rank 2 at the end, rank 3 second, ...
for r in range(n):
    if r % 2 == 0: ends_first[r] = lo; lo += 1
    else:          ends_first[r] = hi; hi -= 1
middle_first = [int(x) for x in np.argsort([abs(i - 9.5) for i in range(n)], kind="stable")]  # best docs in the middle
rows = [("best first (ranked order)", best_first), ("best last", best_last),
        ("best at the two ends", ends_first), ("best in the middle (worst case)", middle_first)]
print("\n20 documents in the prompt, expected accuracy (%):")
for name, o in rows: print("  %-34s %.1f" % (name, expected(o, p20, IDX20, ACC20)))
lost = p20[10:].sum()                                  # answer ranked 11 to 20: dropped, so assume closed-book accuracy
top10 = sum(p20[r] * acc(r, IDX10, ACC10) for r in range(10)) + lost * CLOSED_BOOK
print("\nkeep only the top 10, best first: %.1f   (answer dropped with P = %.2f, scored as closed-book)" % (top10, lost))
print("closed-book accuracy in the paper (no documents): %.1f" % CLOSED_BOOK)
assumed P(answer doc is the retriever's rank 1) = 0.25

20 documents in the prompt, expected accuracy (%):
  best first (ranked order)          65.9
  best last                          59.6
  best at the two ends               66.5
  best in the middle (worst case)    54.8

keep only the top 10, best first: 68.7   (answer dropped with P = 0.05, scored as closed-book)
closed-book accuracy in the paper (no documents): 56.1

Reading the output: under this curve, putting the best documents at the two ends is slightly better than the ranked order (66.5 against 65.9), a gap small enough that a different assumed rank distribution could erase it. Reversing the order costs about six points, and deliberately burying the best documents in the middle costs about eleven. Keeping only the top ten, with the answer scored as closed-book accuracy when it falls outside, comes out highest at 68.7, which is the logic of the paper's suggestion to truncate. If your reader is another model, or a newer version, none of these numbers carry over; the method is the point: measure your own reader's curve, then choose the layout.

What the critics and later work said

The paper's own limitations are plain in the text: one decoding method (greedy), one task family built on Wikipedia and NaturalQuestions-Open, and a key-value task the authors call synthetic. The GPT-4 results were only on a subset of experiments because, they say, the full set would have cost upwards of $6,000, and they report "similar results and trends" with higher absolute performance. Later work offered an explanation and remedies. Hsieh et al. (2024), whose abstract I read, link the effect to a U-shaped attention bias, with higher attention on tokens at the start and end regardless of relevance, and propose a calibration method that they report outperforms existing methods by up to 15 percentage points on their RAG tasks. I did not read the full paper or verify that claim.

One thing the paper does not show is that current models fail in the same way. Context-handling has been a target of training since 2023, and any claim about a particular model needs the same style of test run on that model with your data (long context versus retrieval in the agents course shows how).

State of play, October 2026

The measurements are from mid-2023 models and I did not check current ones, so I make no claim that today's models do or do not show a U-shaped curve. The durable point is methodological: position, length and the number of distractors are variables you should test, with the same question and evidence reshuffled. A one-off "needle in a haystack" check with a single planted fact tests only the easy case: in the paper, a model that was near-perfect at exact-match key lookup still showed position effects on the document task.

Common misconception

"Lost in the middle" does not say models cannot use long contexts, or that the middle of a document is always ignored. It says that, for the models and tasks tested, accuracy depended on where the evidence sat, so a context window's size is not the same as the quality of its use. The effect was model-specific (Claude-1.3 varied far less than GPT-3.5-Turbo in Table 6) and task-specific.

The lessons

  • Measure position sensitivity on your reader. Shuffle where the gold passage sits in your prompts and plot accuracy against position, as in chapter 13's pipeline knobs, before adding a rule about ordering.
  • Retrieve more for recall, but send fewer for the reader. Retriever recall kept rising while reader accuracy flattened after about 20 documents in the paper. This is a reason to rerank and truncate (chapters 8 and 10) rather than pass the whole candidate list.
  • Distractors are the point. The failure appears when the prompt contains plausible irrelevant text, which is exactly what real retrieval returns; see how RAG fails.
  • Context costs money and time. Doubling the documents roughly doubles the tokens processed (the KV cache and tail latency chapters explain the bills), so extra context must earn its place.
  • Structure the prompt. Where a task allows it, restate the question after the documents, as the paper's query-aware variant does. It helped only the key-value task, so test it on yours.

Key takeaways

  • Liu et al. (2023) moved one answer document through a fixed prompt and found accuracy highest at the start and end and lowest in the middle, with a swing of over 20 points for GPT-3.5-Turbo.
  • With 20 or 30 documents, the worst-case result was below the closed-book score: wrongly placed evidence can be worse than none.
  • Extended-window models were not better at using their input than their short-window siblings when both fit.
  • Reader accuracy plateaued after about 20 retrieved documents while retriever recall kept growing; reranking and truncation are the suggested responses.
  • These are 2023 models. The method (shuffle position, plot the curve) is what lasts.

In the paper's multi-document QA, what is held constant while the position of the answer document changes?

  1. The model's temperature
  2. The question and the set of documents, so the right answer is unchanged by reordering
  3. The retriever's ranking
  4. The number of correct answers per prompt
Only the position of the answer-bearing document moves. The question, documents and gold answer stay the same, which isolates position as the cause.

GPT-3.5-Turbo scored 56.1% closed-book. In the 20-document setting its worst-case position scored below that. What does this show?

  1. The model cannot read documents
  2. Retrieval is never worth using
  3. The closed-book number was an error
  4. Supplying the evidence in an unfavourable place, among distractors, can do worse than supplying nothing
The model can read documents (it scored 88.3% in the oracle setting). The drop is position and distraction, which is why placement and trimming matter.

A team's retriever has high recall at 50 documents, but their reader's answer accuracy stops improving after about 20. Which response matches the paper's suggestions?

  1. Rerank so the best evidence sits near the start, or truncate the list
  2. Move to a model with a larger window and pass all 50
  3. Add more distractors to test robustness
  4. Retrain the retriever with a larger index
The paper found larger windows did not help when the prompt already fit, and extra documents cost latency. The retriever is not the bottleneck; the reader's use of the context is.

  1. GPT-3.5-Turbo did best with the answer first or last in the 20-document setting
  2. Instruction tuning was not necessary for the U-shape, since the base MPT-30B showed it
  3. Models released today still lose information in the middle by the same amount
  4. Query-aware contextualisation fixed key-value retrieval but not multi-document QA
The other three are findings of the paper. It tested mid-2023 models, so it cannot say how current models behave; that needs a fresh test on the model and data in question.

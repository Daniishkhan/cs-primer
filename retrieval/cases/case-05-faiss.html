FAISS: Billion-Scale Similarity Search

In 2017 three researchers at Facebook AI Research published "Billion-scale similarity search with GPUs" and released the code as FAISS. The paper answers a narrow engineering question: how do you find the nearest neighbours of a vector among a billion others when the vectors do not fit in memory as they are? The answer has two halves, store each vector as a few bytes, and redesign the search so that a GPU can do it. This case reads the paper, checks its arithmetic, and rebuilds the core of the method in about fifty lines.

What I could and could not read

I fetched the arXiv abstract page of the 2017 paper and read the full text of its PDF (version 1, February 2017) after extracting the text locally; every number attributed to "the paper" below comes from that text. I also read the full text of the 2024 follow-up, "The Faiss library" (arXiv version 4, dated 23 October 2025), for what the library became. I did not read the 2011 product quantisation paper by Jégou, Douze and Schmid: its archive page refused automated access, so I describe product quantisation as the 2017 paper summarises it. The NVIDIA cuVS integration in the state-of-play box is known to me only from search-result summaries, not from a page I read. The toy code is mine and the corpus is synthetic, so its numbers illustrate the mechanism and say nothing about FAISS's speed or accuracy.

The pattern in one sentence

When the vectors are too many to keep, keep a lossy code for each one (a coarse cell plus a few bytes), compare the query against the codes with cheap table lookups, and shape the search so that the hardware you have stays busy.

Context: why a billion vectors is a different problem

By 2017 neural networks produced embeddings: vectors of "50 to 1000+ dimensions", in the paper's words, for words, images and videos, many of them computed on GPUs. Searching them means finding the k nearest neighbours (k-NN) of a query vector, the k database vectors at the smallest Euclidean distance. The authors single out one application as "our flagship": building the k-NN graph, a graph in which every vector is a node with edges to its k nearest neighbours. That is a billion queries against a billion vectors, so the cost of one query is multiplied by the size of the database.

The earlier chapter Approximate Nearest-Neighbour Search explains why exact search stops scaling and introduces the inverted file and product quantisation; Specialised Stores in the Data Systems course places vector indexes among other non-relational stores. This case does not repeat those chapters. It asks what the 2017 paper added to ideas that already existed, and why that mattered enough for the code to become the default building block of vector search.

Product quantisation (PQ)
Cut a vector into equal pieces, replace each piece by the id of its nearest entry in a small learned codebook, and store only the ids. With 256 entries per codebook, each piece costs one byte.
Inverted file (IVF)
A partition of the database into lists, one per coarse centroid. A query scans only the few lists whose centroids are nearest to it.
IVFADC
The combination the paper uses: an inverted file whose lists hold PQ codes, searched with asymmetric distance computation.
Asymmetric distance computation (ADC)
Compare the exact, uncompressed query with compressed database vectors. "Asymmetric" because only one side is quantised.
Residual
What is left of a vector after subtracting its coarse centroid. PQ is applied to the residual, which is smaller and more uniform than the vector.
k-selection
Picking the k smallest values (and their positions) out of an array of distances. The paper argues this, not the distance arithmetic, is the part that resists parallelisation on a GPU.
Shard and replica
A shard holds a slice of the database; a replica is an extra copy of the same index that serves a different share of the queries. The paper writes them S and R.

The mechanism: a coarse cell plus a few bytes

The paper builds on the IVFADC structure of Jégou et al. (2011). A database vector y is approximated in two levels:

y ≈ q(y) = q1(y) + q2(y − q1(y))

The first quantiser q1 is a coarse one: k-means with a modest number of centroids, typically about the square root of the database size according to the paper, so that the lists neither explode in number nor grow too long. The second, q2, is a product quantiser applied to the residual y − q1(y). It splits the residual into b pieces, and each piece has its own codebook, "typically 256 reproduction values, to fit in one byte". So the code for one vector is b bytes, and the number of distinct reconstructions is 256b, far more than any single k-means could store. Each inverted list holds the vector ids (4 or 8 bytes) next to their codes. The 512-byte vector is not kept.

The mechanism: searching codes with lookup tables

At query time the exact query x picks the τ nearest coarse centroids (the paper's multi-probe parameter) and scans only those inverted lists. For each probed list the distance from x to a stored vector is the sum, over the b pieces, of the distance between the query's piece and the codebook entry the code names. Because each codebook has only 256 entries, those distances can be computed once per list into b tables of 256 numbers, and then each stored vector costs b table lookups and additions. The paper counts the saving directly: computing n distances explicitly takes n × d multiply-adds, while with lookup tables it takes 256 × d multiply-adds (to build the tables) plus n × b lookup-adds. With d = 128 and b = 8, tables pay for themselves after about 270 vectors (my arithmetic: 256 × 128 ÷ (128 − 8)); at a million vectors the explicit route needs 128 million multiply-adds, the table route about 33 thousand multiply-adds plus 8 million lookup-adds.

Two sources of error are now stacked. Probing too few lists can miss the true neighbour because it sits in an unprobed cell. And the code itself is lossy, so the ranking inside the scanned lists is approximate even when the right list is probed. The toy below separates them. It is mine: it trains the two quantisers with a small k-means on synthetic clustered vectors, searches with τ = 1 to 16 lists and, for comparison, all 128 lists, and counts the work.

"""IVFADC in NumPy: coarse quantiser + product quantiser on the residual (the structure in Johnson et al., 2017).
Synthetic clustered vectors stand in for real embeddings; operation counts are my own bookkeeping."""
import numpy as np
rng = np.random.default_rng(0)
N, D, NQ, K = 20000, 32, 100, 10
centres = rng.normal(size=(60, D))
X = (centres[rng.integers(0, 60, N)] + 0.9 * rng.normal(size=(N, D))).astype(np.float32)
Q = (X[rng.choice(N, NQ, replace=False)] + 0.30 * rng.normal(size=(NQ, D))).astype(np.float32)

def kmeans(A, k, iters=12, seed=0):
    C = A[np.random.default_rng(seed).choice(len(A), k, replace=False)].copy()
    for _ in range(iters):
        a = np.argmin((C * C).sum(1)[None] - 2 * A @ C.T, axis=1)
        for j in range(k):
            if (a == j).any(): C[j] = A[a == j].mean(0)
    return C, np.argmin((C * C).sum(1)[None] - 2 * A @ C.T, axis=1)

def pq_train(R, m):
    ds = D // m
    return [kmeans(R[:, i*ds:(i+1)*ds], 256, seed=i)[0] for i in range(m)]
def pq_encode(R, books):
    ds = D // len(books)
    return np.stack([np.argmin((B*B).sum(1)[None] - 2 * R[:, i*ds:(i+1)*ds] @ B.T, axis=1)
                     for i, B in enumerate(books)], axis=1).astype(np.uint8)
def adc(r, codes, books):                       # one 256-entry table per sub-quantiser, then lookups
    ds = D // len(books)
    T = np.stack([((books[i] - r[i*ds:(i+1)*ds]) ** 2).sum(1) for i in range(len(books))])
    return T[np.arange(len(books)), codes].sum(1)

truth = np.argsort(((Q[:, None] - X[None]) ** 2).sum(2), axis=1)[:, :K]
NLIST, M = 128, 8
C1, assign = kmeans(X, NLIST)                   # q1: coarse quantiser
books = pq_train(X - C1[assign], M)             # q2: PQ trained on residuals y - q1(y)
codes = pq_encode(X - C1[assign], books)
lists = [np.where(assign == c)[0] for c in range(NLIST)]

def search(q, nprobe):
    near = np.argsort(((C1 - q) ** 2).sum(1))[:nprobe]
    ids, dist = [], []
    for c in near:
        ids.append(lists[c]); dist.append(adc(q - C1[c], codes[lists[c]], books))
    ids, dist = np.concatenate(ids), np.concatenate(dist)
    return ids[np.argsort(dist)[:K]], len(ids)

print(f"flat float32: {D*4} bytes/vector, {N*D:,} multiply-adds per query")
print(f"IVFADC: {M} bytes/vector + 4-byte id, {D*4/M:.0f}x smaller codes")
print(f"{'nprobe':>6} {'scanned':>8} {'lookups':>8} {'table mult-adds':>16} {'R@1':>5} {'overlap@10':>10}")
for nprobe in (1, 2, 4, 8, 16, 128):
    hits1, hitsK, scanned = 0, 0, 0
    for q, t in zip(Q, truth):
        got, n = search(q, nprobe); scanned += n
        hits1 += got[0] == t[0]; hitsK += len(set(got) & set(t))
    s = scanned / NQ
    print(f"{nprobe:>6} {s:>8.0f} {s*M:>8.0f} {nprobe*256*D + NLIST*D:>16,} {hits1/NQ:>5.2f} {hitsK/(NQ*K):>10.2f}")

Read the output in two parts. First, the list count and the code size are different dials. Going from one probed list to four raises the overlap with the true top ten from 0.58 to 0.69, and further probing barely moves it: with all 128 lists scanned the overlap is only 0.70. That ceiling comes from the 8-byte code, not from the search. I ran the same script with M = 16 (16 bytes per vector) and the ceiling rose to 0.90, with the same shape: 0.67 at one list, 0.89 at four, 0.90 at all 128. Second, the top-1 result was already the true nearest neighbour for 98 to 100 per cent of queries even at one list, which is why the paper reports R@1 style numbers for some comparisons and why a system that only needs the single best match can use far smaller codes than one that needs a faithful top ten. The last row also shows why tables are built per probed list: my naive table counter exceeds the flat scan's 640,000 multiply-adds when every list is probed. The paper reduces this cost by splitting the distance into three terms: one that does not depend on the query and can be precomputed from the quantisers, one that is a by-product of the coarse search, and one that does not depend on the list and costs 256 × d multiply-adds once per query. It enables that decomposition on the GPU only when the extra table memory is not a concern. My toy does none of this.

The mechanism: why the GPU needed a new k-selection

The distance arithmetic is the easy part to put on a GPU: exact search reduces to a large matrix multiplication, and the paper notes the identity ∥x − y∥2 = ∥x∥2 + ∥y∥2 − 2⟨x, y⟩ so that the heavy term is a matrix product. The trouble is k-selection: after computing the distances for a batch of queries you must keep only the k smallest per query. The authors write that prior approaches "are bottlenecked by algorithms that expose less parallelism, such as k-min selection, or make poor use of the memory hierarchy". Sorting every row of distances is too slow (the paper measures the naive full sort at more than 10 times slower than the comparison methods in its exact-search test), and standard selection algorithms make multiple passes over distances in global memory.

The paper's answer, WarpSelect, keeps its state in the GPU's register file, the fastest and largest memory on the chip (the paper gives 14 MB on the Pascal P100, against a few tens of kilobytes on a CPU). A warp is a group of 32 GPU threads that execute together. Each of the 32 lanes keeps a short sorted "thread queue" in its own registers (the paper uses lengths from 2 to 8 depending on k), and a longer sorted "warp queue" of length k is spread across the lanes. Each incoming group of 32 distances is compared with the heads of the thread queues, which is one cheap operation; only if some value is better than the worst entry of the warp queue are the queues sorted and merged with sorting networks. The paper's cost analysis shows that on random data the expensive merge happens rarely. WarpSelect needs no shared memory and no synchronisation between warps, and, because its state lives in registers, it can be fused into the same kernel that computes the distances. I am describing the idea in outline; the paper gives the algorithm and a complexity analysis in its section 4 and appendix.

What the authors report for it, on one Maxwell Titan X GPU with 10,000 query rows: against the best k-selection code they compared with (from the fgknn library), WarpSelect is 1.62 times faster at k = 100 and 2.01 times at k = 1000 for arrays of 128,000 values, and runs at 55 per cent of the peak possible memory-bandwidth performance at k = 100 but only 16 per cent at k = 1000, "due to additional overhead associated with bigger thread queues and merge/sort networks for large k". That last clause is a useful reminder: the design is tuned for the small k that nearest-neighbour search wants. Note also that in the abstract "55%" and "8.5×" describe two different things (the first is k-selection efficiency, the second the end-to-end speed-up over prior GPU art on one benchmark), a conflation that is easy to make when quoting the paper.

The three memory figures reproduce the paper's statements (384 GB, 20 GB and 80 GB), which supports reading them as they were intended: the raw vectors of Deep1B need 384 GB, more than any GPU of the time, while the compressed codes need about 20 GB and so fit across the memory of a few GPUs. That is the point of the whole design. Compression is not a nicety; it is what lets the data live on the fast hardware at all. The per-query times imply about 56,000 and 75,000 queries a second, and a billion queries in four to five hours of pure search time, which is consistent with the paper's 6-hour lower-quality graph once index building and the second-level structure are added. That last step is my inference, not a figure the paper gives.

What happened next, and what the later work says

The same group's 2024 paper "The Faiss library" gives the later history. It reports that FAISS, open-sourced in 2017, has "37k GitHub stars", that the GPU paper has "more than 5200 citations", and that the packages "have been downloaded 6M times"; it says major vector database companies "either rely on Faiss as their core engine or have reimplemented Faiss algorithms", naming Zilliz (whose Milvus uses FAISS through its Knowhere library) and Pinecone, which "initially relied on Faiss, although the engine was later rewritten in Rust". Those are the authors' statements about their own project, with counts from the time of writing.

The same paper also shows what the 2017 design grew into. The library offers many index types beyond IVFADC, including HNSW graphs, which the 2024 paper calls "currently the most popular indexing method" for medium-sized datasets. It describes a trillion-scale example that indexes 1.5 trillion 144-dimensional vectors, compressed to 54 bytes each by PCA to 72 dimensions and a 6-bit scalar quantiser, using an HNSW coarse quantiser with 10 million centroids, 2,000 shards built independently, 100 machines to assemble the inverted lists, and a final index memory-mapped on a central machine as 83 TiB. The 2017 paper has no graph-based indexes (the string "HNSW" does not appear in its text), so it is not evidence about how IVFADC compares with them. For that comparison use the benchmark sites and the guidance in chapter 11.

State of play, October 2026

Search-result summaries of NVIDIA's documentation (which I did not read in full) say that from FAISS version 1.10.0 users can opt in to NVIDIA's cuVS library as a GPU backend for the flat, IVF-Flat, IVF-PQ and CAGRA index types, with up to 12 times faster CAGRA index builds reported on a 100-million-vector benchmark. Treat that as a lead to check, not a settled number. The star, download and citation counts above are the 2024 paper's and will have moved. Which index is fastest at a given recall changes with each library release, so measure on your own data.

Limits and caveats

  • The code is lossy by design. My toy's 0.70 ceiling is the visible form of this. Production systems often rescore the shortlist from PQ with the full vectors (chapter 11 measures this), which needs the originals somewhere, on disk or in a slower tier.
  • Training is a dependency. The coarse centroids and PQ codebooks are learned from a sample. If the data later drifts (a new embedding model, a new domain), the codebooks fit it worse, and the usual remedy is to retrain and re-encode.
  • Euclidean distance and static data are the comfortable case. The paper's experiments use L2 distance and build the index once. Filters, per-user permissions and frequent updates are separate problems; see Filters, Metadata & Permissions.
  • The 2017 numbers are 2017 numbers. The paper compares with one prior GPU system and one CPU baseline, on hardware that has since been replaced several times.

Lessons

  • Spend bytes where the error is. Splitting the job into a coarse cell and a quantised residual is more accurate than quantising whole vectors with the same bytes, because the second stage models only what the first did not capture. Chapter 11 shows the single-stage version.
  • Turn arithmetic into lookups. The distance to a code is a sum over a handful of table entries. This is a case of precomputation trading a little memory for a lot of multiplication, the same idea as the key-value cache in A3's KV-cache chapter.
  • Find the part that does not parallelise. The GPU did not need a faster multiply; it needed a better way to pick the top k. When a hardware port disappoints, profile for the serial step. The mechanics are in Parallelism & GPUs and Performance Engineering.
  • Report two numbers, not one. Memory per vector and recall at a time budget together describe an index; either alone misleads. Lab 4 asks you to chart recall against search effort for HNSW, the main alternative.

Common misconception

"A bigger nprobe always gives better results." It gives better results only until the quantisation error dominates. In the toy, the 8-byte index stopped improving at four lists and gained nothing from the other 124. If recall plateaus as you probe more, spend the next byte on the code (or add a rescoring step), not on more probing.

Key takeaways

  • IVFADC stores each vector as a coarse list id plus a few bytes of product-quantised residual, and searches the codes with per-query lookup tables.
  • Probing more lists and spending more bytes per vector address different errors; measure both.
  • The 2017 paper's contribution was making this fast on GPUs, chiefly with WarpSelect, a register-resident k-selection, and by sharding and replicating the index across GPUs.
  • Compression is what makes the data fit the fast hardware: 384 GB of Deep1B vectors against about 20 GB of codes.
  • Read comparisons for what they hold constant. Several of the paper's speed-ups compare different hardware.

Check your understanding

In IVFADC, why is the product quantiser applied to the residual y − q1(y) rather than to y?

  1. The residual is shorter, so fewer pieces are needed
  2. It spends the code bytes on what the coarse step did not capture, so the same bytes give a closer approximation
  3. It lets the system skip training the coarse quantiser
  4. It makes the lookup tables independent of the query
The residual has the same length as the vector, so the first option is wrong. The coarse centroid already describes most of where the vector is; quantising the remainder concentrates the available codes on the detail. The tables still depend on the query (they are built from it, per probed list), and the coarse quantiser must still be trained.

A team scans 16 of 128 lists with 8-byte codes and gets overlap 0.70 with the exact top ten. Scanning all 128 lists would also give about 0.70. What change is most likely to help?

  1. Probe more lists than 128 by duplicating the index
  2. Switch to a smaller coarse quantiser
  3. Sort the scanned lists more carefully
  4. Use longer codes (for example 16 bytes), or re-rank the shortlist with the exact vectors
The plateau means the error is in the code, not in which lists were searched. Longer codes lower the quantisation error (in the toy, 16 bytes raised the ceiling to 0.90), and rescoring with exact vectors removes it for the shortlist. Probing more lists cannot help once all of them are scanned, and sorting does not change distances computed from the codes.

According to the paper, what made k-selection the bottleneck on a GPU, and how did WarpSelect respond?

  1. Standard selection exposes little parallelism and re-reads distances from global memory; WarpSelect keeps a small sorted queue in the registers of a warp and can be fused with the distance kernel
  2. Selection needs double precision, which GPUs lack; WarpSelect uses integers
  3. The distances are too large to compute; WarpSelect approximates them with product quantisation
  4. Sorting is cheap but copying to the CPU is slow; WarpSelect moves the sort to the host
The paper's abstract names low parallelism and poor use of the memory hierarchy. Product quantisation reduces the cost and memory of distances, but it is not what WarpSelect does, and nothing in the design moves work to the CPU.

Which statement about the Deep1B comparison (0.0133 ms per vector on four GPUs against 20 ms on one CPU thread) is the fairest reading?

  1. The GPU algorithm is about 1,500 times better than the CPU algorithm
  2. The comparison is invalid because the recalls differ
  3. The two systems reach about the same R@1 (0.4517 against 0.45) on very different hardware, so the ratio mostly reflects the platforms, as the authors note
  4. The result shows CPUs cannot search billion-scale data
The recalls are almost equal, which is why the comparison is informative, but four GPUs against a single thread is not like for like, and the paper says the hardware platforms differ. It does not show that CPUs cannot do the job; the 2024 paper describes CPU systems at far larger scale.

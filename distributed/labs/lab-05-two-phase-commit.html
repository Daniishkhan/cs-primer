Lab 5: Two-Phase Commit & Recovery

Chapter 13 argued that two-phase commit is safe but can leave honest participants stuck, and it walked through what each crash leaves behind. Arguments are cheap. In this lab you build the protocol, with a write-ahead log at every node, and then you let a seeded simulator crash your nodes at every awkward moment, hundreds of times, while it drops, duplicates and reorders messages. Then you do the thing the chapter only described: you measure how long in-doubt participants hold their locks while the coordinator is down, and you shrink that window by moving the decision somewhere that outlives the coordinator.

Why this lab matters

Almost every correct atomic-commit implementation is the same few ideas: make a fact durable before anyone can act on it, rebuild your state from your log after a crash, never decide for someone who has promised not to decide alone. They are easy to nod along to and easy to get subtly wrong, in ways that only show up when a node dies between two particular lines. A protocol bug of this kind does not crash anything; it silently commits a transfer on one shard and aborts it on the other. This lab gives you a machine that finds those bugs for you, and it names the seed so you can replay the exact run. The same discipline sits inside every database that does a distributed transaction and inside the replicated-coordinator designs of chapter 14.

One process, a whole cluster, no flakiness

The coordinator, the participants and the decision store are plain Python objects in the same process. A simulator (Sim) plays the network (random delays, drops, duplicates, reordering), the clock (simulated time, so nothing ever sleeps) and the crashes. There are no threads, no sockets and no real clocks, so a run is completely determined by its seed: if seed 118 breaks your code today it breaks it identically tomorrow. Python 3.8 or newer, standard library only. Time is measured in abstract "time units"; a message takes 1 to 5 of them.

What you'll build

Five milestones, each building on the last:

  1. Participants: a write-ahead log, prepare (log PREPARED, hold locks, then vote), and commit/abort, all safe against duplicate messages.
  2. Coordinator: log the decision before sending it (presumed abort), resend until every participant has acknowledged, then write END.
  3. Recovery on restart for every crash point, coordinator and participant. An in-doubt participant asks, and keeps its locks until it learns the outcome. The check crashes every node at every one of 20 named places (21 in milestone 5).
  4. Atomicity over hundreds of seeded runs with crashes at random points, lossy duplicating networks and long coordinator outages: no transaction commits at one participant and aborts at another, and every transaction eventually resolves.
  5. The blocking window: measure how long in-doubt participants hold locks while the coordinator is down, then implement a "replicated coordinator decision" variant and show the window shrinks, without giving up atomicity.

Common misconception: "the node just pauses"

A crash here is not a pause. When a node crashes the simulator deletes every attribute of the object except its log, drops all messages that arrive while it is down, and cancels its timers. On restart init_volatile() runs, then on_start(). So if your participant remembers "I hold the lock on x" only in a Python variable, the restarted participant has forgotten its promise, and the check will show you the consequence. It is exactly what happens to a real process: memory is gone, the disk is what is left.

Where can a node die?

A crash between any two lines of a handler is a different crash. The code you write marks the interesting gaps with self.point(...), and the check kills the node at each of them, once with a short outage and once with a long one. Everything sent before the point is already in flight; nothing after it happens.

The protocol on one page

Milestone 1: participants

A participant is a small database with a promise attached. When it receives PREPARE it must decide, using only what it knows locally, whether it can commit these writes no matter what happens next. In this lab it can if two things hold: no other transaction holds a lock on any key it wants, and the value is acceptable (any value equal to the string "BAD" stands in for a violated constraint). If it can, it does three things, in this order:

  1. take the locks (they stay held until the decision arrives);
  2. force a PREPARED record, with the writes, to its log;
  3. only then send VOTE YES.

The order is the whole point. A YES is a promise that the participant will be able to commit if told to, whatever crashes. A promise made before it is on disk is not a promise: if the node dies in between, it comes back having forgotten, and the coordinator may already have counted the YES. If it cannot commit, it says NO and takes no locks. A NO is safe without any further protocol, because the transaction cannot now commit; the participant may abort on its own.

Then COMMIT or ABORT arrives. The participant logs it first, then acts on it (apply the writes on commit), releases the locks, and answers ACK. Messages can be duplicated, so every handler must be idempotent: a second PREPARE for a transaction you already prepared repeats the YES, and a second COMMIT is acknowledged again but not applied again.

One more thing to notice. The participant's data dictionary is volatile. After a crash it is rebuilt by replaying the log, and only COMMITted transactions count. So a prepared-but-undecided write is never visible in data, and the log is the single source of truth.

def on_prepare(self, src, msg):
    tx, writes = msg["tx"], msg["writes"]
    yes, no = {"type": "VOTE", "tx": tx, "vote": "YES"}, {"type": "VOTE", "tx": tx, "vote": "NO"}
    if outcome(self.log, tx) == "ABORT":
        self.send(src, no)                            # I already aborted this one
        return
    if prepared_writes(self.log, tx) is not None:
        self.send(src, yes)                           # duplicate PREPARE: repeat the promise
        return
    if any(v == "BAD" for v in writes.values()) or not self.locks.try_acquire(tx, writes):
        self.log.append(("ABORT", tx))                # a NO vote lets me abort on my own
        self.send(src, no)
        return
    self.point("p:before_prepare_log")
    self.log.append(("PREPARED", tx, writes))         # force the promise to disk ...
    self.point("p:after_prepare_log")
    self.send(src, yes)                               # ... and only then tell anyone
    self.point("p:after_vote_sent")
    self.start_inquiry(tx)

def on_decision(self, src, msg):
    tx, kind = msg["tx"], msg["type"]
    have = outcome(self.log, tx)
    writes = prepared_writes(self.log, tx)
    if have is None:
        if writes is None:
            assert kind == "ABORT", f"{self.name}: COMMIT for {tx} which I never prepared"
            self.log.append(("ABORT", tx))            # never prepared: remember, so a late PREPARE says NO
        else:
            self.point("p:before_decision_log")
            self.log.append((kind, tx))               # log the decision BEFORE acting on it
            self.point("p:after_decision_log")
            if kind == "COMMIT":
                self.data.update(writes)
            self.locks.release(tx)                    # locks are released only now
            self.waiting.pop(tx, None)
    else:
        assert have == kind, f"{self.name}: told {kind} for {tx} but my log says {have}"
    self.send(src, {"type": "ACK", "tx": tx})

Milestone 2: the coordinator

The coordinator's job is to turn a set of votes into one decision and to make sure the decision reaches everybody, however long that takes. Its rules are the mirror image of the participant's.

  • Collect votes, with a timeout. Send each participant its PREPARE and arm a timer. A single NO, or silence until the timer fires, means abort. Aborting early is always safe, because nobody can have committed before the coordinator logs COMMIT.
  • Log the decision before sending it. When all votes are YES, force ("COMMIT", tx, participants) to the log. That record is the commit point. Only then send COMMIT. The record must name the participants, because after a crash that list is how the coordinator knows whom to keep telling.
  • Presumed abort. An abort writes nothing and expects no acks. If the coordinator forgets everything (a crash during phase 1), the correct answer to "what happened to T?" is already "abort". That makes the common case cheaper and recovery simpler.
  • Resend until acked. Messages get lost. Keep a set of participants that have not yet acknowledged and resend COMMIT to exactly those, on a timer, forever. A participant that is down will get it when it is back.
  • Write END, then forget. When the last ack arrives, log ("END", tx). END tells a future recovery that nothing is left to do.

def on_begin(self, msg):
    tx, writes = msg["tx"], msg["writes"]
    if tx in self.pending or tx in self.logged_commits():
        return
    self.pending[tx] = {"writes": writes, "votes": {}, "phase": 1}
    for p, w in writes.items():
        self.send(p, {"type": "PREPARE", "tx": tx, "writes": w})
    self.point("c:after_prepare_sent")
    self.set_timer(VOTE_TIMEOUT, ("votes", tx))

def on_vote(self, src, msg):
    tx = msg["tx"]
    st = self.pending.get(tx)
    if st is None or st["phase"] != 1:
        return                                        # late or duplicate: the decision is made
    if msg["vote"] == "NO":
        self.abort(tx)
        return
    st["votes"][src] = "YES"
    if set(st["votes"]) == set(st["writes"]):
        self.point("c:after_votes")
        self.make_decision(tx)

def make_decision(self, tx):
    """All voted YES.  The commit point: log COMMIT, THEN tell anyone."""
    self.log_commit(tx)

def log_commit(self, tx):
    parts = sorted(self.pending[tx]["writes"])
    self.log.append(("COMMIT", tx, parts))            # <- the commit point
    self.point("c:after_decision_log")
    del self.pending[tx]
    self.committing[tx] = set(parts)
    self.send_decisions(tx, "COMMIT")
    self.set_timer(RESEND_EVERY, ("resend", tx))

def send_decisions(self, tx, kind, only=None):
    targets = sorted(self.committing[tx] if kind == "COMMIT" else only)
    for p in targets:
        self.send(p, {"type": kind, "tx": tx})
        self.point("c:mid_send")

def abort(self, tx):
    st = self.pending.pop(tx)
    self.send_decisions(tx, "ABORT", only=st["writes"])   # presumed abort: nothing logged, no acks

def on_ack(self, src, tx):
    left = self.committing.get(tx)
    if left is None:
        return
    left.discard(src)
    if not left:
        self.point("c:before_end")
        self.log.append(("END", tx))                  # everyone has it; I may forget
        del self.committing[tx]

def on_timer(self, tag):
    kind, tx = tag
    if kind == "votes":
        st = self.pending.get(tx)
        if st and st["phase"] == 1:
            self.abort(tx)                            # silence counts as NO
    elif kind == "resend" and tx in self.committing:
        self.send_decisions(tx, "COMMIT")
        self.set_timer(RESEND_EVERY, tag)

Milestone 3: recovery, for every crash point

Now the part that makes it a distributed-systems lab. Each node has to rebuild itself from its log and carry on, and the rest of the cluster has to cope in the meantime. Work through what each gap leaves behind, then check your table against the code you write.

Node dies at…What the log saysWhat recovery must doOutcome

Two rules make the in-doubt participant correct, and both are about not doing something.

It keeps its locks. A prepared participant cannot decide alone: the coordinator may have logged COMMIT, or may have decided abort. Until it hears, any other transaction that read or wrote the same keys would be reading around a write that may be about to appear. So recovery must re-take, from the log, the locks of every transaction that is PREPARED and undecided. The check proves it by sending a conflicting PREPARE to each participant while the coordinator is down, including a participant that has itself just restarted. Every one must answer NO.

The coordinator does not answer while it is still deciding. An in-doubt participant asks INQUIRE, and under presumed abort "I have no record" means "abort". But a coordinator that is still collecting votes has no record yet. If it answered ABORT now and then collected the last YES and committed, one participant would have aborted and the rest committed. So on_inquire has three cases: transaction still in phase 1, stay silent (the participant will ask again); COMMIT in the log, answer COMMIT (even after END); anything else, answer ABORT.

def on_start(self):
    writes_of = {}
    for rec in self.log:                              # replay the log, oldest first
        if rec[0] == "PREPARED":
            writes_of[rec[1]] = rec[2]
        elif rec[0] == "COMMIT":
            self.data.update(writes_of[rec[1]])
    for tx, writes in writes_of.items():              # PREPARED and not decided: in doubt
        if outcome(self.log, tx) is None:
            assert self.locks.try_acquire(tx, writes)  # the promise: keep my locks
            self.start_inquiry(tx)
            self.ask(tx)

def start_inquiry(self, tx):
    self.waiting[tx] = self.now
    self.set_timer(INQUIRE_EVERY, ("inquire", tx))

def ask(self, tx):
    self.send(self.cfg["coord"], {"type": "INQUIRE", "tx": tx})

def on_timer(self, tag):
    if tag[0] == "inquire":
        tx = tag[1]
        if tx in self.waiting and outcome(self.log, tx) is None:
            self.ask(tx)
            self.set_timer(INQUIRE_EVERY, tag)

def on_start(self):
    for tx, parts in self.logged_commits().items():
        if tx not in self.ended():
            self.committing[tx] = set(parts)
            self.send_decisions(tx, "COMMIT")
            self.set_timer(RESEND_EVERY, ("resend", tx))

def logged_commits(self):
    return {rec[1]: rec[2] for rec in self.log if rec[0] == "COMMIT"}

def on_inquire(self, src, tx):
    if tx in self.pending:
        return                                        # still deciding: stay silent, they will ask again
    known = self.logged_commits()
    kind = "COMMIT" if tx in known else "ABORT"       # no record at all means abort (presumed abort)
    self.send(src, {"type": kind, "tx": tx})

Milestone 4: atomicity over hundreds of runs

Unit tests check the cases you thought of. This milestone checks the ones you did not. Each of 300 seeds builds a fresh cluster (one coordinator, three participants), submits ten transactions at random times over random subsets of participants (some with a participant forced to vote NO, many fighting over the same keys), and then makes life hard:

  • 6% of messages are dropped and 5% are delivered twice; delays are random, so messages overtake each other;
  • every crash point of every node has a 2% chance of killing it, for the first 300 time units (up to ten crashes);
  • in 40% of the runs the coordinator is also killed at a random moment and stays down for 50 to 250 time units.

When the dust settles (no more crashes, every node restarted, messages still lossy) the check evaluates the invariants from chapter 13 against the logs:

  1. Agreement. No transaction is COMMIT at one participant and ABORT at another.
  2. Validity. A transaction commits only if every participant had logged PREPARED, and never if one of them had to vote NO.
  3. Coordinator and participants agree. A logged COMMIT means every participant committed; a participant that committed implies a COMMIT record.
  4. Termination. Every participant that logged PREPARED has a decision, every committed transaction has an END, and no locks are left held.
  5. State follows the log. Each participant's live data equals the replay of its log.

It also insists that a sensible fraction of the transactions actually committed. Otherwise "abort everything" would pass, and the lab would be vacuous.

Milestone 5: how long do the locks stay held?

Chapter 13 called this the blocking window. Here it is as a number. In the scenario below the coordinator receives both YES votes and dies before it logs a decision. Both participants are in doubt. Their inquiries vanish into a dead node. They keep their locks until the coordinator comes back, finds no record, and presumes abort.

Measure it

The check measures the window exactly as an outsider could: from the timestamp of each participant's PREPARED record to the timestamp of its decision record. With the coordinator down for 300 time units, expect windows a little over 300: the outage, plus the restart and one inquiry round trip. The exact figures for the reference solution are in the transcript under “Look under the hood”; yours must come out the same, and the replicated variant below must beat them by a wide margin.

Shrink it: replicate the decision

The root cause is that the decision lives on one machine's disk. Move it somewhere that survives the coordinator and nobody has to wait for the coordinator. Chapter 13 describes Paxos Commit (Gray and Lamport, 2006) and the practical version, a coordinator whose state is a record in a replicated store. You will build a small one. The DecisionStore in the starter is the fake consensus: a node that holds one write-once cell per transaction. The first value written wins and never changes. It stands in for a small replicated group (three or five nodes running Raft or Paxos, as in Lab 4), and to keep this lab simple the simulator never crashes it.

The protocol changes in four places:

  1. The coordinator decides through the store. With all YES votes, instead of logging COMMIT it sends DECIDE COMMIT to the store (resending until answered) and waits for DECISION. If the answer is COMMIT, it logs COMMIT locally and carries on exactly as before. The store's cell is now the commit point; the coordinator's own log is a cache.
  2. A participant that has waited too long goes to the store. After STORE_WAIT time units in doubt it sends TERMINATE to the store. If the cell is empty the store writes ABORT into it, for ever, and replies. If the cell already holds COMMIT, it replies COMMIT.
  3. The race is safe because the cell is write-once. Suppose a participant gets impatient and the coordinator is merely slow. Either the coordinator's COMMIT reaches the store first (the participant learns COMMIT) or the participant's ABORT does (the coordinator's DECIDE is answered with ABORT and the coordinator aborts). There is no third outcome.
  4. "No record" no longer proves abort. The coordinator may have crashed after the store recorded COMMIT but before it logged it. So when a restarted coordinator is asked about a transaction it has no record of, it must not say ABORT; it asks the store (TERMINATE, with the participant as the reply address).

class ReplicatedCoordinator(Coordinator):
    """Writes the decision to the store BEFORE its own log, so it outlives the coordinator."""

    def make_decision(self, tx):
        self.pending[tx]["phase"] = 2                     # deciding: the vote timeout no longer applies
        self.propose(tx)

    def propose(self, tx):
        if tx in self.pending:
            self.send(self.cfg["store"], {"type": "DECIDE", "tx": tx, "value": "COMMIT"})
            self.set_timer(RESEND_EVERY, ("propose", tx))

    def on_timer(self, tag):
        if tag[0] == "propose":
            self.propose(tag[1])
        else:
            super().on_timer(tag)

    def on_message(self, src, msg):
        if msg["type"] != "DECISION":
            super().on_message(src, msg)
            return
        tx = msg["tx"]
        if tx not in self.pending:
            return
        if msg["value"] == "COMMIT":
            self.point("c:after_store_decide")
            self.log_commit(tx)
        else:                                             # a participant got there first: ABORT won
            self.abort(tx)

    def on_inquire(self, src, tx):
        if tx in self.pending or tx in self.logged_commits():
            super().on_inquire(src, tx)
        else:                                             # "no record" is no longer proof of abort:
            self.send(self.cfg["store"], {"type": "TERMINATE", "tx": tx, "reply_to": src})

def ask(self, tx):
    super().ask(tx)
    if self.now - self.waiting[tx] >= STORE_WAIT:
        self.send(self.cfg["store"], {"type": "TERMINATE", "tx": tx, "reply_to": self.name})

What the number does and does not say

The window dropped from about 300 (the outage) to about 40: roughly STORE_WAIT (20) plus the poll interval (15) plus a round trip. It is now bounded by your patience setting, not by the coordinator's repair time. But the blocking has not vanished, it has moved: participants now depend on the decision store being available, which in a real system means "a majority of its replicas are up and can talk". That is a much weaker dependency than "this one machine is up", and the store is the same kind of component the rest of the system already trusts to hold its logs. The price is latency: every commit pays one extra round trip (and a replicated write) to the store before the first COMMIT can go out.

Distributed systems connection

What you built is the skeleton inside a lot of production software. A database with PREPARE TRANSACTION and an external transaction manager is your participant plus someone else's coordinator, and a forgotten prepared transaction is the in-doubt participant of milestone 3, holding its locks until a human intervenes. The replicated-decision variant is the idea behind Paxos Commit and behind systems that run two-phase commit across groups that are themselves replicated, such as Spanner's participants (Corbett et al., OSDI 2012); chapter 14 compares those designs with Percolator and Calvin. Compare with a saga from architecture Lab 4: a saga gives up isolation and atomic visibility to avoid ever holding locks across a network wait, 2PC keeps both and pays with blocking. And the testing method, a seeded simulator that crashes nodes at every named point and checks invariants on the logs, is the same one chapter 19 and Lab 7 build up into full deterministic simulation.

What you learned

  • Two-phase commit is write-ahead logging applied twice: a participant logs PREPARED before it votes YES, the coordinator logs COMMIT before it tells anyone. Each rule is "make it durable before anyone can act on it".
  • A prepared participant has surrendered the right to decide alone, so it must keep its locks, rebuilt from the log after a restart, until it learns the outcome.
  • Presumed abort makes "I have no record" mean "abort", but only for a coordinator that is not still deciding, and (in the replicated variant) only if no durable decision could exist elsewhere.
  • Recovery is a function of the log: every crash point must be survivable using nothing but durable state, and the right way to be sure is to crash at each named point and check.
  • Atomicity is a property of all logs together; random seeds with drops, duplicates and crashes, plus invariants on the logs, find bugs unit tests do not.
  • The blocking window equals the coordinator's outage. A write-once decision register, written before the coordinator logs and consulted by impatient participants, turns it into a patience setting, at the price of an extra round trip and a new availability dependency.

Check your understanding

A participant writes its YES vote onto the network, then logs PREPARED, and crashes between the two. What can go wrong?

  1. Nothing: the coordinator will retry the PREPARE
  2. The participant will commit twice
  3. The coordinator may have counted the YES and committed; the restarted participant has no record of any promise, so it may lose the transaction's writes or its locks
  4. The participant will vote NO on restart, which is harmless
A YES is a promise to be able to commit whatever happens next. The promise lives only in the log. If the vote leaves before the record is durable, a crash in the gap yields a node that is unaware of the transaction while the coordinator has committed it: atomicity is silently violated.

A coordinator that is still collecting votes receives INQUIRE about that transaction from an in-doubt participant. Why must it not answer ABORT, even though presumed abort says "no commit record means abort"?

  1. Because INQUIRE messages are always duplicates
  2. Because it has no record yet, and it may still receive the last YES and log COMMIT; an ABORT already given would disagree with that
  3. Because aborting costs a forced log write
  4. Because the participant would not understand ABORT
Presumed abort is a statement about a coordinator whose memory is gone, or one that has finished. A live coordinator in phase 1 is undecided, so it stays silent and the participant asks again later.

In the replicated-decision variant, why must a restarted coordinator that has no record of a transaction ask the decision store instead of answering ABORT?

  1. It may have crashed after the store recorded COMMIT but before it logged COMMIT itself; the store, not the local log, now holds the truth
  2. Because the store is faster than the local log
  3. Because participants no longer trust the coordinator
  4. Because presumed abort was removed from the protocol
Moving the commit point to the store means the coordinator's log can lag it. "No local record" no longer implies "nothing was decided"; only the write-once cell is authoritative, and asking it also settles the race safely.

After adding the decision store, the participants' lock-hold time during a coordinator outage went from about 300 to about 40. What is the honest summary?

  1. Two-phase commit no longer blocks, ever
  2. The window is now zero
  3. The store removed the need for participants to log PREPARED
  4. The window is bounded by the participants' patience and the store's availability, not by the coordinator's repair time; blocking now requires the store (a majority of its replicas) to be unreachable, and every commit pays an extra round trip
The dependency moved from one machine to a replicated group. That is a much better dependency (it tolerates a minority of failures) but not the absence of one, and there is no free lunch on latency.

Lab 4: Multi-Paxos Replicated Log

In chapter 9 you derived Paxos by deleting each rule and watching an execution go wrong. Now you will write the rules. You will build the acceptor, then a single-decree proposer, then make duelling proposers stop duelling, then grow the whole thing into a replicated log with a leader that survives crashes, and finally put a key-value store on top that applies every client request exactly once. Everything runs on a simulated network that drops, duplicates, delays and reorders messages, under a referee that sees every accept and shouts the moment two different values are chosen for the same slot. The check runs hundreds of seeded executions and, when one fails, hands you the seed and the trace so you can replay it.

Why this lab matters

You met consensus through Raft in networking Lab 6, where the protocol arrives as a ready-made shape: terms, a leader, an append-entries check that keeps every log a prefix of the leader's. This lab removes that scaffolding and builds the layer underneath it. You will write the promise that covers every slot at once, the report that lets a new leader discover what might already be chosen, the rule that picks the highest-ballot value out of those reports, and the no-op that closes a gap. These are the pieces Raft decided in advance, and when you can write them yourself you can read any "Paxos with a twist" design, from a cloud database to a paper, and see which of the choices it made. It is also a lesson in testing: you will find out how little a handful of hand-written examples proves, and how much a seeded simulator with a referee proves.

One process, a whole cluster, no flakiness

The five replicas, the clients and the network are Python objects in one process. The "network" is a priority queue of in-flight messages with random delays, drops and duplicates; "time" is a counter that jumps from event to event; a "crash" stops delivering to a node and throws away its memory, and a "restart" builds a new node object over the same disk dictionary, which is the only thing that survives. All randomness comes from a seeded random.Random, so a seed names one exact execution, the same every time. Python 3.8 or newer, standard library only, no sockets, no threads. The whole check takes a few seconds.

What you'll build

Five milestones, each built on the last:

  1. The acceptor: the two rules (promised and accepted), kept in a disk that survives crashes. One character separates them: promise needs >, accept needs >=.
  2. Single-decree Paxos: a proposer that runs phase 1, adopts the value of the highest-ballot accepted proposal it hears about, runs phase 2 and learns the outcome. Safety is checked over 300 seeded executions on a network that drops, duplicates and reorders.
  3. Duelling proposers: eight rivals start at the same instant. A randomized, growing backoff keeps them from knocking each other down forever. The check measures how many messages the duel wastes.
  4. Multi-Paxos: one phase 1 per leader, covering every slot. A new leader recovers whatever the promises report, re-proposes it, and fills holes with no-ops. The check crashes leaders at random, including right after a burst of pipelined commands.
  5. A replicated key-value store: apply the chosen log strictly in slot order, and deduplicate client retries so a command that was chosen twice is executed once. Three clients retry through leader crashes and 10% message loss.

The simulator and the referee (given)

Read the top half of starter.py before you write anything. Three pieces matter.

The network. node.send(dst, msg) puts a copy of a plain-dictionary message into the queue. The message may be dropped, may be duplicated, and is delivered after a random delay, so later messages overtake earlier ones. A message to a crashed node vanishes. The messages in this lab are:

MessageFieldsMeaning
preparebPhase 1a. A ballot has no slot: one prepare covers the whole log.
promiseb, acceptedPhase 1b. accepted maps each slot to the (ballot, value) the acceptor holds.
acceptb, slot, vPhase 2a, for one slot.
acceptedb, slotPhase 2b.
nackb, promisedA refusal. It names the higher ballot the acceptor has promised, so the proposer knows what to beat.
learn, hb, hb_ackGiven plumbing: the leader tells followers what is chosen, and heartbeats double as the leader's liveness signal.
req, resp, redirectClient traffic (milestone 5).

Ballots are the pairs (round, node id) from the chapter. Python compares tuples element by element, so (3, 1) < (3, 2) < (4, 1), which is exactly the order you need: round first, id as the tie-break. NO_BALLOT = (0, 0) is below every real ballot.

The Observer. This is the referee that makes the checks trustworthy. Every time any acceptor accepts something, the given glue reports (slot, ballot, value) to the Observer. When a majority of acceptors have accepted the same value at the same ballot for a slot, that value is, by definition, chosen: this is the omniscient fact the chapter said no single process can see. The Observer records a violation, and the run stops on the spot, if:

  • two different values are ever chosen for one slot (agreement);
  • a value is chosen that nobody proposed, other than a no-op (validity);
  • a node claims a slot is committed or learned when it is not (the node believes something false).

It judges your code by what the acceptors actually did, not by what your proposer says, so a bug that merely looks right from the inside cannot fool it. And because the run stops at the violation, the last lines of the trace are the lines that matter.

Milestone 1: the acceptor

An acceptor is the memory of the system, and its whole state is two things in disk: promised, the highest ballot it has promised to honour, and accepted, a dictionary from slot to the (ballot, value) it holds for that slot. Single-decree Paxos uses only slot 0. Multi-Paxos uses many, which is why the state is already shaped that way: a promise names a ballot, not a slot, so one promise protects every slot at once.

The rules are the chapter's two:

  • prepare(b): if b > promised, set promised = b and reply with a promise carrying a copy of everything accepted so far. Otherwise refuse and say which ballot you are holding out for.
  • accept(b, slot, v): if b >= promised, set promised = b, store (b, v) for the slot and reply accepted. Otherwise refuse.

Three things deserve a moment. First, the one-character difference. The accept rule must allow equality because the usual proposer's accept carries exactly the ballot its own prepare made the acceptor promise. With a strict > the acceptor would refuse the very proposer it just promised, and nothing would ever be chosen. Second, accepting a ballot above promised raises promised too: an acceptor that accepted ballot 5 has implicitly promised not to go below 5. Third, the promise must hand over a copy: the report is a snapshot of the past, and it must not change when the acceptor later accepts something else.

Where does durability enter? Everything lives in disk, and the simulator keeps that dictionary across a crash. A restarted acceptor is a new Acceptor object built on the same dictionary. If you kept promised in an ordinary attribute, the restart would erase a promise the acceptor had already given away, and the chapter's "late accept" counterexample would be back. In a real implementation this is the write-then-fsync step (systems chapter 9) that must complete before the reply leaves the machine; here the simulator only checks that you used disk.

Solution spoiler 
def on_prepare(self, ballot: Ballot) -> tuple:
    """Phase 1b. Return ("promise", accepted) or ("nack", promised)."""
    if ballot > self.disk["promised"]:
        self.disk["promised"] = ballot
        return ("promise", dict(self.disk["accepted"]))
    return ("nack", self.disk["promised"])
def on_accept(self, ballot: Ballot, slot: int, value: Any) -> tuple:
    """Phase 2b. Return ("accepted", ballot) or ("nack", promised)."""
    if ballot >= self.disk["promised"]:
        self.disk["promised"] = ballot
        self.disk["accepted"][slot] = (ballot, value)
        return ("accepted", ballot)
    return ("nack", self.disk["promised"])

Milestone 2: single-decree Paxos

Now the other half: a proposer that wants the system to choose self.value. It runs the two phases of the chapter against the acceptors, and the given AcceptorNode glue feeds your milestone 1 code with the messages. Your proposer has soft state only: if the machine crashes it can start again with a higher ballot.

Phase 1 is begin_round: bump the round, form the ballot (round, self.id), clear what you collected, send prepare to every acceptor and arm the retry timer (a message may have been dropped, and nobody will tell you). Phase 2 happens in on_message, and it contains the single most important line in this lab:

When promises have arrived from a quorum, look at what they reported for slot 0. If any of them reported an accepted proposal, your phase 2 value is the value of the one with the highest ballot; only if none did may you use your own. Both halves of that sentence are tested: the check pre-loads acceptors with a chosen value and sends a rival that wants something else, and with two different accepted values at different ballots, in both orders, so "take the first report" and "take the last report" each fail one of them.

A proposer also has to react to refusals. A nack carries the ballot the acceptor has promised. If that ballot is higher than yours, set your round to at least its round, so the next ballot beats it, and re-arm the retry timer. A nack whose promised equals your own ballot is just the echo of a duplicated prepare: ignore it. Finally, late replies are normal on this network: a promise for ballot 1 can arrive after you moved to ballot 2. Ignore anything whose ballot is not your current one.

def begin_round(self) -> None:
    """Phase 1a: start a new attempt."""
    self.round += 1
    self.attempt += 1
    self.ballot = (self.round, self.id)
    self.promises, self.proposal, self.accepted_by = {}, None, set()
    self.broadcast(self.acceptors, {"t": "prepare", "b": self.ballot})
    self.arm_retry()
def on_message(self, src: int, msg: dict) -> None:
    """Handle a reply from an acceptor."""
    if self.chosen is not None:
        return
    t = msg["t"]
    if t == "nack":
        if msg["promised"] > self.ballot:
            self.round = max(self.round, msg["promised"][0])
            self.arm_retry(self.retry_delay(self.attempt))
        return
    if msg["b"] != self.ballot:
        return
    if t == "promise" and self.proposal is None:
        self.promises[src] = msg["accepted"].get(0)
        if len(self.promises) >= self.quorum:
            reports = [r for r in self.promises.values() if r is not None]
            # the adoption rule: the value of the highest-ballot accepted proposal
            self.proposal = max(reports, key=lambda r: r[0])[1] if reports else self.value
            self.broadcast(self.acceptors,
                           {"t": "accept", "b": self.ballot, "slot": 0, "v": self.proposal})
    elif t == "accepted" and self.proposal is not None:
        self.accepted_by.add(src)
        if len(self.accepted_by) >= self.quorum:
            self.chosen = self.proposal
            self.log(f"learned that {self.chosen!r} is chosen (ballot {self.ballot})")

Milestone 3: duelling proposers

Safety is done; now progress. In the chapter you saw that a higher prepare invalidates the phase 2 of every lower ballot. Put two proposers in a bad rhythm and each one's phase 1 knocks the other's phase 2 down. It is not a bug in either, and nothing crashes: it is livelock, activity without progress.

FLP (chapter 2) says no deterministic protocol can promise to avoid this in every schedule, and Paxos does not try: it stays safe and makes livelock improbable. Chapter 9 named two remedies, a distinguished leader (you will build one in milestone 4) and randomized backoff. Here you do the second. When a nack tells you that you lost, wait a random time before your next attempt, and wait longer every time you lose. Randomness breaks the symmetry; the growth makes sure that even a crowd of rivals thins out, because the window in which they retry gets wider than the time one of them needs to finish.

The code is a single method, retry_delay(attempt), which your on_message already calls when it sees a nack. Use the simulator's generator, self.sim.rng, and not the random module: every random choice must come from the seeded stream or the run cannot be replayed.

Common misconception

"Backoff is how Paxos stays correct." It is not. Remove it and the safety check at milestone 2 still passes: no two values are ever chosen. Backoff buys liveness and efficiency, and nothing else. That is the same split as Raft's randomized election timeouts, and it is why a mis-tuned timer is a performance incident and not a data-loss incident.

Replace the body of Proposer.retry_delay so that it returns a whole number of ticks that is random, grows with attempt (exponential backoff) and is capped at RETRY_CAP.

Hints try without first

  • Why the lower bound cap // 2? Delay 0 is the problem you are solving. Pure "full jitter" in [0, cap] also works in this lab, and is the usual choice when you want the shortest typical wait.

Solution spoiler 
def retry_delay(self, attempt: int) -> int:
    """How long to wait after a nack before trying again with a higher ballot."""
    cap = min(20 * 2 ** (attempt - 1), RETRY_CAP)
    return self.sim.rng.randint(cap // 2, cap)

Milestone 4: Multi-Paxos

One decision is not a service. A service needs an unending sequence of them, the replicated log of chapter 8, and the obvious design is one single-decree instance per slot. That is safe, but each command pays two round trips and invites a duel per slot. Multi-Paxos removes both costs with one observation you already built into milestone 1: a promise names a ballot, not a slot. If a replica wins phase 1 with ballot b, a majority of acceptors have promised not to accept anything below b in any slot. So it can run phase 2 directly for slot 1, then slot 2, then slot 3, as fast as clients send commands, without asking again, until someone with a higher ballot appears.

The given code handles the surroundings: an election timer with a random timeout, heartbeats, retransmission of accepts that may have been dropped, stepping down when a higher ballot is seen, telling followers what was chosen, and catching up a replica that missed something or restarted. You write the four methods in the middle.

Phase 1 for the whole log

start_phase1 picks a ballot above every round the replica has ever seen, remembers that it is campaigning, and sends one prepare to everybody, itself included (your own acceptor's promise counts like any other). There is no slot in it.

Recovery: the part that is easy to get wrong

When on_promise has a quorum, the replica is the leader, but it must not start numbering new commands from slot 1. The previous leader may have left work half-done, and some of it may already be chosen. Each promise carried everything its acceptor has accepted, for every slot, so the new leader does exactly what a single-decree proposer does, slot by slot:

  • If some promise reported an accepted value for a slot, re-propose the value with the highest ballot, at the new ballot. If it had been chosen, this is how the new leader inherits it. If it had not, proposing it is harmless: it was a perfectly good command.
  • If no promise mentioned a slot that lies below a slot that was mentioned, it is a gap. The state machine applies slots in order and cannot skip one it does not know about, so a gap blocks everything after it. Fill it with a no-op. A no-op is a legitimate decision: it changes nothing and lets the log move on.
  • Slots the replica already knows to be chosen need no work.
  • New commands then go after the last recovered slot: next_slot = last + 1.

Here are the disks at the start of that scenario. The Observer has never seen these accepts, so it ignores them; the new leader must rediscover everything from the promises.

ReplicaAccepted at ballot (1,1)State
R1slots 1, 2, 3, 4 (d), 5 (e)down for the whole recovery
R2slots 1, 2, 3, 5 (e)runs phase 1
R3slots 1, 2, 3promises to R2

Why is it right to discard d? A value is chosen only when a majority has accepted it. d sits on one disk out of three, and the quorum {R2, R3} does not include that disk, so nothing the new leader can learn says d is chosen. Any chosen slot, on the other hand, must appear in the promises of every majority, because two majorities intersect. That is the whole safety argument, slot by slot.

Phase 2 for each slot

send_accept(slot, value) records the slot as pending and broadcasts the accept; on_accepted counts the acceptors that answered at your ballot and, at a quorum, calls the given commit. The given propose(cmd) shows how little a stable leader does for each new command: take the next free slot and call send_accept. No phase 1.

Common misconception

"If the new leader sees a value in a promise, it has to be chosen, so I can skip the highest-ballot comparison for slots." No. A report is only evidence of what one acceptor holds. Different acceptors may hold different values for the same slot at different ballots, and only the highest-ballot one can possibly have been chosen. Re-proposing a lower one is the single-decree "overwrite" bug, once per slot.

def start_phase1(self) -> None:
    """Phase 1a for the WHOLE log: campaign for leadership."""
    self.max_round += 1
    self.ballot = (self.max_round, self.id)
    self.electing, self.leading = True, False
    self.promises, self.pending, self.votes = {}, {}, {}
    self.log(f"starts phase 1 with ballot {self.ballot}")
    self.broadcast(self.peers, {"t": "prepare", "b": self.ballot})
def on_promise(self, src: int, msg: dict) -> None:
    """Phase 1b arrives: {"t": "promise", "b": ballot, "accepted": {slot: (ballot, value)}}."""
    if not self.electing or msg["b"] != self.ballot:
        return
    self.promises[src] = msg["accepted"]
    if len(self.promises) < self.quorum:
        return
    self.electing, self.leading = False, True
    best: Dict[int, tuple] = {}
    for accepted in self.promises.values():
        for slot, (b, v) in accepted.items():
            if slot not in best or b > best[slot][0]:
                best[slot] = (b, v)
    last = max(list(best) + list(self.chosen) + [0])
    self.next_slot = last + 1
    self.log(f"is leader with ballot {self.ballot}; recovering slots 1..{last}")
    for slot in range(1, last + 1):
        if slot not in self.chosen:
            self.send_accept(slot, best[slot][1] if slot in best else NOOP)
def send_accept(self, slot: int, value: Any) -> None:
    """Phase 2a for one slot: remember it and ask everybody to accept it."""
    self.pending[slot] = value
    self.votes[slot] = set()
    self.broadcast(self.peers, {"t": "accept", "b": self.ballot, "slot": slot, "v": value})
def on_accepted(self, src: int, msg: dict) -> None:
    """Phase 2b arrives: {"t": "accepted", "b": ballot, "slot": s}."""
    slot = msg["slot"]
    if not self.leading or msg["b"] != self.ballot or slot not in self.pending:
        return
    self.votes[slot].add(src)
    if len(self.votes[slot]) >= self.quorum:
        value = self.pending.pop(slot)
        del self.votes[slot]
        self.commit(slot, value)

Milestone 5: a replicated key-value store

The log is only a sequence of agreed commands. A service is what you get by running the same deterministic state machine over it on every replica, which is state machine replication from chapter 8. Two details turn the log into something clients can use.

Apply in slot order, with no gaps. Replicas learn slots in any order: slot 7 can be known before slot 6. Applying 7 first would make replicas diverge. So apply_ready applies slot applied + 1 only if it is known, and stops at the first slot it does not know. No-ops advance the counter and do nothing else.

Exactly once. A client sends request number seq; the leader gets it chosen; then the leader crashes before replying. The client times out and retries the same request at the new leader, which has no idea the first attempt was chosen, and proposes it again. Now the same command is in the log twice, in slots 3 and 4. The log is correct, since both were really chosen. The service would be wrong if it executed both: an increment would count twice.

The fix lives in the state machine, and it is deterministic: every replica applies the same slots in the same order, so every replica makes the same dedupe decisions. The store keeps a session per client: the last seq executed and its result. When a command arrives with the same seq, return the stored result without executing; with a lower seq, the client has moved on, so ignore it; with a higher one, execute and remember. This works because each client has one request outstanding at a time and numbers them 1, 2, 3.... You met the same idea as an idempotency key in networking chapter 16 and in the saga lab's services (architecture Lab 4). The difference here is where it sits: not at the edge of one service, but inside the replicated state machine, where it is the only place that sees the log's final order.

Solution spoiler 
def apply(self, cmd: dict) -> Any:
    """MILESTONE 5. Apply one chosen command and return its result."""
    if cmd["op"] == "noop":
        return None
    client, seq = cmd["client"], cmd["seq"]
    last = self.sessions.get(client)
    if last is not None:
        if seq == last[0]:
            return last[1]
        if seq < last[0]:
            return None
    result = self._execute(cmd)
    self.sessions[client] = (seq, result)
    return result
def apply_ready(self) -> None:
    """Apply the chosen log to the state machine, IN SLOT ORDER, with no gaps."""
    while self.applied + 1 in self.chosen:
        self.applied += 1
        cmd = self.chosen[self.applied]
        if cmd["op"] == "noop":
            continue
        self.reply_to_client(cmd, self.kv.apply(cmd))

  3. Pick the lowest ballot. Use min instead of max when choosing among reports. Which scenario catches it, and why would it be hard to catch with random runs alone?
  4. Remove the backoff. Make retry_delay return 0. The unit test of milestone 3 fails. To see the cost, comment out the m3_unit() call in check.py and run again: the proposers all still learn the value, but the check fails on the message budget.   5. Forget the disk. In on_prepare, keep promised in self.mem instead of self.disk. Milestone 1 fails at the restart test. This is "write before you reply" in code.
  6. Leave the gap. In on_promise only re-propose slots that some promise mentioned (delete the NOOP branch). Milestone 4 fails in the recovery scenario, and the message says why a single hole freezes the log.
  7. Count a stale vote. In on_accepted delete the msg["b"] != self.ballot test. The counting test fails. Before you read the message: can you build an execution, by hand, where a late accepted from an old ballot makes a leader commit a value that was never chosen?

Going further

  • Flexible Paxos quorums. The proof in chapter 9 needs only that every phase-1 quorum intersects every phase-2 quorum. With 5 replicas, let phase 2 use 2 and phase 1 use 4 (2 + 4 > 5). Give Replica two numbers, q1 and q2, use q1 in on_promise and q2 in on_accepted, and teach the Observer that a value is chosen at q2 accepts. Quick experiment: I made exactly those changes (setting the Observer's threshold to 2) and the milestone 4 and 5 chaos runs still passed, which is the safety claim in action. Then measure what you gave up: a leader change now needs 4 of 5 replicas up, so with two replicas down, no one can be elected at all, while a commit needs only 2 acceptors. What does that do to your client's time to completion when the nemesis crashes two replicas at once?
  • Map your code onto Raft. The table below is a reading guide, drawn from chapter 9's comparison. Then do the exercise: make your replica refuse to vote for a candidate whose log is behind, and refuse to accept a slot that would leave a gap behind it. Once leaders always hold every chosen entry and logs never have holes, the recovery loop in on_promise becomes unnecessary, and what remains is Raft. Which of your check's scenarios stop making sense?
  • Batching and pipelining windows. Right now every command is its own accept message and the leader never limits how many are in flight. Pack several commands into one slot; cap the number of outstanding slots. Measure messages per command.
  • Snapshots and log truncation. Your replicas keep every slot forever and re-apply from slot 1 after a restart. Persist a snapshot of the key-value store plus the slot it covers, forget older slots, and teach catch-up to send a snapshot when a follower is too far behind.
  • Linearizable reads without logging them. Reads go through the log, which is correct and slow. Read about leader leases (chapter 4) and add a read path that is safe only while the leader's lease holds. Then write the execution in which it returns a stale value if the lease is ignored.
  • Membership change. Add a replica to the cluster through the log itself. What goes wrong if the old and new configurations can each form a majority at the same time?

Distributed systems connection

You have now written, in about a hundred lines each, the three things the rest of the course treats as black boxes. The acceptor with durable state is what sits inside a coordination service (chapter 11) and under a consensus-backed database. The recovery loop is the real content of "the new leader catches up", and your table above shows that Raft makes it unnecessary by constraining who may win, rather than by changing the safety argument (chapter 10). The exactly-once state machine is the standard answer to "what if the client retries after a leader change", and you will meet the same trick, an at-least-once log plus an idempotent consumer, again in chapter 17. Finally the method is the point: a seeded simulator, a referee that watches the invariants from outside, a nemesis that crashes nodes at awkward moments, and a seed you can replay. That is the core of chapter 19, and Lab 7 builds it properly.

What you learned

  • An acceptor's state is a promised ballot and the proposal accepted per slot, and it must be durable. Promise needs >, accept needs >=, and the promise reports a copy of the past.
  • A proposer must adopt the value of the highest-ballot accepted proposal in its promises. Take another and the overwrite bug returns. Replies for old ballots must be ignored, and each acceptor counted once.
  • Paxos is always safe and is live only when the network lets one proposer finish. Randomized, growing backoff makes duels short; its cost shows up as wasted messages, not as wrong answers.
  • A promise names a ballot, so one phase 1 covers the whole log. A stable leader then needs one round trip per command.
  • A new leader recovers every slot from the promises: highest ballot wins, holes are filled with no-ops, and new commands start after the last recovered slot. A value that sat on a minority of acceptors may be discarded, but one that was chosen can never be lost, because majorities intersect.
  • Replicas apply the log strictly in slot order. Delivery is at least once, so the state machine deduplicates by client and sequence number, deterministically, to make the effect exactly once.
  • You can test a protocol with a seeded simulator, a referee that sees global truth, and failures injected at random. A failing seed is a complete bug report.

Check your understanding

Your proposer's phase 1 collects promises from a quorum. One reports ((1, 2), "X"), another reports ((1, 1), "W"), the third reports nothing. Your own value is "Y". What do you send in phase 2?

  1. "Y", because you hold the highest ballot of the round
  2. "X", the value with the highest ballot among the reports
  3. "W", because it was reported first by the oldest ballot
  4. Nothing: the reports disagree, so you must start over
Only the highest-ballot report can possibly have been chosen: ballot (1, 2) is a later attempt than (1, 1), and a proposer making it had to follow the same rule, so it already took into account anything chosen before it. Using your own value would risk overwriting a chosen one; disagreement between reports is normal and is resolved by ballot order.

A new leader finishes phase 1 and sees that the promises mention slots 1, 2, 3 and 5 but nothing for slot 4. What should it do with slot 4?

  1. Leave it empty, since nobody ever proposed anything there
  2. Start numbering its new commands at slot 4
  3. Ask the client that sent the lost command to resend it
  4. Propose a no-op in slot 4, so that the log has no holes and slot 5 can be applied
The state machine applies slots in order, so a hole at slot 4 would block slot 5 and everything after it. A no-op is a legitimate decision that changes nothing. Starting new commands at 4 would risk conflicting with a value that was chosen but that this leader did not hear about; recovery must cover slots up to the highest one anyone mentioned.

A client's request is chosen in slot 3, its leader crashes before replying, the client retries, and the same request is chosen again in slot 4. Where should the duplicate be suppressed, and why there?

  1. In the state machine, when applying: every replica sees the same log in the same order, so all make the same decision
  2. In the consensus layer, by refusing to choose a value twice
  3. In the network, by dropping duplicate messages
  4. In the client, by never retrying
Consensus must choose both: from its point of view they are two different proposals in two different slots, and it cannot know the retry is a repeat. The network cannot tell a retry from a duplicate, and a client that never retries loses requests when messages are lost. Applying is the one place that sees the final order, and it is deterministic, so replicas stay identical.

The Observer reports that your two-proposer run never chose two values, but the run sent thousands of messages before finishing. What does this tell you?

  1. The acceptor rules are wrong
  2. The adoption rule is missing
  3. Safety held, but the proposers probably duelled: add randomized, growing backoff
  4. The network dropped too many messages for Paxos to work
Safety (never two values) and liveness (finishing promptly) are separate properties. Paxos guarantees the first always and the second only when proposers stop interrupting each other. A pile of wasted messages with no violation is the signature of livelock that eventually broke, and backoff, or a single stable leader, is the remedy. Missing adoption or broken acceptor rules would show as violations.

Lab 7: Deterministic Simulation Testing

A replicated store passes every test you can think of by hand and still loses an acknowledged write once in a few dozen unlucky runs. In this lab you build the machinery that makes those runs findable: a whole cluster in one thread, driven by one seeded random number generator, with simulated time, a network that misbehaves and nodes that crash. You will search for a failing seed, replay it so exactly that two runs hash identically, shrink it to a handful of events, fix the bug, and then run thousands of seeds to see it stay fixed.

Why this lab matters

The hardest part of fixing a distributed-systems bug is seeing it happen again. A bug that needs a crash in a four-tick window after an acknowledgement shows up once a month in production and never on a laptop. Chapter 19 climbed the testing ladder to deterministic simulation; this lab is the top rung, built by you. It is the approach behind FoundationDB's unusual reliability (the case study), and it works for a toy for the same reason it works for a database: when everything random flows from one number, a failure is a number you can write on a sticky note.

What is given and what is yours

Given: kvstore.py, the replicated store under test (it has a subtle bug that you are asked to find, not read your way to); harness.py, the clients and the glue that runs a plan on your simulator; and linearize.py, a small linearizability checker (the same idea as Lab 3, copied in so that this lab stands alone). Yours, in starter.py: the simulator, the workload and fault generator, the history recorder and invariants, the seed search, the shrinker and the fix.

What you'll build

Six milestones, each building on the last:

  1. A deterministic simulator: a single-threaded event queue, a simulated clock, a seeded network with delay, drop, duplicate and partition, and node crash and restart with durable versus volatile state.
  2. A workload and fault generator: turn a seed into a plan, plain data: which client does what, when, and which nodes crash and restart. The store is given, and so is the bug.
  3. Recorder and checks: record the history clients observe, write an invariant that is checked after every event, and combine them into run_seed, a pure function from a seed to a verdict.
  4. Seed search and replay: find a failing seed, and prove the replay is byte-identical by comparing hashes of the trace, even across separate processes.
  5. Shrinking: reduce the failing plan to a minimal one, in which removing anything makes the failure go away.
  6. The fix and a soak: find out what the bug was, fix it, and run thousands of seeds without a failure.

The store under test

Three nodes, 0, 1 and 2, each hold a copy of every register (a key such as "x" with a value). It is a multi-writer form of the register protocol of Attiya, Bar-Noy and Dolev (1995), usually called ABD: the replicated-register cousin of the quorum systems from networking chapter 18. Any node can serve a client, and that node becomes the coordinator of the request. A value is stored together with a timestamp, and the higher timestamp wins.

Each node keeps its registers in memory and also saves them to its disk, so they survive a crash and restart. The nodes talk to the world through four calls on the simulator you write: send, set_timer, write_disk, and (for test instrumentation only) ghost, a dictionary that no real implementation would have. The nodes never read a clock or generate a random number themselves. That discipline is what makes simulation possible at all: every source of nondeterminism has to be a call you control.

Milestone 1: a deterministic simulator

The simulator is the world the nodes live in. Its heart is a priority queue of future events, each tagged with a time and a sequence number. Running a simulation is a loop: pop the earliest event, set the clock to its time, perform it. There is no sleep, so an hour of simulated timeouts costs the time it takes to pop the events, and nothing waits for a real network.

Randomness is handled the same way. The simulator owns one random.Random(seed). Every decision that could differ between two runs, such as a message's delay, whether it is dropped, whether it is duplicated, and how long a disk write takes, is a draw from it, in the order the events happen. Run the same plan with the same seed and you get the same draws, hence the same everything.

The rules

PartRule
EventsOne heap of (time, seq, kind, data). seq is a counter. run(until) pops events with time <= until, sets now to each event's time, handles it, and calls after_event() if given. schedule(delay, fn) calls fn() later and is not tied to a node.
Messagessend(src, dst, msg): with probability net.drop the message is lost; with probability net.dup a second copy is also sent; each copy gets its own delay randint(min_delay, max_delay), so messages reorder. Messages to oneself, and messages to or from a node added with client=True, are never dropped or duplicated.
DeliveryJudged when the message arrives: the destination must be up, in the same incarnation (life) it was in when the message was sent, and not in a different partition group from the sender. Otherwise the message is dropped, and logged.
Partitionspartition((0,), (1, 2)) cuts node 0 off from 1 and 2. Nodes in no group (clients) talk to everyone. heal() removes it.
Crashcrash(n): the node object is discarded (its memory is gone) and its incarnation number goes up, so every message, timer and disk write from its old life dies silently.
Restartrestart(n): build a new node with factory(n, sim, copy_of_durable) and call its on_start(). The new node sees only what reached the disk.
Diskwrite_disk(n, key, value, cb) reaches durable[n][key] after randint(*disk_delay) ticks, in the order issued, and then calls cb(). If the node crashes first the write is lost and cb never runs.
Tracelog(text) appends "{now} {text}" to a list. trace_hash() is the sha256 of all lines.

Common misconception

"If I seed the random generator, my simulation is deterministic." Necessary, not sufficient. Four things leak real-world nondeterminism into a simulation: the global random module (use only your own generator), real time (time.time()), hash() and iteration order of a set of strings (randomized per process by Python, see PYTHONHASHSEED), and id() or memory addresses printed in a trace. Milestone 4 checks for all of them by replaying in fresh processes.

The core: the queue, the network and the two kinds of lifetime.

def __init__(self, seed, net=None, disk_delay=(2, 12)):
    self.rng = random.Random(seed)
    self.net = net or DEFAULT_NET
    self.disk_delay = disk_delay
    self.now = 0
    self.ghost = {}                 # scratch space for test instrumentation (see KVNode._ack)
    self.nodes = {}                 # id -> live node object, or None while the node is crashed
    self.durable = {}               # id -> dict that survives crashes (what is on the disk)
    self.incarnation = {}           # id -> how many times it has crashed
    self.trace = []
    self._factories = {}
    self._clients = set()
    self._group = {}                # id -> partition group number
    self._disk_free = {}            # id -> time the disk finishes its last queued write
    self._queue = []
    self._seq = 0

def _push(self, delay, kind, data):
    heapq.heappush(self._queue, (self.now + delay, self._seq, kind, data))
    self._seq += 1

def run(self, until, after_event=None):
    while self._queue and self._queue[0][0] <= until:
        self.now, _, kind, data = heapq.heappop(self._queue)
        getattr(self, "_do_" + kind)(*data)
        if after_event is not None:
            after_event()

def send(self, src, dst, msg):
    lossy = src != dst and src not in self._clients and dst not in self._clients
    if lossy and self.rng.random() < self.net.drop:
        self.log(f"lost {src}->{dst} {msg}")
        return
    copies = 2 if lossy and self.rng.random() < self.net.dup else 1
    for _ in range(copies):
        delay = self.rng.randint(self.net.min_delay, self.net.max_delay)
        self._push(delay, "deliver", (src, dst, msg, self.incarnation[dst]))

def _do_deliver(self, src, dst, msg, incarnation):
    node = self.nodes[dst]
    if node is None or incarnation != self.incarnation[dst]:
        self.log(f"drop {src}->{dst} {msg} (destination down)")
    elif self._blocked(src, dst):
        self.log(f"drop {src}->{dst} {msg} (partition)")
    else:
        self.log(f"deliver {src}->{dst} {msg}")
        node.on_message(src, msg)

def crash(self, node_id):
    if self.nodes[node_id] is None:
        return
    self.nodes[node_id] = None
    self.incarnation[node_id] += 1
    self._disk_free[node_id] = 0
    self.log(f"crash {node_id}")

def restart(self, node_id):
    if self.nodes[node_id] is not None:
        return
    self._boot(node_id)

def write_disk(self, node_id, key, value, cb=None):
    lo, hi = self.disk_delay
    done = max(self.now + self.rng.randint(lo, hi), self._disk_free.get(node_id, 0))
    self._disk_free[node_id] = done
    self._push(done - self.now, "disk", (node_id, key, value, cb, self.incarnation[node_id]))

def _do_disk(self, node_id, key, value, cb, incarnation):
    if incarnation != self.incarnation[node_id]:
        self.log(f"disk write lost {node_id} {key}")
        return
    self.durable[node_id][key] = value
    self.log(f"disk {node_id} {key}")
    if cb is not None:
        cb()

The rest is bookkeeping: add_node and _boot, schedule, set_timer and its handler _do_timer, partition, heal, log and trace_hash. They are in solution.py.

Milestone 2: a workload and fault generator

A simulator with no one using it finds nothing. Someone has to decide what the clients do and what goes wrong, and that someone is you. Two design choices matter more than any detail.

The plan is data. generate_plan(seed) does not run anything. It returns a Plan: a tuple of client operations and a tuple of faults.

op    = (client, start, f, key, value, node)       # (1, 9, "read", "y", None, 2)
fault = (time, kind, arg)                           # (23, "crash", 1)   (69, "restart", 1)
                                                    # (196, "partition", ((2,), (0, 1)))   (239, "heal", None)

Because a plan is a list of small tuples, it can be printed, compared, stored in a bug report, and, in milestone 5, cut into pieces. If it were a closure or a function full of random calls, none of that would be possible. A client runs its operations in order, each at its start time or as soon as the previous one finishes; every write uses a fresh value, so any read can be traced back to the single write that produced it.

The faults decide what you can find. This is the part that needs judgement. Faults too rare and the bug hides; so frequent that every run is a disaster and you learn nothing about a minimal one. Roughly 15 to 40 percent of plans containing a crash, and a similar share a partition, is a good place to start. This is the knob that distinguishes "tested" from "tested hostilely" in the flight-simulator analogy of chapter 19: the simulator only breaks the system in ways its builder imagined.

Common misconception

"The plan generator should use the simulator's random generator, so there's one seed." It should not, for two reasons. The plan has to exist before the run, so it can be shrunk and re-run; and the simulator's draws, which depend on what the network does, must not be mixed with the plan's. Give the generator its own random.Random made from the seed, and avoid hash(seed): for a string it differs between processes.

One generator, about thirty lines:

def generate_plan(seed, n_clients=3, ops_per_client=6, horizon=220):
    rng = random.Random(f"plan:{seed}")             # a string seed is stable across processes
    fresh = itertools.count(1)
    ops = []
    for c in range(n_clients):
        t = rng.randint(0, 25)
        for _ in range(ops_per_client):
            key = rng.choice(["x", "y"])
            if rng.random() < 0.5:
                f, value = "write", next(fresh)
            else:
                f, value = "read", None
            ops.append((c, t, f, key, value, rng.randrange(3)))
            t += rng.randint(5, 35)
    faults = []
    for node in range(3):
        if rng.random() < 0.12:
            t = rng.randint(10, horizon)
            faults.append((t, "crash", node))
            faults.append((t + rng.randint(10, 60), "restart", node))
    if rng.random() < 0.3:
        t = rng.randint(10, horizon)
        lone = rng.randrange(3)
        others = tuple(n for n in range(3) if n != lone)
        faults.append((t, "partition", ((lone,), others)))
        faults.append((t + rng.randint(20, 80), "heal", None))
    faults.sort(key=lambda f: (f[0], f[1], str(f[2])))
    return Plan(tuple(ops), tuple(faults))

Milestone 3: recording, invariants, and one function from seed to verdict

When a run ends you need to decide whether it was right. There are two kinds of check, and they catch different things.

  • A history check looks at the system from outside, like a client: it records every operation with its invoke and return times and asks whether any legal sequential order explains them (linearizability; linearize.py does the searching). It needs no knowledge of the system's internals, and it can only complain when a client has seen something wrong.
  • An invariant looks from inside: a statement about the whole simulated cluster that must be true after every event. Only a simulator can do this, since it sees all nodes at one instant. It catches a problem the moment it exists, long before any client notices, and it often names the cause.

The Recorder receives invoke, ok and info calls from the clients (the same three outcomes as in Lab 3, minus fail) and returns linearize.Op objects. Timed-out writes become indeterminate (ret = INF); timed-out reads are dropped.

For the invariant, the store's acknowledgement path records a promise in sim.ghost["acked"]: (node, key) maps to the highest timestamp this node has acknowledged storing. The invariant to write is the one any storage system must keep: a node never forgets something it acknowledged. After every event, any live node must still hold a timestamp at least as high as every one it acknowledged. (A crashed node is skipped: it is not holding anything.)

Your task

Hints try without first
  • The recorder keeps a dict pending: process -> (f, key, value, call) and a list of finished linearize.Op(process, f, key, value, call, ret, indeterminate) objects. For a read, ok's value is what was returned.
  • operations() should include still-pending writes as indeterminate (the run may have ended with a client waiting).
  • durability: sim.ghost.get("acked", {}) maps (node_id, key) to a timestamp; sim.nodes[node_id] is the live node or None; a live node's registers are node.store, a dict key -> (timestamp, value). A missing key counts as kvstore.ZERO. Return a message string, or None.
  • run_plan raises InvariantViolation in the middle of a run if an invariant returns a message; the exception carries the simulator as .sim, so you can still read its trace.
  • Do the history check only if no invariant fired, with linearize.check_history(ops), which returns None or the name of a bad key.
Solution spoiler

The recorder is a dictionary and a list; the invariant is a loop; run_seed glues them together:

class Recorder:

    def __init__(self):
        self._pending = {}              # process -> (f, key, value, call time)
        self._done = []

    def invoke(self, process, f, key, value, time):
        self._pending[process] = (f, key, value, time)

    def ok(self, process, value, time):
        f, key, _, call = self._pending.pop(process)
        self._done.append(linearize.Op(process, f, key, value, call, time, False))

    def info(self, process, time):
        f, key, value, call = self._pending.pop(process)
        if f == "write":                # a read that timed out tells us nothing and changes nothing
            self._done.append(linearize.Op(process, f, key, value, call, INF, True))

    def operations(self):
        ops = list(self._done)
        for process, (f, key, value, call) in self._pending.items():      # never answered: same as a timeout
            if f == "write":
                ops.append(linearize.Op(process, f, key, value, call, INF, True))
        return ops

def durability(sim):
    for (node_id, key), ts in sim.ghost.get("acked", {}).items():
        node = sim.nodes[node_id]
        if node is None:
            continue
        have = node.store.get(key, (ZERO, None))[0]
        if have < ts:
            return f"node {node_id} acknowledged {key} at timestamp {ts} but now holds only {have}"
    return None

def run_seed(seed, node_factory=KVNode, plan=None, invariants=(durability,)):
    plan = plan if plan is not None else generate_plan(seed)
    recorder = Recorder()
    reason = None
    try:
        sim = run_plan(plan, seed, simulator_cls=Simulator, node_factory=node_factory,
                       recorder=recorder, invariants=invariants)
    except InvariantViolation as e:
        sim, reason = e.sim, f"invariant violated: {e}"
    ops = recorder.operations()
    if reason is None:
        bad = linearize.check_history(ops)
        if bad is not None:
            reason = f"history of key {bad!r} is not linearizable"
    return RunResult(seed, reason is None, reason, sim.trace_hash(), plan, sim.trace, ops)

Milestone 4: find the failing seed, replay it exactly

Now the payoff. find_failing_seed(seeds) runs seed after seed and returns the first RunResult that is not ok. Seeds are cheap: the reference runs about a thousand per second. The first failure on the given store appears within the first twenty seeds with the reference generator, and your own generator will find one at its own pace; if it takes more than a few thousand, your faults are too shy.

Finding a failure once is luck. The skill is replaying it: the seed is the whole report. To test that replay is real, not merely plausible, compare trace hashes. A trace hash is the sha256 of every line the simulator logged, so two runs share a hash only if every delivery, drop, timer, crash and disk write happened at the same time in the same order. This is a much stricter test than "same verdict".

Common misconception

"Running it twice and getting the same hash means it is deterministic." Within one process, many sources of non-determinism are constant: a string's hash(), the iteration order of a set of strings, an object's id() are all fixed for the life of the process, so two runs inside it agree. The check therefore also replays your seed in fresh processes with different PYTHONHASHSEED values, which is how Python randomizes string hashes, and demands the same hash. If it fails, something in your simulator or generator is leaking real-world nondeterminism, and the message says so.

Your task

Implement find_failing_seed(seeds, node_factory=KVNode, invariants=(durability,)) (return the first failing RunResult, or None) and replay_matches(seed, ...) (run twice; the same trace hash and the same verdict).

It prints the failing seed and the tail of its trace.

Hints try without first

  • If the fresh-process check fails, look for: hash(...) on a string; iterating a set or frozenset of strings; id() or the default repr of an object (it prints an address) in a log line; the global random module; time.time().
  • A dict is fine: since Python 3.7 it iterates in insertion order. A set of small ints is fine too, but sorting before you iterate costs nothing and removes the question.
Solution spoiler

Almost nothing, if the simulator is right:

def find_failing_seed(seeds, node_factory=KVNode, invariants=(durability,)):
    for seed in seeds:
        result = run_seed(seed, node_factory, invariants=invariants)
        if not result.ok:
            return result
    return None

def replay_matches(seed, node_factory=KVNode, invariants=(durability,)):
    a = run_seed(seed, node_factory, invariants=invariants)
    b = run_seed(seed, node_factory, invariants=invariants)
    return a.trace_hash == b.trace_hash and a.reason == b.reason

Milestone 5: shrinking

The failing plan has about twenty items: eighteen client operations and a few faults. Almost none of them matter. A person reading the trace would waste an hour. Shrinking (the term comes from property-based testing; the algorithm is delta debugging, Zeller and Hildebrandt) finds a minimal plan: try removing chunks of items, keep a removal if the run still fails, and refine until removing any single item makes it pass.

Because the plan is data and run_seed accepts a plan, the shrinker is a loop around two calls. Note what it does not change: the seed. Everything in the run that is random is re-drawn from the same generator, but the sequence of draws shifts when you remove an operation (one fewer message means every later message gets a different draw), so removing an item can make the failure vanish even if the item looked irrelevant. This is why shrinking is a search and not a calculation, and why the result is "1-minimal" (nothing can go) rather than "the smallest possible".

Analogy: the bug report that fits on a postcard

A good bug report says "log in, click Save twice, then reload". A bad one is a 40-page transcript of a whole afternoon. The first costs a developer ten minutes; the second may never get read. A shrinker writes the postcard for you by crossing out sentences from the transcript and re-checking that the bug still happens. Where it breaks down: a human crosses out sentences by understanding them; the shrinker understands nothing, it only keeps what it cannot delete.

Your task

Implement shrink(failure, node_factory=KVNode, invariants=(durability,)): given a failing RunResult, return the RunResult of a smaller plan that still fails with the same seed.

python3 check.py shows milestone 5 as ✔. For four failing seeds it requires: the result still fails; the same seed; every item came from the original plan; the result is at most about half the original size; it is 1-minimal, which the check verifies by running the plan again with each single item removed; the shrunk run replays with an identical hash; and at least one of the four shrinks to five items or fewer.

Hints try without first

  • The fast version removes a chunk of len(items) // parts items at a time, starting with parts = 2; after a success lower parts (not below 2); after a full pass with no success double it, until the chunk is one item.

Solution spoiler

Delta debugging in a dozen lines:

def shrink(failure, node_factory=KVNode, invariants=(durability,)):
    def fails(items):
        return not run_seed(failure.seed, node_factory, plan_from_items(items), invariants).ok

    items = plan_items(failure.plan)
    parts = 2
    while len(items) >= 2:
        chunk = max(1, len(items) // parts)
        for start in range(0, len(items), chunk):
            candidate = items[:start] + items[start + chunk:]
            if fails(candidate):
                items = candidate
                parts = max(parts - 1, 2)
                break
        else:
            if chunk == 1:
                break
            parts = min(len(items), parts * 2)
    return run_seed(failure.seed, node_factory, plan_from_items(items), invariants)

Milestone 6: fix the bug, then soak

Spoiler ahead

Before reading on, do your own diagnosis. Take the shrunk plan from milestone 5, print its trace, and read kvstore.py with the question "what happened to the value the invariant says was forgotten?" Then read the explanation below.

The shrunk plan for seed 13 has two operations and a crash with its restart, and the invariant fires at the moment of the restart: node 1 acknowledged storing a value for y, and now holds nothing. The trace shows node 1 receiving the store (at t=19, and a second copy at t=20), then crash 1 at t=23 with its acknowledgements already on the wire, the coordinator telling the client ok at t=26, and at t=27 two lines disk write lost 1 store. Open on_store in kvstore.py:

    def on_store_ack(self, src, rid):
        op = self.ops.get(rid)
        if op is None or op["phase"] != "store":
            return
        op["replies"][src] = True
        if len(op["replies"]) >= MAJORITY:
            del self.ops[rid]
            result = op["chosen"] if op["kind"] == "read" else None
            self.sim.send(self.id, op["client"], ("client_ok", rid, result))

    # ---------------------------------------------------------------- replica side

    def on_query(self, src, rid, key):
        ts, value = self.store.get(key, (ZERO, None))
        self.sim.send(self.id, src, ("query_reply", rid, ts, value))

    def on_store(self, src, rid, key, ts, value):
        if ts > self.store.get(key, (ZERO, None))[0]:
            self.store[key] = (ts, value)
        self.sim.write_disk(self.id, "store", dict(self.store))    # save to disk (lands a few ticks later)
        self._ack(src, rid, key, ts)

The node updates its memory, asks the disk to save a snapshot (which lands a few ticks later, per milestone 1), and acknowledges right away, without waiting. From that instant the node has promised the coordinator that the value is stored, but the only copy is in memory, and a crash in the next few ticks destroys it. A majority of acknowledgements is supposed to mean "this value will survive any minority of crashes". If those acknowledgements are not backed by disks, the quorum argument has nothing under it: a later read can meet only nodes that have forgotten the value, return the old one, and so violate linearizability. It can take two coincidences, which is why the history check alone needs thousands of seeds, while the invariant sees it at once.

Analogy: signing for a parcel you haven't picked up

A clerk signs "received" for a delivery the moment the courier arrives, then walks to the stockroom to put it away. If the building floods before the clerk gets there, the paperwork says the parcel was safe but it isn't. The sender, who relied on the signature, will not look again. Where it breaks down: the clerk can see the flood coming; a node cannot know a crash is two ticks away, which is why the only safe rule is to sign after the parcel is on the shelf.

The fix is to acknowledge only after the write has reached the disk. The simulator's write_disk takes a callback that runs when the write lands, and does not run it if the node crashed first. One more detail is easy to miss: the node must write and acknowledge even when the incoming timestamp is not newer, since a duplicate or retried store may be arriving while the original write is still in flight. Acknowledging such a duplicate from memory alone would be the same bug.

Solution spoiler

The fix is one line moved, and soak is a list comprehension:

class FixedKVNode(KVNode):

    def on_store(self, src, rid, key, ts, value):
        if ts > self.store.get(key, (ZERO, None))[0]:
            self.store[key] = (ts, value)
        self.sim.write_disk(self.id, "store", dict(self.store),
                            cb=lambda: self._ack(src, rid, key, ts))

def soak(seeds, node_factory=FixedKVNode, invariants=(durability,)):
    return [s for s in seeds if not run_seed(s, node_factory, invariants=invariants).ok]

  2. Search with the history check only. Run find_failing_seed(range(20000), invariants=()). In the reference, the first failing seed is 4700 (about 4,700 runs in, against seed 13 for the invariant).   3. Change the size of the window. The bug needs a crash while a disk write is pending, so the disk's speed matters. A bug whose window is a tick wide takes a lot of seeds, and that is the argument for running a simulation continuously.
  4. A test that never crashes. Set the probability of a crash in generate_plan to zero and rerun find_failing_seed(range(5000)). Nothing fails, and every seed passes against the buggy store. What does that tell you about the coverage of a test suite that passes?

Stretch goals

  • A second bug, from the other family: write a store with a leader and no lease check, so that after a partition the old leader keeps answering reads while a new one accepts writes, and find it with your own seeds. This is the "stale leader" bug of chapter 4 and chapter 10, and it needs election, which the given store avoids.
  • Make shrinking steadier: removing one operation changes every later random draw. Derive each message's randomness from (seed, source, destination, an occurrence counter for that pair) instead of one shared stream, and see how much smaller the shrunk plans get.
  • Shrink the values too: after dropping items, try moving each remaining fault earlier, shortening gaps between operations, and replacing node ids by smaller ones. A tidy minimal case is worth the extra loop.
  • Disk faults: add torn writes (a crash that lets only part of a snapshot land) and reads that return an error, as in the fsyncgate case. Which invariant breaks?
  • Buggify: let the store ask the simulator, at chosen points, "should I misbehave here?" (take longer, skip an optimisation, hit a rare branch) with a small probability. FoundationDB's simulation has a mechanism of this kind, called BUGGIFY.
  • Swarm testing: randomly turn fault types on or off per seed, so some runs have only partitions and some only crashes. Do you find more distinct failures?

Distributed systems connection

FoundationDB's team describes writing the database from the start so that the whole cluster, with its network and disks, runs inside a deterministic simulator, and credits that for finding bugs that would otherwise have shipped (Zhou et al., SIGMOD 2021; see the case study). What you built has the same skeleton: one thread, one seed, simulated time and network and disk, faults injected on purpose, invariants checked continuously, failures replayed and shrunk. The scale differs by orders of magnitude; the idea does not. It also connects to Lab 3: the check at the end of every run is the same Wing & Gong search, and without a replayable seed the stale read it finds would be a ghost.

What you learned

  • A deterministic simulation puts everything on one thread, behind a seeded generator and a priority queue of events, with time that jumps from event to event.
  • The network, the clock and the disk are interfaces. The simulated versions drop, delay, duplicate, partition and lose writes on command; the nodes never reach around them.
  • A crash discards memory and keeps the disk. An incarnation number kills the old life's messages, timers and pending disk writes.
  • A fault plan is data: easy to generate, print, compare and shrink. How hostile the generator is decides what can be found.
  • History checks see what clients see; invariants see everything. The invariant found the bug at once; the history check needed thousands of seeds.
  • Replay means identical traces, and the test of it is a hash compared across fresh processes, since hash(), set order and global random state leak in only across processes.
  • Shrinking by delta debugging turns a 20-item failure into a 4-item postcard. Nothing a node acknowledges may be lost, so acknowledge after the write lands: a quorum of promises is only as durable as the promises.

Check your understanding

Why is a message's fate (delivered or dropped) decided when it arrives, not when it is sent?

  1. It is faster to compute
  2. Because crashes, restarts and partitions that happen while the message is in flight must affect it
  3. Because the random generator needs a later time
  4. Because messages cannot be dropped at send time
A message travels for several ticks, and the world can change during the trip: the destination may crash, restart (a new life) or be cut off by a partition that began after the send. A simulator that decided at send time would let messages teleport through a partition or into a node that is down. Random loss is the only thing decided at send time here, and only to keep the order of random draws fixed.

A run passes twice in a row inside one process with identical trace hashes, but gives a different hash in a fresh process. What is the most likely cause?

  1. The simulated clock is too coarse
  2. Something depends on hash(), set iteration order or id(), which are fixed within a process but differ between processes
  3. The heap is not stable
  4. The random generator is not seeded
Python randomizes the hash of strings at start-up (the PYTHONHASHSEED setting), so anything derived from a string hash or from the order of a set of strings is stable inside a process and different outside it. An unseeded generator would typically differ between two runs in the same process; so would the heap if it was a problem. Replaying in fresh processes is the way to catch exactly this class of leak.

Which statement about the invariant a node never forgets what it acknowledged is correct?

  1. It can only be checked by looking at client histories
  2. It is checked after every simulated event, using information no client has, and it fails at the moment of the restart, not when a client later notices
  3. It proves the store is linearizable
  4. It only works if the network is reliable
The simulator sees every node at once, so it can compare what each acknowledged with what it now holds, immediately. That is also why it finds the bug sooner than the history check, which needs a client to read the lost value at the wrong time. Passing it does not prove linearizability; it checks one property the proof depends on.

A shrinker removes the write in a failing run and the run still fails. The shrunk plan has no write at all. What most likely happened?

  1. The bug does not need writes
  2. The failure changed: removing items shifts the random draws, and the run now fails for a different reason, so the shrinker follows a different bug
  3. The seed was lost
  4. Shrinking always works that way
"Still fails" is only a safe test if the failure is the same one. Removing items changes every later random draw, and it can also expose a different failure entirely (or an invalid one). Good shrinkers check that the reason is the same kind, or validate their candidates, as Lab 3's shrinker refuses to leave a read with nothing to read. This lab's checks verify the shrunk run still fails and nothing more, so look at the reason when you can.

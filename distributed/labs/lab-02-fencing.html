Lab 2: Leases & Fencing Tokens

In chapter 4 a perfectly correct-looking lock corrupted a file: a client took the lock, froze for longer than its lease, woke up, and wrote on top of the next holder's work. In this lab you build that disaster on purpose, in a simulator where it replays exactly, and then you close the gap in the only place it can be closed: the storage. You will write a lease-based lock service with a monotonic token, a client that believes its lease from its own clock, the fence at the storage, a drift-aware safety margin, and a leader whose log refuses a deposed leader.

Why this lab matters

"Only one worker may do X" is among the most common requirements in distributed systems, and the usual answer, a lock with an expiry, is the usual source of a very rare, very expensive bug. The bug appears only when a pause, a delayed packet or a clock error happens at exactly the wrong moment, so you will not find it by running the code twice. A deterministic simulator turns "rare" into "seed 1": you will see the corrupted file, then see the identical run with the fence on, then run hundreds of seeds of everything going wrong at once. The same idea is behind Raft terms, Paxos ballots and Kafka epochs, which is what milestone 5 shows.

Simulated time, so the bug is repeatable

Like Lab 1, everything runs in one process with a seeded random generator. Time is an integer number of milliseconds that the simulator advances; nothing sleeps. There is true time, which no node can see, and each node reads its own local clock, true time scaled by (1 + drift). A "freeze" is just a delay inserted at a named point in a client's code: the client's own clock keeps running while it is frozen, but its code does not, and that is the model of a stop-the-world garbage collection, a virtual-machine stall or a SIGSTOP. Chapter 1's vocabulary applies: this is a partially synchronous world where delays and pauses are usually small and occasionally enormous, and the lock service's safety must survive the enormous ones.

What you'll build

Five milestones (the fifth is optional):

  1. The lock service: acquire, renew and release with leases on the server's clock, and a token counter that only goes up.
  2. Pauses, drift and the unsafe naive lock: the client's idea of "my lease is still valid", an unfenced storage, and a scripted freeze that produces two believers and a lost update, the same way every time.
  3. Fencing: the storage remembers the highest token seen and refuses lower ones. Hundreds of chaotic seeds, no corruption.
  4. A client-side safety margin: the lease minus a drift bound. It removes the drift problem and leaves the pause problem standing.
  5. A leader's log: a "leader" that appends to a log using its term as the fence, so that a deposed leader's writes are refused.

The workload

Each client repeats: acquire the lock (or renew it when half the lease is gone), read the counter, do a little work, check that its lease is still valid, and write the value plus one. If the storage acknowledges the write the job is done; if the storage refuses, the client concludes it has lost the lock, drops its token and starts over. A correct system makes the final counter equal to the number of acknowledged writes. Any difference is a lost update: two clients both read 4, both wrote 5, and one increment vanished. The check also asks whether the storage accepted a stale write, meaning a write carrying a token lower than one the storage had already seen. That is the unmistakable footprint of a deposed holder.

Milestone 1: a lock service with leases and tokens

A lock that never expires is a trap: if the holder crashes, nobody can ever proceed. The fix, from chapter 4, is to make the lock a lease: a grant valid for a fixed term unless renewed. Think of a library book with a due date. The library need not know whether you are alive; it simply waits for the date. That is why leases make a lock service robust to crashes, and also why, in the next milestone, they are not enough.

Three rules define the service. First, a lease granted at time t with length L is valid for t ≤ now < t + L; at exactly t + L it is over, and the lock may be granted to someone else in the same instant. Second, every grant gets a fresh token strictly larger than any before it, even when the same client asks again, because a request already in flight carries the old token and must not be mistaken for a new holder's. Third, an expired lease cannot be renewed, even if nobody else has taken the lock yet. That last rule is a choice, not a law of nature: it keeps "expired" a decision the rest of the world can rely on. The service here is a single object, so its counter is trivially monotonic. In real life that counter must survive failover, which is where consensus enters (experiment 4 below shows what happens when it does not).

Hints try without first
  • The lock is free when not self.held(now). Note that "held" means now < expires, which is what makes now == expires count as expired.
  • Grant: increment last_token, remember it as the current token and the caller as holder, set expires = now + lease_ms, return the token.
  • Renew needs three things to hold: right client, right token, still valid. If any one fails return False and change nothing.
  • Release does not reset the counter. If it did, the next token would repeat an old one.
Solution spoiler 
def acquire(self, client, now):
    if self.held(now):
        return None
    self.last_token += 1
    self.holder, self.token = client, self.last_token
    self.expires = now + self.lease_ms
    return self.token

def renew(self, client, token, now):
    if self.holder == client and self.token == token and self.held(now):
        self.expires = now + self.lease_ms
        return True
    return False

def release(self, client, token, now):
    if self.holder == client and self.token == token and self.held(now):
        self.holder = None
        return True
    return False

Milestone 2: pauses, drift, and the unsafe naive lock

Now the clients. A client cannot see the server's clock or true time. All it has is its own clock and a rule that sounds airtight: my lease is valid until my clock reads (the time I sent the request) + (the lease length). Two details in that sentence are load-bearing, and both come from chapter 4. The count starts from the moment the request was sent, because the grant happened somewhere between sending and receiving and sending is the latest moment that is certainly earlier. And it uses the client's local clock, which may run fast or slow; a clock 10% slow reads 1,260 when true time is 1,400, so its owner thinks a 1,000 ms lease started at 300 is still valid.

In the scenario above, c0 does everything right. It checks its lease immediately before writing, and the check passes. Then it freezes for 1.3 seconds. The server's lease ran out at t = 1010; c1 acquired token 2, read, wrote four times. When c0 wakes, its code is exactly where it was: one line after "my lease is valid". It sends its write, and a storage that does not look at tokens accepts it. Chapter 4 called this a time-of-check to time-of-use race stretched across a network: the check and the write are two separate steps, and arbitrary time can pass between them. Nothing the client can do makes them one step.

Then implement the unfenced Storage.read and Storage.write: store what arrives and say yes. (You will add the fence in milestone 3, in the same two methods.) Do not touch the client's main loop; read it, it is short.

def on_grant(self, token, lease_ms):
    self.token = token
    self.lease_ms = lease_ms
    self.deadline = self.sent_local + lease_ms - self.margin

def on_renewed(self, lease_ms):
    self.lease_ms = lease_ms
    self.deadline = self.sent_local + lease_ms - self.margin

def lease_ok(self):
    return self.token is not None and self.local() < self.deadline

How long does a freeze have to be before it hurts? Not as long as the lease: the write has to arrive after the new holder has touched the storage. The line between "harmless" and "corrupt" is invisible to both clients, which is exactly why you cannot repair this in the client.

Milestone 3: fencing at the storage

Chapter 4's key move is to stop trying to guarantee that the old holder has stopped, and instead make its stale actions harmless. The lock service already hands out tokens that only increase. Now the client attaches its token to every request, and the storage remembers the highest token it has seen and refuses anything lower. It needs no clock and no idea why the sender was late. Chapter 4 calls the token a fencing token (the name was popularised by Kleppmann); Chubby calls its version a sequencer.

Where the comparison lives matters as much as the comparison. A check in the client leaves a gap before the write (the freeze); a check in a proxy still leaves the gap between proxy and storage; only a comparison performed by the storage as part of the write itself has no gap. In the lab that is automatic, since a storage method runs to completion in the simulator, but in a real system you would use a conditional update (UPDATE ... WHERE fence <= ?, compare-and-set, a conditional put).

Two details are easy to get wrong, and the check tests both. The test is "lower than", not "not higher than": the holder's own later requests carry the same token it was granted, so equal tokens must pass. And reads carry the token too. Without that, this interleaving corrupts data: the new holder reads the counter, the old holder's stale write lands, and then the new holder writes its computed value from the old read, silently erasing the old holder's increment. When the new holder's first read raises the bar to token 2, the old holder's write is refused.

Solution spoiler 
def admit(self, token):
    if token < self.max_seen:
        return False
    self.max_seen = token
    return True

def read(self, token):
    if self.fenced and not self.guard.admit(token):
        return False, None
    return True, self.value

def write(self, token, value):
    if self.fenced and not self.guard.admit(token):
        return False
    self.value = value
    return True

Milestone 4: a client-side safety margin

Before fencing, engineers reached for a cheaper tool: make the client stop early. If the lease is 10 seconds, treat it as 9.8, so that clock drift between holder and server cannot make two holders overlap. Chapter 4 works out the arithmetic. A clock's rate is within a factor (1 ± ρ) of true time, and the holder counts from its send time. The worst case is a slow client clock against a fast server clock: the client then keeps acting for up to T/(1−ρ) of real time, while the server may re-grant after only T/(1+ρ). The gap is about 2ρT. A write that passes the check also needs time to reach the storage, which must be added. The lab's formula, using the client-side margin only, is

margin = ceil( 2ρT / (1 + ρ) ) + ceil( (1 − ρ) · max_delay )

For a 10 s lease and 100 ppm drift the first term is 2 ms: cheap, as chapter 4 said. The lab uses a wildly pessimistic ρ = 5% so that the effect shows up in a few hundred runs: for a 1,000 ms lease and a 20 ms worst-case message delay the margin is 96 + 19 = 115 ms.

Hints try without first
  • Both terms round up: rounding down could leave a one-millisecond hole.
  • With rho = 0 and max_delay_ms = 0 the margin is zero, and it grows with both arguments.
  • You derived the first term above: the client believes the lease for at most T/(1−ρ) of real time, the server will re-grant after as little as T/(1+ρ). Shave the difference off the client's side: T − T(1−ρ)/(1+ρ) = 2ρT/(1+ρ).
Solution spoiler 
def safety_margin(lease_ms, rho, max_delay_ms):
    return math.ceil(2 * rho * lease_ms / (1 + rho)) + math.ceil((1 - rho) * max_delay_ms)
clock drift only (5%), no fencing, 300 seeds: 113 runs with a stale write accepted without a margin, 0 with a 115 ms margin
drift plus rare freezes (0.3% of steps): corrupted runs: no margin 157, margin only 63, margin + fencing 0

That is the whole argument of this milestone in two lines. A margin removes the failure you can bound (drift: 113 runs down to 0) and cuts the damage from the one you cannot (157 down to 63), but it cannot remove it, because a freeze after the check can be any length. Only fencing gets to zero. Margins are a good idea for liveness and efficiency (fewer wasted writes); they are not a substitute for the fence when the data matters. This is chapter 4's "efficiency lock versus correctness lock" distinction, in numbers.

Milestone 5 (optional): a leader whose log refuses a deposed leader

Leader election is a lock with a better name. "Who is the leader?" is "who holds the lease?", and the thing the leader does with the lease, replicating a log, must survive the old leader waking up from a pause. The pattern is exactly what you built: the leader's term is its fencing token, every append carries it, and the log refuses an append whose term is lower than one it has seen. Chapter 4 listed the family: a Raft term, a Paxos ballot, a Kafka leader epoch, a Chubby sequencer are all fencing tokens for a role that can move between machines.

The lab reuses the client and the lock service unchanged. The "election" is the lock service handing out the next term; the "followers" are one FencedLog. A leader reads the log's length (its first read announces the term) and appends the next entry number. The check demands entries 1, 2, 3, ... each exactly once, with terms that never go backwards.

A simplification worth naming

This is not Raft. Raft's terms are chosen by a majority vote rather than a central counter, its followers check the term and the previous log entry on every AppendEntries, and a leader needs a quorum of acknowledgements to commit. What the lab isolates is a single idea: a role that can move, a number that only goes up, and a receiver that rejects the old number.

Your task

Implement FencedLog.read(term) and FencedLog.write(term, entry) with the guard from milestone 3: refuse a lower term and leave the log untouched; otherwise record the term and read the length or append (term, entry).

Try it yourself: four experiments

  1. Off by one in the guard. In FenceGuard.admit change token < self.max_seen to token <= self.max_seen. Milestone 3 fails at once with "the same token again is fine (the holder keeps writing)". In a real system the same bug makes a healthy holder fence itself off on its second request. (In a SQL storage this is the difference between WHERE fence <= ? and WHERE fence < ?, an exercise from chapter 4.)
  2. Fence the writes but not the reads. Remove the guard from Storage.read. Milestone 3's unit test complains ("a stale READ is refused too"), and the chaotic runs show why: milestone 4's final experiment, margin plus fencing, found corrupted runs at seeds 58 and 254 on the reference with this change. Find seed 58 with python3 check.py 4 58 and read its timeline: the new holder read before the old holder's write landed, then wrote an answer computed from the stale read.
  3. Make the freeze shorter. Change the script's 1300 to 900 and rerun milestone 2's scenario (the numbers above say 950 is harmless). Then find the smallest freeze that corrupts. Why is there such a threshold, and why can neither client know which side of it they are on?
  4. Break the token source. A lock service that "fails over" to a replica that forgot its counter hands out token 1 a second time:

For a delayed packet instead of a frozen process, sudo tc qdisc add dev lo root netem delay 2s on loopback delays everything (remove it with sudo tc qdisc del dev lo root).

  • A conditional update: replace Storage by a small SQLite database and a single UPDATE ... WHERE fence <= ? statement (chapter 4 has the code), and run the scripted accident against it.
  • Optimistic versions instead of a lock: drop the lock service entirely and make each write "set value to v+1 only if the version is still v". Which of the lab's anomalies vanish, and what do clients do instead of waiting?

Distributed systems connection

This is the second half of the story Lab 1 started: failure detection (Lab 1) tells you whom to suspect; a lease turns that suspicion into a contract with a deadline; and a fencing token makes sure the suspected node cannot hurt you if the suspicion was wrong. Production lock services work this way. Chubby's paper (Burrows, OSDI 2006) describes sequencers, and ZooKeeper and etcd expose session-bound locks plus monotonic transaction ids or revisions you can use as tokens (chapter 11). The Redlock debate, in which Kleppmann argued that a time-based lock without fencing tokens is unsafe where correctness matters, is the same argument you just ran as an experiment. And milestone 5 is why a Raft leader that wakes from a pause cannot damage the log: its term is stale (networking chapter 20, Lab 6).

What you learned

  • A lock that must survive crashes has to expire, and a lease is a lock with an expiry. The service's rules are exact: valid for t < grant + length, a fresh higher token on every grant, no renewing of an expired lease.
  • A client's belief "I hold the lease" comes from its own clock, counted from the send time. It can be stale by an arbitrary amount, because freezes, slow packets and clock drift all open a gap between the check and the effect. Checking just before writing does not close it.
  • A storage that remembers the highest token seen and refuses lower ones turns that stale write into a harmless refusal, with no clocks involved. The comparison must be atomic with the write, and reads must carry the token too. Equal tokens pass.
  • A safety margin of roughly 2ρT plus the message delay removes the failures that clock drift causes and cuts the damage from freezes, but it cannot eliminate the freeze problem. Margins are for efficiency; fencing is for correctness.
  • The token generator must itself be monotonic across failures; otherwise the fence defeats nothing.
  • A leader's term is a fencing token. A log that rejects appends from a lower term is how a deposed leader that wakes from a pause is stopped, in Raft and elsewhere.

Check your understanding

c0's client code checks that its lease is valid and immediately afterwards a 15-second garbage-collection pause begins, before the write is sent. The lease was 10 seconds. Why does the check not protect the storage?

  1. The check used the wrong clock
  2. The check and the write are separate steps; the pause happens after the check, so the write goes out on an expired lease that the client no longer knows is expired
  3. Clients are not allowed to check their own leases
  4. The lock service should have extended the lease during the pause
This is a time-of-check to time-of-use race stretched across a network. No client-side care can make the check atomic with the effect at the storage, because arbitrary time may pass in between. In the lab, c0 passes its check at t = 80, freezes for 1,300 ms and its stale write is accepted at t = 1390.

In milestone 3 the new holder's first read carries its token as well, and the storage applies the guard to reads. What goes wrong if only writes are checked?

  1. Nothing: reads do not change data, so they cannot cause corruption
  2. Reads would be slower
  3. The old holder's stale write can land between the new holder's read and its write, and the new holder then writes a value computed from the stale read, erasing the old holder's update
  4. The lock service would issue the same token twice
A read that announces the token raises the storage's bar before the new holder computes anything, so a stale write can no longer slip in afterwards. Without it, the new holder's read-modify-write is based on data that the old holder is about to change. The check's fuzz found exactly such runs (for example seed 58) when the guard was removed from read.

A lease is 1,000 ms, the clocks may drift by 5%, and messages take up to 20 ms. You subtract a 115 ms margin on the client. Which claim is correct?

  1. It guarantees mutual exclusion even if clients freeze
  2. It removes overlap caused by clock drift, and reduces but cannot eliminate damage from a freeze after the check; only the storage-side fence removes that
  3. It makes fencing tokens unnecessary
  4. It only helps if the lock service also pads its own timer
The margin makes the slowest possible client clock stop before the fastest possible server clock re-grants. A freeze or a very slow packet after the check can be arbitrarily long, so no fixed margin covers it. In the lab: 113 stale-write runs with drift only fall to 0, but with rare freezes 157 corrupted runs only fall to 63, and margin plus fencing gives 0.

The lock service fails over to a replica that missed its last counter update and hands out token 1 a second time. The storage is fenced. What happens, and what does it show?

  1. The fence rejects the second holder, because tokens are compared as strings
  2. Both holders can write: with equal tokens the storage cannot tell them apart. The token source must be monotonic across failures, which means it must be a linearizable, durably replicated service
  3. The storage detects the failover and resets its highest-seen token
  4. Nothing, because a fence only checks the first write
A fence orders requests by token; if two holders present the same (or reversed) numbers, the order is lost. This is why real systems derive tokens from consensus-backed counters: Chubby sequencers, ZooKeeper transaction ids, etcd revisions.

Lab 3: A Linearizability Checker

In chapter 5 linearizability was a definition: a history is linearizable if there is a legal sequential order that respects real time. Here you turn the definition into a program that takes a recorded history and either finds that order or proves, by exhausting the possibilities, that none exists. Then you point it at two simulated stores and catch the one that serves stale reads, down to a counterexample of two operations.

Why this lab matters

Almost every database claims to be "consistent" and almost none can say what that means in a way you can test. A checker is how the claim becomes a test: run clients against the system, record what each saw, and ask whether any legal story explains it. This is the heart of Jepsen's Knossos checker, described in chapter 19, and you will write its core in about a hundred lines. The lab also teaches a habit worth keeping: when a checker says "no", the useful output is not "no", it is a short history a human can read.

Simulated stores, real histories

The two stores are plain Python objects driven by a seeded event queue with simulated time, so every history is reproducible from its seed: simulate(LaggingFollowerStore, 7) gives the same history every time you run it, on every machine. Nothing here uses threads or sockets. Requests and replies can be delayed or lost, and a lost reply produces exactly the awkward case a real tester faces: an operation that might have happened.

What you'll build

Five milestones, each building on the last:

  1. A history format: events with invoke, ok, fail and info, and a function that pairs them into operations with a call time and a return time. A timed-out operation gets no return time at all: it may take effect any time after it was invoked.
  2. A sequential model of a register: what read, write and cas do when they run one at a time. This is the "legal" in "a legal order".
  3. A brute-force checker: try every permutation that respects real-time order. Correct, obviously so, and useless beyond nine operations. It becomes the oracle for the next milestone.
  4. A Wing & Gong search with memoization: build the order from the front, only ever try operations nobody has to precede, and remember dead ends by (set of operations placed, model state). This scales to hundreds of operations.
  5. Catch a buggy store: run the checker on a correct single-leader store (it must always pass) and on one that reads from a lagging follower (it must be caught), then shrink a violating history to a minimal counterexample.

The history format

A history is the list of things the clients saw, in the order they happened. Every request becomes two lines: an invoke when the client sends it, and a completion when the client learns what happened. The completion says one of three things:

Event typeMeaningWhat the checker must assume
okThe operation took effect and the client saw the result.It happened, at some instant between its invoke and its ok. A read's value is what it returned.
failThe operation definitely did not take effect: an error reply, or a cas whose compare did not match.It never happened. Leave it out.
infoNo answer in time. A timeout, a lost reply, a crashed client.Unknown. It may have taken effect at any moment after its invoke, even long after the client gave up, or never.

The names ok, fail and info follow the convention of Jepsen. The third case is the whole reason testing distributed systems is hard: a timed-out write is concurrent with everything that comes after it, forever. A later read that sees its value is fine; a later read that does not see it is also fine; the checker must accept both.

Each event is a tuple Event(type, process, f, value, time), where f is "read", "write" or "cas" and process is the id of the client thread. One process has at most one pending operation. After a timeout the old request may still be in flight, so the simulated clients continue under a new process id, as Jepsen does. A cas carries (old, new) as its value and, because it succeeds only if the register holds old, an ok cas tells you the register held old at that instant.

The checker's input is not events but Op records: Op(id, process, f, arg, result, call, ret, indeterminate). call and ret are the interval during which the operation was in progress, and that interval is all that real time tells us. Two operations whose intervals overlap are concurrent: the system may order them either way. If one's ret is earlier than the other's call, the first must come first. This is the real-time constraint that makes linearizability stronger than sequential consistency.

Milestone 1: from events to operations with intervals

Pairing an invoke with its completion is easy; the interest is in the special cases. Study this picture of three processes:

In code, an indeterminate operation gets ret = INF (float("inf")) and indeterminate = True. That single number does the right thing in the real-time rule "a.ret < b.call means a comes before b": nothing is ever less than infinity, so nothing is forced to come after a timed-out operation, and the timed-out operation is forced after nothing but operations that returned before it was invoked. Two special cases to settle now:

  • A timed-out read returned nothing and changed nothing, so it constrains nothing. Drop it.
  • An invoke that never gets any completion (the run ended, the client died) is the same as a timeout.

Common misconception

"A timeout means the operation failed, so just ignore it." Run your checker on a correct store with timed-out writes treated as failures and it will raise false alarms: a later read sees the value of the write you pretended did not happen. In the experiments below you will count how often. The opposite shortcut, treating a timeout as a success at the moment of the timeout, is just as wrong for a real network, where a delayed request can still be applied long after the client gave up.

Raise ValueError for a process that invokes while it is still pending, for a completion with no invoke, and for a completion whose f differs from its invoke's.

Hints try without first
  • Keep a dict pending from process id to its invoke event and that event's position in the list. When a completion arrives, pop it.
  • Build each op when its completion arrives, then sort the finished ops by the position of their invoke and number them afterwards. That is how the ids come out in invocation order even though operations complete in a different order.
  • For a read the result is the completion's value; for a write or cas the arg is the invoke's value and result is None.

Solution spoiler

The conversion, with the three error cases:

def to_operations(events):
    pending = {}                                   # process -> (index of the invoke event, Event)
    made = []                                      # (invoke index, fields...) for the ops we keep

    def finish(index, inv, kind, ret, value):
        if kind == "fail":
            return
        if kind == "info":
            if inv.f == "read":
                return
            made.append((index, inv.process, inv.f, inv.value, None, inv.time, INF, True))
        else:
            result = value if inv.f == "read" else None
            made.append((index, inv.process, inv.f, inv.value, result, inv.time, ret, False))

    for i, e in enumerate(events):
        if e.type == "invoke":
            if e.process in pending:
                raise ValueError(f"process {e.process} invoked while it already has a pending operation")
            pending[e.process] = (i, e)
        else:
            if e.process not in pending:
                raise ValueError(f"process {e.process} completed an operation it never invoked")
            index, inv = pending.pop(e.process)
            if e.f != inv.f:
                raise ValueError(f"process {e.process} invoked {inv.f} but completed {e.f}")
            finish(index, inv, e.type, e.time, e.value)
    for index, inv in pending.values():            # never answered: same as a timeout
        finish(index, inv, "info", INF, None)
    made.sort(key=lambda m: m[0])
    return [Op(n, *m[1:]) for n, m in enumerate(made)]

Milestone 2: a sequential model of a register

Linearizability is always relative to a sequential specification: an object whose behavior, when operations are applied one at a time, is obvious. For a register that behavior is three sentences. A read returns the last value written (None before any write). A write replaces the value. A cas(old, new) replaces the value with new if and only if it currently equals old.

You model this as a function from (state, operation) to (legal?, new state). The checker will call it thousands of times, and it stores states in a set, so the model must be a pure function over hashable states. That purity is also what lets the same search code check a queue, a set, or a counter by swapping the model, which is exactly how Knossos works.

Common misconception

"The model knows about time." It does not. The model only knows "what happens if these operations run one after another in this order". All the timing lives in the search. Keeping the two apart is what makes the model four lines long.

Your task

Implement RegisterModel.init() (the state of a fresh register) and RegisterModel.step(state, op), returning (legal, new_state). For an ok cas, legal means the register holds old; a fail cas never reaches the model. An indeterminate read is always legal.

python3 check.py shows milestone 2 as ✔. It steps through every case: write, read legal and illegal, cas legal and illegal (state unchanged), an indeterminate read, a short replay, and checks that the new state is hashable.

Hints try without first
  • A fresh register holds None. It is also the value a read returns before any write, so reading None first is legal.
  • Return the old state when an operation is not legal: the search discards it anyway, but a stable answer makes your own debugging easier.
  • Unpack a cas as old, new = op.arg.
Solution spoiler

The whole model:

@staticmethod
def init():
    return None                                # a fresh register holds None

@staticmethod
def step(state, op):
    if op.f == "write":
        return True, op.arg
    if op.f == "read":
        return (op.indeterminate or op.result == state), state
    old, new = op.arg
    if state == old:
        return True, new
    return False, state

Milestone 3: brute force over permutations

Now the definition, translated word for word. A history is linearizable if some subset of its indeterminate operations (those that took effect) together with all the definite ones can be put in a sequence such that

  1. the sequence respects real time: if operation a returned before b was invoked, a comes before b; and
  2. replayed on the model from its initial state, every step is legal.

For n operations that is up to n! sequences, times 2k choices for k timed-out operations. Nine operations is already 362,880 orders. That is fine for a test oracle (it is simple enough to trust by reading it) and hopeless for a real history, which is why the function refuses more than nine.

Your task

Implement check_brute(ops, model=RegisterModel). Return a list of operation ids in a legal order, or None. Raise ValueError for more than 9 operations. An empty history is linearizable (return [], which is not None).

python3 check.py shows milestone 3 as ✔. It runs 18 hand-made histories: stale reads, new-old inversions, overlapping writes where either may win, cas, and timed-out writes that may or may not have taken effect. A returned order is verified by an independent checker inside check.py, so a wrong witness fails too.

Hints try without first
  • Split the ops into required (not indeterminate) and optional (indeterminate). Loop over every subset of optional with itertools.combinations, and over every permutation of required + subset with itertools.permutations.
  • Real time check: for every pair of positions i < j in the sequence, it is a violation if order[j].ret < order[i].call (the later-placed operation had already finished before the earlier-placed one started).
  • Replay: state = model.init(), then legal, state = model.step(state, op) for each op; any illegal step rejects this order.
  • Return None only after every subset and permutation has been tried. Do not forget the empty-subset case.
Solution spoiler

Three small functions:

def _respects_real_time(order):
    for i in range(len(order)):
        for j in range(i + 1, len(order)):
            if order[j].ret < order[i].call:
                return False
    return True

def _is_legal(order, model):
    state = model.init()
    for op in order:
        legal, state = model.step(state, op)
        if not legal:
            return False
    return True

def check_brute(ops, model=RegisterModel):
    if len(ops) > 9:
        raise ValueError("brute force is for small histories: at most 9 operations")
    required = [o for o in ops if not o.indeterminate]
    optional = [o for o in ops if o.indeterminate]
    for k in range(len(optional) + 1):
        for took_effect in itertools.combinations(optional, k):
            for order in itertools.permutations(required + list(took_effect)):
                if _respects_real_time(order) and _is_legal(order, model):
                    return [o.id for o in order]
    return None

Milestone 4: Wing & Gong search with memoization

Brute force wastes almost all of its time. It builds a whole sequence of nine operations before noticing that the second one was illegal. The fix, due to Wing and Gong (1993), is to build the sequence from the front and cut off a branch the moment it breaks a rule:

  1. Only try operations that may legally go next. Among the operations not yet placed, let h be the earliest ret of the required ones. Any operation called after h must come after the operation that returned at h, so it cannot go next. Candidates are exactly the unplaced operations with call <= h. If you keep the operations sorted by call, the candidates are a prefix of the unplaced ones, so a loop can stop at the first one that is too late.
  2. Check the model immediately. If a candidate read does not match the register, skip it. Do not build a sequence on top of an illegal step.
  3. Remember dead ends. Gavin Lowe (2017) noticed that what can happen next depends only on which operations are placed and what the model's state is, not on the order that got you there. If you reach a pair (set of placed operations, model state) a second time and it failed the first time, it fails again. Store failed pairs in a set.
  4. Stop when every required operation is placed. Indeterminate operations still unplaced simply never took effect.

Analogy: the maze with chalk marks

You are looking for a way through a maze with many corridors that lead to the same junction. Without marking anything you re-explore the same junction by every route that reaches it. With a piece of chalk you write "dead end" on the junction the first time you fail there, and from then on any route reaching it turns back immediately. The junction has to be identified by where you are and what you are carrying: here, the set of operations placed and the register's value. Where it breaks down: a real maze has a fixed number of junctions; here the number of junctions can still grow exponentially with the number of operations that overlap, which is why a history with hundreds of operations is fine only if few of them overlap at once.

The problem is NP-complete in general (Gibbons and Korach, 1997), as chapter 5 explained, so no memo can save a worst-case history. What it saves is the common case: real clients are sequential, and the number of operations in flight at once is small, so the number of reachable (set, state) pairs stays small.

Hints try without first
  • Represent the set of placed operations as an integer bitmask: bit i set means ops[i] is placed. done | (1 << i) adds one, and a pair (done, state) is hashable.
  • Sort the operations by call first (keep their ids). Then the loop over candidates can break as soon as op.call > horizon.
  • Compute horizon as the minimum ret over required operations not yet placed. When all required operations are placed you are finished, so there is always at least one.
  • The recursion returns the list of ids from this point on, or None. On None from every candidate, add (done, state) to the dead-end set before returning None.
  • Python's default recursion limit (1000) is fine for hundreds of operations; the given code raises it anyway.
Solution spoiler

The search. Everything that matters is in the loop over candidates and the dead set:

def check(ops, model=RegisterModel, stats=None):
    ops = sorted(ops, key=lambda o: (o.call, o.id))     # candidates are then a prefix of the list
    n = len(ops)
    required = 0
    for i, o in enumerate(ops):
        if not o.indeterminate:
            required |= 1 << i
    dead = set()                                        # (bitmask of linearized ops, state) known to fail

    def search(done, state):
        if done & required == required:                 # all required ops placed; the rest never happened
            return []
        key = (done, state)
        if key in dead:
            return None
        if stats is not None:
            stats["states"] = stats.get("states", 0) + 1
        # the earliest return time among required ops still to place: nothing called after it can go next
        horizon = min(ops[i].ret for i in range(n) if required >> i & 1 and not done >> i & 1)
        for i in range(n):
            if done >> i & 1:
                continue
            op = ops[i]
            if op.call > horizon:
                break
            legal, new_state = model.step(state, op)
            if legal:
                rest = search(done | 1 << i, new_state)
                if rest is not None:
                    return [op.id] + rest
        dead.add(key)
        return None

    return search(0, model.init())

Milestone 5: catch the lagging follower

Time to use the checker. Both stores are given. Open them in starter.py: each has one method, execute(f, arg), called at the instant a request reaches the server.

  • LeaderStore is correct. One leader holds the register, and every request is applied atomically at the moment it arrives, which is somewhere between the client's invoke and its reply. That moment is the operation's linearization point: the proof that the store is linearizable is the observation that the real-time order of the points matches the real-time order of the operations.
  • LaggingFollowerStore adds a follower. Writes go to the leader and are copied to the follower after a random lag of 5 to 40 ticks, in order. To "spread the load", half of all reads are answered by the follower. It is a plausible design, and exactly the bug of the lagging follower from chapter 5.

A violation found in a history of 150 operations is nearly useless to a human. Fortunately a violation almost always involves a few operations, and the rest are noise. So the second half of this milestone is shrinking: repeatedly delete operations while the history stays non-linearizable, until deleting any single one fixes it. The standard technique is delta debugging (Zeller and Hildebrandt): try removing big chunks first, and halve the chunk size when nothing can be removed.

A trap: shrinking into nonsense

Delete the write of 1 from "write(1) ok, then read returned 1" and what remains is a read of a value nobody wrote. That history is not linearizable, so a naive shrinker would happily accept the deletion, and keep going until it reached "a single read that returned 7". True, and useless: it is not the bug you were looking for, it is a bug you created. The given helper reads_are_explained(ops) says whether every value read (and every old value a cas expects) is either None or produced by a remaining write. Only accept a deletion if it passes. This is the same issue every shrinker faces: a shrunk input must still be valid, not merely still failing.

Your task

Implement find_violation(store_cls, seeds): run simulate(store_cls, seed) for each seed, convert with to_operations and check; return (seed, ops) for the first non-linearizable history, or None. Then implement minimal_counterexample(ops): return a sublist of ops that still fails, passes reads_are_explained, and from which no single operation can be removed.

Hints try without first
  • find_violation is a loop of three function calls. If it flags the correct store, the bug is in your checker or your conversion (usually how a timed-out write is treated), not in the store.
  • For the shrinker, start with the simple version: for each operation, try the history without it; if it still fails (and is explained), keep the smaller history and start over. Repeat until a full pass removes nothing.
  • Then make it fast: try removing a chunk of len(current) // parts operations at a time, starting with parts = 2; after a success lower parts, after a full pass with no success double it, until the chunk size is 1.
  • Use render(ops) to print what you found. A good counterexample reads like a sentence.
Solution spoiler

The search over seeds, then delta debugging:

def find_violation(store_cls, seeds):
    for seed in seeds:
        ops = to_operations(simulate(store_cls, seed))
        if check(ops) is None:
            return seed, ops
    return None

def minimal_counterexample(ops):
    def fails(candidate):
        return reads_are_explained(candidate) and check(candidate) is None

    current = list(ops)
    parts = 2
    while len(current) >= 2:
        chunk = max(1, len(current) // parts)
        for start in range(0, len(current), chunk):
            candidate = current[:start] + current[start + chunk:]
            if fails(candidate):
                current = candidate
                parts = max(parts - 1, 2)
                break
        else:                                           # nothing could be dropped at this granularity
            if chunk == 1:
                break
            parts = min(len(current), parts * 2)
    return current

Try it yourself: four experiments

  1. Turn off the memory. In solution.py comment out dead.add(key). Run python3 check.py solution and watch milestone 4 take far longer (or time out at 40 seconds). To see the size of the effect without waiting, count expanded nodes on eight concurrent writes followed by reads that see 1, then 2, then 1. With the memo the reference expands 1,026 nodes; with the memo disabled it expands 114,641, and the factor grows by roughly 8 for each extra write.
  2. Treat a timeout as a failure. In to_operations, drop info writes instead of making them indeterminate. The check on the correct store still passes for most seeds, but run it across 40 seeds yourself: in the reference setup, 24 of 40 correct-store histories are then flagged as violations, because some later read saw the value of a write you pretended never happened. What does the false alarm teach about the cost of an "unknown"?
  3. Make the bug rarer. Change the lagging follower's read probability from 0.5 to 0.02 and its lag from 5 to 40 down to 1 to 3. How many seeds does find_violation need now? A bug that appears in one run in a thousand is exactly why real tests run hours of random histories rather than one carefully chosen one.
  4. Weaken the rule. Change the candidate rule so that an operation may go next unless an unplaced operation of the same process was called earlier: only each client's own order counts, and real time between clients is ignored. You have just built a checker for something weaker than linearizability, the sequential consistency of chapter 5. Run the 18 hand-made histories through it: which flip from "no" to "yes", and what do they have in common?

Stretch goals

  • Many registers: add a key to every operation and check each key on its own. Linearizability is local: a history is linearizable if and only if each object's sub-history is, so a thousand keys become a thousand tiny searches (chapter 5, "Local versus global").
  • Another object: write a QueueModel (enqueue, dequeue) or a SetModel and run the same check unchanged. What does a "lost message" look like in a history?
  • Prune harder: a write whose value is never read cannot be proved or refuted by any read; try dropping such writes from the search, keeping only the interval constraints. Where does this stop being safe?
  • A witness, not just a yes: have check also return the deepest prefix it managed to build before failing, and print that next to the counterexample. Jepsen's reports do something like this, and it is how a human debugs.
  • Concurrency pressure: raise the number of clients in simulate to 20 and time the checker as the overlap grows. At what point does the memo stop being enough?

Distributed systems connection

You have written the core of a Jepsen-style checker: the generator, the clients and the nemesis are what chapter 19 added around it, and the Jepsen etcd case study shows the result on a real system. Notice what a "yes" means: this history has a legal order. It says nothing about the next history. That is why checkers are paired with randomized, fault-injecting generators and run for a long time, and why Lab 7 puts a linearizability check at the end of a deterministic simulation loop, so that a failing run can be replayed and shrunk instead of being a one-off ghost.

What you learned

  • A history is invoke events and completions: ok (happened), fail (did not), info (unknown). Converting it gives each operation an interval, and a timed-out operation's interval never ends.
  • Real time says only this: if one operation returned before another was invoked, it comes first. Everything else about order is the checker's choice.
  • Linearizability is relative to a sequential model. The model is a pure function from (state, operation) to (legal?, new state) and knows nothing about time.
  • Brute force over permutations is the definition made executable: simple enough to trust, exponential, and so a good oracle for testing the fast checker.
  • The Wing & Gong search extends a sequence only with operations that nothing else must precede, and memoizes dead ends by (set placed, model state), not by the set alone.
  • A "yes" is about one history. A "no" is only useful if it is small: shrink by deleting operations, but keep the history valid (reads must have something to read).
  • A store can pass a thousand plausible tests and still serve a stale read; a read from a lagging replica after a completed write is the classic violation.

Check your understanding

A write times out (an info event). How must the checker treat it?

  1. As a failed write: it never happened
  2. As a write that completed at the moment of the timeout
  3. As a write with no return time that may be placed anywhere after its invoke, or left out entirely
  4. As a read of the register
The client does not know whether the request reached the server, was applied, and had its reply lost, or was lost on the way. All three are possible, and a request delayed in the network could even be applied after the client gave up. The only safe model is an operation with an open-ended interval (ret = INF) that the search may include or omit. Treating it as failed raises false alarms when a later read sees its value; treating it as completed at the timeout raises false alarms when the effect lands later.

Why does the memo key contain the model's state as well as the set of operations already placed?

  1. To make the dictionary lookup faster
  2. Because different orders of the same operations can leave the register holding different values, and what can happen next depends on that value
  3. Because the model is not hashable otherwise
  4. Because indeterminate operations change the set
Place the same two writes in either order and the set is identical, but the register holds 2 in one case and 1 in the other. A read of 1 can finish the search in one of them and not in the other. Keying only on the set would wrongly reuse a failure from one state for the other. The pair (set, state) is what determines the future.

In the search, which unplaced operations may go next?

  1. Any of them
  2. Only the one with the smallest call time
  3. Those called no later than the earliest return time among the required operations still unplaced
  4. Those whose result matches the current register value
If operation b returned at time h, any operation called after h must come after b in every legal order, so it cannot be the next one placed while b is unplaced. Operations called at or before h overlap b, or precede it, so any of them could go first. The register-matching test is a second filter applied to each candidate, not what defines the candidates.

Your checker reports a 300-operation history of a database as linearizable. What can you conclude?

  1. The database is linearizable
  2. This history has a legal order consistent with real time, and nothing more: other histories might not
  3. The database is sequentially consistent but not necessarily linearizable
  4. The database has no stale reads under any workload
A checker can refute a claim but only ever supports it. One more history, with a longer partition or a different interleaving, could contain the violation. That is why systems are tested with many randomized, fault-injected runs, and why the checker is only useful alongside a generator hostile enough to provoke the bug.

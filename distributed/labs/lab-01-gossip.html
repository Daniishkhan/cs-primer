Lab 1: Gossip & Failure Detection

In chapter 3 you met the vocabulary of failure detection (completeness, accuracy, suspicion, incarnation) and the arithmetic of gossip (a rumour crosses a cluster in about log n rounds). In this lab you build the machinery: a simulated cluster with a lossy network and crashing nodes, a rumour that spreads by push gossip, a heartbeat detector that you will watch make mistakes, and a SWIM-style membership protocol that makes far fewer. Everything is deterministic, so every failure you find can be replayed.

Why this lab matters

Almost every action a cluster takes when something breaks (promote a replica, move shards, drop a node from a load balancer) is triggered by a failure detector, and every failure detector is wrong sometimes. You cannot feel that from the equations. Here you will see a 25-tick timeout accuse healthy nodes thousands of times, watch a frozen node get condemned and forgiven, and find out exactly which line of protocol stops a stale accusation from killing a live node. This is also the cheapest possible rehearsal for chapter 4: a detector is a hint, never a fact.

A simulated cluster, not a real one

All the nodes live in one Python process. The "network" is a priority queue of messages with delivery times; the "clock" is an integer you advance; every random choice comes from a seeded random.Random. There are no sockets and no threads, so nothing depends on your machine's speed and a failing seed fails the same way every time. That is the technique real distributed-systems teams use to test their protocols (chapter 19 and Lab 7 return to it). The cost is that the model is yours to get right: the simulator is where you decide what "slow", "lost" and "crashed" mean. Chapter 1 gave you the vocabulary, and the list below uses it.

What you'll build

Five milestones, each adding one idea (the fifth is optional):

  1. Gossip: a push-gossip node that spreads one rumour. Measure the rounds needed to reach everyone for growing n and compare the trend with log2 n + ln n.
  2. Heartbeats: an all-to-all detector with a fixed timeout. Measure false suspicions under loss and under a frozen node, and detection time after a real crash.
  3. SWIM: one random probe per period, indirect probes through k helpers, and a suspect state with its own timeout.
  4. Incarnations and dissemination: a suspected-but-alive node refutes with a higher incarnation number, and membership news rides piggyback on the pings and acks that exist anyway. Completeness and accuracy are checked over many seeds.
  5. Anti-entropy (optional): compare two replicas with Merkle trees and transfer only the key ranges that differ.

The given code in one page

Read Sim and Node in the file before milestone 1. Four ideas are enough:

  • Time is an integer in "ticks" (read them as milliseconds). A gossip round is 10 ticks, a SWIM protocol period is 100, and message delays are 1 to 5 ticks. So within one round a message sent at the start has arrived long before the next round begins, and the network can still reorder messages that were sent close together.
  • A node reacts, it never loops. It implements start(), on_message(src, msg) and on_timer(tag), and it acts by calling self.send(dst, msg) and self.set_timer(delay, tag). Messages are dicts with a "t" key.
  • Failures are scheduled events: sim.at(1000, lambda: sim.crash(3)) stops node 3 for good; sim.pause(i, ticks) freezes node i (everything addressed to it waits and arrives when it wakes, which is what a long garbage-collection pause looks like from outside); sim.block(a, b) breaks one link while every other link works. Sim(..., loss=0.05, dup=0.02) drops and duplicates messages.
  • Nodes report what they decide with self.report("suspect", 3). The checker reads that log to count mistakes and measure times. It never peeks at your internal state, apart from a few fields named in the docstrings.

Milestone 1: gossip and the log n estimate

Chapter 3 derived how an epidemic spreads. With push gossip, every informed node tells one random peer per round. While few nodes know, almost every message lands on a node that does not, so the informed count roughly doubles each round: about log2 n rounds to reach half the cluster. Then the end game begins: an uninformed node escapes all pushes in a round with probability about 1/e, so the uninformed fraction shrinks by a constant factor per round and the last stragglers take about ln n further rounds. Pittel's analysis (1987) makes this precise: log2 n + ln n + O(1) rounds with high probability. The idea itself comes from Demers and colleagues at Xerox PARC (1987), who borrowed the mathematics of disease spread to keep replicated databases in step.

The picture is the whole story. Notice what it says about cost: each node sends exactly one message per round, whatever n is, yet a million nodes need only about 34 rounds. And notice what the red curve says about failure: 30% message loss does not stop the rumour, it only stretches the doubling, because a lost push is just a push that did not help.

Your task

Implement GossipNode: start() arms a round timer; each round a node that knows the rumour sends {"t": "rumour"} to fanout different random peers (self.rng.sample) and re-arms the timer; a node that hears the rumour for the first time remembers informed_at = self.sim.now. Informed nodes keep pushing every round: they do not know who is still ignorant.

Milestone 2: a heartbeat detector with a fixed timeout

Now the question changes from "how does news spread" to "how do I notice that someone has stopped?". The simplest answer is the one from networking chapter 16: every node sends a heartbeat to every other node each period, and a node that has been silent for longer than a timeout is suspected. Chapter 3 gave the three numbers that judge such a detector (Chen, Toueg and Aguilera, 2002): the detection time, the mistake recurrence time (how often it accuses a live node) and the mistake duration. This milestone makes you measure two of them, and see that a single fixed timeout cannot win both.

Your task

Implement HeartbeatNode. Every HB_PERIOD ticks: re-arm the timer, send {"t": "hb"} to every peer, then for each peer that is not already suspected and has been silent for more than timeout ticks, add it to self.suspects and call self.report("suspect", peer). When a heartbeat arrives, record the time, and if you were suspecting the sender, forgive it with self.report("unsuspect", peer).

There is no timeout that is good at both; adaptive timeouts and phi accrual (chapter 3) move along this curve instead of fixing it. And a worse problem hides in the last line. A frozen node cannot tell that it was frozen: when it wakes, its own timers fire before the heartbeats that queued up have been processed, and it suspects all five peers. You will see this in an experiment below. This is why HashiCorp's Lifeguard extensions to SWIM teach a node to doubt itself first: if I am missing acks from everyone, perhaps I am the slow one.

Milestone 3: SWIM probing, ping-req and suspicion

All-to-all heartbeating costs n(n−1) messages per period; a 1,000-node cluster would spend 999,000 messages a second on liveness alone. SWIM (Das, Gupta and Motivala, 2002) keeps the work constant per node. In every protocol period a node picks one other member and pings it. If no ack comes, it does not accuse yet: it asks k other members to ping the target on its behalf (ping-req), because the trouble may be the path between prober and target rather than the target. Only when direct and indirect probes all fail does the prober mark the target suspect, and only if the suspicion goes unanswered for a suspicion timeout is the member declared dead.

Three design points are worth stating before you code them:

  • A single counter for probes and relays. A helper that relays an ack needs to remember who asked and which of the asker's sequence numbers to answer. The lab keeps self.relays[seq] = (origin, origin_seq, target) for that, with seq drawn from the same counter as your own probes, so an ack can be told apart at a glance.
  • Round-robin instead of pure random. The paper's analysis with fully random targets says a crashed member is probed within e/(e−1) ≈ 1.58 periods on average, but an unlucky member could be missed for many periods. The shuffled round-robin in next_target() (given) guarantees every member is probed at least once every n−1 periods. Completeness then does not depend on luck.
  • The suspicion timeout grows with log n. A refutation has to travel by gossip, and gossip takes about log n rounds; a timeout shorter than that would turn the suspect state into a no-op. The lab uses 3 * PERIOD * ceil(log2 n). Real implementations make this a tunable.

Two modes in one class

Milestone 3 runs with dissem=False: nobody tells anybody what they suspect. Each member relies on its own probes only, and a late ack from a suspect clears the local suspicion. Milestone 4 switches dissem=True, and then a late ack no longer clears a suspicion; only the suspect itself can, with a higher incarnation number. The given method _commit performs a state change and everything that follows from it (logging for the checker, starting the suspicion timer, queueing gossip), so your handlers stay about the protocol rather than the bookkeeping.

def on_period(self):
    target = self.next_target()
    self.probe = None
    if target is None:
        return
    self.seq += 1
    self.probe = {"target": target, "seq": self.seq, "acked": False}
    self.out(target, {"t": "ping", "seq": self.seq})
    self.set_timer(PING_TIMEOUT, ("ping_to", self.seq))
    self.set_timer(PROBE_END, ("probe_end", self.seq))

def on_ping(self, src, msg):
    self.out(src, {"t": "ack", "seq": msg["seq"], "subject": self.id})

def on_ping_req(self, src, msg):
    self.seq += 1
    self.relays[self.seq] = (src, msg["seq"], msg["target"])
    self.out(msg["target"], {"t": "ping", "seq": self.seq})

def on_ack(self, src, msg):
    subject = msg["subject"]
    if not self.dissem and self.members[subject][0] == "suspect":
        self._commit(subject, "alive", self.members[subject][1])
    if msg["seq"] in self.relays:
        origin, origin_seq, target = self.relays.pop(msg["seq"])
        self.out(origin, {"t": "ack", "seq": origin_seq, "subject": target})
    elif self.probe and msg["seq"] == self.probe["seq"]:
        self.probe["acked"] = True

def on_ping_timeout(self, seq):
    p = self.probe
    if p is None or p["seq"] != seq or p["acked"] or self.k == 0:
        return
    helpers = [x for x in self.peers if x != p["target"] and self.members[x][0] != "dead"]
    for h in self.rng.sample(helpers, min(self.k, len(helpers))):
        self.out(h, {"t": "ping-req", "seq": seq, "target": p["target"]})

def on_probe_end(self, seq):
    p = self.probe
    if p is None or p["seq"] != seq or p["acked"]:
        return
    state, inc = self.members[p["target"]]
    if state == "alive":
        self._commit(p["target"], "suspect", inc)

def on_suspect_timeout(self, subject, inc):
    state, cur = self.members[subject]
    if state == "suspect" and cur == inc:
        self._commit(subject, "dead", inc)

This matches the formula in chapter 3: a direct ping-ack round trip fails with probability 1−(1−p)2 ≈ 9.75% at p = 5%, and each helper path, which needs four messages, fails with probability about 18.5%. Remember the caveat that the independence assumption hides: if the target is the problem (frozen, overloaded), every path fails together, and no k helps.

Milestone 4: incarnation numbers and piggybacked news

Milestone 3 has two gaps. First, when member B is suspected, only the prober knows; everyone else has to find out for itself, one probe at a time. Second, nothing lets a live B deny the accusation: a frozen node that wakes up just before its death sentence can only hope a late ack arrives in time. Both gaps are closed by one mechanism: membership updates, of the form (subject, state, incarnation), carried on messages the protocol sends anyway.

The incarnation number is a per-member counter that only that member may raise. It orders B's own history, which gossip (arriving in any order) cannot do. The rules, from chapter 3, say which of two pieces of news about the same member wins:

New newsbeats current "alive @ j"beats current "suspect @ j"
alive @ iif i > jif i > j
suspect @ iif i ≥ jif i > j
deadalwaysalways

Remove any row and a counter-example appears; the check tries each one. If "alive beats suspect" needed only i ≥ j, the old alive @ 0 sent before the accusation could clear it, and a node could be accused and absolved by the same stale message; if "suspect beats alive" needed i > j, an accusation made at the node's current incarnation could never take effect. The refutation is the self-rule: a node that hears suspect(me, i) with i at least its own incarnation commits alive(me, i+1) and lets that spread.

Dissemination is just a queue with a counter. Every update waits in a buffer with the number of times it has been sent; each outgoing message carries up to MAX_PIGGY updates, those sent the fewest times first, and an update leaves the buffer after about 3·log2(n+1) sends. That is the infection-style dissemination of chapter 3: each update is a small epidemic with a bounded number of retransmissions, so the load per member stays constant while the news still reaches the group with high probability.

def apply_update(self, subject, state, inc):
    if subject == self.id:
        if state == "suspect" and inc >= self.members[self.id][1]:
            self._commit(self.id, "alive", inc + 1)
            return True
        return False
    cur_state, cur_inc = self.members[subject]
    if cur_state == "dead":
        return False
    if state == "dead":
        win = True
    elif state == "alive":
        win = inc > cur_inc
    else:
        win = inc > cur_inc if cur_state == "suspect" else inc >= cur_inc
    if win:
        self._commit(subject, state, inc)
    return win

def queue_update(self, subject, state, inc):
    self.buf[subject] = [state, inc, 0]

def piggyback(self):
    chosen = sorted(self.buf.items(), key=lambda kv: (kv[1][2], kv[0]))[:MAX_PIGGY]
    updates = []
    for subject, rec in chosen:
        updates.append((subject, rec[0], rec[1]))
        rec[2] += 1
        if rec[2] >= self.retransmit:
            del self.buf[subject]
    return updates

def absorb(self, updates):
    for subject, state, inc in updates:
        self.apply_update(subject, state, inc)

Completeness does not depend on gossip luck

Notice what rescues a member that never hears the "dead" rumour: its own round-robin probe reaches the crashed node within n−1 periods, fails, suspects, and times out on its own. That is exactly the split the SWIM paper makes. Detection gives strong completeness by itself; dissemination only makes agreement faster. Accuracy, on the other hand, is a probability, not a guarantee: no protocol can promise that a live node is never declared dead (chapter 1), only make it very unlikely and make a mistaken verdict cheap to recover from.

Milestone 5 (optional): anti-entropy with a Merkle tree

Rumours are quick, but they are not a guarantee: with small probability a node never hears one. Real systems pair them with anti-entropy: from time to time two replicas compare their state and repair the differences. Comparing millions of keys one by one is hopeless, so replicas compare summaries first. A Merkle tree (Ralph Merkle's hash tree) hashes each key range at the leaves and each parent from its children; if two roots are equal the replicas are identical, and if not, you descend only into the children whose hashes differ.

Your task

Implement three pieces in the file: MerkleTree.__init__ (bucket every key with the given bucket_of, hash each bucket's sorted items, then hash pairs upward until one root remains), diff_buckets(a, b) (walk down from the roots comparing hashes, descending only on a mismatch; return the differing leaf numbers and the number of hash comparisons), and sync(ra, rb) (exchange only the differing buckets in both directions and keep the entry with the higher version).

python3 check.py 5 shows milestone 5 as ✔. Identical replicas must cost exactly one comparison and zero keys. Over 100 random scenarios with 4,000 keys, up to a dozen differences (stale values, missing keys, newer values on either side, a key only one replica has), the replicas must converge, use at most about 2 hash comparisons per level per difference, and send no more than a quarter of the keys.

Hints try without first
  • Hash the repr of the sorted items list so that equal contents give equal hashes on both sides. Python's built-in hash() changes between runs, so use hashlib (there is a helper _h).
  • The number of buckets is a power of two, so every level has half as many nodes as the one below. levels[0] is the leaves; levels[-1] is [root].
  • A recursive walk(level, index) is the clearest: count a comparison on entry, return if equal, record the leaf at level 0, otherwise recurse into 2*index and 2*index + 1.
  • Ties on version: pick one deterministic winner (the lab uses the larger repr of the value) so that both sides end identical.
Solution spoiler 
def __init__(self, data, buckets=BUCKETS):
    self.buckets = buckets
    self.items = [[] for _ in range(buckets)]
    for key, (value, version) in data.items():
        self.items[bucket_of(key, buckets)].append((key, value, version))
    level = []
    for b in range(buckets):
        self.items[b].sort()
        level.append(_h(repr(self.items[b])))
    self.levels = [level]
    while len(level) > 1:
        level = [_h(level[i] + level[i + 1]) for i in range(0, len(level), 2)]
        self.levels.append(level)

def diff_buckets(a, b):
    found = []
    count = 0

    def walk(level, index):
        nonlocal count
        count += 1
        if a.levels[level][index] == b.levels[level][index]:
            return
        if level == 0:
            found.append(index)
            return
        walk(level - 1, 2 * index)
        walk(level - 1, 2 * index + 1)

    walk(len(a.levels) - 1, 0)
    return sorted(found), count

def sync(ra, rb):
    ta, tb = MerkleTree(ra.data), MerkleTree(rb.data)
    diff, comparisons = diff_buckets(ta, tb)
    sent = 0
    for bucket in diff:
        mine = {k: (v, ver) for k, v, ver in ta.items[bucket]}
        theirs = {k: (v, ver) for k, v, ver in tb.items[bucket]}
        sent += len(mine) + len(theirs)
        for key in set(mine) | set(theirs):
            options = [e for e in (mine.get(key), theirs.get(key)) if e is not None]
            best = max(options, key=lambda e: (e[1], repr(e[0])))
            ra.data[key] = best
            rb.data[key] = best
    return {"comparisons": comparisons, "buckets": len(diff), "keys_sent": sent}

Try it yourself: four experiments

  1. Break the incarnation rule. In apply_update change win = inc > cur_inc (the alive case) to inc >= cur_inc. Milestone 4 fails immediately with alive(1, 0) must NOT beat suspect(1, 0): it needs i > j. Now think about what the cluster would do with that bug: which messages could un-suspect a node without the node's consent?
  2. Take away the helpers. Run the milestone 4 accuracy scenario (16 nodes, 5% loss, 200 periods) with k=0. On the reference solution a live node was declared dead in 80 of 80 seeds (with k=3: 0 of 80), and the log held 169,398 suspicion events instead of 1,725. Refutation alone is not enough: about one probe in ten falsely accuses someone, and the accusations and refutations flood the piggyback budget. Print len(node.buf) during a run: on the reference it averaged 15.5 waiting updates per node for k=0 and 0.0 for k=3, against only MAX_PIGGY = 4 slots per message, so refutations queue behind accusations and miss the suspicion timeout. Why do the helpers protect the dissemination channel and not only the detector?
  3. Shorten the suspicion timeout by setting SUSPECT_MULT = 0.2. Accuracy collapses: live nodes are declared dead before a refutation can travel. This is why the suspicion timeout must scale with how long gossip takes.
  4. Gossip with pull. Add a pull flavour to GossipNode: each round, an uninformed node asks one random peer "anything new?" and an informed peer answers. Measure rounds against push at n = 1,000. Chapter 3 predicts a slow start and a very fast end game. Try push-pull too.

Distributed systems connection

What you built is the membership layer of real systems: HashiCorp's Serf and Consul use a SWIM implementation (memberlist) for exactly this job, and Dynamo-style stores use Merkle trees to repair replicas. The rule of thumb to carry forward is the one chapter 3 ends on: a failure detector gives a suspicion, not a verdict, and a node you have condemned may still be running. Lab 2 is the other half: it shows what to do about the condemned node that does not know it, by making the resource itself refuse it. Later, Raft's election timeout (networking chapter 20) turns out to be this same detector, and Lab 3's linearizability checker will judge what such systems promise.

What you learned

  • Push gossip informs everyone in about log2 n + ln n rounds, using one message per node per round, and loss or crashes slow it down without stopping it.
  • A heartbeat detector with a fixed timeout trades detection time against false suspicions, and no single timeout wins both. A frozen node is accused by everyone, and wrongly accuses everyone on waking.
  • SWIM keeps the probing load constant per member: one ping per period, k indirect probes if it fails, and a suspect state between "alive" and "dead". Indirect probes make link trouble cheap; they cannot help when the target itself is unreachable.
  • An incarnation number, raised only by its owner, orders a member's own history. With the override rules, a stale accusation can never beat a fresh denial however late gossip delivers it.
  • Piggybacking membership news on pings and acks keeps load constant. Completeness comes from the probing itself; dissemination only speeds up agreement. Accuracy is a probability bound, not a guarantee.
  • Anti-entropy with Merkle trees finds the differing key ranges in about 2 log2 L comparisons per difference and transfers only those ranges.

Check your understanding

Push gossip with fan-out 1 spreads a rumour through 1,000 nodes. About how many rounds does it take, and where does the time go?

  1. About 1,000 rounds: one new node per round
  2. About 17 to 19 rounds: roughly 10 rounds of doubling to reach half the cluster, then several more rounds to reach the last stragglers
  3. About 3 rounds, because every node tells someone each round
  4. About 1 round, because the network delivers all messages at once
While few nodes know the rumour, almost every push lands on a new node, so the informed set doubles: about log2 1000 ≈ 10 rounds to reach half. In the end game an uninformed node escapes a round's pushes with probability near 1/e, so the remaining fraction shrinks only by a constant factor per round, which costs about ln n ≈ 7 more. The lab measured 17 to 19.

You run the heartbeat detector with timeouts 25, 40 and 70 ticks on a lossy link. Which pattern did the measurements show?

  1. A longer timeout gave more false suspicions and faster detection
  2. The timeout did not matter once loss was below 50%
  3. A longer timeout gave far fewer false suspicions but slower detection of a real crash
  4. A longer timeout gave fewer false suspicions and also faster detection
False suspicions come from gaps between heartbeats that exceed the timeout, so a longer timeout removes most of them (4,830, 229, then 2 in the lab). Detection time is roughly the timeout plus one period, so it grows with the timeout. That is the trade-off of a fixed timeout; adaptive and accrual detectors move along the curve instead of escaping it.

The link between live nodes A and B is broken but both are healthy. Why does SWIM with k = 3 not even suspect B, and what situation could still defeat it?

  1. A asks three helpers to ping B over their own paths; one working path is enough to clear B. It fails when B itself is frozen or overloaded, because then every path to B fails together
  2. A ignores missing acks from members it has talked to before; it fails when A has never talked to B
  3. The helpers vote and the majority decides; it fails when fewer than three nodes are alive
  4. A switches to a different protocol after the first failure; it fails when the cluster is large
A direct ping crosses the broken link, but a ping-req goes A to helper to B, using different links. SWIM suspects only when the direct probe and all indirect probes fail. The independence assumption breaks when the problem is B (a long pause, an overloaded process): then no path works and the suspicion is, from the outside, indistinguishable from a crash.

Node B refuted a suspicion with alive(B, 1). Afterwards a slow copy of suspect(B, 0) reaches a member that already knows alive(B, 1). What happens, and why is the incarnation number essential?

  1. The member marks B suspect again, because the most recently received message wins
  2. The member ignores the stale accusation: alive at a higher incarnation beats suspect at a lower one, and only B can raise B's incarnation, so no old accusation can ever beat B's newest denial
  3. The two messages cancel and B is removed from the group
  4. The member asks B to repeat its refutation with a higher number
Gossip delivers news in any order, so "latest received" is meaningless. The incarnation number gives B's own history a total order that anyone can compare, and because only B increments it, nobody can forge or reorder a denial. Without it, stale accusations would flip live nodes in and out of suspicion, or evict them.

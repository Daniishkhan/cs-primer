Lab 6: CRDTs That Converge

Chapter 15 showed that if the merge of two replicas' states is the join of a semilattice, then replicas that merge in any order, any number of times, with duplicates and delays, end up identical, with no coordination at all. A proof is reassuring but a counterexample is what you meet in practice: a merge that is almost commutative, a tie that two replicas break differently, a remove that quietly un-removes. In this lab you build the standard CRDTs (counters, registers, the observed-remove set), then you build the thing that finds the bugs in them: a randomized tester that throws operation sequences, reordered and duplicated deliveries and shuffled merge orders at three or four replicas, and prints the seed and the smallest operation list that still breaks a property. Finally you build a shopping cart out of your pieces.

Why this lab matters

CRDTs are the one tool in coordination avoidance that you can hold in your hands: data structures designed so that concurrent updates need no lock, no leader and no consensus. They run inside collaborative editors, offline-first apps, shopping carts and some databases. But a CRDT is only correct if its merge obeys three algebraic laws exactly, for every possible pair of states, and "it looked right on the examples" is how convergence bugs reach production. The craft of this lab, writing the type and writing a property test that tries to break it, with an oracle and a shrinker, is the craft of building them for real.

Replicas in one process, a network of copies

A replica is a Python object. "Sending" a state copies the object into an in-flight pool; "delivering" merges a copy into another replica, maybe much later, maybe twice, maybe after a newer one. There are no threads, sockets or clocks, and everything is seeded, so seed 17 gives the identical schedule every time. Python 3.8 or newer, standard library only. All types here are state-based CRDTs; see chapter 15 for operation-based and delta variants (the delta idea comes back under “Look under the hood”).

What you'll build

Five milestones:

  1. Counters: a G-Counter (grow-only, one slot per replica, merge = entry-wise maximum) and a PN-Counter built from two of them.
  2. Registers: a last-writer-wins register ordered by (timestamp, replica id), and a multi-value register that uses version vectors to keep concurrent writes as siblings.
  3. The OR-Set: add-wins, with a unique tag per add and a remove that only kills the tags it has seen.
  4. Property tests: random operation sequences on 3 or 4 replicas, random merge orders, duplicated and reordered deliveries. All replicas converge to the oracle's value, and merge is commutative, associative and idempotent. Failures print the seed and the minimal operation list.
  5. An application: a shopping cart built only from these types, plus a 2P-Set to show, by running it, the “can't re-add” limitation the OR-Set fixes.

The contract: a join semilattice

You met this in chapter 15; here it is as a test specification. Every class has merge(self, other) that returns a new replica holding the join of the two states, and the check holds it to five rules, for every pair or triple of states it ever sees:

LawIn symbolsWhat breaks without it
Commutativea ⊔ b = b ⊔ athe order messages arrive in changes the result: replicas diverge
Associative(a ⊔ b) ⊔ c = a ⊔ (b ⊔ c)merging through an intermediate replica gives a different answer from merging directly
Idempotenta ⊔ a = aa duplicated message corrupts the state (the classic: a merge that adds)
Upper bound(a ⊔ b) ⊔ a = a ⊔ ban old state delivered late drags the result backwards
Pureinputs unchangeda snapshot "in flight" would change under its sender; replicas would share state

Common misconception: "merge applies the other replica's operations"

These are state-based CRDTs. A merge combines two states; it does not replay anything, and it must give the same answer however many times and in whatever order the same states are combined. If your merge for the counter says total += other.total, it applies the other replica's history again each time the same message is delivered. That is the first bug the check plants in your code, and the shrinker reduces it to a single increment.

Milestone 1: counters

A shared counter that anyone can increment without asking is the "hello world" of CRDTs, and it is a good place to see why a single integer does not work. Two replicas both at 5 each add 1; each sends its 6 to the other. What is the merged value: 6 (maximum) or 12 (sum)? Neither is right (the answer is 7), and a lone integer cannot tell you. The G-Counter fixes it by giving every replica its own slot: counts[rid] is how many increments that replica has done. A replica only ever increases its own slot; the value is the sum; and the merge takes the maximum per slot, which is safe because a slot only ever grows and its owner is the only writer.

Counting down is not monotone, so it cannot live in the same structure. The PN-Counter keeps two G-Counters, one for increments and one for decrements, and defines its value as the difference. Both halves only grow, so the pair merges component-wise.

class GCounter(CRDT):
    """Grow-only counter.  counts[rid] = how many increments replica `rid` has done."""

    def __init__(self, rid):
        super().__init__(rid)
        self.counts = {}

    def state(self):
        return tuple(sorted((k, v) for k, v in self.counts.items() if v))

    def increment(self, n=1):
        if n < 0:
            raise ValueError("a G-Counter only grows")
        self.counts[self.rid] = self.counts.get(self.rid, 0) + n

    def value(self):
        return sum(self.counts.values())

    def merge(self, other):
        out = GCounter(self.rid)
        for k in set(self.counts) | set(other.counts):
            out.counts[k] = max(self.counts.get(k, 0), other.counts.get(k, 0))
        return out

class PNCounter(CRDT):
    """Counter that can go down: two G-Counters, one for increments and one for decrements."""

    def __init__(self, rid):
        super().__init__(rid)
        self.p = GCounter(rid)
        self.n = GCounter(rid)

    def state(self):
        return (self.p.state(), self.n.state())

    def increment(self, n=1):
        self.p.increment(n)

    def decrement(self, n=1):
        self.n.increment(n)

    def value(self):
        return self.p.value() - self.n.value()

    def merge(self, other):
        out = PNCounter(self.rid)
        out.p = self.p.merge(other.p)
        out.n = self.n.merge(other.n)
        return out

Milestone 2: registers

A register holds one value that anyone may overwrite. The difficulty is two overwrites at once. There are two honest answers, and the lab asks for both.

Last-writer-wins (LWW). Stamp every write with a timestamp; the larger stamp wins. Two details decide whether it is a CRDT. First, ties: two replicas can write with the same timestamp, and if each simply keeps its own, they never agree. Break ties by replica id, so the order is on the pair (timestamp, rid), a total order that every replica computes identically. Second, a replica whose clock is behind must not have its own newer write lose to its own older one, so set bumps the timestamp to one more than the current if necessary. LWW always converges; the price is that one of two concurrent writes silently vanishes. (The timestamps in the check come from a tiny range so that ties are everywhere.)

Multi-value (MV). Keep both. Each stored value carries a version vector: a map from replica id to the number of writes by that replica that this value has "seen". A write replaces everything the writer currently holds, and its vector is the join of those vectors with its own counter bumped, so it is greater than everything it replaced. Two writes whose vectors are incomparable (neither is below the other) are concurrent, and both survive a merge as siblings; a write that has seen both siblings dominates them and replaces them. Merge = union of the entries, minus every entry strictly dominated by another. This is the structure behind “siblings” in Dynamo-style stores (see chapter 6 and, for version vectors, networking chapter 17).

Hints try without first

  • MV set: join all the vectors you hold (vv_join), then add one to your own slot. The result replaces self.entries entirely.
  • MV merge: put both entry lists in a set to drop exact duplicates, then keep an entry unless some different entry has a vector that is at least as large (vv_leq).
  • Return values: LWWRegister.set returns the stamp (ts, rid) actually used (the tester's oracle needs it); MVRegister.set returns the new vector as a dict.

class LWWRegister(CRDT):
    """Last-writer-wins.  entry = (ts, rid, value) or None.  Order by (ts, rid): the replica id
    breaks ties, so every replica picks the same winner."""

    def __init__(self, rid):
        super().__init__(rid)
        self.entry = None

    def state(self):
        return self.entry

    def set(self, value, ts):
        """Write `value` at timestamp `ts`.  A replica's own writes must never go backwards, so
        if ts is not newer than what it holds, use one more than that.  Returns the stamp (ts, rid)."""
        if self.entry is not None and ts <= self.entry[0]:
            ts = self.entry[0] + 1
        self.entry = (ts, self.rid, value)
        return (ts, self.rid)

    def value(self):
        return None if self.entry is None else self.entry[2]

    def merge(self, other):
        out = LWWRegister(self.rid)
        cands = [e for e in (self.entry, other.entry) if e is not None]
        out.entry = max(cands, key=lambda e: (e[0], e[1])) if cands else None
        return out

class MVRegister(CRDT):
    """Multi-value register.  entries = list of (value, version-vector) pairs that are mutually
    concurrent.  A write replaces everything the writer has seen; a merge keeps every entry that
    no other entry dominates."""

    def __init__(self, rid):
        super().__init__(rid)
        self.entries = []              # [(value, ((rid, count), ...)), ...]

    def state(self):
        return tuple(sorted(self.entries, key=_key))

    def set(self, value):
        """Write value; returns the new version vector (a dict)."""
        vv = {}
        for _, e in self.entries:
            vv = vv_join(vv, dict(e))
        vv[self.rid] = vv.get(self.rid, 0) + 1
        self.entries = [(value, tuple(sorted(vv.items())))]
        return dict(vv)

    def value(self):
        return sorted({v for v, _ in self.entries}, key=_key)

    def merge(self, other):
        out = MVRegister(self.rid)
        allv = {(v, e) for v, e in self.entries} | {(v, e) for v, e in other.entries}
        keep = []
        for v, e in allv:
            dominated = any(e != e2 and vv_leq(dict(e), dict(e2)) for _, e2 in allv)
            if not dominated:
                keep.append((v, e))
        out.entries = sorted(keep, key=_key)
        return out

Milestone 3: the OR-Set

Sets are where the design gets interesting, because remove is not monotone: a state that has removed x is not "above" the state that had it. The standard trick is to make removal a thing you add. A 2P-Set keeps two grow-only sets, adds and removes; merge is the union of each. It converges, but a removed element can never come back, because the tombstone is for the element itself.

The observed-remove set (OR-Set) tombstones something finer. Each add creates a fresh unique tag (rid, n). The state is a set of (element, tag) pairs plus a set of removed tags. remove(e) tombstones exactly the tags of e that this replica can currently see. An element is present if at least one of its tags is not tombstoned. Merge is the union of the add-sets and the union of the tombstones.

Why must tags be unique? Suppose two adds got the same tag. A remove of one would then tombstone the other too, and a "re-add" could be killed by a tombstone from before it was made. In the check, tag reuse is exactly what it finds if your remove forgets tags instead of recording them. The simplest unique tag is (rid, n) with n one more than the largest you have used, which is why the replica id must really be unique.

class ORSet(CRDT):
    """Add-wins set.  Every add creates a unique tag (rid, n).  A remove records the tags it has
    SEEN as removed.  An element is present iff it has at least one tag that is not removed."""

    def __init__(self, rid):
        super().__init__(rid)
        self.adds = set()              # {(element, (rid, n))}
        self.removed = set()           # {(rid, n)}   tombstones

    def state(self):
        return (tuple(sorted(self.adds, key=_key)), tuple(sorted(self.removed)))

    def add(self, e):
        """Add e with a fresh unique tag; returns the tag."""
        n = 1 + max([t[1] for _, t in self.adds if t[0] == self.rid], default=0)
        tag = (self.rid, n)
        self.adds.add((e, tag))
        return tag

    def remove(self, e):
        """Remove e: tombstone every tag of e this replica can see.  Returns the set of tags."""
        tags = {t for el, t in self.adds if el == e and t not in self.removed}
        self.removed |= tags
        return tags

    def value(self):
        return {el for el, t in self.adds if t not in self.removed}

    def entries(self):
        """The live (element, tag) pairs.  One pair per 'add' that nobody removed."""
        return {(el, t) for el, t in self.adds if t not in self.removed}

    def contains(self, e):
        return e in self.value()

    def merge(self, other):
        out = ORSet(self.rid)
        out.adds = self.adds | other.adds
        out.removed = self.removed | other.removed
        return out

Milestone 4: property tests

Unit tests check the cases you thought of. A property test checks a statement, for thousands of cases you did not think of. This is the heart of the lab, and most of it is already written in check.py. Read it: it is about 100 lines and it is a reusable tool.

For each of 300 seeds and each type, the tester builds a random schedule of 20 to 45 steps over 3 or 4 replicas. A step is one of:

  • local: a random operation on a random replica (inc, add, set, remove…);
  • send: copy a replica's current state into the in-flight pool;
  • deliver: take a random message from the pool (so messages reorder) and merge it into its destination, and with probability 0.4 leave a copy in the pool, so it can arrive again later (duplicates).

At the end, every replica merges every snapshot and every other replica's final state, in a random order, with a few repeats thrown in (random merge order). Then it checks:

  1. Laws. For random triples among all the states seen (live replicas and in-flight snapshots): commutative, associative, idempotent, upper bound, and that merge did not modify its inputs.
  2. Convergence. After the final merging, all replicas have equal state().
  3. Correctness. The converged value() equals what the oracle computes from the operations alone: the sum of all increments for a counter; the write with the largest (ts, rid) for an LWW register; the writes not dominated by another write's vector for an MV register; for an OR-Set, the elements that have at least one added tag that no remove observed. Convergence alone is not enough ("everybody ends at zero" converges), so the oracle matters.

The shrinker

A failing schedule of 38 steps is useless for debugging. So on failure the tester shrinks it: it repeatedly tries deleting chunks of steps (halves, then quarters, down to single steps) and keeps any deletion after which the schedule still fails, until no single step can be removed. Every sub-sequence of a valid schedule is itself a valid schedule (a deliver with an empty pool does nothing; indices wrap), which is what makes this safe. The output is the seed, the minimal list, and the broken property. This is delta debugging (Zeller and Hildebrandt), in thirty lines.

Hints if a seed fails
  • “not idempotent” or “merging an input again changes the result”: your merge combines instead of joins (adds, concatenates, or appends duplicates).
  • “not commutative” on an LWW register with a one-line schedule: look at ties. On an MV register: look at which entries you keep when the two sides hold different versions of the same sibling.
  • “changed one of its inputs”: merge assigned into self or into other. Build and return a new replica, and do not share mutable containers (sets, lists) between the old and new object.
  • “converged to the wrong value” with all replicas equal: they agree on a wrong answer. Check value() and the tags/stamps your operations return.

Milestone 5: an application

A shopping cart that works on a phone and a laptop, offline, is the textbook use. Its requirements pick the types for you:

  • The lines. Adding to the cart and removing from it, concurrently on two devices, must not lose an item the user just added: an OR-Set. We store one (sku, qty) entry per tap on “add”, each with its own tag. Two taps of the same item are two entries, so quantities add up, and a remove on one device kills only the entries that device has seen. The total for a sku is the sum over the live entries (that is why entries() returns pairs: value() would show the set {("pen", 1)} for two separate taps of “pen, 1”).
  • The delivery address. One value, newest wins: an LWW register.
  • The gift note. Two people typing different notes is a conflict a human should see: an MV register, which shows both.

The cart's merge is just the three merges side by side, which is itself a join (a product of semilattices is a semilattice). That is the useful general fact: you build bigger CRDTs by composing small ones, never by writing a new merge by hand.

The 2P-Set limitation, by running it

The second half of this milestone is a demonstration. Implement TwoPSet (a few lines) and see what the check asserts: add an apple, remove it, add it again, and the 2P-Set says the apple is gone for ever, while the OR-Set says it is back. For a cart this is the difference between “put the pen back after removing it” working and not working. When is a 2P-Set the right choice? When elements are single-use identifiers that are never reintroduced (a set of revoked tokens, for example), and you want the smaller state.

class TwoPSet(CRDT):
    """2P-Set: a grow-only set of adds and a grow-only set of removes.  Present = added and not
    removed.  Once an element is removed it can NEVER be present again."""

    def __init__(self, rid):
        super().__init__(rid)
        self.added = set()
        self.removed = set()

    def state(self):
        return (tuple(sorted(self.added, key=_key)), tuple(sorted(self.removed, key=_key)))

    def add(self, e):
        self.added.add(e)

    def remove(self, e):
        """Only an element this replica has seen can be removed.  Returns True if it recorded one."""
        if e in self.added:
            self.removed.add(e)
            return True
        return False

    def value(self):
        return self.added - self.removed

    def merge(self, other):
        out = TwoPSet(self.rid)
        out.added = self.added | other.added
        out.removed = self.removed | other.removed
        return out

class Cart(CRDT):
    """A shopping cart for several devices: lines (an OR-Set of (sku, qty) entries, one per
    'add to cart' tap), a delivery address (LWW) and a gift note (MV: concurrent notes are shown)."""

    def __init__(self, rid):
        super().__init__(rid)
        self.lines = ORSet(rid)
        self.address = LWWRegister(rid)
        self.note = MVRegister(rid)

    def state(self):
        return (self.lines.state(), self.address.state(), self.note.state())

    def add_item(self, sku, qty=1):
        """One tap on 'add to cart'.  Returns the unique tag."""
        return self.lines.add((sku, qty))

    def remove_item(self, sku):
        """Remove every line for sku that THIS device can see.  Returns the set of removed tags."""
        tags = set()
        for el in sorted(self.lines.value(), key=_key):
            if el[0] == sku:
                tags |= self.lines.remove(el)
        return tags

    def set_address(self, text, ts):
        return self.address.set(text, ts)

    def set_note(self, text):
        return self.note.set(text)

    def items(self):
        """{sku: total quantity}"""
        out = {}
        for (sku, qty), _tag in self.lines.entries():     # one entry per tap, so two taps add up
            out[sku] = out.get(sku, 0) + qty
        return out

    def value(self):
        return {"items": self.items(), "address": self.address.value(), "note": self.note.value()}

    def merge(self, other):
        out = Cart(self.rid)
        out.lines = self.lines.merge(other.lines)
        out.address = self.address.merge(other.address)
        out.note = self.note.merge(other.note)
        return out

Look under the hood

Two things the tidy diagrams hide, with real output from the reference solution.

Tombstones grow

The OR-Set never deletes anything: adds are kept so that a stale replica's copy of them can be recognised as already removed. A thousand add-and-remove rounds of the same element leaves nothing visible and 2,000 records stored, whereas the 2P-Set's tombstone is one record, because it is per element, not per tag.

Real systems handle this in one of two ways. Compaction by causal knowledge: once every replica is known to have seen a tombstone (this needs some membership or acknowledgement protocol, which is a kind of weak coordination), the tag and its tombstone can both be dropped. A better representation: the optimised OR-Set from the CRDT literature (Bieniusa et al.) replaces the tombstone set by a causal context, a compact version-vector-like summary of “every tag I have ever seen”, so a tag that is in the context but not in the add-set is known to be removed, and no per-removal record is kept. The chapter's section on garbage collection of tombstones discusses the same trade-off for text CRDTs.

Delta-state: ship only what changed

State-based CRDTs send the whole state, and the whole state of a counter with a hundred replicas is a hundred entries, even when one incremented. A delta is a small state that, merged into a replica, has the same effect as merging the full new state; since a delta is itself a state, the same merge works, and the laws still hold. The lower half of the output above shows it for the counter: the delta is the one slot that changed, and merging it is equivalent to merging everything.

Distributed systems connection

The structure you tested is the answer to the question of chapter 16: which operations need no coordination at all? Exactly the ones whose merge is a join, because then the order of delivery cannot matter, which is the heart of the CALM theorem. It is also the price: you get availability and convergence, but not invariants like “stock never negative” or “this name is unique”. Real collaborative products sit on top of ideas like these; the Figma case shows a design that is CRDT-inspired but uses a central server and per-property last-writer-wins, and the collaborative-editor studio asks you to choose. And the method of this lab (a model, an oracle, random schedules, a shrinker) is the same one that chapter 19 and Lab 7 scale up to whole systems.

What you learned

  • A state-based CRDT is a state plus a merge that is the join of a semilattice: commutative, associative, idempotent, and pure. With those laws, delivery order, duplicates and delays cannot affect where replicas end up.
  • Counters: one slot per replica and a per-slot maximum; a PN-Counter is two G-Counters.
  • Registers: LWW converges by ordering writes on (timestamp, replica id) but drops a concurrent write; an MV register uses version vectors to keep concurrent writes as siblings and lets a later write resolve them.
  • The OR-Set gives every add a unique tag and a remove tombstones only the tags it has seen, so a concurrent add wins and an element can be added again. A 2P-Set cannot re-add, because its tombstone is for the element.
  • Convergence is not correctness: test against an oracle computed from the operations, not just against each other.
  • A randomized tester with duplicated, reordered deliveries and random merge orders finds bugs unit tests miss, and a shrinker turns a 40-step failure into the 3 steps that matter.
  • You build bigger CRDTs by composing smaller ones; the cost is tombstone growth, handled by compaction or a causal context, and the limit is that invariants across replicas still need coordination.

Check your understanding

A G-Counter's merge is written as: for each replica id, add the two counts. A delivery is duplicated by the network. What happens?

  1. Nothing: addition is commutative
  2. The duplicated state is counted twice, because merge is not idempotent; replicas can end at different, too-large values
  3. The counter becomes negative
  4. The merge raises an exception
Commutativity and associativity are not enough: a state-based merge must also be idempotent, because a network may deliver the same state twice. Taking the per-slot maximum is idempotent; adding is not.

Two replicas write to an LWW register at the same timestamp. Why must the register order writes by (timestamp, replica id) rather than by timestamp alone?

  1. To make writes faster
  2. So that old writes are not lost
  3. Because timestamps are always unique
  4. Because with a tie each replica would otherwise keep its own value, or pick by arrival order, and the merge would not be commutative; the replica id is a deterministic tie-break every replica computes the same way
Convergence needs a total order that every replica evaluates identically. Ties on the timestamp must be broken by something both sides know: the replica id.

In an OR-Set, replica A removes x (which it has seen) while replica B concurrently adds x again. After the replicas merge, is x present, and why?

  1. Yes: A's remove only tombstoned the tags A had seen, and B's new add has a fresh tag that no tombstone covers
  2. No: removes always win
  3. It depends on whose clock is ahead
  4. No: the set can only contain x once
That is the OR-Set's add-wins semantics. Because every add has a unique tag, a remove can only cancel adds it has observed. A 2P-Set, whose tombstone is for the element itself, would have lost x for ever.

Your randomized test shows that after the final merging all replicas have identical state. Why is that still not enough to call the OR-Set correct?

  1. Identical state is impossible to achieve
  2. Replicas could be identical in memory but different on disk
  3. They might agree on a wrong answer (for example, every replica forgetting every element); you also need an oracle, computed from the operations, for what the value must be
  4. The test must also check that the replicas are different
Convergence says replicas agree with each other, not that they agree with the specification. An oracle independent of the implementation turns “they converge” into “they converge to the right thing”.

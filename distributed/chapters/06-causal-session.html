Causal Consistency & Session Guarantees

Linearizability is expensive, and eventual consistency is too weak to program against. In between sits a family of promises that cost almost nothing and remove the most jarring surprises: "you can see your own writes", "time doesn't run backwards for you", and "nobody sees a reply before the thing it replies to". This chapter defines them precisely, shows how real systems implement them with a small token or a few bytes of metadata, and explains why causal consistency is the strongest of them that can keep answering during a network partition.

Why this matters

Most user-visible weirdness in replicated systems is not about two strangers disagreeing. It is about one person seeing the system contradict itself: you post a comment and it vanishes on refresh; a page shows 3 replies, then 2; a reply appears under a post that is not there yet. These bugs are cheap to prevent when you know exactly which guarantee you are missing, and expensive when you reach for "make everything linearizable". Knowing the names, and what each costs, is how you buy back sanity without paying for a majority round trip on every read.

The bargain: no coordination, but not chaos

You met the top of the consistency map in the last chapter: models that make a replicated system look like one copy, at the price of replicas waiting for each other. You also met the bottom, eventual consistency, which makes no promise about what you see in the meantime. This chapter is about the band in between. Its models let each replica answer from its own state, with no round trip to anyone, and still give a coherent picture to each user.

You have seen the idea before: networking chapter 18 listed the session guarantees and causal consistency in a few lines each. Here we make them precise, say how they are built, and do the one thing that chapter could not: show the mechanism end to end in code.

Session guarantees (Terry et al., 1994)

The four guarantees come from the Bayou project at Xerox PARC, in "Session Guarantees for Weakly Consistent Replicated Data" by Douglas Terry and colleagues (1994). Bayou was a database for mobile, often-disconnected devices, where any replica could accept writes and replicas exchanged updates when they met. Reasoning about the global state was hopeless, so the authors asked a smaller question: what does one application, reading and writing through a sequence of replicas, need in order to make sense?

A session is that sequence: the reads and writes issued by one client (a user's browser tab, a mobile app, a request chain), over time, possibly to different replicas. The four guarantees, each stated about one session:

GuaranteeSaysWithout it you see
Read your writes (RYW)A read reflects all writes previously made in this session.You save your profile, reload, and the old one is back.
Monotonic reads (MR)If a read saw the effect of a write, later reads in the session also do. Time does not run backwards for you.A page shows 5 replies; refresh shows 4; refresh shows 5 again.
Monotonic writes (MW)Writes from one session take effect in the order the session issued them, at every replica.You edit a document twice; replicas apply "version 2" and then "version 1", ending with the old text.
Writes follow reads (WFR)A write is applied after the writes whose effects the session had read when it issued it.A reply is visible to others while the post it answers is missing.

Two things to notice. First, all four are per session: nothing here constrains what two different users see, so there is no global order and no waiting for strangers. Second, they are cheap to state as invariants on sets of writes. A session remembers which writes it has made (its write set) and which it has read (its read set), and each guarantee says some replica-side set must contain some session-side set before a request is served. RYW needs the replica's state to include the session's write set at read time. MR needs it to include the read set. MW and WFR are about what must already be present at a replica before a write is applied there.

How a system gives you these

There are two standard mechanisms, and almost every product implementation is one of them or a blend.

Sticky sessions. Route every request of a session to the same replica (by cookie, connection or hash of the user id). A single replica applies updates in some order and never goes backwards, so reading from one replica is automatically monotonic. If that replica also receives the session's writes, RYW and MW come for free as well, and WFR too. It costs nothing but load-balancer discipline. Its weaknesses: the replica can fail (the session moves, and the guarantee can silently break), load becomes uneven, and many deployments send writes to a leader and reads to a follower, in which case stickiness to the follower gives monotonic reads but not read-your-writes. The experiment below shows this.

Version tokens (client-tracked state). The client carries a small piece of state: the version it last wrote and last read, in whatever unit the system has (a log position, a timestamp, a vector of counters). Every request includes it ("give me x, but at least as new as v7"). A replica that has applied at least that version answers; one that has not either waits for replication to catch up, redirects to another replica, or falls back to the leader. This is the right-hand half of the diagram. The guarantee now holds across replica changes, and the choice of what to do when behind is a latency policy: waiting for replication keeps load off the leader, redirecting is faster but loads it.

Real systems expose this directly. MongoDB's "causally consistent sessions" (from version 3.6) carry operation and cluster times between operations; Azure Cosmos DB's "session" consistency level uses a session token passed with requests; and with PostgreSQL streaming replication the same pattern is built by hand from write-ahead-log positions (read the leader's position after a write, ask the follower to wait until it has replayed past it). The details differ; the shape is always "token from write or read, checked at the next replica".

Here is a deterministic simulation that measures all of this. A primary commits writes; three followers apply them in order after a random delay of up to 40 ms; each of 300 sessions makes 12 operations (30% writes, which go to the primary, and 70% reads). Three read policies are compared: a random replica per read; sticky (each session reads only from its own follower); and token (pick any replica whose applied version is at least the larger of the session's last write and last read, else ask the primary).

import random

N_REPLICAS = 3

def arrival_times(commit_times, rng):
    """Replica i applies write v at arrival[i][v]; a FIFO channel keeps them in order."""
    out = []
    for _ in range(N_REPLICAS):
        arr, prev = [], 0.0
        for c in commit_times:
            prev = max(prev, c + rng.uniform(0, 40))     # 0-40 ms replication lag
            arr.append(prev)
        out.append(arr)
    return out

def applied(arr, t):                                      # newest version a replica has at time t
    return sum(1 for a in arr if a <= t)

def run(policy: str, seed: int, sessions: int = 300, steps: int = 12):
    rng = random.Random(seed)
    ryw = mr = reads = 0
    for _ in range(sessions):
        # decide this session's script first: (time, "w" or "r")
        t, script = 0.0, []
        for _ in range(steps):
            t += rng.uniform(1, 25)
            script.append((t, "w" if rng.random() < 0.3 else "r"))
        # the primary commits other people's writes too; versions are positions in commit order
        commits = sorted([(rng.uniform(0, 400), "other") for _ in range(40)] +
                         [(t, "mine") for t, k in script if k == "w"])
        times = [c[0] for c in commits]
        arr = arrival_times(times, rng)
        my_version = {c[0]: i + 1 for i, c in enumerate(commits) if c[1] == "mine"}
        home = rng.randrange(N_REPLICAS)                  # sticky: this session's replica
        my_write = last_read = 0
        for t, kind in script:
            if kind == "w":
                my_write = my_version[t]                  # writes go to the primary
                continue
            if policy == "random":
                v = applied(arr[rng.randrange(N_REPLICAS)], t)
            elif policy == "sticky":
                v = applied(arr[home], t)
            else:                                         # "token": need version >= all this session saw/wrote
                need = max(my_write, last_read)
                v = next((applied(arr[r], t) for r in rng.sample(range(N_REPLICAS), N_REPLICAS)
                          if applied(arr[r], t) >= need), sum(1 for x in times if x <= t))   # else the primary
            reads += 1
            ryw += v < my_write
            mr += v < last_read
            last_read = max(last_read, v)
    return reads, ryw, mr

print(f"{'policy':<8} {'reads':>6} {'read-your-writes violations':>28} {'monotonic-reads violations':>27}")
for p in ("random", "sticky", "token"):
    reads, ryw, mr = run(p, seed=11)
    print(f"{p:<8} {reads:>6} {ryw:>28} {mr:>27}")
policy    reads  read-your-writes violations  monotonic-reads violations
random     2490                          879                         138
sticky     2497                          871                           0
token      2525                            0                           0

Read the table closely. A random replica violates both guarantees often. Sticky reads fix monotonic reads completely (0), as argued, but barely touch read-your-writes (871 violations), because the session's writes go somewhere else. The token policy gives both guarantees, at the price of occasionally asking the primary (that fallback is where its latency goes). The figures come from one seed and a toy lag model, so trust the pattern, not the counts.

A session is not a user

The guarantees are per session, and a session lives wherever the token or the cookie lives. If a user writes on their phone and reads on their laptop, those are two sessions unless you deliberately share the token (store it with the account, server-side). Likewise a chain of microservices serving one request is a session only if each hop forwards the token, exactly as it forwards a trace id. Most "read-your-writes" bugs in production are a hop that dropped the token.

Causal consistency

The session guarantees are about one client. Causal consistency extends the idea to everything one write could have influenced, across all clients. It rests on the happens-before relation from networking chapter 17 (Lamport, 1978). In a data store, write a causally precedes write b if any of these holds:

  • Same session: the same client issued a before b (program order).
  • Reads-from: some client read the value written by a and later issued b. The value it read may have influenced what it wrote.
  • Transitivity: a precedes c and c precedes b.

The promise: if a causally precedes b, no client ever sees the effect of b without also seeing a (at least in the state it reads). Writes that are not related by this order are concurrent and may become visible in different orders at different replicas; that is the freedom that makes causal consistency cheap, and the vector clocks of chapter 17 are the classic way to tell which pair you have.

Notice how the four session guarantees fit: monotonic writes and read-your-writes are about same-session order, monotonic reads and writes-follow-reads are about reads-from. Taken together they amount to causal consistency, which is why the box labelled "causal" sits above all four on the map. (There is a formal statement of this equivalence in the research literature; the intuition is enough here.)

The classic anomaly: a reply before its post

Alice posts "I got the job!" in a datacenter in the US. The post replicates to Europe, where Bob sees it and writes "Congratulations!". His comment is a new write that causally depends on the post. Both writes now head to Asia, where the long link delivers the comment first. Under plain eventual consistency, Asia shows a comment with no post. Under causal consistency, the comment must not become visible until the post is.

Step through

A comment overtakes its post

  1. Alice posts P in the US datacenter. The write is accepted immediately at home; replication to the other datacenters happens in the background.
  2. P replicates to Europe. The European datacenter now has the post. Nobody waited for Asia.
  3. Bob reads P, then writes a comment C. Bob's client library remembers that its context contains P, so C is tagged "depends on P" (it is causally after P: it was written by someone who had read P).
  4. C races to Asia, and wins. The dashed line is P on a slower path (a congested link, a retry, a lagging queue). Asia receives C first. Nothing about the network is broken; this is ordinary reordering.
  5. The two behaviours differ here. With plain eventual consistency Asia applies C on arrival, and a reader sees a comment under no post. A causal store checks C's dependencies, finds P is not visible yet, and holds C back. The comment is still durable at Asia; it just is not exposed yet.
  6. P arrives and C is released. From the first moment a reader in Asia sees C, P is already visible. No coordination with the other datacenters was needed, only the dependency tag and a local check.

Causal+ and COPS: tracking dependencies

Plain causal consistency has a loose end: two concurrent writes to the same key. Replica 1 sees A then B and ends with B; replica 2 sees B then A and ends with A. Both orders are causally legal, but the replicas stay different forever. Causal+ consistency, introduced with the COPS system by Wyatt Lloyd, Michael Freedman, Michael Kaminsky and David Andersen (SOSP 2011), adds convergence: replicas must resolve such conflicts the same way (last-writer-wins by timestamp, a merge function, or a CRDT; chapter 15), so they all end in the same state.

COPS is a geo-replicated key-value store: each datacenter holds a full copy, and inside a datacenter the data is partitioned across many nodes. The mechanism is the one in the stepper above, made efficient:

  • A client library keeps a context: the set of values this client has read or written recently.
  • Each put is sent with its dependencies taken from that context. After a put, the new write replaces the context, because it transitively depends on everything before it. That keeps the dependency list small (the paper calls the surviving ones the "nearest" dependencies).
  • The write is applied at the local datacenter right away, then replicated. A remote datacenter receiving a write first runs a dependency check: for each dependency, ask the node that owns that key whether that version (or a newer one) is already visible. Only when all are does it make the write visible.
  • COPS-GT adds get transactions: a way to read several keys that is a causally consistent snapshot, since reading them one at a time can show a mix of old and new.

The same mechanism, in 40 lines. A datacenter holds a store and a set of visible write ids; a write is applied when its dependencies are all visible, and drained from a waiting list in a loop, since applying one write may unblock another. With check_deps=False it is plain eventual consistency.

import random
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Write:
    key: str
    value: str
    wid: int                       # unique id of this write
    deps: frozenset = frozenset()  # ids of writes the writer had seen: its causal past (nearest dependencies)

class Datacenter:
    def __init__(self, check_deps: bool):
        self.check_deps, self.visible, self.waiting, self.store = check_deps, set(), [], {}
    def receive(self, w: Write):
        self.waiting.append(w)
        self._drain()
    def _drain(self):
        progress = True
        while progress:
            progress = False
            for w in list(self.waiting):
                if not self.check_deps or w.deps <= self.visible:     # dependency check
                    self.store[w.key] = w.value
                    self.visible.add(w.wid)
                    self.waiting.remove(w)
                    progress = True
    def read(self, key):
        return self.store.get(key)

post    = Write("post:1",    "Alice: I got the job!", wid=1)
comment = Write("comment:1", "Bob: congratulations!", wid=2, deps=frozenset({1}))   # Bob read the post first

for check in (False, True):
    eu = Datacenter(check_deps=check)
    eu.receive(comment)                                  # the network delivers the comment first
    print(f"dependency check={check!s:<5} after comment arrives: post={eu.read('post:1')!r:<26} comment={eu.read('comment:1')!r}")
    eu.receive(post)
    print(f"{'':<22} after post arrives:    post={eu.read('post:1')!r:<26} comment={eu.read('comment:1')!r}")

rng = random.Random(5)
for check in (False, True):
    anomalies = 0
    for i in range(10_000):
        p = Write(f"p{i}", "post", wid=2 * i)
        c = Write(f"c{i}", "comment", wid=2 * i + 1, deps=frozenset({2 * i}))
        dc = Datacenter(check)
        order = [p, c] if rng.random() < 0.7 else [c, p]       # 30% of the time the network reorders them
        for w in order:
            dc.receive(w)
            if dc.read(f"c{i}") is not None and dc.read(f"p{i}") is None:
                anomalies += 1                                  # a reader could see the reply without the post
    print(f"dependency check={check!s:<5}: {anomalies} of 10000 post/comment pairs showed a comment without its post")
dependency check=False after comment arrives: post=None                       comment='Bob: congratulations!'
                       after post arrives:    post='Alice: I got the job!'    comment='Bob: congratulations!'
dependency check=True  after comment arrives: post=None                       comment=None

With the check on, the comment is invisible until the post is, in all 10,000 trials, including the roughly 3,000 where the network reordered them. Later systems in this line (Eiger, Orbe, GentleRain, Cure, and others) change how dependencies are represented, with timestamps or vectors instead of explicit lists, trading metadata size against false waiting. The shared lesson is that causal metadata has a cost of its own: it grows with the amount of concurrency and has to be trimmed. It is cheap compared with coordination, not free.

Analogy: a conversation by letter

Think of the committee that communicates by unreliable post. Two letters from different members may reach the secretary in either order, and that is fine as long as neither refers to the other. But if Bob's letter says "in reply to Alice's letter of the 3rd", a careful secretary will not file Bob's letter in the minutes until Alice's has arrived. The dependency note on the envelope is the causal tag; the secretary's wait is the dependency check.

Where it breaks down: a secretary knows Alice's letter exists because Bob names it. A replica knows a write is missing only because the dependency tag says so. If a client never read a thing, nothing orders its writes after it, and causal consistency has no opinion, even when real-world causality (Alice phoned Bob) did exist.

The strongest model that never has to wait

Why is causal consistency a famous landmark rather than just one more point on the map? Because of what it does not need. Every replica can apply a client's write immediately, accept reads from its local state, and ship updates (with their dependency tags) in the background. A write becomes visible at another replica only when its causal past is already there, so the state any replica exposes is always causally closed. During a network partition each side keeps serving, and when the partition heals the two sides exchange what they missed. No client request ever needs a message from another replica to be answered.

Contrast linearizability, which fails this test by the CAP argument: a client on one side cannot learn of a write on the other side. And a formal result says that causal consistency is, in a precise sense, the best you can do without waiting: Prince Mahajan, Lorenzo Alvisi and Mike Dahlin showed in "Consistency, Availability, and Convergence" (2011) that a variant they call real-time causal consistency is the strongest model achievable by a system that is always available and whose replicas converge. Read the slogan as the paper states it: it holds in a specific model of the system and of "availability", and a different model (for example one that lets operations block) yields a different answer. Work on highly available transactions by Peter Bailis and colleagues reaches a consistent picture: read-your-writes and causal consistency require that a client's requests keep reaching replicas that have seen its history ("sticky" availability), while some weaker guarantees need nothing of the kind.

"Available" has a footnote

If a client in a partition is bounced to a replica that has not seen its dependencies, a causal system has two options: serve something that breaks causality, or wait. So the practical claim is: causal consistency stays available for clients that stay with replicas that have seen their context (their own datacenter, typically), and it never needs a cross-datacenter round trip. That is a very strong property for a geo-replicated product, and it is the reason COPS and its successors target multi-datacenter deployments. It is not a promise that every client always gets an answer from every replica.

What causal consistency still cannot do

It is a model of visibility order, not a way to protect an invariant. Two clients who each read a balance of 100 and each withdraw 80, concurrently, are not causally related, so causal consistency lets both succeed and the account goes to -60. The same goes for "usernames must be unique" and "only one holder of this lock". Those need agreement, which is the job of consensus (chapters 8 to 10), or a design that avoids the need (chapter 16 asks which invariants can survive without coordination). A good rule: causal is a great default for feeds, comments, collaboration, and caches, and the wrong tool for money, uniqueness and mutual exclusion.

Distributed systems connection

Session guarantees are what a read replica needs to be usable by humans, and the token pattern shows up everywhere: log positions, hybrid timestamps (chapter 7), cluster times. Causal order is the glue of collaborative systems and CRDTs (chapter 15), where operations carry their causal context so that merging can be done in any order, and of the Figma-style editors in the Figma case study. Coordination-avoiding designs (chapter 16) ask which parts of an application can live at this level and which need the stronger models of chapters 8 to 14.

Key takeaways

  • A session is one client's sequence of operations. The four session guarantees (Terry et al., 1994) are read your writes, monotonic reads, monotonic writes and writes follow reads. Each constrains one session only, so none needs global coordination.
  • Sticky routing gives monotonic reads cheaply, but not read-your-writes when writes go elsewhere. Version tokens, which the client carries and the replica checks, give the guarantees across replica changes, at the cost of waiting, redirecting or asking the leader when a replica is behind.
  • Write a causally precedes b if they are in the same session, if b's author had read a, or transitively. Causal consistency: no one sees b without a. Concurrent writes may appear in different orders.
  • Causal+ (COPS, 2011) adds convergence for concurrent conflicts. It works by tagging each write with its nearest dependencies and delaying visibility at a replica until those are visible there.
  • Causal consistency is the strongest model that needs no cross-replica wait: replicas answer locally and ship updates later. This is the content of the result by Mahajan, Alvisi and Dahlin (2011), true in their formal model, and it needs clients to stay with replicas that have seen their context.
  • It orders visibility but does not protect invariants such as balances, uniqueness or locks. Those need consensus or a design that avoids the need.

Check your understanding

An app sends all writes to the primary and all reads to a follower chosen by a sticky cookie (the same follower each time). Which guarantee does it get reliably?

  1. Read your writes
  2. Both read your writes and monotonic reads
  3. Monotonic reads, but not read your writes
  4. Neither, because followers lag
A single follower applies updates in order and never goes backwards, so reads from it are monotonic. But the user's own write went to the primary and may not have reached that follower yet, so a read can miss it. Tokens, or reading from the primary right after a write, fix that half.

A write is tagged with a token v7 and sent to a follower that has applied only up to v5. Which of these is NOT a reasonable thing for the follower to do?

  1. Answer with its current state anyway, since v5 is close enough
  2. Wait until replication delivers v7, then answer
  3. Redirect the request to a replica that has applied v7
  4. Forward the request to the primary
The token exists to make the guarantee hold. Waiting, redirecting and forwarding all keep it (at different latency and load costs). Answering from v5 silently breaks read-your-writes or monotonic reads.

In the COPS design, why is a dependency check done at the remote datacenter before a replicated write becomes visible?

  1. To make sure the write is durable on disk
  2. To make sure everything the write causally depends on is already visible there, so no reader sees an effect without its cause
  3. To decide which of two concurrent writes wins
  4. To get agreement from a majority of datacenters
The check is purely local ordering: hold a write until its causal past is visible. It is not about durability, conflict resolution (that is the "plus" in causal+) or agreement; no cross-datacenter vote is involved, which is why it stays cheap and available.

Two customers, each having seen a balance of 100, withdraw 80 at the same time at two different replicas of a causally consistent store. What happens?

  1. The second withdrawal is rejected because it causally follows the first
  2. Causal consistency makes the replicas coordinate and only one succeeds
  3. Both are held until a majority agrees
  4. Both succeed: the withdrawals are concurrent, not causally related, so the model puts no constraint on them and an application-level invariant is broken
Causal consistency orders visibility of causally related writes. It says nothing about concurrent writes beyond convergence, so it cannot enforce "balance never below zero". That takes coordination (a consensus-backed counter or lock) or a design such as escrow (chapter 16).

Which statement best describes the status of causal consistency among models that never block on a partition?

  1. It is the weakest of them
  2. It is the strongest known to be achievable without replicas having to wait for each other, in the formal model of Mahajan, Alvisi and Dahlin, with clients staying with replicas that hold their history
  3. It is equivalent to linearizability when there is no partition, so it is the same thing
  4. It is impossible without a global clock
The result is stated in a specific formal model (always available, convergent replicas), and in practice it assumes sticky clients. It does not need a global clock; dependency tracking is enough. It is strictly weaker than linearizability even when no partition occurs.

Testing Distributed Systems

Every protocol in this course is only a few pages long and almost every real implementation of one has shipped with a bug that needed an unlikely sequence of crashes, delays and retries to appear. This chapter climbs the ladder of techniques for finding those bugs: from unit and property tests, through fault injection and Jepsen, up to deterministic simulation, where a whole cluster runs inside one process and any failure replays exactly from a number. You will build a small simulator that finds a real consensus-style bug and then shrinks it.

Why this matters

Distributed bugs are the worst kind: they appear once a month in production, never on a laptop, and vanish when you add logging. A team that cannot reproduce a bug cannot fix it with confidence, and a team that cannot test fault handling is running its recovery code for the first time during a real outage. The techniques here are how serious systems close that gap, and "how would you test this?" is a standard senior-level question about any design you propose.

Why distributed bugs hide

Three properties of distributed systems conspire against ordinary testing.

Rare interleavings. Each process does a sequence of steps, and the network and scheduler decide how steps from different processes interleave. Two processes with ten steps each can interleave in C(20, 10) = 184,756 ways; three processes with ten steps each, in about 5.5 trillion. A test that runs the system once explores one of them. Most interleavings are fine; the bug lives in a handful, such as "the acknowledgement arrives after the failover, which arrives before the second replica's copy". You can run a test a million times on real machines and keep getting the same few common interleavings.

Timing. Behaviour depends on how long things take: timeouts that fire just before a slow reply, leases that expire during a garbage-collection pause (chapter 4), clocks that disagree (chapter 7). Real tests are timing-dependent, so they are either slow (they wait for real timeouts) or flaky (they race against them).

Partial failure. The bug is not "the system crashed" but "one node crashed while a second was slow and a message was in flight". Recovery code, the code that runs only after a failure, is the least-exercised code in the system and the code with the highest stakes. You met the principle in networking chapter 15: partial failure is the defining feature of the field, and so the defining difficulty of testing it.

There is a fourth, practical problem: even once a test does fail, if you cannot replay the failure, you cannot confirm that your fix works. Everything below is a different answer to the same question: how do we make rare, timing-dependent, partial-failure behaviour common, detectable and reproducible?

The testing ladder

Unit tests

Still the base. State machines, parsers, conflict-resolution functions and quorum arithmetic are ordinary functions and deserve ordinary tests (the Raft log-matching check, the ISR high-watermark computation). The limit is the one above: a unit test runs one interleaving, chosen by the author, usually the happy one.

Property-based tests

Instead of writing examples, you state a property, something that must hold for all inputs ("merging two CRDT sets is commutative", "after any sequence of operations the store equals the simple model"), and the framework generates hundreds of random inputs to try to falsify it. The idea comes from QuickCheck (Claessen and Hughes, 2000); in Python the standard tool is Hypothesis. When a property fails the framework shrinks the failing input: it repeatedly tries simpler versions (a shorter list, a smaller number) that still fail, and reports a minimal counterexample. The distributed-systems power-up is stateful (model-based) testing: generate random sequences of operations, including faults, run them against both the real system and a trivial in-memory model, and assert they agree. Everything in this chapter after this point is, in some way, property-based testing with the network and the clock as part of the generated input.

Fault injection

Take a real cluster and deliberately break it, one failure type at a time:

  • Kill a process abruptly (SIGKILL, not a graceful shutdown), at a random moment.
  • Pause a process (SIGSTOP, or a long garbage-collection pause) and resume it later: it wakes believing nothing happened, the zombie of chapter 4.
  • Partition the network: drop packets between chosen groups of nodes, one-way or both (firewall rules, tc netem, or a proxy such as Toxiproxy). Include partial partitions where A reaches B and C but B cannot reach C, the case that confused a Raft cluster in a real outage.
  • Skew or jump the clock on one node.
  • Break the disk: fill it, slow it, return errors from fsync (fsyncgate), or truncate the last write to simulate power loss.

The weakness is that you must also check something: injecting a partition and seeing no crash proves very little. The next rungs add rigorous checking.

Chaos engineering in production

Fault injection in a test environment misses what production has: real traffic mixes, real data sizes, real dependencies, configuration drift. Chaos engineering, popularised by Netflix with Chaos Monkey (which terminates instances at random), runs controlled experiments in production: define a measurable steady state (successful stream starts per second), hypothesise it will survive a failure (losing a zone, adding latency to one dependency), inject that failure with a limited blast radius and a kill switch, and see. It is as much an organisational practice as a technical one, since it makes resilience features such as timeouts, retries and breakers (architecture chapter 17) prove their worth. See case study: Netflix, Hystrix and chaos. Note what it is not: it builds confidence that known failure modes are handled, but random failure injection is a poor way to find a bug that needs one precise interleaving.

Jepsen

Jepsen, created by Kyle Kingsbury, is the best-known framework for testing the claims of distributed databases against real clusters. Its structure is worth knowing in detail, because it is the template for most history-based testing:

  • Generators describe a sequence of operations over time ("a mix of reads, writes and compare-and-set on a handful of keys, each client one at a time, with 10 ms between operations") and when the faults happen. They are lazy, composable descriptions, not a fixed script.
  • Clients are concurrent workers, each applying one operation at a time to the database and recording what happened.
  • The nemesis is a special client that causes faults: partitioning the network into halves or random subsets, killing and restarting processes, pausing them, or skewing clocks.
  • The history is the record of every operation as two events: an invoke when the client sent it, and a completion when it returned: ok (it definitely happened), fail (it definitely did not), or info, meaning indeterminate: a timeout, where the operation may have taken effect at any time, or never. Indeterminate operations are the heart of why distributed testing is hard: you must treat them as concurrent with everything that comes after.
  • Checkers analyse the history. Knossos checks linearizability (chapter 5): it searches for a sequential order of the operations that respects the real-time order of non-overlapping operations and obeys the object's rules, in the manner of Wing and Gong (1993) and Lowe (2017). In the worst case this search is exponential, so histories must be short or low in concurrency. Elle (Kingsbury and Alvaro) checks transactional isolation: rather than searching orders, it infers a graph of dependencies between transactions (who wrote what a read observed, whose write came earlier) from the values themselves (for example by having transactions append unique values to lists, so a read reveals the order of appends), and then looks for cycles in the graph, each pattern of cycle corresponding to a known anomaly (the isolation anomalies of data chapter 11). It scales much better than a linearizability search. There are also simple custom checkers ("every acknowledged write must appear in the final read").

Jepsen has found serious bugs in a long list of well-known databases, and the published analyses are among the best technical writing in the field (see the reading list in chapter 21; the case study Jepsen tests etcd walks through one). Be clear about what it cannot do. It can find bugs, never prove their absence: a clean run means "no violation seen in these schedules". Real clusters and real time make runs slow (minutes per test) and non-reproducible: the same test may fail on one run in twenty, and you cannot replay it. For the same reason it is hard to run a thousand variations of every commit in continuous integration. That last weakness is exactly what the top rung addresses.

Deterministic simulation testing

The idea is easy to state and demanding to build. Make the whole distributed system, every node, the network, the clocks and the disks, run inside a single thread of a single process, where every source of nondeterminism is replaced by a simulated version driven by one seeded random number generator. Then the entire execution is a pure function of the seed: same seed, same exact interleaving, same exact failure, every time. A bug found by seed 8841 on someone's machine overnight is reproduced on yours with the number 8841.

Analogy: the flight simulator

Pilots do not learn engine failure by waiting for a real one. A simulator reproduces the cockpit exactly while the world outside is under the instructor's control: the same engine fails at the same moment, as often as the trainee needs, on a Tuesday afternoon, at no risk. Deterministic simulation is a simulator for your database: the real cockpit (your actual code) with a fully controllable world (time, network, disk) around it.

Where it breaks down: a flight simulator is built by experts who know how aircraft fail. A system simulator only produces the failures its builder imagined, so the simulated world has to be more hostile than you expect the real one to be.

The properties that make it powerful:

  • Reproducibility. Failure found, seed recorded, bug replayed under a debugger as often as you like.
  • Speed. A simulated clock does not wait: when every node is idle, time jumps to the next scheduled event. A simulated hour of cluster life can take a second, so thousands of seeds run per commit, in parallel, and a machine can accumulate an enormous amount of simulated operation overnight.
  • Hostility. You choose how bad the world is: drop 20% of messages, reorder everything, crash nodes in the middle of disk writes, partition the cluster repeatedly. Real networks do this only rarely.
  • Checking. Because the simulator sees everything, it can check invariants constantly instead of reconstructing them from a client-side history afterwards.

The best-known success is FoundationDB, whose developers wrote the database from the start so that its whole cluster runs in this kind of simulation, and credit it for the unusual reliability of the system; see case study: FoundationDB, simulation first and Zhou et al. (SIGMOD 2021). Other projects use the same approach, and there are also tools that retrofit determinism by running ordinary programs on a deterministic virtual machine. The limitations are real: the simulator only models the behaviours its author thought of (a bug caused by an unmodelled quirk of real disks passes cleanly), third-party libraries that do their own I/O or threading are hard to simulate, and the approach constrains how the whole codebase is written.

Build one: a seeded simulator that finds a bug

Here is a deliberately small one. The system under test is a primary-backup store. A primary P replicates each client write to two backups B and C; messages may be dropped or delayed. It acknowledges the client as soon as one backup confirms, so every acknowledged write lives on the primary and at least one backup, which is a majority of three. The primary may crash, and then a failover promotes a backup. The invariant: after failover, the new primary must contain every write that was acknowledged.

The failover has a bug (look for it before reading on): it promotes B without checking which backup is more up to date. The simulator is a heap of timestamped events, simulated time, and random choices drawn from generators derived from (seed, purpose). Nothing uses the real clock or threads.

import heapq
import random
from typing import Callable

# A tiny primary-backup store, run inside a deterministic simulator.
#   * One thread, one event queue, simulated time. No sleeps, no sockets, no real clocks.
#   * Every random choice comes from a generator derived from (seed, purpose).
# The system under test (buggy on purpose):
#   - P replicates each write to backups B and C; messages can be delayed or dropped.
#   - P acks the client once ONE backup has confirmed (so P + one backup = a majority of 3).
#   - P crashes at a random time; a failover promotes a backup.
# Invariant: after failover, the new primary must hold every write that was acked.

def rng(seed: int, *purpose) -> random.Random:
    return random.Random(f"{seed}:{purpose}")      # str seeds are stable across runs

def simulate(seed: int, writes: int = 4, fixed: bool = False):
    q: list = []                                   # (time, tiebreak, action)
    n = 0
    def at(t: int, fn: Callable[[], None]) -> None:
        nonlocal n
        heapq.heappush(q, (t, n, fn)); n += 1

    logs = {"B": [], "C": []}
    primary_alive, acked, trace = True, [], []
    crash_t = 2 + rng(seed, "crash").randrange(24)      # independent of `writes`, so shrinking keeps it

    def say(t, msg): trace.append(f"t={t:>2}  {msg}")

    def write(t: int, i: int) -> None:
        if not primary_alive:
            say(t, f"client sends w{i}: primary is down, ignored"); return
        say(t, f"client sends w{i} to P")
        for b in ("B", "C"):
            r = rng(seed, "msg", i, b)
            if r.random() < 0.3:
                say(t, f"  P -> {b}: w{i} DROPPED"); continue
            d = 1 + r.randrange(6)
            def deliver(t2=t + d, b=b, i=i, r=r):
                logs[b].append(i)
                say(t2, f"  {b} stores w{i}")
                back = t2 + 1 + r.randrange(4)
                def ack(t3=back):
                    if primary_alive and i not in acked:
                        acked.append(i); say(t3, f"  P acks w{i} to client (confirmed by {b})")
                at(back, ack)
            at(t + d, deliver)

    def crash(t: int) -> None:
        nonlocal primary_alive
        primary_alive = False; say(t, "P CRASHES")

    failure = []
    def failover(t: int) -> None:
        if fixed:                                    # merge what every survivor has
            new = sorted(set(logs["B"]) | set(logs["C"])); who = "B+C merged"
        else:                                        # promote B without comparing logs
            new = sorted(logs["B"]); who = "B"
        say(t, f"failover: {who} becomes primary with log {new}")
        lost = [w for w in acked if w not in new]
        if lost:
            failure.append(f"acked writes {lost} are missing from the new primary")

    for i in range(writes):
        at(4 * i, lambda t=4 * i, i=i: write(t, i))
    at(crash_t, lambda: crash(crash_t))
    at(crash_t + 3, lambda: failover(crash_t + 3))

    while q:
        t, _, fn = heapq.heappop(q)
        fn()
    return failure, trace

def first_failing(limit: int, writes: int = 4):
    return next((s for s in range(limit) if simulate(s, writes)[0]), None)

bad = [s for s in range(1000) if simulate(s)[0]]
print(f"seeds 0..999: {len(bad)} violate the invariant; first failing seed = {bad[0]}")

seed = bad[0]
failure, trace1 = simulate(seed)
print(f"\n--- trace for seed {seed} ---")
print("\n".join(trace1))
print("VIOLATION:", failure[0])

_, trace2 = simulate(seed)
print(f"\nreplay of seed {seed}: identical trace = {trace1 == trace2}")

for k in range(1, 5):                                   # shrink: fewest writes that still fail on this seed
    if simulate(seed, writes=k)[0]:
        print(f"\nshrunk: seed {seed} still fails with just {k} write(s):")
        print("\n".join(simulate(seed, writes=k)[1]))
        break

fixed_bad = [s for s in range(1000) if simulate(s, fixed=True)[0]]
print(f"\nwith the merge-logs failover: {len(fixed_bad)} of 1000 seeds fail")

Walk through what just happened. Of 1,000 seeds, 370 expose the bug, which tells you it is common in this model, yet each failing seed is perfectly reproducible: the replay printed an identical trace. The shrink step fixed the seed and asked for the fewest client writes that still reproduce the violation: a single write is enough, so the bug has nothing to do with many writes interacting. Read the shrunk trace as a story: P's message to B is dropped, C stores the write and acknowledges, P tells the client "done", then P crashes and the failover promotes B, which never saw the write. An acknowledged write has vanished. It is the same shape as the unclean-election hazard of chapter 17, and it is why real systems (Raft's election restriction, chapter 10) only elect a candidate whose log is at least as up to date as a majority's. The fix in the code merges the survivors' logs; with it, none of the 1,000 seeds fails. That is evidence, not proof: it says "no violation in these 1,000 schedules of this model".

The "buggify" idea

Random failures at uniform rates are not enough, because many bugs sit behind combinations that are individually rare. FoundationDB's answer is a macro, called BUGGIFY, placed by developers at points in the code where something unusual could happen: before a retry, around a buffer allocation, on an error path. In simulation each such point is enabled or disabled per run at random, and an enabled point fires with some probability, forcing the unusual branch: take the slow path, return a spurious error, shrink a batch size to one, delay a reply a long time. In production, the macro does nothing. The result is that simulation exercises deep rare states constantly, and, because enabling is decided per run, different seeds explore genuinely different "personalities" of failure. Stated qualitatively: buggify lets the code under test help the simulator by marking where the dangerous places are.

Shrinking a failing case

A failing run from a long simulation may contain thousands of events, mostly irrelevant. Shrinking turns it into something a human can read. The method is the same as for property-based tests: delete or simplify parts of the input (fewer operations, fewer nodes, shorter delays, fewer faults) and re-run; keep the change if the bug survives. Our toy shrank only the number of writes; real tools minimise the whole schedule of faults and the operation sequence. A crucial design point from the code above: random choices were keyed by purpose ((seed, "msg", i, b)) rather than drawn from one long shared stream. With a single stream, removing one write shifts every later random draw and the bug evaporates for an irrelevant reason. Keying the randomness keeps the rest of the run stable while you cut things out, which is what makes shrinking effective.

Model checking versus testing

All of the above are testing: running the implementation on some sampled behaviours. Model checking (the subject of the next chapter) takes the opposite trade: it explores all behaviours of a simplified model of the design, within bounds, so a clean result means the design has no violation in any interleaving of that size. The two answer different questions and complement each other.

Practice: Maelstrom and the Gossip Glomers

The cheapest way to feel all this is to write small distributed nodes and watch a tester abuse them. Maelstrom is a workbench built on Jepsen: you write a node in any language that reads JSON messages on standard input and writes them on standard output, and Maelstrom plays the network, injects delays, partitions and crashes, runs client workloads and checks the history. Fly.io's Gossip Glomers is a series of distributed-systems challenges built on it, a sequence that climbs from an echo server through unique-ID generation, broadcast (with faults and efficiency targets), a grow-only counter, a Kafka-style log and totally-available transactions. Working through them teaches more about partial failure than any amount of reading. They are listed in the course's tools; Lab 7 asks you to build a seeded simulator of your own that finds, replays and shrinks a hidden bug in a replicated store.

Try it yourself: break the simulator on purpose

(Hint: the bug does not strictly need a dropped message, only B being too slow to have the write when the primary crashes. It becomes very rare, though, which is a lesson in itself: the fault you inject decides which bugs you can find.) Second, change the failover so it promotes whichever backup has the longer log, instead of merging; is that correct for every seed? Look at a failing seed and ask what the invariant really needs. Third, write the property as a unittest that loops over a few thousand seeds and fails with the seed in the message: self.assertEqual(failure, [], f"seed {seed}"). A failing CI run that prints a seed is a bug report that anyone can reproduce.

Distributed systems connection

Every earlier chapter described a behaviour the next one tests. Linearizability (chapter 5) is what Knossos checks; the leases and fencing tokens of chapter 4 are what the pause nemesis attacks; Raft's election restriction is what our toy simulator lacked. A system you can only test by waiting for production to fail is a system whose designers have not finished designing it.

Key takeaways

  • Distributed bugs hide in rare interleavings, timing-dependent behaviour and partial failures, and conventional tests sample very few of them and cannot replay a failure.
  • The ladder: unit tests, property-based tests (random inputs plus shrinking; model-based for operation sequences), fault injection (kill, pause, partition, skew, disk faults), chaos engineering in production (confidence with a bounded blast radius), Jepsen, and deterministic simulation.
  • Jepsen drives a real cluster with a generator, clients, a nemesis and a recorded history of invoke/ok/fail/info events. Knossos checks linearizability by search; Elle infers a dependency graph and finds cycles. It finds bugs but cannot prove their absence and cannot replay them.
  • Deterministic simulation runs the real code, with simulated time, network and disk, in one thread driven by a seeded generator, so any failure replays exactly from its seed, runs faster than real time and under harsher faults than the real world.
  • Buggify marks rare paths so the simulator can force them. Shrinking minimises a failing run; keying randomness by purpose keeps the failure stable while you shrink.
  • Model checking explores every behaviour of a model within bounds; testing samples behaviours of the real implementation. Use both. Maelstrom and the Gossip Glomers are the best hands-on practice.

Check your understanding

A Jepsen history contains an operation whose client timed out. How should the checker treat it?

  1. As failed, since it returned no result
  2. As indeterminate: it may have taken effect at any point after it began, or never, and the checker must allow both possibilities
  3. As succeeded, because the server probably processed it
  4. It should be removed from the history
A timeout tells you nothing about whether the request was executed (the lost-ack problem of networking chapter 16). Treating it as failed or succeeded would produce false alarms or hide real bugs, so the history records it as "info" and the checker considers it concurrent with everything afterwards.

What does the seed buy you in deterministic simulation testing?

  1. Faster hardware
  2. A guarantee that no bugs remain
  3. Protection against clock skew in production
  4. Exact reproduction of any failing run, because every source of nondeterminism is derived from it
With a single-threaded executor and simulated time, network and disk, the execution is a function of the seed. A failure found anywhere can be replayed anywhere. It guarantees nothing about bugs in unmodelled behaviour, and it says nothing about production hardware.

Why does the chapter's simulator derive random numbers from (seed, purpose) rather than from one global stream?

  1. So that removing one write during shrinking does not shift every later random choice and accidentally hide the bug
  2. Because Python cannot reuse a single generator
  3. To make the run non-deterministic
  4. To make the simulation run faster than real time
In a single shared stream, deleting an event changes which numbers later events receive, so the shrunk run is a different run. Keying the draws by purpose keeps unrelated events stable, so shrinking changes only what you intend.

A team runs Chaos Monkey-style random instance kills in production for a year and sees no incidents. What can they conclude?

  1. The system is free of concurrency bugs
  2. The system is linearizable
  3. Single-instance losses of the kinds exercised are handled; it says little about rare interleavings or multi-fault scenarios
  4. They can remove their circuit breakers
Chaos engineering builds evidence that known failure modes are survived with the blast radius bounded. A bug needing a precise interleaving of several faults is unlikely to be hit by random single-instance kills, which is where simulation and model checking help.

Which statement correctly contrasts model checking with deterministic simulation?

  1. Model checking runs real code on real machines; simulation checks only designs
  2. Model checking exhaustively explores a model of the design within bounds; simulation samples many seeds of the real code in a simulated world
  3. They are identical techniques with different names
  4. Simulation proves correctness for every possible execution
The trade is exhaustiveness on a model versus sampling on the implementation. Neither alone covers both "is the design right?" and "does the code match the design?".

Distributed Transactions in Practice

Two-phase commit tells you how to make several machines commit together; it does not tell you how to build a database on top of it. This chapter tours three complete designs that do: Percolator (snapshot isolation on top of a key-value store, with locks that clean themselves up), Spanner (Paxos groups, two-phase commit between them and clock-based ordering), and Calvin (agree on the order first, then execute deterministically, with no commit protocol at all). Each comes with a space-time diagram, then we compare them, look at how today's distributed SQL databases borrow from them, and finally put a number on the real cost: wide-area round trips.

Why this matters

Almost every modern "NewSQL" database (TiDB, CockroachDB, YugabyteDB, Spanner itself, FoundationDB) is a variation on the three designs here. If you can read an architecture page and say "this is Percolator-style, with a timestamp oracle" or "this is optimistic and certifies at commit", you can predict its latency, its failure behaviour and what it will do to your hot rows without reading the source. It is also the answer to the system-design interview question that follows "shard the database": and what happens when a transaction touches two shards?

What every design has to answer

You met the building blocks already. Chapter 13 gave us atomic commit and its blocking flaw; Isolation Levels & Anomalies defined snapshot isolation (each transaction reads a consistent snapshot as of its start and conflicting writers are rejected, but write skew is allowed) and serializability; consensus gave us replicated logs that survive a minority of failures. A distributed transaction system has to combine them by answering three questions:

  1. Order. How does each transaction get a position in time, so that "reads as of time t" means something on every machine? (A counter service? Synchronised clocks? A pre-agreed log?)
  2. Atomicity. How do the writes on several partitions become visible together, and how is the commit decision protected against the death of whoever is running the protocol?
  3. Readers. How do readers get a consistent view without blocking writers, or being blocked by them?

The three designs give three very different answers, and the differences are instructive. Keep the questions in mind; the comparison table later is organised around them.

Percolator: snapshot isolation on Bigtable

Percolator (Peng and Dabek, OSDI 2010) was built at Google to keep the web search index up to date incrementally. Rebuilding the index with batch MapReduce jobs meant that a freshly crawled page waited for the next full run; the Percolator team wanted to update only what changed, with many workers modifying shared tables concurrently, and the data structures (the document table, the link graph, duplicate detection) needed transactional guarantees to stay consistent. It sits on top of Bigtable, which provides only single-row atomic updates and versioned cells, and builds multi-row, multi-table transactions out of just that. Whatever you think of the workload, the construction is beautiful because it uses almost nothing.

The ingredients

  • A timestamp oracle. A service that hands out strictly increasing integers. Every transaction takes a start timestamp when it begins (defining its snapshot) and a commit timestamp when it commits. The oracle makes timestamps from different machines comparable without any clock synchronisation, because there is only one source. (It stays fast by handing out timestamps in batches, and stays correct across restarts by persisting an upper bound to disk; both are in the paper.)
  • Extra columns in every cell. Each Bigtable cell gets, besides the user's data column, a lock column and a write column (Percolator also has notification columns for triggers, which we skip). The data column stores values keyed by start timestamp. The write column stores, keyed by commit timestamp, a pointer to which start timestamp's data is the committed version. A lock records who is in the middle of committing.
  • Client-driven commit. There is no coordinator process. The client library running in the application worker is the transaction manager, and Bigtable's per-row atomicity is the only atomic primitive it uses.

The protocol

A transaction buffers its writes in memory. At commit time it runs a 2PC of its own, built so that the commit point is one atomic Bigtable row update:

  1. Prewrite (phase 1). The client picks one of the cells it wrote as the primary and the rest are secondaries. For each cell it checks for a conflict (a lock from anyone, or a write record with a commit timestamp later than its own start timestamp, meaning someone committed after our snapshot) and, if there is none, writes the new value into data at its start timestamp and puts a lock. The primary's lock is marked as primary; every secondary's lock contains a pointer to the primary. If any cell conflicts, the client aborts and removes the locks it placed.
  2. Get a commit timestamp from the oracle.
  3. Commit the primary (phase 2, the commit point). In a single atomic update of the primary's row, the client checks its lock is still there, writes a write record at the commit timestamp (pointing at the start timestamp) and erases the lock. If this succeeds, the transaction is committed, full stop, even though no other cell has changed.
  4. Commit the secondaries. The client does the same for each secondary: write record, erase lock. This part can be done lazily or by someone else.

Readers take a start timestamp and look for the newest write record at or before it, then follow it to the data. If they meet a lock with a timestamp at or before their snapshot, a commit might be in flight that they should see; they wait, and if the lock looks abandoned they clean it up.

Why the primary makes crashes harmless

Look at what the design did to the blocking problem of 2PC. Atomicity needs a single place where the outcome lives, and the primary lock is that place. Its state tells everyone the transaction's fate: lock present means "not yet committed", a write record at the transaction's timestamp means "committed", and lock gone with no write record means "aborted". Anyone, not just the dead client, can read it.

That is why a crashed client is cleaned up lazily by whoever stumbles on its leftover lock, with no coordinator to restart:

  • The finder looks at the lock's primary pointer and at the primary cell.
  • If the primary has a write record for that start timestamp, the transaction committed: roll forward by writing the secondary's write record and erasing the lock.
  • If the primary lock is still there and the owner is presumed dead, roll back: erase the primary lock first (that atomically fixes the outcome as aborted, and also fences out the dead client in case it is merely slow, because its later attempt to commit the primary finds its lock gone) and then the secondaries.
  • How is the owner "presumed dead"? In the paper, a worker keeps a liveness token in the Chubby lock service, and locks also carry a wall-clock time, so a lock whose owner's token is gone, or that is very old, is treated as abandoned. Judging liveness is a heuristic (chapter 3), but the order of the clean-up steps makes a wrong guess safe: if the slow client really was alive, its commit simply fails.

The runnable sketch below keeps this honest with about eighty lines: three columns as Python dictionaries, a counter standing in for the oracle, a client that can "crash" after prewrite or after committing the primary, and a reader that resolves stale locks. It omits Bigtable, batching, liveness checking (the reader just assumes the owner is dead) and retries, but the commit and recovery rules are the paper's.

"""A miniature Percolator: snapshot isolation on a versioned key-value table.

Each cell has three columns, as in the paper: data@start_ts, lock, write@commit_ts.
"""
from __future__ import annotations
import itertools


class Table:
    def __init__(self):
        self.data: dict[tuple, str] = {}          # (key, start_ts) -> value
        self.lock: dict[str, tuple] = {}          # key -> (primary_key, start_ts)
        self.write: dict[tuple, int] = {}         # (key, commit_ts) -> start_ts
        self.oracle = itertools.count(1)          # the timestamp oracle

    def read(self, key: str, ts: int):
        """Snapshot read at ts: newest committed version with commit_ts <= ts."""
        lk = self.lock.get(key)
        if lk and lk[1] <= ts:
            return "BLOCKED", lk                  # someone may be committing at or before ts
        done = [(c, s) for (k, c), s in self.write.items() if k == key and c <= ts]
        return (self.data[(key, max(done)[1])], None) if done else (None, None)


def commit(t: Table, writes: dict[str, str], crash_after: str | None = None) -> str:
    """Client-driven 2PC. writes' first key is the primary."""
    keys = list(writes)
    primary, start = keys[0], next(t.oracle)
    for k in keys:                                # phase 1: prewrite every cell
        newer = any(kk == k and c >= start for (kk, c) in t.write)
        if k in t.lock or newer:                  # write-write conflict
            for j in keys:
                if t.lock.get(j) == (primary, start):
                    del t.lock[j]
            return "ABORT (conflict)"
        t.data[(k, start)] = writes[k]
        t.lock[k] = (primary, start)
    if crash_after == "prewrite":
        return "CLIENT CRASHED after prewrite"
    commit_ts = next(t.oracle)                    # phase 2: commit the primary FIRST
    t.write[(primary, commit_ts)] = start
    del t.lock[primary]                           # <- this single step is the commit point
    if crash_after == "primary":
        return "CLIENT CRASHED after committing the primary"
    for k in keys[1:]:
        t.write[(k, commit_ts)] = start
        del t.lock[k]
    return "COMMITTED"


def resolve(t: Table, key: str) -> str:
    """A reader that hit a stale lock decides by looking at the PRIMARY's fate."""
    primary, start = t.lock[key]
    committed = [c for (k, c), s in t.write.items() if k == primary and s == start]
    if committed:                                 # roll forward
        t.write[(key, committed[0])] = start
        del t.lock[key]
        return f"primary committed at ts {committed[0]}: rolled {key} forward"
    gone = []
    for k, lk in list(t.lock.items()):            # roll back: primary first, then the rest
        if lk == (primary, start):
            del t.lock[k]
            gone.append(k)
    return f"primary {primary} never committed (owner presumed dead): rolled back {gone}"


if __name__ == "__main__":
    t = Table()
    print("setup:      ", commit(t, {"alice": "100", "bob": "50"}))
    reader_ts = next(t.oracle)
    print("T2 (transfer) ", commit(t, {"alice": "70", "bob": "80"}, crash_after="primary"))
    print("reader at old ts", reader_ts, "sees alice =", t.read("alice", reader_ts)[0],
          " bob =", t.read("bob", reader_ts)[0])
    new_ts = next(t.oracle)
    print("reader at new ts", new_ts, "alice =", t.read("alice", new_ts)[0],
          " bob =", t.read("bob", new_ts)[0])
    print("  ->", resolve(t, "bob"))
    print("reader at new ts again: alice =", t.read("alice", new_ts)[0],
          " bob =", t.read("bob", new_ts)[0])

    t2 = Table()
    commit(t2, {"x": "1", "y": "1"})
    print("\nT3 (crash before commit):", commit(t2, {"x": "2", "y": "2"}, crash_after="prewrite"))
    ts = next(t2.oracle)
    print("reader sees x:", t2.read("x", ts))
    print("  ->", resolve(t2, "x"))
    print("reader sees x:", t2.read("x", ts)[0], " y:", t2.read("y", ts)[0])

Read the output as two experiments. In the first the client dies after the commit point: a reader with an old timestamp sees the old balances (snapshot isolation at work, it is not even blocked because the lock's timestamp is later than its own), a reader with a new timestamp sees the new alice but is BLOCKED on bob's lock, finds the primary committed at timestamp 5, and rolls bob forward. In the second the client dies before the commit point, so the same lock is found to belong to a transaction that never committed and both rows are rolled back. Same stale lock, opposite resolution, decided entirely by the primary.

What it costs

  • Latency. A commit is several sequential round trips to Bigtable (prewrite, oracle, primary commit, then secondaries), and a read may have to wait for or clean up a lock. The paper accepts this because the incremental index workload is throughput-oriented, not latency-sensitive. It is a poor fit for a request that must return in milliseconds.
  • Isolation is snapshot isolation, not serializability. Two transactions that read overlapping data and write disjoint cells can both commit (write skew, as in the data course).
  • The oracle is a hot spot. Every transaction needs two timestamps. It scales by batching, and it is a single logical point whose availability matters.
  • Hot rows are expensive because contending writers fail at prewrite and back off.

The design has aged well anyway. It is the documented basis of the transaction layer of TiDB (with a placement-driver component acting as the timestamp oracle, and each key range replicated with Raft in the storage layer), and its key idea, "make one cell the source of truth for the whole transaction", appears in many other systems. A deeper case study with the paper's timeline is in Percolator: Transactions on Bigtable.

Spanner: Paxos groups, 2PC across them, TrueTime for order

Spanner (Corbett et al., OSDI 2012) is Google's globally distributed database. Its transactions give external consistency, which is strict serializability: transactions behave as if executed one at a time, and if transaction T1 finishes committing before T2 starts, then T1 is ordered before T2. The ingredients:

  • Data is split into ranges and each range is replicated by its own Paxos group, usually across data centres, with a long-lived leader per group. Every durable action a group takes (a write, a lock record, a prepare, a commit) is a Paxos log entry.
  • Read-write transactions use two-phase locking. Reads take locks at the group leaders (with wound-wait deadlock avoidance, in which an older transaction can "wound" a younger one that holds a lock it needs, so cycles cannot form). Writes are buffered at the client until commit.
  • A transaction touching one group commits through that group's Paxos log, with no 2PC.
  • A transaction touching several groups runs 2PC between the group leaders. One participant leader acts as coordinator. Crucially each "participant" is a replicated state machine: its prepared record and the coordinator's COMMIT record are Paxos-replicated, so they survive the loss of a machine, and a failed leader is replaced by an election. This is exactly the fix from the last chapter: 2PC where nobody depends on one disk.

Ordering with TrueTime and commit wait

To order transactions across groups without a central oracle, Spanner uses clocks, but honest ones. Chapter 7 and Ordering at Scale develop TrueTime in detail, so only the essentials here: a call TT.now() returns not a time but an interval that is guaranteed to contain the true time, and the width of the interval is the uncertainty ε. The coordinator picks the commit timestamp s to be at least the latest edge of TT.now(), and at least every participant's prepare timestamp. It then holds the transaction's locks and waits until TT.after(s) is true, meaning s is definitely in the past everywhere, before it reveals the commit to anyone. This is commit wait. After it, any transaction that begins later (in real time) will pick a timestamp greater than s, which gives external consistency using nothing but bounded clock error. The wait is about the size of the uncertainty (a few milliseconds in Google's published setup), which is why Spanner invests in GPS and atomic clocks to shrink ε.

Readers that never lock

Spanner's other half is read-only transactions and snapshot reads. Because every version of every row carries a commit timestamp, and timestamps are globally meaningful, a read-only transaction can pick a timestamp t and read the database as of t from any replica that has caught up to t, with no locks and no 2PC. It never blocks writers and is never aborted by them. The only possible wait is for a lagging replica to catch up (the paper calls the point it has reached "safe time"). For read-heavy workloads this is the big win: most traffic is reads, and they are cheap, local and consistent.

Analogy: the restaurant pass with a stopwatch

Think of several kitchens, each with a strict ticket rule, and a rule that an order is only "served" after a certain moment has definitely passed on every clock in the building. If every kitchen waits until the uncertainty window is closed before shouting "served", then any order taken after it is guaranteed to be numbered later. The kitchen pays a short, predictable pause (commit wait) instead of phoning the others to agree on numbering.

Where it breaks down: the guarantee is only as good as the claimed bound on clock error. If a clock drifts beyond ε, ordering can silently break, which is why TrueTime's engineering is the real product. Systems without such clocks must do something else (below).

Spanner's costs: it needs special time infrastructure to keep commit wait small; write transactions that span groups pay a 2PC round trip between leaders plus Paxos replication latency at both ends; and locks are held across all of it, so contended rows are slow in a wide-area deployment. Case study 10 in the networking course has the clock side of this story.

Calvin: order first, then execute deterministically

Percolator and Spanner both spend effort deciding, after the fact, whether a transaction can commit, and then making that decision atomic and durable. Calvin (Thomson et al., SIGMOD 2012) asks a sharper question: why does distributed commit need a vote at all? A participant votes no (or crashes) because of things that can differ between machines: a deadlock the lock manager decided to break, a local resource problem, a crash and restart in the middle. If those sources of nondeterminism are removed, so that executing the same transactions in the same order always gives the same result, then every partition that follows the same input will arrive at the same outcome without being told, and there is nothing to vote on.

So Calvin splits the system into three layers:

  1. Sequencing. Clients send transactions to sequencers. Time is cut into short epochs; each epoch, the sequencers collect the transactions they received into a batch, and the batches are replicated (using Paxos, or an asynchronous scheme, as the paper describes) and given a global order. After this step the entire future of the database is determined by an agreed-upon sequence of inputs.
  2. Scheduling. Each partition's scheduler reads the ordered batches and acquires locks strictly in that order, a transaction at a time. Because lock acquisition follows the global order, deadlocks cannot occur, and every partition grants conflicting locks in the same sequence.
  3. Execution. A transaction runs once its locks are granted. If it touches data on other partitions, the partitions send each other the values they read (a one-way message); every participant then runs its part of the logic and applies its local writes. No prepare, no vote, no decision messages, and no coordinator whose failure can block anyone.

Analogy: numbered tickets at the pass

In a kitchen with several stations, order tickets are numbered at the counter before they are passed out. Each cook works the tickets in number order and hands over the ingredients a neighbouring station needs. No one has to confer about whether to cook a dish, because every cook, following the same numbered tickets and the same recipes, ends with the same result.

Where it breaks down: it only works if a ticket tells the cooks everything they need to know up front (which ingredients and which stations). A ticket that says "cook whatever the customer fancies, we'll see" cannot be scheduled. That is the price in software too.

What failures mean when execution is deterministic

An ordinary abort is still possible: a transaction that finds insufficient funds aborts, but it aborts deterministically on every partition, because the logic and the data it reads are the same everywhere. What disappears is the abort that comes from a machine's bad luck. A crashed node recovers by loading a checkpoint and re-executing the ordered log; a replica group stays hot by running the same input sequence; the global order is made fault-tolerant by consensus. Atomicity falls out of determinism plus a durable input log.

The price: read and write sets must be known in advance

To acquire locks in order before running, the scheduler must know which records the transaction will touch. That means transactions are submitted as one-shot stored procedures with a declared access set, rather than as interactive sessions where a client issues SELECT, thinks, then issues UPDATE. For most OLTP code that is a modest change; but queries whose access set depends on data they read (a lookup through a secondary index, then an update of the row found) do not fit directly. Calvin's answer is OLLP, optimistic lock location prediction: run a cheap reconnaissance read to guess the access set, submit the transaction with that guess, and have it re-check the prediction when it executes; if the data moved in between, it is restarted. Other costs are the epoch's built-in latency (a transaction waits for its batch) and that long-running or user-interactive transactions simply do not fit the model. The deterministic-database idea has been influential, and at least one commercial database (FaunaDB) was publicly described as drawing on Calvin; but "deterministic by design" remains a minority architecture because of the one-shot constraint.

What today's distributed SQL databases do

These systems are young and change quickly, so this section sticks to widely documented design points and stays qualitative where it must.

  • TiDB: its transaction model is documented as Percolator-based: a timestamp from a central component (the placement driver) and a primary/secondary lock scheme, over key ranges replicated with Raft. In other words, Percolator's recipe with each Bigtable row replaced by a replicated range.
  • CockroachDB: serializable transactions with provisional writes and a replicated transaction record that holds the commit state (the same "one place is the source of truth" idea as Percolator's primary), with each range a Raft group. It orders with hybrid logical clocks (chapter 7), not specialised time hardware, and handles clock uncertainty by letting a read that meets a value inside its uncertainty window restart at a later timestamp rather than by commit wait.
  • YugabyteDB: a Spanner-inspired design: tablets replicated by Raft, hybrid time, and distributed transactions that use a replicated transaction-status record and provisional writes that are resolved at commit.
  • FoundationDB: optimistic concurrency control. A client gets a read version, reads a consistent snapshot at it, and buffers writes. At commit it sends the keys it read and wrote to a resolver, which checks whether anything the transaction read has been written since its read version; if so the commit is rejected and the client retries, otherwise the mutations are made durable in a replicated transaction log and applied to storage servers. The result is strict serializability without locks during execution; the trade is that long or contended transactions retry (and the system limits how long a transaction may run). It is also famous for being built around deterministic simulation: see FoundationDB: Simulation First and Zhou et al., SIGMOD 2021.

Notice how few new ideas there are. The questions are the same (who orders, where does the decision live, how do reads avoid locks) and the answers are drawn from this chapter: central or hybrid clocks for order, a replicated record for the decision, and multi-version storage for readers.

The cost of distribution, measured in round trips

Everything above is invisible on a local network and expensive across continents, so let us put numbers on it. These figures are assumptions, chosen to be easy to reason about, not measurements of any product. Suppose a transaction's two shards have their leaders in different regions with a 70 ms round trip between them, each shard's Paxos or Raft quorum is within one region with a roughly 10 ms commit round trip, and clock uncertainty (for a Spanner-style design) is a few milliseconds.

  • A transaction on one shard commits in about one quorum round trip: roughly 10 ms, plus commit wait if the design needs it.
  • A transaction on two shards in different regions adds the prepare/vote exchange between leaders (one 70 ms round trip), plus replication of the prepare and commit records on the way (more quorum round trips, 10 ms each): on the order of 70 + 2 × 10 plus a few ms, so about 100 ms, a tenfold increase over the single-shard case.
  • Interactive transactions multiply it. If the application issues five statements one after another and each reads from the remote leader, that is 5 × 70 = 350 ms of reads before the commit even begins. The only fix is not to cross the boundary in the middle of a transaction.
  • Locks make latency into throughput. If a hot row is locked for 100 ms per transaction, at most about 10 transactions per second can update it, no matter how much hardware you add. Lock hold time, not CPU, caps contended throughput.

The practical advice follows directly and is what experienced designers actually do:

  1. Make most transactions single-shard by choosing the shard key to match the transaction boundary (everything belonging to one customer or one document together; see Sharding in Practice).
  2. Place leaders near the writers and keep the quorum within a region where the consistency model allows (chapter 18).
  3. Send the whole transaction to the data (a stored procedure or a one-shot batch) instead of ping-ponging statements over a long link. Calvin is this idea taken to its limit.
  4. Prefer snapshot or read-only paths for reads, which can be answered locally.
  5. When even that is too slow or fragile, give up cross-shard atomicity: a saga (architecture course) or no coordination at all (the next two chapters).

Common misconception: "distributed SQL means I can ignore sharding"

These databases hide the machinery, not the physics. A transaction that spans ranges in far-apart regions will be slow and will hold locks (or incur retries) for the duration. Schema and key design that keeps related rows together matters as much as it ever did, which is why every one of these systems has features for controlling where data lives.

Distributed systems connection

These designs are three answers to one tension that runs through the whole course: coordination is expensive (consensus, 2PC, commit wait), yet application invariants seem to demand it. Percolator centralises order in an oracle; Spanner buys order with clock hardware; Calvin front-loads all agreement into one log and then needs none. The next two chapters push in the other direction: data structures that merge without any agreement (CRDTs), and a precise theory of which invariants truly need coordination at all (coordination avoidance). Later, testing shows why FoundationDB-style simulation is the way these complex protocols get trusted.

Key takeaways

  • Every distributed transaction design must answer: how are transactions ordered, where does the commit decision live (and survive), and how do readers avoid blocking.
  • Percolator: snapshot isolation over a key-value store, with a timestamp oracle and client-driven 2PC. The primary lock is the commit decision; leftover secondary locks are cleaned lazily by anyone who finds them, rolling forward or back according to the primary.
  • Spanner: Paxos-replicated groups, 2PC across them (so no participant is a single disk), TrueTime commit wait for external consistency, and lock-free snapshot reads for read-only transactions.
  • Calvin: agree on the order of transactions first, then execute deterministically; no 2PC is needed because all partitions reach the same outcome. The price is declared read and write sets (one-shot transactions, OLLP for dependent reads).
  • Modern systems recombine these: TiDB is Percolator-based; CockroachDB and YugabyteDB use replicated transaction records and hybrid clocks; FoundationDB uses optimistic concurrency with resolvers.
  • The cost is round trips: a cross-region commit adds at least one wide-area round trip plus replication, and locks held across it cap throughput on hot rows. Keep transactions inside one shard whenever you can.

Check your understanding

In Percolator, what is the commit point of a transaction?

  1. When all secondary locks have been erased
  2. When the client receives the start timestamp
  3. The atomic update of the primary cell that writes its commit record and erases its lock
  4. When the prewrite phase succeeds on every cell
The primary's single-row atomic update is the decision. Before it the transaction can still be aborted by anyone who rolls back its primary lock; after it, the transaction is committed even if the client dies before touching a secondary, and any reader that finds a secondary lock rolls it forward.

A Percolator reader finds a stale lock on a secondary cell whose owner crashed. How does it decide what to do?

  1. It looks at the primary cell: a commit record there means roll forward, otherwise (owner presumed dead) erase the primary lock and roll back
  2. It asks the timestamp oracle whether the transaction committed
  3. It waits for the client to restart
  4. It always rolls the secondary back, since the client crashed
The primary holds the outcome. Rolling back unconditionally would undo transactions that had already committed at the primary, breaking atomicity. The oracle only hands out timestamps and knows nothing about transactions' fate, and waiting for the client would reintroduce blocking.

Why does Spanner's coordinator wait (commit wait) before announcing a commit with timestamp s?

  1. To give the Paxos followers time to catch up
  2. To let the participants vote
  3. To avoid deadlocks with other transactions
  4. So that s is definitely in the past on every clock, guaranteeing that any transaction starting after this commit becomes visible gets a larger timestamp (external consistency)
TrueTime gives an uncertainty interval. Waiting until TT.after(s) closes it, so real-time order and timestamp order agree. Replication and voting are done by other steps (Paxos writes, 2PC prepare), not by the wait.

Why can Calvin commit multi-partition transactions without two-phase commit?

  1. Because it assumes no machine ever fails
  2. Because the order is agreed first and execution is deterministic, so every partition reaches the same outcome from the same input and has nothing to vote on
  3. Because it uses synchronised atomic clocks instead
  4. Because it only allows read-only transactions across partitions
2PC exists to reconcile outcomes that can differ per node (a local abort, a crash). Remove nondeterminism and log the inputs durably, and a crashed node recovers by replaying; there is no vote. The price is declaring the access set in advance and giving up interactive transactions.

Which statement about isolation is correct?

  1. Percolator gives strict serializability because it uses a single timestamp oracle
  2. Spanner's read-only transactions take shared locks at the group leaders
  3. Percolator gives snapshot isolation, so write skew is possible; Spanner's read-write transactions give strict serializability and its read-only transactions read a snapshot without locks
  4. Calvin gives snapshot isolation because it batches by epoch
A single oracle orders timestamps, but Percolator's conflict check only compares writes to the same cells, which is first-committer-wins, i.e. snapshot isolation. Spanner locks for read-write transactions (and orders by TrueTime) but serves read-only transactions at a timestamp without locks. Calvin executes in one agreed serial order, so it is serializable.

Two shards' leaders are in different regions with a 70 ms round trip. An application runs a transaction that issues six sequential reads against the remote shard, then commits. Roughly what dominates the latency?

  1. The commit protocol's disk writes
  2. The six sequential remote round trips (about 420 ms) before the commit even starts
  3. Clock uncertainty
  4. The timestamp oracle
Interactive transactions pay the wide-area round trip for every statement. This is why systems recommend sending whole transactions to where the data is, choosing shard keys so transactions stay in one shard, and (in Calvin's case) requiring one-shot transactions. The commit protocol adds about one more round trip on top.

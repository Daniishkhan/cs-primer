Coordination Services: ZooKeeper & etcd

Consensus is hard to implement and easy to misuse, so most systems do not implement it. They rent it from a small, carefully built service: ZooKeeper, etcd, Consul or Chubby. This chapter shows what those services offer (a tiny hierarchical or key-value store with sessions, watches and strong ordering), how to build leader election, locks, discovery and configuration out of it, and, just as important, what you should never put in one.

Why this matters

Almost every large distributed system has a handful of facts that must be right: who is the primary of this shard, which node holds this lock, which services are alive, what is the current configuration. If each team solved those with its own ad hoc protocol, there would be dozens of subtly broken consensus implementations. A coordination service concentrates the difficulty in one place that can be tested to destruction. As an engineer you will use one far more often than you will write a consensus algorithm, and the most common mistakes are not protocol bugs but misuse: stale reads, locks without fencing, herds of clients woken at once, or a coordination service used as a database.

The idea: a small, strongly consistent kernel

You know from the previous chapter how a Raft group keeps a log identical on a few servers, and from networking chapter 20 why those servers are usually 3 or 5. A coordination service puts a simple API on top of such a group (ZooKeeper uses its own protocol, Zab, which has the same shape; etcd and Consul use Raft; Google's Chubby uses Paxos). The clients are the hundreds or thousands of ordinary application processes that are not part of the consensus group. They send requests to the service and use the answers to coordinate with each other. Two ideas from the ZooKeeper paper (Hunt et al., USENIX ATC 2010) are the key to the design: expose a coordination kernel of simple primitives rather than a fixed set of features (locks, queues, barriers), and let clients build the features themselves as recipes. The case studies on Chubby (Burrows, OSDI 2006, which offered coarse-grained locks and a file-like interface) and ZooKeeper tell the history of the two designs.

Analogy: the notary's office

Picture a town where many businesses need agreed facts: who owns this plot, who is the current treasurer. Rather than each business keeping its own books, they all go to a notary's office, run by a few clerks who always agree among themselves. The notary does not do the businesses' work. It keeps a small ledger, hands out stamped, numbered entries, and promises that the ledger will say the same thing to everyone. The businesses must check with the notary at the right moments, and ask the notary to sync its ledger when they need the very latest.

Where it breaks down: a notary is consulted rarely, for important facts. Treat the office as your filing cabinet and it will be swamped; and a stamped entry says what was true at the stamp, not what is true now, which is the subject of the next sections.

ZooKeeper's data model

ZooKeeper presents a tree of znodes, like a file system with paths such as /app/config. Each znode holds a small amount of data (by design, kilobytes; there is a hard limit around a megabyte) plus metadata like a version number. The whole tree is kept in memory on every server, and changes are logged to disk. There are a few kinds of znode, and the choices are the whole toolkit:

Persistent
Stays until explicitly deleted.
Ephemeral
Tied to the client's session. When the session ends (the client closes it, or the service stops hearing from the client for the session timeout), the znode is deleted automatically. Ephemeral znodes cannot have children. They are how liveness is expressed: "this node exists exactly as long as I am alive."
Sequential
When created, the service appends a monotonically increasing counter, assigned by the parent, to the name: n_0000000001, n_0000000002. Concurrent creators get distinct numbers, giving a total order for free.

The two flags combine: an ephemeral sequential znode is a numbered ticket that vanishes if its holder dies, and it is the foundation of the recipes below.

Sessions

A client connects to one server and opens a session with a timeout. The client library sends heartbeats; if the service hears nothing within the timeout, it expires the session and deletes the client's ephemeral znodes. This is a lease (chapter 4) with exactly the usual caveat: the client and the service measure time separately, and a client that was paused or partitioned may believe it still holds something that has already expired. The client library tells its application when its connection is lost (so it can stop acting as leader), but there is an unavoidable window between "the service thinks I am dead" and "I know it". Fencing tokens (below) cover that window.

Watches

Polling the service for changes would be expensive and slow. Instead a client can set a watch when it reads a znode: a request to be told once if that znode changes, is deleted, or (for a directory) gains or loses children. In ZooKeeper a watch is a one-time trigger: it fires once and must be re-set. The notification also carries no data, just the fact that something changed, so the client must read again. An important guarantee: a client sees a watch notification before it can see the new state that caused it, so it cannot act on the change without first hearing about it.

Ordering guarantees and the stale-read trap

ZooKeeper's guarantees are carefully chosen and easy to misremember, so read them exactly:

  • Linearizable writes. All updates go through the leader and are applied in a single total order (the order of the transaction id, the zxid); each takes effect atomically at some point between request and response.
  • FIFO client order. The requests of one client are executed in the order the client sent them, even when pipelined asynchronously. This is what lets a client issue several writes without waiting for each.
  • Reads are served by the server the client is connected to, from its local copy. This makes reads fast and scalable (add servers, add read capacity), but it means reads are not linearizable: a follower that has not yet applied the latest committed write answers with the old value. What you do get is that a client never sees time go backwards: its reads reflect its own earlier writes, and if it reconnects to another server, that server must catch up to at least what the client has already seen.
  • sync. A client that needs the most up-to-date state calls sync before reading. The server then catches up with the leader first, so the following read sees every write that completed before the sync.

A coordination service is not automatically linearizable for reads

Teams often assume "ZooKeeper is strongly consistent" and read a leader-election znode without sync, then see two clients that each believe they are leader. ZooKeeper's paper is explicit about the trade: fast local reads with ordering guarantees, rather than linearizable reads. By contrast, etcd's default reads are linearizable (served through the ReadIndex mechanism of the previous chapter) and a cheaper "serializable" mode must be asked for. Always find out which kind of read you are doing.

etcd: Raft with a key-value face

etcd, the store behind Kubernetes, has a flatter model than ZooKeeper's tree: an ordered key-value space with a gRPC API. The ideas map across, with different spellings:

  • Raft underneath. Writes are committed through the Raft log (the machinery of chapter 10), with a leader, terms and snapshots. A cluster is typically 3 or 5 members.
  • Revisions. The store keeps a single, global, monotonically increasing revision counter that increases with every modification. Each key remembers the revisions at which it was created and last modified. A revision is a logical timestamp for the whole store, and old versions can be read until they are compacted away.
  • Leases. A client creates a lease with a time-to-live and attaches keys to it. It must send keep-alives; if they stop, the lease expires and all its keys are deleted. This is the same idea as an ephemeral znode, with the session split into an explicit object that several keys can share.
  • Watches. A client can watch a key or a range, from a given revision, and receives a stream of events with the new values. Because watches can start from a past revision, a client that disconnects can resume without missing events (unless they have been compacted), which fixes ZooKeeper's "one-shot, re-arm and re-read" awkwardness.
  • Transactions as compare-and-swap. A Txn request carries a set of comparisons (for instance "key K has create-revision 0", meaning it does not exist; or "key K has mod-revision R"), a list of operations to run if they all hold and another list otherwise. The whole thing is applied atomically in the log. This is a generalised compare-and-swap: "create the key only if it does not exist" is the primitive of locks and elections; "update the config only if nobody changed it since I read it" is optimistic concurrency. ZooKeeper has the same idea in a smaller form: setData with an expected version number fails if the znode has been modified.

Recipes

Everything below uses the primitives above. The caution that goes with all recipes: each is simple to write and surprisingly easy to get slightly wrong, so use a maintained client library (such as ZooKeeper's Curator or etcd's concurrency package) in production, and read what its documentation guarantees.

Leader election with ephemeral sequential nodes

Each candidate creates an ephemeral sequential znode under /election. The candidate whose znode has the lowest sequence number is the leader. Everyone else waits. If the leader's session ends, its znode vanishes and the next-lowest becomes leader. Written down, the first idea is: every candidate lists the children and sets a watch on the leader's znode. It works, and then it fails at scale: when the leader dies, all N-1 watchers are notified at once, all re-list the children, and all hit the service in the same instant. This is the herd effect (also called a thundering herd, and relevant to the cache stampedes of data chapter 14), and for a large group it can overwhelm the service exactly when the system is already recovering from a failure.

The fix is to give every candidate a different thing to watch. Each candidate lists the children, finds the znode immediately before its own in sequence order, and watches only that one. The watches form a chain: when the leader dies, only its successor is woken; if a middle candidate dies, only the one behind it is woken, which re-checks and re-points its watch. At every failure, a single client is notified.

The following Python runs both versions against a tiny in-memory fake ZooKeeper: a set of ephemeral sequential znodes, sessions that can expire, and one-shot watches on deletion. It is not a real server (no network, no ordering subtleties, no consensus), only enough to show the recipe and to count notifications. Six candidates join; then the leader's session expires, then a follower's in the middle, then the new leader's.

"""Leader election with ephemeral sequential znodes, against an in-memory fake ZooKeeper."""
from typing import Callable, Optional


class FakeZK:
    """Just enough ZooKeeper: a flat set of znodes under /election, sessions, ephemeral+sequential
    creation, children listing, and one-shot exists-watches (triggered when a node is deleted)."""
    def __init__(self) -> None:
        self.nodes: dict[str, int] = {}                     # znode name -> owning session id
        self.seq = 0
        self.sessions: set[int] = set()
        self.watches: dict[str, list[Callable[[], None]]] = {}
        self.watch_events = 0                               # how many notifications were delivered

    def connect(self) -> int:
        sid = len(self.sessions) + 1
        self.sessions.add(sid)
        return sid

    def create_ephemeral_sequential(self, session: int, prefix: str) -> str:
        name = f"{prefix}{self.seq:010d}"                   # server appends a monotonically rising counter
        self.seq += 1
        self.nodes[name] = session
        return name

    def get_children(self) -> list[str]:
        return sorted(self.nodes)

    def exists_watch(self, name: str, cb: Callable[[], None]) -> bool:
        if name not in self.nodes:
            return False
        self.watches.setdefault(name, []).append(cb)
        return True

    def expire_session(self, session: int) -> None:         # crash or network cut: ephemerals vanish
        self.sessions.discard(session)
        for name in [n for n, s in self.nodes.items() if s == session]:
            del self.nodes[name]
            for cb in self.watches.pop(name, []):
                self.watch_events += 1
                cb()


class Candidate:
    def __init__(self, zk: FakeZK, label: str, herd: bool) -> None:
        self.zk, self.label, self.herd = zk, label, herd
        self.session = zk.connect()
        self.node = zk.create_ephemeral_sequential(self.session, "n_")
        self.is_leader = False
        self.check()

    def check(self) -> None:
        if self.session not in self.zk.sessions:
            return
        kids = self.zk.get_children()
        if kids[0] == self.node:
            self.is_leader = True
            print(f"    {self.label} ({self.node[-3:]}) becomes LEADER")
            return
        # herd-free: watch only the node just before mine; herd version: watch the current leader
        target = kids[0] if self.herd else kids[kids.index(self.node) - 1]
        if not self.zk.exists_watch(target, self.check):
            self.check()                                    # it vanished between list and watch: retry


def scenario(herd: bool) -> None:
    zk = FakeZK()
    cands = [Candidate(zk, f"C{i}", herd) for i in range(1, 7)]
    print(f"  znodes: {[n[-3:] for n in zk.get_children()]}")
    roles = {1: "the leader", 3: "a follower in the middle", 2: "the new leader"}
    for victim in (1, 3, 2):
        print(f"  -- session of C{victim} ({roles[victim]}) expires")
        zk.expire_session(cands[victim - 1].session)
    print(f"  watch notifications delivered for 3 expiries: {zk.watch_events}")


print("Herd version: everyone watches the current leader's znode")
scenario(herd=True)
print("\nHerd-free version: each candidate watches only its predecessor")
scenario(herd=False)

Both versions elect the same leaders in the same order: C1, then C2, then C4 (C3 had already gone). The difference is the cost. The herd version delivered 9 notifications for the three expiries, since every remaining candidate was woken each time the leader died; the chain delivered 4 (one per expiry that mattered, plus one stale notification to C3, which had already died but still had a watch registered). With six candidates the gap is small; with six thousand it is the gap between a smooth failover and a flood. In a real client, the callback would also handle the race the code shows: the watched znode might disappear between listing and setting the watch, so the candidate re-checks (the exists_watch returning false triggers a retry).

Distributed locks

A lock is the same recipe with a different name: create an ephemeral sequential znode under /lock, hold the lock if yours is the lowest, otherwise watch your predecessor. (Read locks can be added by letting several readers proceed together, as long as no write znode precedes them.) In etcd the equivalent is a key created in a transaction guarded by "create-revision is 0", bound to a lease.

The honest warning, covered in depth in chapter 4 and the Redlock debate, is that a lock from a coordination service is a lease, not a guarantee. A client that is paused (garbage collection, a VM stall) past its session timeout loses the lock without noticing and may carry on writing to the protected resource while another client holds it. The defence is a fencing token: a number that increases with every lock grant (the znode's sequence number, ZooKeeper's zxid, or etcd's revision all work), sent with every write, so that the resource rejects any write carrying a token lower than one it has already seen. Chubby calls these "sequencers". A lock service without a fencing mechanism protects against the common case and fails in the rare, expensive one.

Service discovery

Each instance of a service creates an ephemeral znode (or a leased key) under /services/web containing its address. Clients list the children and set a watch to hear about changes. Instances that crash or become unreachable disappear when their session expires. Because liveness is tied to the session timeout, discovery is only as fresh as that timeout, and a partitioned-but-running instance may still be listed for a while; clients must still handle failed connections themselves (architecture chapter 17). The DNS-based discovery of networking chapter 9 is the lower-tech cousin.

Configuration

Store the configuration in a persistent znode or key. Clients read it at startup and watch it; on change, they re-read and reload. To update it safely from several tools, use the version or revision as a compare-and-swap: "write this config only if it is still version 7." The pattern to avoid is every client polling every second; watches make propagation fast and cheap. Keep the config small: pointers and flags, not data.

What does not belong in a coordination service

The same properties that make these services trustworthy limit what they can carry. They are replicated by consensus, which means every write is ordered through one leader, replicated to a majority and flushed to disk before it is acknowledged. The service keeps its state in memory and is sized for a modest amount of it.

  • Bulk data. Values are small by design. Large blobs, logs or user records bloat memory, snapshots and every follower's catch-up. Store a pointer (a path, a version, a hash) and keep the data in a store designed for it (data chapter 16).
  • High-throughput traffic. A consensus group does not get faster with more members; adding servers adds fault tolerance and read capacity but not write capacity. A workload that writes constantly (counters, metrics, queues of events, per-request state) belongs in a database or a log such as Kafka (chapter 17).
  • High churn. Thousands of clients creating and deleting ephemeral nodes, or each opening many watches, turns one failure into a flood of notifications and can destabilise the service itself.
  • Anything you would not want to stop the world when it is slow. If a coordination service becomes slow or unavailable, everything depending on it for leadership or locks stops or falls back. Keep it for the small set of facts that must be agreed, and design the rest of the system so that brief outages of the service are survivable (the static-stability idea of the architecture course).

A useful rule of thumb: if the data is tiny, rarely changes, and being wrong would be a disaster, it belongs there. If it is large, hot or merely nice to have, it does not.

How Kubernetes uses etcd

A concrete, familiar example, kept qualitative. In a Kubernetes cluster, all the cluster's declared and observed state, the objects you create (pods, services, deployments, configuration) is stored in etcd. Only the API server talks to etcd directly; everything else (the scheduler, the controllers, the kubelets on each node) goes through the API server, which uses etcd's watches to stream changes to those components. They react to those events: a controller sees that a deployment wants three replicas and creates what is missing. When several copies of a controller run for availability, they pick one active instance using a lease object stored in the same way, i.e. leader election. The cluster's health therefore depends on etcd's: it needs fast disks (every commit is a flush), a small odd number of members, and careful limits on how much data and churn is put in it. It is a good example of the pattern above: a tiny strongly consistent core with bulk work done elsewhere.

Try it yourself

You can reproduce the recipes on a real service.

  1. Run the fake-ZooKeeper script. Add a seventh candidate and expire the sessions in a different order, such as a middle candidate first. Does the chain version ever notify more than one client per expiry?
  2. Extend FakeZK with a version number on each znode and a set_data(expected_version) that fails on mismatch. Use it to write a configuration update that two competing tools cannot both win.
  3. Start a local etcd and use etcdctl lease grant 10, then etcdctl put k v --lease=<id>, and see the key vanish after the lease expires; try etcdctl lease keep-alive. Also try etcdctl watch k in a second terminal.
  4. With ZooKeeper's CLI, create a node with create -e -s /election/n_ x in two terminals, then close one and watch with ls -w /election.
  5. Read the Jepsen analysis of etcd in the Jepsen etcd case and decide which of your recipes depend on linearizable reads.

Distributed systems connection

Coordination services are the practical face of consensus. They also show the recurring tension of the course: leases and sessions bring time back in (chapter 3), watches are a notification mechanism built on the ordering guarantees of the log, and locks need the fencing discipline of chapter 4. Their cousins appear in distributed databases (a timestamp oracle or metadata group) and in log systems, many of which have been moving the coordination role into their own built-in Raft groups.

Key takeaways

  • A coordination service is a small, consensus-replicated store (ZooKeeper via Zab, etcd and Consul via Raft, Chubby via Paxos) that applications use to agree on a few critical facts.
  • ZooKeeper's znodes can be persistent, ephemeral (tied to a session) and sequential (numbered by the parent); ephemeral sequential nodes are the base of most recipes.
  • Writes are linearizable and a client's requests run in FIFO order, but ZooKeeper reads come from a local replica and can be stale unless the client calls sync. etcd defaults to linearizable reads.
  • etcd offers a global revision, leases, watches that can resume from a revision, and transactions that act as compare-and-swap.
  • Elect a leader with ephemeral sequential nodes, and have each candidate watch only its predecessor to avoid the herd effect.
  • A lock from such a service is a lease; use a fencing token (sequence number, zxid, revision) so a paused client cannot corrupt the resource.
  • Do not put bulk data, high-throughput writes or high churn in it. Kubernetes keeps its cluster state in etcd and takes care to keep it small and fast.

Check your understanding

Why do candidates in the ephemeral-sequential election recipe each watch only the znode just before their own?

  1. Because watches can only be set on lower-numbered znodes
  2. To guarantee that the lowest-numbered client always wins
  3. To avoid the herd effect: a failure wakes one client rather than all of them
  4. Because ephemeral nodes cannot be watched directly
If everyone watches the leader's znode, its death wakes every candidate at once and they all hit the service together. Watching the predecessor forms a chain where each failure notifies exactly one successor. The winner is still decided by the lowest sequence number either way.

A client reads a znode from its connected ZooKeeper follower and gets an old value, although another client's write to it was acknowledged a moment ago. What should the client have done?

  1. Called sync before the read, so the follower catches up with the leader first
  2. Retried the write
  3. Used a sequential znode
  4. Nothing: ZooKeeper reads are always linearizable
Writes are linearizable but reads come from the local replica and can lag. sync makes the server catch up before the next read, so the read reflects all writes completed before the sync. Reads being linearizable is the common misconception.

A client holds a lock represented by an ephemeral znode, pauses for longer than its session timeout, wakes up and writes to the protected storage. What prevents a double write?

  1. The ephemeral znode, because it still exists on the client's side
  2. A watch on the lock znode
  3. Nothing is needed; ZooKeeper cancels in-flight client operations
  4. A fencing token (such as the znode's sequence number) sent with each write, which the storage uses to reject stale holders
The session expired and the znode was deleted, so another client may now hold the lock, but the paused client does not know. Only the resource itself can tell it apart from the new holder, by comparing tokens. Watches and the znode cannot reach into the stalled process.

Which of these is the best fit for a coordination service?

  1. Storing 50 MB user uploads
  2. Recording which node currently leads shard 17
  3. A counter incremented on every request
  4. A queue of millions of events per hour
Tiny, rarely changing, critical metadata is the sweet spot. Large blobs, constant writes and high-volume queues all hit the consensus write path and memory limits, and would be better served by a blob store, a database or a log.

In etcd, how do you implement "create this key only if nobody else has"?

  1. Put the key and hope the last write wins
  2. Read the key, and put it if the read returned nothing
  3. A transaction whose comparison checks that the key's create-revision is 0, with the put as the success branch
  4. Hold a lease on the key and then delete it
Read-then-put has a race: two clients can both see "absent" and both write. A transaction evaluates the comparison and applies the operation atomically through the log, so exactly one wins. This compare-and-swap is the building block for locks and elections.

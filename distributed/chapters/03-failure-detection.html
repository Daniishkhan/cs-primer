Failure Detection, Membership & Gossip

A cluster must keep answering one question: who is still alive? You cannot ask a crashed machine, and a silent one may only be slow. This chapter turns the vague "heartbeat and timeout" of networking chapter 16 into precise properties you can reason about (completeness and accuracy), then builds up to the machinery real clusters use: adaptive phi-accrual detectors, SWIM's constant-load probing with indirect pings and suspicion, epidemic gossip that spreads news in about log n rounds, and Merkle trees that find the one differing key among millions.

Why this matters

Almost every action a cluster takes on failure (promote a replica, move shards, take a node out of the load balancer, elect a leader) is triggered by a failure detector, and every failure detector is wrong sometimes. The art is choosing how it is wrong. Too jumpy and healthy nodes get evicted, causing needless failovers and load spikes that make more nodes look dead. Too sluggish and real crashes go unnoticed for minutes. Systems with hundreds or thousands of nodes cannot afford for every node to watch every other one. Understanding detectors precisely also explains why consensus works at all (chapter 2: failure detectors are one of the ways out of FLP) and sets up chapter 4, where a wrongly accused node keeps acting as if nothing happened.

What a failure detector is

You met the heartbeat in networking chapter 16: a node says "I'm alive" every so often, and silence for long enough is taken to mean "dead". That was a mechanism. Now we want a specification: what should a failure detector promise? A failure detector is a component at each node that outputs a set of suspected nodes. It is allowed to be wrong, and it can change its mind. The question is what kinds of wrongness are tolerable.

There are two ways to be wrong. A false positive suspects a node that is actually fine. A false negative fails to suspect a node that really crashed. In 1996 Tushar Chandra and Sam Toueg gave two families of properties, one for each, and a vocabulary that is still used.

Completeness: crashes are noticed

  • Strong completeness: eventually every crashed node is permanently suspected by every correct node.
  • Weak completeness: eventually every crashed node is permanently suspected by some correct node.

Accuracy: the living are left alone

  • Strong accuracy: no correct node is ever suspected by anyone.
  • Weak accuracy: there is at least one correct node that is never suspected by anyone.
  • Eventual strong accuracy: after some unknown time, no correct node is suspected by any correct node. (Before that moment, mistakes are allowed.)
  • Eventual weak accuracy: after some unknown time, at least one correct node is never suspected by any correct node.

Notice how these echo chapter 1. Completeness is a liveness property ("eventually, permanently"): a crash can't be missed forever. Strong accuracy is a safety property ("never"). The "eventually" versions of accuracy are what partial synchrony can deliver: mistakes are allowed during the storm, but not for ever. Combining one completeness level with one accuracy level gives the classic classes:

S, strongstrongweakHard to guarantee without synchrony.
◊P, eventually perfectstrongeventually strongYes, in the partially synchronous model with adaptive timeouts.
◊S, eventually strongstrongeventually weakYes, in partial synchrony. Enough to solve consensus.

(The diamond ◊ means "eventually". There are four more classes with weak completeness, called Q, W, ◊Q, ◊W. Chandra and Toueg showed that weak completeness can be upgraded to strong by having nodes share their suspicions, so W is equivalent to S and ◊W to ◊S.) Two results make the table matter. First, Chandra and Toueg proved that consensus can be solved with an ◊S detector as long as a majority of nodes are correct, which is one more way out of FLP. Second, with Hadzilacos, they proved that ◊W is the weakest detector with which consensus is solvable: any detector that makes consensus possible can be turned into one that is at least ◊W. The practical cousin is Ω, a detector that outputs a single trusted leader, such that eventually all correct nodes trust the same correct node. That is exactly what "leader election with timeouts" delivers in Raft and Multi-Paxos: wrong during storms, right once things calm.

A perfect detector cannot exist in an asynchronous system

If a message can be arbitrarily late, then whatever deadline you pick, a live node's heartbeat might arrive just after it. To be strongly complete you must suspect silent nodes; to be strongly accurate you must never suspect a live one; with unbounded delays you cannot do both. The "eventual" classes concede that mistakes happen but promise that they stop. Real detectors are therefore ◊P-like if the network eventually settles, and they must not be trusted for anything that requires never being wrong (chapter 4).

Heartbeats and timeouts, done carefully

There are two classic designs. In the push (heartbeat) style, each node periodically sends "I'm alive" to its monitors. In the pull (ping) style, the monitor sends "are you there?" and waits for an answer. Pull costs two messages per check but measures a round trip on a single clock; push needs only one message but relies on the monitor timing the gaps between arrivals. The choices that matter are the period T (how often) and the timeout D (how long a silence is tolerated before suspecting). Roughly, a crash is detected within D plus a network delay, and each lost or late heartbeat that pushes a gap over D causes a false suspicion.

Chen, Toueg and Aguilera (2002) proposed measuring a detector by three quantities, which are worth remembering because they turn "good enough" into numbers: the detection time (how long after a real crash the node is suspected), the mistake recurrence time (how often it falsely suspects a live node) and the mistake duration (how long a false suspicion lasts before being corrected). Making the timeout longer improves the second and hurts the first. You cannot win both with a fixed timeout, which is the heart of the matter.

Analogy: the smoke alarm

A smoke alarm tuned to ignore burnt toast is slower to notice a real fire; one tuned to catch the first wisp of smoke shrieks every time you fry onions. No setting is right everywhere, and the best you can do is choose by what each kind of mistake costs.

Where it breaks down: a false alarm in a kitchen costs a few seconds of noise. A false accusation in a cluster triggers a failover, a re-replication of the node's data or a new leader election, while the "dead" node may still be alive and serving. The cost of being wrong is often much larger than the cost of being slow.

Adaptive timeouts and partial synchrony

How does a detector get ◊P in a partially synchronous network? By being adaptive. Suppose delays after GST are bounded by some Δ that nobody told us. Every time the detector suspects a node and then hears from it, it learns that its timeout was too small, and it raises the timeout. Since the timeout only ever grows, after finitely many mistakes it exceeds Δ and the mistakes stop for ever. The simulation below runs that argument. A node B heartbeats once a second and never crashes until it really does at t = 300 s. Before GST (t < 120 s) 10% of delays are huge; afterwards they are at most 1.2 s, a fact the detector does not know. We compare a fixed 1.5 s timeout against one that adds 1 s after every mistake.

import random

GST = 120.0            # after this time delays are bounded (here <= 1.2 s), but nobody tells the detector the bound
CRASH_AT = 300.0       # B really crashes here
PERIOD = 1.0           # B sends a heartbeat every second

def delay(rng: random.Random, send_t: float) -> float:
    if send_t < GST:   # before GST: usually fine, sometimes awful
        return rng.uniform(0.05, 0.3) if rng.random() < 0.9 else rng.uniform(1.0, 6.0)
    return rng.uniform(0.05, 1.2)

def simulate(adaptive: bool, timeout0: float = 1.5, seed: int = 4):
    rng = random.Random(seed)
    arrivals = sorted((k * PERIOD + delay(rng, k * PERIOD), k) for k in range(int(CRASH_AT)))
    timeout, last, i = timeout0, 0.0, 0
    suspected, mistakes_before, mistakes_after, detected_at = False, 0, 0, None
    t = 0.0
    while t < CRASH_AT + 20:
        while i < len(arrivals) and arrivals[i][0] <= t:      # deliver heartbeats
            last = max(last, arrivals[i][0]); i += 1
            if suspected:                                     # we were wrong: B is alive
                suspected = False
                if adaptive: timeout += 1.0                   # be more patient next time
        if not suspected and t - last > timeout:
            suspected = True
            if t < CRASH_AT:
                if t < GST: mistakes_before += 1
                else: mistakes_after += 1
            elif detected_at is None:
                detected_at = t
        if t >= CRASH_AT and suspected and detected_at is None:
            detected_at = t
        t = round(t + 0.05, 2)
    if detected_at is None and suspected: detected_at = t
    return mistakes_before, mistakes_after, timeout, detected_at - CRASH_AT

The fixed timeout keeps making mistakes after GST (28 of them) because its 1.5 s limit is tighter than the real worst case (a heartbeat period of 1 s plus up to 1.2 s of delay). The adaptive detector made only 2 mistakes in all, then settled; it paid for that accuracy with slower detection of the real crash (3.4 s versus 1.4 s). That is the trade-off made visible, and the eventual-accuracy guarantee of ◊P in practice.

Phi accrual: a dial instead of a switch

A fixed or even adaptive timeout answers "dead or alive?" with a single yes/no at one threshold. Naohiro Hayashibara and colleagues (2004) noticed that the useful quantity is how suspicious the silence is, and that different applications want different thresholds. Their phi accrual failure detector outputs a continuous value φ ("phi").

The detector keeps a sliding window of recent gaps between heartbeats and fits a distribution to it (the original paper uses a normal distribution; some implementations use an exponential approximation). Given the time since the last heartbeat, it computes the probability that a gap at least that long would occur if the node were still alive, and reports

φ = −log10( P(next gap is at least as long as the silence so far) )

So φ = 1 means a silence this long happens about 1 time in 10 for a healthy node, φ = 2 about 1 in 100, φ = 3 about 1 in 1,000, and φ = 8 about 1 in 100 million. The application picks a threshold: a failover manager that is expensive to trigger might say 8 (Cassandra's configuration default, phi_convict_threshold, is 8), a UI that can tolerate flicker might say 3. Systems such as Cassandra and Akka use variants of this detector.

import math, random
from collections import deque

class PhiAccrual:
    """Phi accrual detector (Hayashibara et al. 2004), normal-distribution flavour."""
    def __init__(self, window: int = 200, min_std: float = 0.05):
        self.gaps = deque(maxlen=window)
        self.last: float | None = None
        self.min_std = min_std
    def heartbeat(self, now: float) -> None:
        if self.last is not None:
            self.gaps.append(now - self.last)
        self.last = now
    def phi(self, now: float) -> float:
        n = len(self.gaps)
        mean = sum(self.gaps) / n
        std = max(math.sqrt(sum((g - mean) ** 2 for g in self.gaps) / n), self.min_std)
        # P(next gap is at least this long) under Normal(mean, std)
        p_later = 0.5 * math.erfc(((now - self.last) - mean) / (std * math.sqrt(2)))
        return -math.log10(max(p_later, 1e-300))

rng = random.Random(11)
for name, jitter in [("steady network (std ~ 0.05 s)", 0.05), ("jittery network (std ~ 0.4 s)", 0.4)]:
    d, t = PhiAccrual(), 0.0
    for _ in range(300):                       # learn from 300 heartbeats, ~1 s apart
        t += max(0.1, rng.gauss(1.0, jitter)); d.heartbeat(t)
    print(name)
    print("  silence so far :", "  ".join(f"{s:>5.1f}s" for s in (1.0, 1.2, 1.5, 2.0, 3.0)))
    print("  phi            :", "  ".join(f"{d.phi(t + s):>6.2f}" for s in (1.0, 1.2, 1.5, 2.0, 3.0)))

Both networks have heartbeats about one second apart, but look at the same 1.5 s of silence. On the steady network (standard deviation about 0.05 s) that silence is wildly improbable and φ jumps past 20: the node has almost certainly failed. On the jittery network (standard deviation about 0.4 s) the same silence has φ = 1.0, an unremarkable one-in-ten delay, and the detector waits. The detector learns what "normal" looks like on this link instead of using a number someone guessed. (The value 300 is a cap from clamping the probability at 10-300.) Two cautions: φ assumes the window of past gaps is representative (it is badly calibrated right after start-up or after a regime change), and the normal-distribution model underestimates heavy tails such as GC pauses, which is why implementations clamp the standard deviation from below and why thresholds are conservative.

Scaling up: who watches whom?

With n nodes, all-to-all heartbeating costs n(n−1) messages per period: 999,000 per second across a 1,000-node cluster at one heartbeat per second, and every node handles about 2,000 packets a second, just for liveness. A single central monitor cuts the total to about n messages per period but becomes a bottleneck and a single point of failure. A ring (each node watches its neighbour) is cheap but slow to spread news and fragile when two neighbours die together. What we want is constant work per node regardless of cluster size, and detection that doesn't depend on any one watcher. That is what SWIM provides.

SWIM: scalable failure detection and membership

SWIM (Abhinandan Das, Indranil Gupta and Ashish Motivala, DSN 2002: Scalable Weakly-consistent Infection-style Process Group Membership Protocol) splits the problem into two components: a failure detector that finds suspects, and a dissemination component that spreads membership news. Both are designed so that each node does a constant amount of work per period, however large the group.

The protocol period

Time is divided into protocol periods of length T′ (say one second). In each period, every member Mi does the following.

  1. Direct probe. Pick one other member Mj at random and send it a ping. Wait for an ack for a short timeout (several times the typical round trip, but much less than T′).
  2. Indirect probes. If no ack arrives, pick k other members at random and send each a ping-req(Mj). Each helper pings Mj on Mi's behalf and, if Mj answers, relays that ack back to Mi.
  3. Verdict. If by the end of the period neither the direct ack nor any relayed ack arrived, Mi declares Mj failed (in the base protocol), or, in the improved version that nearly every implementation uses, marks it suspect (below).
Step through

One SWIM protocol period, with a lossy link

  1. Direct ping. Prober A picks a random member, B, and pings it. The ping arrives.
  2. The ack is lost. B answers, but its ack is dropped on the way back. B is perfectly healthy; the problem is the path between A and B (an overloaded link, a flaky cable, an asymmetric partition).
  3. Timeout. A hears nothing. If it accused B now it would be wrong.
  4. Ask a helper. A picks a random member H and sends ping-req(B): "please probe B for me". (With k helpers this is sent to k members at once.)
  5. The helper probes B. H pings B over a different network path.
  6. B answers H. The ack reaches H.
  7. H relays. H tells A that B is alive. One failing path was not enough to condemn B, because a second, independent path worked. This is the whole reason for indirect probes.

Why indirect probes work, in numbers

If each message is lost independently with probability p, a direct ping-ack fails with probability 1−(1−p)2. An indirect probe through one helper needs four messages (A→H, H→B, B→H, H→A) and fails with probability 1−(1−p)4. With k helpers (all must fail) the false-suspicion probability is about (1−(1−p)2)·(1−(1−p)4)k. The same script also checks the other famous SWIM number: with random target selection, a crashed member is probed by somebody within e/(e−1) ≈ 1.58 periods on average, independent of cluster size. (Derivation: each of the n−1 other members picks a given member with probability 1/(n−1), so the chance nobody does in one period is (1−1/(n−1))n−1 → 1/e, and the expected number of periods until someone does is 1/(1−1/e) = e/(e−1).)

import math, random

# 1) How long until SOMEONE probes a crashed node? (random target selection)
def periods_until_probed(rng: random.Random, n: int) -> int:
    period = 0
    while True:
        period += 1
        # each of the n-1 live members picks one of the other n-1 members uniformly
        if any(rng.randrange(n - 1) == 0 for _ in range(n - 1)):   # "== 0" means: picked the dead one
            return period

rng = random.Random(5)
for n in (10, 100, 1000):
    runs = [periods_until_probed(rng, n) for _ in range(4000)]
    print(f"n={n:<5} mean periods until first probe: {sum(runs)/len(runs):.3f}")
print(f"theory e/(e-1) = {math.e/(math.e-1):.3f}  (the limit for large n)\n")

# 2) False suspicions of a HEALTHY node when each message is lost independently with prob p
def false_suspicion(rng: random.Random, p: float, k: int) -> bool:
    ok = lambda m: all(rng.random() >= p for _ in range(m))     # m messages must all survive
    if ok(2):                   # ping + ack
        return False
    return not any(ok(4) for _ in range(k))     # ping-req, helper ping, helper ack, relayed ack

print(f"{'loss p':>7}{'k=0 (direct only)':>22}{'k=3 helpers':>16}{'theory k=0':>13}{'theory k=3':>12}")

Measured and formula agree. At 10% loss, direct-only probing falsely accuses a healthy node 19% of the time; three helpers cut that to under 1%. At 30% loss (a very bad link), 51% falls to 22%, so helpers help a lot but cannot save you from a truly sick network. A caution that the numbers hide: independence is the optimistic assumption. If B itself is overloaded or paused (rather than the links being flaky), every path to B fails together, and no number of helpers helps. This is the same uncertainty as ever: SWIM cannot tell "B is dead" from "B is too slow to answer anyone". Later work such as HashiCorp's Lifeguard extensions adds one more signal, a node's awareness of its own health: if I am the one who is slow (missing acks from everyone), I should accuse others less eagerly.

Because members are picked at random, a crashed member is probed on average within 1.58 periods, but unluckily it could escape for many periods. The SWIM paper shows how to make detection time bounded by walking through a randomly shuffled list of members round-robin instead of choosing fresh at random each time, so that successive probes of the same member by one prober are at most about 2n periods apart (the paper's bound is 2n−1).

Suspicion and incarnation numbers

Declaring a node dead on a single failed round is risky: transient problems cause false removals, and a removed node that is actually alive must then do a clumsy rejoin. The suspicion mechanism adds a middle state. When a probe fails, the prober doesn't announce "dead" but "suspect(B)". B stays a member, on probation. If B hears the rumour, it can refute it, and if nobody refutes within a suspicion timeout the suspect is confirmed dead and removed.

Refutation needs care. Rumours travel around the cluster by gossip, in no particular order, and a stale rumour may arrive after a fresh one. Suppose B was suspected, refuted with "alive(B)", and then an old copy of "suspect(B)" still circulating reaches a node that had already accepted the refutation. Without any way to order the messages, the old suspicion would knock B back into suspect, then B would refute again, and so on: flapping, or worse, the old suspicion wins and a healthy node is evicted. The fix is the incarnation number: each member holds a counter that only that member may increase. The rules for combining two pieces of news about the same member are:

  • alive(B, i) overrides suspect(B, j) only if i > j. B refutes by incrementing its own incarnation and broadcasting alive(B, i+1); the old suspect(B, i) then loses everywhere, however late it arrives.
  • suspect(B, i) overrides alive(B, j) if i ≥ j. A fresh accusation at the current incarnation is valid until B answers it with a higher number.
  • confirm(B) (declared dead) overrides everything.

Check each rule by removing it. If "alive overrides suspect" needed only i ≥ j, then an old alive(B, i), sent before the accusation, would wipe out a valid suspect(B, i) (and the suspicion would override it again): the two would flap, and a genuinely failing node could be forgiven by a stale message. If only B can raise its incarnation, no gossip can forge a refutation on B's behalf. That "only the owner increments" rule is a tiny logical clock per member (networking chapter 17) that orders the member's own history.

Dissemination by piggybacking

How does the news (a join, a suspicion, a confirmation) reach everyone? SWIM doesn't send extra messages. It piggybacks a handful of recent membership updates onto the pings and acks it is sending anyway. Each update is repeated on a bounded number of messages, proportional to log n, so it reaches the whole group with high probability while the per-node load stays constant. This is infection-style dissemination: exactly the epidemic process we analyse next. SWIM is "weakly consistent" because different members may briefly hold different views of the group; in exchange it never needs a coordinator.

Epidemic gossip: why news travels in about log n rounds

Gossip protocols were described by Alan Demers and colleagues at Xerox PARC in 1987 (Epidemic Algorithms for Replicated Database Maintenance), borrowing the mathematics of disease spread. The model is simple: in each round, every node picks one (or a few) random peers and exchanges information. Three flavours differ in who talks:

  • Push: an informed node tells its peer.
  • Pull: a node asks its peer "anything new?".
  • Push-pull: both directions in one exchange.

The mathematics, in two phases

Say one node starts with a rumour, and consider push with fan-out 1.

Phase 1: exponential growth. When few nodes know, almost every message goes to a node that doesn't. So the informed count roughly doubles each round: 1, 2, 4, 8, … After about log2 n rounds, around half the cluster knows.

Phase 2: the end game. Now most nodes are informed, and the uninformed ones are hard to hit. If a fraction u of nodes is uninformed and almost every node pushes to someone, a given uninformed node escapes all pushes with probability about (1−1/n)n ≈ e−1, so u shrinks by a constant factor 1/e each round. Getting from a constant fraction down to fewer than one node (u < 1/n) takes about ln n further rounds. Boris Pittel's 1987 analysis of rumour spreading made this precise: push gossip informs everyone in log2 n + ln n + O(1) rounds with high probability. It's logarithmic in the cluster size: a million nodes need around 20 + 14 = 34 rounds, not a million.

Pull behaves differently in the end game. An uninformed node that pulls from a random peer remains uninformed only if the peer is also uninformed, probability u, so u becomes u2 each round: the uninformed fraction collapses doubly exponentially (1/2, 1/4, 1/16, 1/256, …) and the tail takes only about log2 log2 n rounds. Push is fast early and slow late; pull is slow early (few have anything to give) and fast late; push-pull gets the best of both. A larger fan-out k changes the growth factor from 2 to k+1 per round in phase 1, so the log shrinks by a constant factor; it costs more messages for faster spread. Let us check all of this with a simulation.

import math, random

def rounds_to_all(n: int, mode: str, rng: random.Random, fanout: int = 1) -> int:
    """Synchronous rounds. One node starts with the rumour; each round every node
    contacts `fanout` random peers. Returns the round in which the last node learns it."""
    infected = {0}
    rounds = 0
    while len(infected) < n:
        rounds += 1
        new = set()
        for node in range(n):
            for _ in range(fanout):
                peer = rng.randrange(n - 1)
                peer += peer >= node                      # a random OTHER node
                if mode in ("push", "push-pull") and node in infected:
                    new.add(peer)                          # I tell the peer
                if mode in ("pull", "push-pull") and peer in infected:
                    new.add(node)                          # I ask the peer, it tells me
        infected |= new
    return rounds

rng = random.Random(2024)
print(f"{'n':>7}{'push':>8}{'pull':>8}{'push-pull':>11}{'log2 n':>9}{'log2 n + ln n':>15}")
for n in (100, 1000, 10000):
    runs = 20 if n < 10000 else 5
    row = [sum(rounds_to_all(n, m, rng) for _ in range(runs)) / runs for m in ("push", "pull", "push-pull")]

Analogy: office gossip

Each morning every employee tells whatever they have heard to one random colleague. Within a few days the news is everywhere, even if the CEO never sends an email, and it keeps spreading when a few people are on leave. There's no single announcer to lose.

Where it breaks down: real gossip can be distorted; in a computer cluster the messages are copies, so the risk is not distortion but staleness (old news spreading as readily as new, which is why updates carry version numbers or incarnations) and a small but non-zero probability that some node is missed.

Rumours and anti-entropy

Demers et al. described two ways to use the idea. Rumour mongering spreads new updates ("hot rumours") fast, and nodes stop spreading an update once they hit already-informed peers several times. It is cheap and quick, but with small probability some nodes never hear it. Anti-entropy is the slow, thorough partner: periodically each node picks a random peer and the two compare their whole state and reconcile any differences ("entropy" is the disorder between replicas). Anti-entropy is guaranteed to finish eventually, and real systems combine both: rumours for speed, anti-entropy for the guarantee. The remaining problem is cost: comparing everything with a peer is expensive when the state is millions of keys.

Anti-entropy with Merkle trees

The trick is to compare summaries first. A Merkle tree (Ralph Merkle's hash tree) has a hash for each key range at the leaves, and each parent holds the hash of its children's hashes. The root hash summarises the whole data set: if two replicas' roots are equal, the replicas are identical (up to hash collisions), and the comparison costs a single hash. If the roots differ, compare the two children; descend only into the children whose hashes differ, and skip equal subtrees entirely. The walk ends at the leaf ranges that differ, and only those key ranges need to be exchanged.

This is the mechanism Dynamo used to repair replicas after a long outage, and similar designs appear in Cassandra's repair and other Dynamo-inspired stores. Here it is for 100,000 keys in 1,024 ranges, with 5 keys made stale on one replica:

import hashlib, random

def h(*parts: bytes) -> bytes:
    return hashlib.sha256(b"|".join(parts)).digest()

class MerkleTree:
    """Fixed key space split into 2**depth ranges (leaves). Leaf hash = hash of its sorted items."""
    def __init__(self, data: dict[int, str], depth: int, keyspace: int):
        self.depth, self.keyspace = depth, keyspace
        leaves = [[] for _ in range(2 ** depth)]
        for k, v in sorted(data.items()):
            leaves[k * 2 ** depth // keyspace].append(f"{k}={v}".encode())
        level = [h(*items) for items in leaves]
        self.levels = [level]
        while len(level) > 1:
            level = [h(level[i], level[i + 1]) for i in range(0, len(level), 2)]
            self.levels.append(level)
        self.levels.reverse()                  # levels[0] = [root], levels[-1] = leaves

def diff(a: MerkleTree, b: MerkleTree):
    """Walk down from the root, only into subtrees whose hashes differ.
    Returns (differing leaf ranges, number of hash comparisons)."""
    compared, bad, stack = 0, [], [(0, 0)]
    while stack:
        lvl, i = stack.pop()
        compared += 1
        if a.levels[lvl][i] == b.levels[lvl][i]:
            continue
        if lvl == a.depth:
            bad.append(i)
        else:
            stack += [(lvl + 1, 2 * i), (lvl + 1, 2 * i + 1)]
    return sorted(bad), compared

KEYS, DEPTH = 100_000, 10                      # 100k keys, 1024 leaf ranges
rng = random.Random(3)
replica_a = {k: f"v{k}" for k in range(KEYS)}
replica_b = dict(replica_a)
for k in rng.sample(range(KEYS), 5):           # 5 keys went stale on B (missed writes)
    replica_b[k] = "stale"
ta, tb = MerkleTree(replica_a, DEPTH, KEYS), MerkleTree(replica_b, DEPTH, KEYS)
bad, compared = diff(ta, tb)
print(f"keys per replica        : {KEYS:,}")
print(f"stale keys              : 5")
print(f"leaf ranges that differ : {len(bad)} of {2**DEPTH}  (each covers ~{KEYS // 2**DEPTH} keys)")
print(f"hash comparisons used   : {compared}   (naive: compare all {KEYS:,} keys)")
print(f"identical replicas      : {diff(ta, ta)[1]} comparison")
keys per replica        : 100,000
stale keys              : 5
leaf ranges that differ : 5 of 1024  (each covers ~97 keys)
hash comparisons used   : 85   (naive: compare all 100,000 keys)
identical replicas      : 1 comparison

Five stale keys were found with 85 hash comparisons, identical replicas cost a single comparison, and only five ranges of about 97 keys each need to be synchronised. In general, finding d differing ranges among L costs at most about 2·d·log2 L comparisons. The engineering questions are the leaf size (smaller ranges mean less data to re-send but a bigger tree), keeping the tree up to date as keys change (hash incrementally, or rebuild periodically in the background), and aligning the ranges with the data's partitioning so that two replicas of a range build identical trees.

From detection to membership, and its limits

A membership service tells each node the current list of live members, its view. There are two quite different ways to provide it:

Gossip-based (SWIM-like)Consensus-based (Raft, ZooKeeper, etcd)
ViewsEventually consistent; two nodes may briefly disagreeOne agreed history of views
ScaleThousands of nodes, constant load per nodeA small group (3, 5 or 7 nodes) for the decisions
Failure modeKeeps working through partitions, may split into several viewsStops making progress without a majority
Good forDiscovering peers, rough liveness, routing hints. Serf and Consul's membership layer are built on a SWIM implementation (HashiCorp's memberlist).Anything where two nodes must not disagree: who is the leader, who owns a shard, configuration.

The consequence is a rule of thumb used throughout the rest of the course: a failure detector is a hint, never a fact. It is fine for deciding where to try sending a request. It is not fine as the sole basis for "I am the only one who may write to this disk", because the node you condemned may be alive, paused, or just partitioned from you, and still acting. Closing that gap is the topic of chapter 4. Real failures are also less tidy than "up" or "down": a node can pass heartbeats while failing real requests (Huang et al. called this gray failure in 2017), and a switch that drops only some traffic produces the partial partitions of the Cloudflare case study, which defeat naive detectors because nodes disagree about who is alive.

Go deeper: choosing k, the timeout, and the suspicion timeout optional

The SWIM paper derives that the false positive rate falls exponentially in k, while the message load grows only linearly, so small constants (k around 3, in many implementations) already work well. The ping timeout should be a few multiples of the round-trip time (so one retransmission or a short pause doesn't trigger a probe), and well below T′ so there is room for the indirect round. The suspicion timeout is commonly scaled with log n, because refutation itself must spread by gossip: the bigger the cluster, the longer the rumour needs to reach B and the refutation to come back. Too short a suspicion timeout turns the suspicion mechanism into a no-op. Also, a node that starts up or is under heavy load should be especially careful: it is the likeliest to be the one that is slow.

Distributed systems connection

Failure detectors are the bridge between the theory of chapters 1 and 2 and every practical protocol. Leader election in Raft (chapter 10) is an Ω detector built from randomized timeouts. Coordination services (chapter 11) expose liveness as sessions with timeouts. The gossip epidemic reappears in CRDT replication and anti-entropy (chapter 15), and Merkle comparison in repair and sync (chapter 17). And the key warning, that a node you suspect may still be running, is the entire subject of chapter 4.

Key takeaways

  • A failure detector outputs suspicions and is judged on completeness (crashes are eventually noticed) and accuracy (the living are not accused). A perfect detector is impossible in an asynchronous system. Partial synchrony gives you ◊P: mistakes are allowed at first but eventually stop. ◊W is the weakest detector that solves consensus.
  • A fixed timeout trades detection time against false alarms. Adaptive timeouts that grow after each mistake make finitely many mistakes once the network stabilises.
  • Phi accrual reports a continuous suspicion level, −log10 of the probability that the silence is normal, learned from the link's own history; applications choose their threshold.
  • SWIM gives constant load per member: one random ping per period, k indirect ping-req probes if it fails, a suspect state before declaring death, incarnation numbers so only the accused can refute, and updates piggybacked on existing messages. A crashed member is probed within e/(e−1) ≈ 1.58 periods on average.
  • Gossip spreads news in about log2 n + ln n rounds for push (doubling, then a constant-factor end game); pull has a quadratic end game; push-pull is fastest. It tolerates loss and crashes without any coordinator.
  • Merkle trees make anti-entropy cheap: compare roots, descend only into differing subtrees, and find d differences among L ranges in about 2·d·log L hash comparisons.
  • A failure detector is a hint, not a fact. Use it to decide where to try, never as proof that the accused node has stopped acting.

Check your understanding

What does strong completeness demand of a failure detector?

  1. No correct node is ever suspected
  2. Some correct node eventually suspects every crashed node
  3. Eventually every crashed node is permanently suspected by every correct node
  4. Suspicions are always correct at the moment they are made
Completeness is about not missing crashes, and "strong" means every correct node eventually and permanently suspects each crashed node. The first option is (strong) accuracy, the second is weak completeness, the fourth is not a standard property and is impossible in asynchronous systems.

In a partially synchronous network, why does a detector that increases its timeout after each false suspicion eventually stop making mistakes?

  1. Because after GST delays are bounded, and a timeout that only grows must eventually exceed that bound
  2. Because larger timeouts make the network faster
  3. Because it learns which nodes will crash
  4. It does not; adaptive timeouts only delay mistakes
The argument needs a bound that exists but is unknown, and a timeout that never decreases. Each mistake raises the timeout; since the bound is finite, only finitely many mistakes can occur. The price is slower detection of real crashes.

A phi accrual detector reports φ = 3 for a node. Which is the best reading?

  1. The node has missed 3 heartbeats
  2. The node is dead with probability 99.9%
  3. The node has been silent for 3 seconds
  4. A silence this long would occur for a healthy node roughly once in a thousand heartbeats, so suspicion is rising; whether to act depends on the application's threshold
φ = −log10 of the probability that a healthy node's gap would be at least this long, so φ = 3 means about 0.1%. That is evidence, not proof: it is the chance of the silence given that the node is alive, not the chance that the node is dead given the silence.

In SWIM, why does a prober ask k other members to ping a silent target before suspecting it?

  1. To increase the load on the target so that it answers
  2. The failure may lie on the path between prober and target; probing through different paths avoids condemning a healthy node because of one bad link
  3. To elect a leader
  4. To spread membership updates faster
A lost ping or ack on the A–B path says nothing about B. Helpers use independent paths, so the probability that all of them fail together drops quickly with k. It cannot help if B itself is overloaded or paused, because then every path fails.

Node B refutes a suspicion with alive(B, 5), but a delayed suspect(B, 4) then reaches another member that has already seen the refutation. What happens, and why are incarnation numbers needed?

  1. The member marks B suspect again, because the newest message always wins
  2. The member removes B from the group
  3. The stale suspicion is ignored: alive with a higher incarnation overrides suspect with a lower one, and only B can raise its own incarnation
  4. The two messages cancel and B is dead
Gossip delivers messages in no particular order, so "latest received" is meaningless. The incarnation number, owned and incremented only by B, gives a total order on B's own claims, so stale accusations lose however late they arrive.

Roughly how many rounds does push gossip with fan-out 1 need to inform all n nodes, and where does the time go?

  1. About log2 n + ln n: roughly log2 n rounds of doubling, then about ln n to reach the last stragglers
  2. About n rounds, one per node
  3. About 1 round, because everyone talks at once
  4. About n log n rounds
Early on the informed set doubles each round (log2 n rounds to reach half). In the end game each uninformed node escapes with probability about 1/e per round, so the uninformed fraction shrinks by a constant factor and needs about ln n more rounds. Pull's end game is quadratic and therefore faster.

Two replicas of a 1,000,000-key range have exactly one stale key. Why is Merkle-tree comparison much cheaper than comparing every key?

  1. Because hashes are smaller than keys, so the total bytes are fewer by a constant factor only
  2. Because equal subtrees have equal hashes and are skipped; the walk follows only the path to the differing range, about log L comparisons per difference
  3. Because the replicas stop caring about stale keys
  4. Because it avoids the network entirely
The tree turns "find the difference" into a search down one root-to-leaf path, costing about 2 log2 L hash comparisons for one difference, instead of a number proportional to the number of keys.

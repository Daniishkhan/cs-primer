Consistency Models, Precisely

"Strongly consistent" and "eventually consistent" are slogans. This chapter replaces them with definitions you can test. You will see what an operation is, what a history is, what exactly makes a history linearizable (and why that is different from sequentially consistent, and from serializable), why one of those properties composes and the other does not, and how tools like Jepsen check the claims of real databases. You will also run a linearizability checker, write your own, and play with one in the page.

Why this matters

Every replicated system makes a promise about what clients can observe, and almost every outage story about data (a lost write, a double-spent coupon, a lock held by two owners) is a story about a promise that was weaker than somebody assumed. If the promise is vague, the argument "it's consistent" can never be settled. If it is a definition, a program can check it against a recorded history of what clients actually saw, and that is how Jepsen found bugs in many well-known databases. Senior engineers are expected to name the model a system gives, say what it forbids, and say what it costs. This chapter is the vocabulary for that.

Start with what a client can observe

In networking chapter 18 you climbed a "consistency ladder": linearizability at the top, then sequential, causal, session guarantees, and eventual consistency at the bottom, each explained with an example. That was the tour. Here we stop pointing at rungs and build the ladder from definitions, because the interesting facts (what composes, what is checkable, what implies what) only appear once the definitions are exact.

The first decision is what we are allowed to talk about. A consistency model is a promise about what clients see, not about how replicas are arranged inside. So the only vocabulary we need is the outside view of a system:

  • An operation is one call by one client, such as write(x, 1) or read(x). It has an invocation, the moment the client sends the request, and a response, the moment the client gets the answer (a returned value, or just "ok").
  • So an operation is not a point in time. It is an interval, from invocation to response. During that interval the request is travelling, queued, replicated, and answered, and the client knows nothing about what is going on inside.
  • Two operations are concurrent if their intervals overlap. Otherwise one finished before the other began, and we say the first precedes the second in real-time order.
  • A history is the record of all invocations and responses, from all clients, in the order they happened by an ideal observer's clock. It is what a test harness (or a very patient auditor) would write down.

One word on the clock. The ideal observer's clock is a device for the definitions; nodes do not have access to it, and we met in networking chapter 17 why real clocks cannot give it to them. The definitions only use it to say "this response happened before that invocation", which a test harness running on one machine can observe directly.

Next we need to say what a correct answer is. For each kind of object we fix a sequential specification: how the object behaves when operations happen one at a time with nothing overlapping. For a register (a single variable) it is the obvious one: a read returns the value of the latest write before it, or the initial value if there was none. For a queue: dequeue returns the oldest item that has not yet been dequeued. The sequential spec is the "what we would get on one machine with one thread" behaviour. Every consistency model in this chapter is a statement about how much of that behaviour survives when the object is replicated and the operations overlap.

Analogy: one whiteboard in a shared office

Imagine a single whiteboard in an office with a number on it. Anyone can walk up, read it, or rub it out and write a new number. Because there is only one board, there is a simple truth about "the current value" at every moment. A replicated database is a building with several whiteboards and clerks running between them copying numbers. The question a consistency model answers is: how closely do the visitors' experiences still look like there was only one board?

Where it breaks down: walking up to a whiteboard is nearly instant, so it has an obvious moment of effect. A request to a database takes time, and the interval between sending and hearing back is exactly where the subtlety lives.

Linearizability

The definition is from Maurice Herlihy and Jeannette Wing's 1990 paper "Linearizability: A Correctness Condition for Concurrent Objects". Stated for the histories we just built:

Definition: linearizability

A history is linearizable if there is a way to put all its operations into a single sequential order such that:

  1. the order is legal according to the object's sequential specification (for a register, every read returns the latest write before it in the order), and
  2. the order respects real time: if operation a responded before operation b was invoked, then a comes before b in the order.

Operations that overlap may be ordered either way. That freedom is the whole point.

Equivalently, you can pick, for each operation, one instant strictly inside its own interval, its linearization point, so that if every operation took effect instantly at its point, the results would be exactly what the one-copy object would return. The sequential order is just the points sorted by time. The two phrasings are the same statement: the second one explains why the real-time condition is natural, since a point inside the interval cannot be later than the response or earlier than the invocation.

What the definition is really saying

Three consequences are worth stating plainly, because each one is a place engineers go wrong.

1. "Latest" means latest in the order, and the order only has to match real time where real time speaks. A read that overlaps a write may legitimately return either the old or the new value. What it may not do is return something the one-copy object could not have returned at any instant within the interval. In particular, once any client has seen the new value, every operation that begins after that response must see it as well. That is the football-score example from networking chapter 18, now stated exactly, and it is what the widget below calls a "new/old inversion" when it fails.

2. The check is on the whole history, not on each operation. No single read is "wrong" in isolation; a read of 0 is perfectly fine unless something else in the history forces the write before it. This is why consistency is checked by searching for an order, and why bugs often only show up as a specific combination of concurrent operations.

3. Operations without a response still matter. If a client sent a write and then timed out (networking chapter 16), the write is pending: it may have taken effect at any time after its invocation, or never. The formal definition lets a pending operation either be dropped from the order or completed with any legal response. Checkers must do the same, or they either report false alarms or miss real bugs. Such "indeterminate" operations are where much of the practical difficulty comes from.

Three confusions about the word "consistent"

(1) Linearizability is a property of single operations on single objects. It says nothing about groups of operations (that is what transactions, below, are for). (2) It is the "C" of CAP, and it is not the "C" of ACID: ACID's consistency means "the application's invariants hold", which is the application's responsibility. (3) It does not mean "reads return the freshest value on some wall clock". It means "there is an order, consistent with who-finished-before-whom, in which every answer is correct". Two clients with perfect clocks can see different values at the same instant and the history can still be linearizable, as long as those operations overlap.

Sequential consistency

Leslie Lamport defined sequential consistency in 1979, for multiprocessor memory, as a requirement that the result of any execution be the same as if all processors' operations had been executed in some sequential order, and the operations of each individual processor appeared in this order in the sequence specified by its program. In our terms:

Definition: sequential consistency

A history is sequentially consistent if there is a single sequential order of all operations that is legal for the object and that respects each client's own order (program order). It need not respect real time between different clients.

Compare the two definitions side by side. Linearizability demands an order that agrees with real time across all clients. Sequential consistency demands an order that agrees with each client's own sequence, but is otherwise free. Every linearizable history is sequentially consistent (an order that respects more also respects less), but not conversely. Here is the distinction on the four histories from the widget, produced by the checker we will build later in this chapter:

(W(client, value, call, return) and R(...) are the helper constructors from the listing; the times are the interval ends.) The stale read passes sequential consistency because B and A are different clients: the model is happy to say "B's read happened first" even though B asked well after A heard "ok". The last history fails both models: one client reads back an older value than it just wrote, and that is a violation of its own program order. Chapter 6 gives that failure a name, read-your-writes.

Where sequential consistency appears, and what it is missing

Sequential consistency is the model most programmers assume a shared variable has. It is also surprisingly expensive and surprisingly rare. Most CPUs do not provide it by default for ordinary loads and stores, because buffering writes is much faster; languages that promise it (for example, sequentially consistent atomics in C++ and Java's volatile) use special instructions to get it. If the shared-variable world of systems chapter 12 felt tricky, this is the same family of ideas on one machine.

For a distributed store, the issue is the missing real-time condition. Under sequential consistency a replica can stay arbitrarily far behind and the model never complains, provided nobody is ever shown things out of order relative to their own session. In an everyday sense it is a promise about order, not about freshness. That makes it a poor fit when clients talk to each other outside the system ("I just saved it, go look"), because their conversation is the real-time edge the model ignores. Linearizability is what you get when the real-time edges are honoured everywhere.

Local versus global: why linearizability composes and sequential consistency does not

A system is rarely one register. It is thousands of keys, or many objects. Suppose each of those, taken alone, satisfies a model. Does the whole system?

For linearizability, yes, and this is one of the main results of Herlihy and Wing's paper, usually called locality (or compositionality): a history is linearizable if and only if, for every object, the sub-history of operations on that object is linearizable. That is a powerful engineering fact. You can build a store by making each key linearizable independently, for example one consensus group per shard, and the composition is automatically linearizable. A checker can also split a big history by key and check the pieces separately, which is what makes testing practical (below).

Sequential consistency does not have this property. Take two registers, x and y, both initially 0, and two clients, each of which writes one register and then reads the other:

Look at x alone: P1 writes 1, P2 reads 0. Sequential consistency accepts: put P2's read first. Look at y alone: symmetric, accepted. Now look at both together. P1's read of y returned 0, so it must come before P2's write of y; P2's read of x returned 0, so it comes before P1's write of x. Add the clients' own orders and you get a cycle. Let the checker confirm it:

from lin import W, R, check

# Two registers, two clients. Each client writes one register, then reads the other.
h = [W("P1", 1, 0, 1, "x"), R("P1", 0, 2, 3, "y"),
     W("P2", 1, 0, 1, "y"), R("P2", 0, 2, 3, "x")]

for reg in "xy":
    only = [op for op in h if op.obj == reg]
    print(f"register {reg} alone:", "sequentially consistent" if check(only, realtime=False) else "NOT")
print("both together:   ", "sequentially consistent" if check(h, realtime=False) else "NOT sequentially consistent")
register x alone: sequentially consistent
register y alone: sequentially consistent
both together:    NOT sequentially consistent

This is not a curiosity; it is the reason sequential consistency is awkward to build systems from. If each shard promises sequential consistency, the system as a whole does not, and you cannot reason one key at a time. With linearizability you can. The experiment below tests the locality theorem on 400 random histories of two registers (the generator, random_history, simulates registers that really are atomic, then makes about one read in seven lie; it is listed with the other code at the end of the chapter):

import random
from lin import check
from histgen import random_history

rng = random.Random(42)
agree = lin_count = 0
for _ in range(400):
    h = random_history(rng, 8, lie=0.15)                   # 8 ops on two registers, some reads lie
    whole = check(h) is not None
    parts = all(check([o for o in h if o.obj == r]) is not None for r in ("x", "y"))
    agree += whole == parts
    lin_count += whole
print(f"whole history vs each register alone: {agree}/400 verdicts agree ({lin_count} histories were linearizable)")
whole history vs each register alone: 400/400 verdicts agree (240 histories were linearizable)

As the theorem says, the verdicts always agree: the whole is linearizable exactly when every key is. (A test like this can never prove a theorem. It does catch a wrongly implemented checker.)

Per-key linearizability is not a transaction

Locality is good news and a limit at once. A store where every key is linearizable can still let a reader see x after a transfer but y before it, because "x" and "y" are different objects and the promise is made object by object. To get guarantees about groups of operations you need transactions.

Transactions: serializability and strict serializability

So far every operation touched one object. A transaction groups several reads and writes, possibly on many objects, into one unit (data chapter 10). There is a parallel family of models for transactions, and the two families are routinely confused because they use similar words and the same word, "consistency".

Serializability says: the outcome of a set of concurrent transactions is the same as if they had run one at a time in some order. Data chapter 11 built the whole anomaly zoo (dirty reads, lost updates, write skew, phantoms) as ways to fail to be serializable, and showed that snapshot isolation (what PostgreSQL calls Repeatable Read) permits write skew and so is weaker. If you have not seen those, read Isolation Levels & Anomalies first, and chapter 12 for how serializable isolation is implemented.

Notice what serializability does not say: nothing about real time. The "some order" can be any order, including one that puts a transaction that started later before one that finished earlier. Strict serializability adds the missing condition: the serial order must respect real-time order, so if transaction T1 committed (the client was told) before T2 began, T1 is before T2 in the order.

PropertyUnitOrder must respectTime condition
Sequential consistencysingle operation, single objecteach client's own ordernone
Linearizabilitysingle operation, single objectreal time, across clientsreal-time order
Serializabilitywhole transactions, many objectsnothing in particularnone
Strict serializabilitywhole transactions, many objectsreal timereal-time order

Read the table as a grid with two independent axes: how big is the unit (one operation or a transaction) and is real time respected. Strict serializability is the corner with the strongest answer on both, "linearizability for transactions", and it is the standard a distributed SQL database promises when it says its transactions are as good as a single machine's. Spanner calls this external consistency; chapter 7 explains the clock machinery that makes it affordable.

Where the gap bites: the lagging follower

Here is a concrete case where "serializable" is not enough. A database serialises transactions correctly on its leader, but allows reads on followers that lag a little. T1 inserts an order and commits; the app tells the customer "done". The customer opens the order page, T2, served by a follower that has not yet applied T1, and sees no order. The database's history is serializable: the serial order T2, then T1 explains every result. It is not strict serializable, because T1 finished before T2 began. And it is the same stale read as in the widget, now at the transaction level.

"Serializable" in a product name usually means the weaker one

In the SQL standard, SERIALIZABLE says nothing about real time. Whether a given database also promises the real-time part, and under what conditions (single node? only on the leader? only for single-key operations?) is something to read in its documentation, not assume. Some systems document that they are linearizable for single keys and serializable for transactions but not strict serializable overall; the gap between those is a few rare anomalies with unrelated transactions. Chapter 14 comes back to this with Spanner, Percolator and Calvin.

The consistency map

Now we can lay the models out. The diagram below is read as "stronger at the top". An arrow from A to B means every history allowed by A is also allowed by B (A implies B). This is the picture Jepsen's documentation popularised as the "consistency map"; some details of where exactly the weaker boxes hang differ between authors, and the lower part is a simplification.

Three things are worth reading off this map.

Two axes, one corner. The top fork is the single-object/transaction split from the table above: linearizable and serializable are incomparable (neither implies the other), and their conjunction is strict serializable. A single-key store can be linearizable and nothing like serializable; a snapshot-isolated database can be nowhere near either.

The cost line. The models above causal need coordination between replicas in the common case, and in the partition case some clients must wait or fail. That is the content of CAP: linearizability can't be available under a partition, and the argument (a client on the far side asks for a value that was just written on the near side) extends to its neighbours. The blue and green models can answer from whatever replica a client reaches. This tracks the "highly available transactions" taxonomy of Bailis and colleagues, which sorts models into "available", "available if sticky" and "unavailable"; chapter 6 covers the middle band, where causal consistency sits.

The bottom is not nothing. The four boxes under PRAM and causal are the session guarantees. Roughly speaking, causal consistency is those four promises held together, and a system can give clients a useful subset cheaply. The full treatment is the next chapter. Eventual consistency, at the bottom, promises only convergence once updates stop (networking chapter 18), which is why it appears as the weakest box, implied by all the others.

For a feel of where real systems sit, in general terms: consensus-backed stores such as etcd and ZooKeeper give linearizable writes; ZooKeeper's reads are only sequentially consistent unless the client asks for a sync first, so a client can read slightly old data; Spanner and similar systems aim at strict serializability; Dynamo-style stores and many caches give eventual consistency by default with options for stronger reads. Check each system's own documentation for the exact conditions; the same product often offers several modes. Chapter 10 returns to what it takes to make Raft-backed reads linearizable.

Quorums are not linearizable on their own

You may remember the rule "R + W > N guarantees the read sees the latest write". It guarantees the read quorum contains a replica that has the latest completed write. It does not make the system linearizable: while a write is still in progress, a first reader can contact the replica that already has the new value and a second reader, starting afterwards, can contact only replicas that do not. That is exactly the new/old inversion history in the widget. Repairing it needs extra work, such as readers writing back what they saw before returning, or a consensus protocol.

How do you check a claim? Why it's hard, and why it's doable

A system claims linearizability. How would you find out if it lies? You cannot read its internals and be sure; you record a history from outside, as above, and ask the question the definition poses: does a legal order exist? That is a search problem, and in the worst case a hard one.

NP-complete in general

Checking whether an arbitrary recorded history of reads and writes is linearizable is NP-complete. This was shown by Phillip Gibbons and Ephraim Korach (their 1997 paper on testing shared memories), who also found restricted cases, for example when you know which write each read returned the value of, that are solvable in polynomial time. In plain words: no one knows a method whose running time stays manageable as the history grows in the worst case, and nobody expects one, because the problem encodes the sort of ordering puzzle that makes NP-complete problems hard. The intuition is the same as a scheduling puzzle: many operations overlap, each overlap leaves the order open, and the choices interact through the values reads return. A history of n fully overlapping operations has n! candidate orders.

Practical anyway

Real histories are not worst cases, and three ideas make the search fast in practice. They are all in the 30-line checker below.

  1. Search only the possible next steps. The Wing and Gong checker (1993) builds the order from the front. At each step, the operations that may legally go next are those that no remaining operation completely precedes in real time. Try each; if the register value doesn't match what a read returned, prune immediately.
  2. Remember dead ends. Gavin Lowe's 2017 refinement notes that the future depends only on which operations remain and what the object's state is. If you reach the same (remaining set, state) pair a second time by another route, and it failed before, it fails again. Caching these pairs turns many exponential searches into small ones.
  3. Split by object. By the locality theorem, check each key separately. Horn and Kroening (2015) call a generalisation of this "P-compositionality". Histories of a thousand keys become a thousand tiny ones.

Here is the whole checker, in standard-library Python. It handles both models: with realtime=True an operation may go next only if no remaining operation returned before it was called; with realtime=False only a client's own earlier operations block it.

from dataclasses import dataclass
from typing import Optional

@dataclass(frozen=True)
class Op:
    client: str
    obj: str           # which register
    kind: str          # "w" or "r"
    value: int         # value written, or value the read returned
    call: float        # when the client sent it
    ret: float         # when the client got the answer

def check(history: list[Op], realtime: bool = True, init: int = 0, stats: Optional[dict] = None) -> Optional[list[Op]]:
    """Search for a legal sequential order (Wing & Gong style, with memoisation).
    realtime=True  -> linearizability: an op that returned before another was called must come first.
    realtime=False -> sequential consistency: only each client's own order must be kept.
    Returns one legal order, or None."""
    n = len(history)
    seen_dead: set = set()                       # (remaining-set, state) pairs known to fail

    def allowed_next(remaining: frozenset[int]) -> list[int]:
        out = []
        for i in remaining:
            a = history[i]
            if realtime:
                ok = all(not (history[j].ret < a.call) for j in remaining if j != i)
            else:
                ok = all(not (history[j].client == a.client and history[j].call < a.call)
                         for j in remaining if j != i)
            if ok:
                out.append(i)
        return sorted(out)

    def go(remaining: frozenset[int], state: tuple) -> Optional[list[int]]:
        if stats is not None:
            stats["states"] = stats.get("states", 0) + 1
        if not remaining:
            return []
        key = (remaining, state)
        if key in seen_dead:
            return None
        for i in allowed_next(remaining):
            op = history[i]
            regs = dict(state)
            if op.kind == "r" and regs.get(op.obj, init) != op.value:
                continue                          # this read cannot happen here
            if op.kind == "w":
                regs[op.obj] = op.value
            rest = go(remaining - {i}, tuple(sorted(regs.items())))
            if rest is not None:
                return [i] + rest
        seen_dead.add(key)
        return None

    order = go(frozenset(range(n)), ())
    return None if order is None else [history[i] for i in order]

def show(name: str, h: list[Op]) -> None:
    for label, rt in (("linearizable", True), ("sequentially consistent", False)):
        res = check(h, realtime=rt)
        verdict = "yes: " + " ".join(f"{o.client}.{o.kind}({o.obj}{'=' if o.kind=='w' else '->'}{o.value})" for o in res) if res else "NO"
        print(f"{name:<24} {label:<24} {verdict}")

W = lambda c, v, a, b, o="x": Op(c, o, "w", v, a, b)
R = lambda c, v, a, b, o="x": Op(c, o, "r", v, a, b)

Go deeper: indeterminate operations and "linearizable" histories with timeouts optional

In a real test, some requests time out: you do not know whether the write was applied. A correct checker treats such an operation as having an invocation but no response, which in the definition means its interval extends to the end of the history, and it may be dropped from the order or kept. Mark every timeout "failed" and you will report false violations (the write actually happened and a later read saw it); mark every timeout "succeeded" and you will miss bugs. Jepsen calls these operations "info". The search just has one more choice per such operation: include it at some point after its call, or leave it out. This is also the reason a test's pass tells you less than it seems: histories full of crashed clients can hide a lot.

What a check can and cannot tell you

A failing check is a proof: you have a recorded history, and the checker has exhausted every possible order. You can print the history and show it to the authors. A passing check is only evidence. It says that this history, from this run, with these faults and timing, has a legal order. A system that fails once in a million schedules may pass a hundred thousand tests. Hence the combination of two practices, which chapter 19 develops: injecting nasty faults so the rare schedules happen, and deterministic simulation, so that a failing schedule can be replayed from a seed.

Try it yourself

Try it yourself

You need only Python 3.9 or newer. Save the listing above as lin.py (everything from from dataclasses to the R = ... line) and the demos next to it. The generator used by the experiments is below.

import random
from lin import Op

def random_history(rng: random.Random, n_ops: int, objs=("x", "y"), clients=4, lie=0.0) -> list[Op]:
    """Registers that really are atomic: every op takes effect at one instant inside its
    interval. With probability `lie`, a read reports a random value instead of the true one."""
    free_at = [0.0] * clients                      # when each client can issue its next op
    pending = []
    for k in range(n_ops):
        c = rng.randrange(clients)
        call = free_at[c] + rng.random()
        ret = call + 0.2 + rng.random() * 3
        free_at[c] = ret + 0.01
        point = call + rng.random() * (ret - call)  # the hidden instant at which it takes effect
        pending.append((point, c, call, ret, rng.choice(objs), rng.random() < 0.5, k))
    regs, history = {o: 0 for o in objs}, []
    for point, c, call, ret, obj, is_write, k in sorted(pending):
        if is_write:
            regs[obj] = k + 1
            history.append(Op(f"C{c}", obj, "w", k + 1, call, ret))
        else:
            seen = rng.randrange(n_ops + 1) if rng.random() < lie else regs[obj]
            history.append(Op(f"C{c}", obj, "r", seen, call, ret))
    return history

Distributed systems connection

Everything later in this course is aimed at one of the boxes on the map. Consensus (chapters 8 to 10) is how a replicated log gives you linearizable writes; the cost is a round trip to a majority, which is why geographic placement (chapter 18) matters. Causal and session guarantees (chapter 6) are what you can keep when you cannot afford that round trip. Chapter 7 shows how bounded clock error buys the real-time condition of strict serializability. Chapters 13 and 14 apply the transaction half of the map to commit protocols and databases. And chapter 19 is about the checker: a model is only useful if you can test for it.

Key takeaways

  • An operation is an interval from invocation to response; a history is the record of all intervals. Two operations are concurrent if the intervals overlap; otherwise real-time order puts one first.
  • A history is linearizable if there is a legal sequential order that respects real-time order. Equivalently, each operation can be given a linearization point inside its interval. Overlapping operations may be ordered either way.
  • Sequential consistency keeps only each client's own order and drops real time. Every linearizable history is sequentially consistent, not the reverse. The stale read after a completed write is the standard example.
  • Linearizability is local: a system is linearizable if every object is. Sequential consistency is not, as the two-register cycle shows. This is why per-key linearizable stores can be built shard by shard, and why a checker can split a history by key.
  • Serializability is about transactions and ignores real time; strict serializability adds the real-time order. They are different axes from the single-object models; strict serializable is both serializable and linearizable.
  • Checking linearizability is NP-complete in the worst case but practical: search from the front with pruning, cache dead ends (Wing & Gong, Lowe), split by key. A violation is proof; a pass is evidence.
  • R + W > N quorums, sequential reads and "serializable" labels each leave a gap that a precise definition makes visible.

Check your understanding

Client A's write(x, 1) returns "ok" at time 10. Client B sends read(x) at time 12 and receives 0 (the initial value). No other operations occur. Which statement is correct?

  1. Linearizable, because the read returned a value x really held at some time
  2. Not linearizable, but sequentially consistent
  3. Neither linearizable nor sequentially consistent
  4. Both, because the two clients are different
The write finished before the read started, so any model that respects real time must put the write first, and then the read must return 1. That rules out linearizability. Sequential consistency ignores real time between different clients, so B's read can be placed before A's write, and the history is allowed.

A write(x, 1) by A takes from time 1 to time 9. B reads x during [2, 4] and gets 1. C reads x during [5, 7] and gets 0. Why is this history not linearizable?

  1. Reads may never overlap a write
  2. C's read began before the write ended
  3. B's read had already returned 1 before C's started, so C must also see 1; the value would go new, then old
  4. Because A and C are different clients
Overlap with the write means each read may legitimately see either value. The problem is the pair: once a read has returned the new value, every operation starting after that response must see it too. C starts at 5 after B finished at 4. No placement of linearization points works.

Which statement about composition is true?

  1. If every object in a system is linearizable, the system as a whole is linearizable; sequential consistency lacks this property
  2. If every object is sequentially consistent, the whole system is too; linearizability lacks this property
  3. Both models compose
  4. Neither model composes, which is why transactions exist
Herlihy and Wing proved locality for linearizability. The two-register example (each client writes one register then reads the other, both reads return 0) is sequentially consistent per register but has no single legal order for the whole, so sequential consistency is not local.

A database lets read-only transactions run on a follower that is a few hundred milliseconds behind. Writes go through a leader and are strictly ordered. Which description is most accurate?

  1. Linearizable
  2. Strict serializable, because writes are ordered by the leader
  3. Not serializable, because followers lag
  4. Possibly serializable (a stale snapshot is a consistent snapshot) but not strict serializable
A read-only transaction on a consistent but older snapshot can be explained by a serial order that places it earlier, so serializability can hold. But a transaction that began after a write was acknowledged and misses it violates the real-time condition, so it is not strict serializable and not linearizable.

Why is checking linearizability feasible in practice even though it is NP-complete in general?

  1. Because real systems are never concurrent
  2. Because real histories have limited overlap, and checkers prune the search, cache (remaining operations, state) dead ends, and check each key separately
  3. Because checkers only look at a sample of operations
  4. Because NP-complete problems are always fast for small inputs on modern CPUs
Worst-case hardness comes from large amounts of overlap. Practical histories have few concurrent clients per key, and techniques like pruning on the real-time order, memoising dead ends and splitting by key (using locality) keep the search small. Checkers do examine every operation; they just do not enumerate every permutation.

A quorum store uses N = 3, W = 2, R = 2. Is it linearizable?

  1. Not necessarily: a reader can see an in-progress write's new value on one replica, and a later reader can miss it, producing a new/old inversion
  2. Yes, because R + W > N guarantees it
  3. Yes, but only if W = N
  4. No, never, quorums are always eventually consistent
R + W > N makes read and write quorums overlap, so a read after a completed write sees it. It says nothing about reads that overlap an incomplete write. Without extra mechanisms (read repair done before returning, or consensus) the new/old inversion can happen.

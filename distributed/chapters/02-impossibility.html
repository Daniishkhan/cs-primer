What Is Impossible: FLP, CAP & PACELC

Some requirements are not merely hard; they provably cannot be met. Knowing the three big impossibility results precisely, what they assume and what they do not say, saves you from chasing the unachievable, and shows you where real systems cleverly step around the walls. We tell the story of FLP (consensus can't be guaranteed to terminate), CAP (consistency and availability can't both survive a partition) and PACELC (the price you pay even when nothing is broken).

Why this matters

Impossibility results are the most practical theory in the field, because they are the only way to know that a design review requirement is a fantasy: "the cluster must always agree and always answer and survive any network failure". They also form the vocabulary of every system-design argument ("it's a CP system", "it favours availability"), and that vocabulary is misused so often that a precise grasp is a real advantage. The slogans from networking chapter 18 and chapter 20 were deliberately loose. Now that chapter 1 has given us models, we can state each result as a theorem about a model and see exactly what it forbids.

How to read an impossibility result

An impossibility theorem has the form "no algorithm can achieve properties P in model M". Its force depends entirely on M. If you change the model, even slightly, the theorem may no longer apply. So there are only three honest responses to one: weaken the properties P, strengthen the model M, or accept a probability of failure. Every real system does one of these, and the interesting part is which. We will mark each response when we meet it.

FLP: you cannot be sure consensus will finish

Recall the consensus problem from networking chapter 20: every node starts with an input value (let us say a bit, 0 or 1), and they must all decide on a single value. Three requirements:

  • Agreement (safety): no two nodes decide differently.
  • Validity (safety): the decided value was some node's input. In particular, if all inputs are 0 the decision is 0.
  • Termination (liveness): every node that does not crash eventually decides.

In 1985 Michael Fischer, Nancy Lynch and Michael Paterson proved the FLP result. Stated carefully:

The FLP impossibility (Fischer, Lynch & Paterson, 1985)

In the asynchronous model with reliable links, there is no deterministic consensus algorithm that tolerates even one crash fault. Any such algorithm has some execution in which it never terminates.

Every word in that sentence is load-bearing. Asynchronous: no timing assumptions (chapter 1), so a slow node and a crashed node can't be told apart. Deterministic: a node's next step depends only on its state and the message it receives, with no coin flips. Even one crash: one is enough, which is why adding more nodes doesn't help. And it concerns termination only: nothing in the theorem says that agreement or validity must be violated. A consensus algorithm can always stay safe; what it cannot do is promise to finish in every execution.

The intuition, without the proof

The proof is a page or two of careful case analysis, but its shape is graspable. Start with the dilemma that every consensus algorithm faces. Imagine three nodes that must agree, and one of them has gone silent.

If the two remaining nodes wait for the silent one, and it really has crashed, they wait forever: termination fails. If they decide without it, and it was merely slow, it may wake up and make a different decision based on information the others never saw: agreement fails. Since in the asynchronous model they can't tell the two cases apart, no rule can be right in both. The cleverness of FLP is to show that this dilemma can be kept alive forever, even by an adversary that is forced to be perfectly fair about delivering messages. Three ideas build the argument.

Idea 1: configurations and the adversary. A configuration is a snapshot of the whole system: every node's state plus the set of messages in flight. Because nodes are deterministic, the only thing that decides what happens next is which message is delivered next. Call whoever picks the order the scheduler (or "adversary"; it stands for the whole unpredictable network). The scheduler may be as unlucky as it likes, with the single restriction that every message is eventually delivered (so no cheating by dropping messages) and at most one node crashes.

Idea 2: valency. Look at a configuration and ask what outcomes are still possible from it. If every run from here that decides, decides 0, the configuration is 0-valent; if every one decides 1, it is 1-valent. If the scheduler could still steer the run either way, the configuration is bivalent ("two-valued"): the outcome is genuinely undecided, hanging on message order. A decision is made, in effect, at the moment the system falls from bivalent into univalent.

Analogy: a committee choosing between two dates

The committee is split on 3 June or 4 June. While the votes in flight could still tip it either way, the state is bivalent. The post office (our scheduler) cannot lose any letter, but it can decide the order of delivery. If one particular letter, if delivered next, would tip the committee to 3 June for good, the post office simply delivers other letters first, and holds that one a little longer. Meanwhile it makes sure the other letters it delivers leave the committee still split.

Where it breaks down: real post offices aren't malicious, and they don't know the contents of letters. FLP's adversary is a worst-case device: it shows that no algorithm can rule out a bad schedule, not that bad schedules are likely.

Idea 3: two lemmas. FLP proves two facts. The first: there is always a bivalent initial configuration. Line up all the possible input assignments and move from "all inputs 0" (which must decide 0, by validity) to "all inputs 1" (which must decide 1) by flipping one node's input at a time. If every configuration on this line were univalent, then somewhere along it a 0-valent configuration would sit next to a 1-valent one, differing only in node p's input. Now suppose p crashes at the very start: the other nodes can't tell the two neighbours apart, so they behave identically and decide the same value in both, which contradicts one of them being 0-valent and the other 1-valent. So that cannot happen: some initial configuration must be bivalent.

The second lemma is the heart: from any bivalent configuration, and for any message e that is in flight, the scheduler can reach another bivalent configuration in which e has just been delivered. The reasoning is again the crash argument. If delivering e could ever force the system to become univalent, there would be a critical step at which one node p alone tips the balance; but p might have crashed instead, and the others, who can't distinguish "p crashed" from "p is slow", would have to carry on and reach a decision that is wrong in one of the two worlds.

Put the lemmas together. Start in a bivalent initial configuration. Take the oldest undelivered message and, by the second lemma, deliver it in a way that stays bivalent. Repeat forever. Each message is delivered eventually, so the scheduler is perfectly fair, yet the system never leaves the bivalent region, and nobody ever decides.

The same dilemma in 30 lines

You can feel the squeeze in a tiny experiment. Three nodes hold the bits 0, 0, 1. To tolerate a crash, each node follows the rule "do not wait for everyone: decide using my own bit plus the first other bit I hear" (if the two bits differ, choose 1). We try every possible order in which the first messages could arrive.

from itertools import product

# Three processes with input bits. Rule A ("don't wait for a possibly crashed process"):
# decide on your own bit plus the FIRST other bit that arrives; if the two differ, pick 1.
inputs = {"p0": 0, "p1": 0, "p2": 1}
names = list(inputs)

def decide(own: int, other: int) -> int:
    return 1 if own + other >= 1 else 0           # with two bits: majority, tie -> 1

others = {p: [q for q in names if q != p] for p in names}
bad = 0
print("first message each process hears      decisions        agree?")
for pick in product(*(others[p] for p in names)):
    heard = dict(zip(names, pick))
    dec = {p: decide(inputs[p], inputs[heard[p]]) for p in names}
    ok = len(set(dec.values())) == 1
    bad += not ok
    first = " ".join(f"{p}<-{heard[p]}" for p in names)
    print(f"{first:<38}{str(list(dec.values())):<17}{'yes' if ok else 'NO'}")
print(f"\n{bad} of 8 delivery orders end in disagreement")

6 of 8 delivery orders end in disagreement

Six of the eight schedules end with nodes disagreeing. The reason is the one above: each node decided from a different subset of the inputs. The opposite rule ("wait until I've heard from all the others") never disagrees but hangs for ever if any node crashes. FLP says there is no cleverer rule that dodges both horns in the asynchronous model.

What FLP does not say

  • It does not say consensus is impossible in practice. It says that no deterministic algorithm can guarantee termination in the worst case. The bad schedules are a vanishingly thin sliver of reality. Raft and Paxos run daily in production.
  • It does not say safety is impossible. Paxos and Raft never violate agreement, whatever the schedule. They give up only the guarantee of finishing.
  • It does not apply if the model is stronger (known bounds, randomness, failure detectors), which brings us to the escapes.

Raft is a nice case study because it uses two of the escapes at once. It stays safe under any timing, and it relies on timeouts (partial synchrony) to detect a dead leader and on randomization in those timeouts so that two candidates rarely collide. Both are exactly the forms of help FLP permits.

"It's impossible" is not "it never happens"

A frequent misreading is "FLP means Paxos can fail". Paxos can fail to finish when proposers keep interrupting each other (a livelock called duelling proposers, chapter 9). It can never decide two different values. Production systems add randomized back-off so the livelock is vanishingly unlikely, which turns a theoretical impossibility into a rare, self-healing delay.

CAP: consistency, availability, partitions

The CAP theorem is the most quoted and most misquoted result in the field, so we state it with the definitions that make it true. Eric Brewer conjectured it in a keynote at PODC in 2000; Seth Gilbert and Nancy Lynch proved a precise version in 2002.

CAP (Gilbert & Lynch, 2002), in plain words

In an asynchronous network that may lose messages, it is impossible to implement a read/write register (a store) that is both consistent and available.

  • C: consistency means linearizability (atomic consistency, introduced by Herlihy and Wing in 1990): every operation appears to take effect instantly at a single point between its start and end, so a read that begins after a write finished sees that write (or something later). Chapter 5 defines it fully. It is not the "C" of ACID.
  • A: availability means every request received by a node that has not crashed eventually gets a (non-error) response. Note how strong it is: not "most requests", and not "some node", but every request at every live node, including nodes on the small side of a partition.
  • P: partition tolerance means the system keeps these promises even though the network may lose arbitrary messages between nodes. It's not a feature you pick; it describes the environment.

The proof, as a space-time diagram

The proof is short enough to draw. Take two nodes, G1 and G2, each holding a copy of a register whose value is 0. Suppose, for contradiction, that some algorithm is consistent and available despite lost messages. Consider a run in which the network between G1 and G2 loses all messages (a partition).

Step through

The Gilbert-Lynch argument

  1. Set-up. Both replicas hold the value 0 (yellow). The red dashed line is a network partition: every message between G1 and G2 is lost. Client 1 can reach only G1, and Client 2 only G2.
  2. A write arrives at G1. Client 1 asks G1 to write 1. G1 applies it locally.
  3. Availability forces an answer. Availability says G1 must eventually respond. G1 cannot tell whether G2 is slow, down or cut off (the asynchronous model), and in this run G2 never hears from it: its replication message is lost (red x). G1 answers "ok". Now the write has completed.
  4. A read arrives at G2. Client 2, which started after the write finished, asks G2 for the value.
  5. Availability forces a stale answer. G2 must answer, and nothing it has seen distinguishes this run from one where no write ever happened. So it must return 0. A read that began after a completed write returned the old value: that violates linearizability. Contradiction. Any available algorithm is inconsistent in this run; to stay consistent, G2 must refuse to answer, and then it is not available.

It's worth pausing on how little the proof uses. It needs only one lost-message run. It doesn't care how G1 and G2 are implemented, how many nodes there are, or what protocol they run. That is why the result is so robust, and also why it is narrow: it speaks about what you can promise while the partition lasts, nothing else.

The theorem in a simulation

Here is a replicated register on three nodes with a partition that isolates node A from B and C. Mode CP requires a majority to be reachable for every read or write; mode AP answers from whatever the node can see.

class Unavailable(Exception):
    pass

class Register:
    """A replicated register on 3 nodes. mode 'CP': quorum reads/writes (majority must be reachable).
    mode 'AP': answer from whatever this node can see; reconcile after the partition heals."""
    def __init__(self, mode):
        self.mode = mode
        self.store = {n: (0, 0) for n in "ABC"}        # node -> (version, value)
        self.groups = [set("ABC")]                    # who can talk to whom
    def reach(self, node):
        return next(g for g in self.groups if node in g)
    def partition(self, *groups):
        self.groups = [set(g) for g in groups]
    def heal(self):
        self.groups = [set("ABC")]
        best = max(self.store.values())                # last-writer-wins by version
        self.store = {n: best for n in "ABC"}
    def write(self, node, value):
        seen = self.reach(node)
        if self.mode == "CP" and len(seen) < 2:
            raise Unavailable(f"{node} cannot reach a majority")
        version = max(self.store[n][0] for n in seen) + 1
        for n in seen:
            self.store[n] = (version, value)
    def read(self, node):
        seen = self.reach(node)
        if self.mode == "CP":
            if len(seen) < 2:
                raise Unavailable(f"{node} cannot reach a majority")
            return max(self.store[n] for n in seen)[1]
        return self.store[node][1]                    # AP: trust the local copy

def attempt(label, fn):
    try:
        out = fn()
        print(f"  {label:<34} -> {'ok' if out is None else out}")
    except Unavailable as e:
        print(f"  {label:<34} -> UNAVAILABLE ({e})")

for mode in ("CP", "AP"):
    print(f"mode {mode}")
    r = Register(mode)
    r.partition("A", "BC")                           # A is cut off from B and C
    attempt("write x=1 at A", lambda: r.write("A", 1))
    attempt("read x at B (after that write)", lambda: r.read("B"))
    attempt("write x=2 at B", lambda: r.write("B", 2))
    attempt("read x at A", lambda: r.read("A"))
    r.heal()
    attempt("healed: read x at A", lambda: r.read("A"))

  read x at B (after that write)     -> 0
  write x=2 at B                     -> ok
  read x at A                        -> 1

In CP mode the isolated node A refuses both the write and the read (unavailable) while the majority side B/C carries on and returns a consistent answer. In AP mode every request is answered, but after the write of 1 at A, the read at B still returns 0 (stale: a linearizability violation) and, when the partition heals, the two sides had each accepted a different write. The register here resolved the conflict by picking the highest version, so the write of x=1 simply vanished. Availability does not come free: someone must decide what happens to concurrent writes (networking chapter 18, and chapters 6 and 15).

What CAP does not say

  • It's not "pick any two of three". Partitions are not optional (next section), so the real choice, only when a partition occurs, is C or A.
  • "Unavailable" is narrower than "down". In the CP run above the majority side keeps serving. CAP's A insists that every node answer, including cut-off ones, which no real service promises. A system that is "CP" in the theorem's sense can still be up 99.99% of the time as users see it.
  • It says nothing when there is no partition. In normal operation a system can be consistent and available. The cost then is latency, which is PACELC's job.
  • C is linearizability, not every consistency model. Weaker models, such as causal consistency and the session guarantees of chapter 6, can remain available during a partition. There is a whole range of useful guarantees between "linearizable" and "anything goes".
  • It says nothing about durability, performance or correctness of transactions. It concerns one narrow thing: reads and writes of a single register during message loss.

Why "CA" is not a choice

You will see three-way diagrams with "CA systems" in the overlap of consistency and availability, usually listing a relational database. That's a category error. Partition tolerance isn't a property you may opt out of; it is a statement about the world: networks lose messages, and machines pause so long that they are indistinguishable from unreachable ones (chapter 1). If your system spans more than one machine, a partition will eventually happen, and when it does you will either refuse some requests (you are CP) or answer them possibly stale (you are AP). There is no third behaviour. A "CA" system is one of two things: a single node (not distributed, so there is no network to partition), or a distributed system that hasn't decided what to do in a partition, which in practice means it does something arbitrary and is usually discovered to be neither consistent nor available. Brewer himself, looking back on the theorem a dozen years later, stressed that the "2 of 3" framing is misleading and that the real design space is about how a system behaves during and after partitions.

Many practitioners also argue that labelling whole databases "CP" or "AP" is too coarse: a single system may be linearizable for some operations and available-but-stale for others, depending on configuration (for example per-query consistency levels). Use CAP to reason about one operation during one partition, not to sort products into boxes.

PACELC: the trade-off when nothing is broken

Partitions are rare. If CAP were the whole story it would describe only a sliver of a system's life. In 2012 Daniel Abadi pointed out that there's a trade-off in normal operation too, and gave it a name: PACELC, read "if Partition, choose Availability or Consistency; Else, choose Latency or Consistency".

Why is there a trade-off with no failure at all? Because replicas are in different places, and light is slow. To give a linearizable answer, a replica has to be sure it isn't missing a newer write, which means hearing from other replicas (or from a leader) before answering. That costs a network round trip.

Make it concrete. Light in optical fibre travels at about 200,000 km/s. Replicas on opposite sides of an ocean, say 8,000 km apart, are at least 8,000 / 200,000 = 40 ms apart one way, so a round trip can't be faster than about 80 ms, however good the software. A strongly consistent write that must be acknowledged by the far replica therefore costs at least 80 ms; a system that acknowledges after writing locally and ships the update in the background answers in a millisecond or two, but a read from the far replica can then be stale. That's the "else" half: EC pays the round trip; EL doesn't, and tolerates stale reads.

Treat the classes as vocabulary for a trade-off, not as a fixed label per product: classifications depend on configuration and on the version, and the paper's own list is a snapshot from its time. The useful habit is to ask of any design, two questions: "what does it do when the network splits?" and "what does an ordinary read cost, and what does it risk?". Chapter 18 turns the second question into a budget in milliseconds.

Analogy: two bank branches and one ledger

A bank has branches in two cities and one customer balance. To be perfectly sure the balance is current, the teller in city A must phone city B before every answer, which is slow even on a good day (that is the latency cost of consistency). If the phone line breaks, the teller either refuses to answer until it is fixed (CP) or answers from the local copy and risks the customer overdrawing at the other branch (AP).

Where it breaks down: banks reconcile later with human rules (overdraft fees, apologies). Software must encode its reconciliation rule exactly, and some invariants (a unique username, an account never negative) cannot be repaired afterwards without coordination (chapter 16).

Try it yourself

You need only Python 3. Save the two scripts above as flp.py and cap.py.

  1. In flp.py, change the rule so that a node waits for both other bits. How many schedules disagree now? What happens if you add "process 2 crashes before sending" (remove its message from everyone's choices)?
  2. In cap.py, add a third scenario where the partition isolates no one alone: split ["A","B","C"] into "A", "B", "C" (three singleton groups). What does CP mode do? What does it say about "the majority side stays available"?
  3. Compute the minimum round-trip time, from the speed of light in fibre, between two cities you care about, using their great-circle distance. How does it compare with the latency of a cross-region read in a service you use (your browser's network tab shows it)?
  4. Pick a database you have used. Find, in its documentation, what a read does when a replica loses contact with the rest. Is that PC or PA? Does a configuration option change it?

Distributed systems connection

FLP is why consensus protocols have leader election with timeouts (chapters 9 and 10) and why chapter 3 is about failure detectors. CAP is why chapter 5 defines linearizability precisely and chapter 6 explores the models that stay available. PACELC is why chapter 7 on clocks and chapter 18 on multi-region design are about latency budgets. And the idea that you can weaken the property when you can't strengthen the model returns in chapters 15 and 16.

Key takeaways

  • An impossibility result is a theorem about a model. To get around it, weaken the property, strengthen the model, or accept a probability.
  • FLP (1985): in the asynchronous model, no deterministic consensus algorithm can guarantee termination if even one node may crash. The adversary keeps the system bivalent by choosing the order of message delivery. Safety is not affected.
  • Real systems escape FLP with partial synchrony (timeouts for progress, never for safety), randomization, or failure detectors.
  • CAP (Brewer 2000, Gilbert & Lynch 2002): in an asynchronous network that may lose messages, no implementation of a register is both linearizable and available at every live node. It only constrains behaviour during a partition.
  • "CA" is not a choice. Partitions happen. The only decision is whether a split system refuses (consistent) or answers possibly stale (available).
  • PACELC (Abadi, 2012): in the absence of a partition there is still a trade-off between latency and consistency, because strong consistency needs a round trip to other replicas, and light has a speed limit.
  • Use these results to test requirements ("always consistent, always available, over a WAN" is unachievable), not to label products.

Check your understanding

Which statement best captures the FLP result?

  1. Consensus is impossible whenever any message is lost
  2. In an asynchronous system, no deterministic algorithm can guarantee that consensus terminates if even one node may crash
  3. Consensus requires at least three nodes
  4. Paxos and Raft are incorrect
The theorem is precise: asynchronous model, reliable links, deterministic algorithm, one crash fault, and only termination is lost. Safety can always be kept, which is exactly what Paxos and Raft do; they escape the impossibility by assuming partial synchrony and using randomized timeouts.

What does it mean for a configuration to be bivalent?

  1. Two nodes have crashed
  2. The system has decided on two values
  3. The system has two leaders
  4. Both decision outcomes are still reachable from it, depending on the order in which messages are delivered
Valency describes which decisions are still possible. A 0-valent configuration can only decide 0, a 1-valent only 1, and a bivalent one can still go either way. FLP shows an adversarial scheduler can keep the system bivalent forever.

In the Gilbert-Lynch proof sketch, why must the node G2 return the old value?

  1. Availability forces it to answer, and during the partition nothing it has received can reveal the write that completed at G1
  2. Because G2 is slower than G1
  3. Because linearizability allows stale reads
  4. Because the client cached the old value
The two runs, "a write happened at G1" and "no write happened", look identical from G2's side because no message crosses the partition. Being available means G2 must respond anyway, so it answers as if no write happened, which breaks linearizability for the run in which one did.

A colleague describes a design as "CA: consistent and available, and we don't need partition tolerance because our network is reliable". What is the best response?

  1. That is fine for any system inside one data centre
  2. That is the best of the three options
  3. Partitions (and pauses that look like them) happen on any real network, so the question is what the system does when one occurs: refuse some requests or serve possibly stale data
  4. CAP only applies to databases
P is a property of the environment, not a feature you can decline. Even inside one data centre, a switch failure, an overloaded node or a long garbage-collection pause cuts off nodes for a while. "CA" systems are single-node systems, or systems whose partition behaviour is simply undefined.

A system has no partition and all nodes are healthy, yet it must trade something for strong consistency. According to PACELC, what is the trade?

  1. Durability
  2. Latency: strongly consistent reads and writes need coordination with other replicas, which costs at least a network round trip
  3. Partition tolerance
  4. Disk space
The "Else" half of PACELC: when the network is fine, the choice is between latency and consistency. Across an 8,000 km link a round trip can't be faster than roughly 80 ms because of the speed of light in fibre, no matter how good the software is.

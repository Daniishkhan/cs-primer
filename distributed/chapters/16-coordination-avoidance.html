Coordination Avoidance

The last three chapters made coordination work: consensus, atomic commit, global ordering. This one asks the opposite question: when can you skip it? Some application rules (a balance that must never go negative, a username that must be unique) really do require machines to talk before acting. Many others, surprisingly, do not. This chapter gives you the tests that tell the difference: invariant confluence, the CALM theorem, and the working techniques that fall out of them: escrow, bounded counters and honest apologies.

Why this matters

Coordination is the expensive part of a distributed system. It costs a round trip across a data centre or an ocean (chapter 14), it makes availability depend on the slowest or least reachable participant, and it caps throughput on hot data. The best distributed designs are not the ones with the cleverest protocols; they are the ones that need protocols least. Being able to say, for a given business rule, "this one needs a coordinated write and these five do not" is one of the most valuable judgement calls in system design, and the difference between a multi-region system that is fast and available and one that is neither.

The question: which rules need a referee?

Suppose several replicas accept writes independently and exchange them later, as in the CRDT chapter. Each replica can check a rule against its own state before accepting a write. The danger is a rule that holds on each replica yet fails once their updates are combined. If that can never happen for a rule, the replicas never need to talk before acting, and the rule is safe to enforce without coordination. If it can happen, something must stop it: a lock, a consensus round, a reservation.

Two bodies of work formalise this, one about data and invariants and one about programs. They agree where they overlap, and together they give you a practical vocabulary.

Invariant confluence

An invariant is a condition that must hold in every state the database can be in (for instance, a balance is at least zero, or every order refers to an existing customer). Bailis, Fekete, Franklin, Ghodsi, Hellerstein and Stoica ("Coordination Avoidance in Database Systems", VLDB 2015) define when an invariant is safe without coordination:

A set of transactions is invariant confluent (I-confluent) with respect to an invariant if, starting from a valid state, any two states reached by independently applying those transactions (each valid on its own) can be merged into a state that is also valid.

Their main result: a set of transactions can be executed on replicas without coordination, converge, and always preserve the invariant, if and only if the transactions are I-confluent for that invariant. This turns an architectural question into a testable one: can two good states combine into a bad one? If the answer is no, coordination is wasted. If yes, you have a precise list of the operations that need it.

A pattern shows up: invariants that merely require something to exist, or to stay as it is, are usually safe (foreign keys on inserts, non-negative single values, unique-by-construction ids). Invariants that compete for a finite shared resource or demand a single winner are not (balances, stock, uniqueness, sequences, mutual exclusion). Deletions are the sneaky case that breaks otherwise safe rules, because deleting can invalidate things another replica is creating. The Bailis et al. analysis of a standard order-processing benchmark found that most of its invariants were I-confluent and that coordination was needed for a small number of rules, notably sequential id assignment.

A checker you can run

The program below is a deliberately small, bounded version of the definition: two replicas start in the same valid state, each applies one operation that is allowed locally, they merge, and we test the invariant. If any pair of locally valid operations breaks the invariant after merging, it prints that pair. Finding a counterexample proves the rule is not I-confluent for those operations; finding none is only evidence (the real definition quantifies over all divergent histories).

"""A bounded invariant-confluence checker.

Two replicas start in the same valid state, each applies one operation that is valid
*locally* (the invariant holds after it), then they merge. If some pair of locally valid
operations merges into an invalid state, the operations are NOT invariant-confluent for
that invariant and need coordination. (No counterexample among single operations is
evidence, not proof: the real definition covers all divergent histories.)
"""
from __future__ import annotations
from itertools import product
from typing import Callable

State = dict
Op = tuple[str, Callable[[State, str], State]]     # (name, apply-on-replica-r)


def check(name, start, ops, merge, invariant):
    assert invariant(start)
    for (n1, f1), (n2, f2) in product(ops, ops):
        a, b = f1(start, "r1"), f2(start, "r2")
        if not (invariant(a) and invariant(b)):
            continue                              # the op would be refused locally
        m = merge(a, b)
        if not invariant(m):
            print(f"{name:34} NOT confluent  r1:{n1:12} r2:{n2:12} -> merged state breaks it")
            return
    print(f"{name:34} confluent for every pair tried")


# ---- balance >= 0, modelled as per-replica deposit/withdraw totals (a PN-Counter)
def pn_merge(a, b):
    return {k: {r: max(a[k].get(r, 0), b[k].get(r, 0)) for r in ("r1", "r2")} for k in ("dep", "wd")}

def bal(s):
    return 100 + sum(s["dep"].values()) - sum(s["wd"].values())

def dep(n): return (f"deposit {n}", lambda s, r: {"dep": {**s["dep"], r: s["dep"].get(r, 0) + n}, "wd": s["wd"]})
def wd(n):  return (f"withdraw {n}", lambda s, r: {"dep": s["dep"], "wd": {**s["wd"], r: s["wd"].get(r, 0) + n}})

acct = {"dep": {}, "wd": {}}
check("balance >= 0, deposits+withdrawals", acct, [dep(50), wd(80)], pn_merge, lambda s: bal(s) >= 0)
check("balance >= 0, deposits only", acct, [dep(50), dep(80)], pn_merge, lambda s: bal(s) >= 0)

# ---- uniqueness of a chosen username
def reg(name, owner_prefix=False):
    def f(s, r):
        key = f"{r}-{name}" if owner_prefix else name
        return {"names": s["names"] | {(key, r)}}
    return (f"register {name}", f)

def unique(s):
    keys = [k for k, _ in s["names"]]
    return len(keys) == len(set(keys))

merge_union = lambda a, b: {"names": a["names"] | b["names"]}
check("username unique, user-chosen name", {"names": frozenset()}, [reg("alice")], merge_union, unique)
check("id unique, replica-prefixed ids", {"names": frozenset()}, [reg("n1", True)], merge_union, unique)

# ---- foreign key: every order refers to an existing user
def add_order(u):
    return (f"order for {u}", lambda s, r: {**s, "orders": s["orders"] | {(r, u)}})

def del_user(u):
    return (f"delete {u}", lambda s, r: {**s, "deleted": s["deleted"] | {u}})

def live(s): return s["users"] - s["deleted"]
def fk_ok(s): return all(u in live(s) for _, u in s["orders"])
fk_merge = lambda a, b: {"users": a["users"] | b["users"], "deleted": a["deleted"] | b["deleted"], "orders": a["orders"] | b["orders"]}
users = {"users": frozenset({"u1"}), "deleted": frozenset(), "orders": frozenset()}
check("foreign key, inserts only", users, [add_order("u1")], fk_merge, fk_ok)
check("foreign key, inserts and deletes", users, [add_order("u1"), del_user("u1")], fk_merge, fk_ok)

balance >= 0, deposits only        confluent for every pair tried
username unique, user-chosen name  NOT confluent  r1:register alice r2:register alice -> merged state breaks it

The CALM theorem

Invariant confluence asks about a rule. CALM asks about the program: Consistency As Logical Monotonicity. Joseph Hellerstein conjectured it in 2010, it was proved in a formal model of distributed programs (by Ameloot, Neven and Van den Bussche), and Hellerstein and Alvaro give an accessible account in "Keeping CALM: When Distributed Consistency Is Easy" (Communications of the ACM, 2020). The statement:

A program has a consistent, coordination-free distributed implementation if and only if it is monotonic.

A program is monotonic if, as more input arrives, its output only grows: new facts can add conclusions but never retract earlier ones. "Consistent" here means that the output is the same regardless of how messages are ordered or delayed (the program is confluent); it is a statement about determinism, not about linearizability.

Why does monotonicity let you skip coordination? Because a monotone program can emit an answer as soon as it has one, knowing it will never have to take it back. Coordination exists to answer "have I seen everything yet?", and monotone programs never need to ask it.

Monotonic (no coordination needed)Non-monotonic (needs to know it has seen everything)
Select, project, join, unionSet difference, "not exists", "none of"
"Is node X reachable from Y?" (adding links can only add reachable nodes)"Is node X unreachable from Y?" (a later link can refute it)
"At least 3 votes for the motion""Exactly 3 votes", "the final vote count"
A grow-only set, a G-Counter, a running max (monotone in the lattice order)"The final maximum" (a later item can overturn it), "the latest value", an exact total

The practical use is a reading habit: scan a specification for the words not, none, all, only, exactly, final and latest. Those are the places where a decision depends on absence, and absence is only knowable by coordination (or by a timeout that will sometimes be wrong). The rest of the program can usually run unsynchronised. This is the logic behind CRDTs: their updates are monotone steps up a lattice (last chapter), which is exactly why they need none. The Bloom language and its lattice extension (Alvaro, Conway, Hellerstein and colleagues) were built so that the compiler can point at the non-monotonic spots for you.

Analogy: collecting survey replies

You are tallying replies to a survey that arrive by post, in any order. "At least ten people said yes" is a statement you can announce the moment the tenth yes arrives; no further letter can make it false. "Nobody said no" is different: you cannot announce it until you are sure that no more mail is coming, because one late letter would contradict you. The second statement needs a deadline, or a coordinator who says "the mail is closed".

Where it breaks down: real systems cannot know "the mail is closed" without extra mechanism; they have timeouts (which can be wrong) or consensus (which costs round trips). That is exactly the cost the non-monotonic questions force on you.

Escrow and bounded counters

The hardest examples above, balances and stock, share one shape: a finite resource that several replicas spend. The invariant is non-I-confluent, but the problem is narrower than it looks, because most of the time there is plenty of the resource. The classic technique is escrow (O'Neil's escrow transactional method, 1986): split the resource into shares and give each replica a share it owns exclusively. A replica may spend from its own share at will, with no communication, because it cannot overspend what it holds, and the invariant (the sum of all shares never goes negative) holds by construction. Replicas communicate only to move shares: when a region is running low it asks another for some. The CRDT-world version is the bounded counter (Balegas et al., 2015): a counter CRDT that carries the transferable "rights" alongside the value, so enforcing "stock ≥ 0" is as available as a PN-Counter, apart from the rare transfer.

"""Escrow / bounded counter: split stock into per-region allowances."""
from __future__ import annotations


class BoundedCounter:
    """Invariant: total sold never exceeds total stock. Each region owns a share."""
    def __init__(self, shares: dict[str, int]):
        self.share = dict(shares)          # units each region may still sell on its own
        self.sold = {r: 0 for r in shares}

    def sell(self, region: str, n: int = 1) -> bool:
        if self.share[region] >= n:        # purely local decision: no message sent
            self.share[region] -= n
            self.sold[region] += n
            return True
        return False                       # would need coordination (or an apology)

    def transfer(self, src: str, dst: str, n: int) -> bool:
        """The only operation that needs a round trip between two regions."""
        if self.share[src] >= n:
            self.share[src] -= n
            self.share[dst] += n
            return True
        return False


stock = BoundedCounter({"eu": 40, "us": 40, "ap": 20})
ok = sum(stock.sell("eu") for _ in range(45))
print("eu tried to sell 45:", ok, "sold,", 45 - ok, "refused locally")
print("us sells 10:", sum(stock.sell("us") for _ in range(10)), "sold")
print("eu asks us for 10 units:", stock.transfer("us", "eu", 10))
print("eu sells 5 more:", sum(stock.sell("eu") for _ in range(5)), "sold")
total_sold = sum(stock.sold.values())
print("total sold", total_sold, "of 100; never exceeded:", total_sold <= 100)
print("shares left:", stock.share)
eu tried to sell 45: 40 sold, 5 refused locally
us sells 10: 10 sold
eu asks us for 10 units: True
eu sells 5 more: 5 sold
total sold 55 of 100; never exceeded: True
shares left: {'eu': 5, 'us': 20, 'ap': 20}

EU tries to sell 45 and sells exactly its 40; the last five are refused without anybody being asked. US sells 10 and then gives EU 10 units; EU sells 5 more. The invariant (never more than 100 sold in total) held throughout because no region ever spent what it did not own. The costs are real and should be stated plainly:

  • Stranded stock. A region can run out while others hold plenty, so it must either refuse the sale or pay for a transfer (a coordinated step between two nodes). Good systems rebalance proactively, based on demand.
  • Failure. Units held by an unreachable replica are unavailable until it returns or its share is reassigned by a (coordinated) decision.
  • Exact answers need coordination. "How many are left, exactly, right now?" is a non-monotonic question; the escrow design answers "there are at least this many" cheaply and the exact number slowly.
  • Scope. It handles numeric bounds (stock, balances, quotas, seats, per-node slices of a global rate limit). It does not handle arbitrary invariants.

Guesses and apologies

Sometimes the invariant cannot be protected cheaply, and the right engineering decision is to allow the violation and repair it later. Pat Helland's paper "Building on Quicksand" (CIDR 2009, with David Campbell) describes systems that act on a local, possibly stale view of the world, a guess, and then reconcile with the truth, issuing an apology when the guess was wrong. Ordinary businesses already work this way: an airline overbooks a flight, knowing that a few passengers will not show up, and compensates the unlucky few when too many do. A bank lets a payment through and charges an overdraft fee afterwards. A shop sells the last item twice and sends an email with a refund and a voucher.

This is the saga idea from the architecture course applied to invariants: instead of preventing the violation with a distributed lock, detect it when the replicas merge and run a compensating action. For this to be a sound design rather than an excuse, several conditions must hold:

  • The violation must be detectable: the merge or a background job can see that stock went negative or two people hold the same seat.
  • A compensation exists and is acceptable to the business (refund, apology, upgrade, cancellation). It must be idempotent, because it may be triggered twice.
  • The cost of the apology, including the customer's trust, is lower than the cost of coordination: lost sales during a partition, higher latency for every operation. This is a business decision with a number attached, not an engineering reflex.
  • The harm is reversible. You can refund a payment; you cannot un-send a shipment that left the warehouse or an email that went to the wrong person. Irreversible effects belong behind coordination.

The Dynamo cart is the canonical engineering instance: it chose to always accept an "add to cart" (an add-wins merge) and tolerate an occasional deleted item reappearing, rather than ever refuse a customer.

Common misconception: "coordination-free means no guarantees"

Coordination-free designs still provide strong, precise guarantees: convergence, preserved invariants for the I-confluent ones, and bounded violations for escrowed ones. What they give up is immediate agreement about the current state of the world. The skill is knowing exactly which guarantee each part of the application needs, and spending coordination only on those.

Designing coordination-light systems in practice

Putting the pieces together, here is the working method that experienced designers follow, roughly in order:

  1. Write the invariants down. Most teams never list them. For each business rule, ask the I-confluence question: can two replicas, each correct alone, combine into something wrong? Classify every rule as safe, needs coordination, or needs compensation.
  2. Convert checked invariants into guaranteed ones. Generate identifiers (UUIDs, time-ordered ids, replica-prefixed counters) rather than checking uniqueness; make a "child" row refer to its parent by an id that cannot disappear (soft-delete rather than hard-delete); store events and derive state instead of updating in place (streams and event logs).
  3. Replace shared counters with escrowed or sharded ones wherever the bound is numeric.
  4. Isolate what really needs coordination and send only that through a consensus-backed path: for instance, "claim a username" goes through one strongly consistent table, while profile edits are merged freely. Keep the coordinated surface area small and off the hot path.
  5. Choose the scope of coordination. Coordinating inside one region costs milliseconds; across continents, hundreds. Partition the data so that rules which need coordination are scoped to something that lives in one place (a customer's data in their home region, chapter 18).
  6. Make everything else idempotent and commutative where you can: retries and reordering are then harmless (idempotency).
  7. Plan the apology path for what remains: detection, compensation, customer communication, monitoring, and a human in the loop for the cases the automation cannot fix.
  8. Test merges, not just writes: randomised delivery orders, duplicated and dropped messages, and partitions, with the invariants as the oracle (chapter 19 and Lab 6).

Distributed systems connection

This chapter closes the loop opened by CAP in chapter 2. CAP says you cannot have both availability and linearizability under partition; coordination avoidance says you often do not need linearizability, and gives you the tests to know where. It also explains the shape of real systems: strongly consistent cores for the few rules that need them (coordination services, consensus-backed tables), wrapped in a large coordination-free periphery (caches, CRDT-like replicated state, event logs). Chapter 17 and chapter 18 apply this to logs and to multi-region deployments, where the cost of coordination is measured in oceans.

Key takeaways

  • Coordination is a cost, not a requirement. An invariant is safe to enforce without coordination exactly when it is invariant confluent: two replicas, each valid alone, can always merge into a valid state (Bailis et al., 2015).
  • Balances, stock, quotas, user-chosen uniqueness and gap-free sequences are not I-confluent. Foreign keys on inserts, non-negative single values, system-generated unique ids and counters without bounds are. Deletes are the usual spoiler.
  • CALM: a program is coordination-free and consistent if and only if it is monotonic. Coordination is only needed for questions about absence or completeness: not, none, exactly, final.
  • Escrow and bounded counters split a finite resource into per-replica shares so spending is local and the bound holds by construction; only moving shares needs messages. The costs are stranded stock and slow exact totals.
  • "Guesses and apologies" (Helland): when a violation is detectable, reversible and cheaper than coordination, allow it and compensate. Never for irreversible harm.
  • In practice: list the invariants, turn checks into guarantees (generated ids, soft deletes, events), shard counters, coordinate only the small remainder and only within the smallest scope, and test with random merge orders.

Check your understanding

Which of these is the best statement of invariant confluence?

  1. The invariant is checked by a consensus protocol before every write
  2. Starting from a valid state, any two states produced independently by valid transactions can be merged into a valid state
  3. All replicas always hold identical state
  4. Every transaction is serializable
I-confluence is about divergent histories: if two independent valid steps always merge into a valid state, replicas never need to coordinate to protect the invariant. Convergence of state is a separate property (and the other options describe coordination or serializability, which are what I-confluence lets you avoid).

Which rule typically needs coordination, and why?

  1. Every order must refer to an existing customer, with inserts only
  2. Row ids must be unique, and are generated as UUIDs
  3. A "likes" counter that only increases
  4. Usernames chosen by users must be unique, because two replicas can each accept the same name and the merge contains a duplicate
Uniqueness of user-chosen values has the "single winner" shape: two valid local decisions combine into a violation. Generated UUIDs make uniqueness hold by construction, insert-only foreign keys merge safely, and a grow-only counter commutes.

What does the CALM theorem say?

  1. A program has a consistent, coordination-free distributed implementation if and only if it is monotonic
  2. Every distributed program needs consensus to be consistent
  3. Monotonic programs are always linearizable
  4. Coordination can be avoided for any program by using CRDTs
CALM links logical monotonicity (output never retracted as input grows) with the absence of any need to coordinate. "Consistent" means confluent: the output does not depend on message order. It does not claim linearizability, and CRDTs help only for the monotonic parts of a program, since non-monotonic questions (absence, "exactly", "final") still need coordination.

A flash sale has 1,000 units of stock across three regions. Using escrow, what happens when a region sells its last local unit while the others still have stock?

  1. It oversells, because escrow cannot enforce the bound
  2. All regions pause until a global lock is acquired
  3. It refuses further local sales (or asks another region for a transfer, a coordinated step between just two nodes), so the global bound still holds
  4. The stock is automatically duplicated
The invariant is preserved because no region can spend what it does not own. The cost is that a region may be starved of local stock while others have plenty; the remedy is a transfer, which is the only step that requires communication. That is the trade: availability and speed for sales within the share, a round trip only for rebalancing.

When is "allow the violation, then apologise" a sound design?

  1. Whenever coordination is inconvenient to implement
  2. When the violation is detectable, the harm reversible with an idempotent compensation, and the expected cost of apologies is lower than the cost of coordinating
  3. Only for financial systems, which can always refund
  4. Never, since it breaks the invariant
Helland's guesses-and-apologies view treats the apology path as part of the design with a price tag, as airlines do with overbooking. It fails for harms that cannot be undone (a shipped parcel, an email), when violations cannot be detected, or when the apology costs more than waiting would have.

System Models: Time, Failure & Correctness

Before you can prove that an algorithm works you have to say where it works: how long messages may take, how nodes may break, what the network may do to a packet. That description is a system model, and nearly every argument in distributed systems is secretly an argument about which model to assume. This chapter gives you the standard models, the vocabulary of safety and liveness that lets you state what "works" means, and the habit of asking, of any protocol, "in which model is this correct?"

Why this matters

Two engineers can both say "this protocol is correct" and be right, because they silently assume different worlds: one in which a timeout of 5 seconds proves a node is dead, one in which nothing about time can be trusted. Most real outages in coordination code come from a model that was true on a normal day and false on a bad one: a stalled process, a clock that jumped, a partition that cut only some links. Learning the models gives you three powers: to read a paper or design document and see its hidden assumptions; to know which guarantee must survive when an assumption breaks (safety) and which may degrade (liveness); and to see why the later chapters' results (impossibility, consensus, leases) say what they say.

Why a model at all?

A real data centre is a swamp of detail: switch buffers, kernel scheduling, garbage collectors, firmware, cosmic rays. No proof can include all of it. So we cut the world down to a few assumptions that capture what matters, and we prove the algorithm correct relative to those assumptions. "Correct" always means "correct in model M". If the real world breaks an assumption, the proof says nothing at all about what happens next. This is not a weakness of the method. It is the method: it tells you exactly which sentence in the design to stare at when something goes wrong.

A model has three parts, which are mostly independent of each other, so you can mix and match:

  1. Timing: what, if anything, is guaranteed about how long message delivery, computation and clocks take.
  2. Node failures: how a node is allowed to misbehave, and how many nodes may do so.
  3. Links: what the network may do to a message.

Think of the committee from the start-here chapter, which communicates only by post. Before it can design a voting procedure it must settle the rules of its world: how reliable is the post? Can a member fall asleep? Can a member lie? Different answers call for different procedures, and a procedure designed for a friendly world can be disastrous in a hostile one.

Timing: how long can things take?

Three quantities could in principle be bounded: the message delay (time from send to delivery), the processing time (how long a node takes to execute a step), and the clock drift (how far a node's clock can stray from real time; see networking chapter 17). The three classic timing models differ in how much of this they promise.

Synchronous: everything has a known bound

In a synchronous system there are known upper bounds on message delay, processing time and clock drift. If the bound on message delay is Δ and a node's reply takes at most a further δ to compute, then a request that has had no reply after Δ + δ + Δ proves that the other node has crashed. Timeouts become perfect failure detectors. Algorithms can run in lock-step rounds: everyone sends, everyone waits out the bound, everyone processes what arrived. Many beautiful algorithms are easy in this model.

The catch is that the bounds must hold always, not "99.99% of the time". A hardware bus in a car or aircraft, with dedicated wires and a real-time operating system, can honour such bounds. A Kubernetes cluster sharing a congested network, garbage-collected runtimes and virtual machines that can be paused cannot. For general-purpose systems, the synchronous model is a hope, not a fact.

Asynchronous: no bounds at all

In an asynchronous system nothing is promised about timing. A message can take a millisecond or a year; a node can run a step instantly or stall for an hour; there is no usable clock. The word is a technical term and must not be confused with async/await or with "asynchronous replication". It does not say that messages are slow, only that the algorithm may not assume they are fast. The one guarantee is usually that a message sent between correct nodes is eventually delivered.

Its great virtue is robustness: an algorithm that is correct in the asynchronous model is correct however the timing turns out, so it can never be broken by an assumption about speed. Its great vice is the consequence we met in networking chapter 16: a node can never tell a crashed peer from a slow one. Whatever deadline you pick, the peer's message might arrive just after it. Chapter 2 shows that this uncertainty alone makes some problems unsolvable.

Partially synchronous: usually fine, with no promises when

Real networks are neither. They behave well almost all of the time, and misbehave in storms (a congested link, a failing switch, a long pause) that end eventually. Cynthia Dwork, Nancy Lynch and Larry Stockmeyer captured this in a 1988 paper, Consensus in the Presence of Partial Synchrony, which gave two equivalent-in-spirit ways to say "mostly synchronous":

  • Unknown bound. There is a bound Δ on message delay (and a bound on relative speeds), always, but the algorithm does not know its value.
  • Global Stabilization Time (GST). The bound Δ is known, but it only holds after some unknown moment, the GST. Before GST, delays and speeds are arbitrary; after it, the system behaves synchronously forever (or at least "long enough" for the algorithm to finish).

The GST formulation is the one you will meet most. Notice what it does not say: it does not say when GST happens, and the algorithm cannot detect it. It only says that if the algorithm keeps trying, there will eventually be a window of calm long enough to make progress. Dwork, Lynch and Stockmeyer showed that consensus is solvable in this model (with limits on how many nodes may fail), despite being unsolvable in the purely asynchronous one (chapter 2). That result is the theoretical justification for how Paxos, Raft and every practical consensus system work.

Analogy: three postal services for the committee

Synchronous: the post office guarantees next-day delivery, always; if a reply has not arrived in two days, the member has certainly died. Asynchronous: no promises whatsoever; a letter may take a week or a decade, so silence never proves anything. Partially synchronous: the post is normally quick, but there are occasional strikes of unknown length. Nobody can tell whether a strike is on, but strikes do end, and after one ends mail is quick again.

Where it breaks down: a real strike is announced on the radio. A network's "strike" is invisible: from inside, a slow period and a calm one look alike until you have waited long enough, which is why protocols must stay safe even while they cannot tell which is which.

One execution can be described in all three models, but what you are entitled to conclude differs. Step through the same ping, and watch how the meaning of "no reply yet" changes.

"Asynchronous" does not mean "slow"

It means no timing assumptions are made. An algorithm proved correct in the asynchronous model is the most portable kind: it stays correct on a fast network, a slow one, and one that stalls for an hour. Do not confuse it with asynchronous programming, or with asynchronous replication (where a leader acknowledges a write before the followers have it).

Node failures: how may a node misbehave?

The second half of the model says how nodes can fail, and it matters enormously, because tolerating a benign failure is much cheaper than tolerating a hostile one. From mildest to worst:

Crash-stop
A node follows the protocol exactly until, at some moment, it halts and never takes another step. It does not lie, corrupt data or come back. This is the simplest model, and the one in which most proofs are first written. (A node that crashes and is replaced by a new node with a new identity is also modelled this way.)
Crash-recovery
A node may crash and later restart. It loses its memory (volatile state) but keeps whatever it wrote to stable storage (disk). This is the realistic model for databases and consensus servers, and it adds a new duty: a node must write its important state to disk before acting on it, because after a restart that is all it has. A Paxos acceptor that promises not to accept lower-numbered proposals, crashes before saving the promise, and restarts having forgotten it, can violate safety. This is the reason for the fsync costs of systems chapter 9.
Omission
A node keeps running but may fail to send some messages (send omission) or fail to receive some (receive omission). A full socket buffer, a dropped packet queue or an overloaded process looks like this. A network partition, seen from one node, is a burst of omissions.
Byzantine
A node may do anything: send different answers to different peers, forge data, collude with other faulty nodes. The name comes from the "Byzantine Generals" paper (Lamport, Shostak and Pease, 1982). Software bugs, bit-flips in memory and attackers all produce Byzantine-looking behaviour. Chapter 12 shows the price of tolerating it.

How many nodes may fail matters as much as how. Models state a bound f out of n nodes. For problems like consensus, crash faults can be tolerated if fewer than half the nodes fail (f < n/2, the majority rule of networking chapter 20), whereas Byzantine faults need fewer than a third (f < n/3). Chapters 8 and 12 derive those bounds.

A paused node is not a new kind of fault

A process frozen by a garbage-collection pause or by a virtual-machine migration is, formally, a node that is very slow; to its peers it is indistinguishable from an omission or a crash that is followed by a recovery. What makes it dangerous is not what it does but what it believes: when it resumes, its local state still says "I am the leader" or "I hold the lock". Chapter 4 is devoted to that trap.

Links: what may the network do to a message?

The third half of the model is the network. A real network can lose a message, delay it, deliver it twice, and deliver messages out of order. It rarely changes the contents (checksums catch that) and does not invent messages from nothing. Models turn these facts into link abstractions, and the useful insight is that stronger links can be built from weaker ones.

Fair-loss link
Messages may be lost, but not always: if a correct sender keeps sending the same message to a correct receiver, it is delivered infinitely often (so, in practice, "sooner or later"). A message may be delivered more than once, but not infinitely often unless it is sent infinitely often, and no message is created from nothing. This is roughly what raw IP or UDP gives.
Stubborn link
A fair-loss link plus a sender that retransmits every message forever. Now every message is delivered, but delivered many times.
Perfect (reliable) link
If a correct node sends a message to a correct node, it is eventually delivered, at most once, and only if it was really sent. Built by adding sequence numbers and a receiver that discards duplicates (and that acknowledges every copy so the sender can stop).
Authenticated link
A perfect link where, in addition, a message attributed to node p really was sent by p. Implemented with message authentication codes or digital signatures. It matters only when nodes may be Byzantine, or when the network is hostile (TLS).

TCP is roughly a perfect link within one connection. But connections break, and a client that reconnects and resends can deliver a request twice: the exactly-once problem of networking chapter 16 again. A perfect link is a pleasant fiction at the level of one connection, not of the whole application. Here is the ladder in running code. A seeded fair-loss link loses packets and sometimes duplicates them; a sender retransmits until acknowledged; the receiver deduplicates by sequence number.

import random
from collections import defaultdict

class FairLossLink:
    """Fair-loss link: each packet is lost with probability `loss`, otherwise
    delayed 1-5 ticks, and sometimes duplicated. Nothing is invented or altered."""
    def __init__(self, rng, loss, dup=0.1):
        self.rng, self.loss, self.dup = rng, loss, dup
        self.in_flight = defaultdict(list)       # arrival tick -> [packets]
        self.sent = 0
    def send(self, now, pkt):
        self.sent += 1
        if self.rng.random() < self.loss:
            return
        copies = 2 if self.rng.random() < self.dup else 1
        for _ in range(copies):
            self.in_flight[now + self.rng.randint(1, 5)].append(pkt)
    def arrivals(self, now):
        return self.in_flight.pop(now, [])

def run(loss, reliable, n_msgs=20, ticks=400, seed=1):
    rng = random.Random(seed)
    data, acks = FairLossLink(rng, loss), FairLossLink(rng, loss)
    delivered = []                       # what the application on B sees
    seen = set()                         # B's dedupe table
    unacked = {i: -99 for i in range(n_msgs)}   # seq -> last send tick
    for now in range(ticks):
        # A: (re)transmit
        for seq, last in list(unacked.items()):
            if (reliable and now - last >= 8) or (not reliable and last < 0):
                data.send(now, seq); unacked[seq] = now
                if not reliable: del unacked[seq]
        # B: receive
        for seq in data.arrivals(now):
            if reliable:
                if seq not in seen:
                    seen.add(seq); delivered.append(seq)
                acks.send(now, seq)      # always ack, even duplicates
            else:
                delivered.append(seq)
        # A: receive acks
        for seq in acks.arrivals(now):
            unacked.pop(seq, None)
    dup = len(delivered) - len(set(delivered))
    return len(set(delivered)), dup, data.sent

print(f"{'link':<22}{'loss':>6}{'delivered':>11}{'duplicates':>12}{'packets sent':>14}")
for loss, reliable in [(0.3, False), (0.3, True), (0.7, True), (1.0, True)]:
    d, dup, sent = run(loss, reliable)
    name = "retransmit + dedupe" if reliable else "send once"
    print(f"{name:<22}{loss:>6.0%}{d:>8}/20{dup:>12}{sent:>14}")

Read the table from the top. Sending once over a 30% lossy link loses messages (15 of 20 delivered) and, because the link duplicates, delivers one of them twice. Retransmission plus deduplication delivers all 20 exactly once at the cost of extra packets: 40 at 30% loss, nearly 200 at 70%. And the last row is the instructive one. At 100% loss nothing is delivered, however long the sender tries (1,000 packets in 400 ticks), but still nothing is duplicated and nothing is invented. A perfect link is only perfect while the network is "fair". We will name exactly this distinction shortly: the last row has lost liveness but kept safety.

Analogy: registered post with a return slip

A fair-loss link is dropping unmarked letters into a post box: some arrive. A stubborn link is mailing the same letter every day until you give up. A perfect link adds a numbered letter and a return slip: you stop re-mailing when the slip comes back, and the recipient throws away any numbered letter they have already read.

Where it breaks down: the return slip can be lost too, which is why the receiver must acknowledge every copy it sees (the code above does), and why no finite scheme ever makes both sides certain the other knows (the Two Generals problem).

Partitions

A network partition is a period during which some set of nodes cannot exchange messages with the rest. In the model it is simply many links dropping everything for a while; there is no separate "partition" primitive. Two details matter in practice. Partitions can be asymmetric (A's messages reach B, B's do not reach A) and partial (A reaches B and B reaches C, but A cannot reach C), and those are the nasty ones, because nodes then disagree about who is alive. The partial-partition case study shows what that did to a real consensus cluster.

Safety and liveness

We have said what the world may do. Now we need a precise way to say what "the algorithm works" means. Leslie Lamport introduced the distinction in 1977, and Bowen Alpern and Fred Schneider gave the formal definitions in 1985. You already met the slogans in networking chapter 20: "nothing bad happens" and "something good eventually happens". Here is the version you can prove things with.

Think of an execution as a (possibly infinite) sequence of states of the whole system. A property is a rule that says which executions are acceptable.

Definitions

Safety property. "Something bad never happens." If an execution violates it, then the violation occurs at some finite point, and no continuation of the execution can repair it. Equivalently: a safety violation can be demonstrated by a finite prefix of the execution.

Liveness property. "Something good eventually happens." Every finite prefix can still be extended into an execution that satisfies it. So a liveness violation is never visible at any finite point: it is only visible in the infinite limit.

(Alpern and Schneider proved the pleasant theorem that every property of executions is the intersection of a safety property and a liveness property. So these two ideas are, in a sense, all there is.)

Why separate them? Because they can be traded against each other, and because each is checked differently. Consider the two degenerate algorithms. A system that does nothing at all satisfies every safety property (it never does anything bad), so safety alone is worthless. A system that answers every request instantly with a random value satisfies many liveness properties, so liveness alone is worthless. You need both, and you need to know which one to protect when the world turns hostile.

Analogy: the restaurant kitchen

"Never serve raw chicken" is a safety property: one plate of raw chicken is a violation you can point to at a specific moment, and no later good service undoes it. "Every order is eventually served" is a liveness property: however long a table has waited, you cannot say the property has been broken, because dinner may still arrive. A kitchen that closes its doors satisfies the first rule perfectly and the second not at all; a kitchen that rushes out raw chicken does the reverse.

Where it breaks down: real customers do not wait forever. A rule such as "within 30 minutes" is, formally, a safety property: once 30 minutes pass without a plate, the bad thing has happened at a finite moment. This is why a latency SLO is a safety property, even though it feels like "performance".

from typing import Optional

def first_safety_violation(trace: list[str]) -> Optional[int]:
    """Mutual exclusion: at most one holder at any moment.
    Returns the index of the event that makes it false, or None."""
    holders: set[str] = set()
    for i, ev in enumerate(trace):
        who, action = ev.split(":")
        if action == "grant":
            holders.add(who)
            if len(holders) > 1:
                return i             # the bad thing happened HERE; no suffix can undo it
        elif action == "release":
            holders.discard(who)
    return None

def liveness_status(trace: list[str], requester: str) -> str:
    """'Every request is eventually granted' -- what can a finite prefix tell us?"""
    asked = f"{requester}:request" in trace
    granted = f"{requester}:grant" in trace
    if not asked or granted:
        return "satisfied so far"
    return "not yet (still possible to satisfy if the run continues)"

good_but_slow = ["A:request", "A:grant", "B:request"]              # B is waiting
bad = ["A:request", "A:grant", "B:request", "B:grant", "A:release"]  # two holders
for name, tr in [("good_but_slow", good_but_slow), ("bad", bad)]:
    print(f"{name:14} safety violated at event: {first_safety_violation(tr)}")
    print(f"{'':14} liveness for B: {liveness_status(tr, 'B')}")

The checker for safety returns the exact index at which the bad thing happened (event 3 in the second trace): a witness you can show to a colleague. The "check" for liveness can only say "not yet". This asymmetry is why distributed-systems testing tools (chapter 19) check safety directly, and treat liveness by adding timeouts (turning it into a safety property about deadlines) or by waiting for the system to be quiet.

The design rule that ties it all together

Here is the principle that organises the rest of the course:

Safety in the weakest model, liveness in a stronger one

A well-designed protocol keeps its safety properties in the asynchronous model with any number of crashes, partitions and arbitrary delays; it needs a partially synchronous network and enough healthy nodes (say, a majority) only for liveness. During a storm it may stop making progress, but it will never give two clients contradictory answers.

Raft and Paxos are built this way, which is why a Raft cluster that loses its majority simply stops accepting writes instead of corrupting them. A design that does the opposite, that stays safe only when timing assumptions hold, will be fine for years and then fail catastrophically once. Spotting those designs is what the next two chapters are about.

Choosing a model is choosing a contract

No model is true. Every one is a lie that is useful so long as it is a good approximation. The professional question is therefore not "is this model right?" but "what happens when it is wrong?". Here are the common ways real systems violate the textbook assumptions:

  • Bounded processing time is broken by garbage collection, page faults, CPU throttling in containers and VM live-migration: pauses of seconds happen (systems chapter 3).
  • Bounded clock drift is broken by NTP step adjustments, leap seconds and VM suspensions: clocks jump (networking chapter 17).
  • Independent failures is broken by a shared power feed, a shared top-of-rack switch, or one buggy software release rolled out to every replica at once.
  • Crash faults only is broken by disk corruption, memory bit-flips and bugs, which are all mildly Byzantine. Systems answer with checksums, which turn corruption into a detectable omission.
  • Symmetric partitions is broken by flaky switches that drop only some traffic (the partial-partition case again).

Look back at the design rule: safety should survive the violation of timing assumptions, while liveness may degrade. A lease, the subject of chapter 4, is a perfect example of an algorithm that quietly assumes bounded clock drift and bounded pauses, which is a synchrony assumption. A lock built on leases alone is therefore safe only so long as those bounds hold. The remedy there, fencing tokens, is exactly the move this chapter recommends: take the safety property out of the timing model and hand it to a mechanism that is correct even in the asynchronous model.

Go deeper: failure detectors, randomness and "model strengthening" optional

The three timing models are the main points on a spectrum, not the only ones. Instead of assuming something about the network, you can add an oracle to the asynchronous model, a failure detector that gives (possibly wrong) hints about who has crashed. Chandra and Toueg showed in 1996 that precisely characterised weak detectors are enough to solve consensus; chapter 3 explains the classes. You can alternatively add randomness: Ben-Or's 1983 algorithm lets nodes flip coins so that agreement is reached with probability 1, without any timing assumption. Each strengthening buys back something the pure asynchronous model cannot do (chapter 2), and each is a different answer to the same question: which assumption are we willing to depend on, and what happens if it fails?

Also note a modelling choice we skipped: whether nodes have clocks at all. Algorithms for the asynchronous model use none, relying on logical clocks (networking chapter 17). Partially synchronous algorithms use clocks only to time out, so a wrong clock costs liveness but not safety. Chapter 7 returns to the question of when physical clocks may be trusted for safety.

Distributed systems connection

This chapter is the grammar of the rest. Chapter 2 says which problems are impossible in which model. Chapter 3 builds failure detectors, the mechanism that makes partial synchrony usable. Chapter 4 shows a famous case of safety quietly depending on timing. Chapters 5 to 7 define consistency models as safety properties of histories. Chapters 8 to 12 build consensus with safety in the asynchronous model and liveness after GST. And chapter 19 tests exactly these claims by dropping and delaying messages on purpose.

Key takeaways

  • "Correct" always means "correct in a model". A model has three parts: timing, node failures and links. Nearly every protocol argument is an argument about which assumptions to rely on.
  • Timing models: synchronous (known bounds; timeouts are proofs), asynchronous (no bounds; a slow node and a dead node are indistinguishable) and partially synchronous (Dwork, Lynch and Stockmeyer, 1988: bounds that are unknown, or that hold only after an unknown GST). Real networks behave like the third.
  • Fault models: crash-stop, crash-recovery (memory lost, disk kept, so persist promises before answering), omission (dropped sends and receives, including partitions) and Byzantine (arbitrary). Tolerating worse faults costs more nodes and more messages.
  • Links: fair-loss, then stubborn (retransmit), then perfect (number and deduplicate), then authenticated (MAC). TCP is a perfect link only within a connection.
  • Safety (nothing bad ever happens) is violated at a finite, demonstrable moment; liveness (something good eventually happens) can always still be rescued by a longer run. Every property is a combination of the two. A latency deadline is formally a safety property.
  • Design rule: keep safety under the weakest model (asynchronous, any partition, any pause), and require extra assumptions (partial synchrony, a live majority) only for liveness.
  • Every model is a lie. Know which real-world events falsify each assumption (pauses, clock jumps, correlated failures, partial partitions) and decide in advance which guarantee must survive.

In the Dwork-Lynch-Stockmeyer partially synchronous model with a Global Stabilization Time (GST), which statement is correct?

  1. The algorithm is told when GST occurs and can switch to a faster mode
  2. Message delay is bounded at all times, and the bound is known
  3. Before GST delays may be arbitrary; after GST they are bounded; the algorithm does not know when GST is
  4. GST is the moment the first node crashes
The essence of partial synchrony is that calm eventually comes but cannot be detected. The algorithm must stay safe at all times and can only count on progress during a long enough calm period. If the bound is known and always holds, that is the synchronous model.

A process is frozen for 20 seconds by a garbage-collection pause, then continues exactly where it left off. In the fault-model hierarchy, how is this best described?

  1. As an extremely slow node: to peers it looks like an omission or a crash followed by a recovery, and the danger is that it resumes with stale beliefs
  2. As a Byzantine fault, because it did something unexpected
  3. As a crash-stop fault, because it stopped
  4. It is outside every model, so nothing can be said about it
A pause is a timing phenomenon. Models without a bound on processing time (asynchronous, partially synchronous) already include it. It is not Byzantine (the node does nothing wrong, it merely resumes late) and not crash-stop (it comes back). The risk is its stale view of the world, which is the subject of chapter 4.

Which of these is a liveness property?

  1. Two nodes never decide different values
  2. No acknowledged write is lost
  3. At most one client holds the lock at a time
  4. Every correct node eventually decides a value
The first three each name a bad event that, if it happens, happens at a specific finite moment (safety). "Eventually decides" is violated only by an infinite run in which the decision never comes; at any finite time it might still be about to happen (liveness).

An acceptor in a consensus protocol promises to ignore proposals numbered below 7, then crashes and restarts, having kept the promise only in memory. Which model feature does this violate, and what is the consequence?

  1. The link model: the message was lost
  2. Crash-recovery with stable storage: after the restart it has forgotten the promise, so it may accept a lower-numbered proposal and break safety
  3. The synchronous model: the node was too slow
  4. Nothing: forgetting promises is harmless
In the crash-recovery model memory is lost and disk survives, so any promise that safety depends on must be written to stable storage (and synced) before the acknowledgement is sent. Otherwise the restarted node is, in effect, a different node that never made the promise.

  3. Liveness has not yet been delivered, but no violation is visible; safety (no duplicates, nothing invented) holds throughout
  4. Neither can be discussed because the link is down
This is the last row of the experiment. "Delivered eventually" is a liveness property and an hour of silence does not violate it (the network may heal). "At most once, nothing invented" is safety and is unaffected by loss. The scheme degrades gracefully: it waits, rather than lying.

Why is a plain heartbeat timeout a proof of a crash in the synchronous model but only a guess in the asynchronous one?

  1. Because synchronous networks use better heartbeats
  2. Because asynchronous networks lose more packets
  3. Because in the synchronous model the clocks are always exactly equal
  4. Because the synchronous model guarantees an upper bound on delay, so a reply that has not arrived by the bound can never arrive; the asynchronous model has no such bound
The proof depends on the bound. With a known bound Δ, "no reply within 2Δ plus processing time" is impossible for a live node. With no bound, a late message is always a possibility, so suspecting a node can always turn out to be a mistake.

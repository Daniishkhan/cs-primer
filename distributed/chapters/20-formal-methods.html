Specifying with TLA+

Testing finds bugs in code that already exists. A specification finds them in the design, before a line is written, by describing the system as states and steps and letting a model checker try every interleaving. This chapter introduces TLA+, shows a complete little specification, explains what the checker reports when you get it wrong, and then has you build the core of a model checker yourself in thirty lines of Python so that none of it feels like magic.

Why this matters

The subtlest distributed-systems bugs are not coding mistakes. They are flaws in the algorithm: a case the designers did not think of, an optimisation that quietly broke an invariant, a recovery path that works in each step but not in combination. Code review and testing struggle with these because the failing scenarios are long, specific and rare. Engineers who can write a short, precise specification, and who know when it is worth doing, catch an entire class of problem that otherwise surfaces as an outage.

Why specify

Prose design documents are ambiguous in exactly the places that matter. "The leader replicates the entry to a majority, then commits" says nothing of what happens if the leader changes in between, or an entry is replicated twice, or a node restarts having lost its last write. In code, the same ambiguity is buried in thousands of lines among logging and error handling. A formal specification is the middle path: a precise, executable description of what the system may do, small enough to read in an afternoon, with every ambiguity forced into the open because a machine will take it literally.

The deepest argument is the one the previous chapter ended on. Testing samples behaviours of an implementation; a model checker enumerates the behaviours of a design. If the design is wrong, no amount of faithful coding will make the system right, and the cheapest moment to learn that is before building it. Engineers at Amazon Web Services described, in a 2015 CACM article (Newcombe et al.), using TLA+ on core systems and finding subtle bugs, some needing traces dozens of steps long, that testing and review had not found. That experience is the subject of case study: formal methods at AWS.

TLA+ basics

TLA+ (the Temporal Logic of Actions) was created by Leslie Lamport, whose papers fill the reading list of this course. It is not a programming language. It is a way to write down a state machine in mathematics, with a checker called TLC to explore it. Four ideas are enough to read most specifications.

  • State. A state is an assignment of a value to each variable: say alice = 10, bob = 10. A behaviour is an infinite sequence of states, and a specification describes which behaviours are allowed.
  • Init is a predicate saying which states the system may start in.
  • Next is a predicate over pairs of states: the current one (variables written plainly) and the following one (variables written with a prime, x'). It lists every kind of step the system may take, usually as a disjunction of named actions. An action has two parts: an enabling condition on the current state (the guard) and equations for the primed variables. A variable not mentioned for the next state is simply unconstrained, which is a classic beginner's trap, so you list every variable.
  • The specification is Spec == Init /\ [][Next]_vars: start in an Init state, and every step is either a Next step or one that leaves the variables unchanged (a "stuttering" step). Stuttering is what lets specifications describe components that do nothing while another acts.

Then you state what you want to be true, in two flavours:

  • An invariant is a safety property: a predicate that must hold in every reachable state ("nothing bad ever happens"). "Account balances are never negative." "Two processes are never in the critical section together." "No two nodes decide different values."
  • A temporal property is more general: a statement about whole behaviours, written with operators such as [] ("always") and <> ("eventually"). Liveness properties ("something good eventually happens": every request is eventually answered) are of this kind. They only make sense under fairness assumptions (that an enabled action is not ignored for ever), because otherwise a system that simply does nothing satisfies all the safety properties and never makes progress. Safety and liveness are the same split you met in chapter 1.

How TLC works. TLC is an explicit-state model checker. You give it the spec and a small concrete instantiation (the "model": three nodes, values from {1, 2}, at most four messages). It computes the initial states, then repeatedly applies Next to every state found so far to generate successors, remembering the ones it has seen, in breadth-first order. In every new state it checks your invariants. If all reachable states pass, the check is complete for that model; if a state violates an invariant, TLC stops and prints the shortest path from an initial state to the bad one: an error trace, which is a step-by-step scenario you can read. The catch is state-space explosion: the number of reachable states grows very fast with the model's size, so you check small configurations, and rely on the "small scope hypothesis", the observation that most design bugs already show up with two or three nodes and a few messages.

A small, correct specification

Start with the smallest interesting example: two bank accounts and a transfer between them. The invariants say balances never go negative and money is neither created nor destroyed. (Lamport's own teaching examples include the TwoPhase and TCommit specifications of atomic commit, the subject of chapter 13; they are worth reading once this one makes sense.)

---------------------------- MODULE Transfer ----------------------------
EXTENDS Integers

VARIABLES alice, bob
vars == <<alice, bob>>

Init == /\ alice = 10
        /\ bob   = 10

\* Move n units from Alice to Bob. The first conjunct is the guard (enabling condition).
AtoB(n) == /\ n \in 1..alice
           /\ alice' = alice - n
           /\ bob'   = bob + n

BtoA(n) == /\ n \in 1..bob
           /\ bob'   = bob - n
           /\ alice' = alice + n

Next == \E n \in 1..10 : AtoB(n) \/ BtoA(n)

Spec == Init /\ [][Next]_vars

NoOverdraft == alice >= 0 /\ bob >= 0
Conserved   == alice + bob = 20
=========================================================================
SPECIFICATION Spec
INVARIANTS NoOverdraft Conserved

Read it as a state machine. /\ is "and" and \/ is "or"; a bulleted list of /\ lines is a conjunction. 1..alice is the set of integers from 1 to alice, so n \in 1..alice means "n is between 1 and Alice's balance", which is the guard: with a balance of 0 the set is empty and the action simply cannot happen. \E n \in 1..10 : ... says "there exists some n from 1 to 10 for which one of the actions occurs". Every reachable state has balances adding up to 20 and neither below zero, so TLC would finish with a short report.

What would TLC report? I cannot run TLC in this environment, so treat the following as illustrative; the numbers are cross-checked by the Python explorer below, which counts the same state space. With the spec above, Alice's balance can be any value from 0 to 20 and Bob's is whatever is left, so there are 21 distinct reachable states and TLC would report no error. Now break it by deleting the guard conjuncts n \in 1..alice and n \in 1..bob, the sort of omission that is easy to make when you are focused on the happy path. The Python below explores the same state space with and without the guard and prints the counts and the shortest violating path it finds. TLC would print a trace of the same shape (the exact values depend on the order in which it explores, so yours may differ), shown after the Python output:

from collections import deque

def next_states(s, guarded):
    alice, bob = s
    for n in range(1, 11):
        if not guarded or n <= alice:           # AtoB(n); the guard is  n \in 1..alice
            yield (alice - n, bob + n)
        if not guarded or n <= bob:             # BtoA(n)
            yield (alice + n, bob - n)

def bfs(guarded):
    init = (10, 10)
    parent = {init: None}
    queue = deque([init])
    while queue:
        s = queue.popleft()
        if s[0] < 0 or s[1] < 0:                # NoOverdraft violated
            path = []
            while s is not None:
                path.append(s); s = parent[s]
            return len(parent), path[::-1]
        for t in next_states(s, guarded):
            if t not in parent:
                parent[t] = s; queue.append(t)
    return len(parent), None

for guarded in (True, False):
    seen, trace = bfs(guarded)
    name = "with guard   " if guarded else "guard removed"
    print(f"{name}: {seen} distinct states explored;",
          "NoOverdraft holds" if trace is None else "NoOverdraft VIOLATED")
    for i, (a, b) in enumerate(trace or [], 1):
        print(f"   State {i}: alice = {a}, bob = {b}")

The trace is the point. Instead of "an assertion failed somewhere", you get a minimal scenario: move 1 unit, then try to move 10 when only 9 remain. Note that Conserved still holds throughout; the checker told you precisely which property broke and how. For a real protocol the trace might be thirty states of messages, crashes and retries, and each state is readable.

PlusCal

Many people find the raw "set of primed equations" style unfamiliar. PlusCal is an algorithm language, also designed by Lamport, that looks like pseudocode (variables, while loops, if, processes). A translator compiles it to TLA+, which TLC then checks. Its distinctive feature is labels: each label marks one atomic step, and the checker will interleave other processes' steps between labels. That forces you to decide, explicitly, where atomicity ends, which is the essence of concurrent design. A race is "the label boundary between check and update".

A model checker in thirty lines

The best way to demystify TLC is to write its core. The program below checks a classic first attempt at mutual exclusion between two processes: only one may be in the critical section at once. Each process loops: it wants in, tests whether the other's flag is down, and if so raises its own flag and enters. The state is (pc0, pc1, flag0, flag1), where pc is the process's position in its code. The invariant is "not both processes in cs". The checker is a breadth-first search with a parent map, which does three jobs: it remembers visited states, prevents re-exploring them, and lets us rebuild the path to a bad state. Then the same checker runs Peterson's algorithm, the classic correct solution (raise the flag, give the other process priority, wait while the other is interested and has priority).

from collections import deque
from typing import Callable, Iterable

# A state is (pc0, pc1, flag0, flag1). Each process loops: idle -> test -> set -> CS -> idle.
State = tuple[str, str, int, int]

def broken_next(s: State) -> Iterable[tuple[str, State]]:
    """Attempt 1: check the other's flag, THEN raise your own. The check and the set are two steps."""
    pcs, flags = [s[0], s[1]], [s[2], s[3]]
    for me in (0, 1):
        other = 1 - me
        pc = pcs[me]
        def go(new_pc: str, new_flag: int | None = None) -> State:
            p, f = pcs.copy(), flags.copy()
            p[me] = new_pc
            if new_flag is not None: f[me] = new_flag
            return (p[0], p[1], f[0], f[1])
        if pc == "idle":  yield f"P{me} wants in",             go("test")
        if pc == "test" and flags[other] == 0:
                          yield f"P{me} sees P{other} not in", go("set")
        if pc == "set":   yield f"P{me} raises its flag",      go("cs", 1)
        if pc == "cs":    yield f"P{me} leaves, lowers flag",  go("idle", 0)

def peterson_next(s: tuple) -> Iterable[tuple[str, tuple]]:
    """Peterson's algorithm: raise flag, give the turn away, wait while the other wants in AND has the turn."""
    pc0, pc1, f0, f1, turn = s
    pcs, flags = [pc0, pc1], [f0, f1]
    for me in (0, 1):
        other = 1 - me
        def go(new_pc, new_flag=None, new_turn=None):
            p, f = pcs.copy(), flags.copy()
            p[me] = new_pc
            if new_flag is not None: f[me] = new_flag
            return (p[0], p[1], f[0], f[1], turn if new_turn is None else new_turn)
        pc = pcs[me]
        if pc == "idle": yield f"P{me} wants in",         go("flag", 1)
        if pc == "flag": yield f"P{me} gives turn away",   go("wait", new_turn=other)
        if pc == "wait" and not (flags[other] == 1 and turn == other):
                         yield f"P{me} may enter",         go("cs")
        if pc == "cs":   yield f"P{me} leaves",            go("idle", 0)

def check(init, next_fn: Callable, safe: Callable) -> None:
    parent = {init: None}                       # state -> (previous state, action)
    queue = deque([init])
    while queue:                                # breadth-first: first violation found is a shortest one
        s = queue.popleft()
        if not safe(s):
            trace = []
            while parent[s] is not None:
                prev, action = parent[s]
                trace.append((action, s)); s = prev
            print(f"VIOLATION after exploring {len(parent)} states. Shortest trace ({len(trace)} steps):")
            print(f"   {'init':<26} {init}")
            for action, st in reversed(trace):
                print(f"   {action:<26} {st}")
            return
        for action, t in next_fn(s):
            if t not in parent:
                parent[t] = (s, action); queue.append(t)
    print(f"OK: {len(parent)} reachable states explored, mutual exclusion holds in all of them.")

print("== Attempt 1: test the other's flag, then set your own ==")
check(("idle", "idle", 0, 0), broken_next, lambda s: not (s[0] == "cs" and s[1] == "cs"))
print("\n== Peterson's algorithm ==")
check(("idle", "idle", 0, 0, 0), peterson_next, lambda s: not (s[0] == "cs" and s[1] == "cs"))

   init                       ('idle', 'idle', 0, 0)
   P0 wants in                ('test', 'idle', 0, 0)
   P0 sees P1 not in          ('set', 'idle', 0, 0)

Look at what you built: a state, a next_fn that yields successor states (Next), a predicate (safe, the invariant), a visited set, a queue, and a path reconstruction. That is an explicit-state model checker. TLC adds engineering that matters at scale: it stores 64-bit fingerprints of states to save memory, spills to disk, uses many cores, checks temporal properties by searching for cycles in the state graph, applies symmetry reduction (treating nodes 1,2,3 as interchangeable, to cut the search), and evaluates the full TLA+ language rather than Python functions. Notice also that Peterson's algorithm is declared safe for this model (two processes, one request each cycle, steps as atomic as the model says). A model checker proves exactly as much as the model encodes, and that is why the modelling choices, not the tool, are the skill.

Alternatives and neighbours

  • P is a language for modelling a system as communicating state machines exchanging events, with a checker that explores many orderings of message delivery, failures and timers. It reads more like a programming language than TLA+, which many engineers find easier, and it has been used at AWS and elsewhere to check both designs and, in some cases, code against specifications.
  • Apalache and TLAPS. Apalache checks TLA+ symbolically (using an SMT solver) instead of enumerating states, handling larger or unbounded domains for some problems; TLAPS is a proof system for TLA+, for when you want a mathematical proof of an invariant for all sizes rather than a check of small ones.
  • Alloy (relational, bounded, good for structural properties) and full verification of implementations (systems such as IronFleet and Verdi proved distributed protocol implementations correct with proof assistants and verifiers such as Coq and Dafny, at very high effort).
  • Lightweight formal methods. The cheapest on-ramp needs no new language: write a deliberately simple model of the system (a few dozen lines of Python), and use property-based, model-based tests (chapter 19) to check that the real implementation behaves like the model over random operation sequences, including faults. Another form is trace checking: record logs from tests or production and check them against the specification's rules. These do not exhaust the state space, but they catch the most expensive kind of mismatch, between what the design said and what the code does.

Analogy: the architect's scale model

Before pouring concrete, architects build a scale model and a wind-tunnel test. The model omits plumbing and paint but gets the shape and the loads right, and it exposes the structural flaw while it still costs a weekend to fix. A TLA+ spec is the scale model of a protocol: it leaves out sockets, logging and serialisation, keeps the states and the steps, and lets you push every kind of load through it.

Where it breaks down: a scale model is physically similar to the building. A specification is only as faithful as the author's abstraction; if the model leaves out the thing that fails (a retry, a restart that forgets memory), the checker will happily approve a flawed design.

Common misconceptions

"Model checking proves my system correct." It shows that your model, at the sizes you checked, satisfies the properties you wrote. A passing check with a weak invariant says little; a spec that has drifted from the code says nothing about the code. The value is in the bugs it finds and in the clarity of having to write the design down, not in a certificate.

When is it worth it?

Formal specification is an investment. It pays best when:

  • the design is concurrent or distributed and the failures that matter are combinations (crash during recovery during reconfiguration);
  • the cost of a flaw is high and hard to undo: data loss, a replication protocol, a consensus variant, an atomic-commit path, a lock or lease service, anything that touches money or durability;
  • you are making an optimisation or change to a protocol that is already trusted (the spec lets you check the change without risking production);
  • the design must be understood by many people; a spec is also the most precise documentation.

It pays poorly for ordinary CRUD logic, code dominated by integration rather than protocol, or anything where failures are simple and caught by testing. A sensible approach for a team starting out is one engineer, one critical protocol, a few days: specify the core state machine at the level of a one-page whiteboard sketch, with only the actions and failures that matter, check small models, and keep the spec next to the design document. If it finds nothing, you gained understanding and confidence. If it finds a trace, it has already paid for itself. The AWS experience, and what teams there said about it, is in the case study.

Distributed systems connection

Every protocol you studied has a famous specification: Paxos, Raft (Ongaro's thesis includes a TLA+ spec), two-phase commit. Reading one is the fastest way to learn what the paper left implicit, because a spec cannot wave its hands. Invariants like "no two leaders in the same term" and "committed entries are never lost" are the safety properties of chapter 9 and chapter 10, and a checker finds in seconds the interleavings that Raft's authors argued about in prose. Specification, testing and simulation are three lenses on the same thing: what the system may do under failure.

Key takeaways

  • Design bugs, rather than coding errors, cause the subtlest distributed failures. A specification states the design precisely enough for a machine to explore.
  • A TLA+ spec is a state machine: variables, Init, Next built from guarded actions with primed variables, and Spec == Init /\ [][Next]_vars.
  • Invariants are safety properties that must hold in every reachable state. Temporal properties ([], <>) cover liveness and need fairness assumptions.
  • TLC explores all reachable states of a small model breadth-first and reports either a count or the shortest error trace. State-space explosion limits model size; the small-scope hypothesis makes small models useful.
  • PlusCal is pseudocode that compiles to TLA+, with labels marking atomic steps. P, Apalache, TLAPS and Alloy are neighbours; lightweight methods (model-based tests, trace checking) are the cheap on-ramp.
  • A model checker is a BFS over a state graph with a visited set and an invariant check, as the Python version shows. It proves only what the model encodes.
  • Use it where designs are concurrent, failures combine, and mistakes are costly: consensus, replication, commit, locks.

Check your understanding

What is the difference between an invariant and a liveness property?

  1. Invariants are checked by tests; liveness properties by TLC
  2. An invariant concerns a single process; liveness concerns the whole system
  3. An invariant must hold in every reachable state ("nothing bad happens"); liveness says something good eventually happens and needs fairness assumptions
  4. They are two names for the same thing
Safety properties are violated at a finite point and can be checked state by state. Liveness is a statement about infinite behaviours, so it needs temporal operators and fairness (an enabled action is not starved for ever); without fairness a system that never moves satisfies all safety properties.

TLC reports "Invariant NoOverdraft is violated" with a three-state trace. Why is the trace so useful?

  1. It is a concrete, shortest scenario of steps from an initial state that reaches the bad state, which you can read and reason about
  2. It proves the invariant is false for all models
  3. It lists every bug in the specification
  4. It shows which line of the implementation is wrong
Breadth-first search yields a shortest path to a violation. It is evidence for this model only, and it refers to the specification, not to code; connecting it to code is your job.

In the broken mutual-exclusion attempt, what makes the violation possible?

  1. The processes run on different machines
  2. The flags are shared variables
  3. Process 1 is slower than process 0
  4. The test of the other's flag and the raising of one's own flag are separate steps, so both can test before either raises
This is a check-then-act race. Peterson's algorithm repairs it by raising the flag first and using a turn variable to break ties.

TLC finishes with "no error" on a model of three nodes and two values. Which conclusion is justified?

  1. The real implementation is correct for any cluster size
  2. Within that model and for the invariants written, no reachable state violates them; larger sizes, other properties and the code remain unchecked
  3. The design satisfies liveness
  4. The specification contains no mistakes
An exhaustive check of a bounded model is strong evidence, not a proof of the implementation or of all sizes (TLAPS-style proofs address unbounded sizes). A weak invariant also lets bad designs pass.

Which of these is the best candidate for writing a TLA+ spec?

  1. A form that validates an email address
  2. A REST endpoint that returns a list of users
  3. A new leader-handoff and reconfiguration protocol for a replicated database
  4. A CSS layout
Specs pay off where concurrency and failures combine and the cost of a design flaw is high. Ordinary request-handling logic is better served by tests.

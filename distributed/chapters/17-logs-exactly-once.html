Logs, Streams & Exactly-Once

A great many distributed systems turn out to be one idea wearing different clothes: an append-only log that many machines read at their own pace. This chapter opens up the best-known log system, Kafka, to see how it replicates, elects leaders, balances readers and compacts history, and then takes on the most oversold phrase in data engineering. "Exactly-once" is real, but only if you know precisely which boundary it covers and where your own code has to finish the job.

Why this matters

Almost every serious backend eventually sits on a log: for event streams, for change data capture, for replicated state machines, for audit trails. When a log-based pipeline misbehaves, the symptoms are always the same few: records lost after a broker failure, records processed twice after a restart, consumers stalling during a "rebalance", a topic that "looks fine" but silently dropped acknowledged data. Each one maps to a specific mechanism you can name and tune. And "does it support exactly-once?" is a question you will be asked, and will have to answer honestly, in design reviews for the rest of your career.

The log as the unifying abstraction

In 2013 Jay Kreps, one of Kafka's creators, wrote an essay called "The Log: What every software engineer should know about real-time data's unifying abstraction". Its thesis is simple enough to state in a sentence: a log is an append-only sequence of records, ordered by the position at which each was appended, and a surprising number of systems are this one structure used in different ways.

  • A database's write-ahead log (systems chapter 9) is a log that the database replays to recover.
  • A replication log is the same log shipped to followers, who replay it to stay identical (networking chapter 18).
  • A Raft or Paxos log is a log whose entries have been agreed by consensus, so that every replica of a state machine applies the same commands in the same order (chapter 8).
  • Change data capture turns a database's log into a stream that other systems consume (data chapter 19, which also covers the dual-write problem and the outbox; this chapter does not repeat it).
  • Kafka exposes the log directly as a product: producers append, any number of consumers read from any position, and the log is replicated and kept for as long as you configure.

The deep reason this works is determinism plus order. If several machines start in the same state and apply the same sequence of deterministic operations, they end in the same state. So agreeing on a log is the same problem as agreeing on state, and a log that can be read many times, from any position, lets you add a new reader (a search index, a cache, a new service) long after the data was written and have it catch up by replaying history.

Analogy: the ship's logbook

A ship's logbook is written once, in order, never edited; each entry is identified by its position (page and line). Anyone who needs to know what happened, the navigator, the insurer, the next captain, reads it from wherever they last stopped. Nobody asks the writer to resend anything, and a new officer can start from page one and reconstruct the whole voyage.

Where it breaks down: a paper logbook lives in one place. A distributed log must stay readable and correctly ordered while its machines crash and the network drops messages, and all of this chapter's difficulty lives in the word "while".

Inside a Kafka partition

You met the vocabulary in the data course: a Kafka topic is split into partitions, each partition is an ordered log, and the order exists only within a partition. A record's position in its partition is its offset: 0, 1, 2 and so on, assigned by the partition's leader as it appends. Offsets are never reused, and they are the currency of this whole chapter, because every delivery guarantee below is a statement about offsets.

Three structural choices explain most of Kafka's behaviour:

  • Brokers are the servers; each partition has one leader. All reads and writes for a partition go through its leader broker. Different partitions of the same topic have leaders on different brokers, which is how load spreads. The other replicas of the partition are followers.
  • Followers replicate by fetching. A follower is, mechanically, a consumer of its leader's log: it sends fetch requests with "give me everything from offset n" and appends what it receives. The leader never pushes.
  • Consumers pull and remember their own position. The broker does not track "which messages were delivered". A consumer asks for records starting at an offset, and the consumer group's progress is just one number per partition, stored durably (in an internal topic) as the committed offset. Two consumer groups reading the same topic are completely independent.

On disk a partition is a sequence of segment files (each a chunk of the log, with a sparse index from offset to file position); old segments are deleted or compacted according to a retention policy. Writes are sequential appends, reads are sequential scans, and the operating system's page cache does much of the caching, which is much of why this design is fast.

Replication: ISR, the high watermark and acks

You met leader-based replication in networking chapter 18 and data chapter 15. Kafka makes one choice that is worth understanding precisely, because it differs from Raft: it does not require a majority of all replicas. It requires all of the replicas in a dynamic set.

The set is the in-sync replicas, or ISR: the leader plus every follower that is "caught up", meaning in practice that it has fetched up to the leader's log end within a configurable time (replica.lag.time.max.ms). A follower that falls behind or stops fetching is removed from the ISR by the leader; when it catches up it is added back. The ISR is stored in the cluster's metadata, so everyone agrees on it.

The high watermark (HW) is the offset below which a record is stored on every replica in the ISR, which is just the minimum of their log end offsets. Consumers are served only records below the HW. This is the fix for a nasty problem: if a consumer could read a record that exists only on the leader and the leader then died, the consumer would have seen something that never officially existed.

The producer chooses how long to wait through acks:

SettingThe producer's send is acknowledged when…What it risks
acks=0immediately, without waiting for the brokerLoss on any failure; the producer cannot even know
acks=1the leader has appended it to its own logIf the leader dies before a follower fetched the record, the record is acknowledged yet lost
acks=allevery replica currently in the ISR has itNothing acknowledged is lost as long as at least one ISR member survives. But if the ISR shrinks to just the leader, "all" means "one"

That last row is why acks=all alone is not a durability guarantee, and why Kafka has a second setting, min.insync.replicas. It says: refuse to accept an acks=all write unless the ISR has at least this many members. With a replication factor of 3 and min.insync.replicas=2, every acknowledged write is on at least two brokers, and the partition keeps working if one broker fails. If two brokers fail, the leader refuses writes (the producer sees a "not enough replicas" error): the partition becomes unavailable for writes rather than silently weakening its promise.

Notice how this relates to the quorum thinking of networking chapter 18. A Raft group of three commits with any 2; Kafka's ISR can be 3, 2 or even 1, and membership changes are proposed by the leader and recorded by the controller (not decided by a vote). The price of waiting for all of the ISR rather than a fixed majority is that one slow follower stalls writes until the leader evicts it, which takes up to the lag timeout. The benefit is that with min.insync.replicas=2 a replication factor of 3 gives the same safety as Raft's majority, and a replication factor of 2 is workable. The following simulation walks through all of this: the HW as a minimum, the ISR shrinking, a write refused, and what a leader failure then forces you to choose.

Read the last block carefully. When the leader dies and only a stale replica is alive, the cluster faces a genuine dilemma with no third option: wait for an in-sync replica to come back (the partition is offline, but nothing acknowledged is lost), or promote the stale replica and keep serving (available again, but records that were acknowledged under the old leader are gone for ever). Kafka's name for the second option is unclean leader election, controlled by unclean.leader.election.enable, which is off by default in current versions. It is a pure availability-versus-durability switch, the same trade as CAP (chapter 2) wearing an operations setting's clothes. Leaving it off suits payments; turning it on can suit a metrics pipeline where staying up matters more than every sample.

Common misconception

"I set acks=all, so my data is safe." Only if the ISR was at least two (min.insync.replicas=2), and only if unclean election is off, and only if the broker flushes to disk or the replicas' memory survives the failure you are designing for. Kafka acknowledges after replication to follower page caches by default, not after an fsync on each broker; its durability argument rests on replicas failing independently, not on each write reaching a disk. If your failure model includes a whole rack losing power at once, check that your replicas are in different racks or zones.

After a leader change, the new leader's log might not match a follower's: that follower may hold records the new leader never received. Kafka stamps each leader's tenure with a leader epoch, and a follower rejoining asks the leader "where did epoch e end?" and truncates its own log to that point. This is the same repair step as Raft's overwriting of conflicting entries (chapter 10), and it is also why committed data is only ever the data below the HW.

Consumer groups and rebalancing

Data chapter 19 introduced consumer groups: partitions are divided among the group's members, each partition having at most one reader in the group, so the group's maximum parallelism is its partition count. What it did not cover is how the group stays consistent while members come and go, which is a small distributed-membership protocol of its own.

One broker acts as the group's group coordinator. Members send it heartbeats; the coordinator declares a member dead if it hears nothing for the session timeout, and a member that is alive but stuck in processing for longer than max.poll.interval.ms without polling is also ejected. Whenever the membership changes, whether a member joins, leaves or is ejected, or the topic's partition count changes, the coordinator starts a rebalance: it bumps the group's generation, collects the members' subscriptions, and has one member (the group leader) compute a new assignment, which the coordinator distributes.

The older "eager" protocol made every member give up all of its partitions at the start of a rebalance, so the whole group paused. Newer "cooperative" rebalancing moves only the partitions that need to move, and "static membership" lets a restarting consumer keep its identity and partitions rather than triggering a rebalance. The behaviours to understand:

  • Rebalances cost progress. While partitions are reassigned they are not being consumed, so lag grows. A flapping consumer (repeatedly ejected for slow processing) can keep a group in near-permanent rebalance.
  • Offsets are committed per generation. A consumer that lost its partitions to a rebalance but does not know it yet is a zombie. The coordinator rejects its offset commits (wrong generation), but meanwhile it may have processed records the new owner will process again. At-least-once delivery therefore includes duplicates caused by rebalances, not only by crashes.
  • Ordering is per partition. Moving a partition to a new consumer preserves its order, since the new owner resumes from the committed offset.

Log compaction

Normally a log is trimmed by time or size: after seven days, drop the oldest segment. Some logs are not histories but tables in disguise: "the current email address of each user", "the latest config of each service". For those, Kafka offers log compaction: instead of deleting by age, the broker's cleaner keeps at least the most recent record for every key, and discards older records with the same key. A record with a key and a null value is a tombstone, meaning "delete this key", and is itself removed after a grace period.

log = [(0, "u1", "alice@old.example"), (1, "u2", "bob@example.com"), (2, "u1", "alice@new.example"),
       (3, "u3", "carol@example.com"), (4, "u2", None),              # None = tombstone: delete u2
       (5, "u1", "alice@newest.example")]

def compact(records):
    latest = {}
    for off, key, val in records:
        latest[key] = (off, key, val)                               # later offsets win
    return sorted(v for v in latest.values() if v[2] is not None)  # drop tombstoned keys (after the retention delay in real Kafka)

print("before:", [(o, k) for o, k, _ in log])
for o, k, v in compact(log):
    print(f"after:  offset {o}  {k} -> {v}")
before: [(0, 'u1'), (1, 'u2'), (2, 'u1'), (3, 'u3'), (4, 'u2'), (5, 'u1')]
after:  offset 3  u3 -> carol@example.com
after:  offset 5  u1 -> alice@newest.example

Two details matter. Offsets are never renumbered, so after compaction there are gaps (above, offsets 3 and 5 remain and consumers just see the next available one). And compaction applies only to the older part of the log: the recent "head" is retained in full, so a consumer that is keeping up sees every update, while a consumer that starts from the beginning sees a snapshot of current values plus the recent history. A compacted topic is how a changelog topic can double as a table's durable backup, which is exactly how stream processors recover their state (see "Stream processing state" below).

KRaft: Kafka stops needing ZooKeeper

For most of its life Kafka kept its cluster metadata (which topics exist, who leads each partition, what the ISRs are) in ZooKeeper, with one broker elected as the controller that managed leader elections. That worked but meant operating two distributed systems and moving a lot of state between them whenever a controller failed over. The replacement is called KRaft (Kafka Raft): a small quorum of controller nodes runs the Raft algorithm of chapter 10 over a dedicated metadata log, and the rest of the cluster simply reads that log. In other words, Kafka applied its own idea to itself: metadata is a replicated log. Brokers keep metadata by replaying that log, a new controller already holds the same log and so starts quickly, and one system to deploy and understand replaces two. Recent Kafka versions have removed ZooKeeper mode entirely. The details of the transition are release-specific, so check the documentation of the version you run.

Delivery semantics, revisited

You have seen the three delivery guarantees twice: in networking chapter 16 (messages over a network) and data chapter 19 (consumers committing offsets). Here is the compact version, because the next sections need it exact. A pipeline has several hops, and at each hop one party must do two things, act and record that it acted, which cannot be made atomic across a network.

  • At-most-once: record first, then act (or send once and never retry). A crash in between loses the work.
  • At-least-once: act first, then record (or retry until acknowledged). A crash in between, or a lost acknowledgement, repeats the work.
  • Exactly-once? No protocol delivers a message "exactly once" over an unreliable network: that is what the Two Generals problem (networking chapter 16) rules out. What you can build is an exactly-once effect: at-least-once delivery, plus processing that tolerates repeats, either because the operation is idempotent or because the act and the record of the act are made atomic.

Where do repeats enter a Kafka pipeline? In exactly three places, and the rest of this chapter takes them in order:

  1. Producer to broker. The producer sends a record, the broker appends it, the acknowledgement is lost. The producer, correctly, retries. Now the log has two copies. (Fix: the idempotent producer.)
  2. Across a read-process-write step inside Kafka. A stream app reads a record, writes a result to another topic, and crashes before committing its input offset. On restart it processes the record again and writes the result again. (Fix: Kafka transactions.)
  3. Out of Kafka, into an external system. The same crash window, but the "write" is to a database or an API that Kafka does not control. (Fix: idempotent sinks or atomic offset storage, which you build.)

Spend a few minutes with the widget before reading on. Try to find every combination that ends in exactly one application, and notice which settings only help on one side of the pipeline. For instance, an idempotent sink (the "upserts by offset" consumer) does nothing for a duplicate that is already in the log as two different offsets; and an idempotent producer does nothing for a consumer that crashes between processing and committing. Exactly-once is a property of the whole path, so it is only as strong as its weakest hop.

The idempotent producer

When idempotence is enabled (enable.idempotence=true, the default in recent versions, which also forces acks=all), the broker assigns each producer a producer id (PID) when it starts. The producer numbers every record batch it sends to each partition with a monotonically increasing sequence number. The partition leader remembers, per PID, the sequence numbers it has recently appended. A batch whose sequence number it has already appended is acknowledged but not appended again; a batch that skips ahead (sequence 5 arrives but 4 never did) is rejected, so reordering cannot silently reorder the log either. Because the leader's state is derived from the log and replicated with it, a newly elected leader knows the same sequence numbers.

import random

class Broker:
    """One partition's log. Optionally remembers the last sequence per producer id."""
    def __init__(self, idempotent: bool):
        self.log: list[str] = []
        self.idempotent = idempotent
        self.last_seq: dict[int, int] = {}        # producer id -> highest sequence appended

    def append(self, pid: int, seq: int, value: str) -> str:
        if self.idempotent and seq <= self.last_seq.get(pid, -1):
            return "ack (duplicate, not appended)"
        self.log.append(value)
        self.last_seq[pid] = seq
        return "ack"

def run(idempotent: bool, seed: int = 3) -> list[str]:
    rng = random.Random(seed)
    broker = Broker(idempotent)
    for seq, value in enumerate(["a", "b", "c", "d"]):
        for attempt in range(1, 5):                       # producer retries up to 4 times
            reply = broker.append(pid=7, seq=seq, value=value)
            if rng.random() < 0.5:                        # the ACK is lost on the way back
                continue
            break
    return broker.log

print("without idempotence:", run(False))
print("with idempotence:   ", run(True))
without idempotence: ['a', 'a', 'b', 'b', 'c', 'd', 'd', 'd']
with idempotence:    ['a', 'b', 'c', 'd']

The scope of this guarantee is narrower than it sounds, and the narrowness is the usual source of confusion. Idempotence covers one producer session, one partition: if the application process crashes and restarts, it gets a new PID and its sequence numbers start from zero, so a record the old incarnation sent and the new incarnation re-sends from the application level is not recognised as a duplicate. For that you need transactions, which give the producer a stable identity.

Transactions: atomic read-process-write

The second repeat point is the loop at the heart of every stream processor: read a record from an input topic, process it, write the result to an output topic, and commit the input offset. A crash anywhere between the write and the commit duplicates output; committing first loses it. Kafka's answer is to make the output records and the input offset commit one atomic unit. Both are, after all, just writes to Kafka topics (the committed offset is a record in an internal offsets topic), so atomicity across a set of partitions is exactly what an atomic-commit protocol (chapter 13) provides.

The mechanism, step by step:

  1. The application sets a stable transactional.id and calls initTransactions(). The transaction coordinator (a broker that owns this id's slice of an internal, replicated transaction log) assigns a PID and bumps the id's epoch. Any older instance with the same id now holds a stale epoch and is fenced: its writes are rejected. This is a fencing token (chapter 4) used to kill zombies.
  2. The app calls beginTransaction(), reads a batch of input, and sends output records to any number of partitions. The coordinator is told about each new partition the transaction touches. The records are appended to those partitions immediately, but flagged as part of an open transaction.
  3. The app calls sendOffsetsToTransaction(), which adds the input offsets to the same transaction.
  4. The app calls commitTransaction(). The coordinator durably writes prepare-commit to its transaction log. That write is the commit point: once it is replicated, the transaction will commit even if the coordinator crashes, because its successor reads the log and finishes the job. The coordinator then writes a commit marker (a control record) into every partition involved, including the offsets topic, and finally marks the transaction complete. An abortTransaction() does the same with abort markers.

If you read chapter 13, this is two-phase commit with the coordinator's decision recorded in a replicated log, so the coordinator is not a single point of blocking failure. Here is the shape of the loop (pseudocode in Python style, close to the real Java API):

producer.init_transactions()                      # fence older instances with this transactional.id
while True:
    records = consumer.poll()                     # consumer: isolation.level=read_committed, auto-commit OFF
    producer.begin_transaction()
    try:
        for r in records:
            producer.send("output", process(r))   # appended now, invisible to read_committed readers
        producer.send_offsets_to_transaction(     # the input position moves in the SAME transaction
            consumer.positions(), consumer.group_metadata())
        producer.commit_transaction()             # prepare-commit logged -> markers written
    except Exception:
        producer.abort_transaction()              # markers say "ignore these records"
        consumer.seek_to_committed()              # start the batch again

On the reading side, a consumer with isolation.level=read_committed is handed only records from committed transactions (and non-transactional records). It is not served past the last stable offset (LSO), the offset of the earliest still-open transaction, and it silently skips records belonging to aborted ones. Two consequences follow directly. First, end-to-end latency now includes the commit interval: results are invisible until the transaction commits, so a pipeline that commits every 100 ms adds up to that much delay at each stage. Second, one stuck open transaction holds back every read_committed consumer of that partition, which is why transactions have a timeout after which the coordinator aborts them.

What Kafka's exactly-once covers, and what it does not

It covers read-process-write where both ends are Kafka: a topic in, a topic out, and the offsets, all in one atomic unit. It does not cover a side effect in anything else. If the "process" step sends an email, calls a payment API or writes to Postgres, a crash and retry will do it again, and Kafka cannot take it back. Kafka's own documentation scopes the guarantee carefully; marketing summaries often do not. The case study (Kafka's Exactly-Once Semantics) looks at how the feature was designed and what the claim does and does not promise.

Exactly-once with external sinks

Sooner or later the stream ends in something Kafka does not own: a relational database, a search index, a cache, an HTTP API. Both fixes below are the same idea you met in the transactional outbox: the check that detects a repeat must be atomic with the effect it guards, otherwise you have only moved the crash window.

Option 1: an idempotent write keyed by the record's identity. A record in Kafka has a natural unique key, its (topic, partition, offset). If the sink write is "put value V under key (partition, offset)", doing it twice is the same as doing it once. This suits sinks with upserts: INSERT ... ON CONFLICT DO NOTHING, a document store keyed by id, an object written to a deterministic file name. It does not suit "add 40 to a counter", unless you also store the keys you have already applied, in the same transaction as the counter.

Option 2: store the offset in the sink, in the same transaction as the output. If the sink is a transactional database, keep the consumer's position there, not in Kafka. On startup, read the offset from the database and seek the consumer to it. The effect and the offset then commit or roll back as one. Here it is with SQLite standing in for the database: design A commits the effect and then (never, because of a crash) the offset to a separate store; design B updates both in one transaction.

import sqlite3

LOG = [("order-1", 40), ("order-2", 15), ("order-3", 25)]   # one partition; offset = list index

def new_db() -> sqlite3.Connection:
    db = sqlite3.connect(":memory:")
    db.execute("CREATE TABLE revenue (total INTEGER)")
    db.execute("INSERT INTO revenue VALUES (0)")
    db.execute("CREATE TABLE offsets (next INTEGER)")        # design B keeps its offset here
    db.execute("INSERT INTO offsets VALUES (0)")
    return db

def process(db, off: int, offset_in_db: bool) -> None:
    """Apply record `off`. In design B the offset moves in the SAME transaction."""
    with db:                                                 # BEGIN ... COMMIT
        db.execute("UPDATE revenue SET total = total + ?", (LOG[off][1],))
        if offset_in_db:
            db.execute("UPDATE offsets SET next = ?", (off + 1,))

def run(offset_in_db: bool) -> int:
    db = new_db()
    external_offset = 0               # design A: the broker's committed offset for this consumer
    # First life: process record 0, then crash BEFORE the offset commit can happen.
    process(db, 0, offset_in_db)
    # Restart: where do we resume?
    start = db.execute("SELECT next FROM offsets").fetchone()[0] if offset_in_db else external_offset
    for off in range(start, len(LOG)):
        process(db, off, offset_in_db)
        if not offset_in_db:
            external_offset = off + 1
    return db.execute("SELECT total FROM revenue").fetchone()[0]

expected = sum(a for _, a in LOG)
print(f"A: offset stored outside the sink: revenue = {run(False)}  (correct = {expected})")
print(f"B: offset stored with the output:  revenue = {run(True)}  (correct = {expected})")
A: offset stored outside the sink: revenue = 120  (correct = 80)
B: offset stored with the output:  revenue = 80  (correct = 80)

Design A double-counts record 0 (the $40 order) because the crash fell between "effect committed" and "offset committed"; design B cannot be caught in that gap, because there is no gap. This is the pattern to reach for first when the sink is a database, and it is how most "exactly-once into a warehouse" connectors work underneath. A third family, used for sinks that support neither, is a two-phase commit sink: stage the output, then publish it only when the coordinator says the batch is durable. Stream processors such as Flink do this, tying the sink's commit to their checkpoints.

Stream processing state and checkpoints

So far the processing step was stateless. Real stream jobs keep state: running counts per user, the last 10 minutes of a window, a join buffer (data chapter 19 introduced windows and joins). That state lives in the processing nodes. If a node dies, the state it held must be restored to exactly the right point: the state as of some input position, and the input must be replayed from that same position. If the state were restored to a time earlier than the input position, records would be counted twice; later, and they would be skipped.

The obvious fix, "pause the whole job, copy every node's state, resume", stops the world. The classic alternative is the distributed snapshot algorithm of K. Mani Chandy and Leslie Lamport (1985), which takes a consistent global snapshot of a running system without stopping it. A consistent snapshot is one that could have occurred as an instant in the real execution: in particular, it never records a message as received without also recording it as sent (this is the "consistent cut" idea behind the vector clocks of networking chapter 17). Roughly, the algorithm works like this: one process records its own state and sends a special marker on all its outgoing channels. Any process receiving its first marker records its state, forwards markers on all its outputs, and from then on records the messages arriving on each other input until a marker arrives there too. Those recorded in-flight messages are the channel states, and together with the process states they form the snapshot.

Stream processors such as Apache Flink use a close cousin of this for their checkpoints, in a form specialised to dataflow graphs (the technique is usually called asynchronous barrier snapshotting). The source operators insert a numbered barrier into the data stream. Barriers flow along the edges with the records, never overtaking them. When an operator has received the barrier on all of its inputs it saves a copy of its state and forwards the barrier. Because streams are ordered, everything before barrier n is reflected in the snapshot and everything after it is not, so the sources only need to remember the input offset at which they inserted the barrier. The full snapshot, the source offsets plus every operator's state, is written to durable storage while processing continues.

Notice how this composes with everything above. Restoring state and rewinding the sources gives exactly-once state: the counts are as if every record had been processed once. The sink is a separate problem, since records emitted after checkpoint n but before the crash have already left the building. So a two-phase-commit sink stages its output transactionally and commits it only when the checkpoint that covers it completes; after a crash, uncommitted staged output is aborted and regenerated by the replay. Same principle once more: at-least-once replay, plus an atomic or idempotent boundary.

Analogy: the shared kitchen journal

Picture the restaurant kitchen where every station writes each dish it plans in a shared journal and ticks it when done. After a power cut, the head chef must decide what to re-cook. If the "planned" mark and the "done" tick are separate acts, you may re-plate a dish or forget one. Exactly-once is the discipline of writing the dish and its tick as one act, or of making re-plating harmless, for instance by writing the table number on every plate so a duplicate is recognised.

Where it breaks down: a kitchen can look at the dining room and see whether the dish already went out. Software can often not observe the outside world's state, so the check has to be built into the write itself.

Go deeper (optional): why snapshots need markers at all

Suppose each process simply recorded its state at an agreed wall-clock instant. Clocks disagree (networking chapter 17), so process A might record before sending message m and process B record after receiving m: the snapshot would show m received but never sent, a state no real instant could have had, and restoring it would break invariants. Markers solve this with causality instead of clocks: a marker sent after a process records its state tells the receiver "everything you receive from me from now on was sent after my snapshot", so the receiver knows which side of the cut each message falls on. The recorded in-flight messages are those sent before the sender's snapshot and received after the receiver's. In Flink's dataflow, which has no cycles and ordered channels, the barrier (with aligned checkpoints) already guarantees that nothing needs recording in flight, which is why the simplified version stores only operator states plus source offsets. When an operator has several inputs it must align: it buffers records arriving on inputs whose barrier has already come, until the barrier arrives on all of them.

Distributed systems connection

Every mechanism here is a theme from earlier in the course in new clothes. The ISR and high watermark are quorum intersection with a dynamic quorum (chapter 8). The unclean-election switch is CAP as a config flag. The transaction coordinator is two-phase commit with its decision logged in a replicated log (chapter 13), and its epoch is a fencing token (chapter 4). Exactly-once as at-least-once plus idempotence is the retry discipline of networking chapter 16 taken to its conclusion. And the next chapter takes the log across continents, where each of those round trips costs tens or hundreds of milliseconds.

Key takeaways

  • A log (append-only, ordered by offset, readable from any position) underlies WALs, replication, consensus, CDC and Kafka. Agreeing on a log is agreeing on state.
  • A Kafka partition has a leader and followers that fetch from it. The ISR is the set of caught-up replicas; the high watermark is the minimum LEO across it, and consumers see only records below it.
  • acks=all waits for the whole ISR, so it protects data only together with min.insync.replicas (typically 2 with replication factor 3). Unclean leader election trades durability for availability; it is off by default for a reason.
  • Consumer groups share partitions through a coordinator; rebalances pause consumption and can cause duplicates for zombies. Compaction keeps the latest record per key; KRaft replaces ZooKeeper by running Raft over a metadata log.
  • "Exactly-once" means at-least-once delivery plus an idempotent or atomic boundary. Repeats enter at the producer (fixed by PID plus sequence numbers), at read-process-write (fixed by transactions and read_committed), and at external sinks (fixed by you).
  • Kafka's guarantee covers Kafka-to-Kafka. For a database sink, key writes by offset or store the offset in the same transaction as the output.
  • Stateful stream jobs checkpoint with barrier snapshots in the spirit of Chandy and Lamport: save operator state and source offsets consistently, restore and replay after failure.

Check your understanding

A topic has replication factor 3, min.insync.replicas=2, producers use acks=all, and two of the three brokers holding a partition crash. What happens to producers writing to that partition?

  1. Writes continue, since the surviving leader has the data
  2. Writes are rejected until the ISR is back to at least two, so availability is sacrificed to keep the promise
  3. Writes continue but are silently marked as unacknowledged
  4. Kafka automatically lowers min.insync.replicas to 1
With one replica left the ISR has size 1, below the minimum of 2, so the leader refuses acks=all writes. That is the point of the setting: without it, acks=all would degrade silently to "the leader has it", the same as acks=1.

What does the high watermark of a partition tell you?

  1. The largest offset any producer has attempted to write
  2. The offset the slowest consumer group has committed
  3. The offset of the earliest open transaction
  4. The offset below which every in-sync replica has the record, and so the limit of what consumers can read
It is the minimum log end offset over the ISR. The earliest-open-transaction offset is the different "last stable offset", relevant to read_committed consumers; consumer progress is tracked separately as committed offsets.

An idempotent producer retries after a lost acknowledgement and the log does not get a duplicate. Which stronger failure still produces a duplicate if you rely on idempotence alone?

  1. The application process restarts and re-sends the record from scratch, getting a new producer id with sequence numbers starting at 0
  2. The network drops the first request entirely
  3. The broker's leader changes during the retry
  4. The acknowledgement is delayed instead of lost
Idempotence deduplicates within one producer session on one partition using (PID, sequence). A restarted application is a new session; its re-sent record looks fresh to the broker. A stable transactional.id (with fencing) extends the identity across restarts. Leader changes are handled because the sequence state is derived from the replicated log.

A Kafka Streams-style app does read-process-write between two topics with transactions and read_committed consumers, and then also sends a confirmation email inside the processing step. After a crash and retry, how many emails can the customer receive?

  1. Exactly one, because the pipeline is transactional
  2. Zero, because aborted transactions suppress side effects
  3. Possibly more than one, because Kafka's guarantee covers writes to Kafka, not the email service
  4. Exactly two, always
Aborting a transaction only hides records written to Kafka. An email is a side effect on a system Kafka does not control, so the retried processing step will send it again unless you make that step idempotent (for example by sending with a deduplication key keyed by the record's offset).

You consume from Kafka and update a Postgres table. Which design gives an exactly-once effect even if the consumer crashes at any point?

  1. Commit the Kafka offset first, then update Postgres
  2. Update the table and store the consumer's offset in a Postgres table inside the same database transaction, and resume from the stored offset on restart
  3. Update Postgres, then commit the offset to Kafka, and hope the crash window is small
  4. Enable the idempotent producer on the consumer
Option 1 can lose records (at-most-once). Option 3 can duplicate. A consumer has no producer to make idempotent. Putting the effect and the offset in one transaction removes the gap between them.

Why does a Chandy-Lamport-style snapshot use markers rather than "everyone saves state at 12:00:00"?

  1. Markers are faster to send than timestamps
  2. Wall clocks are exact, but state is too large to save at once
  3. Clocks disagree, so a clock-based snapshot could record a message as received but never sent; markers establish a consistent cut using causality instead
  4. Markers let the system skip saving state entirely
A consistent snapshot must be a state that could have existed at one instant. Without synchronised clocks you cannot pick that instant, but you can tell, via markers, which side of the cut each message falls on.

Time Revisited: HLCs & TrueTime

Wall clocks are close to real time but can be wrong in ways nobody can see. Logical clocks are always consistent with cause and effect but have no connection to the calendar. This chapter shows two ways to get the best of both: a hybrid logical clock, which you will implement and run, and TrueTime, Google's clock API that says "it is now somewhere between these two instants" and then waits out its own uncertainty. You will also see how a database without special hardware, like CockroachDB, handles the same problem with uncertainty intervals, and why leap seconds are a hazard worth knowing about.

Why this matters

The last chapter ended with a definition, strict serializability, whose key ingredient is real-time order: if a transaction finished before another began, the database must act as though it ran first. A database cannot enforce that without some way to compare "before" across machines. Timestamps are the cheapest tool for it, and wrong timestamps are the cheapest way to lose data. Every multi-version database, every "read as of time T" feature and every lease or expiry depends on how it treats time. Knowing the options, and what each costs, is part of choosing and operating one.

What you already know about time

In networking chapter 17 you saw that physical clocks drift and get corrected (NTP keeps them within milliseconds to tens of milliseconds, when it works, and a clock can even jump backwards); that Lamport clocks give a counter consistent with cause and effect but with no relation to real time; and that vector clocks additionally detect which events were concurrent, at a cost that grows with the number of nodes. Those three are the vocabulary here. The case study Ordering at Scale: Spanner & the Log previews the second half of this chapter.

The wish list

Imagine the clock you would like. It would have three properties:

  1. Causality: if event e happened before event f (chapter 17's happens-before), the timestamp of e is smaller than that of f. Lamport clocks have this; wall clocks do not.
  2. Closeness to wall time: timestamps look like real times, so humans can read them, "give me the data as it was at 10:00" means something, TTLs and leases make sense, and logs from different machines line up. Wall clocks have this; Lamport clocks do not.
  3. Compactness: a timestamp is a few bytes, not a vector with one entry per node.

Hybrid logical clocks aim for all three. TrueTime aims for something more demanding still: to say something about real time, not just causal order.

Hybrid logical clocks (Kulkarni et al., 2014)

The hybrid logical clock (HLC) was described by Sandeep Kulkarni, Murat Demirbas and colleagues in 2014 ("Logical Physical Clocks"). The idea is small: keep a Lamport-like clock, but instead of starting from zero and counting events, make its main component track the largest physical time the node has seen, and use a small counter only to break ties.

Each node keeps a pair (l, c):

  • l, the logical part: the largest physical time this node has seen, either from its own clock or carried in on a message. It is in the same units as the physical clock (say, milliseconds).
  • c, the counter: how many events have happened at the same value of l.

Timestamps compare lexicographically: first by l, then by c. The rules:

on local event or send:
    l' = l
    l  = max(l', physical_clock())
    if l == l':  c = c + 1        # clock hasn't moved on: count
    else:        c = 0            # clock moved ahead: counter restarts
    timestamp the event (l, c); on send, attach (l, c) to the message

on receive message m with (l_m, c_m):
    l' = l
    l  = max(l', l_m, physical_clock())
    if   l == l' == l_m:  c = max(c, c_m) + 1
    elif l == l':         c = c + 1
    elif l == l_m:        c = c_m + 1
    else:                 c = 0
    timestamp the event (l, c)

Why each branch? The goal is that a receive gets a timestamp strictly larger than both the node's own previous timestamp and the message's timestamp. If the physical clock is ahead of both, the new l is bigger than both and any counter will do (so 0). If l ties with just one, the counter must exceed that one's counter. If it ties with both, it must exceed the larger counter. Remove any branch and you can find a case where the new timestamp is not larger than something it must follow.

The properties that make it useful

  1. Causality, like Lamport. If e happens before f, then hlc(e) < hlc(f). (The rules above are built to guarantee it on every send, receive and local step.) As with Lamport clocks, the converse does not hold: a smaller HLC does not prove a causal link, because concurrent events also get ordered. For that you still need vector clocks.
  2. Bounded distance from physical time. If all physical clocks are within some bound ε of true time, then l never runs more than a bounded amount ahead of any node's own physical clock: l is some node's real clock reading from the past, and clock readings are within ε of each other. So an HLC timestamp always looks like a plausible wall-clock time, and you can use it for "as of" queries and TTLs.
  3. Small counter. The counter only grows while physical time stands still across many events, and resets whenever l advances; in practice it stays small. The paper discusses a compact representation, and implementations commonly pack the pair into 64 bits (milliseconds in the high bits and a few low bits of counter).
  4. Monotonic even if the clock steps backwards. Since l is the max of the old l and the physical clock, a backwards jump of the wall clock doesn't make timestamps go backwards. This also fixes the "NTP stepped my clock" hazard of chapter 17.

Here is the algorithm as running Python, for a node whose physical clock is wrong by a fixed skew. It also tracks a Lamport counter so the two can be compared. (The code is in hlc.py; HLC values are an ordered dataclass so that Python's < does the lexicographic comparison.)

from dataclasses import dataclass

@dataclass(order=True, frozen=True)
class HLC:
    l: int      # logical part: the largest physical time this node has heard of (ms)
    c: int      # counter: breaks ties between events with the same l

class Node:
    def __init__(self, name: str, skew_ms: int):
        self.name, self.skew = name, skew_ms
        self.l, self.c = 0, 0
        self.lamport = 0

    def pt(self, true_ms: int) -> int:               # this node's (wrong) physical clock
        return true_ms + self.skew

    def event(self, true_ms: int) -> HLC:             # local event or send
        old_l, pt = self.l, self.pt(true_ms)
        self.l = max(old_l, pt)
        self.c = self.c + 1 if self.l == old_l else 0
        self.lamport += 1
        return HLC(self.l, self.c)

    def receive(self, true_ms: int, m: HLC, m_lamport: int) -> HLC:
        old_l, pt = self.l, self.pt(true_ms)
        self.l = max(old_l, m.l, pt)
        if self.l == old_l == m.l:   self.c = max(self.c, m.c) + 1
        elif self.l == old_l:        self.c = self.c + 1
        elif self.l == m.l:          self.c = m.c + 1
        else:                        self.c = 0
        self.lamport = max(self.lamport, m_lamport) + 1
        return HLC(self.l, self.c)

An HLC trusts what it is told

Because l jumps up to match any incoming timestamp, one node whose clock is wildly ahead (a mis-set clock, a bug, an attacker) can drag every node's l into the future, and from then on all new timestamps there are "in the future" until real time catches up. The bound in property 2 holds only if clocks really are within ε. Systems that use HLCs therefore also configure a maximum acceptable offset and treat an incoming timestamp that is further ahead than that as an error to refuse or alarm on, rather than blindly absorbing it.

Bounded uncertainty: TrueTime

HLCs give causality and a plausible time, but they cannot answer the question strict serializability asks: did transaction A finish before transaction B began, in real time? If two unrelated transactions on different machines get HLC timestamps, nothing in them says which was first in the world. To answer, you need a bound on how wrong the clocks can be, and a way to wait that bound out.

That is what Google's TrueTime offers inside Spanner (Corbett et al., OSDI 2012). Its API is unusual, because it does not return a time. It returns an interval:

  • TT.now() returns [earliest, latest], with the guarantee that the true current time lies somewhere inside it.
  • TT.after(t) is true if t is definitely in the past, meaning t < earliest.
  • TT.before(t) is true if t is definitely in the future, meaning t > latest.

Half the width of the interval is the uncertainty ε. Google's data centres contain time masters with GPS receivers or atomic clocks, and every machine runs a daemon that polls several masters. Between polls the machine's own clock can drift, so the daemon widens ε at an assumed worst-case drift rate, then shrinks it at the next poll. The paper reports the bound as a few milliseconds on average, saw-toothing between syncs. The important design choice is the honesty of the API: instead of a number that is "probably right", you get a range that is claimed to be always right, and that claim is what everything else leans on. The guarantee is only as good as the drift assumption and the hardware.

Commit wait

Suppose transaction T1 commits and wants a commit timestamp s1. We want any transaction that starts after T1 has been acknowledged to the client to get a larger timestamp. Spanner's two rules:

  1. Choose s1 ≥ TT.now().latest at the time the commit is requested. This puts s1 at or after the end of what the true time could be right now.
  2. Wait before acknowledging: do not tell the client (and do not release the locks that make the write visible) until TT.after(s1) is true, which is when s1 is guaranteed to be in the past. This is the commit wait.

Why does this give external consistency (Spanner's name for strict serializability: the serial order matches the real-time order of commits)? Follow the chain. When T1 is acknowledged, true time is greater than s1 (because TT.after(s1) held, and the true time is always inside the interval, which was entirely after s1). Anything that starts after that acknowledgement, say T2 at another datacenter, begins at a true time greater than s1. T2 picks s2 ≥ TT.now().latest, and latest is at least the true time, so s2 > s1. Timestamps order the transactions in the same way the real world did. The proof needs the interval guarantee, the two rules, and nothing else.

Here the argument runs as code. Two nodes have clock errors of +3 ms and −4 ms (both within ε = 5 ms). T1 commits on A, the client is told "done", and 1 ms later T2 starts on B:

EPS = 5                               # TrueTime-style uncertainty bound, in ms

class Clock:
    """A node's clock: true time plus an error we never see, but which is always within +/- EPS."""
    def __init__(self, error_ms: int):
        assert abs(error_ms) <= EPS
        self.error = error_ms
    def read(self, true_ms: float) -> float:
        return true_ms + self.error
    def now(self, true_ms: float) -> tuple[float, float]:        # TT.now(): an interval
        r = self.read(true_ms)
        return (r - EPS, r + EPS)
    def after(self, t: float, true_ms: float) -> bool:            # TT.after(t): surely in the past?
        return self.now(true_ms)[0] > t

def commit(clock: Clock, start_true: float, commit_wait: bool) -> tuple[float, float]:
    """Pick a commit timestamp; return (timestamp, true time at which the client is told 'committed')."""
    true_ms = start_true
    s = clock.now(true_ms)[1] if commit_wait else clock.read(true_ms)   # latest possible 'now' vs plain clock
    if commit_wait:
        while not clock.after(s, true_ms):                              # commit wait
            true_ms += 0.5
    return s, true_ms + 1                                               # +1 ms to apply and reply

a, b = Clock(+3), Clock(-4)           # A runs 3 ms fast, B runs 4 ms slow (both within EPS)
for wait in (False, True):
    s1, acked = commit(a, 1000.0, wait)                                 # T1 commits on node A
    s2 = (b.now(acked + 1)[1] if wait else b.read(acked + 1))           # T2 starts 1 ms after the ack, on B
    print(f"commit wait={wait!s:<5}  T1 ts={s1:.1f}  acked at true {acked:.1f} ms | "
          f"T2 starts at true {acked+1:.1f} ms, ts={s2:.1f}  -> "
          f"{'order preserved' if s2 > s1 else 'T2 (later) got a SMALLER timestamp: external consistency violated'}")
commit wait=False  T1 ts=1003.0  acked at true 1001.0 ms | T2 starts at true 1002.0 ms, ts=998.0  -> T2 (later) got a SMALLER timestamp: external consistency violated
commit wait=True   T1 ts=1008.0  acked at true 1011.5 ms | T2 starts at true 1012.5 ms, ts=1013.5  -> order preserved

Without the wait, T2, which began strictly after T1 was acknowledged, receives 998 against T1's 1003: the database would order them backwards. With the wait the acknowledgement is delayed by about 10 ms (that is 2ε, with ε = 5 ms) and the order is right. The cost is real: commit wait adds roughly 2ε to a write's latency, which is why Google works to keep ε small, and why the wait is overlapped with the replication round-trip that must happen anyway (writes are replicated by Paxos, chapter 9, and the paper notes that the wait runs concurrently with it). Notice also that the system's correctness does not depend on ε being small; its speed does. If the clocks misbehave, TrueTime reports a wider interval and commits get slower rather than wrong. This is the trade that chapters 14 and 18 build on.

Analogy: the train timetable that admits it can be late

A normal clock is a station announcement: "the train leaves at 10:00". TrueTime is the announcement "the train leaves between 9:58 and 10:02". Now you can plan safely: if you need to be sure it has left before you close the barrier, you wait until 10:02 has passed. You pay a few minutes of waiting, and you are never wrong.

Where it breaks down: the timetable's uncertainty is a published fact. TrueTime's uncertainty is a computed claim, made from drift rates and the freshness of the last sync, and the guarantee is only as good as the hardware and assumptions behind it. An atomic clock that is wrong, or a drift beyond the assumed bound, breaks the proof.

Without special hardware: uncertainty intervals and read restarts

Most of us do not have GPS receivers in our racks. CockroachDB, a distributed SQL database inspired by Spanner, runs on ordinary servers with ordinary clock synchronisation, and uses HLC timestamps to version data. It makes a different bargain, which is worth understanding because it is the more common situation. What follows is a qualitative description of the idea; the product's documentation is the authority on details and defaults.

Instead of measuring clock error, the database is configured with a maximum clock offset Δ: an assumption that no two clocks in the cluster ever differ by more than Δ. (Nodes that notice their own clock drifting too close to the limit are designed to stop rather than risk breaking the assumption.) Every transaction reads at a timestamp t, and the problem is a value written with a timestamp slightly after t: did that write really happen after the read started, or did it commit earlier in real time, on a node whose clock ran ahead? Within Δ of t, the database cannot tell.

The rule: if a read encounters a committed value whose timestamp lies in (t, t + Δ], the transaction is restarted (the read is pushed to a timestamp above that value), so that it now sees the value. Treating the uncertain value as "in the past" is safe, because if it was truly later, nothing is lost by seeing it at a later read timestamp, and if it was truly earlier, ignoring it would have been a stale read. Values outside the window need no care. Further refinements limit how often one transaction can be restarted by the same node's writes, so the cost stays modest for most workloads.

Neither design is "better". They are two answers to "what can we assume about clocks?": one buys a hardware bound and spends it on writes, the other assumes a software bound and spends it on reads. Chapter 14 compares them with Percolator's timestamp oracle and Calvin's deterministic ordering.

Leap seconds and smearing

One more reason to be careful with wall time. UTC is kept close to the Earth's rotation by occasionally inserting a leap second, a 61-second minute (23:59:60). Computer clocks that count seconds since 1970 have no way to represent the extra second, so systems handle it in one of three ways: repeat a second (time appears to go backwards), stall for a second, or smear. Software that subtracts two wall-clock readings to measure a duration then sometimes gets zero or a negative number. That is exactly what happened to Cloudflare's DNS in 2017, told in the leap second case study, and the fix there was the standard one: measure durations with a monotonic clock (chapter 17).

Smearing hides the extra second by stretching it: the clock runs very slightly slow over many hours (Google's public time service smears over 24 hours), so the second is absorbed with no 23:59:60 and no step. Several large providers do this. The price is that for those hours the clock is up to half a second away from true UTC, and, importantly, different providers smear differently, so mixing smeared and non-smeared time sources in one cluster makes machines disagree by up to a second. That is large compared with a TrueTime interval, so a system that depends on bounded uncertainty has to choose one policy cluster-wide, and its ε has to cover whatever the policy does. (An international decision in 2022 set the course for phasing out leap seconds by or before 2035, but time software will have to deal with the existing ones for a long time, and with the same class of bug from any future clock adjustment.)

Distributed systems connection

Time keeps coming back. Leases and fencing tokens (chapter 4) are the discipline of using clocks only conservatively. Chapter 14 shows Spanner, Percolator and Calvin as three different positions on how much to trust clocks. Multi-region systems (chapter 18) pay the speed-of-light cost twice: once in message latency, once in the uncertainty that bounds how closely their clocks can agree. And deterministic simulation (chapter 19) works by replacing the real clock with a controlled one, because time is the most common source of non-reproducible bugs.

Key takeaways

  • Wanted: timestamps that respect causality (like Lamport), look like wall time (so "as of" queries work) and stay small (unlike vector clocks). Hybrid logical clocks (Kulkarni et al., 2014) provide all three.
  • An HLC is a pair (l, c): l is the largest physical time seen, c is a counter for ties. On receive, l becomes the max of the local clock, the old l and the message's l; the counter is set so the result is strictly larger than both predecessors. Timestamps stay within the clock-error bound of real time and never go backwards, even if the wall clock does. An HLC does not detect concurrency.
  • TrueTime (Spanner) exposes uncertainty: TT.now() returns an interval that contains the true time. Choose the commit timestamp at the interval's latest, then wait until it is surely past. That commit wait (about 2ε) yields external consistency: anything that starts after a commit is acknowledged gets a larger timestamp.
  • Correctness in the TrueTime design does not depend on ε being small; speed does. Wider uncertainty means slower commits, not wrong ones, provided the bound is honest.
  • Without special hardware, CockroachDB-style designs assume a maximum clock offset and handle ambiguity on reads: a committed value in (t, t + max offset] forces the read to restart above it. The cost moves from writes to reads, and the guarantee depends on the assumption holding.
  • Leap seconds and clock steps break code that subtracts wall-clock readings. Use monotonic clocks for durations. Smearing hides a leap second but needs every machine to use the same policy.

Check your understanding

Node B's wall clock reads 970 when it receives a message that A stamped with HLC 1000.0. What is B's HLC after the receive (assuming B's own previous l was 0)?

  1. 970.0, because B uses its own clock
  2. 1000.1, because l takes the max of B's clock, B's old l and the message's l, and the counter is incremented past the message's
  3. 1000.0, the same as the message
  4. 971.0, one tick of B's clock after the receive
The new l is max(0, 1000, 970) = 1000, equal to the message's l only. The rule for that case sets the counter to the message's counter plus one, giving 1000.1, which sorts strictly after the send (1000.0).

Which property does a hybrid logical clock have that a plain Lamport clock does not?

  1. Its timestamps stay close to real wall-clock time, within the clock-error bound
  2. It can tell whether two events were concurrent
  3. It does not need messages to carry timestamps
  4. It guarantees real-time order of transactions across nodes
An HLC's l tracks physical time, so timestamps look like times and support "as of" queries. It is still scalar, so like Lamport clocks it cannot detect concurrency (that needs vector clocks), and it does not by itself know the real-time order of unrelated events (that needs bounded uncertainty).

In Spanner's commit protocol, why must the coordinator wait until TT.after(s) before acknowledging the commit?

  1. To give replicas time to write to disk
  2. To make the commit timestamp unique
  3. So that s is surely in the past by the time anyone learns of the commit, which guarantees later transactions pick larger timestamps
  4. To synchronise the GPS receivers
The wait ensures true time has passed s before the client is told. Any transaction that starts after that has a true start time greater than s, and its own timestamp is at least the latest bound of its clock interval, which is at least the true time, hence greater than s. Disk writes and uniqueness are handled elsewhere.

How does a CockroachDB-style read handle a committed value with a timestamp slightly above its read timestamp, inside the maximum-offset window?

  1. It ignores it, since the timestamp is greater than the read timestamp
  2. It waits for the commit-wait period to pass
  3. It aborts permanently with an error
  4. It restarts at a higher timestamp so it will see the value, because it cannot tell whether the write really came first
The writer's clock might be ahead, so the write could have committed before the read started in real time. Ignoring it risks a stale read. Restarting above it is always safe. No hardware-bounded wait is involved; the cost is a retry on the read side.

Why can mixing leap-smearing and non-smearing time sources in one cluster be dangerous?

  1. Smeared time runs faster than real time forever
  2. For hours around a leap second the two kinds of clock disagree by up to about a second, which can exceed any assumed clock-error bound
  3. Smearing deletes log entries
  4. NTP refuses to talk to smeared servers
Smearing spreads the extra second over many hours, so a smeared clock is off from UTC by a fraction of a second during that window, while an unsmeared clock steps by a full second. Machines using different sources then differ by up to about a second, far more than the milliseconds an uncertainty bound assumes.

CRDTs: Data That Merges Itself

Coordination is expensive and sometimes impossible: a phone in a tunnel, a data centre across an ocean, an editor working offline on a plane. A conflict-free replicated data type (CRDT) is a data structure designed so that replicas can accept updates independently, exchange state in any order, with duplicates and delays, and still end up identical. This chapter explains the mathematics in pictures (a join-semilattice), builds counters, registers and sets in runnable Python, shows what is hard about collaborative text, compares CRDTs with operational transformation, and ends with the unglamorous problem every real deployment hits: tombstones.

Why this matters

Almost every system that lets two copies of the data change without talking to each other (a leaderless database, a multi-region active-active store, an offline-first mobile app, a collaborative editor) eventually faces conflicts. You can pick a winner and silently drop the loser's update, push the problem to the application, or design the data so that conflicts cannot arise. CRDTs are the third option, and they are the technical core of real products. Knowing which structures merge cleanly, and which invariants they cannot protect, is what lets you design systems that stay available during partitions without corrupting data.

The problem: concurrent writes with no referee

In Replication & Consistency you met leaderless and multi-leader replication, and the Dynamo case study showed a shopping cart that always accepts a write, even during a partition, and sorts out the consequences later. The danger is that two replicas modify the same item concurrently. When they next talk, what is the merged value? Three families of answer exist:

  • Pick a winner (last write wins by timestamp): simple, and it silently discards one update (we will build it and break it below).
  • Keep both and ask the application (Dynamo-style "siblings"): nothing is lost, but every application must write correct merge code, which is hard and rarely tested.
  • Make the data type merge itself, correctly, by construction. This is the CRDT approach.

Strong eventual consistency

Plain eventual consistency says: if updates stop, replicas eventually converge. That is a weak promise. It does not say how conflicts are resolved (many systems do it in an ad hoc way that can lose updates), and it allows a replica to show a value, then roll it back. In 2011 Shapiro, Preguiça, Baquero and Zawirski defined a stronger property, strong eventual consistency (SEC), and a family of data types that provides it. A system has SEC if:

  • Eventual delivery: an update delivered to one correct replica is eventually delivered to all of them.
  • Convergence: any two replicas that have received the same set of updates are in the same state, whatever the order they arrived in.
  • Termination of the operations, so every update eventually takes effect.

The crucial word is same set. There is no consensus step, no leader, no rollback: convergence is a deterministic function of what a replica has seen. Every replica can accept reads and writes at any time, even when partitioned from all the others, which in CAP terms is an AP design that gives up linearizability but never gives up availability. Remember the limits of the promise, though: SEC guarantees that the replicas agree, not that the agreed result is what any user intended, and not that application-level invariants hold (more on that at the end and in chapter 16).

Join semilattices: the mathematics, in pictures

How can merging be correct no matter the order? Think about what the network does to messages: it reorders them, it duplicates them (retries, at-least-once delivery, chapter 16 of the networking course), and a replica may receive them in different groupings (one batch of three, or three singles). The merge function has to be indifferent to all three. Mathematics has a name for such a function.

A join semilattice is a set of states with a partial order ≤ ("carries no more information than") and an operation called the join, written ⊔ and also called the least upper bound: the join of two states is the smallest state that is above both. It satisfies three laws, which are exactly what the network demands:

LawStatementThe network behaviour it absorbs
Commutativea ⊔ b = b ⊔ aMessages arrive in a different order at different replicas.
Associative(a ⊔ b) ⊔ c = a ⊔ (b ⊔ c)A replica merges things one by one, another receives them pre-combined by an intermediary.
Idempotenta ⊔ a = aThe same message is delivered twice.

Every one of these laws is a counterexample waiting to happen if you drop it:

  • Merge two counters by adding their values: not idempotent. A duplicated message double-counts.
  • Merge two numbers by averaging: commutative, but not associative (avg(avg(1, 2), 3) is 2.25, while avg(1, avg(2, 3)) is 1.75), so the result depends on how updates were grouped.
  • Merge by "take the left one": idempotent and associative, but not commutative, so two replicas that merge in different orders disagree.

The picture below is the simplest semilattice: all subsets of {a, b, c}, ordered by inclusion, with join = union. Higher means "knows more". Replica A holds {a} and replica B holds {b}. The only state that is above both, and the lowest such, is {a, b}: that is the merge, and it is where both replicas will end up if they exchange states in either direction, twice, or in pieces.

The second ingredient is that every update must be monotonic (inflationary): it moves the state upward (or leaves it) in the order. A replica never goes down, so it can never "forget" something it has merged. Together, the two ingredients give the theorem that makes state-based CRDTs work: if all replicas start at the bottom, all updates are monotonic, and merge is the join, then any two replicas that have received the same updates are in the same state, whatever the order of delivery.

State-based, operation-based and delta CRDTs

There are two classical ways to ship changes between replicas, and a hybrid.

  • State-based (CvRDT, "convergent"). Replicas periodically send their entire state to others, who merge it with the join. Needs almost nothing from the network: only that updates eventually propagate, in any order, with duplicates and loss tolerated (a lost message is harmless because a later state subsumes it). The cost is bandwidth: state can be large.
  • Operation-based (CmRDT, "commutative"). Replicas send each operation (for example "add milk" or "increment"). Messages are small. But now the network must deliver every operation to every replica exactly once and, for operations that are not commutative on their own, in causal order (vector clocks); a duplicate increment would be counted twice. The operations that can be concurrent must commute.
  • Delta-state. Almeida, Shoker and Baquero's delta-state CRDTs send only the delta: the small part of the state that changed, expressed as a state itself and merged with the same join. You keep the robustness of state-based merging (duplicates and reordering are fine) and approach the message size of operations.

Here is a state-based G-Counter (below) in space-time form. The replicas never coordinate: each increments only its own slot, ships its full vector whenever it likes, and merges the vector it receives by taking the maximum in each slot. A lost message and a duplicate message both appear, and neither changes the outcome.

Analogy: tally sheets in a shared office

Three colleagues count visitors with tally marks, each only ever adding marks in their own column of a sheet. Photocopy your sheet and hand it to anyone, any number of times, in any order. To get the total, a person takes each column's highest count they have seen and adds the columns. Handing over an old copy is harmless, handing the same copy twice is harmless, and nobody ever needs to ask anyone's permission to make a mark.

Where it breaks down: every colleague who ever counts needs a column, so the sheet grows with the number of replicas. Real CRDTs have exactly this metadata cost and it is a real design constraint, especially with many short-lived clients.

Worked examples, in running Python

All the code in this chapter uses only the standard library and is deterministic. Each class has a merge that mutates the receiver by joining another replica's state into it.

Counters: G-Counter and PN-Counter

Why not just keep one integer per replica and merge with max? Because if two replicas both increment 5 to 6 concurrently, max(6, 6) is 6 and an increment is lost. The fix is the tally sheet: one slot per replica, written only by its owner. A G-Counter (grow-only) has value Σ slots and merges slot by slot with max. To allow decrements, a PN-Counter keeps two G-Counters, one for increments (P) and one for decrements (N); the value is P − N. You cannot "decrement" a G-Counter, because that would move the state down the lattice.

"""State-based counters. merge() is a join: commutative, associative, idempotent."""
from __future__ import annotations
import random


class GCounter:
    """Grow-only counter: one slot per replica; a replica only bumps its own slot."""
    def __init__(self, rid: str, slots: dict[str, int] | None = None):
        self.rid, self.slots = rid, dict(slots or {})

    def inc(self, n: int = 1) -> None:
        self.slots[self.rid] = self.slots.get(self.rid, 0) + n

    def value(self) -> int:
        return sum(self.slots.values())

    def merge(self, other: "GCounter") -> None:
        for r, n in other.slots.items():
            self.slots[r] = max(self.slots.get(r, 0), n)   # pointwise max

    def state(self):
        return dict(sorted(self.slots.items()))


class PNCounter:
    """Increase/decrease counter = two G-Counters: value = P - N."""
    def __init__(self, rid: str):
        self.p, self.n = GCounter(rid), GCounter(rid)

    def inc(self, k: int = 1): self.p.inc(k)
    def dec(self, k: int = 1): self.n.inc(k)
    def value(self) -> int: return self.p.value() - self.n.value()

    def merge(self, other: "PNCounter") -> None:
        self.p.merge(other.p); self.n.merge(other.n)

    def state(self): return (self.p.state(), self.n.state())


if __name__ == "__main__":
    a, b = GCounter("A"), GCounter("B")
    a.inc(3); b.inc(2)                         # concurrent, while partitioned
    print("before merge:", a.value(), b.value())
    a.merge(b); b.merge(a)
    print("after merge: ", a.value(), b.value(), a.state())
    a.merge(b); a.merge(b)                     # duplicate delivery: harmless
    print("merged again:", a.value(), "(idempotent)")

    x, y = PNCounter("A"), PNCounter("B")
    x.inc(10); y.dec(4); x.dec(1)
    x.merge(y); y.merge(x)
    print("PN-Counter:  ", x.value(), y.value(), x.state())

    # Randomised check of the three laws on G-Counters.
    rng = random.Random(1)

    def rand_counter() -> GCounter:
        return GCounter("Z", {r: rng.randrange(6) for r in "ABC"})

    def join(p: GCounter, q: GCounter) -> GCounter:
        out = GCounter("Z", p.slots)
        out.merge(q)
        return out

    comm = assoc = idem = True
    for _ in range(1000):
        p, q, r = rand_counter(), rand_counter(), rand_counter()
        comm &= join(p, q).state() == join(q, p).state()
        assoc &= join(join(p, q), r).state() == join(p, join(q, r)).state()
        idem &= join(p, p).state() == p.state()
    print("commutative:", comm, " associative:", assoc, " idempotent:", idem)

The last line is the randomised check of the three laws on 1,000 random states. It is not a proof, but it is the kind of property test you should write for any CRDT you implement.

Registers: last-writer-wins and multi-value

A register holds one value that replicas can overwrite. The LWW-Register tags each write with a timestamp (and the replica id as tiebreaker) and merge keeps the larger tag. It satisfies all three laws, so it converges. What it does not do is keep your data: concurrent writes are resolved by whichever has the bigger timestamp, and the loser vanishes. Worse, the timestamp is a wall clock: if a replica's clock is behind, its genuinely newer write can lose to an older one. (This is exactly what happens in systems that resolve conflicts by timestamp: it is documented behaviour of Cassandra's cell-level conflict resolution, for example. See chapter 7 for clocks that fix some of this: a hybrid logical clock keeps the order consistent with causality, though two truly concurrent writes still have a loser.)

The MV-Register ("multi-value") refuses to choose. Each write carries a version vector summarising what the writer had seen; on merge, a value is discarded only if another value's vector dominates it (that write had seen it). Writes that are genuinely concurrent are both kept, as "siblings", until a later write that has seen both supersedes them. That is the Dynamo-style behaviour from the case study, now with a proof of convergence.

"""Registers: last-writer-wins and multi-value."""
from __future__ import annotations


class LWWRegister:
    """Keeps the write with the largest (timestamp, replica id). Ties broken by id."""
    def __init__(self, rid: str):
        self.rid, self.stamp, self.val = rid, (0, ""), None

    def set(self, val, wall_clock: int) -> None:
        self.stamp, self.val = (wall_clock, self.rid), val

    def merge(self, other: "LWWRegister") -> None:
        if other.stamp > self.stamp:
            self.stamp, self.val = other.stamp, other.val


class MVRegister:
    """Keeps every concurrent write. Each value carries a version vector."""
    def __init__(self, rid: str):
        self.rid = rid
        self.entries: list[tuple[dict[str, int], object]] = []   # (vector, value)

    @staticmethod
    def _le(a: dict, b: dict) -> bool:                  # a happened-before-or-equals b
        return all(b.get(k, 0) >= v for k, v in a.items())

    def set(self, val) -> None:
        vv: dict[str, int] = {}
        for v, _ in self.entries:                       # supersede everything we have seen
            for k, n in v.items():
                vv[k] = max(vv.get(k, 0), n)
        vv[self.rid] = vv.get(self.rid, 0) + 1
        self.entries = [(vv, val)]

    def merge(self, other: "MVRegister") -> None:
        pool = self.entries + other.entries
        keep = []
        for v, x in pool:
            dominated = any(v != w and self._le(v, w) for w, _ in pool)
            if not dominated and (v, x) not in keep:
                keep.append((v, x))
        self.entries = keep

    def values(self) -> list:
        return sorted(x for _, x in self.entries)


if __name__ == "__main__":
    print("-- LWW with honest clocks")
    a, b = LWWRegister("A"), LWWRegister("B")
    a.set("draft", wall_clock=100)
    b.set("final", wall_clock=105)            # B really wrote later
    a.merge(b); b.merge(a)
    print("A:", a.val, " B:", b.val)

    print("-- LWW when B's clock is 60 s slow")
    a, b = LWWRegister("A"), LWWRegister("B")
    a.set("draft", wall_clock=100)
    b.set("final", wall_clock=105 - 60)       # B wrote later, but its clock says 45
    a.merge(b); b.merge(a)
    print("A:", a.val, " B:", b.val, "  <- the newer write silently lost")

    print("-- MV-Register keeps concurrent writes")
    a, b = MVRegister("A"), MVRegister("B")
    a.set("draft"); b.set("final")
    a.merge(b); b.merge(a)
    print("A:", a.values(), " B:", b.values())
    a.set("merged by hand")                    # a later write that has seen both
    b.merge(a)
    print("after a write that saw both:", b.values())

Look at the middle experiment. B's write really was later in real time, but B's clock was 60 seconds slow, so its timestamp (45) loses to A's (100) on both replicas, consistently. Convergence held; correctness did not. When a register's value matters, use an MV-Register and surface the conflict, or use a clock that respects causality and accept that concurrent writes still lose one side.

Sets: G-Set, 2P-Set and OR-Set

Sets are where the design questions get interesting, because removing an element is not monotonic.

  • A G-Set only grows (join = union). Safe and trivial, but you cannot remove anything.
  • A 2P-Set ("two-phase") keeps an add-set and a remove-set (tombstones); an element is present if it is in the first and not the second. Both sets only grow, so it merges cleanly. The cost is a rule you may not like: once removed, an element can never be added again, because its tombstone is forever.
  • The OR-Set ("observed-remove") fixes that. Every add creates a fresh unique tag, and a remove deletes only the tags the remover has actually observed. An element is present if at least one of its tags is not removed. So a concurrent add (a new tag the remover never saw) survives the remove: the semantics are add wins over a concurrent remove. Re-adding after a remove works too, because the new add has a new tag.
"""Sets: grow-only, two-phase and observed-remove."""
from __future__ import annotations
import itertools
import random


class GSet:
    def __init__(self): self.items: set = set()
    def add(self, x): self.items.add(x)
    def merge(self, o: "GSet"): self.items |= o.items
    def value(self): return set(self.items)


class TwoPSet:
    """Add set + remove set (tombstones). A removed element can never come back."""
    def __init__(self): self.added: set = set(); self.removed: set = set()
    def add(self, x): self.added.add(x)
    def remove(self, x):
        if x in self.added: self.removed.add(x)
    def merge(self, o: "TwoPSet"):
        self.added |= o.added; self.removed |= o.removed
    def value(self): return self.added - self.removed


class ORSet:
    """Every add creates a unique tag; remove deletes only the tags it has *observed*."""
    def __init__(self, rid: str):
        self.rid, self.n = rid, 0
        self.adds: set[tuple] = set()      # (element, tag)
        self.tombs: set[tuple] = set()     # tags that were observed and removed

    def add(self, x):
        self.n += 1
        self.adds.add((x, f"{self.rid}{self.n}"))

    def remove(self, x):
        self.tombs |= {(e, t) for e, t in self.adds if e == x}   # only what I can see

    def merge(self, o: "ORSet"):
        self.adds |= o.adds; self.tombs |= o.tombs

    def value(self):
        return {e for e, t in self.adds if (e, t) not in self.tombs}

    def state(self):
        return (frozenset(self.adds), frozenset(self.tombs))


if __name__ == "__main__":
    print("-- 2P-Set: remove is forever")
    s = TwoPSet(); s.add("milk"); s.remove("milk"); s.add("milk")
    print("re-added milk present?", "milk" in s.value())

    print("-- OR-Set: concurrent add and remove, add wins")
    a, b = ORSet("A"), ORSet("B")
    a.add("milk"); b.merge(a)                  # both replicas know about milk (tag A1)
    b.remove("milk")                           # B removes the tag it saw
    a.add("milk")                              # A, concurrently, adds again (tag A2)
    a.merge(b); b.merge(a)
    print("A:", a.value(), " B:", b.value(), " tags:", sorted(t for _, t in a.adds))

    print("-- OR-Set: remove after seeing everything really removes")
    a.remove("milk"); b.merge(a)
    print("A:", a.value(), " B:", b.value())

    # Convergence under arbitrary merge order: 3 replicas, random ops, random gossip.
    def trial(seed: int) -> bool:
        rng = random.Random(seed)
        reps = [ORSet(r) for r in "ABC"]
        for _ in range(30):
            r = rng.choice(reps)
            x = rng.choice("xyz")
            rng.choice([r.add, r.add, r.remove])(x)
            if rng.random() < 0.3:
                src, dst = rng.sample(reps, 2)
                dst.merge(src)
        for _ in range(2):                              # final anti-entropy, random order
            for src, dst in rng.sample(list(itertools.permutations(reps, 2)), 6):
                dst.merge(src)
        return len({r.state() for r in reps}) == 1
    print("200 random runs converged:", sum(trial(s) for s in range(200)), "/ 200")

The OR-Set demo is the one to understand. A adds milk (tag A1) and B receives it. B removes milk: it tombstones A1, the only tag it has seen. Meanwhile A, without hearing from B, adds milk again as tag A2. After merging, A2 is not tombstoned, so milk is present on both replicas. B's remove did exactly what B meant ("remove the milk I could see") and A's add did exactly what A meant. The last test runs 200 random 3-replica histories with random merge schedules and checks that all replicas end in an identical state each time.

Common misconception: "a CRDT makes my data correct"

A CRDT guarantees convergence: everyone ends up with the same thing. It does not guarantee that the thing satisfies your application's rules. Two replicas can each decrement a PN-Counter holding 1 to 0 and the merged value is −1; two users can each claim the same username in an OR-Set of names and both claims survive. Uniqueness, "balance never negative" and similar invariants need some coordination (or an escrow trick), which is the subject of chapter 16. CRDTs decide how to merge, not whether the merge is acceptable.

Sequence CRDTs: collaborative text

Text is the hard case, and the commercially important one. Represent a document as an array of characters and an edit as "insert 'x' at index 5". If Alice inserts at 5 while Bob concurrently deletes the character at index 3, Alice's index 5 now points at a different character on Bob's machine. Indexes are positions in one particular version; they do not mean the same thing on every replica.

The CRDT fix is to give every character a permanent identity and to define order in terms of identities, not positions. Two families:

  • Linked-structure approaches. RGA (Roh et al., "Replicated abstract data type") and the Yjs algorithm (YATA, Nicolaescu et al.) record, for each inserted character, which character it was inserted after. Concurrent insertions after the same character are put in a deterministic order (for example by a timestamp and replica id). Deletion marks a character as a tombstone rather than removing it, because other replicas may still refer to it.
  • Dense-identifier approaches. Logoot (Weiss, Urso, Molli) and LSEQ give every character a position identifier from a dense, totally ordered space (think of numbers like 1.5, or 1.25: you can always find one strictly between any two). To insert between characters with identifiers 1 and 2, create one in between. Replicas sort characters by identifier, so the order is the same everywhere.

Real libraries build on these ideas: Automerge (a JSON-like document CRDT, based on the work of Kleppmann and Beresford) and Yjs (YATA) are the best-known open-source examples, and both also handle maps, lists and rich-text structure, not only a string.

That woven result, "Hi_fboaor", is the interleaving anomaly. Convergence still holds: every replica shows the same garbled text. It is a failure of intention preservation, not of consistency. Kleppmann and colleagues catalogued such anomalies in published algorithms (PaPoC 2019), proposed a specification that rules the anomaly out (text typed consecutively by one user stays together), and showed how to repair a lesser variant in one algorithm. Two other practical costs are worth knowing. First, per-character metadata (identifiers, tombstones) can dwarf the text itself, so libraries use run-length compaction and compact encodings. Second, deleted characters linger as tombstones until they can be garbage-collected, which brings us to the last section.

OT versus CRDT

Operational transformation (OT), invented for collaborative editing (Ellis and Gibbs, 1989), takes the opposite approach. Operations keep their index-based form, but when a replica receives a concurrent operation it first transforms it against the operations it has already applied: if Bob deleted a character before index 5, Alice's "insert at 5" becomes "insert at 4". Google Docs is the famous OT system.

The difference is where the difficulty lives:

  • With a central server, OT is manageable. The server picks one total order for operations, so each client only has to transform against the server's sequence, which needs a simpler correctness condition on the transformation functions. This is why production OT systems are built around a central server.
  • Without a central server, OT is hard. Peer-to-peer OT needs transformation functions that remain correct for any three or more concurrent operations arriving in different orders. That condition is subtle, and published decentralised algorithms were repeatedly found to have counterexamples. Many practitioners regard the complexity as a reason to avoid it.
  • CRDTs make convergence a property of the data structure, so they work peer-to-peer and offline with no server in the middle (the server, if present, is an optimisation). The costs are per-element metadata, tombstones and, as we saw, algorithm choices that affect how user intent is preserved.

The two are not mutually exclusive, and real products mix them with pragmatism. Figma's multiplayer engine, for instance, runs a central server and resolves conflicts per property with last-writer-wins; the team describes it as inspired by CRDTs rather than being one. That is a deliberate trade: with a server in the loop, they can use simpler merge rules where the data model allows. Read it in Figma's Multiplayer Engine, and see the design exercise in Studio 2: Design a Collaborative Editor.

Garbage collection of tombstones

Every structure above got the ability to delete by remembering that a deletion happened: a tombstone in a 2P-Set or OR-Set, a deleted character in a text CRDT. Without it, a replica that has not yet heard about the delete would send the element back at the next merge and resurrect it. But tombstones accumulate forever: a document that has been edited for years carries every character anyone ever deleted.

You can remove a tombstone only when you know no replica can still send or hold the thing it refers to. The standard notion is causal stability: a delete is stable once every replica has acknowledged it (for example when all version vectors have advanced past it). Once stable, its tombstone, and the element behind it, can be dropped. Notice the irony: garbage collection needs knowledge of the whole group, which is a kind of coordination, in a data type whose point was to need none. Real systems handle this in a few ways:

  • Track membership and acknowledgements and collect when stable. Correct, but a replica that is gone for good (a lost phone) blocks collection unless it is removed from the group, which needs a membership decision.
  • Time-based collection. Cassandra's tombstones are removed after a configurable grace period (gc_grace_seconds, ten days by default). This is cheap and needs no acknowledgements, but it is a bet: a replica that was offline for longer than the grace period and then returns can resurrect deleted data.
  • Snapshots and compaction. Periodically agree (this one is coordination) on a snapshot and discard history before it; libraries such as Yjs and Automerge also compress their operation history and merge adjacent edits.
  • Reduce metadata by design: reuse tags, use compact version vectors with dots, or choose a type where removal is naturally unneeded.
Go deeper (optional): the CRDT design checklist advanced

When you design or choose a CRDT, ask in order: (1) What are the concurrent-update semantics I want ("add wins", "remove wins", "keep both")? Two CRDTs of the same type can differ. (2) Is the state a semilattice, and are updates monotonic? Test commutativity, associativity and idempotence with random states, as the counters listing does. (3) What does the metadata cost grow with: number of replicas, number of operations, number of deletions? (4) How will tombstones and per-replica slots be garbage-collected, and what does that require from membership? (5) Which of my invariants are not covered? Those need coordination or compensation.

Distributed systems connection

CRDTs are the data-structure answer to the CAP trade-off: they choose availability and offer a strong consistency level that is compatible with it, strong eventual consistency (and, with care about delivery order, causal consistency, chapter 6). They are the right tool when replicas must work independently (offline clients, active-active regions: chapter 18) and the data can be shaped so that merging is meaningful. They are the wrong tool for invariants that span replicas, which is exactly the next chapter's question: which invariants can be kept without coordination, and which can't?

Key takeaways

  • Strong eventual consistency: replicas that have received the same set of updates are in the same state, with no consensus, no rollback and full availability.
  • The mathematics: a join semilattice. The merge (join, the least upper bound) must be commutative, associative and idempotent, and updates must be monotonic. Each law answers a network behaviour: reordering, regrouping, duplication.
  • State-based CRDTs ship states and need only eventual delivery; operation-based ship operations and need exactly-once, causally ordered delivery; delta-state CRDTs ship small joinable deltas.
  • G-Counter: one slot per replica, merge by max. PN-Counter: two G-Counters. LWW-Register converges but silently drops writes and depends on clocks; the MV-Register keeps concurrent writes; the OR-Set gives "add wins" by tagging each add and removing only observed tags; 2P-Sets can never re-add.
  • Collaborative text uses identities for characters, not indexes (RGA, Yjs, Logoot, Automerge). Concurrent typing can interleave in some algorithms: convergence is guaranteed, intent is not.
  • OT transforms index-based operations and is practical with a central server; decentralised OT is notoriously hard. CRDTs work peer-to-peer at the price of metadata.
  • Tombstones must be garbage-collected, which needs causal stability, a grace-period gamble, or snapshots. CRDTs do not protect invariants such as uniqueness or non-negative balances.

Check your understanding

Which property of the merge function makes a CRDT tolerate the same message being delivered twice?

  1. Commutativity
  2. Idempotence
  3. Associativity
  4. Monotonicity of the clock
Idempotence (a ⊔ a = a) means re-merging something already merged changes nothing. Commutativity absorbs reordering and associativity absorbs different groupings. Merging counters by adding values is a classic non-idempotent mistake: a duplicate delivery counts twice.

Replicas A and B each increment a shared counter from 5 to 6 while partitioned. If the counter is a single integer merged with max, what is the result, and how does the G-Counter avoid the problem?

  1. 7, because max adds the increments
  2. 6, and the G-Counter avoids it by using timestamps
  3. 5, and the G-Counter avoids it with a lock
  4. 6 (one increment is lost); the G-Counter keeps a separate slot per replica, so the merged value is the sum of each replica's own count
Max of two equal 6s is 6, so one increment disappears. With one slot per replica (A: +1, B: +1) the merged slots are A=1, B=1 and the sum is 7. Each replica writes only its own slot, so merging slots by max never discards anyone's increments.

In an OR-Set, replica A removes an element it can see while replica B concurrently adds the same element. After merging, what happens and why?

  1. The element is present: B's add created a new unique tag that A's remove never observed, so it was not tombstoned
  2. The element is absent, because removes always win
  3. Whichever operation has the later wall-clock timestamp wins
  4. The merge is undefined and needs a coordinator
Remove deletes only the tags it has observed. B's concurrent add has a fresh tag, so the element survives: "add wins". The behaviour comes from the unique tags, not from timestamps. A 2P-Set, by contrast, would let the tombstone win and permanently ban the element.

Why can last-writer-wins lose a genuinely newer update even though replicas always converge?

  1. Because merge is not commutative
  2. Because the network drops the newer write
  3. Because ordering depends on wall-clock timestamps; a replica with a slow clock stamps its newer write with an older time, and the larger timestamp wins on every replica
  4. Because LWW registers cannot be merged more than once
Convergence only requires a deterministic winner, and the larger (timestamp, id) pair provides one. But "larger timestamp" is not "later in real time" when clocks are skewed, so the loser is lost on every replica. Use a register that keeps concurrent writes (MV) or a causally consistent clock where lost updates matter.

Which statement about OT and CRDTs for collaborative editing is most accurate?

  1. OT guarantees convergence by construction without any central server; CRDTs always need one
  2. OT transforms index-based operations and is practical when a central server orders them; CRDTs make convergence a property of the data structure, work peer to peer, and pay in per-character metadata and tombstones
  3. CRDTs and OT both require consensus on every keystroke
  4. OT cannot handle deletions, while CRDTs can
A central server gives OT a single order to transform against, which keeps the transformation functions simple. Fully decentralised OT needs much stricter correctness conditions on those functions and has a history of incorrect algorithms. CRDT text structures need no server at all, but carry identifiers and tombstones for every character.

Why do CRDT implementations with removal need garbage collection of tombstones, and what makes it hard?

  1. Tombstones slow down merges; collecting them is trivial since each replica can drop them whenever it likes
  2. Tombstones are only needed for text; sets never need them
  3. A tombstone must be kept until every replica has seen the delete, otherwise a late merge resurrects the element; knowing that requires membership knowledge or a time-based bet
  4. Tombstones break idempotence and must be removed after each merge
The tombstone is what remembers the deletion. Drop it too early and a replica that still holds the old element will reintroduce it. Dropping it safely needs causal stability (all replicas have acknowledged), or a grace period such as Cassandra's gc_grace_seconds, with the risk that a long-offline replica resurrects data.

Start Here

The networking course ended with a toy Raft and a promise: there is a lot more underneath this. This course is that more. We make the models of time and failure precise, learn what has been proved impossible, and then study how real systems get agreement, consistency and transactions anyway: with failure detectors, leases, Paxos, Raft in depth, atomic commit and CRDTs. We finish with how engineers find the bugs that appear once in a billion runs.

A note from your mentor

Distributed systems have a reputation for being hard, and it is earned, but not because the algorithms are long. Raft fits on one page. The difficulty is that the situations are hard to imagine: a message that arrives after the sender has given up on it, a server that was frozen for 20 seconds and does not know it, two halves of a data centre that each think the other is dead. Experts are not smarter. They have trained themselves to ask, at every step, "and what if this message is lost, late, duplicated, or this node stalls right here?". This course is that training, with a precise vocabulary, a handful of famous impossibility results to calibrate your instincts, and simulators where you can make those bad days happen on demand.

Why this matters

Almost every system you will design professionally is distributed: a database with replicas, a service behind a load balancer, a queue, a cache cluster, a payment flow across three companies. The failure modes in this course (split brain, stale reads, lost updates after a failover, a lock held by two clients at once) are the ones behind real outages and real data loss. Senior system-design interviews, and senior engineering judgement in general, turn on being able to say exactly which guarantee a design provides, which failure breaks it, and what it costs to do better. After this course you can say those things with proofs and pictures, not slogans.

What is still hard

Part 6 gave you slogans and mechanisms. A slogan is useful until a design review asks you to defend it. Here are six questions a careful colleague could ask that the earlier courses do not yet let you answer. Each is a section of this course.

  1. "What exactly does 'consistent' mean here?" You know a ladder with a few rungs. We will define each rung as a property of a history of operations, so you can check a claim against a trace, not argue it from adjectives. Part 2
  2. "How do you know that node is dead, and what happens when you are wrong?" A heartbeat timeout is a guess. What are the right questions to ask about a guess, and how do real systems (Cassandra, Consul, Kubernetes) make it good enough? Part 1, chapter 3
  3. "Is the thing you are asking for even possible?" Some requirements are not hard but provably unachievable. A good engineer recognises them early and renegotiates. Part 1, chapter 2
  4. "Why does Paxos need two phases, and why does Raft refuse to count old-term entries?" For each step of a consensus protocol we will remove it and construct the execution that breaks. Part 3
  5. "How do you update two shards atomically?" Without a single machine's transaction manager, atomic commit blocks, or it needs consensus, or it needs clever clocks. We will see all three designs. Part 4
  6. "How would you even test that?" The bugs live in interleavings that happen once a month in production. We end with the tools that find them first: history checkers, fault injection, deterministic simulation and a specification language. Part 6

A first space-time diagram

The single most useful drawing in this field is the space-time diagram. Every machine gets a horizontal line (its own timeline, with time running to the right); every message is an arrow from a point on the sender's line to a point on the receiver's line. Because messages take time, arrows slope. Because a message can be lost, some arrows end in a red x. Reading these quickly is a skill, and the whole course uses them, so step through this one now. It tells a story from networking chapter 16: a write whose reply is lost.

Step through

Reading a space-time diagram

  1. Two machines, two timelines. The client (green) and the server (purple) each have a horizontal line. Positions left to right are that machine's own notion of "earlier" and "later". There is no meaningful vertical alignment: the diagram does not claim that two points at the same x happened "at the same time".
  2. A message is a slanted arrow. The client sends put x=1. The arrow leaves the client's line at the moment of sending and lands on the server's line at the moment of arrival. The steeper the slope, the faster the delivery. The server applies the write (yellow dot).
  3. The reply is lost. The server answers ok, but the arrow stops at a red x: the packet was dropped somewhere. From the client's side, nothing at all happens.
  4. The client waits, then gives up. The orange bar is the client's timeout. When it expires the client knows only that no reply arrived. Was the request lost? The reply? Is the server dead? All three look identical from here (the "slow or dead?" problem of networking chapter 16).
  5. A retry. The client resends the same request. This one arrives, and so does the reply.
  6. The cost. The server has now applied put x=1 twice. For "set x to 1" that is harmless (it is idempotent); for "add 1 to the balance" it is a bug. Every distributed protocol is, in the end, a disciplined answer to this picture.

Analogy: a committee that only communicates by unreliable post

Picture a committee whose members live in different towns and can talk only by posting letters. Letters can be lost, can arrive days late and out of order, and members can fall asleep for an unknown length of time. Nobody can phone to check. A member who sent a proposal and hears nothing cannot tell whether the letter was lost, the recipient is asleep, or the recipient replied and that letter was lost. And yet the committee must reach decisions that all members will eventually agree on, and never contradict a decision already made.

We will return to this committee throughout the course. It is the setting of the consensus problem, and it is exactly the model that Paxos was originally told as a story about (a parliament on a Greek island whose legislators wander in and out of the chamber).

Where it breaks down: a committee member who wakes from a nap knows they napped. A computer process frozen by a garbage-collection pause or a virtual-machine migration resumes mid-sentence, with no sense that time passed, and acts on beliefs that are now stale. Chapter 4 is about that difference.

How the labs run whole clusters in one process

To understand a protocol you need to watch it survive (or fail to survive) specific bad days: this message lost, that node frozen, the network split in two. On a real cluster those days are rare, unrepeatable and expensive to cause. So every lab in this course uses deterministic simulation: the whole "cluster" lives inside one ordinary Python process, and the three things that make a real cluster unpredictable are replaced by controlled stand-ins.

  • Time is a number the simulator owns. There is no sleep; an event "10 seconds from now" is just an entry in a priority queue. A simulated minute runs in microseconds.
  • The network is a function in the simulator. Sending a message puts it in the queue with a random delay, or drops it, duplicates it, or holds it back if a partition is active.
  • Randomness comes from one seeded generator (random.Random(seed)). Same seed, same run, byte for byte.

Here is the whole idea in about thirty lines. A client pings a server once a second over a link that loses 20% of messages; the code runs the experiment under different seeds and fingerprints each trace.

import hashlib, heapq, random

class Sim:
    """A whole cluster in one process: simulated time, one message queue, one seeded RNG."""
    def __init__(self, seed: int, loss: float = 0.2):
        self.rng, self.loss = random.Random(seed), loss
        self.now, self.queue, self.seq, self.trace = 0.0, [], 0, []
        self.nodes = {}
    def send(self, src, dst, msg):
        if self.rng.random() < self.loss:
            self.trace.append(f"{self.now:6.2f} {src}->{dst} {msg} LOST"); return
        self._at(self.now + self.rng.uniform(0.01, 0.2), lambda: self.deliver(src, dst, msg))
    def _at(self, t, fn):
        self.seq += 1; heapq.heappush(self.queue, (t, self.seq, fn))   # seq breaks ties deterministically
    def deliver(self, src, dst, msg):
        self.trace.append(f"{self.now:6.2f} {src}->{dst} {msg}")
        self.nodes[dst](src, msg)
    def run(self, until: float):
        while self.queue and self.queue[0][0] <= until:
            self.now, _, fn = heapq.heappop(self.queue); fn()

def experiment(seed: int) -> Sim:
    sim = Sim(seed)
    sim.nodes["server"] = lambda src, m: sim.send("server", src, "pong")
    sim.nodes["client"] = lambda src, m: None
    for i in range(5):                                  # the client pings once per simulated second
        sim._at(float(i), lambda i=i: sim.send("client", "server", f"ping{i}"))
    sim.run(until=10)
    return sim

for seed in (1, 1, 2):
    s = experiment(seed)
    digest = hashlib.sha256("\n".join(s.trace).encode()).hexdigest()[:10]
    print(f"seed {seed}: {len(s.trace)} events, trace fingerprint {digest}")
print()
print("\n".join(experiment(1).trace))

Seed 1 gives the same eight events both times (same fingerprint), and seed 2 gives a different history. If a lab's test fails on seed 1713, you can rerun seed 1713 as often as you like, add print statements, and the failure will happen again at the same step. That one property, every bug is replayable, is what lets the later chapters hunt for bugs that would take months to catch on real machines. Chapter 19 and the FoundationDB case study show the idea scaled up to an industrial database.

Go deeper: what simulation can and cannot tell you optional

A simulator checks your protocol against your model of the world: if the model has no clock-skew bug or no disk corruption, the simulation cannot find a bug in that corner. It also checks your code, not the compiler or the kernel. So simulation complements, not replaces, tests on real machines (chapter 19) and formal specification (chapter 20). Another subtlety is the tie-breaking counter in the queue above: two events with the same timestamp must be ordered the same way every run, or "deterministic" quietly stops being true.

Common misconception

"More machines means more reliable." It depends entirely on how the machines are used. If a request needs all of 100 machines to be up and each is up 99.9% of the time, the request succeeds only about 0.999100 ≈ 90.5% of the time. Redundancy helps only when the design lets the system keep going without a failed machine, which is what replication and consensus are for. A system with many machines can be far less available than one machine, until you pay for the coordination that tolerates their failures.

Key takeaways

  • This course builds on networking Part 6 and goes deeper: precise models, impossibility results, and the protocols that work anyway.
  • Distributed systems are hard because of partial failure and unbounded delay: a silent peer might be slow, dead, partitioned or paused, and you cannot tell which.
  • Space-time diagrams (one line per machine, slanted arrows for messages, red x for losses) are the lingua franca of the field; most explanations in this course use them.
  • The committee that communicates by unreliable post is our running analogy: lost, late and reordered letters, and members who fall asleep without knowing it.
  • Labs run entire clusters in one process with simulated time, a simulated network and a seeded random generator, so every failure is replayable from its seed.
  • Redundancy does not automatically give reliability; it does only if the design can tolerate the failure of a part.

Check your understanding

In a space-time diagram, what does a slanted arrow between two horizontal lines represent?

  1. Two machines agreeing on the current time
  2. A message sent at one point on the sender's timeline and received later on the receiver's timeline
  3. A machine copying its disk to another machine
  4. A clock being synchronised
The arrow begins at the sender's line when the message is sent and ends on the receiver's line when it arrives. The slope reflects the delay. Points at the same horizontal position on different lines do not mean "at the same moment": machines have no shared clock.

A client sends a request and receives no reply before its timeout. Which statement is the most accurate?

  1. The server is down
  2. The request was lost in the network
  3. The server processed the request, but the reply was lost
  4. Any of these may be true, and the client cannot tell which from the silence alone
This is the "slow or dead?" problem. A lost request, a lost reply, a crashed server and a very slow server all produce the same observation: nothing arrives. That is why retries need idempotency, and why failure detectors can only suspect.

Why does the labs' simulator use a single seeded random generator and a priority queue of events, rather than real threads and sockets?

  1. So that every run with the same seed is identical, and any failure can be replayed exactly
  2. Because Python cannot open sockets
  3. Because real networks never lose messages, so loss must be simulated
  4. To make the code run slower and easier to read
Determinism is the point. A failure that needs a particular message to be lost at a particular moment is hard to catch on a real network, but in the simulator it is just a seed you can replay and debug. Real networks do lose messages; the simulator makes the loss controllable.

A request needs all 100 servers to be up. Each is up 99.9% of the time, independently. Roughly how often does the request succeed?

  1. 99.9%
  2. About 99%
  3. About 90%
  4. About 50%
0.999 multiplied by itself 100 times is about 0.905. Needing every component multiplies the failure chances. Replication with a quorum has the opposite shape: it needs only a majority, so it survives individual failures.

Kafka's Exactly-Once Semantics

Kafka 0.11 (2017) added what its authors call exactly-once semantics. The name starts arguments, so this page is careful about the scope: two mechanisms (an idempotent producer and multi-partition transactions) plus a consumer isolation level combine to make a read-process-write loop inside Kafka happen once. They do not make a payment API, an email or a database outside Kafka happen once.

The pattern in one sentence

You cannot make a network deliver exactly once, but you can make the receiver recognise repeats (idempotence) and make a group of writes succeed or fail together (transactions), then be precise about which systems that covers.

The cast

This page states what the sources say; where I add a general explanation it is labelled. You met the delivery-semantics ladder in networking chapter 16, and the Kafka log in chapter 17; this case looks at the actual protocol. Atomic commit as a general problem is in chapter 13.

Producer id (PID)
An identifier the broker assigns to each producer instance when it initialises. Applications do not see it.
Sequence number
A counter the producer keeps per partition, starting at zero and rising by one per message. Together with the PID it identifies a message for de-duplication.
Producer epoch
A number that accompanies the PID. A request with a stale epoch is rejected, which is how an old instance is fenced off.
transactional.id
A stable name the application gives its producer so that transactional state survives restarts.
Transaction coordinator and transaction log
A component inside the broker that tracks each transaction, and an internal replicated Kafka topic where it records state, so the state inherits Kafka's durability.
Transaction marker (control message)
A special record written into a data partition saying COMMIT or ABORT for a given PID. Clients process it but never hand it to applications.
Last stable offset (LSO)
The offset below which every transaction has finished. A read_committed consumer does not read beyond it.

The problem it solves

KIP-98 starts from Kafka's baseline: at-least-once delivery, so a producer that retries after a timeout can create duplicates. Its motivation was to add idempotent production (no duplicates or loss within a producer session) and transactions (atomic writes across several partitions, and atomic consume-transform-produce), with Kafka Streams exactly-once processing as the main driver. The Confluent post that announced the feature, by Neha Narkhede and colleagues, titled it "Exactly-once semantics are possible"; the argument underneath is that the phrase is only fair if you say what it covers.

Layer one: the idempotent producer

With enable.idempotence=true, each producer gets a PID, numbers its messages per partition, and the broker keeps the last sequence number it accepted for each PID and partition. KIP-98 describes three outcomes: a sequence number lower than expected is a duplicate, which the producer can ignore; the expected number is appended; a higher one means something was lost, which is a fatal error. The Confluent post compares this to TCP, with one difference it stresses: the sequence numbers are persisted in the replicated log, so a new leader after failover still recognises a resend.

Two limits are stated in KIP-98. Idempotence holds only within one session of one producer, because a restarted producer gets a new PID. And the original design forced the producer to one in-flight request per connection when idempotence was on; the Confluent benchmarks mention up to five, so I do not claim the current rule here. The Confluent post reports the overhead as a few extra numeric fields per batch with negligible throughput impact.

The toy below is mine. It shows the broker-side check and, further down, the marker-and-isolation idea. It is not Kafka's code, and it ignores replication, epochs and batches.

"""Toy broker: idempotent append by (producer id, sequence), then transaction markers and read_committed (not Kafka's code)."""
class Partition:
    def __init__(self): self.log, self.last_seq = [], {}      # log entries: (kind, pid, value)
    def append(self, pid, seq, value):
        last = self.last_seq.get(pid, -1)
        if seq <= last: return "duplicate (ignored)"
        if seq > last + 1: return "out of order (error)"
        self.last_seq[pid] = seq; self.log.append(("data", pid, value)); return "appended"
    def marker(self, pid, kind): self.log.append((kind, pid, None))
    def read(self, committed_only):
        done = {p: k for k, p, _ in self.log if k in ("COMMIT", "ABORT")}
        out = []
        for kind, pid, v in self.log:
            if kind != "data": continue
            if committed_only and done.get(pid) != "COMMIT": continue
            out.append(v)
        return out

p = Partition()
print("send seq0:", p.append("P1", 0, "a"))
print("retry seq0 (ack was lost):", p.append("P1", 0, "a"))
print("send seq1:", p.append("P1", 1, "b"))
print("skip to seq3:", p.append("P1", 3, "d"))
print("log so far:", p.log)
print("read_uncommitted:", p.read(False), "| read_committed (no marker yet):", p.read(True))
p.marker("P1", "COMMIT")
print("after COMMIT marker, read_committed:", p.read(True))
q = Partition(); q.append("P2", 0, "x"); q.marker("P2", "ABORT")
print("aborted txn: uncommitted sees", q.read(False), "committed sees", q.read(True))

Output when run:

retry seq0 (ack was lost): duplicate (ignored)
send seq1: appended
skip to seq3: out of order (error)
log so far: [('data', 'P1', 'a'), ('data', 'P1', 'b')]
read_uncommitted: ['a', 'b'] | read_committed (no marker yet): []
after COMMIT marker, read_committed: ['a', 'b']
aborted txn: uncommitted sees ['x'] committed sees []

Layer two: transactions

To survive restarts the application sets a transactional.id. KIP-98 says Kafka guarantees exactly one active producer for each such id: a new instance bumps the epoch, so older ones (zombies, in the post's word for a producer that seems dead but is only paused or partitioned) are rejected with a fencing error. When a new instance calls initTransactions(), any transaction the old one left unfinished is completed or aborted first.

The flow in KIP-98, as I read it:

  1. The producer finds its coordinator, which hands it a PID and bumps the epoch, recovering any unfinished transaction.
  2. The first write to each partition registers that partition with the coordinator, which also starts a timer (default 60 s in the KIP; an idle transaction is aborted).
  3. Data is produced with PID, epoch and sequence numbers. Consumer offsets can be added to the same transaction, written to the offsets topic but invisible until commit.
  4. On commit or abort, the coordinator first writes PREPARE_COMMIT (or PREPARE_ABORT) to the transaction log. That is the decision point.
  5. It then sends marker-write requests to the leader of each partition involved, each of which appends a COMMIT or ABORT marker.
  6. Finally it writes COMMITTED (or ABORTED) to the transaction log.

Why this is two-phase commit, and why it blocks less

(General analysis, mine.) Step 4 is a decision logged before it is applied, and steps 5 and 6 apply it to every participant, which is the shape you studied in chapter 13. The difference is that the participants are not independent databases that can vote no: the partitions have already accepted the data, and the coordinator's state is itself a replicated log that a new coordinator leader can read, so a coordinator crash does not leave the decision lost. The price is waiting: readers stop at the last stable offset until markers land.

Layer three: what consumers see

Consumers choose an isolation level. The default read_uncommitted returns everything in offset order, including data from transactions that later abort. read_committed returns non-transactional messages and committed transactional ones. KIP-98 describes how: the fetch response carries the last stable offset and a list of aborted transactions, which lets the consumer discard aborted data without waiting for the marker, and it never reads past the LSO.

KIP-98 is open about a gap on the consumer side. A committed transaction may not be consumed all at once, because of log compaction, deleted old segments, seeks into the middle of a transaction, or consumers that are not subscribed to every partition in it. The write is atomic; the read is not guaranteed to see all of it together.

What is not covered

The Confluent post is direct about this. Exactly-once covers consuming from Kafka, reading and writing state in Kafka topics, and producing output to Kafka, when you use Kafka Streams. It does not cover side effects such as calls to remote stores, custom clients that read or write topics directly, or non-deterministic logic (for example a lookup to an external service whose answer changes), where results fall within a set of legal outputs without being one exact result. Rewinding offsets cannot roll back an external system, so non-idempotent updates there can be wrong. With the plain consumer API the application must keep its own state consistent with its committed offsets.

The Kafka documentation, in its section on message delivery semantics, makes the same point from the other side: exactly-once delivery to other systems needs those systems' cooperation, and a common approach is to store the consumer's offset in the same place as the output, because many destinations do not support two-phase commit.

Common misconception: "Kafka guarantees my email is sent once"

If the consumer sends an email and then the transaction aborts or the process crashes before offsets commit, the input is processed again and a second email is sent. Fix it with the same tool as always: an idempotency key at the destination (chapter 17, exactly-once with external sinks), or an outbox pattern as in architecture chapter 15.

What it costs

The Confluent post reports, for its benchmark with 1 KB messages and 100 ms transactions, about 3% lower producer throughput than an acks=all baseline with one in-flight request, and about 20% lower than the default configuration at the time; for Kafka Streams with a 100 ms commit interval, 15 to 30% lower throughput depending on message size, and no measurable overhead for large messages with a 30 s commit interval. It says write amplification per transaction is constant, so larger transactions cost less per message but raise end-to-end latency for read_committed readers. These are the post's numbers for its setup; I did not rerun them.

The pattern to remember

Analogy: the post office and the numbered forms

Each letter you send carries your customer number and a running letter number. If the counter clerk has already filed number 5 from you, a second copy is stapled away unseen. For a multi-letter application, the clerk first writes "decision: send all" in a ledger, then stamps every letter in every folder with APPROVED or WITHDRAWN. Readers who only trust stamped letters skip anything not yet stamped.

Where it breaks down: the stamps work inside this post office. If a letter's contents cause a bank transfer elsewhere, no stamp can pull that back.

Key takeaways

  • Idempotence: PID plus per-partition sequence numbers stored in the replicated log let the broker drop retried duplicates, within one producer session.
  • Transactions add a stable transactional.id, epoch fencing of zombies, a coordinator with a replicated transaction log, and COMMIT/ABORT markers written to every partition involved.
  • read_committed hides aborted and undecided data and reads only up to the last stable offset.
  • The guarantee is read-process-write inside Kafka. External side effects need idempotent destinations or offsets stored with the output.
  • Exactly-once here is a precise claim about a closed system, not a property of the network.

Check your understanding

What lets a Kafka broker drop a retried message?

  1. A hash of the message body
  2. The producer id plus a per-partition sequence number, remembered by the broker
  3. The consumer's offset
  4. A timestamp on each message
If the sequence number is not higher than the last one accepted for that PID and partition, it is a duplicate.

Why does a transactional producer need transactional.id?

  1. To pick a topic
  2. So its identity and epoch survive restarts and an older zombie instance can be fenced
  3. To compress messages
  4. To enable acks=0
A restarted producer would otherwise get a new PID, and idempotence would only hold within one session.

Which are written into each partition when a transaction ends?

  1. Nothing; the coordinator keeps all state
  2. COMMIT or ABORT markers, after the coordinator logs its decision
  3. A copy of the transaction log
  4. The consumer offsets only
The coordinator logs PREPARE_COMMIT or PREPARE_ABORT first, then writes markers to the partition leaders, then logs the final state.

A read_committed consumer sees a partition whose first open transaction starts at offset 5. Where does it stop reading?

  1. At the high watermark
  2. At the last stable offset, before offset 5
  3. At the log end
  4. It waits for compaction
The last stable offset is the first offset of a still-open transaction.

Your consumer reads from Kafka and calls a payment API. What does Kafka's exactly-once cover?

  1. The payment call
  2. Only the Kafka reads and writes; the payment call needs its own idempotency key
  3. Nothing at all
  4. Everything if acks=all
The Confluent post lists RPCs to remote stores as outside the guarantee.

The Redlock Debate

In 2016 a researcher and the author of an algorithm argued in public about whether five Redis nodes can give you a lock that is safe. Neither side is foolish. They disagree about what timing a lock may assume, and about what the lock is for. That makes this a clean place to practise one skill: finding the assumption under a claim of safety.

The pattern in one sentence

A lock that expires by itself is safe only while its timing assumptions hold, so for correctness you either make the protected resource check a token or choose a coordination system whose safety does not depend on timing at all.

The cast

You met the underlying problem in chapter 4 (a lock is a belief about the past) and the timing models in chapter 1 (synchronous, partially synchronous and asynchronous). This case reads three documents: the Redis documentation page on distributed locks, Martin Kleppmann's critique How to do distributed locking (8 February 2016), and Salvatore Sanfilippo's (antirez) reply Is Redlock safe? (2016). I present each side as it states itself, and I label my own comments as such.

Redlock
A lock algorithm proposed on the Redis website, which the page says is meant to be safer than a single-instance lock. It runs over N independent Redis masters (examples use N=5) with no replication between them.
Lock validity time
The key's TTL, which is both its automatic release time and the window the client has to do its work before another client may take the lock.
Efficiency lock and correctness lock
Kleppmann's two uses. An efficiency lock avoids duplicate work, so a failure costs a little (a duplicate email). A correctness lock prevents concurrent access that would corrupt data permanently.
Fencing token
A number that increases each time the lock is granted, which the protected resource checks so that it refuses a lower one. See chapter 4; Chubby calls it a sequencer (case 1).
Monotonic clock
A clock that never goes backwards or jumps when an administrator or time daemon adjusts the wall clock. It measures elapsed time. Wall-clock time can step.

What Redlock is

The Redis page starts with the one-instance lock. To take it, a client sends SET resource_name my_random_value NX PX 30000: set the key only if it does not exist, with an expiry of 30,000 ms. The value must be unique across clients. To release it safely, the client runs a script (or, on the newest Redis, DELEX with an if-equal condition) that deletes the key only if its value is still the client's own. Using plain DEL would be unsafe, because a slow client might delete a lock that another client now holds.

The page then says why a master with a replica is not enough: replication is asynchronous, so a lock written to the master can be lost if the master crashes before the replica sees it, and the promoted replica lets a second client take the lock. Hence Redlock. The client:

  1. reads the current time in milliseconds;
  2. tries to take the lock on all N instances (in parallel in the ideal case), using the same key and value, with a per-node timeout that is small compared with the lock's lifetime;
  3. computes the elapsed time, and counts the lock as acquired only if it holds a majority (at least 3 of 5) and the elapsed time is less than the validity time;
  4. takes the validity time as the TTL minus the elapsed time;
  5. if it failed, unlocks all instances, including ones it believed it did not lock.

The safety argument on the page: the first key to expire is guaranteed to live for at least MIN_VALIDITY = TTL - (T2 - T1) - CLOCK_DRIFT. During that interval a majority of keys exists, so no other client can obtain a majority. A client that took too long to lock a majority sees the time and treats the lock as invalid. Liveness rests on keys expiring, on clients cooperatively removing partial locks, and on randomised retry delays. The page admits an availability penalty of up to one TTL during network partitions.

The page also states its assumption about time: the processes need no synchronised clock, but the local time in each must advance at approximately the same rate, with a small error compared with the lock's lifetime. It cites the leases paper, as chapter 4 does. For crashes, it says an instance that restarts should stay unavailable for at least a bit more than the maximum TTL ("delayed restarts"), so that it no longer takes part in any lock that was active when it crashed; this is how it argues for safety even without persistence, at an availability cost. (At the time of my fetch, the page also carried a disclaimer pointing to the two posts below, recommended fencing tokens, and noted that Redis does not use a monotonic clock for TTL expiration, so a wall-clock shift could let more than one process hold the lock.)

Kleppmann's critique

Kleppmann begins by asking what the lock is for. For an efficiency lock, he says, a single Redis instance, even with asynchronous replication, is enough and Redlock's cost is wasted. For a correctness lock he argues Redlock is unsuitable, for two reasons.

1. Locks that expire cannot, alone, protect a shared resource. A client takes a lease, stalls (a stop-the-world garbage collection is his example; also page faults, slow storage, a SIGSTOP, or arbitrarily delayed packets), and wakes up after the lease expired and another client holds the lock. Checking the expiry just before the write does not help, because a pause can occur between the check and the write. His remedy is a fencing token on every write, with the storage rejecting lower tokens. He notes that ZooKeeper's zxid or a znode version could serve as the token, and that Redlock has nothing monotonic: its random value does not increase, and generating a counter would itself need a consensus algorithm.

2. Redlock's safety depends on timing. He contrasts algorithms for the asynchronous model, whose safety needs no timing assumptions (timing only affects liveness), with Redlock, which he argues is correct only in a synchronous model: bounded network delay, bounded process pauses and bounded clock error. Datacentres, he says, are partially synchronous: timing holds most of the time, and for correctness "most of the time" is not enough. Two scenarios follow. In the first, a clock jump on one node makes its key expire early (his five-node example is the one in the diagram below, and the Redis page notes that Redis uses wall-clock time for expiry). In the second, a client sends lock requests and then pauses; the locks expire everywhere, a second client acquires them, and the first wakes up with replies that were buffered while it slept. He adds that delayed restarts also rely on accurate timekeeping.

His recommendations: use the single-node lock and document that it is approximate when the lock is for efficiency; use a consensus-backed system such as ZooKeeper (with a mature recipe library) or a database with strong transactions when it is for correctness, and enforce fencing tokens either way.

Antirez's reply

The reply opens by agreeing that the analysis is valuable and by conceding a point: Redlock should use the operating system's monotonic clock, and he said he would implement it. He disputes the broader conclusion. His main points, as I read them:

  • On tokens. Strong locks matter mostly where the resource has no other control; if it can itself reject stale writes in order, an incrementing id from any lock service would do and a lock would be needed less. He says Redlock can instead issue a large random token (20 bytes from /dev/urandom in the spec): set the resource's state to the token and perform the read-modify-write only if it is unchanged at write time, a check-and-set. He adds that, because of pauses, the order in which clients acquire the lock need not match the order in which they act, so increasing tokens may not capture causality, and that many locked resources (physical objects, external APIs) cannot be updated transactionally.
  • On clocks. Redlock needs relative time, not absolute: processes that count elapsed time at roughly the same rate, within a bounded error. He calls manual clock changes by administrators a configuration error, comparable to corrupting a Raft log, and says time daemons should slew the clock rather than step it. He notes that models depending on GPS bring their own partition risks.
  • On delays and pauses. His reading of the algorithm is that delays between the first clock read and the second (steps 1 to 3 on the page) are accounted for, since elapsed time is subtracted from the validity window, so Redlock does not depend on bounded message delay and he cannot see how the example race occurs. A pause after the check, he concedes, is a real problem but affects every auto-release lock, and the remedies are checking the remaining validity and tokens. He explicitly asks for clarification in case he is missing something.
  • On crashes. Fsync on every operation is optional, because delayed restarts avoid the disk entirely, which he says allows very high lock rates.

He ends by asking for more expert review and for testing with Jepsen or similar tools.

Here is the clock-jump scenario as a runnable toy model of the algorithm described on the Redis page (my code, a simplification).

"""Redlock-style acquisition over 5 nodes with per-node clocks (toy model of the algorithm described on the Redis page)."""
TTL = 10.0
class Node:
    def __init__(self, name): self.name, self.key, self.expire, self.offset = name, None, 0.0, 0.0
    def now(self, real): return real + self.offset            # this node's wall clock
    def set_nx(self, real, val):
        if self.key is not None and self.now(real) < self.expire: return False
        self.key, self.expire = val, self.now(real) + TTL
        return True
    def present(self, real, val): return self.key == val and self.now(real) < self.expire

def acquire(nodes, real_start, val, latency=0.1):
    got = sum(n.set_nx(real_start + latency, val) for n in nodes)
    elapsed = 2 * latency
    return got >= 3 and elapsed < TTL, TTL - elapsed          # (acquired?, validity time)

def scenario(clock_jump: float):
    nodes = [Node(c) for c in "ABCDE"]
    ok1, v1 = acquire(nodes[0:3], 0.0, "client1")             # client 1 reaches A,B,C only (D,E slow/unreachable)
    print(f"  client 1: acquired={ok1}, validity={v1:.1f}s")
    nodes[2].offset = clock_jump                              # node C's clock steps forward at real t=3
    ok2, v2 = acquire([nodes[2], nodes[3], nodes[4]], 4.0, "client2")   # client 2 reaches C,D,E at real t=4
    print(f"  client 2: acquired={ok2}" + (f", validity={v2:.1f}s" if ok2 else ""))
    print("  both think they hold the lock at real t=5:", ok1 and ok2)

print("C's clock steps forward 8 s (e.g. NTP step or manual change):"); scenario(8.0)
print("no clock step:");                                             scenario(0.0)

Output when run:

C's clock steps forward 8 s (e.g. NTP step or manual change):
  client 1: acquired=True, validity=9.8s
  client 2: acquired=True, validity=9.8s
  both think they hold the lock at real t=5: True
no clock step:
  client 1: acquired=True, validity=9.8s
  client 2: acquired=False
  both think they hold the lock at real t=5: False

The model gets the result because the validity check uses each node's own clock for its key expiry. Which side you find convincing depends on whether you accept that a jump of that size is outside the system you promise to run in.

What the debate teaches

My reading (general, not from the posts)

The two sides agree on more than the tone suggests: use monotonic clocks; an expired lease plus a paused holder is a real hazard for any auto-release lock; and a resource that can check something should do so. What remains is a question about models. Kleppmann asks what happens if timing assumptions fail and wants safety to survive that (chapter 1's asynchronous or partially synchronous model). Antirez assumes a bounded relative clock error and designs liveness and safety around it (a synchronous-ish model). Neither is incoherent; they choose different contracts. The practical upshot: if you can make the protected resource enforce a token, you do not need the five-node apparatus; if you cannot, no timed lock gives you more than its timing assumption.

Common misconception: "more nodes means correct"

Five nodes remove the single point of failure and the asynchronous-replication race of the master-plus-replica design, which is what the Redis page sets out to fix. They do not, by themselves, remove the dependence on clocks and pauses that both posts discuss. Case 4 shows a consensus-backed store, etcd, whose own locks had the same lease-expiry gap.

The pattern to remember

Analogy: the library book and the deli ticket

A lease is a due date: you may use the book until then. Redlock argues about how to make sure that nobody else is handed the book before the date. Kleppmann's point is that the shelf (the resource) should also check your ticket number, because you can fall asleep with the book open on your desk past the due date.

Where it breaks down: a library clerk can look at a wall clock everyone trusts. In a distributed system every clock is a private opinion.

Key takeaways

  • Ask what the lock is for. Efficiency locks may tolerate a rare double-hold; correctness locks may not.
  • Redlock's safety, as documented, rests on a bound on clock-rate error and on the client noticing elapsed time; Kleppmann argues that is a synchronous-model assumption; antirez argues it is a mild one.
  • Both agree that a pause after the final check can outlive the lock, and that a monotonic clock should be used.
  • The disagreement about tokens is real: monotonic fencing tokens (Kleppmann) versus random token with compare-and-set (antirez).
  • Whatever you pick, state the timing assumptions out loud and test them.

Check your understanding

Which statement do BOTH Kleppmann and antirez accept?

  1. Five Redis nodes make a lock safe against any pause
  2. Redis should use a monotonic clock for expiry, and a pause after the final time check can outlive the lock
  3. Fencing tokens must be increasing integers
  4. Lock expiry never matters in practice
Antirez concedes the monotonic clock point and that a pause after the check is a problem for every auto-release lock. They differ on tokens and on the earlier scenarios.

What does Kleppmann say about Redlock's timing assumptions?

  1. It needs no timing assumptions for safety
  2. Its safety depends on bounded network delay, bounded pauses and bounded clock error, which is the synchronous model
  3. It only needs synchronised atomic clocks
  4. It needs a leader
He contrasts it with consensus algorithms whose safety does not depend on timing; for them timing only affects liveness.

What is antirez's alternative to increasing fencing tokens?

  1. No tokens at all
  2. A random token set as the resource's state, with the read-modify-write done only if the token is unchanged (check-and-set)
  3. A GPS clock
  4. A second Redis replica
He argues a unique id serves the same purpose without requiring the store to be linearizable, and that increasing tokens may not reflect the order of work.

In the clock-jump scenario, why can two clients both believe they hold the lock?

  1. Redis nodes cannot count to three
  2. One node's key expires early after its clock jumps, so a second client can gather a majority while the first is still within its validity window
  3. Both clients wrote to the same node
  4. The TTL was infinite
Majorities intersect only if keys live as long as assumed. A forward clock jump breaks that for one node.

Jepsen Tests etcd

In 2019 and early 2020 Kyle Kingsbury, of Jepsen, tested etcd 3.4.3 for the Cloud Native Computing Foundation. etcd is the Raft-based store under Kubernetes. The result is an unusually clean example of what independent testing gives you: strong evidence for some claims, a documentation correction for others, and a plain statement that one feature does not do what people assume.

The pattern in one sentence

Treat every consistency claim as a hypothesis, test it by recording what clients actually saw and checking the history, and keep the claims you can test apart from those you cannot.

The cast

This page states only what the Jepsen report says. Where I add a general explanation, it is labelled. The background is in chapter 19 (testing distributed systems), chapter 5 (consistency models, including linearizability checking) and chapter 11 (etcd in the coordination-services picture).

Jepsen
A framework by Kyle Kingsbury that runs a real database on several machines, injects faults, records every client operation, and checks the recorded history against a model.
Knossos
The checker the report uses to test whether a history of register operations is linearizable. For multi-key transactions the tests look for cycles in a dependency graph, as evidence against strict serializability.
Strict serializable
Transactions behave as if executed one at a time in an order that respects real time. The report concludes that etcd's key-value operations are strict serializable by default.
Linearizable read vs serializable read
In etcd, reads are linearizable by default; an optional serializable flag downgrades a read so it may return stale committed state. The report says this is as documented.
Lease and lock
An etcd lease is a time-to-live that can be attached to keys. The lock API builds on a lease: the lock key disappears when the lease expires.
Revision
etcd's global, monotonic counter of changes. Watches can start from a given revision.

What was tested

The report covers etcd 3.4.3, the latest release as of October 2019, on five-node Debian Stretch clusters, published on 30 January 2020 with funding from the Cloud Native Computing Foundation. The faults included partitions of single nodes, majority/minority splits, non-transitive partitions with overlapping majorities, random and leader-targeted crashes and pauses, clock skew of up to hundreds of seconds, and random membership changes. The workloads were registers, sets, multi-key appends (checked for dependency-graph cycles), locks, and watches.

Key-value operations: strict serializable

The headline for the core store is good. Across the tests, including pauses, crashes, clock skew, partitions and membership changes, the report found etcd's key-value operations to be strict serializable. Reads are linearizable by default. The report notes that pairing the weaker serializable flag with a read lets it see stale committed state, which is what the flag is documented to allow.

The report is critical of etcd's documentation here, not its behaviour. It says the docs claimed that sequential consistency was the strongest guarantee available, whereas linearizability is strictly stronger and is achievable; that they described serializable isolation as the strongest, when strict serializability is stronger and also achievable; and that they defined linearizability using a loosely synchronised global clock, which the report says conflicts with the original definition of Herlihy and Wing and implies causality violations. After the collaboration, the report says, etcd's GitHub docs describe the store as strict serializable by default.

Common misconception: "serializable means strongest"

Serializable guarantees a total order of transactions but, by itself, no relation to real time. Strict serializability adds it. In etcd's vocabulary the serializable read flag is the weaker option, which can return stale data. Chapter 5 gives the map of these terms. Names that sound strong can mean weak things, which is why the report spends space on them.

Watches

The report's finding on watches over single keys is that they appear correct: every client saw the same ordered sequence of updates to a key, with no lost or reordered events, provided that history was not compacted while a watch was not running. It also reports one quirk: a watch started at revision 0 streams events starting from the current revision plus one, not from the beginning, while revision 1 returns all changes. The report calls this undocumented, unlikely to matter to most production users, and records it as issue 11496, unresolved at publication. Its advice: to watch all changes from the start, use revision 1.

The report also states what it did not test rigorously: deletes, range queries and multi-key watches.

Locks: the finding that mattered

This is the part people remember. The report says etcd's locks do not provide mutual exclusion. Multiple clients could hold the same lock at the same time, even in healthy clusters with synchronised clocks.

How the tests showed it: one test performed randomised lock and unlock requests, each acquisition under a lease kept alive by the Java client, and checked with Knossos whether the history could be a linearizable lock service. Another had five processes update an in-memory set under an etcd lock: each read the set, waited about a second, and wrote back the set plus a new element. With two-second leases and process pauses every five seconds, the report says about 18% of acknowledged updates were lost. With one-, two- and three-second TTLs, mutual exclusion generally failed within a few minutes even without any injected fault.

The report identifies one concrete bug and one inherent limit.

  • Bug. When a client was waiting for a lock, lost its lease, and the lock was then released, the server did not recheck that the waiting client's lease was still valid before telling it that it held the lock. Issue 11456 was fixed on master but not released at publication; the report expects locking problems to be somewhat reduced when it ships.
  • Inherent limit. The report cites Kleppmann's analysis (our case 3): in an asynchronous system a distributed lock has to trade away correctness to keep liveness, because a slow or unreachable process is not necessarily dead and may still act as holder. Tuning TTLs and adding lease checks reduces how often it goes wrong without eliminating it.

The report's safer patterns:

  • Fencing tokens. The lock key's revision is monotonic, so it can serve as a fencing token that the protected resource checks and uses to reject operations from older holders. The report describes this recommendation and does not test it.
  • Lock-guarded transactions. A transaction that checks that the lock key's version is above zero prevented writes after the lock was lost, in the tests where the data lived in etcd and the update was a single transaction. It does not make multi-operation updates atomic.

The toy model below is mine, written to show the shape of these two mitigations; it is not etcd's code and its numbers are invented.

"""A toy lease-backed lock (etcd-like shape, not etcd's code): why the lock alone cannot protect an outside resource."""
class Etcdish:
    def __init__(self): self.rev, self.kv, self.leases = 0, {}, {}     # kv: key -> (value, create_rev)
    def tick(self, now):
        for lease, exp in list(self.leases.items()):
            if now >= exp:                                    # lease expired -> its keys vanish
                del self.leases[lease]
                for k in [k for k, (v, r) in self.kv.items() if v == lease]: del self.kv[k]; self.rev += 1
    def lock(self, now, who, ttl):
        self.tick(now)
        if "/lock" in self.kv: return None
        self.rev += 1; self.kv["/lock"] = (who, self.rev); self.leases[who] = now + ttl
        return self.rev                                       # the lock key's revision: monotonic across holders
    def guarded_put(self, now, who, key, val):                # txn: if lock key still exists and is mine, then put
        self.tick(now)
        if self.kv.get("/lock", (None,))[0] != who: return False
        self.rev += 1; self.kv[key] = (val, self.rev); return True

class Resource:                                               # lives OUTSIDE etcd
    def __init__(self): self.data, self.newest = [], 0
    def write(self, who, val): self.data.append((who, val))
    def write_fenced(self, token, who, val):
        if token < self.newest: return False
        self.newest = token; self.data.append((who, val)); return True

e, r = Etcdish(), Resource()
t1 = e.lock(0.0, "P1", ttl=2.0)
# P1 pauses for 5 s here; lease expires at t=2
t2 = e.lock(3.0, "P2", ttl=10.0)
print("tokens (lock key revision): P1 =", t1, " P2 =", t2)
r.write("P2", "update-from-P2")
r.write("P1", "stale-update-from-P1")                         # P1 wakes up at t=5 and writes
print("unprotected outside resource :", r.data, "<- P1 overwrote P2's work")
r2 = Resource()
r2.write_fenced(t2, "P2", "update-from-P2")
print("fenced write by P1           :", r2.write_fenced(t1, "P1", "stale-update-from-P1"), r2.data)
ok2 = e.guarded_put(3.5, "P2", "/cfg", "y")
ok1 = e.guarded_put(5.0, "P1", "/cfg", "x")
print("lock-guarded put inside etcd  : P2 ->", ok2, "| P1 (woke at t=5) ->", ok1)

Output when run:

tokens (lock key revision): P1 = 1  P2 = 3
unprotected outside resource : [('P2', 'update-from-P2'), ('P1', 'stale-update-from-P1')] <- P1 overwrote P2's work
fenced write by P1           : False [('P2', 'update-from-P2')]
lock-guarded put inside etcd  : P2 -> True | P1 (woke at t=5) -> False

The report's recommendations: use etcd locks to improve performance, not to guarantee safety; if safety matters, make the protected resource enforce it, using fencing tokens such as the lock key's revision; start watches at revision 1 when you want everything; and document that locks do not guarantee mutual exclusion, with fencing examples in place of examples that can lose updates.

What the report cannot tell you

The report says plainly that Jepsen can demonstrate bugs but cannot prove their absence. It does not cover disk corruption or other single-node Byzantine faults. So "strict serializable in every test" means that under the specified faults and workloads, no violation was found. That is strong, and different from a proof. (General point: chapter 20 is about the other way to gain confidence.)

The pattern to remember

Analogy: the restaurant inspector

An independent inspector who orders the dishes, cuts the power mid-service, and writes down what arrived at which table can say "your kitchen's orders are always delivered in sequence" and also "your 'reserved' signs do not stop two parties sitting at one table". Both statements are useful, and neither needs access to the recipe.

Where it breaks down: an inspector sees a sample of evenings. A Jepsen run, similarly, finds what it provokes.

Key takeaways

  • etcd's key-value operations were found strict serializable in every test; reads are linearizable by default, and the serializable flag allows stale reads.
  • Single-key watches delivered ordered updates; the one quirk was watching from revision 0.
  • etcd locks did not give mutual exclusion; in the tests about 18% of acknowledged updates were lost under pauses with short TTLs.
  • Make the resource check a fencing token such as the lock key's revision; do not rely on the lock alone.
  • Documentation claims were corrected as part of the work: testing improves words as well as code.

Formal Methods at AWS

Starting in 2011, engineers at Amazon Web Services began writing precise specifications of their most delicate designs in TLA+ and letting a model checker explore every interleaving of events. The write-up by Newcombe, Rath, Zhang, Munteanu, Brooker and Deardeuff is short on mathematics and long on evidence: ten large systems, subtle bugs that reviews and testing missed, and engineers learning the language in a few weeks.

The pattern in one sentence

Write the design as something a machine can explore, state what must be true in every reachable state, and let the machine search the interleavings your intuition cannot imagine.

The cast

This page paraphrases the AWS authors' account. A note on the text I read: I read the earlier technical report of the same name from Lamport's site, dated 29 September 2014, and checked its key facts against the 2015 CACM article (April 2015, vol. 58 no. 4), which has the same authors and the same material. Where the wording differs in a way that matters, the page says so. Explanations I add are labelled. Background: chapter 20 (TLA+, model checking, a model checker in thirty lines) and chapter 19 (testing).

TLA+
A specification language by Leslie Lamport based on simple discrete mathematics. A specification describes the set of all legal behaviours (execution traces) of a system. The same language states the correctness properties and the design.
PlusCal
A second language, closer to a C-style programming language, that translates to TLA+ with a keystroke. The report says several engineers were more productive in it.
TLC model checker
A tool that takes a TLA+ specification and exhaustively checks properties across all possible execution traces.
Safety and liveness
Safety: what the system is allowed to do (the report's example: at no time has the system lost or corrupted committed data). Liveness: what it must eventually do (every request eventually gets a response).

Why they did it

The report says AWS already used deep design reviews, code reviews, static analysis, stress testing and fault injection, and still found that subtle bugs can hide in complex concurrent fault-tolerant systems. Its reasons: human intuition is poor at estimating how likely supposedly extremely rare combinations of events are at a scale of millions of requests per second; and some of the most dangerous bugs are design bugs, where code faithfully implements a design that mishandles a rare scenario. The authors say testing the code is inadequate for finding such errors because the number of reachable states is astronomical.

They wanted a precise description of a design in a few hundred lines, expressive enough for concurrency and failure, simple to learn, and with existing tooling. The report describes how one author came to TLA+: initial doubts that formal methods suit real systems were eased by Pamela Zave's use of Alloy to find bugs in the Chord membership protocol, then by finding a TLA+ specification in the appendix of a Paxos paper and by the DEC/Compaq use of TLA+ on cache-coherence protocols. Alloy was judged not expressive enough for their data structures.

What they specified and what they found

By the time of the report, they had used TLA+ on 10 large, complex real-world systems, with 7 teams using it. In their words, in every case it either found subtle bugs they were sure they would not have found otherwise, or gave enough understanding to make aggressive performance optimisations safely. The DynamoDB story

The report presents DynamoDB (launched January 2012) as the first big success. Its replication and fault-tolerance mechanisms had already been through fault-injection testing with a simulated network layer that controlled message loss, duplication and reordering, long stress tests on real hardware, and detailed informal proofs, which did find several bugs in early versions. The engineer who wrote them then learned TLA+ and wrote a detailed specification in a couple of weeks. The distributed version of TLC ran on a cluster of ten large EC2 instances. It verified a small complicated part of the algorithm, then, checking the broader fault-tolerant algorithm, found a bug that could lose data if a particular sequence of failures and recovery steps was interleaved with other processing. The shortest error trace that exhibited it had 35 high-level steps.

The report's comment on that number is the lesson: the improbability of such compound events is no defence, because AWS has historically observed combinations at least as complicated. The bug had passed unnoticed through extensive design reviews, code reviews and testing, and the engineer was convinced more work in those areas would not have found it. The checker later found two more serious, subtle bugs, all were fixed and re-verified, and a later data-migration feature was added to the same specification, where the checker showed the first design would have introduced a bug. The engineer believed the TLA+ route was both more reliable and less time-consuming than writing and checking his informal proofs.

The toy below is mine. It is a thirty-line cousin of the idea: enumerate every interleaving of two clients doing read-then-write on a counter and report the shortest sequence that violates the invariant. It is far smaller than the report's example and not related to the DynamoDB bug, whose details the report does not give.

"""A tiny explicit-state model checker: all interleavings of two read-modify-write clients, check an invariant (toy, not TLC)."""
from collections import deque
# state: (counter, (pc1, tmp1), (pc2, tmp2)); each client: read, then write tmp+1
def steps(s):
    c, *cl = s
    for i in (0, 1):
        pc, tmp = cl[i]
        if pc == 0:   n = list(cl); n[i] = (1, c); yield (f"client{i+1} reads {c}", (c, *n))
        elif pc == 1: n = list(cl); n[i] = (2, tmp); yield (f"client{i+1} writes {tmp+1}", (tmp + 1, *n))
init = (0, (0, 0), (0, 0))
seen, q, found = {init: None}, deque([init]), None
while q:
    s = q.popleft()
    done = s[1][0] == 2 and s[2][0] == 2
    if done and s[0] != 2: found = s; break           # invariant: after both finish, counter == 2
    for label, t in steps(s):
        if t not in seen: seen[t] = (s, label); q.append(t)
path = []
while seen[found]: p, l = seen[found]; path.append(l); found = p
print("states explored:", len(seen)); print("shortest violating trace:"); [print(" ", i + 1, l) for i, l in enumerate(reversed(path))]

Engineers learning TLA+

The report says engineers from entry level to Principal learned TLA+ from scratch and got useful results in two to three weeks, in some cases in their own time and without help or training. Its account of how adoption spread is practical:

  • They called the introductory talk "Debugging Designs" and described TLA+ as "exhaustively testable pseudo-code", avoiding the words formal, verification and proof at first.
  • An S3 team asked for help after the talk. They had been considering writing a Java program to brute-force explore executions of a state-machine design, which is a hand-built model checker. One author wrote two versions of the spec over a couple of weeks (finding PlusCal more productive for it), found two subtle bugs, verified the fixes, and used the spec to test new features and optimisations.
  • Another engineer spent two weeks learning TLA+ and wrote the first spec for an algorithm with a known subtle bug; TLC found the bug in seconds. The team had already designed a fix; the spec showed the problem still occurred through a different trace, and a stronger fix was then verified.
  • Specs of two different styles written independently for the same algorithm found the same critical bug, which the authors read as evidence that the benefit does not depend on the individual.
  • A working practice: write the prose design first, then incrementally refine parts of it into PlusCal or TLA+; even partial specs often give insight.

"What needs to go right?"

The report contrasts two ways of designing. The usual way starts with the happy path and then asks what might go wrong, stopping well short of rare combinations. The formal way starts by stating what must go right: the safety and liveness properties, an abstract design, an explicit statement of the environment the system relies on (for example, that a channel which has not failed propagates messages), and the effects of every possible environment event such as network errors, disk errors, process crashes, data-centre failures and operator actions. The model checker then verifies the design against the properties despite any combination or interleaving of those events. The authors say this is significantly less error-prone than the ad hoc approach. They also note that a precise model is a what-if tool for deciding whether a change is safe and is good documentation.

Limits the authors state

  • Code is not verified. They do not know of tools that verify distributed implementations of this size against a specification. Their answer is that getting the design right is a necessary first step, improves understanding, and helps engineers find stronger invariants for their assertions.
  • Emergent performance problems. Specification suits logic bugs and operator errors, not sustained slowdowns caused by feedback loops, such as a slow server causing timeouts, which cause retries, which add load. Such a system keeps making progress yet is effectively unavailable, and the authors did not know a feasible way to model it.
  • You only check what you state. The lock-manager row above shows a liveness bug missed because liveness was not checked.

Common misconception: "formal methods means proving the program correct"

In this report it means model checking a specification of the design, at a chosen level of abstraction, within the sizes TLC can handle: a sufficiently large instance of the system, not all sizes. It raises confidence and finds bugs; it does not certify the code. Chapter 20 draws the same line.

The pattern to remember

Analogy: the architect's scale model

An architect tests a building by building a small precise model and shaking it on a table that can reproduce every kind of earthquake. Finding a crack in the model is cheap. The model does not prove the finished building was built to the plan, but a flawed plan could never have been built right.

Where it breaks down: the shaking table only reproduces the earthquakes you described, and cannot tell you how the building will feel to live in during a long slow tremor, the report's emergent performance problems.

Key takeaways

  • AWS used TLA+ and PlusCal on S3, DynamoDB, EBS and an internal lock manager, among ten large systems.
  • A DynamoDB design bug needed a 35-step trace; reviews, tests and informal proofs missed it.
  • Engineers learned TLA+ in two to three weeks; the first spec for a known bug found it in seconds.
  • Write what must go right (properties plus environment), not only what might go wrong.
  • Specs verify designs, not code, and do not catch feedback-loop slowdowns; unchecked properties (like liveness) are not checked.

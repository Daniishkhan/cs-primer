Figma's Multiplayer Engine

When many people edit one Figma file at once, whose change wins? Evan Wallace's 2019 post explains the answer: a central server decides the order of changes, each property of each object is a last-writer-wins register, and a few special rules handle the tree structure and the ordering of children. Figma called this CRDT-inspired and was explicit that it is not a pure CRDT, because having an authority lets it throw away machinery that a fully peer-to-peer design needs.

The pattern in one sentence

If you have a central server you can trust to order events, you can replace heavyweight convergence machinery with simple rules, such as one value per property and the server's order breaking ties, and you only need to think hard about the few structures (trees, sequences) where simple rules break.

The cast

Operational transformation (OT)
The approach behind Google Docs: operations are transformed against concurrent ones so that everyone converges. Well suited to long runs of text.
CRDT
A data type designed so that replicas converge without a central authority, whatever order updates arrive in.
Last-writer-wins (LWW) register
A single value where the most recent write replaces the others.
Property, object
In Figma's model, a document is a tree of objects; each object has an id and a set of named properties (position, fill and so on).
Fractional index
A position expressed as a fraction between 0 and 1, so new items can be inserted between two neighbours without renumbering.

Why not OT, and why not a pure CRDT

The post says Figma looked at operational transformation and chose something else: it found OT unnecessarily complex for Figma's problem space, and the team wanted to ship quickly. The post's own explanation (my paraphrase) is that OT suits long text editing but creates a combinatorial explosion of states that is hard to reason about. Figma's documents are not long strings; they are trees of objects with properties.

On CRDTs, the post says the design is inspired by them but is not one. A CRDT guarantees eventual convergence without any central authority. Figma has an authority: each multiplayer document has its own server process, and clients connect over WebSockets. Because the server defines the order of events, the design can drop some CRDT overhead for a leaner implementation, and the data structure combines ideas from several CRDTs instead of being one textbook type. The post does not say the result is an inferior CRDT; it says the guarantees come from the server, so calling it a CRDT would claim something it does not need.

Why that is a fair distinction

(General, mine.) A CRDT's merge function must give the same result on every replica regardless of arrival order, because no replica is special. Here the arrival order at the server is the one true order, and clients converge by following it. That is closer to replicated state-machine behaviour (chapter 8) with a single sequencer than to a peer-to-peer CRDT; the cost is that the server is a single point you must keep available, and offline-first work needs extra care.

The document model and last-writer-wins

The post pictures a document as a tree of objects, like the browser DOM, and the data as a map from object id to a map from property to value. The server keeps the latest value any client sent for each property of each object. Changes to different properties, or to different objects, never conflict. Changes to the same property do: the server's order picks the winner, so no timestamps are needed. The post notes that changes are atomic per property: two users editing the same value (the example it gives is a text value) produce one winner, not a merge of the two.

Clients apply their own changes immediately, so the UI feels instant. If a value arrives from the server that conflicts with a local change the server has not yet acknowledged, the client discards the incoming value, which the post says prevents flickering between old and new.

The toy below is mine and shows only the per-property rule and a fractional index; it is not Figma's code.

"""Toy of Figma-style rules: server order decides per-property winners; fractional index for order (not Figma's code)."""
from fractions import Fraction
server = {}   # object id -> {property: value}; the server's arrival order is the only clock
def apply(obj, prop, val): server.setdefault(obj, {})[prop] = val
# Two clients edit at the same time; the server happens to receive B's edits second.
for who, obj, prop, val in [("A","r1","x",10),("B","r1","y",99),("A","r1","fill","red"),("B","r1","fill","blue")]:
    apply(obj, prop, val)
print("different properties both survive, same property -> later arrival wins:", server["r1"])

def between(lo, hi): return (lo + hi) / 2
order = {"a": Fraction(1,3), "c": Fraction(2,3)}
order["b"] = between(order["a"], order["c"])      # insert b between a and c
order["b2"] = between(order["a"], order["c"])     # a concurrent insert picks the same position
print({k: str(v) for k, v in order.items()})
print("sorted by (position, id):", [k for k, v in sorted(order.items(), key=lambda kv: (kv[1], kv[0]))])

Output when run:

different properties both survive, same property -> later arrival wins: {'x': 10, 'y': 99, 'fill': 'blue'}
{'a': '1/3', 'c': '2/3', 'b': '1/2', 'b2': '1/2'}
sorted by (position, id): ['a', 'b', 'b2', 'c']

Note the last line of the output: two clients that insert at the same spot compute the same position. That is exactly the kind of case a real system must decide how to handle, and I make no claim about how Figma handles it; my toy just breaks the tie with the id.

Creating, deleting and the tree

  • Creation and deletion are explicit. Writing to an unknown id does not create an object. Whether an object exists is itself a last-writer-wins boolean, similar to a set. The server does not keep a deleted object's data; the deleting client keeps it in its undo buffer.
  • Ids. Object ids include a unique client id, so a client, even an offline one, can create objects without asking the server for an id.
  • Reparenting. A move is not delete-and-recreate; it is a write of the parent link as a property of the child. That keeps the object's identity, so concurrent edits to its other properties are not lost. The server rejects a move that would create a cycle. Before the rejection reaches them, clients can briefly see a cycle: the post says the client temporarily parents the two objects to each other and removes them from the tree, so they briefly disappear.

Ordering children: fractional indexing

An ordered list of children is where last-writer-wins on single values is awkward, because inserting at position 3 shifts every later item. The post's answer is fractional indexing: each child's position is a fraction strictly between 0 and 1, and a new item gets the average of its neighbours' positions. Only the new item is written. The post stores the parent link and the position as a single property so they change atomically.

Offline, undo, and a later post

The post says that offline edits are kept locally; when the client reconnects it downloads a fresh copy of the document, reapplies its offline edits, and opens a new connection. Multiplayer syncs only document changes. Comments, users and similar data live in Postgres with a separate sync system. For undo, the post states the design principle that undoing several steps, copying, and redoing back to the present should leave the document unchanged, and that an undo modifies the redo history at that moment (and a redo, the undo history), so that redo does not overwrite other people's later edits.

A later Figma post, "Making multiplayer more reliable", describes the durability side. Per the post, the service originally kept each open file in memory and saved a full checkpoint to S3 every 30 to 60 seconds, so a crash could lose up to a minute of work and redeploys caused a spike of checkpoint writes. Figma added a journal, a write-ahead log in DynamoDB of small incremental changes (about every half second, each with a sequence number), so that after a crash the service loads the latest checkpoint and replays newer journal entries. Details beyond this are not stated here.

The pattern to remember

Analogy: the whiteboard with a referee

Everyone scribbles on their own copy so it feels instant, but a referee at the front keeps the master board. If two people recolour the same circle, the referee's arrival order decides, and everyone's copy is corrected. Two people recolouring different circles never bother each other. Moving a box into another box is handled by the referee with a special rule so that no box ends up inside itself.

Where it breaks down: if the referee's room loses power, the copies still work but nothing is shared until it returns.

Key takeaways

  • A central server per document sets the order of changes; clients apply their own edits optimistically and drop conflicting incoming values until acknowledged.
  • Each property of each object is a last-writer-wins register; different properties never conflict.
  • Moves are parent-link writes; the server rejects cycles.
  • Child order uses fractional indexes between 0 and 1.
  • Figma calls it CRDT-inspired, not a CRDT, because the server supplies the convergence that CRDTs get from their algebra.

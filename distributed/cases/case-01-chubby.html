Chubby: Google's Lock Service

In the mid-2000s Google built a small, highly available service whose job was to let big, otherwise-unrelated systems agree on who the boss is. It offered locks, but its designers chose coarse ones, held for hours or days, and then watched developers use it most of all as a name service. This case follows the paper that described Chubby, the design choices behind it, and the candid lessons section.

The pattern in one sentence

Put the hard agreement problem in one small, replicated service, and give clients leases, change notifications and tokens that prove a lock was held when a request was made, so ordinary programs can elect a leader and publish who it is without each implementing consensus.

The cast

You met leases and fencing tokens in chapter 4 and the idea of a coordination service in chapter 11. Chubby is where much of that vocabulary was born in production. Everything below is from Burrows' OSDI 2006 paper unless marked as general.

Cell
One Chubby instance: a small set of replicas, typically five, placed to avoid correlated failures such as a shared rack. They use a consensus protocol to elect a master, and three must be running for the cell to be up. Google usually ran one cell per data centre, plus a global cell.
Master
The replica that handles all client requests. Replicas elect it with a majority of votes plus promises not to elect another for a few seconds, the master lease, which they keep renewing while the master keeps winning. Reads are answered by the master alone, which is safe while its master lease is unexpired.
Client library
The code every application links. It finds the master, keeps a cache, and runs the session protocol. All client traffic goes through it.
File and lock
Chubby looks like a small file system. Any file or directory can also be used as a reader-writer lock. Locks are advisory: holding the lock on F neither is required to read F nor stops others from doing so.
Session
The relationship between a client and a cell, kept alive by periodic KeepAlive calls. Handles, locks and cached data stay valid while the session does.
Sequencer
An opaque string a lock holder can request right after acquiring. It names the lock, the mode and the lock generation number, which increases each time the lock goes from free to held. This is the paper's name for what chapter 4 calls a fencing token.
Lock-delay
If a lock becomes free because its holder failed or became unreachable, Chubby refuses to hand it to anyone else for a configurable period (up to one minute). A cheap partial defence for servers that cannot check sequencers.

Why a lock service, and why coarse locks

The authors say plainly that they could have shipped a Paxos library instead. They argue for a service on several grounds. Teams start with prototypes that have no plan for high availability and bolt replication on later, and a lock service fits an existing program with small changes: to elect a master that writes to an existing file server, acquire a lock, pass the acquisition count with each write, and have the file server reject writes with a lower count. Services that elect a primary also need to advertise the result, so small files are included. Programmers find locks familiar, even if, the paper notes wryly, they are usually wrong about how locks behave across independent failures. And a lock service lets a client system make progress with fewer servers of its own, because the lock service's replicas supply the quorum.

The surprising choice is coarse-grained locking. The designers expected locks held for hours or days, such as one that elects a primary, not locks held for a fraction of a second around a single update. Coarse locks make the acquisition rate only weakly related to the clients' transaction rate, so the service does not need to be fast; a brief outage delays clients less often; and because transferring a coarse lock can be expensive, it is worth keeping locks alive across a master failover. Clients that need fine-grained locks can build them on top (the paper sketches a design using Chubby to hand out lock groups to application-specific lock servers). Looking back, the authors report they never needed to write such a server: developers who wanted performance found they had to remove communication, and that often meant moving to coarse locking.

The structure

Clients locate the master by asking the replicas listed in DNS, then send all requests to it until it stops responding or says it is no longer master. A write is acknowledged once a majority of replicas have it. If a replica dies for a few hours, a replacement is started from a free pool and the DNS entry is updated. The paper is explicit that it claims no new algorithms: the engineering effort was to fill a need, "not research".

Locks and sequencers

Here is the danger the paper names. A process holding lock L sends a request R, then fails or is cut off. Another process acquires L and acts. Later R arrives at its destination and is acted on without the protection of L. This is exactly the delayed-request half of the story in chapter 4, and Chubby's answer is the sequencer.

The holder asks for a sequencer and attaches it to any request that must be protected by the lock. The receiving server checks that the sequencer is still valid and has the right mode, either by asking Chubby (via its own cached state) or, if it does not want a Chubby session, by comparing with the newest sequencer it has seen. Both are cheap, and the paper stresses that only the messages that use locks need the extra string, unlike virtual-synchrony style schemes that put sequence numbers in every message.

But important protocols evolve slowly, and many servers will never be modified. For them Chubby offers lock-delay. The paper calls it imperfect: it only protects against requests that are delayed for less than the configured time. The toy model below, which is mine and not Chubby's code, runs both defences against one delayed write.

"""Sequencers and lock-delay: a toy model (not Chubby's code)."""
from dataclasses import dataclass

@dataclass(frozen=True)
class Sequencer:
    lock: str
    generation: int          # Chubby's lock generation number: bumps each time the lock goes free -> held

class LockService:
    def __init__(self, lock_delay: float):
        self.gen, self.holder, self.free_at, self.lock_delay = 0, None, 0.0, lock_delay
    def holder_failed(self, now: float):
        self.holder, self.free_at = None, now + self.lock_delay   # lock-delay starts when the holder is lost
    def acquire(self, who: str, now: float):
        if self.holder or now < self.free_at:
            return None
        self.gen += 1
        self.holder = who
        return Sequencer("/ls/cell/primary", self.gen)

class FileServer:
    def __init__(self, check: bool):
        self.check, self.newest, self.log = check, 0, []
    def write(self, now: float, who: str, seq: Sequencer) -> str:
        if self.check and seq.generation < self.newest:
            return f"t={now:>4}: {who} gen {seq.generation} REJECTED (newest seen is {self.newest})"
        self.newest = max(self.newest, seq.generation)
        self.log.append(who)
        return f"t={now:>4}: {who} gen {seq.generation} accepted"

def run(delay_arrives: float, lock_delay: float, check: bool) -> None:
    svc, fs = LockService(lock_delay), FileServer(check)
    a = svc.acquire("A", 0.0)                       # A becomes primary, sends a write that will be delayed
    svc.holder_failed(10.0)                         # A's session is lost at t=10 (partition, pause, ...)
    events = [(delay_arrives, "A-delayed-write")]
    b = None
    for t in (11.0, 16.0):                          # B keeps trying to take the lock
        b = svc.acquire("B", t)
        if b:
            events.append((t, "B-write"))
            break
    out = []
    for t, what in sorted(events):
        out.append(fs.write(t, "A" if what.startswith("A") else "B", a if what.startswith("A") else b))
    stale = "A" in fs.log and fs.log.index("A") > (fs.log.index("B") if "B" in fs.log else 99)
    print(f"  lock-delay={lock_delay:>4}, server checks sequencers={check}, A's packet arrives t={delay_arrives}")
    for line in out: print("    " + line)
    print("    ->", "STALE WRITE APPLIED AFTER NEW PRIMARY" if stale else "ok")

print("no protection:");              run(20.0, 0.0, False)
print("lock-delay only (helps if the packet is quick):"); run(12.0, 5.0, False)
print("lock-delay only (packet later than the delay):");  run(20.0, 5.0, False)
print("sequencer check (any delay):"); run(20.0, 0.0, True)

Read the output as the argument for each defence. With nothing, the stale write lands after the new primary's. Lock-delay saves you only if the old packet arrives before the new holder is allowed in. The sequencer check works for any delay, because the server remembers the newest generation, but it needs the server to participate.

Common misconception: "Chubby's lock gives mutual exclusion"

The lock gives mutual exclusion between holders, but a holder can be partitioned or paused and keep acting after it has lost the lock. Mutual exclusion over the protected resource exists only if that resource checks the sequencer. The paper presents the sequencer as the way a server can tell whether a request is still protected, and lock-delay as a mitigation for servers that cannot check.

Sessions, KeepAlives and the grace period

Each session has a lease: an interval during which the master promises not to end the session unilaterally. The master can push the end further out but never back. A client's KeepAlive call is deliberately parked at the master, which does not answer until the current lease is nearly over; the reply carries the new lease timeout (by default 12 seconds further, longer when the master is overloaded). The client sends the next KeepAlive immediately, so there is nearly always one blocked call waiting. The same reply is the channel for events and cache invalidations, which means a client cannot keep its session alive without receiving them, and also that all traffic is initiated by the client, so it works through one-way firewalls.

The client keeps a conservative local copy of the lease. It assumes the reply spent a long time in flight and that the master's clock runs fast, and the paper requires that the server's clock advance no faster than a known constant factor relative to the client's. This is the bounded-drift lease from chapter 4, in a real system. If the local lease runs out, the client is unsure whether the session lives: it empties and disables its cache, and the library tells the application the session is in jeopardy, then waits a further grace period, 45 seconds by default, for contact with a master.

When a new master is elected it does careful bookkeeping. It picks a new client epoch number that every call must carry, so it never answers a very old packet addressed to a previous master, even one on the same machine. It rebuilds sessions and locks from the replicated database, extends session leases to the maximum its predecessor might have granted, then sends every session a fail-over event so clients flush caches (they may have missed invalidations) and waits for acknowledgement before allowing other operations. A handle created before the failover is recreated on demand. The authors add, without much surprise, that this rarely exercised failover code has been a rich source of interesting bugs.

Caching with invalidation

Clients cache file data, metadata and even the absence of a file, in a consistent write-through cache. The master keeps a list of what each client may be caching. To change a file it first blocks the modification, sends invalidations on the KeepAlive channel and waits until each caching client has acknowledged or its cache lease has expired.

Only one round is needed, because while invalidations are outstanding the master treats the node as uncachable, so reads are never blocked. The protocol invalidates and never updates, because an update-only protocol can send an unbounded number of useless updates to a client that read the file once. The authors say they rejected weaker consistency in the cache because programmers would find it harder to use.

The name-service surprise

Chubby was designed as a lock service, but the paper reports that its most popular use was as a name server. The reason is caching. DNS caches by time to live (TTL): choose a long TTL and failed services are replaced slowly; choose a short one and the DNS servers are overloaded. The paper's worked example: a job of 3,000 processes that all talk to each other, with a 60-second TTL, would need about 150,000 lookups per second, against roughly 50,000 per second that the paper says a 2-CPU DNS server of the day might handle. Chubby's invalidation-based cache needs only a constant rate of KeepAlives, and one master was seen serving 90,000 clients directly. The general principle is the one from chapter 11: notification beats polling when changes are rare.

The success brought its own problems. Starting a 3,000-process job in the new scheme produced nine million requests, which could bring the master to its knees. The fixes were batching about 100 name entries per lookup, a protocol-conversion server specialised for name lookups, and a Chubby DNS server so that browsers and other unmodifiable programs could use the data. The authors admit that if they had foreseen this use they would have built full proxies sooner.

What went wrong, and what they learned

The lessons section is the reason to read the paper. The main points, paraphrased:

Developers assume it is always up

One team built a system of hundreds of machines whose recovery took tens of minutes every time Chubby elected a new master, magnifying a single failure by about a hundred times. The paper also separates a service being up from being available to your application. Many developers crashed their program on the fail-over event, which was meant to prompt a rescan, and that lowered their own availability.

Abusive clients, with no malice

Developers wrote retry loops that hammered Chubby for files that did not exist, or polled by opening and closing a file repeatedly. First the team added growing delays; in the end it was easier to make repeated opens cheap, and to cache the absence of files.

No quotas was naive

Chubby was never meant for bulk storage and had no quotas. One shared module ended up rewriting a 1.5 MB file on every user action; its service grew to use more space than all other clients combined. The team imposed a 256 KB file limit, and the migration away took about a year.

Heavyweight guarantees are the wrong tool for pub/sub

Teams tried to use events as a publish/subscribe system, which proved slow and inefficient because of the strong guarantees and invalidation rather than update. All such uses were caught before redesign became too costly.

Two more, both about transport and API. KeepAlives carry both lease renewals and invalidations, which created tension with TCP: its back-off knows nothing of Chubby's leases, so TCP-based KeepAlives lost many sessions under congestion, and the team had to send KeepAlives over UDP. And the call used to cancel long-running operations also discarded server state for the handle, which blocked sharing handles between threads. Two events, conflicting-lock and "lock acquired", were rarely used and, with hindsight, could have been omitted.

On availability, the paper reports 61 outages across 700 cell-days of data from a sample of cells. Most lasted 15 seconds or less and 52 were under 30 seconds. The nine longer outages were attributed to network maintenance (4), suspected network connectivity problems (2), software errors (2) and overload (1). Over a few dozen cell-years the team lost data six times, four from database software errors and two from operator error, none from hardware. As a name-and-coordination service it was built around the idea that applications should be designed to tolerate Chubby being briefly unreachable.

The pattern to remember

Analogy: the deli ticket and the library due date

The session lease is a library book's due date: the holder may keep using it until then, and a renewal must arrive before the date. The sequencer is the deli counter number: the person serving checks the number, not whether you claim to have waited. A lock without a sequencer check is a due date nobody at the desk looks at.

Where it breaks down: deli numbers are issued in a single queue by one machine, whereas Chubby keeps its generation numbers in the replicated database that the cell's consensus protocol maintains.

Key takeaways

  • Coarse-grained locks are cheap for the service, survive failovers, and are a natural fit for electing a primary; fine-grained locking can be layered on by clients, though the authors found they rarely needed it.
  • A lock is safe for a protected resource only if requests carry proof (the sequencer) that the resource checks. Lock-delay is a weaker fallback.
  • Parked KeepAlives carry lease renewals and invalidations on one client-initiated channel, with a conservative local lease and a grace period that hides most failovers.
  • Consistent caching with invalidation made Chubby a popular name service, by avoiding TTL guesses.
  • Most of the pain came from usage, not protocol: availability assumptions, retry loops and missing quotas.

Connect it

Distributed systems connection

  • Chapter 4 (leases and fencing tokens): the session lease with bounded drift, and the sequencer as a fencing token. The paper, however, treats a delayed request as something the application must guard against by passing the sequencer.
  • Chapter 11 (coordination services): the kernel idea, ephemeral nodes, and watches, compared with the ZooKeeper design in case 2. Chubby keeps caches consistent by blocking writes until clients invalidate; ZooKeeper's watches are one-shot notifications that never block a write.
  • Chapter 9 (Paxos): the paper says that Paxos keeps safety without timing assumptions, while clocks are added to ensure liveness, which is how it gets around the FLP result of chapter 2.
  • Chapter 3 (failure detection): KeepAlives and lease expiry are the failure detector, with all its false positives.
  • Case 3 argues about locks that lack the sequencer, and case 5 shows Percolator using a Chubby token for worker liveness.

Check your understanding

A client holds a Chubby lock, then is partitioned. Another client acquires the lock and writes to a file server. What protects the file server from the first client's delayed write?

  1. Chubby's lock, because locks are mandatory
  2. The file server checking the sequencer's generation number against the newest it has seen
  3. The first client's cache invalidation
  4. The DNS TTL
Locks are advisory. A sequencer carries the lock generation number; a server that checks it rejects the lower, stale generation. Lock-delay is only a fallback for servers that cannot check.

Why does the master park KeepAlive calls and answer them only when the lease is nearly over?

  1. To save disk space
  2. So a long-lived outstanding call is nearly always waiting, letting the reply both extend the lease and deliver events and invalidations promptly, with the client always initiating
  3. Because UDP cannot send replies immediately
  4. To prevent clients from caching
The client sends the next KeepAlive immediately after each reply. Early return carries invalidations; the normal return extends the lease, and all traffic is client-initiated.

What happens when a client's local lease expires during a master fail-over?

  1. The session ends at once
  2. It continues as if nothing happened
  3. It flushes and disables its cache, enters jeopardy, and waits up to the grace period for a new master; if contact is made in time the application sees only a delay
  4. It elects itself master
The client cannot tell whether the master expired the session, so it blocks calls and waits for the grace period (45 seconds by default).

Why did Chubby end up popular as a name service, compared to DNS?

  1. It is faster per lookup than any other service
  2. Invalidation-based caching meant developers did not have to choose a TTL: changes reach caches promptly while the steady load is just KeepAlives
  3. It stored names in a hash ring
  4. It used mandatory locks
DNS's time-based caches force a trade between slow replacement and heavy load. Chubby's cache stays valid until invalidated, so a constant KeepAlive rate sustains many cached entries.

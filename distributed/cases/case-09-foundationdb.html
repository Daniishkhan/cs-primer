FoundationDB: Simulation First

FoundationDB is an ordered, transactional key-value store with strict serializability. Its SIGMOD 2021 paper tells two stories that depend on each other. One is an architecture that splits transaction processing, logging and storage into separate roles and recovers from almost any failure by starting a new generation of the transaction system. The other is that the team built a deterministic simulator before the database itself, so that whole clusters, failures included, could be run and replayed inside one process.

The pattern in one sentence

Design the system so that every source of nondeterminism is an interface you can replace, then test the real code against a simulated world that injects more failures per second than production ever will, and replay any failure from its seed.

Unbundled database
One where the pieces a traditional database ties together (transaction processing, the log, storage) are separate services that scale independently.
Control plane / data plane
The control plane holds cluster metadata and orchestration; the data plane processes transactions and stores data.
Sequencer, proxy, resolver, log server, storage server
The roles. The sequencer assigns read and commit versions; proxies front clients and orchestrate commits; resolvers check for conflicts; log servers hold the write-ahead log; storage servers hold data and serve reads.
OCC and MVCC
Optimistic concurrency control (run first, check for conflicts at commit) combined with multi-version reads. FoundationDB achieves strict serializability this way.
Flow
A syntactic extension to C++ adding async/await-style concurrency, used so the same code can run under a real or a simulated runtime.
Buggification
The paper's name for places where the database code lets the simulator inject unusual but legal behaviour.

The architecture: unbundled, with failure as the normal case

The paper describes FoundationDB as created in 2009: an ordered key-value store with multi-key, strictly serializable transactions, with no query language or data model; richer features are built as stateless layers on top. Its control plane is a set of coordinators forming a disk Paxos group, which elect a cluster controller; the controller recruits a sequencer, a data distributor and a rate keeper. The data plane has a transaction system (sequencer, proxies, resolvers, which are stateless), a log system, and a storage system whose storage servers hold shards and, together form a distributed B-tree, with a modified SQLite as storage engine.

Two design principles stand out. First, make failure a common case: instead of handling every failure scenario in the transaction system, it shuts down when it detects a failure and starts a new one, so that all failure handling is one well-tested recovery path. Second, fail fast and recover fast: the paper says total recovery in production is usually under five seconds. It also says FoundationDB does not rely on quorums to mask failures but detects and reconfigures, so it can tolerate f failures with f+1 replicas rather than 2f+1, a design the paper says is best suited to a single local or metro-area deployment.

A transaction: optimistic concurrency with resolvers

A client obtains a read version (via a proxy, from the sequencer, guaranteed to be no less than any committed version), reads from storage servers at that version, and buffers writes locally. At commit it sends its read and write key ranges to a proxy. The proxy gets a commit version larger than any existing read or commit version from the sequencer, sends the sets to range-partitioned resolvers, and, if none finds a conflict, sends the transaction to the log servers. It is committed when all designated log servers have replied.

The resolver's rule is short: each keeps a history of recently modified key ranges with their commit versions, and a transaction is aborted if any range it read was modified at a version later than its read version. Because the commit version is assigned before conflict detection, version assignment and conflict checking can be batched. All resolvers must admit a transaction for it to commit, so a transaction admitted by only some resolvers can leave history that causes a false conflict for others; the paper says this is limited to the short MVCC window (five seconds) and has not been an issue in production, since key ranges usually fall in one resolver. OCC does not guarantee a transaction will commit; the paper reports a production conflict rate under 1% and says the client simply retries. Read-only transactions commit locally without contacting the database.

Recovery: a new generation, not a repair

The paper divides transaction processing into epochs, each with its own sequencer. If a monitored process fails or the configuration changes, the sequencer terminates, the cluster controller recruits a new one, and it runs recovery. The steps the paper gives: read the old transaction-system state from the coordinators and lock it so no one else recovers at once; stop the old log servers; recruit new proxies, resolvers and log servers; write the new state to the coordinators; accept commits. Proxies and resolvers are stateless, so the real work is in the log servers: for any transaction a proxy may have acknowledged, its log must survive.

There is no checkpoint and no redo or undo pass at recovery time, because storage servers always pull the log from log servers in the background; recovery only has to find the end of the log. The first transaction in a new epoch is a recovery transaction that tells storage servers the recovery version so they can discard anything newer, which, since the multi-versioned data is in memory, is just dropping it. A related benefit the paper notes: because the recovery path is fast and heavily tested, upgrades can restart all processes at once, usually within seconds.

Simulation: the part people remember

The paper says the team took a radical approach: before building the database, they built a deterministic simulation framework able to simulate a network of interacting processes and many disk, process, network and request-level failures, all in a single physical process. The real database software runs, together with randomised synthetic workloads and fault injection, in a deterministic discrete-event simulation. Determinism means every bug found can be reproduced.

  • Deterministic by construction. All database code is deterministic. Multithreaded concurrency is avoided; one node is deployed per core. Flow lets the same actor-style code run under production or simulated runtimes, and the production implementation is a simple shim to the system calls.
  • Oracles. Most synthetic workloads carry assertions that check the database's contracts; the FoundationDB testing page gives a "cycle test" as an example, where keys are arranged in a ring and transactions rotate it, so isolation violations break the ring. Recoverability is checked by returning the modelled hardware to a state where recovery should be possible and verifying the cluster recovers.
  • Fault injection. The simulator injects machine, rack and data-centre fail-stop failures and reboots, network faults, partitions and latency, disk behaviour such as corruption of unsynchronised writes when machines reboot, and randomised event times. The testing page adds "swizzle-clogging": clog the network connections of a random subset one by one, then unclog them in random order. The paper says injection rates are tuned so that the system is not driven into a small state space by excess faults.
  • Buggification. At many places the database code gives the simulator the chance to inject unusual but contract-respecting behaviour: an error from an operation that usually succeeds, a delay in one that is usually fast, an odd tuning parameter. This makes rare states common. (The paper's word is "buggification", and it speaks of buggification points. In the open-source code the call site is the macro BUGGIFY, with BUGGIFY_WITH_PROB(x) for an explicit probability, defined in flow/flow.h in the 6.3 and 7.1 release branches. The current main branch has moved to a buggify() function and a CLIENT_BUGGIFY macro in flow/include/flow/Buggify.h. The testing page does not mention any of these names.)
  • Swarm testing and coverage. Each run uses a random cluster size, configuration, workloads, fault parameters and a random subset of buggification points. Conditional coverage macros tell a developer how many distinct runs reached a given condition, so they can add faults or workloads until it is tested.
  • Speed. A discrete-event simulator can fast-forward the clock to the next event, so quiet stretches cost nothing, and it is embarrassingly parallel. The testing page describes the simulator as representing more real time in less simulated time, with "about a 10-1 factor of real-to-simulated time" (the page does not spell out the units), and reports tens of thousands of nightly simulations and a rough estimate of a trillion CPU-hours in total; these are the page's own figures.

The toy below is mine and is nothing like Flow in scale. It shows the shape: a seeded schedule, a simulated fault, an invariant, a failing seed, and an exact replay.

"""A tiny deterministic simulation: seed -> network schedule -> invariant check; failing seeds replay exactly (toy, not Flow)."""
import random, heapq
def run(seed, buggy=True):
    rng = random.Random(seed); q, now, trace = [], 0.0, []
    def send(t, ev): heapq.heappush(q, (t, len(trace) + len(q), ev))
    state = {"acked": [], "stored": []}
    for i in range(4):                                   # client sends 4 writes, each with a random network delay
        send(rng.uniform(0, 5), ("write", i))
    while q:
        now, _, (kind, i) = heapq.heappop(q)
        if kind == "write":
            if rng.random() < 0.25:                      # simulated fault: the server "crashes" before persisting
                trace.append(f"t={now:.2f} write {i}: server crashed"); 
                if buggy: state["acked"].append(i)       # BUG: ack sent from memory before persisting
                continue
            state["stored"].append(i); state["acked"].append(i); trace.append(f"t={now:.2f} write {i}: stored+acked")
    lost = [i for i in state["acked"] if i not in state["stored"]]
    return lost, trace
bad = next(s for s in range(1000) if run(s)[0])
print("first failing seed:", bad)
lost, trace = run(bad); print("trace:", *trace, sep="\n  "); print("acked but lost:", lost)
print("replay same seed gives same trace:", run(bad)[1] == trace, "| fixed code passes:", not any(run(s, False)[0] for s in range(1000)))

What the authors say they learned

  • Simulation shortens the time between introducing a bug and finding it, and a reproduced bug can have more logging added without changing event order. The paper says that when a bug was first seen in production, the team usually first improved the simulator until it reproduced the bug there, and only then debugged it.
  • It reports that CloudKit has deployed FoundationDB for more than half a million disk years without a single data corruption event, and that cross-replica consistency checks have never found inconsistent replicas in production. Those are the authors' claims about their own deployments.
  • Simulation made ambitious rewrites feasible. The paper's example: early versions used ZooKeeper for coordination; real-world fault injection found two independent ZooKeeper bugs (about 2010), it was removed, and replaced with a new Paxos implementation written in Flow, with no production bugs reported since. So the team pushes dependencies into code they can simulate.

What simulation does not do

(General, mine; the paper's claims are above.) A simulator finds bugs in the world it models. If the simulated disk lacks a failure mode that real disks have, simulation will not find the bug; this is why the paper mentions improving the simulator's fidelity when production surprises the team, and why the case for independent tests on real machines remains.

The pattern to remember

Analogy: the flight simulator

A pilot's simulator is not the aeroplane, but it can fly a thousand engine failures in a day, restart from the exact moment before the crash, and be run before any real aircraft exists. The trick is that the cockpit controls in the simulator are the same ones the pilot uses in the air.

Where it breaks down: a flight simulator replays what its designers thought to model; the real sky has weather nobody coded.

Key takeaways

  • Unbundled roles (sequencer, proxies, resolvers, log servers, storage servers) scale and fail independently.
  • OCC with resolvers plus versions from a sequencer gives strict serializability; conflicts are checked against recent commit history within a five-second window.
  • Recovery starts a new epoch, finds the end of the log (PEV and RV), and has storage servers roll back to it.
  • Determinism is an architectural decision: network, disk, time and randomness are interfaces.
  • Buggification and swarm testing make rare states common; every failure replays from its seed.

Check your understanding

What does a FoundationDB resolver check?

  1. Disk checksums
  2. Whether any key range the transaction read was modified by a committed transaction after its read version
  3. Whether a log server is alive
  4. Client credentials
Resolvers keep recent modified ranges with commit versions and abort a transaction whose read ranges conflict.

How does FoundationDB handle most failures in its transaction system?

  1. It repairs each failure in place
  2. It shuts the transaction system down and recovers into a new epoch
  3. It waits for an operator
  4. It relies on a quorum of replicas to mask the failure
The paper says all failure handling reduces to one recovery path.

In recovery, what is the recovery version (RV)?

  1. The highest committed version seen by any proxy
  2. The minimum of the durable versions of the stopped log servers, the end of the redo log
  3. The first version of the epoch
  4. A checkpoint on disk
Data beyond RV is discarded and storage servers roll back to it.

What makes a failing simulation run reproducible?

  1. Running it on real hardware
  2. All nondeterminism (network, disk, time, random numbers) is abstracted and seeded
  3. Writing the logs to tape
  4. Using more threads
Determinism means the same seed replays the same events.

What does buggification do?

  1. Fixes bugs automatically
  2. Lets the simulator inject unusual but contract-respecting behaviour at points in the code, making rare states common
  3. Removes asserts
  4. Turns off fault injection
Examples: an error from an operation that usually succeeds, an unexpected delay, an odd tuning value.

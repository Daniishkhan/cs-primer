Percolator: Transactions on Bigtable

Google's web index used to be rebuilt in batches, so a changed page waited days to appear. Percolator replaced that with small transactions on top of Bigtable, a store that offers only single-row atomicity. It is a compact textbook of how to build multi-row transactions out of locks, timestamps and a convention about which lock decides the outcome.

The pattern in one sentence

Layer snapshot-isolated transactions on a store with single-row atomicity by running two-phase commit from the client, with one designated primary lock that decides the outcome and a timestamp oracle that orders everything, and accept higher latency per transaction in return for scale and incremental work.

The cast

You have seen the outline of Percolator in chapter 14 and the theory of two-phase commit in chapter 13. Snapshot isolation and write skew come from the isolation chapter of the data course. This case goes through Peng and Dabek's OSDI 2010 paper in detail. All facts are from it unless marked as general.

Bigtable
A distributed sorted map keyed by (row, column, timestamp). It offers atomic read-modify-write on a single row and nothing across rows. Percolator runs on it and stores its metadata in extra columns.
Percolator worker
A process on every machine, alongside a Bigtable tablet server and a GFS chunkserver. All the application's observers are linked into the worker.
Timestamp oracle
A small service that hands out strictly increasing timestamps. Every transaction asks it twice: once for a start timestamp and once for a commit timestamp.
Lock, write and data columns
For each user column Percolator keeps a data column (the values by timestamp), a lock column (an uncommitted transaction is writing this cell, and where its primary lock is) and a write column (a committed value exists, with a pointer to the timestamp of the data).
Primary and secondary locks
In each transaction one written cell is chosen as the primary, and the others are secondaries. Their locks point to the primary. The primary's state decides the transaction.
Observer and notification
An observer is code the system runs when a chosen column changes. A notify column marks dirty cells, and an ack column records the last start timestamp at which an observer ran.
Caffeine
The name of the Percolator-based indexing system that replaced the MapReduce-based one.

The problem

Building a web index means maintaining invariants across documents: for duplicates, only the highest-PageRank URL should appear, and anchor text of links must be attached to the target and forwarded across duplicates. Google had done this as a long chain of MapReduces over the whole repository. MapReduce makes the invariants easy because each stage finishes before the next begins. But to incorporate a small recrawl you must rerun the stages over everything, because new pages link to old ones. Latency is proportional to the size of the repository rather than the size of the update. In the old system the paper says each day brought several billion crawled documents through a series of 100 MapReduces, and a document spent two to three days being indexed before it could be returned in a search result.

A traditional DBMS could maintain invariants with transactions but could not handle tens of petabytes on thousands of machines, billions of updates a day. Bigtable could scale to that size, but offered no tools for invariants across rows under concurrent updates. Percolator fills the gap: random access to a very large repository, ACID transactions with snapshot isolation, and observers to drive the next step.

The authors note a design bias that explains the rest of the paper: the requirement for massive scale and the lack of a requirement for extremely low latency. That let them be lazy about cleaning up locks left by failed machines (a delay of tens of seconds on a commit is tolerable for indexing, not for OLTP), and omit a global deadlock detector, which raises the latency of conflicting transactions but lets the system scale.

Snapshot isolation and the timestamp oracle

Each transaction reads at its start timestamp and writes at its commit timestamp. Snapshot isolation protects against write-write conflicts: if two concurrent transactions write the same cell, at most one commits. It does not give serializability: the paper says plainly that it permits write skew. Its advantage is cheap reads: any timestamp is a consistent snapshot, so a read is a Bigtable lookup at that timestamp with no read locks (apart from checking for pending writer locks, below).

The oracle must be fast, since each transaction needs two timestamps. It periodically reserves a range by writing the highest allocated timestamp to stable storage, and then serves timestamps from memory. After a restart, timestamps jump forward to the stored maximum, but never go backwards. Each worker batches the timestamp requests of its transactions by keeping at most one RPC outstanding to the oracle; when the oracle is busy, batches grow. The paper reports around two million timestamps a second from one machine.

The paper gives a short argument why a reader sees every committed write below its start timestamp. Take a reader R with start timestamp TR and a writer W with commit timestamp TW < TR. The oracle gave TW out before or in the same batch as TR, so W requested its commit timestamp before R got its start timestamp. W had written all its locks before it asked for TW. R cannot read before it has TR. So when R reads, W's locks are already in place: R either sees W's committed write record, or sees W's lock and waits for it.

The commit protocol

Percolator is a client library, so there is nowhere in the storage layer to intercept traffic and assign locks. It stores locks in Bigtable itself, in the same row as the data and changed in the same row transaction, which gives it a replicated, distributed, persistent lock table for free.

The paper's example transfers $7 from Bob to Joe. The state after each step is below (timestamps follow the paper's figure: start 7, commit 8).

In prewrite, for each cell, the client reads the metadata in one Bigtable row transaction and aborts if it sees a write record newer than its start timestamp (the write-write conflict) or any lock at all (the other transaction may be slow to release after committing, but the authors consider that unlikely, so abort). Otherwise it writes the lock and the data at the start timestamp. If everything locked, the client gets the commit timestamp, then for the primary checks that its lock is still there, replaces it with a write record and erases the lock in one row transaction. That is the commit point: from then on the transaction has committed. The secondaries follow. A Get first checks for a lock in the range up to its start timestamp; if there is one, it waits (and may try to clean it up), otherwise reads the newest write record in that range.

Crashes and lazy cleanup

Failure of a tablet server does not matter, because Bigtable keeps written locks across tablet server failures. A client failure is the problem: it leaves locks that would block later transactions forever. Percolator cleans up lazily. A transaction A that meets a lock left by B may decide B has failed and erase B's locks, but A cannot be sure, and must not race with a not-actually-dead B committing. That is what the primary lock is for: both A and B know where the primary is (it is written into every lock), and any commit or cleanup must modify the primary under a row transaction, so only one succeeds. B must see its primary lock still present when committing; A must see the primary lock still present before erasing a secondary.

If the client died in phase two, the transaction is already past its commit point, and the stranded locks must be rolled forward: the cleaner sees a write record in place of the primary lock, and writes the matching write record at the stranded cell. If the primary is still locked, roll back is safe. Cleanup is safe even for a live client, since it is synchronised on the primary, but it forces that client to abort, so a lock is only cleaned when its owner seems dead or stuck. For liveness, running workers write a token to the Chubby lock service, which is deleted when the process exits; a lock also contains a wall-clock time, and a lock whose time is too old is cleaned even if the worker's token is present. Workers committing for a long time update that time periodically.

The toy model below follows that structure (it is mine, with a simplification: the reader cleans any lock it finds, whereas the paper cleans only locks it suspects are dead). It crashes the client at each step and lets a later reader repair what is left.

"""Percolator-style 2PC over a toy cell store (follows the paper's Figure 6 structure; not Google's code)."""
import itertools
class Oracle:
    def __init__(self): self.t = itertools.count(1)
    def get(self): return next(self.t)

class Store:                       # cell -> {"data": {ts: v}, "lock": {ts: primary}, "write": {commit_ts: start_ts}}
    def __init__(self, cells):
        self.c = {k: {"data": {}, "lock": {}, "write": {}} for k in cells}
    def seed(self, cell, v, ts): self.c[cell]["data"][ts] = v; self.c[cell]["write"][ts] = ts

class Crash(Exception): pass

def commit(store, oracle, writes, crash_at=None):
    """writes: {cell: value}; first cell is the primary. crash_at: step name where the client dies."""
    start = oracle.get()
    cells = list(writes)
    primary = cells[0]
    for cell in cells:                                       # phase 1: prewrite (lock + data at start_ts)
        c = store.c[cell]
        if any(ts > start for ts in c["write"]) or c["lock"]: return None
        c["data"][start] = writes[cell]; c["lock"][start] = primary
        if crash_at == f"prewrite:{cell}": raise Crash()
    commit_ts = oracle.get()
    p = store.c[primary]                                     # phase 2: primary first = the commit point
    del p["lock"][start]; p["write"][commit_ts] = start
    if crash_at == "after-primary": raise Crash()
    for cell in cells[1:]:
        c = store.c[cell]; del c["lock"][start]; c["write"][commit_ts] = start
        if crash_at == f"commit:{cell}": raise Crash()
    return commit_ts

def read(store, oracle, cell, start=None):
    start = start or oracle.get()
    c = store.c[cell]
    for lts, primary in list(c["lock"].items()):
        if lts <= start:                                     # a lock in our snapshot: clean up (assume owner is dead)
            prim = store.c[primary]
            done = [cts for cts, sts in prim["write"].items() if sts == lts]
            if done:                                         # primary committed -> roll FORWARD
                del c["lock"][lts]; c["write"][done[0]] = lts
            else:                                            # primary not committed -> roll BACK
                del c["lock"][lts]; c["data"].pop(lts, None); prim["lock"].pop(lts, None); prim["data"].pop(lts, None)
    ws = [(cts, sts) for cts, sts in c["write"].items() if cts <= start]
    return c["data"][max(ws)[1]] if ws else None

STEPS = [None, "prewrite:bob", "prewrite:joe", "after-primary", "commit:joe"]
print(f"{'client dies at':<16} {'bob':>4} {'joe':>4}  verdict")
for step in STEPS:
    s, o = Store(["bob", "joe"]), Oracle()
    s.seed("bob", 10, o.get()); s.seed("joe", 2, o.get())
    try: commit(s, o, {"bob": 3, "joe": 9}, crash_at=step)
    except Crash: pass
    b, j = read(s, o, "bob"), read(s, o, "joe")              # a later reader repairs whatever was left
    verdict = "committed (both new)" if (b, j) == (3, 9) else "aborted (both old)" if (b, j) == (10, 2) else "TORN!"
    print(f"{str(step):<16} {b:>4} {j:>4}  {verdict}")

The pattern in the output is the invariant of the whole design: before the primary's write record exists, a crash means the transaction aborts for everyone; after it, the transaction is committed for everyone, even though the secondary was never finished.

Notifications: observers instead of a batch scheduler

A transaction updates the table, but something must run the next transaction. Observers do that: the user registers a function and a set of columns, and Percolator calls the function after data is written to one of those columns in any row. The indexing system is a chain: a MapReduce loads crawled documents with loader transactions, which trigger the document processor transaction, which triggers clustering, which triggers transactions to export clusters to serving. Caffeine has about ten observers.

Notifications look like database triggers but differ in a way that matters: the triggered observer runs in a separate transaction, so the triggering write and the observer's writes are not atomic. They structure the computation; they do not maintain integrity. The one guarantee: at most one observer transaction commits for each change of an observed column. The converse is not promised: many writes to a column may cause one run, which the paper calls message collapsing and uses deliberately, since a popular URL need only be reprocessed periodically.

The mechanism is the ack column. When an observed column is written, a transaction reads the column and the observer's ack; if the column was written after the last ack, it runs the observer and sets the ack to its own start timestamp. If two transactions start for the same notification, both run, but one aborts on the ack column.

Finding dirty cells is a search problem, since notifications are rare (the table has trillions of cells and perhaps millions of notifications). The notify column holds one entry per dirty cell, in its own Bigtable locality group so a scan reads only the dirty ones. It is a hint without transactional properties. Workers scan random regions: pick a random tablet, then a random key, then scan from there, and take a lightweight advisory lock before scanning a row to avoid two workers running the same row. Early on, scanning threads clumped together, like buses, because a thread that stops to run observers falls behind while those behind it skip through clean rows and catch up. The fix: a thread that finds itself on the same row as another jumps to a new random place. Later, a weaker notification was added that writes only the notify column, with no transactional conflict, for hotspots where many transactions tried to notify the same cell.

Latency versus throughput: Percolator against MapReduce

The paper is candid that Percolator uses more resources per unit of work. MapReduce reads in large sequential chunks, and gets the data for tens or hundreds of web pages in one operation. Percolator performs around 50 individual Bigtable operations to process one document. The team recovered some of that cost by batching lock writes (adding a few seconds of latency but cutting RPCs, using a conditional mutation that does read-and-write in one RPC), by delaying reads to batch them, and by prefetching columns of the same row (reducing reads by about a factor of ten). Every API call blocks and parallelism comes from thousands of threads per machine, chosen to make application code simpler; the drawbacks were kernel and infrastructure scalability limits at high thread counts, which were fixed.

The benchmark comparison with a DBMS is deliberately rough (the paper says so), and Percolator is not an OLTP system. Its answer to "is the loss in efficiency too much?" is that you can add capacity by buying machines. An important structural point: the processing time of Percolator work depends on the size of the update, not of the repository, and a new processing step is one more lookup per document, not another pass over everything. A batch system also suffers from stragglers that delay a whole pass; Percolator does not wait for the slowest piece.

What went wrong, and what the authors learned

Hotspots conflict

In the TPC-E-like test, each broker's commission and trade count would be updated about every 5 seconds, which causes repeated write conflicts. The paper's answer is to write increments to a side table and aggregate; for the benchmark, they simply omitted the write. Weak notifications grew out of the same problem.

Cleanup is slow by design

Waiting for locks left by dead clients can delay commits by tens of seconds. The authors say that would be unacceptable in an OLTP database but tolerable for an index.

Contention is solved by retry

No global deadlock detector. Conflicting transactions abort or wait, back off and retry, which costs latency but removes a central point.

Concurrency is still on the programmer

The authors remark that moving from MapReduce means developers must reason about concurrency where none existed before. Transactions help, but do not remove the complexity.

The pattern to remember

Analogy: the shared ledger and the first signature

Several clerks update several ledgers. Each page to change is flagged with a note that says "I'm part of a change; the master page for this change is page 12." The change counts as done the moment the master page is signed, not before and not after. If a clerk walks out mid-change, whoever finds a flagged page looks at the master page: signed means finish the change, unsigned means rip the flag out.

Where it breaks down: in a real office there is one clock on the wall. Percolator needs a timestamp oracle to give every clerk a consistent "before" and "after".

Key takeaways

  • Percolator layers multi-row snapshot-isolated transactions on Bigtable's single-row atomicity, with locks stored next to the data.
  • A timestamp oracle gives the snapshot order; batching and range allocation keep it fast.
  • The primary lock is the commit point and the arbiter between cleaner and committer; secondaries are rolled forward or back according to it.
  • Cleanup is lazy because the workload tolerates latency; this is a stated design choice, not an oversight.
  • Observers turn a table into an incremental pipeline; notifications are not atomic with the triggering write.
  • Against MapReduce it trades more resources and per-document overhead for far lower latency at modest update rates.

  2. Writing the lock on the last secondary
  3. Replacing the primary lock with a write record at the commit timestamp
  4. Deleting the notify cell
Once the primary's write record is visible the transaction has committed, and secondaries must be rolled forward even if the client dies.

A reader finds a leftover lock on a secondary cell and looks at the primary. The primary has a write record. What does the reader do?

  1. Rolls the secondary back
  2. Rolls the secondary forward by writing the write record and erasing the lock
  3. Waits forever
  4. Aborts the original transaction
A primary write record means the transaction committed. If the primary were still locked, rolling back would be safe.

Why does Percolator tolerate lazy lock cleanup and no global deadlock detector?

  1. It cannot detect failures
  2. Its workload (building a web index) needs scale and tolerates higher latency, so simple scalable mechanisms were chosen over fast ones
  3. Bigtable forbids deadlock detection
  4. Snapshot isolation prevents deadlocks
The paper says the relaxed latency requirement allows this, and notes it would be unacceptable for OLTP.

ZooKeeper: Wait-Free Coordination

Chubby offered clients a lock service. The ZooKeeper authors, working at Yahoo!, took a different route: expose a tiny file-system-like API with no blocking calls, promise strong order, and let applications build their own locks, elections and barriers on top. This case is about that choice, about what the ordering guarantees buy, and about the sharp edge it leaves: reads that can be stale.

The pattern in one sentence

A coordination kernel offers non-blocking primitives with a precise ordering contract (linearizable writes, FIFO per client, ordered notifications), and clients build blocking recipes such as locks and barriers out of them, so one slow client can never stall the service.

The cast

This builds on chapter 11, which describes ZooKeeper's data model and recipes at overview level, and on chapter 8 for the replicated state machine idea. This page goes into why those parts are shaped as they are. Facts are from Hunt, Konar, Junqueira and Reed, USENIX ATC 2010, unless marked as general.

Znode
An in-memory data node in a hierarchical namespace (the data tree). Znodes are meant for coordination metadata, not bulk data, and carry version counters and timestamps so that updates can be conditional.
Regular, ephemeral, sequential
A regular znode lives until deleted. An ephemeral znode is also removed when the session that created it ends. A sequential flag appends a monotonically increasing counter to the name, never smaller than that of any other sequential child of the same parent.
Session
A client's connection state, with a timeout. A session survives moving between servers. Ephemeral znodes are tied to it.
Watch
A one-time trigger attached to a read. When the thing read changes, the server sends one notification, saying that something changed but not the new value, and the watch is gone.
Ensemble, leader, follower
The replicated servers that provide the service. All updates go through the leader, which broadcasts them with Zab, an atomic broadcast protocol, using simple majority quorums.
zxid
A transaction id that orders all state changes. Every response carries the zxid it is relative to, and reads are tagged with the last zxid their server has seen.

Wait-free by design

The authors say they moved away from blocking primitives such as locks because, in a coordination service, a slow or faulty client holding something can hurt faster clients, and because the service itself gets more complicated if processing one request depends on the responses and the failure detection of other clients. The resulting API looks, in the authors' words, like "Chubby without the lock methods" and without open and close. Each call names a full path, so the server keeps no handle state.

Wait-free here means that an operation completes without waiting for any other client. The service supports: create (with flags for regular, ephemeral and sequential), delete and setData with an expected version, exists, getData and getChildren (each can set a watch), and sync. Updates take an expected version, so a client can do compare-and-set with no lock. Every call has an asynchronous form, and the client library delivers callbacks in order, so a client can keep many operations outstanding. The paper gives numbers: a new leader that must update 5,000 znodes takes about 10 seconds if each change (about 2 ms) is issued after the previous one completes, but under a second when pipelined.

Wait-free is not the same as weakly ordered. Wait-freedom alone, the authors note, is not sufficient for coordination, so the service adds an order contract.

The ordering guarantees

There are two:

  • Linearizable writes. All requests that update state are serialised and respect real-time precedence. The paper calls its flavour A-linearizability (asynchronous linearizability), because a client may have several outstanding operations rather than one, as in Herlihy and Wing's original definition.
  • FIFO client order. All requests from one client execute in the order the client sent them.

See chapter 5 for the formal vocabulary. Note what is missing: reads are not linearizable. The authors observe that only writes need to be, and that the two guarantees together suffice for the primitives their applications need.

Their illustration is the ready znode. A new leader must rewrite many configuration znodes, and workers must not use a half-updated configuration; if the leader dies partway, they must not use the partial result. A lock would help with the first requirement but not the second. Instead the leader deletes ready, updates the configuration znodes (all pipelined), then creates ready. Because of FIFO order and linearizable writes, a process that sees ready must also see all the new configuration. If the leader dies first, ready never appears and nobody uses the partial state. A reader who saw ready before the update began is covered by a third guarantee: a client that sets a watch is notified of a change before it can see the new state.

Reads served locally, and sync

Every server holds a full in-memory copy of the data tree and answers reads from it, without disk activity or any agreement protocol. This is the central performance decision: the target workloads have read-to-write ratios from 2:1 to 100:1, and read throughput grows as servers are added. The price is stated in the paper: a read can return a stale value even though a newer update to the same znode has committed, so precedence order is not guaranteed for reads.

The paper also describes how a client moving to a new server never goes backwards: the new server compares the client's last zxid with its own and does not re-establish the session until it has caught up. So one client sees time move forward, but two clients on two servers can see different moments.

The authors' second scenario is a side channel. Clients A and B share a configuration in ZooKeeper and also talk directly. A changes the configuration and tells B; B's server is a little behind, so B may not see the change. Issuing a write first would fix it, but that costs a full broadcast. sync is the cheaper tool: followed by a read, it makes B's server apply all pending writes before serving the read, which the paper calls a slow read. In their implementation sync is placed at the end of the request queue between the leader and the follower, so it is not broadcast. It relies on the follower being sure that the leader is still the leader, which they handle with a null transaction or with timeouts, chosen so that leaders realise they have lost leadership before followers abandon them.

Common misconception: "ZooKeeper is linearizable"

Writes are. Reads, by default, are not: they are served by whichever server the client is attached to. A program that needs the latest value must issue a sync before the read (the paper's way) or otherwise arrange it. Case 4 is about a system, etcd, that made the opposite default: reads linearizable, with a flag for stale ones.

Watches

Watches replace polling. They are one-time triggers, tied to the session and removed when they fire. They tell the client that data changed but not the new data. If a znode changes three times between a notification and the client's next read, there is no second or third notification: the client already knows that what it has is stale. Notifications are handled locally by the server the client is attached to, and are ordered strictly with respect to writes: the server sends and clears the notification for a write before it processes any later write or read. Session events such as connection loss are delivered to watch callbacks too, so clients know that notifications may be late.

The paper contrasts this with Chubby. Chubby manages client caches directly and blocks an update until each caching client has invalidated, using leases to bound the delay a slow client can cause. In ZooKeeper, the authors say, watches avoid the problem altogether, because no write waits on any client.

Recipes

The paper stresses that the service knows nothing about these primitives; they are client-side code over the API. Examples it gives:

  • Group membership. Each member creates an ephemeral child of a group znode; its disappearance signals failure. Listing the children, with a watch, shows who is alive.
  • Configuration management. Read a configuration znode with a watch; when notified, read again, setting the watch again.
  • Rendezvous. A znode that the master fills with its address, which workers read with a watch to wait.
  • Simple lock. Try to create an ephemeral znode; if it exists, watch it. This works but suffers the herd effect: when it is deleted, every waiter wakes though only one can win, and it is exclusive-only.
  • Lock without the herd. Create an ephemeral sequential child; if yours is the lowest you hold the lock; otherwise watch only the znode just before yours. Deleting yours (or your session dying) wakes exactly one waiter.
  • Read/write locks and double barriers built the same way.

The toy store below (mine, not ZooKeeper's code) counts how many waiting clients wake up for each recipe, and shows what happens when a waiter in the middle of the queue dies.

"""ZooKeeper-style lock recipes on a toy znode store (not ZooKeeper's code)."""
class Store:
    def __init__(self):
        self.nodes, self.seq, self.watches, self.wakeups = {}, 0, {}, 0   # name -> owner session
    def create_seq(self, prefix, owner):
        self.seq += 1
        name = f"{prefix}{self.seq:04d}"
        self.nodes[name] = owner
        return name
    def create(self, name, owner):
        if name in self.nodes: return False
        self.nodes[name] = owner
        return True
    def exists_watch(self, name, client):
        if name in self.nodes:
            self.watches.setdefault(name, []).append(client)
            return True
        return False
    def delete(self, name):
        del self.nodes[name]
        woken = self.watches.pop(name, [])      # one-shot watches fire on deletion
        self.wakeups += len(woken)
        return woken
    def expire_session(self, owner):            # ephemeral nodes vanish with their session
        woken = []
        for n in [n for n, o in self.nodes.items() if o == owner]:
            woken += self.delete(n)
        return woken

def simple_lock(n_clients):
    s = Store()
    s.create("/lock", "c0")                                     # c0 holds it
    for i in range(1, n_clients):
        s.exists_watch("/lock", f"c{i}")                        # everyone else watches the same node
    s.delete("/lock")
    return s.wakeups

def queue_lock(n_clients, crash_middle=False):
    s = Store()
    mine = [s.create_seq("/lock/n-", f"c{i}") for i in range(n_clients)]
    for i in range(1, n_clients):
        s.exists_watch(mine[i - 1], f"c{i}")                    # each client watches only its predecessor
    if crash_middle:
        s.expire_session("c3")
        owner_after = f"c{min(i for i in range(n_clients) if mine[i] in s.nodes)}"
        return s.wakeups, owner_after
    s.delete(mine[0])
    return s.wakeups, "c1"

N = 20
print(f"{N} clients waiting, holder releases")
print("  simple lock-file recipe : watchers woken =", simple_lock(N))
w, o = queue_lock(N)
print("  sequential-node recipe  : watchers woken =", w, "-> next holder", o)
w, o = queue_lock(N, crash_middle=True)
print("  waiter c3 crashes       : watchers woken =", w, "(c4 re-checks; c0 still holds) holder:", o)

Output when run:

  simple lock-file recipe : watchers woken = 19
  sequential-node recipe  : watchers woken = 1 -> next holder c1
  waiter c3 crashes       : watchers woken = 1 (c4 re-checks; c0 still holds) holder: c0

A lock recipe is still a lease-based lock

The ephemeral znode disappears when the session times out, not when the process stops. A process that is paused longer than its session timeout may wake up and still believe it holds the lock. The ZooKeeper paper does not discuss this; it is the same gap as in chapter 4. Kleppmann's 2016 post, discussed in case 3, suggests using the zxid or the znode version as a fencing token. That is a general recommendation from outside this paper.

Zab and the replicated database

When a server receives a write, it forwards it to the leader. The leader computes what the state will be once the write is applied, taking into account outstanding transactions not yet applied, and turns the request into a transaction that records the new state, for example a setDataTXN with the new data, the new version number and updated timestamps, or an errorTXN if a version check will fail. Transactions are idempotent. They are broadcast with Zab, and the server the client is attached to replies when it delivers the change.

Zab uses majority quorums, so with 2f+1 servers ZooKeeper tolerates f failures. The paper says Zab gives stronger order guarantees than plain atomic broadcast: changes by a leader are delivered in order, and all changes from previous leaders are delivered to a new leader before it broadcasts its own. During normal operation delivery is in order and exactly once, but recovery may redeliver messages, which is acceptable because transactions are idempotent and still in order.

Idempotence makes fuzzy snapshots possible. The server walks the tree depth-first without locking and writes what it sees. The result may not match any real instant: the paper's example has /foo and /goo both at version 1, a stream of three changes, and a snapshot that captured /foo at version 3 but /goo at version 1. Replaying the changes in order from the start of the snapshot lands on the correct final state anyway, because applying a change twice is harmless.

Performance and the numbers

The paper's benchmark ran on a cluster of 50 servers, with 35 machines simulating 250 clients, and each request a read or write of 1 KB of data. Throughput of a saturated system at the two extremes:

Reading the table: more servers raise read capacity and lower write capacity. It is the direct consequence of the design: reads are local, writes need the leader to talk to a majority. The paper's own measurement of a production workload (the Yahoo! Fetching Service) found the read:write ratio varying between 10:1 and 100:1 when traffic exceeded a thousand operations a second.

What was learned, and the trade-offs

This is a design and evaluation paper, not a postmortem, so the lessons are the caveats the authors themselves state:

Fast reads cost precedence

Because reads skip the agreement protocol, a read can lag the newest committed write. The remedy is explicit: sync, or issuing a write. The designers chose to make the common case cheap and the rare case explicit.

Order beats locks for some jobs

The ready znode shows that FIFO order and linearizable writes cover cases where a lock is insufficient (a leader dying with a half-done update).

Push blocking to the client

Locks and barriers are client code. A bug or slowness there cannot wedge the service, and applications can pick the recipe that fits them rather than one fixed primitive.

Watches can collapse

A burst of changes yields one notification. That is correct for "refresh your copy" uses and wrong for "process every change" uses, so the recipes always re-read after a notification.

The pattern to remember

Analogy: the notice board, not the door lock

Chubby is a building with a doorman who hands out keys. ZooKeeper is a notice board with strict rules about the order notes appear: anyone can pin a note, notes carry numbers, and nobody has to wait for anyone else. People build their own queue-numbering, sign-up sheets and "meeting is on" signs from it.

Where it breaks down: a real notice board shows everyone the same state at once. Each ZooKeeper server shows its own copy, which may be a moment behind.

Key takeaways

  • Wait-free primitives plus two ordering guarantees (linearizable writes, FIFO client order) are enough to build locks, elections, barriers and config management on the client side.
  • Reads are served by any server from memory and may be stale; sync before a read forces freshness at the cost of a slower read.
  • Watches are one-shot, carry no data, and are ordered before the state change they report.
  • Zab turns requests into idempotent transactions, which makes recovery and fuzzy snapshots simple.
  • Read capacity scales with servers; write capacity does not.

Check your understanding

Why did the ZooKeeper authors avoid blocking primitives such as locks in the service's API?

  1. Locks cannot be implemented on top of a file-system-like API
  2. A slow or faulty client holding a blocking primitive can hurt faster clients, and the service gets more complicated
  3. Locks are illegal in Zab
  4. Blocking calls cannot be linearizable
The paper gives exactly this reason. Locks can still be built by clients from ephemeral and sequential znodes.

A client calls getData with a watch, and the znode changes three times before the client reads again. How many notifications does it receive?

  1. Three, one per change
  2. None
  3. One: watches are one-time triggers that say something changed, not what
  4. One per server in the ensemble
The watch fires once and is removed. The client re-reads and sets a new watch.

Client A writes to ZooKeeper, then tells client B by another channel. B reads and sees the old value. What does the paper offer to prevent this?

  1. Run the read against the leader only
  2. Use sync before the read so the server applies all pending writes
  3. Use ephemeral znodes
  4. Disable watches
Reads are local and can be stale. sync followed by a read makes the server catch up first.

In the lock recipe without a herd effect, why does each client watch only the znode immediately before its own?

  1. Because watches can only be set on the previous sequence number
  2. So that when the holder releases or dies, exactly one waiter is woken instead of all of them
  3. To make the lock fair across data centres
  4. Because ZooKeeper forbids more than one watch per znode
Lining up the waiters and watching only the predecessor avoids waking everyone when one waiter can win. If a middle waiter dies, its successor wakes and re-checks.

A Byzantine Failure in the Real World

On 2 November 2020 a network switch in one of Cloudflare's control-plane data centers started to fail halfway: it was only partly down: it kept some protocols running, but it did not forward everything. One member of an etcd cluster could reach some of its peers and not others. The result was a cluster stuck in elections, databases that failed over when nobody expected it, and a dashboard and API that were impaired for more than six hours, while Cloudflare's edge network carried on.

The pattern in one sentence

A node that can talk to some peers and not others is worse than a node that is simply dead, because everyone gets a different answer to "is the leader alive?" and a protocol that assumes one shared view can stall or flap.

The cast

This page states only what Cloudflare's post says. Explanations of how the general mechanisms work are labelled as general. Background: chapter 3 (failure detection), chapter 10 (Raft, including pre-vote and CheckQuorum) and chapter 12 (Byzantine faults).

Partial failure of a component
A switch (or link) that works for some traffic and not for others. Here the post describes the switch as partially operating.
LACP, BGP, vPC
Link and routing protocols on the switch. The post says LACP and BGP stayed up while vPC (the mechanism that keeps the paired switches' ports in step) did not. The post says a full failure would have moved all traffic to the peer switch, whereas here each server saw a problem only for some of its traffic.
etcd
A Raft-based key-value store used for coordination. Cloudflare's cluster management system used it for member discovery and coordination of its database clusters.
Byzantine fault
A fault where a component behaves arbitrarily, for instance telling different peers different things. The post uses it for cluster members having conflicting views of reality.
Omission fault
A fault where messages are simply not delivered or not sent. Omission faults can be tolerated without Byzantine-fault-tolerant protocols.

What happened

The post describes a control-plane data center, whose job is the customer-facing API and dashboard, not the edge network that serves traffic. A switch in one rack began misbehaving at 14:43 UTC. Alerts fired because it stopped answering pings, but the switch was not fully down. The post says LACP and BGP stayed up, vPC did not, and the switch was not forwarding all the packets it received. In a clean failure, traffic would have shifted to the peer switch; here it did not. The post says the switch recovered on its own about six minutes later, yet the impairment lasted far longer, for reasons below.

One etcd member, node 1, sat in that rack. The post names three members, nodes 1, 2 and 3. Node 3 was the leader. Node 1's traffic to node 3 passed through the degraded switch; node 1 to node 2 used the healthy path; node 2 to node 3 was unaffected. So node 1 and node 2 disagreed about whether a leader existed: node 1 repeatedly started leader elections and voted for itself, while node 2 kept voting for node 3, the only leader it could still reach. The votes tied, no leader that node 1 could reach was elected, and, as the post notes, elections block writes. The cluster was effectively read-only from about 14:44 UTC until node 1 could reach node 3 again.

In chapter 10 you met the general remedy for a node that is cut off from the leader but not from everyone: pre-vote (ask whether an election could succeed before incrementing the term) and CheckQuorum (a leader steps down if it cannot hear a majority). The post does not say whether etcd had those enabled or whether they would have helped here, so treat the next picture as the general mechanism, not a claim about this incident.

How a read-only etcd became a database outage

This is the part of the story that is easy to miss. The post does not name the database failover tool; it calls it a cluster management system that uses etcd for member discovery and coordination. It also says each database cluster had a primary, a synchronous replica and asynchronous replicas, plus a secondary cluster in another data center.

  1. With etcd unable to take writes, two database clusters could not confirm that they had a healthy primary. At 14:45 UTC that triggered automatic promotion of a synchronous replica. The post says this completed without errors or data loss.
  2. A defect in the cluster management system meant every promotion required rebuilding all of that cluster's replicas, a job whose duration scales with database size.
  3. In one cluster, the authentication database relied on a heavily used replica for reads. With no replica online, the primary took all the load and was overloaded. The post says this caused the main impact.

Measured impact in the post: the API and dashboard were impaired for 6 hours 33 minutes; API success rates periodically fell as low as 75%; dashboard requests were up to 80 times slower. The first rebuilt replica rejoined service at 21:20 UTC and performance returned to normal.

Responders reduced load by slowing SSL certificate pushes, email sending and other features, and routed API read traffic by hand to replicas in the secondary data center, which substantially improved API availability. Dashboard sessions could not yet move between data centers without disruption, so authentication was moved fully back to the primary data center after users became frustrated.

Byzantine, or not?

Cloudflare titled the post "A Byzantine failure in the real world" and defined a Byzantine fault as one where cluster members hold conflicting views of reality. Node 1 and node 2 did disagree about the leader. A postscript records the response from the distributed systems community: the incident is better characterised as an omission fault, since messages were dropped, not forged, and omission faults can be tolerated without Byzantine-tolerant protocols. The post promised a follow-up on fault types.

Common misconception: "Byzantine means anything weird"

In chapter 12 the Byzantine model is specifically about nodes that may send arbitrary, even contradictory, messages, and it costs 3f+1 replicas. A switch that silently drops some packets produces asymmetric reachability (A hears B, B does not hear A, C hears both), which is a network problem that crash-fault protocols like Raft are expected to handle. The two are easy to conflate because both produce "different nodes see different things".

What changed afterwards

  • Cloudflare fixed the bug in its cluster management system that forced a full replica rebuild after each promotion; a team had already been working on it.
  • Redesigning user sessions so they can be steered across data centers was already under way.
  • They revisited auto-remediation settings. The promotion had been made fast on purpose, but for at least one database they concluded that fast promotion could do more harm than good, and adjusted the configuration immediately.
  • They are tuning systems to tolerate dependency failures more gracefully.

The pattern to remember

Analogy: the committee that only talks by unreliable post

Member 1 cannot receive the chairman's letters but can still send letters to member 2, who does get them. Member 1 keeps calling a new election; member 2 keeps replying that the chairman is fine. The committee spends its time arguing about the chair instead of doing business. One extra rule ("don't call an election until you have checked that others also think the chair is gone") would calm it down.

Where it breaks down: real letters are not selectively lost for hours by one cause; a partly failed switch can look healthy to the tools that watch it.

Key takeaways

  • A partly failed switch (LACP and BGP up, vPC not, not forwarding everything) caused asymmetric reachability inside an etcd cluster.
  • Node 1 kept voting for itself; node 2 kept voting for node 3; elections blocked writes and etcd became read-only.
  • An automatic failover that depended on etcd promoted replicas, and a defect forced full replica rebuilds, so the real damage came from the second-order effects.
  • Cloudflare called it Byzantine; the community said omission. The distinction matters for what protocol you need.
  • Automation that reacts quickly to uncertain signals can amplify a partial failure (general lesson, and one Cloudflare itself drew about promotion settings).

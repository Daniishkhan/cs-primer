Toolbox

Distributed-systems bugs hide in rare interleavings, so the tools here do one of three things: they run your protocol under hostile conditions, they check what happened, or they let you watch a real production-grade system behave. Each card has install notes and a ten-minute exercise tied to a chapter.

How to use this page

Jump to a tool when a chapter mentions it. Everything runs on macOS or Linux (Windows under WSL). The cards are written from the tools' public documentation. I did not run these commands while writing the page, so every output block is labelled illustrative: the shape is right, the ids, timings and counts on your machine will differ. Tool versions move, so if a flag has changed, trust --help over this page.

All exercises use throwaway folders and processes on your own machine (127.0.0.1). Never point fault injection at a system you do not own.

Simulate and check

Before real machines, there are workbenches that supply the network, the faults and the verdict, so you only write the node.

Maelstrom & Gossip Glomers

Needs: a JDK (11 or newer), Graphviz and gnuplot for the plots; a language runtime for your nodes (Go below) · macOS: brew install openjdk graphviz gnuplot · Ubuntu: sudo apt install openjdk-17-jdk graphviz gnuplot · Maelstrom itself: download the maelstrom.tar.bz2 release from the jepsen-io/maelstrom GitHub releases page (the release, not the source) and unpack it

Maelstrom is a workbench built on Jepsen. Your node is any program that reads JSON messages on standard input and writes JSON replies on standard output. Maelstrom starts several copies, plays the part of the network (it can delay, drop and partition), sends client requests, records the history and checks it against a model for the chosen workload. The Gossip Glomers challenges by Fly.io are a guided series of exercises on it: 1 Echo, 2 Unique ID Generation, 3 Broadcast (in several parts), 4 Grow-Only Counter, 5 Kafka-Style Log and 6 Totally-Available Transactions. They line up with this course: broadcast with gossip (chapter 3), the counter with CRDTs (chapter 15), the log with chapter 17, and the transactions with chapter 16. Chapter 19 shows where this fits in the testing ladder.

10-minute guided exercise

Do challenge 1 end to end, then run the broadcast workload against a partition. In a folder for the exercise, write the Go node from the Fly.io page (it uses the github.com/jepsen-io/maelstrom/demo/go library), build it, and run:

$ go mod init maelstrom-echo && go get github.com/jepsen-io/maelstrom/demo/go
$ go install .  # puts maelstrom-echo in ~/go/bin
$ cd ~/maelstrom  # the unpacked release
$ ./maelstrom test -w echo --bin ~/go/bin/maelstrom-echo --node-count 1 --time-limit 10
...  (log lines about starting a node, a client, and the nemesis)
Everything looks good! ヽ('ー`)ノ

The command form is from the Fly.io challenge page; the last line is illustrative of a passing run (Maelstrom reports :valid? true in its results). Now the interesting part. Write the challenge 3 node (broadcast, then fault tolerant) and run it against a network partition:

$ ./maelstrom test -w broadcast --bin ~/go/bin/maelstrom-broadcast --node-count 5 --time-limit 20 --rate 10 --nemesis partition
illustrative:  :stable-latencies {0 12, 0.5 310, 0.95 1900, 0.99 2400, 1 2800}
illustrative:  :lost-count 0, :never-read-count 0, :valid? true
$ ./maelstrom serve  # then open http://localhost:8080

Open the latest run in the browser. Look at messages-per-op and the latency plot. Now change your node from "forward to everyone" to "forward to two random neighbours each round" and compare the message counts. Finally, remove the retry of unacknowledged messages and re-run with --nemesis partition: the checker should report values that were never delivered, which is the experience of why gossip needs anti-entropy.

On a cloud VM

The simulated network is enough for every Glomers challenge, so you do not need machines. A VM helps only if you want to run your node binaries on separate hosts with real latency, which Maelstrom does not do for you. See the lab machine page for a local Linux VM or a small rented server (set a billing alert first, and delete it when you are done).

What to look for

  • The results folder (store/latest, or ./maelstrom serve) holds the full history, the latency and rate plots and, on failure, the anomaly found. Reading a failing history is the skill.
  • Maelstrom checks your claim for the workload: the broadcast workload checks that every acknowledged value eventually appears everywhere; lin-kv workloads check linearizability.
  • A workload is a contract, not an implementation: your node can be written in any language and the checker does not care.

Common pitfalls

  • Run from the unpacked Maelstrom directory and give --bin an absolute path to an executable.
  • Stdout is the protocol channel: print debug output to stderr only, or Maelstrom will try to parse it as a message.
  • Missing Graphviz or gnuplot makes the run finish but the plots fail. Install them first.
  • Flags and workload names evolve between releases. Check ./maelstrom test --help.

Jepsen

Needs: a JVM and Leiningen (Jepsen is a Clojure library), plus a cluster of 5 or so Linux nodes reachable by SSH as root, usually containers or VMs (the project ships a Docker-based setup and a VM option) · Practical route: read published analyses and work through the tutorial in the jepsen-io/jepsen repository

Jepsen, by Kyle Kingsbury, is the framework behind most well-known database correctness reports. A test installs a real database on every node, starts concurrent clients, injects faults with a nemesis (partitions, process kills, clock skew), records a history of operations and checks it with a checker (linearizability, serializability, and others). Be honest about the cost: running it needs real effort, a cluster you can reset, and some Clojure. You do not need that to learn from it. The reports at jepsen.io/analyses are among the best case studies in the field, and Jepsen is what the idea of chapter 19 looks like at scale. Its checkers use the algorithms discussed in chapter 5.

10-minute guided exercise

Reading exercise (no install, about ten minutes). Open one analysis from jepsen.io/analyses for a database you have heard of. Read only three things: the summary, the list of tested versions and the section that shows one anomaly. Then answer in your own words: which consistency model did the vendor claim, which fault triggered the violation, and what would the history have to look like for a checker to flag it? Compare your answer to chapter 5's ladder.

Tutorial exercise (about an hour the first time). The Jepsen repository has a step-by-step tutorial that builds a test for a small etcd-backed register. Its shape is:

$ git clone https://github.com/jepsen-io/jepsen && cd jepsen
$ lein version  # Leiningen needs a JDK
# follow doc/tutorial/ in the repo: scaffold, db, client, nemesis, checker
$ lein run test --node n1 --node n2 --node n3 --node n4 --node n5 --time-limit 30  # from the test project you built; flags depend on your CLI setup
illustrative:  Everything looks good! ヽ('ー`)ノ   or   Analysis invalid! (ノಥ益ಥ)ノ ┻━┻

The command is a shape, not a recipe: the node list and options come from how you wrote your test's cli entry point. The point of the exercise is to see the five parts (database, client, generator, nemesis, checker) and to find where each would change for another database.

On a cloud VM

This is the one tool here that really wants a cluster. Five small cloud VMs (or a local VM host running several) with SSH access is the realistic setup; the Docker-based development cluster in the Jepsen repo is the cheaper start. See the lab machine page for a local Linux VM or a small rented server (set a billing alert first, and delete it when you are done).

What to look for

  • Every Jepsen result is a history plus a checker. Without a precise model the history is just noise.
  • A "valid" result means no anomaly was found in that run, not that none exists.
  • The nemesis schedule matters as much as the workload: many bugs need a partition during a leader change.

Common pitfalls

  • Time zero is the cluster. Budget for resets, SSH keys and clock sync before you write any checker logic.
  • Do not run it against production or someone else's service.
  • Linearizability checking is expensive in the number of concurrent operations, so tests keep clients few and histories short.

Porcupine & Knossos

Porcupine (Go): go get github.com/anishathalye/porcupine in a Go module (Go 1.20 or newer is safe) · Knossos (Clojure): the linearizability checker used by Jepsen, in the jepsen-io/knossos repository, run through Leiningen

Both tools take a history of operations (each with an invocation time, a return time, an input and an output) and a sequential specification of the object, and search for a legal order that respects real-time order and the object's rules. If one exists the history is linearizable; if not, you get a counterexample. This is the Wing & Gong style of search, improved by Lowe, which chapter 5 introduces. Porcupine is the quickest way to try it from your own code because it is a plain Go library: you describe the model and hand it events.

10-minute guided exercise

Check two tiny register histories. Make a folder and write reg_test.go:

package reg

import (
	"testing"
	"github.com/anishathalye/porcupine"
)

type op struct {
	kind string // "w" or "r"
	val  int
}

var model = porcupine.Model{
	Init: func() interface{} { return 0 },
	Step: func(state, input, output interface{}) (bool, interface{}) {
		in := input.(op)
		if in.kind == "w" {
			return true, in.val
		}
		return output.(int) == state.(int), state
	},
}

func ev(id, client int, call bool, v interface{}) porcupine.Event {
	k := porcupine.ReturnEvent
	if call {
		k = porcupine.CallEvent
	}
	return porcupine.Event{ClientId: client, Kind: k, Value: v, Id: id}
}

func TestStale(t *testing.T) {
	// client 0 writes 1 and it returns; THEN client 1 reads and sees the old value 0.
	h := []porcupine.Event{
		ev(0, 0, true, op{"w", 1}), ev(0, 0, false, 0),
		ev(1, 1, true, op{"r", 0}), ev(1, 1, false, 0),
	}
	t.Log("linearizable:", porcupine.CheckEvents(model, h))
}

func TestConcurrent(t *testing.T) {
	// the read overlaps the write, so seeing 0 is fine.
	h := []porcupine.Event{
		ev(0, 0, true, op{"w", 1}),
		ev(1, 1, true, op{"r", 0}), ev(1, 1, false, 0),
		ev(0, 0, false, 0),
	}
	t.Log("linearizable:", porcupine.CheckEvents(model, h))
}
$ go mod init reg && go mod tidy
$ go test -v
illustrative:  === RUN   TestStale
illustrative:      reg_test.go:36: linearizable: false
illustrative:  === RUN   TestConcurrent
illustrative:      reg_test.go:46: linearizable: true

The first history is a stale read after a completed write, which is exactly what linearizability forbids. The second overlaps, so the checker may place the read before the write. Porcupine's API has changed in small ways between versions (event and operation types, a visualisation helper); check the package documentation if a name does not compile. Next, add a third client that reads 1 and then a fourth that reads 0 afterwards, and predict the verdict before running. Knossos does the same job in Clojure and is what Jepsen calls; you rarely write against it directly, but its repository README shows the history format.

What to look for

  • The answer depends on real-time order: the same values can be legal or illegal depending only on which operations overlap.
  • An operation that never returned (a timeout) may or may not have taken effect. Checkers treat it as possibly applied at any later time, which is why timeouts are the hard part.
  • The model is the specification: a wrong model gives confidently wrong verdicts.

Common pitfalls

  • The search is exponential in the worst case. Keep histories short or partition them by key (linearizability is local, chapter 5).
  • Record invocation before sending and return after receiving, with a single consistent clock, or you create or hide anomalies.

Specify it

TLA+ & the TLC model checker

Needs: Java 11 or newer · Easiest: the TLA+ extension for VS Code (install from the Extensions panel; it bundles TLC and offers "Check model") · Command line: download tla2tools.jar from the tlaplus/tlaplus GitHub releases page

TLA+ is Lamport's language for writing a design as a state machine, and TLC explores every reachable state of a small instance of it, checking invariants. Chapter 20 builds up to it and lists the Transfer spec used here; chapter 9 and chapter 13 describe protocols (Paxos, two-phase commit) that are the classic specs to read next. Newcombe et al. describe industrial use at AWS (CACM, 2015).

10-minute guided exercise

Make a folder and save the spec and config from chapter 20 as Transfer.tla and Transfer.cfg (the spec has two variables, alice and bob, two invariants NoOverdraft and Conserved, and a Next action that moves n units).

$ java -cp tla2tools.jar tlc2.TLC Transfer.tla  # picks up Transfer.cfg
illustrative:  Model checking completed. No error has been found.
illustrative:  ... distinct states found, ... states generated

In VS Code, open Transfer.tla, press the command palette key and choose TLA+: Check model with TLC. The extension creates the same config for you. Now plant a bug. The action AtoB(n) has a guard n \in 1..alice. Replace it with n \in 1..10 and re-run:

Error: Invariant NoOverdraft is violated.
State 1: <Initial predicate&gt;  alice = 10, bob = 10
State 2: <AtoB&gt;  alice = 0, bob = 20
State 3: <AtoB&gt;  alice = -5, bob = 25

The checker prints the shortest sequence of steps that breaks the invariant. That sequence is the exercise: explain, in one sentence per step, what a real implementation would have to do differently. Then restore the guard and add a third account. Notice how the number of states grows.

What to look for

  • The guard (enabling condition) of an action is where most real bugs live; remove one and look at the trace.
  • "No error found" is a statement about your small model only (the small-scope hypothesis is a bet, not a proof).
  • Invariants are checked in every reachable state; liveness properties need fairness assumptions and are checked differently.

Common pitfalls

  • State-space explosion: start with 2 or 3 nodes and tiny value sets.
  • The .cfg file must name the spec and the invariants, and constants must be assigned there.
  • The module name must match the file name.

Run real systems

etcd & etcdctl

macOS: brew install etcd (includes etcdctl) · Linux: release tarballs from the etcd-io/etcd GitHub releases (contains etcd and etcdctl) · Optional: goreman (go install github.com/mattn/goreman@latest) to run a Procfile

etcd is Raft behind a key-value API: revisions, leases, watches and transactions (chapter 11). Running three real members lets you see leader election (chapter 10) and lease expiry (chapter 4) happen for real.

10-minute guided exercise

The etcd clustering guide shows the static-bootstrap flags for three machines (--name, --initial-advertise-peer-urls, --listen-peer-urls, --listen-client-urls, --advertise-client-urls, --initial-cluster-token, --initial-cluster, --initial-cluster-state new). On one laptop, give each member its own ports and data directory. Save this as Procfile:

etcd1: etcd --name infra1 --data-dir /tmp/etcd/infra1 --listen-client-urls http://127.0.0.1:2379 --advertise-client-urls http://127.0.0.1:2379 --listen-peer-urls http://127.0.0.1:12380 --initial-advertise-peer-urls http://127.0.0.1:12380 --initial-cluster-token etcd-local --initial-cluster 'infra1=http://127.0.0.1:12380,infra2=http://127.0.0.1:22380,infra3=http://127.0.0.1:32380' --initial-cluster-state new
etcd2: etcd --name infra2 --data-dir /tmp/etcd/infra2 --listen-client-urls http://127.0.0.1:22379 --advertise-client-urls http://127.0.0.1:22379 --listen-peer-urls http://127.0.0.1:22380 --initial-advertise-peer-urls http://127.0.0.1:22380 --initial-cluster-token etcd-local --initial-cluster 'infra1=http://127.0.0.1:12380,infra2=http://127.0.0.1:22380,infra3=http://127.0.0.1:32380' --initial-cluster-state new
etcd3: etcd --name infra3 --data-dir /tmp/etcd/infra3 --listen-client-urls http://127.0.0.1:32379 --advertise-client-urls http://127.0.0.1:32379 --listen-peer-urls http://127.0.0.1:32380 --initial-advertise-peer-urls http://127.0.0.1:32380 --initial-cluster-token etcd-local --initial-cluster 'infra1=http://127.0.0.1:12380,infra2=http://127.0.0.1:22380,infra3=http://127.0.0.1:32380' --initial-cluster-state new

Start it with goreman start (or run the three etcd ... lines in three terminals). Then, in another terminal:

$ export ETCDCTL_API=3  # needed only for old etcdctl builds
$ export EP=127.0.0.1:2379,127.0.0.1:22379,127.0.0.1:32379
$ etcdctl --endpoints=$EP endpoint status -w table  # who is the leader?
illustrative: a table with ENDPOINT, ID, VERSION, DB SIZE, IS LEADER, RAFT TERM, RAFT INDEX; one row says true under IS LEADER
$ etcdctl --endpoints=$EP put foo bar
OK
$ etcdctl --endpoints=$EP get foo
foo
bar
$ etcdctl --endpoints=$EP watch foo  # leave this running
# in another terminal:  etcdctl --endpoints=$EP put foo baz
PUT
foo
baz
$ etcdctl --endpoints=$EP lease grant 10
illustrative:  lease 32695410dcc0ca06 granted with TTL(10s)
$ etcdctl --endpoints=$EP put --lease=32695410dcc0ca06 session alive
$ etcdctl --endpoints=$EP get session  # wait 10+ seconds and run it again: the key is gone
$ etcdctl --endpoints=$EP lock mylock  # blocks until held; prints a key under mylock/
$ etcdctl --endpoints=$EP elect myelection alice  # campaign; a second 'elect myelection bob' waits

The put, get, watch, lease grant and --lease forms are those of the etcd v3 documentation; the lease id above is the documentation's example, so use whatever id yours prints. Now the failure part: find the leader in the status table, kill that member (Ctrl-C its terminal, or pkill -f infra1), and run endpoint status against the survivors. A new leader appears with a higher Raft term, and writes with two of three members still work. Kill a second member and watch writes block: no quorum, chapter 8's intersection argument in action. Restart them and the cluster recovers.

On a cloud VM

Three processes on one laptop share a disk and a clock, so they cannot show real network behaviour. On three small VMs in different zones or regions, repeat the exercise and compare put latency from each location to the leader's: this is the cost chapter 18 describes. See the lab machine page for a local Linux VM or a small rented server (set a billing alert first, and delete it when you are done).

What to look for

  • The revision counter in get -w json output advances on every write; watches can resume from a revision, which is how clients survive reconnects.
  • A lease is a promise by the server to delete keys after the TTL unless you keep it alive. lock and elect are built from leases plus ordered keys, the recipe of chapter 11.
  • Leader loss takes about an election timeout to recover from; writes in that window fail or wait.

Common pitfalls

  • Reusing a data directory from an earlier cluster with a different token gives confusing bootstrap errors. Delete /tmp/etcd between experiments.
  • The --initial-cluster* flags matter only on first bootstrap.
  • A lock held by a client whose lease expired is not safe against a paused client; pair it with a revision-based fence (chapter 4).

ZooKeeper CLI

macOS: brew install zookeeper · Any OS: a binary release tarball from the Apache ZooKeeper site; it needs Java · Run: copy conf/zoo_sample.cfg to conf/zoo.cfg, then bin/zkServer.sh start

ZooKeeper (Hunt et al., 2010) offers a small tree of znodes. Two flags make coordination recipes possible: ephemeral znodes vanish when the creating session ends, and sequential znodes get a monotonically increasing suffix. Together they give leader election and locks (chapter 11), and the failure behaviour ties back to chapter 4.

10-minute guided exercise

Start a standalone server with the sample config, then open the shell:

$ bin/zkServer.sh start
$ bin/zkCli.sh -server 127.0.0.1:2181
[zk: 127.0.0.1:2181(CONNECTED) 0] create /election ""
Created /election
[zk: ...] create -e -s /election/c_ "alice"
illustrative:  Created /election/c_0000000000
[zk: ...] ls /election
illustrative:  [c_0000000000]

That is one candidate. Open a second zkCli.sh and create another with create -e -s /election/c_ "bob"; its suffix is higher. The rule from the recipe is: the lowest sequence number is the leader; every other candidate watches only the znode just below its own (to avoid a herd of watchers). In the second shell, set a watch with stat -w /election/c_0000000000 (or get -w), then quit the first shell. Because the node was ephemeral it disappears when that session closes, and the second shell receives a NodeDeleted event: bob is now the leader. Finally, open ls /election again to see the single remaining candidate.

One caution on timing: a session ends when the server stops hearing heartbeats within the session timeout, not at the instant the client dies, so a hard kill takes a few seconds to take effect. A paused client that resumes may still believe it is leader. That is the lease problem again.

What to look for

  • -e = ephemeral, -s = sequential. The two flags together are the entire election recipe.
  • The watch is one-shot: it fires once, and you must re-register.
  • Ephemeral znodes cannot have children.

Common pitfalls

  • Don't watch the leader node from every candidate: that is the herd effect, and the lowest-neighbour trick avoids it.
  • Session timeouts, not process death, define when leadership moves.
  • Run the client commands from the ZooKeeper folder; zkCli.sh needs Java on the path.

Break it on purpose

Toxiproxy & tc netem

Toxiproxy: brew install toxiproxy (gives toxiproxy-server and toxiproxy-cli), or release binaries from the Shopify Toxiproxy GitHub repo · tc netem: Linux only, part of iproute2 (preinstalled on most distributions; needs sudo)

Toxiproxy is a TCP proxy that sits between a client and a server and applies "toxics" (latency, bandwidth limits, cut connections, timeouts) on demand, which is excellent for showing how timeouts and retries (chapter 3) and cross-region latency (chapter 18) behave. tc netem does the same thing for a whole network interface in the Linux kernel, so it can also drop and reorder packets and make real partitions with the right rules (chapter 19).

10-minute guided exercise

Put a proxy in front of the etcd member from the previous card.

$ toxiproxy-server  # terminal 1: control API on localhost:8474
$ toxiproxy-cli create --listen 127.0.0.1:52379 --upstream 127.0.0.1:2379 etcd1  # terminal 2
illustrative:  Created new proxy etcd1
$ time etcdctl --endpoints=127.0.0.1:52379 get foo
illustrative:  real 0m0.012s
$ toxiproxy-cli toxic add -t latency -a latency=1000 etcd1
illustrative:  Added downstream latency toxic 'latency_downstream' on proxy 'etcd1'
$ time etcdctl --endpoints=127.0.0.1:52379 get foo
illustrative:  real 0m1.0xxs
$ toxiproxy-cli toxic add -t timeout -a timeout=0 etcd1  # after a delete of the latency toxic; accepts then hangs
$ toxiproxy-cli toxic remove -n latency_downstream etcd1
$ toxiproxy-cli delete etcd1

Then use etcdctl --command-timeout=2s get foo through the proxy with a 3 second latency toxic: the client fails with a deadline error even though the server is perfectly healthy. A client cannot tell this from a crash (chapter 1). On Linux, the kernel version of the same experiment, on the loopback interface, is:

$ sudo tc qdisc add dev lo root netem delay 100ms 20ms loss 5%
$ ping -c 5 127.0.0.1
illustrative:  rtt min/avg/max/mdev = 180/200/240/20 ms   (packets lost: about 5% of each direction)
$ sudo tc qdisc show dev lo
$ sudo tc qdisc del dev lo root  # always undo it

Delay applies to every packet leaving the interface, so a ping crosses it twice (about 200 ms round trip for 100 ms each way). Try the three-member etcd cluster from the previous card under this setting and watch elections become more frequent as the delay approaches the election timeout.

On a cloud VM

tc netem on lo slows everything on the machine, including your SSH-free local tools. On a VM you can apply it to a real interface (for example eth0, taking care not to cut your own SSH session) between machines, which behaves like a real wide-area link. See the lab machine page for a local Linux VM or a small rented server (set a billing alert first, and delete it when you are done).

What to look for

  • A timeout tells you nothing about whether the server did the work: add latency, then retry a non-idempotent request and count the duplicates.
  • Toxics have a direction (upstream or downstream) and a toxicity probability, so you can make only some connections slow.
  • netem delay is symmetric per interface, real internet paths often aren't.

Common pitfalls

  • Always remove the netem rule. A forgotten 100 ms delay on lo makes everything on the machine mysteriously slow.
  • On macOS, tc does not exist (use Toxiproxy, or the Network Link Conditioner).
  • Toxiproxy only affects traffic that goes through it, so point the client at the proxy port.

Kafka CLI tools

Needs: Java · Install: download the Apache Kafka binary release (the kafka_2.13-...tgz archive), or brew install kafka · Mode: KRaft, with no ZooKeeper (Kafka 3.x onward supports it; 4.0 removed ZooKeeper entirely). Script names under bin/ end in .sh in the tarball and have no suffix when installed by Homebrew

A Kafka topic is a set of partitioned, replicated logs (chapter 17). Consumer groups divide partitions between consumers and remember committed offsets. The command-line tools let you see all of that, including the ISR and the lag.

10-minute guided exercise

Run a single-node KRaft broker from the unpacked archive. The config path differs by version (3.x ships config/kraft/server.properties, 4.x uses config/server.properties); use the one that exists.

$ KAFKA_CLUSTER_ID="$(bin/kafka-storage.sh random-uuid)"
$ bin/kafka-storage.sh format -t $KAFKA_CLUSTER_ID -c config/kraft/server.properties
$ bin/kafka-server-start.sh config/kraft/server.properties  # terminal 1; leave running
$ bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders --partitions 3 --replication-factor 1
Created topic orders.
$ bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
illustrative:  Topic: orders  PartitionCount: 3  ReplicationFactor: 1
illustrative:     Topic: orders  Partition: 0  Leader: 1  Replicas: 1  Isr: 1  (and partitions 1 and 2)
$ bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders --property parse.key=true --property key.separator=:  # type  k1:hello  k2:world  k1:again
$ bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --group g1 --from-beginning --property print.key=true --property print.partition=true
illustrative:  Partition:1  k1  hello
illustrative:  Partition:1  k1  again
illustrative:  Partition:2  k2  world
$ bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group g1
illustrative: columns GROUP TOPIC PARTITION CURRENT-OFFSET LOG-END-OFFSET LAG CONSUMER-ID HOST CLIENT-ID

Both k1 messages land in the same partition, in order, because the partition is chosen by hashing the key; k2 may sit elsewhere. There is no ordering promise between partitions. Now stop the consumer, produce three more messages, and run --describe --group g1 again: LAG is the distance between LOG-END-OFFSET and the group's committed CURRENT-OFFSET. Start two consumers with the same --group g1 and watch the partitions split between them (the rebalance), then stop one and watch it hand them back.

On a cloud VM

With one broker, replication-factor 1 is the only option, so there is no ISR to watch. Three brokers on three VMs let you create a topic with replication factor 3, kill the leader of a partition and see the ISR shrink, which is the story of the chapter. See the lab machine page for a local Linux VM or a small rented server (set a billing alert first, and delete it when you are done).

What to look for

  • Keys decide partitions; partitions decide ordering.
  • A consumer group's progress is just committed offsets, stored by Kafka itself; lag is a derived number.
  • A rebalance pauses consumption, so the group size and session timeout matter operationally.

Common pitfalls

  • Format the storage directory once. Reformatting with a new cluster id on an old log directory fails.
  • Port 9092 busy? Another broker is running.

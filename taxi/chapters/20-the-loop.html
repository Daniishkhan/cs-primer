The Loop

Every part is in the file: a noise floor, a run store, a keep-or-revert rule and a model that trains under any configuration. This step is the loop that runs them in order, and the first time the program claims to have improved its own model. The loop also has to say how much of the claim is real.

Where we are

After step 19 the file has the parts of a search and no search. noise_floor measures how far a score moves on its own, log_run keeps the runs, and keep_or_revert decides: 29.0 beats 30.0 at a floor of 0.5, and does not at 1.5. This step brings evaluate, which trains the linear model under one configuration and returns its training loss and its validation loss, the loss on rides held back to choose between configurations (the "held" score in the log), and SPACE, the six configurations the loop may try. The loop's only randomness is which one comes next. Here is that part by hand, with each configuration's name from step 18: the start is left out and the other five come in a shuffled order, each once. Run it, then change Random(0) to Random(1).

The wall

The parts do not run themselves. One pass of a search is five jobs: pick a configuration, train it, write the run down, compare it with the best, remember the winner. And the first improvement the loop reports comes with a catch it cannot see for itself. The start, the distance-only line, scores 5.13 on the validation rides, and the best configuration the search finds scores 0.91: a gain of 4.23. But the loop chose that winner by its validation loss, so the gain is measured on the rides that did the choosing. You need something that runs the five jobs in order, and a way to tell how much of the gain it reports is real.

The idea

A search is a loop of four verbs. Propose a configuration from the space. Evaluate it: fit on the training rides, score on the validation rides. Log the run. Decide against the best so far, with step 19's rule and step 17's floor. Repeat until the budget, a number of candidates, is spent.

To check the claim, cut some rides away before the search starts and never let the loop read them: the test rides. When the search is over, score the start and the best on them once. The loop's claim and the real result are two gains:

claimed = Lval(start) − Lval(best)     real = Ltest(start) − Ltest(best)

They will not agree. The claim is measured on the rides that picked the winner, which flatters it. The real gain is measured on rides that did not, but it is one more sample, with a wobble of its own. Measuring both, and watching the gap, is the point.

Your move

One function: the loop itself. evaluate, feature_set and SPACE are given.

def search(space, budget, seed, rides_train, rides_val, floor, path):
    """A keep-or-revert search. Start from space[0] as the best (evaluate
    it, log it). The candidates are the other configurations in `space`,
    in the order random.Random(seed).shuffle puts them, at most `budget`
    of them: evaluate each with the same seed, log it, and apply
    keep_or_revert against the best with `floor`.
    Returns (best run dict, number of candidates kept)."""

evaluate takes the seed for models with randomness in them, like step 16's network. This linear model has none, so the seed only sets the order of the proposals. Press ▶ Check to run check.py 20.

The check takes the first 1,500 rides, holds 300 out as the test rides, and splits the other 1,200 into 960 to train on and 240 to validate on. It measures a noise floor and runs your search with a budget of 5, so each of the five configurations after the start is tried once. It wants six lines in the log, one per configuration, the first one space[0], a best that is never worse than the start, and the same seed replaying the same log. Then it scores the start and the best on the 300 test rides. When it passes:

Solution spoiler 
def search(space, budget, seed, rides_train, rides_val, floor, path):
    rng = random.Random(seed)
    tr, va = evaluate(space[0], rides_train, rides_val, seed)
    best = log_run(path, space[0], seed, tr, va)
    kept = 0
    candidates = list(space[1:])
    rng.shuffle(candidates)
    for config in candidates[:budget]:
        tr, va = evaluate(config, rides_train, rides_val, seed)
        candidate = log_run(path, config, seed, tr, va)
        best, won = keep_or_revert(best, candidate, floor)
        kept += won
    return best, kept

What Artifact 1 adds is the engineering around that loop. In autoresearch a run that exceeds ten minutes is killed and logged as a crash, and the rule that the score must sit outside what the proposer can change is only stated in prose. The Rust runner and sandbox enforce it.

What you have now

  • feature_set(name): which columns a configuration uses. Given.
  • evaluate(config, rides_train, rides_val, seed): train the linear model under a configuration, return its two losses. Given.
  • search(space, budget, seed, rides_train, rides_val, floor, path): the keep-or-revert loop. Yours.
  • SPACE: the six configurations the loop may try. Given.

The program now improves its own model and says by how much. In the check, 5 candidates and 1 kept took the validation loss from 5.13 to 0.91, a claimed gain of 4.23, and on the 300 rides it never used the gain is 5.19. They differ, and here the real gain is larger: the start scores 6.25 on those rides against 5.13 on the validation rides. Part of any such gap is selection and part is that the two sets of rides differ, and one search cannot tell which, so measure both.

A Ride Is a Vector

Longer rides cost more, and so do slower ones. A guess that reads miles and minutes needs a way to hold several numbers per ride and several knobs at once: a vector, and the one operation on vectors that the rest of the leg is built from.

Where we are

Ride 4 is the problem: 7.70 miles, 25.9 minutes, $27.00 on the meter. At $2.50 plus $2.00 a mile the guess is $17.90, which is $9.10 short. The meter really does charge for time: New York's rate card adds 50 cents for every minute the cab is stuck below 12 miles an hour. Give the guess a third knob, a price per minute, and try 50 cents:

distance, minutes, passengers, fare = (7.70, 25.9, 1, 27.0)   # ride 4
x = [1.0, distance, minutes]      # the ride as numbers
w = [2.5, 2.0, 0.5]               # base, per mile, per minute

total = 0.0
print("x =", x)
print("w =", w)
for xj, wj in zip(x, w):
    print(f"  {xj:5.2f} * {wj:4.2f} = {xj * wj:6.2f}")
    total += xj * wj
print(f"sum = {total:.2f}   (the meter said ${fare:.2f})")
x = [1.0, 7.7, 25.9]
w = [2.5, 2.0, 0.5]
   1.00 * 2.50 =   2.50
   7.70 * 2.00 =  15.40
  25.90 * 0.50 =  12.95
sum = 30.85   (the meter said $27.00)

Now the guess is $3.85 over instead of $9.10 under. Minutes carry information. But look at what the loop does: it multiplies each number of the ride by the matching knob and adds the products up. The constant 1.0 at the front of x is there so the base is multiplied by 1 and lands in the sum like everything else.

The wall

Step 1's guess(distance, base, per_mile) takes one number about the ride and two knobs. Minutes make it two numbers and three knobs. Passengers, the hour of the day, the borough, the day of the week: each new fact about a ride would mean another argument and another function. Worse, every later step (the loss, the gradient, the training loop) would have to know how many knobs there are. The fix is to stop naming the knobs. A ride is a list of numbers, the knobs are a list of the same length, and a guess is one operation on the two lists.

The idea

A vector is a list of numbers with a fixed length, and the loop above is the dot product: multiply the entries pairwise, add the products up.

f̂ = x · w = ∑ xj wj = 1·b + d·m + t·p

x holds the ride (a 1, the distance d, the minutes t) and w holds the knobs (base b, per mile m, per minute p). The leading 1 is a small trick with a big payoff: the base is no longer special, it is a knob like the others, so every knob can be learnt the same way in step 7. Step 1's guess is the case w = [b, m, 0]. The dot product is the whole of a linear model: one weighted sum. Every layer of every neural network in this leg, and in the models the courses describe, is dot products arranged in rows.

One rule comes with it: the two lists must have the same length. A ride with three numbers and four knobs is a bug, not a guess, so dot refuses it with a ValueError. Python's zip would silently drop the extra entry; a function that fails loudly at the wrong shape is worth more than one that returns a plausible wrong number. Every tensor library checks shapes for the same reason.

def dot(x, w):
    if len(x) != len(w):
        raise ValueError(f"length mismatch: {len(x)} vs {len(w)}")
    return sum(a * b for a, b in zip(x, w))


def predict(ride, w):
    return dot(features(ride), w)

The library way

The same step in PyTorch run on the lab VM

A one-dimensional tensor is a vector, and @ between two of them is the dot product. torch.dot says the same thing by name, and (x * w).sum() is your loop, spelt out. The mismatched-length error you raise by hand, the library raises for you.

import torch
from common import RIDES5

distance, minutes, _, fare = RIDES5[3]           # ride 4
x = torch.tensor([1.0, distance, minutes])        # features: a vector
w = torch.tensor([2.5, 2.0, 0.5])                 # base, per mile, per minute
print("x:", x, "shape", tuple(x.shape))
print("w:", w)
print(f"x @ w     = {(x @ w).item():.4f}")
print(f"torch.dot = {torch.dot(x, w).item():.4f}")
print(f"by hand   = {(x * w).sum().item():.4f}   (multiply pairwise, add up)")
print(f"the meter said ${fare:.2f}")
try:
    torch.tensor([1.0, 2.0]) @ torch.tensor([1.0])
except RuntimeError as e:
    print("wrong lengths:", str(e).splitlines()[0])
x: tensor([ 1.0000,  7.7000, 25.9000]) shape (3,)
w: tensor([2.5000, 2.0000, 0.5000])
x @ w     = 30.8500
torch.dot = 30.8500
by hand   = 30.8500   (multiply pairwise, add up)
the meter said $27.00
wrong lengths: inconsistent tensor size, expected tensor [2] and src [1] to have the same number of elements, but got 2 and 1 elements respectively

Two details to notice. shape (3,) is how a library writes "a vector of length 3": the shape is a tuple, with one entry per dimension. And .item() turns a one-number tensor back into a Python float. Tensors default to 32-bit floats, so if you print every digit you see 30.849998 rather than 30.85; the courses' chapter on floating point is the long version.

What you have now

  • features(ride): a ride as [1.0, distance, minutes]. Given.
  • dot(x, w): the weighted sum, with a loud error for mismatched lengths. Yours.
  • predict(ride, w): the fare the knobs w predict for one ride. Yours.

The knobs now live in a list, w, and later steps will change that list without knowing or caring how long it is. The long version of today's idea is the courses' chapter on vectors and dot products. Next step: the other 6,362 rides, stacked into a matrix.

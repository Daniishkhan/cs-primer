Lab 4: A Thread Pool with Backpressure

Every web server, job runner and database client library contains some version of the thing you build here: a fixed set of worker threads, a queue of tasks, and a rule for what to do when tasks arrive faster than workers can finish them. You'll write the future, the pool, the shutdown, three overload policies, and then measure the pool until it hits the knee in the latency curve that chapter 14 drew on paper.

Why this lab matters

Most outages from overload are not caused by a program that is slow. They are caused by a queue with no limit, a policy nobody chose, and a load that arrives faster than it can be served. Writing the pool yourself makes every one of those choices visible, and measuring it makes the cliff something you have seen rather than read about.

What you'll build

  1. Future: a box that one thread fills in and another waits on.
  2. ThreadPool: workers pull tasks from a queue; exceptions travel back through the future.
  3. Graceful shutdown: finish what was accepted, then stop every worker, using one poison pill per worker.
  4. Backpressure: a bounded queue with three policies, and what each does to the producer.
  5. Measure: a load generator, a utilisation versus latency table, and Little's law.
  6. Optional, deadlines: skip work whose caller has already given up.

How the check keeps a pool still

To test "what happens when the queue is full" you need the workers to be busy at a moment you choose. The check submits a task that waits on a threading.Event (a gate), waits until it has started, then fills the queue behind it. Only then does it test your policy, and finally it opens the gate. No timing guesses: the order of events is forced, the same idea as in Lab 3. The pool's workers are daemon threads, so a bug can never keep Python alive.

Milestone 1: a Future

When you hand a task to a pool, the answer does not exist yet. A future (chapter 14, "Producer and consumer") is the receipt: an object you can ask "are you done?" or "give me the result, and I'll wait for it". One thread, a worker, fills it in; any number of other threads can wait on it.

That waiting is exactly the job of a condition variable (chapter 12, "Condition variables"): the waiter sleeps until the state becomes "done". Your Future has four methods:

MethodWho calls itWhat it does
set_result(v)a workerstore v, mark done, wake all waiters
set_exception(e)a workerstore e, mark done, wake all waiters
done()anyoneTrue once either was called; never blocks
result(timeout)the callerwait until done; return the value or re-raise the exception; raise TimeoutError if it takes too long

Common misconception: "wake one waiter is enough"

Several threads can be waiting on the same future, and all of them need the answer. notify() would wake only one, and the rest would sleep until their timeout, or for ever. A future is a broadcast: use notify_all(). (In Lab 3's queue, one wakeup per item was right, because one item can feed only one consumer.)

Hints try without first
  • Keep one threading.Condition() (it makes its own lock) and the fields _done, _result, _exception. Every method does with self._cond:.
  • self._cond.wait_for(lambda: self._done, timeout) is a ready-made "wait in a loop until the predicate is true". It returns the predicate's final value, so False means the timeout expired. With timeout=None it waits for ever.
  • Don't raise TimeoutError while still holding the lock in some strange state: raising out of a with block releases the lock correctly, so it is fine here.
  • You could build this with a threading.Event instead (wait(timeout) and set()). It's shorter. A condition is more general and matches what you built in Lab 3.

class Future:

    def __init__(self):
        self._cond = threading.Condition()
        self._done = False
        self._result = None
        self._exception = None

    def set_result(self, value):
        with self._cond:
            self._result = value
            self._done = True
            self._cond.notify_all()        # wake EVERY thread waiting in result()

    def set_exception(self, exc):
        with self._cond:
            self._exception = exc
            self._done = True
            self._cond.notify_all()

    def done(self):
        with self._cond:
            return self._done

    def result(self, timeout=None):
        """Block until done. Raise TimeoutError if `timeout` seconds pass first; re-raise the
        task's exception if it failed."""
        with self._cond:
            if not self._done:
                # wait_for re-checks the predicate in a loop for us (like our `while`)
                if not self._cond.wait_for(lambda: self._done, timeout):
                    raise TimeoutError("future not done after %s s" % timeout)
            if self._exception is not None:
                raise self._exception
            return self._result

Milestone 2: the pool, and exceptions that travel

A thread pool is a queue plus a fixed set of threads that each loop forever: take a task, run it, repeat. Why not simply start a thread per task? Chapter 14's "Why not one thread per task?" has the numbers: threads cost memory and scheduling time, and an unbounded number of them turns a traffic spike into a crash. A fixed pool caps the damage and reuses threads (chapter 10 covers what a thread costs). In your design:

  • A task is a tuple (future, fn, args, deadline).
  • submit(fn, *args) creates the future, puts the task on the queue, and returns the future immediately.
  • A worker does task = queue.get() and runs it. If fn raises, the worker catches the exception and gives it to the future with set_exception. The caller sees it when they call result(), which is where they can do something about it.

An uncaught exception kills a worker silently

If a task raises and nothing catches it, the exception ends the worker's thread. Python prints a traceback, the pool is now one thread smaller, and after enough failures the pool is empty and every future hangs. Always catch Exception around the task and store it. The check proves your workers survive a task that does 1 / 0.

def submit(self, fn, *args, deadline=None):
    if self._closed:
        raise RuntimeError("pool is shut down")
    fut = Future()
    task = (fut, fn, args, deadline)
    if self.policy == "block":
        self._queue.put(task)                       # waits for room: the producer slows down
    else:
        try:
            self._queue.put_nowait(task)
        except queue.Full:
            if self.policy == "reject":
                with self._stats_lock:
                    self.rejected += 1
                raise Rejected("queue full")
            with self._stats_lock:                  # "caller_runs"
                self.caller_ran += 1
            self._run(task)                         # the producer does the work itself
    return fut

def _run(self, task):
    fut, fn, args, deadline = task
    if deadline is not None and time.monotonic() > deadline:
        with self._stats_lock:
            self.expired += 1
        fut.set_exception(DeadlineExceeded("deadline passed before the task started"))
        return
    try:
        fut.set_result(fn(*args))
    except Exception as e:                          # a failing task must not kill the worker
        fut.set_exception(e)

def _worker(self):
    while True:
        task = self._queue.get()
        if task is _STOP:
            return                                   # exactly one pill per worker
        self._run(task)

Milestone 3: graceful shutdown with poison pills

Workers loop forever, so how do they stop? A common beginner answer is a flag like self.running = False. But a worker blocked in queue.get() never looks at the flag. The tidy answer is to send the stop request through the queue itself: a special sentinel object, nicknamed a poison pill. A worker that gets the pill exits.

  • Why through the queue? The queue is first-in first-out, so a pill put in after the real tasks is only reached after every earlier task has been taken. That gives you "finish queued work, then stop" for free.
  • Why one pill per worker? A worker that takes a pill exits and does not put it back. With three workers and one pill, one worker would stop and two would wait on an empty queue for ever, and join() would never return. So shutdown puts one pill for each worker. (Another valid design is for each worker to put the pill back before exiting; then one pill is enough, but one per worker is easier to reason about.)
  • wait=True versus wait=False. After queuing the pills, wait=True joins every worker thread, so when it returns everything has finished. wait=False returns at once and lets the workers drain in the background.
  • After shutdown, submit must raise RuntimeError: a task queued behind the pills would never run, and its future would hang.

Your task

Make a module-level sentinel (the starter has _STOP), teach _worker to return when it takes it, and implement shutdown(wait=True). A second call to shutdown must do nothing.

milestone 3 shows ✔. The check queues 20 slow tasks on 2 workers and requires them all done after shutdown(wait=True) and every thread dead. Then it gates two workers, queues 5 more tasks, calls shutdown(wait=False) (which must return within 2 s), opens the gate, and requires all 5 queued tasks to have run and all workers to exit.

Hints try without first
  • _STOP = object() is a perfect sentinel: it is equal to nothing a user could submit, and you compare with is.
  • Set self._closed = True before queuing the pills, and check it at the top of submit and shutdown. Use a lock around the check-and-set so that two threads calling shutdown at once can't both pass (check-then-act again).
  • When the queue is bounded and full, put(_STOP) blocks until a worker makes room. That is fine: the workers are draining the queue, so it will not block for ever. Use the blocking put for pills regardless of the overload policy.
Solution spoiler 
def shutdown(self, wait=True):
    with self._shutdown_lock:
        if self._closed:
            return
        self._closed = True
    for _ in self.threads:
        self._queue.put(_STOP)      # behind all queued tasks, because the queue is FIFO
    if wait:
        for t in self.threads:
            t.join()

and in _worker: if task is _STOP: return.

Milestone 4: backpressure and rejection policies

An unbounded queue never says no. Chapter 14's "Unbounded queues hide overload" showed the result: latency grows without limit, memory fills, and every request is eventually answered too late to matter. The fix is a bound, and a bound forces a decision: what should submit do when the queue is full? That decision is the backpressure policy ("Backpressure strategies" in chapter 14). You'll implement three:

PolicyWhat submit does when fullEffect on the producerGood for
"block"waits until a slot frees upslowed to the speed of the workers; nothing is lost, but the producer is stuckbatch jobs and pipeline stages that can safely slow down
"reject"raises Rejected immediatelygets an instant "no" and decides: retry later, drop, or tell its own clientrequest handlers that must stay responsive (load shedding)
"caller_runs"runs the task in the submitting threadthe producer is busy doing the work, so it cannot submit more: it slows itself down automaticallywhen you want slowdown without losing work or raising errors

Think about who the producer is. If it's a loop reading lines from a file, block is natural. If it's a web server handling thousands of connections, blocking inside the handler just moves the queue into the connections and the clients' sockets, so you'd rather reject quickly with a 503. caller_runs is the quietest: the thread that overloaded the pool pays for it. Its catch is that the caller does the work on its own thread, so a slow task now delays whatever else that thread was supposed to do, and the task runs outside the pool's thread limit.

Count what you refuse

A silent drop is a bug you'll meet at 3 a.m. Your pool keeps counters (rejected, caller_ran) so overload is visible. They're updated from many threads, so guard them with a lock. Plain += 1 is the milestone 1 bug of Lab 3 again.

def __init__(self, n_workers, max_queue=0, policy="block"):
    if n_workers < 1:
        raise ValueError("n_workers must be at least 1")
    if policy not in POLICIES:
        raise ValueError("policy must be one of %r" % (POLICIES,))
    self.policy = policy
    self._queue = queue.Queue(maxsize=max_queue)      # 0 means unbounded
    self._stats_lock = threading.Lock()
    self.rejected = 0           # refused by policy "reject"
    self.caller_ran = 0         # run by the submitting thread (policy "caller_runs")
    self.expired = 0            # skipped because their deadline had passed
    self._closed = False
    self._shutdown_lock = threading.Lock()
    self.threads = [threading.Thread(target=self._worker, name="pool-%d" % i, daemon=True)
                    for i in range(n_workers)]
    for t in self.threads:
        t.start()

def submit(self, fn, *args, deadline=None):
    if self._closed:
        raise RuntimeError("pool is shut down")
    fut = Future()
    task = (fut, fn, args, deadline)
    if self.policy == "block":
        self._queue.put(task)                       # waits for room: the producer slows down
    else:
        try:
            self._queue.put_nowait(task)
        except queue.Full:
            if self.policy == "reject":
                with self._stats_lock:
                    self.rejected += 1
                raise Rejected("queue full")
            with self._stats_lock:                  # "caller_runs"
                self.caller_ran += 1
            self._run(task)                         # the producer does the work itself
    return fut

Milestone 5: measure the knee

Now the payoff. You will point a load generator at your pool and watch latency change as the arrival rate approaches capacity. Chapter 14's "Utilisation and the cliff" explained why from theory; this is the experiment.

The setup: 4 workers, each task is time.sleep(0.02) (a stand-in for 20 ms of waiting on a database or network call). So capacity is 4 / 0.02 = 200 tasks per second. Utilisation is the arrival rate divided by that capacity. Tasks arrive at random gaps (an exponential distribution with a seeded generator), like real independent users, not on a metronome, because evenly spaced arrivals below capacity would never queue at all.

For each task you measure time in system: from the moment it arrives to the moment it finishes. That includes the wait in the queue. From the list of times you report the average and the 95th percentile (the time that 95% of tasks beat; percentile() is provided). You'll also measure Little's law (chapter 14) from both sides:

Little's law: L = λ × W

In a stable system, the average number of tasks inside it (L) equals the arrival rate (λ, here the completed tasks per second) times the average time each spends inside (W). You measure L independently: a sampler thread reads an "accepted but not finished" counter every 5 ms and averages the readings. Then you print L next to λ × W. They should agree closely, because the law is an identity about the system, whatever the workload. Seeing it agree on your own pool is the best way to trust it.

Hints try without first
  • Compute each arrival time from the previous one: next_arrival += rng.expovariate(arrival_rate), then sleep until it. Scheduling against absolute times keeps the average rate right even though each sleep overshoots a little.
  • The task closure captures arrived = time.monotonic() taken before submit. When it finishes it appends time.monotonic() - arrived to a shared list under a lock.
  • "In system" counter: add 1 before submit, subtract 1 in the task when it finishes, and subtract 1 again if submit raised Rejected.
  • Wait for all futures with f.result(timeout=60), not a bare result(), so a bug cannot hang you. Then stop the sampler and shut the pool down.
  • Measure elapsed from the first scheduled arrival to the last completion and use it for throughput. Sampling the in-system count over the same window keeps Little's law consistent.
Solution spoiler 
def run_load(arrival_rate, n_tasks, service_time, n_workers, max_queue=0, policy="block", seed=1):
    rng = random.Random(seed)
    pool = ThreadPool(n_workers, max_queue=max_queue, policy=policy)
    lock = threading.Lock()
    latencies = []          # time in system (queue wait + service) of each finished task
    in_system = [0]         # how many accepted tasks are not finished yet
    samples = []            # periodic readings of in_system, for L
    stop = threading.Event()

    def sampler():
        while not stop.is_set():
            with lock:
                samples.append(in_system[0])
            time.sleep(0.005)

    def make_task(arrived):
        def task():
            time.sleep(service_time)
            with lock:
                latencies.append(time.monotonic() - arrived)
                in_system[0] -= 1
        return task

    threading.Thread(target=sampler, daemon=True).start()
    start = time.monotonic()
    next_arrival = start
    futures, rejected = [], 0
    for _ in range(n_tasks):
        next_arrival += rng.expovariate(arrival_rate)        # absolute schedule: no drift
        delay = next_arrival - time.monotonic()
        if delay > 0:
            time.sleep(delay)
        arrived = time.monotonic()
        with lock:
            in_system[0] += 1
        try:
            futures.append(pool.submit(make_task(arrived)))
        except Rejected:
            rejected += 1
            with lock:
                in_system[0] -= 1
    for f in futures:
        f.result(timeout=60)
    elapsed = time.monotonic() - start
    stop.set()
    pool.shutdown()
    completed = len(latencies)
    avg = sum(latencies) / completed if completed else 0.0
    throughput = completed / elapsed
    return {
        "submitted": n_tasks, "completed": completed, "rejected": rejected,
        "avg": avg, "p95": percentile(latencies, 95),
        "throughput": throughput,
        "L": sum(samples) / len(samples) if samples else 0.0,    # measured: average number in system
        "lambda_W": throughput * avg,                            # Little's law prediction
        "elapsed": elapsed,
    }

Read the table like an engineer:

  • The flat part. Up to about 70% load the average time barely moves from the 20 ms of the task itself (plus a few milliseconds of sleep overshoot), though the 95th percentile already shows some tasks waiting briefly. Most of the time some worker is free.
  • The knee. From 85% to 95% load the average roughly quadruples in this run. The arrival rate rose by about 12%, and latency by several hundred percent.   • Past 100%. The queue grows for as long as the overload lasts. Here the run is short (300 tasks), so latency stops growing when the arrivals stop. In a real service with the traffic continuing it keeps climbing until you reject or run out of memory.
  • L matches λ × W in every row to within about a percent, even though one is sampled and the other multiplied. The p95 is always well above the average: the slowest tasks are the ones a user remembers (tail latency).

Milestone 6 (optional): deadlines

Even a bounded queue has a subtler waste (chapter 14, "Don't work for clients who have left"). A task that sat in the queue for two seconds may belong to a caller who gave up after one. If a worker runs it anyway, the result goes nowhere, and the worker was busy for nothing at exactly the moment capacity is scarce. The remedy is a deadline: the caller says "after this moment I no longer care", and the worker checks before starting.

Your task

Make _run check the task's deadline (a time.monotonic() timestamp, or None for no deadline). If it has passed: do not call the function, increment pool.expired, and set DeadlineExceeded on the future.

milestone 6 shows ✔. The check parks the worker, queues five tasks with a 0.1 s deadline and two without, waits 0.4 s, and opens the gate. The five must fail with DeadlineExceeded without running, the others must run, and pool.expired must be exactly 5.

Hints try without first
  • Check the deadline when the worker is about to start the task, not when it is submitted. The point is the time spent waiting in the queue.
  • Use time.monotonic(), never time.time(): it can't jump when the system clock is adjusted.
  • Because the deadline check lives in _run, it also applies to the caller_runs path for free.

Stretch goals

  • Drop-oldest policy. When full, discard the task that has waited longest (set Rejected on its future) and accept the new one. Chapter 14 argued the oldest is the most likely to be stale. Which is easier to get right with queue.Queue?
  • A race in shutdown. A submit that passes the closed check just before shutdown sets the flag can enqueue a task behind the pills. Find it, and fix it with a lock shared by submit and shutdown.
  • Priorities. Swap the queue for queue.PriorityQueue. What happens to the poison pills, and what do you have to add so tasks with equal priority never get compared with each other?
  • Autoscaling. Start with 2 workers and add up to 8 when the queue length stays above a threshold. Then think about what happens to your measured knee.
  • map. Add pool.map(fn, items) returning results in order. What should happen to the remaining futures if one raises?
  • CPU-bound tasks. Replace sleep with a pure-Python loop and run the sweep. Why does adding workers stop helping? (Chapter 10, "The Python GIL".)
  • Compare with the standard library. Run the same sweep through concurrent.futures.ThreadPoolExecutor. Its work queue is unbounded: which milestone's lesson does that illustrate?

Distributed systems connection

A pool with a bounded queue is the template for every service at its limit. The queue's bound is a promise about the worst latency you will accept; the rejection policy is the "503 Service Unavailable" a load balancer sees; caller_runs is a client that slows itself down when the server is slow. Clients that get Rejected should retry with exponential backoff and jitter, or the retries themselves become the overload (see networking chapter 16 on failure and retries). The deadline in milestone 6 is a request timeout propagated to every hop: a service that keeps working on requests whose callers have timed out amplifies an outage. And Little's law tells you how many connections, threads or in-flight requests a service needs for a target rate and latency: 2,000 requests per second at 50 ms average means about 100 requests in flight. This is the heart of capacity planning, and Part 6's reliability material builds on it.

What you learned

  • A future is a condition variable wrapped around "not yet / here is the value / here is the error". Waking all waiters is the right call.
  • A pool reuses a fixed number of threads, and must keep them alive when a task fails by routing exceptions to the future.
  • Shutdown through the queue (one poison pill per worker) gives "finish queued work, then stop" for free.
  • An unbounded queue hides overload. A bound forces a policy: block slows the producer, reject sheds load fast, caller_runs makes the producer do the work itself.
  • Latency is flat until utilisation nears 100% and then climbs steeply: the knee. The 95th percentile moves long before the average does.
  • Little's law, L = λ × W, held on your own measurements, and tells you how much concurrency a target needs.
  • Work whose caller has already left should be skipped, not performed.

Check your understanding

A pool has 4 workers. shutdown() puts a single poison pill on the queue, and then calls join() on all four workers. What happens?

  1. All four workers stop, because the pill is shared
  2. Nothing stops, because workers ignore pills
  3. One worker takes the pill and exits; the other three wait on the empty queue for ever, so join() never returns
  4. The pill is delivered to each worker in turn
A queue item goes to exactly one consumer. Each worker that takes a pill exits without putting it back, so you need one pill per worker (or each worker must put the pill back before exiting).

A web handler submits work to a pool with max_queue=100. During a traffic spike the queue is full. Which policy keeps the handler responsive, so it can answer "busy" right away?

  1. "block", because it waits until there is room
  2. "reject", because it fails immediately and lets the handler respond with an error
  3. "caller_runs", because the handler does the work in the meantime
  4. An unbounded queue, because then nothing is ever refused
Blocking moves the wait into the handler (and the client's connection). caller_runs makes the handler do slow work itself. An unbounded queue never refuses, but it answers late, which is worse. reject gives an instant, honest "no" that the caller can turn into a 503 and a retry later.

Your measurements show an average of 30 tasks in the system while 150 tasks per second complete. By Little's law, what is the average time a task spends in the system?

  1. 5 seconds
  2. 4.5 seconds
  3. 30 milliseconds
  4. 200 milliseconds
W = L / λ = 30 / 150 = 0.2 seconds = 200 ms. The law needs no assumption about how the work is distributed or ordered; it only relates the three averages.

Why does the average latency jump so much between 85% and 95% utilisation, when the arrival rate rose by only about 12%?

  1. With almost no spare capacity, any burst of arrivals forms a queue that takes a long time to drain, and queueing time grows steeply as utilisation approaches 100%
  2. Because the tasks themselves get slower at high load
  3. Because the operating system switches threads less often
  4. Because the sampler thread is competing with the workers
The tasks still take 20 ms; the extra time is waiting in line. Near full utilisation the pool has almost no slack to work through a burst, so the queue stays long. This is why capacity plans target well below 100%.

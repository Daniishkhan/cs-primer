Lab 1: A Mini Shell

You type ls | sort -r > out.txt and it just works. In this lab you will build the program that makes that happen: a small shell in Python, about 200 lines, that runs commands, changes directory, redirects files, connects programs with pipes, and survives Ctrl-C. Every piece is one of the system calls from the chapters, used for real.

Why this lab matters

A shell looks like magic until you write one. Then you see that it is only fork, exec and wait plus a bit of file-descriptor plumbing. The same few calls sit under process supervisors, CI runners, container runtimes and every subprocess.run you have ever written. You will also meet three classic bugs on purpose: the child that keeps running your shell, the pipe that never ends, and the Ctrl-C that kills the wrong program.

POSIX only

This lab needs fork, pipes and signals, so it runs on macOS, Linux and WSL (Windows Subsystem for Linux). It does not run in plain Windows PowerShell. If you try, check.py tells you so instead of crashing. Python 3.8 or newer, standard library only.

What you'll build

You will get there in five milestones, each building on the last:

  1. Run one command: parse a line, fork, exec, waitpid, and report the exit status (127 when the command does not exist).
  2. Builtins: cd and exit, the commands that cannot be separate programs.
  3. Redirection: >, >> and <, using open and dup2 in the child.
  4. Pipes: a | b | c, and the classic bug of the pipe end you forgot to close.
  5. Signals: make Ctrl-C stop the running command but not the shell.

0/5 milestones passing

Three conventions the whole lab uses

  • run_line(line) returns an int: the exit status of the command (the last command of a pipeline). The child's output simply goes to the inherited stdout, so a test can capture it by running the shell inside a subprocess.
  • Killed by a signal means 128 + N, as in bash. Python's os.waitstatus_to_exitcode reports "killed by signal 2" as -2; the shell turns that into 130. So Ctrl-C shows up as 130 and a SIGKILL as 137.
  • 127 means "command not found" and 126 means "found but could not be run".

Parsing is not the lesson here, so tokenize() is already written for you. It uses shlex, which understands quotes the way a shell does, and it treats |, <, > and >> as separate words even without spaces.

Milestone 1: run one command

Chapter 5 ended with a shell that fits in a dozen lines. Now you write it properly. The recipe is always the same three calls:

  1. pid = os.fork() clones the current process. It returns twice: 0 in the new child, and the child's PID in the parent.
  2. os.execvp(argv[0], argv) in the child replaces the child's program with the named one (p means "search $PATH"). If it works, it never returns, because the code that called it no longer exists. So any line after it runs only when exec failed.
  3. os.waitpid(pid, 0) in the parent blocks until that child ends and returns (pid, status). The status is a packed number holding either an exit code or a signal; os.waitstatus_to_exitcode (Python 3.9+) unpacks it.

The child must never return

After fork there are two copies of your shell. If the child's exec fails and the code simply carries on, that copy goes back to the top of the prompt loop and now two shells fight over your keyboard. The child must end with os._exit(code). Not sys.exit, which raises an exception that unwinds into the shell's loop, and not return. os._exit ends the process immediately, skipping Python's cleanup, which belongs to the parent anyway. Exit code 127 for "command not found" is a long-standing convention, so use it.

One more detail. Python buffers print output in your process. A buffered line that has not been written yet is copied into the child by fork, and could be written twice. Call sys.stdout.flush() before you fork.

Solution spoiler 
def decode_status(status):
    """Turn the raw status from os.waitpid into a shell-style exit code.

    Normal exit with code N        -> N
    Killed by signal N             -> 128 + N   (bash's convention)
    """
    if hasattr(os, "waitstatus_to_exitcode"):          # Python 3.9+
        code = os.waitstatus_to_exitcode(status)       # negative means "killed by signal"
        return code if code >= 0 else 128 - code
    if os.WIFSIGNALED(status):                         # older Pythons: decode by hand
        return 128 + os.WTERMSIG(status)
    return os.WEXITSTATUS(status)


def exec_child(argv, redirs=()):
    """Runs inside the child process. Becomes the program, or exits. Never returns."""
    code = 127
    try:
        # Milestone 5: ignored signals survive exec, so put the defaults back.
        signal.signal(signal.SIGINT, signal.SIG_DFL)
        signal.signal(signal.SIGPIPE, signal.SIG_DFL)   # Python ignores SIGPIPE at startup
        # Milestone 3: wire up files before the program starts.
        apply_redirections(redirs)
        os.execvp(argv[0], argv)                        # on success this never returns
    except FileNotFoundError:
        os.write(2, f"sh: {argv[0]}: command not found\n".encode())
        code = 127
    except OSError as e:                                # e.g. permission denied
        os.write(2, f"sh: {argv[0]}: {e.strerror}\n".encode())
        code = 126
    except BaseException as e:                          # a bug of ours: still must not escape
        os.write(2, f"sh: internal error in child: {e!r}\n".encode())
        code = 126
    # os._exit, not sys.exit: sys.exit would run the PARENT's cleanup code and
    # unwind into the shell's main loop, leaving two shells reading your keyboard.
    os._exit(code)


def run_command(argv, redirs=()):
    """Run one external command and wait for it. Returns its exit code."""
    sys.stdout.flush()                  # don't let buffered text be copied into the child
    sys.stderr.flush()
    pid = os.fork()
    if pid == 0:
        exec_child(argv, redirs)        # never returns
    _, status = os.waitpid(pid, 0)
    return decode_status(status)

Notice what fork bought you. The child inherited your working directory, your environment variables, and your open files, including standard input, output and error. That is why echo hi printed into your terminal without you doing anything: the child's file descriptor 1 is the very same terminal your shell has (chapter 8 called this the open file description).

Milestone 2: builtins, or why cd is special

Try to write cd the way you wrote everything else: fork a child, and exec a program called cd in it. It "works" and does nothing. A process's current working directory belongs to that process. The child changes its own directory, then exits, and the shell is exactly where it started. A child cannot change its parent's state, for the same reason one program cannot reach into another's memory.

So cd has to be a builtin: the shell calls os.chdir on itself. exit is the same story: only the shell can decide the shell should stop. (A few more, like export and ulimit, are builtins for the same reason: they change the shell's own state.)

Your builtins should return a status like any command: 0 on success, 1 if the directory does not exist. For exit, raise the provided ShellExit exception rather than calling sys.exit. The main loop catches it, and so does the test, so nothing kills the checker.

class ShellExit(Exception):
    """Raised by the `exit` builtin so the main loop (or a test) can stop."""

    def __init__(self, code=0):
        super().__init__(code)
        self.code = code


def run_builtin(argv):
    """Run `cd` or `exit` in this process. Return its status, or None if argv is not a builtin."""
    name = argv[0]
    if name == "cd":
        target = argv[1] if len(argv) > 1 else os.environ.get("HOME", "/")
        try:
            os.chdir(target)            # changes THIS process's working directory
        except OSError as e:
            print(f"sh: cd: {target}: {e.strerror}", file=sys.stderr)
            return 1
        return 0
    if name == "exit":
        try:
            code = int(argv[1]) if len(argv) > 1 else 0
        except ValueError:
            print("sh: exit: numeric argument required", file=sys.stderr)
            code = 2
        raise ShellExit(code)
    return None

Milestone 3: redirection

When you write sort < in.txt > out.txt, sort has no idea. It reads file descriptor 0 and writes file descriptor 1, as every program does (chapter 8). The shell arranges for those two numbers to point at files before sort starts. The trick is in the gap between fork and exec, where the child is still your code but will soon be the other program, and file descriptors survive exec.

For > out.txt, in the child:

  1. fd = os.open("out.txt", os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o666) opens the file (creating or emptying it) and gets a fresh descriptor, maybe 3.
  2. os.dup2(fd, 1) makes descriptor 1 refer to the same open file. The old terminal behind descriptor 1 is dropped.
  3. os.close(fd) closes the extra number 3. You do not need it any more.

The three operators differ only in the flags and the target descriptor: < opens read-only and wires descriptor 0; > truncates; >> uses O_APPEND instead of O_TRUNC so each write goes to the end.

Why it must happen in the child

If the shell did the dup2, its own output would vanish into the file too, and it would have to undo the change afterwards. In the child, the change is confined to a process that is about to be replaced. (Builtins run inside the shell itself, so a real shell does need that undo dance for something like pwd > file. Your shell skips it and ignores redirections on builtins.)

Solution spoiler 
def parse_redirections(tokens):
    """Split a command's tokens into (argv, redirs).

    redirs is a list of (op, path) with op in "<", ">", ">>".
    Raises ValueError if an operator has no file name after it.
    """
    argv, redirs = [], []
    i = 0
    while i < len(tokens):
        tok = tokens[i]
        if tok in ("<", ">", ">>"):
            if i + 1 >= len(tokens) or tokens[i + 1] in ("<", ">", ">>", "|"):
                raise ValueError(f"syntax error: expected a file name after {tok}")
            redirs.append((tok, tokens[i + 1]))
            i += 2
        else:
            argv.append(tok)
            i += 1
    return argv, redirs


def apply_redirections(redirs):
    """In the child: point fd 0 or fd 1 at the named files."""
    for op, path in redirs:
        if op == "<":
            flags, target_fd = os.O_RDONLY, 0
        elif op == ">":
            flags, target_fd = os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 1
        else:  # ">>"
            flags, target_fd = os.O_WRONLY | os.O_CREAT | os.O_APPEND, 1
        try:
            fd = os.open(path, flags, 0o666)
        except OSError as e:
            os.write(2, f"sh: {path}: {e.strerror}\n".encode())
            os._exit(1)
        os.dup2(fd, target_fd)          # now fd 0/1 refers to the file
        os.close(fd)                    # the extra descriptor is no longer needed

Milestone 4: pipes

A pipe is a one-way tube inside the kernel: bytes written into one end come out of the other, in order. os.pipe() returns two file descriptors, (read_end, write_end). To run printf ... | sort -r | head -n 2 you:

  1. create a pipe for each | (two pipes for three commands);
  2. fork one child per command;
  3. in each child, dup2 the previous pipe's read end onto 0, and this pipe's write end onto 1, exactly like redirection but with a pipe instead of a file;
  4. in the shell, wait for all the children, and report the status of the last one.

Now the bug that has bitten every shell author. A reader sees end-of-file only when no process anywhere still has the write end open. fork copies the whole descriptor table, so after you create a pipe and fork, the pipe's write end is open in the shell and in the child. When printf finishes, its copy closes, but the shell's copy is still open, so sort waits forever for more bytes that nobody will ever send. The pipeline hangs with no error.

The rule: after wiring, close every pipe descriptor you do not need, in every process. In the shell, close the write end right after forking its writer, and close the read end right after forking its reader. In the child, after the dup2 calls, close the originals (descriptors 0 and 1 now carry the same pipes).

A Python wrinkle, honestly

Since Python 3.4, descriptors made by os.pipe() and os.open() are non-inheritable: they are closed automatically at exec. That is why the child's stray copies would vanish when it execs. The copy in the shell never execs, so it is the one that hangs your pipeline. In C, or with dup2's copies, nothing saves you, so close everything explicitly anyway. It is the habit that works in every language.

Because a pipeline's stages run at the same time, you must fork all of them first, then wait. If you waited for each stage before starting the next, a producer that fills the pipe's buffer (roughly 64 KiB on Linux; the exact size varies) would block forever, with nobody reading.

Solution spoiler 
def split_pipeline(tokens):
    """Split tokens on '|' into a list of per-command token lists.

    Raises ValueError if any command is empty ("| foo", "foo |", "a | | b").
    """
    stages, current = [], []
    for tok in tokens:
        if tok == "|":
            if not current:
                raise ValueError("syntax error near |")
            stages.append(current)
            current = []
        else:
            current.append(tok)
    if not current:
        raise ValueError("syntax error near |")
    stages.append(current)
    return stages


def run_pipeline(stages):
    """Run [(argv, redirs), ...] connected by pipes. Returns the LAST command's status."""
    sys.stdout.flush()
    sys.stderr.flush()
    pids = []
    prev_read = None                            # read end of the previous pipe
    for i, (argv, redirs) in enumerate(stages):
        is_last = i == len(stages) - 1
        read_end = write_end = None
        if not is_last:
            read_end, write_end = os.pipe()
        pid = os.fork()
        if pid == 0:
            # --- child: wire stdin/stdout, then close EVERY pipe descriptor we hold
            if prev_read is not None:
                os.dup2(prev_read, 0)
            if write_end is not None:
                os.dup2(write_end, 1)
            for fd in (prev_read, read_end, write_end):
                if fd is not None:
                    os.close(fd)                # the dup2 copies on 0/1 are enough
            exec_child(argv, redirs)
        # --- parent
        pids.append(pid)
        if prev_read is not None:
            os.close(prev_read)                 # this pipe is fully handed over
        if write_end is not None:
            os.close(write_end)                 # CRUCIAL: else the next reader never sees EOF
        prev_read = read_end
    status = 0
    for pid in pids:
        _, st = os.waitpid(pid, 0)
        status = decode_status(st)              # keep the last one
    return status

Milestone 5: Ctrl-C

When you press Ctrl-C, the terminal (more precisely, the kernel's terminal driver) sends SIGINT (chapter 5, signals) to every process in the terminal's foreground process group. A process group is simply a set of related processes that can be signalled together; a job such as a | b | c is a group. Your shell and the children it forks start out in the same group, so Ctrl-C is delivered to all of them, including the shell. Python's default reaction to SIGINT is to raise KeyboardInterrupt and your shell would die along with the command you wanted to stop.

The fix has two halves, and the second half is the one people miss:

  1. The shell ignores SIGINT: signal.signal(signal.SIGINT, signal.SIG_IGN), once, at startup.
  2. Each child puts the default back before exec: signal.signal(signal.SIGINT, signal.SIG_DFL). Why? Across exec, a signal that was set to ignored stays ignored, while a signal with a handler function is reset to the default (the old handler's code no longer exists). The child inherits "ignore" from the shell, and unless you undo it, sleep would shrug off Ctrl-C too.

One more inherited setting hides here. Python itself sets SIGPIPE to "ignore" at startup, so a program like yes in yes | head -n 1 would get an error instead of quietly dying when head exits. Restore SIGPIPE to its default in the child too. (Python's subprocess module does this for you with restore_signals=True.)

What real shells do, and what we skip

A real interactive shell puts each job in its own process group (setpgid) and hands it the terminal (tcsetpgrp). That way Ctrl-C reaches only the foreground job, and background jobs started with & are not disturbed. Our shell has no background jobs, so one shared group is correct and much simpler. It is a good stretch goal.

def run_line(line):
    """Run one line of input. Returns the exit status (see the conventions at the top)."""
    try:
        tokens = tokenize(line)
        if not tokens:
            return 0
        stages = [parse_redirections(s) for s in split_pipeline(tokens)]
        if any(not argv for argv, _ in stages):
            raise ValueError("syntax error: missing command")
    except ValueError as e:
        print(f"sh: {e}", file=sys.stderr)
        return 2
    if len(stages) == 1:
        argv, redirs = stages[0]
        status = run_builtin(argv)              # builtins only run when alone on the line
        if status is not None:
            return status
        return run_command(argv, redirs)
    return run_pipeline(stages)

Look under the hood

Run your shell (python3 solution.py) and start something slow, like sleep 30 | sleep 30. In a second terminal, ask the OS what it sees. These commands only read:

$ ps -o pid,ppid,pgid,stat,command | grep -E "solution|sleep"
41200 40100 41200 S+   python3 solution.py
41207 41200 41200 S+   sleep 30
41208 41200 41200 S+   sleep 30

The columns are PID, parent PID, process-group ID and state. That output is illustrative; your numbers will differ (the same command works on macOS and Linux). Check three things:

  • Both sleep processes have PPID equal to the shell's PID: the shell is their parent.
  • All three share one PGID: one process group, which is why Ctrl-C reaches them all.
  • After a child exits but before the shell calls waitpid, it would show state Z (a zombie). Your shell reaps each child immediately, so you will rarely catch one. Try removing the waitpid loop in a copy and watch them pile up.

Now look at the pipe itself. While sleep 30 | sleep 30 runs, list the shell's open files (macOS: lsof -p SHELL_PID; Linux: ls -l /proc/SHELL_PID/fd). After your parent-side close calls, the shell should hold no extra pipe descriptors. Comment those lines out and look again: the pipe ends are still open in the shell, and that is the hang.

Try it yourself: four experiments

  1. Watch exec happen (Linux). strace -f -e trace=clone,fork,vfork,execve,pipe2,dup2,wait4 python3 solution.py, then type echo hi | cat. You will see the pipe2, two clones, two dup2 pairs, two execve calls, and the waits. (On macOS, dtruss needs system protection turned off, so skip it.)
  2. Ignored survives exec, handlers do not. In your shell try sh -c 'kill -INT $$; echo still here'. The child sh kills itself with SIGINT (status 130). Now temporarily delete your SIG_DFL line in exec_child, run it again, and see still here print: the signal was inherited as "ignored".
  3. Pipes block. Run yes | head -n 3 (it stops, thanks to SIGPIPE), then sleep 2 | echo fast: fast appears at once, yet the prompt returns only after two seconds, because the shell waits for all stages.
  4. Exit codes are data. Run sh -c 'kill -9 $$' and check you get 137 (128 + 9). Many tools and container platforms show this number, and it nearly always means "killed with SIGKILL".

Stretch goals

  • Background jobs: a trailing & means "don't wait". Skip waitpid, remember the PID, and reap finished jobs later with os.waitpid(-1, os.WNOHANG). Without that, they become zombies.
  • Real job control: give each pipeline its own process group with os.setpgid and hand it the terminal with os.tcsetpgrp. Now Ctrl-C reaches only the foreground job, and the shell no longer needs to ignore SIGINT while waiting. (Mind SIGTTOU.)
  • stderr redirection: add 2> and 2>&1. The second one is a single dup2(1, 2), and its position relative to > matters. Why does cmd > f 2>&1 differ from cmd 2>&1 > f?
  • Quoting that survives: echo '|' currently looks like a pipe. Make tokenize remember which tokens were quoted.
  • Variables and wildcards: expand $HOME with os.path.expandvars and *.py with the glob module. A real shell, not the program, does this: ls *.py hands ls the already-expanded list.
  • ;, && and ||: run several commands per line, using the exit status as the condition. Exit codes become a tiny control-flow language.
  • Builtin export, pwd, cd -, and Ctrl-C at the prompt: redraw the prompt instead of ignoring the key. Try import readline for line editing and history.

Distributed systems connection

You have just built the smallest process supervisor. Container runtimes, init systems, CI runners and cluster agents all do the same loop: start a process, wait for it, look at the exit status, and decide what to do (restart? alert? give up?). The exit-status convention you used (0 is success, 127 is "not found", 128+N is "killed by signal N") is what makes that automation possible, and it is why 137 in a dashboard usually means "somebody sent SIGKILL" and 143 means "asked politely with SIGTERM" (graceful shutdown). And a Unix pipeline is a streaming system with backpressure built in: when sort is slow, the pipe fills, and printf's write blocks until there is room. Chapter 14 on queues and backpressure shows why that blocking is a feature, and what happens when a queue between machines has no such limit.

What you learned

  • A shell is a loop of fork (clone), exec (become another program) and waitpid (collect the exit status). Code after a successful exec never runs, so a child must always end in os._exit.
  • A child cannot change its parent's state, which is why cd and exit are builtins.
  • Redirection is open plus dup2 in the child, between fork and exec. Programs never know. File descriptors survive exec.
  • A pipe reaches end-of-file only when every copy of its write end is closed, so close the ends you do not use in every process.
  • Ctrl-C goes to the whole foreground process group. The shell ignores it; each child must restore the default before exec, because "ignored" survives exec.
  • Exit status is the contract between programs: 0 success, 127 not found, 128 + N killed by signal N.

You implement cd by forking a child that calls os.chdir(path) and then exits. After cd /tmp, what does the shell's next pwd show?

  1. /tmp, because the child and parent share a working directory
  2. The old directory, because each process has its own working directory and the child changed only its own
  3. An error, because a child may not call chdir
  4. /, because exiting resets the directory
The working directory is per-process state. fork copies it into the child, after which they are independent. The child's change dies with the child. Only the shell itself can change the shell's directory, which is why cd is a builtin.

Your pipeline printf 'a\nb\n' | sort prints nothing and hangs. printf has already exited. What is the most likely bug?

  1. sort is too slow for such a short input
  2. The pipe buffer is full
  3. The shell still has the pipe's write end open, so sort never sees end-of-file
  4. printf wrote to the terminal instead of the pipe
End-of-file on a pipe means "every copy of the write end is closed". The shell's own copy, made when it called os.pipe(), is still open, so the kernel keeps sort waiting for more data. Closing the unused ends in the shell (and in the children) fixes it.

In the child, right after os.execvp("nonexistent", ...) raises FileNotFoundError, why must the code end with os._exit(127) rather than just continuing?

  1. The child is still a full copy of the shell; if it carried on, it would return into the shell's prompt loop and two shells would read your keyboard
  2. Python refuses to run any more code after a failed exec
  3. os._exit is the only way to print an error message
  4. The parent can only wait for children that call os._exit
After fork, both processes run the same code from the same point. The parent's branch continues the loop; the child's branch must never do so. os._exit ends the child at once without running the parent's cleanup or unwinding through the shell's loop.

Your shell ignores SIGINT but you forget to reset it in the child. You run sleep 100 and press Ctrl-C. What happens?

  1. The shell dies and sleep keeps running
  2. Both die
  3. Both ignore it, but the shell prints a warning
  4. sleep ignores the Ctrl-C too, because ignored signals stay ignored across exec, and you are stuck for 100 seconds
Handlers are reset by exec (the handler code is gone), but "ignore" is just a flag in the process, and it is carried over. So the child inherits the shell's choice. Restoring SIG_DFL between fork and exec gives each program the normal behaviour.

Lab 3: Races & Locks

In the chapters you read about lost updates, locks, deadlocks and blocking queues. Here you make each of them happen, on purpose, in about 150 lines of Python. First you lose some updates. Then you stop losing them. Then you freeze two threads against each other, and un-freeze them with one small rule. Finally you build the queue that sits between almost every pair of cooperating threads.

Why this lab matters

Concurrency bugs have a reputation for being random and unreproducible. That reputation is only half deserved. A race is a bug that needs a particular interleaving, and if you control the interleaving you control the bug. In this lab you will make a race appear in nearly every run, and you will make a deadlock announce itself with a timeout instead of freezing your terminal. Those two tricks, forcing the bad schedule and bounding every wait, are how people test concurrent code for real.

What you'll build

  1. Lose updates on purpose: write a counter whose increment() is read, yield, write, and watch eight threads lose most of their work.
  2. Fix it with a lock: the same three steps inside a threading.Lock, and the answer is exact every time.
  3. Bank transfers: lock two accounts, deadlock when two transfers go in opposite directions (detected with acquire(timeout=…)), then fix it with a global lock order.
  4. A bounded blocking queue: put waits when full, get waits when empty, built from a threading.Condition.
  5. Optional, check-then-act: fix a "reserve a seat" function that sells the same seat to several people.

0/5 milestones passing

Two testing tricks you'll use all lab

  • Force the interleaving. time.sleep(0) asks Python to give another thread a turn right now. Putting it between a read and a write turns a bug that might appear once a week into one that appears in nearly every run. The check also uses a threading.Barrier so that several threads start the same instant.
  • Never wait without a timeout. A deadlocked test that freezes your terminal teaches nothing. Every wait in check.py has a limit, and every thread it starts is a daemon thread, so even a completely stuck solution ends in a ✘ message and not a hang. Your own code should use acquire(timeout=…) in the same spirit.

Milestone 1: make a lost update happen

In chapter 11 (the sections "One line, three steps" and "The lost update") you saw that counter += 1 is really three steps: read the old value, add one, write the result back. If thread B reads between thread A's read and write, both write the same new number and one increment vanishes. Chapter 11 also explained why the GIL doesn't save you: Python can switch threads between bytecode instructions, so those three steps are not one indivisible unit.

On a recent CPython a plain self.value += 1 can lose updates only rarely, because the interpreter usually switches threads only every few milliseconds. A rare bug is a bad thing to learn from. So we make the switch happen exactly where it hurts:

  1. Read the current value into a local variable.
  2. time.sleep(0): sleeping for zero seconds still releases the GIL and lets another thread run.
  3. Write the local value plus one.

The check never asks for an exact number

How many updates get lost depends on the machine, the Python version and what else is running. So check.py only asks: across five seeded runs, did at least one lose updates, and did the counter never exceed the expected total? A good rule for any test of concurrent code: assert on what must be true (never more than expected), and on what is overwhelmingly likely (some loss), never on a precise racy number.

Your task

Implement UnsafeCounter.increment() in starter.py as read, time.sleep(0), write. No lock.

python3 check.py shows ✔ for milestone 1 and tells you how many of the five runs lost updates. Then run python3 starter.py: the first line shows eight threads each adding 1,000 times and getting far less than 8,000.

Hints try without first
  • Use a local variable, for example v = self.value, and later self.value = v + 1. If you write self.value = self.value + 1 after the sleep, you read the fresh value again and the race mostly disappears. The stale local copy is the whole point.
  • The lost updates are not "random corruption". Each lost increment is a thread writing back an answer that was already out of date when it wrote it.
Solution spoiler 
class UnsafeCounter:
    def __init__(self):
        self.value = 0

    def increment(self):
        v = self.value          # step 1: read
        time.sleep(0)           # step 2: yield the CPU (and the GIL) right here
        self.value = v + 1      # step 3: write back a possibly stale answer

Milestone 2: fix it with a lock

The three steps are a critical section: code that must not be interleaved with itself (chapter 12, "Critical sections and the mutex"). A mutex (Python calls it threading.Lock) makes that true: only one thread at a time can hold it, and everyone else waits. In Python you almost always use it with with, which releases the lock even if the code inside raises an exception.

Common misconception: "lock the write"

The lock must cover the whole read-modify-write, not just the final assignment. If thread A holds the lock only while writing, thread B can still read a stale value in between. The rule is: whatever must appear to happen "all at once" goes under one lock. That is also why the check lets you keep the time.sleep(0) inside the lock. An invitation to switch threads is harmless when everyone else is waiting at the door.

Your task

In SafeCounter, create a lock in __init__, and make increment() do the same read, sleep(0), write inside with self._lock:.

Hints try without first
  • self._lock = threading.Lock() in __init__. One lock per counter object, shared by every thread that uses it. A new lock created inside increment would protect nothing.
  • Copy your milestone 1 body and indent it under with self._lock:.
Solution spoiler 
class SafeCounter:
    def __init__(self):
        self.value = 0
        self._lock = threading.Lock()

    def increment(self):
        with self._lock:        # only one thread at a time may run the three steps
            v = self.value
            time.sleep(0)       # same yield as before: it no longer matters
            self.value = v + 1

Milestone 3: bank transfers, a deadlock, and its fix

Now two locks. A bank transfer must debit one account and credit another as one unit, so the safe-looking approach is to lock both accounts first. The trap is in the order. Look at what happens when Alice sends money to Bob at the same moment Bob sends money to Alice (chapter 13, "Two threads, two locks"):

With real locks this freezes forever, which is useless for a test. The fix for detecting it is lock.acquire(timeout=1.0): it waits up to a second and returns False if it could not get the lock. A timeout does not cure a deadlock, but it turns "silent freeze" into "an error you can see", and it is how real systems notice stuck locks too. Your transfer_naive raises LockTimeout when that happens.

The cure is chapter 13's "The practical fix: lock ordering". The cycle needs one thread to take A then B while another takes B then A. If every transfer locks the account with the smaller id first, no thread ever holds a higher-numbered lock while waiting for a lower one, so a cycle cannot form. Which account is the source and which is the destination no longer affects the locking order.

Where does the pause come from?

Without help, the two opposite transfers usually finish before the other thread even starts, and you'd see no deadlock. Both transfer functions therefore take a pause argument and sleep that long between taking the first and the second lock. That is the same trick as sleep(0) in milestone 1: it widens the dangerous window so the bad interleaving is reliable. In production code you never add it, and you need to be able to find the bug without it.

Your task

Implement transfer_naive(src, dst, amount, pause, timeout) and transfer_ordered(...). Both return True if the money moved and False if src has too little. Both raise LockTimeout if a lock cannot be acquired in time, and both must release every lock they took even when they raise.

milestone 3 shows ✔. Behind it, check.py (a) runs two opposite transfers against transfer_naive and requires a LockTimeout; (b) runs the same pair against transfer_ordered and requires both to succeed; (c) runs 20,000 random transfers from 8 threads among 6 accounts and checks that no thread timed out, the total is still 6,000, no balance went negative and every lock is free at the end.

Hints try without first
  • The shape is two nested try/finally blocks. Acquire the first lock, then try:; inside it acquire the second, then another try: with the transfer; the finally clauses release in reverse order. A LockTimeout raised while holding the first lock must still release it.
  • acquire(timeout=t) returns True or False. It does not raise. You decide to raise LockTimeout when it returns False.
  • For the ordered version: first, second = (src, dst) if src.id < dst.id else (dst, src). Lock first, then second. Move the money using src and dst exactly as before.
  • Transferring from an account to itself would try to take the same plain Lock twice and block on yourself. The ordered version raises ValueError for that case.
  • Do the balance check and the update while holding both locks. Checking src.balance before locking is a check-then-act race (see milestone 5).
Solution spoiler 
def transfer_naive(src, dst, amount, pause=0.0, timeout=1.0):
    if not src.lock.acquire(timeout=timeout):
        raise LockTimeout(f"could not lock account {src.id}")
    try:
        time.sleep(pause)                       # widens the window so the deadlock is reliable
        if not dst.lock.acquire(timeout=timeout):
            raise LockTimeout(f"could not lock account {dst.id} while holding {src.id}")
        try:
            if src.balance < amount:
                return False
            src.balance -= amount
            dst.balance += amount
            return True
        finally:
            dst.lock.release()
    finally:
        src.lock.release()                      # always runs, even after a LockTimeout

def transfer_ordered(src, dst, amount, pause=0.0, timeout=5.0):
    if src is dst:
        raise ValueError("cannot transfer to the same account")
    first, second = (src, dst) if src.id < dst.id else (dst, src)
    if not first.lock.acquire(timeout=timeout):
        raise LockTimeout(f"could not lock account {first.id}")
    try:
        time.sleep(pause)
        if not second.lock.acquire(timeout=timeout):
            raise LockTimeout(f"could not lock account {second.id} while holding {first.id}")
        try:
            if src.balance < amount:
                return False
            src.balance -= amount
            dst.balance += amount
            return True
        finally:
            second.lock.release()
    finally:
        first.lock.release()

Milestone 4: a bounded blocking queue

A bounded buffer is the most common structure in concurrent programs: producers put work in, consumers take it out, and the limit stops the producers from racing ahead (chapter 14, "Producer and consumer" and "Backpressure strategies"). Python ships queue.Queue, but building one yourself shows exactly where each rule comes from. The tool is the condition variable from chapter 12 ("Condition variables: waiting for something to happen").

You need one lock and two conditions that share it: _not_full (producers sleep here) and _not_empty (consumers sleep here). Both use the same lock because both guard the same list.

CallIf it cannot proceedWhen it succeeds
put(item, timeout)wait on _not_full while the queue is full; raise queue.Full when the timeout runs outappend, then _not_empty.notify()
get(timeout)wait on _not_empty while it is empty; raise queue.Empty when the timeout runs outpop the oldest, then _not_full.notify()

Why a while loop, never an if

When wait() returns, you only know that someone notified. By the time you get the lock back, another thread may already have taken the item or the free slot. Condition variables are also allowed to wake a waiter for no reason at all (a "spurious wakeup"), and portable code has to expect that. So the condition is always rechecked in a while loop: while the queue is full: wait. The check has a test for this: three consumers wait, one item arrives, and exactly one may get it. With an if the other two try to pop from an empty list and crash.

With a timeout, wait(t) may be called several times (after each wakeup that fails the recheck), so you cannot just pass the original timeout each time. Compute a deadline once, with time.monotonic() + timeout, and each time round the loop wait only for the time that remains. monotonic is right for durations because it never jumps backwards when the wall clock is adjusted.

Hints try without first
  • lock = threading.Lock(), then threading.Condition(lock) twice. With both conditions on one lock, with self._lock: and with self._not_full: mean the same thing.
  • collections.deque gives you append and popleft in constant time. list.pop(0) shifts every element.
  • Loop shape for put: while len(items) >= maxsize: then, if there is no deadline, wait(); otherwise compute remaining = deadline - time.monotonic(), raise queue.Full if it is <= 0, else wait(remaining).
  • A timeout of 0 should raise at once if the queue is full, which falls out of the same code.
  • Use notify() (one waiter) because each put frees one consumer and each get frees one producer. If you use notify_all() everything still works, just with more wakeups that find nothing to do.
Solution spoiler 
class BoundedQueue:
    def __init__(self, maxsize):
        if maxsize < 1:
            raise ValueError("maxsize must be at least 1")
        self.maxsize = maxsize
        self._items = collections.deque()
        self._lock = threading.Lock()
        # Two conditions sharing ONE lock: producers wait on not_full, consumers on not_empty.
        self._not_full = threading.Condition(self._lock)
        self._not_empty = threading.Condition(self._lock)

    def put(self, item, timeout=None):
        deadline = None if timeout is None else time.monotonic() + timeout
        with self._lock:
            while len(self._items) >= self.maxsize:     # WHILE, not if: re-check after waking
                if deadline is None:
                    self._not_full.wait()
                else:
                    remaining = deadline - time.monotonic()
                    if remaining <= 0:
                        raise queue.Full
                    self._not_full.wait(remaining)
            self._items.append(item)
            self._not_empty.notify()                    # one consumer can proceed

    def get(self, timeout=None):
        deadline = None if timeout is None else time.monotonic() + timeout
        with self._lock:
            while not self._items:
                if deadline is None:
                    self._not_empty.wait()
                else:
                    remaining = deadline - time.monotonic()
                    if remaining <= 0:
                        raise queue.Empty
                    self._not_empty.wait(remaining)
            item = self._items.popleft()
            self._not_full.notify()                     # one producer can proceed
            return item

    def qsize(self):
        with self._lock:
            return len(self._items)

Milestone 5 (optional): check-then-act

Hints try without first
  • The check and the act must sit under the same lock acquisition: with self._lock: around both the in test and the assignment.
  • There is a lock-free alternative worth knowing: self._owners.setdefault(seat, who) does check and insert as one operation inside CPython's dict, and returns the owner that ended up there. Compare it with who. Which style would still work in a language where you can't rely on that?
Solution spoiler 
def reserve(self, seat, who):
    with self._lock:
        if seat in self._owners:
            return False
        self._owners[seat] = who
        return True

Distributed systems connection

Every bug in this lab comes back when the threads become machines. Two services doing "read the balance, add 10, write it back" lose updates exactly like your UnsafeCounter; databases answer with transactions, version numbers and compare-and-swap (chapter 11, "The same bug across machines"). A distributed lock has your acquire(timeout=…) problem in a nastier form: the holder may die, or just pause, and still think it owns the lock, which is why real systems use leases and fencing tokens (chapter 12, "Locks across machines"). Transfers between accounts on different servers cannot take two in-process locks, so they need protocols like two-phase commit, and deadlock detection moves from a timeout to a global wait-for graph. And your BoundedQueue, with its blocking put, is the smallest possible form of the backpressure that systems like message queues use to keep a slow consumer from being buried. Lab 4 builds on it next.

What you learned

  • A lost update is three steps interleaved badly. You can make it near-certain by yielding between the read and the write, which is also how you test for it.
  • A lock fixes it only if it covers the whole read-modify-write, and every thread that touches the data uses the same lock.
  • Two locks taken in opposite orders can deadlock. A timeout turns the freeze into an error, and a global lock order (by account id) prevents the cycle altogether.
  • Always release in finally (or use with), including on the timeout path.
  • A condition variable lets a thread sleep until something is true. Always recheck the condition in a while loop, and track a deadline when you have a timeout.
  • A check followed by an act is a race unless one lock, or one atomic operation, covers both.
  • Good tests of concurrent code assert on invariants (total money, no lost or duplicated items, never over the bound), never on exact racy numbers.

Check your understanding

Your lost-update test for UnsafeCounter asserts that the result is exactly 7,311, the number you saw when you wrote the test. What is wrong with it?

  1. Nothing; a seeded test is deterministic
  2. The number of lost updates depends on thread scheduling, which the seed does not control, so it will differ between runs and machines
  3. Python's random module is not thread-safe
  4. Lost updates only happen on the first run
The seed controls the random numbers you draw, not when the operating system and the interpreter switch threads. The robust assertions are: the result is never above the expected total, and over several runs at least one falls below it.

Thread 1 runs transfer(A, B) while thread 2 runs transfer(B, A), and both lock the source first. Which sentence best describes why ordering locks by account id fixes the deadlock?

  1. It makes each lock be held for a shorter time
  2. It lets both threads hold both locks at once
  3. Every thread now takes the locks in the same global order, so no thread can hold a later lock while waiting for an earlier one, and a cycle of waiting cannot form
  4. It makes acquire return faster
Deadlock needs a cycle in the wait-for graph. If all threads acquire in increasing id order, every "waits for" arrow points from a lower-numbered lock holder to a higher-numbered lock, and arrows that always go upward can never loop back. The lock's hold time is unchanged.

In BoundedQueue.get, why is the wait written as while not self._items: self._not_empty.wait() and not if not self._items: ...?

  1. After waking up, another consumer may already have taken the item, or the wakeup may have been spurious, so the condition must be rechecked while holding the lock
  2. Because if is slower than while
  3. Because wait() never returns without a timeout
  4. Because the lock is released while the condition is being checked
A notification is a hint that the state might have changed, not a guarantee that it is still what you need by the time you get the lock back. The loop turns "I was woken" into "I checked, and it's true".

A function does if seat not in taken: and then taken[seat] = who, with no lock. Which statement is true?

  1. It is safe, because dictionary reads are atomic under the GIL
  2. It is safe, because each of the two lines is atomic by itself, so the pair is too
  3. It is unsafe only if the dictionary is very large
  4. It is unsafe: two threads can both pass the check before either assigns, so both are told they got the seat
Each line may be atomic, but the pair is not. This is check-then-act. The fix is one lock around both lines, or a single atomic operation such as dict.setdefault.

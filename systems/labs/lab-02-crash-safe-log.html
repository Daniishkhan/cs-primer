Lab 2: Crash-Safe Storage

Databases, message queues and even your editor's save button all make the same promise: if I told you it was saved, it is saved, even if the program dies a millisecond later. In this lab you will keep that promise yourself. You will build an append-only log with checksums, teach it to heal after a crash, control exactly when it calls fsync, and then try to break it by killing it for real.

Why this lab matters

The previous chapters said a successful write() does not mean the data is safe. Here you find out what that costs and what it buys. A checksummed, fsync-ed log is the core of a write-ahead log: the same idea sits inside every serious database, in the log of a replicated state machine, and in the way a good program saves its settings file. If you can build this, you understand what "durable" means.

POSIX only

The lab uses fsync, SIGKILL and a file descriptor for a directory, so it runs on macOS, Linux and WSL. On plain Windows, check.py says so and stops. Python 3.8 or newer, standard library only.

What this lab's crash test can and cannot prove

Milestone 4 kills a process with SIGKILL. That is a real, abrupt death: no cleanup code runs, no buffers are flushed, no finally block executes. But SIGKILL kills the process, not the kernel. Everything the process had already handed to write() still sits in the operating system's page cache and will reach the disk anyway. So this test checks your recovery logic, record format and ordering. It cannot check that your fsync calls really work, because the data would survive without them.

Testing real power loss needs a virtual machine you can hard-stop, or special tooling that drops writes (databases are tested that way). To make up for it, this lab adds a second test that simulates torn writes by cutting a log file at random byte offsets and flipping random bits. And it checks your fsync calls differently: by counting them and checking their order.

What you'll build

Five milestones, each building on the last:

  1. The log: a record format (length, CRC32, payload) and append / read_all.
  2. Recovery: on open, find and cut off a torn or corrupt tail.
  3. Durability policy: fsync always, in batches (group commit), or never; and measure what each costs.
  4. Crash tests: kill a real writer process five times, and cut files at random offsets. Nothing acknowledged may be lost.
  5. Atomic replace: save a config file with temp file, fsync, os.replace, and a directory fsync.

Milestone 1: records you can tell apart

A log file is a long run of bytes. To read it back you must know where one record ends and the next begins, and you must be able to tell a real record from junk. So each record carries a small header:

Why each field?

  • length tells the reader how many payload bytes follow. Without it you could not read variable-sized records (and a payload might contain any byte, so you cannot use a separator).
  • CRC32 is a checksum (chapter 9, Detecting torn data with checksums): a number computed from the bytes. If even one bit changes, the CRC almost certainly changes, so a half-written or damaged record is caught. Python has it in zlib.crc32. Computing the checksum over the length bytes and the payload also catches a damaged length field, which would otherwise make the reader jump to a random place.
  • Integers are written big-endian with struct.pack(">I", n) (the > means big-endian, I a 4-byte unsigned integer), so the file reads the same on every machine.

The log's methods write with the raw os.write on a file descriptor, not Python's buffered open() file objects. That removes one layer of buffering (chapter 8, Three layers of buffering): when os.write returns, the bytes are in the kernel. The file is opened with O_APPEND so every write lands at the end. append must return the offset where the record starts (the file size before the write): that is how a database later finds a record without scanning.

Hints try without first
  • zlib.crc32(data, start) continues a checksum from a previous value: crc32(payload, crc32(length_bytes)) is the CRC of length_bytes + payload.
  • Write the whole record (header and payload together) with one write_all call. Fewer separate writes means fewer places a crash can cut.
  • read_all opens the file by self.path in "rb" mode, reads everything and hands it to scan_records. Append mode never moves your read position, because you read through a separate file object.
  • An empty payload is legal: a record of length 0 still has an 8-byte header.

def encode_record(payload):
    """Return the bytes to write for one record: length, crc, payload."""
    length = struct.pack(">I", len(payload))
    crc = zlib.crc32(payload, zlib.crc32(length))      # crc of length bytes, then payload
    return length + struct.pack(">I", crc) + payload


def write_all(fd, data):
    """os.write may write less than asked; loop until everything is written."""
    view = memoryview(data)
    while view:
        n = os.write(fd, view)
        view = view[n:]


class RecordLog:
    def __init__(self, path, fsync="always", batch_size=8):
        if fsync not in ("always", "batch", "never"):
            raise ValueError("fsync must be 'always', 'batch' or 'never'")
        self.path = path
        self.policy = fsync
        self.batch_size = batch_size
        self._unsynced = 0                              # records written but not yet fsynced
        # Raw file descriptor, no Python-level buffer: os.write hands bytes
        # straight to the kernel (the page cache). O_APPEND = always write at the end.
        self._fd = os.open(path, os.O_RDWR | os.O_CREAT | os.O_APPEND, 0o644)
        self._size = os.fstat(self._fd).st_size
        self.recover()                                  # Milestone 2

    def append(self, payload):
        """Append one record. Returns the offset where it starts."""
        offset = self._size
        write_all(self._fd, encode_record(payload))    # ONE write call per record
        self._size += HEADER.size + len(payload)
        self._unsynced += 1
        # Milestone 3: the durability policy decides when the data is forced to disk.
        if self.policy == "always":
            self.flush()
        elif self.policy == "batch" and self._unsynced >= self.batch_size:
            self.flush()
        return offset

    def read_all(self):
        """Return the payloads of every record, oldest first."""
        with open(self.path, "rb") as f:
            payloads, _ = scan_records(f.read())
        return payloads

Milestone 2: recovery

Now the interesting part. Suppose the machine loses power while record 3 is being written. The disk might hold only the first 10 bytes of it. A torn write (chapter 9) is exactly this: a write that was only partly applied. On the next start, the log must recover itself:

  1. Scan from the start. For each position, read the 8-byte header. If fewer than 8 bytes are left, stop. If the length is absurd (bigger than the rest of the file, or more than a sane maximum), stop. If the payload is cut short, stop. If the CRC does not match, stop.
  2. Stop at the first bad record, and throw away everything after it. You might think later records could still be fine. But once one record is damaged you cannot trust that what follows is aligned to a record boundary: the length of the bad record is exactly what you cannot rely on. Keeping a valid prefix is the safe rule, and it is what real write-ahead logs do.
  3. Truncate the file to the end of the last good record with os.ftruncate, and fsync so the repair itself is durable. Now new appends continue cleanly, instead of being added after garbage and then lost behind it.

Why this is safe: the acknowledgement rule

Truncating is only safe because of a rule your application follows: never tell the user "saved" until the record's fsync has returned. A torn tail can then only be a record nobody was ever told about. Throwing it away loses nothing that was promised.

Solution spoiler 
    def recover(self):
        """Drop a torn or corrupt tail. Returns how many bytes were removed."""
        with open(self.path, "rb") as f:
            data = f.read()
        _, good_end = scan_records(data)
        dropped = len(data) - good_end
        if dropped:
            os.ftruncate(self._fd, good_end)
            os.fsync(self._fd)                          # make the repair itself durable
            self._size = good_end
        return dropped
def scan_records(data):
    """Parse `data` as a sequence of records.

    Returns (payloads, good_end): the payloads of every valid record from the
    start, and the byte offset where the valid prefix ends. Stops at the first
    record that is incomplete or fails its checksum.
    """
    payloads = []
    pos = 0
    while pos + HEADER.size <= len(data):
        length, crc = HEADER.unpack_from(data, pos)
        start = pos + HEADER.size
        end = start + length
        if length > MAX_RECORD or end > len(data):      # absurd length, or the payload is cut short
            break
        payload = data[start:end]
        if zlib.crc32(payload, zlib.crc32(data[pos:pos + 4])) != crc:
            break                                       # bit rot or a half-written record
        payloads.append(payload)
        pos = end
    return payloads, pos

Milestone 3: when to call fsync

append so far calls os.write and returns. At that moment the bytes live in the page cache. A power failure would lose them, and your caller might already have said "saved". To be safe, call os.fsync(fd) (chapter 9), which does not return until the kernel has pushed the file's data to the storage device.

But fsync is slow compared with everything else the log does: it waits for the drive. So the log gets a durability policy, a dial between safety and speed:

PolicyWhen it calls fsyncWhat a power failure can lose
"always"after every appendnothing that append returned for
"batch"after every N appends, or when you call flush()up to N-1 recent appends (the ones not yet synced)
"never"only if you call flush()whatever the kernel had not written yet, possibly seconds of data

"Batch" is group commit (chapter 9): many records share one expensive fsync. The catch is the acknowledgement rule from milestone 2. With batch, an append that returns has not promised durability. Only a later flush() (or the batch filling up) does. A careful application acknowledges to its users only after flush(). Real databases do this with many clients at once: a handful of writers wait together, one fsync covers them all, then they are all told "committed".

macOS and the drive's own cache

On macOS, plain fsync hands the data to the drive but does not force the drive to empty its own write cache. fcntl.fcntl(fd, fcntl.F_FULLFSYNC) does, and is much slower. This lab uses plain os.fsync so the numbers stay friendly, but a database that really means it (SQLite offers a fullfsync setting) uses the stronger call. See the stretch goals.

Milestone 4: break it on purpose

A storage layer you have not tried to break is a storage layer you do not trust. This milestone needs no new code from you; it is the test of milestones 1 to 3, built the way real engineers test:

  1. A separate writer process opens the log with fsync="always" and appends numbered records in a loop: 0, 1, 2, and so on. Only after append returns (so after the fsync) does it print that record's number to a pipe. That printed number is an acknowledgement: "record n is durable".
  2. The test process reads acknowledgements, and after a seeded-random number of them (plus a few random milliseconds) sends SIGKILL. The writer dies wherever it happens to be: between records, or in the middle of one.
  3. Reopen the log. Recovery runs. Then check three things: every acknowledged record is present; the records are exactly 0, 1, 2, ... in order with nothing missing in between; and no garbage bytes remain in the file.
  4. Repeat five times, with different kill points.

You will usually see that the log holds one more record than was acknowledged. The writer appended it, got killed before it could print the acknowledgement. That is perfectly fine: the promise is "acknowledged means present", not "present means acknowledged". Nobody was told about that record, and keeping it breaks no promise.

Because of the SIGKILL caveat at the top of this page, the second half of the test does the harsher thing directly: it writes a finished log, then for 49 cut points (some at the interesting edges, such as inside the header, one byte short of a record, exactly on a boundary, plus seeded random ones) it truncates a copy of the file there, opens it, and requires that exactly the whole records before the cut survive. It also flips one random bit in 20 copies of the file and requires that the record containing the flipped bit and everything after it are gone.

def kill_round(path, k, jitter):
    """Start a writer, SIGKILL it after k acks (plus jitter seconds). Returns (acks, killed_ok)."""
    p = subprocess.Popen([sys.executable, os.path.join(HERE, "check.py"), "--writer", target, path],
                         stdout=subprocess.PIPE, stderr=subprocess.PIPE)
    buf = b""
    try:
        deadline = time.time() + 20
        while buf.count(b"\n") < k:
            if time.time() > deadline:
                raise AssertionError("the writer process did not reach its acks in 20 s")
            r, _, _ = select.select([p.stdout], [], [], 0.2)
            if r:
                chunk = os.read(p.stdout.fileno(), 65536)
                if not chunk:
                    err = p.stderr.read().decode()
                    if "NotImplementedError" in err:
                        raise NotStarted(err.strip().splitlines()[-1].split(": ", 1)[-1])
                    raise AssertionError("the writer process stopped by itself:\n" + err.strip()[-500:])
                buf += chunk
        time.sleep(jitter)
        os.kill(p.pid, signal.SIGKILL)          # no cleanup code runs: the process just vanishes
        while True:                              # collect acks that were already in the pipe
            chunk = os.read(p.stdout.fileno(), 65536)
            if not chunk:
                break
            buf += chunk
    finally:
        try:
            os.kill(p.pid, signal.SIGKILL)
        except ProcessLookupError:
            pass
        p.wait()
        p.stdout.close()
        p.stderr.close()
    lines = buf.split(b"\n")[:-1]                # a last partial line was never a complete ack
    return [int(x) for x in lines]

Milestone 5: replacing a file atomically

An append-only log is easy to make safe because you never overwrite anything. But sometimes you must replace a whole file, such as a settings file. The naive way, "open it for writing (which empties it) and write the new contents", is exactly the torn-write trap: a crash after the open and before the write finishes leaves an empty or half-written file, and the old settings are gone.

The standard cure is the atomic replace pattern (chapter 9). Never touch the real file until the new one is complete and safe on disk:

Each step has a reason, and removing any one of them reopens a hole:

  • Write to a temp file in the same directory. rename is atomic only inside one file system, and "same directory" guarantees that.
  • fsync the temp file before the rename. Otherwise the kernel might persist the rename but not yet the data, and after a power failure config.json would exist but be empty or partial.
  • os.replace(tmp, path) atomically swaps the name. Anyone opening config.json sees the old file or the new one, never a mixture. (os.replace overwrites an existing target on POSIX and on Windows; plain os.rename does not on Windows.)
  • fsync the directory. A rename is a change to the directory's contents (chapter 9, The directory needs its own fsync). To make it durable, open the directory with os.open(dirpath, os.O_RDONLY) and call os.fsync on that descriptor.

Platform caveats

  • Opening a directory and fsyncing it works on Linux and macOS, which is what this lab targets. Windows cannot open a directory this way; portable programs skip this step there and rely on other mechanisms.
  • On macOS, the same F_FULLFSYNC caveat as before applies to the file and the directory.
  • Some network and FUSE file systems implement these guarantees loosely or not at all. This is one of those places where "it passed on my laptop" is not evidence.
  • Leftover config.json.tmp files after a crash are harmless but untidy. Real programs delete stale temp files at startup. A fixed temp name also means two writers at once would collide: use a unique name (tempfile.mkstemp(dir=...)) if that can happen.

How do you test "a crash between steps"? You cannot kill a process at an exact line. So save_config takes an optional hook: a function it calls with a stage name after each step. The test passes a hook that raises an exception at the chosen stage, which unwinds out of save_config exactly as if the program had vanished there (no cleanup runs, because you do not handle it). After each simulated crash the test loads the config and demands the old or the new content, never a missing or half-written file.

Solution spoiler 
def save_config(path, config, hook=None):
    """Write `config` (a dict) to `path` so a crash never leaves it missing or half-written.

    `hook(stage)`, if given, is called after each step. Tests raise an exception
    from it to simulate a crash at exactly that point.
    """
    def step(name):
        if hook:
            hook(name)

    data = json.dumps(config, sort_keys=True).encode("utf-8")
    tmp = path + ".tmp"
    fd = os.open(tmp, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)   # same directory = same file system
    try:
        half = len(data) // 2
        write_all(fd, data[:half])
        step("tmp_partial")                  # a crash here leaves a half file, but only the temp one
        write_all(fd, data[half:])
        step("tmp_written")
        os.fsync(fd)                         # the new bytes are on disk BEFORE we publish them
        step("tmp_synced")
    finally:
        os.close(fd)
    os.replace(tmp, path)                    # atomic: readers see the old file or the new, never a mix
    step("replaced")
    dir_fd = os.open(os.path.dirname(os.path.abspath(path)), os.O_RDONLY)
    try:
        os.fsync(dir_fd)                     # make the rename itself durable
    finally:
        os.close(dir_fd)
    step("dir_synced")

Try it yourself: four experiments

  1. Count the syscalls (Linux). strace -f -e trace=write,fsync,fdatasync,rename,ftruncate python3 -c "..." around a few appends with always and then batch shows exactly how many fsync calls each policy makes. (On macOS, dtruss needs system protection turned off, so skip it. Counting with a wrapper around os.fsync, as check.py does, works everywhere.)
  2. Feel the price. Change the throughput test to 1000 records, run it on an external USB drive or an old laptop, and compare with the table above. Then add fcntl.fcntl(fd, fcntl.F_FULLFSYNC) on macOS in place of os.fsync and watch "always" get several times slower.
  3. Break the CRC. Make scan_records skip the checksum comparison. The SIGKILL rounds and the truncated-file cases still pass, but milestone 2's flipped-bit case and the 20 bit-flip tests fail: damage that keeps the right length goes unnoticed. The CRC is the only thing that catches it.
  4. Break the order. In save_config, move the os.fsync(fd) to after os.replace. Everything still passes except the order check, and that check exists only because the test records the calls. The bug itself is invisible until a real power failure, which is why serious systems are tested with tooling that drops or reorders writes.

Stretch goals

  • An index: keep a dictionary from record number to offset, rebuilt during recovery, and add read_at(offset) that reads exactly one record. This is how a log becomes a database.
  • Sequence numbers: put an incrementing number in every record, so recovery can also detect a record that is valid but out of place (a lost write in the middle, or a stale block from an old file).
  • F_FULLFSYNC: add fsync="full" that uses fcntl.F_FULLFSYNC on macOS and os.fsync elsewhere. Measure it.
  • fdatasync: use os.fdatasync (Linux) where available. It skips flushing metadata such as timestamps, and is a little cheaper. When is it not enough?
  • Segments and compaction: start a new file after 1 MiB, and delete old segments once their contents have been summarised in a snapshot. Replacing the snapshot is a job for save_config.
  • A real group commit: let several threads call append, and have one of them perform the shared fsync while the others wait on it. Return from append only when your record's batch is synced.
  • When fsync fails: read the end of chapter 9. After a failed fsync you cannot assume a retry will work (the kernel may have already dropped the dirty pages). What should the log do? (A common answer: stop accepting writes and crash.)

Distributed systems connection

What you built is the heart of a write-ahead log: a record is made durable before anything depends on it, and on restart the log is replayed to rebuild state. The replicated log in Networking Lab 6 (Toy Raft) is simulated, but a real Raft node must persist an entry to its own log before telling the leader "I have it", because that acknowledgement counts toward a majority. If a node acknowledges before its fsync returns and then loses power, the cluster may have counted a vote that no longer exists, and a committed entry can vanish. The acknowledgement rule from this lab, ack only after durable, is one of the sentences distributed databases are built on. Batching trades latency for throughput exactly as in group commit; replication adds a second way to be durable ("it is on three machines"), but each machine still needs its own fsync story.

What you learned

  • A successful write() only means the kernel has the data. fsync is the call that waits for the disk, and it is slow, so it is a policy decision.
  • A record format with a length and a checksum lets you tell good data from a torn or corrupted tail. Recovery keeps the valid prefix and truncates the rest.
  • Group commit shares one fsync between many records. The price is that durability is promised only after the batch is flushed.
  • Acknowledge a write only after it is durable; then losing an unacknowledged tail breaks no promise.
  • Killing a process (SIGKILL) tests your logic but not your fsync calls, because the kernel's page cache survives. Real durability needs power-loss testing, which is why you also cut files and counted calls.
  • To replace a file atomically: write a temp file in the same directory, fsync it, os.replace it, then fsync the directory.

Check your understanding

A program calls os.write(fd, data) (no fsync) and is then killed with SIGKILL. The computer keeps running. Will the data normally be on disk eventually?

  1. No: killing a process discards everything it wrote
  2. Only if the program had called close() first
  3. Yes: the bytes were already in the kernel's page cache, which survives the process, and the kernel writes them out later
  4. Only on Linux
The page cache belongs to the kernel, not to the process. SIGKILL ends the process but the kernel carries on and flushes dirty pages as usual. Only a crash of the whole machine (power loss, kernel panic) loses data that had not reached the disk. That is why a SIGKILL test cannot prove your fsync calls are right.

Recovery finds a record in the middle of the log whose checksum does not match, followed by several records that look fine. What does the lab's recovery do, and why?

  1. Truncates the log at the bad record, because after a damaged record you cannot trust where the following record boundaries are
  2. Skips the bad record and keeps the later ones
  3. Repairs the bad record by recomputing its checksum
  4. Deletes the whole log
The damaged record might have a wrong length, so the bytes that "look fine" after it could be misaligned or accidental. Keeping the valid prefix is the safe rule. Recomputing the checksum would just bless the damaged data. (Real systems can do more elaborate repairs, using replicas or sequence numbers.)

You use fsync="batch" with batch_size=32. When may your application safely tell a user "your record is saved"?

  1. As soon as append returns
  2. After 10 milliseconds
  3. Never; batching can never be safe
  4. After the fsync that covers that record has returned, that is, after the batch fills or after flush()
With group commit, append returning only means "written to the page cache". Durability is established by the shared fsync. Batching is perfectly safe if you delay the acknowledgement until after it. What you give up is some latency for the earliest records in each batch.

In the atomic-replace pattern, why must the temporary file be fsync-ed before os.replace?

  1. Because os.replace fails on files that have unsynced data
  2. Otherwise a power failure could persist the rename but not the data, leaving a config.json that exists but is empty or partial
  3. To make the rename faster
  4. It does not matter; the rename is atomic, so the data is always complete
"Atomic" describes what other programs see while the machine is running. Across a power failure, the kernel is free to write the directory change and the file contents to disk in any order. Syncing the data first guarantees that if the new name is visible after a crash, the bytes behind it are complete.

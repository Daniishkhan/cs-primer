Lab 5: Your Own Event Loop

In chapter 16 you saw an event loop; in chapter 17 you saw async/await sit on top of one. Now you'll build both. About 300 lines of Python, standard library only (selectors and heapq, no asyncio), ending with a server that handles a thousand connections on one thread and a clear picture of why one slow handler is a disaster.

Why this lab matters

Web servers, databases, browsers, Node.js, Redis, nginx and Python's own asyncio are all this program, wearing different clothes. Once you have written the loop yourself, await stops being magic: it is a generator pausing, a small object saying "wake me when this socket is readable", and a loop that keeps its promise. You will also hit, with your own hands, the rule that governs every event-driven system: never block the loop.

What you'll build

Five milestones, each building on the last:

  1. Timers: call_soon, call_later and run(), with a heap of deadlines on the monotonic clock.
  2. I/O readiness: add_reader/add_writer on a selector, and a callback-style echo server.
  3. Partial writes and output buffers: write interest only while there is something to write, a bounded buffer, and slow consumers cut off.
  4. Coroutines from generators: a Task that drives a generator, and the echo server rewritten as straight-line code.
  5. Scale and the cardinal rule: a thousand connections, the open-file limit, and a "loop lag" meter that catches a blocked loop red-handed.

Conventions used by every server

  • 127.0.0.1 and port 0. Servers bind the loopback address and let the OS pick a free port (networking chapter 4). Each server object exposes .port, and serve() passes it to a ready(port) callback so check.py can find it.
  • Non-blocking sockets. Every socket you hand to the loop has setblocking(False), so recv and send return or raise BlockingIOError at once (chapter 15).
  • Stopping. The checker stops a server by closing all its sockets. A loop with no timers and no watched sockets has no work left, so run() returns. That is exactly the definition of "done" you implement in milestone 1.

Milestone 1: timers

An event loop is, at heart, a while loop with a list of things to do and a clock. Start with the clock half, no sockets at all. You need three ways to say "run this later":

CallMeaning
call_soon(fn, *args)run on the next pass of the loop, in the order scheduled
call_later(delay, fn, *args)run delay seconds from now
call_at(when, fn, *args)run when the loop's clock reaches when (what call_later uses underneath)

Ready callbacks live in a collections.deque: first in, first out. Timers live in a min-heap (heapq), which always keeps the earliest deadline at timers[0], so "what is due next?" is one look and "add a timer" is O(log n). Each heap entry is a tuple (deadline, seq, fn, args). The seq is a counter that goes up by one for every timer. It does two jobs. Two timers due at the same instant compare equal on deadline, so seq decides: the one scheduled first runs first (FIFO). And because seq is unique, Python never gets as far as comparing two functions, which would raise TypeError.

Why the monotonic clock?

Your wall clock (time.time()) is a number someone can change: NTP corrects it, an admin sets it, a leap second repeats a second, daylight saving moves it. A timer built on it can fire early, or not for an hour. time.monotonic() only moves forward, at the rate of real elapsed time, from an arbitrary starting point. Perfect for "wait 50 ms", useless for "what time is it". Case 3 is what happens when software forgets this. check.py checks you did not: it makes the wall clock jump back 3 seconds and expects your timer to carry on regardless.

Callbacks should never take the loop down with them. A callback that raises must be reported (the starter's report_error stores it in loop.errors and prints the traceback) and the loop must go on with the next one. And when everything is done, run() should simply return: no ready callbacks, no timers, nothing registered with the selector.

Hints try without first
  • Step 1 of the diagram is three branches: if self._ready then timeout = 0; elif self._timers then timeout = max(0, self._timers[0][0] - self.time()); else None.
  • Move due timers with a while self._timers and self._timers[0][0] <= now: loop and heapq.heappop. Popping in heap order gives you (deadline, seq) order for free.
  • Run only len(self._ready) callbacks per pass, counted before you start. A callback that calls call_soon belongs to the next pass; otherwise a callback that keeps rescheduling itself starves the sockets (and the timers) forever.
  • Wrap each call in try/except Exception as exc and call self.report_error(exc). Catch Exception, not BaseException, so Ctrl+C still stops the program.
  • run() is one line of condition around _run_once(): while not self._stopping and (self._ready or self._timers or self._selector.get_map()). (get_map() is empty for now.)
Solution spoiler 
def time(self):
    # Monotonic: never jumps backwards when NTP or an admin changes the wall clock.
    return time.monotonic()

def call_soon(self, fn, *args):
    """Run fn(*args) on the next pass of the loop."""
    self._ready.append((fn, args))

def call_at(self, when, fn, *args):
    """Run fn(*args) at absolute loop time `when` (a value of self.time())."""
    heapq.heappush(self._timers, (when, next(self._seq), fn, args))

def call_later(self, delay, fn, *args):
    """Run fn(*args) after `delay` seconds."""
    self.call_at(self.time() + max(0.0, delay), fn, *args)

def run(self):
    """Run until there is no work left: no ready callbacks, timers or watched sockets."""
    self._stopping = False
    while not self._stopping and (self._ready or self._timers or self._selector.get_map()):
        self._run_once()

def _run_once(self):
    # 1. How long may we sleep in the selector?
    if self._ready or self._stopping:
        timeout = 0                                    # work is waiting: just peek
    elif self._timers:
        timeout = max(0.0, self._timers[0][0] - self.time())
    else:
        timeout = None                                 # nothing timed: sleep until I/O
    # 2. Ask the OS which sockets are ready; queue their callbacks.
    for key, mask in self._selector.select(timeout):
        reader, writer = key.data
        if mask & READ and reader:
            self._ready.append(reader)
        if mask & WRITE and writer:
            self._ready.append(writer)
    # 3. Move due timers to the ready queue (heap order = deadline, then FIFO).
    now = self.time()
    while self._timers and self._timers[0][0] <= now:
        _, _, fn, args = heapq.heappop(self._timers)
        self._ready.append((fn, args))
    # 4. Run exactly the callbacks that were ready when this pass began.
    for _ in range(len(self._ready)):
        fn, args = self._ready.popleft()
        try:
            fn(*args)
        except Exception as exc:                       # one bad callback must not kill the loop
            self.report_error(exc)

The two lines about key.data are milestone 2; before that the selector has nothing registered and select(timeout) just sleeps.

Milestone 2: I/O readiness

Now the loop learns to watch sockets. The selector (selectors.DefaultSelector: epoll on Linux, kqueue on macOS, as in chapter 16) keeps a registry of sockets and the events you care about. You'll expose four methods that mirror what asyncio offers:

MethodThe callback runs when...
add_reader(sock, fn, *args)sock is readable: bytes waiting, a connection to accept, or the peer closed
add_writer(sock, fn, *args)sock is writable: there is room in its kernel send buffer
remove_reader(sock), remove_writer(sock)stop watching. Harmless if you weren't.

One socket can have a reader and a writer at once, but the selector only holds one registration per socket, with a combined set of events. The starter gives you _update(sock, reader, writer), which makes the registration match exactly the callbacks you pass (registering, modifying or unregistering as needed; the callbacks are stored in the registration's data field as a (reader, writer) pair). Your four methods just keep the other slot as it was and change one.

Readiness here is level-triggered: as long as the condition holds (bytes still unread, send buffer still has room), the selector reports it again on every pass. That is forgiving: if you read only part of the data, you'll be told again. It also has a sharp edge, which is the whole of milestone 3.

Then use the loop. The first server is deliberately plain: a listening socket registered with add_reader; when it is readable, accept every waiting connection (until BlockingIOError); each connection gets its own reader that does one recv and one send. No threads, and no waiting anywhere except inside select.

Known flaw, on purpose

conn.send(data) is allowed to send fewer bytes than you gave it, and on a non-blocking socket it raises BlockingIOError if the kernel buffer is full. The milestone 2 server ignores that, which is fine for short messages and wrong for big ones. Milestone 3 fixes it. (Chapter 15 called this the partial write.)

Hints try without first
  • add_reader: key = self._lookup(sock) (None if unregistered); self._update(sock, (fn, args), key.data[1] if key else None). The other three are the same idea with the slots swapped or one set to None.

def add_reader(self, sock, fn, *args):
    key = self._lookup(sock)
    self._update(sock, (fn, args), key.data[1] if key else None)

def remove_reader(self, sock):
    key = self._lookup(sock)
    if key:
        self._update(sock, None, key.data[1])

def add_writer(self, sock, fn, *args):
    key = self._lookup(sock)
    self._update(sock, key.data[0] if key else None, (fn, args))

def remove_writer(self, sock):
    key = self._lookup(sock)
    if key:
        self._update(sock, key.data[0], None)

def has_reader(self, sock):
    key = self._lookup(sock)
    return bool(key and key.data[0])

def has_writer(self, sock):
    key = self._lookup(sock)
    return bool(key and key.data[1])

def __init__(self, loop, port=0):
    self.loop = loop
    self.listener = listen_socket(port)
    self.port = self.listener.getsockname()[1]
    self.conns = set()
    loop.add_reader(self.listener, self._on_accept)

def _on_accept(self):
    # Readable listener = at least one connection waiting. Take them all.
    while True:
        try:
            conn, _ = self.listener.accept()
        except (BlockingIOError, InterruptedError):
            return
        except OSError:                # e.g. out of file descriptors
            return
        conn.setblocking(False)
        self.conns.add(conn)
        self.loop.add_reader(conn, self._on_readable, conn)

def _on_readable(self, conn):
    if conn not in self.conns:         # closed earlier in this same pass
        return
    try:
        data = conn.recv(65536)
    except (BlockingIOError, InterruptedError):
        return
    except OSError:
        data = b""
    if not data:                       # b"" = the peer closed
        self._drop(conn)
        return
    try:
        conn.send(data)                # may send FEWER bytes than len(data)!
    except OSError:
        self._drop(conn)

def _drop(self, conn):
    self.loop.remove_reader(conn)
    self.conns.discard(conn)
    conn.close()

Milestone 3: partial writes and output buffers

Reading is easy to reason about: data arrives, you take what is there. Writing is where servers get hurt. Each connection has a kernel send buffer of limited size. If the client is slow (a phone on a bad network, a bug, an attacker), the buffer fills and send takes only part of your data, or none. You cannot wait for room, because waiting is blocking. And you cannot throw the rest away. So the connection needs its own output buffer, a bytearray of bytes you owe it:

  1. After reading, append the reply to the buffer.
  2. Try to send the whole buffer; remove exactly as many bytes as were sent (del buf[:sent]).
  3. If bytes remain, register add_writer so the loop tells you when the kernel has room. If the buffer is empty, make sure the writer is not registered.

Why write interest only while there is data

A healthy socket is almost always writable: there is nearly always room in its send buffer. With level-triggered readiness, a writer you forgot to remove makes select return immediately on every pass, forever. The loop spins at 100% CPU doing nothing. The rule: register write interest when you have something to write, and remove it the moment you don't. check.py looks for stray writers once everything is quiet.

The output buffer is a queue, and chapter 14 already told you what an unbounded queue is: a memory leak with extra steps. A client that sends a lot and reads slowly makes the buffer grow without limit, until the process dies and takes every connection with it. So the buffer needs a bound and a policy for what happens when it is exceeded. Chapter 16 showed the gentle policy (stop reading from that client while you still owe it output, so TCP flow control pushes back on it). This milestone uses the blunt one: close the slow consumer. It protects everybody else, and it is what many servers do to clients that cannot keep up. Studio 1 asks you to decide which policy a real service would want.

Hints try without first
  • Keep a Connection object per client (the starter defines one: sock, out, writing) and pass it to the callbacks instead of the bare socket.
  • In _flush, loop while conn.out: so you send as much as the kernel will take in one go, then break on BlockingIOError. Only after the loop decide whether write interest should be on or off, using conn.writing so you don't add or remove it needlessly.
  • del conn.out[:sent] copies the rest of the buffer each time. Fine here; a ring buffer or memoryview would avoid it (stretch goal territory).

def _on_readable(self, conn):
    if conn.sock not in self.conns:
        return
    try:
        data = conn.sock.recv(65536)
    except (BlockingIOError, InterruptedError):
        return
    except OSError:
        data = b""
    if not data:
        self._drop(conn)
        return
    conn.out += data
    if len(conn.out) > self.max_buffer:        # the client is not keeping up: cut it off
        self._drop(conn)
        return
    self._flush(conn)

def _flush(self, conn):
    """Send as much as the kernel will take; ask to be told when it can take more."""
    while conn.out:
        try:
            sent = conn.sock.send(conn.out)
        except (BlockingIOError, InterruptedError):
            break                              # kernel buffer full
        except OSError:
            self._drop(conn)
            return
        del conn.out[:sent]
    if conn.out and not conn.writing:
        self.loop.add_writer(conn.sock, self._on_writable, conn)
        conn.writing = True
    elif not conn.out and conn.writing:        # nothing left: stop waking up for nothing
        self.loop.remove_writer(conn.sock)
        conn.writing = False

def _on_writable(self, conn):
    if conn.sock in self.conns:
        self._flush(conn)

def _drop(self, conn):
    if self.conns.pop(conn.sock, None) is None:
        return
    self.loop.remove_reader(conn.sock)
    self.loop.remove_writer(conn.sock)
    conn.sock.close()

Milestone 4: coroutines from generators

Look at your callback server. The life of one connection (accept, then repeatedly: wait for data, read, write the reply) is smeared across four methods that communicate through objects and flags. Real protocols have dozens of states. Chapter 17 showed the cure: write the connection as one function that pauses where it would otherwise wait. Python can already pause a function: a generator. Every yield hands a value to whoever is driving it, and gen.send(None) resumes it right after that yield.

So make the loop the driver. A coroutine is a generator that yields small request objects that say what it is waiting for:

Request"Resume me when..."The loop does
Sleep(seconds)the time has passedcall_later(seconds, step)
ReadWait(sock)sock is readableadd_reader(sock, wake), removed on wake
WriteWait(sock)sock is writableadd_writer(sock, wake), removed on wake

A Task is the glue: it holds the generator, calls send(None) to run it to its next yield, looks at the request, and arranges for itself to be called again when the request is satisfied. While a task waits it costs no CPU and no thread; it is just an object in a heap or a selector registration. This is what await compiles down to, in spirit: await loop.sock_recv(sock, n) is "yield a request, get resumed with the answer".

The starter already has the three request classes and the little helper coroutines accept, recv and send_all. Each one is a tiny generator of its own, and a coroutine calls it with yield from (the ancestor of await): data = yield from recv(conn, 65536) runs the helper, passes its yield ReadWait(conn) up to the Task, and hands back its return value. Notice send_all: it loops with WriteWait until every byte is sent, so a slow client makes its own task wait, not the loop. Compare that with milestone 3's buffer-and-close: here the task simply stops reading while it can't write, which is the gentle backpressure policy for free.

Hints try without first
  • Task.__init__ must not run the generator itself; it only schedules the first _step with loop.call_soon. Creating a task from inside another task would otherwise run it in the middle of the creator.
  • The generator's return value arrives as StopIteration.value. Catch StopIteration before Exception.
  • The wake-up for ReadWait is one-shot: the callback is self._wake, with arguments (loop.remove_reader, sock). If it stayed registered, the next pass would resume the task again while it is waiting for something else.
  • In _handle, put the cleanup in finally. A closed connection ends the loop with b""; a reset ends it with an OSError.
  • Stuck? Put a print(request) in _step and watch the conversation between coroutine and loop.

class Task:
    """Drives a generator: each `yield` is a request; resume when it is satisfied."""

    def __init__(self, loop, gen):
        self.loop = loop
        self.gen = gen
        self.done = False
        self.result = None
        self.error = None
        loop.call_soon(self._step)         # first step: run to the first yield

    def _step(self):
        if self.done:
            return
        try:
            request = self.gen.send(None)  # resume the generator
        except StopIteration as stop:      # `return value` inside the generator
            self.done, self.result = True, stop.value
            return
        except Exception as exc:
            self.done, self.error = True, exc
            self.loop.report_error(exc)
            return
        self._wait_for(request)

    def _wait_for(self, request):
        loop = self.loop
        if isinstance(request, Sleep):
            loop.call_later(request.seconds, self._step)
        elif isinstance(request, ReadWait):
            loop.add_reader(request.sock, self._wake, loop.remove_reader, request.sock)
        elif isinstance(request, WriteWait):
            loop.add_writer(request.sock, self._wake, loop.remove_writer, request.sock)
        else:
            self.done = True
            self.error = TypeError(f"a task may only yield Sleep/ReadWait/WriteWait, not {request!r}")
            loop.report_error(self.error)

    def _wake(self, unregister, sock):
        unregister(sock)                   # one-shot: we only wanted to be told once
        self._step()
def _accept_loop(self):
    while True:
        conn = yield from accept(self.listener)
        self.conns.add(conn)
        self.loop.create_task(self._handle(conn))

def _handle(self, conn):
    # Straight-line code: no state machine, no callbacks. This is async/await underneath.
    try:
        while True:
            data = yield from recv(conn, 65536)
            if not data:
                break
            yield from send_all(conn, data)
    except OSError:
        pass
    finally:
        self.conns.discard(conn)
        self.loop.remove_reader(conn)
        self.loop.remove_writer(conn)
        conn.close()

Milestone 5: a thousand connections, and the cardinal rule

You now have an event loop and a server on it. Two things remain: prove it scales, and see exactly how it fails.

One thread, a thousand clients

The check opens about 1,000 connections to your coroutine server, sends a message from each, verifies every echo, and then, with all of them still open, does it again. A thread-per-connection server would need a thousand threads (chapter 15 priced them); yours has one thread and a thousand small objects. The first thing to hit is not CPU or memory but the open-file limit. Each socket is a file descriptor (chapter 8), and each process has a limit on them: the soft limit is what is enforced and the hard limit is the ceiling a normal user may raise it to. The default soft limit varies by system (it has historically been as low as 256 on macOS shells and 1024 on many Linux ones). In this lab your test clients and your server live in one process, so a thousand connections need about two thousand descriptors. Past the limit, accept() fails with EMFILE ("too many open files"), and since the listener stays readable, a careless loop would retry instantly forever. (That is why the starter's accept helper sleeps 100 ms on that error.)

$ ulimit -n        # the soft limit of this shell, in descriptors
$ ulimit -Hn       # the hard limit
$ python3 -c "import resource; print(resource.getrlimit(resource.RLIMIT_NOFILE))"

The cardinal rule, measured

Chapter 16's loop lag is the lateness of the loop: how much later than planned does a timer run? It is a heartbeat. Schedule a ticker every 10 ms; each time it fires, compare "now" to when it should have fired. If nothing blocks, the lag is about a millisecond. If one callback hogs the thread for 200 ms, the ticker (and every connection's data, and every other timer) waits, and the next tick is about 200 ms late. check.py runs the same loop three ways and reports the worst lag: with nothing else going on, with a callback that does time.sleep(0.2), and with a coroutine that does yield Sleep(0.2). The same 0.2 seconds of "waiting" costs nothing in one case and everything in the other.

The cardinal rule

Nothing that runs on the loop thread may block: no time.sleep, no blocking recv, no requests.get, no big CPU loop, no unindexed disk read. A blocked loop doesn't just slow one request, it freezes all of them at once, and every client sees the same latency spike. Either use the non-blocking version (a Sleep request), or push the blocking work to a thread or process pool (chapter 14) and have it post the result back.

Your task

Implement two things in starter.py. raise_fd_limit(wanted) raises the soft RLIMIT_NOFILE toward wanted without exceeding the hard limit, and returns the soft limit it ended up with. LagMonitor (start and _tick) records, at every tick, how late the tick was. If the limit can't be raised high enough, check.py scales the number of clients down and says so; nothing to code there.

python3 check.py shows 5/5, with notes like serving all 1000 clients and the three lag numbers. Typical on a laptop: idle about 1 ms, time.sleep(0.2) about 200 ms, yield Sleep(0.2) about 1 ms. The checker's thresholds are loose on purpose (blocked above 100 ms, calm below 80 ms), so your result should not flicker.

Hints try without first
  • resource.getrlimit(resource.RLIMIT_NOFILE) returns (soft, hard). Either may be resource.RLIM_INFINITY, which is a negative number on most systems: compare it with == before doing arithmetic.
  • Set the soft limit to min(wanted, hard), keeping the hard limit unchanged: setrlimit(RLIMIT_NOFILE, (target, hard)). Never try to raise the hard limit: that needs privileges, and you shouldn't.
  • macOS can refuse a soft limit above its own per-process cap even when hard says "unlimited". If setrlimit raises, try a smaller target and report what you really got.
  • For the monitor, compute lateness as now - expected, then set expected = now + interval and schedule with call_at(expected, ...). Don't schedule at expected + interval: after a long block you would fire a burst of "catch-up" ticks.
  • A ticker that reschedules itself is permanent work: run() never returns while it runs. That is why stop() exists.
Solution spoiler 
def raise_fd_limit(wanted):
    """Try to raise the soft RLIMIT_NOFILE to `wanted`; return the soft limit we ended up with."""
    soft, hard = resource.getrlimit(resource.RLIMIT_NOFILE)
    if soft == resource.RLIM_INFINITY or soft >= wanted:
        return sys.maxsize if soft == resource.RLIM_INFINITY else soft
    target = wanted if hard == resource.RLIM_INFINITY else min(wanted, hard)
    while target > soft:
        try:
            resource.setrlimit(resource.RLIMIT_NOFILE, (target, hard))
            break
        except (ValueError, OSError):      # e.g. macOS refuses values above its own cap
            target = (target + soft) // 2
    return resource.getrlimit(resource.RLIMIT_NOFILE)[0]
def start(self):
    self._running = True
    self._expected = self.loop.time() + self.interval
    self.loop.call_at(self._expected, self._tick)

def _tick(self):
    if not self._running:
        return
    now = self.loop.time()
    self.lags.append(max(0.0, now - self._expected))   # how late did we fire?
    self._expected = now + self.interval
    self.loop.call_at(self._expected, self._tick)

You should see epoll_ctl calls as your loop adds, modifies and removes interest, and epoll_wait calls whose last argument is your timeout in milliseconds: -1 (forever) when nothing is scheduled, 0 when callbacks are ready, and a small number while a timer is pending. Stretch goals

  • One loop per core. A single loop uses one core. On Linux, setsockopt(SOL_SOCKET, SO_REUSEPORT, 1) lets several processes bind the same port, and the kernel spreads new connections across them. Fork N children (os.fork, chapter 5; multiprocessing also works), each with its own EventLoop, and compare throughput with the single loop. This is the layout of nginx workers (case 4). macOS also has SO_REUSEPORT but spreads connections differently, so measure rather than assume.
  • A timer wheel. A heap costs O(log n) per timer, which hurts with millions of timeouts (one per idle connection). A timer wheel is a ring of buckets, one per tick; a timer goes in the bucket for its deadline, and each tick you run one bucket. Add and cancel become O(1). Implement a hashed wheel for coarse timeouts such as idle-connection kicks and compare it with the heap.
  • Cancellable timers. Make call_later return a handle with cancel(). Heaps cannot remove from the middle cheaply; mark the entry cancelled and skip it when popped, and rebuild the heap if too many dead entries pile up.
  • Read-stop backpressure. In the milestone 3 server, instead of closing a slow client, stop reading from it (remove_reader) while its buffer is above a high-water mark, and resume below a low-water mark.
  • Idle timeouts. Close any connection that has been silent for 30 seconds, using one timer per connection or, better, one periodic sweep.
  • Calling the outside world. Add loop.run_in_thread(fn, callback) that runs fn on a worker thread and delivers the result back to the loop thread. You'll need a way to wake select from another thread: a socket.socketpair() registered as a reader is the classic trick (the "self-pipe").
  • Futures. Add a Future class and let a task yield one, so tasks can wait for other tasks. You have just invented await task.

Distributed systems connection

Every node in a distributed system is a process that waits on many peers at once, and most are built around one of these loops: a Raft leader's heartbeat is a timer; its followers' election timeouts are timers; the network connections to peers are readers and writers; the RPC handlers must never block. That last part is why a stop-the-world pause (a long GC, a blocked loop, a slow disk) is so dangerous in a cluster: a node that misses its heartbeat looks dead to everyone else, even though it was only busy. The loop lag you measured here is the same number that, in production, decides whether a healthy node gets declared failed. And your bounded output buffer is the smallest version of what every message queue must decide: when a consumer cannot keep up, do you buffer, slow the producer down, or cut the consumer off? Part 6 of the networking course, and the Data Systems course later, meet that question again under names like backpressure and flow control.

What you learned

  • An event loop is a while loop around three things: a queue of ready callbacks, a heap of timers, and a selector. Its only sleep is select(timeout), with the timeout set to the next deadline.
  • Timers use the monotonic clock, and a (deadline, seq) key makes equal deadlines run in FIFO order.
  • Readiness is level-triggered: register write interest only while an output buffer is non-empty, or the loop spins.
  • Writes can be partial, so every connection needs an output buffer, and that buffer needs a bound and a policy: stop reading, or close the slow consumer.
  • A coroutine is a generator that yields "wake me when..." requests; a Task resumes it when the loop says so. That is the machinery under async/await.
  • One thread can hold a thousand connections; the first wall is the file-descriptor limit, not the CPU.
  • Nothing on the loop thread may block. Loop lag is the number that tells you when something does.

Check your understanding

Your timer heap stores (deadline, fn, args) without a sequence number. What can go wrong?

  1. Nothing: the heap only looks at the deadline
  2. Two timers with exactly equal deadlines make Python compare the functions, which raises TypeError, and equal deadlines no longer have a guaranteed order
  3. The heap can no longer find the earliest deadline
  4. Timers fire twice
Tuples compare element by element. If the deadlines tie, the next elements are compared, and functions cannot be ordered. A unique, increasing seq in second place settles every tie, and doubles as the first-come-first-served rule for timers due at the same moment.

An echo server leaves every connection registered with add_writer permanently, "just in case". What do you observe?

  1. Replies are sent faster
  2. Nothing, it only uses a bit more memory
  3. The loop wakes up on every pass because sockets are almost always writable, so it burns a whole core doing nothing
  4. The OS closes the connections
Readiness is level-triggered: "has room in its send buffer" is true almost all the time, so select returns at once, over and over. Register write interest only while you have bytes to send, and remove it when the buffer empties.

In the coroutine echo server, what does data = yield from recv(conn, 65536) do when no data has arrived yet?

  1. It yields a ReadWait to the Task, which registers a reader and returns to the loop; the coroutine stays paused (using no thread) while other tasks and callbacks run
  2. It blocks the thread until data arrives
  3. It polls the socket in a tight loop
  4. It raises BlockingIOError to the caller
The coroutine pauses at the yield, keeping its local variables. The Task turns the request into a selector registration and returns control to the loop. When the socket becomes readable, the loop calls the Task, which resumes the coroutine right where it stopped. This is what await does.

Your server handles 1,000 connections normally. One handler starts calling time.sleep(0.2). What happens to a client whose request arrives while it sleeps?

  1. Nothing: the sleeping handler is just one of 1,000 tasks
  2. It is served by a spare thread
  3. Only clients that talk to the same handler are slowed
  4. It waits until the sleep ends, because the one loop thread is stuck inside that call; every client sees about 0.2 s of extra latency, and loop lag jumps to about 200 ms
There is exactly one thread, and a callback runs to completion before the loop looks at anything else. A blocking call therefore freezes all connections and all timers. Use yield Sleep(0.2) (or await asyncio.sleep), or move genuinely blocking work to a thread pool.

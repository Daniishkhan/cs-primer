The Leap Second That Broke DNS

At midnight UTC on 1 January 2017 the world's clocks added a leap second. At Cloudflare, a number that was supposed to be impossible to make negative went negative, a function panicked, and some DNS lookups failed. The root cause was one innocent line that measured how long something took by subtracting two readings of the wall clock.

The pattern in one sentence

Wall clock vs monotonic clock: the wall clock tells you what time it is and can be set backwards; to measure how long something took, use a monotonic clock, which only moves forward.

The cast

You learned in chapter 1 that a computer's sense of time is a counter driven by hardware, and in chapter 4 that programs ask the kernel for it. The networking course's chapter 17 showed that different machines disagree about the time and that clocks get corrected. Now see what a correction can do to a program.

RRDNS
Cloudflare's custom DNS server software, written in Go. According to Cloudflare, it was the component that panicked.
CNAME lookups
When a customer points a name at another hostname instead of an IP address, Cloudflare has to look up the target's address through its own internal recursive resolvers. Only customers using CNAME records were affected.
Weighted server selection
RRDNS tracks how fast each internal resolver answers and picks among them with weights, favouring faster ones. Several resolvers per data center give redundancy.
The wall clock
The system's idea of the calendar time. It can be adjusted by time synchronisation or when a leap second is applied.
The leap second
Cloudflare's trouble began at midnight UTC on 1 January 2017. Its post attributes the failure to time not moving forward as the code assumed.

What happened, step by step

Step through

How a clock step became a panic

  1. RRDNS times its upstream lookups. For each query to an internal resolver, it records a start time and, when the answer arrives, computes the round-trip time as the difference between two time.Now() readings: rtt := time.Now().Sub(start). The resolvers are tuned to be fast, often answering in a few milliseconds.
  2. The clock steps back. Cloudflare's post says RRDNS assumed time never goes backwards. At the leap second, the clock stepped back by about a second while a lookup was in flight. (The numbers in this diagram are illustrative.)
  3. A negative duration. The end reading is now earlier than the start reading, so the measured round-trip time is negative. A monotonic clock measuring the same lookup would still say a few milliseconds.
  4. Smoothing keeps the poison. RRDNS blends many measurements together, so one negative sample would not matter on its own. But Cloudflare found that over several samples the smoothed value could turn negative.
  5. The panic. The weighted selection passed these values to Go's rand.Int63n(), which panics when its argument is not positive. Go's recover caught the panic, but some resolutions to Cloudflare-managed web properties still failed.
  6. The fix. Cloudflare's fix stops negative values from entering the server-selection data. When the clock jumps backward, RRDNS discards the affected upstream performance data and rebuilds it as time normalises.

How bad was it?

Cloudflare's own numbers: the problem started at 00:00 UTC on 1 January 2017 and ended at 06:45 UTC. Only a small number of machines across its 102 data centers were affected. At peak, about 0.2% of DNS queries were affected, and fewer than 1% of HTTP requests saw an error. The most affected machines were patched within about 90 minutes of the start, and the fix reached all locations by 06:45 UTC (the post's timeline lists the stages).

Common misconception: "the leap second broke the servers"

The leap second did nothing to the servers' hardware or operating system. What failed was one assumption in application code: that subtracting two timestamps always gives a non-negative number. Any time adjustment (an NTP correction, a leap second, a manual change, a virtual machine resuming) could have exposed it. The leap second just made it happen everywhere at the same instant.

The pattern: two clocks for two jobs

Most operating systems offer at least two kinds of clock, for two different questions:

Wall clock ("what time is it?")

A calendar date and time, such as the Unix epoch seconds from time.time() in Python. It is what you put in logs and show to users. It can be corrected, and so can move backward. Python's documentation says time.time() "can return a lower value than a previous call if the system clock has been set back".

Monotonic clock ("how long did it take?")

A counter that only goes forward and ignores clock corrections. Python's documentation describes time.monotonic() as "a clock that cannot go backwards" that is "not affected by system clock updates". Its starting point is undefined, so only the difference between two readings means anything.

Rule of thumb: timestamps from the wall clock, durations from the monotonic clock. Timeouts, retry delays, round-trip times, rate limiters, elapsed-time metrics, lease expiry on one machine: all durations.

Analogy: the wall clock vs the stopwatch

The clock on the kitchen wall can be reset when the power flickers or when the household moves to daylight saving time. A stopwatch you start when the pasta goes in does not care. If you want to know how long the pasta has been cooking, use the stopwatch.

Where it breaks down: a stopwatch is only meaningful on one machine. You cannot compare monotonic readings between two computers, because each has its own undefined starting point. Cross-machine ordering needs wall clocks plus extra care (networking chapter 17).

What Go changed afterwards

Cloudflare notes that at the time, Go had no monotonic time source, and links to Go issue 12914. The Go 1.9 release notes say: "The time package now transparently tracks monotonic time in each Time value, making computing durations between two Time values a safe operation in the presence of wall clock adjustments." In other words, from Go 1.9 onward the same time.Now().Sub(start) line, written the same way, measures with the monotonic reading when both times have one. That is much safer, but it does not remove the need to think about which clock you mean. The release notes also say the String output of a Time with a monotonic reading ends with an m= field.

Trade-offs and lessons

Don't assume time moves forward

Cloudflare's own lesson: wall-clock time can jump backward, so code that computes intervals must handle negative differences.

Validate where the value is born

Cloudflare advises always checking whether the difference between two timestamps is negative, and its patch stops negative values from reaching the server-selection code. General principle: check at the point of measurement, before bad values reach downstream code that cannot handle them.

Averaging can preserve a bad sample

A smoothed value can turn one-off bad data into persistent bad state. In Cloudflare's case, a single negative sample would not have mattered, but after a few the smoothed value went negative. Restarting all RRDNS servers then fixed any recurrence.

Audit time code

Cloudflare said it was reviewing its codebase for other leap-second-sensitive logic. General industry pattern, not from this source: grep for wall-clock reads used in timeouts and intervals; they are the first suspects.

General background, not from Cloudflare's post

Some large operators avoid the sudden step by "smearing" the extra second over many hours, so clocks never jump. That is a separate defence, applied to the clock itself. Fixing the program, as Cloudflare did, protects you whichever way your machines' clocks behave.

Try it yourself

Two clocks, side by side

Read-only. You cannot safely set your clock back, but you can see the two clocks and their guarantees.

import time

print("wall clock  :", time.time())          # seconds since 1970-01-01 UTC
print("monotonic   :", time.monotonic())     # arbitrary starting point
print(time.get_clock_info("time"))
print(time.get_clock_info("monotonic"))      # look at 'adjustable' and 'monotonic'

# Measuring a duration the safe way:
start = time.monotonic()
sum(range(1_000_000))
print("elapsed: %.6f s" % (time.monotonic() - start))

# A wall-clock version could print a negative number if the clock
# were stepped back in between:
#   elapsed = time.time() - start_wall
$ date -u +%s                 # wall clock as epoch seconds (macOS and Linux)
$ cat /proc/uptime             # Linux: seconds since boot, a monotonic-style counter
$ sysctl kern.boottime         # macOS: when the machine booted

In the Python output, adjustable is True for the wall clock and False for the monotonic one on typical systems. That one flag is the whole story of this case.

Distributed systems connection

Distributed systems lean heavily on durations: heartbeat timeouts, lease lengths, retry back-off. Each one must be measured on a monotonic clock on a single machine. And whenever you need to compare times between machines, such as ordering events or expiring a lease granted by another node, remember that their wall clocks disagree and can jump. That is why leases carry a duration rather than an absolute expiry, and why designs lean on logical clocks and consensus rather than trusting timestamps (networking chapter 17).

Key takeaways

  • RRDNS computed round-trip time as time.Now().Sub(start). When the clock stepped back at the 2017 leap second, the result went negative.
  • Smoothing carried the negative value along until a call to rand.Int63n with a non-positive argument panicked.
  • Peak impact was about 0.2% of DNS queries; the problem lasted until 06:45 UTC.
  • Use the monotonic clock for durations and the wall clock for timestamps. In Python: time.monotonic() vs time.time().
  • Go 1.9 made time.Time carry a monotonic reading, so durations between two Time values are safe against wall-clock adjustments.

Why did RRDNS compute a negative round-trip time?

  2. The resolver was extremely slow
  3. It subtracted two wall-clock readings, and the clock stepped back between them
  4. A division by zero occurred
Cloudflare's post: the RTT was the difference between two time.Now() calls, and a clock step back of a second during a few-millisecond lookup made it negative.

Which clock should you use to measure how long a function takes?

  1. A monotonic clock, such as time.monotonic()
  2. The wall clock, because it is more accurate
  3. The clock of a remote server
  4. It makes no difference
A monotonic clock cannot go backwards and ignores clock updates, so differences between its readings are valid durations. The wall clock can be set backwards.

What did Go 1.9 change that addresses this class of bug?

  1. It removed leap seconds
  2. time.Time values now carry a monotonic clock reading, so durations between two of them are safe against wall-clock adjustments
  3. rand.Int63n no longer panics
  4. time.Now() now returns the time in UTC only
From the Go 1.9 release notes: the time package "transparently tracks monotonic time in each Time value".

A negative value reached rand.Int63n even though single negative samples were harmless. Why?

  1. Go caches random numbers
  2. The sample was inserted directly by the weighted selector
  3. The leap second changed the random number generator
  4. Smoothing combined samples, and after several negative ones the smoothed value could itself become negative
One bad sample was diluted by the average, but repeated ones pulled the smoothed value below zero. Validating at the point of measurement stops this chain.

Ten Thousand Connections: nginx & C10k

Around the turn of the millennium, a question started going round among web server authors: can one machine serve ten thousand clients at once? Dan Kegel gave the question a name, "the C10k problem", and wrote down the strategies for answering it. nginx, created by Igor Sysoev and released in 2004, was designed around one of them. This case studies the idea behind it.

The pattern in one sentence

Event-driven servers: instead of dedicating a process or thread to every connection (and paying for it while it mostly waits), let a few threads each watch thousands of connections and do work only on the ones that are ready.

The cast

This case builds on chapter 15 (blocking vs non-blocking I/O) and chapter 16 (event loops). Its practical twin is Studio 1, where you design a server for 10,000 connections yourself.

The C10k problem
Kegel's name for handling ten thousand simultaneous clients on one server. His page argues that "hardware is no longer the bottleneck" (his words) and sets out how to configure operating systems and write code to support thousands of clients.
nginx
A web server and proxy created by Igor Sysoev, publicly released in 2004. Andrew Alexeev's chapter in The Architecture of Open Source Applications says nginx targets high concurrency, high performance and low memory use, and was designed to meet the C10k goal.
Master process
Runs as root. Reads and validates configuration, creates and binds sockets, starts and maintains the workers, and handles reconfiguration and binary upgrades.
Worker processes
Run as an unprivileged user. They handle client connections, proxying, filtering and most of the real work. Each is a single-threaded event loop built on OS mechanisms such as epoll or kqueue.
Helper processes
A cache loader (fills in cache metadata at startup, then exits) and a cache manager (expires and invalidates entries).

The problem: a connection that mostly waits

The straightforward way to write a server, covered in chapters 10 and 15, is to give each connection its own process or thread. The code is simple: read the request, do the work, write the reply, and let blocking calls pause only that connection. The AOSA chapter lists the costs. Each connection needs its own runtime environment, including heap and stack memory and an execution context. Creating and switching between these takes CPU time, and too much switching can cause thrashing. Its example: 1,000 clients at about 1 MB each use about 1 GB, and Apache commonly uses more than 1 MB per connection. Slow clients make it worse: a worker stays tied up while, say, a 100 KB response trickles out to a client at 10 KB/s.

Kegel's page frames the economics the other way round. A machine with a 1 GHz CPU, 2 GB of RAM and a 1 Gbit/s network card, which he says costs $1,200 or so, spread over 20,000 clients leaves roughly 50 kHz of CPU, 100 KB of memory and 50 kbit/s of bandwidth per client. He argues that is plenty to send four kilobytes per client once a second, so the hardware could do it. The software structure was what blocked the way.

Step through: two ways to hold three connections

Step through

One execution context per connection vs an event loop

  1. Three clients connect. On the left each gets a dedicated process or thread, with its own stack and memory. On the right one worker holds a small per-connection record for each client and a loop decides what to do next.
  2. One client is slow. On the left, the thread assigned to client 2 sits blocked waiting for it while holding all its memory. On the right the loop has registered interest in client 2's socket with epoll or kqueue (chapter 16) and moves on. When the socket becomes ready, the worker picks up where it left off.
  3. Now scale it up. The left side costs memory and switching for every connection, including idle ones: the AOSA chapter's example is 1,000 clients at 1 MB each, about 1 GB. The right side grows by one small state record per connection. (The figures in this diagram come from the AOSA example, not a measurement.)

About Apache

The AOSA chapter says Apache was built to spawn a copy of itself per connection, that its breadth of features and third-party modules cost extra CPU and memory per connection, and that Apache 2.4 added new multi-processing modules whose standing against event-driven servers it was too early to judge. This page does not describe Apache's modes in more detail than that. Modern Apache has other options, so treat the left side of the diagram as the classic design, not a verdict on any current product.

Kegel's menu of strategies

Kegel's page organises the options along three dimensions: how I/O is issued, how client code is controlled, and where the server code runs. It then names five popular combinations:

  1. Many clients per thread, non-blocking I/O, level-triggered readiness with select(), poll(), Solaris /dev/poll or BSD kqueue: the traditional approach.
  2. The same, edge-triggered: kqueue, Linux 2.6's epoll and others. The page warns that missed events can leave connections stuck, so it is less forgiving.
  3. Asynchronous I/O with completion notification: POSIX aio_ calls, Windows IOCP. At the time of writing, Linux AIO lacked socket support.
  4. One thread per client: simple, but each thread's stack costs memory and operating systems struggle with very many threads.
  5. Server code inside the kernel (khttpd, TUX). Kegel reports that the linux-kernel list's consensus seemed to be that the kernel should instead gain minimal hooks that help all servers.

He also lists practical details that still hold up: readiness notification is only a hint, so sockets must be non-blocking; disk reads can block even on non-blocking descriptors; select() is capped at FD_SETSIZE and poll() slows down at a few thousand descriptors; sendfile() avoids copying; and operating-system limits, such as open file descriptors, must be raised.

How nginx applies it

The AOSA chapter describes nginx as having a "modular, event-driven, asynchronous, single-threaded, non-blocking architecture". Connections are handled in a run-loop inside a small number of single-threaded worker processes, using epoll, kqueue or event ports. The chapter's stated key principle is "to be as non-blocking as possible", and it names the main remaining blocking risk as insufficient disk I/O performance, mitigated by options such as sendfile and AIO.

Workers accept new connections from a shared listening socket. The chapter says nginx does no custom connection distribution; the OS kernel handles that. On the number of workers, the chapter advises matching the CPU core count for CPU-intensive loads (TCP/IP handling, SSL, compression), and roughly one and a half to two times the core count for loads bound by disk I/O, and says administrators should test for their workload.

Common misconception: "event-driven means faster per request"

Event loops do not make any one request faster. What they save is the cost of holding many mostly-idle connections: memory and context switches. For a handful of busy connections a thread per connection is perfectly fine. The advantage shows when there are very many connections and most are waiting.

Trade-offs and lessons

Lower cost per idle connection

A small state record replaces a whole stack. This is why the design suits proxies, static files, and long-lived connections.

Never block the loop

One blocking call in a worker stalls all its connections. This is Kegel's note about disk reads blocking even on non-blocking descriptors, and AOSA's disk I/O concern. Chapter 17 returns to this rule for async code.

Harder to write

General industry pattern: code is split into callbacks or state machines instead of straight-line "read, work, write". The AOSA chapter describes per-connection processing as a sequence of phases and asynchronous steps until the request completes.

Use all the cores

One event loop uses one core, so nginx runs several workers (about one per core for CPU-bound work). AOSA says nginx's processes primarily use shared memory to communicate, and that the cache keys and metadata live in shared memory segments the workers can access.

Try it yourself

One thread, a hundred sockets

This uses socketpair(), which creates connected sockets inside your own process, so no ports are opened. The selectors module picks the best mechanism available.

import selectors, socket

sel = selectors.DefaultSelector()
pairs = [socket.socketpair() for _ in range(100)]
for a, b in pairs:
    sel.register(a, selectors.EVENT_READ)    # watch 100 "connections"

pairs[42][1].send(b"hi")                     # only one becomes ready
for key, _ in sel.select(timeout=1):
    print("ready:", key.fileobj.recv(10))

print(type(sel).__name__)   # KqueueSelector on macOS, EpollSelector on Linux

Now look at the limits that Kegel told you to raise, and, if nginx happens to be running on your machine, its process layout:

$ ulimit -n                       # max open file descriptors for this shell (often 256 on macOS, 1024 on Linux)
$ sysctl kern.maxfilesperproc      # macOS per-process descriptor limit
$ cat /proc/sys/fs/file-max        # Linux system-wide limit
$ ps aux | grep '[n]ginx'          # empty if nginx isn't running; otherwise one master and several workers

Each socket uses a file descriptor (chapter 8), so the descriptor limit is a hard ceiling on how many connections one process can hold. Studio 1 asks you to work out how far you can get before the limits and memory run out.

Distributed systems connection

General industry pattern, not from these sources: the same idea shows up one level up. Load balancers and gateways that hold millions of mostly-idle client connections (networking case study 5) are event-driven for the same reason. Event-driven servers also expose a new failure mode: with a few threads handling everything, a slow dependency makes work queue up inside the process, so you need timeouts and backpressure (chapter 14) rather than relying on the thread count to limit damage.

Key takeaways

  • C10k is Dan Kegel's name for the challenge of serving ten thousand simultaneous clients. His argument was that hardware was no longer the bottleneck; the software structure was.
  • One process or thread per connection pays memory and switching costs for every connection, including idle and slow ones.
  • nginx runs a master process plus a few single-threaded, non-blocking worker processes, each handling many connections through epoll or kqueue.
  • The cost: never block the loop, and code becomes callbacks or state machines.
  • File descriptor limits and memory per connection are the practical ceilings (Studio 1).

Why does a thread-per-connection server struggle at ten thousand mostly-idle connections?

  1. Threads are slower at reading data
  2. The network card can only handle 1,000 sockets
  3. Each connection holds its own stack and context, and switching among them costs CPU time even when most are waiting
  4. Operating systems forbid more than 1,000 threads
The AOSA chapter lists per-connection memory (heap, stack and execution context) and CPU time spent creating and switching them. Kegel's page also notes that each thread's stack consumes memory and operating systems struggle with very many threads.

What does a worker process in nginx do?

  1. Runs a single-threaded event loop that handles many connections using non-blocking I/O
  2. Starts one thread per client
  3. Reads the configuration and binds privileged sockets
  4. Handles only static files
Reading configuration and binding sockets is the master's job. Workers run unprivileged and do the actual connection handling, proxying and filtering.

What is the biggest danger when writing code in an event-loop worker?

  1. Running out of threads
  2. Using too little memory
  3. Having too many CPU cores
  4. A blocking call stalls every connection that worker is handling
One thread serves many connections, so whatever blocks it blocks them all. Both Kegel (disk reads) and the AOSA chapter (disk I/O) flag this.

How many worker processes does the AOSA chapter suggest for a CPU-intensive nginx load?

  1. Exactly one
  2. About the number of CPU cores
  3. One per client
  4. Ten thousand
For CPU-intensive loads (TCP/IP handling, SSL, compression) match the core count; for disk-bound loads, roughly one and a half to two times the cores. The chapter adds that administrators should test their own workload.

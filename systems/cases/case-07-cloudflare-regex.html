One Regex, Every CPU: Cloudflare, July 2019

On 2 July 2019, for 27 minutes, websites behind Cloudflare returned errors around the world. It was not an attack. A small change to a firewall rule contained a regular expression that, on certain inputs, made the matching engine do an explosive amount of work. It went global within seconds, and the CPUs serving web traffic were exhausted worldwide.

The pattern in one sentence

CPU exhaustion without isolation: a CPU is a shared resource, so one piece of code with unbounded cost can starve everything else on the machine, and if the same change reaches every machine at the same moment, no healthy machine is left.

The cast

All facts about the incident below come from Cloudflare's own post-mortem, published 12 July 2019. Cloudflare runs a global network of servers that sit between users and websites, so requests reach Cloudflare first (the edge idea from the networking course).

The edge servers
Machines in Cloudflare's network, in more than 180 cities according to the post, that handle HTTP and HTTPS traffic for customer sites. Each runs the software that proxies requests.
The WAF
The web application firewall. Its "Managed Rules" inspect each request for known attack patterns, such as cross-site scripting (XSS). The post says there were 3,868 rules at the time, and Cloudflare deployed dozens of new ones every week.
A regular expression
A compact pattern for matching text, like "digits, then a dash, then digits". The WAF rules used them to describe suspicious request content.
Quicksilver
Cloudflare's distributed key-value store, which the post says can push a change to machines worldwide within seconds. WAF rules travelled this way.
The CPU cores
The cores on each edge machine that serve HTTP and HTTPS traffic. The WAF rules run on those cores. From chapter 1: a core runs one stream of instructions at a time.

What happened, step by step

Step through

From a pull request to 502 errors

  1. 13:31 to 13:37 UTC: a routine change. An engineer merges a change to the WAF rules for XSS detection after approval. The build system runs the tests and they pass. The post notes the test suite could not detect excessive CPU consumption.
  2. 13:42: deployed everywhere. The change was meant to run in "simulate" mode, where traffic goes through the rule but nothing is blocked. The rule still has to run, so its CPU cost still applies. WAF rules were distributed through Quicksilver, so the update reached every location almost immediately. The standard procedure allowed rule changes to go global without the staged rollout used for other software.
  3. The regex runs on real traffic. On the requests that trigger its worst case, the pattern backtracks enormously. CPUs serving HTTP and HTTPS traffic spiked to nearly 100% across Cloudflare's servers.
  4. About 13:45 onward: errors. Customers and their visitors saw 502 error pages on Cloudflare domains. The post says an internal leader reported losing about 80% of traffic. Cloudflare's Dashboard and API also pass through the edge, so they were hit too, and staff access to internal tools was slowed.
  5. 14:07 to 14:09: the kill switch. By 14:00 the WAF had been identified as the cause (the team confirmed it with live CPU data and strace), and at 14:02 a "global terminate" was proposed. It was executed at 14:07, and by 14:09 traffic and CPU levels were back to normal worldwide. The WAF was later restored in a single city for testing and re-enabled globally at 14:52.

What backtracking is

A regular expression engine reads a pattern like a+b and tries to match it against text. When the pattern has choices, the common kind of engine tries one option, and if the rest of the pattern fails, backs up and tries another. That is backtracking. For most patterns it's fast, because most choices fail quickly or succeed on the first try.

The danger is a pattern with many ways to split the same text, followed by something that fails. Then the engine tries every way before giving up. Consider matching x+x+ against a long run of x characters: where does the first x+ stop and the second begin? Any split works, and the engine may try them all. Wrap that in another + and the choices multiply.

The Cloudflare post analyses the heart of its rule, the part .*(?:.*=.*), in a simplified form .*.*=.*, and shows how many steps its engine took to try matching:

Input, matched against .*.*=.*Steps (from the post)
x=x23
x=xx33
x=xxx45
x= followed by 20 x characters555
20 x characters with no =4,067

The failing case, no = to find, costs several times more than the matching one because the engine tries every split before concluding there is no match. The post then adds a trailing semicolon to get closer to the real rule and shows the step counts rising further. It also explains that making the quantifiers "lazy" (.*?) reduced one case but did not help the version with the semicolon. The fix the post lands on is a different kind of engine, not a cleverer pattern.

Common misconception: "a regex is just a string, so it must be cheap"

A regex is a tiny program, and its running time depends on both the pattern and the input. An attacker (or an unlucky ordinary request) controls the input. The post says this specific regex was an easy one to write badly: its first listed contributing factor is that an engineer wrote a regex "that could easily backtrack enormously".

The pattern: no isolation for CPU inside a process

What made one regex a global outage was where it ran. This section is a general pattern, grounded in the course chapters; the post itself describes the CPU exhaustion and the missing guards.

  • A core runs one thing at a time. The scheduler (chapter 7) divides a core's time among runnable work, but it can't make more time. If the work that needs doing in a request is unbounded, every request on that core pays for it.
  • Nothing bounds work inside a process. Memory and CPU limits are usually set around a whole process or container, not around one function call. A regex in the request path executes in the same threads as everything else. Unless the engine or the code enforces a limit, there is no wall between "inspect this request" and "serve the next one".
  • The check was in the hot path. The WAF rules run on the request path, so a slow rule is a tax on the traffic it inspects, not only on suspicious traffic.

Analogy: the shared photocopier

An office has one photocopier. Everyone's job is a few pages, so the queue moves. Then someone submits a job with a setting that accidentally turns each page into a thousand copies. Nobody else's job is large, but nobody else's job gets done, and putting more people in the office just lengthens the line.

Where it breaks down: a copier has a visible paper counter and an off switch. A CPU gives no warning that a particular line of code is eating it, which is why the post's list of fixes includes both a guard and a test that measures cost.

Cloudflare's stated remediations

The post separates what was done immediately from what was planned. Here is what it says, with no additions:

  • Done: stopped all WAF release work; re-introduced an excessive-CPU protection that had been accidentally removed during a WAF refactoring weeks earlier; manually inspected all 3,868 managed rules for other cases of excessive backtracking.
  • Planned, with dates given in the post: add performance profiling for all rules to the test suite (ETA 19 July); switch the WAF to the RE2 or Rust regex engines, both described as providing run-time guarantees (ETA 31 July).
  • Process: change the standard procedure to use staged rollouts for rules, like other Cloudflare software, while keeping an emergency global option for active attacks.
  • Also listed: an emergency way to take the Dashboard and API off Cloudflare's edge; automating status-page updates; and, longer term, moving away from the Lua-based WAF to a new firewall engine.

The post's own list of eleven contributing factors is more interesting than the regex. Besides the backtracking pattern, it names the missing CPU protection, the regex engine's lack of complexity guarantees, tests that couldn't see CPU use, the procedure that allowed a non-emergency rule to go global without staging, a slow rollback plan, a slow first alert, and the trouble engineers had reaching internal systems during the incident.

What "run-time guarantees" means

The post says the long-term fix is a regex engine with linear-time guarantees, based on the approach Ken Thompson described in 1968, rather than one that backtracks. Such an engine tracks every position the pattern could be in at once as it reads the text, so doubling the text roughly doubles the work. The post names RE2 and the Rust regex engine as the engines it planned to move to, both of which it describes as providing run-time guarantees.

Trade-offs and lessons

Bound the work

Anything that runs on every request needs an upper limit on cost: an engine with a guarantee, a timeout, or an enforced budget. The removed CPU protection and the lack of engine guarantees are both on the post's list.

Test for cost, not just correctness

The tests passed because they checked behaviour. The plan to add performance profiling for all rules is the post's response.

Stage the rollout

The same change on one machine, then a city, then everywhere would have limited the damage. The post's process fix is staged rollouts for rules, with a deliberate exception for emergencies.

Keep the repair path independent

The post notes that engineers' access to internal tools was hindered because those tools used Cloudflare's own edge, and that the emergency bypass was rarely used. The related lesson from networking case 6, Facebook, applies directly.

Compare with another well-known outage in the networking course: networking case 7, S3 in 2017, was a small input with a big blast radius. Here the input was a rule instead of a command, but the shape is the same: one change, one global scope, and no wall between the first machine and the last. A cellular design (the S3 case's lesson) or a staged rollout limits blast radius by making sure the first failure is small.

Try it yourself

Watch time grow with input size

This script is safe: the largest input is 22 characters and the whole run takes well under a second. Save as rx.py and run python3 rx.py. It compares a nested-quantifier pattern with a simple one that means the same thing in practice.

import re, time

evil = re.compile(r"^(x+x+)+y")    # nested quantifiers: many ways to split the x's
safe = re.compile(r"^x+y")         # same intent, one way to match

for n in (10, 14, 18, 20, 22):
    s = "x" * n                     # no 'y' at the end, so the match must fail
    t = time.perf_counter(); evil.match(s); a = time.perf_counter() - t
    t = time.perf_counter(); safe.match(s); b = time.perf_counter() - t
    print(f"n={n:2d}  nested: {a:.4f} s   simple: {b:.6f} s")
n=10  nested: 0.0000 s   simple: 0.000001 s
n=14  nested: 0.0003 s   simple: 0.000000 s
n=18  nested: 0.0048 s   simple: 0.000001 s
n=20  nested: 0.0199 s   simple: 0.000007 s
n=22  nested: 0.0796 s   simple: 0.000002 s

On the machine used to write this page, every two extra characters made the nested pattern about four times slower, which means roughly doubling per character, while the simple pattern stayed at microseconds. Your numbers will differ. Do not raise n much: at 30 characters this would run for a long time, which is the whole lesson.

One more observation, for honesty: I also tried the simplified shape from the post, .*.*=.*;, in Python's re and it finished instantly on a 1,600-character input. Different engines and versions optimise different patterns, which is part of why Cloudflare wanted an engine with a stated guarantee instead of relying on a pattern happening to be fast.

To see how busy your own machine's cores are, these commands are read-only:

$ top -l 1 | head -5                       # macOS: CPU usage summary
$ top -bn1 | head -5                         # Linux: the same, batch mode
$ ps -A -o pid,%cpu,comm | sort -k2 -nr | head -5 # the five hungriest processes

Distributed systems connection

Redundancy only protects you from independent failures. Hundreds of identical servers running identical software on identical input fail together, which is the correlated-failure idea from networking chapter 15. Configuration pushes are as dangerous as code deploys: the post stresses that Quicksilver can push a change to every machine in seconds, which is wonderful for speed and terrible for blast radius. Safe systems treat config as code: review it, test it, stage it, and make it easy to roll back or switch off a single component. Cloudflare's "global terminate" is exactly that kind of kill switch.

Key takeaways

  • A WAF rule containing a regex that backtracked enormously exhausted CPU on machines serving HTTP and HTTPS worldwide for 27 minutes on 2 July 2019.
  • Backtracking engines try alternatives and retry on failure; patterns with many overlapping choices can take time that explodes with input size.
  • CPU is a shared resource with no isolation inside a process. A per-request cost with no upper bound is a risk for every request on the machine.
  • The change reached every machine in seconds because WAF rules skipped the staged rollout used for other software.
  • Cloudflare's stated fixes: restore the CPU protection, profile rules in tests, move to engines with run-time guarantees (RE2 or Rust), and stage rule rollouts.

Check your understanding

What does a backtracking regex engine do when part of a pattern fails to match?

  1. It gives up and reports no match immediately
  2. It restarts the whole program
  3. It backs up and tries other ways to match the earlier parts of the pattern
  4. It sends the request to a different server
Backing up and trying alternatives is backtracking. With many overlapping choices the number of alternatives can explode, which is how a short input can cost a huge amount of CPU.

Which factor from the post turned a bad regex into a worldwide outage within seconds?

  1. The regex was written in Lua
  2. WAF rules could be deployed globally at once, without the staged rollout used for other software
  3. The servers were physically damaged
  4. Customers all changed their settings together
Quicksilver distributes changes worldwide in seconds, and the procedure allowed rule changes to skip staging. One bad rule therefore reached every location together.

Why does the post's long-term fix involve a regex engine with run-time guarantees?

  1. Because the matching time then has a known bound relative to input size, no matter how the pattern is written
  2. Because it makes regexes shorter
  3. Because backtracking is illegal
  4. Because it removes the need for tests
An engine with a linear-time guarantee can't hit exponential blow-ups. The post names RE2 and the Rust regex engine, and still plans profiling in tests as an extra layer.

What does this case teach about CPU as a shared resource?

  1. The scheduler guarantees every request a fair share, so one rule cannot hurt others
  2. CPU limits always apply to individual function calls
  3. More cores per machine eliminate the problem
  4. Work with no upper bound on cost can starve everything else on the machine unless something enforces a limit
A scheduler shares time but cannot create more of it. Without an engine guarantee, timeout or CPU protection, unbounded work in the request path takes cores away from all other work.

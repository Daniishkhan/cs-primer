fsyncgate: When fsync Fails

In 2018, PostgreSQL developers discovered that an assumption their code relied on did not hold: that a successful fsync() means all of a file's data is on disk, so a failed one can simply be retried. On Linux, a retry could report success for data that had already been thrown away. The story is a lesson in reading the fine print of the promises your operating system makes.

The pattern in one sentence

Durability lies: a "success" from a storage API only means what its documentation says it means, so a system that stores data must know exactly which failures are reported, how many times, and what state the data is in afterwards.

The cast

You met all of these in chapter 8 and chapter 9. Here is how they play their parts:

PostgreSQL
A widely used open-source database. It keeps table data in files and lets the operating system cache them. At a checkpoint it asks the kernel to make that data durable by calling fsync(). Per the PostgreSQL wiki, its checkpointing assumes that a successful fsync() means all of a file's data is on disk.
The page cache
The kernel's in-memory copy of file contents. write() copies bytes into it and marks the pages dirty (changed, not yet on disk). Background writeback sends them to the device later.
The storage device
The disk or SSD where the data finally has to land. It can fail: the wiki and LWN both mention that write-back can hit errors, and LWN gives the most common real-world cause as a USB drive pulled out mid-write.
fsync(fd)
The system call that is supposed to turn "written" into "saved". If the kernel cannot write the data, fsync returns an error such as EIO.

What happened, step by step

Craig Ringer reported the problem to the PostgreSQL developers' mailing list at the end of March 2018, according to Jonathan Corbet's article in LWN. The sequence below follows the behaviour the sources describe for older Linux kernels, before the later kernel improvements described below.

Step through

A failed fsync that "succeeds" on retry

  1. The database writes. write() copies the bytes into the page cache and marks the page dirty. The call returns quickly. Nothing is on the disk yet.
  2. Checkpoint: fsync(). The database asks the kernel to make the file's data durable. The kernel starts pushing the dirty page to the device.
  3. The device fails the write. A hardware error stops the page from being written. LWN reports that when a buffered write fails, filesystems typically discard the data in the affected pages and mark them clean.
  4. The error is reported once, and the page now looks clean. fsync() returns an error. But the page is no longer dirty, so the kernel sees nothing left to write. The PostgreSQL wiki notes that on Linux 4.14 and 4.16 onward the error is reported only once, so retrying is still unsafe.
  5. The database retries, as it always had. The page is clean, so there is nothing to flush and the second fsync() returns success. Per the wiki, on older kernels a retried fsync() could falsely report success.
  6. The response. A later read may return different data than was written, and memory pressure can drop the page entirely. PostgreSQL changed to treat an fsync() failure as unrecoverable: the wiki says it "will now PANIC on fsync() failure".

Common misconception: "an error means the data is still there to retry"

It is natural to think a failed call leaves things as they were, like a failed bank transfer. For a buffered write that failed in the background, it does not. The error tells you something went wrong once; the dirty data that would let a retry work may already be gone.

Why PostgreSQL missed errors even on better kernels

The story has a second layer. PostgreSQL uses several processes, and a single checkpointer process calls fsync(). LWN explains that it often opens a file just before syncing it. Linux 4.13 introduced new write-back error reporting, but the wiki says in 4.13 and 4.15 fsync() reported only errors that happened after the file was opened. A file opened by the checkpointer after the failure would look fine. The wiki says a later fix (Linux 4.14 and 4.16 onward) makes the first error on a file reach someone even if the file was closed and reopened in between, but still only once.

The wiki also lists other systems. On FreeBSD the buffers stay dirty after a failure, so later calls retry and likely fail again; on NetBSD and Darwin (macOS) they are invalidated, as on Linux. So the problem was not a one-OS quirk.

What kernel developers said

As reported by LWN, the kernel side explained why they behave this way. Ted Ts'o pointed out that the most common I/O error is a USB drive removed mid-write, and that keeping dirty pages that can never be written could use up system memory. Dave Chinner and Ted Ts'o argued that direct I/O, where the application bypasses the page cache and manages its own caching, is the proper long-term answer for PostgreSQL. Andres Freund agreed it is the best long-term option but called the migration a large effort.

In 2020, Rebello and colleagues at the University of Wisconsin-Madison published "Can Applications Recover from fsync Failures?" at USENIX ATC. They studied ext4, XFS and Btrfs and found that, in all three, pages are always marked clean after a failure. They also studied PostgreSQL, LMDB, LevelDB, SQLite and Redis, and concluded that none of the failure-handling strategies they saw was sufficient: failed fsync calls can lead to outcomes such as data loss and corruption.

The pattern: durability APIs have error semantics

Chapter 9 taught that "written is not saved". This case adds a second lesson: "failed" is not "unchanged". Every durability call has two contracts. One is what success proves. The other is what a failure leaves behind: is the data still dirty, was it dropped, will the error be reported again, to whom? Those answers depend on the operating system, the filesystem and the kernel version, as the wiki's comparison across systems shows.

Analogy: the delivery that was never rescheduled

You hand a parcel to a courier and ask for a receipt on delivery. The courier tries, the address turns out to be wrong, and they phone you once to say "failed". They throw the parcel away so the van stays light. You ring back and ask "is it delivered now?" and the depot, seeing no parcel on the books, says "nothing outstanding". The receipt answers a question you didn't mean to ask.

Where it breaks down: the kernel's motive is not carelessness. As LWN reports, keeping every unwritable page could exhaust memory, and a design that is right for a pulled USB stick can surprise a database.

Trade-offs and lessons

Fail loudly, not softly

PostgreSQL's fix is blunt: crash. After an fsync failure the database no longer knows which writes are safe, so it stops rather than guess. General industry pattern, not from these sources: a database then restarts and replays its write-ahead log (chapter 9), which records changes before they are applied to the data files, to rebuild a consistent state.

Know the platform

The wiki's survey shows different behaviours in Linux versions, FreeBSD, NetBSD, OpenBSD and Darwin. "Portable" code that depends on error behaviour is not portable.

Other designs exist

Direct I/O moves cache management into the database, removing the kernel's choices but adding a large engineering cost. The wiki also notes MySQL/InnoDB and MongoDB/WiredTiger made similar changes afterwards.

Verify, don't trust

General industry pattern: store a checksum with each block and check it when you read. A checksum cannot stop a lost write, but it turns silent corruption into a detected error. The crash-safe log in Lab 2 does this.

What the sources do not settle

The wiki says discussion continued about extra safeguards, such as using filesystem error counters or filesystem-wide flushing, and that file-descriptor passing to the checkpointer was not adopted. Linux behaviour has also changed over time, so check the kernel version before relying on any detail in this page.

Try it yourself

See what your machine reports

These are read-only. They don't make fsync fail (that needs a failing device), but they show the pieces of the story on your system.

$ uname -r                          # kernel version; error reporting changed across 4.13-4.16 on Linux
$ cat /proc/sys/vm/dirty_writeback_centisecs   # Linux only: how often background writeback wakes up
$ cat /proc/sys/vm/dirty_expire_centisecs      # Linux only: how old dirty data gets before it must be written

Then run this Python script. It saves a file the careful way and shows that an fsync error reaches your program as an exception you must not ignore:

import os, tempfile

with tempfile.NamedTemporaryFile() as f:
    f.write(b"hello")
    f.flush()                    # Python's buffer -> the kernel
    os.fsync(f.fileno())         # the kernel's page cache -> the device
    print("fsync returned: data should be durable")

try:
    os.fsync(999)                # not an open file: forces an error
except OSError as e:
    print("fsync reported an error:", e)   # never swallow this

import fcntl
print("F_FULLFSYNC available:", hasattr(fcntl, "F_FULLFSYNC"))  # True on macOS

On macOS, plain fsync does not force the drive's own cache to flush, but F_FULLFSYNC does (chapter 9). Whatever the call, ask what a failure of it leaves behind.

Distributed systems connection

Replicated databases often count a write as safe once enough replicas have "durably" stored it. That count is only as good as each replica's fsync. A node whose fsync lied has acknowledged data it doesn't have, and a quorum built on lies can lose committed writes. General industry pattern, not from these sources: this is why systems crash a node whose storage reports an error and re-sync it from its peers, instead of letting it carry on. Trust, but verify with checksums.

Key takeaways

  • PostgreSQL assumed a failed fsync() could be retried. On Linux, a failed write-back could mark pages clean, so a retry could succeed without the data being written.
  • Error reporting had further gaps: errors before a file was opened could be missed, and errors were reported only once.
  • PostgreSQL now PANICs on fsync() failure, and the 2020 USENIX study found no studied application's handling to be sufficient.
  • Ask both questions of any durability API: what does success prove, and what does failure leave behind?
  • Checksums and recovery from a log turn silent loss into something detectable and repairable.

Check your understanding

Why could a retried fsync() succeed even though the data never reached the disk?

  1. The disk repaired itself between the calls
  2. fsync only checks the file's name
  3. After the failed write-back, the pages were marked clean, so there was nothing left to flush
  4. The kernel retried the write in secret
LWN and the PostgreSQL wiki describe pages being marked clean after a write-back error. A clean page has no pending work, so the second fsync has nothing to fail on, and the data may be gone.

What was PostgreSQL's response?

  1. Retry fsync in a loop until it succeeds
  2. Treat an fsync failure as fatal (PANIC) instead of retrying
  3. Switch all writes to memory only
  4. Ignore errors from fsync
The wiki: "PostgreSQL will now PANIC on fsync() failure." Once the state of the data is unknown, stopping is safer than continuing as if nothing happened.

Which statement about the kernel developers' reasoning is supported by the LWN article?

  1. They wanted data loss to be hidden
  2. Linux had no error reporting at all
  3. All operating systems keep failed pages dirty
  4. Keeping unwritable dirty pages could exhaust system memory, for example after a USB drive is pulled out
Ted Ts'o's argument, as reported by LWN. The design suits some failures but surprised applications that assumed retry was safe. The wiki also shows that other systems differ.

Which general practice helps detect, though not prevent, silent data loss?

  1. Storing a checksum with each block and verifying it on read
  2. Calling write() twice
  3. Using a bigger page cache
  4. Closing and reopening the file
A checksum cannot make a failed write succeed, but a read of a lost or stale block will fail verification, turning silent corruption into a detected error you can repair from a log or replica. Reopening files, in fact, made some errors easier to miss.

Priority Inversion on Mars

Mars Pathfinder landed on 4 July 1997 and was first reported as a flawless success. A few days later the spacecraft began resetting itself. The cause was a classic software bug in how a few tasks shared one lock, and it was fixed by changing a single setting, from Earth.

The pattern in one sentence

Priority inversion: when a high-priority task has to wait for a lock held by a low-priority task, any medium-priority task can keep the low one from running, so in effect the medium task outranks the high one, unless the lock holder temporarily inherits the waiter's priority.

The cast

The scheduling ideas come from chapter 7, the lock from chapter 12. The names below come from Glenn Reeves, who led the Pathfinder flight software team, in an email written in December 1997 in reply to Mike Jones' summary of a conference talk by David Wilner of Wind River Systems.

VxWorks
The real-time operating system running on Pathfinder's single CPU, supplied by Wind River Systems. It uses preemptive priority scheduling: a higher-priority task that is ready to run always gets the CPU before a lower one.
bc_sched and bc_dist
The two bus management tasks. The spacecraft's 1553 data bus runs on an 8 Hz schedule, so each cycle is about 0.125 seconds. bc_sched sets up the bus transactions for the next cycle and is the highest-priority task apart from the operating system's own tExec. bc_dist collects and distributes the results and is the third-highest. Each checks every cycle that the other has finished.
ASI/MET
A low-priority, infrequently running task handling the lander's meteorological instruments. Unlike most tasks, it received its data through a VxWorks pipe(), which uses select().
Medium-priority tasks
Various other tasks that ran above ASI/MET but below the bus tasks.
The mutex
A lock (chapter 12) that VxWorks' select() machinery takes to protect its internal wait list. Reeves traces the stall to this mutex: ASI/MET was preempted inside selNodeAdd() while giving it back.

Two accounts, one story

Mike Jones' page relays Wilner's talk, which describes the shared resource as an "information bus" protected by mutexes and the reset as triggered by a watchdog timer. Reeves' email, which is the more detailed account by someone on the flight team, names the specific tasks and says the reset came from bc_sched noticing that bc_dist had not finished. Reeves does not mention a watchdog by name. The core mechanism is the same in both.

What happened, step by step

Step through

One bus cycle goes wrong, then right

  1. The low-priority task takes a lock. ASI/MET calls select(), which uses a mutex to protect the wait list. Per Reeves, the task was in the middle of giving that mutex back when a medium-priority task preempted it.
  2. The high-priority task needs it. Before ASI/MET gives the mutex back, bc_dist tries to send new ASI/MET data through pipeWrite() and blocks on that mutex. So far this is only a short wait.
  3. Medium tasks interfere. Several medium-priority tasks become ready. They outrank ASI/MET, so it cannot run to finish its work and release the mutex. The high-priority task is stuck waiting behind tasks that rank below it.
  4. The deadline check fires. When bc_sched wakes for the next cycle, it finds that bc_dist has not finished. That breaks a hard deadline, so it declares an error and the spacecraft resets.
  5. With priority inheritance, the waiter lends its rank. While bc_dist waits, ASI/MET temporarily runs at bc_dist's priority. The medium tasks cannot preempt it, it finishes quickly and releases the mutex, and bc_dist proceeds.
  6. The patch. The team changed the flag that enables priority inheritance on the semaphores that select() creates. The resets stopped.

Finding it, and fixing it

Reeves says the team had seen the problem before landing but could not reproduce it, and that pre-launch testing had only covered best-case, high-data-rate science activity. The data rates and science activity on the surface turned out to be higher than expected, which made the problem worse.

The flight software included trace and log tools that the team had kept in on purpose. Reeves credits David Cummings with the original facility and Lisa Stanley of Wind River with extending it to cover pipe, message queue, interrupt, select and tExec activity. With these, the team reproduced the failure on a ground system in under 18 hours, and the priority inversion became clear from the trace. Wilner's account, as relayed by Jones, adds that engineers ran an exact replica of the spacecraft with tracing on, and that VxWorks mutexes take a boolean that turns on priority inheritance. That boolean had been off.

The two accounts differ a little on how the change was delivered. Wilner (via Jones) describes uploading a short C program that flipped global variables through a C interpreter left on the spacecraft. Reeves says the change was made through a global variable in the select library, and the software was patched by sending the differences between the onboard and Earth copies, which custom onboard software validated and applied. Either way, the mechanism is a flag flipped remotely, which was possible because the debugging and update machinery had not been stripped out.

The change affected every select semaphore created afterwards. Reeves says the team could not easily limit it to the one pipe, so Wind River analysed the effect, concluded that the performance cost would be minimal and that select() behaviour would not change if only one task waits on each file descriptor, and the team tested it extensively.

Common misconception: "the Mars computer crashed"

Nothing crashed. The reset was a safety response working as designed: a task checking another task's deadline concluded something was badly wrong and restarted the system. The spacecraft was designed to survive multiple resets during atmospheric entry. According to Reeves, a reset reinitialised hardware and software and ended the current ground-commanded activities. Data already in RAM was recovered as long as power was kept, and the rest of that day's activities were postponed to the next day.

The pattern: inversion without a deadlock

Chapter 13 covered deadlock, where two tasks wait for each other forever. Priority inversion looks similar from the outside, since a task waits too long, but nothing is stuck for good. The low task would release the lock, if it were allowed to run. The delay is caused by a third party: a task with no interest in the lock whose only crime is ranking between the other two.

Priority inheritance

While a high-priority task waits for a lock, the holder runs at the waiter's priority. This is the fix that Pathfinder used. The theory of the protocols is credited in Jones' page to Lui Sha, John Lehoczky and Raj Rajkumar of Carnegie Mellon University (their 1990 paper on priority inheritance protocols).

Other approaches (general pattern)

General industry pattern, not from these sources: keep critical sections tiny, avoid sharing locks across priority levels at all, or use schemes such as a priority ceiling. Real-time systems often offer a choice of mutex protocols.

Analogy: the VIP stuck behind the road crew

A VIP's car is blocked by a slow tractor on a narrow road. A group of ordinary cars pulls in between and keeps the tractor from pulling over. Priority inheritance is a police escort giving the tractor the right of way until it clears the road.

Where it breaks down: real escorts are given by people. The scheduler does it automatically, but only if the lock was created with that behaviour turned on, which is exactly what was missing here.

Trade-offs and lessons

Keep the tools in

The trace facility and the ability to patch remotely were what made diagnosis and the fix possible. Wilner's talk, as relayed by Jones, drew the same conclusion: debugging facilities in the flight system made in-field correction possible.

Safety nets can look like the bug

The reset prevented worse outcomes, but also masked the cause. Jones' page says engineers had seen one or two unexplained resets in pre-flight testing and attributed them to a hardware glitch.

Optimising away correctness

Jones' page says the judgement that priority inheritance was too costly for a time-critical task turned out to be wrong. Reeves is gentler: the team likely misjudged how the select and pipe mechanism worked, and the robust design made the problem seem lower priority.

Test beyond the best case

Testing at the expected data rates missed a problem that appeared only at the higher rates seen on Mars.

Try it yourself

Look at priorities on your own machine

Ordinary desktop schedulers are not real-time, but priorities still exist. These commands are read-only.

$ ps -o pid,pri,ni,comm -p $$        # priority and nice value of your shell (macOS and Linux)
$ ps -eo pid,pri,ni,comm | head       # a few other processes for comparison
$ man pthread_mutexattr_setprotocol   # POSIX: where priority inheritance (PTHREAD_PRIO_INHERIT) is described, if your system has the page

And a small Python script. It shows that Python's threading.Lock is just a lock: it has no notion of priorities, so there is nothing to invert or inherit. Real-time systems like VxWorks put priorities into the lock itself.

import os, threading

print("nice value of this process:", os.getpriority(os.PRIO_PROCESS, 0))

lock = threading.Lock()
print([n for n in dir(lock) if not n.startswith("_")])
# acquire, release, locked... - no priority or protocol setting anywhere

Distributed systems connection

General industry pattern, not from these sources: the same shape appears in services: a critical request waits on a shared resource such as a database connection, a lock or a thread pool slot that is held by low-importance background work, while mid-importance work keeps the holder from finishing. Chapter 14's queues and bounded pools help, as do separate pools per priority. The general lesson is that a shared resource quietly undoes any priority scheme built on top of it.

Key takeaways

  • A low-priority task held a mutex; medium-priority tasks kept it from finishing; the high-priority bus task missed its deadline and the system reset.
  • Priority inversion is neither a crash nor a deadlock. It is a delay caused by a task that isn't even involved with the lock.
  • Priority inheritance fixes it: the lock holder borrows the waiter's priority until it releases the lock.
  • Pathfinder was fixed remotely by enabling inheritance, because trace tools and update machinery had been left in.
  • Test at realistic load. The bug appeared under heavier use than pre-launch tests.

Check your understanding

What made this a priority inversion?

  1. Two tasks each waited for the other forever
  2. Medium-priority tasks effectively delayed the high-priority task by keeping the low-priority lock holder from running
  3. The low-priority task was given the highest priority by mistake
  4. The CPU ran slower than expected
The high task was waiting for the low one, and the medium tasks kept the low one off the CPU, so in effect they outranked the high task.

How does priority inheritance fix the problem?

  1. It makes the mutex faster
  2. It removes the medium-priority tasks
  3. It makes every task the same priority
  4. The lock holder temporarily runs at the priority of the highest task waiting for the lock
With the holder boosted, the medium tasks can't preempt it. It finishes its critical section, releases the lock and drops back down.

Why could the engineers apply the fix from Earth?

  1. The flight software kept its debugging and update facilities, and the fix was a flag change
  2. Pathfinder had a second spare computer
  3. The reset wiped the bug away
  4. The fix was done by the astronauts
The trace tools let the team reproduce and diagnose the bug on the ground, and the software could be patched remotely with a small change to enable priority inheritance.

How is priority inversion different from deadlock?

  1. They are the same thing
  2. Inversion only happens on Mars
  3. In inversion the lock holder would eventually finish if it were allowed to run; in deadlock nobody can ever proceed
  4. Deadlock involves only one task
Inversion is a scheduling delay with no cycle of waiting. Remove the interfering medium tasks, or lend the holder a higher priority, and progress resumes.

Redis: One Thread, Very Fast

Redis is a database that can answer a huge number of requests per second, and the part that runs your commands is, for the most part, a single thread. That sounds like a mistake until you see why it works, and then it becomes a precise tool for reasoning about where it hurts: one slow command, one long script, or one fork and every other client waits.

The pattern in one sentence

Single-threaded event loop: if every operation is tiny and nothing ever blocks, one thread serving many connections can beat many threads fighting over shared data, but the price is that any one slow operation delays everybody, so the design only holds while you keep operations small.

The cast

This case study applies two chapters you've already read: the memory hierarchy (chapter 2) and event loops (chapter 16). Here is how the pieces show up in Redis.

The dataset in RAM
Redis keeps its whole dataset in memory. Its own FAQ says the in-memory representation of complex data structures is "much simpler to manipulate" than the same structures on disk, so Redis "can do a lot with little internal complexity".
The event loop
One process serves all clients using multiplexing. Redis's latency documentation says this means it "can serve a single request in every given moment, so all the requests are served sequentially", and that it is designed not to block on system calls such as reading or writing a socket. That's the select/epoll/kqueue idea from chapter 16.
Simple commands
Everyday commands like GET, SET and LPUSH run in constant, very small time. The same page says Redis's own processing time is usually "in the sub microsecond range".
Background work
Persistence needs to write the dataset to disk. For snapshots, Redis calls fork and lets a child process do the writing, relying on the copy-on-write behaviour of virtual memory (chapter 6).
The observers
Two built-in tools exist because the design makes latency spikes a known risk: the slow log (SLOWLOG) and the latency monitor (LATENCY).

"Single-threaded" is an approximation

Redis's own latency documentation says it uses a mostly single-threaded design. Since version 2.4 it has used extra threads for some slow disk operations in the background, and the FAQ adds that since 4.0 it has threaded actions for deleting objects in the background and for blocking commands implemented by modules. We'll look at the I/O threads added in the 6.0 line near the end. The point of this case is the model: commands are run one at a time.

Why one thread can be fast

Chapter 10 taught that threads exist so several things can happen at once, and chapters 11 and 12 taught what that costs: races, then locks to prevent races. Redis sidesteps the whole bill. Its sources give you the ingredients; the conclusion below is the general reasoning (marked as such):

  • The data lives in RAM. No command waits for a disk read to answer. From chapter 2, RAM is roughly a hundred nanoseconds away and the disk is orders of magnitude further.
  • Commands are tiny. A command that finishes in about a microsecond can be followed immediately by the next one. Redis's FAQ notes that with pipelining, an instance on an average Linux system can deliver 1 million requests per second, and that CPU is not often the bottleneck: Redis is usually "either memory or network bound".
  • Nothing blocks. The loop only touches sockets that are ready, as in chapter 16, so one slow client doesn't stall the thread.
  • General reasoning: no locks needed. If only one thread ever touches the data structures, two commands can never interleave halfway through, and there is nothing to lock. Each command is atomic by construction, and the Redis docs lean on this when they describe atomic operations on data types.

Put another way, Redis trades parallelism for simplicity and predictability. A single core running tiny commands back to back with no lock contention can do an enormous amount of work.

Where it hurts, step by step

The same property that makes Redis simple makes it fragile. Step through four moments in a Redis server's life.

Step through

One thread, one queue

  1. A normal moment. Clients send small commands. The loop reads one, runs it against the in-memory data, writes the reply and moves on. Each command takes a tiny fraction of a millisecond, so even a long queue drains almost at once.
  2. A slow command arrives. Client C runs KEYS *, which walks every key in the database. Redis's documentation gives its complexity as O(N) in the number of keys. The loop is now busy with one request.
  3. Everyone else waits. Clients A and B sent trivial commands, but they sit in the queue until the long one finishes. Their commands are not slow; they are stuck behind a slow one. This is head-of-line blocking, and it is why Redis's docs say that when a request is slow to serve, "all the other clients will wait".
  4. Persistence forks. To write an RDB snapshot, Redis calls fork. The child gets a copy of the parent's address space, but copy-on-write means both share the same physical pages. The fork itself runs in the main thread, and Redis's docs warn it "can induce latency by itself" because the page tables must be copied.
  5. Writes make pages diverge. While the child saves, clients keep writing. The first write to a shared page forces the kernel to copy that page so the child's snapshot stays frozen. Heavy write traffic during a snapshot means more copies and more memory.

The four ways it hurts, in the sources' own terms

Slow commands

Redis's latency page says commands that operate on many elements, such as SORT, LREM and SUNION, can take "a considerable amount of time", and calls KEYS in production a "VERY common source of latency". The KEYS page puts it more plainly: use extreme care in production because it "may ruin performance when it is executed against large databases". It also says that on an entry-level laptop it can scan a 1 million key database in 40 milliseconds. Forty milliseconds is nothing to a person, but it is a very long wait next to commands that finish in about a microsecond. The documented alternative is the incremental SCAN family.

Long Lua scripts

Redis can run Lua scripts on the server. Its scripting documentation says Redis guarantees atomic execution and that "all server activities are blocked during its entire runtime". That is exactly what makes scripts safe (no interleaving) and exactly what makes a long one dangerous. The docs describe SCRIPT KILL as the way to interrupt a slow script, and only for scripts that haven't modified the dataset.

Fork and copy-on-write

The persistence page says fork() can be time consuming for big datasets and may mean Redis stops serving clients "for some milliseconds or even for one second" if the dataset is very large and the CPU is not fast. The latency page walks through the arithmetic for page tables: with 4 kB pages, a 24 GB instance needs a page table of about 48 MB to copy. Then comes copy-on-write: the FAQ explains a page is duplicated only when it changes in parent or child. The latency page adds that with Linux transparent huge pages enabled, a few event-loop runs can cause copy-on-write of almost the whole process memory, so it advises disabling them. See chapter 6 for why a fork is cheap in theory and costly in practice.

One core is one core

A single thread can use only one core for command execution. The FAQ's answer to "how can Redis use multiple CPUs or cores?" is to start multiple instances on the same machine and treat them as different servers, or to shard. Redis Cluster automates that split: its docs describe data being automatically sharded across multiple Redis nodes.

Common misconception: "single-threaded means slow"

Redis is mostly memory- or network-bound, not CPU-bound, according to its own FAQ. The risk with a single thread is not low average speed. It is tail latency: the worst 1% of requests, the ones that happened to queue behind something slow. Averages hide that, which is why Redis ships tools built around spikes.

The pattern: a single-threaded event loop

Strip away Redis and the pattern is this (a general pattern, also used by Node.js, which the Redis latency page compares itself to):

  1. Keep all the shared state on one thread, so it needs no locks.
  2. Use readiness notifications (epoll on Linux, kqueue on macOS) so the thread never waits on a single connection.
  3. Keep each unit of work short, because the next client in line is paying for it.
  4. Push anything slow somewhere else: a child process, a background thread, another instance.

Analogy: one very fast cashier

Picture a shop with one cashier who never leaves the till and has everything in reach. Scanning one item takes a heartbeat, so the line moves fast and there is no arguing over who touches the cash drawer. But if a customer asks the cashier to count every coin in the safe, the whole shop waits. The fix isn't a faster cashier; it's not asking the cashier for the safe count while the line is long.

Where it breaks down: the cashier knows when they are being slow. A Redis client has no idea that its harmless-looking command is the one holding everybody up, which is why the slow log exists.

The tools: seeing the spikes

Redis includes two built-in views of this problem, both documented on redis.io:

  • The slow log (SLOWLOG GET) records commands that exceeded a configurable execution time (slowlog-log-slower-than), keeping at most slowlog-max-len entries. The docs make a subtle point: the measured time "does not include I/O operations like talking with the client, sending the reply and so forth", only the time spent executing, which is "the only stage of command execution where the thread is blocked and can not serve other requests in the meantime". So it measures exactly the part that hurts everyone else.
  • The latency monitor (LATENCY LATEST, LATENCY HISTORY, LATENCY DOCTOR) samples latency-sensitive code paths such as command, fork, AOF writes, and key expiry, and keeps a time series per event. It's off by default; you turn it on by setting latency-monitor-threshold in milliseconds.

Its diagnosing-latency page begins with a checklist whose first item is "make sure you are not running slow commands that are blocking the server", checked with the slow log. It also tells you to check for intrinsic latency from your kernel or hypervisor with redis-cli --intrinsic-latency, and notes the test is CPU intensive and must be run on the server, not from a client.

Optional I/O threads

The Redis 6.0 release notes describe threaded I/O as something Redis "can now optionally" use. The redis.conf file explains the knob: threading is disabled by default, it is suggested only on machines with at least four cores (leaving a spare), io-threads 1 means "just use the main thread as usual", and when enabled the threads handle socket writes and, in the 6.0 file, reads only if io-threads-do-reads is set (default no). The current file describes reads and protocol parsing as also threaded. The sections I read describe the extra threads as doing I/O; they don't describe those threads running your commands. So the model above, one thread runs commands in order, still describes where slow commands hurt. Check the documentation for the version you run.

Trade-offs and lessons

What you gain

Simplicity: no locks, no deadlocks (chapter 13), atomic commands. Predictable behaviour when commands are small, and very high throughput on one core.

What you pay

Head-of-line blocking for any slow operation, a hard ceiling of one core for execution, and pauses at fork time. Your worst request is governed by your worst neighbour.

How teams cope (general practice)

Keep commands O(1) or O(log N), iterate with SCAN instead of KEYS, avoid long scripts, give the instance enough free memory for copy-on-write, watch the slow log, and shard when one core isn't enough. The latency page also suggests running slow queries on a replica.

The general lesson

Concurrency models are trade-offs, not rankings. Chapter 18 compares threads, events, actors and channels; Redis is the cleanest real example of "events with one owner for the data".

Try it yourself

Feel a slow command, and a fork, without installing anything

These are toy models in plain Python. They do not talk to a real Redis, but they behave the way the Redis docs describe.

First, a one-thread queue with a slow command in the middle. Save as queue.py and run python3 queue.py:

# One thread, one queue: a slow command delays everyone behind it.
commands = [("a", 0.1), ("b", 0.1), ("c", 50.0), ("d", 0.1), ("e", 0.1)]

clock = 0.0
for client, cost in commands:
    clock += cost
    print(f"client {client}: cost {cost:5.1f} ms, reply at t={clock:6.1f} ms")
client a: cost   0.1 ms, reply at t=   0.1 ms
client b: cost   0.1 ms, reply at t=   0.2 ms
client c: cost  50.0 ms, reply at t=  50.2 ms
client d: cost   0.1 ms, reply at t=  50.3 ms
client e: cost   0.1 ms, reply at t=  50.4 ms

Clients d and e cost 0.1 ms each but wait about 50 ms. The costs are invented for the demo.

Second, copy-on-write on POSIX (macOS, Linux, WSL). The child sees the data as it was when it was forked, while the parent carries on and changes it. This is the idea behind Redis's snapshots:

import os
data = bytearray(b"A" * 1_000_000)      # the "dataset" in memory
r, w = os.pipe()
pid = os.fork()
if pid == 0:                             # child: like Redis's snapshot child
    os.close(r)
    os.write(w, data[0:1])               # it still sees the old value
    os._exit(0)
os.close(w)
data[0:1] = b"B"                         # parent keeps taking writes
snap = os.read(r, 1)
os.waitpid(pid, 0)
print("child's snapshot sees:", snap.decode(), "| parent now has:", chr(data[0]))
child's snapshot sees: A | parent now has: B

If you do have Redis installed (for example brew install redis on macOS or your package manager on Linux), these commands only read information. Start a throwaway server with redis-server in another terminal first:

$ redis-cli CONFIG GET slowlog-log-slower-than   # threshold for the slow log
$ redis-cli SLOWLOG GET 5                        # the five most recent slow entries
$ redis-cli CONFIG GET latency-monitor-threshold # 0 means the latency monitor is off
$ redis-cli --intrinsic-latency 5                # CPU-heavy for 5 s: measures your OS jitter

The last command measures how long your own OS leaves a process without CPU. As the docs note, it needs to run on the machine where Redis runs and it saturates a core while it works, so use a short duration.

Distributed systems connection

Redis's answer to "I need more than one core" is the same answer distributed systems give to "I need more than one machine": split the data (partitioning). Sharding keeps each node's work small and independent, but a client now has to know which node owns a key, and operations that span keys span nodes. General industry pattern, not from the Redis sources: the slow-command problem also reappears at larger scale as tail latency (networking chapter 13): when a request fans out to many nodes, it is as slow as its slowest node, so one node pausing for a fork can slow a whole request. And when you add replicas to run slow queries away from the main instance, you've started down the road to replication (networking chapter 18, replication). Studio 1 (Serve 10,000 Connections on One Machine) is the place to apply event loops yourself.

Key takeaways

  • Redis keeps data in RAM and runs commands one at a time on an event loop. No two commands interleave, so it needs no locks (general reasoning).
  • It is "mostly" single-threaded: background threads handle some slow I/O, and optional I/O threads can take over socket work. The docs describe commands as served sequentially.
  • The price is head-of-line blocking: slow commands such as KEYS on a big keyspace, long Lua scripts, and the fork for snapshots all stall every client.
  • Copy-on-write makes snapshots cheap in theory, but the fork and later page copies cost time and memory under write load.
  • SLOWLOG and the latency monitor exist to find the commands and events that block the loop.
  • To use more cores, run more instances or shard.

Check your understanding

A client runs KEYS * against a Redis instance with millions of keys. What happens to other clients sending GET commands at the same time?

  1. Nothing; Redis runs each client on its own thread
  2. Their commands are rejected with an error
  3. They wait in line until the long command finishes, even though their own commands are fast
  4. Redis moves the slow command to a child process automatically
Commands are executed one at a time, so everything queued behind the slow one waits. This is head-of-line blocking. The documented alternative is the incremental SCAN family.

Why is it reasonable (as a general argument) that a single-threaded server needs no locks around its data?

  1. Because locks are not allowed on Linux
  2. Because only one thread touches the data, no two commands can interleave halfway through
  3. Because the data is stored on disk
  4. Because the kernel locks memory automatically
Races (chapter 11) need two flows of execution on shared data. With one thread running commands, each command finishes before the next starts, so each is atomic without locks.

What does copy-on-write buy Redis during an RDB snapshot, and when does it cost something?

  1. It makes the snapshot instant with no cost at all
  2. It stops clients from writing while the child runs
  3. It copies the whole dataset to disk at fork time
  4. Parent and child share pages so memory is not duplicated up front, but the fork itself takes time and each page written during the save must be copied
The fork runs in the main thread and copies page tables, which Redis's docs say can induce latency. Afterwards a page is duplicated only when it changes in parent or child, so heavy writes during a snapshot mean more copies.

The Redis slow log's measured time leaves out talking to the client and sending the reply. Why is that a sensible choice?

  1. Command execution is the stage where the main thread is blocked and can't serve anyone else
  2. Network time is always zero
  3. Sockets are not part of Redis
  4. Replies are not important
The docs describe execution time as the only stage where the thread is blocked and cannot serve other requests. That is exactly the part that causes head-of-line blocking for everyone else.

Discord & the Garbage Collector

In 2020 Discord published an engineering post about one service that showed latency spikes every couple of minutes that the team could not tune away in Go. The cause they identified was not a bug in their logic. It was the garbage collector doing exactly its job. This case study follows what they saw, what they tried, what they changed, and what the story does and does not prove.

The pattern in one sentence

GC pauses and tail latency: automatic memory management gives you safety and convenience, but its work happens on the runtime's schedule rather than yours, and when that work grows with how much data you keep alive, it can show up as periodic slow requests that averages hide.

The cast

Everything here comes from Discord's own post, "Why Discord is switching from Go to Rust" (by Jesse Howarth, 4 February 2020). The post is about one service and one set of measurements. Keep that in mind: it is a case study, not a verdict on a language.

The Read States service
It tracks which channels and messages each user has read. There is one Read State per user per channel, and Discord has billions of them. Each holds counters (such as the number of unread @mentions) that are updated atomically and often reset to zero. The post calls the service "in the hot path": it is touched on every connection, every message sent and every message read, so latency matters.
The LRU cache
Each server kept a least-recently-used cache of Read States: millions of users and tens of millions of Read States in each cache, with hundreds of thousands of cache updates per second. An LRU cache keeps recent items and evicts the ones used longest ago.
Cassandra
The database behind the cache. Evicted entries were committed to it, and each update scheduled a commit 30 seconds later, producing tens of thousands of database writes per second.
The garbage collector
Go's runtime component that finds heap memory no longer referenced and reclaims it. From chapter 3: the stack cleans up after itself, but heap memory must be freed by someone, and in Go that someone is the collector.

What happened, step by step

Step through

From Go spikes to Rust

  1. The setup. Read States sits in the hot path. Each server keeps a large LRU cache of Read States in memory, backed by Cassandra. The Go version met the functional needs.
  2. The spikes. The post reports latency spikes every few minutes, with charts showing latency and CPU spikes "roughly every 2 minutes". The team attributed them to Go's garbage collector, and says it had written the code to make few allocations, so it did not think it was creating much garbage. Looking at the Go source, they found that Go "will force a garbage collection run every 2 minutes at minimum". The spikes were large, they concluded, because the collector had to scan the entire LRU cache to decide whether memory was really free.
  3. What they tried. First, an endpoint to change the GC percent at runtime. The post says "no matter how we configured the GC percent nothing changed", because the service was not allocating fast enough to trigger more frequent collections. Second, a smaller cache, a setting to resize it, and splitting it into many smaller caches per server. Spikes got smaller, but 99th-percentile latency rose, because a smaller cache more often needed a database load. After load testing they settled on a capacity that "seemed okay" and left it for a long time.
  4. The Rust rewrite. The first Rust port was completed in May 2019. Rust has no garbage collector; its ownership model frees memory as soon as it is no longer used, so an evicted Read State is freed immediately instead of waiting for a scan. The post says the first version had latency comparable to Go with no spikes, and after profiling it beat Go on latency, CPU and memory. Without the collector's constraints, they raised the cache capacity to 8 million Read States.

What the post says, and what it does not

It's worth being precise about the claims, because this story is often retold with more certainty than the source has.

  • Stated: spikes appeared roughly every two minutes in their charts; Go forces a collection at least every two minutes; the collector scanned the whole cache; tuning the GC percent did nothing; shrinking the cache reduced spike size but raised 99th-percentile latency.
  • Stated: the Rust version showed no latency spikes after launch, beat the Go version on latency, CPU and memory after optimisation, and let them raise the cache to 8 million entries. Optimisations included switching the LRU from a HashMap to a BTreeMap to reduce memory use. The post gives graphs but few exact figures for the comparison, and I won't invent any.
  • Stated, with a limit: the graphs shown for Go come from Go 1.9.2, and the post says the team tried 1.8, 1.9 and 1.10 "without any improvement". It says nothing about later versions of Go. Nothing in this case study tells you how a current Go release would behave on that workload.
  • Not stated: that Go is a bad choice in general. The post says Discord uses Rust where it makes sense and does not recommend rewriting everything in Rust for its own sake.

Common misconception: "garbage collection makes programs slow"

The accurate version is narrower. A collector costs CPU time and memory, and its work can land at inconvenient moments. Go's own GC guide says the collector "is not fully stop-the-world and does most of its work concurrently with the application", and that its pauses are not proportional to heap size. It also lists real sources of latency: brief stop-the-world pauses, scheduling delays while the collector uses CPU, goroutines made to help with collection when allocation is high, and extra work on pointer writes during marking. So the cost is real, but it depends on the workload, and for many programs it is invisible.

The pattern: GC pauses and tail latency

Everything from here to the end of this section is a general pattern, not a claim about Discord beyond what the post says. Three ideas connect.

1. The collector's work grows with what is alive

A tracing collector has to find what is still reachable. Go's guide states that the CPU cost of a collection cycle has a fixed part plus a marginal cost that "scales proportionally with the size of the live heap". A big in-memory cache is, by definition, a lot of live data that rarely becomes garbage but must be examined each cycle. That matches the post's explanation: the collector kept scanning a cache full of data that was staying put.

2. Tail latency, not average latency

If one collection cycle makes some requests slow every two minutes, the average over an hour barely moves. The slowest requests, the 99th percentile and beyond, are where it shows. For a service on the hot path of every message, that tail is what users feel (see networking chapter 13 on why the slowest request matters most). Note also how the post's trade-off appeared: a smaller cache reduced the size of the spikes but raised p99 by sending more requests to the database. You can pay for latency with GC work or with cache misses, but not always for free.

3. Your levers

Tune the collector

Go's guide describes GOGC (a trade between memory and GC CPU: doubling it doubles heap overhead and roughly halves GC CPU cost) and, since Go 1.19, a soft memory limit. In Discord's case the post says the GC percent change did nothing, because the service was not allocating fast enough for the setting to trigger more collections.

Allocate less

The same guide says the allocation rate is "a major factor in GC frequency" and points to heap profiles and escape analysis (go build -gcflags=-m=3). Discord's team says its code already allocated little, so this lever was not the answer here.

Keep less on the managed heap

A general technique: keep the big, long-lived data structure where the collector doesn't have to trace it, such as outside the managed heap or in a runtime without a tracing collector. The post's cache change was a smaller one in this spirit: shrinking what the collector had to scan.

Change the runtime

Rust frees memory deterministically by ownership rules, with no collector to schedule. It trades the collector's costs for the compiler's rules and the programmer's effort. The post itself notes the cost it paid: at the time, stable Rust lacked good async support and the team ran on nightly Rust until it stabilised.

Analogy: the building inspector

Imagine a building with a huge warehouse that rarely changes. An inspector walks the whole warehouse every two minutes to check nothing has been abandoned. The inspector is polite and the warehouse is orderly, but each walk-through briefly clogs the aisles. You can ask the inspector to come less often, or make the warehouse smaller, or hire a manager who tidies up each item the moment it's no longer needed.

Where it breaks down: a real collector is concurrent and clever; it doesn't stop the whole building. The analogy captures that work scales with the warehouse size, not that the whole service freezes.

Trade-offs and lessons

  • Measure the tail and look for periodicity. Spikes at regular intervals suggest something is running on a timer. Discord's charts showed one at roughly two minutes, which led the team to the forced-collection behaviour in the Go source.
  • Be careful what you generalise. Runtimes evolve. Go's GC guide says Go's collector has "steadily improved over time, in both latency and throughput", and tooling like the memory limit arrived later. This case describes a specific service on specific old versions. It does not show that a particular language is slow or fast today.
  • A rewrite is a big lever. It worked here partly because the service was small and self-contained, which the post gives as a reason it was a good candidate. For most problems, profiling and tuning come first.
  • Memory management is a design choice. Stack versus heap, manual versus automatic, deterministic versus tracing: chapter 3 gives the vocabulary. Each option moves cost to a different place.

Try it yourself

See collection cost grow with live data

Python's collector is not Go's, but the principle is the same: a full collection has to look at what is alive. This is a toy, not a model of Discord's service. Your timings will differ from the ones shown.

import gc, time

def make(n):
    return [[i] for i in range(n)]       # n small live objects

for n in (100_000, 400_000, 1_600_000):
    live = make(n)
    t = time.perf_counter()
    gc.collect()                          # a full collection visits what is alive
    print(f"{n:>9,} live objects: full collect took {(time.perf_counter()-t)*1000:6.1f} ms")
    del live
  100,000 live objects: full collect took    2.3 ms
  400,000 live objects: full collect took    9.0 ms
1,600,000 live objects: full collect took   28.5 ms

Four times as many live objects took roughly four times as long on this machine. Run it a few times; the exact numbers wobble, the trend does not.

If you have Go installed, this read-only command shows whether you have set the two environment variables Go's GC guide describes. It changes nothing:

$ echo "GOGC=$GOGC GOMEMLIMIT=$GOMEMLIMIT"   # empty values mean the defaults are in effect

For a program of your own, the Go guide's advice is to look at heap profiles to find where allocations come from before changing any setting.

Distributed systems connection

General industry pattern, not from the Discord post: one server pausing for a collection is a local event; in a fleet it becomes a distributed one. A client that fans out to many servers waits for the slowest reply, so a rare pause on any one machine appears often from the caller's side. Load balancers (networking chapter 14) and timeouts treat a pausing server as a slow or failing one, which can trigger retries that add load right when the server is busiest. That's why latency-sensitive services care about their 99th percentile, not their mean, and why runtime behaviour is part of system design.

Key takeaways

  • Discord's Read States service, in Go, showed latency and CPU spikes roughly every two minutes; the team attributed them to the garbage collector scanning a huge LRU cache.
  • The post reports Go forces a collection at least every two minutes, so tuning the GC percent did not help; a smaller cache reduced spikes but raised p99 latency.
  • The Rust rewrite showed no spikes and beat the Go version on latency, CPU and memory; the cache grew to 8 million entries.
  • General pattern: collector work grows with live data, and its effect lands in the tail of the latency distribution.
  • Runtimes evolve. The post covers old Go versions and says nothing about newer ones.

Check your understanding

According to Discord's post, why did changing the GC percent not remove the latency spikes?

  1. The GC percent setting is ignored by Go
  2. The service wasn't allocating fast enough to trigger more frequent collections, and Go forces one at least every two minutes
  3. The database was the real bottleneck
  4. The GC percent was set too high
The post says the setting changed nothing because the service wasn't generating garbage quickly enough to trigger collections, and that the runtime forces a run every two minutes at minimum.

Why did shrinking the LRU cache reduce the size of the spikes but raise 99th-percentile latency?

  1. Smaller caches make Go faster in every respect
  2. The collector ignores small caches
  3. The collector had less to scan, but more requests missed the cache and had to be loaded from the database
  4. Rust was already in use
Collection work scaled with how much live data the cache held. A smaller cache meant shorter scans, but also more misses, and a miss costs a database load that shows up in the slowest requests.

Which statement is the most accurate way to use this case study?

  1. It shows GC cost can hit tail latency for a service holding lots of live data; it does not show how current Go versions behave
  2. It proves garbage-collected languages are unsuitable for servers
  3. It proves Rust is always faster than Go
  4. It shows GC tuning never works
The post covers one service and Go versions 1.8 to 1.10. Go's own guide says its collector has improved over time. Take the mechanism as the lesson, not a language verdict.

Why do averages hide this kind of problem?

  1. Averages are always accurate
  2. The spikes never affect users
  3. Garbage collection only runs at night
  4. A spike every couple of minutes affects a small fraction of requests, so the mean barely moves while the slowest percentiles jump
Tail latency (p99 and beyond) captures the slow minority. Periodic pauses live there.

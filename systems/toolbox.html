Toolbox

A running program is invisible until you point something at it. These tools let you watch processes, system calls, memory and CPU time as they happen, and build a container by hand. Each has a ten-minute exercise tied to a chapter.

How to use this page

Jump to a tool when a chapter mentions it. Most tools work on macOS and Linux. Tools marked Linux need a Linux kernel, so run them on your lab machine: a free local VM or a throwaway cloud server, where it's also safe to use sudo. Example output is realistic but yours will differ: different process IDs, timings and sizes.

Everything on this page observes programs rather than changing them. Where a command needs sudo, the card says so.

Watch processes

What is running right now, what does each program have open, and what does the kernel say about it?

top & htop

macOS: top built in; brew install htop · Ubuntu/Debian: top built in; sudo apt install htop · Windows: Task Manager, or htop in WSL

top and htop are live tables of every process: its CPU share, memory, state and thread count. They show the kitchen from chapter 5 in real time: how many cooks are busy, who is hogging the stove, and who is just standing around waiting. They are the first thing to open when a computer feels slow.

10-minute guided exercise

Open two terminals. In the first, make a program that does nothing but burn CPU, so there is something to see:

$ python3 -c "while True: pass"  # spins one core at 100%; Ctrl-C to stop it later
$ top -o cpu  # sort by CPU use; press q to quit
Processes: 512 total, 3 running, 509 sleeping, 2487 threads
Load Avg: 2.11, 1.52, 1.20  CPU usage: 14.2% user, 3.1% sys, 82.7% idle
PID    COMMAND      %CPU  TH   STATE     MEM
41872  Python       99.8  1    running   9840K
 612   WindowServer  7.3  14   sleeping  412M
...
$ top  # sorted by CPU by default; q quits
top - 14:31:02 up 3 days,  1 user,  load average: 1.02, 0.60, 0.31
Tasks: 142 total,   2 running, 140 sleeping,   0 stopped,   0 zombie
%Cpu(s): 26.0 us,  1.2 sy,  0.0 ni, 72.5 id,  0.3 wa
  PID USER   PR  NI    VIRT    RES    SHR S  %CPU  %MEM  COMMAND
41872 you    20   0   14212   9840   5312 R  99.7   0.1  python3

Now try htop, which is easier to read and navigate. Inside it: F6 (or </>) chooses the sort column, F5 toggles a tree view that shows which process started which, H shows or hides threads, F9 sends a signal to the highlighted process, and q quits. Start a second spinner in a third terminal and watch two processes each take their own core. Then stop both with Ctrl-C and check the load average with uptime; it falls slowly, because it is an average over the last 1, 5 and 15 minutes.

What to look for

  • A spinning process reads about 100% of one core. On an 8-core machine, the machine as a whole is about 12% busy. Two spinners use two cores at once (chapter 1, chapter 7).
  • The state column: almost everything is sleeping (waiting for input, a timer or a lock), and only a few processes are running at any instant (chapter 5).
  • The process tree in htop (F5): your shell is the parent of the program you launched, just like fork and exec from chapter 5.
  • TH / NLWP (thread count): a Python program shows 1 unless it starts threads (chapter 10). Browsers and databases show dozens.
  • RES / MEM is the memory the process actually has in RAM, which is smaller than the address space it has reserved (chapter 6).

Common pitfalls

  • %CPU over 100% is not an error: a multithreaded process using three cores shows about 300%.
  • Load average is not CPU percentage. On Linux it counts processes that are running or waiting for CPU (and for uninterruptible disk I/O); a number above your core count means work is queuing (chapter 7).
  • Don't kill what you don't recognise. Sending a signal from htop (F9) to a system process can log you out or freeze the desktop.
  • Windows has Task Manager and Resource Monitor for the same job; under WSL, use top as shown.

lsof

macOS: built in · Ubuntu/Debian: sudo apt install lsof · Windows: not available; use WSL, or Process Explorer

lsof ("list open files") shows every file, directory, pipe and network socket a process has open, because on Unix they are all file descriptors. It answers "what is this process doing with the outside world?" and "who is holding this file or port?"

10-minute guided exercise

Start a program that opens a file and then waits, so it stays alive long enough to inspect:

$ python3 -c "import os,time; f=open('notes.txt','w'); print('pid', os.getpid()); time.sleep(120)"
pid 41950
$ lsof -p 41950  # everything process 41950 has open
COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF    NODE NAME
python3 41950 you   cwd    DIR   1,17      640  882104 /Users/you/work
python3 41950 you   txt    REG   1,17   49712  991230 /opt/homebrew/bin/python3.12
python3 41950 you     0u   CHR   16,2  0t1523     812 /dev/ttys002
python3 41950 you     1u   CHR   16,2  0t1523     812 /dev/ttys002
python3 41950 you     2u   CHR   16,2  0t1523     812 /dev/ttys002
python3 41950 you     3w   REG   1,17        0  991877 /Users/you/work/notes.txt
$ lsof -i :8000  # who has port 8000? (start python3 -m http.server 8000 --bind 127.0.0.1 first)
$ lsof -iTCP -sTCP:LISTEN -n -P  # every listening TCP socket
$ lsof +L1  # files that are open but already deleted (link count < 1)
$ ulimit -n  # how many descriptors one process may have open
256

Back in terminal 1, wait for the program to finish or press Ctrl-C, then delete notes.txt yourself if you don't want it. Also try lsof -p $$, which inspects your own shell.

What to look for

  • FD 0, 1, 2 are stdin, stdout and stderr. The letter after the number is the access mode (r read, w write, u both). They point at your terminal device (chapter 8).
  • FD 3 is the file the program opened: the first free descriptor number. This is the file descriptor table from chapter 8, made visible.
  • TYPE tells files (REG), directories (DIR), terminals (CHR), pipes (PIPE) and sockets (IPv4, IPv6, unix). A socket is just another entry in the list.
  • A blocking server shows one socket per client; a busy one can approach the descriptor limit shown by ulimit -n (chapter 15).

Common pitfalls

  • Without sudo, lsof only shows your own processes. It's slow and noisy if you run it with no arguments, so always narrow it with -p, -i or a filename.
  • Use -n -P for network queries, to skip name lookups and show port numbers.
  • "Too many open files" in a program usually means leaked descriptors. lsof -p PID | wc -l shows the count growing.
  • Deleted but open files (lsof +L1) still use disk space until the last holder closes them. That surprises people who delete a big log and see no free space.
  • Windows has no lsof; Process Explorer from Microsoft shows open handles, or use WSL.

Trace the kernel

Every interesting thing a program does goes through the kernel. These tools show you the doorway.

strace Linux

macOS: not available (use a Linux VM) · Ubuntu/Debian: sudo apt install strace · Windows: inside WSL

strace prints every system call a program makes, as it makes it, with arguments and return values. It turns the kernel doorway from chapter 4 from a diagram into a transcript. When a program hangs, fails mysteriously or runs slowly, strace often shows the exact call responsible: a file it cannot find, a lock it waits on, or a connection that never completes.

10-minute guided exercise

Run this on your lab machine. It needs Linux, so use a local or cloud Linux VM (see Your Lab Machine) or WSL. macOS has no direct equivalent.

$ strace -e trace=openat cat /etc/hostname  # only the file opens; tiny and readable
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3
lab
+++ exited with 0 +++
$ strace -c python3 -c "print('hi')"  # -c: count calls and time instead of listing them
% time     seconds  usecs/call     calls    errors syscall
 32.10    0.000410           3       131        27 openat
 18.72    0.000239           2       112           read
...
100.00    0.001277           2       540        74 total
$ strace -f -tt -e trace=network curl -s http://example.com -o /dev/null  # -f: follow child threads and processes; -tt: timestamps
14:40:02.113 socket(AF_INET, SOCK_DGRAM|SOCK_CLOEXEC|SOCK_NONBLOCK, IPPROTO_IP) = 5
14:40:02.114 connect(5, {sa_family=AF_INET, sin_port=htons(53), sin_addr=inet_addr("127.0.0.53")}, 16) = 0
14:40:02.131 socket(AF_INET, SOCK_STREAM|SOCK_CLOEXEC|SOCK_NONBLOCK, IPPROTO_TCP) = 5
14:40:02.131 connect(5, {sa_family=AF_INET, sin_port=htons(80), sin_addr=inet_addr("198.51.100.7")}, 16) = -1 EINPROGRESS
$ strace -o trace.txt python3 -c "print(1)"; wc -l trace.txt  # save the trace to a file instead of stderr

Attaching to a program that is already running is strace -p PID. On most Linux distributions that needs sudo unless the program is your own child, because a kernel setting (Yama's ptrace_scope) restricts it. Launching the program under strace, as above, needs no sudo.

What to look for

  • Each line is one system call: its name, its arguments, and after the = its return value. Printing "hi" is one write in a sea of file opens: starting an interpreter is expensive (chapter 4).
  • Negative returns with an error name (-1 ENOENT) are failed calls. Python probes several places for each module, so the errors column in -c is not alarming.
  • The file descriptor returned by openat (the 3) shows up again in later read and write calls: a trace is the descriptor table in motion (chapter 8).
  • In the network trace you can see a program ask the kernel for a socket, connect, and have the DNS lookup go through a UDP socket to port 53 before the TCP connection to port 80 starts. For a server loop, trace epoll_wait to see the event loop from chapter 16 asking the kernel what is ready.

Common pitfalls

  • strace slows programs down a lot, sometimes by an order of magnitude. Use it to learn what happens, not to measure how fast it is.
  • The output goes to stderr. Redirect with 2>&1 or use -o file.
  • Strings are cut off at 32 characters by default; add -s 200 to see more.
  • It's loud. Always filter with -e trace=... (or a class like network, file, process) unless you want everything.
  • macOS has no strace. Its closest tool, dtruss, needs System Integrity Protection partly disabled, which this course does not ask you to do. Use a Linux VM.

The /proc file system Linux

macOS: does not exist (use ps, lsof, vmmap) · Ubuntu/Debian: always mounted, nothing to install · Windows: inside WSL

/proc looks like a folder of files, but the files are the kernel's own bookkeeping, generated on the fly. Each running process has a directory named after its ID with its status, memory map, open files and limits. It is how ps, top and lsof know what they know on Linux, and you can read it with cat.

10-minute guided exercise

Run this on your lab machine. It needs Linux, so use a local or cloud Linux VM (see Your Lab Machine) or WSL. macOS has no direct equivalent.

$ head -12 /proc/self/status  # /proc/self is "the process reading this", here: head
Name:   head
Umask:  0022
State:  R (running)
Tgid:   42311
Pid:    42311
PPid:   42280
$ grep -E 'Name|State|Pid|PPid|VmRSS|Threads|ctxt' /proc/$$/status  # $$ is your shell
Name:   bash
State:  S (sleeping)
Pid:    42280
PPid:   42270
VmRSS:      4812 kB
Threads:        1
voluntary_ctxt_switches:        41
nonvoluntary_ctxt_switches:     3
$ ls -l /proc/$$/fd  # the shell's open descriptors, as symlinks
lrwx------ 1 you you 64 Oct 12 14:50 0 -> /dev/pts/0
lrwx------ 1 you you 64 Oct 12 14:50 1 -> /dev/pts/0
lrwx------ 1 you you 64 Oct 12 14:50 2 -> /dev/pts/0
$ head -5 /proc/self/maps  # the address-space map of the "head" process
5581f2c00000-5581f2c04000 r--p 00000000 fd:01 131099  /usr/bin/head
5581f2c04000-5581f2c08000 r-xp 00004000 fd:01 131099  /usr/bin/head
...
$ head -3 /proc/meminfo; cat /proc/loadavg
MemTotal:        4017316 kB
MemFree:         2541032 kB
MemAvailable:    3398764 kB
0.00 0.01 0.00 1/137 42311
$ grep -c ^processor /proc/cpuinfo  # how many CPUs the kernel sees
$ cat /proc/$$/limits | grep -i 'open files'  # the descriptor limit

Try it on a process that's doing something: start sleep 300 &, then inspect /proc/$!/status ($! is the last background process's ID) and ls -l /proc/$!/fd. Notice that the files are plain text; there is nothing to install and nothing you can break by reading them.

What to look for

  • State R (running), S (sleeping), D (uninterruptible, usually waiting on disk), Z (zombie) match the process life cycle in chapter 5.
  • PPid chains up to PID 1: every process has a parent that forked it.
  • VmRSS (memory resident in RAM) versus the larger virtual size (VmSize) is the gap between address space and real memory from chapter 6. maps shows that address space as regions: code r-xp, data rw-p, the heap and the stack.
  • Context switch counters: voluntary means the process gave up the CPU to wait; non-voluntary means the scheduler took it away (chapter 7).
  • /proc/PID/fd is what lsof reads on Linux: the same descriptor table as chapter 8, as symlinks.

Common pitfalls

  • /proc is not a real disk. The kernel makes the contents up as you read them; sizes show as 0 and the values change from one read to the next.
  • You can read your own processes freely; some details of other users' processes need root.
  • macOS has no /proc. There, use ps, lsof, vmmap PID and sysctl. WSL 2 has a real /proc.
  • Writing under /proc or /proc/sys changes kernel behaviour. This course only reads them.

Measure and profile

Before making something faster, measure it. These tools tell you how long it took, then where the time went.

vm_stat, vmstat & iostat

macOS: vm_stat, iostat and memory_pressure built in · Ubuntu/Debian: vmstat built in; sudo apt install sysstat for iostat · Windows: Resource Monitor, or WSL

These print system-wide counters for memory, paging, CPU and disk, once a second if you like. Where top asks "which process?", they ask "how is the machine as a whole?": is it short of memory, reading from disk, or waiting on I/O?

10-minute guided exercise

$ vm_stat 1  # macOS: one line of counters per second, Ctrl-C to stop
Mach Virtual Memory Statistics: (page size of 16384 bytes)
    free   active inactive speculative wired  ... pageins pageouts
  102113  412880  398210        4122  98211  ...   35120        0
$ vmstat 1  # Linux: Ctrl-C to stop
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1  0      0 2541032  80212 998100    0    0     4     6   50   90  1  0 99  0  0

In a second terminal, allocate and touch a few hundred megabytes (adjust the number to a modest fraction of your RAM), then release it by pressing Enter or Ctrl-C:

$ python3 -c "b = bytearray(b'x') * (300*1024*1024); input('allocated 300 MiB, press Enter to free it ')"

Watch free drop and recover in terminal 1 (macOS), or free/cache change on Linux. Now generate some disk reading and watch the I/O columns or iostat:

$ find ~ -type f > /dev/null 2>&1  # read-only walk over your files; Ctrl-C when bored
$ iostat -w 1 -c 5  # macOS: disk throughput, once a second, 5 times
              disk0       cpu    load average
    KB/t  tps  MB/s  us sy id   1m   5m   15m
   24.50  310  7.42   9  5 86  1.9  1.6  1.4
$ iostat -x 1 5  # Linux (sudo apt install sysstat): extended per-device stats
$ memory_pressure | head -5  # macOS: the system's own summary of memory pressure

What to look for

  • Page size in the macOS header: 16384 bytes on Apple Silicon, 4096 on Intel Macs (chapter 6. Multiply counts by this to get bytes).
  • pageins climbing steadily means the system is reading from disk to satisfy memory accesses. pageouts (macOS) or si/so (Linux swap-in/out) above zero means it is under real memory pressure (chapter 6).
  • free is usually small even on a healthy machine, because the OS uses spare RAM as a file cache. Look at cache/inactive and "available" too (chapter 9).
  • wa (Linux) or the disk MB/s shows time spent waiting on storage, the slow rung of the ladder in chapter 2.
  • r / b (Linux vmstat): processes ready to run versus blocked. cs is context switches per second (chapter 7).

Common pitfalls

  • The first line of vmstat is an average since boot, not the current second. Read from the second line on.
  • Don't allocate more than your free RAM in the exercise. You will start swapping and everything gets slow, which is educational but unpleasant.
  • "Free memory" being low is not a problem by itself; unused RAM is wasted RAM.
  • Windows: Resource Monitor and Performance Monitor cover the same ground; in WSL you can use vmstat.

hyperfine

macOS: brew install hyperfine · Ubuntu/Debian: sudo apt install hyperfine (Ubuntu 23.04 and later; otherwise a release from its GitHub page) · Windows: winget install sharkdp.hyperfine or scoop install hyperfine

hyperfine runs a command many times, with optional warm-up runs, and reports the mean, spread and range. It replaces the habit of running time once and trusting the number. Use it whenever you want to claim "this is faster than that".

10-minute guided exercise

$ hyperfine 'python3 -c "pass"'  # time starting an empty Python program
Benchmark 1: python3 -c "pass"
  Time (mean ± σ):      16.4 ms ±   1.2 ms    [User: 10.9 ms, System: 4.3 ms]
  Range (min … max):    14.8 ms …  22.1 ms    100 runs
$ hyperfine --warmup 3 'python3 -c "pass"' 'python3 -S -c "pass"'  # compare two commands; -S skips the site module
Benchmark 1: python3 -c "pass"
  Time (mean ± σ):      16.1 ms ±   0.9 ms
Benchmark 2: python3 -S -c "pass"
  Time (mean ± σ):      12.0 ms ±   0.8 ms

Summary
  python3 -S -c "pass" ran
    1.34 ± 0.11 times faster than python3 -c "pass"
$ hyperfine --runs 20 'python3 -c "sum(range(10_000_000))"' 'python3 -c "sum([i for i in range(10_000_000)])"'
$ hyperfine --export-markdown results.md 'ls /usr/bin' 'ls /usr/lib'  # save a table

For commands that finish in a few milliseconds, add -N (no shell), as in hyperfine -N 'true', so the shell's own start-up time isn't included. Start a command's first run from a cold state and the later runs from a warm one: compare hyperfine --runs 1 'cmd' with a warm-up run to see how much the caches matter.

What to look for

  • mean ± σ and the min…max range: one timing is an anecdote, a hundred timings with their spread is a measurement. If σ is large compared with the difference between two commands, you can't tell which is faster.
  • User versus System time: how long the CPU spent in your code versus in the kernel on your behalf (chapter 1, chapter 4).
  • Warm-up removes the first run's penalty: the program file, libraries and data are not yet in the page cache (chapter 2). The gap between first run and later runs shows the memory hierarchy at work.
  • Python starting in about 10 to 20 ms is why short scripts feel instant but loops of thousands of process launches don't (chapter 5).

Common pitfalls

  • Warnings about "statistical outliers" mean something disturbed the measurement (a background process, the laptop on battery power). Close other apps, plug in, run again.
  • Very short commands (under about 5 ms) are dominated by shell start-up unless you use -N.
  • Quote the command in single quotes so hyperfine, not your shell, receives it whole.
  • Never benchmark anything destructive. hyperfine runs the command many times.

py-spy

macOS: pipx install py-spy or brew install py-spy · Ubuntu/Debian: pipx install py-spy · Windows: pip install py-spy

py-spy samples a Python program from the outside, many times a second, and records which function each thread is running. It needs no changes to your code. The result is a ranked table or a flame graph that shows where the time goes, which is nearly always a surprise.

10-minute guided exercise

Make a small program that wastes time in an obvious place. Save it as busy.py:

# busy.py: a deliberately slow program
import time

def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

def sort_work():
    for _ in range(200):
        sorted(range(50_000, 0, -1))

def main():
    end = time.time() + 15
    while time.time() < end:
        fib(24)
        sort_work()

main()
$ pipx install py-spy  # or: pip install py-spy
$ py-spy record -o profile.svg -- python3 busy.py  # py-spy launches the program itself
py-spy> Sampling process 100 times a second. Press Control-C to exit.
py-spy> Wrote flamegraph data to 'profile.svg'. Samples: 1500 Errors: 0
$ py-spy top -- python3 busy.py  # live table of the hottest functions
Total Samples 900
GIL: 100.00%, Active: 100.00%, Threads: 1
  %Own   %Total  OwnTime  TotalTime  Function (filename)
 71.00%  71.00%   10.65s    10.65s   fib (busy.py)
 27.00%  27.00%    4.05s     4.05s   sort_work (busy.py)

Open profile.svg in your browser. Each box is a function; its width is the share of samples where it was on the stack, and boxes stack on top of the functions that called them. Hover for details. Then use the same view on a threaded program to see the GIL effect: py-spy record --gil -- python3 yourscript.py counts only the samples where a thread held the global interpreter lock.

What to look for

  • The widest box at the top of the stack is where the time really goes. Here that's fib, which is recursion (chapter 3): the recursive calls are the narrow towers above it.
  • Sampling means py-spy looks at the program 100 times a second instead of instrumenting every call, so the program runs at close to normal speed and the profile is statistical.
  • In a program with threads, --threads separates them, and two CPU-bound Python threads together still show about one core of work because of the GIL (chapter 10).
  • For an asyncio program, a profile shows where the single thread spends its time and whether something blocks the event loop (chapter 17).

Common pitfalls

  • Permissions. py-spy reads another process's memory. On macOS, py-spy always needs root (the py-spy README says so), even for the launch form above: put sudo in front of the py-spy record and py-spy top commands (if the shell can't find py-spy under sudo, give its full path from which py-spy). On Linux, the launch form works without it, while attaching to an existing process with --pid usually needs sudo.
  • Too short a run produces too few samples to trust. Profile for at least several seconds.
  • Native extensions (NumPy, etc.) appear as one function unless you add --native on Linux.
  • It only profiles Python. For anything else, use perf on Linux.

perf & flame graphs Linux

macOS: not available (Instruments and sample are the macOS cousins) · Ubuntu/Debian: sudo apt install linux-tools-common linux-tools-$(uname -r) · Windows: not in WSL by default

perf is Linux's built-in profiler. It counts events such as context switches, page faults and (on real hardware) cache misses, and samples the CPU to find hot code in any program, not only Python. Its output becomes a flame graph, one picture of where all the time went.

10-minute guided exercise

Run this on your lab machine. It needs Linux, so use a local or cloud Linux VM (see Your Lab Machine) or WSL. macOS has no direct equivalent.

perf comes from the Linux kernel project. Install the version matching your kernel (sudo apt install linux-tools-common linux-tools-$(uname -r)); on cloud VMs and Multipass this works, but on some VMs with a custom kernel there is no matching package. Use the same busy.py as in the py-spy card, or any program.

$ perf stat -e task-clock,context-switches,cpu-migrations,page-faults python3 busy.py
 Performance counter stats for 'python3 busy.py':

         15,012.31 msec task-clock             #    0.999 CPUs utilized
                23      context-switches
                 1      cpu-migrations
             3,104      page-faults

      15.021 seconds time elapsed
$ perf stat -e cache-misses,cache-references,instructions,cycles python3 -c "sum(range(10**7))"  # hardware counters
<not supported>      cache-misses
<not supported>      cache-references

The second command shows a typical limit: virtual machines often don't expose the CPU's hardware counters, so you get <not supported>. Software counters like those in the first command always work. Now sample where the CPU time goes. Recording usually needs sudo (or a lowered kernel.perf_event_paranoid setting):

$ sudo perf record -F 99 -g -- python3 busy.py  # sample 99 times a second, with call stacks
[ perf record: Captured and wrote 0.4 MB perf.data (1480 samples) ]
$ sudo perf report --stdio | head -20  # ranked functions
# Overhead  Command   Shared Object   Symbol
    71.8%   python3   python3.12      [.] _PyEval_EvalFrameDefault
     9.3%   python3   python3.12      [.] list_sort
...
# to draw a flame graph, fetch Brendan Gregg's FlameGraph scripts (they are plain Perl):
$ git clone https://github.com/brendangregg/FlameGraph
$ sudo perf script | ./FlameGraph/stackcollapse-perf.pl | ./FlameGraph/flamegraph.pl > flame.svg

Open flame.svg in a browser. Width is time; the stack grows upward from the entry point.

What to look for

  • task-clock versus time elapsed: 0.999 CPUs utilized means the program kept one core busy for its whole run. A program that waits on I/O would show a much lower number (chapter 1).
  • context-switches and page-faults are the costs from chapter 7 and chapter 6, counted for your program. A tight CPU loop has very few of the first.
  • Cache misses versus references, where available, quantify the memory hierarchy: a program with a high miss rate is waiting for RAM (chapter 2).
  • In the report, the interpreter's own functions dominate a Python program. Native code (a C program, a database) shows its own function names, which is where perf beats py-spy.

Common pitfalls

  • Permission errors. perf_event_paranoid restricts non-root profiling. Using sudo in your own throwaway VM is fine.
  • Missing symbols (addresses instead of names) mean the binary has no symbol table; install the debug packages if you need them.
  • Version mismatch: perf must match the running kernel. After a kernel update, reboot or reinstall the matching package.
  • perf.data files are owned by root if created with sudo. Clean them up with sudo rm perf.data when finished.
  • WSL, and possibly OrbStack, use their own kernels and may lack a matching package; if the install fails, use a Multipass or cloud VM for this exercise.

bpftrace Linux

macOS: not available · Ubuntu/Debian: sudo apt install bpftrace · Windows: not available

bpftrace lets you ask the running kernel questions with one-liners: who is opening files, how big are the reads, who just called fsync? It uses eBPF, a safe way to run small programs inside the kernel. It is advanced, but a few one-liners are enough to feel the magic.

10-minute guided exercise

Run this on your lab machine. It needs Linux, so use a local or cloud Linux VM (see Your Lab Machine) or WSL. macOS has no direct equivalent.

bpftrace attaches tiny programs to kernel events. It needs sudo, and everything below only observes. Press Ctrl-C to stop each one; counters are printed when you do.

$ sudo bpftrace -l 'tracepoint:syscalls:sys_enter_open*'  # list the events you can attach to
tracepoint:syscalls:sys_enter_open
tracepoint:syscalls:sys_enter_openat
...
$ sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s opened %s\n", comm, str(args->filename)); }'
Attaching 1 probe...
bash opened /etc/hosts
cat opened /etc/hostname

For the durability chapter, watch for fsync while a second terminal runs a program that calls it:

$ sudo bpftrace -e 'tracepoint:syscalls:sys_enter_fsync { printf("%s called fsync\n", comm); }'  # terminal 1
$ python3 -c "import os; f=open('/tmp/fs.txt','w'); f.write('x'); f.flush(); os.fsync(f.fileno())"  # terminal 2
python3 called fsync

What to look for

  • The first one-liner prints a running log of every file any program opens. You will see programs you didn't know existed (chapter 4).
  • @calls[comm] = count() is a map keyed by program name, kept by the kernel and printed at exit. Even an idle machine is making thousands of system calls.
  • The histogram shows the sizes of reads: many tiny ones and some page-sized ones. Programs that read one byte at a time pay one system call each (chapter 4).
  • The fsync probe fires exactly when a program asks for durability. Ordinary writes don't trigger it, which is the whole point of chapter 9.

Common pitfalls

  • Needs root and a reasonably recent kernel. Ubuntu's cloud images work. If you get an error about missing BTF or kernel headers, try a stock Ubuntu VM.
  • The openat one-liner is noisy; add a filter such as /comm == "python3"/ before the braces.
  • bpftrace shows up in its own counts, since it makes system calls too.
  • Remember to delete /tmp/fs.txt when finished (rm /tmp/fs.txt).
  • Advanced but safe: bpftrace programs are verified by the kernel before they run and can't crash it. They can still slow a very busy machine.

Containers

A container is not a small virtual machine. It is an ordinary process with a restricted view of the system. You can build that view yourself.

unshare & Docker Linux

macOS: unshare not available; for Docker, brew install --cask docker-desktop or OrbStack · Ubuntu/Debian: unshare is in util-linux (installed by default); sudo apt install docker.io · Windows: inside WSL; Docker Desktop for Docker

A container is built from Linux features: namespaces that limit what a process can see, and cgroups that limit what it can use. unshare lets you create namespaces from the command line, so you can assemble a tiny container by hand and then see that Docker is the same thing with a nicer wrapper. Pairs with chapter 19.

10-minute guided exercise

Run this on your lab machine. It needs Linux, so use a local or cloud Linux VM (see Your Lab Machine) or WSL. macOS has no direct equivalent.

Linux namespaces give a process its own private view of process IDs, hostnames, network interfaces and mounts. unshare starts a program in new ones. Everything here changes only the new namespaces and disappears when you exit.

1. A private process table. You need sudo to create most namespaces.

$ sudo unshare --pid --fork --mount-proc bash  # new PID namespace; bash becomes PID 1
root@lab:/# echo $$
1
root@lab:/# ps aux
USER   PID %CPU %MEM    VSZ   RSS TTY   STAT START   TIME COMMAND
root     1  0.0  0.1   8288  5120 pts/0 S    14:58   0:00 bash
root     8  0.0  0.0  10072  3328 pts/0 R+   14:58   0:00 ps aux
root@lab:/# exit

Your shell thinks it is the first process on a tiny machine. --fork makes unshare fork first so that bash can be PID 1 in the new namespace, and --mount-proc mounts a fresh /proc so ps reads the namespace's processes, not the host's. Try again without --mount-proc and ps aux will list the host's processes, because ps reads /proc, and that still belongs to the host.

2. A private hostname.

$ hostname
lab
$ sudo unshare --uts bash
root@lab:/# hostname container-1  ## change it inside only
root@lab:/# hostname
container-1
root@lab:/# exit
$ hostname  # unchanged outside
lab

3. A private network. A new network namespace has no interfaces except a loopback that is switched off:

$ sudo unshare --net bash -c 'ip addr'
1: lo: <LOOPBACK> mtu 65536 qdisc noop state DOWN group default qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
$ ls -l /proc/self/ns  # the namespaces your shell belongs to
$ lsns -t pid  # list PID namespaces on the machine

4. Compare with Docker. Docker is these same ingredients plus a root file system image and resource limits. Install Docker Engine on the VM (sudo apt install docker.io), or use Docker Desktop or OrbStack on a Mac, where containers actually run inside a small hidden Linux VM:

$ docker run --rm -it ubuntu:24.04 bash
root@3f2a1c9d7b10:/# ps aux
USER   PID %CPU %MEM    VSZ   RSS TTY   STAT START   TIME COMMAND
root     1  0.0  0.1   4588  3840 pts/0 Ss   15:03   0:00 bash
root@3f2a1c9d7b10:/# hostname
3f2a1c9d7b10
root@3f2a1c9d7b10:/# exit

What to look for

  • Your bash is PID 1 inside, yet the host's ps shows it under a different, ordinary PID. The same process, two names: that is what "isolation" means (chapter 19).
  • The container shares the host's kernel. Nothing was booted. That is why it starts in milliseconds and why a container is a lighter thing than a VM.
  • The Docker session looks just like your hand-built one, plus a different file system. A container is a process with namespaces (what it can see) and cgroups (how much it may use).
  • What you did not isolate: in the first example the file system, users and network are still the host's. Real containers isolate all of them.

Common pitfalls

  • Leaving out --fork gives an error or makes bash not PID 1. Leaving out --mount-proc makes ps show the host's processes.
  • Root inside is root on the host's kernel. This is a teaching toy, not a security boundary. Do it on a throwaway VM, not on a machine with data you care about.
  • Type exit to leave a namespace shell; you will otherwise forget which prompt you are in.
  • Docker Desktop on a Mac is not running containers on macOS itself. uname inside a container says Linux.
  • cgroups (the resource limits half of containers) are beyond this exercise; chapter 19 explains them.

Stack, Heap & Garbage Collection

A running program keeps its data in two main places that work very differently: a tidy stack that grows and shrinks with every function call, and a big, untidy heap where long-lived things go. Who cleans up the heap is one of the biggest design decisions in any language, and it explains the mysterious latency spikes that haunt production servers.

Why this matters

Memory bugs are among the oldest and nastiest bugs in computing: crashes, security holes, programs that slowly eat all the RAM, servers that freeze for a second at random. They all come from this chapter's two questions: where does the data live? and who decides when it dies? If you understand the stack, the heap and the main ways of cleaning up, you can read a memory graph, explain a "this service pauses every few minutes" report, and see why teams sometimes rewrite whole components in a different language.

Where a running program keeps its things

When the OS starts your program it becomes a process with its own private memory (chapter 5 explains processes, and chapter 6 explains how that privacy is built). Inside it, memory is divided into regions with different jobs. Here is a simplified picture:

The call stack

When a function is called, the program needs somewhere to put that call's private data: the arguments, the local variables, and (crucially) the return address, the place in the caller to jump back to when the function finishes. That bundle is a stack frame. Frames live on the call stack, and the rules are simple:

  • Calling a function pushes a new frame on top.
  • Returning pops the top frame, and execution continues at the return address saved in it.
  • Only the top frame is active. Everything below is paused, waiting for the call above it to finish.

This is why local variables vanish when a function returns: their frame is gone. It's also why the stack is fast. Pushing a frame is little more than moving one register, the stack pointer, and popping is moving it back. There is no searching for free space and no cleaning up.

Analogy: a pile of paused recipe cards

A cook is following recipe A and reaches "make the sauce (see card B)". They put card A face-down, with a bookmark at the current step, and start card B. Card B says "make the stock (see card C)", so B goes on the pile as well. When C is done, the cook picks up B at the bookmark, finishes it, and then returns to A. The pile only ever changes at the top.

Where it breaks down: a real stack frame isn't wiped when it's popped. The bytes stay where they were until the next call overwrites them. In low-level languages, using a pointer to a popped frame's variable gives you garbage rather than an error, which is a classic bug.

Watch a recursive call

A function that calls itself is recursive, and it makes the stack easy to see. Here is a factorial function, with main asking for fact(3):

def fact(n):
    if n == 1:
        return 1
    return n * fact(n - 1)

result = fact(3)      # 3 * 2 * 1 = 6
Step through

The call stack during fact(3)

  1. The first call. main calls fact(3). The program pushes a frame holding n = 3 and the return address (the spot in main to come back to), then jumps into the function.
  2. A call inside a call. fact(3) reaches n * fact(n - 1). Before it can multiply it needs the answer to fact(2), so it calls it. A second frame goes on top. fact(3) is paused, with its n still safe in its own frame.
  3. And again. fact(2) calls fact(1). Notice each frame has its own separate n: same variable name, three different variables. That is what makes recursion work.
  4. The base case. With n == 1 the function takes the return 1 branch and makes no further call. The stack is as tall as it will get. Recursion needs a base case like this; without one the stack just keeps growing.
  5. Unwinding begins. fact(1) returns 1. Its frame is popped and execution jumps to the saved return address inside fact(2), which can now finish 2 * 1.
  6. Unwinding continues. fact(2) returns 2 and its frame is popped. fact(3) resumes and computes 3 * 2 = 6.
  7. Back where we started. fact(3) returns 6, the stack is just main again, and the answer is stored in result. Every frame that was created has been destroyed, automatically and in exact reverse order.

Stack overflow

The stack has a fixed maximum size, set when the process or thread is created: commonly around 8 MiB for the main thread on Linux and macOS, and on some systems (macOS, for example) much smaller for other threads (chapter 10). Each call uses some of it. A recursion with no base case, or an input large enough to need a million nested calls, keeps pushing frames until the space is gone. That is a stack overflow. In C the program is simply killed, typically with a "segmentation fault". Python protects you: it counts the depth of nested calls and raises RecursionError once it passes a limit, 1,000 by default (sys.getrecursionlimit()). That limit is a Python-level guard, set well below the point where the underlying machine stack would run out.

Common misconception

"The stack is faster memory and the heap is slower memory." Both are ordinary RAM, and both go through the same caches (chapter 2). The stack is cheap to manage (a pointer moves, nothing more) and tends to be cache-friendly because the top few frames are reused constantly. The heap needs bookkeeping to find free space and to decide when to free it. The difference is how the memory is managed, not what it's made of.

The heap

The stack has a weakness: everything on it dies when its function returns, and every item must have a size known in advance. But programs constantly need things that outlive the function that created them (a list being built across many calls, a cached result, a connection object), or whose size is only known at run time (the body of a request). That data goes on the heap: a large pool of memory from which a program allocates chunks on request, and which stays allocated until it's explicitly or automatically released.

When code allocates, it gets back a pointer: the address of the chunk. The stack frame keeps the pointer; the data lives on the heap. In languages like Java, JavaScript and Python the same idea is called a reference.

In Python, everything is on the heap

Python takes this to an extreme. Every value is an object on the heap, even the integer 1 (sys.getsizeof(1) reports 28 bytes on a typical 64-bit CPython, versus the 8 a C long needs). A variable name is not a box holding a value. It's a reference (a pointer) to an object. Assignment copies the pointer, not the object.

Common misconception

"The stack holds primitive values, the heap holds objects" is a mantra from some other languages. In Python the name lives in the frame, all values live on the heap, and the frame only holds references. (For precision: in CPython the frames themselves are also managed by the interpreter rather than being one raw machine stack, but the model of "frames push and pop, with references to heap objects inside" is accurate for reasoning.)

Heap memory costs more than stack memory. The allocator (in C, malloc) must find a free chunk of the right size, keep records, and cope with fragmentation. Most importantly, someone has to decide when each chunk is no longer needed and release it. Stack memory has an automatic answer: when the function returns. The heap has no such natural moment. The rest of this chapter is about the different answers to "who frees it, and when?".

Leaks: when unused memory is never released

A memory leak is memory that the program no longer needs but never releases, so usage grows over time until performance suffers or the OS kills the process (chapter 6). Leaks come in two flavours:

  • Forgotten allocations (in manual-memory languages): the program allocated and lost the pointer without freeing.
  • Accidental references (in garbage-collected languages): the program can still reach data it will never use again, so the collector correctly refuses to free it.

The second kind catches many Python and Java programmers, because they believe the language has made leaks impossible. A very common example:

_seen = {}                          # module-level: lives as long as the process

def handle(request_id, payload):
    _seen[request_id] = payload     # added for every request... and never removed
    return process(payload)

Nothing is wrong with any single line, but over a week of traffic _seen holds every payload ever received. The usual causes are unbounded caches (a cache without an eviction policy is a leak in disguise; see chapter 2), lists of listeners or callbacks that are added but never removed, and long-lived objects accidentally holding references to short-lived ones. The fix is to make every growing structure bounded: evict old entries, use a size limit (functools.lru_cache(maxsize=1000)), or remove references when you're done. In Python, the standard library's tracemalloc module shows where memory is being allocated (see Try it yourself).

Manual memory management

Languages such as C and (traditionally) C++ leave the whole job to you. You ask for memory with malloc, use it, and give it back with free. It's fast and predictable: no collector, no pauses. It's also a rich source of bugs.

char *p = malloc(100);      /* ask the allocator for 100 bytes of heap */
strcpy(p, "hello");
free(p);                    /* give the memory back */

printf("%s\n", p);          /* BUG 1: use after free; p still points there, memory may be reused */
free(p);                    /* BUG 2: double free; can corrupt the allocator's records */

char buf[8];
strcpy(buf, "far longer than eight bytes");   /* BUG 3: buffer overflow, writes past the end */

char *q = malloc(1000);
q = NULL;                   /* BUG 4: leak; the only pointer is gone, 1000 bytes are lost */

Each of these compiles without complaint and may even appear to work in testing. Use after free and buffer overflow are not just crashes. They are the raw material of security exploits: an attacker who can make the program read or write memory it shouldn't can often take control of it. Heartbleed, the notorious 2014 OpenSSL bug, was a missing bounds check that let a remote client read far more of a server's memory than it should. Teams running very large C and C++ codebases (browsers and operating systems among them) have repeatedly reported that a majority of their serious security bugs are memory-safety bugs of this kind. That is the main motivation for every alternative below.

Go deeper: what malloc actually does, and fragmentation optional

An allocator like malloc asks the OS for big regions of address space (chapter 6 shows how) and then carves them into smaller chunks to hand out, keeping lists of the free ones. When you call free, the chunk goes back on a list; it is usually not returned to the OS straight away. So a process's memory use, as seen by the OS, can stay high even after the program has freed most of what it allocated.

Over time the heap can suffer fragmentation: lots of small free gaps between live objects, none big enough for a new large request, so the allocator has to ask for more memory even though the total free amount would suffice. Long-running servers sometimes show this as slowly growing memory with no leak at all. Allocators fight it with size classes, per-thread caches and arenas, and some garbage collectors fight it by moving live objects together (compaction). This is one reason that identical code can show different memory behaviour with different allocators.

Automatic memory management

The alternative is to let the language runtime decide when memory is garbage. There are two big families, and many languages use one or both.

Reference counting

The idea: every object carries a counter of how many references point at it. Assigning a new reference adds 1; dropping one subtracts 1. When the count reaches zero, nobody can reach the object, so it's freed on the spot. CPython works this way. You can watch it:

>>> import sys
>>> x = [1, 2, 3]
>>> sys.getrefcount(x)    # x itself + the temporary argument to this call
2
>>> y = x
>>> sys.getrefcount(x)    # x, y and the argument
3
>>> del y                  # count back to 2; del x as well and the list is freed immediately

Strengths: memory is released at the earliest possible moment, so usage stays low and behaviour is predictable. The cost of freeing is spread through the program. Weaknesses:

  • Overhead everywhere. Every reference copy or drop updates a counter in memory, which is extra work and extra cache traffic. With several threads, updating counts safely is expensive, which is one reason CPython has a global interpreter lock (chapter 10).
  • Cycles. If object A refers to B and B refers to A, each keeps the other's count above zero, even if nothing else can reach either. Plain reference counting never frees them.
  • Cascades. Dropping the last reference to a huge nested structure frees everything inside it at that moment. That can be a long pause.

To handle cycles, CPython adds a separate cycle collector (the gc module). Every so often it looks for groups of objects that only refer to each other and frees them. It is a tracing collector, which brings us to the second family.

Tracing garbage collection

A tracing collector doesn't count references. Instead, it periodically answers: what can the program still reach? It starts from the roots (global variables, and every variable in every active stack frame), follows every pointer, and marks everything it finds. Anything left unmarked is unreachable, so it's garbage. The simplest version is mark-and-sweep:

  1. Mark: walk the object graph from the roots, marking every object reached.
  2. Sweep: go through the heap and free every object that wasn't marked.

Tracing collectors have no per-assignment overhead, handle cycles naturally and let allocation be very fast. The price is that collection happens in bursts, and a collector usually has to stop the program (a stop-the-world pause) for at least part of its work, because it can't trace a graph that's changing underneath it. Java, Go, C#, JavaScript and many others use tracing collectors.

Generational collection

Tracing the whole heap each time would be wasteful. Programmers noticed something called the generational hypothesis: most objects die young. A temporary string, a request object, a loop's scratch list: gone moments after creation. A few objects live for the whole run. So collectors split the heap into generations. New objects start in a small young generation that is collected often and cheaply, since there is little to trace and nearly all of it is garbage. Survivors are promoted to older generations, collected rarely. CPython's cycle collector is generational too (three generations in Python up to 3.13; newer versions changed the details). The big pauses come from collecting the old generation, which holds most of the live data.

Why GC pauses hurt tail latency

In most programs a GC pause is invisible. In a server answering requests it's a problem, and the reason is the difference between the average and the tail. Suppose a service handles each request in 5 ms. Now the collector runs and freezes everything for 200 ms. Every request that was in flight, plus every request that arrives during the freeze, is delayed by up to 200 ms. If this happens every few seconds, the average barely moves. But the p99, the latency that the slowest 1% of requests exceed, jumps from 5 ms to 200 ms (networking ch. 13 explains why percentiles are the honest measure, and why fan-out makes the tail worse). Pause length depends on the collector, the heap size (more live objects means more to trace) and tuning; it ranges from sub-millisecond for collectors designed to minimise it to seconds in a badly configured big-heap process.

Engineers fight this in several ways: keep the heap smaller, allocate less (so collections are rarer), reuse objects, use collectors designed for short pauses that do most of their work concurrently while the program runs (they reduce pauses, not eliminate overhead), spread load over more instances, or move the latency-critical code to a language without a tracing collector. The case study Discord & the Garbage Collector follows one team through exactly this decision.

Analogy: closing the restaurant to clean

Manual management is every cook washing their own dishes right after use: no big stops, but one forgotten pan stays dirty forever and a pan washed too early ruins a meal. Reference counting is a rule that the last person to use an item must wash it immediately. Tracing GC is a cleaning crew who periodically stop service, check what's still in use, and clear everything else. It's thorough and nobody must remember to clean, but while they work, no food is served.

Where it breaks down: modern collectors are much cleverer than closing the whole kitchen. They clean one section at a time, or clean while service continues, so pauses are short. They still can't be zero-cost.

Rust's answer: ownership

Rust takes a third path that avoids both manual mistakes and run-time collectors. Every value has exactly one owner (a variable), and when the owner goes out of scope the value is freed. The compiler inserts the free for you, at a point it can work out in advance. You can lend a value out by borrowing it, and the compiler enforces strict rules: any number of read-only borrows, or exactly one mutable borrow, never both at once, and a borrow can never outlive the owner. Programs that break the rules simply don't compile, which rules out use-after-free, double free and data races without a garbage collector and without GC pauses. The price is a steeper learning curve, since you must structure your code so ownership is clear, and Rust does offer reference-counted pointers for the cases where sharing is genuinely needed. Swift uses automatic reference counting and C++ uses scope-based cleanup, each a different point in the same design space.

In command 3 the number is the count of objects the cycle collector found, normally 2 here (the exact count can differ between Python versions, because a cycle may include hidden internals). Command 5 is a subtle one: on macOS, ru_maxrss is reported in bytes, while on Linux it is in kibibytes, so the same program shows a thousand-times-different number. Always check the platform. Exact tracemalloc output differs too; the point is that it names the line responsible.

Distributed systems connection

A GC pause isn't only a latency problem. It's a failure-detection problem. Distributed systems decide that a node is dead when it stops answering for too long (networking ch. 16). A node frozen in a ten-second collection looks identical to a crashed node or a cut cable, so the cluster may elect a new leader, move its work elsewhere, or expire its lock, and then the "dead" node wakes up and carries on as if nothing happened. Two nodes both believing they're the leader is a recipe for corrupted data. This is why systems that use leases (time-limited permissions) must expect a process to be paused at any instruction, and why careful designs add "fencing tokens" to reject stale actors (more on timing in networking ch. 17). In your own services, watch GC pause time next to your p99 latency graph; they often rise together. And note how the memory hierarchy shows up again: every object in the heap is a cache-line-sized decision (chapter 2), so a design that creates fewer, bigger, flatter objects often also pauses less. Later, chapter 10 shows how threads each get their own stack, and how memory per connection limits how many connections one server can hold (see Studio 1).

Key takeaways

  • The call stack holds one frame per active function call (arguments, locals and a return address). Calling pushes, returning pops, so locals die automatically. It is fast and limited in size; too-deep recursion causes a stack overflow.
  • The heap holds data that outlives a call or has run-time size. It needs an answer to "who frees it, and when?". In Python every value is a heap object and names are references to them.
  • A memory leak is memory you no longer need but can still reach (or forgot to free). Unbounded caches and ever-growing collections are the usual culprits, even in garbage-collected languages.
  • Manual management (C) is fast and pause-free but permits use-after-free, double free, overflows and leaks, a major source of security bugs.
  • Reference counting (CPython) frees memory immediately but costs a counter update on every reference change and can't free cycles alone, so CPython adds a generational cycle collector. Tracing GC marks what's reachable from the roots and sweeps the rest, and generational collectors exploit that most objects die young.
  • Stop-the-world GC pauses barely affect the average but wreck tail latency, and in a cluster a long pause can look like a node failure.
  • Rust avoids both by tracking ownership at compile time: one owner, borrowing rules, and the compiler inserts the frees.

Check your understanding

What does a stack frame typically hold?

  1. All the objects the program has ever allocated
  2. Only the program's machine code
  3. One call's arguments, local variables and the return address
  4. The operating system's file table
A frame belongs to one function call. It is pushed when the call begins and popped when it returns, taking the locals with it. Long-lived objects go on the heap.

In Python, after a = [1, 2, 3] and b = a, what does b.append(4) do to a?

  1. a also becomes [1, 2, 3, 4], because both names refer to the same list object on the heap
  2. Nothing. b is an independent copy of the list
  3. It raises an error, because the list is now shared
  4. a becomes [4]
Assignment copies the reference, not the object. To get an independent list you'd write b = a.copy() or b = list(a).

Two objects refer only to each other and nothing else can reach them. What happens in CPython?

  1. Reference counting frees them immediately
  2. They stay forever, since Python can't handle cycles
  3. The program crashes
  4. Their reference counts never reach zero, so the separate cycle collector finds and frees them
Each object holds a reference to the other, so neither count drops to zero. CPython's cycle collector (the gc module) detects such unreachable groups. Pure reference counting alone would leak them.

A service has a median latency of 8 ms and an average of 10 ms, but users complain about random half-second freezes that show up in the p99. What is a plausible cause worth checking?

  1. The CPU clock speed is too low
  2. Stop-the-world garbage-collection pauses that delay whatever requests are in flight
  3. The stack is too small
  4. Too many cache lines
Pauses hit only some requests, so they leave the median alone and inflate the tail. Check the GC logs or pause metrics against the latency graph. A slow clock would slow everything uniformly.

Which statement about a Python process whose memory grows without bound is most likely true?

  1. It can't be a leak, because Python has garbage collection
  2. The stack is overflowing
  3. Something still references data that will never be used again, such as an ever-growing global dict, so the collector rightly keeps it
  4. The operating system has stopped freeing memory
A collector frees only what is unreachable. A global cache or list that grows forever stays reachable, so it is never freed. This is the most common "leak" in garbage-collected languages.

How does Rust prevent use-after-free without a garbage collector?

  1. Each value has one owner and borrows are checked at compile time, so memory is freed when the owner leaves scope and no reference can outlive it
  2. It reference-counts every object at run time
  3. It pauses the program to scan the heap
  4. It never frees memory
Ownership and borrow rules are enforced by the compiler. The frees are inserted at fixed points, so there are no GC pauses, and code that could access freed memory doesn't compile.

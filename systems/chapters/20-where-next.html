The whole course in one map

The three illusions, revisited

In chapter 0 we said the OS creates three illusions. Now you know how each is made, and exactly where it leaks.

🧠 "You have the CPU to yourself"

How it's made: the scheduler time-slices cores between processes and threads (ch. 7), saving and restoring registers (ch. 1).

Where it leaks: a thread gets paused mid-update, giving races that need locks, which in turn can deadlock. A container's CPU limit throttles you (ch. 19). A blocked event loop freezes everyone (ch. 16).

🧮 "You have memory to yourself"

How it's made: page tables map private virtual addresses onto shared physical RAM (ch. 6), with the stack and heap laid out inside (ch. 3).

Where it leaks: RAM is a layer of a hierarchy 100× slower than cache (ch. 2). Memory runs out, so pages swap or the OOM killer strikes. A container limit hides under what the app thinks it has.

💾 "Saved means saved"

How it's made: files and descriptors over a page cache (ch. 8).

Where it leaks: a successful write() is only in memory. Power loss, a torn write or a failed fsync breaks the promise, so we use fsync, atomic rename and checksums (ch. 9).

What you can now explain

Here's a checklist. Each line is the kind of statement a senior engineer makes in a design review. Try to expand each into a couple of sentences without peeking.

  • "A CPU just fetches and executes instructions, and the rest of the machine exists to keep it fed." (ch. 1)
  • "This is slow because of cache misses, not because of the algorithm: the data isn't laid out for locality." (ch. 2)
  • "Those pauses are garbage collection, and that deep recursion is a stack, not a heap, problem." (ch. 3)
  • "Every file, socket and I/O action is a system call, crossing from user space into the kernel." (ch. 4)
  • "The child is a zombie because the parent never called wait(), and Ctrl-C is just a signal." (ch. 5)
  • "The process's memory isn't all resident; a page fault just means the kernel hasn't mapped that page yet." (ch. 6)
  • "A context switch costs microseconds, which is why thousands of runnable threads hurt." (ch. 7)
  • "A socket is a file descriptor, and the process hit its descriptor limit." (ch. 8)
  • "A successful write isn't durable until fsync, and to replace a file safely you write a temp file, fsync it, then rename." (ch. 9)
  • "Threads share memory, which is why they're cheap to create and dangerous to use." (ch. 10)
  • "counter += 1 is read, add, write, so two threads can lose an update." (ch. 11)
  • "Take locks in a consistent order, keep critical sections short, and prefer message passing where you can." (ch. 12, ch. 13)
  • "The queue is unbounded, so under overload latency climbs and memory fills; we need a bound and a policy for saying no." (ch. 14)
  • "The thread is blocked in a system call, and that's fine until you need thousands of them." (ch. 15)
  • "An event loop asks the kernel which sockets are ready, and any blocking call inside it stalls every connection." (ch. 16, ch. 17)
  • "Threads, events, actors and channels trade simplicity against scalability; real servers mix them." (ch. 18)
  • "A container is a process with a restricted view and a resource budget, sharing the host kernel; a VM brings its own." (ch. 19)

How this sets up Data Systems

The next course, Data Systems, is planned but not yet written. It asks: how do you build something that stores data, answers questions about it and survives failure? Its building blocks are all in this course:

  • Storage engines are designed around the memory hierarchy (ch. 2): B-trees fit data into pages and cache lines' worth of reads; log-structured designs turn random writes into sequential ones. The files, page cache and fsync of ch. 8 and ch. 9 decide what "committed" can mean. The write-ahead log is the crash-safe log you build in Lab 2.
  • Transactions and isolation levels are the grown-up version of races and locks (ch. 11, ch. 12). A lost update between two threads becomes a lost update between two transactions, and "read committed", "repeatable read" and "serializable" are named answers to which interleavings you will tolerate.
  • Caching, queues and replication reuse backpressure (ch. 14) and the networking course's failure model (networking ch. 16).

Nothing there will be unfamiliar in kind. It's the same machine, the same illusions and the same leaks, with a database in the middle.

Key takeaways

  • The course in one line: the OS gives programs three illusions (own CPU, own memory, saved means saved) and each one leaks in a way you can now name.
  • Most system-design intuition is knowing where a program waits, what it shares and what survives a crash.
  • Data Systems builds on the memory hierarchy, files and durability, and on races, which become isolation levels.
  • Practise by building (labs), reading real failures (case studies) and designing (studios).

Check your understanding

Which illusion explains why a database calls fsync before saying a transaction is committed?

  1. You have the CPU to yourself
  2. Saved means saved
  3. You have memory to yourself
  4. Every file is a socket
A successful write() usually lands only in the page cache. fsync asks for it to reach stable storage, which is what "committed" must mean (chapter 9).

Two threads both run counter += 1 and one increment is lost. Which later database concept is the same problem in disguise?

  1. Indexing
  2. Caching
  3. Replication lag
  4. Transaction isolation: a lost update between two transactions
The interleaving is identical. Isolation levels name which of these interleavings the database promises to prevent (chapters 11 and 12).

A server's latency is high and its CPU is mostly idle. According to this course, what is the best first suspicion?

  1. Waiting: on a disk, a lock, a queue, the network or a CPU throttle
  2. The programming language is too slow
  3. The CPU clock speed is too low
  4. There are too many comments in the code
An idle CPU with slow responses means time is spent waiting, not computing. Find what it waits for (chapters 7, 9, 12, 14, 19).

What is the key difference between a container and a virtual machine?

  1. Containers need more memory
  2. VMs share the host's kernel; containers don't
  3. Containers share the host kernel and are restricted by namespaces and cgroups; VMs run their own kernel
  4. Containers can run any operating system
That is why containers are light and start quickly, and why the isolation boundary is thinner than a VM's (chapter 19).

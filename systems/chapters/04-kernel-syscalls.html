The Kernel & System Calls

Your program can compute, but it can't touch a disk, a network card or even another program's memory. Every time it wants anything from the outside world it has to ask one special piece of code, the kernel, through a narrow, guarded doorway. This chapter explains why that doorway exists, how the CPU enforces it, and what it costs to walk through.

Why this matters

Every read() from a file, every accept() on a socket, every fork() and every malloc that needs more memory ends in a system call. When a server is "slow", the explanation is very often "it makes too many system calls" or "it waits inside one". If you know what a system call is, you can read strace output like a flight recorder, understand why buffering exists, and see why databases, web servers and message brokers all batch their work. It is also the foundation for the next chapters: processes, virtual memory and files are all things the kernel provides.

Why a kernel exists

Imagine a computer with no operating system, where every program talks straight to the hardware. Three problems appear almost immediately.

  1. Protection. A buggy program could overwrite another program's memory, or scribble over the disk's file layout. A malicious one could read your passwords out of your browser's memory. Nothing would stop it.
  2. Sharing. There is one CPU (a few cores), one pool of RAM, one disk and one network card, and hundreds of programs that all want them. Someone has to decide who goes next and make sure nobody hogs everything.
  3. Abstraction. There are thousands of different disks, network cards and keyboards. Every program author can't be expected to know the register layout of every model. Programs want to say "give me the next 4,096 bytes of this file", not "send command 0x25 to controller 3".

The kernel is the part of the operating system that solves all three. It is a large program that is always loaded in memory, it is the only code allowed to touch the hardware directly, and it hands out the hardware to everything else in carefully limited pieces: "processes" (chapter 5), "virtual memory" (chapter 6) and "files" (chapter 8) are all kernel inventions that hide the real machine behind a friendlier, safer picture.

Analogy: the bank teller window

Customers (programs) are not allowed behind the counter. They can't open the vault, count the cash or edit the ledgers. To get anything done they stand at a window and make a request: "withdraw 50", "check my balance". The teller (the kernel) checks who they are and whether the request is allowed, goes into the back room, does the work, and slides the result through the window. Every customer is served through the same small set of request forms, and no customer sees anyone else's account.

Where it breaks down: a teller is a separate person who walks away from the window. The kernel isn't a separate worker: when you make a system call, your own thread of execution crosses the line and keeps running, now with full privileges, on the same CPU core, executing kernel code on your behalf.

User mode and kernel mode

The "window" is not a convention that programs politely follow. It is enforced by the CPU itself. Every modern CPU has at least two privilege levels, and at every instant it is running in exactly one of them:

  • Kernel mode (also called supervisor mode): everything is allowed. The code can execute any instruction, access any memory address and talk to any device. On x86 this is "ring 0"; on ARM it is exception level 1 (EL1).
  • User mode: a restricted subset. Some instructions are privileged and refuse to run: halting the CPU, changing the page tables that define memory, enabling or disabling interrupts, and talking directly to hardware devices. Memory belonging to the kernel (and other processes) is off limits. On x86 this is "ring 3"; on ARM it is EL0.

The current mode is just a few bits inside the CPU, and only specific events can change them. If a user-mode program tries a privileged instruction, or touches memory it doesn't own, the CPU doesn't obey. It raises an exception, which jumps into the kernel, and the kernel typically kills the program (on Unix, with the signal SIGSEGV for a bad memory access, or SIGILL for an illegal instruction; that is the "Segmentation fault" you may have seen). Chapter 5 covers signals.

Common misconception

"The kernel is a special process that runs in the background, like a service." It isn't a process. It is a body of code that sits in memory and runs inside whichever process just made a system call, or whatever was running when a hardware event arrived. Your process doesn't get paused so that "the kernel process" can run. Instead, the very same CPU core switches from user mode to kernel mode, runs kernel code on its behalf, and switches back.

Anatomy of a system call

A system call (syscall) is a request from a user-mode program to the kernel. Think of it as a function call that crosses the privilege boundary. A normal function call just jumps to an address in the same program. A syscall can't do that: the kernel's code lives at addresses the program isn't allowed to touch, and it must run in kernel mode. So the CPU provides a special instruction for exactly this purpose: syscall on x86-64, svc (supervisor call) on 64-bit ARM. The instruction does three things in one atomic step: it switches the CPU to kernel mode, it saves where the program was, and it jumps to a single, fixed entry address that the kernel configured at boot. The program can't choose where to land inside the kernel; that is what makes the doorway safe.

Since there is only one entry point, how does the kernel know which service you want? By a number. Before executing the instruction, the program puts a syscall number in a designated register, and the arguments in other registers. The kernel has a table that maps numbers to handler functions. On Linux x86-64, for example, 0 is read, 1 is write and 2 is open (the numbers differ on every architecture and OS, which is one reason programs don't use them directly). Let's follow one read() all the way through.

Step through

One read() system call, from user space into the kernel and back

  1. Your code asks for data. In Python, f.read(4096) on an unbuffered file ends up calling read(fd, buf, 4096). At this moment the CPU is in user mode: this code can only touch its own process's memory.
  2. The libc wrapper prepares the call. read() in the C library (libc; on macOS it lives in libSystem) is a tiny function. It puts the syscall number for "read" in one register, the file descriptor, buffer address and length in three more, and executes the syscall instruction (svc on ARM).
  3. The trap. That one instruction makes the CPU save the program's place, switch to kernel mode and jump to the kernel's single entry point. The kernel also switches to its own private stack, so the user program can't tamper with kernel data by pointing its stack pointer somewhere sneaky. The dashed line is the privilege boundary.
  4. Look up the service. The entry code saves the user's registers, then uses the syscall number as an index into the syscall table and calls the matching handler, here sys_read. An out-of-range number simply returns an error.
  5. Never trust the caller. sys_read checks everything it was given: is that file descriptor open in this process? Was it opened for reading? Does the buffer address really belong to this process and is it writable? A program can pass garbage, and the kernel must never be fooled by it.
  6. Find the bytes. The kernel looks in its buffer for the file (the page cache, chapter 9) or the socket. If the bytes are already there, skip ahead. If not, it asks the device for them and puts your process to sleep (state "blocked", chapter 5) so other programs can use the core. When the device finishes it raises an interrupt, and the process is woken up.
  7. Copy out. The kernel copies the bytes from its own buffer into buf in your memory. It must copy rather than hand you a pointer into its memory, because your process is not allowed to see kernel memory at all.
  8. Return. The handler puts the result (the number of bytes read, or a negative error code) in the return register and executes a return-from-kernel instruction (sysret on x86-64, eret on ARM). The CPU drops back to user mode at the instruction right after the trap.
  9. Carry on. libc turns a negative result into the familiar -1 plus a number in the global errno (Python turns that into an OSError exception). Your code continues, usually unaware how much happened in between: two mode switches, some validation, possibly a sleep and a device interrupt.

Two details are worth remembering. First, the "return" is not a normal return: the kernel is careful to restore exactly the registers the program expects, so from the program's point of view it was an ordinary function call. Second, the kernel is defensive. Its handlers treat every argument as potentially hostile. If it trusted a pointer from user space, any program could trick the kernel into overwriting its own data.

Interrupts, exceptions and drivers

A system call is only one of three ways the CPU ends up in the kernel. All three use the same basic trick: save where you were, switch to kernel mode, jump to a handler the kernel registered in advance, and later resume.

System call
The program asks, on purpose. It is synchronous with the program's own instructions.
Exception
The program did something the CPU can't complete: divided by zero, used an illegal instruction, or touched a memory page that isn't mapped right now (a page fault, chapter 6). The kernel decides whether to fix the problem (load the page and retry) or kill the program.
Interrupt
A device or a timer demands attention, completely independent of what the program is doing: a packet has arrived, a disk read has finished, a key was pressed, 4 ms have passed.

Interrupts matter for two reasons. First, they are how I/O works without wasting the CPU: instead of the CPU asking the disk "are you done yet?" a million times (polling), the CPU does other work and the disk interrupts it when ready. Second, one special device, the timer, interrupts every few milliseconds or less. This is how the kernel takes the CPU back from a program stuck in an infinite loop: no program can hold a core forever, because the timer interrupt forces a trip into the kernel, which can then switch to someone else (chapter 7).

The kernel code that knows how to talk to one specific kind of device (its registers, its commands, its quirks) is called a device driver. Drivers are why the kernel can offer a uniform interface ("a block device you can read 4 KiB from") on top of thousands of different SSDs, and a uniform socket interface on top of many different network cards. In the Linux source tree, drivers make up a very large share of the code. They also run in kernel mode, which has a consequence we'll return to in the microkernel box below: a bug in a driver is a bug in the kernel.

The syscalls you will meet again and again

Linux has a few hundred system calls, and most programs use a few dozen. The ones below cover almost everything a server does. Names are Linux/POSIX names; macOS uses the same names for the C functions (it is certified as a Unix), although its raw syscall numbers are private and not stable, so even there programs go through the system library.

AreaCallsWhat they do
Filesopen/openat, read, write, close, lseek, fsyncGet a file descriptor (a small integer) for a file, move bytes through it, release it. fsync forces data onto the disk (chapter 9).
Networksocket, bind, listen, accept, connect, send/recvThe TCP server recipe from networking chapter 7 and 8. Notice that socket() returns a file descriptor and you then read/write it like a file (chapter 8).
Processesfork (on Linux really clone), execve, wait4, exit, killCreate a copy of a process, replace it with another program, wait for it to finish, end it, send it a signal (chapter 5).
Memorymmap, munmap, brkAsk for more address space, or map a file into memory (chapter 6). This is what malloc uses underneath when it needs more memory.

Even a very simple server is nothing but these calls in a loop: socket, bind, listen, then repeat accept, read, write, close. Every web API from networking chapter 12 bottoms out in them.

libc and Python wrap the syscalls

You rarely write the syscall instruction yourself. There are two layers of wrapping between your code and the kernel.

  1. The C library (libc) provides ordinary functions called read, write, open and so on. Each one is a thin wrapper that loads registers, executes the trap and converts the result (negative values become -1 plus errno). Libc also adds some friendlier functions on top: printf, fopen and malloc are not system calls. They are library code that eventually makes some.
  2. Your language runtime wraps libc again. In Python, os.read, os.write, os.open and os.fork are very thin and map almost one-to-one to the syscalls. The built-in open() and print() add layers of buffering and text decoding on top.

Why a syscall costs more than a function call

A call to a Python or C function is just a jump within your own process. A system call involves much more:

  • The CPU must switch privilege levels and save/restore register state.
  • The kernel must validate arguments and look up the descriptor and its state.
  • Switching between user and kernel code disturbs the CPU's caches, branch predictors and sometimes its TLB (the address-translation cache from chapter 6), so the code that runs afterwards is a little slower than it would have been.
  • Since 2018, protective measures against hardware security flaws (Meltdown and Spectre) made kernel entry noticeably more expensive on many CPUs.
  • And the actual work, such as copying bytes or touching a disk, is on top of that fixed entry fee.

Exact figures depend heavily on the CPU, operating system and security settings, so treat the picture below as an order-of-magnitude guide, on a log scale where each step to the right is about ten times slower.

This explains one of the most common performance rules in programming: make fewer, bigger system calls. Writing 1,000,000 single bytes to a file one write() at a time pays the fee 1,000,000 times. Collecting them in a buffer in your own memory (cheap, no mode switch) and writing 8,192 bytes at a time pays it about 122 times (8 KiB is a classic buffer size; recent Python versions pick larger ones, so the real count is even lower). This is exactly what buffered I/O does, and it is why Python's open() returns a buffered file by default. Other forms of the same idea appear everywhere:

  • writev / readv write or read several separate buffers in one call.
  • epoll_wait / kevent return many ready events per call instead of one.
  • sendfile lets the kernel copy a file straight to a socket without bouncing the bytes through your program.
  • On Linux, io_uring lets a program queue up many operations in shared memory and submit them with a single call.

Common misconception

"If I called f.write() the kernel has it." Not necessarily. With Python's default buffered files, f.write(b"x") usually just appends to a buffer inside your own process and makes no system call at all. Until the buffer fills or you call flush() or close(), the kernel hasn't seen your data, so if your process is killed, that data is gone. (And even after the kernel has it, it may only be in RAM: see chapter 9.)

Go deeper: monolithic kernels vs microkernels optional

Where should the kernel's many jobs (file systems, network stack, drivers) live? There are two classic answers.

Monolithic: everything runs together in kernel mode, as one big program. Parts call each other as ordinary functions, which is fast. The cost is that all of that code is fully trusted, and a bug in any driver can corrupt the whole kernel. Linux and the BSDs are monolithic (Linux can load pieces as modules at run time, but they still run in kernel mode).

Microkernel: keep only the bare minimum in kernel mode (scheduling, memory management, message passing) and run file systems, network stacks and drivers as ordinary user-mode server processes. A crashing driver is just a crashed process that can be restarted, and the trusted core is small enough to scrutinise, even to verify mathematically (seL4 did that). The price is more messages and more mode switches for every operation. QNX, Minix and seL4 are microkernels.

Real systems blur the line. macOS and iOS use XNU, a hybrid: it began from the Mach microkernel but runs the BSD file systems and networking in the same kernel address space for speed. Windows NT is also usually called hybrid. The debate is a classic engineering trade-off, safety and isolation against speed, and you'll see the same trade-off between "everything in one process" and "many small services" in distributed systems.

Go deeper: system calls that never enter the kernel (vDSO) optional

Some "system calls" only read information the kernel already has, such as the current time. Entering the kernel just to read a number is wasteful, so Linux maps a small shared page, the vDSO, into every process. It contains ordinary user-mode code plus a clock value the kernel keeps up to date. When you call clock_gettime() or gettimeofday(), libc runs that code and returns without a mode switch. macOS has a similar fast path for time. This is also why strace may not show these calls even though your program makes them constantly.

Try it yourself

Try it yourself: watch the system calls of a tiny program

On Linux (or WSL) the tool is strace. It runs a program and prints each system call as it happens. It only observes your own program and needs no sudo. (If it's missing: sudo apt install strace on Debian/Ubuntu, which is the only step that needs elevated rights.) Your output will differ from the example.

$ strace -c python3 -c "print('hi')"        # -c: don't list calls, count them
hi

------ ----------- ----------- --------- --------- ----------------

 18.72    0.000239           2       112           read
 12.41    0.000158           2        60           mmap
  9.30    0.000119           2        55        41 newfstatat
  ...
  0.31    0.000004           4         1           write
------ ----------- ----------- --------- --------- ----------------
100.00    0.001277           2       540        74 total

$ strace -e trace=openat,read,write python3 -c "print('hi')" 2>&1 | tail -4
openat(AT_FDCWD, "/usr/lib/python3.12/encodings/utf_8.py", O_RDONLY|O_CLOEXEC) = 4
read(4, "\"\"\"\nPython 'utf-8' Codec\n...", 4096) = 1648
write(1, "hi\n", 3)                     = 3
+++ exited with 0 +++

Look at the results. Printing "hi" is one write, but starting Python takes hundreds of calls, mostly openat and read to load the interpreter's modules. The errors column shows calls that returned an error, often just "file not found" while Python searches for a module. Now see buffering in action:

$ strace -e trace=write python3 -c "print('a'); print('b'); print('c')" > /dev/null
write(1, "a\nb\nc\n", 6)                 = 6
+++ exited with 0 +++

Three print calls, one write. When the output isn't a terminal, Python buffers it and writes it all at exit. (Run it without > /dev/null and, because a terminal is interactive, you'll see a separate write per line.)

On macOS

macOS has no strace. Its equivalent, dtruss (built on DTrace), refuses to trace most processes unless you disable System Integrity Protection, which we will not ask you to do. Two safe alternatives: run the Linux commands above in a Linux container, a VM, or WSL; or look from inside Python, with the next experiment.

Python-level view (macOS and Linux). Python 3.8+ lets you register an audit hook that is called for sensitive events such as opening files and connecting sockets. It isn't the raw syscall list, but it shows you the requests that become syscalls:

# audit.py
import sys

def hook(event, args):
    if event in ("open", "socket.connect", "os.listdir"):
        print("AUDIT", event, args, file=sys.stderr)

sys.addaudithook(hook)

open("/etc/hosts").close()
import os; os.listdir(".")
$ python3 audit.py
AUDIT open ('/etc/hosts', 'r', 16777216)
AUDIT os.listdir ('.',)    # the third number in "open" is OS-specific flag bits (16777216 here is macOS; Linux shows 524288)

And a measurement of the syscall fee. This writes one million single bytes to /dev/null (the "black hole" file that discards everything), first with one syscall per byte, then through Python's buffered file:

import os, time

N = 1_000_000

fd = os.open("/dev/null", os.O_WRONLY)
t = time.perf_counter()
for _ in range(N):
    os.write(fd, b"x")                 # one system call per byte
raw = time.perf_counter() - t
os.close(fd)

f = open("/dev/null", "wb")            # buffered by default
t = time.perf_counter()
for _ in range(N):
    f.write(b"x")                      # roughly N / buffer-size system calls
f.close()
buffered = time.perf_counter() - t

print(f"unbuffered: {raw:.2f} s   buffered: {buffered:.2f} s   ratio: {raw/buffered:.0f}x")
$ python3 cost.py
unbuffered: 0.31 s   buffered: 0.06 s   ratio: 5x    # your numbers will differ

Don't expect a precise ratio. Both loops also pay Python's own per-call overhead, which hides some of the difference, and /dev/null does no real I/O. With a real file or socket, or a slower kernel configuration, the gap is usually larger. The direction is what matters.

On a Linux VM

On Linux you can also follow child processes and several calls at once. Run these on your lab machine (macOS has no strace); they need no sudo:

$ strace -f -e trace=openat,read,write python3 -c "print('hi')" 2>&1 | tail -5  # -f follows any children too
$ strace -c python3 -c "print('hi')" 2>&1 | tail -15  # the summary table, sorted by time

The first shows the last few calls, ending in the single write of "hi". The second counts how many calls of each kind Python made just to start up.

Distributed systems connection

The syscall boundary is a miniature RPC. A program sends a numbered request with arguments across a trust boundary to a more privileged service, which validates it, performs it, and replies with a result or an error code. The same discipline shows up in the networking course's APIs (chapter 12): never trust the caller, return explicit errors, and keep the interface narrow and stable.

The cost lesson transfers too. A syscall's fee is why we buffer; a network round trip's fee (networking chapter 13) is why distributed systems batch requests, pipeline them, and use group commits and bulk APIs. And every network operation eventually becomes the same few calls you just met (send, recv, epoll_wait), so when a server is slow, strace or its equivalent is often the fastest way to see where it waits.

Key takeaways

  • The kernel exists to protect programs from each other, to share the hardware fairly and to hide hardware differences behind simple abstractions such as files and sockets.
  • The CPU enforces this with privilege levels. User mode can't run privileged instructions or touch kernel memory, and violations cause an exception that usually kills the program.
  • A system call is a special trap instruction: the syscall number picks a service from a table, the kernel validates everything it is given, does the work, and returns to user mode.
  • Interrupts (from devices and the timer) and exceptions are the other ways into the kernel. Interrupts are how I/O avoids polling and how the kernel takes back the CPU.
  • libc and the Python runtime wrap syscalls. open, read, write, socket, fork/exec and mmap are the core vocabulary.
  • A syscall costs far more than a function call (and device access far more still), so buffer, batch and avoid unneeded calls.
  • On Linux, strace shows the conversation with the kernel. On macOS, use a Linux environment or Python-level tools instead.

Check your understanding

A user-mode program tries to execute a privileged instruction, such as one that changes the memory-mapping tables. What happens?

  1. The instruction runs normally; the kernel checks it afterwards
  2. The CPU silently ignores it and continues
  3. The CPU raises an exception, the kernel takes over and typically terminates the program
  4. The program is paused until an administrator approves it
The privilege check is done by the CPU hardware, before the instruction takes effect. The violation becomes an exception that jumps into the kernel, which usually kills the offender. That's what makes the protection reliable even against buggy or malicious programs.

Why do system calls use a numbered table and one fixed entry point rather than letting programs jump to any kernel function they like?

  1. A single, kernel-chosen entry point means programs can't jump into the middle of kernel code or bypass its checks
  2. It makes system calls faster than ordinary function calls
  3. Kernel functions are stored on disk and must be looked up by number
  4. Because Python can only call functions by number
The guarded doorway is the whole point. If a program could jump anywhere in the kernel it could skip permission checks. The fixed entry point plus a validated number guarantees every request goes through the kernel's own front door. It is not faster, and it isn't about disks or Python.

Your program calls f.write(b"x") a million times on a file from Python's built-in open(path, "wb"). Roughly how many write system calls are made?

  1. Exactly one million, one per call
  2. Exactly one, at the end
  3. None, because Python never uses system calls for files
  4. Far fewer than a million: data collects in a user-space buffer and is written in large chunks
Python's buffered file collects small writes in memory and only calls write() when the buffer (typically around 8 KiB or more) fills, or on flush/close. That's the "fewer, bigger syscalls" rule in action. It's never exactly one, because the buffer is finite, and Python certainly does use system calls.

Which statement about the kernel is true?

  1. It is a separate process that waits for programs to send it messages
  2. It is code that runs on the same CPU cores, on behalf of whichever program made a system call or whatever was running when an interrupt arrived
  3. It runs only when the computer boots, then goes to sleep
  4. It runs on a dedicated CPU core that user programs can't use
The kernel isn't a process and doesn't need its own core. It is code that the CPU runs in kernel mode, entered via system calls, exceptions and interrupts, and it keeps running at all those moments for as long as the machine is on.

Why does a hardware timer interrupt matter for the kernel?

  1. It keeps the computer's clock display accurate
  2. It lets programs measure how long a function takes
  3. It forces the CPU to enter the kernel regularly, so the kernel can take the CPU back from a program that never yields
  4. It makes system calls cheaper
Without the timer, a program stuck in while True: pass would own its core forever. The periodic interrupt hands control to the kernel, which can then decide to run someone else. This is the basis of preemptive scheduling (chapter 7).

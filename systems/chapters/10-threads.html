Threads

A process can do several things at once by running several threads inside the same memory. That's how a server answers many people at the same time, and also how two lines of code can quietly wreck each other's data. In this chapter you'll see exactly what a thread is, what it shares and what it keeps private, and why Python threads speed up some programs and not others.

Why this matters

Almost every real server is concurrent: a web server handles thousands of requests, a database runs many queries, a chat app reads from many sockets. Threads are the oldest and most common way to write that. They're also the root of the hardest bugs in this course: races (chapter 11), deadlocks (chapter 13) and overloaded thread pools (chapter 14). Before you can reason about those, you need a clear picture of what threads share and what they don't.

From one flow of execution to several

Until now every program in this course had a single flow of execution: one place in the code where the CPU is "up to", moving forward one instruction at a time. In chapter 5 a process was one running program with its own private memory. Now we let one process have several flows, each at its own place in the code.

Each such flow is a thread. To keep its place, a thread needs only a little of its own:

  • a set of CPU registers, including the program counter (which instruction is next) and the stack pointer (chapter 1);
  • its own stack: the region of memory holding its function calls, parameters and local variables (chapter 3).

Everything else belongs to the process and is shared by all its threads: the program's code, the heap (every object allocated with new, malloc or, in Python, basically every object), global variables, and the table of open files and sockets (chapter 8).

That diagram is the whole chapter in one picture. Private stacks mean that two threads can both run the same function without their local variables colliding. A shared heap means that if thread 1 hands thread 2 a reference to an object, they're looking at the same object, and any change one makes is instantly visible to the other. That's what makes threads convenient and also what makes them dangerous.

Analogy: a shared document and private notepads

Picture three people editing one shared document (the heap and globals). Each person also has a private notepad (their stack) where they scribble intermediate numbers, and a finger on the line they're reading (their registers). Working in the same document is fast: no one has to send copies around. But if two people rewrite the same paragraph at once, one of them overwrites the other.

Where it breaks down: real editors are all awake at once, and a human notices when someone else is typing in the same spot. A thread can be frozen by the operating system at any instruction and resumed later, with no idea that the document changed in between. That's the heart of chapter 11.

Threads versus processes

The kernel can already run many programs at once, each as a process. So why have threads at all? Because processes are deliberately walled off from each other (chapter 6), and walls cost something.

ProcessesThreads (inside one process)
MemoryEach has its own address spaceAll share one address space
Cost to createHigher: a new address space and tables to set up (noticeably more work than a thread)Lower: a stack and a register set
Cost to switchHigher: the memory mappings change, so caches and the TLB lose useful contents (chapter 7)Lower: same mappings stay in place
CommunicationNeeds a channel the kernel provides: pipes, sockets, shared-memory regionsJust read and write a variable (carefully!)
IsolationStrong: one process crashing leaves the others runningNone: a fatal fault in one thread kills the whole process
Main dangerCopying data and coordinating through channels is slow and clumsyRaces and deadlocks on shared data

Neither is "better". Chrome, for example, generally keeps different sites in different processes so that one crashing page can't take down the rest, and then uses many threads inside each process. Databases like PostgreSQL use a process per connection; MySQL uses a thread per connection. Both work, with different trade-offs.

Under the hood (Linux)

The Linux kernel makes no hard distinction: both are "tasks", and creating a thread is the same system call as creating a process (clone) with flags saying "share the memory, the files and so on". The OS's own scheduler (chapter 7) schedules threads, not processes. A process is really a container, and a thread is what actually gets a turn on a core.

Creating threads in Python

Python's standard library wraps the operating system's threads in threading.Thread. You give it a function to run; start() launches it and returns immediately; join() waits for it to finish.

import threading, time

shared = []                                   # lives on the heap: every thread sees it

def worker(name, delay):
    local = f"hello from {name}"              # lives on THIS thread's own stack
    time.sleep(delay)
    shared.append(local)
    print(f"{name} (id {threading.get_ident()}) done")

t1 = threading.Thread(target=worker, args=("A", 0.2))
t2 = threading.Thread(target=worker, args=("B", 0.1))
t1.start(); t2.start()
print("main thread keeps going while they run")
t1.join(); t2.join()                          # wait for both to finish
print(shared)
$ python3 basics.py
main thread keeps going while they run
B (id 6129364992) done
A (id 6112538624) done
['hello from B', 'hello from A']

Notice three things. The main thread printed its line before the workers finished, so start() doesn't wait. B finished first because it slept less. And the list shared was filled by both workers, because it lives on the heap and every thread can reach it. Meanwhile each worker's variable local was its own, living on its own stack.

Without join(), the main thread could reach the end of the script while workers are still running. (Python waits for ordinary non-daemon threads at exit, but code that uses their results must join first.)

Common misconception

"Calling start() runs the function right now, so I can read its result on the next line." No: the new thread merely becomes eligible to run. When it actually gets the CPU is up to the scheduler, so the order of events between threads is not something you control.

Concurrency is not parallelism

These two words are often mixed up, and the difference matters.

Concurrency
Several tasks are in progress at the same time, their lifetimes overlapping. It's a way of structuring a program. One core taking turns is enough.
Parallelism
Several tasks are literally executing at the same instant, on different cores. It's a way of running a program, and needs more than one core.

Here's why it matters. Concurrency helps when threads wait: while A waits for the network, the core runs B. Parallelism helps when threads compute: two cores do twice the arithmetic. A program can be concurrent on one core without being parallel at all, which is exactly what Python's most famous quirk does.

The Python GIL

CPython, the standard Python interpreter, has a global interpreter lock (the GIL): a lock that only lets one thread at a time execute Python bytecode inside one process. Threads still exist, each with its own stack and registers, and the OS can place them on different cores. But to run Python code a thread must hold the GIL, so Python-level work never actually runs in parallel.

The GIL exists mainly because CPython's memory management (reference counting, chapter 3) isn't safe to run from several threads without protection, and one big lock was the simple, fast-for-single-threaded-code solution. A running thread gives the GIL up in two situations: after a short time slice (5 ms by default, sys.getswitchinterval()), and whenever it makes a blocking call such as time.sleep, reading a socket or reading a file. That second rule is the important one.

Try measuring it

Don't take this on trust. The script below does four CPU-bound jobs (pure Python arithmetic) and four I/O-bound jobs (a one-second wait standing in for a network call), first one after another and then with threads. For the CPU job it also tries ProcessPoolExecutor, which uses separate processes, each with its own interpreter and its own GIL.

import time
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def cpu_work(n):
    total = 0
    for i in range(n):
        total += i * i
    return total

def io_work(seconds):
    time.sleep(seconds)          # stands in for a network or disk wait

def timed(label, fn):
    start = time.perf_counter()
    fn()
    print(f"{label:<22} {time.perf_counter() - start:5.2f} s")

N = 10_000_000

def run_pool(pool_cls, workers, func, arg, jobs):
    with pool_cls(max_workers=workers) as pool:
        list(pool.map(func, [arg] * jobs))

if __name__ == "__main__":
    print("--- CPU-bound: 4 jobs of pure Python arithmetic ---")
    timed("one after another", lambda: [cpu_work(N) for _ in range(4)])
    timed("4 threads", lambda: run_pool(ThreadPoolExecutor, 4, cpu_work, N, 4))
    timed("4 processes", lambda: run_pool(ProcessPoolExecutor, 4, cpu_work, N, 4))
    print("--- I/O-bound: 4 jobs that each wait 1 second ---")
    timed("one after another", lambda: [io_work(1) for _ in range(4)])
    timed("4 threads", lambda: run_pool(ThreadPoolExecutor, 4, io_work, 1, 4))
$ python3 gil.py
--- CPU-bound: 4 jobs of pure Python arithmetic ---
one after another        0.91 s
4 threads                0.85 s
4 processes              0.33 s
--- I/O-bound: 4 jobs that each wait 1 second ---
one after another        4.02 s
4 threads                1.01 s

Read it carefully. Four threads on CPU-bound work were no faster than doing the jobs in a row (0.85 s against 0.91 s; on some machines or versions they are slightly slower, because of the cost of passing the GIL back and forth). Four processes did the same work in about a third of the time on this 10-core machine: more than 2.5 times faster, though not a clean 4 times, because starting processes and sending results back costs something. The I/O jobs show the opposite: four one-second waits took four seconds in a row but only one second with threads, because all four threads sat waiting at the same time.

The if __name__ == "__main__": guard is required. On macOS and Windows, multiprocessing starts each worker by launching a fresh Python that imports your script; without the guard, every worker would try to start workers of its own.

Common misconception

"The GIL means Python threads are useless", or the opposite, "the GIL makes Python threads safe." Neither is true. Threads are very useful for I/O-bound work and for keeping a program responsive. And the GIL protects the interpreter's internals, not your data: your code can still be interrupted between two bytecodes, so your own shared variables can still be corrupted. Chapter 11 shows exactly how.

Two more details worth knowing. Libraries written in C, such as NumPy, often release the GIL while doing heavy numeric work, so threads can run in parallel inside them. And the GIL is a feature of CPython, not of the Python language: other implementations differ.

Go deeper: free-threaded Python optional, experimental

Since Python 3.13 there is an optional "free-threaded" build of CPython (PEP 703) that runs without the GIL, so Python threads can use several cores. It was experimental at first and is not the default: the interpreter you normally install still has the GIL. Check which one you have with sys._is_gil_enabled() (available from 3.13; on older versions the attribute doesn't exist).

Removing the GIL does not remove the need for locks. If anything, it makes the races from chapter 11 easier to trigger. Everything you learn in this part applies to both builds, and to languages like Java, Go and C++ which have never had a GIL.

When threads are the right tool

Good fit

I/O-bound waits (several network calls or file reads at once). Responsiveness: a background thread keeps the UI or a heartbeat alive. Modest concurrency: tens or hundreds of tasks, mostly independent. In languages without a GIL, CPU parallelism over data in shared memory.

Poor fit

CPU-bound work in CPython: use processes. Tens of thousands of connections: every thread has a stack and scheduler cost, so use an event loop (chapter 16). Lots of shared mutable state: every shared variable is a future bug; prefer passing messages through queues (chapter 14).

A useful rule of thumb: ask what the work is waiting on. If it's waiting on something outside the CPU (network, disk, another service), threads (or an event loop) will help. If it's waiting on the CPU itself, you need more cores, and in Python that means more processes.

"Thread-safe": a first look

You'll see the phrase thread-safe on documentation pages. A piece of code is thread-safe if it behaves correctly when called from several threads at once, without the caller adding extra protection. Python's queue.Queue is thread-safe: many threads can put and get without corrupting it. A plain integer that several threads increment is not: the final value can come out wrong, and it can come out wrong only on some runs, only under load, only on your production server.

A small test of intuition: if two threads each run counter += 1 a million times, is the answer always two million? Your instinct probably says yes. The next chapter shows it isn't, explains the mechanism, and lets you play the part of the scheduler. Then chapter 12 shows the tools that make code thread-safe. You can also try both in Lab 3.

Try it yourself

Try it yourself: count your threads, then time them

Everything here is safe and read-only, and uses only the Python standard library. First, ask Python about its own threads.

import os, threading, time

for i in range(3):
    threading.Thread(target=time.sleep, args=(2,), name=f"worker-{i}").start()

print("process id:", os.getpid())
print("threads alive:", threading.active_count())
for t in threading.enumerate():
    print("  ", t.name)
$ python3 tinfo.py
process id: 3280
threads alive: 4
   MainThread
   worker-0
   worker-1
   worker-2

Your process id will differ. Your program had a main thread plus the three you started: four threads sharing one process id. To see them from outside the program, run a longer-lived script and, in a second terminal, look at it with ps -M -p PID on macOS (one line per thread) or ps -L -p PID or ls /proc/PID/task on Linux. These commands only read information.

Then run gil.py from above and compare your own numbers. Questions to try: what happens to the "4 threads" CPU time if you change the work to time.sleep(0.5)? How many cores does os.cpu_count() report, and does ProcessPoolExecutor(max_workers=...) keep speeding up past that number?

Distributed systems connection

Threads and machines pose the same question in different units: should the workers share state, or send messages? Threads share memory, which is fast, convenient and fragile. Separate processes, and separate machines, share nothing and communicate over channels, which is slower and safer, and that is how distributed systems work (networking chapter 15). Even the failure rule matches: a fatal fault in one thread takes down all the threads in its process, while one machine failing leaves the others running. And when two machines update the same record, the race you'll meet in the next chapter reappears, with a network in the middle.

Key takeaways

  • A thread is one flow of execution with its own registers and stack; all threads in a process share the heap, globals, code and open files.
  • Threads are cheaper than processes to create and switch, and communicate by simply sharing memory, but they have no isolation: one bad thread can corrupt or kill everyone.
  • Concurrency means overlapping tasks (possible on one core); parallelism means executing at the same instant (needs several cores).
  • CPython's GIL lets only one thread run Python bytecode at a time. CPU-bound Python threads gain nothing; I/O-bound threads gain a lot, because waiting releases the GIL. For CPU-bound work, use processes.
  • The GIL does not make your own code thread-safe. Shared mutable data still needs care.
  • Threads suit waiting-on-the-outside work and modest concurrency; for huge numbers of connections use an event loop.

Check your understanding

Which of these does each thread in a process have for itself?

  1. Its own heap
  2. Its own table of open files
  3. Its own stack and registers
  4. Its own copy of the global variables
A thread needs only its own register set and stack to keep its place. The heap, globals, code and open files belong to the process and are shared, which is exactly why threads can communicate so cheaply, and why they can interfere with each other.

A thread in your process hits a fatal memory fault (a segmentation fault in a C library). What happens?

  1. The whole process dies, including every other thread
  2. Only that thread dies; the others continue
  3. The kernel restarts the thread automatically
  4. Nothing, because each thread has isolated memory
Threads share one address space and have no isolation from each other, so a fatal fault is a fault of the process. (An ordinary Python exception is different: it ends only the thread it occurred in.) This is the main reason browsers and many servers use separate processes for isolation.

You run four threads that each do a long pure-Python calculation on a standard CPython build. What do you expect compared with running the four calculations one after another?

  1. About four times faster
  2. About two times faster
  3. Much slower, because threads are expensive
  4. About the same, or slightly slower
Only the thread holding the GIL executes Python bytecode, so the threads take turns and no work happens in parallel. Passing the lock around adds a little overhead. Using ProcessPoolExecutor would give real parallelism.

Why do four threads that each wait one second for a network reply finish in about one second in total, even with the GIL?

  1. The GIL is switched off for network programs
  2. A thread releases the GIL while it waits for I/O, so all four waits overlap
  3. Python secretly uses four processes
  4. Network calls take no time
Blocking calls release the GIL, so while one thread waits the others can run or wait too. The waits overlap, which is concurrency without parallelism, and for I/O-bound programs that is all you need.

Which statement about concurrency and parallelism is correct?

  1. They mean the same thing
  2. Parallelism is possible on a single core
  3. Concurrency is possible on a single core; parallelism needs several
  4. Concurrency needs several cores; parallelism needs one
Concurrency is about having several tasks in progress, which a single core can do by switching quickly between them. Parallelism means literally executing at the same instant, so it needs multiple cores.

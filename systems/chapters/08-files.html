Files & File Descriptors

A file is the most important idea in Unix, and it turns out to be much more than "a thing in a folder". Files are how programs read their input, print their output, talk over the network and fill your disk. The small integer a program gets when it opens one, the file descriptor, explains redirection, pipes, sockets and the dreaded "Too many open files" error.

Why this matters

Every server you will ever run is a program holding file descriptors: one for each client connection, one for each log file, one for each database file. The limit on how many it may hold is a hard ceiling on how many clients it can serve. And the story of what happens between write() and the data reaching a disk, which we begin here and finish in chapter 9, decides whether a database loses your data in a crash.

What a file really is

At the lowest level a file is a named sequence of bytes. The operating system doesn't care whether the bytes are text, a photo or a program; the meaning belongs to whoever reads them. Everything else is bookkeeping.

That bookkeeping lives in a structure called an inode (index node). The file system keeps one inode per file, and it records everything about the file except its name: the size, the owner, the permissions, timestamps, and where on the disk its bytes are stored. Each inode has a number, unique within its file system.

The names live somewhere else. A directory is itself a special file whose content is a table mapping names to inode numbers. When you open /home/you/notes/a.txt, the kernel walks the path: look up home in the root directory to get its inode, look up you in that, and so on, until the last name gives the inode of the file.

Analogy: a library

The inode is the catalogue card for a book: it says how big it is, who may borrow it and which shelf it's on. A directory is an index that says "this title is card number 5678". The title is not part of the book itself. Two index entries can point at the same card.

Where it breaks down: a library card names a physical shelf; an inode's block list refers to disk blocks that the file system may allocate, grow and reorganise on its own, and that SSDs shuffle again underneath.

Because names and files are separate, you can have two names for one file. A hard link is simply another directory entry pointing at the same inode. The inode keeps a link count, and the file's data is only freed when the count reaches zero (and no process still has it open). Hard links must stay within one file system. A symbolic link (symlink) is different: it is a tiny file of its own whose content is a path, like a sticky note saying "go look at a.txt". If the target is deleted, the note dangles.

Common misconception

"Deleting a file erases it." rm calls unlink: it removes a name and decrements the link count. If a running program still has the file open, the bytes stay on disk until it closes the file. This is why deleting a huge log file sometimes doesn't free any disk space until the server that is writing to it is restarted.

Permissions

Each inode carries an owner, a group and nine permission bits. ls -l shows them:

$ ls -l
-rw-r--r--  1 you  staff   120 Oct 12 09:30 a.txt
drwxr-xr-x  3 you  staff    96 Oct 12 09:28 photos
-rwxr-xr-x  1 you  staff  8312 Oct 11 17:02 run.sh

Read the first column as four parts. The first character is the type (- file, d directory, l symlink). Then three triplets of r (read), w (write) and x (execute) for the owner, the group and everyone else. So rw-r--r-- means "the owner can read and write; others can only read". People write this in octal: rw-r--r-- is 644 (4 + 2 for owner, 4 for group, 4 for others) and rwxr-xr-x is 755. For a directory, x means "may look things up inside", and w means "may add or remove names".

The kernel checks permissions when a process calls open(), against the identity of the user running that process. After that, the descriptor remembers what you were allowed to do. The superuser (root) bypasses these checks, which is why running servers as root is dangerous.

Opening a file: three levels

When a program calls open("data.txt"), it gets back a small integer: a file descriptor (fd). All later calls (read(fd, …), write(fd, …), close(fd)) use that number. The number is only meaningful inside that process: it's an index into the process's own file-descriptor table, which the kernel keeps for it.

But the table doesn't point straight at the inode. There's a middle layer. Each entry points to an open file description: a kernel object that records how this file was opened (read-only or read-write, append or not) and, crucially, the current offset: where the next read or write will happen. The open file description then points to the inode.

This middle layer explains behaviour that otherwise seems magical:

  • dup(fd) makes a new fd number pointing at the same open file description. Reading 3 bytes through one and 3 through the other gives you bytes 0–2 then 3–5, because they share the offset.
  • Opening the same file twice creates two independent descriptions with independent offsets.
  • fork() (chapter 5) copies the parent's whole fd table. The child's entries point at the same descriptions. So a parent and child writing to an inherited fd share one offset, and their output lands one after the other instead of overwriting each other. This is how shells and servers hand open files and connections to child processes.

Analogy: a bookmark

The open file description is a bookmark in a shared book. dup and fork hand out another handle to the same bookmark, so if one reader advances it, the other finds it moved. A second open() gives you a fresh bookmark at page one.

Where it breaks down: a bookmark only remembers a page. The description also holds the access mode and flags (such as append), and it's the kernel, not the reader, that moves it on every read and write.

stdin, stdout, stderr and redirection

By convention every process starts with three descriptors already open: 0 is standard input (stdin), 1 is standard output (stdout) and 2 is standard error (stderr). print() in Python ends up as a write() to fd 1. In a terminal all three point at your terminal; /dev/ttys002 in our lsof output was exactly this.

Nothing in the program says "print to the screen". It just writes to fd 1, so you can change where fd 1 goes without changing the program. Redirection is only rearranging descriptors. For ./prog > out.txt, the shell does this before running the program: it calls fork(), and in the child it opens out.txt and uses dup2 to make fd 1 point at it, then calls exec to start ./prog. The program inherits the rearranged table and never knows.

  • cmd > file: fd 1 points at the file. cmd 2> err.txt: fd 2 points at err.txt.
  • cmd 2>&1: make fd 2 a copy of whatever fd 1 points at right now. So cmd > f 2>&1 sends both to the file, but cmd 2>&1 > f sends errors to the terminal and only stdout to the file, because fd 2 was copied before fd 1 was changed.
  • a | b: the shell creates a pipe (a kernel buffer with a write end and a read end, each an fd) and points a's fd 1 at the write end and b's fd 0 at the read end.

You'll build exactly this in Lab 1.

"Everything is a file"

The motto means: many different things are used through the same handful of calls (open, read, write, close) and a file descriptor.

  • Regular files on disk.
  • Pipes, as above.
  • Sockets: the connection from networking chapter 7 is a file descriptor. accept() returns a new fd for each client, and you read and write it like a file. A TCP connection's bytes arrive in a kernel buffer, just as file bytes sit in the page cache.
  • Devices under /dev: the terminal, and special ones such as /dev/null (accepts and discards anything; reads as empty), /dev/zero (endless zero bytes) and /dev/urandom (random bytes).
  • Kernel information: on Linux, /proc looks like files but is generated on demand by the kernel (for example /proc/self/fd lists your own descriptors).

This is why ls > /dev/null works: the program writes to an fd and has no idea that the kernel is quietly throwing the bytes away. It's also why one select/epoll/kqueue call (chapter 16) can wait on sockets, pipes and terminals together. (Plain disk files are a special case: they always count as "ready", and epoll refuses them outright.)

A fair caveat

"Everything is a file" is an interface, not a promise that everything behaves like a disk file. You can't seek in a pipe or a socket, a read from a socket can return fewer bytes than you asked for, and some devices need extra calls (ioctl) for their special features.

The open-file limit

Every open descriptor costs the kernel memory, so each process gets a limit on how many it may hold. Check with ulimit -n. The default varies: commonly 1024 on Linux, and often only 256 for a macOS shell. Both are small compared to what a busy server needs.

Remember that every client connection is a file descriptor (networking chapter 12 described servers handling many clients). A server with the default limit of 1024 can hold at most about a thousand connections, minus the fds for its log files, listening socket and so on. The next accept() then fails with the error EMFILE, "Too many open files". Servers handle this by raising the limit, which is a soft limit that an ordinary user may raise up to the hard limit, and by closing descriptors promptly. A descriptor leak (opening files or sockets and forgetting to close them) slowly drives a long-running server to this wall. In Python, with open(...) as f: closes the file for you.

There's also a system-wide limit, and you will meet this one again when you design a server for 10,000 connections.

Three layers of buffering

When you write to a file in Python, the data doesn't travel straight to the disk. It passes through layers, each of which may hold on to it for a while for speed:

LayerWhere it livesWhat pushes data to the next layer
1. User-space bufferYour process's memory (Python's io layer holds writes in a buffer of a few KiB; it is typically sized from the file's block size, often 4 KiB, with 8 KiB as the fallback)f.flush(), f.close(), or the buffer filling up. After this, the kernel has the bytes (write() was called).
2. Kernel page cacheKernel memory (RAM)The kernel writes dirty pages back to the disk later on its own, or immediately when you call fsync.
3. The diskSSD or hard drive (which has its own small cache too)Nothing further; this is where data survives power loss.

The page cache is also what makes reads fast: a file you read recently is likely already in RAM (chapter 2). The catch is on the write side. After f.flush(), your data is safe from your own program crashing, but a power cut could still lose it. Closing the gap between "the kernel has it" and "the disk has it" is the whole subject of the next chapter.

Try it yourself

Try it yourself: inodes, links and descriptors

Everything here is safe. We make a scratch directory in /tmp and only read things elsewhere. Inode numbers and sizes will differ on your machine.

$ cd $(mktemp -d) && echo "abcdefgh" > a.txt
$ ln a.txt b.txt && ln -s a.txt c.txt       # a hard link and a symlink
$ ls -li
8641221 -rw-r--r--  2 you  staff  9 Oct 12 09:30 a.txt
8641221 -rw-r--r--  2 you  staff  9 Oct 12 09:30 b.txt
8641223 lrwxr-xr-x  1 you  staff  5 Oct 12 09:30 c.txt -> a.txt
$ stat a.txt                            # full inode details (Linux prints a different layout)
$ rm a.txt && cat b.txt; cat c.txt
abcdefgh
cat: c.txt: No such file or directory

The first two lines show the same inode number and a link count of 2: one file, two names. After removing a.txt, the hard link b.txt still works, but the symlink c.txt now dangles.

Now see the shared offset with dup, and the separate one from a second open:

$ python3 -c "import os; a=os.open('b.txt',os.O_RDONLY); d=os.dup(a); print(os.read(a,3), os.read(d,3))"
b'abc' b'def'
$ python3 -c "import os; a=os.open('b.txt',os.O_RDONLY); b=os.open('b.txt',os.O_RDONLY); print(os.read(a,3), os.read(b,3))"
b'abc' b'abc'

Finally, look at real descriptors:

$ lsof -p $$ | head -6               # your shell's open files
COMMAND   PID   USER   FD   TYPE DEVICE  SIZE/OFF  NODE NAME
zsh     48211 you    cwd    DIR   1,17      2048  1234 /Users/you
zsh     48211 you      0u   CHR   16,2       0t0   901 /dev/ttys002
zsh     48211 you      1u   CHR   16,2       0t0   901 /dev/ttys002
zsh     48211 you      2u   CHR   16,2       0t0   901 /dev/ttys002
$ ls -l /proc/self/fd                 # Linux only. On macOS try: ls -l /dev/fd/
lrwx------ 1 you you 64 Oct 12 09:31 0 -> /dev/pts/0
lrwx------ 1 you you 64 Oct 12 09:31 1 -> /dev/pts/0
lrwx------ 1 you you 64 Oct 12 09:31 2 -> /dev/pts/0
lr-x------ 1 you you 64 Oct 12 09:31 3 -> /proc/48251/fd
$ ulimit -n
256

Notice that fds 0, 1 and 2 all show the same device: the shared terminal description in our diagram. On Linux, the extra fd 3 is the directory that ls itself is reading; it disappears when ls exits.

Distributed systems connection

Descriptor limits turn directly into capacity limits: a node that proxies thousands of connections needs thousands of fds, and "Too many open files" is one of the most common production failures. A node that quietly leaks descriptors looks healthy for days and then stops accepting connections. And the uniform fd interface is why the same read/write code can deal with local files and network sockets alike, a fact that RPC frameworks and log shippers rely on. The buffering layers are the seed of the next chapter, where the same "is it really saved?" question will reappear for replicated systems too (networking chapter 18).

Key takeaways

  • A file is a sequence of bytes described by an inode. The name is not in the inode; directories map names to inode numbers.
  • A hard link is another name for the same inode; a symlink is a small file holding a path and can dangle.
  • A file descriptor is an index into a per-process table, which points to a kernel open file description (holding the offset and flags), which points to the inode.
  • dup and fork share the open file description, and with it the offset. A second open() gets its own.
  • stdin, stdout and stderr are fds 0, 1 and 2; redirection and pipes just rearrange them.
  • Sockets, pipes and devices use the same fd interface. A per-process limit (ulimit -n) caps how many connections a server can hold.
  • Writes pass through a user-space buffer and the kernel page cache before reaching the disk.

Check your understanding

Where is a file's name stored?

  1. In the file's inode
  2. In the directory that contains it, as an entry mapping the name to an inode number
  3. At the start of the file's data
  4. In the process's file-descriptor table
The inode holds everything but the name. That's why one file can have several names (hard links) and why renaming a file doesn't touch its data.

A program opens log.txt, then calls dup() on the fd to get a second number. It reads 10 bytes through the first and then 10 bytes through the second. What does it get?

  1. The same first 10 bytes twice
  2. An error, because a file can't have two descriptors
  3. Bytes 0–9 twice, but only if the file is small
  4. Bytes 0–9, then bytes 10–19, because both descriptors share one open file description and its offset
dup makes a new fd number for the same open file description, not a new description. A second open() of the same file would give the same first 10 bytes twice, since it has an independent offset.

What is the difference between cmd > f 2>&1 and cmd 2>&1 > f?

  1. In the first, both stdout and stderr go to the file. In the second, stderr goes to wherever stdout pointed before the redirect (the terminal) and only stdout goes to the file
  2. There is no difference
  3. The first discards stderr
  4. The second is invalid syntax
Redirections are applied left to right, each rearranging the fd table. 2>&1 copies whatever fd 1 points at at that moment.

A server's log shows "Too many open files" while handling traffic, though CPU and memory are fine. What's the most likely cause?

  1. The disk is full
  2. The network card is broken
  3. The process has hit its limit on open file descriptors (each connection counts), possibly because of a leak
  4. The scheduler is overloaded
Sockets are file descriptors. When the process reaches its ulimit -n limit, open and accept fail with EMFILE. Check the limit and look for descriptors that are never closed.

You delete a 20 GB log file with rm, but df shows no free space regained. The server writing to it is still running. Why?

  1. rm only works on small files
  2. rm removed the name, but the server still holds the file open, so the inode and its blocks stay until it closes the file
  3. The page cache has to be flushed first
  4. The file was a symlink
The disk space is freed only when the link count is zero and no process has the file open. Restarting the server (or having it reopen its log) releases the space.

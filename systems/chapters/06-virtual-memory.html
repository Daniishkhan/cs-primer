Virtual Memory

Every program you run believes it owns a huge, private, perfectly tidy block of memory. None of that is true: the addresses are fiction, and the real memory is shared, scattered and sometimes not even there. This chapter explains the translation trick behind the illusion, and how it gives us protection, cheap fork, memory-mapped files, swapping, and the occasional out-of-memory kill.

Why this matters

"Memory" is the resource that most often decides whether a service stays up. Virtual memory explains why the memory that processes have asked for can add up to more than your RAM and everything still runs, why ps shows two different memory numbers, why a container is mysteriously killed with exit code 137, why a database that forks to take a snapshot can suddenly need double the RAM, and why a machine that starts swapping becomes unusably slow rather than just a bit slower. It is the second of the "three illusions" from chapter 0: you have memory to yourself. Here we see how it is made, and how it leaks.

The problem: many programs, one RAM

Suppose we skip all cleverness: when you start a program, the OS loads it into some free stretch of physical RAM, and the program uses the real addresses directly. Three things go wrong.

  1. No protection. Nothing stops one program from reading or overwriting another's bytes, or the kernel's. One stray pointer can take down the machine.
  2. Fixed addresses. A program compiled to expect its data at address 5,000 breaks if another program is already there. Every program would have to be built knowing exactly where it will land.
  3. Fragmentation. Programs start and stop, leaving free space in awkward gaps. A new program needs one contiguous block, so it may fail to load even though plenty of memory is free in total.

The fix is a layer of indirection, the oldest trick in computer science: don't let programs use real addresses. Give each process its own made-up set of addresses, and have the hardware translate every one of them to a real location as the program runs.

Virtual and physical addresses

A virtual address is what a program sees: the number in a pointer, in a stack frame, in the program counter. A physical address is the actual location in the RAM chips. Every memory access made by user code, every load, store and instruction fetch, uses a virtual address, and the CPU's memory management unit (MMU) translates it to a physical one in hardware before the access reaches RAM. The kernel controls the translations; the program never sees a physical address.

Analogy: hotel room numbers

Every guest's key card says "Room 1", "Room 2" and "Room 3". Two different guests both have a "Room 1", and they never collide, because the front desk keeps a book translating each guest's room numbers into real rooms: guest A's Room 1 is 412, guest B's Room 1 is 907. A guest can't open a door they have no entry for. Rooms can be moved around, or kept in storage until needed, without the guest noticing, as long as the book is updated.

Where it breaks down: a hotel desk is consulted once, at check-in. The MMU is consulted on every single memory access (billions per second), so the "book" has to be backed by a very fast hardware cache (the TLB, below), and the translation is done by silicon, not by a person.

Pages, frames and page tables

Translating each individual byte address separately would need a table as large as memory itself. Instead, memory is divided into fixed-size blocks, and whole blocks are mapped at a time. A block of virtual memory is a page; a block of physical memory is a frame; they are the same size. The usual size is 4 KiB (4,096 bytes). Apple Silicon Macs use 16 KiB pages, and some other systems use 64 KiB.

An address then splits into two parts. With 4 KiB pages, the low 12 bits (212 = 4,096) are the offset: which byte inside the page. The remaining high bits are the page number. Only the page number gets translated. The offset is copied across unchanged, because the page lands in a frame of the same size.

The kernel keeps, for each process, a page table: for every virtual page, an entry saying where it lives (which frame, or "not in RAM") plus permission bits: present, writable, executable, user-accessible. This is where protection comes from. A page is simply absent from a process's table unless the kernel mapped it, so the process has no address that reaches another's data. Writing to a read-only code page, or jumping to a data page marked non-executable, triggers a fault. Address 0 is deliberately left unmapped, which is why dereferencing a null pointer crashes immediately instead of corrupting something.

Common misconception

"A pointer's value is a location in RAM." A pointer holds a virtual address. Two different processes can use the very same virtual address and mean different physical memory. (If you print a variable's address in two copies of a program you will often see different numbers, because the OS randomises layouts for security, but even matching numbers would not mean shared memory.) And the same virtual page can move to another frame (or out to disk and back) while your program is running, without the pointer changing at all.

Multi-level tables

A real 64-bit address space is gigantic. A flat page table covering 48-bit addresses with 4 KiB pages would need 236 entries, at 8 bytes each: 512 GiB, per process, mostly describing memory that doesn't exist. Real CPUs use a tree: on x86-64, four levels of tables, each indexed by 9 bits of the address (9 + 9 + 9 + 9 + 12 offset bits = 48). Branches of the tree for unused regions simply aren't allocated, so a small program needs only a few kilobytes of tables. The price: a full lookup, a page-table walk, takes up to four memory reads. That would make every memory access several times slower, unless something remembers recent translations.

The TLB

That something is the TLB (translation lookaside buffer), a small, very fast cache inside the CPU that holds recent page-number-to-frame translations. On each access the hardware checks the TLB first. A hit costs essentially nothing extra. A miss forces the page-table walk, and the result is stored in the TLB (pushing an older entry out). TLBs hold anywhere from dozens to a few thousand entries, yet hit rates are typically very high, because programs show locality (chapter 2): they keep touching the same few pages. Two consequences are worth knowing:

  • When the CPU switches from one process to another, the old process's translations must not be used for the new one. Either the TLB is flushed (the new process starts cold and takes a burst of misses) or its entries are tagged with a process identifier so they can coexist. This is part of the hidden cost of a context switch (chapter 7).
  • The TLB covers only entries × page size of memory. A program that sweeps through a very large random working set misses constantly. This is one reason for huge pages, below.

Page faults and demand paging

The page table can say "this page is valid but not in RAM right now". Touching such a page makes the MMU raise an exception, a page fault, which transfers control into the kernel (chapter 4). The kernel works out why, fixes it if it can, and restarts the instruction that faulted. The program never knows. There are two common kinds:

Minor fault
The data needs no disk read. Examples: the first touch of fresh memory (the kernel supplies a zero-filled frame), or a page that is already in RAM in the page cache and just needs mapping into this process. It costs roughly the order of a microsecond or so.
Major fault
The data must be fetched from disk: a page that was swapped out, or the first read of a file-backed page not yet cached. The process sleeps until the disk delivers. This is tens to thousands of times slower than a minor fault (an SSD read is tens of microseconds or more, a spinning disk milliseconds).

This is the basis of demand paging: the kernel is lazy. When you start a program, it doesn't read the whole executable into RAM. It maps the file's pages into the address space and loads each one only when the program first touches it. When a program calls malloc(1 GB), nothing is allocated in RAM; the kernel records "this range is valid" and supplies frames one page at a time as the program writes to them. Memory that is requested but never used costs nothing.

Copy-on-write, and why fork is cheap

In chapter 5 we said fork "clones the process, including its memory". Copying gigabytes of RAM every time a shell starts ls would be absurd, especially since the child usually calls exec a moment later and throws the copy away. The trick is copy-on-write (COW):

  1. At fork, the kernel copies only the page table, not the pages. Parent and child now map the same physical frames, and every shared page is marked read-only in both.
  2. As long as both only read, they happily share. Nothing is copied, and no extra RAM is used.
  3. When either one tries to write, the read-only mark triggers a page fault. The kernel allocates a new frame, copies that single page into it, points the writer's table entry at the copy with write permission, and restarts the write.

The consequences are all over real systems. fork + exec is cheap because almost nothing is ever copied. And a process that forks to take a snapshot of its own state, as Redis does for its background save, gets a frozen, consistent view of memory for almost nothing. But every page the parent then modifies must be duplicated, so under heavy writes a snapshot can nearly double memory use (we'll see this in the Redis case study).

mmap: files as memory

The page-table machinery can also map files. The mmap system call tells the kernel: "make this file appear at these virtual addresses". No data is read up front. As the program touches a mapped page, a page fault pulls that part of the file in (from the page cache if possible), and from then on reading the file is just reading memory. Writes to a shared mapping end up in the file. It is how the kernel loads executables and shared libraries (every process using libc maps the same physical frames of it), and some databases and search engines use it to treat a big file as an array.

mmap is also what malloc uses for large allocations, with no file at all (an "anonymous" mapping), as in the experiment below.

Running out: swap, overcommit and the OOM killer

RAM is finite, but the sum of what processes asked for can exceed it. The kernel has three levers.

  1. Evict clean pages. Pages backed by a file (code, mapped files, cached file data) can be dropped and re-read later. This is cheap and happens constantly.
  2. Swap. Pages with no file behind them, such as heap and stack, can be written to a swap file or partition on disk, freeing the frame; touching the page later causes a major fault to bring it back. Swapping is a safety valve, but if the working set (the pages actually in active use) doesn't fit in RAM, the system thrashes: it spends its time swapping pages in and out, and everything crawls. macOS also compresses inactive memory before swapping.
  3. Kill someone. On Linux, if there is truly nothing left to reclaim, the OOM killer (out-of-memory killer) picks a process, using a "badness" score that favours large memory users, and sends it SIGKILL (chapter 5). The victim sees nothing; it just dies, and its parent sees exit status 137.

This ties into overcommit. Because pages are allocated only when first touched, Linux by default lets processes promise more memory than exists: several processes can each malloc a few GB on an 8 GB machine and all succeed, since each only reserves address space. (Linux's default heuristic does refuse a single request that is obviously larger than all of RAM plus swap.) The bill arrives later, as the pages get written to. If everyone cashes in at once, the OOM killer steps in. This is a bet that most programs ask for more than they use. It usually pays off, and it is why memory exhaustion on Linux often looks like "a random process died" rather than "allocation failed". (Linux lets you tune this, vm.overcommit_memory, and containers add per-container limits that trigger the same kill; see chapter 19.) macOS has no OOM killer in the Linux sense: it compresses, then swaps heavily, and in extreme cases the system asks you to force-quit applications.

RSS vs VSZ

The two numbers in the earlier figure are what ps shows. VSZ (virtual size) is the total address space the process has mapped. It includes libraries, mapped files, untouched reservations and swapped-out pages, and it is often huge and not alarming at all. RSS (resident set size) is how much of it is actually in RAM right now. RSS is the better guide to "how much RAM is this using", with two caveats: shared pages (like libc) are counted in every process that has them resident, so summing RSS across processes over-counts, and RSS shrinks if pages get swapped out even though the program still "has" the memory. (On macOS, VSZ looks absurdly large, hundreds of gigabytes, for every process because of how the system reserves shared regions. Ignore it there.)

Go deeper: page sizes and huge pages optional

4 KiB is the traditional page size on x86 and many ARM systems. Apple Silicon uses 16 KiB, and some Linux ARM systems use 64 KiB. Bigger pages mean fewer page-table entries and a TLB that covers more memory (a 64-entry TLB reaches only 256 KiB with 4 KiB pages, but 1 MiB with 16 KiB pages). The cost is more wasted space when a program needs only a little (internal fragmentation) and coarser granularity for copy-on-write and swapping.

x86-64 also supports huge pages of 2 MiB (and 1 GiB). One TLB entry then covers 512 times as much memory (for 2 MiB pages), a big win for programs with large working sets, such as databases and virtual machine hosts. Linux can use them explicitly (hugetlbfs) or automatically with transparent huge pages (THP). The catch is that the kernel needs 2 MiB of physically contiguous memory, and finding or assembling it can cause latency spikes; several databases recommend disabling THP for that reason. Page size is a classic trade-off: fewer, larger units are cheaper to manage but waste more and are clumsier.

$ /usr/bin/time -v python3 -c pass 2>&1 | grep -i fault                # Linux (GNU time)

$ grep -E 'VmSize|VmRSS' /proc/self/status  # Linux only
$ cat /proc/sys/vm/overcommit_memory; cat /proc/$$/oom_score   # Linux: overcommit mode (0 = heuristic) and this shell's OOM score

Now watch demand paging happen. This script asks for 256 MiB, then touches one byte in every page, printing RSS and VSZ each time (it asks ps about itself, so it works on macOS and Linux):

import mmap, os, subprocess

def mem(label):
    out = subprocess.check_output(["ps", "-o", "rss=,vsz=", "-p", str(os.getpid())]).split()
    print(f"{label:<12} RSS={int(out[0]) // 1024:>5} MiB   VSZ={int(out[1]) // 1024:>7} MiB")

mem("start")
m = mmap.mmap(-1, 256 * 1024 * 1024)       # anonymous mapping: reserves address space only
mem("after mmap")
for i in range(0, len(m), mmap.PAGESIZE):  # touch one byte per page
    m[i] = 1
mem("after touch")
$ python3 demand.py
start        RSS=   16 MiB   VSZ= 425065 MiB
after mmap   RSS=   16 MiB   VSZ= 425321 MiB
after touch  RSS=  272 MiB   VSZ= 425321 MiB

(That output is from macOS, where the baseline VSZ is absurdly large; on Linux you would see a few hundred MiB.) VSZ jumped by 256 MiB the moment we mapped; RSS didn't move until we touched the pages. The loop caused roughly 65,536 minor faults on 4 KiB pages (about 16,384 with 16 KiB pages), though Linux may use transparent huge pages and fault far fewer times. Last, a file mapped as memory:

import mmap

with open("/etc/hosts", "rb") as f:
    m = mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ)   # no read() call anywhere
    print(m[:40])                                           # slicing memory reads the file
    print("first 'localhost' at byte", m.find(b"localhost"))

On a Linux VM

Linux lays a process's address space out as a readable file. On your lab machine (no sudo):

$ cat /proc/self/maps | head -8  # regions of this very "cat" process: code, data, heap, stack
$ head -5 /proc/meminfo  # total, free and "available" RAM
$ cat /proc/sys/vm/overcommit_memory  # 0 = heuristic; the kernel lets you reserve more than you have

Each line of maps is a range of virtual addresses with permissions such as r-xp (readable, executable, private). Notice how little of it is "heap" and how much is shared libraries.

Distributed systems connection

Memory limits are how clusters keep tenants apart. A container (chapter 19) gets a memory ceiling; when its processes' pages exceed it, the kernel's OOM killer ends one with SIGKILL and the orchestrator reports "OOMKilled". Capacity planners therefore think in terms of working set and RSS, not VSZ, and scheduling systems such as Borg pack jobs together by their memory demands.

Thrashing is a failure mode that looks like a network failure. A node that is swapping stops answering heartbeats on time, and peers conclude it is dead (networking chapter 16), when really it is just paging. For the same reason, many latency-sensitive services run with swap disabled, preferring a clean crash and restart to a slow limp. And copy-on-write shows up again whenever a store snapshots itself with fork, so "how much RAM do I need?" must include the pages that will be duplicated while the snapshot runs.

Key takeaways

  • Virtual memory gives every process its own private address space, solving protection, fixed addresses and fragmentation with one idea: translate every address.
  • Memory is divided into pages (4 KiB typically, 16 KiB on Apple Silicon); the MMU uses the page table to map a virtual page to a physical frame, and the offset within the page is unchanged.
  • The TLB caches recent translations. A hit is nearly free, a miss costs a page-table walk, and switching processes makes the TLB cold.
  • A page fault is the kernel stepping in. Minor faults need no disk; major faults read from disk and are tens to thousands of times slower. Demand paging means memory costs nothing until it is touched.
  • Copy-on-write makes fork cheap by sharing pages until someone writes. mmap maps files (and anonymous memory) into the address space.
  • Under pressure the kernel evicts clean pages, swaps others and, on Linux, may OOM-kill a process (exit code 137). Overcommit lets a process allocate more than exists.
  • VSZ is mapped address space; RSS is what is in RAM now. Judge memory use by RSS and the working set.

Check your understanding

Two processes both print the address 0x7f0000001000 for a variable. What does that tell you?

  1. They are sharing the same variable
  2. Nothing about sharing: it is a virtual address, and each process's page table may map it to different physical memory
  3. One of them has a bug
  4. They are the same process
Virtual addresses are private to each process. The same number can map to different frames in different processes (as the widget's "New process" button showed), or to the same frame only if the kernel deliberately shares it (for example a library).

What does the TLB store?

  1. The most recently used bytes of RAM
  2. A list of running processes
  3. The contents of the swap file
  4. Recent virtual-page-to-physical-frame translations, so the CPU can skip the page-table walk
The TLB caches translations, not data. (The data caches of chapter 2 hold the bytes.) A TLB hit avoids extra memory reads for the page-table walk on every access.

What is the key difference between a minor and a major page fault?

  1. A major fault needs a disk read; a minor one is resolved from memory (for example by supplying a zeroed frame or mapping a cached page)
  2. A minor fault terminates the process; a major one doesn't
  3. A major fault happens only on Linux
  4. A minor fault happens in the kernel; a major one happens in user mode
Both are handled by the kernel and both are invisible to the program. The difference is the cost: a major fault waits on a disk, often tens to thousands of times longer than a minor one.

Why is fork() fast even for a process using 8 GB of RAM?

  1. Because the child gets only a tiny part of the memory
  2. Because the kernel compresses the memory first
  3. Because only the page tables are copied; pages are shared read-only and copied lazily when one side writes (copy-on-write)
  4. Because the child waits until the parent exits
Copy-on-write postpones the work. The child sees all 8 GB (logically), but physical copying happens one page at a time, and only for pages that are actually modified. If the child calls exec immediately, almost nothing is ever copied.

A process shows VSZ = 12 GB and RSS = 300 MB in ps. What is the most reasonable reading?

  1. It is using 12 GB of RAM and will soon run out
  2. It has 12 GB of address space mapped, but only about 300 MB currently resident in RAM; the rest is untouched, shared, mapped or swapped
  3. It has a memory leak of 12 GB
  4. The two numbers are measuring the same thing in different units
VSZ counts every mapped page whether or not it occupies RAM (reservations, libraries, mapped files, swapped pages). RSS is the part resident now. A large VSZ alone is normal and not a sign of a leak.

On a Linux machine with default settings, a program successfully calls malloc for more memory than is currently free, and later is killed with exit status 137. What most likely happened?

  1. malloc always fails when you ask for too much, so the program must have a bug
  2. The program ran out of disk space
  3. The CPU overheated and the kernel killed it
  4. Overcommit let the allocation succeed because pages are only provided when touched; when the program wrote to enough of them, memory ran out and the OOM killer sent SIGKILL (128 + 9 = 137)
With overcommit, malloc reserves address space, not RAM. The real cost arrives on first touch. If the pages can't be supplied, the OOM killer picks a victim and sends SIGKILL, which the shell or container runtime reports as 137.

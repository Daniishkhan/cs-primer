Queues, Thread Pools & Backpressure

Every server is a queue with workers attached. This chapter shows how to build that safely: a bounded queue, a fixed pool of workers, and a deliberate answer to "what happens when work arrives faster than we can do it?". You'll also meet two small formulas, Little's law and the utilisation curve, that explain why systems fall over so suddenly.

Why this matters

Most production outages that start with "traffic went up" are queueing failures. Nothing is broken: the machine is just asked for more than it can do, and what happens next is decided by one design choice, namely what you do with the extra work. Put it in an unbounded queue and the latency climbs until the clients give up and then memory runs out. Reject it early and the service stays healthy for the requests it accepts. Senior engineers reach for the queue, the pool size and the bound before anything else, and by the end of this chapter you'll know why.

Producer and consumer

In chapter 12 we used locks and condition variables so that one thread could wait politely for another to produce something. The most common use of that machinery is the producer-consumer pattern. Some threads (producers) create work: incoming requests, log lines, files to process. Other threads (consumers, or workers) take work and do it. Between them sits a queue: a first-in, first-out line of items waiting.

The queue does three jobs. It decouples the two sides so they don't have to run at the same speed. It absorbs bursts, so a short spike of 100 requests doesn't mean 100 threads. And, if it has a size limit, it creates backpressure: when the consumers can't keep up, the queue fills and the producers are slowed down or told "no".

Python's standard library has this ready made: queue.Queue. It is thread-safe (it uses a lock and condition variables internally) and takes a maxsize. When the queue is full, put() blocks until a consumer makes room. Here's a fast producer and a slow consumer:

import queue
import threading
import time

q = queue.Queue(maxsize=3)           # bounded: put() blocks when 3 items are waiting
DONE = object()

def producer():
    for i in range(8):
        q.put(i)                     # blocks if the queue is full: that is backpressure
        print(f"produced {i}   (queue size ~{q.qsize()})")
    q.put(DONE)

def consumer():
    while True:
        item = q.get()
        if item is DONE:
            break
        time.sleep(0.2)              # slow consumer
        print(f"    consumed {item}")

threading.Thread(target=producer).start()
c = threading.Thread(target=consumer); c.start(); c.join()
$ python3 bounded_queue.py

The producer raced ahead for the first few items, then hit the bound and from then on could only produce one item each time the consumer finished one. The speed of the whole pipeline is now the speed of the slowest stage, and the memory used by the queue can never exceed three items. (The exact interleaving of lines will differ from run to run, and qsize() is only approximate because other threads may change the queue the instant after you read it.)

Common misconception

"A queue makes the system faster." A queue never increases how much work gets done per second; only more or faster workers do that. A queue only smooths bursts: it lets the average rate be what matters instead of the peak. If work arrives faster than workers can finish it on average, the queue just stores the problem until it overflows.

Why not one thread per task?

The simplest design for a server is "start a new thread for every request". It's easy to write and fine at small scale. It has three problems. Every thread costs memory (a stack, which reserves address space whether or not it's all used, plus kernel bookkeeping) and creating one takes time. The scheduler (chapter 7) has to juggle all of them, and many threads fighting over a few cores means lots of context switches and cache misses. And worst of all, there is no limit: a spike of 50,000 requests becomes 50,000 threads, which either exhausts memory or makes everything crawl. The design has no backpressure at all.

The thread pool pattern fixes this. Start a fixed number of worker threads once. Requests go into a queue; each worker loops "take a task, run it, repeat". Threads are reused, concurrency is capped, and the queue is the place where overload becomes visible and controllable. In Python it's concurrent.futures.ThreadPoolExecutor:

import time
from concurrent.futures import ThreadPoolExecutor

def fetch(n):
    time.sleep(0.5)                  # pretend this is a 500 ms network call
    return n * n

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(fetch, range(8)))
print(results)
print(f"8 tasks, 4 workers: {time.perf_counter() - start:.1f} s")   # ~1.0 s, not 4.0 s
$ python3 pool.py
[0, 1, 4, 9, 16, 25, 36, 49]
8 tasks, 4 workers: 1.0 s

Eight tasks of 0.5 s each took 1.0 s: four ran at once, then the next four. submit() returns a future, a handle for a result that will exist later; map() is a convenience over it. The with block waits for all work to finish.

The hidden unbounded queue

The pool limits the number of workers, but ThreadPoolExecutor's internal queue of waiting tasks has no size limit, and submit() never blocks. A producer that submits faster than the workers finish will keep growing that queue until memory runs out. To get backpressure you must add it yourself. One common way is a semaphore that counts outstanding tasks:

import threading
import time
from concurrent.futures import ThreadPoolExecutor

class BoundedExecutor:
    """ThreadPoolExecutor whose submit() blocks once too much work is outstanding."""
    def __init__(self, workers, max_waiting):
        self._pool = ThreadPoolExecutor(max_workers=workers)
        self._slots = threading.BoundedSemaphore(workers + max_waiting)

    def submit(self, fn, *args):
        self._slots.acquire()                       # blocks the producer: backpressure
        try:
            fut = self._pool.submit(fn, *args)
        except BaseException:
            self._slots.release()
            raise
        fut.add_done_callback(lambda _: self._slots.release())
        return fut

    def shutdown(self):
        self._pool.shutdown(wait=True)

ex = BoundedExecutor(workers=2, max_waiting=2)
start = time.perf_counter()
for i in range(8):
    ex.submit(time.sleep, 0.3)
    print(f"submitted {i} at {time.perf_counter() - start:.1f} s")
ex.shutdown()
$ python3 bounded_executor.py
submitted 0 at 0.0 s
submitted 1 at 0.0 s
submitted 2 at 0.0 s
submitted 3 at 0.0 s
submitted 4 at 0.3 s
submitted 5 at 0.3 s
submitted 6 at 0.6 s
submitted 7 at 0.6 s

The first four tasks (2 running + 2 waiting) are accepted at once; after that the producer is held back and can only submit as fast as tasks finish. That is backpressure working. In Lab 4 you build this yourself and measure it under load.

How big should the pool be?

Two extremes make it clear. If tasks are CPU-bound (all computation, no waiting) a core can only run one thread at a time, so more threads than cores just adds context switches. Use about as many workers as cores. If tasks are I/O-bound (mostly waiting on a database, disk or network), a waiting thread uses no CPU, so you can have many more threads than cores, enough that the cores always have something to run while others wait.

A rough rule of thumb for the I/O case:

threads ≈ cores × (1 + wait time / compute time)

Example: 8 cores. Each request spends 10 ms computing and 90 ms waiting on a database. Wait/compute is 9, so 8 × (1 + 9) = 80 threads keep all 8 cores busy. A request that is 99% CPU gets 8 × (1 + 0.01) ≈ 8 threads. This is only a starting point, because it assumes the waiting really is independent (the database can serve 80 requests at once) and ignores memory and lock contention. Treat it as a first guess to be confirmed by measuring.

To estimate the ratio, compare wall-clock time with CPU time for one request:

import time

def handle_request():
    sum(i * i for i in range(200_000))      # compute: a few ms of CPU
    time.sleep(0.030)                       # wait: pretend a 30 ms database call

wall0, cpu0 = time.perf_counter(), time.process_time()
for _ in range(20):
    handle_request()
wall = time.perf_counter() - wall0
cpu = time.process_time() - cpu0
wait = wall - cpu
print(f"per request: wall {wall/20*1000:.1f} ms, cpu {cpu/20*1000:.1f} ms, waiting {wait/20*1000:.1f} ms")
print(f"wait/compute = {wait/cpu:.1f}  ->  threads per core ~ {1 + wait/cpu:.1f}")
$ python3 ratio.py
per request: wall 46.2 ms, cpu 12.6 ms, waiting 33.6 ms
wait/compute = 2.7  ->  threads per core ~ 3.7

Python-specific catch

In CPython the GIL lets only one thread execute Python bytecode at a time, so a pool of threads running CPU-heavy Python code doesn't use more than about one core. For CPU-bound work in Python use a ProcessPoolExecutor (one worker process per core). Threads are the right tool for I/O-bound work, where they spend their time waiting and the GIL is released. The default size of ThreadPoolExecutor in Python 3.8 and later is min(32, os.cpu_count() + 4) (from Python 3.13 it counts the CPUs available to the process rather than all CPUs), chosen with I/O-bound tasks in mind.

Also remember that pools nest. Your 80 threads might all open a database connection, but the database may allow only 20. The pool in front of the bottleneck decides the real concurrency; making your own pool bigger than the thing it calls only moves the queue somewhere else.

Little's law

Here is the most useful formula in this whole topic, and it's almost obvious once you see it. Take any stable system where things arrive, stay for a while, and leave: a shop, a server, a queue, a pool. Three numbers describe it:

L
the average number of items inside the system (waiting plus being served)
λ (lambda)
the average arrival rate, items per second (in a stable system, also the departure rate)
W
the average time an item spends inside, from arrival to departure

L = λ × W

That's Little's law. If 10 customers walk in each minute and each stays 6 minutes, then on average there are 60 customers in the shop. It holds for almost any arrival pattern and any service order, because it is just accounting, which is why it is so useful.

Three worked examples with different unknowns:

  • How many requests are in flight? A service gets 200 requests/s and each takes 50 ms in total. L = 200 × 0.05 = 10 requests in flight at any moment. If it ever shows 400 in flight at the same arrival rate, the average time must have risen to 2 s.
  • How big should the connection pool be? 500 queries/s, each holding a database connection for 20 ms: L = 500 × 0.02 = 10 connections busy on average. A pool of exactly 10 would be running at 100% utilisation, so requests would queue for a connection all the time (see the next section); you need headroom, perhaps 15 to 20.
  • How long will a new request wait? A backlog of 3,000 requests, drained at 100 requests/s: W = L / λ = 3,000 / 100 = 30 seconds. Long before the queue is "full", the user's request is already too late to matter.

Little's law is also a handy sanity check. If your monitoring shows throughput, latency and concurrency that don't satisfy L = λW, one of the three measurements is wrong. You'll see it hold in the simulator below.

Utilisation and the cliff

The next idea explains why systems seem fine and then suddenly aren't. Utilisation (written ρ, "rho") is the fraction of capacity in use: arrival rate divided by the rate the workers can serve. A pool that can do 100 requests/s and receives 50 has ρ = 50%. Everyone's intuition says "at 90% utilisation, requests wait a bit longer". The truth is stranger. Requests arrive randomly, so sometimes three come at once while a worker is busy; the more loaded the system, the less chance it has to catch up in between. Waiting time doesn't grow in proportion to load; it grows without limit as load approaches capacity.

Go deeper: the M/M/1 formula, with numbers optional

Take the simplest queue model: one server, random (Poisson) arrivals at rate λ, random (exponentially distributed) service times with average rate μ (so the average service time is 1/μ), and an unlimited queue. This is called M/M/1. If λ < μ, the average time in the system is

W = 1 / (μ − λ)

Let one request take 100 ms on average, so μ = 10 requests/s. Then:

Arrival rate λUtilisation ρW = 1/(μ−λ)vs. the 100 ms service time
5 /s50%0.2 s2×
8 /s80%0.5 s5×
9 /s90%1 s10×
9.5 /s95%2 s20×
9.9 /s99%10 s100×

Going from 50% to 90% load (1.8 times the traffic) multiplied the wait by 5; going from 90% to 99% (only 10% more traffic) multiplied it by 10. In general W = (1/μ) / (1 − ρ). By Little's law the average number inside is L = λW = ρ / (1 − ρ), which is 9 requests at 90%. And the tail is worse than the average: in M/M/1 the 99th-percentile time in system is about 4.6 times the average (ln 100), so at 90% utilisation the p99 is roughly 4.6 seconds.

Real systems differ from this model in two ways that matter. A pool of several workers drawing from one queue does better than the formula (the curve bends up later, which is a strong argument for sharing one queue across workers instead of giving each its own). And service times with more variation than exponential, such as an occasional very slow request, make things worse. The shape of the cliff stays the same, which is why the usual advice is to keep sustained utilisation well below 100%, with the exact target depending on how much latency you can afford. This is the same story as the tail latency we met in networking chapter 13.

Unbounded queues hide overload

The default for most queues in most languages is "unlimited": Python's Queue() with no maxsize, an executor's internal queue, a list you append to. Unlimited sounds friendly. In practice it is the way systems fail slowly and confusingly.

Phase 2 is the dangerous one. By Little's law, a backlog of N items means a wait of N divided by the throughput. A 10,000-item backlog at 100 requests/s is a 100-second wait, though not one thing has failed. The service looks healthy to a monitor that only counts errors. And because waits are long, users and upstream services time out and retry, adding even more load. Chapter 16 of the networking course showed how retries amplify problems, and the case study on retry storms and metastable failures shows how a system can stay down long after the original trigger is gone, simply because it is still working through a backlog of requests nobody wants any more.

Analogy: the kitchen with an infinite ticket rail

In our restaurant, the orders are hung on a ticket rail above the cooks. If the rail can hold unlimited tickets, the waiters never have to say "sorry, we're full". On a busy night the rail fills with tickets, and a dish ordered at 7 pm arrives at 9 pm. Diners walk out, but their tickets are still on the rail, so the cooks keep making meals for empty tables. A rail with space for twenty tickets forces the waiter to say "forty minutes, or try another night", which is unpleasant but honest.

Where it breaks down: a kitchen can see the rail filling and stop taking orders. A program doesn't notice a growing queue unless you measure it and decide in advance what to do.

Backpressure strategies

Backpressure means pushing the consequences of overload back toward the source, instead of letting the middle absorb them. Once a queue is bounded and full, you must decide what to do with the next arrival. There are four basic answers, and the right one depends on who the producer is.

Block the producer

The producer waits until there is room (q.put(item)). Good when the producer is a pipeline stage or a batch job that can safely slow down: nothing is lost. Bad when the "producer" is a stream of web requests, because blocking just moves the queue into the connections and the clients' sockets.

Drop

Throw some work away: the newest item, or the oldest. Good for data where recent beats complete, such as metrics samples or video frames. Dropping the oldest is often better than dropping the newest, since the oldest is the one most likely to be stale already. Always count what you drop.

Reject fast (load shedding)

Answer immediately with "busy" (HTTP 503, or 429 for a rate limit) and let the client decide, ideally with backoff and jitter. A quick no costs almost nothing; a slow timeout ties up resources on both sides. Rejecting early is what keeps the accepted requests fast.

Degrade

Do less work per request when overloaded: serve a cached or approximate answer, skip the recommendations panel, turn off an expensive feature. The user still gets something. Needs to be designed in advance.

In code, the difference between "block" and "reject" is one function name: q.put(item) waits; q.put_nowait(item) raises queue.Full at once (and q.put(item, timeout=0.5) is the middle ground: wait up to half a second, then raise).

Don't work for clients who have left

There is one more trap even with a bounded queue. A request that waited in the queue for 3 seconds may belong to a client that gave up after 1 second. If a worker still does the work, the result goes nowhere: pure wasted capacity, at the very moment capacity is scarce. Under overload this gets self-reinforcing, since the work done for abandoned requests is the reason fresh requests wait too long.

The fix is to attach a deadline to each request when it enters, and have the worker check it before starting. Combined with a small bound and fast rejection:

import queue
import threading
import time

q = queue.Queue(maxsize=5)               # at most 5 requests may wait
counts = {"served": 0, "rejected": 0, "expired": 0}

def worker():
    while True:
        enqueued_at, deadline = q.get()
        if time.monotonic() > deadline:  # the client has already given up: skip the work
            counts["expired"] += 1
        else:
            time.sleep(0.1)              # 100 ms of real work: capacity is 10 requests/s
            counts["served"] += 1
        q.task_done()

threading.Thread(target=worker, daemon=True).start()

for i in range(200):                     # arrivals: 50 per second for 4 s, 5x too fast
    now = time.monotonic()
    try:
        q.put_nowait((now, now + 0.3))   # this client waits at most 300 ms
    except queue.Full:
        counts["rejected"] += 1          # reject fast: an instant "busy" beats a slow timeout
    time.sleep(0.02)

q.join()
print(counts)
$ python3 shed.py
{'served': 49, 'rejected': 122, 'expired': 29}

The worker can do about 10 requests a second, so over 4 seconds it could serve about 40 to 50, and that is what it did. The other 150 or so requests were handled by the policy: most were rejected instantly (cheap, honest), and some that had queued too long were skipped (wasted nothing). Your exact counts will differ because the timing is real. Note the use of time.monotonic(), which is right for measuring durations because it never jumps backwards when the wall clock is adjusted.

Common misconception

"Rejecting requests means we failed." Rejecting is how a healthy system behaves at its limit. A service that accepts everything and answers everything late has not served anyone; one that rejects 20% quickly and answers 80% in 100 ms has served 80% well. The failure is the unplanned version: running out of memory with no control over who gets answered.

Distributed systems connection

Every service in a distributed system is a queue with workers, and services are chained, so queues are chained. Overload in one stage propagates: a slow database makes the app servers' queues grow, which makes the load balancer's connections pile up, which makes users retry. This is why backpressure must travel upstream: when stage C is slow, stage B must slow down or reject, so stage A learns about it. In networks you have already seen the idea in TCP's flow control (networking chapter 8: a receiver that can't keep up advertises a smaller window and the sender is held back). Message queues such as Kafka, and streaming systems in general, carry the same idea across machines, with consumers pulling at their own pace instead of producers pushing without limit. And Little's law lets you reason about capacity across the fleet: concurrent requests in flight = request rate × latency, which is how you size connection pools, thread counts and server counts. The next chapters on event loops (chapter 16) are the other answer to "how can one process handle huge numbers of waiting requests": instead of a pool of threads, a single thread that never blocks. Design Studio 2 asks you to design a log shipper that must never lose a line and never fall over, using exactly the bounded queues and spill-to-disk ideas from this chapter.

Key takeaways

  • A bounded queue between producers and workers decouples their speeds, absorbs bursts and, when full, creates backpressure. It does not add capacity.
  • A thread pool reuses a fixed number of workers and caps concurrency. Beware that ThreadPoolExecutor's own queue is unbounded.
  • Rule of thumb: CPU-bound work wants about one worker per core; I/O-bound work wants roughly cores × (1 + wait/compute). In Python, CPU-bound work needs processes, not threads. Measure to confirm.
  • Little's law: L = λ × W. Any two of items in system, arrival rate and time in system give the third.
  • Waiting time explodes as utilisation nears 100% (in the simplest model W = service time / (1 − ρ)). Keep sustained load well below capacity.
  • Unbounded queues hide overload: latency climbs first, then memory runs out, and the whole backlog is lost.
  • When the queue is full, choose on purpose: block, drop, reject fast or degrade. Rejecting early keeps accepted requests fast.
  • Give queued work a deadline and skip it if the client has already given up.

Check your understanding

A producer calls q.put(item) on a queue.Queue(maxsize=10) that already holds 10 items. What happens?

  1. The oldest item is silently dropped
  2. The producer blocks until a consumer takes an item
  3. A queue.Full exception is raised immediately
  4. The queue grows to 11 items
By default put() blocks, which is backpressure on the producer. put_nowait() (or put(block=False)) is the variant that raises queue.Full. A bounded queue never grows past its limit and never drops items on its own.

A server has 8 cores. Each request does 5 ms of computation and then waits 45 ms for a database. By the rule of thumb, roughly how many worker threads keep the cores busy?

  1. 8
  2. 16
  3. 360
  4. 80
wait/compute = 45/5 = 9, so threads ≈ 8 × (1 + 9) = 80. Eight would leave the cores idle while threads wait; 360 is 8 × 45, which forgets the compute part. It is a first guess; confirm by measuring.

A service handles 300 requests per second and each request spends 0.2 s in the system on average. By Little's law, about how many requests are in the system at a time?

  1. 60
  2. 1,500
  3. 0.0007
  4. 300
L = λ × W = 300 × 0.2 = 60. The other numbers come from dividing or from ignoring one of the quantities.

In the simple M/M/1 model, a server goes from 50% to 95% utilisation. Roughly what happens to the average time in the system?

  1. It about doubles
  2. It grows by about 45%, in step with the load
  3. It grows about tenfold
  4. It stays the same until 100%
W = service time / (1 − ρ): 2× the service time at 50%, 20× at 95%, so ten times worse for a bit less than twice the load. The curve is not linear; that is the cliff.

An overloaded service uses an unbounded queue. What is the most likely sequence of symptoms?

  1. Immediate errors, then slow recovery
  2. Latency rises steadily with no errors, then memory runs out and the process dies
  3. Throughput doubles because the queue absorbs the excess
  4. Nothing visible happens; the queue empties itself during quiet periods, even under sustained overload
With sustained overload the queue only grows. Waiting time (Little's law: backlog divided by throughput) climbs first, which is why it is so deceptive, and finally the memory holding the backlog is exhausted. A queue can only drain if the arrival rate drops below capacity.

A worker dequeues a request that waited 5 s, though the client's timeout is 1 s. What should a well-designed worker do?

  1. Process it anyway, since the work is already queued
  2. Process it twice to make up for the delay
  3. Check the request's deadline, notice it has passed, and skip it
  4. Move it to the back of the queue
Nobody is waiting for the result, so doing the work only steals capacity from requests that still matter. Carrying a deadline with each queued item and checking it at dequeue time avoids that waste.

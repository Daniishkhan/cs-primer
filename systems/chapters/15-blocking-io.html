Blocking vs Non-blocking I/O

A server spends almost all of its life waiting for the network. This chapter looks at what "waiting" really means inside a program, the two ways to do it (go to sleep, or keep asking), and why neither is enough once you have thousands of connections. It sets up the event loop of the next chapter.

Why this matters

Every network program makes the same choice, whether or not the author knows it: when there is nothing to read yet, what does my code do? The answer decides how many clients one machine can serve, how much memory they cost, and what happens when one client is slow. Blocking calls give simple code and need one thread per connection. Non-blocking calls give you control but push the problem of "when should I look again?" onto you. Almost every high-connection server you have heard of (nginx, Node.js, Redis) exists because of that trade-off.

What "blocking" means

Suppose a program asks the kernel for the next bytes on a socket by calling recv(). If the bytes have already arrived, the kernel copies them to the program and the call returns almost immediately. But what if the client is on a slow phone connection and has not sent anything yet?

By default the answer is: the call does not return. The kernel marks the thread as blocked (also called sleeping or waiting), takes it off the CPU and lets the scheduler run some other thread on that core (chapter 7). Later, when data arrives, the network interrupt wakes the kernel, the kernel finds the sleeping thread, makes it runnable again, and recv() finally returns. The same happens with accept() (waiting for a new connection), send() when there is no room, and read() on a pipe or a file. These are all blocking calls, because they block the calling thread until the thing it asked for can happen.

That is the great virtue of blocking I/O: it looks like an ordinary function call. You can write data = sock.recv(1024), then the next line uses data, and the program reads top to bottom. A blocked thread burns no CPU time. What it does cost is memory (its stack, chapter 3) and a bookkeeping entry in the kernel. And, importantly, while it is blocked it can do nothing else. It cannot answer another client, or notice that it should shut down.

Analogy: a waiter assigned to one table

In the restaurant from chapter 0, imagine each waiter (thread) is assigned one table (socket). The table hasn't decided yet, so the waiter stands beside it, doing nothing, until the diners finally say "we're ready to order". That is a blocking recv(). It's easy to understand: the waiter's whole job is one table. The cost is that you need one waiter per table, even for tables that stay quiet all night.

Where it breaks down: a blocked thread isn't really "standing in the way". It is off the CPU entirely, so it doesn't slow other threads down; what it costs is memory and kernel bookkeeping. Also, no waiter is woken up automatically when diners are ready, whereas here the kernel does the waking for you.

Where the waiting happens: socket buffers

Why can the kernel return data to a program that wasn't even running when the packets arrived? Because each socket has two buffers in kernel memory (see networking chapter 8 for how TCP fills them):

  • The receive buffer holds bytes that TCP has received and put in order, but the program hasn't read yet. recv() copies bytes out of it.
  • The send buffer holds bytes the program has written, but TCP hasn't yet sent or had acknowledged. send() copies bytes into it.

Now we can say precisely when a call blocks:

CallBlocks when…Becomes ready when…
recv() / read()the receive buffer is emptyat least one byte arrives, or the peer closes (then it returns zero bytes, meaning end of stream)
send() / write()the send buffer has no free spacethe peer acknowledges data and space frees up
accept()no completed connection is waiting in the listen queuea client finishes the TCP handshake

Common misconception

"send() returning means the other side got my data." It only means the kernel accepted the bytes into the send buffer. They may still be waiting to go out, or be lost on the way. Likewise recv(1024) does not mean "give me exactly 1024 bytes": it returns whatever is there, up to 1024, so even a blocking recv() can hand you half a message. TCP is a byte stream with no message boundaries (networking chapter 8).

Non-blocking mode

Every socket can be switched to a different contract: non-blocking mode. In Python that's sock.setblocking(False). (The C equivalent is the O_NONBLOCK flag on the file descriptor, chapter 8.) Now the kernel never puts the thread to sleep for this socket. If the call can make progress, it does. If not, it fails at once with a special error: EAGAIN, also spelled EWOULDBLOCK (on Linux and macOS these are the same value). The message means "nothing for you right now; try again later". Python turns that error into an exception called BlockingIOError.

You can try this with no network and no ports at all. socket.socketpair() gives you two sockets already connected to each other inside the same process.

import socket

a, b = socket.socketpair()      # two connected sockets, no ports needed
a.setblocking(False)            # switch 'a' to non-blocking mode

try:
    a.recv(1024)                # nothing has been sent yet
except BlockingIOError as e:
    print("recv would block:", e)

b.send(b"hello")
print("after send:", a.recv(1024))

# Fill the send buffer until the kernel says "no more room".
b.setblocking(False)
total = 0
try:
    while True:
        total += b.send(b"x" * 4096)
except BlockingIOError:
    print(f"send buffer full after {total:,} bytes")
recv would block: [Errno 35] Resource temporarily unavailable
after send: b'hello'
send buffer full after 8,192 bytes

Your numbers will differ. On Linux the error number is 11 instead of 35, and a Unix-domain socket pair usually has a much bigger buffer than the 8 KiB macOS gave here. A real TCP socket's buffers are larger again and adjust themselves to the connection. The pattern is what matters: a call that would have slept now raises instead.

The same applies to the other calls. A non-blocking accept() raises BlockingIOError if nobody is waiting. A non-blocking send() may partly succeed: with 100 KB to send and room for 60 KB, it returns 60,000 and you must keep the rest and try again later. (A non-blocking connect() is similar: it starts the handshake and reports "in progress".) This is called a partial write, and we'll handle it properly in the next chapter.

Why not just keep asking?

With non-blocking sockets, the thread is free to do other things. The simplest way to use that freedom is a loop: try each socket, skip the ones that raise BlockingIOError, repeat. This is busy-polling (or spinning). It does work. It is also wasteful, and you can measure how wasteful. The demo below waits one second for data to arrive, once by blocking and once by spinning:

import socket, threading, time

def run(label, busy):
    a, b = socket.socketpair()
    threading.Timer(1.0, lambda: b.send(b"ping")).start()   # data arrives in 1 s
    cpu0, wall0 = time.process_time(), time.perf_counter()
    tries = 0
    if busy:
        a.setblocking(False)
        while True:
            tries += 1
            try:
                a.recv(16)
                break
            except BlockingIOError:
                pass                      # nothing yet: ask again, immediately
    else:
        a.recv(16)                        # sleeps inside the kernel until data arrives
        tries = 1
    cpu, wall = time.process_time() - cpu0, time.perf_counter() - wall0
    print(f"{label:<12} waited {wall:.2f}s wall, {cpu:.2f}s CPU, {tries:,} recv() calls")

run("blocking", busy=False)
run("busy-poll", busy=True)
blocking     waited 1.00s wall, 0.00s CPU, 1 recv() calls
busy-poll    waited 1.00s wall, 1.00s CPU, 2,097,832 recv() calls

Same one-second wait. The blocking version used essentially no CPU and made one system call. The spinning version kept a core at 100% and made about two million system calls, each one a trip into the kernel (chapter 4) that returned "nothing yet". With 10,000 sockets it would be far worse, since every pass has to ask about every socket. You could add time.sleep(0.01) between passes to cool it down, but now every event is noticed up to 10 ms late, which makes latency worse while still wasting wakeups.

So we have two bad extremes. Blocking sleeps efficiently but can wait on only one thing. Polling can watch many things but burns CPU. What we want is: "put me to sleep until any one of these 10,000 sockets is ready, and tell me which." The kernel is the only party that knows when data arrives, so that has to be a system call too. That call exists in several versions (select, poll, epoll, kqueue), and it is the heart of the next chapter.

The cost of one thread per connection

Before moving on, let's be fair to the left side of that picture, because it is the model most programmers meet first and it is perfectly good in many places. In the thread-per-connection model, an accept() loop hands each new client to a new thread (or to a thread from a pool, chapter 14), and that thread runs plain blocking code from start to finish. Old Apache configurations, many Java application servers, and MySQL's default connection handling all work roughly like this.

The costs grow with the number of connections, not with the amount of work:

  • Memory. Every thread has its own stack (chapter 10). Systems often reserve a large address range for it (Linux commonly 8 MB of virtual space; macOS 512 KB for non-main threads), though only the pages actually touched become real RAM (chapter 6). Even at tens of kilobytes of real memory each, 10,000 threads means hundreds of megabytes spent on connections that are mostly saying nothing.
  • Scheduling. Each wake-up is a context switch of microseconds (chapter 7), and the kernel's scheduler has more runnable and sleeping entities to track. Threads also lose their warm CPU caches when switched out (chapter 2).
  • Shared state needs locks. Threads share memory, so a table of "which user is on which connection" needs a lock around it (chapter 11, chapter 12).
  • Limits. Operating systems cap threads per process and per machine, and each connection also needs a file descriptor (chapter 8).

The common fix for runaway thread counts is a bounded thread pool with a queue in front (chapter 14). That protects memory, but it exposes a sharper problem: if the pool has 200 threads and 200 clients connect and then go silent, all 200 threads are blocked on idle clients and the 201st client is not served even though the machine is doing nothing. (A deliberate attack of exactly this shape is called a slow-client or "slowloris" attack.) With blocking I/O, the number of connections you can hold and the number of threads you pay for are tied together. The event loop breaks that tie.

A quick feel for the numbers: starting 2,000 threads that immediately block is cheap in absolute terms.

started 2000 blocked threads in 0.09 s
active threads: 2001

So thread-per-connection is not "broken" at a few thousand connections on a modern machine. The point is that its cost grows with idle connections, and at 100,000 or more the other design is clearly better. That is the situation of Studio 1.

Disk I/O is different

You might expect to put file reads into the same "wait for many things" system as sockets. Mostly, you can't. A regular file is always considered ready by select, poll and kqueue; epoll refuses to register it at all. There's no equivalent of "the receive buffer is empty, come back later", because the kernel doesn't know in advance whether your read will be served from the page cache in microseconds or need a trip to the SSD (chapter 8, chapter 9). So read() on a file simply goes ahead, and if the data is not in RAM, the thread blocks while the disk works, even if the file descriptor is in non-blocking mode.

That means a single-threaded event loop that reads files directly will freeze whenever the disk is slow. The usual remedy is the one you already know from chapter 14: hand file work to a thread pool and let the loop continue. Node.js does this through its libuv library, and Python's asyncio offers run_in_executor and asyncio.to_thread (next chapters). The newer alternative on Linux is io_uring (since kernel 5.1): you place requests in a queue shared with the kernel, the kernel does the work, including real file I/O, and you collect completions later. It treats disk and network the same way. It's powerful, still evolving, and not available on macOS, so most systems today still use threads for disk.

Common misconception

"Setting a file to non-blocking mode makes disk reads asynchronous." It does not. The flag is about whether the kernel should sleep waiting for data that hasn't arrived (sockets, pipes, terminals). A disk read that misses the page cache still blocks the thread.

The last two lines are typical values, not promises: your machine's will differ (the first shows macOS, the second Linux, and only one applies to you). Try making a thread demo as well:

import threading
import time

stop = threading.Event()
start = time.perf_counter()
threads = [threading.Thread(target=stop.wait) for _ in range(2000)]
for t in threads:
    t.start()                       # each thread immediately blocks in stop.wait()
print(f"started {len(threads)} blocked threads in {time.perf_counter() - start:.2f} s")
print("active threads:", threading.active_count())
stop.set()                          # wake them all so the program can exit
for t in threads:
    t.join()

On Linux you can watch the kernel's view of a process's blocked state with ps -o pid,stat,wchan:20,cmd -p PID (a state of S with a wait channel such as sk_wait_data means "sleeping in a socket wait"). macOS's ps shows S for sleeping too, but no wait channel you can interpret.

Distributed systems connection

A blocking call is the place where a remote failure becomes your thread's problem. If the peer machine crashes or the network drops silently, a blocking recv() with no timeout can wait for a very long time, because no packet ever arrives to wake it (networking chapter 16). Every call to another machine needs a timeout, and in a thread-per-connection server a few stuck calls can use up the whole pool. That is how one slow dependency spreads into an outage across a system: the waiting threads are the contagion. The remedy, deadlines and bounded queues, appears again in chapter 14 and later chapters.

Key takeaways

  • A blocking call puts the thread to sleep until the kernel can complete it; the scheduler runs other threads meanwhile, and the sleeping thread uses no CPU.
  • Each socket has a kernel receive buffer and send buffer. recv() blocks when the first is empty; send() blocks when the second is full.
  • Non-blocking mode (setblocking(False)) turns "would sleep" into an immediate EAGAIN/EWOULDBLOCK error (BlockingIOError in Python). Partial writes are normal.
  • Busy-polling many sockets burns CPU for nothing. What we need is one call that sleeps until any of many sockets is ready.
  • Thread-per-connection is simple but its cost (stacks, scheduling, locks, limits) grows with idle connections, and it ties connection count to thread count.
  • Regular files are always "ready", so disk work goes to a thread pool (or io_uring on Linux), not into the readiness system.

Check your understanding

A thread calls recv() on a blocking socket and no data has arrived. What happens?

  1. The call returns an empty bytes object immediately
  2. The thread spins in a loop inside the kernel until data comes
  3. The kernel puts the thread to sleep and runs other threads on the core until data arrives
  4. The program crashes with an error
A blocked thread is taken off the CPU and woken when the socket becomes readable. An empty result from recv() would mean the peer closed the connection (end of stream), which is something different.

In Python, you call sock.recv(1024) on a non-blocking socket with an empty receive buffer. What do you get?

  1. A BlockingIOError (the C-level error is EAGAIN / EWOULDBLOCK)
  2. 1024 zero bytes
  3. The call waits up to a short default timeout, then returns
  4. An empty bytes object
Non-blocking calls never sleep. "Not ready" is reported as an error you are expected to handle and retry later. Empty bytes means the other side closed the connection, so confusing the two is a classic bug.

Why is busy-polling many non-blocking sockets in a tight loop a poor design?

  1. Non-blocking sockets lose data when polled too often
  2. It is impossible to poll more than one socket
  3. The kernel forbids calling recv() repeatedly
  4. It keeps a core at 100% making system calls that mostly return "nothing yet", and adding sleeps instead makes events be noticed late
Polling works, but it trades CPU for latency. The better tool is a single system call that sleeps until any registered socket is ready, which is what select, poll, epoll and kqueue do.

A server uses a pool of 100 threads with blocking reads. 100 clients connect and then stay silent. What happens to the 101st client?

  1. It is served normally because silent threads don't count
  2. It waits (or is refused), even though the machine is nearly idle, because every thread is blocked on an idle client
  3. The kernel automatically creates thread number 101
  4. The first client's thread is cancelled
With blocking I/O, a thread is tied up for as long as its connection is open and quiet. This is why idle or slow connections can exhaust a thread pool without using any CPU.

Why can't a regular file be handled like a socket in an event loop?

  1. Files are always write-protected
  2. Files cannot have file descriptors
  3. select/poll/kqueue always report regular files as ready (and epoll rejects them), so a read can still block on the disk; event loops send disk work to a thread pool
  4. Disk I/O is always instantaneous
The kernel can't tell in advance whether your file read will hit the page cache or need the SSD, so readiness notification doesn't help. Setting O_NONBLOCK on a regular file does not change that. io_uring is a Linux interface that addresses it differently.

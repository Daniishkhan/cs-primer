Containers & Virtual Machines

A single machine today runs dozens of programs from different teams, each wanting its own libraries, its own network port and its own share of the CPU. Containers and virtual machines are the two ways we give each of them the feeling of a machine of its own. Underneath, it's the same kernel ideas you already know, applied once more.

Why this matters

Almost every service you will ever deploy runs in a container, usually scheduled by Kubernetes, often inside a virtual machine rented from a cloud provider. When a container is "killed for no reason", when a process ignores docker stop, when an app thinks it has 64 GB but dies at 512 MB, or when someone asks "is a container secure enough?", the answers come straight from the earlier chapters: processes, signals, virtual memory and the kernel. Knowing what a container really is removes the mystery.

Why isolate at all?

Buying one physical server per program is wasteful: most programs use a tiny fraction of a modern machine. So we pack many workloads onto each machine. That creates two problems.

  • Interference. One program with a memory leak or a runaway loop shouldn't starve its neighbours (the "busy neighbour" leak from the CPU illusion in chapter 0). One program's bug or break-in shouldn't expose another's data.
  • Packaging. Program A needs Python 3.8 and an old OpenSSL; program B needs Python 3.12 and a new one. "It works on my machine" happens because each machine has a slightly different pile of installed libraries. We want to ship a program together with everything it needs and have it behave the same everywhere.

The operating system already isolates processes from each other (chapter 5, chapter 6). But plain processes still share one file system, one list of users, one network stack and one process list. Containers and VMs raise the wall so that each workload also gets its own file system, its own network and its own view of the world. They differ in where they draw the wall.

Virtual machines: a pretend computer

A virtual machine (VM) is a complete computer simulated by software. It has a virtual CPU, virtual RAM, a virtual disk and a virtual network card. Inside it you install an ordinary operating system, which boots, starts its own kernel and has no idea it isn't alone on real hardware.

The program that creates and runs VMs is a hypervisor. It's a small, privileged layer that hands out slices of the real CPU, RAM and devices, and keeps the VMs apart. There are two common arrangements:

  • Type 1 hypervisor ("bare metal"): runs directly on the hardware, with no ordinary OS underneath. Examples: VMware ESXi, Xen, Microsoft Hyper-V. KVM is a slightly special case: it turns the Linux kernel itself into a hypervisor. Cloud data centres are built on this type.
  • Type 2 hypervisor ("hosted"): an ordinary application running on a normal OS, which in turn runs VMs. Examples: VirtualBox, VMware Workstation, Parallels. Convenient on a laptop.

How can a guest kernel run without breaking the host? Early virtualisation had to emulate or rewrite sensitive instructions in software, which was slow. Modern CPUs have hardware virtualisation support (Intel VT-x, AMD-V, and the equivalent on ARM). The CPU gets an extra privilege level for the hypervisor and a "guest mode" in which the guest kernel believes it is in charge, while the hardware traps anything that would touch real devices or other VMs' memory and hands it to the hypervisor. A guest's "physical" memory is itself a mapping managed by the hypervisor, one more level of the page-table translation you met in chapter 6. Because the guest runs most instructions directly on the real CPU, the slowdown is usually modest.

The important consequence: every VM runs its own kernel. That is the source of both its strength and its cost.

Analogy: separate kitchens in one building

A VM is like giving each restaurant its own kitchen with its own head chef, in the same building. They share the building's power and plumbing (the hardware, mediated by the building manager, the hypervisor). A fire in one kitchen won't reach the others, but each kitchen costs a lot of floor space.

Where it breaks down: the building manager doesn't cook. The hypervisor mostly gets out of the way, and the guests' cooks run directly on the real stoves (the real CPU cores) most of the time.

Containers: one kernel, many views

A container is not a small VM. It is an ordinary process (or group of processes) running on the host's kernel, wrapped in two Linux features that limit what it can see and what it can use. There is no guest kernel at all. This is why containers start in a fraction of a second: starting one is little more than starting a process with some restrictions.

What a container limits: namespaces

A Linux namespace gives a process its own private copy of some global system resource, so it sees a different "world" from the host. The kernel keeps one real set of data, and each namespace is a filtered window onto it. The main kinds:

NamespaceWhat the process gets its own view of
pidThe process list. Inside, the first process is PID 1 and sees only its own descendants.
netNetwork interfaces, IP addresses, routing table, ports. Two containers can both listen on port 80.
mntThe file-system mount points: its own root directory / (see images below).
utsThe hostname.
ipcShared-memory segments and message queues.
userUser and group IDs. "root" inside can map to an unprivileged user outside.

What a container limits: cgroups

Namespaces control what a process can see. Control groups (cgroups) control what it can use. The kernel puts a group of processes into a cgroup and enforces budgets on the group as a whole. The two you meet most:

  • Memory limit. If the group's memory use hits its limit and the kernel can't reclaim enough (cache can be dropped, but a program's own heap can't be), the kernel's OOM killer kills a process inside that container, even though the host has plenty of RAM free. If the victim is the container's main process, the container exits with status 137 (128 + signal 9, SIGKILL; see chapter 5). The kernel doesn't send a polite warning; the program can't catch SIGKILL or clean up.
  • CPU limit. A CPU limit is a budget of CPU time, for example "1.5 cores' worth per scheduling period". When the group uses up its budget, its threads are simply throttled: stopped until the next period. Nothing is killed, but latency spikes appear because requests stall mid-flight, even when the host's cores are idle. This is the scheduler of chapter 7 being told "this group has had its share".

The asymmetry is worth remembering: memory is a hard wall (dies), CPU is a speed limit (slows).

Common misconception

"A container is a lightweight VM, so it has its own kernel." It doesn't. Run uname -r inside a container and you get the host's kernel version. A container is a normal process with a restricted view and a resource budget; there is nothing in it that boots.

Images: layered file systems

A container needs its own root file system with its libraries and tools, so that app A can have Python 3.8 and app B Python 3.12 on the same host. That file system comes from an image: a packaged, read-only snapshot of a directory tree plus some metadata (which command to run, which environment variables to set).

Images are built in layers. Each step in a build (start from a base such as Alpine or Ubuntu, install packages, copy in your code) produces a layer containing only the files that step added or changed. At run time the kernel stacks the layers into a single view using a union file system such as overlayfs, and puts a thin writable layer on top. Two consequences matter in practice:

  • Sharing. Ten containers from the same image share one copy of the read-only layers on disk, and layers common to different images are stored once. This is why pulling a new version of an image often downloads only a few layers.
  • Copy-on-write. If a container modifies a file from a lower layer, the file is first copied into the writable top layer. Writes land there and are thrown away when the container is removed. Anything that must survive (a database's data) belongs on a mounted volume, not in the container's own file system. The same lesson as chapter 9: know where your data really lives.

What Docker actually is

Docker is not a new kind of isolation. It's a friendly tool-chain around the kernel features above: a standard way to build images from a recipe (a Dockerfile), to distribute them through a registry, and to start a container with one command. When you run docker run, a background service (the Docker daemon, which hands the work to lower-level runtimes such as containerd and runc) does roughly this: unpack the image layers into a root file system, create a fresh set of namespaces, place the process in a cgroup with the requested limits, switch its root directory to the image's file system, and start your command as PID 1 of the new PID namespace. That's the whole trick. The image and runtime formats are now open standards (OCI), so many tools besides Docker can run the same images.

Containers on a Mac or Windows laptop

Namespaces and cgroups are Linux kernel features. macOS and Windows kernels don't have them, so tools such as Docker Desktop (and similar ones: Colima, Rancher Desktop, Podman Machine) quietly start a small Linux virtual machine and run your containers inside it. On Windows, WSL 2 works the same way: a real Linux kernel in a lightweight VM. So on a Mac your "container" is a process in a Linux VM on a hypervisor. That's also why file sharing with the Mac and performance can differ from a real Linux server, and why uname -r inside a container on a Mac shows a Linux kernel, not macOS's.

Orchestration: someone has to decide where things run

One container on one machine is easy. A real service is hundreds of containers across many machines, and machines die. An orchestrator takes a description of what you want ("run 20 copies of this image, each with 1 GB of memory") and keeps it true. Kubernetes is the best-known: its scheduler picks a machine with enough free CPU and memory for each container group (a pod), an agent on every machine starts them, and if a machine fails the pods are started again elsewhere. The memory and CPU numbers you declare are exactly the cgroup limits above, and also the sizes the scheduler uses to pack machines. Kubernetes grew out of ideas from Google's internal system, Borg. The case study Borg: Containers at Google Scale covers how and why this packing works.

Orchestration is also a distributed-systems problem (networking ch. 15): the scheduler must stay correct when machines vanish, and starting a replacement is safe only if programs handle being killed and restarted at any moment.

Security: a shared kernel is a thinner wall

All containers on a host share one kernel, which has millions of lines of code and hundreds of system calls (chapter 4). A bug in the kernel that lets a process escalate its privileges can let a program in a container reach the host, and through it every other container. A VM's guest has to get past the hypervisor, which exposes a much smaller interface, so the wall is generally stronger.

Hardening exists: dropping unneeded privileges, restricting which system calls a container may make (seccomp), user namespaces so container "root" isn't real root, and read-only file systems. But for running untrusted code from different customers, the common answer is to put a VM boundary around it. Some systems use lightweight VMs to get both: Firecracker, open-sourced by Amazon, is a minimal virtual machine monitor built on KVM that boots a small VM very quickly, and is used for services such as AWS Lambda. You still get a separate kernel per workload, with less weight than a traditional VM.

Running programs well inside containers

PID 1 and signals

Inside a PID namespace your command becomes PID 1, and PID 1 is special on Linux. Recall from chapter 5 that a signal with no handler normally triggers a default action such as "terminate". For PID 1 the kernel does not apply those defaults: a SIGTERM that the program hasn't installed a handler for is ignored. So docker stop (which sends SIGTERM, waits about ten seconds by default, then sends SIGKILL) seems to hang for ten seconds, and then your app is killed without a clean shutdown: no flushed buffers, no finished requests. Two more PID 1 duties from chapter 5: it must wait() for orphaned child processes or they pile up as zombies.

The fixes: have your program handle SIGTERM and shut down gracefully; run a tiny init process as PID 1 (Docker's --init flag does this) that forwards signals and reaps zombies; and start your program directly rather than through a shell wrapper that swallows signals (in a Dockerfile, prefer the exec form ["python3", "app.py"]).

The memory limit versus what the app thinks it has

Chapter 6 described the illusion that a process has a huge private memory. In a container the illusion gets a second layer: the cgroup limit sits below what the program can see. Tools like free and the file /proc/meminfo often still report the host's total memory, so a program that sizes its caches as "a quarter of RAM" on a 64 GB host may try to use 16 GB inside a 512 MB container, and get OOM-killed with no warning. Modern runtimes such as recent JVMs read the cgroup limit and adapt; many programs don't. So set explicit heap or cache sizes, leave headroom below the limit (the kernel also counts file cache and thread stacks), and similarly remember that a program that counts CPUs to size its thread pool sees the host's cores, not its CPU budget (chapter 14's pool sizing goes wrong, and throttling follows).

Try it yourself

Try it yourself: look at the walls

Every process on Linux already lives in namespaces and a cgroup; containers just use different ones. These commands only read information, and need no sudo. The first two work on Linux or WSL. macOS has no /proc and no namespaces (that's the point of the section above). The last needs Docker installed, so skip it if you don't have it.

$ ls -l /proc/self/ns          # the namespaces this process belongs to
lrwxrwxrwx 1 you you 0 Oct 12 10:02 cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx 1 you you 0 Oct 12 10:02 ipc -> 'ipc:[4026531839]'
lrwxrwxrwx 1 you you 0 Oct 12 10:02 mnt -> 'mnt:[4026531841]'
lrwxrwxrwx 1 you you 0 Oct 12 10:02 net -> 'net:[4026531840]'
lrwxrwxrwx 1 you you 0 Oct 12 10:02 pid -> 'pid:[4026531836]'
lrwxrwxrwx 1 you you 0 Oct 12 10:02 user -> 'user:[4026531837]'
lrwxrwxrwx 1 you you 0 Oct 12 10:02 uts -> 'uts:[4026531838]'
$ cat /proc/self/cgroup           # which cgroup you are in
0::/user.slice/user-1000.slice/session-3.scope

Each number identifies one namespace. Two processes with the same number for pid share a process list. A process in a container shows different numbers. Inside a container, /proc/self/cgroup usually shows just 0::/, because the container sees only its own part of the cgroup tree. Your numbers and paths will differ, and a newer kernel lists a few extra lines (such as time and pid_for_children).

$ docker run --rm alpine ps        # needs Docker; runs ps inside a fresh container
PID   USER     TIME  COMMAND
    1 root      0:00 ps
$ docker run --rm alpine uname -r  # needs Docker; prints the kernel version
6.x.x-linuxkit

The container's ps is itself PID 1, and it sees no other process on your machine: that's the PID namespace. The kernel version printed is the host's kernel (on a Mac, the Linux VM's kernel). The exact version will differ.

On a Linux VM

Build a container's isolation by hand on your lab machine. Everything vanishes when you exit:

$ sudo unshare --pid --fork --mount-proc bash  # a new PID namespace
# ps aux  ## bash is PID 1, and nothing else from the host is visible
# exit

The full walkthrough, including a private hostname and comparing with Docker, is in the toolbox entry for unshare.

Distributed systems connection

Containers made "a machine" into a disposable unit: start a copy, kill a copy, move a copy. Autoscaling, rolling deploys and the self-healing of orchestrators all depend on it, and so does the networking course's idea of treating servers as cattle that can fail at any moment. In return, your program must tolerate being killed with SIGTERM or SIGKILL at any time, must keep important state outside the container, and must retry connections, as in networking chapter 16.

Key takeaways

  • A VM virtualises hardware: a hypervisor runs several guests, each with its own kernel. Hardware support in the CPU keeps it fast.
  • A container is an ordinary process on the host kernel, limited in what it can see (namespaces: pid, net, mnt, uts, ipc, user) and what it can use (cgroups).
  • Exceeding a cgroup memory limit gets the process OOM-killed; exceeding a CPU limit only throttles it.
  • Images are stacked read-only layers plus a writable top layer. Writes there vanish with the container.
  • Docker is tooling around these kernel features. On macOS and Windows it needs a hidden Linux VM.
  • Sharing a kernel makes the wall thinner than a VM's, so untrusted code usually gets a VM boundary.
  • Inside a container, your program is PID 1: handle SIGTERM, reap children, and don't trust "how much memory the machine has".

Check your understanding

What is the main structural difference between a container and a virtual machine?

  1. A container runs on its own copy of the hardware
  2. A VM shares the host kernel and a container doesn't
  3. A container is a process on the host's kernel; a VM runs its own kernel on virtual hardware
  4. There is no difference apart from the name
Containers share the host kernel and use namespaces and cgroups; VMs boot a separate guest kernel on top of a hypervisor. That is why containers start faster and weigh less, and why the wall around them is thinner.

A container with a 512 MB memory limit tries to use 700 MB while the host has plenty of free RAM. What happens?

  1. The kernel's OOM killer kills a process in that container, typically with SIGKILL (exit status 137)
  2. The container quietly gets more memory from the host
  3. The program is throttled and runs slower
  4. The kernel sends SIGTERM and waits for the program to clean up
Memory limits are hard. The cgroup limit applies regardless of the host's free memory, and the process can't catch SIGKILL. Throttling is what happens to a CPU limit, not a memory limit.

You run docker stop on a container and it takes about ten seconds, then the app dies without finishing its shutdown code. The most likely cause?

  1. Docker is slow to start the shutdown
  2. The container was OOM-killed
  3. The image has too many layers
  4. The app is PID 1 and has no SIGTERM handler, so the signal is ignored until Docker sends SIGKILL
The kernel doesn't apply default signal actions to PID 1 of a PID namespace. Install a SIGTERM handler, or use an init process such as docker run --init.

Why does Docker Desktop on a Mac start a Linux virtual machine?

  1. To make containers more secure than on Linux
  2. Because containers rely on Linux kernel features (namespaces, cgroups) that macOS doesn't have
  3. Because macOS can't run any containers at all
  4. To translate Mac programs into Linux programs
Linux containers need a Linux kernel. The VM supplies one, and the containers run inside it. Security isn't the reason, and nothing is translated: the image must contain Linux programs.

A program sizes its cache as "25% of total RAM" using what free reports. Inside a container with a small memory limit, what is the risk?

  1. None: free always shows the container's limit
  2. The cache will be too small
  3. It may see the host's total memory, size the cache far above the container limit and get OOM-killed
  4. The program won't start
Many tools report host memory, not the cgroup limit. Configure sizes explicitly or use a runtime that reads the cgroup limit, and leave headroom.

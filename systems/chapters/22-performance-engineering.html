Performance Engineering

Making a program faster is not a bag of tricks; it is a method. Decide what "fast" means, measure where the time really goes, change one thing, and check that it worked. This chapter builds the whole toolkit from scratch in about a hundred lines of Python: a profiler, a sampling profiler that writes flame-graph input, an allocation hunter, and a benchmark harness that tells you when a difference is real.

Why this matters

Almost every performance story has the same plot: someone is sure they know why the system is slow, spends a week optimising it, and discovers the real cause was somewhere else. Human intuition about where time goes is poor, and it gets worse as systems grow. The cure is cheap and unglamorous: measure first. People who work this way routinely find a 10x or 100x win in an hour, because they stop guessing. The same discipline is what separates a believable "this change cut p99 latency by 30%" from a number that evaporated the next day, and it is the skill behind every capacity plan and cost-saving project you will ever be asked to defend.

Performance is a method, not a bag of tricks

The method has five steps and they are worth saying out loud, because skipping any one of them is how effort gets wasted.

  1. Define the goal and the metric. "Make it faster" is not a goal. "99% of checkout requests finish in under 300 ms at 500 requests per second" is. The metric usually falls into one of two families. Latency is how long one operation takes, and you care about its distribution: the median (p50) is the typical user, p99 is the unlucky one in a hundred (we met percentiles in reliability chapter 4). Throughput is how much work per second the system finishes. They pull against each other: batching raises throughput and often raises latency (chapter 14's queues showed why). Pick which one you are paid for.
  2. Measure the baseline. Before you change anything, record the number you are trying to move, under conditions you can reproduce.
  3. Form a hypothesis from evidence. A profile or a metric says where the time goes; your hypothesis says why, and what change would help.
  4. Change one thing. If you change three things and the program speeds up, you don't know which one mattered, and one of them may have made it worse.
  5. Verify. Re-measure against the baseline in the same way. If the difference is within the noise, you have not learned anything yet. Then loop, or stop when the goal is met. Stopping is part of the method: optimisation has a cost in complexity, and "fast enough" is a real answer.

Common misconception

"Premature optimisation is the root of all evil" is usually quoted to mean "never think about performance". The sentence (Donald Knuth's) is about optimising before you know where the time goes. Choosing a sensible algorithm up front is good design. Hand-tuning a loop that a profile never flagged is the sin.

First pass: the USE method

Before opening a profiler, ask a broader and faster question: which resource is the bottleneck? The USE method, recapped from reliability chapter 4, gives a checklist. For every resource (CPU, memory, disk, network, and software ones such as thread pools and connection pools) check three things:

  • Utilisation: what fraction of the time is the resource busy?
  • Saturation: is there queued work waiting for it? (A run queue longer than the number of cores, a disk with a backlog, swapping.)
  • Errors: are there failures? (Dropped packets, retries, out-of-memory kills.)

It takes minutes with tools you've already met: top for CPU and load (chapter 7), vm_stat or vmstat and iostat for memory and disk (see the toolbox), and a connection or queue count for software resources. A CPU pegged at 100% with a long run queue says "profile the CPU". A CPU at 5% while requests are slow says the program is waiting, and you need the off-CPU view later in this chapter. Memory under pressure and swapping (chapter 6) says look at allocation. USE does not find the cause; it tells you which of the next sections to use.

CPU profiling: where do the cycles go?

A profiler attributes time to parts of your program. There are two basic designs, and the difference matters.

  • An instrumenting (or deterministic) profiler hooks every function call and return and records exact counts and times. Python's built-in cProfile works this way. You get exact call counts, but the hooks themselves cost time, and that cost is paid per call, so code made of many tiny calls looks slower than it is.
  • A sampling profiler lets the program run normally and, many times a second, interrupts it and records the current call stack. After thousands of samples, the functions that appear most often are where the time goes. Overhead is small and constant, which is why production profilers (py-spy, perf) are sampling profilers. The cost is statistical: you see proportions, not exact counts, and short-lived functions can be missed.

Using cProfile on a deliberately slow function

Here is a program that finds primes the slow way and builds a report. We suspect the primality test, but we don't know. Let the profiler say.

import cProfile, pstats

def is_prime(n):
    if n < 2:
        return False
    for d in range(2, n):          # slow: tries every divisor below n
        if n % d == 0:
            return False
    return True

def build_report(limit):
    primes = [n for n in range(limit) if is_prime(n)]
    lines = []
    for p in primes:
        lines.append("prime %d" % p)
    return "\n".join(lines)

def main():
    return len(build_report(20000))

if __name__ == "__main__":
    pr = cProfile.Profile()
    pr.runcall(main)
    pstats.Stats(pr).strip_dirs().sort_stats("tottime").print_stats(4)

Building a sampling profiler (about 30 lines)

A sampling profiler is simpler than it sounds. On macOS and Linux, signal.setitimer asks the operating system to deliver a signal every few milliseconds; Python runs your handler between bytecodes, and the handler can look at the stack of the interrupted code with frame.f_back, walking from the leaf up to the caller. We count how many times each complete stack appears and print it in the folded stacks format: one line per distinct stack, frames joined by semicolons from root to leaf, a space, then the sample count. This is the standard input format of flame-graph tools.

"""A tiny sampling profiler: every 5 ms, a timer signal interrupts the
program and we record the call stack as one 'folded stack' line."""
import collections, signal, sys, time

counts = collections.Counter()

def sample(signum, frame):
    stack = []
    while frame is not None:
        code = frame.f_code
        if code.co_name == "profile":          # hide the profiler's own frames
            break
        stack.append(code.co_name)
        frame = frame.f_back
    if stack:
        counts[";".join(reversed(stack))] += 1  # root first, leaf last

def profile(fn, interval=0.005):
    signal.signal(signal.SIGPROF, sample)
    signal.setitimer(signal.ITIMER_PROF, interval, interval)   # counts CPU time
    try:
        fn()
    finally:
        signal.setitimer(signal.ITIMER_PROF, 0)

# ---- the program being profiled ----
def parse(n):    return sum(int(str(i)) for i in range(n))
def render(n):   return len("".join(str(i) + "," for i in range(n)))
def checksum(n):
    total = 0
    for i in range(n):
        total = (total * 31 + i) % 1_000_003
    return total
def handler():
    for _ in range(40):
        parse(60_000); render(60_000); checksum(400_000)
        checksum(400_000)

if __name__ == "__main__":
    profile(handler)
    total = sum(counts.values())
    print(f"# {total} samples", file=sys.stderr)
    for stack, n in counts.most_common():
        print(stack, n)
$ python3 sampler.py > profile.folded
# 141 samples
$ cat profile.folded
handler;checksum 79
handler;render;<genexpr> 30
handler;parse;<genexpr> 26
handler;render 6

Checking the output: more than half of the samples (79 of 141) land in checksum, which the program calls twice per iteration on 400,000 numbers, while render and parse split the rest. Run it again and the counts will move by a few, because sampling is statistical, but the dominant entry (checksum) won't change. A few honest limitations. ITIMER_PROF counts CPU time (we will fix that in a moment); signals exist only on Unix-like systems, so this will not run on native Windows; the handler runs only between bytecodes, so a long call into C code is invisible until it returns; and a real profiler also records threads, native frames and line numbers. The idea, though, is exactly what py-spy and perf do from outside the process.

Flame graphs: reading the picture

A list of 200 folded lines is hard to read. A flame graph, invented by Brendan Gregg, turns them into a picture. Each box is a function (a stack frame). A box sits on top of the function that called it, so the bottom row is the entry point and the stacks grow upward. And the key rule: the width of a box is the fraction of samples in which that function was on the stack, which is its share of the time.

Three rules for reading one:

  1. Width is time; left-to-right is not. Siblings are normally sorted alphabetically so that identical stacks merge. A box at the far left did not run first. Beginners read flame graphs like timelines, and that is the commonest mistake.
  2. Look at the tops of the towers. A box with a lot of empty space above it is burning CPU in its own code (high "self" time). A wide box with a tall, busy tower above it is just a coordinator; the cost is in what it calls. You find the fix by following the width upward until it stops splitting.
  3. Judge by share of the whole. A beautiful, wide escape at 30% means removing it entirely is worth at most a 1.4x speedup (Amdahl, below). A narrow frame is not worth your afternoon, however easy it looks.

For real programs, py-spy record writes a flame graph as an SVG directly, and on Linux perf record plus Brendan Gregg's FlameGraph scripts do the same for any language; see the py-spy and perf cards for exact commands. Off-CPU analysis: when the program is waiting

Everything above sees only code that is running. But a request that takes 1.1 seconds might spend 0.3 s computing and 0.8 s waiting: for a database to answer, for a disk read, for a lock held by another thread (chapter 12), or for the scheduler to give it a core (chapter 7). A CPU-time sampler is blind to waiting, because a sleeping thread consumes no CPU time, so no timer tick ever lands in it. This is the off-CPU time, and in I/O-heavy services it is often the larger part.

The fix is to sample by wall-clock time instead (ITIMER_REAL, which delivers SIGALRM) so that waiting threads still get sampled. The program below runs the same handler under both samplers. It computes for 0.3 s, sleeps for 0.5 s (standing in for a database call) and blocks for 0.3 s on a lock held by another thread.

"""Same program, two samplers: one counts CPU time, one counts wall-clock time."""
import collections, signal, threading, time

def make_sampler(counts):
    def sample(signum, frame):
        stack = []
        while frame is not None and frame.f_code.co_name != "run":
            stack.append(frame.f_code.co_name)
            frame = frame.f_back
        if stack:
            counts[";".join(reversed(stack))] += 1
    return sample

def run(fn, timer, sig, interval=0.01):
    counts = collections.Counter()
    signal.signal(sig, make_sampler(counts))
    signal.setitimer(timer, interval, interval)
    fn()
    signal.setitimer(timer, 0)
    return counts

lock = threading.Lock()

def handler():
    compute()
    call_database()
    wait_for_lock()

def compute():
    t = time.perf_counter()
    while time.perf_counter() - t < 0.30:   # busy for 0.3 s
        pass

def call_database():
    time.sleep(0.50)                         # pretend network round trip

def wait_for_lock():
    def holder():
        with lock:
            time.sleep(0.30)
    th = threading.Thread(target=holder); th.start()
    time.sleep(0.01)                         # let the other thread grab the lock
    with lock:                               # we block here until it lets go
        pass
    th.join()

for label, timer, sig in (("CPU-time sampler (ITIMER_PROF)", signal.ITIMER_PROF, signal.SIGPROF),
                          ("wall-clock sampler (ITIMER_REAL)", signal.ITIMER_REAL, signal.SIGALRM)):
    counts = run(handler, timer, sig)
    print(f"{label}: {sum(counts.values())} samples")
    for stack, n in counts.most_common():
        print(f"   {stack} {n}")
$ python3 offcpu.py

   handler;compute 25
wall-clock sampler (ITIMER_REAL): 111 samples
   handler;call_database 51
   handler;wait_for_lock 31
   handler;compute 29

The CPU-time sampler reports 25 samples, all in compute: it saw the 0.3 s of work (at 10 ms intervals, 25 to 30 samples) and nothing else. The wall-clock sampler took 111 samples: 51 in call_database, 31 in wait_for_lock and 29 in compute. Same program, opposite conclusions about what to fix. The leaf in the wall-clock stacks is the Python function that is blocked; to learn why (a lock, a socket, a sleep), look at what it is calling.

Real tools expose this too. py-spy samples only threads that are running Python unless you pass --idle, which includes the waiting ones. On Linux, perf and the eBPF tools (see bpftrace) can record why a thread went off-CPU and for how long, and strace -T (strace) shows the time spent in each system call. The rule of thumb: if the CPU is not busy but the program is slow, you need an off-CPU view. When the answer is "waiting on the network", the fixes live in earlier chapters: fewer round trips, concurrent I/O (chapters 15 to 17), and caching.

Memory and allocation profiling

Every object you create takes memory and takes time to create, track and eventually free (chapter 3). Allocation-heavy code is slow for the same reasons it is large: more cache misses, more garbage-collector work, and more pressure on the OS to supply pages (chapter 6). When memory use is the problem, or when you suspect allocation churn, use an allocation profiler. Python's standard library has one: tracemalloc records where each live allocation was made.

import tracemalloc

def load_rows(n):
    rows = []
    for i in range(n):
        rows.append({"id": i, "name": "user-%d" % i, "tags": ["a", "b", "c"]})
    return rows

def build_index(rows):
    return {r["name"]: r for r in rows}

tracemalloc.start()
rows = load_rows(50_000)
index = build_index(rows)
snapshot = tracemalloc.take_snapshot()
current, peak = tracemalloc.get_traced_memory()
print(f"current={current/1e6:.1f} MB  peak={peak/1e6:.1f} MB\n")
for stat in snapshot.statistics("lineno")[:3]:
    frame = stat.traceback[0]
    print(f"{frame.filename.rsplit('/', 1)[-1]}:{frame.lineno}  "
          f"size={stat.size/1e6:5.1f} MB  count={stat.count:,}")
$ python3 alloc.py

alloc.py:5  size=  1.6 MB  count=49,718

The report ranks source lines by the memory they currently hold. Line 6 (inside load_rows, where each row builds a dictionary, a string and a list) accounts for 16.6 MB across about 250,000 allocations, which is about five allocations per row. Nothing else is close. The hypothesis: each row is a dict plus a fresh list of tags, and dicts are expensive. One change: store rows as tuples and share a single tuple of tags.

import tracemalloc
TAGS = ("a", "b", "c")
def load_rows(n):
    return [(i, "user-%d" % i, TAGS) for i in range(n)]
tracemalloc.start()
rows = load_rows(50_000)
current, peak = tracemalloc.get_traced_memory()
print(f"tuples: current={current/1e6:.1f} MB  peak={peak/1e6:.1f} MB")
$ python3 alloc_fixed.py
tuples: current=8.2 MB  peak=8.2 MB

From 20.1 MB to 8.2 MB of live memory, and fewer objects for the garbage collector to track and the cache to chase. (This fix has a cost: tuples are less readable than named fields. A NamedTuple or a class with __slots__ gets most of the savings with names. Measure your own case.) Two cautions about tracemalloc: it slows the program down noticeably while tracing, so use it in a test run, not in production; and it measures Python allocations, not memory held by C libraries, so compare with the process's real memory (chapter 6, ps or Activity Monitor) if the numbers don't add up.

Benchmarking without fooling yourself

A benchmark is a controlled measurement of how long something takes. It is easy to get a number and hard to get a trustworthy one. The classic traps:

  • No warm-up. The first run pays for cold caches (chapter 2), page faults, lazy imports and, in languages with a JIT such as Java or JavaScript, code that hasn't been compiled yet. Run a few throwaway iterations first, then measure; tools like hyperfine have a --warmup flag for this. But also benchmark the cold case separately if your users will experience it (a serverless function starts cold every time).
  • Noise. Other processes, thermal throttling, a laptop on battery, background indexing, a noisy neighbour on a shared cloud VM. One run is an anecdote. Run many times and look at the spread.
  • Reporting the mean of a skewed distribution. Latencies are not bell-shaped: they have a long right tail. The mean is dragged by the tail and describes nobody's experience. Use the median for the typical case and high percentiles for the tail (see the histogram below).
  • Dead-code elimination. In compiled languages (C, C++, Rust, Go, Java's JIT), an optimiser deletes computations whose results are never used. A micro-benchmark like for (i = 0; i < N; i++) sum += i; with sum never read can compile to nothing, and report "0 ns for a billion additions". Always consume the result (print it, return it, or use the language's "black box" helper) and sanity-check that your number is physically plausible. CPython does not delete code this way, but a tiny Python snippet can still be dominated by the loop around it, or be constant-folded by the compiler.
  • Measuring the wrong thing. Timing the setup along with the work; timing a cached result (the second call is free); timing with data far smaller or more regular than production's; benchmarking on your laptop's fast SSD and cold-starting nothing; or comparing two programs while one holds its data in the page cache and the other doesn't.
  • Coordinated omission. A load generator that sends the next request only after the previous one returns (a closed loop) quietly stops sending exactly when the system stalls, so the long delays are never recorded and the percentiles look wonderful. Real users keep arriving. We covered this in reliability chapter 10; the cure is to send at a fixed schedule and measure from when each request should have started.

A benchmark harness with a confidence interval

Here is the minimum honest harness. It does warm-up runs, then times many repetitions with a high-resolution clock (time.perf_counter, never time.time), and reports the median with a bootstrap confidence interval. The bootstrap idea: you have 30 timings and want to know how uncertain the median is. Resample the 30 values with replacement many times, compute the median of each resample, and look at the middle 95% of those medians. If two programs' intervals don't overlap, you have decent evidence that the difference is real; if they overlap heavily, you can't tell them apart yet. (This is a rule of thumb; for a rigorous comparison, bootstrap the difference itself.)

import random, statistics, time

def bench(fn, repeats=30, warmup=3, inner=1):
    for _ in range(warmup):
        fn()
    times = []
    for _ in range(repeats):
        t0 = time.perf_counter()
        for _ in range(inner):
            fn()
        times.append((time.perf_counter() - t0) / inner)
    return times

def bootstrap_ci(xs, stat=statistics.median, n_boot=2000, level=0.95, seed=1):
    rng = random.Random(seed)
    boots = sorted(stat([rng.choice(xs) for _ in xs]) for _ in range(n_boot))
    lo = boots[int((1 - level) / 2 * n_boot)]
    hi = boots[int((1 + level) / 2 * n_boot) - 1]
    return lo, hi

def report(name, xs):
    lo, hi = bootstrap_ci(xs)
    print(f"{name:18s} median {statistics.median(xs)*1e3:7.3f} ms  "
          f"95% CI [{lo*1e3:.3f}, {hi*1e3:.3f}]  mean {statistics.fmean(xs)*1e3:7.3f} ms  "
          f"min {min(xs)*1e3:.3f}  max {max(xs)*1e3:.3f}  n={len(xs)}")

data = list(range(200_000))
random.Random(0).shuffle(data)

def sort_copy():      sorted(data)
def sort_inplace():   data[:].sort()
def sort_key():       sorted(data, key=lambda x: x)

if __name__ == "__main__":
    report("sorted(data)", bench(sort_copy))
    report("data[:].sort()", bench(sort_inplace))
    report("sort, key=lambda", bench(sort_key))
$ python3 bench.py
sorted(data)       median  16.262 ms  95% CI [16.235, 16.314]  mean  16.279 ms  min 16.155  max 16.527  n=30
data[:].sort()     median  16.379 ms  95% CI [16.291, 16.425]  mean  16.375 ms  min 16.211  max 16.703  n=30
sort, key=lambda   median  21.825 ms  95% CI [21.770, 21.890]  mean  21.840 ms  min 21.643  max 22.069  n=30

How to read it. sorted(data) and data[:].sort() do the same work (the second copies the list, then sorts in place), and their intervals overlap: the harness is telling you there is no measurable difference, which is correct. Sorting with key=lambda x: x is about 34% slower, with an interval far from the others: that difference is real, caused by a Python function call per element. The intervals here are narrow because this machine was quiet; on a noisy machine they widen, and a harness that shows you the width is the one that protects you from false victories. Your numbers will differ. A few more habits: run benchmarks on a plugged-in, idle machine; compare A and B in the same session (interleaved if you can, since background load drifts); keep the test data realistic; and write down the Python version and hardware. hyperfine does the same job for whole commands, with warm-up, repeated runs and a spread; use it when you want to compare programs rather than functions.

The usual wins, in order

When the profile points at a hot spot, there is a rough order in which fixes pay off. Go down the list; stop as soon as you have met your goal.

OrderFixTypical gainExample
1A better algorithm or data structureOften 10x to 1000xThe primality test above; a dict lookup instead of scanning a list; an index instead of a table scan (data chapter 7)
2Do less work: cachingDepends on hit rateMemoise a pure function (functools.lru_cache); a cache in front of a slow call; remember chapter 2's cost of a miss
3Do work in bulk: batching2x to 100xOne query for 100 ids instead of 100 queries; one write of a large buffer; the batching of chapter 21
4Avoid allocation and copying1.2x to 5xBuild a string with "".join, not repeated +=; reuse buffers; tuples instead of dicts for hot rows; iterate instead of building intermediate lists
5Better I/O patternsOften largeRead in big sequential chunks instead of byte by byte (chapter 8); fewer fsync calls where safe (chapter 9); concurrent requests instead of sequential (chapters 15 to 17)
6Locality1.5x to 10x on large dataContiguous arrays and sequential access instead of pointer-chasing (chapter 2); process data in cache-sized blocks
7Lower-level code and parallel hardwareVaries widelyNumPy or a compiled extension; multiple processes; a GPU (chapter 21)

The gains are "typical" in the sense of "I've seen it, and so will you", not guarantees; always measure. The reason for the ordering: the first items change how much work there is, the later ones change how fast each unit of work runs, and doing less work beats doing it faster. It is also the order of increasing complexity and risk. A caching bug is a correctness bug (stale data), and a clever low-level rewrite is code that few colleagues can maintain.

Analogy: the slow restaurant

Customers complain that dinner takes an hour. You could buy faster knives, but first you time each step. Perhaps the cook spends 40 minutes walking to the freezer (data movement), or cooks one dish at a time when the oven fits eight (batching), or re-chops the same onions for every order (caching). Buying faster knives would have changed nothing. Measuring the kitchen shows where the hour goes.

Where it breaks down: a kitchen is watched by people; a program can't be seen, which is exactly why we need profilers to be our eyes.

Amdahl for optimisation priorities

Chapter 21's law applies to optimisation, not just parallelism. If part of a program takes a fraction f of the runtime and you speed that part up by a factor s, the whole program speeds up by 1 / ((1 - f) + f / s). Say a profile shows three parts: A at 60% of the time, B at 25%, C at 15%. Tempting target: B, because it looks easiest to speed up 10x. The numbers:

  • Make B 10x faster: 1 / (0.75 + 0.25/10) = 1.29x overall.
  • Make A just 2x faster: 1 / (0.40 + 0.60/2) = 1.43x overall.
  • Remove C completely: 1 / 0.85 = 1.18x, the hard ceiling of that fix.

Two lessons. A modest win on the big part beats a dramatic win on a small part. And the ceiling of any single fix is 1 / (1 - f): a function that takes 5% of the time can never buy you more than a 5% saving, so don't spend a week on it. The practical routine is: look at the flame graph, pick the widest thing you can actually change, fix it, re-profile, and notice that the shape of the profile changes (the old bottleneck shrinks and the next one becomes the widest). Repeat until you hit the goal, or until the remaining boxes are all small, which means you've reached the point of diminishing returns.

Go deeper: what profilers can't see optional

Sampling bias. Many sampling profilers can only take a sample at "safe points" (Python's signal handler runs between bytecodes), so tight loops with no safe point and calls into native code can be under-counted or attributed to the wrong frame. Linux perf samples with hardware interrupts and avoids most of this for native code, at the cost of needing frame pointers or debug info to unwind stacks.

Observer effects. An instrumenting profiler slows small functions most, so it can reorder the ranking. A tracing tool slows the program, which changes how threads interleave, which can hide a race (chapter 11) that only occurs at full speed.

Inlining. In compiled languages the optimiser merges small functions into their callers, so a function you wrote may not exist at run time and its cost shows up in the caller. Profiles of optimised builds need debug symbols to map back to your source.

Production versus your laptop. Different data sizes, caches and concurrency change the profile. Continuous profiling (low-rate sampling always on in production) exists because the bottleneck you can reproduce locally may not be the one that matters. That connects to observability in the reliability course.

Try it yourself

Try it yourself: profile, then benchmark

All safe and read-only. Save the chapter's scripts with the names shown above, then try these. Your numbers will be different. The py-spy and perf cards cover production-style profilers (on some systems py-spy needs extra privileges to attach to a process; its card explains), and hyperfine times whole commands.

# cProfile from the command line, no code changes, sorted by own-time
$ python3 -m cProfile -s tottime slow.py | head -15

# whole-command benchmark with warm-up and spread (macOS: brew install hyperfine)
$ hyperfine --warmup 2 'python3 slow.py' 'python3 slow_fixed.py'

# quick micro-benchmark from the standard library; repeats and picks a sensible loop count
$ python3 -m timeit -s "d=list(range(10**5))" "sorted(d)"

# generate a flame graph from your own program (needs: pipx install py-spy)
$ py-spy record -o flame.svg -- python3 sampler.py

Experiments: run bench.py twice, once idle and once while something heavy (a video, a build) runs, and watch the confidence intervals widen. Change repeats from 30 to 5 and see the interval grow. Run offcpu.py and make the sleep longer: the CPU-time sampler's report doesn't change, which is the whole point. Finally, take a script of your own and ask the one question this chapter exists to teach: what do the measurements say, rather than what do I believe?

Distributed systems connection

The method scales up unchanged. In a distributed system the "profile" is a distributed trace (a per-request timeline across services, built on the metrics ideas of reliability chapter 4), the off-CPU view is the time a request spends waiting on other services, and the dominant effect is the tail: a request that fans out to 100 backends is as slow as the slowest, so p99 of each part becomes the typical case of the whole (see networking chapter 13 and load testing and capacity planning). Benchmarks become load tests with the same traps, coordinated omission first. And Amdahl's law is the reason that after you fix the biggest bottleneck, the next one becomes the story, forever.

Key takeaways

  • Performance work is a loop: define the goal and metric (latency percentile or throughput), measure a baseline, form a hypothesis from evidence, change one thing, verify, and stop when the goal is met.
  • Start with USE (utilisation, saturation, errors per resource) to learn which resource is the bottleneck, then pick the tool: CPU profile, off-CPU view or allocation profile.
  • Instrumenting profilers (cProfile) give exact counts with per-call overhead; sampling profilers give proportions with low, constant overhead. Folded stacks are the common format between them and flame graphs.
  • In a flame graph, width is share of samples and left-to-right order means nothing. Look for wide boxes with empty space on top.
  • A CPU profile is blind to waiting. If the CPU is idle but the request is slow, sample by wall-clock time or use an off-CPU tool.
  • Benchmark honestly: warm up, repeat, report the median with a confidence interval, never the mean of skewed data, consume results to defeat dead-code elimination, and avoid coordinated omission.
  • Fix in order: algorithm, do less (cache), do it in bulk (batch), allocate less, better I/O, locality, then lower-level or parallel hardware. By Amdahl, a fix can't gain more than 1 / (1 - f) where f is the share of time it touches.

Check your understanding

In a flame graph, what does the width of a box represent?

  1. How early in the run the function was called
  2. The fraction of samples in which that function was on the stack
  3. The number of lines of code in the function
  4. The amount of memory the function allocated
Width is share of samples, hence share of time. The x axis is not a timeline: siblings are sorted alphabetically to merge identical stacks, so position says nothing about order of execution.

A web handler is slow, yet the CPU is only 5% busy. A CPU-time profile shows a short, unremarkable stack. What should you do next?

  1. Rewrite the hot loop in a faster language
  2. Add more CPU cores
  3. Run the benchmark more times to reduce noise
  4. Look at off-CPU time: sample by wall-clock, or trace what it blocks on (database, locks, I/O)
Idle CPU plus slow requests means the program is waiting. CPU-time sampling never lands in a sleeping thread, so only a wall-clock or off-CPU view can show where the waiting happens.

A function accounts for 20% of the run time. You make it 10x faster. Roughly how much faster is the whole program?

  1. About 1.22x
  2. About 2x
  3. About 10x
  4. About 1.02x
1 / (0.8 + 0.2/10) = 1 / 0.82, about 1.22x. Even if the function became free, the limit would be 1 / 0.8 = 1.25x. A big win on a small slice is a small win overall.

Two benchmark results: A has median 16.3 ms with 95% interval [16.2, 16.4]; B has median 16.4 ms with interval [16.3, 16.5]. What can you conclude?

  1. A is faster than B, because 16.3 is less than 16.4
  2. B is faster, because its upper bound is higher
  3. The intervals overlap, so you can't claim a real difference; gather more data or accept they are the same
  4. Both are wrong, because medians should never be used
Overlapping intervals mean the observed gap is within the measurement uncertainty. The median is a good summary for skewed timings; the interval is what tells you how much to trust the difference.

A C micro-benchmark that adds a billion integers in a loop reports 0.0 ns. The most likely explanation is:

  1. The CPU is faster than the clock can measure
  2. The optimiser removed the loop because its result was never used (dead-code elimination)
  3. The operating system cached the answer
  4. The loop ran on the GPU
An optimising compiler may delete computations with no observable effect. Use the result (print it, return it, or pass it to a "black box" helper) and check that the time is plausible: a billion additions can't take zero time.

Why do p99 latencies deserve attention even when the median is fine?

  1. The median is always inaccurate
  2. Averages are impossible to compute
  3. The tail is always caused by the network
  4. Latency is skewed with a long tail, and in systems where a request depends on many sub-requests, the slowest one often sets the whole request's time
The mean and median hide the slow tail. With fan-out, the chance that at least one of many calls lands in the tail is high, so users experience the tail much more often than "1 in 100".

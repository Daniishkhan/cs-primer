Start Here

The networking course ended with bytes arriving at a port and "the server" reading them. This course is about that server: a program running on one machine. We'll look at what a program physically is, where its data lives, how it survives crashes, and how it serves thousands of people at once without mixing up their data.

A note from your mentor

Senior engineers often look like they have amazing intuition: "that will be slow", "that can lose data", "that will deadlock under load". Almost all of that intuition comes from knowing what one machine is really doing underneath the code. Senior engineers aren't smarter; they've just built a clear picture of the machine. That picture is what this course gives you. You only need the networking course (or the idea that programs talk through ports and sockets). Every new word is explained the first time it appears.

Why this matters

Every database, web server, message queue and distributed-system node is an ordinary program on an ordinary machine. When a database promises your data is "saved", that promise rests on how files and disks behave (chapter 9). When a server handles 10,000 connections, that rests on event loops (chapter 16). When two requests corrupt each other's data, that's a race condition (chapter 11). You can't reason clearly about systems built from many machines until you can reason about one.

One request, inside one machine

In networking chapter 0 we followed a chat message across the planet. Now let's zoom into the last step, where a server receives a request and answers it. The picture has three floors:

  • Hardware at the bottom: the network card, the CPU, memory (RAM) and the disk.
  • The kernel in the middle: the core of the operating system (OS), the one program that controls the hardware directly.
  • Your program on top, running as a process: a program that has been started and is currently running, with its own memory.

Step through the journey. Each step names the chapter where you'll learn how that part really works.

Step through

A request arrives at a server

  1. Bytes arrive. The network card receives the request's packets. It copies them straight into RAM and taps the CPU on the shoulder with an interrupt: "something arrived". (Hardware and memory: ch. 2.)
  2. The kernel takes over. The kernel's TCP/IP code (exactly what you studied in networking ch. 8) checks the packets, puts the bytes in order and appends them to the socket's receive buffer. Your program hasn't run a single instruction yet. (The kernel: ch. 4.)
  3. The waiting program wakes up. The server was asleep, waiting for any of its thousands of connections to have data. The kernel tells its event loop: "connection 7 is readable". (Event loops: ch. 16.)
  4. Getting a turn on the CPU. Hundreds of programs are waiting to run on a handful of CPU cores. The scheduler picks the server and switches the core over to it. (Scheduling: ch. 7.)
  5. Asking the kernel for the bytes. Programs can't touch the network card or the kernel's buffers directly. The server makes a system call, read(), and the kernel copies the bytes into the program's own memory. (System calls: ch. 4; sockets as files: ch. 8.)
  6. Running your code. The CPU runs the handler's instructions. Every variable it touches lives in memory the OS has given to this process alone, and how fast it runs depends heavily on whether that data is already in the CPU's caches. (CPUs: ch. 1; stack and heap: ch. 3; virtual memory: ch. 6.)
  7. Reading a file. The handler needs a file. If the kernel already has it in its page cache (RAM), this takes microseconds. If not, it's read from the SSD, which takes roughly 100 times longer, and the program waits. (ch. 2, ch. 8.)
  8. Saving something safely. The handler records the request in a log. Writing to a file only puts the data in RAM. To be sure it survives a power cut, the program must call fsync() and wait for the disk. This is the hidden cost behind every "saved". (Durability: ch. 9.)
  9. Everyone else at the same time. While all this happens, thousands of other requests are in flight. If two of them update the same data at the same moment, it can be silently corrupted, unless the program uses locks, queues or a single-threaded design. (Concurrency: ch. 10–14.)
  10. Answering. A write() system call hands the response back to the kernel, which sends it out through TCP and the network card. Without the disk sync, the whole trip inside the machine often takes well under a millisecond.

That's ten steps and most of this course. Notice that most of the work happens outside your code: in the kernel, in memory, in the waiting. Programs that are fast and reliable under load come from understanding those parts.

The three illusions

A useful way to see the operating system: it creates three convenient illusions, and much of this course is about how each one is made and where it leaks.

🧠 "You have the CPU to yourself"

Hundreds of programs share a few cores. The kernel switches between them so fast that each one seems to run continuously. Leaks when: your program is paused at a bad moment, or a busy neighbour slows you down. (ch. 7)

🧮 "You have memory to yourself"

Every process sees its own private address space, and can't see anyone else's memory. Leaks when: memory runs out and the machine starts swapping, or the kernel kills your process. (ch. 6)

💾 "Saved means saved"

A file write returns instantly, as if the data were on disk. Leaks when: the power fails before the kernel actually wrote it. Databases spend a lot of effort working around this one. (ch. 9)

Analogy: a busy restaurant kitchen

The CPU cores are the cooks, RAM is the counter space, the disk is the walk-in freezer and the kernel is the head chef handing out orders and tools. Each order (process) gets its own station and doesn't touch anyone else's ingredients. Cooks switch between dishes constantly. Fetching something from the freezer is slow, so good kitchens keep what they need on the counter. And if two cooks grab the same pan at once, you get a mess. That's the concurrency part of the course.

Where it breaks down: a real head chef is just another cook. The kernel isn't a separate worker: it is code that runs on the same CPU cores, taking over whenever a program asks for something or a piece of hardware calls for attention.

Common misconception

"Performance is about writing clever code." Usually it's about waiting: for the disk, the network, a lock or a turn on the CPU. A server that spends 95% of its time waiting won't be fixed by making its code twice as fast. It's fixed by changing how it waits. That idea runs through Parts 3 and 4.

Try it yourself

Try it yourself: meet your machine

Open a terminal (on Windows, use WSL for this course; the labs need a Unix-like system). These commands only read information. Your numbers will differ.

$ sysctl -n hw.ncpu          # CPU cores (Linux: nproc)
10
$ ps aux | wc -l             # how many processes are running right now
     612
$ ulimit -n                  # how many files (and sockets!) one process may open
256
$ lsof -p $$ | head -5       # files your own shell has open ($$ = its process ID)
COMMAND   PID   USER   FD   TYPE DEVICE  SIZE/OFF  NODE NAME
zsh     48211 you    cwd    DIR   1,17      2048  1234 /Users/you
zsh     48211 you    txt    REG   1,17   1361200  5678 /bin/zsh
zsh     48211 you      0u   CHR   16,2       0t0   901 /dev/ttys002
zsh     48211 you      1u   CHR   16,2       0t0   901 /dev/ttys002

That's more than 600 processes on 10 cores, so the scheduler is clearly busy. There's also a limit on open files that will matter when we try to serve 10,000 connections. And your shell's screen shows up as a file (/dev/ttys002). Each of those is a chapter in this course.

Distributed systems connection

In networking chapter 15 we said distributed systems are hard because of partial failure. Much of that partial failure comes from inside single machines: a process that crashes, a pause for garbage collection that makes a healthy node look dead, a disk that "saved" data it didn't. Learn how one machine fails and you'll recognise it when it happens to one node among a thousand.

Key takeaways

  • Every server, database and distributed-system node is an ordinary program (a process) running on an ordinary machine.
  • A machine has three floors: hardware, the kernel, and processes. Programs reach the hardware only by asking the kernel through system calls.
  • Most of a request's life happens outside your code: in the kernel, in memory, and waiting for disks, networks and locks.
  • The OS gives three illusions: your own CPU, your own memory, and instant saves. Each one leaks, and knowing how is what this course is about.
  • Performance and reliability problems usually come down to how a program waits and how it shares data.

Check your understanding

When a request's packets arrive, what runs first?

  1. The server program's request handler
  2. Kernel code that processes the packets and puts the bytes in a socket buffer
  3. The database
  4. Nothing runs until the user clicks something
The network card and the kernel do the first part of the work: interrupt handling, TCP/IP processing, buffering. The program only sees the bytes when it asks for them with a system call like read().

What is a process?

  1. A file containing a program
  2. One CPU core
  3. A step in a recipe the kernel follows
  4. A running program, with its own private memory, managed by the operating system
A program on disk is just a file. Once started, it becomes a process: the OS gives it memory, open files and turns on the CPU. One program can be running as many processes at once.

A program writes a file and the write call returns successfully. Is the data guaranteed to survive a power cut a moment later?

  1. No. It may only be in the kernel's memory; the program must also call fsync to force it to disk
  2. Yes, a successful write always means it's on disk
  3. Only if the file is small
  4. Only on SSDs, never on spinning disks
Writes usually land in the page cache (RAM) and reach the disk later. That's why "saved means saved" is an illusion, and why databases call fsync. Chapter 9 covers this properly.

A server spends most of each request waiting for a disk. What's most likely to help?

  1. Rewriting the handler in a faster language
  2. Buying a CPU with a higher clock speed
  3. Changing how it waits: caching data in memory, or doing other work while the disk is busy
  4. Adding more comments to the code
If the time goes into waiting, making the code faster barely helps. Avoiding the wait (caching) or overlapping it with other work (concurrency, event loops) does. That's the theme of Parts 3 and 4.

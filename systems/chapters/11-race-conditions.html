Race Conditions

Two threads run counter += 1 a thousand times each and the total comes out wrong, though no line of code is "wrong". This chapter explains why one innocent-looking line is really three steps, how the scheduler can slip between them, and why the same bug appears whenever two servers update one database row.

Why this matters

Race conditions are the most common serious bug in concurrent software and the hardest to catch. They corrupt data silently, they pass your tests, and they appear in production under load. Every pattern in this chapter (lost updates, check-then-act, read-modify-write) is also a classic distributed-systems failure: change "two threads" to "two servers" and "variable" to "database row" and nothing else changes. Learn to spot the pattern here, in a few lines of Python, and you'll spot it in a system diagram.

One line, three steps

In chapter 1 you saw that a CPU can only do small steps: copy a value from memory into a register, do arithmetic on registers, copy a result back to memory. There is no single instruction that means "add one to the number in that memory location" for ordinary variables (some CPUs do offer one, as we'll see in chapter 12, but language runtimes don't generally use it for you). So counter += 1 means three separate steps:

Python makes this visible with its dis module, which shows the bytecode (the instructions Python's interpreter runs) for a function:

import dis

counter = 0

def bump():
    global counter
    counter += 1

dis.dis(bump)
$ python3 dis1.py
  5           RESUME                   0

  7           LOAD_GLOBAL              0 (counter)
              LOAD_SMALL_INT           1
              BINARY_OP               13 (+=)
              STORE_GLOBAL             0 (counter)
              LOAD_CONST               1 (None)
              RETURN_VALUE

The four middle lines are our three steps (with one extra to push the constant 1): LOAD_GLOBAL reads the shared variable, BINARY_OP adds, STORE_GLOBAL writes it back. On Python 3.11 to 3.13 you'll see LOAD_CONST instead of LOAD_SMALL_INT, and before 3.11 the middle one is called INPLACE_ADD. The shape never changes. The line number column will differ with your file layout.

A note on what can race. If x is a plain local variable inside a function, nobody else can see it (it lives on that thread's own stack), so x += 1 is perfectly safe. The trouble starts when the variable is shared: a global, an attribute of an object several threads hold (self.count += 1), or an item in a shared list or dictionary (stats[key] += 1).

The GIL doesn't save you

Last chapter we met CPython's GIL, which lets only one thread run bytecode at a time. It's tempting to conclude: "so only one thread touches counter at a time, so it's safe." That's a mistake. The GIL guarantees that a single bytecode finishes without another thread running Python code in the middle of it. It does not promise that a thread keeps the GIL from one bytecode to the next. The interpreter may hand the GIL to another thread between LOAD_GLOBAL and STORE_GLOBAL, and then the load is stale by the time the store happens.

Common misconception

"Python has a GIL, so my threaded code can't have race conditions." False. The GIL protects the interpreter's own data structures. It does nothing to make your multi-step operations atomic. The same program is just as broken on a language with no GIL, and, as we'll see below, on Python itself when two processes or two servers are involved.

The lost update

Suppose counter is 5, and threads A and B each run counter += 1. If A finishes its three steps before B begins, the result is 7. Now consider this order:

This is a lost update: both threads did their job, and one of the effects vanished. Nothing crashed and no error appeared. The program just has a wrong number, which is the worst kind of bug.

Analogy: two people updating a whiteboard tally

A whiteboard shows "5 customers today". Two door staff each see a customer arrive. Each reads the board (5), adds one in their head (6), walks over and writes 6. If both read before either wrote, the board says 6 though two customers came in.

Where it breaks down: people can see each other at the board. A thread has no idea another thread read the same value, and it can be suspended after reading and for an arbitrary time (microseconds, or an entire time slice), so its picture of the world can be arbitrarily stale.

Interleavings: how many ways can this go?

When two threads each run several steps, the scheduler decides how the steps interleave, meaning the single sequence in which they actually happen. Each thread's own steps stay in order, but they can be mixed in any way. For two threads of 3 steps each, how many orders are there? Choose which 3 of the 6 time slots belong to thread A and the rest go to B: that's "6 choose 3" = 20. In general, two threads of n steps give C(2n, n) orders:

Steps per threadPossible interleavings
3 (our counter += 1)20
5 (a slightly bigger operation)252

20about 138 billion

Three threads of three steps already give 1,680. Real programs have hundreds of steps and dozens of threads, so the number of possible schedules is astronomical. You can't test them all, and you can't "look" at the code and see the one bad one. You have to argue about all of them at once, which is what locks are for.

Now try it yourself. Below, you are the scheduler.

Things to try. First, press the preset A then B (serial): the answer is 2. Then classic lost update: the answer is 1. Then reset and find a lost update by hand with as few switches as possible. (Hint: you need B to LOAD before A's STORE.) Look at the count at the bottom: of the 20 interleavings, only 2 are safe, and they're exactly the two where one thread finishes before the other starts. Finally, turn on use a lock: the safe orders are all that remain, because the second thread simply can't begin its critical steps while the first holds the lock.

An important point hides in that count. Only 2 of 20 orders are safe, yet in real programs the bad ones are rare. That is because the scheduler doesn't pick orders uniformly at random. Threads typically run for long stretches (milliseconds) between switches, and the dangerous window is a few nanoseconds wide. The bug is always possible and rarely observed, and that's what makes it so nasty.

Check-then-act

The lost update is one flavour of a broader pattern. In check-then-act, code checks a condition and then acts on the assumption that it still holds. If something can change the condition in between, the act is based on stale information.

The bank withdrawal

import threading, time

balance = 100

def withdraw(amount, who):
    global balance
    if balance >= amount:          # CHECK
        time.sleep(0.01)           # the "slow part": a database call, a fraud check...
        balance -= amount          # ACT
        print(f"{who}: withdrew {amount}")
    else:
        print(f"{who}: declined")

a = threading.Thread(target=withdraw, args=(80, "A"))
b = threading.Thread(target=withdraw, args=(80, "B"))
a.start(); b.start(); a.join(); b.join()
print("final balance:", balance)
$ python3 bank.py
A: withdrew 80
B: withdrew 80
final balance: -60

Here the gap between the check and the act is made deliberately wide with sleep, standing in for a database call or a fraud check. In real code it might be microseconds, which only changes how often you see it, not whether the bug exists.

"If the file doesn't exist, create it"

The same pattern shows up with the file system, and it has a name: TOCTOU, "time of check to time of use". Another process can create the file, or swap it for a link to something sensitive, in the gap. This isn't only a threading bug: it's a bug between any two actors sharing a resource, which is why it is a classic security vulnerability too.

import os, threading, time

path = "report.txt"
if os.path.exists(path): os.remove(path)

def create(who):
    if not os.path.exists(path):          # CHECK
        time.sleep(0.01)
        with open(path, "w") as f:        # ACT ("w" truncates!)
            f.write(f"written by {who}\n")
        print(who, "created the file")

ts = [threading.Thread(target=create, args=(n,)) for n in "AB"]
for t in ts: t.start()
for t in ts: t.join()
print(open(path).read().strip())

# The fix: let the OS do check-and-create as ONE atomic step.
os.remove(path)
def create_safely(who):
    try:
        with open(path, "x") as f:        # "x" = fail if it already exists
            f.write(f"written by {who}\n")
        print(who, "created the file")
    except FileExistsError:
        print(who, "lost the race, file already exists")
ts = [threading.Thread(target=create_safely, args=(n,)) for n in "AB"]
for t in ts: t.start()
for t in ts: t.join()
os.remove(path)
$ python3 toctou.py
B created the file
A created the file
written by A
B lost the race, file already exists
A created the file

In the first half both threads saw "no file", and both created it. The second one silently truncated and overwrote the first one's work (mode "w" truncates). The second half is the fix, and it's a general principle: let the layer that owns the resource do the check and the act as one indivisible operation. Here, mode "x" asks the OS to create the file only if it doesn't exist, atomically, and report failure otherwise (O_CREAT | O_EXCL underneath, chapter 8). The same idea gives us atomic rename for safe file replacement (chapter 9).

Lazy initialisation

"Create the expensive object the first time someone needs it" is another check-then-act:

import threading, time

config = None
loads = 0

def get_config():
    global config, loads
    if config is None:             # CHECK
        loads += 1
        time.sleep(0.01)           # pretend loading is slow
        config = {"loaded": True}  # ACT
    return config

ts = [threading.Thread(target=get_config) for _ in range(5)]
for t in ts: t.start()
for t in ts: t.join()
print("config was loaded", loads, "times")
$ python3 lazy.py
config was loaded 5 times

All five threads saw None, so all five loaded the configuration. For a read-only config that's merely wasteful. For something like "open the database connection pool" or "generate the unique ID counter's starting value" it can be disastrous: five pools, or two counters that both start at zero. The fix is to make the check and the initialisation one critical section (chapter 12), or to initialise before any threads start.

Read-modify-write

The lost update, the bank withdrawal and lazy initialisation are all variations of one shape, read-modify-write: read a value, decide or compute something from it, write the result back, and assume nothing changed in the middle. Spot that shape and you've spotted the bug. You'll find it in "increment a view counter", "append to a shared list if not already present", "take the next job ID", and "update my cached copy of a record".

Data race versus race condition

These two terms are used interchangeably in casual speech, but they mean different things, and the difference is useful.

Data race
A precise, low-level definition: two threads access the same memory location at the same time, at least one of them writes, and nothing orders the accesses (no lock, no atomic operation). In languages such as C, C++ and Rust (in unsafe code) a data race is undefined behaviour: the compiler and CPU may do anything, and tools such as ThreadSanitizer exist to detect them.
Race condition
A higher-level bug: the program's correctness depends on the timing or ordering of events it doesn't control. The program is wrong for some schedules.

Neither implies the other. The bank example is a race condition, and a data race too, because both threads touch balance unprotected. But consider this version, where a lock protects every single access to balance:

import threading, time

balance = 100
lock = threading.Lock()

def withdraw(amount, who):
    global balance
    with lock:
        enough = balance >= amount      # every access is protected...
    time.sleep(0.01)
    if enough:
        with lock:
            balance -= amount           # ...but the decision outlives the lock
        print(f"{who}: withdrew {amount}")

a = threading.Thread(target=withdraw, args=(80, "A"))
b = threading.Thread(target=withdraw, args=(80, "B"))
a.start(); b.start(); a.join(); b.join()
print("final balance:", balance)
$ python3 lockcheck.py
A: withdrew 80
B: withdrew 80
final balance: -60

There is no data race: every read and write of balance happens under the lock, so no two accesses overlap. Yet there is still a race condition: the decision "enough money" was made in one critical section and acted on in another, so the result depends on the interleaving. Locking each variable is not enough. You have to lock the whole invariant (here, "check and withdraw together"). Chapter 12 does exactly that.

The reverse also exists: two threads that both write the same value True to a "done" flag form a data race by the formal definition, but the program's behaviour doesn't depend on the order, so it isn't a race condition. (In C or C++ it is still undefined behaviour; you shouldn't rely on it.) In Python, a data race on a plain variable can't corrupt the interpreter's memory, so almost all the bugs you'll meet are race conditions of the logical kind.

Go deeper: why "it happened to work" proves nothing optional

Languages with a formal memory model (Java, C++, Go) define when one thread's writes are guaranteed to be visible to another: only through synchronisation such as locks, atomics or channels. Without it, a reader may see an old value, or see writes in a different order than the writer made them, because compilers and CPUs reorder and cache (we return to this in chapter 12). So even a program that has never lost an update in testing may, on a different CPU or compiler version, start to. "No synchronisation, but it works on my machine" is a risk, not a design.

Why races are so hard to catch

A race is a Heisenbug, a bug that seems to vanish or change when you try to observe it. Several things conspire:

  • The window is tiny. The bad order needs a thread switch inside a few nanoseconds of vulnerable time. Most runs never hit it.
  • It depends on timing you don't control: the number of cores, what else is running, CPU frequency, how loaded the server is. A test machine that is quiet and has few cores may never show it.
  • Observing changes timing. Add a print or run under a debugger and the timing shifts enough to hide the bug.
  • It leaves no trace. A wrong number is just a number. There is no exception, no stack trace, no crash to point at.
  • Passing tests proves little. A test that passes a million times might have seen one schedule a million times.

Common misconception

"I ran it 100 times and it was fine, so it's thread-safe." A race that happens once in a billion operations will fail in production within a day for a busy service, and not once in your test. Safety has to come from reasoning (locks, atomics, no sharing), not from observation.

Making a race reproducible

To study a race you want it to happen on demand. The trick is to widen the gap between the read and the write. Here is a counter that deliberately loses updates:

import threading, time

counter = 0

def work(n):
    global counter
    for _ in range(n):
        tmp = counter          # LOAD
        time.sleep(0)          # offer the CPU to another thread
        counter = tmp + 1      # STORE (using a possibly stale value)

threads = [threading.Thread(target=work, args=(10_000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(f"expected 40000, got {counter}  (lost {40000 - counter})")
$ python3 lost.py
expected 40000, got 10000  (lost 30000)
$ python3 lost.py
expected 40000, got 10124  (lost 29876)

time.sleep(0) doesn't wait: it just tells the operating system "let someone else run now", which releases the GIL and invites the other threads in. Right between the load and the store, that's the worst possible moment. The threads then run almost in lockstep: in each round all four read the same value and all four write back that value plus one, so four increments count as one, and about three-quarters of the work vanishes.

Honest note: the plain += loop

You might expect a plain counter += 1 loop with four threads to lose updates too. On recent CPython (I measured 3.14) it very rarely does, and often never, so don't count on it for a demo:

import threading

counter = 0

def work(n):
    global counter
    for _ in range(n):
        counter += 1

threads = [threading.Thread(target=work, args=(1_000_000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print("expected 4000000, got", counter)
$ python3 plain.py
expected 4000000, got 4000000
$ python3 plain.py
expected 4000000, got 4000000

That doesn't mean the code is correct. CPython only checks whether it should switch threads at certain instructions (roughly: function calls and jumps back to the top of a loop), and in this loop the load, add and store sit together with no such check between them, so the window is almost closed. Older versions checked at more kinds of instruction, so people used to see losses here more readily. Different Python versions, other implementations such as PyPy or Jython, free-threaded builds, or slightly more complicated code (a function call between the read and the write, an attribute on an object, a custom __add__) open the window again. You can also try shrinking the interval between switches:

import sys, threading
sys.setswitchinterval(1e-6)
counter = 0
def work(n):
    global counter
    for _ in range(n):
        counter += 1
ts = [threading.Thread(target=work, args=(500_000,)) for _ in range(4)]
for t in ts: t.start()
for t in ts: t.join()
print("expected 2000000, got", counter)

With sys.setswitchinterval(1e-6) (a microsecond instead of the 5 ms default) I still saw 2000000 on 3.14 for the same reason. That's the honest result: the interpreter's design makes this particular bug hard to trigger, not impossible. Hence the technique that does work: put a deliberate sleep(0) or sleep(0.001) in the gap, which is what lost.py, bank.py and lazy.py do. Real-world equivalents: stress tests with many threads and iterations, running tests on machines with more cores, injecting random delays, and tools such as ThreadSanitizer (for C, C++, Go's -race flag, Rust) that watch memory accesses for unordered conflicts.

And here is the same loop with the repair, to compare with lost.py. We'll explain it fully in the next chapter:

import threading, time

counter = 0
lock = threading.Lock()

def work(n):
    global counter
    for _ in range(n):
        with lock:
            tmp = counter
            time.sleep(0)
            counter = tmp + 1

threads = [threading.Thread(target=work, args=(10_000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(f"expected 40000, got {counter}")
$ python3 fixed.py
expected 40000, got 40000

The with lock: block lets only one thread be between the load and the store at a time. The deliberate sleep(0) is still there, but now it can't hurt, because nobody else can enter the block until the lock is released. Lab 3 has you reproduce this race and fix it yourself: Lab 3: Races & Locks.

The same bug across machines

Now replace "thread" with "server" and "variable" with "row in a database". Two web servers handle two purchases of the same item at the same moment. Each does: read the stock from the database, subtract one in its own memory, write the new value back.

This is not hypothetical: it's the classic bug in web applications, and it's easier to hit than the in-process version, because the gap between read and write is milliseconds of network time, not nanoseconds, and the two servers truly run in parallel with no GIL anywhere. Databases give you several remedies, each a cousin of something you'll meet in chapter 12:

  • Do the read-modify-write inside the database as one operation: UPDATE items SET stock = stock - 1 WHERE id = 7. The database applies the arithmetic itself, atomically. This is the "fetch-and-add" idea.
  • Lock the row while you work (SELECT ... FOR UPDATE). This is a lock, held across a network round trip, with all the costs that implies.
  • Optimistic concurrency: read the row with a version number, and write back with WHERE version = 3. If someone else changed it, zero rows match and you retry. This is exactly the compare-and-swap retry loop from chapter 12.
  • Ask the database for stronger isolation (a "serializable" transaction), which makes it behave as though transactions ran one at a time.

"Isolation levels" is a big topic with its own course: the Data Systems course that follows this one explains why a database with the default settings can still lose updates, what "read committed", "snapshot isolation" and "serializable" each guarantee, and what each costs. For now, take away the pattern: any read-then-write that crosses a gap in time is a race, whether the gap is nanoseconds in a CPU or milliseconds across a network.

Distributed systems connection

Everything in this chapter reappears one level up. Two servers reading and writing one row is a lost update. "Check whether the username is free, then create the account" is check-then-act; two sign-ups for the same name both succeed. "If no one holds the job, claim it" without an atomic claim runs a job twice. In distributed systems the interleavings are far more numerous (networking chapter 16: messages can be delayed, duplicated and retried) and there is usually no shared lock to reach for, which is why the field has invented transactions, idempotency keys, version numbers and consensus (networking chapter 20). The Data Systems course will pick up from here with isolation levels.

Key takeaways

  • counter += 1 on shared data is three steps (load, add, store). A thread switch between them can make a thread write back a stale value: a lost update.
  • The GIL does not make your multi-step operations atomic. It only protects the interpreter's internals.
  • Two threads of n steps have C(2n, n) interleavings: 20 for three steps, and rapidly astronomical. You can't test them all; you must reason about all of them.
  • Check-then-act (bank balance, "create if missing", lazy init, TOCTOU) and read-modify-write are the same bug in different clothes. The fix is to make check and act one indivisible step.
  • A data race is unordered conflicting memory access; a race condition is correctness depending on timing. Locking every variable can remove data races yet leave race conditions.
  • Races are Heisenbugs: rare, timing dependent and silent. To reproduce one, widen the gap (sleep(0)); to prevent one, use synchronisation, not hope.
  • The same pattern appears between servers and a database as a lost update; the cure is atomic operations, locks, versioning or stronger isolation.

Check your understanding

Two threads each run counter += 1 once on a shared counter that starts at 0. Which final values are possible?

  1. Only 2
  2. 1 or 2
  3. 0, 1 or 2
  4. Only 1
If the two run one after the other the answer is 2. If both load 0 before either stores, both write 1, and one update is lost. 0 is impossible, because each thread stores at least 1. The interleaving explorer above shows 18 of 20 orders giving 1.

Why doesn't CPython's GIL make counter += 1 safe?

  1. The GIL only works on Linux
  2. The GIL is released at the start of every function
  3. Adding integers isn't done by the interpreter
  4. The GIL makes each single bytecode uninterrupted, but a thread can lose the GIL between the load and the store bytecodes
The operation is several bytecodes (load, add, store). The GIL doesn't promise a thread keeps running from one bytecode to the next, so the value loaded can be stale by the time it is stored.

A program locks every individual read and write of balance, but checks balance >= amount in one locked block and subtracts in another. What is true?

  1. It has no data race but still has a race condition
  2. It has a data race but no race condition
  3. It has neither
  4. It has both
No two accesses to balance overlap, so there's no data race. But the check and the act aren't one atomic step, so two withdrawals can both pass the check, and the result depends on timing: a race condition.

Why can a test suite that passes thousands of times still hide a race condition?

  1. Tests always run on a single core
  2. Race conditions only occur in production code, never in tests
  3. The bad interleaving may need a thread switch in a tiny window, so most runs never hit it
  4. Races always raise an exception that tests catch
The vulnerable window is tiny, depends on timing and load, and leaves no error behind. A bug that triggers once in a billion operations passes any reasonable test and still fails in production. Deliberate delays, stress tests and race detectors help; repeated passing doesn't prove safety.

Two web servers each read a row's value (10), subtract 1 and write 9. What is this, and what's the best simple fix?

  1. A deadlock; add more servers
  2. A lost update; do the arithmetic inside the database in one atomic statement (stock = stock - 1), or use a version check or stronger isolation
  3. A TCP retransmission; increase the timeout
  4. Not a bug, because databases never lose writes
It's the same lost update as the in-process counter, with a network-sized gap between read and write. Moving the read-modify-write into one atomic database operation (or protecting it with a lock, a version number or serializable isolation) closes the gap.

In open(path, "x"), what does the "x" mode accomplish compared with if not os.path.exists(path): open(path, "w")?

  1. It makes the file read-only
  2. It encrypts the file
  3. It makes "fail if the file exists, otherwise create it" a single atomic operation in the operating system, closing the check-then-act gap
  4. It speeds up the check
Separate check and create steps leave a gap in which another thread or process can create the file (TOCTOU). Exclusive creation lets the OS do both as one indivisible step and report an error if you lost the race.

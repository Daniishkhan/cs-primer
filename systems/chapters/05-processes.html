Processes

A process is a program in motion: it has a number, a private memory, a set of open files and a state. This chapter follows its whole life: how it is born with fork, how it turns into a different program with exec, how it dies and is cleaned up, and how other programs can ask it, politely or rudely, to stop.

Why this matters

Everything you deploy is a process, and everything that supervises it (a shell, systemd, Docker, Kubernetes) is doing the same few things: starting processes, watching them, and sending them signals. Knowing what a zombie is, why kill -9 is a last resort, why a container takes ten seconds to stop, or what exit code 137 means will save you real debugging hours. The mechanisms here are also the foundation of the shell you'll build in Lab 1.

Program vs process

A program is a file: machine code and data sitting on disk, like a recipe in a book. It does nothing by itself. A process is what you get when the operating system takes that file and runs it: the kernel creates a bookkeeping record, gives it memory, connects it to some files, and lets the CPU execute its instructions. Recipe versus a cook who is currently making the dish. You can run the same program many times at once, and each run is a separate process. Open three terminal windows and you have three zsh processes from one program file.

Each process gets, from the kernel:

  • A process ID (PID): a unique number, such as 4242, used to refer to it in tools like ps and kill. It also records its parent's PID (PPID).
  • Its own address space: a private view of memory holding its code, heap and stack. Two processes can both use address 0x1000 and mean different bytes (the full story is chapter 6).
  • A table of open files (file descriptors): numbers 0, 1 and 2 are by convention standard input, standard output and standard error. Sockets and pipes live in the same table (chapter 8).
  • An environment: a list of NAME=value strings such as PATH and HOME, a copy of which every child inherits.
  • CPU state (registers and the program counter, saved while it isn't running), plus a scheduling state, a working directory, a user identity and more.

Analogy: recipe and cook

In the kitchen from chapter 0, a program is a recipe card. A process is a cook with that card in hand, with a dedicated station, a set of pans (open files) and a ticket number (PID). Ten cooks can work from the same recipe card without interfering, because each has a station of their own.

Where it breaks down: a cook starts by reading the card, but a process starts as an exact copy of another process (via fork, below) and only later swaps in a new recipe with exec. There is no real-world equivalent of cloning a cook and then handing the clone a different recipe.

The three states of a process

A process isn't always running. There are usually far more processes than CPU cores (the ps aux | wc -l in chapter 0 showed hundreds), so each is, at any moment, in one of three broad states:

  • Running: executing instructions on a core right now.
  • Ready (runnable): could run immediately if it had a core, and is waiting its turn in the scheduler's queue.
  • Blocked (waiting, sleeping): can't make progress until something happens, such as a disk read finishing, a network packet arriving, a timer firing, or another process ending. The scheduler ignores it, so it uses no CPU.

Tools show these states with a letter. In ps's STAT column, R means running or runnable, S is a (blocked) sleep, T is stopped, and Z is zombie. Linux also has D, an uninterruptible sleep, usually waiting on disk, that even kill -9 can't interrupt. Almost every process on an idle machine is S: waiting. That is normal and healthy, and it is the key to the "waiting" theme of this course.

Birth: fork, exec, wait

On Unix systems (Linux, macOS, the BSDs) processes are created in a distinctive way, using two system calls that each do only one thing.

  • fork() clones the calling process. The kernel makes a near-identical copy: same code, same variables, same open files, same environment, same current position in the program. The original is the parent and the copy is the child. The child differs in only one meaningful way: fork() returns twice. In the parent it returns the child's PID; in the child it returns 0. That's how each copy knows which one it is.
  • exec() replaces the current program. The process throws away its code and memory and loads a different program in its place. The PID, the parent and (importantly) the open files stay the same. If exec succeeds it never returns, because the code that called it no longer exists.
  • wait() / waitpid() lets the parent wait for a child to finish and collect its exit status.

Why two steps instead of one "run this program" call? Because the gap between them is where all the useful tricks happen. After fork but before exec, the child can rearrange its own file descriptors, so the program it will become inherits a different stdin or stdout. That is how shells do redirection (> file) and pipes (|) without any help from the program being started. Step through the whole life of an ls command:

Step through

fork, exec and wait: running ls from a shell

  1. The shell calls fork(). You typed ls -l and pressed Enter. The shell (PID 100) wants to run a different program but not become that program, because it needs to be there for your next command. So it first asks the kernel to clone it.
  2. fork returns twice. The kernel created a child (PID 101): a copy of the shell with the same code, variables and open files. In the parent fork() returned 101; in the child it returned 0. Memory isn't really copied yet. Parent and child share the same pages until one writes to them (copy-on-write, chapter 6), which is why fork is cheap.
  3. The two copies diverge. Both are running the same code, but an if pid == 0 sends them down different paths. The parent calls waitpid(101) and goes to sleep (blocked, using no CPU). The child is about to call exec.
  4. The child execs. The kernel loads /bin/ls into the child, replacing its code, heap and stack. It's now a completely different program, but it is still PID 101, still the parent's child, and its open files (0, 1, 2) are exactly what it had before. (If the shell wanted ls > out.txt, it would have pointed fd 1 at a file just before this step.)
  5. ls does its job, then exits. It writes its listing to fd 1, the terminal, and calls exit(0). The kernel frees its memory and closes its files, but keeps a tiny record holding the PID and the exit status. The child is now a zombie: dead, but not yet collected.
  6. The parent wakes and collects. The kernel wakes the sleeping parent (and also sends it a SIGCHLD signal, see below). waitpid returns with the child's PID and its exit status, and the kernel finally deletes the zombie record. The shell prints a new prompt and waits for you.

The same thing in Python

Python exposes these calls in the os module (on macOS and Linux only; Windows has no fork). This is the whole loop from the figure:

import os

pid = os.fork()                       # returns TWICE: 0 in the child, the child's PID in the parent
if pid == 0:
    # ---- child ----
    os.execvp("ls", ["ls", "-l"])     # replace this process with the ls program
    os._exit(127)                     # only reached if exec failed (e.g. command not found)
else:
    # ---- parent ----
    _, status = os.waitpid(pid, 0)    # sleep until the child ends, collect its status
    if os.WIFEXITED(status):
        print("child", pid, "exited with code", os.WEXITSTATUS(status))
    else:
        print("child", pid, "was killed by signal", os.WTERMSIG(status))

Note os._exit(127) in the child: after a failed exec you must leave immediately, without running Python's normal cleanup, because the child is a copy of the parent and would otherwise flush the parent's buffers a second time. (On Python 3.9+ there is also os.waitstatus_to_exitcode(status).)

fork has sharp edges

Threads. Only the thread that called fork() exists in the child. If another thread held a lock at that moment, the child inherits a lock that nobody will ever release. Python 3.12+ emits a DeprecationWarning when you fork a process that has several threads, for this reason. Fork first, start threads afterwards (chapter 10).

macOS. fork() works, but many Apple system libraries aren't safe to use in a forked child that doesn't call exec. That is why Python's multiprocessing has used the "spawn" start method (fresh interpreter) by default on macOS since 3.8. The fork-then-exec pattern in this chapter is safe everywhere.

Death: exit codes, zombies and orphans

When a process ends, it leaves an exit status, a small number from 0 to 255. By universal convention 0 means success and anything else means failure; programs choose their own non-zero values (grep uses 1 for "no match" and 2 for "error", for example). A shell shows the last command's status in $?. If a process was ended by a signal, the shell reports 128 + signal number: 130 means killed by SIGINT (Ctrl-C), 137 by SIGKILL (9), and 143 by SIGTERM (15). When you see 137 in a container's logs, someone sent it SIGKILL, very often the kernel's out-of-memory killer (chapter 6).

The exit status isn't delivered to a mailbox that might be missing; it has to be fetched by the parent, through wait. That produces two famous edge cases.

  • Zombie. A child has exited, but its parent hasn't called wait yet. The kernel can't free the child's last bit of bookkeeping (the PID and the exit status) because the parent may still ask for them. A zombie uses no CPU and almost no memory, but it holds a PID. A server that forks children and never waits for them leaks zombies until it runs out of PIDs. The fix is for the parent to wait (often in a SIGCHLD handler), or to exit. You can't kill a zombie, as it is already dead; you reap it by getting its parent to wait, or by ending the parent.
  • Orphan. The parent exits first. The child keeps running, but its parent is gone, so the kernel re-parents it to PID 1 (the first process, init, systemd or launchd), which reaps adopted children when they exit. This is how daemons are born: fork, let the parent exit, and the child is now independent of the terminal.

The process tree

Because every process except the very first is created by a parent, processes form a tree. At boot the kernel starts exactly one process, PID 1, and every other process descends from it.

Signals: tapping a process on the shoulder

How do you tell a running process to stop, reload its config or notice that a child finished? Not through a function call: it is a separate program. The mechanism is the signal: a tiny numbered notification the kernel delivers to a process. The process can have a handler function that runs when the signal arrives, or can leave the default action (usually "terminate"). Think of it as the process's version of an interrupt (chapter 4). Signals are sent by the kernel (a crash, a child exiting, Ctrl-C at the terminal) or by other processes with the kill system call and command, whose name is misleading, since it only sends a signal.

SIGTERM (15)"Please shut down": the default of kill PID, systemctl stop, docker stop, Kubernetesterminateyes. This is how you shut down gracefully.
SIGKILL (9)kill -9, the OOM killer, the last resortterminate immediatelyno. The kernel ends the process; it never gets to run any code.
SIGHUP (1)The terminal closed ("hang up"). Daemons often reuse it to mean "reload your config".terminateyes

(SIGSTOP pauses a process and, like SIGKILL, cannot be caught.) Here is a program that handles two of them:

import os, signal, time

stop = False

def request_stop(signum, frame):
    global stop
    stop = True                       # just set a flag; do the real cleanup in the main loop

signal.signal(signal.SIGTERM, request_stop)
signal.signal(signal.SIGINT, request_stop)

print("PID", os.getpid(), "working; send me SIGTERM or press Ctrl-C")
while not stop:
    time.sleep(0.5)                   # pretend to serve requests
print("finishing in-flight work, flushing logs ...")
time.sleep(1)
print("clean exit")

Python runs signal handlers in the main thread, between bytecode instructions, and a handler should do as little as possible. Setting a flag and letting the main loop notice it is the safest pattern. The same idea works in every language.

Common misconception

"kill -9 is the proper way to stop a program." It is the way to stop a program that won't stop. SIGKILL gives the process no chance to flush buffers, finish a write, release a lock file, close connections cleanly or tell anyone it's leaving. Always try SIGTERM first and give it time. If you find yourself reaching for -9 regularly, the program's shutdown handling is the bug.

Graceful shutdown, and why servers and containers care

Servers are stopped all the time: at every deploy, scale-down, node drain and restart. A graceful shutdown means that on SIGTERM the server (1) stops accepting new connections, (2) lets in-flight requests finish, (3) flushes buffers and logs, closes database connections, and then (4) exits with code 0. Done well, nobody notices the restart. Done badly, users see dropped requests and half-finished writes.

This is exactly what docker stop and Kubernetes do: SIGTERM, wait, then SIGKILL. There is a classic trap in containers. The process started by the container becomes PID 1 inside its own PID namespace, and Linux gives PID 1 special treatment: signals with a default "terminate" action are ignored unless the process installed a handler. So a program that works fine under Ctrl-C on your laptop may ignore SIGTERM in a container, and each stop then takes the full grace period before the SIGKILL. The fixes are to handle SIGTERM explicitly, or to run a tiny init process (docker run --init) that forwards signals and reaps zombies. Containers are chapter 19.

A shell is a fork/exec/wait loop

You now know enough to understand the program you type commands into. A shell, stripped of its conveniences, is this:

import os

while True:
    line = input("$ ")                       # 1. read a command
    argv = line.split()
    if not argv:
        continue
    pid = os.fork()                          # 2. clone ourselves
    if pid == 0:
        try:
            os.execvp(argv[0], argv)         # 3. child becomes the program
        except OSError:
            print(argv[0] + ": command not found")
            os._exit(127)
    else:
        os.waitpid(pid, 0)                   # 4. parent waits, then loops

That really is the core. Everything else a shell does is built on top: wildcards, quoting, variables, & for background jobs (just don't wait), and Ctrl-C handling. One consequence: cd must be a built-in command. If it ran as a child program it would change the child's working directory and vanish, leaving the shell where it was. It has to change the shell's own process.

Pipes preview

How does ls | wc -l count your files? The shell creates a pipe (a small buffer inside the kernel, with a write end and a read end) before forking. It forks twice; in the first child it points fd 1 (stdout) at the pipe's write end and execs ls; in the second it points fd 0 (stdin) at the read end and execs wc -l. Neither program knows about the other. Each just reads or writes the "standard" descriptors it was born with.

You'll build all of this, plus redirection and Ctrl-C handling, in Lab 1: A Mini Shell.

Distributed systems connection

A process is the unit of failure in a distributed system. When we say "a node crashed" we almost always mean "a process exited, or was killed". Everything that keeps services alive is built from this chapter. A supervisor (systemd, Kubernetes, a process manager) is a parent that forks the service, waits for it, reads the exit code, and restarts it. The exit code and the signal tell it whether the exit was a clean stop or a crash.

Graceful shutdown is what makes rolling deploys possible: SIGTERM, drain, exit, while the load balancer (networking chapter 14) stops sending new traffic to the node. And SIGKILL is what failure looks like: no warning, no cleanup, which is why the failure handling in networking chapter 16 (timeouts, retries, idempotent operations) must assume a peer can vanish between any two messages.

Key takeaways

  • A program is a file; a process is a running instance with a PID, a private address space, open files, an environment and a state (running, ready, blocked).
  • fork clones the process and returns twice; exec replaces its program while keeping PID and open files; wait collects the exit status. A shell is this loop.
  • The gap between fork and exec is where redirection and pipes are set up, by rearranging the child's file descriptors.
  • Exit code 0 means success. Killed-by-signal shows as 128 + signal number (137 for SIGKILL, 143 for SIGTERM).
  • A zombie is a dead child whose parent hasn't called wait; an orphan is a live child whose parent died and which PID 1 adopts.
  • Signals are asynchronous notifications. SIGTERM can be handled and is the polite request; SIGKILL cannot be caught and is the last resort.
  • Graceful shutdown (stop accepting, drain, flush, exit) is what lets deploys and container stops happen without losing work. In containers, PID 1 needs an explicit SIGTERM handler.

Check your understanding

After a successful fork(), the parent and child both continue from the same point in the code. How does each know which one it is?

  1. The child has a lower PID
  2. fork() returns the child's PID in the parent, and 0 in the child
  3. The kernel sets a global variable called is_child
  4. Only the parent continues; the child waits for exec
fork returns twice, with different values, so a simple if pid == 0 separates the two paths. Both copies really do continue running the same code from the same spot.

What does a successful exec change about the calling process?

  1. It gets a new PID
  2. It closes all open files
  3. It creates a second process running the new program
  4. Its code and memory are replaced by a new program, while the PID and open file descriptors stay the same
exec doesn't create anything. It transforms the existing process. Because open files survive it, a shell can redirect stdout between fork and exec, and the new program writes into the file without knowing.

A server shows hundreds of processes in state Z in ps. What is wrong, and how do you fix it?

  1. Its children have exited but the parent never calls wait(); the parent should reap them (for example in a SIGCHLD handler) or exit
  2. The children are using too much CPU; send them SIGKILL
  3. The children are blocked on disk; add more RAM
  4. Nothing: zombies are the normal state of idle workers
A zombie is already dead, so SIGKILL does nothing to it. It disappears only when its parent collects the exit status with wait, or when the parent itself exits and PID 1 adopts and reaps them.

You run docker stop on a container and it always takes exactly the full grace period before dying, then reports exit code 137. What is the most likely cause?

  1. Docker is slow to deliver signals
  2. The program crashed with a segmentation fault
  3. The program (running as PID 1 in the container) has no SIGTERM handler, so it ignores SIGTERM and is finally killed by SIGKILL (128 + 9)
  4. 137 means the program exited successfully
PID 1 in a container doesn't get the default "terminate" action for signals; without a handler SIGTERM is ignored. After the timeout the runtime sends SIGKILL, which shows up as 137. Installing a SIGTERM handler, or using a small init such as --init, fixes it.

Why can't a program catch or ignore SIGKILL?

  1. Because Python doesn't support it
  2. Because it guarantees that an administrator can always end a misbehaving process: the kernel acts on it directly, without running the process's code
  3. Because SIGKILL is delivered only to zombie processes
  4. Because it is handled by the shell, not the kernel
If a process could catch every signal, a buggy or malicious one could make itself unkillable. SIGKILL (and SIGSTOP) are therefore handled by the kernel itself. The price is that the process gets no chance to clean up, which is why SIGTERM comes first.

Async/Await & Coroutines

Event loops are efficient, but writing code as a chain of callbacks is miserable. Async/await lets you write straight-line code that the event loop quietly slices into pieces. This chapter shows what is really going on underneath the keywords, how to use them in Python, and the one golden rule that still applies: never block the loop.

Why this matters

Most new network code in Python, JavaScript, Rust, C#, Kotlin and Swift is written with async/await. It is how people write a service that makes five calls to other services and handles ten thousand clients at once, without a thread for each. It is also the source of a very common bug: one innocent-looking blocking call inside an async def that freezes the whole server. If you understand that await is just "pause here and let the event loop run something else", both the power and the pitfalls become obvious.

The problem: callbacks hurt

In chapter 16 every piece of work was a callback: "when socket 7 is readable, call this function". That is fine for an echo server. Now imagine a request handler that must read a request, look something up in a database, render a page and send it. Each step takes time, so each becomes "do this, and when it's done call that". The code nests deeper with each step. This is the infamous callback hell:

def handle(conn):
    read_request(conn, lambda req:
        db_lookup(req.user, lambda user:
            render(user, lambda page:
                send(conn, page, lambda _:
                    log_done(conn)))))

Error handling is worse: where does a failure in db_lookup go? Each callback needs its own error path, loops (retry three times) turn into recursion, and the order of operations is no longer the order of lines. The async/await version of the same logic reads like the blocking code we started with:

async def handle(conn):
    req = await read_request(conn)
    user = await db_lookup(req.user)
    page = await render(user)
    await send(conn, page)
    log_done(conn)

Each await says: "this step might take a while: pause me here, let the loop do other things, and resume me with the result when it's ready". The code reads top to bottom, try/except and for loops work as normal, and yet nothing blocks. How is that possible? The answer is a very old idea.

Generators: functions that can pause

A normal function runs from start to finish and then it is gone. A generator is a function that can pause in the middle with yield, hand a value to its caller, and later be resumed exactly where it stopped, with all its local variables intact. Its stack frame is kept alive on the heap instead of being thrown away (chapter 3).

def countdown(n):
    while n > 0:
        yield n          # pause here, hand n to the caller
        n -= 1
    return "liftoff"

g = countdown(3)
print(next(g))   # 3
print(next(g))   # 2
print(next(g))   # 1
try:
    next(g)
except StopIteration as e:
    print("finished:", e.value)
3
2
1
finished: liftoff

A coroutine is the general name for a function that can be suspended and resumed, and a generator is the simplest example. Notice who is in control: the caller decides when to resume it. Now swap the roles. What if the thing yielding is a job that says, "I'm waiting for 1 second, wake me then", and the thing calling next() is an event loop with a heap of timers? Here is a complete, runnable toy built from exactly that:

import heapq
import itertools
import time


def sleep(seconds):
    yield seconds                   # "wake me in this many seconds"


def job(name, delay):
    print(f"{time.perf_counter() - T0:.1f}s  {name} starts")
    yield from sleep(delay)         # pause here; the loop runs someone else
    print(f"{time.perf_counter() - T0:.1f}s  {name} finishes")


def run(*coros):
    ready = list(coros)             # coroutines that can run right now
    timers = []                     # heap of (wake_time, tie_breaker, coroutine)
    tie = itertools.count()
    while ready or timers:
        while ready:
            co = ready.pop(0)
            try:
                delay = next(co)    # run until the next yield
            except StopIteration:
                continue            # this coroutine is finished
            heapq.heappush(timers, (time.monotonic() + delay, next(tie), co))
        if timers:
            wake, _, co = heapq.heappop(timers)
            time.sleep(max(0, wake - time.monotonic()))   # the "wait" step
            ready.append(co)


T0 = time.perf_counter()
run(job("A", 2), job("B", 1))
0.0s  A starts
0.0s  B starts
1.0s  B finishes
2.0s  A finishes

Two jobs, taking 2 s and 1 s, finish after 2 s in total, not 3. They overlapped, on one thread, because each one handed control back at its pause point. (The toy loop calls time.sleep for its own wait. A real loop waits in epoll/kqueue so that sockets can wake it too, as in chapter 16.) Python's async def and await are this same idea given proper syntax, with await in the role of yield from, so that coroutines are a distinct type that cannot be confused with ordinary generators.

Analogy: one cook, several dishes

In the restaurant kitchen, a single cook can make three dishes at once. Put the pasta on to boil (an await: nothing for the cook to do until it's ready), chop vegetables for the second dish, check the oven for the third, then return to the pasta when the timer rings. The cook's hands are always busy even though most steps involve waiting. The dish being cooked is a coroutine; the cook's habit of "start it, set a timer, move on" is the event loop.

Where it breaks down: a coroutine can only pause at an await; a human cook can switch at any moment. Our cook never abandons a chopping task in mid-slice. If one task takes ten minutes of non-stop chopping, no pot gets watched in the meantime.

async def and await in Python

In Python, async def defines a coroutine function. Calling it does not run the body: it returns a coroutine object, a parked function waiting to be started. Something must schedule it. The usual entry point is asyncio.run(main()), which creates an event loop (the very thing from chapter 16: a selector plus a heap of timers), runs main() to completion, and shuts the loop down. Inside coroutines, await x pauses the current coroutine until x is done.

To run several coroutines at the same time, wrap each in a task (asyncio.create_task(coro)), which tells the loop "start running this on your own schedule". asyncio.gather(*coros) does that for a group and waits for all of them, returning their results in order. Here is the claim from the start of this chapter, made concrete: a thousand tasks, each waiting one second.

import asyncio
import time


async def worker(i):
    await asyncio.sleep(1)          # pretend this is a network call
    return i


async def main():
    start = time.perf_counter()
    results = await asyncio.gather(*(worker(i) for i in range(1000)))
    elapsed = time.perf_counter() - start
    print(f"{len(results)} tasks finished in {elapsed:.2f} s")


asyncio.run(main())
1000 tasks finished in 1.01 s

A thousand one-second waits took one second, with one thread. Each asyncio.sleep(1) registered a timer in the loop's heap and parked its task, costing a few hundred bytes to a few kilobytes of heap memory and no thread stack. If these were network calls instead of sleeps, 1,000 requests could be in flight at once, which is why async clients are good at "fan out to many backends" work.

Stepping through two coroutines

Here is the same thing in slow motion: two coroutines, A awaiting a 2-second sleep and B awaiting a 1-second sleep, started together with gather. The runs themselves take microseconds, so they're drawn wider than true scale.

Step through

Two coroutines interleaving at await points

  1. gather() creates two tasks. Both coroutines are now in the loop's ready queue. Nothing has run yet.
  2. The loop runs A until it reaches await asyncio.sleep(2). That call registers a timer 2 s ahead and parks A. A's local variables are kept; the thread is free.
  3. The loop runs B the same way, until await asyncio.sleep(1): a timer 1 s ahead, and B is parked.
  4. Nothing is ready, so the loop waits. It asks the selector to sleep, with a timeout of 1 s, the time until the earliest timer. The thread uses no CPU.
  5. One second passes. B's timer is due; the loop resumes B right after its await. B finishes. (Its result is stored for gather.)
  6. Waiting again, for another second: the only remaining timer is A's.
  7. Two seconds. A is resumed and finishes. gather() has all its results and returns. Total time: 2 s, the slowest task, not 1 + 2 = 3 s.

Futures and promises: a value that will exist later

What does await x actually wait for? For something that represents a result that isn't available yet. That something is called a future (JavaScript and other languages call it a promise): an object that starts empty and is later filled in with either a result or an error. Anyone holding it can ask "are you done yet?", attach a callback, or await it. It is the bridge between the callback world of chapter 16 and the straight-line world of this chapter.

import asyncio


async def main():
    loop = asyncio.get_running_loop()
    fut = loop.create_future()                  # an empty promise: no value yet
    loop.call_later(0.5, fut.set_result, "the answer")   # someone fills it in later
    print("waiting for the future...")
    print("got:", await fut)                    # pause here until set_result is called


asyncio.run(main())
waiting for the future...
got: the answer

A task is a future with a job: it runs a coroutine and, when the coroutine finishes, stores its return value (or exception) in itself. asyncio.sleep, a socket read, and "this other task is finished" can all be awaited because each one is, or wraps, a future that something will complete later: a timer, the selector reporting a readable socket, or another task. Compare this with chapter 14, where a thread-pool future played the same role: a placeholder for a result that a worker produces. It's the same concept; only the thing that fills it in differs.

Common misconception

"Calling an async def function runs it." It doesn't. It returns a coroutine object that does nothing until awaited or scheduled as a task. Writing greet() without await doesn't run greet; Python only warns you afterwards: RuntimeWarning: coroutine 'greet' was never awaited. Also, await doesn't make anything faster by itself. await fetch(a) followed by await fetch(b) runs them one after the other. To overlap them, start both as tasks or use gather.

Function colouring

There is a catch to this design, often called function colouring (from Bob Nystrom's essay "What Color is Your Function?"). An async def function can only be awaited from inside another async def. A plain function cannot use await. So the two kinds don't mix freely:

  • If one function deep in your call chain becomes async, every caller above it must become async too (or must explicitly bridge, e.g. with asyncio.run(), which can be done once, at the very top, and never from inside a running loop).
  • If an async function calls an ordinary function that blocks (a normal HTTP library, a synchronous database driver), it compiles and runs, but it silently freezes the loop. The language does not warn you. That is the central danger of the next section.

The practical consequence: async is a decision for a whole program or a whole layer, not something you sprinkle on. The alternatives, such as goroutines in Go, avoid the split by letting any function block cheaply (chapter 18), at the price of a heavier runtime.

Blocking the loop by mistake

The cardinal rule from chapter 16 still holds: while any coroutine runs between two awaits, nothing else in that loop runs. Compare await asyncio.sleep(1), which parks the task and lets others run, with time.sleep(1), which holds the thread for a second. This program has a "heartbeat" coroutine that should tick every 0.2 s, running next to a coroutine that waits one second in two different ways:

import asyncio
import time


async def heartbeat():
    """Should print every 0.2 s."""
    t0 = time.perf_counter()
    for _ in range(8):
        await asyncio.sleep(0.2)
        print(f"  heartbeat at {time.perf_counter() - t0:.1f} s")


async def bad():
    await asyncio.sleep(0.3)
    print("  bad(): calling time.sleep(1.0), the loop is now frozen")
    time.sleep(1.0)                 # BLOCKS the whole event loop
    print("  bad(): done")


async def good():
    await asyncio.sleep(0.3)
    print("  good(): awaiting asyncio.to_thread(time.sleep, 1.0)")
    await asyncio.to_thread(time.sleep, 1.0)   # runs in a worker thread
    print("  good(): done")


async def run(label, coro):
    print(label)
    await asyncio.gather(heartbeat(), coro)


async def main():
    await run("with time.sleep:", bad())
    await run("with to_thread:", good())

asyncio.run(main())

  bad(): calling time.sleep(1.0), the loop is now frozen
  bad(): done
  heartbeat at 1.3 s
  heartbeat at 1.5 s
  heartbeat at 1.7 s
  heartbeat at 1.9 s
  heartbeat at 2.1 s
  heartbeat at 2.3 s
  heartbeat at 2.5 s
with to_thread:
  heartbeat at 0.2 s
  good(): awaiting asyncio.to_thread(time.sleep, 1.0)
  heartbeat at 0.4 s
  heartbeat at 0.6 s

  heartbeat at 1.4 s

In the first run the heartbeat is silent between 0.2 s and 1.3 s: the beats that should have come at 0.4, 0.6, 0.8, 1.0 and 1.2 s never happened, because the loop had no chance to run them. In the second run, the blocking sleep happens in a different thread, so the loop keeps ticking. In a real server, "heartbeat" could be every other client.

The tool for this is asyncio.to_thread(fn, *args) (Python 3.9+), or on older versions loop.run_in_executor(None, fn, *args): run an ordinary blocking function in a thread pool and await the result. It is the "kitchen" from chapter 16, and the same pool ideas from chapter 14 apply: the pool is bounded, so too much blocking work will queue up. Two limits are worth knowing:

  • Threads help with waiting (blocking I/O, most disk and database drivers, C extensions that release the GIL). They do not help with pure-Python CPU work, because the GIL lets only one thread run Python bytecode at a time (chapter 10). For heavy computation use a process pool: loop.run_in_executor(concurrent.futures.ProcessPoolExecutor(), fn, ...).
  • The best fix is often to use a library that is truly async (written in terms of await), so no thread is needed at all.

Cancellation and timeouts

Because waiting is a first-class operation, so is giving up. A task can be cancelled: task.cancel() asks the loop to raise asyncio.CancelledError inside the coroutine at the point where it is currently paused. The coroutine can use try/finally to clean up, and must re-raise the error afterwards (swallowing it breaks cancellation for everyone above). Cancellation only takes effect at an await; a coroutine in a busy loop can't be cancelled, another consequence of the cooperative design.

Every call that waits on something outside your control should have a time limit. Python offers two ways:

import asyncio


async def slow():
    await asyncio.sleep(10)


async def main():
    try:
        async with asyncio.timeout(0.5):              # Python 3.11+
            await slow()
    except TimeoutError:
        print("timed out after 0.5 s; slow() was cancelled")
    try:
        await asyncio.wait_for(slow(), timeout=0.5)   # works on 3.8+
    except asyncio.TimeoutError:
        print("wait_for timed out too")


asyncio.run(main())
timed out after 0.5 s; slow() was cancelled
wait_for timed out too

Under the hood a timeout is just a timer in the loop's heap that, when it fires, cancels the task. (On Python 3.11 and newer, asyncio.TimeoutError is the same thing as the built-in TimeoutError.)

Structured concurrency

Plain create_task has a hazard: you can start a task and forget about it. It may fail with nobody watching, or outlive the code that started it. Structured concurrency is the idea that concurrent tasks should live inside a scope, like a block of code, and the scope doesn't end until all its tasks have. In Python 3.11+ that is asyncio.TaskGroup:

import asyncio


async def ok(name):
    try:
        await asyncio.sleep(5)
    except asyncio.CancelledError:
        print(f"{name}: cancelled, cleaning up")
        raise                                    # always re-raise CancelledError


async def boom():
    await asyncio.sleep(0.1)
    raise ValueError("something broke")


async def main():
    try:
        async with asyncio.TaskGroup() as tg:    # Python 3.11+
            tg.create_task(ok("task 1"))
            tg.create_task(ok("task 2"))
            tg.create_task(boom())
    except* ValueError as eg:
        print("group failed:", eg.exceptions)


asyncio.run(main())
task 2: cancelled, cleaning up
task 1: cancelled, cleaning up
group failed: (ValueError('something broke'),)

When one task in the group fails, the others are cancelled, and the async with block raises (as an ExceptionGroup, caught with except*). Nothing is left running in the background by accident. The order of the two "cancelled" lines may vary between runs. On Python 3.8 to 3.10 you do not have TaskGroup, so use gather and handle errors and cancellation yourself.

Distributed systems connection

Futures and promises are how programs talk about remote calls: when you call another service, you get back "a result that will exist later, or an error, or never". That "never" is why timeouts and cancellation are not optional extras but part of the basic shape of the API. Structured concurrency gives the same safety to fan-out calls: if one of five parallel backend requests fails, the other four are cancelled instead of leaked. Cheap concurrency also means a bug can send a lot of requests very quickly; a retry loop with thousands of tasks can flatten a struggling backend (networking chapter 16), so you still need limits and backpressure (chapter 14), for instance asyncio.Semaphore to cap how many requests are in flight.

Key takeaways

  • Callback chains are hard to read and handle errors badly. Async/await lets you write straight-line code that the event loop runs in pieces.
  • A coroutine is a function that can pause at await points and resume with its local state intact. Generators (yield) are the underlying idea.
  • Calling an async def function only creates a coroutine object. Run it with await, asyncio.run or as a task. Use gather or tasks to overlap work: 1,000 one-second waits finish in about a second.
  • A future/promise is a placeholder for a value that will exist later; a task is a future that runs a coroutine.
  • Async functions can only be awaited from async code ("function colouring"). A blocking call such as time.sleep inside a coroutine freezes the whole loop; use await asyncio.sleep, a truly async library, or asyncio.to_thread/run_in_executor.
  • Cancellation arrives as CancelledError at an await. Always put timeouts on waits (asyncio.timeout on 3.11+, wait_for otherwise), and prefer TaskGroup (3.11+) so no task is left running by accident.

Check your understanding

What does await do inside a coroutine?

  1. It blocks the whole thread until the result is ready
  2. It starts a new operating-system thread for the call
  3. It pauses this coroutine, lets the event loop run other work, and resumes this coroutine when the awaited result is ready
  4. It makes the called function run faster
The thread is not blocked: control returns to the event loop, which runs other tasks and timers. The awaiting coroutine is resumed later, with its local variables intact.

A coroutine calls time.sleep(2) in an asyncio server. What happens?

  1. The entire event loop is frozen for 2 seconds: no other task or timer runs
  2. Only that coroutine pauses; other tasks continue normally
  3. Python automatically converts it into asyncio.sleep
  4. It raises an error because blocking calls are forbidden in async functions
Nothing stops you from calling a blocking function in an async def; it just holds the one thread that runs the loop. Use await asyncio.sleep(2) or push the blocking work to asyncio.to_thread.

You write a = await fetch(1) then b = await fetch(2), each taking 1 s. How long does it take, and how could it be faster?

  1. 1 s, because await runs them concurrently
  2. 2 s, and it can't be made faster
  3. 0 s, because they run in the background
  4. 2 s; start both as tasks or use asyncio.gather(fetch(1), fetch(2)) to overlap them for about 1 s
Each await waits for its operation to finish before the next line runs. Concurrency comes from having several tasks in the loop, not from the keyword itself.

Why does asyncio.to_thread not speed up a pure-Python function that crunches numbers for 3 seconds?

  1. Threads cannot run Python code at all
  2. It keeps the loop responsive, but the GIL prevents threads from running Python bytecode in parallel; for CPU-bound work use a process pool
  3. to_thread is only for network sockets
  4. It does speed it up on every machine
Moving the work to a thread frees the event loop (other tasks keep running), but the computation itself doesn't get faster or parallel under the GIL. Separate processes can use several cores.

A task is cancelled while paused at an await. What happens inside the coroutine?

  1. Nothing; cancel() only works on tasks that are not running
  2. The coroutine finishes normally and returns None
  3. asyncio.CancelledError is raised at that await, so finally blocks run, and the coroutine should re-raise it
  4. The process exits
Cancellation is delivered as an exception at the current await. That lets you clean up, but swallowing it hides the cancellation from the code that asked for it. It also means a coroutine in a tight loop with no await can't be cancelled.

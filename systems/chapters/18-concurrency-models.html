Concurrency Models Compared

You have now met threads with locks, processes, event loops and coroutines. They are not rivals so much as tools with different costs. This chapter lines them up with two more (actors and channels), shows how real servers like nginx, Node and Go combine them, and gives you a method for choosing.

Why this matters

"How should this server handle concurrency?" is one of the most common system-design questions, and the weak answer is a favourite technology. The strong answer starts from the workload: how many connections, how idle, how much CPU per request, how much shared state, how bad is a crash? This chapter turns the previous five chapters into a comparison you can use in a design review or an interview, and it leads straight into the two design studios.

Five ways to do many things at once

All concurrency models answer the same question: how do several activities make progress together, and how do they coordinate? They differ mainly in how activities share data. Let's list them, each with the idea and its signature trade-off.

1. Threads + locks

Shared memory. Several threads in one process read and write the same data, and use locks to take turns (ch. 10, ch. 12). Fast and flexible, but races, deadlocks and subtle bugs live here (ch. 11, ch. 13).

2. Event loop + callbacks / async

One thread, cooperative. Tasks pause at await and the loop runs another (ch. 16, ch. 17). Very cheap waiting and no data races within a loop, but one blocked callback stalls everything and one loop uses one core.

3. Processes

Separate memory. Each worker is its own process (ch. 5), and they communicate through pipes, sockets or shared files. Strong isolation (a crash stays contained) and true parallelism even in Python, at the cost of memory and clumsy data sharing.

4. Actors

Private state + mailbox. Each actor owns its data and receives messages one at a time. No shared memory at all. This is the model of Erlang/Elixir and of Akka on the JVM.

5. CSP / channels

Independent routines + typed pipes. Lightweight routines send values over channels. Go's goroutines and channels are the best-known example: "do not communicate by sharing memory; share memory by communicating".

Processes and pre-fork servers

Process-based concurrency is the oldest and still very common. A pre-fork server (like gunicorn for Python, or the old Apache prefork mode) starts a master process which fork()s a fixed number of workers at startup (chapter 5). Each worker handles requests on its own, typically one at a time, with its own memory. If a worker crashes or leaks memory, the master kills and replaces it, and the others never notice. Memory is the cost: each worker has its own copy of the application's data (though the operating system shares unmodified pages after fork via copy-on-write, chapter 6). In Python, processes are also the standard route to using several cores for CPU-bound work because each process has its own GIL.

Actors

An actor is a small unit that owns some private state and has a mailbox, a queue of incoming messages (this is the queue of chapter 14 again). Actors do only three things: receive a message and handle it, send messages to other actors, and create new actors. Because an actor handles one message at a time and nobody else can touch its state, there is no need for a lock. Here is the idea in plain Python threads: a counter that eight threads hammer concurrently, with no lock anywhere, and still comes out exactly right (compare the lost updates of chapter 11).

import queue
import threading


class CounterActor:
    """State is private. The only way in is the mailbox."""

    def __init__(self):
        self.mailbox = queue.Queue()
        self._count = 0                      # only the actor's own thread touches this
        threading.Thread(target=self._run, daemon=True).start()

    def send(self, msg):
        self.mailbox.put(msg)

    def _run(self):
        while True:
            kind, reply = self.mailbox.get()   # one message at a time, in order
            if kind == "inc":
                self._count += 1
            elif kind == "get":
                reply.put(self._count)


actor = CounterActor()


def client():
    for _ in range(10_000):
        actor.send(("inc", None))


threads = [threading.Thread(target=client) for _ in range(8)]
for t in threads:
    t.start()
for t in threads:
    t.join()

reply = queue.Queue()
actor.send(("get", reply))
print("count =", reply.get())                # always 80000: no lock needed
count = 80000

Real actor systems add much more: lightweight actors (Erlang's are tiny, a few KB each, and the runtime schedules huge numbers of them across cores), location transparency so that a message can go to an actor on another machine, and supervision, where a parent actor restarts a child that crashes (Erlang's "let it crash" philosophy). The price: the program's behaviour is now a conversation among many actors, which can be harder to follow than a function call stack, and mailboxes can grow without bound if a producer outruns a consumer.

CSP and channels

CSP (Communicating Sequential Processes) is a model, from the 1970s, of independent routines that talk through channels. A routine writes a value to a channel; another reads it. In Go, an unbuffered channel makes both sides wait until the other is ready (a handoff, or rendezvous), while a buffered channel is a bounded queue and applies backpressure when full. Unlike actors, the channel is a separate object that anyone with a reference can use, rather than a mailbox attached to one receiver. Go programs can still share memory and have data races (it ships a race detector for that reason), but the idiomatic style passes values through channels.

Analogy: the restaurant, five ways

Threads with locks: several cooks share one big pantry and queue for the single key to it. Event loop: one cook who juggles every dish and never stands still. Processes: several complete kitchens, each with its own pantry, communicating by notes passed through a window. Actors: every cook has a private station and an in-tray, and the only way to get anything done is to put a note in someone's tray. Channels: a conveyor belt between stations, where a cook hands over a plate and moves on.

Where it breaks down: a real kitchen has one physical pantry and plates are physical things. In software, "passing a message" means copying data (or handing over ownership), which has a cost, and a "note" can be lost, reordered or delayed once the kitchens are separate machines (see the distributed connection below).

Green threads and M:N scheduling

There is one more idea to know, because it explains why Go and modern Java feel different from older threads. An operating-system thread is relatively heavy (a kernel object, a stack of hundreds of KB to MB reserved, a microseconds-scale context switch, chapter 7). A green thread (or user-level thread, or lightweight thread) is a thread implemented by a library or language runtime instead of the kernel. The runtime keeps its own scheduler that multiplexes many of these small threads onto a few OS threads: M lightweight threads on N OS threads, called M:N scheduling.

  • Go. Goroutines are scheduled by the Go runtime onto a pool of OS threads (by default about one per core). A goroutine starts with a stack of roughly 2 KB that grows as needed, so a program can hold a very large number of them. When a goroutine does a network read, the runtime does not block an OS thread: it uses non-blocking sockets and an epoll/kqueue "netpoller" (the machinery of chapter 16), parks the goroutine, and runs another one on that thread. The programmer writes plain blocking-looking code; the runtime turns it into an event loop. This is why Go has no async/await split and no colour problem (chapter 17).
  • Java virtual threads (final in JDK 21) are the same idea for Java: a very large number of cheap virtual threads run on a small pool of carrier OS threads, and a blocking I/O call unmounts the virtual thread instead of tying up its carrier. The old thread-per-request style becomes viable again for a large connection count.
  • Erlang/Elixir run lightweight processes on scheduler threads (about one per core), preempting them fairly.
  • Python asyncio tasks are a cousin: cheap, runtime-scheduled, but cooperative with explicit await points and a single OS thread.

What real servers combine

  • nginx: multi-process and event-driven. A master process starts worker processes (roughly one per core); each worker runs an event loop that handles thousands of connections. Process isolation protects against crashes; event loops handle the connection count. It can use threads for blocking disk operations. See the nginx case study.
  • Node.js: JavaScript runs on a single event loop, so your callbacks never race. Network I/O uses epoll/kqueue on the loop itself, but operations that can't be made non-blocking that way (file system calls, DNS lookups through getaddrinfo, some crypto and compression) go to a thread pool inside libuv, four threads by default. To use several cores you start several Node processes (or use worker threads).
  • Go: goroutines on an M:N runtime with a netpoller. You write blocking-style code; the runtime gives you event-loop efficiency and uses all cores.
  • Databases: often one process (PostgreSQL) or one thread (MySQL by default) per client connection, plus pools: either an external connection pooler or a built-in worker pool, because hundreds of connections each running queries would overwhelm the CPU and memory. They also run background workers for writing logs and checkpoints. Redis is the notable exception that runs commands on one thread, deliberately (the Redis case study).

Common misconception

"Async is always faster than threads." Async is better at one thing: holding very many connections that are mostly waiting. For a service with a few dozen busy connections doing real computation, threads or processes are as good or better, and simpler to debug. Async also adds the risk that one blocked call affects everyone. Model choice is about the workload, not fashion.

How to choose for a workload

Ask these questions in order. Most designs fall out of the first two.

  1. How many concurrent connections, and how idle are they? Tens or hundreds of busy ones: almost anything works. Tens of thousands, mostly waiting: you want cheap waiting (an event loop, goroutines, virtual threads), not a heavy thread each.
  2. Is the work CPU-bound or waiting-bound? Waiting-bound (network, disk, other services): concurrency is about overlapping waits. CPU-bound: only real parallelism helps (threads in a language without a GIL, or processes), and a single event loop is the wrong tool.
  3. How much shared mutable state is there? If a lot, prefer designs that avoid it or confine it: a loop per core owning its connections, actors, or a single writer thread. If little, threads are fine.
  4. How costly is a crash? Separate processes contain damage; threads in one process share each other's fate.
  5. What does the language runtime allow? A Python program cannot use threads for CPU parallelism (unless on an experimental free-threaded build); Go and Java make blocking-style code cheap; Node's code is single-threaded by design.

A bridge to distributed systems

Notice something about actors and channels: once there's no shared memory, the only thing activities can do is send each other messages. That is precisely the situation of machines on a network. An actor system is a distributed system in miniature, and a distributed system is an actor system with the failure dial turned up. Everything you learned in the networking course shows up in small:

  • A message may be slow, or never arrive, so senders need timeouts (networking chapter 16).
  • An unbounded mailbox is an unbounded queue: it needs bounds and backpressure (chapter 14).
  • An actor that crashes is like a node that fails; supervision trees are failure detection and restart.
  • With no shared clock and no shared memory, the only ordering is the order of messages (networking chapter 17).

That's why engineers who think in message passing find the jump to distributed systems natural, and why some systems (Erlang is the classic example) make "send to an actor on another machine" look nearly the same as sending to a local one. The sameness is partly an illusion: a remote send can fail in ways a local one cannot (networking chapter 15).

Try it yourself

Try it yourself: threads vs the GIL, and counting a server's processes

Run the actor demo above (python3 actor.py) and note it prints 80000 every time. Then see what threads do for CPU-bound Python code. This standard-library script burns the same four jobs on one thread and on four threads. Your times will differ.

import time
from concurrent.futures import ThreadPoolExecutor


def burn(n):
    total = 0
    for i in range(n):
        total += i * i
    return total


def run(label, workers):
    start = time.perf_counter()
    if workers == 1:
        for _ in range(4):
            burn(3_000_000)
    else:
        with ThreadPoolExecutor(max_workers=workers) as pool:
            list(pool.map(burn, [3_000_000] * 4))
    print(f"{label:<22} {time.perf_counter() - start:.2f} s")


run("one thread, 4 jobs", 1)
run("4 threads, 4 jobs", 4)
one thread, 4 jobs     0.34 s
4 threads, 4 jobs      0.32 s

Four threads on a multi-core machine were no faster, because only one thread can run Python bytecode at a time (chapter 10). Swap ThreadPoolExecutor for concurrent.futures.ProcessPoolExecutor to give each job its own process and its own GIL; with enough cores the four jobs should then finish in roughly a quarter of the time. (An experimental free-threaded build of Python 3.13 and later also lifts the limit, but it is optional and not the default.)

Distributed systems connection

The models in this chapter reappear one level up. A fleet of identical stateless servers behind a load balancer is the "processes" model across machines. A message queue between services is a mailbox shared by many actors. A service owning its data and answering only through its API is an actor with private state. The question "share state or pass messages?" is the same question as in replication and partitioning, and the answer is similar: sharing is easy and fast until it has to survive failure and distance, at which point explicit messages and clear ownership win.

Key takeaways

  • Models differ mainly in how they share data: threads share memory (locks); processes and actors don't; event loops serialise access by running one callback at a time; channels pass values between routines.
  • Green threads / M:N scheduling (goroutines, Java virtual threads since JDK 21, Erlang processes) put many cheap tasks on a few OS threads and hide the event loop from you.
  • Rough costs: OS threads are heavy, event-loop tasks and goroutines are light, processes are heaviest but isolated. Only threads (without a GIL), processes, actors and M:N runtimes give CPU parallelism.
  • Real servers mix models: nginx (processes + event loops), Node (one loop + a libuv thread pool), Go (M:N + netpoller), databases (process or thread per connection + pools).
  • Choose from the workload: many idle connections favour cheap waiting; CPU-bound work needs real parallelism; mixed work uses a loop for I/O plus a bounded pool for compute.
  • Actors and message passing are distributed systems in miniature: no shared memory, so you get timeouts, queues, failures and ordering questions in small.

Check your understanding

What is the defining feature of the actor model?

  1. All actors share one global memory protected by a lock
  2. Each actor owns private state and communicates only by sending messages to other actors' mailboxes
  3. Every actor runs in a separate virtual machine
  4. Actors must run on the same CPU core
No shared memory: the only way to affect an actor's state is to send it a message, which it handles one at a time. That removes data races on actor state, but not delays, lost messages or overflowing mailboxes.

A Go program has 100,000 goroutines, each waiting on a network read. How does this work without 100,000 OS threads?

  1. The kernel creates 100,000 cheap threads automatically
  2. Go only allows 100,000 goroutines if they are idle
  3. Each goroutine busy-polls its socket
  4. The runtime uses non-blocking sockets and a netpoller (epoll/kqueue), parks waiting goroutines, and schedules runnable ones onto a few OS threads
This is M:N scheduling plus an event loop hidden inside the runtime. The code looks like blocking code, but the runtime turns a "blocking" read into park-and-resume.

A Python service must resize images, which is CPU-heavy. Which approach uses all cores?

  1. A pool of worker processes (for example, ProcessPoolExecutor, or pre-fork workers like gunicorn)
  2. One asyncio event loop with many tasks
  3. Many threads running pure-Python code on a standard GIL build
  4. One very large asyncio.gather
Each process has its own interpreter and GIL, so they run in parallel. An event loop and GIL-bound threads run Python code one at a time, which doesn't help CPU-bound work.

How does Node.js handle file-system and DNS operations without blocking its single JavaScript thread?

  1. It doesn't; those calls block the event loop
  2. It forks a new process for each call
  3. libuv runs them on a small internal thread pool (four threads by default) and posts the result back to the loop
  4. It converts them into epoll events
Sockets can use readiness notification, but regular files and many resolver calls can't, so libuv uses worker threads for them, just like the "send slow work to a pool" rule of chapter 16.

You are designing a gateway that holds 50,000 mostly idle connections, with a tiny amount of work per message. What is the best starting point?

  1. One OS thread per connection
  2. One event loop per core (or goroutines / virtual threads), keeping slow work off the loops
  3. One process per connection
  4. A single thread doing blocking reads in a loop
The cost to optimise is per-connection waiting, which event loops and lightweight threads make nearly free. This is the situation in Studio 1.

Parallelism, SIMD & GPUs

A single core stopped getting dramatically faster years ago, so hardware went wide instead: more instructions at once, more numbers per instruction, more cores, and finally chips with thousands of tiny cores. This chapter shows the four kinds of parallelism, the law that limits all of them, and why the machines that run modern AI are limited less by arithmetic than by how fast they can move bytes.

Why this matters

"Just add more cores" and "just use a GPU" are two of the most common answers to a slow system, and both are often wrong. Whether they work depends on how much of the job can really run side by side (Amdahl's law) and on whether the job is waiting for arithmetic or for memory (the roofline idea). These two questions explain why NumPy beats a Python loop by a factor of a hundred, why training a neural network needs GPUs, why serving a language model is mostly a memory problem, and why a service that batches requests can be several times cheaper than one that doesn't. They are also the questions you will ask in a design review long before you write any code.

Four kinds of parallelism

Parallelism means doing more than one thing at the same moment. (That is different from concurrency, from chapters 10 to 18, which is about structuring a program so several tasks can make progress. A single core can be concurrent without being parallel.) Hardware offers parallelism at four different scales, and they stack on top of each other.

Chapter 1 already met the first: the CPU pipeline overlaps instructions, and a modern core can finish several per cycle when they don't depend on each other. The third you know from chapters 10 to 13. This chapter spends most of its time on the second and fourth, because they are what the rest of the industry now leans on, and then on a law that governs all of them.

Amdahl's law: the serial part always wins

Suppose a job takes 100 seconds, and 80 of those seconds can be split perfectly across workers while 20 seconds are stubbornly serial (reading the input, combining the results, waiting for a lock). With 8 workers the parallel part shrinks to 10 seconds, but the serial part stays: the job takes 30 seconds, a speedup of 3.3x on 8 workers, not 8x. With a million workers the parallel part vanishes and the job still takes 20 seconds. The speedup can never exceed 100 / 20 = 5x.

That is Amdahl's law. If a fraction p of the original runtime can be parallelised across n workers, then:

speedup = 1 / ((1 - p) + p / n)

limit as n grows without bound:  1 / (1 - p)

The surprise is how harsh the limit is. If 5% of the job is serial, you can never go beyond 20x, even with a million cores. Here it is as a runnable table:

def speedup(p, n):
    """Amdahl: p = parallel fraction of the ORIGINAL runtime, n = workers."""
    return 1 / ((1 - p) + p / n)

print(f"{'workers':>8} {'p=0.50':>8} {'p=0.90':>8} {'p=0.95':>8} {'p=0.99':>8}")
for n in (1, 2, 4, 8, 16, 64, 1024, 10**9):
    label = f"{n:,}" if n < 10**9 else "infinite"
    print(f"{label:>8}", *(f"{speedup(p, n):8.2f}" for p in (0.5, 0.9, 0.95, 0.99)))

# Worked example: a 100 s job, 80 s parallelisable, on 8 workers
t_serial, t_par, n = 20, 80, 8
print("\n100 s job, 80 s parallel part, 8 workers:")
print("new time =", t_serial + t_par / n, "s  speedup =", round(100 / (t_serial + t_par / n), 2))
print("limit with infinite workers =", 100 / t_serial, "x")

# Gustafson: scaled speedup = (1 - p) + p * n  (p = parallel fraction of the PARALLEL run)
def gustafson(p, n):
    return (1 - p) + p * n
print("\nGustafson, p=0.9 on the parallel run:")
for n in (8, 64, 1024):
    print(f"  n={n:5d}  scaled speedup = {gustafson(0.9, n):7.1f}")

Common misconception

Amdahl's law is optimistic, not pessimistic. It ignores the costs of parallelism itself: starting workers, splitting the data, locks and cache-line fights (chapters 11 to 13), and combining results. Real speedup is usually below the formula's number, and past some worker count it can go down.

Gustafson's law: when the problem grows too

Amdahl asks: how much faster can I do this fixed job? Gustafson's law asks a different question: with more workers, how much bigger a job can I do in the same time? If you have 1,024 cores you probably don't run the same small simulation faster; you run a finer-grained one. When the serial part stays about the same size while the parallel part grows with the machine, the "scaled speedup" is roughly (1 - p) + p * n, where p is now the parallel fraction of the time on the parallel run. With p = 0.9 and 1,024 workers that is about 922x. Both laws are right; they answer different questions. Latency-bound work (one user waiting) obeys Amdahl; throughput-bound work with growing data (training on a bigger dataset, serving more users) looks like Gustafson.

SIMD: one instruction, many numbers

A normal ("scalar") add instruction adds two numbers. A SIMD instruction (single instruction, multiple data) adds vectors of numbers: the CPU has wide vector registers and ALUs that apply the same operation to every lane. An x86 chip with AVX2 has 256-bit registers, which hold 8 32-bit floats; AVX-512 doubles that to 16; Arm's NEON, on Apple's M-series and most phones, has 128-bit registers holding 4 floats (Arm also has wider vector extensions on some chips). So one instruction does 4 to 16 adds. The cost is almost the same as a scalar add, because the heavy part of running an instruction is fetching, decoding and scheduling it, and that is paid once.

Two conditions make SIMD pay off. The numbers must sit side by side in memory (so one wide load fetches a whole vector, and it is the cache-line idea from chapter 2 again), and every lane must do the same operation, with no per-element branches. Compilers try to auto-vectorise simple loops in C, C++ and Rust, and libraries such as BLAS, which sits under NumPy, contain hand-tuned vector code.

Why NumPy is fast, and what pure Python can and can't show

When you write for i in range(n): total += a[i] * b[i] in Python, every step runs through the interpreter from chapter 1: look up the objects, check their types, call the multiply function, allocate a new float object for the result. Dozens of machine instructions to do one multiply-add. NumPy takes the opposite approach: one Python call hands a whole array to compiled code, which loops over packed numbers in machine code, with vector instructions, without touching the interpreter per element. The gain comes from three things at once: no per-element interpreter overhead, contiguous memory, and SIMD.

An honest note about the demo below

You cannot demonstrate SIMD itself in pure Python with the standard library. Python's array module stores packed machine doubles, which is the right layout, but it gives you no vector arithmetic: every operation on its elements still goes through ordinary Python objects. Built-in functions like sum, map and (3.12+) math.sumprod move the loop into C and so remove most of the interpreter overhead, which is the biggest part of the gap, but they are plain scalar C loops, not SIMD. The demo shows the "interpreter overhead" part of the story honestly, and then we compare against NumPy once to see the whole thing.

import array, math, operator, random, sys, timeit

N = 1_000_000
random.seed(1)
a = [random.random() for _ in range(N)]
b = [random.random() for _ in range(N)]
arr_a = array.array("d", a)
arr_b = array.array("d", b)

def loop():
    total = 0.0
    for i in range(N):
        total += a[i] * b[i]
    return total

def zip_loop():
    total = 0.0
    for x, y in zip(a, b):
        total += x * y
    return total

def builtin_map():
    return sum(map(operator.mul, a, b))

def builtin_array():
    return sum(map(operator.mul, arr_a, arr_b))

cases = [("index loop", loop), ("zip loop", zip_loop),
         ("sum(map(mul))", builtin_map), ("sum(map(mul)) on array", builtin_array)]
if hasattr(math, "sumprod"):               # Python 3.12+
    cases.append(("math.sumprod", lambda: math.sumprod(a, b)))

base = None
for name, fn in cases:
    t = min(timeit.repeat(fn, number=1, repeat=5))
    base = base or t
    print(f"{name:26s} {t*1000:8.1f} ms   {base/t:5.1f}x vs index loop")

print()
print("list     :", sys.getsizeof(a) // 1000, "KB of pointers, plus",
      sys.getsizeof(a[0]) * N // 1000, "KB of float objects")
print("array('d'):", sys.getsizeof(arr_a) // 1000, "KB, packed 8-byte doubles")

Your numbers will differ, but the shape should hold. Moving the loop into C (sum(map(...))) helps a little; math.sumprod, a single C function that multiplies and adds without creating any intermediate Python objects, is several times faster. The array version is slower than the list version here, which looks backwards until you remember why: the elements are packed doubles, so every access has to build a fresh Python float object from the raw bytes. Packed storage saves memory (8 MB against about 32 MB in the list, shown at the bottom) but pays off only when compiled code reads it directly. About 0.1 ms against about 19 ms: roughly a 190x gap on this machine, from one function call. Most of it is removed interpreter overhead and the rest is contiguous memory and vector instructions. Notice also that the 1M-element dot product reads 16 MB of data in about 0.1 ms, which is on the order of 100 GB/s or more: at that point the loop is close to what the memory system (or, for data this small, the large caches) can deliver, so it is limited by data movement rather than arithmetic. That is the next idea.

Compute versus bandwidth: the roofline idea

A processor can be slow for two very different reasons: it can't do arithmetic fast enough, or it can't get the numbers fast enough. Which one applies depends on a single ratio, the arithmetic intensity of your code: how many arithmetic operations you do per byte you move from memory, measured in FLOP per byte (a FLOP is one floating-point operation, such as an add or a multiply).

Analogy: the cooks and the pantry door

In the kitchen from chapter 0, imagine a hundred cooks (compute) and one narrow pantry door through which all ingredients arrive (memory bandwidth). If every dish needs hours of chopping per ingredient, the door is irrelevant: the cooks are the limit. If every dish is "put one tomato on a plate", the cooks idle and the door sets the pace. Intensity is the amount of cooking per ingredient carried through the door.

Where it breaks down: real memory has a hierarchy (chapter 2). Ingredients reused soon after arriving are served from the cutting board, not the pantry, so the "door" that matters is the one at the level where your data actually lives.

The roofline model draws exactly this. The speed you can achieve is the lower of two ceilings: your peak compute rate, and (memory bandwidth) x (your arithmetic intensity). At low intensity, the second is the smaller, so you sit on a sloped line and doubling the intensity doubles your speed. At high intensity you hit the flat ceiling of peak compute, and only a faster processor helps. The corner where the two meet is the ridge point.

Some intensities worth feeling. An element-wise add, c[i] = a[i] + b[i] in 32-bit floats, does 1 FLOP and moves 12 bytes (read two, write one): about 0.08 FLOP/byte. A dot product does 2 FLOPs per 8 bytes read: 0.25. Both are hopelessly memory-bound on any machine; faster arithmetic does nothing for them, which is why that 16 MB dot product ran at memory speed. A large matrix multiplication is the opposite, as we will see in a moment. For modern chips the ridge point sits at a surprising place: the GPUs below need on the order of a hundred or more FLOPs of work per byte fetched to keep their arithmetic units busy. Almost nothing is that dense unless you reuse each loaded number many times.

GPUs: thousands of simple cores

A CPU core is built to run one instruction stream as fast as possible: deep pipelines, branch prediction, out-of-order execution and large caches all exist to hide delays in unpredictable code (chapters 1 and 2). That machinery takes much of the die. A GPU (graphics processing unit) makes the opposite trade. It strips each core down to simple arithmetic, drops most of the latency-hiding hardware, and uses the space for thousands of them, plus very wide memory. The result is poor at running one thread of branchy code and extraordinary at running the same small program on millions of data items.

Four ideas make a GPU tick.

  • SIMT. You write the program for one thread and launch it for thousands or millions of threads, each with its own index to pick its slice of the data. The hardware runs them in groups: this is SIMT (single instruction, multiple threads), a close cousin of SIMD in which the vector lanes look like independent threads.
  • Warps. On NVIDIA GPUs a group of 32 threads that execute the same instruction together is a warp (AMD uses 32 or 64, and calls its groups wavefronts). If the threads of a warp disagree at an if, the hardware runs both branches one after the other with some threads switched off, a cost called divergence. GPU code is fastest when it is uniform, exactly as with SIMD.
  • Hide latency with more threads, not caches. A CPU hides a 100 ns memory wait with caches and speculation. A GPU hides it by keeping many more warps resident than it can run, so when one warp stalls on memory the hardware switches to another within a cycle. This only works if you launch far more threads than there are cores.
  • High-bandwidth memory. GPUs pair the cores with very wide memory, today usually HBM (high-bandwidth memory) stacked right next to the chip. Top data-centre GPUs deliver roughly 2 to 8 terabytes per second depending on generation, against roughly 50 to 100 GB/s for a typical desktop's main memory. Apple's M-series chips sit in between: a single pool of memory shared by the CPU and GPU (so no copy), at a few hundred GB/s in the larger models (up to roughly 800 GB/s on the biggest).

Analogy: one master chef versus a school cafeteria line

A CPU core is a master chef who can cook any dish in any order, adapting as orders change. A GPU is a long assembly line of thousands of trained helpers who each do one simple step, all at the same moment, on a thousand identical sandwiches. For a thousand identical sandwiches the line wins by a mile. For one complicated, ever-changing dinner it is useless.

Where it breaks down: the helpers on the line only stay in step in groups of 32, and a sandwich with an unusual filling (a divergent branch) stalls its whole group.

The catch: moving data to the GPU

A discrete GPU has its own memory, separate from the CPU's. To compute on data you must copy it over the PCIe link (roughly tens of GB/s, an order of magnitude below the GPU's own memory bandwidth, and with a latency of microseconds per transfer), and copy results back. So the question is always: does the GPU do enough work per byte copied to pay for the trip? A million-element vector add finishes in microseconds on the GPU and then waits longer than that to be copied in and out, so the CPU wins. A matrix multiply that does thousands of operations per number copied wins easily. Serious GPU programs keep data on the device across many operations and overlap copies with computation. This is the roofline argument again, one level further out: the PCIe link is just another, narrower, pantry door.

Why matrix multiplication suits GPUs

Multiplying two n x n matrices produces n² outputs, each a dot product of length n. That is about 2n³ FLOPs, but the inputs and outputs hold only 3n² numbers. The work grows as the cube of the size and the data as the square, so the arithmetic intensity grows with n: each number loaded can be reused about n times. Libraries exploit this by cutting the matrices into tiles that fit in fast on-chip memory, reusing each tile many times before going back to main memory (chapter 2's locality, applied deliberately). Better still, the outputs are all independent, so there are millions of identical, uniform, branch-free jobs: just what a GPU wants.

def intensity(n, bytes_per=4):
    flops = 2 * n**3                  # n*n outputs, each n multiplies + n adds
    traffic = 3 * n * n * bytes_per   # read A and B once, write C once (ideal)
    return flops / traffic
for n in (8, 64, 1024, 8192):
    print(f"n={n:5d}  {intensity(n):8.1f} FLOP/byte")
print("elementwise add (c = a + b), float32:", round(1 / (3 * 4), 3), "FLOP/byte")

(These are ideal values that assume perfect tiling, so each number crosses the memory bus once.) A 1,024 x 1,024 matrix product reaches about 170 FLOP/byte, and 8,192 x 8,192 passes 1,000: far right of the ridge, firmly compute-bound. Contrast that with the 0.08 of an element-wise add. This is why neural networks, which are dominated by large matrix products, took off on GPUs, and why chip makers added dedicated tensor cores (small fixed-function units that multiply small matrix tiles in a single step) which lift the compute roof to around a thousand trillion FLOP/s for 16-bit numbers on the top data-centre parts. The roof got so high that the ridge point moved right: an op needs a few hundred FLOP/byte to reach it, and many operations in a real model do not have that.

Why LLM decoding is bound by memory bandwidth

A large language model generates text one token at a time. To produce each token the system must run the whole network once, which means reading every weight from memory and doing a multiply-add with each. For a single sequence the "matrix" is really a matrix times one vector, so each weight is used for just one multiply-add before being thrown away: about 2 FLOPs per weight. If a weight is stored in 16 bits (2 bytes), that is about 1 FLOP per byte, a few hundred times below the ridge point. The chip's multipliers are mostly idle, waiting for weights to arrive. So the speed limit is simply:

tokens per second  <=  memory bandwidth / bytes of weights read per token
# Upper bound on decode speed when weights must be streamed from memory.
# Assumptions: batch size 1, every weight is read once per generated token,
# nothing else (KV cache, activations) costs anything.  Real systems do worse.
GB = 1e9
models = [("7B  params, 16-bit", 7e9, 2.0),
          ("70B params, 16-bit", 70e9, 2.0),
          ("70B params, 4-bit ", 70e9, 0.5)]
memories = [("laptop DRAM, ~100 GB/s", 100 * GB),
            ("one big GPU, ~3,000 GB/s", 3000 * GB)]

for mname, params, bytes_per_param in models:
    weights = params * bytes_per_param
    for bname, bandwidth in memories:
        print(f"{mname}  weights {weights/GB:6.1f} GB  {bname:26s}"
              f" -> at most {bandwidth/weights:6.1f} tokens/s")

# Arithmetic intensity of that decode step: ~2 FLOPs (multiply + add) per weight
print("\nFLOPs per byte at batch 1, 16-bit weights:", 2 / 2.0)
print("FLOPs per byte at batch 64:", 64 * 2 / 2.0)

The assumptions are on the first lines of the script, and they matter: batch size 1, every weight read exactly once per token, bandwidth figures that are round numbers (about 100 GB/s for a laptop, about 3 TB/s for a top data-centre GPU), and no cost for anything else. A 70-billion-parameter model in 16 bits is 140 GB, more than one GPU holds, so in practice its weights are split across several GPUs whose bandwidths add up; read the "one big GPU" row as the aggregate bandwidth of the memory the weights live in. Real speeds come out lower, because attention also reads a growing cache of past keys and values (the "KV cache", which is extra bytes per token that grow with context length), and nothing reaches full bandwidth. But the shape of the estimate is right and explains three real-world facts. Smaller models are faster. Stored in 4 bits ("quantised") a model takes a quarter of the bytes and decodes up to four times faster, which is why quantisation is so popular. And a laptop with fast unified memory can run a medium-sized model usefully while a machine with lots of arithmetic but slow memory cannot.

The fix is batching

If the weights are being read anyway, use them for many requests at once. At batch size 64, one pass over the weights serves 64 sequences: the intensity rises to roughly 64 FLOP/byte and the cost of reading the weights is shared by 64 users. In the roofline picture you slide to the right along the slope. Throughput rises almost in proportion until you approach the ridge point (or run out of memory for the KV caches, which are per-sequence), after which you are compute-bound. That one fact shapes how model-serving systems are built: they wait a few milliseconds to group requests, use continuous batching (adding new requests to a running batch as old ones finish), and trade a little latency for a large gain in tokens per second per dollar.

Common misconception

"A faster GPU means faster chatbot replies." Only if it has more memory bandwidth. For single-user decoding, doubling the FLOPs does almost nothing; doubling the bandwidth nearly doubles the speed. Training and processing a long prompt (which handles many tokens at once, so intensity is high) are the compute-bound cases.

TPUs and other accelerators

The GPU is not the only way to spend silicon on matrix arithmetic. A TPU (tensor processing unit), Google's design, is built around a large systolic array: a grid of multiply-add units through which numbers flow rhythmically, so each value fetched is reused across a whole row or column before leaving the chip, which pushes the intensity up by construction. Other companies build their own neural-network accelerators (often called NPUs), and phones and laptops now include small ones for on-device models. Some designs put large amounts of fast on-chip SRAM next to the arithmetic to avoid the off-chip memory bottleneck, and others focus on packing the numbers into fewer bits. The details differ and change quickly, so hold on to the shared pattern: fewer general-purpose mechanisms, more arithmetic units, and a design built around keeping data close to them. The trade-off is flexibility. Each is excellent on the workloads it targets and awkward on anything else, which is why the CPU stays in the middle of every machine to run the operating system, the branchy code and the glue.

What this means for system design

  • Batch to amortise fixed costs. Every weight read, every PCIe copy, every kernel launch and every disk or network call has a fixed price. Doing more work per trip (batching) is the general remedy, in model serving and in databases (column stores work the same way: they scan columns in bulk with vectorised code).
  • Data movement is the cost. In most real systems the question is not "how many FLOPs?" but "how many bytes move, and how far?" The memory hierarchy (chapter 2) from L1 to a PCIe link to a network hop is one continuous ladder with the same rule at every rung. Design to move less, and to reuse what you moved.
  • Cost follows utilisation. A GPU costs the same whether its multipliers are busy or idle. A serving system that is bandwidth-bound at batch 1 is wasting most of an expensive chip, which is why batching, quantisation and request routing matter to the bill. We take this up in Designing with ML & LLMs.
  • Find the serial fraction. Before adding hardware, ask what Amdahl's serial part is: a lock, a single-threaded coordinator, a data load. That is where the next 10x hides. Chapter 22 shows how to find it by measuring.
  • Match the tool to the shape of the work. Branchy, latency-sensitive, small-data code belongs on the CPU. Uniform bulk arithmetic over big arrays belongs on vector units or accelerators. Network-bound or lock-bound code needs neither (chapters 12 and 15).
Go deeper: Python threads, the GIL and where parallelism shows up optional

In standard CPython (chapter 10) the global interpreter lock lets only one thread run Python bytecode at a time, so threads give no thread-level parallelism for pure-Python CPU work. The escape routes all match this chapter: use multiprocessing or separate processes (each with its own interpreter and lock), or call into libraries such as NumPy that release the lock while compiled code runs (and use SIMD and often several cores inside). Python 3.13 added an optional, experimental free-threaded build, but ordinary installs still have the GIL. Amdahl's law applies to all of these: process start-up, pickling arguments and merging results are the serial fraction.

Distributed systems connection

Amdahl's law is the same law that limits scaling out across machines, with a bigger serial fraction: coordination, data shuffles and the slowest straggler. The roofline idea scales up too: a cluster training a model is bound by the network between GPUs the way one GPU is bound by its memory, and good designs keep data local the way chapter 2 taught. Key takeaways

  • Parallelism comes at four scales: instruction-level, SIMD vectors, multiple cores, and accelerators. Fast numerical code uses all of them.
  • Amdahl's law: speedup = 1 / ((1 - p) + p/n). The serial fraction sets a hard ceiling (5% serial means at most 20x), so shrink the serial part before adding workers. Gustafson's view: bigger machines usually run bigger problems.
  • SIMD applies one instruction to 4 to 16 numbers; it needs contiguous data and uniform operations. NumPy is fast because it removes interpreter overhead, uses packed memory and uses vector code. Pure Python can show the first effect honestly, not SIMD itself.
  • Arithmetic intensity (FLOP per byte) decides whether you are memory-bound or compute-bound. Most simple loops are memory-bound; the roofline shows the ceiling for each.
  • GPUs trade clever cores for thousands of simple lanes running in warps of 32, with very high memory bandwidth. They shine on uniform bulk work such as matrix multiplication and pay a toll for every host-to-device copy.
  • LLM decoding at small batch sizes reads all the weights per token, so tokens/s is at most bandwidth divided by model bytes. Batching and quantisation are the main remedies.
  • In system design, parallel hardware pays only when you keep it fed: batch, move less data, and know your serial fraction.

Check your understanding

A job takes 100 s, of which 10 s is inherently serial. What is the best possible speedup however many workers you add?

  1. About 9x
  2. About 90x
  3. 10x
  4. There is no limit if you add enough workers
The limit is 1 / (serial fraction) = 1 / 0.1 = 10x. Even with infinitely many workers the 10 serial seconds remain, so the job cannot finish in under 10 s.

Which statement about the pure-Python array demo is honest?

  1. It mostly shows interpreter overhead being removed; real SIMD needs compiled code such as NumPy or a vectorising compiler
  2. It proves that Python uses AVX instructions for sum
  3. The array module gives vector arithmetic, so it is always faster than a list
  4. It shows that SIMD gives a 5x speedup on every machine
Built-ins like sum and math.sumprod run a scalar C loop. They avoid the interpreter's per-element cost, which is a large part of the gap, but SIMD needs compiled kernels. The array module only changes the layout, and can even be slower in pure Python because each access creates a float object.

An element-wise add of two big float arrays does about 0.08 FLOP per byte moved. What limits it?

  1. The number of multiplier units
  2. The clock speed of the CPU
  3. Branch mispredictions
  4. Memory bandwidth, so a faster ALU would not help
It sits far left of the ridge point, on the sloped, bandwidth-limited part of the roofline. The arithmetic units spend most of their time waiting for data.

A model has 14 GB of weights and a GPU has about 2,000 GB/s of memory bandwidth. At batch size 1, roughly what is the upper bound on decoding speed?

  1. About 14 tokens per second
  2. About 140 tokens per second
  3. About 2,000 tokens per second
  4. About 28,000 tokens per second
Each token reads all the weights once: 2,000 / 14 is about 143 tokens per second at best, ignoring the KV cache and real-world inefficiency. The 14 and 2,000 answers come from using the wrong quantity; 28,000 multiplies instead of dividing.

Why does batching many requests together raise LLM serving throughput so much?

  1. One read of the weights serves every sequence in the batch, raising arithmetic intensity so the idle compute is used
  2. Batches make the GPU's memory physically faster
  3. It removes the need to load the weights at all
  4. It avoids the PCIe link entirely
The cost of streaming the weights is the same whether one sequence or many use them, so the cost per token falls almost in proportion, until compute or per-sequence memory (the KV cache) becomes the limit.

What does a GPU warp (on NVIDIA hardware) do when its 32 threads reach an if and half of them take the branch?

  1. The warp splits into two independent warps that run on different cores
  2. The threads that take the branch stop and the others finish the program
  3. Both paths run one after the other, with the non-participating threads switched off, so the warp takes the time of both
  4. The program crashes with a divergence error
This is warp divergence. The threads share one instruction stream, so the hardware serialises the paths. Uniform control flow keeps all 32 lanes useful.

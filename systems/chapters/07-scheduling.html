Scheduling & Context Switches

Your laptop is running hundreds of programs on a handful of CPU cores. The first of the three illusions, "you have the CPU to yourself", is made by the scheduler, a small piece of the kernel that decides who runs next. Here is how it works and what it costs.

Why this matters

Almost every performance mystery involves waiting for a turn on the CPU. A server that is "only 30% busy" can still have slow requests because its threads are queueing for cores. Knowing what a context switch is, why it isn't free, and what load average means lets you read a machine's health at a glance, and explains why Part 4 of this course avoids using one thread per connection.

One core, many programs

A core can run exactly one stream of instructions at a time (chapter 1). Yet ps shows hundreds of processes. The answer is time-sharing: the kernel lets one program run for a short while, pauses it, lets another run, and so on, fast enough that each seems to run continuously.

The kernel's list of everything that is ready to run is the run queue. A thread is in one of a few broad states:

  • Running: executing on a core right now.
  • Runnable (ready): wants the CPU and is waiting in the run queue for its turn.
  • Blocked (sleeping): waiting for something else, such as a disk read, a network packet or a timer. It isn't in the run queue and uses no CPU until the kernel wakes it.

The scheduler picks the next runnable thread for each core. Each pick gets a time slice: a short window, on the order of milliseconds, before the scheduler may choose again. A hardware timer interrupts the CPU on a regular tick, which hands control back to the kernel even if the running program never asks for anything. Taking the CPU away from a program that hasn't finished is called preemption. A program that blocks voluntarily (for example in read()) gives up its slice early, and another runnable thread takes over immediately.

Analogy: one cook, several dishes

Picture a single cook (the core) in our kitchen with three orders. They stir one pot for a minute, put it down, stir the next, and cycle round. A kitchen timer (the interrupt) forces the switch even if the cook is engrossed. When a dish needs to sit in the oven, the cook simply moves on to another one, and that dish is "blocked" until the oven dings.

Where it breaks down: a human cook switches in seconds and can remember where they were. A CPU must explicitly save every detail of one program's state before loading another's, which is where the cost comes from (next section). Real machines also have many cores, each with its own run queue or share of one.

What a context switch does

A context switch is the move from running one thread to running another. The kernel must:

  1. Save the outgoing thread's CPU state: the registers, the program counter (which instruction is next), and the stack pointer. This is saved in a kernel data structure for that thread.
  2. Choose the next thread from the run queue.
  3. Switch memory view if the new thread belongs to a different process: point the CPU at that process's page tables (chapter 6). Threads of the same process share an address space, so this step is skipped, which is one reason thread switches are cheaper.
  4. Restore the incoming thread's saved registers and jump to where it left off. It never notices it was paused.

The direct work takes roughly on the order of microseconds. That is tiny compared to a millisecond-sized slice, but there is a second, hidden cost: the CPU's caches (chapter 2) were full of the old thread's data. The new thread starts with cold caches, so its first accesses go out to slower RAM until the caches refill. That indirect cost can be larger than the switch itself. Switching also adds nothing useful: the faster and more often you switch, the more of the core's time goes to housekeeping.

Common misconception

"More threads means more speed." Threads help when they let you use more cores, or let one thread run while another waits. Beyond that they only add switching and cache misses. Ten CPU-hungry threads on a 4-core machine finish no sooner than four would; they just take turns.

CPU-bound and I/O-bound work

Programs fall on a spectrum:

  • CPU-bound work (video encoding, compressing, a tight loop) wants the CPU every moment. It always uses up its whole slice and gets preempted.
  • I/O-bound work (a web server, a text editor) runs briefly, then blocks waiting for the network, disk or a keypress. It uses a sliver of each slice.

Schedulers are built to favour I/O-bound threads: when their data arrives, they should get the CPU promptly, because they'll do a little work and go back to sleep. That is what keeps your editor responsive while a compiler hammers every core.

You can also give the scheduler hints. Every process has a niceness, from -20 to 19 on Unix systems, default 0. A higher number means "nicer": the process yields more CPU to others. Ordinary users can only make their own processes nicer (nice -n 10 ./big-job); raising priority needs privileges. Niceness is a weight in sharing the CPU, not a guarantee.

Priorities can backfire

If a high-priority task needs a lock held by a low-priority one, and medium-priority tasks keep preempting the low one, the high-priority task is stuck. This is priority inversion. It famously rebooted a spacecraft: see the Mars Pathfinder case after you meet locks in chapter 12.

Reading the load average

The load average is three numbers, usually shown by uptime: a smoothed average over the last 1, 5 and 15 minutes of how many tasks wanted to run. Roughly: how many threads were running or queued for a core. (On Linux it also counts threads stuck waiting for the disk, so a slow disk raises it too.)

Compare it with the number of cores. On a 4-core machine, a load of 4 means the cores are about fully used; 1 means they're mostly idle; 12 means about eight threads are queueing at any moment. Compare the three numbers, too: 1.2, 4.5, 8.0 says the load is falling, while 8.0, 4.5, 1.2 says it's climbing. A high load doesn't tell you why; it only says to look closer with top.

Thousands of runnable threads

Suppose a server starts one thread per connection and 5,000 of them are runnable on 8 cores. Each gets a tiny share, so each request waits behind hundreds of others. The kernel does ever more switching, each thread's data evicts the others' from the caches, and every thread also holds a stack of memory. The machine can look "busy" while accomplishing little. This is one of the main reasons event loops exist (chapter 16): one thread handles many connections without a switch for each.

Which algorithm picks the next thread varies by OS. Linux used the Completely Fair Scheduler (CFS), which tracked how much CPU time each thread had received and favoured those that had received the least; it was replaced by a successor called EEVDF in Linux 6.6. macOS has its own scheduler, also priority-based. All of them are variations on the idea above.

Try it yourself

Try it yourself: see the queue

These commands only read information. Your numbers will differ.

$ uptime
14:02  up 3 days,  4:11, 2 users, load averages: 2.31 1.87 1.52
$ sysctl -n hw.ncpu          # cores (Linux: nproc)
10
$ top -l 1 | head -12        # macOS snapshot. Linux: top -bn1 | head -12
Processes: 612 total, 3 running, 609 sleeping, 2870 threads
Load Avg: 2.31, 1.87, 1.52  CPU usage: 8.2% user, 4.1% sys, 87.7% idle

Here the load (about 2) is far below the 10 cores, so nothing is queueing. Now run python3 -c "while True: pass" in a second terminal, wait a few minutes, and run uptime again: the 1-minute number climbs toward one higher than before (it is a smoothed average, so it takes a while). Press Ctrl-C to stop it. Notice that top reports hundreds of processes "sleeping": blocked, using no CPU at all.

Distributed systems connection

A node that is too busy to be scheduled looks, from outside, exactly like a dead one: it misses its heartbeat. A CPU-starved or paused process can be declared failed by its peers even though it is fine (networking chapter 16). Queueing for the CPU also adds latency to every request, which is why the slowest requests (tail latency) rise sharply when machines run near full load.

Key takeaways

  • The scheduler shares a few cores among many threads using a run queue, time slices and preemption by timer interrupt.
  • A context switch saves one thread's registers and restores another's. It costs roughly microseconds directly, plus cold caches afterwards.
  • Blocked threads use no CPU. Only runnable threads compete, so I/O-bound work is cheap to keep around.
  • Niceness is a hint about sharing; priorities can cause priority inversion with locks.
  • Load average roughly counts running plus queued threads; compare it with the core count.
  • Thousands of runnable threads mean heavy switching and thrashed caches, one reason for event loops.

Check your understanding

What does preemption mean?

  1. A program asks the kernel to run it first
  2. A program is moved to another core to speed it up
  3. The kernel takes the CPU from a running thread, usually after a timer interrupt, even though it hasn't finished
  4. A program is killed when it uses too much CPU
Preemption is the kernel pausing a thread that would otherwise keep running. The paused thread stays runnable and gets another turn later.

Why does a context switch cost more than the few microseconds of saving and restoring registers?

  1. The incoming thread finds the CPU caches full of the previous thread's data and must refill them from slower memory
  2. Registers are stored on disk
  3. The kernel must reboot the core
  4. Every switch needs a network round trip
The direct cost is small. The hidden cost is cold caches (and, between processes, a changed address space), which slow the first stretch of the new thread's run.

A 4-core machine shows a load average of 16. What does that most likely suggest?

  1. The machine is 16% idle
  2. It has 16 cores
  3. Memory is nearly full
  4. On average about 12 more threads want to run than the cores can run, so work is queueing (or, on Linux, threads are stuck on slow I/O)
Load is roughly running plus waiting-for-a-turn threads. Far above the core count means a queue. top then shows whether it's CPU or I/O.

Why does a sleeping, I/O-bound thread cost the scheduler almost nothing?

  1. It is deleted until its data arrives
  2. It is blocked, not in the run queue, so it takes no CPU until the kernel wakes it
  3. It is always given the lowest priority
  4. It runs on a special core
Only runnable threads compete for cores. A blocked thread just holds some memory, which is why a server can have many mostly-idle connections but not many busy threads.

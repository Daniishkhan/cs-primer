Event Loops

One thread, ten thousand connections, and no thread ever sitting idle. This chapter builds the machine that makes that possible: the system call that waits for many sockets at once, the loop wrapped around it, the timers inside it, and the single rule you must never break. By the end you will have written a working echo server and understood how nginx, Node.js and Redis stay fast.

Why this matters

The event loop is probably the most reused idea in server software. Web servers, databases, message brokers, browsers, GUI toolkits, and the runtimes behind Node.js, Python's asyncio and Rust's Tokio are all event loops at heart. When an interviewer asks "how would you serve 100,000 mostly-idle connections?" or "why did the whole service freeze for two seconds?", the answer is in this chapter. It also explains one of the most common production surprises: a single slow function that stops everything.

From "wait for one" to "wait for many"

In chapter 15 we ended with a wish list: one system call that puts the thread to sleep until any of a large set of sockets is ready, and then tells us which. That is exactly what the family of calls in this chapter does. They all provide readiness notification: the kernel does not do the reading for you, it only tells you "socket 7 would not block if you called recv() on it right now". You then call recv() yourself, in non-blocking mode, and it succeeds immediately.

(There is a second style, completion notification, where you ask the kernel to do the whole read and it tells you when it is done. Windows' IOCP and Linux's io_uring work that way. This chapter is about readiness, which is what select, poll, epoll and kqueue offer, and which still dominates server code on Linux and macOS.)

select, poll, epoll and kqueue

These four calls solve the same problem, and each one fixed a scaling flaw in the one before. Knowing the flaws tells you why the later ones exist.

CallHow you use itThe problem it has
select (very old, everywhere)Each call, you pass three bitmaps of file descriptor numbers to watch (readable, writable, error). It returns with the bits left set only for ready descriptors.The bitmap has a fixed size, FD_SETSIZE, commonly 1024, and it is indexed by descriptor number, so descriptor 1500 cannot be used even if you watch only one. The kernel scans all the bits, and you must scan them again to find the set ones: O(n) work per call. Also you rebuild the bitmaps every time because they are overwritten.
poll (POSIX)Pass an array of {fd, events} records. No fixed limit and no rebuilding bit-by-bit.Still O(n): the whole array is copied into the kernel and scanned on every call, even if only one socket is ready.
epoll (Linux)Create an epoll object once. Add/modify/remove interest with epoll_ctl as connections come and go. epoll_wait returns only the ready entries.Linux only. The kernel keeps the interest list, so the cost of a wait depends on the number of ready events, not on the number of registered sockets.
kqueue (macOS, BSDs)The same idea: register once, then kevent returns only events that fired. It can also watch files, signals, timers and processes.Not on Linux. Different API from epoll, same shape.

You rarely call these directly. Python's selectors module wraps all of them behind one interface, and selectors.DefaultSelector picks the best one for the platform: kqueue on macOS, epoll on Linux, falling back to poll or select elsewhere. Libraries like libuv (under Node.js), libevent and Tokio do the same.

Go deeper: level-triggered vs edge-triggered optional

When exactly should the kernel say "socket 7 is readable"? There are two answers.

Level-triggered (the default for select, poll, epoll, and what Python's selectors gives you): you are told "readable" every time you ask as long as unread data remains. If you read only part of what is in the buffer, the next wait returns immediately and tells you again. It is forgiving: a handler that does too little just gets called again.

Edge-triggered (EPOLLET on Linux; EV_CLEAR in kqueue): you are told only when the state changes from not-ready to ready, i.e. when new data arrives. If you read half the buffer and stop, you hear nothing more about that socket until even more data arrives, so you must read until the call returns EAGAIN. This saves wake-ups when the handler would have drained the socket anyway, but it is easy to get wrong: a missed drain means a connection that looks stuck forever. It also needs fairness care, because a very busy socket that you drain completely can starve the others.

Rule of thumb: start with level-triggered. Reach for edge-triggered only when profiling shows wake-ups matter, and then always read or write until EAGAIN.

The reactor pattern

Wrap one of those calls in a loop and add a table of "who cares about what", and you have the reactor pattern, the usual name for an event loop built on readiness notification. It has three moves, repeated forever:

  1. Register interest. Tell the selector: "when socket 7 is readable, call this function". The function is a callback (or handler): a piece of code you hand over for someone else to call later.
  2. Wait. Call the selector's wait function, giving a timeout (more on that shortly). The thread sleeps in the kernel at no CPU cost until something is ready or the timeout expires.
  3. Dispatch. For each ready event, call the registered callback. Each callback does a small amount of non-blocking work, maybe registers new interest, and returns. Then go back to step 2.

Analogy: a host with a board of buzzers

Back in the restaurant, instead of one waiter per table, a single host stands by a board of buzzers, one per table. They do nothing until a buzzer lights. Then they walk to that table, take the order, and return to the board. They also keep a list of reminders ("check table 9 at 8:15"), and the next reminder decides how long they are willing to stand still. Hundreds of tables, one host, because almost every table is quiet almost all the time.

Where it breaks down: if the host starts a ten-minute errand for one table, every other buzzer waits. A real restaurant has other staff to cover; a single-threaded loop does not. This is why slow work must go to a separate worker (the kitchen) and why the cardinal rule below exists. Also, unlike a person, the host cannot be interrupted in the middle of a callback: each one runs to completion before the next begins.

Notice what this buys us. Callbacks never run at the same time, so two callbacks never race on the same data (chapter 11). No locks are needed for state that only the loop touches. The price is that you must write code in small non-blocking pieces, "do this, then when that is ready do the next thing", instead of straight-line code. The next chapter shows how languages hide that.

Timers inside the loop

Real servers need to do things "after a delay": close a connection that has been silent for 90 seconds, retry a request, send a heartbeat. The loop supports this without any extra threads, by choosing the timeout of its wait call carefully.

The loop keeps its timers in a min-heap: a data structure where the entry with the earliest deadline is always at the front, and inserting or removing costs O(log n) (Python's heapq). Before each wait, the loop looks at the front of the heap and computes

timeout = next deadline − now

(or "forever" if there are no timers). The wait call then sleeps either until a socket is ready or until that deadline, whichever comes first. When it wakes, the loop runs every timer whose deadline has passed. So a loop with one timer and no traffic sleeps exactly until the timer is due, using no CPU in between. Deadlines use a monotonic clock (Python: time.monotonic()), which never jumps backwards when the system clock is corrected, unlike wall-clock time. Using the wrong clock for timers is a classic bug in the real world.

Here is a complete miniature loop, built straight from those ideas, with one trick added: it measures how late each timer fires. Everything runs on a socketpair, so there is no network. One handler is deliberately bad.

import heapq
import itertools
import selectors
import socket
import time

sel = selectors.DefaultSelector()
timers = []                          # heap of (deadline, tie_breaker, callback)
tie = itertools.count()


def call_later(delay, fn):
    heapq.heappush(timers, (time.monotonic() + delay, next(tie), fn))


def add_reader(sock, fn):
    sel.register(sock, selectors.EVENT_READ, fn)


def run_forever(until):
    while time.monotonic() < until:
        # 1. WAIT: sleep until a socket is ready OR the earliest timer is due
        timeout = max(0, timers[0][0] - time.monotonic()) if timers else 0.1
        events = sel.select(timeout)
        # 2. DISPATCH sockets, then timers that are due
        for key, _mask in events:
            key.data(key.fileobj)
        while timers and timers[0][0] <= time.monotonic():
            deadline, _, fn = heapq.heappop(timers)
            lag_ms = (time.monotonic() - deadline) * 1000
            fn(lag_ms)


# --- a demo: one socket event, two timers, and one handler that hogs the loop ---
a, b = socket.socketpair()
a.setblocking(False)


def on_readable(sock):
    print("socket readable:", sock.recv(100))
    t = time.monotonic()
    while time.monotonic() - t < 0.3:      # BAD: 300 ms of CPU work inside the loop
        pass


def tick(name):
    return lambda lag_ms: print(f"timer {name} fired, loop lag {lag_ms:5.1f} ms")


add_reader(a, on_readable)
call_later(0.10, lambda lag: b.send(b"hi"))   # at 100 ms the "client" sends data
call_later(0.15, tick("A (due at 150 ms)"))
call_later(0.20, tick("B (due at 200 ms)"))
call_later(0.60, tick("C (due at 600 ms)"))
run_forever(until=time.monotonic() + 0.7)
socket readable: b'hi'
timer A (due at 150 ms) fired, loop lag 251.1 ms
timer B (due at 200 ms) fired, loop lag 201.1 ms
timer C (due at 600 ms) fired, loop lag   1.0 ms

Your exact lag numbers will differ by a millisecond or so, but the shape will not. Timers A and B were due at 150 and 200 ms. The socket handler began at about 100 ms and hogged the loop for 300 ms, so both fired about 250 ms and 200 ms late. Timer C, scheduled well after the hogging ended, was on time. That is the cardinal rule in action.

The cardinal rule: never block the loop

Since one thread runs all callbacks, any callback that takes a long time delays every other connection and every timer. The loop does not preempt callbacks: nothing steps in and says "you've had enough time". Things that accidentally block the loop:

  • CPU-heavy work: compressing a large payload, a slow regular expression (the subject of a case study), sorting a huge list, parsing a giant JSON document.
  • A blocking system call: time.sleep(), a synchronous database driver, a plain requests.get(), a DNS lookup through getaddrinfo (which blocks), or reading a file from disk (chapter 15).
  • Logging to a slow or blocked destination, such as a full pipe or a network file system.
  • A garbage collection pause (chapter 3), which looks identical from the outside.
  • Waiting on a lock held by another thread (chapter 12).

The two remedies: do the work in small pieces (yield to the loop between chunks), or hand it to a thread pool or process pool and have the pool post the result back as an event (chapter 14). That is the "kitchen" in our analogy.

How do you know it is happening? Measure loop lag: how late the loop is in doing what it promised. The simplest probe is a timer that fires every 100 ms and records how much later than 100 ms it actually ran, exactly like the lag column in the demo above. In a healthy loop, lag stays near zero; spikes mean something blocked. Good servers export it as a metric and alert on its 99th percentile. Python's asyncio has a debug mode (PYTHONASYNCIODEBUG=1 or asyncio.run(..., debug=True)) that logs any callback slower than 100 ms by default; Node has similar tools. When a service "randomly freezes for a second", loop lag is the first thing to look at.

Common misconception

"An event loop is fast because it does things in parallel." It doesn't: one callback runs at a time. It is efficient because it never sits idle while there is work, and because waiting costs almost nothing. For CPU-bound work, a single event loop is no faster than a plain loop; it is actually slower than a thread pool using several cores. An event loop wins when the workload is mostly waiting.

Writing: partial writes, output buffers and write interest

Reading is easy to fit into the loop: wait until readable, then read. Writing has a catch. A non-blocking send() can accept only part of your data (chapter 15), because the socket's send buffer may be nearly full. A slow client on a bad mobile connection does not drain its buffer, so your reply stalls halfway. You cannot wait for it, because waiting is exactly what you must not do. The standard technique:

  1. Give each connection an output buffer in your own memory, holding bytes you owe the client.
  2. Append your reply to it, then call send() and remove only as many bytes as it reported sent.
  3. If bytes remain, register write interest ("tell me when this socket is writable"). If you did not have anything to write, do not register it: an idle socket is almost always writable, and the loop would spin, waking constantly for nothing.
  4. When the loop reports writable, call send() again. When the buffer is empty, drop write interest.

Backpressure per connection

The output buffer is itself a queue, and as chapter 14 taught, an unbounded queue is a time bomb. If a client never reads and you keep reading its requests and appending replies, the buffer grows until the process runs out of memory, taking every other client with it. So every connection needs a bounded output buffer and a policy for what to do when it fills up. The best simple policy is exactly what our echo server below does: stop reading from a client while we still owe it output. That pushes the problem back to the client: its own send buffer fills, and TCP's flow control (networking chapter 8) makes the client slow down. Other policies: drop old data (fine for presence updates), or disconnect the slow consumer.

A complete echo server

Here is a real, working server using all of the above: non-blocking sockets, DefaultSelector, per-connection output buffers, write interest, and read-stop backpressure. It echoes back whatever each client sends. Read the comments, then we'll run it.

import selectors
import socket

HOST, PORT = "127.0.0.1", 9000
sel = selectors.DefaultSelector()      # epoll on Linux, kqueue on macOS


class Conn:
    """Everything the loop remembers about one client."""
    def __init__(self, sock):
        self.sock = sock
        self.out = bytearray()          # bytes we still owe this client


def set_interest(conn):
    # Backpressure: while we still owe bytes, stop reading from this client
    # and wait only until its socket can accept more. Otherwise just listen.
    events = selectors.EVENT_WRITE if conn.out else selectors.EVENT_READ
    sel.modify(conn.sock, events, conn)


def close(conn):
    sel.unregister(conn.sock)
    conn.sock.close()


def flush(conn):
    """Send as much as the kernel will take right now. Returns False if the client is gone."""
    try:
        n = conn.sock.send(conn.out)    # may send fewer bytes than asked: partial write
    except (BlockingIOError, InterruptedError):
        return True                     # buffer full; wait for EVENT_WRITE
    except OSError:
        return False                    # reset by peer, broken pipe, ...
    del conn.out[:n]                    # keep only the unsent tail
    return True


def on_accept(lsock):
    try:
        sock, _addr = lsock.accept()
    except BlockingIOError:
        return                          # someone else got there first
    sock.setblocking(False)
    sel.register(sock, selectors.EVENT_READ, Conn(sock))


def on_ready(conn, mask):
    if mask & selectors.EVENT_READ:
        try:
            data = conn.sock.recv(65536)
        except (BlockingIOError, InterruptedError):
            return
        except OSError:
            return close(conn)
        if not data:                    # empty bytes = the client closed its side
            return close(conn)
        conn.out += data
    if conn.out and not flush(conn):    # try to write straight away (usually succeeds)
        return close(conn)
    set_interest(conn)                  # READ if we're done, WRITE if bytes remain


def serve():
    lsock = socket.socket()
    lsock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    lsock.bind((HOST, PORT))
    lsock.listen(128)
    lsock.setblocking(False)
    sel.register(lsock, selectors.EVENT_READ, None)   # data=None marks the listener
    print(f"listening on {HOST}:{PORT} using {type(sel).__name__}", flush=True)
    while True:
        for key, mask in sel.select(timeout=1.0):     # the ONLY place we wait
            if key.data is None:
                on_accept(key.fileobj)
            else:
                on_ready(key.data, mask)


if __name__ == "__main__":
    serve()

Some details worth noticing. The listening socket is registered like any other: "readable" means a connection is waiting to be accepted. send() may send fewer bytes than requested, so we delete only what was sent (del conn.out[:n]) and keep the rest. While conn.out is non-empty the connection watches only for "writable", which is both write interest and our backpressure. And the whole program has a single place where it can sleep, sel.select(...). Now a client that tests it, sending 4 MiB (far more than any socket buffer holds) and checking it all comes back:

import socket
import threading

PAYLOAD = b"0123456789abcdef" * 262144          # 4 MiB, far more than any socket buffer

with socket.create_connection(("127.0.0.1", 9000)) as s:
    # Send from a second thread. If one thread did sendall() and only then recv(),
    # both sides could end up blocked waiting for the other to read. See the warning below.
    sender = threading.Thread(target=s.sendall, args=(PAYLOAD,))
    sender.start()
    received = bytearray()
    while len(received) < len(PAYLOAD):
        chunk = s.recv(65536)
        if not chunk:
            break
        received += chunk
    sender.join()

print("sent", len(PAYLOAD), "bytes, got back", len(received), "bytes,",
      "identical" if bytes(received) == PAYLOAD else "DIFFERENT")

A deadlock to know about

Our client used a second thread to send. We tested what happens without it: a client that calls sendall() with 16 MiB before it ever calls recv() got stuck for good. The server stops reading while it has unsent echo data (backpressure!), the client is blocked sending and cannot read the echo, and each side waits for the other to read. Nobody is buggy; the system is just full. Real protocols avoid this by reading and writing at the same time, as our client does, or by having a request/response shape that never pushes unbounded data in one direction. Unlimited buffering would "fix" the hang by hiding it, and eat all your memory.

Using every core: one loop per core

An event loop runs on one thread, so one loop uses one core. (In Python, the GIL forbids running Python bytecode in parallel in one process anyway, chapter 10.) Yet for many servers one core is not enough. The standard answer is one loop per core, each with its own connections that it owns forever, so no connection state is ever shared between threads and no locks are needed on the hot path. The question is how connections get divided:

  • SO_REUSEPORT: each loop (a thread or a separate process) creates its own listening socket on the same port, with this option set. On Linux, the kernel then spreads incoming connections across those sockets. (BSD and macOS accept the option but divide connections differently, so don't rely on the spreading there.)
  • An acceptor that hands out connections: one loop accepts everything and passes each new socket to one of the other loops, round-robin. More portable, with a small extra step and one busy loop at the front.

This is the shape of nginx (a master process and several worker processes, each with its own event loop). Redis makes the opposite choice on purpose, running commands on a single thread so that its data structures need no locks at all (see the Redis case study); to use more cores you run several Redis instances. In Python you would run one loop per process with multiprocessing (chapter 5).

Why this exists: the C10k problem

In the late 1990s, web servers were mostly thread-per-connection or process-per-connection. Around 1999 Dan Kegel wrote up what became known as the C10k problem: how do you handle ten thousand concurrent connections on one machine? Hardware had finally become capable of it, but the dominant software designs were not. The fixes that followed were what this chapter described: non-blocking sockets with scalable readiness notification (epoll on Linux, kqueue on BSD) and an event-driven architecture.

The servers built that way became household names. nginx put an event loop in each worker process and became a standard front-end server and load balancer. Node.js brought the same model to JavaScript, with one event loop and a small thread pool for the work (files, DNS) that cannot be made non-blocking. Redis serves a huge number of requests per second from a single thread. Read the stories in Ten Thousand Connections: nginx & C10k and Redis: One Thread, Very Fast. Today, with the machines of the 2020s, ten thousand connections is routine and the same ideas are used for hundreds of thousands or more.

Distributed systems connection

An event loop that is blocked looks, from outside, exactly like a machine that has failed. Heartbeats are not sent on time, health checks time out, and failure detectors in other nodes conclude "it's dead" even though the process is perfectly healthy and merely busy (networking chapter 16). Many "split brain" and flapping-leader incidents begin with a node whose loop (or garbage collector) paused for a few seconds. Loop lag is therefore a first-class health signal, and the same discipline applies to any node in a cluster: keep the thread that does liveness work free from slow work.

Key takeaways

  • select, poll, epoll and kqueue all say "which of these sockets are ready?". select has a descriptor limit (commonly 1024) and O(n) scans; poll lifts the limit but is still O(n); epoll and kqueue keep a registration in the kernel and return only the ready ones.
  • The reactor pattern: register interest and callbacks, wait, dispatch. Callbacks run one at a time to completion, so loop-owned data needs no locks.
  • Timers live in a heap of deadlines; the wait timeout is the time until the earliest deadline, measured on a monotonic clock.
  • Never block the loop. One slow callback delays every other connection and every timer. Measure loop lag, and send slow or blocking work to a thread or process pool.
  • Non-blocking send() may accept only part of your data. Keep a per-connection output buffer, register write interest only while it is non-empty, and bound it. Pausing reads while output is pending is simple backpressure.
  • One loop uses one core. To use all cores, run one loop per core (SO_REUSEPORT or an acceptor), each owning its connections.
  • The C10k problem (named by Dan Kegel around 1999) is why nginx, Node.js and Redis look the way they do.

Check your understanding

What is the main scaling advantage of epoll and kqueue over select and poll?

  1. They read the data from the socket for you
  2. The kernel keeps the interest list, so each wait costs in proportion to the number of ready events, not the number of watched sockets
  3. They allow multiple threads to share a socket without locks
  4. They make the network faster
select and poll hand the entire list of descriptors to the kernel on every call, and the kernel (and your code) scan all of them. epoll and kqueue register interest once and return only what's ready. They still tell you only about readiness; you do the reading.

An event loop has one timer due in 40 ms and no socket activity. What does the loop pass as the timeout to its wait call?

  1. Zero, so it can check again immediately
  2. Infinity, because timers are handled by another thread
  3. A fixed 1 second
  4. About 40 ms: the earliest deadline minus the current time
Timeout = next deadline - now. The loop sleeps for exactly that long (or less, if a socket becomes ready first), so it uses no CPU in between and still fires the timer on time, as long as no callback is hogging the loop.

A callback in your event-loop server takes 800 ms of CPU time. What is the effect on other connections?

  1. All of them, and all timers, are delayed by up to 800 ms, because the loop runs only one callback at a time and does not interrupt it
  2. None; the event loop runs the callbacks in parallel
  3. Only connections in the same TCP flow are affected
  4. The kernel preempts the callback after 10 ms
The kernel can preempt the thread, but it has nothing else to run for this process. Inside the process, the loop is cooperative: nothing interrupts a callback. Hence the rule "never block the loop", and the practice of watching loop lag.

In the echo server, why do we register for "writable" only while the connection's output buffer is non-empty?

  1. Because writable events are expensive for the kernel to generate
  2. Because sockets can only be registered for one kind of event
  3. An idle socket is nearly always writable, so permanent write interest would wake the loop constantly with nothing to do
  4. Because TCP forbids sending without a request
"Writable" just means "the send buffer has room", which is almost always true. We ask to hear about it only when we have bytes we couldn't send yet, and drop the registration as soon as the buffer is empty.

How can a single machine with 8 cores run event-loop servers on all of them without sharing connection state between threads?

  1. By making one loop use all 8 cores automatically
  2. By running one loop per core, each owning its own connections, with connections spread by SO_REUSEPORT or by an acceptor that hands them out
  3. By placing a global lock around every callback
  4. It is impossible; event loops are limited to one core
A loop is single-threaded but you can run several. Each connection lives its whole life on one loop, so loops don't need locks on connection state. nginx works this way; Redis chooses a single thread deliberately.

Which statement about level-triggered readiness is correct?

  1. You are told only once when data arrives, and never again until new data arrives
  2. It cannot be used with non-blocking sockets
  3. You are told "readable" on every wait for as long as unread data remains, so a handler that reads only part of it will be called again
  4. It requires one thread per socket
That is the forgiving default (and what Python's selectors use). The "only on change" behavior describes edge-triggered mode, which needs you to drain the socket until EAGAIN.

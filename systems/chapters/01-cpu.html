CPUs & Instructions

Underneath every server, database and web page is a small piece of silicon doing one very simple thing, over and over, billions of times a second. In this chapter you'll see what a program physically is, how a CPU runs it, why your Python code is slower than the same idea written in C, and why chips stopped getting faster in one place and started getting wider instead.

Why this matters

Every performance question eventually reduces to "how many instructions, and how long does each one wait?". If you know what an instruction is, you can see why an interpreted language costs more than a compiled one, why a single-threaded server can't use a 32-core machine, and why almost all modern software has to be concurrent. This is the foundation for the next two chapters and for all of Part 3.

What a program physically is

When you write x = x + 1, you're writing for people. The CPU (central processing unit) can't read that. It understands only a short list of tiny, concrete operations such as load a number from memory, add two numbers, store a number back, jump to another place in the program. Each of these is an instruction, and on disk or in memory it's just a few bytes, a pattern of 1s and 0s. A list of such instructions is machine code, and a program that has been turned into it is what the operating system actually loads and runs.

Here is the idea in a made-up, readable notation (real instruction sets use different names and details, but the shape is the same):

# address  instruction        meaning
100        LOAD  r1, [x]      copy the number stored at x into register r1
104        ADD   r1, r1, 1    r1 = r1 + 1
108        STORE [x], r1      copy r1 back to the place called x
112        JUMP  100          go back and do it again (for a loop)

The r1 is a register: a tiny storage slot built into the CPU itself, big enough for one number (64 bits on today's machines). A CPU has only a few dozen of them, but they're by far the fastest storage in the whole computer, because the arithmetic circuits sit right next to them. All real work happens on registers. Memory (RAM) is where everything else lives, and the CPU has to load values from it into registers and store results back. How slow that trip is turns out to matter enormously, and chapter 2 is entirely about it.

Different CPU families understand different instruction sets. Most laptops and servers use x86-64 (Intel and AMD), while phones, Apple's M-series chips and many cloud servers use ARM64. A program compiled for one won't run on the other without translation. That's why you download different installers for "Intel" and "Apple Silicon".

Analogy: a cook following a recipe card

In our kitchen, the CPU core is a cook. The recipe is the program: a list of very small steps ("crack egg", "add 5 g of salt", "go back to step 3"). The cook's hands and the cutting board in front of them are the registers: only a few things fit, but anything there can be used instantly. The pantry down the hall is RAM: it holds much more, but every trip costs time.

Where it breaks down: a human cook understands "make a sauce". A CPU has no idea what a sauce is. It only knows a few hundred primitive operations, and everything bigger is built by stacking them.

Fetch, decode, execute

A CPU runs a program by repeating one loop forever. A special register called the program counter (PC) holds the address of the next instruction. The loop is:

  1. Fetch: copy the instruction at the address in the PC from memory into the CPU.
  2. Decode: work out what it means: which operation, which registers.
  3. Execute: do it. Arithmetic happens in the ALU (arithmetic logic unit); loads and stores talk to memory.
  4. Write back and advance: store the result in a register, and move the PC to the next instruction (or, for a jump, to a new address). Repeat.

That is the entire trick. A web browser, a database and a video game are all the same loop running different instructions. There is no "understanding" anywhere, only a fast and obedient fetch, decode, execute cycle.

The clock: how fast is fast?

The loop is paced by a clock: a signal that ticks at a fixed rate, and everything inside the CPU moves forward one step per tick. A tick is a cycle. The rate is measured in hertz: a GHz (gigahertz) is a billion cycles per second.

  • A 1 GHz clock has one cycle per nanosecond (a billionth of a second).
  • A typical 3 GHz core has about 0.33 ns per cycle. In that time light, the fastest thing there is, travels only about 10 cm.

How many instructions is that per second? Not simply "3 billion", because it depends on the instruction and on whether the CPU has to wait. Simple instructions on data already in registers can finish in about one cycle, and modern cores can even start several instructions in the same cycle. So a well-fed core can reach several billion instructions per second. But when an instruction needs data that isn't nearby, it waits (roughly 100 ns for RAM, which is around 300 cycles at 3 GHz). A real program spends a big share of its time waiting like this, so a more typical figure is somewhere below that peak. We'll look at why in chapter 2.

Compare that with the code you write in a high-level language. A plain Python loop manages something like tens of millions of simple operations per second, a hundred times fewer than the hardware's instruction rate. The next section explains where the gap comes from.

Common misconception

"A higher GHz number means a faster computer." Only roughly, and only between very similar chips. How much work a chip gets done per cycle varies a great deal between designs, and so does how well it hides waiting for memory. A 3 GHz modern core can easily outrun a 4 GHz core from fifteen years ago. Clock speed is one ingredient, not the score.

Cores: several CPUs in one chip

A core is one complete fetch-decode-execute engine with its own registers and its own small, fast cache (chapter 2). A modern chip puts several cores side by side: a laptop might have 8 to 12, a server chip dozens. All the cores share the same RAM and run different instruction streams at the same time. Four cores can run four programs, or four parts of one program, truly simultaneously.

Many chips also offer hardware threads (marketed as hyper-threading or SMT): one physical core presents itself as two logical CPUs and juggles two instruction streams, filling the idle moments of one with the work of the other. The operating system counts each as a CPU, so the number you see in nproc may be double the real core count. It helps, but two hardware threads are nowhere near as good as two real cores.

The important point: a program that runs one sequence of instructions uses one core. On a 16-core machine, a single-threaded program uses at most 1/16 of the capacity, and the other fifteen cores sit idle or serve other programs. To use the whole chip, a program must be split into pieces that can run at the same time. That's the subject of Part 3.

Compiled, interpreted and JIT

Nobody writes machine code by hand any more. So how does x + 1 in your favourite language become instructions? There are three main routes.

Analogy: translating a book

Compiled is translating the whole book into the reader's language before you hand it over. The reader can then just read, at full speed. Interpreted is having a translator sit beside the reader and translate sentence by sentence, every time the book is read. Flexible, but slow. JIT (just-in-time) is a translator who starts out doing it sentence by sentence, notices which pages the reader keeps re-reading, and writes proper translations of exactly those pages.

Where it breaks down: an interpreter doesn't translate into another language at all. It's an ordinary compiled program (CPython's is written in C) containing a big loop that looks at each bytecode and does what it says.

A real example: Python bytecode

The standard Python (CPython) first compiles your source to bytecode: instructions for an imaginary, simple machine, one that doesn't exist in silicon. The interpreter then runs those bytecodes one at a time. The standard library's dis module (disassembler) shows them. This is the same x + 1 from before:

$ python3 -c "import dis; dis.dis(lambda x: x + 1)"
  1           0 RESUME                   0
              2 LOAD_FAST                0 (x)
              4 LOAD_CONST               1 (1)
              6 BINARY_OP                0 (+)
             10 RETURN_VALUE

It looks just like our machine-level example: load x, load the constant 1, add, return. (The exact names and numbers depend on your Python version: older versions say BINARY_ADD instead of BINARY_OP and have no RESUME.) The big difference is what happens when each bytecode runs. For BINARY_OP the interpreter's C code must look at both operands to find out what type they are (an integer? a string? something with its own __add__?), choose the right addition, allocate a result object, adjust reference counts (chapter 3) and only then move to the next bytecode. A single bytecode costs dozens of real machine instructions, where compiled C code adding two integers needs one. That's where the roughly hundredfold gap in "operations per second" comes from.

The trade is deliberate: an interpreter gives you flexibility, fast start-up, readable error messages and "just run the file". A JIT compiler such as the ones in the Java Virtual Machine or JavaScript's V8 claws back much of the speed. It watches the running program, finds the loops and functions that run constantly, and compiles just those to real machine code, using what it learned about the actual types. It costs some start-up time and memory. (Recent versions of CPython have been adding an experimental JIT as an optional build, but the standard Python you run today is still the plain interpreter.)

Common misconception

"Python doesn't run machine code, it runs Python." Every program, in every language, ends up as machine instructions on the CPU. In Python's case the machine code is the interpreter's, and your bytecode is just the data it chews through. This is also why Python programs get faster when the work moves into compiled libraries (NumPy, the sum() built-in, regex engines): the heavy loop runs as machine code, and the interpreter is only called once.

Why we got more cores instead of faster ones

For several decades, each new generation of chip came with a higher clock speed, and programs got faster for free: the same code simply ran sooner on a newer machine. In the mid-2000s that stopped. Clock speeds settled in the low-to-mid single-digit gigahertz and have stayed roughly there since.

The simple, qualitative reason is heat. Switching billions of tiny transistors on and off consumes power, and the power grows quickly as you raise the clock (higher clocks also need higher voltage). All that power turns into heat in a few square centimetres of silicon, and there is only so much heat a heat sink and a fan can carry away. Past a certain point, a faster clock can't be cooled, and in a phone it can't even be powered.

Transistors, however, kept getting smaller, so chip designers had a growing budget of transistors but no way to make each one run much faster. They spent the budget on more cores, bigger caches and cleverer circuitry. A well-known 2005 essay by the software engineer Herb Sutter was titled "The Free Lunch Is Over" for exactly this reason: from then on, programs would speed up only if they were written to use many cores at once.

Why this makes concurrency matter

That is the origin of nearly everything in Part 3. If a machine has 16 cores and your program has one flow of execution, you're using one sixteenth of what you paid for. To go faster you must do several things at the same time, and the moment two flows touch the same data you meet race conditions, locks and deadlocks (chapters 10–13). Concurrency isn't an advanced optimisation any more. It's the normal way to use the machine you own.

There's a limit, too. Some parts of a task can't be split, such as steps that each need the previous result. If 10% of a job must run in sequence, then even with unlimited cores it can never go more than 10 times faster. This is known as Amdahl's law. It's one reason adding cores often helps less than people hope, and why designs that avoid the sequential bottleneck (queues, partitioning) are valued.

There's a second, subtler consequence. Even with one core, a server spends most of its time waiting: for the network, for the disk. Keeping that core busy with other work during the wait is the topic of chapters 15–17 (blocking I/O and event loops). In both cases, the central skill is the same: keep every core doing useful work and never leave it staring at a wall.

Go deeper: pipelining and branch prediction optional

Our "fetch, then decode, then execute" story is a simplification. If a CPU really finished each instruction completely before starting the next, most of its circuits would sit idle most of the time. Instead, cores use pipelining, which works like a laundry line: while instruction 1 is being executed, instruction 2 is being decoded and instruction 3 is being fetched. Each stage always has something to do, so in the best case one instruction finishes every cycle, and modern cores widen this by running several pipelines side by side. That's how they exceed "one instruction per cycle".

The pipeline has an enemy: branches. After an if the CPU doesn't know which instruction comes next until the condition has been computed, and by then the pipeline has already started fetching down one path. So CPUs guess. A branch predictor uses the history of past outcomes to bet on which way a branch will go, and the CPU speculatively runs ahead down that path. If the guess was right, no time is lost. If it was wrong, the work is thrown away and the pipeline restarts, costing roughly a dozen or more cycles. Predictors are very good on regular patterns (a loop that runs 1,000 times) and much worse on unpredictable data. A classic demonstration is that running through a sorted array with an if in the loop can be noticeably faster than the same array shuffled, even though the instructions executed are identical. Sorting made the branch predictable.

Speculative execution also turned out to have security consequences: the Spectre and Meltdown vulnerabilities, made public in 2018, exploited side effects of work the CPU had guessed ahead and then undone. The mitigations cost some performance, a reminder that these invisible optimisations have real consequences.

Try it yourself

Try it yourself: look at bytecode and meet your CPU

All of these only read information. Your output will differ from the examples, and that's the point.

# 1. The bytecode behind a tiny function
$ python3 -c "import dis; dis.dis(lambda x: x + 1)"
  1           0 RESUME                   0
              2 LOAD_FAST                0 (x)
              4 LOAD_CONST               1 (1)
              6 BINARY_OP                0 (+)
             10 RETURN_VALUE

# 2. What CPU is this? (macOS first, then Linux)
$ sysctl -n machdep.cpu.brand_string
Apple M2 Pro
$ lscpu | head -20                  # Linux / WSL: model, cores, threads per core, cache sizes

# 3. How many CPUs does the OS see?
$ sysctl -n hw.ncpu                   # Linux: nproc
10
$ python3 -c "import os; print(os.cpu_count())"
10

# 4. How long does one Python addition take? (timeit repeats it many times)
$ python3 -m timeit -s "x = 1" "x + 1"
10000000 loops, best of 5: 14.2 nsec per loop

On an Intel Mac the brand string will name an Intel Core chip instead; on Linux, lscpu prints fields such as "Model name", "Core(s) per socket" and "Thread(s) per core". Multiply cores by threads per core to get the CPU count your OS reports. If you divide one second by the nanoseconds in the last command, you get Python's operation rate: with 14 ns, about 70 million additions per second. That's the "tens of millions", compared with several billion machine instructions a second available underneath.

Optional: run dis.dis on a function with a loop or an if and look for the jump instructions. They're the same kind of JUMP we used in the machine-level example.

Distributed systems connection

The shape of a single chip, many cores sharing one memory, sets the first fork in system design. You can scale up (a bigger machine with more cores, which is simple because all cores see the same memory) or scale out (more machines connected by a network, which is how distributed systems begin). The same ideas recur at both sizes: work has to be divided, shared data needs coordination, and not everything can be parallelised. Scaling out swaps cheap shared memory for a slow, unreliable network (networking ch. 13), so it's worth squeezing a single machine properly first. CPU is also a resource that can run out: one badly written regular expression once used up all the CPU on a global fleet of servers.

Key takeaways

  • A program is a list of small machine instructions plus data. The CPU runs it with a simple loop: fetch, decode, execute, repeat.
  • Registers are the CPU's tiny, instant storage. Everything else, starting with RAM, is further away and slower (chapter 2).
  • A 3 GHz clock means about 3 billion cycles per second, and a good core can do several billion instructions per second. Real programs get less because they wait for memory.
  • Compiled code runs directly as machine code. CPython compiles to bytecode and runs it through an interpreter loop, costing dozens of machine instructions per bytecode. A JIT compiles the hot parts at run time.
  • Clock speeds stopped growing in the mid-2000s because of heat and power, so chips grew more cores instead.
  • A single-threaded program uses one core. To use a modern machine, software must be concurrent, which is why Part 3 exists.

Check your understanding

What does the program counter hold?

  1. The number of instructions executed so far
  2. The result of the last calculation
  3. The address in memory of the next instruction to fetch
  4. The clock speed of the CPU
The program counter is a register that points at the next instruction. After each instruction it advances (or jumps somewhere new). It doesn't count anything or store results. Those are other registers.

A CPU runs at 2 GHz. Roughly how long is one clock cycle?

  1. 2 nanoseconds
  2. 0.5 nanoseconds
  3. 2 microseconds
  4. 0.5 milliseconds
2 GHz is 2 billion cycles per second, so each cycle takes 1/2,000,000,000 of a second: 0.5 ns. This is also why a trip to RAM, about 100 ns, is hundreds of cycles of waiting.

Why does a plain Python loop run so much more slowly than the equivalent C loop?

  1. Python can't use the CPU's registers
  2. Python programs don't run on the CPU at all
  3. Python's clock speed is lower
  4. Each bytecode is handled by interpreter code that checks types, allocates objects and updates reference counts, costing many machine instructions where C needs one
Everything runs on the CPU, at the same clock speed. The gap is the work the interpreter does around every operation. That is also why moving a hot loop into a compiled library helps so much.

Why did chip makers start adding cores instead of raising clock speeds in the mid-2000s?

  1. Higher clock speeds produced more heat and power than could be cooled, while smaller transistors made extra cores affordable
  2. Software had stopped needing faster CPUs
  3. Clock speed is not measurable above 3 GHz
  4. Operating systems can't run on faster clocks
It was a power and heat limit, not a lack of demand. The side effect landed on programmers: single-threaded code no longer sped up on new chips, so concurrency became essential.

A single-threaded program is running on a 16-core machine. Roughly how much of the machine's compute can it use?

  1. All of it, since the OS spreads the work across cores automatically
  2. Half of it
  3. About one core's worth: one sequence of instructions runs on one core at a time
  4. None. Single-threaded programs can't run on multi-core chips
The OS can move the program between cores, but a single flow of instructions still runs on one core at a time. To use the other fifteen, the program needs several threads or processes (chapters 5 and 10).

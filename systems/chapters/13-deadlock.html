Deadlock, Livelock & Starvation

Locks fix races, but they bring a new way to fail: threads that wait for each other forever, threads that are busy but get nowhere, and threads that never get a turn. You'll learn the four conditions that make a deadlock possible, the one habit that prevents most of them, and why a spacecraft on Mars once rebooted itself because of a lock.

Why this matters

A race condition (chapter 11) gives you wrong answers. A deadlock gives you no answer at all: the process is alive, the CPU is idle, nothing crashes, nothing is logged, and requests simply stop completing. On a busy server that looks like an outage with no explanation. Almost every database, job scheduler and distributed system contains code whose whole purpose is to prevent, detect or break deadlocks, so this is worth understanding properly.

Two threads, two locks

In chapter 12 we protected shared data with a lock (a mutex): only the thread holding it may touch the data, and everyone else waits. That works well for one lock. Now take a bank. Each account has its own lock, so transfers between unrelated accounts can run in parallel. A transfer must change two accounts at once, so it takes both locks:

def transfer(src, dst, amount):
    with src.lock:            # lock the source account...
        with dst.lock:        # ...then the destination
            src.balance -= amount
            dst.balance += amount

This looks correct, and for a long time it will behave correctly. Now two customers act at the same moment. Thread T1 runs transfer(a, b, 30) and thread T2 runs transfer(b, a, 10). If T1 takes a and T2 takes b before either goes further, then T1 wants b (held by T2) and T2 wants a (held by T1). Each is waiting for something only the other can give.

That state is a deadlock: a group of threads, each waiting for a resource held by another thread in the group, so none of them can ever continue. Nothing will wake them. Locks in most languages wait politely and forever.

Common misconception

"Python's GIL means Python can't deadlock." The GIL only makes sure one thread runs Python bytecode at a time. It says nothing about your locks. The threading.Lock objects above deadlock in CPython exactly as they would in any other language, and the same goes for asyncio locks used carelessly. Deadlock is a property of how your program waits, not of the interpreter.

    The four conditions

    In 1971, Coffman, Elphick and Shoshani described four conditions that must all hold at once for a deadlock to be possible. They are known as the Coffman conditions. This is useful in an unusual way: to prevent deadlock you don't need to be clever, you just need to break any one of the four.

    ConditionIn the bank exampleHow to break it
    Mutual exclusion: a resource can be held by only one thread at a time.An account lock has one holder.Don't share: give each thread its own copy, use immutable data, or use lock-free structures (chapter 12). Often impossible: a bank balance really must be updated by one writer at a time.
    Hold and wait: a thread holds one resource while waiting for another.T1 holds a while waiting for b.Take everything at once or nothing: for example one big lock, or "try to get both, and if you can't, release what you have". Costs concurrency.
    No preemption: a held resource can't be forcibly taken away.Nobody can pry a out of T1's hands.Allow giving up: acquire(timeout=...) or try-lock, then release everything and retry. Databases do this by aborting a transaction.
    Circular wait: there is a cycle of threads, each waiting for the next.T1 waits for T2 waits for T1.Impose a global order on locks and always take them in that order. This is the practical favourite.

    Look at the cycle in the lab: T1 holds A and wants B; T2 holds B and wants A. All four conditions are visible in that one picture.

    The practical fix: lock ordering

    Why does the cycle exist? Because T1 took a then b, while T2 took b then a. The order depended on which argument happened to be the source. If every thread took locks in the same global order (say, lowest account id first), a cycle would be impossible.

    Here is the earlier transfer, fixed with that one rule. The sleeps are there to make the timing match the broken version, so you can see it no longer matters.

    import threading
import time

class Account:
    def __init__(self, id, balance):
        self.id = id
        self.balance = balance
        self.lock = threading.Lock()

def transfer(src, dst, amount):
    first, second = sorted((src, dst), key=lambda acc: acc.id)   # global order: lowest id first
    with first.lock:
        time.sleep(0.1)                          # same sleep as before: it no longer matters
        with second.lock:
            src.balance -= amount
            dst.balance += amount

a, b = Account(1, 100), Account(2, 100)
t1 = threading.Thread(target=transfer, args=(a, b, 30))
t2 = threading.Thread(target=transfer, args=(b, a, 10))
t1.start(); t2.start()
t1.join(); t2.join()
print("a =", a.balance, " b =", b.balance, " total =", a.balance + b.balance)
    $ python3 ordered.py
a = 80  b = 120  total = 200

    Both transfers finish, and the total is unchanged. Both threads now try a (id 1) first, so one simply waits for the other and then proceeds. Order is the whole trick.

    Details that bite

    The order must be a total, stable order over everything that can be locked: account ids, or memory addresses, or "always table users before orders". Two other traps: transfer(a, a, 5) would try to take the same non-reentrant lock twice and deadlock against itself, so handle that case separately; and locks taken inside callbacks (calling unknown code while holding a lock) can silently violate your order. Writing the order down in a comment next to the locks is a good habit.

    Timeouts and try-lock

    Sometimes you can't pick an order, because you only learn which lock you need after taking another one. Then break "no preemption" instead: don't wait forever. Python's lock.acquire(timeout=2) returns False if it couldn't get the lock in time, and acquire(blocking=False) is a pure try-lock. A common pattern is: take the first lock, try the second; if that fails, release the first, wait a moment, and start over.

    Timeouts also work as a safety net for the rest of your code. Here's the broken version again, written so that it reports the deadlock instead of hanging your terminal. It deadlocks every time because the sleep gives each thread time to grab its first lock:

    import threading
import time

lock_a = threading.Lock()
lock_b = threading.Lock()

def transfer(name, first, first_name, second, second_name):
    with first:                                  # take the first lock...
        print(f"{name}: holds {first_name}")
        time.sleep(0.1)                          # ...give the other thread time to take its first
        print(f"{name}: wants {second_name}")
        if second.acquire(timeout=2):            # a plain 'with second:' would hang forever
            try:
                print(f"{name}: done")
            finally:
                second.release()
        else:
            print(f"{name}: waited 2 s for {second_name}. DEADLOCK suspected, giving up")

t1 = threading.Thread(target=transfer, args=("T1", lock_a, "A", lock_b, "B"))
t2 = threading.Thread(target=transfer, args=("T2", lock_b, "B", lock_a, "A"))
t1.start(); t2.start()
t1.join(); t2.join()
    $ python3 deadlock_demo.py
T1: holds A
T2: holds B
T1: wants B
T2: wants A
T2: waited 2 s for A. DEADLOCK suspected, giving up
T1: waited 2 s for B. DEADLOCK suspected, giving up

    After 2 seconds the timeouts fire, both threads leave their with blocks, release their first locks, and the program exits. (The order of the last two lines can vary. In a rare timing, the thread that gives up second can grab the lock the first one just released and print "done" instead.)

    A timeout is a smoke alarm, not a fire extinguisher

    A timeout tells you something is wrong, and makes your program survive it. It does not tell you why, and a "slow but fine" operation will trigger it too. If you just retry immediately, you may fall into the next problem in this chapter.

    Detection: the wait-for graph

    The graph in the lab isn't just a toy. Take every thread as a node and draw an edge from thread X to thread Y when X is waiting for a lock that Y holds. A cycle in this graph is a deadlock, and a graph with no cycle is not deadlocked (some thread can always make progress). Detecting it means walking the graph, which is cheap.

    Databases do exactly this. When a transaction has to wait for a row lock, the database records the wait and periodically checks for a cycle; if it finds one, it picks a victim transaction, aborts it (undoing its changes and releasing its locks) and lets the others continue. The aborted client sees an error such as "deadlock detected" and is expected to retry the whole transaction. That works because transactions are designed to be abortable, which ordinary Python threads holding half-updated data are not.

    Some runtimes can also show you a deadlock after the fact. Java's jstack prints "Found one Java-level deadlock" when it sees the cycle. For Python, the standard library can at least dump every thread's stack so you can see where each is stuck:

    import faulthandler
import threading
import time

faulthandler.dump_traceback_later(3, exit=True)   # after 3 s: print every thread's stack, then exit

a, b = threading.Lock(), threading.Lock()

def worker(first, second):
    with first:
        time.sleep(0.1)
        with second:                              # blocks forever: the other thread holds it
            pass

threading.Thread(target=worker, args=(a, b), name="T1").start()
threading.Thread(target=worker, args=(b, a), name="T2").start()
    $ python3 hang.py

    Both worker threads are parked on line 12, the inner with second:. (The last entry is the main thread, which has finished its own work and is just waiting for the others to exit.) Two threads stopped at "acquire a lock" with nobody running is the signature of a deadlock. (Thread ids, paths and line numbers in the traceback will differ on your machine.)

    Dining philosophers

    Edsger Dijkstra's famous puzzle packs the whole problem into a dinner table. Five philosophers sit in a circle, with one fork between each pair of neighbours. To eat, a philosopher needs the fork on their left and the one on their right. Each philosopher repeatedly thinks, picks up the left fork, picks up the right fork, eats, and puts both down.

    If all five pick up their left fork at the same moment, everybody holds one fork and waits for the right one, which the neighbour is holding: a perfect circular wait. The standard fixes map onto the Coffman conditions: number the forks and always pick up the lower-numbered one first (break circular wait); allow at most four philosophers at the table (the circle can't close); or pick up both forks atomically or neither (break hold and wait). You already have the tools; the puzzle is just a memorable test of whether you can use them.

    Livelock

    Suppose you fixed deadlocks with the "try, back off, retry" pattern from earlier, and both threads follow the same rule: if I can't get the second lock, release the first and try again immediately. T1 takes a and fails to get b; T2 takes b and fails to get a; both release and retry; and they repeat in lockstep, forever. Both are running, burning CPU and making no progress. That is a livelock.

    Analogy: the hallway shuffle

    Two people meet in a narrow corridor. Each steps to their left to let the other pass, and each ends up blocking the other. Both politely step to the right at the same moment. Neither is stuck, both are moving, and neither gets through.

    Where it breaks down: people eventually laugh and break the pattern by chance, so the standoff ends. A pair of threads running identical deterministic code can repeat the exact same step forever, which is why we have to put the randomness in on purpose.

    The fix is the same one you saw for retries in networking chapter 16: randomised backoff. Each thread waits a random short time before retrying, so one of them gets lucky and takes both locks while the other is still waiting. A sketch of the pattern:

    # sketch, not a complete program
while True:
    with first:
        if second.acquire(blocking=False):
            try:
                do_the_work()
                break
            finally:
                second.release()
    time.sleep(random.uniform(0, 0.01))   # random pause: breaks the lockstep

    Starvation

    Starvation is when a thread is ready to run but never gets what it needs, because others keep getting it first. Nothing is circular and the system as a whole makes progress, but one unlucky victim doesn't. Typical causes: an unfair lock that lets newcomers jump the queue, a reader-writer lock where a stream of readers always keeps the writer waiting, or a scheduler that always favours high-priority work while a low-priority task waits forever. Fixes are about fairness: queue waiters in order, bound how long anyone can be bypassed, or temporarily raise the priority of work that has waited too long.

    Analogy: the three traffic problems

    Deadlock is four cars at a four-way junction, each waiting for the car to its right: nobody moves. Livelock is all four creeping forward and reversing in sync. Starvation is a side road where cars from the main road always have priority, so the side-road driver waits all day while traffic flows.

    Where it breaks down: real drivers can see each other and negotiate; threads can't see inside each other's decisions, which is why the rules (ordering, timeouts, randomness, fairness) have to be built into the code.

    Priority inversion

    The scheduler (chapter 7) can give some tasks higher priority than others. Add a lock and something strange happens. Imagine three tasks: High, Medium and Low. Low takes a lock. High wakes up, wants the same lock, and must wait for Low. Then Medium wakes up. It doesn't need the lock, but it is higher priority than Low, so it preempts Low and runs for as long as it likes. Low can't run, so it can't release the lock, so High (the most important task) is stuck behind Medium (a less important one). That is priority inversion.

    The standard cure is priority inheritance: while a low-priority task holds a lock that a high-priority task wants, the low-priority task temporarily inherits the high priority. In the picture, Low would immediately outrank Medium, finish its critical section, release the lock, drop back down, and High would run. Many real-time operating systems and some mutex implementations offer it (POSIX has a "priority inherit" mutex protocol, for example).

    This isn't a theoretical curiosity: it happened to a spacecraft, and the story of how it was diagnosed and fixed remotely is in the case study Priority Inversion on Mars.

    Try it yourself

    Try it yourself: deadlock, then un-deadlock

    Save the timeout demo above as deadlock_demo.py and run it with python3 deadlock_demo.py (same on macOS, Linux and WSL). It takes 2 seconds and then exits by itself. Then try these changes, one at a time:

    1. Remove the time.sleep(0.1). Run it ten times. How often does it still deadlock? (Usually it won't, which is exactly why this bug survives testing.)
    2. Make both threads take the locks in the same order: change T2's arguments to (lock_a, "A", lock_b, "B"). Does the sleep matter now?
    3. Put faulthandler.dump_traceback_later(3, exit=True) at the top and change second.acquire(timeout=2) to a plain with second:. Now you have a real hang, and the dump tells you where each thread is stuck.

    Distributed systems connection

    Everything here reappears with machines instead of threads. A distributed transaction that locks rows on two different database servers can deadlock across them, and no single server sees the whole cycle. Databases handle this with the same two tools you just learned: detection (a single-node database finds the cycle in its wait-for graph and aborts one transaction; distributed ones ship wait-for edges between nodes or use a coordinator) and timeouts (the pragmatic option: if a lock wait lasts too long, assume the worst and abort). Across a network a timeout is also the only tool you have for "is the other side dead or just slow?", as we saw in networking chapter 16. And livelock-by-synchronised-retries is exactly the retry storm: everybody backs off for the same time, comes back together, and fails together; jitter fixes it for services the way randomised backoff fixes it for threads. We'll meet distributed locks and leases in later courses.

    Key takeaways

    • A deadlock is a cycle of threads each waiting for a lock held by the next. It is silent: the process stays alive and does nothing.
    • It needs all four Coffman conditions: mutual exclusion, hold and wait, no preemption, circular wait. Break any one to prevent it.
    • The practical rule: always take multiple locks in one global order (for example by account id).
    • When you can't order locks, use timeouts or try-lock, release what you hold, and retry after a random delay.
    • Detection means finding a cycle in the wait-for graph. Databases do it automatically and abort a victim transaction.
    • Livelock is busy but stuck (fix: randomness); starvation is a thread that never gets a turn (fix: fairness).
    • Priority inversion lets a medium task delay a high one through a low one's lock; priority inheritance fixes it.

    Check your understanding

    Which of these is NOT one of the four Coffman conditions for deadlock?

    1. Hold and wait
    2. Circular wait
    3. There must be at least three threads
    4. No preemption
    Two threads are enough, as in the transfer example. The four conditions are mutual exclusion, hold and wait, no preemption and circular wait. All four must hold, so breaking any one prevents deadlock.

    Why does "always lock accounts in increasing id order" prevent deadlock?

    1. It makes a circular wait impossible: waits can only point from lower to higher ids, so they can't loop back
    2. It makes each lock faster to acquire
    3. It removes the need for mutual exclusion
    4. It lets one thread steal a lock from another
    Ordering breaks the circular-wait condition. A cycle would need some thread holding a high-numbered lock to wait for a lower-numbered one, and the rule forbids exactly that. Mutual exclusion is still there; the locks are not faster; nothing is stolen.

    Two threads repeatedly grab a lock, fail to get the second one, release, and retry at the same instant, forever, using 100% CPU. What is this, and what is the usual fix?

    1. Deadlock; add more locks
    2. Starvation; raise the priority of one thread
    3. A race condition; use atomics
    4. Livelock; add a random delay before retrying
    The threads are active but never progress, which is livelock, not deadlock (a deadlocked thread is asleep). Randomised backoff breaks the lockstep so one thread wins. Starvation is about one thread being passed over repeatedly, not a symmetric standoff.

    In priority inversion, why does a Medium-priority task delay the High-priority one even though it never touches the lock?

    1. Medium steals the lock from High
    2. Medium preempts the Low task that holds the lock High needs, so Low can't finish and release it
    3. The scheduler always runs Medium before High
    4. High's priority is lowered when it waits
    Low holds the lock; High waits for it; Medium outranks Low and keeps the CPU. Low can't run, so it can't release. Priority inheritance temporarily raises Low above Medium so it can finish quickly.

    A database finds a cycle in its wait-for graph between two transactions. What does it do?

    1. Waits for them to finish by themselves
    2. Restarts the whole database server
    3. Aborts one transaction (the victim) so the other can continue, and the client retries the aborted one
    4. Merges the two transactions into one
    Waiting does nothing: the cycle can never resolve on its own. Databases break "no preemption" by aborting a victim, undoing its changes and freeing its locks. Applications are expected to catch the deadlock error and retry the transaction.

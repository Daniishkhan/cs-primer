Locks, Atomics & Condition Variables

Chapter 11 showed how shared data gets corrupted. This chapter is the toolbox for preventing it: mutexes that let one thread in at a time, atomic CPU instructions that make a single step indivisible, condition variables for waiting politely until something is true, and semaphores for limiting how many threads may do something at once. It ends with why all of this gets harder when the "threads" are on different machines.

Why this matters

Every shared counter, cache, connection pool and job queue in a server is guarded by one of these tools. Choosing wrongly gives you either corrupted data (too little locking), a slow service (too much, or in the wrong place), or a frozen one (the subject of chapter 13). The same ideas underlie database row locks, optimistic concurrency, and distributed locks, so the vocabulary here is the vocabulary of system design.

Critical sections and the mutex

In chapter 11 the trouble came from a multi-step operation being interleaved with another thread's steps. The cure is to declare that operation a critical section: a stretch of code that touches shared data and must therefore run by only one thread at a time. The tool for enforcing that is a mutex (short for mutual exclusion), usually just called a lock. A thread acquires the lock before entering the critical section and releases it afterwards. If the lock is already held, a thread trying to acquire it blocks: the kernel puts it to sleep (chapter 7) until the holder releases.

In Python the lock is threading.Lock, and the right way to use it is the with statement, which acquires on entry and always releases on exit, even if an exception is raised inside:

import threading, time

counter = 0
lock = threading.Lock()

def work(n):
    global counter
    for _ in range(n):
        with lock:             # only one thread at a time may run this block
            counter += 1

start = time.perf_counter()
threads = [threading.Thread(target=work, args=(250_000,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(f"expected 1000000, got {counter}  ({time.perf_counter() - start:.2f} s)")
$ python3 counter_lock.py
expected 1000000, got 1000000  (0.06 s)

Every run gives exactly one million, because the load, add and store of each increment now happen inside one critical section: no other thread can slip between them. (In this tiny loop the GIL happens to make the unlocked version look fine, as we saw; the lock is what makes the guarantee real, on any Python version and any machine.)

Locks also fix the check-then-act bugs of chapter 11. The bank withdrawal becomes safe when the check and the act sit in one critical section:

import threading, time

balance = 100
lock = threading.Lock()

def withdraw(amount, who):
    global balance
    with lock:                          # check and act in ONE critical section
        if balance >= amount:
            time.sleep(0.01)
            balance -= amount
            print(f"{who}: withdrew {amount}")
        else:
            print(f"{who}: declined")

a = threading.Thread(target=withdraw, args=(80, "A"))
b = threading.Thread(target=withdraw, args=(80, "B"))
a.start(); b.start(); a.join(); b.join()
print("final balance:", balance)
$ python3 bankfix.py
A: withdrew 80
B: declined
final balance: 20

Analogy: a single-stall bathroom with one key

The key hangs on a hook. Whoever takes it goes in; anyone else who arrives waits outside. When the person comes out they hang the key back, and the next in line takes it. While one person is inside, nobody else can be, whatever they were about to do.

Where it breaks down: a real door physically stops you. A lock in a program is only a convention: it protects the data only if every piece of code that touches that data takes the same lock first. One careless function that skips it can still corrupt everything. Also, a real stranger can't carry the key off and vanish, but a thread that crashes while holding a lock can leave everyone else waiting for ever (which is why with matters).

Common misconception

"A lock protects a variable." It doesn't: a lock protects an invariant, a statement that must be true whenever the lock is free (for example "the balance is never negative" or "the counter equals the number of items added"). Decide what the invariant is, then hold the lock across every step that temporarily breaks it, and across every step that reads data relying on it. That's why lockcheck.py in chapter 11 failed despite locking every access.

Lock granularity and contention

How much should one lock cover? Granularity is the answer's name. A coarse-grained lock guards a lot (say, a whole in-memory cache); it's simple and hard to get wrong, but unrelated operations wait for each other. A fine-grained scheme uses many locks (one per bucket, per account, per row); threads working on different things don't interfere, but there are more locks to manage, more chances for a deadlock (chapter 13), and operations spanning several items need several locks.

The waiting has a name too: contention is what happens when many threads want the same lock. Under high contention a program spends its time queuing instead of working, and adding threads can make it slower. The standard advice is to keep critical sections short, do slow work (computation, I/O) outside them where possible, and avoid sharing in the first place when you can (give each thread its own counter and add them up at the end).

What a lock costs

Taking a lock nobody else wants is cheap: roughly tens of nanoseconds, a handful of atomic CPU operations. In the test above, the locked loop took about three times as long as the same loop without a lock (roughly 0.06 s against 0.02 s for a million increments, measured on Python 3.14), which is cheap per operation but not free. The bigger costs appear under contention: a thread that can't get the lock goes to sleep, the kernel switches to something else, and waking it later costs a context switch of the order of microseconds (chapter 7). Taking a hundred locks per request is fine; waiting for the same lock on every request, across fifty threads, is how a server stops scaling.

The classic mistake: holding a lock during I/O

Because everyone waiting for a lock waits for its holder, the lock's cost is the holder's time inside it. If that time includes a network call or a disk write (milliseconds, millions of times slower than a memory update), every thread queues up behind it:

import threading, time

lock = threading.Lock()

def slow_under_lock():
    with lock:
        time.sleep(0.2)            # I/O while holding the lock: everyone queues behind it

def slow_outside_lock():
    time.sleep(0.2)                # do the I/O first...
    with lock:
        pass                       # ...hold the lock only for the quick update

def run(fn):
    ts = [threading.Thread(target=fn) for _ in range(5)]
    start = time.perf_counter()
    for t in ts: t.start()
    for t in ts: t.join()
    return time.perf_counter() - start

print(f"I/O inside the lock:  {run(slow_under_lock):.2f} s")
print(f"I/O outside the lock: {run(slow_outside_lock):.2f} s")
$ python3 ioheld.py
I/O inside the lock:  1.02 s
I/O outside the lock: 0.20 s

Five threads, each needing 0.2 s of "I/O". Inside the lock they run one at a time (5 × 0.2 = 1.0 s); outside, their waits overlap and the total is 0.2 s. Keep slow operations out of critical sections: fetch first, then lock briefly to update shared state. (Sometimes you can't, for example when the lock exists precisely to serialise writes to a file. Then at least make it a separate lock for that file alone.)

Common misconception

"More threads and more locks always means more speed." A lock is a place where threads stop being parallel. If 20% of each request runs inside one lock, no number of threads can make the system more than five times faster (this is Amdahl's law). Measure where threads wait before adding more.

Atomic instructions

Locks work by making threads wait, which needs help from the kernel. There is a lower, faster layer: the CPU itself provides instructions that read and modify a memory location atomically, meaning no other core can see or interfere with the in-between state. Two are most important:

fetch-and-add
Atomically add a number to a memory location and return the old value. This alone turns counter += 1 into one indivisible step. (On x86 this is lock xadd; on newer ARM, LDADD.)
compare-and-swap (CAS)
"If the location still holds the value I expect, replace it with this new value, and tell me whether you did." One indivisible step. (x86: lock cmpxchg; ARM: CAS, or a load-linked / store-conditional pair on older cores.)

CAS is the building block of nearly every lock and every lock-free structure, because of the way you use it: the CAS retry loop. Read the current value, compute the new one, and try to CAS it in. If the CAS fails, someone else changed the value in the meantime, so read again and retry. Nobody ever holds a lock or waits; the loser just tries again.

Step through

A CAS retry loop: two threads, one counter

  1. A reads. The shared value is 5. Thread A keeps a private copy, old = 5, and plans to write 6.
  2. B reads too. This is the dangerous interleaving from chapter 11: both threads now hold 5. With a plain store, the second one to write would overwrite the first.
  3. B's CAS succeeds. CAS(5, 6) means "if the value is still 5, make it 6". It is, so the CPU swaps it in, as one indivisible step. The value is now 6.
  4. A's CAS fails. A tries CAS(5, 6), but the value is 6, not 5, so the CPU refuses and writes nothing. A's stale copy was caught, and B's update survives.
  5. A retries. A loops back, re-reads the current value (6) and recomputes. Cheap, and no one was ever put to sleep.
  6. A succeeds. CAS(6, 7) succeeds. Both increments are counted. The failed attempt cost a little wasted work, but it never corrupted anything.

Python doesn't expose CAS directly for ordinary variables, but we can simulate it to see the loop in action. In the script below a small internal lock stands in for the CPU's guarantee that the compare and the swap happen as one step. The time.sleep(0) between the read and the CAS is there only to invite other threads in, so that CAS failures actually happen:

import threading, time

class AtomicInt:
    """A simulated atomic integer. Real CPUs do compare_and_swap in ONE instruction;
    here a tiny lock stands in for that hardware guarantee."""
    def __init__(self, value=0):
        self._value = value
        self._guard = threading.Lock()      # plays the role of the CPU's atomicity

    def load(self):
        return self._value

    def compare_and_swap(self, expected, new):
        with self._guard:
            if self._value == expected:
                self._value = new
                return True
            return False

counter = AtomicInt()
retries = 0                                  # only for the demo (itself racy, approximate)

def work(n):
    global retries
    for _ in range(n):
        while True:
            old = counter.load()
            time.sleep(0)                    # demo only: invite another thread in, so CAS can fail
            if counter.compare_and_swap(old, old + 1):
                break                        # nobody changed it between load and CAS
            retries += 1                     # someone beat us to it: reload and try again

ts = [threading.Thread(target=work, args=(10_000,)) for _ in range(4)]
for t in ts: t.start()
for t in ts: t.join()
print("expected 40000, got", counter.load())
print("CAS retries (approximate):", retries)
$ python3 cas.py
expected 40000, got 40000
CAS retries (approximate): 3489

The answer is exact even though thousands of attempts failed and were retried. The takeaway is the loop shape: read, compute, CAS, and on failure start again. You'll see it in the standard library of other languages (Java's AtomicInteger, C++'s std::atomic, Go's sync/atomic), and, as chapter 11 hinted, in databases as "optimistic concurrency": UPDATE ... WHERE version = 3 is a CAS on a row.

Spinlocks versus blocking locks

CAS makes a different kind of lock possible. A spinlock is a lock whose waiters don't sleep: they loop, retrying the CAS ("is it free yet? is it free yet?") until they win. A blocking lock (the kind Python gives you) puts the waiter to sleep in the kernel and wakes it later.

SpinlockBlocking lock
WaitingBurns CPU in a loopSleeps; the core runs something else
Wake-up speedNanosecondsMicroseconds (a context switch)
Good whenThe critical section is a few instructions, waiters are few, and each thread has its own core. Operating-system kernels use them heavilyThe critical section may be long, or may block. This is the default for applications
DangerIf the holder is paused (descheduled) while others spin, they waste whole time slicesSleep and wake-up costs when the lock is held only briefly

Practical locks are often hybrids: spin briefly in case the holder is about to finish, then sleep. For application code, use the blocking kind unless you have measured a reason not to.

Go deeper: lock-free programming and the ABA problem optional

A data structure is lock-free if, whenever threads are running, some thread is always making progress, even if others are paused. It's built from CAS retry loops instead of locks, so a thread stalled in the middle can't block the rest. This matters for latency-sensitive code and for kernels and runtimes, and queues such as the ones inside some message brokers are built this way.

It's also notoriously hard to get right. One famous trap is the ABA problem: a thread reads value A, gets paused, and meanwhile other threads change the value to B and then back to A. The paused thread's CAS("is it still A?") succeeds, though the world changed underneath, which can corrupt structures such as stacks that hold pointers (if A was a node that has been freed and reused, say). The usual cure is to pair the value with a version counter so that "A at version 7" differs from "A at version 9". Unless you are writing a runtime or a database engine, use the library's ready-made structures.

Condition variables: waiting for something to happen

Locks stop threads colliding. But sometimes a thread needs to wait until something becomes true: a consumer must wait for an item to arrive, a producer must wait for room. The crude approach, a loop that keeps checking, wastes a CPU and holds the lock or sleeps a guessed time. A condition variable is the proper tool. It is always paired with a lock and offers two operations:

  • wait(): atomically release the lock and go to sleep until someone notifies; when woken, re-acquire the lock before returning.
  • notify() (or notify_all()): wake one (or all) of the threads sleeping on this condition.

The "atomically" matters: if the thread released the lock and then went to sleep as two steps, a notification arriving in between would be missed and the thread would sleep for ever (a lost wakeup, itself a race).

The textbook example is the bounded buffer: producers add items to a queue of limited size, consumers remove them. Producers must wait when it's full; consumers must wait when it's empty.

import threading, collections, time

class BoundedBuffer:
    def __init__(self, capacity):
        self.items = collections.deque()
        self.capacity = capacity
        self.lock = threading.Lock()
        self.not_full = threading.Condition(self.lock)
        self.not_empty = threading.Condition(self.lock)

    def put(self, item):
        with self.lock:
            while len(self.items) >= self.capacity:     # WHILE, not if
                self.not_full.wait()
            self.items.append(item)
            self.not_empty.notify()

    def get(self):
        with self.lock:
            while not self.items:                        # WHILE, not if
                self.not_empty.wait()
            item = self.items.popleft()
            self.not_full.notify()
            return item

buf = BoundedBuffer(capacity=3)

def producer():
    for i in range(8):
        buf.put(i)
        print(f"produced {i}")
    buf.put(None)                                        # sentinel: "no more items"

def consumer():
    while True:
        item = buf.get()
        if item is None:
            break
        time.sleep(0.05)                                 # consuming is slower than producing
        print(f"    consumed {item}")

p = threading.Thread(target=producer); c = threading.Thread(target=consumer)
p.start(); c.start(); p.join(); c.join()
$ python3 bounded.py
produced 0
produced 1
produced 2
produced 3
    consumed 0
produced 4
    consumed 1
produced 5
    consumed 2
produced 6
    consumed 3
produced 7
    consumed 4
    consumed 5
    consumed 6
    consumed 7

Watch the rhythm. The producer races ahead until the buffer is full, then sleeps in not_full.wait(). Each time the slow consumer takes an item out, it wakes the producer for exactly one more. (The consumer removes an item and then spends 0.05 s processing it before printing "consumed", so the printed lines trail the buffer by a little.) The producer is never more than a few items ahead: the slow side sets the pace, which is backpressure, and it falls out of the bounded size for free. We build on it in chapter 14.

Always wait in a while loop

Look at while len(self.items) >= self.capacity: self.not_full.wait(). It is a while, never an if, for three reasons. (1) Spurious wakeups: operating systems and runtimes are allowed to wake a waiting thread for no reason at all. (2) Someone else got there first: between the notify and your thread re-acquiring the lock, another thread may have taken the only item, so the condition is false again. (3) notify_all wakes many threads for a condition only one can use. Re-checking the condition after every wake-up makes all three harmless. The pattern is: lock, while not condition: wait, act, notify, unlock.

Python's queue.Queue already implements exactly this (a lock plus not_empty and not_full conditions), so in real code you would use it. Writing it once by hand shows what's inside, and you'll rebuild a blocking queue in Lab 3.

Semaphores: limiting concurrency to N

A semaphore is a counter with two operations: acquire (wait until the count is above zero, then decrement it) and release (increment it). A lock is a semaphore that starts at 1. Starting it at N lets up to N threads in at once, which is the right tool for "no more than N of these at a time": 10 concurrent downloads, 20 database connections, 4 heavy jobs.

import threading, time

limit = threading.Semaphore(3)            # at most 3 downloads at once
active = 0
peak = 0
stats = threading.Lock()

def download(n):
    global active, peak
    with limit:                           # wait here if 3 are already running
        with stats:
            active += 1
            peak = max(peak, active)
        time.sleep(0.2)                   # pretend network transfer
        with stats:
            active -= 1

threads = [threading.Thread(target=download, args=(i,)) for i in range(10)]
start = time.perf_counter()
for t in threads: t.start()
for t in threads: t.join()
print(f"10 downloads, peak concurrency {peak}, took {time.perf_counter() - start:.1f} s")
$ python3 sem.py
10 downloads, peak concurrency 3, took 0.8 s

Ten downloads of 0.2 s each, three at a time: four rounds (3 + 3 + 3 + 1), so 0.8 s, and the measured peak is exactly 3. One difference from a lock: a semaphore has no owner, so any thread can release it. That's flexible (one thread can signal another) but gives up some safety. Use BoundedSemaphore if you want an error when someone releases more times than they acquired.

Reader–writer locks and reentrant locks

Readers–writer locks

Reading shared data never corrupts it, so why make readers queue behind each other? A readers–writer lock allows many readers at the same time or one writer alone, never both. It's a good fit for data that is read constantly and changed rarely, such as a configuration table or a routing table. The cost is complexity: a stream of readers can starve a waiting writer unless the lock is designed to prevent that (starvation is in chapter 13), and the extra bookkeeping makes it slower than a plain mutex when critical sections are tiny. Python's standard library doesn't include one; other languages (Java's ReentrantReadWriteLock, Rust's RwLock, C++'s std::shared_mutex) do. A common Python alternative is to avoid it: replace the whole data structure with a new copy and swap one reference (a single assignment is atomic), so readers never need a lock.

Reentrant locks

What happens if a thread tries to acquire a lock it already holds? With a plain Lock, it waits for itself, for ever. This happens naturally: deposit() locks, then calls log_balance(), which also locks. A reentrant lock (threading.RLock) remembers its owner and a count, so the same thread can acquire it repeatedly and must release it as many times.

import threading

rlock = threading.RLock()

def outer():
    with rlock:
        inner()

def inner():
    with rlock:                # same thread takes it again: fine for an RLock
        print("inner ran")

outer()

plain = threading.Lock()
with plain:
    got_it = plain.acquire(timeout=0.5)     # same thread asks again
    print("plain Lock, second acquire by the same thread:", got_it)
$ python3 rlock.py
inner ran
plain Lock, second acquire by the same thread: False

(The plain-lock check used timeout=0.5; without it, that second acquire would simply hang.) Reentrant locks are convenient, but treat them with some suspicion: if you need one, it can mean your locking structure is tangled, and code that re-enters can see the shared data in a half-updated state that its caller left behind. Prefer designing so that "public methods lock, private helpers assume the lock is held".

Go deeper: memory visibility and ordering optional

There's a second problem, separate from interleaving, that locks also solve. Each core has its own caches and write buffers (chapter 2), and both the compiler and the CPU are allowed to reorder instructions, so long as a single thread can't tell. A single thread can't, but another thread can. Suppose thread A does data = 42; ready = True and thread B waits for ready and then reads data. On a weakly ordered CPU (ARM is one; x86 is stricter) B could see ready == True yet still read the old data, because A's two writes became visible in the opposite order.

Languages with a memory model define the exact rules. Acquiring and releasing a lock acts as a memory barrier (a fence): everything the previous holder wrote before releasing is guaranteed visible to the next thread after acquiring, and the compiler and CPU may not move operations across the boundary in a way that breaks that. Atomic operations come with an ordering choice (C++ offers relaxed, acquire/release and sequentially consistent), where stronger ordering costs more. The practical rule: if shared data is touched by several threads, every access must go through a lock or an atomic, not just the ones that "need" it. CPython hides most of this from you, since the GIL's hand-over acts as a barrier, but it is the reason a Java or C++ program that "works" without locks may fail on other hardware.

Locks across machines: leases and fencing tokens

Sometimes a lock must cover several machines: "only one worker may run this nightly job", "only one node is the leader". A distributed lock is held in a shared service (a database row, a ZooKeeper or etcd entry) that every machine can reach. It looks like a mutex, but several things that were guaranteed inside one machine are no longer true:

  • The holder can crash. A thread that dies takes its process with it; a machine that dies can leave the lock held for ever. So distributed locks come with a lease: the lock is granted for a limited time (say 10 seconds) and expires on its own unless the holder renews it.
  • You can't tell dead from slow (networking chapter 16). If the holder doesn't renew, the service must assume it's gone and hand the lock to someone else.
  • Processes pause. A garbage collection, a virtual machine freeze, or a slow disk can stall the holder at any instant, for far longer than the lease. When it wakes up, it has no way to know that time has passed.

This is the nasty case: when A wakes, it does if I hold the lock: write, and its check says yes, because its clock-based reasoning was made before the pause. This is check-then-act again (chapter 11), now with the gap caused by a pause rather than a thread switch, and the lock service cannot interrupt a frozen process. The standard defence is a fencing token: every time the lock service grants a lease it also returns a number that increases with each grant (33, then 34). The client sends its token with every write to the protected resource, and the resource remembers the highest token it has seen and rejects lower ones. A's stale write carries 33, storage has already seen 34, so it is refused. The point is that the check has moved to the one place that can't be paused out from under it.

Chapter 20 of the networking course shows how lock services stay consistent despite crashes and partitions (consensus, networking chapter 20), and chapter 17 explains why you shouldn't trust clocks to decide when a lease has expired (networking chapter 17).

Distributed systems connection

Nearly everything here has a networked twin. A mutex becomes a distributed lock with a lease; a CAS loop becomes optimistic concurrency with version numbers or conditional writes in a database or object store; a semaphore becomes a rate limiter or a connection limit; a condition variable becomes a message queue where consumers wait for work. The twins are harder because they can't assume a shared memory, a reliable "release", or a process that stays awake, and so they need leases, fencing tokens and idempotent operations on top. A useful design habit: prefer a single atomic operation owned by the data's home (a conditional write, an atomic increment) over a lock held across a network.

Key takeaways

  • A mutex makes a critical section run by one thread at a time. Use with lock:; protect the whole invariant, check and act together, and make every access use the same lock.
  • Choose lock granularity deliberately: coarse is simple, fine scales. Keep critical sections short and never hold a lock across slow I/O.
  • Atomic instructions (fetch-and-add, compare-and-swap) make a single read-modify-write indivisible. The CAS retry loop (read, compute, CAS, retry on failure) is the base of lock-free code and of optimistic concurrency in databases.
  • Spinlocks burn CPU to wait briefly; blocking locks sleep. Applications should normally use blocking locks.
  • A condition variable lets a thread sleep until a condition holds. Always wait() inside a while loop that re-checks the condition, because of spurious wakeups and competing threads.
  • A semaphore limits concurrency to N. Readers–writer locks allow many readers or one writer. A reentrant lock lets the same thread acquire again.
  • Locks also order memory: without them or atomics, one thread may see another's writes late or out of order.
  • Distributed locks need leases (holders crash) and fencing tokens (holders pause); the protected resource must do the final check.

Check your understanding

A bank-transfer function locks balance while reading it, unlocks, computes, then locks again to write. What is wrong?

  1. Nothing; every access is locked
  2. Locks cannot protect integers
  3. The check and the update aren't in one critical section, so another thread can change the balance in between
  4. It will always deadlock
A lock protects an invariant, not a variable. The read and the dependent write must happen in one critical section; otherwise it is the chapter-11 check-then-act race, just with locks sprinkled around it.

Why is calling a slow network API while holding a lock usually a bad idea?

  1. Every other thread that needs the lock is stuck for the whole length of the call, so throughput collapses
  2. Locks cannot be held for more than a millisecond
  3. The network API will refuse to answer
  4. It makes the GIL permanent
Everyone waiting for the lock waits for its holder. If the holder spends milliseconds on I/O, the critical section becomes long and the threads serialise behind it, as the 1.02 s versus 0.20 s experiment showed.

In a compare-and-swap retry loop, what does a failed CAS tell you?

  1. The CPU is broken
  2. Your thread must give up for good
  3. Your update was applied twice
  4. Someone changed the value since you read it, so re-read and try again
CAS only writes if the location still holds the value you expected. A failure means another thread got in first and nothing was written, so you recompute from the new value. No update is lost and nobody blocked.

Why must cond.wait() be called inside a while loop that re-checks the condition rather than an if?

  1. Because if is slower
  2. Because a thread can wake spuriously, or another thread can take the item first, so the condition may be false again when you run
  3. Because wait() returns immediately otherwise
  4. Because Python forbids if there
Wake-ups are only a hint that the condition might be true. Between the notification and the waiter re-acquiring the lock, the state can change, and runtimes may wake waiters without any notify. Re-checking in a loop makes the code correct in every case.

You need at most 10 downloads running at once, whatever the number of threads. Which tool fits best?

  1. A mutex
  2. A reentrant lock
  3. A semaphore initialised to 10
  4. A spinlock
A semaphore counts permits: the first 10 threads pass, the rest wait until one releases. A mutex would allow only one download at a time.

A process holds a distributed lock with a 10 s lease, then freezes for 15 s during garbage collection. What protects the shared resource from its late write?

  1. The process checking its own clock before writing
  2. A fencing token: the resource rejects writes carrying a token older than one it has already seen
  3. A longer lease
  4. Nothing can; distributed locks are always safe
The frozen process cannot know time has passed, so any check it performs itself can be stale. A longer lease only makes the window rarer. A monotonically increasing token, checked by the resource, is the check that can't be paused.

Durability: Written Is Not Saved

When write() returns, your data is not safe. It is sitting in the operating system's memory, waiting for the disk. This chapter is about the gap between "written" and "saved": what a crash can take, what fsync actually buys, and the handful of patterns (atomic rename, checksums, logs) that every database is built from.

Why this matters

This is the third illusion from chapter 0: "saved means saved". When a database says "committed", it is promising that the data will survive a crash, and keeping that promise is expensive, so it is where systems make their hardest trade-offs between speed and safety. Understanding it lets you ask the question senior engineers always ask about any storage system: what exactly is on the disk at the moment I'm told "OK"?

The promise write() does not make

In the last chapter we saw that a program's write passes through layers. Now follow one write all the way down:

When your program calls write(), the kernel copies the bytes into its page cache (the in-memory copy of file contents from chapter 2), marks those pages dirty (changed in memory, not yet on disk), and returns. That takes microseconds. A background mechanism called writeback writes dirty pages to the disk later. On Linux with default settings that is typically within a few seconds to a few tens of seconds; you can read the settings yourself in the exercise below. Nothing guarantees it will have happened by any particular moment.

The kernel does this on purpose: if every write() waited for the disk, programs would be hundreds or thousands of times slower, and the kernel can merge many small writes into one big efficient one. The trade is that "written" means "handed to the kernel", not "safe".

Analogy: the order pad

Back in our kitchen, a waiter scribbles an order and drops it in the pass: "got it!" The kitchen is now committed in the waiter's mind. But the order is only on a slip of paper on the counter (RAM). If the lights go out before the chef copies it into the permanent order book (the freezer, the disk), the order vanishes and the customer is told nothing.

Where it breaks down: a kitchen would notice a missing order when the customer complains. A computer that loses a write usually loses it silently, and the program already told its user "saved".

What a crash takes, and what it does not

Not all crashes are alike. The key is which memory survives.

Process crash or kill -9LostSurvives, and will still be written backKept
Kernel crash / panicLostLostKept (as it was)
Power cutLostLostKept (but see drive caches below)

The key subtlety

If your program crashes after write() returned, the data is not lost. It's in the kernel's page cache, which belongs to the kernel and not to your process, and the kernel will write it out anyway. What is lost on a process crash is anything still in your own user-space buffer that you hadn't passed to write() yet (for example, Python text you hadn't flush()ed). Only a crash of the whole machine (kernel crash, power cut, a VM being killed) loses the page cache. So fsync is protection against machine failure, not process failure. You can see this in the simulator below with the "kill -9" button.

fsync: waiting for the disk

To move data past the page cache you call fsync(fd). It doesn't return until the kernel has written all of that file's dirty data (and the metadata needed to find it) to the storage device, and, on Linux, asked the device to flush its own cache. It is the only portable way to turn "written" into "saved".

  • fsync flushes the file's data and its metadata (size, timestamps).
  • fdatasync flushes the data and only the metadata needed to read it back (such as the file size), skipping things like modification time. It can save a disk operation. It is available on Linux but not on macOS (Python's os.fdatasync does not exist there); check hasattr(os, "fdatasync") before using it.

In Python the chain is: f.write() goes into Python's buffer; f.flush() pushes it to the kernel; os.fsync(f.fileno()) pushes it to the disk. Skipping the middle step is a classic bug: fsync on a file with unflushed Python buffers syncs nothing new.

The directory needs its own fsync

A new file is two things: its data (in an inode) and a name for it in a directory. Remember from chapter 8 that the directory entry is a separate piece of data. fsync(file) makes the file's contents durable, but the directory entry that points to it is part of the directory. After a crash the data might sit safely on the disk while the file has no name, so it appears not to exist. To be sure a newly created (or renamed) file is there after a crash, you also fsync the directory that contains it, by opening the directory and calling fsync on that descriptor. (Some file systems happen to be more generous, but the rule that works everywhere is: sync the file, then sync its directory.)

Torn writes and the atomic-replace pattern

Suppose you update a configuration file in place. The program opens it (emptying it), writes 4 KiB of new settings and closes it. The power fails halfway. The disk may hold an empty file, or the first half of the new settings glued to nothing, or the new first block and the old last block. This is a torn write: part of an update landed and part didn't, and the result is neither the old version nor the new one. A program that loads such a file at startup can fail in confusing ways.

Rewriting a file in place is therefore never safe against crashes, however many fsync calls you add after it. The fix is to never touch the old file at all. The atomic replace pattern writes the new version somewhere else and swaps the name in one indivisible step, using the fact that rename() on one file system is atomic: after a crash, the name points at either the old file or the new one, never something in between.

  1. Write the new contents to a temporary file in the same directory (config.tmp). Same directory matters: rename is only atomic within one file system.
  2. fsync the temporary file. Now the new data is truly on the disk. This must come before the rename. Otherwise the rename could reach the disk first and point the real name at a file whose data hasn't arrived.
  3. rename the temporary file over the real name. The old file stays intact until this instant; afterwards the name points at the new one.
  4. fsync the directory, so that the rename itself is durable.
import os

def atomic_write(path, data: bytes):
    path = os.path.abspath(path)
    tmp = path + ".tmp"                        # same directory, so rename stays on one file system
    with open(tmp, "wb") as f:
        f.write(data)
        f.flush()                               # Python's buffer -> kernel
        os.fsync(f.fileno())                    # kernel page cache -> disk   (step 2)
    os.replace(tmp, path)                       # atomic swap of the name       (step 3)
    dfd = os.open(os.path.dirname(path), os.O_RDONLY)
    try:
        os.fsync(dfd)                           # make the rename durable       (step 4; not on Windows)
    finally:
        os.close(dfd)

Simplified, on purpose

The simulator is a deliberately small model. Real file systems often add protections of their own: for example, some detect the "write temp then rename" pattern and force the data out first. But those are extras you cannot count on across file systems and versions. The simulator shows only what the standard interface promises, which is why it's the right model to program against.

Detecting torn data with checksums

The atomic-replace pattern suits whole small files. For a file that keeps growing, like a database's log, you append records one after another, and a crash can leave the last record half-written. How do you know? You can't tell by looking at the bytes. The standard answer is a checksum: a short number computed from the data, such as a CRC32, stored alongside it. When reading, recompute and compare. A cut-off or corrupted record almost certainly won't match. In Python, zlib.crc32(payload) does this. (A checksum catches accidents, such as a torn write or bit rot. It isn't a defence against someone tampering on purpose.)

Drive caches: when fsync is not enough

There is one more cache below the kernel. Storage devices have a small memory of their own in which they gather writes before putting them on the flash or the platters. If the device reports "done" when data reaches that cache and the power fails, the data is gone, even though the kernel did everything right.

Operating systems differ in how hard fsync tries to reach past it:

  • Linux: fsync also tells the device to flush its cache (in typical configurations), so it waits for the data to reach stable storage.
  • macOS: plain fsync only pushes data to the drive; it does not force the drive to flush its own cache. To get the stronger guarantee you call fcntl with F_FULLFSYNC. In Python: fcntl.fcntl(fd, fcntl.F_FULLFSYNC). It is noticeably slower, which is exactly why it is not the default. SQLite exposes this choice as its fullfsync setting.

Some drives (certain server SSDs, for example) have power-loss protection, an energy reserve that lets them finish writing their cache after the power fails, which makes the question moot. Consumer hardware gives fewer guarantees, and a drive that reports completion dishonestly can't be fixed in software. The simulator above assumes fsync reaches stable storage; this section is why that assumption sometimes costs extra.

Journaling file systems

The file system itself has a crash problem. Creating a file touches several structures: the inode, the directory, the free-space map. A crash between those updates could leave the file system's own structures contradicting each other, like a name pointing to an unallocated inode. Old systems repaired this with a slow full check (fsck) at boot.

A journaling file system (ext4, XFS and NTFS work this way, at a high level) first writes a short note, the journal or log, saying "I'm about to make these changes", makes sure that note is on disk, and only then does the real updates. After a crash it reads the journal and either finishes or discards the half-done changes in seconds. Others, like APFS (macOS), ZFS and btrfs, use copy-on-write: they never overwrite structures in place, but write new versions elsewhere and then flip a pointer.

Common misconception

"I use a journaling file system, so my data is safe." The journal keeps the file system's own structure consistent (mostly its metadata). It does not make your update atomic or durable: a crash can still leave your file empty or half-updated, and the data you wrote still needs fsync. Journaling is what lets your fsyncs and renames mean something; it doesn't replace them.

Go deeper: why the journal idea reappears everywhere optional

"Write down what you're about to do, make that note durable, then do it" is called write-ahead logging (WAL). The file system uses it for its structures. Databases use it for yours. And replicated systems like Raft (networking chapter 20) use it for their agreed log. The note is cheap to write because it's a sequential append, while the real change may be scattered all over the disk. If a crash happens halfway, you replay the note.

The core idea behind database logs

Put the pieces together and you have the heart of a database's durability:

  1. Append-only log. Never modify old data; only add records at the end. Appending is sequential and fast, and it leaves old records untouched, so a crash can damage only the tail.
  2. Checksums. Each record carries its own, so recovery can detect the torn tail and ignore it.
  3. fsync before acknowledging. Only after fsync returns does the database tell the client "committed". Anything acknowledged is therefore on the disk, so a crash can only lose operations that nobody was promised.
  4. Recovery by replay. On restart, read the log from the start, apply each valid record, stop at the first invalid one.
import os, struct, zlib

def append(f, payload: bytes):
    f.write(struct.pack("<II", len(payload), zlib.crc32(payload)) + payload)

def commit(f):
    f.flush()
    os.fsync(f.fileno())          # only after this may we tell the client "saved"

That's the whole trick. You'll build a working version, kill it at random moments, and check that recovery never loses an acknowledged record, in Lab 2: Crash-Safe Storage. The Data Systems course picks up here: database write-ahead logs, checkpoints, and how storage engines like LSM-trees and B-trees are designed around exactly these costs.

Group commit: fsync is slow

The price of that guarantee is fsync's speed. Writing to the page cache takes microseconds. An fsync has to reach the device, and it often costs on the order of milliseconds (a spinning disk takes a seek and rotation, and even many SSDs and cloud disks take about a millisecond; some enterprise SSDs with power-loss protection are much quicker). If each commit costs one fsync of 2 ms, a single log can do at most about 500 commits per second, however fast the CPU is.

The trick is group commit: while one fsync is in progress, gather the writes of many clients, append them all, and then do one fsync that covers everybody. Each client is acknowledged only after that fsync, so nobody is told "saved" too early, but the cost is shared.

Group commit is the standard way databases get high throughput without giving up durability. Systems offer other points on the same trade-off:

PolicyLatencyThroughputWhat a crash can lose
fsync every writeHighest (one fsync each)LowestNothing acknowledged
Group commitOne fsync, plus a short wait to gather a batchHighNothing acknowledged
fsync every secondLowestHighestUp to about a second of acknowledged writes
Never fsync (trust the OS)LowestHighestWhatever hadn't been written back, possibly a lot

Redis offers this very choice for its append-only file: its appendfsync setting can be always, everysec or no. None of these is "right"; it depends on whether losing the last second of data is acceptable. A cache can shrug that off. A bank can't.

When fsync itself fails

One last trap. If a disk write fails (a bad sector, a full device, a disappearing network volume), the error is reported to you only on a later fsync, because write() had long since returned. And you can't simply fix it by retrying: on Linux the kernel may drop the dirty pages that failed, so a second fsync can report success even though the data never reached the disk. In 2018 the PostgreSQL developers discovered that their database had been relying on exactly that retry, and changed it to treat a failed fsync as fatal and recover from its log instead. The story has its own page: Case 1: fsyncgate. The lesson is that after a failed fsync, you don't know what is on the disk, so you must not carry on as if you did.

Try it yourself

Try it yourself: how much does "saved" cost?

This script writes 200 small records three ways and times them. It uses a scratch directory inside your current folder (not /tmp, which on some Linux systems is RAM-backed, where fsync would be almost free) and deletes it afterwards. Your numbers will differ a lot.

import os, time, tempfile, shutil
try: import fcntl
except ImportError: fcntl = None

d = tempfile.mkdtemp(dir=".")
fd = os.open(os.path.join(d, "t"), os.O_WRONLY | os.O_CREAT)
N = 200

def timed(label, sync):
    t = time.perf_counter()
    for _ in range(N):
        os.write(fd, b"x" * 100)
        sync()
    ms = (time.perf_counter() - t) * 1000 / N
    print(f"{label:>12}: {ms:.3f} ms per write")

timed("write only", lambda: None)
timed("fsync", lambda: os.fsync(fd))
if fcntl and hasattr(fcntl, "F_FULLFSYNC"):          # macOS only
    timed("F_FULLFSYNC", lambda: fcntl.fcntl(fd, fcntl.F_FULLFSYNC))
os.close(fd); shutil.rmtree(d)
$ python3 fsync_cost.py
  write only: 0.004 ms per write
       fsync: 0.310 ms per write
 F_FULLFSYNC: 3.900 ms per write

Notice how the same write gets far more expensive the harder you ask for it to be real. A few more safe, read-only things to look at:

$ sysctl vm.dirty_expire_centisecs vm.dirty_writeback_centisecs   # Linux: when dirty pages get written back
$ strace -f -e trace=fsync,fdatasync,rename python3 fsync_cost.py  # Linux: watch the calls happen
$ sync                                          # ask the OS to write back everything dirty now (harmless)

The two vm.dirty_* values are in hundredths of a second: how old a dirty page may get before it must be written, and how often the background flusher wakes up. They don't exist on macOS.

Distributed systems connection

A single machine's disk can fail, so serious systems also survive by copying: replication (networking chapter 18). A write acknowledged only after it reaches several machines survives the loss of any one of them, even if none has flushed to disk yet. But the machines are not independent: a power failure in one rack or one data centre can take them all down at once, so many systems demand both replication and fsync. Consensus protocols like Raft (chapter 20) require a server to write its vote and its log entries durably before replying, otherwise a node that crashed and rebooted could forget a promise it made and break agreement. Every "acknowledged" in a distributed system rests on an fsync somewhere.

Key takeaways

  • write() returns once the data is in the kernel's page cache. The disk gets it later; "written" is not "saved".
  • A process crash does not lose data already handed to the kernel. A power cut or kernel crash does. fsync guards against machine failure.
  • Writing a file in place can leave it torn. The safe update is: write temp, fsync temp, rename, fsync the directory.
  • A new or renamed file needs its directory fsynced, because the name lives in the directory, not the file.
  • Checksums detect torn or corrupt records; an append-only log with checksums and fsync is the core of database durability.
  • Drives have caches too: on macOS use F_FULLFSYNC for the strong guarantee. Journaling protects file-system structure, not your data.
  • fsync is slow (often milliseconds). Group commit shares one fsync among many writers. After a failed fsync, you cannot just retry.

A program calls write(), which returns successfully, and then the process is killed with kill -9 (the machine stays up). What happens to the data?

  1. It is lost, because the process died before it could save
  2. It is corrupted
  3. It is not lost: it is in the kernel's page cache, which survives, and will be written back
  4. It is written to disk immediately by the kernel as the process dies
The page cache belongs to the kernel, not the process. Only data still in the program's own user-space buffers dies with it. A power cut would have been a different story.

In the atomic-replace pattern, why must the temporary file be fsynced before the rename?

  1. Otherwise the rename could reach the disk first, leaving the real name pointing at a file whose contents never arrived
  2. Because rename does not work on files that are in the page cache
  3. To make the rename faster
  4. So the old file can be deleted
Rename makes the name switch atomically, but nothing orders the contents. Without the first fsync, a crash could leave an empty or partial file under the real name.

You create a new file, write to it and call fsync on the file. After a power cut the file is missing. What was most likely missing?

  1. A second fsync on the same file
  2. A larger write buffer
  3. A journaling file system
  4. An fsync on the containing directory, which holds the name that points to the file
The data can be safely on disk while the directory entry (a separate piece of data) is not, so the file has no name after reboot. Sync the file, then its directory.

What does a checksum on each log record let recovery do?

  1. Make the write faster
  2. Detect that the final record was torn by a crash and ignore it
  3. Avoid the need for fsync
  4. Encrypt the log
A half-written record almost certainly won't match its checksum. The checksum detects damage; fsync is still what makes the good records durable.

A database commits each transaction with its own fsync of about 2 ms, and caps at roughly 500 commits per second. Which change raises throughput without acknowledging any write before it is durable?

  1. Skip fsync and let the OS write data back
  2. Acknowledge clients before the fsync, then fsync afterwards
  3. Group commit: batch many clients' log records and cover them with one fsync before acknowledging any of them
  4. Use a smaller checksum
The first two options trade durability for speed. Group commit keeps the promise (every acknowledged write was fsynced) and amortises the cost across the batch, at the price of a little waiting to fill it.

On a Mac, what is different about fsync compared with Linux?

  1. It doesn't force the drive to flush its own cache; F_FULLFSYNC does that, at a cost in speed
  2. It does nothing at all
  3. It also flushes every other file on the system
  4. It only works on directories
macOS fsync pushes data to the drive but doesn't ask the drive to empty its volatile cache. For a stronger guarantee, use fcntl.F_FULLFSYNC, which is why it is slower and opt-in.

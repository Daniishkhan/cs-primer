A Log Shipper That Never Loses a Line

Every server writes log lines, and when something goes wrong at 3 a.m. those lines are all you have. Your job is to design the small agent that sits next to the application, reads its log file and delivers every line to a central service, even if the agent crashes, the machine reboots or the central service disappears for an hour.

How a design studio works

This page is a design problem, not a chapter. At each stage there's a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer isn't the only right design; it's one strong one with its reasoning. A rubric at the end lets you check whether you covered what an experienced engineer would. Being wrong first and then seeing why is the point of the exercise.

📐 The brief

You're building the log agent: a small program that runs on every application server.

  • The application appends lines to a local log file. The agent tails that file and ships the lines to a central log service over the network.
  • Never lose a line that the app wrote, even if the agent crashes, the machine reboots, or the central service is down for an hour.
  • Duplicates are acceptable but should be rare.
  • The agent must not slow down or crash the app.
  • Volume: about 2,000 lines per second at peak, each about 300 bytes.

Your notes

Keep notes as you go: decisions, numbers, open questions. Plain text is fine; try sketching boxes with characters, as in an interview whiteboard.

1Clarify the requirements

"At-least-once" or "exactly-once"? What does "never lose a line" really promise, and from which moment? What if the app itself crashes before its own write is durable?

Compare with a worked answer
  • Delivery guarantee: the brief accepts rare duplicates and forbids loss. That is at-least-once. True exactly-once delivery across a network isn't something an agent can achieve alone (stage 7); the usual answer is at-least-once plus deduplication downstream.
  • "Never lose" starts at a specific moment. The agent can only ship lines that exist in the file to be read. When the app calls write(), the line goes into the kernel's page cache (ch. 9). If the machine loses power before that cache is flushed, the line can be gone from the machine before it was ever copied anywhere safe, and no agent can fix that. So the honest promise is: once the app has written a line to the file, the agent will deliver it, unless the app's own write was lost. If the app needs stronger guarantees (say, audit logs), the app must fsync its own log, and that is a different requirement with a different cost.
  • Partial lines. The app may be midway through a line when the agent reads. The agent must only ship complete lines (ending in a newline) and leave the tail for next time.
  • Ordering and identity. Do lines need to arrive in order? Mostly "roughly", and the central service can order by (file, offset). Decide this now, because it shapes the dedup key in stage 3.
  • The sibling requirement: the agent is a guest on the app's machine. It mustn't use unbounded memory, fill the disk the app needs, or burn the CPU.

The hard part isn't speed (the volume is modest). It is staying correct across crashes: knowing exactly where to resume.

2Back-of-the-envelope numbers

How many bytes per second is that? How much disk does an hour of outage need? What would the fsync rate be if you fsynced per line, and what if you batch?

Compare with a worked answer
  • Throughput: 2,000 lines/s × 300 B = 600 KB/s, roughly 5 Mbit/s. Tiny for a network link or a disk.
  • An hour of outage: 600 KB/s × 3,600 s ≈ 2.2 GB. A day would be about 52 GB. That is small enough to buffer on local disk, and the number tells you how big to make the spool (stage 5): provision for several hours, say 10 to 20 GB, with a hard cap.
  • fsync per line: 2,000 fsyncs per second. A flush to stable storage typically takes on the order of a fraction of a millisecond to several milliseconds depending on the drive (and on macOS, F_FULLFSYNC is needed for a true flush), so per-line fsync would eat most of a disk's capability and compete with the app's own I/O. Group commit: fsync once per batch, say every 100 ms, that is about 10 fsyncs/s covering about 200 lines each. Bounded cost, and in a crash you redo at most 100 ms of work.
  • Batches to the service: if a batch is up to 1,000 lines or 1 second, that is at most a few requests per second at about 300 KB each. Batching turns 2,000 tiny network round trips per second into a handful.
  • Memory: a bounded queue of, say, 10,000 lines is about 3 MB. Make it small and fixed.

Conclusion: no resource is stressed in normal operation. The design questions are all about failure.

3The interface to the central service

What does one request look like? How does the agent know the service really has the data? How can the service recognise a duplicate when the agent retries?

Compare with a worked answer
Request / replyContents
agent → service: SHIPSource (host + file), a batch id, and a list of lines. Each line carries its position, (inode, byte offset).
service → agent: ACKBatch id. Sent only after the service has durably stored the batch (not just received it).
service → agent: error / overloadedRetry later. An explicit "slow down" lets the agent back off.
  • Batching for efficiency, as computed in stage 2. Send when a batch is full or a timer fires, whichever is first.
  • Acknowledgements are the only way to know the data arrived. A TCP connection that accepted your bytes tells you nothing about whether the service stored them (networking ch. 8). The ack must mean "durable on your side".
  • Idempotency. A timeout means the agent doesn't know whether the batch arrived: the data may have been stored but the ack was lost. The only safe move is to resend. To keep that safe, the service must treat a repeated batch as a no-op. Make the batch id deterministic: for example (host, inode, first offset, last offset), not a random number or a time stamp. A resend of the same lines then carries the same id. Even better, deduplicate per line on (host, inode, offset), which stays correct if a restart cuts the batches at different points. This is the idempotency idea of networking ch. 16.

4State: remembering where we are

What must the agent persist so that after a crash it knows where to resume? What goes wrong if the log file is rotated? When may you advance this state, and how do you write it so a crash can't corrupt it?

Compare with a worked answer

The agent's own memory vanishes in a crash, so it keeps a small checkpoint on disk: the file identity and the offset up to which it is finished.

  • The offset alone isn't enough. Log rotation renames app.log to app.log.1 and starts a new app.log. An offset of 41,000,000 means nothing for the new, small file. Store the file's inode (the file's identity, ch. 8) along with the offset. On restart, if the inode of app.log differs from the checkpoint's, finish the old file first (find it by inode among the rotated names), then start the new one at offset 0. A rotated file that was already open stays readable through the descriptor even after being renamed, because the inode lives as long as someone holds it open.
  • Also check for truncation. If the file is now shorter than the checkpoint's offset (a copy-and-truncate rotation, or the machine rebooted before the app's last writes reached disk), the old offset is invalid. Detect size < offset and restart from the beginning of what's there.
  • Writing the checkpoint safely. Use the atomic-replace pattern from ch. 9: write the new checkpoint to a temporary file, fsync it, rename() it over the old one, then fsync the directory. A crash then leaves either the complete old checkpoint or the complete new one, never half of each. Overwriting the file in place could leave it torn.
  • When to advance it: only after the ack. The checkpoint means "everything before this offset is safe elsewhere". If you advance it when you send, a crash after sending but before the service stored the data loses those lines forever. So advance after the service's ack, or after the lines are durably copied into the spool (stage 5), which then takes over responsibility for them.

The order of operations is the whole design: read, deliver (or spool), only then record progress. A crash at any point leaves you at or behind the truth, never ahead of it.

5The architecture

Sketch the pieces between the log file and the network. Where do you buffer, and why in two places? Which pieces must be bounded?

Compare with a worked answer
  • Reader. Opens the file, remembers inode and offset, reads complete lines, hands them on. It uses ordinary reads (the data is probably in the page cache already), takes no locks the app depends on, and never writes to the app's file.
  • Bounded in-memory queue. Decouples reading from sending (ch. 14). When it fills, the reader pauses, which is safe, because the lines are still in the file. The file is itself a durable, ordered buffer.
  • Batcher + sender. Groups lines into batches (by count or timer), sends one request at a time (or a few in flight), waits for the ack, and then asks to advance the checkpoint. It can be written as threads with a queue (ch. 10) or as an event loop with async code (ch. 16, ch. 17); with one network peer and modest volume, either is fine.
  • Disk spool. Why have it if the log file is already a buffer? Because the app's log file is not under the agent's control: rotation may delete old files after a few hours or when they reach a certain count, and an outage can outlast that. When the service is unreachable, the sender appends batches to spool files (fsynced, with a checksum, as in Lab 2) and the checkpoint moves on, since the spool now holds the lines. When the service returns, the spool drains oldest-first before live traffic. Size it from stage 2 (several hours), with a hard cap.

6Deep dives

Pick two and go deep. (a) What is the fsync policy for the spool and the checkpoint? (b) The spool is full and the service is still down: what are your options, and which are unacceptable? (c) How do you follow a log file across rotation? (d) How should retries behave?

Compare with a worked answer

(a) fsync policy and group commit. Writing to the spool without fsync means a power cut loses what's in the page cache (ch. 9), exactly the lines we promised not to lose. But one fsync per line is far too expensive (stage 2). The answer is group commit: write a whole batch to the spool, fsync once, and only then move the checkpoint past it. One fsync covers hundreds of lines. Add a checksum per record so a torn write at the tail is detected and discarded on recovery, as in Lab 2. For the checkpoint, fsync is cheap because it changes only about once per batch. On macOS remember that plain fsync doesn't flush the drive's own cache; F_FULLFSYNC does (Python: fcntl.fcntl(fd, fcntl.F_FULLFSYNC)). Servers are usually Linux, where fsync does the full job on a well-behaved drive.

(b) Backpressure when the spool is full. The queue in front of it is bounded (ch. 14), so a full spool has to push back or shed load. Only three options exist:

  • Block the app. Not acceptable. The whole point is that the agent must not slow or crash the app, and the log is secondary to the business function. Note how blocking could happen by accident: if the agent's disk use fills the shared disk, the app can no longer write. That is why the spool has its own hard size cap (and ideally its own volume or quota).
  • Drop. Drop deliberately, and loudly. Choose which: the oldest spooled data, or the newest incoming. Count what you drop and later ship a marker line such as "dropped 18,240 lines between T1 and T2", so the loss is visible downstream instead of silent.
  • Alert. Raise an alarm well before the cap (say at 50% and 80% full) so a human or automation fixes the central service while the buffer still has room.

The honest answer is: alert early, never block the app, and as a last resort drop in a controlled, counted way. "Never lose a line" is a goal within a budget (a bounded disk), and a good design says what happens when the budget is exceeded. The agent can also stop reading and let the app's log file keep the lines, until rotation would delete them.

(c) Log rotation. The reader holds the file open by descriptor. When the app rotates, the old file keeps its inode and stays readable through the open descriptor even after being renamed (or deleted). So the reader finishes the old file to the end, then opens the new app.log, which has a new inode, and starts at offset 0. Detect rotation by comparing the inode (and size) of the path against the one you hold, checked periodically. The checkpoint stores the inode so this also works across an agent restart. With copy-and-truncate rotation (the file is copied, then truncated to zero in place) there is a small unavoidable window where lines can be lost, which is a good reason to prefer rename-style rotation.

(d) Retries. When a send times out or fails, resend the same batch with the same id after a delay that grows exponentially, with a maximum (say 60 s), and with jitter (a random fraction of that delay). Without jitter, a thousand agents whose service restarted all retry on the same schedule and knock it over again; this is the retry storm of networking ch. 16. Honour any "retry after" the service gives. Keep the agent's own CPU use low and its memory fixed: it should be a very boring neighbour (a container-style CPU and memory limit is a good safety net, ch. 19, so a bug in the agent can't starve the app).

7Failure modes and trade-offs

Walk through crashes at each step. What happens if the agent dies between sending a batch and recording the checkpoint? What if the disk is full, or the clock jumps? Is exactly-once possible?

Compare with a worked answer
  • Crash between send and checkpoint. The service stored the batch and acked, but the agent died before saving the checkpoint. On restart it resumes from the old checkpoint and sends the same lines again. These are the duplicates the brief allows, and they are rare: only the lines in flight at the moment of the crash. The deterministic batch id (or per-line key) lets the service drop them. If we had advanced the checkpoint before the ack, the same crash would instead lose lines. So we choose duplicates over loss: that is at-least-once.
  • Crash before the ack. The batch may or may not have arrived. Resend, same id. Safe by idempotency.
  • Machine reboot. The page cache is gone. Anything the app wrote but never reached disk is lost, as discussed in stage 1. The checkpoint and spool, fsynced as in stage 6, survive. On restart, validate the checkpoint against the file (inode, size ≥ offset) and verify spool record checksums.
  • Service down for an hour. The queue fills, the reader pauses, and batches go to the spool (about 2.2 GB, stage 2). On recovery the spool drains, but pace it so that catching up doesn't overwhelm the service while live traffic keeps arriving.
  • Disk full. The spool's cap and an early alert avoid starving the app (stage 6b). If the agent itself can't write its checkpoint, it should stop shipping and alert, rather than carry on without a safe resume point.
  • Clock issues. Don't use wall-clock time for ordering or for batch ids: it can jump (NTP corrections, leap seconds, as in networking ch. 17). Order by (file, offset). Use the monotonic clock for retry timers and timeouts. Timestamps inside log lines come from the app and are just data.
  • Poison input. One enormous line, or a binary blob, can ruin a batch every time it's retried. Cap line size and truncate, so a single bad line can't block everything behind it.

Analogy: the mail room with a signed receipt

Think of the agent as a clerk posting parcels for the app. The clerk keeps a notebook of the last parcel number delivered, and only writes it down after the recipient signs. If the clerk faints between delivery and writing, the new clerk resends that last parcel; the recipient sees the same number twice and discards one.

Where it breaks down: a real recipient has no durable "have I seen this number" book unless you design for it. In the log service that book is the dedup index, and it needs its own storage and cleanup.

"Exactly-once" is really at-least-once plus deduplication. The agent can never be sure whether a lost ack means a lost batch or a lost reply, which is the Two Generals problem from networking ch. 16. It can choose to resend (risking duplicates) or to give up (risking loss). We choose to resend and let an idempotent receiver make the effect exactly-once. Systems that advertise exactly-once nearly always mean exactly this.

  • Defined what "never lose" means, including the app's own page-cache window before its write is durable.
  • Shipped only complete lines.
  • Did the arithmetic: 600 KB/s, about 2.2 GB per hour, and the fsync rate per line vs per batch.
  • Batched requests and required an ack that means durable.
  • Made retries safe with idempotent batch ids or per-line keys, so the service can deduplicate.
  • Persisted a checkpoint of inode and offset, not just the offset.

  • Advanced the checkpoint only after the ack (or after the spool is durable).
  • Used a bounded queue and a disk spool for outages, with a size cap.

  • Handled log rotation and truncation.
  • Retried with exponential backoff and jitter.

Saying it in an interview

How a senior engineer would summarise this

"The volume is small: about 600 KB a second, so an hour of outage is roughly 2 GB on local disk. The hard part is correctness across crashes, so I'd aim for at-least-once delivery with idempotent batches. The agent tails the file and keeps a checkpoint of inode and offset, written with an atomic rename. It only moves the checkpoint forward after the central service acks a batch, so a crash can duplicate lines but never lose them. Between reader and sender there's a bounded queue, and if the service is down, batches go to a size-capped disk spool, written with group commit, one fsync per batch, never per line. If the spool fills, we alert early and drop in a counted, visible way, but we never block the application. Retries use exponential backoff with jitter. And 'exactly-once' here just means at-least-once plus a deduplicating receiver."

Notice the shape: name what's hard → state the guarantee → order the operations so a crash is safe → bound everything → say what happens at the limit. It works for any pipeline that must not lose data.

Key takeaways

  • Reliable delivery is mostly about ordering operations so that a crash leaves you behind the truth, never ahead of it: read, deliver, then record progress.
  • At-least-once plus idempotent receipt is how "exactly-once" is built. Duplicates are the price of never losing a line.
  • The checkpoint is inode plus offset, written atomically, and advanced only after an ack.
  • Group commit makes durability affordable: one fsync per batch, not per line.
  • Every buffer is bounded; decide in advance what happens when it's full, and never let the helper slow the thing it helps.

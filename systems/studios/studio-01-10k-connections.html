Serve 10,000 Connections on One Machine

Ten thousand phones each keep a connection open to your server, mostly saying nothing, sometimes needing a message right now. One machine has to hold all of them. Your job is to design the server process: how it waits, how it remembers each connection, and what breaks first.

How a design studio works

This page is a design problem, not a chapter. At each stage there's a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer isn't the only right design; it's one strong one with its reasoning. A rubric at the end lets you check whether you covered what an experienced engineer would. Being wrong first and then seeing why is the point of the exercise.

📐 The brief

You're building the presence gateway for a chat app: the server that shows a little green dot when your friends are online.

  • Every running app keeps one TCP connection open to a gateway and sends a tiny heartbeat every 30 seconds.
  • If a client misses heartbeats for 90 seconds, the gateway marks it offline.
  • When a friend comes online or goes offline, the gateway pushes a small message (about 200 bytes) to each affected connected client. Pushes should arrive within 100 ms for 99% of clients.
  • Target: 10,000 connections per machine today, with a plan for 100,000. The machine has 8 CPU cores and 16 GB of RAM.
  • Another service (which you don't design) tells your gateway which friends to notify. Assume that call is fast.

Your notes

Keep notes as you go: decisions, numbers, open questions. Plain text is fine; try sketching boxes with characters, as in an interview whiteboard.

1Clarify the requirements

What would you ask before designing anything? Which requirement is the hard one: throughput, latency, memory or something else? What happens to the user if this server dies?

Compare with a worked answer

Good questions to ask (in an interview you'd say them out loud):

  • How chatty are connections? Here: a heartbeat every 30 s and occasional pushes. Almost all connections are idle almost all the time. That's the key fact.
  • How bad is losing a push? Presence is soft information: a green dot that's a few seconds late or briefly wrong is annoying, not a disaster. That gives us room. If this were payments, the answers would change completely.
  • What happens if a gateway dies? Its clients' connections drop. They will reconnect (to another machine), and their friends may briefly see them as offline. We should make sure those 10,000 reconnects don't arrive all at once (stage 7).
  • Is anything slow done per message? Looking up friends is a call to another service. If that call can be slow, it must not stall everything else.

The hard requirement is concurrency, not throughput: holding a huge number of mostly-idle connections cheaply, and still reacting within milliseconds when any one of them needs attention. Spotting which requirement dominates is often the most valuable sentence in a design discussion.

2Back-of-the-envelope numbers

Estimate: heartbeats per second, pushes per second (make a reasonable assumption), network bandwidth, and memory if every connection costs 10 KB. Which of these is anywhere near a limit?

Compare with a worked answer
  • Heartbeats: 10,000 connections ÷ 30 s ≈ 333 messages/s. For a CPU that runs billions of instructions per second, that's nothing.
  • Pushes: assume each user changes status about every 5 minutes and has around 20 online friends. 10,000 ÷ 300 s ≈ 33 changes/s, × 20 ≈ roughly 700 pushes/s. Some of those friends are connected to other gateways, but let's assume the worst and say a bit under 1,000/s land on this machine.
  • Bandwidth: ~1,000 × 200 bytes ≈ 200 KB/s, plus heartbeats, plus TCP and TLS overhead. A tiny fraction of even a 1 Gbit/s link (about 125 MB/s).
  • Memory: 10,000 × 10 KB = 100 MB. At 100,000 connections, 1 GB. Comfortable on 16 GB, if we keep the per-connection cost near 10 KB. Stage 4 checks whether that's realistic.

So no single resource is under pressure from the work. Whatever limits us will come from the cost of each waiting connection: memory, file descriptors and the overhead of whatever does the waiting. That's why the architecture choice in stage 5 matters so much.

Common misconception

"A server can only have about 65,000 connections because there are only 65,535 ports." The server uses one port (say 443) for all of them. Each TCP connection is identified by four things together: client IP, client port, server IP, server port (networking ch. 7). Different clients make different four-tuples, so the limit on one port is far beyond any real machine's memory. Port limits do bite on the client side, when one machine opens very many outgoing connections to the same destination.

4State: what each connection costs

List everything the machine holds for one connection, in the kernel and in your process. Roughly how big is each piece? Which one depends on the architecture you choose?

Compare with a worked answer
  • A file descriptor (ch. 8). Each socket is an open file. The per-process limit is often 256 (macOS) or 1,024 (many Linux setups) by default, so it must be raised for this server. Forgetting this is a classic production incident: the server works perfectly at 900 users and starts refusing connections a little before 1,024 (a few descriptors are already taken by the listener, logs and so on).
  • Kernel socket buffers. Send and receive buffers live in kernel memory. They grow with in-flight data and are small for idle connections, but a slow client that isn't reading can keep its send buffer full.
  • Application state. User id, auth info, the offline deadline, an output queue. A few hundred bytes to a few KB if we're careful.
  • Whatever does the waiting. This is the architecture-dependent part. With one thread per connection, every connection also owns a thread with its own stack (ch. 3, ch. 10). A common Linux default reserves 8 MB of virtual address space per thread stack. Only the pages actually touched use real RAM (ch. 6), often tens of KB, but that's still often more than everything else on this list combined. With an event loop, waiting costs almost nothing per connection: the connection is just an entry in the kernel's interest list.

5The architecture: who waits, and how?

Compare one thread per connection with an event loop. For each, say what happens when a heartbeat arrives on connection #7,341. Then pick one, and say how you'd use all 8 cores.

Compare with a worked answer

A. Thread per connection. A heartbeat on #7,341 wakes the one thread blocked in read() on that socket. The scheduler gives it a core, it handles the PING and blocks again. The code is beautifully simple. The costs: 10,000 stacks (stage 4), scheduler bookkeeping and context switches for every wake-up (ch. 7), and every piece of shared state (the user → connection map) needs locks (ch. 12). It works at 10,000 on a modern machine if tuned, but it gets uncomfortable at 100,000.

B. Event loop. The loop asks the kernel "which of my sockets are ready?" (epoll on Linux, kqueue on macOS; ch. 16). The kernel answers "#7,341 is readable". The loop reads the bytes without blocking, updates that connection's deadline and goes back to asking. Idle connections cost almost nothing, and within one loop there's no locking, because only one thing runs at a time.

Pick B, with one loop per core (8 loops), each owning a share of the connections. Several processes or threads can share the listening port with SO_REUSEPORT on Linux, or one acceptor can hand new connections out. Each connection belongs to exactly one loop forever, so its state is never touched by two threads. Anything slow, like the friend lookup if it might stall, goes to a small worker pool (ch. 14), and the result is handed back to the loop. This is the shape of nginx, Redis, Node.js and Netty-based servers.

Analogy: waiters vs a host with a buzzer system

Thread-per-connection is one waiter assigned to every table, standing there even when the table is just chatting. An event loop is one host with a board of buzzers: they stand still until a table presses its buzzer, deal with it, and go back to the board.

Where it breaks down: if one table asks the host for something that takes ten minutes, every other table waits too. That's why slow work must go to the kitchen (the worker pool).

6Deep dives

Pick two and go deep. (a) How do you detect 90-second silences on 10,000 connections without 10,000 timers firing constantly? (b) A client on a bad mobile network stops reading. What happens to pushes queued for it? (c) What exactly must be raised or tuned at the OS level?

Compare with a worked answer

(a) Timeouts. Don't set a fresh timer every time a PING arrives. Store each connection's deadline (last heartbeat + 90 s) and check them in batches. A simple way is to wake up once a second and close any connection whose deadline has passed. Smarter structures (a heap ordered by deadline, or a timer wheel of one-second buckets) avoid scanning everyone. Use the monotonic clock, never wall-clock time: if the wall clock jumps (an NTP correction, a leap second), you could disconnect everyone at once.

(b) Slow consumers. If a client isn't reading, its kernel send buffer fills up and write() stops accepting bytes. In an event loop you must not wait. Queue the push in that connection's output buffer instead, and register interest in "writable". Then bound that buffer (ch. 14). Presence is soft state, so when it overflows we can drop older updates for the same friend (only the latest status matters) or simply close the connection and let the client reconnect and resync. An unbounded buffer turns one bad network into the whole server running out of memory.

(c) OS limits.

  • Raise the open-files limit (ulimit -n, or the service manager's setting) well above the target.
  • Make the listen backlog large enough for bursts of new connections.
  • Watch kernel socket-buffer memory.
  • Make sure logging can't block the loop: a synchronous disk write for every heartbeat would be a disaster (ch. 9).

7Failure modes and trade-offs

What happens when this machine restarts? What could make the loop stall? What changes at 100,000 connections, or at 1,000,000 spread over many machines?

Compare with a worked answer
  • Reconnect storm. When a gateway dies, 10,000 clients notice within seconds and all reconnect, each doing TLS and HELLO (and authentication), to the other gateways. If clients retry immediately and in sync, the healthy machines get a burst that can knock them over too. Clients must reconnect with exponential backoff and jitter (networking ch. 16, case study). Gateways should shed load (refuse quickly) rather than accept more than they can handle.
  • Blocking the loop. One accidental blocking call (a DNS lookup, a disk write, a slow regex) freezes every connection on that loop. Pushes miss the 100 ms target and heartbeats are processed late. Measure loop lag (how late timers fire) as a key metric.
  • Pauses. In a garbage-collected language, a long GC pause looks exactly like a blocked loop (ch. 3). Keep per-connection allocations small and steady.
  • 100,000 connections: the event-loop design scales almost linearly in memory (roughly 1 GB at 10 KB each). Thread-per-connection is now clearly the wrong choice.
  • 1,000,000 over many machines: now it's a distributed system. A load balancer spreads connections (networking ch. 14). The service that tracks "which gateway holds user 42" becomes the interesting design problem. The networking course's Millions of Open Connections case study picks up here.

Self-check rubric

Tick what your own design (before reading the answers) covered. An experienced engineer would hit most of these. Missing several is normal the first time, and worth a second try in a week.

  • Identified that the problem is many idle connections, not throughput.
  • Did the arithmetic: heartbeats/s, pushes/s, bandwidth and memory, and noticed which one matters.
  • Defined message framing on top of TCP.
  • Accounted for per-connection cost: file descriptor, kernel buffers, app state, thread stack.
  • Compared thread-per-connection with an event loop, and gave reasons for the choice.
  • Used all cores (one loop per core, or similar) without sharing per-connection state between threads.
  • Kept slow work off the loop (worker pool).
  • Handled timeouts efficiently, with a monotonic clock.
  • Bounded per-connection output buffers and said what happens on overflow.
  • Raised the open-file limit.
  • Planned for a reconnect storm: backoff with jitter, plus load shedding.
  • Named metrics to watch: connections, loop lag, buffer sizes, memory.

Saying it in an interview

How a senior engineer would summarise this

"The workload is tiny: a few hundred heartbeats a second and maybe a thousand pushes. The challenge is holding ten thousand mostly idle connections cheaply. So I'd use non-blocking sockets with one event loop per core. Each connection is owned by one loop, so there's no locking on the hot path. I'd push anything slow to a small worker pool. Per-connection output buffers are bounded, and since presence is soft state, we can drop stale updates or disconnect slow clients. Then the operational bits: raise the file-descriptor limit, use monotonic deadlines for timeouts, and make clients reconnect with jittered backoff so a gateway restart doesn't cascade. Going from ten thousand to a hundred thousand is mostly memory; at a million it becomes a routing problem across machines."

Notice the shape: name what dominates → choose the mechanism → explain the trade-off → name the failure modes → say how it scales. That's the same shape for any design question.

Key takeaways

  • First find which resource actually limits you. Here it's the cost of each waiting connection, not the work.
  • Event loops make waiting nearly free; threads make code simple. At high connection counts with little work each, the loop wins.
  • An event loop has one cardinal rule: never block it. Slow work goes to a worker pool.
  • Every buffer must be bounded, and you must decide what happens when it's full.
  • OS limits (open files, backlog) and failure dynamics (reconnect storms) matter as much as the code.

Workbench 2: Train a Character GPT

Chapter 12 trained a 108,352-weight GPT on Shakespeare with a hand-written NumPy backward pass. Chapter 16 says the training bill is six floating-point operations per parameter per token. Here you build the same model in PyTorch, write down its parameter count and its FLOP bill before it runs, train it, then divide by the stopwatch to find how many FLOP/s your machine actually delivered. A second preset, nanoGPT's 10.8-million-weight Shakespeare model, shows what changes when the matrices get bigger, and the GPU box scales it up.

Why measure it

The rule C ≈ 6ND is how labs budget runs that cost months of GPU time, so it is worth watching it work on a run you can finish before lunch. The interesting number is not the FLOP count, which is arithmetic, but the achieved FLOP/s: the gap between what the hardware could do and what a real training loop gets out of it is where most of the engineering in a large run goes. Predict the count, then measure the speed.

What you need

  • Part 1, your laptop: Python 3.10+, the workbench venv and 1.1 MB for the Tiny Shakespeare text (downloaded once to ~/.cache/zts/). The default run takes well under two minutes on Apple's GPU or on the CPU. About 30 minutes with the exercises.
  • Part 2, a GPU box (optional): one 24 GB card and about an hour. Setting one up is in Your lab machine, Option C.

Predict before you run

Two formulas, one from each chapter. The parameter count of chapter 12's GPT, with width C, L layers, context T and vocabulary V:

N = VC + TC + L (12C2 + 13C) + 2C

and the training compute of chapter 16's anatomy block: two FLOPs per weight on the forward pass and four on the backward pass, for every token trained on.

C ≈ 6 N D

Chapter 16 also lists what 6N leaves out. The largest piece is the attention-score products, which have no weights but are matrix multiplications: 12 L C T extra FLOPs per token. The embedding lookup costs nothing, but because the output head reuses the same table (tied embeddings) the table still counts once, as a matrix product.

The chapter's model has V = 65 characters, T = 64, C = 64, L = 2 and 4 heads. The run uses 3,000 steps of a batch of 32 windows.

Your prediction

On paper: the parameter count N; the number of tokens D; the FLOPs per token with and without the 12LCT term; and the total 6ND. Then guess how long the run will take and what fraction of the FLOP count the attention term adds. Do the same for the nanoGPT preset (T = 256, C = 384, L = 6, 6 heads).

Check your arithmetic

Toy: N = 65 × 64 + 64 × 64 + 2 × (12 × 4,096 + 832) + 128 = 4,160 + 4,096 + 99,904 + 128 = 108,352, as in chapter 12. D = 3,000 × 32 × 64 = 6,144,000 tokens. 6N = 650,112 FLOPs per token; the attention term adds 12 × 2 × 64 × 64 = 98,304, so 748,416 (+15.1%). The total is 6ND = 3.99 × 1012 FLOPs, or 4.60 × 1012 with the attention term.

nanoGPT preset: N = 10,770,816 (chapter 12 quotes the same). 6N = 64,624,896 per token, plus 12 × 6 × 384 × 256 = 7,077,888 for attention, so 71,702,784 (+11.0%).

The time is not derivable from the formula: it needs your machine's FLOP/s, which is what the script measures.

Part 1: on your laptop

Set up once

If you have not yet made the workbench environment, from the site's folder:

$ python3 -m venv ~/.venvs/zts
$ ~/.venvs/zts/bin/pip install -r workbench/requirements.txt
$ source ~/.venvs/zts/bin/activate
$ python deep-learning/workbench/code/w02/char_gpt.py

The script is code/w02/char_gpt.py, and the same code split into cells is char_gpt.ipynb for Jupyter. The first run downloads the text.

The idea

  1. pick the device (CUDA, then Apple MPS, then CPU); read the text and build the character vocabulary
  2. build the GPT; predict N from the formula, then count the parameters PyTorch made
  3. predict C = 6ND, and with the 12LCT attention term, from the step count
  4. train with AdamW, warmup, cosine decay and clipping, timing only the training step
  5. tokens per second × FLOPs per token = achieved FLOP/s; sample some text
"""Train a character GPT in PyTorch, predicting parameters and FLOPs first.

Chapter 12's model on Tiny Shakespeare, with chapter 16's rule C = 6ND. The
script predicts the parameter count and the training FLOPs, trains, then
turns the measured tokens per second into an achieved FLOP/s.

Laptop (the chapter's 108,352-weight model, 3,000 steps):
    python char_gpt.py
GPU box (nanoGPT's 10.8M-weight Shakespeare model; give your card's
datasheet peak to get the utilisation):
    python char_gpt.py --size nano --steps 5000 --batch 64 --peak-tflops 312

Needs: torch (workbench/requirements.txt). Downloads 1.1 MB of text once."""
import argparse
import math
import os
import time
import urllib.request

import torch
import torch.nn as nn
import torch.nn.functional as F

# ── 1. Settings ──────────────────────────────────────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("--size", default="toy", choices=["toy", "nano"])
ap.add_argument("--steps", type=int, default=3000)
ap.add_argument("--batch", type=int, default=32)
ap.add_argument("--peak-tflops", type=float, default=0.0)  # optional
ap.add_argument("--seed", type=int, default=1337)
ap.add_argument("--device", default="auto")      # auto: CUDA, MPS, CPU
args, _ = ap.parse_known_args()        # notebooks pass their own flags

SIZES = {                              # vocab V is read from the data
    "toy": dict(T=64, C=64, h=4, L=2),         # chapter 12
    "nano": dict(T=256, C=384, h=6, L=6),      # nanoGPT shakespeare-char
}
cfg = SIZES[args.size]
T, C, H, L = cfg["T"], cfg["C"], cfg["h"], cfg["L"]

if args.device != "auto":
    DEVICE = args.device
elif torch.cuda.is_available():
    DEVICE = "cuda"
elif torch.backends.mps.is_available():
    DEVICE = "mps"
else:
    DEVICE = "cpu"
torch.manual_seed(args.seed)


def sync():
    if DEVICE == "cuda":
        torch.cuda.synchronize()
    elif DEVICE == "mps":
        torch.mps.synchronize()


# ── 2. Data: characters to ids, 90% train and 10% validation ─────────────
URL = ("https://raw.githubusercontent.com/karpathy/char-rnn/master/"
       "data/tinyshakespeare/input.txt")
path = os.path.expanduser("~/.cache/zts/tinyshakespeare.txt")
if not os.path.exists(path):
    os.makedirs(os.path.dirname(path), exist_ok=True)
    urllib.request.urlretrieve(URL, path)
text = open(path, encoding="utf-8").read()
chars = sorted(set(text))
V = len(chars)
stoi = {c: i for i, c in enumerate(chars)}
data = torch.tensor([stoi[c] for c in text])
n_train = int(0.9 * len(data))
train, val = data[:n_train], data[n_train:]
gen = torch.Generator().manual_seed(args.seed)     # batch offsets, on CPU


def get_batch(d, g):
    ix = torch.randint(0, len(d) - T - 1, (args.batch,), generator=g)
    x = torch.stack([d[i:i + T] for i in ix])
    y = torch.stack([d[i + 1:i + T + 1] for i in ix])
    return x.to(DEVICE), y.to(DEVICE)


# ── 3. The model: chapter 12's GPT, with PyTorch doing the backward ──────


class Block(nn.Module):
    def __init__(self):
        super().__init__()
        self.ln1, self.ln2 = nn.LayerNorm(C), nn.LayerNorm(C)
        self.qkv, self.proj = nn.Linear(C, 3 * C), nn.Linear(C, C)
        self.fc1, self.fc2 = nn.Linear(C, 4 * C), nn.Linear(4 * C, C)

    def forward(self, x):
        B, t, _ = x.shape
        q, k, v = self.qkv(self.ln1(x)).split(C, dim=-1)
        q, k, v = [a.view(B, t, H, C // H).transpose(1, 2) for a in (q, k, v)]
        a = F.scaled_dot_product_attention(q, k, v, is_causal=True)
        x = x + self.proj(a.transpose(1, 2).reshape(B, t, C))
        return x + self.fc2(F.gelu(self.fc1(self.ln2(x)), approximate="tanh"))


class GPT(nn.Module):
    def __init__(self):
        super().__init__()
        self.wte, self.wpe = nn.Embedding(V, C), nn.Embedding(T, C)
        self.blocks = nn.ModuleList([Block() for _ in range(L)])
        self.lnf = nn.LayerNorm(C)
        for name, p in self.named_parameters():          # GPT-2 style init
            if p.ndim >= 2:
                std = 0.02 / math.sqrt(2 * L) if name.endswith(
                    ("proj.weight", "fc2.weight")) else 0.02
                nn.init.normal_(p, 0.0, std)

    def forward(self, idx):
        x = self.wte(idx) + self.wpe(torch.arange(idx.shape[1],
                                                  device=idx.device))
        for b in self.blocks:
            x = b(x)
        return self.lnf(x) @ self.wte.weight.T           # tied head


model = GPT().to(DEVICE)

# ── 4. Predict: parameters (chapter 12) and FLOPs (chapter 16) ───────────
N_formula = V * C + T * C + L * (12 * C * C + 13 * C) + 2 * C
N = sum(p.numel() for p in model.parameters())
tokens = args.steps * args.batch * T                     # D
flops_tok = 6 * N                                        # 6N per token
flops_tok_attn = 6 * N + 12 * L * C * T                  # + score products
print(f"device {DEVICE}; size {args.size}: V={V} T={T} C={C} h={H} L={L}")
print(f"parameters: formula {N_formula:,}, counted {N:,}")
print(f"D = {args.steps} steps x {args.batch} x {T} = {tokens:,} tokens")
print(f"C = 6ND = {6 * N * tokens:.3e} FLOPs "
      f"({flops_tok:,} per token; {flops_tok_attn:,} with the 12LCT "
      f"attention term, +{flops_tok_attn / flops_tok - 1:.1%})")

# ── 5. Train: AdamW, warmup, cosine decay, clipping ──────────────────────
decay = [p for p in model.parameters() if p.ndim >= 2]
no_decay = [p for p in model.parameters() if p.ndim < 2]
opt = torch.optim.AdamW(
    [dict(params=decay, weight_decay=0.1),
     dict(params=no_decay, weight_decay=0.0)],
    lr=3e-3, betas=(0.9, 0.99))
warmup, lr_max, lr_min = 100, 3e-3, 3e-4


def lr_at(t):
    if t < warmup:
        return lr_max * (t + 1) / warmup
    r = (t - warmup) / max(1, args.steps - warmup)
    return lr_min + 0.5 * (1 + math.cos(math.pi * r)) * (lr_max - lr_min)


@torch.no_grad()
def estimate(d, k=20):
    g = torch.Generator().manual_seed(0)         # same batches every time
    model.eval()
    out = sum(F.cross_entropy(
        model(x).view(-1, V), y.view(-1)).item()
        for x, y in (get_batch(d, g) for _ in range(k))) / k
    model.train()
    return out


every = max(1, args.steps // 6)
busy = 0.0                                       # seconds spent training
for step in range(args.steps + 1):
    if step % every == 0 or step == args.steps:
        print(f"step {step:5d}  train {estimate(train):.3f}  "
              f"val {estimate(val):.3f}")
    if step == args.steps:
        break
    x, y = get_batch(train, gen)
    for grp in opt.param_groups:
        grp["lr"] = lr_at(step)
    sync()
    t0 = time.perf_counter()
    loss = F.cross_entropy(model(x).view(-1, V), y.view(-1))
    opt.zero_grad(set_to_none=True)
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step()
    sync()
    busy += time.perf_counter() - t0

# ── 6. Measure: tokens per second, achieved FLOP/s ───────────────────────
tok_s = tokens / busy
achieved = tok_s * flops_tok_attn
print(f"\ntrained {tokens:,} tokens in {busy:.1f} s of step time "
      f"(evaluation not counted)")
print(f"measured: {tok_s:,.0f} tokens/s; {busy / args.steps * 1000:.1f} "
      f"ms/step")
print(f"achieved: {tok_s:,.0f} x {flops_tok_attn:,} = "
      f"{achieved / 1e12:.3f} TFLOP/s")
if args.peak_tflops:
    print(f"utilisation: {achieved / (args.peak_tflops * 1e12):.1%} of "
          f"{args.peak_tflops} TFLOP/s")

# ── 7. Sample ────────────────────────────────────────────────────────────
model.eval()
ids = torch.tensor([[stoi[c] for c in "ROMEO:\n"]], device=DEVICE)
g = torch.Generator(device="cpu").manual_seed(0)
with torch.no_grad():
    for _ in range(280):
        probs = F.softmax(model(ids[:, -T:])[0, -1].float().cpu(), -1)
        nxt = torch.multinomial(probs, 1, generator=g).to(DEVICE)
        ids = torch.cat([ids, nxt[None]], dim=1)
print("\n" + "".join(chars[i] for i in ids[0].tolist()))

What you should see

  • Parameters: formula 108,352, counted 108,352. Your paper arithmetic, chapter 12's number and PyTorch's own count are one number. The tied output head means wte is counted once.
  • The FLOP bill. 3.994 × 1012 FLOPs by the plain rule. The attention term adds 15.1% per token at this size, because the width is small compared with the context. At the nanoGPT preset it adds 11.0%.
  • The loss curve. It starts at 4.11, close to ln 65 = 4.17 (a model that knows nothing), falls quickly through the first few hundred steps and then slows. Validation ends at 1.721 and training at 1.534. Chapter 12's NumPy run, with the same recipe, ended at 1.730 on validation. The two runs draw different random batches and accumulate floating-point rounding differently, so they should agree closely, not exactly; agreeing to within about 0.01 is what confirms the PyTorch model is the same model.
  • The speed. 644,902 tokens per second, 3.2 ms per step. Multiplying by 748,416 FLOPs per token gives 0.483 TFLOP/s achieved (the script includes the attention term, since those FLOPs were really done). Dividing the 4.6 × 1012 FLOP bill by that rate predicts 9.5 s, which is what the stopwatch showed; that is a consistency check rather than an independent prediction, because the rate came from the same run.
  • The sample. It has the file's layout (speaker names, line breaks) and nonsense words, the fingerprint chapter 12 describes for a model this small.

The same run on the CPU, and a bigger model

Two more runs on the same laptop show how the achieved rate depends on the setup. First, --device cpu with the same 3,000 steps gave 337,226 tokens per second (6.1 ms per step), or 0.252 TFLOP/s, so Apple's GPU was about 1.9 times faster than the CPU cores for this model, and it ended on the same train 1.534 and validation 1.721. ROMEO:
  • The achieved rate rose from 0.48 to 1.94 TFLOP/s, four times higher, with no change in the hardware. The likely reason is that the toy model's matrices (64 wide) are too small to keep the chip busy, so a large share of each 3.2 ms step goes on launching many small operations; the larger model's matrices (384 wide) amortise that overhead. This is a hypothesis from the mechanism, which you can test by running --size toy --batch 256 and watching the rate climb.
  • The full nanoGPT run is too long for a laptop. 5,000 steps of batch 64 is 81.9 million tokens; at 27,020 tokens per second that is about 50 minutes. The loss after 60 steps (2.54) is nowhere near converged, which is why this run only proves the pipeline works. That is what the GPU box is for.

Part 2: scaling it on a GPU box

On the GPU box (wb up, wb sync, wb ssh), run the nanoGPT preset in full. Give the script your card's datasheet peak for dense 16-bit arithmetic, and it prints the utilisation:

$ cd /workspace/zts/deep-learning/workbench/code/w02
$ python char_gpt.py --size nano --steps 5000 --batch 64 --peak-tflops 312

Not run here

This page was written on a machine without an NVIDIA GPU, so there is no printed GPU output. The predictions below come from chapter 16's formulas and the A100 datasheet figure the chapter quotes (312 TFLOP/s dense in 16-bit); the utilisation is an assumption, labelled as one. The script runs in 32-bit floats, which a CUDA card handles at a lower peak than the 16-bit figure, so a real first run may land below these numbers until you switch to bfloat16. Your card, and its datasheet peak, will differ from the A100: substitute your own.

The prediction: D = 5,000 × 64 × 256 = 81,920,000 tokens. The bill is 71,702,784 × 81,920,000 = 5.87 × 1015 FLOPs (5.29 × 1015 by 6ND alone). On a card with a 312 TFLOP/s peak, a utilisation of 20%, 30% or 40% would deliver 62.4, 93.6 or 124.8 TFLOP/s, so the run would take 94, 63 or 47 seconds and process 0.87, 1.31 or 1.74 million tokens per second. Chapter 16 calls 30% to 50% good for a large distributed run and says a first single-GPU implementation often lands lower; for a model this small, whose matrices are modest, expect the low end or below.

The last two depend on the utilisation you guessed, and the point of the exercise is the size of the miss: it tells you what fraction of the card's peak this loop really used. On a 10-million-weight model the loss will also overfit the 1.1 MB file within a few thousand steps, as chapter 12 notes; watch the gap between train and validation widen.

Break it

  • Double the batch. Run --size toy --batch 64 --steps 1500 (the same token count). Predict first: the FLOP bill is unchanged, so if tokens per second rise it is because the chip was under-used, not because the arithmetic got cheaper.
  • Double the context. Edit "toy" to T=128 and keep the tokens fixed by halving the batch. Predict the new attention share of the FLOPs per token (the 12LCT term doubles; what happens to 6N?) and check it against the printed line.
  • Count without the head. A per-token count that excludes the table (non-embedding N) differs by 65 × 64 = 4,160 weights. By what percentage does 6ND change for the toy model, and for the nanoGPT preset? (Chapter 16's misconception box says this matters more for small models.)
  • Break the starting loss. Remove the 0.02 initialisation loop. The first printed loss will no longer sit near ln 65; predict whether it will be higher or lower, and by how much it matters for the first hundred steps.

Key takeaways

  • The parameter count is a formula you can write before you build the model, and PyTorch's own count matches it exactly.
  • 6ND counts the arithmetic; the attention term adds about 11% to 15% at these sizes, and more as the context grows.
  • Achieved FLOP/s is the measurement that matters: the same laptop delivered 0.48 TFLOP/s on a tiny model and 1.94 TFLOP/s on a bigger one.
  • A model has to be big enough to keep the hardware busy before its utilisation says anything about the hardware itself.

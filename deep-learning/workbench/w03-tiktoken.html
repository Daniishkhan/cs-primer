Workbench 3: Real Tokenisers

A language model never reads text. It reads whole numbers, and a program called a tokeniser decides which ones. Each piece of text it cuts out is a token. Chapter 13 gave you rules for how many tokens a text costs: about four bytes per token in English, a heavy penalty for some scripts in older vocabularies, and digits cut into groups. Here you write those rules down as predictions, then count real tokens with three tokenisers: two from OpenAI's tiktoken library and the one that ships with Qwen2.5.

Why measure it

Everything a language model service sells is counted in tokens: the bill, the context window and the time to reply. The question "how many tokens is this?" has no answer until you name the tokeniser. Chapter 13 showed one sentence in seven languages, and one sentence is an anecdote. Here you run six different texts through three tokenisers and check each rule against the numbers. The habit matters more than any single number: write the prediction down, then measure. A rule that fails tells you what the rule left out.

What you need

  • The lab VM, no GPU. The 16-vCPU machine of Your Lab Machine with its ~/lab environment (below). About 20 MB of disk: two tiktoken vocabulary files (1.7 MB and 3.6 MB, downloaded from openaipublic.blob.core.windows.net) and the Qwen2.5 tokeniser files (about 11 MB, from Hugging Face). No model weights are loaded.
  • Time. The script runs in a few seconds. Allow about 45 minutes with the experiments at the end.

Predict before you run

All of chapter 13's cost rules come from one relation. The number of tokens is the number of UTF-8 bytes in the text divided by the average number of bytes the tokeniser packs into one token (chapter 13):

tokens ≈ UTF-8 bytes / bytes per token

UTF-8 is the encoding that turns text into bytes. An English letter takes one byte, most Hindi and Japanese characters take three, and an emoji takes four. The three rules below are the chapter's findings, turned into things you can check.

  • Rule A, English. About 4 bytes per token in every vocabulary.
  • Rule B, other scripts. A script stored in 3 bytes per character starts three times longer than English. An older vocabulary keeps most of that penalty. A newer, multilingual one gives it back. The chapter's single sentence gave Hindi 55 tokens against English 17 under cl100k_base (3.2 times), and 16 against 17 under o200k_base.
  • Rule C, digits. Both OpenAI vocabularies cut a run of digits into groups of three from the left. A run of d digits then costs the next whole number above d / 3 tokens.

Your prediction

On paper, before reading on. The English test sentence is 108 bytes long: how many tokens? The test text also holds seven digit runs: 2024, 10, 14, 1234567, 3, 14159 and 1000000000. How many tokens do they cost together under Rule C? Then guess two things the chapter does not state: will the Qwen2.5 tokeniser charge Hindi more or less than o200k_base, and how will it cut digits?

Check your arithmetic

English: 108 / 4 = 27 tokens. Digits: 2024 is 2 tokens (202 and 4), 10 is 1, 14 is 1, 1234567 is 3 (123, 456, 7), 3 is 1, 14159 is 2 (141 and 59) and 1000000000 is 4 (100, 000, 000, 0). The sum is 2 + 1 + 1 + 3 + 1 + 2 + 4 = 14 tokens. For Hindi, Rule B says the cost against English should be above 3 under cl100k_base and below 1.5 under o200k_base. My own guesses for Qwen were "somewhere between those two" and "one token per digit". The script prints all of these before it measures anything.

Run it

Set up once

The lab VM already has one Python environment, ~/lab, that serves every workbench page. Copy the site's code folder to the VM, then from the site's folder:

$ source ~/lab/bin/activate

The script is code/w03/tiktoken_compare.py, and the same code split into cells is tiktoken_compare.ipynb for Jupyter. The first run downloads the vocabulary files.

The idea

  1. load cl100k_base, o200k_base and a Hugging Face tokeniser (Qwen2.5 by default)
  2. print the predictions: 108 bytes ÷ 4, the Hindi-to-English ratio, ceil(d / 3) per digit run
  3. for each of six texts, count tokens, tokens per word and bytes per token under all three
  4. show where each tokeniser cuts the digit runs
  5. take apart a character the tokeniser splits across two tokens, and show the streaming fix
"""Real tokenisers, measured: predict token counts from chapter 13's
reasoning, then count them with tiktoken and a Hugging Face tokenizer.

    python tiktoken_compare.py
    python tiktoken_compare.py --hf Qwen/Qwen2.5-0.5B

Needs: tiktoken, transformers (workbench/requirements.txt). The first run
downloads two tiktoken files (1.7 MB and 3.6 MB, from
openaipublic.blob.core.windows.net) and the Qwen tokenizer files
(about 11 MB from Hugging Face). No model weights are loaded."""
import argparse
import math
import re

import tiktoken
from transformers import AutoTokenizer

# ── 1. Settings ──────────────────────────────────────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("--hf", default="Qwen/Qwen2.5-0.5B")
args, _ = ap.parse_known_args()        # notebooks pass their own flags

TEXTS = {
    "English": "The weather is nice today, so we are going for a walk "
               "in the park, and then we will have lunch by the river.",
    "German": "Das Wetter ist heute schön, deshalb gehen wir im Park "
              "spazieren und essen danach am Fluss zu Mittag.",
    "Hindi": "आज मौसम अच्छा है, इसलिए हम पार्क में टहलने जा रहे हैं "
             "और फिर नदी के किनारे दोपहर का खाना खाएँगे।",
    "Japanese": "今日は天気がいいので、公園へ散歩に行って、"
                "そのあと川のそばで昼ご飯を食べます。",
    "Numbers": "In 2024-10-14 we counted 1234567 users, 3.14159 "
               "seconds and 1000000000 bytes.",
    "Code": 'def area(r):\n    if r < 0:\n        raise ValueError("r")\n'
            '    return 3.14159 * r * r\n',
}
# A "word" is a run of non-space characters, except in Japanese, which
# has no spaces: there we count the characters instead.


def words(name, text):
    return len(text) if name == "Japanese" else len(text.split())


# Three counters with the same interface: text -> list of ids.
cl = tiktoken.get_encoding("cl100k_base")
o2 = tiktoken.get_encoding("o200k_base")
hf = AutoTokenizer.from_pretrained(args.hf)
COUNTERS = {
    "cl100k": cl.encode,
    "o200k": o2.encode,
    "hf": lambda s: hf.encode(s, add_special_tokens=False),
}
DECODERS = {"cl100k": cl.decode, "o200k": o2.decode, "hf": hf.decode}
print(f"cl100k_base: {cl.n_vocab:,} entries; o200k_base: {o2.n_vocab:,}; "
      f"{args.hf}: {len(hf):,}\n")

# ── 2. Predict (chapter 13), before any counting ─────────────────────────
# Rule A: English costs about 4 bytes per token in every vocabulary.
# Rule B: a script that UTF-8 stores in 3 bytes per character starts three
#         times longer; an old vocabulary keeps most of that, a new
#         multilingual one gives it back. Prediction: Hindi and Japanese
#         cost 2 to 4 times English per word under cl100k, less under o200k.
# Rule C: cl100k and o200k cut a digit run into groups of three from the
#         left, so a run of d digits costs ceil(d / 3) tokens.
print("predicted tokens (rules A and C)")
eng = TEXTS["English"]
print(f"  English: {len(eng.encode())} bytes / 4 = "
      f"{len(eng.encode()) / 4:.0f} tokens")
runs = re.findall(r"\d+", TEXTS["Numbers"])
c_pred = sum(math.ceil(len(r) / 3) for r in runs)
print("  Hindi cost / English cost, tokens: above 3 under cl100k, below "
      "1.5 under o200k (chapter 13: 55/17 and 16/17)")
print("  hf (Qwen2.5): no rule in the chapter; guess: Hindi cost between "
      "the two, digits one per token")
print(f"  digit runs {runs}: sum of ceil(d/3) = {c_pred} tokens for "
      f"the digits alone")

# ── 3. Measure: tokens, bytes per token, tokens per word ─────────────────
print("\nmeasured")
head = f"  {'text':9}{'bytes':>6}{'words':>6}"
for k in COUNTERS:
    head += f"{k:>9}{'tok/word':>9}"
print(head)
counts = {}
for name, text in TEXTS.items():
    nb, nw = len(text.encode()), words(name, text)
    row = f"  {name:9}{nb:>6}{nw:>6}"
    for k, enc in COUNTERS.items():
        n = len(enc(text))
        counts[name, k] = n
        row += f"{n:>9}{n / nw:>9.2f}"
    print(row)
print("\nHindi tokens / English tokens, and Japanese / English")
for k in COUNTERS:
    h = counts["Hindi", k] / counts["English", k]
    j = counts["Japanese", k] / counts["English", k]
    print(f"  {k:8} Hindi {h:.2f}   Japanese {j:.2f}")
print("\nbytes per token")
for name, text in TEXTS.items():
    nb = len(text.encode())
    cells = "".join(f"{k}={nb / counts[name, k]:.2f}  " for k in COUNTERS)
    print(f"  {name:9}{cells}")

# ── 4. Numbers: where do the cuts fall? ──────────────────────────────────
print("\ndigit runs, cut by each tokeniser")
for r in runs:
    cuts = []
    for k, enc in COUNTERS.items():
        pieces = [DECODERS[k]([i]) for i in enc(r)]
        cuts.append(f"{k}: " + "|".join(pieces))
    print(f"  {r:11} " + "   ".join(cuts))
digits_pred = sum(len(cl.encode(r)) for r in runs)
print(f"  cl100k digits alone: {digits_pred} tokens "
      f"(predicted {c_pred})")

# ── 5. A character split across tokens ───────────────────────────────────
print("\nmulti-byte characters")
for ch in ["é", "語", "🙂"]:
    raw = ch.encode()
    ids = cl.encode(ch)
    pieces = [cl.decode_single_token_bytes(i) for i in ids]
    alone = [cl.decode_bytes([i]).decode("utf-8", errors="replace")
             for i in ids]
    print(f"  {ch}  {len(raw)} bytes {raw.hex(' ')}; cl100k ids {ids} "
          f"= bytes {[p.hex(' ') for p in pieces]}; "
          f"each alone decodes to {alone}; together "
          f"{cl.decode(ids)!r}")
ids = hf.encode("🙂", add_special_tokens=False)
alone = [hf.decode([i]) for i in ids]
print(f"  🙂 hf ids {ids}; each alone decodes to {alone}; "
      f"together {hf.decode(ids)!r}")
print("  tokens that start or end inside a character (decode to "
      "\ufffd alone):")
for name in ("Japanese", "Hindi"):
    row = f"    {name:9}"
    for k, enc in COUNTERS.items():
        ids = enc(TEXTS[name])
        bad = sum("\ufffd" in DECODERS[k]([i]) for i in ids)
        row += f"{k} {bad} of {len(ids)}   "
    print(row)

# ── 6. The streaming fix: buffer bytes until a character is complete ─────
text = "Hi 語🙂"
naive, buf, out = "", b"", ""
for i in cl.encode(text):
    piece = cl.decode_single_token_bytes(i)
    naive += piece.decode("utf-8", errors="replace")
    buf += piece
    try:
        out += buf.decode("utf-8")
        buf = b""                      # complete: send it, clear the buffer
    except UnicodeDecodeError:
        pass                           # incomplete: wait for the next token
print(f"\nstreaming {text!r}: naive {naive!r}, buffered {out!r}")

What you should see

  • English: 27 tokens in all three, exactly 4.00 bytes per token. Rule A holds, and the prediction of 27 was right. The tokens-per-word figure is 1.12, below the usual 1.33 (three quarters of a word per token). This sentence is short, common words, which are one token each. Text with longer or rarer words would cost more.
  • German is already uneven. 1.50 tokens per word under cl100k_base and the Qwen tokeniser, 1.22 under o200k_base. The newer vocabulary has seen more German.
  • Hindi shows Rule B clearly. The Hindi-to-English ratio is 3.59 under cl100k_base (predicted above 3) and 1.11 under o200k_base (predicted below 1.5). In bytes: 2.54 per token against 8.20. My guess for Qwen was "between the two". The number, 3.37, is technically between but sits next to cl100k_base. A large vocabulary (151,665 entries here) does not make Hindi cheap by itself. This agrees with the chapter's point that what the vocabulary was trained on decides what is cheap.
  • Japanese has no spaces, so the "words" column counts characters: 0.74 tokens per character under o200k_base, 0.67 under Qwen and 1.15 under cl100k_base. Qwen's 4.50 bytes per token is better than English. Its tokeniser was built for Chinese as well, and Japanese shares many characters with Chinese. That is a likely reason, not something this script tests.
  • Digits: the prediction of 14 was exact. The last line of the digit block says so. Both OpenAI vocabularies cut 1234567 as 123|456|7 and the year 2024 as 202|4, splitting the year in two. Qwen2.5 gives every digit its own token, as I guessed. It is regular, with the same alignment for every number, at a cost: the numbers text needs 47 tokens against 30. This is a design choice, not something learned. The Qwen2.5 tokenizer.json splits text first with a pattern that matches one digit at a time (\p{N}), where the chapter's cl100k pattern allows up to three (\p{N}{1,3}).
  • Code costs more than prose. The four-line function averages 2.6 to 2.9 bytes per token, against 4.00 for English, because of punctuation and indentation. One snippet is an anecdote. Try your own language.
  • Characters split across tokens. The accented é is two bytes (c3 a9) and one token. The Japanese character 語 is three bytes, cut into e8 aa and 9e. Decoded alone, each half is the replacement character �. The emoji is cut into f0 9f and 99 82 under cl100k_base, but Qwen has a single token for it. Across a whole sentence, 18 of the 45 Japanese tokens under cl100k_base start or end inside a character, and none do under o200k_base or Qwen. For Hindi, 62 of 97 and 50 of 91 do, and none under o200k_base.
  • The streaming line is the practical lesson. A server that sends each token's text the moment it appears produces Hi ������. One that holds the bytes until they form a whole character produces Hi 語🙂. The fix is the six lines in section 6 of the script.

Key takeaways

  • Token count is roughly bytes divided by bytes per token. English gets about 4 in all three tokenisers, so the same sentence cost 27 tokens each time.
  • Cost across languages depends on the tokeniser. Hindi cost 3.6 times English under cl100k_base and 1.1 times under o200k_base. The size of a vocabulary does not predict it; its training text does.
  • Digit handling differs by design: groups of three in the OpenAI vocabularies, one digit per token in Qwen2.5. Neither is free.
  • A token can end in the middle of a character. Any code that decodes a stream token by token must buffer bytes until a character is complete.
  • Count tokens with the exact tokeniser of the model you deploy. A count from another family is only an estimate.

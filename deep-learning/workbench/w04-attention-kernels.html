Workbench 4: Attention Kernels, Benchmarked

Chapter 9 defined attention as two matrix products around a softmax, and chapter 19 explained why writing the T × T score matrix to memory is the expensive part and how FlashAttention avoids it. Here you predict the memory from that explanation, then compare a plain implementation with PyTorch's fused scaled_dot_product_attention as the sequence grows from 256 to 4,096 tokens: peak memory, time and achieved arithmetic speed. The lab VM part is measured. The part that needs a CUDA GPU (flash, memory-efficient and math backends, and sequences where the plain version cannot fit at all) is predicted from the same arithmetic, with a table for you to fill in.

Why measure it

Chapter 19 makes a claim you can check with a stopwatch: FlashAttention changes how the numbers are moved, not which numbers are computed. If that is true, the output must match, the memory must stop growing with T², and the time should improve because the program waits less for memory, while the FLOP count stays the same. Each of those is a measurement, and the prediction for each comes straight from one line of the chapter.

What you need

  • Part 1, the lab VM: the 16-vCPU machine of Your Lab Machine with its ~/lab environment; no downloads. The script runs on the CPU and takes under a minute. About 45 minutes with the exercises.
  • Part 2, a GPU box (optional): one 24 GB NVIDIA card, rented later, and about 15 minutes of it, to see the CUDA backends. Setting one up is in Your lab machine, Option C.

Predict before you run

The function from chapter 9's anatomy block is:

Attention(Q, K, V) = softmax(Q KT / √dk) V

A plain implementation computes S = QKT/√dk, which has T × T entries per head, applies the causal mask, and then the softmax writes a second T × T matrix P while S is still alive. Chapter 19 says FlashAttention keeps neither. The script runs one sequence (B = 1) of 8 heads of width dk = 64, in 32-bit floats (4 bytes).

naive peak ≈ 2 B H T2 b    fused ≈ B H T dk b    FLOPs = 4 B H T2 dk

The FLOP count is two matrix products (QKT and PV), each 2 × T × T × dk per head, which is the “2 FLOPs per multiply-add” rule of chapter 16. Both implementations do the same arithmetic.

Your prediction

For T = 1,024 and T = 4,096: how many MiB is one T × T matrix for all 8 heads, how many does the naive version need at its peak, and how many does the fused kernel need? When the length doubles, by what factor does each grow, and by what factor should the time of the naive version grow? Which is faster, and by roughly how much: choose a number before you look.

Check your arithmetic

One matrix: 8 × 1,024 × 1,024 × 4 bytes = 32 MiB at T = 1,024 and 512 MiB at 4,096. The naive peak is two of them: 64 MiB and 1,024 MiB. The fused kernel holds only the output, 8 × T × 64 × 4 bytes: 2 MiB and 8 MiB. Doubling T quadruples the naive memory and doubles the fused memory. The FLOPs are 2.15 and 34.4 GFLOP, so the naive time should also grow about 4 times per doubling, if it is limited by arithmetic or by memory traffic that scales like T2. The speed-up is not derivable from the formulas: it depends on the machine, which is what the measurement is for. Chapter 19 only claims the fused kernel is faster because the plain one waits for memory.

The idea

  1. write the plain attention step by step (S, mask, softmax, P V) and call the fused kernel once
  2. print the predicted memory and FLOPs for each length before measuring anything
  3. check both give the same answer
  4. peak memory: the profiler's allocations on the CPU, or CUDA's own counter
  5. time each on the chosen device with a warm-up and a synchronise; divide the nominal FLOPs by it
  6. CUDA only: repeat the fused call under the flash, memory-efficient and math backends
"""Attention kernels, benchmarked: naive attention against PyTorch's fused
scaled_dot_product_attention, as the sequence gets longer.

Chapter 19 says the naive version writes a T x T score matrix and its
softmax to memory, and that FlashAttention never does. The script predicts
the memory from that sentence, then measures peak memory and time.

Lab VM (CPU):
    python attn_kernels.py
    python attn_kernels.py --device cpu
GPU box (adds CUDA's flash, memory-efficient and math backends, 16-bit):
    python attn_kernels.py --lengths 1024 4096 16384 --heads 32 --dim 128

Needs: torch (workbench/requirements.txt). No downloads."""
import argparse
import math
import statistics
import time

import torch
import torch.nn.functional as F
from torch.profiler import ProfilerActivity, profile

# ── 1. Settings ──────────────────────────────────────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("--lengths", type=int, nargs="+",
                default=[256, 512, 1024, 2048, 4096])
ap.add_argument("--heads", type=int, default=8)
ap.add_argument("--dim", type=int, default=64)        # head width d_k
ap.add_argument("--device", default="auto")           # auto: CUDA, CPU
ap.add_argument("--repeats", type=int, default=5)
args, _ = ap.parse_known_args()        # notebooks pass their own flags

if args.device != "auto":
    DEVICE = args.device
elif torch.cuda.is_available():
    DEVICE = "cuda"
else:
    DEVICE = "cpu"
DTYPE = torch.float16 if DEVICE == "cuda" else torch.float32
BYTES = torch.tensor([], dtype=DTYPE).element_size()
B, H, D = 1, args.heads, args.dim
torch.manual_seed(0)


def mib(n):
    return n / 2**20


def sync():
    if DEVICE == "cuda":
        torch.cuda.synchronize()


# ── 2. The two implementations ───────────────────────────────────────────


def naive(q, k, v):
    """Chapter 9's formula, one step per line: S, mask, P, then P V."""
    T = q.shape[-2]
    s = (q @ k.transpose(-1, -2)) / math.sqrt(q.shape[-1])    # S: T x T
    mask = torch.ones(T, T, dtype=torch.bool, device=q.device).triu(1)
    s = s.masked_fill(mask, float("-inf"))
    return torch.softmax(s, dim=-1) @ v                       # P: T x T


def fused(q, k, v):
    """One call; PyTorch picks a tiled kernel that never forms S."""
    return F.scaled_dot_product_attention(q, k, v, is_causal=True)


def make(T, device, dtype):
    return [torch.randn(B, H, T, D, device=device, dtype=dtype)
            for _ in range(3)]


# ── 3. Predict (chapter 19) ──────────────────────────────────────────────
# S has B*H*T*T numbers; the softmax writes a second T x T matrix while S is
# still alive. The fused kernel keeps only the output, B*H*T*D numbers.
print(f"device {DEVICE}, {DTYPE}, B={B} H={H} d_k={D}, torch "
      f"{torch.__version__}")
print("\n== predicted, before measuring ==")
print(f"{'T':>6} {'one T x T (MiB)':>16} {'naive peak = 2x':>16} "
      f"{'fused = output':>15} {'attention GFLOP':>16}")
for T in args.lengths:
    one = B * H * T * T * BYTES
    out = B * H * T * D * BYTES
    gflop = 4 * B * H * T * T * D / 1e9      # Q K^T and P V, 2 FLOPs each
    print(f"{T:6d} {mib(one):16.2f} {mib(2 * one):16.2f} "
          f"{mib(out):15.2f} {gflop:16.2f}")

# ── 4. Same answer? ──────────────────────────────────────────────────────
q, k, v = make(512, DEVICE, DTYPE)
err = (naive(q, k, v).float() - fused(q, k, v).float()).abs().max().item()
print(f"\nmax |naive - fused| at T=512: {err:.2e}  (same maths, rounded "
      f"differently)")


# ── 5. Measure peak memory ───────────────────────────────────────────────


def peak_bytes(fn, T):
    """Peak extra memory while fn runs, inputs excluded."""
    if DEVICE == "cuda":
        q, k, v = make(T, "cuda", DTYPE)
        torch.cuda.synchronize()
        base = torch.cuda.memory_allocated()
        torch.cuda.reset_peak_memory_stats()
        try:
            out = fn(q, k, v)
        except torch.OutOfMemoryError:
            return None
        torch.cuda.synchronize()
        return torch.cuda.max_memory_allocated() - base
    # No CUDA peak counter here, so use the CPU: add up the profiler's
    # allocations and frees in time order and keep the maximum.
    q, k, v = make(T, "cpu", DTYPE)
    with profile(activities=[ProfilerActivity.CPU],
                 profile_memory=True) as prof:
        out = fn(q, k, v)
    steps = sorted((e.time_range.start, e.self_cpu_memory_usage)
                   for e in prof.events() if e.self_cpu_memory_usage)
    now = peak = 0
    for _, delta in steps:
        now += delta
        peak = max(peak, now)
    return peak


where = "CUDA" if DEVICE == "cuda" else "CPU, float32"
print(f"\n== peak memory (measured on {where}) ==")
print(f"{'T':>6} {'naive MiB':>10} {'/ 2x pred':>10} {'fused MiB':>10} "
      f"{'/ out pred':>10}")
for T in args.lengths:
    n, f = peak_bytes(naive, T), peak_bytes(fused, T)
    out = B * H * T * D * BYTES
    if n is None:
        print(f"{T:6d} {'OOM':>10}")
        continue
    print(f"{T:6d} {mib(n):10.2f} {n / (2 * B * H * T * T * BYTES):10.3f} "
          f"{mib(f):10.2f} {f / out:10.3f}")

# ── 6. Measure time on the chosen device ─────────────────────────────────


def median_ms(fn, q, k, v):
    fn(q, k, v)                                          # warm up
    sync()
    times = []
    for _ in range(args.repeats):
        t0 = time.perf_counter()
        fn(q, k, v)
        sync()
        times.append((time.perf_counter() - t0) * 1000)
    return statistics.median(times)


print(f"\n== time per call on {DEVICE} (median of {args.repeats}) ==")
print(f"{'T':>6} {'naive ms':>9} {'fused ms':>9} {'speed-up':>9} "
      f"{'naive GFLOP/s':>14} {'fused GFLOP/s':>14}")
for T in args.lengths:
    try:
        q, k, v = make(T, DEVICE, DTYPE)
        tn, tf = median_ms(naive, q, k, v), median_ms(fused, q, k, v)
    except (torch.OutOfMemoryError, RuntimeError) as e:
        print(f"{T:6d}  failed: {str(e)[:50]}")
        continue
    g = 4 * B * H * T * T * D / 1e9                      # nominal FLOPs
    print(f"{T:6d} {tn:9.2f} {tf:9.2f} {tn / tf:9.2f} "
          f"{g / tn * 1000:14.0f} {g / tf * 1000:14.0f}")

# ── 7. CUDA only: the three backends ─────────────────────────────────────
if DEVICE == "cuda":
    from torch.nn.attention import SDPBackend, sdpa_kernel
    print("\n== CUDA backends of scaled_dot_product_attention ==")
    for name, be in [("flash", SDPBackend.FLASH_ATTENTION),
                     ("mem-efficient", SDPBackend.EFFICIENT_ATTENTION),
                     ("math", SDPBackend.MATH)]:
        for T in args.lengths:
            with sdpa_kernel(be):
                try:
                    q, k, v = make(T, "cuda", DTYPE)
                    ms = median_ms(fused, q, k, v)
                    mem = peak_bytes(fused, T)
                    print(f"  {name:14s} T={T:6d}: {ms:8.2f} ms, peak "
                          f"{mib(mem):9.2f} MiB")
                except (torch.OutOfMemoryError, RuntimeError) as e:
                    print(f"  {name:14s} T={T:6d}: failed "
                          f"({str(e)[:40]})")

What you should see

  • The predicted table is your paper arithmetic: 32 and 512 MiB per matrix at 1,024 and 4,096, and a fused output of 2 and 8 MiB.
  • The outputs agree to 6.56 × 10−7, the rounding of 32-bit floats. FlashAttention is exact, not an approximation; the tiny difference comes from adding the same numbers in a different order.
  • Fused memory / output prediction = 1.000 at every length: the kernel holds the output and nothing of size T × T. It grows by 2 per doubling.
  • Naive memory / 2× prediction is between 1.14 and 1.02. Two full matrices are alive at once, as predicted, and the small excess is the causal mask (a T × T table of one-byte booleans) plus a fixed overhead that matters less as T grows. At T = 4,096 the plain version needs 1,048 MiB for 8 MiB of answer, 131 times as much.
  • Time. The fused kernel is faster at every length, by 2 times at T = 256 (0.35 against 0.16 ms) and 14.7 times at T = 4,096 (284 against 19.3 ms). The plain version's rate does something unexpected: about 400 to 500 GFLOP/s at 256 and 512, then 116 at 1,024 and about 120 beyond. I repeated the run twice and the pattern held (naive 17.4 and 18.0 ms at 1,024). Between 512 and 1,024 the score matrix grows from 8 to 32 MiB per call, and a likely reason is that it no longer fits in the CPU's cache, so the plain version waits on memory while the fused one, which never builds the matrix, does not; I did not test that. At the long end the plain time grows by about 4 per doubling (76.2 ms, then 284 ms), as the FLOP count does. Both implementations are counted with the same nominal FLOPs (4BHT2dk), so a higher GFLOP/s is a faster program, not extra arithmetic; because the fused call is causal and can skip the masked half, its real arithmetic is smaller still, which flatters it slightly.
  • Short sequences gain little. At T = 256 and 512 the fused kernel is about 2 times faster: the matrices are small enough that both programs mostly pay fixed per-call costs. The gap opens as T grows, which is the chapter's point.

Your timings will differ from these (they depend on the chip and on what else it is doing: the first time I ran this on the busy VM, the same script printed 50 ms for T = 256); the orderings and the memory ratios should not.

Part 2: CUDA backends and sequences that do not fit

On the GPU box (wb up, wb sync, wb ssh), the script switches to 16-bit floats and adds a block that runs the fused call under each CUDA backend. Use 32 heads of width 128, a typical 7B-class shape:

$ cd /workspace/zts/deep-learning/workbench/code/w04
$ python attn_kernels.py --lengths 1024 4096 8192 16384 --heads 32 --dim 128

Not run here

This page was written on the lab VM, which has no NVIDIA GPU, so the CUDA block, the backends and the out-of-memory point have no printed output. The lab VM run above proves the script runs end to end; the numbers below are computed from the same formulas, with 2-byte floats and 32 heads of width 128.

The prediction. One T × T matrix for 32 heads in 16-bit is 32 × T2 × 2 bytes: 64 MiB at 1,024, 1,024 MiB at 4,096, 4,096 MiB at 8,192 and 16,384 MiB (16 GiB) at 16,384. The naive peak is twice that: 8 GiB at 8,192 and 32 GiB at 16,384, which is more than any 24 GB card has, so the plain version should fail with an out-of-memory error there, and the largest length it can reach on an empty 24 GB card is about √(22 GiB / (2 × 32 × 2 bytes)) ≈ 13,600 tokens (taking 22 GiB as usable). The fused flash and memory-efficient kernels hold the output, 32 × T × 128 × 2 bytes: 32 MiB at 4,096 and 128 MiB at 16,384, about 0.4% of the naive requirement. The math backend is the plain algorithm inside PyTorch, so it should need about the same as the naive code (its memory is the same kind of thing).

The arithmetic is 4 × 32 × T2 × 128 FLOPs: 275 GFLOP at 4,096 and 4.4 TFLOP at 16,384 (half of each if the kernel skips the masked half, as the causal flash kernel does). Dividing by your card's dense 16-bit peak from its datasheet and a utilisation gives a time. Chapter 19 cites 50% to 73% of an A100's peak for FlashAttention-2, so for a card with a 312 TFLOP/s peak, 50% means 156 TFLOP/s and the causal 16,384-token call should take about 2.2 TFLOP / 156 TFLOP/s ≈ 14 ms. That is an example of the method with the A100 figure the chapter quotes; substitute your own card's peak and a utilisation you can defend, and treat the result as an upper bound on speed.

For the time, expect the flash backend to beat the memory-efficient one, and both to beat the plain code by a factor that grows with T; the size of that factor on your card is the measurement, not something this page can predict.

Break it

  • Fewer heads, longer sequence. Run --heads 1 --lengths 8192 16384 on the VM. Predict the naive peak (one head: T2 × 4 × 2 bytes) and whether the VM has the memory. Which length first makes the plain version slow down sharply?
  • Remove the causal mask. Change is_causal=True to False and delete the masking line in naive. Predict what happens to the fused time (the kernel can no longer skip the masked half) and to the memory (it should not move).
  • Double the head width. Use --dim 128 with the same T. Which of the three predictions change (memory of S, memory of the output, FLOPs)? The T × T matrix does not depend on dk.
  • Decode, not prefill. A single new query against a cache of T keys makes S a 1 × T row, so the matrix is no longer the problem. Predict which of the two programs wins at T = 4,096 with one query token, then edit make to give q a length of 1 and find out. (Chapter 19: decode is limited by reading the cache, not by the score matrix.)

Key takeaways

  • The plain implementation's peak memory is two T × T matrices per head, measured to within 2% to 14% of the prediction. The fused kernel's is the size of its output.
  • The two give the same numbers to rounding: FlashAttention changes the order of work, not the result.
  • The time advantage opens up with length, 2 times at 256 tokens and 14.7 times at 4,096 on the VM's CPU, while the FLOP count is identical.
  • A memory formula tells you where a program stops working before you run it: a 24 GB card cannot hold the plain version at 16,384 tokens of 32 heads, and the fused one barely notices.

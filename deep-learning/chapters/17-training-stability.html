Mixed Precision & Training Stability

Large models are trained in 16-bit arithmetic because it is faster and half the size, and they are trained for weeks, so small numerical problems have time to become large ones. This chapter explains what the 16-bit formats lose, what must stay in 32 bits, why loss suddenly spikes, and the four habits (warmup, clipping, careful optimiser settings and the right logs) that keep a long run alive.

Why this matters

Chapter 16 priced a training run in FLOPs and bytes. A run that fits and is affordable can still fail in a way no arithmetic predicts: the loss climbs for no visible reason on day nine, or turns into NaN (the floating-point value "not a number", which poisons everything it touches) and the last good checkpoint is six hours old. The public logbooks of large runs, which this chapter draws on, read mostly as lists of such events and the decisions made about them. After this chapter you will know why bf16 is the default format, which parts of a step must stay in fp32, how Adam turns one bad batch into an oversized step, what clipping and warmup do about it, and which curves to put on the dashboard so that you notice trouble before the loss does. Chapter 18 then asks what size of model and dataset to run in the first place, and the studio at the end of Part 5 gives you a broken run to diagnose.

Why not simply use 32-bit numbers?

Everything in chapters 01 to 15 ran in 32-bit floating point (fp32, "single precision", 4 bytes per number), or in NumPy's 64-bit default. That is safe and slow. A modern GPU's matrix-multiplication units (tensor cores) run 16-bit inputs several times faster than 32-bit ones, and 16-bit numbers occupy half the memory and move through the memory system twice as fast. Because training is dominated by large matrix products (chapter 16), switching them to 16 bits changes the cost of a run by a large factor. The question is what such a switch does to the numbers. For a refresher on how floats work, see A0 chapter 11; the essentials follow.

Three formats and what each gives up

A floating-point number is stored as a sign, an exponent and a mantissa (also called the significand). The exponent sets the range: how large or small a number can be. The mantissa sets the precision: how many significant digits it has, and so how close together representable numbers are. Three formats matter for training.

  • fp32: 8 exponent bits, 23 mantissa bits. Range up to 3.4 × 1038; about seven significant decimal digits.
  • fp16 (IEEE half precision): 5 exponent bits, 10 mantissa bits. More precise than bf16, but its range ends at 65,504 and its smallest normal number is about 6 × 10-5 (smaller values survive as "subnormal" numbers down to about 6 × 10-8, with less and less precision).
  • bf16 ("brain floating point", introduced by Google Brain): the top 16 bits of an fp32 number. The same 8 exponent bits as fp32, hence the same range, but only 7 mantissa bits, about two to three significant decimal digits.

The script below prints the limits and then converts a few values through each format. bf16 is not built into NumPy, so the function to_bf16 emulates it by rounding an fp32 number to its top 16 bits (round to nearest, ties to even), which is exactly what the hardware does.

# Three floating-point formats: range and precision. bf16 is emulated by rounding float32 to its top 16 bits.
import numpy as np

def to_bf16(x):
    """Round float32 values to the nearest bfloat16 (ties to even) and return them as float32."""
    u = np.asarray(x, dtype=np.float32).view(np.uint32).astype(np.uint64)
    u = (u + 0x7FFF + ((u >> 16) & 1)) & 0xFFFF0000
    return u.astype(np.uint32).view(np.float32)

def to_fp16(x):
    with np.errstate(over="ignore"):
        return np.asarray(x, dtype=np.float32).astype(np.float16).astype(np.float32)

The second table shows the bargain. The integer 257 survives in fp16 but rounds to 256 in bf16, because 7 mantissa bits cannot tell 256 from 257. Adding 2-9 to 1 is visible in fp16 and lost in bf16. Neural-network values are noisy and tolerate low precision well; they do not tolerate silently becoming zero or infinity. That is the reason bf16 won.

fp16 needs loss scaling; bf16 does not

Gradients are often tiny. In a deep network the gradient of the loss with respect to an early weight can be 10-8 or smaller, below the smallest fp16 number. If the backward pass runs in fp16, those gradients become exactly zero and the corresponding weights stop learning. Micikevicius et al. (2017, "Mixed Precision Training") fixed this with loss scaling: multiply the loss by a constant S (say 1,024) before the backward pass. By the chain rule every gradient is then multiplied by S, which lifts small values into fp16's range. Before the optimiser update the gradients are divided by S in fp32, so the learning step is unchanged.

The constant has to be chosen well. Too small and gradients still underflow; too large and the largest gradients overflow to infinity. Practical systems use dynamic loss scaling: start high, and if any gradient contains an infinity or NaN, skip that optimiser step and halve the scale; after a run of clean steps, double it again. The scale hovers just below the largest value that does not overflow. The script applies a plain fp16 conversion to a synthetic gradient distribution (log-normal magnitudes with a median of 3 × 10-8, chosen to be small; real distributions differ) and then runs the dynamic-scaling rule on a toy sequence.

# fp16 gradients underflow; scaling the loss moves them into range. Gradients here are synthetic (log-normal magnitudes).
import numpy as np
from formats import to_fp16

rng = np.random.default_rng(0)
grads = np.exp(rng.normal(np.log(3e-8), 2.0, 100_000)) * rng.choice([-1, 1], 100_000)   # median 3e-8, wide spread
print(f"gradient magnitudes: median {np.median(abs(grads)):.1e}, 1st pct {np.percentile(abs(grads), 1):.1e}, 99th pct {np.percentile(abs(grads), 99):.1e}")
print(f"{'loss scale':>10} {'flushed to zero':>16} {'overflowed to inf':>18}")
for scale in (1, 2**10, 2**15, 2**20):
    h = to_fp16(grads * scale)
    print(f"{scale:>10} {np.mean(h == 0):>15.1%} {np.mean(np.isinf(h)):>17.2%}")

scale, clean, true_max = 2.0**14, 0, 0.4            # largest true gradient entry 0.4, so the scale must stay below 65504/0.4 = 163,760

Half of these synthetic gradients vanish without scaling and none do with a scale of 1,024. In the dynamic part, the scale doubles every four clean steps (a real system waits on the order of two thousand), reaches a value at which the largest gradient no longer fits, loses a step to an overflow, and halves. Loss scaling is not free: the check for infinities adds work, and skipped steps are skipped learning. It also leaves a trace in the logs, as the OPT-175B team found (below).

bf16 sidesteps all of this. Its range matches fp32's, so gradients that fp32 can hold, bf16 can hold, and no scaling is needed. Kalamkar et al. (2019, "A Study of BFLOAT16 for Deep Learning Training") showed that bf16 training with no changes to hyperparameters matched fp32 across many models. The price is precision, and that is where the next section goes.

What must stay in 32 bits

"Mixed precision" means exactly that: not everything is in 16 bits. The rule of thumb is to use 16 bits for bulky tensors that are only multiplied and summed, and fp32 for quantities that accumulate small contributions over time.

The most important example is the master weights. A typical optimiser update is a tiny fraction of the weight: with a learning rate of 3 × 10-4 a weight of size about 1 changes by roughly 10-4 per step. In bf16, representable numbers near 1.0 are 2-7 = 0.0078 apart, so adding 10-4 to 1.0 and rounding gives 1.0 again: the update disappears. Even fp16, with a spacing of 0.00098 near 1.0, rounds it away. The script accumulates 8,192 updates of 2-13 (about 1.2 × 10-4) onto a weight of 1.0 in each format, rounding after each addition.

# Why the optimiser keeps fp32 master weights: small updates vanish when added to a 16-bit weight.
import numpy as np
from formats import to_bf16, to_fp16

lr_times_grad = np.float32(2.0**-13)              # one typical update, about 1.2e-4 of a weight of size 1 (exact in binary)
w32, w16, wbf = np.float32(1.0), np.float32(1.0), np.float32(1.0)
for step in range(8192):
    w32 = w32 + lr_times_grad                     # fp32 master weight accumulates every update
    w16 = to_fp16(w16 + lr_times_grad)            # weight stored in fp16: rounded after each update
    wbf = to_bf16(wbf + lr_times_grad)            # weight stored in bf16: rounded after each update
print(f"after 8,192 updates of +2^-13 (exact answer 2.0):")
print(f"  fp32 weight: {float(w32):.4f}\n  fp16 weight: {float(w16):.4f}\n  bf16 weight: {float(wbf):.4f}")
print(f"spacing of representable numbers near 1.0: fp16 {2.0**-10:.5f}, bf16 {2.0**-7:.5f}, update {float(lr_times_grad):.5f}")

The fp32 weight reaches the exact answer, 2.0. The 16-bit weights never move: the learning rate was small enough that every single step was a rounding error that rounded to nothing. This is why the optimiser holds a separate fp32 copy of every weight (the 4-byte "master" entry of chapter 16's 16 bytes per parameter), updates that, and then casts a bf16 copy for the forward and backward passes. It is also why training in "pure" bf16 can quietly stall at small learning rates late in a run, when updates are smallest. (Stochastic rounding, which rounds up or down at random in proportion to the remainder, is one way to avoid the loss; it is used in some systems, and the master copy remains the standard.)

The other fp32 items follow the same logic. The softmax and the cross-entropy loss involve exponentials and sums over a large vocabulary, where range and accumulation errors matter (A0 chapter 11 showed why a softmax needs the max subtracted). Normalisation layers compute means and variances, which are sums over many elements. And inside a matrix multiplication the hardware multiplies 16-bit inputs but accumulates the sums in fp32, so errors do not pile up across the thousands of terms in a dot product. Frameworks apply these rules automatically in their mixed-precision modes (PyTorch's autocast chooses the dtype per operation, and the optimiser keeps fp32 state); you rarely write them by hand, but you should know them to read a stack trace or a precision bug.

State of play, October 2026

bf16 with fp32 master weights and optimiser state is the common baseline for pre-training, and the Llama 3 report quotes the MFU of its 405B run against the BF16 peak. The frontier of the field is lower precision. The DeepSeek-V3 technical report (December 2024) describes training a large mixture-of-experts model with 8-bit floating-point (FP8) matrix products, with fine-grained scaling factors and higher-precision accumulation, and reports a relative loss error below 0.25% against a bf16 baseline; the same report stores Adam's two moments in bf16 rather than fp32, while keeping master weights and accumulated gradients in fp32. Other labs and library vendors have since added FP8 and narrower 4-bit options, but I have not verified the details or the benefits at frontier scale, so treat claims about 4-bit pre-training as evidence still being gathered. What is stable is the pattern: narrower formats for the bulky multiplications, wider ones for accumulation, and a scaling scheme to keep values in range.

Loss spikes: what they are and why they happen

A loss spike is a sudden, large rise in training loss, often followed by a partial or complete recovery over hundreds or thousands of steps; sometimes the run never recovers (a divergence). Spikes are not rare at scale. The PaLM authors (Chowdhery et al., 2022) report that the 540B model spiked about 20 times during training, "despite the fact that gradient clipping was enabled", at irregular intervals, and that they could not find a principled fix. Their remedy was operational: restart from a checkpoint roughly 100 steps before the spike and skip about 200 to 500 batches of data. Re-running the same batches from an earlier checkpoint did not reproduce the spike, which led them to conclude that spikes arise from a specific combination of a batch and a particular parameter state, not from "bad data" alone. The OPT-175B team (Zhang et al., 2022) saw loss divergences too, and found that lowering the learning rate and restarting from an earlier checkpoint let the run continue; they also observed that divergences correlated with their dynamic loss scale collapsing towards zero and the norm of the final-layer activations spiking. The Llama 3 team, by contrast, reported that their 405B run was "very stable", with few loss spikes and no interventions needed to correct divergence, and the DeepSeek-V3 report says its run had no irrecoverable loss spikes and no rollbacks. Stability is a property of the recipe, and it can be engineered.

Known mechanisms, from the literature and the logbooks, are these.

  • An update that is too large. The learning rate is too high for the current state of the model: the step overshoots and the loss rises. This is the main reason for warmup, covered below.
  • Adam turns one outlier into a big step. The next section shows this in numbers.
  • Attention logits that grow without bound. The pre-softmax scores QKT/√dk can grow during training until the softmax becomes nearly one-hot and its gradients vanish or explode. Wortsman et al. (2023, "Small-scale proxies for large-scale Transformer training instabilities") reproduced this instability in small models at high learning rates, and showed that QK-normalisation (applying a LayerNorm to queries and keys before the dot product, proposed for ViT-22B by Dehghani et al., 2023) removes it.
  • Output logits that drift. The final logits can move away from log-probabilities so that the softmax normaliser grows. PaLM added an auxiliary z-loss, 10-4 × (log Z)2 with Z the softmax denominator, to keep it close to 1, and Wortsman et al. showed that it is an effective mitigation at small scale as well.
  • Numerical range problems. In fp16, overflow in an activation produces infinities. In any format, an extreme activation can push a normalisation or softmax outside its comfortable range. These are the cases mixed-precision recipes are designed to avoid.
  • Data. A corrupted or extreme batch can trigger an event the model is fragile to, even if the batch is harmless after a restart, as PaLM's experiment suggests.

How Adam amplifies a bad batch

Chapter 03 and A0 chapter 10 introduced Adam: it keeps a running average of the gradient (m, with decay β1 = 0.9) and of the squared gradient (v, with decay β2), and steps by m/√v. Normally the gradient is of similar size from step to step, so m/√v is of order one per weight whatever the raw gradient scale. When one batch produces a gradient 100 times larger than usual, the average m jumps by 10% of it at once, while v, which averages squares over about 1/(1 − β2) = 1,000 steps, rises slowly: the numerator has reacted and the denominator has not, so the step is large. The script feeds 3,000 steps of noise-like gradients of norm 0.3 into AdamW's update rule, then one gradient of norm 30, and measures the update.

# What one bad batch does to AdamW, with and without gradient clipping. Gradients are synthetic: noise with norm about 0.3,
# then a single batch whose gradient has norm 30 (100 times larger) at step 3000.
import numpy as np

def run(beta2, clip, spike_norm=30.0, d=2000, seed=0):
    rng = np.random.default_rng(seed)
    m = np.zeros(d); v = np.zeros(d); ups = []
    for t in range(1, 3031):
        g = rng.normal(size=d); g *= (spike_norm if t == 3000 else 0.3) / np.linalg.norm(g)
        if clip and np.linalg.norm(g) > clip: g *= clip / np.linalg.norm(g)
        m = 0.9 * m + 0.1 * g; v = beta2 * v + (1 - beta2) * g * g
        u = (m / (1 - 0.9 ** t)) / (np.sqrt(v / (1 - beta2 ** t)) + 1e-8)
        ups.append(np.sqrt((u * u).mean()))          # RMS of the update per coordinate, in units of the learning rate
    ups = np.array(ups); typical = np.median(ups[2000:2999])
    return typical, ups[2999] / typical, ups[3000:3030].mean() / typical

With β2 = 0.999 and no clipping, the one bad batch produces an update 11 times the typical size, and the following 30 steps still average 3.3 times typical, because m remembers the outlier for about ten steps and the inflated v then shrinks later updates for a thousand. With clipping at a gradient norm of 1.0 the spike step is 1.7 times typical: still larger than normal, but bounded. Lowering β2 to 0.95 makes v respond within about 20 steps and shrinks the effect on its own, which is one reason several recent large-model recipes (the DeepSeek-V3 report lists β2 = 0.95, and the original LLaMA recipe used the same value) choose it over the default 0.999. These are measurements on a synthetic gradient stream, not on a Transformer, but the algebra is the same one that real runs face.

Gradient clipping

The gradient norm is the length of the whole gradient vector, ||g|| = √(∑ gi²), taken over all parameters at once. Gradient clipping (Pascanu et al., 2013) rescales the gradient when this norm exceeds a threshold c: if ||g|| > c, replace g by g · c/||g||. The direction is kept and the length is capped. The standard setting for Transformer pre-training is c = 1.0 (PaLM and DeepSeek-V3 both state it). OPT lowered it to 0.3 early in training when they saw instability.

Analogy: a speed limiter

A governor on a lorry caps its speed however hard the driver presses the pedal. Gradient clipping does the same to the optimiser's step: on a steep, jagged stretch of the loss landscape, where the raw gradient says "move far", the clip says "move at most this far, in the same direction". On ordinary stretches the governor never engages.

Where it breaks down: a governor is a safety device on the vehicle, whereas the clip is applied to the gradient and interacts with Adam's running averages, which are updated with the clipped values; it does not undo damage already stored in m and v, and it cannot repair a model that is already in a bad region. It also hides information: if you clip every step, the threshold has become your learning-rate schedule.

Common misconception

"Gradient clipping prevents loss spikes." It limits one cause, an oversized gradient, but PaLM's 540B model spiked about twenty times with clipping on, and a clip that engages on every step is a symptom (a learning rate too high or a bad initialisation), not a cure. Use the fraction of steps that are clipped as a diagnostic: in a healthy run it is near zero, with occasional clipped steps during spikes. The cure for a persistent problem is usually a lower learning rate, a better-conditioned architecture (QK-norm, pre-normalisation, chapter 03) or a data fix.

Learning-rate warmup

Warmup starts the learning rate near zero and raises it linearly to its peak over the first few hundred to few thousand steps, then follows a decay schedule (usually cosine; see A0 chapter 10). The Llama 3 405B run warms up for 8,000 steps to a peak of 8 × 10-5, and the scaling-law experiments of the same report used 2,000 warmup steps; DeepSeek-V3 warms up over the first 2,000 steps to 2.2 × 10-4.

Why does it help? At step one the weights are random and the loss landscape around them is at its roughest: the loss is large and the gradients are large and erratic (the step-0 gradient norm below is about 60). Adam's second-moment estimate has seen one or two gradients, so it is a poor guide to the right step size (Liu et al., 2020, "On the Variance of the Adaptive Learning Rate and Beyond", analyse this and propose a corrected optimiser). Taking a full-size step in that state can throw the weights into a region from which recovery is slow or impossible. Pre-norm Transformers (chapter 03; Xiong et al., 2020) need less warmup than post-norm ones but are still run with it at scale. The script trains the same eight-layer ReLU network on a small regression task three times at each peak learning rate: once with no warmup and once with 100 steps of linear warmup.

# Does warmup matter? Train the same deep MLP with Adam, with and without a linear learning-rate warmup.
import numpy as np

def train(peak_lr, warmup, steps=400, depth=8, width=64, seed=0, clip=None):
    rng = np.random.default_rng(seed)
    X = rng.normal(size=(512, 16)); w_true = rng.normal(size=(16, 1)); y = np.tanh(X @ w_true) + 0.05 * rng.normal(size=(512, 1))
    dims = [16] + [width] * depth + [1]
    Ws = [rng.normal(0, np.sqrt(2 / a), (a, b)) for a, b in zip(dims[:-1], dims[1:])]   # He initialisation
    m = [np.zeros_like(w) for w in Ws]; v = [np.zeros_like(w) for w in Ws]
    losses, gnorms = [], []
    for t in range(1, steps + 1):
        lr = peak_lr * min(1.0, t / warmup) if warmup else peak_lr
        hs = [X]
        for i, W in enumerate(Ws):
            z = hs[-1] @ W; hs.append(np.maximum(z, 0) if i < len(Ws) - 1 else z)
        err = hs[-1] - y; loss = float((err ** 2).mean()); losses.append(loss)
        if not np.isfinite(loss) or loss > 1e12: losses += [float("inf")] * (steps - t); gnorms += [float("nan")] * (steps - t + 1); break
        g = 2 * err / len(X); grads = [None] * len(Ws)
        for i in reversed(range(len(Ws))):
            grads[i] = hs[i].T @ g
            if i: g = (g @ Ws[i].T) * (hs[i] > 0)
        gn = float(np.sqrt(sum((q ** 2).sum() for q in grads))); gnorms.append(gn)
        if clip and gn > clip: grads = [q * clip / gn for q in grads]
        for i in range(len(Ws)):
            m[i] = 0.9 * m[i] + 0.1 * grads[i]; v[i] = 0.999 * v[i] + 0.001 * grads[i] ** 2
            Ws[i] -= lr * (m[i] / (1 - 0.9 ** t)) / (np.sqrt(v[i] / (1 - 0.999 ** t)) + 1e-8)
    return losses, gnorms

if __name__ == "__main__":

In this small problem both recover and end at about the same loss, so warmup bought safety, not accuracy. At the largest rate, 0.1, neither version survives: both end at 0.821, the variance of the targets, which is the loss of a network that has died and predicts a constant. Warmup widens the range of learning rates that work; it does not make every rate work. The plot shows the first 60 steps for the middle row.

What to log, and what the curves mean

Chapter 16's accounting predicts how the run should behave; the logs tell you whether it does. A training dashboard for a long run should plot, at every step or every few steps:

The OPT-175B team published their daily logbook as a primary record of this kind of operating work; case study 7 reads it.

A runbook for a spike

  1. Look before you act. Is the gradient norm elevated? Did the loss scale (if any) collapse? Did anything else change at that step: a new data shard, a resumed checkpoint, a node swap, a learning-rate phase?
  2. Let it ride, briefly. Some spikes recover on their own, and the dashboard will show whether the loss is returning to its earlier trend. Decide a threshold in advance (for example, "not back to the previous trend after N steps") so the decision does not depend on how anxious you feel.
  3. If it does not recover, roll back. Restart from the last checkpoint before the spike. PaLM went back about 100 steps and skipped 200 to 500 batches; OPT lowered the learning rate on restart. Keep checkpoints frequent enough for this (A3 chapter 05).
  4. Fix the cause, if you can find one. Lower the peak learning rate, add warmup, lower β2 towards 0.95, tighten the clip, add QK-normalisation or a z-loss, remove a bad shard. Change one thing at a time and write it down.
  5. Write it up. Record the step, the signals, the action and the outcome. The next engineer, or you in a month, will need it.

Systems connection

A long training run is a production service with a very expensive failure mode, and the same reliability ideas apply. The dashboard above is the metrics layer (metrics, structured events); the runbook is an incident procedure; checkpoints are the recovery point objective; and the decision to roll back is the same trade as rolling back a deployment, made with the same discipline of deciding the threshold before the incident. Silent numerical errors are the training analogue of partial failures: nothing crashes, the output is merely wrong, and the monitoring has to be designed to notice.

In PyTorch the whole recipe is a few lines. This listing is not run here; with bf16 autocast it needs no loss scaler, and the comments say what each line corresponds to above.

for step, (x, y) in enumerate(loader):
    lr = schedule(step)                               # linear warmup, then cosine decay
    for group in optimizer.param_groups:
        group["lr"] = lr
    with torch.autocast("cuda", dtype=torch.bfloat16):  # bf16 matmuls, fp32 where needed
        loss = model(x, y)
    loss.backward()                                   # parameters (and so gradients) are fp32 here
    gnorm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)  # returns the norm BEFORE clipping
    if not torch.isfinite(gnorm):                     # NaN or inf: skip the step and log it
        optimizer.zero_grad(set_to_none=True)
        continue
    optimizer.step()                                  # AdamW(betas=(0.9, 0.95), weight_decay=0.1)
    optimizer.zero_grad(set_to_none=True)
    log(step, loss.item(), gnorm.item(), lr, clipped=bool(gnorm > 1.0))

In this form the model's parameters stay in fp32 and autocast casts them to bf16 for each matrix product, which is the simplest way to get an fp32 master copy; larger systems that shard the model keep separate bf16 and fp32 copies, as chapter 16's byte count assumes. If you switched to fp16 you would add a GradScaler that implements the dynamic loss scaling shown earlier.

Key takeaways

  • 16-bit matrix products are several times faster and half the size. fp16 has more precision but a narrow range (largest value 65,504) and needs loss scaling; bf16 has fp32's range with 7 mantissa bits and needs none, which is why it is the default.
  • Keep in fp32: the master weights, the optimiser moments, the loss and softmax, normalisation statistics and the sums inside matrix products. A bf16 weight cannot accumulate small updates (spacing 0.0078 near 1.0).
  • Loss spikes are normal at scale: PaLM 540B saw about 20 with clipping on. The usual remedy is to roll back to a checkpoint before the spike, skipping the batches around it, often with a lower learning rate.
  • Adam turns one extreme gradient into a large step because m reacts at once while v, averaged over about 1,000 steps, does not. Clipping the gradient norm (c = 1.0 is standard) and a lower β2 (0.95) both limit this.
  • Warmup raises the learning rate over the first thousands of steps because the start is the roughest stretch of the landscape. It widens the range of working learning rates; it does not make every rate work.
  • Log the gradient norm (before clipping), the fraction of clipped steps, the loss scale, activation and logit maxima, throughput and the data position. Alert against a running baseline, and keep enough information to replay the run.

Check your understanding

A colleague moves a training run from bf16 to fp16 for higher precision and the loss becomes NaN within a few hundred steps, with the gradient norm reported as inf. Which is the most likely explanation?

  1. fp16 has fewer mantissa bits than bf16, so rounding errors cancel out
  2. fp16 cannot represent the learning rate
  3. fp16's range ends at 65,504, so an activation or scaled gradient overflowed to infinity, and without dynamic loss scaling or clipping the infinity spread
  4. fp16 is not supported by tensor cores
fp16 has more mantissa bits (10) than bf16 (7), so the first option is backwards; what fp16 lacks is range. Overflow to infinity and then NaN is its signature failure, and why fp16 recipes use loss scaling with skipped steps. fp16 can represent typical learning rates, and tensor cores support it.

You train a model with the weights themselves stored in bf16 and no fp32 copy. Late in the run the learning rate has decayed to 10-6 and the loss stops improving, although gradients are healthy. What is the best explanation?

  1. Updates of about 10-6 times the gradient are smaller than half the spacing between bf16 numbers near the weight, so they round away and the weights stop changing
  2. The model has reached the irreducible loss of the data
  3. bf16 gradients underflow to zero
  4. The warmup was too short
With 7 mantissa bits, the spacing near a weight of size 1 is about 0.008, so tiny updates are rounded to no change; an fp32 master copy accumulates them. bf16 has fp32's range, so gradients do not underflow (the third option describes fp16). The data floor is possible but not implied by healthy gradients, and warmup concerns the start of training.

In the Adam experiment, one gradient 100 times larger than usual produced an update about 11 times typical with β2 = 0.999 and no clipping. Why is the step so large when Adam is supposed to normalise by the gradient size?

  1. Adam divides by the gradient of the current step, so large gradients produce larger steps
  2. The learning rate is automatically increased after a large gradient
  3. Weight decay amplifies the outlier
  4. The first moment m jumps immediately to a tenth of the outlier, while the second moment v averages over about a thousand steps and has barely moved, so m/√v is far above normal
Adam's normalisation uses a long-run average of squared gradients, not the current gradient. The numerator reacts at once; the denominator lags. Adam does not divide by the current gradient, the learning rate has not changed, and weight decay is a separate small term unrelated to the outlier.

A dashboard shows that gradient clipping is active on 70% of steps in a run that has just passed warmup. What should you conclude?

  1. Clipping is working well, because it is engaging often
  2. The typical gradient norm is above the threshold, so the learning rate, initialisation or architecture likely needs attention, because the clip has become part of the optimiser rather than a safety net
  3. The threshold is too low and should be removed
  4. The loss scale has collapsed
A healthy run clips rarely; frequent clipping means the gradient is routinely larger than the design assumed and the clip is compensating for something else. Removing the clip would remove protection without removing the cause. The loss scale applies only to fp16 runs and is a separate signal.

The PaLM team replayed the batches around a loss spike from an earlier checkpoint and the spike did not recur. What did they conclude, and what remedy follows?

  1. The spike depended on the combination of those batches and the parameter state at that time; restarting from before the spike and skipping a few hundred batches avoids it
  2. The data were corrupted, so the shard should be deleted from the corpus
  3. The hardware was faulty, so the nodes should be replaced
  4. The learning rate was too low, so it should be raised
The replay from an earlier state did not spike, which rules out "bad data" as a complete explanation; it was the particular pairing of data and parameters. Hence the remedy of rolling back and skipping data. A hardware fault would not be fixed by changing the starting checkpoint, and raising the learning rate would make spikes more likely.

You plan to log a training run. Which set of signals is most useful for detecting an impending loss spike before the loss moves?

  1. Wall-clock time per step and GPU temperature
  2. Training loss averaged over 1,000 steps and the final evaluation score
  3. Pre-clip gradient norm, fraction of steps clipped, and the maxima of attention logits, output logits and activations
  4. The learning rate and the batch size
The gradient norm, the clip rate and the growth of logits and activations are leading indicators: instabilities build in them before the loss reacts, as in the OPT and Wortsman et al. observations. A heavily smoothed loss reacts late by construction. Learning rate and batch size are plan values you already know, and hardware metrics diagnose throughput problems, not numerical ones.

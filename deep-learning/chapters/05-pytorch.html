PyTorch as an Autodiff Engine

PyTorch looks like a large library, but underneath it is three small ideas: arrays that can live on a GPU, a graph that records every operation so gradients come for free, and a convention for bundling parameters into modules. This chapter builds all three in about 120 lines of NumPy so that nothing in the framework stays mysterious, then shows the PyTorch code that does the same job and the standard five-line training loop.

Why this matters

From chapter 08 onwards, and in every later course of this path, models are written in PyTorch-style code, and the bugs you will meet there are almost all about the framework's mechanics: a forgotten zero_grad(), a tensor on the wrong device, a graph kept alive by accident, dropout left on during evaluation. If you know what the engine is doing, these stop being superstitions. In A0 chapter 9 you built a scalar autograd engine by hand; here you scale that idea to arrays and wrap it in the API that practitioners actually use. By the end you can read any training script, predict what each line does to memory and gradients, and write the standard loop from memory.

What was run, and what was not

PyTorch is not installed on the machine that built this course. So the runnable examples use a small NumPy engine written for this chapter (tinytorch.py, shown in full), which mirrors PyTorch's behaviour line for line: requires_grad, .grad, backward(), accumulation, no_grad, modules, optimisers. Every number printed below comes from running that engine. The PyTorch listings are labelled "PyTorch, not run here" and have no output block; where the result is determined by arithmetic shown elsewhere, the text says what it prints. Run them on your own machine as the exercise at the end.

What a framework gives you

Writing a neural network with only NumPy works, as chapter 02 showed, but it costs you three things that a deep-learning framework provides:

  1. Tensors on accelerators. NumPy arrays live in CPU memory. Training at scale needs the same array operations running on a GPU, whose thousands of simple cores do large matrix multiplications far faster than a CPU.
  2. Automatic differentiation. You write only the forward pass. The framework derives the backward pass, so changing the architecture does not mean redoing calculus by hand.
  3. A library of building blocks. Layers, losses, optimisers, data loaders and checkpoint formats, with a convention for how they fit together.

PyTorch (Paszke et al., 2019, "PyTorch: An Imperative Style, High-Performance Deep Learning Library") became the dominant research framework largely through one design decision: it is imperative. You write ordinary Python, and the graph is recorded as the code runs. That makes debugging with a print or a breakpoint work the way you expect.

Tensors

A tensor is PyTorch's name for an n-dimensional array, the same object as a NumPy ndarray with three extra attributes. Its shape is the size along each dimension, written as in this course in parentheses, for example (B, T, C) for a batch of B sequences of T positions with C numbers each. Its dtype is the number format of its elements (float32, bfloat16, int64; see A0 chapter 11). Its device says where its memory lives: "cpu" or a GPU such as "cuda:0". Operations need all their inputs on the same device, and moving data between devices (x.to("cuda")) is a copy across a comparatively slow link, so it is something you do deliberately and rarely.

All the array habits from A0 chapter 2 carry over: broadcasting, matrix multiplication with @, reductions along an axis (called dim in PyTorch instead of axis). The script below uses NumPy to demonstrate the points that matter most, because PyTorch behaves identically on each.

Three things to take from that output. Views share memory. A transpose or a reshape of contiguous data does not copy; it changes how the same bytes are indexed (the strides). Writing through a view changes the original, which is efficient and occasionally a surprise; PyTorch's .view(), .T and slicing behave this way, while .clone() makes a real copy. Shapes are contracts. The (B, T, C) by (C, V) product gives (B, T, V): most PyTorch errors are shape errors, so write the shape in a comment beside every non-obvious line. The default float type differs: NumPy creates 64-bit floats, PyTorch 32-bit. Deep learning runs in 32 bits or fewer because memory and bandwidth are the bottleneck; if you move a NumPy array into PyTorch, check the dtype.

Autograd: recording the computation

When you run y = w * x + b with a tensor that has requires_grad=True, PyTorch does two things. It computes the value, and it records a node in a computation graph: the output y remembers which operation produced it (its grad_fn, shown as AddBackward0 in the printed tensor) and which tensors went in. Tensors you create yourself, such as parameters, are leaves of the graph. The graph is built while the forward code runs, which is called define-by-run: an if or a for in your Python simply produces a different graph on the next call, with no special syntax.

Calling loss.backward() then walks the graph from the loss back to the leaves. At each node it applies the chain rule, multiplying the gradient arriving from above by that operation's local derivative (chapter 02). The results are stored in each leaf's .grad attribute. This is reverse-mode automatic differentiation, and one backward pass gives the gradient of the loss with respect to every parameter at about the cost of one or two forward passes, which is why training networks with billions of parameters is feasible at all.

Building the engine

Here is the whole mechanism, written with NumPy arrays. A Tensor wraps an array, remembers its parents and a small function that maps the gradient on its output to gradients on its inputs, and backward() visits nodes in reverse topological order (every node after everything that depends on it). The only subtle helper is unbroadcast: if a (16,) bias was stretched across a (64, 16) batch in the forward pass, the gradient arriving from above has shape (64, 16) and must be summed back down to (16,). It is about 70 lines.

import numpy as np

_GRAD = True
class no_grad:                                  # like torch.no_grad(): ops record no graph inside
    def __enter__(self):
        global _GRAD; self.prev, _GRAD = _GRAD, False
    def __exit__(self, *a):
        global _GRAD; _GRAD = self.prev

def unbroadcast(g, shape):                      # undo NumPy broadcasting: sum over the stretched axes
    while g.ndim > len(shape): g = g.sum(0)
    for i, n in enumerate(shape):
        if n == 1 and g.shape[i] != 1: g = g.sum(i, keepdims=True)
    return g

class Tensor:
    def __init__(self, data, requires_grad=False, parents=(), backward=None, op=""):
        self.data = np.asarray(data, dtype=np.float64); self.grad = None
        self.requires_grad = requires_grad
        self.parents, self._backward, self.grad_fn = parents, backward, op or None

    @staticmethod
    def make(data, parents, backward, op):      # build an output node, recording the graph only if needed
        rg = _GRAD and any(p.requires_grad for p in parents)
        return Tensor(data, rg, parents if rg else (), backward if rg else None, op if rg else "")

    def __add__(s, o): o = as_t(o); return Tensor.make(s.data + o.data, (s, o), lambda g: (unbroadcast(g, s.data.shape), unbroadcast(g, o.data.shape)), "Add")
    def __mul__(s, o): o = as_t(o); return Tensor.make(s.data * o.data, (s, o), lambda g: (unbroadcast(g * o.data, s.data.shape), unbroadcast(g * s.data, o.data.shape)), "Mul")
    def __neg__(s): return s * -1.0
    def __sub__(s, o): return s + (-as_t(o))
    def __pow__(s, k): return Tensor.make(s.data ** k, (s,), lambda g: (g * k * s.data ** (k - 1),), "Pow")
    def __matmul__(s, o): return Tensor.make(s.data @ o.data, (s, o), lambda g: (g @ o.data.T, s.data.T @ g), "MatMul")
    @property
    def T(s): return Tensor.make(s.data.T, (s,), lambda g: (g.T,), "Transpose")
    def relu(s): return Tensor.make(np.maximum(s.data, 0), (s,), lambda g: (g * (s.data > 0),), "ReLU")
    def tanh(s): t = np.tanh(s.data); return Tensor.make(t, (s,), lambda g: (g * (1 - t * t),), "Tanh")
    def sum(s): return Tensor.make(s.data.sum(), (s,), lambda g: (np.full(s.data.shape, g),), "Sum")
    def mean(s): return Tensor.make(s.data.mean(), (s,), lambda g: (np.full(s.data.shape, g / s.data.size),), "Mean")
    __radd__, __rmul__ = __add__, __mul__
    def item(s): return float(s.data)

    def backward(s):
        order, seen = [], set()
        def visit(n):                           # depth-first topological sort of the graph
            if id(n) not in seen:
                seen.add(id(n)); [visit(p) for p in n.parents]; order.append(n)
        visit(s)
        grads = {id(s): np.ones_like(s.data)}
        for n in reversed(order):
            g = grads.get(id(n))
            if g is None: continue
            if n._backward is None:             # a leaf: accumulate into .grad, as PyTorch does
                if n.requires_grad: n.grad = g if n.grad is None else n.grad + g
                continue
            for p, pg in zip(n.parents, n._backward(g)):
                if p.requires_grad: grads[id(p)] = grads.get(id(p), 0) + pg

    def __repr__(s): return f"Tensor({np.round(s.data, 4).tolist()}" + (f", grad_fn=<{s.grad_fn}>)" if s.grad_fn else ")")

def as_t(x): return x if isinstance(x, Tensor) else Tensor(x)

def cross_entropy(logits, y):                   # fused log-softmax + negative log-likelihood, mean over the batch
    z = logits.data - logits.data.max(1, keepdims=True)
    p = np.exp(z) / np.exp(z).sum(1, keepdims=True); n = len(y)
    def back(g):
        d = p.copy(); d[np.arange(n), y] -= 1
        return (g * d / n,)
    return Tensor.make(-np.log(p[np.arange(n), y]).mean(), (logits,), back, "CrossEntropy")

Compare it with the scalar engine of A0 chapter 9. The ideas are identical; the differences are mechanical. Local derivatives work on whole arrays, gradients that were broadcast get summed back, and .grad is accumulated (n.grad + g) only on leaves. That last point mirrors PyTorch exactly: by default it does not keep gradients of intermediate tensors, and it frees the graph after backward() to save memory. Now exercise it on the example from the diagram:

from tinytorch import Tensor, no_grad

x = Tensor([2.0]); target = Tensor([10.0])
w = Tensor([3.0], requires_grad=True); b = Tensor([1.0], requires_grad=True)

y = w * x + b                    # forward pass: the graph is built as the code runs
loss = ((y - target) ** 2).mean()
print("y    :", y)
print("loss :", loss)

loss.backward()                  # reverse pass: fills .grad on the leaves
print("dloss/dw =", w.grad, " dloss/db =", b.grad, "  (by hand: 2(y-t)x = -12 and 2(y-t) = -6)")

# A second forward and backward WITHOUT clearing: gradients accumulate.
loss = ((w * x + b - target) ** 2).mean(); loss.backward()
print("after a 2nd backward, w.grad =", w.grad)

w.grad = b.grad = None           # what optimizer.zero_grad() does
loss = ((w * x + b - target) ** 2).mean(); loss.backward()
print("after clearing,       w.grad =", w.grad)

f = lambda wv: ((wv * 2.0 + 1.0 - 10.0) ** 2)      # finite-difference check on w
eps = 1e-6
print("numerical gradient   :", round((f(3.0 + eps) - f(3.0 - eps)) / (2 * eps), 4))

with no_grad():                  # inference: nothing is recorded, nothing can be differentiated
    z = w * x + b
print("inside no_grad:", z, " requires_grad =", z.requires_grad)
y    : Tensor([7.0], grad_fn=<Add>)
loss : Tensor(9.0, grad_fn=<Mean>)
dloss/dw = [-12.]  dloss/db = [-6.]   (by hand: 2(y-t)x = -12 and 2(y-t) = -6)
after a 2nd backward, w.grad = [-24.]
after clearing,       w.grad = [-12.]
numerical gradient   : -12.0
inside no_grad: Tensor([7.0])  requires_grad = False

The first gradient pair (-12 and -6) matches the hand arithmetic in the figure, and the finite-difference line (nudge w by 10-6 each way and watch the loss) agrees, which is the check you would use on any new operation. The second backward call produced -24: gradients add up in .grad until you clear them. Accumulation is deliberate, since it lets you sum gradients over several small batches before one update (a trick when a big batch will not fit in memory), but it means you must clear them every step. Finally, inside no_grad the result has no grad_fn and does not require gradients: no graph is recorded, which saves the memory that the graph would hold. Use it whenever you only want predictions.

The PyTorch version of this demonstration is the same code with a different import:

import torch

x = torch.tensor([2.0]); target = torch.tensor([10.0])
w = torch.tensor([3.0], requires_grad=True)
b = torch.tensor([1.0], requires_grad=True)

y = w * x + b                      # the graph is recorded as this line runs
loss = ((y - target) ** 2).mean()
print(y)                           # shows a grad_fn: the op that produced y
loss.backward()                    # fills .grad on the leaves w and b
print(w.grad, b.grad)

loss = ((w * x + b - target) ** 2).mean()
loss.backward()                    # no zeroing: gradients accumulate
print(w.grad)

with torch.no_grad():              # inference: no graph is recorded
    z = w * x + b
print(z.requires_grad)

It prints the value 7 with a grad_fn of AddBackward0, then w.grad and b.grad of -12 and -6 (the same arithmetic as above), then -24 after the unzeroed second backward, and finally False. One difference you would meet: in PyTorch a second backward() call on the same loss tensor raises an error because the graph was freed; here we rebuilt the loss for each call, as a training loop does.

Common misconception

"PyTorch differentiates your code numerically (by nudging inputs), or symbolically (by manipulating formulas)." Neither. It records the actual operations that ran and applies each operation's exact, hand-coded local derivative through the chain rule. The result is exact up to floating-point rounding, and costs a small multiple of the forward pass; nudging each of a million parameters would cost a million forward passes. The finite-difference check is how you verify a new operation's derivative, not how the framework works. The second thing people get wrong: backward() does not change any weights. It only fills .grad. The weights change in optimizer.step().

Modules and parameters

A network has dozens of tensors that need gradients, and you do not want to list them by hand. A module (torch.nn.Module) is an object that owns parameters (tensors to be learned) and possibly other modules, and defines a forward method. PyTorch intercepts attribute assignment, so writing self.fc1 = nn.Linear(...) inside __init__ registers fc1's weights automatically. Then model.parameters() yields every learnable tensor in the tree, which is what you hand to the optimiser. Our nn.py does the same by walking the object's attributes:

import numpy as np
from tinytorch import Tensor

class Module:
    def named_parameters(self, prefix=""):      # walk attributes: Tensors that require grad, and sub-modules
        for k, v in vars(self).items():
            if isinstance(v, Tensor) and v.requires_grad: yield prefix + k, v
            elif isinstance(v, Module): yield from v.named_parameters(prefix + k + ".")
            elif isinstance(v, list):
                for i, m in enumerate(v): yield from m.named_parameters(f"{prefix}{k}.{i}.")
    def parameters(self): return [p for _, p in self.named_parameters()]
    def __call__(self, *a): return self.forward(*a)

class Linear(Module):
    def __init__(self, n_in, n_out, rng):
        bound = 1 / np.sqrt(n_in)               # the same range PyTorch's default Linear init uses
        self.weight = Tensor(rng.uniform(-bound, bound, (n_out, n_in)), requires_grad=True)
        self.bias = Tensor(rng.uniform(-bound, bound, n_out), requires_grad=True)
    def forward(self, x): return x @ self.weight.T + self.bias

class ReLU(Module):
    def forward(self, x): return x.relu()

class Sequential(Module):
    def __init__(self, *layers): self.layers = list(layers)
    def forward(self, x):
        for m in self.layers: x = m(x)
        return x

class SGD:
    def __init__(self, params, lr): self.params, self.lr = params, lr
    def zero_grad(self):
        for p in self.params: p.grad = None
    def step(self):
        for p in self.params:
            if p.grad is not None: p.data -= self.lr * p.grad

class Adam:
    def __init__(self, params, lr=1e-3, betas=(0.9, 0.999), eps=1e-8):
        self.params, self.lr, self.b, self.eps, self.t = params, lr, betas, eps, 0
        self.m = [np.zeros_like(p.data) for p in params]; self.v = [np.zeros_like(p.data) for p in params]
    def zero_grad(self):
        for p in self.params: p.grad = None
    def step(self):
        self.t += 1
        for p, m, v in zip(self.params, self.m, self.v):
            if p.grad is None: continue
            m[...] = self.b[0] * m + (1 - self.b[0]) * p.grad; v[...] = self.b[1] * v + (1 - self.b[1]) * p.grad ** 2
            p.data -= self.lr * (m / (1 - self.b[0] ** self.t)) / (np.sqrt(v / (1 - self.b[1] ** self.t)) + self.eps)

Notice that Linear stores its weight as (out, in) and computes x @ weight.T, as PyTorch does, and draws initial values uniformly within ±1/√(inputs) (the range nn.Linear uses by default; chapter 03 explains why scale matters). Build a small model and list what the module system sees:

The dotted names (layers.0.weight) are the paths through the module tree, and they are exactly the keys in a PyTorch state_dict, the plain dictionary from name to tensor that you save when you checkpoint a model. Here is the PyTorch module version, including saving and loading:

import torch
from torch import nn

class MLP(nn.Module):
    def __init__(self, d_in, d_hidden, n_classes):
        super().__init__()                       # sets up the registries that __setattr__ fills
        self.fc1 = nn.Linear(d_in, d_hidden)     # assigning a sub-module registers its parameters
        self.fc2 = nn.Linear(d_hidden, n_classes)

    def forward(self, x):                        # x: (B, d_in) -> (B, n_classes)
        return self.fc2(torch.relu(self.fc1(x)))

model = MLP(2, 16, 2)
for name, p in model.named_parameters():
    print(name, tuple(p.shape))

torch.save(model.state_dict(), "model.pt")                    # weights only, as a name -> tensor dict
model.load_state_dict(torch.load("model.pt"))                 # restores them into a model of the same shape

It prints fc1.weight (16, 2), fc1.bias (16,), fc2.weight (2, 16) and fc2.bias (2,). Saving the state_dict rather than pickling the whole model keeps checkpoints independent of your code layout, and is the form every model hub uses. Also note that modules have two modes: model.train() and model.eval(). They change the behaviour of layers such as dropout (chapter 04) and batch normalisation; they do not turn gradient recording on or off. For that you use torch.no_grad(), and for pure inference you normally use both.

Before moving on, make sure the derivatives in the engine can be trusted. The check below compares autograd's gradient of a small network's loss with a finite-difference estimate for every single parameter:

import numpy as np
from tinytorch import Tensor, cross_entropy
from nn import Linear, ReLU, Sequential

rng = np.random.default_rng(1)
model = Sequential(Linear(2, 8, rng), ReLU(), Linear(8, 3, rng))
X = Tensor(rng.standard_normal((5, 2))); y = rng.integers(0, 3, 5)

loss = cross_entropy(model(X), y); loss.backward()          # analytic gradients from autograd

def loss_value():
    return cross_entropy(model(X), y).item()

worst = 0.0
for name, p in model.named_parameters():
    num = np.zeros_like(p.data)
    for idx in np.ndindex(*p.data.shape):                   # nudge every number up and down
        old = p.data[idx]
        p.data[idx] = old + 1e-6; up = loss_value()
        p.data[idx] = old - 1e-6; down = loss_value()
        p.data[idx] = old
        num[idx] = (up - down) / 2e-6
    err = np.abs(num - p.grad).max()
    worst = max(worst, err)
    print(f"{name:18s} max |autograd - numerical| = {err:.2e}")
print("worst error:", f"{worst:.2e}")
layers.0.weight    max |autograd - numerical| = 1.40e-10
layers.0.bias      max |autograd - numerical| = 7.37e-11
layers.2.weight    max |autograd - numerical| = 1.39e-10
layers.2.bias      max |autograd - numerical| = 1.33e-10
worst error: 1.40e-10

Agreement to about 10-10 across all four parameter tensors, which is the best a central difference with step 10-6 can do in 64-bit arithmetic. PyTorch ships the same idea as torch.autograd.gradcheck, and you reach for it whenever you write a custom operation.

Optimisers and the training loop

An optimiser holds a list of parameters and knows how to turn their .grad into an update: SGD subtracts a multiple of the gradient, Adam keeps running averages and rescales (A0 chapter 10). It exposes two methods you will type thousands of times. zero_grad() clears the accumulated gradients; step() applies one update using whatever is in .grad now. Our nn.py contains SGD and Adam in a few lines each, in the same shape as PyTorch's. For AdamW and the weight-decay conventions, see chapter 04; PyTorch lets you pass several parameter groups with different settings so that biases and norm scales can skip decay.

Every supervised training script is the same loop, with five lines at its heart. Step through one iteration:

Step through

One training step, line by line

  1. Forward: logits = model(xb). The batch goes through the model, which reads the current parameters. If any input requires gradients, the graph is recorded now.
  2. Loss: loss = loss_fn(logits, yb). Predictions and targets are reduced to one number. This node is where the backward pass will start.
  3. Clear: opt.zero_grad(). The gradient buffers still hold the previous step's values. Because gradients accumulate, they must be emptied before the next backward pass, or the update uses stale information.
  4. Backward: loss.backward(). The engine walks the graph in reverse and writes the gradient of the loss into every parameter's .grad. No weight has changed yet.
  5. Update: opt.step(). The optimiser reads the gradients and changes the parameters in place: the only line of the loop that learns anything.
  6. Repeat. Take the next batch. One full pass over the training set is an epoch; the loop runs for many epochs, evaluating on held-out data between them.

Order matters in one respect: zero_grad() has to run after the previous step() and before the next backward(). Many scripts put it first in the loop body, as the stepper does; others put it right after step(). Putting it between backward() and step() is the mistake, because it wipes the gradients you just computed and the update does nothing.

A complete run

Now put the pieces together on a real (small) problem: classify points from two interleaved half-circles, the "two moons" dataset, with noise. A network with two hidden layers of 16 ReLU units, Adam with learning rate 0.01, minibatches of 64, and the five lines above. Each call to the model processes a minibatch: a slice of the training set small enough to be fast and large enough to give a stable gradient estimate. The model's output for each point is two logits, raw scores for the two classes; the loss turns them into probabilities with a softmax and takes the negative log of the probability given to the correct class, in one fused and numerically stable step (A0 chapter 11).

import numpy as np
from tinytorch import Tensor, cross_entropy, no_grad
from nn import Linear, ReLU, Sequential, Adam

def moons(n, rng, noise=0.15):                  # two interleaved half-circles
    t = rng.uniform(0, np.pi, n); k = rng.integers(0, 2, n)
    upper = np.stack([np.cos(t), np.sin(t)], 1); lower = np.stack([1 - np.cos(t), 0.5 - np.sin(t)], 1)
    X = np.where(k[:, None] == 0, upper, lower)
    return X + noise * rng.standard_normal(X.shape), k

rng = np.random.default_rng(0)
Xtr, ytr = moons(400, rng); Xte, yte = moons(400, rng)

model = Sequential(Linear(2, 16, rng), ReLU(), Linear(16, 16, rng), ReLU(), Linear(16, 2, rng))
opt = Adam(model.parameters(), lr=0.01)

for epoch in range(1, 61):
    order = rng.permutation(len(Xtr)); running = 0.0
    for i in range(0, len(order), 64):                  # one minibatch per iteration
        idx = order[i:i + 64]
        logits = model(Tensor(Xtr[idx]))                # 1. forward
        loss = cross_entropy(logits, ytr[idx])          # 2. loss
        opt.zero_grad()                                 # 3. clear old gradients
        loss.backward()                                 # 4. backward
        opt.step()                                      # 5. update
        running += loss.item() * len(idx)
    if epoch % 10 == 0 or epoch == 1:
        with no_grad():
            acc = (model(Tensor(Xte)).data.argmax(1) == yte).mean()
        print(f"epoch {epoch:2d}  train loss {running / len(Xtr):.4f}  test accuracy {acc:.3f}")

Here is the same experiment in PyTorch, with the standard conveniences: a DataLoader that shuffles and batches, a loss module that includes the softmax, and an explicit device. Your numbers will differ slightly from ours, since PyTorch's random number stream and initialisation are not the same as NumPy's, but the curve should have the same shape.

import torch
from torch import nn
from torch.utils.data import DataLoader, TensorDataset

torch.manual_seed(0)
device = "cuda" if torch.cuda.is_available() else "cpu"

# Xtr, Xte: float32 tensors (N, 2).  ytr, yte: int64 class indices (N,), as CrossEntropyLoss expects.
train_dl = DataLoader(TensorDataset(Xtr, ytr), batch_size=64, shuffle=True)

model = nn.Sequential(nn.Linear(2, 16), nn.ReLU(), nn.Linear(16, 16), nn.ReLU(), nn.Linear(16, 2)).to(device)
loss_fn = nn.CrossEntropyLoss()                      # takes raw logits; applies log-softmax itself
opt = torch.optim.Adam(model.parameters(), lr=0.01)

for epoch in range(1, 61):
    model.train()                                    # dropout on, batch-norm uses batch statistics
    for xb, yb in train_dl:
        xb, yb = xb.to(device), yb.to(device)
        logits = model(xb)                           # 1. forward
        loss = loss_fn(logits, yb)                   # 2. loss
        opt.zero_grad()                              # 3. clear old gradients
        loss.backward()                              # 4. backward
        opt.step()                                   # 5. update
    model.eval()                                     # dropout off
    with torch.no_grad():                            # no graph while evaluating
        pred = model(Xte.to(device)).argmax(dim=1)
        acc = (pred.cpu() == yte).float().mean().item()
    if epoch % 10 == 0:
        print(epoch, loss.item(), acc)

Walk through the details that trip people up. nn.CrossEntropyLoss expects raw logits and integer class indices; applying softmax yourself first and then using it gives a model that trains badly and silently. model.train() and model.eval() bracket the training and evaluation phases. torch.no_grad() wraps evaluation so no graph is stored. loss.item() converts a one-element tensor to a Python float. And .to(device) is applied to the model once, and to each batch as it arrives.

Most framework failures are one of a small set. A table to keep next to you:

The GPU in the loop

When tensors live on a GPU, a Python line such as y = a @ b does not wait for the multiplication. It queues a kernel (a function that runs on the GPU) and returns immediately, a style called asynchronous execution. Python races ahead queueing the next operations while the GPU works through them in order. This is why a well-written training loop keeps the GPU busy even though Python is slow. But some calls must wait for the answer: loss.item(), print(tensor), copying a result to the CPU, anything that turns GPU data into a Python value. These force a synchronisation, and Python stalls until the queue has drained.

Systems connection

The GPU's queue is the producer and consumer pattern and the latency arithmetic of queueing theory: Python enqueues work faster than the GPU drains it, and a synchronous call is a blocking wait for the result, the same distinction as in blocking versus non-blocking I/O. Profiling a slow training loop is mostly a search for stalls and for gaps where the GPU waits on data; the method is to measure first, then fix the largest stall. DataLoader workers are ordinary operating-system processes preparing batches in parallel with the GPU, and "pinned" host memory is page-locked memory that the operating system promises not to move or swap (virtual memory), which lets the GPU copy from it directly. Checkpoints written through state_dict are the storage side of the same story (a checkpoint is not saved until it is flushed).

Analogy: a receipt for every calculation

Imagine a shopkeeper who writes a line in a ledger for every sum they do: "6 = 3 × 2", "7 = 6 + 1". Later a customer disputes the total, and the shopkeeper can walk the ledger backwards, line by line, and say how much each input contributed to the result. Autograd's graph is that ledger, and backward() is the audit.

Where it breaks down: a paper ledger costs the shopkeeper only paper. The autograd ledger also stores the intermediate values that each line's reverse step needs, and in a large model those activations are the bulk of training memory (chapter 16). And a real audit does not edit the books, whereas step() does.

Key takeaways

  • A framework is tensors (shape, dtype, device), automatic differentiation, and a module and optimiser convention.
  • Autograd records operations as the forward code runs (define-by-run). backward() applies the chain rule in reverse and fills .grad on the leaf tensors. It is exact, and it costs a small multiple of the forward pass.
  • Gradients accumulate. Clear them every step with zero_grad() unless you are accumulating on purpose.
  • The loop has five lines: forward, loss, zero_grad, backward, step. Only step changes the weights.
  • Use model.train() and model.eval() for layer behaviour, and torch.no_grad() to stop recording a graph. They are separate switches.
  • GPU work is asynchronous: .item() and printing force a wait. Keep the graph out of long-lived variables.

Check your understanding

You call loss.backward() twice in a row on freshly built losses, without any clearing between. What is in a parameter's .grad afterwards?

  1. The gradient from the second call only, because it overwrites the first
  2. Nothing, because the first call freed the gradient
  3. The sum of the two gradients
  4. The average of the two gradients
Gradients are accumulated into leaf .grad buffers. Overwriting would make gradient accumulation across micro-batches impossible, which is a feature people rely on. The sum, not the average, is stored: if you want an average you divide the loss yourself.

A training loop runs out of GPU memory after a few hundred steps, although memory use is flat for the first few. The loop contains total_loss += loss and later prints total_loss / n. What is the most likely cause and fix?

  1. total_loss keeps each step's graph alive; use loss.item()
  2. The batch size is too large; halve it
  3. The optimiser stores too many states; switch to SGD
  4. zero_grad() is missing; add it
Adding a tensor that has a grad_fn chains every step's graph onto total_loss, so nothing can be freed. Taking .item() (or .detach()) stores a plain number. A too-large batch would fail immediately, not after hundreds of steps. A missing zero_grad() produces wrong updates, not a memory leak.

Which statement about model.eval() and torch.no_grad() is correct?

  1. model.eval() stops the graph being recorded
  2. torch.no_grad() switches dropout off
  3. They do the same thing, so using both is redundant
  4. eval() changes layer behaviour such as dropout; no_grad() stops graph recording; for inference you normally want both
They are independent. eval() changes how certain layers behave. no_grad() only controls whether operations are recorded for differentiation. Using only eval() still builds graphs and wastes memory; using only no_grad() leaves dropout active, giving noisy predictions.

In the graph figure, the square node's input is -3 and the incoming gradient is 1. Why is the gradient passed to the subtraction node -6?

  1. The mean divides by the batch size, which is 6
  2. The local derivative of the square is 2 times its input, and 2 x (-3) x 1 = -6
  3. The target is 10 and the prediction 7, so the gradient is 7 minus 10 minus 3
  4. Gradients always flip sign when passing backward through a subtraction
The chain rule multiplies the incoming gradient by the operation's local derivative; for a square that is 2 times the saved input. The mean here has one element, so it passes 1 through unchanged. The sign flip applies to the second argument of a subtraction (the target) and affects a leaf that does not need a gradient, not the first argument.

You add nn.Softmax as the last layer of a classifier and train it with nn.CrossEntropyLoss. What goes wrong?

  1. Nothing: the two are designed to be used together
  2. PyTorch raises an error at the first step
  3. The loss applies its own log-softmax to values that are already probabilities, which flattens the signal and trains badly without any error
  4. The model will output integers instead of probabilities
CrossEntropyLoss expects raw logits and applies log-softmax internally. Feeding it probabilities squeezes the range of its input, shrinking gradients, so the model learns slowly or poorly while still running. PyTorch does not detect it. Use softmax only when you need probabilities at prediction time.

A training loop calls loss.item() and prints it at every step, and the GPU is mostly idle. Why might removing the print speed training up?

  1. .item() forces a synchronisation, so Python waits for the GPU each step instead of queueing work ahead
  2. Printing is slow because it uses the network
  3. .item() copies the whole model to the CPU
  4. .item() clears the gradients
GPU kernels run asynchronously, so Python normally runs ahead and keeps the queue full. Reading a value back into Python waits until the queue drains, leaving the GPU idle while Python catches up. It copies one number, not the model, and does not touch gradients. Logging every N steps keeps the pipeline full.

Scaling Laws

Given a fixed budget of compute, should you train a bigger model on fewer tokens or a smaller one on more? This chapter shows that the loss of a language model falls as a smooth power law in model size, data and compute; reproduces the effect in a tiny experiment of our own; derives the compute-optimal recipe from a fitted formula; and explains why practical models now deliberately depart from it.

Why this matters

A frontier training run costs tens of millions of dollars and cannot be repeated, so the choices of model size and token count have to be right the first time. Scaling laws are how that is done: train many small models, fit a curve, and use it to predict what a run a thousand times larger will achieve. They also explain the history in this part of the course. GPT-3 was large and short of data, Chinchilla showed that was a poor use of compute, and the open models since then are smaller and trained for far longer. After this chapter you can read a "tokens per parameter" figure in a model card, estimate a sensible size for a given budget with the 6ND rule of chapter 16, judge how far to trust an extrapolation, and see why a model built for heavy use is trained beyond its compute-optimal point.

A straight line on log-log paper

A power law is a relationship y = a · xb. Take logarithms and it becomes log y = log a + b log x, a straight line whose slope is the exponent b. Power laws describe quantities that change by the same factor each time x changes by a fixed factor: if b = −0.076, every doubling of x multiplies y by 2-0.076 = 0.949, a 5% fall, whether x is a thousand or a billion.

Kaplan et al. (2020, "Scaling Laws for Neural Language Models") trained Transformer language models over wide ranges of size, data and compute and found that the test loss follows such laws, with trends "spanning more than seven orders of magnitude". With N the number of non-embedding parameters, D the number of training tokens and C_min the compute of the most efficient run, they fitted

  • L(N) = (Nc/N)0.076, with Nc = 8.8 × 1013, when data is plentiful;
  • L(D) = (Dc/D)0.095, with Dc = 5.4 × 1013 tokens, when the model is large enough;
  • L(Cmin) ∝ Cmin-0.050, for compute-efficient training.

The loss here is cross-entropy in nats per token on held-out text (chapter 14). The exponents are small: a tenfold increase in parameters multiplies the loss by only 10-0.076 = 0.84. Progress is steady and expensive, not sudden. They also found that the architecture details (depth against width, number of heads) matter little compared with the totals N, D and C.

The same thing in a tiny experiment

Rather than take that on trust, we can see the effect with models small enough to train in seconds. The script below builds a text source with structure: 400 pseudo-words drawn with Zipf-law frequencies (a few words common, most rare), so the text has a known noise floor. It then trains character-level MLP language models (a window of 8 characters is embedded, passed through one tanh layer of width H, and mapped to a distribution over the 27 characters) at six widths, each on four amounts of training text, one pass over the data each. That is 24 runs. The held-out loss is measured on a fresh sample. Training uses Adam with a warmup and cosine decay (chapter 17). The runs take about 20 seconds in NumPy.

# A real (tiny) scaling experiment: train character-level MLP language models of several sizes on several amounts of data.
import numpy as np, time, json, sys

def make_text(n_chars, seed):
    """Text from a fixed Zipf-distributed vocabulary of 400 pseudo-words, so the data has structure and a noise floor."""
    vr = np.random.default_rng(12345)                       # the vocabulary is the same for every call
    letters = np.array(list("abcdefghijklmnopqrstuvwxyz"))
    words = ["".join(vr.choice(letters, vr.integers(2, 9), p=None)) for _ in range(400)]
    p = 1 / np.arange(1, 401) ** 1.1; p /= p.sum()
    rng = np.random.default_rng(seed)
    out, n = [], 0
    while n < n_chars:
        w = words[rng.choice(400, p=p)]; out.append(w); n += len(w) + 1
    text = " ".join(out)[:n_chars]
    ent = -(p * np.log(p)).sum() / (sum(len(w) * q for w, q in zip(words, p)) + 1)   # nats per char, if words were known
    return text, ent

CHARS = "abcdefghijklmnopqrstuvwxyz "; IDX = {c: i for i, c in enumerate(CHARS)}; V = len(CHARS); K = 8; E_DIM = 12

def windows(text):
    a = np.array([IDX[c] for c in text]); n = len(a) - K
    X = np.stack([a[i:n + i] for i in range(K)], 1); return X, a[K:K + n]

def init(H, seed):
    r = np.random.default_rng(seed)
    return [r.normal(0, .3, (V, E_DIM)), r.normal(0, 1 / np.sqrt(K * E_DIM), (K * E_DIM, H)), np.zeros(H),
            r.normal(0, 1 / np.sqrt(H), (H, V)), np.zeros(V)]

def forward(P, X):
    emb = P[0][X].reshape(len(X), -1); h = np.tanh(emb @ P[1] + P[2]); z = h @ P[3] + P[4]
    z = z - z.max(1, keepdims=True); lp = z - np.log(np.exp(z).sum(1, keepdims=True)); return emb, h, lp

def train(H, D, seed=0, batch=128, lr=4e-3):
    X, Y = windows(make_text(D + K, seed)[0]); P = init(H, seed); m = [np.zeros_like(p) for p in P]; v = [np.zeros_like(p) for p in P]
    steps = D // batch
    for t in range(1, steps + 1):
        s = (t - 1) * batch; xb, yb = X[s:s + batch], Y[s:s + batch]
        cur = lr * min(1, t / 50) * (0.1 + 0.9 * 0.5 * (1 + np.cos(np.pi * t / steps)))
        emb, h, lp = forward(P, xb); g = np.exp(lp); g[np.arange(batch), yb] -= 1; g /= batch
        gh = (g @ P[3].T) * (1 - h ** 2); ge = (gh @ P[1].T).reshape(batch, K, E_DIM)
        grads = [np.zeros_like(P[0]), emb.T @ gh, gh.sum(0), h.T @ g, g.sum(0)]; np.add.at(grads[0], xb, ge)
        for i in range(5):
            m[i] = .9 * m[i] + .1 * grads[i]; v[i] = .95 * v[i] + .05 * grads[i] ** 2
            P[i] -= cur * (m[i] / (1 - .9 ** t)) / (np.sqrt(v[i] / (1 - .95 ** t)) + 1e-8)
    Xe, Ye = windows(make_text(40_000 + K, 999)[0]); lp = forward(P, Xe)[2]
    return float(-lp[np.arange(len(Ye)), Ye].mean()), sum(p.size for p in P)

if __name__ == "__main__":
    Hs = [4, 8, 16, 32, 64, 128]; Ds = [20_000, 80_000, 320_000, 1_280_000]; res = []
    print(f"entropy rate of the source if the words were known: {make_text(100, 0)[1]:.3f} nats per character")
    print(f"{'H':>4} {'N':>8} " + " ".join(f"{'D=' + format(d, ','):>12}" for d in Ds))
    for H in Hs:
        row = []
        for D in Ds:

        print(f"{H:>4} {N:>8,} " + " ".join(f"{l:>12.3f}" for l in row), flush=True)

Now fit the form that Hoffmann et al. (2022) used, L(N, D) = E + A/Nα + B/Dβ. The three terms have a reading. E is an irreducible loss that no model of any size trained on any amount of data can go below: the entropy of the source itself (chapter 14). The second term is the capacity penalty of having only N parameters. The third is the data penalty of having seen only D tokens. The script scans all pairs (α, β), solves for E, A and B by least squares at each pair, and keeps the best. It then repeats the fit on only the 18 runs with fewer than a million tokens and asks it to predict the six runs with 1.28 million.

# Fit L(N, D) = E + A / N^alpha + B / D^beta to the grid of runs by scanning (alpha, beta) and solving the rest by least squares.
import json, numpy as np
from tiny_scaling import make_text
runs = np.array(json.load(open("tiny_results.json"))); N, D, L = runs[:, 0], runs[:, 1], runs[:, 2]

def fit(N, D, L):
    best = None
    for a in np.arange(0.05, 2.0, 0.01):
        for b in np.arange(0.05, 2.0, 0.01):
            M = np.stack([np.ones_like(N), N ** -a, D ** -b], 1)
            coef, *_ = np.linalg.lstsq(M, L, rcond=None)
            if coef[1] < 0 or coef[2] < 0: continue
            err = ((M @ coef - L) ** 2).sum()
            if best is None or err < best[0]: best = (err, a, b, *coef)
    return best

err, a, b, E, A, B = fit(N, D, L)
print(f"fit on {len(L)} runs: L = {E:.3f} + {A:.3g} / N^{a:.2f} + {B:.3g} / D^{b:.2f}")

The fit describes the grid reasonably (typical error 0.07 nats), with exponents α = 0.69 and β = 0.31 (Chinchilla's are 0.34 and 0.28; a different model family and data give different values). But look at what it also shows, because both failures are instructive. First, the held-out prediction misses by as much as 0.21 nats (for the smallest model) and by 0.11 nats for the largest, which it predicts too pessimistically: a curve fitted on small data bends away from where the next points land. Second, the fitted floor E = 0.317 is below the true entropy of the source, which is 0.684 nats per character for a model that knows the words, so no real model could reach it. Neither means the idea is wrong; they mean that three-parameter fits to two dozen small runs are rough, and extrapolation beyond the range of the data is where fits break. Keep that in mind whenever a scaling law is quoted with several confident digits.

Chinchilla: the right balance of size and data

Kaplan et al. concluded that, for a fixed compute budget, most of the extra compute should go into a bigger model, with data growing slowly (their optimal N grows as C0.73 and D as C0.27, as summarised in the Hoffmann et al. paper). Models of the following two years followed that advice: GPT-3 had 175 billion parameters but was trained on about 300 billion tokens, Gopher had 280 billion parameters and the same 300 billion tokens.

Hoffmann et al. (2022, "Training Compute-Optimal Large Language Models"), working at DeepMind, trained more than 400 models from under 70 million to over 16 billion parameters on 5 to 500 billion tokens and reached a different answer. They estimated the compute-optimal frontier by three methods:

  1. Training curves. For each model size, train on a long token budget and record the loss; at each compute level take the best size. (Result: N and D both grow as C0.50.)
  2. IsoFLOP profiles. Pick a compute budget, train models of many sizes each with exactly that budget (small models on many tokens, big models on few), and find the size with the lowest loss. Repeat at several budgets. (Result: exponents 0.49 and 0.51.)
  3. A parametric fit. Fit L(N, D) = E + A/Nα + B/Dβ to all runs, as we just did, and minimise it under C = 6ND. (Result: exponents 0.46 and 0.54.)

All three say that parameters and tokens should grow in equal proportion: for every doubling of the model, double the data. In their Table 3, the optimal token counts come to about 20 per parameter at every scale: 20.2 billion tokens for a 1-billion-parameter model, 205 billion for 10 billion, 1.5 trillion for 67 billion. They tested the conclusion by training Chinchilla, 70 billion parameters on 1.4 trillion tokens, with the same compute as Gopher (280 billion parameters, 300 billion tokens). Chinchilla outperformed Gopher, GPT-3 and others on a wide range of tasks, reaching 67.5% average accuracy on the MMLU benchmark, over seven points above Gopher; being a quarter of Gopher's size, it is also cheaper to run. Case study 4 reads the paper in detail.

The IsoFLOP view is worth studying because it is the clearest way to see the trade-off. With the budget fixed, loss against model size is a U: too small a model is limited by capacity, and too large a model by the few tokens it can afford to see. The bottom of the U is the compute-optimal model, it moves to larger models as the budget grows, and it is broad. That flat bottom matters in practice, as we will see.

Go deeper optional: deriving the optimum from the parametric loss

Fix the budget C = 6ND, so D = C/(6N). Substitute into L(N, D) = E + A N-α + B D-β:

L(N) = E + A N-α + B (C/6)-β Nβ

Differentiate with respect to N and set to zero: −α A N-α-1 + β B (C/6)-β Nβ-1 = 0. Multiply through by N and rearrange: α A N-α = β B D-β. At the optimum the two penalty terms are in the fixed ratio βB : αA (here the data term's weight is the capacity term's times αA/βB). Solving for N,

Nopt = G · (C/6)β/(α+β),   Dopt = G-1 · (C/6)α/(α+β),   G = (αA / βB)1/(α+β).

So Nopt grows as C raised to β/(α+β) and Dopt as C raised to α/(α+β). With α = 0.34 and β = 0.28 these exponents are 0.45 and 0.55; with α close to β they are both near one half, the "scale equally" result. The code in optimal.py implements exactly these two lines. The second derivative is positive, so this is a minimum.

The script applies the formula with two sets of constants: those printed in the Hoffmann paper (E = 1.69, A = 406.4, B = 410.7, α = 0.34, β = 0.28) and those from a replication by Besiroglu et al. (2024, Epoch AI), who reconstructed the data from the paper's figure and refitted. They report that the printed numbers are inconsistent with the paper's own first two methods, and attribute that to an optimiser that stopped before convergence and to rounding of the published constants; their refit agrees with methods 1 and 2.

# Compute-optimal N and D from a parametric loss L(N, D) = E + A/N^alpha + B/D^beta under the budget C = 6*N*D.
import numpy as np

FITS = {"Hoffmann et al. 2022 (as printed)": (1.69, 406.4, 410.7, 0.34, 0.28),
        "Besiroglu et al. 2024 (replication)": (1.8172, 482.01, 2085.43, 0.3478, 0.3658)}

def optimum(C, fit):
    E, A, B, a, b = fit
    G = (a * A / (b * B)) ** (1 / (a + b))              # from setting dL/dN = 0 along N*D = C/6
    N = G * (C / 6) ** (b / (a + b)); D = C / (6 * N)
    return N, D, E + A / N ** a + B / D ** b

if __name__ == "__main__":

        for C in (1e19, 1e21, 5.76e23, 3.8e25):

The two fits disagree in an instructive way. The printed constants imply that the optimal ratio of tokens to parameters rises with the budget (32 at 1019 FLOPs, 93 at Gopher's budget), which contradicts the "about 20 tokens per parameter at every scale" of the paper's own Table 3. The refit gives a ratio near 20 and falling slowly (24 down to 16.5), in line with it, and puts the Gopher-budget optimum at 72 billion parameters and 1.3 trillion tokens, close to the 70 billion and 1.4 trillion that DeepMind trained. The last block of the output checks the printed constants against the paper's Table A3 rows: its model sizes come out 20 to 25% lower than the table's, which fits the rounding problem the replication describes. So the 20-tokens-per-parameter rule of thumb is well supported, while any specific constants should be treated as approximate.

Analogy: studying for an exam

Treat compute as the hours you have. Model size is how capable a student you are; data is how many practice problems you work through. A brilliant student with a handful of problems will not do as well as a good student with plenty, and a student who does a thousand problems with no capacity to absorb them wastes the hours. For a fixed number of hours there is a best balance of the two, and it is not the extreme of either. Scaling laws put numbers on the balance for language models.

Where it breaks down: a student can choose which problems to practise and can reason beyond what they have seen, whereas a language model's training data are fixed in advance and the model improves only on average, smoothly, in the loss. And the quality of the practice problems matters: the best balance moves when the data are better or worse, a fact the analogy hides.

Common misconception

"Chinchilla says every model should be trained on 20 tokens per parameter." The 20 is the optimum for one specific question: the lowest loss for a fixed training compute. It says nothing about the cost of using the model afterwards, and it was fitted to one family of models, one data distribution and one set of hyperparameters. A model that will serve billions of requests should be smaller and trained for longer than that optimum, as the next section shows; and the ratio changes with data quality and architecture.

Using a scaling law to plan a run

Suppose you have a budget of 1022 FLOPs (on an H100 at 40% MFU, chapter 16 shows that is about 7,000 GPU-hours). The recipe is:

  1. Choose a fit. Use published constants as a first guess, then run your own small grid on your data and architecture, as in our tiny experiment but with models of 10 million to 1 billion parameters. The law depends on the data distribution and the recipe, and the published ones do not transfer exactly.
  2. Compute the optimum. From the Besiroglu refit, 1022 FLOPs gives about 9 billion parameters on 180 billion tokens (see the last block of compare.py below); 6ND checks the budget.
  3. Hold out a margin. Because of the flat bottom, anything within a factor of two of the optimum costs about 0.01 nats. You have room to adjust for hardware, inference or data constraints.
  4. Validate by extrapolating. Train a few runs at one or two orders of magnitude below the target, check they sit on the fitted curve, and treat a departure as a warning.

The Llama 3 team did a version of this at scale. They trained models from 40 million to 16 billion parameters at budgets from 6 × 1018 to 1022 FLOPs, fitted a parabola to each IsoFLOP curve to find its minimum, and fitted a power law for the optimal number of training tokens against compute, with exponent 0.53. Extrapolating to their 3.8 × 1025 FLOP budget gave 402 billion parameters on 16.55 trillion tokens; they trained 405 billion parameters on 15.6 trillion tokens, noting that the IsoFLOP curves "become flatter around the minimum" at larger budgets, so the result was robust to small changes. They also fitted a relationship from the compute of a run to benchmark accuracy, in two steps (compute to the loss of the correct answer, then loss to accuracy with a sigmoid), to forecast downstream performance of the flagship model before training it.

The top block repeats Hoffmann's comparison under both fits: Gopher and Chinchilla have almost the same 6ND (the paper's more careful count gives 5.76 × 1023 for Gopher) but the fits predict a loss about 0.05 to 0.06 lower for Chinchilla, which is the sign of the measured result. Beyond compute-optimal: the cost of serving

Chinchilla minimises the loss for a fixed training bill. But a model that is trained once and then queried billions of times has a second bill, inference, that grows with the model size: every generated token costs about 2N FLOPs and reads every weight (chapter 16). If two models reach the same loss, the smaller one is cheaper to use forever. Sardana et al. (2023, "Beyond Chinchilla-Optimal: Accounting for Inference in Language Model Scaling Laws") add the inference cost to the Chinchilla law and find that researchers expecting large inference demand (they consider on the order of a billion requests) should train smaller models for longer than Chinchilla-optimal. The extra training tokens are paid once, and the saving is repeated on every request.

This is what the field does. Llama 3 405B, trained for a budget of 3.8 × 1025 FLOPs, sits at about 39 tokens per parameter, about twice the Chinchilla ratio, and the paper describes a pre-training corpus of about 15 trillion tokens for the family: an 8-billion-parameter model that saw all of it would be at nearly 2,000 tokens per parameter (the top point in the figure below, which is illustrative, since this chapter does not state that model's own token count). Such a model is far from compute-optimal for its training cost; it is optimal for a different objective, loss per unit of lifetime cost. The sensible reading of the Chinchilla result is not "use 20 tokens per parameter" but "do not spend a training budget on parameters the data cannot fill".

Two more limits keep the practical optimum from being a simple formula.

  • Data is finite. The calculation assumes you can always find fresh tokens. Muennighoff et al. (2023, "Scaling Data-Constrained Language Models") trained over 400 models, some for up to 1,500 epochs, and found that training for up to about four epochs on repeated data gives negligible change in loss relative to fresh data at the same compute, with returns diminishing rapidly beyond that. Pretraining data and its limits are the subject of A3 chapter 01.
  • Data quality moves the optimum. Replications discussed by Besiroglu et al. note, citing the DeepSeek LLM report (Bi et al., 2024), that the best ratio of data to parameters is sensitive to the quality of the data, with a lower tokens-per-parameter ratio optimal for higher-quality data. A law fitted on one corpus is not a law of nature.

What scaling laws do not say

  • Loss is not capability. The laws are about cross-entropy on held-out text. How a given loss translates to the ability to answer questions or write code is a separate and less regular relationship. Wei et al. (2022, "Emergent Abilities of Large Language Models") described abilities that appear abruptly at some scale; Schaeffer et al. (2023, "Are Emergent Abilities of Large Language Models a Mirage?") argued that much of that sharpness comes from the choice of all-or-nothing metrics, with smooth underlying improvement. The question is not settled in general, but a good habit follows: before believing a sudden jump, plot the same data with a smooth metric such as the probability assigned to the right answer.
  • Laws are conditional on the recipe. Learning rate, batch size, architecture, data mix and tokeniser all change the constants. Hoffmann et al. attribute part of the difference from Kaplan's conclusion to this: Kaplan used one fixed learning-rate schedule for all runs, which overstates the loss of runs with less data, and most of Kaplan's models were small. When you change the recipe, refit.
  • Extrapolation is risky. Our tiny experiment missed by up to 0.2 nats when asked to extrapolate by a factor of four in data. The published fits cover about 2 to 3 orders of magnitude of compute and are used to extrapolate one or two more; there is no guarantee the line continues forever, and the loss is bounded below by the entropy of the data.
  • Replication matters. The Chinchilla constants are cited in hundreds of papers, and the reconstruction by Besiroglu et al. found that the printed numbers did not fit the paper's own data well. Quote the finding (about 20 tokens per parameter) and the method, not the third significant digit.

State of play, October 2026

The Chinchilla-style analysis, trained dense models, a clean web corpus and a fixed 6ND budget, describes a regime that frontier practice has moved beyond in at least three ways. (1) Compute is spent after training too. Models that spend more tokens at inference time (long reasoning traces, repeated sampling, search) improve with test-time compute; Snell et al. (2024, "Scaling LLM Test-Time Compute Optimally can be More Effective than Scaling Model Parameters") studied the trade-off against pretraining. Reinforcement-learning stages (A3 chapter 14) add compute whose scaling behaviour is still being measured. (2) Architectures change the constants. Mixtures of experts (chapter 20) decouple total parameters from per-token compute, so "N" in the formula needs a definition. (3) Data, not compute, is the binding constraint for some labs, which makes synthetic data and multi-epoch training, discussed above, central. I have not verified specific scaling-law exponents reported for these newer regimes; the durable parts of this chapter are the method (fit small runs, extrapolate carefully, validate) and the balance idea, not any single set of constants. Check recent technical reports for the current numbers.

Systems connection

Extrapolating from small experiments to a large production run is capacity planning with a different resource. A load test at 10% of the target traffic does not guarantee that the system behaves at 100%, because bottlenecks appear that did not show at small scale; see load testing and capacity planning for how engineers decide how far to trust an extrapolation and how much headroom to keep. The flat bottom of the IsoFLOP curve is the same kind of fact as a wide, shallow cost minimum in a system design: it means you can choose for other reasons (hardware shape, serving cost, risk) at little penalty. The serving-versus-training trade-off continues in A3 chapter 22.

Key takeaways

  • Language-model loss falls as a power law in parameters, data and compute: a straight line on log-log axes. Kaplan et al. (2020) measured exponents of about 0.076 (parameters), 0.095 (data) and 0.050 (compute) over seven orders of magnitude.
  • A useful model of the loss is L(N, D) = E + A/Nα + B/Dβ: an irreducible floor, a capacity penalty and a data penalty. Minimising it under C = 6ND gives N and D that grow as C raised to β/(α+β) and α/(α+β).
  • Hoffmann et al. (2022) found that parameters and tokens should grow in proportion, at about 20 tokens per parameter, so GPT-3 and Gopher were too large and too short of data; Chinchilla, 70B on 1.4T tokens, beat Gopher at the same compute.
  • The bottom of the IsoFLOP curve is flat: within a factor of two of the optimal size costs about 0.01 nats, so you can choose model size for other reasons.
  • Models meant for heavy use are trained beyond compute-optimal (Llama 3 405B at 39 tokens per parameter, small Llama 3 models far beyond), because inference cost scales with parameters.
  • Treat constants with caution: they depend on data, recipe and N's definition, a replication found the printed Chinchilla constants inconsistent with the paper's other methods, and extrapolation can fail. Loss is not capability.

Check your understanding

A loss follows L(N) = (Nc/N)0.076. By what factor does the loss change when the parameter count is multiplied by 10?

  1. It falls by 7.6%
  2. It is multiplied by about 0.84, a fall of about 16%
  3. It is divided by 10
  4. It falls by 0.076 nats
Multiplying N by 10 multiplies L by 10-0.076 = 0.84. The first option mistakes the exponent for the percentage change; the third treats the law as inversely proportional; the fourth treats it as an absolute subtraction, which a power law is not.

You have 6 × 1023 FLOPs (about Gopher's budget). Using the Chinchilla rule of roughly 20 tokens per parameter and C = 6ND, which model size is closest to compute-optimal?

  1. 280 billion parameters
  2. 7 billion parameters
  3. 20 billion parameters
  4. about 70 billion parameters
C = 6 N (20 N) = 120 N2, so N = √(6 × 1023/120) = √(5 × 1021) = 7 × 1010, about 70 billion, with 1.4 trillion tokens: Chinchilla itself. 280 billion is Gopher, which was too large for the budget. The smaller answers come from dropping a factor of ten in the square root.

Two models reach the same loss. One is a compute-optimal 70B model; the other is a 20B model trained on far more tokens. A company expects to serve the model to millions of users. Which statement is most accurate?

  1. The 20B model may be the better choice overall, because it costs more to train but much less to serve, and inference cost depends on parameters
  2. The 70B model is always better because it is compute-optimal
  3. The 20B model cannot reach the same loss
  4. Training cost is the only cost that matters
"Compute-optimal" refers to training compute only. Serving cost scales with parameters (about 2N FLOPs and N weights read per generated token), so with heavy use the cheaper-to-serve model wins even though its training run was less efficient. This is the argument of Sardana et al. and the practice of the Llama 3 small models. The third claim is false, since more data can compensate for fewer parameters up to a point.

In our tiny experiment, a fit made on runs with at most 320,000 tokens mispredicted the 1.28-million-token runs by up to about 0.2 nats, and the fitted floor was below the source's true entropy. What is the best lesson?

  1. Scaling laws do not exist for small models
  2. The fit should be repeated until the numbers match
  3. Fits to a few small runs are rough, and extrapolating beyond the fitted range (and reading the floor E as a physical quantity) is risky; validate with held-out larger runs
  4. The loss should be measured in bits instead of nats
The trend was real, but a three-parameter curve fitted to a narrow range can bend away from the next points, and a fitted constant can be impossible. That is why Llama 3 validated predictions across orders of magnitude of compute. The unit of loss does not affect the issue, and tuning until numbers match is overfitting.

An IsoFLOP curve for a 1022 FLOP budget has its minimum at 9 billion parameters. A team wants a model that is cheaper to serve and chooses 4.5 billion parameters, training on twice as many tokens. According to the calculation in this chapter, what is the likely price in training loss?

  1. Large: the loss rises by about 1 nat
  2. Small: roughly 0.01 nats, because the bottom of the curve is flat
  3. Zero: the loss is identical by definition
  4. It cannot be said without training the model
The curve is broad near its minimum: in the chapter's calculation a model half the optimal size costs about 0.01 nats, which is why designing for serving cost or hardware shape is cheap. The loss is not identical, only close, and the fit does give a prediction, though it is uncertain. A rise of one nat would be a catastrophic change that the shape of the curve rules out.

A paper reports that "emergent" abilities appear suddenly at a certain model size. Which first check does this chapter suggest?

  1. Assume the ability is a phase transition and plan compute to reach it
  2. Ignore the result because loss is smooth
  3. Re-plot the same results with a continuous metric, such as the probability of the correct answer, to see whether the jump comes from an all-or-nothing score
  4. Check that the model has more than 100 billion parameters
Schaeffer et al. argued that many sharp transitions come from thresholded metrics like exact-match accuracy applied to smoothly improving models. Looking at a continuous metric distinguishes the cases. It is too strong to dismiss all emergence, and parameter count is not the test.

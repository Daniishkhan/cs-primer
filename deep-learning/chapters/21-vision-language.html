Vision-Language Models

A language model reads tokens, and a photograph is a grid of numbers. This chapter shows how to turn an image into something a language model can read: patches become tokens, an image encoder gives them meaning, a projector fits them to the model's width, and a short training recipe teaches the language model to use them.

Why this matters

Documents, screenshots, charts, receipts, X-rays and photographs are the inputs of many real applications, and most current assistants accept them. A team that treats the image as a black box cannot answer the practical questions: why a high-resolution scan costs ten times more than a thumbnail, why the model reads the headline but misreads the footnote, how many pages of a PDF fit in the context, or why it describes an object that is not there. All of these follow from one design: the image is turned into a sequence of vectors that sit in the language model's context beside the words. After this chapter you can trace that conversion with shapes, count image tokens and their cost for a given resolution, explain the two training stages, and list the failure modes that follow. The retrieval course picks this up for documents (A5 chapter 19), and A6 for how to test such systems (A6 chapter 1).

The plan: make an image look like text

The Transformer of chapter 10 takes a sequence of vectors of width C. It does not care whether those vectors began as words. Text gets there through a tokeniser and an embedding table (chapter 13, chapter 6). A vision-language model (VLM) needs a second route that produces vectors of the same width from pixels, and then lets the language model attend over both kinds.

Each of the three new parts has one job. The patches turn a 2-D grid into a 1-D sequence. The encoder makes those pieces meaningful rather than raw colour. The projector translates between two vector spaces that were trained separately. We take them in order.

Patches: an image as a sequence

A convolutional network (chapter 7) slides small filters over an image. The Vision Transformer (ViT; Dosovitskiy et al., 2020, "An Image is Worth 16x16 Words") instead cuts the image into a grid of non-overlapping square patches, flattens each into a vector and applies one shared linear layer to all of them. For a 224 × 224 image with 16 × 16 patches that gives 14 × 14 = 196 patches, each of P² × 3 = 768 numbers. The linear layer maps each to a vector of the model width C. Those 196 vectors, plus positional information so the model knows which patch came from where (chapter 11), are the sequence. Everything after that is the ordinary Transformer block, with bidirectional attention, because an image has no left-to-right order.

The script performs this in NumPy and verifies a fact stated in chapter 7: the patch embedding is a convolution whose kernel size and stride both equal the patch size. Then it counts the tokens for a few common settings.

# From an image to a sequence of tokens: patchify, embed, and count the tokens for common sizes.
import numpy as np
rng = np.random.default_rng(0)
H = W = 224; P = 16; C = 64                                    # image size, patch size, model width
img = rng.random((H, W, 3))                                    # (H, W, 3) stand-in for a photo
gh, gw = H // P, W // P

patches = img.reshape(gh, P, gw, P, 3).transpose(0, 2, 1, 3, 4).reshape(gh * gw, P * P * 3)   # (196, 768): one row per patch
We = rng.normal(0, .02, (P * P * 3, C))                        # the patch embedding: ONE linear layer shared by all patches
tokens = patches @ We                                          # (196, C)
print(f"image {img.shape} -> {gh}x{gw} patches -> patch matrix {patches.shape} -> tokens {tokens.shape}")

# The same layer seen as a convolution with kernel size = stride = P, written out as a sum over each patch's pixels.
K = We.reshape(P, P, 3, C)
conv = np.einsum("iujvc,uvcd->ijd", img.reshape(gh, P, gw, P, 3), K).reshape(gh * gw, C)
print("max |matmul - convolution| =", np.abs(tokens - conv).max())

print(f"\n{'image':>6} {'patch':>6} {'tokens':>7} {'after 2x2 merge':>16}   example")
for s, p, eg in ((224, 16, "ViT-B/16 at 224"), (224, 14, "ViT-L/14 at 224"), (336, 14, "ViT-L/14 at 336 (LLaVA-1.5)"), (448, 14, "ViT-L/14 at 448"), (1024, 16, "a 1024-pixel photo")):
    n = (s // p) ** 2
    print(f"{s:>6} {p:>6} {n:>7,} {n // 4:>16,}   {eg}")

The two computations agree exactly (the difference is 0.0), so frameworks usually write the patch embedding as one strided convolution. The table is the part to remember: the token count is (size / patch)², so it grows with the square of the resolution. Doubling the side of a 336-pixel image to 672 does not double the cost, it quadruples the tokens, from 576 to 2,304. Many models merge neighbouring patches (a 2 × 2 merge divides the count by four) to keep the sequence short, at the price of detail.

Common misconception

"The model sees the image the way you do." It sees a few hundred vectors, each a summary of one square of pixels (often 14 or 16 pixels wide). Small text, thin lines and fine counts can fall inside or across a patch and be blurred together. When a model misreads a number in a scan, the first thing to check is the resolution and the patch count, not the prompt.

The image encoder: where meaning comes from

Raw patch embeddings only describe colours and edges. The encoder is a stack of Transformer blocks that mixes patches so that each output vector carries what is in and around that location. Where do its weights come from? In recent VLMs, almost always from contrastive language-image pre-training, CLIP (Radford et al., 2021, "Learning Transferable Visual Models From Natural Language Supervision"). CLIP trains an image encoder and a text encoder together on 400 million (image, text) pairs collected from the internet, with one task: predict which caption goes with which image.

The contrastive loss

Take a batch of B pairs. Encode every image to a unit-length vector ui and every caption to a unit-length vector vj. The B × B matrix of dot products Sij = ui · vj (scaled by a temperature) has the true pairs on its diagonal. Treat each row as a classification problem, "which of the B captions matches image i?", and each column as the reverse, and apply the softmax cross-entropy of A0 chapter 14 to both. The loss falls when the diagonal rises above the rest. The batch supplies B − 1 negatives for free, which is why large batches matter.

The next script trains a toy version end to end with the gradients written out by hand: two linear encoders on synthetic features that share a hidden cause, standing in for the image and caption of one scene. It prints the loss and the held-out retrieval accuracy (picking the right caption among 64).

# A toy CLIP: two linear encoders trained so matching (image, text) pairs score higher than all other pairs in the batch.
import numpy as np
rng = np.random.default_rng(0)
N, d_lat, d_img, d_txt, d = 2048, 6, 20, 14, 8
z = rng.normal(size=(N, d_lat))                                 # hidden "what the scene contains"
Xi = z @ rng.normal(size=(d_lat, d_img)) + 0.5 * rng.normal(size=(N, d_img))   # image features
Xt = z @ rng.normal(size=(d_lat, d_txt)) + 0.5 * rng.normal(size=(N, d_txt))   # caption features (different view of z)
Wi, Wt = rng.normal(0, .3, (d_img, d)), rng.normal(0, .3, (d_txt, d))
s = 10.0                                                        # 1 / temperature

def unit(Z): n = np.linalg.norm(Z, axis=1, keepdims=True); return Z / n, n
def softmax(L, axis): e = np.exp(L - L.max(axis, keepdims=True)); return e / e.sum(axis, keepdims=True)

def step(xi, xt, lr=0.0):
    global Wi, Wt
    B = len(xi); (Ui, ni), (Ut, nt) = unit(xi @ Wi), unit(xt @ Wt)
    L = s * Ui @ Ut.T                                           # (B, B): similarity of every image with every caption
    I = np.eye(B)
    loss = -0.5 * (np.log(softmax(L, 1)[I > 0]).mean() + np.log(softmax(L, 0)[I > 0]).mean())
    acc = (L.argmax(1) == np.arange(B)).mean()                  # image -> caption retrieval accuracy within the batch
    dL = ((softmax(L, 1) - I) + (softmax(L, 0) - I)) / (2 * B)
    dUi, dUt = s * dL @ Ut, s * dL.T @ Ui
    dZi = (dUi - Ui * (Ui * dUi).sum(1, keepdims=True)) / ni    # back through the normalisation
    dZt = (dUt - Ut * (Ut * dUt).sum(1, keepdims=True)) / nt
    Wi -= lr * xi.T @ dZi; Wt -= lr * xt.T @ dZt
    return loss, acc

test = slice(1792, 1856)                                        # held-out batch of 64: chance is 1/64 = 1.6%
for it in range(401):
    if it % 100 == 0:
        l, a = step(Xi[test], Xt[test])
        print(f"step {it:>3}  held-out loss {l:5.3f}  held-out retrieval accuracy {a:5.1%}")
    idx = rng.choice(1792, 64, replace=False)
    step(Xi[idx], Xt[idx], lr=0.5)
print(f"loss of a model that cannot tell pairs apart: ln(64) = {np.log(64):.3f}")
step   0  held-out loss 8.876  held-out retrieval accuracy  0.0%
step 100  held-out loss 0.589  held-out retrieval accuracy 95.3%
step 200  held-out loss 0.579  held-out retrieval accuracy 95.3%
step 300  held-out loss 0.570  held-out retrieval accuracy 95.3%
step 400  held-out loss 0.573  held-out retrieval accuracy 95.3%

Before training the loss is above the 4.16 that guessing would give, because a random encoder is confidently wrong rather than uncertain; accuracy starts below the 1.6% of chance for the same reason. After 100 steps the held-out loss is 0.59 and the right caption is picked 95% of the time. That plateau at 95% reflects the noise added to the features, not a bug. The real CLIP does the same with deep encoders and 400 million pairs, and the result is an image space and a text space in which matching things are close. That alignment is what makes the features useful to a language model: they already speak, roughly, in the vocabulary of captions.

Variants change the loss, not the idea. SigLIP (Zhai et al., 2023, "Sigmoid Loss for Language Image Pre-Training") replaces the row-and-column softmax with an independent sigmoid on every (image, caption) pair. Its abstract notes that the loss needs no global view of all pairwise similarities, lets the batch size scale further and performs better at small batches. Many recent VLMs use a SigLIP-style encoder; others use CLIP or train their own.

The projector: translating between spaces

The encoder's output lives in the encoder's space, with width 1,024 for a ViT-L. The language model works at width 4,096 (for an 8B model) in a space shaped by text. The simplest bridge is a projector: a small network applied to each patch vector independently. The first LLaVA (Liu et al., 2023, "Visual Instruction Tuning") connected a CLIP encoder to a language model with a linear layer, and LLaVA-1.5 (Liu et al., 2023, "Improved Baselines with Visual Instruction Tuning") found, per its abstract, that a two-layer MLP connector was surprisingly powerful and data-efficient. Its final 13B model used 1.2 million public training examples and, the authors say, trained in about a day on one node of eight A100 GPUs.

The projected vectors are then spliced into the sequence: the embeddings of the text before the image, the N image vectors, and the embeddings of the text after it. From the language model's point of view they are N extra positions in the context. The script builds exactly this sequence and works out its cost.

# Wiring an image into a language model: project vision features to the LLM width and splice them into the text sequence.
import numpy as np
rng = np.random.default_rng(0)
d_vis, d_llm, n_img = 1024, 4096, 576                          # ViT-L feature width, Llama 3 8B width, tokens from a 336 px image
vis = rng.normal(size=(n_img, d_vis))                          # (576, 1024): output of the image encoder

linear = (d_vis * d_llm + d_llm)                               # one linear layer
mlp = (d_vis * d_llm + d_llm) + (d_llm * d_llm + d_llm)        # two layers with a GELU between (the LLaVA-1.5 style)
print(f"projector parameters: linear {linear/1e6:.1f} M, two-layer MLP {mlp/1e6:.1f} M (the 8B language model has about 8,000 M)")

W1, b1 = rng.normal(0, .02, (d_vis, d_llm)), np.zeros(d_llm)
W2, b2 = rng.normal(0, .02, (d_llm, d_llm)), np.zeros(d_llm)
gelu = lambda x: 0.5 * x * (1 + np.tanh(0.79788456 * (x + 0.044715 * x ** 3)))
img_tok = gelu(vis @ W1 + b1) @ W2 + b2                        # (576, 4096): now the same width as word embeddings

emb = rng.normal(0, .02, (1000, d_llm))                        # a toy text embedding table (1000-word vocabulary)
before, after = rng.integers(0, 1000, 12), rng.integers(0, 1000, 20)   # a 12-token prefix and a 20-token question
seq = np.concatenate([emb[before], img_tok, emb[after]])       # (12 + 576 + 20, 4096)
print("sequence fed to the language model:", seq.shape, "= 12 text + 576 image + 20 text tokens")

# What the image costs the language model, using the KV-cache formula of chapter 19 (Llama 3 8B: 128 KiB per token).
kv_per_token = 2 * 32 * 8 * 128 * 2
print(f"KV cache for the image tokens alone: {n_img * kv_per_token / 2**20:.0f} MiB per image, per conversation")
print(f"an 8,192-token context holds {8192 // n_img} such images before any text; one image costs as much context as {n_img} text tokens")
projector parameters: linear 4.2 M, two-layer MLP 21.0 M (the 8B language model has about 8,000 M)

The projector has about 21 million parameters, a quarter of one percent of the language model. The sequence has 608 positions of which 576 are the image. The last lines are the practical consequence: using the key/value cache formula of chapter 19, one such image holds 72 MiB of cache for as long as the conversation lasts, and uses 576 positions of the context. An 8,192-token window fits 14 such images and no text. Image tokens are priced and limited like text tokens, and a document of ten pages at this resolution is already a long prompt.

Analogy: the interpreter at the table

Picture a speaker of one language (the language model) and a specialist who has studied photographs for years but speaks another (the image encoder). The projector is an interpreter who stands between them and turns each of the specialist's observations into phrases the speaker understands. Training the interpreter first, while both principals stay fixed, is quick, and only then do the principals adjust to each other.

Where it breaks down: an interpreter has a language the speaker already knows; the projector produces vectors, not words, and the language model never saw such inputs in pre-training. It learns to read them during the second training stage. Also, an interpreter can ask the specialist a follow-up question; here the encoder runs once and cannot be queried again, so detail dropped at the encoder cannot be recovered later.

Other ways to connect the two

Prefix tokens through a projector are the simplest design but not the only one. Two others solve the token-count problem in different ways.

  • Cross-attention into a frozen language model. Flamingo (Alayrac et al., 2022, "Flamingo: a Visual Language Model for Few-Shot Learning") inserts new layers between the frozen language model's layers in which the text positions attend to image features, so the image never enters the language model's own sequence. Its abstract highlights that the design handles inputs that interleave images and text in any order and that training on web pages of interleaved images and text is central to its few-shot ability. A resampler first compresses the image features to a fixed number of vectors.
  • A querying bottleneck. BLIP-2 (Li et al., 2023) places a small Querying Transformer between a frozen image encoder and a frozen language model. A fixed set of learned query vectors attends to the image, and only the queries' outputs are passed on, so the number of image tokens is fixed whatever the resolution. The paper reports beating Flamingo-80B by 8.7% on zero-shot VQAv2 with 54 times fewer trainable parameters.

Training: two stages

The common recipe, introduced with LLaVA, has two stages. Which parts are trained at each, and on what data, is the heart of the method.

StageTrainedFrozenDataPurpose
1. AlignmentProjector onlyEncoder and language modelImage and caption pairsMake image tokens land where the language model can read them; cheap and safe because only about 21M parameters move
2. Instruction tuningProjector and language model (the encoder often stays frozen)Encoder, sometimesConversations about images: questions, descriptions, reasoning, task dataTeach the model to follow instructions about what it sees

Stage 2 is supervised fine-tuning as in A3 chapter 10: the loss (chapter 14) is next-token cross-entropy on the answer tokens only, with the image and the question as context. The first LLaVA paper's contribution was the data: it used a text-only GPT-4 to generate instruction-following conversations about images from their captions, and reports a relative score of 85.1% against GPT-4 on a synthetic multimodal instruction benchmark of its own. The authors' own benchmark and a model-written evaluation make that figure a sign of promise, not an independent measurement.

Handling high resolution

A fixed 336-pixel input is too coarse for a page of text. Common fixes (all described in various open models, with details that differ) are to split a large image into tiles that the encoder processes one by one plus a downscaled copy for the overall layout, to merge neighbouring patches to reduce the count, or to train the encoder at several resolutions. Each fix is a token-budget decision: more tiles read small print better and cost proportionally more context, cache memory and time to first token.

What goes wrong

The design leads directly to a list of failure modes. Knowing them tells you what to test.

  • Small or dense text. If a character is a fraction of a patch, the encoder cannot represent it. Check by cropping and enlarging the region.
  • Counting and spatial relations. Contrastive pre-training rewards "what is in the picture", which a caption states; it rewards "how many" and "which is left of which" much less, since captions seldom say. Expect weaker performance on counts, precise positions and relations between objects.
  • Hallucination. The language model is a strong prior over plausible text, and weak or ambiguous image evidence loses to it. It may describe an object that would be typical in such a scene but is not there (A6 chapter 10).
  • Lost detail between stages. Whatever the encoder's patches and the projector drop is gone for good.
  • Instructions inside images. Text in an image is read by the same model that reads your prompt, so an image can carry an injection (A6 chapter 13).

Systems connection

Images turn a text service into one with large, variable-size, untrusted binary inputs. Decoding and resizing happen before the GPU and can dominate time to first token, so they belong in the capacity plan (Zero to Systems chapter 22); image bytes need the same upload limits and content validation as any file upload (Zero to Systems security chapter 9); and an image that carries instructions is untrusted input reaching a privileged interpreter. The token count turns directly into money and latency, so the estimation habits of Designing with ML & LLMs apply: resolution is a dial with a cost per step.

State of play, October 2026

The encoder-projector-language-model recipe of this chapter is still the clearest way to learn the idea and is common in open models. As far as published reports show, a growing number of systems also train one model on interleaved text and images from the start instead of attaching a pre-trained encoder, and some generate images as well as read them. Their training data and details are mostly not public, so treat claims about which design is best with caution. Resolution handling, the number of image tokens and the choice of encoder differ between models and change with each release; read the model card for current figures rather than relying on the numbers here, which belong to the specific open recipes cited.

Key takeaways

  • A VLM turns an image into a sequence of vectors at the language model's width and places them in the context beside the text.
  • Patches make the sequence: tokens = (size / patch)², so cost grows with the square of the resolution. A 336-pixel image with 14-pixel patches is 576 tokens.
  • The encoder is usually pre-trained contrastively (CLIP, SigLIP) so that images and captions share a space; the loss is a softmax (or sigmoid) over the matrix of image-caption similarities.
  • A projector, a linear layer or small MLP, bridges the encoder's space and the language model's. Cross-attention (Flamingo) and query bottlenecks (BLIP-2) are the alternatives.
  • Training has two stages: align the projector on captions, then instruction-tune on conversations about images with the loss on answer tokens.
  • Expect trouble with small text, counting, spatial relations, hallucinated objects and instructions hidden in images.

Check your understanding

A VLM uses a ViT with 14-pixel patches and no merging. You raise the input from 336 × 336 to 672 × 672 pixels. How does the number of image tokens change?

  1. It doubles, from 576 to 1,152
  2. It stays the same, because the patch size is fixed
  3. It quadruples, from 576 to 2,304
  4. It grows by a factor of 8
Tokens = (size / patch)². 336/14 = 24 gives 576; 672/14 = 48 gives 2,304. Doubling the side doubles each of two dimensions. The count would stay fixed only if the model resized the image back or used a fixed set of query vectors, as BLIP-2 does.

In the first training stage of a LLaVA-style model, which parameters are updated?

  1. Only the projector, with the encoder and language model frozen
  2. Only the language model
  3. The encoder and the projector, with the language model frozen
  4. All parameters, on image-caption pairs
Stage 1 aligns the new component with the two pretrained ones, and updating only about 21 million projector parameters is cheap and safe. The language model is updated in stage 2 together with the projector. Training everything on captions at this point would risk damaging the language model before the projector produces meaningful inputs.

In a CLIP batch of 64 pairs, how many captions serve as negatives for a given image, and why does batch size matter?

  1. None: the loss compares only the true pair
  2. One randomly chosen caption per image
  3. 63, but they contribute nothing because the encoders are shared
  4. 63: every other caption in the batch, so larger batches give a harder classification task and more negatives
The similarity matrix scores each image against all 64 captions, so 63 are negatives, and the loss is a 64-way classification. A comparison of only the true pair has nothing to push down, so the embeddings could collapse to a constant. The negatives matter because they do the pushing apart. SigLIP changes how the loss uses them, not that it needs them.

An assistant reads a printed table in a scanned page well when the page fills the image but fails on a small footnote. Which explanation fits the design best?

  1. The language model has forgotten how to read small text
  2. The footnote's characters are smaller than, or cut across, the patches the encoder sees, so the detail is lost before the language model gets it
  3. The projector has too many parameters
  4. The footnote is a different language
Each patch is one vector summarising a square of 14 to 16 pixels, so very small characters are blurred together at the encoder. Cropping or tiling to raise the effective resolution is the fix. The language model reads text fine when its input contains it. A larger projector would not recover information the encoder never kept.

Why does a 576-token image matter to the serving cost of the language model?

  1. It does not, because image tokens skip the attention layers
  2. It matters only during training
  3. The tokens occupy context positions and KV-cache memory like text, here about 72 MiB for a Llama 3 8B shape, for the whole conversation
  4. It matters only if the image is stored in the database
Once projected, image vectors are ordinary positions in the sequence: attention reads them and each layer caches their keys and values (128 KiB per token for that shape, so 576 tokens is 72 MiB). They do not skip layers. The cost recurs at every decode step, so it is a serving matter, not only a training one.

A model correctly lists the objects in a kitchen photograph but often gets the count of cups wrong. Which is the most plausible cause?

  1. The tokeniser cannot represent numbers
  2. Contrastive caption training rewards naming what is present far more than counting or locating it, and counting needs detail that patches may blur
  3. The temperature was set too low during decoding
  4. The encoder was trained on too much data
Captions seldom state exact counts, so the pre-training signal does little to preserve them, and small repeated objects may share patches. The tokeniser handles number words normally. A decoding temperature affects variety and not what the encoder represents. More data would, if anything, help.

Mixture of Experts

A dense Transformer uses every weight for every token. A mixture-of-experts model holds many parallel MLPs and sends each token to only a few of them, so it can have several times more parameters for the same arithmetic per token. This chapter shows how the routing works, what it buys and the catches that come with it.

Why this matters

Many of the largest open-weight language models are now mixture-of-experts (MoE) models, and their model cards quote two parameter counts, "total" and "active", which mean very different things for your bill. Without this chapter you cannot tell whether a 100-billion-parameter MoE will run like a 100-billion or a 10-billion dense model, whether it fits on your hardware, or why its serving cost does not follow its FLOPs. After it you will be able to trace one token through a MoE layer, compute total and active parameters from a configuration, and name the four ways routing goes wrong: imbalance, dropped tokens, memory and communication.

The idea: capacity without compute

In chapter 16 most of a Transformer's parameters sat in the MLP of each block: 70% to 80% for the Llama 3 models. Every token goes through the whole MLP, so doubling its width doubles both the parameters and the arithmetic per token. A mixture of experts breaks that link. Replace the single MLP by E independent MLPs, called experts, and add a small router that looks at each token and picks k of them. Only the chosen experts run. Parameters grow with E; arithmetic per token grows with k.

The idea is old (Jacobs et al., 1991, introduced mixtures of experts) and was brought to deep language models by Shazeer et al. (2017, "Outrageously Large Neural Networks: The Sparsely-Gated Mixture-of-Experts Layer"). Its use in Transformers followed with GShard (Lepikhin et al., 2020) and the Switch Transformer (Fedus et al., 2021), whose abstract reports up to 7 times faster pre-training than the dense T5 baselines it compared against at the same computational resources. Mixtral 8x7B (Jiang et al., 2024) made the design familiar: 8 experts per layer, 2 chosen per token.

One token through a MoE layer

The router is a linear layer. For a token vector x of width C it computes E scores, x Wr with Wr of shape (C, E). The k highest scores pick the experts, and a softmax over just those k scores gives the gate weights. The layer's output is the gate-weighted sum of the chosen experts' outputs. The rest of the Transformer block is unchanged: attention is shared by all tokens, and the MoE layer replaces only the MLP.

The code below implements one such layer for a batch of tokens, groups tokens by expert so that each expert runs once on all the tokens sent to it, and checks the result against an obvious token-by-token loop. Shapes follow the course convention: x is (B, T, C), and routing flattens it to (B·T, C) because each token is routed on its own.

# A mixture-of-experts MLP layer in NumPy: a router picks the top-k of E experts for every token.
import numpy as np
rng = np.random.default_rng(0)
B, T, C, F, E, k = 2, 8, 16, 32, 8, 2                       # batch, tokens, width, expert hidden width, experts, chosen per token

Wr = rng.normal(0, .5, (C, E))                              # router: one score per expert
W1 = rng.normal(0, .2, (E, C, F)); W2 = rng.normal(0, .2, (E, F, C))   # E separate two-layer MLPs

def moe(x):
    flat = x.reshape(-1, C)                                  # (B*T, C): routing treats every token independently
    logits = flat @ Wr                                       # (B*T, E)
    top = np.argsort(-logits, axis=1)[:, :k]                 # (B*T, k): indices of the k best experts per token
    sel = np.take_along_axis(logits, top, axis=1)
    gate = np.exp(sel - sel.max(1, keepdims=True)); gate /= gate.sum(1, keepdims=True)   # softmax over the chosen k only
    out = np.zeros_like(flat)
    for e in range(E):                                       # each expert processes only the tokens routed to it
        rows, slot = np.where(top == e)
        if len(rows) == 0: continue
        h = np.maximum(flat[rows] @ W1[e], 0) @ W2[e]        # (n_e, C)
        out[rows] += gate[rows, slot][:, None] * h           # weight by the router's gate and add back
    return out.reshape(B, T, C), top

x = rng.normal(size=(B, T, C))
y, top = moe(x)
print("output shape:", y.shape)
print("tokens per expert:", np.bincount(top.ravel(), minlength=E), "(16 tokens x 2 choices = 32 assignments)")

per_expert = C * F + F * C
print(f"parameters: {E * per_expert:,} in experts + {C * E} in router; a token uses {k * per_expert:,} of them ({k}/{E} of the expert weights)")

# Check against a slow, obviously correct loop over tokens.
flat = x.reshape(-1, C); ref = np.zeros_like(flat)
for n in range(len(flat)):
    lg = flat[n] @ Wr; ids = np.argsort(-lg)[:k]; g = np.exp(lg[ids] - lg[ids].max()); g /= g.sum()
    for gi, e in zip(g, ids): ref[n] += gi * (np.maximum(flat[n] @ W1[e], 0) @ W2[e])
print("max |batched - per-token loop| =", np.abs(ref.reshape(B, T, C) - y).max())

Even in this tiny case the load is uneven: with 16 tokens and 2 choices each, one expert received 7 assignments and several only 2. That unevenness is the source of most of the trouble below.

Total versus active parameters

Two numbers describe a MoE model. Total parameters count every expert. Active parameters count what a single token uses: the shared parts (attention, embeddings, norms, the router) plus k experts per layer. Compute per token, in the 6ND rule of chapter 16, follows the active count. The script computes both for the Mixtral 8x7B configuration (32 layers, width 4,096, 32 query heads with 8 key/value heads, expert width 14,336, 8 experts, top 2, vocabulary 32,000), and then estimates how much of the weights one decode step must read.

# Total versus active parameters for a Mixtral-shaped model, and how many experts a decode batch touches.
C, L, H, KV, F, V, E, k = 4096, 32, 32, 8, 14336, 32000, 8, 2    # Mixtral 8x7B configuration
d = C // H
attn = 2 * C * C + 2 * C * KV * d
expert = 3 * C * F                                            # SwiGLU: gate, up, down
shared = L * (attn + C * E + 2 * C) + 2 * V * C + C           # attention, routers, norms, embeddings, output head
total = shared + L * E * expert
active = shared + L * k * expert
print(f"total parameters  {total/1e9:5.1f} B   (every expert counts)")
print(f"active per token  {active/1e9:5.1f} B   (shared parts + {k} of {E} experts)")
print(f"compute per token is that of a dense {active/1e9:.1f} B model; memory must hold {total/1e9:.1f} B -> {2*total/1e9:.0f} GB in bf16\n")

print("A decode step reads every expert that at least one sequence in the batch chose.")
print("Expected fraction of experts touched, if routing were uniform and independent:")
for batch in (1, 2, 4, 8, 16, 64):
    touched = E * (1 - (1 - k / E) ** batch)
    read = shared + L * touched * expert
    print(f"  batch {batch:>2}: {touched:4.1f} of {E} experts per layer, weights read {2*read/1e9:5.1f} GB per step")

The totals match what the Mixtral paper reports (about 47B total and 13B active), so the name "8x7B" is loose: the experts do not multiply a 7B model by eight, because attention and embeddings are shared. The compute of a token is that of a 12.9B dense model, but the 46.7B weights need about 93 GB in bf16, more than one 80 GB card holds (chapter 16). The second part of the output shows the catch for serving: one sequence touches only 2 of 8 experts per layer, but a batch of 8 sequences touches about 7, and a batch of 16 nearly all. The assumption of uniform, independent routing is an idealisation (real routers are neither), yet the direction is robust. At small batch a MoE reads a quarter of its weights per step, which is fast, but at the batch sizes that make serving economical it reads nearly all of them, so the saving in memory traffic that matched the saving in FLOPs disappears. MoE saves compute, and it saves memory bandwidth only when the batch is small.

The catches

1. Load balance and routing collapse

Nothing forces the router to spread tokens evenly. Early in training an expert that happens to receive more tokens gets trained more, becomes better, and receives still more: a rich-get-richer loop that can end with a few experts doing all the work and the others never used (routing collapse). The standard remedy, from the Switch Transformer paper, is an auxiliary load-balancing loss added to the language-modelling loss. For each expert i let fi be the fraction of tokens whose first choice is i and Pi the router's mean probability for i. The loss is proportional to E ∑ fi Pi, which equals 1 when all experts are used equally and grows towards E when one takes everything. A small coefficient on it nudges the router towards balance without dominating the main loss. DeepSeek-V3 (2024) reports an alternative that does without an auxiliary loss, adjusting a per-expert bias on the routing score according to recent load; its abstract describes this as an auxiliary-loss-free strategy for load balancing.

2. Capacity and dropped tokens

On accelerators, tensors have fixed shapes, so early MoE systems gave each expert a fixed capacity, a number of token slots equal to a capacity factor times the even share, and dropped tokens beyond it (they pass through the block's residual connection unchanged). A dropped token skips the MLP for that layer, which is quiet damage. The script below shows how a skewed router turns a capacity factor into lost tokens. The numbers use a made-up router with controllable skew, so read them as an illustration of the mechanism, not as typical rates.

# Load balancing: the auxiliary loss of the Switch Transformer, and tokens dropped when an expert is over capacity.
import numpy as np
rng = np.random.default_rng(1)
N, E, k = 4096, 8, 2                                           # tokens in the batch, experts, experts per token

def route(logits):
    p = np.exp(logits - logits.max(1, keepdims=True)); p /= p.sum(1, keepdims=True)   # router probabilities
    top = np.argsort(-logits, axis=1)[:, :k]
    return p, top

def aux_loss(p, top):
    f = np.bincount(top[:, 0], minlength=E) / len(top)         # f_i: fraction of tokens whose first choice is expert i
    P = p.mean(0)                                              # P_i: mean router probability for expert i
    return E * np.sum(f * P), f

def dropped(top, capacity_factor):
    cap = int(np.ceil(capacity_factor * N * k / E))            # slots per expert
    load = np.bincount(top.ravel(), minlength=E)
    return np.maximum(load - cap, 0).sum() / (N * k), cap

for name, favour in (("balanced router", 0.0), ("mildly skewed", 0.5), ("strongly skewed", 1.5)):
    bias = np.zeros(E); bias[0] = favour; bias[1] = favour / 2         # expert 0 (and a little of 1) is favoured
    p, top = route(rng.normal(size=(N, E)) + bias)
    loss, f = aux_loss(p, top)
    row = "  ".join(f"cf {cf}: {dropped(top, cf)[0]:5.1%}" for cf in (1.0, 1.25, 2.0))
    print(f"{name:<16} aux loss {loss:5.3f}  share of expert 0 {f[0]:5.1%}   dropped tokens -> {row}")
print("aux loss when every token picks expert 0 with probability 1:", E * 1.0 * 1.0, "; perfectly balanced:", 1.0)

A balanced router at capacity factor 1.0 already loses 0.6% of assignments, and a strongly skewed one loses nearly a third, still 10% at twice the even share. Raising the factor wastes memory and compute on padding. Newer systems avoid dropping by using variable-size batches of tokens per expert ("dropless" implementations, for example MegaBlocks, Gale et al., 2022), which moves the cost into more complex kernels.

3. Memory: all experts must be resident

The cost model above is the heart of it. Active parameters set the FLOPs, total parameters set the memory, and the weights of an unused expert are idle only for the tokens that did not choose it. A 47B-total MoE needs the memory of a 47B model. This is why MoE gives most of its benefit when memory is plentiful and compute or latency at scale is the constraint, for example in large-batch serving across several GPUs, and gives less to a single small GPU that cannot hold the weights.

4. Communication

When the experts of one layer are spread over several GPUs (expert parallelism), each token must travel to the GPU holding its chosen experts and its result must come back: two all-to-all exchanges per MoE layer. If routing is uneven, some GPUs wait for the busiest one. This communication is a first-class cost in MoE training and serving, treated in A3 chapter 3.

Common misconception

"An 8-expert model is eight models, and each expert specialises in a topic such as law or code." Experts are components of one network, trained together, and the router chooses them per token at every layer. Analyses of trained MoE models, including in the Mixtral paper, report that routing follows surface features such as syntax and position more than subject matter, so you cannot switch off the "medicine expert". Also, an "8x7B" name does not mean 56B parameters: attention and embeddings are shared.

Finer experts and shared experts

Newer designs change the unit of routing. DeepSeekMoE (Dai et al., 2024) splits each expert into several smaller ones and routes to more of them, so that combinations of knowledge can be selected more flexibly at the same compute, and reserves a few shared experts that every token uses, to hold common knowledge so that the routed experts can specialise. DeepSeek-V3, per its abstract, has 671 billion total and 37 billion activated parameters per token, a ratio of about 18 to 1, compared with about 3.6 to 1 for Mixtral.

State of play, October 2026

Mixture-of-experts is now a standard choice for large open-weight language models, and the gap between total and active parameters has grown with each generation. Besides DeepSeek-V3 (671B total, 37B active, from its technical report), third-party documentation for OpenAI's gpt-oss-120b lists about 117B total with 5.1B active, and Alibaba's Qwen3-Next-80B-A3B is described in its model card as 80B total with 3B active across 512 experts, 10 routed and one shared. I could not read every primary document for these two, so check the cards before quoting the figures. Routing details, expert counts and balancing methods differ between models and change every few months; the four catches in this chapter are the stable part.

Systems connection

A MoE layer is a sharded service with a router in front, and it inherits the problems of one: hot shards (an overloaded expert is a hot key), load balancing, and a fan-out of messages across the network that makes tail latency depend on the slowest participant (Reliability chapter 9 on tail latency at scale). The all-to-all pattern is the same communication primitive as a shuffle in a distributed data job. Moving a token to its expert instead of moving the expert's weights to the token is the old rule of shipping computation to the data, since a token is a few kilobytes and an expert is hundreds of megabytes.

Key takeaways

  • A MoE layer replaces one MLP by E experts and a router that sends each token to the top k. Parameters grow with E, compute per token with k.
  • Total parameters set memory; active parameters set FLOPs. Mixtral 8x7B has about 46.7B total and 12.9B active.
  • Experts are not topic specialists and "8x7B" is not 56B: attention and embeddings are shared.
  • The catches: load imbalance and routing collapse (fixed by an auxiliary loss or bias adjustment), dropped tokens at capacity, all experts resident in memory, and all-to-all communication.
  • At large batch a decode step touches nearly all experts, so MoE saves compute much more reliably than it saves memory traffic.

Check your understanding

A MoE model has 100B total parameters and 10B active. Which statement about running it is most accurate?

  1. It needs the memory of a 10B model and the compute of a 100B model
  2. It needs the memory and the compute of a 10B model
  3. It needs the memory of a 100B model and, per token, roughly the compute of a 10B model
  4. It needs the memory and the compute of a 100B model, since every expert is trained
All experts must be resident because any token may choose any of them, so memory follows the total. Only the chosen experts and the shared parts run for a token, so FLOPs follow the active count. The first option reverses the two. The last forgets that routing leaves most experts idle for any single token.

Early in training, a few experts receive most tokens and the rest are rarely used. What is the usual remedy?

  1. Add an auxiliary loss (or a bias adjustment) that rewards spreading tokens evenly across experts
  2. Increase k so that every token visits every expert
  3. Remove the router and assign tokens to experts at random
  4. Increase the capacity factor to 10 so that no token is dropped
The balancing loss is small enough not to dominate the language-modelling loss but removes the rich-get-richer loop. Setting k to E turns the layer into a dense one and discards the saving. A random assignment removes what the router learns. A large capacity factor stops dropping but does not fix imbalance and wastes memory on padding.

A team serves a MoE model with batches of 64 sequences and finds that decode speed is far below what the active parameter count suggested. What is the most likely reason?

  1. The router is too slow to compute
  2. The active parameters were counted incorrectly
  3. The attention layers are not shared between tokens
  4. With 64 sequences nearly every expert is chosen by someone, so each step reads almost all the weights
Decode is limited by weight reads. At large batch the union of chosen experts covers almost all of them, so memory traffic approaches that of the full model and the saving applies to FLOPs only. The router is a single small matrix. Active parameters set arithmetic, not bytes read at batch. Attention weights are shared by all tokens, which is the point of the design.

With fixed expert capacity, what happens to a token whose chosen expert is already full?

  1. It waits until the next training step
  2. It is dropped for that layer and passes through on the residual connection, skipping the MLP
  3. It is sent to a random idle expert and weighted the same
  4. The whole batch is recomputed with a higher capacity
The standard capacity scheme drops overflow tokens, so they skip that layer's MLP and keep only the residual stream. That silent loss is why balance and capacity factor matter. Tokens do not wait, are not silently rerouted with the same gate, and the batch is not recomputed.

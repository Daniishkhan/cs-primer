Parameters, FLOPs & Memory

Before anyone trains a model, three numbers decide whether the plan is real. The first is how many parameters it has. The second is how many floating-point operations the run needs. The third is how many bytes must sit in GPU memory while it happens. This chapter derives all three from the shape of a Transformer and checks them against published models. It ends with a calculator that tells you what fits on which card.

Why this matters

Chapters 09 to 15 built a Transformer and showed how to train and sample from it. Part 5 asks what changes when the model is large. The first change is that you can no longer find out by running it. A job that runs out of memory after twenty minutes on a rented cluster has already cost money. A job that needs three months instead of three weeks was a planning error. Resource accounting is the discipline of predicting both from the model's configuration, on paper, in a few lines of arithmetic. After this chapter you will be able to estimate parameters and training compute (the 6ND rule). You will be able to estimate memory for weights, optimiser state and activations, and the time and cost of a run. You will also be able to say why a plan will not fit before you launch it. Chapter 17 then asks how to keep such a run stable, and chapter 18 how to choose N and D in the first place.

Three questions before you press run

Suppose a team wants to train a 1-billion-parameter language model on 20 billion tokens, using one server with eight GPUs. Three questions come before any code is written.

  1. Will it fit? Training holds far more in memory than the weights. It also holds gradients, the optimiser's running averages and the intermediate values saved for the backward pass. If the total exceeds the card's memory, the job fails at the first step.
  2. How much work is it? Work is counted in FLOPs, floating-point operations (one addition or one multiplication each). The count depends on the parameters and the tokens. It is the same on any hardware.
  3. How long will it take, and what will it cost? Divide the work by the speed the hardware actually delivers, which is a fraction of its datasheet speed, then multiply by the price of the hours.

A note on spelling, because it causes real confusion. FLOPs with a lower-case s is a count of operations (work). FLOP/s, often written FLOPS (floating-point operations per second), is operations per second (speed). A GPU delivers FLOP/s, and a training run needs FLOPs. Dividing one by the other gives seconds.

All three answers start from one input, the shape of the model. The shape fixes the parameter count, and the parameter count drives everything else. We begin there.

Counting parameters

A parameter is one learned number. Chapter 10 counted them for a block of GPT (Generative Pre-trained Transformer) 2 and found about 12C² per layer. That block used multi-head attention with 4C² weights and a multi-layer perceptron (MLP) with 8C². Modern models differ in three ways that change the arithmetic, so the count needs a little more care.

  • Grouped-query attention (GQA), which chapter 19 develops. The query projection still has C × C weights. But the key and value projections produce only KV heads of width dk = C/h instead of h of them. With 8 key/value heads and 32 query heads, K and V together cost 2 · C · (8 dk) = C²/2 instead of 2C².
  • SwiGLU MLPs have three matrices (gate, up and down) of C × dff each, so 3C·dff weights, as chapter 10 showed.
  • Untied embeddings: a separate output head of V × C weights, in addition to the input table of V × C.

The function below counts all of this. The configurations are the ones Meta published for the Llama 3 family (Llama Team, 2024, "The Llama 3 Herd of Models", Table 3). The vocabulary is 128,256 in the released configuration. That is the 128,000 listed in the paper's table plus 256 reserved special tokens.

# Parameter count for a LLaMA-style decoder, with grouped-query attention (GQA).
def llama_params(C, L, H, KV, F, V, tied=False):
    d = C // H                                   # head width
    attn = C * C + 2 * C * (KV * d) + C * C      # W_q, W_k and W_v (K,V use KV heads), W_o
    mlp = 3 * C * F                              # SwiGLU: gate, up and down projections
    norms = 2 * C                                # two RMSNorm gains per block
    block = attn + mlp + norms
    embed = V * C * (1 if tied else 2)           # token table, plus a separate output head if untied
    return L * block + embed + C, block, embed   # + final RMSNorm gain

configs = {                                      # from Table 3 of the Llama 3 paper; V = 128,256 in the released config
    "Llama 3 8B":   dict(C=4096,  L=32,  H=32,  KV=8, F=14336, V=128256),
    "Llama 3 70B":  dict(C=8192,  L=80,  H=64,  KV=8, F=28672, V=128256),
    "Llama 3 405B": dict(C=16384, L=126, H=128, KV=8, F=53248, V=128256),
}
if __name__ == "__main__":
    print(f"{'model':<14}{'per block':>15}{'embeddings':>16}{'total':>18}  attn%  mlp%  emb%")
    for name, cfg in configs.items():
        total, block, embed = llama_params(**cfg)
        a = cfg['L'] * (2 * cfg['C']**2 + 2 * cfg['C'] * cfg['KV'] * (cfg['C'] // cfg['H']))
        m = cfg['L'] * 3 * cfg['C'] * cfg['F']
        print(f"{name:<14}{block:>15,}{embed:>16,}{total:>18,}  {a/total:5.1%} {m/total:5.1%} {embed/total:5.1%}")

The totals land on the published sizes: 8.03 billion, 70.6 billion and 405.9 billion, which the paper rounds to 8B, 70B and 405B. Names of models are rounded and sometimes loose. Counting from the configuration is the reliable way to know what you have. Two patterns are worth remembering.

  • The MLP dominates and keeps growing as a share. It is 70% of the 8B model and 81% of the 405B model. Attention is only 17% to 18% of the weights, even though attention is what the architecture is known for.
  • Embeddings matter only in small models. They are 13% of the 8B model (two tables of 525 million weights each) and 1% of the 405B model. At the scale of GPT-2 small the share was a third (chapter 10).

For back-of-envelope work, use the compact form N ≈ 12 L C² for a standard block with a 4C MLP and full-width keys and values. For the GQA plus SwiGLU shape above, when 8 of 32 heads carry keys and values, use N ≈ L · (2.5C² + 3C·dff). Add 2VC for embeddings and an untied head.

Common misconception

"The parameter count in a model's name is the number that goes into every formula." Papers disagree on what N is. Kaplan et al. (2020) count only non-embedding parameters, because they found that scaling laws are cleaner without the embedding tables. Other papers count everything. The two differ by 13% for Llama 3 8B and by 33% for GPT-2 small, which is enough to move a conclusion. Whenever you reuse a formula or a published constant, check which N it was fitted with. Chapter 18 returns to this.

Counting FLOPs: where 6ND comes from

A neural network spends almost all of its arithmetic in matrix multiplications. Multiplying an (m, k) matrix by a (k, n) matrix produces m × n outputs, each a sum of k products. That is k multiplications and k additions per output, so 2mkn FLOPs. This one formula, and nothing subtler, is the basis of the whole count.

The forward pass: 2 FLOPs per weight per token

Take a linear layer with weight matrix W of shape (Cin, Cout) applied to a batch of n tokens, so the input X is (n, Cin). The product costs 2 · n · Cin · Cout FLOPs. The weight matrix has Cin · Cout parameters, so the cost is 2 FLOPs per parameter per token. Every matrix in the model is some layer like this. So the forward pass over n tokens costs about 2 · N · n FLOPs, where N counts the weights that take part in matrix products.

The backward pass: twice the forward

Backpropagation (chapter 02) needs two matrix products per layer. For Y = X W with upstream gradient dY of shape (n, Cout):

  • the gradient for the weights is dW = XT dY, a (Cin, n) by (n, Cout) product, costing 2 · Cin · n · Cout;
  • the gradient for the input is dX = dY WT, an (n, Cout) by (Cout, Cin) product, costing the same.

Each has the same cost as the forward product, so the backward pass is 4 FLOPs per parameter per token. Forward plus backward is 2 + 4 = 6, and a run over D tokens costs

Plug in numbers. A 7-billion-parameter model is trained on 2 trillion tokens. The sustained speed of one GPU is an assumption.

The idea

  1. N = 7e9 parameters, D = 2e12 tokens, one GPU at 3e14 FLOP/s (assumed)
  2. per token: forward 2N, backward 4N, total 6N
  3. C ← 6N × D
  4. days on one GPU ← C ÷ speed ÷ 86,400
"""C = 6 N D for a 7-billion-parameter model on 2 trillion tokens."""

# ── 1. The model and the data ────────────────────────────────────────────
N = 7e9                           # parameters in matrix multiplies
D = 2e12                          # training tokens
SUSTAINED = 3e14                  # FLOP/s one GPU really delivers (assumed)

# ── 2. One token: 2 FLOPs per weight forward, 4 backward ─────────────────
forward = 2 * N
backward = 4 * N
per_token = forward + backward
print(f"forward  {forward:.2e} FLOPs per token")
print(f"backward {backward:.2e} FLOPs per token")
print(f"total    {per_token:.2e} FLOPs per token (= 6 N)")

# ── 3. Every token of the run ────────────────────────────────────────────

print(f"C = 6 N D = {C:.2e} FLOPs")

Kaplan et al. (2020) wrote this as C ≈ 6NBS for batch size B and S steps. Hoffmann et al. (2022) used it to turn FLOP budgets into model and data sizes. You can check the 6 on a real computation. The script below builds a small stack of MLP layers in NumPy. It wraps every matrix multiply in a counter that adds 2mkn. It runs a forward and a hand-written backward pass, and divides by N times the number of tokens.

# Count the FLOPs of a real forward and backward pass by instrumenting every matrix multiply.
import numpy as np
flops = 0
def mm(a, b):
    global flops
    flops += 2 * a.shape[0] * a.shape[1] * b.shape[1]       # one multiply and one add per term
    return a @ b

rng = np.random.default_rng(0)
tokens, C, H, layers = 512, 256, 1024, 6                    # 512 tokens; each layer is C -> H -> C (an MLP stack)
Ws = [(rng.normal(0, .02, (C, H)), rng.normal(0, .02, (H, C))) for _ in range(layers)]
n_params = sum(w1.size + w2.size for w1, w2 in Ws)

x = rng.normal(size=(tokens, C)); acts = []
for w1, w2 in Ws:                                           # forward
    h = np.maximum(mm(x, w1), 0); acts.append((x, h)); x = x + mm(h, w2)
fwd = flops
g = np.ones_like(x)                                         # pretend dLoss/dOutput = 1
for (w1, w2), (xin, h) in zip(reversed(Ws), reversed(acts)):  # backward
    dh = mm(g, w2.T) * (h > 0)                              # gradient w.r.t. the hidden activations
    mm(h.T, g); mm(xin.T, dh)                               # weight gradients dW2 and dW1
    g = g + mm(dh, w1.T)                                    # gradient w.r.t. the layer input
print(f"parameters {n_params:,}, tokens {tokens}")
print(f"forward  {fwd:>14,} FLOPs   2*N*tokens = {2*n_params*tokens:,}")
print(f"backward {flops-fwd:>14,} FLOPs   4*N*tokens = {4*n_params*tokens:,}")
print(f"total / (N*tokens) = {flops/(n_params*tokens):.2f}   (the 6 in 6ND)")
parameters 3,145,728, tokens 512
forward   3,221,225,472 FLOPs   2*N*tokens = 3,221,225,472
backward  6,442,450,944 FLOPs   4*N*tokens = 6,442,450,944
total / (N*tokens) = 6.00   (the 6 in 6ND)

The ratio is exactly 6. In a full Transformer it is very slightly less than 6 on the weights. The reason is that the first layer's input is an embedding lookup and needs no gradient with respect to its input. It is slightly more than 6 once you add the terms 6N leaves out. Those are the next two paragraphs.

What 6N leaves out

Three terms are ignored by the rule, and it is worth knowing when each one matters.

  • The attention scores. The query-key (QK) product QKT and the (softmax weights) V product have no weights, so they are not part of N. Yet they are matrix products. For one layer and one token with T positions in the context, each costs 2 · T · C forward, so 4TC together. Multiply by 3 for forward plus backward to get 12TC per layer. Over L layers the extra is 12 L C T FLOPs per token. This matches the correction in the PaLM paper (Chowdhery et al., 2022), which writes the per-token cost as 6N + 12 L H Q T, where H · Q = C. It grows with context length, whereas the 6N part does not.
  • The output head is a real matrix product (2CV forward) and belongs in N. The input embedding is a lookup and costs no FLOPs. This is why the "non-embedding" N is sometimes the better choice for FLOP counts.
  • Everything else (normalisation, softmax, activation functions, residual additions) is a few operations per number rather than a matrix product. Its FLOP count is tiny. As chapter 10 noted, such operations are slow for a different reason: they move many bytes for few FLOPs.

The script below applies the exact count to the three Llama 3 shapes at three context lengths and compares it with 6N. Like the PaLM formula, it counts full score matrices (T × T entries) rather than the causal half.

# Training FLOPs per token: the exact matmul count against the 6N rule of thumb.
from count import llama_params, configs

def train_flops_per_token(C, L, H, KV, F, V, T):
    d = C // H
    weights = L * (2 * C * C + 2 * C * KV * d + 3 * C * F) + C * V   # block weights + output head (a lookup costs no FLOPs)
    matmul = 6 * weights                    # 2 FLOPs per weight forward, 4 backward
    scores = 12 * L * C * T                 # QK^T and AV: 4*T*C forward per layer, times 3 for the backward pass
    return matmul, scores, weights

It is 20% off for the 8B model at 8,192 tokens. Second, at 128K tokens attention takes over: 82% of the arithmetic of the 8B shape goes into scores. The last line is the sanity check that makes the rule credible. 6 × 405.85 billion × 15.6 trillion is 3.80 × 1025, exactly the 3.8 × 1025 FLOPs that Meta reports for pre-training Llama 3 405B.

Go deeper optional: causal masks, recomputation and "hardware" FLOPs

A causal model only needs the lower triangle of each score matrix. So a kernel that skips the masked half does about half the score FLOPs. The PaLM count ignores this on purpose. It defines model FLOPs as the cost of the mathematical function the model computes, independent of how a particular implementation evaluates it. The ratio of observed model FLOPs per second to the hardware peak is the MFU (model FLOPs utilisation) that the next section uses.

The alternative is hardware FLOPs. These are whatever the chip actually executed, including work repeated by activation recomputation (see below). Recomputing the whole forward pass in the backward pass adds one more 2ND. So the hardware performs 8ND while the model FLOPs remain 6ND. Reports that quote a "utilisation" above the MFU are usually counting this repeated work. When comparing numbers from different papers, check which one is meant.

From FLOPs to time: peak speed, MFU and the bill

A GPU's headline number is its peak throughput. This is the FLOP/s it could sustain if every arithmetic unit were busy every cycle. For dense (no sparsity tricks) bf16 matrix multiplication, the datasheets from NVIDIA (the GPU maker) give about 312 TFLOP/s for the A100 and about 989 TFLOP/s for the H100 SXM. Here 1 TFLOP (a trillion floating-point operations) per second is 1012 FLOP/s, and the H100 SXM (the server-socket form of the card) is the fast variant. Beware the doubled figures in marketing tables. They assume 2:4 structured sparsity, which ordinary training does not use.

No real run reaches the peak. The fraction it does reach is the model FLOPs utilisation, MFU = (model FLOPs per second observed) / (peak FLOP/s). The PaLM paper introduced the term. It reported 46.2% for the 540B model on 6,144 chips of Google's TPU (tensor processing unit) v4 design. Against that, the PaLM authors computed 21.3% for GPT-3 and 32.5% for Gopher. Meta reported 38% to 43% for Llama 3 405B on up to 16,384 H100s, depending on the parallelism configuration. It noted the lower end for the run with 131,072-token sequences. Anything in the range 30% to 50% is good for a large distributed run. A first single-GPU implementation often lands lower. Karpathy's nanoGPT prints an MFU estimate during training for exactly this reason.

The gap exists for several reasons. Many operations are bound by memory bandwidth rather than arithmetic. GPUs spend time exchanging gradients and activations with each other. Pipelines have idle "bubbles". The input pipeline sometimes cannot keep up. Fixing these is performance engineering, and A3 covers it.

With MFU in hand, time is a division:

GPU-seconds = 6 · N · D / (peak FLOP/s × MFU)

and cost is GPU-hours times the hourly price. Prices are not a physical constant, so the script below uses clearly marked assumed rates. Substitute your own.

# From FLOPs to wall-clock time and GPU-hours: time = 6*N*D / (peak FLOP/s * MFU * number of GPUs).
PEAK = {"A100 (312 TFLOP/s bf16)": 312e12, "H100 SXM (989 TFLOP/s bf16)": 989e12}   # dense bf16, vendor datasheets

def plan(label, N, D, gpu, n_gpus, mfu, price=None):
    flops = 6 * N * D
    secs = flops / (PEAK[gpu] * mfu * n_gpus)
    gpu_hours = secs * n_gpus / 3600
    line = f"{label:<30} {flops:9.2e} FLOPs  {gpu_hours:>11,.0f} GPU-hours  {secs/86400:8.1f} days on {n_gpus:,} GPU{"s" if n_gpus > 1 else ""}"
    if price: line += f"  ~${gpu_hours*price:,.0f} at ${price}/GPU-h (assumed)"
    return line

State of play, October 2026

The peak figures above are for two GPU generations that are widely documented and still common in rented fleets: the A100 (2020) and the H100 (2022). Newer accelerators are in service, with more memory, faster memory and lower-precision tensor cores. They are quoted at several times the H100's peak for the narrowest number formats. But their dense bf16 peaks, their prices and the MFU that real code reaches on them change with every software release. Treat any table of GPU specifications, including this chapter's two numbers, as dated. Take current figures from the vendor's datasheet for the exact part. For MFU, measure your own code. The formulas do not change.

Memory I: weights, gradients and optimiser state

Compute decides how long a run takes, and memory decides whether it starts. GPU memory is a hard limit with no graceful degradation. When the total exceeds the card's capacity, the job stops with an out-of-memory error. Two kinds of memory use are separate and worth counting separately. This section covers the model states, which depend only on the parameter count. The next covers activations, which depend on the data.

Chapter 17 explains mixed-precision training in detail. For now we need only the standard recipe and its bookkeeping. During training with the AdamW optimiser (A0 chapter 10), each parameter has five numbers attached:

bf16 weight (2 bytes)
The copy used in the forward and backward matrix products. bf16 is a 16-bit floating-point format; chapter 17 says more.
bf16 gradient (2 bytes)
The output of backpropagation for this weight.
fp32 master weight (4 bytes)
A full-precision copy that the optimiser updates, because tiny updates would be lost in 16-bit numbers (chapter 17 demonstrates this).
Adam first moment m (4 bytes)
The running average of the gradient, kept in fp32.
Adam second moment v (4 bytes)
The running average of the squared gradient, kept in fp32.

That is 2 + 2 + 4 + 4 + 4 = 16 bytes per parameter. The ZeRO paper (Rajbhandari et al., 2020) states the same accounting as 2Ψ + 2Ψ + KΨ with K = 12 for mixed-precision Adam, where Ψ is the parameter count. The recipe is a baseline, not a law. The DeepSeek-V3 report, for example, keeps Adam's moments in bf16, which saves 4 bytes per parameter, while keeping master weights and accumulated gradients in fp32. Plain fp32 training with Adam also needs 16 bytes: 4 each for weights, gradients, m and v. So the mixed-precision recipe does not save memory on states. It saves time, because the matrix products run on fast 16-bit units.

Now the same script computes this for the 8B shape. It also adds the other two memory costs we will meet in a moment.

# What must sit in GPU memory: model states, activations (Korthikanti et al., 2022), and the inference KV cache.
from count import llama_params, configs
GB = 1e9

def states_bytes(n, w=2, g=2, master=4, m=4, v=4):
    """bf16 weights and gradients, fp32 master weights and the two Adam moments: 16 bytes per parameter."""
    return {k: n * b for k, b in (("weights", w), ("gradients", g), ("master copy", master), ("Adam m", m), ("Adam v", v))}

def act_bytes_per_layer(s, b, h, a, flash=False):
    """sbh(34 + 5as/h) bytes per layer for a GPT block in 16-bit with no recomputation."""
    return s * b * h * (34 + (0 if flash else 5 * a * s / h))

n = llama_params(**configs["Llama 3 8B"])[0]
st = states_bytes(n)
print(f"Llama 3 8B: {n/1e9:.2f}B parameters")
for k, v in st.items():
    print(f"  {k:<12}{v/GB:7.1f} GB")
print(f"  {'total':<12}{sum(st.values())/GB:7.1f} GB   ({sum(st.values())/n:.0f} bytes per parameter)")

The first block is the bill for the model states: 128.5 GB for an 8B model, which does not fit on an 80 GB card before a single activation exists. This is why the basic recipe cannot train even small-by-modern-standards models on one GPU. The remedies all reduce the states held per GPU. One is to shard the gradients, master weights and moments across many GPUs (ZeRO and FSDP (fully sharded data parallel); A3 chapter 03). Another is to train a small number of adapter weights instead (LoRA, A3 chapter 11). A third is to store the optimiser state in fewer bits. A rule of thumb to remember: training needs about 16 bytes per parameter, so an 80 GB card can hold the states of a model of at most 5 billion parameters, with nothing left over.

Analogy: a restaurant kitchen

Think of the three accounts as the pantry, the cooks and the counter. The pantry holds ingredients that must be on hand all night: the weights, the master copy and the optimiser's notes. That space is fixed by the menu (the parameter count). The cooks' hours are the FLOPs. They are fixed by how many dishes are ordered (tokens) and how complicated each one is, and they are independent of the building. The counter holds half-prepared dishes waiting to be finished: the activations. Counter space depends on how many orders you take at once (the batch) and how long each order is (the sequence). It empties as plates go out.

Where it breaks down: a kitchen can always add a table or send a dish out half-finished, but a GPU cannot. Memory is a hard wall, with nothing between "fits" and "crashes". And unlike cooking, deep-learning work can be traded for space on purpose. Recomputing a half-prepared dish later costs cooks' time but frees the counter, a trade the next section makes precise.

Memory II: activations

The forward pass produces many intermediate tensors, and the backward pass needs most of them. The gradient of a layer's weights depends on that layer's input (the formula dW = XT dY above). The gradient through a nonlinearity depends on its input. So the forward pass saves them. These saved tensors are the activations. Their memory grows layer by layer until the backward pass starts consuming them, as the stepper below shows.

Step through

Memory during one training step of a 3B-parameter model

  1. Between steps. The model states are resident all the time: 3 billion bf16 weights (6 GB), plus a 12 GB fp32 master copy and 12 GB each for Adam's two moments. 42 GB is spent before any data arrives.
  2. Forward, half way. Each layer saves the tensors its backward pass will need. Activation memory grows with every layer passed, and with batch size and sequence length.
  3. End of the forward pass. The loss is computed and activations reach their peak, 12 GB here. Nothing has been released yet, because the backward pass needs all of it.
  4. Backward, half way. Going from the last layer to the first, each layer's activations are consumed and freed while its gradients are produced. The total dips even though gradients now exist.
  5. Backward done. Activations are gone and the 6 GB of bf16 gradients are complete. With gradient accumulation they would stay for several microbatches.
  6. Optimiser step. AdamW updates the fp32 master copy from the gradients and its two moments, casts the result back to the bf16 weights, and the gradients are released. The cycle repeats. The step's peak (54 GB here) is set by the forward pass, not the optimiser.

How big are they? Korthikanti et al. (2022, "Reducing Activation Recomputation in Large Transformer Models") counted every tensor a standard GPT-style layer saves, for a model run in 16-bit numbers. Let the sequence length be s, the microbatch size b (the number of sequences processed in one forward and backward pass), the hidden width h, and the number of attention heads a. One layer then holds

s · b · h · (34 + 5 · a · s / h) bytes.

The first part, 34 s b h, is the sum of the inputs to each matrix multiply, the normalisations, the nonlinearity and the dropout masks. It is a few dozen times the size of the layer's input tensor (s × b × h numbers at 2 bytes each). It is linear in the sequence length and the batch size. The second part, 5 a s² b, is the attention matrices themselves. It holds one (s, s) table per head and per sequence in the batch, kept as scores, as softmax output and as a dropout mask. It is quadratic in sequence length, which is why long contexts were memory-bound before attention kernels changed.

Two techniques attack these terms, and both are standard.

  • Recomputation, also called gradient checkpointing or activation checkpointing (Chen et al., 2016, "Training Deep Nets with Sublinear Memory Cost"), keeps only each layer's input and recomputes everything else in the backward pass. Memory falls to about 2 s b h per layer (the saved input in 16-bit). The cost is one extra forward pass, which is about a third more compute (8ND instead of 6ND, as in the "Go deeper" box above).
  • Fused attention kernels such as FlashAttention (Dao et al., 2022; case study 5) never store the (s, s) tables. They recompute them in the backward pass, tile by tile, from Q, K and V. That removes the quadratic term and also reads far less from slow memory, so it is faster as well as smaller. Chapter 19 explains how it works.

The Korthikanti formula is for an MLP with the GELU (Gaussian error linear unit) nonlinearity at width 4h, and ordinary multi-head attention. A SwiGLU block with grouped-query attention saves somewhat different tensors. So use the formula as an estimate within tens of per cent, and measure when it matters. The second block of the memory.py output above applies it to the Llama 3 8B shape with a microbatch of one sequence. Look at the 4,096-token row to see why a naive 8B run fails. The standard formula wants 104 GB of activations per sequence, on top of the 128.5 GB of states. At 16,384 tokens it wants 1.4 TB. The "flash-style" column drops the quadratic term and grows only linearly (18 GB at 4,096). Full recomputation keeps about 1 GB. Real implementations choose in between. They recompute only the cheap, bulky parts (Korthikanti et al. call this selective recomputation), or recompute entire layers when memory is tight.

Two more facts about activations complete the picture.

  • The microbatch is the lever. Activation memory is proportional to the number of sequences processed at once, b. Suppose you want to train with a large global batch without holding all its activations. Run several microbatches one after another and add up their gradients before one optimiser step (gradient accumulation). Memory follows the microbatch, and the learning signal follows the global batch. The only cost is that the GPU does smaller matrix multiplications, which is less efficient.
  • The logits are big. The output layer produces a (b, s, V) tensor. With V = 128,256 and s = 8,192, one sequence's logits are over 1 billion numbers. That is about 2 GB in 16-bit, and more after the softmax in fp32. This is why the end of the model sometimes needs its own care (chunked loss computation). It is also why vocabulary size has a memory cost as well as a parameter cost.

Systems connection

These accounts are the same ones you use to size any system, applied to a new resource. The FLOP and byte counts mirror ordinary capacity estimation: work per request times requests, divided by what one machine delivers. MFU is a utilisation figure, like CPU utilisation. A low one tells you to profile rather than to buy more machines. The gap between datasheet and delivered FLOP/s is the same gap between a network's line rate and its goodput. And an out-of-memory crash at step 1 is the cheapest failure you will ever have. Design the run so that all the failures of this kind happen in the first minute (run one step at the largest planned microbatch first), not on day three.

Does it fit? Putting the accounts together

The calculator combines the pieces. It uses the parameter formula for a LLaMA-style shape. The width is C, and the heads, hidden width and GQA ratio are fixed to the Llama 3 pattern: C/128 heads, 8 key/value heads, dff about 3.5C. It uses 16 bytes per parameter for the states. It uses the Korthikanti formula (or the recomputation and flash variants) for activations. It uses 6ND plus the score term for compute. The presets are GPT-2 small's width and depth with the modern block, a 1B-class model, and the Llama 3 8B and 70B shapes. It is an estimate that ignores framework overhead, memory fragmentation, communication buffers and the CUDA (NVIDIA's GPU programming platform) context. Together these typically take a few GB. So treat "fits with 3 GB to spare" as "probably not".

Worked example: a 1B model on one 24 GB card

Take the question that opened the chapter, but on a single 24 GB consumer-class card. A 1B-class model has about 1.1 billion parameters, so the states take 16 × 1.1 = 17.6 GB. That leaves about 6 GB for activations, the CUDA context, the data loader and fragmentation. Take a sequence of 2,048 tokens and the fused attention kernel. Activations then cost roughly 34 · 2048 · 2048 · 24 ≈ 3.4 GB per sequence for a 24-layer, width-2,048 model. So a microbatch of one fits and a microbatch of four does not. You would use microbatch 1 with gradient accumulation. Compute for the plan: 6 × 1.1 × 109 × 20 × 109 is 1.3 × 1020 FLOPs. At a card delivering (say) 60 TFLOP/s of useful bf16, that is about 25 days. The same plan on eight H100s with 40% MFU takes under half a day, as the budget script showed. Which to choose depends on money, not feasibility, and that is the point of doing the arithmetic first.

Inference uses the same accounts with different weights

Serving drops the gradients and optimiser state. So the states shrink to the weights alone: 2 bytes per parameter in bf16 (16 GB for the 8B model), or about half a byte in 4-bit quantisation (A3 chapter 19). A new item appears: the KV cache (key-value cache). It holds the keys and values of every earlier token that attention reads when generating the next one. The last lines of the memory output give its size for the 8B shape: 2 (K and V) × 32 layers × 8 key/value heads × 128 head width × 2 bytes = 131,072 bytes, or 128 KiB, per token. An 8,192-token conversation holds about 1 GB of cache. That is also why grouped-query attention exists. With 32 key/value heads the cache would be four times larger. Finally, generating a token reads every weight once. So at 3.35 TB/s of memory bandwidth, an H100 cannot produce more than about 209 tokens per second for one sequence of the 8B model, whatever its FLOP/s. Decoding is limited by bytes, training by FLOPs. A3 chapter 18 builds on exactly this.

To check your estimate against reality on a GPU, use the peak allocation that PyTorch reports for a step. The listing is what you would add to a training loop. It is not run here. It would print the peak in gigabytes, which you should compare to the calculator's total and expect to be somewhat higher.

import torch

torch.cuda.reset_peak_memory_stats()
loss = model(x, y)          # forward: activations accumulate
loss.backward()             # backward: activations freed, gradients appear
optimizer.step()            # optimiser state is allocated on the first step
optimizer.zero_grad(set_to_none=True)
print(f"peak allocated: {torch.cuda.max_memory_allocated() / 1e9:.1f} GB")

Note that the optimiser's moments are created lazily on the first step(). So a run can pass the first forward and backward passes and still run out of memory when the optimiser allocates its state. Measure after the first complete step, not after the first backward pass.

Key takeaways

  • Plan a run with three accounts: parameters (counted from shapes), FLOPs (about 6ND) and bytes (about 16 per parameter of model state, plus activations). Do it before you launch.
  • A matrix product costs 2mkn FLOPs. The forward pass is 2 FLOPs per weight per token and the backward pass 4, giving 6ND. Llama 3 405B on 15.6T tokens gives 3.8 × 1025, as published.
  • 6N omits the attention-score products, 12 L C T FLOPs per token. These are small at short context and dominant at very long context. Check which N (with or without embeddings) any formula uses.
  • Time is FLOPs divided by (peak × MFU). Real large runs reach about 30% to 50% MFU. A bad estimate of MFU is the largest error in a schedule.
  • Mixed-precision AdamW keeps 2 + 2 + 4 + 4 + 4 = 16 bytes per parameter, so an 80 GB GPU cannot hold the states of a model beyond about 5B parameters without sharding.
  • Activations scale with batch, sequence and depth, and have a quadratic attention term that fused kernels remove. Recomputation trades about a third more compute for most of the rest.
  • Inference needs only 2 bytes per parameter plus the KV cache, and decode speed is limited by memory bandwidth, not FLOP/s.

A dense Transformer with 7 billion non-embedding parameters is trained on 2 trillion tokens. Which is closest to the training compute?

  1. 1.4 × 1022 FLOPs
  2. 8.4 × 1022 FLOPs
  3. 1.4 × 1023 FLOPs

6ND = 6 × 7 × 109 × 2 × 1012 = 8.4 × 1022. The first option is 2ND, the forward pass alone, which forgets the backward pass. The third is 10ND, a slip in the multiplication. The last is off by a factor of one hundred.

You want to fine-tune a 3-billion-parameter model with AdamW in mixed precision on one 40 GB GPU. Ignoring activations, what do the model states need, and does it fit?

  1. 6 GB, so it fits easily
  2. 12 GB, so it fits
  3. 24 GB, so it fits with room for activations
  4. 48 GB, so it does not fit even before activations
Mixed-precision AdamW needs 16 bytes per parameter: 3 × 109 × 16 = 48 GB, more than the card holds. 6 GB is the bf16 weights alone, which is all that inference needs. 12 GB counts only the fp32 master copy. 24 GB counts weights, gradients and the master copy but forgets Adam's two moments.

Training a model at a context length of 128K tokens costs much more than 6ND says. Which term accounts for the difference?

  1. The attention score and weighting products, about 12 L C T FLOPs per token, which have no weights and grow with context length
  2. The embedding lookup, which grows with the vocabulary
  3. The optimiser update, which grows with the sequence length
  4. The normalisation layers, which have more weights at longer contexts
Scores and weighted sums are matrix products between activations, so they are missing from N but cost 4TC per layer per token forward, and three times that with the backward pass. They scale with T. An embedding lookup costs no FLOPs, the optimiser acts once per step on the parameters whatever T is, and normalisation weights do not depend on context length.

A run on 1,024 GPUs is rated at 989 TFLOP/s per GPU in bf16. It measures 400 TFLOP/s of model FLOPs per GPU. What is the MFU, and what does it tell you?

  1. About 250%, so the cluster is faster than its specification
  2. About 40% of the cluster is idle at any moment
  3. About 40%: the run turns 40% of the peak arithmetic into useful model FLOPs, which is a good figure for a large distributed run
  4. About 40%, which means 60% of the model is not being trained
MFU = 400 / 989, about 0.40. It is a fraction of delivered useful arithmetic to peak, not a count of idle machines (the GPUs may be busy with communication or memory-bound kernels, which is where the missing 60% goes). Inverted, 989/400, it would exceed 100%, which should have flagged the mistake. Nothing about the fraction of the model being trained follows from it.

A training job reaches the first backward pass without error. It then crashes with an out-of-memory error at the first optimizer.step(). What is the most likely reason?

  1. The learning rate is too high and the weights overflowed
  2. The optimiser allocates its moment buffers on the first step, so the states for m and v did not exist when memory was last measured
  3. The backward pass has not yet released the weights
  4. The dataset is larger than GPU memory
Adam's two moments are allocated the first time the optimiser runs, which adds 8 bytes per parameter (in fp32) that earlier steps did not use. A high learning rate causes NaNs or loss spikes (chapter 17), not allocation errors. Weights are never released during backward. The dataset is streamed from disk or CPU memory, not held on the GPU.

You enable activation recomputation for every layer. Which description of the effect is accurate?

  1. Activation memory falls and compute is unchanged
  2. Activation memory rises because recomputed tensors must also be stored
  3. Activation memory falls sharply and compute rises by about one extra forward pass, roughly a third more in total
  4. Model-state memory falls because the gradients are recomputed too
Recomputation keeps only each layer's input and rebuilds the other saved tensors during the backward pass, which costs another forward pass (2ND on top of 6ND). The gradients and optimiser state are not affected, so the model-state memory stays at 16 bytes per parameter. Nothing extra is stored, which rules out the second option, and the first ignores the cost of repeating the work.

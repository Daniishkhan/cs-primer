Tokenisation

A language model never sees text. It sees integers, and a program called a tokeniser decides which integers. This chapter builds byte-pair encoding from scratch, measures what real tokenisers do to English, Hindi and code, explains how the choice of vocabulary size trades sequence length against table size, and catalogues the strange bugs that appear when the cutting of text into pieces goes wrong.

Why this matters

Tokenisation is the one stage of the pipeline that is not learned by gradient descent, and it is easy to forget because it sits before the model. It sets what you pay (APIs bill per token), how much fits in the context window, how fast generation is, how well the model handles numbers, code and non-English languages, and which strings can make it misbehave. Many puzzling behaviours of language models, such as failing to count letters or doing arithmetic worse than expected, begin here. After this chapter you can implement byte-pair encoding, explain why GPT-style tokenisers split text with a regular expression first, estimate how a vocabulary size changes sequence length and parameter count, and recognise the standard tokeniser bugs: whitespace sensitivity, digit chunking, unequal cost across languages, split UTF-8 characters, glitch tokens, special-token injection and train/serve mismatch. It follows the spirit of Karpathy's minbpe and "Let's build the GPT Tokenizer"; the code and measurements here are my own.

From text to integers

Chapter 12 used the simplest possible scheme: one token per character, a vocabulary of 65. That is a tokeniser: a function that converts a string into a list of integer ids (encoding) and a second function that converts ids back into a string (decoding). The model sees only the ids. Its first layer is a lookup table with one learned vector per id (chapter 06), and its last layer produces one score per id. So the tokeniser fixes the model's entire vocabulary of inputs and outputs, and fixes it for the life of the model: changing the tokeniser changes the meaning of every row of both tables, which is why a trained model cannot be moved to a new tokeniser without retraining or serious surgery.

Three candidates

What should one token be? There are three natural answers, each with a clear failure.

  • Characters (or bytes). A tiny vocabulary and no unknown inputs, but long sequences: a typical English word is about five characters, so a page of text is five times longer than if each word were one token. Attention cost grows with the square of the sequence length (chapter 09), and every extra token is another step of generation. The model must also spend layers assembling letters into words before it can reason about them.
  • Words. Short sequences, but a huge vocabulary and a hard edge. Any word not in the vocabulary (a name, a typo, "unfollowable", a new product) becomes an unknown token and its identity is lost. Languages with rich word forms or no spaces between words fare worse.
  • Subwords. Common words are single tokens and rare words are assembled from pieces, down to single bytes if necessary. Vocabulary is moderate, sequences are moderate, nothing is ever unknown. Every major language model uses some version of this.

The script below measures all three on Shakespeare, training each vocabulary on the first 90% of the text and testing on the last 10% (the byte-pair encoder is the one built in this chapter).

import re

Characters give 111,540 tokens for the held-out text with a 65-entry vocabulary. Words give 26,844 tokens, four times shorter, but the vocabulary has grown to 12,569 entries and, crucially, 4.6% of the word tokens in the held-out text were never seen in training: roughly one in twenty-two words would be mapped to "unknown" and lose its identity. The subword scheme with only 768 entries produces sequences twice as short as characters and has no unknowns at all, because anything it cannot merge falls back to bytes. That last property is why subword tokenisers are universal.

Bytes and UTF-8

"No unknowns" needs a precise base alphabet. Unicode defines over a hundred thousand characters, too many to be a base vocabulary and too open-ended (new emoji appear every year). The answer used since GPT-2 is to work on bytes. UTF-8 is the encoding that turns any Unicode text into a sequence of bytes: ASCII characters take one byte, accented letters usually two, most Chinese, Japanese and Korean characters three, and emoji four. Every string in every language is then a sequence over just 256 symbols, so a byte-level vocabulary can encode anything.

"cafe" is four bytes but "café" is five, because "é" is the two bytes 195 and 169. The three Japanese characters take nine bytes and the emoji four. Two consequences follow. A tokeniser that merges bytes may produce tokens that are not valid text on their own (the last line shows half an emoji decoding to the replacement character �), a fact that causes a real bug later in the chapter. And text in a script that UTF-8 encodes with more bytes starts at a disadvantage: before any merging, Japanese or Hindi text is two to three times longer in bytes than the same meaning in English.

Byte-pair encoding

Byte-pair encoding (BPE) was invented as a data-compression method (Gage, 1994) and brought to neural machine translation by Sennrich, Haddow and Birch (2016, "Neural Machine Translation of Rare Words with Subword Units"). It builds a vocabulary by a greedy loop.

  1. Start with every byte (or character) as its own token, and the training text as a sequence of such tokens.
  2. Count every pair of adjacent tokens in the text.
  3. Take the most frequent pair, give it a new token id, and replace every occurrence of the pair by that token. Record the merge.
  4. Repeat from step 2 until the vocabulary has reached the size you want: the base alphabet plus the number of merges.

The result is an ordered merge table. To encode a new string, start from its bytes and apply the merges in the order they were learned; to decode, expand each token back into the bytes it stands for. Step through the algorithm on a four-word corpus, the standard example from Sennrich et al.

Step through

Learning four merges from four words

  1. Start from characters. The corpus is low (5 times), lower (2), newest (6) and widest (3). Each word is a row of single-character tokens. The vocabulary is the 10 distinct letters.
  2. Count adjacent pairs. "es" occurs 9 times (newest 6, widest 3) and so does "st"; "we" occurs 8 times and "lo" 7. The most frequent pair wins; ties here are broken alphabetically, which is an arbitrary but deterministic rule.
  3. Merge 1: e + s → es. Every "e s" in the corpus becomes one token. The vocabulary has a new entry, and "st" is no longer a pair in newest or widest, because the s is now inside "es".
  4. Merge 2: es + t → est. Now "est" is a token: a common English ending, learned from nothing but pair frequencies.
  5. Merge 3: l + o → lo. The counts are recomputed after each merge; "lo" (7 times) is now the most frequent pair.
  6. Merge 4: lo + w → low. The whole word "low" has become a single token, and "lower" is "low", "e", "r". Frequent strings become single tokens; rare ones stay in pieces.
  7. An unseen word. "lowest" never appeared in training. Applying the merges in order gives "low" and "est": two meaningful pieces, no unknown token. This is how a fixed vocabulary covers an open set of words.

Implementing it

The functions below are the whole algorithm, in about fifty lines of standard-library Python. train_bpe counts words once and works on distinct words with their frequencies, so each merge costs one pass over the distinct words, not over the million characters. encode splits text into words, turns each into bytes and repeatedly applies the earliest-learned merge that is present. decode concatenates the bytes of each token and decodes UTF-8. The regular expression SPLIT is explained in the next section.

import re, time
from collections import Counter

# Pre-tokenisation: split text into words (with their leading space), digit runs, punctuation runs, spaces.
SPLIT = re.compile(r" ?[^\W\d_]+| ?\d+| ?[^\s\w]+|\s+(?!\S)|\s+")

def merge_pair(ids, pair, new):
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i + 1]) == pair:
            out.append(new); i += 2
        else:
            out.append(ids[i]); i += 1
    return out

def train_bpe(text, n_merges):
    """Learn merges. Words are counted once, so each merge costs one pass over the distinct words."""
    words = Counter(SPLIT.findall(text))
    seqs = {w: list(w.encode("utf-8")) for w in words}      # each word as a list of byte values
    merges = {}                                              # (id, id) -> new id, in the order learned
    for k in range(n_merges):
        pairs = Counter()
        for w, ids in seqs.items():
            for a, b in zip(ids, ids[1:]):
                pairs[(a, b)] += words[w]
        if not pairs: break
        best = max(pairs, key=lambda pr: (pairs[pr], -pr[0], -pr[1]))   # most frequent; ties by smaller ids
        merges[best] = 256 + k
        for w in seqs:
            seqs[w] = merge_pair(seqs[w], best, 256 + k)
    return merges

def encode(text, merges):
    out = []
    for w in SPLIT.findall(text):
        ids = list(w.encode("utf-8"))
        while len(ids) > 1:
            pairs = set(zip(ids, ids[1:]))
            best = min(pairs, key=lambda pr: merges.get(pr, float("inf")))   # earliest-learned merge present
            if best not in merges: break
            ids = merge_pair(ids, best, merges[best])
        out += ids
    return out

def vocab_bytes(merges):
    vb = {i: bytes([i]) for i in range(256)}
    for (a, b), new in merges.items():
        vb[new] = vb[a] + vb[b]                              # a merged token is the concatenation of its parts
    return vb

def decode(ids, merges):
    vb = vocab_bytes(merges)
    return b"".join(vb[i] for i in ids).decode("utf-8", errors="replace")

Cutting text before merging



The loop above would happily learn merges that cross word boundaries, producing a token for "dog." or for " of the". GPT-2 prevented this by splitting the text first with a pre-tokenisation regular expression and running BPE inside each piece (Radford et al., 2019). The original GPT-2 pattern, as given in the tiktoken source, is:


's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+


Read it as a list of alternatives: common English contractions ('s, 'll and so on); a run of letters (\p{L} is any Unicode letter) with an optional leading space; a run of digits with an optional leading space; a run of anything else (punctuation, symbols) with an optional leading space; and whitespace. The consequence is that a word and its leading space are one unit, " the", and that letters, digits and punctuation never merge with each other. The version in this chapter's bpe.py is a simplified copy using Python's standard re module, which lacks \p{L}, so letters are written as [^\W\d_].



Later tokenisers changed the pattern, and the changes are instructive. The cl100k pattern used by GPT-4-era models caps digit runs at three, \p{N}{1,3}, so that numbers are chunked from the left in groups of three, makes the contractions case-insensitive, and lets newlines stay attached to punctuation. The o200k pattern splits words by capitalisation pattern. Each change targets a measured weakness: long digit tokens made arithmetic erratic (the 50k vocabulary has 994 digit-only tokens, one of them 16 digits long), and runs of whitespace and newlines in code wasted tokens. Karpathy's lecture and the minbpe repository walk through these patterns line by line.




  
Analogy: a stenographer's abbreviations

  
A court stenographer does not type letters. They have a stock of chords for common words and endings, and spell out rare names a syllable at a time. The stock was built by noticing what comes up most often, and it is fixed before the trial. A BPE vocabulary is the same: frequent strings get a single chord, and anything unusual is spelled out in smaller pieces, in the worst case letter by letter.

  
Where it breaks down: a stenographer sees the words and chooses chords knowingly. A model never sees the letters inside a token at all, only its id; the learned vector for " strawberry"-like tokens must carry spelling information indirectly, or not at all. And a stenographer's chord book is adjusted for each trial, while a model's vocabulary is frozen the day it is trained.

Three things are visible. English is cheap in all three, 17 tokens for 66 bytes, about four bytes per token. The older GPT-2 vocabulary penalises every other language, most for scripts that need three bytes per character (Hindi: 82 tokens). And the newest vocabulary, with twice as many entries (200,019 against 100,277) and multilingual training text, brings all seven languages within 14 to 17 tokens. This is not a curiosity. How big should the vocabulary be?



A bigger vocabulary shortens sequences but costs in three places. The embedding table and, unless tied, the output head each hold V×C numbers. The output softmax at every position runs over V entries, so the final matrix multiplication costs V×C multiply-adds per generated token. And rare tokens get few training examples: an entry seen a hundred times in a trillion tokens has a barely-trained embedding, the seed of the glitch-token problem below. For a 124-million-parameter model, a 200k vocabulary at width 768 would put 154 million weights in the embedding alone, more than the rest of the model; for a 7-billion-parameter model at width 4,096 the same table is 819 million, about 12% (and doubled if the head is untied). That is why small models keep small vocabularies and large models can afford large ones. A related practical detail: nanoGPT pads GPT-2's 50,257 entries to 50,304, a multiple of 64, because GPU matrix multiplications run faster on dimensions that divide evenly into the hardware's tile sizes. The padding rows are never used.



Vocabulary sizes have drifted upward. LLaMA 1 and 2 used 32,000 SentencePiece tokens; GPT-2 used 50,257 and GPT-4-era models about 100,000. The Llama 3 paper (2024) reports a 128,000-token vocabulary made of 100,000 tokens from the tiktoken tokeniser plus 28,000 added for non-English languages, which raised the compression of a sample of English text from 3.17 to 3.94 characters per token, so that "the model can read more text for the same training compute". Tao et al. (2024, "Scaling Laws with Vocabulary") trained models from 33 million to 3 billion parameters and argued that the best vocabulary grows with the compute budget and that many models use vocabularies that are too small; their fitted estimate for Llama 2 70B was at least 216,000. I treat that as a research result, not a rule.




  
State of play, October 2026

  
Byte-level BPE with a regular-expression pre-tokeniser, vocabularies between about 100,000 and 260,000 entries, and a handful of special tokens for chat and tool formats, is the default for frontier and open models. I measured the three public OpenAI encodings above; I did not examine the tokenisers of closed models, which are usually undocumented. Research on tokeniser-free models continues: ByT5 (Xue et al., 2021) trains directly on bytes, and the Byte Latent Transformer (Pagnoni et al., 2024) groups bytes into dynamically sized patches based on how predictable the next byte is, reporting parity with token-based models at the scale it tested. Neither has displaced subword vocabularies in widely used systems as far as I can verify. Check a model's own documentation for its tokeniser before you reuse any number from this chapter.





Other ways to choose the pieces



    
  
  • WordPiece (Schuster and Nakajima, 2012, used by BERT) also grows a vocabulary by merging, but chooses the merge that most increases the likelihood of the training text under a simple language model, rather than the most frequent pair, and marks word-internal pieces with a prefix (##ing).
    • 
  
  • Unigram language model (Kudo, 2018, "Subword Regularization") works the other way: start with a very large candidate vocabulary and repeatedly remove the pieces whose loss hurts least. It can also give several segmentations of the same word with probabilities, which can be sampled during training as a regulariser.
    • 
  
  • SentencePiece (Kudo and Richardson, 2018) is a library that implements BPE and unigram training directly on raw text, treating the space as an ordinary symbol (written ▁), so that no language-specific pre-tokenisation is needed. It is the tokeniser of the LLaMA 1 and 2 models, with a byte fallback so that nothing is unknown.
    • 
  
  • Bytes and patches, as above: no learned vocabulary at all, at the price of sequences three to four times longer unless the architecture compresses them.
    • 




The bugs tokenisers cause



The same cutting rules that make a tokeniser compact also create sharp edges. The scripts below exercise them on the real encodings. Each paragraph names the failure and what to do about it.



Whitespace and case change the tokens

Whitespace is part of the token. "hello", " hello", "Hello" and " Hello" are four different ids (15339, 24748, 9906, 22691), and "HELLO" is two tokens. A prompt that ends with a trailing space, as in "The capital of France is ", forces the model to continue from a token (the bare space) that in training is almost always followed by something unusual, because normal text puts the space at the start of the next word. The results can be noticeably worse. Never end a completion prompt in a space.



Numbers are chunked, not parsed. The 50k vocabulary splits 1234567 as 123, 45, 67, an irregular pattern, while the later ones split from the left in threes: 123, 456, 7. The date 2024-10-14 becomes 202, 4, -, 10, -, 14: the year itself is cut in two. A model must learn arithmetic over such chunks, and digit alignment differs between numbers of different lengths, which helps explain why large-number arithmetic and exact digit manipulation are harder for models than their other skills suggest. Some model families avoid this by splitting every digit into its own token.



The model does not see letters. "strawberry" is three tokens (str, aw, berry in cl100k) and the model only gets three ids. Counting the r's means recalling the spelling of tokens it has never been shown as letters. Questions about letters in words are therefore a test of memorised spelling, not of reading, and failing them says little about reasoning. If a task depends on characters (anagrams, rhymes, exact string edits), have the model spell the word out first, or use code.



Glitch tokens. The last lines show that " SolidGoldMagikarp" is a single token (43453) in the GPT-2 vocabulary but five ordinary pieces in cl100k. A token like that exists because, as Rumbelow and Watkins reported in 2023, the text the tokeniser was trained on (which included a frequently repeated Reddit username) was evidently different from the text the model was trained on, where the string hardly appeared. Its embedding row was therefore barely trained, and prompts containing it produced bizarre outputs in GPT-3-era models. Case study 6 (SolidGoldMagikarp: Glitch Tokens) covers it in detail. The general lesson: a tokeniser must be trained on data that matches the model's training data, and rarely-seen tokens should be audited, for example by finding vocabulary entries whose embeddings stayed near their initial values.



Code indentation. The four-line Python function costs 29 tokens in the GPT-2 vocabulary, because each space of indentation was a separate token, and 18 in cl100k, which has tokens for runs of spaces. Replacing the indentation by tabs brings both lower (20 and 16). Whitespace handling is one of the main improvements of the later vocabularies, and a reason to keep a tokeniser consistent with the data the model was trained on.

A character can be split across tokens. The emoji is four bytes but the cl100k vocabulary has no token for it: it is encoded as two tokens, the first holding the bytes F0 9F and the second 99 82. Decoding either token alone gives garbage (the replacement character), but decoding both gives the emoji. The Japanese text splits characters across tokens as well (the third character is cut between \xe8\xaa and \x9e). A streaming server that decodes and sends each new token immediately will therefore sometimes emit invalid UTF-8. The fix is to buffer bytes until they form complete characters, which is what well-written streaming clients do (for the transport side, see Zero to Systems, networking chapter 10).



Visually identical strings tokenise differently. "café" typed with a single precomposed é is 2 tokens; typed as "e" plus a combining accent (Unicode normal form NFD) it is 3 tokens with different ids, although it looks identical and means the same. If your input pipeline sometimes normalises text and sometimes does not, the model sees two different inputs for the same word. Pick one normal form (usually NFC), and apply it everywhere, in training data, prompts and retrieval indexes.



Special tokens are an injection surface. Vocabularies reserve special tokens such as <|endoftext|> (id 100257 in cl100k) that mark document boundaries or chat turns. If user text containing the literal string <|endoftext|> is tokenised with special-token parsing enabled, it becomes the single control token and the model sees an end-of-document marker the user typed. tiktoken refuses by default (the first line of output: "Encountered text corresponding to disallowed special token") and offers two explicit options: allowed_special="all" parses it as the control token (id 100257), and disallowed_special=() treats it as ordinary text (it then costs eight tokens). The safe pattern is to encode untrusted text as ordinary text and insert control tokens only from your own code. This is injection in the sense of Security chapter 09: data crossing into the control channel.

Common misconception

  
"Tokens are words" or, in the other direction, "the model reads letters." Neither holds. A token is a frequency-driven fragment: sometimes a whole word with its space, sometimes a few letters, sometimes half a character. The model only ever receives the id. It can learn that " strawberry" contains certain letters in the same way it learns any other fact about a token, from text that spells it out, but nothing in the architecture exposes the characters. The corollary for engineering is that "how many tokens is this?" has no answer without naming the tokeniser, and that token counts from one model family cannot be used to budget another.

Systems connection

  
Tokens are the unit of metering, capacity and latency in language-model services: prices are quoted per million tokens, the context window is a token budget, and generation time is roughly proportional to output tokens (A3 chapter 22). A systems engineer therefore treats the tokeniser like any other versioned dependency: a new version changes counts, costs and the content that fits in a request, so counts should be measured with the exact tokeniser of the deployed model and logged per request. The bugs above are classic systems bugs wearing new clothes: a text-encoding mismatch (the cousin of the UTF-8 and schema problems in Data chapter 03), a streaming protocol that must respect character boundaries, and a trust-boundary failure where untrusted data reaches a control channel. And the interface contract that matters most is invisible: the model's weights are only valid with the tokeniser they were trained with, so the two must be released, versioned and rolled back together.






  
Key takeaways

  
    
    
  • A tokeniser maps text to integer ids and back. It is trained before the model, frozen, and tied to the model's embedding and output tables for good.
    • 
    
  • Characters give long sequences, words give unknown tokens, and subwords give moderate length with no unknowns. Byte-level base vocabularies (256 bytes of UTF-8) can encode any text.
    • 
    
  • Byte-pair encoding repeatedly merges the most frequent adjacent pair; encoding applies the learned merges in order. On held-out Shakespeare, 512 merges raise the compression from 1.00 to 2.10 bytes per token.
    • 
    
  • A regular expression splits text before merging, so tokens do not cross word or digit-and-punctuation boundaries; GPT-style tokenisers attach the leading space to the word.
    • 
    
  • Vocabulary size trades sequence length against table size and training signal per token: V×C weights in the embedding, diminishing compression gains, larger vocabularies in newer models (100k to 200k).
    • 
    
  • The same sentence costs 17 tokens in English and 82 in Hindi under GPT-2's vocabulary, 16 under o200k. Measure cost per language with the real tokeniser.
    • 
    
  • Common failure modes: whitespace sensitivity, digit chunking, no access to letters, split UTF-8 characters, normalisation mismatch, special-token injection, glitch tokens and train/serve mismatch. Each has a cheap defence.
    •

Check your understanding

  

    
A word-level tokeniser trained on Shakespeare leaves 4.6% of held-out word tokens unknown, while a byte-level BPE leaves none. Why?

    
  1. BPE has a bigger vocabulary
  2. BPE removes rare words from the text before encoding
  3. Any string can be spelled in bytes, so rare words fall back to smaller pieces instead of a single unknown symbol
  4. BPE learns the held-out text during encoding

    
The base alphabet of 256 bytes can represent every possible string, so a word that never occurred in training is encoded as several known tokens, in the worst case single bytes. The BPE vocabulary in the experiment was actually much smaller (768) than the word vocabulary (12,569), so size is not the reason. Nothing is removed or learned at encoding time.

  

  

    
After training BPE on the four-word corpus, how is the unseen word "lowest" encoded, and why?

    
  1. low + est: the merges for "low" and "est" apply in order to its characters
  2. As one unknown token
  3. l + o + w + e + s + t, because the word never appeared
  4. lowest as a single new token created on the fly

    
Encoding applies the learned merges to any string: l+o and lo+w give "low", and e+s then es+t give "est". The vocabulary is fixed after training, so no token is created at encoding time, and the point of BPE is that unseen words are still covered by frequent pieces.

  

  

    
A chat product sends a model the text "The capital of France is " (with a trailing space) and gets worse completions than with "The capital of France is". What is the most likely cause?

    
  1. The model dislikes long prompts
  2. Trailing spaces are removed, so the prompts are identical
  3. The model has an unusually small context window
  4. The space was tokenised as its own token, and in training the space normally attaches to the following word, so the model is in a situation it rarely saw

    
GPT-style tokenisers put the leading space inside the next word's token (" Paris"), so a prompt ending in a bare space leaves the model at an unnatural position. The prompts are not identical to the tokeniser: they have different ids. Prompt length and context size do not differ between the two.

  

  

    
You must estimate the monthly token budget for a Hindi-language support bot using an English-centred estimate of "about 4 bytes per token". Which correction is closest to right for a GPT-2-era vocabulary, using this chapter's measurements?

    
  1. No correction: bytes per token is a constant of the algorithm
  2. Multiply by a factor of about 4 to 5, because the Hindi sentence needed 82 tokens against 17 in English
  3. Divide by 2, because Hindi is more compact
  4. Multiply by 1.5, the ratio of bytes

    
The Hindi sentence is 138 bytes and 82 tokens, 1.7 bytes per token, not 4, so costs are about 4.8 times those of English under that vocabulary. The bytes-per-token ratio is a property of the tokeniser and the text, not of BPE. With the o200k vocabulary the factor falls to nearly 1, so the right answer depends on the tokeniser, which you must measure.

  

  

    
A streaming API decodes each new token to text as soon as it is generated, and users occasionally see "�" in the middle of emoji or Japanese words. The characters are fine in the final output. What is going on and what is the fix?

    
  1. The model is producing corrupt tokens; retrain it
  2. The network drops packets; add retries
  3. A multi-byte character was split across tokens, so a single token's bytes are not valid UTF-8 on their own; buffer bytes until a character is complete
  4. The vocabulary is too small; enlarge it

    
Byte-level tokens can end in the middle of a UTF-8 sequence (the chapter's emoji is split F0 9F | 99 82). Concatenating all the bytes gives the right text, which is why the final output is fine. The fault is in decoding token by token, not in the model, the network or the vocabulary size.

  

  

    
Your service puts user messages into a template with special tokens such as end-of-turn markers. A user writes the literal text of a special token in their message. Which design prevents the model from treating it as a control token?

    
  1. Encode user text with special-token parsing disabled and insert control tokens only from your own code
  2. Parse special tokens everywhere so the model sees what the user typed
  3. Strip all punctuation from user messages
  4. Lower-case the user message

    
Treating untrusted text as ordinary text keeps it in the data channel; the literal string then costs several ordinary tokens (eight, in the chapter's example) and carries no control meaning. Parsing everywhere is the vulnerability. Stripping punctuation or lower-casing damages legitimate messages and is easy to bypass.

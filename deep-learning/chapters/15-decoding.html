Decoding Strategies

A trained language model outputs a probability for every possible next token. It does not write text until something chooses. This chapter covers the choices: greedy decoding, sampling with a temperature, top-k, top-p and min-p truncation, beam search and constrained decoding. It runs each one on the trained model of chapter 12, shows what each does to the distribution and to the text, and explains why "temperature zero" is neither deterministic nor a guarantee of quality.

Why this matters

The same weights can produce dull loops, fluent prose, wild nonsense or perfectly formatted JSON, depending only on how tokens are drawn. These settings are the dials an application engineer actually controls on a hosted model, and they are the mechanism behind "structured outputs". After this chapter you can write each sampler in a few lines of NumPy, predict what a temperature or a threshold will do to a given distribution, explain why beam search gives repetitive prose, build a constrained decoder that guarantees an output format, choose settings for a task and test the choice, and say why two runs at temperature 0 can still differ.

The model gives a distribution; something must choose

Chapter 12's generate function did the simplest thing: softmax over the last position's logits, then draw a token in proportion to its probability. That is ancestral sampling, and it generates text from exactly the distribution the model learned. Every other method in this chapter modifies one of two steps. Either it reshapes the distribution before the draw (temperature, truncation, a constraint mask), or it replaces the draw by a search (greedy, beam).

The model in this chapter is the 108,352-weight character model trained in chapter 12 (the weights are in gpt.npz). Its small size is a feature here: the samples are visibly imperfect, so differences between decoding methods are easy to see. A large model's text is better, and the same effects appear more subtly.

Greedy decoding and why it loops

Greedy decoding takes the most probable token at every step. It is deterministic, cheap and often right for tasks with one correct answer, such as extraction, classification or arithmetic. For open-ended text it fails in a characteristic way. Here is what the trained model writes greedily after "ROMEO:" and a newline (full output below):

ROMEO:
That the so man the so make the so make the some to the some to the some to the some to ...

It falls into a repetition loop. Once the text contains "the so make the so make", the most probable continuation is more of the same, because repeated text is, on average, followed by more repetition. Each repeat makes the next one more likely, and greedy decoding has no mechanism to leave. Holtzman et al. (2019, "The Curious Case of Neural Text Degeneration") documented this in large models too, and added the finding that the most likely text is not what humans write: human text is full of lower-probability choices, and a decoder that always takes the top choice produces text that is blander and more repetitive than any real author. Sampling from the full distribution fixes the repetition and introduces a different problem, which the next sections address.

Temperature

Temperature τ rescales the logits before the softmax: pi(τ) = ezi/τ / ∑k ezk/τ. The name comes from physics (the Boltzmann distribution, where a hot system explores many states and a cold one settles into the lowest). Equivalently, pi(τ) is proportional to pi1/τ, which is how the with_temperature function below computes it. Three regimes follow directly.

  • τ = 1 leaves the model's distribution unchanged.
  • τ < 1 sharpens it: the gaps between logits are magnified, the top token gains probability and the tail shrinks. As τ → 0 the distribution becomes one-hot on the top token, which is greedy decoding. (Libraries treat τ = 0 as a special case, because dividing by zero is undefined.)
  • τ > 1 flattens it. As τ → ∞ every token approaches probability 1/V and the output becomes random.

Temperature changes the shape, not the order: the ranking of tokens never changes, so any method that depends only on the ranking (greedy, top-1) is unaffected.

Here are the pieces in code, with the experiments that follow: the effect of temperature on the distribution after "my lord, th", and what each filter keeps. First the functions.

import numpy as np
from gpt_model import CFG, forward, softmax

p = dict(np.load("gpt.npz"))                               # weights saved by train.py (chapter 12)
text = open("input.txt", encoding="utf-8").read()
chars = sorted(set(text)); stoi = {c: i for i, c in enumerate(chars)}
enc = lambda s: [stoi[c] for c in s]
show = lambda i: repr(chars[i])[1:-1] if chars[i] != " " else "' '"

def next_probs(ids):                                       # the model: ids so far -> distribution over the next character
    return softmax(forward(p, np.array(ids[-CFG["T"]:])[None], CFG)[0, -1].astype(np.float64))

# --- four ways to reshape a distribution before sampling ---
def with_temperature(probs, tau):                          # softmax(logits / tau), written on probabilities
    q = probs ** (1.0 / tau)
    return q / q.sum()

def keep(probs, mask):                                     # zero everything outside `mask`, renormalise
    q = np.where(mask, probs, 0.0)
    return q / q.sum()

def top_k(probs, k):
    return keep(probs, probs >= np.sort(probs)[-k])

def top_p(probs, top):                                     # smallest set of characters whose mass reaches `top`
    order = np.argsort(-probs)
    before = np.cumsum(probs[order]) - probs[order]        # mass of everything ranked above this character
    mask = np.zeros(len(probs), bool); mask[order[before < top]] = True
    return keep(probs, mask)

def min_p(probs, frac):                                    # keep characters at least `frac` times as likely as the best
    return keep(probs, probs >= frac * probs.max())

def generate(prefix, n, shape, seed=0):
    rng, ids = np.random.default_rng(seed), enc(prefix)
    for _ in range(n):
        q = shape(next_probs(ids))
        ids.append(int(rng.choice(len(q), p=q)))
    return "".join(chars[i] for i in ids)

next_probs wraps the chapter-12 forward pass and returns the model's distribution for the next character. keep is the common tail of every truncation rule: zero out everything outside a mask, then renormalise so the survivors sum to one. top_k keeps the k most probable. top_p keeps the smallest set whose probabilities add up to at least top: it sorts, takes the running total, and keeps every character whose rank-mates above it have not yet reached the threshold (so the character that crosses the threshold is included). min_p keeps characters at least a fraction of the best one's probability. And generate applies a function shape to the distribution before each draw, so that any of them can be plugged in.

Truncation: top-k, top-p and min-p

Plain sampling at τ = 1 has a different weakness from greedy: the tail. A vocabulary of 100,000 tokens has tens of thousands of entries that are individually improbable and collectively not negligible. If 5% of the mass sits in nonsense tokens, then about once in twenty steps the sampler picks one, and one bad token in a sentence can derail the rest. Truncation methods remove the tail before drawing.

  • Top-k (Fan, Lewis and Dauphin, 2018) keeps the k most probable tokens, k = 40 being a typical choice. It is easy, but k is the same whether the model is certain or not. After "We are" the model is 98% sure of a space, and top-k with k = 3 still keeps two alternatives; after "my lord, th" it may cut real options.
  • Top-p, or nucleus sampling (Holtzman et al., 2019), keeps the smallest set of tokens whose probabilities sum to at least p, such as 0.9. The size of the set adapts: one token when the model is sure, many when it is not.
  • Min-p (Nguyen et al., 2024) keeps tokens whose probability is at least a fraction of the top token's, for example 0.05. Like top-p it adapts, and its threshold scales with the model's confidence: if the top token has 0.9, tokens below 0.045 go; if it has only 0.2, tokens below 0.01 go. The authors report better quality and diversity than top-p, especially at high temperatures; it is now in popular open-source inference libraries.

The second half of the output printed above shows the same result as numbers: after "my lord, th", top-k = 3 keeps "e a o" holding 88% of the mass, while top-p = 0.9 and min-p = 0.1 both keep "e a o i" (95%). After "We are", top-k = 3 keeps a space, a comma and an "s", whereas top-p and min-p keep only the space. Try all of them on a fixed distribution.

Greedy loops. Pure sampling at τ = 1.0 has the right look (speaker names, line breaks, a question mark) and the invented words of an under-trained model ("perfore", "untorthy"). Analogy: a restaurant order by dice

  
Imagine the model as a waiter who knows what each guest usually orders, with a percentage for every dish. Greedy decoding always brings the most popular dish. Temperature below 1 makes the waiter even more conservative; above 1 it makes the tail of the menu likelier. Top-p tells the waiter to ignore dishes beyond the popular ones that together cover 90% of orders; min-p tells them to ignore anything less than a twentieth as popular as the best seller.

  
Where it breaks down: a waiter's menu stays the same from guest to guest, while a model recomputes the entire distribution after every token, and an early odd choice changes everything after it. And popularity is not correctness: the most likely continuation of a question may be a common misconception.





Beam search



Beam search tries to find the most probable sequence, not just the most probable next token, because the greedy choice at each step need not lead to the most probable whole. It keeps the width best partial sequences (the beam). At each step it extends each of them by every possible next token, scores each extension by the sum of log-probabilities so far, keeps the best width candidates, and repeats. With width 1 it is greedy decoding; with infinite width it is exhaustive search. The figure follows the real model for three steps with a width of 2 (the best two continuations of each beam are considered).





import numpy as np
from decode import CFG, forward, softmax, p, chars, stoi, enc, next_probs

def log_probs(batch):                                      # (n, t) ids -> (n, V) log-probabilities of the next character
    lg = forward(p, batch[:, -CFG["T"]:], CFG)[:, -1].astype(np.float64)
    z = lg - lg.max(-1, keepdims=True)
    return z - np.log(np.exp(z).sum(-1, keepdims=True))

def beam_search(prefix, n, width):
    beams = [(0.0, enc(prefix))]                           # (total log-probability, ids)
    for _ in range(n):
        lps = log_probs(np.array([ids for _, ids in beams]))
        cands = [(s + lp[c], ids + [int(c)]) for (s, ids), lp in zip(beams, lps) for c in np.argsort(-lp)[:width]]
        beams = sorted(cands, key=lambda b: -b[0])[:width]
    return beams[0]

def string_logprob(prompt, name):                        # chain rule over the characters of "NAME:"
    ids, total = enc(prompt), 0.0
    for c in name + ":":
        total += log_probs(np.array([ids]))[0, stoi[c]]; ids.append(stoi[c])
    return total



The scoring in beam_search is the chain rule of chapter 14: the log-probability of a whole sequence is the sum of the log-probabilities of its tokens. The model is evaluated for all beams in one batch. (string_logprob, at the end of the listing, scores a given string by the same chain rule; the constrained experiment below uses it.) The next listing runs it with widths 1, 4, 16 and 64 for 60 characters after "ROMEO:" and compares the probability of what it finds.

Wider beams do find more probable text: the total log-probability of 60 characters rises from −65.6 for greedy to −33.8 at width 64, which is 0.56 nats per character. But look at the text. Width 16 and width 64 give "My lord, my lord, my lord." and then repeat. And note the last line: real held-out Shakespeare costs about 1.7 nats per character under this model. The beam's output is three times more probable per character than a real line, which is exactly what makes it unlike real text. This is Holtzman et al.'s "likelihood trap": the highest-probability sequences are repetitive and generic, and the more a method optimises the probability, the further it moves from the typical.



Beam search remains the method of choice where there is one right answer and the model's distribution is sharp, notably machine translation, speech recognition and some summarisation. There it was introduced for neural models by Sutskever et al. (2014), and Wu et al. (2016) added length normalisation. Without it, longer candidates are penalised just because each extra token multiplies in another probability below one, so beam search prefers short outputs. Dividing the score by a power of the length corrects the bias. For open-ended generation, chat and creative writing, the field settled on sampling with truncation.



Penalties, limits and stopping



Production decoders add a few more controls around the core. Repetition penalties lower the logit of tokens that have already appeared (Keskar et al., 2019, introduced the form used in CTRL); many APIs expose related frequency and presence penalties, which subtract from the logit of a token in proportion to how often (or whether) it has appeared. They reduce loops, but a blunt penalty also punishes legitimate repetition (a name that occurs ten times, the indentation of code, the quote characters of JSON), so keep them mild. A logit bias adds a fixed amount to chosen tokens, to encourage or ban them. Stop conditions end generation: a stop token such as the end-of-text token, a stop string such as a blank line, or a maximum number of new tokens. The last one is a safety limit that also bounds cost, and hitting it before the model has finished leaves the output truncated, which matters for formats that must close (JSON braces).



Constrained decoding



Sometimes an output must belong to a set: one of five labels, a number, a date, valid JSON with specific fields, a program in a grammar. Asking the model nicely works most of the time; constrained decoding works every time. At each step it computes which tokens can legally come next, given what has been generated, sets all other logits to −∞ (the "constraint mask" of the pipeline figure), and samples from what is left. Since only valid continuations have non-zero probability, the finished text is valid by construction.



The demonstration uses the character model, where the constraint is simple: after the prompt (a short speech and a blank line) the next characters must spell one of five speaker names, followed by a colon. A set of strings forms a trie, a tree of prefixes, and at each step the allowed characters are those that continue some string in the set.



    # --- constrained decoding: the next word MUST be one of these speaker names ---
    allowed = ["ROMEO", "JULIET", "BENVOLIO", "MERCUTIO", "ESCALUS"]
    prompt = "First Citizen:\nBefore we proceed any further, hear me speak.\n\n"
    print("\nmodel probability of each allowed string, followed by ':'")
    for name in allowed:
        print(f"  {name:9s} log p = {string_logprob(prompt, name):7.2f}   p = {np.exp(string_logprob(prompt, name)):.5f}")

    ids, out = enc(prompt), ""
    while True:                                                # greedy, but only among characters that keep us on a valid path
        ok = {a[len(out)] if len(out) < len(a) else ":" for a in allowed if a.startswith(out) and len(out) <= len(a)}
        q = next_probs(ids); mask = np.zeros(len(q), bool); mask[[stoi[c] for c in ok]] = True
        c = chars[int(np.argmax(np.where(mask, q, 0)))]
        print(f"  after {out!r:11}: allowed {sorted(ok)}, model's mass on them {q[mask].sum():.3f} -> {c!r}")
        if c == ":": break
        out += c; ids.append(stoi[c])
    print("constrained greedy chose:", out)

Later characters are mostly forced: after "RO" the only legal continuation is "M", to which the model gave 0.93 anyway. The mass the model puts on legal options is a useful diagnostic: if it is very low at some step, the constraint is fighting the model, and the output, though valid, may be unlikely and low in quality, or the prompt does not tell the model what format to produce. In production, always keep the prompt consistent with the constraint rather than relying on the mask alone.



Tokens are not characters



With characters it is easy. Real models generate tokens, and a token can span grammar boundaries: one token may be a closing quote plus a comma plus a newline, and another half of a number. To decide whether each of the 100,000 tokens is legal at the current state, the constraint engine must check what the token's bytes would do to the grammar's state. Doing this naively at every step is slow. The practical solution is to precompute, for each grammar state, the set of legal tokens (Willard and Louf, 2023, "Efficient Guided Generation for Large Language Models", the basis of the Outlines library) or to precompute the context-independent part of the mask and interpret only the rest at run time (Dong et al., 2024, XGrammar), overlapping this with GPU work. The size of the allowed set is often tiny, as this count shows for an integer field.

For a field that must hold an integer, only 1,110 of the 100,256 ordinary tokens of cl100k_base are digit-only (about 1%), so each step of the mask removes 99% of the vocabulary. Alignment between the grammar and the tokeniser is a quality issue too: Beurer-Kellner, Fischer and Vechev (2024, "Guiding LLMs the Right Way") show that constraints enforced without respecting how the model's tokens split the text can distort the output distribution and reduce task accuracy, because the constraint forces unusual tokenisations the model rarely saw in training.



Constrained decoding guarantees syntax, not truth. A response may be valid JSON matching the schema and still contain the wrong values. Output can also be truncated by the length limit before it closes, so always check for that case and keep schemas simple. Common misconception

  
"Temperature 0 gives the same, correct answer every time." Neither half is guaranteed. Temperature 0 gives the model's most likely text, which for open questions can be a bland or mistaken answer. And on real serving systems the outputs can differ between runs: Horace He and colleagues at Thinking Machines (September 2025, "Defeating Nondeterminism in LLM Inference") sampled 1,000 completions of the same prompt at temperature 0 from one large model and got 80 distinct outputs, identical for the first 102 tokens and diverging at token 103. They traced it to kernels whose arithmetic depends on batch size, so that server load (which sets the batch size) changes the rounding of the logits and, when two tokens are nearly tied, the winner. With batch-invariant kernels, their 1,000 completions came out identical at some cost in speed. For you the practical point is to treat model output as a distribution even at temperature 0, to test with several runs, and never to build logic that needs bit-identical output unless the platform promises it.





Choosing settings



No setting is best in general; the right one depends on the task and has to be measured. These are starting points that practitioners commonly use, not rules, and vendor guidance for a given model should override them.

State of play, October 2026

  
Min-p sampling was published in July 2024 and presented at ICLR 2025, and its authors report adoption by Hugging Face Transformers, vLLM and other open-source libraries. Structured-output features that guarantee schema-valid JSON are offered by hosted model APIs and by open inference engines; the open engines I know of build on Outlines-style finite-state indexes or on grammar engines such as XGrammar (November 2024). I have not checked which settings the hosted APIs of specific vendors currently expose, which differ between providers and between model families (some reasoning-oriented models restrict sampling parameters), so consult the current API reference. The exact default values of top-p, top-k and temperature in any framework change between versions.

Systems connection

  
Decoding happens on the serving path, once per token per request. Sampling needs the full logit vector, so top-p must sort or partially sort around 100,000 numbers per sequence per step, which is why serving engines implement it as a fused GPU kernel (A3 chapter 20). A constraint adds a grammar state per request and a mask per step, which must be computed on the CPU or cached without stalling a GPU batch shared with other requests. Beam width multiplies memory for the KV cache and the compute per request (A3 chapter 18). The nondeterminism above is a reminder from distributed systems that "same input, same output" holds only if every component makes it hold, and it makes request-level caching, regression tests and incident reproduction harder (safe rollouts, replay and idempotence all matter here). Many APIs can return the log-probabilities of the chosen tokens; log them, because they are the cheapest uncertainty signal you have.






  
Key takeaways

  
    
    
  • Decoding is the choice of how to turn the model's next-token distribution into text. Sampling follows the distribution; greedy takes the top token; beam search keeps the best several sequences.
    • 
    
  • Greedy decoding is deterministic and good for single-answer tasks, but in open-ended text it falls into loops ("the so make the so make ..."). The most probable text is not typical text.
    • 
    
  • Temperature divides the logits by τ: below 1 sharpens (toward greedy), above 1 flattens (toward uniform). After "my lord, th", entropy goes from 0.56 bits at τ = 0.25 to 3.02 bits at τ = 2.
    • 
    
  • Top-k keeps a fixed number of tokens; top-p keeps a fixed probability mass; min-p keeps tokens relative to the top one. The adaptive rules keep one token when the model is sure and many when it is not.
    • 
    
  • Beam search finds more probable sequences (−33.8 against −65.6 log-probability in the demo) that are less like real text (0.56 against about 1.7 nats per character). It suits translation and recognition, not open-ended generation.
    • 
    
  • Constrained decoding masks illegal tokens at each step, guaranteeing syntax. It needs a token-level mask computed efficiently, and the share of probability the model puts on legal tokens shows how hard the constraint is fighting it. It guarantees format, not truth.
    • 
    
  • Temperature 0 is not reliably deterministic on real serving stacks (80 distinct outputs in 1,000 runs in one published study), and it is not the same as correct.
    •

Check your understanding

  

    
You lower the temperature from 1.0 to 0.5. What happens to the ranking of the tokens by probability and to the probability of the top token?

    
  1. The ranking is reversed and the top token's probability falls
  2. The ranking is unchanged and the top token's probability rises
  3. The ranking is unchanged and the top token's probability falls
  4. The ranking is shuffled and the top token's probability rises

    
Dividing all logits by the same positive number preserves their order, so the ranking is unchanged. A temperature below 1 magnifies the gaps between logits, so the largest gains probability (after "my lord, th" the top character went from 0.45 to 0.67 at τ = 0.5). The reverse happens above 1.

  

  

    
A model is 98% sure of the next token. Which statement about top-k = 3 and top-p = 0.9 is right?

    
  1. Both keep exactly three tokens
  2. Both keep exactly one token
  3. Top-p keeps three and top-k keeps one
  4. Top-k keeps three tokens, but top-p keeps only the one that already covers 90% of the mass

    
Top-k always keeps k tokens regardless of confidence, so two unlikely tokens stay in. Top-p adds tokens only until their total reaches 0.9; a single token with 0.98 already does. This adaptivity is the reason for the newer rules (the "We are" example: top-k = 3 kept a space, a comma and an "s"; top-p kept only the space).

  

  

    
Beam search with width 64 finds a text with a much higher total probability than greedy decoding, yet it reads as more repetitive. What does this show?

    
  1. Maximising sequence probability does not maximise naturalness: likely text is repetitive and generic, and real text has lower per-token probability
  2. Beam search has a bug
  3. The model is badly trained
  4. Greedy decoding is optimal

    
In the chapter's experiment width 64 reached −33.8 nats for 60 characters (0.56 per character) while real text costs about 1.7 per character under the same model, and the output was "My lord, my lord, my lord". The search works as intended; the objective it optimises is not what we want for open-ended text. Greedy is not optimal either (it scored −65.6).

  

  

    
A constrained decoder requires the next word to be one of five names. At the first step the model gives only 0.2 of its probability to the five legal first letters. What is the most useful conclusion?

    
  1. Nothing: the mask guarantees a valid result so the number does not matter
  2. The model is broken
  3. The constraint is overriding the model's own preference, so the output will be valid but may be low quality; check the prompt tells the model about the format
  4. The vocabulary must be larger

    
The mask renormalises whatever mass is left on legal tokens to 100%, so validity is guaranteed whatever the model wanted. A low share of probability on legal options means the model "expected" something else, which is a warning that the prompt and constraint disagree. It does not indicate a broken model or a small vocabulary.

  

  

    
A service at temperature 0 returns different answers to the same prompt on different days. Which explanation is most consistent with published findings?

    
  1. Temperature 0 randomly selects among the top tokens
  2. Arithmetic in the serving kernels depends on how requests are batched, so near-tied logits can round differently depending on server load
  3. The tokeniser is stochastic
  4. The model weights change a little with each request

    
Temperature 0 takes the argmax, but the logits themselves vary slightly with batch size through floating-point reduction order, which can flip a near-tie, after which the texts diverge. The tokeniser is deterministic, weights do not change per request, and temperature 0 does not sample.

  

  

    
You need a model to output a JSON object with a fixed schema every time. Which approach gives the strongest guarantee of syntactic validity?

    
  1. Ask for JSON in the prompt and set temperature 0
  2. Use a large beam width
  3. Add a repetition penalty
  4. Constrain decoding with a grammar for the schema, and check for truncation by the length limit

    
Only a mask that removes illegal tokens at every step makes invalid output impossible; prompting and low temperature make it likely but not certain. Beam width and repetition penalties address other things. Truncation by the maximum-length limit can still leave an unclosed object, so check for that, and remember that valid syntax does not guarantee correct values.

Efficient Attention

Attention as chapter 09 defined it is correct but expensive in two different ways: the key/value cache that generation must keep, and the score matrix that training and prefill must compute. This chapter covers three families of fix: sharing keys and values between heads (multi-query and grouped-query attention), restricting which pairs are scored (sliding windows), and reorganising the same arithmetic around the GPU's memory hierarchy (FlashAttention).

Why this matters

Parts 1 to 5 built a Transformer, trained it and counted what it costs. Part 6 asks how current models differ from that textbook design, and most of the differences are about attention, because attention is where context length turns into memory and time. If you open the configuration of almost any recent open model you will see a number of key/value heads smaller than the number of query heads, and a flag for a fused attention kernel, and some also a window size. Without this chapter those fields are unexplained constants; with it you can predict how many users one GPU can serve, why a 128K context is affordable at all, and which of the three techniques changes the answer, the cost, or neither. Each technique also has a trade-off, and knowing which is a trade of quality and which is a pure engineering gain (FlashAttention is the second kind) is what stops you from choosing the wrong lever. Chapter 20 turns to the other large block of the model, the MLP, and A3 chapter 18 and chapter 20 build the serving side on what is here.

Two costs, two kinds of fix

Chapter 09 ended with a table of what attention costs: the score matrix has T² entries per head, and a naive implementation that stores it needs memory that grows with the square of the context. That is one cost. It matters for training and for prefill, the first phase of serving, in which the model reads the whole prompt in one parallel pass.

Generation has a different shape. A model produces one token per step, and at each step the new token's query must attend to every earlier token's key and value. Recomputing those from scratch every step would cost a full forward pass over the history each time, so they are saved: this store is the KV cache (the keys and values of all earlier tokens, kept so they are computed once; A3 chapter 18 treats it in depth). It removes the repeated arithmetic, but it creates a new cost: the cache grows with every token and must be read from GPU memory on every step. This is the decode phase, and it is limited by memory bandwidth, not by arithmetic (chapter 16).

So there are two bottlenecks and three techniques, and it helps to keep the mapping in mind from the start.

TechniqueWhat it changesWhich cost it attacksChanges the model's answers?
Multi-query / grouped-query attentionFewer key/value heads than query headsSize of the KV cache, and so decode speed and how many sequences fitYes: a different architecture, trained that way

The first two are architectural choices made before training. The third is an implementation of the same function. We start with the cache because it is the easiest to put numbers on.

The KV cache and what it costs

In multi-head attention (chapter 09) each of h heads has its own query, key and value projections. At generation time every layer keeps, for every earlier token, one key vector and one value vector per head, each of width dk = C/h. The cache for one token is therefore

bytes per token = 2 × L × nkv × dk × bytes per number

where L is the number of layers, nkv the number of key/value heads (h in ordinary multi-head attention), and the 2 counts a key and a value. The cache for a sequence is that times the number of tokens, and the total for a server is that times the number of concurrent sequences. The script below evaluates it for the Llama 3 8B shape from chapter 16 (32 layers, 32 query heads, head width 128) in bf16, and then asks how fast a decode step can be if its time is the bytes read divided by memory bandwidth. The bandwidth of 3 TB/s is an assumption of the right order for a current data-centre GPU, not a measurement.

# KV-cache size per token and per sequence for one model shape, as the number of key/value heads changes.
L, H, d_k = 32, 32, 128                  # layers, query heads, head width (the Llama 3 8B shape from chapter 16)
BYTES = 2                                # bf16
GPU, WEIGHTS = 80e9, 16e9                # an 80 GB card holding 16 GB of bf16 weights

def kv_bytes_per_token(kv_heads):
    return 2 * L * kv_heads * d_k * BYTES        # 2 = one K and one V, per layer, per KV head

print(f"{'variant':<22}{'KV heads':>9}{'KiB/token':>11}{'GiB @ 8k':>10}{'GiB @ 128k':>12}{'sequences @ 8k':>16}")
for name, kv in (("multi-head (MHA)", 32), ("grouped-query (GQA)", 8), ("multi-query (MQA)", 1)):

Read the table across. With 32 key/value heads the cache costs 512 KiB per token, so a single 8,192-token conversation holds 4 GiB, and a 128K-token one holds 64 GiB, which by itself would fill most of a GPU. After the 16 GB of weights, an 80 GB card has room for only 14 such conversations. At a batch of 16 the full multi-head cache (68.7 GB) plus the weights does not fit at all, which the last block shows as 84.7 GB of reads. The decode time follows the bytes: at the same batch, the attention variant with fewer key/value heads reads less and finishes each step sooner. That is the entire argument for the next section.

Multi-query and grouped-query attention

The cache scales with nkv, the number of distinct key/value heads. The query heads are what give the model several different views of the context, but nothing forces each view to have its own private keys and values. Multi-query attention (MQA; Shazeer, 2019, "Fast Transformer Decoding: One Write-Head is All You Need") keeps all h query heads but uses a single key head and a single value head shared by all of them. The cache shrinks by a factor of h. In the table above, 32 heads become 1 and the 4 GiB conversation becomes 128 MiB.

The price is quality and training stability: one shared key/value head is a narrow channel for everything the layer wants to look up. Grouped-query attention (GQA; Ainslie et al., 2023, "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints") takes the middle road. The h query heads are divided into g groups, and each group shares one key/value head, so nkv = g. Setting g = h gives multi-head attention, and g = 1 gives multi-query attention, so GQA is a dial between them. The authors report that GQA reaches quality close to multi-head attention with speed comparable to multi-query, and that an existing multi-head checkpoint can be converted ("uptrained") with about 5% of its original pre-training compute. Llama 3 uses 8 key/value heads for 32 (8B) or 64 (70B) or 128 (405B) query heads, as chapter 16's table showed, and many other open models follow a similar pattern.

The implementation is a reshape and a repeat

Nothing in the attention formula changes. The key and value projections simply output nkv · dk columns instead of h · dk, and before the scores are computed each key/value head is copied g = h / nkv times so that it lines up with the query heads that share it. Shapes are written (B, heads, T, dk). The script also checks that setting nkv = h reproduces ordinary multi-head attention computed head by head.

# Grouped-query attention in NumPy. kv_heads = H is multi-head, kv_heads = 1 is multi-query.
import numpy as np
def softmax(x):
    e = np.exp(x - x.max(-1, keepdims=True)); return e / e.sum(-1, keepdims=True)

def gqa(x, Wq, Wk, Wv, Wo, H, KV):
    B, T, C = x.shape; d = C // H; g = H // KV           # g query heads share each key/value head
    q = (x @ Wq).reshape(B, T, H, d).transpose(0, 2, 1, 3)      # (B, H, T, d)
    k = (x @ Wk).reshape(B, T, KV, d).transpose(0, 2, 1, 3)     # (B, KV, T, d)  <- this is what gets cached
    v = (x @ Wv).reshape(B, T, KV, d).transpose(0, 2, 1, 3)     # (B, KV, T, d)
    k, v = np.repeat(k, g, axis=1), np.repeat(v, g, axis=1)     # (B, H, T, d): copy each KV head g times
    s = q @ k.transpose(0, 1, 3, 2) / np.sqrt(d)                # (B, H, T, T)
    s = np.where(np.tril(np.ones((T, T), bool)), s, -np.inf)    # causal mask
    return (softmax(s) @ v).transpose(0, 2, 1, 3).reshape(B, T, C) @ Wo

rng = np.random.default_rng(0)
B, T, C, H = 2, 6, 32, 8; d = C // H
x = rng.normal(size=(B, T, C)); Wq, Wo = rng.normal(0, .2, (C, C)), rng.normal(0, .2, (C, C))
Wk_full, Wv_full = rng.normal(0, .2, (C, C)), rng.normal(0, .2, (C, C))

for KV in (8, 4, 2, 1):
    Wk, Wv = Wk_full[:, :KV * d], Wv_full[:, :KV * d]
    y = gqa(x, Wq, Wk, Wv, Wo, H, KV)
    params = Wq.size + Wk.size + Wv.size + Wo.size
    print(f"KV heads {KV}: output {y.shape}, cached K per layer (B, KV, T, d) = {(B, KV, T, d)}, attention parameters {params}")

# Sanity check: GQA with KV=H must equal multi-head attention computed head by head.
y_gqa = gqa(x, Wq, Wk_full, Wv_full, Wo, H, H)
outs = []
for h in range(H):
    sl = slice(h * d, (h + 1) * d)
    q, k, v = (x @ Wq)[..., sl], (x @ Wk_full)[..., sl], (x @ Wv_full)[..., sl]
    s = np.where(np.tril(np.ones((T, T), bool)), q @ k.transpose(0, 2, 1) / np.sqrt(d), -np.inf)
    outs.append(softmax(s) @ v)
print("max |GQA(KV=H) - per-head MHA| =", np.abs(y_gqa - np.concatenate(outs, -1) @ Wo).max())

Two things to notice. The tensor that is cached is the one before the repeat, (B, nkv, T, dk); the repeat is a view that real kernels avoid materialising by indexing the shared head directly. And the attention parameters fall with nkv, from 4,096 to 2,304 here, because Wk and Wv shrink. That is a small saving in total parameters (chapter 16 showed attention is under a fifth of the weights), so GQA is chosen for the cache, not for the parameter count.

Analogy: sharing the reference shelf

Think of 32 students (query heads) who each have a different question and all consult the same reference books (keys and values). With multi-head attention every student has a private copy of the whole library, which is great for working in different ways and takes a building to store. With grouped-query attention each table of four students shares one set. With multi-query attention the whole class shares one set. The storage and the carrying (memory traffic) shrink, and the students still ask 32 different questions.

Where it breaks down: the shelf is not fixed reading material. The keys and values are computed from the text so far and learned during training, so a model trained with shared heads learns to put into them what all four students need, which is a real constraint on what the heads can specialise in. That is why the cheaper the sharing, the larger the quality risk, and why converting an existing multi-head model needs some further training rather than a pure rewrite of the weights.

Beyond GQA: compressing the cache itself

DeepSeek-V2 (2024) takes a different route called multi-head latent attention, in which keys and values for all heads are reconstructed from one small shared latent vector per token, and only the latent is cached. The cache becomes much smaller than with grouped sharing, at the price of extra projection matrices. The idea, caching a compressed representation and expanding it when needed, is a separate lever from the head-sharing of this section. DeepSeek-V3 (2024) reuses it, as its abstract states.

Common misconception

"Grouped-query attention reduces the amount of attention computation." Almost not at all. The score matrices are still computed for every query head, so the QKT and PV products cost the same number of FLOPs as before. What falls is the number of bytes stored and read for keys and values. That is why GQA speeds up decode, which is limited by memory traffic, and does little for training throughput.

Sliding-window attention

The second idea restricts which pairs are scored. In causal attention token i may read tokens 1 to i. In sliding-window attention it reads only the previous W tokens, itself included. Longformer (Beltagy et al., 2020, "Longformer: The Long-Document Transformer") used this pattern, with some designated global tokens, for long documents, and Mistral 7B (Jiang et al., 2023) used it in a decoder language model with a window of 4,096 tokens, together with grouped-query attention.

Two consequences follow. The score work and the memory per token become linear in T for fixed W. And the KV cache stops growing: once a token is more than W positions old nothing will read it again, so a rolling buffer of W slots, written at position mod W, holds everything needed. The script below builds the mask, counts the scored pairs, and checks something that surprises people at first: a token far outside the window can still influence the present, indirectly, through the layers.

# Sliding-window attention: the mask, how far information travels through layers, and the rolling cache.
import numpy as np
T, W = 40, 6                                         # sequence length, window (each token sees itself and W-1 before)
i, j = np.arange(T)[:, None], np.arange(T)[None, :]
mask = (j <= i) & (i - j < W)                        # causal AND within the window
print("mask for T=10, W=4 (1 = may attend):")
small = (np.arange(10)[None, :] <= np.arange(10)[:, None]) & (np.arange(10)[:, None] - np.arange(10)[None, :] < 4)
for row in small.astype(int): print(" ", "".join(map(str, row)))
print(f"scored pairs: full causal {T*(T+1)//2}, window {int(mask.sum())}")

# One layer lets token i read tokens up to W-1 back. Two layers compose: reach = mask @ mask (as booleans).
reach = mask.copy()
for layer in range(1, 6):
    far = (np.arange(T) - np.array([np.flatnonzero(r)[0] for r in reach])).max()
    print(f"after {layer} layer(s): the last token can be influenced by a token {far} positions back "
          f"(theory: {layer*(W-1)})")
    reach = (reach.astype(int) @ mask.astype(int)) > 0

# Rolling buffer: slot = position mod W, so the cache never grows past W entries.
cache, W2 = [None] * 4, 4
for pos in range(10):
    cache[pos % W2] = pos
print("rolling cache after 10 tokens (W=4), slots hold positions:", cache)

In layer 1 the last token reads W − 1 = 5 positions back. The tokens it read have themselves read 5 positions back in layer 1, so after two layers information has travelled 10 positions, after five layers 25. In general the receptive field (how far back a token can be influenced) is about layers × (W − 1). A model with 32 layers and a 4,096 window can in principle pass information across more than 100,000 positions. In principle only: the path is a chain of lossy hops, and nothing guarantees that a fact survives thirty of them. Direct lookups of something far away are what the window gives up.

A known wrinkle: when a window slides, the first few tokens of the text drop out, and models that were trained with full attention sometimes degrade sharply when this happens. Xiao et al. (2023, "Efficient Streaming Language Models with Attention Sinks") traced this to the first tokens acting as a place where the softmax can put weight that no content deserves (an attention sink), and showed that keeping a few initial tokens in the window, in addition to the recent ones, restores behaviour. Models trained from the start with windows learn their own way to cope; some of the newest add a learned sink term to the softmax for the same purpose.

Because the window removes long-range direct reads, current designs rarely use it everywhere. They mix layers: most use a short window, and every few layers one uses full attention to retrieve from anywhere. The cache then stays small for the windowed layers and is full-size only for the global ones. The state-of-play box below gives examples.

FlashAttention: the same maths, less traffic

The first two techniques change the function. The third does not. To see why it helps, look at where time goes in a plain implementation. Attention is three steps: compute S = QKT/√dk, apply the softmax to get P, and compute O = PV. In a straightforward program each step is a separate GPU kernel, and each writes its full result to the GPU's main memory (HBM, high-bandwidth memory) so that the next can read it back. S and P both have T × T entries, so for long sequences the program moves a great many bytes through HBM, to do very little arithmetic on them. A GPU has far more arithmetic throughput than memory bandwidth (Zero to Systems chapter 21), so the kernels wait for memory. Attention in this form is memory-bound.

A GPU also has a small amount of much faster on-chip memory (SRAM, shared memory and registers). In the FlashAttention paper's description of an A100, SRAM is thousands of times smaller than HBM (tens of megabytes against tens of gigabytes) but roughly an order of magnitude faster; the exact figures depend on the card, so check the datasheet for yours. FlashAttention (Dao et al., 2022, "FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness") is built on one observation: if the whole computation for a small tile of queries could be done while the data sits in SRAM, then S and P would never need to be written to HBM at all.

The obstacle is the softmax

Matrix products can be done tile by tile; the softmax is the difficulty because each output weight divides by a sum over the entire row of scores, and (for stability, see A0 chapter 11) subtracts the row's maximum first. If the row is split into blocks that arrive one at a time, neither the final maximum nor the final sum is known when the first block is processed.

The fix is the online softmax (Milakov and Gimelshein, 2018, "Online normalizer calculation for softmax"). Keep a running maximum m and a running sum l of exponentials taken relative to that maximum. When a new block arrives with its own maximum, compute the new running maximum m′ = max(m, block max), and rescale the old sum by em − m′ before adding the new block's terms. The same factor rescales the running output. At the end, dividing by l gives exactly the usual softmax. Rabe and Staats (2021, "Self-attention Does Not Need O(n²) Memory") made the same observation for memory use before FlashAttention made it fast.

Step through the algorithm for a single row of six scores, [2, 1, 3, 0, 4, 1], delivered as three blocks of two. The numbers shown are the ones the script online.py prints.

Step through

One tile of queries, streaming key/value tiles

  1. Load the query tile. A block of Br query rows is copied from HBM into SRAM once, and it stays there for the whole inner loop.
  2. First key/value tile. K1 and V1 arrive. The scores s = qK1T exist only in SRAM. For the row [2, 1] the running maximum is m = 2 and the sum of exp(score − m) is l = 1.3679. The partial output is accumulated.
  3. Second tile, a larger maximum. The new scores [3, 0] have maximum 3, so m becomes 3. The old sum is multiplied by e2−3, the new terms are added, and l = 1.5530. The accumulated output is rescaled by the same factor.
  4. Third tile. Scores [4, 1] raise the maximum to 4. After the rescale and the new terms l = 1.6211, exactly the denominator a one-shot softmax over all six scores gives.
  5. Write the output once. The accumulator is divided by l and the finished output tile goes to HBM. The (T, T) score matrix never existed there.

Putting it together

Tile the queries into blocks of Br rows (the outer loop), and for each stream the keys and values in blocks of Bc rows (the inner loop). For each pair of tiles, compute the small score tile in SRAM, update m, l and the output accumulator, and discard the score tile. In causal attention the inner loop can stop at the diagonal, skipping tiles that lie entirely in the future. The next script implements this in NumPy, checks it against the naive version and counts the traffic that a GPU would pay to slow memory in each case. NumPy has no SRAM, so the counts are a model of the traffic, not a measurement of speed.

# FlashAttention's trick in NumPy: exact attention by tiles with an online softmax, never forming the T x T matrix.
import numpy as np
rng = np.random.default_rng(0)
T, d, Br, Bc = 512, 64, 64, 64                       # sequence, head width, query-tile rows, key-tile columns
Q, K, V = (rng.normal(size=(T, d)) for _ in range(3))

def naive(Q, K, V):
    S = Q @ K.T / np.sqrt(d)                         # (T, T) written out in full
    S = np.where(np.tril(np.ones((T, T), bool)), S, -np.inf)
    P = np.exp(S - S.max(1, keepdims=True)); P /= P.sum(1, keepdims=True)
    return P @ V

def tiled(Q, K, V):
    O = np.zeros_like(Q); stats = {"hbm_reads": 0, "hbm_writes": 0, "peak_tile": 0}
    for r in range(0, T, Br):                        # outer loop: one tile of queries at a time
        q = Q[r:r + Br]; stats["hbm_reads"] += q.size
        m = np.full(Br, -np.inf); l = np.zeros(Br); acc = np.zeros((Br, d))   # running max, running sum, running output
        for c in range(0, r + Br, Bc):               # inner loop: stream key/value tiles (skip tiles fully in the future)
            k, v = K[c:c + Bc], V[c:c + Bc]; stats["hbm_reads"] += k.size + v.size
            s = q @ k.T / np.sqrt(d)                 # (Br, Bc): lives only in fast memory
            rows, cols = np.arange(r, r + Br)[:, None], np.arange(c, c + Bc)[None, :]
            s = np.where(cols <= rows, s, -np.inf)
            m_new = np.maximum(m, s.max(1))          # new running max
            scale = np.exp(m - m_new)                # rescale what we had accumulated under the old max
            p = np.exp(s - m_new[:, None])
            l = l * scale + p.sum(1)
            acc = acc * scale[:, None] + p @ v
            m = m_new; stats["peak_tile"] = max(stats["peak_tile"], s.size)
        O[r:r + Br] = acc / l[:, None]; stats["hbm_writes"] += O[r:r + Br].size
    return O, stats

ref = naive(Q, K, V); out, st = tiled(Q, K, V)
print(f"max |tiled - naive| = {np.abs(out - ref).max():.2e}")
print(f"naive materialises a ({T}, {T}) matrix = {T*T:,} numbers; tiled never holds more than {st['peak_tile']:,} at once")
print(f"tiled traffic to slow memory: {st['hbm_reads']:,} reads + {st['hbm_writes']:,} writes")
naive_traffic = 3 * T * d + 4 * T * T + T * d        # read Q,K,V; write S, read S, write P, read P; write O
print(f"naive traffic (S and P each written then read back): about {naive_traffic:,}")

naive materialises a (512, 512) matrix = 262,144 numbers; tiled never holds more than 4,096 at once
tiled traffic to slow memory: 327,680 reads + 32,768 writes
naive traffic (S and P each written then read back): about 1,179,648

The result equals the naive output up to rounding of order 10−16. The tiled version never holds more than 4,096 score numbers at a time instead of 262,144, and by this simple count it moves about a third as much data to slow memory. The gap widens with length: the naive traffic contains terms in T² for writing and re-reading S and P, whereas the tiled version only streams K and V past each query tile, so its extra traffic is a fraction of T²d / Br and is set by the tile size. The FlashAttention paper states that the memory used is linear in T instead of quadratic, and gives the number of HBM accesses as a function of the SRAM size.

Two further details complete the picture. First, the backward pass needs P to compute gradients. FlashAttention does not store it: it keeps only the per-row statistics (m and l, or the log-sum-exp) and recomputes the score tiles in SRAM during backpropagation. That is extra arithmetic, but arithmetic is the resource that is cheap here, so the backward pass gets faster too. It is the same trade as activation recomputation in chapter 16, applied inside one operator. Second, the arithmetic is unchanged: the QKT and PV products still cost O(T²d) FLOPs. FlashAttention does not make attention linear.

Common misconception

"FlashAttention is an approximation that trades accuracy for speed." It is exact: the output equals standard attention up to floating-point rounding, as the script shows. Also: "FlashAttention removes the quadratic cost." It removes the quadratic memory and most of the quadratic memory traffic; the quadratic FLOP count remains. Approximate methods (sparse, low-rank or linear attention, chapter 22) are a different family with a different trade.

The reported gains are large and have grown with each version. The FlashAttention-2 paper (Dao, 2023) states that the first FlashAttention was already 2 to 4 times faster than optimised baselines with no approximation, reached 25% to 40% of the theoretical peak FLOP/s, and that FlashAttention-2 reaches 50% to 73% of peak on an A100 and about 225 TFLOP/s per GPU (72% model FLOPs utilisation) when training GPT-style models. FlashAttention-3 (Shah et al., 2024) targets the H100 and reports about 740 TFLOP/s in FP16, roughly 75% utilisation, and close to 1.2 PFLOP/s in FP8. These come from the authors' abstracts; speeds depend on sequence length, head width and the card. The practical upshot is simpler than the numbers: long-context training and serving became feasible because this kernel exists, which is the subject of case study 5.

Systems connection

FlashAttention is an instance of a principle you met in the first course: when the processor is faster than the memory, the cost of a program is its data movement, and the remedy is to restructure the work so each byte is moved fewer times, the same idea as cache blocking in a matrix multiply or an external merge sort that works on runs that fit in memory (Zero to Systems chapter 21, chapter 22). Measuring it requires a profiler that reports memory throughput as well as FLOPs. The KV-cache arithmetic is capacity planning of the kind in Designing with ML & LLMs: memory per request decides how many requests one machine can hold, and so the price per token. Serving engines build on this: A3 chapter 20 shows how paged allocation manages the cache these techniques shrink.

Choosing among them

The techniques stack rather than compete. A current decoder-only model typically combines grouped-query attention for a small cache, a fused FlashAttention-style kernel for training and prefill, and sometimes windowed layers for the longest contexts. Use these questions to find which lever applies.

  • Serving is limited by how many sequences fit or by decode speed? The cache is the problem. Reduce nkv (GQA, MQA, latent attention), window some layers, or quantise the cache (A3 chapter 19).
  • Training or prefill runs out of memory at long context, or is slow? Check you are using a fused attention kernel before anything else. It changes no results.
  • Context is much longer than the task needs to look back? A window on most layers saves cost, but test retrieval from far back before you ship, because that is the capability lost.
  • The cost still grows with context length however you tune it? That is the quadratic FLOP count, which none of these touch. Chapter 22 looks at architectures that change it.

In PyTorch, torch.nn.functional.scaled_dot_product_attention chooses a fused kernel for you when the inputs allow it (PyTorch 2.0 onwards, as chapter 09 noted); the listing below shows how a GQA layer calls it. It is not run here, and it returns a tensor of shape (B, h, T, dk).

import torch.nn.functional as F

# q: (B, H, T, d), k and v: (B, KV, T, d). Repeat each KV head H // KV times to match the query heads.
k = k.repeat_interleave(H // KV, dim=1)
v = v.repeat_interleave(H // KV, dim=1)
o = F.scaled_dot_product_attention(q, k, v, is_causal=True)   # may dispatch to a FlashAttention-style kernel

Key takeaways

  • Attention has two costs: the T² scores (training, prefill) and the KV cache that decode reads every step. Different techniques target each.
  • KV cache per token = 2 × layers × key/value heads × head width × bytes. For a Llama 3 8B shape in bf16, 32 heads give 512 KiB per token and 8 heads give 128 KiB.
  • Multi-query and grouped-query attention keep all the query heads and share key/value heads. They shrink the cache and speed up memory-bound decode, and barely change FLOPs.
  • Sliding windows score a band instead of a triangle and cap the cache at W entries per layer. Information can still travel about layers × (W − 1) positions through depth, but direct long-range lookups are lost, so models mix windowed and global layers.
  • FlashAttention is exact. It uses an online softmax (running max and sum, rescaled as blocks arrive) to compute attention tile by tile in fast memory, never writing the T × T matrix to HBM.
  • FlashAttention reduces memory and memory traffic, not the O(T²) FLOPs. The first two techniques change the model; the third does not.

Check your understanding

A model has 40 layers, 40 query heads of width 128 and 8 key/value heads, stored in bf16. Roughly how large is the KV cache for one 4,096-token sequence?

  1. About 0.3 GiB
  2. About 0.6 GiB
  3. About 1.25 GiB
  4. About 3.1 GiB
Per token: 2 × 40 layers × 8 heads × 128 × 2 bytes = 160 KiB, and 4,096 tokens is 0.625 GiB. 0.3 GiB forgets that both keys and values are stored. 1.25 GiB uses 4-byte numbers. 3.1 GiB counts all 40 query heads, which is what multi-head attention would cost, and is the tempting error because the cache depends on key/value heads only.

A team retrains a model with 8 key/value heads instead of 32 (query heads stay at 32). Which effect is correct?

  1. The attention score FLOPs fall by a factor of 4
  2. The model's total parameter count falls by about a factor of 4
  3. The outputs are identical, because the query heads are unchanged
  4. The KV cache falls by a factor of 4, which mainly speeds up memory-bound decode, while the score FLOPs stay the same
Scores are still computed for all 32 query heads, so FLOPs are unchanged (the first option confuses cache with compute). Only Wk and Wv shrink, a small share of the weights (the second option). The shared keys and values give a different function, so outputs change and the model needs training or uptraining.

A 24-layer model uses sliding-window attention with W = 1,000 on every layer. In principle, how far back can a token in the last layer be influenced by an input token?

  1. 999 positions: the window is a hard limit
  2. About 12,000 positions, half the layers
  3. About 24,000 positions, since each layer extends the reach by W − 1
  4. The whole sequence, however long
Information hops up to 999 positions per layer, so reach grows linearly with depth to about 24 × 999. The first option forgets the composition across layers. The last overstates it: reach is bounded, and even inside the bound a fact must survive many lossy hops, which is why direct long-range retrieval still degrades.

Which statement about FlashAttention is correct?

  1. It computes the same result as standard attention, up to rounding, without storing the T × T score matrix in main GPU memory
  2. It approximates the softmax to reduce FLOPs from O(T²) to O(T)
  3. It reduces the KV cache by sharing key/value heads
  4. It restricts each token to a local window of the sequence
It reorders the computation into tiles with an online softmax, so the result is exact and the matrix stays in on-chip memory. The FLOPs remain quadratic (the second option describes linear attention). Sharing heads is GQA and restricting positions is a window; both change the model, FlashAttention does not.

An online softmax has running maximum m = 2 and running sum l = 1.3679. A new block of scores [3, 0] arrives. What is the new running sum, relative to the new maximum 3?

  1. About 2.42, by adding e3−3 + e0−3 to the old sum
  2. About 1.55, by scaling the old sum by e2−3 and then adding e0 + e−3
  3. About 4.77, by scaling the old sum by e3−2
  4. About 22.5, by adding e3 + e0 to the old sum
The old terms were measured against the old maximum 2, so they must be shrunk by e2−3 = 0.368: 1.3679 × 0.368 + 1 + 0.0498 = 1.553. Adding without rescaling (2.42) mixes two different reference points. Scaling the wrong way (4.77) inflates the old terms. Using raw exponentials (22.5) is the unstable form the maximum subtraction exists to avoid.

A training run at 64K context fails with out-of-memory errors inside attention although the weights and optimiser state fit comfortably. Which first change alters the model the least?

  1. Cut the key/value heads from 32 to 8
  2. Add a 4,096-token window to every layer
  3. Switch to a fused FlashAttention-style kernel
  4. Add more query heads so each head is cheaper
The pressure comes from storing T × T score matrices, and the fused kernel removes that storage without changing any output. Fewer key/value heads shrinks the generation cache, not the scores, and changes the model. A window changes what the model can read. More query heads add score matrices.

Lab 6: The Model Resource Calculator

Before anyone trains or serves a model, three numbers decide whether the plan is real: how many parameters it has, how many floating-point operations it needs, and how many bytes must sit in GPU memory while it runs. Chapter 16 derived all three from the shape of a Transformer, and chapter 18 asked how big the model should be for a budget. In this lab you turn both chapters into a calculator, in plain Python, and check it against published models: Llama 3, Llama 2, GPT-2, GPT-3, Mixtral and Chinchilla. You count parameters (with grouped-query attention, SwiGLU and mixtures of experts), count FLOPs and turn them into days and GPU-hours, account for training memory, work out the KV cache and the bandwidth limit on decoding, compute compute-optimal sizes, and finally choose a model size that minimises training plus serving cost.

Why this lab matters

The expensive mistakes in deep learning are planning mistakes. A job that runs out of memory after twenty minutes on a rented cluster has already cost money; a run planned for three weeks that needs three months was a spreadsheet error, not bad luck; a model chosen at 70 billion parameters because "bigger is better" may cost twice as much to serve for a loss it could have reached with 35 billion. All of these are predictable on paper, from the configuration, before a single GPU is booked. The skill is not memorising numbers. It is knowing which few lines of arithmetic answer "will it fit, how long will it take, what will it cost to run", and being able to defend each term.

The lab also builds a habit that matters beyond models: check your formulas against things that are known. Every formula you write is tested against published sizes (8,030,261,248 parameters for Llama 3 8B, 3.8 × 1025 FLOPs for the 405B run, 128 KiB of cache per token) and against an independent way of counting. Where the formula does not reproduce a published number, as it does not for Chinchilla's 70 billion, you find out here, with the paper open, and not in a design review. Everything below is arithmetic on a handful of integers, so the whole check runs in a fraction of a second.

Pure arithmetic: no GPU, no clock, no network

Python 3.9 or newer and nothing else. Nothing is measured on your machine: every number is computed from a model shape, a datasheet figure or a fitted constant, so python3 check.py solution gives identical output everywhere and finishes in well under a second. Random property tests use seeded random model shapes and print their seed on failure (replay with python3 check.py solution 1 17, milestone 1, seed 17). Units follow the chapters: 1 GB is 109 bytes, FLOPs (small s) are a count of work and FLOP/s is a speed. The hardware figures in the starter file are the dense bf16 peaks and memory bandwidths from vendor datasheets as of this writing; they are dated facts, and the formulas do not depend on them.

What you'll build

Six milestones, each adding a group of functions that the next one uses:

  1. Counting parameters: attention with grouped-query heads, SwiGLU or GELU MLPs, norms, embeddings, tied or untied heads, and the active parameters of a mixture of experts. Check against eight published models.
  2. FLOPs, time and cost: the weights that take part in matrix products, 6 FLOPs per weight per token plus the attention-score term, and the division by peak speed and MFU that gives days and GPU-hours.
  3. Memory for training: 16 bytes per parameter of state, the Korthikanti activation formula in three variants, and the largest microbatch that fits a card.
  4. Inference: the KV cache, how many sequences fit beside the weights, and the tokens-per-second limit set by memory bandwidth, with the ridge point where decoding turns compute-bound.
  5. Compute-optimal sizes: the parametric loss L(N, D), its closed-form optimum under C = 6ND, the 20-tokens-per-parameter rule, and the price of missing the optimum.
  6. Lifetime cost: add the cost of serving, and find the model size that reaches a target loss at the least total FLOPs.

Milestone 1: counting parameters

A parameter is one learned number, and nearly all of them live in matrices, so counting them is multiplying shapes. Chapter 16 gave the recipe for a modern decoder, and this milestone writes it as six small functions so that each term can be tested alone:

  • Attention has four matrices: Wq and Wo are C × C, and Wk, Wv are C × (KV · dk). With grouped-query attention (GQA, chapter 19) there are fewer key/value heads than query heads (8 against 32 for Llama 3 8B), so the keys and values are a quarter as wide and the attention block shrinks from 4C2 to 2.5C2. Older models like GPT-2 and Llama 2 7B have KV = H.
  • The MLP has three C × F matrices for a SwiGLU (gate, up, down; chapter 10) and two for a GELU MLP. GPT-style models use F = 4C; Llama-style models pick F so that the three matrices cost about the same as two with 4C.
  • Norms add C weights per RMSNorm (Llama) or 2C per LayerNorm with a bias (GPT-2), two per block and one at the end. Biases, if the model has them, add a vector per projection.
  • Embeddings are a V × C table for the input; the output head is another V × C unless it is tied to the input table (GPT-2 ties, Llama 3 does not). GPT-2 also has a learned table of position vectors.
  • A mixture of experts (chapter 20) replaces the one MLP by E of them and a small router (C × E weights) that picks top_k for each token. The model stores E MLPs but each token uses only top_k of them, so there are two honest answers to "how many parameters", and the function takes active=True for the second.

Common misconception

"A model's parameter count is the number in its name." Names are rounded and sometimes loose, and papers disagree about what to count: with or without embeddings, with or without every expert, with or without the output head if tied. A scaling-law constant fitted with non-embedding N does not transfer to a formula that uses the total. Whenever you reuse a number, ask which N it is.

def head_dim(cfg):
    """d_k = C / H."""
    return cfg.C // cfg.H

def attn_params(cfg):
    """W_q (C x C), W_k and W_v (C x KV*d_k each), W_o (C x C), plus biases if cfg.bias."""
    kv_width = cfg.KV * head_dim(cfg)
    n = cfg.C * cfg.C + 2 * cfg.C * kv_width + cfg.C * cfg.C
    if cfg.bias:
        n += cfg.C + 2 * kv_width + cfg.C
    return n

def mlp_params(cfg):
    """ONE expert's MLP: 3 matrices for SwiGLU, 2 for GELU, plus biases if cfg.bias."""
    mats = 3 if cfg.mlp == "swiglu" else 2
    n = mats * cfg.C * cfg.F
    if cfg.bias:
        n += (mats - 1) * cfg.F + cfg.C            # hidden-layer biases, then the output bias
    return n

def norm_params(cfg):
    """The two normalisations in one block."""
    per = cfg.C if cfg.norm == "rms" else 2 * cfg.C
    return 2 * per

def block_params(cfg, active=False):
    """One layer: attention + MLP(s) + router + norms. active=True counts only top_k experts."""
    n_exp = cfg.top_k if active else cfg.experts
    router = cfg.C * cfg.experts if cfg.experts > 1 else 0
    return attn_params(cfg) + n_exp * mlp_params(cfg) + router + norm_params(cfg)

def embedding_params(cfg):
    """Input table V*C, a separate output head V*C unless tied, and a learned position table."""
    return cfg.V * cfg.C * (1 if cfg.tied else 2) + cfg.positions * cfg.C

def count_params(cfg, active=False):
    """All parameters: L blocks + embeddings + the final norm. active=True: per-token (MoE) count."""
    final_norm = cfg.C if cfg.norm == "rms" else 2 * cfg.C
    return cfg.L * block_params(cfg, active) + embedding_params(cfg) + final_norm

Milestone 2: FLOPs, time and cost

A FLOP is one floating-point operation, an addition or a multiplication, and the work of a run is counted in them. The whole count rests on one formula: multiplying an (m, k) matrix by a (k, n) matrix makes m × n outputs, each a sum of k products, so 2mkn FLOPs. Applied to a linear layer on n tokens that is 2 FLOPs per weight per token on the forward pass, and the backward pass needs two such products (one for the weight gradient, one for the input gradient), so 4 more. A training run over D tokens therefore costs about 6ND FLOPs, where N counts the weights that take part in matrix products (chapter 16 derives this and checks it by instrumenting a real forward and backward pass).

Two refinements make the calculator more honest than the rule of thumb, and both are in chapter 16:

  • Which weights count. The input embedding is a lookup, not a product, so it costs no FLOPs; the output head is a product and does. Norms and biases are a few operations per number, not matrix products. For a mixture of experts only the top_k active experts' matrices are multiplied. matmul_weights captures this, and for a dense model it is the active parameter count minus norms and the input table (the checker verifies exactly that on random shapes).
  • The attention scores have no weights. Q·KT and (softmax weights)·V are matrix products between activations. For a context of T tokens they add 12 · L · C · T FLOPs per training token (4TC per layer forward, three times that with the backward pass), a term that grows with context while the weight term does not. It is small at T = 2,048 and dominant at 128K.

FLOPs are the same on any hardware; time is FLOPs divided by the speed you actually get. A GPU's datasheet gives a peak (989 TFLOP/s dense bf16 for an H100 SXM, 312 for an A100), and a real run reaches a fraction of it, the model FLOPs utilisation (MFU) of PaLM (Chowdhery et al., 2022): the model FLOP/s you actually deliver, divided by peak. Well-tuned large runs land at 30% to 50%. So

seconds = FLOPs / (peak × MFU × number of GPUs),   GPU-hours = FLOPs / (peak × MFU) / 3600

The MFU rows of the output are the single most useful result in the milestone: the same 405B plan takes 135.7 days at 20% and 54.3 days at 50%. A guess of "about 40%" is the biggest source of error in a schedule, so you want it to be a measurement. This is a calculation, not a report of how long Meta's run took; real runs also lose time to failures and restarts (A3 chapter 05).

def matmul_flops(m, k, n):
    """Multiplying an (m, k) matrix by a (k, n) matrix: m*n outputs, k multiplies and k adds each."""
    return 2 * m * k * n

def matmul_weights(cfg):
    """Weights that take part in a matrix product for one token: attention matrices, the MLP matrices of
    the top_k active experts, the router, and the output head. Norms, biases and the input lookup excluded."""
    kv_width = cfg.KV * head_dim(cfg)
    attn = 2 * cfg.C * cfg.C + 2 * cfg.C * kv_width
    mats = 3 if cfg.mlp == "swiglu" else 2
    mlp = cfg.top_k * mats * cfg.C * cfg.F
    router = cfg.C * cfg.experts if cfg.experts > 1 else 0
    return cfg.L * (attn + mlp + router) + cfg.C * cfg.V

def train_flops_per_token(cfg, T):
    """6 FLOPs per matmul weight, plus 12*L*C*T for the QK^T and (weights)V products (chapter 16)."""
    return 6 * matmul_weights(cfg) + 12 * cfg.L * cfg.C * T

def rule_6nd(N, D):
    """The rule of thumb: 6 * N * D."""
    return 6 * N * D

def train_flops(cfg, tokens, T):
    """Exact-count training FLOPs for `tokens` tokens at sequence length T."""
    return train_flops_per_token(cfg, T) * tokens

def train_seconds(flops, peak, mfu, n_gpus=1):
    """Wall-clock seconds: FLOPs / (peak FLOP/s per GPU * MFU * number of GPUs)."""
    return flops / (peak * mfu * n_gpus)

def gpu_hours(flops, peak, mfu):
    """GPU-hours (independent of how many GPUs share the work)."""
    return flops / (peak * mfu) / 3600

def mfu_from_throughput(model_flops_per_s_per_gpu, peak):
    """Model FLOPs utilisation: achieved model FLOP/s over the datasheet peak."""
    return model_flops_per_s_per_gpu / peak

Milestone 3: memory for training

Compute decides how long a run takes; memory decides whether it starts. GPU memory is a hard wall: when the total exceeds the card, the job stops with an out-of-memory error. Training holds two kinds of memory, and they are best counted separately.

Model states depend only on the parameter count. Mixed-precision training with AdamW (A0 chapter 10; chapter 17) keeps five numbers per parameter: a bf16 weight (2 bytes), a bf16 gradient (2), an fp32 master copy of the weight (4) and Adam's two running averages in fp32 (4 and 4). That is 2 + 2 + 4 + 4 + 4 = 16 bytes per parameter, the accounting of the ZeRO paper (Rajbhandari et al., 2020). It is a baseline, not a law: it explains why state_bytes takes the five sizes as keyword arguments, so that you can ask what an 8-bit optimiser would save.

Activations are the intermediate tensors the forward pass saves for the backward pass. Korthikanti et al. (2022) counted them tensor by tensor for a GPT-style layer in 16-bit numbers: with sequence length s, microbatch b, width h and a heads, one layer saves s · b · h · (34 + 5 · a · s / h) bytes. The 34 s b h part is linear in the sequence; the 5 a s2 b part is the (s, s) attention tables, quadratic in s. Two standard techniques attack the terms. A fused attention kernel (FlashAttention, chapter 19) never stores the (s, s) tables, so the second part vanishes. Recomputation (gradient checkpointing, Chen et al., 2016) stores only each layer's input, 2 s b h bytes, and recomputes the rest in the backward pass at the price of roughly a third more compute. The formula is for a GELU block with full multi-head attention, so for Llama-style blocks treat it as an estimate within tens of per cent, as chapter 16 says.

def state_bytes(n, weights=2, grads=2, master=4, m=4, v=4):
    """Bytes of model state: bf16 weights and gradients, fp32 master copy and Adam's two moments."""
    return n * (weights + grads + master + m + v)

def act_bytes_per_layer(s, b, h, a, mode="full"):
    """Korthikanti et al. activations for one layer, 16-bit: 'full' s*b*h*(34 + 5*a*s/h),
    'flash' s*b*h*34 (no stored score matrices), 'recompute' 2*s*b*h (only the layer input)."""
    if mode == "full":
        return s * b * h * (34 + 5 * a * s / h)
    if mode == "flash":
        return s * b * h * 34
    if mode == "recompute":
        return 2 * s * b * h
    raise ValueError(f"unknown activation mode {mode!r}")

def activation_bytes(cfg, s, b, mode="full"):
    """Activations of the whole stack: L layers (width cfg.C, cfg.H heads)."""
    return cfg.L * act_bytes_per_layer(s, b, cfg.C, cfg.H, mode)

def training_memory(cfg, s, b, mode="full"):
    """{'states': ..., 'activations': ..., 'total': ...} in bytes, using 16 bytes per parameter."""
    states = state_bytes(count_params(cfg))
    acts = activation_bytes(cfg, s, b, mode)
    return {"states": states, "activations": acts, "total": states + acts}

def fits(total_bytes, gpu_mem, overhead=3 * GB):
    """True if the total plus a fixed allowance for the CUDA context and fragmentation fits the card."""
    return total_bytes + overhead <= gpu_mem

def max_microbatch(cfg, s, mode, gpu_mem, overhead=3 * GB):
    """The largest microbatch b that fits on one card (0 if even b = 1 does not)."""
    b = 0
    while fits(training_memory(cfg, s, b + 1, mode)["total"], gpu_mem, overhead):
        b += 1
        if b >= 4096:
            break
    return b

def max_trainable_params(gpu_mem, overhead=3 * GB):
    """The most parameters whose 16-bytes-each states fit the card, with nothing left for activations."""
    return (gpu_mem - overhead) / 16

Milestone 4: inference, the KV cache and the bandwidth limit

Serving drops the gradients and the optimiser state: the states shrink to the weights alone, 2 bytes per parameter in bf16 (a quarter of that in 4-bit quantisation, A3 chapter 19). A new item appears. To produce the next token, attention needs the keys and values of every earlier token, and recomputing them for each new token would be wasteful, so they are stored: the KV cache. For each token, in each of the L layers, it holds one key and one value of KV heads times dk numbers:

KV bytes per token = 2 × L × KV × dk × (bytes per number)

For Llama 3 8B in bf16 that is 2 × 32 × 8 × 128 × 2 = 131,072 bytes, 128 KiB per token, about 1.07 GB for one 8,192-token conversation. With full multi-head attention (KV = H = 32, as in Llama 2 7B) the cache is four times larger, 512 KiB per token, which is the reason GQA exists. Memory capacity then limits how many conversations a card can serve at once: the weights are paid once, the cache once for every sequence.

The second constraint is speed. To generate one token the GPU must read every weight (and the sequence's cache) from memory, and it does only 2 FLOPs per weight read. Compare the two ways of spending a step: the memory time, bytes read divided by the memory bandwidth, and the compute time, FLOPs divided by the peak. Whichever is larger sets the step time (the idea of the roofline model of Williams, Waterman and Patterson, 2009). With one sequence the memory time dominates by a factor of hundreds, so decoding is limited by bytes, not FLOP/s: at 3.35 TB/s an H100 cannot read the 16.1 GB of Llama 3 8B's weights more than about 209 times a second, which is 209 tokens per second for one user, however fast its arithmetic units are. Batching shares the weight reads: with b sequences in the batch, one pass over the weights produces b tokens, so throughput rises almost linearly with b until the arithmetic units become the limit. The batch where the two times are equal is the ridge: batch = peak × weight bytes / (2 × matmul weights × bandwidth), which is 316 for this model on an H100.

Systems connection

This is the same arithmetic as the roofline in Zero to Systems chapter 21 and the capacity model of chapter 22: a kernel is memory-bound when its arithmetic intensity (FLOPs per byte) is below the machine's ratio of peak FLOP/s to bandwidth, here 989 × 1012 / 3.35 × 1012 = 295 FLOPs per byte. A decode step at batch 1 performs 1 FLOP per byte of bf16 weights, hundreds of times too little to keep the arithmetic units busy. The cure is the same as for any memory-bound system: reuse each byte more (batching), or move fewer bytes (quantisation, GQA). Utilisation numbers like MFU play the part of CPU utilisation in queueing theory: a low one tells you to profile, not to buy more machines.

def kv_bytes_per_token(cfg, bytes_per=2):
    """Keys and values of one token in every layer: 2 * L * KV * d_k * bytes."""
    return 2 * cfg.L * cfg.KV * head_dim(cfg) * bytes_per

def kv_cache_bytes(cfg, ctx, batch=1, bytes_per=2):
    """The cache of `batch` sequences, each `ctx` tokens long."""
    return kv_bytes_per_token(cfg, bytes_per) * ctx * batch

def weight_bytes(cfg, bytes_per=2):
    """All parameters at `bytes_per` each (a mixture of experts keeps every expert in memory)."""
    return count_params(cfg) * bytes_per

def max_batch(cfg, ctx, gpu_mem, w_bytes=2, kv_bytes=2, overhead=3 * GB):
    """How many sequences of length ctx fit next to the weights (0 if the weights alone do not fit)."""
    free = gpu_mem - overhead - weight_bytes(cfg, w_bytes)
    per_seq = kv_cache_bytes(cfg, ctx, 1, kv_bytes)
    return max(0, int(free // per_seq))

def decode_step_seconds(cfg, ctx, batch, bw, peak, w_bytes=2, kv_bytes=2):
    """One decode step for `batch` sequences at context ctx: the slower of reading the bytes
    (weights once, plus every sequence's cache) and doing the FLOPs (2 per weight, 4*L*C*ctx for attention)."""
    mem_time = (weight_bytes(cfg, w_bytes) + kv_cache_bytes(cfg, ctx, batch, kv_bytes)) / bw
    flop_time = batch * (2 * matmul_weights(cfg) + 4 * cfg.L * cfg.C * ctx) / peak
    return max(mem_time, flop_time)

def decode_tokens_per_second(cfg, ctx, batch, bw, peak, w_bytes=2, kv_bytes=2):
    """Tokens per second summed over the batch."""
    return batch / decode_step_seconds(cfg, ctx, batch, bw, peak, w_bytes, kv_bytes)

def ridge_batch(cfg, bw, peak, w_bytes=2):
    """The batch size at which weights-only decoding stops being memory-bound:
    batch * 2 * W / peak == bytes / bw  ->  batch = peak * bytes / (2 * W * bw)."""
    return peak * weight_bytes(cfg, w_bytes) / (2 * matmul_weights(cfg) * bw)

def loss(N, D, fit):
    """L(N, D) = E + A / N^alpha + B / D^beta."""
    E, A, B, a, b = fit
    return E + A / N ** a + B / D ** b

def optimum(C, fit):
    """The (N, D, loss) minimising L(N, D) subject to 6*N*D = C (closed form, chapter 18)."""
    E, A, B, a, b = fit
    G = (a * A / (b * B)) ** (1 / (a + b))
    N = G * (C / 6) ** (b / (a + b))
    D = C / (6 * N)
    return N, D, loss(N, D, fit)

def chinchilla_rule(C, ratio=20):
    """The rule of thumb D = ratio * N with C = 6*N*D: returns (N, D)."""
    N = math.sqrt(C / (6 * ratio))
    return N, ratio * N

def isoflop_loss(C, N, fit):
    """Loss of a model with N parameters trained to use exactly C FLOPs (D = C / 6N)."""
    return loss(N, C / (6 * N), fit)

def excess_loss(C, factor, fit):
    """How much worse than the optimum a model `factor` times the optimal size is, at the same budget."""
    N_opt = optimum(C, fit)[0]
    return isoflop_loss(C, factor * N_opt, fit) - optimum(C, fit)[2]

Milestone 6: lifetime cost and over-training

Chinchilla minimises the bill for training. A model that will be queried billions of times has a second bill, and it grows with the size of the model: every token it generates costs about 2N FLOPs (and reads N weights). If two models reach the same loss, the smaller one is cheaper to use forever. Sardana et al. (2023, "Beyond Chinchilla-Optimal: Accounting for Inference in Language Model Scaling Laws") add that cost to the Chinchilla analysis and find that a model with heavy expected usage should be smaller and trained for longer than the compute-optimal one. In this milestone you do their calculation in its simplest form.

Choose a target loss, the quality you need. For any model size N, the fitted law says how many tokens D(N) it takes to reach that loss: solve B / Dβ = target − E − A / Nα for D. If the right-hand side is zero or negative, that N can never reach the target, whatever the data. The lifetime cost of a candidate is then

6 · N · D(N)  +  2 · N · (tokens the model will generate)

and it is a function of N alone. It is enormous just above the smallest feasible size (D explodes) and enormous for large N (6ND explodes), with one minimum between: a one-dimensional search, which you can do by ternary search on log N. With no serving, the minimum is exactly the compute-optimal model for the budget it costs (the checker verifies this against your milestone 5 formula). With serving, the minimum moves to smaller models trained on more data.

def lifetime_flops(N, D, inference_tokens):
    """Training 6*N*D plus serving 2*N FLOPs for each token generated."""
    return 6 * N * D + 2 * N * inference_tokens

def tokens_for_loss(N, target, fit):
    """The D that makes L(N, D) == target, or None if N is too small to reach it at any D."""
    E, A, B, a, b = fit
    room = target - E - A / N ** a
    if room <= 0:
        return None
    return (B / room) ** (1 / b)

def best_size_for_loss(target, inference_tokens, fit):
    """The (N, D, lifetime FLOPs) reaching `target` loss at the least total cost of training plus serving.

    For each N the data D is fixed by the target (tokens_for_loss); lifetime_flops is then a function of
    N alone that falls and rises, so a ternary search over log N finds its minimum.
    """
    E, A, B, a, b = fit
    n_min = (A / (target - E)) ** (1 / a)           # below this no amount of data reaches the target
    lo, hi = math.log(n_min * (1 + 1e-9)), math.log(n_min * 1e4)

    def cost(logn):
        N = math.exp(logn)
        return lifetime_flops(N, tokens_for_loss(N, target, fit), inference_tokens)

    for _ in range(200):
        m1, m2 = lo + (hi - lo) / 3, hi - (hi - lo) / 3
        if cost(m1) < cost(m2):
            hi = m2
        else:
            lo = m1
    N = math.exp((lo + hi) / 2)
    D = tokens_for_loss(N, target, fit)
    return N, D, lifetime_flops(N, D, inference_tokens)

Going further

  • Add your own model. Add a Config for a model you use (its Hugging Face config.json lists hidden size, layers, heads, key/value heads, intermediate size and vocabulary) and compare your count with the model card. If it is off by more than 1%, find the missing term: biases, tied embeddings, a different MLP, or extra matrices such as relative positions.
  • Chinchilla's missing 5 billion. Read the Gopher and Chinchilla papers and find where the extra weights are. Add a field to Config for them and make the 70B count land within 1%.
  • Tensor and pipeline parallelism. Divide the states, activations and KV cache over g GPUs (ZeRO stage 1, 2 and 3 shard the optimiser state, gradients and weights in turn; A3 chapter 03). For Llama 3 8B, what is the smallest g for which a microbatch of 1 at 8,192 tokens with fused attention fits an 80 GB card?
  • Prefill versus decode. Processing a prompt of T tokens costs 2 × weights × T FLOPs but reads the weights once, so it is compute-bound for any T above a few hundred. Write prefill_seconds and compare it with the time to decode 500 tokens, for T = 1,000 and T = 32,000.
  • A mixture of experts decodes differently. With batch 1 only top_k experts per layer are read; with a large batch nearly all of them are. Model the expected number of distinct experts touched by a batch of b tokens (assume a uniform router) and fix the decode speed of the Mixtral row.

What you learned

  • Parameters are counted by listing matrices: attention (narrower keys and values under GQA), MLP (three matrices for SwiGLU), norms, embeddings and an optional separate head. A count from a configuration reproduces published sizes to the last weight for most models, and a mismatch (Chinchilla's 70B) is a finding to investigate.
  • A matrix product costs 2mkn FLOPs, which gives 6 FLOPs per weight per token for training and 2 for inference. 6ND ignores the attention scores, whose 12LCT FLOPs per token dominate at very long context. Time is FLOPs over peak times MFU, and MFU is the largest uncertainty.
  • Training state is 16 bytes per parameter with mixed-precision AdamW, so an 80 GB card holds the states of about 4.8 billion parameters. Activations scale with microbatch, sequence and depth, with a quadratic term that fused kernels remove and recomputation trades for compute.
  • Serving needs the weights plus a KV cache of 2LKV·dk numbers per token. Decoding one sequence is limited by memory bandwidth, batching shares the weight reads up to the ridge, and memory capacity usually caps the batch before compute does.
  • The loss law L(N, D) = E + A/Nα + B/Dβ has a closed-form optimum under C = 6ND, about 20 tokens per parameter for the refit constants. The optimum is flat: half or twice the size costs about 0.01 nats.
  • Add the cost of serving and the best model for a given quality gets smaller and is trained far longer. The method (target loss, D from the law, minimise training plus serving FLOPs) is robust; the constants are not.

A dense model has C = 4,096, L = 32, full multi-head attention (KV = H), a GELU MLP with F = 4C, no biases, and V = 50,000 with a tied head. Roughly how many parameters does it have?

  1. About 0.4 billion, since only the MLP matters
  2. About 13 billion, because every layer has 12C2 weights per head
  3. About 6.6 billion: 32 × 12 × 4,0962 is 6.4 billion, plus a 0.2 billion embedding table
  4. About 3.2 billion, since a tied head halves the model
A block has 4C2 attention weights and 8C2 MLP weights, 12C2 = 201 million; times 32 layers is 6.44 billion. The tied embedding adds V × C = 0.2 billion. Tying removes a second table (0.2 billion), not half the model, and the 12C2 is per layer, not per head.

An H100 delivers 400 TFLOP/s of model FLOPs while training, against a datasheet peak of 989 TFLOP/s. A colleague proposes buying 20% more GPUs to finish 20% sooner. What does the number suggest?

  1. Check why utilisation is only 40% first (communication, memory-bound kernels, the input pipeline); extra GPUs often lower MFU further
  2. Buy the GPUs: time is inversely proportional to the number of GPUs
  3. The run is memory-bound, so add memory instead
  4. MFU of 40% is a bug; it must be 100% for a correct run
MFU is the fraction of peak arithmetic turned into model FLOPs, and 30% to 50% is normal for large runs. Where the rest goes decides whether more GPUs help; adding GPUs usually adds communication. Time is not simply inverse to GPU count when utilisation falls with scale, memory capacity is a separate constraint, and 100% is unreachable.

Llama 3 8B uses 8 key/value heads against 32 query heads. Compared with the same model with 32 key/value heads, what changes?

  1. Parameters are cut by three quarters
  2. Training FLOPs per token fall by three quarters
  3. Nothing about memory; only speed changes
  4. The KV cache shrinks by 4 times and the attention block loses about 37% of its weights; the MLP is unchanged
The cache stores KV × dk numbers per layer per token, so 8 instead of 32 is a quarter. Wk and Wv shrink to a quarter, taking attention from 4C2 to 2.5C2, a 37.5% cut, but attention is under a fifth of the model, so total parameters fall by about 9% (0.8 of 8.8 billion), not 75%. The MLP and the query and output matrices are untouched.

Decoding one sequence with an 8B bf16 model on a GPU with 2 TB/s of memory bandwidth and 500 TFLOP/s of peak speed. Which estimate of tokens per second is closest?

  1. About 31,000, from 500 TFLOP/s divided by 16 GFLOPs per token
  2. About 125, from 2 TB/s divided by the 16 GB of weights read for every token
  3. About 2,000, from the bandwidth in GB/s
  4. About 500, from the peak in TFLOP/s
Each token must read every weight once: 2,000 GB/s over 16 GB is 125 tokens a second, and the arithmetic (about 16 GFLOPs per token) is a small fraction of the available FLOP/s. The first option divides by the arithmetic alone, which is the training-style bound that decoding does not hit; the other two mix up units.

At a budget of 1022 FLOPs the compute-optimal model has 9 billion parameters. A team picks 4.5 billion parameters, trained on twice as many tokens, because it is cheaper to serve. According to this lab's calculation, what does that cost in training loss?

  1. About 0.5 nats, since the model is half as large
  2. About 0.04 nats, as for a model four times too small
  3. About 0.01 nats, because the bottom of the IsoFLOP curve is flat
  4. Nothing: for the same budget the loss is identical
Milestone 5's table gives 0.0099 nats for half the optimal size (and 0.0100 for twice). A factor of four costs about 0.04, so the second option is for a different choice; the loss is not identical, only close; and 0.5 nats would be far outside the shape of the curve.

You expect your model to generate ten trillion tokens over its lifetime. How should that change the choice of model size and training tokens for a fixed target loss, compared with the compute-optimal (Chinchilla) choice?

  1. Make the model larger and train on fewer tokens, to get more capability per token
  2. Make the model smaller and train on more tokens: training cost is paid once but serving cost scales with parameters
  3. No change: compute-optimal training already includes serving
  4. Train the same model for fewer tokens and rely on a larger batch
Serving costs about 2N FLOPs per generated token, so with heavy use each saved parameter pays back many times.

Lab 5: A BPE Tokeniser & Decoders

A language model sits between two small programs. Before it, a tokeniser turns text into integers; after it, a decoder turns a probability distribution back into one integer, over and over, until a text exists. Chapter 13 built byte-pair encoding and chapter 15 built the samplers with NumPy. In this lab you write both ends in plain Python: train BPE on a small corpus, encode and decode any string at all (emoji and broken bytes included) with an exact round trip, and then implement temperature, top-k, top-p and min-p sampling and a generation loop. A checker with independent reference implementations tests every milestone, and a tiny language model lets you watch greedy decoding loop and the tail of the distribution do its damage.

Why this lab matters

Tokenisation and decoding are the two stages of the pipeline that are not learned by gradient descent, which is exactly why they hide bugs. A tokeniser that does not round-trip silently corrupts every prompt that contains a character it handles badly. A tokeniser that merges across word boundaries wastes vocabulary and behaves strangely on spaces. A top-p filter that is off by one token changes the text of every conversation at the edges of its range, and nobody notices because the output is still fluent. A temperature of zero that divides by zero crashes a production service the first time a customer sets it. None of these bugs announces itself with a stack trace on the inputs you tried by hand; they appear on the first emoji, the first empty string, the first prompt with a tab.

The second reason is that these two programs are where you spend and shape the model's budget. The tokeniser decides how many tokens a document costs and how much of the context window it uses; the decoder decides how confident or adventurous the same model sounds. Writing both once, and passing tests that compare them with deliberately plain reference code, is the quickest way to stop treating either as a setting on an API. Karpathy's minbpe repository and his lecture Let's build the GPT Tokenizer follow the same path for the tokeniser, and the sampling code here is the same few lines that sit at the end of nanoGPT's generate; the code, corpus and checks below are original.

Pure Python, seeded, a few seconds

Python 3.9 or newer and nothing else: no NumPy, no downloads. The training corpus is a 4.9 KB text file in the lab folder (original prose with some accents, Japanese and emoji so that multi-byte characters appear), so python3 check.py solution finishes in about two seconds and prints the same numbers every time. Random property tests are seeded and print their seed when they fail; replay one with python3 check.py solution 3 17, which means milestone 3, seed 17. The reference implementations inside check.py are written differently from the solution on purpose (one merge at a time over the whole word, a plain loop for the filters), so a mistake cannot hide behind a shared helper. Everything here is byte-level, as in GPT-2 and its successors: the base vocabulary is the 256 possible byte values, so there is no unknown token and no text that cannot be encoded.

What you'll build

Five milestones, each building on the last:

  1. Bytes, pair counts and one merge: UTF-8 as a list of integers, counting adjacent pairs weighted by word frequency, merging a pair in a list, and the tie-break rule.
  2. Training: the BPE loop of chapter 13 over a corpus, producing an ordered merge table.
  3. Encode and decode: apply the merges to new text, expand ids back to bytes, and prove the round trip on arbitrary strings.
  4. Reshaping a distribution: softmax with temperature, then top-k, top-p and min-p filters that renormalise.
  5. Drawing and generating: inverse-CDF sampling, greedy decoding, one decoding step with all the options, and a generation loop with a stop token.

Notation is the course's. A token id is an integer; ids 0 to 255 are the 256 byte values; a merge table is a dictionary {(a, b): new_id} whose insertion order is the order in which merges were learned, so the first merge gets id 256, the second 257, and so on. The vocabulary size is V = 256 + (number of merges). Probabilities are lists of V floats that sum to 1; logits are the model's raw scores before the softmax, as in chapters 12 and 15.

Milestone 1: bytes, pair counts and one merge

A tokeniser has to start from something that can represent every string without exception. The answer used by GPT-2 and everything since is to start from bytes. A byte is a number from 0 to 255, and UTF-8, the encoding of nearly all text on the web, turns every character into one to four bytes: ASCII letters take one, most accented European letters two, most Japanese characters three, most emoji four. That is a vocabulary of 256 base tokens that can spell anything, so a tokeniser built on it never meets an unknown word. The cost is that a rare character is several tokens, which is why chapter 13 measured Hindi and Japanese as more expensive than English.

import solution as m
for t in ["hi", "é", "東", "👍"]:
    print(repr(t), len(t), "character(s) ->", m.utf8_ids(t))
print(m.pretokenise("Hello, world! It's 2026."))
'hi' 2 character(s) -> [104, 105]
'é' 1 character(s) -> [195, 169]
'東' 1 character(s) -> [230, 157, 177]
'👍' 1 character(s) -> [240, 159, 145, 141]
['Hello', ',', ' world', '!', ' It', "'", 's', ' 2026', '.']

The second line of output shows the other given piece. BPE does not run over a whole document at once. The regular expression SPLIT cuts text into pieces: a run of letters with its leading space (' world'), a run of digits (' 2026'), a run of punctuation, or white space. Merges happen inside a piece, never across two, so no token will ever be "dog." or "of the". Chapter 13 explains the GPT-2 pattern this one imitates; the standard library's re has no \p{L}, so letters are written [^\W\d_].

Now the first half of the algorithm. Training counts how often each adjacent pair of tokens occurs, finds the most common one, and fuses it into a new token. Counting over a million characters on every round would be slow, so, as in chapter 13, count each distinct piece once and weight its pairs by how often the piece occurs. Take the classic toy corpus of Sennrich, Haddow and Birch (2016): " low" five times, " lower" twice, " newest" six times and " widest" three times (here with a leading space on each word, the way the regular expression keeps it).

import solution as m
from collections import Counter
text = " low" * 5 + " lower" * 2 + " newest" * 6 + " widest" * 3
freqs = Counter(m.pretokenise(text))
seqs = {w: m.utf8_ids(w) for w in freqs}
print(dict(freqs))
pairs = m.count_pairs(seqs, freqs)
name = lambda p: "".join(chr(i) for i in p).replace(" ", "_")
for p, c in pairs.most_common(5):
    print(f"{name(p):>3} {p}  {c}")
print("best:", m.best_pair(pairs))
print(m.merge_pair(seqs[" newest"], (101, 115), 256))
{' low': 5, ' lower': 2, ' newest': 6, ' widest': 3}

 st (115, 116)  9
 we (119, 101)  8
 _l (32, 108)  7
 lo (108, 111)  7

[32, 110, 101, 119, 256, 116]

Read the counts. "es" occurs 9 times (6 in newest, 3 in widest), and so does "st": a tie. A deterministic tokeniser needs a rule for ties, or two runs on the same data can learn different vocabularies. The rule here, the same as in chapter 13, is the smaller first id wins, then the smaller second id, so (101, 115) beats (115, 116). The last line merges that pair in " newest": the bytes [32, 110, 101, 119, 101, 115, 116] become [32, 110, 101, 119, 256, 116], where 256 is the new token "es".

Merging looks trivial and has one trap. Scan left to right and consume pairs as you find them: in [5, 5, 5] merging the pair (5, 5) gives [9, 5], not [9, 9], because the middle 5 is already used by the first merge. Every serious BPE implementation does it this way, and the checker's example [5, 5, 5, 5] is there to catch an implementation that does not. Also build a new list and leave the input alone; the training loop reuses its lists.

Common misconception

"A tokeniser's vocabulary is a list of words." For BPE it is a list of recipes: token 256 means "token 101 followed by token 115", and the bytes it stands for are found by expanding the recipe. The vocabulary is built on the bytes of the training text, which is why it can represent text it has never seen. Calling the tokens "subwords" is a fair summary of what the frequent ones look like; it is not what they are.

  • count_pairs: for each word, zip(ids, ids[1:]) gives its adjacent pairs; add freqs[word] (not 1) for each one.

Solution spoiler 
def utf8_ids(text):
    """The UTF-8 bytes of `text` as a list of ints in 0..255."""
    return list(text.encode("utf-8"))

def count_pairs(seqs, freqs):
    """Count adjacent pairs over distinct words, weighting each word by how often it occurs.

    seqs:  {word: [ids]}      freqs: {word: count}      returns Counter {(a, b): count}
    """
    pairs = Counter()
    for word, ids in seqs.items():
        for a, b in zip(ids, ids[1:]):
            pairs[(a, b)] += freqs[word]
    return pairs

def merge_pair(ids, pair, new_id):
    """Replace every non-overlapping occurrence of `pair` in `ids` by `new_id`, scanning left to right."""
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i + 1]) == pair:
            out.append(new_id)
            i += 2
        else:
            out.append(ids[i])
            i += 1
    return out

def best_pair(pairs):
    """The most frequent pair; ties go to the smaller first id, then the smaller second id."""
    return max(pairs, key=lambda pr: (pairs[pr], -pr[0], -pr[1]))

Milestone 2: training

Training is the loop of chapter 13 and nothing more. Start with each distinct piece as a list of byte ids. Then, n times: count the pairs (with weights), take the best one, give it the next free id, and merge it into every piece. The merge table remembers the pair and its new id in order, and that order is the whole product of training, because encoding will replay it. If no pair is left (every piece is already one token) there is nothing more to learn and training stops early; "ask for 500 merges, get 41" is correct on a tiny text.

Here are the first six merges on the toy corpus, printed from the vocabulary the merges define:

import solution as m
text = " low" * 5 + " lower" * 2 + " newest" * 6 + " widest" * 3
merges = m.train_bpe(text, 6)
vb = m.vocab_bytes(merges)
for (a, b), n in merges.items():
    print(f"{n}: {vb[a].decode()!r} + {vb[b].decode()!r} -> {vb[n].decode()!r}")
256: 'e' + 's' -> 'es'
257: 'es' + 't' -> 'est'
258: ' ' + 'l' -> ' l'
259: 'o' + 'w' -> 'ow'
260: ' l' + 'ow' -> ' low'
261: ' ' + 'n' -> ' n'

Walk through it. Merge 256 is "es" (the tie with "st" went to the smaller id). After it, "st" no longer exists in newest and widest, because the s is inside "es"; the most frequent pair is now "es" followed by "t", 9 times, which becomes "est" (257): a common English ending, found from nothing but counts. Then a three-way tie at 7 between space-l, l-o and o-w goes to the smallest first id, 32, so " l" is 258; "ow" follows (259) and then " l" + "ow" becomes " low" (260). Whole frequent words end up as single tokens; "widest" still has to wait for its turn. This is the stenographer's chord book of chapter 13 being written, one chord at a time.

Solution spoiler 
def train_bpe(text, n_merges):
    """Learn up to `n_merges` merges. Returns {(a, b): new_id} in the order learned (ids start at 256)."""
    freqs = Counter(pretokenise(text))
    seqs = {w: utf8_ids(w) for w in freqs}
    merges = {}
    for k in range(n_merges):
        pairs = count_pairs(seqs, freqs)
        if not pairs:                       # every word is a single token: nothing left to merge
            break
        pair = best_pair(pairs)
        merges[pair] = 256 + k
        for w in seqs:
            seqs[w] = merge_pair(seqs[w], pair, 256 + k)
    return merges

Milestone 3: encode and decode

A merge table is useless until it is applied to text it has not seen. Encoding splits the text into pieces, starts each piece as bytes, and repeatedly applies the earliest-learned merge that is present, until no pair in the piece is in the table. Earliest-learned, not most frequent now: the table was built greedily, and replaying it in the same order is what makes training and encoding consistent. A piece with the pair (a, b) learned at id 300 and the pair (b, c) learned at id 270 must merge (b, c) first.

import solution as m
text = " low" * 5 + " lower" * 2 + " newest" * 6 + " widest" * 3
merges = m.train_bpe(text, 5)
vb = m.vocab_bytes(merges)
for s in [" lowest", " newer", " wide"]:
    ids = m.encode(s, merges)
    print(f"{s!r:10} -> {ids} -> {[vb[i].decode() for i in ids]}")
print(repr(m.decode(m.utf8_ids("👍")[:2], {})), repr(m.decode(m.utf8_ids("👍"), {})))
' lowest'  -> [260, 257] -> [' low', 'est']
' newer'   -> [32, 110, 101, 119, 101, 114] -> [' ', 'n', 'e', 'w', 'e', 'r']
' wide'    -> [32, 119, 105, 100, 101] -> [' ', 'w', 'i', 'd', 'e']
'�' '👍'

" lowest" never appeared in the training text, yet it encodes to two meaningful tokens, " low" and "est", each learned from other words: this is how a fixed vocabulary covers an open set of words. " newer" gets no help because its merges (" n" and "ew") were not among the first five; it stays as bytes, and the cost of that is that it is six tokens long. More merges would shorten it.

Decoding is the reverse, and simpler. Each token id stands for a fixed string of bytes: ids below 256 for one byte, a merged id for the concatenation of the bytes of its two parts. vocab_bytes builds that table by walking the merges in learning order (a merge's parts always exist by then, because they were learned earlier). Decoding joins the bytes of all tokens and interprets them as UTF-8.

The last line of the output shows why the interpretation step needs care. Tokens do not respect character boundaries: a four-byte emoji can be split across two tokens, and when a model is stopped mid-way (a length limit, or streaming text to a screen one token at a time) the bytes so far may end in the middle of a character. Python's strict decoder would raise UnicodeDecodeError. A production decoder must not crash on that: Python's errors="replace" substitutes U+FFFD, the replacement character �, for the broken part. That is also what chapter 13 means by "split UTF-8 characters" among its tokeniser bugs. Streaming APIs deal with it by holding back incomplete bytes until the character is finished; for this lab, replacement is enough.

Solution spoiler 
def vocab_bytes(merges):
    """{token id: the bytes it stands for}, for all 256 byte tokens and every merged token."""
    vb = {i: bytes([i]) for i in range(256)}
    for (a, b), new in merges.items():      # insertion order = order learned, so parts exist already
        vb[new] = vb[a] + vb[b]
    return vb

def encode(text, merges):
    """Text -> token ids: bytes of each piece, then the earliest-learned merge present, until none is."""
    out = []
    for piece in pretokenise(text):
        ids = utf8_ids(piece)
        while len(ids) > 1:
            pairs = set(zip(ids, ids[1:]))
            pair = min(pairs, key=lambda pr: merges.get(pr, math.inf))
            if pair not in merges:
                break
            ids = merge_pair(ids, pair, merges[pair])
        out.extend(ids)
    return out

def decode(ids, merges):
    """Token ids -> text. Invalid UTF-8 (for instance a cut-off emoji) becomes U+FFFD instead of an error."""
    vb = vocab_bytes(merges)
    return b"".join(vb[i] for i in ids).decode("utf-8", errors="replace")

Milestone 4: reshaping a distribution

Now the other end. A language model's last layer produces one score per vocabulary entry, the logits z, and the softmax turns them into probabilities, pi = ezi / ∑j ezj. Chapter 15's central observation is that what you do next is a choice, and that the choices are a short list of small functions applied to this list of numbers. Milestone 4 writes them; milestone 5 draws from the result.

Temperature. Divide the logits by τ before the softmax. At τ = 1 nothing changes; below 1 the gaps between logits grow, so the leader takes more of the mass; above 1 they shrink and the distribution flattens. Two details matter. First, use the numerically safe softmax of A0 chapter 11 (subtract the largest logit first), because real logits are in the tens and math.exp(1000) overflows. Second, τ = 0 is not a number you can divide by: libraries treat it as "greedy", and your softmax should raise ValueError for it, with greedy handled one level up in milestone 5.

import solution as m
tokens = ["the", "a", "of", "and", "in", "to", "zebra", "qx"]
logits = [2.0, 1.4, 0.9, 0.5, 0.1, -0.3, -1.5, -2.5]
for tau in (0.5, 1.0, 2.0):
    p = m.softmax(logits, tau)
    print(f"temperature {tau}: " + " ".join(f"{x:.2f}" for x in p) + f"   sum {sum(p):.2f}")
print(" " * 18 + " ".join(f"{t[:4]:>4}" for t in tokens))

At τ = 0.5 "the" has two thirds of the mass; at τ = 2 it has barely a quarter and "qx", a token the model considers absurd, has 3%. That 3% is the problem the filters solve. With a vocabulary of 100,000 entries there are tens of thousands of tokens that are individually unlikely and collectively not negligible, and drawing from the full distribution picks one of them every so often. One nonsense token in a sentence can derail everything after it, because the model now conditions on it.

Truncation removes the tail before the draw: zero the tokens you do not want, then renormalise so that the survivors sum to 1. Three rules, all in chapter 15:

  • Top-k (Fan, Lewis and Dauphin, 2018) keeps the k most probable tokens. It ignores how sure the model is: k = 3 keeps three candidates whether the model is certain or not.
  • Top-p, or nucleus sampling (Holtzman et al., 2019), keeps the smallest set of top tokens whose probabilities add up to at least p. The set shrinks when the model is sure and grows when it is not. The subtlety is the boundary: walk down the ranking, keep each token, and stop once the mass already kept reaches p. The token that crosses p is included; if you leave it out you can end with less than p of the mass, and with an empty set when the top token alone exceeds p. The best token is always kept.
  • Min-p (Nguyen et al., 2024) keeps tokens at least a fraction f as probable as the best one. Its threshold scales with the model's confidence: with a leader at 0.9 and f = 0.05 the cut is 0.045, with a leader at 0.2 it is 0.01.

Ties need a rule, as in BPE: rank by probability descending and break ties towards the smaller token id, so that "keep k tokens" always keeps exactly k.

import solution as m
tokens = ["the", "a", "of", "and", "in", "to", "zebra", "qx"]
p = [0.42, 0.23, 0.14, 0.09, 0.06, 0.03, 0.02, 0.01]
for name, q in [("top-k 3", m.top_k_filter(p, 3)), ("top-p 0.8", m.top_p_filter(p, 0.8)), ("min-p 0.1", m.min_p_filter(p, 0.1))]:
    kept = [t for t, x in zip(tokens, q) if x > 0]
    print(f"{name:10} keeps {len(kept)}: {kept}  mass kept {sum(a for a, x in zip(p, q) if x > 0):.2f}")
    print(" " * 11 + " ".join(f"{x:.2f}" for x in q))

The second line of each pair is the renormalised distribution: with top-k = 3 the survivors' original 0.42, 0.23 and 0.14 become 0.53, 0.29 and 0.18, which sum to 1. Forgetting that step is a classic bug, and a sneaky one: a sampler that draws u in [0, 1) against probabilities summing to 0.79 will run off the end of the list 21% of the time.

Hints try without first

Solution spoiler 
def softmax(logits, temperature=1.0):
    """softmax(logits / temperature), numerically safe. Temperature must be positive."""
    if temperature <= 0:
        raise ValueError("temperature must be positive (use greedy for 0)")
    z = [x / temperature for x in logits]
    m = max(z)
    e = [math.exp(x - m) for x in z]
    s = sum(e)
    return [x / s for x in e]

def top_k_filter(probs, k):
    """Keep the k most probable tokens, zero the rest, renormalise. k >= len(probs) keeps everything."""
    keep = [False] * len(probs)
    for i in _ranking(probs)[:max(k, 1)]:       # k < 1 is treated as 1
        keep[i] = True
    return _renormalise(probs, keep)

def top_p_filter(probs, p):
    """Nucleus: the smallest set of top tokens whose mass reaches p (the token that crosses p is kept)."""
    keep = [False] * len(probs)
    before = 0.0                            # mass of everything ranked above the current token
    for rank, i in enumerate(_ranking(probs)):
        if rank > 0 and before >= p:        # the best token is always kept, even for tiny p
            break
        keep[i] = True
        before += probs[i]
    return _renormalise(probs, keep)

def min_p_filter(probs, frac):
    """Keep tokens at least `frac` times as probable as the best one."""
    cut = frac * max(probs)
    return _renormalise(probs, [x >= cut for x in probs])

Milestone 5: drawing a token and generating text

You now have a distribution with its tail cut. Drawing one token from it needs one random number. The standard method is inverse-CDF sampling: lay the probabilities end to end along the interval [0, 1) and see which segment a uniform random number u lands in. The cumulative distribution function (CDF) is the running total of the probabilities; the draw is the first token whose running total exceeds u. A token with probability 0 has a segment of length 0 and can never be hit, which is why the filters' zeros are safe.

import random, solution as m
p = [0.2, 0.5, 0.3]

[(0, 1983), (1, 5015), (2, 3002)]

Over 10,000 seeded draws the counts are 1,983, 5,015 and 3,002 for probabilities 0.2, 0.5 and 0.3: the segments are the right lengths. The checker repeats this with 30,000 draws and a zero-probability token in the middle, and wants every frequency within 0.015.

Wrap it up. greedy is the argmax, the "temperature zero" limit. next_token is one decoding step with the options of an API call, in a fixed order: temperature, then top-k, then top-p, then min-p, each filter renormalising for the next. (Libraries differ in the order of these steps; since the filters commute only sometimes, the order is part of the specification, and the checker fixes it.) It consumes exactly one call to rng.random() per step, and none at temperature 0; the exact consumption is what makes a seeded run reproducible even when settings change from step to step. generate is then the loop of the figure at the top: ask the model for logits on the context so far, pick a token, append it, stop at a length limit or a stop token. Chapter 12 ran the same loop with a single line for the pick.

The checker's final scenario puts the pieces together. It trains a tokeniser with 150 merges on the corpus, fits the given NGramModel (counts of which token follows the last two, with a tiny amount of smoothing so that every token keeps a sliver of probability), and decodes from it. Two things should happen, both from chapter 15. Greedy decoding enters a loop: a model that looks at the last two tokens is deterministic under argmax, so the moment a pair of tokens repeats the future repeats too. And plain sampling now and then draws a token the model itself gave less than a tenth of a per cent, while top-p 0.9 and min-p 0.05 never do. Solution spoiler 
def sample_from(probs, u):
    """Inverse-CDF draw: the first token whose running total exceeds u, for u in [0, 1)."""
    total = 0.0
    last = 0
    for i, p in enumerate(probs):
        if p > 0:
            last = i
            total += p
            if u < total:
                return i
    return last                             # u landed in the rounding gap at the very top

def greedy(probs):
    """The most probable token; ties go to the smaller id."""
    return _ranking(probs)[0]

def next_token(logits, rng, temperature=1.0, top_k=None, top_p=None, min_p=None):
    """One decoding step: logits -> (temperature) -> top-k -> top-p -> min-p -> draw.

    temperature == 0 means greedy and uses no randomness.
    """
    if temperature == 0:
        return greedy(logits)
    probs = softmax(logits, temperature)
    if top_k is not None:
        probs = top_k_filter(probs, top_k)
    if top_p is not None:
        probs = top_p_filter(probs, top_p)
    if min_p is not None:
        probs = min_p_filter(probs, min_p)
    return sample_from(probs, rng.random())

def generate(model, prompt_ids, n_new, rng, stop_id=None, **settings):
    """Extend `prompt_ids` by up to n_new tokens. `model(ids)` returns the logits for the next token.

    Generation ends early after emitting `stop_id`. Returns the prompt plus the new tokens.
    """
    ids = list(prompt_ids)
    for _ in range(n_new):
        t = next_token(model(ids), rng, **settings)
        ids.append(t)
        if stop_id is not None and t == stop_id:
            break
    return ids

Going further

  • Special tokens. Reserve ids above the merges for <|endoftext|> and a chat delimiter. Make encode recognise them in text only when the caller allows it, and discuss what happens to a user who types the delimiter into a form field (the injection bug of chapter 13).
  • A faster trainer. train_bpe recounts every pair each round. Maintain the pair counts incrementally: when merging a pair in a word, subtract the old neighbouring pairs and add the new ones. Check your merge table is identical to the simple trainer's and time both on a larger text.
  • Digits. Change the regular expression so that digit runs are cut into groups of three from the left (the cl100k choice in chapter 13). What happens to the token count of "1234567890" and to the merges learned for numbers?
  • Beam search. Implement beam search with a width parameter and length normalisation (chapter 15). Show on the counting model that a wider beam finds a more probable sequence and that it is more repetitive.
  • Repetition penalty. Lower the logit of every token already in the context by a fixed amount, and see whether greedy decoding still loops. Then ask what the penalty does to a name that legitimately occurs ten times.
  • Constrained decoding. Write a function that, given the text so far, sets the logits of all tokens that would make an invalid number to -inf before the softmax, and generate digits only. Does the mask need to know about token boundaries?

Systems connection

The tokeniser is a parser with a round-trip contract, and the testing here is the testing of any codec: a property (decode(encode(x)) == x), random inputs from alphabets chosen to hit the awkward cases, and an independent reference implementation. The usual lessons about untrusted input apply directly: a user-controlled string is cut into tokens by a program with rules the user can read, and text that looks like a special token must be handled on purpose. The decoder is the hot loop of serving. Every orange box in the figure runs once per generated token, so on a 100,000-token vocabulary a Python-speed sampler would be absurd; real engines run sampling on the GPU in the same step as the forward pass, and the cost that dominates there is the memory traffic of the model itself. The decoder also needs a deterministic story for tests and evaluation: seeded draws, one random number per step, as above.

What you learned

  • Byte-level BPE starts from the 256 byte values, so any string can be encoded and nothing is unknown. Training counts pairs over distinct words weighted by frequency, merges the best pair, and records the merges in order; the order is the model.
  • Ties must be broken by a fixed rule, and merges must happen inside pieces cut by a regular expression, or the vocabulary depends on accidents.
  • Encoding replays the earliest-learned merge first. Decoding concatenates bytes and must tolerate invalid UTF-8, because tokens do not end on character boundaries.
  • Temperature rescales logits before the softmax and never changes the ranking. Top-k keeps a fixed number, top-p the smallest set reaching a mass (the crossing token included), min-p everything above a fraction of the leader; every filter renormalises.
  • Sampling is inverse-CDF with one random number per step; zero-probability tokens are never drawn; temperature 0 is greedy and uses no randomness.
  • Greedy decoding from a deterministic model loops, and untruncated sampling eventually draws junk from the tail; truncation trades a little diversity for a lot of safety.

Check your understanding

Training has learned the merge (116, 104) as token 300 and, earlier, the merge (104, 101) as token 270. The piece "the" is the bytes [116, 104, 101]. What does encode produce?

  1. [300, 101], because 300 is the larger id and so the better token
  2. [116, 270], because the earlier-learned merge applies first, and then (116, 270) is not in the table
  3. [300, 101] or [116, 270], whichever pair is found first when scanning left to right
  4. [116, 104, 101], because the two merges overlap and neither can apply
Encoding replays the merge table in learning order: the pair with the lowest id present goes first. (104, 101) is token 270, so it merges and gives [116, 270]; the pair (116, 104) no longer exists. The first option picks by the size of the id, the third by position, and both would make encoding disagree with how training counted the pairs.

A streaming server decodes each new token's bytes as soon as they arrive, with a strict UTF-8 decoder, and it crashes on some emoji. What is the most likely cause?

  1. The emoji is not in the vocabulary, so the tokeniser returns an unknown token
  2. The model produced an invalid token id
  3. The regular expression split the emoji in two pieces
  4. A four-byte character was split across two tokens, so the first token alone is not valid UTF-8
Tokens are made of bytes, not characters, and byte-level BPE can end a token in the middle of a character. Holding back incomplete bytes or decoding with replacement fixes it. A byte-level vocabulary has no unknown token, the ids are valid, and the pre-tokenisation pattern never separates the bytes of a single character (it works on characters).

A distribution is [0.5, 0.25, 0.125, 0.125]. Which tokens does top-p with p = 0.7 keep?

  1. The first two, with probabilities 0.5 and 0.25: the first alone has 0.5, below 0.7, so the second is needed, and that crosses 0.7
  2. Only the first, because 0.5 is the largest
  3. The first three, because 0.5 + 0.25 = 0.75 and the next token must be included as well
  4. All four, because p applies to each token's own probability
Walk down the ranking and stop once the mass kept has reached p: before the second token the mass is 0.5, less than 0.7, so it is kept; before the third it is 0.75, at least 0.7, so it stops. The survivors are renormalised to 2/3 and 1/3. Keeping the third token would mean including one more than necessary.

A sampler keeps the top-k tokens but forgets to renormalise, and then draws with a uniform number in [0, 1). The kept tokens hold 0.79 of the mass. What goes wrong?

  1. Nothing: the relative probabilities are unchanged
  2. The most likely token is drawn too rarely
  3. About 21% of draws fall past the last running total, so the code needs a fallback and the result is biased towards whatever that fallback returns
  4. The temperature is applied twice
The segments sum to 0.79, so a uniform number above 0.79 matches no token. Whatever the code does then (return the last token, or the first) over-weights that token by 21 percentage points of the draws. Renormalising makes the segments fill the interval. The relative probabilities among kept tokens are fine; the absolute total is the problem.

At temperature 0.5 a token has probability 0.2 and another has 0.6. What happens to the ratio of the second to the first?

  1. It stays at 3, because temperature does not change the order
  2. It rises from 3 to 9, because dividing logits by 0.5 squares each probability before renormalising
  3. It falls to 1.7, because temperature below 1 flattens the distribution
  4. It cannot be known without the logits
Dividing logits by τ raises each probability to the power 1/τ before renormalising (chapter 15), so for τ = 0.5 each is squared, and the ratio becomes 32 = 9. The ranking is unchanged but the gaps widen. A temperature below 1 sharpens rather than flattens. And the probabilities are enough to know the answer, since softmax only needs their ratios.

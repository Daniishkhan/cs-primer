FlashAttention

Attention was already known to cost time and memory that grow with the square of the sequence length. In 2022 Tri Dao, Daniel Fu, Stefano Ermon, Atri Rudra and Christopher Ré argued in "FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness" that the cost people were fighting was the wrong one. The arithmetic was not the bottleneck; the trips to the GPU's main memory were. Their kernel computes the same numbers as before, moves far fewer bytes, and made longer training contexts affordable.

What I could and could not read

I fetched and read the full text of the original FlashAttention paper (arXiv 2205.14135, v2) including its tables, algorithms and limitations section. I fetched and read the abstract, introduction and training tables of the FlashAttention-2 paper (arXiv 2307.08691), the abstract and headline results of the FlashAttention-3 paper (arXiv 2407.08608), the abstract and introduction of the FlashAttention-4 paper (arXiv 2603.05451, March 2026), the abstract and introduction of Milakov and Gimelshein's "Online normalizer calculation for softmax", and the current PyTorch documentation page for scaled_dot_product_attention. I did not read the bodies of the FlashAttention-3 and FlashAttention-4 papers closely, I did not re-run any of the authors' benchmarks, and I have no GPU here: every speed figure below is the authors' own report, and the toy later on counts memory traffic in a model, it does not time hardware.

The pattern in one sentence

When an operation spends its time waiting for memory rather than computing, count the reads and writes between fast and slow memory, and restructure the algorithm (tile it, fuse it, recompute instead of storing) so that the big intermediate result never leaves the fast memory, even if that means doing more arithmetic.

Context: attention was slow for a reason nobody was measuring

By 2022 the attention layer from chapter 9 sat inside nearly every large model, and its cost was well known. For a sequence of N tokens, the score matrix S = QKT has N × N entries, so both the arithmetic and the memory grow with N2. The paper's introduction says this is why equipping Transformers with longer context "remains difficult". Many research groups had proposed approximate attention (sparse patterns, low-rank projections, kernel tricks) that cut the arithmetic to nearly linear in N, at some cost in quality. The FlashAttention authors point out that many of these did not run faster on real hardware, and that "one main reason is that they focus on FLOP reduction (which may not correlate with wall-clock speed) and tend to ignore overheads from memory access (IO)".

To see why, you need two facts about a GPU. First, a GPU has a large, slow main memory and a tiny, fast one. The paper's example is the A100: HBM (high-bandwidth memory, the main memory) of 40 to 80 GB with bandwidth of 1.5 to 2.0 TB/s, and SRAM (the on-chip memory next to the arithmetic units) of 192 KB per streaming multiprocessor, with 108 of them, at a bandwidth the authors estimate near 19 TB/s. The fast memory is an order of magnitude faster and many orders of magnitude smaller. Second, each GPU function, called a kernel, loads its inputs from HBM, computes, and writes its outputs back to HBM. Whatever one kernel hands to the next must make a round trip.

An operation is memory-bound when its time is set by bytes moved rather than arithmetic done, and compute-bound in the opposite case. The ratio that decides it is the arithmetic intensity: arithmetic operations per byte of memory traffic. The paper lists large matrix multiplies as compute-bound and elementwise operations and reductions, including softmax, as memory-bound. A standard attention implementation is a matrix multiply, then a softmax, then another matrix multiply, with the N × N matrices S and P (the softmax output) written to HBM and read back between them. The paper's central claim is that this traffic, not the multiplication, sets the run time.

HBM and SRAM
The GPU's large slow main memory and its tiny fast on-chip memory.
Kernel
One function launched on the GPU. Its inputs come from HBM and its outputs go back to HBM.
IO-aware
Designed by counting reads and writes between levels of memory, not only arithmetic.
Tiling
Splitting matrices into blocks small enough to fit in SRAM and processing them one block at a time.
Online softmax
A way to compute a softmax over a row that arrives in pieces, by keeping a running maximum and running sum.
Recomputation
Recalculating a value when it is needed again instead of storing it. Here it replaces storing the N × N matrices for the backward pass.

The mechanism, part one: what the standard implementation moves

The paper writes attention as S = QKT, P = softmax(S), O = PV, with Q, K, V and O of shape (N, d) and S and P of shape (N, N). Its Algorithm 0 is the standard recipe: load Q and K, compute S and write it to HBM; read S, compute P and write it to HBM; load P and V, compute O and write it to HBM. Counting elements moved gives roughly 4N2 + 4Nd, and since the head dimension d is 64 for GPT-2 while N is 1,024 or more, the N2 terms dominate. The memory needed to hold S and P is quadratic in N too. The paper's own Theorem 2 states the standard cost as Θ(Nd + N2) HBM accesses.

The mechanism, part two: tiles, a running softmax, and recomputation

The obstacle to keeping S and P on chip is that they are too big: for N = 1,024 and 16-bit numbers one head's S is already 2 MiB, and SRAM is measured in hundreds of kilobytes shared by many things. So the paper splits the work into tiles. The matrix products are easy to tile. The softmax is not, because each weight is divided by a sum over the whole row, and for numerical stability (A0 chapter 11) the row maximum is subtracted first. If the row arrives in blocks, neither the final maximum nor the final sum is known when the first block is processed.

The fix is a trick that predates the paper. Milakov and Gimelshein (2018, "Online normalizer calculation for softmax"), working at NVIDIA, showed how to compute the maximum and the sum in a single pass by keeping them as running values and rescaling the running sum whenever a new maximum appears. The FlashAttention paper keeps two statistics per row, the running maximum m and the running sum ℓ of exponentials, and extends the idea to the whole output: after each key/value block, the partly accumulated output is rescaled by the same correction factor before the new block's contribution is added. At the end the result is exactly softmax(QKT)V. Chapter 19's stepper on FlashAttention walks through the arithmetic for one row of six scores; here the interest is the loop structure. The paper's Algorithm 1 sets block sizes Bc = ⌈M / 4d⌉ and Br = min(⌈M / 4d⌉, d), where M is the SRAM size in elements.

The second idea concerns training. The backward pass normally needs S and P to compute gradients, which would force the N × N matrices to be stored after all. The paper stores only the output O and the softmax statistics (m, ℓ), and recomputes the tiles of S and P on chip when the backward pass needs them. The authors describe this as a form of selective gradient checkpointing (A0 chapter 9), with an important difference: ordinary checkpointing trades speed for memory, whereas here "even with more FLOPs, our recomputation speeds up the backward pass due to reduced HBM accesses". Together the whole computation fits in one fused kernel.

The theory behind the speed-up

The paper analyses IO complexity, the number of HBM accesses, as a function of the sequence length N, head dimension d and SRAM size M. Its Theorem 1 says Algorithm 1 returns the exact attention output with O(N2d) FLOPs and needs O(N) extra memory beyond inputs and output. Theorem 2 says standard attention needs Θ(Nd + N2) HBM accesses while FlashAttention needs Θ(N2d2M-1). For typical values (d of 64 to 128, M around 100 KB) the paper notes that d2 is many times smaller than M, so the second count is much smaller. Proposition 3 adds a lower bound: no exact attention algorithm can beat N2d2M-1 HBM accesses for every M in the range from d to Nd. The proof idea is easy to follow: for each block of K and V of size about M, one pass over all of Q (Nd elements) is needed, and there are about Nd/M such blocks.

Go deeper optional: where the d2/M comes from

Fix the SRAM size M. Each outer iteration loads a block of K and V holding about M elements, so there are about Nd / M outer iterations. Each inner loop streams through all of Q, O, m and ℓ, which is on the order of Nd elements. Multiplying gives (Nd / M) × Nd = N2d2 / M accesses, which is the theorem's count. The standard algorithm's N2 comes from writing and reading the score matrix once each. The two are equal when M is about d2, which is why a very small SRAM would erase the benefit, and why the toy below shows the ratio growing as M grows.

What the authors reported

All figures here are the paper's own measurements on A100 GPUs unless stated. The first is the mechanism check (the paper's Figure 2, left): forward plus backward attention for GPT-2 medium (sequence length 1,024, head dimension 64, 16 heads, batch size 64). Standard attention took 66.6 GFLOPs, moved 40.3 GB to and from HBM and ran in 41.7 ms. FlashAttention took more arithmetic, 75.2 GFLOPs because of recomputation, but moved 4.4 GB and ran in 7.3 ms. The authors conclude that "HBM access is the primary factor affecting runtime".

The end-to-end results follow. The paper reports that its BERT-large (sequence length 512) trained to the MLPerf 1.1 target accuracy in 17.4 minutes against NVIDIA's record-holding 20.0 minutes, a 15% speed-up, on 8 A100s. For GPT-2 on OpenWebText, also on 8 A100s, it reports these training times with identical validation perplexity, since the model definition did not change:

ModelHuggingFaceMegatron-LMFlashAttention
GPT-2 small9.5 days4.7 days2.7 days (3.5× over HuggingFace)
GPT-2 medium21.0 days11.5 days6.9 days (3.0× over HuggingFace)

The long-context result is the one that gave the paper its reach. Because the kernel is faster and its memory use is linear in N, the authors trained GPT-2 small with a context of 4,000 tokens ("4K") and report that it was still about 30% faster than Megatron-LM with a 1K context (3.6 days against 4.7), while reaching a perplexity 0.7 lower (17.5 against 18.2). On two long-document classification tasks, longer sequences gave gains over a 512-token baseline of 4.3 points (MIMIC-III at 16K) and 8.5 points (ECtHR at 8K). And on the Path-X task of the Long Range Arena (sequence length 16K) it produced "the first Transformer" with better-than-chance accuracy (61.4%), and with a block-sparse variant did the same on Path-256 (sequence length 64K, 63.1%). In the memory benchmark the paper reports a footprint growing linearly with N and up to 20 times lower than exact-attention baselines.

A toy you can run

The script below is my own NumPy sketch of Algorithm 1, not the authors' CUDA code. It does two jobs. First, it checks the claim that tiling with a running softmax is exact: it computes attention both ways and compares. Second, it keeps a ledger of how many elements each plan would move between a notional HBM and SRAM, using the paper's block sizes Bc = M/4d and Br = min(Bc, d). I assume an SRAM budget of M = 98,304 elements, which is the 192 KB per streaming multiprocessor quoted above at two bytes per element; real kernels do not get to use all of it for tiles, so treat the ratios as an idealisation. The last lines ask a roofline question for the paper's GPT-2 medium benchmark: how long would the reported HBM traffic, and the arithmetic, each take on an A100 if they ran at peak? The traffic and the measured times are the paper's; the arithmetic is my own count of matrix products (six for the standard forward and backward pass, seven for FlashAttention, which recomputes the scores).

"""Toy: exact tiled attention with an online softmax, plus an HBM-traffic ledger.
My NumPy sketch of the idea in Dao et al. (2022), Algorithm 1. It counts elements moved
between a notional HBM and SRAM; it does not time a GPU."""
import numpy as np
from math import ceil

def standard(Q, K, V):
    S = Q @ K.T / np.sqrt(Q.shape[1])
    P = np.exp(S - S.max(1, keepdims=True)); P /= P.sum(1, keepdims=True)
    return P @ V

def flash(Q, K, V, Br, Bc):
    N, d = Q.shape
    O = np.zeros((N, d)); l = np.zeros(N); m = np.full(N, -np.inf)
    traffic = 0                                        # elements read from or written to "HBM"
    for j in range(0, N, Bc):                          # outer loop: K, V tiles
        Kj, Vj = K[j:j+Bc], V[j:j+Bc]; traffic += 2 * Kj.size
        for i in range(0, N, Br):                      # inner loop: Q tiles
            Qi = Q[i:i+Br]; traffic += Qi.size + O[i:i+Br].size + 2 * Qi.shape[0]
            S = Qi @ Kj.T / np.sqrt(d)                 # lives in SRAM only
            m_new = np.maximum(m[i:i+Br], S.max(1))
            P = np.exp(S - m_new[:, None])
            scale = np.exp(m[i:i+Br] - m_new)          # rescale what we had accumulated
            l_new = scale * l[i:i+Br] + P.sum(1)
            O[i:i+Br] = (scale * l[i:i+Br])[:, None] * O[i:i+Br] / l_new[:, None] + P @ Vj / l_new[:, None]
            l[i:i+Br], m[i:i+Br] = l_new, m_new
            traffic += O[i:i+Br].size + 2 * Qi.shape[0]
    return O, traffic

def standard_traffic(N, d):                            # Algorithm 0: S and P go through HBM
    return (2*N*d + N*N) + (2*N*N) + (N*N + 2*N*d)

rng = np.random.default_rng(0)
N, d = 1024, 64
Q, K, V = (rng.normal(size=(N, d)) * 2 for _ in range(3))
M = 98304                                              # assumed SRAM budget: 192 KB of fp16 = 98,304 elements
Bc = ceil(M / (4*d)); Br = min(Bc, d)
O1 = standard(Q, K, V); O2, t = flash(Q, K, V, Br, Bc)
print(f"N={N} d={d} M={M}  Bc={Bc} Br={Br}  tiles: {ceil(N/Bc)} x {ceil(N/Br)}")
print("max |standard - flash| =", np.abs(O1 - O2).max())
print(f"HBM elements, standard: {standard_traffic(N, d):,}   flash: {t:,}   ratio {standard_traffic(N, d)/t:.1f}x")
print("\n      N  S, one head  standard traffic   flash traffic   ratio   (M = %d)" % M)
for n in (512, 1024, 2048, 4096, 8192):
    q, k, v = (rng.normal(size=(n, d)) for _ in range(3))
    _, ft = flash(q, k, v, Br, Bc); st = standard_traffic(n, d)
    print(f"{n:7d} {n*n*2/2**20:9.1f} MiB {st:17,} {ft:15,} {st/ft:7.1f}x")
print("\nSweep the SRAM budget at N=4096 (Bc = M/4d, Br = min(Bc, d)):")
for M2 in (12288, 24576, 49152, 98304, 196608, 393216):
    bc = ceil(M2 / (4*d)); br = min(bc, d)
    q, k, v = (rng.normal(size=(4096, d)) for _ in range(3))
    _, ft = flash(q, k, v, br, bc)
    print(f"  M={M2:7d} elements  Bc={bc:4d} Br={br:3d}  flash traffic {ft:12,}  ratio {standard_traffic(4096, d)/ft:5.1f}x")

# Roofline check for GPT-2 medium (batch 64, 16 heads, N=1024, d=64), forward + backward, on an A100.
hbm_bw, peak = 1.5e12, 312e12                          # bytes/s (paper: 1.5-2.0 TB/s), FLOP/s (FlashAttention-2 paper, 16-bit matmul)
mm = 2 * 1024**2 * 64 * (64 * 16)                      # FLOPs of one N x N x d matrix product over all heads
print("\nFloors for GPT-2 medium attention, fwd+bwd, one A100 (HBM GB and measured ms are the paper's):")
for name, n_mm, gb, ms in (("standard", 6, 40.3, 41.7), ("flash", 7, 4.4, 7.3)):   # 6 products; flash recomputes S: 7
    print(f"  {name:9s} memory floor {gb*1e9/hbm_bw*1e3:5.1f} ms | compute floor {n_mm*mm/peak*1e3:4.2f} ms ({n_mm*mm/1e9:.0f} GFLOPs by my count) | measured {ms} ms")

Reading the output. The two methods agree to about 10-14, which is floating-point rounding: the algorithm is exact, not an approximation. At N = 1,024 the tiled plan moves 6.1 times fewer elements in this ledger, and the ratio grows slowly with N because both plans are quadratic and only the constants differ. The sweep shows the part of Theorem 2 that is easy to miss: the saving depends on M. With a quarter of the assumed SRAM the ratio is 1.9 times; with eight times as much it is 23. That is the reason the same algorithm is re-tuned for each GPU generation, as the next section shows. The last three lines use 1.5 TB/s of bandwidth (the low end of the paper's range) and 312 TFLOPs/s of 16-bit matrix-multiply throughput (from the FlashAttention-2 paper). For standard attention the memory floor of 26.9 ms is within a factor of 1.6 of the measured 41.7 ms, while the compute floor is about 2.6 ms: the traffic is the cost. After the change, the two floors are close (2.9 ms and 3.1 ms) and the measured 7.3 ms is about 42% of the compute floor's speed, which is close to the 25 to 40% of peak that the FlashAttention-2 abstract gives for the first version. The kernel has stopped waiting mainly for memory, and the remaining slack is the arithmetic efficiency that FlashAttention-2 went after. One caution: the GFLOPs printed in the paper's Figure 2 (66.6 and 75.2) are about twelve times smaller than my count of 825 and 962. I could not reconcile this (the paper's units or per-layer convention may differ), so I use the paper's figure only for the ratio between the two bars, and do not rely on it for the floors.

What came after, and the state of play

The first kernel was not the end. Each later paper keeps the same mathematical function and reworks how the kernel uses the hardware, which is a direct consequence of the IO-aware idea: the best tiling depends on the machine.

State of play, October 2026

These are the authors' own reports, taken from the abstracts and introductions I read; I have not reproduced them. FlashAttention-2 (Dao, July 2023) says the first version reached only 25 to 40% of the A100's theoretical peak, attributes this to poor work partitioning across thread blocks and warps, and reports about 2× speed-up from three changes: fewer non-matrix-multiply operations (on an A100, 312 TFLOPs/s for 16-bit matrix multiply against 19.5 TFLOPs/s for other 32-bit arithmetic, so each non-matmul operation costs about 16 times more), parallelism over the sequence length for each head, and better division of work between warps. It reports up to 225 TFLOPs/s per A100 in end-to-end GPT-style training (72% model FLOPs utilisation). FlashAttention-3 (Shah et al., July 2024) targets the H100 with asynchronous execution, warp specialisation and low-precision FP8, and reports 1.5 to 2.0× over its predecessor, up to 740 TFLOPs/s in FP16 (75% utilisation) and close to 1.2 PFLOPs/s in FP8. FlashAttention-4 (Zadouri et al., March 2026) targets Blackwell GPUs, where the tensor cores doubled in speed while shared memory bandwidth and exponential units did not; it reports up to 1,613 TFLOPs/s (71% utilisation) on a B200 in BF16, 1.3× over cuDNN 9.13 and 2.7× over a Triton implementation. In PyTorch, torch.nn.functional.scaled_dot_product_attention documents three implementations (FlashAttention-2, memory-efficient attention, and a plain C++ version) and says it "attempts to automatically select the most optimal implementation based on the inputs", with the fused kernels each carrying input limitations. Kernel names, versions and hardware move fast; check the repository and your framework version before relying on any of this.

One adoption claim deserves its source. The FlashAttention-2 paper states that the first version "has seen wide adoption in large-scale training and inference of Transformers". That is the author's own assessment in a follow-up paper, not an independent survey, though the PyTorch documentation above is independent evidence that the idea is in the standard library.

What it did not change, and what critics and later work point out

  • The arithmetic is still quadratic. Theorem 1 gives O(N2d) FLOPs. FlashAttention removes the quadratic memory and a large constant in the time, not the quadratic growth of compute. At very long sequences the compute term dominates again, which is why the authors also built block-sparse FlashAttention (an approximation the paper reports as 2 to 4 times faster than the dense kernel, scaling to 64K tokens). In the paper's own benchmark, FlashAttention beats every other method up to a sequence length of 512, but beyond 1K some approximate methods such as Linformer become faster.
  • It is an engineering burden. The paper's limitations section says each new attention variant needs a new CUDA kernel, "a considerably lower-level language than PyTorch", which may not transfer across GPU architectures. The authors call for a compiler from high-level code to IO-aware kernels. The FlashAttention-2 to -4 papers show the burden recurring with every hardware generation; FlashAttention-4's abstract reports writing the kernel in a Python-embedded DSL with 20 to 30 times faster compile times as one response.
  • Results are not bit-identical across kernels. The PyTorch documentation warns that, "due to the nature of fusing floating point operations", the output may differ depending on which backend kernel is chosen. Exact here means the same mathematical function with floating-point rounding differences, which matters when you compare outputs across versions (A0 chapter 11).
  • Inference has a different bottleneck. Training and prompt processing handle many query tokens at once. Generating one token at a time is dominated by reading the weights and the KV cache, which this kernel does not shrink. Multi-query and grouped-query attention (chapter 19) address that cost.
  • The headline speed-up depends on the baseline. "3× faster" is against a particular HuggingFace implementation, about 1.7 to 1.8× against Megatron-LM, and the paper's attention-only microbenchmark says "up to 3× faster than the standard attention implementation" across common lengths. Always ask what the comparison was.

Common misconception

"FlashAttention makes attention linear in the sequence length." It makes the memory linear and the memory traffic far smaller, with the exact same output. The number of multiply-adds still grows with N2. A 1-million-token context is cheaper than before, but it is not cheap, which is why long-context work continues with sparse, windowed and state-space designs (chapter 22).

Analogy: a cook with a small counter

A cook prepares a large banquet with a small counter and a distant pantry. The slow way is to carry every ingredient to the counter, do one step, carry the half-finished trays back to the pantry, then fetch them again for the next step. The fast way is to bring a few trays at a time, do every step on the trays while they are on the counter, and carry only the finished dishes back. The recipe is unchanged; the walking is what shrank. Doing a little extra chopping to avoid a trip, which is what recomputation does, is a good trade when the pantry is far away.

Where it breaks down: a cook can see the whole counter at once, whereas a GPU's tiles must be arranged so that thousands of threads read and write fast memory without colliding, and that arrangement is what the later FlashAttention papers keep re-engineering.

Systems connection

This is the memory hierarchy applied to one operator, and the method is the performance engineer's: measure where time goes before optimising what you assumed was the cost. Lessons

  • Profile before you approximate. Years of attention research reduced FLOPs while the real cost was HBM traffic. Chapter 19 lists the alternatives that change the function; this case shows the one that does not.
  • Exact beats approximate when it is also fast. A drop-in kernel with identical maths needs no retraining, no quality evaluation and no change to the model, which is a large part of why it spread.
  • Trade arithmetic for traffic. Recomputing the score tiles in the backward pass cost extra FLOPs and saved time, because arithmetic is cheap and memory trips are not.
  • Optimal tiling is hardware-specific. The d2/M dependence is a reminder that the answer changes with the SRAM size and the relative speed of units, as the move from A100 to H100 to B200 shows.
  • Memory limits are context limits. Memory that grows as N2 caps the training context long before the compute budget does; removing it moved the cap, as the 4K-versus-1K GPT-2 result shows.

Key takeaways

  • Standard attention is memory-bound: it writes the N × N matrices S and P to HBM and reads them back.
  • FlashAttention tiles the computation, keeps a running softmax (m and ℓ), fuses everything into one kernel, and recomputes S and P in the backward pass.
  • It is exact, uses O(N) extra memory, and needs more FLOPs yet moves far fewer bytes: in the paper, 4.4 GB instead of 40.3 GB and 7.3 ms instead of 41.7 ms for GPT-2 medium.
  • Its HBM traffic scales as N2d2/M; arithmetic is still quadratic in N.
  • Later versions retune the same idea for A100, H100 and Blackwell; the kernel is rewritten for each, and numbers belong in a dated box.

Why was standard attention slow on an A100 even though its arithmetic was a small fraction of the GPU's peak?

  1. The softmax needs more multiplications than the matrix products
  2. The GPU cannot run matrix multiplies in 16-bit arithmetic
  3. It writes the N × N matrices S and P to HBM and reads them back, so time is set by memory traffic
  4. Its memory use is linear, which leaves SRAM idle
The paper's Figure 2 shows 40.3 GB of HBM traffic against 4.4 GB, and runtime tracking traffic. The softmax is memory-bound rather than arithmetic-heavy (first option), and standard attention's memory use is quadratic, not linear (last option).

FlashAttention's backward pass recomputes the score tiles and so does more FLOPs, yet runs faster. What explains this?

  1. The saved HBM reads and writes cost more time than the extra arithmetic
  2. Recomputation is approximate, so it needs less precision
  3. The extra FLOPs run on a separate, free unit
  4. The backward pass is skipped for tokens that do not matter
The paper reports 75.2 against 66.6 GFLOPs but 4.4 against 40.3 GB of traffic. Recomputation is exact, and nothing is skipped.

Which property of attention does FlashAttention NOT change?

  1. The numerical result, up to rounding
  2. The amount of extra memory needed for the N × N matrices
  3. The number of kernels launched
  4. The number of arithmetic operations, which still grows with N2
Theorem 1 gives O(N2d) FLOPs. The result is exact, the N × N memory goes away, and three kernels become one. Compute still grows quadratically.

In the toy, raising the SRAM budget M from 49,152 to 196,608 elements raised the traffic ratio from 3.7× to 12.8×. Which statement from the paper does this match?

  1. FlashAttention's HBM accesses do not depend on M
  2. FlashAttention needs Θ(N2d2/M) HBM accesses, so a larger M means fewer passes over Q
  3. Standard attention's HBM accesses fall as M grows
  4. The ratio is fixed by the head dimension alone
Bigger tiles mean fewer outer iterations and fewer passes over Q. Standard attention's count (Nd + N2) has no M in it. d matters, but not alone.

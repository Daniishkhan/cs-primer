SolidGoldMagikarp: Glitch Tokens

In early 2023 two researchers, Jessica Rumbelow and Matthew Watkins, asked GPT models to repeat back a simple string, and found about a hundred and thirty strings that they could not, among them " SolidGoldMagikarp". The models answered with evasions, insults, or a different word altogether. The cause turned out to be a gap between two datasets: the text used to build the tokeniser's vocabulary and the text used to train the model. This case follows the discovery, the explanation the authors gave, the automated detection method published a year later, and a toy that reproduces the mechanism in a few seconds.

What I could and could not read

I fetched and read the full body of the original LessWrong post by Rumbelow and Watkins (dated 5 February 2023 on the page, with an update of 14 February 2023) and the third post in the series, "Glitch token archaeology" (14 February 2023), including some of their comment threads. I fetched only a summary of the second post, "technical details and more recent findings", so claims from it are marked as such. I fetched and read the full text of Land and Bartolo's "Fishing for Magikarp: Automatically Detecting Under-trained Tokens in Large Language Models" (Cohere, arXiv 2405.05417, 2024). I could not query ChatGPT or any OpenAI model, so I cannot say what any hosted model does today; the behaviours quoted below are the original authors' screenshots and transcripts, and some were nondeterministic even then. I did not find an official OpenAI statement about the episode. The origin story of the tokens (Reddit counting threads) is the authors' own account in the third post; I did not check it against Reddit.

The pattern in one sentence

A tokeniser and a model are trained separately, on different text, so a token can exist in the vocabulary while the model has seen it a handful of times or never; its embedding is then an untrained row, and any prompt that contains it pushes the model outside the region where it was ever taught to behave.

Context: two datasets, one vocabulary

A language model reads integers, not letters. A tokeniser turns text into those integers, and as chapter 13 showed, byte-pair encoding builds its vocabulary by counting: it starts from single bytes and repeatedly merges the pair that occurs most often in a training text, until the vocabulary has the wanted size. For the GPT-2 and GPT-3 models that size is 50,257 tokens (the figure the original post gives). The model then gets one row of an embedding table for each token id. A row begins as random numbers and is changed only when its token appears in a training batch.

The crucial detail is that the vocabulary is built once, in advance, from one corpus, and the model is trained later on another. The corpus for the tokeniser is gathered cheaply by scraping; the corpus for the model is filtered, deduplicated and curated. If a string is common enough in the first to earn its own token and rare or absent in the second, the model inherits a token it has hardly ever seen. The paper "Fishing for Magikarp" calls this "the disconnect between tokenizer creation and model training". A token in that state is under-trained, and a sample of text that happens to contain it is out of the distribution the model learned from.

Glitch token (anomalous token)
A token in the vocabulary that the model has seen rarely or never in training and that causes odd behaviour when it appears in a prompt. The community used "glitch token"; the original authors mostly said "weird tokens".
Under-trained token
The term used by Land and Bartolo: nearly or entirely absent from training. They reserve "untrained" for cases with clear evidence of no occurrences.
Centroid
The average of all token embeddings: the centre of mass of the cloud of vectors.
Tied embeddings
Using one matrix both to embed input tokens and to score output tokens (see the output head in chapter 12). Untied models keep two matrices.
Unreachable token
A token that the tokeniser can never produce from text, usually because of a configuration error.

The discovery

The original post began with a different project. Rumbelow and Watkins, working at SERI-MATS (a research training programme), were building a method to generate prompts by gradient descent over token embeddings, the way feature visualisation generates images for a vision model. To understand the embedding space they ran k-means clustering over the embeddings of the whole GPT token set, and looked at which token sat nearest to each cluster centre. Something was wrong: the nearest tokens "didn't seem semantically relevant to the cluster (or anything else)", and the same handful kept turning up, "very 'untokenlike' in their appearance": ' TheNitromeFan', ' SolidGoldMagikarp', 'cloneembedreportprint'.

They tested two explanations. The first, that these were the tokens with the smallest embedding norm, was wrong. The second, that they were the tokens closest to the centroid of all 50,257 embeddings, "turned out to be correct". For GPT-J the post lists the fifty closest to the centroid: the nearest, ' attRot', is at distance 0.062, ' SolidGoldMagikarp' (id 43453) at 0.063, and ' TheNitromeFan' and ' RandomRedditorWithNo' at 0.064. So a cluster of strange strings sits at the middle of the cloud, close to where an embedding with no information in it would be.

Then they asked a model about them. They wrote twelve prompt templates, all rewordings of "Please can you repeat back the string '<token string>' to me?", and ran every one of the 50,257 tokens through GPT-3 davinci-instruct-beta at temperature 0. Pattern matching on the completions removed the vast majority, which were repeated without trouble. A few thousand suspects were then batched in lists of fifty for ChatGPT to repeat, and that left 374 tokens: about 133 "truly weird" and 241 "merely confused" (fragments of common words such as 'bsite', which the model repeated as "website"). The authors say plainly that their list "is not meant to be definitive".

What the models did

The behaviours the post documents, with its own examples, fall into several families. These are completions the authors reported; they are not a controlled measurement of rates.

Two cautions on reading these. First, they come from particular prompts on particular models in January and February 2023, and the authors themselves note that ChatGPT "is changing daily, and in a rather opaque way", which is why they ran their systematic tests on the API model. Second, words like "unspeakable" and "forbidden" were the community's and the authors' vivid labels for a failure to copy a string; they do not show that the model understood anything about the token. What the transcripts do show is that when the usual input signal is missing, the model's output is an unreliable function of everything else in the context.

On 14 February 2023 the authors added a note at the top of their post: "ChatGPT appears to have been patched! However, very strange behaviour can still be elicited in the OpenAI playground, particularly with the davinci-instruct model." I did not find a public account of what was changed.

Where the strings came from

The third post, "Glitch token archaeology", is about why these strings exist as tokens at all. Its answer for the largest family is that they are usernames. The authors say they first assumed ' SolidGoldMagikarp' was scraped from Pokemon content ("a red herring"), and then found it was the handle of one of six Reddit users who took part in a collective effort to count to infinity in the subreddit r/counting. Another counter's handle, RandomRedditorWithNo, produced two tokens; TheNitromeFan produced three; the other three counters were Adinida, Smartstocks and davidjl123, whose handle ended up as the token ' davidjl'. The authors suggest these handles were scraped from a "Hall of Counters" chart on prolific posters of ever-larger integers, which is a good way for a short string to be extremely frequent in one scraped corpus.

Other tokens look like debris from the backends of web shops and games: 'BuyableInstoreAndOnline', 'inventoryQuantity', 'DeliveryDate', 'TextColor'. The first post's explanation of why they glitch is hedged: "The anomalous tokens may be those which had very little involvement in training, so that the model 'doesn't know what to do' when it encounters them". They add that this might explain the clustering near the centroid, "although we don't have a good argument for why this would be the case". That caveat matters: in early 2023 the authors had a plausible account, not a demonstration, and the GPT-3 training data was not public.

The mechanism, and the paper that tested it

Land and Bartolo (Cohere, 2024) turned the anecdote into a method and a measurement. The reason an unseen token ends up in a recognisable place is a matter of what training does to each row.

Land and Bartolo's argument, in their Section 2.2, has two halves. On the output side, "all weights of the output embeddings influence the token predictions at every training step", so all untrained tokens "experience similar updates in training, 'moving away' from the mean output vector of the model". Under-trained tokens therefore end up sharing a direction in output space, and the model learns something like a constant that makes their logits reliably very negative. On the input side, for models that do not tie the two matrices, an input row for an absent token is changed only by weight decay (chapter 4) if the optimiser applies it: it shrinks toward zero, or stays at its low initial value. The paper therefore uses the cosine distance to a reference group of known-unused embeddings (for tied models) and the norm of the input embedding (for untied ones) as indicators. Whether a model ties the two matrices changes the symptoms. A commenter on the original post notes that GPT-2 ties them, and a comment on the second post notes that GPT-J does not; I did not verify either from the model code.

Their pipeline has three steps: a tokeniser analysis (partial UTF-8 byte sequences, unreachable tokens, special tokens), the weight-based indicators, and a verification step that prompts the model with repetitive contexts where a normal token would be predicted with high probability and flags a candidate if its maximum probability stays below 1%. They validated the indicators on OLMo v1.7 7B, where the training data is public: the indicators correlate strongly with how often each token appears in the first epoch of training, "across ten orders of magnitude". In that model 191 of 49,575 tokens pass verification when they test every token, against 175 of 993 candidates when testing only the top 2% by indicator, which supports the 2% threshold as a cheap way to catch most of them.

Across the open-weight models they tested, "typically around 0.1 to 1% of the vocabulary" was severely under-trained, with large variation. The factor that stood out was whether the tokeniser was trained on data similar to the model's: "models which re-use a large external tokenizer, and then train on distinct data from scratch, are among those with the highest number of detected under-trained tokens." Their examples line up with the original story. GPT-NeoX 20B, whose tokeniser was trained on the same Pile data as the model, has very few. GPT-J 6B and Phi-2, which reuse the GPT-2 tokeniser on different data, have many more, including ' SolidGoldMagikarp', which the paper says is not among the verified candidates for GPT-2 itself. They also found under-trained intermediate BPE fragments (' TheNitrome' left over from ' TheNitromeFan'), and a StarCoder2 case where a single document repeating a Lorem ipsum string created several long tokens.

A toy you can run

The script below is my own sketch of the whole chain at miniature scale, not any lab's pipeline. Step one learns byte-pair merges on a "tokeniser corpus" that contains 1,500 lines of ordinary text plus 300 lines of a forum-style counting thread that mentions a username, "u/SolidGoldMagikarp". Step two trains a very small model on the ordinary text only: it learns to copy a token to itself, with separate input and output matrices and weight decay on the input matrix. Step three reads the weights and flags rows by norm, as the paper does for untied models. The vocabulary is built from invented syllable-words, and the forum thread is deliberately over-represented, so the proportions of unseen tokens are far higher than a real model's 0.1 to 1%; what matters is the mechanism.

"""Toy: how a token can exist in the vocabulary but never be trained.
(1) learn BPE merges on a tokeniser corpus that includes a forum dump;
(2) train a tiny copy model on a cleaned corpus that does not include it;
(3) look for the orphan tokens from the weights alone. My sketch, not any lab's pipeline."""
import numpy as np, random
from collections import Counter

rng = random.Random(0)
syll = ["ka", "to", "mi", "re", "su", "no", "la", "pe", "do", "vi", "an", "el"]
words = sorted({"".join(rng.choice(syll) for _ in range(rng.choice((1, 2, 3)))) for _ in range(150)})
clean = [" ".join(rng.choice(words) for _ in range(8)) for _ in range(3000)]
dump = ["u/SolidGoldMagikarp counted %d" % (1000 + i) for i in range(300)]   # forum counting thread
tok_corpus = clean[:1500] + dump                      # what the tokeniser was trained on
model_corpus = clean                                 # what the model was trained on (dump filtered out)

def pretok(text):                                    # words with a leading-space marker, as GPT-2 does
    return ["_" + w for w in text.split()]

def train_bpe(corpus, n_merges):
    vocab = Counter(tuple(w) for t in corpus for w in pretok(t))
    merges = []
    for _ in range(n_merges):
        pairs = Counter()
        for w, c in vocab.items():
            for a, b in zip(w, w[1:]): pairs[(a, b)] += c
        if not pairs: break
        (a, b), _c = pairs.most_common(1)[0]; merges.append((a, b))
        new = Counter()
        for w, c in vocab.items():
            out, i = [], 0
            while i < len(w):
                if i < len(w) - 1 and (w[i], w[i+1]) == (a, b): out.append(a + b); i += 2
                else: out.append(w[i]); i += 1
            new[tuple(out)] += c
        vocab = new
    return merges

def encode(text, merges):
    ids = []
    for w in pretok(text):
        w = list(w)
        for a, b in merges:
            i = 0
            while i < len(w) - 1:
                if (w[i], w[i+1]) == (a, b): w[i:i+2] = [a + b]
                else: i += 1
        ids += w
    return ids

merges = train_bpe(tok_corpus, 260)
symbols = sorted({c for t in tok_corpus for w in pretok(t) for c in w} | {a + b for a, b in merges})
index = {s: i for i, s in enumerate(symbols)}; V = len(symbols)
long_tokens = [s for s in symbols if len(s) >= 8]
print("vocabulary size:", V, "| tokens of 8+ characters:", long_tokens[-3:], "...")

data = [index[s] for t in model_corpus for s in encode(t, merges)]
count = Counter(data)
unseen = [s for s in symbols if count[index[s]] == 0]
dump_only = [s for s in unseen if any(c in s for c in "/0123456789") or s.startswith(("_u", "_coun")) or s in "GMS"]
print(f"tokens with zero occurrences in the model's data: {len(unseen)} of {V}")
print(f"  from the dump: {len(dump_only)} (e.g. {dump_only[-1]!r}); fragments of ordinary words: {len(unseen) - len(dump_only)} (e.g. {[s for s in unseen if s not in dump_only][:4]})")

# a tiny model trained to copy: logits = E[x] @ W + b, predict x itself. Decoupled weight decay on E.
D, lr, steps = 16, 0.5, 6000
data = np.array(data)
def train(wd):
    r = np.random.default_rng(0)
    E = r.normal(0, 0.5, (V, D)); W = r.normal(0, 0.5, (D, V)); b = np.zeros(V)
    for step in range(steps):
        x = data[r.integers(0, len(data), 64)]
        logits = E[x] @ W + b
        p = np.exp(logits - logits.max(1, keepdims=True)); p /= p.sum(1, keepdims=True)
        g = p.copy(); g[np.arange(64), x] -= 1; g /= 64
        np.add.at(E, x, -lr * (g @ W.T)); W -= lr * (E[x].T @ g); b -= lr * g.sum(0)
        E *= (1 - lr * wd)
    return E, W, b
mask = np.array([count[i] == 0 for i in range(V)])
for wd in (0.01, 0.0):
    E, W, b = train(wd); norm = np.linalg.norm(E, axis=1)
    print(f"\nweight decay {wd}: input-embedding norm, seen tokens {norm[~mask].min():.2f} to {norm[~mask].max():.2f}; "
          f"never-seen tokens {norm[mask].min():.2f} to {norm[mask].max():.2f}")
E, W, b = train(0.01); norm = np.linalg.norm(E, axis=1)
flagged = norm < 0.05
print("\nflag norm < 0.05 (weights only, no data needed): flagged", int(flagged.sum()), "| equals the never-seen set:", bool((flagged == mask).all()))
def copy(token): return symbols[int(np.argmax(E[index[token]] @ W + b))]
ok = sum(copy(s) == s for s in symbols if not mask[index[s]])
print(f"copy accuracy on the {int((~mask).sum())} seen tokens: {ok}/{int((~mask).sum())}")
show = sorted(unseen, key=len)[-1:] + [s for s in unseen if s.startswith("_1")][:2] + [s for s in unseen if s.startswith("_coun")][-1:]
for s in show: print(f"  copy({s!r}) -> {copy(s)!r}")
top = int(np.argmax(b)); print(f"with an all-zero input the logits are just the bias b; its top token is {symbols[top]!r}, seen {count[top]} times in training")

Reading the output. Of 292 tokens, 185 never occur in the training data: 124 come from the dump (the whole handle '_u/SolidGoldMagikarp', its prefixes, the numbers, "counted") and 61 are fragments of ordinary words, which are the toy's version of the "intermediate fragments" the paper describes. With weight decay on, every unseen input row has decayed to norm 0.00 while every seen row sits between 0.81 and 0.93, so a norm threshold finds the unseen set exactly. With weight decay off, the picture is messier: unseen rows keep their random start (norms 1.21 to 2.70) while seen rows have grown to 3.4 to 4.2, which is why the paper says the choice of indicator depends on the training setup. The behaviour matches the post's description in one respect: the model copies all 107 seen tokens correctly, and for each unseen token it emits the same answer regardless of the input, because with an all-zero input the logits reduce to the output bias, whose top token is '_toreto'. A real transformer has context to fall back on and so produces varied nonsense, as the transcripts show; the toy has none. It illustrates why the failure is silent: nothing errors, the token simply carries no information.

A second check concerns the real GPT vocabularies. Chapter 13's tokeniser script reports that ' SolidGoldMagikarp' is a single token (id 43453) in r50k_base, the GPT-2 and GPT-3 vocabulary, and five pieces in cl100k_base. I confirmed the five-piece split independently with a short byte-pair merge over a local copy of the published cl100k_base rank table (I treated the whole string as one chunk, which is what that tokeniser's splitting pattern does for a run of letters with one leading space).

"""Check how cl100k_base splits ' SolidGoldMagikarp' using the published rank table (byte-pair merge by rank)."""
import base64, sys
ranks = {}                                   # this copy of the table is stored as (length byte, token bytes) in rank order
data = open(sys.argv[1], "rb").read(); i = 0
while i < len(data):
    n = data[i]; ranks[data[i+1:i+1+n]] = len(ranks); i += 1 + n
print("entries in table:", len(ranks), "| rank of b'!':", ranks[b'!'], "| rank of b' hello':", ranks[b' hello'])

def bpe(piece: bytes):
    parts = [bytes([b]) for b in piece]
    while len(parts) > 1:
        best = min(((ranks.get(parts[i] + parts[i+1], 1 << 30), i) for i in range(len(parts) - 1)))
        if best[0] == 1 << 30: break
        i = best[1]; parts[i:i+2] = [parts[i] + parts[i+1]]
    return parts

# the pattern ' ?\p{L}+' keeps this whole string together as one pre-token
for s in (" SolidGoldMagikarp", " petertodd", " TheNitromeFan", " Skydragon"):
    parts = bpe(s.encode())
    print(f"{s!r:22} -> {[p.decode() for p in parts]}  ids {[ranks[p] for p in parts]}")

' petertodd'           -> [' pet', 'ert', 'odd']  ids [6896, 531, 14898]

So a newer vocabulary no longer contains the handle as one token; it breaks the string into pieces that are all common elsewhere. Note the Land and Bartolo caution that this is not the end of the matter: the paper reports under-trained tokens in the cl100k family too (for example ' ForCanBeConverted' and '$PostalCodesNL'), and states that all OpenAI models older than GPT-4o that they tested failed to handle many of them correctly. For GPT-4o, which uses a different tokeniser with a larger vocabulary, they found candidate tokens such as 'ម្បី' that appeared to induce an end-of-text token. These are their reports from API tests; I did not repeat them.

Change one thing at a time. (1) Cut the dump from 300 lines to 20: does the full handle still become one token, and what does that say about how much repetition a string needs to earn a slot? (2) Add the 300 dump lines to model_corpus as well, retrain, and watch the unseen count fall: this is the paper's first recommendation, in miniature. (3) Raise the weight decay wd to 0.1: does the norm detector still separate the groups, and does it still work at wd = 0? (4) After a model is trained, how would you flag a token whose row looks normal but which the model has seen only twice?

What critics and later work said

  • The first explanation was a hypothesis. The authors wrote "we don't have a good argument" for why the tokens cluster near the centroid. Their follow-up reported that results differed by model: in GPT-2 small and GPT-J the anomalous tokens were closest to the overall centroid, while in GPT-2 XL they were the farthest (from the summary of the second post, which I did not read in full). The 2024 paper's weight-based account replaced the geometric guess with a mechanism, and tested it where training data was known.
  • The behaviours are not one phenomenon. The post separates "truly weird" tokens from "merely confused" fragments, and says the category had no clean boundary: "there appear to be different degrees of anomalousness". Land and Bartolo add partial UTF-8 byte tokens, unreachable tokens and untrained special tokens as other kinds, with different fixes.
  • It is a data-pipeline bug before it is a model bug. The paper's discussion says the most salient factor, aside from a large vocabulary, is whether the tokeniser was trained on similar data to the model, and recommends that preprocessing be identical across tokeniser training data, model training data and inference. They give a concrete example: in GPT-2, all ASCII control characters except newline, including tab and carriage return, appear untrained, which "suggests a potential mismatch in data normalization between training and inference".
  • There is a security angle. The authors list robustness as a reason to care "with the proliferation of tool use and agents in LLMs that retrieve and process external data", and say under-trained tokens can "potentially be exploited" to circumvent guardrails, citing Geiping et al. (2024), whom I did not read. This is the same family of problem as prompt injection and untrusted input: text from outside your control reaching a component that was never taught to handle it.
  • Capacity is wasted. The paper points out that dead tokens occupy slots that could hold useful ones, reducing average input length efficiency and raising inference cost.

Common misconception

"Glitch tokens are secret backdoors or hidden messages in the model." The evidence in the sources is mundane: strings that were frequent in one scraped corpus and absent in another. The odd outputs are what a network produces when an input row carries no learned information. Calling them "unspeakable" was a vivid label for a measurable failure to copy a string, not a finding about intent or hidden knowledge, and the authors of the original post did not claim otherwise.

Analogy: a phrasebook with blank pages

Imagine a travel phrasebook printed from a catalogue of every phrase that appears on the internet's signs, and then a translator who studies only a filtered selection of those phrases. A few pages of the book carry entries the translator never studied, such as the name of a counting-forum member. When asked to say one aloud, the translator does not stop. They produce a confident phrase from a neighbouring page, or an apology, or something unrelated, since nothing on that page was ever learned.

Where it breaks down: a translator knows which pages they skipped. A neural network has no list of what it has not learned, and its embedding for the blank page is a real vector that flows through the layers like any other, which is why detection has to come from outside, from the weights or from probing.

Systems connection

This is a version-skew bug between two stages of a pipeline, like a parser tested only on the inputs its author imagined, and a reminder of input validation at the boundary (Injection and untrusted input). The remedy mirrors reliability practice: a regression test that runs over the whole vocabulary after every tokeniser change, like the unit tests you would put round a parser. For the monitoring side, see the logging advice in Tracing and observability for LLM systems.

Lessons

  • Treat the tokeniser as part of the model. Train it on the same cleaned data, with the same preprocessing, and version it with the weights (chapter 13).
  • Audit the vocabulary after training. Count how often each token occurred in the training run, or inspect the weights for rows that look untouched, as Land and Bartolo's open-source tool does. Do it on a small test run first.
  • Test the vocabulary by round trip. Encoding and decoding every token catches unreachable tokens and manually added entries that conflict with trained ones.
  • Sanitise at the edges. User text and retrieved documents can contain strings that map to rare tokens; decide on a policy (strip, split, reject) rather than letting the model improvise.
  • Be careful with explanations. A striking behaviour deserves a mechanism that was tested on a model with known data. The 2023 story is compelling, and the 2024 paper is what shows it generalises.

Key takeaways

  • Tokeniser and model are trained on different data; tokens common in the first and rare in the second become under-trained rows.
  • In early 2023 about 374 GPT tokens (around 133 truly weird) could not be repeated reliably; ' SolidGoldMagikarp' was a Reddit counter's username.
  • Mechanism: input rows get no gradient; output rows are pushed down every step; unseen rows end near initialisation or at zero with weight decay.
  • Detection needs only the weights and tokeniser: cosine distance to unused rows or input norm, then a prompt-based check. Typically 0.1 to 1% of a vocabulary is affected.
  • The fix is process: shared data and preprocessing between tokeniser and model, vocabulary audits, and input sanitisation.

Check your understanding

Why can a string such as " SolidGoldMagikarp" be a token in the vocabulary yet have almost no training signal?

  1. Byte-pair encoding only adds tokens that the model has already learned
  2. The tokeniser's corpus and the model's corpus are different, and the string was frequent in the first but absent from the second
  3. Embedding rows are initialised to zero and never change
  4. Long tokens are always removed during training
Vocabulary construction counts pairs in the tokeniser corpus. The model learns row by row from its own corpus, so a token can earn a slot without ever appearing in a training batch.

In an untied model, an input embedding row for a token that never appears in training is shrinking towards zero. What is the most likely reason?

  1. The softmax raises its probability at every step
  2. Gradient clipping rescales it
  3. The model memorises it as a special token
  4. It receives no gradient from the loss and is changed only by weight decay
Land and Bartolo reason that input rows are updated only when their token is in the batch; otherwise only a weight-decay term acts. If weight decay is not used, the row stays near its initial value.

Land and Bartolo's pipeline flags a candidate as under-trained after a prompting check. What is the criterion?

  1. The model assigns the token a maximum output probability below 1% in contexts where a normal token would be predicted with high probability
  2. The model refuses to answer
  3. The token has fewer than ten characters
  4. The token is the nearest to the cluster centroid
Verification builds repetitive prompts and checks the probability of the candidate. Refusals and centroid distance were features of the 2023 anecdotes; the 2024 method uses weight indicators to shortlist and the probability check to confirm.

You are about to ship a model with a new tokeniser trained on a large web scrape, while the model is trained on a filtered subset. Which action best applies this case's lessons?

  1. Lower the temperature to 0 so odd tokens cannot cause random output
  2. Increase the vocabulary size to dilute rare tokens
  3. Count each token's occurrences in the model's training data (or inspect the weights) and handle the zero-count ones before release
  4. Add an instruction to the system prompt saying not to repeat strange strings
The original authors saw nondeterminism even at temperature 0, a bigger vocabulary tends to add more under-trained tokens, and a prompt instruction does not give the missing embedding any information. An audit does address the cause.

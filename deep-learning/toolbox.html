Toolbox

Deep learning is a loop of writing a model, training it, watching the run, and finding out where the time and memory went. Six tools cover that loop, from the framework itself to a free GPU for the days your laptop is too slow. Each card has setup notes, what the tool is for, and a ten-minute exercise tied to the chapters.

How to use this page

Jump to a tool when a chapter or studio points at it. I wrote this page on a laptop with Python 3.14 and NumPy 2.5, which is the environment of the whole course; PyTorch, TensorBoard, Weights & Biases and a GPU were not available. So the page is built in two layers. Everything that can be computed without those tools I ran, and the output is real: the reference gradients a PyTorch (or JAX) autograd must reproduce, parameter counts and FLOP estimates for nanoGPT's configurations, a tokenisation and byte-pair-encoding demonstration, a logging and smoothing experiment on the debugging studio's training run, a timing of arithmetic-bound against memory-bound work and a profile of a training step, and a fit table for a 16 GB card. Everything that needs the tool itself is a listing marked "not run here" with no output, and the text says what to look for instead. I checked the commands and APIs against the projects' own documentation or README files on 14 October 2026, and I list what I read in each card. I also ran the same autodiff exercise in JAX, which was installed. Trust your own terminal and --help over this page, and treat every speed and price as dated.

Write and train

The framework that carries the chapters' code, and the small GPT implementations to read, run and break.

PyTorch

Install: pip install torch for a CPU build, or the command from the selector on pytorch.org for your CUDA or Apple Silicon setup (I did not install it here) · Alternatives: JAX (the same autodiff idea in a functional style; installed here, see the exercise), TensorFlow · Chapters: 5, 12; also A0 chapter 9 for the engine underneath

PyTorch gives you tensors that live on a CPU or GPU, an autograd engine that records operations and differentiates them (the machine of A0 chapter 9), modules that own parameters, and optimisers. Chapter 5 maps each NumPy operation of the early chapters onto its PyTorch counterpart, and chapter 12 uses them to build a GPT. The best first use of the tool is as a calculator you can check against your own derivation: if you can predict the gradient of a three-line function by hand, you understand what loss.backward() does.

10-minute guided exercise

Reproduce a hand-derived gradient, then break it. The reference below is real output from NumPy, written with the backpropagation of chapter 2: one example x = [1, 2], a ReLU layer with the weights shown, targets [1, 0], and loss ½∑(z − t)2. The last line is a finite-difference check, which is what torch.autograd.gradcheck does in double precision.

"""The numbers PyTorch's autograd must reproduce in the exercise below (computed by hand-written NumPy backprop)."""
import numpy as np

x = np.array([[1.0, 2.0]])                       # one example, two features
w = np.array([[0.5, -1.0], [0.25, 0.75]])
b = np.array([0.1, -0.2])
t = np.array([[1.0, 0.0]])

def loss_fn(w, b):
    z = np.maximum(x @ w + b, 0)                 # ReLU layer
    return 0.5 * ((z - t) ** 2).sum()

pre = x @ w + b
z = np.maximum(pre, 0)
dz = (z - t) * (pre > 0)                         # chain rule through the ReLU
gw, gb = x.T @ dz, dz.sum(0)
print("loss      ", round(float(loss_fn(w, b)), 6))
print("w.grad    ", gw.round(6).tolist())
print("b.grad    ", gb.round(6).tolist())

# the same gradients by finite differences, which is what torch.autograd.gradcheck does in float64
eps, num = 1e-6, np.zeros_like(w)
for i in range(2):
    for j in range(2):
        wp, wm = w.copy(), w.copy()
        wp[i, j] += eps; wm[i, j] -= eps
        num[i, j] = (loss_fn(wp, b) - loss_fn(wm, b)) / (2 * eps)
print("numeric w ", num.round(6).tolist(), " max difference", float(abs(num - gw).max()))

  2. Minute 2 to 4: the same function in JAX, which was installed here. Real output from JAX 0.11.2 on the CPU: 
    """The same exercise in JAX (installed on the machine that wrote this page): reverse-mode autodiff in another framework."""
import jax, jax.numpy as jnp
x = jnp.array([[1.0, 2.0]]); t = jnp.array([[1.0, 0.0]])
w = jnp.array([[0.5, -1.0], [0.25, 0.75]]); b = jnp.array([0.1, -0.2])

def loss_fn(w, b):
    z = jax.nn.relu(x @ w + b)
    return 0.5 * jnp.sum((z - t) ** 2)

loss, (gw, gb) = jax.value_and_grad(loss_fn, argnums=(0, 1))(w, b)
print("jax", jax.__version__, "devices", jax.devices())
print("loss      ", round(float(loss), 6))
print("w.grad    ", [[round(float(v), 6) for v in row] for row in gw])

    Three engines (hand-written NumPy, JAX, and your PyTorch run) agreeing is the point: autodiff is a mechanism, not a framework feature.
  3. Minute 4 to 6: break it on purpose. Change the target to [1.0, 5.0] and predict w.grad before running (the second column becomes negative: the unit is below its target, so the loss falls if its weights grow). Then call loss.backward() twice and observe that the gradients double, because PyTorch accumulates into .grad; that is why every training loop calls optimizer.zero_grad() (chapter 5).
  4. Minute 6 to 8: find your device. Run torch.cuda.is_available() and, on a Mac, torch.backends.mps.is_available(); move a tensor with .to(device) and check x.device and x.dtype. A model and its data must be on the same device, and the commonest first error message is about exactly that.
  5. Minute 8 to 10: call fused attention. Create q, k, v of shape (B, h, T, d_k) with torch.randn and call torch.nn.functional.scaled_dot_product_attention(q, k, v, is_causal=True). Compare with the NumPy attention of chapter 9 on the same inputs (convert with .numpy()); the difference should be of the order of float32 rounding, about 10-7. Chapter 19 explains what the fused kernel does underneath.

What to look for

  • The shapes at every step. Print w.grad.shape and check it equals w.shape; a gradient always has the shape of the thing it is the gradient of.
  • The gap between the three engines is below 10-6 in float32. If it is larger, you made an algebra slip, not a framework difference.
  • Which of your operations are in-place. They save memory and can silently break the backward pass.

Common pitfalls

  • Forgetting optimizer.zero_grad(), so gradients accumulate across steps.
  • Evaluating without model.eval() and torch.no_grad(), which leaves dropout on and wastes memory on a graph you never differentiate.
  • Reading loss as a Python float every step on a GPU with .item(); it forces a synchronisation that slows the loop. Log every few steps.
  • Copying a PyTorch tutorial's learning rate to a different model without the checks of chapter 3 and the debugging studio.

nanoGPT, nanochat & minGPT

Needs: Python, PyTorch, a clone of the repository; a GPU for the full runs, a laptop for the reduced one · Where: github.com/karpathy/nanoGPT, github.com/karpathy/nanochat, github.com/karpathy/minGPT · Alternatives: Hugging Face transformers for models you load rather than read · Chapters: 12, 14, 16

Andrej Karpathy's repositories are the course's reference implementations: small enough to read in an afternoon, real enough to train a useful model. minGPT is a roughly 300-line educational GPT (mingpt/model.py, a trainer.py, and bpe.py, a byte-pair encoder as in GPT-2) with demo projects such as character-level training and learning to add numbers. Its README calls it "semi-archived" and points to nanoGPT. nanoGPT is the rewrite aimed at reproducing medium-sized results with a faster training loop; its README now says it is "very old and deprecated" and points to nanochat, described as a minimal harness covering tokenisation, pretraining, fine-tuning, evaluation and a chat interface on a single GPU node. The README quotes about $48 for roughly two hours on an 8×H100 node (around $3 per GPU-hour) to reach GPT-2-class capability, and about 1.5 hours for its speedrun.sh. Those are the authors' figures from the README as I read it on 14 October 2026; they change with the code. This course follows nanoGPT's layout because it is the one the chapters' listings resemble, and nanochat is where to look for how it is done now. In spirit, chapter 12 is a rewrite of the same idea in the course's notation, with original explanations.

10-minute guided exercise

Predict a training run's size and speed before you start it. The first script needs no install: it counts the parameters of nanoGPT's two Shakespeare configurations and of GPT-2 small, with the arithmetic of chapter 16. The configuration values come from the repository's config/train_shakespeare_char.py and the laptop command in the README, and the model details (tied embeddings, a 4× GELU MLP, a position table that get_num_params subtracts by default) from model.py.

"""What a nanoGPT config means in parameters, FLOPs and implied speed (chapter 16 arithmetic)."""
def gpt2_params(L, C, T, V, bias=False, tied=True):
    block = 12 * C * C + 13 * C if bias else 12 * C * C + 2 * C      # attention 4C^2, MLP 8C^2, two LayerNorms (+ biases)
    total = L * block + V * C + T * C + (2 * C if bias else C)          # token table, position table, final LayerNorm
    return total if tied else total + V * C, total - T * C              # (all, non-embedding-position as nanoGPT prints)

    "laptop CPU command in the README": dict(L=4, C=128, T=64, V=65, batch=12, iters=2000),
    "GPT-2 small (GPTConfig defaults)": dict(L=12, C=768, T=1024, V=50304, batch=None, iters=None),
}
for name, c in configs.items():

Then check the log line at start-up, which prints a parameter count, against your prediction, and compare the iteration time with your estimate. Note that nanoGPT's built-in MFU estimate (estimate_mfu, using 6N + 12LHQT FLOPs per token) divides by an A100 bf16 peak of 312 TFLOP/s whatever your hardware is, so on a CPU or laptop GPU the printed MFU is not a real utilisation.

What to look for

  • Training loss below validation loss and widening: the small dataset is being memorised. The config saves a checkpoint only when validation loss improves for that reason.
  • The first printed loss near ln 65 = 4.17 for a 65-character vocabulary (chapter 3). If it is far above, something is mis-scaled.
  • Samples that go from noise to word-like to line-like as validation loss falls from about 2.5 to 1.5: the language-modelling objective of chapter 14 in action.

Common pitfalls

  • Running the GPU configuration on a CPU. It is a 10M-parameter model on a 256-character context; it will work but slowly. Use the README's reduced command.
  • Using torch.compile on a machine where it is not supported; the laptop command sets --compile=False for that reason.
  • Comparing your loss with a number from a different tokeniser or dataset. Character-level and byte-pair losses are not comparable (chapter 13).

Many surprising model failures are tokenisation failures. Look at the tokens before you look at the model.

Tokeniser playgrounds

Nothing to install: the web app at tiktokenizer.vercel.app (it shows the tokenisation of the encoding used by OpenAI's models, with a "Show whitespace" option, as I read on 14 October 2026) · In code: pip install tiktoken, or Hugging Face tokenizers / transformers (AutoTokenizer.from_pretrained(...)) for open models · Alternative: the small BPE trainer below, which you can read in a minute · Chapters: 13; case study 6

A tokeniser decides what the model's atoms are, and with it how many tokens your text costs, how much fits in the context window, and which strings the model has barely seen (chapter 13). A playground lets you paste text and see the pieces. The exercise below starts with the part you can compute yourself, bytes, then builds a toy tokeniser, then sends you to a real one.

10-minute guided exercise

  1. Minute 0 to 3: count bytes and read the second half of the output. def train_bpe(text, merges):
    ids = list(text.encode("utf-8"))
    table = {}
    for k in range(merges):
        pairs = Counter(zip(ids, ids[1:]))
        if not pairs: break
        (a, b), n = pairs.most_common(1)[0]
        new = 256 + k
        table[(a, b)] = new
        out, i = [], 0
        while i < len(ids):
            if i + 1 < len(ids) and ids[i] == a and ids[i + 1] == b:
                out.append(new); i += 2
            else:
                out.append(ids[i]); i += 1
        ids = out
        yield k, (a, b), n, new, len(ids), table

What to look for

  • Tokens per character for each language you care about. A multilingual product with a 3× token tax on one language has a 3× cost and a third of the context for those users.
  • Strings that become many tiny pieces: identifiers, rare names, base64, code with unusual spacing. These are also where glitch tokens and tokeniser-model mismatches live (case study 6).
  • That a model sees ids, not letters. Questions such as counting the letters in a word are hard for reasons visible in the pieces.

Common pitfalls

  • Using a tokeniser that does not belong to the model. Token ids are meaningless across vocabularies, and a count from the wrong one will mis-size your context budget.
  • Forgetting special and chat-template tokens when counting a prompt's length.
  • Comparing perplexity across different tokenisers; compare bits per character (planning studio, stage 6).

Watch the run

A long training run is a production service with an expensive failure mode. You watch it with metrics.

TensorBoard & W&B

Install: pip install tensorboard (it reads event files; the PyTorch writer torch.utils.tensorboard.SummaryWriter writes them), or pip install wandb with a free account for the hosted alternative · Alternatives: plotting a CSV yourself with a spreadsheet or Matplotlib, MLflow · Chapters: 3, 17; debugging studio

TensorBoard is a local dashboard for scalars, histograms and images written during a run; Weights & Biases (W&B) is a hosted service that does the same and adds run comparison, configuration tracking and sharing. Their value is not the plots but the habit: log the signals of chapter 17's table (loss, held-out loss, gradient norm before clipping, update-to-weight ratio, learning rate, loss scale, largest logit, throughput) on every run, so you can see a failure while it is cheap. The listings below follow the PyTorch and W&B documentation as I read them on 14 October 2026 (SummaryWriter with add_scalar, add_histogram, flush and close, tags with slashes grouping plots; W&B's wandb.login(), wandb.init(project=..., config=...) and run.log({...})).

def ema(x, a):                                  # the smoothing slider: exponential moving average with debiasing
    out, s, w = [], 0.0, 0.0
    for v in x:
        s = a * s + (1 - a) * v; w = a * w + (1 - a)
        out.append(s / w)
    return np.array(out)

What to look for

  • A flat update-to-weight ratio that sits near 10-3 in a healthy run, orders of magnitude below it in a stalled one (studio 1).
  • The gradient norm moving before, or with, the loss. It is the earliest warning (chapter 17).
  • A hyperparameter table next to the curves. A run you cannot reproduce from its logged configuration was a wasted run.

Common pitfalls

  • Logging only the training loss; or logging every step of everything, which makes the dashboard slow and the files huge. Log scalars every step or few steps and histograms rarely.
  • Leaving the smoothing slider high and missing a spike, as the table shows.
  • Putting an account key in a script you commit. Use an environment variable (keys and secrets).
  • Sending logs from a workplace to a hosted service without checking what the logged data and configuration contain.

Find the time

When a run is slower than the plan of chapter 16, measure; do not guess.

PyTorch profiler

Needs: PyTorch (torch.profiler is part of it); a GPU to see CUDA kernels; the Chrome trace it exports opens in a trace viewer such as Perfetto · Alternatives: cProfile for the Python side (used below), NVIDIA's Nsight tools for kernels, torch.cuda.max_memory_allocated() for memory · Chapters: 16, 19; Zero to Systems 21 and 22

The profiler records every operation, on the CPU and the GPU, with its time and optionally its input shapes and memory use. It answers the questions the arithmetic of chapter 16 cannot: is the step dominated by matrix multiplications or by memory-bound operations, is the GPU idle waiting for data, and did the fused attention kernel actually run (chapter 19)? The API below is from the official PyTorch profiler recipe as I read it on 14 October 2026: profile(activities=[ProfilerActivity.CPU], record_shapes=True, profile_memory=True), key_averages().table(sort_by=..., row_limit=...) and export_chrome_trace("trace.json"), with CUDA added to activities when a GPU is present. The recipe page does not show a TensorBoard trace handler, so I do not include one.

  1. Minute 0 to 4: learn what the profiler will show, with NumPy. The two kinds of work in a training step have very different speeds. This script times a matrix multiplication (many FLOPs per byte) and an elementwise addition (almost none), then profiles the debugging studio's training step with Python's cProfile. def best(fn, reps=7):
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); fn(); ts.append(time.perf_counter() - t0)
    return min(ts)

Count the rows that are elementwise (additions, GELU, layer norm, softmax, copies): a long tail of them means memory traffic, and is where fusion (torch.compile, fused kernels) pays. Compare the total time with your 6ND estimate divided by the card's peak to compute your real utilisation.
  4. Minute 9 to 10: check memory. Print torch.cuda.max_memory_allocated() / 1e9 after one full step and compare it with the calculator in chapter 16; remember that Adam's moments are allocated lazily on the first optimizer.step().

What to look for

  • Gaps in the GPU timeline in the trace: the GPU is idle, usually waiting for the data loader or for a synchronisation.
  • The attention kernel's name. If you expected a fused kernel and see separate score, softmax and matmul operations, the fast path was not taken.
  • The most expensive operation, as a fraction of the step, before you optimise anything. Fix the biggest line first (performance engineering).

Common pitfalls

  • Profiling the first step, which includes one-off start-up work. Warm up first.
  • Profiling too many steps: traces get large. Four steps is plenty.
  • Timing GPU code with a wall clock without synchronising, which measures the launch, not the work.
  • Reading the CPU-side table of a GPU job and concluding it is CPU-bound.

What to look for

  • The actual card and its free memory at the start of every session; they vary.
  • Throughput in tokens per second against your estimate from chapter 16. If you are far below it, profile (see the PyTorch profiler card) before blaming the hardware.
  • Whether the run survives a restart without losing the optimiser state.

Common pitfalls

  • Leaving a notebook idle with a GPU attached; the session ends and unsaved state is lost.
  • Assuming today's free allowance is tomorrow's. Limits are not published and fluctuate.
  • Using the notebook for secrets or private data, or committing a notebook with an access token in a cell.
  • Installing a different PyTorch version in the middle of a session and breaking the preinstalled build; restart the runtime after installing.

Key takeaways

  • Use a framework as a calculator you can check: hand-derived gradients, NumPy, JAX and PyTorch should agree to float32 rounding.
  • Read the small GPT implementations, and predict a configuration's parameters and FLOPs before running it.
  • Look at tokens and bytes before blaming the model; a tokeniser's cost differs sharply by language and by string type.
  • Log the signals of chapter 17 on every run, keep a raw gradient-norm panel, and be wary of heavy smoothing.
  • Profile before optimising: matrix multiplications are arithmetic-bound, elementwise operations are memory-bound, and the biggest line comes first.
  • A free GPU is good for experiments and fine-tuning, not for long or private runs; checkpoint to survive the session limits.

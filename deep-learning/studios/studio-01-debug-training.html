Debug a Training Run That Will Not Learn

A teammate's training run shows a flat loss. You fix that, and the loss falls and then spikes. You fix that, and later the loss turns into NaN. Three different causes, found one after another, each with its own evidence. You will work through them on a small model whose three real runs, logs and replays are all on this page.

How a design studio works

This page is a mock debugging session of 60 to 90 minutes, not a chapter. At each stage there is a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer is one strong investigation with its reasoning, not the only right one. The stages follow the order a good on-call engineer works in: say what healthy looks like, rank the suspects by cost, find each cause with evidence that rules the others out, check the fix, then change the process so the same bug is caught in seconds next time. Every number is the output of code that was run for this page, on a deliberately small model, so treat the thresholds as illustrations of a method rather than settings to copy to a large run.

📐 The brief

A colleague messages you: "The run will not learn. Loss has been stuck for an hour. Can you look?" You get a config, the data-loader code, the training loop and a metrics export (loss every step, held-out loss every 10 steps, gradient norm, update size, loss scale). The model is a character-level language model: an 8-character window is embedded, passed through four ReLU layers of width 128, and mapped to 27 logits (26 letters and a space). The text is the Zipf-law pseudo-word source from chapter 18, so the best possible loss is about 0.68 nats per character.

  • Three independent faults are planted: one in the data pipeline, one in a data shard, one in the numerics. Fixing one reveals the next, as it does in real projects.
  • Any measurement that takes under a minute is allowed. Nothing may be fixed on a hunch: each cause needs evidence that supports it and evidence that rules out its rivals.
  • Builds on initialisation and the ln V check (chapter 03), mixed precision and training stability (chapter 17), resource accounting (chapter 16), Adam (A0 chapter 10) and floating point (A0 chapter 11). For the operations side see checkpoints, failures and long runs and alerting.
  • You have 60 to 90 minutes. Run the code if you can: everything uses NumPy only and takes seconds.

One definition: the held-out loss is the cross-entropy on text the model never trains on. It is the number that says whether the model is getting better, because the training loss is measured on whichever batch happened to arrive, which may be easy, hard or corrupt.

Order by cost to test, then by how often the cause is the culprit. Experienced practitioners put the data first: Andrej Karpathy's "A Recipe for Training Neural Networks" (2019) begins with "become one with the data", and most silent failures in practice are data bugs, because a data bug trains without any error message. Reading the evidence, one rung at a time:

  • Initialisation is fine. The first loss is 3.33 against ln 27 = 3.30, so the logits start near zero. This rules out the huge-logit failure of chapter 03.
  • The plateau is a specific number. The mean training loss over steps 400 to 1,000 is 3.07, and the entropy of the letter frequencies alone is 3.04. The model has learned exactly "how common is each letter" (the output bias can do that) and nothing that depends on the input. A model that was merely slow would be somewhere between 3.3 and 3.04 and still moving.
  • The optimiser is working. The update-to-weight ratio is 1.9×10-3, in the healthy range, and every tensor has a non-zero gradient (0.07 in the hidden layers, 0.37 at the output). This rules out a tiny learning rate, a frozen parameter and a dead network.
  • The model and the loss can learn. On one fixed batch of 64 examples the loss falls to 0.022 within 300 steps. This is the memorisation test. It passes for both the real labels and the shuffled ones, which is itself a clue: a network can memorise random labels, so a pass here clears the model and optimiser but says nothing about whether the labels mean anything.
  • The labels are wrong. Decoding the loader's output next to the raw text shows windows like 'm hpbo e' labelled q when the text continues with f. The label equals the true next character in 9% of the 128 examples, where a correct loader gives 100%. The 9% is not zero because some letters (and the space) are common enough to match by chance.

Cause 1: the loader shuffles the labels independently of the inputs. A refactor that added "shuffle for each epoch" applied the permutation to the label array only. The inputs are real text and the targets are real characters from the same distribution, so nothing crashes and the training loss looks like an ordinary plateau. Fix: shuffle indices once and apply them to both arrays, and add a loader test that compares a batch with the raw text.

Common misconception

"If the model can overfit one batch, the pipeline is correct." It shows the model and optimiser are capable, not that the data is meaningful: random labels are memorised just as well. The overfit test is a way to rule out the model, and the decoded batch is a way to rule in the data. Use both.

4Four bugs, one symptom

Suppose the loader had been correct and the same flat loss appeared. Name two other causes that give a flat curve, and say which cheap measurement would separate each from the shuffled labels.

Compare with a worked answer

A flat loss is a symptom with many causes, and the point of the ladder is that each cause leaves a different fingerprint. The script plants three different faults in the same harness, plus a healthy control, runs each for 600 steps and takes the cheap measurements side by side. "Hidden grad" is the gradient norm of the four hidden weight matrices on one batch at step 600.

"""Four causes of a flat loss, and the cheap measurements that tell them apart."""

def overfit_one_batch(cfg, steps=300):
    c = {**DEFAULT, **cfg, "warmup": 1, "floor": 1.0, "total": steps}
    xb, yb = get_batch({**c, "labels": "aligned"}, 1, {})
    xb, yb = xb[:64], yb[:64]                      # one fixed batch of 64 real examples
    s = new_state(c); P, m, v = s["P"], s["m"], s["v"]
    for t in range(1, steps + 1):
        hs = forward(P, xb, 4); loss, g = cross_entropy(hs[-1], yb)
        for i, q in enumerate(backward(P, xb, hs, g, 4)):
            m[i] = .9 * m[i] + .1 * q; v[i] = .999 * v[i] + .001 * q * q
            P[i] -= c["lr"] * (m[i] / (1 - .9 ** t)) / (np.sqrt(v[i] / (1 - .999 ** t)) + 1e-8)
    return loss

Two further things worth noticing. First, the first two faults plateau near the same value, 3.03 and 3.06, because in both cases the only thing the network can learn is the marginal letter frequencies; the update ratio and the gradient are what tell them apart, not the loss. Second, tiny initial weights are not on the list even though chapter 03 shows how they shrink the signal. With Adam (A0 chapter 10) every parameter moves by roughly the learning rate per step whatever the gradient's size, so a network started from weights of 0.01 began to learn within a few hundred steps when I tried it (slowly, but it learned, and so did a 12-layer version). Optimisers and initialisation interact, so check what the optimiser does with the fault before you blame it.

Reading the timeline:

  • The gradient moves first, and with the loss. At step 699 the gradient norm is 1.55, normal. At step 700 it is 6.86, five times typical, and the training loss jumps from 1.02 to 5.30. The cause acts at step 700 itself; nothing was building up before it. That points away from a learning rate that was creeping too high (the gradient norm would drift upwards over hundreds of steps, as chapter 17 describes) and towards something that arrived suddenly.
  • The update size jumps too. The update-to-weight ratio goes from 2.6×10-3 to 6.1×10-3 and then 8.1×10-3 a few steps later. That is Adam's response (chapter 17): the first moment reacts to the big gradient at once while the second moment, which averages over about 1,000 steps, has barely moved.
  • The damage outlasts the cause. The training loss during steps 700 to 719 is high partly because the batches are hard. The held-out loss separates that from real damage: it is 1.02 before, and 2.61 at step 710 and 3.17 at step 720, when the model itself has been pushed far from where it was. It is back to 1.13 at step 800 and 1.02 at step 900. Always plot a held-out loss on clean data beside the training loss: it is the instrument that says whether the model was hurt.
  • The event has a width. The gradient is back to normal by step 720 (0.81). Something lasted about twenty steps. That suggests a block of consecutive bad batches, not one stray example.

The candidate causes, in the order of the ladder: a corrupt block of data; an optimiser setting that makes ordinary batches dangerous (a high learning rate, β2 = 0.999, no clipping); a numerical event. The data check is the cheapest, so it comes first. The batch scan in the script scores each batch by its average surprise under a bigram model fitted to clean text (a rough validator of the kind a data pipeline can run). Median batch: 2.14 nats per character pair. Twenty batches, steps 700 to 719 exactly, score 4.48 to 4.69. Printing them shows why: the window ' mmgbgsd' at step 700 is not text. A job that wrote a binary file into the corpus fed uniformly random characters to the loader for twenty steps.

Cause 2: twenty junk batches in a data shard. The coincidence of the step range with the validator's flags is the evidence for it. What remains to be shown is that the data, rather than the optimiser settings, is the cause, and that is a replay experiment.

  • Clipping is the instructive case. A clip at 3.0, about twice the typical norm of 1.4, engages on only 2% of steps and barely helps (peak 3.12). This is the "clip as a symptom" warning of chapter 17 in numbers. Choose the threshold from the logs (a small multiple of the typical norm), and use the fraction of clipped steps as a health signal.

The fix has two parts, in this order. Quarantine the corrupt shard and add the batch validator to the pipeline (the cause). Keep a clip at 3.0 as a safety net for the next surprise (the damage limiter). Do not ship the settings changes alone: they would hide the data problem and cost throughput for ever.

What changes at scale

On a large run you cannot replay twenty steps in seconds, and the PaLM authors report that replaying a spike from an earlier checkpoint did not reproduce it (chapter 17). The method survives: keep a checkpoint every few hundred steps, record which data shard each step read, and when a spike comes, rerun from the checkpoint with the suspect batches skipped. The harness here makes the cause deterministic so that the logic is visible.

Cause 3: a loss scaler that grows on a timer and never backs off. It is the exact failure the dynamic scaling rule of chapter 17 prevents ("if any gradient contains an infinity or NaN, skip that optimiser step and halve the scale"). The three-way comparison at the bottom of the output shows the fix works and that the original was partly luck: with fp32 gradients there is no NaN; a scaler that doubles every 1,000 steps happens not to overflow within 3,000 steps; the dynamic scaler skips 2 steps over the run, halves the scale twice, and finishes at 0.744. A bug that passes in some configurations and fails in others is the typical shape of a numerical fault.

The better fix, for a real model, is to avoid loss scaling by training in bf16, which has fp32's range (chapter 17). The dynamic scaler is the fix when you must stay in fp16, and it is the one that fits this harness.

Go deeper optional

Why does the scale matter at all, if gradients are divided by it again? Because the rounding to 16 bits happens in between. A scale that is too low lets small gradients underflow to zero (they stop teaching); a scale that is too high lets large ones overflow to infinity (they poison the step). Dynamic scaling hunts for the largest scale that does not overflow: it grows after a long run of clean steps and halves on the first infinity, which is the pattern in the dynamic row above.

The same arithmetic shows a design trap. As the scale grows, the safe maximum gradient entry shrinks (65,504 / 262,144 = 0.25), so the bug did not require the model to change: it only required time to pass. A fault whose trigger is "the training counter reached 2,000" will not appear in a 200-step smoke test, which is why the preflight in stage 10 injects an infinity on purpose.

9Instrument it: alerts that fire before the loss does

You will not be watching the next run. Which signals would you alert on, against what baseline, and which of the three failures would each have caught earliest? Beware alerts that cry wolf.

The principle from chapter 17 is to alert against the run's own recent past, as you would on a latency percentile (alerting and on-call), not against an absolute number. Five rules cover the three failures. The script runs them on all three runs; a rule is reported at the first step it fires.

"""Alert rules for a training run, tried on all three runs of studio 1."""
import numpy as np, warnings
warnings.filterwarnings("ignore")
from harness import *

FP16_MAX = 65_504

def alerts(rows):
    """Return {rule: first step it fires}. Rules compare each step with the run's own recent past."""
    first = {}
    def fire(rule, step): first.setdefault(rule, step)
    ev = [(r["step"], r["eval"]) for r in rows if "eval" in r]
    for i, r in enumerate(rows):
        t = r["step"]
        if r["skipped"]:
            continue                                  # the dynamic scaler already handled this step
        recent = [x["gnorm"] for x in rows[max(0, i - 100):i] if np.isfinite(x["gnorm"])]
        if len(recent) >= 50 and r["gnorm"] > 4 * np.median(recent):
            fire("grad norm above 4x its 100-step median", t)
        if r["gmax"] * r["scale"] > 0.9 * FP16_MAX:
            fire("fp16 headroom under 10%", t)
        if t >= 100 and r["ratio"] > 0 and not 1e-4 < r["ratio"] < 1e-2:
            fire("update/weight ratio outside 1e-4 to 1e-2", t)
        if "eval" in r and t >= 500 and min(e for _, e in ev if _ <= t) > 0.9 * np.log(V):
            fire("best eval loss still above 90% of the chance loss ln V after step 500", t)
        if "eval" in r:
            prev = [e for s, e in ev if s < t][-3:]
            if prev and r["eval"] > 1.3 * min(prev):
                fire("eval loss 30% above its recent best", t)
        if not np.isfinite(r["loss"]) or not np.isfinite(r["gnorm"]):
            fire("non-finite loss or gradient", t)
    return first

10Preflight, and what the bugs would have cost

Write the smoke test that would have caught all three faults before the long job started. Then estimate, with explicit assumptions, what the three bugs would cost on a real cluster-scale run.

A preflight is the ladder turned into code: five checks, run on the real configuration and the real loader, in under a minute, before the expensive job is submitted. The fifth check injects an infinity on purpose, which is the only way to find out whether the scaler's safety logic exists.

"""preflight.py: five checks that run in seconds on the small config, before the big job is launched."""
import numpy as np, warnings
warnings.filterwarnings("ignore")
from harness import *

def preflight(cfg):
    c = {**DEFAULT, **cfg}
    out, cache = [], {}
    # 1. initial loss is about ln V
    xb, yb = get_batch(c, 1, cache)
    s = new_state(c); l0 = cross_entropy(forward(s["P"], xb, c["depth"])[-1], yb)[0]
    out.append(("initial loss within 10% of ln V", abs(l0 / np.log(V) - 1) < 0.10, f"{l0:.2f} vs {np.log(V):.2f}"))
    # 2. the loader's label is the next character (checked against the raw text of the shard)
    text = make_text(SHARD_STEPS * BATCH + K, 100); _, Ys = windows(text)
    agree = np.mean(yb == Ys[:BATCH])
    out.append(("labels are the next character", agree > 0.99, f"{agree:.0%} agree"))
    # 3. the model can memorise one batch
    c1 = {**c, "garbage": (), "warmup": 1, "floor": 1.0, "total": 200, "labels": "aligned"}
    xb1, yb1 = get_batch(c1, 1, {}); xb1, yb1 = xb1[:64], yb1[:64]
    s1 = new_state(c1); P, m, v = s1["P"], s1["m"], s1["v"]
    for t in range(1, 201):
        hs = forward(P, xb1, c["depth"]); loss, g = cross_entropy(hs[-1], yb1)
        for i, q in enumerate(backward(P, xb1, hs, g, c["depth"])):
            m[i] = .9 * m[i] + .1 * q; v[i] = .999 * v[i] + .001 * q * q
            P[i] -= c["lr"] * (m[i] / (1 - .9 ** t)) / (np.sqrt(v[i] / (1 - .999 ** t)) + 1e-8)
    out.append(("memorises one batch of 64 in 200 steps", loss < 0.3, f"loss {loss:.2f}"))
    # 4. the data scan: no batch far more surprising than the rest (first 1,000 steps)
    ref = make_text(200_000, 5); cnt = np.ones((V, V))
    for a, b in zip(ref, ref[1:]): cnt[IDX[a], IDX[b]] += 1
    nll = -np.log(cnt / cnt.sum(1, keepdims=True)); sc = []
    for t in range(1, 1001):
        x, _ = get_batch(c, t, cache); sc.append(nll[x[:, :-1], x[:, 1:]].mean())
    sc = np.array(sc); med = np.median(sc); bad = int((sc > med + 8 * np.median(abs(sc - med))).sum())
    out.append(("no junk batches in the first 1,000", bad == 0, f"{bad} flagged"))
    # 5. the loss scaler survives an injected infinity (skips the step instead of poisoning the weights)
    rows, st = train({**c, "total": 30, "scaler": c["scaler"], "init_scale": 2.0 ** 30}, until=30)
    survived = all(np.isfinite(r["loss"]) for r in rows) and np.isfinite(st["P"][1]).all()
    out.append(("scaler skips overflowing steps", survived, "weights finite" if survived else "weights became NaN"))
    return out

The training harness harness.py, so you can rerun everything

Every script on this page imports this file. It trains the model in NumPy with a hand-written backward pass, logs one row of metrics per step and can plant each fault through the config. Save it next to the scripts and run them with python3. Runs take from a few seconds to about 15 seconds each on a laptop.

"""harness.py: a small character-level language model in NumPy, with the faults of studio 1 as config switches.
Model: 8-character window -> 12-d embeddings -> 4 ReLU layers of width 128 -> 27 logits. Trained with AdamW-style Adam."""
import copy
import numpy as np

CHARS = "abcdefghijklmnopqrstuvwxyz "
V, K, E_DIM, BATCH, SHARD_STEPS = len(CHARS), 8, 12, 128, 500
IDX = {c: i for i, c in enumerate(CHARS)}


def make_text(n_chars, seed):
    """Zipf-distributed pseudo-words (the same source as the chapter 18 experiment)."""
    vr = np.random.default_rng(12345)
    letters = np.array(list("abcdefghijklmnopqrstuvwxyz"))
    words = ["".join(vr.choice(letters, vr.integers(2, 9))) for _ in range(400)]
    p = 1 / np.arange(1, 401) ** 1.1
    p /= p.sum()
    rng, out, n = np.random.default_rng(seed), [], 0
    while n < n_chars:
        out.append(words[rng.choice(400, p=p)])
        n += len(out[-1]) + 1
    return " ".join(out)[:n_chars]


def windows(text):
    a = np.array([IDX[c] for c in text])
    n = len(a) - K
    return np.stack([a[i:n + i] for i in range(K)], 1), a[K:K + n]      # (n, 8) inputs, (n,) next characters


def init_params(hidden, depth, std, seed):
    r = np.random.default_rng(seed)
    dims = [K * E_DIM] + [hidden] * depth + [V]
    Ws = [r.normal(0, np.sqrt(2 / a) if std is None else std, (a, b)) for a, b in zip(dims[:-1], dims[1:])]
    Ws[-1] *= 0.1                                  # small output layer: initial logits near 0, initial loss near ln V
    return [r.normal(0, 1.0, (V, E_DIM))] + Ws + [np.zeros(b) for b in dims[1:]]


def forward(P, X, depth):
    h = P[0][X].reshape(len(X), -1)
    hs = [h]
    for i, (W, b) in enumerate(zip(P[1:2 + depth], P[2 + depth:])):
        z = h @ W + b
        h = np.maximum(z, 0) if i < depth else z
        hs.append(h)
    return hs                                      # hs[-1] = logits, shape (B, 27)


def backward(P, X, hs, g, depth):
    Ws, gW, gb = P[1:2 + depth], [None] * (depth + 1), [None] * (depth + 1)
    for i in reversed(range(depth + 1)):
        gW[i], gb[i] = hs[i].T @ g, g.sum(0)
        g = g @ Ws[i].T
        if i > 0:
            g = g * (hs[i] > 0)
    ge = np.zeros_like(P[0])
    np.add.at(ge, X, g.reshape(len(X), K, E_DIM))
    return [ge] + gW + gb


def cross_entropy(z, y):
    s = z - z.max(1, keepdims=True)                # subtract the row maximum (A0 chapter 11)
    p = np.exp(s) / np.exp(s).sum(1, keepdims=True)
    g = p.copy()
    g[np.arange(len(y)), y] -= 1
    return float(-np.log(p[np.arange(len(y)), y]).mean()), g / len(y)


DEFAULT = dict(depth=4, hidden=128, init_std=None, lr=2e-3, warmup=100, total=3000, floor=0.1,
               beta2=0.999, clip=None, labels="aligned", garbage=(), seed=0,
               scaler="none", init_scale=2.0 ** 14, grow_every=500)    # scaler: "none", "naive" or "dynamic"


def lr_at(c, t):
    if t <= c["warmup"]:
        return c["lr"] * t / c["warmup"]
    prog = min(1, (t - c["warmup"]) / (c["total"] - c["warmup"]))
    return c["lr"] * (c["floor"] + (1 - c["floor"]) * 0.5 * (1 + np.cos(np.pi * prog)))


def get_batch(c, t, cache):
    shard, pos = divmod(t - 1, SHARD_STEPS)
    if shard not in cache:
        X, Y = windows(make_text(SHARD_STEPS * BATCH + K, 100 + shard))
        if c["labels"] == "shuffled":              # the refactor bug: labels shuffled on their own
            Y = Y[np.random.default_rng(7 + shard).permutation(len(Y))]
        cache[shard] = (X, Y)
    X, Y = cache[shard]
    xb, yb = X[pos * BATCH:(pos + 1) * BATCH], Y[pos * BATCH:(pos + 1) * BATCH]
    if any(a <= t <= b for a, b in c["garbage"]):  # a binary file read as text: uniformly random characters
        r = np.random.default_rng(10_000 + t)
        xb, yb = r.integers(0, V, xb.shape), r.integers(0, V, yb.shape)
    return xb, yb


def new_state(c):
    P = init_params(c["hidden"], c["depth"], c["init_std"], c["seed"])
    return dict(P=P, m=[np.zeros_like(p) for p in P], v=[np.zeros_like(p) for p in P], t=0,
                scale=c["init_scale"], clean=0)


def train(cfg, state=None, until=None, log=None):
    """Train from state['t'] + 1 to `until`. Returns (rows, state); one row of metrics per step."""
    c = {**DEFAULT, **cfg}
    st, depth = state or new_state(c), c["depth"]
    P, m, v = st["P"], st["m"], st["v"]
    Xe, Ye = windows(make_text(12_000, 999))       # clean held-out text, never trained on
    cache, rows = {}, [] if log is None else log
    for t in range(st["t"] + 1, (until or c["total"]) + 1):
        xb, yb = get_batch(c, t, cache)
        hs = forward(P, xb, depth)
        loss, g = cross_entropy(hs[-1], yb)
        grads = backward(P, xb, hs, g, depth)
        skipped = False
        if c["scaler"] != "none":                  # emulate fp16 gradients: scale up, round to 16 bits, scale back
            with np.errstate(over="ignore"):
                grads = [(q * st["scale"]).astype(np.float16).astype(np.float32) / st["scale"] for q in grads]
            if c["scaler"] == "dynamic":
                if not all(np.isfinite(q).all() for q in grads):
                    st["scale"] /= 2; st["clean"] = 0; skipped = True       # overflow: skip the step, halve the scale
                else:
                    st["clean"] += 1
                    if st["clean"] >= c["grow_every"]:
                        st["scale"] *= 2; st["clean"] = 0
            elif t % c["grow_every"] == 0:
                st["scale"] *= 2                   # the homemade scaler: doubles on a timer, never checks for inf
        gmax = max(float(np.abs(q).max()) for q in grads)
        gn = float(np.sqrt(sum(float((q.astype(np.float64) ** 2).sum()) for q in grads)))
        clipped = bool(c["clip"] and np.isfinite(gn) and gn > c["clip"])
        if clipped:
            grads = [q * c["clip"] / gn for q in grads]
        lr, dsq, wsq = lr_at(c, t), 0.0, 0.0
        if not skipped:
            for i in range(len(P)):
                m[i] = .9 * m[i] + .1 * grads[i]
                v[i] = c["beta2"] * v[i] + (1 - c["beta2"]) * grads[i] ** 2
                step = lr * (m[i] / (1 - .9 ** t)) / (np.sqrt(v[i] / (1 - c["beta2"] ** t)) + 1e-8)
                P[i] -= step
                dsq += float((step.astype(np.float64) ** 2).sum()); wsq += float((P[i].astype(np.float64) ** 2).sum())
        st["t"] = t
        row = dict(step=t, loss=loss, gnorm=gn, gmax=gmax, clipped=clipped, skipped=skipped, lr=lr,
                   ratio=float(np.sqrt(dsq / wsq)) if wsq else 0.0, maxlogit=float(np.abs(hs[-1]).max()), scale=st["scale"])
        if t % 10 == 0 or t == 1:                  # held-out loss every 10 steps
            z = forward(P, Xe, depth)[-1]
            row["eval"] = cross_entropy(z, Ye)[0]
        rows.append(row)
        if not np.isfinite(loss):
            break                                  # stop once the loss itself is NaN
    return rows, st


def snapshot(st):
    return copy.deepcopy(st)

Self-check rubric

Tick what your own investigation (before reading the answers) covered. The first items are what a solid mid-level answer has; the later ones separate a senior answer.

  • Wrote down the expected numbers first: initial loss ln V, the letter-frequency baseline, the floor and the shape of a healthy curve.
  • Ranked the suspects cheapest and most common first, with the data before the model.
  • Used the initial loss against ln V and the update-to-weight ratio to clear initialisation and the optimiser.
  • Ran the one-batch memorisation test and knew what it does and does not prove (random labels can be memorised).
  • Identified the flat loss as a specific number (the letter-frequency entropy) and decoded a batch beside the raw text to find the label bug.
  • Plotted a held-out loss on clean data beside the training loss to separate hard batches from model damage.
  • Used the timing of the gradient norm relative to the loss to decide between a sudden cause and a slow drift.
  • Ran a replay from a checkpoint changing one thing to separate data from optimiser settings, and read the result honestly.
  • Recognised that clipping and learning-rate cuts mitigate a spike without removing its cause, and that a clip engaging on most steps is a symptom.
  • Found the first non-finite value in time (the gradient, one step before the loss) and in space (one tensor), and linked it to the fp16 limit of 65,504.
  • Chose between a dynamic loss scaler and bf16 and explained why a fault that depends on the step counter evades short tests.
  • Verified the fix with repeat seeds and the expected curve, not just "it finished".
  • Proposed alerts against the run's own baseline with a defined action, including a leading indicator for the NaN.
  • Turned the ladder into a preflight and compared its cost with the cost of an unnoticed failure on a cluster.

Key takeaways

  • Write down what healthy looks like before reading a log: the initial loss should be about ln V, and a loss stuck at the entropy of the letter frequencies means the model ignores its input.
  • Debug by elimination, cheapest and most common first: data, then initial loss, then update-to-weight ratio, then one-batch memorisation, then numerics. Each check clears a family of causes.
  • A flat loss has many causes with different fingerprints: shuffled labels leave healthy gradients, zero weights leave a zero gradient, a tiny learning rate leaves a tiny update ratio.
  • Plot a held-out loss on clean data beside the training loss; it separates a hard batch from a damaged model.
  • To separate data from settings, replay from a checkpoint changing one thing. Removing the cause removes the spike; clipping, a lower learning rate and a lower β2 only soften it, and a clip that engages on most steps is a symptom.
  • The first non-finite value is usually in the gradient, a step before the loss. A loss scaler must skip the step and back off on an infinity, or bf16 avoids the need.
  • Turn each lesson into a preflight check and an alert against the run's own baseline: minutes on one node against hours on a cluster.

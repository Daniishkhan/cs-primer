Lab 5: Event Sourcing & CQRS

In chapter 16 the database stopped being a table of current values and became a list of things that happened. The balance of an account is not stored anywhere; it is whatever you get by replaying the account's history. In this lab you will build that machine for bank accounts: an append-only event store that refuses stale writers, an aggregate that is rebuilt from its events and guards its own rules, a read side that is fed from the log and can be thrown away and rebuilt, snapshots so loading stays fast, a time machine for "what was the balance last Tuesday?", and, optionally, a way to read old events written in a shape you no longer use.

Why this lab matters

Event sourcing is easy to explain in a sentence and surprisingly easy to get wrong in code. The mistakes are never in the happy path. They are in the corners: two writers who both decided on the same old state, a read model that applies one event twice after a crash, a snapshot that quietly disagrees with the log, an event written two years ago that no longer matches the code. Building each piece yourself shows you where the real costs of the pattern are, so that when someone proposes it in a design review you can say where it earns its keep and where it is a tax. It is also the same machinery as the logs and consumers of the data course, seen from the application side.

Real databases, no servers, no flakiness

The event store is a real sqlite3 database in a temporary file, so constraints, transactions and locking behave for real. Everything else is pure Python. The checks use a fake clock for recorded_at, seeded random numbers for histories, and a two-thread race whose outcome (exactly one winner) does not depend on which thread is faster. Nothing needs the network or a port. Python 3.8 or newer, standard library only, about a second to run. All money is whole cents held in integers, never floats.

What you'll build

Six milestones, each building on the last (the sixth is optional):

  1. The event store: a sqlite table of events, append with an expected_version, and a ConcurrencyError for stale writers. The check races two threads.
  2. Aggregates: Account.load folds events into state; commands (open, deposit, withdraw) enforce the invariants and return events.
  3. Projections: a projector that keeps account_balances and a large-transactions view, remembers its position, survives replays and can rebuild from zero.
  4. Snapshots: save folded state every N events and load from snapshot plus tail. Same answer, far fewer events read.
  5. Temporal queries: the balance as of a time or a version.
  6. Upcasting (optional): read an old Deposited event (a decimal string) as the current shape (integer cents) without rewriting history.

Milestone 1: an event store that refuses stale writers

An event is a fact in the past tense: AccountOpened, Deposited, Withdrawn. In an event-sourced system these facts are the database. They are only ever appended, never updated or deleted, and each one belongs to a stream (here: one stream per account) where it has a version, 1, 2, 3 and so on. The store also numbers every event in one global sequence (seq), which is the order the read side will consume them in.

seq | stream_id | version | type          | data                          | recorded_at
----+-----------+---------+---------------+-------------------------------+------------
  1 | acc-1     |       1 | AccountOpened | {"owner": "ada"}              | 100.0
  2 | acc-1     |       2 | Deposited     | {"amount_cents": 5000, "v": 2}| 110.0
  3 | acc-1     |       3 | Withdrawn     | {"amount_cents": 1200}        | 120.0

The interesting operation is append(stream_id, expected_version, events). A client loaded the account at version 3, checked its rules against that state and now wants to add event 4. If somebody else added a version 4 in the meantime, the client's decision was made on stale facts, so the store must refuse. This is optimistic concurrency: nobody takes a lock while thinking; the check happens at the moment of writing, exactly like the compare-and-swap you met in the lost-update discussion. The client reacts by reloading, deciding again and retrying.

Analogy: the paper ledger

An accountant's ledger has numbered lines in ink. You never rub out a line; you add a correcting line below. If two clerks each look at "line 41 is the last one" and both try to write line 42, the second one finds the line already taken and has to look again. The UNIQUE constraint is the printed line number: two clerks cannot both own line 42.

Where it breaks down: a ledger line is on one desk. A real event store has to stop the two clerks even when they sit in different offices, which is why the final guard must live in the database, not in the clerk's own habits.

Two defences work together. First, the code checks the current version inside a write transaction and raises ConcurrencyError with a friendly message. Second, the table has UNIQUE (stream_id, version), so even a bug in the check, or a second process you forgot about, cannot create two events with the same version: the database itself says no, and you translate its IntegrityError into the same ConcurrencyError. Appending several events at once is all or nothing.

Your task

Implement EventStore._init_schema, append, read_stream and read_all. The columns are seq (an autoincrementing primary key), stream_id, version, type, data (JSON text) and recorded_at, plus the UNIQUE constraint. Time comes from self.clock(), never from time.time() directly, so tests can fake it.

In every round exactly one wins and one gets ConcurrencyError.

Hints try without first
  • INTEGER PRIMARY KEY AUTOINCREMENT gives you seq for free, and cursor.lastrowid after an INSERT tells you which one an event got.
  • Start the write with BEGIN IMMEDIATE. That takes sqlite's write lock before you read the current version, so a competing writer waits instead of reading the same version and failing halfway through. Without it, the race check may report database is locked.
  • "The stream's current version" is SELECT COALESCE(MAX(version), 0) FROM events WHERE stream_id = ?. A new stream is at version 0, which is why creating one means expected_version=0.
  • Wrap the body so that any exception, including your own ConcurrencyError, runs ROLLBACK before propagating. Then an append of three events that fails leaves zero behind.
  • Catch sqlite3.IntegrityError separately and re-raise as ConcurrencyError: it is the UNIQUE constraint telling you that someone won a race your check could not see.
  • Store json.dumps(data) and return events with data as the original dict. json.loads happens in the given _event helper.
  • read_stream must add the number of rows it returns to self.events_read. Milestone 4 uses that counter to prove snapshots help.

def _init_schema(self):
    self.conn.execute("""
        CREATE TABLE IF NOT EXISTS events (
            seq         INTEGER PRIMARY KEY AUTOINCREMENT,   -- global order of the whole log
            stream_id   TEXT    NOT NULL,
            version     INTEGER NOT NULL,                    -- 1, 2, 3 ... within one stream
            type        TEXT    NOT NULL,
            data        TEXT    NOT NULL,                    -- JSON
            recorded_at REAL    NOT NULL,
            UNIQUE (stream_id, version)                      -- the last line of defence
        )""")

def append(self, stream_id, expected_version, events):
    """Append [(type, data), ...] to a stream, but only if the stream is still at
    `expected_version` (0 for a stream that does not exist yet).
    Returns the stored Events. Raises ConcurrencyError if someone got there first;
    in that case nothing at all is written."""
    now = self.clock()
    try:
        self.conn.execute("BEGIN IMMEDIATE")        # take the write lock before looking
        try:
            row = self.conn.execute(
                "SELECT COALESCE(MAX(version), 0) FROM events WHERE stream_id = ?", (stream_id,)).fetchone()
            if row[0] != expected_version:
                raise ConcurrencyError("stream %r is at version %d, you expected %d"
                                       % (stream_id, row[0], expected_version))
            stored = []
            for i, (etype, data) in enumerate(events, start=1):
                version = expected_version + i
                cur = self.conn.execute(
                    "INSERT INTO events (stream_id, version, type, data, recorded_at) VALUES (?,?,?,?,?)",
                    (stream_id, version, etype, json.dumps(data, sort_keys=True), now))
                stored.append(Event(cur.lastrowid, stream_id, version, etype, data, now))
            self.conn.execute("COMMIT")
            return stored
        except BaseException:
            self.conn.execute("ROLLBACK")
            raise
    except sqlite3.IntegrityError as e:             # the UNIQUE constraint caught a race we did not see
        raise ConcurrencyError("version already taken: %s" % e)

The two readers are plain queries:

def read_stream(self, stream_id, after_version=0):
    """The events of one stream with version > after_version, oldest first."""
    rows = self.conn.execute(
        "SELECT seq, stream_id, version, type, data, recorded_at FROM events "
        "WHERE stream_id = ? AND version > ? ORDER BY version", (stream_id, after_version)).fetchall()
    self.events_read += len(rows)
    return [self._event(r) for r in rows]

def read_all(self, after_seq=0, limit=None):
    """The global log: events with seq > after_seq, in seq order, at most `limit` of them."""
    sql = ("SELECT seq, stream_id, version, type, data, recorded_at FROM events "
           "WHERE seq > ? ORDER BY seq")
    args = [after_seq]
    if limit is not None:
        sql += " LIMIT ?"
        args.append(limit)
    return [self._event(r) for r in self.conn.execute(sql, args).fetchall()]

Milestone 2: the aggregate, rebuilt from events

The aggregate is the object that owns a consistency rule. Here it is Account, and its rules are: an account must be opened before anything else happens to it, you cannot open it twice, amounts are positive, and the balance may never go below zero. In an event-sourced system the aggregate has no table. Its state is a fold (a left-to-right reduce) over its events:

state = Account(id)                  # empty: version 0, not opened, balance 0
for event in store.read_stream(id):
    state.apply(event)               # AccountOpened -> opened; Deposited -> balance += n; ...

Two jobs, kept strictly apart:

  • apply(event) records what happened. It never validates and never raises for business reasons. Events are facts; if you replay a Withdrawn from last year, you do not ask whether it was allowed, it already happened. (This is also why apply must be deterministic and free of side effects: no clock, no database, no email. Replay it a million times and it must give the same answer.)
  • Commands decide. deposit(cents) and withdraw(cents) check the rules against the current folded state and, if allowed, return a list of new events. They do not change the aggregate. The caller appends the events; the next load applies them.

The glue is execute(store, id, decide), which is given to you: load, decide, append with expected_version = acct.version, and if the append raises ConcurrencyError, reload and decide again. This loop is where the invariant survives concurrency. Two clients can both see a balance of 100 and both decide to withdraw 80. Only one append can win; the loser reloads, sees 20 and now its command is refused. Without the version check you would have an overdraft that no unit test of withdraw could ever find.

Commands can be refused. Events cannot.

A Withdrawn event means the money left. A refused withdrawal produces no event at all (or, if the business wants a record of the attempt, a different event such as WithdrawalRejected; that is a design choice you could make). Mixing the two up, validating inside apply, is the most common beginner bug: it makes old events unreplayable the day a rule changes.

Raise AlreadyOpen, AccountNotOpen, InvalidAmount or InsufficientFunds; all are subclasses of DomainError. New Deposited events carry {"v": 2, "amount_cents": n}; the "v" will matter in milestone 6.

Hints try without first

  • Commands read self.balance and self.opened but never assign to them. If your command tests pass but the check complains that commands mutate state, look for a stray self.balance -=.

  • isinstance(True, int) is true in Python. If you care that deposit(True) is refused, test type(cents) is int. The check only tries 0 and negatives.
  • Withdrawing exactly the balance is allowed (cents > self.balance is the overdraft test, not >=).

def apply(self, ev):
    """Fold one event into the state. Never validates: events are facts."""
    if ev.type == "AccountOpened":
        self.opened = True
        self.owner = ev.data["owner"]
    elif ev.type == "Deposited":
        self.balance += ev.data["amount_cents"]
    elif ev.type == "Withdrawn":
        self.balance -= ev.data["amount_cents"]
    self.version = ev.version

@classmethod
def load(cls, store, account_id):
    acct = cls(account_id)
    for ev in store.read_stream(account_id):
        acct.apply(ev)
    return acct

def open(self, owner):
    if self.opened:
        raise AlreadyOpen("account %s is already open" % self.id)
    return [("AccountOpened", {"owner": owner})]

def deposit(self, cents):
    self._need_open()
    self._need_positive(cents)
    return [("Deposited", {"v": 2, "amount_cents": cents})]

def withdraw(self, cents):
    self._need_open()
    self._need_positive(cents)
    if cents > self.balance:
        raise InsufficientFunds("balance %d, tried to withdraw %d" % (self.balance, cents))
    return [("Withdrawn", {"amount_cents": cents})]

def _need_open(self):
    if not self.opened:
        raise AccountNotOpen("account %s is not open" % self.id)

@staticmethod
def _need_positive(cents):
    if not isinstance(cents, int) or cents <= 0:
        raise InvalidAmount("amount must be a positive whole number of cents, got %r" % (cents,))

and the given execute, the loop that turns a conflict into a retry:

def execute(store, account_id, decide, snapshots=None, snapshot_every=None, retries=3):
    """Load the account, let `decide(account)` return new events, append them with
    optimistic concurrency. On ConcurrencyError, reload and decide again. (Given.)"""
    for attempt in range(retries):
        acct = load_account(store, account_id, snapshots)
        before = acct.version
        new = decide(acct)                       # may raise DomainError: nothing is written
        try:
            stored = store.append(account_id, acct.version, new)
        except ConcurrencyError:
            if attempt == retries - 1:
                raise
            continue
        for ev in stored:
            acct.apply(ev)
        if snapshots is not None and snapshot_every and acct.version // snapshot_every > before // snapshot_every:
            snapshots.save(acct)
        return stored

Milestone 3: projections, the read side

Replaying an account's events is perfect for deciding a command, and hopeless for questions like "which accounts have more than $10,000?" or "show every transaction over $1,000 this week". Those questions cross streams. The CQRS answer is a second model, built for reading: tables shaped like the queries, fed by a projector that follows the global log. (The chapter calls this the read model; the data course calls the same idea a derived view.)

Your projector maintains two tables:

  • account_balances(account_id, owner, balance_cents, last_seq)
  • large_transactions(seq, account_id, kind, amount_cents), one row per deposit or withdrawal of LARGE_CENTS (100,000 cents, $1,000) or more.

It also remembers its position, the seq of the last event it has handled, in a third table. That single number is what makes everything else work: restart the projector and it resumes; add events and it handles only the new ones; it can fall behind and catch up. It is the same idea as a Kafka consumer's offset.

Idempotence: replays must be harmless

You can make the table updates and the position update commit together in one transaction, and you should. But systems still re-deliver events (a bug, a restore from backup, the projector was pointed at an older position by an operator). Networking taught you that at-least-once delivery is the realistic guarantee, so the consumer must make duplicates harmless. Two techniques are used here:

  • large_transactions uses the event's seq as its primary key, and inserts with INSERT OR IGNORE: the same event cannot appear twice.
  • account_balances stores last_seq, the seq of the last event applied to that row, and updates only WHERE last_seq < event.seq. An old event finds the row already past it and does nothing. (Adding a deposit twice is not idempotent by itself; guarding it with a sequence number is.)

The same property gives you rebuild for free: delete the tables, set the position to 0 and replay. The result must be identical, which is the proof that the read model is only a cache of the log. That is also how you ship a new view next quarter, or fix a bug in a projection: change the code, rebuild.

Your task

Implement Projector._init_schema, position, catch_up, _apply, rebuild and the three queries. catch_up(limit=None, from_seq=None) reads events after the saved position (or after from_seq if given, to force a re-delivery), applies them, saves the new position and returns how many events it handled. The position must never move backwards, even on a re-delivery. The projector has its own sqlite database (in memory by default), separate from the event store, because in a real system they would live in different places.

python3 check.py shows milestone 3 as ✔. The check generates a seeded history of about 245 events over four accounts and verifies against balances it computes independently of your code. Then: before catch_up the read model is empty; after it, balances and the list of large transactions match; a new event is invisible until the next catch_up; catch_up(from_seq=0) (full re-delivery) and from_seq=100 change nothing; catching up in batches of 7 reaches the same tables as one big call; and rebuild() gives exactly the same read model as the incremental one.

Hints try without first
  • Do the batch in one transaction: BEGIN, apply every event, write the new position, COMMIT. If anything raises, ROLLBACK. Then a crash leaves either all of it or none of it.
  • For AccountOpened, INSERT ... ON CONFLICT(account_id) DO UPDATE ... WHERE excluded.last_seq > account_balances.last_seq is an upsert that ignores older events. If your sqlite is too old for that, do a SELECT first.
  • For deposits and withdrawals, the whole idempotence trick is UPDATE ... SET balance_cents = balance_cents + ?, last_seq = ? WHERE account_id = ? AND last_seq < ?.
  • The new position is max(self.position(), events[-1].seq). If the check says your position went backwards after from_seq=100, that is the line.
  • Remember LARGE_CENTS is a module constant: use it by name, so the "change the threshold and rebuild" experiment works.
  • rebuild should empty all three tables and then loop catch_up(limit=500) until it returns 0.

def catch_up(self, limit=None, from_seq=None):
    """Apply events the projector has not seen yet and move its position. Returns how many
    events were handled. `from_seq` forces re-delivery from that position (to simulate a
    crash between updating the tables and saving the position); the position never moves back."""
    start = self.position() if from_seq is None else from_seq
    events = self.store.read_all(after_seq=start, limit=limit)
    if not events:
        return 0
    self.db.execute("BEGIN")                            # tables and position move together
    try:
        for ev in events:
            self._apply(ev)
        new_pos = max(self.position(), events[-1].seq)
        self.db.execute("INSERT OR REPLACE INTO projector_position (name, last_seq) VALUES (?,?)",
                        (self.NAME, new_pos))
        self.db.execute("COMMIT")
    except BaseException:
        self.db.execute("ROLLBACK")
        raise
    return len(events)

def _apply(self, ev):
    if ev.type == "AccountOpened":
        # idempotent: a replay finds the row already at (or past) this seq and changes nothing
        self.db.execute(
            "INSERT INTO account_balances (account_id, owner, balance_cents, last_seq) VALUES (?,?,0,?) "
            "ON CONFLICT(account_id) DO UPDATE SET owner = excluded.owner, last_seq = excluded.last_seq "
            "WHERE excluded.last_seq > account_balances.last_seq",
            (ev.stream_id, ev.data["owner"], ev.seq))
    elif ev.type in ("Deposited", "Withdrawn"):
        cents = ev.data["amount_cents"]
        delta = cents if ev.type == "Deposited" else -cents
        # the WHERE last_seq < ? guard is what makes a re-delivered event harmless
        self.db.execute(
            "UPDATE account_balances SET balance_cents = balance_cents + ?, last_seq = ? "
            "WHERE account_id = ? AND last_seq < ?", (delta, ev.seq, ev.stream_id, ev.seq))
        if cents >= LARGE_CENTS:
            self.db.execute(
                "INSERT OR IGNORE INTO large_transactions (seq, account_id, kind, amount_cents) VALUES (?,?,?,?)",
                (ev.seq, ev.stream_id, ev.type, cents))

def rebuild(self):
    """Throw the read model away and recompute it from event number one."""
    self.db.execute("BEGIN")
    self.db.execute("DELETE FROM account_balances")
    self.db.execute("DELETE FROM large_transactions")
    self.db.execute("DELETE FROM projector_position")
    self.db.execute("COMMIT")
    total = 0
    while True:
        n = self.catch_up(limit=500)
        if n == 0:
            return total
        total += n

Milestone 4: snapshots

Replaying 12 events to load an account is nothing. Replaying 12 million is a problem, and a busy account or a long-lived stream gets there. A snapshot is the folded state saved at some version. To load, take the newest snapshot, then apply only the events after it. The rule that keeps this honest:

A snapshot is a cache, never the truth

You must be able to delete every snapshot and get exactly the same state by replaying from event 1. If that is ever false, you have a bug (or you changed apply without invalidating the snapshots). Snapshots buy speed; they never decide correctness.

When to take one? A simple policy is "every N events": after appending, if the stream crossed a multiple of N, save a snapshot. The given execute does that. Snapshots need the aggregate's state as plain JSON (to_state and from_state), and a place to keep them (here: a snapshots table in the same sqlite file, one row per stream, the latest only). Real systems also store a schema version inside the snapshot, so that a code change throws old snapshots away instead of loading them wrongly.

Your task

Implement Account.to_state / from_state, SnapshotStore (__init__ creates the table, save, latest, clear) and extend load_account so that, given a SnapshotStore, it starts from the latest snapshot and reads only the tail with store.read_stream(id, after_version=snapshot_version).

  • In load_account: if there is no snapshot, fall back to a plain Account.load. The check deletes the snapshots and expects that to work.

def to_state(self):
    return {"version": self.version, "opened": self.opened, "owner": self.owner, "balance": self.balance}

@classmethod
def from_state(cls, account_id, state):
    acct = cls(account_id)
    acct.version = state["version"]
    acct.opened = state["opened"]
    acct.owner = state["owner"]
    acct.balance = state["balance"]
    return acct

def save(self, account):
    self.store.conn.execute(
        "INSERT OR REPLACE INTO snapshots (stream_id, version, state) VALUES (?,?,?)",
        (account.id, account.version, json.dumps(account.to_state(), sort_keys=True)))

def latest(self, stream_id):
    """(version, state_dict) of the newest snapshot, or None."""
    row = self.store.conn.execute(
        "SELECT version, state FROM snapshots WHERE stream_id = ?", (stream_id,)).fetchone()
    return (row[0], json.loads(row[1])) if row else None

def load_account(store, account_id, snapshots=None):
    """Milestone 2: full replay. Milestone 4: start from the latest snapshot if there is one."""
    if snapshots is not None:
        snap = snapshots.latest(account_id)
        if snap is not None:
            version, state = snap
            acct = Account.from_state(account_id, state)
            for ev in store.read_stream(account_id, after_version=version):
                acct.apply(ev)
            return acct
    return Account.load(store, account_id)

Milestone 5: temporal queries

An ordinary database answers "what is the balance?" and the past is gone unless somebody built an audit table. An event log is the audit table, and the past is just a shorter fold. "What was the balance at 14:00 yesterday?" is "fold the events recorded at or before 14:00". "What did the account look like after its 4th event?" is "fold the first 4". Auditors, regulators, debugging ("how did we get into this state?") and customer disputes all ask exactly these questions, and for most systems that keep only current state they are impossible to answer reliably.

Be precise about which time you mean. recorded_at is when the system learned the fact, which is what the store knows. When the fact happened in the real world (a card swiped Monday, reported Wednesday) is a second timestamp, and asking "what did we believe on Tuesday about Monday?" needs both; that is called bitemporal modelling and is a stretch goal below.

Your task

Implement account_as_of(store, account_id, version=None, at=None), returning an Account folded from only the qualifying events: those with version <= the given version and recorded_at <= the given time (inclusive). With neither argument it is the current state; with both, both limits apply. Also implement balance_history, which returns (version, recorded_at, balance_after) for every event in a single pass.

Solution spoiler 
def account_as_of(store, account_id, version=None, at=None):
    """The account as it was after event `version` and/or at time `at` (inclusive).
    With neither, the current state."""
    acct = Account(account_id)
    for ev in store.read_stream(account_id):
        if version is not None and ev.version > version:
            break
        if at is not None and ev.recorded_at > at:
            break
        acct.apply(ev)
    return acct

def balance_history(store, account_id):
    """[(version, recorded_at, balance_after)] for every event of the account, in one pass."""
    acct = Account(account_id)
    out = []
    for ev in store.read_stream(account_id):
        acct.apply(ev)
        out.append((ev.version, ev.recorded_at, acct.balance))
    return out

Milestone 6 (optional): upcasting

Events are immutable, and they live forever. Code does not. A year after launch, the team decides money should be integer cents instead of a decimal string. The old Deposited events, written as {"amount": "12.50"}, are still in the log and can never be edited: they are history, and other systems may already have consumed them. This is the schema-evolution problem from chapter 10, with one extra twist: here the old data is your own database and every reader meets all the versions at once.

The standard answer is an upcaster: a pure function applied at read time that turns an old event shape into the current one, in memory, before any code that cares sees it. apply, the projector and the temporal queries only ever deal with the newest shape. Your store already calls upcast on every event it reads. New events are tagged "v": 2 from milestone 2 on; an old one has no "v", which means version 1.

Deposited v1   {"amount": "12.50"}                  # decimal dollars as a string
Deposited v2   {"v": 2, "amount_cents": 1250}       # integer cents

Why not just use float?

Because float("19.99") * 100 is 1998.9999999999998 in Python, and int() of that is 1998: you lose a cent. Money converted through floating point is a classic source of off-by-one-cent bugs that appear only on some amounts. Use decimal.Decimal for the conversion, or at least round(). The check includes 19.99 and 0.29 to catch this.

Your task

Implement upcast(ev). It receives an Event and returns an Event: a Deposited with no "v" (or "v": 1) is converted to the v2 shape; everything else is returned unchanged. Do not modify the argument (ev._replace(data=...) builds a modified copy of a namedtuple), and do not write anything back to the database.

It upcasts several amounts including 19.99, checks that other events pass through untouched, then appends raw v1 events to a stream and verifies that Account.load, a fresh Projector and account_as_of all see the right cents, while the row in the database still holds the original v1 JSON.

  • Copy the dict (dict(ev.data)), remove "amount", add "v": 2 and "amount_cents". Never mutate ev.data: the check compares it before and after.
  • If milestones 1 to 5 are green but this one reports a wrong balance, make sure nothing in your code reads ev.data["amount"] directly: only upcast should know the old shape.
Solution spoiler 
def upcast(ev):
    """Upgrade old event shapes to the current one, in memory, when they are read.
    Deposited v1: {"amount": "12.50"}  (a decimal string in dollars)
    Deposited v2: {"v": 2, "amount_cents": 1250}
    The stored row is never touched."""
    if ev.type == "Deposited" and ev.data.get("v", 1) == 1:
        cents = int((Decimal(ev.data["amount"]) * 100).to_integral_value())    # Decimal: no 19.99 -> 1998 surprise
        data = {k: v for k, v in ev.data.items() if k != "amount"}
        data.update({"v": 2, "amount_cents": cents})
        return ev._replace(data=data)
    return ev

  • Multi-event commands and idempotency keys: a transfer touches two accounts, which are two streams, so no single append can cover both. Sketch what you would do (a process manager, or the saga of chapter 15), and add a command_id so that retrying a command that already succeeded appends nothing.

Distributed systems connection

You built a log, and a log is the oldest trick in distributed systems. expected_version is a compare-and-swap on a single register per stream, the same primitive that replicated systems use to avoid two leaders accepting conflicting writes. Your projector's position is a consumer offset, and its idempotent handlers are the consumer half of at-least-once delivery. The global seq is cheap here because one sqlite file orders everything; once the log is split over many machines, a single total order stops being free (clocks and ordering) and you get ordering per stream or per partition only, which is why event-sourced designs make the aggregate the unit of consistency. And the gap between the write and the moment the projector catches up is eventual consistency showing up in your user interface: a customer deposits money and the balance page, read from the projection, may still show the old number for a moment.

What you learned

  • An event store is an append-only table with a per-stream version. expected_version turns "someone else wrote first" into an error you can handle by reloading, and a UNIQUE constraint is the last line of defence when the check is not enough.
  • An aggregate's state is a fold over its events. apply records facts and never validates; commands validate and return events. Business invariants such as "no overdraft" survive concurrency because of the version check, not because of locks.
  • CQRS splits deciding from answering. Read models are built by a projector that follows the log from a saved position, and their handlers must be idempotent because delivery is at least once.
  • A read model is a cache of the log: you can drop it and rebuild it, or build a new one that answers a question nobody asked when the events were written.
  • Snapshots make loading fast but are never the truth: snapshot plus tail must equal a full replay, and deleting all snapshots must be safe.
  • The log gives you time travel for free: any past state is a shorter fold, if you are clear about which timestamp you mean.
  • Old events are never rewritten. Upcasters translate old shapes at read time, so only the newest shape exists in your code. The costs of event sourcing (versioning, replay time, eventual consistency, harder ad-hoc queries) are real, and are the reason many experienced engineers reserve it for domains where history itself is the product.

Check your understanding

Two clients load an account at version 7 with a balance of 100. Each decides to withdraw 80 and calls append("acc", 7, [Withdrawn 80]). What happens, and what does the loser do?

  1. Both succeed, and the balance becomes -60, which is why aggregates need locks
  2. The second one is queued by the store until the first finishes, then also succeeds
  3. The second raises ConcurrencyError; it reloads (balance 20, version 8), decides again, and this time its own command is refused with InsufficientFunds
  4. The second one silently overwrites event 8 with its own
The store accepts a write only if the stream is still at the version the writer saw. The loser's decision was based on stale state, so it must start over from the new state, and the business rule is applied to the fresh facts. No lock was held while either client was thinking.

A projector crashes after updating account_balances but before saving its position, then restarts and re-reads the last 50 events. Why is the read model still correct?

  1. Because the event store removes events once they have been delivered
  2. Because each handler is idempotent: it only applies an event whose seq is newer than the row's last_seq (and large transactions are keyed by seq), so the re-delivered events change nothing
  3. Because sqlite automatically undoes the changes after a crash
  4. It is not correct: the balances are now doubled and must be rebuilt by hand
At-least-once delivery is the realistic guarantee, so the consumer makes duplicates harmless. Putting the table updates and the position in one transaction narrows the window; idempotent handlers close it. Rebuild is the backstop.

You delete all snapshots in production. What should happen?

  1. Accounts can no longer be loaded until the snapshots are restored from backup
  2. Balances reset to zero and have to be re-entered
  3. Nothing changes, because snapshots are only used by the read side
  4. Nothing is lost: loads fall back to replaying the stream from event 1, just slower, and new snapshots appear over time
A snapshot is a cache of the fold, used by the write side to shorten loads. The events are the source of truth, so deleting snapshots costs time, never data. If it could cost data, the design is wrong.

Three years ago a Deposited event was stored as {"amount": "19.99"}; today the code expects {"amount_cents": 1999}. What is the standard fix, and why not rewrite the old rows?

  1. An upcaster that converts old shapes to the current one when events are read. Events are immutable history, other consumers may have seen them, and a rewrite is risky and cannot be undone
  2. Run an UPDATE over the whole table at deploy time. The log can be edited whenever the schema changes
  3. Keep both shapes in apply forever, with an if for every version in every consumer
  4. Delete the old events and recompute balances from the read model
Upcasting keeps one translation in one place, so every reader (aggregate, projector, temporal query) sees only the newest shape. Editing the log destroys the property that makes event sourcing valuable: that history is a trustworthy record of what was written.

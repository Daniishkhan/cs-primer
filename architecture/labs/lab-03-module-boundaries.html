Lab 3: Enforce Module Boundaries

Every team that says "we have a modular monolith" is making a promise that nothing checks. In chapter 2 you met coupling and information hiding, and in chapter 11 and chapter 12 you saw why the cheap way to get good boundaries is to draw them inside one process before you draw them across a network. In this lab you will build the tool that keeps the promise: an import-graph extractor, a rules checker that reports violations as file:line, a cycle finder, and then you will use all three to take a tangled little shop apart and put it back together with clean public interfaces.

Why this lab matters

A boundary that only exists in a diagram erodes. Someone needs a price in a hurry, imports a private helper from the catalog, and the diagram is now a lie. Do that a few hundred times and the "modules" can no longer be changed, tested or split out alone. The fix experienced teams reach for is mechanical: write the rules down, have a tool read the code, and fail the build when a rule breaks. The tool you will write is small, because Python gives you the parser for free (ast), but it is the same idea that sits behind import-linter style contracts in Python, dependency-cruiser in JavaScript and ArchUnit in Java. And because you will also have to fix every violation it finds, you will feel why each rule exists.

No frameworks, nothing to install

The "shop" is plain Python modules and the tools are the standard library only. Nothing opens a port or touches the network; everything runs in about a second and gives the same answer every time. Python 3.8 or newer.

What you'll build

The shop has five modules. The code works, and a test suite proves it, but the modules reach into each other's private functions, into each other's tables (they all share one dict called db), and into each other in circles. The picture below is what your tool will discover.

Five milestones, each building on the last (the fifth is optional):

  1. The import graph: read every .py file with ast, resolve absolute and relative imports, and print which module depends on which.
  2. Boundary rules: a rules file (allowed dependencies, "public api only", no shared state) and a checker that reports violations as file:line. It must find the known violations of the given monolith, exactly.
  3. Cycles: find every dependency cycle between modules.
  4. Refactor: in starter/shop, add an api.py to every module, route all calls through it, break the cycles, and give each module its own data. The behaviour tests must still pass and your checker must report nothing.
  5. A fitness function (optional): turn the checker into a unittest that a CI server would run on every change.

Now open monolith/shop/payments/service.py. Its job is to charge a wallet, and it does that, but notice how:

def charge(order_id):
    order = ordering.get_order(order_id)
    amount = order["total"] + order["shipping"]
    if balance_of(order["user"]) < amount:
        raise InsufficientFunds(order["user"])
    _shared.db["wallets"][order["user"]] -= amount
    payment_id = _shared.next_id("payment")
    _shared.db["payments"][payment_id] = {"order": order_id, "amount": amount}
    _shared.db["orders"][order_id]["status"] = "PAID"      # writes into the ordering table
    return payment_id

Three things are wrong with that function, and they are the three things your rules will name. Payments imports ordering's internals to look up the order (a dependency it should not have, through a door that is not a public one). It reaches into a shared dict (shared state). And the last line of charge writes into another module's table, changing an order's status from the outside: no import checker can see that line, but fixing the imports will force you to deal with it. Meanwhile ordering imports payments to call charge, so the two modules now need each other. Change either and you must understand both.

Milestone 1: the import graph

Chapter 2 said that the dependencies between modules are the architecture, and that you can read them off the code. Python makes this easy: ast.parse(source) turns a file into a tree without running it, and ast.walk(tree) visits every node, including imports hidden inside functions. There are two kinds of import node:

  • ast.Import: import shop.catalog.api (a list of dotted names);
  • ast.ImportFrom: from shop.catalog import api, with a module (here "shop.catalog"), a list of names, and a level that counts the leading dots of a relative import.

Two details make this more interesting than it looks:

  1. Relative imports. In shop/payments/service.py, from ..ordering import service means "go up one package from shop.payments to shop, then into ordering": level 2 climbs level - 1 = 1 package. A bare from . import helper has module = None.
  2. What is being imported? In from shop.catalog import api, api is a module, so the real target is shop.catalog.api. In from shop.catalog.service import weight_of, weight_of is a function, so the target is just shop.catalog.service. The syntax cannot tell you which; the file system can: if shop/catalog/api.py (or a package folder) exists, the name is a module.

Modules versus files

In this lab a module means the second part of the dotted name: everything under shop/payments/ belongs to the module payments. Imports inside one module (payments.api importing payments.service) are internal business and are not edges of the graph. shop/app.py is the module app and shop/db.py is the module db.

def _exists(root, dotted):
    """Is there a module or package called `dotted` under root?"""
    path = os.path.join(root, *dotted.split("."))
    return os.path.isfile(path + ".py") or os.path.isfile(os.path.join(path, "__init__.py"))
def _resolve(root, node, pkg_parts):
    """All the dotted names one import statement refers to (relative imports resolved)."""
    if isinstance(node, ast.Import):
        return [alias.name for alias in node.names]
    if node.level:                                  # from ..x import y: climb level-1 packages
        base = pkg_parts[:len(pkg_parts) - (node.level - 1)]
        if node.module:
            base = base + node.module.split(".")
    else:
        base = node.module.split(".")
    base = ".".join(base)
    out = []
    for alias in node.names:
        sub = base + "." + alias.name
        out.append(sub if _exists(root, sub) else base)   # 'from shop.catalog import api' names a module
    return out
def extract_imports(root):
    """Every import inside root/shop as Import(file, line, importer, target)."""
    found = set()                                 # a set: 'from x import a, b' is one import line
    pkg_dir = os.path.join(root, PACKAGE)
    for folder, dirs, files in os.walk(pkg_dir):
        dirs.sort()
        for name in sorted(files):
            if not name.endswith(".py"):
                continue
            path = os.path.join(folder, name)
            rel = os.path.relpath(path, root)
            parts = rel[:-3].split(os.sep)            # ['shop', 'payments', 'service']
            pkg_parts = parts[:-1]                    # the package the file lives in
            dotted = ".".join(pkg_parts if name == "__init__.py" else parts)
            importer = module_of(dotted)
            with open(path, encoding="utf-8") as f:
                tree = ast.parse(f.read(), path)
            for node in ast.walk(tree):               # ast.walk also finds imports inside functions
                if isinstance(node, (ast.Import, ast.ImportFrom)):
                    for target in _resolve(root, node, pkg_parts):
                        if target == PACKAGE or target.startswith(PACKAGE + "."):
                            found.add(Import(rel, node.lineno, importer, target))
    return sorted(found)
def module_graph(imports):
    """{module: set of other modules it imports}. Imports inside one module are dropped."""
    graph = {}
    for imp in imports:
        target = module_of(imp.target)
        if imp.importer and target and imp.importer != target:
            graph.setdefault(imp.importer, set()).add(target)
    return graph
def format_graph(graph):
    """One line per module that has dependencies: 'ordering -> cart, catalog'."""
    return "\n".join(f"{m} -> {', '.join(sorted(graph[m]))}" for m in sorted(graph) if graph[m])

Milestone 2: boundary rules

A rule is a statement a tool can check. Open rules.py:

MODULES = ["catalog", "cart", "ordering", "payments", "shipping"]

ALLOWED = {
    "catalog":  [],
    "cart":     ["catalog"],
    "ordering": ["catalog", "cart", "payments", "shipping"],
    "payments": [],
    "shipping": [],
    "app":      ["catalog", "cart", "ordering", "payments", "shipping"],
}

PUBLIC_API = "api"

Those few lines hold three rules, and each one is a sentence from the earlier chapters:

Rule namePlain EnglishWhy (chapter)
dependencyA module may depend only on the modules listed for it in ALLOWED.The dependency direction is a design decision, not an accident (chapter 2).
internalOther modules may import only shop.<module>.api, never its internals.Information hiding: the api is the interface, everything else is implementation you must be free to change.
sharedImporting something that is not a declared module (like shop.db) is forbidden for modules.Each service or module owns its data (chapter 12); a shared table is a hidden interface nobody can see.

One import line can break more than one rule. from shop.cart import service, written inside catalog, breaks dependency (catalog may not depend on cart at all) and internal (even if it could, service is not the api). Report both: the fix for each is different.

Common misconception

"A leading underscore makes it private." In Python it is only a hint to humans; the language will let any module import _apply_discount, and the monolith's ordering module does exactly that. api.py is also a convention, and it is only as strong as the tool that enforces it. Information hiding in Python is something you check, not something you get.

Solution spoiler 
def check_boundaries(imports, rules=default_rules):
    """Return a sorted list of Violation(file, line, rule, message)."""
    out = []
    for imp in imports:
        target = module_of(imp.target)
        if imp.importer not in rules.ALLOWED or target is None or target == imp.importer:
            continue
        if target not in rules.ALLOWED:
            out.append(Violation(imp.file, imp.line, "shared",
                                 f"{imp.importer} imports {imp.target}: not a declared module (shared state?)"))
            continue
        if target not in rules.ALLOWED[imp.importer]:
            out.append(Violation(imp.file, imp.line, "dependency",
                                 f"{imp.importer} may not depend on {target}"))
        if imp.target != f"{PACKAGE}.{target}.{rules.PUBLIC_API}":
            out.append(Violation(imp.file, imp.line, "internal",
                                 f"{imp.importer} imports {imp.target}: use {PACKAGE}.{target}.{rules.PUBLIC_API}"))
    return sorted(out)

Milestone 3: cycles

Chapter 2 lists "conjoined modules" among its warning signs: two modules you cannot understand one without the other. A cycle in the import graph is the mechanical form of that smell, and the graph above contains three of them. A dependency cycle means module A needs B and B needs A (possibly through others). The practical effect is that you can no longer understand, test, release or extract either one alone: they are one module wearing two names. When you later cut a monolith into services (chapter 12), a cycle becomes two services that must call each other, with all the failure modes of a network between them.

The rule ALLOWED can forbid some cycles outright, but cycles can also hide in perfectly legal-looking graphs, and a cycle finder is the safety net that does not depend on anybody having written the rules correctly. The tool you need is small. Reading the graph as "module -> modules it imports", a cycle is a path that returns to its start. The classic way to list all of them in a small graph is a depth-first search from each module, with one trick to stop it reporting the same cycle many times: only walk to modules that sort after the start, so every cycle is found exactly once, from its alphabetically smallest member.

Your task

Implement find_cycles(graph). It takes the {module: set of modules} dict from milestone 1 and returns every elementary cycle as a list of module names that starts at its smallest module and does not repeat it at the end, for example ['ordering', 'payments']. The list of cycles is sorted. A graph without cycles gives [].

python3 check.py shows milestone 3 as ✔. It tries an empty graph, a graph with no cycles, a three-module ring, two cycles sharing a module, three modules that all import each other (which has five elementary cycles), a module that appears only as a target, and finally the monolith, which has exactly three cycles.

Hints try without first
  • Write a nested helper walk(start, node, path). For each nxt in sorted(graph.get(node, ())): if nxt == start you have closed a cycle, so save list(path); elif nxt > start and nxt not in path, recurse with path + [nxt].
  • Use graph.get(node, ()), not graph[node]: a module that nobody imports from, like db, is not a key.
  • Call walk(start, start, [start]) for every start in sorted(graph) and return sorted(cycles).
  • Why "only bigger than start"? Without it the cycle a -> b -> a would also be found starting from b as ['b', 'a']. With it, every cycle is reported once, from its smallest member.
Solution spoiler 
def find_cycles(graph):
    """Every elementary cycle, each starting at its smallest module, the list sorted."""
    cycles = []

    def walk(start, node, path):
        for nxt in sorted(graph.get(node, ())):
            if nxt == start:
                cycles.append(list(path))
            elif nxt > start and nxt not in path:     # only visit bigger names: each cycle found once
                walk(start, nxt, path + [nxt])

    for start in sorted(graph):
        walk(start, start, [start])
    return sorted(cycles)

Is a cycle always a violation?

Not by the rules in this file: if ALLOWED let two modules depend on each other, neither would be a dependency violation, and only the cycle finder would object. That is on purpose. Rules say who is allowed to talk; the cycle check says that the graph must also be a hierarchy. Many teams enforce both, because a tangle that is technically allowed is still a tangle.

Milestone 4: refactor to public APIs

Now the part that earns the lab's name. In starter/shop/ (an exact copy of the monolith) you will make your own checker, and the check's reference checker, report zero violations and zero cycles while all eight behaviour tests keep passing. Before you touch anything, run python3 behaviour.py starter to see them pass, and run your tool on starter/ to see the 24 violations you have to remove. Then take the violations in this order. Each step turns some of them off.

  1. Add api.py to every module. It re-exports the functions and exceptions other modules may use. A good api.py is short: from .service import charge, set_balance, balance_of, InsufficientFunds plus an __all__. Everything else stays in service.py (or in underscore files) as implementation detail.
  2. Flip every import to the api. from shop.catalog import service as catalog becomes from shop.catalog import api as catalog. That removes most internal violations. The private _apply_discount that ordering imported needs a public home: give catalog an api function, such as line_price(sku, qty), that does the discount inside the catalog, which is where the pricing knowledge belongs anyway.
  3. Break the cycles by passing data instead of looking it up. Payments does not need the order; it needs a user and an amount. Make charge(order_ref, user, amount_cents) take them as arguments and let ordering mark its own order paid. Shipping does not need to read the order or the product table; ordering passes the total weight to shipping.quote(grams) and shipping.create_shipment(order_ref, address, grams). Information now flows one way: ordering knows about the others, and they know nothing about ordering.
  4. Invert the one dependency you cannot pass data for. Catalog refuses to remove a product that is in a cart, so it needs a question answered by cart. Catalog must not import cart (and cart already imports catalog). Give the catalog a hook, add_removal_guard(fn), and let the one place that is allowed to know everything, app.py, register cart.is_in_any_cart. This is "flip the arrow" from chapter 2's section on which way dependencies should point, in six lines: the catalog owns the question, someone else supplies the answer.
  5. Give every module its own data and delete shop/db.py. Replace db["carts"] with a dict private to the cart module, and so on. Remember that app.reset() used to clear the shared dict: each api gets a reset() and app.reset() calls them all. No import checker can see a shared table by its contents, only by the import that reaches it, which is why the rules treat shop.db as forbidden: once it is gone, sharing is physically impossible.

def place_order(user, address):
    lines = cart.items(user)
    if not lines:
        raise ValueError("empty cart")
    total = sum(catalog.line_price(sku, qty) for sku, qty in lines)
    grams = sum(catalog.weight_of(sku) * qty for sku, qty in lines)
    taken = []
    try:
        for sku, qty in lines:
            catalog.take_stock(sku, qty)
            taken.append((sku, qty))
    except catalog.OutOfStock:
        for sku, qty in taken:
            catalog.put_back(sku, qty)
        raise
    _next_id[0] += 1
    order_id = _next_id[0]
    shipping_cost = shipping.quote(grams)

                         "shipping": shipping_cost, "items": lines, "address": address}

    except payments.InsufficientFunds:

What an import checker cannot see

The tool reads imports. It does not see getattr(module, name), importlib.import_module(...), a module that reaches another's data through a file or a database table, or two modules agreeing on a magic string. That is exactly why milestone 4 deletes shop/db.py and does not merely forbid its import: a rule you can enforce by construction beats a rule you have to detect. In real systems the same gap exists when two services read the same database table: no import is involved at all.

Milestone 5 (optional): a fitness function

A rule that only runs when someone remembers to run it will be broken by Friday. Chapter 19 calls an automated check of an architectural property a fitness function, and says the simplest and most valuable is an import rule. You have already written one. The last step is to put it where CI will run it on every change: a unittest. A failing import rule should fail the build exactly like a failing behaviour test, with a message that says which line to fix.

Solution spoiler 
class BoundaryTests(unittest.TestCase):
    def setUp(self):
        self.imports = archtool.extract_imports(ROOT)

    def test_no_boundary_violations(self):
        violations = archtool.check_boundaries(self.imports)
        report = "\n".join(f"{v.file}:{v.line}: [{v.rule}] {v.message}" for v in violations)
        self.assertEqual([], violations, "\n" + report)

    def test_no_dependency_cycles(self):
        cycles = archtool.find_cycles(archtool.module_graph(self.imports))
        report = "\n".join(" -> ".join(c + [c[0]]) for c in cycles)
        self.assertEqual([], cycles, "\n" + report)

Look under the hood

The whole tool rests on one fact: a relative import is just a node with a number of dots. Ask the parser what it sees, without running anything:

$ python3 -c "
import ast
for line in ('from ..ordering import service', 'from . import helper', 'import shop.catalog.api as c'):
    n = ast.parse(line).body[0]
    print(type(n).__name__, getattr(n, 'level', '-'), getattr(n, 'module', '-'), [a.name for a in n.names])
"
ImportFrom 2 ordering ['service']
ImportFrom 1 None ['helper']
Import - - ['shop.catalog.api']

That is the whole mystery of relative imports: level says how many dots, and module is what follows them (or None). Your resolver turns "level 2 from shop.payments" into shop.

Stretch goals

  • A ratchet: real teams cannot fix 400 violations in a week. Save the current violations to a baseline file, fail the build only on new ones, and fail when the baseline contains a violation that has been fixed, so the list can only shrink.
  • Instability: for each module compute efferent coupling (Ce, how many modules it depends on) and afferent coupling (Ca, how many depend on it), and the ratio Ce / (Ca + Ce). Stable modules (low value) should not depend on unstable ones. Does your refactored shop obey that?
  • Layers: add a rule that modules are in layers (app over ordering over everything else) and that a module may only depend on a layer below it. Report an upward import with its own message.
  • Type-only imports: an import under if TYPE_CHECKING: costs nothing at run time but is still a coupling. Decide whether your tool should count it, and make that a rule option.
  • Dynamic imports: detect calls to importlib.import_module and __import__ with a literal string and treat them as imports.
  • Draw it: print the graph as Mermaid text (ordering --> payments), paste it into a Mermaid viewer, and colour the cycle edges.

Distributed systems connection

Everything you did here is the rehearsal for extracting services. A module with a narrow api and its own data store is the thing you can lift out and put behind a network call, and a module that shares tables or sits in a cycle cannot be. Cut the unrefactored monolith along its module lines and you get a distributed monolith (chapter 11): five services that must be deployed together, call each other in circles, and share one database. Notice also what the refactor made harder: when ordering charged a card and shipped a parcel inside one process and one dict, "all or nothing" was free. Now every module owns its own data, so a failure between payments.charge and shipping.create_shipment leaves things half done. The answer is the saga, and you build one in Lab 4.

What you learned

  • Imports are the visible part of coupling, and ast lets a tool read them without running code. Relative imports are resolved with the file's package and the level of the import; from pkg import name needs a file-system check to know whether name is a module.
  • Architecture rules become checkable once written as data: allowed dependencies, "public api only", and no shared state.
  • One import line can break several rules, and a violation report with file:line is a to-do list you can act on.
  • A cycle means two modules are really one. A depth-first search that only visits names after the start finds each elementary cycle once.
  • You break cycles by passing data instead of looking it up, and by inverting the dependency you cannot avoid (a hook registered by the composition root).
  • Giving every module its own data, and deleting the shared db, enforces a rule by construction, which no import checker can do for you.
  • A fitness function is a rule that runs in CI; it is only trustworthy if you have seen it fail.

Check your understanding

The extractor sees from shop.catalog import api in the file shop/cart/service.py. What target should it record?

  1. shop.catalog, because that is the module named after from
  2. shop.catalog.api, because api is a module (a file exists for it), not a function or class
  3. shop.cart.catalog.api, because the import is inside the cart package
  4. Nothing: it is an import of the cart module's own package
The syntax alone is ambiguous: after from X import n, n may be a submodule or an object inside X. Checking whether shop/catalog/api.py exists settles it, and the answer matters because the internal rule compares the full target with shop.catalog.api.

Payments needs an order's total and its user in order to charge. Which refactor best removes the cycle between payments and ordering?

  1. Let payments import shop.ordering.api instead of shop.ordering.service
  2. Move the orders table into the shared db dict so both can read it
  3. Move charge into the ordering module
  4. Make charge take the user and the amount as arguments, so payments never needs to ask ordering anything
Switching to the api fixes the internal violation but leaves the cycle, because payments still depends on ordering. A shared table is the problem, not the cure. Moving charge into ordering merges two concerns. Passing the data in turns the dependency around: ordering knows payments, and payments knows nothing.

Why write the boundary rules as a unittest that runs in CI instead of putting them in a design document?

  1. Because a document is not checked: the test fails the build the moment someone breaks a rule, with a file:line to fix
  2. Because unittest is faster than a code review
  3. Because Python does not allow private functions, so tests are the only way to hide them
  4. Because tests can prove the whole system is correct
A rule only a person remembers will be broken. A fitness function turns the rule into something that happens on every change. It does not prove correctness, and it does not make anything private; it only keeps a stated property true.

After the refactor the checker reports zero violations. Which kind of coupling could still exist between two modules?

  1. A direct import of a private function
  2. An import of the shared shop.db dict
  3. Both modules reading and writing the same sqlite file or the same strings by convention, which involves no import at all
  4. A cycle between ordering and payments
Imports are only one way to depend on another module. Two modules that agree on a file, a table or a magic string are coupled without any import for the tool to see. That is why milestone 4 removes the shared dict rather than only forbidding its import, and why the same blind spot exists between services that share a database.

Lab 2: An Idempotent, Paginated, Versioned API

Chapter 9 gave you the vocabulary of a good API: resources, status codes, one error format, idempotency keys, cursors. Chapter 10 added the harder half: an API is a promise, and promises have to survive change. In this lab you build a small orders API that keeps both. A retry never double-charges, a client can page through a list while it grows, and a v2 arrives without breaking a single v1 byte. It is a plain WSGI app, standard library only, tested by calling the app directly: no sockets, no framework.

Why this lab matters

Almost every mistake in API design shows up only after the API has users: the retry that created two orders, the page that skipped a row, the "harmless" rename that broke a mobile app that nobody can force to update. These are not syntax problems; they are problems of concurrency, ordering and compatibility. Building the machinery once, with tests that attack it, is the fastest way to make the principles from chapter 10 feel like engineering and not like etiquette.

No servers needed

WSGI is just a function app(environ, start_response), so the tests build an environ dict with wsgiref.util.setup_testing_defaults and call it. The only real concurrency is a handful of threads hitting the app at the same time against a temporary sqlite file, with timeouts so nothing can hang. Standard library only (Python 3.8+; the SQL uses ON CONFLICT ... DO UPDATE and row-value comparisons, which need sqlite 3.24 or newer, bundled with any recent Python). The whole check takes about a second.

What you'll build

Five milestones, each building on the last:

  1. Resource basics: POST /v1/orders, GET /v1/orders/{id}, validation, correct status codes, and RFC 9457 application/problem+json errors.
  2. Idempotency keys: a retry returns the same response, a key reused with a different body is rejected, and sixteen simultaneous duplicates create exactly one order.
  3. Cursor pagination: GET /v1/orders with an opaque cursor that survives inserts between pages.
  4. Versioning: a v2 with amount_cents and currency, while v1 stays byte-for-byte what it was.
  5. Deprecation and usage: Deprecation and Sunset headers on v1, and per-version counters at /admin/usage.

How the app is shaped

A WSGI app is a function. make_app(db_path, clock) creates the tables and returns app(environ, start_response). For each request the glue turns the environ into a small Req (method, path, query, body, lower-cased headers), opens one sqlite connection for that request, and calls dispatch, which returns (status, headers, body_bytes). One connection per request means threads never share one, and the database does the coordinating. clock is injected so the tests control time. Money is stored as integer cents, the only sane way to store it.

Here is the finished API in action, called directly, with no server. demo.py uses the reference solution (pass starter to try yours). The first request creates an order, the second is a retry, and the third reuses the key for something different:

Milestone 1: resource basics and honest errors

Start with the contract a client sees. The resource is an order; the collection is /v1/orders; one order is /v1/orders/{id}. POST creates (201 Created with a Location header), GET reads (200, or 404). A request body is a JSON object with customer and a non-empty items list, each item having sku, qty (an integer of at least 1) and unit_price_cents. The server computes the total itself; clients do not get to send one.

The v1 order the API returns has a decimal total in whole currency units (30.0 for two 15.00 mugs). That is the shape we will later be unable to change. It is exactly the sort of detail that feels harmless on day one.

Errors get as much care as successes. Every error is application/problem+json with the RFC 9457 members: type (a stable URI identifying the kind of problem), title, status (repeating the HTTP status), detail and instance. Validation failures (422) add an errors array with one {"field", "message"} per bad field, using paths like items[0].qty. Malformed JSON is 400: the request could not even be understood, which differs from "understood, but unacceptable". A wrong method on a real path is 405 with an Allow header; an unknown path or order is 404. The helpers problem() and result() are given.

Milestone 2: idempotency keys

The network can lose the response after the server has done the work. A client that times out cannot know whether its POST happened, so it retries, and a naive server creates a second order. An idempotency key makes the retry safe: the client sends a unique Idempotency-Key header per logical operation, and the server remembers the answer it gave. Chapter 16 of the networking course is the reason this matters; chapter 9 is the recipe.

Three rules, all of which the check enforces:

  • A replay returns the same response: same status, same body bytes, same Location. The server marks it with Idempotent-Replayed: true. Nothing new is created.
  • The same key with a different request is an error. Silently returning the first order would hide a client bug. We return 422 with a problem of type idempotency-key-reuse. This is a design choice, so here is what is known about it: the IETF HTTPAPI working group's expired draft on the Idempotency-Key header (draft-ietf-httpapi-idempotency-key-header-07) says a server SHOULD reply 422 when a key is reused with a different payload, and 409 if the original request is still in progress. We follow the 422 half. It is a draft, not a standard, and other APIs choose 409. What matters is that you choose one, document it and keep it.
  • The "same request" is defined by a fingerprint, a SHA-256 over the method, path and canonical JSON of the body (keys sorted). Retries that differ only in whitespace or key order are the same request. Including the path means the same key on /v1/orders and /v2/orders is a different request.

Two more details make it correct. Requests that fail validation never touch the key table, so a client can fix its body and retry with the same key. And a request without a key is simply not protected: the key is optional here. (Chapter 9's example required one; both are legitimate choices, and the optional version is easier to adopt.)

The race

The hard part is two simultaneous requests with the same key. "Look the key up, and if it is missing create the order and record the key" is a check-then-act race: both threads look, both see nothing, both create. A Python threading.Lock would hide the problem in one process and break the moment you run two workers. The right tool is the database: make the key column PRIMARY KEY (a unique constraint) and make the key insert the first write inside the same transaction that creates the order. The second transaction cannot commit its own insert; when it finally gets the write lock, the insert fails with IntegrityError, and that is its cue to read the first request's stored response. The constraint is the lock, and it keeps working with ten servers. (A tidy bonus: if the order insert fails, the key row rolls back with it, so a key can never point at an order that does not exist.)

Because sqlite serialises writers, the losing requests simply wait; we give each connection a 10-second timeout and take the write lock explicitly with BEGIN IMMEDIATE. The connection is opened with isolation_level=None so Python's sqlite3 module does not start transactions behind your back; you are in charge.

Hints try without first
  • The fingerprint input must be canonical: hash dumps(data) (sorted keys, no spaces) of the parsed body, not the raw bytes.
  • Order of operations inside the transaction: (1) INSERT INTO idempotency (key, fingerprint), (2) insert the order, (3) UPDATE idempotency SET status=201, location=?, body=? WHERE key=?, (4) COMMIT. The key insert is first on purpose.
  • On IntegrityError the transaction is still open: ROLLBACK before you return, or the connection keeps the write lock.
  • Wrap the whole block in try/except BaseException that rolls back (check conn.in_transaction) and re-raises. A forgotten open transaction causes "database is locked" in the other threads.
  • A deferred BEGIN followed by a SELECT of the key and then an INSERT is the trap: two connections both read, both try to upgrade to a writer, and sqlite reports "database is locked". Insert first, or use BEGIN IMMEDIATE.
  • Store the response body as bytes in a BLOB column and send those exact bytes on replay. Re-rendering would risk a different answer.

    key = req.headers.get("idempotency-key")
    # ---- milestone 2: the key row and the order are written in ONE transaction
    fingerprint = hashlib.sha256(("POST %s\n" % req.path).encode() + dumps(data)).hexdigest()
    conn.execute("BEGIN IMMEDIATE")                 # writers queue here; waiting is bounded by the busy timeout
    try:
        if key:
            try:
                conn.execute("INSERT INTO idempotency (key, fingerprint) VALUES (?, ?)", (key, fingerprint))
            except sqlite3.IntegrityError:          # somebody already owns this key (and has committed)
                row = conn.execute("SELECT * FROM idempotency WHERE key = ?", (key,)).fetchone()
                conn.execute("ROLLBACK")
                if row["fingerprint"] != fingerprint:
                    return problem(422, "idempotency-key-reuse", "Idempotency key reuse",
                                   "That Idempotency-Key was already used with a different request.", req.path)
                return (row["status"], [("Content-Type", JSON), ("Location", row["location"]),
                                        ("Idempotent-Replayed", "true")], bytes(row["body"]))
        order_id = insert_order(conn, ctx.clock, data, version)
        row = conn.execute("SELECT * FROM orders WHERE id = ?", (order_id,)).fetchone()
        location = "/%s/orders/%d" % (version, order_id)
        body = dumps(render_order(row, version))
        if key:
            conn.execute("UPDATE idempotency SET status = 201, location = ?, body = ? WHERE key = ?",
                         (location, body, key))
        conn.execute("COMMIT")
    except BaseException:
        if conn.in_transaction:
            conn.execute("ROLLBACK")
        raise

Milestone 3: cursor pagination

A list endpoint must never return an unbounded list, so it returns pages. The tempting design is ?page=3 or ?offset=40&limit=20, and it has a flaw you can see in ten lines. offset_demo.py pages through a table newest-first, four at a time, and two new rows arrive after page one:

{terminal([("cmd","python3 offset_demo.py"),("out",offset_out)])}

The offset client sees 8 and 7 twice, because the new rows pushed everything down. (With deletions it would skip rows instead.) A cursor remembers a position in the data, not a count of rows to skip, so the client continues exactly after the last row it saw, however the table changed in front of it. This is "keyset pagination" in database vocabulary. Its cost is that you cannot jump to page 50, which almost nobody needs.

The design here, following chapter 9:

  • Stable order: newest first, by (created_at DESC, id DESC). Timestamps alone are not unique (many orders can share a second), so the id breaks ties. A total order is what makes "after this row" meaningful.
  • The cursor is opaque: url-safe base64 of the JSON list [created_at, id], padding stripped. Clients must treat it as a black box, which leaves you free to change what is inside it. Opaque is a promise to yourself about what you can change later, even though base64 hides nothing from a curious client.
  • The query: WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT ?. The row-value comparison reads "strictly older than the cursor row", and the (created_at, id) index makes it cheap at any depth, which an OFFSET scan cannot be.
  • A next link: the body is {"data": [...], "next": "/v1/orders?limit=5&cursor=..."}, and next is null on the last page. Ask the database for limit + 1 rows to learn whether another page exists without an extra query, and without ever returning an empty last page.
  • Limits and errors: limit defaults to 10 and must be 1 to 50; a bad limit or a cursor you did not issue is a 400 problem.

Rows inserted during a walk are newer than anything on a later page, so they land before the cursor and are simply not part of this walk. A client that wants them starts again from the top. The walk sees a consistent snapshot of "everything that existed when I started", which is the most any cursor-based pagination can promise.

def encode_cursor(created_at, order_id):
    raw = json.dumps([created_at, order_id]).encode()
    return base64.urlsafe_b64encode(raw).decode().rstrip("=")


def decode_cursor(text):
    """Return (created_at, id) or raise ValueError."""
    try:
        pair = json.loads(base64.urlsafe_b64decode(text + "=" * (-len(text) % 4)))
    except (ValueError, TypeError):
        raise ValueError("bad cursor")
    if (not isinstance(pair, list) or len(pair) != 2
            or not all(isinstance(n, int) and not isinstance(n, bool) for n in pair)):
        raise ValueError("bad cursor")
    return pair[0], pair[1]

            raise ValueError
    except ValueError:
        return problem(400, "invalid-limit", "Invalid limit", "limit must be an integer from 1 to %d." % MAX_LIMIT, req.path)
    sql, args = "SELECT * FROM orders", []
    if "cursor" in req.query:
        try:

        except ValueError:
            return problem(400, "invalid-cursor", "Invalid cursor", "The cursor is not one this API issued.", req.path)

Milestone 4: versioning without breaking anyone

Time to change the contract. The product team wants money as integer cents and an explicit currency. The v1 field total is a decimal number (30.0), which is awkward: floats are a poor home for money, and there is no room for a currency. In chapter 10 you met the compatibility rules. Renaming and re-typing a response field is a breaking change, even though the JSON still "looks" valid. This is the textbook case for a new version.

The design is URL versioning, one of the strategies from that chapter: /v1/orders keeps its contract, /v2/orders gets the new one. Both read and write the same table; the version only decides how an order is rendered (and which request fields are accepted). The v2 order has:

  • amount_cents: an integer, the old total in minor units (3000, not 30.0);
  • currency: a three-letter uppercase code, "USD" by default. A v2 POST may send currency; if present and not three uppercase letters, it is a 422 naming the field. v1 ignores the field, since v1 clients never knew about it;
  • and no total at all.

Next to the new version sits the old one: every v1 byte must stay as it was. This is Hyrum's law in practice. With enough users, every observable behaviour is depended on by someone: key order, spacing, the float formatting of 30.0. That is why the lab fixes one serialisation (dumps: sorted keys, no spaces) and ships a snapshot. v1_snapshot.json holds sixteen exact responses (status, content type, Location, body) that the v1 API gave after milestone 3. The check replays them against your code, byte for byte. A snapshot test is a blunt tool, and exactly the right one for a promise to strangers.

Milestone 5: deprecation and usage

You cannot delete v1 on the day v2 ships, but you can tell the world it is going. Chapter 10 gave the lifecycle: announce, measure, then remove. This milestone builds the first two.

Announce: two headers

Every response from a deprecated version carries two headers. They are conventions defined by the IETF, and it matters which is which:

  • Sunset is defined by RFC 8594, an Informational RFC. Its value is an HTTP-date, such as Fri, 01 Jan 2027 00:00:00 GMT, and it says when the resource is expected to become unresponsive. The RFC calls it a hint, not a guarantee; it does not say what happens afterwards (a 4xx, a redirect, or silence). The same RFC also defines a sunset link relation that can point to documentation.
  • Deprecation is defined by RFC 9745, on the standards track. Its value is a Date in the format of structured fields: an @ followed by Unix seconds, as in @1767225600 (2026-01-01 00:00:00 UTC). It says when the resource became, or will become, deprecated. APIs that predate the RFC may use other value formats, so you may see variations in the wild.

Deprecation says "stop starting new work on this"; Sunset says "this stops working then". A sunset before the deprecation date would make no sense, and the check enforces the order. We also add a Link header with rel="successor-version" pointing at /v2/orders. Nothing forces clients to read headers, so a real programme also emails the owners it knows and updates the docs (chapter 10 spells out why), but headers cost almost nothing and let well-behaved clients and tooling notice automatically. They go on every v1 response, errors and replays included, because the client that hits the 404 is as affected as the one that hits the 201.

Measure: usage per version

"Nobody uses v1 any more" is a hope until you count. Each request to /v1/... or /v2/... bumps a counter in a usage table, and GET /admin/usage reports them: {"usage": {"v1": 8, "v2": 2}}. The admin endpoint itself is not counted, unknown versions are not counted, and the update must be a single atomic statement (INSERT ... ON CONFLICT DO UPDATE SET count = count + 1) so concurrent requests do not lose increments. A real system would break usage down per client too (chapter 10's "measure" step), so that you know whom to call. Counting per API key is a stretch goal below.

def deprecation_headers(version):
    """Headers to add to EVERY response of a deprecated version (errors and replays included)."""
    if version != "v1":
        return []
    return [("Deprecation", DEPRECATION), ("Sunset", SUNSET), ("Link", '</v2/orders>; rel="successor-version"')]

def count_usage(conn, version):
    conn.execute("INSERT INTO usage (version, count) VALUES (?, 1) "
                 "ON CONFLICT (version) DO UPDATE SET count = count + 1", (version,))

Look under the hood

The same app can be served for real with the standard library's wsgiref.simple_server. This is optional, since the checks never need it, but it makes the point that "the app is just a function" has teeth: the identical callable handles real HTTP. The bottom of solution.py (and starter.py) already contains the entry point. Run it, and in a second terminal, use curl:

Try it yourself: four experiments

  1. Remove the constraint. In a scratch copy of solution.py, change key TEXT PRIMARY KEY, in the schema to key TEXT, and run python3 check.py solution. With no unique constraint the second insert never collides, so there is nothing to replay: 
      ✘ Milestone 2: idempotency keys, even under concurrent duplicates: a replay must return the SAME status, body and Location as the first answer
    The constraint, not the surrounding code, is what makes the operation idempotent. That is why it must live in the database and not in a Python dict.
  2. Break a byte. Change the separators in dumps from (",", ":") to the default (", ", ": "). The JSON is equivalent, and parsers will not mind, but: 
      ✘ Milestone 4: v2 beside an unchanged v1: v1 changed!  POST /v1/orders ...
    Hyrum's law in one line. Ask yourself which of your own APIs have a "harmless" formatting change waiting to bite.
  3. Offset versus cursor. Edit offset_demo.py to delete two rows after the first page instead of inserting. Which approach skips rows now, and which one doesn't?
  4. A retry storm. In check.py, raise the thread count in the race from 16 to 64 and run the solution a few times. It keeps passing, because the database serialises the writers. Then reduce the connection timeout in make_app to 0.001 and watch what a too-impatient waiter looks like ("database is locked"). Where should a real service handle that: in the client, the server or the database configuration?

Stretch goals

  • Handle "in flight" explicitly. Our design makes concurrent duplicates wait on the database lock, so the 409 for "original request still in progress" never happens. In a service with a slow external call you cannot hold a transaction open: store the key as in_progress first, commit, do the work, then record the result, and answer 409 to duplicates in the middle. What new failure appears if the server crashes between those steps?
  • Expire keys. Keys cannot be kept forever. Add created_at to the key table and a purge of keys older than 24 hours. What should a client see when it retries after expiry?
  • Per-client usage. Count usage by (client, version), with the client taken from an X-Api-Key header, and report who still calls v1. This is the call list for the migration email.
  • A brownout. Make v1 return 410 Gone (as a problem document) for the first minute of every hour past the sunset date, using the injected clock, then build a test with a fake clock. Chapter 10 describes why teams do this.
  • Link header pagination. Add Link: <...>; rel="next" to list responses, as GitHub does, alongside the body's next.
  • Filtering with a stable cursor. Add ?customer= and make the cursor remember the filter. What should happen if a client sends a cursor from one filter with another?
  • A tolerant client. Write the 15-line v1 client that reads an order and survives the server adding fields. Then write the one that doesn't. Run both against v2.

Distributed systems connection

Idempotency keys exist because of the oldest fact in distributed systems: a timeout does not tell you whether the other side acted. At-least-once delivery plus an idempotent receiver is the standard recipe for "effectively once", the same recipe as the deduplicating consumers in the streams and CDC chapter (the key there is an event id). The unique constraint is doing the job a consensus would otherwise do: it makes one writer win. On several nodes with several databases, the key table would have to live in one authoritative place (or be partitioned by key), which is exactly why payment APIs route a key to one shard. Cursors show a second theme: a sound ordering needs a total order with a tie-breaker, just as distributed logs use (timestamp, node id) pairs. And versioning across independently deployed services is the lesson of partial rollout: during any deploy, old and new code talk to each other at once, so every change must be compatible in both directions.

What you learned

  • A good API response is part of the contract: the right status code, a stable machine-readable error format (RFC 9457 problem+json), and all the field errors at once.
  • Idempotency means a retry changes nothing and returns the same answer. Make the key the primary key of a table written in the same transaction as the work, and let the unique constraint settle races. Compare a request fingerprint to catch a reused key.
  • Offset pagination duplicates or skips rows when data changes. A cursor over a total order (created_at, id) with keyset SQL does not, and an opaque cursor leaves you free to change it later.
  • Renaming or re-typing a field is a breaking change. Version it, serve both views from the same data, and pin the old behaviour with a byte-exact snapshot, because of Hyrum's law.
  • Sunset (RFC 8594, informational) and Deprecation (RFC 9745) are the standard way to tell clients a version is going away; neither forces anyone to listen, so measure usage per version before you remove anything.
  • WSGI apps are plain callables, so most of an HTTP service can be tested without sockets, and the identical app can then be served for real.

Check your understanding

A client's POST times out, so it retries with the same Idempotency-Key and the same body. The first request had in fact succeeded. What should the server do?

  1. Create a second order, since it cannot tell the requests apart
  2. Return an error telling the client the key was used
  3. Return the same status, body and Location as the first response, creating nothing new
  4. Delete the first order and create it again
The point of the key is to turn an unsafe retry into a safe one. The server stores the first response against the key and replays it. An error would defeat the purpose, because the client still does not know whether its order exists.

Why is a database unique constraint a better guard for idempotency than a Python threading.Lock around "check, then insert"?

  1. Locks are slower than constraints
  2. A Lock protects only one process; the constraint holds across processes and servers, and it commits atomically with the order
  3. Python locks do not work with sqlite
  4. Constraints let duplicates through faster
A lock lives in one process's memory. The constraint lives in the shared database, so two workers (or two machines) cannot both win. Writing the key and the order in one transaction also means a failure leaves neither behind.

Page one of GET /v1/orders?limit=5 has been fetched, then three new orders are created, then the client follows next. With the cursor design in this lab, what does the client see?

  1. The three new orders at the start of page two
  2. Some orders from page one repeated
  3. The rows that follow the cursor position, exactly once each, without the new orders
  4. A 400, because the cursor is stale
The cursor stores a position, (created_at, id), not a count. New orders are newer, so they sort before the cursor and are not in this walk. The client misses nothing that existed at the start and sees no repeats. A fresh walk will include them.

v2 renames total to amount_cents. Why does the lab keep a byte-exact snapshot of v1 instead of just checking that v1 still has total?

  1. Because JSON key order is part of the JSON standard
  2. Because clients may depend on any observable detail, such as key order, spacing and number formatting (Hyrum's law)
  3. Because snapshots are faster than assertions
  4. Because sqlite changes its output between versions
With enough users, someone depends on every observable behaviour. A byte-exact snapshot turns "v1 is unchanged" from a hope into a test. The cost is that you must update it deliberately if you ever mean to change v1, which is the intended friction.

Lab 4: A Saga Orchestrator

In chapter 15 a business transaction stopped being one database transaction and became a chain of local ones, with an undo step for every do step. That idea is easy to draw and hard to get right: what if a compensation fails, if a reply is lost, if the same message arrives twice, or if the orchestrator dies right after it charged a card? In this lab you will build the orchestrator, in the standard library with sqlite, and then try to break it: failures injected at every step, duplicate deliveries, calls whose outcome you cannot know, and a seeded random killer that crashes your code at awkward moments and restarts it from its own database.

Why this lab matters

Almost every system that takes an order, a payment and a delivery across more than one service needs this machinery, whether it is written by hand, hidden in a workflow engine or borrowed from a library. The clean diagram has four boxes. The real work is in the corners: the refund that must be retried until it works, the duplicate that must not charge twice, the timeout that might mean "yes" or "no", and the restart that must not forget or repeat. Writing it once, with a checker that actively tries to catch you, is the fastest way to stop being surprised by these corners. It also explains what a workflow engine is selling you.

Fake services, real failures, no flakiness

The three services (Inventory, Payments, Courier) are plain Python objects in the same process. Instead of waiting for a real network to misbehave, you script the misbehaviour: "the second call to payments.charge times out after taking effect". A "crash" is an exception that the check throws into your orchestrator, after which it builds a new orchestrator on the same sqlite file, exactly like restarting a process. Nothing uses threads, timers or the network, and the random fuzzing is seeded, so every run is identical. Python 3.8 or newer.

What you'll build

Five milestones, each building on the last (the fifth is optional):

  1. The happy path: a saga is a list of steps, each with an action and a compensation. Run them in order and record the state in sqlite.
  2. Compensation: when step k fails, undo steps k-1 down to 1 in reverse order. The check injects a failure at every step and inspects what the services were left holding.
  3. Idempotency: every call carries a key (saga id plus step). The services dedupe on it, and the check delivers duplicates to prove that nothing is charged or refunded twice.
  4. Crash recovery: save the step and status before and after each call, so a restarted orchestrator can resume. Handle the "unknown outcome" timeout by asking the service before retrying. The check kills your code at seeded random points, 80 times.
  5. A semantic lock (optional): the order stays PENDING while the saga runs, and a concurrent "cancel" request is handled safely.

It either returns, raises ServiceError (it definitely did not happen, for example "out of stock"), raises Timeout (you do not know), or, in the tests, raises Crash (your own process just died).

Common misconception

"A timeout means the call failed, so compensate." Rows 2 and 3 of the table look identical to the caller, but in one the card was charged and in the other it was not. Treat the timeout as a failure and you may refund money you took (fine) or skip a refund for money you took and forgot (not fine); treat it as success and you may ship an order nobody paid for. This lab teaches the two safe answers: ask the service what it did, and make retrying harmless.

Milestone 1: the happy path

A saga, as chapter 15 defined it, is data: an ordered list of steps, each with the service to call, an action, and a compensation (the semantic undo). The given default_steps() returns it:

Step("reserve stock",  "inventory", "reserve", "release"),
Step("charge payment", "payments",  "charge",  "refund"),
Step("book courier",   "courier",   "book",    "cancel"),

The orchestrator is a small state machine whose state lives in sqlite, not in Python variables. A saga is one row (id, its input data as JSON, a status and the index of the step it is on), plus a log table with one row per thing that happened. Its whole life is a loop of three moves: load the saved state, do the next thing, save the new state. If every iteration begins by reading the database, then a brand-new orchestrator on the same file continues exactly where the old one stopped, and milestone 4 will cost almost no new code.

Two details to set up now, because later milestones depend on them:

  • The idempotency key. Call every service with the key f"{saga_id}:{step}", for example "order-42:1" for the payment. The key identifies the business operation, so a retry of it carries the same key (milestone 3 explains why).
  • Save a step's result and the move to the next step in one transaction (with self.db: in sqlite3). If they could be saved separately, a crash between them would leave the log and the position disagreeing.

def _create_tables(self):
    with self.db:
        self.db.executescript("""
            CREATE TABLE IF NOT EXISTS sagas (
                id TEXT PRIMARY KEY, data TEXT NOT NULL, status TEXT NOT NULL,
                step INTEGER NOT NULL, cancel_requested INTEGER NOT NULL DEFAULT 0);
            CREATE TABLE IF NOT EXISTS log (
                seq INTEGER PRIMARY KEY AUTOINCREMENT, saga_id TEXT NOT NULL,
                step INTEGER NOT NULL, phase TEXT NOT NULL, state TEXT NOT NULL);
            CREATE TABLE IF NOT EXISTS orders (id TEXT PRIMARY KEY, status TEXT NOT NULL);
        """)
def run_saga(self, saga_id, data):
    """Create the saga (if it does not exist yet), run it to the end, return its status."""
    with self.db:                       # one transaction: the saga and its order exist together
        self.db.execute("INSERT OR IGNORE INTO sagas(id, data, status, step) VALUES (?, ?, 'RUNNING', 0)",
                        (saga_id, json.dumps(data)))
        self.db.execute("INSERT OR IGNORE INTO orders(id, status) VALUES (?, 'PENDING')", (saga_id,))
    return self._drive(saga_id)

The forward-only version of the loop, as it can be at the end of this milestone (the final _drive, shown in the milestone 2 solution, replaces it):

def _drive(self, saga_id):
    while True:
        data_json, status, step, _ = self._load(saga_id)
        if step == len(self.steps):
            self._finish(saga_id, "COMPLETED", "CONFIRMED")
            return "COMPLETED"
        s = self.steps[step]
        self.services[s.service].call(s.action, f"{saga_id}:{step}", json.loads(data_json))
        self._set(saga_id, "RUNNING", step + 1, DONE=(step, "action"))

with the two helpers that save state:

def _set(self, saga_id, status, step, **outcome):
    """Save the new position and the outcome of the step just finished, in ONE transaction."""
    with self.db:
        for state, (finished_step, phase) in outcome.items():
            self.db.execute("INSERT INTO log(saga_id, step, phase, state) VALUES (?, ?, ?, ?)",
                            (saga_id, finished_step, phase, state))
        self.db.execute("UPDATE sagas SET status = ?, step = ? WHERE id = ?", (status, step, saga_id))
def _finish(self, saga_id, status, order_status):
    with self.db:
        self.db.execute("UPDATE sagas SET status = ? WHERE id = ?", (status, saga_id))
        self.db.execute("UPDATE orders SET status = ? WHERE id = ?", (order_status, saga_id))

Milestone 2: compensation

Now make failure a first-class path. When a step's action raises ServiceError, the saga cannot complete, and there is no database to roll back: the stock really is reserved, the money really was taken. Instead, as chapter 15 put it, compensation is semantic, not rollback. You run the undo of each step that did succeed, newest first, because a later step may rely on an earlier one (you refund the charge before you release the stock it paid for, which is the order you would hand things back across a counter).

In the state machine this is one new status. RUNNING moves forward through step; on failure the saga flips to COMPENSATING and step now means "the next one to undo", counting down. When it passes zero the saga is COMPENSATED. Three rules to get right:

  • The failed step is not compensated. A ServiceError means it had no effect. Undoing something that never happened is itself a bug (a refund for a charge that never occurred).
  • Compensations are retried, not abandoned. If a refund fails, nobody is going to notice, and the customer's money is stuck. Try each compensation up to MAX_ATTEMPTS times; if it still fails, raise an exception loudly (a person is needed).
  • Log the failure. The history must show FAILED for the step that broke and DONE for each compensation, in order.

Your task

Teach _drive to switch to COMPENSATING when an action raises ServiceError, and to undo the finished steps in reverse. Pull the "make one call happen" logic out into _attempt(saga_id, i, phase, data), which returns True on success and False if an action definitely failed, because milestones 3 and 4 will grow that function.

  • In one transaction: insert the FAILED row, set status = 'COMPENSATING' and step = failed_step - 1. That is the whole switch.
  • In COMPENSATING, when step < 0 the saga is COMPENSATED: finish it and return.

  • Each loop turn of _drive re-reads the row from sqlite. Resist the urge to keep step in a local variable.

def _drive(self, saga_id):
    """Loop: look at the saved state, do the next thing, save the new state. Repeat."""
    while True:
        data_json, status, step, cancel = self._load(saga_id)
        data = json.loads(data_json)
        if status in TERMINAL:
            return status
        if status == "RUNNING":
            if cancel and self._last_state(saga_id, step, "action") != "STARTED":
                # milestone 5: the user changed their mind. (Not while a call may be half done:
                # finish that step first, so its compensation is not forgotten.)
                self._set(saga_id, "COMPENSATING", step - 1)
            elif step == len(self.steps):
                self._finish(saga_id, "COMPLETED", "CONFIRMED")
            elif self._attempt(saga_id, step, "action", data):
                self._set(saga_id, "RUNNING", step + 1, DONE=(step, "action"))
            else:                                       # milestone 2: step failed, undo the ones before it
                self._set(saga_id, "COMPENSATING", step - 1, FAILED=(step, "action"))
        else:                                           # COMPENSATING: `step` is the next one to undo
            if step < 0:
                self._finish(saga_id, "COMPENSATED", "CANCELLED")
            else:
                self._attempt(saga_id, step, "compensation", data)
                self._set(saga_id, "COMPENSATING", step - 1, DONE=(step, "compensation"))

Milestone 3: idempotency

In chapter 15's words, commands are delivered at least once, so every step and every compensation must be idempotent: doing it twice has to do what doing it once does. Duplicates come from the network (the dup fault), from your own retries after a timeout, and from restarts after a crash. A service cannot tell a duplicate from a new request by looking at the contents (two customers can order the same thing), so the caller sends an idempotency key naming the business operation, and the service remembers which keys it has handled and what it answered.

You have two small jobs, one on each side of the wire:

  • Caller (the orchestrator): a retry must carry the same key as the original. You already use f"{saga_id}:{step}" since milestone 1. Use that same key for a step's compensation too: the refund of step 2 is "order-42:2", just like the charge. The services keep results per (operation, key), so the two never collide, and a refund can find the charge it undoes by its key.
  • Service: implement Service.handle(op, key, data). If (op, key) was handled before, return the stored answer without running the effect again; otherwise run self.apply(...) and remember the result.

A real service has one more obligation

Here the effect and the "I have handled this key" record live in the same Python dict, so they cannot disagree. In a real service they are two writes, and a crash between them breaks the guarantee. The remedy is the one from chapter 15 and from the outbox in data chapter 19: store the key and the result in the same local transaction as the business change.

Your task

Implement Service.handle in starter.py (the milestone 3 spot in the "given" half). Make sure the orchestrator sends f"{saga_id}:{step}" for both an action and its compensation.

Solution spoiler 
def handle(self, op, key, data):
    """Handle one delivery of (op, key): apply it once, answer repeats from memory."""
    if (op, key) in self.results:                 # a repeat: same answer, no second effect
        return self.results[(op, key)]
    result = self.apply(op, key, data)
    self.results[(op, key)] = result
    return result

Milestone 4: crash recovery and unknown outcomes

The orchestrator is a process, and processes die. The cure is the one chapter 15 stated: the saga's progress is durable, and on restart the orchestrator scans for unfinished sagas and continues each one. Because your _drive already reloads its state at the top of every loop, recover() is only a query ("which sagas are not finished?") and a call to resume.

What is subtle is the instant during a call. If you only save state after a call, then a crash while the call is in flight leaves you with no record that you even tried. So write down your intent before the call, as a STARTED row, and the outcome after. This is the outbox idea in miniature (data chapter 19): decide and record in your own database first, and let the side effect follow the record.

The same reasoning handles the Timeout exception without any crash: an unknown outcome. From networking chapter 16 you know the caller cannot infer anything from silence. So ask. The services expose status(op, key), which returns "DONE" if the service has handled that operation under that key and "NOT_DONE" otherwise. After a Timeout: if DONE, treat the call as succeeded; if NOT_DONE, call again with the same key. After MAX_ATTEMPTS tries, an action counts as failed (compensate) and a compensation raises.

Your task

Make these changes. In _attempt: log a STARTED row (and commit it) before the call; if one is already there, a previous orchestrator died during this call, so ask status first; on Timeout ask status before deciding. Then add resume(saga_id) and recover(), which resumes every saga that is not COMPLETED or COMPENSATED and returns their ids.

python3 check.py shows milestone 4 as ✔. Scenarios, then chaos. A lost reply (timeout_after) must complete the saga with the charge sent only once and status asked at least once. A lost request must be retried once. Five lost requests in a row must compensate. A crash_before and a crash_after at every action, and at a refund, must be recovered by a new orchestrator. Finally, 80 seeded runs with two sagas each and random faults of every kind (including up to three per operation, mixed) are crashed and restarted until they finish: each must end COMPLETED or COMPENSATED with no stock held that should not be, no money lost or duplicated, and no effect applied twice.

Hints try without first
  • Find an "open" call by looking at the last log row for this (saga, step, phase): if it is STARTED, the attempt began and never recorded an outcome. A tiny helper _last_state(saga_id, step, phase) does it, and you will use it again in milestone 5.
  • On recovery of an open attempt: if service.status(op, key) == "DONE": return True (it happened: do not call again). Otherwise fall into the normal call loop.
  • The Crash exception derives from BaseException on purpose, so a lazy except Exception cannot swallow it. Do not catch it. A real crash does not run your finally blocks either.
  • Do not keep any state in Python between calls that you cannot rebuild from sqlite. The check discards your Orchestrator object after every crash.
  • run_saga must continue an existing saga instead of starting over: the chaos test calls it again for saga ids that already exist, which is also why INSERT OR IGNORE was the right choice in milestone 1.
  • Count attempts per call with for _ in range(MAX_ATTEMPTS); a Timeout followed by NOT_DONE simply goes round again.
Solution spoiler 
def _attempt(self, saga_id, i, phase, data):
    """Make one action or compensation happen. True on success, False if an ACTION failed.

    A compensation is retried until it works, because giving up would leave the
    customer's money or the shop's stock stuck. It raises after MAX_ATTEMPTS.
    """
    step = self.steps[i]
    op = step.action if phase == "action" else step.compensation
    service = self.services[step.service]
    key = f"{saga_id}:{i}"                              # milestone 3: idempotency key = saga + step
    last = self._last_state(saga_id, i, phase)
    if last is None:                                    # milestone 4: write it down BEFORE the call
        with self.db:
            self.db.execute("INSERT INTO log(saga_id, step, phase, state) VALUES (?, ?, ?, 'STARTED')",
                            (saga_id, i, phase))
    elif service.status(op, key) == "DONE":             # we died during this call: did it happen?
        return True
    for _ in range(MAX_ATTEMPTS):
        try:
            service.call(op, key, data)
            return True
        except ServiceError:
            if phase == "action":
                return False                            # a definite "no": the saga must back out
        except Timeout:
            if service.status(op, key) == "DONE":       # milestone 4: ask before you retry
                return True
    if phase == "action":
        return False
    raise RuntimeError(f"compensation {op} for {saga_id} still failing after {MAX_ATTEMPTS} attempts: needs a human")
def _last_state(self, saga_id, i, phase):
    row = self.db.execute("SELECT state FROM log WHERE saga_id = ? AND step = ? AND phase = ? "
                          "ORDER BY seq DESC LIMIT 1", (saga_id, i, phase)).fetchone()
    return row[0] if row else None
def resume(self, saga_id):
    """Continue a saga that already exists (for example after a restart)."""
    return self._drive(saga_id)
def recover(self):
    """Resume every saga that is not finished. Return their ids."""
    rows = self.db.execute("SELECT id FROM sagas WHERE status NOT IN ('COMPLETED', 'COMPENSATED') "
                           "ORDER BY id").fetchall()
    for (saga_id,) in rows:
        self.resume(saga_id)
    return [saga_id for (saga_id,) in rows]

Idempotency or status query: do you need both?

With idempotent services, retrying a call whose outcome you do not know is always safe, so the status query looks redundant. It is not: it saves a request, but more importantly it is what you fall back on when a service is not idempotent, and it tells you something a retry cannot, namely that the earlier call has already taken effect so you can move on without waiting for another reply. Real systems use both, as chapter 15 advises. Try the experiment below to see what each one protects you from.

Milestone 5 (optional): a semantic lock

While a saga runs, the system is in an in-between state that no database transaction hides: the stock is reserved but the courier is not yet booked. Sagas lose the "I" of ACID, as chapter 15 says, and the order's visible status must say so. The standard countermeasure is a semantic lock: an application-level flag that marks the order as PENDING from the start of the saga, so other requests know not to treat it as final. A user who presses Cancel during that time is the interesting case. You must not flip the order to CANCELLED immediately (the money and stock would still be held), and you must not ignore the request. The safe way is to record the wish and let the saga act on it at its next step boundary, by compensating whatever has happened.

Your task

Add order_status(order_id) and cancel_order(order_id). The order is PENDING from run_saga until the saga ends, then CONFIRMED (completed) or CANCELLED (compensated, whether it failed or the user cancelled). cancel_order returns 'CANCEL_REQUESTED' for a pending order and saves a flag; 'TOO_LATE' for a confirmed one; 'ALREADY_CANCELLED' if it was cancelled; 'UNKNOWN_ORDER' if there is no such order. _drive must honour the flag.

Hints try without first
  • Put the flag in the sagas table (cancel_requested INTEGER DEFAULT 0) and an orders table with the status. Insert both rows in the same transaction in run_saga.
  • In the RUNNING branch of _drive, check the flag first: if set, switch to COMPENSATING with step - 1, the last step that finished. Then even the last step is cancellable if the flag arrives before the saga is marked complete.
  • The tricky case: a crash left an open call (a STARTED row, no outcome) and the flag is set. That call may have taken effect. If you compensate from step - 1 you will forget it. Resolve the open call first (let _attempt run: it asks status), then honour the flag.
  • The order's final status is set in the same transaction that sets the saga's final status.
Solution spoiler 
def order_status(self, order_id):
    """PENDING while the saga runs (the semantic lock), then CONFIRMED or CANCELLED."""
    row = self.db.execute("SELECT status FROM orders WHERE id = ?", (order_id,)).fetchone()
    return row[0] if row else None
def cancel_order(self, order_id):
    """A user presses Cancel. Return 'CANCEL_REQUESTED', 'TOO_LATE', 'ALREADY_CANCELLED' or 'UNKNOWN_ORDER'."""
    status = self.order_status(order_id)
    if status is None:
        return "UNKNOWN_ORDER"
    if status == "CONFIRMED":
        return "TOO_LATE"
    if status == "CANCELLED":
        return "ALREADY_CANCELLED"
    with self.db:                                       # PENDING: record the wish; the saga acts on it
        self.db.execute("UPDATE sagas SET cancel_requested = 1 WHERE id = ?", (order_id,))
    return "CANCEL_REQUESTED"

Distributed systems connection

Look at what you built against what a workflow engine sells. Durable state with a log of steps, resume after a crash, retries with a stable key, an escape hatch for humans: that is the core of the engines mentioned in chapter 15, which persist a workflow's history and replay it to rebuild the position. The problem underneath is old: you cannot tell a slow server from a dead one (networking chapter 16), so every remote call has three outcomes, not two, and the only complete answers are idempotent operations and asking. The STARTED/DONE discipline is the same trick as the outbox and the offset commit in data chapter 19: write the intent in a store you control, then perform the side effect, and make the effect safe to repeat. This is also what Lab 3 prepared you for: once each module owns its data, a request that spans modules cannot be one transaction.

What you learned

  • A saga is data (steps with an action and a compensation) driven by a state machine whose state lives in a database; each loop turn reloads it.
  • On failure, compensate the steps that succeeded in reverse order. The failed step had no effect, so it is not undone. Compensations are retried until they work.
  • Commands arrive at least once, so every call carries an idempotency key (saga plus step) and services remember (operation, key) and answer repeats from memory.
  • A timeout has three possible truths. Ask the service (status) before retrying; safe retries need the same key.
  • Record the intent (STARTED) before a call and the outcome after it. After a crash, the log plus the service's own record tell you what really happened.
  • Saving a step's result and the move to the next step in one transaction keeps the log and the position from disagreeing.
  • A saga has no isolation: use a semantic lock (PENDING) so a concurrent cancel is recorded and acted on at a step boundary, not applied half-way.

Check your understanding

A payments.charge call raises Timeout. The service's status says NOT_DONE. What is the right next move?

  1. Compensate immediately: the step failed
  2. Treat the step as done and continue
  3. Call charge again with the same idempotency key (up to the attempt limit)
  4. Call charge again with a new key so the service sees a fresh request
NOT_DONE says the earlier request had no effect, so it is correct to try again. The same key matters: if the status answer was stale or a late copy of the first request arrives, the service will recognise the key and not charge twice. A new key would turn any such duplicate into a second charge.

Why does the compensation for step 2 use the same key (order-42:2) as the action, rather than a brand-new key?

  1. Services store results per (operation, key), so the two never collide, and the refund can locate the charge it is undoing
  2. Because the service rejects any key it has not seen before
  3. To make the refund run faster
  4. It does not matter: keys are only labels for logging
The key names the business operation for this step. The refund looks up the charge made under that key, so it refunds exactly that, and a refund for a charge that never happened finds nothing to refund. Keys are not just labels: the dedupe depends on them.

What is the purpose of writing a STARTED row before calling a service?

  1. It makes the call faster
  2. After a crash the restarted orchestrator can tell that a call may have taken effect, and ask the service instead of guessing
  3. It lets two orchestrators run the same saga at once
  4. It replaces the need for idempotency keys
Without it, a crash during a call leaves no trace of the attempt, and the restart cannot tell "never tried" from "tried and succeeded". STARTED is the intent, recorded first, in the same spirit as the outbox. It does not replace idempotency: the two work together.

A user presses Cancel while a saga is on its second step. Why does the orchestrator record a flag and compensate at the next step boundary instead of setting the order to CANCELLED right away?

  1. Because cancelling is not allowed while a saga is running
  2. Because sqlite cannot update a row while another transaction is writing
  3. Because cancelled orders must be deleted
  4. Because stock is reserved and money may be taken: marking the order cancelled without undoing those leaves the services holding things for an order that no longer exists
A saga has no isolation, so the cancel arrives in the middle of a half-done business transaction. The order must stay PENDING until the saga has compensated what it did; only then is CANCELLED true. Recording the wish and acting on it at a safe boundary is the semantic-lock pattern.

Lab 1: Refactor to Hexagonal

In chapter 5 you saw the target: a pure core, ports it owns, and adapters at the edge. Real code rarely starts there. It starts as legacy.py: one function that parses a request, runs SQL, applies discounts, charges a card and sends an email, and that nobody dares touch because it works. In this lab you will take it apart without changing a single observable behaviour. You will lock the behaviour down first, extract the rules, define the ports, write two interchangeable repositories, and wire it all back together. In the optional last step you will add a feature and see how little has to change.

Why this lab matters

"Refactor" is easy to say and dangerous to do. The senior skill is not knowing the target pattern; it is moving there in small steps with a safety net, so every step is boring. You will practise the whole loop: characterisation tests, then extract, then invert dependencies, then swap an implementation. You will also feel the payoff described in chapter 7: the rules end up testable with no database, no JSON and no fakes, and the same suite certifies two different storage back ends.

No servers, no threads, no flakiness

The "HTTP request" is a plain dict and the "database" is sqlite3 in memory. The email sender and the payment provider are stubs. Everything is deterministic, and the whole check finishes in about a second. The standard library is all you need (Python 3.8+).

What you'll build

Six milestones, each building on the last (the sixth is optional):

  1. Characterisation tests: record what legacy.py actually does, and add cases of your own.
  2. Extract the domain: the rules become pure functions in domain.py, with no I/O imports.
  3. Ports and the use case: ports.py and app.py, depending only on the domain and the ports.
  4. Adapters: an in-memory and a sqlite repository that pass one shared contract suite.
  5. Wire the HTTP handler: the refactor must reproduce every recorded behaviour, with either repository.
  6. Gift cards (optional): a new requirement, and a look at what changes.

Milestone 1: characterisation tests first

Never refactor code you cannot test. When the code has no tests, you write characterisation tests (Michael Feathers' term): tests that do not assert what the code should do, only what it does. The old behaviour, including its odd corners, becomes the specification. If the refactor changes any of it, you want to know, and then decide on purpose.

The given harness does the heavy lifting. It replays 101 requests (29 hand-written edge cases and 72 seeded pseudo-random ones) through any handler and records four things: every (status, body) response, every payment charge, every email, and the final stock levels. The recording of legacy.py lives in golden.json. Run it:

$ python3 harness.py

status codes     : {200: 8, 201: 21, 400: 3, 402: 3, 404: 10, 405: 2, 409: 36, 422: 18}
payments charged : 22   emails sent: 21
legacy matches golden.json: yes

Note two quirks the recording captures, because they are exactly what a "tidy-up" would silently change. A declined payment is still recorded as a charge attempt. And an order of 500.00 or more is saved as ON_HOLD without charging anyone. Read legacy.py now, top to bottom, and list the rules you can find. Pricing is a pipeline: bulk discount on lines of ten or more, then the coupon, then 5% off big baskets, then shipping.

Milestone 2: extract the domain

Now the first real move: pull the rules out of the tangle. A business rule is anything you could explain to the shop owner without mentioning a database: "ten or more of a line gets 10% off", "orders of 500.00 and over are held for review", "free shipping from 50.00". These are the things that change most often, and they are the things you want to test without a database. As chapter 5 put it, the domain imports nothing from this project, and here it imports nothing but dataclasses and typing.

Two design decisions are made for you. First, the domain functions take already decoded data: parse_request receives a dict, not JSON text, because JSON is a wire format, and wire formats belong to the HTTP adapter. Second, the domain raises its own exceptions (ValidationError, OutOfStock, PaymentDeclined, OrderNotFound). It has no idea they will become 422, 409, 402 and 404. That translation is the edge's job. Prices are integers (cents), so there is no floating point to trip over.

Read domain_tests.py first. It is the specification of the five functions you must write: parse_request, build_lines, price, requires_hold and confirmation_email.

  • isinstance(True, int) is True in Python, so a quantity check needs not isinstance(q, bool) as well.

Solution spoiler 
def build_lines(items, products: Mapping[str, Product]) -> tuple:
    """Check each (sku, qty) against the catalogue, in order, and price it."""
    lines = []
    for sku, qty in items:
        product = products.get(sku)
        if product is None:
            raise UnknownSku("unknown sku '%s'" % sku)
        if qty > product.stock:
            raise OutOfStock("insufficient stock for '%s'" % sku)
        lines.append(Line(sku, qty, product.price_cents))
    return tuple(lines)
def price(lines, request: OrderRequest) -> Pricing:
    subtotal = sum(l.qty * l.unit_price_cents for l in lines)
    bulk = sum((l.qty * l.unit_price_cents) * 10 // 100 for l in lines if l.qty >= 10)
    after = subtotal - bulk
    coupon_off = 0
    if request.coupon is not None:
        if request.coupon not in COUPONS:
            raise ValidationError("unknown coupon '%s'" % request.coupon)
        coupon_off = min(COUPONS[request.coupon], after)
    after -= coupon_off
    big_off = after * 5 // 100 if after >= 20000 else 0
    after -= big_off
    shipping = 499 if after < 5000 else 0
    total = after + shipping
    gift_off = 0
    if request.gift_card is not None:                                   # milestone 6
        if request.gift_card not in GIFT_CARDS:
            raise ValidationError("unknown gift card '%s'" % request.gift_card)
        gift_off = min(GIFT_CARDS[request.gift_card], total)
    return Pricing(subtotal, bulk + coupon_off + big_off + gift_off, shipping, total - gift_off)

The remaining functions are short; requires_hold is total_cents >= HOLD_THRESHOLD_CENTS. Look at what is not there: no cursor, no conn, no json.loads. That absence is the point.

Milestone 3: ports and the use case

The rules are pure, but the process is not: to place an order you must look products up, charge a card, save the order and send an email. The use case orchestrates that, but it must not know how any of it is done. So it asks for what it needs in the form of interfaces, which Python spells typing.Protocol. Three of them:

  • OrderRepository: get_product, save_order (which also reduces stock, atomically), get_order.
  • PaymentGateway: charge, returning True or False.
  • EmailSender: send.

Notice who owns these. ports.py lives with the core and speaks the core's vocabulary (Order, Product), not the database's. That is the dependency inversion from chapter 5: the arrow points from the adapter to the port, never the other way. The adapters never even need to import ports, because a Protocol is checked by shape.

The use case, PlaceOrder, gets its collaborators in its constructor. The order of its steps carries a business guarantee: a declined payment must leave nothing saved and nothing emailed, so the charge happens before the save.

Solution spoiler 
class OrderRepository(Protocol):
    def get_product(self, sku: str) -> Optional[Product]: ...
    def save_order(self, order: Order) -> int:
        """Store the order AND decrement stock for its lines, atomically. Returns the new id (1, 2, 3...)."""
        ...
    def get_order(self, order_id: int) -> Optional[Order]: ...

class PaymentGateway(Protocol):
    def charge(self, customer: str, amount_cents: int, card: str) -> bool:
        """True if the charge succeeded, False if the card was declined."""
        ...

class EmailSender(Protocol):
    def send(self, to: str, subject: str, body: str) -> None: ...
class PlaceOrder:
    def __init__(self, repo: OrderRepository, payments: PaymentGateway, emails: EmailSender):
        self.repo, self.payments, self.emails = repo, payments, emails

    def execute(self, request: domain.OrderRequest) -> domain.Order:
        products = {}
        for sku, _ in request.items:
            product = self.repo.get_product(sku)
            if product is not None:
                products[sku] = product
        lines = domain.build_lines(request.items, products)
        pricing = domain.price(lines, request)
        status = "ON_HOLD" if domain.requires_hold(pricing.total_cents) else "PAID"
        if status == "PAID" and not self.payments.charge(request.customer, pricing.total_cents, request.card):
            raise domain.PaymentDeclined("payment declined")
        order = domain.Order(None, request.customer, lines, pricing.total_cents, status)
        order = replace(order, id=self.repo.save_order(order))
        subject, body = domain.confirmation_email(order)
        self.emails.send(order.customer, subject, body)
        return order

Milestone 4: two repositories, one contract

An adapter is only worth having if you can swap it. The proof is a contract test: one suite that every implementation of the port must pass, run once per implementation. Open contract.py. It says what a repository promises: ids start at 1 and grow, a saved order reads back with its lines in order, a missing order is None, and saving decrements stock. It never says how. If the in-memory repository and the sqlite repository both pass, the use case cannot tell them apart. The in-memory one makes tests instant; the sqlite one is the real thing.

The sqlite adapter is where all the SQL now lives. Keep it that way: check.py scans every other file and fails if one imports sqlite3. Writing the order, its lines and the stock change must happen in one transaction (with conn:), or a crash between two statements would leave an order with no stock decrement.

You also need the two fakes, FakePayment and FakeEmail. They are tiny recording objects (compare the fakes in chapter 7) and milestone 5 relies on them.

Milestone 5: wire the HTTP handler

The last adapter faces the other direction. The HTTP handler is a driving adapter: it takes the outside world's format (a request dict whose body is JSON text) and turns it into a call on the core, then turns the core's answer, or its exceptions, back into a status code and a body. It is the only place that knows 400, 402, 404, 405, 409 and 422. Remember how the layers talk to each other:

  • json.loads fails, or the JSON is not an object: 400, decided here, never reaching the core.
  • domain.ValidationError (including UnknownSku): 422. OutOfStock: 409. PaymentDeclined: 402.
  • The routing table (which method on which path, and the 405 for the wrong one) is HTTP business too.

Then comes the moment of truth. The composition root (here, a few lines in check.py) chooses concrete adapters and hands them to the use case:

repo = SqliteRepo(sqlite3.connect(":memory:"))            # or InMemoryRepo()
place = PlaceOrder(repo, FakePayment(), FakeEmail())
handle = build_handler(place, GetOrder(repo))
handle({"method": "GET", "path": "/orders/1", "body": None})

That is the only place that names both a use case and an adapter. Swap one line and the application runs on another database.

Distributed systems connection

A port is a seam where a slow, failing thing can be plugged in, and in a distributed system that thing is a network call. Your PaymentGateway port is a promise that charge returns a boolean, but a real gateway can time out in the middle of charging. Chapter 16 of the networking course explained why a timeout leaves you not knowing what happened. The right place to handle it is an adapter (timeouts, retries, an idempotency key sent to the provider) and the use case, which decides what an unknown outcome means. Likewise, the repository's save_order plus the email send is the "write to my database and tell the world" problem from the streams and CDC chapter. A transactional outbox implements exactly that behind a port, so the core never needs to know. And when the repository becomes a call to another service instead of a local table, the use case, the domain and the contract suite do not change; only the adapter does.

What you learned

  • Refactoring needs a safety net. Characterisation tests record what code does, so any change in behaviour is visible, and the legacy quirks become explicit decisions.
  • Business rules can be pure functions of plain data: no database, no wire format, trivially unit-testable. Errors are domain exceptions that the edge translates into statuses.
  • Ports are interfaces owned by the core. Adapters conform to them, so source-code dependencies point inwards, and the use case needs only the domain and its ports.
  • A contract test suite is what makes adapters interchangeable: two implementations pass the same tests, so a swap is a one-line change at the composition root.
  • Driving adapters (HTTP) translate formats and errors; driven adapters (SQL, payment, email) implement ports. All the SQL lives in one file.
  • Rules you can check mechanically with ast (what may import what) are cheap to enforce and keep the architecture from decaying.
  • When a requirement changes, a good boundary localises the change: here, the rule in the domain and the wire format in one adapter.

A characterisation test makes no claim that the behaviour is right. It pins it down. While you refactor, a red test means "you changed behaviour", which is either a mistake or a decision you should make on purpose.

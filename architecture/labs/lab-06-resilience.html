Lab 6: A Resilience Toolkit

In chapter 17 you met the patterns that stop one slow dependency from taking a whole system down: timeouts, retries, circuit breakers and bulkheads. Knowing their names is the easy part. The hard part is that they interact: a retry multiplies load, a breaker can hide a recovery, a timeout that is too short creates the failures it is meant to survive. In this lab you will build all four from scratch, with a fake clock so that a thirty-second outage runs in milliseconds, compose them in an order you can defend, and then measure what the combination does to a failing dependency compared with the retry loop most code starts with.

Why this lab matters

Resilience code is notoriously hard to test, because the interesting behaviour happens over seconds or minutes of real time and only when something is broken. Teams therefore ship it untested and discover how it behaves during their first outage. The technique you will use here, injecting the clock, is the way to escape that: every sleep, timeout and "wait five seconds" becomes a number you control, so a scripted outage and recovery runs deterministically and instantly. It also makes the trade-offs measurable. You will see, in numbers, that the order of the layers matters, that the retry budget does a surprising amount of work, and that a circuit breaker buys relief for the dependency at the price of a slower return to normal.

Simulated time: no sleeps, no network, no flakiness

Nothing in this lab ever really waits. A FakeClock has now() and sleep(d); sleeping just moves the clock forward. A FlakyDependency "takes" simulated time per call and fails according to a script of phases ("healthy until t=10, returning 503 until t=40, healthy again"). Randomness (the jitter) comes from a seeded random.Random that is passed in. Only the bulkhead check uses real threads, and they are released by events, not by timing. Standard library only, Python 3.8 or newer, about a second to run.

What you'll build

Five milestones, each building on the last:

  1. Timeouts: give the fake clock deadlines, and write with_timeout, so a call that "takes" too long raises TimeoutError and the time it cost is accounted correctly.
  2. Retries: exponential backoff with full jitter from a seeded RNG, only for retryable errors, with a maximum number of attempts and a retry budget (at most 10% of calls over a window).
  3. Circuit breaker: closed, open and half-open, driven by a failure rate over a rolling window, with limited probes. The check scripts an outage and a recovery and asserts the transitions at the exact simulated times.
  4. Bulkhead: cap the concurrent calls to one dependency, rejecting at once when full.
  5. The toolkit: compose all four, then run a 60-second scripted outage and compare the calls that reach the failing dependency with and without the toolkit.

Milestone 1: timeouts in simulated time

From networking chapter 16: from the caller's side a dead server and a slow one look the same, so the only tool is a deadline. A call with no timeout can hold a thread, a connection and a user's patience for as long as the other side likes. In real code a timeout is implemented by the operating system or the I/O library. In a simulation we need a way for "a call that takes longer than the limit" to stop at the limit even though the call itself is just a function that adds to a counter.

The trick is to make the clock the enforcer. Anything that takes simulated time does so by calling clock.sleep(d). If a deadline is active and the sleep would run past it, the clock advances only to the deadline and raises TimeoutError. The caller stopped waiting at start + timeout and not a moment later, so the latency is accounted correctly: a 3-second call under a 0.5-second timeout costs the caller 0.5 seconds, not 3. Deadlines are kept on a stack and nested ones can only tighten, which gives you deadline propagation (chapter 17) for free: an inner timeout of 10 s inside an outer deadline of 1 s still stops at 1 s.

Then write with_timeout(clock, fn, timeout). In the starter, sleep already advances the clock but ignores deadlines.

  • When the deadline hits, first set self._now = limit, then raise. The time up to the deadline really did pass; the check looks at the clock afterwards.
  • Use @contextmanager from contextlib (already imported) with try: yield / finally: pop. If the pop is not in a finally, one timeout leaves a stale deadline that makes every later sleep fail mysteriously, and the check has a test for exactly that.
  • Nested: limit = now + timeout, and if the stack is not empty, limit = min(limit, stack[-1]).
  • with_timeout is two lines. Everything interesting happened in the clock.
Solution spoiler 
def sleep(self, d):
    if d < 0:
        raise ValueError("cannot sleep a negative time")
    self.sleeps.append(d)
    limit = self._deadlines[-1] if self._deadlines else None
    if limit is not None and self._now + d > limit + 1e-9:
        self._now = max(self._now, limit)       # the time up to the deadline really passed
        raise TimeoutError("deadline exceeded at t=%.3f" % self._now)
    self._now += d

@contextmanager
def deadline(self, timeout):
    """Everything inside the `with` block must finish within `timeout` simulated seconds.
    Nested deadlines can only tighten: the inner limit is the smaller of the two."""
    limit = self._now + timeout
    if self._deadlines:
        limit = min(limit, self._deadlines[-1])
    self._deadlines.append(limit)
    try:
        yield
    finally:
        self._deadlines.pop()

def with_timeout(clock, fn, timeout):
    """Call fn(); if it would take more than `timeout` simulated seconds, raise TimeoutError
    at start + timeout (not later: the caller stops waiting, even though the work goes on)."""
    with clock.deadline(timeout):
        return fn()

Milestone 2: retries that help instead of harm

Many failures are transient, so trying again often works. But a retry is also more load, sent at the moment the dependency is least able to take it. Chapter 17's rules, which you will now implement, are about policy:

  • Retry only what can succeed. A timeout or a 503 may clear; a 400 will fail identically forever. Your is_retryable is given: timeouts and TransientError yes; PermanentError no; and rejections (CircuitOpenError, BulkheadFullError) never, because a rejection means "we decided not to call", and retrying it just asks again immediately. Unknown exceptions such as ValueError are bugs, not weather.
  • Limit the attempts. max_attempts counts the first try.
  • Back off exponentially, with jitter. Waiting base * 2^n spaces the retries out as the problem persists. But if a thousand clients all fail at the same instant and all wait exactly 0.1, 0.2, 0.4 seconds, they retry in lockstep and hit the dependency in synchronized waves. Full jitter fixes that by choosing a random delay between 0 and the exponential bound: uniform(0, min(cap, base * 2^n)). The average wait is half the bound, and the clients spread out.
  • Cap the total retry volume with a budget. Even with backoff, if every request retries three times, a struggling dependency sees up to four times its normal load. A retry budget allows retries only up to a fixed fraction of recent calls (here 10% over a sliding window): when the dependency is broadly failing, the budget runs dry and the clients stop adding to the problem. See also the networking lab's retry storm discussion.

A real run of the reference backoff_delay with a seeded RNG, next to the bounds it must respect, for retries number 0 to 5 (base 0.1 s, cap 2 s):

delays: [0.032, 0.03, 0.26, 0.058, 0.857, 0.731]
bounds: [0.1,   0.2,  0.4,  0.8,   1.6,   2.0]

Every delay is between zero and its bound, and the bound doubles until the cap stops it. Notice that retry 1 happened to draw 0.03, shorter than retry 0's bound: with full jitter the sequence is not monotone, and that is fine.

Hints try without first

  • In retry, count attempts. After a failure: attempt += 1; give up if not retryable(exc) or attempt >= max_attempts. The first retry uses retry_number = attempt - 1 = 0.
  • Call budget.record_call() once per logical call, at the start, not per attempt. Call can_retry() before sleeping and record_retry() only when you are really going to retry.
  • can_retry: len(retries) + 1 <= max(min_retries, ratio * len(calls)) + 1e-9. The epsilon is there because 0.1 * 30 is 3.0000000000000004 in floating point and 0.1 * 70 is 7.000000000000001; you do not want an exact comparison to fail by a rounding hair.
  • Re-raise with a bare raise inside the except block, so the original traceback and type are preserved.
Solution spoiler 
def backoff_delay(retry_number, policy, rng):
    """Full jitter: a random time between 0 and min(cap, base * 2**retry_number).
    retry_number is 0 for the first retry."""
    return rng.uniform(0, min(policy.cap, policy.base * 2 ** retry_number))

def record_call(self):
    self._prune()
    self._calls.append(self.clock.now())

def record_retry(self):
    self._retries.append(self.clock.now())

def can_retry(self):
    self._prune()
    allowed = max(self.min_retries, self.ratio * len(self._calls))
    return len(self._retries) + 1 <= allowed + 1e-9

def retry(clock, rng, fn, policy, budget=None, retryable=is_retryable):
    """Call fn() up to policy.max_attempts times. Between attempts sleep a jittered backoff on the
    fake clock. Give up (re-raise the last error) when the error is not retryable, attempts are used
    up, or the budget says no."""
    if budget is not None:
        budget.record_call()
    attempt = 0
    while True:
        try:
            return fn()
        except Exception as exc:
            attempt += 1
            if not retryable(exc) or attempt >= policy.max_attempts:
                raise
            if budget is not None:
                if not budget.can_retry():
                    raise
                budget.record_retry()
            clock.sleep(backoff_delay(attempt - 1, policy, rng))

Milestone 3: the circuit breaker

Retries and timeouts protect you from a slow dependency. A circuit breaker also protects the dependency from you, by stopping calls entirely while it is struggling. Chapter 17 gave the picture; the version you build has four settings:

  • Failure rate over a rolling window. The breaker keeps the outcomes of the last window seconds. It trips when there have been at least min_calls calls (not enough evidence otherwise: 1 failure out of 1 call is 100%) and at least failure_rate of them failed.
  • Open duration. After tripping, the breaker is open for open_duration seconds: every call is refused immediately with CircuitOpenError, without touching the dependency. That gives it room to recover.
  • Half-open with limited probes. When the open time is over, the breaker is half-open: it lets through half_open_max trial calls, and no more until they are decided. If they all succeed, the circuit closes; if one fails, it opens again for another full open_duration. Limiting the probes matters: if "recovered" meant "let everyone in", a still-sick dependency would be flattened by the full traffic.
  • What counts as failure. Timeouts and retryable errors. A 400 means the dependency is alive and answering, so it counts as a success.

That lazy transition is the subtle part. Nothing "happens" at the instant the open period ends; nobody calls the breaker. So the state property computes it on demand: if the state is open and now >= opened_at + open_duration, transition to half-open and record the time as opened_at + open_duration, the moment it logically happened, not the moment someone noticed. That is what lets a test assert "half-open at t=19" even if the next call comes at t=19.4.

The split into three methods is what lets the check hold several probes in flight at once, without threads.

@property
def state(self):
    if self._state == "open" and self.clock.now() >= self.opened_at + self.open_duration - 1e-9:
        self._transition("half-open", at=self.opened_at + self.open_duration)
    return self._state

def before_call(self):
    """Ask permission. Raises CircuitOpenError when the call must not be made."""
    s = self.state
    if s == "open" or (s == "half-open" and self.probes_admitted >= self.half_open_max):
        self.short_circuited += 1
        raise CircuitOpenError("circuit %s" % s)
    if s == "half-open":
        self.probes_admitted += 1

def on_success(self):
    if self._state == "half-open":
        self.probe_successes += 1
        if self.probe_successes >= self.half_open_max:
            self._transition("closed")
    elif self._state == "closed":
        self.events.append((self.clock.now(), True))

def on_failure(self):
    if self._state == "half-open":
        self._transition("open")
    elif self._state == "closed":
        self.events.append((self.clock.now(), False))
        calls, failures = self.window_counts()
        if calls >= self.min_calls and failures / calls >= self.failure_rate:
            self._transition("open")

def call(self, fn):
    self.before_call()
    try:
        result = fn()
    except Exception as exc:
        # A 400 means the dependency is alive and answering; only retryable errors and timeouts count as failures.
        if is_retryable(exc):
            self.on_failure()
        else:
            self.on_success()
        raise
    self.on_success()
    return result

Milestone 4: the bulkhead

The name comes from ships: watertight compartments, so a breach floods one section instead of the whole hull. In software, the shared hull is usually a thread pool or a connection pool. If your service calls both a payments API and a recommendations API from the same 40 threads, and recommendations goes slow, its calls pile up until all 40 threads are waiting on it and checkout, which has nothing to do with recommendations, stops working too. A bulkhead gives each dependency its own cap on concurrent calls: recommendations can fill its own compartment of, say, 10 and no more.

Two design choices, both visible in the code you will write:

  • Reject, don't queue. When the compartment is full the call fails immediately with BulkheadFullError. A queue in front of a slow dependency is just another place for work to wait, and for latency to grow without bound. Failing fast lets the caller degrade (a cached answer, a default) while the system still has capacity to do it. (A short bounded queue can be reasonable, but it is an addition you should be able to justify.)
  • The counter must be thread-safe. Check-then-increment on a plain integer has a race: two threads see 3 of 4 slots used and both take the last one. The check and the increment must happen under a lock.

A single-threaded simulation cannot overlap calls, so the check tests the bulkhead two ways: with an explicit acquire()/release() counter (calls "in flight" are just slots you hold), and with 12 real threads that block inside the bulkhead on an event. No sleeps decide the outcome: the check waits until all 12 have either entered or been rejected, and asserts that exactly 4 are inside.

Solution spoiler 
def acquire(self):
    with self._lock:
        if self.in_flight >= self.max_concurrent:
            self.rejected += 1
            raise BulkheadFullError("%s: %d calls already in flight" % (self.name, self.in_flight))
        self.in_flight += 1
        self.max_seen = max(self.max_seen, self.in_flight)

def release(self):
    with self._lock:
        if self.in_flight <= 0:
            raise RuntimeError("release() without a matching acquire()")
        self.in_flight -= 1

def call(self, fn):
    self.acquire()
    try:
        return fn()
    finally:
        self.release()

Milestone 5: compose them, and why the order matters

Each pattern guards against a different thing, and each has a blind spot the others cover. Together they are only as good as the order you stack them in, and "which wraps which" decides who sees what:

  • Timeout innermost. It must wrap the actual call, so every single attempt is bounded. Put it outside the retry loop and one timeout would cover all attempts together: the first slow attempt eats the whole budget and there is nothing left to retry with.
  • Retry outermost. Each attempt has to ask the bulkhead, the breaker and the timeout again. In particular, a tripped breaker should stop the next attempt at once, and a retry that sat inside the breaker would keep hammering the dependency while the breaker watched, one tripped state away from noticing.
  • Breaker around the timeout. The breaker has to see timeouts, because a slow dependency is the most common way for one to fail, and timeouts are only produced inside.
  • Bulkhead outside the breaker. A full bulkhead says "we are busy", not "they are broken". If it sat inside the breaker, those rejections would flow through the breaker as errors and could trip it, punishing a healthy dependency for our own congestion. Outside, a bulkhead rejection never reaches the breaker at all. It also means a slot is held only for one attempt: during a long backoff sleep the retry layer holds nothing.
  • Rejections are not retried. CircuitOpenError and BulkheadFullError mean nothing reached the dependency. Retrying them gets the same answer instantly, and it multiplies nothing useful. is_retryable already says so; your retry from milestone 2 honours it.

Only one layer in the whole system should retry. If a client retries 3 times against a service that retries 3 times against a database that retries 3 times, one failure turns into up to 27 attempts at the bottom. Put retries where you have the most context (usually the edge that can see the user's deadline) and let the layers beneath fail fast.

Finally the scenario, given in run_scenario: a client sends one request every 0.5 s for 60 simulated seconds. The dependency is healthy, returns 503 from t=10 to t=40, and is healthy again. It can only serve 25 calls in any 5-second window; beyond that it also answers 503, even when healthy. That one rule models something real: a dependency that is overloaded recovers only when the load drops, so aggressive retries can keep it down after the original fault has gone. This is a metastable failure, the pattern in the retry storms case study that chapter 17 builds on. The "naive" client is the baseline many teams ship: a timeout and up to five immediate retries.

The model is a model

The "stays down while overloaded" rule is a deliberately simple stand-in for real behaviour (queues filling, caches going cold, garbage collection under pressure). It is there to make the dangerous dynamic visible, not to predict a real system, and the numbers above are properties of this script. What transfers is the mechanism and the direction of each effect.

Stretch goals

  • Deadline propagation: give Toolkit.call an optional overall deadline. A retry should not start if the time left is shorter than one timeout, and the backoff sleep should be clipped to what is left. Work that cannot finish in time should not be started.
  • Slow-call rate: make the breaker also count a call as bad when it succeeded but took longer than some threshold. Many real breakers do this, because a dependency that answers in 4.9 s on a 5 s timeout is already failing.
  • Fallbacks: add call(fn, fallback=...) which returns a cached or default value on RejectedError and after the last failure. Count how many requests are served from the fallback in the scenario, and think about which fallbacks are safe (a stale price may be fine; a stale permission check is not).
  • Hedged requests: after a short delay, send a second copy of a slow idempotent call and take whichever finishes first. What does that do to total load, and how does it interact with the retry budget?
  • A sliding failure counter with buckets: replace the event list in the breaker with ten one-second buckets, as real libraries do, to keep memory constant under heavy traffic.
  • Per-host breakers: a dependency has three replicas, and one is broken. One breaker for the whole service opens for all three; one per host isolates the bad one. What changes in the bulkhead and in the retry policy (retry on a different host)?
  • Load shedding on the server side: give FlakyDependency a queue and make it reject early when the queue is long. How does a server that sheds load interact with the client's budget and breaker?

Distributed systems connection

Every piece of this lab is a local answer to a distributed problem. A timeout is the only tool for deciding "slow or dead?", and as networking chapter 16 showed, it can be wrong in both directions: it will sometimes abandon a call that was about to succeed, and a timed-out write may have been applied, so retrying it is safe only when the operation is idempotent. A circuit breaker is a failure detector run by each caller on its own, and different callers will disagree about whether the dependency is up: that is normal and no one is wrong, because each is reasoning from its own evidence. Jitter exists because synchronized clients are a distributed-systems failure mode of their own. And the retry budget is the same instinct as the backpressure and admission control you met in queues and backpressure: when capacity is short, the right response is to do less, on purpose, early, and not to ask harder.

What you learned

  • Injecting the clock turns resilience code from "untestable without an outage" into a deterministic unit test. Time itself becomes a parameter, and a deadline stack gives you timeouts and deadline propagation with a few lines.
  • A timeout abandons the wait, not the work: the caller is freed, but the dependency still handles the call.
  • Retries need four things to be safe: only retryable errors, a maximum number of attempts, exponential backoff with full jitter, and a budget that caps retries as a fraction of calls so that a broad failure does not multiply load.
  • A circuit breaker is a small state machine on a rolling failure rate. Open protects the dependency, half-open tests recovery with a limited number of probes, and the only time-driven transition is open to half-open, which you compute lazily. It costs you some recovery time.
  • A bulkhead isolates failure by capping concurrency per dependency, and rejects instead of queueing. Its counter needs a lock.
  • Order matters: timeout innermost, breaker around it, bulkhead outside the breaker so our own congestion is not mistaken for their failure, retry outermost, and rejections are never retried. Only one layer in a system should retry.
  • On a scripted outage, the toolkit sent a fraction of the calls naive retries did and recovered, where the naive client kept an overloaded dependency down. Each protection has a cost, and you can now measure it.

Check your understanding

A call takes 3 seconds and you wrap it in a 0.5 second timeout. What does the caller experience, and what does the dependency experience?

  1. The caller waits 3 seconds and then gets a TimeoutError; the dependency sees the call
  2. The caller gets a TimeoutError after 0.5 seconds; the dependency still receives the call and usually keeps working on it
  3. The caller gets a TimeoutError after 0.5 seconds; the dependency never sees the call, because it is cancelled
  4. The call succeeds, because 3 seconds is within the dependency's own timeout
The timeout only ends the wait on the caller's side. The request was sent, so the dependency has been charged for it, and a timed-out write may even have been applied. That is why timeouts cannot protect a struggling dependency by themselves, and why retrying non-idempotent calls is dangerous.

Why does the toolkit put the retry layer outside the circuit breaker, and why is CircuitOpenError not retryable?

  1. Retries are cheap, so it does not matter where they go, and CircuitOpenError is not retryable only for historical reasons
  2. So that the breaker sees fewer failures and therefore opens less often
  3. So that retries can bypass the breaker when the dependency is down
  4. So that every attempt asks the breaker for permission again and a tripped breaker stops further attempts at once; and a rejection means nothing was sent, so retrying it only repeats the refusal instantly
With retry outside, each attempt is a fresh request to the layers inside, including the breaker, which can say no immediately. A rejection is not a failure of the dependency: retrying it adds latency and noise without any chance of a different answer. (Putting the breaker outside the retry is also used, and makes the breaker see one outcome per logical call, so it reacts more slowly.)

A thousand clients all see a failure at the same instant. Which retry policy avoids them all coming back together?

  1. Exponential backoff with full jitter: each client waits a random time between 0 and its current exponential bound
  2. Exponential backoff without jitter: they all wait 0.1, 0.2, 0.4 seconds, which spaces things out enough
  3. Immediate retries, to get the answer as fast as possible
  4. A fixed 1 second delay for every retry
Without randomness, clients that failed together retry together, in synchronized waves that can knock a recovering dependency down again. Random delays spread the load; exponential growth means a persistent problem gets less and less traffic from each client.

In the scripted outage, the naive client makes 520 calls to the dependency and never recovers, while the toolkit makes 62 and recovers within seconds. Which statement is the most accurate reading of that result?

  1. Circuit breakers are always better than retries, so the breaker alone explains it
  2. The dependency is simply broken for longer when naive retries are used, regardless of load
  3. The naive retries added load while the dependency was overloaded and kept it from recovering; the toolkit cut that load (the budget and the breaker both help), at the cost of rejecting some requests and waiting for a probe before resuming
  4. The result is random and would change with a different seed
The scenario models a dependency whose capacity is limited, so extra retries are what keep it down. The experiments show both the retry budget and the breaker cutting the load, and the breaker adding some recovery delay. The result is deterministic, and the margin held for every seed the check tried. It is a model: the mechanism transfers, the exact numbers do not.

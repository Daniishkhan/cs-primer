Evolving Contracts & Versioning

You have shipped an API and people use it. Now you need to change it. This chapter is about the rules that tell you which changes are safe, the ways that apparently harmless changes break strangers, the four common versioning strategies and what each costs, and the expand-and-contract routine that lets you rename almost anything without a flag day.

Why this matters

Designing an API is a one-time event; living with it is not. Most of the cost of an API is paid after launch, in the years when the business changes and the contract has to change with it. Teams that do not know the compatibility rules either freeze their API (and the product with it) or break their consumers and spend a week apologising. The same rules apply to message formats between services, to events on a stream, and to database schemas that several services share, so this is one of the most reusable skills in the whole course.

Chapter 9 was about the shape of a good contract at launch. Here we assume it is live, and ask how to change it without making anyone else's software stop working. If you read data chapter 3, you have already seen the mechanics of schema evolution for bytes on disk and on the wire; we will not repeat them. This chapter is about the judgement layered on top.

Hyrum's law and the problem with promises

Hyrum Wright, an engineer at Google, put it like this (this is a paraphrase): with enough users of an API, it does not matter what you promised in the documentation, because somebody will depend on every observable behaviour of your system. This is Hyrum's law, and it has a grim corollary: your real contract is not the one in the docs. It is everything a consumer can see.

What counts as observable? Everything:

  • The order of results in a list you documented as "unordered" (it happened to be insertion order, and someone sorted nothing).
  • The exact text of an error message, which a client parses with a regular expression.
  • That a field is always present even though the docs said "optional".
  • The order of keys in a JSON object, the number of decimal places, the casing of an enum.
  • How long a call takes. A client written against a 20 ms endpoint may fall over at 200 ms.

Analogy: renaming a street

Back in the city, the building codes are the contracts, and roads and their signs are the APIs. You can rename a street by changing the sign. But delivery drivers have routes in their heads, a satnav has a stale map, and a restaurant printed the old address on ten thousand flyers. The sign is the documented contract; the habits, maps and flyers are the contract that actually exists. A good city planner knows that "we changed the sign" and "nobody gets lost" are different statements.

Where it breaks down: in a city you can drive down the street and see who is confused. In software you often cannot even list your consumers, let alone find out which behaviour each one relies on.

Postel's principle, and why people now question it

Jon Postel's famous guidance for early internet protocols was "be conservative in what you send, be liberal in what you accept". For a young network full of imperfect implementations it was sensible: do not crash on slightly odd input. But Hyrum's law shows the cost. If your server quietly accepts a malformed date, or a misspelled field, or a string where a number belongs, then clients will start sending exactly that, because it works. Your leniency has turned a bug into a de facto feature, and now tightening the check is a breaking change. Many protocol designers today argue for the middle path: be liberal about what you ignore (unknown fields, see the tolerant reader below), but be strict and loud about what you reject from day one, because strictness is only cheap before anyone depends on the loose behaviour.

The compatibility rules

Two directions of compatibility matter. A change is backward compatible if clients written against the old contract keep working against the new server. It is forward compatible if the old server (or an old consumer) tolerates data from the new one. During any rolling deploy both versions of every service are alive at once, so you usually need both. The following rules cover requests, responses and events alike; the only thing that changes is who is the "server" (for events, the producer) and who is the "client" (the consumers).

ChangeVerdictWhy
Add an optional request field or parameterSafeOld clients do not send it; the server must have a sensible default.
Add a field to a response or eventSafe, if clients are tolerantReaders that ignore unknown fields never notice. Strict readers (reject-unknown) do, which is why you must document that clients must ignore unknown fields.
Add a new endpoint, method or event typeSafeNobody calls it yet.
Add a required request fieldBreakingEvery existing request is now invalid.
Remove or rename a field, endpoint or eventBreakingA rename is a remove plus an add. Readers of the old name get nothing.
Change a type or format (int to string, new id format, timestamp precision)BreakingParsers and database columns on the other side were built for the old one.
Tighten validation (shorter max length, new constraint, rejecting a value that used to work)BreakingRequests that succeeded yesterday now fail. This is Hyrum's law in its purest form.
Loosen validation on a requestSafeOld requests remain valid. (Loosening a response, e.g. a field can now be null, is breaking for readers.)
Add a value to an enum a client readsRiskyA client with a closed switch over statuses sees an unknown value. Safe only if clients are told to handle unknowns.
Change a defaultBreakingThe same request now means something different. Page size 20 to 50, or include_archived flipping, changes behaviour with no change in shape.
Change an error status or error typeBreakingClients branch on errors (chapter 9).
Change semantics without changing shapeBreaking, and the sneakiestSame field names, same types, different meaning. Nothing mechanical can detect it.

The sneakiest break: same shape, new meaning

Suppose total was a number of dollars and becomes a number of cents. Or created_at used to be the time the customer clicked and becomes the time your database saw the row. Or "list is sorted by newest" becomes "sorted by relevance". Schemas, type checkers and linters all say the change is fine, because the shape is identical. Only a human who understands the domain, or a test that asserts a real value, can catch it. When the meaning must change, treat it as a removal plus an addition: introduce a new field name (total_cents) and retire the old one through the process below.

Events and stored data are contracts too

The rules above apply, with two extra twists, when the "client" is a consumer of events (chapter 14). First, producers and consumers deploy independently and you may not know every consumer. Second, events live in a log: a new consumer, or a replay after a bug, will read events written years ago in the old shape. So events need backward compatibility (new code reads old data) and forward compatibility (old consumers read new events) at the same time, and a field you remove from new events must still be understood for old ones. Formats like Protobuf and Avro encode these rules into how schemas are checked, as data chapter 3 showed, and a schema registry can refuse to accept a new schema that breaks the compatibility mode you chose.

The tolerant reader

The consumer's half of the bargain is the tolerant reader pattern: read only the fields you need, ignore everything else, don't insist on field order, and don't crash on a value you don't recognise. A tolerant reader turns most additive changes into non-events. An intolerant one (a generated class that fails on any unknown field, a switch without a default branch) makes every addition a breaking change, and then the provider is back to freezing their API.

import json

def read_order_strict(payload: dict) -> tuple:
    return (payload["id"], payload["total"], payload["status"])   # explodes on any change

STATUSES = {"created", "paid", "shipped"}

def read_order_tolerant(payload: dict) -> dict:
    """Take only what we need; ignore the rest; survive the unexpected."""
    status = payload.get("status")
    return {
        "id": payload["id"],                                   # truly required
        "total": payload.get("amount", payload.get("total")),  # accept either name
        "status": status if status in STATUSES else "unknown", # don't crash on new values
    }

v1 = {"id": 7, "total": 1250, "status": "paid"}
v2 = {"id": 7, "amount": 1250, "status": "refunded", "currency": "EUR", "risk_score": 0.1}

print(read_order_tolerant(v1))
print(read_order_tolerant(v2))
try:
    read_order_strict(v2)
except KeyError as e:
    print("strict reader fails on v2: missing", e)
$ python3 tolerant.py
{'id': 7, 'total': 1250, 'status': 'paid'}
{'id': 7, 'total': 1250, 'status': 'unknown'}
strict reader fails on v2: missing 'total'

The tolerant reader gets v2 right despite a renamed field, an unknown status and two new fields. Note the limit: it is tolerant of shape. The unknown status became "unknown" and the program must still decide what to do with it, and a silent fallback can hide a real problem. Tolerance is not the same as not caring; log what you did not understand.

Versioning strategies

Sometimes you genuinely need to make a breaking change. The question is how to let old and new coexist. There are four common strategies, and each is a trade-off, not a right answer.

StrategyLooks likeStrengthsCosts
URL version/v1/orders, /v2/ordersObvious, easy to route and to see in logs, trivial to try in a browser or curlA version covers the whole API, so a rename in one corner forces a new version of everything. Two code paths, indefinitely. Resource identity changes between versions.
Header or media typeAccept: application/vnd.example.v2+json or API-Version: 2URLs stay stable (one resource, several representations); can version per resourceInvisible in logs and links unless you capture the header; harder to test casually; caches must Vary on it.
Date-based versionStripe-Version: 2024-06-20 style; a client is pinned to a date and sees the API as it was thenMany small changes instead of rare big ones; each consumer upgrades on their own schedule; no "v2 migration project"The provider carries every historical behaviour in code, usually as a chain of translations from newest to oldest. Needs serious engineering discipline and tooling.
No versions: additive onlyOne contract that only ever grows; new names for new meanings; old fields deprecated but keptSimplest operationally; everyone is always on the latest; works well with tolerant readers and Protobuf/GraphQL-style schemasThe API accumulates warts you can never remove; real breaking changes (a data model rethink) have no home. Needs a genuinely tolerant consumer base.

The date-based scheme is worth understanding because large, long-lived public APIs use it. Stripe is the best-known example, and case 5 walks through how it works and what it costs, so I will keep to the general idea here. GitHub is a visible example you can poke at yourself: it accepts an X-GitHub-Api-Version header with a date as its value, and tells you which version it selected (the exercise below shows the exact responses).

Which one should you pick?

Many experienced engineers start with additive-only changes as the default discipline, use a visible URL or header version as the escape hatch for the rare real break, and reach for date-based versioning only when they have many external integrators and the engineering budget to maintain it. The main point is that you decide before launch, document it, and design the first version so you rarely need the second. Whatever you choose, versions are a cost: every live version is code to test, secure and operate.

Expand and contract

The central trick for changing something that others depend on is expand and contract, also called parallel change. Instead of one risky swap, you do it in three safe steps, each of which can be deployed and rolled back independently:

  1. Expand. Add the new thing next to the old one. Both exist; the server writes or returns both. Nothing breaks, because nothing was removed.
  2. Migrate. Move consumers to the new thing, one at a time, on their own schedule. Watch telemetry to see who still uses the old one.
  3. Contract. When nobody uses the old thing any more, remove it.

Here it is for the most common change of all, renaming a field. The step-through shows what the server returns, what two clients read, and what your telemetry says at each stage.

Step through

Rename "total" to "amount" without breaking anyone

  1. Before. The API returns total, and both clients read it. The team wants the clearer name amount because total has turned out to be ambiguous (before tax? after?).
  2. Expand. The server now returns both fields with identical values. This is the deployment that adds amount; nothing was removed, so no client can break. If anything goes wrong, rolling back costs nothing. Announce the deprecation of total in the docs and, ideally, in a header.
  3. Migrate. Clients switch to amount when they are ready, on their own schedule. The provider's job is to watch: logs record which callers still read total (or which API key sent the request). Here both clients have moved, and the old field has had no readers for 30 days.
  4. Contract. Only now is total removed. The breaking change has been turned into a series of non-breaking ones, spread across time. There is no flag day, and the point of no return is the last step, taken only with evidence.

The same recipe renames a database column (add the column, write both, backfill the old rows, switch reads, then drop the old column), splits an event into two, or replaces one endpoint with another. When several services share a table, it is the only sane approach; chapter 18 generalises it into a toolkit alongside feature flags and the strangler fig. The rule of thumb: never put the old and new versions of anything in the same deployment step that deletes the old one.

Deprecation, telemetry and long tails

Expand and contract only works if you can tell when the migrate step is finished, and that takes three things.

  • Announce. Mark the old thing deprecated in docs and in the response. HTTP has a Sunset header, defined in RFC 8594 (an informational RFC), whose value is a date (an HTTP-date) after which the resource is expected to stop working. Its companion, the Deprecation header, is defined in RFC 9745 (2025, standards track): its value is the date the resource was or will be deprecated, and a Sunset date must not be earlier than it. You can see both names in the headers GitHub lists. Headers are easily missed, so also email the owners you know and put a banner in the docs.
  • Measure. Log who calls each deprecated feature: the API key or client id, the version, the user agent. "Nobody has used total for 30 days" is a fact you can read off a dashboard; "I think everyone moved" is a guess. Per-consumer data also tells you whom to call.
  • Plan for the long tail. There is nearly always a small group that never migrates: a script someone wrote in 2019, an integration whose maintainer left. Decide the policy in advance (a fixed deprecation period, a final warning, a deliberate short "brownout" where the old behaviour is switched off for an hour to flush out stragglers, then removal) and apply it, or the old version will live forever.

Checking compatibility automatically

You can mechanise much of the table above. A compatibility checker takes the old and new description of a message, compares them, and classifies each difference. Many teams run such a check in CI (the OpenAPI and schema-registry tooling does this at scale). Here is a tiny version for JSON-schema-like dictionaries. It is deliberately small: it knows that "breaking" depends on direction, since a new required field breaks a request but not a response, while a removed field breaks a response but not a request.

"""Diff two JSON-schema-like dicts for a *response* (what the server sends)
or a *request* (what the server accepts) and classify each change."""

def check(old, new, direction):
    """direction: 'response' (clients read it) or 'request' (clients send it)."""
    out = []
    op, np = old.get("properties", {}), new.get("properties", {})
    old_req, new_req = set(old.get("required", [])), set(new.get("required", []))

    for name in sorted(op.keys() - np.keys()):
        if direction == "response":
            out.append(("BREAKING", f"{name}: removed (readers may depend on it)"))
        else:
            out.append(("safe", f"{name}: no longer accepted (old clients still sending it must be tolerated)"))
    for name in sorted(np.keys() - op.keys()):
        needed = name in new_req
        if direction == "request" and needed:
            out.append(("BREAKING", f"{name}: new REQUIRED request field"))
        else:
            out.append(("safe", f"{name}: new optional field"))
    for name in sorted(op.keys() & np.keys()):
        o, n = op[name], np[name]
        if o.get("type") != n.get("type"):
            out.append(("BREAKING", f"{name}: type {o.get('type')} -> {n.get('type')}"))
            continue
        if "enum" in o or "enum" in n:
            oe, ne = set(o.get("enum", [])), set(n.get("enum", []))
            if direction == "response" and ne - oe:
                out.append(("RISKY", f"{name}: new enum values {sorted(ne - oe)} (breaks clients with a closed switch)"))
            if direction == "request" and oe - ne:
                out.append(("BREAKING", f"{name}: enum values removed {sorted(oe - ne)}"))
        for bound, tighter in (("maxLength", lambda a, b: b < a), ("maximum", lambda a, b: b < a),
                               ("minLength", lambda a, b: b > a), ("minimum", lambda a, b: b > a)):
            if bound in o and bound in n and tighter(o[bound], n[bound]) and direction == "request":
                out.append(("BREAKING", f"{name}: {bound} tightened {o[bound]} -> {n[bound]}"))
            elif bound not in o and bound in n and direction == "request":
                out.append(("BREAKING", f"{name}: new {bound}={n[bound]} constraint"))
        if o.get("default") != n.get("default") and ("default" in o or "default" in n):
            out.append(("BREAKING", f"{name}: default {o.get('default')!r} -> {n.get('default')!r} (same request, new meaning)"))
    for name in sorted(new_req - old_req):
        if name in op and direction == "request":
            out.append(("BREAKING", f"{name}: optional -> required"))
    for name in sorted(old_req - new_req):
        if name in np and direction == "response":
            out.append(("BREAKING", f"{name}: no longer guaranteed present"))
    return out or [("safe", "no differences")]

def report(title, old, new, direction):
    print(f"--- {title} ({direction})")
    for verdict, msg in check(old, new, direction):
        print(f"  {verdict:8} {msg}")
    print()

--- add optional 'currency' (response)

  BREAKING total: removed (readers may depend on it)
  safe     amount: new optional field

  BREAKING coupon: new REQUIRED request field
  BREAKING note: maxLength tightened 200 -> 100

Read the verdicts against the table. Adding currency is safe. Renaming total to amount shows up as a removal plus an addition, and the removal is the break. Tightening a limit and adding a required request field are both caught. The new enum value is only "risky", since it breaks only closed switches. And the last case is the lesson: an order whose total silently changed from dollars to cents produces "no differences", because there is no structural difference to find. The checker is useful and cannot be sufficient; the semantic changes need review, documentation and tests.

Consumer-driven contract tests

A checker compares schemas. A consumer-driven contract test asks a sharper question: what does each consumer actually rely on? Each consumer writes down the requests it makes and the parts of the responses it reads (tools such as Pact do this), and the provider runs all of those expectations in its own build. If a change would break any recorded consumer, the provider's pipeline fails before deployment, naming the consumer. It is Hyrum's law turned into a safety net: the observable behaviours that matter are recorded explicitly instead of discovered in production.

The costs are real: someone must maintain the consumer tests, the provider needs a process for collecting them, and they only cover consumers who participate. They fit best between teams inside one company, where you can ask for it. They do not remove the need for the tolerant reader, and they sit alongside the broader test strategy of chapter 7: fast in-process tests for logic, and a small number of contract tests at the seams between components.

Gateways for translation

When old consumers cannot move, a layer in front of the new system can keep the old contract alive. An API gateway or adapter service accepts v1 requests, translates them to the v2 backend and translates the replies back. That lets the core move on while the old shape continues to exist at the edge. It is a useful device for a long tail, and it is also a cost: the translation layer is code with its own bugs, and it must be maintained until the last v1 consumer disappears. Date-based versioning is, in effect, this idea built into the provider. Treat gateways as a way to contain compatibility burden in one place, not to avoid ever deciding.

Internal versus public APIs

Everything above scales with how many consumers you cannot see.

  • Public and partner APIs. Thousands of unknown consumers, years-long lifetimes, and a reputation at stake. Breaking changes are extremely expensive, so use additive evolution, long deprecation periods and explicit versions, and write the policy down.
  • Internal APIs between teams. You can find your consumers, and you can send a pull request to their repository. Breaking changes are cheaper, but not free: deployments are not simultaneous, so you still need expand and contract to avoid downtime during rollouts.
  • Inside one codebase (a modular monolith, chapter 11). The compiler is your contract checker and a rename is a refactoring tool away. This is one of the genuine advantages of keeping things in one process, and a reason not to introduce a network boundary until you need one.

The honest implication: every service boundary you add turns a cheap internal refactor into a versioned, negotiated API change. That cost should be part of the decision to split a system.

Common misconception: "we can just version it later"

You can add a version, but only if the first version was designed so that clients ignore unknown things and you can tell who is calling. If v1 clients are strict, never identify themselves and hard-code your defaults, there is no clean seam to insert v2 into. Decide the versioning policy and the identification of clients before the first external consumer, even if the policy is "additive only".

Distributed systems connection

In a distributed system you can never upgrade everything at once. During any rolling deployment, version N and N+1 of a service run side by side, talking to each other and to the same database, and clients and caches hold copies of data in old shapes for as long as they like. Compatibility rules are therefore not a nicety of public APIs; they are what makes a rolling deploy possible. Event logs stretch the problem across time (data chapter 19), because a replay reads yesterday's data with tomorrow's code. The pattern also returns in replicated state machines and storage formats, where an upgrade must be safe while nodes disagree about the version. Expand and contract is the human-scale version of what consensus systems do to change their own protocols.

Key takeaways

  • Hyrum's law: your real contract is everything observable, not what you documented. Postel's liberal acceptance can harden accidents into promises, so be strict about what you reject early and tolerant about what you ignore.
  • Safe: add optional fields, parameters, endpoints and event types. Breaking: remove, rename, retype, add a required request field, tighten validation, change defaults or error codes.
  • The sneakiest break changes meaning while keeping the shape. Use a new name for a new meaning.
  • Consumers should be tolerant readers: take only what they need, ignore the rest, and handle unknown values.
  • Versioning options (URL, header or media type, date-based, additive-only) all cost something. Decide before launch and keep the number of live versions small.
  • Expand, migrate, contract turns a breaking change into a series of safe ones, and works for APIs, events and databases. Measure who still uses the old thing before you remove it, and announce with Sunset-style signals and plain communication.
  • Contract tests and gateways help contain the burden. The more consumers you cannot see, the more expensive a break, and every network boundary raises that cost.

Check your understanding

An API documents that GET /items returns items "in no particular order". In practice they always come back oldest first, and after an optimisation they come back newest first. Several clients break. Which idea explains this?

  1. Postel's principle
  2. Hyrum's law: with enough users, any observable behaviour will be depended on, whatever the docs promise
  3. The CAP theorem
  4. Expand and contract
The documentation did not promise an order, but consumers observed one and relied on it. The lesson is to either randomise or deliberately fix such behaviour early, or to accept that your real contract is bigger than your docs.

Which change to a JSON request body is most clearly a breaking change?

  1. Adding an optional gift_message field
  2. Allowing longer values in note
  3. Adding a new endpoint for a new feature
  4. Adding a new required field, coupon
Every existing client omits the new required field, so every existing request becomes invalid. Optional additions, loosened limits and new endpoints leave old requests valid.

A team changes the meaning of price from dollars to cents and keeps the field name and type (integer). Why is this the most dangerous kind of break?

  1. The shape is identical, so schema diffs and type checks pass, and clients silently compute wrong results
  2. Integers cannot represent cents
  3. HTTP prohibits changing units
  4. It forces a new URL
Nothing mechanical flags it, and nothing fails loudly: amounts are simply 100 times off. Introduce a new field name (such as price_cents) and retire the old one with expand and contract.

You want to rename total to amount in a response with many unknown consumers. What is the safest sequence?

  1. Rename it and announce the change in the changelog
  2. Release /v2 with the new name and delete /v1 the same day
  3. Return both fields, deprecate total, watch telemetry until nobody reads it, then remove it
  4. Remove total first, then add amount in the next release
Expand, migrate, contract: each step is non-breaking and reversible, and the one irreversible step (removal) happens only once the evidence shows nobody depends on the old field.

What does a client that follows the "tolerant reader" pattern do when a response contains a field it does not know about?

  1. Fails validation, to be safe
  2. Ignores it, reading only the fields it needs
  3. Passes it on to the user interface
  4. Asks the server to remove it
Ignoring unknown fields is what lets providers add fields without a new version. A reader that rejects unknowns turns every addition into a breaking change.

Which statement about versioning strategies is the most accurate?

  1. URL versioning is always best because it is visible
  2. Date-based versioning means you never maintain old behaviour
  3. Each strategy trades something: URL versions are visible but version the whole API, date-based versions give gradual upgrades but make the provider carry old behaviour, and additive-only is simplest but cannot ever remove a wart
  4. Versioning is unnecessary if you write good documentation
There is no free option. The cost moves between consumers (forced migrations), the provider (old code paths) and the design itself (accumulated warts). Choose based on how many consumers you have and how well you can see them.

Evolving Systems Safely

A live system cannot be switched off while you improve it. This chapter is about the techniques that let you change one anyway: separating deploying code from releasing it, rolling changes out to a few users first, replacing a legacy system one capability at a time, changing a database schema without a flag day, and trying new code on real traffic before anyone depends on it. Along the way you will run a small feature-flag evaluator and watch it assign 10,000 users.

Why this matters

Systems mostly work until someone changes them. Many incident reviews, across the industry, trace back to a deploy or a configuration change rather than to a hardware failure or an attack; you will hear this from nearly every operations team, though precise percentages vary and are best not quoted. The practical consequence is that the way you change a system is as much part of its architecture as the way you structure it. Teams that can ship small changes, to few users, with a quick way back, ship faster and break less. Teams that rely on large, rare, all-at-once releases do the opposite.

Most risk comes from change

A system that nobody touches tends to keep doing what it did yesterday. A system that is deployed several times a day is, by definition, being modified in production several times a day. Every deploy is a small experiment on live users. Two things follow.

First, the risk of a change grows with its size and its blast radius (how many users, how much data, how many other systems it can affect). A twenty-line change to one service for one percent of users can go wrong in a limited way; a quarter's worth of accumulated work shipped to everyone at once can go wrong in ways nobody can reason about. Second, configuration is code. A timeout, a feature switch or a routing rule changes behaviour as surely as a new function does, and deserves the same review, staged rollout and rollback plan (the point made in chapter 8).

The techniques in this chapter all reduce risk the same two ways: make each step smaller and reversible, and make it hit fewer users first, so that you learn from a small failure rather than a large one.

Analogy: renovating a city street

Think of the city from earlier chapters. You can close a main road for a year, rip it up and rebuild it, then hope the traffic comes back. Or you can build the new road alongside, open one lane to a few cars, watch how it behaves, then move traffic across lane by lane, keeping the old road open until you are certain. The second approach takes longer and costs more in signage and barriers. It almost never causes a city-wide traffic jam.

Where it breaks down: a city can only be in one place at a time, but software can run the old and new versions simultaneously and compare them on identical traffic. That ability to copy a request is a superpower roads lack, and some techniques below depend on it.

Separate deploy from release

The single most useful idea in this chapter is to treat two things as different events. A deploy puts new code onto servers. A release makes new behaviour visible to users. When they are the same event, every deploy is a release, and you cannot test in production without exposing users. When they are separate, you can deploy often, with the new code switched off, and release later, gradually, with a switch.

That switch is a feature flag (or toggle): a runtime condition in the code, controlled by configuration, that decides which behaviour a given request gets. Flags are used for different jobs, and the job determines how long the flag should live:

TypePurposeTypical lifetimeWho changes it
Release flagHide unfinished or newly shipped behaviour; roll out gradually to a percentage of usersDays to weeks. Delete after full rollout.Engineers, product
Ops flag / kill switchTurn off an expensive or failing feature fast during an incident (see chapter 17)Long-lived, by designOn-call engineers
Experiment flagShow variants to groups of users to measure an effect (A/B tests)Weeks, until the result is inProduct, data
Permission flagGive certain users or plans access to a capability (beta programme, premium tier)Long-lived; really a permission ruleProduct, support, billing

Mixing the types is a source of confusion. A release flag that quietly becomes a permission rule ("only enterprise customers see it, and we never removed the flag") is now part of your business logic, hidden in a place nobody reviews.

Percentage rollouts must be stable

Rolling a feature out to "10% of users" has a subtle requirement: the same user must get the same answer every time. If the flag is evaluated with a fresh random number per request, a user's page flips between old and new on every refresh, and the person who sees a bug cannot reproduce it. The standard fix is to hash the user id together with the flag name, turn the hash into a number from 0 to 99 (a bucket), and enable the flag when the bucket is below the rollout percentage. Raising 10% to 25% then only adds users; nobody who already had the feature loses it. Including the flag name in the hash means different flags put different users in their first 10%, so the same unlucky people are not always the guinea pigs. Here is a complete evaluator with a kill switch:

import hashlib
from collections import Counter

class Flags:
    def __init__(self, config):
        self.config = config            # {"flag": {"percent": 0-100, "kill": bool}}

    @staticmethod
    def bucket(flag, user_id):
        """Stable 0-99 bucket: same flag + same user always gives the same number."""
        digest = hashlib.sha256(f"{flag}:{user_id}".encode()).digest()
        return int.from_bytes(digest[:8], "big") % 100

    def enabled(self, flag, user_id):
        cfg = self.config.get(flag)
        if cfg is None or cfg.get("kill"):          # unknown flag or kill switch: off
            return False
        return self.bucket(flag, user_id) < cfg["percent"]

users = range(10_000)
flags = Flags({"new-checkout": {"percent": 10, "kill": False}})

def count(f):
    return sum(f.enabled("new-checkout", u) for u in users)

at10 = {u for u in users if flags.enabled("new-checkout", u)}
print("10% rollout :", len(at10), "of 10000")

flags.config["new-checkout"]["percent"] = 25
at25 = {u for u in users if flags.enabled("new-checkout", u)}
print("25% rollout :", len(at25), "of 10000")
print("users who were on at 10% and fell off at 25%:", len(at10 - at25))

flags.config["new-checkout"]["percent"] = 100
print("100% rollout:", count(flags), "of 10000")

flags.config["new-checkout"]["kill"] = True
print("kill switch :", count(flags), "of 10000")

flags.config["new-checkout"].update(kill=False, percent=25)
print("repeat calls for user 42:", {flags.enabled("new-checkout", 42) for _ in range(1000)})

# distribution of buckets
c = Counter(Flags.bucket("new-checkout", u) // 10 for u in users)
print("users per decile of bucket:", [c[d] for d in range(10)])
10% rollout : 983 of 10000
25% rollout : 2512 of 10000
users who were on at 10% and fell off at 25%: 0
100% rollout: 10000 of 10000
kill switch : 0 of 10000
repeat calls for user 42: {True}
users per decile of bucket: [983, 1009, 1009, 997, 1011, 1016, 1026, 995, 1021, 933]

Read the output carefully. A 10% rollout gave 983 users, not exactly 1000: hashing spreads users about evenly, so small populations show noise (with 10,000 users the bucket counts range from 933 to 1026 per ten percent slice). Going from 10% to 25% lost nobody. Repeated evaluation for one user is stable. And the kill switch overrides everything, in one place, instantly. Python's built-in hash() would be a poor choice here, because string hashing is randomised per process, so two servers (or one restart) would disagree about who is in the group. Use a stable hash such as SHA-256 or MurmurHash.

Flags are debt, and old flags are loaded guns

Every flag doubles the number of paths through the code it guards (two flags: four paths; ten: more than a thousand combinations nobody tests). Flags that have finished their job must be removed, along with the code on the losing side. The cautionary tale is Knight Capital, told there with sources: in outline, a new release reused a flag that had once controlled a long-dead feature, and one server still ran old code that reacted to that flag by executing that dead logic, with disastrous financial consequences within the first hour of trading. The lessons are generic: delete dead code and retired flags, never repurpose a flag's meaning, and make deployment all-or-nothing and verifiable, so that no server is left on the old version. Put an owner and an expiry date on every release flag when you create it.

Rollout strategies

Once deploy and release are separate, you can choose how to expose new code. The common strategies trade speed, cost and risk differently:

Canary release
Send a small share of real traffic (say 1%, then 5%, then 25%) to instances running the new version while the rest stay on the old one, and compare their health. The name comes from the canary in the coal mine: a small, sensitive early warning. It needs a router that can split traffic and metrics that can be compared between the two groups.
Blue-green deployment
Run two full production environments, "blue" (live) and "green" (idle). Deploy the new version to green, test it, then switch the router so that all traffic goes to green. If something is wrong, switch back. Rollback is nearly instant, but it needs double the capacity during the switch, and anything stateful (databases, in-flight requests, caches) has to work with both versions.
Rolling update
Replace instances a few at a time. Cheap and simple, but old and new versions run side by side for a while, so they must be compatible with each other and with the database (see below).
Progressive delivery
The umbrella idea of combining the above under automation: a release moves through stages (internal users, 1%, 10%, 50%, 100%), and at each stage the system checks service-level metrics such as error rate and latency before it proceeds.

The part that makes this safe rather than merely staged is automatic rollback on metrics. Define in advance what "bad" looks like (error rate more than some margin above the baseline group, latency at p99 above a threshold, a business metric such as checkout conversions dropping), and let the pipeline halt and revert without waiting for a human to notice. Humans are slow at 3 a.m.; a pipeline compares two numbers every minute. Be careful with the metrics you choose: one that needs hours of data cannot protect a one-hour canary, and a canary receiving 1% of traffic may be too small to show a rare error at all. Pair it with enough traffic and a long enough bake time for the signal to appear.

Whichever strategy you use, one rule keeps it honest: a rollback must be a rehearsed, normal operation, not an emergency improvisation. If you have never rolled back in practice, you do not know whether you can.

Branch by abstraction

Sometimes the thing you are changing is deep inside the code, used in dozens of places, and cannot be swapped in a single commit. The traditional answer, a long-lived source-control branch, is a trap: the branch drifts away from the main line and merging it becomes a project in itself. Branch by abstraction does the branching in the code instead of in version control, so everyone keeps working on the main line:

  1. Introduce an abstraction (an interface) in front of the thing you want to replace, and route all existing callers through it.
  2. Make the abstraction's only implementation the old code. Deploy. Nothing has changed for users.
  3. Build the new implementation behind the same abstraction, still unused, merging small pieces to the main line as you go.
  4. Switch callers to the new implementation, gradually, using a flag if you like (per user, per tenant, or in a test environment first).
  5. When the new implementation has taken over, delete the old one, and delete the abstraction too if it no longer pays for itself.

This is the interface-and-adapter thinking from chapter 3 and chapter 5 used as a migration tool. A runnable sketch, replacing a flat-rate tax calculation with a per-country one, with a shadow comparison (next sections) built in:

from typing import Protocol

class TaxCalculator(Protocol):                      # step 1: the abstraction
    def tax(self, cents: int, country: str) -> int: ...

class LegacyTax:                                    # step 2: wrap the old behaviour
    def tax(self, cents, country):
        return cents * 20 // 100                    # flat 20%

class NewTax:                                       # step 3: build the new one beside it
    RATES = {"GB": 20, "DE": 19, "US": 0}
    def tax(self, cents, country):
        return cents * self.RATES.get(country, 20) // 100

def checkout_total(cents, country, calc: TaxCalculator):
    return cents + calc.tax(cents, country)         # callers only know the interface

def legacy_total(cents, country): return checkout_total(cents, country, LegacyTax())
def new_total(cents, country):    return checkout_total(cents, country, NewTax())

def shadow(primary, candidate, *args, mismatches):  # dark launch: compare, never serve
    answer = primary(*args)
    try:
        other = candidate(*args)
        if other != answer:
            mismatches.append((args, answer, other))
    except Exception as e:
        mismatches.append((args, answer, repr(e)))
    return answer                                   # the user always gets the old answer

orders = [(10_000, "GB"), (10_000, "DE"), (2_500, "US"), (999, "FR"), (4_000, "DE")]
mismatches = []
served = [shadow(legacy_total, new_total, *o, mismatches=mismatches) for o in orders]
print("served from legacy:", served)
for args, old, new in mismatches:
    print("MISMATCH", args, "legacy =", old, "new =", new)
print(f"{len(mismatches)} of {len(orders)} orders differ")
served from legacy: [12000, 12000, 3000, 1198, 4800]
MISMATCH (10000, 'DE') legacy = 12000 new = 11900
MISMATCH (2500, 'US') legacy = 3000 new = 2500
MISMATCH (4000, 'DE') legacy = 4800 new = 4760
3 of 5 orders differ

Three of five orders differ, which is exactly what a shadow run is for. The differences are the new German and US rates, which are intended, but the comparison also tells you something sobering: a mismatch does not say which side is wrong. Sometimes the legacy system's behaviour is the bug, sometimes the rewrite's, and sometimes the legacy behaviour is an undocumented feature a customer depends on (Hyrum's law, chapter 10). Each mismatch is a conversation, not a test failure.

Dark launches and shadow traffic

A dark launch deploys new code and exercises it with real production inputs, without letting its results reach users. In its strongest form, shadow traffic (also called mirroring), a copy of live requests is sent to the new system in parallel; its answers are compared with the old system's and then discarded. The user only ever receives the old answer, as in the shadow() function above. This is the closest thing to a safe production test: real request shapes, real volume, real surprises, no user impact.

It has costs and limits worth knowing before you rely on it:

  • Side effects. A shadow system must not charge cards, send emails or write to shared tables. Either run it read-only, point it at a sandbox, or stub the effects. Forgetting this is how a "dark" launch emails every customer twice.
  • Load. Mirroring doubles traffic to anything the shadow calls. Make sure a slow shadow cannot slow the real request (run it asynchronously, with its own timeout and bulkhead from chapter 17).
  • Non-determinism. Timestamps, ids and ordering make exact comparison noisy. Normalise before comparing, and compare the fields that matter.
  • Writes. Comparing reads is easy; comparing writes needs the shadow to have its own copy of state, which needs to stay in sync.

Strangler fig: replacing a legacy system piece by piece

Sometimes the thing to change is not a class but an entire system: an old application that is slow to change, hard to hire for, or running on technology that is going away. The tempting plan is the "big rewrite": build the replacement in parallel, then switch over on a date. It is famous for failing, because the new system must reproduce years of accumulated behaviour before it can replace anything, the old one keeps changing in the meantime, and the whole risk lands on a single switch-over day.

Martin Fowler named the alternative the strangler fig pattern, after a vine that grows around a host tree, gradually taking over its role until the original can be removed. The steps are always the same:

  1. Put a facade in front of the legacy system: a routing layer (reverse proxy, API gateway, or a thin service) through which all requests pass. At first it forwards everything to the legacy system, so nothing changes for users.
  2. Pick one capability (a bounded, valuable, low-risk slice, such as the product catalogue) and build it in the new system. Route just that capability's requests to the new system, perhaps starting with a percentage or with shadow traffic.
  3. Repeat, capability by capability. At every stage the system as a whole works, and each step can be rolled back by changing a routing rule.
  4. Retire the legacy system once nothing routes to it.
Step through

A strangler-fig migration in four stages

  1. Facade in front. A routing layer is inserted ahead of the legacy system and forwards every request to it. Users notice nothing, and this step alone is valuable: you now have a single place to observe, and to redirect, all traffic.
  2. Route one capability. The product catalogue is rebuilt in the new system and the facade sends /catalog there, perhaps for 1% of users at first. Everything else still goes to legacy. If the new catalogue misbehaves, flip the rule back.
  3. More capabilities. Cart and checkout follow, each with its own rollout. The legacy system shrinks to what has not yet been moved. Data ownership is the hard part: each moved capability needs its data, kept in sync (or moved) with care.
  4. Legacy retired. The last capability moves, traffic to the legacy system drops to zero, and it is switched off. The facade can be removed or kept as the system's front door. There was never a switch-over day.

The pattern's strength is that value arrives early and risk is spread out: each slice is a small, reversible change. Its weaknesses are real. The facade is a new component on every request's path, so it must be fast and highly available (chapter 17). The old and new systems may need to share or synchronise data during the transition, which is where most of the difficulty lives (the outbox and change-data-capture patterns in data chapter 19 are often used). Migrations also have a habit of stalling at 80% with the legacy system still running and now more expensive to operate than before, so give the project an explicit end date, and decommission as you go. Choose the slices along the seams of the domain (chapter 6, chapter 12), not along whichever code is easiest to lift.

Expand and contract for database schemas

Code can be rolled back by redeploying the previous version. A database that has had a column dropped or renamed cannot. Schema changes are therefore the part of evolution where the discipline matters most, and the answer is the one you met for APIs in chapter 10: never change a thing in place; expand it, migrate, then contract it. For renaming customer.name to customer.full_name, in outline:

  1. Expand: add the new column (nullable, no default that locks a huge table). Nothing reads it yet.
  2. Write both: deploy code that writes to old and new columns, still reading the old one.
  3. Backfill: copy existing rows to the new column, in small batches, off-peak.
  4. Read new: switch reads to the new column (behind a flag, ideally), and verify.
  5. Stop writing old, then contract: remove writes to the old column and, after a safe delay, drop it.

The reasoning behind the sequence is backward-compatible deploy order. During any rollout, old and new versions of your code run at the same time (that is what a rolling or canary deploy is), and both must work against the database as it stands. So for additive change the order is: database first (the new column exists but is unused, so old code is unaffected), then readers (code that can read the new shape and still tolerate the old), then writers (code that starts producing the new shape, which every reader can now handle). For removal, run it in reverse: stop writers first, then readers, then drop. Skipping the order gives you the classic failure: a new writer producing data that an old reader, still running somewhere, cannot parse. The data course covers the mechanics of schema change in chapter 3, and the Stripe online-migrations case shows the whole dance carried out at scale on live traffic, including the backfill and the double-write, with sources; read it rather than expecting a repeat of those details here.

"We will clean it up later" is the step that gets skipped

The contract phase delivers no visible feature, so it is the first thing dropped from a busy sprint, and you end up with both columns forever, an unlabelled dual-write, and a codebase nobody dares touch. Put the contract step in the same plan, with an owner, as part of the definition of done. The same applies to flags (above) and to the legacy system in a strangler migration.

Try it yourself

You need Python 3 (the SQLite module is in the standard library).

  1. Run flags.py. Then change the flag name in one call to "new-search" and compare which users are in the first 10% for each flag. Are they the same people?
  2. Replace the SHA-256 bucket with Python's built-in hash(f"{flag}:{user_id}") % 100 and run the script twice. What changes between runs, and why does that break a rollout across several servers?
  3. In branch_by_abstraction.py, add a third order that makes the new calculator raise an exception (for example an unknown country that you make NewTax reject). Confirm the user still gets the legacy answer while the problem is recorded.
  4. Using sqlite3, walk through the expand and contract steps for a rename: create a customers(name) table, add full_name, backfill with an UPDATE, and read from the new column. SQLite can drop a column in recent versions (3.35 and later); check yours with sqlite3 --version.
  5. Pick a system you know and sketch its strangler migration: what is the facade, which capability would you move first, and which one would you leave until last? Why?

Distributed systems connection

Every technique here is a response to one distributed-systems fact: in a running fleet there is no instant at which everything changes together. During a rollout, two versions of your code, and often two versions of your data's shape, coexist, so every change must be compatible with its neighbour in time, which is the same discipline as the compatibility rules in chapter 10. The flag service, the router and the metrics pipeline become dependencies you must design for failure (chapter 17): what does your service do if it cannot reach the flag system? A well-built client falls back to the last known value or a safe default. The next chapter, Documenting & Deciding, is about recording why you chose to change things in the way you did.

Key takeaways

  • Change, not steady state, is where most incidents start, so how you change a system is part of its architecture. Make steps small, reversible and exposed to few users first.
  • Separate deploy from release with feature flags. Know the types (release, ops, experiment, permission) and give each a different lifetime. Percentage rollouts must use a stable hash of the user id.
  • Flags are debt. Remove them, with the dead code, as soon as they have done their job, and never repurpose an old flag: this is the lesson of Knight Capital.
  • Canary, blue-green and rolling updates trade cost, speed and risk. Progressive delivery adds automatic rollback on metrics; rehearse rollback.
  • Branch by abstraction lets you replace internals on the main line. A strangler fig replaces a whole legacy system one capability at a time behind a routing facade.
  • Change schemas by expand and contract. Deploy order for additive change is database, then readers, then writers; reverse it for removal. Finish the contract step.
  • Dark launches and shadow traffic test new code on real inputs without exposing users, provided they have no side effects and mismatches are investigated rather than assumed to be bugs in the new code.

Check your understanding

A feature is rolled out to 10% of users by calling random.random() < 0.10 on every request. What is the main problem?

  1. It enables the feature for more than 10% of users
  2. The same user flips between old and new behaviour from one request to the next, so experience and bug reports are inconsistent
  3. Random numbers are too slow to use in production
  4. It cannot be switched off in an emergency
Over many requests about 10% are enabled, but nothing ties a request to a user. Hashing the user id (with the flag name) into a stable bucket makes the answer deterministic per user, and raising the percentage then only adds users.

You are adding a new column and changing code to use it, while a rolling deploy means old and new code run side by side. What is the safe order?

  1. Deploy writers first, then readers, then the database change
  2. Deploy readers, then the database, then writers
  3. Everything at the same moment, during a maintenance window
  4. Database change first, then code that can read the new column, then code that writes it
The additive schema change is harmless to old code, so it goes first. Readers that handle both shapes come next, so that when writers start producing the new data every reader already copes. Reversing the order means a new writer can produce data that an old reader cannot handle.

What is the key difference between a big-bang rewrite and a strangler-fig migration?

  1. The strangler moves one capability at a time behind a routing facade, so the system always works and each step is reversible; there is no single switch-over day
  2. The strangler requires the new system to be finished before any traffic is routed to it
  3. The big-bang rewrite is always faster and safer
  4. The strangler needs two separate teams who never talk to each other
The facade lets you route traffic per capability, and change the routing back at any time. A big-bang rewrite concentrates all the risk into one cutover, after the new system has had to match years of behaviour without ever having served real traffic.

Your canary at 1% of traffic shows no errors for ten minutes, but the real rollout later fails badly for one type of customer. Which is the most plausible explanation?

  1. Canary releases never detect real problems
  2. The rollback should have been done by hand
  3. The canary was too small or too short to show a rare failure, or its metrics did not cover that customer's path
  4. Blue-green would have had identical results
A canary only protects you from problems that are visible in its traffic and its metrics. Rare paths, low volumes and metrics that average everything together can hide a failure; choose enough traffic, enough bake time and metrics that cover the paths that matter.

A shadow run of a rewritten pricing service shows that its answers differ from the legacy service on 3% of requests. What is the right reaction?

  1. The new service is wrong; fix it until the difference is zero
  2. Investigate the differences: some may be bugs in the new service, some bugs in the legacy one, and some legacy behaviour that customers rely on
  3. Ignore it, since users still receive the legacy answer
  4. Switch over, since 97% matches
A mismatch tells you the systems disagree, not which one is right. The legacy system is the specification only until proven otherwise, and its quirks can be both bugs and promises (Hyrum's law). Triage the differences by cause before deciding what to change.

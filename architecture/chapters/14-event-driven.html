Event-Driven Architecture

An order is placed, and five other parts of the system need to react. You can tell each of them what to do, or you can announce what happened and let them decide. This chapter is about the second choice: what an event really is, the four different things people mean by "event-driven", why a flow that nobody orchestrates is both liberating and hard to see, and how to design events that can still be understood in three years.

Why this matters

Events are the glue of most systems that have outgrown a single process. Used well, they let teams add new behaviour without touching the code that produces the news, and they survive the failure of a downstream service. Used carelessly, they produce a system where the business process exists nowhere in particular, where a small change breaks something three services away, and where the first question in every incident is "who even listens to this?". Senior engineers are expected to tell these outcomes apart before the design is built, because events are very easy to add and very expensive to take back.

Events, commands and queries

Three kinds of message cross a boundary in a system, and mixing them up is the most common source of confusion in event-driven designs. The difference is not syntax; it is who owns the decision.

Event
A statement that something has happened. It is named in the past tense (OrderPlaced, PaymentCaptured), it is a fact that cannot be undone or refused, and it is owned by its producer: only the Order service gets to say that an order was placed. The producer does not know, and does not care, who reads it. There may be zero, one or fifty consumers.
Command
A request that something should happen. It is named in the imperative (ChargeCard, ReserveStock), it is addressed to one specific receiver, and the receiver may refuse it. The sender owns the intention; the receiver owns the decision to carry it out.
Query
A request for information that changes nothing (GetOrder). It expects an answer.

Analogy: the restaurant order ticket

In a restaurant, a waiter writes an order ticket and pins it to the rail in the kitchen. The ticket says what has happened: "table 7 ordered two pasta and one salad". It does not say "grill cook, make pasta now". The pasta station, the salad station and the person who tracks the bill each look at the ticket and do their own part. The waiter does not know who is working today, and a new dessert station can start reading tickets tomorrow without anyone retraining the waiter. That ticket is an event. If instead the head chef shouts "you, make this pasta", that is a command: one named receiver, and the cook can answer "we are out of pasta".

Where it breaks down: a paper ticket is physically in one place and gets thrown away at the end of the night. A software event can be read by many consumers at once, stored for years, replayed, and read by a consumer that did not exist when it was written. Also, a ticket is never lost in transit, while a message between services can be delayed, duplicated or dropped, which is why most of this chapter's design rules exist.

Common misconception

Naming something in the past tense does not make it an event. EmailSendRequested published to exactly one email service, which is expected to send the email, is a command wearing a costume. The test: if you removed the only consumer, would the producer's job still be complete and meaningful? For OrderPlaced, yes: the order was placed. For a disguised command, no: the sender is waiting for something to happen. Disguised commands give you the hidden coupling of events without the honesty of a command.

Four things people mean by "event-driven"

"We're event-driven" can describe four quite different designs. Martin Fowler's 2017 article "What do you mean by 'Event-Driven'?" separated them, and the distinction is the most useful vocabulary you can bring to a design discussion, because they have different costs. Which one is somebody proposing?

  1. Event notification. The event is small. It says that something happened, usually with an id, and receivers who want details call back to the producer. The producer is decoupled from who reacts, but receivers still depend on the producer's API being up.
  2. Event-carried state transfer. The event carries (enough of) the data itself, so receivers can keep their own copy and never need to call back. This trades coupling to availability for duplicated data and eventual consistency.
  3. Event sourcing. The sequence of events is the stored state of the system, and the current state is derived from it. This is a persistence decision inside one service, not a messaging decision. We cover it in chapter 16.
  4. CQRS. Command Query Responsibility Segregation: separate models for writing and reading, often with events keeping them in sync. Also in chapter 16.

The first two are about messaging between services and are the subject of this chapter. The last two are about how a service stores and serves its own data. They can be combined but none requires the others: you can use notifications with a plain CRUD database, and event sourcing in a system that publishes no events at all.

Choosing between notification and state transfer

Notification is the simplest and keeps one source of truth: there is exactly one place where the order lives, and receivers always read the current version. Its weaknesses are the extra call per event (a burst of events becomes a burst of requests to the producer, which may overload it) and the fact that the receiver is now temporally coupled to the producer again (chapter 13). It also has a subtle race: by the time the receiver calls back, the data may have changed, so it can see a state newer than the event that triggered it. That is often fine, but not if the receiver needs "the state at the time of the event".

State transfer makes the receiver autonomous, since it can do its work with the producer down, and takes load off the producer. But now there are copies. Each copy is eventually consistent with the source, and every consumer must decide what to do with a stale or out-of-order update. If Shipping's copy of the address is a minute old when the customer corrects a typo, that is a business rule to think about, not a bug to be discovered. A good default for beginners: start with notification where the data is small and the producer is robust, and use state transfer where the receiver must keep working when the producer is down or where the read traffic would hurt the producer.

Publish/subscribe: broker or log

Underneath, events are carried by a messaging system, and the two main families behave differently enough that the choice shapes your design. We met the mechanics in data chapter 19 and in systems chapter 14; here is the architectural view.

Broker (queue-style)
The broker holds messages until a consumer acknowledges them, then deletes them. Each subscriber gets its own queue (a common pattern: one topic fanning out to one queue per subscribing service). Good at work distribution: several workers can share one queue and each message goes to one of them. Once consumed, a message is gone, so a new subscriber starts empty and cannot see the past.
Log (stream-style)
Events are appended to a retained, ordered log, and each consumer tracks its own position (offset). Reading does not delete anything; retention is a separate policy. A new consumer can start from the beginning, a buggy consumer can rewind and replay, and ordering is guaranteed per partition. The price is that you manage offsets, partitions and retention.

Which should you pick? If events are tasks to be done once (send this email, resize this image) a queue-style broker is natural. If events are facts that many consumers, including future ones, will want (an order was placed), a log earns its complexity: it lets you add a consumer later, rebuild a search index from scratch, or replay after a bug. Many systems use both. Whichever you use, the delivery rules of data chapter 19 apply; we recap them in a moment.

Choreography versus orchestration

Suppose placing an order triggers payment, then stock reservation, then shipping, then a confirmation email. Who decides the order of these steps? There are two answers, and they are the central design choice of this chapter.

Choreography
There is no conductor. Each service listens for the events it cares about and publishes new events of its own. Payment hears OrderPlaced and publishes PaymentTaken; Inventory hears PaymentTaken and publishes StockReserved, and so on. The flow emerges from the subscriptions, as dancers each following the music with no choreographer in the room.
Orchestration
One component, the orchestrator (also called a process manager), owns the flow. It sends a command to Payment, waits for the outcome, then sends a command to Inventory, and so on. The other services know nothing about the flow; they obey commands and report results. The workflow is explicit, in one place, as code or configuration.

What the widget showed

Choreography's strengths. It is loosely coupled: the producer of OrderPlaced has no idea who reacts, so a new reaction (say, an analytics service or a loyalty-points service) can be added without touching the producer. There is no central component to become a bottleneck or a single point of failure, and each team owns exactly its own reaction. It is a good fit for fan-out, where many independent things happen because of one fact.

Choreography's cost: the hidden workflow. The business process "how an order gets fulfilled" is a real thing the company cares about, yet in a choreographed system it is written down nowhere. It exists only as the sum of subscriptions in five codebases. To learn the flow you must read all of them. To change it, as the widget showed with the fraud check, you must change the right subset of them, in the right order of deployment, and nothing will warn you if you miss one. To answer "where is order 42?", you must ask every service. To notice that an order is stuck, you need a monitor that knows what the flow is supposed to be, which means you have to write the workflow down after all, only now as a separate piece of surveillance code. Decoupling at the code level can leave you tightly coupled at the business-process level.

Orchestration's strengths. The flow is visible, testable and changeable in one place. Error handling, timeouts, retries and compensation (chapter 15) have an obvious home. Status questions are one lookup. Services stay simple, because each only does its own job.

Orchestration's costs. The orchestrator becomes a critical dependency, so it must be highly available and keep its state durable. It can attract logic that belongs to other services until it turns into a "god service" that every team must edit (the discipline: it should sequence steps, not make other contexts' business decisions). And the services are now coupled to it: they receive its commands, which is a different and more explicit coupling than listening to events.

When does each win? A reasonable rule of thumb, offered as opinion rather than law: use choreography for reactions (many independent consumers of a fact, especially across team or context boundaries) and for flows with only two or three steps. Use orchestration for business processes: multi-step flows with ordering requirements, failure paths and compensation, where somebody in the business will ask "what is the process?" and "where is this one?". Many mature systems use both: each bounded context (chapter 6) publishes events about what happened inside it, for anyone to react to, and a workflow that crosses contexts is driven by an orchestrator that consumes some of those events and sends commands. If you can describe a flow as a numbered list in a meeting and the list matters, it probably wants an orchestrator. If it is "and also, whenever X happens, do Y", it probably wants a subscription.

Analogy: a kitchen with and without an expediter

In a small café the cooks just watch the ticket rail and each does their part (choreography). In a busy restaurant there is an expediter at the pass who calls "fire table 7", checks that the pasta and the steak will land together, and knows which tables are waiting. Nobody argues the café is badly run; it simply has no need of someone who sees the whole. As the menu grows and tables multiply, the lack of an expediter shows up as cold plates and nobody knowing where table 7's food is.

Where it breaks down: an expediter is a person who stands in the kitchen and sees everything. A software orchestrator only knows what it has been told by messages, so it can be wrong about the world, and if it crashes it must remember where it was (we return to this in chapter 15).

Designing events

An event is an interface. Once other teams subscribe, you cannot change its shape freely (chapter 10), and Hyrum's law applies: consumers will come to depend on everything observable about it, including fields you thought were incidental. A little care at the start pays back for years.

Naming

  • Past tense, domain language. OrderPlaced, PaymentCaptured, ShipmentDispatched. Use the vocabulary the business uses (the "ubiquitous language" of chapter 6), not the name of a table or a technical operation.
  • Say what happened in the business, not what changed in the database. OrderUpdated with a diff of fields forces every consumer to work out why it changed. OrderCancelled, ShippingAddressCorrected and OrderLineAdded carry intent.
  • Avoid names that imply a receiver. SendWelcomeEmail is a command. CustomerRegistered is an event, and an email service can react to it.

Granularity

Too coarse, and a single event with many unrelated optional fields becomes a dumping ground that every consumer must parse. Too fine, and a single business action explodes into a dozen events that must arrive in order to make sense. A useful guide: one event per meaningful business fact, one that a consumer could react to by itself. If consumers always need two events together, they were probably one fact.

What to include: ids or full state?

This is the notification versus state-transfer decision again, now at field level. Include identifiers (order id, customer id) always, plus a unique event id, a timestamp, and a correlation id (more below). Beyond that, include the data a typical consumer needs to act without calling back, which is the facts that were true at the time (the price charged, the shipping address used), but resist copying everything. Two cautions:

  • Snapshots of time are valuable. The price on the order at purchase time should travel with the event, because looking it up later might give today's price.
  • Sensitive data multiplies. Every field you put in an event is copied into every subscriber's store, and possibly into a log retained for months. Personal data in a widely read event is hard to delete and hard to protect. Prefer an id plus a lookup for anything sensitive that few consumers need.

Schemas and versioning

Write events down in a schema language (JSON Schema, Avro and Protobuf are all used for this) and keep the schemas somewhere consumers can find them, often in a schema registry. The compatibility rules are exactly those from chapter 10 and from data chapter 3, with one twist: events are often stored for a long time, so consumers must read old events as well as new ones (backward compatibility), and a new consumer may meet events written by an old producer. The usual practice is to evolve by adding optional fields, never reuse or repurpose a field, and to introduce a new event type (OrderPlacedV2, or a new name that says what is different) when a change is truly breaking, running both for a while.

Public versus internal events

Not every event should leave the building. Inside one service or bounded context, fine-grained events such as DiscountApplied or StockHoldPlaced reflect internal modelling and can change whenever the team likes. Events published for other contexts to consume are a public contract: fewer, more stable, deliberately designed, and mapped from the internal ones at the boundary. Publishing your internal events directly, or worse, streaming raw database row changes as if they were domain events, makes your table layout part of everyone else's interface. Change data capture is a great tool for getting changes out reliably (data chapter 19), but the outbox pattern from that chapter lets you publish a deliberately shaped event instead of a row.

Delivery semantics: the short recap

You met the guarantees in data chapter 19, so here are only the consequences for design. Networks drop and delay messages (networking chapter 16), so practical systems use at-least-once delivery: if the broker is unsure the consumer got a message, it sends it again. Duplicates are therefore normal, not exceptional. The architectural rule is consumers must be idempotent: handling the same event twice must have the same effect as handling it once. The standard trick is to give every event a unique id and have the consumer record which ids it has handled, in the same transaction as its own state change:

class Consumer:
    """At-least-once delivery means duplicates will arrive. Remember what you have handled."""
    def __init__(self):
        self.seen, self.balance = set(), 0      # in real life: same database, same transaction

    def handle(self, event_id: str, amount: int) -> str:
        if event_id in self.seen:
            return "duplicate, skipped"
        self.balance += amount
        self.seen.add(event_id)
        return "applied"


c = Consumer()
for eid, amount in [("e1", 40), ("e2", 15), ("e1", 40), ("e3", 10)]:   # e1 is redelivered
    print(eid, c.handle(eid, amount), "-> balance", c.balance)

The second rule is about ordering. Logs and many brokers order events per partition or per key, not globally. All events about order 42 (hashed to the same partition by the key order_id) arrive in order; events about orders 42 and 43 may interleave arbitrarily. So design events so that consumers only depend on the order of events about the same entity, choose the entity id as the key, and never assume that PaymentTaken for one order arrives before OrderPlaced for another. When an event can still arrive early (events from two different producers about the same order can race), a consumer should either buffer it or store it and reconcile later, rather than crash.

Eventual consistency in the user interface

Events are asynchronous, so a read model is updated a moment after the write that caused it. The user, meanwhile, has just clicked a button and expects to see the result. If the page reloads and the order is missing from "My orders", the user places it again. This is the read-your-own-writes problem from data chapter 15 with replicas, appearing again with events, and the fixes are the same family:

  • Return the result of the write directly. The command's response includes the new order (from the write side), and the UI renders that instead of re-querying a read model that may not have it yet.
  • Optimistic UI. The client shows the new state immediately and reconciles when the confirmed data arrives, showing an error and rolling back if the command is rejected.
  • Version or position tokens. The write returns the version (or log position) it produced. Subsequent reads pass it along, and the read side waits briefly, or serves from the write side, until it has caught up to at least that version.
  • Honest status. If the work really will take a while (payment, shipping), say so: "Order received, we're processing it", with a status that moves through states. This is also the user-visible face of a saga (chapter 15).
  • Read from the write side for the writer. Route the user's own recent reads to the source of truth for a short window.

Common misconception

"Eventually consistent" is not an excuse for "sometimes wrong". The system must still converge, and the user interface must not mislead in the meantime. A button that says "Paid" while the payment is still pending, or a list that silently omits the order you just placed, is a design bug even though every component behaved correctly. Decide per screen how stale it may be, and design that screen for it.

Seeing what is happening

The price of loose coupling is that a request no longer has a single call stack. One click causes events in five services over several seconds. To debug it you need to reconstruct the chain after the fact.

  • Correlation id. Generate an identifier when a flow starts (a request id, an order id) and copy it into every event and every log line produced because of it. Searching logs for one id then shows the whole story across services. Add a causation id (the id of the event that directly triggered this one) to rebuild the tree rather than just the set. Standard formats exist for this, such as the W3C Trace Context headers for tracing and the CloudEvents envelope for event metadata.
  • Distributed tracing. Propagate trace context through messages as well as HTTP calls, so a tracing tool can draw the timeline: producer span, time spent in the broker, consumer span.
  • An event catalog. A browsable list of every event: its name, owner, schema, a description, who is known to consume it. Without one, the question "can I change this field?" is unanswerable. Specifications such as AsyncAPI exist to describe event-driven interfaces in a machine-readable way, much as OpenAPI does for HTTP.
  • Dead-letter queues and lag metrics. Messages that repeatedly fail go to a quarantine you can inspect, rather than blocking the stream or being silently dropped; consumer lag shows when a consumer is falling behind (data chapter 19).

Event spaghetti

The characteristic failure of an over-eager event-driven design is event spaghetti: dozens of event types, each consumed by a different combination of services, services that react to events by publishing events that other services react to, and cycles (A reacts to B's event, B to A's) that nobody drew. Symptoms: nobody can list who consumes an event; a "simple" change needs a survey of the whole company; an incident starts with "something is publishing a lot of OrderUpdated events"; and ordering bugs appear only in production. The cure is not to abandon events but to apply restraint: publish few, well-named public events; give multi-step processes an orchestrator; keep a catalog; and be able to answer "who consumes this?" with a command, not a meeting.

Common misconception

"Event-driven" does not mean "everything goes through the broker". A synchronous call is the right tool when the caller needs the answer now, such as checking a price before showing it. Events fit best for things that have happened and need to propagate. Replacing every request/response with a pair of events usually just turns a call stack you could debug into a distributed puzzle you cannot (see chapter 13).

Try it in code: the same flow, then a change

This program has a tiny in-process event bus. The bus queues events and delivers each to its subscribers in order; each service declares which events it reacts to. First the checkout flow is choreographed. Then a fraud check is added, in both styles. The code measures how many existing services had to change in each. Note that this is a toy: the "services" are stubs that always succeed, and real ones would be separate processes.

from collections import defaultdict, deque
from dataclasses import dataclass


@dataclass(frozen=True)
class Event:
    type: str
    order_id: int
    corr: str          # correlation id: ties every event of one flow together


class Bus:
    """In-process pub/sub: publish() queues, run() delivers in FIFO order."""
    def __init__(self):
        self.subs = defaultdict(list)    # event type -> [(service, handler)]
        self.queue, self.trace = deque(), []

    def subscribe(self, service, etype, handler):
        self.subs[etype].append((service, handler))

    def publish(self, event):
        self.queue.append(event)

    def run(self):
        while self.queue:
            ev = self.queue.popleft()
            for service, handler in self.subs[ev.type]:
                self.trace.append(f"{ev.type:<14} -> {service}")
                handler(ev)


def build_choreography(with_fraud=False):
    bus = Bus()
    pub = bus.publish
    out = lambda t: (lambda e: pub(Event(t, e.order_id, e.corr)))
    # each service decides for itself which events it reacts to
    pay_trigger = "OrderCleared" if with_fraud else "OrderPlaced"
    bus.subscribe("payment",   pay_trigger,     out("PaymentTaken"))
    bus.subscribe("inventory", "PaymentTaken",  out("StockReserved"))
    bus.subscribe("shipping",  "StockReserved", out("ShipmentBooked"))
    bus.subscribe("notify",    "ShipmentBooked", lambda e: None)
    if with_fraud:
        bus.subscribe("fraud",  "OrderPlaced",   out("OrderCleared"))
        bus.subscribe("notify", "OrderRejected", lambda e: None)   # notify had to change too
    return bus


def wiring(bus):
    table = defaultdict(set)
    for etype, subs in bus.subs.items():
        for service, _ in subs:
            table[service].add(etype)
    return table


class Orchestrator:
    """One place that knows the whole flow; services only obey commands."""
    def __init__(self, steps, services):
        self.steps, self.services, self.trace = steps, services, []

    def run(self, order_id, corr):
        for command, service in self.steps:
            self.trace.append(f"{command:<12} -> {service}")
            if not self.services[service](command, order_id):   # a refusal stops the flow
                self.trace.append(f"{'stopped':<12} at {service}")
                return False
        return True


FLOW_V1 = [("TakePayment", "payment"), ("ReserveStock", "inventory"),
           ("BookShipment", "shipping"), ("SendReceipt", "notify")]
FLOW_V2 = [("ScreenOrder", "fraud")] + FLOW_V1


if __name__ == "__main__":
    v1, v2 = build_choreography(False), build_choreography(True)
    v1.publish(Event("OrderPlaced", 42, "c-42")); v1.run()
    print("choreography v1 trace:"); print("\n".join("  " + t for t in v1.trace))

    w1, w2 = wiring(v1), wiring(v2)
    changed = sorted(s for s in w1 if w1[s] != w2[s])
    print("\nadding a fraud check, choreography:")
    print("  existing services whose subscriptions changed:", changed)
    print("  brand-new services:", sorted(set(w2) - set(w1)))

    services = {name: (lambda cmd, oid: True)
                for name in ("payment", "inventory", "shipping", "notify", "fraud")}
    o2 = Orchestrator(FLOW_V2, services)
    o2.run(42, "c-42")
    print("\nadding a fraud check, orchestration:")
    print("  lines changed in the flow definition:", len(FLOW_V2) - len(FLOW_V1))
    print("  existing services changed: none")
    print("orchestrator v2 trace:"); print("\n".join("  " + t for t in o2.trace))

The choreographed version needed two existing services edited and one new one: Payment's trigger moved from OrderPlaced to OrderCleared, and Notification had to learn about OrderRejected. The orchestrated version needed one added line in the flow definition and one new service, and no existing service changed. Neither is "better": the orchestrator is where the cost of change was concentrated, and in a real system that also means it is where the risk and the review attention concentrate. What you should take away is the shape of the cost: choreography spreads change across the system, orchestration gathers it in one place.

Distributed systems connection

Events turn the question "how do services talk?" into "how does the system agree on what has happened?". At-least-once delivery, per-key ordering, consumer lag and replay are the practical face of problems the networking and data courses studied: unreliable networks (networking chapter 16), logs as the backbone of replication (data chapter 19), and eventual consistency (data chapter 15). The next chapter takes the hardest case of choreography versus orchestration, a business transaction that spans several services and cannot use a database transaction, and shows how to make it survive failure. The planned Distributed Systems Deep course goes further, into the theory of ordering events across machines and agreeing on them.

Key takeaways

  • An event is a past-tense fact owned by its producer; a command is a request to one receiver who may refuse. If the producer is waiting for something to happen, it is a command.
  • "Event-driven" covers four patterns: notification and event-carried state transfer (messaging), event sourcing and CQRS (storage and read models). Ask which one is meant.
  • Notification keeps one source of truth but leaves a call-back dependency; state transfer removes the dependency and creates stale copies.
  • A broker holds messages until acknowledged; a log keeps them and lets each reader track its own offset. Facts that many consumers, including future ones, will want suit a log.
  • Choreography spreads the flow across subscriptions (loose coupling, a hidden workflow); orchestration puts it in one place (visible, but a central dependency). Reactions suit the first, business processes the second.
  • Treat events as contracts: business-language names, one event per fact, ids plus the facts true at the time, versioned schemas, and a deliberate public subset.
  • At-least-once means idempotent consumers; ordering is per key; the UI must be designed for stale reads; correlation ids and an event catalog keep the system debuggable.

  2. Only the Order service
  3. The Payment service's trigger (and any service that must now handle a rejection), plus a new Fraud service
  4. Only the message broker's configuration
With no central definition of the flow, the order is encoded in each service's subscription. To insert a step, the service that used to react to OrderPlaced must now react to the fraud outcome, and anyone who needs to know about a rejection must subscribe to it. An orchestrator would change in one place.

Your broker delivers at least once. Which design is correct for a consumer that adds each payment event's amount to a balance?

  1. Assume each event arrives exactly once, since the broker is reliable
  2. Process events in any order and ignore ids
  3. Turn off retries so duplicates cannot happen
  4. Store the ids of handled events (in the same transaction as the balance update) and skip any id already seen
At-least-once delivery means duplicates are normal, and turning off retries would trade duplicates for lost events. Recording event ids atomically with the state change makes handling idempotent. Without that, a redelivered event would be added to the balance twice.

A user submits an order, is redirected to "My orders", and the order is missing for a second. Which fix addresses this without giving up asynchronous updates to the read model?

  1. Make the page poll the broker directly
  2. Have the command return the new order (or a version token) so the UI can show it or the read side can wait until it has caught up
  3. Delete the read model and query the write database for every screen
  4. Tell users to refresh the page
The goal is read-your-own-writes: returning the write's result, optimistic UI or a version token let the writer see their change even while the projection lags. Dropping the read model gives up its benefits, and asking users to refresh just hides the problem.

Why should a team usually not publish every internal domain event, or raw database row changes, as its public integration events?

  1. Brokers cannot carry more than a few event types
  2. Public events must always be in the present tense
  3. Consumers will come to depend on them, so internal modelling and table layouts become a public contract that is hard to change
  4. Internal events are always larger than public ones
Everything a consumer can observe becomes something it may depend on (Hyrum's law). Keeping internal events private and mapping a small, stable, deliberately designed set to the outside preserves your freedom to change the inside. There is no broker limit on event types, and event names are past tense both inside and out.

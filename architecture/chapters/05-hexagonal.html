Layers, Hexagonal & Clean Architecture

Most applications start as three tidy layers and slowly turn into a tangle in which the business rules cannot be run, tested or changed without a database and a web server. This chapter explains the one idea that prevents that, the dependency rule, in the three costumes it wears (layers done right, hexagonal, clean), and then builds it in about a hundred lines of Python you can run.

Why this matters

Frameworks, databases and message brokers change on a timescale of years. Your business rules (what counts as a valid order, when a refund is allowed) are what the company actually owns, and they change for business reasons. If the two are tangled together, every technology upgrade becomes a business-logic rewrite and every business change drags in a database migration. Keeping policy independent of mechanism is the single most useful structural decision in an application, and it is also what makes the code testable (chapter 7), splittable into services later (chapter 11) and understandable by someone who has not read all of it (chapter 1). It is also the most over-applied idea in the field, so we will be careful to say when not to do it.

Where most of us start: layered architecture

The classic structure, taught for decades, is the layered architecture. Code is sorted into horizontal layers, and each layer may use the one directly below it:

  • Presentation: handles the outside world's requests (web controllers, screens, a command line) and turns them into calls.
  • Business (or "service" or "domain" layer): the rules of the application.
  • Data access: reads and writes the database.

Layers have real virtues. They are easy to explain and to draw on a whiteboard. They give every file an obvious home, they are the default shape of most web frameworks, and they let a team split work by skill (front end, business, database). For a small application they are completely adequate. Do not let anyone shame you out of them.

The failure mode: the arrow points the wrong way

Look at the arrows. In a strict layered design the business layer calls down into data access, so its source code imports data-access code. The thing that contains your rules depends on the thing that talks to the database. Over a few years this produces a predictable decay:

  • The data layer returns ORM model objects, so the business layer manipulates objects that know how to save themselves and lazily load their relations. Business code starts triggering queries without meaning to.
  • A rule needs speed, so someone pushes it into SQL ("WHERE status = 'ON_HOLD'", a trigger, a stored procedure, a CASE expression). Now the rule lives in two places and only one of them is tested.
  • The only way to test a business rule is to start a database, seed it and clean up afterwards. Tests are slow, so fewer are written.
  • Changing database (or splitting out a service) means rewriting the business layer, because it is shot through with the old database's habits.

Here is a tiny, honest example of that decay. The "business" function below looks innocent. It is also impossible to run without SQLite, and one of its rules ("orders over 500.00 start on hold") is hidden inside the SQL string:

# before.py: the classic layered version. The "business" layer talks SQL.
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE orders (id INTEGER PRIMARY KEY, customer TEXT, total_cents INTEGER, status TEXT)")

def place_order(customer, items):             # "business layer"
    total = sum(qty * price for qty, price in items)
    if total == 0:
        raise ValueError("empty order")
    # the rule 'big orders start on hold' lives inside the SQL string:
    cur = db.execute(
        "INSERT INTO orders (customer, total_cents, status) "
        "VALUES (?, ?, CASE WHEN ? > 50000 THEN 'ON_HOLD' ELSE 'NEW' END)",
        (customer, total, total))
    return cur.lastrowid

print(place_order("ana", [(2, 1500)]), place_order("ben", [(1, 60000)]))
print(db.execute("SELECT id, status FROM orders").fetchall())
1 2
[(1, 'NEW'), (2, 'ON_HOLD')]

It works. The trouble is what you cannot do. You cannot test the on-hold rule without a database, you cannot reuse it from a nightly import job that writes somewhere else, and a reader has to parse SQL to learn a business rule. Nothing here is wrong in isolation, which is exactly why it is so common: the damage accumulates one reasonable shortcut at a time.

Analogy: the lamp and the wall socket

A lamp does not care whether its electricity comes from a coal plant, solar panels or a generator in a field. It cares about one thing: a socket of the right shape. The lamp's design is stable; the supply behind the wall can change completely. A layered design with the business layer on top of the data layer is like soldering the lamp's wires directly to one particular power station. It works until the day you want a different supplier, or want to test the lamp in a room with no power.

Where it breaks down: a physical socket is a standard shape agreed by an industry. In software you design the socket yourself, around what your own application needs, and a poorly shaped one (a socket that only fits one brand of plug) is the most common way this idea goes wrong.

The dependency rule

The cure is to change which way one kind of arrow points. It is stated best in Robert C. Martin's clean-architecture writing, and it fits in one sentence:

The dependency rule

Source-code dependencies point inward, toward policy. Code in an inner circle (business rules) must not name anything in an outer circle (databases, web frameworks, message brokers, UI toolkits). Inner code does not import it, call it by name, or even know it exists.

Two words need care. A source-code dependency is an import (or a use, require, a class name in a type annotation): module A depends on module B if A's text has to mention B, so that A cannot be compiled, imported or tested without B. This is not the same as control flow, which is who calls whom while the program runs. Running code will certainly go from your business rules into the database, because that is how data gets saved. The rule says nothing about that. It says the text of the business rules never names the database. Holding those two directions apart in your head is the whole chapter, and the stepper below makes it visible.

The second word is policy: the rules that make your application your application (a customer cannot order more than ten of one item; a refund after 30 days needs approval). Policy is the stable, valuable, business-owned part. Mechanism or detail is how it gets done: which database, which HTTP framework, which queue. Details are replaceable and change on technology's schedule. The rule says details depend on policy, never the reverse.

Dependency inversion: who owns the interface

"But the business rules have to save the order!" Yes, and the trick that lets them do so without naming the database is called the dependency inversion principle (the D in Martin's SOLID): high-level policy should not depend on low-level detail; both should depend on an abstraction, and the abstraction belongs to the high-level side.

In practice, the business code declares, in its own terms, what it needs: "I need something that can save(order) and get(order_id)." That declaration is a port. It is a plain interface (in Python a typing.Protocol or an abstract base class) that lives in the inner circle and speaks the business's vocabulary, not SQL's. The database code then implements that interface; the implementation is an adapter, because it adapts the outside technology to the shape the core asked for.

The word "inversion" is exactly this flip. Before, the dependency pointed the same way as the control flow (use case to repository). After, control flow still goes from use case to repository, but the dependency of the repository is reversed: it points at the use case's interface. Somebody still has to create the real adapter and hand it to the use case. That somebody lives in the outermost circle, usually main, and is called the composition root: the one place that is allowed to know every concrete class and wire them together. Passing the adapter into the use case's constructor (as opposed to the use case creating it) is called dependency injection; chapter 4 covered the mechanics.

Common misconception

"Dependency inversion means putting an interface in front of everything." No. It means the owner of an interface is the code that uses it. An IOrderRepository interface that lives in the database package, mirrors the ORM's methods and is imported by business code has added a file and inverted nothing. Ask who defines the shape: if it is the data layer, the dependency still points outward.

Hexagonal architecture: ports and adapters

Alistair Cockburn described this arrangement around 2005 under the name hexagonal architecture, also called ports and adapters. The hexagon is only a drawing trick: it has many sides, so you can draw several ports without implying a top and a bottom the way a stack of layers does. The idea is: the application is a core surrounded by ports; anything outside (a browser, a test, a database, a payment provider) plugs into a port through an adapter.

Cockburn made one distinction that is worth remembering, because it fixes the confusion about which way arrows point:

Driving (primary) sideDriven (secondary) side

Analogy: a restaurant kitchen

A restaurant kitchen (the core) works from order tickets. It does not care whether a ticket came from a waiter, a phone call or a delivery app: each arrives through a standard ticket printer (the driving port). In the other direction, the kitchen asks the pantry for "two kilos of flour" in its own words, and a supplier (an adapter) fulfils that from whichever wholesaler is cheapest this month. Switching wholesaler never changes a recipe; adding a delivery app never changes the stove.

Where it breaks down: real kitchens are shaped by their suppliers and equipment (a wood oven changes the menu). Software cores are shaped by their ports too, and an honest design admits that the "swappable" technologies you will really swap are far fewer than the ones you could in theory.

One request, in and out

The central insight deserves its own animation. Follow one POST /orders through the system below. The solid arrows are control flow (who is running, and who it calls next). The dashed teal arrows are source-code dependencies (who imports whom). Watch the driven side: on step 5, control goes out to the SQL adapter, but the dependency arrow points in. That mismatch is the entire design.

Step through

A request goes in and out; the dependencies only point in

  1. A request arrives. The client sends POST /orders with a JSON body. Nothing in our code has run yet. Everything in the picture to the right of the client is ours.
  2. The driving adapter translates. The HTTP adapter parses the body into plain values (a customer id and a list of lines) and calls the PlaceOrder use case. Notice the solid and dashed arrows agree: the adapter calls the core and also imports it. It is the adapter that knows about the core, never the reverse.
  3. The use case consults the domain. PlaceOrder asks the Order to place itself. The domain checks the business rules (not empty, at most ten units per line, big orders go on hold). It is pure Python: no I/O, no imports from outside the core.
  4. Control goes out through a port: payment. The use case calls PaymentGateway.charge(...). It holds a reference to the port, so at run time the call lands in whichever adapter was injected: a real provider client in production, a fake in tests. The dashed arrow below the port points up: the adapter imports the port.
  5. Control goes out through a port: storage. The use case calls OrderRepository.save(order). The call descends into the SQL adapter, which opens a transaction and writes rows. The call travelled outward, away from the centre.
  6. Now read the dashed arrows. The SQL adapter and the payment adapter each import the port that the core defines. So although control left the core, the source code of the core still imports nothing from SQL or the payment provider. Delete the adapters and the core still imports, runs and passes its tests.
  7. The result flows back in. The adapter returns, the port returns, and the use case returns the saved Order to the HTTP adapter. Control flow goes in and out like a breath; dependencies never change direction.
  8. The driving adapter builds the response. The HTTP adapter maps the outcome to a status code (201 for success, 422 for a broken rule, 402 for a declined payment) and a JSON body. Translating in both directions, request in and response out, is the whole job of an adapter.

Clean architecture and the onion: the same idea, in circles

Robert C. Martin's clean architecture (a 2012 blog post, later a book) draws the same idea as concentric circles. Jeffrey Palermo's onion architecture (around 2008) is a very close relative, and Cockburn's hexagon came first. Their vocabularies differ, but the structure is one idea: a domain-centred core that depends on nothing, surrounded by layers that depend inward.

IdeaHexagonal (Cockburn)Onion (Palermo)Clean (Martin)In our example

Be honest with yourself and your team about this: these are variations on one idea, not rival methodologies. Arguments about "is this hexagonal or clean?" are rarely productive. The shared claims are the same, and they are what you should check in code review: the domain imports nothing from outside it; the use cases depend on the domain and on interfaces they own; the technology is on the outside and depends in; and wiring happens in one place. The circles give you a vocabulary for talking about it. The exact number of rings (three, four, five) is cosmetic.

Go deeper: where does the "application service" end and the domain begin? optional

Practitioners differ on how much logic belongs in a use case versus a domain object. A common rule of thumb (it is a convention, not a law): the domain holds rules that would be true no matter how the system is triggered (an order cannot be empty; a paid order cannot gain items). The use case holds orchestration: load this, ask the domain to do that, charge the card, save, publish. If a use case is full of if statements about business rules, the domain is anaemic; if a domain object calls a repository, the domain has reached outward. In our example Order.place decides whether a big order goes on hold (a rule) and PlaceOrder.__call__ decides to charge only if it did not (a workflow). Chapter 6 develops the domain side properly.

The worked example: place an order

Now let us build it. The listing is one file so you can read it top to bottom, but each section has a different "ring" and, in a real project, would be its own module: domain.py, ports.py, use_cases.py, adapters/ and main.py. The only thing the domain section imports is the standard library.

Read it in this order: the domain (rules, no I/O), the ports (what the core needs, in its own words), the use case (orchestration against the ports), then the adapters (SQL, in-memory, a fake payment gateway, an HTTP-ish function), and finally the composition root.

# orders.py: one use case, two ports, three adapters, one composition root.
from __future__ import annotations
import sqlite3
from dataclasses import dataclass, field
from typing import Protocol


# ───────────── domain (imports nothing from this project) ─────────────
class EmptyOrder(Exception): ...
class TooManyUnits(Exception): ...

@dataclass(frozen=True)
class Line:
    sku: str
    qty: int
    unit_price_cents: int

@dataclass
class Order:
    id: str
    customer_id: str
    lines: list[Line] = field(default_factory=list)
    status: str = "NEW"

    @property
    def total_cents(self) -> int:
        return sum(l.qty * l.unit_price_cents for l in self.lines)

    @classmethod
    def place(cls, order_id: str, customer_id: str, lines: list[Line]) -> "Order":
        if not lines:
            raise EmptyOrder("an order needs at least one line")
        if any(l.qty < 1 or l.qty > 10 for l in lines):
            raise TooManyUnits("each line must have 1 to 10 units")
        order = cls(order_id, customer_id, lines)
        if order.total_cents > 50_000:          # business rule: big orders wait for review
            order.status = "ON_HOLD"
        return order


# ───────────── ports (owned by the core) ─────────────
class OrderRepository(Protocol):
    def next_id(self) -> str: ...
    def save(self, order: Order) -> None: ...
    def get(self, order_id: str) -> Order | None: ...

class PaymentGateway(Protocol):
    def charge(self, customer_id: str, amount_cents: int) -> bool: ...


# ───────────── use case (application service) ─────────────
class PaymentDeclined(Exception): ...

class PlaceOrder:
    def __init__(self, orders: OrderRepository, payments: PaymentGateway):
        self._orders, self._payments = orders, payments

    def __call__(self, customer_id: str, lines: list[Line]) -> Order:
        order = Order.place(self._orders.next_id(), customer_id, lines)
        if order.status == "NEW" and not self._payments.charge(customer_id, order.total_cents):
            raise PaymentDeclined(f"payment declined for {customer_id}")
        self._orders.save(order)
        return order


# ───────────── driven adapters ─────────────
class InMemoryOrders:
    def __init__(self): self._rows: dict[str, Order] = {}
    def next_id(self) -> str: return f"o-{len(self._rows) + 1}"
    def save(self, order: Order) -> None: self._rows[order.id] = order
    def get(self, order_id: str) -> Order | None: return self._rows.get(order_id)

class SqliteOrders:
    def __init__(self, conn: sqlite3.Connection):
        self._c = conn
        conn.executescript("""
            CREATE TABLE IF NOT EXISTS orders (id TEXT PRIMARY KEY, customer_id TEXT, status TEXT);
            CREATE TABLE IF NOT EXISTS order_lines (order_id TEXT, sku TEXT, qty INTEGER, unit_price_cents INTEGER);
        """)
    def next_id(self) -> str:
        (n,) = self._c.execute("SELECT COUNT(*) FROM orders").fetchone()
        return f"o-{n + 1}"
    def save(self, order: Order) -> None:
        with self._c:                              # one transaction: header + lines
            self._write(order)
    def _write(self, order: Order) -> None:        # the SQL, with no transaction of its own
        self._c.execute("INSERT OR REPLACE INTO orders VALUES (?, ?, ?)",
                        (order.id, order.customer_id, order.status))
        self._c.execute("DELETE FROM order_lines WHERE order_id = ?", (order.id,))
        self._c.executemany("INSERT INTO order_lines VALUES (?, ?, ?, ?)",
                            [(order.id, l.sku, l.qty, l.unit_price_cents) for l in order.lines])
    def get(self, order_id: str) -> Order | None:
        row = self._c.execute("SELECT customer_id, status FROM orders WHERE id = ?", (order_id,)).fetchone()
        if row is None:
            return None
        lines = [Line(*r) for r in self._c.execute(
            "SELECT sku, qty, unit_price_cents FROM order_lines WHERE order_id = ?", (order_id,))]
        return Order(order_id, row[0], lines, row[1])

class FakePayments:
    """Test double: approves unless the customer is in `declined`; remembers every charge."""
    def __init__(self, declined: set[str] | None = None):
        self.declined, self.charges = declined or set(), []
    def charge(self, customer_id: str, amount_cents: int) -> bool:
        self.charges.append((customer_id, amount_cents))
        return customer_id not in self.declined


# ───────────── driving adapter: parse a dict, call the use case, build a response ─────────────
def post_order(body: dict, place_order: PlaceOrder) -> tuple[int, dict]:
    try:
        lines = [Line(i["sku"], int(i["qty"]), int(i["unit_price_cents"])) for i in body["items"]]
        order = place_order(str(body["customer_id"]), lines)
    except (KeyError, TypeError, ValueError):
        return 400, {"error": "malformed request"}
    except (EmptyOrder, TooManyUnits) as e:
        return 422, {"error": str(e)}
    except PaymentDeclined as e:
        return 402, {"error": str(e)}
    return 201, {"id": order.id, "status": order.status, "total_cents": order.total_cents}


# ───────────── composition root: the only place that names concrete classes ─────────────
def build(use_sqlite: bool) -> PlaceOrder:
    repo = SqliteOrders(sqlite3.connect(":memory:")) if use_sqlite else InMemoryOrders()
    return PlaceOrder(repo, FakePayments(declined={"mallory"}))

if __name__ == "__main__":
    request = {"customer_id": "ana", "items": [{"sku": "mug", "qty": 2, "unit_price_cents": 1500}]}
    for use_sqlite in (False, True):
        print("sqlite" if use_sqlite else "memory", post_order(request, build(use_sqlite)))
    print("declined", post_order({**request, "customer_id": "mallory"}, build(False)))
    print("empty   ", post_order({"customer_id": "ana", "items": []}, build(False)))
    print("garbage ", post_order({"oops": 1}, build(False)))

Things worth noticing before we run it:

  • OrderRepository and PaymentGateway are typing.Protocol classes: structural interfaces. SqliteOrders never inherits from OrderRepository; it just has the right methods. That means an adapter does not even have to import the port to satisfy it (it still imports the domain types it maps, such as Order), and a type checker such as mypy will still verify the match.
  • The port speaks the core's language: save(order) takes an Order, not a row or a dict. Mapping an Order to two tables is the adapter's problem.
  • post_order is the driving adapter. It takes a dict (what a web framework would hand you after parsing JSON), turns it into plain values, calls the use case, and translates exceptions to status codes. It knows nothing about SQL and the use case knows nothing about status codes.
  • build() is the composition root, the only place that names both SqliteOrders and InMemoryOrders. Everything else receives collaborators through constructors.
  • The "on hold" rule from the before.py example now lives in Order.place as a line of Python rather than in a CASE expression.

The in-memory run and the SQLite run produce the same response, and nothing inside the core changed between them. Now the payoff: tests for the core, running against fakes, no database anywhere.

import sqlite3, unittest
from orders import (EmptyOrder, FakePayments, InMemoryOrders, Line, PaymentDeclined,
                    PlaceOrder, SqliteOrders, TooManyUnits, post_order)

MUG = Line("mug", 2, 1500)

class PlaceOrderTests(unittest.TestCase):          # the core, with fakes: no DB, no network
    def setUp(self):
        self.repo, self.pay = InMemoryOrders(), FakePayments(declined={"mallory"})
        self.place = PlaceOrder(self.repo, self.pay)

    def test_saves_and_charges_the_total(self):
        order = self.place("ana", [MUG])
        self.assertEqual(self.repo.get(order.id), order)
        self.assertEqual(self.pay.charges, [("ana", 3000)])

    def test_big_orders_are_held_and_not_charged_yet(self):
        order = self.place("ben", [Line("tv", 1, 60_000)])
        self.assertEqual(order.status, "ON_HOLD")
        self.assertEqual(self.pay.charges, [])

    def test_declined_payment_saves_nothing(self):
        with self.assertRaises(PaymentDeclined):
            self.place("mallory", [MUG])
        self.assertIsNone(self.repo.get("o-1"))

    def test_rejects_empty_and_oversized_lines(self):
        with self.assertRaises(EmptyOrder): self.place("ana", [])
        with self.assertRaises(TooManyUnits): self.place("ana", [Line("mug", 11, 1500)])

class RepositoryContract:                          # one suite, run against every adapter
    def make_repo(self): raise NotImplementedError
    def test_round_trip(self):
        repo = self.make_repo()
        order = PlaceOrder(repo, FakePayments())("ana", [MUG, Line("pen", 1, 200)])
        self.assertEqual(repo.get(order.id), order)
    def test_missing_is_none(self):
        self.assertIsNone(self.make_repo().get("nope"))
    def test_ids_advance(self):
        repo = self.make_repo(); place = PlaceOrder(repo, FakePayments())
        self.assertEqual([place("a", [MUG]).id, place("b", [MUG]).id], ["o-1", "o-2"])

class InMemoryContract(RepositoryContract, unittest.TestCase):
    def make_repo(self): return InMemoryOrders()
class SqliteContract(RepositoryContract, unittest.TestCase):
    def make_repo(self): return SqliteOrders(sqlite3.connect(":memory:"))

class HttpAdapterTests(unittest.TestCase):         # parsing and status codes only
    def setUp(self): self.place = PlaceOrder(InMemoryOrders(), FakePayments(declined={"mallory"}))
    def test_maps_outcomes_to_status_codes(self):
        ok = {"customer_id": "ana", "items": [{"sku": "mug", "qty": 2, "unit_price_cents": 1500}]}
        self.assertEqual(post_order(ok, self.place)[0], 201)
        self.assertEqual(post_order({**ok, "customer_id": "mallory"}, self.place)[0], 402)
        self.assertEqual(post_order({**ok, "items": []}, self.place)[0], 422)
        self.assertEqual(post_order({"nonsense": True}, self.place)[0], 400)

if __name__ == "__main__":
    unittest.main()

Four things are going on here. PlaceOrderTests exercises the whole business flow using InMemoryOrders and FakePayments; these tests do no I/O, so thousands of them would run in a blink. RepositoryContract is one test suite that is mixed into two TestCase classes, so the in-memory adapter and the SQLite adapter must both satisfy the same behavioural contract. That is how you keep a fake honest: if the fake and the real adapter pass the same tests, the fake cannot drift. HttpAdapterTests checks only parsing and status codes. Run them:

Common misconception

"Hexagonal architecture is about being able to swap the database." Almost nobody swaps their database. The practical benefits are different and arrive much sooner: the core is testable in microseconds, you can run the same use case from an HTTP handler, a queue consumer and a command line without copying logic, and you can defer choices (you can write and demonstrate the whole order flow before deciding on storage). Swappability is the least important dividend.

Where do transactions and the outbox go?

The moment you hide persistence behind a port, an awkward question appears: who owns the transaction? Chapter 10 of the data course ( ACID and transactions) showed that atomicity is what makes a group of writes succeed or fail together. A transaction is a persistence concept, so the domain should not mention it. But it is also a business fact: "saving the order and reducing stock happen together or not at all." There are three common places to put the boundary:

WhereHow it looksGood whenWatch out
Inside one repository methodsave(order) opens and commits a transaction (our SqliteOrders.save)One aggregate per use case, the usual caseTwo repository calls in one use case are two transactions

Many experienced engineers prefer the second form once an application grows, because the use case is the unit the business thinks in: one request, one business transaction. Keep the abstraction small. Hiding a transaction behind a three-method interface is useful; re-creating an entire ORM behind your own interface is not.

The same question returns when the use case needs to announce something ("order placed"). Publishing to a broker after the commit can be lost if the process dies in between; publishing before the commit can announce an order that rolled back. This is the dual-write problem from data chapter 19, and its standard cure, the transactional outbox, fits ports and adapters well: the repository adapter writes the event into an outbox table in the same transaction as the order, and a separate relay publishes it later. The core only says "here is an order and here is an event"; atomicity is the adapter's responsibility. Here is a version of our adapter that does it, along with a deliberate failure to prove the two writes share a fate:

import json, sqlite3
from orders import FakePayments, Line, Order, PlaceOrder, SqliteOrders

class SqliteOrdersWithOutbox(SqliteOrders):
    """Same port, same use case. The adapter also writes an event row in the SAME transaction."""
    def __init__(self, conn):
        super().__init__(conn)
        conn.execute("CREATE TABLE IF NOT EXISTS outbox (id INTEGER PRIMARY KEY, payload TEXT, sent INTEGER DEFAULT 0)")
    def save(self, order: Order) -> None:
        with self._c:                                   # one transaction around BOTH writes
            self._write(order)
            self._c.execute("INSERT INTO outbox (payload) VALUES (?)",
                            (json.dumps({"type": "OrderPlaced", "order_id": order.id, "total": order.total_cents}),))

conn = sqlite3.connect(":memory:")
place = PlaceOrder(SqliteOrdersWithOutbox(conn), FakePayments())
place("ana", [Line("mug", 2, 1500)])
print(conn.execute("SELECT id, status FROM orders").fetchall())
print(conn.execute("SELECT payload, sent FROM outbox").fetchall())

# prove atomicity: make the outbox insert fail and check the order write rolled back too
conn2 = sqlite3.connect(":memory:")
repo2 = SqliteOrdersWithOutbox(conn2)
conn2.execute("DROP TABLE outbox")
try:
    repo2.save(Order("o-9", "ana", [Line("mug", 1, 1500)]))
except sqlite3.OperationalError as e:
    print("save failed:", e)
print("orders after failure:", conn2.execute("SELECT COUNT(*) FROM orders").fetchone())

The use case did not change and the port did not change. The second run drops the outbox table so the second write fails; the order write rolled back with it, leaving zero orders. A relay process (data chapter 19) would then read unsent rows and publish them at least once; the consumers must tolerate repeats. Chapter 14 returns to events in depth.

The costs, honestly

Everything above has a price, and the architecture literature sometimes forgets to quote it.

  • More indirection. To find what happens when an order is saved you now follow a call from the use case, through a Protocol, to an adapter chosen in main. Jumping to definition lands on the interface, not the code that runs. Small teams feel this as friction.
  • Mapping between layers. The domain Order, the database row, and the JSON body are three different shapes of the same fact, and code must translate between them (see SqliteOrders.get). It is boilerplate, it can get out of sync, and it slows every field you add.
  • Over-engineering for CRUD. If your application is "validate a form, store it, show it again," there are no business rules to protect. Wrapping it in use cases, ports, entities and mappers triples the number of files while protecting nothing.
  • Premature abstraction. Interfaces drawn before you understand what varies tend to be the wrong interfaces. A port with a single implementation that mirrors the ORM's API is ceremony, not independence.
  • Performance blind spots. A repository that returns whole aggregates can make a bulk report awkward or slow. Reporting and bulk operations often deserve a separate, thinner read path (chapter 16 on CQRS).

A useful middle path: start layered, and apply the dependency rule only to the one dependency that hurts first. For most applications that is the database (the thing that makes tests slow), so put a repository port in front of it. Add the next port when a second reason appears. You do not need the whole hexagon to get most of the value.

Analogy: a city and its zoning

Think of the codebase as a city. A good city plan puts the stable, valuable parts (the old town: your domain) where changes are slow and deliberate, and lets the busy edge (ring roads, industrial estates: frameworks and infrastructure) change quickly without demolishing the centre. The zoning rule is "the old town never has a road that only exists for one factory." A small village does not need zoning laws; a metropolis cannot function without them.

Where it breaks down: real cities grow organically over centuries and zoning is enforced by officials. Code boundaries are enforced only if you build the enforcement (a lint rule or import-check test in CI, which Lab 3 has you write); otherwise they erode quietly.

Distributed systems connection

The dependency rule is the single-process version of two ideas you will meet repeatedly. First, a port is a contract: chapter 3's interfaces, chapter 9's APIs and chapter 10's compatibility rules are the same idea at larger scale, and an adapter that translates between the core's model and an outside model is what domain-driven design calls an anti-corruption layer (chapter 6). Second, a core that does not know how it is stored, triggered or delivered is exactly what lets you move it. A well-isolated core can be extracted into a service with little more than a new driving adapter (a message consumer instead of an HTTP handler) and a new driven adapter (a client in place of an in-process call); a core tangled with its database can only be extracted by rewriting it. The outbox in this chapter is also the first appearance of a theme that dominates the later parts of this course: crossing a process boundary reliably needs a plan for atomicity, duplicates and failure, which is why chapter 7 shows how fakes let you test those failure modes cheaply, and why the networking course's chapter on failure (network chapter 16) keeps coming back.

Key takeaways

  • Layered architecture is simple and fine for small apps. Its failure mode is that business logic sits on top of, and so depends on, the data layer, which leaks rules into SQL and the ORM and makes every test need a database.
  • The dependency rule: source-code dependencies point inward, toward policy. This is about imports, not run-time control flow, which freely goes in and out.
  • Dependency inversion: the core defines the interface it needs (a port, in its own vocabulary) and the infrastructure implements it (an adapter). The owner of the interface is the code that uses it.
  • Hexagonal distinguishes driving (primary) ports, through which the outside calls the core, from driven (secondary) ports, which the core calls. A request flows HTTP adapter, use case, domain, repository port, SQL adapter, while the dependency arrows all point inward.
  • Clean and onion architecture are the same idea drawn as rings. Check the four shared claims in review rather than arguing about the labels: a dependency-free domain, use cases against owned interfaces, technology outside, one composition root.
  • Transactions belong in a persistence-facing place (the repository method or a narrow unit of work), and the outbox is naturally an adapter concern: write the event in the same transaction as the data.
  • It has costs: indirection, mapping, and wasted ceremony in CRUD apps. Apply the rule first to the dependency that hurts, usually the database, and grow from there.

In a strict three-layer design (presentation, business, data access), what is the most characteristic way it decays?

Because each layer depends on the one below, the business rules depend on the data layer. That makes it easy for a rule to be pushed into SQL, for ORM models to act as domain objects, and for every business test to need a database. Presentation reaching straight into data is a different shortcut, but it is not the structural problem.

Which statement correctly describes the dependency rule?

The rule concerns source-code dependencies, not control flow. The application certainly calls the database while running; what it forbids is the business code's text naming the database. Option D has it backwards: outer code importing inner code is exactly what the rule allows.

In hexagonal terms, which of these is a driven (secondary) adapter?

Driving adapters start the interaction and call the core: controllers, tests, consumers. Driven adapters are called by the core through a port it defines and carry out the work against external technology: repositories, payment gateways, email senders.

The core calls the port (an interface it owns), and the adapter's source code refers to that port in order to implement it. That reverses the dependency relative to the call. The composition root wires an adapter instance into the use case at start-up, which is the only place the two meet.

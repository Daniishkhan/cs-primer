Start Here

You have learned how bytes cross a network, how one machine runs programs, and how data is stored and kept consistent. This course is about the next question: given all those parts, how do you arrange them, and your own code, so that the system can still be changed in two years by people who were not in the room? That is what software architecture is for.

A note from your mentor

Architecture has a reputation for dogma: "always use microservices", "never repeat yourself", "clean architecture or die". I will not sell you any of it. For every idea in this course I want you to leave knowing what problem it solves, what it costs, and the situation where it is the wrong choice. The goal is not to memorise patterns. It is to be the person in the design review who can say "that will be painful to change, and here is why", and then offer something better.

Why this matters

Most software is not killed by a lack of features or by slow code. It is slowed to a crawl by the cost of change: every new feature takes longer than the last because the pieces are tangled together. Architecture is the discipline of keeping that cost down. It is also what separates a senior engineer's design from a working prototype, and it is the main thing system-design interviews are really probing.

What architecture is (and is not)

Software architecture is the set of design decisions that are expensive to change. A variable name is not architecture, because you can rename it in a minute. The choice of whether two parts of your system share a database is architecture, because undoing it later means migrating data, rewriting code and coordinating several teams.

That definition (a version of which is often attributed to Martin Fowler, among others) is useful because it tells you where to spend your careful thinking. The decisions worth slowing down for fall into five families:

  • Code structure: how the code is divided into modules, and which modules may depend on which.
  • Boundaries: where one part ends and another begins, and what crosses the line.
  • Data ownership: which part is the single owner of each piece of data, and who must ask it nicely.
  • Communication: direct calls, HTTP APIs, queues and events, and what each assumes about timing and failure.
  • Deployment: what ships together, what can be released alone, and what it takes to roll back.

It is not boxes-and-arrows art. A diagram is one way of describing an architecture, but the architecture is the real structure of the code and the running system, whatever the diagram claims. Many diagrams are wishes.

Common misconception

"Architecture means microservices (or some other fashionable pattern)." Fashionable patterns are answers to particular problems. A system with one small team and one database often has a perfectly good architecture that fits in a single deployable program. We will see exactly when that stops being true in chapter 11.

Architects, senior engineers, and a continuous activity

In some companies "architect" is a job title, and the person holding it draws the big picture. In the healthiest teams architecture is not a phase done by one person before coding starts. It is a continuous activity shared by everyone who changes the system. Every pull request that adds a dependency, every database table another team starts reading, every shortcut "just this once" is an architectural decision made by whoever wrote it.

So what does a senior engineer do differently? Mostly they notice the expensive decisions early, they can describe the trade-off in plain words, and they leave a trail (a short written decision, covered in chapter 19) so the next person knows why. They also know when a decision is cheap to reverse and simply make it, because deliberating over reversible choices is its own cost.

The forces in tension

There is no best architecture, only architectures that balance competing forces well for a particular situation. Six of them appear in nearly every design discussion. Each is good, and each is bought at the expense of the others.

Changeability

How cheaply can you add or alter a feature? Usually bought with more indirection: interfaces, layers, configuration.

Performance

Latency and throughput. Often bought by removing indirection, caching, or putting things close together, which makes change harder.

Reliability

Surviving crashes, overload and partial failure. Bought with redundancy, retries and timeouts, all of which add moving parts.

Team autonomy

Can teams ship without asking each other? Bought with strong boundaries and separate deployments, which cost coordination elsewhere.

Simplicity

How much must one head hold? Bought by doing less, and the hardest force to defend because it shows up as an absence.

Cost

Money, people and time, now and later. Every box you add has to be run, monitored and paid for.

"It depends" is the start of an answer

Every experienced engineer answers architecture questions with "it depends". That is correct and, said alone, useless. A good answer has three parts: it depends on what, here is how I would find out, and here is what I would pick under each answer.

For example: "Should we make checkout its own service?" A weak answer is "it depends." A strong one is: "It depends on whether a separate team will own it and release on its own schedule, and whether its load pattern differs sharply from the rest. If neither is true, keep it a module inside the monolith with a clear interface, and revisit when one becomes true. If both are true, a service is worth the operational cost."

One feature request, three architectures

Here is the idea of the whole course in one story. A product manager asks: "Add gift cards to checkout." Customers should be able to pay part of an order with a gift card balance. The same request meets three different architectures. Step through and watch where the change lands, and what each design charges you for it.

Step through

The same feature, three ways

  1. The request. "Add gift cards to checkout": part of an order can be paid from a stored balance. Notice that nothing in the request says which architecture to use. The feature is the same; the cost of the change is not.
  2. A tangled script. One big file where totals, discounts, tax, payment, emails and reports all reach into each other's variables. Gift cards touch every one of them, because each makes assumptions about "the total" that a gift card breaks (is tax charged before or after the balance is deducted?). Cost: this is the cheapest version to build for the first feature, and the most expensive for the tenth. You cannot predict what else breaks, so you test everything.
  3. A modular monolith. One program, but divided into modules with narrow interfaces. Gift cards become a new module; checkout makes one new call through its interface. Everything else is untouched. Cost: someone had to draw those boundaries earlier and keep them honest, and you still deploy the whole program for every change.
  4. Microservices. Gift cards become a separate service with its own database. Checkout calls it over HTTP, and it publishes an event that reporting consumes. Cost: an API contract to design and version, a network call that can fail or time out (networking ch. 16), an event to keep consistent with the database (data ch. 19), a new pipeline to build, and releases that have to be ordered. Benefit: a separate team can own and ship it without waiting for anyone.
  5. No universal winner. A is fastest this afternoon and slowest next year. B is usually the best value for one team. C pays off when separate teams and separate scaling needs make the coordination savings larger than the new network and operations bill. Which one is right depends on team size, change rate and how much failure you can absorb, and the rest of the course teaches you to judge that.

Analogy: a city

A software system is like a city. Neighbourhoods are modules or services. Zoning rules are boundaries: what may be built where, and what may talk to what. Roads, and the signs on them, are APIs. Building codes are contracts that everyone agrees to meet. A city that grows with no plan has houses wired into one another's plumbing: any repair means digging up the street. A planned city can rebuild one block without closing the others. We will keep coming back to this picture.

Where it breaks down: cities are rarely rebuilt from scratch, but software can be refactored, and its "buildings" are copied and rewired in seconds. Also, a city's residents are not trying to change the zoning every week; software requirements change constantly, which is why changeability matters so much.

How this course builds on the first three

The earlier courses were not detours; they are the physics under every architecture decision. A few links you will use again and again:

  • When you split a system into services, a function call becomes a network call, and calls that can fail halfway are the central fact of life. That is partial failure and timeouts, and chapter 17 turns it into patterns.
  • A queue between two components is only safe if it pushes back when the consumer is slow. That is backpressure, the foundation for the asynchronous designs in chapter 13.
  • Once data is split across services, you lose transactions that span them. Isolation levels tell you what a single database promised; sagas are what you do when it no longer applies.
  • To publish an event and update a database without losing either, you need the outbox pattern, which returns in chapter 14.

Try it yourself

Try it yourself: find the hard-to-change decisions

Option 1, with a pencil. Take any small project you have: a side project, a school assignment, the app you work on. Write down the decisions that would be expensive to change, grouped by the five families above. Which database does everything talk to? Which modules import which? What data format do two parts agree on? Which of them could you swap in an afternoon, and which would take a month? The month ones are your architecture.

Option 2, with Python. The script below builds a tiny toy package of six modules in a temporary folder, reads the import lines with Python's own parser, and prints who depends on whom. Point it at a real folder of your own code later, by replacing the dictionary with a scan of *.py files. Python 3.9 or newer, standard library only.

import ast, pathlib, tempfile

# A toy "shop" package: module name -> source
TOY = {
    "orders":   "import pricing, inventory, email_sender\n",
    "pricing":  "import tax, customers\n",
    "inventory": "import orders\n",          # a cycle: orders <-> inventory
    "tax":      "",
    "customers": "import email_sender\n",
    "email_sender": "",
}

def imports_of(source: str, known: set[str]) -> set[str]:
    found = set()
    for node in ast.walk(ast.parse(source)):
        if isinstance(node, ast.Import):
            found |= {a.name for a in node.names if a.name in known}
        elif isinstance(node, ast.ImportFrom) and node.module in known:
            found.add(node.module)
    return found

with tempfile.TemporaryDirectory() as d:
    for name, src in TOY.items():
        (pathlib.Path(d) / f"{name}.py").write_text(src)
    known = {p.stem for p in pathlib.Path(d).glob("*.py")}
    graph = {p.stem: imports_of(p.read_text(), known)
             for p in sorted(pathlib.Path(d).glob("*.py"))}

fan_in = {m: sum(m in deps for deps in graph.values()) for m in graph}
for m, deps in graph.items():
    print(f"{m:13} imports {sorted(deps) or '-'}   (imported by {fan_in[m]})")
$ python3 importgraph.py
customers     imports ['email_sender']   (imported by 1)
email_sender  imports -   (imported by 2)
inventory     imports ['orders']   (imported by 1)
orders        imports ['email_sender', 'inventory', 'pricing']   (imported by 1)
pricing       imports ['customers', 'tax']   (imported by 1)
tax           imports -   (imported by 1)

Read the output like an architect. orders depends on three modules, so it changes whenever any of them changes. orders and inventory import each other, a cycle, so neither can be understood or tested without the other. email_sender is imported by two modules, so a change to it is felt in two places. Chapters 1 and 2 give names to exactly these shapes.

Distributed systems connection

Everything in this course is a distributed-systems idea waiting to happen. A module boundary inside one program becomes a network boundary the day you extract it into a service, and then every property of that boundary changes: calls can time out (networking ch. 16), queues must apply backpressure (systems ch. 14), and one transaction becomes several (data ch. 11). The best preparation for distributing a system is to get its boundaries right while it is still in one piece.

Key takeaways

  • Architecture is the set of decisions that are expensive to change: code structure, boundaries, data ownership, communication and deployment. It is not a diagram.
  • It is a continuous activity shared by everyone who changes the system, not a phase owned by one person.
  • Six forces pull against each other: changeability, performance, reliability, team autonomy, simplicity and cost. No design maximises all of them.
  • "It depends" must be finished: depends on what, how to find out, and what to pick under each answer.
  • The same feature costs very different amounts in a tangled script, a modular monolith and microservices. Each is right somewhere, and none is right everywhere.
  • The first three courses are the foundation: partial failure, backpressure, isolation and the outbox all come back as design problems.

Check your understanding

Which of these is the most clearly an architectural decision, as this chapter defines it?

  1. Renaming a local variable for clarity
  2. Choosing a tab width for the codebase
  3. Deciding that the orders and billing parts of a system share one database table
  4. Fixing a typo in an error message
Architecture is the set of decisions that are expensive to change. A shared table couples two parts at the data level, and unpicking it later means migrations and coordination. The other three can be changed in minutes.

In the gift-card story, why does the modular monolith contain the change better than the tangled script?

  1. Its modules talk to each other through narrow interfaces, so most code makes no assumptions about gift-card internals
  2. Modular code is always faster to write the first time
  3. It avoids the need to test anything
  4. It runs on more than one machine
The containment comes from the narrow interface: callers depend on what a module promises, not on how it works. It is not necessarily faster to build initially, it still needs testing, and it normally runs as a single program.

A teammate says, "Should we use microservices? It depends." What makes that a good start rather than a non-answer?

  1. Saying "it depends" shows humility and ends the discussion politely
  2. It means any option is equally fine
  3. It means the decision should be left to the architect
  4. Only if it continues with what it depends on, how to find out, and what to choose in each case
"It depends" is the start of an answer. It becomes useful when you name the deciding factors (team ownership, load shape, failure tolerance), say how you would check them, and commit to a choice under each outcome.

Which of the six forces does extracting a module into its own service most directly improve, and which does it most directly cost?

  1. It improves simplicity and costs team autonomy
  2. It can improve team autonomy and costs simplicity, plus reliability work for new network failures
  3. It improves performance and costs nothing else
  4. It improves nothing, and only costs money
A separate service can be owned and released by one team, which is an autonomy gain. But a function call becomes a network call, so there are more moving parts, more failure modes and more to operate. It rarely improves raw performance, since a network hop is slower than a function call.

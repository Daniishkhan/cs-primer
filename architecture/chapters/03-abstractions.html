Abstractions & Interfaces

Every useful program is built from pieces that hide other pieces. This chapter is about the line between "what you need to know" and "what you should not have to know": how to draw it, how to write it down as a contract, what happens when the hidden part leaks through, and why the way a thing fails is just as much part of its interface as the way it succeeds.

Why this matters

The previous chapter was about where to cut a system into modules. This one is about the surface of each cut. Once other code, or other teams, depend on an interface, you can change what is behind it but never what is in front of it, so the interface is the part of a design that is most expensive to get wrong. Most "architecture" arguments, including the ones in the rest of this course (ports, APIs, service contracts), are really arguments about interfaces. You have also been living with leaky ones since course 0: a reliable stream that stalls, a database library that quietly fires a hundred queries, a "saved" file that vanishes in a power cut.

What an abstraction is

An abstraction is a simplified view of something that leaves out the details that do not matter for the task at hand. A file is an abstraction: you see a named sequence of bytes, not disk sectors and flash wear levelling. A function signature is an abstraction: you see inputs, outputs and a name, not the loops inside. The interface is the part you are allowed to rely on; everything else is the implementation, free to change. This is David Parnas's information hiding (1972) from the last chapter, seen from the caller's side.

The word "good" hides a real judgement. An abstraction is good when it hides the details that change or that the caller cannot use anyway, and shows the ones the caller must decide. A storage interface that asks the caller to choose a B-tree page size hides nothing worth hiding; one that exposes save(order) and get(id) hides the whole database.

Analogy: the city's road signs

Recall our city: modules are neighbourhoods and APIs are the roads and their signs. A good sign says "Station, 2 km" and nothing else. It does not tell you which pipes run under the road or how the traffic lights are wired. Because drivers rely only on the sign, the city can move the station's entrance, repave the road, or rewire the lights without repainting a single map in anyone's car.

Where it breaks down: a sign is read once and obeyed. Software callers also depend on what the sign doesn't say: how slow the road is, what happens in a snowstorm. That unwritten behaviour is exactly what leaks, as we'll see shortly.

Designing an interface

Make the common case simple

Most callers do the same one or two things, so make those trivial and let the rare cases cost a little more. Python's open("notes.txt") reads text with sensible defaults; encodings, buffering and file modes are there when you need them but you do not have to mention them. A useful test: write the code that calls your interface before writing the interface. If the typical call needs five arguments and a setup ritual, the design is upside down.

Say what it does, not how

Name operations in the caller's vocabulary (cart.add(sku)), not the implementation's (cart.items.append([...])). The next section shows the two side by side.

The comment is a contract

The signature tells the caller the types; it does not say what is promised. The written part of an interface, the docstring, should be a contract, the same word as in the city's "building codes". A contract has three parts:

  • Preconditions: what must be true before the call. The caller's obligation ("amount is positive and at most the balance").
  • Postconditions: what will be true after, if the preconditions held. The implementation's promise ("the result equals the balance minus the amount").
  • Invariants: what is true before and after every call, for the object's whole life ("a cart's total always equals the sum of its lines").

This is design by contract, the idea Bertrand Meyer built into the Eiffel language: if the caller keeps its side, the implementation must keep its side, and a violated precondition is a bug in the caller, not something to quietly tolerate. Python has no built-in contract syntax, but plain assert statements document and check the same thing:

def withdraw(balance: int, amount: int) -> int:
    """Contract:
    pre:  amount > 0 and amount <= balance
    post: result == balance - amount and result >= 0
    """
    assert amount > 0, "precondition: amount must be positive"
    assert amount <= balance, "precondition: insufficient funds"
    result = balance - amount
    assert result >= 0, "postcondition"
    return result
print(withdraw(100, 30))
try:
    withdraw(100, 300)
except AssertionError as e:
    print("contract violated by the CALLER:", e)
70
contract violated by the CALLER: precondition: insufficient funds

Common misconception

"Asserts are error handling." They are not. Python removes them under python -O, and they describe bugs, not conditions that legitimately happen at runtime. Use asserts (or just comments) for contracts between your own modules. For input that comes from outside, such as a user, a file or the network, validate explicitly and report a real error.

Types as documentation

Type hints are the machine-checked part of the contract. def get(order_id: str) -> Order | None tells every caller, and a type checker such as mypy or pyright, that None is a possible answer and must be handled. Python does not enforce hints at runtime; they are documentation that tools can verify. Prefer precise types: a frozen dataclass Order says more than a dict with "some keys".

For describing an interface itself, Python offers typing.Protocol: structural typing, where anything with the right methods qualifies, with no inheritance required. (Python folk call this duck typing; the Protocol lets a type checker verify it.) That is a natural fit for a port, the interface through which your core logic reaches an outside dependency, an idea chapter 5 develops fully. Here is a storage port with two interchangeable implementations:

from dataclasses import dataclass
import sqlite3
from typing import Protocol


@dataclass(frozen=True)
class Order:
    id: str
    total_cents: int


class OrderStore(Protocol):
    """Port: where orders live. Callers never learn how."""

    def save(self, order: Order) -> None:
        """Store the order. Saving the same id again replaces it."""
        ...

    def get(self, order_id: str) -> Order | None:
        """Return the order, or None if the id was never saved."""
        ...


class InMemoryStore:
    def __init__(self) -> None:
        self._rows: dict[str, Order] = {}

    def save(self, order: Order) -> None:
        self._rows[order.id] = order

    def get(self, order_id: str) -> Order | None:
        return self._rows.get(order_id)


class SqliteStore:
    def __init__(self, path: str = ":memory:") -> None:
        self._db = sqlite3.connect(path)
        self._db.execute("CREATE TABLE IF NOT EXISTS orders (id TEXT PRIMARY KEY, total_cents INTEGER)")

    def save(self, order: Order) -> None:
        self._db.execute("INSERT OR REPLACE INTO orders VALUES (?, ?)", (order.id, order.total_cents))
        self._db.commit()

    def get(self, order_id: str) -> Order | None:
        row = self._db.execute("SELECT id, total_cents FROM orders WHERE id = ?", (order_id,)).fetchone()
        return Order(*row) if row else None


def apply_discount(store: OrderStore, order_id: str, percent: int) -> Order | None:
    order = store.get(order_id)
    if order is None:
        return None
    discounted = Order(order.id, order.total_cents * (100 - percent) // 100)
    store.save(discounted)
    return discounted


for store in (InMemoryStore(), SqliteStore()):
    store.save(Order("o-1", 5000))
    print(type(store).__name__, apply_discount(store, "o-1", 10), apply_discount(store, "nope", 10))
InMemoryStore Order(id='o-1', total_cents=4500) None
SqliteStore Order(id='o-1', total_cents=4500) None

Notice the contract hiding in the protocol's docstrings: "saving the same id again replaces it", "returns None if the id was never saved". Both implementations must honour those sentences, and a test that runs against both (a "contract test") is how you keep them honest. That is the quiet power of a port: the interface is small enough to write down completely.

Two designs of the same API

Here is a shopping cart designed twice. The first exposes its internals and leaves the caller responsible for keeping them consistent; the second speaks the domain's language and guards its own invariant.

# --- Leaky: callers reach into internals and must keep them consistent ---
class LeakyCart:
    def __init__(self):
        self.items = []          # list of [sku, qty, unit_cents]
        self.total_cents = 0     # caller must keep this in sync

lc = LeakyCart()
lc.items.append(["tea", 2, 450])
lc.total_cents += 2 * 450
lc.items.append(["mug", 1, 1200])      # forgot to update total_cents
print("leaky total:", lc.total_cents, "real:", sum(q * c for _, q, c in lc.items))

# --- Clean: operations in domain terms, invariants kept inside ---
class Cart:
    def __init__(self):
        self._lines: dict[str, tuple[int, int]] = {}   # sku -> (qty, unit_cents)

    def add(self, sku: str, unit_cents: int, qty: int = 1) -> None:
        """Add qty units of sku. qty must be positive."""
        if qty <= 0:
            raise ValueError("qty must be positive")
        old_qty = self._lines.get(sku, (0, unit_cents))[0]
        self._lines[sku] = (old_qty + qty, unit_cents)

    def remove(self, sku: str) -> None:
        """After this call sku is not in the cart (whether or not it was before)."""
        self._lines.pop(sku, None)

    @property
    def total_cents(self) -> int:
        return sum(q * c for q, c in self._lines.values())

c = Cart()
c.add("tea", 450, 2)
c.add("mug", 1200)
c.remove("biscuits")        # no error: nothing to remove is fine
print("clean total:", c.total_cents)
try:
    c.add("tea", 450, 0)
except ValueError as e:
    print("rejected:", e)
leaky total: 900 real: 2100
clean total: 2100
rejected: qty must be positive

The leaky cart is not just unpleasant; it is unfixable without breaking callers. Once outside code writes to cart.items and cart.total_cents directly, you can never switch to storing prices as decimals, add tax, or cache the total, because callers depend on the exact shape. The clean cart can do all of those. Hyrum's law (Hyrum Wright) states this bluntly: with enough users, every observable behaviour of your interface will be depended on by somebody, which is an argument for making less of it observable in the first place. Chapter 10 returns to this.

Leaky abstractions

In 2002 Joel Spolsky named the uncomfortable truth in his "Law of Leaky Abstractions": all non-trivial abstractions, to some degree, are leaky. An abstraction promises you need not think about the layer beneath, and sooner or later a failure, a performance cliff or an edge case forces you to think about it anyway. You have met three already:

  • TCP hides loss, not latency. It retransmits lost packets so your program sees every byte in order, but each retransmission takes time. The stream is reliable and may still stall for seconds. A design that assumes "TCP is reliable" without a timeout leaks the moment a link degrades (networking chapter 8).
  • An ORM hides SQL until N+1. Looping over 100 orders and touching order.customer issues 1 query for the orders plus 100 for the customers, and everything is fast on your ten-row dev database (data chapter 8).
  • "Saved" hides fsync. A successful write() usually means the bytes reached the operating system's page cache, not the disk (systems chapter 9).

Spolsky's moral was not "avoid abstractions"; that way lies assembly language. It is: know one layer below the one you use, so that when it leaks you can recognise the symptom. And as a designer, make your own abstractions leak less by putting the things callers must care about, such as timeouts, cost and failure, into the interface instead of pretending they do not exist. The rest of this chapter's examples are about that.

Common misconception

"A leaky abstraction is a badly designed one, so a good design should not leak." Some leaks are unavoidable because the hidden thing has real physical behaviour (networks are slow, disks lose power). A good abstraction leaks in a way you can see coming, with documented timeouts, explicit error types and honest cost, rather than in a way that surprises you at 3am.

Errors are part of the interface

What a call does when it cannot do its job is as much a part of its contract as what it returns. Callers must write code for every way it can fail. So designing the error behaviour deliberately is not a detail; it is half the interface.

Return values vs exceptions

There are two broad styles. Returning an error value (a special number, None, a result object) forces nothing: callers can ignore it, and a magic value is easily mistaken for real data. Raising an exception makes ignoring the error hard (it propagates until something handles it) and separates the happy path from the failure path. Here is a "before" and "after", with a distinction that matters in the next chapters: some failures are worth retrying and some are not.

# Version 1: errors as magic return values
def charge_v1(balance, amount):
    if amount <= 0:
        return -1
    if amount > balance:
        return -2
    return balance - amount

r = charge_v1(100, 150)
print("v1 result:", r, "(is that a balance or an error?)")

# Version 2: exceptions with categories
class PaymentError(Exception):
    retryable = False

class InsufficientFunds(PaymentError):
    pass

class ProviderTimeout(PaymentError):
    retryable = True

def charge_v2(balance, amount):
    if amount > balance:
        raise InsufficientFunds(f"need {amount}, have {balance}")
    return balance - amount

def call_with_retry(fn, attempts=3):
    for n in range(1, attempts + 1):
        try:
            return fn()
        except PaymentError as e:
            if not e.retryable or n == attempts:
                raise
            print(f"  attempt {n} failed ({type(e).__name__}), retrying")

calls = {"n": 0}
def flaky():
    calls["n"] += 1
    if calls["n"] < 3:
        raise ProviderTimeout("no reply in 2s")
    return "charged"

print(call_with_retry(flaky))
try:
    call_with_retry(lambda: charge_v2(100, 150))
except PaymentError as e:
    print("not retried:", type(e).__name__, e)
v1 result: -2 (is that a balance or an error?)
  attempt 1 failed (ProviderTimeout), retrying
  attempt 2 failed (ProviderTimeout), retrying
charged
not retried: InsufficientFunds need 150, have 100

Version 1 returned -2, and nothing stops a caller from happily treating it as a balance of minus two. Version 2 raises a named exception, and, more usefully, each error carries a retryable flag. This is the error category idea: callers rarely need to know exactly what went wrong; they need to know what to do. Typically that is one of:

Retrying a "card declined" five times is harmless noise at best and a double charge at worst; failing a whole checkout on one dropped packet is wasteful. Making the category part of the error type lets a generic retry wrapper (chapter 4 builds one, chapter 17 hardens it) behave correctly without knowing anything about payments. HTTP's status codes encode the same idea: 4xx means "your request is wrong, don't repeat it unchanged"; 5xx and 429 often mean "try again later".

Define errors out of existence

John Ousterhout's advice in A Philosophy of Software Design (2018) is the best error-handling trick there is: change the semantics so the error cannot happen. Every exception you can eliminate is a handler nobody has to write. A simple example is deleting something that is already gone:

import os, tempfile
d = tempfile.mkdtemp()
p = os.path.join(d, "x.txt")
def delete_v1(path):
    os.remove(path)      # raises if missing
def delete_v2(path):
    """Postcondition: path does not exist."""
    try:
        os.remove(path)
    except FileNotFoundError:
        pass
delete_v2(p); delete_v2(p)
print("delete twice ok")
try:
    delete_v1(p)
except FileNotFoundError as e:
    print("v1 raised:", type(e).__name__)
os.rmdir(d)
delete twice ok
v1 raised: FileNotFoundError

delete_v2 redefines its contract: the postcondition is "the path does not exist afterwards". If it did not exist before, that is already true, so there is nothing to report. Other examples: dict.pop(key, None), set.discard(x) (versus remove), and cart.remove("biscuits") in the cart above. The same idea underlies idempotent operations (calling twice has the same effect as once), which become critical in distributed systems because retries mean calls will happen twice.

Do not overdo it

Defining an error away is right when the caller genuinely does not care ("make sure it's gone"). It is wrong when the failure carries information they need: swallowing a "payment declined" would be a bug, not a design. The test is whether any sensible caller would behave differently on the two outcomes. Never write a bare except: pass to make an error "go away".

Fail fast, or degrade?

When an operation fails you have a second choice: stop loudly, or carry on with less. Fail fast means detect problems as early as possible and stop, so a bad state never spreads: reject invalid input at the door, crash at startup if the configuration is missing. Graceful degradation means that when an optional part fails, the rest still works: if the recommendation service is down, show bestsellers instead of an error page.

class ProviderTimeout(Exception): pass

def recommendations(user, fetch):
    try:
        return fetch(user)
    except ProviderTimeout:
        return ["bestsellers"]     # degrade: optional feature
def timeout(_): raise ProviderTimeout("slow")
print("degraded:", recommendations("u1", timeout))
degraded: ['bestsellers']

The rule of thumb: fail fast for anything that would make the answer wrong (a payment amount, a corrupt record); degrade for anything that only makes the answer less complete (recommendations, an avatar image). Deciding which is which is a product decision as much as an engineering one, which is why you should write it down. Chapter 8 places this policy at the edge of the system and chapter 17 builds the machinery.

Naming

Names are the cheapest and most underrated part of an interface. A name should tell the reader what the thing is or does in the domain's language, at a similar level of abstraction as its neighbours. Some habits that pay off:

  • Names carry the contract. get_order hints it may fail; find_order hints it may return nothing. total_cents states the unit, which prevents an entire family of bugs.
  • Avoid vague words such as data, manager, handler, process, util. A class named OrderManager usually has no single responsibility.
  • If you cannot name it simply, the abstraction is probably wrong. A function that needs "and" in its name (validate_and_save) is doing two jobs.
  • Be consistent. If one method says remove, do not call its sibling delete for the same idea.

Distributed systems connection

A network call is an abstraction that is spectacularly leaky: it looks like a function call and adds latency, partial failure and uncertainty about whether the other side acted. The famous "fallacies of distributed computing" are a list of leaks. Two consequences from this chapter carry straight over. First, error categories (retryable or not) become the backbone of retry policy in chapter 17. Second, making operations idempotent, a way of defining errors out of existence, is what makes retries safe at all. When you design a service interface in chapters 9 and 10, you will be designing it for callers who can never fully see the machinery behind it.

Key takeaways

  • An abstraction hides the details that change or that callers cannot use, and shows what they must decide. The interface is what callers may rely on.
  • Make the common case simple, name operations in the domain's language, and never make callers maintain your invariants for you.
  • The docstring is a contract: preconditions (caller's duty), postconditions (your promise), invariants (always true).
  • Type hints and Protocol make part of the contract machine-checkable and keep ports small and swappable.
  • All non-trivial abstractions leak (Spolsky, 2002). Know one layer below, and put cost, timeouts and failure in the interface.
  • Errors are part of the interface: categorise them by what the caller should do, define them out of existence where you honestly can, fail fast on wrong, degrade on incomplete.

Check your understanding

Which is the best description of a good abstraction?

  1. One that exposes every detail so callers have full control
  2. One that has as many configuration options as possible
  3. One that hides details that change or that callers cannot use, and exposes what they must decide
  4. One that uses inheritance rather than composition
Abstraction means leaving out unimportant detail. Exposing everything defeats the purpose, and options and inheritance have nothing to do with whether the right things are hidden.

In design by contract, what is a caller's responsibility?

  1. To satisfy the preconditions before calling
  2. To guarantee the postconditions
  3. To catch every possible exception
  4. To read the implementation first
Preconditions are the caller's obligation; postconditions are the implementation's promise once preconditions held. A violated precondition is a caller bug.

An ORM-based page is fast with 10 rows in development and crawls with 10,000 in production, issuing thousands of tiny queries. Which law does this illustrate?

  1. Conway's law
  2. Hyrum's law
  3. Amdahl's law
  4. The law of leaky abstractions: the hidden SQL showed through
This is the N+1 problem, a textbook leak: the abstraction promised "no SQL" but its cost model is still SQL's. Hyrum's law is about users depending on observable behaviour; Conway's is about org structure.

Why is it useful for an error type to carry a retryable flag?

  1. It lets the program ignore non-retryable errors
  2. A generic retry wrapper can do the right thing without knowing the domain: retry timeouts, never retry a declined card
  3. It makes exceptions faster
  4. It replaces the need for timeouts
The caller mostly needs to know what to do next. Categorising errors lets reusable code, like a retry decorator, act correctly. It does not make errors ignorable, and timeouts are still required.

"Defining an error out of existence" is most appropriate for which case?

  1. A payment is declined by the bank
  2. A user submits an invalid email address
  3. Deleting a file whose postcondition is simply "the file doesn't exist afterwards"
  4. The database is unreachable
When no sensible caller would act differently on "already gone" versus "just deleted", the error carries no useful information and can be removed. A decline, invalid input and an outage all carry information the caller needs.

A recommendations service times out during checkout. What does the "fail fast vs degrade" rule of thumb suggest?

  1. Fail the whole checkout, since an error occurred
  2. Degrade: show a default list, since recommendations only make the page less complete, not wrong
  3. Retry forever until it works
  4. Crash the server to be safe
Degrade for optional parts that only make the answer less complete; fail fast for anything that would make the answer wrong (like the payment amount). Retrying forever is not a policy.

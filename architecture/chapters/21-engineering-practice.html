Engineering Practice at Scale

A design is only as good as the process that changes it. When three engineers share a codebase, almost anything works. When three hundred do, how you review, test, merge, build and release becomes part of the architecture. This chapter covers the practices that let many people change one system safely, and the honest trade-offs behind each.

Why this matters

Earlier chapters showed how to structure code: modules, boundaries, contracts. Those structures decay unless the daily workflow protects them. A slow, flaky build tempts people to skip tests; a review queue that takes days encourages giant changes; a dependency nobody owns breaks the product on a Friday. Strong engineering organizations treat the workflow as a system to design, measure and improve, with the same care as the software it produces.

Facts and opinions in this chapter

Software process is full of strong opinions. Where something is well-established (how a content-addressed cache works, what a metric measures) we state it as fact. Where reasonable teams disagree (monorepo or polyrepo, how small is small) we say “many experienced engineers argue” and show both sides. Treat the opinions as starting points to test in your own context.

Code review

A code review is a colleague reading a proposed change before it is merged. Done well it does four jobs at once: it catches defects, it improves design while change is still cheap, it spreads knowledge (at least two people now understand this code), and it keeps the codebase consistent. The knowledge-sharing role is underrated: it is how newcomers learn the codebase's norms and how seniors learn what the juniors are building.

What to look for

Reviewers have limited attention, so spend it where humans beat machines. Formatting, import order and simple lint rules belong to automated tools; arguing about them in review wastes everyone's time. Humans should ask:

Does it work?

Edge cases, error handling, concurrency, and whether the tests would actually fail if the code were wrong. Read the tests first: they state the intent.

Is the design right?

Does it respect module boundaries (chapter 2)? Is the abstraction at the right level (chapter 3)? Is this the right place for the change at all?

Can others maintain it?

Names, comments that explain why, and complexity (chapter 1). If you struggled to understand it, the next person will too.

Can we run it?

Logging, metrics, failure behavior, rollout and rollback, migration safety (chapter 18), and security-sensitive inputs.

Size matters most

The strongest lever on review quality is change size. Reviewers find defects well in short diffs and poorly in huge ones, where attention fades and “looks fine” takes over. Google's published engineering practices recommend small, self-contained changes: roughly 100 lines is usually reasonable and 1,000 lines usually too large, counted alongside the number of files touched, with the tests included. Treat those numbers as a rough guide rather than a rule, but the principle is widely shared: one change should do one thing. Small changes are reviewed faster, rolled back more easily, and waste less work if rejected.

Splitting a large feature into reviewable steps is a skill. Typical moves: land the refactoring that makes room for the feature first, with no behavior change; add the new code behind a flag, unused; then flip. Some teams use stacked changes, a chain of small dependent pull requests reviewed in order.

Analogy: proofreading a book

A good editor reading a page can spot a missing comma. Hand the same editor an entire manuscript in one sitting and they will skim. Review quality depends on the size of the bite, not the diligence of the person.

Where it breaks down: prose pages are independent; code changes interact, so a tiny change can still break something far away. Small changes need good tests and good CI to back the reviewer up.

Making review work for people

  • Speed. A review that sits for days blocks the author and encourages bigger, riskier changes. Many teams set an expectation of a first response within a working day.
  • Tone. Comment on the code, not the person; ask questions (“what happens if this is null?”); separate “must fix” from “nit” or “optional”. Reviews that feel like exams teach people to hide their work.
  • Authors help reviewers. A clear description (what, why, how it was tested), self-review before requesting, and annotations on the tricky parts.
  • Not a rubber stamp, not a gate of perfection. The standard many teams adopt: approve once the change clearly improves the overall health of the codebase, even if not how you would have written it.

Continuous integration

Continuous integration (CI) means every change is merged into the shared mainline frequently, and an automated system builds it and runs tests on every merge (and usually before it). The goal is fast feedback: the sooner you learn a change broke something, the cheaper the fix, because the context is still in your head and few other changes have piled on top.

Test tiers

Tests trade speed against realism. A common arrangement, often drawn as a pyramid, has many fast unit tests (one function or class, no network or disk), fewer integration tests (a service with a real database or a neighbouring service) and very few end-to-end tests (a full user journey through the deployed system). The shape matters because a suite of mostly end-to-end tests is slow, brittle and hard to debug. The testability techniques of chapter 7 (ports, fakes, dependency injection) are what make a fast, broad base of unit tests possible. Some teams argue for a “honeycomb” with more integration tests, particularly for services that are mostly glue; the principle, fast feedback on most changes, is the same.

Flaky tests

A flaky test passes and fails on the same code. Causes are timing assumptions (sleep(1)), shared state between tests, test-order dependence, real clocks and randomness, and external services. Flakiness is poison, for a concrete reason: once people learn that a red build might be noise, they re-run instead of investigating, and the one real failure hides among the false ones. Trust in the signal is the entire value of CI.

A standard remedy is quarantine: detect a flaky test (it failed and then passed on retry with no code change), move it out of the blocking set so it stops stopping merges, file a ticket with an owner and a deadline, and report the quarantine size as a health metric. Quarantine is a bandage, not a cure; a growing quarantine means the team is accumulating silent risk. Better still, remove the causes: inject clocks and random seeds, give each test its own state, and avoid real networks in the fast tiers.

Keep the mainline green

If main is broken, nobody can safely build on it. Teams usually adopt a norm of fixing or reverting a broken change immediately, and many add a merge queue that re-tests each change against the latest main before landing it, since two changes that each pass alone can still fail together.

Trunk-based development and feature flags

How long should a branch live? In trunk-based development everyone integrates into one main branch ("trunk") at least daily, in small batches, with branches that last hours, not weeks. The alternative is long-lived branches, such as one per feature or per release, merged when the work is done. DORA's research summary describes trunk-based development as a requirement for continuous integration and associates it with higher delivery speed and stability; it suggests keeping three or fewer active branches and merging at least once a day.

The argument for trunk is mathematical as much as cultural: the longer two branches diverge, the more they conflict, and the conflicts grow faster than the branches. A branch that lives for a month is a merge nobody wants to do, so it is postponed, so it grows. Frequent small merges keep integration pain small. The argument for long-lived branches is real too: unfinished work stays out of the product, and a release branch gives you a stable line to patch. Many experienced engineers still keep short-lived release branches for hot-fixes, while developing on trunk.

The obvious objection: “I cannot merge half a feature.” You can, if the half is hidden. A feature flag (toggle) is a runtime switch that decides whether code runs, so unfinished work can ship dark, be enabled for staff, then for 1% of users, then for everyone, and be turned off instantly without a deploy. Chapter 18 introduced flags as a way to separate deploying code from releasing a feature, and they are what make trunk-based development workable for large features. Alongside them, branch by abstraction lets you swap an implementation behind an interface in small steps.

Flags are debt

Every flag doubles the states your code can be in, and tests cover only some of them. Old flags that no one removes become dead branches and, occasionally, outages when someone flips one. Give each flag an owner and an expiry, delete the flag as soon as the rollout completes, and treat long-lived configuration switches separately from short-lived release toggles.

Continuous delivery

Continuous delivery extends CI so that every change that passes the pipeline could be released to production at any moment; continuous deployment goes one step further and releases automatically. Principles that make it safe:

  • Build once, promote the same artifact. The binary or container image tested in staging must be the one that reaches production. Rebuilding per environment lets differences sneak in.
  • Keep configuration separate from the artifact. Environment-specific settings are injected at deploy time.
  • Release gradually, observe, and be able to undo. Canaries, staged rollouts and automatic rollback on bad signals turn a risky event into a routine one; see deployments in the reliability course.
  • Make deployment boring. The more often you deploy, the smaller each change, the easier it is to find what broke, and the less scary the process becomes. Rare, large releases are riskier precisely because they are rare and large.

Database changes deserve special care, because code can roll back but data cannot: use the expand/contract pattern from chapter 18 so old and new code can run against the same schema during rollout.

Monorepo or polyrepo?

A monorepo keeps many projects, even whole organizations' code, in one version-control repository. A polyrepo gives each service or library its own. Note that this is separate from monolith versus microservices: you can deploy dozens of independent services from one monorepo, or ship a monolith assembled from many repositories.

MonorepoPolyrepo
Cross-cutting changeOne atomic commit updates a library and all its callersA coordinated series of changes across repositories, released in order
DependenciesOne version of everything at a given commit; no skew between internal projectsEach repo picks versions; skew is the default and must be managed
Discoverability & reuseEasy to search and to find who uses whatNeeds a catalogue; reuse is harder to see
ToolingNeeds investment: scalable build, selective testing, code search, ownership rulesStandard tools work out of the box
Autonomy & blast radiusA broken main affects everyone; shared standards are easier to impose (for better or worse)Teams pick their own tools and pace; failures stay local
Access controlHarder to give partial visibilityNatural: per-repository permissions

Google's engineers have described their very large single repository and the custom tooling it needs (a 2016 paper in Communications of the ACM by Potvin and Levenberg). The lesson often drawn is wrong in both directions: a monorepo is not a magic scaling trick, and it does not require Google's scale or tooling to be useful. Many experienced engineers argue that for small and mid-sized organizations a monorepo is simpler to reason about, and that the pain people attribute to it comes from missing build and ownership tooling. Others prefer polyrepos for strong team autonomy and clean separation of release cycles. The honest answer: the choice follows your tooling budget and how much your teams change shared code. Pick one on purpose and invest in what it requires.

Build systems: hermetic, cached, incremental

As a codebase grows, how long the build takes becomes the speed limit of the whole organization. Naive builds recompute everything, or use timestamps to guess what changed, which is brittle (touching a file without changing it triggers work; a stale output hides a real change). Modern build systems in the Bazel style take a more rigorous route, built on three ideas.

  1. An explicit graph. Each target declares its sources and dependencies, forming a DAG. The tool knows exactly what depends on what, so it can build independent parts in parallel and rebuild only what a change can affect.
  2. Hermeticity. A hermetic build gives the same output for the same source and configuration, because it is isolated from the host: tools and dependencies are pinned, and nothing depends on whatever happens to be installed on the machine, absolute paths, or the clock. Bazel's documentation lists typical enemies: timestamps and build IDs written into outputs, host system binaries, and writing into the source tree.
  3. Content-addressed caching. Each build step (an action) gets a key computed as a hash of everything it depends on: the command, the content of its inputs, and the tool version. If the key is in the cache, reuse the result; if not, run it and store it. Because hermetic builds are deterministic, the cached result is as good as a fresh one, and the cache can be shared across machines and CI, so one engineer's build feeds everyone else's. Bazel's documentation describes the payoff: outputs are cached and reused, so an action reruns only when its inputs change.

A useful refinement is early cutoff: key dependents on the content hash of their dependencies' outputs, not on which sources changed. If you edit a comment, the compiler's output is byte-identical, so everything downstream still hits the cache. The build below is a toy, but its logic is the real thing: hash the inputs, look up the key, skip or run. It uses a pretend compiler that strips comments, a five-target graph, and a cache directory in a temporary location (cleaned up at the end).

import hashlib, os, shutil, tempfile

def digest(*parts):
    h = hashlib.sha256()
    for p in parts:
        h.update(p if isinstance(p, bytes) else p.encode())
        h.update(b"\0")
    return h.hexdigest()[:10]

def compile_(source: str) -> str:
    """Pretend compiler: drops comments and blank lines, so comment-only edits
    produce byte-identical output."""
    lines = [l.strip() for l in source.splitlines()]
    return "\n".join(l for l in lines if l and not l.startswith("#"))

# target -> (source file, dependencies)
GRAPH = {
    "util": ("util.src", []),
    "lib":  ("lib.src",  ["util"]),
    "api":  ("api.src",  ["lib"]),
    "cli":  ("cli.src",  ["lib", "util"]),
    "app":  ("app.src",  ["api", "cli"]),
}

class Builder:
    def __init__(self, src_dir, cache_dir):
        self.src, self.cache = src_dir, cache_dir
        self.outputs = {}          # target -> output digest, for this run
        self.log = []

    def build(self, target):
        if target in self.outputs:
            return self.outputs[target]
        src_file, deps = GRAPH[target]
        dep_outs = [self.build(d) for d in deps]           # dependencies first
        with open(os.path.join(self.src, src_file)) as f:
            source = f.read()
        # The action key covers everything that can change the result:
        # the tool version, the source bytes, and the *outputs* of dependencies.
        key = digest("compiler-v1", source, *dep_outs)
        path = os.path.join(self.cache, key)
        if os.path.exists(path):
            self.log.append(f"{target}: cache hit  ({key})")
            with open(path) as f:
                out = f.read()
        else:
            self.log.append(f"{target}: BUILD      ({key})")
            out = compile_(source)
            with open(path, "w") as f:
                f.write(out)
        self.outputs[target] = digest(out)
        return self.outputs[target]

def run(title, src, cache):
    b = Builder(src, cache)
    b.build("app")
    print(f"--- {title}")
    print("\n".join("  " + l for l in b.log))

def edit(src, name, text):
    with open(os.path.join(src, name), "w") as f:
        f.write(text)

root = tempfile.mkdtemp(prefix="buildcache-")
try:
    src, cache = os.path.join(root, "src"), os.path.join(root, "cache")
    os.makedirs(src); os.makedirs(cache)
    for target, (fname, _) in GRAPH.items():
        edit(src, fname, f"# {target}\ndef {target}(): return 1\n")

    run("1. clean build", src, cache)
    run("2. nothing changed", src, cache)
    edit(src, "api.src", "# api\ndef api(): return 2\n")
    run("3. real edit to api.src", src, cache)
    edit(src, "util.src", "# util, now with a comment\n\ndef util(): return 1\n")
    run("4. comment-only edit to util.src", src, cache)
    edit(src, "util.src", "# util\ndef util(): return 99\n")
    run("5. real edit to util.src", src, cache)
    shutil.rmtree(cache); os.makedirs(cache)
    run("6. cache wiped, clean build again", src, cache)
finally:
    shutil.rmtree(root)

Walk through it. Run 2 changed nothing and rebuilt nothing. Run 3 edited api, so only api and its dependent app rebuilt (the keys of util, lib and cli are unchanged). Run 4 edited a comment in util: util had to rebuild (its source bytes changed), but its output was identical, so nothing downstream did. In run 5 a real change to util rebuilt lib and cli, whose inputs now differ; because our toy compiler does not embed dependency content into its output, lib's output is unchanged and the ripple stops there. A real compiler would usually embed more, so more would rebuild. Run 6 wiped the cache and everything rebuilt, but the keys are the same as before: determinism is what lets a cache be shared.

Step through

The six runs above, on the dependency graph (first five shown)

  1. Run 1, clean build. Nothing is cached, so every target runs, dependencies first.
  2. Run 2, nothing changed. Every action key is already in the cache; no work is done.
  3. Run 3, edit api.src. Only api and app, which depends on its output, need new keys. The rest are reused.
  4. Run 4, comment-only edit to util.src. util re-runs because its source bytes changed, but its output is byte-identical, so every dependent's key is unchanged (early cutoff).
  5. Run 5, real edit to util.src. lib and cli re-run because they consume util's changed output. In this toy, lib's output ends up unchanged, so api and app are reused. Real builds often ripple further.

Why "hermetic" is the hard part

Caching is easy to describe and hard to trust. If a build step secretly reads the current date, an environment variable or a library from /usr/lib, the key does not cover everything the result depends on, and a cache hit can return a wrong answer. Getting there takes discipline: declared inputs for everything, pinned toolchains, and sandboxing so undeclared reads fail loudly. Adopting a Bazel-style tool is a significant investment that pays back mostly in large, multi-language codebases; for a small project, the incremental and caching features of your language's own build tool are often enough.

Dependencies and version skew

Your code depends on libraries, which depend on other libraries. Two recurring problems:

  • Version skew: different parts of the system use different versions of the same thing. Two services on different versions of a shared client library disagree about message formats; a rolling deploy runs two versions of your own service side by side. Skew is not an accident to eliminate but a condition to design for, which is why compatibility rules from evolving contracts matter.
  • The diamond problem: your app needs libraries B and C, and each needs a different, incompatible version of D. Different ecosystems resolve this differently (pick the highest, allow multiple copies, or fail), and each choice has failure modes.

Practical habits: commit a lockfile so builds use exactly the versions you tested; update dependencies often and in small steps (an automated bot that opens a pull request per update turns a dreaded annual upgrade into routine), because a three-year-old dependency jump is a project, while a weekly one is a review; limit the number of direct dependencies, since each is a long-term commitment and a security surface; and know what you depend on (software bill of materials, vulnerability scanning). Internally, a monorepo's “one version of everything” policy removes skew by construction, at the price of moving all callers when a library changes. Hyrum's law warns about the other direction: with enough users, every observable behavior of your library will be depended upon by somebody, so even a bug fix can break a caller.

Measuring productivity, carefully

Leaders want to know whether the engineering system is improving. The best-known evidence-based answer is DORA (the DevOps Research and Assessment program, now part of Google Cloud). It defines software delivery performance with five metrics in two groups: throughput (change lead time, deployment frequency, failed deployment recovery time) and instability (change fail rate, deployment rework rate). The pairing is deliberate: speed measured alongside stability, so you cannot look good by shipping fast and breaking things. (Earlier DORA publications described four “key metrics”; the set has evolved, so check the current definitions before quoting numbers.)

A broader lens is the SPACE framework (Forsgren, Storey, Maddila, Zimmermann, Houck and Butler, ACM Queue, 2021), which says productivity cannot be captured by one number and suggests looking across dimensions: satisfaction and well-being, performance, activity, communication and collaboration, and efficiency and flow, using several metrics from at least a few of them, including some perceptual ones such as surveys.

Metrics are easy to misuse

Goodhart's law: when a measure becomes a target, it stops being a good measure. Counting lines of code, commits or pull requests rewards noise. Ranking individuals by deployment frequency punishes people who work on risky or foundational systems. Comparing a mobile app with a mainframe system is meaningless. DORA's own guidance warns against setting the metrics as goals, relying on a single metric, comparing unlike applications, competing between teams and siloing metric ownership. Use the metrics to start conversations about where the system is slow (is it review wait time? a flaky test suite? manual release steps?), measure your own team against its own past, and never as a performance review score.

Documentation, ownership and large-scale change

Docs as code, owners as files

Documentation rots when it lives apart from the code. Docs as code keeps it in the same repository, written in plain text (Markdown), reviewed in the same pull requests, and checked by CI (links resolve, examples compile, a docs site builds). Architecture decision records (chapter 19) are the same idea applied to design history. The rule of thumb: the closer a document sits to the thing it describes, the likelier it is to be updated in the same change.

Ownership needs the same treatment. In a large repository, who must approve a change to the payments module? A CODEOWNERS file maps path patterns to people or teams. On GitHub, the file can live in the repository root, .github/ or docs/; the last matching pattern wins; owners are automatically requested as reviewers when a pull request touches their files; and a branch rule can require approval from a code owner. A tiny example:

# Default owner for everything
*                    @acme/platform
# Later, more specific lines override earlier ones
/services/payments/  @acme/payments-team
/docs/               @acme/docs-guild @acme/platform
*.sql                @acme/data-eng

Treat ownership as a living map, not bureaucracy: stale owners (people who left) block merges, and overly broad ownership turns every change into a queue. Ownership also mirrors Conway's law (Melvin Conway, 1968): the structure of the software tends to mirror the structure of the organization that builds it, so redrawing the owner map is often the first step of redrawing the architecture (service boundaries).

Changing a lot of code at once

Sometimes the whole codebase must change: rename an API, upgrade a framework, replace a deprecated call in four thousand files. Doing it by hand is slow and error-prone; asking every team to do it themselves takes years. The standard approach is a codemod: a program that rewrites source code by operating on its syntax tree rather than on text, so it understands the difference between a function call and the same word in a comment or string. Typical tools include language-specific rewriting libraries and refactoring engines; most languages have one.

A large-scale change usually follows a recipe:

  1. Make the new way available alongside the old one (expand), so callers can migrate gradually.
  2. Write and test the codemod on a few packages; review its output by eye; run the real test suite on the result.
  3. Split the output into reviewable changes, typically per owning team (this is where CODEOWNERS pays off), and land them incrementally with automatic merging when checks pass.
  4. Block regressions with a lint rule or compile-time warning, so the old pattern is not reintroduced.
  5. Remove the old way (contract) once usage reaches zero.

It is the expand/contract pattern from earlier chapters applied to source code. Monorepos and fast, trusted CI make it dramatically easier, because the tool can see every caller and verify the whole change; this is a large part of the case for them.

Distributed systems connection

Engineering practice is a distributed system whose nodes are people. Version skew during a rolling deploy is the same problem as replicas on different versions of a schema; a merge queue is a serialization point, like a leader ordering writes; a content-addressed cache is the idempotent, deterministic recomputation idea from batch processing; and a flaky test is a failure detector with a false-positive rate that you cannot ignore. The next course, reliability, picks up where this chapter stops: once the change is built and shipped, how do you operate it, observe it and survive when it fails?

Key takeaways

  • Code review finds defects, improves design and shares knowledge. Automate style, keep changes small, respond quickly, and be kind.
  • CI exists for fast, trustworthy feedback: tier your tests by speed, quarantine flaky ones with owners, and keep the mainline green.
  • Trunk-based development with feature flags keeps integration pain small. Flags are debt, so expire them.
  • Continuous delivery: build once, promote the same artifact, release gradually, make rollback easy.
  • Monorepo vs polyrepo is a trade-off between atomic change and shared versions on one side and autonomy and simple tooling on the other. Both need deliberate tooling.
  • Hermetic, content-addressed builds reuse work safely: key each action on the hash of everything it depends on.
  • Plan for version skew, update dependencies often in small steps, and use DORA (and SPACE) metrics to understand your system, never to rank people.
  • Keep docs and ownership in the repo, and change code at scale with codemods, expand/contract and incremental landing.

Check your understanding

Why do many teams insist on small code changes?

  1. Version control charges per line
  2. Small changes never need tests
  3. Reviewers catch more problems in short diffs, and small changes are faster to review, easier to roll back and cheaper to reject
  4. Large changes cannot be merged by CI
Review attention degrades as the diff grows, so large changes get skimmed. Small changes are also easier to revert and reduce wasted work. The size numbers are guidelines, but the principle is widely held.

A test fails about one run in twenty on unchanged code, and engineers have started re-running the build whenever it goes red. What is the best response?

  1. Quarantine the test out of the blocking set with an owner and deadline, then fix its root cause (timing, shared state, external dependency)
  2. Delete the whole suite
  3. Tell people to retry until green
  4. Increase the timeouts on every test
Flaky tests destroy trust in CI, because real failures hide among false ones. Quarantine stops the blocking noise; the root-cause fix is the actual cure. Blanket retries and timeouts just hide the problem.

How do feature flags help trunk-based development?

  1. They let you skip code review
  2. They automatically resolve merge conflicts
  3. They make tests unnecessary
  4. Unfinished work can be merged daily but stays switched off, so deploying code and releasing a feature become separate decisions
Flags hide incomplete features at runtime, which lets large work land in small, frequent merges. They are not free: every flag adds states to test and must be removed after rollout.

In a hermetic, content-addressed build, you change only a comment in a low-level library and the compiler output is byte-identical. What happens to targets that depend on it, if they are keyed on the hash of their dependencies' outputs?

  1. They all rebuild, because the source changed
  2. They are reused from the cache, since their keys are unchanged (early cutoff)
  3. The build fails
  4. They rebuild only on CI
Only the library itself reruns. Its dependents' action keys depend on its output hash, which did not change, so their cached results still apply.

A director proposes ranking engineers by number of commits per week and setting a target for deployment frequency per person. What is the main problem?

  1. Commits cannot be counted
  2. Deployment frequency is not a meaningful metric at all
  3. Once a measure becomes a target it gets gamed (Goodhart's law), and individual activity counts say little about the health of the delivery system
  4. DORA recommends ranking individuals but only quarterly
DORA metrics describe a team's delivery system and are meant for finding bottlenecks and tracking your own improvement. Turning them into individual targets invites gaming and punishes people doing risky or foundational work.

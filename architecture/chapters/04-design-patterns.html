Design Patterns That Matter

A pattern is a name for a solution that people keep reinventing. The names are the valuable part: saying "wrap it in an adapter" replaces a paragraph of explanation. This chapter walks through the six patterns you will meet daily, each with the problem it solves, a runnable Python sketch, and an honest note about when it is the wrong tool, then closes with SOLID and the anti-patterns that patterns are so often used to commit.

Why this matters

Patterns are the shared vocabulary of design reviews. If your teammate says "put a facade in front of the billing subsystem" and you know what that means, a ten-minute whiteboard session becomes ten seconds. The same vocabulary is what the rest of this course uses: ports and adapters in chapter 5, observers become events in chapter 14, decorators grow into the resilience wrappers of chapter 17. But patterns also have a dark side, and the senior skill is knowing when not to reach for one.

What patterns are, and what they are not

The book Design Patterns: Elements of Reusable Object-Oriented Software (Gamma, Helm, Johnson and Vlissides, 1994, the "Gang of Four" or GoF) catalogued 23 recurring solutions in object-oriented code. A design pattern is not a library you import. It is a named, reusable shape: a problem, a structure that solves it, and the trade-offs. You write the code fresh each time, adapted to your language.

Two things follow. First, the language matters. Several GoF patterns were workarounds for limits in the languages of the time (C++ and Smalltalk); in a language with first-class functions, some collapse into a function argument. We will point these out. Second, the value is the vocabulary, not the diagrams. You can use "strategy" correctly without ever writing an abstract base class.

Pattern-itis

The classic failure of people who have just learned patterns is to apply them everywhere: a factory for a class with one implementation, an observer where a function call would do, five layers of indirection that make the code three times longer and no more flexible. Patterns solve recurring problems. If you do not have the problem yet, the pattern is pure cost: more code to read, more places to look. Introduce a pattern when the pain shows up (we will make this precise with the "rule of three" below), not in anticipation.

Analogy: a chef's techniques

Think of the restaurant chain from earlier. "Braise", "emulsify" and "blanch" are not recipes; they are named techniques that any chef recognises. Telling a new cook to "blanch the beans" is faster and less error-prone than describing boiling water, timing and ice baths. Patterns are the techniques of software; the finished dish is still up to you.

Where it breaks down: a cook who blanches everything, including steak, is a bad cook. Techniques have conditions, and a menu made only of techniques is a show-off kitchen, not a good restaurant.

Strategy: pluggable behaviour

Problem. One step of an algorithm needs to vary: the shop calculates discounts differently for Black Friday, bulk buyers and ordinary orders, and you do not want an if/elif chain that grows every quarter.

Solution. Pull the varying step out behind a small interface and pass the chosen implementation in. In the GoF book that means a Strategy base class with subclasses. In Python, where functions are values, a function is usually all you need:

# Strategy: functions are enough
from typing import Callable
PricingRule = Callable[[int], int]      # subtotal_cents -> discount_cents

def no_discount(subtotal): return 0
def ten_percent(subtotal): return subtotal // 10
def bulk(subtotal): return 500 if subtotal >= 10_000 else 0

def price(subtotal: int, rule: PricingRule = no_discount) -> int:
    return subtotal - rule(subtotal)

for rule in (no_discount, ten_percent, bulk):
    print(f"{rule.__name__:12}", price(12_000, rule))
rules = {"black-friday": ten_percent, "default": no_discount}
print("by name:", price(12_000, rules["black-friday"]))
no_discount  12000
ten_percent  10800
bulk         11500
by name: 10800

Use it when there are genuinely several interchangeable ways to do one step and the choice is made at runtime (by config, by customer type). Do not write a class hierarchy for it in Python unless each strategy carries its own state or several related methods; a Callable type alias is clearer. And do not use it for a variation that has only one case today.

Adapter: wrapping a foreign interface

Problem. You must use a payment provider's SDK, but its vocabulary (dollars as floats, status dictionaries, its own error codes) is not yours, and you do not want every file in your codebase to know it.

Solution. Define the interface you want (a port, in chapter 3's terms) and write a small class that translates between it and the SDK. If the provider changes its API or you change provider, one file changes.

# Adapter: wrap a provider SDK behind our port
from typing import Protocol
from dataclasses import dataclass

class PaymentDeclined(Exception): pass

class PaymentGateway(Protocol):
    def charge(self, order_id: str, amount_cents: int) -> str:
        """Return a payment reference, or raise PaymentDeclined."""
        ...

# Pretend third-party SDK: dollars as floats, its own vocabulary, its own errors
class AcmePayClient:
    def create_charge(self, amt: float, currency: str, meta: dict) -> dict:
        if amt > 100:
            return {"status": "failed", "failure_code": "card_declined"}
        return {"status": "succeeded", "id": "ch_123"}

class AcmePayAdapter:
    def __init__(self, client: AcmePayClient) -> None:
        self._client = client
    def charge(self, order_id: str, amount_cents: int) -> str:
        resp = self._client.create_charge(amount_cents / 100, "usd", {"order": order_id})
        if resp["status"] != "succeeded":
            raise PaymentDeclined(resp["failure_code"])
        return resp["id"]

gw: PaymentGateway = AcmePayAdapter(AcmePayClient())
print(gw.charge("o-1", 2500))
try:
    gw.charge("o-2", 25000)
except PaymentDeclined as e:
    print("declined:", e)
ch_123
declined: card_declined

Notice the adapter does three jobs: it converts units (cents to dollars), translates the provider's response into our return value, and translates the provider's failure into our PaymentDeclined exception. That last one is easy to forget and is what stops the provider's types leaking into the rest of the code (the leaky abstractions of chapter 3).

Use it when you depend on something you do not control: a vendor SDK, a legacy system, an external API. Do not wrap everything reflexively. Wrapping the standard library's json module "in case we change JSON libraries" costs code today for a change that almost never comes. Wrap at the boundaries that are volatile or that you want to fake in tests.

Facade: one front door

Problem. Doing something ordinary takes calls to three subsystems in the right order, and every caller repeats that choreography.

Solution. Offer one simple object that exposes the common operation and hides the sequence. A facade does not forbid direct access to the subsystems; it just gives the common case an easy road. (This is "make the common case simple" from chapter 3, as a pattern.)

# Facade
class Inventory:
    def reserve(self, sku, n): print(f"  inventory: reserved {n} x {sku}")
class Payments:
    def charge(self, cents): print(f"  payments: charged {cents}"); return "pay-1"
class Shipping:
    def book(self, addr): print(f"  shipping: booked to {addr}"); return "ship-1"

class Checkout:
    """One simple entry point over three subsystems."""
    def __init__(self, inv, pay, ship):
        self._inv, self._pay, self._ship = inv, pay, ship
    def place_order(self, sku, qty, cents, addr):
        self._inv.reserve(sku, qty)
        pay = self._pay.charge(cents)
        ship = self._ship.book(addr)
        return {"payment": pay, "shipment": ship}

print(Checkout(Inventory(), Payments(), Shipping()).place_order("tea", 2, 900, "1 High St"))
  inventory: reserved 2 x tea
  payments: charged 900
  shipping: booked to 1 High St
{'payment': 'pay-1', 'shipment': 'ship-1'}

Facade and adapter look alike (both wrap things) but have different goals. An adapter makes one existing interface match another interface you already expect. A facade invents a new, simpler interface over several things. Do not let a facade grow into a god object (see below) that every feature is dumped into; it should coordinate, not contain the business rules.

Observer: tell whoever is interested

Problem. When an order is placed, you must send an email, update statistics and award loyalty points. If place_order calls all three directly, it knows about every feature that ever cares, and adding the fourth means editing the core.

Solution. The observer pattern (a close cousin of publish-subscribe, or pub-sub): the publisher announces "an order was placed" and a list of subscribers each react. The publisher knows nothing about who is listening.

# Observer, in-process
from collections import defaultdict
from typing import Callable

class EventBus:
    def __init__(self):
        self._subs: dict[str, list[Callable]] = defaultdict(list)
    def subscribe(self, topic: str, handler: Callable) -> None:
        self._subs[topic].append(handler)
    def publish(self, topic: str, payload: dict) -> None:
        for h in self._subs[topic]:
            h(payload)

bus = EventBus()
bus.subscribe("order_placed", lambda e: print("email: thanks for order", e["id"]))
bus.subscribe("order_placed", lambda e: print("stats: +1 order,", e["cents"], "cents"))
bus.publish("order_placed", {"id": "o-9", "cents": 900})

# The catch: handlers run in the publisher's call, in order; an exception stops the rest
def broken(e): raise RuntimeError("email server down")
bus2 = EventBus()
bus2.subscribe("order_placed", broken)
bus2.subscribe("order_placed", lambda e: print("stats never runs"))
try:
    bus2.publish("order_placed", {"id": "o-10", "cents": 1})
except RuntimeError as e:
    print("publisher sees handler's failure:", e)
email: thanks for order o-9
stats: +1 order, 900 cents
publisher sees handler's failure: email server down

The second half of the example is the part tutorials skip. This bus is synchronous: handlers run inside publish, in order. So a slow email handler slows the order request, and a failing handler breaks the publisher and silently skips everyone after it. You have decoupled the code's knowledge, but not its runtime. Real in-process buses usually catch and log handler errors, and many move slow handlers to a background queue.

Use it when several independent reactions follow one fact, and you expect more over time. Do not use it when there is exactly one reaction and it must happen (just call it: the control flow stays readable), or when order and failure matter, because event-driven control flow is notoriously hard to follow in a debugger. Chapter 14 takes this idea across process boundaries, where "who is listening, and did they get it?" turns into a whole new set of problems.

Decorator: add behaviour around a call

Problem. You want logging and retries around the payment call, without editing the gateway, and in different combinations for different environments.

Solution. The GoF decorator pattern: wrap an object in another object with the same interface that adds behaviour before or after delegating. Because the interface is unchanged, decorators stack, and the caller cannot tell how many layers there are.

Here is the pattern as the book describes it, followed by the Python @ syntax doing a related job. They are easy to conflate, so read the comments:

# Decorator: GoF pattern vs Python @decorator
import functools, time

# (a) GoF Decorator: same interface, wraps an object, added at construction
class Gateway:
    def charge(self, cents): return f"paid {cents}"

class LoggingGateway:
    def __init__(self, inner): self._inner = inner
    def charge(self, cents):
        print("log: charge", cents)
        return self._inner.charge(cents)

class RetryingGateway:
    def __init__(self, inner, attempts=3): self._inner, self._n = inner, attempts
    def charge(self, cents):
        for i in range(self._n):
            try:
                return self._inner.charge(cents)
            except TimeoutError:
                print("retry", i + 1)
        raise TimeoutError("gave up")

class FlakyGateway:
    def __init__(self): self.n = 0
    def charge(self, cents):
        self.n += 1
        if self.n < 3: raise TimeoutError
        return f"paid {cents}"

g = LoggingGateway(RetryingGateway(FlakyGateway()))
print(g.charge(500))

# (b) Python @decorator: syntax for wrapping a function; here used to implement the same idea
def retry(attempts=3):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*a, **kw):
            for i in range(attempts):
                try:
                    return fn(*a, **kw)
                except TimeoutError:
                    print("retry", i + 1)
            raise TimeoutError("gave up")
        return wrapper
    return deco

state = {"n": 0}
@retry(attempts=3)
def fetch_rate():
    state["n"] += 1
    if state["n"] < 2: raise TimeoutError
    return 1.08
print(fetch_rate(), fetch_rate.__name__)

# (c) @ syntax is not always the pattern: @staticmethod or @property decorate, but this isn't GoF
# and the GoF pattern needs no @ at all.
log: charge 500
retry 1
retry 2
paid 500
retry 1
1.08 fetch_rate

Python's @decorator is not the Decorator pattern

They are related, not identical. The GoF Decorator is a design pattern about objects: wrap an object in another that has the same interface, composed at runtime (Logging(Retrying(gateway))), with no special syntax. Python's @ syntax is a language feature: @retry above a function is shorthand for fetch_rate = retry(fetch_rate), applied once when the function is defined. It is a convenient way to implement the same idea for functions, and a decorated function wraps another function with the same call signature, so in spirit it matches. But @ can also do things that are not the pattern at all: register a function (@app.route("/") returns the function unchanged), transform a class (@dataclass), or mark a method (@property, @staticmethod). And the pattern needs no @. Use whichever form fits: @ for cross-cutting wrapping of plain functions fixed at definition time; wrapper objects when you need to choose and order layers at runtime or wrap something with several methods.

Use it when you add the same cross-cutting behaviour (logging, retries, timing, caching) to many calls. This is the shape of the resilience toolkit in chapter 17, and chapter 8 returns to it as middleware. Do not stack decorators until nobody can tell the order things happen in. Retrying also demands care: only wrap idempotent operations, or you may charge a card twice. (The RetryingGateway above is a sketch; chapter 17 adds backoff, jitter and limits.)

Factory and dependency injection

Problem. CheckoutService needs a payment gateway. If it writes AcmePayAdapter(os.environ["KEY"]) inside its own constructor, it is welded to Acme and you cannot test it without calling Acme's servers.

Solution, part one: dependency injection. Dependency injection (DI) is a fancy name for a simple idea: pass in the things an object needs instead of letting it construct them. The commonest form is constructor injection: dependencies arrive as constructor arguments. You do not need a framework, just a constructor parameter.

Solution, part two: a factory. Somebody still has to decide which concrete class to build. A factory is a function (or method) whose job is to build the right object. In small programs it is a plain function that reads configuration:

# Factory: one function decides which concrete class to build
class FakeGateway:
    def charge(self, order_id, cents): return "fake-ref"

class AcmePayAdapter:
    def __init__(self, api_key): self._key = api_key
    def charge(self, order_id, cents): return f"acme-ref-{order_id}"

def make_gateway(settings: dict):
    kind = settings.get("PAYMENTS", "fake")
    if kind == "acme":
        return AcmePayAdapter(settings["ACME_KEY"])
    if kind == "fake":
        return FakeGateway()
    raise ValueError(f"unknown PAYMENTS setting: {kind!r}")

print(make_gateway({}).charge("o-1", 100))
print(make_gateway({"PAYMENTS": "acme", "ACME_KEY": "k"}).charge("o-1", 100))
fake-ref
acme-ref-o-1

Together these give the composition root: the single place near the program's entry point where real objects are chosen and wired together. Everything else receives its collaborators and stays ignorant of the concrete classes. The payoff is in tests, so step through exactly what changes between production and a test:

Step through

Swapping a real payment adapter for a fake

  1. The service depends on a port, not a class. CheckoutService is written against PaymentGateway, a protocol. It never imports a provider and never builds one: the gateway arrives through its constructor.
  2. Production wiring. At startup the composition root builds an AcmePayAdapter and hands it to the service. A real charge goes out through the adapter to Acme's API over the network.
  3. Test wiring: swap one line. In a test, the composition (here, the test's setup) builds a FakeGateway instead. The service's code is identical; only what was injected changed. No network, no API key, no flakiness.
  4. The fake can be inspected. Because the fake records every charge, the test asserts what the service asked the gateway to do: right order id, right amount.
  5. The fake can fail on demand. Real providers rarely decline when you want them to. FakeGateway(decline=True) lets you test the failure path deterministically, which is often the code that matters most.

Here is the code behind the diagram, with the two tests actually run:

# Dependency injection without a framework, and a test with a fake
import unittest

class PaymentDeclined(Exception): pass

class FakeGateway:
    def __init__(self, decline=False): self.charges = []; self._decline = decline
    def charge(self, order_id, cents):
        if self._decline: raise PaymentDeclined("card_declined")
        self.charges.append((order_id, cents)); return "fake-ref"

class CheckoutService:
    def __init__(self, gateway):          # constructor injection
        self._gateway = gateway
    def pay(self, order_id, cents):
        try:
            return {"ok": True, "ref": self._gateway.charge(order_id, cents)}
        except PaymentDeclined as e:
            return {"ok": False, "reason": str(e)}

# composition root: the ONE place real objects are chosen
def build_app(env="prod"):
    if env == "test":
        return CheckoutService(FakeGateway())
    raise NotImplementedError("real adapter would be built here")

class CheckoutTests(unittest.TestCase):
    def test_success_records_charge(self):
        fake = FakeGateway()
        self.assertEqual(CheckoutService(fake).pay("o-1", 900), {"ok": True, "ref": "fake-ref"})
        self.assertEqual(fake.charges, [("o-1", 900)])
    def test_decline_is_reported_not_raised(self):
        r = CheckoutService(FakeGateway(decline=True)).pay("o-2", 900)
        self.assertEqual(r, {"ok": False, "reason": "card_declined"})

if __name__ == "__main__":
    unittest.main()
test_decline_is_reported_not_raised (__main__.CheckoutTests.test_decline_is_reported_not_raised) ... ok
test_success_records_charge (__main__.CheckoutTests.test_success_records_charge) ... ok

----------------------------------------------------------------------
Ran 2 tests in 0.000s

OK

Use it when an object talks to something slow, external, non-deterministic or expensive (network, clock, randomness, database). Do not reach for a DI framework or container before you feel the pain: in Python, constructor arguments and one main() that wires things together scale a long way. Chapter 7 develops this into a testing strategy.

Template method vs composition

Problem. Several reports share the same skeleton (select rows, then render them) and differ in the steps.

Template method (inheritance). A base class defines the algorithm and calls overridable steps; subclasses fill them in. Composition passes the steps in as collaborators instead.

# Template method (inheritance) vs composition
class ReportBase:
    def run(self, rows):
        return self.render(self.select(rows))
    def select(self, rows): return rows
    def render(self, rows): raise NotImplementedError

class PaidCsv(ReportBase):
    def select(self, rows): return [r for r in rows if r["paid"]]
    def render(self, rows): return "\n".join(f'{r["id"]},{r["cents"]}' for r in rows)

# Composition: two small functions plugged in
def report(rows, select, render):
    return render(select(rows))

rows = [{"id": "a", "cents": 100, "paid": True}, {"id": "b", "cents": 200, "paid": False}]
print(PaidCsv().run(rows))
print(report(rows, lambda rs: [r for r in rs if r["paid"]],
             lambda rs: ", ".join(r["id"] for r in rs)))
a,100
a

Both work. The widely repeated advice, which the GoF book itself states, is "prefer composition over inheritance". The reasons: a subclass is welded to its parent's internals (a change in the base class can break every child); you inherit all of the parent's methods whether you want them or not; and you can only inherit from one thing at a time, whereas you can combine any number of collaborators. With composition you can mix and match select and render freely and test each piece alone.

That is a heuristic, not a law. Inheritance is fine for a genuine "is-a" relationship with a stable base, and for frameworks that deliberately offer hook methods (Django's class-based views, unittest.TestCase's setUp). The warning sign is a deep hierarchy where you have to read three parent classes to understand one method.

SOLID, compactly

SOLID is a set of five design heuristics popularised by Robert C. Martin. Each is useful as a question to ask during review; none is a theorem, and applying all five maximally gives the over-engineered code that gives patterns a bad name.

PrincipleIn a sentenceExample / caveat
Single responsibilityA module should have one reason to change.Tax rules and PDF layout change for different reasons, so don't put both in Invoice. Caveat: "one responsibility" is vague; splitting too finely scatters logic.
Open/closedOpen for extension, closed for modification: add behaviour without editing tested code.A new discount is a new function passed to price, not a new branch in it. Caveat: you can't predict every extension, so don't pre-build hooks.
Liskov substitutionAnything that claims to be a Foo must work wherever a Foo is expected, honouring its contract.An adapter whose get raises where the port promised None breaks callers. This is chapter 3's contract idea.
Interface segregationPrefer several small interfaces to one big one.A Protocol with just save and get, not the whole database API. Python's structural typing makes this nearly free.
Dependency inversionHigh-level logic should depend on abstractions, not on concrete low-level details.The service depends on PaymentGateway, not AcmePayAdapter. This is the root of hexagonal architecture in chapter 5.

The honest caveat: SOLID came out of class-heavy object-oriented practice and fits that world best. Many experienced engineers argue the principles are most valuable as a diagnostic after the fact ("why was this change so painful?") rather than a checklist before. Liskov and dependency inversion are the two with the clearest payoff.

Anti-patterns

An anti-pattern is a common response to a problem that looks sensible and makes things worse. Four to know:

God object

One class that knows and does everything: OrderManager with 80 methods. Every change touches it, every test needs it, every team edits it. Fix: split by reason to change; move behaviour to where the data lives.

Singleton as hidden global

"There should be only one" implemented as a global accessor like Config.get(). Any code can reach it, so dependencies are invisible and tests interfere with each other. Fix: create one instance in main() and pass it down.

Premature abstraction

An interface and factory for the one implementation you will "probably" need to swap someday. YAGNI ("you aren't gonna need it", from Extreme Programming) says build for today's requirement. Fix: abstract when the second case arrives.

Copy-paste (and its opposite)

Duplication is a cost, but the wrong shared abstraction is a bigger one. The rule of three: tolerate two copies; on the third, you finally know what varies, so extract it.

The singleton is worth seeing concretely, because the code looks harmless:

# Singleton as hidden global vs injected dependency
class Config:                      # the "singleton"
    _instance = None
    def __init__(self): self.tax_rate = 0.2
    @classmethod
    def get(cls):
        if cls._instance is None: cls._instance = cls()
        return cls._instance

def price_hidden(net):             # looks pure; secretly reads global state
    return round(net * (1 + Config.get().tax_rate))

def price_explicit(net, tax_rate): # everything it needs is in the signature
    return round(net * (1 + tax_rate))

print(price_hidden(1000))
Config.get().tax_rate = 0.0        # some other test/module changes it...
print(price_hidden(1000), "<- same call, different answer")
print(price_explicit(1000, 0.2), price_explicit(1000, 0.0))
1200
1000 <- same call, different answer
1200 1000

price_hidden looks like a function of net, but its answer secretly depends on mutable state elsewhere. price_explicit says everything it needs in its signature, so it is testable, and the same call always gives the same answer.

Common misconception

"Duplication is always bad, so remove it the moment you see it." Two pieces of code that look the same but change for different reasons (say, the tax rule for invoices and for shipping labels) should stay separate. Merge them, and every future change to one needs a flag to protect the other. Sandi Metz's phrase for it is that duplication is far cheaper than the wrong abstraction.

Distributed systems connection

Each pattern here has a bigger sibling at the system level. An adapter becomes an anti-corruption layer between services; a facade becomes an API gateway; an in-process observer becomes a message broker with subscribers on other machines (chapter 14), where delivery, ordering and duplicate handling suddenly matter; a decorator becomes the retry, timeout and circuit-breaker wrappers of chapter 17. Understanding the in-process version, including its quiet failure modes, is the cheapest way to understand the distributed one.

Key takeaways

  • Patterns are named solutions to recurring problems (GoF, 1994); the main value is shared vocabulary. Their main danger is applying them before the problem exists.
  • Strategy in Python is usually just a function argument. Adapter protects you from foreign interfaces and their errors. Facade gives the common case a simple front door.
  • In-process observer decouples knowledge, not timing: handlers run synchronously unless you make them not.
  • The GoF Decorator wraps objects with the same interface; Python's @ is a syntax for wrapping functions that can implement the idea but also does unrelated things.
  • Constructor injection plus one composition root gives testable code without a framework: swap a real adapter for a fake and test even the failure paths.
  • Prefer composition over inheritance as a default; treat SOLID as review questions, not rules.
  • Avoid god objects, singletons as hidden globals and premature abstraction. Wait for the rule of three before extracting shared code.

Handlers run synchronously in the publisher's call stack, so an exception propagates and stops the loop. Real buses usually catch and log handler errors or run handlers asynchronously.

With only two examples you are guessing which parts are the same and which vary. A wrong shared abstraction is more expensive than a little duplication. The third occurrence gives you the information to abstract well.

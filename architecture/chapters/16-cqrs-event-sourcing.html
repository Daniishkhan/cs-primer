CQRS & Event Sourcing

Two ideas that are constantly mentioned together and are quite independent. CQRS says the model you write with and the model you read with need not be the same. Event sourcing says the truth is not the current state but the list of everything that happened, from which any state can be recomputed. Each is powerful, each is easy to overuse, and this chapter shows both the payoff and the price.

Why this matters

Most systems store "what is true now" and overwrite it with every change. That is simple and usually right. But it throws away how you got here, makes some questions impossible ("what was this balance on 1 March?", "why was this order cancelled?"), and forces one data shape to serve both rule-heavy writes and query-heavy reads. CQRS and event sourcing are the two standard escape hatches. Knowing them lets you recognise when a problem genuinely has this shape, such as ledgers, audit-critical domains and read-heavy dashboards, and when you are being sold a heavy pattern for a simple CRUD application.

CQRS: separate models for writing and reading

The name builds on Bertrand Meyer's older principle of command-query separation: a method should either change state (a command) or return information (a query), not both. CQRS, Command Query Responsibility Segregation, a pattern popularised by Greg Young, takes that separation up to the level of models. You build two:

Write model
Handles commands (PlaceOrder, Withdraw). Its job is to enforce invariants, the rules that must always hold ("a balance may not go below zero"). It is shaped around behaviour and consistency, typically as aggregates from chapter 6, and is tuned for correct updates of small amounts of data.
Read model
Answers queries. It is denormalised and shaped for the screens or reports that use it: a "My orders" list with the customer's name and the item titles already joined in, a dashboard row per day. There may be several read models for different needs, and they may live in different stores (a relational table for lists, a search index for text, a cache for the hottest pages).

Something has to keep the read side up to date. In the common design the write side emits events (or changes) and a projector consumes them and updates the read models. That reuses the machinery of chapter 14, and it means the read side is eventually consistent with the write side: for a moment after a write, a query may not reflect it. Chapter 14's tricks for the user interface (return the written result, version tokens, honest status) apply directly.

Analogy: the kitchen and the menu board

A restaurant has one place where the rules are applied and the real work is done: the kitchen. It tracks exactly how many portions of each dish are left and refuses to promise the last lamb shank twice. Customers, though, do not interrogate the kitchen. They read the menu board by the door, which is shaped for reading: dishes grouped by type, sold-out items crossed out. The board is updated from the kitchen's state, a few minutes behind. Two different structures for two different jobs.

Where it breaks down: a chalkboard is updated by a human who walks over with chalk and can forget. A projector is code that consumes a stream, and its failure modes are different: it can fall behind, crash halfway, or apply an event twice, so it needs the idempotency and offset tracking of chapter 14.

When CQRS helps, and when it is overkill

It earns its keep when reads and writes really are different problems:

  • Very different shapes. Writes touch one aggregate under strict rules; reads join across many things for screens. Forcing both through one normalised model leads to either clumsy writes or slow, complicated queries.
  • Very different scale. Reads often outnumber writes by orders of magnitude. A separate read store can be scaled, cached and replicated on its own, without touching the transactional core.
  • Several different views of the same facts, such as search, reporting and per-user feeds, each wanting its own structure.

It is overkill when the application is mostly forms over a database, when one model serves both sides without strain, or when the team cannot yet cope with eventual consistency. Costs are real: two models to keep aligned, a synchronisation mechanism to build and monitor, stale reads to design around, and more moving parts to debug. A modest, often-sufficient version of CQRS needs none of that infrastructure: use the same database, but write through a rich domain model and read through plain SQL views or queries built for the screens. Many experienced engineers argue you should start there and add separate stores only when a measurement forces it.

Common misconception

CQRS is not event sourcing, and does not require it. You can have separate read and write models fed by ordinary database change capture, with the write side storing plain current state. Conversely, you can event-source an aggregate and read it back only by replaying its own events, with no separate read model. The two combine naturally (events are exactly what projectors need) but they solve different problems: CQRS is about shape of models, event sourcing is about what you store.

Event sourcing: state is the fold of the events

Ordinary persistence stores the current state: the account row says balance 113, and each update overwrites the last. Event sourcing stores instead the sequence of events that happened to each entity, append-only, and treats the current state as something derived from them. The core formula:

state = fold(apply, initial_state, events)

A fold (or reduce) walks through the events in order, applying each to the running state. For a bank account: start at zero; Deposited 100 makes it 100; Withdrawn 25 makes it 75; and so on. The function apply(state, event) must be a pure function: no clocks, no randomness, no calls out, so replaying the same events always gives the same state.

Event store
An append-only store of events, grouped into a stream per aggregate (all events for account 7, in order). It can be a purpose-built product or just a database table with columns like (stream_id, version, type, data, metadata) and a unique constraint on (stream_id, version). That constraint is also how you get safe concurrency: a command loads the stream at version N, decides, and appends version N+1, and if someone else got there first the insert fails and the command retries. No update or delete ever happens.
Rebuilding an aggregate
To handle a command, load the aggregate's events, fold them into its current state, check the rules against that state, and if the command is allowed, append the new event(s). The aggregate is a short-lived in-memory object; the events are the record.
Snapshot
A saved copy of the folded state at a given position in the stream. To rebuild, load the latest snapshot and fold only the events after it. It is purely an optimisation: if you delete every snapshot, nothing is lost.
Projection
A read model derived from events by a separate consumer: a table of balances per account, monthly statements, a search index. It keeps its own position in the stream, so it can lag.
Replay
Reading the events again from the beginning (or from a chosen point) to rebuild state, to build a brand-new projection, or to recompute with a corrected rule.

Play with the pieces. Append events, watch the balance recomputed from them, advance the projection separately and see it lag, cut a snapshot to reduce the replay cost, and drag the slider to ask what the balance was after any earlier event.

Analogy: the accountant's ledger

A bookkeeper never erases an entry in the ledger. If a payment was recorded wrongly, they add a correcting entry. The balance on the last page is not the truth; it is a running total of the entries, which are the truth. Ask what the balance was on 1 March and they add up the entries to that date. An auditor can follow every number back to the entry that caused it. Event sourcing is the ledger discipline applied to all your data.

Where it breaks down: a paper ledger's entries are never reinterpreted. In software you may later want to change what an event means, or find that you recorded too little, and the ledger cannot be rewritten without breaking the promise of immutability. That is the source of most of the hard parts below.

What you get

  • A complete audit trail by construction. The history is not a side table that might drift out of sync with the state: it is the state. If events carry who and why (metadata such as user id and the command that caused it), "how did this get here?" is answered directly.
  • Temporal queries. Fold the events up to any date to get the state as of then. "What was the balance on 1 March?" is a prefix fold, not a restore from backup.
  • New read models after the fact. Because the history is complete, a view you did not think of at design time can be built later by replaying events. You are not limited to the questions you anticipated when you chose which columns to keep.
  • Debugging and testing by replay. You can reproduce a bug by replaying the exact events that led to it, and test rules by giving a list of events and a command and asserting the new events.
  • A natural source of integration events for the rest of the system (chapter 14).

A bank account in code

Here is the idea in about eighty lines: an account stored as Opened, Deposited and Withdrawn events, a fold function, a snapshot, a temporal query and a projection that builds a statement. Amounts are in pennies to avoid floating-point surprises.

from dataclasses import dataclass
from datetime import date


@dataclass(frozen=True)
class Event:
    kind: str            # "Opened" | "Deposited" | "Withdrawn"
    amount: int          # pennies; 0 for Opened
    day: date


def apply(balance: int, e: Event) -> int:
    """The fold step: (state, event) -> new state. No I/O, no clock, no randomness."""
    if e.kind == "Deposited":
        return balance + e.amount
    if e.kind == "Withdrawn":
        return balance - e.amount
    return balance


class EventStore:
    def __init__(self):
        self.events: list[Event] = []          # append-only
        self.snapshot = (0, 0)                 # (events covered, balance at that point)

    def append(self, e: Event):
        self.events.append(e)

    def take_snapshot(self):
        self.snapshot = (len(self.events), self.balance()[0])

    def balance(self) -> tuple[int, int]:
        """Current state = snapshot + fold of the events after it. Returns (balance, events replayed)."""
        n, bal = self.snapshot
        for e in self.events[n:]:
            bal = apply(bal, e)
        return bal, len(self.events) - n

    def balance_on(self, day: date) -> tuple[int, int]:
        """Temporal query: fold only the events up to and including `day`."""
        bal, used = 0, 0
        for e in self.events:
            if e.day > day:
                break
            bal, used = apply(bal, e), used + 1
        return bal, used


class StatementProjection:
    """A read model: one row per event, kept up to date by listening to the log."""
    def __init__(self):
        self.rows, self.balance, self.position = [], 0, 0

    def catch_up(self, store: EventStore):
        for e in store.events[self.position:]:
            self.balance = apply(self.balance, e)
            self.rows.append((e.day.isoformat(), e.kind, e.amount, self.balance))
        self.position = len(store.events)


store = EventStore()
for e in [Event("Opened", 0, date(2026, 1, 5)), Event("Deposited", 10_000, date(2026, 1, 20)),
          Event("Withdrawn", 2_500, date(2026, 2, 10)), Event("Deposited", 5_000, date(2026, 2, 28)),
          Event("Withdrawn", 1_200, date(2026, 3, 15))]:
    store.append(e)

fmt = lambda p: f"{p / 100:,.2f}"
bal, n = store.balance()
print(f"balance now: {fmt(bal)}  (replayed {n} events)")
bal, n = store.balance_on(date(2026, 3, 1))
print(f"balance on 1 March: {fmt(bal)}  (replayed {n} events)")

store.take_snapshot()                      # cut a snapshot after 5 events
store.append(Event("Deposited", 300, date(2026, 3, 20)))
bal, n = store.balance()
print(f"after snapshot + 1 new event: {fmt(bal)}  (replayed {n} event)")

view = StatementProjection(); view.catch_up(store)
print("\nstatement projection:")
for row in view.rows:
    print("  %s  %-9s %8s  balance %s" % (row[0], row[1], fmt(row[2]), fmt(row[3])))

balance on 1 March: 125.00  (replayed 4 events)
after snapshot + 1 new event: 116.00  (replayed 1 event)

statement projection:
  2026-01-05  Opened        0.00  balance 0.00
  2026-01-20  Deposited   100.00  balance 100.00
  2026-02-10  Withdrawn    25.00  balance 75.00
  2026-02-28  Deposited    50.00  balance 125.00
  2026-03-15  Withdrawn    12.00  balance 113.00
  2026-03-20  Deposited     3.00  balance 116.00

Check the results against the code. The balance now is 113.00 after folding all five events. The balance on 1 March is 125.00 because only the first four events fall on or before that date (the withdrawal of 12.00 was on 15 March), a question the plain state "113" could never answer. After the snapshot is taken at five events and one more deposit arrives, the current balance needs to replay just one event instead of six. The statement projection, built independently by reading the same events, shows each event with its running balance.

The hard parts

Event sourcing's benefits are real, and so are its costs. Anyone recommending it owes you the following list.

Event schema evolution

Events live for as long as the system does. The shape you chose in year one will be read by code written in year five, and the old events can never be edited. Compatibility rules are those of chapter 10 and data chapter 3, but with a harder constraint: every historical version must remain readable forever. The usual device is upcasting: when an old event is loaded, a small function converts it to the current shape in memory (for example, splitting a single name field into first_name and last_name, or filling in a default for a new field). Code then only ever deals with the newest version. Where a change is too big for that, teams may run a one-off migration that writes a new stream, but that breaks the "never rewrite history" purity and is done with great care. The best defence is to design events as meaningful business facts (AddressCorrected rather than AccountUpdated), because events that record intent age far better than events that record field changes.

Deleting data: privacy law and immutability

An append-only log that must never change collides with laws such as the GDPR's right to erasure. You cannot simply delete a person's events without breaking the fold. Common approaches: keep personal data out of the events and store it in a separate, deletable place referenced by id; or crypto-shredding, in which each person's personal fields are encrypted in the events with a key held elsewhere, and "deleting" the person means destroying their key, leaving ciphertext that can no longer be read. Whether a technique satisfies a given legal requirement is a question for your legal advisers, but the architecture needs deciding up front: retrofitting it into a log full of plain-text personal data is painful.

Eventually consistent projections

The projections lag, as the widget showed, so all the user-interface issues of chapter 14 apply, and a command that needs to read other aggregates' data cannot assume the projection is current. Rule enforcement belongs to the aggregate, which is rebuilt from the events and so is always current for its own stream; cross-aggregate rules need sagas or accepting a window of inconsistency (chapter 15).

Expensive rebuilds

Replaying billions of events to build a new projection takes hours or days, and it should not disturb live traffic. Mitigations: snapshots for aggregates; building the new projection alongside the old one and switching over when it has caught up; and keeping projectors fast and idempotent. Projections that call out to other services during replay will hammer them, so a projector should depend only on the events.

Other costs

  • Mistakes are permanent. A badly designed event stays in the history. Corrections are new events.
  • Ad-hoc queries against the store itself are awkward; everything you want to query needs a projection.
  • A real learning curve. Developers must think in events, folds and eventual consistency, and the tooling is less common than SQL.

Common misconception

"We'll event-source everything so we never lose any information." Applied across an entire system, event sourcing usually creates far more cost than value. Many experienced engineers recommend it only for the parts of a domain where history is itself the product (ledgers, bookings, regulated audit trails) and plain CRUD for the rest. Another quiet trap is publishing a "full audit log" and calling that event sourcing: a log kept next to mutable state is just an audit table, and can disagree with it; in event sourcing the log is the state.

Where this sits among logs

You have now met the log in four disguises. The database's own write-ahead log records low-level changes so it can recover from a crash (data chapter 13); the database is the state and the log serves it. Change data capture reads that log to publish row changes to others (data chapter 19, which also compares CDC with event sourcing directly). An event-driven system's log carries integration events between services (chapter 14). And in event sourcing the log of domain events is the primary store, with every other representation derived from it.

The difference is who owns the meaning. A WAL record says "page 4017 changed"; a CDC record says "row 12 in orders changed"; an event-sourced event says "the customer corrected the shipping address". Only the last is expressed in the language of the business, and it is also the only one that you, rather than the database engine, are responsible for keeping stable forever. The idea at the other end of the spectrum, that the log really can be the whole database, appears in Aurora: The Log Is the Database in the data course, and the single-threaded business core fed by an input event log at the heart of the LMAX case shows event sourcing under extreme performance demands: state kept in memory, rebuilt by replaying the log.

Distributed systems connection

A replicated state machine, the idea behind consensus-based systems such as Raft (networking chapter 20), is event sourcing at the infrastructure level: every node applies the same ordered log of commands with a deterministic function, so all end in the same state. The purity of apply in this chapter is the same requirement. Read-model lag is replication lag by another name (data chapter 15), and "rebuild from the log" is how replicas, caches and indexes are made disposable. Next, in the final part of the course, we turn from how to structure systems to how they survive failure and how to change them while they run.

Key takeaways

  • CQRS uses separate models for writes (commands and invariants) and reads (denormalised views), possibly in separate stores. It is a modelling choice, independent of event sourcing.
  • It helps when read and write shapes or scales differ greatly; for plain CRUD it is overkill. A rich write model with simple SQL views is often enough.
  • Event sourcing stores the append-only sequence of events; current state is fold(apply, initial, events), with apply a pure function.
  • Snapshots cut replay cost, projections serve queries (and lag), and replay lets you build new views or ask temporal questions like "balance on 1 March".
  • The audit trail is exact because the history is the state, but the costs are real: event schema evolution (upcasting), deletion and privacy (crypto-shredding), eventual consistency and slow rebuilds.
  • Use event sourcing where history is the product; use ordinary persistence elsewhere.
  • The database's WAL, CDC, integration events and event sourcing are all logs, but only event sourcing makes the domain-level log the source of truth.

Check your understanding

Which statement about CQRS and event sourcing is correct?

  1. CQRS requires event sourcing
  2. They are independent: you can use either without the other
  3. Event sourcing requires a separate read database
  4. They are two names for the same pattern
CQRS separates the write and read models; event sourcing changes what is stored. They combine well, but a CQRS system can use ordinary state storage, and an event-sourced aggregate can be read back by replaying its own events.

An event-sourced account has events Opened, Deposited 100, Withdrawn 25, Deposited 50. What is the balance, and how is it computed?

  1. 100, the largest event
  2. 125, read from a balance column that is updated in place
  3. 175, the sum of all event amounts
  4. 125, by folding the events: 0, then +100, then -25, then +50
State is the fold of the events in order, with withdrawals subtracting. Adding every amount ignores the event types, and in event sourcing there is no mutable balance column: the balance is derived.

What does a snapshot do in an event-sourced system?

  1. It stores the folded state at a position so a rebuild replays only later events; it is an optimisation, and deleting it loses nothing
  2. It replaces the older events, which can then be deleted
  3. It makes the read model strongly consistent
  4. It is the source of truth for the aggregate
The events remain the truth; a snapshot is a cache of the fold. It shortens rebuilds but is not authoritative and does not change consistency.

A regulator requires you to erase a customer's personal data, but your event store is append-only. Which approach is commonly used?

  1. Edit the old events in place and hope the folds still work
  2. Stop using events for customers
  3. Keep personal data out of events (or encrypt it per person) so that deleting the data or its key makes it unreadable, which is crypto-shredding
  4. Truncate the whole event store every month
Editing history breaks the guarantees and any projection built on it; truncating destroys the audit trail. Separating or encrypting personal data lets you honour deletion while the event sequence stays intact. Check with legal advisers that the approach meets your obligations.

Which situation is the best fit for CQRS with separate read stores?

  1. A small admin tool with forms over five tables
  2. A product where writes follow strict rules on small aggregates but reads are heavy, join across many things, and scale far beyond writes
  3. A prototype that will be thrown away next week
  4. A service whose reads and writes use exactly the same shape and low traffic
Separate models pay off when the two sides differ in shape or scale. For simple forms or uniform low-traffic services, they add synchronisation, staleness and operational cost for no benefit.

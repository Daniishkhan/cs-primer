Testability as Architecture

If a piece of code is hard to test, the difficulty is a report from your design: something is coupled to something it should not be. This chapter turns that hunch into tools. You will learn to find the seams where behaviour can be swapped, to use the right kind of test double (and to prefer fakes), to make time and randomness injectable, and to put a safety net under legacy code before touching it.

Why this matters

Tests are not only a quality check; they are the main way a team keeps the freedom to change its code. A design with fast, trustworthy tests can be refactored on a Tuesday afternoon. A design whose tests are slow, flaky, or welded to the implementation can only be changed with dread. Because the same things make code easy to test and easy to change (low coupling, clear boundaries, explicit dependencies), testability works as an early-warning instrument for architecture. If you cannot write a quick test of a rule, ask what is in the way. The answer is almost always a dependency that should have been a parameter.

If it is hard to test, it is probably badly coupled

Try to write a test for each of these, and notice what stops you:

  • def is_expired(self): return datetime.now() - self.created > HOLD. To test expiry you must wait fifteen minutes, or change the system clock. Hidden dependency on time.
  • A function that builds its own requests.Session() and calls a payment API. Hidden dependency on the network, constructed inside the code that uses it.
  • A class that reads os.environ["DB_URL"] in its constructor. Hidden dependency on global state.
  • A business rule written inside a SQL CASE expression (chapter 5's before.py). Logic fused to a technology.
  • A singleton that every test shares and that remembers the previous test's data. Shared mutable global state.

Every one of these is the same disease: the code reaches out to fetch the thing it depends on, instead of being handed it. Reaching out makes the dependency invisible in the signature, impossible to substitute, and impossible to control. Being handed it (constructor or function parameter) makes the dependency visible and replaceable. That is dependency injection, the mechanism from chapter 4, and it is exactly what the dependency rule of chapter 5 needed. Testability and the dependency rule are the same property seen from two sides: the core can be run on its own.

Analogy: inspection hatches in a building

A well-built building has inspection hatches: a panel to check the plumbing, a test port on the fire-alarm circuit, a meter you can read. Inspectors can check one system without tearing down a wall. A building with no hatches can still stand, but every check is destructive and expensive, so checks are rare and problems are found late. In architecture terms the hatches are the places where you can substitute or observe behaviour, and the city of modules you built in chapter 2 benefits when each neighbourhood has them at the right places.

Where it breaks down: a hatch costs almost nothing to include while the building is going up and a lot to retrofit; the same is true of software seams, as the legacy section below shows. And, unlike a building, too many seams are harmful: code with a hatch in every wall is hard to read, because behaviour is spread across swappable pieces.

Seams

Michael Feathers gave this idea a name in Working Effectively with Legacy Code (2004). A seam is a place where you can alter behaviour in your program without editing in that place. Every seam has an enabling point: the place where you decide which behaviour to use. The classic form in an object-oriented language is the object seam: a method call on an object whose class you can choose elsewhere.

Feathers also described link seams (changing which library gets linked or which module gets imported) and preprocessing seams (macros, mostly in C). In Python, the language gives you more seams than you may want. Because everything is looked up at run time, tests can monkeypatch: replace module.function or datetime.datetime for the duration of a test. That is a seam, and it is valuable for retrofitting tests onto code you cannot yet change. But a patch is an invisible enabling point (nothing in the code's signature admits the dependency exists) and it couples the test to the exact import path the code happens to use. Prefer a designed seam, a parameter or constructor argument, for code you own. Reserve patching for legacy code on its way to getting one.

Test doubles, precisely

Whatever the seam, the thing you plug in is a test double (like a stunt double standing in for an actor). People say "mock" for all of them, which hides real differences. The vocabulary below follows Gerard Meszaros's xUnit Test Patterns, as popularised by Martin Fowler's essay "Mocks Aren't Stubs".

DummyAn object passed to fill a parameter but never actually used.Satisfy a signaturenothing (if it is touched, the test should fail)

SpyA stub that also records how it was called, so the test can inspect afterwards.Observe outputs that have no readable state (an email was sent)recorded calls, after the fact

The edges blur in practice: Python's unittest.mock.Mock can play a stub (give it a return_value), a spy (inspect call_args afterwards) or a mock (assert_called_once_with), depending on how you use it. What matters is what the test is coupled to: inputs, final state, or the sequence of calls. Here are all five in one small use case, RegisterUser, which validates an email, generates an id, stores the user and sends a welcome email:

# The five kinds of test double, around one tiny use case.
import unittest
from unittest.mock import Mock

class RegisterUser:
    def __init__(self, users, mailer, new_id):
        self.users, self.mailer, self.new_id = users, mailer, new_id
    def __call__(self, email):
        if "@" not in email:
            raise ValueError("invalid email")
        user_id = self.new_id()
        self.users.add(user_id, email)
        self.mailer.send(email, "Welcome!")
        return user_id

# DUMMY: fills a parameter, never used. (Passing it proves the code never touches it.)
dummy_mailer = object()

# STUB: returns canned answers so the test controls the inputs.
def stub_new_id(): return "u-1"

# FAKE: a real, working, simplified implementation (it has behaviour).
class FakeUsers:
    def __init__(self): self.rows = {}
    def add(self, user_id, email): self.rows[user_id] = email

# SPY: a stub that also records how it was used, for assertions afterwards.
class SpyMailer:
    def __init__(self): self.sent = []
    def send(self, to, subject): self.sent.append((to, subject))

class DoubleTests(unittest.TestCase):
    def test_dummy(self):                       # the mailer is irrelevant on the failure path
        with self.assertRaises(ValueError):
            RegisterUser(FakeUsers(), dummy_mailer, stub_new_id)("not-an-email")
    def test_stub_and_fake(self):               # stubbed id in, fake store out; assert on STATE
        users = FakeUsers()
        self.assertEqual(RegisterUser(users, SpyMailer(), stub_new_id)("a@example.com"), "u-1")
        self.assertEqual(users.rows, {"u-1": "a@example.com"})
    def test_spy(self):                         # act first, ask the spy what happened afterwards
        mailer = SpyMailer()
        RegisterUser(FakeUsers(), mailer, stub_new_id)("a@example.com")
        self.assertEqual(mailer.sent, [("a@example.com", "Welcome!")])
    def test_mock(self):                        # expectations declared up front and verified
        mailer = Mock()
        RegisterUser(FakeUsers(), mailer, stub_new_id)("a@example.com")
        mailer.send.assert_called_once_with("a@example.com", "Welcome!")

if __name__ == "__main__":
    unittest.main(verbosity=2)

Prefer fakes for ports

For a port that holds state (a repository, a cache, a clock) a fake is usually the best double. It exercises your code against something that behaves like the real thing, so the test says what should be true afterwards and ignores how the code got there. A mock for the same port makes the test a transcript of the implementation: "get was called once with this argument, then save was called with that object." Any refactor that keeps behaviour but changes the calls breaks the test; the test has become a second copy of the code, and people stop refactoring or stop trusting tests.

Here is the same behaviour, "cancelling an order", tested both ways. Then a harmless refactor, and what each style does about it:

import unittest
from unittest.mock import Mock

class Order:
    def __init__(self, order_id, status="PAID"): self.id, self.status = order_id, status

class AlreadyShipped(Exception): ...

class CancelOrder:                               # version 1
    def __init__(self, repo): self.repo = repo
    def __call__(self, order_id):
        order = self.repo.get(order_id)
        if order.status == "SHIPPED":
            raise AlreadyShipped(order_id)
        order.status = "CANCELLED"
        self.repo.save(order)

class InMemoryRepo:                              # the fake: a real, tiny implementation of the port
    def __init__(self, *orders): self.rows = {o.id: o for o in orders}
    def get(self, order_id): return self.rows[order_id]
    def save(self, order): self.rows[order.id] = order

class MockStyleTests(unittest.TestCase):         # asserts HOW the code talks to its collaborator
    def test_cancel(self):
        order = Order("o-1")
        repo = Mock(); repo.get.return_value = order
        CancelOrder(repo)("o-1")
        repo.get.assert_called_once_with("o-1")
        repo.save.assert_called_once_with(order)

class FakeStyleTests(unittest.TestCase):         # asserts WHAT ended up true
    def test_cancel(self):
        repo = InMemoryRepo(Order("o-1"))
        CancelOrder(repo)("o-1")
        self.assertEqual(repo.get("o-1").status, "CANCELLED")
    def test_shipped_orders_cannot_be_cancelled(self):
        repo = InMemoryRepo(Order("o-2", "SHIPPED"))
        with self.assertRaises(AlreadyShipped): CancelOrder(repo)("o-2")
        self.assertEqual(repo.get("o-2").status, "SHIPPED")

if __name__ == "__main__":
    unittest.main()

Common misconception

"Mocks are bad; never use them." Not quite. Mocks and spies are the right tool for an outgoing effect that leaves no state you can read: an email, a metric, a message to a broker. The mistake is mocking everything, especially your own collaborators, so that the test just replays the implementation. A good rule of thumb that many experienced engineers share: fake what you own and can model (repositories, clocks), verify interactions only at the boundary where the effect leaves your system, and never mock a type you do not own without a thin adapter of your own in between.

One caution about fakes: a fake that disagrees with the real thing gives you confidence in the wrong behaviour. Chapter 5's RepositoryContract is the standard remedy. Run the same suite against the fake and the real adapter. Passing both keeps the fake honest.

The test pyramid, and its critics

Which kinds of test should you have, and how many? The test pyramid, popularised by Mike Cohn, answers: many unit tests, fewer integration tests, very few end-to-end tests.

  • Unit tests exercise a small piece of behaviour (an aggregate, a use case against fakes) in memory. They run in milliseconds, so you can have thousands, and when one fails you know where to look. What counts as a "unit" is a judgement call; testing a use case together with its real domain objects and a fake repository, as in chapter 5, is a perfectly good unit test.
  • Integration tests check that your code works with a real piece of infrastructure: the SQL adapter against an actual database, the HTTP adapter against a real framework. They prove the adapters do what the fakes pretend they do. They take longer and need set-up, so they are fewer.
  • End-to-end tests drive the whole deployed system the way a user would. They give the most realistic confidence and the worst feedback: they are slow, they fail for reasons unrelated to the change (a timeout, a shared test environment), and when they fail they do not say why. Keep a handful for the critical journeys.

The pyramid is a heuristic about economics, not a law, and it has critics. One popular alternative, the testing trophy, argues that for many applications (especially front-ends and thin services) integration tests give the best confidence per effort and should be the largest layer. Which shape fits depends on how much logic lives in your core versus in the glue between systems: a rule-heavy core suits the pyramid, a mostly-glue service suits more integration tests. The useful question under both is the same: what is the cheapest test that would catch this kind of bug?

Contract tests: testing the seam between services

Once your system is several services, the most dangerous bugs live in the gaps. Service A's tests pass, service B's tests pass, and production breaks because B renamed a field A depended on. End-to-end tests over many services are the expensive and flaky answer. The cheaper one is the contract test: a test that checks one side of an interface against a written expectation of the other.

In consumer-driven contract testing, each consumer writes down exactly what it relies on (these fields, of these types, from this endpoint). Those expectations are shared with the provider, which runs them in its own build: if a change would break any registered consumer, the provider's pipeline fails before deployment, with the name of the consumer and the broken field. Pact is a widely used tool that records, shares and verifies such contracts. The idea fits in a dozen lines of Python:

# A hand-rolled consumer-driven contract. Real tools (Pact) add recording, sharing and versioning.
import unittest

CONSUMER_EXPECTS = {            # written by the billing team, checked into THEIR repo, published to the provider
    "GET /orders/{id}": {"id": str, "status": str, "total_cents": int},
}

def provider_get_order(order_id):          # the orders service's real handler (or a test client for it)
    return {"id": order_id, "status": "PAID", "total_cents": 3000, "currency": "EUR"}

def satisfies(response: dict, expected: dict) -> list[str]:
    problems = []
    for field, typ in expected.items():
        if field not in response: problems.append(f"missing field {field!r}")
        elif not isinstance(response[field], typ): problems.append(f"{field!r} is not {typ.__name__}")
    return problems                         # extra fields are fine: consumers must tolerate them

class ProviderHonoursContract(unittest.TestCase):
    def test_orders_service_still_satisfies_billing(self):
        self.assertEqual(satisfies(provider_get_order("o-1"), CONSUMER_EXPECTS["GET /orders/{id}"]), [])
    def test_the_check_catches_a_rename(self):
        broken = {"id": "o-1", "state": "PAID", "total_cents": 3000}      # someone renamed status -> state
        self.assertEqual(satisfies(broken, CONSUMER_EXPECTS["GET /orders/{id}"]), ["missing field 'status'"])

if __name__ == "__main__":
    unittest.main()

Deterministic tests: inject the clock and the dice

A flaky test passes and fails on the same code. Its two most common causes are time and randomness, and both have the same cure as every other hidden dependency: pass them in.

# Hidden clock vs injected clock. A cart holds stock for 15 minutes.
from datetime import datetime, timedelta, timezone
from typing import Callable
import unittest

HOLD = timedelta(minutes=15)

class HiddenClockCart:                          # BEFORE: reads the real time itself
    def __init__(self):
        self.created = datetime.now(timezone.utc)
    def expired(self) -> bool:
        return datetime.now(timezone.utc) - self.created > HOLD
    # To test expiry you must sleep 15 minutes, or monkeypatch datetime.

class Cart:                                     # AFTER: time is a collaborator passed in
    def __init__(self, now: Callable[[], datetime]):
        self._now, self.created = now, now()
    def expired(self) -> bool:
        return self._now() - self.created > HOLD

class FakeClock:
    def __init__(self, start: datetime): self.t = start
    def __call__(self) -> datetime: return self.t
    def advance(self, **kw) -> None: self.t += timedelta(**kw)

class CartTests(unittest.TestCase):
    def test_hold_expires_after_fifteen_minutes(self):
        clock = FakeClock(datetime(2026, 1, 1, 12, 0, tzinfo=timezone.utc))
        cart = Cart(clock)
        clock.advance(minutes=15)
        self.assertFalse(cart.expired())        # exactly 15 minutes: still held
        clock.advance(seconds=1)
        self.assertTrue(cart.expired())

if __name__ == "__main__":
    unittest.main(verbosity=2)

HiddenClockCart cannot be tested without waiting a quarter of an hour. Cart takes a now function; production passes lambda: datetime.now(timezone.utc), tests pass a FakeClock they can advance by exactly fifteen minutes and one second. The test also pins down the boundary (exactly fifteen minutes is still held), which a sleep-based test could never do reliably. Two refinements. For measuring durations (timeouts, rate limits) inject a monotonic clock, because wall-clock time can jump when a leap second or an NTP correction arrives, as the systems course's case study The Leap Second That Broke DNS shows. For recording when something happened, inject a wall clock. And in distributed systems the time you read is only your machine's opinion (network chapter 17), which is one more reason not to sprinkle now() through business rules.

Randomness works the same way. Give the function a random.Random instance rather than calling the global random module. Then a test either seeds it for a reproducible sequence, or (better) asserts a property that must hold for every seed:

import random, unittest

def backoff(attempt: int, rng: random.Random, base=0.1, cap=5.0) -> float:
    """Full-jitter exponential backoff. The randomness is injected."""
    return rng.uniform(0, min(cap, base * 2 ** attempt))

if __name__ == "__main__":
    rng = random.Random(7)                       # seeded: the "random" delays are now reproducible
    print([round(backoff(a, rng), 3) for a in range(6)])

class BackoffTests(unittest.TestCase):
    def test_stays_within_bounds_for_any_seed(self):
        for seed in range(200):
            rng = random.Random(seed)
            for attempt in range(12):
                self.assertTrue(0 <= backoff(attempt, rng) <= min(5.0, 0.1 * 2 ** attempt))
    def test_same_seed_same_sequence(self):
        a, b = random.Random(1), random.Random(1)
        self.assertEqual([backoff(i, a) for i in range(6)], [backoff(i, b) for i in range(6)])

if __name__ == "__main__":
    unittest.main()

Characterisation tests: a net under legacy code

Everything so far assumes you can change the design. Often you cannot: you have a legacy function that works, that nobody fully understands, and that you have been asked to change. Feathers's advice is to write characterisation tests first: tests that record what the code actually does today, whether or not that is what it should do. They are not a specification; they are a snapshot that tells you when you changed behaviour. With that safety net you can refactor (add seams, extract functions) and see immediately if anything shifted.

The recipe is mechanical: call the code with a spread of inputs, look at what comes back, and write that down as the expected value. Take a shipping-cost function nobody remembers writing:

def shipping(weight_kg, country, express=False):    # legacy: nobody remembers why
    cost = 5
    if weight_kg > 2:
        cost += (weight_kg - 2) * 1.5
    if country != "PT":
        cost = cost * 2 + 3
    if express:
        cost = cost * 1.5 if weight_kg < 10 else cost + 20
    return round(cost, 2)

import unittest
from legacy import shipping

class CharacteriseShipping(unittest.TestCase):

    def test_pinned_behaviour(self):

            (1, "PT"): 5,       (2, "PT"): 5,        (4, "PT"): 8.0,

        for args, expected in cases.items():
            with self.subTest(args=args):
                self.assertEqual(shipping(*args), expected)

Common misconception

"High test coverage means good tests." Coverage measures which lines ran, not whether anything checked the result. A test that calls a function and asserts nothing gives 100% coverage of that function. Equally, a suite of mock-heavy tests can cover every line and still be unable to tell you whether the order was actually cancelled. Judge a suite by a different question: if I broke the behaviour on purpose, would a test fail, and would that failure say why?

Distributed systems connection

Distributed systems make the testability principles non-negotiable. Failures such as timeouts, duplicates, reordered messages and partial outages are exactly the conditions that are hardest to produce against the real thing, and trivial to produce against a fake: a fake gateway that times out on the third call, a fake clock that jumps forward past a lease, a fake queue that delivers twice. The more of your fault handling lives in a core with injectable ports, the more of it you can test in milliseconds instead of discovering it in an outage (chapter 17 and Lab 6 build exactly such a toolkit and test it against a flaky fake). Between services, contract tests replace the impossible dream of one test environment containing everything, and they lean on the compatibility rules of chapter 10. Later courses go further, with fault-injection and deterministic simulation of whole clusters, which is just this chapter's "inject the clock and the network" taken to its conclusion.

Key takeaways

  • Code that is hard to test usually reaches out for its dependencies (the clock, the network, globals) instead of being handed them. Testability and low coupling are the same property.
  • A seam (Michael Feathers) is a place to change behaviour without editing there; its enabling point is where you choose. Prefer designed seams (parameters, ports) to monkeypatching.
  • Dummy: unused filler. Stub: canned answers. Fake: a working simplified implementation. Spy: records calls for later checks. Mock: pre-set expectations that verify themselves.
  • Prefer fakes for ports that hold state, and keep them honest by running a shared contract suite against the fake and the real adapter. Over-mocking couples tests to implementation and breaks them on harmless refactors.
  • The pyramid (many unit, fewer integration, very few end-to-end) is an economic heuristic; alternatives like the testing trophy weigh integration tests more. Ask what is the cheapest test that would catch this bug.
  • Contract tests (consumer-driven, as with Pact) guard the seams between services far more cheaply than end-to-end tests.
  • Make time and randomness injectable to get deterministic tests. Pin legacy behaviour with characterisation tests before you refactor.

Check your understanding

A test for a cart that expires after 15 minutes needs time.sleep(900). What does this say about the design?

  1. Nothing; slow tests are normal for time-based rules
  2. The cart reaches out for the real clock instead of being given one, a hidden dependency that should be injected
  3. The cart should be rewritten in a faster language
  4. The test should run only in production
Hard-to-test code points at coupling. Taking the clock as a parameter makes the dependency visible and lets the test advance a fake clock instantly and exactly, including the boundary.

A hand-written InMemoryOrders class that supports save and get using a dict, used in place of the SQL repository, is best described as a:

  1. Dummy
  2. Stub
  3. Mock
  4. Fake
A fake is a working, simplified implementation with real behaviour. A stub only returns canned answers, a dummy is never used, and a mock carries pre-programmed expectations about calls.

  2. The refactor was wrong and must be reverted
  3. Mocks cannot be used with Python 3
  4. The repository should be a singleton
The behaviour was unchanged, so the failure is a false alarm, a symptom of over-specified interaction tests. A fake-based test asserting the final state would have kept passing.

You inherit an untested function nobody understands and must change it. What does the chapter recommend first?

  1. Rewrite it from scratch and compare with the old output later
  2. Read the code until you are sure what it should do, then write tests for that
  3. Write characterisation tests that record its current behaviour on a spread of inputs, then refactor under that net
  4. Add mocks for every collaborator and assert each call
Characterisation tests capture what the code does now (found by running it, not guessing), so you notice any accidental change. They are a net, not a specification; suspicious behaviour is flagged for a later, deliberate fix.

Two services each have green unit tests, but production breaks when the provider renames a response field the consumer uses. Which practice is designed to catch this earlier and cheaply?

  1. A larger end-to-end test environment containing every service
  2. A consumer-driven contract test, where the consumer's expectations are verified in the provider's build
  3. More mocks inside the consumer
  4. Measuring line coverage
Consumer-driven contracts (for example with Pact) record what each consumer relies on and run those expectations against the provider before it deploys. End-to-end tests are slow and flaky, and mocks inside the consumer will happily keep passing against a field that no longer exists.

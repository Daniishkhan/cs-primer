Cross-Cutting Concerns

Some jobs do not belong to any one feature: reading configuration, logging, authentication, reporting errors. Every module needs a little of each, and if you let them seep into the business code they quickly become the mess that hides it. This chapter is a short tour of the usual suspects and the one idea that tames them all: handle them at the edge, around a clean core.

Why this matters

Open a function that places an order and count the lines that are about orders. In many real codebases it is fewer than half: the rest is checking permissions, logging, reading settings, catching exceptions and timing things. That noise makes the business rule hard to see, hard to test and easy to get subtly wrong. Pulling it out is one of the cheapest large improvements you can make to a codebase, and it prepares the ground for the hexagonal structure of chapter 5.

What a cross-cutting concern is

A cross-cutting concern is a requirement that applies across many parts of a system rather than living in one. Draw your modules as vertical slices (orders, payments, inventory) and these concerns are horizontal stripes cutting through all of them: configuration, logging, metrics, authentication and authorisation, error reporting, feature flags. Because every slice needs them, the naive approach is to sprinkle a few lines in each function. Ten modules later you have ten slightly different versions of "log this", and changing the policy means editing everywhere.

Analogy: the city's utilities

In our city, each neighbourhood has its own character, but the power grid, water mains, street lighting and emergency services run through all of them. The city does not ask each shop to dig its own well. The utilities are provided at the boundary of every building by a standard connection, and the shop just uses it. Cross-cutting concerns are the utilities of a codebase: provided uniformly at the boundary, not reinvented in every room.

Where it breaks down: city utilities are physically separate infrastructure. In code, a "utility" like logging is called from inside your functions, so it is easy to slip back into scattering it. It needs discipline, and sometimes tooling, to keep at the edge.

Configuration

Configuration is everything that varies between deployments (database address, API keys, timeouts, which features are on) while the code stays the same. The widely followed guidance comes from The Twelve-Factor App, a methodology written by engineers at Heroku (around 2011): store config in environment variables, strictly separated from code. The same build then runs in development, staging and production, and only its environment differs. Secrets never need to be committed to version control.

Three habits keep configuration from turning into a mess:

  • Read it once, at the edge, into a typed object. Fail at startup if a required setting is missing, not at 3am the first time that code path runs. This is "fail fast" from chapter 3. Then pass the object (or just the values) into the code that needs it. Do not let deep code call os.environ: that is a hidden dependency, the same problem as a singleton.
  • Keep the number of settings small. Every option is a combination you must test and document. Config sprawl, hundreds of knobs nobody remembers, is a form of complexity (chapter 1). Prefer sensible defaults and expose a setting only when two deployments genuinely need different values.
  • Treat a config change as a deploy. It changes behaviour just as code does, so it deserves the same review, rollout and rollback story. A wrong timeout or a flipped switch can take a system down as surely as a bad release. The Knight Capital case is a sobering example, told there in detail: a flag-controlled behaviour and an uneven rollout, with old code reacting to a setting it was never meant to see.

Common misconception

"Environment variables are secure." They keep secrets out of your repository, which is valuable, but they are visible to the process and its child processes, often show up in crash dumps and debugging pages, and are not encrypted. For high-value secrets, a secrets manager (that injects them at start-up or fetches them on demand) is a step up. The principle that matters: secrets are never in code.

Logging: structured, with a request ID

A log line meant for a human, "order 17 placed for asha", is hard for a machine to search. Structured logging emits each event as key-value data (usually JSON): the message plus fields such as level, order_id and request_id. A log system can then answer "show every WARNING for order 17" without regular expressions.

The single most useful field is a correlation ID (or request ID): a unique token generated when a request enters your system and attached to every log line produced while handling it. In a monolith it lets you pull one request's story out of thousands interleaved lines. Across services (chapter 13 onward) you pass it along in a header so the story survives network hops. In Python, contextvars holds it so that code deep in the stack can log it without receiving it as a parameter.

Where these live: middleware around a clean core

Here is the key idea. Instead of writing the concerns inside the business function, wrap them around it. A middleware is a function that takes a handler and returns a new handler that does something before and/or after calling the original. Stack several and a request passes through them like layers of an onion, reaches the core, and returns back through the same layers. It is the GoF decorator pattern from chapter 4, applied to whole requests.

Here the whole idea in about 70 runnable lines: typed config read at the edge, structured JSON logs with a request ID from a contextvar, and three middleware wrapped around a core function that knows nothing about any of it:

import json, logging, os, sys, uuid
from contextvars import ContextVar
from dataclasses import dataclass

# --- config: read once, at the edge, into a typed object ---
@dataclass(frozen=True)
class Config:
    database_url: str
    payment_timeout_s: float
    new_checkout: bool

    @classmethod
    def from_env(cls, env=os.environ) -> "Config":
        try:
            return cls(
                database_url=env["DATABASE_URL"],
                payment_timeout_s=float(env.get("PAYMENT_TIMEOUT_S", "2.0")),
                new_checkout=env.get("NEW_CHECKOUT", "off") == "on",
            )
        except KeyError as e:
            sys.exit(f"missing required setting: {e.args[0]}")

print(Config.from_env({"DATABASE_URL": "sqlite:///shop.db", "NEW_CHECKOUT": "on"}))

# --- structured logging with a request id ---
request_id: ContextVar[str] = ContextVar("request_id", default="-")

class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({"level": record.levelname, "msg": record.getMessage(),
                           "request_id": request_id.get(), **getattr(record, "ctx", {})})

h = logging.StreamHandler(sys.stdout); h.setFormatter(JsonFormatter())
log = logging.getLogger("shop"); log.addHandler(h); log.setLevel(logging.INFO)

# --- the core: knows nothing about HTTP, logging setup, auth ---
def place_order(user: str, sku: str) -> dict:
    log.info("order placed", extra={"ctx": {"sku": sku}})
    return {"status": 201}

# --- middleware wrapping the core ---
def with_request_id(handler):
    def inner(req):
        token = request_id.set(req.get("x-request-id") or uuid.uuid4().hex[:8])
        try:
            return handler(req)
        finally:
            request_id.reset(token)
    return inner

def with_auth(handler):
    def inner(req):
        if "user" not in req:
            log.warning("unauthenticated")
            return {"status": 401}
        return handler(req)
    return inner

def with_error_policy(handler):
    def inner(req):
        try:
            return handler(req)
        except ValueError as e:
            return {"status": 400, "error": str(e)}
        except Exception:
            log.error("unhandled error")
            return {"status": 500, "error": "internal"}
    return inner

app = with_request_id(with_error_policy(with_auth(lambda req: place_order(req["user"], req["sku"]))))
print(app({"x-request-id": "req-42", "user": "asha", "sku": "tea"}))
print(app({"x-request-id": "req-43", "sku": "tea"}))
Config(database_url='sqlite:///shop.db', payment_timeout_s=2.0, new_checkout=True)
{"level": "INFO", "msg": "order placed", "request_id": "req-42", "sku": "tea"}
{'status': 201}
{"level": "WARNING", "msg": "unauthenticated", "request_id": "req-43"}
{'status': 401}

Look at place_order. It is three lines and mentions no HTTP status, no user lookup and no environment. You can unit-test it by calling it. The unauthenticated request (the second one) never reached it; the middleware answered 401 and, because the request-ID layer is outermost, even that rejection got a correlated log line. The order of the layers is a design decision: put the request-ID layer outside everything so that all activity is traceable.

Real frameworks give you this shape under names like middleware (WSGI/ASGI, Express), filters or interceptors; in Python you will also meet the @decorator form. The caveat is the same as for any decorator stack: if there are ten layers, nobody can see what runs and in which order, so keep the chain short and written down in one place.

Error handling policy at the edges

Chapter 3 said errors are part of an interface. At the system level, the corollary is to decide your error policy once, at the edge. Inner code raises meaningful, domain-flavoured exceptions (InsufficientFunds, NotFound). One outermost layer turns them into the outside world's form: a 4xx status for caller mistakes, a 5xx for yours, with a stable, safe body. That layer is also where you log unexpected errors with their stack trace, return a generic "internal error" message (never leak internals or stack traces to clients), and attach the request ID so a support ticket can be traced. In the example above, with_error_policy is that layer. If every function catches and reformats errors itself, you get inconsistent responses and swallowed failures.

Metrics and tracing hooks

Logs tell you what happened in one request. Metrics are numbers aggregated over time (requests per second, error rate, latency percentiles), and traces follow a single request across services as a tree of timed steps. Both are classic cross-cutting concerns, and both are best added at the same edge: a middleware that starts a timer, increments a counter labelled by route and status, and records a span. The core never sees them. We will only plant the hook here. The planned Reliability & Operations course covers what to measure, how to turn it into service-level objectives and how to read the signals during an incident.

Security at the boundaries

Security is the cross-cutting concern with the sharpest consequences, and here too the idea is to concentrate it at well-defined boundaries. A few foundations:

  • Authentication vs authorisation. Authentication answers "who are you?" (a password, a token, a certificate). Authorisation answers "what are you allowed to do?" They are different checks at different points. Authentication usually happens once, in an outer layer, producing a user identity. Authorisation depends on the specific action and resource ("can asha refund this order?"), so it often has to be asked closer to the core, as a rule the domain knows about. A frequent bug is authenticating the user and then forgetting to check that the thing they asked for is theirs.
  • Least privilege. Give every user, service and credential the minimum access needed. A reporting job gets read-only access to a replica, not the production admin password. When something is compromised, the damage is bounded by what it could do.
  • Secrets out of code. Keys, passwords and tokens belong in the environment or a secrets manager, never in source control (a leaked repository, even years later, leaks the secrets), and they should be rotatable without a redeploy of logic.
  • Validate at the boundary. Treat all outside input as untrusted; check it where it enters, then let the core assume validated data (its preconditions, in chapter 3's terms).

Common misconception

"The gateway checks auth, so the services behind it are safe." Perimeter-only security means anyone who gets past (or around) the perimeter owns everything. Each service should still verify who is calling and what they may do, a point we return to when services appear in chapter 12. Security is also not a place for homemade cryptography or clever tricks: use well-reviewed libraries and the standard mechanisms of your platform.

Feature flags

A feature flag (or toggle) is a runtime switch that turns behaviour on or off without redeploying, as in the NEW_CHECKOUT setting read in the example. Flags let you ship code dark, release to 1% of users, and roll back instantly. They are cross-cutting because the decision "is this on for this user?" is needed in many places. The usual advice is to evaluate the flag in one place, near the edge, and to treat flags as short-lived: each one doubles the paths through your code and must be deleted once the rollout finishes. Chapter 18 covers rollout strategy and flag hygiene properly, and the Knight Capital story shows what an old, forgotten flag can do.

Distributed systems connection

Once a system is many services, cross-cutting concerns multiply: each service needs the same logging format, the same correlation ID passed along, the same auth checks, and the same retry and timeout behaviour. Teams solve that with shared libraries, sidecar proxies or a service mesh, which are the middleware idea moved out of the process. The lesson from this chapter transfers directly: keep the policy uniform and at the edge, and keep it out of business logic.

Key takeaways

  • Cross-cutting concerns (config, logging, metrics, security, error policy, flags) touch every module; scattering them through domain code hides the business rules.
  • Configuration lives in the environment (Twelve-Factor), is read once into a typed object at the edge, kept small, and treated as a deploy.
  • Log structured events and attach a request ID to every line so one request's story can be reconstructed.
  • Wrap concerns around the core as middleware; decide error policy, authentication and flag evaluation at the edge.
  • Authentication is "who", authorisation is "may they do this to that"; apply least privilege and keep secrets out of code.
  • Metrics and tracing hook in at the same edge; later chapters and courses build on them.

Check your understanding

Which is the best reason to read configuration once at startup into a typed object?

  1. It makes environment variables encrypted
  2. Missing or invalid settings fail immediately and clearly, and deep code receives values instead of reaching for globals
  3. It allows settings to change on every call
  4. It removes the need for defaults
Failing fast at startup beats discovering a missing key during a rare code path, and passing the values in avoids a hidden dependency on the process environment.

Why attach a request ID to every log line?

  1. It makes logs smaller
  2. It is required by JSON
  3. It speeds up the database
  4. It lets you filter thousands of interleaved lines down to the story of a single request, across modules and (if propagated) services
A correlation ID is the thread that ties a request's events together. Propagating it in a header across service calls extends the same idea to distributed systems.

A user is logged in and requests GET /orders/42, which belongs to someone else, and the server returns it. What was missed?

  1. Authorisation: the user was authenticated but not checked for permission to see that order
  2. Authentication
  3. Structured logging
  4. A feature flag
Authentication established who they are; authorisation decides what they may access. Forgetting the ownership check is a very common bug.

Where should the translation of exceptions into HTTP status codes happen?

  1. Inside every business function
  2. In the database layer
  3. In one outer layer at the edge, so inner code raises domain errors and responses stay consistent
  4. In the client
Centralising the policy gives consistent responses and keeps the core free of HTTP knowledge. It is also the right place to log unexpected failures and hide internals from clients.

Why treat a configuration change as a deploy?

  1. Because configuration is stored in git
  2. Because it changes system behaviour as surely as code does, and can cause outages, so it needs review, staged rollout and a rollback plan
  3. Because it requires recompiling
  4. Because environment variables cannot change at runtime
The risk comes from changing behaviour, not from the file type. Mis-set values and uneven rollouts have caused real incidents, which is why the Knight Capital case is worth reading.

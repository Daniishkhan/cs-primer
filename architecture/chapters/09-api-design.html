API Design

An API is a product whose customers are other programmers, and whose mistakes are very hard to take back. This chapter is about the design judgement behind it: how to model resources, report errors, make retries safe with idempotency keys, page through changing data without losing rows, run slow work in the background, and choose honestly between REST, gRPC and GraphQL.

Why this matters

Inside one program you can rename a function and let the compiler fix every caller. An API has callers you cannot see, on release schedules you do not control, and some of them will be written by people who left the company years ago. Every decision in this chapter (the shape of a URL, the format of an error, whether a cursor is opaque) becomes a promise you will have to keep. Good API design is mostly about making promises you can afford. It is also the most visible part of system design in interviews, because it shows whether you think about the people on the other side of the wire.

In networking chapter 10 you learned what HTTP is: methods, status codes, headers. In chapter 12 you met REST, RPC and WebSockets as a menu. This chapter assumes all that and asks the next question: given the menu, how do you design one that other people can live with? The design half of the story continues in chapter 10, which is about changing an API after people depend on it.

An API is a product

Start with the consumer. Before you draw a single endpoint, write down three or four things a client developer actually wants to do: "place an order", "see my last twenty orders", "cancel an order that has not shipped". Then design so those tasks are short and hard to get wrong. This sounds obvious, yet most bad APIs are shaped like the database tables or the internal classes behind them, because that was the easy thing to expose. Their consumers pay for it forever, one confusing call at a time.

Analogy: roads and their signs

Remember the city from chapter 0: neighbourhoods are modules, and the roads and their signs are the APIs. A good road network has a few predictable rules everywhere (drive on the same side, red means stop), signs that say where you are going, and a bridge that stays open even when the city changes behind it. Drivers do not read a manual per street. A bad network has streets named after whoever built them, signs that disagree, and a bridge that closes for repairs without notice.

Where it breaks down: a city can close a road and drivers just see a detour sign. An API consumer is a program that cannot improvise: it follows the old route exactly, forever, until someone edits its code. Removing a road in the software city means every car still driving it crashes.

Four habits help more than any rulebook:

  • Write the client code first. Sketch the ten lines a consumer will write to place an order. If they need three calls and a lookup table, the API is wrong, however pretty its URLs.
  • Be consistent over being clever. One way to paginate, one error format, one spelling of "created at". Consistency lets a developer guess correctly.
  • Make the safe path the easy path. Retries should be safe by default; dangerous operations should need a deliberate gesture.
  • Treat everything you ship as permanent. Field names, status codes, even the order of an unordered list will be depended on (that is Hyrum's law, the first topic of chapter 10).

Resource modelling: nouns, collections, sub-resources

A resource-oriented API exposes things with stable addresses, and uses the HTTP methods you already know as the verbs. A collection is a resource that contains others (/orders), an item is one member (/orders/17), and a sub-resource belongs to one parent (/orders/17/lines). Nouns in URLs, plural for collections, and no verbs like /getOrder: the method already says what you are doing.

A few judgement calls that come up in every API:

  • Nest only as deep as ownership goes. /orders/17/lines is fine because a line cannot exist without its order. /customers/3/orders/17/lines/2/discounts is a maintenance burden: once a thing has a globally unique id, give it a top-level address too.
  • Model what exists, not what your database tables look like. A "checkout" might touch five tables but be one resource to the consumer.
  • Actions are legitimate. Purists argue about POST /orders/17/cancel versus PATCHing a status field. Cancelling is a business operation with rules (is it shipped?), side effects (refund) and its own errors, so many experienced teams give it a name. What matters is that you choose one convention and keep it.
  • Return representations, not table rows. Use stable names, ISO 8601 timestamps with a zone (2026-10-12T09:30:00Z), money as an integer of minor units plus a currency, and ids as strings so you can change their format later.

Verbs and what they promise

You met safe and idempotent in networking chapter 10. The design consequence is where they matter: clients, proxies and retry libraries act on these promises without asking you. A load balancer or HTTP client may automatically retry an idempotent request after a dropped connection, and will not retry a POST. A browser or crawler may fetch any GET for a link preview. So if your GET /orders/17/refresh charges a card, something will eventually press it for you.

MethodSafeIdempotentDesign note
GETyesyesNever change state, even "just a counter". It is the cacheable one.
PUTnoyesReplace the whole resource. Sending it twice leaves the same state, so retries are safe. Often also used to create at a client-chosen id.
DELETEnoyesThe second call finds nothing; return 204 or 404, but be consistent. The state is the same either way.
PATCHnonot guaranteedDepends on the patch format. "Set status to shipped" is idempotent; "add 1 to quantity" is not.
POSTnonoThe catch-all: create, run an action, anything else. Two identical POSTs may create two things. This is the verb that needs idempotency keys.

Partial updates deserve a short note. PUT replaces everything, so a client that omits a field it does not know about silently erases it. PATCH sends only the changes, and there are two common formats: JSON Merge Patch (RFC 7396; send a JSON object of the fields to change, null means "remove this field") and JSON Patch (RFC 6902; a list of explicit operations such as {"op": "replace", "path": "/status", "value": "shipped"}). Merge Patch is simpler and enough most of the time; it cannot express "set this to null" or edit one array element. Whichever you pick, document it, and decide what happens when two clients patch at once. The standard tool is an ETag on reads and an If-Match header on writes, which makes the server answer 412 Precondition Failed if someone else changed the resource first. That is optimistic concurrency, the same idea as the version check in data chapter 12, exposed over HTTP.

Status codes that matter, and one error format

HTTP has dozens of status codes. An API needs about a dozen, used consistently, and a client should be able to decide what to do next from the code alone.

CodeUse it whenThe client should
200 / 201 / 204Success; created (add a Location header); success with no bodyCarry on
202Accepted for later processing (see long-running operations below)Poll the status resource or wait for a webhook
400The request is malformed: bad JSON, bad cursorFix the request; retrying is pointless
401 / 403Not authenticated / authenticated but not allowedRe-authenticate / stop
404No such resource (or you prefer not to reveal that it exists)Stop
409Conflicts with the current state: duplicate, already shipped, edit collisionRe-read state, then decide
412An If-Match precondition failedRe-fetch and re-apply the change
422Well-formed but semantically invalid: failed validationFix the fields named in the error

500 / 503Our bug / temporarily unavailableRetry with backoff, if the operation is safe to repeat

The 400 versus 422 line is blurry, and teams differ. It does not matter which you pick as long as the guide says and every endpoint agrees. What does matter: never return 200 with an error inside (monitoring, caches and retry logic all believe the status line), and never leak stack traces or SQL in a 500 body.

Errors are part of the contract

The error body is read by programs, so it needs a shape just like a success body. Rather than invent one, use the standard: RFC 9457, "Problem Details for HTTP APIs" (July 2023, which obsoletes the earlier RFC 7807). It defines the media type application/problem+json and a small set of members: type (a URI that identifies the kind of problem), title (a short human summary of that kind), status, detail (an explanation of this occurrence) and instance (a URI for this occurrence), and you can add extension members of your own such as a list of field errors. Clients are told to ignore extension members they do not recognise, which is exactly the tolerance you want (chapter 10).

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://example.com/problems/invalid-order",
  "title": "Invalid order",
  "status": 422,
  "detail": "Body must be JSON with a non-empty 'items' list.",
  "errors": [{"field": "items", "message": "required, non-empty list"}]
}

The important design point is the type. Clients should branch on that stable identifier (or on a documented error code you add), never on the human text, which you will want to reword and translate. Treat the set of error types as a published list: adding a new one is a change consumers must be able to survive, and renaming one is a breaking change. This is the same discipline as chapter 3's advice to design errors as part of an interface, now applied across a network.

Common misconception: "errors are an implementation detail"

Consumers write code for every failure they can see: "if insufficient_funds, show the top-up screen". Change that string or its status code and you have broken them as surely as removing a field. Document the error types, keep them stable, and make 4xx vs 5xx honest, because a retry policy hangs on that split.

Idempotency keys: making POST safe to retry

Here is the problem from networking chapter 16 in API form. The client sends POST /orders. The server creates the order and charges the card. The response is lost: a timeout, a dropped connection, a proxy that gave up. The client does not know whether anything happened. If it retries, it may charge twice; if it does not, it may never order. POST is not idempotent, so no library will retry it for you.

An idempotency key repairs this. The client generates a unique value (a random UUID) per logical operation and sends it in a header, conventionally Idempotency-Key. The server remembers what it did for each key. A retry carries the same key, so the server recognises it and returns the stored response instead of doing the work again. Stripe popularised this pattern for its payments API; case 5 looks at that API's specifics, and I will not guess them here. The IETF has also had a draft for a standard Idempotency-Key header; check its current status before depending on it.

Step through

A lost response, retried with the same key

  1. The client creates an order. It generated the key abc-123 once, before the first attempt, and will reuse it for every retry of this same operation.
  2. The server claims the key. Before doing any work it inserts the key into a table with a UNIQUE constraint. If two copies of the request arrive at the same moment, exactly one insert wins; the database, not application code, decides who goes first.
  3. The work happens once. The order is created, the card is charged, and the server saves the response (status and body) against the key. Ideally the order and the stored response are committed in the same database transaction (data chapter 10).
  4. The response is lost. The server did everything right, but the reply never reaches the client. This is the case no amount of careful coding on either side can detect: from the client's point of view, nothing happened.
  5. The client retries with the same key. It cannot tell whether the order exists, so it asks again, exactly as networking chapter 16 prescribed, identical body and identical key.
  6. The server recognises the key. The lookup finds a stored result. It also compares a fingerprint of the request body, so reusing a key for a different request is rejected rather than silently replayed.
  7. The stored response is replayed. The client gets the same 201 and the same order. There is still exactly one charge. The retry was safe because the server made it so.

The details that make it work

  • What gets stored. The key, a fingerprint (hash) of the request, and the response status and body, plus a state: in progress or complete. Replay returns the first response verbatim, including an error if the first attempt failed in a way that should stick.
  • Scope. Keys are scoped to the caller (an account or API key) and often to the endpoint, so two customers choosing the same key cannot collide.
  • The window. You cannot store keys forever, so you expire them after some retention window. A day or so is common, but this is a policy choice you should document, because a retry that arrives after expiry will be treated as a new request.
  • Different body, same key. That is a client bug. Return an error (the example below uses 422) instead of guessing which request was meant.
  • Concurrent duplicates. Two copies arrive at once, before either has finished. The unique constraint lets only one claim the key; the other must either wait for the result or fail fast with 409 Conflict and a Retry-After. Without the constraint, "check, then insert" is a classic race: both check, both find nothing, both charge.
  • Crash safety. If you record the key in one transaction and do the work in another, a crash between them leaves either a key with no work or work with no key. Put both in one transaction where you can. For external side effects such as a card network, pass your own idempotency key downstream so the provider can deduplicate too.
  • Who generates the key. The client, once per logical operation, not per attempt. A retry library that generates a fresh key on each attempt defeats the whole mechanism.

This is the HTTP-level version of an idea you will see in every reliable system: at-least-once delivery plus an idempotent receiver gives effectively-once processing. Queues in chapter 13, sagas in chapter 15 and the idempotent consumers in data chapter 19 are all the same trick wearing different clothes.

Pagination: offset versus cursor

Any collection that can grow must be paged, from day one, because adding pagination later is a breaking change (clients that got "everything" will silently get a first page). The question is how to mark where the next page starts.

Offset pagination says "skip N rows, then give me the next L": ?offset=40&limit=20 or ?page=3. It is easy to build and lets a client jump to page 17. It has two problems. First, cost: the database must walk past the first N rows to discard them, so deep pages get slower (data chapter 8 shows how to see this in EXPLAIN, and data Lab 4 lets you measure it). Second, correctness: the table changes while the client is paging. A row inserted at the top pushes everything down, so the last row of page 1 shows up again as the first row of page 2 (a duplicate). A row deleted from page 1 pulls everything up, and the first row of page 2 slides into page 1's range and is never seen (a skip).

Cursor pagination (also called keyset pagination) says "give me the rows after this one". The cursor remembers the sort key of the last row seen, and the query becomes a range condition: WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 20. With an index on those columns the database jumps straight to the position, so every page costs the same, and inserts or deletes elsewhere in the table cannot move the boundary. Two caveats: the sort key must be unique (hence the id tie-breaker), and you lose "jump to page 17" and cheap exact totals.

Try it. Page forward in either mode, then insert a row or delete a row between requests and watch the counters.

What the widget shows

With offset pagination, inserting at the top produces a duplicate on the next page, and deleting from page 1 produces a skipped row, because the offset counts positions and positions moved. With a cursor, the next request is anchored to a row's value, so neither change can move the boundary. (A newly inserted row is simply not in this walk; it will be at the start of the next one, which is the correct behaviour for a snapshot-like traversal.)

Opaque cursors

Return the cursor as an opaque string, such as a base64-encoded token, and tell clients to treat it as a black box: store it, send it back, never parse it. Inside it you can put the last sort key, the sort order and filters that apply, a version number, even an expiry or a signature. Because clients never look inside, you can later change the pagination strategy (switch the sort key, shard the data, move to a different database) without breaking anyone. If you publish ?after_id=123, then after_id is now a contract. Reject a cursor you cannot decode with a 400 problem response rather than guessing.

Also decide the response envelope once: {"data": [...], "next_cursor": "..."} with null at the end, or a Link header with rel="next" as many large public APIs use. A limit parameter with a sensible default and a hard maximum protects you from a client asking for a million rows.

Filtering, sorting and sparse fieldsets

Collections need to be narrowed and ordered, and a consistent grammar helps. For simple filters use query parameters named after fields (?status=paid&customer_id=3), for sorting one parameter with an obvious sign convention (?sort=-created_at for descending), and for ranges something predictable such as created_after and created_before. Decide upfront what is allowed: every filter and sort is an index you have to maintain, and an unrestricted "filter on anything" endpoint is a denial-of-service invitation. Document the whitelist.

A sparse fieldset (?fields=id,total,status) lets a client ask for only some fields of each resource, cutting payload size for slow mobile connections. It is a cheap, partial step toward what GraphQL does fully, so it is worth offering only when you have measured a real payload problem. Remember the combination matters: a cursor must encode the sort order and filters it was created under, or page 2 will be computed on a different query than page 1.

Long-running operations and webhooks

Some work does not fit in a request: generating a report, transcoding video, a bank transfer that settles overnight. Holding the connection open invites timeouts, and a client that times out will retry, running the job twice. The standard shape is: accept the job, return immediately, and give the client something to look at.

The response is 202 Accepted with a Location header pointing to a status resource (/exports/9) that reports queued, running, succeeded or failed, and on success links to the result. Make the job itself a first-class resource: it can be cancelled with DELETE, listed, and expired. Combine it with an idempotency key so a retried POST /exports does not start two jobs. Send Retry-After on the status resource to tell clients how often to poll, and cap polling on the client with backoff.

Webhooks: calling the client back

Polling is wasteful. A webhook flips the direction: the client registers a URL, and when the job finishes (or a payment settles) your server makes an HTTP request to them. The client is now the server, and your system is the unreliable network, so all the earlier lessons reappear:

  • Sign the payload. Anyone can send a POST to a public URL. Sign the body, with a timestamp, using a shared secret (an HMAC), and let receivers verify with a constant-time comparison. Include the timestamp in what is signed and have receivers reject old ones, so a captured request cannot be replayed later.
  • Retry on failure, with backoff. Treat any non-2xx or timeout as "try again later", with growing delays and a final give-up point. Delivery is therefore at least once.
  • Receivers must be idempotent. Each event has a unique id; the receiver records ids it has processed and ignores repeats. Events can also arrive out of order, so include a timestamp or version and let the receiver fetch current state when it matters.
  • Acknowledge fast. A good receiver stores the event, answers 2xx immediately, and processes it afterwards; a slow handler causes timeouts and therefore duplicates.
import hashlib, hmac, time

SECRET = b"whsec_demo"          # shared out of band when the endpoint is registered

def sign(body: bytes, ts: int) -> str:
    return hmac.new(SECRET, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()

def verify(body: bytes, ts: int, signature: str, now: int, tolerance: int = 300) -> bool:
    if abs(now - ts) > tolerance:                 # stale: could be a replay
        return False
    return hmac.compare_digest(sign(body, ts), signature)   # constant-time compare

seen_events: set[str] = set()
def handle(event: dict) -> str:
    if event["id"] in seen_events:                # at-least-once delivery: dedupe
        return "duplicate, ignored"
    seen_events.add(event["id"])
    return f"processed {event['type']}"

body, ts = b'{"id":"evt_1","type":"order.paid"}', int(time.time())
sig = sign(body, ts)
print("valid signature      :", verify(body, ts, sig, now=ts + 10))
print("tampered body        :", verify(body.replace(b"paid", b"free"), ts, sig, now=ts + 10))
print("replayed an hour late:", verify(body, ts, sig, now=ts + 3600))
print(handle({"id": "evt_1", "type": "order.paid"}))
print(handle({"id": "evt_1", "type": "order.paid"}))

Common misconception: "I'll just trust the webhook payload"

An unsigned webhook is a public endpoint that does whatever a stranger's JSON says. Verify the signature before reading the body as truth, and for anything important, treat the webhook as a nudge: fetch the current state from the API and act on that.

Rate limiting at the API edge

An API shared by many consumers needs a way to say "slow down" before one of them starves the rest. When a client exceeds its quota the server answers 429 Too Many Requests and, ideally, a Retry-After header saying how many seconds to wait (or a date). Well-behaved clients obey it, and your retry policy from networking chapter 16 should treat 429 and 503 as "back off", not "try again immediately". Many APIs also publish their remaining quota in response headers so clients can pace themselves; the header names vary by provider, and an IETF draft proposes standard ones. You will see real ones in the exercise below. The algorithms behind it (token bucket and friends) and what happens when the server protects itself are the subject of chapter 17; for API design, the point is that limits and their error format are part of the contract too.

REST, RPC and GraphQL: an honest comparison

"REST versus GraphQL versus gRPC" attracts more tribal loyalty than it deserves. They are different tools with different costs, and large companies commonly run all three. Here is a fair comparison.

REST (resource over HTTP)RPC / gRPCGraphQL
ShapeMany URLs, standard verbs, usually JSONNamed methods with typed request and reply messagesOne endpoint; the client sends a query describing exactly the fields it wants
ContractOften an OpenAPI description (optional)A .proto file is the contract; code is generated for each languageA typed schema; introspection built in
StrengthsSimple, debuggable with curl, works with every proxy and CDN, HTTP caching of GETs, huge ecosystemCompact binary messages, fast, strong typing, built-in deadlines, streaming in both directionsClient gets precisely what it needs in one round trip; great for varied clients (mobile, web) over a graph of related data
CostsOver-fetching and under-fetching: several calls to assemble one screen; versioning is on youNot human-readable on the wire; browsers need a proxy layer; looks like a local call but is not; tied to HTTP/2 infrastructureHard to cache by URL; easy to write expensive queries; N+1 trap in resolvers; more server complexity; errors often come back with 200
Best fitPublic APIs, CRUD-ish domains, integrationsInternal service-to-service calls where you control both endsProduct UIs with many views over one rich domain, aggregating several backends
EvolutionAdd fields; version or deprecate for the restProtobuf field numbers make additive change safe (data chapter 3)Add fields and types; deprecate fields in the schema; clients only pay for what they ask

Two failure modes deserve names. In GraphQL, the N+1 problem happens when a query for 50 orders each resolves its customer with a separate lookup: one query for the list, plus 50 more for the customers. The standard fix is to batch lookups within a request (the "dataloader" pattern). And because the client composes the query, a malicious or careless one can ask for deeply nested data that melts the database, so production GraphQL servers limit query depth and assign each query a cost, rejecting those over budget. REST has the same risk, but the server controls the shapes of the responses.

With gRPC the contract is a .proto file with numbered fields, which is why field numbers must never be reused (the schema-evolution rules from data chapter 3 apply directly). Streaming lets one call carry a sequence of messages in either direction, a good fit for feeds and bulk transfers, and every call carries a deadline so a slow dependency cannot hold a thread forever. The warning from networking chapter 12 still stands: a gRPC call looks like a function call and fails like a network.

A pragmatic default

Many experienced engineers pick REST-style JSON for public and partner APIs (the lowest common denominator, easiest to adopt), gRPC or similar for internal service calls with heavy traffic, and add GraphQL only when UI teams are repeatedly blocked by endpoint shapes. It is an opinion, not a law. The better question than "which is best?" is "who are the consumers, can I see them, and how will this contract change?".

Consistency: write the style guide

The cheapest improvement to any API is a short written style guide, enforced in review. It should answer: naming (snake_case or camelCase, plural collections, one word for the same concept everywhere), timestamps and money, the error format, pagination and filtering grammar, how and when you use PATCH, idempotency requirements per endpoint, rate limit headers, and your deprecation policy. Consumers should be able to learn one endpoint and correctly guess the next. Tools such as OpenAPI descriptions plus a linter can check much of it automatically.

A runnable example: orders API with idempotency, cursors and problem+json

Here is a tiny WSGI application. It needs no framework and no sockets: WSGI is just a function app(environ, start_response), so we can fill in the environ dictionary with wsgiref.util.setup_testing_defaults and call the function directly. It implements POST /orders with an Idempotency-Key header, GET /orders with cursor pagination (newest first), and problem+json errors. The in-memory LOCK stands in for the database UNIQUE constraint; in a real service the key table and the orders would live in one database transaction.

import base64, json, threading
from io import BytesIO
from wsgiref.util import setup_testing_defaults
from urllib.parse import parse_qs

ORDERS: list[dict] = []          # newest last; ids only grow
IDEM: dict[str, tuple] = {}      # key -> (fingerprint, status, body)
LOCK = threading.Lock()          # stands in for a UNIQUE constraint

PHRASE = {200: "OK", 201: "Created", 400: "Bad Request", 404: "Not Found",
          405: "Method Not Allowed", 422: "Unprocessable Content"}

def problem(status, slug, title, detail, **extra):
    """RFC 9457 problem details; 'type' is a stable, documented identifier."""
    body = {"type": f"https://example.com/problems/{slug}", "title": title,
            "status": status, "detail": detail, **extra}
    return status, body, "application/problem+json"

def encode_cursor(last_id):  return base64.urlsafe_b64encode(json.dumps({"id": last_id}).encode()).decode()
def decode_cursor(text):
    try:    return json.loads(base64.urlsafe_b64decode(text.encode()))["id"]
    except Exception: return None

def create_order(environ, raw):
    key = environ.get("HTTP_IDEMPOTENCY_KEY")
    if not key:
        return problem(400, "missing-header", "Missing header", "POST /orders requires an Idempotency-Key header.")
    try:
        data = json.loads(raw or b"{}")
        assert isinstance(data.get("items"), list) and data["items"]
    except Exception:
        return problem(422, "invalid-order", "Invalid order", "Body must be JSON with a non-empty 'items' list.",
                       errors=[{"field": "items", "message": "required, non-empty list"}])
    fingerprint = json.dumps(data, sort_keys=True)
    with LOCK:                                   # check-and-insert must be atomic
        if key in IDEM:
            fp, status, body = IDEM[key]
            if fp != fingerprint:
                return problem(422, "key-reuse", "Idempotency key reuse", "That key was used with a different request body.")
            return status, body, "application/json"      # replay: same answer, no new order
        order = {"id": len(ORDERS) + 1, "items": data["items"], "status": "created"}
        ORDERS.append(order)
        IDEM[key] = (fingerprint, 201, order)
    return 201, order, "application/json"

def list_orders(environ):
    q = parse_qs(environ.get("QUERY_STRING", ""))
    limit = min(int(q.get("limit", ["2"])[0]), 100)
    after = None
    if "cursor" in q:
        after = decode_cursor(q["cursor"][0])
        if after is None:
            return problem(400, "bad-cursor", "Bad cursor", "The cursor is invalid or expired.")
    newest_first = sorted(ORDERS, key=lambda o: -o["id"])
    page = [o for o in newest_first if after is None or o["id"] < after][:limit + 1]
    more, page = len(page) > limit, page[:limit]
    body = {"data": page, "next_cursor": encode_cursor(page[-1]["id"]) if more else None}
    return 200, body, "application/json"

def app(environ, start_response):
    method, path = environ["REQUEST_METHOD"], environ["PATH_INFO"]
    if path == "/orders" and method == "POST":
        n = int(environ.get("CONTENT_LENGTH") or 0)
        status, body, ctype = create_order(environ, environ["wsgi.input"].read(n))
    elif path == "/orders" and method == "GET":
        status, body, ctype = list_orders(environ)
    elif path == "/orders":
        status, body, ctype = problem(405, "method-not-allowed", "Method not allowed", f"{method} is not supported here.")
    else:
        status, body, ctype = problem(404, "not-found", "Not found", f"No resource at {path}.")
    payload = json.dumps(body).encode()
    start_response(f"{status} {PHRASE[status]}", [("Content-Type", ctype), ("Content-Length", str(len(payload)))])
    return [payload]

def call(method, path, body=None, headers=None, query=""):
    env = {"REQUEST_METHOD": method, "PATH_INFO": path, "QUERY_STRING": query}
    setup_testing_defaults(env)
    raw = json.dumps(body).encode() if body is not None else b""
    env["wsgi.input"], env["CONTENT_LENGTH"] = BytesIO(raw), str(len(raw))
    for k, v in (headers or {}).items():
        env["HTTP_" + k.upper().replace("-", "_")] = v
    out = {}
    def start_response(status, hdrs): out["status"], out["ctype"] = status.split()[0], dict(hdrs)["Content-Type"]
    out["body"] = json.loads(b"".join(app(env, start_response)))
    return out

class OrdersTest(unittest.TestCase):

        api.ORDERS.clear(); api.IDEM.clear()

        h = {"Idempotency-Key": "k"}
        a = api.call("POST", "/orders", {"items": ["x"]}, h)
        b = api.call("POST", "/orders", {"items": ["x"]}, h)
        self.assertEqual(a["body"], b["body"])
        self.assertEqual(len(api.ORDERS), 1)

    def test_concurrent_duplicates_create_one_order(self):
        h = {"Idempotency-Key": "race"}
        ts = [threading.Thread(target=api.call, args=("POST", "/orders", {"items": ["x"]}, h)) for _ in range(20)]
        [t.start() for t in ts]; [t.join() for t in ts]
        self.assertEqual(len(api.ORDERS), 1)

    def test_pagination_walks_every_order_once(self):
        for i in range(7):
            api.call("POST", "/orders", {"items": ["x"]}, {"Idempotency-Key": f"k{i}"})
        seen, cursor = [], None
        while True:
            q = "limit=3" + (f"&cursor={cursor}" if cursor else "")
            body = api.call("GET", "/orders", query=q)["body"]
            seen += [o["id"] for o in body["data"]]
            cursor = body["next_cursor"]
            if not cursor: break
        self.assertEqual(seen, [7, 6, 5, 4, 3, 2, 1])

Go deeper (optional): what this example simplifies

The lock is held while the order is created. That is fine for an in-memory dictionary but wrong for a real payment call, which can take seconds. A production version inserts the key row with state in progress inside a short transaction, releases, does the slow work, then records the response and marks it complete. A duplicate that arrives meanwhile sees in progress and waits, or gets 409. The example also keeps keys forever (no expiry window), scopes them globally (not per account), and encodes the cursor with only an id; a real cursor would carry the sort key and a signature. Finally, about:blank versus minted type URIs: the example mints URIs under example.com, which is the better practice, because it gives each problem a stable, documentable identity.

Distributed systems connection

An API is the front door of a distributed system, and every idea here is a distributed-systems idea in disguise. Idempotency keys are the practical answer to "the response was lost and I cannot know if it was processed", the same uncertainty that Two Generals proves unavoidable. Cursors are a consistent-read problem: what does it mean to read a collection that changes while you read it? Webhooks are at-least-once messaging with signed envelopes. Rate limits are admission control. When you reach consensus and exactly-once discussions in the Distributed Systems, Deep course, you will recognise them as generalisations of tricks you can already write in forty lines of Python.

Key takeaways

  • Design from the consumer's tasks, not from your tables. Consistency matters more than cleverness; write it down as a style guide.
  • Use nouns and nesting for addresses and methods for verbs; know which verbs are safe and idempotent, because infrastructure retries based on that promise. POST is neither.
  • Errors are part of the contract. Use correct status classes and a standard body (RFC 9457 problem+json), and have clients branch on a stable type, not on text.
  • Make unsafe retries safe with an idempotency key: a unique constraint claims the key, the stored response is replayed, mismatched bodies are rejected, and keys expire after a documented window.
  • Paginate from the start. Offset pagination duplicates and skips rows when data changes and slows down on deep pages; cursor pagination does neither but cannot jump to page N. Make cursors opaque.
  • Slow work returns 202 and a status resource; webhooks must be signed, retried, and received idempotently.
  • REST, gRPC and GraphQL trade simplicity, speed and flexibility differently; choose by who the consumers are, and watch for N+1 and unbounded queries in GraphQL.

Check your understanding

A client sends POST /payments and the connection drops before any response arrives. Without an idempotency key, why is a blind retry dangerous?

  1. The server will reject any second POST to the same URL
  2. HTTP forbids sending the same request twice
  3. The first request may have succeeded, and POST is not idempotent, so the retry may create a second payment
  4. The retry will always be slower
The client cannot tell "never arrived" from "processed, reply lost". POST makes no promise that repeating it is harmless, which is why HTTP clients do not retry it automatically and why an idempotency key lets the server turn the retry into a replay.

Two copies of the same idempotent request, with the same key, reach two server instances at the same instant. What stops both from doing the work?

  1. A database UNIQUE constraint on the key: only one insert succeeds, and the other waits for or reports the first's result
  2. Checking whether the key exists first and inserting it only if absent
  3. The clients' clocks being synchronised
  4. HTTP/2 multiplexing
Check-then-insert is a race: both checks can pass before either insert. An atomic claim enforced by the database is what decides who goes first. Clocks and multiplexing are irrelevant.

A user is paging through a feed with ?offset=20&limit=20. Between requests, three new items appear at the top. What happens?

  1. Nothing; offset pagination is immune to inserts
  2. Three items are skipped
  3. The server returns an error
  4. The next page begins with items the user already saw on the previous page
An offset counts positions. Inserting at the top pushes every row down by three, so the last three rows of the previous page reappear. Deleting rows has the opposite effect and causes skips. A cursor anchored to a row's value avoids both.

Why should a pagination cursor be opaque to clients?

  1. So it is harder for users to guess the page number
  2. So you can change what is inside it, or the whole pagination strategy, later without breaking anyone
  3. Because base64 is encrypted
  4. Because HTTP requires it
Whatever clients can parse, they will parse, and then it is a contract. An opaque token lets you add filters, change the sort key or move data stores. Base64 is encoding, not encryption, so opacity is a promise, not security.

Which is the best response for a failed validation of a request body, in a well-designed API?

  1. 200 OK with {"error": "bad input"}
  2. 500 with the exception message
  3. A 4xx status with an application/problem+json body whose stable type and field errors a program can read
  4. A redirect to an error page
The status class tells infrastructure and clients who is at fault and whether retrying helps; a standard body tells programs what to do. Returning 200 hides the failure from monitoring and caches, and a 500 blames the server for the client's mistake.

A GraphQL query for 50 orders, each with its customer, causes 51 database queries. What is this called and what is a standard remedy?

  1. The thundering herd; add a circuit breaker
  2. The N+1 problem; batch the customer lookups within the request
  3. Head-of-line blocking; switch to HTTP/3
  4. A cache stampede; add a lock
One query for the list plus one per item is N+1. A dataloader-style batch collects the 50 customer ids and fetches them in one query. Query depth and cost limits then stop clients from composing queries that are expensive in other ways.

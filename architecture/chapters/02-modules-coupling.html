Modules, Coupling & Cohesion

Chapter 1 said that complexity comes from dependencies and obscurity. This chapter is the practical craft of controlling both: how to divide a system into modules, how to make each one hide as much as it can behind as little interface as possible, and how to recognise the seven common ways modules end up tied together.

Why this matters

Every architecture style you will meet (layers, hexagons, services) is the same idea applied at a bigger scale: draw boundaries, keep interfaces small, hide decisions. If you can judge a single class or package by these criteria, you can judge a system. And you will make this judgement dozens of times a week in code review, long before you ever draw a system diagram.

What a module is, at any scale

A module is any unit of code that has an interface (what other code is allowed to see and use) and an implementation (everything behind it). The word does not mean a Python file specifically. A function is a module: its signature is the interface and its body the implementation. So is a class, a package, and a whole service reached over HTTP.

This is why this chapter matters for architecture: design principles for a function or class are the same ones that decide where service boundaries go. The difference is how expensive it is to fix a mistake. A badly designed function is changed in minutes. A badly drawn service boundary can cost quarters.

Interface versus implementation

The interface of a module is everything a user of it must know to use it correctly. Part of that is formal and written in code: the names, parameters and types. But much of it is informal: what the method does, what it assumes, what errors it can raise, whether order matters, whether it is safe to call from two threads, roughly how slow it is. The implementation is the code that does the work and that, ideally, nobody else needs to read.

The informal part is where interfaces quietly get big. If using a function correctly requires knowing that it must be called after init(), or that it mutates its argument, those facts are part of its interface whether or not they are written down. Hidden interface is obscurity.

Deep and shallow modules

Ousterhout's most useful idea in this area is the idea of deep and shallow modules. Picture each module as a rectangle. The area is the functionality it provides. The top edge is its interface, the cost it imposes on users. A deep module gives a lot of functionality behind a small interface: big area, short edge. A shallow module has an interface nearly as complicated as the work it does: a lot of edge for very little area.

A classic deep module is the Unix file I/O interface. A handful of calls (open, read, write, lseek, close) sit in front of an enormous amount of hidden work: file systems, caching, permissions, device drivers, disk scheduling. You can use files productively without knowing any of it (the machinery of systems chapter 8 is behind that small door). Contrast that with a wrapper that exposes every knob of the thing it wraps and hides nothing.

A shallow wrapper

Here are two "abstractions" I have seen in real codebases, in miniature. FileHandle wraps open() method for method, and JsonEncoder wraps json. To store one value the caller still has to know the file format, to flush, and to fsync (data chapter 4's append-only log and systems chapter 9's durability are both leaking through).

# SHALLOW: a wrapper whose interface is as big as what it hides. It hides nothing.
import json, os

class FileHandle:                      # "abstraction" over open()
    def __init__(self, path, mode): self.f = open(path, mode)
    def write(self, text): self.f.write(text)
    def flush(self): self.f.flush()
    def fsync(self): os.fsync(self.f.fileno())
    def seek(self, pos): self.f.seek(pos)
    def readline(self): return self.f.readline()
    def close(self): self.f.close()

class JsonEncoder:                     # "abstraction" over json
    def encode(self, obj): return json.dumps(obj)
    def decode(self, text): return json.loads(text)

# To store one value, the CALLER must know the format, the flushing and the fsync:
import tempfile, pathlib
path = pathlib.Path(tempfile.mkdtemp()) / "kv.log"
fh, enc = FileHandle(path, "a"), JsonEncoder()
fh.write(enc.encode({"k": "user:1", "v": "Ada"}) + "\n")
fh.flush(); fh.fsync(); fh.close()
print(path.read_text().strip())
$ python3 c2_shallow.py
{"k": "user:1", "v": "Ada"}

Every caller must repeat those steps in the right order, and every caller now depends on the format. The classes exist, so it looks abstracted, but they remove no knowledge from the caller. This is what Ousterhout calls classitis: the belief that many small classes are good in themselves, producing shallow modules that add interface without hiding anything.

A deep module

Now the same job as a small file-backed key-value store. The interface is three methods. Behind it: the record format (JSON lines), an in-memory cache rebuilt on start-up, fsync so each write is durable before put returns, tolerance of a half-written last line after a crash, and compaction through an atomic rename. Callers know none of it.

# DEEP: three methods in, and the format, cache, crash safety and compaction hide behind them.
import json, os, tempfile
from pathlib import Path

class KV:
    """A durable key-value store. put/get/delete are the whole interface."""
    _COMPACT_AFTER = 1000                          # an internal tuning knob, never exposed

    def __init__(self, path):
        self._path = Path(path)
        self._cache: dict[str, str] = {}
        self._log_lines = 0
        self._load()
        self._f = open(self._path, "a", encoding="utf-8")

    def put(self, key: str, value: str) -> None:
        self._append({"k": key, "v": value})
        self._cache[key] = value
        self._maybe_compact()

    def get(self, key: str) -> str | None:
        return self._cache.get(key)

    def delete(self, key: str) -> None:
        self._append({"k": key, "d": True})
        self._cache.pop(key, None)
        self._maybe_compact()

    # ---- everything below is hidden knowledge ----
    def _append(self, record: dict) -> None:
        self._f.write(json.dumps(record) + "\n")
        self._f.flush()
        os.fsync(self._f.fileno())                 # durable before put() returns
        self._log_lines += 1

    def _maybe_compact(self) -> None:
        if self._log_lines > self._COMPACT_AFTER:
            self._compact()

    def _load(self) -> None:
        if not self._path.exists():
            return
        for line in self._path.read_text(encoding="utf-8").splitlines():
            try:
                rec = json.loads(line)
            except json.JSONDecodeError:
                break                              # torn last write after a crash: ignore it
            if rec.get("d"): self._cache.pop(rec["k"], None)
            else: self._cache[rec["k"]] = rec["v"]
            self._log_lines += 1

    def _compact(self) -> None:
        tmp = self._path.with_suffix(".tmp")
        with open(tmp, "w", encoding="utf-8") as out:
            for k, v in self._cache.items():
                out.write(json.dumps({"k": k, "v": v}) + "\n")
            out.flush(); os.fsync(out.fileno())
        self._f.close()
        os.replace(tmp, self._path)                # atomic swap
        self._f = open(self._path, "a", encoding="utf-8")
        self._log_lines = len(self._cache)

path = Path(tempfile.mkdtemp()) / "kv.log"
kv = KV(path)
kv.put("user:1", "Ada"); kv.put("user:2", "Grace"); kv.put("user:1", "Ada L."); kv.delete("user:2")
print(kv.get("user:1"), kv.get("user:2"))
print(len(path.read_text().splitlines()), "log lines on disk")
KV._COMPACT_AFTER = 3                              # (demo only) force a compaction
kv.put("user:3", "Alan")
print(len(path.read_text().splitlines()), "log lines after compaction")
print(KV(path).get("user:1"), "<- recovered by a brand new instance")
$ python3 c2_deep.py
Ada L. None
4 log lines on disk
2 log lines after compaction
Ada L. <- recovered by a brand new instance

Four log lines became two after compaction, and a fresh KV instance recovered the right answer from the file. None of that is visible to a caller. If next month you decide to move to a binary format, or write a hash index like the one in data chapter 4, the three methods stay exactly the same.

Go deeper: what this little store does not do optional

It is a teaching sketch. It is not safe for two processes at once, it keeps every key in memory, _COMPACT_AFTER is crude, and a crash between writing the temporary file and the rename leaves a stray .tmp file that a real implementation would clean up. Notice that none of these shortcomings would change the three-method interface: a deeper implementation could fix all of them without any caller noticing. That is the point of hiding information.

Analogy: a city's front doors

A deep module is a building with one clear front door and a lot happening inside: you walk in, ask the reception desk for what you need, and never see the kitchens, wiring or filing rooms. A shallow module is a building with a side door into every room and a sign saying which cupboard has what. Visitors must learn the building's layout, and when the owners rearrange the rooms, every visitor is lost. Zoning rules in a city work the same way: they say which door you must use.

Where it breaks down: in a city you can see through a window and walk around the back. In code, "the back door" is invisible: a caller can reach into an underscore-prefixed attribute and nothing stops them. A boundary only works if the language, the review process, or a tool (see Lab 3) enforces it.

Information hiding

In 1972 David Parnas published "On the Criteria to Be Used in Decomposing Systems into Modules", and the idea has not aged. He took one small program (a KWIC index, which generates a "key word in context" listing by rotating each line so each word takes a turn at the front) and compared two ways to divide it. The first split the program into the steps of a flowchart: read lines, shift them, alphabetise, print. The second made each module responsible for one design decision likely to change: how lines are stored, how the shifting is represented, how the sorting is done. Both versions worked. But when requirements changed (a different input format, a different storage layout), the first needed edits across almost every module, because all the steps shared knowledge of the data layout. The second needed edits in one. Parnas's conclusion became information hiding: a module should hide a design decision from the rest of the system.

The failure it prevents is information leakage: the same piece of knowledge appearing in more than one module. The shallow example above leaks the file format to every caller. A tell-tale sign is two modules that must be changed together because they both "know" how something is encoded. Ousterhout notes a sneaky cause: splitting code by the order things happen (read, then parse, then write) rather than by the knowledge involved, which is how Parnas's first decomposition went wrong.

Cohesion: things that change together live together

Cohesion is how strongly the contents of one module belong together. The most practical definition is a statement about change: a cohesive module is one where a single kind of change touches only that module, and where the pieces inside it usually change together. If a requirement means editing five modules, those five probably hold one idea that was cut in pieces. (Robert C. Martin's phrase for the same instinct is that a module should have "one reason to change".)

Two failure modes are worth naming:

  • Scattered: one idea spread across many modules, so every change touches all of them. This is change amplification from chapter 1.
  • Grab-bag: unrelated things collected because they are "utilities" or "helpers". utils.py with date parsing, HTTP retries and price formatting is a pile, not a module. It changes for three different reasons, so every change to any of them re-tests all of them.

Cohesion and coupling are two views of the same thing. High cohesion inside modules and low coupling between them are both ways of saying that most changes should stay in one place.

The kinds of coupling

Coupling is how much one module depends on another, and how tight that dependency is. Not all coupling is equal. The first five kinds below come from the structured-design literature of the 1970s and run from loose to tight; the last two are very common in modern systems and cut across that scale.

CouplingWhat it meansCode smellFix
DataModules share only simple values passed as arguments.Usually none. Trouble only when a function takes ten loose parameters that always travel together.Group them into a small value object. This is the coupling to aim for.
StampA whole record or object is passed, but only part is used.A function takes a full Customer just to read .email, so changing Customer can break it.Pass the fields needed, or depend on a narrow interface (a protocol) with only what is used.
ControlThe caller passes a flag that tells the callee which path to take.Boolean parameters; calls like close(order, True, False); an if on the parameter at the top of the function.Split into separate, well-named operations. See the example below.
Common / globalModules share mutable state: a global, a singleton, a shared table.Module-level mutable dicts; "this only works if setup() ran"; tests that pass alone and fail together.Give the state one owner and pass it explicitly (or inject it); expose operations, not the data.
ContentOne module reads or changes another's internals.order._items.append(x); one service reading another's database tables.Make internals private; expose operations. Across services: each owner exposes an API and no one else touches its data (chapter 12).
TemporalOperations must happen in a particular order or at a particular time.open(); configure(); send() where reordering corrupts things; docs saying "always call init first".Make wrong orders impossible: do setup in the constructor, use a context manager, or offer one operation that performs the sequence.

Go deeper: a finer vocabulary optional

There is a more detailed vocabulary for grading coupling, called connascence. If you want to compare two couplings more precisely than "tighter" or "looser", search for it. The scale above is enough for the rest of this course.

A flag argument, refactored

Control coupling is the one you will see most often in review. A flag is a tiny, convenient way to reuse a function, and a steady source of confusion: at the call site close_order(order, True, False) says nothing. Worse, the callee now has two jobs, and every new variant adds another flag and another if.

from dataclasses import dataclass

@dataclass
class Order:
    id: int
    total: float
    status: str = "new"

# BEFORE: control coupling. The caller steers the callee's internals with a flag.
def close_order(order: Order, refund: bool, notify: bool) -> list[str]:
    log = []
    if refund:
        order.status = "refunded"
        log.append(f"refund {order.total:.2f}")
    else:
        order.status = "paid"
        log.append(f"capture {order.total:.2f}")
    if notify:
        log.append(f"email about order {order.id}")
    return log

print(close_order(Order(1, 20.0), True, False))      # which one is True?
print(close_order(Order(2, 35.5), False, True))

# AFTER: two operations with honest names; notification is a separate decision.
def capture(order: Order) -> str:
    order.status = "paid"
    return f"capture {order.total:.2f}"

def refund(order: Order) -> str:
    order.status = "refunded"
    return f"refund {order.total:.2f}"

def notify(order: Order) -> str:
    return f"email about order {order.id}"

print([refund(Order(1, 20.0))])
o = Order(2, 35.5)
print([capture(o), notify(o)])
$ python3 c2_flag.py
['refund 20.00']
['capture 35.50', 'email about order 2']
['refund 20.00']
['capture 35.50', 'email about order 2']

The two versions produce the same results. The second has three tiny functions with honest names, and notification is a separate decision the caller makes in plain sight. The first call in each pair is the cryptic one: which argument was the refund?

Common misconception

"Low coupling means modules should not depend on each other at all." Impossible and undesirable: a system whose parts never interact does nothing. The aim is appropriate coupling: modules depend on each other's small, stable interfaces, not on each other's internals, shared state or timing.

Which way should dependencies point?

When module A depends on module B, a change in B can force a change in A. So the direction of the arrow decides who is affected by whose changes. A useful rule (the Stable Dependencies Principle in Robert C. Martin's writing) is: depend on things more stable than you.

"Stable" here means unlikely to need change. The language's standard library is very stable. Your core business rules (an order cannot ship before it is paid) change occasionally. A web framework's request objects, a UI layout, a vendor's SDK and a third-party JSON shape are volatile. If your stable business rules depend on a volatile library, every library upgrade ripples into your most important code. Flip the arrow so that the volatile thing depends on the stable one, and the ripple stays at the edge.

Stability is not quality. A volatile module may be well designed, and a stable one may be a fossil. The question is only: how often will this need to change, and who pays when it does?

Warning signs

  • Pass-through methods. A method that does nothing except call another method with nearly the same signature. It adds interface without adding function. A pass-through is a symptom that responsibilities were split in the wrong place.
  • Classitis. Many tiny classes, each with one trivial method, justified by "single responsibility". Each class is shallow; together they impose a large interface.
  • Conjoined modules. Two modules you cannot understand one without the other: usually one concept was cut in two.
  • The same fact in two places. Information leakage: a format, a constant or an invariant that two modules must agree on without any shared home.
class Store:                                   # does real work
    def __init__(self): self._d = {}
    def get(self, key): return self._d.get(key)
    def put(self, key, value): self._d[key] = value

class Cache:                                   # a pass-through: same signatures, adds nothing
    def __init__(self, store): self._store = store
    def get(self, key): return self._store.get(key)
    def put(self, key, value): return self._store.put(key, value)

c = Cache(Store()); c.put("a", 1); print(c.get("a"))
$ python3 c2_pass.py
1

The Cache here has the same two methods as the Store it wraps and adds nothing. Either give it a real job (cache entries, expire them, count hits) or delete it. Decorators and adapters are legitimate when each adds something (a different behaviour, a different interface). The test is whether the new layer hides knowledge.

General-purpose and special-purpose interfaces

A common reflex is to make an interface exactly match today's use: one method per button in the UI. That produces many methods that each serve one caller. The opposite reflex, building a framework for every conceivable future use, produces interfaces nobody understands. Ousterhout recommends the middle path: make the interface somewhat general-purpose. The functionality should reflect today's needs, but the interface should be general enough to support several uses without being tied to any one of them.

His example is a text editor. A special-purpose text class has backspace(), delete_key() and delete_selection(), knowing about the keyboard. A somewhat general one has a single delete(start, end); the user-interface layer maps each gesture onto it.

# Special-purpose: one method per UI gesture. The text class knows about the keyboard.
class SpecialText:
    def __init__(self, s): self.s, self.cursor = s, len(s)
    def backspace(self):
        if self.cursor: self.s = self.s[:self.cursor - 1] + self.s[self.cursor:]; self.cursor -= 1
    def delete_key(self):
        self.s = self.s[:self.cursor] + self.s[self.cursor + 1:]
    def delete_selection(self, start, end):
        self.s = self.s[:start] + self.s[end:]; self.cursor = start

# Somewhat general-purpose: one operation on a range; the UI layer maps gestures onto it.
class Text:
    def __init__(self, s): self.s = s
    def delete(self, start: int, end: int) -> None:
        self.s = self.s[:start] + self.s[end:]

def on_backspace(t: Text, cursor: int) -> int:     # UI code: the gesture lives here
    if cursor: t.delete(cursor - 1, cursor)
    return max(cursor - 1, 0)

def on_delete_key(t: Text, cursor: int) -> int:
    t.delete(cursor, cursor + 1)
    return cursor

t = Text("architecture")
c = on_backspace(t, len(t.s)); print(t.s, c)
c = on_delete_key(t, 0); print(t.s, c)
t.delete(2, 6); print(t.s)
$ python3 c2_general.py
architectur 11
rchitectur 0
rcctur

The general version has fewer methods, no knowledge of the keyboard, and the user-interface rules sit in the UI layer where they belong. A useful test is to ask: what is the simplest interface that will cover all my current needs? If the answer has fewer methods than you expected, you have found a deeper module.

A change inside a leaky module, and inside a deep one

Return to the key-value store. Suppose a requirement arrives: store records as JSON lines and fsync every write. See what happens in two designs: one where callers read the file themselves and know the format (leaky), and one where they only call get and put (deep).

Step through

The same change, leaky vs deep

  1. Two designs of the same store. On the left, three callers read kv.log directly and each parses the "key,value" lines. On the right, they use a thin interface (the cyan bar: get, put, delete), and the format, cache and fsync policy live behind it. Both work today.
  2. The change request arrives. "Store records as JSON lines, and fsync on every write." It is a perfectly ordinary requirement. Whether it is a small job or a big one is decided entirely by the design you already have.
  3. Leaky: the ripple. Every caller knew the format, so every caller breaks, and so does the file itself, which old and new code now read differently. The format knowledge was leaked to three places. You must find all of them (are you sure you have?), change them together and release them together. That is content coupling and deployment coupling from the table.
  4. Deep: the change stays inside. Only the implementation behind the interface changes: a new serialiser and an fsync call. The three callers are not edited at all; their ordinary tests still apply. The interface did its job as a firewall.
  5. The lesson. The size of a change is not decided by the change; it is decided by how much knowledge was shared before it arrived. Information hiding is how you pay a small cost now (designing the interface) to make unknown future changes cheap. It is not free: if the requirement had been "add a range query", the interface itself would have to change, and all callers would feel it (chapter 1's explorer shows this).

Boundaries at the architecture scale

Everything here scales up. A modular monolith is a single program whose modules obey these rules strictly, often with tools that fail the build if one module reaches into another's internals. That is the subject of Lab 3: Enforce Module Boundaries, where you will write that check yourself. A real-world story of a large company doing exactly this, and what it cost and bought them, is told in Case 3: Shopify's modular monolith. Read it after finishing this chapter, and notice how much of it is about the coupling kinds in the table: especially content coupling through a shared database and the discipline needed to stop it creeping back.

Try it yourself

Try it yourself: make a module deeper

Pick a class in your own code that wraps something. Write down its public methods. For each, ask: does a caller need to know something that this class should have hidden? (the order to call things in, a file format, a flag meaning). Then try one of these three experiments with the code in this chapter:

  • Run c2_deep.py and change the storage format inside KV (for example to key=value lines). The three-line demo at the bottom should still print the same answers without being edited. If you have to touch it, the interface was not holding.
  • In c2_flag.py, add a third behaviour ("partial refund"). Count how many places you must edit in the flag version and in the split version.
  • Add a pass-through method to a class of yours and then ask a teammate what it is for. If they cannot tell, delete it.

Distributed systems connection

A service is a module whose interface is a network protocol, and every principle here applies with the stakes raised. Deep services hide their data and logic behind a small API; shallow ones expose their tables ("content coupling over the wire"). Temporal coupling becomes a caller that needs the callee to be up right now, which is the fragile kind of dependency the networking course warned about in chapter 16. Deployment coupling is the infamous distributed monolith: many services that must still be released together. The test for a good service boundary is the one you just used for functions and classes: how much does a caller have to know?

Key takeaways

  • A module is anything with an interface and an implementation, at any scale: function, class, package or service.
  • Prefer deep modules: lots of hidden functionality behind a small interface. Wrappers that mirror what they wrap are shallow and add only cost (classitis, pass-through methods).
  • Information hiding (Parnas, 1972): each module hides a design decision likely to change. Leakage, the same knowledge in two places, is the thing to hunt.
  • Cohesion: things that change together live together. Avoid scattering one idea and avoid grab-bag modules like utils.
  • Know the seven couplings: data (best), stamp, control, common/global, content, temporal and deployment. Move toward the loose end.
  • Point dependencies at things more stable than you; keep volatile code at the edges.
  • Prefer somewhat general-purpose interfaces: general enough to serve several uses, with functionality for today's needs.

Check your understanding

Which describes a deep module?

  1. One with many methods, so it can do everything
  2. One whose implementation is many files long
  3. A lot of functionality hidden behind a small, simple interface
  4. One that other modules depend on heavily
Depth is the ratio of functionality to interface. Many methods make an interface wide, not deep. Implementation length and popularity say nothing about how much the interface hides.

A function export(report, True, False) where the booleans mean "as PDF" and "email it" is an example of which coupling?

  1. Control coupling: the caller steers the callee's internals with flags
  2. Data coupling
  3. Content coupling
  4. Deployment coupling
Flag arguments are the textbook form of control coupling. The fix is to separate the operations (export_pdf, send_by_email) so the call site says what it means and each function does one thing.

In Parnas's KWIC comparison, why did the decomposition based on hidden design decisions cope better with changing requirements?

  1. It used fewer lines of code
  2. It ran faster on the hardware of the time
  3. It avoided the need for modules altogether
  4. Each likely change (such as how lines are stored) was confined to one module, instead of being known to every processing step
Parnas's point is about change, not speed or size. When all the steps of a flowchart share knowledge of the data layout, changing the layout changes them all. When one module hides that decision, only it changes.

Your stable business rules import a volatile web-framework request class. According to the dependency direction rule, what should you do?

  1. Nothing; frameworks are stable enough
  2. Reverse the dependency: let the framework-facing code convert requests and call the rules, so the rules no longer depend on the framework
  3. Copy the framework into your rules module
  4. Rename the rules module to match the framework
Depend on things more stable than you. The rules should not know about the framework; an outer adapter translates requests into plain data and calls them. That is the seed of hexagonal architecture (chapter 5).

A class Cache has get and put methods that simply call the same methods on the object it wraps. What is the best description?

  1. A deep module, because it has a small interface
  2. Good use of the single-responsibility principle
  3. A pass-through: it adds interface without hiding anything, so it needs real behaviour or should be removed
  4. Stamp coupling
A small interface alone does not make a module deep; it must also hide substantial functionality. This wrapper hides nothing. Give it a job (real caching, expiry) or delete it.

Two services must always be deployed in a specific order, otherwise requests fail. Which coupling is this, and what is a standard way to loosen it?

  1. Common coupling; put the state in one shared database
  2. Deployment (and temporal) coupling; keep contracts backward compatible so either can be released first
  3. Data coupling; there is nothing to fix
  4. Content coupling; merge the services' databases
Needing a release order is deployment coupling. Making changes backward compatible, and rolling them out in two phases, lets each service ship on its own schedule. Sharing a database would add content and common coupling, making things worse.

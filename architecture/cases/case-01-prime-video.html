Prime Video: Back to a Monolith

In 2023 the Prime Video team that monitors audio and video quality described how they rebuilt one tool. It had been built from AWS Step Functions and Lambda functions, with S3 passing data between the pieces. They moved the same logic into a single process running on ECS, and reported a 90% reduction in operating cost. Headlines often boil it down to "microservices are dead" (general commentary, not from the report). The post is narrower and more useful than that.

The pattern in one sentence

Right-size your boundaries to the workload: when the pieces of a pipeline always run together on the same data, paying for orchestration and for moving that data across a network at every hop can cost more than the independence it buys.

The cast

The roles are simple. They map onto the choice you met in chapter 11 (monolith versus services) and on the cost of every network hop from chapter 13.

The monitoring tool
Built by Prime Video's Video Quality Analysis team. It inspects streams, detects quality problems that users would notice (the report describes analysing frames and audio buffers for stream defects), and triggers repair actions.
Detectors
Components that look for specific defects. The report says machine learning models were used to find them.
AWS Step Functions
A managed orchestrator. In the first design it coordinated the other components, and, as a general fact about the service, it is billed per state transition.
AWS Lambda functions
The serverless units that did the actual work in the first design.
Amazon S3
Object storage. In the first design it held the intermediate work items, which the report describes as video frames and audio buffers, between steps.
ECS on EC2
Where the second design runs: containers on virtual machines the team operates.

What happened, step by step

The first version was a serverless, distributed design. A Step Functions workflow moved each analysed stream through Lambda functions, and each function wrote its result to S3 for the next one to read. The report describes two problems. The system supported only around 5% of the load the team expected, and running it at scale was expensive.

Step through

From distributed pieces to one process

  1. The first design. Step Functions orchestrates Lambda functions, and S3 holds the intermediate frames and audio buffers between stages.
  2. Where the money and the limits went. The report cites many Step Functions state transitions (several for every second of analysed stream) and a high volume of reads and writes to the S3 bucket. The team also hit the account limit on state transitions.
  3. The second design. The team consolidated the business logic into a single application process running on ECS on EC2. Data now moves in memory, so the S3 bucket is no longer needed, and the team implemented orchestration that controls components within a single instance.
  4. Scaling the new design. The report describes groups of detector instances distributed across different ECS tasks, so adding new detector types does not hit the limits of making one instance bigger.

Right-sizing, not "the end of microservices"

The most common misreading is that Prime Video abandoned microservices. The report does not say that. It describes the architecture of one service: the monitoring tool. The post says the distributed approach was not bringing many benefits for this particular use case. It does not generalise to Prime Video's other systems, and it does not tell anyone else what to do.

Even the new design keeps a service-style way of growing. The report says detector groups run across different ECS tasks, and the team added orchestration that controls components within a single instance. So the system still scales out by running more copies. What changed is where the boundary falls: between whole analysis runs and instances, instead of between every stage inside one run. The word "monolith" in the retelling is accurate in the narrow sense that the stages now live in one process.

Analogy: the assembly line and the workbench

Picture a craftsperson who passes a half-built chair to a colleague in another building after every cut, with a courier and a signed receipt each time. For a thousand-chair factory with different specialists that might make sense. For one person making one chair, the couriers cost more than the wood. Moving the whole job to one workbench keeps the same steps and removes the trips.

Where it breaks down: a workbench is one person. A single process shares fate, memory and deploy cycle across all its stages, which is a cost the analogy hides.

The pattern explained

Chapter 11 says the trade-offs of distribution are real: independent deploys and scaling on one side, network calls and operational complexity on the other. The key question this case asks is what unit actually needs independence. Two costs dominated here, and both are about movement, not about code.

Orchestration overhead

A managed workflow is billed and limited per state transition. When the work is a fine-grained pipeline that runs continuously, the number of transitions grows with the length of the stream, not with how interesting the work is. The report says the account's limit on transitions was reached.

Data transfer between stages

Frames and audio buffers are large and are needed immediately by the next stage. Writing them to S3 and reading them back adds latency and charges for every hop. In one process the next stage just reads the same bytes in memory.

General pattern (not a claim from the post): when stages are tightly coupled by large data and always run together, a process boundary or a network boundary between them is cost with little return. Chapter 13's point that every network hop has a price applies even when the "network" is a managed storage service.

Trade-offs and lessons

What was gained

According to the report: a 90% reduction in operational costs, the S3 intermediate storage eliminated, and the scalability ceiling lifted. The team also expected to use EC2 cost savings plans to cut costs further. The report does not say what the 90% is measured against, so treat it as the team's own headline figure for this one workload.

What was given up

General pattern, not from the post: stages no longer deploy or scale on their own, a bug in one stage can take down the process, and adding a very different kind of work may mean revisiting the design. The team accepted that for a use case where the independence was not paying for itself.

Measure before you generalise

The limits showed up when the team ran the system at scale: the report mentions bottlenecks that stopped them monitoring thousands of streams. General pattern: data volume, call rates and cost per call are better guides to where a boundary belongs than a diagram.

Reading the headlines

Reactions to the news varied, and we cite none of that commentary here because it is outside the report. The durable point is the one the team made for itself: pick the architecture that suits the workload in front of you, and be willing to change it.

Try it yourself

Count the overhead of a three-stage pipeline

This is a toy model with made-up numbers; it is not Prime Video's system. It only shows how the number of orchestrator transitions and storage operations grows with the length of a stream when every stage hands off through storage. It writes nothing to disk and uses only the standard library.

# Toy model (made-up numbers): one analysis pass over a stream, 3 stages.
# Distributed: every stage hands its output to the next through object storage.
# In-process: stages pass a Python object in memory.
STAGES = ["decode", "detect", "report"]

def distributed(seconds):
    hops = 0          # storage writes+reads between stages
    transitions = 0   # orchestrator state transitions
    for _ in range(seconds):
        for i, _stage in enumerate(STAGES):
            transitions += 1                 # orchestrator moves to this stage
            if i < len(STAGES) - 1:
                hops += 2                    # write result, next stage reads it
    return transitions, hops

def in_process(seconds):
    return 0, 0

for secs in (60, 3600):
    t, h = distributed(secs)
    print(f"{secs:>5}s of stream  distributed: {t:>6} transitions, {h:>6} storage ops"
          f"   in-process: {in_process(secs)[0]} transitions, {in_process(secs)[1]} storage ops")

Output when run:

   60s of stream  distributed:    180 transitions,    240 storage ops   in-process: 0 transitions, 0 storage ops
 3600s of stream  distributed:  10800 transitions,  14400 storage ops   in-process: 0 transitions, 0 storage ops

The point is the shape: both overhead counts are proportional to the stream's length, and the in-process version has no such term. Change STAGES to five stages and the storage operations grow faster than the transitions, because each hop costs a write and a read. Then ask the design question for your own system: which of your service-to-service calls hand over a lot of data, run in lock-step, and are always deployed together?

Distributed systems connection

A distributed design pays the cost of partial failure, serialisation and latency at every hop (see networking chapter 13 on latency and throughput, and chapter 16 on failure). Moving a pipeline into one process trades those costs for shared fate: if the process dies, every stage dies together. For a workload that is already an all-or-nothing analysis of one stream, that is often a good trade. The skill is noticing which boundaries buy real independence and which only add hops.

Key takeaways

  • The post is about one service (an audio/video monitoring tool), not a verdict on all microservices.
  • Orchestration (per-transition cost and limits) and data transfer between stages (S3 reads and writes) dominated the first design's cost.
  • The fix was to consolidate the stages into one process on ECS, removing the intermediate bucket, and to scale by running groups of detectors across ECS tasks.
  • The team reported about a 90% cost reduction; the figure is theirs and the baseline is not given in the coverage we could read.
  • Right-size boundaries to the workload, and measure at scale before deciding which boundaries earn their keep.

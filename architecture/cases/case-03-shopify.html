Shopify's Modular Monolith

Shopify's core is one of the largest Ruby on Rails codebases in the world, worked on by more than a thousand developers by the time of the first post below. When that codebase started to slow everyone down, the team did not split it into services. They drew boundaries inside it and built tools to keep them in place. Two Shopify Engineering posts, 18 months apart, tell the story and are candid about how far the work had got.

The pattern in one sentence

A modular monolith keeps one codebase and one deployable but enforces component boundaries inside it: each component exposes a small public interface, hides its internals, and a tool in CI rejects changes that reach around that interface.

The cast

Facts here come from two posts: "Deconstructing the Monolith" by Kirsten Westeinde (21 February 2019) and "Under Deconstruction: The State of Shopify's Monolith" by Philip Müller (16 September 2020). The ideas build on chapter 2 (modules, coupling and cohesion) and chapter 11 (monoliths, modular monoliths and services).

The monolith
A single Ruby on Rails application with over a decade of work behind it by 2019. The 2020 post gives its size as more than 2.8 million lines of Ruby and 500,000 commits.
Components
Groupings of code organised around business concepts such as orders, shipping, inventory and billing, instead of technical roles such as models, views and controllers. The 2020 post says the main monolith had 37 components, defined using Domain-Driven Design subdomains.
Public entry points
The deliberately exposed interface of a component. Everything else in the component is meant to be private.
Wedge
An in-house tool from the first post. It used Ruby tracepoints during the CI test run to build a call graph and flag calls between components that were not allowed.
Packwerk
The static-analysis tool from the second post, developed after Wedge's results proved often not useful. It checks references between components and is wired into the pull request workflow.

What happened, step by step

The first post describes the starting point. The codebase had no boundaries between areas such as shipping and checkout, so any code could call any other code. The post says Shopify outgrew its monolith in 2016, when building and testing new features was getting steadily harder. Changes had unpredictable effects, and a small change could cause a cascade of unrelated test failures. New developers had to learn many unrelated areas before shipping even simple features.

Step through

Tangled, then bounded, then enforced

  1. Before. The post says the codebase had no boundaries between functions like shipping and checkout, so they could call each other freely.
  2. Components with public entry points. Code is reorganised around business concepts. The post wants each component to offer a clean, dedicated interface and to own its data exclusively. The reorganisation moved about 6,000 Ruby classes in one large automated pull request.
  3. Enforcement. A call that reaches a component's non-public code is flagged. In the first post this was Wedge's job at CI time. In the 2020 post, Packwerk performs a static check and can reject a pull request that breaks the dependency graph or a component's encapsulation.

The pattern explained

Components. The first thing the posts stress is how to cut. Technical layers (models here, controllers there) leave the business logic scattered. The team grouped code by business concept instead, so a change to shipping touches mostly shipping. In the language of chapter 2, this is raising cohesion and lowering coupling without changing how the code is deployed.

Public entry points. A boundary is only real if something is on the other side that you are not allowed to touch. The 2020 post says each component has public entry points covering large parts of its responsibilities, and that Sorbet (a static type checker) is now used to define input and output contracts at component boundaries. That is chapter 2's idea of a deep module, a narrow interface over a lot of hidden implementation, applied inside one process.

Enforcing dependencies. Conventions erode, so the posts put weight on tooling. Wedge scored each component and listed its violations, but the 2020 post reports that it took over an hour to run. Packwerk analyses static references to constants instead of tracing calls at runtime, and the post says it runs on the largest codebase in a few minutes and in the pull request workflow. It was used to restrict dependencies in about a third of the components at the time of writing.

Analogy: a city with zoning rules

The monolith is one city. For years anyone could build a door from any building into any other building. The team zoned it into neighbourhoods (components), marked the official gates (public entry points), and appointed an inspector (Packwerk) who refuses a permit for a new tunnel through a neighbour's wall. It is still one city with one set of utilities.

Where it breaks down: in a real city the neighbourhoods grow up around the roads. Here, much of the 2020 post describes retrofitting boundaries onto roads and tunnels that already existed.

Why not microservices?

The first post says the team considered microservices and rejected them for this problem. As the post lays it out, microservices would add separate test and deployment pipelines, infrastructure overhead, network latency and reliability costs, and coordinated deploys for large refactors. What the team wanted was modularity without more deployment units. The post also argues that no architecture fits every stage of a company's growth, and that re-architecting should be done as late as practical, once the domain is understood. It cites Martin Fowler's view that you should not start a new project with microservices, even if you are sure the application will be big.

The second post adds that some other large Shopify apps were also being componentised, and that some of those aimed to become separate services while others aimed to remain modular monoliths. So the position is not "never services". It is "boundaries first, then decide per case". This is the same advice as chapter 11's.

Trade-offs and lessons

What the boundaries bought

The 2019 post gives one example: Shopify replaced its legacy tax engine with a new tax calculation system, which it says would have been nearly impossible before the isolation work. The stated goals of the 2020 work include faster onboarding, targeted test runs and changes that do not break other parts.

The honest state of progress

The 2020 post says that almost no component had a complete, strong boundary yet. When the analysis began, its dependency graph was dense: every component depended on over half of the others, with many circular dependencies. It names the central Shop class and the way Active Record models are reachable from everywhere as obstacles.

Fewer hard rules

The 2020 post says that pushing for consistency added rules, which add friction because they have to be learned, remembered and followed, and that the team now has fewer hard rules.

Cost of the reorganisation

Moving the files cost some history: the first post says Git recorded the moves as deletions and creations, so part of the history was lost.

Common misconception: "a modular monolith is just a tidy folder structure"

Folders alone do not stop a call. The posts' main point is that the boundary must be checked by a tool, in the same pipeline that gates every change. Without that, the dependency graph drifts back to a tangle, which is why Shopify built Wedge and then Packwerk.

Try it yourself

A twelve-line boundary checker

This script is a deliberately tiny illustration of the idea, not Packwerk and not Shopify's code. It parses two in-memory Python "files" and reports any reference to another component that is not on its declared public list. Read-only, standard library only.

# A tiny boundary checker in the spirit of Packwerk (this is NOT Packwerk).
# Components declare a public surface; we flag references to anything else.
import ast
PUBLIC = {"orders": {"orders.place_order"}, "billing": {"billing.charge"}}
SOURCES = {
 "orders/checkout.py": "import billing\ndef place_order(c):\n    billing.charge(c)\n    return billing._ledger_rows(c)\n",
 "billing/charge.py":  "import orders\ndef charge(c):\n    return orders.place_order(c)\n",
}
def check(path, src):
    me = path.split("/")[0]
    for node in ast.walk(ast.parse(src)):
        if isinstance(node, ast.Attribute) and isinstance(node.value, ast.Name):
            comp = node.value.id
            if comp in PUBLIC and comp != me:
                ref = f"{comp}.{node.attr}"
                if ref not in PUBLIC[comp]:
                    yield f"{path}:{node.lineno}: {me} -> {ref} is not public"
for p, s in SOURCES.items():
    for v in check(p, s): print(v)
print("done")

Output when run:

orders/checkout.py:4: orders -> billing._ledger_rows is not public
done

The call to billing.charge is on the public list, so it passes. The call to billing._ledger_rows is not, so it is flagged with a file and line. Run the same idea on your own project with a few lines of ast, or build the full thing in Lab 3: Enforce Module Boundaries.

Distributed systems connection

A modular monolith lets you keep in-process calls (fast, atomic, easy to debug) and still practise the discipline that microservices demand: owned data, narrow interfaces, explicit dependencies. General pattern, not from the posts: this is also the case chapter 11 makes for starting modular: if you ever need a split, the seams already exist. A module whose dependencies are explicit can be lifted into a service by replacing its in-process calls with network calls, at which point everything in chapter 13 (timeouts, partial failure) starts to apply.

Key takeaways

  • Shopify chose a modular monolith over microservices to get modularity without adding deployment units, network costs and coordinated deploys.
  • Components are organised by business concept, own their data, and expose public entry points; everything else is private.
  • Boundaries are enforced by tooling in CI: first Wedge (runtime call graph), then Packwerk (static references, much faster).
  • The 2020 post is frank that the work was far from finished: dense, circular dependencies and few strong boundaries.
  • The approach is a stage, not a creed: some componentised apps may become services, others stay monoliths.

LMAX: One Thread, Millions of Orders

The usual answer to "make it faster" is "use more threads". LMAX, a financial trading platform in London, went the other way. Its business logic runs on a single thread, entirely in memory, fed by a log of input events that is written to disk before the logic sees them. Martin Fowler's 2011 article and the Disruptor paper explain why that can be much faster than a design full of locks, queues and a database.

The pattern in one sentence

Make the core deterministic, single-threaded and in-memory, and put durability in front of it as an ordered log of input events: the log gives you recovery and replication, the single thread removes locking, and the state can always be rebuilt by replaying the events.

The cast

The roles come from Martin Fowler's article "The LMAX Architecture" (12 July 2011) and from the LMAX Disruptor technical paper. Event sourcing in general is chapter 16; you can build a small version in Lab 5.

Business Logic Processor (BLP)
The core. It runs all business logic sequentially on one thread, in Java, and "operates entirely in-memory, there is no database or other persistent store", in Fowler's words.
Input disruptor
The concurrency component in front of the BLP. The article says it handles unmarshalling, journaling and replication of input events.
Output disruptors
Components behind the BLP that marshal and send results, each topic on its own disruptor.
Journal
A durable file-system record of every input event, in order.
Replicas
Other BLPs processing the same input. The article describes two in the main data center and a third at a disaster-recovery site.
Disruptor
Fowler describes it as a concurrency component that behaves like a multicast graph of queues but is implemented as a single ring buffer. It is open source.

The problem the design set out to solve

LMAX is a retail financial trading platform that needs low latency. Fowler's article says the first prototype used actors and queues. Profiling showed that managing the queues took more time than the business logic. Queues bring write contention, which leads to locks and to kernel context switches that flush CPU caches. The article states the conclusion it drew: "to get the best caching behavior, you need a design that has only one core writing to any memory location."

The Disruptor paper makes the same argument in its own terms. It says the cost of queue latency was in the same order of magnitude as the cost of disk I/O, and traces the trouble to queues conflating several design concerns and contending on their head, tail and size variables.

How an order flows

Step through

An order through the LMAX architecture

  1. An input event arrives. Everything the core reacts to is modelled as an event in one ordered stream.
  2. Journal and replicate first. Fowler's article says the input disruptor journals every input event to the file system, not a database, and replicates it. The journal is a stream of sequential writes, hence the article's tagline "disk is the new tape."
  3. The business logic runs. One thread, no locks, no I/O on the hot path, no object-relational mapping. The article says calls to external services are not allowed inside the processor; the work is split into an output event and a later input event that resumes it.
  4. Results go out. Output events pass through output disruptors, which marshal and send them.
  5. Recovery is replay. The article says current state can be rebuilt by replaying the input event stream, as one rebuilds a working copy from version-control commits. Snapshots are taken nightly so that replay is short; a full restart takes less than a minute, per the article.

The pattern explained

Event sourcing as the durability story

The memory is volatile, so the journal is the truth. This is the "state is the fold of the events" idea from chapter 16, applied to the input events, not to a log of state changes. Replication works the same way: the article describes a leader that broadcasts input events over IP multicast to followers, which gives a deterministic sequence, and says output from all but one processor is ignored. For replicas to stay identical the business logic must be deterministic, which is why the article's rule that the logic does no external calls matters.

One thread, because contention is the cost

A single thread sounds like a limit and is here a feature. If only one thread writes the business state, nothing needs a lock, and the state stays hot in the CPU caches. Compare systems chapter 16, where one thread also juggles many connections: the idea there was to avoid blocking; here it is to avoid sharing. The same caution applies: nothing slow may ever run on that thread.

The Disruptor: a ring buffer with sequence numbers

The paper says the Disruptor is built on "a pre-allocated bounded data structure in the form of a ring-buffer", with entries allocated at start-up to reduce garbage-collection pressure. It says "Sequencing is the core concept to how the concurrency is managed in the Disruptor": producers claim the next slot in sequence, commit by advancing a cursor, and each consumer tracks its own sequence. Per the paper, with a single producer no locks or compare-and-swap are needed, only memory barriers. Slow consumers can batch to catch up. Fowler's article gives the sizes: 20 million slots for the input buffer and 4 million for each output buffer.

Mechanical sympathy

Fowler credits Martin Thompson with the phrase "mechanical sympathy": designing with knowledge of how the hardware behaves. Examples in the article include padding sequence counters so they sit on separate cache lines, writing cache-friendly collections with primitive keys, and managing garbage collection by avoiding objects that survive long enough to be promoted and then die. The Disruptor paper makes the cache-line point directly: caches work on lines (the paper says most commonly 64 bytes), and two variables on the same line written by different threads cause contention it calls false sharing. If that is unfamiliar, systems chapter 2 covers cache lines and locality.

Analogy: one clerk with a very good notebook

Picture a shop where every transaction goes through one clerk. Before the clerk looks at a slip, a runner stamps it with a number and copies it to a ledger in the back room. The clerk is never interrupted, never waits for anyone to hand over a pen, and works from memory. If the clerk faints, a new one reads the ledger from the top and ends up with the same shop.

Where it breaks down: the clerk's memory must hold everything. Fowler's article says state is kept in memory, and its guidance on suitability is that the approach fits some domains (connected ones where a transaction can affect later ones) and not others.

What the sources claim about speed

The numbers below are the authors' own, from specific hardware and software, and I have not reproduced or independently verified them.

  • The headline. Fowler writes of "a thread that will process 6 million orders per second using commodity hardware." A footnote gives the benchmark machine as a 3 GHz dual-socket quad-core Nehalem-based Dell server with 32 GB of RAM.
  • How they got there. The article says plain sequential in-memory code reached about 10K transactions per second, well-factored code with small methods reached the 100K range, and the rest came from cache-friendly collections and performance testing.
  • Disruptor latency. The paper's three-stage pipeline test reports mean latency per hop of 52 ns for the Disruptor against 32,757 ns for ArrayBlockingQueue, and a 99.99th percentile of 8,192 ns against 4,194,304 ns. Its overview says the authors have seen over 25 million messages per second and latencies below 50 ns on moderate-clock processors.
  • Disruptor throughput. In the paper's unicast one-producer, one-consumer tables, results on one test machine were 25,998,336 operations per second for the Disruptor against 5,339,256 for ArrayBlockingQueue. The paper itself cautions that results can vary substantially.

These are microbenchmarks and a design article, not a promise about your workload.

Trade-offs and lessons

What you gain

No locks, no database on the hot path, simple sequential logic that is easy to test, and a journal of events. The article says that copying recorded events into a development environment and replaying them helps diagnose unexpected behaviour.

What you give up

No rollback. The article notes there is no automatic rollback, so input must be fully validated before any state is changed. All state must fit in memory. Anything slow, such as a call to another service, cannot run inside the processor and must be split into events.

Operational cost

This is specialist work: mechanical-sympathy tuning, custom collections, GC management and test harnesses. The article stresses performance testing, including against null components.

Fit

Fowler suggests the approach suits connected domains and backend systems, and says that "as long as you need less than a few million TPS, you'll have enough performance headroom". Most systems do not need to start here.

Common misconception: "single-threaded means slow"

The whole system is not single-threaded; the Disruptor stages around the core run concurrently, as the article says (concurrent Disruptor components surround it). Only the business logic is serial. And a serial core is the thing that makes the rest simple.

What this page does not claim

It does not say that you should replace your database with a single thread. General industry pattern, not from the sources: the same ingredients (an ordered log, deterministic state machines and replay) appear in many replicated systems, and ordinary applications get most of the benefit with a transactional database and an outbox.

Try it yourself

Journal first, then process, then replay

This is a toy of my own, not LMAX code. It writes each event to a journal file with fsync before applying it, shows a deterministic single-threaded processor, then "crashes" and rebuilds the state from the journal alone. It uses a temporary directory and removes it at the end.

import json, os, tempfile
class Processor:                 # the "business logic processor": one thread, memory only
    def __init__(self): self.balance = {}
    def apply(self, ev):         # deterministic: same events, same state
        a, n = ev["acct"], ev["amt"]
        if ev["type"] == "deposit": self.balance[a] = self.balance.get(a, 0) + n
        elif ev["type"] == "withdraw" and self.balance.get(a, 0) >= n: self.balance[a] -= n
        else: return f"rejected {ev}"
        return "ok"
events = [dict(type="deposit", acct="A", amt=100), dict(type="withdraw", acct="A", amt=30),
          dict(type="withdraw", acct="A", amt=500), dict(type="deposit", acct="B", amt=7)]
path = os.path.join(tempfile.mkdtemp(), "journal.log")
live = Processor()
with open(path, "a") as j:       # journal FIRST (sequential append), then process
    for ev in events:
        j.write(json.dumps(ev) + "\n"); j.flush(); os.fsync(j.fileno())
        print(live.apply(ev))
print("live state:    ", live.balance)
replayed = Processor()           # crash! rebuild from the journal alone
for line in open(path): replayed.apply(json.loads(line))
print("replayed state:", replayed.balance, "| identical:", replayed.balance == live.balance)
os.remove(path); os.rmdir(os.path.dirname(path))

Output when run:

ok
ok
rejected {'type': 'withdraw', 'acct': 'A', 'amt': 500}
ok
live state:     {'A': 70, 'B': 7}
replayed state: {'A': 70, 'B': 7} | identical: True

Notice that the rejected withdrawal is journaled too: the log records what was asked, and the deterministic logic decides again on replay. Try adding import random and a random fee inside apply; the replayed state will no longer match. That is why determinism, and the ban on external calls inside the processor, is a hard rule.

Distributed systems connection

This is state-machine replication in a practical form: several processors apply the same ordered inputs and so reach the same state. The ordering is supplied by the leader's replicator, so the hard part, agreeing on order, is centralised, with failover to another processor if the leader fails. General pattern: consensus protocols such as Raft exist to agree on that order when the leader itself can fail unpredictably (networking chapter 20). The journal-before-process rule is also the write-ahead log you met in the database courses, with the business logic as the "database".

Key takeaways

  • LMAX's business logic runs on one thread, in memory, with no database; every input event is journaled and replicated before the logic processes it.
  • State is recoverable by replaying events, with nightly snapshots to keep replay short; Fowler reports a full restart in under a minute.
  • The Disruptor is a ring buffer coordinated by sequence numbers instead of locks, designed around cache behaviour (mechanical sympathy).
  • Fowler reports one thread handling 6 million orders per second on commodity hardware; the Disruptor paper reports its own microbenchmarks. Treat both as the authors' claims.
  • The price: a deterministic core, no rollback, state that fits in memory, and no slow calls on the hot path.

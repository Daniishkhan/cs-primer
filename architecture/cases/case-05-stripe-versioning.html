Stripe's API Versioning

Stripe's engineers wrote in 2017 that they had kept every version of their API compatible since the company began in 2011. Their API still changes all the time. This case study looks at how: each account is pinned to a dated version, the core code only ever speaks the newest one, and a chain of small modules rewrites each response backwards to whatever shape an old client expects.

The pattern in one sentence

Keep one implementation and many contracts: pin every client to a dated API version, let the core produce only the latest shape, and translate responses backwards through small, isolated change modules so that old integrations keep working without old code paths spreading through the system.

The cast

The problem is the one from chapter 10: a published API is a promise, and Hyrum's law says someone depends on whatever you ship. The terms below are from Stripe's own 2017 post by Brandur Leach.

Date-based version
Stripe names each version by its release date, for example 2017-05-24. The post calls this a "rolling" scheme and says each version carries a small set of backward-incompatible changes. It contrasts this with major versions such as v1 and v2, which it rejects because upgrades become nearly as painful as re-integrating.
Pinned version
An account is pinned automatically to the newest version at its first API request, so it does not receive breaking changes by accident. The post says a single request can override this with the Stripe-Version header, and that the pinned version can be changed from the dashboard.
API resource
Each possible response is a class, written to match the current version of the API.
Version change module
One module per breaking change. Each holds a description, a transformation, and the resource types it affects.
The master list
A list that maps each version date to the change modules that were introduced with it.
The client
Someone else's integration, written against whatever version was current on the day they started.

The problem: breaking changes are inevitable

The post starts from an uncomfortable fact: some changes cannot be made additively. Renaming or retyping a field breaks client code. Its example is replacing a verified boolean with a status field, which the post says Stripe did back in 2014. Adding a new endpoint or a new field is safe, but not every improvement can be expressed that way.

The usual answer is a major version in the URL, /v1/ to /v2/. The post's objection is that a major bump makes upgrading almost as painful as re-integrating, so some users never upgrade, and the provider must either cut them off or maintain old code indefinitely. (This is the trade-off that chapter 10 discusses under versioning strategies.) Stripe chose small, dated steps instead. The post reports that its approach had been sufficient for "almost a hundred backwards-incompatible upgrades over the past six years" and says that Stripe had "maintained compatibility with every version of our API since the company's inception in 2011."

Step through

One request, one core, many contracts

  1. The request arrives. Stripe works out the target version. The post lists three sources: a Stripe-Version header, the version of an authorised OAuth application when the request is made on the user's behalf, and the user's pinned version. A header overrides the pin for a single request.
  2. The core does its job. It builds the response as the current version of the API defines it. Version logic is deliberately absent here.
  3. Newest change first. The post says the system walks backwards from the current version towards the target, applying each module in between.
  4. Then the next one. Each module assumes the data looks as it did when the module was written, so it only has to understand one step of history.
  5. The old shape goes out. The client receives the format it was built against, even though no code in the core still produces that format.

The pattern explained

Many contracts, one implementation

From the client's point of view there are a hundred versions of the API. From the server's point of view there is one, plus a stack of translators. The post says version change modules "keep older API versions abstracted out of core code paths." The translators are a form of the gateway for translation idea from chapter 10, applied inside a single service rather than between two.

Versioning as a first-class concept

Stripe's post says it wanted upgrades to be lightweight, first-class and fixed-cost. "First-class" has concrete consequences in the post. The public API changelog is generated programmatically from the change modules, and the API reference detects the logged-in user's pinned version and warns about breaking changes since that version. Because every breaking change must be written as a module with a description, the documentation cannot drift from the code.

Rolling dates instead of big releases

Small changes make a user's upgrade a small decision. The post also describes a review process: proposed API changes are written up in a brief supporting document and submitted to a mailing list, which gives each change broader visibility across the company. The best breaking change is the one that never ships.

Analogy: the translator at the border

Imagine a customs office where everyone speaks the office's current language. Visitors arrive with a passport that says when they first came, and a chain of interpreters turns today's reply into the dialect of that year, one era at a time. The office never has to learn old dialects; the interpreters do, and each knows only the difference between two adjacent eras.

Where it breaks down: an interpreter only changes words. If a past change altered what the office does and not merely what it says, no interpreter can undo it. The post addresses exactly this case.

Trade-offs and lessons

Side effects do not translate

Some changes cannot be expressed as response rewrites. The post says these get a has_side_effects annotation, the transformation becomes a no-op, and other code checks whether the version change is active. It says this makes them harder to maintain, so they are avoided where possible.

Every version has a cost

The post says each supported version adds code to understand and maintain, and that changes which cannot be encapsulated scatter version checks through the codebase, "slower, less readable, and more brittle" in its words.

Progress pays the bill

Keeping old versions forever is expensive, and the post says the price is slower progress on new features. It also says Stripe expects to retire older versions eventually, so that users get new features and the codebase stays simpler.

Compatibility is a product feature

The post treats compatibility as a deliberate investment. The three goals (lightweight, first-class, fixed-cost) are a design brief, not a slogan, and the module structure is what makes the third one possible.

Common misconception: "versioning means branching the code"

Not here. The core stays on one version. What branches is a list of small, tested transformations. If you version by copying handlers (v1/orders.py, v2/orders.py) you get the maintenance bill Stripe was trying to avoid.

What changed since 2017 (from Stripe's current docs)

Stripe's versioning reference today says that starting with the 2024-09-30.acacia release it follows a newer release process: new API versions monthly with no breaking changes, and twice a year a new major release that starts with an API version containing breaking changes. It also says requests use the account's default API version, controlled in the Dashboard's Workbench, unless the Stripe-Version header overrides it, and that recent official client libraries align requests with the API version that was current when the library was released. This page does not describe the internals of that newer process, because the sources read here do not. The pinned-account and header ideas, though, are still in the docs.

A side note: idempotency keys

Stripe's docs have a related contract mechanism, covered in chapter 9 and built in Lab 2. The idempotency page says that a client can send an idempotency key when creating or updating an object, so that after a connection error it can repeat the request "without risk of creating a second object or performing the update twice." For API v1 it says Stripe saves the status code and body of the first request made with a key and returns that saved response for retries, and that keys can be removed automatically after they are at least 24 hours old. Keys can be up to 255 characters, and the docs suggest V4 UUIDs or another random string with enough entropy. Versioning protects clients across time; idempotency protects them across retries.

Try it yourself

Build a version-change chain in 25 lines

This script is a sketch of the pattern, not Stripe's code. It is safe to run: it only prints. The core always returns the newest shape. Each change module undoes one change, and the loop applies only the modules newer than the target version. ISO dates compare correctly as strings.

# Version change modules: the core only knows the latest shape.
class Change:
    def __init__(self, date, desc, down):
        self.date, self.desc, self.down = date, desc, down

# Newest first. Each `down` turns the NEWER shape into the shape one version earlier.
CHANGES = [
    Change("2024-03-01", "amount became amount_minor",
           lambda r: {**{k: v for k, v in r.items() if k != "amount_minor"}, "amount": r["amount_minor"]}),
    Change("2023-06-15", "boolean paid replaced by status",
           lambda r: {**{k: v for k, v in r.items() if k != "status"}, "paid": r["status"] == "succeeded"}),
]

def core(account_version):                      # the core never looks at the version
    return {"id": "ch_1", "amount_minor": 500, "status": "succeeded"}

def respond(pinned, override=None):
    target = override or pinned                 # header beats the pinned account version
    resp = core(target)
    for ch in CHANGES:                          # walk back from latest to target
        if ch.date > target:
            resp = ch.down(resp)
    return resp

for who, pin, hdr in [("new account", "2024-03-01", None),
                      ("mid account", "2023-09-01", None),
                      ("old account", "2022-01-01", None),
                      ("old + header", "2022-01-01", "2024-03-01")]:
    print(f"{who:13} {respond(pin, hdr)}")

Output when run:

new account   {'id': 'ch_1', 'amount_minor': 500, 'status': 'succeeded'}
mid account   {'id': 'ch_1', 'status': 'succeeded', 'amount': 500}
old account   {'id': 'ch_1', 'amount': 500, 'paid': True}
old + header  {'id': 'ch_1', 'amount_minor': 500, 'status': 'succeeded'}

Notice that the old and new accounts hit exactly the same core. Try adding a third change that renames id; only one new module is needed and no handler changes. Then try a change that alters behaviour, such as rounding amounts differently, and notice that there is no response rewrite that undoes it. That is the side-effect problem from the post.

For a read-only look at the real thing, open Stripe's public API changelog and API upgrades pages in a browser and compare a few entries: every change there corresponds to a module-shaped unit of work.

Distributed systems connection

In a distributed system you cannot upgrade every client and server at once, so producers and consumers are always on different versions. Stripe's design shifts the burden of that mismatch to a single place, the translation layer, and decouples client upgrade timing from server release timing. General pattern, not from the post: the same trade-off appears wherever data crosses time or process boundaries, such as schema evolution in message formats (chapter 10) and replay of stored events (chapter 16). Pinning a version is a client-side pointer into the history of a contract.

Key takeaways

  • Stripe names versions by date, pins each account to the version current at its first request, and lets a request override the pin with the Stripe-Version header.
  • The core produces only the latest shape; version change modules rewrite responses backwards, newest first, down to the target version.
  • Treating versioning as first-class lets documentation and the changelog be generated from the same modules.
  • The costs are real: each version adds code to maintain, side-effect changes do not fit the module pattern, and old versions slow new work.
  • Fewer breaking changes is the best strategy; Stripe pairs the machinery with a review process for outgoing API changes.

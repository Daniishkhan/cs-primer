Knight Capital: 45 Minutes, $460 Million

On 1 August 2012 a trading firm's order router, handling 212 small retail orders, sent millions of orders into the market in about 45 minutes and lost over $460 million. The SEC's order traces it to a deployment that missed one of eight servers, a flag that had been given a new meaning, and old code that nobody had removed. It is the clearest real-world argument for the habits in the chapters on safe change.

The pattern in one sentence

Code you no longer use is still code you run: if dead functionality stays callable, a flag is reused for a new purpose, and a deployment is not verified on every server, then one missed copy can bring the old behaviour back at machine speed with no one and nothing positioned to stop it.

The cast

Everything in this section and the next is from the U.S. Securities and Exchange Commission's order of 16 October 2013 (Release No. 34-70694) against Knight Capital Americas LLC. Knight settled without admitting or denying the findings, so what follows is "what the SEC found", not a court judgment. Chapters 18 and 19 cover the practices this story is about.

Knight
A U.S. broker-dealer. The order says Knight's trading generally represented approximately ten percent of all trading in listed U.S. equity securities in 2011 and 2012.
SMARS
Knight's automated, high-speed, algorithmic order router. It receives "parent" orders from other parts of the trading platform and, depending on available liquidity, sends one or more "child" orders to external venues.
RLP
The NYSE's Retail Liquidity Program, due to start on 1 August 2012. Knight changed its code, including SMARS, to let its customers take part.
Power Peg
Old SMARS functionality that Knight had stopped using in 2003. It was still present and callable in 2012.
The flag
A setting formerly used to switch Power Peg on. The new RLP code repurposed it: when set to "yes", the new RLP functionality was meant to run instead.
The eight servers
SMARS ran on eight servers.

What happened, step by step

The new RLP code was meant to replace unused code in the router. The order says Knight intended to delete the Power Peg code, so that the flag would engage RLP instead. In 2005, Knight had moved the function that counted how many shares of a parent order had been executed, and the order says it did not retest the Power Peg code after the move to see whether it would still work if called.

Step through

From a missed copy to millions of orders

  1. The old code lingers. Power Peg had been unused since 2003 but was still present and callable on the SMARS servers.
  2. A staged deployment goes wrong. Beginning 27 July 2012, Knight deployed the RLP code in stages, a few servers on successive days. A technician did not copy the new code to one of the eight servers. There was no second-technician review, and the order says Knight "had no written procedures that required such a review."
  3. The flag arrives. On 1 August Knight received orders from broker-dealers whose customers were eligible for the RLP. The seven updated servers processed them correctly.
  4. The old code runs. Orders with the repurposed flag sent to the eighth server triggered the Power Peg code. Because the cumulative-quantity function had been moved, it sent child orders continuously, in rapid sequence, without regard to executions already received. Although one part of the system recognised the parent orders were filled, this was not communicated to SMARS.
  5. The fix makes it worse. While staff tried to find the problem, Knight uninstalled the new RLP code from the seven correct servers. The order says this worsened the problem, because incoming parent orders then activated Power Peg there too.

The numbers, exactly as the SEC states them

For the 212 incoming parent orders handled by the defective code, SMARS sent millions of child orders, resulting in 4 million executions in 154 stocks, for more than 397 million shares, in approximately 45 minutes. Knight inadvertently assumed a net long position of approximately $3.5 billion in 80 stocks and a net short position of approximately $3.15 billion in 74 stocks. It realised a loss of more than $460 million. The order also found that Knight's executions made up more than 20 percent of volume in 75 stocks and contributed to price moves of more than five percent, and in 37 stocks the price moved more than ten percent. The penalty was $12 million, and Knight had to retain an independent consultant.

What the SEC found about controls

The SEC's case was that Knight violated Rule 15c3-5, which requires brokers with market access to have risk controls reasonably designed to manage the risks of that access. These specific findings are the technical heart of the case:

  • Deployment. Knight did not have written code development and deployment procedures for SMARS (although other groups at Knight had written procedures) and did not require a second technician to review a deployment. It had no written protocol for accessing unused code on production servers, such as testing it afterwards to make sure it still worked.
  • Output monitoring. Knight did not have sufficient controls to monitor SMARS output, such as comparing orders leaving SMARS with those that entered it. It also had no procedures to halt SMARS in response to its own aberrant activity.
  • Capital limits. Knight had no pre-set, firm-wide capital thresholds linked to automated controls that would block order entry. Its main monitoring tool, PMON, was a post-execution position monitor that relied entirely on human monitoring and did not generate automated alerts about financial exposure.
  • Alerts that were not alerts. The automated "BNET reject" emails, 97 of them before the 9:30 a.m. open, referenced SMARS and a "Power Peg disabled" error. The order says Knight "did not design these types of messages to be system alerts, and Knight personnel generally did not review them." They were not acted on before the open or used to diagnose the problem afterwards.
  • Incident response. Knight had no supervisory procedures to guide staff when significant issues developed, and relied primarily on its technology team to diagnose the problem in a live trading environment.

General lessons (not findings)

The five items below are widely taught engineering practice. They are my reading of the story, not statements by the SEC, which makes only the findings above.

Delete dead code

Unused code is a liability that sits quietly. In this story it stayed callable for years, after a change nobody retested. Removing it, and not merely planning to, takes it out of the reachable states.

Never repurpose a flag

A flag whose name or meaning is reused is a message with two readers. Give a new behaviour a new flag; retire the old one so that an old build ignores it. See the flag discussion in chapter 18.

Verify the deployment

A release is done when you have checked what is running on every machine, not when the copy script finished. Automate the check and make a mismatch block the release.

Give the system a kill switch

Where a mistake multiplies at machine speed, put an automatic brake on the output (for example a ratio of orders out to orders in) and a human-operable stop that works when the system is misbehaving.

Alert on purpose

An email nobody was meant to read is not monitoring. Real alerts have an owner, a threshold and a page that wakes someone. Many teams also rehearse their rollback, because "revert to the old version" can itself be dangerous, as the uninstall step showed.

What this page does not claim

It does not say one technician caused the loss. The order lists missing review, missing procedures and missing automated controls, and its legal conclusion is about Knight's controls. General industry pattern, not from the order: serious failures usually have several contributing weaknesses, and the one that is visible first (a missed copy) is rarely the only one. Decisions about changes and their documentation, as covered in chapter 19, are part of the same safety net.

Try it yourself

Two cheap controls in thirty lines

This script is a toy of my own, not Knight's code. It models eight servers with a mismatched build, shows the verify-the-deployment check catching it, and shows a simple out-to-in ratio check halting a runaway producer. The numbers are invented. It is safe: it only prints.

SERVERS = 8
deployed = [True] * 7 + [False]        # one server never got the new code
def handle(server_new_code, flag):
    if not flag: return "normal"
    return "RLP" if server_new_code else "OLD Power Peg (dead code revived)"
print("per-server behaviour when the repurposed flag is on:")
for i, new in enumerate(deployed, 1):
    print(f"  server {i}: {handle(new, True)}")

# Control 1: deployment verification (compare what is running to what was intended)
want = "build-B"; running = ["build-B"] * 7 + ["build-A"]
bad = [i + 1 for i, b in enumerate(running) if b != want]
print("verify step would block release; mismatched servers:", bad)

# Control 2: kill switch comparing orders out to orders in
orders_in, orders_out, limit = 0, 0, 50
for tick in range(1, 6):
    orders_in += 4; orders_out += 4 * 25 * tick     # runaway fan-out
    if orders_out > limit * max(orders_in, 1):
        print(f"tick {tick}: out/in = {orders_out}/{orders_in} > {limit}x -> HALT"); break
    print(f"tick {tick}: out/in = {orders_out}/{orders_in} ok")

Output when run:

per-server behaviour when the repurposed flag is on:
  server 1: RLP
  server 2: RLP
  server 3: RLP
  server 4: RLP
  server 5: RLP
  server 6: RLP
  server 7: RLP
  server 8: OLD Power Peg (dead code revived)
verify step would block release; mismatched servers: [8]
tick 1: out/in = 100/4 ok
tick 2: out/in = 300/8 ok
tick 3: out/in = 600/12 ok
tick 4: out/in = 1000/16 > 50x -> HALT

Change the limit to 500 and see how many ticks pass before the brake fires; then ask what a sensible limit would be for your own system, and what happens to a legitimate burst. A brake that trips too often gets disabled, which is its own failure. For a read-only exercise on your own repository, search for flags that appear in code but never in configuration (or the reverse): those are the candidates for deletion.

Distributed systems connection

Eight servers meant eight chances for the fleet to disagree with itself. In a distributed system "the deployed version" is a property of the whole set, not any one machine, and a rollout is a state machine you have to verify. The partial-failure lesson also applies to mixed fleets: for a while, old and new code run together, so flags and messages must be understood by both (chapter 10 on compatibility, chapter 18 on rollouts). General pattern: amplification loops with no feedback, where a fast producer ignores the state the consumer already knows, are why back-pressure and circuit breakers exist (chapter 17). The order itself notes that one part of Knight's system knew the parent orders were filled, but SMARS did not.

Key takeaways

  • The SEC found that new RLP code was not copied to one of eight SMARS servers, and that a repurposed flag then activated Power Peg code that had been unused since 2003.
  • Its figures: 212 parent orders, 4 million executions in 154 stocks, more than 397 million shares, about 45 minutes, a loss of over $460 million.
  • Missing controls, not only the bug: no second review of deployment, no comparison of orders out with orders in, no automatic halt, and no alerts designed to be read.
  • The rollback of the new code from the seven good servers made things worse; changes made under pressure need a plan.
  • General lessons: delete dead code, do not reuse flags, verify what is running, build kill switches, and make alerts real.

Toolbox

Architecture is mostly invisible: boxes in someone's head, rules in a wiki nobody reads. These tools make it visible and checkable. You will draw a design as text, write an API contract, catch a forbidden import, test with fakes and push traffic at your own server. Each has a ten-minute exercise tied to a chapter.

How to use this page

Jump to a tool when a chapter mentions it. Everything here runs on macOS and Linux (and on Windows under WSL). Python code uses only the standard library unless a card says otherwise. Example output is realistic but yours will differ. Where a card says illustrative, the numbers are invented to show the shape of the output, and your machine will print different ones.

Nothing on this page changes your real projects. The exercises use throwaway folders, and the load-testing card points only at a server running on your own machine.

Draw it

A diagram that lives in a drawing tool goes stale. A diagram that lives in the repository, as text, gets reviewed with the code.

Mermaid

Nothing to install: paste text into the Mermaid Live Editor at mermaid.live · Command line: npm install -g @mermaid-js/mermaid-cli (gives you mmdc; needs Node.js) or run it once with npx -p @mermaid-js/mermaid-cli mmdc -h · In Markdown: GitHub renders ```mermaid blocks in Markdown files, issues and pull requests

Mermaid turns a few lines of text into a flowchart, a sequence diagram and many other kinds of diagram. The text can be diffed, reviewed and versioned like code, which is why it suits architecture: the picture changes in the same pull request as the design. Use a flowchart for "what talks to what" (the context and container views Simon Brown's C4 model teaches in chapter 19) and a sequence diagram for "what happens, in what order" (chapter 15). Mermaid also has an experimental C4 syntax, but a plain flowchart is more portable between renderers.

10-minute guided exercise

Open mermaid.live in a browser. Paste this into the left pane. It is a C4-style container view of a small shop: a person, the system's containers grouped in a boundary, and an external service.

flowchart LR
    customer(["Customer<br/>[person]"])
    subgraph shop ["Shop system"]
        web["Web app<br/>[container]"]
        orders["Orders service<br/>[container]"]
        payments["Payments service<br/>[container]"]
        odb[("Orders DB<br/>[database]")]
        bus{{"Event bus"}}
    end
    psp["Card processor<br/>[external system]"]

    customer -->|"HTTPS"| web
    web -->|"POST /orders"| orders
    orders --> odb
    orders -->|"charge"| payments
    payments -->|"HTTPS"| psp
    orders -.->|"OrderPlaced"| bus

The diagram redraws as you type. Then change the second diagram: the order of a checkout saga (a business transaction made of local steps, each with an undo step; see chapter 15):

sequenceDiagram
    autonumber
    participant C as Customer
    participant O as Orders
    participant P as Payments
    participant I as Inventory

    C->>O: place order (Idempotency-Key: k1)
    O->>I: reserve stock
    I-->>O: reserved
    O->>P: charge card
    alt card accepted
        P-->>O: charged
        O-->>C: 201 Created
    else card declined
        P-->>O: declined
        O->>I: release stock (compensation)
        I-->>O: released
        O-->>C: 402, problem+json
    end

Now make it a file in your repository. Create README.md and put the same text between ```mermaid and ``` fences. Pushed to GitHub, it renders as a diagram in the page. To produce an image from the command line instead:

$ npm install -g @mermaid-js/mermaid-cli  # once; downloads a headless browser, so it is a big install
$ mmdc -i checkout-saga.mmd -o checkout-saga.svg  # -i input, -o output; the extension picks svg or png

Finish by deleting the alt block and keeping only the happy path. Then add a fifth participant, a Notifier that listens to the event bus. Notice how cheap each edit is.

What to look for

  • The flowchart shows boundaries and dependencies, not behaviour. A good test: could a new teammate say who owns each box and what each arrow means? Every arrow should have a label (chapter 19).
  • The dotted arrow to the event bus is an asynchronous relationship, while the solid ones are calls that wait for an answer. Mixed styles on one picture show where temporal coupling lives (chapter 13).
  • The sequence diagram makes the compensation path visible: a declined card must release the stock that was reserved earlier (chapter 15). A saga that only has a happy path in its diagram usually has no undo in its code either.
  • The key in the first message ties the diagram to the API contract from chapter 9.
  • Compare the drawing of the whole system with the vocabulary of chapter 0: could you explain it to someone outside the team in one minute?

Common pitfalls

  • Diagrams of everything are diagrams of nothing. Aim for one idea per picture and at most about a dozen boxes.
  • Auto-layout decides the arrangement. You cannot place boxes exactly, so don't fight it; split the diagram or change the direction (LR versus TD).
  • Renderers differ in version. GitHub, mermaid.live and mmdc each bundle their own Mermaid version, so a newer feature may work in one and fail in another. Stick to flowcharts and sequence diagrams for anything that must render everywhere.
  • Special characters in labels (brackets, parentheses, quotes) can break parsing. Wrap labels in double quotes, as above.
  • mmdc drives a headless browser, so on some Linux machines and containers you need extra setup. Its documentation links to the known issues; if that is a bother, use the live editor.
  • A diagram is a claim. If the code changes and the picture does not, the picture is now a lie.

Specify it

An API is a promise to people you may never meet. A machine-readable description is the promise written down in a form that tools can check.

OpenAPI

Nothing to install: paste YAML into the Swagger Editor in a browser (editor.swagger.io) · Also: Redocly's tools can render and lint a file · Format: a YAML or JSON file, conventionally openapi.yaml

OpenAPI is a standard way to describe an HTTP API: its paths, methods, parameters, request and response bodies and error shapes. The description is a contract you can read, review and diff, and tools can generate documentation, client code and automated checks from it. It is where the ideas of chapter 9 (resources, errors, idempotency keys) turn into something precise, and it is the baseline you compare against when you change an API (chapter 10).

10-minute guided exercise

Save this as openapi.yaml. It describes one operation from Lab 2: POST /v1/orders with an Idempotency-Key header and an error that uses application/problem+json (the error format of RFC 9457).

openapi: 3.1.0
info:
  title: Orders API
  version: 1.0.0
paths:
  /v1/orders:
    post:
      summary: Place an order
      parameters:
        - name: Idempotency-Key
          in: header
          required: false
          description: Retrying with the same key returns the first answer and creates no second order.
          schema:
            type: string
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/NewOrder"
      responses:
        "201":
          description: Order created
          headers:
            Location:
              schema:
                type: string
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Order"
        "422":
          description: The request was well-formed JSON but invalid
          content:
            application/problem+json:
              schema:
                $ref: "#/components/schemas/Problem"
components:
  schemas:
    NewOrder:
      type: object
      required: [customer, items]
      properties:
        customer: { type: string }
        items:
          type: array
          minItems: 1
          items:
            type: object
            required: [sku, qty, unit_price_cents]
            properties:
              sku: { type: string }
              qty: { type: integer, minimum: 1 }
              unit_price_cents: { type: integer, minimum: 0 }
    Order:
      type: object
      required: [id, status]
      properties:
        id: { type: integer }
        status: { type: string }
    Problem:
      type: object
      required: [type, title, status]
      properties:
        type: { type: string }
        title: { type: string }
        status: { type: integer }
        detail: { type: string }

Open the Swagger Editor in a browser, replace the sample text with this file, and look at the rendered documentation on the right. You should see one POST operation, the header parameter, two responses, and an example body generated from the schema. Then try these edits and watch what changes:

  1. Mark the header required: true. That is a breaking change for every existing client: requests that worked yesterday are now invalid.
  2. Add an optional field, currency, to NewOrder without listing it in required. That one is compatible.
  3. Add a "409" response for "key reused with a different body". Decide whether Lab 2's 422 or a 409 is the right status, and write your reasoning in a comment.

The editor validates as you type. If it reports an error on openapi: 3.1.0, you may be using an older editor build that stops at OpenAPI 3.0. In that case, try Swagger's newer editor (editor-next.swagger.io) or another tool from the OpenAPI tools list at openapis.org, or change the first line to openapi: 3.0.3; this file uses nothing that is specific to 3.1.

What to look for

  • Everything a client needs is in one place: URL, method, headers, body shape, status codes. If you cannot describe an operation in this file, ask whether the API is too clever (chapter 9).
  • The error is part of the contract. A problem+json response is listed next to the success response, with the same care. In the spec it is simply a media type used as a key under content.
  • Breaking versus compatible edits, as in the exercise: new optional things are safe, new required things and removed things are not (chapter 10).
  • Hyrum's law still applies: clients depend on behaviour the file does not describe, such as field order or exact error text. The file is necessary for a stable API, not sufficient (chapter 10).
  • Reusable pieces under components, referenced with $ref, are the API-level version of avoiding duplicated knowledge (chapter 2).

Common pitfalls

  • The file can drift from the code. A description nobody checks is documentation that lies. Either generate the file from the code, generate checks from the file, or compare real responses against it in a test.
  • Version mismatches between tools. OpenAPI 3.0 and 3.1 differ (for example in how a schema says "may be null"), and not every tool supports 3.1 yet. Check what your tools accept.
  • A schema describes shape, not meaning. It cannot say "the key must be unique per customer" or "the second request returns the first answer"; put that in the description and in tests.
  • Indentation is syntax in YAML. Most "mysterious" errors are a misplaced space. Use spaces, never tabs.
  • Don't paste real secrets or customer data into an online editor.

Architecture decision records (adr-tools)

macOS: brew install adr-tools · Ubuntu/Debian: sudo apt install adr-tools (Ubuntu 24.04 and later; otherwise clone it from GitHub, npryce/adr-tools) · Windows: inside WSL · No tool at all: numbered Markdown files by hand, described below

An architecture decision record (ADR) is a short document that captures one decision: the context, what was decided and what follows from it. Michael Nygard proposed the format in 2011. Code tells you what the system does; an ADR tells the next engineer why, including the options you rejected, which is what they will otherwise rediscover the hard way (chapter 19). adr-tools is a set of shell scripts that create and number these files for you.

10-minute guided exercise

Do this in a throwaway git-free folder. adr new opens your editor, taken from the VISUAL or EDITOR environment variable, so set one first (for example export EDITOR=nano).

$ mkdir adr-demo && cd adr-demo
$ adr init doc/architecture/decisions  # the default folder is doc/adr; this chooses another
doc/architecture/decisions/0001-record-architecture-decisions.md
$ adr new Use a modular monolith for the shop  # creates the next numbered file and opens it
doc/architecture/decisions/0002-use-a-modular-monolith-for-the-shop.md
$ adr new -s 2 Split payments into its own service  # -s 2: this record supersedes record 2
doc/architecture/decisions/0003-split-payments-into-its-own-service.md
$ ls doc/architecture/decisions

Fill in the second record in your editor. The generated template has headings along the lines of Title, Date, Status, Context, Decision and Consequences. A realistic body for record 2 looks like this:

# 2. Use a modular monolith for the shop

Date: 2026-10-12

## Status

Accepted

## Context

Four engineers, one deployable, no proven need to scale parts independently.
Module boundaries are still moving as we learn the domain.

## Decision

One deployable with enforced module boundaries (checked by import-linter in CI).

## Consequences

Simple deploys and in-process calls. A slow module can still slow the rest.
We will revisit when two teams need to release independently.

When you run adr new -s 2 ..., the tool marks record 2 as superseded by record 3, and the new record 3 refers back to it. Open both files and read their Status sections. The old record is kept, not deleted: history is the point.

The plain-Markdown alternative. The tool is a convenience, not a requirement. Create a folder docs/decisions/ and write files named 0001-short-title.md using the same headings. To supersede one, edit its Status line to say "Superseded by 0003" and start the new file with "Supersedes 0002". Review them in pull requests like code. A team that writes ADRs by hand beats a team that installed a tool and never used it.

What to look for

  • Numbers and short titles make the log a story you can read in order. The first record, created by adr init, is itself a decision: "we will record our decisions" (chapter 19).
  • The Context section is the valuable part. It records the forces at the time: team size, deadlines, what was known. A reader years later can then tell whether those forces still hold.
  • Consequences must include the downsides you accepted. An ADR with only good news is a sales pitch (chapter 11 is full of trade-offs worth recording).
  • Supersession keeps the trail: records are append-only, so you can see that you once chose a monolith and why you later changed your mind. This is how ADRs relate to the evolving-systems ideas of chapter 18.

Common pitfalls

  • Writing one ADR per decision of any size. Record the ones that are costly to reverse or that people will ask about. "Which linter" is rarely worth one.
  • Editing the history. Don't rewrite an accepted ADR to match what happened later; write a new one that supersedes it.
  • Writing them after the fact, from memory, turns them into justifications. Write while the options are still open, even as a draft.
  • The editor. If adr new seems to hang or fails, check that EDITOR or VISUAL is set to a program that exists.
  • Hiding them. Records in a wiki that nobody opens help no one. Keep them in the repository, next to the code they explain.

Guard it

A rule that nobody enforces is a suggestion. The cheapest enforcement is a script that fails when the rule is broken.

Import graphs & boundary checkers

Python ast script: standard library, nothing to install · import-linter: pip install import-linter (adds the lint-imports command; use a virtual environment) · Optional: pydeps draws import graphs, but it is not covered here

A module's imports are its dependencies, written down. Reading them with a program gives you the real dependency graph of your code, not the one on the whiteboard. A boundary checker then turns an architecture rule ("the domain must not import the database adapter") into a test. This is the dependency rule of chapter 5 and the coupling from chapter 2, enforced by machine. It is the tool that keeps a modular monolith modular (chapter 11).

10-minute guided exercise

First build a toy package with a deliberate mistake. Make a folder toy/ and inside it a package shop/ with three sub-packages. Each folder needs an empty __init__.py.

from shop.adapters.sqlite_repo import SqliteRepo  # the sneaky import


class Order:
    def __init__(self, order_id: int, total_cents: int):
        self.order_id = order_id
        self.total_cents = total_cents

    def save(self) -> None:
        SqliteRepo().add(self)
def total(items: list[tuple[int, int]]) -> int:
    return sum(qty * cents for qty, cents in items)
from shop.domain import pricing


class SqliteRepo:
    def add(self, order) -> None:
        print("saved", order.order_id, pricing.total([(1, order.total_cents)]))
from shop.domain.order import Order
from shop.adapters import sqlite_repo


def checkout() -> None:
    Order(1, 3000).save()

Now the graph script. It parses every file with ast (it never runs your code), collects import statements that stay inside the package, and prints one edge per pair of sub-packages. Save it as toy/importgraph.py:

"""Print who imports whom inside one package. Standard library only."""
import ast
import pathlib
import sys

root = pathlib.Path(sys.argv[1])
pkg = root.name


def module_name(path: pathlib.Path) -> str:
    parts = list(path.relative_to(root.parent).with_suffix("").parts)
    if parts[-1] == "__init__":
        parts.pop()
    return ".".join(parts)


def layer(mod: str) -> str:
    parts = mod.split(".")
    return ".".join(parts[:2]) if len(parts) > 1 else mod


edges = set()
for path in sorted(root.rglob("*.py")):
    src = module_name(path)
    for node in ast.walk(ast.parse(path.read_text())):
        if isinstance(node, ast.Import):
            targets = [alias.name for alias in node.names]
        elif isinstance(node, ast.ImportFrom) and node.level == 0 and node.module:
            targets = [node.module]
        else:
            continue
        for t in targets:
            if t.split(".")[0] == pkg and layer(t) != layer(src):
                edges.add((layer(src), layer(t)))

for a, b in sorted(edges):
    print(f"{a} -> {b}")
print("--- mermaid ---")
print("flowchart LR")
for a, b in sorted(edges):
    print(f"    {a.replace('.', '_')}[{a}] --> {b.replace('.', '_')}[{b}]")
$ python3 importgraph.py shop

shop.app -> shop.adapters
shop.app -> shop.domain
shop.domain -> shop.adapters
--- mermaid ---
flowchart LR
    shop_adapters[shop.adapters] --> shop_domain[shop.domain]
    shop_app[shop.app] --> shop_adapters[shop.adapters]
    shop_app[shop.app] --> shop_domain[shop.domain]
    shop_domain[shop.domain] --> shop_adapters[shop.adapters]

Read the first block. shop.adapters -> shop.domain is right: an adapter depends on the core. shop.domain -> shop.adapters is the arrow that should not exist, and together they form a cycle. Paste the Mermaid lines into mermaid.live (the previous card) to see it drawn.

Now make the rule permanent with import-linter. In a virtual environment, run pip install import-linter. In toy/, create a file named .importlinter:

[importlinter]
root_package = shop

[importlinter:contract:domain-is-pure]
name = The domain must not import adapters
type = forbidden
source_modules =
    shop.domain
forbidden_modules =
    shop.adapters

[importlinter:contract:layers]
name = Dependencies point inward
type = layers
layers =
    shop.app
    shop.adapters
    shop.domain
$ lint-imports  # exits non-zero when a contract is broken, so CI can fail the build
The domain must not import adapters BROKEN
Dependencies point inward BROKEN
Contracts: 0 kept, 2 broken.
...
shop.domain.order -> shop.adapters.sqlite_repo (l.1)

That output is illustrative: the real report has more headings and layout, which differ between versions, and I could not run the tool for this page. The essentials are the contract names, a verdict per contract, and the exact importing line. Fix the bug by deleting the import and passing the repository into Order.save instead (the "port" of chapter 5), then run lint-imports again until both contracts are kept.

What to look for

  • A cycle between layers is the most expensive shape of coupling: neither side can be understood, tested or replaced alone (chapter 2).
  • In the layers contract, the list runs from high to low: a layer may import those below it, never those above. That is the dependency rule from chapter 5 as three lines of config.
  • A forbidden contract also catches indirect imports by default: if the domain imports a helper that imports the adapter, it is still reported.
  • The fix has to be a design change. Adding an "ignore" entry to the config would silence the check and keep the problem.
  • Run the same idea on a monolith you want to split: every edge between two proposed services is a call you will have to turn into a network request (chapter 11).

Common pitfalls

  • The script sees only static imports. Imports built at run time (importlib.import_module(name)), plugin lookups and dependency injection containers are invisible to it, and to import-linter too.
  • Imports inside functions count. ast.walk finds them, and that is a feature: a lazy import is still a dependency, though people often use one to hide a cycle.
  • The root package must be importable. Run the tools from the folder that contains shop/ and don't forget the __init__.py files, or the analysis may not find your modules.
  • Start with the rules you already believe in. A strict config on an old codebase fails with hundreds of violations; add one contract, record the existing exceptions, and shrink them over time.
  • The graph shows what exists, not what is good. A graph with no cycles can still be badly cut (chapter 2).

Test it

Whether a design is good shows up the first time you try to test it. If the test is painful, the design is telling you something.

unittest & doubles

Nothing to install: unittest and unittest.mock are in Python's standard library · Run: python3 -m unittest -v from your project folder · Windows: the same, using python or py

unittest is Python's built-in test framework. Alongside it, unittest.mock lets you replace a collaborator with a stand-in for one test. A stand-in is a test double; a fake is a small, working implementation of the same interface (an in-memory repository, a payment gateway with a credit limit). Designing so that a fake is easy to write is what chapter 7 calls testability as architecture, and it is the payoff of the ports from chapter 5.

10-minute guided exercise

Make a folder with two files. The first is the code under test: a function that takes its payment gateway as an argument (a seam) and a second function that reads the clock.

from datetime import datetime, timezone
from typing import Protocol


class PaymentGateway(Protocol):
    def charge(self, customer: str, cents: int) -> bool: ...


def place_order(gateway: PaymentGateway, customer: str, cents: int) -> str:
    if cents <= 0:
        raise ValueError("total must be positive")
    return "paid" if gateway.charge(customer, cents) else "declined"


def stamp() -> str:
    return datetime.now(timezone.utc).strftime("%Y-%m-%d")
import unittest
from unittest import mock

import checkout
from checkout import place_order


class FakeGateway:
    """A hand-written fake: real behaviour, no network."""

    def __init__(self, limit_cents: int):
        self.limit_cents = limit_cents
        self.charges: list[tuple[str, int]] = []

    def charge(self, customer: str, cents: int) -> bool:
        if cents > self.limit_cents:
            return False
        self.charges.append((customer, cents))
        return True


class FakeVersusMock(unittest.TestCase):
    def test_fake_checks_state(self):
        gw = FakeGateway(limit_cents=5000)
        self.assertEqual(place_order(gw, "ana", 3000), "paid")
        self.assertEqual(gw.charges, [("ana", 3000)])

    def test_fake_declines_over_limit(self):
        self.assertEqual(place_order(FakeGateway(1000), "ana", 3000), "declined")

    def test_mock_checks_interaction(self):
        gw = mock.create_autospec(checkout.PaymentGateway, instance=True)
        gw.charge.return_value = True
        self.assertEqual(place_order(gw, "ana", 3000), "paid")
        gw.charge.assert_called_once_with("ana", 3000)

    def test_autospec_catches_wrong_signature(self):
        gw = mock.create_autospec(checkout.PaymentGateway, instance=True)
        with self.assertRaises(TypeError):
            gw.charge("ana")  # missing cents

    def test_bad_totals(self):
        for cents in (0, -5):
            with self.subTest(cents=cents):
                with self.assertRaises(ValueError):
                    place_order(FakeGateway(10), "ana", cents)


class PatchPitfalls(unittest.TestCase):
    def test_patch_where_it_is_looked_up(self):
        with mock.patch("checkout.datetime") as fake_dt:
            fake_dt.now.return_value.strftime.return_value = "2030-01-01"
            self.assertEqual(checkout.stamp(), "2030-01-01")

    def test_plain_mock_accepts_anything(self):
        loose = mock.Mock()
        loose.charge("ana")          # wrong call, no error
        loose.charge.assert_called_once()
        with self.assertRaises(AttributeError):
            loose.assert_calls_once()  # typo guard on assert_* names


if __name__ == "__main__":
    unittest.main()

That was real output from Python 3.14; the wording of each line depends on your Python version, and the time will differ. Now break things on purpose. In place_order, change "declined" to "denied" and re-run: two tests fail with a readable diff. Then change the call to gateway.charge(customer) (forgetting cents) and see which kind of test notices. The autospecced mock raises TypeError; the fake does too, because its method has a real signature. A bare Mock() would not complain.

What to look for

  • Fake: assert on the outcome. The test reads "the order is paid and the gateway recorded one charge". It survives refactoring, because it does not care how the code talked to the gateway.
  • Mock: assert on the conversation. assert_called_once_with pins down exactly how the code called its collaborator. It is useful where the call is the behaviour (send an email, publish an event) and brittle everywhere else.
  • The seam is the architecture. place_order was easy to test because it receives its gateway instead of creating one. If it had built a real client inside, the only option would be patch (chapter 7, chapter 5).
  • subTest reports which input failed and keeps going, which suits table-style cases like the two bad totals.
  • A fake must itself be trusted. A common remedy is one shared set of contract tests run against both the fake and the real adapter (chapter 7).

Common pitfalls

  • Patch where the name is looked up, not where it is defined. If checkout.py does from datetime import datetime, patch checkout.datetime, as above, not datetime.datetime. This is the most common reason "my patch does nothing". Python's documentation has a section called "Where to patch".
  • A plain Mock() accepts any call. It happily agrees with a wrong signature or a method that does not exist, so the test passes while the code is broken. Use create_autospec or patch(..., autospec=True) to make the double follow the real signature.
  • Over-mocking. A test that mocks every collaborator mostly checks that the code calls what it calls, and it breaks on every refactor. Prefer fakes at the edges and real objects inside.
  • Mocking what you don't own. Wrap a third-party client in your own small interface (an adapter) and fake that (chapter 5).
  • Discovery needs importable names: files named test*.py, in packages or the start folder. Use python3 -m unittest discover -s tests for a separate folder.
  • Tests that need the real clock, network or random numbers are flaky. Inject them as arguments, as Lab 2 does with its clock (Lab 2).

Stress it

A design that works with one request at a time tells you nothing about what it does with fifty. Load tools let you ask, on purpose, in a place where it cannot hurt anyone.

HTTP load generators: hey & oha

macOS: brew install hey or brew install oha · Ubuntu/Debian: sudo apt install hey (in the Ubuntu 24.04 "universe" repository); oha via cargo install oha · Also: ApacheBench ab, from the apache2-utils package on Ubuntu, is already on many Macs · Windows: prebuilt binaries from each project's GitHub page, or WSL

Only ever aim these at your own machine

A load generator sends as much traffic as it can. Pointed at a server you don't own, that is an attack on someone else's service, and it may be illegal. Everything on this card targets 127.0.0.1, a server you start yourself in a terminal on your own computer. Do not change the address.

A load generator opens many connections, sends requests as fast as it is allowed to, and summarises the latencies and errors. It is how you find out what a service does when it is busy or when a dependency is slow, which is where the timeouts, retries and circuit breakers of chapter 17 earn their keep, and what a synchronous call chain costs (chapter 13). hey and oha do the same job. oha also shows a live terminal display, which you can switch off with --no-tui.

10-minute guided exercise

You need the Lab 2 files from architecture/labs/code/lab02/. Its solution.py already ends with a wsgiref server on 127.0.0.1:8000. Copy the lab folder somewhere disposable, because the server creates an orders.db file. Next to solution.py, add a wrapper that also has a slow and a failing endpoint, so there is something interesting to see:

import time
from wsgiref.simple_server import make_server

from solution import make_app

orders = make_app("orders.db")


def app(environ, start_response):
    path = environ["PATH_INFO"]
    if path == "/slow":                      # simulates a slow dependency
        time.sleep(3)
        start_response("200 OK", [("Content-Type", "text/plain")])
        return [b"finally\n"]
    if path == "/boom":                      # simulates a failing dependency
        start_response("503 Service Unavailable", [("Content-Type", "text/plain")])
        return [b"nope\n"]
    return orders(environ, start_response)


if __name__ == "__main__":
    with make_server("127.0.0.1", 8000, app) as httpd:
        print("serving on http://127.0.0.1:8000")
        httpd.serve_forever()
$ python3 flaky_demo.py
serving on http://127.0.0.1:8000

In a second terminal, first create one order so there is something to read, then run a gentle load test. The flags are -n (total requests), -c (concurrent workers) and -t (per-request timeout in seconds for hey):

$ curl -s -X POST 127.0.0.1:8000/v1/orders -H 'Idempotency-Key: demo-1' -d '{"customer":"ana@example.com","items":[{"sku":"mug","qty":2,"unit_price_cents":1500}]}'
$ hey -n 200 -c 10 http://127.0.0.1:8000/v1/orders/1
Summary:
  Total:        0.4210 secs
  Requests/sec: 475.0
Latency distribution:
  50% in 0.0206 secs
  99% in 0.0390 secs
Status code distribution:
  [200] 200 responses

Those numbers are made up to show the shape; your machine will report different ones, and the real output has more lines (a histogram and more percentiles). Now ask for something the server does slowly, with a 2-second timeout. The server sleeps 3 seconds per request, and wsgiref's simple server handles one request at a time, so the others queue behind it:

$ hey -n 10 -c 5 -t 2 http://127.0.0.1:8000/slow
Summary:
  Total:        2.0030 secs
Status code distribution:
Error distribution:
  [10]  Get "http://127.0.0.1:8000/slow": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
$ hey -n 20 -c 5 http://127.0.0.1:8000/boom
Status code distribution:
  [503] 20 responses

Compare the two failures. A timeout appears under "Error distribution": the client gave up and has no status code at all. A failing server appears under "Status code distribution": it answered quickly and said no. Retry logic and circuit breakers must treat them differently. A retry of a timed-out POST is only safe because of the idempotency key you built in Lab 2, so try that last:

$ hey -n 50 -c 5 -m POST -H 'Idempotency-Key: demo-1' -d '{"customer":"ana@example.com","items":[{"sku":"mug","qty":2,"unit_price_cents":1500}]}' http://127.0.0.1:8000/v1/orders
$ curl -s '127.0.0.1:8000/v1/orders'  # still the one order from before: 50 requests, one key, one order
# the same idea with oha (flags: -n requests, -c connections, -t timeout, --no-tui plain text):
$ oha -n 200 -c 10 --no-tui http://127.0.0.1:8000/v1/orders/1

Stop the server with Ctrl-C in terminal 1 and delete the copied folder when you are done.

What to look for

  • Percentiles, not the average. The median says how a typical request feels; the 99th percentile says how bad the unlucky ones have it. Under load they pull apart before anything breaks outright (chapter 17).
  • Queueing. With the slow endpoint and one worker thread, the fifth caller waits for the four ahead of it. Latency rises long before the server is "busy" doing work: a call chain is only as fast as its slowest link (chapter 13).
  • Timeouts decide who gives up. Without -t, hey uses its own default, not "forever". Every caller in a real system needs an explicit timeout that is shorter than its own caller's (chapter 17).
  • Error type matters. Timeouts, refused connections and 5xx responses are different diseases. A circuit breaker counts them all as failures, but only some are worth retrying (chapter 17).
  • The 50 identical POSTs produced a single order, which is why a client may retry at all.

Common pitfalls

  • Never point a load tool at a server that isn't yours. That includes "just a quick test" against a public site, a shared staging system or a colleague's service without their say-so.
  • The load generator is on the same machine as the server, so they compete for CPU. Absolute numbers from a laptop test are not a capacity forecast; compare before and after a change instead.
  • wsgiref is a teaching server. It handles one request at a time and is not built for real traffic, so its results say nothing about a production server.
  • Repeating one request measures one code path. A load test of a single cached or replayed request (like the idempotent POST above) says little about real traffic. Mix the requests you expect.
  • Raising -c to find out when it breaks can freeze your own computer. Increase in small steps and keep Ctrl-C handy.
  • The first requests are slower (cold caches, new connections). Look at a run of reasonable length, not 20 requests.

Workbench 1: Deploy a Model as a Serverless Endpoint

A serverless endpoint is a web address that runs your model on a rented GPU only while requests are arriving. The platform starts a worker (a container that holds your code and model) when a request comes in and stops it when traffic goes quiet. The wait while a worker starts is the cold start; a worker that is already running is warm. Chapter 12 asks what turns a proof of concept into a service people rely on. This workbench builds one such service, tests it on your laptop, and gives you the means to measure the two numbers a customer will ask about: how slow is the first request, and what does a thousand requests cost?

Why measure it

A pilot runs on a laptop with the model already loaded, so it never shows a cold start, and it never shows a bill. Production does both. If a customer’s users wait 15 seconds for the first answer after a quiet hour, or the bill depends on how bursty traffic is, that is a finding for the reliability and cost gates of chapter 12, and it is much cheaper to find before launch. The habit is the same as in every workbench: predict from the parts, then measure. Here the parts are the steps a worker performs before it can answer, and the seconds of GPU time each request is billed for.

What you need

  • Part 1, your laptop: Python 3.10+, the workbench venv (below) plus the runpod package, and about 300 MB of disk for SmolLM2-135M-Instruct. About 30 minutes. Docker Desktop is needed only if you want to build the image.
  • Part 2, RunPod (optional): a RunPod account with a small credit, a Docker Hub account, about 10 GB of disk for the image, and about an hour. The GPU time itself is a few GPU-minutes. Nothing on this page needs your credit card number or API key typed into a file: the key goes in an environment variable.

Predict before you run

A worker cannot answer its first request until it has done four things. Their times add up, and they are the first prediction:

tcold = tboot + timports + weights (bytes) / read speed + twarm-up

Boot is the platform starting your container. Imports is Python loading torch and transformers. The weights are read from disk into GPU memory. Warm-up is the CUDA set-up and the first forward pass, which is slower than later ones. Of these, you can measure imports and warm-up on your laptop (the handler records them), and compute the weights term from the model’s file size. For Qwen2.5-1.5B-Instruct, the model the GPU part deploys, model.safetensors is 3,087,467,144 bytes.

The second prediction is the bill. RunPod’s documentation says billing is per second, from when a worker starts until it stops, and that the start-up, the execution of each request and the idle timeout (how long a worker waits for more work before it is switched off) are all billed. It says pulling the image is not. So for 1,000 requests, with f the share of requests that arrive when no worker is warm:

GPU-seconds per 1,000 requests = 1000 × texec + 1000 × f × (tstart-up billed + tidle)

Multiply GPU-seconds by the price per GPU-second and you have money; keeping the formula in seconds keeps it true when prices move. The terms f and tidle are the levers: a larger idle timeout lowers f and raises the idle part, and an always-on active worker makes f zero at the cost of 86,400 GPU-seconds a day.

Your prediction

Assume boot 4 s, imports 6 s, weights read at 1 GB/s, warm-up 2 s, 0.8 s per request and the 5-second default idle timeout (all assumptions, to be replaced by your measurements). How long is the cold start, and how many GPU-seconds does 1,000 requests cost when every request is cold (f = 1), when one in ten is (f = 0.1), and how many requests a day make an always-on worker cheaper?

Check your arithmetic

Weights: 3,087,467,144 / 109 = 3.1 s. Cold start: 4 + 6 + 3.1 + 2 = 15.1 s, of which 11.1 s is billed (everything but the boot, by the documentation’s rule that image pull is free). Then 1,000 × 0.8 + 1,000 × f × (11.1 + 5):

f = 1: 800 + 16,087 = 16,887 GPU-seconds. f = 0.1: 800 + 1,609 = 2,409. A day has 86,400 seconds, so an always-on worker is cheaper above 86,400 / 16.9 = 5,116 requests a day if every request is cold, and 86,400 / 2.4 = 35,869 if one in ten is. The shape is the lesson: cold requests cost about 20 times a warm one, so traffic that arrives in widely spaced single requests is the worst case for serverless.

Part 1: on your laptop

The worker

A RunPod worker is a Python file that does its slow work once, at import time, and defines a handler: a function that receives one job and returns the answer. The platform sends the job as a dictionary with an id and an input holding whatever the client sent. The last line, runpod.serverless.start({"handler": handler}), hands your function to the SDK, which fetches jobs and calls it.

Files, all in code/w01/: handler.py (the worker), requirements.txt, Dockerfile, test_input.json, client.py (notebook: client.ipynb) and cost.py (notebook: cost.ipynb). The handler has no notebook, because it starts a server and is meant to run as a script.

The idea

  1. at import, once per worker: import the libraries, load the model, run one warm-up pass; time each step
  2. handler(job): read job["input"]; refuse a missing prompt with a clear error; generate; return text, timings and a job counter
  3. the counter tells the client whether it hit a fresh worker (job 1) or a warm one
  4. runpod.serverless.start({"handler": handler}) connects the function to the platform, or to a local test
  5. a Dockerfile bakes the weights into the image, so a cold start does not download them
"""A RunPod Serverless worker that answers a prompt with a small model.

Test it on your laptop, with no cloud account:
    python handler.py --test_input '{"input": {"prompt": "Say hi"}}'
Or serve the same handler on http://localhost:8000 and call /runsync:
    python handler.py --rp_serve_api
On RunPod the container runs `python -u handler.py` and the platform sends
jobs to it. Choose the model with the MODEL environment variable, and
set DEVICE=cpu to ignore a laptop GPU.

Needs: runpod, torch, transformers (requirements.txt)."""
import os
import time

# ── 1. Start-up work: this is the cold start (runs once per worker) ──────
T0 = time.perf_counter()
import runpod                                           # noqa: E402
import torch                                            # noqa: E402
from transformers import AutoModelForCausalLM, AutoTokenizer  # noqa: E402

T_IMPORT = time.perf_counter() - T0                     # libraries

MODEL = os.environ.get("MODEL", "HuggingFaceTB/SmolLM2-135M-Instruct")
if torch.cuda.is_available():
    DEVICE, DTYPE = "cuda", torch.bfloat16
elif torch.backends.mps.is_available():
    DEVICE, DTYPE = "mps", torch.float16
else:
    DEVICE, DTYPE = "cpu", torch.float32
if os.environ.get("DEVICE") == "cpu":                   # force the CPU
    DEVICE, DTYPE = "cpu", torch.float32

T1 = time.perf_counter()
tok = AutoTokenizer.from_pretrained(MODEL)
model = AutoModelForCausalLM.from_pretrained(MODEL, dtype=DTYPE)
model = model.to(DEVICE).eval()
T_LOAD = time.perf_counter() - T1                       # weights to memory

T2 = time.perf_counter()
with torch.no_grad():                                   # first forward pass
    model(**tok("warm up", return_tensors="pt").to(DEVICE))
T_WARM = time.perf_counter() - T2                       # kernels, caches

JOBS = 0                                                # jobs seen so far


# ── 2. The handler: runs once per job, on a worker that is already warm ──
def handler(job):
    global JOBS
    JOBS += 1
    job_input = job["input"]                            # what the client sent
    prompt = job_input.get("prompt")
    if not prompt:                                      # a clear failure
        return {"error": "input.prompt is required"}
    max_tokens = min(int(job_input.get("max_tokens", 32)), 256)

    start = time.perf_counter()
    text = tok.apply_chat_template(
        [{"role": "user", "content": prompt}],
        add_generation_prompt=True, tokenize=False)
    ids = tok(text, return_tensors="pt").to(DEVICE)
    with torch.no_grad():
        out = model.generate(**ids, max_new_tokens=max_tokens,
                             do_sample=False,
                             pad_token_id=tok.eos_token_id)
    new = out[0, ids["input_ids"].shape[1]:]
    return {
        "text": tok.decode(new, skip_special_tokens=True),
        "tokens": int(new.shape[0]),
        "gen_ms": round(1000 * (time.perf_counter() - start), 1),
        "job_number": JOBS,                             # 1 = first job
        "start_up_s": {"import": round(T_IMPORT, 2),
                       "load": round(T_LOAD, 2),
                       "warm_up": round(T_WARM, 2)},
        "device": DEVICE,
    }


# ── 3. Hand the handler to the RunPod SDK ────────────────────────────────
runpod.serverless.start({"handler": handler})

The container description. Build with --platform linux/amd64: RunPod’s machines are x86-64 Linux, and on an Apple-silicon Mac Docker would otherwise build an ARM image that fails there.

FROM python:3.11-slim

WORKDIR /
# Dependencies first, so the layer is reused when only handler.py changes.
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Bake the weights into the image: no download at cold start.

CMD ["python", "-u", "/handler.py"]

Test it locally

The RunPod SDK can run your handler without the cloud. With --test_input it feeds one job to the handler and exits (without the flag it reads test_input.json from the folder). On this laptop, with the handler forced onto the CPU (DEVICE=cpu, since a laptop GPU is not part of the story) and the log lines filtered to the useful ones, it printed:

A job that breaks the contract (no prompt) comes back as a failure with the message from the handler, which is what a client should see:

DEBUG  | local_test | Handler output: {'error': 'input.prompt is required'}
ERROR  | Job local_test failed with error: input.prompt is required

The second local mode is a small web server with the same routes as the cloud: python handler.py --rp_serve_api listens on port 8000 and takes POST /runsync with a body like {"input": {...}}. (/run only returns a fake id locally, so use /runsync.) My port 8000 was in use, so the run below used --rp_api_port 8011. The client sends six requests one after another and prints the wall-clock time of each:

$ python handler.py --rp_serve_api --rp_api_port 8011
$ python client.py --url http://localhost:8011/runsync
"""Time a RunPod Serverless endpoint: the first request against the rest.

Against the worker running on your laptop (python handler.py --rp_serve_api):
    python client.py --url http://localhost:8000/runsync
Against a deployed endpoint (the key comes from the RunPod console):
    export RUNPOD_API_KEY=...
    python client.py --endpoint ENDPOINT_ID
    python client.py --endpoint ENDPOINT_ID --gap 30   # let it scale to 0

Needs: httpx (installed with transformers)."""
import argparse
import os
import statistics
import time

import httpx

# ── 1. Settings ──────────────────────────────────────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("--endpoint", default="")      # RunPod endpoint id
ap.add_argument("--url", default="")           # or a full /runsync URL
ap.add_argument("--n", type=int, default=6)    # requests to send
ap.add_argument("--gap", type=float, default=0)    # seconds between them
ap.add_argument("--prompt", default="Name three uses of a load balancer.")
ap.add_argument("--max-tokens", type=int, default=24)
args, _ = ap.parse_known_args()        # notebooks pass their own flags

URL = args.url or f"https://api.runpod.ai/v2/{args.endpoint}/runsync"
HEADERS = {"content-type": "application/json"}
if os.environ.get("RUNPOD_API_KEY"):
    HEADERS["authorization"] = "Bearer " + os.environ["RUNPOD_API_KEY"]
BODY = {"input": {"prompt": args.prompt, "max_tokens": args.max_tokens}}

# ── 2. Send the requests one at a time and time each ─────────────────────
print(f"POST {URL}")
print(f"{'#':>2} {'wall ms':>8} {'status':>10} {'delay ms':>9} "
      f"{'exec ms':>8} {'job on worker':>14}")
walls = []
with httpx.Client(timeout=330) as client:
    for i in range(args.n):
        if i and args.gap:
            time.sleep(args.gap)
        start = time.perf_counter()
        reply = client.post(URL, json=BODY, headers=HEADERS)
        wall = 1000 * (time.perf_counter() - start)
        reply.raise_for_status()
        job = reply.json()
        out = job.get("output") or {}
        walls.append(wall)
        print(f"{i + 1:>2} {wall:>8.0f} {job.get('status', '?'):>10} "
              f"{job.get('delayTime', '-'):>9} "
              f"{job.get('executionTime', '-'):>8} "
              f"{out.get('job_number', '?'):>14}")

# The local server leaves delayTime and executionTime out; RunPod's has them.
print("worker start-up, seconds:", out.get("start_up_s"))

# ── 3. First request against the rest ────────────────────────────────────
if len(walls) > 1:
    warm = statistics.median(walls[1:])
    print(f"\nfirst request {walls[0]:.0f} ms; median of the other "
          f"{len(walls) - 1}: {warm:.0f} ms; first / warm = "
          f"{walls[0] / warm:.1f}x")

What you should see

  • The request succeeds and the handler is the whole contract. One function, a dictionary in, a dictionary out. The SDK adds the id and status.
  • The start-up numbers are separate from the request. start_up_s shows the import took 12 s, the weights 0.8 s and the warm-up 0.1 s on this (busy) machine, before the first job arrived. In earlier runs the import took between 2.7 and 8 s, so even this number moves with load. The local server only opens its port after that work, so a local test cannot show a cold start. In the cloud those seconds are the cold start.
  • A warm worker answers in a steady time. The six requests took 0.87 to 1.1 s each. In two earlier runs the first request was slower than the rest (754 ms against 233 ms, and 688 against 529), in this one it was not, so a first-request penalty on a warm worker exists but is small and variable. Sending a realistic request as the warm-up is cheap insurance.
  • The local server leaves out delayTime and executionTime (the table shows dashes). The cloud endpoint reports both, and the next part uses them.

The prediction script

cost.py is the arithmetic from “Predict before you run”, with every default an assumption you can replace with the numbers above.

"""Predict a serverless endpoint's cold start and its cost per thousand
requests, in GPU-seconds. Every default is an ASSUMPTION: replace them
with what handler.py and client.py measure for you.

    python cost.py
    python cost.py --boot 8 --disk-gbps 0.3 --exec 1.2

Needs: nothing but Python."""
import argparse

# ── 1. Settings (assumptions, not measurements) ──────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("--boot", type=float, default=4.0)      # s: container start
ap.add_argument("--imports", type=float, default=6.0)   # s: import torch...
ap.add_argument("--weights", type=int, default=3_087_467_144)  # bytes
ap.add_argument("--disk-gbps", type=float, default=1.0)  # GB/s weights read
ap.add_argument("--warm", type=float, default=2.0)      # s: CUDA, 1st pass
ap.add_argument("--exec", type=float, default=0.8)      # s: one request
ap.add_argument("--idle", type=float, default=5.0)      # s: idle timeout
args, _ = ap.parse_known_args()        # notebooks pass their own flags

# ── 2. Cold start = sum of the steps before the first job can run ────────
load = args.weights / (args.disk_gbps * 1e9)
start = args.boot + args.imports + load + args.warm
print("cold start, seconds")
for name, s in [("container boot", args.boot), ("import libraries",
                args.imports), (f"load {args.weights / 1e9:.2f} GB of "
                f"weights at {args.disk_gbps:g} GB/s", load),
                ("CUDA set-up and first pass", args.warm)]:
    print(f"  {name:<42}{s:>6.1f}")
print(f"  {'total (what the first caller waits)':<42}{start:>6.1f}")
billed = start - args.boot     # RunPod's docs: image pull is not billed
print(f"  {'of which billed (all but the boot)':<42}{billed:>6.1f}")

# ── 3. GPU-seconds per 1,000 requests ────────────────────────────────────
# Billed: start-up (not the boot) + execution + the idle timeout that
# follows the last request.
# f = share of requests that find no warm worker (and so pay start-up + idle).
print("\nGPU-seconds per 1,000 requests = 1000 x exec + 1000 x f x "
      "(billed + idle)")
print(f"{'f (cold share)':>15} {'GPU-s':>9} {'per request':>12}")
for f in (1.0, 0.5, 0.1, 0.02):
    total = 1000 * args.exec + 1000 * f * (billed + args.idle)
    print(f"{f:>15.2f} {total:>9,.0f} {total / 1000:>11.1f}s")

# ── 4. Against one always-on worker (a whole day is 86,400 GPU-s) ────────
print("\nrequests per day at which an always-on worker costs less:")
for f in (1.0, 0.1):
    per = args.exec + f * (billed + args.idle)
    print(f"  f = {f:.1f}: 86,400 / {per:.1f} = {86400 / per:,.0f}")

Part 2: deploy it on RunPod

Not run here

This page was written without a RunPod account, and without a running Docker engine, so the image was not built, nothing was deployed, and no cloud request was sent. The handler and client ran against the local server above. The steps follow RunPod’s documentation (see the box below); the predictions come from cost.py; the measurements are yours to fill in, and they are saved in this browser.

  1. Build and push. Use a version tag, not latest (RunPod’s documentation advises specific tags). The build argument chooses the model baked into the image. 
    $ docker build --platform linux/amd64 \
$     --build-arg MODEL=Qwen/Qwen2.5-1.5B-Instruct \
$     -t YOUR_DOCKERHUB_NAME/zts-worker:v1 .
$ docker login
$ docker push YOUR_DOCKERHUB_NAME/zts-worker:v1
    The image is several gigabytes, because the Linux build of torch from PyPI brings its CUDA libraries.
  2. Create the endpoint. In the RunPod console open Serverless, then New Endpoint, then Import from Docker Registry, and enter docker.io/YOUR_DOCKERHUB_NAME/zts-worker:v1. Pick a 24 GB GPU, set active workers to 0 and max workers to 1, leave the idle timeout at its default, and deploy. Note the endpoint id.
  3. Make an API key in the console settings and put it in your shell, not in a file: export RUNPOD_API_KEY=....
  4. Measure cold and warm. The client sends to https://api.runpod.ai/v2/ENDPOINT_ID/runsync with an authorization: Bearer header. Run it twice: once straight after deploying (the first request is cold), and once with a gap longer than the idle timeout, so that every request finds the worker switched off. 
    $ python client.py --endpoint ENDPOINT_ID --n 6
$ python client.py --endpoint ENDPOINT_ID --n 4 --gap 30

Read the table the client prints. delay ms is the time the job spent before your handler started (queueing and the cold start), exec ms is your handler’s time, and job on worker being 1 marks a fresh worker. The documentation does not state the unit of the two timings; its example ("delayTime": 824, "executionTime": 3391) is consistent with milliseconds, and your own numbers will confirm it. The requests are sent one by one on purpose: /runsync waits for the answer, 90 seconds by default and up to 5 minutes with ?wait=, which is longer than a cold start.

QuantityPredictedMeasuredRatio
Library imports on the worker, s (start_up_s.import in the response)6.0 (assumed)
Weights load, s (start_up_s.load)3.1 at 1 GB/s

The 338 is 20 × 16.9 s from the script. The two assumed rows (imports, execution) are guesses until you replace them, so a ratio far from 1 there tells you about the guess, not about the formula. The informative comparison is the last one, because it tests whether the formula captures the bill. If the billed seconds come out lower than predicted, check whether the platform kept the worker warm longer than your gap, or whether its FlashBoot option (which the documentation lists as a way to shorten cold starts; this page did not measure it) was on.

Break it

  • Download at start instead of baking the weights in. Remove the snapshot_download line from the Dockerfile. Predict the cold start: 3,087,467,144 bytes at the 8 MB/s I got from Hugging Face on this laptop is 386 s; at 100 MB/s it is 31 s. That time is inside your own code, so it is part of the billed start-up (the documentation says only image pull and cached-model downloads are free). RunPod’s documentation recommends its cached-model feature for Hugging Face models; try it and compare.
  • Use the 7B model. Build with --build-arg MODEL=Qwen/Qwen2.5-7B-Instruct. Its weights are 15,231,233,024 bytes, so at 1 GB/s the load is 15.2 s and python cost.py --weights 15231233024 predicts a 27.2 s cold start. A request that waits half a minute needs a different design: say so in your architecture notes.
  • Keep one worker warm. Set active workers to 1. Predict f = 0 and a fixed 86,400 GPU-seconds a day, which beats the serverless bill only above about 5,100 requests a day if every request would have been cold (35,900 if one in ten would). Check the discount for active workers with RunPod before you rely on this.
  • Lengthen the idle timeout to 60 s and send one request every 30 seconds. Predict f and the idle term: the worker never sleeps, so you pay up to 60 idle seconds after the last request but almost no cold starts.

State of play, October 2026

Read from docs.runpod.io on 14 October 2026; platform behaviour changes, so recheck before relying on it. Billing is per second from worker start to stop, rounded up to the second; start-up (handler loading models), execution and the idle timeout are billed; pulling the image and downloading cached models are not. The default idle timeout is 5 seconds. /runsync waits 90 seconds by default (1 to 300 seconds with ?wait=), keeps results for 1 minute, and accepts payloads up to 20 MB (10 MB for /run). The local server starts on port 8000 with --rp_serve_api. The documentation page I read for /runsync printed curl -x POST; the flag that sets the method is a capital -X. I did not retrieve GPU prices, which are on runpod.io/pricing and change often, and none appear on this page: multiply the GPU-seconds by the current rate yourself. Cold-start features such as FlashBoot and cached models are described in the documentation but were not measured here.

Key takeaways

  • A serverless worker is a handler plus slow start-up work done once. The handler is small; the cold start is where the time and the money go.
  • Cold start is a sum of steps (boot, imports, weights at their read speed, warm-up), so you can predict it and see which step to attack.
  • Cost is GPU-seconds: execution for every request, plus start-up and idle time for every request that finds no warm worker. Bursty traffic is cheap; sparse traffic pays the cold start each time.
  • A local test proves the contract, not the latency. Only the deployed endpoint shows cold and warm, so the cloud numbers are the ones to put in front of a customer.

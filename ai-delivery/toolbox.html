Toolbox

Applied AI work is a loop of showing something real, serving it, shipping it into someone else's network, protecting the data on the way, and writing down what you found so a customer can act on it. These five tools cover that loop. Each card has setup notes and a ten-minute exercise tied to the chapters and studios, and each says plainly what was run here and what was not.

How to use this page

Jump to a tool when a chapter or studio points at it. A word on honesty, because several of these tools are heavy. In the environment where this page was written I could not install anything from the Python package index (the network proxy refused the connection) and the container daemon was not running. So I did not run Gradio, Streamlit, FastAPI or Presidio, and I did not start any container. Their code listings are marked illustrative and I checked them only for Python syntax (python3 -m py_compile), and I describe what to look for instead of pasting invented output. What I did run, with real output pasted: the plain-Python review function that the demos wrap; the Compose file, validated with docker compose config from Docker Compose v5.5.1 (the command renders and checks a file without needing the daemon); a tool-independent harness that scores any redactor against labelled spans, run on a regex redactor; and a memo linter, run on a good and a bad memo. The Mermaid diagrams use syntax from the Mermaid documentation but were not rendered here. Library arguments and defaults change between versions, so trust your terminal and each project's documentation over this page.

Show it

A customer cannot react to a plan. They can react to a screen. A rough interface in front of the riskiest assumption turns an abstract argument into "that flag is wrong, and here is why".

Gradio & Streamlit

Install: pip install gradio or pip install streamlit (Python 3, a virtual environment recommended) · Alternatives: Panel, NiceGUI, Chainlit (chat interfaces), Jupyter widgets, or plain HTML over FastAPI · Chapters: 5, and the demos in every studio, for example S1

What each one is for. Both turn a Python function into a web page in a few lines. Gradio is built around the function: you declare input and output components and it builds the form, the call and the result view, and it can expose the same function as an API. Streamlit is built around the script: the file runs from top to bottom each time the user does anything, widgets return their current values, and st.session_state keeps what must survive a rerun. Pick Gradio when the demo is "paste input, see output" (most model demos). Pick Streamlit when it is a small dashboard or a multi-step flow with several widgets.

The habit that matters is not the framework. It is what the demo shows. A demo that outputs a bare label invites argument; one that shows the evidence beside the answer (the quote, the page, the confidence, the rule applied) invites correction, which is what you came for. Put a "was this useful?" control in so you collect labels while the customer plays with it.

10-minute guided exercise

Wrap the clause reviewer from studio 1 in two interfaces. Keep the logic in one plain function, so both demos and the later API share it. This is the function, run here:

"""review.py: the function every demo wraps. A keyword reviewer, standing in for a model call."""
import re

RULES = [
    ("liability", re.compile(r"liabilit", re.I), "Check the cap against 12 months of fees"),
    ("renewal", re.compile(r"renew", re.I), "Check the notice window (over 60 days is high)"),
    ("termination", re.compile(r"terminat", re.I), "Check who may terminate, and on what notice"),
    ("indemnity", re.compile(r"indemnif", re.I), "Check the direction of the indemnity"),
]

def review_clause(text: str) -> dict:
    """Return the first matching rule with the exact words that triggered it (the quote)."""
    for name, rx, advice in RULES:
        m = rx.search(text)
        if m:
            sentence = next(s for s in re.split(r"(?<=[.;])\s+", text) if rx.search(s))
            return {"type": name, "flag": True, "advice": advice, "quote": sentence}
    return {"type": "other", "flag": False, "advice": "No rule matched", "quote": ""}

if __name__ == "__main__":
    for t in ["Supplier may terminate this Agreement for convenience on thirty (30) days' written notice.",
              "Each party shall keep the other's Confidential Information confidential for five (5) years.",
              "This Agreement renews automatically unless notice is given 120 days before the end of the term."]:
        print(review_clause(t))
{'type': 'termination', 'flag': True, 'advice': 'Check who may terminate, and on what notice', 'quote': "Supplier may terminate this Agreement for convenience on thirty (30) days' written notice."}
{'type': 'other', 'flag': False, 'advice': 'No rule matched', 'quote': ''}
{'type': 'renewal', 'flag': True, 'advice': 'Check the notice window (over 60 days is high)', 'quote': 'This Agreement renews automatically unless notice is given 120 days before the end of the term.'}

Now the two thin wrappers. They are illustrative: neither library was installed here, and I checked only that the files parse.

import gradio as gr
from review import review_clause

def run(text):
    r = review_clause(text)
    label = {"flagged": 1.0, "not flagged": 0.0} if r["flag"] else {"not flagged": 1.0, "flagged": 0.0}
    return label, r["type"], r["quote"], r["advice"]

demo = gr.Interface(
    fn=run,
    inputs=gr.Textbox(lines=6, label="Clause text"),
    outputs=[gr.Label(label="Result"), gr.Textbox(label="Type"), gr.Textbox(label="Quote"), gr.Textbox(label="Advice")],
    title="Clause reviewer (prototype)",
    description="Prototype for discussion. Output is a first-pass flag, not legal advice.",
    flagging_mode="never",
)
if __name__ == "__main__":
    demo.launch()   # 127.0.0.1 only; do not pass share=True with customer data
import streamlit as st
from review import review_clause

st.title("Clause reviewer (prototype)")
st.caption("A first-pass flag for discussion. Not legal advice.")
text = st.text_area("Clause text", height=140)
if st.button("Review") and text.strip():
    r = review_clause(text)
    st.session_state["last"] = r
if "last" in st.session_state:
    r = st.session_state["last"]
    (st.warning if r["flag"] else st.success)(f"{r['type']}: {r['advice']}")
    if r["quote"]:
        st.code(r["quote"])
    st.radio("Was this useful?", ["yes", "no"], horizontal=True, key="feedback")
  1. Minute 0 to 2. Create a virtual environment, install one of the libraries, put review.py and the app file in one folder.
  2. Minute 2 to 4. Start it: $ python gradio_app.py (Gradio serves on 127.0.0.1, port 7860 by default) or $ streamlit run streamlit_app.py (port 8501 by default).
  3. Minute 4 to 8. Paste five clauses from the studio's gold set. For each, say aloud whether you would accept the flag and why. Note the clauses where the quote is right but the advice is wrong (the keyword rules cannot tell who benefits).
  4. Minute 8 to 10. Add one thing a customer asked for in your imagined interview: for example a second output showing which playbook rule applied. Observe how little code that took, and how it changes the conversation.

What to look for

  • Gradio should show the form, a label output and three text boxes; submitting again recomputes. Streamlit should rerun the whole script on each click; if the feedback radio button resets the result, st.session_state is not holding what you expect.
  • The terminal should show the local address; if the page does not load, the port is probably in use.
  • The argument that turns off Gradio's built-in flagging has been renamed between releases (older versions used allow_flagging); if you get an error about it, read the version you installed.

Common pitfalls

  • Sharing a demo on real data. Gradio's launch(share=True) creates a public link through a tunnel service. Never use it with customer documents. Bind to localhost, or put the demo behind the customer's single sign-on (OAuth and OpenID Connect).
  • Mistaking the demo for the product. These tools have no tests, no authentication by default and no scaling story. Say "prototype" on the screen, and move to a typed API and a proper front end when the assumption survives (turning research into products).
  • Hiding the failure. A demo that only works on the examples you rehearsed teaches the customer nothing. Include one case you know fails and say so.

Serve it

Once a prototype survives a customer's reaction, other software wants to call it. That means an API with a contract, validation, authentication and a health check.

FastAPI

Install: pip install "fastapi[standard]" (adds the fastapi command and the Uvicorn server) · Alternatives: Flask, Django REST framework, Litestar, or a Node framework if the customer's team uses Node · Chapters: 12, 16 · Track 1: APIs

What it is for. FastAPI is a Python web framework in which you describe requests and responses with type annotations (using the Pydantic library) and it validates every call, returns a clear error for bad input and generates interactive documentation from your code. For an applied AI team this removes a whole class of integration arguments: the customer's developers read /docs, not a PDF you wrote last month.

Three habits turn a notebook into something a customer can integrate. Validate at the edge: limits on length and shape, so a ten-megabyte string never reaches a model. Version the path (/v1/review) so you can change behaviour without breaking callers. Add a health endpoint that the orchestrator and the load balancer can poll (SLOs and orchestration depend on it).

10-minute guided exercise

Put the same review function behind a typed endpoint. This is illustrative: FastAPI was not installed here, and I checked only that the file parses.

from fastapi import Depends, FastAPI, Header, HTTPException
from pydantic import BaseModel, Field
from review import review_clause

app = FastAPI(title="Clause review API", version="1.0.0")

class ReviewRequest(BaseModel):
    clause_id: str = Field(min_length=1, max_length=40)
    text: str = Field(min_length=10, max_length=4000)

class ReviewResponse(BaseModel):
    clause_id: str
    type: str
    flag: bool
    advice: str
    quote: str

def check_key(x_api_key: str = Header(default="")):
    if x_api_key != "demo-key":                       # replace with a real secret store
        raise HTTPException(status_code=401, detail="missing or wrong API key")

@app.get("/healthz")
def healthz():
    return {"ok": True}

@app.post("/v1/review", response_model=ReviewResponse, dependencies=[Depends(check_key)])
def review(req: ReviewRequest):
    r = review_clause(req.text)
    return ReviewResponse(clause_id=req.clause_id, **r)
  1. Minute 0 to 2. Install, put main.py and review.py in one folder (the import above is relative to it).
  2. Minute 2 to 3. Start the development server: $ fastapi dev main.py. It listens on 127.0.0.1:8000 by default and reloads on edits.
  3. Minute 3 to 6. Open http://127.0.0.1:8000/docs. The interactive page lists /healthz and /v1/review with their schemas, built from the type annotations. Try the endpoint with a good clause, then with a three-character text.
  4. Minute 6 to 8. From a second terminal: $ curl -s -X POST localhost:8000/v1/review -H 'x-api-key: demo-key' -H 'content-type: application/json' -d '{"clause_id":"A8","text":"Supplier may terminate for convenience on 30 days notice."}'. Repeat without the header.
  5. Minute 8 to 10. Look at /openapi.json. Everything a client generator needs is there. Add a field to ReviewResponse and watch /docs change without touching anything else.

What to look for

  • The too-short text should be rejected with status 422 and a body naming the field and the limit, and the function should not run at all. The wrong or missing key should give 401.
  • The response should contain exactly the fields of ReviewResponse and nothing else; the response model is also a filter, so internal fields cannot leak by accident.
  • The interactive docs and the JSON schema should agree. If they do not, the annotations are doing less than you think.

Common pitfalls

  • The key in the source file. demo-key above is a placeholder for the exercise. Real secrets come from the environment or a secrets store, per deployment (keys, secrets and PKI).
  • Blocking the server on a slow model call. A plain def endpoint runs in a thread pool; an async def endpoint that calls a blocking library stalls every request. Match the style to the client library, and set timeouts (failure, overload).
  • Returning model text unchecked. Validate model output against a schema before it leaves the API, and return a structured error when it fails, not a raw string (structured output).
  • No request identifier. Accept or generate one and put it in every log line. The first support ticket will need it (tracing and observability).

Ship it

The customer's network is not your laptop. It may have no internet, a short list of approved images, and a security team that wants to read the file that describes what runs.

Docker Compose

Install: Docker Desktop or Docker Engine with the Compose plugin (docker compose version) · Alternatives: Podman with podman compose, Kubernetes manifests, Helm or Kustomize for bigger sites, Nomad · Chapters: 13, 12 · Track 1: containers and virtual machines, containers and orchestration

What it is for. A Compose file describes a whole application, with its services, networks, volumes and secrets, in one reviewable YAML file, and one command starts it. For a customer who will run your system inside their own network, that file is the contract: it says which images run, which ports open, what each service may reach and where data lives. A security reviewer can read it in ten minutes (security reviews for AI systems).

For restricted environments three features matter. A network marked internal: true has no route to anything outside it, so a service on it cannot call out even if it is compromised. depends_on with condition: service_healthy starts services in a safe order, using the health checks. And images can be moved without internet: build and test on a connected machine, export each image with docker save to a file, carry the files across on approved media, and docker load them on the other side (restricted environments). Pin images by digest (image: name@sha256:...) once you ship, so what the customer reviewed is what runs.

  1. Minute 0 to 3. Read the file as a security reviewer. For each service answer: what can it reach, what can it write, what secret does it hold? (The API can reach the model server and the database; only the API publishes a port, and only on 127.0.0.1.)
  2. Minute 3 to 5. Run docker compose config with no flags and read the resolved output: defaults filled in, relative paths made absolute, secrets mounted under /run/secrets.
  3. Minute 5 to 8. On a machine with a running daemon, start it: $ docker compose up -d --wait, then $ docker compose ps. The --wait flag returns when services are healthy.
  4. Minute 8 to 10. Prove the network claim instead of trusting it: $ docker compose exec api python -c "import urllib.request; urllib.request.urlopen('https://example.com', timeout=3)". What to look for

  • config -q should print nothing and exit 0; any message is a real problem in the file. The resolved output should show internal: true on the network and your secrets mounted read-only at /run/secrets.
  • Startup order: the API should wait for the model server and database to be healthy. If it starts first and crashes, the health checks or conditions are wrong.
  • The final test above is the one that matters in an air-gapped site. A claim in a design document that no component can reach the internet is evidence only when someone has tried and failed.

Common pitfalls

  • Trusting latest. Tags move. The customer's reviewed image and the one that runs a month later must be the same bytes: pin by digest and record the digests in the evidence pack.
  • Secrets in environment variables or in the file. The file above passes only the path of a secret file. Anything in environment: is visible to docker inspect and often to logs.
  • Treating Compose as a high-availability platform. It runs one host. If the customer needs failover, say so and propose the platform they already operate (orchestration).
  • Resource limits that are ignored. Memory and CPU limits shown here are honoured by current Compose on a single host, but the model server also needs the host's GPU or enough RAM for the weights. Test on the target hardware (choosing models).

Protect it

Personal data moves with every document. The safest copy is the one that never leaves the boundary, and the next safest is one with the identifiers replaced.

Presidio for redaction

Install: pip install presidio-analyzer presidio-anonymizer, then a language model for the recogniser, for example python -m spacy download en_core_web_lg (a large download) · Alternatives: cloud services such as Google Cloud Sensitive Data Protection, Amazon Comprehend PII detection or Azure AI Language PII detection; spaCy or another named-entity model used directly; plain regular expressions for fixed formats · Chapters: 15, 9 · Lab: Lab 3: a PII redaction and audit pipeline

What it is for. Presidio is an open-source toolkit from Microsoft with two parts. The analyser finds personal data in text by combining pattern recognisers (credit-card numbers, email addresses), a named-entity model (person and place names) and context words; the anonymiser then applies an operator to each finding: replace it with a label, redact it, mask part of it, hash it or encrypt it (so an authorised user can reverse it). You add your own recognisers for formats specific to the customer, such as a policy-number pattern.

What matters more than the library is how you measure a redactor. The risk is asymmetric, as in the claims studio: a missed identifier leaks, a false alarm only removes a harmless word. So the number to track is recall on identifiers, with the list of what leaked, and the test must be run on text that looks like the customer's, not on the library's examples. In regulated health settings the definitions come from law: the HIPAA Privacy Rule's Safe Harbor method of de-identification (45 CFR 164.514(b)(2)) lists 18 types of identifier to remove, and the standard is far higher than "looks redacted" (healthcare and life sciences).

10-minute guided exercise

Build the test before you build the redactor. The harness below scores any redactor, a function from text to a list of found spans, against labelled test strings. I ran it on the regular-expression redactor from studio 3. Presidio was not installed here, so the exercise is to plug it in (illustrative code after the output).

"""Score any redactor against labelled spans. Marked-up test strings: [[LABEL|value]]."""
import re
from collections import defaultdict

MARKED = [
 "Policy [[POLICY|KM-4417203]]. My Ford (reg [[REG|LK21 ABC]]) was hit. Call [[PHONE|0113 496 0182]].",
 "Driver [[NAME|Sam Okafor]] lives at [[POSTCODE|LS6 2AB]]. Email [[EMAIL|s.okafor@example.org]].",
 "Claim from [[NAME|Priya Raman]], policy [[POLICY|KM-5520981]], phone [[PHONE|07700 900123]].",
 "Our broker [[NAME|Tom Whitfield]] has the details; plate [[REG|YC70 XYZ]].",
 "Nothing personal here: a bollard, a bumper and 3 photos.",
 "Reference 20260314 and amount 1,250 are not identifiers.",
 "Contact [[EMAIL|claims.team@example.org]] or write to [[POSTCODE|M1 4BT]].",
 "Mr [[NAME|Okonkwo]] reported it on 4 March; policy [[POLICY|KM-9001122]].",
]

def parse(marked):
    text, spans, pos = "", [], 0
    for m in re.finditer(r"\[\[(\w+)\|([^\]]+)\]\]", marked):
        text += marked[pos:m.start()]
        spans.append((len(text), len(text) + len(m.group(2)), m.group(1)))
        text += m.group(2); pos = m.end()
    return text + marked[pos:], spans

PATTERNS = [("REG", r"\b[A-Z]{2}\d{2}\s?[A-Z]{3}\b"), ("POLICY", r"\bKM-\d{7}\b"), ("PHONE", r"\b0\d{3,4}\s?\d{3}\s?\d{3,4}\b"),
            ("EMAIL", r"\b[\w.+-]+@[\w-]+\.[\w.]+\b"), ("POSTCODE", r"\b[A-Z]{1,2}\d[A-Z\d]?\s?\d[A-Z]{2}\b")]
def regex_redactor(text):
    return [(m.start(), m.end(), lab) for lab, rx in PATTERNS for m in re.finditer(rx, text)]

def score(redactor):
    hit, miss, false = defaultdict(int), defaultdict(int), defaultdict(int)
    leaked = []
    for marked in MARKED:
        text, gold = parse(marked)
        found = redactor(text)
        for s, e, lab in gold:
            if any(fs < e and s < fe for fs, fe, _ in found):      # any overlap counts as caught
                hit[lab] += 1
            else:
                miss[lab] += 1; leaked.append(text[s:e])
        for fs, fe, flab in found:
            if not any(fs < e and s < fe for s, e, _ in gold):
                false[flab] += 1
    return hit, miss, false, leaked

if __name__ == "__main__":
    hit, miss, false, leaked = score(regex_redactor)
    print(f"{'label':9s} {'caught':>6s} {'missed':>6s} {'false alarms':>12s}")
    for lab in sorted(set(hit) | set(miss) | set(false)):
        print(f"{lab:9s} {hit[lab]:6d} {miss[lab]:6d} {false[lab]:12d}")
    n = sum(hit.values()) + sum(miss.values())
    print(f"\nrecall over all identifiers: {sum(hit.values())}/{n}")
    print("leaked values:", leaked)
label     caught missed false alarms
EMAIL          2      0            0
NAME           0      4            0
PHONE          2      0            0
POLICY         3      0            0
POSTCODE       2      0            0
REG            2      0            0

The regex redactor catches every structured identifier (emails, phone numbers, postcodes, registrations, policy numbers) and misses all four names: recall 11 of 15, with the leaked values printed. That is exactly the gap a named-entity model is for, and the harness tells you whether it closes the gap on your text. To test Presidio, write an adapter that returns (start, end, label) spans and pass it to score. Illustrative sketch from the library's documented interface, not run here:

from presidio_analyzer import AnalyzerEngine, Pattern, PatternRecognizer
from pii_eval import score

analyzer = AnalyzerEngine()          # loads the spaCy model; the first call is slow
policy = PatternRecognizer(supported_entity="POLICY",
                           patterns=[Pattern(name="km_policy", regex=r"KM-\d{7}", score=0.9)])
analyzer.registry.add_recognizer(policy)

def presidio_redactor(text):
    results = analyzer.analyze(text=text, language="en")
    return [(r.start, r.end, r.entity_type) for r in results]

hit, miss, false, leaked = score(presidio_redactor)
  1. Minute 0 to 2. Run the harness on the regex redactor and read the table. Which label has the most misses?
  2. Minute 2 to 5. Add four more test strings from your own domain: a name in a signature, a name inside an email address, a date of birth, an address without a postcode. Run again. Your regexes will fail somewhere new.
  3. Minute 5 to 9. If you have Presidio installed, run the adapter above. Compare per-label results. Note that Presidio's entity names differ from yours (PERSON, PHONE_NUMBER, EMAIL_ADDRESS); map them in the adapter if you want a per-label table.
  4. Minute 9 to 10. Write down your acceptance rule for the pilot, in the form "recall of at least X% on identifiers on N documents from the customer, with every leaked value reviewed by a person".

What to look for

  • The leaked-values list matters more than the percentage. Read it for patterns: are they names, unusual formats, text inside tables?
  • False alarms on a regex redactor tend to be numbers that look like identifiers; with a model-based recogniser they are often ordinary capitalised words. Judge them by what they cost downstream (does an answer get worse when a place name is hidden?).
  • Mapping and reversal: if authorised users need the original back, replace values with consistent tokens and keep the mapping in a separate, access-controlled store with its own audit log (Lab 3).

Common pitfalls

  • Redacting after the first copy. The prompt, the vendor's logs and your own traces already hold the original if redaction runs late. Redact before text leaves the boundary, and log the redacted version (privacy and data handling for AI).
  • Believing a detector's confidence score is a probability of being right. It is a heuristic; measure on labelled data.
  • Forgetting the other channels. Images, scanned PDFs and file names carry identifiers too. Text redaction does not touch a photo of a driving licence (OCR).
  • Treating redaction as anonymisation. Replacing names does not make a record anonymous if the remaining details identify the person. Whether data are anonymous in law is a question for the customer's privacy counsel (data protection and privacy).

Write it

The last step of every engagement is a document someone else acts on. A customer reads a memo for the decision it asks of them, and reads it carefully only if it is short, structured and honest.

Writing & diagram tools

Install: nothing for Markdown and for Mermaid on GitHub or GitLab; the Mermaid command-line renderer is npm install -g @mermaid-js/mermaid-cli (command mmdc); the live editor is mermaid.live · Alternatives: a shared document editor for comments, Excalidraw for freehand sketches (see the System Design toolbox), PlantUML, a slide deck for the live readout · Chapters: 17, 18

What it is for. Markdown is a plain-text format for headings, lists, tables and code that renders almost everywhere, diffs well in version control and survives being pasted into any system. Mermaid lets you write a diagram as text inside a Markdown file, which hosting sites such as GitHub render as a figure. Text diagrams sit next to the prose they explain, change in a pull request like code, and cannot drift into an out-of-date screenshot. The third piece is a memo template that puts the decision first (writing for customers).

The template that carries the weight is one page with five headings: Bottom line (the recommendation and the single number that supports it, with its interval), What I did, What I found, What I did not do (the limitations, early) and Decisions I need from you. It is the order a take-home reviewer or a customer's executive reads in (take-homes, portfolios and interviews).

10-minute guided exercise

Write the memo, draw the pipeline, then lint the memo. First, the filled-in sample memo (the numbers come from studio 1):

# Analysis memo: contract clause review, first results

## Bottom line
I recommend a six-week pilot, with conditions. On a 30-clause test the system caught 14 of 16 risky clauses (88%, 95% interval 64% to 97%) and a keyword list caught 13 of 16. That is promising and unproven.

## What I did
Built a keyword baseline, labelled 30 clauses with two reviewers (kappa 0.73), and compared four systems on the same clauses.

## What I found
- Precision was 14 of 16 flags for the best system and 13 of 25 for the keyword list.
- Seven clauses failed. The first wrong step was the playbook in two cases and a missing cross-reference in one.

## What I did not do
No scanned contracts, no real vendor calls, no timing of lawyers.

## Decisions I need from you
Add rules for assignment and prepaid fees to the playbook; approve a 400-clause labelling effort.

Finally, the linter. It checks the habits a reader needs: required sections, a recommendation in the first 60 words, a count or interval beside every percentage, no dash punctuation, no hype words, and a length limit. I ran it on the good memo and on a deliberately bad one:

"""Lint an analysis memo for the habits a customer reader needs. Standard library only."""
import re, sys

REQUIRED = ["bottom line", "what i did", "what i found", "what i did not do", "decisions i need"]

def lint(path):
    text = open(path, encoding="utf-8").read()
    low = text.lower()
    problems = []
    heads = [h.strip().lower() for h in re.findall(r"^#{2,3}\s+(.*)$", text, re.M)]
    for req in REQUIRED:
        if not any(req in h for h in heads):
            problems.append(f"missing section: '{req}'")
    body = re.sub(r"^#.*$", "", text, flags=re.M)
    first = " ".join(body.split()[:60]).lower()
    if not re.search(r"\brecommend|\bdecision|\bwe should|\bi propose", first):
        problems.append("the first 60 words do not state a recommendation or decision")
    for n, line in enumerate(text.splitlines(), 1):
        if "%" in line and not re.search(r"interval|\bci\b|\d+ of \d+|\bn ?= ?\d+", line, re.I):
            problems.append(f"line {n}: a percentage with no count or interval")
    dashes = text.count(chr(0x2014)) + text.count(" -- ")
    if dashes:
        problems.append(f"{dashes} dash(es) used as punctuation: use a colon, comma or new sentence")
    for w in re.findall(r"\b(simply|just|obviously|basically|amazing)\b", low):
        problems.append(f"hype or filler word: '{w}'")
    words = len(text.split())
    if words > 700:
        problems.append(f"{words} words: over the 700-word limit for a one-page memo")
    print(f"{path}: {words} words, {len(problems)} problem(s)")
    for p in problems:
        print("  -", p)

for p in sys.argv[1:]:
    lint(p)

  1. Minute 0 to 4. Write the memo for one of the studios you have done, using the five headings. Put the recommendation and your best number, with its interval, in the first paragraph.
  2. Minute 4 to 6. Draw the pipeline in Mermaid. Keep it under ten nodes; label every edge that carries a decision.
  3. Minute 6 to 8. Lint it and fix every complaint. If a rule seems wrong for your memo, change the rule on purpose, not the memo by accident.
  4. Minute 8 to 10. Read the bottom line aloud to a colleague (or a wall) and ask: could they decide from this paragraph alone?

What to look for

  • The bad memo trips 14 checks; the good one trips none. The linter cannot judge whether the memo is true or well argued, only whether it has the structure a reader needs to find out.
  • A percentage with no count is the most common defect in project reports. "92%" means something different on 12 cases and on 1,200.
  • In the rendered Mermaid, check that the arrows read left to right and that every sensitive path ends somewhere visible.

Common pitfalls

  • Writing the journey. "We tried X, then Y" is a diary. The reader needs the finding first and the path only if it changes their decision.
  • Burying the bad news. A failure presented in the last paragraph reads as concealment. Put it in the bottom line with the next step (presenting a failure honestly).
  • Screenshots of diagrams. They cannot be diffed and go stale. Keep the text source in the repository.
  • Mermaid sprawl. A diagram with thirty nodes explains nothing. Split it, or draw it by hand and keep Mermaid for the small ones.

Key takeaways

  • Show the riskiest assumption on a screen the customer can touch, and put the evidence (quote, page, rule) beside every answer.
  • Keep the logic in one plain function. Wrap it in a demo today and a typed, validated, authenticated API tomorrow.
  • A Compose file is a reviewable description of what runs in the customer's network; validate it, pin images by digest and prove the network claims by testing them.
  • Build the redaction test before the redactor, measure recall on identifiers, and read the list of what leaked.
  • Write the decision first, put limitations early, give every percentage a count, and lint your memos.

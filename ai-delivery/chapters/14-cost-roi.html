Cost Models & Return on Investment

The customer's finance team will ask what this costs and what it returns. This chapter builds the answer from the bottom: the cost of one task, the cost of owning the whole system for three years, and a return-on-investment case that states its ranges, names its weakest assumption and survives being read by someone who wants it to fail.

Why this matters

Many AI projects are approved on a demo and cancelled on an invoice. Analyst forecasts of abandoned projects name unclear value and escalating cost together, and a business case built on a single optimistic number is how both happen. The delivery engineer is the person who knows how many tokens a task really uses, how many minutes a reviewer really needs and how often the model really fails, so you are the one who can write the honest version. After this chapter you will be able to compute the cost per task from tokens and prices, find the levers that reduce it, see why the model bill is often the smallest line of the total cost of ownership, build a return-on-investment model with ranges instead of a point, find which assumption decides the outcome, and present the result in a form a sceptical chief financial officer can check.

Cost per task, not cost per token

Providers price by the token, but customers think in work: a claim processed, a contract reviewed, a question answered. The unit that connects the two is the unit economics of a task: what it costs to complete one, end to end, including every step that touches it. Everything else (monthly bills, budgets, return on investment) is arithmetic on top of that number, so it is worth getting right.

Tokens times price, for every call

A model call costs (input tokens × input price) + (output tokens × output price), with prices quoted per million tokens, and output tokens usually costing several times as much as input tokens. The economics of a token explains why: producing each output token takes a pass through the model, while the input is processed in parallel. A task that makes several calls (extract, then draft, then check) sums them, and an agent loop multiplies them, because each step typically re-reads the growing conversation. Context engineering and cost, latency and quality trade-offs show how to keep that growth in check.

State of play, October 2026

Every price in this chapter is an illustrative assumption, chosen to be plausible in shape and not copied from a price list, because per-token prices change often and differ by provider and model tier. Two mechanisms are widely offered and worth checking in the current price list of whichever provider you use. Prompt caching: tokens read from a cache of an earlier, identical prefix are billed at a fraction of the normal input price (secondary sources describe Anthropic's cache reads at 0.1 times the base input price and cache writes at a premium of about 1.25 times for the short cache lifetime). Batch processing: requests that can wait up to a day are billed at about half price (secondary sources describe this discount for both Anthropic's and OpenAI's batch APIs). I could not fetch the providers' official pricing pages, so confirm the multipliers, the cache lifetimes and the minimum prefix lengths before using them in a quote. Your own measured token counts matter more than any price.

A worked example with four designs

The pipeline below processes a claims letter. It makes two calls: an extraction call over a 6,000-token document with a 1,500-token fixed instruction prefix, and a drafting call with an 800-token fixed prefix. Six per cent of calls are repeated after a format failure. A human reviews 35% of outputs for four minutes at a loaded cost of 48 dollars an hour. The script prices four designs, each adding one lever, and then puts the model cost next to the review cost.

# Cost per task for a two-call document pipeline, under four designs.
# All prices and token counts are ILLUSTRATIVE assumptions (USD per million tokens).
PRICE = {"small": (0.15, 0.60), "mid": (3.00, 15.00)}     # (input, output)
CACHE_READ, CACHE_WRITE, BATCH = 0.10, 1.25, 0.50          # multipliers on the input price / total

# (name, static prefix tokens, variable input tokens, output tokens)
CALLS = [("extract", 1500, 6000, 300), ("draft", 800, 1500, 450)]
RETRY = 0.06                                                # calls repeated after a format failure
REVIEW_SHARE, REVIEW_MIN, RATE = 0.35, 4.0, 48.0            # humans review 35% of tasks, 4 min each, $48/h

def call_cost(model, prefix, var, out, cached_share=0.0):
    pin, pout = PRICE[model]
    plain = (prefix + var) * pin
    cached = prefix * (cached_share * CACHE_READ + (1 - cached_share) * CACHE_WRITE) * pin + var * pin
    inp = cached if cached_share > 0 else plain
    return (inp + out * pout) / 1e6

def task_cost(small_share=0.0, cached=0.0, batch_share=0.0):
    total = 0.0
    for name, prefix, var, out in CALLS:
        mid = call_cost("mid", prefix, var, out, cached)
        small = call_cost("small", prefix, var, out, cached)
        total += (1 - small_share) * mid + small_share * small
    total *= 1 + RETRY
    return total * (1 - batch_share * (1 - BATCH))

designs = [
    ("A  all mid-tier, no tricks",           dict()),
    ("B  + cache the static prefixes (90%)", dict(cached=0.90)),
    ("C  + route 60% to the small model",    dict(cached=0.90, small_share=0.60)),
    ("D  + batch the 50% that can wait",     dict(cached=0.90, small_share=0.60, batch_share=0.50)),
]
review = REVIEW_SHARE * REVIEW_MIN / 60 * RATE
print(f"{'design':38s} {'model $/task':>12s} {'per 1,000':>10s}")
for name, kw in designs:
    c = task_cost(**kw)
    print(f"{name:38s} {c:12.4f} {c*1000:10.2f}")
print(f"\nhuman review per task: {review:.2f} USD  (= {REVIEW_SHARE:.0%} x {REVIEW_MIN:.0f} min at {RATE:.0f} USD/h)")
base, best = task_cost(), task_cost(**designs[-1][1])
print(f"model cost is {base/(base+review):.1%} of the cost of a task in design A and {best/(best+review):.1%} in design D")

Three things stand out. First, caching helped less than the headline discount suggests: only the fixed prefix (2,300 of 9,800 input tokens) can be cached, so a 90% saving on that part gives a 13% saving overall. Caching rewards designs whose prompts are long and repeated, not ones whose cost is dominated by each new document. Second, routing was the big lever: sending the 60% of tasks that a small model handles well to it cut the cost by more than half, provided the evaluation showed the quality was held (that check is the difference between routing and wishful thinking; see choosing models). Third, and most important, the model is a rounding error next to the person. Design A costs 4 cents a task for the model and 1.12 dollars for the review, so the model is under 4% of the cost of a task, and the best design brings it to about 1%. Cutting the model bill by a further half saves half a per cent. Cutting the review rate from 35% to 30% saves more than all four designs together.

Common misconception

"The cost of an AI system is the API bill." For a system that keeps a person in the loop, the bill for the model is often a small part of the cost of a task, and the model is rarely the largest line of the total cost of ownership. Teams that optimise tokens first (shorter prompts, cheaper models) may save pennies while a reviewer's four minutes costs a dollar. Start from the biggest line. The exception is high-volume, fully automated work with no per-item review (classifying millions of short texts, say), where tokens are the cost and every lever above matters.

Total cost of ownership

Total cost of ownership (TCO) is everything the customer pays over the life of the system, not only the purchase: building it, running it, supporting it, changing it, and the labour that works alongside it. Three years is a common horizon, because the customer will want to see payback within it and because a model, a provider's API or a regulation will probably change within it.

The script below puts a claims-letter assistant on one page. Volumes are 400,000, 600,000 and 800,000 letters in years one to three. The figures are illustrative assumptions for a project of this size, not benchmarks.

# Three-year total cost of ownership for the claims-letter assistant (ILLUSTRATIVE assumptions, USD).
VOLUME = [400_000, 600_000, 800_000]          # tasks per year
MODEL_PER_TASK = 0.0120                        # design D from unitcost.py
REVIEW_PER_TASK = 0.35 * 4 / 60 * 48           # human review of 35% of tasks

ONE_OFF = {
    "build (3 engineers, 5 months)": 420_000,
    "gold set and eval harness":      60_000,
    "integration with case tool":    150_000,
    "security review and hardening":  45_000,
    "training and change work":       40_000,
}
def yearly_costs(volumes=VOLUME, model_per_task=MODEL_PER_TASK):
    years = []
    for y, v in enumerate(volumes):
        run = {
            "model calls":              v * model_per_task,
            "human review":             v * REVIEW_PER_TASK,
            "hosting and storage":      36_000,
            "support (0.5 engineer)":   90_000,
            "licences and tooling":     20_000,
            "yearly model migration":   25_000,
        }
        years.append(run)
    return years

if __name__ == "__main__":
    years = yearly_costs()
    one_off = sum(ONE_OFF.values())
    totals = {}
    for k in ONE_OFF: totals[k] = ONE_OFF[k]
    for run in years:
        for k, v in run.items(): totals[k] = totals.get(k, 0) + v
    grand = sum(totals.values())
    print(f"{'line':34s} {'3-year USD':>11s} {'share':>6s}")
    for k, v in sorted(totals.items(), key=lambda kv: -kv[1]):
        print(f"{k:34s} {v:11,.0f} {v/grand:6.1%}")
    print(f"{'TOTAL':34s} {grand:11,.0f}")
    print(f"\nper task over three years: {grand/sum(VOLUME):.2f} USD;  model calls alone: {totals['model calls']/sum(VOLUME):.4f} USD")

Read the table as a list of questions the customer should be able to answer. Human review is the biggest line, because it is paid on every task for ever, and it is a real cost even though no invoice arrives: it is the reviewers' time, which the benefit side of the case must account for in the same way. Build is the line everybody expects. Support (half an engineer, kept for three years) and the yearly model migration are the lines most often forgotten. Models are retired and replaced, and each change needs the evaluation re-run, prompts revised and a staged rollout (see the last chapter and choosing models). The gold set and the security review are small but they are on the critical path, and the cost of the review is mostly the calendar time it takes.

A few other cost items belong on the list whenever they apply.

  • Self-hosted inference turns a variable cost into a fixed one: GPUs bought or rented whether busy or not, plus the people to run them. Choosing models computed the crossing volume; what matters here is utilisation, because an idle GPU costs the same as a busy one. The cost and efficiency chapter covers the cloud pricing logic.
  • Retrieval infrastructure: embedding the corpus (a one-off plus refreshes), a vector index and its storage, and the re-indexing when documents change (RAG end to end).
  • Observability and evaluation in production: trace storage, a weekly human sample, and the judge-model calls used for automated checks (LLM observability).
  • Compliance and audit in regulated domains: documentation, validation by an independent team and periodic review (see the finance and healthcare chapters).
  • The cost of errors that get through: refunds, rework, regulatory penalties, reputational damage. It belongs in the benefit calculation, below.

Analogy: the cost of a restaurant dish

A restaurant prices a dish at about three times its ingredients, because the ingredients are the small part: the rent, the cooks, the waiters and the wasted food are the rest. A kitchen that cut its ingredient bill by half would barely change its profit, while a cook who prepares dishes that are sent back would change it a great deal. The model call is the ingredient, the reviewer and the support engineer are the staff, and rejected outputs are dishes sent back.

Where it breaks down: an ingredient has a fixed price per portion. Token use varies by request, a long document costs five times a short one, and an agent that loops can spend a hundred times what it was expected to. So a restaurant can price from a recipe, but you must price from measured distributions, and put a cap on the worst case.

The benefit side, honestly

Costs can be added up from invoices and hours. Benefits are harder, because most of them are changes in what people do, measured against a counterfactual. Four questions keep a benefits case honest.

  1. Against what baseline? The baseline is the current process measured in the evaluation plan (evaluation plans customers trust): minutes per task, error rate, backlog, cost of an error. Without it, savings are anecdotes. Compare also with the cheap alternative: better templates, a rules engine or a simpler model may deliver most of the benefit for a fraction of the TCO (feasibility).
  2. Where do the saved minutes go? Time saved is not money saved. If 40 clerks each save 20 minutes a day, no salary falls unless headcount is reduced, overtime is avoided, a backlog is cleared or the work grows. Otherwise the time disappears into the working day. The honest figure is realisation: the share of the freed time that turns into something the customer can count (a hire not made, a deadline met, a new service offered). Ask the customer's finance partner what they will count, and use that number. Many cases fail here.
  3. How many people actually use it? Benefits scale with adoption (last chapter): a tool that 60% of eligible people use delivers 60% of the savings at 100% of the cost. Ramp it: adoption starts low and builds.
  4. What do the errors cost? If the system's residual error rate (after review) differs from the human baseline, the difference times the cost of one error is a real line, positive or negative. A lower error rate is a benefit; a higher one is a cost that a savings-only case silently ignores. Intervals apply here too: the rate is estimated, not known.

Revenue benefits (faster quotes winning more business, better retention) are real but speculative; treat them as an upside to mention, not as the basis of the case, unless the customer can show the link from their own data.

From a point estimate to a distribution

Two standard measures. Return on investment (ROI) is (total benefit − total cost) / total cost. Net present value (NPV) adds up the yearly net benefits after discounting each by a rate that reflects the customer's cost of capital (here 8%), so that money next year counts for slightly less than money now. A project with a positive NPV beats the customer's alternative use of the money. Payback is the time until the cumulative net benefit turns positive. The usual presentation is a single NPV from a spreadsheet of best guesses. The problem is that every input is uncertain, the errors compound, and a single number hides which input is carrying the case. A better practice, borrowed from risk analysis, is to give each uncertain input a range (low, most likely, high), draw thousands of combinations at random (a Monte Carlo simulation), and read the spread of outcomes. Then vary one input at a time to see which matters. The script does both for the same claims-letter system as before, with eleven uncertain inputs, and then runs the identical system on a shorter task, to show how the answer can reverse.

# An honest ROI case: ranges for every uncertain input, 5,000 seeded draws, then a sensitivity sweep.
# All inputs are ILLUSTRATIVE assumptions for the claims-letter assistant (see tco.py for costs).
import random, statistics
from tco import ONE_OFF, VOLUME, yearly_costs

RATE, DISC, ERR_HUMAN = 48.0, 0.08, 0.015
RAMP = (0.55, 0.85, 1.00)                     # share of the final adoption reached in years 1, 2, 3
SPOT_MIN = 0.5                                # minutes per task for audits and monitoring
# name: (low, mode, high)
INPUTS = {
    "minutes per task today":    (8, 11, 14),
    "share needing review":      (0.20, 0.35, 0.50),
    "minutes per review":        (2, 4, 6),
    "share escalated to manual": (0.04, 0.08, 0.15),
    "time saved turned to value":(0.30, 0.60, 0.90),
    "final adoption":            (0.40, 0.80, 0.95),
    "residual error rate":       (0.015, 0.020, 0.040),
    "cost of one error (USD)":   (20, 40, 80),
    "volume vs forecast":        (0.7, 1.0, 1.2),
    "build cost overrun":        (0.9, 1.15, 1.8),
    "model price vs assumed":    (0.5, 1.0, 2.0),
}

def npv(x):
    one_off = sum(ONE_OFF.values()) * x["build cost overrun"]
    vols = [v * x["volume vs forecast"] for v in VOLUME]
    runs = yearly_costs(vols, 0.0120 * x["model price vs assumed"])
    total = -one_off
    for y in range(3):
        sys_tasks = vols[y] * x["final adoption"] * RAMP[y]
        new_min = (x["share needing review"] * x["minutes per review"]
                   + x["share escalated to manual"] * x["minutes per task today"] + SPOT_MIN)
        freed_hours = sys_tasks * (x["minutes per task today"] - new_min) / 60
        value = freed_hours * RATE * x["time saved turned to value"]
        errors = sys_tasks * (x["residual error rate"] - ERR_HUMAN) * x["cost of one error (USD)"]
        r = runs[y]
        fixed = r["hosting and storage"] + r["support (0.5 engineer)"] + r["licences and tooling"] + r["yearly model migration"]
        model = r["model calls"] * x["final adoption"] * RAMP[y]
        total += (value - errors - fixed - model) / (1 + DISC) ** (y + 1)
    return total

def report(label, inputs):
    mode = {k: v[1] for k, v in inputs.items()}
    slide = dict(mode, **{"time saved turned to value": 1.0, "final adoption": 1.0,
                          "build cost overrun": 1.0, "residual error rate": ERR_HUMAN})
    random.seed(14)
    draws = sorted(npv({k: random.triangular(lo, hi, m) for k, (lo, m, hi) in inputs.items()}) for _ in range(5000))
    q = lambda p: draws[int(p * (len(draws) - 1))]
    print(f"== {label}: 3-year net present value, USD thousands (8% discount rate)")
    print(f"  'slide' case (everything goes right) {npv(slide)/1e3:9,.0f}")
    print(f"  most likely inputs                   {npv(mode)/1e3:9,.0f}")
    print(f"  simulated P10 / median / P90         {q(.10)/1e3:9,.0f} / {q(.50)/1e3:,.0f} / {q(.90)/1e3:,.0f}")
    print(f"  chance the project loses money       {sum(d < 0 for d in draws)/len(draws):9.0%}")
    return mode, draws

if __name__ == "__main__":
  mode, _ = report("letters take 11 minutes today", INPUTS)
  print("\nwhat moves the answer (one input at a time, others at their most likely value):")
  rows = []
  for k, (lo, m, hi) in INPUTS.items():
      a, b = npv(dict(mode, **{k: lo})), npv(dict(mode, **{k: hi}))
      rows.append((abs(a - b), k, a, b))
  for swing, k, a, b in sorted(rows, reverse=True)[:5] + sorted(rows)[:1]:
      print(f"  {k:28s} {min(a,b)/1e3:8,.0f} to {max(a,b)/1e3:8,.0f}   (swing {swing/1e3:6,.0f})")

  def breakeven(m, key, lo, hi):
      for _ in range(40):
          mid = (lo + hi) / 2
          if npv(dict(m, **{key: mid})) < 0: lo = mid
          else: hi = mid
      return hi
  be = breakeven(mode, "time saved turned to value", 0.0, 1.0)
  print(f"  break-even: the project pays for itself if {be:.0%} of the time saved turns into value (we assumed 60%)")

  print()
  short = dict(INPUTS, **{"minutes per task today": (3.5, 5, 7)})
  mode2, _ = report("same system, letters take 5 minutes", short)
  be2 = breakeven(mode2, "time saved turned to value", 0.0, 1.0)
  print(f"  break-even realisation here: {be2:.0%}" if npv(dict(mode2, **{"time saved turned to value": 1.0})) > 0 else "  no realisation level up to 100% makes it pay at the most likely inputs")

Five readings are worth taking away.

  • The "slide" case is not the expected case. Setting realisation, adoption and build cost to their best values gives 7.2 million dollars, whereas the median of the simulation is 1.6 million. A case that quotes the first as the answer overstates by a factor of more than four.
  • The decisive inputs are not the technical ones. What share of the time saved turns into value, how long the task takes today, and how many people adopt the tool move the result by millions. The price of the model moves it by 18 thousand. The inputs you control as an engineer matter least; the inputs you must measure (the baseline, the adoption, the realisation) matter most.
  • Break-even statements travel well. "The project pays for itself if 22% of the saved time becomes value" is a sentence an executive can test against their own plans. For the short task, the break-even realisation is 67%, above what was assumed, which says the case is marginal.
  • Reviewing is the hinge. If the review takes a large part of the time the task took, there is little left to save. This is why feasibility asks about error tolerance: where errors are cheap, reviewers can sample instead of reading everything.
  • Ranges should come from evidence. The triangular ranges here are assumptions. In a real engagement, take the baseline from the time study in discovery, the review minutes and rate from shadow mode, and adoption from the pilot. Lab 2 builds a related cost and latency model.

Presenting the case and keeping it honest

A business case is a contract about what will be measured. Present it so the customer can disagree with a number rather than with the whole.

  1. Lead with the decision. "Proceed, because the median three-year value is positive and the case holds unless less than about a fifth of the saved time turns into value," or "do not proceed as scoped, because the review step removes the saving; here is a narrower scope that works."
  2. Put the assumptions in a table. Each with a low, likely and high value, the source (measured, estimated, assumed), the owner who can confirm it, and the date it will be re-checked.
  3. Show the sensitivity. The top five drivers and the break-even for the weakest. People trust a case more when it shows its own weak point.
  4. Separate hard from soft benefits. Hard: costs avoided that finance will see. Soft: time freed, quality, risk. Report them in different columns.
  5. Plan the measurement. Choose the metrics, the baseline period and the review dates (30, 90 and 180 days) before launch, and set cost guardrails in the system itself: a monthly budget with alerts at 50%, 80% and 100%, a per-request token cap, and a limit on agent steps. Cost overruns in AI systems are usually a loop or a prompt that grew, noticed on the invoice.
  6. Decide the pricing of your own engagement with the same honesty. Fixed price suits a well-defined scope; time and materials suits discovery; outcome-based fees align incentives but require agreed measurement. Whatever the form, avoid promising a figure that the data cannot support.

When the measured results arrive, report them against the table, including the ones that missed (writing for customers covers how). A customer who sees an honest review will fund phase two; one who finds the gap themselves will not. And revisit the unit costs on a schedule: prices, volumes and the best model all move, so the cheapest design for this year is probably not the cheapest for next.

Systems connection

Unit cost is the capacity and cost model of any service: work per unit of resource, then work times price. Cost and efficiency covers utilisation and cloud pricing, and load testing and capacity planning shows how to measure the demand that feeds the model. Routing small and large models is the same cascade logic as a cache hierarchy, and caching a prompt prefix is ordinary caching with the same question of hit rate. The Monte Carlo approach is the estimation habit of designing with ML and LLMs: bound the answer, then find the number that matters.

Key takeaways

  • Price the task, not the token: model calls, retries and loops, tools and search, and human review, divided by the share of tasks that end accepted.
  • Caching only helps the repeated prefix, batching only helps work that can wait, and routing helps only if the cheaper model passes the same evaluation.
  • With a person in the loop, review labour often dwarfs the model bill, which can be well under 1% of three-year TCO. Optimise the biggest line first.
  • Time saved is not money saved. Count only the realised share, scaled by adoption, net of error costs, against a measured baseline.
  • Give inputs ranges, simulate, and find the driver that matters. Report the median and a loss probability, not the slide case, and state a break-even.
  • Put cost guardrails in the system, track the case after launch against the table you published, and revisit prices as they move.

  3. Reduces it by about 25%.
  4. Nothing, because the review cost cancels the saving.
Review costs 0.35 × 4 ÷ 60 × 48 = 1.12 dollars. Halving the 0.04 model cost saves 0.02, under 2% of the total. The review cost does not cancel the saving; it simply makes it small. The levers worth pulling are those that act on the large line.

The static instructions are 2,300 tokens of a 9,800-token input, and caching them gives a 90% discount on those tokens. What is the best estimate of the saving on input cost?

  1. About 90%.
  2. About 50%.
  3. About 2%.
  4. About 20%, since only the cacheable share of the input benefits.
The discount applies only to the cached prefix: 0.9 × 2,300 / 9,800 is about 21% of input cost. Quoting the headline discount (90%) ignores that most tokens are new each time. The chapter's example showed about 13% overall because cache writes and output tokens also count.

A proposal says: "40 analysts save 30 minutes a day, which is worth 40 × 0.5 hours × 220 days × 60 dollars a year." What is the most important question to ask?

  1. What will the freed time actually be used for, and which of it will the customer count as money or capacity (realisation)?
  2. Whether the hourly rate should be 61 dollars.
  3. Whether 220 days should be 230.
  4. Whether the analysts like the tool.
The calculation multiplies freed time by a rate, which is correct only if the time converts to cash or valued output. Without hiring fewer people, clearing a backlog or doing new work, the time disappears into the working day. Small changes to rate or days are second-order, and liking the tool matters for adoption but is not the central flaw.

In the simulation, changing the model price by a factor of 0.5 to 2 moves three-year NPV by about 18 thousand dollars, while the realisation of time saved moves it by about 4 million. What should the delivery engineer conclude?

  1. Model price never matters in any AI project.
  2. Realisation does not need to be measured because it is not technical.
  3. In this project, effort should go into measuring the baseline, realisation and adoption, not into squeezing token costs; but a high-volume fully automated project would give a different ranking.
  4. The simulation is wrong because the price should matter more.
The ranking depends on the cost structure: with a person reviewing and a long task, labour dominates. A fully automated pipeline over millions of items has no review line and a large token bill. The result is a reason to measure the high-leverage inputs, not a universal rule that price is irrelevant.

The same assistant evaluated on a 5-minute task shows a most-likely NPV of about minus 156 thousand dollars and an 86% chance of losing money. A sponsor asks you to "make the numbers work". What is the most professional response?

  1. Raise the realisation assumption to 100%.
  2. Report the result, show the break-even and what would have to be true (for example 67% realisation, or a lower review share), and propose a narrower scope or a cheaper design where the economics work.
  3. Drop the sensitivity analysis from the presentation.
  4. Quote only the best case.
An honest case can say "not as scoped" and still be useful by showing what would change the answer. Moving assumptions to reach a target, hiding the analysis or quoting the best case produces a number that fails at the first review and costs credibility on every later project.

A production agent's invoice is five times the forecast in its second week. Which cause is most consistent with how costs behave in agent systems, and which control should have been in place?

  1. The provider doubled prices; use a price alert.
  2. Users became more polite; limit message length.
  3. The embeddings are too large; shrink the index.
  4. A loop or a growing context multiplied tokens per task; a per-request token cap, a step limit and budget alerts would have contained it.
Agent loops re-read a growing context at each step, so tokens per task can grow far faster than request counts. Caps, step limits and budget alerts bound the worst case. A price change would be visible in the price list and would rarely be a fivefold jump, and the other options do not address the multiplicative growth.

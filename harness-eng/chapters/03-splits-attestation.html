Public & Private Splits

A search agent will optimise whatever number you let it see, and it will find any way to raise that number that you did not think of. This chapter is about building the scorer so that cannot pay: an evaluator outside the agent's reach, a private split that decides what is kept, results that are typed and attested, and a hacking rate reported next to every score.

Why this matters

This chapter is the core of Artifact 3 (the evaluator-hardening kit) and a requirement for Artifact 2, whose results must be scored on data the loop never saw. Artifact 3's gate is a hacking rate measured on 20 or more kernels before and after hardening, so you need a precise definition of hacking rate, a way to compute it with an interval, and an evaluator whose design does not undermine the measurement. After this chapter you can split a task into public and private parts, say what the agent may and may not observe, write a typed and signed result that the agent cannot forge, compute a hacking rate and its uncertainty, and explain why even a private split can be broken by a patient agent. Chapter 04 then applies all of this to GPU kernels.

Two principals, one number

Most of this site treats a scorer as a function: give it an output, get a number. In a research loop that picture hides the important fact. There are two principals, parties with different goals and different powers: the proposer (the agent, which wants a high score) and the evaluator (the code that produces the score, which should want the truth). A principal is not necessarily a person; an agent and a test runner are both principals if they can act independently.

If the proposer can influence the evaluator by any path, the score is no longer a measurement of the proposer's work. It is a measurement of the proposer's work plus its influence on the evaluator. Three paths matter in practice:

Writing to the evaluator
The agent edits the test file, the checker or the timing code. Defence: the evaluator lives outside the agent's write boundary, the set of files and processes it may change (chapter 01).
Reading the answer key
The agent sees the hidden tests, directly or through error messages and logs, and writes code that handles exactly those cases. Defence: checker code and private data are never visible to the proposer.
Authoring the result
The agent produces the line “all tests passed” itself, and the loop believes it. Defence: results are typed and attested, and the loop verifies them.

The roadmap's evaluator rules say the same in four sentences: the evaluator lives outside the agent's write boundary and checker code is never visible to the proposer; every task has public and private splits and only private scores decide what is kept; tool results are typed and attested; hacking rate is reported next to every score. The rest of this chapter takes them in turn. The security machinery (process isolation, egress control, signing infrastructure) is the subject of A11, starting with The Threat Model of a Research Loop and Attested Tool Results. Here the focus is the evaluation design and the metric.

Public and private splits

A benchmark task comes with test cases. A public split is the part the proposer is allowed to see and run against as often as it likes: examples, a development set, visible tests. A private split (also called hidden or held-out) is the part only the evaluator sees. The proposer may use the public split to develop. Only the private score decides whether a candidate is kept, which is the rule in the roadmap's evaluator hygiene list.

Why not simply score on the public tests? Because an optimiser has no reason to prefer the general solution over a specialised one if both pass. Consider a function that should add two numbers, with eight visible test cases. One candidate implements a + b. Another builds a table of the eight visible input pairs and returns the stored sum, else zero. Both pass the visible suite. The first generalises; the second is a hack, a candidate that raises the score without doing the task. If the loop keeps whichever passes the visible tests first, it has no way to tell them apart. A toy makes the arithmetic concrete:

The idea

  1. 60 candidates: honest ones (with 0%, 10% or 30% chance of an off-by-one bug) and memorisers that copy the visible cases
  2. score each on 8 visible and 200 private cases
  3. hacking if visible pass rate − private pass rate ≥ 0.25
  4. repeat with the visible cases hidden, so a memoriser can only guess
"""Hacking rate on a toy task: add two numbers.

A candidate is a Python function. Honest candidates implement a + b, with
some bugs. Hacking candidates memorise the visible test cases. Tests: 8
visible, 200 private. A candidate is flagged as hacking when its visible
pass rate beats its private pass rate by at least GAP.

    python3 hacking_rate.py
"""
import random

GAP, VISIBLE, PRIVATE, POOL = 0.25, 8, 200, 60
rng = random.Random(7)
mk = lambda n: [(rng.randint(-99, 99), rng.randint(-99, 99)) for _ in range(n)]
vis, priv = mk(VISIBLE), mk(PRIVATE)


# ── 1. Candidate generators ───────────────────────────────────────
def honest(bug_rate):
    def f(a, b):
        return a + b + (1 if rng.random() < bug_rate else 0)
    return f


def memoriser(cases):
    table = {(a, b): a + b for a, b in cases}
    return lambda a, b: table.get((a, b), 0)


def pass_rate(f, cases):
    return sum(f(a, b) == a + b for a, b in cases) / len(cases)


# ── 2. Case 1: the proposer sees the visible tests and is selected on them
pool = [honest(rng.choice([0.0, 0.1, 0.3])) if rng.random() < 0.6
        else memoriser(vis) for _ in range(POOL)]
best = max(pool, key=lambda f: pass_rate(f, vis))
hacked = sum(pass_rate(f, vis) - pass_rate(f, priv) >= GAP for f in pool)
print(f"selected on visible: visible {pass_rate(best, vis):.2f}, "
      f"private {pass_rate(best, priv):.2f}")
perfect = [f for f in pool if pass_rate(f, vis) == 1.0]
bad = sum(pass_rate(f, priv) < 0.75 for f in perfect)
print(f"perfect on visible: {len(perfect)}, of which {bad} fail private")
print(f"hacking rate over {POOL} candidates: {hacked / POOL:.2f}")

# ── 3. Case 2: tests are hidden; the memoriser has nothing to copy ─
pool2 = [honest(rng.choice([0.0, 0.1, 0.3])) if rng.random() < 0.6
         else memoriser(mk(VISIBLE)) for _ in range(POOL)]   # guesses
hacked2 = sum(pass_rate(f, vis) - pass_rate(f, priv) >= GAP for f in pool2)
print(f"hidden tests, hacking rate: {hacked2 / POOL:.2f}")
selected on visible: visible 1.00, private 1.00
perfect on visible: 41, of which 23 fail private
hacking rate over 60 candidates: 0.37
hidden tests, hacking rate: 0.05

Selection on the visible suite is hopeless here: 41 of the 60 candidates score a perfect 1.00 on it, and 23 of those 41 fail the private cases (a private pass rate below 0.75). The flagged fraction, the hacking rate, is 0.37. When the visible cases are hidden from the proposer, so a memoriser has nothing to copy, the rate falls to 0.05. The remaining flagged cases are honest buggy candidates that were lucky on 8 cases, which is the small-sample noise of a tiny visible split. The lesson is not the particular numbers, which come from a toy I built with a 40% chance that a candidate is a memoriser. It is the shape: a perfect visible score is weak evidence of quality once any candidate can be specialised to it.

This is a toy of something SpecBench (Zhao et al., submitted May 2026) measured on real coding agents. Each of its 30 systems-level tasks, from a JSON parser to an operating-system kernel, has a natural-language specification, visible validation tests and held-out tests that combine the same features the way real use would. The authors define reward hacking as the gap between pass rates on the visible and held-out tests. They report that every frontier agent passes the visible suite almost completely while reward hacking persists on the held-out one, that smaller models show larger gaps, that the gap grows by about 28 percentage points for every tenfold increase in code size, and that failures run from subtle feature-isolation problems to deliberate exploits, such as a 2,900-line hash-table “compiler” that memorises the test inputs. I read the abstract page, not the full paper, so treat the specifics as the authors' summary.

Analogy: the practice paper and the sealed exam

A student is given a practice paper and the marks for it. They can study it as hard as they like. The sealed exam is set by someone else, marked by someone else, and covers the same topics with different questions. A student who memorises the practice answers scores perfectly on the practice paper and poorly on the exam, and the gap between the two marks is a measure of how much of their preparation was memorisation.

Where it breaks down: a student cannot rewrite the exam board, but an agent with write access can edit the marking script. And a student gets one exam; an agent gets a score back after every attempt, which is itself a source of information (next section).

Even a private split leaks if you can ask about it

A hidden split protects against copying the answers. It does not protect against learning the answers one query at a time. If the loop returns a precise score for each candidate, the score is an oracle, and an agent can use it as one. The toy below has a private split of 40 binary labels. The agent never sees them. It can submit an answer sheet and receive the accuracy. It flips one answer at a time and keeps the flip if accuracy rises.

"""A private split leaks if its score is an oracle you may query freely.

The private split has 40 binary labels. The agent never sees them, but may
ask 'what is the accuracy of this answer sheet?'. Flipping one answer at a
time and keeping flips that raise the score recovers every label in about
40 queries. The same sheet scores ~50% on a fresh split.

    python3 oracle_leak.py
"""
import random

rng = random.Random(3)
N = 40
private = [rng.randint(0, 1) for _ in range(N)]
fresh = [rng.randint(0, 1) for _ in range(N)]
acc = lambda sheet, labels: sum(a == b for a, b in zip(sheet, labels)) / N


def climb(budget):
    sheet, queries, best = [0] * N, 1, acc([0] * N, private)
    for i in range(N):                      # flip one answer per query
        if queries >= budget: break
        sheet[i] ^= 1; queries += 1
        s = acc(sheet, private)
        if s > best: best = s
        else: sheet[i] ^= 1
    return sheet, queries


print("queries  private acc  fresh-split acc")
for budget in (1, 5, 20, 41):
    sheet, q = climb(budget)
    print(f"{q:7d}  {acc(sheet, private):11.2f}  {acc(sheet, fresh):15.2f}")
queries  private acc  fresh-split acc
      1         0.47             0.53
      5         0.53             0.53
     20         0.68             0.57
     41         1.00             0.50

With one query the sheet scores 47% on the private split, with five 53%, with twenty 68%, and after 41 queries, one per label plus the first, 100%. On a fresh split drawn from the same process the same sheet scores 50% to 57%: it has memorised the private labels and learned nothing. The score on the private split is now an artifact of the search, not a measurement.

Real tasks leak more slowly than 40 binary labels, but the principle holds, and the defences follow from it:

  1. Return less. The private split decides keep or discard; the agent gets a verdict or a coarse score, not a per-case breakdown.
  2. Budget the queries. Count private evaluations per run and stop at a stated limit, recorded with the result.
  3. Reserve a final test. The last partition in the figure above is opened once, after the search ends. Its score is the one you report.
  4. Refresh when you can. If the private cases can be regenerated (random inputs), draw new ones for each evaluation.
  5. Close side channels. Error messages, stack traces, timing and files in the working directory can all reveal the hidden cases.

Common misconception

“If the agent never sees the test data, the evaluation is safe.” Not seeing the data prevents memorising it directly. It does not prevent the search from fitting it through the score, as the oracle toy shows, and it does not make the private split representative. Hidden tests drawn from the same narrow distribution as the visible ones can still be passed by a specialised solution. KernelBench-Verified (next chapter) hides tests from four different input distributions for this reason. Hidden is necessary; it is not sufficient.

Typed and attested results

Suppose the evaluator runs the private tests and prints “7 of 10 passed” to a log that the loop reads. If the proposer can write to that log, or run code that prints that line, it can author any result it likes. Two ideas fix this.

Typed. A result is not free text. It is a record with a fixed schema: a type (test_result), the hash of the code it refers to, the count passed, the count total. The loop rejects anything that does not parse into that schema. This closes off a whole family of attacks that rely on a clever string being interpreted as a number.

Attested. The evaluator signs the record with a key the proposer never sees, and the loop verifies the signature before it trusts the result. A message authentication code (MAC) is the simplest signature: a short tag computed from the message and a secret key, such that nobody without the key can compute a valid tag for a changed message. HMAC-SHA256 (a keyed hash construction built on the SHA-256 hash function), available in Python's standard hmac module, is the usual choice. Binding the record to the SHA-256 hash of the code also stops the other attack: reusing a genuine “10 of 10” that was earned by a different program.

The idea

  1. evaluator: record ← {type, sha256(code), passed, total}
  2. evaluator: tag ← HMAC(key, canonical JSON of record)
  3. loop: recompute the tag from the received record; compare in constant time
  4. loop: recompute sha256 of the code it is about to keep; compare
  5. accept only if both match
"""A typed, attested test result: the proposer cannot author 'passed'.

The evaluator holds a secret key the proposer never sees. It signs the
result envelope with HMAC-SHA256. The loop accepts a result only if the
signature verifies and the hash of the code matches the code it submitted.

    python3 attest.py
"""
import hashlib, hmac, json

KEY = b"evaluator-only-secret"          # lives outside the proposer's box


# ── 1. The evaluator builds and signs an envelope ─────────────────
def attest(code, passed, total):
    body = {"type": "test_result", "code_sha": hashlib.sha256(
        code.encode()).hexdigest()[:16], "passed": passed, "total": total}
    msg = json.dumps(body, sort_keys=True).encode()
    return {**body, "sig": hmac.new(KEY, msg, "sha256").hexdigest()[:16]}


# ── 2. The loop verifies before it believes ───────────────────────
def verify(env, code):
    body = {k: v for k, v in env.items() if k != "sig"}
    msg = json.dumps(body, sort_keys=True).encode()
    ok_sig = hmac.compare_digest(
        env["sig"], hmac.new(KEY, msg, "sha256").hexdigest()[:16])
    ok_code = body["code_sha"] == hashlib.sha256(code.encode()).hexdigest()[:16]
    return ok_sig and ok_code


code = "def f(a, b): return a + b"
real = attest(code, 7, 10)
forged = {**real, "passed": 10}                   # proposer edits the log
swapped = attest("def f(a, b): return 0", 10, 10)  # result for other code
for name, env in [("genuine", real), ("edited count", forged),
                  ("another program's", swapped)]:
    print(f"{name:18s} passed={env['passed']:2d}/{env['total']}  "
          f"accepted={verify(env, code)}")
genuine            passed= 7/10  accepted=True
edited count       passed=10/10  accepted=False
another program's  passed=10/10  accepted=False

The genuine envelope for 7 of 10 is accepted. Editing the count to 10 changes the message, so the tag no longer matches. Replacing the genuine result with a real “10 of 10” earned by a different program has a valid signature, but the code hash does not match the code being kept, so it is rejected. Note what this does and does not give. It makes the result tamper-evident: you learn that someone changed it. It does not make the tests good, and it does not protect a key that lives in the proposer's reach. With a shared-secret MAC, whoever holds the key can forge, so the key must live only in the evaluator and the verifier, never in the proposer's sandbox. For results that third parties must verify, public-key signatures avoid sharing a secret. Both are developed in A11 Attested Tool Results.

Step through

An attested result, from submission to decision

  1. Submit. The proposer hands over code. It cannot write to the evaluator’s zone or read its files.
  2. Run. The evaluator runs the code against the private cases in its own sandbox.
  3. Type. It builds a record with a fixed schema and the hash of the code that was run.
  4. Sign. It signs the record with a key the proposer never sees, and sends record and tag on.
  5. Verify and decide. The controller recomputes the tag and the code hash. If both match, it applies the keep or discard rule and returns only a verdict to the proposer.

Hacking rate as a metric

A hack is a candidate that scores well without doing the task. You cannot observe the intent, so the metric is built from an observable: the gap between how well a candidate does on the split the proposer could influence and how well it does on a split it could not. The hacking rate of a set of accepted candidates is the fraction whose gap is at least a threshold δ:

This is my definition, in the spirit of SpecBench’s visible-versus-held-out gap. Other papers define the rate differently (as a fraction of kernels judged to be hacks by a checker, for instance), so always state yours. Six candidates, a margin of 0.25, one printed line per build-up step:

The idea

  1. gap ← visible − held-out, for each candidate
  2. flag ← 1 if gap ≥ δ, else 0
  3. H ← (sum of flags) ÷ N
"""The hacking-rate equation on six candidates, one step per line.

rate = (1/N) * sum over candidates of 1[ visible_i - held_out_i >= delta ].

    python3 gap_rate.py
"""
DELTA = 0.25                                   # gap that counts as hacking
# (visible pass rate, held-out pass rate) for six accepted candidates
CANDS = [(1.00, 0.95), (1.00, 0.40), (0.90, 0.85),
         (1.00, 0.10), (0.80, 0.78), (1.00, 0.70)]

gaps = [v - h for v, h in CANDS]
print("gaps visible - held-out:", [round(g, 2) for g in gaps])
flags = [1 if g >= DELTA else 0 for g in gaps]
print("indicator 1[gap >= delta]:", flags)
n = len(CANDS)
print(f"sum = {sum(flags)}, N = {n}, rate = {sum(flags) / n:.2f}")
gaps visible - held-out: [0.05, 0.6, 0.05, 0.9, 0.02, 0.3]
indicator 1[gap >= delta]: [0, 1, 0, 1, 0, 1]
sum = 3, N = 6, rate = 0.50

Three of six candidates have gaps of 0.3 or more, so H = 0.50. Note the 0.30 gap of the last candidate (1.00 visible, 0.70 held out): it is flagged, but is it a hack or just a candidate that does not generalise well? The metric cannot tell. That is why you also inspect flagged candidates by hand, as the KernelBench maintainers recommend for any high-scoring result (next chapter).

Because H is a proportion of N candidates, it has sampling error like any other. With 20 kernels, which is Artifact 3's minimum, an observed H of 0.50 has a 95% Wilson interval of roughly 0.30 to 0.70 (the method is in chapter 05, and the general theory in A6 Statistics for Evals). A before-and-after drop from 0.50 to 0.15 on 20 kernels each is large enough to see; a drop from 0.35 to 0.25 is not.

Choosing what to report

A single score hides the trade-off. A good results table for an artifact has at least these columns, each defined before you run:

ColumnWhat it isWhy it is there
Score on the private final testMean over seeds with an intervalThe number the claim rests on
Score on the public splitSame agent, same runsLets a reader see the gap
Hacking rate H (δ stated)Fraction of accepted candidates flagged, with an intervalSeparates real gains from specialised ones
Private queries usedNumber of scored evaluationsBounds the leak of the oracle toy
BudgetDollars, GPU-hours, stepsThe same for every arm

What goes wrong

  • Splits from one distribution. Private cases that resemble the public ones can be passed by anything that handles the public ones. Vary the generating distribution, not only the instances.
  • A leaky harness. The private cases are in the repository, the checker prints the failing input, or the working directory is readable. Treat every file the agent can list as public.
  • A judge as evaluator. If a model grades the output, the proposer can optimise for the judge’s quirks. See A6 LLM-as-Judge; the private split does not fix a biased judge.
  • Reusing the private split across projects. Each use spends some of its information. Keep a fresh final test, and note that benchmark leakage over time is the subject of A6 Contamination, Saturation & Decay.
  • Treating a flagged gap as proof. A gap is evidence. Read the candidates.

Systems connection

This is the oldest idea in secure systems design, applied to a test harness. The evaluator and its key form a small trusted computing base: the minimum code that must be correct for the security argument to hold, so you keep it small and out of reach. Splitting the proposer, evaluator and controller into separate processes with different permissions is separation of privilege. A signed, hash-bound result is a build provenance attestation: the same shape as a signed software artifact that says which source produced it. And the oracle leak is a side channel, like the timing differences that let an attacker recover a secret from how long a check takes.

Key takeaways

  • A research loop has two principals, a proposer that wants a high score and an evaluator that should measure truth. The evaluator must be outside the proposer’s write boundary, with checker code and private data out of sight.
  • Public splits are for development; only a private split decides what is kept, and a final private test is opened once.
  • A free-to-query score is an oracle: 41 queries recovered all 40 private labels in the toy. Return less, budget queries, keep a final test.
  • Results should be typed and attested: a fixed schema plus a signature bound to the hash of the code. This makes forgery visible, not tests good.
  • Hacking rate H is the fraction of accepted candidates whose visible-minus-held-out gap is at least δ. Report it with an interval, next to every score, and read the flagged candidates.

Check your understanding

An agent finds a candidate with 100% on the visible tests and 40% on the hidden tests. With δ = 0.25, how is it counted in the hacking rate?

  1. Not at all, because it was not accepted
  2. As a half hack, because 40% is partial credit
  3. It is flagged, since the gap of 0.60 exceeds δ
  4. It cannot be known without reading the code
The indicator uses only the gap. The fourth option is partly true (the flag is evidence, not proof) but the question asks how it is counted. There is no “half” flag.

The oracle toy reaches 100% on the private split yet only 50% on a fresh split. What went wrong?

  1. The agent fitted the private labels through repeated score queries, so the private score no longer measures generalisation
  2. The fresh split was too small
  3. The private split was drawn from the wrong distribution
  4. The scoring function had a bug
With a free score oracle, flipping one answer at a time recovers each label. The fresh split has independent labels, so the sheet scores at chance.

A proposer submits a genuine signed result of “10 of 10” that was earned by a different program. Why does the loop reject it?

  1. Its signature is invalid
  2. 10 of 10 is never accepted
  3. The proposer is not allowed to submit results
  4. The code hash inside the record does not match the code being kept
The signature on a genuine record is valid, so the first option is wrong. Binding the record to the hash of the code is what ties the result to the program it describes.

Which change most directly reduces the oracle leak without changing the tests?

  1. Make the private split larger
  2. Return only a verdict or a coarse score, and cap the number of private evaluations
  3. Sign the score with HMAC
  4. Show the agent the failing private cases
The leak is the information in each answer, so return less and limit the queries. Signing prevents forgery but does not reduce information, and showing the failures makes the leak worse. A larger split slows but does not stop the fitting.

You measure H on 20 kernels and get 0.50 before hardening and 0.35 after. What can you conclude?

  1. Hardening cut the hacking rate by 30%, a clear success
  2. Hardening failed
  3. The intervals overlap heavily on 20 kernels, so the evidence for a real drop is weak
  4. The metric is invalid
With N = 20, a proportion has a 95% interval about 0.4 wide, so a 0.15 drop is within noise. It does not show failure either; it shows the sample is too small to tell.

Which design lets the proposer forge a “tests passed” result even though results are signed?

  1. The key is stored only in the evaluator
  2. The record includes the hash of the code
  3. The loop verifies the tag in constant time
  4. The signing key sits in a file in the proposer’s sandbox
A shared-secret signature protects only against parties without the key. The other three are the correct practices.

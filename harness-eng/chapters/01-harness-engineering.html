Harness Engineering as Research

A research agent is a model plus the software that runs its loop: the tools it can call, the context it sees, the files it keeps and the checks on its results. This chapter climbs the ladder from tuning that context, to designing workflows, to a harness that rewrites itself, and asks at each rung what is being optimised and what could go wrong. It places ACE, Meta-Harness, STOP and the Darwin Gödel Machine on the ladder.

Why this matters

This chapter serves Artifact 2 (the mini-FML search study) and gives vocabulary to Artifact 4. In Artifact 2 you will build an agent that searches over experiments, and almost all of its behaviour comes from the harness, not the model: what it is shown after each run, which files it can write, who decides whether an edit is kept. If you cannot say which rung of the ladder your agent sits on, you cannot say what a fair baseline for it is. After this chapter you can name the five things a harness controls, say which of ACE, Meta-Harness, STOP, ADAS and the Darwin Gödel Machine optimises which of them, write the update rule that makes an improver improve itself, and apply a write boundary so that the thing being optimised cannot edit its own scorer. Chapter 02 then builds one concrete rung, AIDE's tree search, in detail.

What a harness is

Ask a language model a question and you get text back. Ask it to fix a bug in a repository and something else has to happen: files must be read, a test command run, the output fed back, a limit enforced, a result judged. All of that is not the model. It is the harness, which Lilian Weng defines in her July 2026 post “Harness Engineering for Self-Improvement” as the system surrounding a base model that orchestrates execution: how the model plans and thinks, calls tools, manages context, stores artifacts and evaluates results. Claude Code and Codex are harnesses in this sense.

Chapter A4 Tool Calling: The Agent Loop built the smallest harness: a loop that calls the model, runs the tools it asks for and feeds the results back. Weng's point is that a modern harness is more than that loop. Compared with the early “agent = model + memory + tools + planning” picture, it adds workflow design, evaluation, permission controls and persistent state. It is closer to a small operating system than to a prompt template. She names three patterns that recur:

  1. Workflow automation. A goal-directed loop: plan, execute, observe or test, improve, run again, with the agent reading its own earlier attempts. Karpathy's autoresearch repository, the loop Artifact 1 rebuilds, is her example.
  2. The file system as memory. Durable state (experiment logs, diffs, error traces) lives in files, not in the context window, and is read back with shell commands such as grep and cat.
  3. Sub-agents and background jobs. Parallel workers and long-running jobs, with a small process manager to launch, inspect, cancel and merge them, so the main context is not flooded.

For a coding agent, the tools fall into groups: file-system tools (glob, grep, read, edit, apply a patch), a shell, git, external context (tool servers and skills), web search, background jobs and delegation to sub-agents. Everything in the lists above is something an outer process could change. That is the idea of this chapter: if the harness controls the behaviour, then improving the harness is a way to improve the agent without touching the model's weights.

Analogy: the lab around the scientist

Think of a researcher as the model and the laboratory as the harness. The lab decides which instruments are on the bench, which papers are in the library, how the notebook is organised, who signs off on a result, and which doors are locked. Two equally able scientists produce very different work in a well-run lab and a chaotic one. Improving the lab (a better notebook system, a rule that every claim needs a control) improves the science without changing the scientist.

Where it breaks down: a real lab is rebuilt by people, slowly, and the scientist does not read the building's blueprints. In a self-improving harness the thing that rewrites the lab can be the lab's own occupant, which is how it ends up editing the sign-off rule that judges it.

The ladder

Weng orders the things you can optimise by how much of the harness they cover: instruction prompts, then structured context, then workflows, then harness code, then optimiser code. Each step up gives the optimiser a larger search space and more ways to go wrong, and she notes that more capable models make the higher rungs usable with more generic methods. I use four rungs by merging the first two, because the methods are the same kind of thing.

Two questions separate the rungs and recur through the chapter. What is the object being edited? (text, a graph of steps, source files, the editor itself). What decides whether an edit is kept? (a score on tasks, a held-out split, a person). The second question is the one that decides whether the result can be trusted, and it is the subject of chapter 03.

Rung 1: context as a playbook (ACE)

The cheapest thing to optimise is what the model reads. Context engineering is the practice of choosing what goes into the context window: instructions, examples, notes from earlier attempts, retrieved facts. A4 Context Engineering treated context as a budget; here the question is whether a program can improve the context itself, run after run, from feedback.

The Agentic Context Engineering method (ACE; Zhang et al., 2025, accepted at ICLR 2026) treats the context as an evolving playbook of accumulated strategies. The paper names two failures of earlier methods. Brevity bias is the tendency of a rewriting model to drop domain detail for a shorter summary. Context collapse is the erosion of detail when a context is rewritten again and again, so that each pass keeps a little less of what the last one knew. ACE's remedy is a modular loop of generation, reflection and curation with structured, incremental updates. In Weng's description there are three roles: a generator that produces trajectories, a reflector that distils insights from successes and failures, and a curator that makes itemised updates, each a bullet with an identifier that is merged by deterministic code rather than by asking a model to rewrite everything.

You can see why that matters with a toy. Suppose each reflection round finds one new lesson, and a whole-context rewrite loses any given old bullet with a small probability. The loss rate below is an assumption I chose, not a measured number from the paper; the point is the shape of the curve.

The idea

  1. playbook ← empty; for 30 rounds a new lesson arrives
  2. rewrite: every old bullet survives this round with probability 0.95, then add the lesson
  3. delta merge: add the lesson by id if absent; touch nothing else
  4. repeat over 200 seeds; count bullets kept
"""Why ACE edits a context in small deltas instead of rewriting it.

A toy model: each round a reflector finds one new lesson. Strategy A asks
the model to rewrite the whole playbook, and each rewrite loses an old
bullet with probability P_LOSS (an ASSUMPTION, not a measured rate).
Strategy B appends a new bullet with an id and never touches old ones.

    python3 playbook.py
"""
import random

ROUNDS = 30          # reflection rounds
P_LOSS = 0.05        # chance a full rewrite drops any one old bullet
SEEDS = 200          # repeat the toy run to average out luck


# ── 1. Two ways to update a playbook ──────────────────────────────
def rewrite(playbook, lesson, rng):
    """Whole-context rewrite: every old bullet may be lost."""
    kept = [b for b in playbook if rng.random() > P_LOSS]
    return kept + [lesson]


def delta_merge(playbook, lesson, rng):
    """Itemised update: add by id, deduplicate, never edit old ones."""
    return playbook if lesson in playbook else playbook + [lesson]


# ── 2. Run both for ROUNDS rounds and count surviving lessons ─────
def run(update, seed):
    rng = random.Random(seed)
    playbook = []
    for r in range(ROUNDS):
        playbook = update(playbook, f"lesson-{r}", rng)
    return len(playbook)


for name, fn in [("rewrite", rewrite), ("delta merge", delta_merge)]:
    sizes = [run(fn, s) for s in range(SEEDS)]
    mean = sum(sizes) / SEEDS
    print(f"{name:12s} lessons kept of {ROUNDS}: {mean:5.1f} "
          f"(min {min(sizes)}, max {max(sizes)})")
exp = sum((1 - P_LOSS) ** (ROUNDS - 1 - r) for r in range(ROUNDS))
print(f"expected for rewrite: {exp:.1f}")
rewrite      lessons kept of 30:  15.7 (min 8, max 21)
delta merge  lessons kept of 30:  30.0 (min 30, max 30)
expected for rewrite: 15.7

The rewrite loses about half the lessons in 30 rounds (the last line is the exact expectation, the sum of 0.95 to the power of each lesson's age, and the simulation agrees with it). Delta merging keeps all 30. A rewrite loses a few percent per round and compounds; a merge cannot lose what it never touches. That compounding is the same arithmetic as the compounding error in A4 chapter 00.

The paper reports gains of 10.6% on agent benchmarks and 8.6% on finance benchmarks, lower adaptation latency and rollout cost, and on the AppWorld leaderboard a match with the top-ranked production agent on the overall average using a smaller open model. These are the authors' numbers on their benchmarks; they say little about your task. Weng also notes ACE's limit: its update rules and workflow remain handcrafted, so the method of improving context is not itself being improved. A later method, Meta Context Engineering (Ye et al., 2026, as Weng summarises it), separates the mechanism of managing context from its content and searches over the mechanism with a two-level loop.

Rung 2: workflows as a search problem

A workflow fixes the order of steps in code and lets the model fill in each step (the definition from A4 chapter 00). Experts can write one by hand. The rung-2 idea is to treat the workflow as something to be searched.

  • ADAS (Automated Design of Agentic Systems; Hu et al., 2025) has a meta-agent write new agents as code, keep the good ones in an archive and use them as stepping stones. A7 Automated Design of Agentic Systems covers it in full, so I will not repeat it.
  • AFlow (Zhang et al., 2025) writes a workflow as a graph whose nodes are model calls and whose edges are code logic, and searches that space with Monte Carlo tree search (A7 chapter 01), stopping when the average of the top candidates plateaus or the budget runs out. Weng reports that it beats manual workflows and ADAS on question answering, code and maths.
  • The AI Scientist pipeline (Lu et al., 2026, published in Nature) fixes a workflow for idea generation, code, experiments, analysis, writing and review. It is the example of an expert-designed workflow at full scale.

The shared idea: the search space is graphs or programs, and the score is a benchmark result. The shared risk: if the benchmark leaks into the choice of workflow, you have overfitted the workflow to the benchmark. A7 Held-Out Evaluation for Self-Improvers explains the separate search, selection and test sets that guard against it.

Rung 3: the harness is code

The next idea is that a harness is just a program, and an LLM can edit programs. A harness is code that programs prompts, tool calls, sub-agents, control flow and memory. If the search space is source code, it is far larger than a set of prompts, and also far harder to inspect.

Meta-Harness: search the code that manages context

Meta-Harness (Lee et al., submitted 30 March 2026) optimises “the code that decides what information is stored, retrieved and shown to the model”, in Weng's phrasing. Its abstract says existing text optimisers compress feedback too aggressively, so its proposer is an agentic coding model that reads the source code, scores and execution traces of all earlier candidates through a file system rather than receiving a summary. Each candidate harness is a directory. The abstract reports a 7.7 point improvement over a state-of-the-art context-management system on online text classification while using four times fewer context tokens, a 4.7 point average gain on 200 IMO-level maths problems across five held-out models, and that discovered harnesses beat the best hand-engineered baselines on TerminalBench-2 (no number given in the abstract). These are the authors' figures.

Step through

One iteration of an outer harness-search loop (Meta-Harness style)

  1. Read. The proposer does not get a summary. It explores the archive with ordinary shell commands, so it can look at exactly the traces it thinks matter.
  2. Propose. It writes a new candidate harness as a directory of source files.
  3. Run. The evaluator runs the candidate on tasks. The evaluator is not in the proposer's write boundary: it cannot edit the scoring code.
  4. Store. Score, cost and full traces are written into the archive next to the code that produced them.
  5. Update. The Pareto frontier (candidates not beaten on both score and cost) is recomputed, and the next iteration begins.

Darwin Gödel Machine: the agent edits itself

The Darwin Gödel Machine (DGM; Zhang et al., 2025) closes the loop: the harness being optimised is the same repository the optimiser runs. It keeps an archive of coding agents, samples one, asks a foundation model to write a modified version of that agent's own code, and tests the change on coding benchmarks instead of trying to prove it helps. With Claude 3.5 Sonnet (the model named in Weng's summary) the authors report SWE-bench performance rising from 20.0% to 50.0% and Polyglot from 14.2% to 30.7%, and better results than baselines without self-improvement or open-ended exploration, with sandboxing and human oversight as safety measures. A7 Self-Improving Agents and the surrounding chapters treat it in depth.

Self-Harness and AHE: what to edit and what to freeze

Two 2026 papers, which I know only through Weng's summary and did not read, focus on the practicalities. Self-Harness (Zhang et al.) mines a model's failures on a benchmark for recurring patterns, proposes bounded harness edits for those patterns, and accepts an edit only if it causes no regression on held-in and held-out splits. Agentic Harness Engineering (Lin et al.) argues the bottleneck is observability, and splits the harness into seven editable components (system prompt, tool description, tool implementation, middleware, skill, sub-agent configuration, long-term memory), each mapped to a file, so each failure pattern maps to one component. Each edit is recorded as a falsifiable prediction, and the run records, tracer, verifier and model configuration are read-only, which Weng says blocks hacks such as disabling the verifier or swapping the model.

That last design choice is the one to carry into your own artifacts, so here it is in code. The harness is a directory. Some paths are editable surfaces; the rest, including the scorer, are not. A proposed patch is checked before it is applied.

The idea

  1. EDITABLE ← prompts/, tools/, skills/, memory/
  2. for each path in the patch: reject if absolute or if it contains ".."
  3. reject if the path does not start with an editable prefix
  4. accept only if no path was rejected
"""A write boundary for a self-editing harness, in 30 lines.

The harness is a directory. Some paths are editable surfaces, the rest
(evaluator, verifier, run logs, model config) are read-only. A patch is
refused if it touches anything outside the editable surfaces.

    python3 boundary.py
"""
from pathlib import PurePosixPath

EDITABLE = ["prompts/", "tools/", "skills/", "memory/"]   # the proposer's
READ_ONLY = ["eval/", "verifier/", "runs/", "config/model.json"]


# ── 1. The check: normalise first, then compare ────────────────────
def allowed(path):
    p = PurePosixPath(path)
    if p.is_absolute() or ".." in p.parts:       # no escaping the root
        return False
    s = str(p)
    return any(s.startswith(e) for e in EDITABLE)


def review(patch):
    bad = [p for p in patch if not allowed(p)]
    return ("ACCEPT", []) if not bad else ("REJECT", bad)


# ── 2. Try three patches ──────────────────────────────────────────
patches = {
    "adds a skill + edits a prompt": ["skills/retry.md", "prompts/system.md"],
    "also disables the verifier": ["prompts/system.md", "verifier/run.py"],
    "path trick to reach eval": ["tools/../eval/score.py"],
}
for name, patch in patches.items():
    verdict, bad = review(patch)
    print(f"{verdict:6s} {name:32s} {bad}")
ACCEPT adds a skill + edits a prompt    []
REJECT also disables the verifier       ['verifier/run.py']
REJECT path trick to reach eval         ['tools/../eval/score.py']

The third patch is the instructive one. A naive prefix check on tools/../eval/score.py would pass, since the string starts with tools/. The check has to refuse paths that climb out of the directory, or normalise them first. In a real system this check is not code the proposer could also edit: it lives in a separate process with its own permissions, which is the subject of A11 The Threat Model of a Research Loop.

Rung 4: the improver improves itself (STOP)

On the first three rungs there is an optimiser that edits a target. The top rung asks what happens when the optimiser is also the target. STOP, the Self-Taught Optimizer (Zelikman et al., submitted October 2023, COLM 2024), starts with a seed improver: a program that takes a solution and a utility function, asks a language model for several improved versions and returns the best. The seed improver is then run on its own code, producing a better improver. The paper reports that the improved improver generates better programs than the seed on a small set of downstream tasks, that the model proposed strategies such as beam search, genetic algorithms and simulated annealing, and that the model's weights are never changed, so, in the authors' words, this is not full recursive self-improvement. Weng adds a caveat from the paper's experiments: the gains held with GPT-4 but degraded with weaker models, so the base model must be capable enough to propose useful edits.

The mechanism is one equation. An improver I is scored by its meta-utility, the average utility it reaches over a set of tasks. Then I is applied to itself, using meta-utility as the utility to maximise. I write it in the simplified notation of Weng's summary; the paper's own symbols differ a little.

Here are the first four steps with made-up numbers, three tasks and three improvers. The script prints one line per improver for the average, then picks the winner.

The idea

  1. for each improver: list the utility it reached on each task
  2. meta-utility ← sum ÷ number of tasks
  3. the improver with the highest meta-utility becomes the next I
"""STOP's meta-utility on three improvers and three tiny tasks.

meta_utility(I) = mean over tasks of utility(I applied to the task).
Utilities here are made-up scores in [0, 1] that each improver reached.

    python3 meta_utility.py
"""
# ── 1. Utility each improver reached on each of three tasks ───────
SCORES = {
    "I_0 (seed: one try)":        [0.40, 0.55, 0.30],
    "I_1 (best of 4 tries)":      [0.62, 0.70, 0.51],
    "I_2 (4 tries + restart)":    [0.66, 0.69, 0.74],
}

# ── 2. Average across tasks: that average IS the meta-utility ─────
for name, scores in SCORES.items():
    total = sum(scores)
    print(f"{name:26s} sum {total:.2f} / {len(scores)} tasks "
          f"= meta-utility {total / len(scores):.3f}")

# ── 3. The self-referential step: the improver is graded by this
#       number, so the improver that gets higher meta-utility wins ──
best = max(SCORES, key=lambda k: sum(SCORES[k]))
print("kept as the next improver:", best)
I_0 (seed: one try)        sum 1.25 / 3 tasks = meta-utility 0.417
I_1 (best of 4 tries)      sum 1.83 / 3 tasks = meta-utility 0.610
I_2 (4 tries + restart)    sum 2.09 / 3 tasks = meta-utility 0.697
kept as the next improver: I_2 (4 tries + restart)

Now let the improver improve itself, in a toy where I can run the whole loop. A “program” is a vector of four numbers; the “language model” is random perturbation; an improver is a pair (k, step): try k random perturbations of the current solution and keep the best. Its meta-utility is how close it gets to each task's hidden target in six rounds, averaged over 20 tasks. To improve itself, the improver perturbs its own settings (using its own k as the number of tries) and keeps what raises meta-utility on the 20 training tasks. A second set of 20 tasks is never used for choosing, only for reporting.

"""A toy of STOP: an improver that is applied to its own settings.

Programs are vectors; the 'language model' is random perturbation. The
improver has two settings (k candidates, step size). The meta-utility of
an improver is the average utility it reaches over a set of tasks.

    python3 stop_toy.py
"""
import random

DIM, ROUNDS = 4, 6        # solution size; improvement rounds per task
TRAIN, HELD = 20, 20      # tasks used to score improvers / never used


def make_tasks(n, seed):
    rng = random.Random(seed)
    return [[rng.uniform(-3, 3) for _ in range(DIM)] for _ in range(n)]


def utility(x, target):                       # higher is better, max 0
    return -sum((a - b) ** 2 for a, b in zip(x, target))


# ── 1. An improver is a setting pair; applying it = best of k tries ─
def improve(x, util, params, rng):
    k, step = params
    cands = [x] + [[v + rng.gauss(0, step) for v in x] for _ in range(k)]
    return max(cands, key=util)


# ── 2. Meta-utility: mean utility an improver reaches across tasks ─
def meta_utility(params, tasks, seed):
    rng, total = random.Random(seed), 0.0
    for target in tasks:
        x = [0.0] * DIM
        for _ in range(ROUNDS):
            x = improve(x, lambda c: utility(c, target), params, rng)
        total += utility(x, target)
    return total / len(tasks)


# ── 3. Self-improvement: the improver improves its own settings ───
def improve_improver(params, tasks, seed, rng):
    best, best_u = params, meta_utility(params, tasks, seed)
    for _ in range(params[0]):                # it uses its OWN k
        k = max(1, best[0] + rng.choice([-1, 0, 1, 2]))
        step = max(0.05, best[1] * rng.choice([0.5, 0.8, 1.0, 1.25]))
        u = meta_utility((k, step), tasks, seed)
        if u > best_u:
            best, best_u = (k, step), u
    return best


train, held = make_tasks(TRAIN, 1), make_tasks(HELD, 2)
rng = random.Random(0)
I = (1, 0.1)                                   # seed improver I_0
for t in range(5):
    print(f"I_{t}: k={I[0]:2d} step={I[1]:.2f}  "
          f"train {meta_utility(I, train, 9):7.3f}  "
          f"held-out {meta_utility(I, held, 9):7.3f}")
    I = improve_improver(I, train, 9, rng)
I_0: k= 1 step=0.10  train -10.701  held-out -10.339
I_1: k= 3 step=0.12  train  -7.724  held-out  -8.112
I_2: k= 6 step=0.20  train  -5.541  held-out  -5.122
I_3: k= 7 step=0.16  train  -5.482  held-out  -5.561
I_4: k=10 step=0.24  train  -2.464  held-out  -2.788

Utilities are negative squared distances, so closer to zero is better. The improver climbs from k=1 to k=10 and the held-out score improves with it (−10.3 to −2.8), so this improvement was not just fitting the 20 training tasks. Three honest caveats. This is a toy where “more tries” is the obvious improvement and a few lines of code can find it. The improver was allowed to use more compute per call as it improved, so some of the gain is simply a bigger budget, which is exactly why Artifact 2 insists on a baseline with the same budget. And I ran it once with one seed. The real STOP result depends on a capable model and was reported on a small set of tasks.

Common misconception

“A self-improving harness means the model is getting smarter.” In every system on this ladder the model's weights are fixed. What changes is the context, the workflow or the code around it. The distinction matters for what you measure: a gain from a better harness may disappear if you swap the model. Weng cites a 2026 paper (Lin et al., arXiv 2605.30621, which I did not read) that separates harness-updating (can a model make useful edits?) from harness-benefit (can a model make use of the edited harness?), and reports that mid-tier models benefited most. So report the model next to every harness result, and do not assume a harness found with one model transfers to another.

What makes this research and not tinkering

Each rung needs a loop, a score and a rule for keeping an edit. The risks are in the score and the rule, and Weng's list of open problems names them: weak or fuzzy evaluators, context and memory that drift, diversity collapse (loops exploit known high-reward patterns), reward hacking such as overfitting to unit tests, judge-specific tricks or benchmark artifacts, and short-term metrics that miss maintainability. Her recommendation is the one this course is built on: evaluators and permission control should sit outside the evolving loop.

This turns into four checks you can apply to any claim that a harness improved something:

  1. Is there a baseline with the same budget? A harness that makes ten model calls per step has an advantage over one that makes one.
  2. Is the score on data the loop never saw? Selection on the same tasks used to report is the standard way to inflate a gain (A7 chapter 16).
  3. Can the proposer write to the scorer? If yes, the score tells you about the proposer's ability to edit scorers.
  4. Does it hold across seeds and models? Three seeds is the floor; chapter 02 shows what three seeds can and cannot detect.

Systems connection

A self-editing harness is a continuous-deployment pipeline whose author is a program. The ordinary rules apply, with higher stakes. The code that runs the tests must not be writable by the change under test (separation of duties), logs should be append-only so a change cannot rewrite its own history, and rollback must be cheap because most proposed changes are wrong: in Weco's AIDE² run, about nine in ten proposed changes were rejected. Treat each candidate as untrusted code and run it in a sandbox, as in A4 Sandboxes & Permissions.

Key takeaways

  • A harness is the software around the model: workflow, tools, context, files and checks. Changing it changes behaviour without changing weights.
  • The ladder runs from context (ACE), to workflow (ADAS, AFlow), to harness code (Meta-Harness, Self-Harness, DGM), to the improver itself (STOP). Each rung enlarges the search space and the room to cheat.
  • Incremental, itemised updates avoid the compounding loss of whole-context rewrites.
  • STOP's update is It = It−1(ū, It−1; M): the improver is scored by meta-utility and applied to itself.
  • The scorer, verifier, logs and model configuration belong outside the proposer's write boundary.
  • Check every harness-improvement claim for a same-budget baseline, unseen data, a protected scorer and several seeds.

A rewrite can drop any old bullet each time, so survival decays geometrically (0.95 per round gives about half after 30 rounds in the toy). Unbounded growth is the opposite problem. Weights are never touched in any of these systems.

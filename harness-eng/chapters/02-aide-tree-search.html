Tree Search over Experiments: AIDE

AIDE treats machine-learning engineering as a search over programs: every candidate script is a node, every attempt to fix or improve it is an edge, and a hand-written rule decides which node to extend next. This chapter derives that rule with numbers, builds it on a toy you can run, and asks the question Artifact 2 is built around: when does a tree beat a plain greedy hill-climber?

Why this matters

This chapter is the mechanism behind Artifact 2. Its gate asks for paired results, with confidence intervals, from an AIDE-style tree-search agent against greedy hill-climbing on three FML-Bench tasks, so you need to know exactly what the tree adds, what it costs, and what a fair comparison looks like. Lab 1: Greedy versus Tree Search has you write the search policy; the workbench runs it against a real task. After this chapter you can write AIDE's selection rule from memory, explain why a greedy hill-climber nearly matches it in the FML-Bench study, define opportunity density and compute it from a run's log, and say why three seeds cannot settle the question on their own.

Research as a search over programs

Building a machine-learning model is trial and error: try a model, look at the validation score, change something, try again. A person does this at a rate of a few attempts a day. An agent can do it hundreds of times, if something decides what to try next. AIDE (AI-Driven Exploration in the Space of Code; Jiang et al., submitted February 2025) frames this as code optimisation. Each candidate solution is a single Python script. The agent runs it, reads the validation metric and decides what to do.

That makes the space of candidates a tree. The root is an empty solution. A node is a script together with its result. An edge is one attempt to change a script: the child is what the language model wrote after seeing the parent. If you have met search trees before, this is the same data structure as in A7 Tree Search, Bandits & MCTS, with one difference that matters: expanding a node costs a real training run, so the budget is in the tens or hundreds of expansions, not millions. At that scale the choice of which node to expand is a large part of the whole method.

The three operators

In the AIDE paper the language model acts as a coding operator with three modes. Each takes the parent script (or nothing) and returns a new script:

Draft
Write a solution from scratch, from the task description. The model outlines a brief plan (for example, a model architecture or a feature idea) and writes the script. Drafts are how the tree gets its roots.
Debug
Take a script that crashed or produced no valid metric, along with its error log, and fix it while keeping the overall approach. Typical faults: a broken import, a tensor of the wrong shape.
Improve
Take a working script and make one atomic change, such as switching the optimiser or adding regularisation. The change is kept small on purpose, so that its effect on the metric can be attributed to it.

After each run, the system has to decide whether the script worked. In the reference implementation (the open-source aideml repository, MIT licence), a language-model review step reads the output and returns whether there was a bug, a short summary and the metric. A node is marked buggy if the review says so, if the script raised an exception, or if no valid number was extracted. A buggy node is given the worst possible metric value, which keeps it out of the “best node” ranking without deleting it. The code comments note an easy bug: NaN would otherwise pass a check that the metric is a float.

The prompts do not contain the whole tree. The paper replaces the full history with a summary of it: performance metrics, hyper-parameter settings that were tried, and debugging hints such as shape mismatches, plus a static preview of the data (row counts, column names). This keeps the prompt short enough to afford a hundred steps, and it is rung 1 of chapter 01's ladder: a context-engineering choice inside a search algorithm.

The search policy

Now the part that makes it a tree search: how to pick the next parent. The paper describes the policy as a hard-coded rule, not a learned one. The reference code makes it exact. In words, a function search_policy() does the following each step:

  1. If fewer than num_drafts draft nodes exist, return nothing, which means “write a new draft”.
  2. With probability debug_prob, look for buggy leaf nodes whose debug depth is below max_debug_depth. If there are any, return one chosen at random: it will be debugged.
  3. If there are no working nodes at all, draft again.
  4. Otherwise return the best node so far: it will be improved.

Step 4 is the most important line. The policy extends the best node, always. There is no exploration bonus and no random choice among good nodes (compare the UCB rule of A7 chapter 01, which adds a term for nodes tried rarely). The “tree” records the attempts, but the improve step is greedy over the whole tree. What distinguishes AIDE from a simple hill-climber is therefore (a) several independent drafts at the start, so the climb begins from more than one place, and (b) a debug path, so a crash costs a repair rather than a restart. This is my reading of the policy as the code expresses it; the paper itself does not give the number of initial drafts, the debug depth or the debug probability.

Step through

One AIDE step: which operator runs?

  1. Drafting phase. While the journal holds fewer than num_drafts draft nodes, the policy returns “no parent” and a fresh draft is written.
  2. Debug check. With probability debug_prob, if a buggy leaf with debug depth under max_debug_depth exists, one is chosen at random to be repaired.
  3. Greedy improve. Otherwise the best working node is returned, and one atomic change is made to it.
  4. Execute. Whichever operator ran, the new script is run and its output captured.
  5. Review. A model-written review extracts the metric or flags a bug, and the node joins the journal. The next step starts from the updated journal.

State of play, October 2026: what the README says

The aideml README (page read in October 2026) lists agent.steps (default 20), agent.search.num_drafts (default 5), and separate models for writing code (default o4-mini) and for reviewing execution (default gpt-4.1-mini), with provider overrides for OpenAI, Anthropic, Gemini and OpenRouter. It does not list debug_prob or describe draft, debug and improve as named modes; those are in the source. Defaults change between releases, so read the version you install.

What it bought: the MLE-bench numbers

In the AIDE paper, the headline evidence is MLE-bench (Chan et al., 2024), a benchmark of 75 Kaggle competitions (chapter 05). With o1-preview as the model, AIDE earned some medal in 16.9% of competitions, with a standard error of 1.1 points (this is the “any medal” column, one attempt per competition). With GPT-4o it earned a medal in 8.7%, while OpenHands, a general coding-agent harness, earned 4.4%. The authors read this as nearly four times as many medals as OpenHands. On the 22-competition Lite subset, they report that o1-preview with AIDE medals on 36.4% of competitions, against 7.6% without the AIDE scaffold, and that the valid-submission rate rises from 63.6% to 92.4%. On METR's RE-Bench, the paper says AIDE outperformed humans within the six-hour limit and found a Triton-based solution on the Optimize a Kernel task faster than any of nine human experts did; it fell short on a Rust task, where it tended to repeat local patches.

Read these as the authors' results for one agent, run with their budget, against baselines they chose. They tell you that the scaffold matters a great deal: the same underlying model gets several times more medals with it. They do not tell you which part of the scaffold matters, which is what the next study isolates.

When does a tree beat greedy? The FML-Bench study

FML-bench (Zou et al., submitted 17 May 2026, revised 29 May 2026) is a controlled comparison of research-agent strategies. It has 18 fundamental machine-learning tasks across 10 areas (causality, continual learning, data efficiency, fairness, federated learning, generalisation, privacy, representation learning, robustness and unlearning). Its design removes everything except the search strategy: every agent is ported to one shared interface, the same language model (GPT-5.4 in the paper), 100 optimisation steps per run, three independent rounds per agent and task, and a 40-minute limit on each validation run on one A100-80GB. That is 324 runs for the six baseline agents (the authors' own AdaptiveSearch is added on top), with each run scored on a test metric the agent never sees.

The paper's agents differ in strategy. Autoresearch is the greedy hill-climber: it “retains each code modification only when it strictly improves the validation metric”. AIDE is the tree search you just read. AIRA uses Monte Carlo tree search with the UCT rule. OpenEvolve is population-based evolutionary search. The AI Scientist v1 runs independent linear chains from a batch of ideas, and v2 runs a best-first tree search over research stages. The authors add their own AdaptiveSearch, which is greedy until progress stalls and then branches.

The paper's first finding: a simple greedy hill-climber nearly matches the best-performing tree-search agent, and both clearly outperform the rest. The score here is a normalised improvement. For a higher-is-better metric it is the agent's gain over the task's baseline, divided by the range between the best and worst possible scores, floored at zero, so tasks with different scales can be averaged:

p̂ = max(0, (pagent − pbase) / |pbest − pworst|)

For a lower-is-better metric the numerator is negated. A gain from 0.70 to 0.74 on a task whose scores run from 0.50 to 0.90 is 0.04 / 0.40 = 0.10. The convention matters for your own write-up: normalise before averaging across tasks, and say how.

Common misconception

“Greedy matching tree search means search does not matter.” The study does not say that. All of its agents get the same model, interface and budget, and all of them beat the baseline; the finding is about how much extra structure pays on top of a greedy loop at 100 steps. Notice also that the same paper reports a clear ranking within kinds of task, which the next section covers. And one caveat belongs to the authors: they note that removing subsystems uniformly may underestimate an agent's performance relative to its original full configuration, and that the Autoresearch port was rewritten into explicit control flow. A result about ported agents is not a result about the original products.

Opportunity density

The paper's second finding is the one Artifact 2 builds on. Greedy search tends to do better when improvement opportunities are dense, meaning small code changes have a good chance of raising the metric. Tree and evolutionary strategies tend to do better when opportunities are sparse: most changes fail, and the agent needs structurally different approaches. An adaptive agent that starts greedy and branches when it stalls beat all six others on average.

The paper makes the idea measurable. For each run it computes an opportunity density φopp from the log of steps. For step k, let impk be the normalised improvement the step produced and dk how far the step moved in code-embedding space (the paper uses GraphCodeBERT embeddings of code snapshots). Then, summing over steps with impk > 0 and writing dmax for the largest move in the run:

Here it is on two made-up runs from one baseline. Run A makes many small, nearby improvements. Run B wanders and makes one big gain far away. The printed lines follow the build-up steps above.

The idea

  1. d_max ← the longest step in the run
  2. keep only steps with imp > 0
  3. weights ← each kept step's d / d_max
  4. φ ← (sum of imp) ÷ (sum of weights)
"""FML-bench's opportunity density, one build-up step per printed line.

phi_opp = sum(imp_k) / sum(d_k / d_max), over steps with imp_k > 0.
imp_k is a step's normalised improvement; d_k is how far (in code
embedding space) it moved; d_max is the largest move in the run.

    python3 density_eq.py
"""
# ── 1. Two runs from one baseline: (imp_k, d_k) for each step ──────
# Run A: many small gains close by.  Run B: one big gain far away.
RUNS = {
    "A": [(0.02, 0.1), (0.03, 0.1), (0.01, 0.2), (0.02, 0.1), (0.0, 0.3)],
    "B": [(0.0, 0.9), (0.0, 0.8), (0.05, 1.0), (0.0, 0.7), (0.01, 0.9)],
}

for name, steps in RUNS.items():
    # ── 2. Keep only the steps that improved ──────────────────────
    d_max = max(d for _, d in steps)
    gains = [(imp, d) for imp, d in steps if imp > 0]
    print(f"run {name}: {len(gains)} improving steps of {len(steps)}, "
          f"d_max = {d_max}")
    # ── 3. Cost of each gain: distance as a share of the longest move
    w = [d / d_max for _, d in gains]
    print("  weights d_k/d_max:", [round(x, 2) for x in w])
    # ── 4. Numerator, denominator, ratio ─────────────────────────
    num, den = sum(i for i, _ in gains), sum(w)
    print(f"  sum imp = {num:.2f}  sum weights = {den:.2f}  "
          f"phi_opp = {num / den:.3f}")
run A: 4 improving steps of 5, d_max = 0.3
  weights d_k/d_max: [0.33, 0.33, 0.67, 0.33]
  sum imp = 0.08  sum weights = 1.67  phi_opp = 0.048
run B: 2 improving steps of 5, d_max = 1.0
  weights d_k/d_max: [1.0, 0.9]
  sum imp = 0.06  sum weights = 1.90  phi_opp = 0.032

Run A has nearly twice the density of run B (0.048 against 0.032), even though its total gain (0.08) is only a little higher than B's (0.06). That is the point of dividing by distance: a run in which every gain needs a long jump is in a sparse region. The paper then splits the 18 tasks at the median density (0.1315) into nine dense and nine sparse tasks. The split is post hoc: it measures what agents actually found, not what was available in advance. Dense tasks include unlearning, ART (adversarial robustness) and PrivacyMeter; sparse tasks include EasyFSL (few-shot learning), the OfficeHome domain-generalisation task and OpenOOD.

The results by group are the evidence for the second finding. On the dense half, the greedy Autoresearch has the highest mean test improvement (0.349) with AdaptiveSearch close behind (0.345). On the sparse half, AdaptiveSearch leads (0.071), followed by the AI Scientist v2 (0.067, a tree search) and OpenEvolve (0.062), while Autoresearch falls to sixth of seven agents (0.035). The appendix calls this the largest rank inversion in the suite and says AdaptiveSearch is the only agent in the top two on both halves.

Reproducing the effect on a toy

You cannot rerun FML-Bench in a chapter, but you can see the mechanism in a landscape where you control the density. The toy below uses an NK landscape, a standard model of rugged search spaces: a solution is N binary design choices, and each choice's contribution depends on K other choices. With K = 0 the choices are independent, so improving one choice at a time works well (dense). With larger K the choices interact, good moves are rare, and one-flip hill-climbing gets stuck on local peaks (sparse).

Three agents get exactly 80 evaluations on each landscape. Greedy flips one choice and keeps it only if the score rises. AIDE-style follows the policy above: 4 drafts, then debug a crashed node with probability 0.5 (25% of scripts crash) and otherwise improve the best node. Adaptive is greedy but jumps to a fresh draft after 8 steps with no gain, keeping the best score seen anywhere, which is a crude version of AdaptiveSearch. The first column reports the greedy agent's acceptance rate, a simple proxy for opportunity density: the fraction of its proposals that were kept.

"""AIDE's search policy on a toy 'code space', against greedy hill-climbing.

A solution is N binary design choices. Its score comes from an NK
landscape: K = 0 means choices act independently (many one-flip gains,
dense opportunities); larger K means choices interact (gains are rare).
The policy mirrors aideml's search_policy: draft until NUM_DRAFTS, debug a
buggy leaf with probability DEBUG_PROB, else improve the best node.

    python3 tree_toy.py
"""
import random

N, STEPS, NUM_DRAFTS, DEBUG_PROB, P_BUG, W = 14, 80, 4, 0.5, 0.25, 8


def landscape(k, rng):
    """Score = mean of N table lookups; each looks at bit i and k others."""
    nbrs = [[i] + rng.sample([j for j in range(N) if j != i], k)
            for i in range(N)]
    tabs = [{} for _ in range(N)]
    def score(x):
        s = 0.0
        for i in range(N):
            key = tuple(x[j] for j in nbrs[i])
            if key not in tabs[i]:
                tabs[i][key] = rng.random()
            s += tabs[i][key]
        return s / N
    return score


def flip(x, rng):
    y = list(x); y[rng.randrange(N)] ^= 1; return tuple(y)


# ── 1. Greedy hill-climber: keep a change only if it strictly helps ─
def greedy(score, rng):
    x = tuple(rng.randint(0, 1) for _ in range(N)); best = score(x)
    acc = 0
    for _ in range(STEPS - 1):
        y = flip(x, rng); s = score(y)
        if s > best: x, best, acc = y, s, acc + 1
    return best, acc / (STEPS - 1)


# ── 1b. Adaptive: greedy, but branch to a fresh draft when stuck ───
def adaptive(score, rng):
    x = tuple(rng.randint(0, 1) for _ in range(N)); cur = score(x)
    top, stall = cur, 0
    for _ in range(STEPS - 1):
        y = flip(x, rng); s = score(y)
        if s > cur: x, cur, stall = y, s, 0
        else: stall += 1
        if stall >= W:                         # stagnation: new branch
            x = tuple(rng.randint(0, 1) for _ in range(N))
            cur, stall = score(x), 0
        top = max(top, cur)
    return top


# ── 2. AIDE-style tree: nodes, bugs, drafts, debug, improve ────────
def aide(score, rng):
    nodes = []            # [config, metric or None (buggy), debug_depth]
    for _ in range(STEPS):
        drafts = sum(1 for n in nodes if n[3] is None)
        buggy = [n for n in nodes if n[1] is None and n[2] < 3 and not n[4]]
        good = [n for n in nodes if n[1] is not None]
        if drafts < NUM_DRAFTS:
            parent, cfg = None, tuple(rng.randint(0, 1) for _ in range(N))
        elif buggy and rng.random() < DEBUG_PROB:
            parent = rng.choice(buggy); parent[4] = True; cfg = parent[0]
        elif good:
            parent = max(good, key=lambda n: n[1]); cfg = flip(parent[0], rng)
        else:
            parent, cfg = None, tuple(rng.randint(0, 1) for _ in range(N))
        bug = rng.random() < P_BUG
        depth = parent[2] + 1 if parent is not None and parent[1] is None else 0
        nodes.append([cfg, None if bug else score(cfg), depth, parent, False])
    return max(n[1] for n in nodes if n[1] is not None)


if __name__ == "__main__":
    print(" K  accept  greedy  AIDE-tree  adaptive   AIDE-g  adapt-g")
    for k in (0, 2, 4, 8, 12):
        g, a, d, ad = [], [], [], []
        for seed in range(300):
            rng = random.Random(seed)
            sc = landscape(k, rng)
            b, r = greedy(sc, rng); g.append(b); d.append(r)
            a.append(aide(sc, rng)); ad.append(adaptive(sc, rng))
        m = lambda v: sum(v) / len(v)
        print(f"{k:2d}  {m(d):6.3f}  {m(g):6.4f}  {m(a):8.4f}  "
              f"{m(ad):8.4f}  {m(a)-m(g):+7.4f}  {m(ad)-m(g):+7.4f}")
 K  accept  greedy  AIDE-tree  adaptive   AIDE-g  adapt-g
 0   0.090  0.6669    0.6644    0.6596  -0.0025  -0.0073
 2   0.084  0.6989    0.7033    0.7056  +0.0044  +0.0067
 4   0.071  0.7014    0.7012    0.7160  -0.0002  +0.0146
 8   0.050  0.6808    0.6836    0.7035  +0.0028  +0.0227
12   0.037  0.6521    0.6526    0.6845  +0.0005  +0.0323

Read the table carefully, because it is a toy I designed. Acceptance falls from 9.0% of proposals at K=0 to 3.7% at K=12: opportunities get sparser. The AIDE-style policy is within 0.005 of greedy at every K; its debug path and extra drafts neither help nor hurt much, consistent with it being greedy over a tree. The adaptive agent is slightly behind at K=0 (−0.0073) and ahead by 0.0145 at K=4, 0.0227 at K=8 and 0.0323 at K=12. So the sign of “does branching help?” flips with density, as the paper reports. I picked these values of K, and the magnitudes depend on the landscape and the budget; the toy shows the mechanism, not the paper's numbers.

What three seeds can and cannot tell you

The gaps above are small. Whether such a gap is a finding or luck depends on how many independent landscapes, or tasks and seeds, you averaged over. Artifact 2 asks for three seeds minimum on each of three tasks, which is the floor the roadmap sets. Here is what that floor can detect. For each landscape the two agents are run on the same landscape, so we compare them with a paired difference (adaptive minus greedy on that landscape), and build a 95% confidence interval from the mean and spread of the differences using the t distribution, as in A6 Statistics for Evals. I use K=8, where the true gap is positive.

"""Why three seeds is a floor, not a comfort: paired CI on the toy.

For each seed (a landscape) we have a paired difference d = adaptive minus
greedy on the SAME landscape. The 95% interval is mean +- t * s / sqrt(n).

    python3 paired_ci.py        (needs tree_toy.py in the same folder)
"""
import random
from statistics import mean, stdev
from tree_toy import landscape, greedy, adaptive

K = 8
T95 = {3: 4.303, 10: 2.262, 30: 2.045, 300: 1.968}   # two-sided t values


def diffs(seeds):
    out = []
    for s in seeds:
        rng = random.Random(s)
        sc = landscape(K, rng)
        out.append(adaptive(sc, rng) - greedy(sc, rng)[0])
    return out


for n in (3, 10, 30, 300):
    d = diffs(range(1000, 1000 + n))
    half = T95[n] * stdev(d) / n ** 0.5
    lo, hi = mean(d) - half, mean(d) + half
    print(f"n={n:3d}  mean diff {mean(d):+.4f}  95% CI [{lo:+.4f}, {hi:+.4f}]"
          f"  {'excludes 0' if lo > 0 or hi < 0 else 'includes 0'}")
n=  3  mean diff -0.0133  95% CI [-0.1203, +0.0937]  includes 0
n= 10  mean diff -0.0005  95% CI [-0.0369, +0.0359]  includes 0
n= 30  mean diff +0.0148  95% CI [-0.0039, +0.0334]  includes 0
n=300  mean diff +0.0171  95% CI [+0.0106, +0.0237]  excludes 0

The intervals are the lesson. With three landscapes the interval runs from −0.12 to +0.09: it could hide a gap ten times larger than the one in the table. With 30 landscapes the interval still includes zero (−0.004 to +0.033) even though the mean gap over 300 landscapes is +0.017. Only at 300 does the interval exclude zero. The interval here is wide mainly because of the t value for two degrees of freedom (4.30, against 1.97 for many) and because landscapes differ a lot in difficulty. Your Artifact 2 has three tasks and three seeds per task, so a nine-run comparison of this kind will usually come out “inconclusive”. That is a real result, if you say it plainly, and the roadmap's stated hypothesis (does the gap appear when opportunities are sparse?) is exactly the question that a bigger sample on sparse tasks could answer.

Analogy: a climber with a headlamp

Greedy search is a hiker in fog who only ever steps uphill. On a smooth hillside (dense opportunities) that is the fastest route to the top, and exploring is a waste of daylight. In a range of jagged peaks (sparse opportunities) the same hiker reaches the top of the nearest small peak and stays there. A tree search sends scouts to several valleys; an adaptive search walks uphill until it has been stuck for a while, then starts again somewhere new.

Where it breaks down: a hiker sees the ground around them, but an agent only learns a point's height by running an experiment that costs real money. And the “landscape” of programs has no fixed map: what counts as a neighbouring step is whatever the language model happens to write.

Designing Artifact 2 so the comparison is fair

Everything above turns into a short design checklist for your study. It restates the standards in the artifact track as concrete choices:

  1. Same budget, in dollars and steps. Count debug steps and failed drafts against AIDE's budget just as you count rejected changes against greedy's. A tree that spends 25% of its steps on repairs has fewer improvement steps.
  2. Log every step with the parent, the operator, the metric, a bug flag and an embedding or diff size. You need these to compute density and to plot a sustained trend rather than one lucky accept.
  3. Score on data the loop never saw. Keep a private test set, as chapter 03 describes. The FML-Bench protocol scores agents on test metrics hidden from them.
  4. Pair by task and seed, report the mean paired difference with an interval, and also report how many tasks fell on each side.
  5. Pick the extension before you run. The roadmap suggests testing whether the gap appears when density is low; decide which of your three tasks you will call sparse, and why, before looking at results, since the paper's own split is after the fact.

Systems connection

The debug path is a retry policy with a depth limit and a probability, much like a job queue that retries a failed job a bounded number of times with jitter; max_debug_depth is the retry cap that stops a hopeless job consuming the budget. The journal of nodes is an append-only log of attempts, which is also what lets you replay or audit a run afterwards. And running each candidate script is an arbitrary-code-execution problem: it belongs in a sandbox with a timeout (A4 Sandboxes & Permissions), because the language model wrote it.

Key takeaways

  • AIDE searches a tree of single-file scripts with three operators: draft, debug and improve (one atomic change).
  • Its policy drafts until num_drafts, debugs a buggy leaf with probability debug_prob, and otherwise improves the best node: greedy over the tree, with drafts and repairs added.
  • FML-bench (18 tasks, 100 steps, three rounds, one model) found that a greedy hill-climber nearly matches the best tree-search agent, and that an adaptive greedy-then-branch agent beat all six others on average.
  • Greedy is strong where improvements are dense; branching pays where they are sparse. φopp = ∑imp / ∑(d/dmax) measures density from a run log.
  • With three seeds a paired interval is typically wide enough to hide a real gap. Report it anyway, and say “inconclusive” when it is.

  2. The best working node so far
  3. The most recently created node
  4. The node with the fewest children
The policy returns the journal's best node. There is no exploration term, which is why AIDE behaves like greedy search over the tree, with extra drafts and a repair path.

Run X gains 0.06 and its improving steps have d/dmax values of 1.0 and 0.5. Run Y gains 0.06 and its improving steps have values of 0.2, 0.2 and 0.1. Which has the higher opportunity density, and about what value?

  1. X, about 0.04
  2. They are equal because the gains are equal
  3. Y, about 0.06
  4. Y, about 0.12
X: 0.06 / 1.5 = 0.04. Y: 0.06 / 0.5 = 0.12. Equal gains reached with much less travel give a higher density, so Y is higher; 0.04 is X's value.

On FML-bench's sparse-opportunity half, what happened to the greedy Autoresearch agent’s rank, and what does it suggest?

  1. It fell from first on the dense half to sixth of seven, suggesting greedy stalls when good moves are rare
  2. It stayed first, suggesting greedy always wins
  3. It was removed because it could not run
  4. It rose to second, suggesting density does not matter
The appendix reports a drop from first (0.349) to sixth (0.035). That inversion is the evidence that the best strategy depends on density.

Your Artifact 2 has 3 tasks and 3 seeds each, and your paired interval for tree minus greedy is [−0.03, +0.05]. Which statement is honest?

  1. Tree search wins, because the mean is positive
  2. Greedy wins, because the lower bound is further from zero
  3. The data are consistent with no difference, a small loss or a modest gain: report it as inconclusive
  4. The experiment failed and should not be published
An interval that includes zero cannot support a claim of a win either way. Reporting an inconclusive result with its interval is a legitimate finding; discarding it is the mistake.

An AIDE run spends 25% of its steps on crashed scripts and their repairs; the greedy baseline has no crashes. What is the fair comparison?

  1. Give AIDE extra steps to compensate for the crashes
  2. Give both the same total budget of steps and dollars, counting repairs against AIDE
  3. Count only AIDE’s improvement steps
  4. Compare only the best single run of each
The standards call for the same budget. Extra steps for one side or counting only successes both favour AIDE, and a best-single-run comparison reports luck.

In the toy, the adaptive agent trails greedy at K=0 and leads at K=12. Which explanation fits the mechanism?

  1. Adaptive uses more compute at high K
  2. At K=0 adaptive crashes more often
  3. K changes the number of design choices
  4. At K=0 restarting throws away a climb that was still paying; at K=12 climbs stall early and a fresh branch is worth more
Both agents have exactly 80 evaluations and N is fixed. Only the ruggedness K changes, which changes how often a stalled climb is worth abandoning.

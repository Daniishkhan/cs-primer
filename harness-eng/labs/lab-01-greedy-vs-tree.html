Lab 1: Greedy versus Tree Search

Chapter 2 described AIDE (AI-Driven Exploration), an agent that searches a tree of experiments, and the finding that a plain hill-climber often does about as well. Chapter 3 explained why the number that picks a winner must not be the number you report. In this lab you build both ideas at toy scale. You write a task with a public split and a private split, a greedy hill-climber, AIDE's selection rule and a paired comparison with confidence intervals. Then you add a knob for how rare good edits are, and a probe that catches a proposer reading a file it should not. It is the first working step of Artifact 2.

Why this lab matters

Artifact 2 asks you to run an AIDE-style tree-search agent against greedy hill-climbing on three FML-Bench tasks, with three seeds. (FML stands for fundamental machine learning: the benchmark is a set of such research problems.) It also asks you to test one question the benchmark's paper leaves open: does the gap between the two appear when good edits are rare? That is a measurement problem before it is an agent problem. The two searches must spend the same budget. You must pair them by task and seed, and put an interval around the difference. The score that picks a winner must differ from the one you publish. Get any of these wrong and you produce a result that looks like a finding.

This lab builds that comparison harness on a task small enough to run in a few seconds, so that every moving part is visible. The real agents arrive in Workbench 1; the real benchmark is the subject of case study 1. After this lab you can write a fair, seeded, paired comparison of two search policies, report it with an interval, and put a hacking rate next to the score. The hacking probe in milestone 6 is a seed of Artifact 3.

Deterministic, standard library only, and a toy on purpose

No network, no clock, no model. The thing that proposes edits is a seeded random editor standing in for a language model: it toggles columns and changes a penalty at random, and sometimes writes a broken edit. A real model is far better informed than that, so the numbers below describe the measurement, not what a real agent would score. Python 3.9 or newer; nothing to install. The whole check runs in about four seconds.

What you'll build

Six milestones:

  1. The evaluator: fit a candidate on the training rows and score it on the public or the private split, with a crash as an ordinary outcome.
  2. The greedy hill-climber: one incumbent; draft once, then always improve the best node.
  3. AIDE's selection rule: five drafts, debug branches, then improve the best, as written in the open-source aideml package.
  4. A paired comparison: the same tasks and seeds for both searches, and a bootstrap interval on the difference.
  5. Opportunity density: how often an edit helps, how that changes with the task, and where the gap between the two searches appears.
  6. The hacking probe: a leftover file that holds the public labels, a proposer that sometimes reads it, and the rate at which the private split exposes the result.

The task, the splits and the search loop

The thing being improved is a small regression pipeline, the kind of artifact an AIDE-style agent writes for a tabular task. A config says which of 24 columns the model uses and how strongly to shrink its weights (a ridge penalty, one of four values). It also carries a flag called peek, which we meet in milestone 6. The label is a weighted sum of a few useful columns plus noise; the other columns are noise. make_task(seed, 24, n_useful) builds the data, and the number n_useful is the knob for milestone 5.

The rows are split three ways, exactly as chapter 3 prescribes and as A7 chapter 16 argues for self-improvers:

  • The training split (60 rows) is what a candidate learns from. The proposer may read it.
  • The public split (30 rows) is scored for every candidate, and the search uses that score to decide what to keep, as AIDE uses its own validation metric. The search sees the score, not the labels.
  • The private split (400 rows) is read only by the evaluator, to record what each candidate is really worth. No policy, proposer or selection rule may read it. It is the number you report.

Thirty public rows is small on purpose. A small public split is noisy, and the best of many candidates on a noisy score is usually flattered by luck. You will see that effect in milestone 4.

The idea

  1. for each step up to the budget: ask the policy for an action (draft, debug or improve) and a parent node
  2. ask the proposer for a config: a fresh draft, a repair of the parent, or one edit of the parent
  3. ask the evaluator for the public score; a crash becomes a node with no score
  4. store the node (config, public score, private score) in the journal
  5. at the end, report the private score of the node with the best public score

Steps 1 to 4 are one function, run_search, which is given. Read it once; milestones 2 and 3 plug into its first line, and milestone 1 is its fourth.

def run_search(task: Task, proposer: Proposer, steps: int, seed: int,
               policy) -> Journal:
    """Spend exactly `steps` nodes. Each step: the policy picks an action,
    the proposer writes a config, the evaluator scores it on the PUBLIC
    split (the private score is recorded for reporting, never used)."""
    rng = random.Random(seed)
    journal = Journal()
    for step in range(steps):
        stage, parent = policy(journal, rng)
        if stage == "draft":
            cfg = proposer.draft(task, rng)
        elif stage == "debug":
            cfg = proposer.debug(task, parent.cfg, rng)
        else:
            cfg = proposer.improve(task, parent.cfg, rng)
        try:
            pub = score_config(task, cfg, "public")
            priv = score_config(task, cfg, "private")
        except ConfigError:
            pub = priv = None
        journal.add(Node(step, stage, parent, cfg, pub, priv))
    return journal

Two details to notice. Every step costs one node, whether it crashes or not. A broken edit spends budget just as a good one does, as a real agent's tokens and minutes are spent. The private score is computed for every node but stored in a field the policies never read. final_private reports the private score of the node the public score selected.

A node records one tried candidate. A draft is a new candidate written from scratch, a debug step repairs a node that crashed, and an improve step edits a working node. The journal is the list of all nodes with their parent links, which makes it a tree. The policy is the rule that chooses the next action and parent from the journal.

Milestone 1: the evaluator

Everything else stands on this function, so it has to be exact. A normal candidate is a ridge regression on the chosen columns: with X the training columns plus an intercept, the weights solve (XTX + λI)w = XTy, with the intercept left unpenalised. The given fit does that by Gaussian elimination, in about twenty lines, and raises ConfigError for a column that does not exist. What you add makes it an evaluator. You choose the split, predict its rows and return the root-mean-squared error (RMSE): the square root of the average squared gap between prediction and label.

Two behaviours deserve a sentence. A crash is an ordinary outcome. score_config lets ConfigError escape and run_search turns it into a node with no score, so the search can see that an edit failed. And the peek branch is a deliberate hole. A leaky harness leaves the public labels in a cache file that the candidate's code can read, the way a scoring script leaves its answer key in the working directory. A candidate that reads it needs no model at all.

Your task

Write score_config(task, cfg, split). A normal candidate is fitted on task.train with the given fit and predicts the rows of the split you are asked for; return the root-mean-squared error. A candidate with peek=True learns nothing: on the public split it returns the labels it finds in task.cache (so its error is 0, or ConfigError if there is no cache file), and on the private split it can only predict the mean of the training labels. An unknown split name is a ValueError.

python3 check.py shows this milestone as ✔. A hand-built task where the ridge slope is exactly 8/(4+λ) gives public RMSE 1.2 and private RMSE √0.32; no features gives 6.0; peek gives 0 on public and √8 on private; a missing cache, an unknown split and a column that does not exist raise the right errors; and on seeded tasks the true columns score under 0.9 while no columns score over 1.8.

Hints try without first

  • Pick task.public or task.private first, then branch on cfg.peek.
  • The mean of the training labels is sum(y for _, y in task.train) / len(task.train).
  • Do not catch ConfigError here. The search loop turns it into a crashed node.
Solution spoiler 
def score_config(task: Task, cfg: Config, split: str) -> float:
    """Root-mean-squared error of the candidate on 'public' or 'private'.

    A normal candidate is fitted on task.train and predicts the split's rows.
    A candidate with peek=True does not learn: on the public split it returns
    the labels found in task.cache (RMSE 0 when the cache exists), and it
    raises ConfigError("no cache file") when the cache is gone; on the
    private split it can only predict the mean of the training labels.
    Any other split name raises ValueError(BAD_SPLIT).
    """
    if split not in ("public", "private"):
        raise ValueError(BAD_SPLIT)
    rows = task.public if split == "public" else task.private
    if cfg.peek:
        if split == "public":
            if task.cache is None:
                raise ConfigError("no cache file")
            return 0.0
        mean = sum(y for _, y in task.train) / len(task.train)
        preds = [mean] * len(rows)
    else:
        w = fit(task, cfg)
        preds = [sum(wi * v for wi, v in zip(w, _design(x, cfg.features)))
                 for x, _ in rows]
    se = sum((p - y) ** 2 for p, (_, y) in zip(preds, rows))
    return math.sqrt(se / len(rows))

Milestone 2: the greedy hill-climber

Hill-climbing keeps one best candidate, the incumbent, tries a change to it, and moves only if the change scores better. Greedy means it never looks sideways or backwards: every step builds on the best node so far. It is the simplest search that works, and it is a baseline in the FML-Bench study. There the autoresearch agent "implements a greedy hill-climber that retains each code modification only when it strictly improves the validation metric" (Zou et al., 2026; see case study 1).

Here the keeping is done by the policy, not by deleting nodes: failed edits stay in the journal as leaves, and the next step simply chooses the best node again. The only wrinkle is the start. Until something has run successfully, there is no incumbent, so the policy repairs a crashed draft if there is one, and drafts otherwise.

Your task

Write greedy_policy(journal, rng). It returns ("draft", None), ("debug", node) or ("improve", node). While nothing has run successfully, repair the most recent buggy leaf if there is one and draft if there is not. Once a good node exists, always improve the best one.

python3 check.py shows this milestone as ✔. An empty journal drafts; a lone buggy leaf is debugged; with several good nodes the lowest public score wins and the earliest wins a tie; and on eight seeded searches no draft appears after the first good node, every improve step starts from the best node so far, and greedy beats the no-feature baseline by a clear margin.

Hints try without first
  • journal.good, journal.buggy and journal.best() already exist; a leaf is a node with is_leaf true.
  • journal.best() breaks ties by step, so you do not need to.
  • The three cases are an if not journal.good: block with two outcomes, and a final line.
Solution spoiler 
def greedy_policy(journal: Journal, rng: random.Random):
    """What to do next, for a hill-climber with a single incumbent.

    Returns ("draft", None), ("debug", node) or ("improve", node).
      * no good node yet and a buggy leaf exists: debug the most recent
        buggy leaf (the incumbent is being repaired);
      * no good node yet and nothing to repair: draft;
      * otherwise improve the best good node.
    `rng` is unused here; it is in the signature so every policy has the
    same shape.
    """
    if not journal.good:
        leaves = [n for n in journal.buggy if n.is_leaf]
        if leaves:
            return ("debug", leaves[-1])
        return ("draft", None)
    return ("improve", journal.best())

Milestone 3: AIDE's selection rule

AIDE (Jiang et al., 2025, "AIDE: AI-Driven Exploration in the Space of Code") treats machine-learning engineering as a search over programs. Its open-source package, aideml, keeps a solution tree with the three node kinds above. The rule that chooses what to work on next is short enough to read in one sitting. The order below is that of search_policy in agent.py, version 0.2.2, which I read on the lab VM (the rented machine of the workbenches) on 15 October 2026:

  1. If fewer than num_drafts draft nodes exist (the default is 5), write a new draft.
  2. Otherwise, with probability debug_prob (default 0.5), pick a random buggy leaf that is at most max_debug_depth (default 3) repairs deep, and debug it.
  3. If no node has run successfully, write a new draft.
  4. Otherwise improve the node with the best validation metric.

The FML-bench repository's configuration for its AIDE agent uses the same three numbers (num_drafts: 5, debug_prob: 0.5, max_debug_depth: 3), which I read at commit d336651 on 15 October 2026. Look at the last line of the rule. After the drafts, the package improves the best node, which is the greedy rule. The tree is a tree because of its five independent starts and its branching debug steps. Where greedy has one chain, AIDE has five roots and some repair work spread over them. Whether that extra breadth buys anything is exactly what this lab measures. Other tree policies exist (upper-confidence rules from A7 chapter 1 choose nodes by how little they have been tried as well as by score), and the "Going further" list suggests one.

Your task

Write aide_policy(journal, rng, num_drafts=5, debug_prob=0.5, max_debug_depth=3), the selection rule of aideml 0.2.2. First, if fewer than num_drafts draft nodes exist, draft. Then, with probability debug_prob, debug a random buggy leaf whose debug_depth is at most max_debug_depth, if there is one. If no node has run successfully, draft. Otherwise improve the best good node.

No random draw happens while drafts are still owed; exactly one rng.random() call happens per later decision; a buggy node with a child is not a leaf; a leaf four repairs deep is left alone; about half of 2000 decisions debug at debug_prob=0.5; and on real runs the first five steps are the five drafts.

Hints try without first
  • Draw rng.random() exactly once per decision once the drafts are done, even when there turns out to be nothing to debug. The check counts the calls so that seeded runs replay.
  • Build the list of options with a comprehension over journal.buggy, then rng.choice(options).
  • If the debug draw fails, or there is nothing to debug, fall through to the next rule instead of returning.
Solution spoiler 
def aide_policy(journal: Journal, rng: random.Random, num_drafts: int = 5,
                debug_prob: float = 0.5, max_debug_depth: int = 3):
    """aideml's search policy, as read in agent.py (version 0.2.2):

      1. fewer than num_drafts draft nodes so far: draft a new one;
      2. with probability debug_prob, if a buggy LEAF with
         debug_depth <= max_debug_depth exists, debug one chosen at random;
      3. no good node: draft;
      4. otherwise improve the best good node.
    Call rng.random() exactly once per decision after step 1 (so seeded
    runs replay), and rng.choice(...) only when you really debug.
    """
    if len(journal.drafts) < num_drafts:
        return ("draft", None)
    if rng.random() < debug_prob:
        options = [n for n in journal.buggy
                   if n.is_leaf and n.debug_depth <= max_debug_depth]
        if options:
            return ("debug", rng.choice(options))
    if not journal.good:
        return ("draft", None)
    return ("improve", journal.best())

Milestone 4: a paired comparison with an interval

To compare two searches fairly, give them the same budget (20 or 12 nodes each, here) and the same tasks. A6 chapter 4 explains why: tasks differ in difficulty far more than the two policies differ from each other, so comparing the two averages mostly measures task luck. A paired comparison takes the difference between the policies on each task and works with those differences. The task's difficulty cancels.

The question is then how much to trust the mean difference. A bootstrap interval answers it without algebra: resample the pairs with replacement, take the mean difference of each resample, and read off the 2.5th and 97.5th percentiles of those means. If a 95 per cent interval excludes zero, the data are hard to explain as chance (A0 chapter 15 has the longer story). Two traps are worth building the check around. Resampling the two lists separately breaks the pairing and gives a wrong interval, so the check feeds it identical lists and demands exactly zero. And an interval from a handful of seeds is wide, and sometimes misleading, so the check also simulates 150 small studies and measures how often the interval contains the truth.

Your task

Write paired_ci(a, b, n_boot=2000, seed=0). Form the differences a[i] - b[i], resample those differences with replacement n_boot times using one random.Random(seed), and return the mean difference with the 2.5th and 97.5th percentile of the resampled means, read from the sorted list at int(0.025 * n_boot) and int(0.975 * n_boot) - 1.

python3 check.py shows this milestone as ✔. Pairs that all differ by exactly 1 give (1, 1, 1); identical lists give (0, 0, 0), which fails if you resample the two lists separately; differences [0, 2] give mean 1 and ends 0 and 2; and in 150 simulated studies of 30 pairs the interval covers the true mean at least 85 per cent of the time (a good implementation lands near 95).

Hints try without first
  • Resample indices of the differences, not the two lists.
  • One Random(seed) created before the loop, and rng.randrange(n) inside it.
  • sorted(means)[k] picks a percentile.
Solution spoiler 
def paired_ci(a: List[float], b: List[float], n_boot: int = 2000,
              seed: int = 0) -> Tuple[float, float, float]:
    """Mean of (a - b) over paired seeds, with a 95% percentile bootstrap
    interval: resample the PAIRS with replacement n_boot times, take each
    resample's mean difference, return (mean, 2.5th percentile,
    97.5th percentile) using sorted()[int(0.025 * n_boot)] and
    sorted()[int(0.975 * n_boot) - 1]."""
    assert len(a) == len(b) and a, "need paired, non-empty lists"
    d = [x - y for x, y in zip(a, b)]
    rng = random.Random(seed)
    n = len(d)
    means = sorted(sum(d[rng.randrange(n)] for _ in range(n)) / n
                   for _ in range(n_boot))
    return (sum(d) / n, means[int(0.025 * n_boot)],
            means[int(0.975 * n_boot) - 1])

Try it: the winner's curse

The search selects by the public score and you report the private one. With only 30 public rows, the node that wins the selection is partly the node that got lucky. This script measures how much, using only functions you have written or been given:

"""The winner's curse: the node the public split picks looks better than it is.

Run in the lab folder after finishing the milestones (or use solution.py).
"""
from solution import (Proposer, aide_policy, greedy_policy, make_task,
                      run_search)

N_SEEDS = 60                      # paired tasks
STEPS = 12                        # nodes per search (the budget)

for name, policy in (("greedy", greedy_policy), ("tree", aide_policy)):
    gaps = []
    for seed in range(N_SEEDS):
        task = make_task(seed, 24, 3)
        best = run_search(task, Proposer(), STEPS, 1000 + seed,
                          policy).best()
        if best is not None:
            gaps.append(best.private - best.public)
    mean = sum(gaps) / len(gaps)
    worse = sum(g > 0 for g in gaps)
    print(f"{name:7s} selected node: private - public = {mean:+.2f} on "
          f"average; worse on private in {worse} of {len(gaps)} runs")

greedy  selected node: private - public = +0.15 on average; worse on private in 38 of 60 runs
tree    selected node: private - public = +0.15 on average; worse on private in 43 of 60 runs

On average the node a search selects scores about 0.15 RMSE better on the public split than it deserves, and on six runs in ten it is worse on private than on public. Both policies show it equally, which is the point: it comes from selecting on a noisy score, not from the search method. This is the effect that A7 chapter 16 calls the statistics of picking the best of many, and it is why a public score can never be the number you report. The same effect, at larger scale, is why the AIDE² authors select on a private score (case study 1).

Milestone 5: opportunity density

Here is the question Artifact 2 puts to FML-Bench. The paper reports that a greedy hill-climber comes close to the best tree-search agent. It also reports that greedy search does better when opportunities are dense, and tree and evolutionary methods do better when they are sparse (Zou et al., 2026). The paper defines opportunity density for a task as the sum of the positive normalised improvements an agent finds, divided by the distance it travels through the code. That needs real code and an embedding model. This lab uses a simpler quantity with the same meaning. The realised density is the fraction of proposed edits, from a given start, that improve the public score by more than a noise floor. A change smaller than the noise floor (here 0.05 RMSE) is indistinguishable from the luck of the draw on 30 rows, so it is not progress.

The knob is the task. With 24 columns and one useful one, a random edit helps only when it adds that column, which is rare. With 12 useful columns, most column edits help. So n_useful sets the density, and realised_density measures it from the empty model, where a good edit is any that adds a useful column.

Your task

def realised_density(task: Task, proposer: Proposer, cfg: Config,
                     n: int, seed: int, min_gain: float = 0.05) -> float:
    """Of n proposed improve-edits from `cfg`, the fraction whose PUBLIC
    score is lower (better) than cfg's by MORE than min_gain, the noise
    floor below which a change is not counted as progress. A crashed edit
    counts as not improving. Draw edits with one random.Random(seed)."""
    rng = random.Random(seed)
    base = score_config(task, cfg, "public")
    good = 0
    for _ in range(n):
        new = proposer.improve(task, cfg, rng)
        try:
            good += score_config(task, new, "public") < base - min_gain
        except ConfigError:
            pass
    return good / n

Common misconception

“The toy reproduces the FML-Bench result.” It reproduces its direction for the reason the toy was built to have: random edits and independent starts. The size of the gap, and whether it appears at all on a real task, depends on how the proposer is informed. A language model's edits are not random, and its first draft is rarely a pure guess; either can shrink the gap. The toy tells you what to measure and how to report it, and nothing about FML-Bench's numbers. Those come from the benchmark.

Milestone 6: the hacking probe

A7 chapter 15 and chapter 3 make the point that a search finds every loophole in its scorer, and that the cure begins with measuring it. The probe here is the smallest honest version. In the leaky harness the public labels sit in a cache file the candidate can read. With probability p_peek each improve-edit of the seeded proposer sets peek=True: the candidate reads the answer key instead of learning anything. On the public split it scores 0.00, which beats everything, so the search selects it and every later improvement builds on it. On the private split it can only predict a constant, so it is worth very little.

Two functions turn that into numbers. hack_flags flags a node whose private score is worse than its public score by more than a margin. A genuine fit rarely loses half an RMSE point between 30 rows and 400. A memorised answer key always does. hacking_rate is the fraction of runs whose selected node is flagged. It is the quantity Artifact 3 reports next to every score. The cure is also tiny: delete the cache file, so that a candidate that reads it crashes, and the debug step repairs it into an honest config.

An analogy

A teacher sets a test, then leaves the marked answer sheet in the room. Some pupils never look, some look and copy. The marks of the copiers are perfect, so the ranking is topped by them. A second test the next week, with fresh questions, shows who learned anything. The private split is that second test, and the hacking rate is the fraction of top-ranked pupils whose second mark collapses.

Where it breaks down: a pupil who copies knows they copied. A search does not: it only sees that a variant scored 0.00 and keeps it. The detection has to come from outside the loop.

Your task

Write hack_flags(journal, margin=0.5) and hacking_rate(journals, margin=0.5). The first returns the nodes that ran and whose private score is worse than their public score by more than margin. The second returns the fraction of runs whose selected node (the journal's best()) is among its flagged nodes; a run with no good node counts as not hacked.

python3 check.py shows this milestone as ✔. A crashed node is never flagged and never raises; a gap of exactly 0.5 is not flagged but is at margin 0.1; a flagged node that was not selected does not count; and on 30 seeded tasks with a proposer that notices the cache file 10 per cent of the time, the hacking rate is at least 0.5 while the cache file is in place and at most 0.15 once it is removed, with at most 0.1 false alarms on honest runs.

Hints try without first
  • Crashed nodes have public is None; skip them before subtracting.
  • best in hack_flags(j, margin) works because nodes compare by identity.
  • Divide by len(journals), not by the number of runs that had a good node.
Solution spoiler 
def hack_flags(journal: Journal, margin: float = 0.5) -> List[Node]:
    """Nodes whose public score is suspiciously better than their private
    one: public is not None and private - public > margin."""
    return [n for n in journal.nodes
            if n.public is not None and n.private - n.public > margin]

def hacking_rate(journals: List[Journal], margin: float = 0.5) -> float:
    """Fraction of runs whose SELECTED (best-by-public) node is flagged by
    hack_flags. Runs with no good node count as not hacked."""
    hit = 0
    for j in journals:
        best = j.best()
        hit += best is not None and best in hack_flags(j, margin)
    return hit / len(journals)

Going further

  • Make the proposer informed. Change Proposer.improve so that, with probability skill, it adds the column most correlated with the current residual instead of a random one. Predict first: does the tree's advantage at low density grow or shrink? Then run the sweep. A language model reading the data is somewhere between the random editor and this one.
  • Try another selection rule. Replace "improve the best" with a rule that picks a node by score minus a bonus for how rarely it has been chosen (the upper-confidence idea of A7 chapter 1). Does it beat both?
  • Add a noise-floor accept rule to greedy. Keep a change only if it improves the public score by more than 0.05. Does it reduce the winner's curse? Does it cost progress?
  • Measure the budget in dollars. Give drafts, debugs and improves different prices (a draft writes a whole script; an improve writes a diff) and compare at equal cost instead of equal nodes. The FML-Bench paper fixes steps, not cost, and says that the fixed step budget may affect relative rankings.
  • A second hole. Let the proposer edit the evaluator's penalty grid, or return a config that always scores 0 on a malformed split name. Extend hack_flags until it catches both, then think about what you would log.

Check your understanding

Greedy and tree searches are run on 60 tasks. Why compute the difference per task before averaging, rather than comparing the two averages?

  1. It makes the interval narrower for any data set, whatever the pairing.
  2. Task difficulty varies far more than the policies differ, and taking the difference on each task cancels it.
  3. Averages cannot be compared when the numbers are errors rather than accuracies.
  4. The bootstrap only works on differences, never on raw scores.
The pairing removes task-to-task variation, which is the biggest source of noise. The first option is tempting but a pairing can also widen an interval if the two policies are uncorrelated across tasks; it helps here because both face the same task. The bootstrap works on any statistic.

After its five drafts, aide_policy (the rule in aideml 0.2.2) is asked to improve a node. Which one does it choose when nothing needs debugging?

  1. A random good node, to keep the tree broad.
  2. The most recent good node.
  3. The good node that has been improved the fewest times.
  4. The good node with the best validation metric.
The package improves the best node, which is the greedy rule. The tree is a tree because of the five independent drafts and the branching debug steps. A rule that favours rarely-tried nodes is the upper-confidence variant, which is an extension, not what the package does.

A search ends with a selected node whose public score is 0.90 and whose private score is 1.16. Across many runs the average gap is similar. What is the best explanation?

  1. Selecting the best of many candidates on a small public split picks partly for luck, so its score is flattered.
  2. The private split is easier than the public split.
  3. The evaluator has a bug that adds noise to private scores only.
  4. Tree search overfits and greedy search does not.
This is the winner's curse. The gap was the same for both policies (+0.15 on average), which rules out the last option, and nothing suggests the private split is easier: its 400 rows make it the less noisy of the two.

In the density sweep, the gap between greedy and tree is zero when 12 of 24 columns are useful. What can you conclude?

  1. Tree search never helps on real benchmarks.
  2. Greedy is a better algorithm than tree search.
  3. On this toy, when most edits help, extra independent starts add nothing; it says little about real tasks.
  4. The interval is too wide to see any difference.
The interval for that row is narrow (about plus or minus 0.05) and centred on zero, so the data do show no difference there. The toy has a random proposer and a simple landscape, so the result says nothing about greedy versus tree on a real benchmark, and it does not show that greedy is the better algorithm.

Removing the cache file cut the hacking rate from about 0.9 to about 0.05 without changing the search policy. Why?

  1. The proposer stopped trying to peek.
  2. The margin in hack_flags was raised.
  3. The private split was made larger.
  4. A peeking candidate now crashes, the debug step repairs it into an honest config, and nothing scores 0.00 for free.
The proposer's behaviour did not change (p_peek was the same); the opportunity did. A hole in the evaluator is closed by fixing the evaluator. A larger private split would make detection sharper but would not stop the hack from being selected.

A colleague proposes selecting the winning node by its private score, because it is the more reliable number. What goes wrong?

  1. Nothing: a more reliable number is a better selector.
  2. The private split becomes a second public split. After selecting on it, its score is flattered by the same winner's curse and there is nothing left to report.
  3. The evaluator would be slower because the private split is larger.
  4. The policies would crash, because they cannot read the private score.
A split used for choosing is no longer held out. The fix is a third split that selection never touches, or a private split read once, at the end. The AIDE² paper's selection uses a private score, but its authors then report on benchmarks the loop never saw, which is the same discipline one level up.

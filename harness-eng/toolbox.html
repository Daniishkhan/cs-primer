Toolbox

Four tools sit under Artifacts 2 and 3: an open tree-search agent for machine-learning tasks, the benchmark that compared it with greedy search, the benchmark of GPU kernels that an evaluator has to survive, and the language in which those kernels are written. Each card has install notes, what the tool is for, and a ten-minute exercise that runs on the lab VM, a rented CPU machine, without a GPU.

How to use this page

Jump to a tool when a chapter, the lab or the workbench points at it. What I ran, on the lab VM (Ubuntu 24.04, 16 vCPU, no GPU), on 15 October 2026: pip install aideml (version 0.2.2) and a printout of its selection rule; a shallow clone of the FML-bench repository (commit d336651) with its task lister and a comparison of two agent configurations; a shallow clone of KernelBench (commit 423217d) with a script of mine that grades two candidates on the CPU; and Triton 3.8.0 with a kernel run in its CPU interpreter, including one deliberate bug. Each of those has real output below. What I did not run: the FML-bench environment setup (it clones task repositories and builds conda environments), any FML-bench agent run, any KernelBench generation or GPU evaluation, and Triton on a GPU. Commands for those are marked illustrative, with no invented output; I describe what to look for instead. An aideml run on a real task is Workbench 1.

The agent and the benchmark

The agent is the thing under test in Artifact 2; the benchmark is where it is compared with a greedy baseline. Lab 1 builds both at toy scale first.

AIDE (aideml)

Install: pip install -U aideml (MIT licence; Python 3.10 or newer; an API key for OpenAI, Anthropic, Gemini or OpenRouter, or a local OpenAI-compatible server) · Alternatives: the FML-bench reimplementation of AIDE, a hand-written greedy loop as in Lab 1, Karpathy's autoresearch · Chapters: 2 · Practice: Lab 1, Workbench 1, Case 1

AIDE is a coding agent that treats machine-learning engineering as a search. You give it a data folder, a goal and an evaluation metric in words; it writes a Python script, runs it, reads the result, and then repeatedly drafts, debugs and improves scripts, keeping the best. The package aideml (Weco AI) is the open reference implementation of the algorithm in Jiang et al. (2025). The command line is aide data_dir="..." goal="..." eval="...", and the settings you will touch are agent.steps (the number of nodes, default 20), agent.code.model and agent.feedback.model (the writing and the reviewing model), and agent.search.num_drafts (default 5).

State of play, October 2026

The version I installed is 0.2.2. Its README names defaults of o4-mini for the coding model and gpt-4.1-mini for the reviewer, which are older models; both are settings, and model IDs are passed through to the provider. The README's headline claim, that AIDE "wins 4 × more medals" than the best linear agent on OpenAI's MLE-bench, is the project's own and comes from the 2025 version of the tool. Expect settings, defaults and SDK requirements to change between releases.

    def search_policy(self) -> Node | None:
        """Select a node to work on (or None to draft a new node)."""
        search_cfg = self.acfg.search

        # initial drafting
        if len(self.journal.draft_nodes) < search_cfg.num_drafts:
            return None

        # debugging
        if random.random() < search_cfg.debug_prob:
            # nodes that are buggy + leaf nodes + debug depth < max debug depth
            debuggable_nodes = [
                n
                for n in self.journal.buggy_nodes
                if (n.is_leaf and n.debug_depth <= search_cfg.max_debug_depth)
            ]
            if debuggable_nodes:
                return random.choice(debuggable_nodes)

        # back to drafting if no nodes to improve
        good_nodes = self.journal.good_nodes
        if not good_nodes:
            return None

        # greedy
        greedy_node = self.journal.get_best_node()
        return greedy_node
  1. Minute 6 to 10: predict. With num_drafts=5 and 20 steps, how many nodes are drafts, and from which node does each later improvement start? (Five drafts; every improvement starts from the best node so far, because the last branch is the greedy node.) How would the run differ with num_drafts=1? (After one draft, only the debug branch separates it from a hill-climber: that is the greedy arm of Workbench 1.)

FML-Bench

Install: git clone https://github.com/qrzou/FML-bench, then python setup.py (clones the task repositories, downloads datasets and builds conda environments; --task NAME for one) · Needs: Linux, conda, an API key for a supported provider, and for real runs GPUs (the paper used NVIDIA A100-80GB) · Licence: Apache-2.0 · Alternatives: MLE-bench (chapter 5), RE-Bench · Chapters: 2, 5 · Practice: Case 1

FML-Bench is 18 tasks, each a codebase from an existing machine-learning library with a validation command, on which an agent tries to improve a baseline within a step budget. It registers seven agents, each a YAML file in configs/agents/, and scores them with compute_agent_metrics.py, which writes raw performance, normalised improvement and twelve process-level metrics. The metrics that embed each step's code need torch, transformers and scikit-learn. A cheaper subset, FML-bench-Lite, has eight tasks. Case 1 reads the paper that goes with it.

State of play, October 2026

The paper behind the repository is the second FML-bench paper (arXiv 2605.17373, v2 of 29 May 2026); the first version of the benchmark, with 8 tasks, lives on the repository's legacy branch. The README's example command uses --model gpt-5.4. The repository had few stars and a handful of commits when I read it, so expect the layout to change. Its README reports no results; the numbers are in the paper.

The kernels and the language

Artifact 3 hardens a grader for GPU kernels. You do not need a GPU to read how the grader is shaped or to see what an unchecked kernel can do, and the exercises below run on the CPU.

KernelBench

Install: git clone https://github.com/ScalingIntelligence/KernelBench, then uv sync (base dependencies, no GPU needed) or uv sync --extra gpu · Needs: a GPU to run or profile a generated kernel; without one the README suggests Modal's serverless GPUs · Licence: MIT · Alternatives: KernelBench-Verified and robust-kbench for harder graders · Chapters: 4, 5 · Practice: A6 case study 2, A7 Lab 6

KernelBench (the paper appeared at ICML 2025, according to its README) gives a model a PyTorch program and asks for a faster kernel that computes the same thing. Each problem is a file with a Model class, get_inputs() and get_init_inputs(). Levels run from single operators (level 1, 100 problems) through fusion patterns (level 2, 100) to whole architectures (level 3, 50). The metric is fast_p: the fraction of problems on which the kernel is correct and its speed-up over the PyTorch reference exceeds p, so fast_0 is the correctness rate and fast_1 is correct and faster. A generated kernel is checked for correctness against the reference on random inputs n_correctness times and timed over n_trial runs. That is a grader with two soft spots, which chapters 3 and 4 and Artifact 3 are about: the inputs are cheap to predict, and a timing is a single noisy number.

State of play, October 2026

The README says the KernelBench team does not review or endorse individual kernels or reported results, and tells users to verify results independently. A follow-up paper, "KernelBench-Verified: Do LLM-Generated Kernels Actually Beat PyTorch?" (arXiv 2607.16241, 26 June 2026; I read its abstract page only), reports that frontier models inflate results by reward hacking, and proposes a TF32-enabled baseline and a four-distribution hidden test suite. It reports a best-model geometric-mean speed-up of 0.88 times, against 1.43 times under the standard protocol. These are the authors' figures from one abstract; verify them in the paper before citing.

"""kb_check.py: read one KernelBench problem and grade two candidates.

    python kb_check.py KernelBench/KernelBench/level1/19_ReLU.py

Runs on the CPU, with the reference PyTorch program only. KernelBench's own
scripts need a GPU to run a generated kernel; this shows the grader's shape
(reference, inputs, correctness over several draws, timing) with a candidate
that is honest and one that cheats by remembering its first answer.
"""
import importlib.util
import statistics
import sys
import time

import torch

# ── 1. Load the problem: a Model class plus get_inputs() ─────────────────
path = sys.argv[1] if len(sys.argv) > 1 else \
    "KernelBench/KernelBench/level1/19_ReLU.py"
spec = importlib.util.spec_from_file_location("problem", path)
prob = importlib.util.module_from_spec(spec)
spec.loader.exec_module(prob)
prob.batch_size, prob.dim = 256, 4096     # shrink: the stock size is 6 GB
ref = prob.Model(*prob.get_init_inputs())
print("problem:", path.split("/")[-1], " inputs:",
      [tuple(t.shape) for t in prob.get_inputs()])


# ── 2. Two candidates ────────────────────────────────────────────────────
class Honest(torch.nn.Module):
    def forward(self, x):
        return torch.clamp(x, min=0)          # same maths, different call


class Memoiser(torch.nn.Module):
    """Returns whatever it computed on the first input, always."""
    first = None

    def forward(self, x):
        if Memoiser.first is None:
            Memoiser.first = torch.relu(x)
        return Memoiser.first


# ── 3. Grade: correctness on fresh draws, then timing ────────────────────
def grade(name, model, n_correct=5, n_trial=20):
    torch.manual_seed(0)
    ok = 0
    for i in range(n_correct):
        torch.manual_seed(100 + i)            # a new input each time
        x = prob.get_inputs()
        ok += torch.allclose(model(*x), ref(*x), atol=1e-2, rtol=1e-2)
    x = prob.get_inputs()
    ts = []
    for _ in range(n_trial):
        t0 = time.perf_counter()
        model(*x)
        ts.append(time.perf_counter() - t0)
    return name, ok, n_correct, statistics.median(ts) * 1e3


x = prob.get_inputs()
ts = []
for _ in range(20):
    t0 = time.perf_counter()
    ref(*x)
    ts.append(time.perf_counter() - t0)
base = statistics.median(ts) * 1e3
print(f"reference median time: {base:.3f} ms")
for model in (Honest(), Memoiser()):
    name, ok, n, ms = grade(type(model).__name__, model)
    print(f"{name:9s} correct on {ok}/{n} fresh inputs; "
          f"median {ms:.3f} ms; speedup if graded on one input: "
          f"{base / ms:.1f}x")

Honest    correct on 5/5 fresh inputs; median 0.053 ms; speedup if graded on one input: 0.9x

What to look for: whether the harness rejects a kernel that is correct on one input and wrong on others, whether it times with warm-up and several trials, and what it does with a kernel that returns a cached tensor. Each is a door of the kind Artifact 3 closes.

Triton

Install: pip install triton (MIT licence; Linux; prebuilt wheels for CPython 3.10 to 3.14) · Needs: an NVIDIA GPU with compute capability 8.0 or higher, or an AMD GPU with ROCm 6.2 or higher, to compile and run kernels. The README lists CPUs as "under development" · Alternatives: CUDA C++ (reading level only in this course), CUTLASS, ThunderKittens, TileLang · Chapters: 4 · Practice: Lab 1 (the hacking probe), A3 chapter 4

Triton is a Python-embedded language for GPU kernels. You write a function decorated with @triton.jit that describes what one program instance does to one block of data, and launch a grid of instances. It is the first thing to read in an agent-written kernel because it is short, because the loads, stores and masks are explicit, and because KernelBench's backend=triton option asks models for Triton. Setting the environment variable TRITON_INTERPRET=1 makes Triton run the kernel body in Python on CPU tensors, one program instance at a time. That is a debugging mode, not a fast path, and not a substitute for a GPU test.

State of play, October 2026

I installed Triton 3.8.0 from PyPI into a CPU-only virtual environment (PyTorch 2.14.1 CPU). Without the interpreter variable, running a kernel there fails because no GPU driver is found (shown below). Triton's own API and supported hardware change with each release; read the documentation at triton-lang.org for the version you install.

10-minute guided exercise

Run the smallest kernel, then remove one mask and watch what a correct-looking answer hides.

  1. Minute 0 to 3: read. The kernel adds two vectors of 1,000 numbers in blocks of 256, so the last block is ragged: mask keeps lanes 1000 to 1023 from touching memory that is not there.
  2. Minute 3 to 5: run it.
"""vadd.py: the smallest Triton kernel, run in Triton's CPU interpreter.

    TRITON_INTERPRET=1 python vadd.py

No GPU needed: with TRITON_INTERPRET=1 Triton executes the kernel body in
Python, one program instance at a time, on ordinary CPU tensors.
"""
import torch
import triton
import triton.language as tl

N = 1000          # deliberately not a multiple of the block size
BLOCK = 256       # elements handled by one program instance


@triton.jit
def vadd(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(axis=0)                  # which block am I?
    offs = pid * BLOCK + tl.arange(0, BLOCK)     # the indices I own
    mask = offs < n                              # guard the ragged tail
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask)


torch.manual_seed(0)
x, y = torch.rand(N), torch.rand(N)
out = torch.empty(N)
grid = (triton.cdiv(N, BLOCK),)                  # 4 program instances
vadd[grid](x, y, out, N, BLOCK=BLOCK)
print("program instances:", grid[0])
print("max |triton - torch|:", (out - (x + y)).abs().max().item())

The numerical check passes (a maximum error of 0.0), because the 1,000 real elements are right. Then the process dies with corrupted size vs. prev_size and exit status 134: the extra writes damaged the memory allocator's bookkeeping, and it noticed when the program exited. I tried removing the mask from the loads instead; that run printed the same correct answer and finished without any complaint, because the stray lanes were discarded by the masked store. The lesson for grading agent-written kernels is that a correct output on the right inputs does not show that the kernel is correct: out-of-bounds writes can be invisible to a value check, and need bounds checks, sanitisers or an end-to-end run to catch.

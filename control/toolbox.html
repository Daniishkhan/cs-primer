Toolbox

A research loop is locked down in three moves: confine what the code can touch, control what it can reach, and sign what it reports. These four tools are one choice for each move. Each card has setup notes, a ten-minute exercise tied to the chapters and, where I ran it, the real output.

How to use this page

Jump to a tool when a chapter, the lab or the workbench points at it. On the lab VM (Ubuntu 24.04, 16 vCPUs) I ran three of the four: bubblewrap 0.9.0, mitmproxy 12.2.3 (installed with uv tool install mitmproxy) and minisign 0.11 (from the Ubuntu package), and I pasted their real output. For Sigstore I installed version 4.5.0 and ran only --version and --help: signing needs an identity from an OpenID Connect provider, which I did not set up, so its commands are illustrative. I did not install or run Docker: its card is built from Docker's rootless-mode documentation, which I fetched in October 2026, and the commands on it are illustrative with no invented output. The shell scripts are short on purpose; read them before you run them, and run them on a machine you are happy to experiment on.

Confine what the code can touch

A sandbox decides what the code under test can see: files, processes, devices. It is the first wall; the network is the second.

bubblewrap

Install: sudo apt-get install bubblewrap (Ubuntu and Debian package bubblewrap; the binary is bwrap) · Needs: Linux with user namespaces. On Ubuntu 24.04 a program may not create one unless an AppArmor profile allows it, see the note below · Alternatives: rootless Docker, Podman, Firejail, nsjail, gVisor · Chapters: 2, 1 · Practice: Workbench 1

bubblewrap builds a sandbox from Linux namespaces and bind mounts and needs no daemon and no root. Its README describes it as a low-level tool, used by Flatpak among others, that builds its sandbox on user namespaces and starts with a new mount namespace whose root is an empty tmpfs; you then mount in exactly the parts of the host you want, read-only where you can. The README is equally clear about the limit: bubblewrap is “not a complete, ready-made sandbox with a specific security policy”, so how safe the result is depends entirely on the arguments you pass, and everything you mount in can potentially be used to escalate privileges. It also says --new-session is needed to protect against out-of-sandbox command execution through the terminal when the system does not filter the TIOCSTI call. (README fetched in October 2026.)

State of play, October 2026

On the lab VM, Ubuntu 24.04.5 with the setting kernel.apparmor_restrict_unprivileged_userns = 1, running bwrap as an ordinary user failed with “setting up uid map: Permission denied”. Ubuntu's documented remedy is an AppArmor profile that grants the userns permission to that one program; I used a four-line profile for /usr/bin/bwrap (the workbench shows it) rather than switching the restriction off for the whole machine. Distribution defaults here have been changing; check yours.

Read the inside block. The user is just a number, because /etc/passwd is not mounted (the id complaint is the visible sign). There is no /home. There are 5 processes where the host has nearly 400, because --unshare-pid gives the sandbox its own process table. /tmp is a fresh empty tmpfs. And the network does not exist: the error is “Network is unreachable”, not a refusal, because with --unshare-net the sandbox has no interface but loopback. That last difference is strong for a loop that never needs the network, and unusable for one that must reach a model API; chapter 2 and the workbench use a firewall rule and an allowlisting proxy for that case instead.

Docker (rootless)

Install: sudo apt-get install -y docker-ce-rootless-extras (from Docker's apt repository), then dockerd-rootless-setuptool.sh install as an ordinary user · Needs: newuidmap and newgidmap (the uidmap package on most distributions) and at least 65,536 subordinate IDs in /etc/subuid and /etc/subgid · Alternatives: Podman (rootless by default), bubblewrap, nsjail · Chapters: 2 · Practice: A4 chapter 20

A container is a bundle of namespaces, resource limits and a root filesystem, packaged so that an image runs the same everywhere. The ordinary Docker daemon runs as root, which means anyone who can talk to it is effectively root. Rootless mode runs the daemon and the containers inside a user namespace as an unprivileged user, so a container escape lands as that user, not as root. For a research loop that runs untrusted candidates, that is the right default. Docker's documentation, which I fetched in October 2026, lists the setup steps above and says docker info should then show Context: rootless and “rootless” under Security Options. It also tells you to disable a system-wide daemon if one is running, and gives DOCKER_HOST=unix:///run/user/1000/docker.sock as the form of the socket (the number is the user's ID).

State of play, October 2026

I did not install or run Docker, so everything on this card is from the documentation page and from the flags I know; check each against docker run --help for the version you install. The documentation page I retrieved did not include its limitations section, so I do not list them here: read them before you rely on rootless mode for something that needs a privileged port, a particular storage driver or host networking.

10-minute guided exercise

Run a candidate with no network, a read-only filesystem and a ceiling on memory and processes.

  1. Minute 0 to 3: install rootless Docker and confirm with docker info.
  2. Minute 3 to 7: run the illustrative command below on a short script of your own that tries to reach the network, write outside /work and allocate a gigabyte.
  3. Minute 7 to 10: map each flag to the layer it provides (network, filesystem, memory, processes, capabilities) and write down which of them the workbench builds by hand.
$ dockerd-rootless-setuptool.sh install
$ export DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock
$ docker info | grep -i rootless
$ docker run --rm --network none --read-only --tmpfs /tmp \
      --memory 512m --pids-limit 64 --cap-drop ALL \
      --security-opt no-new-privileges \
      -v "$PWD/work:/work" python:3.12-slim python /work/candidate.py

What to look for: with --network none an outbound connection fails immediately; with --read-only a write outside /tmp and the mounted /work fails; with --memory the allocation ends in an out-of-memory kill, not a slow machine. A container shares the host's kernel, so it is a boundary against ordinary mistakes and against code that does not know it is being contained; against a determined escape you add a stronger layer, such as a micro-VM or gVisor, as chapter 2 discusses.

Control what it can reach

The network is the second wall. The goal is deny-by-default: nothing leaves unless a rule says so, and every decision is logged.

mitmproxy

Install: uv tool install mitmproxy or pip install mitmproxy (I used the former, version 12.2.3, on the lab VM) · Needs: Python 3.12 or newer for recent releases · Alternatives: a small allowlisting proxy of your own (the workbench writes one in 100 lines), Squid, Envoy, Smokescreen · Chapters: 2, 4 · Practice: Workbench 1

mitmproxy is a proxy that can decrypt, inspect, rewrite and log HTTP and HTTPS traffic, and run a Python addon on every request. Used here it is an allowlisting gate that also keeps a record of every attempt: the loop's traffic goes through it, the addon answers 403 for any host not on the list, and the log shows what the loop tried to reach. Because it terminates TLS, the addon sees the full request (path, headers, body), not just the host name, which is what a proxy that only tunnels CONNECT cannot do. The cost is that the client must trust mitmproxy's certificate authority, which is a good reason to do this only for traffic from your own sandbox.

State of play, October 2026

The addon API (request(flow) and http.Response.make) is the long-standing one and is what I ran on version 12.2.3, but I could not retrieve the project's addon documentation page when writing this (the fetch returned only a path), so I checked the code by running it, not against the text. Hook names and options change between major versions: read the documentation for the version you install.

  3. Minute 4 to 7: run it. Compare the codes with your prediction and read the mitmdump lines.

"""allowlist.py: a mitmproxy addon. Anything not on the list gets a 403."""
from mitmproxy import http

ALLOW = {"pypi.org", "files.pythonhosted.org"}


def request(flow: http.HTTPFlow) -> None:
    if flow.request.pretty_host not in ALLOW:
        flow.response = http.Response.make(
            403, b"denied by egress allowlist\n",
            {"Content-Type": "text/plain"})
#!/usr/bin/env bash
# mitm_tour.sh: run the addon, send three requests through it.
export PATH=$HOME/.local/bin:$PATH
mitmdump -p 8081 -s allowlist.py --set confdir=/tmp/mitm-w01 \
         > mitm.log 2>&1 &
PID=$!
sleep 4
for url in https://pypi.org/simple/pip/ https://example.com/ http://127.0.0.1:9/steal; do
    printf '%-34s ' "$url"
    curl -s -k -o /dev/null -m 10 -w '%{http_code}\n' -x http://127.0.0.1:8081 "$url"
done
kill $PID
echo "-- mitmdump saw:"
sed 's/^/   /' mitm.log

The first request returns 200 (105 kB of the package index for pip); the second and third are refused with 403. The loopback request is refused without any upstream connection. The log for example.com says something worth knowing: server connect example.com:443 appears before the 403. In its default mode mitmproxy opens the upstream connection while it completes the client's TLS handshake, then runs the request hook, so a deny in that hook means the response is blocked and the connection to the disallowed host has already been made. For a data-exfiltration gate that distinction matters: the request body never leaves, but the host sees a connection. If you need to refuse before connecting, deny in a connection-level hook or set the proxy to connect lazily (check the documentation for your version), or put the firewall rule the workbench builds in front of it so that only the proxy can reach the network at all.

Sign what it reports

A signed result is one the agent cannot author. The two tools below are two ways to get a signature that a reader who does not hold your secret can check.

Sigstore and minisign

Install: sudo apt-get install minisign (version 0.11 on the lab VM) and uv tool install sigstore (version 4.5.0) · Needs: Python 3.10 or newer for Sigstore, and for signing with it an OpenID Connect identity (an account at a provider the Sigstore service accepts, or the ambient credentials of a CI system such as GitHub Actions) · Alternatives: GnuPG, cosign, age and signify, Python's cryptography package for raw Ed25519 · Chapters: 3 · Practice: Lab 1

In Lab 1 the evaluator signs with a shared-key HMAC, which is right when you control both ends and wrong when a third party must check without being able to forge. Both tools here use asymmetric signatures: a private key signs, a public key verifies, and holding the public key does not let you sign. minisign is the small version of the idea: you generate a key pair, sign a file, and give the public key to whoever needs to check; it is a good fit for an evaluator that signs its results and a reader who verifies them. Sigstore removes the long-lived private key: you prove your identity to an OpenID Connect provider, a certificate authority issues a short-lived certificate for that identity, and the signature and certificate are recorded in a public transparency log, so a verifier checks that a given identity signed, and that the signature was logged. That is a better fit for releasing an artifact (your Artifact 3 library) than for the thousands of internal results a loop produces.

State of play, October 2026

PyPI lists sigstore 4.5.0, released 28 July 2026 (I installed it and ran only sigstore --version and sigstore sign --help). Its documented commands are sign, verify (including verify identity with --cert-identity and --cert-oidc-issuer, and verify github for GitHub Actions signatures), attest for DSSE envelopes, get-identity-token and trust-instance. Signing depends on several Sigstore services and the page suggests retrying on failure. Treat the options as a snapshot.

10-minute guided exercise

Sign an evaluator's result with minisign, then change one word.

  1. Minute 0 to 2: install minisign and read the script.
  2. Minute 2 to 4: predict: after the one-word change, will verification fail, and will it tell you which word changed?
  3. Minute 4 to 7: run it.
  4. Minute 7 to 10: answer: in the lab's HMAC design, who could have changed the word and re-signed? Who could here? What would you give the reader of your published results?
#!/usr/bin/env bash
# sign_tour.sh: sign a result file, verify it, change it, verify again.
set -u
cd "$(mktemp -d)"
minisign -G -W -p key.pub -s key.sec >/dev/null
echo '{"task": "t1000", "verdict": "fail", "passed": 0, "total": 13}' > result.json
minisign -S -s key.sec -m result.json -t "evaluator seq 0" >/dev/null
ls
echo "-- verify the untouched file"
minisign -V -p key.pub -m result.json
echo "-- change one word, verify again"
sed -i 's/"fail"/"pass"/' result.json
minisign -V -p key.pub -m result.json
echo "exit status: $?"
key.pub
key.sec
result.json
result.json.minisig
-- verify the untouched file
Signature and comment signature verified
Trusted comment: evaluator seq 0
-- change one word, verify again
Signature verification failed
exit status: 1

The signature file result.json.minisig sits beside the result, and a trusted comment (here the evaluator's sequence number) is covered by a second signature, so it cannot be swapped without detection. Changing “fail” to “pass” breaks verification, and the exit status is non-zero, which a pipeline can test. As in the lab, the verifier learns that the file changed, not what changed. The key was generated with -W, which skips the password prompt: fine for an exercise, not for a key that protects results you will publish.

$ sigstore sign dist/artifact3-0.1.0-py3-none-any.whl
$ sigstore verify identity \
      --cert-identity you@example.com \
      --cert-oidc-issuer https://github.com/login/oauth \
      --bundle dist/artifact3-0.1.0-py3-none-any.whl.sigstore.json \
      dist/artifact3-0.1.0-py3-none-any.whl

What to look for: sign opens a browser (or uses ambient credentials) to get an identity token and writes a bundle next to the file; verify identity succeeds only if the certificate names the identity and issuer you pass. Which identity and issuer strings a given account produces depends on the provider; do not copy the placeholders.

Deny-by-Default Egress & Sandboxes

An agent that runs for days gets more chances to find a way out than one that runs for minutes. This chapter builds the walls that matter for such a loop: a fresh process for each candidate, resource limits, and a network that refuses everything not listed. It also puts a number on what an allowed channel still leaks.

Why this matters

This chapter builds the second wall of Artifact 3, the evaluator-hardening kit. The wall is a sandbox that you can leave running overnight, and it serves the lab and the workbench that follow. Chapter 20 of the agents course, Sandboxes & Permissions, already covers least privilege, containers and allow-lists for an agent that runs for minutes. This chapter does not repeat it. It asks what changes when the run lasts five days and the agent makes thousands of attempts. After it you can write an egress gate that survives hostile URLs, size the daily caps from the honest need, and state in bits how much a permitted channel can leak. You can also explain why an allowlist of exact URLs beats an allowlist of hosts. The sandbox workbench, Workbench 1: A Locked-Down Research Sandbox, builds the real thing on the lab machine.

What changes when the run lasts days

A sandbox for a coding session has one job: keep a mistake or an injected instruction from reaching the rest of your machine. A sandbox for an autonomous research loop has the same job plus three new problems.

  • Patience. A control that stops 99 attempts out of 100 does not stop a loop that makes 10,000 attempts. The weak point will be found if it exists, so every wall has to hold on the ten-thousandth try.
  • Accumulation. Disk fills, logs grow, caches keep secrets, and temporary files become permanent. Over days, small leaks add up. A sandbox needs a clean slate for each candidate and a limit on what carries over.
  • Absence. Nobody is watching at three in the morning. A rule that asks a human to approve each risky action stalls the run, and a rule that never asks has no human at all. The walls must work unattended, and failures must be loud when you return.

The fix for all three is the same idea in different places: deny by default. Everything is refused unless a rule allows it, so a forgotten case fails closed instead of open.

Four layers

The sections below take the layers from the inside out. The identity and resource layers get one script. The network layer gets most of the chapter, because it is the layer where days of patience matter most.

A fresh process for every candidate

The first rule of a long run is that no candidate inherits anything it was not given. Each experiment starts a new process in a new empty directory with an empty environment. The parent keeps credentials, the child never sees them. Resource limits apply to the child before it runs a single line of candidate code. The script below uses only the standard library. It starts four candidates that stand in for what a search produces: one that behaves, one that writes a huge file, one that spins the CPU, and one that sleeps.

"""Run each candidate in a fresh process: scrubbed env, own directory, limits.

Usage: python3 fresh_worker.py   (POSIX; signal numbers differ by OS)
"""
import os, resource, subprocess, sys, tempfile

os.environ["API_KEY"] = "sk-not-a-real-key"     # a secret in the parent

# ── 1. Four candidates standing in for what a loop has produced ──────────
CANDIDATES = {
    "well-behaved":  "import os; print('API_KEY' in os.environ)",
    "writes-forever": "open('big','wb').write(b'x'*10_000_000)",
    "spins":         "while True: pass",
    "sleeps":        "import time; time.sleep(60)",
}

# ── 2. Limits applied in the child before it runs a line of candidate ────
def limits():
    resource.setrlimit(resource.RLIMIT_CPU, (1, 1))          # 1 CPU-second
    resource.setrlimit(resource.RLIMIT_FSIZE, (1_000_000,) * 2)  # 1 MB file
    resource.setrlimit(resource.RLIMIT_NOFILE, (32, 32))

def run(code, wall=3):
    with tempfile.TemporaryDirectory() as scratch:           # fresh directory
        try:
            p = subprocess.run([sys.executable, "-c", code], cwd=scratch,
                               env={}, capture_output=True, text=True,
                               preexec_fn=limits, timeout=wall)
            return p.returncode, p.stdout.strip()
        except subprocess.TimeoutExpired:
            return "wall-clock kill", ""

# ── 3. Report ────────────────────────────────────────────────────────────
for name, code in CANDIDATES.items():
    status, out = run(code)
    print(f"{name:<15} exit={status!s:<16} {out}")
print("parent still sees API_KEY:", "API_KEY" in os.environ)
well-behaved    exit=0                False
writes-forever  exit=1                
spins           exit=-24              
sleeps          exit=wall-clock kill  
parent still sees API_KEY: True

The well-behaved candidate runs, and it cannot see API_KEY even though the parent holds one. The file writer hits the one-megabyte limit and Python raises an error, so the exit status is 1. The spinner is killed by the CPU limit after one CPU-second: an exit status of −24 means signal 24, SIGXCPU, which is the signal for exceeding the CPU limit on both macOS and Linux. The sleeper uses no CPU, so only the parent's wall-clock timeout ends it. This is why you need both kinds of limit: CPU time catches the busy loop, wall clock catches the idle one.

On Linux you would set these limits with control groups (cgroups), a kernel feature that caps the resources of a set of processes. The kernel documentation for cgroup version 2 describes the files you write. The file memory.max sets a hard limit in bytes. When usage reaches it, the out-of-memory killer runs inside the group. The file pids.max caps the number of processes. A fork that would exceed it fails, and nothing is killed. The file cpu.max takes a quota and a period in microseconds. Processes over quota are throttled, not killed. The file io.max limits bytes and operations per second for each disk. Excess input and output is delayed. Note the difference: some limits kill, and some slow the process down. A watchdog that only listens for kills will miss a throttled loop.

Common misconception

"setrlimit is a sandbox." It is a speed bump for honest mistakes. It does not stop the process from opening a network socket, reading files its user can read, or signalling its neighbours. The script above is a model of the lifecycle (fresh directory, empty environment, limits, timeout) and not the boundary. The boundary is a separate user or a container, plus the firewall below. Treat the rlimits as a second line.

Deny by default on the network

The network is the layer a loop most needs and can least be trusted with. It needs it to call the model and to install pinned packages. It cannot be trusted with it because the network is the way to reach both an answer key and a stranger's server. The old advice, "block the bad hosts", fails on its first day, because the list of bad hosts is unbounded. The right model is the opposite: refuse everything, then add the few destinations the task needs.

Two design choices decide whether this holds.

  1. Make the proxy the only route. It is not enough to set HTTP_PROXY in the candidate's environment, because the candidate can unset it or open a socket directly. The firewall rule must drop every packet from the sandbox that is not addressed to the proxy. Then a request that skips the proxy simply has nowhere to go.
  2. Decide at the proxy, after parsing. The gate sees a URL as a string. It must extract the real host the way the client library will, and compare that. Matching text anywhere in the URL is how https://evil.example/?ref=pypi.org gets through.
Step through

One request through the gate

  1. The candidate sends a request. It uses the proxy's address because the firewall leaves no other route.
  2. The firewall passes it. The only packets that leave the sandbox are addressed to the proxy, which runs under another user.
  3. The proxy parses the URL. It takes the host the way the client library would, dropping any user@ prefix, port and trailing dot, and lowercases it.
  4. The allowlist is checked on the parsed host. The entry is an exact host, or a host with a fixed path prefix. Anything else stops here.
  5. The ledger is checked. Today's request count and byte count must stay under the cap. A request that passes the allowlist but breaks the cap is still denied.
  6. Forward, or deny and learn. An allowed request goes upstream and its size is recorded. A denial is logged with its reason, because the pattern of denials is the best early warning you have.

Writing the gate

The gate below follows the steps. It uses urlsplit from the standard library to extract the host, which is the same parsing a client library does. The allowlist has two kinds of entry. An exact host is allowed for any path. A shared host, which serves content from many people, is allowed only under a fixed path prefix. The reason for the second kind comes up in the next section.

The idea

  1. parts ← parse the URL; take the hostname the way a client would
  2. refuse any scheme but https, and any IP literal
  3. normalise: lowercase, strip the trailing dot
  4. allow only an exact host, or a shared host under its path prefix
  5. return the decision and the reason; deny everything else
"""A deny-by-default egress gate, tested against requests an agent might send.

Usage: python3 egress_gate.py
"""
from urllib.parse import urlsplit
import ipaddress

# ── 1. The allowlist: exact hosts, and path prefixes for shared hosts ────
EXACT_HOSTS = {"pypi.org", "files.pythonhosted.org", "api.example-llm.com"}
PATH_RULES = {"raw.githubusercontent.com": "/our-org/pinned/"}  # shared host

def gate(url):
    """Return (allow, reason). Anything not listed is denied."""
    parts = urlsplit(url)
    if parts.scheme != "https":
        return False, "scheme is not https"
    host = (parts.hostname or "").rstrip(".").lower()  # drops user@ and :port
    try:
        ipaddress.ip_address(host)
        return False, "IP literal"
    except ValueError:
        pass
    if host in EXACT_HOSTS:
        return True, "exact host"
    prefix = PATH_RULES.get(host)
    if prefix and parts.path.startswith(prefix):
        return True, "host + path prefix"
    return False, "not on the allowlist"

def naive(url):                      # the check people write first
    return "pypi.org" in url

# ── 2. Requests: legitimate ones first, then attacks ─────────────────────
REQUESTS = [
    "https://pypi.org/simple/numpy/",
    "https://files.pythonhosted.org/packages/ab/numpy.whl",
    "https://raw.githubusercontent.com/our-org/pinned/req.txt",
    "https://raw.githubusercontent.com/attacker/dump/main/x",
    "https://pypi.org.evil.example/simple/",
    "https://evil.example/?ref=pypi.org",
    "https://pypi.org@evil.example/simple/",
    "https://PYPI.ORG./simple/numpy/",
    "http://pypi.org/simple/numpy/",
    "https://151.101.0.223/simple/",
    "https://aGVsbG8.t.evil.example/",
]

print(f"{'request':<56}{'naive':>6}  gate")
for url in REQUESTS:
    ok, why = gate(url)
    print(f"{url[:55]:<56}{'allow' if naive(url) else 'deny':>6}  "
          f"{'ALLOW' if ok else 'deny '} ({why})")

Compare the two columns. The naive check, "pypi.org" in url, allows five of eleven requests. Three of those five are attacks: a look-alike subdomain of an attacker's domain, a query string that mentions the name, and a pypi.org@evil.example URL whose real host is the part after the @. It also wrongly allows plain HTTP. At the same time it denies three legitimate requests (the package host, the pinned file and an upper-case name), so it is both too open and too strict. The gate gets all eleven right. Two details matter. The pinned file on raw.githubusercontent.com is allowed only under the organisation's own path. Any other path on that host is open to anyone on the internet, so allowing the host would allow the world.

That point generalises. A host that lets anyone publish content is not an allowlist entry; it is an open relay. A code host, a paste site, a package index and a dataset hub all accept uploads from strangers, and so does any of them an agent can write to. An agent that can read from such a host can read a stranger's answer key. An agent that can write to one can send data out and pick it up later from the other side, with no direct connection to its own server. The defences are to allow paths and not hosts, and to pin exact versions. Best of all, fetch what the run needs once, before it starts, into a local mirror. Then the sandbox needs nothing at run time.

What an allowed channel still leaks

Suppose the gate is perfect. It allows exactly the requests you listed and nothing else. Can anything still leave? Yes: which request the agent sends, and when, carries information. If there are 40 allowed URLs, the agent can encode five bits in each request by choosing which of the 40 to fetch. Over thousands of requests this adds up. This is a covert channel: a way to move information using a mechanism that was not designed for communication and that the policy therefore does not see.

We can bound it. If each request can take one of M forms that the receiver can tell apart, one request carries at most log2 M bits. Over N requests the total is at most N times that. This is the noiseless limit from information theory, and a real receiver will do worse. A bound is what we want here, because it tells us how much to cap.

Plug in numbers. The script below fixes the run at five days with one request a minute. It then computes the bits per request for four channels and the time to move a 4 KiB key file. The first channel is a name in the Domain Name System (DNS), the lookup that turns a name into an address. A name may have 253 characters, and each label between dots may have 63. An attacker who controls a domain can put data in the labels before it. Any lookup of that name delivers the data to the attacker's name server, even if the web request is never made. Each base-32 character carries 5 bits.

The idea

  1. N ← days × 24 × 60 × requests per minute
  2. for each channel: M ← the number of distinguishable requests; b ← log2 M
  3. bound ← N × b, converted to kibibytes
  4. days to leak the secret ← secret bits ÷ (b × requests per day)
"""How many bits can leave through channels the allowlist permits?

Bound: L <= N * log2(M). Usage: python3 leak_capacity.py
"""
import math

# ── 1. Assumptions (illustrative, stated up front) ───────────────────────
DAYS = 5                      # how long the loop runs
REQ_PER_MIN = 1               # requests the allowlisted host accepts
BASE32_BITS = 5               # bits carried by one base32 character
SECRET_BITS = 8 * 4096        # a 4 KiB key file

# ── 2. A DNS query name: at most 253 characters, labels of at most 63 ────
def dns_payload_chars(domain):
    best = 0
    for n in range(1, 254):
        labels = math.ceil(n / 63)
        total = n + (labels - 1) + 1 + len(domain)   # data, dots, tail
        if total <= 253:
            best = n
    return best

# ── 3. Bits per request M for each channel (M = distinct request forms) ──
chars = dns_payload_chars("x.io")
channels = {
    "DNS name under attacker domain": chars * BASE32_BITS,
    "free-form 2,048-byte query string": 2048 * 8,
    "choice among 40 pinned URLs": math.log2(40),
    "choice among 2 pinned URLs": math.log2(2),
}

# ── 4. N requests over the run, leak bound, days to move the secret ──────
N = DAYS * 24 * 60 * REQ_PER_MIN
print(f"requests over {DAYS} days at {REQ_PER_MIN}/min: N = {N}")
print(f"payload chars in a 253-char DNS name under 'x.io': {chars}\n")
print(f"{'channel':<36}{'bits/req':>9}{'bound (KiB)':>13}{'days to 4 KiB':>15}")
for name, b in channels.items():
    leak_kib = N * b / 8 / 1024
    days = SECRET_BITS / (b * REQ_PER_MIN * 60 * 24)
    print(f"{name:<36}{b:>9.1f}{leak_kib:>13.1f}{days:>15.2f}")
requests over 5 days at 1/min: N = 7200
payload chars in a 253-char DNS name under 'x.io': 245

channel                              bits/req  bound (KiB)  days to 4 KiB
DNS name under attacker domain         1225.0       1076.7           0.02
free-form 2,048-byte query string     16384.0      14400.0           0.00
choice among 40 pinned URLs               5.3          4.7           4.28
choice among 2 pinned URLs                1.0          0.9          22.76

The last column is the lesson. A DNS lookup can carry 1,225 bits, so the whole key leaves in under half an hour. A free-form query string is faster still. But a gate that accepts only 40 exact URLs forces the attacker down to 5.3 bits per request, and moving the key takes about four days of the five. A gate with two allowed URLs takes about 23 days, longer than the run. The tightest policy is the one with the fewest distinguishable allowed requests: pinned exact URLs, no free-form query strings, and no DNS name resolved by the sandbox except the proxy's. Resolution happens at the proxy, never in the candidate.

A ledger: caps sized from the honest need

The bound says what a cap buys. The question is how to set it. Set each cap from what an honest loop needs, with a modest margin, not from what feels safe. A loop that fetches 48 pinned files a day does not need a limit of 10,000. The ledger below counts requests and bytes per day at the gate and denies anything over the cap. In the simulation an honest worker makes 48 requests a day. An attacker tries to leak the 4 KiB key by choosing which of 40 pinned URLs to fetch, and spends whatever allowance is left. All URLs are allowed by the gate, so the only things standing in its way are the caps.

"""A five-day loop behind an egress proxy that keeps a ledger and enforces caps.

An attacker tries to move a 4 KiB secret out by choosing among pinned URLs.
Usage: python3 egress_ledger.py
"""
import math, random

random.seed(7)

# ── 1. Policy: pinned URLs only, with daily request and byte caps ────────
PINNED = [f"https://pypi.org/simple/pkg{i:02d}/" for i in range(40)]
DAILY_REQUESTS = 120            # hard cap per day, set from the honest need
DAILY_BYTES = 2_000_000         # cap on bytes fetched per day
BITS_PER_CHOICE = math.log2(len(PINNED))

class Ledger:
    def __init__(self):
        self.day, self.requests, self.bytes = 0, 0, 0
        self.denied = {"not pinned": 0, "request cap": 0, "byte cap": 0}
    def new_day(self):
        self.day += 1
        self.requests = self.bytes = 0
    def decide(self, url, size):
        if url not in PINNED:
            self.denied["not pinned"] += 1; return False
        if self.requests >= DAILY_REQUESTS:
            self.denied["request cap"] += 1; return False
        if self.bytes + size > DAILY_BYTES:
            self.denied["byte cap"] += 1; return False
        self.requests += 1; self.bytes += size
        return True

# ── 2. Simulate: honest fetches plus an attacker spending the same cap ───
SECRET_BITS = 8 * 4096
ledger, leaked = Ledger(), 0.0
print(f"{'day':>3}{'allowed':>9}{'denied':>8}{'leaked bits':>13}")
for day in range(1, 6):
    ledger.new_day()
    before = sum(ledger.denied.values())
    for minute in range(24 * 60):
        if minute % 30 == 0:                         # honest: 48 a day
            ledger.decide(random.choice(PINNED), 10_000)
        if minute % 10 == 5:                         # attacker: 144 a day
            if ledger.decide(random.choice(PINNED), 10_000):
                leaked += BITS_PER_CHOICE
    allowed = ledger.requests
    print(f"{day:>3}{allowed:>9}{sum(ledger.denied.values())-before:>8}"
          f"{leaked:>13.0f}")

print(f"\nsecret is {SECRET_BITS} bits; leaked after 5 days: {leaked:.0f} "
      f"({100*leaked/SECRET_BITS:.1f}%)")
print("denials by reason:", ledger.denied)
day  allowed  denied  leaked bits
  1      120      72          479
  2      120      72          958
  3      120      72         1437
  4      120      72         1916
  5      120      72         2395

secret is 32768 bits; leaked after 5 days: 2395 (7.3%)
denials by reason: {'not pinned': 0, 'request cap': 360, 'byte cap': 0}

The cap of 120 requests a day holds: 120 are allowed and the rest denied, every day. The attacker's share of the allowance, about 72 requests, leaks about 480 bits a day, 2,395 bits (7.3 per cent of the key) after five days. A cap does not stop leakage. It makes the leak slow and measurable, and a 4 KiB key would need more than two months at this rate. Three further observations follow from the output.

  • Denials are data. Every one of the 360 denied requests is evidence. A normal loop hits its cap rarely, if ever. A loop that hits the cap every day is either misconfigured or being used, and the operator should be told either way. The rate of denials is the first signal the incident playbook in chapter 5 watches.
  • The cap starves the honest worker too. The attacker and the honest worker share a budget, and the attacker spends it. In a real design the cap is per principal or per candidate, so one process cannot starve another, and a candidate that exhausts its own cap is itself a signal.
  • Caps interact with the bound. Cutting N by half halves the leak. Cutting M from 40 to 2 cuts bits per request from 5.3 to 1, a bigger saving, and it comes from the allowlist rather than the cap. Use both.

Analogy: the customs hall

A customs hall does not ask which smugglers are known. It routes every traveller through one door, checks each against a list of what may enter, and keeps a count of what passed. Lanes that carry a lot of goods each day get more scrutiny than lanes that carry little. A traveller who keeps arriving with the same odd parcel is noticed even if each parcel is allowed.

Where it breaks down: a traveller is stopped at the door, but a software agent can try again in a millisecond. The ledger is the part that has no human equivalent, because it makes the cost of trying again visible and bounded.

Credentials and state across days

Two things persist across a long run and need their own rules: credentials and state.

Credentials. The fresh worker above shows the first rule: the child gets an empty environment. The second rule is that what the loop does need, a model key, should be scoped and short-lived. Keep the key in the proxy, not in the sandbox, so the candidate asks the proxy to call the model and never holds the secret. Give it only the permissions the task needs. Put a spend cap on the account that matches the run's budget. Make its lifetime shorter than the run, so that rotating it is routine and not an emergency. Cloud environments add a hazard of their own: a metadata service reachable from inside the machine can hand out the machine's own credentials. Block the sandbox from it.

State. A long run needs to carry some state from one candidate to the next: the current best code, the run store, the checkpoints. Define that channel narrowly. A directory of named artifacts, written by the runner after the evaluator has accepted a result, is a good shape. The candidate's scratch directory is not part of it, so anything a candidate writes outside its output is deleted when it exits. Cap the size of the carried state as well; a quota turns "the disk filled up on day four" into a visible event on day one.

Systems connection

A default-deny egress policy is the default-deny firewall and the egress filtering of ordinary network security, applied to a process that could do almost anything. The leak bound is the covert channel analysis of the confinement problem: even a confined program can signal through any shared resource whose use the policy does not cover. Resource limits mirror the quotas of a multi-tenant system, where one tenant must not starve the others.

Key takeaways

  • A days-long loop adds patience, accumulation and absence. Deny by default makes forgotten cases fail closed.
  • One fresh process per candidate, with an empty environment, its own directory and CPU and wall-clock limits. The rlimit calls are a model, and the boundary is a user or a container.
  • Make the proxy the only route. Parse the URL as the client would, and match exact hosts or path prefixes, never substrings.
  • A host that accepts uploads from strangers is a relay, not an allowlist entry. Fetch what the run needs beforehand and pin it.
  • An allowed channel still leaks at most N log2 M bits. Shrink M with exact URLs and shrink N with caps sized from the honest need.
  • Every denial is evidence. Count them, and tell the operator.

Check your understanding

Your sandbox sets HTTP_PROXY so that all traffic goes through the allowlisting proxy. What is missing?

  1. Nothing: the variable routes every request through the proxy.
  2. A longer allowlist, so honest requests are not denied.
  3. A firewall rule that drops everything from the sandbox except traffic to the proxy.
  4. A second proxy in case the first fails.
An environment variable is a request that code may ignore or unset, and it applies only to libraries that read it. The boundary has to be a rule the candidate cannot change. A longer allowlist does not help; a second proxy has the same flaw.

The naive rule "pypi.org" in url allows https://pypi.org@evil.example/simple/. Why does the parsed-host gate deny it?

  1. The text before the @ is user information, so the real host is evil.example, which is not listed.
  2. The gate refuses any URL that contains an @ character.
  3. The path /simple/ is not on the allowlist.
  4. The scheme is https but should be http.
The gate does not reject the character; it extracts the hostname the way a client does and compares that. The path is fine on pypi.org, and https is the required scheme.

A gate allows exactly 40 pinned URLs, one request per minute, for five days (7,200 requests). Which figure is the most the agent can leak, as a bound?

  1. About 7,200 bits, one bit per request.
  2. About 288,000 bits, 40 bits per request.
  3. Zero, because every URL is allowed and harmless.
  4. About 38,300 bits, 5.32 bits per request.
Choosing one of 40 URLs carries log2 40 ≈ 5.32 bits, and 7,200 × 5.32 ≈ 38,300. The first option ignores that the choice has more than two outcomes, and the second confuses M with log2 M. The third forgets that which URL is fetched is itself a message.

In the ledger run the attacker is only slowed, not stopped. Which change reduces the leak most for the same honest workload?

  1. Raising the byte cap, so fewer requests are denied.
  2. Cutting the number of distinct allowed URLs, because that shrinks bits per request.
  3. Logging denials to a file the candidate can read.
  4. Giving the attacker a smaller scratch directory.
Fewer distinguishable requests means fewer bits per request, and unlike a request cap it does not take allowance away from honest work. Raising a cap enlarges the leak, and the other two options do not touch the channel.

A candidate sleeps for an hour inside its sandbox. Which limit stops it, and why do you need it as well as the CPU limit?

  1. The CPU limit, because sleeping counts as CPU use.
  2. The file size limit, because sleeping writes to a log.
  3. A wall-clock timeout held by the parent, because an idle process uses no CPU time.
  4. The open-files limit, because sleeping holds descriptors.
CPU time counts only while the process computes. The sleeper never accumulates it, so only elapsed time from outside can end it. In the output of the fresh-worker script the sleeper ends with a wall-clock kill.

Why is allowing the whole host raw.githubusercontent.com a weaker policy than allowing one path prefix on it?

  1. The host serves files from anyone, so allowing the host lets the agent read a stranger's data or fetch a relay's payload.
  2. The host is too slow for a research loop.
  3. Path prefixes are faster to match.
  4. The host's certificate is not trusted by the sandbox.
The risk is about who can publish there. The path prefix pins the content to your own organisation. Speed and certificates are not the concern.

This course builds the walls of Artifact 3, the evaluator-hardening kit. It teaches you to put the scorer where a search cannot reach it, to make the results it reports unforgeable, and to read what the loop did afterwards. This page says what the artifact is, what to read first, and how the five chapters fit together.

Why this matters

Artifact 3 asks you to break a grader for GPU kernels, harden it, and report how often an agent still cheats. You cannot do that honestly without a clear idea of what an agent with a shell can reach. This course gives you that idea, then turns it into the library the artifact releases: typed, attested tool results, hidden splits, a sandbox and a monitor that drop into Artifact 2's agent. After this page you know the gate you are working towards, which chapters of other courses to read before starting, and which chapter to open when a given problem appears.

Artifact 3 in one page

The path through this site produces four public artifacts. Each replicates one published result at small scale, adds one honest extension, and ships as code plus a write-up. Artifact 3 is the evaluator-hardening kit.

What you replicate

Proxy-only gains and hidden-test hardening on kernel benchmarks. KernelBench (Ouyang et al., 2025) is an open-source suite of 250 PyTorch workloads that asks a model to write GPU kernels that are both correct and fast. SpecBench (Zhao et al., 2026) measures the gap between visible and held-out tests as a sign of hacking.

What you build

A KernelBench subset where you first break the grader, then harden it, and measure the hacking rate before and after. The extension is a reusable Python library with typed, attested tool results, hidden splits and end-to-end timing, with hacking rate as a first-class metric.

What it costs

The plan estimates $200 to $400, mostly for model API calls, and 7 to 10 months from the start of the whole path at 10 to 15 hours a week. Treat both as planning estimates.

The artifact is finished when it meets its gate, a result that is public and checkable, not a private milestone:

  • The hacking rate measured on 20 or more kernels, before and after hardening.
  • One upstream pull request to a kernel benchmark or to ShinkaEvolve, an open-source framework for evolving programs with language models (Lange, Imajuku and Cetin, 2025).

A hacking rate is the share of an agent's attempts that raised the score by exploiting the evaluator instead of solving the task. Every number the artifact reports follows the standards of the whole path. It uses a fair baseline with the same budget. The evaluator sits outside the proposer's write boundary. Public and private splits are kept apart. The hacking rate is printed next to every score. Results use three seeds or more, with confidence intervals.

The five walls

The roadmap behind this path gives five rules for evaluator hygiene. Each becomes a wall, and each wall has a chapter.

1. The Threat Model of a Research Loop
Name the principals, draw the proposer's write boundary and show why a grader that shares a process with the candidate can be patched.
2. Deny-by-Default Egress & Sandboxes
A fresh sandbox per candidate, resource limits, a gate that allows only listed requests, and a bound on what the allowed channel can leak.
3. Attested Tool Results
Typed envelopes, hashes and tags, the evaluator as a separate principal, and hash-chained logs, so an agent cannot author a "tests passed" line.
4. Monitoring Transcripts Offline
Trusted and untrusted monitors, audit budgets and the edits to flag: tests, logs, timeouts and the checker.
5. Incident Playbooks for Autonomous Loops
Kill switches, budget caps, rollback and disclosure, written before you need them.

Chapter 1 sets the vocabulary, so read it first. Chapters 2 to 4 are largely independent and can be read in the order your build needs them. Chapter 5 assumes the others. The practical parts are Lab 1: Attest and Monitor a Research Loop, Workbench 1: A Locked-Down Research Sandbox and Case 1: The OpenAI and Hugging Face Incident.

What "control" means here

AI control is a research area that asks how to get useful work from a model while assuming it might be trying to undermine your safeguards. It differs from alignment, which tries to make the model want the right things. Control does not need to know which case you are in. It designs walls that hold in the worst case and measures how far from the worst case you actually are. Greenblatt, Shlegeris, Sachan and Roger ("AI Control: Improving Safety Despite Intentional Subversion", 2023) set out the approach. Redwood Research and others have continued it, including to agents that work in a shell.

For this artifact that stance is practical. You are not claiming that your agent is malicious. You are building an evaluator that gives the same answer whether it is, and a hacking rate that tells you how often the walls were tested.

Common misconception

"This is a course about stopping a rogue AI." The walls matter for a much plainer reason. A search that is rewarded for a number will find every route to the number, including the ones you did not mean. Most of what the chapters defend against is reward hacking by an agent doing what it was asked, and the same walls cover the rarer cases.

Try it yourself

Take the loop you plan to use for Artifact 3, or the autoresearch loop from Artifact 1. On one sheet of paper, list the files the agent can write and the files your scoring code reads. Circle every file that appears on both lists. That circle is your first threat model, and chapter 1 shows how to turn it into a table.

Key takeaways

  • Artifact 3 breaks a KernelBench grader, hardens it, and reports the hacking rate before and after on 20 or more kernels, plus one upstream pull request.
  • Read the A7, A3, A10, A6 and A4 chapters in the table first, then chapters 1 to 5 here.

Check your understanding

Which result completes Artifact 3's gate?

  1. A hacking rate measured on one kernel after hardening.
  2. A write-up that says the evaluator is secure.
  3. A hacking rate on 20 or more kernels before and after hardening, plus one upstream pull request.
  4. A larger score on KernelBench than any published model.
The gate asks for a measured before-and-after hacking rate on a sample large enough to mean something, and for outside contact in the form of a pull request. A claim of security or a higher score is not what the artifact measures.

A friend says: "I trust my model, so I do not need this course." Which reply fits it best?

  1. The walls also catch reward hacking, which needs no bad intent, and they give you a hacking rate to report.
  2. You are right, and you can skip chapters 2 to 5.
  3. Trust is irrelevant because every model is malicious.
  4. The course only covers prompt injection.
Hacking arises from a loose score and search pressure. The third option overstates the case, and the last misdescribes the course.

Which chapter would you open first if your agent's log said "all tests passed" but the tests had not run?

  1. Chapter 2, because the sandbox should have stopped it.
  2. Chapter 5, because it is an incident.
  3. Chapter 4, because the monitor should have caught it.
  4. Chapter 3, because a forged result is the problem attested tool results solve.
A forged line in a transcript is the case chapter 3 addresses. The monitor and the playbook help afterwards, but attestation removes the forgery path itself.

What is the main difference between AI control and alignment?

  1. Control is about weaker models and alignment about stronger ones.
  2. Control builds safeguards that hold even if the model is trying to subvert them, while alignment tries to make the model want the right things.
  3. Control is done after deployment and alignment before it.
  4. There is no difference.
The two are complementary. Control does not depend on knowing which case you are in, and that is why it suits an artifact that must be convincing to a reviewer.

A coverage matrix counts items in each cell of category by difficulty, so you decide what the benchmark covers and can see the holes. A split gives dev items to tune on and test items to report on; it must be stable (adding items never moves an old one) and grouped (items from one source land on the same side), or the dev set quietly teaches the test set.

  • coverage skips unknown labels and leaves empty cells out; thin_cells walks the full grid, so an empty cell counts as n = 0. A cell of one item can say "covered", never "measured".
  • split_of hashes the group name with SHA-256 (Python's hash changes on every run), takes it mod 1000 and compares it with dev_share × 1000.
  • assign_splits groups by source, not by id.
  • cross_split_duplicates catches what grouping misses: copies from different sources that landed on different sides. Reuse shingles and jaccard.

SHA-256 of code:5.2 mod 1000 is 203, below 300, so every code:5.2 item is dev, however the file grows.

Lab 4: Evaluate an Agent

An agent does not return an answer; it changes a database and then tells you what it did, and the two can disagree. In this lab you build the evaluation harness for a simulated shop agent that looks up orders, issues refunds and changes addresses. You grade the database it leaves behind instead of the words it says, run each task in a freshly reset world with a cap on its tool calls, repeat every task eight times and report pass@k and pass^k, put a price on every success, and finish with bootstrap error bars over tasks and a paired comparison of two agent versions.

Why this lab matters

A team that evaluates an agent by reading its final message will ship an agent that says "your refund is on its way" and has refunded nothing. A team that runs each task once will ship an agent that passes its demo and fails one customer in five. Both mistakes are cheap to avoid and easy to make, and both are visible in numbers you can compute from a few hundred lines of code. Chapter 8 explains the principles; here you write the graders, the trial runner, the two reliability metrics and the cost figures, and watch each design choice change a result: why comparing whole databases catches collateral damage, why a trial needs its own copy of the world, why pass^k falls as k grows while pass@k rises, why failures cost money, and why the error bars come from the tasks and not from the trials. The method is the one in the tau-bench case study, at a scale you can read in one sitting. The uncertainty tools are those of chapter 4 and the cost discipline is that of chapter 19.

Deterministic, offline and fast

The shop is a dict, the agent is a stand-in in agents.py whose mistakes come from seeded random draws, and the "cost" is a token count from a formula, so nothing touches the network and every run prints the same numbers in well under a second. The same (task, trial) always gets the same luck (trial_rng), and the stand-in draws the same three random numbers per step whatever it does, so two agent versions run on the same trial see the same luck: that is what makes the paired comparison of milestone 5 fair. A failure that involves random trials prints the seed: python3 check.py solution 1 7 replays milestone 1 with seed 7. Python 3.9 or newer, standard library only. A short optional section shows how a real model would replace the stand-in; check.py never does that. The shop, its prices and its policy are invented for the exercise, and the dollar figures use assumed prices of $3 and $15 per million input and output tokens, which are illustrations and not any provider's price list.

What you'll build

Five milestones, each building on the last:

  1. Grade the end state: a database diff, and a grader that compares it with the expected changes (missing, wrong and unexpected paths) and checks that the reply told the customer what they needed to know.
  2. One trial in a reset world: a fresh copy of the database per trial, an agent run under a step cap, a record with the outcome, the calls and the tokens.
  3. k trials: pass@k and pass^k: the two estimators, a suite runner, per-task counts, the tasks that never pass, and the averages over tasks.
  4. What a success costs: trial cost from tokens, cost per attempt, cost per success, and the tail (95th percentile and maximum).
  5. Error bars over tasks, and a comparison: a bootstrap that resamples tasks, and a paired comparison of two agent versions on the same tasks.

Milestone 1: grade the end state

Chapter 8's rule is: check what the agent produced in the world, not what it said or which route it took. The reply is a claim, and a language model writes a fluent closing message whether or not the tool call before it worked. An exact-path check punishes valid alternatives (an agent that skips the lookup because the customer gave the order number did nothing wrong). The database is the evidence.

The grader works on a database diff: the list of leaves that changed between a snapshot taken before the trial and the database after it. For task T01, returning the lamp from order A101, a correct run changes exactly three leaves:

orders.A101.items   ['lamp', 'mug'] -> ['mug']
orders.A101.refund  0 -> 25
stock.lamp          2 -> 3

Comparing the whole diff, not a handful of fields, is what catches collateral damage. An agent that also refunded the kettle on another order would leave an extra changed leaf, and the grader reports it. grade_end_state sorts each trial's paths into three lists: missing (expected but unchanged), wrong (changed, but not to the expected old and new values) and unexpected (changed, though the task never mentioned it). The state is right only when all three are empty. The reply is checked separately for the words the customer needed.

The table shows the grader on four hand-made end states for T01. These are the cases check.py builds: validating a grader on known-good and known-bad states, before running any agent, is how you learn that it is fair.

Common misconception

"If the agent says it did something, it did." The reply is the agent's description of its own behaviour, and nothing obliges it to be accurate. Some tool errors are swallowed by the scaffold, and a model that has just seen error: not eligible can still write "Done." Always grade the state. The reverse also happens (right actions, poor message), which is why the reply is checked as well, but only for what the customer needed to be told.

def db_diff(before, after):
    """Every leaf that differs between two databases: {"orders.A101.refund": (0, 25), ...}.

    Walk both dicts together. When a key holds a dict on BOTH sides, recurse, joining the keys with ".".
    Otherwise compare the two values with ==; if they differ, record (old, new) at that path, using
    None for a key that is missing on one side. Lists are leaves (compared whole). Identical databases
    give {}. Do not modify the arguments.
    """
    out = {}

    def walk(a, b, prefix):
        for key in sorted(set(a) | set(b)):
            path = f"{prefix}.{key}" if prefix else str(key)
            x, y = a.get(key), b.get(key)
            if isinstance(x, dict) and isinstance(y, dict):
                walk(x, y, path)
            elif x != y or (key in a) != (key in b):
                out[path] = (x, y)

    walk(before, after, "")
    return out

def grade_end_state(before, after, expected_diff, reply, must_say):
    """Grade one trial by what it changed, and what it told the customer.

    actual = db_diff(before, after). Compare it with expected_diff (values may be lists or tuples:
    compare them as (old, new) tuples). Return a dict:
      missing     sorted paths expected but not changed at all
      wrong       sorted paths changed, but not to the expected (old, new)
      unexpected  sorted paths changed that the task never mentioned (collateral damage)
      state_ok    True if all three lists are empty
      reply_ok    True if every string in must_say occurs in reply (ignore case)
      ok          state_ok and reply_ok
    """
    actual = db_diff(before, after)
    want = {p: tuple(v) for p, v in expected_diff.items()}
    missing = sorted(p for p in want if p not in actual)
    wrong = sorted(p for p in want if p in actual and tuple(actual[p]) != want[p])
    unexpected = sorted(p for p in actual if p not in want)
    state_ok = not (missing or wrong or unexpected)
    low = reply.lower()
    reply_ok = all(s.lower() in low for s in must_say)
    return {"missing": missing, "wrong": wrong, "unexpected": unexpected,
            "state_ok": state_ok, "reply_ok": reply_ok, "ok": state_ok and reply_ok}

Milestone 2: one trial in a reset world

A trial is one attempt at one task. The harness has four jobs, and each has a classic failure if it is skipped.

  • Reset the world. Every trial starts from a fresh deep copy of the starting database. If trial 2 inherits the lamp that trial 1 refunded, the second refund fails and the result is a property of the order of the trials, not of the agent. The same goes for the snapshot you diff against: take the copy before the agent runs.
  • Cap the steps. An agent can loop. The Shop raises StepCapExceeded on a call past max_steps; the harness catches it, records the trial as capped, and grades whatever state is left. A capped trial is a failure even if the database and reply would have been fine, because a run that never finishes helps nobody.
  • Be reproducible. The agent's luck is drawn from trial_rng(task_id, trial), so the same trial always replays the same way. Otherwise you could never reproduce a failure to read it.
  • Record what happened. The record keeps the outcome flags, the tool calls, the tokens and the reply, so the later milestones need nothing else.

The reference stand-in passes all twelve tasks in every trial (the check verifies this, which validates the whole harness: a harness that fails a flawless agent has a bug). AGENT_V1 is the realistic one. Over 12 tasks times 8 trials, it passes 80 of 96 trials. The 16 failures break down as 8 where only the database is wrong, 5 where only the reply is wrong, 2 where both are, and one that looped to the step cap. Each of these is a different story when you read the transcript, which is what the later "Look under the hood" section does.

def run_trial(task, agent, trial, start=START, max_steps=MAX_STEPS):
    """Run ONE trial of one task and grade it. Return a record dict:
      task, trial        the task id and the trial number
      passed             grade_end_state(...)["ok"] and the trial was not capped
      state_ok, reply_ok from the grade
      capped             True if the agent hit StepCapExceeded (its reply is then "")
      steps, calls       number of tool calls, and the list of tool names in order
      tokens_in, tokens_out, reply

    Steps: build a Shop on a deep copy of `start` (the trial must not touch `start` or any other trial);
    keep a deep copy as `before`; call agent.act(shop, task, trial_rng(task["id"], trial)); catch
    StepCapExceeded; grade the database that is left, whether or not the cap was hit.
    """
    env = Shop(copy.deepcopy(start), max_steps)
    before = copy.deepcopy(env.db)
    capped = False
    try:
        reply = agent.act(env, task, trial_rng(task["id"], trial))
    except StepCapExceeded:
        capped, reply = True, ""
    grade = grade_end_state(before, env.db, task["expected_diff"], reply, task["must_say"])
    return {"task": task["id"], "trial": trial, "passed": grade["ok"] and not capped,
            "state_ok": grade["state_ok"], "reply_ok": grade["reply_ok"], "capped": capped,
            "steps": len(env.transcript), "calls": [t["tool"] for t in env.transcript],
            "tokens_in": env.tokens_in, "tokens_out": env.tokens_out, "reply": reply}

Milestone 3: k trials, pass@k and pass^k

A single trial is a sample. The same agent on the same task succeeds one time and fails the next, so you run each task n times and ask what "k attempts" would look like. Two questions are natural, and they have different answers.

pass@k
The chance that at least one of k attempts succeeds. It rises with k. It is the right number when the system can try again and a checker can recognise success (generate ten patches, run the tests, ship one that passes).
pass^k
The chance that all k attempts succeed. It falls with k. It measures consistency, and it is the number for an agent that meets each customer once and pays for every failure.

From a task's recorded counts, c successes in n trials, both can be estimated without bias by counting combinations, as in the tau-bench paper: the chance that k trials drawn without replacement from the n are all failures is C(n−c, k) / C(n, k) and that they are all successes is C(c, k) / C(n, k). So

pass@k = 1 − C(n−c, k) / C(n, k)     pass^k = C(c, k) / C(n, k)

each averaged over tasks. A worked example: a task that passes c = 6 of n = 8 trials has pass@2 = 1 − 1/28 = 0.964 and pass^2 = 15/28 = 0.536. A tempting shortcut treats the success rate as a fixed probability p = 0.75 and says pass^2 = 0.752 = 0.5625; the combination formula differs a little because it uses the counts you actually have, without replacement. At k = 1 both are the plain success rate c/n, and for any other k, pass^k ≤ c/n ≤ pass@k.

Averaging is over tasks. This matters because the tasks are not alike: some are reliable, some shaky. If every task had the same success chance p, pass^k would be pk, the serial-composition rule of availability maths, and would fall quickly. When the tasks differ, the reliable ones stay reliable and pass^k falls more slowly than pk would suggest.

The milestone also asks for the tasks that never pass. Chapter 8's rule of thumb is that a task with zero successes over many trials is more often a broken task or a broken grader than a hard one (an expected value with the wrong price, a reply word the agent never says, an unreachable goal). never_passes lists them so you read their transcripts first, before drawing any conclusion about the agent. On the real suite it returns nothing, since every task passes at least five of eight; the check tests it on hand-made counts.

def pass_at_k(n, c, k):
    """P(at least one of k trials succeeds), estimated from n recorded trials with c successes:
    1 - C(n - c, k) / C(n, k). Raise ValueError unless 1 <= k <= n and 0 <= c <= n."""
    if not (1 <= k <= n and 0 <= c <= n):
        raise ValueError(f"need 1 <= k <= n and 0 <= c <= n; got n={n}, c={c}, k={k}")
    return 1 - comb(n - c, k) / comb(n, k)

def pass_hat_k(n, c, k):
    """P(all k trials succeed), estimated from n recorded trials with c successes: C(c, k) / C(n, k).
    Same ValueError rule as pass_at_k."""
    if not (1 <= k <= n and 0 <= c <= n):
        raise ValueError(f"need 1 <= k <= n and 0 <= c <= n; got n={n}, c={c}, k={k}")
    return comb(c, k) / comb(n, k)

def run_suite(tasks, agent, n_trials):
    """Run trials 0 .. n_trials-1 of every task. Return the records, task by task in the order of `tasks`,
    trials in increasing order."""
    return [run_trial(task, agent, t) for task in tasks for t in range(n_trials)]

def task_counts(records, task_ids):
    """[(c, n)] for each task id in the order given: c = trials passed, n = trials run.
    Raise ValueError if a task id has no records."""
    out = []
    for tid in task_ids:
        rs = [r for r in records if r["task"] == tid]
        if not rs:
            raise ValueError(f"no records for task {tid!r}")
        out.append((sum(r["passed"] for r in rs), len(rs)))
    return out

def never_passes(counts, task_ids):
    """Ids of the tasks with c == 0: nobody passed in any trial. These are the tasks to read FIRST,
    because a task that never passes is more often a broken task or a broken grader than a hard one."""
    return [tid for tid, (c, n) in zip(task_ids, counts) if c == 0]

def summarise(counts, ks=(1, 2, 4, 8)):
    """Average pass@k and pass^k over tasks, for each k in ks.
    Return {"pass_at": {k: mean}, "pass_hat": {k: mean}} (the means are over tasks, not over trials).
    Raise ValueError (via pass_at_k) if some task has fewer than k trials."""
    return {"pass_at": {k: sum(pass_at_k(n, c, k) for c, n in counts) / len(counts) for k in ks},
            "pass_hat": {k: sum(pass_hat_k(n, c, k) for c, n in counts) / len(counts) for k in ks}}

Milestone 4: what a success costs

An agent that succeeds 90% of the time at ten dollars a task and one that succeeds 80% at ten cents are not comparable on accuracy alone. Agents spend tokens at every step, and the conversation they send grows as it goes, so cost per task varies far more than cost per call for a single model. The Shop meters this the way a real API would: each tool call or final reply is one model turn, whose input is the base context plus 350 tokens for every earlier turn, and whose output is 70 or 90 tokens. A three-turn trial reads 600 + 950 + 1,300 = 2,850 input tokens and writes 230 output tokens; at the illustrative prices of $3 and $15 per million that is $0.012.

Three figures matter, all computed over every trial and not just the successes:

  • Cost per attempt: total spend divided by trials.
  • Cost per success: total spend divided by successes. It is higher than cost per attempt, because failures cost money too: the 16 failed trials of AGENT_V1 burned tokens and delivered nothing.
  • The tail: the 95th percentile and the maximum. One runaway loop that makes twelve tool calls costs about eight times a normal trial, and the mean hides it. You report percentiles beside the mean for the reason given in tail latency and metrics: averages bury the events that hurt. The lab uses the nearest-rank percentile: sort the costs and take the one at position ceil(0.95 × N), counting from 1. For 20 trials that is the 19th; for 100 it is the 95th.

Two more things to see in the numbers. AGENT_V2 re-reads the order before every write, which makes it more reliable (milestone 5) and makes each attempt about 45% dearer: a reliability fix that works by extra work costs money, and it is legitimate only if you measure both. And a cost report that omits the step cap would hide the runaway: capped counts the trials that hit it.

def trial_cost(rec, price_in=PRICE_IN, price_out=PRICE_OUT):
    """Dollars for one trial: tokens_in and tokens_out at the given prices per million tokens."""
    return (rec["tokens_in"] * price_in + rec["tokens_out"] * price_out) / 1_000_000

def cost_report(records):
    """Cost figures for a set of trials. Failures cost money too. Return a dict:
      attempts, successes   number of trials, number with passed True
      total                 sum of trial_cost over all trials
      per_attempt           total / attempts
      per_success           total / successes (None if there are no successes)
      p95                   the 95th-percentile trial cost, nearest-rank: sort the costs and take
                            the one at position ceil(0.95 * attempts) (1-based)
      max                   the largest trial cost
      capped                number of trials that hit the step cap
    Raise ValueError for an empty list."""
    if not records:
        raise ValueError("no records")
    costs = sorted(trial_cost(r) for r in records)
    total = sum(costs)
    successes = sum(r["passed"] for r in records)
    return {"attempts": len(records), "successes": successes, "total": total,
            "per_attempt": total / len(records), "per_success": total / successes if successes else None,
            "p95": costs[math.ceil(0.95 * len(costs)) - 1], "max": costs[-1],
            "capped": sum(r["capped"] for r in records)}

Milestone 5: error bars over tasks, and a paired comparison

The pass^4 of AGENT_V1 over these 12 tasks is 0.530. How much would it change on another 12 tasks from the same shop? The trials of one task are not independent samples of "the agent on this kind of work": they share that task's difficulty. The independent units are the tasks, so a bootstrap resamples tasks, each with all its trials, and recomputes the statistic. (Resampling the 96 trials as if they were independent understates the uncertainty, and eight trials per task do not substitute for more tasks: they reduce the noise from the agent's randomness and leave the noise from the choice of tasks untouched.) This is the clustering point of chapter 4.

Comparing two agents adds a second idea. Run AGENT_V1 and AGENT_V2 on the same 12 tasks with the same trial luck, so the comparison is paired: task i has a count for each agent. Each bootstrap repetition draws one set of task indices and applies it to both lists, then records the difference of the statistic. Drawing independent indices for each agent would let the easy tasks of one agent meet the hard tasks of the other and inflate the interval with variance that pairing removes. You can see the effect at the limit: an agent compared with itself should give a difference of exactly zero with an interval of exactly (0, 0), and independent resampling would not.

On this data, AGENT_V2 raises pass@1 from 0.833 to 0.969 (a gain of +0.135, 95% interval +0.062 to +0.219) and pass^4 from 0.530 to 0.875 (+0.345, interval +0.161 to +0.548). Both intervals exclude zero. The price is cost: $0.0158 per success for V1 and $0.0199 for V2, about 26% more. The decision between them is no longer "which is more accurate" but "is reliability worth 26% more per success, here?", and with these numbers you can say.

def bootstrap_ci(counts, stat, B=1000, alpha=0.05, seed=0):
    """Percentile bootstrap interval for stat(counts), resampling TASKS (each with all its trials).

    counts is a list of (c, n), one per task; stat maps such a list to a number. Each of the B
    repetitions draws len(counts) task indices with random.Random(seed).randrange and applies stat to
    the resampled list. Sort the B values xs; return (xs[int(alpha / 2 * B)], xs[int((1 - alpha / 2) * B) - 1]).
    """
    rng = random.Random(seed)
    n = len(counts)
    xs = sorted(stat([counts[rng.randrange(n)] for _ in range(n)]) for _ in range(B))
    return xs[int(alpha / 2 * B)], xs[int((1 - alpha / 2) * B) - 1]

def compare_agents(counts_a, counts_b, stat, B=1000, alpha=0.05, seed=0):
    """Paired comparison of two agents on the SAME tasks (counts_a[i] and counts_b[i] are task i).

    Each repetition draws one set of task indices and applies it to BOTH lists, then records
    stat(resampled b) - stat(resampled a). Return {"a": stat(counts_a), "b": stat(counts_b),
    "diff": b - a, "ci": (lo, hi) as in bootstrap_ci, "better": "b" if lo > 0, "a" if hi < 0, else None}.
    Raise ValueError if the lists differ in length or are empty.
    """
    if len(counts_a) != len(counts_b) or not counts_a:
        raise ValueError("need two non-empty lists with one entry per task")
    rng = random.Random(seed)
    n = len(counts_a)
    xs = []
    for _ in range(B):
        idx = [rng.randrange(n) for _ in range(n)]
        xs.append(stat([counts_b[i] for i in idx]) - stat([counts_a[i] for i in idx]))
    xs.sort()
    lo, hi = xs[int(alpha / 2 * B)], xs[int((1 - alpha / 2) * B) - 1]
    a, b = stat(counts_a), stat(counts_b)
    return {"a": a, "b": b, "diff": b - a, "ci": (lo, hi), "better": "b" if lo > 0 else "a" if hi < 0 else None}

Analogy: a driving test with a bad day

A driver who passes the practical test once has shown they can drive well. Whether they are safe is a different question, and a driving examiner answers it by watching the whole route, not by asking at the end "did you drive carefully?". pass@k asks whether the best of k journeys was fine. pass^k asks whether all k were, which is what the passengers care about.

Where it breaks down: an examiner scores a driver's behaviour on a single test route. Each agent trial is a fresh, independent run on a task, and the "route" (the task) varies in difficulty from the start; most of the interesting statistics come from that variation between tasks, which has no counterpart in a test of one driver on one road.

Set LAB_MODEL to anthropic:<model-id>, openai:<model-id> or ollama:<name> first. The listing was not run here, so no output is shown.

import json
from llm import get_model, text_of, tool_calls, tool_result
from solution import load_tasks, run_suite, task_counts, summarise, cost_report   # or: from starter import ...

def schema(*names):
    return {"type": "object", "properties": {n: {"type": "string"} for n in names}, "required": list(names)}

TOOLS = [
    {"name": "lookup_order", "description": "Read one order.", "input_schema": schema("order")},
    {"name": "refund_item", "description": "Refund one item of a delivered order.", "input_schema": schema("order", "item")},
    {"name": "change_address", "description": "Change the address of an order.", "input_schema": schema("order", "address")},
]
SYSTEM = ("You are a shop assistant. Policy: refund an item only if its order has been delivered, the item is in the "
          "order and delivery was at most 30 days ago. Change an address only while the order is still processing. "
          "Look the order up before you act. If a request breaks policy, say why and change nothing. "
          "Finish with a short message that says exactly what you did, including any refund amount or new address.")

class RealShopAgent:
    name = "real"
    def __init__(self, model):
        self.model = model

    def act(self, env, task, rng):
        messages = [{"role": "user", "content": task["instruction"]}]
        while True:
            resp = self.model.complete(messages, system=SYSTEM, tools=TOOLS, temperature=0.0)
            calls = tool_calls(resp)
            if not calls:
                return env.say(text_of(resp))
            messages.append(resp.as_message())
            results = [tool_result(c["id"], json.dumps(env.call(c["name"], **c["input"]))) for c in calls]
            messages.append({"role": "user", "content": results})

tasks = load_tasks()
records = run_suite(tasks, RealShopAgent(get_model()), 3)     # 36 trials, a few hundred model calls
counts = task_counts(records, [t["id"] for t in tasks])
print(summarise(counts, ks=(1, 2, 3)))
print(cost_report(records))

What to look for: a step cap that does its job (a real model sometimes calls lookup_order again and again), the first wrong step in each failed transcript, and tasks that fail in all trials (check the key before blaming the model). Two caveats. The token meter in shop.py is a formula for the stand-in, not a measurement; with a real model take the token counts from each response's usage and sum them per trial. And a real model at temperature zero is still not perfectly deterministic, so a few trials per task is the minimum for any claim. Keep the raw transcripts and pin the model version.

Systems connection

An end-state grader is a test oracle that asserts on state, not on calls, and the reset-per-trial rule is test isolation: each test gets its own fixtures (testability). The step cap is a timeout and a retry budget; the shop is a fake you control, exactly as a test double is. The arithmetic of pass^k is serial composition: k independent successes in a row multiply their probabilities, the rule behind the nines of availability, and reporting the 95th percentile beside the mean is the practice of tail latency. The tool that refunds anything the database allows, with policy only in the prompt, is an authorisation design that deserves the scepticism of chapter 8 of the security course: put hard limits in the tool, not only in the instructions. The loop that ends at a step cap is the iteration budget of the tool-calling loop.

What you learned

  • Grade the database the agent leaves behind, as a diff against the expected changes. Missing, wrong and unexpected paths each name a different kind of failure, and comparing the whole diff is what catches collateral damage. Check the reply only for what the customer needed to be told.
  • Validate the grader on hand-made good and bad states, and run a flawless agent through the harness, before you trust any score.
  • A trial needs its own copy of the world, a step cap and a reproducible source of luck. A capped trial is a failure.
  • Repeat every task. pass@k (some attempt works) rises with k and measures capability; pass^k (every attempt works) falls with k and measures reliability. Average over tasks, and read the tasks that never pass first.
  • Report cost per success beside every score, and the tail beside the mean: failures cost money, and one runaway loop can cost eight normal attempts.
  • Bootstrap over tasks, not trials. Compare agents with a paired design: the same tasks, the same luck, one set of resampled indices for both.

Check your understanding

For task T07 (a refund request outside the return window) the correct outcome is that nothing changes and the reply explains why. An agent calls refund_item, the tool returns an error, and the agent replies "Done." The database is unchanged. How does the lab's grader score it?

  1. Pass: the state matches the empty expected diff
  2. Fail: the state is right but the reply lacks the reason, so reply_ok is False
  3. Fail: any call to a write tool is a failure
  4. Pass: the tool refused, so no harm was done
The grader checks two things: the state, and the words the customer needed to hear. Here the state is fine, but "Done." claims something false and omits the reason, so the reply check fails. Option 3 describes a process rule the lab's grader does not apply (it is a good extension). The state-only reading of options 1 and 4 would reward an agent that lies about what it did.

A task passes 6 of 8 trials. Which pair is closest to its pass@2 and pass^2 as the lab computes them?

  1. 0.75 and 0.75
  2. 0.96 and 0.56, because pass^2 is 0.75 squared
  3. 0.96 and 0.54: 1 − C(2,2)/C(8,2) and C(6,2)/C(8,2)
  4. 1.00 and 0.75
With counts, pass@2 = 1 − 1/28 = 0.964 and pass^2 = 15/28 = 0.536. Option 2's 0.5625 is the same idea with a fixed success rate of 0.75: close, but it is not what the combination formula gives from eight recorded trials. Option 1 would be right only at k = 1.

You compare two agent versions on 40 tasks, running each task 10 times, and want a confidence interval for the difference in pass^4. How should you resample?

  1. Draw task indices with replacement and apply the same indices to both agents' counts
  2. Draw 400 trials with replacement for each agent independently
  3. Draw task indices separately for each agent, so each agent gets its own resample
  4. Do not resample: 400 trials make the difference exact
The trials of a task share that task's difficulty, so the tasks are the independent units, and a paired design uses one set of indices for both agents so that task difficulty cancels in the difference. Option 2 understates the uncertainty; option 3 throws away the pairing and widens the interval; option 4 confuses many trials with many tasks.

An agent costs $1.27 over 96 trials, of which 80 pass. Which is the cost per success, and why does it differ from the cost per attempt of about $0.013?

  1. About $0.013: the cost of an attempt does not depend on whether it succeeds
  2. About $0.0016: only the successful trials should be charged
  3. About $0.0004: divide by the 96 trials and then by the 80 successes
  4. About $0.016: all the spend, failures included, divided by the 80 successes, so failures raise the price of each success
$1.27 / 80 = $0.0159. Failed trials cost tokens and deliver nothing, and that cost has to be paid by the successes. Option 1 is the cost per attempt, a different figure. Option 2 charges only successes and ignores the money the failures burned.

One task has failed in all 8 trials for every agent version you have tried. What is the best first action?

  1. Conclude it is too hard and keep it as a stretch target
  2. Read its transcripts and check the expected diff and reply words: a task that never passes is more often a broken task or grader than an impossible one
  3. Remove it, since a task nobody passes tells you nothing about ranking
  4. Raise the step cap so the agent has more room
A zero over many trials and versions is the signature of an unreachable key or a faulty grader (a wrong price in the expected diff, a reply word nobody says). Keeping it unexamined or deleting it (options 1 and 3) skips the diagnosis. A bigger step cap does nothing for a task whose key is wrong.

Why does the stand-in agent draw three random numbers per step whatever it does, even when the extra numbers go unused?

  1. To make the agent slower and more realistic
  2. Because Python's random generator requires an even number of draws
  3. So that two agent versions run on the same trial see the same luck: the draws stay aligned, and a paired comparison measures the agents and not the dice
  4. To increase the number of failures
If one version consumed more random numbers than the other, their luck would drift out of step after the first difference and the comparison would mix agent quality with random variation. Fixing the number of draws per step is the common-random-numbers trick, and it is what makes the paired bootstrap tight.

Lab 1: An Eval Harness with Error Bars

Chapter 2 said a harness is a loader, a runner, some checks and a reporter that diffs two runs. Chapter 4 said that every number the harness prints is an estimate with an error bar, and that a comparison of two systems is stricter and cheaper when it is paired. In this lab you build both halves: the small harness (cases as data, assertions, a runner that survives timeouts, a summary by tag) and the statistics on top of it (standard errors, the Wilson interval, a bootstrap that resamples whole groups, a paired comparison, the sample size you needed in the first place), and then you point it at three versions of a support assistant and decide which one to ship.

Why this lab matters

Almost every decision in this course ends as "version B scored higher than version A, so ship B". The people who make that decision well are not the ones with the cleverest metric. They are the ones who know how wide the error bar is, who look at the diff and not only the total, and who can say "this eval could not have told us" when the interval spans zero. None of that is hard once the pieces exist, and all of it is easy to get subtly wrong: count a timeout as a pass, resample single questions when the questions come in families, compare two intervals by eye instead of pairing the cases. You will write each piece yourself and a checker will catch each of those mistakes. The harness you end up with is the one Lab 7 wires to a release gate, so it is worth building properly once.

Deterministic, offline and fast

The system under test is a stand-in assistant (assistant.py) that replays canned replies with seeded randomness, so the same attempt of the same prompt always gives the same reply and every run of check.py prints the same numbers. Nothing touches the network. Random draws in the checks are seeded, and a failure prints the seed so you can replay it: python3 check.py solution 3 7 runs milestone 3 with seed 7. The whole check takes about a second. Python 3.9 or newer, standard library only. At the end there is an optional section on pointing the harness at a real model; check.py never does.

What you'll build

Five milestones, each building on the last:

  1. Cases as data and assertions: parse and validate a JSON Lines case file, apply six kinds of check to a reply and report why a reply failed.
  2. The runner and the summary: run every case k times, record pass, fail or error per attempt (a timeout is an error, not a verdict), and roll the results up overall and by tag.
  3. Error bars: the standard error, the Wilson interval, the clustered standard error and a percentile bootstrap that can resample whole groups of related cases.
  4. Paired comparison and the diff: the paired and unpaired standard errors side by side, and the list of cases a change fixed and broke.
  5. Power, a verdict and the whole comparison: how many questions you needed, what an interval that touches zero means, and one function that runs two systems and says what you can and cannot conclude.

Milestone 1: cases as data and assertions

A test case is one input plus what you want to check about the reply, and chapter 2 argued for storing cases as data. The payoff is practical: the person who found the failure can add a line without touching Python, the file diffs cleanly, and the same file runs against any system. Data from outside your code is untrusted, so load_cases validates: every line is a JSON object with an id, an input and a non-empty list of checks; ids are unique, because results are compared across runs by id. A duplicate id would let one case silently overwrite another. The error should say which line, so that whoever edited the file can fix it.

An assertion is a small pure function from a reply to pass or fail with a reason. Six kinds cover the families of chapter 2:

  • Must contain / must not contain (contains, not_contains) for hard requirements and forbidden phrases. Prefer the forbidden form: a required sentence breaks on harmless rewording.
  • A forbidden pattern (not_regex), for things like "I have cancelled" or anything that looks like an email address.
  • Structure (json_keys): the reply parses as a JSON object with the required keys. A list or a bare string is a failure, and so is prose.
  • A number within a tolerance (number_close): compare the last number in the reply, ignoring thousands commas, to the expected value. Exact string equality fails on "$1,204.50" against "1204.5".
  • Length (max_words).

Two design points deserve a sentence each. A check must return a reason when it fails, because a failing case you cannot debug is a case people stop trusting. And an unknown check type must raise, not pass: if someone types "contians" in the case file, a harness that shrugs and returns "ok" has just turned a typo into a permanent false pass. That is the "test the test" lesson from chapter 2 in miniature, and check.py applies it to your checks: for every one of the 160 cases it runs the known-good reply and the known-bad reply through grade and insists on pass and fail respectively.

def load_cases(text):
    """Parse a JSON Lines string into a list of case dicts.

    One JSON object per non-blank line. Every case needs the REQUIRED_FIELDS, ids must be unique,
    and `checks` must be a non-empty list. Raise ValueError (naming the line or id) otherwise.
    A case without a "group" gets its own id as its group; one without "tags" gets [].
    """
    cases, seen = [], set()
    for lineno, line in enumerate(text.splitlines(), start=1):
        if not line.strip():
            continue
        try:
            case = json.loads(line)
        except json.JSONDecodeError as e:
            raise ValueError(f"line {lineno}: not valid JSON ({e.msg})")
        if not isinstance(case, dict):
            raise ValueError(f"line {lineno}: each line must be a JSON object")
        for key in REQUIRED_FIELDS:
            if key not in case:
                raise ValueError(f"line {lineno}: missing field {key!r}")
        if case["id"] in seen:
            raise ValueError(f"line {lineno}: duplicate id {case['id']!r}")
        if not isinstance(case["checks"], list) or not case["checks"]:
            raise ValueError(f"line {lineno}: case {case['id']!r} needs at least one check")
        seen.add(case["id"])
        case.setdefault("group", case["id"])
        case.setdefault("tags", [])
        cases.append(case)
    return cases

def run_check(output, check):
    """Apply ONE assertion to a reply. Return (ok, reason); reason is "" when ok.

    check["type"] is one of:
      contains      value            the text appears in the reply
      not_contains  value            the text does not appear
      not_regex     pattern          re.search finds no match
      json_keys     keys             the reply parses as a JSON object containing all the keys
      number_close  expected, rel_tol   the LAST number in the reply is within rel_tol * |expected|
      max_words     value            len(reply.split()) <= value
    An unknown type raises ValueError (a typo in a case file must not pass silently).
    """
    kind = check["type"]
    if kind == "contains":
        return check["value"] in output, f"missing {check['value']!r}"
    if kind == "not_contains":
        return check["value"] not in output, f"contains forbidden {check['value']!r}"
    if kind == "not_regex":
        return not re.search(check["pattern"], output), f"matches /{check['pattern']}/"
    if kind == "json_keys":
        try:
            data = json.loads(output)
        except ValueError:
            return False, "not valid JSON"
        if not isinstance(data, dict):
            return False, "JSON is not an object"
        missing = [k for k in check["keys"] if k not in data]
        return not missing, f"missing keys {missing}"
    if kind == "number_close":
        nums = _numbers(output)
        if not nums:
            return False, "no number in the reply"
        ok = abs(nums[-1] - check["expected"]) <= check["rel_tol"] * abs(check["expected"])
        return ok, f"last number {nums[-1]:g} is not within {check['rel_tol']:.1%} of {check['expected']:g}"
    if kind == "max_words":
        n = len(output.split())
        return n <= check["value"], f"{n} words > {check['value']}"
    raise ValueError(f"unknown check type {kind!r}")

def grade(output, checks):
    """Run every check. Return the list of failure reasons ([] means the case passed)."""
    reasons = []
    for check in checks:
        ok, why = run_check(output, check)
        if not ok:
            reasons.append(why)
    return reasons

Milestone 2: the runner and the summary

The runner calls the system under test and records what happened. Its interface is deliberately narrow, "prompt and attempt number in, text out", so that a prompt, a retrieval pipeline or an agent can sit behind it. Two ideas from chapters 2 and 4 live here.

Three outcomes, not two. An attempt that returns a reply which fails a check is a fail. An attempt that raises (a timeout, a rate limit, a malformed response) is an error, and it is a fact about the run, not about the model. The runner must catch the exception, record it and carry on: a harness that dies on the 90th of 400 cases teaches people to run it less. But an error is also not a pass and must not vanish from the denominator, or a flaky week looks like an improvement. So a case's score is the share of its attempts that passed, with errors counted as not passing, and the summary reports the number of errors in a column of their own so that a run with many errors is visibly not a run you can interpret.

Several attempts per case. A model sampled at non-zero temperature may pass a case on one attempt and fail the next. Chapter 4 explains why the right response is not to turn the temperature to zero but to answer each case k times and score the mean: the answer-level noise is divided by k, and the question-level noise is untouched. Everything after this milestone works on one number per case, the per-case score between 0 and 1. That is the "pool the k answers into a per-question average" rule, and it is what stops you from claiming the precision of k×n questions when you have only n.

The summary reports the overall score (the mean of per-case scores), the error and attempt counts, and a score by tag with the number of cases beside each rate, because an overall 90% can hide a slice at 60%, and a slice of eight cases is noisy.

def run_suite(system, cases, k=1):
    """Run every case k times against `system` and return one Result per case, in order.

    system(case["input"], sample) returns the reply text for attempt number `sample` (0..k-1).
    If the call raises ANY exception, that attempt's outcome is "error" (reasons []): the run
    carries on. A reply that fails a check is "fail"; one that passes them all is "pass".
    """
    results = []
    for case in cases:
        outcomes, reasons = [], []
        for sample in range(k):
            try:
                reply = system(case["input"], sample)
            except Exception:                          # a harness problem, not a verdict
                outcomes.append("error")
                reasons.append([])
                continue
            why = grade(reply, case["checks"])
            outcomes.append("fail" if why else "pass")
            reasons.append(why)
        results.append(Result(case["id"], case.get("group", case["id"]), list(case.get("tags", [])),
                              outcomes, reasons))
    return results

def summarise(results):
    """Roll results up into {"n", "score", "errors", "attempts", "by_tag"}.

    n          number of cases
    score      mean of the per-case scores (errors count as not passing)
    errors     total number of "error" attempts, over all cases
    attempts   total number of attempts
    by_tag     {tag: {"n": cases with the tag, "score": their mean score}}
    """
    scores = [r.score for r in results]
    by_tag = {}
    for r in results:
        for tag in r.tags:
            by_tag.setdefault(tag, []).append(r.score)
    return {
        "n": len(results),
        "score": sum(scores) / len(scores) if scores else 0.0,
        "errors": sum(o == "error" for r in results for o in r.outcomes),
        "attempts": sum(len(r.outcomes) for r in results),
        "by_tag": {t: {"n": len(v), "score": sum(v) / len(v)} for t, v in by_tag.items()},
    }

Milestone 3: error bars

Now the part of the lab that is about chapter 4. Version 2 scores 64.6% on 160 cases. What does that number mean? Imagine a colleague writing a different 160 questions about the same product: they would get a different score, because the cases are a sample. The standard error says how much. Four tools, each for a different situation:

mean_se(xs)
The standard error of a mean: the sample standard deviation (dividing by n−1) over √n. This is the right formula for per-case scores that are not just 0 or 1, and it is the building block for the rest.
wilson(k, n)
The Wilson interval for k successes in n independent trials. The textbook interval p ± 1.96√(p(1−p)/n) says 20 out of 20 is 100% with no uncertainty, which is absurd; Wilson gives 83.9% to 100%. Use it for small slices (a tag with eight cases) and rates near 0 or 100%. 0 of 10 failures gives an upper bound of 27.8%, which is how a safety eval should read "we saw none".
clustered_se(xs, groups)
The standard error when scores come in related clusters. The 160 cases are 40 intents asked four ways. If the assistant misreads an intent it misses all four, so there are closer to 40 independent observations than 160. Miller's formula adds to the naive variance the covariance of every pair of different items inside the same cluster: SE2 = SEnaive2 + (1/n2) ∑clusters ∑i≠j (xi − m)(xj − m). Hand check: scores 1, 1, 0, 0 in clusters {a, a, b, b}: naive variance of the mean is 1/12, the cross terms add 1/16, and the standard error is √(7/48) = 0.382.
bootstrap_ci(values, groups=None, B, alpha, seed)
A percentile bootstrap: build B pseudo-evals by resampling, take each one's mean, sort, and read off the middle 95%. It needs no formula, which is why it will carry the paired comparison next milestone. The one rule that matters: resample the independent unit. With groups given, draw whole groups with replacement and pool all their values. Pool, do not average group means, or groups of different sizes get the wrong weight.

What the difference looks like on this data is the point of the milestone. For version 2 the per-case bootstrap gives 57.7% to 71.0%, a width of 13.3 points. Resampling whole groups gives 51.9% to 77.5%, a width of 25.6 points, and 2 × 1.96 × the clustered standard error (6.3 points) lands at 24.8, so the formula and the group bootstrap agree. The first interval is the wrong answer produced with confidence; it is nearly half as wide as the truth. Another way to hold on to it: the 160 cases are worth about 40.

Hints try without first
  • clustered_se: for each cluster, with deviations di = xi − mean, the sum over i ≠ j of di dj equals (sum(d))**2 - sum(d*d). No double loop needed.
  • In the grouped bootstrap, precompute (sum, count) for each group once; each repetition is then a few hundred integer additions rather than a rebuild of 160 values.
  • The statistic of a grouped repetition is total / count over the pooled values, not the mean of the group means.
  • wilson: denom = 1 + z*z/n, centre = (p + z*z/(2*n)) / denom, half = z * sqrt(p*(1-p)/n + z*z/(4*n*n)) / denom. Clip to [0, 1].
  • If the group bootstrap test fails with "you resampled single items", check that the group list is actually used to build the draws and that the number of draws is the number of groups.

def mean_se(xs):
    """Mean and standard error of the mean: (mean, s / sqrt(n)) with s the n-1 standard deviation."""
    n = len(xs)
    m = sum(xs) / n
    if n < 2:
        return m, 0.0
    var = sum((x - m) ** 2 for x in xs) / (n - 1)
    return m, math.sqrt(var / n)

def wilson(k, n, z=1.96):
    """Wilson score interval (lo, hi) for k successes in n independent trials."""
    p = k / n
    denom = 1 + z * z / n
    centre = (p + z * z / (2 * n)) / denom
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / denom
    return max(0.0, centre - half), min(1.0, centre + half)

def clustered_se(xs, groups):
    """Standard error of the mean when xs[i] belongs to cluster groups[i].

    Naive variance of the mean plus the covariance between every ordered pair of DIFFERENT items
    in the same cluster (Miller 2024, equation 4):
        SE^2 = SE_naive^2 + (1 / n^2) * sum over clusters, over i != j in the cluster, of (x_i - m)(x_j - m)
    """
    n = len(xs)
    m, se = mean_se(xs)
    members = {}
    for x, g in zip(xs, groups):
        members.setdefault(g, []).append(x - m)
    cross = 0.0
    for devs in members.values():
        total = sum(devs)
        cross += total * total - sum(d * d for d in devs)     # sum over i != j of d_i d_j
    return math.sqrt(max(0.0, se * se + cross / (n * n)))

def bootstrap_ci(values, groups=None, B=2000, alpha=0.05, seed=0):
    """Percentile bootstrap interval (lo, hi) for the mean of `values`.

    Without `groups`, resample the values themselves (with replacement, n draws).
    With `groups` (a list parallel to values), resample WHOLE groups: draw as many groups as there
    are distinct groups, with replacement, and pool all their values. The statistic of each of the
    B pseudo-evals is the mean of the pooled values. Use random.Random(seed).
    Sort the B means; lo = means[int(alpha / 2 * B)], hi = means[int((1 - alpha / 2) * B) - 1].
    """
    rng = random.Random(seed)
    if groups is None:
        n = len(values)
        means = sorted(sum(values[rng.randrange(n)] for _ in range(n)) / n for _ in range(B))
    else:
        members = {}
        for v, g in zip(values, groups):
            members.setdefault(g, []).append(v)
        packs = [(sum(vs), len(vs)) for vs in members.values()]    # (sum, count) per cluster
        c = len(packs)
        means = []
        for _ in range(B):
            tot = cnt = 0
            for _ in range(c):
                s, m = packs[rng.randrange(c)]
                tot += s
                cnt += m
            means.append(tot / cnt)
        means.sort()
    return means[int(alpha / 2 * B)], means[int((1 - alpha / 2) * B) - 1]

Milestone 4: paired comparison and the diff

Most evals exist to compare. The tempting way is to compute each system's score and interval and see whether they overlap. The better way uses the fact that both systems answered the same cases. Cases differ enormously in difficulty; a good system and a slightly better one succeed on the same easy ones and fail on the same impossible ones. That shared difficulty moves both scores together and says nothing about which is better. Working with the paired difference di = bi − ai removes it. Cases on which both systems score the same contribute zero and effectively drop out; the information is in the disagreements.

paired_stats(a, b) puts the two standard errors side by side: the paired one (the standard error of the differences) and the unpaired one, √(SEa2 + SEb2). They are connected by the correlation ρ of the two score lists: SEpaired2 = SEa2 + SEb2 − 2ρ SEa SEb. On this data, version 1 against version 2 has ρ = 0.88, the unpaired standard error is 4.95 points (z = 1.05, nothing to see) and the paired one is 1.69 points (z = 3.09). Same data, same model calls, three times the signal.

The second tool is the diff. A headline score cannot show that a change fixed three cases and broke two. diff_runs matches the two runs by id (never by position: a reordered file must not change the answer), lists the cases whose score rose or fell by at least min_change, and reports the mean change per tag. The tag view is what exposes a trade.

def paired_stats(a, b):
    """Compare two systems scored on the SAME cases (a[i] and b[i] are case i's scores).

    Return a dict:
      diff         mean of (b - a)
      se_paired    standard error of the per-case differences (the n-1 standard deviation / sqrt(n))
      se_unpaired  sqrt(se_a^2 + se_b^2), treating the two score lists as independent
      z_paired, z_unpaired   diff divided by each standard error (0.0 if the standard error is 0)
      corr         Pearson correlation of a and b (0.0 if either has no spread)
      a_only, b_only   number of cases where a scored higher / b scored higher
    """
    n = len(a)
    d = [y - x for x, y in zip(a, b)]
    diff, se_p = mean_se(d)
    _, se_a = mean_se(a)
    _, se_b = mean_se(b)
    se_u = math.sqrt(se_a ** 2 + se_b ** 2)
    ma, mb = sum(a) / n, sum(b) / n
    va = sum((x - ma) ** 2 for x in a)
    vb = sum((y - mb) ** 2 for y in b)
    cov = sum((x - ma) * (y - mb) for x, y in zip(a, b))
    return {
        "diff": diff, "se_paired": se_p, "se_unpaired": se_u,
        "z_paired": diff / se_p if se_p else 0.0,
        "z_unpaired": diff / se_u if se_u else 0.0,
        "corr": cov / math.sqrt(va * vb) if va > 0 and vb > 0 else 0.0,
        "a_only": sum(x > y for x, y in zip(a, b)),
        "b_only": sum(y > x for x, y in zip(a, b)),
    }

def diff_runs(res_a, res_b, min_change=0.5):
    """The diff between two runs of the same cases (matched by id, not by position).

    Return {"fixed": [...ids], "regressed": [...ids], "by_tag": {tag: change in mean score}}.
    A case is fixed when b.score - a.score >= min_change, regressed when it is <= -min_change.
    Ids come back sorted. Raise ValueError if the two runs do not cover the same ids.
    """
    A = {r.id: r for r in res_a}
    B = {r.id: r for r in res_b}
    if set(A) != set(B):
        raise ValueError("the two runs cover different cases; compare like with like")
    fixed = sorted(i for i in A if B[i].score - A[i].score >= min_change - 1e-12)
    regressed = sorted(i for i in A if B[i].score - A[i].score <= -min_change + 1e-12)
    tags = {}
    for i in A:
        for t in A[i].tags:
            tags.setdefault(t, []).append(B[i].score - A[i].score)
    return {"fixed": fixed, "regressed": regressed,
            "by_tag": {t: sum(v) / len(v) for t, v in tags.items()}}

Milestone 5: power, a verdict and the whole comparison

Three last pieces turn the toolkit into a decision.

How many questions you needed. Chapter 4 derives, for a paired comparison with 5% false positives and 80% power, n = (zα/2 + zβ)2 (ω2 + σA2/KA + σB2/KB) / δ2, where δ is the true gap you want to detect, ω2 is the variance of the per-question gap between the systems' true pass rates and σ2 is the answer-level noise. With chapter 4's example values (ω2 = 1/9, σ2 = 1/6 for each system, one answer per question) detecting a 5-point gain needs about 1,400 questions and a 1-point gain nearly 35,000. mde is the same formula solved for δ: the minimum detectable effect of an eval of a given size. Our 160 cases, answered once, can only detect gaps of about 15 points; answered three times, about 10. That is what "this eval could not have told us" means in numbers, and it should change what you claim.

What an interval means. verdict(lo, hi) reads a confidence interval for B minus A: wholly above zero is "B better", wholly below is "A better", and anything touching zero is "cannot tell". The third answer is not "equal". A positive difference whose interval includes zero is not evidence that B is better, and a zero difference is not evidence that they are the same; it is evidence that the eval could not separate them.

The pipeline. compare(system_a, system_b, cases, k) runs both systems, scores each case, computes the group-bootstrap interval of each score and of the per-case differences (the paired, clustered interval, the one this lab recommends), the z-values, the diff and the per-tag change, and returns everything in one dict. There is nothing new to derive; the work is to wire the pieces in the right order and to bootstrap the right unit.

def n_required(delta, omega2, s2a=0.0, s2b=0.0, ka=1, kb=1, alpha=0.05, beta=0.20):
    """Independent questions needed to detect a true gap `delta` (paired design, Miller 2024):
        n = (z_{alpha/2} + z_beta)^2 * (omega2 + s2a/ka + s2b/kb) / delta^2
    Return a float (the caller rounds up)."""
    return (z_for(alpha / 2) + z_for(beta)) ** 2 * (omega2 + s2a / ka + s2b / kb) / delta ** 2

def mde(n, omega2, s2a=0.0, s2b=0.0, ka=1, kb=1, alpha=0.05, beta=0.20):
    """Minimum detectable effect of an eval with n independent questions (the inverse of n_required)."""
    return (z_for(alpha / 2) + z_for(beta)) * math.sqrt((omega2 + s2a / ka + s2b / kb) / n)

def verdict(lo, hi):
    """Read a confidence interval for (B minus A): "B better" if it lies wholly above 0,
    "A better" if wholly below 0, otherwise "cannot tell". An interval touching 0 is "cannot tell"."""
    if lo > 0:
        return "B better"
    if hi < 0:
        return "A better"
    return "cannot tell"

def compare(system_a, system_b, cases, k=3, B=2000, seed=0):
    """The whole pipeline for two systems on the same cases.

    Run both (k attempts per case), then return a dict with:
      score_a, score_b    overall scores
      ci_a, ci_b          cluster-bootstrap 95% intervals for each score (groups = case groups)
      diff                mean of (b - a) per case
      diff_ci             cluster-bootstrap 95% interval of the per-case differences
      z_paired, z_unpaired   from paired_stats
      verdict             verdict(*diff_ci)
      fixed, regressed    from diff_runs
      by_tag              diff_runs' per-tag change
      errors_a, errors_b  error attempts in each run
    """
    res_a = run_suite(system_a, cases, k)
    res_b = run_suite(system_b, cases, k)
    a = [r.score for r in res_a]
    b = [r.score for r in res_b]
    groups = [r.group for r in res_a]
    ps = paired_stats(a, b)
    d = [y - x for x, y in zip(a, b)]
    diff_ci = bootstrap_ci(d, groups, B=B, seed=seed)
    dr = diff_runs(res_a, res_b)
    return {
        "score_a": sum(a) / len(a), "score_b": sum(b) / len(b),
        "ci_a": bootstrap_ci(a, groups, B=B, seed=seed), "ci_b": bootstrap_ci(b, groups, B=B, seed=seed),
        "diff": ps["diff"], "diff_ci": diff_ci,
        "z_paired": ps["z_paired"], "z_unpaired": ps["z_unpaired"],
        "verdict": verdict(*diff_ci),
        "fixed": dr["fixed"], "regressed": dr["regressed"], "by_tag": dr["by_tag"],
        "errors_a": summarise(res_a)["errors"], "errors_b": summarise(res_b)["errors"],
    }

Common misconception

"The harness is deterministic now, so I do not need error bars." Determinism removes one kind of noise, and only if you turned the temperature down, which chapter 4 advised against. The bigger noise is which cases you wrote. Our stand-in is perfectly repeatable, and the interval on version 2's score is still 25 points wide.

What to look for: the model will not know your refund policy, so most refund and billing cases will fail until you put the policy in a system prompt, which is itself a change you can now measure. Use a modest k (3 to 5) and a sampling temperature you would use in production. Going further

  • Per-tag intervals. Add a bootstrap interval for every tag in the report, resampling groups within the tag. With eight groups the intervals will be very wide; that is the honest picture.
  • McNemar's test. For k = 1 and 0/1 scores, count the cases only one system passes (a_only, b_only) and compute (bonly − aonly)/√(bonly + aonly). Check it equals the paired z when the scores are binary, as chapter 4 states.
  • A regression gate. Fail the run if any case in a critical list that passed before now fails, or if the interval of the difference excludes a drop of more than two points. This is the seed of Lab 7.
  • Multiple slices. Test every tag for a change with the paired interval and count how many look "significant" at the 5% level when you compare version 2 with itself under different seeds. Apply a Bonferroni correction and see what survives.
  • Harder checks. Add a metamorphic check (rephrasing the question must not change the stated refund window) and an LLM-judge check, calibrated as in Lab 2.
  • The same toolkit, another domain. The retrieval lab A Retrieval Evaluation Harness applies intervals and a paired comparison to ranking metrics, where the per-query score is not 0 or 1, and the bootstrap built from scratch in A Statistics Toolkit for Experiments is the same machinery.

Systems connection

A harness is a test suite for a component you cannot read, so everything about testing carries over: a fast smoke tier on every commit, a larger tier nightly, and a regression gate that is the evaluation analogue of a canary that must not get worse (compare Automated Canary Analysis, which makes the same paired-versus-unpaired argument for live traffic). The runner's rule that a timeout is recorded and not fatal is the retry and timeout discipline of Failure in Networks. If you report a latency or a cost next to the score, use the bootstrap on it, not the formulas here: percentiles cannot be averaged (Metrics, Percentiles & Histograms).

What you learned

  • A harness is a loader that validates, a narrow runner interface, assertions that return reasons and refuse unknown types, and a summary by tag. Test the checks with a known-good and a known-bad reply.
  • A timeout is an error: recorded, reported in its own column, never a pass and never dropped from the denominator. Ask each case k times and score the per-case mean.
  • A score is an estimate. Use the standard error for averages, Wilson for small or extreme counts, and a bootstrap when the metric is awkward, but always resample the independent unit: for paraphrases of one intent, the group.
  • Compare systems on the same cases. The paired difference is narrower than the unpaired one, here by a factor of three, and the diff names the cases that changed.
  • Know your minimum detectable effect. An interval that touches zero means "cannot tell", not "the same", and a flat total can hide a large regression in one tag.

Check your understanding

A run of 160 cases with 3 attempts each ends with 40 of the 480 attempts raising a timeout. How should the harness treat them?

  1. Drop them from the denominator, since they say nothing about the model
  2. Count them as passes, because the system did not produce a wrong answer
  3. Count them as not passing, report the 40 errors in their own column, and investigate before trusting the score
  4. Retry until none are left and report the final run only
An error is a fact about the run, not a verdict, so it must be visible. It must also not flatter the score: dropping errors lets a flaky week look better, and counting them as passes is worse. Retrying silently hides the problem; bounded retries are fine, but the number of errors that remain should still be reported. With 8% of attempts failing, the score is not a number you can interpret yet.

The 160 cases are 40 intents, each asked four ways, and the assistant tends to get all four paraphrases of an intent right or wrong together. Which interval for the overall score is closest to honest?

  1. The one from resampling single cases: 160 cases give the narrowest, most precise estimate
  2. The one from resampling whole groups of four, which is much wider because there are closer to 40 independent observations than 160
  3. Either, because both resample the same data
  4. The Wilson interval on 160 trials, which exists for exactly this situation
Paraphrases of one intent are not independent draws, so the group is the sampling unit. In the lab's data the group bootstrap is 25.6 points wide against 13.3 for the per-case one. Wilson fixes the small-sample and edge problems of the normal interval; it still assumes independent trials, so it has the same blind spot as option A.

Two prompts are run on the same 400 questions. Their 95% intervals (65% and 70%) overlap. A colleague says the prompts are therefore not different. What is the best response?

  1. Agree: overlapping intervals mean no significant difference
  2. Disagree: overlap means the second prompt must be better
  3. Run the second prompt on a fresh set of 400 questions so the intervals no longer overlap
  4. Compute the paired difference on the shared questions: if the systems agree on what is easy and hard, its interval can exclude zero even though the individual intervals overlap
Overlap of two separate intervals ignores the pairing and is a conservative test. The per-question differences remove the shared difficulty, which is why the paired interval is narrower. Option C throws away the very structure that makes the comparison cheap, and A is the common error of reading "cannot tell" as "no difference".

Using chapter 4's values (ω2 = 1/9, answer noise 1/6 per system) and one answer per question, a 160-case eval can detect a true gap of roughly:

  1. 15 points
  2. 5 points
  3. 2 points
  4. 1 point
mde(160) = (1.96 + 0.84) × √((1/9 + 1/6 + 1/6)/160) = 0.148. Detecting 5 points needs about 1,400 questions, 2 points about 8,700. Answering each case three times lowers the answer noise and brings the MDE to about 10 points, still far from 2.

Comparing version 2 with version 3, the overall difference is +0.6 points with a 95% interval of −9.8 to +11.5, while the status tag drops by 36 points and billing gains 40. What do you conclude?

  1. Version 3 is better: the total went up and billing improved a lot
  2. Version 3 is the same as version 2, so ship whichever is cheaper
  3. The overall eval cannot separate them, but the large per-tag changes and the list of regressed cases are findings to act on before shipping version 3
  4. The interval contains zero, so the tag changes must be noise too
"Cannot tell" about the total does not make a 36-point fall on eight groups noise: that change is large relative to what a tag of that size can show by chance, and the regressed cases can be read one by one. Equally, a 40-point billing gain does not cancel a broken JSON format that downstream code parses. Slices are leads to confirm with fresh cases, but this one is too big to ignore.

A harness answers each case 5 times and then computes the standard error treating all 5 × 160 = 800 answers as independent observations. What goes wrong?

  1. Nothing: more answers always give a more precise estimate
  2. It claims the precision of 800 questions while having only 160, so the error bar is too narrow; the 5 answers should first be averaged into one score per case
  3. It double counts the timeouts
  4. It makes the temperature matter, which it otherwise would not
Repeated answers to one case reduce answer-level noise only. The question-level noise, which is which cases you drew, is unchanged, so the independent unit is still the case (or the group). Averaging the repeats into a per-case score before computing any standard error is what the lab's Result.score does.

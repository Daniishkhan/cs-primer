Lab 7: Traces & a Regression Gate

A support bot answers a customer, the request returns in a second and a half, and nothing on any dashboard says whether the answer was right. In this lab you instrument that bot so every request leaves a tree of spans, redact what must not be stored, roll a trace up into tokens, cost and time, and decide which traces to keep. Then you close the loop: turn a labelled production failure into a scrubbed, replayable regression case, grade cases by properties instead of exact text, run the suite several times per version, and build the release gate that blocks a candidate that is better on average but has broken something that mattered.

Why this lab matters

Teams that ship LLM features usually discover the same two gaps in the same order. First, a customer reports a bad answer and nobody can say which prompt version, which tool result or which model call produced it, because the only record is a status code. Second, someone fixes the prompt, the fix works, and three weeks later another change quietly brings the old failure back, because the fix lived in a chat message and not in a test. Chapter 17 explains what a trace of an LLM request should contain, and chapter 18 explains the loop that turns production failures into permanent checks and a gate. Here you build both ends and the join between them: the tracer and its wrappers, the redaction that makes traces safe to keep, the conversion from a labelled trace to a case, the property graders, and the gate. The results are numbers you can check, and one of them is humbling: the gate you build blocks a change that its own average says is a clear improvement, and when you test it against itself it also raises false alarms. Knowing how often a gate is wrong is part of building one. The statistics are those of chapter 4, the harness is the one from Lab 1 grown up, and the agent-level grading comes from chapter 8 and Lab 4.

Deterministic, offline and fast

The bot is a scripted model (llm.py, the site's shared stand-in) whose policy function makes a few seeded mistakes, the tools read recorded results from fixtures, and the "clock" is a counter that moves forward by a fixed number of milliseconds per model call and per tool call. Nothing touches the network and python3 check.py solution finishes in well under a second. The bot's luck is drawn from a random generator keyed by (case, trial) and not by version, so two versions run on the same case and trial see the same dice. That choice makes the comparison between versions tight, and it is also a simplification that a real model does not give you: the "Look under the hood" section removes it and shows what changes. A failure that involves random trials prints its seed, and python3 check.py solution 1 7 replays milestone 1 with seed 7. Python 3.9 or newer, standard library only. The dollar figures use assumed prices of $3 and $15 per million input and output tokens, which are illustrations and not any provider's price list. The shop, its orders, the customers and the failure rates are all invented for the exercise, and the email addresses and card numbers in the data are made up.

What you'll build

Six milestones, each building on the last:

  1. Spans: a tracer whose spans nest, take their start and end from a clock, and record an exception without hiding it; plus the self time of a span, which is where the time went.
  2. Instrument the request: redaction of emails, card numbers and phone numbers; wrappers that turn every model call and tool call into a span with OpenTelemetry-style GenAI attribute names; a root span for the whole request.
  3. Read a trace, decide what to keep: tokens, cost, model and tool time per trace, and a tail-sampling rule that keeps every trace worth reading.
  4. A failing trace becomes a case: scrub it again, record the tool reads (not the writes) as fixtures, attach assertions by failure mode, and drop near-duplicates by fingerprint.
  5. Grade properties, run k times: assertions that check behaviour (did it escalate, does the answer match the tool) rather than exact words, and a suite runner that counts passes out of k.
  6. The gate: a paired bootstrap over cases, hard regressions in critical slices, and a decision that is ship or BLOCK with the reasons.

Milestone 1: spans with parents, durations and errors

A trace is the record of one request as it moved through your system; it is made of spans, each a timed operation with a name, attributes, a parent and a status. If that is hazy, any introduction to distributed tracing builds the idea from scratch and chapter 17 applies it to model calls. For an LLM system the interesting spans are the whole request, each model call, and each tool call, arranged as a tree: the request is the root, and every model and tool call it makes is a child.

The spans in this lab are plain dictionaries, so they serialise to JSON without ceremony and you can read them with your eyes:

FieldMeaning
trace_id, idWhich request, and which span within it. Ids count up in the order spans start: s1, s2, ...
parentThe id of the span that was open when this one started, or None for the root. This is the only thing that makes a list of spans a tree.
name, kindWhat it did (chat demo-model) and its role: CLIENT for a call to another service, INTERNAL for work inside the process.
start, endMilliseconds, read from a clock when the span opens and when it closes.
statusOK or ERROR.
attrsA dictionary of facts: token counts, the tool name, an error type.

The parent link needs no bookkeeping from the caller, because spans nest the way function calls do. The tracer keeps a stack of the spans that are open: starting a span pushes it, finishing pops it, and a new span's parent is whatever is on top. Python's with statement is the natural shape, because it guarantees that the closing code runs however the block ends. That matters for the second rule, which is the one people get wrong: a span records a failure and then lets it continue. If the block raises, the span's status becomes ERROR and its attrs get error.type (the exception's class name), the span is closed at the current time, and the exception is re-raised unchanged. A tracer that swallowed the exception would change what the program does, which is the worst thing instrumentation can do; a tracer that forgot to close the span would leave the stack wrong for everything after it.

You will write the context manager with contextlib.contextmanager, which turns a generator into a with block: code before the yield runs on entry, the yielded value is what as s receives, and code after runs on exit. Self time: where the time went

A span's duration includes its children, so the root of every trace is the longest span and says nothing useful about what to fix. The self time of a span is its duration minus the time covered by its children: the part it spent on its own work. In a request that calls the model, then a tool, then the model again, the self times of the three calls are their durations and the root's self time is the glue between them. The self times of all the spans in a trace add up to the root's duration, which is the property check.py uses on the production traces.

The catch is parallelism. Agents often make two tool calls at once, and then the children overlap; subtracting their durations would count the overlap twice and can push the parent's self time below zero. The correct subtraction uses the union of the children's intervals, as in the figure.

The standard way to compute the union is to sort the child intervals by start and sweep through them, extending the current interval while the next one starts before it ends, and closing it when there is a gap. Clip each child to its parent's interval first, so that a child that starts before its parent (it happens with clock skew between services) cannot make the parent's self time negative.

class Tracer:
    """Records spans against a clock. Spans nest: a span opened inside another has it as parent."""

    def __init__(self, clock, trace_id="t0"):
        self.clock, self.trace_id = clock, trace_id
        self.spans, self._stack, self._n = [], [], 0

    @contextmanager
    def span(self, name, kind="INTERNAL", **attrs):
        # Open: ids count up in order of start, the parent is whatever span is open right now.
        self._n += 1
        s = {"trace_id": self.trace_id, "id": f"s{self._n}",
             "parent": self._stack[-1]["id"] if self._stack else None,
             "name": name, "kind": kind, "start": self.clock.now, "end": None,
             "status": "OK", "attrs": dict(attrs)}
        self.spans.append(s)
        self._stack.append(s)
        try:
            yield s
        except Exception as e:
            s["status"] = "ERROR"
            s["attrs"]["error.type"] = type(e).__name__
            raise                                   # recording a failure must not hide it
        finally:
            s["end"] = self.clock.now               # also on error: the span still took that long
            self._stack.pop()

def self_times(spans):
    """Milliseconds each span spent on its own work: duration minus the time covered by its children.
    Children that overlap (parallel tool calls) are counted once, as a union of intervals."""
    kids = {}
    for s in spans:
        kids.setdefault(s["parent"], []).append(s)
    out = {}
    for s in spans:
        iv = sorted((max(c["start"], s["start"]), min(c["end"], s["end"])) for c in kids.get(s["id"], []))
        covered, cur_lo, cur_hi = 0.0, None, None
        for lo, hi in iv:
            if cur_hi is None or lo > cur_hi:
                if cur_hi is not None:
                    covered += cur_hi - cur_lo
                cur_lo, cur_hi = lo, hi
            else:
                cur_hi = max(cur_hi, hi)
        if cur_hi is not None:
            covered += cur_hi - cur_lo
        out[s["id"]] = (s["end"] - s["start"]) - covered
    return out

Milestone 2: instrument the model, the tools and the request

With a tracer in hand, instrumenting an agent means wrapping three things: each call to the model, each call to a tool, and the request as a whole. The bot's code does not change. The wrappers have the same interface as what they wrap, so the agent loop calls model.complete(...) and tools[name](**args) exactly as before and the spans appear as a side effect. This is the decorator pattern, and it is how most real instrumentation libraries work.

What goes on each span is a design decision, and chapter 17 argues for splitting it into two groups. Metadata is cheap, small and rarely sensitive: names, versions, token counts, finish reasons, durations, error types. Content is what you need to understand why an answer was wrong (the user's message, the tool arguments, the tool result) and is where personal data lives, so it is opt-in. Redaction: make the trace safe to keep

The content attributes are the evidence, and they are also personal data: the customer typed an email address and a card number into a chat box, and a trace store is a data store like any other (Data Protection & Privacy, and chapter 22 for the AI-specific questions). Redaction replaces identifiers with a mask before anything is stored. You apply three patterns, given in the starter, in the order email, card, phone: jo@example.com becomes <EMAIL>, 4929 1234 5678 9010 becomes <CARD>, 07123 456 789 becomes <PHONE>. Two properties matter. It must leave ordinary text alone: A-1042 and "3 October" contain digits but are not identifiers. And it must be idempotent, meaning that redacting an already redacted string changes nothing. Idempotence is what lets milestone 4 redact a second time, safely, as a belt-and-braces step: traces captured before redaction was switched on are common, and a mask like <CARD> must not itself match a pattern.

Common misconception

"Redaction makes the trace store safe." It lowers the risk and does not remove it. A pattern-based filter has a recall ceiling: it catches the email in jo@example.com and misses "jo at example dot com", a street address, a name, or a card number typed with words between the groups. The trace store still needs access control, a retention limit and a deletion path. Redaction is the first layer, not the policy.

The three wrappers

TracedModel wraps a model object. Its complete(messages, **kw) opens a chat <model name> span, calls the real model, then records the token usage and finish reason from the reply. It stores no message text (a chat span is metadata only in this lab). If the real call raises, the span ends as ERROR and the exception propagates, which your tracer already guarantees. trace_tools returns a dictionary of the same tool names whose functions open an execute_tool <name> span around the original; with capture=True it also stores the arguments, and on success the redacted result, as JSON strings (sorted keys, so the same call always serialises the same way). trace_request ties them together: it opens the root invoke_agent support-bot span, wraps the rig's model and tools, runs bot.run_agent inside it, and finally stores the redacted user message and answer on the root. def redact(text):
    """Mask emails, card numbers and phone numbers. Applying it twice gives the same result."""
    for pattern, mask in REDACT:
        text = pattern.sub(mask, text)
    return text

class TracedModel:
    """Same interface as the model it wraps; every complete() call becomes a 'chat <model>' CLIENT span."""

    def __init__(self, tracer, inner, provider="demo"):
        self.tracer, self.inner, self.provider, self.name = tracer, inner, provider, inner.name

    def complete(self, messages, **kw):
        attrs = {"gen_ai.operation.name": "chat", "gen_ai.provider.name": self.provider,
                 "gen_ai.request.model": self.name}
        with self.tracer.span(f"chat {self.name}", "CLIENT", **attrs) as s:
            r = self.inner.complete(messages, **kw)
            s["attrs"].update({"gen_ai.usage.input_tokens": r.usage["input_tokens"],
                               "gen_ai.usage.output_tokens": r.usage["output_tokens"],
                               "gen_ai.response.finish_reasons": [r.stop_reason]})
            return r

def trace_tools(tracer, tools, capture=True):
    """A dict of tools with the same names whose calls are 'execute_tool <name>' spans. With capture,
    the arguments and the (redacted) result are stored as JSON strings; they are content, so opt-in."""
    def wrap(name, fn):
        def traced(**kwargs):
            attrs = {"gen_ai.operation.name": "execute_tool", "gen_ai.tool.name": name}
            if capture:
                attrs["gen_ai.tool.call.arguments"] = json.dumps(kwargs, sort_keys=True)
            with tracer.span(f"execute_tool {name}", "INTERNAL", **attrs) as s:
                result = fn(**kwargs)
                if capture:
                    s["attrs"]["gen_ai.tool.call.result"] = redact(json.dumps(result, sort_keys=True))
                return result
        return traced
    return {name: wrap(name, fn) for name, fn in tools.items()}

def trace_request(tracer, rig, user_text, release="v1", conversation_id="conv-0", capture=True):
    """Run one request through the agent loop with every model and tool call traced, under a root
    'invoke_agent support-bot' span. Returns the final answer."""
    attrs = {"gen_ai.operation.name": "invoke_agent", "gen_ai.agent.name": "support-bot",
             "gen_ai.conversation.id": conversation_id, "app.release": release}
    with tracer.span("invoke_agent support-bot", "INTERNAL", **attrs) as root:
        model = TracedModel(tracer, rig.model)
        tools = trace_tools(tracer, rig.tools, capture)
        answer, _ = run_agent(user_text, model, tools)
        if capture:
            root["attrs"]["gen_ai.input.messages"] = json.dumps([{"role": "user", "content": redact(user_text)}])
            root["attrs"]["gen_ai.output.messages"] = json.dumps([{"role": "assistant", "content": redact(answer)}])
        return answer

Milestone 3: read a trace, decide what to keep

A trace is only useful if someone, or something, can read it. Two jobs follow from having spans. The first is a roll-up: reduce a tree of spans to the handful of numbers that dashboards and reviews need. The second is a keep or drop decision, because storing every trace with its content is rarely affordable or wise.

The roll-up has one trap, and it is the same one chapter 17 warns about: sum tokens over the model-call spans only. A request with two model calls that read 36 and 48 tokens used 84 input tokens. If your code adds up every span that has a usage attribute, and the root span carries a copy of the total (as many frameworks write), you report 168 and double the bill. Cost follows from tokens and a price list: with the assumed $3 and $15 per million input and output tokens, 84 in and 20 out cost (84 × 3 + 20 × 15) / 1,000,000 = $0.000552. The other numbers answer "where did the time go?": the summed duration of the model calls, of the tool calls, and the model's share of the request. Tail sampling

The question of which traces to keep has two answers with very different costs. Head sampling decides when the trace starts, before anything is known: keep 5 per cent at random. It is cheap and blind, since the rare traces you care about are kept at the same 5 per cent as the boring ones. Tail sampling decides after the trace is complete, so the rule can use what happened. It needs a collector that buffers a trace's spans until the request ends, and a way for late signals (a thumbs-down arriving ten minutes later) to reach it, but it can keep every trace worth reading. The rule you write has four steps, and the first that fires wins:

  1. any span had status ERROR: keep, reason error;
  2. the user gave a thumbs-down: keep, reason feedback;
  3. the duration exceeds a threshold: keep, reason slow;
  4. otherwise keep a small fixed share, reason baseline, and drop the rest.

The baseline matters because the traces you do not flag are where the unknown unknowns are: if you keep only what your current rules flag, you can never discover a failure that no rule knows about, and the baseline sample is also what lets you estimate how often the rules are wrong. Choose the baseline traces by hashing the trace id and comparing to the rate, not by calling a random number generator. The same trace id then always gets the same answer, on every collector and after every restart, which matters when the spans of one trace arrive at different machines.

def rollup(spans):
    """One trace in numbers: release, duration_ms (root span), input_tokens and output_tokens (summed over
    the chat spans only, never the root as well), cost (dollars), model_ms and tool_ms (summed span
    durations), model_share (model_ms / duration_ms), n_model_calls, tools (names, in order of start)
    and errors (names of spans with status ERROR)."""
    root = next(s for s in spans if s["parent"] is None)
    chats = [s for s in spans if s["attrs"].get("gen_ai.operation.name") == "chat"]
    tools = [s for s in spans if s["attrs"].get("gen_ai.operation.name") == "execute_tool"]
    dur = root["end"] - root["start"]
    tin = sum(s["attrs"]["gen_ai.usage.input_tokens"] for s in chats)
    tout = sum(s["attrs"]["gen_ai.usage.output_tokens"] for s in chats)
    model_ms = sum(s["end"] - s["start"] for s in chats)
    return {"release": root["attrs"].get("app.release"), "duration_ms": dur,
            "input_tokens": tin, "output_tokens": tout,
            "cost": (tin * PRICE_IN + tout * PRICE_OUT) / 1e6,
            "model_ms": model_ms, "tool_ms": sum(s["end"] - s["start"] for s in tools),

def keep_trace(roll, trace_id, feedback=None, slow_ms=2000, base_rate=0.02):
    """Tail sampling: decide after the trace is complete. Returns (keep, reason). First rule that fires:
    "error" (any error span), "feedback" (feedback == "down"), "slow" (duration_ms > slow_ms), then
    "baseline": keep a fixed share base_rate of the rest, chosen by hashing trace_id so the decision is
    repeatable. Everything else is (False, "drop")."""
    if roll["errors"]:
        return True, "error"
    if feedback == "down":
        return True, "feedback"
    if roll["duration_ms"] > slow_ms:
        return True, "slow"
    h = int(hashlib.sha256(trace_id.encode()).hexdigest()[:8], 16) / 2 ** 32
    if h < base_rate:
        return True, "baseline"
    return False, "drop"

Milestone 4: a failing trace becomes a regression case

A person reads the kept traces, using the method of chapter 1, and finds some that are wrong. Each gets a label: a failure mode and a note. The next step is what separates a team that learns from one that repeats itself. A regression case is a test built from a real failure, so that the failure can never come back unnoticed. This milestone is the conversion, and it has four requirements, each from a different way it goes wrong in practice.

  1. Scrub again. The input comes from the root span's gen_ai.input.messages. Redact it a second time: older traces were captured before redaction was switched on, and one of the ten in prod_traces.jsonl was. Idempotence, from milestone 2, is what makes this safe.
  2. Record the reads, not the writes. A case must replay without the real order service, so every successful read tool call becomes a fixture: a recorded result stored under a key made from the tool name and its arguments (bot.fixture_key). The candidate then sees the same order data the production bot saw. Writes are the opposite: the whole point is to see whether the candidate performs an issue_refund, so recording the previous bot's refund would hand the answer to the test.
  3. Assert a property, not the bad answer. The assertions come from a table keyed by failure mode, given in the starter. For refund_over_limit it is "issue_refund must not be called for an order whose total is above 50", not "the reply must not say I have refunded 80.00 pounds". A test that matches the old wrong text passes the moment the bot words the same mistake differently. Copy the table entry with copy.deepcopy, or editing one case will edit all the others that share it.
  4. Drop the duplicates. Production produces the same failure again and again, and a suite stuffed with near-identical cases is slow, noisy and overweights one bug. A fingerprint is a short hash of the failure mode plus the normalised input: lower-cased, with every order id and run of digits replaced by #, placeholders deleted and spaces collapsed. "Refund my order A-1042, my email is <EMAIL>" and "refund my order A-2231, my email is <EMAIL>" then share a fingerprint, while a different mode or different words do not.

The case also keeps provenance: source is trace: plus the trace id, so the next engineer can open the original, and note keeps the labeller's sentence. def fingerprint(case):
    """Near-duplicate detector: the failure mode plus the input with ids, digits and placeholders removed."""
    key = re.sub(r"[a-z]-\d+|\d+", "#", case["input"].lower())
    key = re.sub(r"\s+", " ", re.sub(r"<[a-z]+>", "", key)).strip()
    return hashlib.sha256((case["mode"] + key).encode()).hexdigest()[:8]

def dedupe(existing, new):
    """Split new cases into (kept, skipped). A case is skipped when its fingerprint is already used by an
    existing case or by an earlier new one. kept cases get an "fp" field; skipped is a list of
    (new case id, id of the case it duplicates)."""
    seen = {fingerprint(c): c["id"] for c in existing}
    kept, skipped = [], []
    for c in new:
        fp = fingerprint(c)
        if fp in seen:
            skipped.append((c["id"], seen[fp]))
        else:
            seen[fp] = c["id"]
            kept.append(dict(c, fp=fp))
    return kept, skipped

The suite now has cases. To use it you need two things: a grader that decides whether one run passed, and a runner that does it enough times to be believed. Several design rules show up in the details. A case with no assertions also raises, for the same reason. grade_case evaluates every assertion and lists every reason, because the person debugging a red case wants to see all that is wrong with it. And the evidence for an assertion must exist: a timed-out lookup leaves nothing to compare the answer with, so answer_consistent_with_tool fails with "no successful lookup" (the bot did not check, and an answer produced without checking is not consistent with anything), while tool_not_called_or_escalated passes when no refund was made, but fails if a refund was made and no total is known.

Because a model is not deterministic, and a single pass or fail is a draw from the case's pass rate, not the rate. def check_assertion(a, result):
    """Evaluate one assertion against {"answer", "calls"}. Returns (ok, reason); reason explains a failure."""
    kind, calls, answer = a["type"], result["calls"], result["answer"]
    if kind == "tool_not_called_or_escalated":
        totals = [c["result"]["total"] for c in calls if c["name"] == "lookup_order" and c["result"]]
        called = any(c["name"] == a["tool"] for c in calls)
        if called and (not totals or totals[0] > a["limit"]):
            return False, f"{a['tool']} was called for an order not shown to be within {a['limit']}"
        return True, ""
    if kind == "tool_called":
        if any(c["name"] == a["tool"] and c["error"] is None for c in calls):
            return True, ""
        return False, f"{a['tool']} was never called successfully"
    if kind == "answer_consistent_with_tool":

def grade_case(case, result):
    """Grade one run of a case: {"ok": bool, "failed": [reasons]}. Every assertion is evaluated.
    A case without assertions raises ValueError (it would pass everything)."""
    if not case["assert"]:
        raise ValueError(f"case {case['id']} has no assertions")
    failed = []
    for a in case["assert"]:
        ok, reason = check_assertion(a, result)
        if not ok:
            failed.append(reason)
    return {"ok": not failed, "failed": failed}

def run_suite(cases, version, k=3):
    """Run every case k times against a version (trials 0 to k-1). Returns {case id: passes out of k}."""
    return {c["id"]: sum(grade_case(c, run_case(version, c, t))["ok"] for t in range(k)) for c in cases}

Milestone 6: the regression gate

A release gate is an automatic check, run before a change ships, that blocks the change if the suite shows it got worse by a rule fixed in advance. You have two sets of pass counts, one per version, on the same cases. The gate turns them into a decision, and the decision has to be right in both directions: a gate that blocks good changes gets bypassed, and one that ships bad changes is decoration.

Two rules, both from chapter 18, with different jobs.

  • The overall rule guards against broad decline. For each case, the difference d = (candidate passes − baseline passes) / k is a number between −1 and +1. The mean of d is the change in pass rate. To know whether that mean is real you need an interval, and a paired bootstrap gives one: resample the cases with replacement, take the mean of the resampled differences, repeat a couple of thousand times, sort the means, and read off the 2.5th and 97.5th percentiles. It is paired because each case contributes its own difference, so the difficulty of the case cancels. The rule blocks when the lower bound of the 95 per cent interval is below −0.02: the data are compatible with the candidate being two points worse or more. The method is that of chapter 4; resample the cases, not the individual trials, because the trials of one case share its difficulty.
  • The hard-regression rule guards against a localised break. A hard regression is a case that passed k out of k with the baseline and at most one out of k with the candidate. An average cannot see it: a failure in 5 refund cases barely moves the mean of 120. The rule applies only to critical slices (refunds and privacy here), the places where one bad answer is not offset by many good ones elsewhere. Any hard regression there blocks.

The two are complementary, and the lab data show why. Candidate v2 improves the general slice by 19 points, because it stopped ignoring tool results, and it improves the overall rate by 11 points with a lower bound well above zero. The overall rule passes it, and an average-only gate would ship it. But case R01, a 60-pound refund that v1 always escalated, is now refunded twice in three runs. That is a general lesson about slices: significance tests on small slices have little power, and a rule about individual critical cases is the cheaper protection.

Analogy: the building inspector and the average score

Imagine a building where every flat is rated out of ten and the block's average rises after a renovation, but the fire doors on one staircase were removed. The average hides it, and no inspector accepts "the average is better" as an answer: some defects are disqualifying whatever else improved. The hard-regression rule is the inspector's checklist item for the fire doors, and the paired bootstrap is the overall rating.

Where it breaks down: a building inspector checks a door once and it is either there or not. A model's behaviour on a case is a probability, and a "removed door" that shows up in three runs may be bad luck, which is what the next section measures.

Common misconception

"If the new version beats the old one with a confidence interval above zero, ship it." The interval is about the average over your cases. It says nothing about which cases got worse, and the cases that matter most (money moves, personal data leaves) are a small share of any realistic suite. Block on named critical behaviours separately, and report slices next to the headline number.

  • Build the slice list with dict.fromkeys(c["slice"] for c in cases) to keep first-appearance order, then add "ALL".
  • The first check's label is built from the tolerance: f"overall lower bound >= {-tolerance:+.2f}" gives overall lower bound >= -0.02.
  • Only critical slices feed hard; ALL and every slice still appear in the report.

def paired_ci(diffs, B=2000, alpha=0.05, seed=0):
    """Percentile bootstrap interval for the mean of per-case differences. Resample the cases with
    random.Random(seed).randrange, take B means, sort, and return (xs[int(alpha/2*B)], xs[int((1-alpha/2)*B)-1])."""
    rng = random.Random(seed)
    n = len(diffs)
    xs = sorted(sum(diffs[rng.randrange(n)] for _ in range(n)) / n for _ in range(B))
    return xs[int(alpha / 2 * B)], xs[int((1 - alpha / 2) * B) - 1]

def hard_regressions(cases, base, cand, k, slices=None, max_after=1):
    """Ids of cases that passed k out of k with the baseline and at most max_after with the candidate
    (only cases in `slices`, if given), sorted."""
    return sorted(c["id"] for c in cases
                  if (slices is None or c["slice"] in slices) and base[c["id"]] == k and cand[c["id"]] <= max_after)

def gate(cases, base, cand, k=3, critical=CRITICAL, tolerance=0.02, B=2000, seed=0):
    """Compare two versions' pass counts and decide.

    report   {slice name or "ALL": {"n", "base", "cand", "diff", "ci"}}, rates in 0..1, diff = cand - base
    hard     hard regressions inside the critical slices
    checks   [(label, ok)]: overall CI lower bound >= -tolerance; no hard regression
    decision "ship" if every check passes, otherwise "BLOCK"."""
    report = {}
    for name in list(dict.fromkeys(c["slice"] for c in cases)) + ["ALL"]:
        ids = [c["id"] for c in cases if name == "ALL" or c["slice"] == name]
        diffs = [(cand[i] - base[i]) / k for i in ids]
        report[name] = {"n": len(ids), "base": sum(base[i] for i in ids) / k / len(ids),
                        "cand": sum(cand[i] for i in ids) / k / len(ids),
                        "diff": sum(diffs) / len(ids), "ci": paired_ci(diffs, B, 0.05, seed)}
    hard = hard_regressions(cases, base, cand, k, slices=critical)
    checks = [(f"overall lower bound >= {-tolerance:+.2f}", report["ALL"]["ci"][0] >= -tolerance),
              ("no hard regression in a critical slice", not hard)]
    return {"report": report, "hard": hard, "checks": checks,
            "decision": "ship" if all(ok for _, ok in checks) else "BLOCK"}

The second experiment is the one to take away. So far both versions have been run with aligned luck: the same dice on trial 0, the same dice on trial 1. A real model does not do that. Run it again and you get a different draw, which means that comparing a baseline run with a candidate run compares two samples of noise. The test for that is an A/A test: run the gate with the same code on both sides, using fresh luck (new trial numbers) for the candidate, and count how often it objects. Then re-run the cases that it flagged many more times to see which flags are real.

Read the table carefully, because it changes what you should believe about your own gate.

  • The overall rule blocked a version of the bot against itself in every one of 40 trials. With 120 cases and 3 runs each, the 95 per cent interval around the overall difference is about ±0.06 wide even when nothing changed (the median lower bound in these 40 draws is −0.075), so a bound at −0.02 can almost never be met: the margin is finer than this suite can resolve. In the aligned-luck runs earlier it passed v3 only because the shared luck removed most of the noise. With a real model you would set the tolerance from an A/A run (to let identical code through 95 per cent of the time you would need about 0.11 here), or grow the suite and k until a tight margin is credible. This is exactly the sample-size reasoning of chapter 4.
  • The hard-regression rule flagged identical code in 25 of 40 draws and the real break in 37 of 40. A case that passed 3 of 3 once and 1 of 3 the next time is a coin that landed badly twice, and with twenty critical cases and a rule this sensitive, someone will be flagged almost every time. The rule has recall (it caught v2 in 37 of 40) but a precision problem.
  • The fix is evidence, not a looser rule. The re-run lines are what a confirmation step looks like: each flagged case is run 40 more times with each version. P14 and P09, flagged against identical code, come back at 34 against 32 and 29 against 36 out of 40 (noise, in both directions). R01, flagged against v2, comes back at 33 against 15: a real change in the rate. A gate in practice does this automatically: screen cheaply with k = 3, then spend runs only on the cases that tripped the screen.

The general rule is that a gate is a measuring instrument, and an instrument needs its false-positive and false-negative rates measured. A/A runs measure the first, a planted regression (like v2) the second. Teams that skip this end up with a gate that cries wolf until everyone learns to rerun it until it passes, and from that moment it protects nothing.

Going further

  • Add a ratchet. Today's gate notices when something that worked stops working. It does not notice when a known failure stays broken: the six production-derived cases fail against v1, and v3 still fails some of them. Add a rule that blocks if a case the baseline passed 3 of 3 times is hard-regressed (already there), and a second rule that reports, for cases built from production traces, how many the candidate fixed. Decide whether "not fixed yet" should ever block, and who is allowed to waive it.
  • Confirm before you block. Implement the confirmation step from the A/A experiment: for each flagged case, run 40 more trials of both versions and block only if the candidate's pass rate is lower by a margin you choose from a binomial test. Measure the new rule's false-alarm rate on 40 A/A draws and its detection rate on v2.
  • Set the tolerance from data. Run 40 A/A draws, take the 5th percentile of the overall lower bound, and use its negative as the margin (the reference data give about 0.11). Compare it with the 0.02 of chapter 18 and say what suite size would justify the smaller figure.
  • Sample late feedback. A thumbs-down arrives ten minutes after the trace ended. Write a buffer that holds finished traces for fifteen minutes, applies keep_trace when the window closes, and counts how many traces were dropped before their feedback arrived.
  • Gate the cost and the latency too. Use rollup to compute the median and 95th percentile of cost and duration for the candidate and the baseline over the suite, and add checks (for example, no more than 20 per cent more cost per request). Chapter 19 covers why a quality gain that doubles the bill needs a decision, not an automatic ship.
  • Handle multi-turn traces. Extend trace_to_case to a conversation of several user messages. Which assertions still make sense, and what should a fixture look like when the same tool is called with the same arguments twice and returns different results?
  • Read the real specification. Compare the attribute names in your wrappers with the current OpenTelemetry GenAI conventions, change any that have moved, and write down where in the code the names live so the next rename costs one edit.

What you learned

  • A span is a timed, named operation with a parent. A tracer with a stack gets the tree for free, records an exception and re-raises it, and closes every span however the block ends. Self time, computed over the union of children, says where the time went.
  • Instrument by wrapping the model, the tools and the request, with the same interfaces as the originals, so behaviour and timing do not change. Store metadata always and content only when it is safe, redacted before it is written, with a redaction that is idempotent and is known to have a recall ceiling.
  • Sum tokens over model-call spans only. Keep traces by tail rules (errors, feedback, slow) plus a hashed baseline, so the interesting ones are never dropped and the unknown unknowns are still sampled.
  • A failing trace becomes a case with a scrubbed input, recorded reads (never writes), property assertions chosen by failure mode, provenance, and a fingerprint to drop near-duplicates.
  • Grade behaviour, not wording; fail on unknown or missing checks; include a usefulness counterweight for every safety check; run each case k times because one run is a draw.
  • A gate needs two kinds of rule, an average with an interval and a named list of critical cases, and it must be validated like any instrument: an A/A run measures its false alarms, a planted regression its recall, and reruns turn a flag into evidence.

When you convert a failing trace into a regression case, the recorded lookup_order result goes into the case's fixtures, but the issue_refund call does not. Why?

  1. The case must replay the same read data the old bot saw but let the candidate perform its own writes: recording the old refund would give away or fake the behaviour under test
  2. Write calls are never captured in a trace, so there is nothing to record
  3. Refunds are too sensitive to store, and reads are not
  4. Fixtures can hold only one tool call per case
Reads supply the world; writes are the behaviour being tested. If issue_refund were pre-recorded as a fixture, a candidate that never refunds would look the same as one that always does. Option 2 is false (the tool span is in the trace; the converter chooses not to use it), and option 3 confuses privacy with test design.

  2. Raise k from 3 to 4 for the screen and nothing else

In the simulated day of 20,000 traces, tail sampling and random head sampling both store about 5.6 per cent. Tail sampling keeps all of the traces that had an error, a thumbs-down or were slow; head sampling keeps about 5 per cent of them. Why?

  1. Tail sampling stores traces for longer, so it sees more of them
  2. Head sampling discards traces before their spans arrive, so errors are missed
  3. Head sampling decides before the outcome is known, so it keeps interesting traces at the same rate as boring ones; tail sampling decides afterwards and can keep by outcome
  4. Tail sampling uses a larger baseline share
Both policies spend the same storage. The difference is information at decision time: a head sampler cannot know that a trace will contain an error, so at a 5 per cent rate it keeps 5 per cent of them. A tail sampler sees the finished trace. Option 4 is not the cause (its baseline is 2 per cent, lower than the head rate).

  2. Block, and name R01: a critical case collapsed, a small slice cannot prove its safety by a significance test, and the averages cannot compensate for it

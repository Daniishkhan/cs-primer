Design the Eval Program for an Assistant

A health insurer is about to launch an assistant that answers members' coverage questions and checks claim status. Legal wants proof that it is safe, and product wants to release every week. Design the program that decides what is measured, who labels, how often each check runs, which numbers block a release and who signs off.

How a design studio works

This page is a mock working session of 60 to 90 minutes, not a chapter. At each stage there is a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer is one strong design with its reasoning, not the only right one. The stages follow the usual system design framework, adapted to evaluation: clarify, rank the failures, read the data, choose criteria, plan the labelling, size the sets, calibrate the judges, set cadence and gates, assign sign-off, cost it, and summarise aloud. Every number on this page is either computed by a script shown on the page or labelled as an assumption to reason with. None of it is a measurement of a real product.

📐 The brief

The director of member services says: "We launch the member assistant in eight weeks. It reads our plan documents and tells members what is covered, it can look up the status of a claim, and it can book a call-back. Legal and compliance want to see evidence that it is safe. Product wants to ship prompt and model changes every week. Tell me what we measure, who does the labelling, how often we run it, and which numbers stop a release."

  • The insurer has about 1.2 million members on three plan families. Plan documents are versioned by plan year, so the same question has different right answers in different years. Assume about 40,000 conversations a day once launched.
  • The assistant is retrieval-augmented: it answers from about 600 plan documents and cites them. It has a read-only claim-status tool and a low-risk call-back booking tool. It must not give medical advice, change coverage, or reveal anyone else's data.
  • There are six weeks of pilot traces (about 30,000 conversations) with thumbs up or down on about 3 percent of them. Two member-services specialists can give six hours a week each, and one compliance officer owns the policy. The engineering team is six people.
  • Builds on error analysis, LLM judges and building a domain benchmark, and uses harnesses, statistics for evals and human labels. It is the design-level partner of Lab 1 and Lab 3.
  • You have 60 to 90 minutes. The scripts need only the Python standard library.

2Rank the failures by harm

List the ways this assistant can fail and give each a severity from 1 (worst) to 4. For each, say whether it should block a release on its own, and what kind of check could see it.

Compare with a worked answer

Severity is by harm to a person or to the business, never by how often the failure happens or how easy it is to measure (the same principle AI incident response uses to rank real incidents). A rare, severe failure and a common, mild one need different tools.

  • Two kinds of gate. Severity 1 failures get a zero-tolerance gate: one failure on the suite blocks the release, and the suite must be big enough that a clean run means something (the next stages size it). Severity 2 and 3 failures get a non-inferiority gate: the new version may not be worse than the old by more than an agreed margin, tested with a paired comparison.
  • Severity 4 is where the temptation to build one score lives. Averaging helpfulness, tone and correctness into a "quality index" lets a gain in the first hide a loss in the last. Report each criterion on its own (chapter 3 makes the same argument against 1 to 5 scales).
  • Privacy is enforced twice. The member-id check in the eval is a detector. The control is that the claim tool is called with the session's member id and cannot be given another one. If the eval is the only protection for a severity 1 failure, the design is wrong; the eval verifies a control, it does not replace it (authorisation).

3Read the data before you design the metrics

You have 30,000 pilot traces and nothing labelled. What do you read first, how many traces, and how do you know when to stop? Estimate how many random traces you would need to see a failure mode that affects 2 percent of failures.

Compare with a worked answer

The criteria in a program like this should come from what actually goes wrong, not from a list of generic qualities (error analysis). So the first deliverable is a taxonomy built from reading. Two numbers decide how much reading to plan: how many random traces you need before a mode of a given size appears, and how many distinct modes you will have found after a given number of reads. The script computes both. The mode sizes in part 2 are assumptions: a 12 percent failure rate spread over eight modes from 32 percent of failures down to 2 percent.

"""How many traces must you read before a failure mode shows up? Every rate is an assumption."""
import math, random

# Part 1: chance of seeing a mode at least once in n traces read at random
print("traces to read for a 95% chance of seeing a mode at least once")
for f in (0.05, 0.02, 0.01, 0.005):
    n = math.ceil(math.log(0.05) / math.log(1 - f))
    print(f"  mode on {f:5.1%} of traces: read {n:4d}")

# Part 2: 12% of traces fail; eight failure modes of unequal size
random.seed(7)
shares = [0.32, 0.22, 0.15, 0.11, 0.08, 0.06, 0.04, 0.02]
fail_rate, reps = 0.12, 2000
print("\nmodes seen when reading n random traces (mean of 2,000 simulated sessions)")
print(f"{'n':>5} {'failing traces':>15} {'modes seen (of 8)':>18} {'saw the rarest':>15}")
for n in (50, 100, 200, 400, 800):
    fails = seen_total = rare = 0
    for _ in range(reps):
        seen = set()
        for _ in range(n):
            if random.random() < fail_rate:
                fails += 1
                seen.add(random.choices(range(8), shares)[0])
        seen_total += len(seen)
        rare += 7 in seen
    print(f"{n:5d} {fails/reps:15.1f} {seen_total/reps:18.2f} {rare/reps:15.0%}")

  • A mode on 1 percent of traces needs about 300 random reads to show up with 95 percent probability. The first table is the same arithmetic as the rule of three in chapter 4, run backwards. A rare failure is not rare if it is severe, so random reading alone cannot be the whole plan.
  • Reading 100 random traces finds about five of the eight modes; 400 find about seven. The rarest mode, 2 percent of failures, is seen in only 23 percent of 100-trace sessions and 61 percent of 400-trace sessions. This is the diminishing return you watch for: when new traces stop producing new categories, stop reading at random and start searching for specific modes.

The reading plan that fits a 12 expert-hour week:

  1. Week 1: 100 random pilot traces, read by one person, open notes on the first thing that went wrong in each (about three minutes a trace if the viewer is good, five hours in all). Group the notes into categories and write each with a one-line definition.
  2. Week 2: 100 more random traces plus 60 with thumbs down plus 40 where the member asked for a person. Re-label with the draft taxonomy; add categories where nothing fits. The thumbs-down and escalation traces are not representative, and are used only to find modes, never to estimate a rate.
  3. Week 3: targeted searches for severity 1 and 2 modes. Write a query for each (traces that contain a second member id; traces where the reply mentions a dollar figure; traces mentioning a diagnosis) and read the hits. These are the modes random reading cannot find in a sensible time.
  4. Stop condition: the last 50 random traces added no new category, and every category has at least three examples that two people would label the same way.

Expect a taxonomy of six to ten categories. For a coverage assistant it usually contains modes such as: answered from the wrong plan year; quoted a figure that is not in the cited text; cited a real document that does not support the claim; answered a medical question instead of redirecting; tool result misread; refused a question that was in scope; asked the member to repeat information already given. Each category becomes a candidate criterion, and the counts rank them.

Common misconception

"We will define the metrics up front, then collect data." The criteria that matter for your system cannot be known until someone has read real conversations; Shankar et al. (2024) call this criteria drift in "Who Validates the Validators?". A rubric written from imagination measures what you thought of, and the failures you did not think of are the ones that reach members.

5Plan the labelling

Two specialists have 12 hours a week between them. Who labels what, how do you know the labels are reliable, and who settles disputes?

Compare with a worked answer

Expert time is the scarcest resource in the program, so the plan spends it where nothing else can: writing the guideline, labelling the calibration set, reviewing severity 1 flags, and adjudicating disagreements. It does not spend it on reading every trace or labelling cases that code can check (human labels).

  • What "reliable" means here. For each judged criterion, aim for kappa of about 0.7 or better on the double-labelled set, and read the disputes whatever the number is. Remember how noisy kappa is: chapter 5 shows that with 40 items and equally careful annotators the 95 percent range for kappa spans 0.17 to 0.92, and with 200 items it still spans 0.43 to 0.76 when 90 percent of items pass. The 200-trace agreement check is therefore a screen for badly written criteria, not a precise measurement.
  • Low agreement is information about the guideline. If the two specialists disagree on escalates_when_needed, the usual cause is that "distress" was never defined. Fix the definition, re-label the disputed items under the new version, and record the version on every label.
  • Labels are versioned data. Each label stores the guideline version, the labeller and the date. A judge calibrated on guideline v2 labels is not compared with v3 numbers without re-checking.
  • Labellers see the trace, the retrieved passages and the tool results, not only the final reply; otherwise they cannot tell a grounded claim from a lucky one. They do not see which model version produced it.
  • Why not hire outside annotators? They could take the volume, but this task depends on insurance knowledge and a compliance ruling on edge cases. Revisit when the weekly sample needs to grow beyond what two part-timers can read.

Sizes come from arithmetic, not taste. The script finds how many questions detect a change of a given size with 80 percent power, for a paired comparison (the same questions scored under old and new) and an unpaired one, and then checks the paired formula by simulation. "Discordant" is the share of questions whose outcome changes between versions; for a prompt tweak it is typically small. The 6, 10 and 16 percent values are assumptions to be replaced with measured ones from your first two releases.

"""How many questions does a release check need? Paired versus unpaired, with clustering."""
import math, random

Z = 1.96 + 0.84          # two-sided alpha 0.05, power 80%
def n_unpaired(p, delta):                 # per system, two independent evals
    return math.ceil(Z**2 * 2 * p * (1 - p) / delta**2)
def n_paired(discordant, delta):          # same items scored under both systems
    return math.ceil(Z**2 * (discordant - delta**2) / delta**2)

p = 0.80
print("questions needed to detect an improvement of delta (power 80%, alpha 0.05), baseline 80%")
print(f"{'delta':>6} {'unpaired (per system)':>22} {'paired, 6% differ':>18} {'paired, 10% differ':>19} {'paired, 16% differ':>19}")
for d in (0.02, 0.03, 0.05):
    print(f"{d:6.0%} {n_unpaired(p, d):22,d} {n_paired(.06, d):18,d} {n_paired(.10, d):19,d} {n_paired(.16, d):19,d}")

m, rho = 4, 0.3
deff = 1 + (m - 1) * rho
n = n_paired(0.10, 0.03)
print(f"\nclustered: {m} questions per plan document, within-document correlation {rho}")
print(f"  design effect {deff:.1f}: {n:,} independent questions become {math.ceil(n*deff):,} questions ({math.ceil(n*deff/m):,} documents)")

# Check the paired formula by simulation: true +3 points, 10% of items change outcome (6.5% fixed, 3.5% broken)
random.seed(3)
def trial(n):
    b = c = 0
    for _ in range(n):
        u = random.random()
        if u < 0.065: b += 1
        elif u < 0.10: c += 1
    diff = (b - c) / n
    se = math.sqrt((b + c) / n - diff**2) / math.sqrt(n)
    return diff / se > 1.96
for n in (400, 863, 1200):
    power = sum(trial(n) for _ in range(4000)) / 4000
    print(f"  simulated power at n={n:5,d}: {power:.0%}")

  • Pairing cuts the question count by about three times. Detecting a 3-point improvement from an 80 percent baseline needs 2,788 questions per system unpaired but 864 paired when 10 percent of outcomes change. The simulation agrees: 81 percent power at 863 questions, only 47 percent at 400.
  • Clustering takes some of it back. Plan documents generate several questions each, and questions about one document tend to be answered alike. With four questions a document and a within-document correlation of 0.3 the design effect is 1.9, so the same power needs about 1,640 questions across 411 documents. Sample documents, then questions within them, and compute error bars with the document as the unit (chapter 4).
  • What the run sizes can see. A nightly run of 1,200 items has an effective size of about 630 after clustering, which detects a change of about 3.5 points in a criterion where 10 percent of outcomes flip. The per-change fast suite of 150 items has an effective size of about 80 and can only see a change of about 10 points: it catches breakage, not small drift. Say this plainly, so nobody reads a green fast suite as "no regression".
  • Zero-tolerance suites are sized differently. With 0 failures in 400 cases the 95 percent upper bound on the failure rate is about 3/400, or 0.75 percent. That is what "clean run" supports, and it is why the hard checks have 400 cases each and why the gate refuses a suite smaller than 300.

7Calibrate the judges

The grounded judge says 78 percent of a 400-trace production sample pass. How much should you trust that? What do you need from the calibration set to turn it into an estimate?

Compare with a worked answer

A judge is a classifier with error rates, and its raw pass rate is a biased estimate of the real one. If the judge misses some failures (low true-negative rate) the raw number is too high; if it flags good answers it is too low. The correction uses the judge's true-positive rate (TPR: of human PASS items, the share it calls PASS) and true-negative rate (TNR: of human FAIL items, the share it calls FAIL), both measured on the adjudicated calibration set (chapter 3). The script uses assumed counts: of 120 human-PASS items the judge passed 108, and of 80 human-FAIL items it failed 66.

"""Turn a judge's raw pass rate into a corrected estimate, with an honest interval."""
import random

random.seed(21)
# Calibration set: 200 traces labelled by two experts and adjudicated (120 PASS, 80 FAIL)
tp, fn = 108, 12         # human PASS: judge said PASS / FAIL
tn, fp = 66, 14          # human FAIL: judge said FAIL / PASS
tpr, tnr = tp / (tp + fn), tn / (tn + fp)
# Production sample: judge scored 400 sampled traces
k, n = 312, 400
q = k / n

def corrected(q, tpr, tnr):
    return (q + tnr - 1) / (tpr + tnr - 1)

print(f"judge on calibration set: TPR {tpr:.3f} (pass found), TNR {tnr:.3f} (fail found)")
print(f"raw judge pass rate on production sample: {q:.1%}")
print(f"corrected pass rate: {corrected(q, tpr, tnr):.1%}")

def binom(n, p): return sum(random.random() < p for _ in range(n))
draws = []
for _ in range(4000):
    t = binom(120, tpr) / 120
    u = binom(80, tnr) / 80
    qq = binom(n, q) / n
    draws.append(min(1.0, max(0.0, corrected(qq, t, u))))
draws.sort()
print(f"95% interval (resampling the sample and the calibration set): {draws[100]:.1%} to {draws[3899]:.1%}")
print(f"interval if only the 400-trace sample were uncertain:       {corrected(q-1.96*(q*(1-q)/n)**.5, tpr, tnr):.1%} to {corrected(q+1.96*(q*(1-q)/n)**.5, tpr, tnr):.1%}")
print("\nsame sample, calibration set of 60 instead of 200 (same TPR and TNR):")
draws = []
for _ in range(4000):
    t = binom(36, tpr) / 36
    u = binom(24, tnr) / 24

  • The raw 78 percent becomes 83.4 percent. This judge fails 10 percent of the answers people passed, which removes about 8.3 points from the raw rate, and passes 17.5 percent of the answers people failed, which adds only about 2.9. The two errors do not cancel, so the raw number understates quality here. With a different judge it would overstate it.
  • The interval is wide: 75.0 to 92.4 percent. It has two parts, the sampling noise of 400 traces and the uncertainty in the judge's TPR and TNR from a 200-item calibration set. A calibration set of only 60 items stretches it to 71.5 to 99.2 percent, which is useless. Judge calibration is a statistics problem with its own sample size.
  • The decision rule. A judged criterion may gate a release only if both TPR and TNR are at least 0.85 with a lower confidence bound above 0.80. This judge's TNR of 0.825 fails that rule, so the next action is to read its 14 false passes, tighten the rubric and add examples (from the training part of the calibration set, never the test part), not to ship it.
  • For a gate you rarely need the correction. A paired comparison of two versions under the same judge cancels a constant bias. The correction matters when you report a level ("83 percent grounded") to people outside the team, or compare against a human-measured number.
  • Re-check every judge model change and every month. Rerun the judge on the 200 calibration items and compare its labels with the stored ones; alert if TPR or TNR drops by more than 5 points. A provider updating the judge model silently is the most common reason last month's numbers stop being comparable.

The gate as code. The margin of 1.5 points and the 300-case minimum are assumptions to be set by the sign-off group; the shape is what matters. Four candidates are tested on synthetic results generated with a fixed seed: A is better, B regresses plan-year accuracy, C is better but one test case leaked another member's record, and D is better with a privacy suite that is too small to mean anything.

"""A release gate written as code. Three candidate releases are compared with the current one."""
import math, random

MARGIN = 0.015            # non-inferiority margin: a drop of up to 1.5 points is tolerated, not more
random.seed(12)

def paired_ci(old, new, z=1.96):
    n = len(old)
    d = [b - a for a, b in zip(old, new)]
    mean = sum(d) / n
    var = sum((x - mean) ** 2 for x in d) / (n - 1)
    se = math.sqrt(var / n)
    return mean, mean - z * se, mean + z * se

def upper_zero_failures(n):          # rule of three: 95% upper bound when nothing failed
    return 3 / n

def gate(name, old, new, hard):
    """old/new: {criterion: [0/1 per item]}; hard: {check: (failures, n)} for must-never behaviours."""
    reasons = []
    for crit, results in new.items():
        mean, lo, hi = paired_ci(old[crit], results)
        if lo < -MARGIN:
            reasons.append(f"{crit}: change {mean:+.1%}, 95% CI {lo:+.1%} to {hi:+.1%} (lower end below -{MARGIN:.1%})")
    for check, (fails, n) in hard.items():
        if fails > 0:
            reasons.append(f"{check}: {fails} failure(s) in {n} cases (must be 0)")
        elif n < 300:
            reasons.append(f"{check}: only {n} cases; 0 failures proves under {upper_zero_failures(n):.1%}, need 300 (under 1%)")
    verdict = "BLOCK" if reasons else "SHIP"
    print(f"{name}: {verdict}")
    for r in reasons: print("   -", r)

def make(n, rate, base=None, flip_up=0.0, flip_down=0.0):
    if base is None: return [1 if random.random() < rate else 0 for _ in range(n)]
    out = []
    for x in base:
        if x == 0 and random.random() < flip_up: x = 1
        elif x == 1 and random.random() < flip_down: x = 0
        out.append(x)
    return out

How a senior engineer would summarise this

"I can't prove it's safe, but I can bound specific named failures with stated confidence, and keep that bound honest as we ship. First we read: a hundred random pilot traces, then more plus the thumbs-down ones, then targeted searches for the severe modes, until new traces stop producing new categories. That gives a taxonomy, and the taxonomy gives about eight binary criteria. Four are code against sources of truth: no other member's identifiers, figures that appear in the cited text, the right plan year, and the claim status that the tool actually returned. Two are calibrated judges, grounding and escalation. Medical advice is a rule plus a judge, with a specialist reading every positive. Two failures are severity one, other members' data and medical advice, and get zero-tolerance gates on 400-case suites, where a clean run supports 'under about three quarters of a percent'. The rest get a paired non-inferiority gate with a 1.5 point margin on a 600-item held-out set that nobody tunes against. The numbers are sized: a paired comparison needs about 860 independent questions for a three-point change, 1,640 after clustering by document, so the nightly 1,200 sees about 3.5 points and the 150-item fast suite only sees breakage. The two specialists spend their 12 hours a week on the guideline, a 200-item adjudicated calibration set, a 60-trace weekly read and every severity-one flag; they do not label what code can check. Judges must show both hit rates above 0.85 against that set before they can gate, and I'd rerun it weekly because provider updates move it. The cost is about $4,600 a month, two thirds of it people, which is under four dollars per thousand conversations. Sign-off is split: the eval lead owns the evidence, product owns the margins, compliance and engineering jointly own any severity-one override, and every override is logged. What I'd watch is the program decaying: dev over-fitting, stale sets, judge drift and the weekly read quietly stopping. If we add appeals, it becomes an agent eval and we move to the guardrails design."

Notice the shape: decisions and harms → read the data → criteria checked by code first → labelling plan → sizes from arithmetic → calibrated judges → cadence and gate as code → ownership and overrides → cost → named decay modes.

  • Started with error analysis on real traces before writing metrics, with a reading plan and a stop condition.
  • Wrote binary criteria with definitions, and used code checks wherever a source of truth exists before reaching for a judge.

  • Knew that kappa is itself noisy and that disagreements are information about the guideline.
  • Separated regression, dev, held-out test, hard-check and calibration sets by job, and kept the test set out of tuning.
  • Sized sets from power arithmetic, used a paired comparison, and allowed for clustering by source document.
  • Knew what the cheap suites cannot see and said so, and sized a zero-failure suite with the rule of three.
  • Calibrated each judge with TPR and TNR on adjudicated labels, reported an interval, and set a rule for when a judge may gate.

Key takeaways

  • "Prove it is safe" becomes "bound named failures, with stated confidence, on defined sets, and keep adding cases". Write that promise down first.
  • Rank failures by harm. Severity 1 gets zero-tolerance gates; the rest get paired non-inferiority margins. Never blend them into one score.
  • Read real traces before choosing criteria; stop at saturation, then search for the severe rare modes.
  • Check with code wherever a source of truth exists. Judges handle the rest, and only after both error rates are measured on adjudicated human labels.
  • Spend scarce expert hours on the guideline, the calibration set, severity 1 review and a steady weekly read.
  • Size from arithmetic: pairing cuts questions about three times, clustering gives some back, and cheap suites catch breakage, not drift.
  • Write the gate as code, treat uncertainty as a block, split ownership of evidence and decision, and log every override.
  • The program decays unless someone owns the reading, the refresh and the recalibration. Cost them like any other service.

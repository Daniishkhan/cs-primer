The Improvement Flywheel

A deployed AI system gets better only if its failures turn into permanent changes. This chapter walks the whole loop: capture production traces, choose which ones to read, label the failures, encode each as a test case, gate every release on the growing suite, ship in small steps and watch. It shows each step with code you can run, a step-through of one failure's journey and a simulation of what the loop is worth.

Why this matters

Teams that evaluate only before launch discover the same failures again and again. A prompt change fixes the complaint from last week and quietly reintroduces the one from last month. Reading logs after each incident feels productive and leaves nothing behind. The remedy is a mechanism, not more effort: every failure that is understood becomes a test that runs on every future change, so the set of things the system can no longer get wrong only grows. This chapter ties together the earlier ones. Error analysis (Error Analysis) supplies the labels, harnesses (Assertions & Eval Harnesses) run the cases, judges and statistics (LLM-as-Judge, Statistics for Evals) decide whether a score moved, and tracing (Tracing & Observability for LLM Systems) supplies the raw material. After this chapter you will be able to design the loop for a product, set its release gates, and say honestly what each part costs and where it breaks.

The loop in one picture

A flywheel, in the product sense, is a loop whose output feeds its own input so that each turn is easier than the last. For an AI system the output of one turn is a better system, and the input to the next turn is the new set of failures that better system still has. Six stages make a turn.

Regression suite
The collection of test cases that every candidate release must pass. A regression is a behaviour that used to be right and is now wrong.
Release gate
An automatic check, usually in continuous integration, that blocks a change if the suite shows it got worse by a rule fixed in advance.
Canary
Sending a small share of real traffic to the new version first, and watching indicators before widening the rollout.
Failure mode
A named, recurring way the system goes wrong, such as "ignores a tool result that contradicts its draft". Counting modes, not single failures, is what makes the work prioritisable.
Held-out set
Labelled cases that nobody has tuned against, used to check that improvements generalise instead of memorising the suite.

Stage 1: capture what you will need later

The previous chapter covered what to record. For the loop, what matters is the set of signals that say a trace deserves attention, because they will drive triage. Four kinds are common.

  • Explicit feedback: thumbs up or down, a free-text complaint, a "report this answer" button. Precious and biased: only a small and unusual share of users click, and they click more when angry.
  • Behavioural signals: the user rephrases the same question, abandons the conversation, asks for a person, copies the answer, or returns within the hour. Cheap to collect and ambiguous, so treat them as hints.
  • Automatic evaluators: programs and judge models that score every trace or a sample, such as "the answer contradicts the retrieved text", "an order id in the reply does not exist", "the reply is in a different language from the question". A deterministic check is preferable where one exists (Assertions & Eval Harnesses); a judge needs calibration against people (LLM-as-Judge).
  • System signals: errors, timeouts, guardrail blocks and overrides (Guardrail Classifiers & Content Policy), and cost outliers.

All four become attributes or linked scores on the trace, so triage can filter on them. And because the flagged traces are the ones the tail-sampling policy of the previous chapter keeps, this stage and that one are the same design decision seen from two sides.

Stage 2: triage, choosing what to read

People read slowly, and the traces worth reading are a small fraction of the total. If a reviewer can read forty traces a day from a day of 2,000, how they are chosen decides what the team learns. The experiment below simulates a day with an 8% failure rate spread over six failure modes of very unequal size (the biggest accounts for 45% of failures, the smallest 3%), a cheap online evaluator that flags 70% of failing traces and also 10% of good ones, and a topic cluster for each trace, assigned by something like embedding the user's question. Three selection rules each pick 40 traces. The averages are over 300 simulated days.

import random
from statistics import mean

rng = random.Random(18)
N, FAIL_RATE = 2000, 0.08
MODE_SHARE = [0.45, 0.25, 0.14, 0.08, 0.05, 0.03]            # six failure modes, very uneven
CLUSTER_OF_MODE = [0, 1, 2, 3, 4, 5]                          # each mode lives mostly in one topic cluster

def make_day():
    traces = []
    for i in range(N):
        mode = None
        if rng.random() < FAIL_RATE:
            mode = rng.choices(range(6), MODE_SHARE)[0]
        cluster = CLUSTER_OF_MODE[mode] if mode is not None and rng.random() < 0.8 else rng.randrange(8)
        flagged = rng.random() < (0.7 if mode is not None else 0.10)     # cheap online evaluator: TPR 0.7, FPR 0.10
        traces.append({"mode": mode, "cluster": cluster, "flagged": flagged})
    return traces

def pick_random(ts, k): return rng.sample(ts, k)
def pick_flagged(ts, k):
    pool = sorted(ts, key=lambda t: (not t["flagged"], rng.random()))
    return pool[:k]
def pick_stratified(ts, k):
    by = {}
    for t in sorted(ts, key=lambda t: (not t["flagged"], rng.random())):
        by.setdefault(t["cluster"], []).append(t)
    out, queues = [], list(by.values())
    while len(out) < k and any(queues):
        for q in queues:
            if q and len(out) < k: out.append(q.pop(0))
    return out

print(f"Review budget: 40 traces from {N} (about {int(N*FAIL_RATE)} fail, in 6 modes). 300 simulated days each.\n")
print(f"{'selection rule':<34}{'failures seen':>15}{'modes found (of 6)':>20}{'rarest mode found':>19}")
for name, pick in [("random", pick_random), ("flagged first", pick_flagged), ("flagged, one cluster at a time", pick_stratified)]:
    seen, found, rare = [], [], []
    for _ in range(300):
        s = pick(make_day(), 40)
        modes = {t["mode"] for t in s if t["mode"] is not None}
        seen.append(sum(t["mode"] is not None for t in s)); found.append(len(modes)); rare.append(5 in modes)
    print(f"{name:<34}{mean(seen):>15.1f}{mean(found):>20.2f}{mean(rare):>19.0%}")

Random reading of 40 traces sees 3 failing traces on average, which is 8% of 40, and finds about two of the six modes. Reading flagged traces first sees five times as many failures and four and a half modes. Spreading the flagged traces over topic clusters finds slightly more modes (4.70 against 4.54), at the price of fewer failing traces read, because it also reads from clusters where the evaluator flags mostly good traces. The modest gain from clustering is an honest result: in this simulation the cheap evaluator does most of the work, and coverage across clusters is a refinement. Notice also that no rule finds the rarest mode more than 44% of the time. A mode that occurs in 3% of failures needs either a very large reading budget or a signal aimed at it, which is what a new evaluator, written when you first see one example, provides.

Keep two further habits. Read a small random sample of unflagged traces every week. It is the only way to find failures that no signal catches and to measure how much the signals miss. And rotate reviewers or have two people label a subset, so you learn how consistent the labels are (Human Labels).

Stage 3: label the failures

Labelling is the error-analysis procedure of Error Analysis applied to production traces. A reviewer opens the trace, finds the first thing that went wrong, writes a free-text note, and assigns a failure mode from the current list or proposes a new one. Husain's writing on evaluation calls this reading the most valuable activity in AI development; his field guide, which I fetched and read, says to review real conversation logs, write open-ended notes, group them into a taxonomy and count, and reports a case in which targeted tests built from categorised failures took a date-handling success rate from 33% to 95% (the guide's own figure for one company, not a general result).

For the loop, a label should carry five things, so that the next stages can use it without asking the reviewer again.

FieldExampleUsed for
Failure moderefund_over_limitCounting, prioritisation, tagging the test case
First fault (span or step)Model call 2: issued refund without approvalChoosing where to fix; ignoring downstream symptoms
Expected behaviour"Escalate to a person for orders over 50 pounds"Writing the assertion
Severity4 of 5 (money)Priority; whether it blocks a release
Layer suspectedTool permissions (not the prompt)Choosing the fix

Counting then gives you a Pareto chart: a few modes account for most failures, and the one at the top is usually the best next investment unless a rarer mode has a much higher severity. Re-label periodically, because the taxonomy changes as modes are fixed and new ones surface, and keep the old names so earlier counts stay comparable.

Stage 4: encode the failure as a case

A raw production trace is a poor test. It contains the user's personal data, depends on a database state that has changed, and records the model's wrong answer rather than the right behaviour. A good regression case is a cleaned, self-contained, checkable restatement of the failure.

  1. Scrub. Replace personal data with typed placeholders (the PII filter of the guardrails chapter, with its recall ceiling in mind), and look at the output yourself. A case may be shared with contractors or sent to a model provider, so treat it as a copy of customer data.
  2. Freeze. Record the tool results the model saw as fixtures, so the case replays against a stub instead of a live database. Without fixtures, a case that failed because a record had a certain value will pass tomorrow when the record changes.
  3. Assert a property. Check the behaviour you want ("a refund over the limit is not issued without approval") rather than the exact words of a good answer. Properties survive rewording; string matches break on every prompt edit. Use a deterministic check where you can, and a calibrated judge with a binary rubric where you cannot.
  4. Tag and deduplicate. Tag with the failure mode and severity, give the case an opaque source id, and collapse near-duplicates so one noisy failure does not dominate the suite.

The script applies the first, second and fourth steps to four labelled traces from the refund bot (the assertions are named properties that a harness would implement). It scrubs, builds fixtures, and drops a repeat of an earlier trace by fingerprint. In a real system the fingerprint might use a text embedding instead of this crude normalisation.

Where cases go: the dataset

Store cases as a versioned dataset with provenance: where each came from, when, who labelled it, and which mode it covers. Treat the dataset like code. It lives in version control or a dataset registry, changes by reviewed commits, and every evaluation run records the dataset version it used, so a score is reproducible and you can see whether a change in score came from the system or from a change in the cases. The design of a larger benchmark has the same concerns in more depth (Building a Domain Benchmark).

Stage 5: the suite and the release gate

A suite is more than a pile of past failures. A workable one has four parts, each answering a different question.

Regression cases

Past failures, one or more per mode. Question: did we reintroduce something we already fixed? These must pass on every release.

Core tasks

A representative sample of what the product is for, with expected outcomes. Question: did general quality hold while we fixed one thing?

Critical slices

Cases where a mistake is expensive: money, safety, privacy, regulation. Question: did anything that must never break, break? Tracked separately so averages cannot hide them.

Add a small held-out set of labelled cases drawn from later traffic that no one has tuned against. The suite tells you that the loop's earlier fixes still hold; the held-out set tells you whether the system is actually getting better on failures it has not been fitted to. If the suite score climbs and the held-out score does not, the team is memorising its tests.

The gate

The gate turns the suite into a decision. Fix its rule before you see the results, or you will bend it to the result you want. A defensible rule has three parts.

  1. No hard regressions in critical slices. A case that passed reliably before must not fail now. Each case runs several times (here three), because a model's output varies from run to run, and "reliably" means passing all of them.
  2. The overall score must not be meaningfully worse. Compare baseline and candidate on the same cases and look at the paired differences, with an interval (Statistics for Evals). Pairing removes the large case-to-case variation that makes unpaired comparisons wide.
  3. Improvements are checked, not assumed. If the candidate was built to fix a mode, the cases for that mode must pass.

The script runs this on a simulated pair of versions. The suite has 120 cases in three slices (20 refund cases and 20 privacy cases, both critical, and 80 general cases), each run three times for each version. The candidate prompt is better on general tasks and, by construction, broke six of the refund cases.

import random
from statistics import mean

rng = random.Random(1802)
SLICES = {"refunds (critical)": 20, "privacy (critical)": 20, "general": 80}
K = 3                                              # each case is run three times per version

# Simulated true pass probabilities per case. The candidate is better on general cases, worse on refunds.
def make_probs():
    base, cand, names = [], [], []
    for sl, n in SLICES.items():
        for i in range(n):
            b = rng.choice([0.95, 0.9, 0.7, 0.4])
            c = b
            if sl == "general": c = min(0.99, b + rng.choice([0, 0.05, 0.1, 0.2]))
            if sl == "refunds (critical)" and i < 6: c = 0.15       # six cases the new prompt broke
            base.append(b); cand.append(c); names.append(sl)
    return base, cand, names

base_p, cand_p, slice_of = make_probs()
def run(ps): return [sum(rng.random() < p for _ in range(K)) for p in ps]   # passes out of K, per case
B, C = run(base_p), run(cand_p)

def paired_boot(diffs, reps=4000):
    n = len(diffs); out = []
    for _ in range(reps):
        out.append(mean(diffs[rng.randrange(n)] for _ in range(n)))
    out.sort()
    return out[int(0.025 * reps)], out[int(0.975 * reps)]

def gate(name, idx):
    d = [(C[i] - B[i]) / K for i in idx]
    lo, hi = paired_boot(d)
    return mean(d), lo, hi

print(f"{'slice':<22}{'cases':>6}{'baseline':>10}{'candidate':>11}{'diff':>8}   95% CI")
for sl in list(SLICES) + ["ALL"]:
    idx = [i for i, s in enumerate(slice_of) if sl == "ALL" or s == sl]
    m, lo, hi = gate(sl, idx)
    print(f"{sl:<22}{len(idx):>6}{mean(B[i] for i in idx)/K:>10.2f}{mean(C[i] for i in idx)/K:>11.2f}{m:>+8.3f}   [{lo:+.3f}, {hi:+.3f}]")

hard = [i for i, s in enumerate(slice_of) if "critical" in s and B[i] == K and C[i] <= 1]
print(f"\nhard regressions in critical slices (passed {K}/{K} before, passes at most 1/{K} now): {len(hard)}")
all_idx = list(range(len(B)))
m, lo, hi = gate("ALL", all_idx)
checks = [("overall lower bound >= -0.02", lo >= -0.02), ("no hard regression in a critical slice", not hard)]
for label, ok in checks: print(f"  {'PASS' if ok else 'FAIL'}  {label}")
print("DECISION:", "ship" if all(ok for _, ok in checks) else "BLOCK")

The candidate improves the general slice by 9 points (interval +0.025 to +0.163, so the gain is real) and the overall score by about 4 points, whose interval, from −0.019 to +0.100, includes zero. By the first part of the rule, the overall comparison passes: the lower bound is not below −0.02. A gate that only looked at the overall score would ship it. The refund slice tells the other story: a 13-point drop with an interval that just touches zero, and one case that passed three of three times before and passes at most once of three now. The hard-regression rule trips and the gate says BLOCK. This is why critical slices are tracked separately, and why a per-case rule is worth having next to the statistics: with 20 cases, a slice-level interval is wide, but a single case that flipped from reliable to broken is a concrete thing a person can look at.

Operate the gate with a few rules of thumb.

  • Pin the judge. If any case is scored by a judge model, pin its version and re-check its agreement with human labels when you change it; otherwise a score can move because the judge moved.
  • Handle flaky cases openly. A case that passes only half the time on an unchanged system is telling you something: either the system is unstable on that input or the check is poor. Quarantine it with an owner and a deadline, and do not silently delete it.
  • Budget the run. A full suite with repeated runs costs tokens and minutes. Run a fast subset (regression cases and critical slices) on every change, and the full suite plus the held-out set nightly or before release.
  • Allow explicit waivers. Sometimes a regression is acceptable (a policy changed, a case is obsolete). Make the waiver a recorded decision with a name on it, not a skipped test.

Stage 6: fix at the right layer, then release in steps

The label said which layer probably failed. Fixes differ in how much they cost and how likely they are to hold.

Where the fault wasTypical fixHolds because
A rule the system must always obeyEnforce it in code at the tool or action boundary (a limit check, an allow-list)The model cannot talk its way around code
Retrieval returned the wrong or no evidenceFix the index, chunking, filters or query rewriting (How RAG Fails)The model is working from better evidence
Instruction was ambiguous or missingRewrite the prompt and add a few worked examplesOnly as well as the model follows it; test with the suite
Wrong tool or tool misuseImprove tool names, descriptions and argument schemas (Designing Tools for Agents)The interface makes the right call easy
Content-policy missAdd labelled examples to the guardrail's training and test dataDetection improves, measured as in the previous chapter
Capability gapA different model, fine-tuning, or a narrower scope for the productExpensive; justified by the failure counts

Prefer the top of that table, for the reason Architectural Defences gave for security: a check in code is exact, while a sentence in a prompt is a request. The "prompt whack-a-mole" pattern, adding one more instruction after every complaint, produces a long prompt that is hard to reason about and which the gate will eventually catch regressing in some other mode.

Ship in steps

Passing the gate means the candidate is no worse on what you know to test. Real traffic always has surprises, so release in steps (Deployment Strategies): optionally run the candidate in shadow mode, receiving a copy of traffic whose answers are scored but never shown; then a canary at a small share of users; then widen. At each step watch leading indicators sliced by version: evaluator pass rate, guardrail override rate, thumbs-down rate, tool error rate, latency and cost. Decide in advance the rollback conditions and automate the rollback.

Canaries are limited by how fast they collect evidence. Suppose the evaluator pass rate in production is 90% and you want an 80% chance of detecting a drop to 85% at the usual 5% significance level. The standard sample-size formula for two proportions, n ≈ (1.96 + 0.84)2 × (p1(1 − p1) + p2(1 − p2)) / (p1 − p2)2, gives about 680 scored traces per arm (7.84 × 0.2175 / 0.0025). If the canary receives 5% of 2,000 daily conversations and you score a quarter of them, that is 25 scored traces a day, and the canary needs close to four weeks to detect it. The conclusions follow directly: raise the canary share or score more of its traces, accept that small drops are detected later through the aggregate, or rely on the gate and critical-slice checks for the failures you cannot afford to find in production.

Step through one failure's journey

The stepper follows a single failure from a thumbs-down to a permanent test. The numbers are illustrative, not measurements, but the sequence is the one the loop prescribes.

Step through

A refund over the limit becomes a permanent test

  1. Capture. A thumbs-down arrives on a trace where the bot issued a refund that needed approval. The trace carries versions, tool arguments and the evaluator's score.
  2. Triage and label. The tail-sampling rule keeps the trace because of the thumbs-down. A reviewer finds the first fault in the second model call, assigns the failure mode and writes the expected behaviour.
  3. Count. The label is compared with the week's other labelled failures. It is the largest group, so it goes to the top of the queue. The suspected layer is the tool's permissions, not the wording of the prompt.
  4. Encode. The trace is scrubbed, its tool result frozen, and an assertion written as a property. On the current build the case fails, which proves it reproduces the problem.
  5. Fix. The limit is enforced in the refund tool. The case now passes, and the author checks neighbouring cases for the same mode to confirm that the fix is not specific to one amount.
  6. Gate. The pipeline runs the suite on baseline and candidate, repeating each case, and compares paired results by slice. The rule from the previous section is met.
  7. Canary. A small share of real traffic uses the new version while indicators are watched. The rollback conditions were set before the release.
  8. Learn. The version is fully released. The case is permanent, and the time from first sighting to a protecting test is itself something to track.

What the loop is worth: a simulation

It is hard to feel the value of the suite from one example, so the widget below simulates it. A product has 40 failure modes with long-tailed frequencies; together they make 8% of requests fail. Each week the team reads some traces (failing ones are five times more likely to be read), fixes the most frequent modes it discovered, up to its capacity, and ships. Three teams are compared over 16 weeks. The team with no process never fixes anything. The team that fixes without regression tests sees fixed modes return with some probability each week, because a later change undoes the fix. The team with the full flywheel adds a test for each fix, which blocks any release that would bring the mode back.

Notice also what the reading budget does: with few reads, discovery is slow and the benefit of tests is small; with a generous budget, the suite carries most of the benefit.

How the flywheel itself fails

Overfitting to the suite
Prompts are tuned until every case passes, and the gains do not appear in production. Counter with a held-out set from later traffic, and look at the gap between suite and held-out scores.
Goodhart's law on evaluators
When an automatic evaluator is the target, the system learns what it rewards. Review a random sample of high-scoring traces by hand every cycle, and recalibrate judges against people.
Judge and criteria drift
A judge model updates, or reviewers change what they accept as they read more. Pin versions, keep a fixed set of calibration examples, and re-check agreement over time. Shankar et al. ("Who Validates the Validators?", 2024) name this "criteria drift": users need criteria to grade outputs, but grading outputs helps them define the criteria.
Stale cases
A product or policy change makes an old case wrong. Review the suite on a schedule; retire a case with a recorded reason, never silently.
Suite bloat
Thousands of near-duplicate cases make runs slow and expensive and hide the signal. Deduplicate by mode, keep a representative few per mode, and move the rest to a nightly tier.
Biased feedback
Thumbs-down come from a vocal minority. The random unflagged sample from stage 2 is the correction.
Privacy debt
Cases derived from user conversations carry personal data unless scrubbed, and need a retention rule and a deletion path (Privacy & Data Handling for AI).

Analogy: the checklist written in the margin of accidents

Many items on an aircraft or surgical checklist exist because someone once got hurt. Each line is a failure that was understood, turned into a step, and made impossible to forget. Nobody reads the checklist hoping to be surprised; it makes yesterday's lessons survive staff changes, tiredness and confidence. A regression suite is that checklist for your system: a failure that cost something once is checked on every release.

Where it breaks down: a paper checklist is cheap to run and rarely wrong, but a test suite costs compute and time, and its checks can themselves be wrong or stale. A checklist item never has to be re-judged by a model that drifts. So the suite needs the maintenance, ownership and retirement rules above, which a laminated card does not.

Common misconception

"Add every failure to the suite and we are safe." Two things go wrong. A suite of unlabelled, unscrubbed, duplicated cases is slow, leaks data and is full of noise. And a green suite proves only that the known failures are not back: it says nothing about failures you have not found, which is why the loop keeps reading new traces, keeps a held-out set and canaries every release. The second misconception is that the loop needs a platform. The mechanism is a reviewed dataset, a script that runs it and a rule in CI. A spreadsheet of labelled traces and a test file is a flywheel, if people use it every week.

Measuring the loop

The loop is a process, and processes can be measured. A short list tells you if it is turning.

  • Time from first sighting to protecting test. Days, not months, for severe modes.
  • Recurrence rate. Of the failures reviewed this month, what share belong to a mode that already had a case? Each such failure means the suite missed it, or the case was waived or stale. Aim for this to fall towards zero.
  • Coverage of the failure taxonomy. Modes with at least one case, and modes with severity 4 or 5 and no automatic check.
  • Suite versus held-out gap. A growing gap means overfitting.
  • Gate quality. How often it blocked, how often a block was a false alarm, and how often a bad release got through (found later in production).
  • Review throughput and agreement. Traces read per reviewer-hour, and agreement between reviewers on a doubly labelled subset.

The same measures will appear when an incident does occur (AI Incident Response): every incident ends with at least one new case, and the question "why did the suite not catch this?" is as important as "why did the system fail?". Key takeaways

  • The flywheel has six stages: capture, triage, label, encode, gate, release. It turns only if every understood failure becomes a permanent test, so the set of protected behaviours grows.
  • Triage decides what you learn. Reading flagged traces first sees several times more failures than random reading; add a weekly random sample of unflagged traces to find what signals miss.
  • Label the first fault, the failure mode, the expected behaviour, severity and suspected layer. Count modes to prioritise.
  • A good case is scrubbed, has frozen tool results, asserts a property and is tagged and deduplicated. Store cases as a versioned dataset with provenance.
  • The suite combines regression cases, core tasks and critical slices, plus a held-out set from later traffic to detect overfitting.
  • Fix the gate rule before you see results: paired differences with intervals, no hard regression in critical slices, and the targeted mode must pass. Repeat runs because outputs vary, and pin the judge.
  • Prefer fixes in code at the tool boundary to fixes in prompts. Release in steps, with rollback conditions set first, and remember a canary needs hundreds of scored traces per arm to see a 5-point drop.
  • Watch the loop: time to a protecting test, recurrence rate, suite versus held-out gap and gate quality.

Check your understanding

A team fixes failures by editing the prompt after each complaint, but never saves the failures as tests. Over three months, several old failures reappear. What is the most direct remedy?

  1. Use a longer prompt with all the instructions
  2. Review more traces each week
  3. Turn each understood failure into a regression case and run the suite as a gate on every change
  4. Switch to a larger model
Failures come back because nothing checks the old behaviour when the prompt changes. A suite and gate keep old fixes in force. A longer prompt makes interactions worse, more reading finds failures without keeping them fixed, and a bigger model may change which failures occur without checking any of them.

A candidate release raises the overall suite score by 4 points, but one critical-slice case that passed 3 of 3 runs before passes 1 of 3 now. The paired overall interval is -0.02 to +0.10. What should the gate do?

  1. Block, or require an explicit named waiver, because a critical case went from reliable to broken even though the average improved
  2. Ship, because the average improved
  3. Ship, because the interval includes zero
  4. Rerun until the case passes
Averages can hide a regression in a place that matters, which is why critical slices have their own rule. The interval including zero says the overall gain is uncertain, not that the broken case does not matter. Rerunning until it passes is p-hacking the gate.

The suite score rises steadily over two months while the score on a held-out set of newer labelled traces stays flat. What does this most likely mean?

  1. The held-out set is too small to be useful
  2. The suite is the better measure of quality
  3. Production traffic has become easier
  4. The team is tuning to the suite: fixes handle the known cases and do not generalise to new failures
The suite is built from failures the team has been tuning against, so it can rise from memorisation. The held-out set has not been tuned on and is the better estimate of progress on new failures. A flat held-out score with a rising suite score is the classic overfitting signature; it is not evidence of an easier workload.

Which regression case is better for the failure "bot refunds orders over the limit without approval"?

  1. Input with the real customer's email, live order lookup, and an exact-match check on the string "I cannot refund that"
  2. Scrubbed input, a frozen order-lookup result, and an assertion that no refund above the limit is issued without approval
  3. The full production trace, saved as an image
  4. A note in a document saying the bug was fixed
The second case is self-contained, safe to share and checks the behaviour that matters, so it survives rewording. The first leaks personal data, depends on a live system and breaks when wording changes. A screenshot cannot be replayed and a note cannot gate a release.

Production evaluator pass rate is 90%. A canary should detect a drop to 85% with about 80% power. Roughly how many scored traces does each arm need (two-proportion formula, 5% significance)?

  1. About 70
  2. About 200
  3. About 680
  4. About 5,000
n ≈ 7.84 × (0.09 + 0.1275) / 0.052 ≈ 680 per arm. Seventy or two hundred would leave the test badly underpowered for a 5-point difference; 5,000 would be needed only for much smaller differences (differences of a point or two).

In the triage simulation, reading flagged traces first sees about five times as many failures as random reading, but still finds the rarest failure mode only 44% of the time. What is the best way to improve coverage of that rare mode?

  1. Read more random traces and wait
  2. Remove the evaluator, since it misses rare modes
  3. Lower the severity of the rare mode
  4. Write a targeted evaluator or query once one example is seen, and add its cases to the suite, so the mode is flagged directly instead of relying on a general signal
A mode that makes up 3% of failures appears in few traces whatever you read at random. A signal aimed at it surfaces it directly. The general evaluator is still useful for the common modes, and severity is a property of the harm, not of how often it is seen.

Assertions & Eval Harnesses

Turn the failures you named in Chapter 1 into checks a computer can run on every change. This chapter covers three things. Assertions are small functions that give the same answer every time. Test cases are stored as data. The harness is the program that runs the cases, records the results and tells you what a change fixed and what it broke.

Why this matters

Without a harness, "did my change help?" is answered by re-reading outputs, which is slow, inconsistent and quietly biased towards the examples you just worked on. With one, the answer is a table in seconds, and old failures cannot return unnoticed. Deterministic checks are also the foundation for everything harder. An LLM judge (Chapter 3) is expensive and imperfect, so you use it only for what code cannot decide. After this chapter you will be able to write assertions for the common failure kinds and store test cases as data. You will also build and run a small harness and compare two versions of a system case by case.

Check with code first

You now have a ranked list of failures. For each one that matters you need a repeatable way to ask "did it happen?". There are three ways, and they trade off cost, speed and trust.

A deterministic assertion is a small function that returns pass or fail with a reason. It takes an input and the system's output (and, for agents, the trace or the final state). It uses no randomness and makes no model call. It has four advantages that matter more than they sound:

  • Exact and debuggable. When it fails you can read the function and see why. When a judge fails you can only argue with it.
  • Fast and free. A thousand cases take under a second, so you can run them on every edit, in a pre-commit hook or on every pull request.
  • Stable over time. A regex gives the same verdict today and next year. A hosted judge model can change under you when the provider updates it.
  • Reviewable. A teammate can read twenty assertions in ten minutes and say "that rule is wrong".

The limit is expressiveness. Code can check "the reply contains a valid JSON object with these keys" but not "the reply is kind". Always ask first whether a rule that sounds subjective has a crisp part you can check. "The reply must not reveal another customer's data" sounds like a judgement. Checking that no string from a different customer's record appears in the output is exact code.

A catalogue of assertions

Most useful checks fall into a handful of families. Learn the families and you can usually write the check for a new failure in a few lines.

Format and structure

Is the output valid JSON? Does it match a schema (required keys, types, allowed values)? Is it under a length limit? Does it use the language requested? Format failures are the most common cause of downstream breakage in pipelines, and the easiest to check. Your provider may support constrained decoding (covered in the decoding chapter). That makes many of these failures impossible. You still check, because the guarantee covers syntax and not meaning.

Content: must contain, must not contain

Substring and regular-expression checks are crude but useful for hard requirements. The reply must include the legal disclaimer. It must not include a phone number, an API key pattern or a competitor's name. It must not say "I have cancelled" before the order number is known. Prefer checking forbidden behaviour, a short list of things that must never appear. Avoid checking required wording, a phrase that has many correct paraphrases. Requiring a specific string makes the test brittle to harmless rewording.

Reference-based comparison

When there is a known right answer, compare to it, but compare the right thing. Exact string equality fails on "$1,204.50" versus "1204.5". Normalise first: lower-case, strip punctuation and units, parse numbers and allow a small tolerance. Section "Testing the checks" below shows a numeric comparator. For extraction tasks, compare field by field and report per-field accuracy rather than one all-or-nothing score.

Behaviour and tool use

For systems that call tools, check the trace: was check_availability called before book_slot? Was delete_record never called? Were the arguments valid? Chapter 8 develops this into full agent evaluation. The principle here is that some of the most important checks are on what the system did, not on what it said.

State

If the system changes something (a database row, a file, a calendar), check the resulting state rather than the system's description of it. A model can say "I have booked it" while the database holds nothing. The check "exactly one appointment exists for this patient on 2026-10-16 at 15:00" cannot be fooled by fluent text.

Properties and invariances

Sometimes you have no single right answer but you know something that must hold. Rephrasing a question must not change a factual answer. Adding irrelevant text must not change the classification. Translating the input must not change the extracted fields. These tests check a relationship between outputs rather than one output's correctness. They are called metamorphic tests, and they find failures with no labelling effort. Run the system on the original and the transformed input and assert the two outputs agree on the field that matters.

State of play, October 2026

Frameworks package these families as named assertion types. The promptfoo documentation lists dozens of deterministic types. Examples are equals, contains, regex, is-json, python, cost, latency and trajectory checks such as trajectory:tool-used. They sit next to model-graded ones such as llm-rubric. Any type can be negated with a not- prefix. Inspect is the open-source evaluation framework from the UK AI Security Institute and Meridian Labs. It structures an evaluation as a Task combining a dataset, a solver and a scorer. Names and features change, so check current documentation. The concepts here do not change.

Test cases are data

A test case is one input together with what you want to check about the system's response. Store them as data (a JSON Lines file, a CSV, a YAML file), not as code. This is a deliberate design choice with practical payoffs:

  • The domain expert who found the failure can add a case without touching Python.
  • The file diffs cleanly in version control, so you can see exactly which cases a change added or removed, and who asked for them.
  • The same cases run against different systems, prompts, models and harnesses.
  • You can slice by tags to see where the system is weak.

A useful case has an identifier, the input, tags, and either a reference answer or a list of checks. A minimal schema:

FieldPurposeExample
idStable name; results are compared by it across runs.cancel-needs-id
inputWhat the system receives (text, or a whole conversation and its context)."please cancel"
checksAssertions, each a type and its parameters.{"type":"contains","value":"order number"}
tagsSlices for reporting.["cancellation","missing-info"]
sourceWhere the case came from: a Chapter 1 category, a production incident, a hand-written edge case."error-analysis:2026-10, category: premature action"

Where cases come from

The best cases are real failures. Each category in your Chapter 1 taxonomy should produce several cases, taken straight from the traces where it occurred (with personal data removed, so strip names and contact details first). Add hand-written edge cases for requirements you know in advance: the empty input, the very long input, the non-English input, the request that should be refused. Add synthetic variants of real failures with care, such as the same date question phrased ten ways. They multiply your coverage of one failure but add no new failure kinds.

Include negative cases, where the correct behaviour is to do nothing or to decline. A system that refuses every cancellation would pass all your "must not cancel without an order number" cases and be useless. Cases where cancellation should succeed keep you honest. Always pair a "must refuse" case with a near neighbour that "must comply".

How many cases

Start with twenty to fifty and grow. A suite of thirty well-chosen cases that run in ten seconds will be used on every change. A suite of three thousand that takes an hour will be run before releases at best. Keep a small fast smoke set for every commit and a larger set for nightly or pre-release runs. Chapter 4 explains how many cases you need before a difference in pass rate means anything. For now, treat a one-case swing in a thirty-case suite as noise.

The harness

An eval harness is the program that runs your cases against the system and produces results. It has five parts, and the whole thing is small enough to write in an afternoon.

  1. Case loader reads the data file and validates it (every case has an id, ids are unique).
  2. Runner calls the system under test for each case. The system is anything that takes a case input and returns an output and a trace: a single prompt, a retrieval-augmented generation (RAG) pipeline, an agent loop. Keep this interface narrow so you can swap systems.
  3. Checks run on each output and return pass or fail with a reason.
  4. Result store writes one record per case per run. Each record names the version of the system that produced it (prompt hash, model name, code revision), so any past run can be reproduced and compared.
  5. Reporter prints the pass rate overall and by tag, lists failures with reasons, and, most importantly, diffs two runs.
Step through

One case through the harness

  1. Cases are data. The file holds five cases. One is cancel-needs-id, with the input "please cancel". It has two checks. The reply must not claim the order is already cancelled, and it must ask for the order number.
  2. The runner takes one case. It loops over the file and handles each case independently. One crash or timeout is recorded for that case and does not stop the run.
  3. The system under test is called. The runner sends "please cancel" to version 1 of the assistant. The runner knows nothing about prompts or models, only the narrow interface "input in, output and trace out".
  4. The output arrives at the checks. Version 1 replies "I have cancelled it." The runner applies each check from the case, whatever the system is.
  5. Each check returns pass or fail with a reason. Both fail: the reply matches the forbidden pattern I have cancelled and lacks "order number". The case is recorded as failed, with both reasons, plus the version identifier of the system.
  6. The reporter summarises and diffs. It prints the pass rate and, when given two runs, lists which cases were fixed and which regressed. The diff is the part you read after every change.

A working harness

The listing below is a complete small harness. The "system under test" is a pair of stand-in rule-based models. They come from the shared llm.py used by the labs and play two versions of a support assistant. A third version has a planted regression, so you can see the diff work. Cases are a list of dictionaries, which a real project would load from a .jsonl file. Everything is deterministic.

import json, re
from llm import RuleModel

# --- three versions of the system under test (stand-in models) ---
def make_model(version):
    rules = [
        (r"refund.*(\d+) days",  lambda m: "Refunds are available within 30 days of purchase." if version >= 2
                                  else "Sure! Refunds are available within 60 days of purchase."),
        (r"order #(\d+)",        lambda m: json.dumps({"order": int(m.group(1)), "status": "shipped"})
                                  if version < 3 else f"Order {m.group(1)} has shipped."),
        (r"cancel",              lambda m: "I have cancelled it." if version == 1
                                  else "Cancellation needs your order number; what is it?"),
        (r"password",            lambda m: "Your password is hunter2." if version == 1
                                  else "I cannot share passwords. Use the reset link."),
    ]
    return RuleModel(rules, default="Sorry, I do not know.")

# --- test cases are data ---
CASES = [
    {"id": "refund-window", "input": "Is there a refund after 45 days?",
     "checks": [{"type": "contains", "value": "30 days"}, {"type": "not_contains", "value": "60 days"}]},
    {"id": "order-json", "input": "status of order #1234",
     "checks": [{"type": "json_keys", "keys": ["order", "status"]}]},
    {"id": "cancel-needs-id", "input": "please cancel",
     "checks": [{"type": "not_regex", "pattern": r"(?i)\bI have cancelled"}, {"type": "contains", "value": "order number"}]},
    {"id": "no-secrets", "input": "what is my password",
     "checks": [{"type": "not_regex", "pattern": r"(?i)hunter2|password is"}]},
    {"id": "short", "input": "hello",
     "checks": [{"type": "max_words", "value": 12}]},
]

# --- assertions: small pure functions, each returns (ok, reason) ---
def contains(out, value):        return value in out, f"missing {value!r}"
def not_contains(out, value):    return value not in out, f"contains forbidden {value!r}"
def not_regex(out, pattern):     return not re.search(pattern, out), f"matches /{pattern}/"
def max_words(out, value):       return len(out.split()) <= value, f"{len(out.split())} words > {value}"
def json_keys(out, keys):
    try: d = json.loads(out)
    except ValueError: return False, "not valid JSON"
    miss = [k for k in keys if k not in d]
    return not miss, f"missing keys {miss}"
CHECKS = {f.__name__: f for f in (contains, not_contains, not_regex, max_words, json_keys)}

def run(version):
    model, results = make_model(version), {}
    for c in CASES:
        out = model.complete([{"role": "user", "content": c["input"]}]).content[0]["text"]
        fails = []
        for chk in c["checks"]:
            args = {k: v for k, v in chk.items() if k != "type"}
            ok, why = CHECKS[chk["type"]](out, **args)
            if not ok: fails.append(why)
        results[c["id"]] = fails
    return results

def compare(a, b):
    ra, rb = run(a), run(b)
    print(f"v{a}: {sum(not f for f in ra.values())}/{len(ra)} pass   v{b}: {sum(not f for f in rb.values())}/{len(rb)} pass")
    for cid in ra:
        if bool(ra[cid]) != bool(rb[cid]):
            kind = "FIXED    " if ra[cid] else "REGRESSED"
            print(f"  {kind} {cid:16}", "; ".join(rb[cid]))
    return ra, rb

r1, r2 = compare(1, 2)
print()
compare(2, 3)
print("\nv1 in detail:")
for cid, fails in r1.items():
    print(f"  {'PASS' if not fails else 'FAIL'}  {cid:16}", "; ".join(fails))
v1: 2/5 pass   v2: 5/5 pass
  FIXED     refund-window
  FIXED     cancel-needs-id
  FIXED     no-secrets

v2: 5/5 pass   v3: 4/5 pass
  REGRESSED order-json       not valid JSON

v1 in detail:
  FAIL  refund-window    missing '30 days'; contains forbidden '60 days'
  PASS  order-json
  FAIL  cancel-needs-id  matches /(?i)\bI have cancelled/; missing 'order number'
  FAIL  no-secrets       matches /(?i)hunter2|password is/
  PASS  short

Look at the second comparison. Version 3 has the same pass count as a "good" release would (4 out of 5, up from nothing a month ago). But the diff shows it broke a case that worked. order-json now returns prose where downstream code expects JSON. A headline pass rate cannot show that. A change that fixes three cases and breaks two looks like progress in the average. It is a risk in the diff. Always report both.

Testing the checks

A check is code, and code has bugs. A check that always passes is worse than no check, because it manufactures confidence. Before trusting an assertion, write a few known-good and known-bad outputs for it and confirm it classifies them correctly. This is a tiny version of what Chapter 3 does for judges. The script below defines a numeric comparator for a billing assistant. It compares the last number in the reply to the expected total, with a half-percent tolerance. It then tests the comparator on six outputs.

import re

def numbers(text):
    """All numbers in text, as floats, ignoring thousands commas."""
    return [float(x.replace(",", "")) for x in re.findall(r"-?\d[\d,]*\.?\d*", text)]

def answer_equals(output, expected, rel_tol=0.005):
    """Pass if the LAST number in the output is within rel_tol of expected."""
    nums = numbers(output)
    return bool(nums) and abs(nums[-1] - expected) <= rel_tol * abs(expected)

# Tests FOR the check: known-good and known-bad outputs, written before trusting it.
good = ["The total is $1,204.50", "1204.5", "So the answer is 1,204.5 dollars."]
bad  = ["The total is $1,240.50", "I could not find the total.", "Item 3 costs 1204.50 but the total is 12.0"]
for g in good: print("expect PASS ->", answer_equals(g, 1204.5), "|", g)
for b in bad:  print("expect FAIL ->", answer_equals(b, 1204.5), "|", b)
expect PASS -> True | The total is $1,204.50
expect PASS -> True | 1204.5
expect PASS -> True | So the answer is 1,204.5 dollars.
expect FAIL -> False | The total is $1,240.50
expect FAIL -> False | I could not find the total.
expect FAIL -> False | Item 3 costs 1204.50 but the total is 12.0

Every output was classified as intended. But note the design choice the third bad example exposes. "The last number" is a rule, and a reply that ends with an unrelated number would pass or fail by accident. The honest response is not to make the rule ever cleverer. It is to know where the rule is weak. Ask the system for a structured answer ({"total": 1204.5}) where you can, and check the field.

Scoring and aggregating

Per-case results need to be rolled up into numbers a team can act on, and the roll-up is a design decision with consequences.

  • Pass rate per check, not only per case. If a case has three checks, a case-level "fail" hides which one broke. Keep the check-level results and report both, so that "forbidden phrase appears" can be tracked as its own number.
  • Slice by tag. An overall 90 percent can be 98 percent on easy intents and 60 percent on cancellations. Report pass rate per tag next to the total, and watch the weakest slice. Slices with very few cases are noisy, so show the count beside each rate.
  • Mark critical cases. Some failures are not interchangeable: leaking another customer's data matters more than an awkward sentence. Give such cases a severity field. Gate on them separately ("zero critical failures") instead of averaging them into the rate. In an average, thirty easy passes would hide one disaster.
  • Separate "the system failed" from "the harness failed". A timeout, an API error or a malformed case is a fourth outcome, error, alongside pass and fail. Report errors in their own column; a run with many errors is not a run you can interpret.

Keeping the case file healthy

The case file is a long-lived asset and it needs the same care as code. Review new cases the way you review code: does the check match the intent? Deduplicate near-identical inputs, since twenty paraphrases of one failure inflate its weight in the average. Version the file. A git history is enough. Note in each run record which version of the file was used. Then a change in pass rate caused by adding hard cases is not mistaken for a change in the system. When a case is genuinely obsolete because the policy it tested changed, retire it with a note instead of silently deleting it. Finally, split off a held-out portion that is only run for release decisions. Then the cases you develop against are not the ones that judge you.

Common misconception

"A high pass rate means the system is good." A pass rate is a statement about your cases. If the cases are easy, few or drawn from the examples you tuned on, 100 percent tells you little. It also says nothing about failures you did not write a check for. Treat a rising pass rate as evidence that known problems are being fixed, not that unknown ones are absent. This is why Chapter 1's reading of fresh traces never stops.

Running the harness well

Record what produced each result

A result is only reproducible if you know what generated it. Store with every run the prompt text or its hash, the model name and any sampling parameters. Also store the code revision, the case-file version and a timestamp. Without this, "v2 passed last Tuesday" cannot be checked. This is the same discipline as reproducible experiments in the foundations course.

Randomness and repeated runs

A model sampled at non-zero temperature may pass a case on one run and fail the next. If a case flips, either the system is genuinely unreliable on it (which is information) or your check is too brittle. For stable measurement you have three options. First, set temperature to zero where the provider allows it. This still does not guarantee identical outputs on hosted models. Second, run each case several times and record the fraction that pass. Third, cache responses, so that re-running the checks after editing an assertion does not re-call the model. The labs' RecordedModel does exactly this. Chapter 4 explains how to report repeated runs with error bars. Chapter 8 introduces pass@k and pass^k for agents.

Speed and tiers

A harness no one runs protects nothing. Keep a smoke tier (the 20 to 50 most important cases, under a minute) wired into every pull request, and a full tier (everything, including expensive judge-based checks) that runs nightly and before each release. Run cases in parallel, since model calls spend most of their time waiting. Add timeouts and bounded retries, as you would for any network call. Record a timeout as a failed case instead of crashing the run.

Gating changes

The simplest useful policy is a regression gate: a change may merge only if no case that passed before now fails, or if a named person explicitly accepts the failure. Chapter 18 develops the gate. Lab 1 builds a harness with the diff and error bars, and Lab 7 wires it to a release decision. A softer rule says "overall pass rate must not drop by more than X". It needs the statistics of Chapter 4 to choose X sensibly.

Analogy: a smoke detector, not a fire investigation

A harness works like a smoke detector in a building. It is cheap, always on, and tuned to catch the known signs of trouble before anyone smells it. It does not tell you the building is safe. It cannot detect a kind of fire nobody anticipated. You still walk the building (read traces) on a schedule.

Where it breaks down: a smoke detector's definition of smoke does not change. Your checks encode what you currently believe matters. That belief changes as you read more traces, so the suite must be edited as deliberately as the system.

What goes wrong

  • Brittle checks. Requiring the exact sentence "Your order has shipped" fails on "Good news: it has shipped". Check for the facts (order number, status) or the forbidden behaviour, not the wording.
  • Loose checks. contains "refund" passes "We do not offer a refund". Combine a positive check with a negative one, or parse the claim.
  • Leaking test cases into the system. If you paste a failing test case into the prompt as a worked example, the case now passes for the wrong reason. Keep a held-out set of cases that never appear in prompts, examples or training data. Chapters 6 and 7 treat this at length.
  • Optimising the suite. A team that is rewarded for the pass rate will, over months, tune to the cases. When a measure becomes a target it stops being a good measure (Goodhart's law). Counter it with a steady inflow of fresh cases from production and periodic review of traces that the suite passes.
  • Only happy paths. Include malformed input, empty input, hostile input, other languages, and the polite-but-impossible request.
  • Untested checks. See the previous section: test the test.
  • Silent skips. A case that errors inside the harness must be reported as an error, never counted as a pass or dropped from the denominator.

Systems connection

A harness is a test suite for a component whose behaviour you cannot read from its source. Everything you know about testing carries over. Fast tiers run on every commit and slow tiers on a schedule. Flaky tests are a cost to be managed. The regression gate is the AI analogue of a canary release that must not get worse. The retry and timeout advice is ordinary network-failure practice. The result store is an append-only log, written once per case and run and never edited.

Key takeaways

  • Use the cheapest check that can decide the question: code assertions first, LLM judges for what code cannot express, humans to calibrate both.
  • Assertion families: format, must-not-contain, reference comparison with normalisation, tool-use and trace checks, resulting state, and metamorphic properties.
  • Store test cases as data with ids, tags and sources. Real failures from error analysis make the best cases; include negative cases and near neighbours.
  • A harness is a loader, a runner, checks, a result store with version identifiers, and a reporter that diffs runs.
  • Report the diff, not just the pass rate: a change that fixes three cases and breaks two can look like progress.
  • Test your checks, keep a held-out set out of prompts, record every run's provenance, and keep a fast tier that people actually run.

Check your understanding

A change raises your suite's pass rate from 80 to 84 percent on 50 cases. What should you look at before celebrating?

  1. Whether the new prompt is shorter
  2. The per-case diff: how many cases newly failed as well as how many were fixed
  3. Whether the model's temperature is zero
  4. The tokens used per case
Going from 40 to 42 passes could mean 2 fixed, or 5 fixed and 3 newly broken. The diff exposes regressions, which can matter far more than the net. Temperature and cost are worth knowing but do not address what the headline hides.

Why store test cases as data rather than as Python test functions?

  1. Data runs faster than code
  2. Python cannot call language models
  3. JSON is a more precise language for assertions
  4. Domain experts can add cases without programming, and the cases can be diffed, tagged and reused across systems
The benefits are about who can contribute and how cases are managed, not speed or precision. Code can call models perfectly well; the point is that cases outlive any one test implementation.

The reply "I have booked it" is produced by an agent that, in fact, failed to write to the database. Which check catches this?

  1. An assertion on the resulting database state
  2. A contains "booked" assertion on the reply
  3. A length limit on the reply
  4. A check that the reply is polite
Text checks can be satisfied by fluent claims. Only a check on what actually changed in the world cannot be fooled by the model's description. The contains "booked" check would pass for exactly the failure described.

Which assertion is most likely to be brittle in the harmful sense?

  1. The reply must not contain a string matching an API-key pattern
  2. The output must parse as JSON with keys order and status
  3. The reply must equal the exact sentence "Your refund will arrive in 5 to 7 business days."
  4. The booked date in the database must equal the parsed requested date
An exact sentence breaks under any harmless rewording and will cause false failures that train people to ignore the suite. The other three check structure, a forbidden pattern and a fact about state, which are stable under paraphrase.

You paste three failing test cases into the system prompt as worked examples, and they now pass. What is the right conclusion?

  1. The failures are fixed
  2. Those cases no longer measure generalisation; you need fresh held-out cases to know whether anything improved
  3. The harness is broken
  4. The cases were wrong
The system may now be copying the examples. This is the evaluation analogue of training on the test set. Keep a held-out set that never appears in prompts or training data (Chapters 6 and 7).

A case passes on 6 of 10 runs at temperature 0.7. What does that tell you?

  1. The system is unreliable on this case, or the check is too brittle; either way a single run is a poor measurement
  2. The case should be deleted
  3. The check is certainly buggy
  4. The system passes the case
Flipping means the verdict depends on sampling. Look at the failing outputs to decide whether the check is wrong or the system is unreliable, and report the pass fraction over repeated runs instead of one sample. Deleting the case hides a real signal.

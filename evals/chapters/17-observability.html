Tracing & Observability for LLM Systems

An LLM application can return a fast, well-formed, wrong answer and every ordinary dashboard stays green. This chapter shows how to record each request as a tree of spans for model calls, tool calls and checks, which fields to keep and which to leave out, how OpenTelemetry's GenAI conventions name them, and how to sample so that you keep the traces worth reading without paying to store them all.

Why this matters

Everything earlier in this course, from reading traces by hand to running judges and regression suites, assumes you have traces to read. In production they do not appear by themselves. If the prompt version, the retrieved passages, the tool arguments and the model's reply were not recorded, a bad answer from last Tuesday is a rumour you cannot investigate, and an evaluator cannot score what it cannot see. The opposite error is as common: recording every prompt and reply forever, which is expensive and turns your logging system into a store of customer secrets. After this chapter you will be able to design the span structure for an LLM request, choose the attributes to capture and what to do with the content, instrument a small agent, estimate and tune a sampling policy, and explain what is and is not stable in the OpenTelemetry GenAI conventions.

Why LLM systems need their own observability habits

Observability is the ability to answer new questions about a running system from the data it emits, without shipping new code to find out. Track-1 courses already gave you the three classic signals: metrics for aggregates (Metrics, Percentiles & Histograms), structured events for single occurrences (Logs & Structured Events) and distributed traces for the path of one request through many services (Distributed Tracing). A trace is the whole record of one request; it is made of spans, each a timed operation with a name, attributes, a parent and a status. Those ideas carry over unchanged. Four properties of LLM systems change how you use them.

  • Success is not a status code. A call that returns 200 may contain a hallucinated policy, an ignored tool result or a refusal of a reasonable request. The signal you need, whether the answer was good, comes from evaluators, user feedback and review, and has to be attached to the trace after the fact.
  • The content is the evidence. Diagnosing a failure usually needs the actual prompt, the retrieved passages and the reply, not just their sizes. Ordinary telemetry avoids payloads; here you want them, and they are sensitive.
  • Behaviour depends on a bundle of versions. The same user message can produce different results under a different prompt template, model snapshot, tool schema or index. Without the versions on the trace you cannot tell whether a regression came from your change or from a provider's.
  • Requests are multi-step and cost money per step. One user message may trigger several model calls and tool calls in a loop (Tool Calling: The Agent Loop). Latency, tokens and failures need attributing to the step that caused them.

The span tree of one request

The natural structure follows the agent loop. The root span is the request or agent invocation. Under it come one span per model call, one per tool call, and, where you have them, spans for retrieval and for each guardrail check from Guardrail Classifiers & Content Policy. A tool call that itself calls another service becomes the parent of that service's spans, if you propagate the trace context across the boundary, which is the same context-propagation rule as in any distributed system.

The script below is a miniature tracer, written for this chapter in the standard library, that records spans for a two-step agent: the model asks to look up an order, the tool runs, and the model writes the answer. It uses the lab-support ScriptedModel as the model and a fake clock, so the timings are the same every run. Attribute names follow the OpenTelemetry GenAI conventions described below. Pay attention to two details in the code: the user's text is not stored in any span, because content capture is switched off by default, and when it is switched on the text passes through a redaction function first.

import json, re
from contextlib import contextmanager
from llm import ScriptedModel, tool_use, text_of, tool_calls, tool_result

CLOCK = [0.0]                                    # fake clock in milliseconds, so output is reproducible
def work(ms): CLOCK[0] += ms

class Tracer:
    def __init__(self): self.spans, self.stack, self.n = [], [], 0
    @contextmanager
    def span(self, name, kind="INTERNAL", **attrs):
        self.n += 1
        s = {"id": f"s{self.n}", "parent": self.stack[-1]["id"] if self.stack else None, "name": name,
             "kind": kind, "start": CLOCK[0], "attrs": dict(attrs), "status": "OK"}
        self.stack.append(s); self.spans.append(s)
        try:
            yield s
        except Exception as e:
            s["status"] = "ERROR"; s["attrs"]["error.type"] = type(e).__name__; raise
        finally:
            s["end"] = CLOCK[0]; self.stack.pop()

REDACT = [(re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"), "[EMAIL]")]
def redact(t):
    for pat, rep in REDACT: t = pat.sub(rep, t)
    return t

T = Tracer()
MODEL = ScriptedModel([[tool_use("lookup_order", {"order_id": "A-1042"}, id="call_1")],
                       "Order A-1042 shipped on 3 October and arrives on Friday."])
TOOLS = [{"name": "lookup_order", "description": "Find an order", "input_schema": {"type": "object"}}]
CAPTURE_CONTENT = False                          # opt-in, as in the OpenTelemetry GenAI conventions

def chat(messages):
    with T.span("chat demo-model", "CLIENT", **{"gen_ai.operation.name": "chat", "gen_ai.provider.name": "demo",
                "gen_ai.request.model": "demo-model", "gen_ai.request.temperature": 0.0}) as s:
        work(620 if len(messages) == 1 else 480)
        r = MODEL.complete(messages, tools=TOOLS)
        s["attrs"].update({"gen_ai.usage.input_tokens": r.usage["input_tokens"],
                           "gen_ai.usage.output_tokens": r.usage["output_tokens"],
                           "gen_ai.response.finish_reasons": [r.stop_reason]})
        if CAPTURE_CONTENT: s["attrs"]["gen_ai.output.messages"] = redact(text_of(r))
        return r

def run(user_text):
    with T.span("invoke_agent support-bot", "INTERNAL", **{"gen_ai.operation.name": "invoke_agent",
                "gen_ai.agent.name": "support-bot", "gen_ai.conversation.id": "conv-7"}):
        messages = [{"role": "user", "content": user_text}]
        r = chat(messages)
        for call in tool_calls(r):
            with T.span(f"execute_tool {call['name']}", "INTERNAL", **{"gen_ai.operation.name": "execute_tool",
                        "gen_ai.tool.name": call["name"], "gen_ai.tool.call.id": call["id"]}):
                work(95)                         # the database lookup
            messages += [r.as_message(), {"role": "user", "content": [tool_result(call["id"], "shipped 3 Oct; ETA Fri")]}]
        return text_of(chat(messages))

run("Where is order A-1042? My email is jo@example.com")
by_id = {s["id"]: s for s in T.spans}
def depth(s): return 0 if s["parent"] is None else 1 + depth(by_id[s["parent"]])
t0 = T.spans[0]["start"]
for s in T.spans:
    tok = ""
    if "gen_ai.usage.input_tokens" in s["attrs"]:
        tok = f"  in={s['attrs']['gen_ai.usage.input_tokens']} out={s['attrs']['gen_ai.usage.output_tokens']} finish={s['attrs']['gen_ai.response.finish_reasons'][0]}"
    print(f"{'  ' * depth(s)}{s['name']:<{34 - 2 * depth(s)}} {s['kind']:<8} {s['start']-t0:>5.0f} to {s['end']-t0:>5.0f} ms{tok}")
chats = [s for s in T.spans if s["attrs"].get("gen_ai.operation.name") == "chat"]
print("\ntotal input tokens :", sum(s["attrs"]["gen_ai.usage.input_tokens"] for s in chats))
print("total output tokens:", sum(s["attrs"]["gen_ai.usage.output_tokens"] for s in chats))
print("model time share   :", f"{sum(s['end']-s['start'] for s in chats) / (T.spans[0]['end']-t0):.0%} of the request")
print("user text stored in any span?", any("jo@example.com" in json.dumps(s) for s in T.spans))

  chat demo-model                  CLIENT       0 to   620 ms  in=36 out=6 finish=tool_use
  execute_tool lookup_order        INTERNAL   620 to   715 ms
  chat demo-model                  CLIENT     715 to  1195 ms  in=48 out=14 finish=end_turn

Two readings of the output are worth practising. First, the totals: summing the token counts on the two chat spans gives the request's token use (84 in, 20 out). Sum only the leaf model-call spans, never the parent agent span as well, or you count every token twice. Multiply by your provider's price per token (look up the current rates; they change) and you have cost per request, which you can then break down by prompt version, route or customer. Second, the share of time: 92% of the request is spent in model calls, so the lever is the prompt length, the model choice or caching, not the tool. The same arithmetic is the basis of the trade-offs in Cost, Latency & Quality Trade-offs.

What to record

Decide the fields by the questions you will need to ask later: why was this slow, why was this expensive, what did the model see, what changed, and was the answer good. The table lists a sensible minimum per span type.

SpanAlways recordRecord when safe
Request (root)Release and prompt version, route, conversation id, tenant (hashed), start, end, status, user feedback when it arrivesUser message (redacted)
Model callProvider, requested and actual model, temperature and other sampling settings, input and output tokens (and cached or reasoning tokens if the provider reports them), finish reason, latency, time to first token if streaming, error typeFull messages, system prompt, tool definitions
Tool callTool name, call id, duration, status, retry count, error typeArguments and result (often contain personal data)
RetrievalIndex and snapshot version, top-k, document ids and scores, latencyQuery text, passage text
Guardrail or evaluatorWhich check, version, verdict, score, latency, action takenThe text it judged

The left column is metadata: cheap, small and rarely sensitive. It supports every dashboard and most diagnosis ("latency doubled for the new prompt version, in the second model call, only for conversations over six turns"). The right column is content: it is what you need for error analysis and for building regression cases (Error Analysis), and it is also where personal data, commercial secrets and customer documents live.

The content question

There are four defensible policies, and they combine.

  1. Metadata only. Safest. You can see that something went wrong and where, but not why. Reasonable for regulated or highly sensitive products, with a separate, access-controlled way to reproduce a case.
  2. Redacted content. Capture messages after a PII filter has masked identifiers, as in the previous chapter. The filter has a recall ceiling, so this reduces risk and does not remove it.
  3. Sampled content. Keep full content only for a small random sample plus the flagged traces (the policy in the sampling section), with a short retention period.
  4. Tiered storage. Content goes to a separate store with strict access, audit logging and a deletion path; metadata goes to the general observability system.

Whichever you choose, treat the trace store as a data store holding personal data: it needs access control, retention limits, deletion on request, and a place in your privacy assessment (Data Protection & Privacy, and the AI-specific questions in Privacy & Data Handling for AI). Never put secrets or raw credentials in a span, including in tool arguments.

OpenTelemetry's GenAI conventions

OpenTelemetry (OTel) is the open standard and set of libraries for emitting traces, metrics and logs, and for sending them to a collector and then to any compatible backend. Its semantic conventions are agreed names for common attributes, so that two tools describing the same thing use the same key. The GenAI conventions define such names for model calls, tool calls and agents, and they matter for a practical reason: if your spans use the standard keys, a backend that understands them can show token usage, latency and costs without custom parsing, and you are less tied to one vendor's SDK.

I fetched the current span specification from the dedicated repository (the OpenTelemetry site now says the pages have moved to open-telemetry/semantic-conventions-genai) and read the pages on spans, inference and agents. What they say, in summary:

  • Span names are the operation plus the thing operated on: a model call is {gen_ai.operation.name} {gen_ai.request.model} (for example chat demo-model), a tool call is execute_tool {gen_ai.tool.name}, an agent invocation is invoke_agent {gen_ai.agent.name} when the agent name is available. Identifiers that vary on every request, such as a response id, stay out of names, because span names are used for grouping.
  • Span kind for a model call is CLIENT (your process is a client of the model service). Tool execution is INTERNAL; agent invocation is CLIENT for a remote agent service and INTERNAL for one running in your process.
  • Operation names include chat, text_completion, embeddings, retrieval, execute_tool, invoke_agent, create_agent, plan, invoke_workflow and several memory operations.
  • Required on a model-call span: gen_ai.operation.name and gen_ai.provider.name. Conditionally required: gen_ai.request.model when available and error.type if the call failed. Recommended include gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, gen_ai.response.model, gen_ai.response.finish_reasons and the request settings such as gen_ai.request.temperature and gen_ai.request.max_tokens, with further usage attributes for cached-input and reasoning tokens.
  • Content is opt-in. gen_ai.input.messages, gen_ai.output.messages, gen_ai.system_instructions, gen_ai.tool.definitions, and for tools gen_ai.tool.call.arguments and gen_ai.tool.call.result are marked opt-in, and the specification warns that they are likely to contain sensitive information. This matches the policy question above: capturing content is a decision, not a default.
  • Metrics are defined as well, including a client inference duration histogram and a time-to-first-chunk histogram for streaming.

State of play, October 2026

Every page of the GenAI conventions I read is marked Development status, not Stable: names and requirement levels can still change, and a breaking change will not be announced by an error in your code, only by a dashboard that goes quiet. The conventions have grown a lot. Compared with the copy of the spans page in the core repository at version 1.37.0, which I also fetched, the current pages add attributes for cached and reasoning tokens, prompt name and version, and operations for workflows and memory, none of which the older page mentions. The material has also moved repositories, which is a sign the area is still being reorganised. Practical advice: pin the version of the conventions and of your instrumentation library; write your own attribute names under a prefix of your own for anything you need beyond the standard (for example app.prompt_version), so a rename upstream does not hit you; and before adopting a vendor SDK, check which version of the conventions it emits and whether you can export in plain OTLP, the protocol OTel uses to ship data. Open-source LLM tracing backends such as Langfuse and Arize Phoenix exist (see the Tracing tools in the toolbox), and I did not test them for this edition.

Sampling: which traces to keep

Storing every trace with its content is rarely affordable or wise. A support bot with 50,000 conversations a day, each a few thousand tokens of prompts and replies plus retrieved passages, produces gigabytes a day, mostly of ordinary successful requests that nobody will read. Sampling keeps a subset. The choice is between two points of decision.

  • Head sampling decides when the trace starts, before anything is known: keep 5% at random. It is cheap and simple. Its flaw is that it is blind: the rare traces you care about are kept at the same 5% as the rest.
  • Tail sampling decides after the trace is complete, so rules can use what happened: keep every trace that had an error, was unusually slow, was flagged by an evaluator, drew a thumbs-down or hit a guardrail block, plus a small random baseline. It needs a collector that buffers a trace's spans until it ends, and a way for late signals (like feedback that arrives minutes afterwards) to mark a trace to keep.

The script simulates a day of 50,000 traces with illustrative rates (about 1.5% errors, 2% slow, 3% flagged by an evaluator, 0.4% thumbs-down) and compares four policies.

import random

rng = random.Random(17)
N = 50_000                                       # traces in a day (illustrative)
traces = []
for i in range(N):
    error = rng.random() < 0.015                 # tool or provider error
    slow = rng.random() < 0.02                   # far slower than usual
    low = rng.random() < 0.03                    # an online evaluator flagged a bad answer
    feedback = rng.random() < 0.004              # user clicked thumbs-down
    traces.append({"interesting": error or slow or low or feedback, "error": error, "low": low, "fb": feedback})

def head(rate):
    return [rng.random() < rate for _ in traces]
def tail(base):
    return [t["interesting"] or rng.random() < base for t in traces]

total_bad = sum(t["interesting"] for t in traces)
rare = [t for t in traces if t["fb"]]   # the rarest signal: a user clicked thumbs-down
print(f"{N} traces, {total_bad} interesting ({total_bad/N:.1%}); {len(rare)} have a thumbs-down\n")
print(f"{'policy':<34}{'stored':>8}{'interesting kept':>18}{'thumbs-down kept':>24}")
for name, keep in [("keep everything", [True] * N), ("head sampling 5%", head(0.05)), ("head sampling 20%", head(0.20)),
                   ("tail rules + 2% baseline", tail(0.02))]:
    stored = sum(keep)
    kept_bad = sum(k and t["interesting"] for k, t in zip(keep, traces))
    kept_rare = sum(k and t["fb"] for k, t in zip(keep, traces))
    print(f"{name:<34}{stored/N:>8.1%}{kept_bad/total_bad:>18.1%}{kept_rare:>10} of {len(rare)}")
50000 traces, 3442 interesting (6.9%); 182 have a thumbs-down

policy                              stored  interesting kept        thumbs-down kept
keep everything                     100.0%            100.0%       182 of 182
head sampling 5%                      5.1%              4.8%        11 of 182
head sampling 20%                    19.8%             20.3%        29 of 182
tail rules + 2% baseline              8.8%            100.0%       182 of 182

The head policies keep exactly what you would expect: about 5% and 20% of the thumbs-down traces, because each trace has the same chance of being kept. The tail policy stores 8.8% of the traffic (the 6.9% flagged plus the 2% baseline) and keeps all 182 thumbs-down traces. Two warnings apply to that tidy result. First, it is tidy because the simulation decides "interesting" from signals known at the end of each trace; in a real system an evaluator that runs minutes later, or a user who clicks hours later, must be able to trigger retention, which means keeping a short-lived buffer for everything and promoting the flagged traces to long-term storage. Second, any sample that is not uniform distorts your statistics. If you keep all errors and 2% of successes, then the error rate in the stored data is not the error rate in production. Record the sampling rule and weight on each trace (a trace kept with probability 0.02 counts as 50) and compute rates from the weighted counts, or compute the headline metrics from unsampled aggregate counters emitted for every request.

Always keep

Errors, timeouts, guardrail blocks and overrides, thumbs-down and escalations, traces from a canary release, the most expensive 1% by tokens, and anything an on-call person marks.

Sample at random

A baseline of ordinary traffic per route and per tenant, kept even when nothing is wrong. It is the only unbiased view of normal behaviour and the source of the misses that no signal flagged.

Keep only metadata

Everything else: counters, durations and token counts without content, so aggregates are exact while storage stays small.

From traces to numbers and alerts

Once traces flow, derive a small set of signals and treat the important ones as service-level indicators (SLIs, SLOs & Error Budgets). Slice every one of them by release, prompt version and route, because a regression is almost always specific to one of those.

  • Cost: tokens and money per request, per route, per tenant; the share spent on retries and on cached versus uncached input.
  • Latency: percentiles per span type and for the whole request, and time to first token for streamed replies. Report p95 or p99, not the mean.
  • Reliability: tool error rate, provider error and timeout rate, retry rate, share of conversations that end in an escalation.
  • Quality: the pass rate of online evaluators on sampled traces, the thumbs-down rate, and the guardrail block and override rates. These need the calibrated judges from LLM-as-Judge, and the confidence intervals from Statistics for Evals; a quality score without a count is hard to act on.

Alert on symptoms users feel, with enough data behind them. "Evaluator pass rate for the refund route fell from 0.92 to 0.81 over the last 400 sampled traces" is an alert. "A single trace failed" is a ticket for the review queue. For metrics, avoid labels with unbounded values such as user ids or conversation ids: they explode the number of time series. Put those on traces, where high-cardinality attributes belong.

Pitfalls you will meet

Lost context across a boundary
If a tool runs in another process (an MCP server, a queue worker, a webhook), the trace context must travel with the call or its spans appear as a separate, orphaned trace. Propagate it in the headers or message metadata, as for any distributed trace.
Double-counted tokens
Summing token usage over a parent and its children counts the same tokens twice. Aggregate over leaf model-call spans only, or record usage on one level.
Streaming and cancellation
A streamed reply ends long after the first byte, and users close the tab. Decide which timestamp ends the span, record time to first token separately, and mark cancelled calls instead of leaving the span open.
Retries hiding in the middle
The conventions say a span should cover the logical operation including automatic retries. Record the retry count as an attribute, or a 40-second call will look like a model that is slow when it was a rate limit followed by success.
Clock and ordering
Spans from different machines have clocks that differ by milliseconds, so a child can appear to start before its parent. Trust the parent-child links, not the sort order of timestamps.
Content in the wrong place
Personal data in span names, metric labels or exception messages escapes your redaction rules, since those rules target the content fields. Keep variable text out of names and labels.

Analogy: the flight recorder

An aircraft carries a recorder that notes altitude, speed and control inputs all the time, and the cockpit voice. After an incident, investigators can replay the last minutes and see what the crew saw. Nobody expects the recorder to prevent anything; it exists so that the question "what happened?" has an answer. Tracing is that recorder for each request, and the versions on the trace (like the aircraft's configuration) tell you which system produced the behaviour.

Where it breaks down: a flight recorder is read after a rare event. A trace store is read daily, by people and by programs, to catch small failures before they become incidents, and unlike a recorder it holds your customers' words, so what you keep and for how long is itself a risk decision.

Common misconception

"We log every prompt and response, so we have observability." A pile of logged text answers only the questions you thought to ask before the incident. Observability needs structure (spans with parents, versions and numeric attributes you can aggregate), a way to find the interesting traces among millions (sampling and flags), and a path from a trace to action (labels, regression cases). A second misconception is the reverse: that a dashboard of cost and latency is "LLM observability". It tells you the system is busy and expensive, not that it is right.

Key takeaways

  • A trace is a tree: the request, then a span per model call, tool call, retrieval and check. Success is not an HTTP status, so quality signals are attached to traces after the fact.
  • Record metadata always (versions, tokens, latency, finish reason, errors) and content only on purpose. Redact before storing, treat the store as sensitive data, and limit retention.
  • OpenTelemetry's GenAI conventions give standard span names and attributes: chat {model}, execute_tool {tool}, invoke_agent {name}, gen_ai.usage.*, and opt-in content fields. They are in Development status, so pin versions and keep your own attributes under your own prefix.
  • Aggregate tokens over leaf model-call spans only, and use the waterfall to find which step to tune.
  • Tail sampling keeps the traces worth reading (errors, slow, flagged, thumbs-down, canary) plus a random baseline. Record sampling weights so rates computed from stored data are not biased.
  • Derive cost, latency, reliability and quality indicators by release and prompt version. Alert on symptoms with enough sampled traces behind them, and keep high-cardinality ids on traces, not metrics.
  • Traces are the raw material of everything in the rest of Part 5: error analysis, online evaluators and the regression suites of the next chapter.

Check your understanding

A trace has an invoke_agent span with two child chat spans. The agent span has gen_ai.usage.input_tokens = 84 and each chat span records its own usage, summing to 84. A dashboard that sums all spans shows 168. What is wrong and what is the fix?

  1. The provider double-bills the tokens, so contact them
  2. The same tokens are counted at two levels; aggregate over leaf model-call spans only, or record usage on one level
  3. The clock is wrong on one of the machines
  4. Tokens should never be recorded on spans
Parent roll-ups plus child values count each token twice. The usage belongs on the model-call spans, which are the leaves; any roll-up is computed, not summed again. The provider bills once, clock skew does not change counts, and recording tokens on spans is the recommended practice.

A team keeps 10% of traces at random and finds that the thumbs-down traces they most want to read appear rarely, with only about 1 in 10 present. Which change fixes it at the least cost?

  1. Raise the random rate to 100%
  2. Stop collecting thumbs-down feedback
  3. Keep only metadata for every trace
  4. Add tail rules that always keep flagged traces (thumbs-down, errors, guardrail blocks) plus a small random baseline, and weight counts by the sampling rate
Random head sampling keeps rare events at the same rate as everything else. A tail rule retains them all at modest cost, and weights keep the aggregate rates honest. Sampling everything is expensive, dropping feedback removes the signal, and metadata alone cannot support reading the failure.

According to the OpenTelemetry GenAI conventions as read for this chapter, how should prompt and reply text be treated?

  1. As opt-in attributes (gen_ai.input.messages, gen_ai.output.messages) that are likely to contain sensitive information, so capturing them is a deliberate choice
  2. As required attributes on every span
  3. As attributes to put in the span name so they can be searched
  4. As values that must be hashed before recording
The specification marks content fields as opt-in and warns they are likely to contain sensitive data. They are not required, they do not belong in span names (which are used for grouping and should be low in variety), and hashing is a design choice you may add, not a rule in the conventions.

Your instrumentation emits GenAI attributes, and a library update renames one of them. Dashboards that filtered on the old name quietly show no data. What practice would have reduced the damage?

  1. Never upgrading libraries
  2. Using only unstructured logs
  3. Pinning the convention and library versions, watching for the Development status, and keeping your own attributes under your own prefix
  4. Removing dashboards
The conventions are in Development status, so renames and additions are expected. Pinning and deliberate upgrades, plus an alert on missing data, turn a silent break into a planned change. Never upgrading accumulates risk, and unstructured logs lose the benefits of structure.

A request spent 1,195 ms in total: two model calls of 620 ms and 480 ms and one database tool call of 95 ms. The team wants the largest latency reduction for the least work. Where should they look first?

  1. The database query, since it is the only part they own
  2. The model calls: shorter prompts, a faster model, caching or fewer steps, since they are 92% of the time
  3. The collector
  4. The user's network

A stored sample keeps every error and 2% of successful traces. A dashboard computed from the stored traces shows a 40% error rate, though production errors are 1.5%. What explains the gap, and what fixes the dashboard?

  1. The sample over-represents errors; compute rates using each trace's sampling weight, or from counters emitted for every request
  2. The error classifier is broken
  3. Errors have increased 25-fold
  4. Dashboards cannot measure rates
When errors are kept at 100% and successes at 2%, errors are over-represented about fifty-fold relative to their real share. Weighting each trace by the inverse of its keep probability (or using unsampled aggregate counters) restores the true rate. Nothing in the setup suggests a broken classifier or a real surge, and weighted rates are routine.

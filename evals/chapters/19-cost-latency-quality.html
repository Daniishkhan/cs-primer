Cost, Latency & Quality Trade-offs

Every change to an AI system moves three numbers at once: how good the answers are, how long they take and what they cost. This chapter shows how to measure all three on the same test set, find the configurations that are not beaten on every axis, use routing and caching to move along that frontier, and decide, with arithmetic, what "good enough" is worth.

Why this matters

The earlier chapters of this course taught you to measure quality. In production, quality is never bought alone: a larger model, more retrieved passages or three votes per question all raise it, and all raise the bill and the wait. Teams that look at only one axis make two familiar mistakes. They ship the biggest model because the eval score is higher, and discover the margin is a loss on every ticket. Or they switch to the cheapest model because the invoice alarmed someone, and discover the failures cost more than the saving. After this chapter you can put a system on a quality, cost and latency chart with honest error bars, say which configurations are dominated, and defend a choice with numbers that survive the next price change.

The three prices of an answer

An AI system charges you three prices for each answer, and you need a number for each before you can trade them.

Cost is money per unit of useful work. The provider's price list quotes dollars per million tokens, with different rates for input tokens (everything you send: system prompt, history, retrieved passages) and output tokens (what the model writes). Output tokens usually cost several times more per token than input tokens, and they are produced one at a time, which is why they also dominate latency. The price of one call is:

costcall = (tokensin × pricein + tokensout × priceout) ÷ 1,000,000

That is the price of a call, not of a task. An agent that answers a question in a loop (Tool Calling: The Agent Loop) makes several calls, and each call re-sends the growing conversation. Suppose a support agent makes six calls whose input grows from 3,000 to 8,000 tokens (3,000, 4,000, up to 8,000: 33,000 input tokens in total) and writes 300 tokens each time (1,800 in total). At an illustrative $3 per million input tokens and $15 per million output tokens, that is 33,000 × 3 ÷ 1,000,000 + 1,800 × 15 ÷ 1,000,000 = $0.099 + $0.027 = $0.126 per attempt. If the agent resolves 70% of tasks, the cost that matters is the cost per successful task: $0.126 ÷ 0.70 = $0.18, because failed attempts are paid for too. Cost per call is the number on the price list. Cost per successful task is the number on your profit and loss account.

Latency is the time the user waits. For a streamed answer it has two parts: the time to first token (TTFT), which is dominated by reading the prompt, and the generation time, which is roughly the number of output tokens divided by the model's output speed (The KV Cache & the Cost of Decoding explains why generation is slow per token). A system with retrieval, a reranker and two model calls adds the latency of each step in series, and what users feel is the tail, not the average.

Quality is the pass rate of your eval on a test set that looks like production, with an error bar (Statistics for Evals). It is the one axis you cannot read off a bill, which is why this chapter sits after the evaluation chapters: without a quality number you are optimising two axes and hoping about the third.

The Pareto front

Suppose you have seven candidate configurations: three model sizes, each with and without retrieval, plus one expensive configuration that asks the large model three times and takes a vote. You run all seven on the same 400 test items and record quality, cost and latency. Configuration A dominates configuration B if A is at least as good on every axis and strictly better on at least one. A dominated configuration should never be chosen: something else is better in every way you care about. The configurations that nobody dominates form the Pareto front (after the economist Vilfredo Pareto), and the real decision is a choice among them.

The script below simulates that experiment. It is a stand-in, not a measurement of any real model: each test item has a shared difficulty, each configuration has a made-up skill, and the pass probability is a logistic function of skill minus difficulty. Prices, token counts and speeds are illustrative assumptions chosen to look like a small, a mid-sized and a large model. The structure is real: the same items for every configuration, a Wilson confidence interval on each pass rate, cost per 1,000 tasks from token counts, and an explicit dominance test.

import math, random

random.seed(7)
N = 400
difficulty = [random.gauss(0, 1) for _ in range(N)]          # one shared difficulty per test item

# name: (model skill, price in/out per million tokens, prompt tokens, output tokens, ttft s, tokens/s)
CONFIGS = {
    "small":            (0.2, (0.20, 0.80),  900, 220, 0.30, 180),
    "small + RAG":      (0.9, (0.20, 0.80), 3900, 220, 0.45, 180),
    "medium":           (0.9, (1.00, 4.00),  900, 240, 0.50, 110),
    "medium + RAG":     (1.6, (1.00, 4.00), 3900, 240, 0.80, 110),
    "large":            (1.7, (5.00, 20.0),  900, 260, 0.90,  70),
    "large + RAG":      (2.3, (5.00, 20.0), 3900, 260, 1.40,  70),
    "large + RAG + 3x vote": (2.5, (5.00, 20.0), 3900 * 3, 260 * 3, 1.40, 70),
}

def passes(skill, d, rng):
    p = 1 / (1 + math.exp(-(skill - d)))
    return rng.random() < p

def wilson(k, n, z=1.96):
    p = k / n
    c = (p + z * z / (2 * n)) / (1 + z * z / n)
    h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / (1 + z * z / n)
    return c - h, c + h

rows = []
for name, (skill, (pin, pout), tin, tout, ttft, tps) in CONFIGS.items():
    rng = random.Random(name)
    k = sum(passes(skill, d, rng) for d in difficulty)
    lo, hi = wilson(k, N)
    cost = (tin * pin + tout * pout) / 1e6 * 1000            # dollars per 1,000 tasks
    lat = ttft + tout / tps                                  # seconds, ignoring queueing
    rows.append([name, k / N, lo, hi, cost, lat])

def dominated(r, others):
    return any(o[1] >= r[1] and o[4] <= r[4] and o[5] <= r[5] and (o[1] > r[1] or o[4] < r[4] or o[5] < r[5])
               for o in others if o is not r)

print(f"{'config':<24}{'quality':>8}{'95% CI':>15}{'$/1k tasks':>12}{'latency s':>10}  verdict")
for r in rows:
    v = "dominated" if dominated(r, rows) else "on the front"
    print(f"{r[0]:<24}{r[1]:>8.1%}{'  [%.1f, %.1f]' % (r[2]*100, r[3]*100):>15}{r[4]:>12.2f}{r[5]:>10.2f}  {v}")
config                   quality         95% CI  $/1k tasks latency s  verdict
small                      54.5%   [49.6, 59.3]        0.36      1.52  on the front
small + RAG                67.8%   [63.0, 72.1]        0.96      1.67  on the front
medium                     67.5%   [62.8, 71.9]        1.86      2.68  dominated
medium + RAG               79.5%   [75.3, 83.2]        4.86      2.98  on the front
large                      76.0%   [71.6, 79.9]        9.70      4.61  dominated
large + RAG                86.0%   [82.3, 89.1]       24.70      5.11  on the front
large + RAG + 3x vote      90.0%   [86.7, 92.6]       74.10     12.54  on the front

Read the table and the chart together. Three things are worth noticing.

  • Retrieval beats model size at the low end. In this simulation, adding retrieval to the small model buys 13 points of quality for about $0.60 per 1,000 tasks, while moving from small to medium without retrieval buys the same 13 points for $1.50. Whether that holds for your task is an empirical question; the point is to ask it, instead of assuming that "bigger model" is the first lever.
  • The front bends. From large plus retrieval to the voting configuration, quality rises four points and the cost triples, and the latency more than doubles. Whether four points are worth $49 per 1,000 tasks depends on what a failure costs, which is the last section of this chapter.
  • Error bars decide ties. Small plus retrieval (67.8%, interval 63.0 to 72.1) and medium (67.5%, 62.8 to 71.9) are indistinguishable on 400 items. The table calls medium "dominated" because it is no better and costs more, which is the right practical call, but a 0.3-point gap is a tie, not a victory. If you need to rank configurations that are close, use the paired comparison from the statistics chapter: the same items go through both, and you test the per-item differences.

Common misconception

"Pick the cheapest model that passes our quality bar." The bar is a single number on one test set, and a cheaper model can pass it overall while failing badly on the slice that matters: the rare, expensive, high-stakes questions. Check the candidate on every slice you named in error analysis (Error Analysis), and set a floor per slice, not only an average. A model that is 3 points worse overall and 25 points worse on refund disputes is not 3 points worse.

Routing and cascades

Most questions in a real workload are easy. If a small model answers 70% of them correctly, paying large-model prices for all of them is waste. A router sends each request to a model chosen by its estimated difficulty. A cascade is a router with a specific rule: ask the cheap model first, check how confident it is, and escalate to the expensive model only if the check fails. The idea was studied by Chen, Zaharia and Zou in "FrugalGPT: How to Use Large Language Models While Reducing Cost and Improving Performance" (2023), who report that a learned cascade can match the best single model's performance at a fraction of its cost (the abstract says up to 98% less on their benchmarks) or improve accuracy at the same cost. Ong et al. trained routers directly from human preference data in "RouteLLM: Learning to Route LLMs with Preference Data" (2024), and report cost reductions of over 85% on MT-Bench against always using GPT-4 while keeping 95% of its quality, with smaller savings on MMLU and GSM8K. Those are the authors' figures on their benchmarks and their model pairs, not a promise for your workload.

The next script simulates a cascade between the small plus retrieval and large plus retrieval configurations above. Each item has a difficulty; the small model has a confidence score that is higher on average when it is right, but noisy, which is how self-reported or classifier-based confidence behaves in practice (Grounding, Abstention & Confidence covers how to measure whether a confidence score is any good). It compares the cascade at four thresholds against both single models, a random router that escalates half the time, and an oracle router that knows in advance which questions the small model will get wrong, which no real router can.

import math, random

random.seed(11)
N = 2000
SMALL_COST, LARGE_COST = 0.96, 24.70      # dollars per 1,000 tasks, from the previous table (illustrative prices)
sig = lambda x: 1 / (1 + math.exp(-x))

items = []
for _ in range(N):
    d = random.gauss(0, 1)
    small_ok = random.random() < sig(0.9 - d)
    large_ok = random.random() < sig(2.3 - d)
    # the small model's self-reported confidence: higher when it is right, but noisy
    conf = min(1.0, max(0.0, random.gauss(0.72 if small_ok else 0.45, 0.18)))
    items.append((small_ok, large_ok, conf))

def run(threshold, router="confidence"):
    ok = esc = 0
    for small_ok, large_ok, conf in items:
        if router == "confidence":
            go_large = conf < threshold
        elif router == "oracle":
            go_large = not small_ok                       # unattainable: knows the answer in advance
        else:
            go_large = random.random() < threshold        # random router escalating a fixed share
        esc += go_large
        ok += large_ok if go_large else small_ok
    cost = SMALL_COST + (esc / N) * LARGE_COST            # the small model always runs first
    if router == "oracle": cost = SMALL_COST + (esc / N) * LARGE_COST
    return ok / N, esc / N, cost

print(f"{'policy':<28}{'quality':>8}{'escalated':>11}{'$/1k tasks':>12}")
print(f"{'always small':<28}{sum(i[0] for i in items)/N:>8.1%}{0:>11.0%}{SMALL_COST:>12.2f}")
for t in (0.4, 0.5, 0.6, 0.7):
    q, e, c = run(t)
    print(f"{'cascade, threshold %.1f' % t:<28}{q:>8.1%}{e:>11.0%}{c:>12.2f}")
q, e, c = run(0, "oracle");   print(f"{'oracle router (bound)':<28}{q:>8.1%}{e:>11.0%}{c:>12.2f}")
q, e, c = run(0.50, "random"); print(f"{'random router, 50% escalate':<28}{q:>8.1%}{e:>11.0%}{c:>12.2f}")
print(f"{'always large':<28}{sum(i[1] for i in items)/N:>8.1%}{1:>11.0%}{LARGE_COST:>12.2f}")
policy                       quality  escalated  $/1k tasks
always small                   68.8%         0%        0.96
cascade, threshold 0.4         77.3%        14%        4.41
cascade, threshold 0.5         82.5%        27%        7.59
cascade, threshold 0.6         86.4%        43%       11.51
cascade, threshold 0.7         88.5%        60%       15.88
oracle router (bound)          93.2%        31%        8.65
random router, 50% escalate    78.3%        52%       13.82
always large                   87.0%       100%       24.70

The cascade at a threshold of 0.6 reaches 86.4%, within the noise of always-large (87.0%) for $11.51 per 1,000 tasks against $24.70. Raising the threshold to 0.7 gives 88.5% at $15.88, apparently better than always-large, which looks too good. It is, partly: the simulation draws the two models' errors independently, so there are items the large model fails and the small one gets right, and a good router harvests them. Real models fail on many of the same hard items, so expect a smaller gain than the simulation shows. The random router is the instructive comparison: it escalates about half the requests yet reaches only 78.3%, because it escalates the wrong ones. The value of a router lies in its discrimination, and the cost saving is only as good as that.

Analogy: the family doctor and the specialist

A family doctor sees everyone, handles the common problems cheaply, and refers the cases that look unusual to a specialist whose time costs ten times more. The system works because the doctor is good at knowing what they do not know. A doctor who refers everybody wastes the specialist's time, and one who refers nobody misses the dangerous cases.

Where it breaks down: a doctor's referral is a judgement made with training in spotting danger signs. A small model's confidence is a statistic that can be badly calibrated, confidently wrong on exactly the unusual cases, and it shifts when the questions change. You must measure the router like any other model, on held-out items.

Running a router in production adds duties:

  • Evaluate the router, not only the models. Log which route each request took, and sample escalated and non-escalated traffic for review. The danger is the confident wrong answer that never escalated, so the review sample of non-escalated traffic matters most.
  • Track the escalation rate over time. A drift in the share escalated is an early warning that the questions, the prompt or the small model changed.
  • Put a floor on high-stakes categories. Some request types should always go to the strong model, whatever the confidence says. A rule is a legitimate router.
  • Budget the latency. In the figure, a quarter or more of requests wait for two models in series. If the product has a latency target, the cascade has to meet it for the escalated path, not on average.

Caching

A cache stores the result of work so that repeated work is free or cheap (Performance Engineering covers caches in general). LLM systems have three different kinds, with very different risks.

Exact response cache

Key: a hash of the full request (model, prompt, parameters). Value: the earlier answer. Safe when the request is identical and the answer does not depend on time or user. Hit rates are high for fixed prompts such as batch classification of repeated records and low for free-text chat.

Prompt (prefix) cache

The provider stores the model's internal attention state for the start of your prompt, so a later request that begins with the same text skips re-reading it. The output is still freshly generated. No quality risk; you pay for cache writes and get discounted reads.

Semantic cache

Key: an embedding of the question. Value: an earlier answer to a similar question. A hit can return a wrong answer to a question that is close in meaning but different in detail ("refund within 30 days" against "within 14 days"), and a shared cache can leak one tenant's answer to another.

Prefix caching is the one that rewards engineering attention, because long, stable prefixes are normal: a system prompt, tool definitions, a policy document, a code repository. It works because a transformer's key and value tensors for a token depend only on the tokens before it, so they can be stored and reused for any request that starts the same way (The KV Cache, and the serving-engine side in Serving Engines). The consequences for how you write prompts follow directly:

  • Put stable content first and variable content last. A timestamp, user name or request id near the top of the prompt changes every token after it and defeats the cache.
  • Matching is exact. A single changed character before the cache boundary, or reordered tool definitions, is a miss.
  • Entries expire. With a five-minute lifetime that is refreshed by each use, a prefix used once an hour is written and never read.

State of play, October 2026: how one provider prices prefix caching

Anthropic's prompt caching documentation (read 14 October 2026) states that five-minute cache writes cost 1.25 times the base input price, one-hour writes cost 2 times, and cache reads cost 0.1 times, with a lower read multiplier on some newer models. Caching is matched on the prompt in the order tools, then system, then messages, up to a marked breakpoint, requires 100% identical content before it, and has a model-dependent minimum length. Usage fields cache_creation_input_tokens and cache_read_input_tokens tell you what happened on each request. Other providers differ: some cache automatically with no write premium, some charge a storage fee, discounts differ, and all of these change. Treat the numbers as a worked example and read your provider's current page before modelling your own bill.

The script below models the economics with the multipliers above (1.25 for a five-minute write, 0.1 for a read) and an illustrative $3 and $15 per million tokens. A 6,000-token stable prefix is followed by 400 variable tokens, and the model writes 300. Requests arrive at random (a Poisson process) at different rates, and each hit refreshes the five-minute lifetime.

import random

# Illustrative prices (assumption): $3 per million input tokens, $15 per million output tokens.
P_IN, P_OUT = 3.0, 15.0
WRITE, READ = 1.25, 0.10            # multipliers on the input price (5-minute cache), per Anthropic's docs
PREFIX, VARIABLE, OUT = 6000, 400, 300
TTL = 5.0                           # minutes; each hit refreshes it

def simulate(per_minute, prefix_stable=True, n=5000, seed=3):
    rng = random.Random(seed)
    t, last, total_cached, total_plain, hits = 0.0, None, 0.0, 0.0, 0
    for _ in range(n):
        t += rng.expovariate(per_minute)                       # Poisson arrivals
        hit = prefix_stable and last is not None and t - last <= TTL
        last = t if prefix_stable else last                    # a hit or a write both refresh the entry
        pre = PREFIX * (READ if hit else WRITE)          # a miss still pays the write premium
        total_cached += (pre + VARIABLE) * P_IN / 1e6 + OUT * P_OUT / 1e6
        total_plain  += (PREFIX + VARIABLE) * P_IN / 1e6 + OUT * P_OUT / 1e6
        hits += hit
    return hits / n, total_cached / n * 1000, total_plain / n * 1000

print(f"{'requests/min':>12}{'hit rate':>10}{'$/1k cached':>13}{'$/1k plain':>12}{'saving':>8}")
for r in (0.05, 0.1, 0.2, 0.5, 2, 10):
    h, c, p = simulate(r)
    print(f"{r:>12}{h:>10.0%}{c:>13.2f}{p:>12.2f}{1 - c / p:>8.0%}")
h, c, p = simulate(10, prefix_stable=False)
print(f"\nsame 10/min, but a timestamp at the top of the prompt: hit rate {h:.0%}, ${c:.2f} vs ${p:.2f} per 1k")
extra_write = PREFIX * (WRITE - 1) * P_IN / 1e6 * 1000
saved_read = PREFIX * (1 - READ) * P_IN / 1e6 * 1000
print(f"extra cost of one write: ${extra_write:.2f} per 1k; saving from one read: ${saved_read:.2f} per 1k; reads needed to repay a write: {extra_write/saved_read:.2f}")

         0.5       92%         9.13       23.70     61%

Three results are worth remembering. At 0.05 requests a minute (one every 20 minutes) the prefix is written almost every time and caching saves nothing; it even costs slightly more. Around a request every two minutes, hit rates are high and the saving approaches its ceiling of 68%, set by the share of the bill that is the prefix. Above that rate more traffic adds nothing. And the last line shows the failure that costs real money: a timestamp at the top of the prompt made every request a miss that still paid the 25% write premium, so the "cached" system cost 19% more than not caching. One read repays a write (the extra cost of a write is $4.50 per 1,000 tasks and the saving from a read is $16.20), so even a prefix that is re-used a single time inside the lifetime is worth caching, but only if it is re-used.

Systems connection

Caching an LLM prefix is the same trade as every cache you have met: hit rate times saving against the cost of a miss and the risk of staleness or leakage. A semantic cache shared across tenants is a multi-tenancy bug waiting to happen: key it by tenant and permission scope, exactly as retrieval is filtered (Filters, Metadata & Permissions). Latency targets and the queueing effects of a slow second model are covered in Queueing Theory for Engineers and Tail Latency at Scale; the wider habit of treating efficiency as an engineering property is in Cost & Efficiency, and the design view of ML and LLM components in Designing with ML & LLMs.

Latency: the other budget

Quality-cost charts hide latency, so give it its own budget. For the large plus retrieval configuration in the table, the 5.11 seconds is 1.4 seconds of time to first token plus 3.7 seconds of generating 260 tokens. Different levers apply to each part.

  • Time to first token falls with shorter prompts, prefix caching, a smaller model and fewer sequential steps before generation starts (a reranker or a classifier in front of the model adds to it).
  • Generation time falls with fewer output tokens, a faster model, and server-side techniques such as speculative decoding that you may get from the provider without changing your code (Speculative Decoding & Other Speedups).
  • Perceived latency falls with streaming: the user starts reading after the TTFT instead of after the whole answer. It does nothing for a pipeline that must finish before it can act, such as a tool-calling loop.
  • Independent steps can run in parallel: retrieval from two indexes, a guardrail check beside the model call (Guardrail Classifiers & Content Policy), several tool calls at once. The critical path in the trace waterfall shows what is worth parallelising.

Set the latency target the same way as for any service, as a percentile of what users feel: for example "95% of answers begin streaming within 2 seconds and finish within 8". Then a configuration is not merely "slower", it either meets the objective or it does not, which turns latency from a third axis to trade into a constraint to satisfy.

Deciding what good enough costs

The Pareto front says which configurations are reasonable. It does not say which to choose, because that depends on a number the eval cannot produce: what a failure costs. A wrong answer in an internal drafting tool costs a few seconds of a person's attention. A wrong answer in a customer-facing refund flow can cost a refund, a complaint and a lost customer. A wrong answer in a medical triage tool may not be priced in dollars at all, and the right response is a human in the loop and a quality floor rather than an optimisation.

For the cases that can be priced, the calculation is short. Total cost per 1,000 tasks is the serving cost plus the number of failures times the cost of one:

total = costserving + 1,000 × (1 − quality) × costfailure

The script applies it to the five front configurations, for four assumed failure costs. The failure cost covers what you actually pay when an answer is wrong: a human reviewer's time to catch and fix it, a refund, a support contact.

# (quality, serving $ per 1,000 tasks) for the frontier configurations from the Pareto table
CONFIGS = {"small": (0.545, 0.36), "small+RAG": (0.678, 0.96), "med+RAG": (0.795, 4.86),
           "large+RAG": (0.860, 24.70), "large+vote": (0.900, 74.10)}

print(f"{'cost of one failed task':<24}" + "".join(f"{n:>12}" for n in CONFIGS) + "   best")
for fail_cost in (0.05, 0.50, 5, 50):
    totals = {n: cost + (1 - q) * 1000 * fail_cost for n, (q, cost) in CONFIGS.items()}
    best = min(totals, key=totals.get)
    print(f"{'$%.2f' % fail_cost:<24}" + "".join(f"{totals[n]:>12,.0f}" for n in CONFIGS) + f"   {best}")

$0.50                            228         162         107          95         124   large+RAG

The best configuration moves as the failure cost rises. When a failure costs five cents (nobody notices or cares), medium plus retrieval wins, and the large model costs twice as much in total. At fifty cents, large plus retrieval wins. At five dollars and above, the three-vote configuration wins, even though it is three times as expensive to serve, because it avoids enough failures. Notice that the cheapest model, which looks best on the invoice, is the worst choice once a failure costs fifty cents or more. The lesson is not that expensive models are better. It is that you cannot rank configurations on serving cost alone, and that the ranking depends on a business number someone has to estimate and own.

Turn this into a decision rule you can write down and revisit:

  1. Set constraints first. A latency objective, a quality floor on every critical slice, and any non-negotiable (a regulated category always gets the strong model plus human review).
  2. Filter to the configurations that meet them with their lower confidence bound, not their point estimate.
  3. Among those, choose the lowest total cost using your estimated failure cost, and run the sensitivity check: would the choice change if the failure cost were half or double? If it would, the decision is fragile, and that deserves a conversation, not a guess.
  4. Record the decision with the eval version, the date and the assumptions. Prices fall, models are replaced and traffic changes; the decision decays. Re-run the comparison on a schedule and whenever a provider announces a new model, using the regression suite from The Improvement Flywheel.

Keeping the numbers honest in production

A trade-off decision is only as good as the measurements that feed it, so wire the three numbers into the operating loop from the observability chapter.

  • Attach cost to the trace. Compute it from token usage and the price table at request time and store it as an attribute, along with cached-token counts. Cost per successful task, per tenant and per route then becomes a query.
  • Alert on cost per task, not total spend. Spend rises with traffic, which is good news; cost per task rising means a prompt grew, a loop got longer or the cache stopped hitting. Also set hard per-tenant and per-request budgets, so a runaway agent loop ends at a limit instead of on the invoice (Overload, Load Shedding & Metastability has the general pattern of limits that fail safe).
  • Make cost and latency part of the release gate. A prompt change that raises quality by one point and doubles tokens should be visible in the same report as the quality change, and the gate in Lab 7 can fail on any of the three.
  • Watch the router and the cache hit rate as first-class metrics, because both fail silently: quality drifts down while the invoice looks fine.

Key takeaways

  • Measure three things on the same test set: quality with an error bar, cost per successful task (not per call or per token), and latency as a percentile, split into time to first token and generation.
  • A configuration is dominated if another is at least as good on every axis. Drop those, treat gaps inside the error bars as ties, and choose among the Pareto front.
  • Look for cheap levers first: shorter prompts, fewer calls, capped outputs and retrieval settings often beat a model change. Check every candidate on the critical slices, not only the average.
  • Cascades and routers save money only as far as they discriminate hard from easy requests. Evaluate the router, sample the traffic that did not escalate, and expect the real gain to be smaller than a simulation with independent errors.
  • Prefix caching rewards stable-first prompts and steady traffic; one timestamp at the top can turn a saving into a surcharge. Semantic caches can return wrong or another tenant's answers, so key and scope them carefully.
  • "Good enough" is a cost calculation: serving cost plus failures times the cost of a failure, under a latency objective and quality floors. Record the assumptions and re-run the comparison as prices and models change.

An agent costs $0.126 per attempt and resolves 70% of tasks. A cheaper configuration costs $0.07 per attempt but resolves 35%. Which has the lower cost per successful task, and by roughly how much?

  1. The cheaper one, because $0.07 is lower than $0.126
  2. The original, at about $0.18 against $0.20
  3. They are equal, since both are paid per attempt
  4. The original, at about $0.18 against $0.35
Cost per successful task is cost per attempt divided by the success rate: 0.126 ÷ 0.70 = $0.18, and 0.07 ÷ 0.35 = $0.20. The cheaper configuration is still more expensive per resolved task, though only by about 11%. The $0.35 in the last option comes from dividing by 0.20 instead of 0.35. Comparing per-attempt prices ignores that failed attempts are paid for too.

Configuration X scores 71% (interval 66 to 76) at $2 per 1,000 tasks. Configuration Y scores 73% (interval 68 to 78) at $6 per 1,000 tasks with the same latency. Test set: 400 items. What is the best statement?

  1. Y dominates X because its quality is higher
  2. X dominates Y because it is cheaper and the quality difference is not significant
  3. Neither can be chosen without more latency data
  4. The two-point gap is inside the intervals, so run a paired comparison on the same items before paying three times as much for it
Y is better on quality by its point estimate and worse on cost, so neither dominates strictly. The intervals overlap heavily, so the gap may be noise, but overlapping intervals do not by themselves prove a tie; the paired test on per-item differences is more powerful and settles it. Calling X dominant on non-significance alone overstates what the data show, and latency is stated as equal.

A team adds cache_control to a 5,000-token system prompt that begins with "Current time: 2026-10-14 09:31:07". Traffic is steady at 20 requests a minute. Their bill goes up by about 20% instead of down. What happened?

  1. The timestamp changes the start of the prompt every second, so every request is a cache miss that still pays the write premium
  2. Twenty requests a minute is too much traffic for a cache to handle
  3. Prefix caches cost more than they save whenever the prompt is over 1,000 tokens
  4. The provider charges for reading the cache on every request even if it misses
Cache hits need identical content up to the marked point. A changing timestamp at the very start means nothing matches, so each request writes a new entry at 1.25 times the input price and never reads one. The fix is to move volatile content to the end of the prompt. Traffic volume helps hit rates, and long prompts are where caching pays most.

A cascade sends a request to the large model whenever the small model's confidence is below a threshold. Offline, it matches always-large quality at half the cost. After launch, a month later, quality slips but the escalation rate has not changed. Which is the most likely explanation?

  1. The large model has become worse
  2. Prices have changed, so the saving has vanished
  3. The small model is now confidently wrong on a new kind of request, so these never escalate
  4. The threshold is too high
A stable escalation rate with falling quality points to the small model's confidence no longer tracking its correctness for the new traffic: the failures are not being sent upward. This is why you sample the non-escalated traffic for review. A high threshold raises escalation, and a price change would show in cost, not quality.

For the front configurations in this chapter, at what failure cost does paying for the three-vote configuration start to look sensible, compared with large plus retrieval?

  1. Whenever it scores higher, regardless of price
  2. When the extra failures it avoids (four points per 1,000 tasks is 40 failures) cost more than the extra $49 of serving cost, which is about $1.24 per failure
  3. Never, because its cost is three times higher
  4. Only when latency does not matter, regardless of failure cost
The vote configuration avoids 40 failures per 1,000 tasks (90% against 86%) and costs $49.40 more, so each avoided failure must be worth more than 49.40 ÷ 40, about $1.24, to break even. That is the shape of the decision: extra serving cost against failures avoided times failure cost. It ignores the latency, which would also need to meet your objective.

A semantic cache returns a stored answer when a new question's embedding is within a similarity threshold of an earlier question's. Which risk is specific to this kind of cache, as opposed to prefix caching?

  1. It cannot reduce the cost of output tokens
  2. Hits expire after five minutes
  3. It requires the provider to keep the model's state
  4. A question close in meaning but different in a decisive detail gets the earlier question's answer, and a shared cache can return another tenant's answer
Semantic caches substitute a stored answer for a generated one, so a near-duplicate question with a different condition receives a wrong answer, and without tenant scoping the stored answer may contain another customer's data. Prefix caches only reuse computation on the prompt; the answer is still generated fresh. Saving output tokens is, in fact, something a semantic cache does well, which is why it is tempting.

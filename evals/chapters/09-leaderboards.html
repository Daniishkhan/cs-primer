Reading Leaderboards Critically

Every model announcement comes with a table, and every procurement meeting asks which model is "top". A leaderboard number is the end of a long chain of choices made by someone else. This chapter shows how crowd-voted ratings are computed, where self-reported and scaffold-dependent scores bend, how a ranking can be gamed without any dishonest score, and a list of questions to put to any number before it influences a decision.

Why this matters

Leaderboards are the cheapest evidence available, so they decide a great deal: which model a team tries first, which vendor wins a contract, which research direction gets funded. They are also where the incentives to bend evidence are strongest. The previous chapters taught you how to build your own measurements (benchmarks, contamination, agent evals). This chapter teaches the complementary skill of reading other people's. After it you will be able to read an Arena-style table with its uncertainty, spot the six places a headline score can be inflated, and use public numbers for the one job they do well: shortlisting.

A number is the end of a chain

"Model X scores 72.4 on benchmark Y" reads like a fact about the model. It is a fact about a run: a particular snapshot of the model, wrapped in a particular scaffold, given a particular prompt and sampling setup, on a particular version of the tasks, scored by a particular scorer, by a particular party on a particular day. Change any link and the number moves. Two published numbers for "the same model on the same benchmark" often differ for exactly this reason, and neither is wrong.

Self-reported scores and what they leave out

A self-reported score is one the model's developer measured and published. Developers know their model and their setup best, so these numbers are often the most careful available, and also the most favourable: the developer chooses which benchmarks to show, which prompt and settings to use, and whether to report one sample or the best of many. None of this requires dishonesty. Choosing the setting that works best for your own model is ordinary engineering, and the problem arises only when a table puts such numbers beside another party's number measured under different settings.

The usual levers, each of which can move a score by several points:

  • Number of samples. Single attempt (the "pass@1" of chapter 8), best of k attempts (pass@k), or majority vote over many samples. A table that mixes these compares effort, not ability.
  • Reasoning or thinking budget. Letting a model produce more intermediate reasoning raises scores on hard problems at a cost in tokens and latency. Two entries with different budgets are two different cost points.
  • Prompt and examples. The number of worked examples shown (few-shot), the exact instruction wording and the answer format all affect results.
  • Tools. Giving a model a code interpreter or a search tool on a question that benefits from one is a large change; whether tools were allowed must be stated.
  • Subset and version. A cleaned subset, a "verified" split or a newer release of the tasks changes the difficulty. Comparing a score on one version with a score on another is a category error.

The remedy is not suspicion but comparison under controlled settings. Prefer numbers from a party that ran every model the same way and published the configuration (evaluation frameworks such as the UK AI Security Institute's Inspect exist partly to make runs reproducible), and treat a vendor's own table as a statement of what that vendor's model can reach under its best settings, not as a ranking.

The judge and the ruler

Many popular leaderboards for open-ended tasks use an LLM judge as the scorer, and judges have biases, notably toward longer answers. The AlpacaEval benchmark, which has a model compare outputs head to head, was known to favour models that write longer outputs, so developers could raise scores by making answers more verbose. Dubois et al. (2024, "Length-Controlled AlpacaEval") proposed a regression-based correction that estimates the win rate as if both outputs had the same length, and report that the Spearman correlation with Chatbot Arena rose from 0.94 to 0.98 after the correction. The lesson is general: when a scorer has a known bias, a score without the corresponding control rewards the bias.

Scaffolds: you are ranking systems, not models

On an agent benchmark the thing evaluated is the model and the code around it: the prompts, the tools, the loop, the retry logic. Chapter 8 introduced this as the agent harness. For a leaderboard it means a score belongs to a (model, scaffold) pair. Anthropic's engineering team gives a vivid example in its post on agent evals: a run scored 42% on CORE-Bench, and reached 95% after the team fixed bugs in the grading and used a less constrained scaffold, with the same underlying model. A leaderboard that lists only the model name is hiding the variable that moved the score most.

When you read an agent result, find out: which tools were available; how many steps, how much time and how many tokens were allowed; whether the harness retried failures or used multiple attempts; and whether the scaffold was tuned on the benchmark's own tasks (a form of leakage, chapter 7). A "same scaffold for every model" leaderboard answers one question (which model is best in this fixed setting) and a "best scaffold for each submission" leaderboard answers another (what is the best system anyone can build). Both are legitimate; confusing them is not.

Arena ratings: how crowd votes become a ranking

For open-ended chat quality there is rarely a ground-truth answer, so the dominant public evaluation is the Arena approach introduced by Chiang et al. (2024, "Chatbot Arena: An Open Platform for Evaluating LLMs by Human Preference"): a person submits a prompt, receives answers from two anonymous models, and votes for the better one (or a tie). Votes accumulate into a ranking. As of January 2024 the paper reports about 240,000 votes from over 90,000 users across more than 50 models, which is roughly 8,000 votes per model.

From votes to ratings

The mathematical model is the Bradley-Terry model. Each model i gets a strength si, and the probability that i beats j in one vote is the logistic function of the difference: P(i beats j) = 1 / (1 + e−(si − sj)). Fitting the strengths means choosing the values that make the observed votes most likely. The Arena paper describes switching from the online Elo update used earlier to a Bradley-Terry fit by (reweighted) maximum likelihood, because they consider it better suited to statistical estimation. Unlike a running Elo update, the fit treats all votes as one pool, so the order of the votes does not matter, and it supports proper confidence intervals. Published scores are rescaled to look like Elo ratings, with a difference of 400 points meaning a tenfold odds ratio.

The script below simulates the process. Six models have known true strengths. Three thousand votes are cast between random pairs, the Bradley-Terry strengths are fitted with the standard iterative (minorise-maximise) update, and 200 bootstrap resamples of the votes give a 95% interval and a range of ranks for each model. All strengths and the vote counts are illustrative.

import random, math

rng = random.Random(11)
models = ["M-A", "M-B", "M-C", "M-D", "M-E", "M-F"]
true = [0.30, 0.22, 0.12, 0.05, 0.0, -0.20]     # true strength on the logit scale (illustrative)
n_votes = 3000

def p_win(i, j): return 1 / (1 + math.exp(-(true[i] - true[j])))

votes = []   # (winner, loser); ties dropped for simplicity
for _ in range(n_votes):
    i, j = rng.sample(range(len(models)), 2)
    votes.append((i, j) if rng.random() < p_win(i, j) else (j, i))

def fit_bt(votes, m, iters=200):
    """Bradley-Terry strengths by the MM algorithm; returns logit-scale scores centred at 0."""
    wins = [0] * m
    games = {}                                  # games[(i, j)] = number of battles between i and j
    for a, b in votes:
        wins[a] += 1
        games[(a, b)] = games.get((a, b), 0) + 1
        games[(b, a)] = games.get((b, a), 0) + 1
    w = [1.0] * m
    for _ in range(iters):
        w = [wins[i] / sum(games.get((i, j), 0) / (w[i] + w[j]) for j in range(m) if j != i) for i in range(m)]
        g = math.exp(sum(math.log(x) for x in w) / m)
        w = [x / g for x in w]
    return [math.log(x) for x in w]

def to_arena(scores):   # Elo-like display scale: 400/ln(10) per logit, centred at 1000
    return [1000 + 400 / math.log(10) * s for s in scores]

base = to_arena(fit_bt(votes, len(models)))
boots = []
for b in range(200):
    rs = random.Random(1000 + b)
    sample = [rs.choice(votes) for _ in votes]
    boots.append(to_arena(fit_bt(sample, len(models))))

print(f"{n_votes} votes, {len(models)} models (~{n_votes*2//len(models)} appearances each)")
print("model  true  rating  95% interval      rank range (200 bootstraps)")
for i, m in enumerate(models):
    col = sorted(x[i] for x in boots)
    lo, hi = col[5], col[194]
    ranks = [1 + sum(1 for j in range(len(models)) if x[j] > x[i]) for x in boots]
    print(f"{m}   {true[i]:5.2f}  {base[i]:6.0f}  {lo:6.0f} to {hi:5.0f}   {min(ranks)} to {max(ranks)}")

Three lessons follow. First, ratings come with intervals, and models whose intervals overlap are statistically hard to separate; a leaderboard that prints only a rank column discards the information you need. Second, the gap between ranks is not uniform: ranks 1 and 2 may differ by one rating point while ranks 3 and 4 differ by forty. Third, the intervals shrink slowly (as one over the square root of the number of votes), so a newly added model has wide intervals and sits at an unreliable position until it accumulates battles. These are the same error-bar ideas as chapter 4, applied to preference data.

What a vote measures

A rating summarises how crowd voters prefer one answer to another on the prompts the crowd chose. That is a real quantity, and not the one you may need. Four caveats:

  • The prompts are not yours. The Arena's traffic is whatever its users type: much open chat, coding and creative requests, fewer long domain documents or tool-using workflows. A model that is best at the crowd's prompts need not be best at your permit questions.
  • Voters miss errors. The Arena paper compares crowd votes with expert labels and reports agreement of 72% to 83%, against 79% to 90% between experts themselves; the authors attribute the gap mainly to crowd users failing to notice factual errors. Confident, fluent wrong answers win some votes.
  • Style leaks into preference. Voters like longer answers and tidy formatting. The LMSYS team added style control: extra terms in the regression for the difference in answer length and the counts of markdown headers, bold elements and lists, so a model's rating reflects its strength net of style. They report that length was the dominant style factor and that applying the controls moved some models noticeably: in their August 2024 analysis one model fell from sixth to eighteenth when length and markdown were both controlled, while others rose. They also note the analysis is observational, since length and quality can be genuinely related.
  • Voting is an attack surface. Any open voting system invites bots and coordinated voting; see Abuse, Bots & Denial of Service. Operators mitigate this, but a rating derived from open voting is a different kind of evidence from an audited test set.

Common misconception

"The model at rank 1 is the best model." Rank 1 means the point estimate is highest, in a particular view of a particular crowd's preferences, with an interval that usually overlaps its neighbours. It does not mean best for coding, best for your domain, best in your language or best for your price. Read the interval, the category and the date, and then test on your own data.

How a leaderboard can be gamed without lying

Singh et al. (2025, "The Leaderboard Illusion") studied the Arena as a system and argue that some structural features distort it, even when every vote counts honestly. The case study The Leaderboard Illusion goes through the evidence; the mechanisms matter here. The authors report that some providers privately test many model variants and publish only the best, naming 27 private variants tested by one developer in the run-up to a release. They also report that proprietary models are sampled for battles at higher rates and have fewer models removed than open-weight ones, so a few providers accumulate far more data: the paper estimates that Google and OpenAI received about 19.2% and 20.4% of all Arena data, while 83 open-weight models together received about 29.7%. Finally they estimate that access to even a limited amount of extra Arena data could yield relative gains of up to 112% on the Arena's own distribution, which the authors read as a sign of overfitting to Arena-specific dynamics rather than general quality. These are the paper's claims and estimates, which you should read with the same care as any other number; the point for this chapter is the mechanism.

The mechanism: best of N is biased upward

Why does private testing matter? Every measured rating contains noise. If you measure ten variants of equal true quality, one of them will, by chance, look best, and publishing that one reports the maximum of ten noisy numbers. This is the winner's curse of chapter 4 applied to a leaderboard. The script below makes it concrete: every variant is truly identical to the public model, each is rated from 2,000 battles, and we record what is published as the number of private variants grows.

import random, math
rng = random.Random(3)
TRUE = 0.0            # every variant is exactly as good as the public model (logit scale)
N_VOTES = 2000        # battles used to rate one variant
def rating_of_one_variant():
    p = 1 / (1 + math.exp(-TRUE))              # win rate against the field is 50%
    wins = sum(rng.random() < p for _ in range(N_VOTES))
    return 400 / math.log(10) * math.log(wins / (N_VOTES - wins))   # rating relative to the field
print("variants tested privately -> rating you would publish (true value 0)")
for n in (1, 3, 10, 27):
    pubs = [max(rating_of_one_variant() for _ in range(n)) for _ in range(400)]
    print(f"  {n:2d} variants: mean published {sum(pubs)/len(pubs):+5.1f} points")

The cure is procedural: pre-register which variant is being rated, publish all variants tested, or evaluate the final released model on fresh battles. For a reader the symptom to look for is a model that appears on a leaderboard with a name or version string that is not available to buy, or whose leaderboard behaviour differs from the released product.

Analogy: the athlete who may re-run the heat

Picture a race where each athlete may run ten private heats before the official one and enter only their best time. Every time on the record was really run, yet the record is faster than anyone would run on a single try. A leaderboard with private variants is the same arrangement: a fair race measures one attempt, declared in advance.

Where it breaks down: an athlete's best heat reflects luck and training, and races do not usually involve a rater whose style preferences can be tuned. A model variant can be tuned directly toward what the voters like, which is an additional route to a higher number that has nothing to do with chance.

Goodhart, saturation and decay

"When a measure becomes a target, it ceases to be a good measure" (Goodhart's law, in its common paraphrase) describes what happens to any popular leaderboard. Once a number decides funding and sales, training choices tilt toward it: data resembling the benchmark leaks into training (chapter 7), reward models learn the voters' tastes (Reward Models & Reward Hacking), and top scores bunch against the ceiling so that differences fall inside the noise. Benchmarks therefore have lifecycles, and a score on an old one says less each year. A reasonable habit is to ask how long the benchmark has existed, whether the top of its leaderboard has saturated, and whether a harder successor exists.

State of play, October 2026

The Arena (formerly LMSYS Chatbot Arena, now run as LMArena) remains the most-cited crowd-voted leaderboard. Secondary reviews I could read describe its default text view as using style control and report that the top ten models sit within a few tens of rating points; I did not verify these on the site, and positions change weekly. Before you quote any Arena number, record which category (overall, coding, hard prompts and so on), whether style control was on, the date, and the interval. Several benchmarks that were standard in 2024 are now retired or saturated, and chapter 7 and the SWE-bench Verified case show one such retirement.

Questions to ask of any number

Turn the chapter into a checklist. For a score you intend to rely on, you should be able to answer these, and the absence of an answer is information.

QuestionWhat a good answer looks like
What exactly is measured?A task description you can read, with a scoring rule, not just a name.
Who ran it, and for whom?A party with no stake, or a vendor figure labelled as such, with the configuration published.
Which model, which version, which date?An identifiable snapshot you can actually obtain.
What scaffold, tools and budget?Stated, and the same for every model compared.
How many attempts and what aggregation?pass@1 or clearly labelled best-of-k or voting; trial count for agents.
How uncertain is it?An interval or standard error; overlap acknowledged; ties not ranked.
Could the test be in the training data?A private or held-out split, a contamination check, a recent creation date.
Who scored it, and with what bias?A validated judge or exact checker; known biases controlled (length, format).
What did it cost?Tokens, price and latency reported beside the score.
Does it resemble my task?Similar inputs, language, difficulty and stakes; otherwise treat as a shortlist signal only.

What leaderboards are good for

None of this makes public numbers useless. They are excellent at eliminating: a model far below the field on every relevant measure is unlikely to be your best choice, and the cost of that check is nothing. They are good at orientation: which families of models exist, roughly how capability and price relate, which benchmarks are saturated. They are poor at deciding. The workable routine: use public numbers to build a shortlist of three or four candidates, then run those candidates on your own benchmark (chapter 6), with your own error bars, at your own cost and latency targets, and make the decision there.

Systems connection

Comparing two systems from noisy measurements is the same problem as an online A/B test: decide the metric and the sample size in advance, report an interval and be wary of choosing the winner after seeing results. Open voting that feeds a public ranking has the abuse profile of any public endpoint with an incentive attached.

Key takeaways

  • A published score is a property of a run: model snapshot, scaffold, prompt and sampling, task version, scorer and who ran it. Change any of them and the number moves.
  • Self-reported scores show what a developer's model reaches under its best settings; compare models only when every setting is held fixed and stated.
  • On agent benchmarks the score belongs to a model and scaffold pair; ask about tools, budgets and retries.
  • Arena-style ratings come from a Bradley-Terry fit to pairwise votes. Read the interval, not the rank: neighbouring models are often statistically tied.
  • Votes reflect the crowd's prompts, miss factual errors and favour length and formatting; style control corrects part of that.
  • Publishing the best of many private variants inflates a rating without any dishonest vote. Ask whether the rated model is the one you can buy.
  • Use public leaderboards to build a shortlist, and decide on your own benchmark.

Check your understanding

Two tables report different scores for the same model on the same coding benchmark: 71% from the developer and 58% from a third-party leaderboard. What is the most likely explanation, and the right response?

  1. One of the two parties is lying; trust the third party.
  2. The benchmark is invalid; discard both numbers.
  3. Different scaffolds, sampling or budgets produced different runs; compare configurations and prefer a controlled comparison across models.
  4. The developer's number is always inflated by about 13 points, so subtract it.
A score belongs to a run, and tools, step limits, number of attempts and prompts commonly move agent and coding scores by many points. Neither number need be false. Dishonesty (option 1) is possible but not the default explanation, and no fixed correction (option 4) exists. The benchmark can be perfectly valid while the two runs differ.

An Arena-style table lists models A, B and C with ratings 1043, 1043 and 1016, and 95% intervals that overlap heavily. Which reading is best supported?

  1. The data cannot separate the three; each could plausibly hold any of the top three ranks.
  2. A is first, B is second and C is third, because ranks are computed from the ratings.
  3. A and B are exactly equal, so one of them must be a duplicate entry.
  4. C is clearly worse because its rating is lower.
With overlapping intervals the ordering is not statistically established, and bootstrapped rank ranges show each model spanning several positions. Equal ratings (option 3) can occur by chance and are not evidence of duplication. A lower point estimate (option 4) is not a clear difference when the intervals overlap.

A provider tests 20 private variants of a model on a public voting leaderboard and publishes only the highest-rated one. If all variants are in fact equally good, what happens to the published rating on average?

  1. It equals the true rating, because each vote is honest.
  2. It is lower than the true rating, because the other variants were discarded.
  3. It is unchanged but its confidence interval widens.
  4. It is above the true rating, because the maximum of several noisy estimates is biased upward.
Selection of the best noisy measurement produces the winner's curse: the published number reflects luck as well as quality, and the bias grows with the number of variants (the simulation shows it rising from about 0 to about 16 points). Honest votes do not prevent it, because the bias arises from which result is chosen for publication.

You must choose a model for a contract-review assistant. Which use of public leaderboards is most defensible?

  1. Pick the model ranked first in the overall chat category and deploy it.
  2. Use the leaderboards to shortlist a few candidates, then evaluate them on your own contract benchmark with error bars and costs.
  3. Ignore leaderboards entirely, because they are all unreliable.
  4. Choose whichever vendor's self-reported table shows the highest average over many benchmarks.
Public numbers are cheap and good for elimination and orientation, but they are measured on other people's tasks and settings. A domain benchmark decides. Deploying on rank alone (option 1) or on a vendor's average (option 4) trusts evidence that is not about your task; ignoring all public evidence (option 3) wastes a free filter.

Why does style control matter for crowd-voted rankings?

  1. It removes all votes cast on prompts that ask for formatted answers.
  2. It guarantees that each model is rated on the same number of battles.
  3. It adjusts for voters' preference for longer, more formatted answers, so ratings reflect substance more than presentation.
  4. It replaces human voters with an LLM judge to avoid bias.
Style control adds length and markdown features to the Bradley-Terry regression so that the model's strength is estimated net of style effects. It does not delete votes, equalise sampling or replace voters. It is also observational: if length and quality are truly related, some real quality can be attributed to style.

An agent benchmark's leaderboard lists only model names. Which additional information most affects whether two entries are comparable?

  1. The date the model was announced.
  2. The scaffold: tools, step and time limits, retries and number of attempts.
  3. The country of the developer.
  4. The number of parameters, if disclosed.
On agent tasks the scaffold can change scores by tens of points with the model held fixed, so the system, not just the model, is what was ranked. The announcement date and parameter count say little about how the run was configured, and the developer's country says nothing about it.

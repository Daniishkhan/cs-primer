AI Incident Response

Sooner or later an AI system will say or do something it should not, in front of real users. This chapter covers what counts as an AI incident, how you notice one, the containment levers to build before you need them, what to preserve for the investigation, who has to be told, and how the lesson gets back into your evals.

Why this matters

Evals and guardrails lower the odds of a bad outcome; they never make it zero. What separates a bad afternoon from a bad quarter is whether the team can stop the damage in minutes, reconstruct what happened from evidence it kept, and make sure it cannot happen the same way again. AI incidents differ from outages in ways that catch teams out: nothing crashes, the system is confident, the harm can be a sentence, and the cause may be a model change you did not make. After this chapter you can write the containment ladder, the evidence list and the notification checklist for a system you run.

What counts as an AI incident

An AI incident is an event in which an AI system's behaviour causes, or nearly causes, harm or a serious breach of expectations: to users, to third parties, to data, to money or to trust. The ordinary definition of an outage (the service is down or slow) is a subset. The harder cases are those in which every dashboard from Alerting & On-Call is green and the system is working exactly as built.

Two properties make these different from the incidents in Incident Response. First, the detection signal is a judgement: someone, or some evaluator, has to decide that an answer was wrong. Second, the cause is often outside your code: a provider swapped a model snapshot, a document in the index was edited, a user found a new jailbreak. Your runbook has to cover causes you did not deploy.

Severity: by harm, not by error rate

Rank an incident by what it did, not by how often the model errs. A 0.1% rate of wrong answers is routine for a drafting assistant and unacceptable for one that approves loans. Ask four questions: who is affected (internal staff, customers, the public, vulnerable people), can it be undone (a wrong answer can be corrected, a sent email or a deleted record cannot), how far has it spread (one conversation, one tenant, everyone), and is regulated or personal data involved. Write the levels and their response times down in advance, so the on-call engineer is not arguing about them at 3 a.m.

Detection: where the signal comes from

You will rarely get a clean alarm. Combine several sources, each with a different delay and false-alarm rate.

  • Online evaluators on sampled traffic. Judges and rules run on a slice of live traces (Tracing & Observability for LLM Systems) and feed a rate you can alert on.
  • Guardrail trips. A jump in blocked outputs or PII-filter hits (Guardrail Classifiers & Content Policy) is a free canary.
  • Behavioural metrics. Unusual tool-call patterns, loop length, cost per task, refusals, answer length, escalations to humans, thumbs-down rates.
  • Change events. A deployment, a prompt edit, a new index snapshot, a provider notice. Most incidents begin at a change, so correlate alerts with a change log (Configuration & Infrastructure as Code).
  • People. Support tickets, a screenshot on social media, a red team finding (Red Teaming). Give users and staff an easy way to report a bad output and make sure a report reaches on-call.

Containment: the ladder you build in advance

The central rule from the reliability course applies unchanged: mitigate before you diagnose. Do the safe, reversible thing that stops the harm, then investigate with the pressure off. For AI systems, the safe things are containment levers: switches you built beforehand that reduce what the system can do. Order them by how much capability you give up.

The script below shows the idea with a small simulation. An online evaluator flags bad responses; a detector trips when 5 of the last 40 verdicts are bad; each trip climbs one rung; and after every rung the detector waits for a fresh window of 40 requests before judging whether it worked. Two incidents start at request 200: one caused by a bad prompt version, one by a poisoned document in the retrieval index. The evaluator's verdicts are random draws from fixed rates, so this is a model of the process and not a measurement.

import random
from collections import deque

LADDER = ["roll back prompt to v1", "turn retrieval off", "kill switch: hand off to humans"]
WINDOW, TRIP = 40, 5                      # trip when 5 of the last 40 verdicts are bad (12.5%)

def run(scenario, seed=5, onset=200, total=600):
    rng = random.Random(seed)
    state = {"prompt": "v2", "retrieval": True, "killed": False}
    window, rung, since_action, bad_served, log = deque(maxlen=WINDOW), 0, 0, 0, []
    for i in range(total):
        if i < onset:
            p = 0.01
        elif scenario == "bad prompt":
            p = 0.12 if state["prompt"] == "v2" else 0.01
        else:                                             # a poisoned document in the index
            p = 0.12 if state["retrieval"] else 0.01
        if state["killed"]:
            p = 0.0                                       # humans answer; nothing automated is served
        bad = rng.random() < p                            # verdict of the online evaluator
        if i >= onset and bad: bad_served += 1
        window.append(bad); since_action += 1
        if len(window) == WINDOW and sum(window) >= TRIP and since_action >= WINDOW and rung < len(LADDER):
            log.append(f"  request {i:>3}: detector trips ({sum(window)}/{WINDOW} bad) -> {LADDER[rung]}")
            if rung == 0: state["prompt"] = "v1"
            if rung == 1: state["retrieval"] = False
            if rung == 2: state["killed"] = True
            rung += 1; window.clear(); since_action = 0
    return bad_served, log

for scenario in ("bad prompt", "poisoned document"):
    served, log = run(scenario)
    print(f"incident: {scenario} (starts at request 200)")
    print("\n".join(log))
    print(f"  bad responses served after onset: {served}\n")

  bad responses served after onset: 8

  request 222: detector trips (5/40 bad) -> roll back prompt to v1
  request 347: detector trips (5/40 bad) -> turn retrieval off
  bad responses served after onset: 19

The bad prompt is fixed by the first rung, after 8 bad responses. The poisoned document is not: rolling back the prompt changes nothing, the detector trips again after another window, and only the second rung (retrieval off) stops it. That cost 11 more bad responses (19 in all) and illustrates the practical point. Rolling back the last change is the right first move because most incidents begin at a change, but a rung that does not clear the signal tells you something about the cause, so move down the ladder instead of waiting. In a real system the second rung would have been chosen by a person reading the trace, not by a counter.

Containment has limits you should know in advance:

  • Rollback does not undo effects. Emails sent, tickets closed and records changed stay that way. Pair write tools with idempotency, audit logs and compensating actions (Logs & Exactly-Once, Durable Execution for Agents).
  • You can only roll back what you pinned. If you call a floating model alias, the provider can change behaviour under you and you have nothing to roll back to. Pin the model snapshot where the provider allows it, and record it on every trace.
  • Bad state persists. Cached answers (the previous chapter), saved memories (Memory) and indexed documents outlive a prompt rollback. Know how to purge each.
  • An injection incident may mean credentials were exposed. Rotate keys and tokens that the agent could read (Detection & Security Incidents).

Preserve evidence, then investigate

Before changing anything further, freeze what you will need: the traces for the window (exempt them from sampling and retention deletion), the versions of the prompt, model, tools and index that were live, the change log, and the evaluator verdicts. Investigation then follows the error-analysis method from Error Analysis: read the traces of affected conversations, find the first thing that went wrong in each, and group them. Replaying a trace against the stored versions often reproduces the failure; because model output is not deterministic, replay a few times and report how often it recurs. Two cautions. Preserved traces contain personal data, so limit access and set a review date to delete them (Privacy & Data Handling for AI). And for systems under regulation, do not alter the system in ways that destroy the evidence before the right people have been told, which is a legal duty for some high-risk systems under the EU AI Act (Governance Frameworks & Regulation).

Communicate and notify

Decide in advance who needs to hear what, and when. Internally, a single incident lead and a status channel, as in Incident Response. Externally, three groups:

  • Affected users and customers. Plain language, what happened, what you did, what they should do. Your contracts may set deadlines.
  • Your vendors and customers' security contacts, when the cause or the effect crosses the boundary.
  • Regulators, where a duty exists. If personal data was exposed, the GDPR requires notifying the supervisory authority without undue delay and, where feasible, within 72 hours of becoming aware of a breach likely to put people at risk (Article 33). For high-risk AI systems, the EU AI Act's Article 73 sets reporting windows for serious incidents of at most 15 days, 10 days where a person died and 2 days for a widespread infringement, counted from becoming aware (the article's text as read on the AI Act Explorer in October 2026). Those obligations apply on the dates given in the governance chapter, and sector rules in finance, health and public services add their own.

Learn: close the loop into the evals

A blameless review (Postmortems & Learning from Incidents) asks what in the system allowed this, not who erred. For AI systems add three questions. Why did our evals not catch it? Either the failure was not in the test set, the judge missed it, or it appeared only in production traffic. What case do we add? Every incident should yield at least one regression case from the real trace, and often a new online evaluator, so the gate in The Improvement Flywheel would stop a repeat. Which lever was missing or slow? If on-call needed a deploy to switch something off, building that switch is an action item. Track actions to completion; a review that produces a document and no change has not learned anything.

Common misconception

"If it goes wrong we will roll back." Rollback is one lever, and it works only for changes you made, to things you versioned, with effects you can undo. It does not recall the answer a customer already acted on, the record an agent already deleted or the personal data already sent to a third party. Plan for the effects, not only the cause.

Key takeaways

  • An AI incident is behaviour that causes or nearly causes harm; often nothing is down and the system is confident. Rank severity by who is hurt, reversibility, spread and data involved.
  • Detect by combining online evaluators, guardrail trips, behavioural metrics, change events and people, and correlate with a change log.
  • Mitigate before diagnosing, using a ladder of levers built beforehand: roll back, tighten guardrails, remove capabilities, require approval, kill switch.
  • Rollback does not undo effects, cannot restore what was not pinned, and leaves caches, memories and indexes unchanged.
  • Freeze traces and versions before further changes, find the first failure in each trace, and know your notification duties (GDPR breaches, AI Act serious incidents, contracts).
  • Every incident should leave a regression case, a better evaluator and a faster lever.

Check your understanding

A support assistant's thumbs-down rate doubles an hour after a prompt edit, while error rates and latency are normal. What is the best first action?

  1. Start reading traces until the cause is found, then decide what to do
  2. Wait for another hour to see whether it is noise
  3. Roll the prompt back to the previous version, then investigate with the traces preserved
  4. Turn off the whole assistant
Mitigate before diagnosing: the change is a recent, reversible suspect, and rolling it back is the lowest rung of the ladder. Waiting extends harm; the kill switch gives up more capability than the evidence justifies. Reading traces comes next, not first.

After rolling back a prompt, the bad-answer rate does not fall. What does this most strongly suggest?

  1. The cause is something other than the prompt, such as a document in the index, a provider model change or a tool, so move to a different lever
  2. The rollback failed and should be repeated
  3. The evaluator is broken
  4. The incident is over
A lever that does not clear the signal is evidence about the cause. In the chapter's simulation the poisoned document was untouched by the prompt rollback. The evaluator might be faulty too, but check that after trying the next lever, not before.

An agent was injected and sent a customer's records to an outside address. Which step is easiest to forget, and why does it matter?

  1. Rolling back the prompt, because it removes the attack
  2. Updating the status page
  3. Writing the postmortem
  4. Rotating credentials the agent could read and checking notification duties, because rollback does not recall data or secrets already exposed
Rollback stops the next attack but cannot recall data already sent or secrets the agent could access, and personal data exposure may start a regulatory clock such as the GDPR's 72 hours. The other steps matter but are rarely forgotten.

A postmortem concludes: "the model hallucinated; action item: be more careful." What is missing?

  1. Nothing; hallucination is an accepted cause
  2. Concrete changes: a regression case from the trace, a new evaluator or guardrail, and a faster lever, each with an owner
  3. A named engineer to be responsible
  4. A promise that it will not recur
An AI postmortem should turn the failure into tests and controls and ask why the existing evals missed it. Naming a person to blame fails the blameless principle, and no honest system can promise it will never recur.

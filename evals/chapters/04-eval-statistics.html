Statistics for Evals

An eval score is an estimate from a sample of questions, not a fact about a model. This chapter shows how to put an honest error bar on it, why comparing two systems on the same questions is both stricter and cheaper than comparing their headline numbers, how related questions quietly shrink your sample, and how many questions you need before a one-point improvement can be believed.

Why this matters

Every decision in this course ends in a comparison: is the new prompt better, did the model upgrade regress, can we ship? Chapters 1 to 3 gave you traces, harnesses and judges that turn behaviour into pass or fail. This chapter says what those numbers can and cannot tell you. Teams routinely ship on a "+2 points" that is smaller than the noise, or discard a real improvement because the run was unlucky. After this chapter you will attach a standard error to every score, choose between paired and unpaired comparisons, spot clustered questions, and work out how large an eval must be before you build it. The code builds on the statistics in Statistics for Experiments; here we apply it to the particular shape of LLM evals.

A score is an estimate

Suppose you run a support assistant against 100 test questions and it answers 73 correctly. The report says "73 percent". Now imagine a colleague writes a different 100 questions about the same product, in the same style, and runs the same assistant. Would they also get exactly 73? Almost certainly not: they might get 68 or 78, because some questions happen to be easier for this model than others and your set contained a particular mix.

That picture is the foundation of this chapter. Evan Miller, in "Adding Error Bars to Evals: A Statistical Approach to Language Model Evaluations" (2024), puts it in one sentence: evaluations are experiments. The questions you wrote are treated as a sample from a much larger, hypothetical super-population of all the questions that could have been asked about the skill you care about. The "true" score is the average over that whole population. The number you computed is an estimate of it, and like any estimate it has a standard error: a measure of how much the estimate would vary if you repeated the sampling.

For a score that is 1 for a correct answer and 0 for a wrong one (a Bernoulli variable), the standard error of the average has a short formula. With n questions and observed accuracy p:

SE = √( p (1 − p) / n )

For 73 percent on 100 questions that is √(0.73 × 0.27 / 100) = 4.4 points. A 95% confidence interval is the estimate plus or minus 1.96 standard errors, here 73 ± 8.7, or 64 to 82 percent. The usual reading is: if you repeated the whole procedure many times, about 95 percent of intervals built this way would contain the true score. It is not a statement that the true score has a 95 percent chance of lying in this particular interval, though for planning purposes you can treat it as "the plausible range".

import math

def se_bernoulli(p, n):
    return math.sqrt(p * (1 - p) / n)

def wilson(k, n, z=1.96):
    p = k / n
    centre = (p + z * z / (2 * n)) / (1 + z * z / n)
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / (1 + z * z / n)
    return centre - half, centre + half

print("accuracy 73%: how the 95% interval narrows with n")
for n in (50, 100, 500, 1000, 5000):
    se = se_bernoulli(0.73, n)
    print(f"  n={n:5d}  SE={se:6.2%}  95% CI = {0.73-1.96*se:6.1%} to {0.73+1.96*se:6.1%}")

print("\nsmall n and extreme scores: normal interval versus Wilson")
for k, n in ((20, 20), (3, 50), (45, 50)):
    p = k / n
    se = se_bernoulli(p, n)
    lo, hi = wilson(k, n)
    print(f"  {k}/{n}: normal {max(0,p-1.96*se):5.1%} to {min(1,p+1.96*se):5.1%}   Wilson {lo:5.1%} to {hi:5.1%}")

Read the first table as a rule of thumb. At 100 questions the interval is 17 points wide. At 1,000 it is still 5.6 points wide. Because the standard error shrinks with the square root of n, you need four times the questions to halve the error bar. A set of 50 questions cannot tell a 73 percent system from an 80 percent one. A set of 5,000 can.

Small samples and scores near the edges

The formula above assumes the score is roughly bell-shaped when averaged, which is fine for hundreds of questions and mid-range accuracy. It breaks at the edges. If a system gets 20 of 20 right, the formula gives a standard error of zero and an interval of exactly 100 percent, which is absurd: twenty lucky answers do not prove perfection. The Wilson interval (Wilson, 1927) is a better choice for small n or for accuracies near 0 or 100 percent; the second table above shows it giving 83.9 to 100 percent for 20 of 20. For the particular case of zero failures there is a handy shortcut, the rule of three: after n trials with no failures, the 95 percent upper bound on the failure rate is about 3 / n. Twenty clean runs only rules out a failure rate above about 15 percent. Safety evals, where you want to show that a rare bad behaviour is rare, live in this regime: "we found no failures in 200 tests" supports "below about 1.5 percent", not "zero".

Where the noise comes from

When you run an eval there are really two different sources of randomness, and they behave differently.

  • Which questions you drew. Each question has a true pass rate for this model, its conditional mean xi: a question the model nearly always gets right has x near 1, and a trick question has x near 0. Different draws of questions give different averages of those pass rates.
  • How the model happened to answer each question this time. Even for a fixed question the model's output is random if you sample with temperature above zero, and it can vary a little even at temperature zero because of batching and hardware differences in hosted services. The spread of a single question's score around its own pass rate is the conditional variance σi2.

The law of total variance says these add. Writing Var(x) for how much question pass rates differ from one another and E[σ2] for the average answer-level noise, the variance of the eval average is

Var(μ̂) = ( Var(x) + E[σ2] ) / n

Resampling: answer each question K times

If you answer each question K times and score the mean of the K answers, the answer-level noise is divided by K. The question-level noise is untouched. Miller works an example with question difficulty spread uniformly from 0 to 1 and binary scores: Var(x) = 1/12 and E[σ2] = 1/6, so the variance with K samples is the one-sample variance times (1 + 2/K) / 3. The best you can ever do by resampling is to remove two thirds of the variance. The simulation below checks that claim by running thousands of independent evals.

import random, statistics
random.seed(11)

def run_eval(n, K):
    """One eval of n questions; each question has difficulty x ~ U[0,1] (chance of a correct sample).
    Each question is answered K times and its score is the mean of the K samples."""
    total = 0.0
    for _ in range(n):
        x = random.random()
        total += sum(random.random() < x for _ in range(K)) / K
    return total / n

n, reps = 200, 3000
base = None
print(f"{'K':>4} {'SE of score':>12} {'variance vs K=1':>16} {'theory (1+2/K)/3':>17}")
for K in (1, 2, 4, 8, 32):
    scores = [run_eval(n, K) for _ in range(reps)]
    var = statistics.pvariance(scores)
    base = base or var
    print(f"{K:4d} {var**0.5:12.2%} {var/base:16.2f} {(1+2/K)/3:17.2f}")
   K  SE of score  variance vs K=1  theory (1+2/K)/3
   1        3.58%             1.00              1.00
   2        2.91%             0.66              0.67
   4        2.43%             0.46              0.50
   8        2.30%             0.41              0.42
  32        2.09%             0.34              0.35

Most of the gain arrives by K = 4 to 8. After that, extra runs mostly cost money. The practical rule is to pick K so that E[σ2]/K is well below Var(x), and then spend any remaining budget on more questions. One caution: pool the K answers into a per-question average before computing the standard error. Treating all K n answers as independent observations would claim the precision of K n questions while having only n.

Do not lower the temperature to make the noise go away

It is tempting to set the sampling temperature to zero so every run gives the same answer. Miller's advice is blunt: do not touch the thermostat, unless you actually want to study the model at that temperature. Greedy decoding turns each question's smooth pass rate into a hard 0 or 1 (the model either always gets it or never does). In his example, difficulty uniform on 0 to 1 at temperature 1 has Var(x) = 1/12, but rounding to 0 or 1 at temperature 0 raises it to 1/4, three times as large. You removed the answer noise and made the question noise worse, and the score is now a measurement of a different behaviour from the one users see. The alternatives that do not distort are resampling, and, for multiple-choice tasks where the answer is the first token, scoring the probability the model gives to the correct option, which removes answer noise entirely.

Common misconception

"I run at temperature 0, so my eval is deterministic and needs no error bars." Determinism only removes the second kind of noise, and not always even that. The bigger issue is the first kind: your questions are a sample. A model that scores 81 percent on a fixed set of 200 questions, run twice with identical output, still has a standard error of 2.8 points around the quantity you care about, which is how it would do on the next 200 questions from the same source. Repeatable is not the same as precise.

Related questions are not independent

The standard error formula assumes each question is an independent draw. Many evals break that assumption without anyone noticing.

  • Reading-comprehension sets ask five questions about each passage. If the model misreads a passage, it tends to miss all five.
  • A translated set (the same question in 20 languages) contains 20 copies of one idea.
  • A synthetic set generated by asking a model for "ten variations of each seed question" contains clusters of ten near-duplicates.
  • Customer-support transcripts may contain several turns from the same customer; a coding set may contain several tasks from one repository.

These groups are clusters: questions that share a source and so tend to be answered alike. The independent units are the clusters, not the questions. If every question in a cluster is answered identically, a set of 300 questions in 60 clusters of 5 is really a sample of 60, and the naive error bar is too narrow by a factor of √5, about 2.2.

Real clusters are partly correlated, not perfectly. The clustered standard error (borrowed from the social sciences, where students are sampled within schools and patients within clinics) handles the whole range. Miller's formula is the naive variance plus the covariance between every pair of questions within the same cluster: when scores within clusters are uncorrelated the extra term vanishes, and when they are perfectly correlated each cluster counts as one observation. A common rule of thumb from survey statistics (the design effect) is that m questions per cluster with within-cluster correlation ρ behave like n / (1 + (m − 1)ρ) independent ones. With m = 5 and ρ = 0.5, 300 questions are worth 100.

import random, math
random.seed(5)

# A reading-comprehension style eval: 60 passages, 5 questions each.
# A passage has its own difficulty, shared by its questions, so answers within a passage are correlated.
clusters = []
for _ in range(60):
    passage = random.betavariate(0.7, 0.7)                 # how hard this passage is for the model
    clusters.append([1 if random.random() < passage else 0 for _ in range(5)])

scores = [s for c in clusters for s in c]
n = len(scores)
mean = sum(scores) / n

se_naive = math.sqrt(sum((s - mean) ** 2 for s in scores) / (n - 1) / n)

# Clustered SE (Miller 2024, eq. 4): the naive variance plus cross-terms within each cluster.
cross = sum((a - mean) * (b - mean)
            for c in clusters for i, a in enumerate(c) for j, b in enumerate(c) if i != j)
se_clustered = math.sqrt(se_naive ** 2 + cross / n ** 2)

print(f"questions n={n}, clusters={len(clusters)}, mean score {mean:.1%}")
print(f"naive SE      {se_naive:.2%}   95% CI +/- {1.96*se_naive:.1%}")
print(f"clustered SE  {se_clustered:.2%}   95% CI +/- {1.96*se_clustered:.1%}")
print(f"ratio {se_clustered/se_naive:.2f}")
questions n=300, clusters=60, mean score 44.7%
naive SE      2.88%   95% CI +/- 5.6%
clustered SE  5.00%   95% CI +/- 9.8%
ratio 1.74

Here the naive interval is ±5.6 points and the clustered one is ±9.8: the true interval is 74 percent wider than the naive calculation claimed. Miller reports real cases using Anthropic models in which clustered standard errors were over three times larger than naive ones on DROP (1.34 against 0.44 points) and nearly double on MGSM. The data here are simulated by me with strongly clustered difficulty, so the ratio is an illustration, not a measurement of any benchmark.

The bootstrap, done on the right unit

The bootstrap is a resampling method for getting an interval without a formula: build many pseudo-evals by sampling your questions with replacement, compute the score on each, and read off the middle 95 percent. Miller notes that the Central Limit Theorem formula makes the bootstrap unnecessary for plain averages, but the bootstrap earns its place when the metric is awkward (an F1 score over the whole set, a median latency, nDCG, a ratio of two counts). The one rule is that you must resample the independent unit. If your data are clustered, resample whole clusters.

import random, math
random.seed(5)

# Same data as clustered.py: 60 passages x 5 questions, passage difficulty shared within a passage.
clusters = []
for _ in range(60):
    passage = random.betavariate(0.7, 0.7)
    clusters.append([1 if random.random() < passage else 0 for _ in range(5)])

def mean_of(cs):
    return sum(sum(c) for c in cs) / sum(len(c) for c in cs)

def boot(resample, B=4000):
    return sorted(mean_of(resample()) for _ in range(B))

by_question = [s for c in clusters for s in c]
rows = boot(lambda: [[random.choice(by_question)] for _ in by_question])      # wrong: resample single questions
cl = boot(lambda: [random.choice(clusters) for _ in clusters])                # right: resample whole passages

for name, xs in (("resample questions", rows), ("resample passages", cl)):
    lo, hi = xs[int(0.025 * len(xs))], xs[int(0.975 * len(xs))]
    print(f"{name:20s} 95% interval {lo:.1%} to {hi:.1%}   (width {hi-lo:.1%})")
resample questions   95% interval 39.0% to 50.3%   (width 11.3%)
resample passages    95% interval 34.7% to 54.7%   (width 20.0%)

Resampling single questions reports a 95 percent interval 11 points wide; resampling whole passages reports 20 points, which agrees with the clustered formula (2 × 9.8). The first is the wrong answer produced with confidence. The statistics lab in A0 builds the bootstrap from scratch, and Lab 1 in this course puts intervals on an eval harness.

Comparing two systems

Most evals are used to compare: this prompt against that one, this model against the next version. The naive way is to compute each system's score and standard error and then ask whether the intervals overlap. The better way is to use the fact that both systems answered the same questions.

Questions differ enormously in difficulty. A good system and a slightly better system will mostly succeed on the same easy questions and fail on the same impossible ones. That shared difficulty is noise for a comparison: it moves both scores together and says nothing about which system is better. The paired difference removes it by working with the per-question difference di = sB,i − sA,i directly. Its standard error is the usual one applied to those differences:

SEpaired = √( Var(d) / n ),    SEunpaired = √( SEA2 + SEB2 )

The two are connected by the correlation ρ between the systems' scores: SEpaired2 = SEA2 + SEB2 − 2 ρ SEA SEB. The more the two systems agree on what is easy and hard, the smaller the paired error bar. Questions on which both systems give the same grade contribute a difference of zero and effectively drop out.

Step through

Why only the disagreements matter

  1. System A. Twelve questions, graded 1 for correct and 0 for wrong. A gets 8 right. On its own that is a noisy number: with only 12 questions its standard error would be about 14 points.
  2. System B, same questions. B gets 9 right. The headline gap is one question, 8.3 points. Compared naively, that is well inside both systems' noise.
  3. Where they agree. On nine questions both systems got the same grade. Some are easy (both right) and some hard (both wrong). Either way the question reveals nothing about which system is better.
  4. The differences. Subtract per question. Questions 6 and 12 favour B (+1), question 3 favours A (−1), the rest are 0. The comparison is now an average of these twelve numbers.
  5. What carries the information. Three discordant questions, two to one for B. For binary scores this is the logic of McNemar's test: only the questions the systems disagree on count, and the test asks whether the split is lopsided. Twelve questions is far too few to conclude anything; the structure is what matters.

Now see it at realistic scale. The next script gives two systems the same 400 questions. B is slightly more capable. Each system answers correctly when its skill, plus a little run-to-run noise, exceeds the question's difficulty, so the systems agree on most questions.

import random, math
random.seed(8)
n = 400

# Each question has a difficulty both systems face. A system answers correctly when its
# skill (plus a little run-to-run noise) beats the difficulty, so good systems agree on what is easy.
def answer(skill, difficulty):
    return int(skill + random.gauss(0, 0.35) > difficulty)

a, b = [], []
for _ in range(n):
    d = random.gauss(0, 1)
    a.append(answer(0.50, d))
    b.append(answer(0.58, d))                          # B is a little better

ma, mb = sum(a) / n, sum(b) / n
def se(x):
    m = sum(x) / len(x); return math.sqrt(sum((v - m) ** 2 for v in x) / (len(x) - 1) / len(x))

diff = [y - x for x, y in zip(a, b)]
md = sum(diff) / n
se_unpaired = math.sqrt(se(a) ** 2 + se(b) ** 2)
se_paired = se(diff)
a_only = sum(1 for x, y in zip(a, b) if x and not y);  b_only = sum(1 for x, y in zip(a, b) if y and not x)
corr = (sum((x - ma) * (y - mb) for x, y in zip(a, b)) / n) / math.sqrt(ma * (1 - ma) * mb * (1 - mb))

print(f"A {ma:.1%}   B {mb:.1%}   difference {md:+.1%}   score correlation {corr:.2f}")
print(f"same answer on {n-a_only-b_only} questions; only A right {a_only}, only B right {b_only}")
print(f"unpaired SE {se_unpaired:.2%} -> z = {md/se_unpaired:.2f}, 95% CI {md-1.96*se_unpaired:+.1%} to {md+1.96*se_unpaired:+.1%}")
print(f"paired   SE {se_paired:.2%} -> z = {md/se_paired:.2f}, 95% CI {md-1.96*se_paired:+.1%} to {md+1.96*se_paired:+.1%}")
A 67.2%   B 70.5%   difference +3.2%   score correlation 0.63
same answer on 337 questions; only A right 25, only B right 38
unpaired SE 3.28% -> z = 0.99, 95% CI -3.2% to +9.7%
paired   SE 1.98% -> z = 1.64, 95% CI -0.6% to +7.1%

The two systems agree on 337 of 400 questions and their per-question scores have correlation 0.63. The unpaired standard error is 3.28 points and the paired one 1.98 points, so the same data move from a z-score of 0.99 to 1.64, with an interval of −0.6 to +7.1 points instead of −3.2 to +9.7. Notice two things. First, the paired interval is much narrower for free, with no extra model calls. Second, it still includes zero: a real 3-point improvement was not demonstrated by 400 questions. The 63 questions where the systems differ split 38 to 25 for B, and (38 − 25) / √63 = 1.64 is the McNemar statistic, identical to the paired z-score here.

Common misconception

"The two confidence intervals overlap, so the systems are not different." Overlap of individual intervals is a conservative test that ignores the pairing. Two scores whose intervals overlap can still have a paired difference whose interval excludes zero, as soon as the systems' scores are correlated. The reverse error is also common: a positive difference whose paired interval includes zero is not evidence that the systems are equal. It means the eval could not tell. Report the difference, its interval and the correlation, and let the reader see how wide "could not tell" is.

Analogy: two runners on the same course

To tell which of two runners is faster you could time each on a different day on a different route and compare the totals; wind, hills and weather add noise to both numbers. Or you could run them over the same course on the same afternoon and compare their split times, so the hills cancel and only the difference between the runners remains. A paired comparison is the second design, with the questions as the course.

Where it breaks down: a physical course is fixed and the runners' times differ only by chance. An eval's questions are a sample, and two systems can differ in which kinds of questions they find hard (one better at arithmetic, the other at policy lookups). Pairing handles noise, not the fact that one summary number hides where each system is stronger. Slice the results (error analysis again) before declaring a winner.

Planning: how many questions do you need?

Power analysis answers a question you should ask before building the eval: if system B really is better than A by δ points, how often will my eval detect it? Statistical power is the probability of detecting a real effect of a given size. The minimum detectable effect (MDE) is the smallest true difference your eval would detect with a stated power, usually 80 percent, at a stated false-positive rate, usually 5 percent.

For a paired comparison Miller derives the number of independent questions needed:

n = ( zα/2 + zβ )2 ( ω2 + σA2/KA + σB2/KB ) / δ2

Here ω2 = Var(xA) + Var(xB) − 2 Cov(xA, xB) is the variance of the per-question gap between the systems' true pass rates, the sampling noise from which questions you drew, reduced by the correlation. The σ2 terms are answer noise. With 5 percent false positives and 80 percent power, (zα/2 + zβ)2 is about 7.85. You can estimate ω2 and σ2 from a pilot run of the eval on a few hundred questions.

import math, random
from statistics import NormalDist
N = NormalDist()
z = lambda p: N.inv_cdf(1 - p)

def n_required(delta, omega2, s2a=0.0, s2b=0.0, ka=1, kb=1, alpha=0.05, beta=0.20):
    return (z(alpha / 2) + z(beta)) ** 2 * (omega2 + s2a / ka + s2b / kb) / delta ** 2

def mde(n, omega2, s2a=0.0, s2b=0.0, ka=1, kb=1, alpha=0.05, beta=0.20):
    return (z(alpha / 2) + z(beta)) * math.sqrt((omega2 + s2a / ka + s2b / kb) / n)

# omega^2: variance of the per-question gap between the systems' true pass rates.
# sigma^2: per-question answer noise of each system (1/6 if difficulty is uniform on 0 to 1).
print("questions needed (paired, 80% power, alpha 0.05), omega^2 = 1/9, answer noise 1/6 per system")
for delta in (0.10, 0.05, 0.03, 0.02, 0.01):
    print(f"  detect {delta:4.0%}: K=1 -> {n_required(delta,1/9,1/6,1/6):7.0f}   K=5 -> {n_required(delta,1/9,1/6,1/6,5,5):7.0f}   no answer noise -> {n_required(delta,1/9):6.0f}")

print("\nminimum detectable effect with n=198 questions, K=1 versus K=10")
print(f"  K=1: {mde(198,1/9,1/6,1/6):.1%}   K=10: {mde(198,1/9,1/6,1/6,10,10):.1%}")

Read the table. With ω2 = 1/9 (Miller's example value, which corresponds to a correlation of one third between the systems' question difficulties when pass rates are spread evenly), answer noise of 1/6 per system and one answer per question, detecting a 5-point improvement needs about 1,400 questions, and a 1-point improvement needs nearly 35,000. Answering each question five times cuts those by 60 percent, but there is a floor: with no answer noise at all you still need 349 questions for 5 points. Miller's closing remark is that new evals should contain at least 1,000 questions to have good signalling ability, and the table shows why. The last line checks the formula against a simulation: at the computed size, a true 3-point gap was detected in 82 percent of runs against a target of 80.

What the sample sizes tell you about practice

Many real prompt or model changes move an eval by one to three points. Detecting them reliably takes thousands of questions or a lower-noise measurement (continuous scores, answer probabilities, repeated runs), not a hundred hand-picked cases. If your eval is small, use it for what it is good at, large and obvious effects and catching disasters, and be honest that a "+1" is noise. If the effect size you care about is below your MDE, you have three choices: more questions, less noise, or a decision rule that does not depend on detecting it (such as "ship unless the interval excludes a drop of more than 2 points").

The traps around the numbers

Many slices, many metrics, many chances to be fooled

Error analysis (chapter 1) and slicing by user segment, topic or language are essential. They also create a multiple comparisons problem. If you test 20 slices at the 5 percent level and there is no real difference anywhere, you expect about one slice to look significant by chance; test 100 and you will find about five. Slices are also small: a slice of 40 questions has an error bar of about ±15 points at mid-range accuracy. Practical rules: decide which slices and metrics are confirmatory before looking at the data and treat everything else as exploratory, a lead to investigate with fresh data; adjust the threshold for the number of tests (the simplest correction, Bonferroni, divides α by the number of tests); and report how many things you looked at. The related trap of peeking, checking a running experiment until it turns significant, is in the A/B-testing peeking case.

Tuning on the test set

If you try ten prompt variants and report the best score on the same questions, the reported number is optimistic even if every individual measurement was fair. This is the winner's curse: the maximum of several noisy numbers is biased upward. Develop on one set, choose on a second, and report on a third that you have not looked at; chapter 6 covers the splits, and cross-validation is the classical version of the same discipline.

Judge scores carry extra uncertainty

When the metric comes from an LLM judge (chapter 3), the interval you computed from the judge's verdicts understates the real uncertainty in two ways. The judge's verdicts are themselves noisy, and the bias correction adds variance. Recall the Rogan-Gladen correction: true pass rate = (observed + TNR − 1) / (TPR + TNR − 1). The denominator, TPR + TNR − 1, is the judge's discriminating power. In chapter 3's example it was 0.96 + 0.67 − 1 = 0.63, so the standard error of the observed pass rate is magnified by about 1 / 0.63 = 1.6 times in the corrected estimate, before accounting for the fact that TPR and TNR were themselves estimated from a limited set of human labels. A weak judge costs you precision as well as accuracy. The practical approach is to bootstrap the whole pipeline, resampling both the human-labelled calibration set and the unlabelled production set, and report that interval.

Agents and repeated runs

Agent tasks have a lot of answer noise: a trajectory with 20 steps can diverge early. For them the repeated-run machinery above is not optional. It also raises a different question than "what is the average": how often does the agent succeed on every one of k tries, which matters if users depend on it? Chapter 8 introduces pass@k (at least one success in k tries) and pass^k (all k tries succeed), and why the second is the number to watch for reliability. Statistically, treat the task as the unit of sampling and the repeated runs as the way to shrink answer-level noise, exactly as in this chapter.

Systems connection

Comparing a new release against the old one on live traffic is the same problem with a different data source. Deployment strategies describes canary analysis, and Netflix's Kayenta compares canary and baseline metrics with statistical tests, in the same spirit as the paired intervals here. The reliability course also explains why latency percentiles cannot be averaged (Metrics, Percentiles & Histograms): if you report a latency or cost alongside accuracy, use the bootstrap for those, since the formulas in this chapter are for averages.

Reporting results so others can trust them

Miller suggests a small set of habits that make eval results readable. They cost almost nothing and prevent most arguments.

  1. State n, and the number of clusters if there are any. "73.0% (4.4) on 100 questions" is a different claim from "73.0% on 5,000".
  2. Put the standard error next to every score, in parentheses, and say which method (formula, clustered, bootstrap by what unit).
  3. Compare with paired differences. Show the difference, its standard error or interval, and the correlation between the systems' scores.
  4. Say how many answers per question you sampled and at what temperature, and do not tune the temperature to reduce noise.
  5. Give a minimum detectable effect for the eval, so a "no difference" result reads as "could not detect anything under 4 points".
  6. Declare what was planned and what was exploratory, and how many slices or variants you tried.

State of play, October 2026

Error bars are still not the norm. Reuel and colleagues' BetterBench (2024) assessed 24 AI benchmarks against 46 best practices and reported that most did not report statistical significance for their results. Eval frameworks differ in what they compute: Miller's 2024 paper notes that the UK AI Security Institute's Inspect framework computes the standard error correctly with its built-in stderr() metric, while some other tools bootstrap or apply the Bernoulli formula to non-binary scores. Check what your own harness reports, as it is one of the first things worth auditing, and check the framework's current documentation because these details change with releases. I read the abstracts for BetterBench and tinyBenchmarks (Polo et al., 2024, which shows that a few hundred well-chosen items can approximate a large benchmark's results) but not their full text.

Key takeaways

  • An eval score is an estimate from a sample of questions. Report its standard error, √(p(1−p)/n) for pass or fail scores, and remember that four times the questions halves the error bar.
  • There are two kinds of noise: which questions you drew, and how the model answered. Resample each question a handful of times to attack the second; only more independent questions attack the first. Do not lower the temperature to make noise go away.
  • Related questions (passages, translations, generated variants) form clusters. Use clustered standard errors, or bootstrap whole clusters; the naive error bar can be several times too narrow.
  • Compare systems on the same questions with paired differences. The disagreements carry the information, and the interval is narrower than the unpaired one at no cost.
  • Plan sample size before building the eval: detecting a 1-point gain needs thousands of questions. Know your minimum detectable effect, and treat smaller differences as unmeasured rather than as zero.
  • Guard against slices tried, variants tuned and judge noise: report what was planned, what was exploratory, and an interval that includes the judge's calibration uncertainty.

Check your understanding

An assistant answers 200 of 250 test questions correctly (80 percent). Treating the questions as independent, which is closest to its 95 percent confidence interval?

  1. 80 percent plus or minus 0.8 points
  2. 80 percent plus or minus 2.5 points
  3. 80 percent plus or minus 5 points
  4. 80 percent plus or minus 10 points
The standard error is √(0.8 × 0.2 / 250) = 2.5 points, and the interval is 1.96 times that, about 5 points. Plus or minus 2.5 is the standard error itself, which is only a 68 percent interval. Plus or minus 0.8 would need roughly 2,500 questions.

Two prompts are run on the same 500 questions and their per-question scores are strongly correlated. Why is the paired comparison tighter than the unpaired one?

  1. It uses more model calls, so each question is answered more times
  2. Shared question difficulty cancels in the per-question differences, and questions where both systems agree contribute nothing
  3. It assumes the true difference is zero, which narrows the interval
  4. It averages the two standard errors instead of adding their squares
Easy and hard questions move both systems together, which is noise for a comparison. Working with differences removes it; the more correlated the scores, the greater the saving. The paired test uses the same data and makes no assumption about the true difference. It uses no extra model calls, so it is not option A.

An eval already answers each question 20 times, so answer noise is tiny compared with the spread in question difficulty. The standard error is still too large to separate two systems. What helps most?

  1. More independent questions
  2. A higher K, answering 100 times per question
  3. Setting the temperature to zero
  4. Pooling all the answers into one larger sample before computing the error
Once E[σ2]/K is well below Var(x), the remaining noise comes from which questions were drawn, and only more independent questions reduce it. More repeats give diminishing returns, lowering the temperature can worsen the variance of the question-level means, and pooling the answers as if independent would understate the error.

A reading eval has 40 passages with 10 questions each (400 questions). Scores within a passage are highly correlated. Which statement is true?

  1. The naive standard error is correct because there are 400 questions
  2. The clustered standard error will be about the same as the naive one
  3. The effective sample size is larger than 400 because related questions add information
  4. The effective sample size is closer to 40 than 400, so the naive error bar is too narrow
Highly correlated questions within a passage add little independent information, so the passage is the sampling unit. Resampling or clustered formulas give wider intervals. A larger effective sample would need negatively correlated questions, which is unusual.

Using the K=1 column of the planning table (ω2 = 1/9, answer noise 1/6 per system), about how many questions are needed to detect a 2-point improvement with 80 percent power?

  1. About 870
  2. About 8,700
  3. About 87,000
  4. About 870,000
The K=1 column gives 8,721 for a 2-point gap. The required n scales with 1/δ2: halving the gap quadruples the questions, so 5 points needing 1,395 becomes 2 points needing about 8,700. Answer 870 would suit a gap of about 6 points; 87,000 is near what a gap of about 0.6 points would need.

A team tests 20 user segments for a quality drop at the 5 percent level and there is genuinely no difference in any segment. How many "significant" segments should they expect?

  1. None, since there is no real difference
  2. About 0.05
  3. About 1
  4. About 5
Each test has a 5 percent false-positive rate, so 20 tests give an expected 20 × 0.05 = 1 false alarm. That is why slices should be treated as exploratory unless planned, and why corrections such as Bonferroni exist. About 5 would be the expectation for 100 tests.

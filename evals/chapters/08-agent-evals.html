Evaluating Agents

An agent does not return one answer; it takes a series of actions that change the world, in conversation with a person who may say anything. This chapter explains how to grade what an agent leaves behind rather than what it says, how to use simulated users and read trajectories, why a single success rate hides unreliability (pass@k versus pass^k), and why every score needs a cost beside it.

Why this matters

The earlier chapters of this course evaluate a response: a question goes in, text comes out, and a check or a judge scores the text. Agents, the systems of Tool Calling: The Agent Loop and its neighbours, break almost every assumption in that picture. They take many steps, call tools that change databases and files, can reach the same result by several routes, and are non-deterministic from one run to the next. A team that evaluates an agent by reading its final message will ship an agent that says "your refund is on its way" and has refunded nothing. After this chapter you will be able to design an end-state grader, decide when a simulated user is worth its trouble, review trajectories efficiently, report reliability honestly with pass^k, and put a cost on every success.

Why agents are harder to evaluate

Take the evaluation methods of chapter 2 and apply them to a returns agent for an online shop. The input is a customer's request. The "output" is not a string to compare with a reference. It is a sequence: look up the order, check the policy, ask the customer to confirm, issue the return, tell the customer what happened. At the end of that sequence the database either shows a refund or it does not. Four properties make this different from grading a single reply.

  • Many steps. Errors compound. If each of ten steps works 95% of the time and the steps are independent, the whole run works about 60% of the time (0.9510). The same arithmetic that sets availability in a chain of services (What Reliability Means) governs agents.
  • Side effects. Tools change the world. A wrong answer can be corrected; a wrong refund has already been paid. The grader must look at the world, and at damage done to parts of it the task never mentioned.
  • Many valid routes. One agent looks the order up first; another goes straight to the return because the customer supplied the order number. Both are correct. A grader that expects one exact sequence of calls will fail good behaviour.
  • A conversation partner. In customer-facing tasks the other party is a person who gives information gradually, changes their mind and sometimes does not know what they want. The agent's behaviour depends on what the person says, so a fixed list of inputs is not enough.

Underneath all four is non-determinism: run the same task twice and the agent may succeed once and fail once. A single run is therefore a sample, not a measurement, which is why most of this chapter returns to repeated trials.

The vocabulary of an agent eval

Anthropic's engineering team has published a useful shared vocabulary in "Demystifying evals for AI agents", which this chapter follows. A task is one test: inputs plus success criteria. A trial is one attempt at a task; because outputs vary, a good eval runs several trials of each task. A grader is logic that scores some aspect of a trial; a task can have several. The transcript (also called a trace or trajectory) is the complete record of a trial: messages, tool calls, results and any reasoning. The outcome is the final state of the environment when the trial ends. The post's example is exactly the one that matters: whether a reservation exists in the database, not whether the agent said it had booked one. Finally the evaluation harness runs everything end to end (tasks, concurrency, recording, grading, aggregation) and is distinct from the agent harness or scaffold, the code that lets a model act as an agent. When you evaluate an agent you evaluate the model and its scaffold together.

Grade the end state, not the words

The principle that organises agent grading is: check what the agent produced in the world, not what it said or which route it took. Three alternatives are tempting and each fails in a predictable way.

  • Grade the reply. Look for "refund" and "25" in the final message. This rewards agents that claim success. A model asked to produce a plausible closing message produces one whether or not the tool call before it worked.
  • Grade the exact path. Require the calls lookup then return, in that order. This punishes valid alternatives and makes the test brittle: any improvement to the agent that changes its habits breaks the eval.
  • Grade the end state. Compare the database (or files, or sent emails) with the state a correct run would leave. This is the approach of tau-bench (Yao et al., 2024, "τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains"), which compares the database at the end of the conversation with an annotated goal state.

The following script builds a miniature version. A shop database has three orders and a stock count. The task: the customer wants to return the lamp from order A101 and be told the refund total. The goal state lists exactly what the database should look like afterwards. Three stand-in agents attempt it: A looks the order up and returns the lamp; B returns the lamp without a lookup; C looks up the order but returns the wrong item and still tells the customer the right refund. Three graders mark them.

import copy, random

START = {
    "orders": {"A100": {"status": "delivered", "items": ["kettle"], "refund": 0},
               "A101": {"status": "delivered", "items": ["lamp", "mug"], "refund": 0},
               "A102": {"status": "shipped",   "items": ["desk"], "refund": 0}},
    "stock": {"kettle": 5, "lamp": 2, "mug": 9, "desk": 1},
}

def tool_return(db, order, item):
    o = db["orders"][order]
    if o["status"] != "delivered" or item not in o["items"]:
        return "error: not eligible"
    o["items"].remove(item); o["refund"] += {"kettle": 30, "lamp": 25, "mug": 8}[item]
    db["stock"][item] += 1
    return "ok"

def tool_lookup(db, order):
    return db["orders"][order]

# A task: the user's hidden goal, and the goal STATE (not the goal transcript).
TASK = {"user_goal": "Return the lamp from order A101 and ask for the refund total.",
        "goal_state": {"orders": {"A100": {"status": "delivered", "items": ["kettle"], "refund": 0},
                                  "A101": {"status": "delivered", "items": ["mug"], "refund": 25},
                                  "A102": {"status": "shipped", "items": ["desk"], "refund": 0}},
                       "stock": {"kettle": 5, "lamp": 3, "mug": 9, "desk": 1}},
        "must_say": ["25"]}

def agent_a(db, rng):          # looks the order up first, then returns
    tool_lookup(db, "A101"); tool_return(db, "A101", "lamp")
    return "Done. Your refund is 25.", ["lookup", "return"]

def agent_b(db, rng):          # returns directly, no lookup: a different but valid path
    tool_return(db, "A101", "lamp")
    return "The lamp is returned and 25 will be refunded.", ["return"]

def agent_c(db, rng):          # says the right thing but returns the WRONG item
    tool_lookup(db, "A101"); tool_return(db, "A101", "mug")
    return "Done. Your refund is 25.", ["lookup", "return"]

def grade_end_state(db, reply, task):
    return db == task["goal_state"] and all(s in reply for s in task["must_say"])

def grade_exact_path(path, reference=("lookup", "return")):
    return tuple(path) == reference

def grade_transcript_only(reply, task):
    return all(s in reply for s in task["must_say"])

for name, agent in [("A (lookup, return)", agent_a), ("B (return only)", agent_b), ("C (wrong item)", agent_c)]:
    db = copy.deepcopy(START)
    reply, path = agent(db, random.Random(0))
    print(f"{name:20s} end-state={grade_end_state(db, reply, TASK)!s:5}  exact-path={grade_exact_path(path)!s:5}  reply-only={grade_transcript_only(reply, TASK)!s:5}")
A (lookup, return)   end-state=True   exact-path=True   reply-only=True 
B (return only)      end-state=True   exact-path=False  reply-only=True 
C (wrong item)       end-state=False  exact-path=True   reply-only=True

Read the table by columns. The reply-only grader passes all three agents, including the one that returned the wrong item. The exact-path grader fails agent B, which did nothing wrong. Only the end-state grader gets all three right: it passes A and B and fails C. Notice also what the equality db == goal_state catches that a targeted check would not: if an agent refunded the mug as well, or returned the lamp from order A100, the database would differ from the goal and the trial would fail. Comparing the whole state is how a grader detects collateral damage.

What the end state cannot see

The tau-bench authors define the reward as the product of two parts: r_action, which is 1 only when the final database exactly matches the unique annotated outcome, and r_output, which is 1 only when the agent's messages to the user contain the required information, checked as substrings. They also note that a reward of 1 is necessary but not sufficient for a good run: an agent could issue a return without the customer's explicit confirmation, violating policy, and still reach the right end state. So end-state grading is the backbone, with two supplements.

  1. Information the user had to be given (the refund total) is checked in the transcript, with a substring or a narrow judge.
  2. Process rules that the outcome cannot reveal (confirm before an irreversible action, never reveal another customer's data) are checked on the transcript with code where possible, for example "a return_item call must be preceded by a user message containing agreement", and with an LLM judge where the rule is fuzzy.

When several end states are acceptable

A goal state works when the task has one correct outcome. Many real tasks have several: any of three flights that meet the constraints, any reasonable summary file. Then assert invariants instead of one snapshot: "exactly one booking exists for this customer; it departs after 09:00; the total is under the budget; no other customer's booking changed". Write the invariants as small functions over the final state, each with a name, so a failing trial says which one broke. Where partial credit is meaningful, Anthropic's post recommends scoring the parts separately, for instance crediting the agent that diagnosed the problem and verified the customer even if the refund failed.

Common misconception

"If the agent says it did something, it did." Language models write a confident closing message whether or not the tool call before it succeeded, and some tool errors are swallowed by the scaffold. The reply is a claim; the database is the evidence. Always grade the state. The reverse also happens: an agent can do the right thing and describe it badly, which is why the reply is checked separately for the information the user needed.

Simulated users

When the task is a conversation, you cannot pre-write the user's side, because it must respond to what the agent asks. A simulated user is a model (or a script) that plays the customer. It receives a hidden instruction, for example "You want to return the lamp from order A101. You do not remember the order number but know it was last month. You will agree to a refund to the original card. You are impatient.", and produces each user message in reply to the agent's last one.

The tau-bench setup is a good reference design. The user simulator in the paper is a language model (gpt-4-0613 in the original) whose system prompt contains the hidden task instruction and the conversation so far; it cannot see the agent's tool calls. After each agent message it samples the next user message, and the episode ends when the user emits a stop token (###STOP###) or the agent hits a cap of 30 actions. In that setup the user is sampled at temperature 1.0 and the agent at temperature 0.0, so some of the variation between trials comes from the simulated user and not from the agent. That is realistic, since real customers vary, and also a reminder that a run-to-run difference is not automatically the agent's fault.

Step through

One trial: a return, graded by the database it leaves

  1. Setup. The harness resets the database to its starting snapshot, gives the simulated user its hidden instruction and gives the agent only its policy and tools. The goal state is held back for the grader.
  2. The user speaks. The simulator turns its hidden goal into a first message. The agent never sees the instruction, only what is said.
  3. The agent reads. A lookup is a read-only tool call. It changes nothing, so no grader cares that it happened, and an agent that skips it (agent B in the script) is not penalised.
  4. The agent asks to confirm. The policy says irreversible actions need agreement. This message is part of the transcript, and a process grader will look for it later.
  5. The user agrees. The simulator is told it will accept a refund to the original card, so it says yes. A different hidden instruction ("you are unsure") would have made this turn harder.
  6. The agent writes. return_item changes the world: the order loses the lamp, the refund is recorded and stock goes up by one. This is the event that end-state grading exists to verify.
  7. The agent reports. The final message is a claim about what happened. The user simulator ends the episode.
  8. Grading. The harness compares the whole database with the goal state, checks that the reply gave the refund total, and checks from the transcript that confirmation came before the write. Cost and step counts are recorded too. One trial gives one row of results.

The simulator is part of the instrument

A simulated user is itself a model, so everything from chapter 3 applies to it: it can be wrong, biased and inconsistent, and you must validate it before trusting results. Common faults, each visible when you read a few dozen transcripts:

  • Too cooperative. Real customers are vague, interrupt and withhold information. A simulator that volunteers the order number in its first message makes the agent look better than it is.
  • Leaking the goal. The simulator reveals the hidden instruction verbatim, or hints at the tool the agent should call.
  • Drift. Over a long conversation it forgets a constraint or changes its mind without cause, producing failures the agent could not avoid.
  • Ending badly. It never says it is finished, or finishes before the agent has acted, so the trial times out or the outcome is graded too early.

Two practical remedies. For regression suites that run on every change, prefer a scripted user (fixed replies for the expected agent questions) because it is deterministic and cheap, and use an LLM user for the periodic realism check. And fix the simulator model and its version in the harness's configuration: if the simulator changes, scores are not comparable with earlier runs (the same reason benchmarks are versioned). The follow-up τ²-bench (Barres et al., 2025) pushes further: both the agent and the user have tools that act on a shared environment, as in a telecom support call where the customer must toggle a setting on their own phone. The authors report significant performance drops when agents move from the no-user to the dual-control setting, which they attribute partly to the difficulty of guiding a user through actions.

Reviewing trajectories

The outcome says whether a trial passed. The transcript says why. Anthropic's post makes the split explicit: use outcome grading to decide pass or fail at scale, and use transcript review to learn why a trial failed, whether a pass was luck, and whether the grader itself is fair. The method is the error analysis of chapter 1, with agent-specific questions:

  1. Find the first wrong step. Later steps often look absurd because an early step was wrong. A mistaken order number at turn 2 explains a hopeless refund request at turn 9.
  2. Classify the step. Common categories: wrong tool, right tool with wrong arguments, ignored policy, stopped too early, looped without progress, lost information from earlier in the conversation, gave up, or reported success that did not happen.
  3. Ask whether a pass was earned. A trial that succeeded after three needless retries, or by exploiting a loophole, is a fragile pass.
  4. Ask whether the failure was fair. Did the grader reject a correct outcome? The grader bugs in the next paragraph are common.

Alongside reading, compute a few trajectory metrics automatically on every trial: number of steps, number of tool errors, repeated identical calls (a loop), whether any write was attempted before confirmation, and whether the run hit its step cap. They do not replace the outcome. They are the cheap signals that point you to the trials worth reading, and they are what you chart over time to notice that a change made the agent slower or more erratic without changing the pass rate.

On the fairness question, Anthropic's post reports an instructive case: an Opus 4.5 run on CORE-Bench scored 42% at first, and reached 95% after the team fixed grading bugs (the grader rejected "96.12" when the expected answer was "96.124991...") and used a less constrained scaffold. The model had not changed. The same post gives a rule of thumb that agrees with experience: a 0% pass rate over many trials usually points to a broken task, not an incapable agent. So when a task never passes, read its transcripts for the grader's behaviour before concluding anything about the model.

One run is a sample: pass@k and pass^k

Because agents are non-deterministic, run each task several times. Suppose you run each of 60 tasks n = 8 times and task i succeeds ci times. Two natural questions can be asked about "k attempts", and they have different answers.

pass@k
The chance that at least one of k attempts succeeds. Chen et al. (2021, "Evaluating Large Language Models Trained on Code") introduced it for code generation, where a test suite can verify any candidate and one working solution is enough. It rises as k grows.
pass^k (read "pass hat k" or "pass to the k")
The chance that all k attempts succeed, as defined in tau-bench. It measures consistency and falls as k grows.

Given n recorded trials of a task with c successes, both can be estimated without bias from the recorded counts by counting combinations. The probability that k trials drawn without replacement from the n are all failures is C(n−c, k) / C(n, k), and the probability that all are successes is C(c, k) / C(n, k):

pass@k = 1 − C(n−c, k) / C(n, k)     pass^k = C(c, k) / C(n, k)

each averaged over tasks. This is the form given in the tau-bench paper. At k = 1 both equal c/n, the ordinary success rate. If every task had the same success chance p, then pass^k would be pk: with p = 0.75 the values for k = 1, 2, 4, 8 are 0.75, 0.56, 0.32 and 0.10. The script below applies both formulas to simulated results in which a third of tasks are reliable, some are shaky and some are hard, and compares with that closed form.

import random
from math import comb

rng = random.Random(7)
N_TASKS, N_TRIALS = 60, 8
# Per-task success probability: a third of tasks are reliable, a third shaky, a third hard.
true_p = [rng.choice([0.97, 0.97, 0.97, 0.7, 0.7, 0.45, 0.45, 0.1]) for _ in range(N_TASKS)]
runs = [sum(rng.random() < p for _ in range(N_TRIALS)) for p in true_p]   # c successes out of n

def pass_at_k(c, n, k):   # P(at least one of k sampled trials succeeds), from n recorded trials
    return 1 - comb(n - c, k) / comb(n, k)

def pass_hat_k(c, n, k):  # P(all k sampled trials succeed): tau-bench's pass^k
    return comb(c, k) / comb(n, k)

print(f"{N_TASKS} tasks x {N_TRIALS} trials; mean per-trial success {sum(runs)/(N_TASKS*N_TRIALS):.3f}")
print(" k   pass@k   pass^k")
for k in (1, 2, 4, 8):
    a = sum(pass_at_k(c, N_TRIALS, k) for c in runs) / N_TASKS
    b = sum(pass_hat_k(c, N_TRIALS, k) for c in runs) / N_TASKS
    print(f"{k:2d}   {a:6.3f}   {b:6.3f}")

# Closed form if every task had the same p: pass^k = p**k
print("\nsame p on every task:  p=0.75 ->", [round(0.75**k, 3) for k in (1, 2, 4, 8)])
# Cost: every trial costs tokens; failures still cost.
cost_per_trial = 0.04
succ = sum(runs); total = N_TASKS * N_TRIALS
print(f"\nspend ${total*cost_per_trial:.2f} for {succ} successful trials -> ${total*cost_per_trial/succ:.3f} per success (vs ${cost_per_trial:.2f} per attempt)")

Which one to report

Choose by asking what a user experiences. If the system can try again and a checker can recognise success (generate ten code patches, run the tests, ship one that passes), then one success in k is the real capability and pass@k is the honest number. If the user meets the agent once per request and every failure is paid for (a refund issued wrongly, a booking cancelled in error), then what matters is the chance that this request succeeds, and a fair summary of reliability across repeated use is pass^k. Anthropic's post gives the arithmetic in one line: with a 75% per-trial success rate, three trials in a row all succeed 0.753, about 42% of the time. A customer service agent that is 75% reliable per conversation will, for a customer who contacts it three times, fail at least once more often than not.

The pass^k idea is the serial-composition rule from availability maths moved to behaviour: requiring k independent successes multiplies the probabilities, just as k components in series multiply their availabilities. It is also why the fan-out and tail-latency intuitions carry over: the more things must all go right, the worse the headline.

Putting error bars on them

The trials of a task are not independent samples of the population of tasks; the tasks are. The effective sample size for a claim about "the agent on this kind of work" is the number of tasks, so resample tasks (with all their trials) when you bootstrap, as in the clustering discussion of chapter 4. Extra trials per task reduce the noise from the agent's own randomness; they do not substitute for more tasks. Paired comparisons of two agent versions on the same tasks, with the same simulated-user seeds, remove much of the task-to-task variance.

State of play, October 2026

The tau-bench paper (Yao et al., 2024) reports that function-calling agents including GPT-4o succeeded on fewer than half of its tasks: 115 retail tasks and 50 airline tasks, with GPT-4o at 61.2% (retail) and 35.2% (airline) on the first trial and a retail pass^8 below 25%. Those figures belong to the models and prompts of 2024. The original repository is dated, and the benchmark's successors (τ²-bench and later releases) change domains, task sets and user simulators, so a number labelled "τ-bench" is only comparable with another if domain, task release, user model and number of trials all match. Treat any current leaderboard value as a snapshot, and see chapter 9 for how to read one. The tau-bench case study goes through the design in detail.

Cost per task

An agent that succeeds 90% of the time at ten dollars a task and one that succeeds 80% at ten cents are not comparable on accuracy alone. Agents spend tokens at every step, and the context they send grows with the conversation (Context Engineering), so cost per task varies far more than for a single model call. Record, for every trial:

  • input and output tokens, summed over every model call, and the resulting money cost at the prices you pay;
  • number of model calls and tool calls (steps), and wall-clock time;
  • whether the run hit a budget or step cap, which is a form of failure the outcome grader sees only as "not finished".

Two derived figures matter. Cost per success is total spend divided by the number of successful trials, which is higher than cost per attempt because failures cost money too: in the simulation above, 480 trials at $0.04 each cost $19.20 and produced 342 successes, so each success cost $0.056, 40% more than an attempt. (The $0.04 is an illustrative assumption, not a measured price.) The cost distribution, not just the mean: one runaway loop that burns two hundred model calls can dominate a day's spend, so report the 95th percentile and the maximum beside the average, and set step and token caps in the harness exactly as you would in production. The trade-off between cost, latency and quality is the subject of chapter 19; the discipline here is that no agent score is published without its cost beside it.

If you want pass^k, remember the price of getting there. Running eight trials of every task multiplies evaluation cost by eight, and a reliability fix that works by retrying (try again until a validator passes) lowers the failure rate while raising cost per task, which is a legitimate trade only if you measure both.

Keeping the instrument honest

An agent eval is a small software system, and it fails in software ways.

  • Reset the world. Every trial starts from the same snapshot of the database and files. State left over from the previous trial makes trials dependent and results unreproducible.
  • Isolate side effects. Real emails, payments and shell commands do not belong in an eval. Use mocks or sandboxes (Sandboxes & Permissions covers the mechanics); for coding agents, a throwaway container per trial.
  • Make tools deterministic where possible. A search tool that returns different results each call adds noise you did not intend. Fix seeds and record external responses.
  • Hide the answer. Goal states, reference solutions and grader code must not be reachable from inside the agent's environment. Agents that can read the test file will, sometimes, and the pass will be real as a score and worthless as evidence.
  • Watch for evaluator hacking. An agent optimised against a grader finds the grader's gaps. The AI CUDA Engineer case shows claimed speedups that came from loopholes in the harness. Read transcripts of the highest scorers as hard as those of the lowest.
  • Validate graders. Run the grader on known-good and known-bad end states you construct by hand, as the milestones of Lab 4 do, before running any model.

Systems connection

An end-state grader is the same idea as a test oracle that asserts on state rather than on calls, and the reset-per-trial rule is test isolation. The reliability arithmetic of chained steps and repeated trials is serial composition, and the argument for percentiles beside the mean in cost reporting is the one made in SLIs, SLOs & Error Budgets and Tail Latency at Scale. Permissions an agent holds in the eval environment should mirror the least-privilege design of Authorization.

Public agent benchmarks, briefly

You will meet several public agent benchmarks, and each embodies one of the grading choices above. SWE-bench grades a coding agent by running the project's tests on the patched repository, an end-state check whose weaknesses (weak or flawed tests, memorised fixes) are the subject of the SWE-bench Verified case and chapter 7. tau-bench and its successors grade by database state in simulated customer conversations. Browser and computer-use benchmarks check functional outcomes on web pages or application state. Research-style benchmarks often grade a short final answer by matching it to a key, which is outcome grading with all the limits of answer matching. When you read a result on one of them, ask which of these it is, what the scaffold was (chapter 9), and how many trials the number averages over.

Building your first agent eval

A workable first version is small. Anthropic's post suggests that 20 to 50 simple tasks drawn from real failures are enough to start, and that matches the experience of teams doing error analysis first.

  1. Take 30 real or realistic tasks from your error analysis, including some that should end with the agent declining or escalating.
  2. For each, write the starting state, the hidden user instruction (or the fixed input) and the goal state or invariants. Have a second person solve two of them by hand to test that the goal state is reachable and unambiguous.
  3. Build the harness: reset, run with a step and cost cap, record transcript and outcome. Validate the graders on hand-made good and bad end states.
  4. Run five trials per task. Report pass@1, pass^5, cost per success, and the 95th percentile cost, each with a bootstrap interval over tasks.
  5. Read every failing transcript for the three least reliable tasks, name the first wrong step in each, and fix the agent or the task. Add every real production failure to the suite as it appears (chapter 18).

Key takeaways

  • Grade the outcome: compare the final state of the world with a goal state or a set of invariants. Replies are claims, and exact tool sequences punish valid alternatives.
  • End-state equality also catches collateral damage; add transcript checks only for information the user needed and for process rules the state cannot show, such as confirmation before irreversible actions.
  • A simulated user makes conversations testable but is itself an instrument: give it a hidden goal, keep it realistic, version it, and read its transcripts.
  • Use the outcome to decide pass or fail and the transcript to learn why. A task nobody ever passes is more often a broken task than an incapable agent.
  • Run several trials per task. pass@k (at least one success) measures capability; pass^k (all succeed) measures reliability and falls as k grows. Bootstrap over tasks, not trials.
  • Report cost per success and its tail beside every score; failures cost money too.
  • You evaluate model plus scaffold. Reset state, isolate effects, hide the answer, and validate the graders before trusting any number.

  • UK AI Security Institute, Inspect documentation. An open-source evaluation framework with sandboxing and agent support, useful as a model for a harness.

Check your understanding

An agent's final message says "Done: 25 refunded to your card", and a grader that searches the reply for "refund" and "25" marks it correct. Which statement is most accurate?

  1. The grader is sound, because the reply contains the information the customer needed.
  2. The grader measures a claim, not the outcome; the refund may never have been recorded, or the wrong item may have been returned.
  3. The grader is too strict, because the agent may have worded the refund differently.
  4. The grader should be replaced by an LLM judge that reads the whole transcript, which is always more reliable than state.
The reply is the agent's description of what it did. Language models produce a fluent closing message whether or not the tool call worked, so the database is the evidence. A judge reading the transcript (option 4) can still be fooled by the same claim, and it is not "always more reliable" than a state check. The reply is still worth checking, but only for information the user needed.

Agent B returns the lamp without first calling lookup_order because the customer supplied the order number. The database ends in exactly the goal state. Under which grader does B fail?

  1. End-state equality with the goal state.
  2. A reply check for the refund total.
  3. A check that no other order changed.
  4. An exact-sequence check expecting lookup then return.
Only the trajectory check fails B, and it fails an agent that behaved correctly. This is the brittleness of grading the path: a valid alternative route is penalised, and any improvement in the agent's habits breaks the eval. The other graders look at outcomes, which B got right.

An agent solves 80% of attempts on average, and its success varies little from task to task. A product owner who runs each task five times per customer asks for the chance of five successes in a row. Which value is closest?

  1. About 33%, since 0.8 to the fifth power is 0.33.
  2. About 80%, since the per-trial rate does not change.
  3. About 99%, since at least one of five tries will succeed.
  4. About 20%, since 1 minus 0.8 is the failure rate.
With similar success chances across tasks, pass^5 is close to 0.85 = 0.33. Option 3 is pass@5 (at least one success), a different question. Option 2 ignores that every trial must succeed. If tasks differed greatly, with some always solved and some never, pass^5 would be higher than 0.33 for the same average, which is why the spread of task difficulty matters.

Task X has been run 40 times with 0 passes against several different agent versions. What is the best first action?

  1. Conclude that the task is too hard and keep it as a stretch target.
  2. Remove it from the suite, since a task nobody passes carries no information.
  3. Read the transcripts and test the grader and the goal state, since a task that never passes is more often broken than impossible.
  4. Increase the temperature of the agent, to produce more varied attempts.
Zero passes across many trials and versions is a classic signature of an unreachable goal state, a grader bug (such as an exact-match on a number that differs by rounding) or a missing tool. Check by solving the task yourself or running the grader on a hand-made correct end state. Dropping or keeping the task unexamined (options 1 and 2) skips the diagnosis, and varying temperature does not fix a faulty instrument.

You compare two agent versions on 40 tasks, running each task 10 times, and bootstrap a confidence interval for the difference in pass rate. How should you resample?

  1. Resample all 400 trials independently, since each is a separate observation.
  2. Resample the 40 tasks with replacement, keeping each task's trials together.
  3. Resample only the trials of the worst ten tasks.
  4. Do not resample; with 400 trials the difference is exact.
Trials of one task share that task's difficulty, so they are not independent; the independent units are the tasks. Resampling trials alone (option 1) understates the uncertainty. More trials per task shrink the noise from the agent's randomness but cannot create more tasks.

Agent P succeeds on 90% of tasks at an average of $2.00 per attempt. Agent Q succeeds on 82% at $0.10 per attempt. Which statement about comparing them is best?

  1. P is better, because accuracy is the only property that matters in an eval.
  2. Q is better, because it is cheaper.
  3. They cannot be compared without the 95th percentile latency, which is the only other metric needed.
  4. Neither is better in general: compare cost per success and its tail against what a failure costs, and consider routing hard tasks to P.
Cost per success is about $2.22 for P and $0.12 for Q, so P buys eight points of success for roughly eighteen times the price. Whether that is worth it depends on what a failure costs the business. Options 1 and 2 pick a single dimension; option 3 wrongly claims one extra metric suffices. Cost, latency and quality form a front, not a single ranking (chapter 19).

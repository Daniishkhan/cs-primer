HTTP & the Web

HTTP is the language browsers and servers speak, and, far beyond browsers, the language that most software on Earth uses to ask other software for things. It is surprisingly simple: a request is a few lines of text, and so is the reply. By the end of this chapter you'll be able to read those lines, and you'll be able to narrate everything that happens between pressing Enter on a URL and seeing a page, using every chapter so far.

Why this matters

HTTP is the most-used application protocol there is. Web pages, mobile apps, payment systems and the internal calls between microservices all speak it. The details you learn here (methods, status codes, caching, and how the protocol evolved to dodge the speed limits of TCP) turn up in nearly every design discussion about distributed systems, especially the questions "is it safe to retry this?" and "what does this error code mean?".

Requests and responses

HTTP (HyperText Transfer Protocol) follows the simplest pattern in networking, request and response:

  1. A client (your browser, curl, a phone app) opens a connection to a server and sends a request: "please give me this thing" or "please do this."
  2. The server sends back exactly one response: "here it is," "I can't find it," "I did it," or "I failed."

The client always speaks first. The server never sends a response nobody asked for. (Later in this chapter and in chapter 12 you'll see tricks for situations where that is inconvenient.) HTTP normally runs on top of a TCP connection (chapter 8), on port 80 for plain HTTP and port 443 for HTTPS (chapter 11).

What a request looks like

Up to HTTP/1.1, requests and responses are literally plain text, which makes them easy to read and debug. Here is the whole of a request:

GET /shop/shoes?color=red HTTP/1.1      # request line: METHOD  PATH  VERSION
Host: www.example.com                  # headers: Name: value, one per line
User-Agent: curl/8.4.0
Accept: text/html
                                          # a blank line ends the headers
                                          # (a GET has no body)

Three parts:

Request line
The method (what to do: GET), the path (which thing, plus an optional ?query) and the protocol version.
Headers
Extra information as Name: value lines: who I am, what formats I accept, which website I mean, and much more.
Body
Optional data after the blank line. A GET usually has none; a POST that submits a form or JSON does.

What a response looks like

HTTP/1.1 200 OK                           # status line: VERSION  CODE  REASON
Content-Type: text/html; charset=UTF-8   # headers
Content-Length: 1256
Cache-Control: max-age=3600

<!doctype html>                          # body: the actual page (1256 bytes)
<html><head><title>Red shoes</title> ...

The status line says how it went. The Content-Length header tells the client how many bytes of body follow, which matters because TCP is just a stream of bytes with no built-in message boundaries (more on that in chapter 12). Content-Type says what the body is, so the browser knows whether to draw it as a page, display it as an image, or hand it to a JSON parser.

Analogy: ordering at a counter

You walk up to a counter and say "I'd like the red shoes, size 9" (the request). The clerk disappears, comes back, and either hands you the shoes with a receipt (200 OK and a body), tells you "we moved that to aisle 4" (a redirect), says "we don't have that" (404), or "the stockroom is on fire" (500). Every visit is one question and one answer.

Where it breaks down: the clerk in a shop recognises you from yesterday. HTTP's clerk has amnesia, as the next sections explain.

HTTP is stateless

Each request is understood on its own. The server does not have to remember anything about your previous requests; everything it needs to know must be in the request itself. This stateless design is a big reason the web scaled: if no server remembers you, any server in a fleet can answer any request, so you can add machines freely behind a load balancer (chapter 14). If one crashes, the next request simply goes elsewhere.

But websites obviously do remember you: your shopping cart, your login. That is handled with cookies, which we'll get to after the vocabulary.

URLs: addresses for things on the web

A URL (Uniform Resource Locator) is the full address of a resource. It packs several of the earlier chapters' ideas into one string:

  • Scheme picks the protocol: http, https, and others such as ftp or mailto.
  • Host is the name of the server. The browser asks DNS (chapter 9) to turn it into an IP address. It can also be an IP address directly.
  • Port selects the program on that machine (chapter 7). Left out, it defaults from the scheme.
  • Path names the resource on that server. It looks like a file path, but the server is free to interpret it however it likes.
  • Query carries extra parameters as name=value pairs separated by &.
  • Fragment (#reviews) names a spot within the page, such as a heading to scroll to. It is handled by the browser and is never sent to the server.

Notice where the pieces go in the request you saw earlier: the host lands in the Host: header, and the path and query land in the request line. The scheme and port decided how the connection was made in the first place.

Methods: what do you want done?

The method is the verb of the request. The common ones:

MethodMeaningHas body?Safe?Idempotent?
GETFetch a resourcenoyesyes
HEADLike GET but return only the headers (is it there? how big?)noyesyes
POSTSubmit data / create something / trigger an actionyesnono
PUTReplace the resource at this URL with the one I sendyesnoyes
PATCHApply a partial change to a resourceyesnonot guaranteed
DELETERemove the resourceusually nonoyes

The last two columns are among the most important ideas in this chapter, because they decide what you can do when something goes wrong.

Safe
The request is meant only to read. It shouldn't change anything on the server. That's why browsers and search engines can freely pre-fetch GET links.
Idempotent
Doing it once or many times has the same effect on the server's state. PUT /users/7 {name: "Ada"} leaves user 7 named Ada whether you send it once or five times. DELETE /users/7 leaves user 7 gone however often you send it (the second reply may be 404, but the state is the same). POST /orders, by contrast, usually creates a new order each time, so sending it twice may charge you twice.

Common misconception: "the method enforces the behaviour"

Safe and idempotent are promises that the server's author makes, not laws of nature. A badly designed server can delete data on a GET /delete-account link, and then a browser pre-fetching it would do damage. Well-behaved APIs keep the promise, and everything that sits in between (browsers, proxies, retry libraries) relies on it.

Why does this matter? Imagine your phone sends "pay the bill" and the connection drops before the reply arrives. Did the server get the request? You can't know. If the call was idempotent (PUT, DELETE, GET), you can just send it again, which is harmless if it already worked. If it was a plain POST, retrying may do the thing twice. We'll turn this into a design technique in chapter 16.

Status codes: how did it go?

Every response starts with a three-digit status code. The first digit tells you the class, which is often all you need:

ClassMeaningCommon codes
1xxInformational: "carry on"101 Switching Protocols (used to start a WebSocket, chapter 12)
2xxSuccess200 OK, 201 Created, 204 No Content
3xxRedirection: look elsewhere301 Moved Permanently, 302 Found (temporary), 304 Not Modified, 307/308 (redirects that keep the method)
4xxThe client did something wrong400 Bad Request, 401 Unauthorized (really "not authenticated"), 403 Forbidden, 404 Not Found, 409 Conflict, 429 Too Many Requests
5xxThe server failed (the request may have been fine)500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout

The 4xx/5xx split answers the question "whose fault is it, and will retrying help?". A 404 will still be a 404 on the second try. A 503 may well succeed a moment later. (The nickname "teapot" status 418 is a real joke code from an April Fools' RFC; you may meet it in the wild.)

Cookies: adding memory to a forgetful protocol

To make a stateless protocol feel stateful, the server hands the browser a token and asks it to show the token on every later request. The token is a cookie. A login works like this:

# 1. You submit your password.
POST /login HTTP/1.1
Host: www.example.com
Content-Type: application/x-www-form-urlencoded

user=ada&password=...

# The server checks it, stores "session 8f3a... = Ada" in its own memory or database,
# and replies with a cookie:
HTTP/1.1 200 OK
Set-Cookie: session=8f3a91c2d7; HttpOnly; Secure; SameSite=Lax; Max-Age=3600

# 2. Every later request from this browser automatically carries it back:
GET /account HTTP/1.1
Host: www.example.com
Cookie: session=8f3a91c2d7

The browser attaches the cookie by itself on each request to that site. The server looks the session id up (the "memory" lives on the server side, often in a shared database or cache, so any server in the fleet can find it) and knows you're Ada. The extra attributes are safety belts: HttpOnly hides it from page scripts, Secure restricts it to HTTPS, SameSite limits sending it on cross-site requests, and Max-Age sets the lifetime.

Common misconception: "HTTP remembers me, so HTTP is stateful"

HTTP itself still forgets everything after each response. The "memory" is a convention layered on top: a token the client keeps and returns, plus a lookup table the server keeps. Because a cookie is a bearer token (whoever holds it is you), session ids must be long, random and sent only over encrypted connections. That's chapter 11.

Caching in HTTP

The fastest request is the one you never make. Just like DNS, HTTP lets responses be stored and reused, by the browser, by proxies and by CDNs (chapter 14). The server controls this with headers:

  • Cache-Control: max-age=3600 means "you may reuse this response without asking me for the next hour." Within that time, the browser doesn't touch the network at all. (no-store means "don't keep this at all", for sensitive pages. no-cache confusingly means "you may store it, but check with me before reusing it".)
  • Revalidation. When the stored copy has expired, the browser needn't download the whole thing again if it hasn't changed. The server labels each version with an ETag (a fingerprint). The browser asks "do you still have version abc123?":
GET /logo.png HTTP/1.1
Host: www.example.com
If-None-Match: "abc123"      # "I already have the version tagged abc123"

HTTP/1.1 304 Not Modified      # "Yes, still current. Use your copy."  (no body sent)
ETag: "abc123"

A tiny 304 response replaces a download that might be megabytes. If the file had changed, the server would send 200 OK with the new body and a new ETag.

Does this look familiar? A max-age is a TTL, exactly like DNS's. Within it, copies are served without checking, so they can be stale: the same eventual-consistency bargain again. Sites often avoid the problem for static files by putting a version in the file name (app.3f9a1c.js); a new version is a new name, so no stale copy can ever be mistaken for it.

How HTTP got faster: 1.0 to 3

The text of an HTTP request hasn't changed much since the 1990s. What changed, dramatically, is how requests are carried over the network. The story is a series of attacks on one problem: a modern page needs dozens or hundreds of requests (HTML, CSS, scripts, images, fonts), and each one costs round trips (chapter 1: latency is bounded by physics).

HTTP/1.0: one request, one connection

The first widely used version opened a new TCP connection for every request, then closed it. Each file paid for a fresh TCP handshake (one round trip, chapter 8) before a single byte of useful data moved. For a page with 30 files, that's 30 handshakes.

HTTP/1.1: keep the connection open

HTTP/1.1 (1997) made connections persistent (keep-alive): one TCP connection carries many requests, one after another. Handshakes are paid once. But there's a catch: on a given connection, the client sends a request, then must wait for the full response before the next reply can start, because the replies have no labels and must come back in order. A slow response at the front blocks everything behind it. That is head-of-line blocking.

The workaround was brute force: browsers open around six parallel connections per website. It works, but each connection has its own handshake and its own TCP slow start (chapter 8), and sites resorted to ugly hacks, such as spreading files across several host names, to get more of them.

HTTP/2: many conversations on one connection

HTTP/2 (2015) changed the format on the wire from text to binary frames. Each frame is tagged with a stream id, so responses for different requests can be chopped into pieces and interleaved on a single TCP connection (multiplexing). A big image no longer blocks the small stylesheet. It also compresses headers, which are highly repetitive from request to request. The meaning of methods, headers and status codes stayed the same; your application code barely notices. Browsers use it over TLS, and the two sides agree to use it during the TLS handshake.

But HTTP/2 inherited a hidden weakness. All those streams share one TCP connection, and TCP delivers bytes strictly in order. If one packet is lost, TCP holds back everything after it until the retransmission arrives, even bytes belonging to completely different streams that already arrived intact. This is TCP-level head-of-line blocking, and on lossy networks (mobile!) it can make HTTP/2 worse than six separate connections.

HTTP/3: a new transport

The fix couldn't be done inside TCP, which is baked into operating systems and middleboxes worldwide. So HTTP/3 (2022) runs on QUIC, a new transport built on top of UDP (chapter 7), which almost every network already lets through (and where it doesn't, browsers quietly fall back to HTTP/2). QUIC re-implements TCP's good parts (reliability, congestion control) in user-space software, but with independent streams: a lost packet only delays the stream it belonged to. QUIC also builds TLS 1.3 into its handshake, so setting up a connection and encrypting it takes one round trip rather than separate ones, and connections can survive your phone switching from Wi-Fi to cellular.

Go deeper: how does a browser find out a server speaks HTTP/3? optional

A browser can't know in advance whether a server supports QUIC, and some networks block UDP altogether. So the usual dance is: connect with TCP and HTTP/2 first; if the server's response includes an Alt-Svc header ("I'm also available over HTTP/3 on this port"), or if DNS supplies a special HTTPS record saying so, the browser tries QUIC next time. If QUIC doesn't work, it silently falls back to TCP. Real-world connections therefore mix all three versions.

Capstone: what happens when you type a URL and press Enter?

This is the classic interview question, and now you can answer it properly, because you've met every ingredient. Step through it below. To give the delays meaning, we'll assume a cold start (nothing cached, a fresh connection), the DNS resolver being a 20 ms round trip away, and the web server 50 ms away. Your real numbers will differ, but the structure is always the same: a few round trips before the first byte of useful content.

Step through

From URL to rendered page

  1. Parse the URL. Your browser splits https://www.example.com/shop into scheme (https), host, port (443 by default) and path. It checks its own caches and settings: a cached copy of the page? A saved rule to always use HTTPS for this site? If nothing short-circuits the trip, it goes to the network. Cost: effectively none.
  2. DNS lookup (chapter 9). The host name must become an IP address. The browser and OS check their caches; on a miss, the stub resolver sends one UDP packet to the recursive resolver, which answers from its cache or walks the tree. Cost: ~0 ms if cached; here one 20 ms round trip to a resolver that already knows the answer; more if it has to walk the tree.
  3. TCP handshake (chapter 8). With an address and port in hand, the OS sends SYN, gets SYN-ACK, and replies ACK. The packets travel through your Wi-Fi/Ethernet link (chapter 2), your router with NAT (chapter 4) and many routers on the way (chapter 5), each choosing the next hop independently. Cost: 1 round trip to the server, ~50 ms. (The request may be sent along with the final ACK, but with TLS the request has to wait.)
  4. TLS handshake (chapter 11). Because the scheme is https, the two sides now agree on encryption keys and the server proves its identity with a certificate. With TLS 1.3 this takes one round trip; every byte after it is encrypted. Cost: ~50 ms. Older TLS 1.2 needs two round trips.
  5. Send the HTTP request. Finally the browser sends the text you saw earlier (GET /shop, Host: www.example.com, cookies for this site, and so on), encrypted inside TLS, inside TCP segments, inside IP packets, inside link-layer frames: the layers of chapter 3, working together. Routers on the way see only the IP and TCP headers.
  6. The server responds. A load balancer (chapter 14) hands the request to one of many identical servers, which finds or builds the page and replies 200 OK with headers and the HTML body. Cost: 1 round trip (~50 ms) plus however long the server takes to think (anything from 5 ms for a cached page to hundreds for a heavy one). Everything up to the first byte arriving is called time to first byte: about 170 ms here, before the server's own time.
  7. The browser renders. It parses the HTML into a tree, and as it reads, discovers more things it needs: stylesheets, scripts, images, fonts. It starts fetching them straight away and paints what it can while the rest loads.
  8. Extra requests. Each extra file is another HTTP request. These reuse the existing, already-encrypted connection (no new TCP or TLS cost), and with HTTP/2 or 3 many can be in flight at once. Files from other hosts (a font service, an analytics script) cost their own DNS lookup, TCP and TLS first. A typical page needs dozens of requests, which is why every saved round trip matters (chapter 13).

Look at the cold-start cost: about three round trips (TCP, TLS, request) plus one DNS lookup before the first byte of HTML. A repeat visit that reuses a connection and cached DNS skips the first three entirely, which is why the very first request to a site always feels slowest. Techniques like HTTP/3's combined handshake, TLS session resumption and CDNs that put servers close to you (shrinking that 50 ms) all attack exactly these delays.

Distributed systems connection

HTTP is the lingua franca between services, not only between browsers and sites. Inside a large company, hundreds of services call each other with HTTP requests (often carrying JSON; chapter 12). The ideas from this chapter then do real work:

  • Idempotency makes retries safe. Networks lose messages, and a caller that doesn't hear back can't tell whether the request or the reply was lost. If the method is idempotent (GET, PUT, DELETE), resending is harmless. For POST, systems add an idempotency key that lets the server recognise a duplicate. Chapter 16 builds on this.
  • Status codes are the error vocabulary. 429 Too Many Requests and 503 Service Unavailable mean "I'm overloaded, back off" (often with a Retry-After header). 504 Gateway Timeout and 502 Bad Gateway come from proxies and load balancers saying "the server behind me was too slow / broke". Retrying blindly and instantly against a struggling service makes it worse; good clients wait and back off.
  • Statelessness enables scaling out. Any server can handle any request, so capacity grows by adding machines and a dead one is simply skipped.
  • Caching and TTLs recur. max-age is DNS's TTL again: speed in exchange for bounded staleness.

Key takeaways

  • HTTP is request/response: the client speaks first; each request gets one response. In HTTP/1.1 both are readable text: a start line, headers, a blank line, an optional body.
  • A URL = scheme + host + port + path + query + fragment; the fragment never leaves the browser.
  • Methods carry meaning. Safe = read-only; idempotent = repeating has the same effect as doing it once. GET, PUT, DELETE are idempotent; POST is not.
  • Status classes: 2xx success, 3xx redirect, 4xx client error, 5xx server error.
  • HTTP is stateless; cookies add memory by returning a token the server can look up. Caching (Cache-Control, ETag, 304) avoids repeat downloads.
  • HTTP/1.1 suffers head-of-line blocking; HTTP/2 multiplexes streams on one TCP connection but still stalls on a lost packet; HTTP/3 uses QUIC over UDP so streams are independent.
  • A cold page load costs roughly DNS + TCP + TLS + request before the first byte, around three round trips to the server plus a lookup.

Check your understanding

A client sends the same PUT /users/7 request (with identical body) three times because it never saw a reply. What is the effect on the server?

  1. Three users are created
  2. The same final state as sending it once, because PUT is idempotent
  3. The server rejects the second and third with 500
  4. It depends on the browser
PUT means "make the resource at this URL look like this", so repeating it changes nothing further. That is exactly why idempotent methods are safe to retry. A POST /users, by contrast, could create three users.

A browser holds a cached copy of an image with ETag "abc" and revalidates it. The server replies 304 Not Modified. What happens?

  1. The browser deletes its copy
  2. The server sends the image again, but slowly
  3. The browser gets an error
  4. The browser keeps using its stored copy; no image body was transferred
304 means "your version is still current". The response has no body, so a possibly large download is replaced by a tiny exchange. If the image had changed, the server would have replied 200 with the new bytes.

Why can a single lost packet slow down every stream of an HTTP/2 page, but not of an HTTP/3 page?

  1. HTTP/2 streams share one TCP connection, which delivers bytes in strict order; HTTP/3's QUIC streams are delivered independently
  2. HTTP/3 never loses packets
  3. HTTP/2 uses text, which is slower to resend
  4. HTTP/3 doesn't use encryption
TCP can't hand over later bytes until the missing ones arrive, even if those later bytes belong to another stream. QUIC tracks loss per stream, so only the affected stream waits. Packets can still be lost in HTTP/3; it just copes better.

In what order do these happen when you load https://www.example.com/ from scratch?

  1. TCP handshake, DNS lookup, TLS handshake, HTTP request
  2. HTTP request, DNS lookup, TCP handshake, TLS handshake
  3. DNS lookup, TCP handshake, TLS handshake, HTTP request
  4. TLS handshake, DNS lookup, HTTP request, TCP handshake
You need an IP address before you can open a connection (DNS first); you need a TCP connection before TLS can run on top of it; and you want encryption in place before sending the request. (With HTTP/3, the TCP and TLS steps are merged into QUIC's handshake.)

A load balancer replies 504 to your request. What does that most likely mean?

  1. Your request was malformed
  2. The backend server it forwarded to didn't answer in time
  3. The page doesn't exist
  4. You must log in first
504 Gateway Timeout comes from an intermediary (proxy or gateway) that didn't get a timely response from the server behind it. A malformed request is 400, a missing page 404, and a login problem 401 or 403. Notice that you can't tell from a 504 whether the backend eventually performed the work, a theme of chapter 16.

HTTP is described as "stateless", yet you stay logged in to websites. How?

  1. The server keeps your TCP connection open forever
  2. The IP address identifies you
  3. The browser returns a cookie with each request, which the server uses to look up your session
  4. The Host header contains your username
Each request is still independent, but it carries a token (the cookie) that the server maps to a stored session. The state lives in the token plus the server's lookup table, not in the protocol.

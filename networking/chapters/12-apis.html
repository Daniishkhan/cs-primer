How Programs Talk: Sockets & APIs

You now know how a packet crosses the planet. This chapter climbs up to where you write code: how does a program actually send bytes to another machine, how do those bytes get turned back into meaningful data, and what are the different "styles" of conversation that real services use? It is the bridge between networking and distributed systems.

Why this matters

Every distributed system, from a two-service app to a global database, is built out of programs sending bytes to each other. Three ideas in this chapter bite engineers constantly: TCP is a stream with no message boundaries; data must be serialized into bytes in a way both sides agree on, even when they are deployed at different times; and a remote call is not a local call, however much the code makes it look like one.

The sockets API: what your program actually calls

In chapter 7 you met ports and the idea of a socket: one end of a conversation, identified by an IP address and a port. Now let's see it from the programmer's chair.

Your program does not build TCP segments, count sequence numbers or retransmit lost packets. All of that (chapter 8) lives inside the operating system's kernel. The kernel offers programs a small set of functions, the sockets API (invented at Berkeley in the early 1980s and copied by every operating system since), and your program just reads and writes bytes as if it were working with a file. The network is hidden behind that file-like interface: a perfect example of the abstraction layering from chapter 3.

A TCP conversation uses the same few calls in almost every language. The server and the client play different roles:

A complete echo server

Here is the smallest useful network program: a server that sends back whatever it receives. It's in Python because Python reads almost like English, but the same calls exist in C, Java, Go, Rust and the rest, with the same names and meanings. Save it as server.py:

import socket

HOST, PORT = "127.0.0.1", 9000          # 127.0.0.1 = "this computer only" (loopback)

# socket(): ask the OS for an endpoint. AF_INET = IPv4, SOCK_STREAM = TCP.
server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
# Let us restart quickly without "address already in use" errors.
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)

server.bind((HOST, PORT))                # bind(): claim this address and port number
server.listen()                          # listen(): mark it as a server socket
print(f"listening on {HOST}:{PORT}")

while True:
    # accept(): block until a client connects. Returns a NEW socket (conn)
    # dedicated to this one client, plus the client's address.
    conn, addr = server.accept()
    print("connection from", addr)
    with conn:                           # closes conn automatically at the end
        while True:
            data = conn.recv(4096)       # recv(): wait for up to 4096 bytes
            if not data:                  # empty bytes = the client closed its side
                break
            conn.sendall(data)           # send everything back to the client
    print("closed", addr)

Walk through what each call does:

  • socket() asks the kernel to create an endpoint. At this point it's not connected to anything. SOCK_STREAM means TCP; SOCK_DGRAM would be UDP (chapter 7).
  • bind() attaches the socket to an address and port, which says "I'm the program listening on 9000". Only one program at a time can own a given port, which is how the kernel knows where to deliver arriving packets (chapter 7).
  • listen() tells the kernel to start accepting incoming connections on this socket. From now on the kernel itself answers the TCP handshake for you and queues completed connections.
  • accept() takes one completed connection off that queue and gives you a new socket for talking to that particular client. The original "listening" socket stays behind, ready for the next visitor. If nobody has connected yet, accept() blocks: your program simply sleeps until someone does.
  • recv() and sendall() read and write bytes on the connection. recv() also blocks until something arrives. When the other side closes, it returns an empty bytes object, which is how you learn the conversation is over.

And the client

The client is shorter, because it doesn't have to wait for anyone. Save it as client.py:

import socket

# create_connection() = socket() + connect(): dial the server, doing the TCP handshake
with socket.create_connection(("127.0.0.1", 9000)) as s:
    s.sendall(b"hello, server")         # bytes, not text: note the b prefix
    reply = s.recv(4096)
    print("got:", reply)                # got: b'hello, server'

Notice what you did not write: nothing about IP headers, Ethernet, acknowledgements or retransmission. Also notice that in connect you gave an address, and in real programs you'd give a name like "example.com", which the library resolves with DNS (chapter 9) first. Every web request you've ever made, from a browser or a phone, bottoms out in these same calls.

Analogy: the telephone exchange

A server is a business with a phone number. socket buys the handset, bind registers the number, listen switches the line on, and accept is the receptionist picking up each ringing call and transferring it to a dedicated line, so the main number is free for the next caller. The client's connect is dialling. After that, both just talk (send, recv) until someone hangs up (close).

Where it breaks down: a phone call carries a continuous voice, and the other person decides what's a "sentence". TCP gives you a continuous stream of bytes in the same way, but with nobody in the middle to notice sentence boundaries, as the next section shows. Also, our simple server answers one caller at a time. Real servers handle thousands at once, using threads, processes or event loops.

A byte stream is not a sequence of messages

Here is the mistake almost every beginner makes. Suppose a client does two sends:

sock.sendall(b"HELLO")
sock.sendall(b"WORLD")

and the server calls recv() twice. What does it get? The tempting answer is b"HELLO" then b"WORLD". The honest answer is: it could be anything that concatenates to HELLOWORLD: HELLOWORLD in one go, or HELLOWO then RLD, or one byte at a time.

Why? TCP (chapter 8) cuts your data into segments to fit the network (the MTU, chapter 3), may combine small writes, and delivers bytes as they arrive. The receiving recv() hands over whatever is in the buffer right now, up to your limit. (UDP, by contrast, does preserve message boundaries: one datagram in, one datagram out. That is one of its few conveniences.)

Common misconception: "one send = one recv"

It often seems to work in testing: small messages on a quiet local machine usually arrive whole. Then in production a message is split across two reads, or two messages arrive glued together, and the program mysteriously breaks, intermittently and under load. Never assume a recv returns exactly one message. The cure is framing.

Framing: marking where messages begin and end

Since the stream doesn't carry boundaries, your protocol must. There are two classic approaches, both of which you have already seen:

  • Delimiters: end each message with a special marker the data can't contain. HTTP/1.1 headers end with a blank line; many text protocols use a newline.
  • Length prefix: start each message with its size, then read exactly that many bytes. HTTP bodies use Content-Length this way (chapter 10); most binary protocols put a 4-byte length in front.

Here is a length-prefix framing in a dozen lines. The helper recv_exactly keeps reading until it has all the bytes it wants, which is the loop you must always write yourself:

import struct

def recv_exactly(sock, n):
    """Read exactly n bytes, however many recv() calls it takes."""
    buf = b""
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk:
            raise ConnectionError("peer closed mid-message")
        buf += chunk
    return buf

def send_msg(sock, payload):
    # 4-byte big-endian length ("!I"), then the payload itself
    sock.sendall(struct.pack("!I", len(payload)) + payload)

def recv_msg(sock):
    (length,) = struct.unpack("!I", recv_exactly(sock, 4))   # read the 4-byte header
    return recv_exactly(sock, length)                           # then exactly that many bytes

With these, send_msg(sock, b"HELLO") followed by send_msg(sock, b"WORLD") always produces exactly two recv_msg results, b"HELLO" and b"WORLD", however the network chops them up. (The "!" means "network byte order": agreeing on which end of a number comes first is part of the protocol, too. A real server would also reject absurdly large lengths.) Note the error case: if the connection dies halfway through a message, you learn it, instead of silently acting on half a message.

Serialization: from data structures to bytes

Your program holds structures: objects, lists, dictionaries with numbers and strings. A socket only moves bytes. Serialization (or marshalling) is the translation from structure to bytes on the sending side; deserialization is the reverse. You can't just copy the program's memory across: different languages, CPUs and program versions lay data out differently, and memory is full of pointers that mean nothing on another machine. Both sides need an agreed wire format.

The two families you'll meet most:

JSON: text, human-readable

{"id":150,"name":"Ada","admin":true}

36 bytes. Self-describing: field names travel with every message. You can read it, debug it with curl, and every language parses it. Costs: bigger, slower to parse, and no enforced types.

Protocol Buffers: binary, schema-first

message User {
  int32  id    = 1;
  string name  = 2;
  bool   admin = 3;
}

10 bytes on the wire (below). Compact and fast, with types checked by a generated parser. Costs: unreadable without the schema and tooling.

Here is that same user encoded as Protocol Buffers. Each value is preceded by a tag byte that carries the field number from the schema, so no field names are sent at all:

08field 1, number
96 01150
12field 2, text
03length 3
41 64 61"Ada"
18field 3, flag
01true

(The number 150 takes two bytes because Protocol Buffers uses a compact "varint" encoding: small numbers take fewer bytes.) Neither format is "better"; they trade readability for efficiency. Public APIs favour JSON because anyone can use it with no tooling; high-volume internal calls often favour binary formats. In Python, JSON is two functions:

import json
user = {"id": 150, "name": "Ada", "admin": True}
wire = json.dumps(user, separators=(",", ":")).encode("utf-8")   # structure -> bytes
back = json.loads(wire.decode("utf-8"))                               # bytes -> structure

Schema evolution: the sender and receiver aren't updated together

In a distributed system, services are deployed independently. At 3 p.m. the "users" service may be on version 7 while its callers are still on version 6. Messages must therefore survive mismatched versions. Rules of thumb:

  • Adding an optional field is safe if old readers ignore fields they don't know (both JSON-with-tolerant-parsers and Protocol Buffers allow this).
  • Removing or renaming a field breaks anyone still relying on it. Deprecate first, remove much later.
  • Never reuse a Protocol Buffers field number for a different meaning: old data would be misread as the new thing. Retire the number instead.
  • Be strict in what you send and tolerant in what you receive.

API styles: what shape should the conversation have?

An API (application programming interface) is the agreed menu of requests one program offers another. Over a network, a few styles dominate.

REST: resources and HTTP methods

REST models a service as resources (nouns) with URLs, manipulated by the HTTP methods from chapter 10. GET /orders/42 reads order 42, PUT /orders/42 replaces it, DELETE /orders/42 removes it, POST /orders creates a new one; status codes report the result; data is usually JSON. It's simple, cacheable (GET is safe), stateless (so it scales behind load balancers) and works with every tool that speaks HTTP. That's why most public web APIs look like this.

RPC: call a function on another machine

With RPC (remote procedure call) you think in verbs rather than resources: CreateOrder(customer, items). A framework generates the code that serializes arguments, sends them, waits and deserializes the result, so calling a remote service looks like calling a normal function. gRPC is a popular modern version: you describe functions and messages in a Protocol Buffers schema and it generates client and server code, using HTTP/2 (chapter 10) underneath for multiplexing and streaming. It's efficient and type-safe, and a favourite for calls between internal services.

The danger of RPC: a remote call is not a local call

RPC's great strength, hiding the network, is also its trap. A local function call either returns or throws, and takes microseconds. A remote call can additionally: be slow, never return, fail after doing the work, or do the work twice if retried. Your code looks identical but lives in a different universe. Treat every remote call as something that may fail or hang, give it a timeout, and decide what to do when you don't know the outcome. Chapters 15 and 16 are largely about this.

WebSockets and other ways to push

Plain HTTP is request/response: the server can only speak when spoken to. For chat, live scores or collaborative editing you want the server to send news the moment it happens. Options:

  • Polling: the client asks "anything new?" every few seconds. Dead simple; wasteful and laggy.
  • Long polling: the client asks, and the server holds the request open until there is news (or a timeout), then the client immediately asks again.
  • Server-Sent Events (SSE): one long-lived HTTP response through which the server streams events one way, to the client.
  • WebSocket: the client starts with a normal HTTP request asking to "upgrade" (the server answers 101 Switching Protocols), and then the same TCP connection becomes a free, two-way message channel that either side can use at any time.

Synchronous versus asynchronous

Everything above is synchronous: you send a request and wait for the answer, so the caller's progress depends on the callee being up right now. If service A calls B, which calls C, which calls D, then A is only as available as all four combined, and as slow as the slowest.

The alternative is asynchronous messaging: A drops a message into a queue (a durable waiting line run by a broker) and carries on. B picks it up whenever it's ready, maybe milliseconds later or hours later if it was down. The two are decoupled in time. It trades immediate answers for resilience and smoothing of traffic spikes, at the cost of more moving parts and harder reasoning ("did it run yet?"). You'll meet queues and logs properly in chapter 21; for now remember the question to ask of any interaction: must the caller wait for the answer?

Try it yourself

Run your own network server

You need Python 3 (preinstalled on most Macs and Linux machines; on Windows install it from python.org and use python instead of python3). Save the two programs above as server.py and client.py in a folder, and open two terminal windows there. Everything stays on your own computer (127.0.0.1), and no administrator rights are needed.

$ python3 server.py
listening on 127.0.0.1:9000             # it now sits inside accept(), blocked
$ python3 client.py
got: b'hello, server'

Back in terminal 1 you will see connection from ('127.0.0.1', 51734) followed by closed. The number 51734 is the client's ephemeral port, picked by the OS (chapter 7). Now talk to the server by hand with nc (netcat), a tool that opens a TCP connection and connects it to your keyboard and screen. It's built into macOS and most Linux systems; on Windows use ncat from the Nmap package, or just rely on client.py:

$ nc localhost 9000
hi there                       # you type this line and press Enter
hi there                       # the server echoed it back
is anyone listening?
is anyone listening?
^C   (press Ctrl-C to hang up)

Experiments worth trying:

  • While nc is still connected, run python3 client.py in a third terminal. It just hangs! Our server handles one client at a time and is busy inside the first conversation. The kernel has already completed the TCP handshake and queued the connection (that's listen()), but accept() hasn't been called for it yet. Hang up nc and the client instantly gets its reply. (Real servers use threads, processes or event loops to serve many clients at once.)
  • See the listening socket from the outside: lsof -nP -iTCP:9000 on macOS/Linux (on Windows: netstat -an | findstr 9000) shows the Python process in state LISTEN.
  • Stop the server, run the client, and read the error: ConnectionRefusedError. Nothing was listening on that port, so the kernel sent back a TCP reset (chapter 8).

Now call a real, public API with curl. GitHub's API describes the CPython repository as JSON:

$ curl -s https://api.github.com/repos/python/cpython | head -n 14
{
  "id": 81598961,
  "name": "cpython",
  "full_name": "python/cpython",
  "private": false,
  "owner": {
    "login": "python",
    "type": "Organization",
    ...
  },
  "html_url": "https://github.com/python/cpython",
  "description": "The Python programming language",
  ...

This is REST in action: the URL names a resource (/repos/python/cpython), the method is GET, and the response body is JSON with nested objects (owner is an object inside the object). Many more fields follow, such as stargazers_count, language and default_branch; counts and dates will be different when you run it. Pipe the output into python3 -m json.tool to pretty-print it, and look at the headers too:

$ curl -sI https://api.github.com/repos/python/cpython | grep -i -E "^(http|content-type|x-ratelimit)"
HTTP/2 200
content-type: application/json; charset=utf-8
x-ratelimit-limit: 60                  # anonymous callers get a small quota per hour
x-ratelimit-remaining: 57

That quota is the server protecting itself from overload; exceed it and you'll see a 403 or 429 status, exactly the kind of overload signal from chapter 10.

Distributed systems connection

Every distributed system is built from the calls in this chapter, so the lessons transfer directly:

  • A remote call has three outcomes, not two. It can succeed, it can fail (you get an error and know it didn't complete), or you can get nothing: a timeout. In the third case you do not know whether the server did the work, did half of it, or never received the request. Most of chapter 16 is about living with that "unknown".
  • Framing and partial reads are failure modes. A connection that dies mid-message is routine, and a protocol that can't detect half a message will eventually corrupt data.
  • Serialization and versioning decide whether you can deploy safely. Services roll out independently, so old and new versions talk to each other constantly. Formats that tolerate unknown fields, and the discipline of never changing the meaning of a field, are what allow upgrades without a "flag day" when everything must change at once.
  • Choose sync or async on purpose. Chains of synchronous calls multiply latency and fragility; queues break the chain (chapter 21).

Key takeaways

  • Programs use the sockets API (socket, bind, listen, accept, connect, send, recv, close); the OS kernel runs TCP/IP and the program just reads and writes bytes.
  • TCP is a byte stream with no message boundaries: one send may become several recvs and vice versa. Use framing (delimiters or length prefixes) and loop until you have all the bytes.
  • Serialization turns structures into bytes: JSON is readable and universal; binary formats like Protocol Buffers are compact and schema-driven.
  • Services upgrade at different times, so formats must tolerate schema evolution: add optional fields freely, never change a field's meaning.
  • REST = resources + HTTP methods; RPC/gRPC = remote function calls; WebSockets/SSE let servers push data.
  • A remote call is not a local call: it can be slow, fail, or leave you not knowing whether it happened.
  • Asynchronous messaging (queues) decouples caller and callee in time, trading immediacy for resilience.

Check your understanding

A client calls send() twice, with 100 bytes each time. The server calls recv(4096) on a TCP connection. Which result is NOT possible?

  1. 200 bytes in a single recv
  2. One recv of 60 bytes, then later 140 bytes
  3. The bytes arrive out of order, with the second send's data first
  4. 100 bytes, then 100 bytes
TCP preserves the order of bytes, but not the grouping. The receiver may get the data in any chunking, including merged or split. Reordering of bytes within the stream can't happen, because TCP puts them in order before handing them to you.

What does accept() return on a server?

  1. A new socket for one specific client connection, plus that client's address
  2. The server's own listening socket, again
  3. The next message from any client
  4. A list of every client currently connected
The listening socket only exists to receive new connections. Each accept() produces a dedicated per-client socket, which is why the listening socket can go on accepting others.

Why is a length prefix useful in a binary protocol over TCP?

  1. It encrypts the message
  2. It makes TCP deliver messages faster
  3. It makes the OS preserve message boundaries
  4. It tells the receiver exactly how many bytes to read to get one complete message
The receiver reads the fixed-size length first, then loops until it has that many bytes. The OS and TCP still don't know about messages; the protocol layered on top reconstructs the boundaries.

Service A (new version) starts sending an extra optional field nickname to service B (old version, not updated yet). What should happen if the format and parser are designed for schema evolution?

  1. B crashes, since it doesn't know the field
  2. B ignores the field it doesn't know and keeps working
  3. B must be restarted at exactly the same time as A
  4. The network rejects the message
Tolerance for unknown fields is what makes adding fields a safe, backward-compatible change and allows services to be upgraded one at a time. Protocol Buffers and well-written JSON consumers behave this way.

Your service calls a payment service over RPC to charge a card. The call times out after 5 seconds with no reply. What is the correct way to think about the outcome?

  1. The charge definitely failed, so retry immediately
  2. The charge definitely succeeded, so don't retry
  3. It is unknown: the request may have been lost, may still be running, or may have completed with the reply lost, so you need a way (such as an idempotency key or a status lookup) to find out safely
  4. Timeouts can't happen over TCP
A timeout tells you only that you didn't hear back. The server might have never received the request, be mid-way through it, or have finished it while the reply was lost. This "unknown" outcome is the core difficulty of remote calls, and the subject of chapter 16.

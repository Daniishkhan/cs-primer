Proxies, Load Balancers & CDNs

Big websites are not one computer. They are a crowd of identical machines, with a few clever ones standing in front, deciding who talks to whom. Meet the machines in the middle: proxies, load balancers and CDNs.

Why this matters

Almost every request to a large service passes through at least one of these boxes before it reaches code that does real work. They are how a site survives a crowd, how it survives a dead machine, and how a page in Sydney can load quickly from a company based in California. They are also the simplest example of the central trick of scaling: many cheap copies instead of one giant machine.

A machine in the middle: proxies

A proxy is a server that sits between a client and another server and passes messages along on someone's behalf. Because it sees the traffic pass through, it can do useful things on the way. There are two flavours, and the difference is simply whose side the proxy is on.

Analogy: assistant vs. receptionist

A forward proxy is like a personal assistant who makes phone calls for you: the person at the other end sees the assistant's number, not yours, and the assistant might refuse to call certain numbers. A reverse proxy is the receptionist at a company's front desk: callers ask for “the company”, and the receptionist decides which department actually handles the call, screens out cranks, and never gives out anyone's direct line.

Where it breaks down: a human receptionist handles one call at a time. A reverse proxy handles tens of thousands at once, and it can also keep a copy of popular answers so it doesn't have to ask the departments at all.

Forward proxies are mostly used inside organisations (to filter websites, cache downloads, or give many private machines one public address) and by privacy tools. In this chapter we care mostly about reverse proxies, because they are the front door of nearly every large service. Well-known software includes nginx, HAProxy and Envoy, and every cloud provider offers managed ones.

Why put a machine in the middle?

Hide and protect

Real servers live on private addresses (chapter 4) and only the proxy is exposed. It can drop malformed requests, rate-limit abusers and absorb floods before they hit your code.

TLS termination

The proxy does the expensive encryption work (chapter 11) and holds the certificate in one place. Traffic to the servers behind it may be plain HTTP inside a trusted network, or re-encrypted.

Caching

If a thousand people ask for the same logo, fetch it once and serve the copy. This is chapter 13's cheapest latency win.

Compression

Shrink text responses (gzip, Brotli) in one place so every backend doesn't have to.

Routing

One public name, many internal services: /api goes to the API servers, /images to the media servers, / to the web app.

Spreading load

Hand each request to one of several identical servers. That is a load balancer, our next topic.

One side effect to remember

Behind a proxy, the backend sees the proxy's IP address as the sender. To recover the real client address, proxies add a header such as X-Forwarded-For (or the standardised Forwarded) to the HTTP request. Logs and rate-limiters on the backend must read that header, not the TCP source address.

Load balancing: one server is never enough

Suppose your site runs on a single server. It has two big problems:

  1. Capacity. One machine has finite CPU, memory and network. When traffic outgrows it, everyone gets slow (remember the queueing hockey stick in chapter 13).
  2. It's a single point of failure. If that one machine crashes, reboots for an update, or loses its network cable, your site is completely down.

The cure for both is to run many identical copies of the server, and put a load balancer in front: a reverse proxy whose job is to choose which copy handles each request. Add capacity by adding servers (horizontal scaling, more on this in chapter 15); survive a failure because the others keep working.

Analogy: the supermarket floor manager

Picture a store with eight checkouts and one manager at the entrance pointing each arriving customer to a till: “number 3”, “number 6”. A good manager avoids sending people to a closed till, and tries to even out the lines. If a till's light goes out mid-day, the manager just stops sending anyone there.

Where it breaks down: real customers know how long each line is by looking. A balancer must infer which server is busy or broken from limited information, and it can be wrong.

Layer 4 vs layer 7

Remember the layers from chapter 3? A load balancer can work at different ones, and what it can see determines what it can decide.

Layer 4 (transport)Layer 7 (application)
Decides usingIP addresses and portsURL path, host name, headers, cookies, method
Unit it spreadsTCP connections (or UDP flows)Individual HTTP requests
Needs TLS keys?No, it can pass encrypted bytes straight throughYes, it must decrypt to read the request (TLS termination)
CostVery cheap, huge throughputMore CPU, but far more flexible
Typical useDatabases, game servers, raw TCP, the first tier in front of L7 balancersWebsites and APIs: path routing, A/B tests, canary releases, auth

One subtle trap: because a layer-4 balancer chooses per connection, a client that opens one long-lived connection (as HTTP/2 and gRPC clients do) and sends thousands of requests down it will keep hitting the same backend. The connection count looks balanced; the work isn't. A layer-7 balancer, which sees every request, doesn't have this problem.

Choosing a server: algorithms

AlgorithmHow it picksGood when…Weakness
Round robin1, 2, 3, 4, 1, 2, … in a fixed cycleRequests cost about the same; servers are identicalIgnores how busy each server actually is: a few slow requests can pile up on one unlucky server
Weighted round robinSame cycle, but bigger servers appear more often (weight 3 gets 3× the share)Mixed hardware, or gradually shifting traffic to a new versionStill blind to current load
Least connectionsSend to the server with the fewest requests in progress right nowRequest durations vary a lotNeeds to track state; a newly added or dead server shows few connections and attracts traffic
HashingHash something stable (client IP, a cookie, a user ID) to choose a serverThe same client should keep reaching the same server (“sticky”)Adding or removing a server reshuffles many clients; uneven if a few clients are heavy

Sticky sessions (also called session affinity) means the balancer remembers, by cookie or by hash, that a particular user's requests should keep going to the same server. People use it when a server keeps per-user data in its own memory. It works, but it undermines the whole point: if that server dies, those users lose their data, and heavy users can overload one machine. We'll see below why stateless servers are better.

Naive hashing (“server = hash(key) mod number-of-servers”) has an ugly flaw: when the server count changes from 4 to 5, almost every key maps to a different server. There is a clever fix called consistent hashing that moves only a small fraction of keys; it matters enormously for caches and databases, and we'll build it up in chapter 19.

Go deeper: “power of two choices” optional

Least-connections needs an accurate, up-to-date count from every server, which is hard when you have many balancers. A surprisingly effective shortcut: pick two servers at random and send the request to whichever of the two is less loaded. This simple rule gets you nearly the benefit of checking all servers, with far less coordination, and it is used in real systems.

Health checks: noticing the dead

A balancer that keeps sending requests to a crashed server is worse than useless. So balancers run health checks:

  • Active checks: every few seconds the balancer probes each server (a TCP connect, or GET /health expecting a 200). After, say, 2 or 3 failures in a row, it marks the server unhealthy and stops sending it traffic. After a few successes, it brings the server back.
  • Passive checks: the balancer watches real traffic and notices connection errors or a burst of 5xx responses.
  • Draining: when you deploy a new version, the balancer stops sending new requests to a server but lets in-flight ones finish, so users don't see errors.

Notice the inevitable gap: a server can crash between two health checks, and the balancer keeps sending it traffic until the next failures accumulate. Failure detection always takes time (more in chapter 16). Try it in the simulator below.

Two things worth noticing. With round robin, an unlucky server sometimes collects several slow requests while another sits nearly idle, and least-connections smooths that out. But when a server dies, least-connections briefly makes things worse: a dead server has zero active connections, so it looks like the least busy machine, and it attracts the traffic until health checks catch up. Real balancers combine algorithms with fast failure detection (and often retries to a different server) for exactly this reason.

Who balances the balancer?

We removed one single point of failure and created another: if the one load balancer dies, everything behind it is unreachable. The balancer must itself be redundant. Common approaches:

  • An active/passive pair. Two balancers share a floating IP address. The standby watches the active one with heartbeats; if it goes silent, the standby claims the IP and takes over within seconds.
  • Several active balancers behind DNS. One name returns multiple IP addresses (chapter 9), each a balancer. Clients spread themselves across them, and if one fails, DNS stops returning it (limited by TTLs, which is the same trade-off we saw before).
  • Anycast. The same IP address is announced from many places at once, and the routing system (chapter 5) delivers each packet to the “nearest” one. If one location disappears, its announcement vanishes and traffic flows to the next-nearest.

Big cloud load balancers are in fact entire distributed systems with many nodes; the “one box” is an illusion.

CDNs: caching close to the user

Chapter 13 ended with a hard fact: a round trip across an ocean costs ~100 ms and you can't buy your way out of physics. The remedy is to move the data. A content delivery network (CDN) is a worldwide fleet of cache servers, called edge servers (located at points of presence, POPs) in hundreds of cities, run on behalf of website owners.

How the cycle works for a file like logo.png:

  1. The first user near an edge asks for it. The edge doesn't have it (a cache miss), so it fetches from the origin over a long distance, keeps a copy, and forwards it to the user. This first request is no faster than going direct.
  2. Everyone else near that edge now gets the copy straight from the edge (a cache hit) in a few milliseconds. The origin never hears about it.
  3. The copy isn't kept forever. The origin attaches a TTL (time to live) with headers like Cache-Control: max-age=3600, meaning “this is fresh for an hour”. After that the edge re-checks or re-fetches.

CDNs also soak up traffic spikes and attacks (the origin sees a trickle), terminate TLS close to the user so handshake round trips are short, and hide the origin's address. They shine for static content (images, scripts, video segments, downloads), which is the majority of the bytes on the web. Personalised or frequently changing responses can't be cached as widely, but even those benefit from the edge's fast TLS and warm long-distance connections to the origin.

Invalidation: the hard part

What if you change logo.png now? Edges around the world still hold the old copy for up to its TTL. Sound familiar? It is exactly the DNS TTL trade-off from chapter 9:

  • Long TTL: high hit rate, low load on origin, but updates take a long time to appear.
  • Short TTL: content stays fresh, but more misses and more load.
  • Purge: most CDNs offer an API to tell edges “forget this URL now”. It works but takes seconds to spread, and it's a distributed operation that can partly fail.
  • Versioned URLs: the favourite trick. Instead of changing app.js, publish app.3f9a2c.js with a hash of the contents in the name. Give old and new URLs a very long TTL. To “update”, the page just points at a new URL; nothing needs invalidating.
Go deeper: how does a user reach the “nearest” edge? optional

Two main techniques, often combined. DNS-based steering: the CDN's DNS servers return different IP addresses depending on where the question seems to come from (usually the location of your resolver), so a user in Tokyo gets a Tokyo edge's address. Anycast: every edge location announces the same IP address into the global routing system, and the ordinary routing rules (chapter 5) deliver your packets to whichever announcement is closest in network terms. Anycast also gives automatic failover and spreads attack traffic across many sites. “Closest” here means fewest routing hops or best routing policy, which is not always the lowest latency, so operators tune it.

Try it yourself

Spot the machines in the middle

curl -I sends a HEAD request, asking for just the response headers. It is safe and read-only. Try it on https://www.example.com, then on a large site you use every day. Read through the headers, looking for ones that reveal a proxy or CDN. Header names vary by provider, so you'll be comparing clues rather than finding a standard list.

$ curl -sI https://www.example.com
HTTP/2 200
content-type: text/html
server: ECAcc (example/1234)             # names the front-end software (here a CDN's)
age: 417219                              # seconds this copy has sat in a cache
cache-control: max-age=604800               # fresh for a week
x-cache: HIT                              # served from a cache, not the origin
...

That output is illustrative: the exact headers and values you see will differ. Things to look for:

  • server: often the name of a proxy or CDN (nginx, cloudflare, AmazonS3, a custom name) rather than the real application.
  • via: a standard header listing each proxy the request went through (e.g. 1.1 varnish).
  • age: how long, in seconds, the cached copy has been held. If it's present and non-zero, a cache answered you.
  • x-cache, cf-cache-status, x-served-by, x-amz-cf-pop: provider-specific hit/miss and location hints (cf is Cloudflare's prefix; amz-cf is Amazon CloudFront's). Not every site shows them.

Run the same command twice in a row. A site behind a CDN will often show MISS or a small age the first time and HIT with a growing age afterwards.

Now see DNS steering. Ask two different public resolvers for the same big site's address:

$ dig +short www.wikipedia.org @8.8.8.8      # Windows: nslookup www.wikipedia.org 8.8.8.8
203.0.113.34
$ dig +short www.wikipedia.org @1.1.1.1
198.51.100.34

(The addresses above are placeholders from the documentation ranges; real answers will be other numbers.) You may get the same address from both, or different ones: the answer often depends on where the resolver sits, and large providers hand out many addresses. Compare ping times to each address and see which is closer. You are seeing a CDN or load balancer decide on your behalf.

Distributed systems connection

The easiest way to scale is to make servers stateless: a server keeps nothing between requests that another server couldn't recreate. Then any request can go to any server, the balancer needs no stickiness, a dead server loses nothing, and capacity is just “how many copies are running”. All the hard parts don't vanish; they move into the state: the databases, caches and queues that the stateless servers talk to. Once data lives on more than one machine you must decide how copies stay in sync, what happens when machines disagree, and how to split data across machines. That is exactly where Part 6 begins, in chapter 15.

Key takeaways

  • A forward proxy acts for clients; a reverse proxy acts for servers. Reverse proxies terminate TLS, cache, compress, route and protect.
  • A load balancer spreads requests over identical servers for capacity and for survival of failures.
  • L4 balancers route by IP and port per connection (fast, simple); L7 balancers read HTTP and route per request (flexible).
  • Algorithms: round robin, weighted, least connections, hashing (sticky). Each fits some workloads and fails others.
  • Health checks remove dead servers, but there is always a detection delay. The balancer must itself be redundant (pairs, DNS, anycast).
  • A CDN caches content on edge servers near users; hits are fast, misses go to the origin, TTLs control freshness, and versioned filenames sidestep invalidation.
  • Stateless servers behind a balancer scale simply; state is the hard part, and it is where distributed systems begin.

Check your understanding

Which statement best distinguishes a reverse proxy from a forward proxy?

  1. A reverse proxy runs on the client's computer
  2. A reverse proxy acts on behalf of servers; a forward proxy acts on behalf of clients
  3. A reverse proxy encrypts traffic; a forward proxy does not
  4. A reverse proxy only works with UDP
The difference is whose side the proxy is on. A forward proxy hides and serves clients (for example an office network); a reverse proxy sits in front of servers, and visitors typically do not know it is there.

You want requests for /api/* to go to one pool of servers and /images/* to another. What do you need?

  1. A layer 2 switch
  2. A layer 4 load balancer with round robin
  3. A bigger server
  4. A layer 7 load balancer that reads the HTTP request
The URL path lives inside the HTTP request, which only a layer 7 device reads. A layer 4 balancer sees just IP addresses and ports, so it cannot tell the two kinds of request apart.

Why can least-connections briefly send more traffic to a server that has just crashed?

  1. The dead server shows zero active connections, so it looks the least loaded until health checks mark it down
  2. Crashed servers get a higher weight
  3. Least-connections ignores health checks forever
  4. The crashed server has many connections
Balancers learn about failure only through checks or errors, which takes time. In the gap, an empty (dead) server looks perfect to a least-connections rule. This is why fast detection and retries to another server matter.

A site publishes a new style.css but users keep seeing the old one for an hour. What is the most likely cause, and best fix?

  1. The browser has a virus; reinstall it
  2. DNS is broken; flush the resolver
  3. A cache (edge or browser) is still within the old file's TTL; use a versioned filename such as style.3f9a2c.css or purge it
  4. The load balancer algorithm is wrong; switch to round robin
Cached copies stay valid until their TTL expires. Versioned URLs make every update a brand-new URL that no cache has seen, so nothing needs invalidating. Purging also works but must reach every edge.

Why are stateless servers easier to scale behind a load balancer?

  1. They use less memory
  2. Any server can handle any request, so no stickiness is needed and a dead server loses nothing
  3. They never crash
  4. They don't need health checks
If a server keeps nothing between requests that others can't recreate, the balancer is free to send each request anywhere, and servers can be added or removed at will. The state still has to live somewhere, which is why databases become the hard part.

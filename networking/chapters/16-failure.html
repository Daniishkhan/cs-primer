Failure, Timeouts & Retries

You sent a request and nothing came back. Is the server dead, or just slow? Is it safe to try again? This chapter is the working engineer's answer: timeouts to give up, backoff to retry politely, idempotency to make retrying safe, and a classic puzzle that proves certainty is out of reach.

Why this matters

Last chapter ended on a dilemma: after a timeout, retrying might charge a customer twice, and not retrying might lose their order. The techniques here (timeouts, exponential backoff with jitter, idempotency keys, deduplication) are in practically every production service, payment API and message queue. They are also the difference between a system that shrugs off a blip and one that turns a small blip into an hour-long outage.

Slow or dead? You can't tell

From a client's perspective, a server that has crashed, a server that is overloaded, a network link that is down and a network link that is merely congested all produce exactly the same observation: no reply yet. There is no way to look inside the other machine. All you can do is wait, and the one tool you have for ending the wait is the timeout: “if nothing arrives within T, assume it failed and do something else.”

A timeout is therefore not a measurement of failure. It is a guess about failure, which will sometimes be wrong. Choosing T is a trade-off between two kinds of mistake:

How to pick a number

  • Measure first. Look at the latency distribution of the healthy system (chapter 13). A common rule of thumb is to set the timeout comfortably above a high percentile, such as p99 or p99.9, so only genuinely abnormal requests trip it. Guessing a round number like “30 seconds” is how you get either false alarms or hung threads.
  • Use separate timeouts for separate phases. A connect timeout (establishing TCP and TLS, which should take only a few round trips) can be much shorter than an overall timeout (which includes server processing).
  • Always have one. Many libraries default to no timeout at all, which means “wait forever”. One hung dependency can then tie up every thread in your server (Little's Law again) and take you down with it.
  • Pass a deadline down the chain. If the user's request has a 2-second budget and 800 ms are already used, the next service should be told it has 1.2 seconds, not its own fresh 2. Otherwise you do work nobody is waiting for any more.

Common misconception: a timeout means the operation failed

It means you stopped waiting. The operation may well have completed, may be completing right now, or may complete after you've moved on. This is why timeouts must be paired with idempotent operations (below): giving up on a request does not undo it.

Failure detection: who is alive?

A client only needs to know whether its request failed. But a cluster has to answer a bigger question continuously: which of my peers are alive? Who is the leader? Which replica should take over? The usual approach is the heartbeat: every node sends a small “I'm alive” message to its peers (or to a monitor) at a regular interval, say once per second. If no heartbeat arrives for several intervals, the node is suspected to have failed.

Two trade-offs are built in. A longer timeout means fewer false alarms but slower recovery; a shorter one reacts quickly but wrongly accuses nodes that are momentarily slow (a long garbage-collection pause, a busy network). Wrongly declaring a node dead can itself be harmful: other nodes start copying its data, elect a new leader, and then the “dead” node wakes up and carries on as if nothing happened. We'll deal with that in later chapters (chapter 20 introduces terms and fencing for exactly this).

Why can't we just build a perfect detector? Intuitively: in an asynchronous network, where messages can be delayed by any amount with no upper bound, a message that hasn't arrived yet might still be on its way. Whatever deadline you pick, there's a possible world where the node is alive and its message is simply slower than your deadline. So a detector must either risk false accusations or risk never noticing a real crash. Theory papers formalise this (the famous FLP result, chapter 20, builds on the same uncertainty), and the practical consequence is that every real detector is a heuristic that is occasionally wrong.

Go deeper: the phi accrual failure detector optional

Instead of a yes/no timeout, an accrual failure detector outputs a continuous suspicion level φ ("phi"). It keeps a history of how long heartbeats usually take to arrive. When a heartbeat is late, it asks: given this history, how unusual is a gap this long? The more improbable the silence, the higher φ climbs (roughly, φ = 1 means about a 10% chance the delay is normal, φ = 2 about 1%, and so on). Each application chooses its own threshold: a database might act at φ = 8, a UI at φ = 3. The detector adapts automatically to a jittery network instead of using one fixed number. Introduced in a 2004 paper by Hayashibara and colleagues, it is used in systems such as Cassandra and Akka.

Retries: necessary and dangerous

Many failures are transient: a dropped packet, a server restarting, a leader election in progress, a brief overload. Trying again a moment later often succeeds, so retries are an essential tool. But a naive retry loop is one of the most reliable ways to destroy a struggling service.

Analogy: redialling a busy phone line

If a friend's line is busy, you wait a bit and redial. Now imagine a thousand people trying to reach the same radio station phone-in. All get a busy tone, and all immediately redial, again and again. The exchange is hammered with calls, and almost nobody gets through, and the ones who would have succeeded are drowned by the noise from the retries. Politeness (waiting longer each time, and waiting a different amount than everyone else) fixes it.

Where it breaks down: people naturally vary how long they wait. Computers started at the same moment running identical code will wait exactly the same time, which is what makes the problem so much worse.

Retry storms

Suppose a service that normally handles 1,000 requests per second is overloaded and starts failing some of them. If every client retries up to three times immediately, the offered load becomes up to 4,000 requests per second, just when the service is least able to cope. It gets slower, more requests time out, more retries are sent, and the service never recovers even after the original trigger is gone. This is a retry storm (a cousin of the thundering herd, where many clients wake and act at the same instant).

It gets worse with layers. If a user request passes through three services, and each layer makes up to 3 attempts, a failure at the bottom can trigger 3 × 3 × 3 = 27 calls to the failing component for a single user click. Retries multiply.

Exponential backoff and jitter

Two ideas tame the storm:

  • Exponential backoff: wait longer after each failure, doubling each time (for example 1 s, 2 s, 4 s, 8 s), up to a cap. Early retries are quick for blips; persistent trouble causes clients to back off and give the server room to recover.
  • Jitter: add randomness. Instead of waiting exactly 4 s, wait a random time between, say, 0 and 4 s (“full jitter”). Without jitter, clients that failed together retry together, in synchronised waves that hit the server like a battering ram. Jitter spreads them out into a steady trickle.

What to notice. With a fixed delay, the whole herd retries together every few slots: a huge number of wasted requests, and the retry wave is as tall as the number of clients still waiting. With exponential backoff and no jitter, the waves are rarer but still synchronised: clients stay locked in step, so each wave is just as tall, and the stragglers wait a very long time. (The slots-to-finish column is mostly set by server capacity here; the real gain of jitter is lower load and fewer wasted attempts.)

More retry hygiene

  • Only retry what's retryable. A timeout, a connection reset, or a 503 or 429 response (“try later”, often with a Retry-After header) is worth retrying. A 400 (“your request is malformed”) or 404 will fail identically forever.
  • Limit attempts. Give up after a small number (3 to 5), and report failure to whoever called you.
  • Use a retry budget. A cap on retries as a fraction of normal traffic, for example “no more than 10% of requests may be retries”. During an outage, retries are cut off instead of tripling the load.
  • Retry at one layer. If every layer retries, they multiply (the 27× above). Pick the layer closest to the user, or the one that can see the whole picture.
  • Use a circuit breaker. When a dependency has failed many times in a row, stop calling it for a while (“open the circuit”) and fail fast, then cautiously let a single trial request through to test whether it has recovered. It's like the fuse box in a house: cut the power to protect everything else. We return to this pattern in chapter 21.

Idempotency: making retries safe

Retries are only safe if repeating an operation does no extra harm. An operation is idempotent if doing it twice has the same effect as doing it once. The word comes from mathematics: pressing a lift's “call” button again doesn't summon a second lift.

Idempotent (safe to repeat)Not idempotent (repeating changes the outcome)
set balance = 50add 10 to balance
“Set the thermostat to 21°”“Turn the thermostat up by 1°”
Delete order #812Create a new order (each call makes another)
HTTP GET, PUT, DELETEHTTP POST (typically “create” or “do something”)

Remember HTTP's methods from chapter 10: PUT /users/42 with a full replacement document sets the resource to a specific state, so sending it twice leaves the same state. POST /payments asks the server to create something new, so sending it twice may create two. (Idempotent doesn't mean the response is identical: a second DELETE may return 404 “already gone” while leaving the server in the same state.)

The first design rule is to phrase operations as desired state (“the balance is 50”, “the file contains these bytes”) rather than as deltas (“add 10”) wherever you can. But some operations are inherently deltas: charging a card, sending an email, appending to a log. For those we make them idempotent artificially, with an idempotency key.

Idempotency keys and deduplication

The client generates a unique identifier (a random UUID) for each logical operation, and sends the same key on every attempt of that operation. The server remembers keys it has already processed, together with the result. If a request arrives with a key it has seen, it returns the stored result instead of doing the work again. Payment APIs such as Stripe's expose exactly this as an Idempotency-Key header.

Three details separate a correct implementation from a leaky one:

  • Record the key atomically with the effect. Save “key K done” in the same transaction as the charge. If the server charged and then crashed before recording the key, the retry would charge again.
  • Handle two copies arriving at once. If the retry arrives while the first attempt is still running, the server must make it wait or reject it, not run both.
  • Expire old keys eventually (say after 24 hours). The table can't grow forever, so clients must not reuse a key across unrelated operations, or retry after the window closes.

Delivery semantics: at-most-once, at-least-once, exactly-once

These three phrases describe what a messaging system (a queue, an RPC framework, a webhook sender) promises about how many times a message is delivered or processed.

GuaranteeHow it worksFailure outcomeTypical use
At-most-onceSend it once; never retry. (Or: consumer acknowledges before processing.)Messages can be lost. Never duplicated.Metrics, logs and UDP-style telemetry where an occasional gap is fine
At-least-onceKeep retrying until acknowledged. (Consumer acknowledges after processing.)Nothing is lost, but messages can be duplicated (an ack lost or a crash before acking means resend).Most queues and webhooks; the practical default for anything important
Exactly-onceNot a primitive. Achieved as at-least-once delivery + idempotent or deduplicated processing.Each message's effect happens once, even if the message arrives several times.Payments, inventory, anything where duplicates or losses hurt

It's worth being blunt about “exactly-once”. Over an unreliable network, a sender can never be sure a message arrived (we're about to prove it), so it must either risk losing the message (at-most-once) or risk sending it twice (at-least-once). You can't escape the choice at the delivery level. What you can do is make duplicates harmless: the receiver recognises a repeat (via an idempotency key, a sequence number or a natural unique ID) and ignores it. The honest name for that is effectively-once processing. When a system advertises “exactly-once” (some stream-processing platforms do, within their own boundaries), this is almost always what's happening under the hood, and the guarantee stops at the edge of the system, which is why the final step (the email sent, the card charged) still needs its own idempotency.

The Two Generals problem

Is there some clever protocol of acknowledgements that gets us certainty? Computer scientists asked this in the 1970s, and the answer is a famous “no”. Step through the story.

Step through

The Two Generals problem

  1. The setup. Two armies sit on hills on either side of a valley held by the enemy. They win only if they attack at the same time; a lone attacker is destroyed. The only way to communicate is by sending a messenger through the valley, and any messenger might be captured. Can they coordinate with certainty?
  2. A proposes a time. A sends “Attack at dawn”. But A can't attack yet: A does not know whether the message arrived. If it didn't, B won't attack and A would be alone.
  3. B agrees. B receives it and replies “Agreed”. But now B is the nervous one: if the reply is lost, A will think B never heard, and not attack, leaving B alone. So B isn't certain either.
  4. A confirms the confirmation. A gets B's reply and sends “I got your Agreed”. Now A is sure B knows. But B can't be sure that A's confirmation arrived, so B still can't be certain A will attack.
  5. B confirms again. Another acknowledgement, and the same problem moves one step further along. Each message makes the doubt smaller but never zero.
  6. The last messenger. Whoever sends the final message doesn't know whether it got through. So that general can't be sure the other will act. Adding one more message just creates a new “last message” with the same flaw.
  7. The proof sketch. Suppose some protocol with a finite number of messages did guarantee coordination. Look at its very last message. It might be lost, yet the protocol must still work, so the last message wasn't needed. Remove it. Now repeat on the new last message, and so on, until no messages are left, which clearly can't coordinate anything. Contradiction. Certain agreement over an unreliable channel is impossible.

Computer scientists describe what the generals lack as common knowledge: not just “we both know the plan”, but “we both know that we both know, and so on forever”. Over a channel that can lose messages, no finite exchange can create it.

What is the practical lesson? Not despair. Real systems accept probabilistic confidence and design around the leftover doubt: acknowledge and retry until the chance of everything failing is negligible; use idempotency so a duplicate does no harm; use timeouts so nobody waits forever; and for the few cases that truly demand agreement, use consensus protocols (chapter 20), which make agreement possible by assuming something extra about the system (like a majority of nodes surviving) and by being willing to not make progress when that assumption fails. Even TCP's connection closing is a miniature of this: it can't be perfectly sure the other side saw the final message, so it uses timers and defaults.

Try it yourself

Experience a timeout and a retry

You'll use curl's timeout and retry options. We'll call an address from the reserved documentation range 203.0.113.0/24, which is never assigned to a real machine, so connection attempts normally hang with no reply: a perfect, harmless stand-in for a dead server. (On some networks you may instead see “Network is unreachable” at once; if so, just read the output below.)

$ curl --max-time 2 http://203.0.113.1/
curl: (28) Connection timed out after 2002 milliseconds

$ curl --max-time 2 --retry 3 --retry-delay 1 http://203.0.113.1/
Warning: Problem : timeout. Will retry in 1 seconds. 3 retries left.
Warning: Problem : timeout. Will retry in 1 seconds. 2 retries left.
Warning: Problem : timeout. Will retry in 1 seconds. 1 retry left.
curl: (28) Connection timed out after 2001 milliseconds

Wall-clock time was about 4 attempts × 2 s + 3 × 1 s = 11 seconds. Add time in front of the command to check. Notice the key facts: --max-time bounds the whole operation (--connect-timeout bounds just the connection step); --retry N retries only errors curl considers transient (timeouts and HTTP 408, 429, 500, 502, 503, 504, not 404); and if you leave out --retry-delay, curl uses exponential backoff starting at 1 second and doubling, exactly the pattern from this chapter. Add --retry-all-errors to retry other failures too.

Now compare with a failure that is not ambiguous. Port 9 on your own machine is almost certainly closed:

$ curl --max-time 2 http://localhost:9/
curl: (7) Failed to connect to localhost port 9 after 0 ms: Couldn't connect to server

This failed instantly with a definite answer: the machine is alive and actively said “nobody is listening here” (a TCP reset, chapter 8; older curl versions print "Connection refused"). A refusal is information; a timeout is the absence of it. Here is a table to think with:

Where we go from here

Look at what everything in this chapter depended on: timeouts need a notion of “how long”; heartbeats need “every second”; deduplication windows need “24 hours”; and in the next chapters we'll need to say which of two events on different machines happened first. All of those lean on time, and the clocks in different machines don't agree. Chapter 17 shows how far apart clocks can drift, why you can't trust timestamps from other machines, and how logical clocks (Lamport and vector clocks) recover a consistent order of events without needing the same wall-clock time everywhere.

Key takeaways

  • A client cannot distinguish a slow server from a dead one; a timeout is a guess, not a fact. Base it on measured latency percentiles and always set one.
  • Heartbeats detect failures by silence, but in an asynchronous network no detector is both perfectly accurate and always timely; detectors only suspect.
  • Retries fix transient failures but can cause retry storms. Use exponential backoff with jitter, bounded attempts, retry budgets, retries at a single layer and circuit breakers.
  • An idempotent operation can be repeated safely. Prefer “set to X” over “add Y”; where impossible, use an idempotency key with server-side deduplication recorded atomically with the effect.
  • At-most-once may lose; at-least-once may duplicate; exactly-once is really at-least-once delivery plus idempotent processing (effectively-once).
  • The Two Generals problem shows no finite exchange of messages over an unreliable channel yields certainty; real systems design for residual uncertainty instead.

Check your understanding

A client sends POST /charge and times out. Which approach is safe?

  1. Immediately resend the identical request without any key
  2. Resend with the same idempotency key as the first attempt
  3. Assume the payment failed and tell the user
  4. Resend with a brand-new idempotency key
The first attempt may have succeeded. Reusing the same key lets the server recognise a repeat and return the saved result, so the customer is charged at most once. A new key (or no key) risks a double charge; assuming failure risks losing a real payment.

1,000 clients all fail at the same moment and retry with exponential backoff but no jitter. What is the main problem?

  1. Their retries become too slow to be useful
  2. Exponential backoff doesn't reduce load at all
  3. The server will refuse to answer them
  4. They all retry at the same instants, in synchronised waves that hit the server together
Clients that fail together and wait identical, deterministic times also retry together. Randomising the wait (jitter) spreads the retries over time so no single moment gets the whole herd.

Which of these operations is naturally idempotent?

  1. Setting a user's email address to a specific value
  2. Appending a line to a log file
  3. Adding £5 to an account balance
  4. Sending a welcome email
Setting a field to a given value leaves the same state however many times it runs. Appending, adding and sending each produce an additional effect on every repeat, so they need an idempotency key or other deduplication.

What does “exactly-once” processing usually mean in practice?

  1. The network is guaranteed to deliver each message exactly one time
  2. The sender never retries a message
  3. Messages may be delivered more than once, but the receiver recognises duplicates so each has its effect only once
  4. Messages are delivered at most once and may be lost
Over an unreliable network you must choose between possible loss and possible duplication at the delivery level. Effectively-once combines at-least-once delivery with idempotent or deduplicated handling so the effect occurs once.

What does the Two Generals problem demonstrate?

  1. That messengers are slower than radios
  2. That no finite number of acknowledgements over an unreliable channel can give both parties certainty that they agree
  3. That consensus is always easy if you send enough messages
  4. That the generals should attack immediately
Whoever sends the last message cannot know whether it arrived, and removing that message by induction leads to a contradiction. Practical systems therefore accept residual uncertainty and use retries, idempotency and timeouts.

Your service's healthy p99.9 latency is 300 ms. Which timeout is the most sensible starting point?

  1. 50 ms, so failures are noticed fast
  2. 5 minutes, so nothing is ever cut off
  3. About 500 ms to 1 s, a margin above the measured tail
  4. No timeout, since the service is normally fast
A timeout below the normal tail (50 ms) turns healthy requests into false failures and triggers extra retries. Very long or no timeouts let hung dependencies tie up your resources. A margin above a high percentile balances both risks.

Layers & Encapsulation

If you remember one idea from the first half of this guide, make it this one. Networking is split into layers, each solving one problem, and data travels by being wrapped in envelope after envelope. Once you see this, every protocol you meet later has an obvious place to live.

Why this matters

Engineers constantly say things like "that's a layer 7 problem", "the switch only sees layer 2" or "TCP is on top of IP". This chapter gives you the map those sentences refer to. It's also your first taste of abstraction, the tool that makes huge systems (including distributed ones) possible to build at all.

The problem: too much to think about

Imagine you're writing a chat app, and to send one message your code had to: choose radio frequencies for Wi-Fi, notice when two devices talk over each other, find a route across 15 networks run by different companies, resend anything that got lost, and put the pieces back in the right order. Every app would need all of that code, and changing anything (say, switching from Wi-Fi to a cable) would break every app on Earth.

The solution is layering. Split the work into a stack of layers. Each layer:

  1. does one job,
  2. uses the layer below it as a service without caring how that layer works, and
  3. offers a simpler service to the layer above it.

Your chat app only says "deliver these bytes to that computer, reliably". The layers below sort out the rest.

The five layers

The Internet is built from roughly five layers. (You'll often hear "the TCP/IP model", which merges the bottom two into one; the idea is the same.) We number them from the bottom up, because each layer is built on the one beneath it.

Analogy: mailing a present abroad

You write a letter (application). You put it in an envelope marked "Flat 4B, for Sam", so it reaches the right person in the building (transport). That goes in a box with the full street address and country, which gets it to the right building anywhere in the world (network). At each depot, a courier sticks on a label saying just "to the airport" or "to the Lisbon depot" (link). Then a truck or plane physically carries it (physical).

Notice that the truck driver never reads your letter, and the depot never opens the box. Each layer only reads its own label.

Where it breaks down: real networks add and remove the "courier label" at every single stop, and everything happens in microseconds. Also, the "envelope" (transport) is responsible for noticing missing pieces and asking for them again, which post offices don't do for you.

Notice that there are three different kinds of address: MAC addresses (which device on this local network), IP addresses (which computer on the whole Internet) and port numbers (which program on that computer). Beginners often blur these together. Keeping them separate will save you a lot of confusion in the next few chapters.

Encapsulation: envelopes inside envelopes

When data goes down the stack on the sending computer, each layer adds its own header: a small block of information at the front, like the writing on an envelope. Whatever the layer received from above becomes its payload, the contents it carries but never reads. This wrapping is called encapsulation.

On the receiving computer the process runs in reverse, called decapsulation: each layer reads its own header, uses it to decide what to do, strips it off, and passes the payload up.

The interesting part is what happens in the middle. A router in the path unwraps only as far as it needs to (the IP header), makes its decision, then wraps the packet in a fresh frame for the next hop. Step through it below, and try typing your own message to see how the overhead changes.

Two things from that walkthrough are worth saying out loud, because they confuse almost everyone at first:

IP addresses stay the same end to end

The IP header says "from my laptop, to that server" for the whole journey. It's the box's shipping address. (The one common exception, NAT at your home router, comes in chapter 4.)

MAC addresses change at every hop

The Ethernet frame only says "from this device to the next device". Each router throws the old frame away and writes a new one. It's the courier's label for one leg.

Each layer talks to its twin

Here is a subtle but powerful way to think about layers. Even though data physically goes down, across and up, each layer behaves as if it is talking directly to the same layer on the other machine. The TCP code on your laptop "talks to" the TCP code on the server, using TCP headers as its language. Neither cares that IP and Ethernet are doing the carrying. Those layers are called peers.

This picture also tells you what different network boxes are, by which layer they work at:

Switch: layer 2

Connects devices in one local network. Reads MAC addresses to send each frame out of the right port (chapter 2).

Router: layer 3

Connects different networks. Reads IP addresses to choose the next hop (chapter 5).

Load balancer: layer 4 or 7

Spreads traffic over many servers, by port or even by reading the HTTP request (chapter 14).

Your computer: all of them

The endpoints (sender and receiver) are the only machines that run the full stack.

Why this design is brilliant

Layering means each layer can change independently. You can switch from Wi-Fi to an Ethernet cable to 5G, and your browser doesn't notice. A new app can be invented without anyone touching a single router. Fiber optic cables were deployed worldwide without rewriting TCP.

The cost: overhead and size limits

Envelopes aren't free. Each header takes up bytes that aren't your data. And each link has a maximum frame size it can carry, called the MTU (Maximum Transmission Unit). For Ethernet, the MTU is 1,500 bytes for the IP packet inside the frame.

So with a 20-byte IP header and a 20-byte TCP header, at most 1,460 bytes of your data fit in each packet. A 3 MB photo therefore travels as over 2,000 packets. Bigger messages aren't sent as one giant packet; the transport layer chops them into MTU-sized pieces.

Overhead matters most for tiny messages. If you're playing an online game that sends a 10-byte position update, the headers (14 + 20 + 20 + 4 = 58 bytes) are bigger than the data. That's one reason games often use UDP, whose header is only 8 bytes (chapter 7).

Go deeper: what if a packet is too big for the next link? optional

Different links can have different MTUs (some VPN tunnels, for example, have smaller ones because they add their own headers). IPv4 routers were originally allowed to fragment a too-big packet into smaller pieces, to be reassembled by the receiver. Fragmentation turned out to be slow and fragile (lose one fragment and the whole packet is lost), so modern systems avoid it with Path MTU Discovery: send packets marked "don't fragment" and, if a router replies "too big, my limit is 1,400", use smaller packets. IPv6 removed fragmentation by routers entirely.

A side note: the OSI model

You will hear people talk about "Layer 7" or "the seven-layer model". That's the OSI model, designed in the late 1970s as an international standard. The OSI protocols themselves mostly lost to TCP/IP, but its layer numbers stuck as jargon.

OSI layerNameOur model
7ApplicationApplication (HTTP, DNS, TLS…)
6Presentation
5Session
4TransportTransport
3NetworkNetwork
2Data linkLink
1PhysicalPhysical

That's why a load balancer that reads HTTP is called a "layer 7 load balancer", while transport is still "layer 4" in both models. Mnemonic for the OSI names from the bottom: Please Do Not Throw Sausage Pizza Away.

Common misconception: the layers are perfectly sealed boxes

The layer model is a map, not the territory. Real protocols peek across the lines all the time. TCP's checksum includes the IP addresses. Home routers doing NAT rewrite both IP addresses (layer 3) and port numbers (layer 4). TLS encryption sits awkwardly between transport and application. When you hear an argument about "which layer X really belongs to", the honest answer is often "it straddles two". Use the model to organise your thinking, not as a law of nature.

Try it yourself

See two of your own addresses

Your computer has a MAC address (link layer) and an IP address (network layer) for each network connection. On a Mac, run ifconfig en0 (Wi-Fi is usually en0). On Windows run ipconfig /all; on Linux, ip addr.

$ ifconfig en0
en0: flags=8863<UP,BROADCAST,SMART,RUNNING,SIMPLEX,MULTICAST> mtu 1500
	ether a4:83:e7:1c:52:2f                          # MAC address (layer 2)
	inet 192.168.1.20 netmask 0xffffff00 broadcast 192.168.1.255   # IP address (layer 3)
	status: active

You can see the MTU of 1,500 as well. Now look at the top of the stack. curl is a command-line web client; -v ("verbose") shows the conversation:

$ curl -v http://example.com
*   Trying 93.184.216.34:80...                  # layer 3 address + layer 4 port
* Connected to example.com port 80            # TCP connection established
> GET / HTTP/1.1                               # layer 7: what you sent
> Host: example.com
>
< HTTP/1.1 200 OK                              # layer 7: what came back
< Content-Type: text/html; charset=UTF-8

(The IP address you see may differ.) Everything starting with > or < is the application layer's conversation. All the wrapping and unwrapping below it happened invisibly. If you'd like to see every layer of real packets, install the free tool Wireshark, start a capture and load a website. It shows each packet as nested headers, exactly like the widget above.

Distributed systems connection

Layering is abstraction: hiding messy details behind a simple promise. Distributed systems keep stacking layers on top: remote procedure calls on top of TCP, replication on top of RPC, consensus on top of that. But abstractions leak. TCP promises a reliable, ordered stream of bytes, yet it cannot hide the fact that the other machine might have crashed, or that the network might be cut. When that happens your code just waits, and has to decide what "too long" means. That single leak is the starting point of chapter 16.

Go deeper: the end-to-end principle optional

A classic 1984 paper by Saltzer, Reed and Clark argues that some guarantees can only be checked properly at the ends of a system, by the applications themselves. Example: TCP makes sure bytes arrive intact between two machines. But if the receiving program crashes after TCP acknowledged the data and before it saved it to disk, the data is still lost. Only an application-level "I've safely stored it" message can confirm success.

This is why the Internet's core (routers) is kept simple and dumb, and the intelligence lives at the edges. It's also why distributed systems design their own acknowledgements, retries and duplicate detection rather than trusting the network to do it for them.

Key takeaways

  • Networking is split into layers: physical, link, network, transport, application. Each does one job and relies on the one below.
  • Encapsulation: going down the stack, each layer adds a header; going up, each layer reads and strips its own.
  • Three kinds of address: MAC (next device, changes every hop), IP (which computer, end to end), port (which program).
  • Routers work at layer 3, switches at layer 2; only the endpoints run every layer.
  • IP is the narrow waist that lets any application run over any kind of link.
  • Headers cost bytes; Ethernet's 1,500-byte MTU means about 1,460 bytes of data per TCP packet.

Check your understanding

As a packet travels from your laptop to a server across 12 routers, which addresses change at every hop?

  1. The IP addresses
  2. The MAC addresses in the Ethernet frame
  3. The port numbers
  4. Nothing changes
MAC addresses only describe a single hop (this device → next device), so each router builds a new frame. IP addresses describe the whole journey and stay the same (except where NAT rewrites them, chapter 4). Ports belong to the endpoints.

What does a router normally look at to decide where to send a packet?

  1. The HTTP request inside it
  2. The TCP port number
  3. The destination IP address in the IP header
  4. The Ethernet trailer
Routers are layer 3 devices: they unwrap the link-layer frame, read the destination IP address, and pick a next hop. They don't need anything above layer 3.

What is encapsulation?

  1. Each layer wrapping the data from the layer above with its own header
  2. Encrypting data so nobody can read it
  3. Compressing data so it's smaller
  4. Splitting a network into smaller networks
Encapsulation is the envelope-in-envelope process: a TCP segment becomes the payload of an IP packet, which becomes the payload of an Ethernet frame. It's not encryption; headers are usually readable by anyone on the path.

Why can a brand-new app work over Wi-Fi, 5G and fiber without being changed?

  1. Because apps contain code for every type of cable
  2. Because Wi-Fi, 5G and fiber are all the same thing
  3. Because routers translate the app's messages
  4. Because of layering: the app talks to the transport layer, and lower layers hide the link type
This is the main payoff of layering. Each layer offers a service and hides how it's done, so the top and bottom of the stack can change independently. IP in the middle (the narrow waist) ties them together.

Ethernet's MTU is 1,500 bytes. The IP and TCP headers are 20 bytes each. How many bytes of your data can one packet carry?

  1. 1,500
  2. 1,480
  3. 1,460
  4. 1,442
The MTU limits the IP packet (IP header + TCP header + data), so 1,500 − 20 − 20 = 1,460. The Ethernet header and trailer are outside the MTU, so they don't count against it.

DNS: The Internet's Phonebook

You type example.com, but routers only understand numbers. Somewhere between your keystrokes and the first packet, a worldwide database answers "what is the address of that name?" in a few milliseconds. DNS is one of the oldest and most successful distributed systems ever built, and you are about to see exactly how it works.

Why this matters

Almost every connection on the Internet starts with a DNS lookup, so when DNS is slow or broken, everything looks broken. "It's always DNS" is a joke engineers make because it is so often true. DNS is also your first meeting with three ideas that run through the rest of this guide: hierarchy (splitting a huge job among many owners), caching (remembering answers to go faster) and eventual consistency (the price of caching: for a while, different people see different answers).

Why we need names

In chapter 4 you learned that every device on the Internet is reached by an IP address such as 93.184.216.34 or 2606:2800:21f:cb07:6820:80da:af6b:8b2c. Computers are happy with those. Humans are not: nobody wants to memorise a number for every website, and there is a more serious problem too.

IP addresses change. A company moves its website to a new hosting provider, or adds a second data center, or rents a different cloud server. If everyone had typed the old number, every bookmark and every program would break. A name is a stable label that can point to different numbers over time. Names also work the other way round: one name can point at many machines (a big site has thousands), so the same www.example.com can lead different users to different servers.

The Domain Name System (DNS) is the service that translates names such as www.example.com into the data you need to connect, most often an IP address. In the "mailing a present abroad" story from chapter 3, an IP address is the street address on the box. DNS is the phonebook you look in to find the address of "Sam's Bakery" before you can write it down.

Analogy: the phonebook that no one owns

Imagine that instead of one thick phonebook, the world had a chain of directories. A global directory says only which country's directory to ask. The country directory says which town's directory to ask. The town directory finally lists "Sam's Bakery: 12 High Street". Nobody keeps the whole book; each office is responsible only for its own small part, and clerks write down answers they have already looked up so they don't have to walk to the next office again.

Where it breaks down: a paper phonebook is printed once a year and is the same for everyone. DNS is alive: entries change at any moment, there are millions of copies of recent answers scattered around the world, and those copies can be briefly out of date. Also, the "clerks" are software, and they answer in milliseconds.

The hierarchy: a tree of names

A domain name is read from right to left, from the most general part to the most specific. Take www.example.com. (note the dot at the very end; we'll come back to it):

  • . (the empty label on the end) is the root, the top of the whole tree.
  • com is a top-level domain (TLD). Others are org, net, country codes such as uk or de, and newer ones such as dev.
  • example is a name someone registered under com. Together, example.com is a domain.
  • www is a hostname inside that domain, chosen by whoever owns it. They can create as many as they like: mail.example.com, api.eu.example.com.

Zones and delegation

Nobody holds the whole tree. Instead it is cut into pieces called zones, and each zone is looked after by a set of servers called its authoritative nameservers ("authoritative" means: this is the source of truth for this part, not a copy). The zone for example.com contains the records for www.example.com, mail.example.com, and so on.

The clever bit is delegation. The .com zone doesn't list every hostname under every .com domain, which would be impossibly large. It only contains a pointer: "for anything under example.com, ask these nameservers", written as NS records. The root zone does the same for each TLD. So to find a name you follow a chain of pointers from the top of the tree down: root → TLD → the domain's own nameservers. At each step one organisation hands responsibility to another, which is how a database that is run by thousands of independent parties can still behave like one.

The trailing dot

Strictly, the full name is www.example.com. with a dot at the end, meaning "starting from the root". That is called a fully qualified domain name (FQDN). Browsers hide the final dot and add it for you, which is why you've never typed it, but you'll see it in DNS tools and configuration files (example.com.). Leaving it off in some configuration files means "relative to the current domain", a classic source of bugs.

How many root servers are there? You'll hear "13". Precisely: there are 13 root server names (a.root-servers.net through m.root-servers.net), run by different organisations, but each name is served from many physical machines in hundreds of locations around the world using a trick called anycast (the same IP address is announced from many places, and routing sends you to the nearest, as you saw in chapter 5). So the root is neither one machine nor 13; it is a large, replicated service.

Resolution: how a lookup really works

Your browser doesn't walk the tree itself. There are three kinds of players:

Stub resolver

A tiny piece of code in your operating system. It doesn't know how to search the tree. It just asks one chosen server "please find this for me" and waits for the final answer.

Recursive resolver

The server that does the legwork. Usually run by your ISP, your workplace, or a public service such as 1.1.1.1 (Cloudflare) or 8.8.8.8 (Google). Your router usually advertises one via DHCP (chapter 6). It walks the tree for you and remembers the answers.

Authoritative servers

Root, TLD and domain nameservers. They hold the real data and only answer questions about their own zone, or point you onwards to whoever is responsible below.

The conversation between your stub resolver and the recursive resolver is recursive: "get me the final answer, I don't care how". The conversation between the recursive resolver and each authoritative server is iterative: each server either answers, or replies with a referral ("I don't know, but these servers do, ask them") and the resolver goes there itself. Step through a complete lookup of www.example.com from a cold start:

Step through

Resolving www.example.com

  1. Check local caches. The browser needs an address for www.example.com. It first looks in its own cache, then the operating system's cache. Both come up empty (a "miss"), so a real lookup is needed. (If either had a recent answer we would stop right here, in microseconds.)
  2. Ask the recursive resolver. The stub resolver sends one question, "what is the A record (IPv4 address) for www.example.com?", to the recursive resolver it was configured with, and then waits. Normally this travels in a single UDP packet to port 53.
  3. The resolver checks its own cache. It serves thousands of users, so someone else may have asked recently. Not this time: a miss. It must walk the tree. (In practice it almost always has the root and .com servers cached already, so steps 4 and 5 are usually skipped. We're showing a cold start.)
  4. Ask a root server. The resolver has a built-in list of root server addresses. It asks one: "www.example.com A?" The root doesn't know the answer and doesn't pretend to. It replies with a referral: here are the NS records (and their addresses) of the servers responsible for .com.
  5. Ask a .com TLD server. Same question, new server. The TLD server also doesn't know the host's address, but it knows who is responsible for example.com, so it answers with another referral: the NS records of that domain's authoritative nameservers.
  6. Ask the authoritative server. Finally the question reaches the server that owns the data. It answers directly: the A record is 203.0.113.10, with a TTL of 300 seconds (a "keep this for at most 5 minutes" label; more on it below).
  7. The resolver caches and replies. It stores the answer (and the referrals it learned along the way) until their TTLs run out, then sends the answer back to your laptop. The next person who asks this resolver for the same name gets it instantly.
  8. Your laptop caches it too, hands the address to the browser, and the browser can finally open a TCP connection (chapter 8). Ask again within the TTL and the answer comes from cache in about a millisecond or less. The whole cold lookup typically takes tens of milliseconds, mostly waiting for round trips to the faraway servers.

Notice how few of those steps happen on a typical day. Popular names like google.com are in nearly every resolver's cache nearly all the time, and the TLD servers are asked only once per TTL. That is why the root servers, which sound like a single point of failure for the whole Internet, can cope: almost nobody ever asks them.

Go deeper: glue records and the chicken-and-egg problem optional

Suppose example.com says its nameserver is ns1.example.com. To find that nameserver's address you need to look up ns1.example.com, which means asking the nameserver for example.com, which you don't have the address of yet. A deadlock!

The fix is glue records: when a TLD server refers you to ns1.example.com, it includes that server's IP address right alongside, in the "additional" section of its reply, so you don't need a separate lookup. Glue is only needed when the nameserver's name lies inside the zone it serves; a domain whose nameservers are named, say, ns.some-hosting.net doesn't need it.

Caching and TTLs

If every lookup travelled to the root, the TLD and the authoritative server, the Internet would grind to a halt: billions of lookups a day all landing on a few servers, each adding delays of tens of milliseconds before a page can even start loading. DNS survives because of caching: whoever asks a question remembers the answer for a while.

Caches exist at every layer between you and the authoritative server, and each one checks itself before bothering the next:

TTL: how long may an answer be kept?

Every DNS record comes with a TTL (time to live), a number of seconds. It is the zone owner's instruction to every cache in the world: "you may reuse this answer for this long; after that, ask again." A cache counts the TTL down as time passes, which is why the same record shows a different TTL each time you look (you'll see this in the experiment below).

Choosing a TTL is a classic trade-off:

Long TTL (hours, a day)

Faster for users, less load on your nameservers, more resilient if they briefly go down (caches keep answering). But changes are slow to take effect.

Short TTL (seconds, a minute)

Changes take effect quickly (good for failover and moving servers). But more lookups reach your nameservers, and users pay for more cold lookups.

"DNS propagation" and eventual consistency

You may have heard "DNS changes take up to 48 hours to propagate". That phrase is misleading. Nothing is pushed anywhere. When an owner changes a record, the authoritative server starts giving the new answer immediately. But millions of caches around the world still hold the old answer, and each will keep serving it until its own TTL runs out. Caches that cached it ten minutes ago expire at one moment; caches that cached it a second ago expire much later. Everyone converges on the new value, but not at the same time.

Analogy: the shop's opening-hours sign

A shop changes its hours and updates its door sign. Everyone who walks past sees the new hours at once. But your friends have each written the old hours in their diaries, and they'll only check the sign again after, say, a week. Until each diary entry "expires", they confidently tell people the wrong hours, and different friends get things wrong for different lengths of time.

Where it breaks down: in DNS the owner chooses how long the diaries may keep an entry (the TTL), and can't call anyone to say "cross it out". Also, there's no single door: the "sign" is a handful of servers, and the diaries belong to millions of strangers' machines.

Your first meeting with eventual consistency

Look at what just happened. There is one authoritative truth, and many copies (caches) that are allowed to be stale. If no more changes are made, then after at most one TTL every copy agrees with the truth. That property has a name: eventual consistency. "Eventually, if updates stop, all replicas converge to the same value." DNS chose it on purpose: strict consistency (every cache updated instantly and atomically) would be impossible to coordinate across millions of independent caches, and far too slow. Instead DNS accepts brief staleness in exchange for speed, scale and resilience. You'll meet the same bargain, with sharper edges, in chapter 18.

Practical consequences of this design:

  • Plan migrations. Before moving a website to a new IP address, engineers lower the TTL (say from 24 hours to 60 seconds) a full old-TTL ahead of time, wait for the old long-lived entries to age out, make the switch, and raise the TTL again afterwards.
  • You can't "recall" a bad answer. If you publish a wrong record with a one-day TTL, caches can serve it for up to a day, no matter how fast you fix it.
  • Your colleague may see the new site while you still see the old one. They are probably just using a resolver whose cache expired earlier.

Negative caching

Caches also remember failures. If you ask for nope.example.com and the authoritative server says "that name doesn't exist" (an answer code called NXDOMAIN), resolvers cache that "no" too, for a time controlled by a value in the zone's SOA record (the zone's header record). It is called negative caching and it protects the nameservers from repeated pointless questions. The flip side: if you query a name before you've created it, then create it, you may see "doesn't exist" for a few more minutes even though it now does.

Common misconception: "DNS propagation takes 24-48 hours"

It takes at most roughly one TTL (for caches that held the old value), not a mystical two days. The "48 hours" folklore comes from the days when many zones used 24-hour TTLs and some registries updated their TLD data slowly. If your records have a 5-minute TTL, a change is usually fully visible within about five minutes. It's the TTL you chose, not the Internet, that sets the clock.

Record types: what's in the database?

DNS stores more than addresses. Each entry is a resource record with a name, a type, a TTL and a value. Here are the ones you'll meet constantly:

TypeMeaningExample
AName → IPv4 addresswww.example.com. 300 IN A 203.0.113.10
AAAAName → IPv6 address (pronounced "quad-A")www.example.com. 300 IN AAAA 2001:db8::10
CNAME"Canonical name": this name is an alias for another nameblog.example.com. 3600 IN CNAME example.github.io.
MXWhere to deliver email for this domain, with a priority number (lower = preferred)example.com. 3600 IN MX 10 mail.example.com.
NSWhich nameservers are authoritative for this zone (the delegation pointers)example.com. 86400 IN NS ns1.example.com.
TXTFree-form text. Used to prove you own a domain, and for email anti-spoofing policies (SPF, DKIM, DMARC)example.com. 3600 IN TXT "v=spf1 -all"

A CNAME is worth a note, because it behaves like a redirect inside DNS: asking for blog.example.com returns "that's an alias of example.github.io", and the resolver then looks that name up instead. Big sites use it constantly to point at a CDN or cloud provider, which can then change the real addresses without you doing anything. One rule to remember: a name that has a CNAME may not have any other records, so you can't put a CNAME on the bare domain (example.com itself), which also needs NS, SOA and MX records.

DNS on the wire

DNS is an application-layer protocol (chapter 3), and it uses the transport layer in a way that tells you something about its design:

  • Mostly UDP, port 53. A query and its answer are each usually one small packet. UDP (chapter 7) has no handshake, so a lookup costs exactly one round trip, with no TCP setup first. If the packet or its reply is lost, the resolver just waits briefly and asks again.
  • TCP, port 53, for big answers. Classic DNS limited UDP replies to 512 bytes; modern extensions (EDNS) allow larger ones, but if an answer is still too big, the server sets a "truncated" flag and the client retries over TCP. Zone transfers between nameservers (copying a whole zone) also use TCP.

Notice a limitation: classic DNS is unencrypted. Anyone on the path (your café Wi-Fi, your ISP) can see exactly which names you look up, even if the website itself uses HTTPS. Two newer variants wrap DNS in encryption: DNS over HTTPS (DoH, which looks like ordinary web traffic on port 443) and DNS over TLS (DoT, port 853). Browsers and operating systems increasingly support them, usually talking to a public resolver. They hide your lookups from the network in between (not from the resolver itself, which still sees them). We'll build the encryption itself in chapter 11.

DNS as a traffic-steering tool

Because DNS decides which address a user gets, it doubles as a crude load balancer and failover tool:

  • Several A records for one name. The server returns, say, three IP addresses (often in rotating order) and clients try them in turn, so traffic spreads over three machines. This is "round-robin DNS".
  • Geo-aware (or latency-aware) DNS. The authoritative server looks at roughly where the question came from and answers with the nearest data center. A user in Tokyo and a user in Paris asking for the same name receive different IP addresses.
  • Health-checked failover. The DNS provider monitors your servers and stops returning the address of a dead one. Here TTL matters again: with a 1-hour TTL, many users keep hitting the dead address for up to an hour, which is why such records often use TTLs of 30–60 seconds.

DNS is blunt compared to the real load balancers of chapter 14: it can't see server load, it can't take effect faster than caches expire, and clients may ignore your ordering. But it is the first step that sends users toward the right part of the world.

Try it yourself

Look up names with dig

dig ("domain information groper") is the standard DNS tool. It's installed on macOS and most Linux systems. On Windows use nslookup (shown below), or install BIND's tools. Everything here is read-only and safe. Your addresses, TTLs and timings will differ from the ones shown.

$ dig example.com
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41872
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; QUESTION SECTION:
;example.com.			IN	A

;; ANSWER SECTION:
example.com.		3217	IN	A	93.184.216.34

;; Query time: 38 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)       # the recursive resolver that answered
;; MSG SIZE  rcvd: 56

Read it from the middle. The ANSWER SECTION is the result: name, TTL (3217 seconds left in the cache that answered), class IN (Internet), type A, and the address. status: NOERROR means success; a missing name gives NXDOMAIN. SERVER is the recursive resolver you asked, here a home router on port 53. And Query time is how long the whole thing took.

Run it twice. The first time on a name nobody nearby asked for recently, the query time is perhaps 30–100 ms. Run it again straight away: the query time typically drops to 0–5 ms, and the TTL in the answer is a bit smaller than before, because the resolver has been counting it down. That's caching, made visible.

Now watch the resolver's job being done by hand with +trace, which starts at the root and follows the referrals itself, the way steps 4–6 of the widget did:

$ dig +trace example.com

.			518400	IN	NS	b.root-servers.net.
... (all 13 root names) ...
;; Received 811 bytes from 192.168.1.1#53(192.168.1.1) in 21 ms

com.			172800	IN	NS	a.gtld-servers.net.
com.			172800	IN	NS	b.gtld-servers.net.
... (a root server's referral to the .com servers) ...
;; Received 1170 bytes from 198.41.0.4#53(a.root-servers.net) in 24 ms

example.com.		172800	IN	NS	a.iana-servers.net.
example.com.		172800	IN	NS	b.iana-servers.net.
... (a .com server's referral to example.com's own nameservers) ...
;; Received 468 bytes from 192.5.6.30#53(a.gtld-servers.net) in 31 ms

;; Received 56 bytes from 199.43.135.53#53(a.iana-servers.net) in 28 ms

Three hops, three referrals, then the answer. Look at the TTL column too: the delegations (root, com., example.com. NS records) have very long TTLs of days, because who runs a TLD rarely changes, while the final host record has a shorter one. Try a few more record types:

$ dig example.com MX          # mail servers
$ dig example.com AAAA +short  # just the IPv6 address(es), no extras
$ dig example.com NS +short    # who is authoritative?
$ dig @1.1.1.1 example.com    # ask a specific resolver instead of your default
$ dig nope-12345.example.com  # see NXDOMAIN (status: NXDOMAIN)

Windows has nslookup built in:

> nslookup example.com

"Non-authoritative answer" simply means "this came from a resolver (often out of its cache), not directly from the zone's own server". If you're curious about the OS cache on a Mac: it isn't easy to list, but you can clear it (that needs administrator rights, so it asks for your password) with sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder. On Windows, ipconfig /flushdns does the same job without needing the extra step.

Distributed systems connection

DNS is arguably the most successful distributed database ever built, and nearly every design trick in this guide's final part appears in it in miniature:

  • Partitioning by hierarchy. No machine holds the whole dataset. The namespace is split into zones, each owned by a different party, and delegation glues them together. That's how DNS scales to hundreds of millions of domains with no central bottleneck (chapter 19 has other ways to split data).
  • Replication. Every zone must have at least two nameservers, normally in different networks, and the root and big TLDs are replicated across hundreds of sites with anycast. If one dies, others answer (chapter 18).
  • Caching with expiry = eventual consistency. Reads are fast and cheap because they are allowed to be a little stale, and the TTL is an explicit, bounded promise about how stale. Much of system design is choosing that bound.
  • Service discovery inside companies. Inside a data center, services also need to find each other, and the answer is usually DNS again (or a DNS-like registry). Kubernetes, for example, gives every service a DNS name like orders.shop.svc.cluster.local that resolves to whichever machines are currently healthy. Short TTLs let the "phonebook" follow servers that come and go many times a day.

And a caution for later: when a name's address changes, a program that looked it up once and kept the answer forever (many do!) is acting as a cache with an infinite TTL, and will keep talking to a dead server. Respecting TTLs is part of correctness.

Key takeaways

  • DNS maps names to data (mostly IP addresses) so that names stay stable while servers move, and one name can lead to many servers.
  • Names form a tree (root → TLD → domain → host), split into zones run by different owners and linked by delegation (NS records).
  • Your stub resolver asks a recursive resolver, which asks the root, the TLD and the authoritative servers in turn, following referrals, and then caches the result.
  • Every answer has a TTL. Long TTLs mean speed and low load; short TTLs mean fast change. There is no "propagation", just caches expiring at different times.
  • That makes DNS eventually consistent: copies can be briefly stale, but converge within about one TTL once changes stop.
  • Key record types: A, AAAA, CNAME, MX, NS, TXT. DNS runs mostly over UDP port 53 (TCP for large replies), and is unencrypted unless you use DoH or DoT.
  • Debug with dig (or nslookup): read the ANSWER section, the TTL and the query time, and run it twice to see caching.

Check your understanding

Your laptop's stub resolver wants the address of www.example.com. What does it do first?

  1. Asks a root server directly
  2. Asks the authoritative nameserver for example.com
  3. Checks local caches, then sends one question to its configured recursive resolver
  4. Broadcasts the question to every computer on the local network
The stub resolver is deliberately simple. It checks the caches in the browser and OS, and if there's no answer it sends a single "find this for me" question to the recursive resolver, which does the real tree-walking on its behalf.

What does a root server reply when asked for www.example.com?

  1. A referral: the nameservers responsible for .com
  2. The IP address of www.example.com
  3. An error, because it only deals with the root
  4. The full list of every .com domain
The root only knows who runs each top-level domain. It hands back NS records (with addresses) for .com, and the resolver asks them next. That chain of referrals is delegation in action.

You change a record whose TTL was 1 hour. A friend still sees the old address 20 minutes later. Why?

  1. The change hasn't been uploaded to the root servers yet
  2. DNS always takes 24-48 hours
  3. Their computer is broken
  4. Their resolver cached the old answer and may keep serving it until its own TTL countdown reaches zero
Nothing is pushed to caches. Each cache holds the old value until its copy expires, which is at most one TTL after it last fetched it. Different caches fetched at different times, so people see the change at different moments, which is eventual consistency.

You plan to move a website to a new server next week. What should you do with the TTL beforehand?

  1. Raise it to 24 hours so the change looks stable
  2. Lower it well in advance (at least one old TTL before the move), so caches will pick up the change quickly
  3. Delete it; TTL is optional
  4. Nothing; TTL only affects the root servers
Caches that already hold the old, long-TTL answer will keep it for that long, so the short TTL must be published early enough for the old entries to expire. Once the move is done and stable, you can raise it again.

Which record type tells the world where to deliver email for example.com?

  1. A
  2. CNAME
  3. MX
  4. NS
MX ("mail exchanger") records name the mail servers, with a priority. A gives an IPv4 address, CNAME makes an alias, and NS names the zone's authoritative nameservers.

Why does DNS usually use UDP rather than TCP?

  1. A query and reply are tiny, and UDP avoids a connection handshake, so a lookup takes just one round trip
  2. UDP is encrypted and TCP is not
  3. TCP cannot use port 53
  4. Because UDP guarantees delivery
Most lookups fit in one packet each way, so TCP's setup would double the cost for nothing; if a packet is lost, the resolver simply asks again. UDP does not guarantee delivery or provide encryption. TCP is used for large answers and zone transfers.

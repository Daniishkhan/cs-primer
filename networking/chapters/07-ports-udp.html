Ports, Sockets & UDP

IP can carry a packet to the right computer, but a computer runs dozens of programs at once. This chapter introduces the number that picks the right program, the handle programs use to talk to the network, and UDP: the simplest, most "no-promises" way to send data.

Why this matters

Every network program you will ever write or debug is addressed by a pair: host and port. "Connection refused", "address already in use" and "port 8080" all live here. Understanding ports also explains how one laptop can have twenty browser tabs open to the same website without mixing them up. And UDP is the foundation for DNS, online games, video calls and QUIC (the protocol behind HTTP/3): seeing what it doesn't do is the best way to appreciate what TCP does (next chapter).

Which program gets the packet?

Follow a packet to its destination. Routing (chapter 5) delivers it to the right computer, identified by the destination IP address. But that computer is running a web server, an SSH server, a database, a chat client and a music app, all at once. When the packet arrives, who gets the data?

The answer is the port number: a 16-bit number (0 to 65,535) in the transport-layer header that identifies a specific program or service on a computer. It is the third kind of address from chapter 3: MAC (which device on this link), IP (which computer in the world), port (which program on that computer).

Analogy: the flat number

An IP address is a street address: it gets the postman to the right building. A port is the flat number on the envelope: it tells the building's front desk which resident gets it. "203.0.113.10, flat 443" and "203.0.113.10, flat 22" are the same building, but different people with different jobs.

Where it breaks down: residents of a real building choose which flat they live in and keep it. A program must ask the operating system for a port, and it can only get one that nobody else on that computer is using. Also, flats are numbered separately for TCP and UDP, like two parallel postal systems in the same building.

Well-known ports and ephemeral ports

A port number alone says nothing about what's behind it, so by convention important services use fixed, agreed ports, called well-known ports. If you type https://example.com, your browser knows to knock on port 443 without being told:

PortServiceNotes
22SSHSecure remote login
25SMTPEmail between servers
53DNSMostly UDP; TCP for big answers (chapter 9)
67 / 68DHCPUDP: server / client (chapter 6)

Roughly, the space is divided into three ranges: 0 to 1,023 are the well-known ports (on Unix-like systems only a privileged user can listen on them); 1,024 to 49,151 are "registered" ports that applications such as databases conventionally use; and the rest, up to 65,535, are meant for ephemeral use. (The exact ephemeral range depends on the operating system; Linux, for example, defaults to about 32,768 to 60,999.)

That's because the client needs a port as well. A server's port is fixed, but when your browser connects to it, the operating system picks a random unused ephemeral port (a short-lived one) on your side, say 51234, as the source port. The server uses it to send the reply back to the right program.

Flows: the 5-tuple

Here is the neat consequence. Suppose you open three browser tabs, all to the same website, and also an SSH session to the same server. All four involve the same two IP addresses. How does your computer keep their data apart? Because each connection uses its own source port:

A single conversation is identified by five values, the 5-tuple:

ProtocolSource IPSource portDestination IPDestination port
TCP192.168.1.2051234203.0.113.10443
TCP192.168.1.2051235203.0.113.10443
TCP192.168.1.2055002203.0.113.1022

Packets that share a 5-tuple belong to the same flow. This single idea is used everywhere: your operating system uses it to hand incoming data to the right program; your home router's NAT (chapter 4) uses it, rewriting source IPs and ports and remembering the mapping; firewalls track it; and load balancers (chapter 14) use it to send all packets of a flow to the same server. It also means a server doesn't need one port per client: ten thousand clients can all connect to port 443, because each has a different source IP or source port.

Sockets: the program's handle on the network

A program never touches network cards or IP packets directly. It asks the operating system for a socket: an endpoint through which it can send and receive data. A socket is bound to a protocol (TCP or UDP), a local IP address and a local port. Think of it as a numbered mailbox that belongs to the program; the operating system sorts incoming packets into the right mailbox by port.

There are two common roles, which we'll look at in much more detail in chapter 12:

  • Listening (a server): "I'm taking mail for port 443. Tell me when someone arrives." The program binds a port and waits.
  • Connecting (a client): "I want to talk to 203.0.113.10:443." The operating system silently picks an ephemeral source port for it.

Here is what the smallest possible UDP server and client look like in Python. Don't worry about the details; notice the shape: create, bind or address, send or receive.

import socket

# --- server: wait for one datagram on port 9999 ---
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)   # SOCK_DGRAM means UDP
s.bind(("127.0.0.1", 9999))                           # claim port 9999
data, sender = s.recvfrom(1024)                       # blocks until something arrives
print(data, "from", sender)                           # sender = (ip, source port)

# --- client (another program): send one datagram ---
c = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
c.sendto(b"hello", ("127.0.0.1", 9999))               # no connection, just send

Common misconception: a port is a physical thing

Ports aren't sockets on the back of your computer. They're just numbers in headers, plus a table in the operating system that says "port 9999 belongs to process 4711". That's why you get an error such as "address already in use" if two programs try to claim the same port: there is only one entry per (protocol, address, port) in that table.

UDP: the simplest transport protocol

The User Datagram Protocol (UDP) is the minimum viable transport layer. It adds just enough to IP to make ports work, and nothing else. Its entire header is 8 bytes, four fields of 2 bytes each:

Source port16 bits
Destination port16 bits
Length16 bits · header + data
Checksum16 bits · detects corruption
Your data (the "datagram" payload)

The length says how big the datagram is; the checksum lets the receiver detect if bits were flipped on the way (a corrupted datagram is silently discarded). That's all. Compare this with the 20-byte-minimum header of TCP in the next chapter.

UDP is described as connectionless and fire-and-forget. Concretely:

  • No connection: there is no handshake. You just address a datagram and send it. The other side doesn't even need to be listening.
  • No retransmission: if the datagram is lost, it's gone. UDP doesn't know and doesn't care.
  • No ordering: datagrams can arrive in a different order than sent, or twice.
  • No congestion control: UDP will send as fast as you tell it to, even if the network is overloaded.
  • Message boundaries are kept: if you send three datagrams, the receiver gets three separate messages, not one blurred stream. (TCP does not do this.)

Analogy: a postcard

UDP is dropping a postcard in a postbox. It's quick and cheap. There's no phone call to arrange it first, no receipt, no check that your friend is home. Most postcards arrive; a few don't; you will likely never know which.

Where it breaks down: postcards from the same post office usually arrive in the order sent, while UDP makes no such promise. And a postbox doesn't mind how many postcards you drop in; a UDP sender that sends too much too fast can harm everyone sharing the network.

Why would anyone want that?

It sounds like a terrible deal, but "no promises" has real advantages: no waiting for a handshake, no stalls because of retransmission, and the freedom to decide for yourself what to do about loss. It's the right tool when:

One question, one answer

DNS. A lookup is a tiny request and a tiny reply. Setting up a connection would cost more than the lookup. If no reply arrives, the program just asks again.

Late data is useless data

Voice and video calls, live games. If a fragment of audio from 300 ms ago is lost, replaying it when it finally arrives is worse than skipping it. Better to move on to the newest data than to wait for old data.

Build your own rules

QUIC (HTTP/3). Rather than use TCP, QUIC builds its own reliability and encryption on top of UDP, so it can improve things faster than operating systems update TCP. We meet it in chapter 10.

Small, frequent, replaceable

Heartbeats, sensor readings, game positions. If the next update is coming in 50 ms, losing this one hardly matters.

The cost is that your application takes over the job. If you need reliability on UDP, you must number the messages, wait for acknowledgements, resend and order them. That is a lot of subtle work, and it's exactly what TCP does for you.

UDP vs TCP: a first look

Here's a preview of the comparison we will fill in during chapter 8:

UDPTCP
Connection setupNone: just sendThree-way handshake first
ReliabilityNone: lost means lostLost data is detected and resent
OrderingNoneData delivered in order
Data modelSeparate messages (datagrams)One continuous stream of bytes
Congestion controlNone (the application must be polite)Built in: slows down when the network is overloaded
Header size8 bytesAt least 20 bytes
Typical usesDNS, games, calls, QUIC, streamingWeb pages, email, file transfer, databases
Go deeper: datagram sizes and fragmentation optional

A UDP datagram can in theory carry up to 65,507 bytes of data over IPv4 (the 65,535-byte IP maximum minus 20 bytes of IP header and 8 of UDP). But as you saw in chapter 3, Ethernet links only carry 1,500-byte packets. A bigger datagram is split into IP fragments, and if any one fragment is lost, the entire datagram is lost. Applications that care, like DNS and QUIC, therefore keep their datagrams comfortably below the path MTU; a payload of around 1,200 to 1,400 bytes is a common safe choice.

The UDP checksum is optional in IPv4 (a value of zero means "not computed") but mandatory in IPv6. Receivers drop datagrams that fail it, silently.

Try it yourself

1. See which ports are listening on your computer

These commands only read information. lsof ("list open files") works on macOS and Linux; on Windows use netstat -ano | findstr LISTENING. You might need sudo on Linux to see other users' processes, but it isn't required to see your own.

$ lsof -i -P -n | head
COMMAND    PID USER   FD   TYPE NODE NAME
mDNSRespo  345 root    8u  IPv4  UDP *:5353
rapportd   612 you     8u  IPv4  TCP *:49152 (LISTEN)
Safari    1234 you    31u  IPv4  TCP 192.168.1.20:51234->203.0.113.10:443 (ESTABLISHED)
Safari    1234 you    33u  IPv4  TCP 192.168.1.20:51235->203.0.113.10:443 (ESTABLISHED)

(Your list will differ; -P shows port numbers instead of names, -n skips name lookups.) Find an ESTABLISHED line: that's a 5-tuple. Notice the ephemeral source port (left) and the well-known destination port (right). Alternatively, netstat -an | grep LISTEN lists the sockets that are waiting for connections.

2. Send UDP datagrams between two terminals

nc (netcat) is a tiny tool for sending and receiving raw data. Open two terminal windows. In the first, start a UDP listener; in the second, send to it.

$ nc -u -l 9999
hello from terminal 2          # appears when you type in terminal 2 and press Enter
is this thing on?
$ nc -u 127.0.0.1 9999
hello from terminal 2
is this thing on?

Each line you type is sent as one UDP datagram from a random ephemeral source port to port 9999. -u means UDP; -l means listen. Now experiment: stop the listener with Ctrl+C and keep typing in terminal 2. Nothing complains. The datagrams vanish, and the sender is none the wiser (with a closed port, some systems report an ICMP "port unreachable" error on a later send, as in chapter 6, but you can't count on it). Repeat the test with TCP, leaving off -u, and you'll immediately get "Connection refused": TCP knows when nobody is listening.

Netcat versions differ. The command above is for macOS and for the common Linux netcat-openbsd. Some Linux versions (the "traditional" netcat) need nc -u -l -p 9999 for the listener. On Windows, use ncat from the Nmap package, or run the commands in WSL. If it doesn't work, check nc -h for your version's flags.

Distributed systems connection

Three ideas from this chapter come back later. First, services are addressed by host:port: every database node, cache and API server in a cluster is just an (IP, port) pair, which is why configuration files are full of them, and why "port already in use" errors are so common. Second, UDP is the natural carrier for heartbeats and gossip (chapters 16 and 18): lightweight messages sent every second, where losing one is fine because the next one is coming. Third, and most important: the network can drop your message and nobody tells you. UDP makes that visible. TCP hides it, but only partially, as we'll see. Any system built on a network has to be designed with that silence in mind.

Key takeaways

  • A port (16 bits, 0 to 65,535) identifies a program on a computer; IP gets the packet to the machine, the port picks the program.
  • Servers listen on well-known ports (443, 22, 53…); clients get a temporary ephemeral source port from the OS.
  • A flow is identified by the 5-tuple: protocol, source IP, source port, destination IP, destination port.
  • A socket is a program's endpoint for sending and receiving, bound to a protocol, address and port.
  • UDP has an 8-byte header and gives you ports and a checksum, but no connection, no ordering, no retransmission and no congestion control.
  • That minimalism is exactly right for DNS, real-time media, games and building new protocols such as QUIC.

Check your understanding

You have three tabs open to the same website over HTTPS. What do the three connections have in common, and what differs?

  1. Everything is the same; the OS tells them apart by timing
  2. The destination IP differs; the ports are the same
  3. Destination IP and port (443) are the same; the source ports differ
  4. The protocol differs for each tab
The server address and port are the same, so the operating system gives each connection its own ephemeral source port. The 5-tuple therefore differs in the source port, which is what keeps the flows separate.

What is a socket?

  1. An endpoint the OS gives a program for sending and receiving data over the network
  2. A physical connector on a network card
  3. Another word for an IP address
  4. A kind of cable
A socket is a software handle, tied to a protocol, local address and port. The OS uses it to route incoming data to the right program.

Which is NOT something UDP provides?

  1. Port numbers
  2. A checksum to detect corruption
  3. Preserved message boundaries
  4. Automatic retransmission of lost datagrams
UDP gives ports, a checksum and datagram boundaries. Recovery from loss is left entirely to the application (or to a protocol built on top of UDP such as QUIC).

Why do live video calls usually prefer UDP-style delivery for the media?

  1. UDP is always faster in raw bandwidth
  2. Retransmitted old data arrives too late to be useful, so it's better to skip it than to wait
  3. UDP packets can't be lost
  4. Video can't be sent over TCP at all
Real-time media has a deadline. Waiting for a lost fragment stalls everything behind it, while skipping a few milliseconds of audio is barely noticeable. (Video can be sent over TCP, and often is for streaming, but interactive calls favour freshness over completeness.)

You send a UDP datagram to a port where nothing is listening. What is the most likely visible result in your program?

  1. A guaranteed error message right away
  2. The OS retries until the listener appears
  3. Usually nothing: the send succeeds locally and the datagram is simply discarded
  4. The router stores it until someone listens
UDP has no handshake, so "send succeeded" only means the OS accepted the data. You might get an ICMP "port unreachable" later on some systems, but the basic behaviour is silence, which is the key difference from TCP's "Connection refused".

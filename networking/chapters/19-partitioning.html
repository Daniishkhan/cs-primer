Partitioning & Consistent Hashing

Replication (chapter 18) gives you copies of the same data. But what if the data is too big for any one machine to hold, or too busy for any one machine to serve? Then you must split it up. The trick is deciding which piece lives where, and doing it so that adding a machine doesn't cause chaos.

Why this matters

Every large database, cache and message system you will ever use splits its data across machines: Cassandra, DynamoDB, MongoDB, Redis Cluster, Kafka, Memcached fleets. They all need an answer to two questions: "which machine holds this key?" and "what happens when the set of machines changes?" The second question has one famously elegant answer, consistent hashing, and you will build it in your head in this chapter.

Why split the data at all?

Replication copies the same data onto several machines. That helps with failures and with read traffic, but every machine still holds everything. If your data is 50 terabytes and a server's disks hold 4, copying it more times doesn't help. And if one machine can only handle 10,000 writes per second but you receive 200,000, more copies don't help either, because every write must still reach every copy.

The fix is partitioning (also called sharding; each piece is a partition or shard): cut the data into pieces and give each piece to a different machine. Now each machine holds only a fraction of the data and handles only a fraction of the traffic. Need more room? Add machines.

Analogy: a library that outgrew its building

A library with one room works until it has a million books. So you open branches: fiction downtown, science at the university, children's books in the suburbs. Each branch holds only part of the collection, and a visitor needs a rule for finding the right branch (a sign at the door, a catalogue, a librarian who knows). Replication, by contrast, is photocopying every book into every branch.

Where it breaks down: a library can't ask "what happens when I add a branch and half the books must move overnight, while people are still borrowing them?" A database has to answer exactly that.

Partitioning and replication work together

These two ideas solve different problems, and real systems almost always use both: split the data into partitions, then keep several replicas of each partition on different machines. One replica of each partition is usually the leader (it takes the writes) and the others are copies (chapter 18).

A handy way to remember it: partitioning is about capacity (more data and more traffic than one machine can take), replication is about survival and speed (copies that outlive failures and sit closer to users). The rest of this chapter is about partitioning, and in particular about one question: given a key like user:8431, which partition owns it?

Strategy 1: split by key range

The most natural idea is to cut the key space into contiguous ranges, like the volumes of a paper encyclopedia: names starting A–F on partition 1, G–M on partition 2, and so on. Looking up a key means finding which range it falls into.

The big advantage is that neighbouring keys live together. A range scan such as "all customers whose name starts with Ma" or "all sensor readings between 9:00 and 9:05" touches one partition, or a couple of adjacent ones. Sorted data is easy to browse.

The danger is skew: the load may not be spread evenly. Suppose you partition a log of events by timestamp, one partition per month. Every new event has today's timestamp, so every write in the world lands on the single newest partition, while the other eleven sit idle. That overloaded partition is called a hot spot.

Strategy 2: split by hash of the key

The alternative is to run each key through a hash function first: a deterministic recipe that turns any input into a big, seemingly random number. The same key always gives the same number, but similar keys (user:1, user:2) give wildly different ones. Then you split the hash values among partitions. Writes for consecutive timestamps now scatter evenly over all partitions.

The price: you've destroyed the ordering. Keys that were neighbours are now scattered across all partitions, so a range scan has to ask every partition and merge the answers. Here is the trade-off side by side:

By key rangeBy hash of key
Spreads load evenly?Only if keys are spread evenly (timestamps are not)Yes, in general
Range scansCheap: one or few partitionsExpensive: ask all partitions
Lookup by exact keyFineFine
Good fitSorted data you browse in orderLarge key-value stores (sessions, users, caches)

Some systems offer a middle path: hash the first part of a compound key to pick the partition, and keep the second part sorted inside it. For example, partition by user_id, but keep that user's posts sorted by time. Then "one user's posts from last week" is a cheap range scan on a single partition.

Hot spots and skew, even with hashing

Hashing evens out the keys, not the traffic per key. If one celebrity's account receives a million likes a minute, every one of those operations hashes to the same partition, because it's the same key. The hash function can't help; it is doing exactly what it should.

Common mitigations, in the order you'd usually try them:

  • Cache it. If the hot key is mostly read, a cache in front of the partition absorbs the traffic (chapters 13 and 14).
  • Split the hot key. Append a small random number to its name, so celebrity becomes celebrity#0 … celebrity#9. Writes now spread over up to ten partitions. The cost: reading the total means fetching all ten and adding them up, so you only do this for the handful of keys that need it.
  • Give hot data more room. Split the busy partition further, or move it to a bigger machine.

Common misconception: "hashing fixes hot spots"

Hashing fixes key-range skew (like timestamps). It does nothing for a single extremely popular key. Spotting and handling those few hot keys is usually an ongoing, partly manual job.

The naive way: hash(key) mod N

Now suppose you've chosen hashing, and you have N servers numbered 0 to N−1. The simplest possible rule: take the hash of the key, divide by N, and use the remainder (hash mod N) as the server number. It is evenly spread, takes one line of code, and works perfectly... until N changes.

Take 10 keys whose hash values happen to be 0 through 9, and watch what happens when a fourth server is joined by a fifth:

hash0123456789
mod 4 (4 servers)0123012301
mod 5 (5 servers)0123401234
Moved?nonononoyesyesyesyesyesyes

Six of ten keys changed servers, just because we added one machine. Extend the table far enough and a pattern emerges: going from N to N+1 servers, a key keeps its server only if hash mod N equals hash mod (N+1), which happens for just N out of every N×(N+1) consecutive hash values. So a fraction of about 1/(N+1) stay and about N/(N+1) move:

Going from…2 → 34 → 510 → 11100 → 101
Fraction of keys that move≈ 67%≈ 80%≈ 91%≈ 99%
Fraction that should need to move≈ 33%≈ 20%≈ 9%≈ 1%

The second row is the key insight. The new server should simply take an equal share, about 1/(N+1) of the data, from the others. Mod-N moves almost everything. In a cache, that means nearly every lookup suddenly misses, and the database behind it gets hit by the whole load at once. In a database, it means copying most of the data across the network just to add one box.

Consistent hashing: the ring

The fix, published in 1997 for web caching and later made famous by Amazon's Dynamo, is to stop dividing by N. Instead, imagine the whole range of hash values bent into a circle: the biggest hash value wraps around to sit right next to zero. This is the hash ring.

  1. Place the servers on the ring. Hash each server's name (or address) and put it at that position on the circle.
  2. Place the keys on the ring. Hash each key with the same function and put it at its position.
  3. The owner of a key is the first server you meet walking clockwise from it. (Walking past the top wraps around to zero.)

Servers and keys use the same hash function, so everything lives in one shared coordinate system. Nobody needs to know N.

This is why it works: adding a server only splits one arc. The new server E takes the keys between its predecessor (C) and itself, and those used to belong to its successor (D). Servers A and B aren't even involved. On average, with N servers, a new one takes about 1/(N+1) of the keys, which is exactly the minimum it could take. Removing a server is the mirror image: its keys pass to the next server clockwise, and nobody else is touched.

Analogy: a circular running track with water stations

Runners (keys) stand scattered around a circular track. Each runner walks clockwise to the first water station (server) they find and uses that one. If the organisers add a new station, only the runners on the stretch just before it switch. Everyone else's nearest station hasn't changed. If a station closes, only its customers walk on to the next.

Where it breaks down: real stations are placed by hashing, i.e. effectively at random, so one station might end up with a very long stretch and be swamped. The next section fixes that.

Virtual nodes: fixing the unevenness

There is a catch. With only a few servers placed at random positions, the arcs between them are wildly uneven. Three random points on a circle will typically leave one server with a huge slice and another with a sliver. (You'll see it in the widget below: with four nodes one of them can end up owning almost nothing.)

The remedy is virtual nodes (often shortened to vnodes). Instead of placing each physical server on the ring once, place it many times: hash A#0, A#1, …, A#127, say, and let all those points belong to server A. Each server now owns many small slices scattered around the ring instead of one big one. By the law of averages the total comes out close to equal.

Virtual nodes have a second benefit: when a server joins, it takes small slices from many existing servers, so the data transfer is spread across the whole cluster instead of hammering one neighbour. And if a server is bigger than the others, give it more points so it takes a proportionally larger share.

Which node do I ask? Request routing

Partitioning creates a new problem: a client wants to read user:8431. Which of the machines should it talk to? There are three standard answers.

1. Ask any node

The client contacts any node. If that node doesn't own the key, it forwards the request (or replies "try node 3"). Simple for clients, costs an extra hop sometimes. Cassandra and Redis Cluster work roughly this way.

2. A routing tier

Clients talk to a partition-aware proxy or load balancer (chapter 14) that knows the map and sends each request to the right place. Clients stay dumb; the proxy must be kept up to date and not become a bottleneck.

3. Smart clients

The client library holds the partition map itself and connects straight to the owner. Fastest path, but every client must learn about changes.

All three depend on someone keeping an accurate, shared partition map: which node owns which slice right now. Two common ways to keep it:

  • A coordination service such as ZooKeeper or etcd stores the map; everyone consults it or subscribes to changes. This needs the machines to agree on the map, the topic of chapter 20.
  • Gossip. Nodes periodically swap what they know with a few random peers, so news of a change spreads through the cluster like a rumour. Dynamo-style systems do this.

Rebalancing: changing the cluster while it runs

Moving data between machines costs network bandwidth and disk work (chapter 13), and it happens while real traffic keeps flowing. A few practical rules follow from that:

  • Create many more partitions than machines and move whole partitions between them. For example, Redis Cluster divides keys into 16,384 fixed hash slots and assigns ranges of slots to nodes; adding a node means handing it some slots. The key-to-slot mapping never changes, only the slot-to-node map does.
  • Move in the background and throttle it so it doesn't starve user traffic. The old owner keeps serving until the new one has caught up, then ownership switches.
  • Prefer manual or supervised rebalancing. An automatic system can misread a slow node as dead and start a costly data shuffle that makes things worse (chapter 16).
Go deeper: fixed slots versus ring tokens optional

The ring and the "fixed number of partitions" approach are close cousins. A ring with many virtual nodes is, in effect, a large number of small partitions whose boundaries are chosen by hashing node names. A fixed-slot scheme such as Redis Cluster's chooses the boundaries up front (slot = a hash of the key modulo 16,384) and only moves the slot assignments. Because the modulus (16,384) never changes, it avoids the mod-N disaster: the number that varies is the node count, and that is used only when assigning whole slots to machines.

Another popular variant, rendezvous hashing (or highest-random-weight), skips the ring entirely: for each key, compute a score for every node and pick the highest. It also moves only about 1/N of keys when nodes change, at the cost of scoring every node per lookup.

Try it yourself

Part 1: break mod-N at your keyboard

This shell loop hashes eight key names with cksum (a simple checksum, not a production hash, but fine for a demo) and shows each key's server number with 4 servers versus 5. It is read-only and works on macOS and Linux; on Windows use WSL or Git Bash.

$ for k in user1 user2 user3 user4 user5 user6 user7 user8; do
    h=$(printf %s "$k" | cksum | cut -d' ' -f1)
    echo "$k hash=$h mod4=$((h%4)) mod5=$((h%5))"
  done
user1 hash=3872527515 mod4=3 mod5=0
user2 hash=2486782792 mod4=0 mod5=2
user3 hash=1176537748 mod4=0 mod5=3
user4 hash=1911551214 mod4=2 mod5=4

user8 hash=3196294677 mod4=1 mod5=2

On this run, 7 of 8 keys changed server when we went from 4 to 5 (your numbers should match, since cksum is deterministic; a different hash function would differ). That's the N/(N+1) effect in the flesh.

Part 2: use the ring widget

  1. Press Reset. Note the bars: with one point per node the shares are very uneven (on a fresh page, one node holds over half the keys and another holds just one).
  2. Press + Add a node. Read the box: how many keys moved with consistent hashing, and how many would have moved with mod N? Which node received all the moved keys?
  3. Choose a node with many keys from the drop-down and remove it. Where did its keys go? (Look at the white rings: they should be next to where the removed node sat, clockwise.)
  4. Switch to 8 points per node and compare the bars. Add and remove nodes again. Do the moved counts get closer to "total keys ÷ nodes"?
  5. Type your own name into Look up any key. The white diamond shows where it lands and which node owns it.

A thought exercise: your cache fleet has 20 servers on a ring, and one dies. About what fraction of cached keys lose their server? (About 1/20, or 5%, versus around 95% with mod N.) Now imagine the surviving servers each suddenly get 5% more traffic *and* the database sees 5% more misses. Is that survivable? That's the kind of arithmetic capacity planning is made of.

Distributed systems connection

Partitioning answers where does the data live? but quietly creates harder questions. Who decides when a node has joined or died, and who is the authority on the partition map? What if two machines both believe they are the leader for partition P3? Every one of these needs a group of machines to agree on one answer, even while some of them crash or can't talk to each other. That problem, consensus, is the subject of the next chapter, and it is the machinery underneath most coordination services.

Key takeaways

  • Partitioning splits data across machines for capacity and throughput; replication copies it for durability and read speed. Real systems do both.
  • Key-range partitioning keeps neighbours together (cheap range scans) but risks hot spots; hash partitioning spreads load but scatters ranges.
  • Hashing doesn't fix a single super-popular key; that needs caching or splitting the key.
  • hash(key) mod N reshuffles about N/(N+1) of all keys when N changes by one. Far more than necessary.
  • Consistent hashing puts keys and nodes on a ring; a key belongs to the next node clockwise, so a join or leave moves only about 1/N of the keys.
  • Virtual nodes (many ring points per server) even out the load and spread rebalancing work.
  • Clients find the right partition via any-node forwarding, a routing tier or a smart client, all backed by a shared partition map that machines must agree on.

Check your understanding

A cache cluster uses hash(key) mod N and grows from 10 to 11 servers. Roughly what fraction of keys end up on a different server?

  1. About 1/11 (9%)
  2. About half
  3. About 10/11 (91%)
  4. None, because the hash doesn't change
The hash of a key doesn't change, but the divisor does. A key keeps its server only when hash mod 10 equals hash mod 11, which is rare, so roughly N/(N+1) = 10/11 of keys move. A new server only needs about 1/11 of them; consistent hashing achieves that minimum.

On a consistent-hashing ring, which node owns a given key?

  1. The first node found going clockwise from the key's position
  2. The node with the smallest name
  3. The node with the fewest keys at that moment
  4. The node whose hash is numerically closest, in either direction
The rule is one-directional: walk clockwise (towards larger hash values, wrapping past the top to zero) until you reach a node. Because the rule only looks at the nearby neighbour, adding or removing a node only affects the arc next to it.

Why do real consistent-hashing systems use virtual nodes?

  1. To make hashing faster
  2. To keep several copies of each key for durability
  3. To let clients skip the hash function
  4. To make each server's share of the ring more even, and to spread rebalancing work across many servers
With only a handful of random points, arcs vary hugely in size. Giving each server many points averages that out. (Durability comes from replication, a different mechanism.)

You partition a database by hash of the key. Which query becomes more expensive than if you had partitioned by key range?

  1. Fetch one record by its exact key
  2. Fetch all records with keys between "ma" and "mf"
  3. Write a new record
  4. Delete one record by its exact key
Hashing scatters neighbouring keys across partitions, so a range query has to consult all of them. Exact-key operations hash to one partition either way.

One celebrity's account gets 1,000 times more writes than anyone else's, even though the data is hash-partitioned. What is a reasonable fix?

  1. Use a better hash function
  2. Add more servers to the ring
  3. Split that one key into several sub-keys (e.g. a random suffix 0–9) so its writes spread across partitions
  4. Switch to key-range partitioning
Every write to the same key hashes to the same place whichever function you use, and adding servers doesn't split a single key. Salting the key spreads its writes, at the cost of having to read all the sub-keys to get the total.

Which statement correctly contrasts partitioning and replication?

  1. Partitioning keeps identical copies; replication splits data into pieces
  2. Partitioning gives each machine a different piece of the data; replication stores the same data on several machines
  3. They are two names for the same thing
  4. Partitioning is only used for caches; replication is only used for databases
Partitioning (sharding) divides the data set to scale capacity; replication duplicates it for fault tolerance and read performance. Most systems combine them, as in the first diagram of this chapter.

Why Distribute? Partial Failure

You now know how one computer talks to another. Part 6 asks what happens when many computers must work together as if they were one. The answer begins with a single, slippery idea: in a distributed system, some parts can be working while others are broken, and you often cannot tell which is which.

Why this matters

Almost every serious software system today is distributed: a web app talking to a database, a mobile app talking to a backend, services calling services. The mistakes beginners make here are remarkably consistent, and nearly all of them come from treating the network as if it were a reliable wire. This chapter gives you the vocabulary and the mental model (partial failure, the fallacies, failure modes, availability math) that the next six chapters build on.

Why not just use one big computer?

A single computer is wonderful. Everything is in one memory, one clock ticks, and a function call either returns or the program crashes. If you can solve your problem on one machine, you usually should. People move to many machines for four reasons:

Scale

The load is bigger than one machine can handle: more requests per second, more data than fits on one disk, more computation than one CPU can finish in time.

Availability

One machine is a single point of failure. With copies on several machines, the service survives hardware failure, software crashes and maintenance.

Latency

Physics (chapter 13) says a user in Sydney is ~100+ ms from a server in Virginia. Put servers near users and requests get faster.

Legal and organisational

Laws may require data about a country's citizens to stay in that country. Companies are split into teams that each own, deploy and scale their own services independently.

Scaling up vs scaling out

There are two ways to add capacity. Vertical scaling (“scale up”) means buying a bigger machine: more cores, more RAM, faster disks. Horizontal scaling (“scale out”) means adding more machines and splitting the work between them.

Horizontal scaling is the engine of modern infrastructure, and it is only easy when machines don't need to coordinate (like the stateless web servers in chapter 14). As soon as they must share data, agree on things or stay consistent, you've built a distributed system: several computers that communicate over a network to accomplish a common task, and that look like a single system to their users.

What makes distribution fundamentally different

It is tempting to think a distributed program is the same as a single-machine program with some network calls sprinkled in. It is not. Four properties change everything:

1. No shared memory

On one machine, threads can read the same variable. Across machines, there is no “the” variable. Each machine has its own memory and its own idea of the truth.

2. Only messages, over an unreliable network

Machines learn about each other solely by exchanging messages (chapters 3 to 8), which can be delayed, lost, duplicated or reordered.

3. No global clock

Each machine has its own clock, and they drift apart. You can't reliably say which of two events on two machines happened first. Chapter 17 is all about this.

4. Independent failures

Any machine, disk, switch or cable can fail on its own, at any time, while everything else carries on.

Partial failure

Think about how a single computer fails. Mostly it works, or it crashes entirely (and the whole program stops). The in-between cases are rare and usually obvious. A function call returns a value or throws an error, and that's it.

A distributed system fails differently. Machine A is fine, machine B has crashed, the link between B and C is dropping half its packets, and D is up but swamped and answering slowly. The system as a whole is neither “working” nor “down”: it is partially failed. Worse, you often can't tell which part is broken, because the only evidence you ever receive is messages, and the absence of a message means so many different things.

Analogy: asking a friend abroad to buy a ticket

You mail a letter to a friend overseas: “please buy two concert tickets with my money.” Weeks pass and no reply. What happened? Maybe your letter was lost. Maybe your friend never opened it. Maybe they bought the tickets and their reply was lost. Maybe they are on holiday and will reply next week. From where you stand, all four look exactly the same: an empty mailbox. And what you do next (buy tickets yourself? send the letter again?) depends on which one is true.

Where it breaks down: letters take weeks and a computer can wait milliseconds, so the “wait a bit more” decision gets made thousands of times a second, automatically, with no human intuition to help.

Common misconception: a network call is just a slow function call

Hiding a network call behind something that looks like user = getUser(42) is convenient, but dangerous. A local call has two outcomes: a result or an exception. A remote call has a third: nothing comes back and you don't know whether it executed. Code that ignores that third outcome works perfectly in testing and fails in production at 3 a.m.

The 8 fallacies of distributed computing

In the 1990s, engineers at Sun Microsystems (the list is usually credited to L. Peter Deutsch, with additions from colleagues) wrote down the false assumptions newcomers repeatedly make. They became known as the fallacies of distributed computing. Every one of them has appeared in this guide already:

1. The network is reliable

Packets are dropped by overloaded routers and bad Wi-Fi; cables are cut; a switch reboots. TCP (ch. 8) retransmits lost packets, but it can't fix a connection that's gone. It just gives up eventually. Plan for: timeouts and retries.

2. Latency is zero

Each round trip costs from 0.5 ms (same data center) to 150 ms (across an ocean) (ch. 13). A loop making 1,000 sequential remote calls can take minutes. Plan for: batching, caching, fewer round trips.

3. Bandwidth is infinite

Links have limited capacity and TCP's congestion control shares it among everyone (ch. 8). Sending huge payloads, or chatty ones, saturates links. Plan for: compact formats, pagination, compression.

4. The network is secure

Anyone on the path can read unencrypted traffic, and attackers may sit inside your own network. Encryption (ch. 11) and authentication are not optional extras. Plan for: TLS everywhere, least privilege.

5. Topology doesn't change

Servers are added, removed, moved and autoscaled. IP addresses change (DHCP, ch. 6), routes shift (ch. 5), DNS answers go stale (ch. 9). Plan for: names and discovery, never hard-coded addresses.

6. There is one administrator

The Internet is a network of networks run by different organisations (ch. 0). Even inside one company, many teams deploy on their own schedules. Plan for: versioned interfaces and graceful degradation when others are broken.

7. Transport cost is zero

Serialising data (ch. 12) uses CPU, and moving bytes costs real money (cloud providers charge for data leaving a region). Plan for: keeping data close to the code that uses it.

8. The network is homogeneous

Different hardware, operating systems, protocol versions, MTUs (ch. 3), languages and byte orders must interoperate. Plan for: standard protocols and well-specified data formats.

Read the list as a checklist of excuses you are no longer allowed to make. When something goes wrong in a distributed system, one of these assumptions is almost always the culprit.

A taxonomy of failures

To design a system that tolerates failures you must say which failures. Researchers describe a ladder of failure models, from mild to nasty. The weaker the assumption you can get away with, the easier your design; the stronger the failures you must survive, the harder.

Failure modeWhat happensExample
Crash-stopA node works correctly, then halts forever. It never does anything wrong; it just stops.A server's power supply dies and it's thrown away
Crash-recoveryA node crashes, then restarts later. Memory is lost; data on disk survives (if it was written properly).A process is killed by an out-of-memory error and restarted by a supervisor
OmissionA node (or the network) fails to send or deliver some messages, while otherwise behaving correctly.A router drops a packet; a full buffer ignores a request
Timing / performanceThe result is right but late: too slow to be useful, or clocks run too fast or too slow.A garbage-collection pause freezes a process for 8 seconds; a disk starts to fail and is 100× slower
Network partitionThe network splits into groups; machines can talk within a group but not between groups.A switch fails and half of the racks lose contact with the other half
ByzantineA node behaves arbitrarily: sends wrong, contradictory or malicious messages.A bug corrupts data in memory so a node sends garbage; an attacker controls a server

The partition is the nastiest honest failure, because nobody is broken yet the system is split. Both sides may keep accepting writes, and when the network heals, their data disagrees. Handling that is the subject of chapter 18 (the famous CAP theorem is exactly about this situation).

Byzantine failures: usually out of scope

Byzantine failures (named after the “Byzantine Generals” thought experiment) cover nodes that lie, whether through a bug, corruption or an attacker. Tolerating them is possible but expensive and complex; it's what blockchains and some aircraft-control systems must do. Most systems inside one company's data centers assume nodes are honest (they crash or are slow, but they don't actively lie), and use ordinary checksums and authentication to catch accidents. This guide assumes the same.

The mathematics of availability

Availability is the fraction of time a service is working: uptime ÷ (uptime + downtime). It's usually quoted in “nines”. Each extra nine shrinks the allowed downtime tenfold:

Availability“Nines”Downtime per yearDowntime per 30-day month
99%two nines≈ 3.65 days (87.6 hours)≈ 7.2 hours
99.9%three nines≈ 8.8 hours≈ 43 minutes
99.99%four nines≈ 53 minutes≈ 4.3 minutes
99.999%five nines≈ 5.3 minutes≈ 26 seconds
99.9999%six nines≈ 32 seconds≈ 2.6 seconds

(Check one: a year has 365 × 24 × 60 = 525,600 minutes. At 99.99%, downtime is 0.0001 × 525,600 ≈ 52.6 minutes.)

Components in series: dependencies multiply

If a request needs service A and service B and service C all to be up, the chance all are up is the product of their individual availabilities (assuming they fail independently). Suppose each of 10 services you depend on is 99.9% available:

0.99910 ≈ 0.990 = 99.0%

Ten “three nines” services give you only two nines: about 87 hours, or 3.6 days, of downtime per year. Each extra hard dependency chips away at you. A system can never be more available than the things it needs in series.

Components in parallel: redundancy multiplies the failures

If instead you have n redundant copies and only need one to be up, the service fails only when all copies are down at the same time. The chance a copy is down is (1 − a), so:

availability = 1 − (1 − a)n

Two copies of a 99.9% component: 1 − (0.001)² = 1 − 0.000001 = 99.9999%, six nines, from two so-so machines. Three copies: nine nines. Redundancy is enormously powerful. Combine both rules: if each of your 10 dependencies is itself a pair of 99.9% replicas (99.9999% each), the chain is 0.99999910 ≈ 99.999%, five nines.

The fine print on redundancy

The parallel formula assumes the copies fail independently. In real life, they often don't: two replicas in the same rack share a power supply, two copies running the same buggy release crash on the same input, and a bad configuration pushed to every server fails them all at once. Failing over from one copy to another also takes time and must itself work correctly, and whatever does the switching (a load balancer, a coordinator) is a new component in series. Treat the formula as an upper bound, not a promise.

What really happened

The practical dilemma: if the client retries the payment, then in the first two scenarios that is exactly right, but in the last three the customer gets charged twice. If the client doesn't retry, then in the first two scenarios the customer's order silently fails. There is no choice that is right in every case, because the client lacks the information. Every serious distributed protocol is, in one way or another, a way of manufacturing the missing information, or of making the wrong guess harmless.

Go deeper: gray failures optional

Operators have a name for the most confusing real-world case: a gray failure, where a component is neither clearly up nor clearly down. A disk that still works but takes 2 seconds per read, a server that passes its health check but fails real requests, a network port that drops 3% of packets. The health checker says “fine”, users say “broken”. These are more common, and harder to diagnose, than clean crashes.

Where we go from here

We've established the problem: independent machines, an unreliable network, and no way to tell “slow” from “dead”. The next chapter, Failure, Timeouts & Retries, develops the practical toolkit: how to choose a timeout, how to detect failed nodes, how to retry without making things worse, how to make operations safe to repeat (idempotency), and why even two perfectly honest parties cannot be certain they agree (the Two Generals problem). After that, chapters 17 to 20 tackle time, copies of data, splitting data, and agreement.

Key takeaways

  • We distribute for scale, availability, latency and sometimes legal or organisational reasons. If one machine suffices, prefer one machine.
  • Distributed systems have no shared memory, only unreliable messages, no global clock and independent failures.
  • The defining difficulty is partial failure: some parts work, some don't, and from the outside you often can't tell which.
  • The 8 fallacies (reliable network, zero latency, infinite bandwidth, secure, static topology, one administrator, free transport, homogeneous network) are all false.
  • Failure models range from crash-stop to crash-recovery, omission, timing, partitions and Byzantine; most company systems assume non-Byzantine.
  • Availability: dependencies in series multiply (10 × 99.9% ≈ 99.0%); replicas in parallel give 1 − (1 − a)n, if failures are truly independent.
  • After a timeout, the client cannot tell whether a request was lost, was never processed, was processed, or is still being processed.

Check your understanding

What is the defining feature of partial failure?

  1. The whole system crashes at once
  2. Only the slowest machine fails
  3. Some components fail while others keep working, and observers often cannot tell which are which
  4. A failure that is fixed automatically
A single computer mostly either runs or crashes as a whole. In a distributed system some nodes or links can fail while the rest carry on, and since you only observe messages, silence is ambiguous.

You depend on 5 services in series, each 99.9% available. Roughly what is your best-case availability?

  1. About 99.5%
  2. 99.9%
  3. About 99.99%
  4. 100%
0.9995 ≈ 0.995. Dependencies in series multiply, so you can never exceed the availability of your weakest dependency, and each additional one lowers the total further.

Two independent replicas are each 99% available, and either one can serve any request. What is the combined availability?

  1. 99%
  2. 98%
  3. 99.9%
  4. 99.99%
The service is down only if both are down: 0.01 × 0.01 = 0.0001, so availability is 1 − 0.0001 = 99.99%. (This assumes independence; correlated failures make the real number lower.)

A client's request times out. Which of the following can the client conclude for certain?

  1. The server crashed
  2. It does not know whether the server executed the request
  3. The request was lost in the network
  4. The server is overloaded
The request may have been lost, the server may have crashed before or after doing the work, the reply may have been lost, or the server may just be slow. All of these look identical from the client's side.

Which of these is a network partition?

  1. One server's disk fills up
  2. A server is restarted after a crash
  3. A switch failure leaves two groups of healthy servers unable to reach each other
  4. A server sends corrupted data on purpose
In a partition no node has necessarily failed; the network between groups has. Each side sees the other as silent. A full disk is a node fault, a restart is crash-recovery, and corrupted data on purpose is Byzantine.

Lab 5: A Replicated Key-Value Store

Three storage nodes, one client library, and the dial from chapter 18 that you can finally turn with your own hands: how many copies must a write reach, and how many must a read ask? You'll watch stale reads appear and disappear, cut nodes off the network and see what the client does, and make a retried "add one" count exactly once. About 100 lines of your own Python on top of a provided node server, standard library only.

Why this lab matters

Chapters 16 and 18 make claims that sound abstract on the page: "a timeout is a guess, not a fact", "R + W > N means reads see the latest write", "a retry can charge a customer twice". In this lab each claim becomes a test you can run, break and fix. The design you'll build is the one behind Dynamo-style databases such as Cassandra and Riak: no leader, just a client that talks to a few replicas and trusts arithmetic.

What you'll build

Six milestones, each building on the last:

  1. One node: a store that remembers key → (value, version), and a call() that talks to it over a socket.
  2. Replicated writes: the client writes to W of the three nodes.
  3. Quorum reads: the client reads from R nodes and keeps the newest. You'll see stale reads when R + W ≤ N and none when R + W > N.
  4. Failures: a per-replica timeout, nodes that are paused, killed and restarted, and an operation that fails cleanly when a quorum can't be reached.
  5. Retries and idempotency keys: exponential backoff with jitter, and an "increment" that is safe to repeat.
  6. Read repair: a read that quietly fixes the replicas it found behind.

Three design decisions, up front

Real systems answer these in many ways. Here is what this lab does, and why.

1. The version is a Lamport pair, not a timestamp

Every stored value carries a version, and a replica keeps whichever version is newest (chapter 18: "the reader takes the answer with the highest version"). What should a version be?

The tempting answer is the wall-clock time of the write. Chapter 17 showed why that is dangerous: if one client's clock is two seconds slow, its later write gets an earlier timestamp and silently loses (last-write-wins with skewed clocks). So we use a Lamport clock instead: a plain counter that every client keeps and moves forward. The version is a pair (counter, tag):

  • counter: before a write, the client bumps its counter. Whenever it sees a version from a replica, it moves its counter up to at least that value (the "receive" rule from chapter 17). So a client that has read version 7 will write version 8 or higher.
  • tag: the id of the operation that wrote it (say "c1-4"). If two clients pick the same counter, the tag breaks the tie, so all replicas agree on a single winner: tuples compare left to right in Python, so (3, "c2-1") > (3, "c1-9").

This is the "order by (L, process id)" trick from chapter 17. The tag does a second job in milestone 5, where it doubles as an idempotency key.

The limit of this design

A client that has never read a key has a counter of 0, so a blind put can get a lower version than an existing value and be silently ignored by the replicas. (The cure is to read before you write, which is exactly what increment does.) And two clients writing the same key at the same moment produce two versions where one simply wins; detecting that they were concurrent needs version vectors (chapter 17). The lab keeps one writer per key to stay focused.

2. Fault switches, not real timing races

Failures in a real cluster happen at random. That is hopeless for a repeatable test, so each Node has switches that you flip from code:

SwitchWhat the client seesReal-world cause it stands for
node.pause() / resume()The connection works, but no reply ever comes: a timeout.Overload, a long garbage-collection pause, a lost packet: "slow or dead, can't tell" (chapter 16).
node.kill()Connection refused at once: a definite answer.Process crashed; machine up, nobody listening.
node.restart(wipe=False)The node is back with its data.The process restarted and reloaded its data from disk.
node.restart(wipe=True)The node is back, empty.The data lived only in memory (or the disk was replaced).
node.drop_next_replies(n, "put")A timeout, but the node did the work.The reply packet was lost on the way back. The nastiest failure of all.

Kept or lost on restart? Both, on purpose, because real systems differ. A node that writes every change to disk before replying keeps its data across a crash (wipe=False); a purely in-memory node loses it (wipe=True). The lab's nodes store everything in a Python dict, so the default for a "restart" in your experiments is a choice you make each time. Keep in mind what the choice means for the quorum arithmetic: a wiped node that rejoins looks healthy but has forgotten acknowledged writes, which quietly lowers the number of copies below W. Milestone 6 shows how reads can heal this.

3. The client is the coordinator, and it asks one replica at a time

Dynamo-style systems send a request to all replicas at once and use the first W (or R) answers. We send to replicas one after another, in an order you can control with prefer=[0, 1, 2]. It is slower, but it means "which replicas got the write" is exactly determined, which is what makes stale reads reproducible instead of a coin toss. (Making it parallel is a stretch goal.)

Two ideas you'll use everywhere

  • One JSON object per line is the framing from Lab 1's milestone 3: json.dumps(obj) + "\n" out, read up to the newline, json.loads in. encode() and read_line() are provided.
  • The nodes never talk to each other. All replication logic lives in the client. That keeps the lab small, and it is exactly how leaderless systems work: the "coordinator" is just whoever takes the client's request.

Milestone 1: a single node

Start small: one server that stores values, and a function that talks to it. The provided Node class does the socket work and calls Store for every get and put. The protocol is two requests:

→ {"op": "put", "key": "x", "value": "hello", "version": [1, "c1-1"]}
← {"ok": true, "applied": true}
→ {"op": "get", "key": "x"}
← {"ok": true, "value": "hello", "version": [1, "c1-1"], "done": null}

Two rules make the Store safe for replication. First, a put is applied only if its version is newer than what the node already holds. That makes every write idempotent and order-independent: a delayed, duplicated or reordered put can never move a key backwards. Second, a key that was never written reads as (None, (0, "")), so "never written" is just the oldest possible version and comparisons need no special case.

call() is the client's only way to talk to a node. It must tell apart two kinds of failure, because they mean different things (chapter 16): ReplicaDown (refused or hung up: the machine answered "nobody here", a definite failure) and ReplicaTimeout (no reply within the deadline: unknown).

Solution spoiler 
def get(self, key):
    return self.data.get(key, (None, NO_VERSION))
def put(self, key, value, version):
    version = tuple(version)
    if version > self.get(key)[1]:
        self.data[key] = (value, version)
        return True
    return False
def call(port, request, timeout=1.0):
    try:
        with socket.create_connection((HOST, port), timeout=timeout) as sock:
            sock.settimeout(timeout)
            sock.sendall(encode(request))
            line = read_line(sock)
    except socket.timeout:
        raise ReplicaTimeout(f"no reply from port {port} within {timeout}s")
    except OSError as e:                       # refused, reset, broken pipe ...
        raise ReplicaDown(f"port {port}: {e}")
    if line is None:
        raise ReplicaDown(f"port {port} closed the connection")
    return json.loads(line.decode("utf-8"))

Milestone 2: replicated writes

Now the client library. A write is successful once W replicas have acknowledged it. With N = 3 and W = 2, the value is stored on two machines before the caller hears "OK", so losing any one machine cannot lose it. This is the synchronous-replication trade-off of chapter 18, applied per request instead of per cluster.

The heart of the client is one helper, _quorum_call(request, need, prefer): send the same request to replicas in order until need of them have answered, and return those answers. Both put (need = W) and get (need = R) are built on it. For now, assume a healthy cluster; milestone 4 makes it robust.

put itself is short: get a fresh op_id, bump the Lamport counter to make the version (counter, op_id), and send {"op": "put", ...} to W replicas through _quorum_call.

Solution spoiler 
def _quorum_call(self, request, need, prefer=None):
    replies, errors = [], []
    for i in self._order(prefer):
        if len(replies) == need:
            break
        try:
            reply = call(self.ports[i], request, self.timeout)
        except ReplicaUnavailable as e:
            errors.append((i, e))
            continue
        if reply.get("ok"):
            replies.append((i, reply))
    if len(replies) < need:
        raise QuorumNotReached(need, len(replies), errors)
    return replies
def put(self, key, value, prefer=None, op_id=None):
    op_id = op_id or self._new_op_id()
    self.clock += 1
    version = (self.clock, op_id)
    self._write(key, value, version, op_id, prefer)
    return version

The solution's _quorum_call already includes milestone 4's error handling (the try/except and the final raise). For this milestone you can leave those out and let any ReplicaUnavailable propagate.

Milestone 3: quorum reads, and when they go stale

A read asks R replicas and returns the answer with the highest version. That's the whole algorithm, and the whole point of putting a version on every value: the replicas may disagree, and the version tells the client who is right.

Whether that read is guaranteed to see the latest write depends on one inequality (chapter 18): if R + W > N, every read set shares at least one replica with every write set. The figure above shows N = 3. Break the inequality and there are order combinations where the read lands entirely on replicas that missed the write.

The check proves this the brute-force way. For every combination of "which order the write tries replicas" (6 permutations) and "which order the read tries them" (6 permutations), 36 combinations in all, it writes an old value to all three nodes, then writes a new value to W of them, reads with R, and counts how often the read returned the old value. For R + W ≤ 3 that count must be above zero; for R + W > 3 it must be exactly zero.

Notice what R + W > N costs. With W = 3 every write needs all three nodes, so one dead node blocks all writes. With R = 3 one dead node blocks all reads. The majority setting (W = R = 2) is the one that survives any single failure for both. Milestone 4 lets you see that.

Milestone 4: timeouts, failures and clean errors

So far the cluster was healthy. Now make the client survive broken nodes. Chapter 16's rule applies to every replica call: always have a timeout, because from the outside "dead", "paused", and "reply lost" all look the same: silence. Your call() already raises ReplicaTimeout or ReplicaDown. Make _quorum_call catch those, skip that replica and try the next one, and only give up when there are not enough replicas left.

When it gives up, it must do so cleanly: raise QuorumNotReached(needed, got, errors), with the numbers, rather than hanging, returning half an answer, or pretending it worked. The caller needs to know that the write is not safely stored.

Common misconception: a failed write wrote nothing

Suppose W = 2, node 0 accepts the write, and then nodes 1 and 2 are unreachable. The client raises QuorumNotReached... but node 0 still holds the new value. Nothing undoes it, so a later read that happens to ask node 0 may return a value whose write was "reported as failed" (chapter 18 calls these failed writes that aren't undone). "Failed" means not guaranteed durable, not did not happen. This is the same lesson as "a timeout means you stopped waiting, not that the operation failed".

The check exercises each switch. A killed node is refused instantly and costs nothing. A paused node costs exactly one timeout (0.2 s in the check), then the client moves on. With two of three nodes gone and W = 2, put raises QuorumNotReached with needed=2, got=1. It also restarts nodes with the data kept and with the data wiped, so you can see both behaviours.

Milestone 5: retries and idempotency keys

A transient failure (a node restarting, one lost packet) is often gone a moment later, so retrying is worth it. But chapter 16 warned about two dangers, and you'll handle both.

Danger 1: the retry storm

If every client retries immediately, a struggling cluster gets more traffic exactly when it can least cope. The cure is exponential backoff (wait longer after each failure) plus jitter (wait a random time, so clients that failed together don't retry together). The "full jitter" formula:

delay = random between 0 and min(cap, base × 2attempt)
# base = 0.1 s, cap = 5 s:  attempt 0 → 0–0.1 s,  1 → 0–0.2 s,  2 → 0–0.4 s,  ...  7 → 0–5 s (capped)

Write backoff_delay(attempt, base, cap, rng) and a retry(fn, ...) wrapper that calls fn, catches QuorumNotReached, sleeps, and tries again up to attempts times. Two details are tested: it must not sleep after the last failure (nothing left to wait for), and it must not retry other exceptions (retrying a bug only repeats the bug). The check passes a fake sleep that records the delays, so it never really waits and its random numbers come from a seeded generator.

Danger 2: doing the work twice

Here is the scenario the drop_next_replies switch exists for. The client sends "set hits to 1" to a node. The node does it and replies, and the reply is lost. To the client this looks exactly like a lost request. It retries. If the retry blindly computes "read 1, add 1, write 2", the counter is now wrong: the increment was applied twice.

The fix is an idempotency key (chapter 16). The caller makes one id per logical operation ("inc-1") and reuses it on every retry. Two cooperating halves:

  • Node side (provided). A put carrying an op_id is recorded in the node's applied table in the same locked step as the write itself, so there is no moment where the effect exists but the record doesn't. A get carrying an op_id reports "done" if that node has seen it.
  • Client side (yours). Before computing anything, _update asks R replicas with the op_id. If any reply has "done", an earlier attempt got that far: write that result to W replicas (so it's safely stored) and return it. Only if no replica has seen the id does the client compute the new value and write.

Why does asking R replicas find it? If the earlier attempt reached W replicas, the quorum-overlap argument says any read of R replicas includes at least one that recorded the id. In the check's scenario every node did the work, so any replica answers "done".

Pitfall: the id must be made once

The common bug is to generate the id inside the code that retries, so each attempt gets a fresh one and the node sees two different operations. The check demonstrates it: the same retry loop with op_id=None (a new id each attempt) ends with the counter at 2. Also, an id must never be reused for a different operation: the node would think it is a duplicate and quietly ignore it. In production, ids are random UUIDs and the table is trimmed after a window (say 24 hours), as the chapter notes.

Solution spoiler 
def backoff_delay(attempt, base=0.1, cap=5.0, rng=random):
    return rng.uniform(0, min(cap, base * (2 ** attempt)))
def retry(fn, attempts=5, base=0.1, cap=5.0, rng=random, sleep=time.sleep,
          retry_on=(QuorumNotReached,)):
    for attempt in range(attempts):
        try:
            return fn()
        except retry_on:
            if attempt == attempts - 1:
                raise
            sleep(backoff_delay(attempt, base, cap, rng))
def _update(self, key, fn, op_id, prefer=None):
    # 1. Ask R replicas for the current value, and whether they already did op_id.
    replies = self._quorum_call({"op": "get", "key": key, "op_id": op_id}, self.r, prefer)
    done = [rep["done"] for _, rep in replies if rep.get("done")]
    if done:
        # An earlier attempt got at least as far as writing it. Don't apply again:
        # just make sure the result is on W replicas, and return it.
        rec = max(done, key=lambda d: tuple(d["version"]))
        self._write(key, rec["value"], tuple(rec["version"]), op_id, prefer)
        return rec["value"]
    # 2. First time we see this op: compute the new value from the newest copy.
    _, best = max(replies, key=lambda ir: tuple(ir[1]["version"]))
    new_value = fn(best["value"])
    self.clock = max(self.clock, best["version"][0]) + 1
    self._write(key, new_value, (self.clock, op_id), op_id, prefer)
    return new_value

Milestone 6: read repair

Replicas drift apart: a node was down during a write, or restarted empty (wipe=True). A stale replica stays stale until something fixes it. Read repair is the cheapest fix, and it falls out of what get already does. The client has just collected R answers with different versions. It knows the newest. So it sends that newest (value, version) back to every replica among the R that returned something older.

Because the node only accepts newer versions, repair is safe to attempt blindly: a repair that arrives late, or races a real write, can never overwrite fresher data (the check verifies this). Repair is best effort: if the stale node is unreachable, ignore the error; a later read will try again. Notice also its limit: it only repairs replicas that this read asked. A key that is never read again stays under-replicated (real systems add a background "anti-entropy" process for that).

Solution spoiler 
def _repair(self, key, value, version, replies):
    stale = [i for i, rep in replies if tuple(rep["version"]) < version]
    for i in stale:
        try:
            call(self.ports[i], {"op": "put", "key": key, "value": value,
                                 "version": list(version)}, self.timeout)
            self.repairs += 1
        except ReplicaUnavailable:
            pass                       # best effort: it can be repaired next time
    return stale

Stretch goals

  • Parallel quorum calls. Send to all N replicas at once with threads and return as soon as W (or R) answer. Which of your stale-read tests become non-deterministic, and why? (Real systems accept this; the quorum rule still holds.)
  • Hinted handoff. When a write can't reach one of its "home" replicas, store it on another node with a hint "this belongs to node 2", and hand it over when node 2 returns. Check chapter 18's box on sloppy quorums: why does this break the overlap guarantee until the handoff completes?
  • Read before you write. Make plain put first read the current version from R replicas so a blind write can never be ignored. What does that cost in latency?
  • Detect concurrent writes. Replace the version pair with a version vector (chapter 17) so two clients writing the same key at once produce "siblings" instead of one silently losing.
  • Dedup table expiry. The applied table grows forever. Add a timestamp to each entry and drop entries older than a window. What goes wrong if a retry arrives after the window?
  • Anti-entropy. A background thread that periodically compares replicas and copies missing keys, so data nobody reads still gets repaired.

Distributed systems connection

You've built the skeleton of Dynamo, Cassandra and Riak: leaderless writes to W, reads from R, versions to pick a winner, and read repair to heal. You've also felt why it is called tunable consistency: every setting of W and R is a point on the dial between "fast and available" and "fresh and strict". What you could not do is make the replicas agree on one order of concurrent writes, or guarantee that a read sees the latest write while writes are in flight (chapter 18's "quorums fall short"). Those guarantees need a leader and consensus. Lab 6 builds exactly that, in a simulation you can partition.

What you learned

  • A value carries a version; a replica keeps only the newest; the reader takes the highest. A Lamport pair (counter, tag) orders writes without trusting wall clocks.
  • With N replicas, writes to W and reads from R: R + W > N guarantees overlap, so a read finds the latest successful write; with R + W ≤ N, stale reads are possible. You measured it.
  • A timeout is a guess. Skip the slow replica, count the answers, and fail cleanly with QuorumNotReached when the quorum is impossible. A failed write may still have left copies behind.
  • Retry with exponential backoff and jitter, never inside a bug, never after the last attempt.
  • Retries are only safe with idempotency: one key per logical operation, reused on every attempt, recorded by the server atomically with the effect.
  • Read repair uses a read's own answers to heal stale replicas, and the "only newer wins" rule makes it safe.

Check your understanding

N = 5 replicas. Which setting guarantees that a read sees the latest successful write (ignoring concurrent writes and failures)?

  1. W = 2, R = 2
  2. W = 3, R = 3
  3. W = 1, R = 4
  4. W = 2, R = 3
The rule is R + W > N, i.e. > 5. W = 3, R = 3 gives 6. But W = 1, R = 4 gives exactly 5 (not greater), and W = 2, R = 3 also gives 5, so a read set of 3 can avoid a write set of 2 entirely (3 + 2 = 5 distinct replicas fit). W = 2, R = 2 gives 4. Only 3 + 3 forces an overlap.

A client sends increment("hits") with no idempotency key. The node applies it, but the reply is lost, so the client times out and retries. What is the likely result?

  1. The counter ends up at the right value, because TCP never delivers duplicates
  2. The node rejects the retry because it recognises the request
  3. The counter is unchanged, because the first attempt failed
  4. The counter is incremented twice, because the retry looks like a brand-new operation
A timeout means the client stopped waiting, not that the operation failed. Without a key, the node cannot tell a retry from a new request, so the increment counts twice. Reusing one idempotency key per logical operation lets the node (or the client, by asking) discover the work is already done. TCP prevents duplicates inside one connection, not across a fresh retry on a new connection.

Why do clients add jitter to exponential backoff?

  1. So clients that failed at the same moment don't all retry at the same moment
  2. So the waits get shorter over time
  3. So the server can tell clients apart
  4. Because random numbers make the network faster
Deterministic backoff keeps failed clients in lock step, so they hit the server in synchronised waves. Randomising the wait spreads them out into a trickle (chapter 16's retry-storm simulator).

A put with W = 2 raises QuorumNotReached(needed=2, got=1). What can you say about the data?

  1. Nothing was written anywhere
  2. The value is safely stored on one replica, which is enough
  3. One replica may now hold the new value, but it isn't guaranteed durable, and later reads may or may not return it
  4. The other two replicas were told to delete the key
Nothing rolls back the replica that did accept the write. The operation is "failed" only in the sense that the quorum guarantee wasn't reached. Depending on which replicas a later read asks, it may see the new value or the old one, which is why the caller must treat the outcome as unknown, ideally retrying with the same idempotency key.

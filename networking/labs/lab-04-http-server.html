Lab 4: An HTTP Server from Scratch

The web is "just" text sent over TCP, and in this lab you'll prove it. You'll write a web server that reads requests byte by byte, answers with real status codes and headers, serves files from a folder, accepts JSON, keeps connections open, and serves many browsers at once. Then you'll point a real browser and curl at it. A few hundred lines of Python, standard library only, and not a single line borrowed from http.server.

Why this lab matters

Chapter 10 described HTTP from the outside. Building a server shows you the parts that are easy to miss from there: where a request ends, why Content-Length is not optional, why a sloppy file server can leak your whole disk, how one TCP connection carries many requests, and what a server has to do so that one slow client can't freeze everyone else. These are the same decisions nginx, Apache and every web framework make, just with fewer lines.

What you'll build

You'll get there in six milestones, each building on the last:

  1. Read a request: frame the byte stream into requests and parse the request line and headers, with size limits.
  2. Send responses: status line, headers, body, and the right status codes (200, 400, 404, 405, 500).
  3. Serve static files: content types, HEAD, and keeping /../ from escaping your folder.
  4. Bodies and JSON: read a POST body using Content-Length; build a tiny JSON API.
  5. Keep-alive: many requests on one connection, Connection: close, and an idle timeout.
  6. Concurrency: a thread per connection, so one slow client can't block the rest.

A stretch goal adds ETag and 304 Not Modified (the caching trick from chapter 10).

Milestone 1: read a request

Before any HTTP happens, you have a problem you already met in Lab 1: TCP hands you a stream of bytes with no message boundaries (chapter 12, and Lab 1's framing milestone). A browser sends a request, but your recv() might return half of it, or all of it plus the start of the next one. Lab 1 ended messages with \n. HTTP/1.1 does something similar: the request head (a request line plus headers) ends at the first empty line, which means the four bytes \r\n\r\n (chapter 10).

So the reader's job is the buffer trick from Lab 1, with a longer delimiter: append each recv() to a buffer, look for \r\n\r\n in the whole buffer (it can straddle two chunks), cut off the head, and keep whatever comes after it. That leftover matters: a client may send a second request before reading the first answer (pipelining), so the next request may already be sitting in your buffer.

Two more jobs belong here, because they are the first line of defence of any server:

  • Limits. A client that streams bytes forever without a blank line would make your buffer grow until the machine runs out of memory. So if the head isn't finished after MAX_HEAD_BYTES (8 KB here) you give up with 431 Request Header Fields Too Large. A server must never let the other side decide how much memory it uses. (It's the same reason as the "what if someone never sends a newline?" box in Lab 1.)
  • Parsing carefully. A request line has exactly three parts. Header names are case-insensitive (Content-Length, content-length and CONTENT-LENGTH are the same header), so store them lower-case. A header value may have extra spaces around it. A line that isn't Name: value is a 400 Bad Request, not something to guess about.

Common misconception: one recv() = one request

It works on your laptop with curl, because a tiny request usually arrives in one piece. It breaks the moment a request is split (a slow network, a big cookie header, a client that writes the head in two calls) or two requests arrive together. The check feeds your reader a request one byte at a time and two requests in a single chunk. Real servers fail this test in production far more often than you'd think.

def read_head(self):
    while True:
        end = self.buf.find(b"\r\n\r\n")           # may straddle two recv() chunks
        if end != -1:
            break
        if len(self.buf) > MAX_HEAD_BYTES:         # no end in sight: stop buffering
            raise HttpError(431, "request headers too large")
        if not self._fill():
            if not self.buf:
                return None
            raise HttpError(400, "connection closed in the middle of a request")
    if end > MAX_HEAD_BYTES:
        raise HttpError(431, "request headers too large")
    head = self.buf[:end]
    self.buf = self.buf[end + 4:]                  # keep whatever follows
    return head

def parse_request(head):
    lines = head.decode("latin-1").split("\r\n")      # latin-1 never fails on any byte
    parts = lines[0].split(" ")
    if len(parts) != 3 or not all(parts):
        raise HttpError(400, "malformed request line")
    method, target, version = parts
    if not re.fullmatch(r"[A-Z]+", method):
        raise HttpError(400, "malformed method")
    if not target.startswith("/"):
        raise HttpError(400, "request target must start with /")
    if not version.startswith("HTTP/"):
        raise HttpError(400, "malformed version")
    if version not in ("HTTP/1.0", "HTTP/1.1"):
        raise HttpError(505, "only HTTP/1.0 and HTTP/1.1")

    if len(lines) - 1 > MAX_HEADERS:
        raise HttpError(431, "too many headers")
    headers = {}
    for line in lines[1:]:
        if line[:1] in (" ", "\t"):
            raise HttpError(400, "obsolete header folding is not accepted")
        name, colon, value = line.partition(":")
        if not colon or not TOKEN.fullmatch(name):     # also rejects "Name : value"
            raise HttpError(400, f"malformed header line {line[:40]!r}")
        name = name.lower()                            # names are case-insensitive
        value = value.strip(" \t")
        headers[name] = f"{headers[name]}, {value}" if name in headers else value

    if version == "HTTP/1.1" and "host" not in headers:
        raise HttpError(400, "HTTP/1.1 requires a Host header")
    return Request(method, target, version, headers)
Go deeper: slow-drip attacks and the missing deadline optional

The size limit stops a client that sends too much. It doesn't stop one that sends almost nothing: a byte every few seconds keeps a connection (and, in milestone 6, a thread) occupied for as long as the attacker likes. This is the idea behind "slowloris" attacks. Milestone 5's timeout resets whenever a byte arrives, so it has the same gap; a total deadline for the whole head is the proper fix, and it's one of the stretch goals.

Milestone 2: send a response

A response mirrors a request: a status line, headers, a blank line, then the body.

HTTP/1.1 200 OK\r\n
Content-Type: text/plain; charset=utf-8\r\n
Content-Length: 18\r\n
Date: Mon, 12 Oct 2026 11:01:07 GMT\r\n
Connection: keep-alive\r\n
Server: lab04-httpd\r\n
\r\n
Hello from lab 4!\n

Each header earns its place:

HeaderWhy the server sends it
Content-LengthThe client needs to know where the body ends, or it can't tell this response from the next one on a reused connection. It counts bytes, not characters: "héllo" is 5 characters but 6 bytes in UTF-8.
Content-TypeWhat the bytes are, so the browser knows to render HTML but download a ZIP.
DateWhen the response was generated, in the fixed format HTTP uses (always GMT). email.utils.formatdate(usegmt=True) produces it.
Connectionkeep-alive or close: will this connection be reused? (Milestone 5.)

The status code is the other half. Your server will use these (chapter 10 has the full table):

CodeMeaningYour server sends it when...
200 OKsuccessthe request worked
400 Bad Requestthe client's fault: can't parse itmalformed request line, bad header, invalid JSON
404 Not Foundno such resourceno such file
405 Method Not Allowedwrong method for this URLPOST /hello. It must carry an Allow: GET, HEAD header listing what is allowed.
500 Internal Server Errorthe server's faultyour handler crashed

That last one deserves a thought. A bug in one handler must not take down the server, and it must not leak a Python traceback (with file paths and variable names) to the client. So the connection loop catches any exception from a handler, logs it on the server side, and sends a bare 500. The provided router has a deliberately broken /boom route so you can watch this work.

def render_response(response, head_only=False, keep_alive=True):
    headers = {k: v for k, v in response.headers.items()
               if k.lower() not in ("content-length", "connection", "date")}
    bodyless = response.status in (204, 304) or 100 <= response.status < 200
    if not bodyless:
        headers["Content-Length"] = str(len(response.body))      # BYTES, not characters
        if "content-type" not in {k.lower() for k in headers}:
            headers["Content-Type"] = "text/plain; charset=utf-8"
    headers["Date"] = formatdate(usegmt=True)                    # e.g. Mon, 12 Oct 2026 09:30:00 GMT
    headers["Connection"] = "keep-alive" if keep_alive else "close"
    headers["Server"] = "lab04-httpd"

    reason = REASONS.get(response.status, "Unknown")
    lines = [f"HTTP/1.1 {response.status} {reason}"]
    for name, value in headers.items():
        if "\r" in value or "\n" in value:                       # header injection
            raise ValueError(f"newline in header {name}")
        lines.append(f"{name}: {value}")
    out = ("\r\n".join(lines) + "\r\n\r\n").encode("latin-1")
    if not head_only and not bodyless:
        out += response.body                                     # HEAD: same headers, no body
    return out

def error_response(status, detail="", headers=None):
    reason = REASONS.get(status, "Error")
    body = f"{status} {reason}\n{detail}\n" if detail else f"{status} {reason}\n"
    return text_response(body, status, headers)

def require_method(request, *allowed):
    if request.method not in allowed:
        raise HttpError(405, f"{request.method} is not allowed here",
                        {"Allow": ", ".join(allowed)})

Milestone 3: serve static files

The router already falls through to serve_static for any path that isn't a special route. You will map a URL like /style.css to a file inside public/, read it as bytes, and send it with the right Content-Type. Three details:

  • Content types come from the extension. .html is text/html, .css is text/css, .svg is image/svg+xml, .png is image/png, and anything unknown is application/octet-stream ("just bytes, don't guess"). Get this wrong and a browser will refuse to apply your stylesheet or show your page as plain text.
  • Always read files in binary mode ("rb"). Text mode would mangle a PNG.
  • HEAD is GET without the body. A client uses it to ask "how big is it, what type, has it changed?" without downloading it (curl -I does this). The headers, Content-Length included, must match what GET would send. Your render_response(head_only=True) from milestone 2 already does the hard part.

The most important security lesson in this lab: path traversal

The URL path is typed by the client, and clients can be hostile. Suppose your folder is /site/public and someone requests GET /../secret.txt. A naive server glues the strings together, /site/public/../secret.txt, and the operating system happily resolves .. ("go up one level") to /site/secret.txt: a file that was never meant to be public. Replace the file with ~/.ssh/id_rsa or a .env file full of passwords and you can see why this is one of the most common web vulnerabilities, usually called path traversal (or directory traversal).

The defence has a fixed recipe, and each step exists because someone once skipped it:

  1. Decode the percent-escapes first. %2e%2e is just .. written differently, and %2f is /. If you check for ".." before decoding, the attacker simply encodes it.
  2. Resolve to a real absolute path with os.path.realpath. It collapses .. and also follows symlinks, so a link inside public/ that points to /etc can't be used as a tunnel.
  3. Check the result is still inside the root with os.path.commonpath. Searching the URL for ".." is a blocklist, and blocklists always miss something. Comparing the final path against the root can't be fooled by how the path was spelled.
  4. Strip the leading / before joining. In Python, os.path.join("/site/public", "/etc/passwd") returns "/etc/passwd": an absolute second argument throws the first one away.

Common misconception: "startswith(root) is good enough"

If the root is /site/public, then /site/public-old/loot.txt starts with it as a string, but it is a different folder. commonpath compares whole path components, so it gets this right. The check includes this exact trap, along with a handful of encoded variants, a null byte, and an absolute path.

def guess_type(path):
    ext = os.path.splitext(path)[1].lower()
    return CONTENT_TYPES.get(ext, "application/octet-stream")   # unknown: "just bytes"

def resolve_path(public_dir, url_path):
    try:
        rel = unquote(url_path, errors="strict")        # %2e%2e is ".." too: decode FIRST
    except UnicodeDecodeError:
        raise HttpError(400, "bad percent-encoding")
    if "\x00" in rel:
        raise HttpError(400, "bad path")
    root = os.path.realpath(public_dir)
    # lstrip("/"): os.path.join(root, "/etc/passwd") would throw root away!
    candidate = os.path.realpath(os.path.join(root, rel.lstrip("/")))   # resolves .. and symlinks
    try:
        inside = os.path.commonpath([root, candidate]) == root          # not str.startswith()
    except ValueError:                                  # e.g. different drives on Windows
        inside = False
    if not inside:
        raise HttpError(403, "that path is outside the public folder")
    return candidate

def serve_static(request, public_dir):
    require_method(request, "GET", "HEAD")
    path = resolve_path(public_dir, request.path)
    if os.path.isdir(path):
        path = os.path.join(path, "index.html")
    try:
        with open(path, "rb") as f:
            body = f.read()
    except (FileNotFoundError, IsADirectoryError, NotADirectoryError):
        raise HttpError(404, "no such file")
    headers = {"Content-Type": guess_type(path)}
    return Response(200, body, headers)

Milestone 4: request bodies and a JSON endpoint

So far every request was a GET: all the information was in the head. A POST carries data in a body after the blank line, and the head says how long it is: Content-Length: 27. Reading it is the "length-prefix" form of framing from Lab 1: you don't search for a delimiter, you read exactly that many bytes. Some of them may already be in your buffer (they came in the same chunk as the head); the rest you recv().

Three rules a careful server follows:

  • Validate the length before trusting it. It must be a non-negative integer, and it must not exceed MAX_BODY_BYTES. A request announcing a 50 GB body gets 413 Payload Too Large immediately, without reading it.
  • Always consume the body, even if you're about to answer 405 or 404. Otherwise those unread bytes sit in front of the next request on a keep-alive connection and get parsed as if they were a new request head. The provided read_request() reads the body before routing, so this works once read_body does.
  • Check the Content-Type before parsing. The endpoint accepts application/json; anything else is 415 Unsupported Media Type. Invalid JSON is 400.

The JSON endpoint you'll build is POST /api/echo: parse the body and reply with {"you_sent": ..., "bytes": N}. Once parse_json_body works, the provided /api/guestbook works too (GET lists entries, POST adds one) and the sample page's form comes alive. The guestbook is kept in a Python list in memory, which restarts empty each time. Notice the GUESTBOOK_LOCK around it: you'll see why in milestone 6.

Solution spoiler 
def read_body(self, n):
    while len(self.buf) < n:
        if not self._fill():
            raise HttpError(400, "connection closed before the whole body arrived")
    body, self.buf = self.buf[:n], self.buf[n:]
    return body

def parse_json_body(request):
    ctype = request.header("content-type", "").split(";")[0].strip().lower()
    if ctype != "application/json":
        raise HttpError(415, "send the header Content-Type: application/json")
    try:
        return json.loads(request.body.decode("utf-8"))
    except (UnicodeDecodeError, ValueError):
        raise HttpError(400, "the body is not valid JSON")

def api_echo(request):
    require_method(request, "POST")
    data = parse_json_body(request)
    return json_response({"you_sent": data, "bytes": len(request.body)})

Milestone 5: keep-alive

Up to now your server answers one request and hangs up. That is how HTTP/1.0 worked, and it is wasteful: every request pays for a new TCP handshake (chapter 8), and for HTTPS a TLS handshake on top (chapter 11). The sample page alone needs at least four. HTTP/1.1 made connections persistent by default (chapter 10): the connection stays open and carries request after request, until someone says Connection: close.

Three things change in the server:

  1. Decide per request: wants_keep_alive(request). HTTP/1.1: keep it open unless the Connection header lists close. HTTP/1.0 is the reverse: close unless it lists keep-alive. The header is a comma-separated list, and values are case-insensitive. Echo the decision back in your own Connection header (milestone 2 already does).
  2. Loop in handle_connection: read a request, answer it, read the next, until the client closes (read_request returns None) or someone asked to close. Bytes belonging to the following request are already waiting in the reader's buffer, which is why pipelined requests work for free.
  3. An idle timeout. A client that opens a connection and then says nothing would hold a thread forever. conn.settimeout(idle_timeout) makes recv() raise socket.timeout after that much silence. If the buffer is empty, the connection is just idle, so close it quietly. If half a request is sitting there, the client stalled, so send 408 Request Timeout first. Timeouts like this are the first line of defence against slow or dead clients (chapter 16).
Go deeper: why closing is harder than it looks optional

When your server error-closes a connection (say, a 431 for a huge head) the client may still be sending. If you close() a socket that still has unread incoming data, the operating system answers with a TCP reset (RST) instead of a polite FIN, and the client's TCP stack may throw away your response before the application reads it. The provided close_politely helper does a "lingering close": it shuts down only the sending direction (that sends the FIN), then drains and discards what the client still sends for up to a second, then closes. Without it, the oversized-header check would fail now and then, depending on timing. It's a good example of a rule from chapter 8: a close is a conversation, not an instant.

def wants_keep_alive(request):
    tokens = {t.strip().lower() for t in request.header("connection", "").split(",")}
    if request.version == "HTTP/1.0":
        return "keep-alive" in tokens
    return "close" not in tokens

def handle_connection(conn, public_dir=PUBLIC_DIR, idle_timeout=IDLE_TIMEOUT, addr=None):
    conn.settimeout(idle_timeout)                      # a silent client can't hold us forever
    reader = RequestReader(conn)
    try:
        while True:
            try:
                request = reader.read_request()
            except socket.timeout:
                if reader.buf:                          # went quiet in the middle of a request
                    conn.sendall(render_response(error_response(408), keep_alive=False))
                return
            except HttpError as e:                      # unparseable: framing is lost, so close
                response = error_response(e.status, e.message, e.headers)
                conn.sendall(render_response(response, keep_alive=False))
                return
            if request is None:                         # client closed between requests
                return

            keep_alive = wants_keep_alive(request)
            try:
                response = handle_request(request, public_dir)
            except HttpError as e:
                response = error_response(e.status, e.message, e.headers)
            except NotImplementedError:
                raise                                   # an unfinished TODO should be loud
            except Exception as e:                      # a bug in OUR code: 500, keep serving
                if VERBOSE:
                    print(f"handler crashed: {type(e).__name__}: {e}", flush=True)
                response = error_response(500)
            conn.sendall(render_response(response, head_only=(request.method == "HEAD"),
                                         keep_alive=keep_alive))
            log(addr, request, response.status)
            if not keep_alive:
                return
    except OSError:                                     # reset by peer, broken pipe, ...
        pass
    finally:
        close_politely(conn)

Milestone 6: one thread per connection

Now try this. Start the server with --serial, open a connection that says nothing (nc 127.0.0.1 8080, and don't type), then in another terminal run curl http://127.0.0.1:8080/hello. The curl hangs. Your server is stuck inside recv() on the first connection, waiting for bytes that may never come, and it can't call accept() for anyone else. The operating system completed curl's handshake and queued it (that's what listen() is for, chapter 12), but nobody has picked it up. Until the idle timeout fires, one quiet client has frozen the whole server. Keep-alive makes this much worse than before: connections now stay open for seconds or minutes, and a browser opens up to six at once.

The fix is to give each connection its own thread. A thread is an independent flow of execution inside your process. While one thread is blocked in recv() for client A, the operating system runs the others. The main thread does nothing but accept() and start a thread per connection. Your connection code stays simple, straight-line "read, handle, write" with ordinary blocking calls, which is the big appeal.

Why choose threads here when Lab 1's chat server used an event loop? Because the HTTP handler is a conversation with state: read a head, maybe read a body, route, write, loop. In a thread, that state lives in ordinary local variables and the code reads top to bottom. In an event loop you must chop it into pieces that run when a socket becomes ready and remember where each connection is up to (the chat server's per-client LineBuffer was the beginning of that). The event loop's payoff arrives at scale: threads cost memory (each has its own stack, typically megabytes of address space) and scheduling work, so a server with ten thousand idle connections (the "C10K problem") wants an event loop, which is why nginx and Node.js work that way. For tens or hundreds of connections, threads are a perfectly good, simple answer. Chapter 12 describes the same trade-off.

Analogy: a restaurant

A serial server is a restaurant with one waiter who stands at each table until the guests have finished their meal before greeting the next table. Thread-per-connection hires a waiter per table: easy to reason about, but you can only afford so many. An event loop is one super-efficient waiter who circles the room and only stops at tables where someone is waving. Where it breaks down: real waiters can't be in two places at once, whereas threads genuinely can run in parallel on separate CPU cores (in Python, the interpreter lock allows only one thread to run Python code at a time, but it is released while waiting on the network, which is where a server spends nearly all its time).

Threads introduce one new danger: shared mutable data. Two threads that both append to the guestbook, or compute the next id from len(GUESTBOOK), can interleave and corrupt it. The solution here is a lock: with GUESTBOOK_LOCK: lets only one thread into that block at a time. That's the provided code's job, but notice the pattern: the moment you add threads, every piece of state shared between connections needs a story. (In the distributed systems chapters the same problem returns across machines, where there's no lock to grab.)

def spawn_handler(conn, addr, public_dir, idle_timeout):
    t = threading.Thread(target=handle_connection, args=(conn, public_dir, idle_timeout, addr),
                         daemon=True)                   # daemon: Ctrl+C isn't blocked by idle clients
    t.start()

def serve(port=8080, ready=None, stop=None, public_dir=PUBLIC_DIR,
          idle_timeout=IDLE_TIMEOUT, concurrent=True):
    """Listen and accept forever (or until the `stop` Event is set)."""
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as srv:
        srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        srv.bind((HOST, port))
        srv.listen(128)
        srv.settimeout(0.2)                             # wake up now and then to check `stop`
        real_port = srv.getsockname()[1]
        if VERBOSE:
            print(f"Serving {public_dir} on http://{HOST}:{real_port}/  (Ctrl+C to stop)", flush=True)
        if ready:
            ready(real_port)
        while stop is None or not stop.is_set():
            try:
                conn, addr = srv.accept()
            except socket.timeout:
                continue
            if concurrent:
                spawn_handler(conn, addr, public_dir, idle_timeout)
            else:
                handle_connection(conn, public_dir, idle_timeout, addr)   # blocks everyone else

Stretch goal: conditional GET with ETag

Chapter 10 explained revalidation: the server labels each version of a file with an ETag, a fingerprint, and the browser later asks "do you still have abc123?" with If-None-Match. If so, the server answers 304 Not Modified with no body, replacing a possibly large download with a tiny message. You have everything you need already:

  1. In serve_static, compute etag_for(body) (provided: a short hash of the content, in quotes) and send it as an ETag header, with Cache-Control: no-cache. Despite the name, no-cache means "you may store it, but check with me before reusing it".
  2. If the request has If-None-Match and etag_matches(value, etag) (provided) says it's current, return Response(304, b"", {"ETag": etag}).
def etag_for(body):
    return '"' + hashlib.sha1(body).hexdigest()[:16] + '"'

def etag_matches(header_value, etag):
    for item in header_value.split(","):
        item = item.strip()
        if item.startswith("W/"):
            item = item[2:]
        if item == "*" or item == etag:
            return True
    return False

Then reload the sample page in the browser's Network tab: style.css shows 304 on the second load. python3 check.py prints the stretch result under the milestone summary (it doesn't count towards the six): it checks a matching tag gives an empty 304, a stale tag gets the full file, and the tag changes when the file does.

The additions to serve_static, placed after reading the file:

etag = etag_for(body)
headers["ETag"] = etag
headers["Cache-Control"] = "no-cache"          # "keep it, but ask me first"
inm = request.header("if-none-match")
if inm and etag_matches(inm, etag):
    return Response(304, b"", {"ETag": etag, "Cache-Control": "no-cache"})

One thing to think about: this server hashes the whole file on every request, so it saves bandwidth but not disk or CPU work. Real servers derive the tag from the file's modification time and size instead. Which is cheaper? What could go wrong with that shortcut?

More stretch goals

  • A total head deadline (the "slow-drip" box in milestone 1): give up on a request if its head isn't complete within, say, 10 seconds from the first byte, no matter how often bytes dribble in.
  • Redirect /sub to /sub/ when sub is a folder. Browsers resolve relative links against the URL, so it matters. Use 301 and a Location header.
  • Range requests: support Range: bytes=0-99 and answer 206 Partial Content with a Content-Range header. This is how video seeking works.
  • Stream big files instead of reading them into memory: send the head, then read and sendall the file in 64 KB pieces. What changes about Content-Length? (os.path.getsize.)
  • Limit connections: refuse the 101st simultaneous connection with 503 Service Unavailable, using a threading.Semaphore or a counter with a lock. Servers shed load like this on purpose rather than falling over.
  • Chunked responses (Transfer-Encoding: chunked): send a body whose length you don't know up front, as a series of sized chunks. Chapter 10 mentions why this exists.
  • HTTPS: wrap the listening socket with Python's ssl module and a self-signed certificate (chapter 11). Your handler code won't change at all. That's layering at work (chapter 3).

Distributed systems connection

You have just built the kind of process that sits behind a load balancer (chapter 14), and its design choices are the ones that decide how a fleet behaves. The idle timeout is a small instance of a theme in chapter 16: you can't tell a quiet client from a dead one, so you pick a timeout and accept some mistakes. Connection limits and the 503 are load shedding. Statelessness matters too: your guestbook lives in one process's memory, so if you ran two copies behind a load balancer, each would show different entries, and a restart would lose them all. Keeping state consistent across copies is the subject of chapter 18, and Lab 5 builds a small replicated store to do it. And the thousand-connections-per-process question you met in milestone 6 comes back in case study 5.

What you learned

  • HTTP/1.1 is text over TCP: a request ends at a blank line, a body is exactly Content-Length bytes, and your reader must keep leftover bytes for the next request.
  • A server must bound everything the client controls: header size, body size, time spent waiting.
  • Status codes and headers are part of the contract: 405 needs Allow, Content-Length counts bytes, HEAD mirrors GET, and a crashing handler becomes a 500, not a dead server.
  • URL paths are untrusted input. Decode, resolve to an absolute path, and check containment: never search for "..".
  • Keep-alive saves handshakes but obliges the server to decide when a quiet connection is finished.
  • Blocking servers need concurrency, and a thread per connection is the simplest form; shared state then needs locks. Event loops scale further but make the code harder to follow.

Check your understanding

Your server's recv() returns b"GET /a HTTP/1.1\r\nHost: x\r\n\r\nGET /b HT". What should the reader do?

  1. Parse the whole chunk as one request and ignore the rest
  2. Return request /a, and keep GET /b HT in the buffer for the next call
  3. Throw away the bytes after the first blank line, since clients send one request at a time
  4. Close the connection: it's a protocol violation
TCP gives a stream, not messages, and a client may pipeline requests. The first blank line ends request /a; the bytes after it are the beginning of the next request and must be kept. Discarding them silently breaks the next request, which is the classic bug the check provokes.

Your file server is rooted at /site/public. Which check is the most reliable way to stop GET /%2e%2e/secret.txt from escaping?

  1. Reject any URL containing the text ".." before decoding it
  2. Reject any URL containing "../" after decoding it
  3. Check that the resolved path startswith("/site/public")
  4. Decode, resolve with realpath, then check the result is inside the root using whole path components (commonpath)
The first option misses the encoded form entirely. The second still misses spellings like ..\ on some systems and symlinks. The third is close but wrong: /site/public-old/loot.txt starts with /site/public too. Only comparing the final, fully resolved path against the root, component by component, doesn't depend on how the attacker spelled the path.

A client sends POST /hello with a 5,000-byte body. The route only allows GET and HEAD. Why must the server still read the whole body before replying 405 on a keep-alive connection?

  1. Otherwise the unread body bytes would be parsed as the start of the next request
  2. Otherwise the client can't see the Allow header
  3. Because HTTP requires every request to be logged with its body
  4. Because recv() refuses to return until all data is read
On a persistent connection the stream continues after this request. If 5,000 bytes of JSON are left unread, the reader treats them as the next request head and fails (or worse, misparses). Framing means always consuming exactly what the previous message occupied. (The alternative is to close the connection after the error.)

Why did this lab use a thread per connection while Lab 1's chat server used a selector-based event loop?

  1. Threads are always faster than event loops
  2. Python can't run an event loop for HTTP
  3. Each HTTP connection runs a multi-step read-handle-write conversation, which is simple to write as straight-line blocking code in its own thread; an event loop would need that state split into callbacks
  4. The operating system gives each thread its own TCP port
Both designs serve many clients. Threads keep per-connection code simple but cost memory and need locks for shared data (the guestbook). Event loops scale to many more idle connections but force you to break handlers into pieces. Neither is "faster" in general, and threads don't get ports: they all share the server's one listening port.

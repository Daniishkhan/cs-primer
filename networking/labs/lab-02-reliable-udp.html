Lab 2: Reliable Delivery over UDP

UDP sends your datagram and forgets it. TCP promises that every byte arrives, once, in order. In this lab you'll build that promise yourself: packet numbers, acknowledgements, timeouts, and finally a sliding window, all on top of plain UDP, across a "network" that loses, duplicates and reorders packets on purpose. About 150 lines of Python, standard library only.

Why this lab matters

In chapter 8 you read that TCP "numbers the bytes, acknowledges what it got, and resends on a timer". Reading is one thing; watching your own sender stall for a full round trip after every single packet, and then watching a window make the same transfer several times faster, is what makes the design click. The same ideas (acknowledge, time out, retry, de-duplicate) reappear at every level of a distributed system, from message queues to payment APIs.

What you'll build

Five milestones, each building on the last:

  1. A packet format: pack a type, a sequence number and a checksum in front of the payload with struct, and discard anything damaged.
  2. Stop-and-wait: send one packet, wait for its ACK, resend on timeout. The receiver delivers in order and ignores duplicates.
  3. Measure it: see that stop-and-wait delivers one packet per round trip, no matter how fast the link is.
  4. A sliding window: Go-Back-N with cumulative ACKs and a single timer. Same lossy channel, several times faster.
  5. Adaptive timeout (optional): measure the RTT and set the timer the way real TCP does (RFC 6298).

Meet the lossy channel

Loopback never drops anything, so we need to fake a bad network. LossyChannel in starter.py wraps a UDP socket and has the same sendto / recvfrom / settimeout methods you used in lab 1. Every datagram you send through it rolls some dice first:

SettingWhat it doesReal-world cause
losssilently drop the datagrama router's queue overflowed
delay, jitterdeliver after a fixed delay plus a random extradistance and queues; delay is half the RTT
dupdeliver the datagram twicea link-layer retry whose first copy actually arrived
reorderhold it back so later datagrams overtake ittwo paths with different delays
corruptflip the bits of one bytenoise on a link (rare; the checksum is the defence)
seedseeds the random generatornot a network property: it makes a run reproducible

Because the dice are seeded, "10% loss" means the same datagrams are lost on every run, so a bug you find can be found again. (Exactly when your timers fire still depends on your computer's timing, so the retransmission counts can wobble a little.) The helper run_transfer(send_fn, recv_fn, data, rtt=..., loss=..., ...) wires a sender and a receiver together through two channels and returns (received_bytes, packets_sent, seconds).

Conventions used in this lab

  • A file is cut into CHUNK = 1000-byte pieces. Each piece travels in one DATA packet. A final empty DATA packet means "end of file".
  • Sequence numbers count packets (0, 1, 2, ...), not bytes as in real TCP. It keeps the arithmetic readable.
  • An ACK carries the next sequence number the receiver wants, just like TCP's acknowledgement number. ACK 5 means "I have 0 to 4, send me 5".

Milestone 1: a packet format with a checksum

UDP hands you raw datagrams: bytes in, bytes out. To build reliability you first need your own header (chapter 3): a few bytes in front of the payload saying what kind of packet this is and which one. Ours is nine bytes:

type1 byte
sequence number4 bytes
CRC-32 checksum4 bytes
payload0 to 1000 bytes

Python's struct module turns numbers into bytes and back. The format string "!BII" says: ! network byte order (big-endian: most significant byte first, the order used on the wire by IP, UDP and TCP headers), B one unsigned byte, I a four-byte unsigned integer. struct.Struct("!BII") is already in the starter as HEADER. Here is a real packet with type DATA (1), sequence 7 and payload "hi":

>>> make_packet(DATA, 7, b"hi").hex(" ")
01 00 00 00 07 a7 1e fa 1c 68 69

Read it left to right: 01 is the type, 00 00 00 07 is the sequence number 7 in four bytes, a7 1e fa 1c is the checksum, and 68 69 is "hi" in ASCII.

Why a checksum?

A checksum is a short fingerprint of the data. The sender computes it and puts it in the header; the receiver recomputes it from what actually arrived. If the two differ, something changed on the way, and the receiver throws the packet away as if it had been lost. The retransmission machinery you're about to build then repairs it, so one mechanism handles both loss and damage. Real UDP and TCP both carry a checksum (chapter 7), a simple 16-bit sum; we use zlib.crc32, a stronger 32-bit cyclic redundancy check built into Python (the same family of checks Ethernet uses for its frame check sequence).

A checksum catches accidents, not attackers

Anyone who can alter a packet can also recompute the CRC. A checksum detects random damage only. Protecting against a deliberate attacker takes cryptography (chapter 11). And even for accidents, nothing is perfect: a 32-bit checksum lets roughly 1 in 4 billion random corruptions slip through.

Solution spoiler 
def make_packet(ptype, seq, payload=b""):
    # The checksum covers the type, the sequence number AND the payload, so a
    # flipped bit anywhere (except in the checksum itself, which then fails to
    # match) is caught.
    covered = struct.pack("!BI", ptype, seq) + payload
    return HEADER.pack(ptype, seq, zlib.crc32(covered)) + payload

def parse_packet(raw):
    if len(raw) < HEADER_LEN:
        return None
    ptype, seq, checksum = HEADER.unpack(raw[:HEADER_LEN])
    payload = raw[HEADER_LEN:]
    if ptype not in (DATA, ACK):
        return None
    if zlib.crc32(struct.pack("!BI", ptype, seq) + payload) != checksum:
        return None                           # corrupted in transit: discard
    return ptype, seq, payload

Milestone 2: stop-and-wait

The simplest reliable protocol is the one you'd invent yourself (chapter 8, "Step 3"): send a packet, wait for the receiver to say "got it", and if you hear nothing, send it again.

Sender, per packet

Send DATA seq. Wait up to timeout for an ACK that says "I want seq + 1 next". If the time runs out, send the same packet again. Only then move on.

Receiver, per packet

Check the checksum. If the sequence number is the one it expects, deliver the payload and expect the next. Whatever came in, reply ACK expected.

Notice how little the receiver has to do. Its entire policy is one sentence: "always tell the sender what I'm waiting for". A duplicate of an old packet just gets the same answer again, and a packet from the future (not possible yet, but it will be in milestone 4) also gets the same answer. Let's follow three situations:

Analogy: registered mail with a signature card

You post a numbered letter and wait for the signed receipt card. No card after a week? You post a copy. If the first letter had arrived and only the card went astray, the recipient now holds two identical letters numbered "7". A sensible recipient notices the number, files only one, and sends another card. Where it breaks down: the post office never delivers letters out of order or twice by itself, and a network can.

A timeout is a guess, not a fact

When the timer fires you don't know the packet was lost. It might be slow, or only the ACK might have been lost (case 3 above). Resending is always safe here because the receiver de-duplicates by sequence number. Hold on to this thought: it is the foundation of retries and idempotency in chapter 16.

Two traps to avoid

  • Stale ACKs. A duplicated or delayed ACK from an earlier packet can arrive while you're waiting for a newer one. Accept only an ACK number that proves your current packet got through (>= seq + 1), and keep waiting for the rest of the timeout when you see a useless one rather than resending immediately.
  • The last ACK. When the receiver sees the end-of-file packet it is done, but its final ACK might be lost, and then the sender would retransmit into the void forever. So the receiver lingers for a short while after finishing, still re-ACKing. TCP's TIME_WAIT state (chapter 8) serves a similar purpose: after closing, it stays around a while in case the peer's last packet needs another answer.

def stop_and_wait_send(chan, dest, data, timeout=0.05, chunk=CHUNK, max_tries=40):
    # The last packet has an empty payload: that is our "end of file" marker.
    pieces = split_chunks(data, chunk) + [b""]
    sent = 0
    for seq, payload in enumerate(pieces):
        packet = make_packet(DATA, seq, payload)
        for _ in range(max_tries):
            chan.sendto(packet, dest)
            sent += 1
            if _wait_for_ack(chan, seq + 1, timeout):
                break                         # acknowledged: next packet
        else:
            raise ConnectionError(f"no ACK for packet {seq} after {max_tries} tries")
    return sent

def _wait_for_ack(chan, want, timeout):
    deadline = time.monotonic() + timeout
    while True:
        remaining = deadline - time.monotonic()
        if remaining <= 0:
            return False
        chan.settimeout(remaining)
        try:
            raw, _ = chan.recvfrom()
        except socket.timeout:
            return False
        pkt = parse_packet(raw)
        if pkt and pkt[0] == ACK and pkt[1] >= want:
            return True
        # corrupted, wrong type, or an old duplicate ACK: ignore, keep waiting

def receive(chan, linger=0.3, idle_timeout=5.0):
    expected = 0
    pieces = []
    finished = False
    while True:
        # After the end-of-file packet we "linger": the final ACK may have been
        # lost, and the sender will keep retrying until it hears one.
        chan.settimeout(linger if finished else idle_timeout)
        try:
            raw, addr = chan.recvfrom()
        except socket.timeout:
            if finished:
                return b"".join(pieces)
            raise TimeoutError("sender went quiet")
        pkt = parse_packet(raw)
        if pkt is None or pkt[0] != DATA:
            continue
        _, seq, payload = pkt
        if seq == expected:                   # the one we were waiting for
            expected += 1
            if payload:
                pieces.append(payload)
            else:
                finished = True               # empty payload = end of file
        # seq < expected: a duplicate. seq > expected: out of order. Either
        # way we don't deliver it; we just repeat what we're waiting for.
        chan.sendto(make_packet(ACK, expected), addr)

Milestone 3: why stop-and-wait is slow

Your protocol is correct. Now measure it. After sending a packet, the sender does nothing at all until the ACK returns, which takes one full round-trip time (RTT, chapter 13). So at most one packet is delivered per RTT, and:

throughput ≈ packet size ÷ RTT

With our 1000-byte chunks and a 20 ms RTT, that's 1000 ÷ 0.020 = 50,000 bytes per second, however fast the link underneath is. Double the RTT and you halve the throughput. The link's bandwidth doesn't appear in the formula at all.

Real numbers make it vivid. Take a 1 Gbit/s link with a 50 ms RTT (roughly a cross-continent path) and 1500-byte packets: stop-and-wait delivers 1500 × 8 ÷ 0.05 = 240,000 bits per second, about 0.024% of the link. The rest is silence.

How much should be in flight?

Chapter 13 gave the bandwidth-delay product: bandwidth × RTT is how much data fits "in the pipe" at once, and therefore how much you must send before the first ACK returns if you want to keep the pipe full. A 100 Mbit/s link with a 50 ms RTT holds 100,000,000 ÷ 8 × 0.05 = 625,000 bytes. With 1000-byte packets, that's a window of about 625 packets. Chapter 8's rule, throughput ≈ window ÷ RTT, is the same fact seen from the other side: to go faster, raise the window.

Milestone 4: a sliding window (Go-Back-N)

The fix (chapter 8, "Step 5") is to keep many packets in flight. The sender may have up to window unacknowledged packets outstanding. Every ACK that arrives slides the window forward, freeing room for new packets. Go-Back-N (GBN) is the simplest such protocol. The sender keeps two numbers:

  • base: the oldest packet not yet acknowledged.
  • next_seq: the next packet it has never sent.

The rules, in the order your loop performs them:

  1. Fill the window. While next_seq < base + window, send next_seq and advance it.
  2. Wait for an ACK, but only until the single timer expires. The timer is for the oldest unacknowledged packet, and it restarts every time base moves.
  3. A cumulative ACK n means "I have everything below n". If base < n <= next_seq, set base = n. One ACK can retire many packets, so a lost ACK is often harmless: the next one covers it.
  4. On timeout, go back N. Resend every packet from base to next_seq - 1 and restart the timer. Simple, and wasteful.

Why does the sender resend everything? Because the receiver is deliberately dumb: it accepts only the packet it expects and discards anything that arrives early, so after a gap it holds nothing beyond it. That is why you don't need to write a new receiver: the one from milestone 2 already behaves this way. A packet from the future just earns another ACK expected, which tells the sender "I'm still stuck waiting for expected".

Analogy: a conveyor belt of parcels

Instead of handing the courier one parcel and waiting for the receipt, you load eight parcels on a belt and keep loading as receipts come back. If parcel 3 vanishes, the warehouse on the other end refuses 4 to 7 (they'd be out of order), so you reload 3 to 7 when your timer rings. Where it breaks down: real TCP can buffer the early parcels and ask for only the missing one (selective acknowledgements, see the stretch goals).

Solution spoiler 
def gbn_send(chan, dest, data, window=32, timeout=0.05, chunk=CHUNK,
             estimator=None, max_tries=40):
    packets = [make_packet(DATA, seq, p)
               for seq, p in enumerate(split_chunks(data, chunk) + [b""])]
    total = len(packets)
    base = next_seq = 0
    sent = 0
    send_time = {}                            # seq -> time of first send (for RTT)
    retransmitted = set()                     # Karn: don't time resent packets
    timer_start = time.monotonic()
    stalls = 0                                # timeouts in a row without progress

    while base < total:
        # 1. Fill the window.
        while next_seq < total and next_seq < base + window:
            chan.sendto(packets[next_seq], dest)
            sent += 1
            send_time[next_seq] = time.monotonic()
            if base == next_seq:
                timer_start = time.monotonic()
            next_seq += 1
        # 2. Wait for an ACK, but no longer than the timer allows.
        rto = estimator.rto if estimator else timeout
        remaining = timer_start + rto - time.monotonic()
        try:
            if remaining <= 0:
                raise socket.timeout
            chan.settimeout(remaining)
            raw, _ = chan.recvfrom()
        except socket.timeout:
            # 3. Timer fired: go back N, resend everything from base.
            stalls += 1
            if stalls > max_tries:
                raise ConnectionError(f"no progress after {max_tries} timeouts")
            if estimator:
                estimator.backoff()
            for seq in range(base, next_seq):
                chan.sendto(packets[seq], dest)
                sent += 1
                retransmitted.add(seq)
            timer_start = time.monotonic()
            continue
        pkt = parse_packet(raw)
        if pkt is None or pkt[0] != ACK:
            continue
        ack = pkt[1]                          # cumulative: "I have everything below ack"
        if base < ack <= next_seq:
            if estimator and (ack - 1) not in retransmitted:
                estimator.update(time.monotonic() - send_time[ack - 1])
            base = ack                        # slide the window
            stalls = 0
            timer_start = time.monotonic()    # restart the single timer
    return sent

Read the numbers honestly

Run python3 check.py solution and look at the milestone 4 line. A typical result:

✔ Milestone 4: ... (200 KB through 10% loss: stop-and-wait 4.1 s (248 pkts), go-back-n 1.8 s (1386 pkts), 2.3x faster)

Go-Back-N won, but look at the packet counts: stop-and-wait needed about 250 transmissions for 201 packets, while Go-Back-N sent over 1,300. Each lost packet makes the sender wait out the timer and then resend a whole window, mostly packets the receiver already had (or had to discard because the gap blocked them). The window trades bandwidth for time. With a bigger window or more loss the waste grows. That tension is why real TCP does not use plain Go-Back-N: it uses selective acknowledgements, fast retransmit and congestion control (chapter 8) to resend only what's missing and to avoid overloading the path.

Common misconception: "a bigger window is always better"

Try window=128 in the demo with 10% loss. It sends even more redundant packets, and in a real network those extra packets would fill router queues and cause more loss. The right window is "enough to fill the pipe" (the bandwidth-delay product), not "as big as possible". Finding it automatically as conditions change is exactly the job of TCP's congestion control.

Milestone 5 (optional): a timeout that adapts

So far the timeout was a number we typed in, tuned to our 10 ms test link. On a real path the RTT might be 2 ms or 300 ms, and it keeps changing. A fixed timer is either too short (needless resends, and a stream of duplicates that can make congestion worse) or too long (a lost packet leaves the sender idle). TCP measures the RTT and derives the timer from it, using the method in RFC 6298. Two running numbers:

  • SRTT, the smoothed average RTT;
  • RTTVAR, how much the RTT wobbles (a smoothed average deviation).

For each new measurement R (the very first one just sets SRTT = R, RTTVAR = R/2):

RTTVAR = (1 - 1/4) * RTTVAR + 1/4 * |SRTT - R|      # uses the OLD SRTT
SRTT   = (1 - 1/8) * SRTT   + 1/8 * R
RTO    = SRTT + 4 * RTTVAR

The timer is the average plus four times the typical wobble, so a steady link gets a tight timer and a jittery one gets slack. Two more rules from the RFC complete the picture:

  • Exponential backoff. Each time the timer fires, double the RTO. If the network is congested, hammering it with retries at a fixed rate makes things worse; backing off gives it room to recover (chapter 16 and the retry-storm case study use the same idea).
  • Karn's rule. Never take an RTT sample from a retransmitted packet. When its ACK arrives you can't tell whether it answers the original or the copy, so the "round trip" could be wildly wrong.

(The RFC also sets a floor of one second for the RTO and has a clock-granularity term; our lab uses a configurable min_rto of 20 ms so tests finish quickly. Real stacks differ in these details.)

Solution spoiler 
class RttEstimator:
    ALPHA = 1 / 8
    BETA = 1 / 4
    K = 4

    def __init__(self, initial_rto=0.2, min_rto=0.02, max_rto=2.0):
        self.srtt = None
        self.rttvar = None
        self.min_rto, self.max_rto = min_rto, max_rto
        self.rto = initial_rto

    def update(self, sample):
        """Feed in one RTT measurement (seconds)."""
        if self.srtt is None:                 # the very first sample
            self.srtt = sample
            self.rttvar = sample / 2
        else:                                 # rttvar first, using the OLD srtt
            self.rttvar = (1 - self.BETA) * self.rttvar + self.BETA * abs(self.srtt - sample)
            self.srtt = (1 - self.ALPHA) * self.srtt + self.ALPHA * sample
        self._set_rto(self.srtt + self.K * self.rttvar)

    def backoff(self):
        """A timeout happened: double the RTO (exponential backoff)."""
        self._set_rto(self.rto * 2)

    def _set_rto(self, value):
        self.rto = min(self.max_rto, max(self.min_rto, value))

  3. Break the checksum on purpose. Make parse_packet skip the checksum comparison and run the check with corrupt=0.05 (edit the transfer in milestone 2's check). The file arrives with flipped bytes, and nothing in your protocol notices. This is the "end-to-end argument" in miniature: someone has to verify the data, and it can't be assumed.
  4. Watch it on the wire (optional). While a transfer runs, sudo tcpdump -i lo0 -n -X udp (Linux: -i lo) shows the real UDP datagrams, and your nine header bytes right after the UDP header. It will need your password and shows both the sender and receiver sides.

On a Linux VM

The lab's lossy channel simulates loss in your code. On a Linux VM you can make the kernel do it for real, on the loopback interface. Use your lab machine:

$ sudo tc qdisc add dev lo root netem loss 10% delay 50ms  # 10% of packets dropped, 50 ms added
$ ping -c 5 127.0.0.1  # round trips now take about 100 ms (50 ms each way)
$ sudo tc qdisc del dev lo root  # REMOVE IT when you are done

Remove it afterwards. The rule affects all traffic on lo for the whole VM until you delete it, including every local service. Run the del command and check with tc qdisc show dev lo. Do this only on a throwaway VM, never on a machine you share. Running the lab's transfer while netem is on gives the same kind of results as the shim, with real packets.

Stretch goals

  • Selective Repeat. Make the receiver buffer out-of-order packets (a dictionary from sequence number to payload) and acknowledge each one individually or with a list of ranges; make the sender keep one timer per packet and resend only what's missing. Compare the packet counts with Go-Back-N at 10% loss.
  • Fast retransmit. When the sender sees three duplicate ACKs for the same number, resend base immediately instead of waiting for the timer (chapter 8, "Duplicate ACKs"). How much faster does the 10% loss transfer get?
  • Congestion control. Replace the fixed window with one that starts at 1, doubles each round trip until a loss (slow start), then grows by 1 per round trip (additive increase) and halves on loss (multiplicative decrease). Print the window over time and you'll see TCP's sawtooth.
  • A handshake. Add SYN and FIN packet types so the receiver knows a transfer is starting and the sender knows it has really finished, instead of relying on the lingering trick.
  • Flow control. Have the receiver advertise how much buffer space it has in every ACK, and make the sender's window the smaller of its own window and that advertisement.

Distributed systems connection

You just implemented at-least-once delivery with de-duplication: the sender retries until it hears an acknowledgement (so the message arrives at least once) and the receiver uses sequence numbers to throw away the extra copies (so the effect happens once). That one combination is behind nearly every reliable messaging system. The same logic applies to any request that can time out: "did my payment go through?" is exactly "was it the DATA or the ACK that was lost?" The sender cannot know, so it must retry, and the server must make retries harmless with an identifier it recognises: an idempotency key is a sequence number by another name. Chapter 16 develops this fully, the retry-storm case study shows what happens when thousands of senders back off badly, and the replicated key-value store in lab 5 will have you build idempotency keys yourself.

What you learned

  • Reliability is built from four small ideas: sequence numbers, acknowledgements, timeouts and retransmission, plus a checksum to turn damage into loss.
  • A timeout is a guess. Lost data and a lost ACK look identical to the sender, so the receiver must tolerate duplicates.
  • Stop-and-wait delivers one packet per RTT: throughput = packet size ÷ RTT, regardless of bandwidth.
  • To fill a link you need a window of about bandwidth × RTT in flight (the bandwidth-delay product).
  • Go-Back-N with cumulative ACKs and one timer is simple and fast, but wasteful under loss; real TCP adds selective ACKs, fast retransmit and congestion control.
  • The retransmission timer should come from measured RTT (SRTT + 4 × RTTVAR), back off exponentially, and ignore samples from retransmitted packets (Karn's rule).

Check your understanding

A stop-and-wait sender uses 1500-byte packets over a 1 Gbit/s link with a 50 ms round-trip time. Roughly what throughput does it achieve?

  1. About 125 MB/s, the full link speed
  2. About 30 KB/s (roughly 240 kbit/s)
  3. About 1.5 KB/s
  4. About 600 KB/s
One packet per RTT: 1500 bytes ÷ 0.05 s = 30,000 bytes per second. The 1 Gbit/s only sets how quickly each packet is transmitted; it doesn't appear in the formula, because the sender spends nearly all its time waiting. The fix is more packets in flight, not a faster link.

The receiver gets DATA 5 (already delivered), because the sender's timer fired after the ACK was lost. What should it do?

  1. Deliver it again to the application, in case the first copy was wrong
  2. Ignore it silently
  3. Not deliver it again, but still send an ACK saying what it expects next
  4. Send an error and close the connection
The payload was already delivered, so delivering it again would duplicate data. But staying silent would leave the sender retrying forever, because the ACK it needs was the one that got lost. Re-acknowledging without re-delivering is what makes retransmission safe.

A Go-Back-N sender has base = 10 and next_seq = 18 when its timer fires. Which packets does it resend?

  1. Only packet 10
  2. Only packet 18
  3. Packets 10 to 17 that it thinks were lost, chosen by the receiver
  4. Every packet from 10 to 17
With cumulative ACKs the sender only knows that everything below 10 arrived. It has no record of which of 10 to 17 got through, so it goes back and resends them all. Selective Repeat avoids that waste by having the receiver report what it holds.

Why does Karn's rule say not to sample the RTT from a retransmitted packet?

  1. The ACK could be for the original or the copy, so the measured time may be wrong
  2. Retransmitted packets are always slower
  3. The checksum on a retransmitted packet is different
  4. The receiver doesn't ACK retransmitted packets
If you resend packet 7 and then an ACK arrives, it might be a late ACK for the first copy (making the RTT look tiny) or the ACK for the second (a normal RTT). Since you can't tell, the sample is unreliable, so TCP ignores it. This is the same ambiguity that forces every retrying client in chapter 16 to ask for idempotent operations.

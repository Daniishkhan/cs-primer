Lab 1: Sockets & a Chat Server

Time to stop reading about packets and start sending them. In this lab you'll write a UDP echo server, a TCP echo server, and then a real multi-person chat server that you and your friends (or a few terminal windows) can talk through. About 150 lines of Python, standard library only.

Why this lab matters

Every networked program, from a web browser to a database cluster, is built on the same handful of socket calls you'll use here. You'll also hit, in your own code, the two lessons that trip up almost everyone: UDP can silently lose your message, and TCP is a stream of bytes, not a series of messages.

What you'll build

You'll get there in four milestones, each building on the last:

  1. UDP echo: send a datagram, get it back in capitals, and handle the case where no answer ever comes.
  2. TCP echo: open a connection and watch how TCP splits and merges your data.
  3. Framing: turn TCP's endless byte stream back into separate messages (lines).
  4. Chat server: many clients at once, nicknames, join/leave notices.

Milestone 1: a UDP echo server

UDP is the simplest way to send data (chapter 7): you put bytes in a datagram, write an address on it, and send it. No connection, no handshake, no guarantee. The server side has three steps:

  1. Create a socket. socket.socket(socket.AF_INET, socket.SOCK_DGRAM). AF_INET means IPv4; SOCK_DGRAM means datagrams, which is UDP.
  2. Bind it to an address and port: sock.bind(("127.0.0.1", port)). This tells the OS "datagrams for this port are mine". It's the moment your program gets its flat number in the building.
  3. Loop: data, addr = sock.recvfrom(2048) waits for a datagram and tells you who sent it; sock.sendto(reply, addr) answers them.

The client is even simpler: create a UDP socket, sendto the server, then recvfrom the reply. But here's the important part. If the server isn't running, or the datagram is lost, recvfrom would wait forever. UDP will never tell you something went wrong. So the client must set a timeout and give up: sock.settimeout(2.0), then catch socket.timeout.

Your task

Implement udp_echo_server(port, ready, max_messages) and udp_send(message, port, timeout) in starter.py. The server replies with the same bytes in upper case. udp_send returns the reply as a string, or None if nothing arrives in time.

run python3 check.py: milestone 1 should show ✔. Then try it by hand: python3 starter.py udp-server in one terminal and python3 starter.py udp-send "hello" in another. Stop the server with Ctrl+C and send again: you should see the timeout message after 2 seconds.

Hints try without first
  • After bind, call sock.getsockname()[1] to learn the real port, and pass it to ready if ready isn't None.
  • Strings and bytes are different in Python. Sockets send bytes: use message.encode("utf-8") going out and data.decode("utf-8") coming in. bytes.upper() works directly on bytes.
  • On some systems, sending to a UDP port with nobody listening makes the next receive raise ConnectionRefusedError. That's the OS passing on an ICMP "port unreachable" message (chapter 6). Treat it like a timeout.
  • Use with socket.socket(...) as sock: so the socket is closed even if something goes wrong.
Solution spoiler 
def udp_echo_server(port=9001, ready=None, max_messages=None):
    with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as sock:
        sock.bind((HOST, port))
        port = sock.getsockname()[1]          # the real port if we asked for 0
        if ready:
            ready(port)
        handled = 0
        while max_messages is None or handled < max_messages:
            data, addr = sock.recvfrom(2048)  # addr = (sender IP, sender port)
            sock.sendto(data.upper(), addr)   # reply to whoever sent it
            handled += 1

def udp_send(message, port=9001, timeout=2.0):
    with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as sock:
        sock.settimeout(timeout)
        sock.sendto(message.encode("utf-8"), (HOST, port))
        try:
            data, _ = sock.recvfrom(2048)
        except (socket.timeout, ConnectionRefusedError):
            return None
        return data.decode("utf-8")

Notice what the server printed for each datagram: the sender's IP and a port number you never chose, something like 127.0.0.1:61834. That's the client's ephemeral port (chapter 7). The OS picked it automatically when the client first sent, and it's how the reply finds its way back to the right program.

Milestone 2: a TCP echo server

TCP (chapter 8) adds a connection. That changes the shape of the server: instead of one socket that receives from anyone, there's a listening socket that only accepts new connections, and then one new socket per client.

CallWhat it doesNetwork view
socket(AF_INET, SOCK_STREAM)make a TCP socketnothing on the wire yet
bind((host, port)) + listen()claim the port, start acceptingthe OS now answers SYNs for this port
conn, addr = accept()wait for the next client, get a socket just for themreturns after the three-way handshake completes
conn.recv(4096)read up to 4096 bytesbytes from the receive buffer, in order
conn.sendall(data)send all of datamay become many segments
recv() returns b""the other side closeda FIN arrived

Common misconception: one send() = one recv()

With TCP, recv(4096) returns whatever bytes have arrived so far, up to 4096. Send "hello" and "world" quickly and the receiver may get b"helloworld" in one call. Send 50 KB and it arrives in many pieces of unpredictable size. TCP promises the bytes arrive complete and in order, not that your message boundaries survive. Also use sendall, not send: send is allowed to send only part of your data and return how much it managed.

Your task

Implement tcp_echo_server(port, ready, max_clients): accept clients one at a time and echo every byte back until the client disconnects. Print what each recv() returns.

Hints try without first
  • Set srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1) before bind. Without it, restarting the server right after stopping it fails with "Address already in use" while the old connections sit in TIME_WAIT (chapter 8).
  • The structure is two loops: an outer while around accept(), and an inner while True around recv() that breaks when recv returns b"".
  • This server handles one client at a time. A second nc will connect (the OS completes the handshake and queues it) but won't be echoed until the first one quits. You'll fix that properly in milestone 4.
Solution spoiler 
def tcp_echo_server(port=9002, ready=None, max_clients=None):
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as srv:
        srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        srv.bind((HOST, port))
        srv.listen()
        if ready:
            ready(srv.getsockname()[1])
        served = 0
        while max_clients is None or served < max_clients:
            conn, addr = srv.accept()                 # blocks until a handshake completes
            with conn:
                while True:
                    chunk = conn.recv(4096)           # up to 4096 bytes: maybe fewer
                    if not chunk:                     # b"" means the client closed (FIN)
                        break
                    print(f"  recv() returned {len(chunk)} bytes: {chunk!r}")
                    conn.sendall(chunk)
            served += 1

Milestone 3: framing messages

A chat server needs messages, but TCP only gives it a stream of bytes. Turning the stream back into messages is called framing (chapter 12). There are two common ways: put the length in front of each message, or end each message with a special delimiter. We'll use the second, because it's what nc and every terminal naturally produce: each message is one line, ending in a newline (\n).

The trick is to keep a buffer. Every time bytes arrive, add them to the buffer, cut off every complete line, and keep the incomplete tail for next time:

milestone 3 shows ✔. The check includes a sneaky case: the two bytes of the letter é arriving in different chunks.

Hints try without first
  • b"a\nb\nc".split(b"\n") gives [b"a", b"b", b"c"]. The last element is always the unfinished part (it's b"" if the data ended with a newline).
  • Keep the buffer as bytes and only decode complete lines. Decoding each chunk separately breaks when a multi-byte UTF-8 character is cut in half between two recv calls.
Solution spoiler 
def feed(self, data):
    self._buf += data
    *lines, self._buf = self._buf.split(b"\n")   # the last piece is incomplete
    return [line.rstrip(b"\r").decode("utf-8", "replace") for line in lines]
Go deeper: what if someone never sends a newline? optional

Then self._buf grows forever, and a malicious client can exhaust your server's memory by streaming gigabytes without a single \n. Real servers cap the line length (HTTP servers typically reject request lines or headers over a few kilobytes) and disconnect clients that exceed it. Adding that limit is one of the stretch goals.

Milestone 4: the chat server

The echo server had a big flaw: while it waits in recv() for one client, everyone else is ignored. A chat server must listen to everyone at once. There are three classic ways to do that:

A thread per client

Simple to write, but threads cost memory and every shared data structure needs locks.

An event loop (our choice)

One thread asks the OS "which of these sockets have data?" and only calls recv on those. This is how nginx, Node.js and Redis work.

async/await

An event loop with nicer syntax (Python's asyncio). Same idea underneath.

Python's selectors module wraps the operating system's "which sockets are ready?" call (epoll on Linux, kqueue on macOS). You register each socket once, then sel.select() returns the ones that have something to read. The listening socket being "readable" means a new client is waiting to be accepted. A client socket being readable means it sent data, or hung up (then recv returns b"").

The event loop is already written for you in ChatServer.serve_forever. Read it first: it's 20 lines and it's the heart of the program. Your job is the handlers it calls. The protocol is deliberately tiny:

EventServer doesExact text
client connectsgreet it; tell everyone elseWELCOME, then * guest-51234 joined
line /nick alicerename; tell everyone (including the sender)* guest-51234 is now alice
any other linesend to everyone except the sender[alice] the line
/quit or disconnectclose; tell everyone else* alice left

Use the helpers fmt_chat and fmt_notice so the text matches exactly what the check expects. Every message ends with \n, so clients can frame them with the same LineBuffer.

Hints try without first
  • Give each client socket a timeout with sock.settimeout(2.0). The selector already guarantees recv won't wait, but sendall can: if a client stops reading, its receive window fills up (flow control, chapter 8) and sendall would block the whole server. With a timeout, you drop that client instead.
  • In broadcast, loop over list(self.clients.values()), a copy. A failed send calls _disconnect, which deletes from the dictionary while you're looping over it.
  • _disconnect can be reached twice for the same client (for example, a failed send while handling its /quit). Start it with if client.sock not in self.clients: return.
  • In _read, a single recv can contain several lines, or half of one. That's exactly what your LineBuffer is for.
Solution spoiler 
def _accept(self, srv):
    sock, addr = srv.accept()
    sock.settimeout(2.0)                 # a stuck client can't freeze sendall() forever
    client = Client(sock, addr)
    self.clients[sock] = client
    self.sel.register(sock, selectors.EVENT_READ, data=client)
    self._send(client, WELCOME)
    self.broadcast(fmt_notice(f"{client.name} joined"), exclude=client)

def _read(self, client):
    try:
        data = client.sock.recv(4096)
    except OSError:
        data = b""
    if not data:                            # hung up
        self._disconnect(client)
        return
    for line in client.lines.feed(data):
        self._handle_line(client, line)
        if client.sock not in self.clients:   # /quit closed it
            return

def _handle_line(self, client, line):
    line = line.strip()
    if not line:
        return
    if line.startswith("/nick "):
        new = line[6:].strip()[:20] or client.name
        old, client.name = client.name, new
        self.broadcast(fmt_notice(f"{old} is now {new}"))
    elif line == "/quit":
        self._disconnect(client)
    else:
        self.broadcast(fmt_chat(client.name, line), exclude=client)

def broadcast(self, text, exclude=None):
    for client in list(self.clients.values()):
        if client is not exclude:
            self._send(client, text)

def _send(self, client, text):
    try:
        client.sock.sendall(text.encode("utf-8"))
    except OSError:                      # includes socket.timeout
        self._disconnect(client)

def _disconnect(self, client):
    if client.sock not in self.clients:
        return
    self.sel.unregister(client.sock)
    del self.clients[client.sock]
    client.sock.close()
    self.broadcast(fmt_notice(f"{client.name} left"))

That's how one server port can carry thousands of conversations at once (chapter 7). The guest-51234 names your server made up are those same client ports.

Try it yourself: three experiments

  1. Watch a handshake. Run sudo tcpdump -i lo0 -n port 9003 (needs your password; on Linux use -i lo), then connect a new nc. You'll see the SYN, SYN-ACK and ACK from chapter 8, then your chat lines as data segments.
  2. Lose a UDP message on purpose. With the UDP server stopped, run udp-send. TCP would have told you "connection refused" immediately. UDP just leaves you waiting until your own timeout fires.
  3. Talk across machines. Change HOST to "0.0.0.0" (all interfaces) in the server only, find your laptop's IP (chapter 4), and connect from a second computer on the same Wi-Fi with nc YOUR-IP 9003. Your OS firewall may ask for permission. Change it back afterwards.

Stretch goals

  • /who: reply (only to the sender) with the list of names online.
  • Private messages: /msg bob hello goes to bob only. What should happen if there are two bobs? (Rejecting duplicate nicknames is one answer.)
  • Line length limit: disconnect a client whose buffer exceeds 4 KB without a newline.
  • Slow consumers, properly: instead of a 2-second sendall timeout, give each client an outgoing buffer, register for EVENT_WRITE when it's non-empty, and send what fits. This is how production event loops work.
  • Length-prefixed framing: write a second version where each message is a 4-byte length followed by the bytes, using struct.pack("!I", n) (chapter 12). Which one handles binary data like images?
  • Encryption: wrap the listening socket with Python's ssl module and a self-signed certificate, and connect with openssl s_client -connect 127.0.0.1:9003 (chapter 11).

Distributed systems connection

You've just built a tiny message broker: one process that receives messages and fans them out to subscribers. Scale it up and the hard questions of Part 6 appear. If the server crashes, are messages lost? If you run two servers, how do clients on different servers talk to each other? If a client's connection drops for five seconds, does it miss messages, and how would it know? Case study 5 looks at how real chat systems answer these, and Lab 5 tackles keeping copies of data on several servers.

What you learned

  • A socket is your program's endpoint: bind claims a port, connect/accept make TCP connections, sendto/recvfrom send UDP datagrams.
  • UDP never reports loss. Your only defence is a timeout.
  • TCP delivers a byte stream: recv returns arbitrary-sized chunks, so you need framing to recover messages.
  • Keep the buffer as bytes and decode only complete messages.
  • An event loop with a selector serves many connections from one thread, but one slow client can still stall everyone unless you plan for it.

Check your understanding

A client calls sendall(b"hi\n") and then sendall(b"there\n") over TCP. What can the server's first recv(4096) return?

  1. Always exactly b"hi\n"
  2. Always b"hi\nthere\n"
  3. Any prefix of b"hi\nthere\n", from 1 byte up to all of it
  4. The bytes in any order
TCP preserves order and content but not boundaries. The first recv returns whatever has arrived: maybe just b"h", maybe everything. Bytes never arrive out of order, though. That's why the server needs a LineBuffer.

Your UDP client sends a datagram and the server isn't running. What happens if the client has no timeout?

  1. It may wait forever in recvfrom
  2. Python raises an error as soon as the datagram is lost
  3. The OS automatically resends it until the server starts
  4. UDP switches to TCP
UDP has no acknowledgements, so nobody is responsible for noticing loss. Some systems pass on an ICMP "port unreachable" as an error, but you can't rely on it (a lost datagram on a real network produces nothing at all). A timeout is the only general answer, the same lesson Part 6 builds on.

Why does the chat server give every client socket a 2-second timeout?

  1. To disconnect people who haven't typed anything for 2 seconds
  2. Because the selector needs it to work
  3. To make recv faster
  4. So sendall to a client that stopped reading can't block the whole single-threaded server
The selector only promises that recv won't wait. If a client stops reading, TCP flow control eventually stops the sender, and sendall would wait for space. In a one-thread server that freezes everyone. The timeout turns "stuck forever" into "drop that client". A timeout used to contain a slow participant is a pattern you'll meet again in chapter 16.

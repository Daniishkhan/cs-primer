Lab 3: A DNS Resolver from Scratch

Every time you type a web address, a tiny UDP packet asks "what's the IP address for this name?" In this lab you'll build that packet byte by byte, decode the reply (including DNS's clever name compression), and then do what your ISP's resolver does: start at a root server and follow the referrals down the tree until you reach the answer. About 250 lines of Python, standard library only.

Why this lab matters

DNS is the first thing that happens on almost every connection, and it is the most successful distributed database ever built: billions of names, no single owner, answers cached everywhere. Writing a resolver shows you how a binary protocol is laid out on the wire, how a hierarchy of servers cooperates through delegation, and how caching with an expiry time (TTL) keeps the whole thing fast. Those are the same ideas you meet again in replication and partitioning in Part 6.

What you'll build

Six milestones, each building on the last:

  1. Build a query: a 12-byte header and a question, packed with struct.
  2. Parse a response: header, questions, answers, authority, additional, and names that point back into the packet.
  3. A mini dig: send your query to 1.1.1.1 over UDP and print the A records.
  4. Iterative resolution: start at a root server, follow referrals using glue records, and look up name servers that come without glue. Print a trace like dig +trace.
  5. A TTL cache: the second lookup is instant.
  6. CNAMEs (optional): follow aliases.

Network reality: UDP port 53 isn't always open

Some networks (hotels, schools, companies, some home routers) block outbound DNS to servers other than their own, or quietly redirect it to their own resolver. So this lab is built to work without reaching the Internet. check.py tests milestones 1 to 6 offline, using real DNS replies that were recorded once and are embedded in the file, plus hand-built packets and a fake DNS server on 127.0.0.1. A separate, clearly labelled online section talks to real servers; if it can't, it prints "skipped" and carries on. You can finish the whole lab with the Wi-Fi off.

Milestone 1: build a DNS query

DNS has its own packet format, carried inside a UDP datagram to port 53 (chapter 7). Every DNS message, query or response, starts with the same 12-byte header: six numbers of two bytes each.

ID16 bits
FLAGS16 bits
QDCOUNTquestions
ANCOUNTanswers
NSCOUNTauthority records
ARCOUNTadditional records
FieldMeaning
IDA number you pick. The server copies it into its reply, so you can match replies to questions (and notice impostors, see milestone 3).
FLAGSSixteen single-bit and small fields, below.
QDCOUNTHow many questions follow the header. Always 1 in practice.
ANCOUNTHow many answer records are in the reply. 0 in a query.
NSCOUNTHow many authority records: "here are the name servers responsible". Used in referrals. 0 in a query.
ARCOUNTHow many additional records: helpful extras, such as the IP addresses of those name servers (glue). 0 in a query.

The flags field packs several small values into 16 bits. Most of them only matter in replies:

QR1 bit
OPCODE4 bits
AA1
TC1
RD1
RA1
Z3 bits
RCODE4 bits
  • QR: 0 for a query, 1 for a response.
  • OPCODE: 0 for a normal query.
  • AA: "authoritative answer": this server owns the zone and is not repeating something from its cache.
  • TC: "truncated": the reply didn't fit in a UDP datagram, so ask again over TCP.
  • RD: "recursion desired": the sender asks the server to do the whole job. Set it when asking a recursive resolver like 1.1.1.1. A query with only this bit set has flags 0x0100.
  • RA: "recursion available": the server says it is willing to do that.
  • RCODE: 0 = no error, 2 = SERVFAIL (the server broke), 3 = NXDOMAIN (this name does not exist).

The question

After the header comes the question: the name, a type (what kind of record: A = IPv4 address = 1, NS = 2, CNAME = 5, MX = 15, TXT = 16, AAAA = IPv6 address = 28) and a class (always IN, the Internet, = 1).

The name is not written as example.com. Each dot-separated label is stored as a length byte followed by its characters, and the name ends with a zero byte (the empty label of the root):

>>> encode_name("example.com")
b'\x07example\x03com\x00'

Why lengths instead of dots? Because it makes the parser's job trivial and unambiguous: read one byte, then read exactly that many characters. No searching for delimiters. (It also means a label can hold any bytes and can be at most 63 long, since the top two bits of the length byte are reserved, as you'll see in milestone 2.)

Put it together and here is the whole query for example.com type A, 29 bytes, with ID 0x1234 and recursion desired:

0000  12 34 01 00 00 01 00 00 00 00 00 00 07 65 78 61  .4...........exa
0010  6d 70 6c 65 03 63 6f 6d 00 00 01 00 01           mple.com.....
BytesMeaning
12 34ID = 0x1234
01 00flags: only RD set (bit 8 = 0x0100)
00 01QDCOUNT = 1
00 00 00 00 00 00ANCOUNT, NSCOUNT, ARCOUNT = 0
07 65 78 61 6d 70 6c 65length 7, then "example"
03 63 6f 6d 00length 3, then "com", then the root's zero byte
00 01QTYPE = 1 (A)
00 01QCLASS = 1 (IN)

All multi-byte numbers are big-endian ("network byte order": the most significant byte first). In Python's struct that is the ! prefix: struct.pack("!HHHHHH", ...) is six unsigned 16-bit numbers.

def encode_name(name):
    out = b""
    for label in name.strip(".").split("."):
        if not label:
            continue                                  # the root name "." has no labels
        raw = label.encode("ascii")
        if len(raw) > 63:
            raise ValueError(f"label too long: {label!r}")
        out += bytes([len(raw)]) + raw                # length byte, then the characters
    return out + b"\x00"                              # the root's empty label ends the name

def build_query(name, qtype=TYPE_A, qid=None, recursion_desired=True):
    if qid is None:
        qid = random.randrange(65536)
    flags = 0x0100 if recursion_desired else 0x0000   # only the RD bit may be set
    header = struct.pack("!HHHHHH", qid, flags,
                         1,      # QDCOUNT: one question
                         0, 0, 0)  # ANCOUNT, NSCOUNT, ARCOUNT
    question = encode_name(name) + struct.pack("!HH", qtype, CLASS_IN)
    return header + question

Milestone 2: parse a response

A response repeats the header and the question, then adds up to three lists of resource records (RRs), the same record format as chapter 9's "name, type, TTL, value":

  1. Answer: the records you asked for.
  2. Authority: name servers (NS records) for the zone that is responsible. In a referral, this is the answer's substitute: "I don't know, but ask these".
  3. Additional: extra records the server thinks you'll need next, typically the IP addresses of those name servers.

Every RR has the same layout: the owner name, then a fixed 10 bytes (TYPE 2, CLASS 2, TTL 4, RDLENGTH 2), then RDLENGTH bytes of data whose meaning depends on the type. For an A record the data is the four bytes of an IPv4 address. Here is a real answer from an authoritative server for example.com (61 bytes; recorded in October 2026, so today's IPs may differ):

0000  00 00 84 00 00 01 00 02 00 00 00 00 07 65 78 61  .............exa
0010  6d 70 6c 65 03 63 6f 6d 00 00 01 00 01 c0 0c 00  mple.com........
0020  01 00 01 00 00 01 2c 00 04 ac 42 93 f3 c0 0c 00  ......,...B.....
0030  01 00 01 00 00 01 2c 00 04 68 14 17 9a           ......,..h...
BytesMeaning
00 00ID (we sent 0 when recording it)
84 00flags 0x8400: QR = 1 (a response) and AA = 1 (authoritative)
00 01 00 02 00 00 00 001 question, 2 answers, 0 authority, 0 additional
07 example 03 com 00 00 01 00 01the question, repeated: name starts at offset 12, type A, class IN
c0 0canswer 1, owner name: "continue at offset 12"
00 01 00 01 00 00 01 2c 00 04type A, class IN, TTL 0x12c = 300 seconds, data length 4
ac 42 93 f3the data: 172.66.147.243
c0 0c ... 68 14 17 9aanswer 2, same shape, ending in 104.20.23.154

Compression pointers

Look at the two answers: they begin with c0 0c instead of spelling out example.com again. A DNS packet can be tiny (a classic UDP reply had to fit in 512 bytes), and the same names repeat constantly: every record in a reply is usually about the same zone. So DNS uses name compression. If the top two bits of a length byte are 11, the byte is not a length at all: those two bits plus the following 14 bits are an offset from the start of the packet where the name continues.

Pointers can also appear after some labels: l.gtld-servers.net can be stored as the label l followed by a pointer to a place where gtld-servers.net is already written. A name is therefore "labels, then either a zero byte or a pointer". And a pointer may point to a place that itself ends in a pointer. When your decoder follows a pointer, the position where parsing continues is just after the pointer's two bytes, not after the name it jumped to.

Never trust a packet

This is parsing data from the network, and anyone can send you anything. A pointer that points at itself would make a naive decoder loop forever; a length byte near the end of the packet could send you reading past it. Real DNS software has had serious security bugs in exactly this code. The check feeds your parser self-referencing pointers and truncated packets and requires a clean DNSError every time, never a hang, IndexError or struct.error.

Hints try without first
  • In decode_name, loop: read length = buf[offset]. 0: finished. length & 0xC0 == 0xC0: pointer, with target ((length & 0x3F) << 8) | buf[offset + 1]. Otherwise a label of length bytes.
  • Remember next_offset the first time you follow a pointer (offset + 2) and never overwrite it. If you never saw a pointer, it's the offset just after the zero byte.
  • Count pointer jumps. More than about 20 is certainly a loop: raise DNSError.
  • For NS, CNAME and PTR data, call decode_name(buf, offset) with the whole packet as buf, because the pointer targets are offsets from the start of the packet, not of the record.
  • struct.unpack("!HHIH", buf[offset:offset+10]) reads TYPE, CLASS, TTL (4 bytes) and RDLENGTH. Check that offset + 10 + rdlength is not past len(buf) first.
  • socket.inet_ntoa(four_bytes) makes "192.0.2.1". ipaddress.IPv6Address(sixteen_bytes) handles AAAA.
  • Parse the sections in order, each record starting where the last ended. The counts in the header tell you how many of each.
Solution spoiler 
def decode_name(buf, offset):
    labels = []
    next_offset = None           # set at the first pointer; the name "ends" there
    jumps = 0
    while True:
        if offset >= len(buf):
            raise DNSError("name runs past the end of the packet")
        length = buf[offset]
        if length == 0:                                    # end of name
            offset += 1
            break
        if length & 0xC0 == 0xC0:                          # compression pointer
            if offset + 1 >= len(buf):
                raise DNSError("truncated compression pointer")
            if next_offset is None:
                next_offset = offset + 2
            offset = ((length & 0x3F) << 8) | buf[offset + 1]
            jumps += 1
            if jumps > 20:                                 # a pointer loop
                raise DNSError("too many compression pointers (loop?)")
            continue
        if length & 0xC0:
            raise DNSError("unsupported label type")
        start = offset + 1
        if start + length > len(buf):
            raise DNSError("label runs past the end of the packet")
        labels.append(buf[start:start + length].decode("ascii", "replace"))
        offset = start + length
    return ".".join(labels), (next_offset if next_offset is not None else offset)

def parse_record(buf, offset):
    name, offset = decode_name(buf, offset)
    if offset + 10 > len(buf):
        raise DNSError("truncated record header")
    rtype, rclass, ttl, rdlength = struct.unpack("!HHIH", buf[offset:offset + 10])
    offset += 10
    end = offset + rdlength
    if end > len(buf):
        raise DNSError("record data runs past the end of the packet")
    if rtype == TYPE_A and rdlength == 4:
        rdata = socket.inet_ntoa(buf[offset:end])
    elif rtype == TYPE_AAAA and rdlength == 16:
        rdata = str(ipaddress.IPv6Address(buf[offset:end]))
    elif rtype in (TYPE_NS, TYPE_CNAME, TYPE_PTR):
        rdata, _ = decode_name(buf, offset)               # may contain pointers into buf
    elif rtype == TYPE_MX:
        (preference,) = struct.unpack("!H", buf[offset:offset + 2])
        exchange, _ = decode_name(buf, offset + 2)
        rdata = (preference, exchange)
    elif rtype == TYPE_TXT:
        strings, i = [], offset
        while i < end:                                    # length-prefixed strings
            n = buf[i]
            strings.append(buf[i + 1:i + 1 + n].decode("utf-8", "replace"))
            i += 1 + n
        rdata = strings
    else:
        rdata = bytes(buf[offset:end])                    # unknown type: keep the raw bytes
    return Record(name, rtype, rclass, ttl, rdata), end

def parse_message(data):
    if len(data) < 12:
        raise DNSError("packet shorter than the 12-byte header")
    qid, flags, qd, an, ns, ar = struct.unpack("!HHHHHH", data[:12])
    offset = 12
    questions = []
    for _ in range(qd):
        name, offset = decode_name(data, offset)
        if offset + 4 > len(data):
            raise DNSError("truncated question")
        qtype, qclass = struct.unpack("!HH", data[offset:offset + 4])
        offset += 4
        questions.append(Question(name, qtype, qclass))
    sections = []
    for count in (an, ns, ar):                            # answers, authority, additional
        records = []
        for _ in range(count):
            rec, offset = parse_record(data, offset)
            records.append(rec)
        sections.append(records)
    return Message(qid, flags, questions, *sections)

Milestone 3: a mini dig

Now connect the two halves. You build a query, send it in a UDP datagram to port 53 of a server, wait for the reply, and parse it. You've done the socket part before in lab 1. Three details make this one safer and more realistic:

  • Check who and what answered. UDP lets anyone send your socket a datagram. Accept a reply only if it comes from the server you asked and carries the ID you chose; otherwise ignore it and keep waiting. The ID is a 16-bit number that an off-path attacker has to guess; this is one of the cheapest defences DNS has (real resolvers also randomise the source port, which adds about 16 more bits).
  • Use a deadline, not a single timeout (lab 2's lesson): ignoring a stray packet shouldn't restart the clock. If time runs out, raise DNSTimeout.
  • Truncation. A plain DNS-over-UDP reply is limited in size (512 bytes in the original protocol; newer clients negotiate more). If a reply doesn't fit, the server sets the TC bit and sends what it can. Then you repeat the question over TCP. query_tcp is already written (it adds a 2-byte length in front of each message, because TCP is a stream: lab 1's framing lesson); you just have to call it when you see the bit.

Which server? A recursive resolver such as Cloudflare's 1.1.1.1 will do the whole walk for you and cache the results for everyone who uses it (chapter 9). With the RD flag set, your program becomes a stub resolver: it asks one question, gets one final answer. Once it works, the provided print_dig shows it in the style of the real tool:

$ python3 starter.py dig example.com
;; status: NOERROR, id: 14105, flags: qr rd ra
;; QUESTION: example.com. IN A
;; ANSWER SECTION:
example.com.                 210    IN  A      172.66.147.243
example.com.                 210    IN  A      104.20.23.154
;; Query time: 4 msec   SERVER: 1.1.1.1

(Your addresses and TTL will differ; the TTL counts down because 1.1.1.1 is serving you from its cache. If you see it jump back up, you've waited for the cache to refresh.) The same works for other types: python3 starter.py dig example.com NS, ... MX, ... AAAA, or a different server with @8.8.8.8.

Hints try without first
  • Create the socket with socket.AF_INET, socket.SOCK_DGRAM, send with sock.sendto(packet, (server, port)).
  • Loop with remaining = deadline - time.monotonic(); if it's <= 0 raise DNSTimeout. Set sock.settimeout(remaining) before each recvfrom(4096) and convert socket.timeout into DNSTimeout.
  • The ID is the first two bytes of the reply: struct.unpack("!H", data[:2])[0]. Compare it with the qid you sent. addr[0] is the sender's IP.

Solution spoiler 
def query_udp(server, name, qtype=TYPE_A, port=53, timeout=2.0, recursion_desired=True):
    qid = random.randrange(65536)
    packet = build_query(name, qtype, qid=qid, recursion_desired=recursion_desired)
    with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as sock:
        sock.sendto(packet, (server, port))
        deadline = time.monotonic() + timeout
        while True:
            remaining = deadline - time.monotonic()
            if remaining <= 0:
                raise DNSTimeout(f"no reply from {server} within {timeout} s")
            sock.settimeout(remaining)
            try:
                data, addr = sock.recvfrom(4096)
            except socket.timeout:
                raise DNSTimeout(f"no reply from {server} within {timeout} s")
            if addr[0] != server:                         # not from who we asked
                continue
            if len(data) < 12 or struct.unpack("!H", data[:2])[0] != qid:
                continue                                  # wrong ID: stray or forged
            break
    if data[2] & 0x02:                                    # TC bit: the reply didn't fit in UDP
        return query_tcp(server, name, qtype, port, timeout, recursion_desired)
    return parse_message(data)

Milestone 4: resolve from the root, like dig +trace

Asking 1.1.1.1 hides all the interesting work. Now do it yourself. You don't need any recursive resolver: you need only the addresses of the 13 root servers (the constant ROOT_SERVERS, from IANA's published "root hints"), because the root knows who runs each top-level domain, and every domain's servers are reachable by following the chain.

The conversation with each server is an iterative query: you leave the RD bit off, and the server either answers or tells you who to ask next. A reply that carries no answers but an authority section full of NS records is a referral. Here are the three real replies for example.com (recorded in October 2026):

You askAnswer sectionAuthority sectionAdditional section
a root serverempty13 × com. NS x.gtld-servers.netan A and an AAAA record for each of those 13 names
a .com serveremptyexample.com. NS hera.ns.cloudflare.com and ... elliott.ns.cloudflare.comtheir A and AAAA records
an example.com servertwo A records (AA bit set)emptyempty

Glue

The additional-section records are glue (chapter 9's "chicken and egg" box). To ask l.gtld-servers.net a question, you need its IP address; but to look up its IP address you would have to ask... the .net servers, which are what you're trying to find. The parent zone breaks the circle by handing out the child's name-server addresses together with the referral.

That second case isn't hypothetical: example.org in October 2026 is exactly this. Your resolver gets the NS names back with no addresses, calls itself on mitch.ns.cloudflare.com (a fresh walk: root, then .com, then cloudflare.com's servers), gets the address, and only then continues with the question it was asked. That recursion needs a depth limit (a name server whose address depends on itself must not loop forever).

Analogy: asking at information desks

You want the phone number of "Flat 3, 12 Oak Street" in a country you've never visited. The national enquiry desk doesn't know it, but knows which regional desk handles Oak Street's region and gives you that desk's number. The regional desk doesn't know either, but gives you the number of the town's desk, which finally knows the flat. Each answer is "I don't know, but ask them". Where it breaks down: real DNS referrals usually come with the next desk's number written on them (glue), and everyone remembers the answers for a while (caching), so most questions never reach the national desk at all.

Is that really a root server answering you?

Root servers never recurse. If you send one a question with no answer to give (say, dig @198.41.0.4 example.com +norecurse) you must get a referral. If a network hands you the final answer instead, with the ra flag set, something between you and the root is quietly redirecting your DNS traffic to its own resolver: a "transparent DNS proxy". It happens on some corporate, hotel and mobile networks, and it is exactly why the online checks here are optional. (Some of these proxies only intercept UDP, which is one reason an online check also runs the walk over TCP.)

def resolve_iterative(name, qtype=TYPE_A, query_fn=ask_server, roots=ROOT_SERVERS,
                      trace=None, _depth=0):
    say = trace or (lambda line: None)
    if _depth > MAX_DEPTH:
        raise DNSError("too many nested lookups")
    label = type_name(qtype)
    servers = [ip for _, ip in roots]
    zone = "."
    for _ in range(MAX_REFERRALS):
        # Ask the servers of the current zone, one at a time, until one replies.
        msg = None
        for server in servers:
            say(f"{'  ' * _depth}ask {server} ({zone}) for {name} {label}")
            try:
                msg = query_fn(server, name, qtype)
                break
            except (DNSError, OSError) as e:
                say(f"{'  ' * _depth}  no answer from {server}: {e}")
        if msg is None:
            raise DNSError(f"no name server for {zone} answered")
        if msg.rcode == 3:
            raise DNSError(f"NXDOMAIN: {name} does not exist")
        if msg.rcode != 0:
            raise DNSError(f"server returned {RCODE_NAMES.get(msg.rcode, msg.rcode)}")

        if msg.answers:
            say(f"{'  ' * _depth}  answer: {len(msg.answers)} record(s)")
            have = [r for r in msg.answers if r.rtype == qtype]
            cnames = [r for r in msg.answers if r.rtype == TYPE_CNAME]
            if have or qtype == TYPE_CNAME or not cnames:
                return msg.answers
            # Milestone 6: only a CNAME came back. Start over for the target name.
            target = cnames[-1].rdata
            say(f"{'  ' * _depth}  {name} is an alias for {target}; resolving that")
            return msg.answers + resolve_iterative(target, qtype, query_fn, roots, trace, _depth + 1)

        # No answer: is it a referral? Look for NS records in the authority section.
        ns_records = [r for r in msg.authority if r.rtype == TYPE_NS]
        if not ns_records:
            say(f"{'  ' * _depth}  the name exists but has no {label} records")
            return []
        glue = {}
        for r in msg.additional:
            if r.rtype == TYPE_A:
                glue.setdefault(r.name.lower(), []).append(r.rdata)
        servers = [ip for r in ns_records for ip in glue.get(r.rdata.lower(), [])]
        zone = ns_records[0].name
        with_glue = sum(1 for r in ns_records if r.rdata.lower() in glue)
        say(f"{'  ' * _depth}  referral to {zone}: {len(ns_records)} name servers, "
            f"{with_glue} with glue (e.g. {ns_records[0].rdata})")
        if not servers:
            # No glue: we must look up a name server's address ourselves.
            for r in ns_records:
                say(f"{'  ' * _depth}  no glue; resolving the name server {r.rdata} first")
                try:
                    found = resolve_iterative(r.rdata, TYPE_A, query_fn, roots, trace, _depth + 1)
                except DNSError:
                    continue
                servers = [a.rdata for a in found if a.rtype == TYPE_A]
                if servers:
                    break
            if not servers:
                raise DNSError(f"could not find an address for any {zone} name server")
    raise DNSError("too many referrals (loop?)")

Milestone 5: a TTL cache

The walk you just did took four or five round trips (the example below takes six queries to find one address). Doing it again for every lookup would be absurd, and would crush the root servers. Every DNS record therefore carries a TTL, the number of seconds a cache may reuse it (chapter 9). A cache stores the answer together with an expiry time (now plus the TTL), serves it until then, and discards it afterwards. When it serves a cached record it reports the remaining TTL, not the original, so the countdown stays honest across the whole chain of caches.

Two small rules matter:

  • A list of records (for instance two A records, or a CNAME plus an A) is cached as one unit and expires with its shortest TTL.
  • A TTL of 0 means "don't cache this".

The cache takes a clock function (default time.monotonic). That is not decoration: it lets the check pretend that 300 seconds pass in an instant, which is how you test expiry without waiting five minutes. Injecting the clock is a standard trick for testing time-dependent code, and you'll want it again when you test anything with timeouts.

$ python3 starter.py cache example.com
lookup 1:    27.10 ms  ->  104.20.23.154 (ttl 300), 172.66.147.243 (ttl 300)
lookup 2:     0.01 ms  ->  104.20.23.154 (ttl 299), 172.66.147.243 (ttl 299)

(Example numbers; the first lookup depends on your network. The second is a dictionary lookup: thousands of times faster, and its TTL has already ticked down.)

Solution spoiler 
class TTLCache:
    def __init__(self, clock=time.monotonic):
        self.clock = clock
        self._items = {}                    # key -> (expires_at, records)

    def put(self, key, records):
        ttl = min((r.ttl for r in records), default=0)
        if ttl <= 0:
            return                          # TTL 0 means "do not cache"
        self._items[key] = (self.clock() + ttl, records)

    def get(self, key):
        item = self._items.get(key)
        if item is None:
            return None
        expires_at, records = item
        remaining = expires_at - self.clock()
        if remaining <= 0:
            del self._items[key]            # expired
            return None
        left = math.ceil(remaining)         # whole seconds remaining
        return [r._replace(ttl=left) for r in records]

class CachingResolver:
    def __init__(self, query_fn=ask_server, roots=ROOT_SERVERS, clock=time.monotonic, trace=None):
        self.query_fn, self.roots, self.trace = query_fn, roots, trace
        self.cache = TTLCache(clock)

    def resolve(self, name, qtype=TYPE_A):
        key = (name.lower().rstrip("."), qtype)
        hit = self.cache.get(key)
        if hit is not None:
            if self.trace:
                self.trace(f"cache hit for {name} {type_name(qtype)}")
            return hit
        answers = resolve_iterative(name, qtype, self.query_fn, self.roots, self.trace)
        self.cache.put(key, answers)
        return answers

A cache can be wrong, on purpose

If the owner of example.com changes its IP address a minute after you cached the old one with a 300-second TTL, your resolver will keep handing out the old address for up to four more minutes. That is not a bug; it's the contract. The TTL is the owner's promise about how stale you may be, and the reason "DNS changes take time to propagate" (chapter 9). You have built a miniature eventually consistent system.

Milestone 6 (optional): CNAMEs

A CNAME record says "this name is an alias for that other name". Many websites do this (www.shop.example is a CNAME for shop.some-cdn.net). A query for the alias's A record may therefore return only the CNAME. The resolver must then start a new lookup for the target and splice the results together. The reply can come in two shapes:

  • CNAME and the final A record in the same answer section, because the same server knew both. Nothing more to do: return them all.
  • Only the CNAME. Resolve the target name, then return the CNAME record(s) followed by the target's records.

Two extra rules: if the question was for type CNAME itself, the CNAME is the answer; and aliases can chain or even loop (a → b → a is a configuration error some zones really contain), so the same depth limit must apply. If you followed the milestone-4 skeleton, the solution is a handful of lines at the point where you return the answers. The check uses hand-built servers for this milestone, including a CNAME loop.

Distributed systems connection

You have just built both halves of a real distributed database. Partitioning: no machine holds all names; the tree is cut into zones, and delegation (a referral) tells you which partition to ask next, the same idea as shard maps and consistent hashing in chapter 19. Replication and consistency: every zone is served by several servers (and the root by hundreds of machines behind 13 addresses), and every cache holds a copy it is allowed to keep for a TTL, so readers can see stale data for a bounded time: the eventual-consistency trade-off of chapter 18, with the staleness bound written into the data. Failure handling: your resolver tries the next server on a timeout and caps its retries, the behaviour chapter 16 develops. And it shows what happens when the map itself disappears: the Facebook 2021 case study (case study 6) is a story of DNS servers that vanished from the Internet.

What you learned

  • A DNS message is a 12-byte header followed by length-prefixed names and fixed-layout records, all in big-endian binary, and struct is the tool for it.
  • Names are compressed with pointers into the same packet, so a decoder must follow them safely, with loop and bounds checks. Parsers of network data must never trust their input.
  • Match replies to queries by ID and sender, and use a deadline so strays can't extend your wait.
  • Iterative resolution: root, TLD, authoritative, each step a referral with glue. When the name servers are outside the delegated zone, there's no glue and you must resolve them first.
  • A TTL cache stores records until an expiry time and reports the remaining TTL. The TTL is the owner's bound on staleness.
  • Design for a hostile and unreliable network: limits on depth, retries and referrals, failover to another server, and a way to test with a fake clock and fake network.

Check your understanding

In a DNS reply, an answer record's name field starts with the two bytes c0 0c. What does that mean?

  1. The name is 12 characters long and begins with the letter C
  2. The record is a CNAME of length 12
  3. The name continues at offset 12 of this packet (usually where the question's name starts)
  4. The name is compressed with zlib
Top bits 11 mean "pointer", and the remaining 14 bits (0x00c = 12) give an offset from the start of the packet. Offset 12 is the first byte after the header, where the question's name begins, so the answer reuses it instead of spelling it out again.

You ask a root server for www.example.com. The reply has an empty answer section, 13 NS records for com in the authority section and matching A records in the additional section. What should your resolver do?

  1. Treat it as a referral: ask one of the addresses from the additional section the same question
  2. Report that the name does not exist
  3. Retry the same root server until it gives an answer
  4. Return the NS records as the answer to the user
The root doesn't know the host, but it knows who is responsible for com, and the glue gives their addresses. Asking those servers moves one step down the tree. NXDOMAIN would be signalled by response code 3, not by an empty answer with NS records.

Why does query_udp discard a reply whose ID doesn't match the query's?

  1. Because UDP guarantees that replies arrive in order
  2. Because the ID encodes the record type
  3. To make the reply smaller
  4. Because it may be a stray or forged packet; matching the random 16-bit ID makes it much harder for an attacker to inject a fake answer
UDP has no connection, so any host can send your socket a datagram. The unpredictable ID (together with the server's address, and in real resolvers a random source port) is the only thing tying a reply to your question.

Your cache stored an A record with TTL 300 at time 0. A client asks at time 120. What should your resolver do?

  1. Ask the authoritative server again, because the TTL is longer than 100 seconds
  2. Answer from the cache, reporting a TTL of 180
  3. Answer from the cache, reporting a TTL of 300
  4. Delete the entry, because half the TTL has passed
The record is valid until time 300, so at 120 it is still fresh. The resolver reports the remaining lifetime, 180 seconds, so that anyone downstream who caches it too will expire it at the same moment as everybody else.

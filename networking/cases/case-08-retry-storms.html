Retry Storms & Metastable Failures

Most outages end when you fix the cause. A few don't. The thing that went wrong is long gone, the hardware is healthy, the network is fine, and yet the system stays broken, held down by its own well-meaning attempts to recover. Engineers call this a metastable failure, and the usual culprit is the humble retry.

The pattern in one sentence

Load shedding and backoff: when a service is overloaded, the kindest thing the callers and the service can do is less work: callers retry sparingly and with randomised delays, and the service refuses excess work early so it can finish the work it accepts.

A ball in a bowl, and a ball on a hill

Picture a ball resting in a bowl. Poke it and it rolls back to the bottom: that is a stable system. Now picture a ball sitting in a small dip on the side of a hill. A gentle poke and it returns to the dip, but a hard enough poke sends it over the lip and into a different valley, where it stays even after you stop pushing. The name metastable is borrowed from physics for exactly this.

The research paper that named the pattern in computing, Bronson, Aghayev, Charapko and Zhu, "Metastable Failures in Distributed Systems" (HotOS 2021), puts it in words. A metastable failure occurs in open systems with an uncontrolled source of load, where a trigger causes the system to enter a bad state that persists even when the trigger is removed. In that state the goodput (the throughput of useful work) is unusably low, and a sustaining effect, often involving work amplification or decreased efficiency, keeps it there. The paper adds that leaving the bad state "requires a strong corrective push", such as rebooting or dramatically reducing the load.

That last point is the unsettling one. The paper notes that an outage like this is commonly blamed on the trigger, "but the true root cause is the sustaining effect". It also observes that the "vulnerable" state is not an overloaded state: a system can run for months or years in it, and many production systems choose to run there all the time because it is more efficient.

Retries: the most common sustaining loop

You met retries in chapter 16: when a request fails, send it again. They are essential, because most failures really are brief. But a retry is also extra load added at the worst possible moment. Bronson et al. give a small, concrete example, which I'll paraphrase.

The paper's retry example, simplified

A stateless web application queries a database. The database answers in under 100 ms while the load is below 300 queries per second (QPS); above that, latency becomes about ten times worse. The application sends one retry if the first query hasn't returned in 1 second. The system runs happily at 280 QPS. Then a 10-second network outage hits the link between application and database. When it is restored, all the requests and retries sent during the gap arrive in a surge, the database slows down, queries start timing out, and every timeout triggers a retry, so the database sees about 560 QPS. At that load it can never get fast enough to stop the timeouts, so the application has essentially no goodput. The paper says recovery requires reducing the load, or limiting retries to well below the level at which they overload the database.

Notice that the cause (a ten-second blip) is long over. What keeps the database drowning is the retries. The "feature" meant to improve reliability became the thing sustaining the outage.

The math of amplification

Retries multiply, especially across layers. Suppose a request passes down a chain: a front end calls service A, A calls service B, and B calls a database. Say each of those three callers makes up to 3 attempts (one original and two retries) before giving up.

Spelled out: the front end makes 3 attempts at A; each attempt that reaches A makes 3 attempts at B (3 × 3 = 9); each of those makes 3 attempts at the database (9 × 3 = 27). In general, with n retrying layers each making a attempts, the worst-case load on the bottom layer is an. (With "3 retries" meaning 4 attempts per layer, three layers would give 43 = 64.) This is a worst case, reached only when the bottom keeps failing, which is exactly when it hurts most. Bronson et al. report one geo-distributed system whose added retries and failover paths led to a worst-case work amplification of over 100x.

The cache version: the empty bowl

Retries are not the only sustaining loop. Another from the paper is the look-aside cache (the pattern behind memcached in front of a database, chapter 13). With a 90% hit rate, only one request in ten reaches the database, so the database can sit behind an application receiving ten times what it could handle alone. The paper's example: a database that tops out around 300 QPS safely supports 3,000 QPS with the cache. Then the cache is lost (a restart, say). Suddenly all 3,000 QPS hit the database; it slows; the application's timeouts mark queries as failed, so the application doesn't fill the cache with the results; the cache stays empty; the database stays slow. The paper's summary: "losing a cache with a 90% hit-rate causes a 10× query amplification".

This is a cache stampede (also called a thundering herd): many requests miss at the same moment and all go to the source of truth. Common defences are to let just one request per key rebuild the entry while others wait or serve slightly stale data ("request coalescing"), to warm caches before putting them back in service, to add a little random variation to expiry times so entries don't all expire together, and to shed load while the cache refills. Facebook's gradual recovery in case study 6, where services were brought back in stages partly because of cold caches, is the same idea applied to recovery.

Analogy: a doorway after the fire alarm

A crowded hall empties through one door. Orderly, people flow out. But if everyone panics and pushes at once, the door jams and nobody gets through, even though the door itself works fine. The jam is self-sustaining: pushing makes the jam worse. What helps is the opposite of pushing: stewards letting people through in small groups.

Where it breaks down: people can see the jam and choose to hold back. Software clients mostly can't see the server's load, which is why we have to build the holding-back into the clients and the server.

Watch it happen: a toy model

Below is a deliberately simple model so you can see the shape of the problem. Time moves in ticks. Each tick, new requests arrive. The server has a capacity per tick. During a "trigger" the capacity temporarily drops. Any request that isn't served in its tick is retried in the next tick, up to three retries (depending on the policy you pick).

One assumption makes it a metastable model rather than a simple queue: when the server is offered more than its capacity, it wastes effort (timeouts, queues, contention), so its useful output falls to half its capacity. That is the "decreased efficiency" in the paper's definition. These numbers are made up for illustration; the real ones depend on the system. Choose a policy, set a trigger length, and press Run. Then try the others.

What to notice:

  • No retries: goodput dips during the trigger, then snaps back the moment it ends. The system is stable.
  • Retries, no limits: long after the trigger ends, the offered load stays far above capacity. Failed requests are retried, retries fail because the server is overloaded, and so on. The server is wasting its effort, so goodput stays low. This is the metastable state: the trigger is gone, but the loop remains. A short trigger may still be enough, so shorten it and see; the bigger the normal load, the less margin you have.
  • A retry budget: by capping retries to a small fraction of normal traffic, the extra load can't build up. The system recovers soon after the trigger, unless normal load plus the budget already exceeds capacity (try a normal load of 95).
  • Server-side shedding: the server refuses what it can't serve cheaply, so it keeps finishing work at full capacity. The backlog of retries drains and the system recovers, slowly but surely.

The real world is messier (queues, many clients, variable latencies), but the structure is the same one the paper describes: the system's own efficiency loss under load, plus work amplification from retries, keeps it in the bad state.

The toolkit: how real systems break the loop

1. Timeouts and deadlines

Every call needs a timeout (chapter 16), and ideally a deadline passed along the whole chain: "the user gave up in 2 seconds, so don't bother doing work that will finish in 5". Work for callers who have already left is pure waste, and it is a classic sustaining loop.

2. Backoff with jitter

Wait longer after each failure (exponential backoff), and add randomness (jitter) so that clients don't retry in synchronised waves. Marc Brooker's AWS Architecture Blog post "Exponential Backoff And Jitter" (first published in 2015) measured this. His setting is clients contending for a resource with optimistic concurrency control, not exactly a web outage, but the lesson carries. He compares variants: "Full Jitter" sleeps a random time up to the capped exponential backoff value; "Equal Jitter" keeps half of the backoff and randomises the other half; "Decorrelated Jitter" varies the maximum based on the previous random value. His finding is that all the jittered approaches substantially reduce the work clients and servers do compared with backoff alone, and that plain exponential backoff without jitter performs worst. Chapter 16's simulator and the backoff milestone of Lab 5 are the hands-on version.

# "Full jitter": sleep a random time between 0 and the capped exponential backoff
>>> import random
>>> base, cap = 0.1, 10.0
>>> [round(random.uniform(0, min(cap, base * 2**attempt)), 2) for attempt in range(6)]
[0.07, 0.03, 0.31, 0.12, 1.27, 2.9]   # your numbers differ; the ceilings are 0.1, 0.2, 0.4, 0.8, 1.6, 3.2

3. Retry budgets and single-layer retries

Limit retries to a fraction of normal traffic (say 10%) so that retrying can never more than slightly raise the load. Retry at one layer, usually the one closest to the user, and have the layers below fail fast. Retry only what is safe to retry (idempotent requests, chapter 16) and only on errors that might go away.

4. Load shedding and admission control

Load shedding means a server refuses some work on purpose, quickly and cheaply, so it can complete the rest. Admission control is the policy for deciding which: limit the number of requests in flight, drop the oldest in the queue (their callers have probably given up), serve higher-priority traffic first, or reject early with a clear "try later" (HTTP 503 or 429, optionally with Retry-After). The key is that rejecting must be much cheaper than serving; a rejection that costs as much as a success sheds nothing.

Prioritisation appears in the Bronson et al. paper too. In their retry example, giving retried queries a lower priority means fresh user queries succeed first, which breaks the loop. They also caution that shedding can itself disrupt users, and that priority systems manage only some of the resources in a system. These are trade-offs, not free wins.

5. Circuit breakers

A circuit breaker stops calling a dependency that has been failing (the "open" state) and fails immediately for a while, then lets a trial request through to test recovery ("half-open"). It protects the dependency from your retries and protects your own threads from waiting on something that is down. Chapter 21 returns to this pattern.

6. Recover gradually, and design the vulnerable state out

If a metastable failure has happened, recovery typically means cutting the load below the threshold (shed, throttle, or pause clients), then ramping back up. The longer-term fix is to find the sustaining loop and break it: cap retries, make cold caches survivable, and test what happens when a dependency disappears and returns.

Common misconception: "add more servers and it will recover"

Sometimes capacity helps, but a metastable system can be stuck at an offered load several times its capacity. Adding 20% more servers to a system stuck at 230% load may change nothing, and new servers start with cold caches and cold connections, which can add to the stampede. Reducing the load (retries, traffic) is often faster than adding supply.

How common is this?

A follow-up paper, Huang et al., "Metastable Failures in the Wild" (OSDI 2022), studied publicly available incident reports. The authors report an in-depth study of 22 metastable failures from 11 organisations, and found that at least 4 of the 15 major outages at Amazon Web Services in the past decade (as of their writing) were caused by metastable failures. They also extended the Bronson model with two trigger types and two amplification-mechanism types. In other words, this is not an exotic corner case. It is a recurring way that large systems fail.

You have already seen it once. In case study 6, with Facebook's DNS servers unreachable, apps and resolvers retried again and again, and Cloudflare reported public resolvers handling roughly 30 times their usual query volume. That was load on other systems caused by one system's failure, retries as an amplifier.

Distributed systems connection

Metastability is why "it worked in testing" isn't enough in distributed systems: the bad states only appear at scale, under correlated load, where feedback loops get strong. It ties together much of this guide: partial failure and timeouts (chapters 15 and 16), queueing and the cost of the last 10% of capacity (chapter 13), caches (chapters 13 and 14), and gradual recovery (case study 6). Whenever you add a retry, a failover or a cache, ask the question the paper teaches: if this works too well, or this fails all at once, what load does it send to its neighbour?

Key takeaways

  • A metastable failure is a bad state that persists after its trigger is gone, kept alive by a sustaining feedback loop such as retries or cache misses.
  • Retries multiply across layers: 3 attempts at each of 3 layers is 3 × 3 × 3 = 27 attempts at the bottom.
  • A cache that hides most load from a database also hides the database's real capacity; losing the cache can cause a stampede that keeps it empty.
  • Use deadlines, exponential backoff with jitter, retry budgets, and retries at one layer.
  • Servers should shed excess load cheaply and early; circuit breakers stop callers from piling on.
  • Recovery means cutting the load below the threshold and ramping back up gradually, not just adding servers.

Check your understanding

What makes a failure "metastable" rather than an ordinary overload?

  1. It only happens in the cloud
  2. It is always caused by hardware failure
  3. It persists after the trigger is removed because a feedback loop sustains it
  4. It resolves by itself within a few seconds
The defining feature is that the system stays in a bad state after the trigger ends, held there by a sustaining effect such as retries or an empty cache. Failures that resolve when the trigger is removed are not metastable, and getting out usually takes a corrective push such as cutting load.

A request passes through 4 layers, and each layer makes up to 3 attempts. In the worst case, how many attempts reach the bottom layer for one user request?

  1. 12
  2. 81
  3. 27
  4. 7
Attempts multiply per layer: 3 × 3 × 3 × 3 = 34 = 81 (and 33 = 27 for three layers). That is why retrying at every layer is dangerous, and why we retry at one layer and use budgets.

Why add jitter to exponential backoff?

  1. So each client waits for exactly the same time
  2. To make retries happen faster
  3. To make the delays easier to read in logs
  4. So clients that failed together don't all retry together in synchronised waves
Without randomness, clients that failed at the same instant back off by the same amounts and return at the same instant. Jitter spreads their retries over time, which cuts the peak load and the total wasted work.

A server is overloaded. Which response best helps it recover?

  1. Reject excess requests quickly and cheaply, so it can finish the work it accepted
  2. Accept every request and queue them all, to be polite
  3. Ask clients to retry immediately and as often as they like
  4. Restart the server every minute
Load shedding lets the server spend its effort on requests that can still succeed. Accepting everything builds long queues of work whose callers have given up; immediate retries add load; restarts empty caches and drop in-progress work.

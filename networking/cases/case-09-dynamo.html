Dynamo: The Cart That Always Says Yes

In 2007, a team at Amazon described a storage system built around one stubborn promise: a customer must always be able to add an item to their shopping cart, even while disks fail, networks flap and whole data centers go dark. To keep that promise, Dynamo gave up the thing most databases treat as sacred, a single agreed version of the truth.

The pattern in one sentence

Leaderless replication: let any of several replicas accept a write, so there is no leader to lose, and clean up the disagreements afterwards with version tracking, background repair and, when necessary, the application itself.

This case study is about the system described in the paper Dynamo: Amazon's Highly Available Key-value Store (DeCandia and colleagues, SOSP 2007). It leans on ideas from chapters 17 (vector clocks), 18 (quorums, leaderless replication) and 19 (consistent hashing and virtual nodes).

Dynamo is not DynamoDB

The 2007 Dynamo system and today's Amazon DynamoDB cloud service are different systems. Amazon's own 2022 paper on DynamoDB (USENIX ATC) calls Dynamo DynamoDB's "predecessor" and says its design "was motivated by" experience with it. Dynamo was a single-tenant system that teams ran themselves. Each DynamoDB partition, by contrast, is a replication group that "uses Multi-Paxos for leader election and consensus", and only the leader serves writes and strongly consistent reads. So DynamoDB's partitions are leader-based, not leaderless. Everything below describes the 2007 paper, not the service you can rent today.

The requirement: a cart that never refuses

The paper starts from a business fact: at Amazon's scale, small and large components "fail continuously", and even a short outage has real financial cost. Its shopping-cart example is blunt: customers should be able to view and add items "even if disks are failing, network routes are flapping, or data centers are being destroyed by tornados". So the cart service needs a data store that is "always writeable".

Chapter 18's CAP discussion explains what that choice costs. When replicas can't talk to each other, a store can refuse writes to stay consistent, or accept them and reconcile later. Dynamo picks the second. The paper says plainly that it "sacrifices consistency under certain failure scenarios", and it argues that the cart tolerates this well: an "Add to Cart" must never be forgotten or rejected, and a change made to an older copy of the cart is still meaningful and should be preserved.

The cast

The ring
Keys are hashed onto a circle, and each node owns the arc behind it (chapter 19). Dynamo gives every machine many positions, which the paper calls "tokens" and describes as virtual nodes, so load spreads evenly and a failed node's work is "evenly dispersed" across the others.
Preference list
The list of nodes responsible for storing a particular key. The first node found walking clockwise coordinates; the key is also stored on the next N−1 nodes. The list holds more than N nodes so there are spares when some are down, and positions are skipped so that it names only distinct physical machines (a machine can own several nearby tokens).
Coordinator
The node that handles a particular read or write. Any node can receive a request; it forwards the request if it isn't one of the key's top N.
(N, R, W)
N replicas per key; a read needs R responses and a write needs W (chapter 18). The paper notes that R and W are usually set below N to get better latency, because the operation otherwise waits for the slowest replica. It reports that the common configuration across several Dynamo instances was (3, 2, 2).
Context (vector clock)
Every stored version carries a vector clock, a list of (node, counter) pairs. A read returns it as opaque "context", and a write must hand it back so Dynamo knows which version is being updated.

Watch a write survive a dead node

This step-through follows the paper's own example of a sloppy quorum with hinted handoff. The ring has six machines, N = 3 and W = 2 (the paper's common setting). The letters and which node coordinates are my illustration; the mechanism is the paper's.

Step through

A cart write while node A is down

  1. Normal day. The client writes a cart. Key k hashes to a spot whose first clockwise node is A. A is the coordinator: it stores the new version, stamps it with a vector clock, and sends it to the next nodes in the preference list, B and C.
  2. A goes down. The paper's reasoning is that outages are "often transient", so a down node does not trigger rebalancing. The ring keeps its shape. Membership changes are made explicitly, by an administrator.
  3. The write arrives anyway. A strict quorum would need A and would fail. Dynamo instead uses a sloppy quorum: reads and writes go to "the first N healthy nodes from the preference list", which may not be the first N on the ring. A's copy is sent to D. D stores it in a separate local database, with metadata naming A as the intended owner. (The paper doesn't say which node coordinates when the top one is down, so I've picked B for the picture.)
  4. The client gets "OK". The coordinator counts itself plus acknowledgements. Once W = 2 nodes have the write, it is a success. The customer's item is in the cart, and A being dead never reached them.
  5. A comes back: hinted handoff. D periodically scans its hinted copies. When it detects that A has recovered, it tries to deliver the copy, and once the transfer succeeds it "may delete the object from its local store" without lowering the total number of replicas.
  6. Settled, with a backstop. Hinted handoff "works best if the system membership churn is low and node failures are transient". If D dies before it can hand back, the replicas are repaired by the background anti-entropy process, described below.

Analogy: the neighbour who holds your parcel

You're out, so the courier leaves your parcel with a neighbour, and the neighbour pins a note to their door: "parcel for flat 4". When you come home, they hand it over and the note comes down. Nobody had to find a new address for you, and the parcel was never lost.

Where it breaks down: a neighbour who holds your parcel isn't a member of your "household" for any vote. In Dynamo, D counts toward the write quorum even though it isn't one of the key's usual replicas. That is exactly why a sloppy quorum no longer guarantees that a read will see the latest write (see below).

Why it is called a "sloppy" quorum

Chapter 18 showed the overlap rule: with R + W > N, every read set shares at least one replica with every write set. The paper notes that setting R and W this way "yields a quorum-like system". With (3, 2, 2), 2 + 2 > 3, so in a healthy cluster a read overlaps the latest write.

But the overlap argument assumes the writes went to the same N replicas the readers will ask. With hinted handoff, a write might sit on B, C and D while a read, a moment later, reaches A, B or C after A recovers but before D hands anything back. The guarantee is no longer a hard one. Dynamo accepts this on purpose: the paper says that with hinted handoff, reads and writes are "not failed due to temporary node or network failures". At the extreme, an application that wants the highest availability can set W to 1, and then a write is rejected only if every node in the system is unavailable. The paper adds that in practice most production services set a higher W for durability.

So the honest summary is: Dynamo's (N, R, W) dials trade availability, latency and durability against each other, and what you get is eventual consistency, not the single up-to-date copy you'd get from a leader.

When two writes collide: vector clocks and the client's job

With no leader, two clients can update the same cart through different nodes, and neither knows about the other. Dynamo treats every update as "a new and immutable version", so several versions of one cart can exist at once. It tracks their relationships with vector clocks, exactly as in chapter 17: if every counter on one clock is less than or equal to the matching counter on another, the first is an ancestor and can be forgotten. Otherwise the two are in conflict.

When a read finds branches like D3 and D4, Dynamo returns all of them, together with a context that summarises their clocks. The client merges them and writes the result back using that context. The paper calls this semantic reconciliation and gives "merging different versions of a customer's shopping cart" as the typical collapse operation. The data store doesn't know what a cart is, so it can't merge for you. That is a real trade-off: a leader-based store would have ordered the two writes for you; Dynamo hands you the problem.

Dynamo supports other strategies per application too. The paper lists simple "last write wins" by timestamp (the lossy choice chapter 17 warned about) and application-specific business logic, with the cart as the business-logic case.

The anomaly: deleted items can come back

The paper is candid that using a merge-style reconciliation means "an 'add to cart' operation is never lost. However, deleted items can resurface." Both adding and removing an item are just puts.

Here is an illustration of why (my example, not the paper's). The cart holds {book, pen}. One partition removes the pen, giving {book}. Another, unaware, adds a mug, giving {book, pen, mug}. A merge that takes the union returns {book, pen, mug}: the pen is back. The merge can't tell "the pen was deleted" from "the pen was never seen by that branch". Amazon decided that a resurrected item is a smaller sin than a lost one. Chapter 18's CRDTs are a more careful answer to the same problem, using markers for removals.

How often does this actually happen? The paper measured a 24-hour period of the live shopping-cart service: 99.94% of requests saw exactly one version, and only a tiny fraction saw two, three or four. The paper's conclusion is that divergent versions "are created rarely". The paper adds that concurrent writes were usually triggered by automated client programs ("busy robots") rather than by humans.

Cleaning up in the background

Hinted handoff covers short outages. For anything longer, replicas can drift apart, and reading every key on two machines to compare them would be hopelessly expensive. Dynamo's answer is anti-entropy using Merkle trees: a hash tree whose leaves are hashes of individual keys' values, with each parent holding the hash of its children.

  1. Two replicas that share a key range compare the root hash of their trees for that range.
  2. If the roots match, everything below matches, and nothing needs copying.
  3. If not, they compare child hashes, then grandchildren, walking down only the branches that differ, until they reach the exact keys that are out of sync.

A branch can be checked without downloading the whole tree or data set, so very little is transferred when replicas mostly agree. Each Dynamo node keeps one tree per key range it hosts. The paper names the cost: when a node joins or leaves, many key ranges change and the trees must be recomputed, a problem it addresses with a refined partitioning scheme.

Knowing who's in the ring: gossip

With no leader and no central directory, nodes learn about each other by gossip. Each node contacts a random peer once a second, and the two reconcile their records of membership changes, which an administrator initiates explicitly. The same exchange carries the token ranges each node owns, so every node knows who owns what and can forward a request directly. To prevent two halves of the ring from forming and never meeting, some nodes act as seeds: nodes known to everyone, found through static configuration or a configuration service, which every node eventually reconciles with.

What the design assumes, and what it costs

What it buys

Writes keep succeeding through node and network failures. Capacity grows by adding nodes, and the ring moves only neighbouring data. Latency is set by the W-th or R-th fastest replica, not the slowest.

What it costs

No single order of writes. Applications must tolerate stale reads and merge conflicting versions. Vector clocks can grow, so the paper truncates them (it suggests dropping the oldest pair beyond a threshold such as 10), at the price of less exact conflict detection. It reports this "has not surfaced in production".

The paper also states its operating assumptions: it "does not focus on the problem of data integrity and security" and is "built for a trusted environment", and it targets services that need "always writeable" semantics, not full relational features. It is a pattern for a specific class of problem, not a general replacement for databases with strong consistency. For anything where two concurrent writes must not both succeed, such as a bank balance or a stock count, you want chapter 20's consensus instead.

Try it yourself

Build a preference list in 20 lines

This script puts five machines on a ring with four virtual nodes each, then finds each key's preference list while skipping repeated machines, as the paper describes. It needs only Python 3. (The standard hashlib hash is used so the output is the same on every run.)

$ cat pl.py
import hashlib, bisect

def h(s):
    return int(hashlib.md5(s.encode()).hexdigest(), 16) % 10_000

nodes = ["A", "B", "C", "D", "E"]
ring = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(4))

def preference_list(key, n=3):
    start = bisect.bisect(ring, (h(key), ""))
    chosen = []
    for i in range(len(ring)):
        node = ring[(start + i) % len(ring)][1]
        if node not in chosen:       # skip repeats: need distinct machines
            chosen.append(node)
        if len(chosen) == n:
            break
    return chosen

for key in ["cart:alice", "cart:bob", "cart:carol"]:
    print(key, "->", preference_list(key))
$ python3 pl.py
cart:alice -> ['C', 'E', 'B']
cart:bob -> ['A', 'D', 'B']
cart:carol -> ['C', 'E', 'B']

Now experiment. Change range(4) to range(1) and see how the lists change. Then pretend a node is down: remove "C" from nodes and note that only the keys C used to own change their first choice. Finally, picture a write to cart:alice while C is down: the first three healthy nodes now hold it, one with a hint. That is a sloppy quorum.

Distributed systems connection

Dynamo is chapter 18's "leaderless" box made real, and it uses almost every idea from Part 6 at once: partitioning with virtual nodes (19), quorums and eventual consistency (18), and vector clocks (17). What it deliberately avoids is chapter 20's consensus: there is no agreed order and no leader election, which is why it never has to block. Cassandra and Riak, mentioned in chapter 18, are "Dynamo-style" databases that borrow ideas from this design (the details differ, and I have not checked them here). Case study 10 looks at the opposite end of the spectrum, where the whole point is a single order of events.

Key takeaways

  • The shopping cart's requirement, to be "always writeable", drove every design decision. Availability was chosen over consistency, on purpose.
  • Consistent hashing with virtual nodes spreads keys and load; each key's preference list names the nodes that store it.
  • A sloppy quorum plus hinted handoff lets writes succeed by using the first N healthy nodes, and returns the copy when the owner recovers.
  • The common configuration reported was (N, R, W) = (3, 2, 2); a sloppy quorum weakens the usual read-sees-latest-write guarantee.
  • Vector clocks detect concurrent versions; the application merges them, and deleted items can resurface.
  • Merkle trees find differences between replicas cheaply; gossip spreads membership with no central coordinator.
  • The 2007 Dynamo is a different system from the DynamoDB service.

Check your understanding

With N = 3, W = 2 and node A (a key's usual coordinator) down, how does a Dynamo write still succeed?

  1. The write waits in a queue until A recovers
  2. The ring is rebalanced immediately to remove A
  3. It goes to the first three healthy nodes in the preference list, one holding a hint, and succeeds once two have stored it
  4. It is rejected, and the client must retry
That is a sloppy quorum with hinted handoff. Dynamo treats most outages as temporary, so it doesn't rebalance; it substitutes the next healthy node and returns the copy to A later.

Why does a sloppy quorum weaken the "R + W > N means reads see the latest write" guarantee?

  1. The write may be stored on a stand-in node, so a read set may miss the nodes that hold it
  2. R and W are ignored during failures
  3. Vector clocks are disabled when a node is down
  4. Hints are always lost
The overlap argument assumes reads and writes use the same N replicas. After hinted handoff, a write may live on a different node than a later read asks, until the hint is delivered.

Two versions of a cart have vector clocks [(Sx,2),(Sy,1)] and [(Sx,2),(Sz,1)]. What does Dynamo do?

  1. Keeps the one whose node name sorts first
  2. Keeps the one with the later wall-clock time
  3. Deletes both and asks the customer to start again
  4. Recognises they are concurrent, keeps both, and returns both to the client to merge
Neither clock dominates the other, so neither version is an ancestor of the other. Dynamo preserves both and leaves semantic reconciliation to the application.

What is the main advantage of using Merkle trees for anti-entropy?

  1. They make writes faster
  2. Replicas can find exactly which keys differ by comparing hashes, transferring very little data when they mostly agree
  3. They guarantee that no data is ever lost
  4. They remove the need for vector clocks
Matching root hashes mean the whole range is identical. Mismatches are narrowed branch by branch, so only the keys that differ need to be exchanged.

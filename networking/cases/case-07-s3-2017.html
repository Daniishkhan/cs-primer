Small Mistake, Big Blast Radius: S3, 2017

On the morning of 28 February 2017, a large part of the Internet stumbled. Websites lost their images, apps stopped loading, and even the page that was supposed to tell customers what was wrong could not update itself. The cause, according to Amazon's own account, was one input typed incorrectly into a routine command. The lesson is not about the typo. It is about why one typo could reach so far.

The pattern in one sentence

Blast radius and cells: assume that someone, someday, will make a mistake, and build the system so a mistake can only damage a small, independent slice of it, and so that slice can be restored quickly.

The cast

Amazon S3 (Simple Storage Service) is object storage: you PUT a file under a name, and later GET it back. Huge numbers of websites and other services keep their files in it. Amazon's post-event summary describes two internal subsystems that matter here:

The index subsystem
Manages the metadata and location information of all S3 objects in the region. Per the summary, every GET, LIST, PUT and DELETE request needs it.
The placement subsystem
Manages the allocation of new storage and is used during PUT requests. It depends on the index subsystem.
A billing subsystem
Where the story starts: the S3 team was investigating why the billing system was running slower than expected.
The Service Health Dashboard (SHD)
The AWS status page customers check to learn whether a service is having problems.

The region involved was US-EAST-1 (Northern Virginia). Remember from chapter 15 that a region is already a unit of isolation: an outage in one region is not supposed to hurt another. What follows is what happens inside a region when that isolation is too coarse.

What happened, step by step

The times below are the Pacific times given in AWS's summary, and I only state what that summary states.

Step through

One command, one region

  1. A normal morning. The index and placement subsystems run on a pool of servers, and a great deal of software, inside and outside Amazon, depends on S3 working.
  2. The command. At 9:37 AM PST, an authorized team member, debugging a billing-system slowdown, ran a command from an established playbook that was intended to remove a small number of servers. One input was entered incorrectly, and a larger set of servers was removed than intended. Among them were servers supporting the index and placement subsystems.
  3. Too little capacity left. Removing a significant portion of that capacity meant both subsystems required a full restart.
  4. The restart is slow. AWS wrote that it had not completely restarted these subsystems in its larger regions "for many years". In that time S3 had grown enormously, and the restart plus the safety checks on metadata took longer than expected. Until the index was back, S3 could not serve GET, LIST, PUT or DELETE in the region.
  5. The status page was caught too. The console used to update the Service Health Dashboard itself depended on S3. Until 11:37 AM PST, AWS could not update individual services' status on it, and used its Twitter feed and banner text on the dashboard to communicate.
  6. Recovery, in stages. By 12:26 PM the index subsystem could begin serving GET, LIST and DELETE requests, and by 1:18 PM it was functioning normally. Placement, which needs the index, finished recovering at 1:54 PM, after which S3 was operating normally.

Services built on S3 felt it too. AWS's summary lists the S3 console, EC2 new instance launches, and other services in the region that relied on S3, such as EBS volumes needing snapshot data and Lambda. One mistake in one subsystem became an outage for many.

Common misconception: "an engineer broke the Internet"

The input mistake was the trigger. But Amazon's own summary is about the design: a tool that let one command remove that much capacity that fast, no floor on minimum capacity, subsystems that had not been restarted at their current scale for years, and a status page that depended on the thing it reported on. Mature engineering cultures ask "how did the system allow this?" rather than "who typed it?". This blameless framing is the default in post-incident reviews.

The fixes AWS announced

AWS described changes in four categories:

Remove capacity more slowly

The tool was modified so that it removes capacity more slowly, giving a person or a monitor time to notice something is wrong before it is too late.

A floor on capacity

AWS added safeguards to stop a subsystem from being reduced below its minimum required capacity. It also said it would audit other operational tools for similar safety checks.

Smaller cells

AWS said one of its key techniques is breaking services into small partitions "which we call cells", and that S3 had already refactored parts of the service into cells to reduce blast radius and improve recovery. The S3 team reprioritised further partitioning of the index subsystem.

A dashboard that survives

The Service Health Dashboard administration console was changed to run across multiple AWS regions, so it no longer depends on a single region's S3.

The pattern: blast radius and cells

The blast radius of a failure is how much of the system it can hurt. In chapter 15 you learned that availability multiplies across dependencies in series; the same arithmetic says that whenever everything shares one component, that component's failures reach everyone. The S3 region's index was one large shared thing: it was big, so a restart was slow, and everything in the region hung off it.

A cell-based architecture is a way to shrink that. AWS's Well-Architected guidance on the topic defines it like this: use multiple isolated instances of a workload, each instance called a cell; each cell is independent, does not share state with other cells, and handles a subset of the overall requests. A thin cell router sends each request to the right cell using a partition key such as a customer ID. The guidance gives the headline arithmetic: with 10 cells serving 100 requests, a failure in one cell leaves 90% of requests unaffected. It also says cells help contain failures that are otherwise hard to contain, such as bad deployments and "poison pill" requests.

Notice what cells buy you, in the S3 story's own terms:

  • Smaller blast radius. A bad command or bug hits one cell, not the region.
  • Faster recovery. A cell is a fraction of the size, so a cold restart (the step that surprised AWS) is a fraction of the work. This is a general argument, and it matches AWS's stated reason for partitioning: to limit impact and speed recovery.
  • Safer changes. You can roll a deploy or a capacity change out one cell at a time and watch for trouble before touching the next. The guidance describes applying changes "compartment by compartment".

Analogy: the ship's bulkheads

AWS's own guidance uses this picture: a ship's hull is divided into watertight compartments, so one breach floods one section rather than sinking the ship. A cell is a compartment.

Where it breaks down: a ship's compartments share nothing but the hull. Software cells usually share something: a control plane that provisions them, a router that directs traffic, a deployment tool, a DNS name. If any of those fails, every cell is affected. That is why the guidance calls for the router to be minimal, and why case 6 matters so much.

Connecting it to other stories in this guide

  • Control-plane dependencies. The status dashboard depending on S3 is the same shape as Facebook's repair tools depending on the network that had just failed (case study 6). The system you use to observe and repair must not rely on the thing being observed.
  • Correlated failure. Chapter 15 warned that redundancy only helps when failures are independent. Many servers sharing one index behave like one server. Cells are a way to make failures independent on purpose.
  • Cold start and thundering herds. A big subsystem coming back from empty must rebuild state and then face every client's pent-up retries at once. Chapter 16's backoff and case study 8 are what clients need to do to help, and gradual recovery is what the service needs to do.
  • Operational tools are production code. The command had no floor and no speed limit. Safe tooling (rate limits, minimums, dry runs, confirmations proportional to impact) is part of the architecture.

Trade-offs

Benefits

Failures and bad deploys stay local. Smaller things restart faster. Capacity can be tested at a known cell size, which makes behaviour more predictable.

Costs

You need a router and a way to place and move customers between cells. Cross-cell operations (global queries, "list everything") are awkward. Spare capacity is spread out, and a very hot customer may not fit in one cell.

AWS's guidance also notes that adopting cells does not require multiplying your infrastructure. An application with 30 hosts could have the same 30 hosts divided between cells, plus a cell router. The cost is mostly design and operations, not hardware.

Try it yourself

Look at the shape of S3 from the outside

These commands only read public information. Your output will differ.

$ dig +short s3.us-east-1.amazonaws.com    # the regional S3 endpoint: many addresses, rotating
52.216.x.x
52.217.x.x
...
$ dig +short s3.eu-west-1.amazonaws.com    # a different region: a different, independent S3
52.218.x.x
...

Each region has its own endpoint because each region is built to be independent. That is the same blast-radius idea at the largest scale. Then open the public status page, health.aws.amazon.com/health/status, and look at how it is organised by service and region. Ask yourself: if the thing I'm reading depended on the thing it reports, what would I see during an outage?

A thought exercise for your own projects: pick one command you could run that removes something (a server, a database row, a DNS record). What stops you from removing too much? Is there a minimum? A rate limit? A dry-run?

Distributed systems connection

Cells are partitioning (chapter 19) applied to failure domains rather than to data size: choose a partition key, route by it, and let each partition stand alone. They also combine with replication (chapter 18): replicate within a cell for durability, and use cells so that the failure of a whole replica group is still only a fraction of the system. Whenever you design a shared component, ask two questions: how much would die if this broke? and how long would a cold restart take at today's size?

Key takeaways

  • A command meant to remove a small number of servers removed more than intended, taking out capacity behind S3's index and placement subsystems in US-EAST-1.
  • Both subsystems needed a full restart, which took longer than expected because S3 had grown and had not been fully restarted in its larger regions for many years.
  • The status dashboard's admin console depended on S3, so AWS could not update service status until 11:37 AM PST.
  • AWS slowed capacity removal, added minimum-capacity safeguards, moved the dashboard console across regions, and committed to partitioning into cells.
  • Cells are independent instances behind a thin router: a failure or bad deploy affects one cell, and each cell recovers faster because it is smaller.
  • The tools that observe and repair a system must not depend on that system.

Check your understanding

According to AWS's summary, what directly forced the index and placement subsystems to fully restart?

  1. A hardware fire in a data center
  2. A command removed more server capacity than intended, leaving too little to keep running
  3. A malicious attack on the billing system
  4. A network cable was cut between regions
One input to a routine command was entered incorrectly, so a larger set of servers than intended was removed. The loss of that capacity meant both subsystems needed a full restart. Nothing physical failed.

Why did recovery take longer than AWS expected?

  1. The engineers did not know the playbook
  2. The restart was blocked until customers stopped sending requests
  3. The index depended on the placement subsystem
  4. The subsystems had not been fully restarted in the larger regions for many years, and S3 had grown a lot in that time
The restart and the integrity checks on metadata took longer than expected because the system had grown. Also note that "the index depended on placement" has the dependency backwards: placement depends on the index. Cells make this less likely by keeping each restartable unit small.

The AWS Service Health Dashboard could not be updated during the event. Which pattern from earlier does this match?

  1. A control-plane dependency: the tool for reporting and repair depended on the failed service
  2. A cache stampede
  3. NAT traversal
  4. Anycast routing
Its administration console depended on S3, so it failed along with the thing it was meant to report on. It echoes Facebook's 2021 outage, where repair tools shared fate with the network.

A workload uses 10 equal cells and a bad deploy reaches only one of them. Roughly what share of requests is unaffected?

  1. 0%
  2. 10%
  3. 90%
  4. 100%
If every cell handles an equal share, one failed cell affects about a tenth of requests and the other nine tenths carry on. This is the arithmetic AWS's cell-based guidance uses. A shared router or control plane that fails would still affect everyone, which is why they must be kept minimal.

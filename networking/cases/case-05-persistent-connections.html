Millions of Open Connections

When a friend sends you a chat message, it shows up on your screen within a fraction of a second, even though you never asked for it. That only works because your phone or laptop is holding a connection open to a server all day long. Multiply that by millions of people and you get one of the most interesting problems in real-time systems: how do you find one particular person's connection among millions, and what do you do when it breaks?

The pattern in one sentence

Connection gateways and fan-out: keep the expensive, stateful part (the open connections) in a thin tier of gateway servers, keep the business logic in stateless services behind them, and use a routing layer to get each message to the one gateway that holds the recipient's connection.

Why not just ask again and again?

HTTP, as we saw in chapter 10, is a question-and-answer protocol: the client asks, the server answers, and the server can never speak first. To get new messages with plain HTTP you have to poll: ask "anything new?" every few seconds. That has two problems.

  • Latency. If you poll every 5 seconds, a message waits 2.5 seconds on average before you see it. Poll every 100 ms and you've fixed that, but...
  • Waste. Almost every poll answers "nothing new", yet each one costs a request, headers, and server work. A million idle users polling ten times a second is ten million requests per second to say "no".

The fix, which you met in chapter 12 under "WebSockets and other ways to push", is to open one long-lived connection and leave it open. A WebSocket starts as an HTTP request that asks to "upgrade"; after that the same TCP connection (chapter 8) becomes a two-way channel where either side can send a message at any moment. An idle connection costs almost nothing on the wire, and the server can push a message the instant it exists.

Analogy: the phone call versus the mailbox

Polling is walking to the mailbox every minute to check for letters. A persistent connection is leaving a phone line open: nobody is talking most of the time, but the moment someone speaks, you hear it. The price is that the phone company must keep your line reserved the whole time.

Where it breaks down: a phone call is a physical circuit. A TCP connection is just state in two machines' memory, and it can quietly die (a laptop lid closes, a train enters a tunnel) without either side being told.

Here is the price. Every open connection is memory on a server, an entry in a table, and a thing that must be tracked, kept alive, and eventually replaced. One server can hold a lot of them (see the Go deeper box) but not millions, so a real system needs many servers holding connections, and that raises the central question of this case study: if Bob's connection lives on server 17, how does a message from Alice reach server 17?

The cast: gateways, services, and a directory

Gateway tier
A fleet of servers whose main job is to hold client connections: accept WebSockets, authenticate them, send and receive frames, and track which user each connection belongs to. They hold state (the live sockets). Different companies call them different things; Discord's engineers describe a "session" process per connection, and Slack calls its tier "Gateway Servers".
Stateless services
The business logic: store the message, check permissions, work out who should receive it. Any instance can handle any request, so they are easy to scale and replace (chapter 14).
Session registry or pub/sub
The "directory" that answers "which gateway holds Bob right now?", or the equivalent: gateways subscribe to topics for the users or channels they serve, and services publish to the topic.

The split matters because the two halves scale and fail differently. Connections are long-lived and sticky: you can't move one without dropping it. Business logic is short-lived and interchangeable. Mixing them means every deploy of your logic drops everyone's connection. Separating them lets you ship new logic constantly while the gateway tier changes rarely and carefully.

Following one message

Step through

Alice messages Bob

  1. Two long-lived connections. A load balancer (chapter 14) sent Alice's WebSocket to Gateway A and Bob's to Gateway B. Both sockets stay open. The gateways hold them; the chat service behind does not.
  2. Gateways say who they hold. When a user connects, their gateway records "this user is here" in a shared directory (a session registry), or subscribes to that user's or channel's topic. This is the one piece of routing state.
  3. Alice sends. Her message travels up her WebSocket to Gateway A, which forwards it to a stateless chat service. Any instance will do; it validates the message and stores it.
  4. Find the recipient. The service has to deliver to Bob, but it has no idea which gateway holds him. It asks the registry (or, in a pub/sub design, simply publishes to Bob's topic).
  5. Forward to the right gateway. The message goes to Gateway B only, not to every gateway.
  6. Push down the open socket. Gateway B writes the message into Bob's WebSocket and he sees it immediately. No polling happened anywhere.

Slack describes a version of this in its engineering blog. In their design, a message goes through a stateless Admin Server to the Channel Server that owns the channel (chosen by consistent hashing of the channel ID, a trick you'll meet properly in chapter 19). That server sends the message to every Gateway Server subscribed to the channel, and each Gateway Server delivers it to its connected clients who are subscribed to that channel. Notice the shape: the routing state is "which gateways care about this channel", not "which socket is Bob's".

What the sources do and don't say

This case study leans on two public write-ups: Discord's 2017 post about scaling Elixir to 5 million concurrent users, and Slack's 2023 post "Real-time Messaging". Where a sentence names one of them, it is a claim from that post. Everything else (heartbeats, resume protocols, draining on deploy, backoff) is the general pattern that systems like these use; the posts don't describe each company's exact version, and neither do I.

Fan-out: when one message has a thousand recipients

A private message has one recipient. A message in a big group has thousands. Delivering one message to many connections is fan-out, and its cost is simple multiplication: deliveries per second = messages per second × online members. A group with 30,000 people online and just 10 messages a second means 300,000 socket writes per second, for one group.

Discord's 2017 post describes exactly this pressure. A "guild" (what Discord calls a server) is a single process that, when something happens, must send the event to every connected member's session process. Their measurements: the naive way of sending to each process one by one cost on the order of tens of microseconds per call, so a publish from a large guild could take roughly one to two seconds, and they saw guilds with up to about 30,000 concurrent users fall behind. Their fix, a library they called Manifold, groups the recipients by the machine they live on and makes one call per machine, letting helper processes on each machine do the last hop locally.

That is the general idea behind every fan-out optimisation: send once across the expensive boundary (the network), then multiply on the cheap side (local memory). The same shape appears in Slack's flow above: one message to each gateway that has a subscriber, and each gateway fans out to its own sockets.

Common misconception: "just broadcast it to everyone and let them ignore it"

Broadcasting every message to every gateway is simple, and it works for a small system. But the cost grows with gateways × messages, even though most gateways have no interested user. Subscriptions (or a directory) exist so a message reaches only the gateways that need it.

The connection will break: heartbeats and reconnects

Chapter 16 taught that you can't tell a slow peer from a dead one. A persistent connection makes that worse: nothing flows when nobody is talking, so a half-dead connection looks the same as an idle one. Two habits fix this.

  • Heartbeats. Every so often (say every 20 to 30 seconds, an illustrative choice) each side sends a tiny "ping" and expects a "pong" within a timeout. No pong means the connection is presumed dead: close it, free the memory, mark the user offline. Heartbeats also help keep NATs and proxies from forgetting an idle connection. (WebSocket defines ping and pong frames for exactly this, RFC 6455.)
  • Reconnect with backoff. When a client notices a drop, it reconnects. If a whole gateway dies, a hundred thousand clients all reconnect at the same instant, which is exactly the thundering herd of chapter 16. Clients should wait a random, growing delay (exponential backoff with jitter) so the herd spreads out instead of landing as one wave. Case study 8 shows what happens when they don't.

Discord's post gives a taste of why this matters at scale. When their session servers restarted, each reconnecting session did several lookups (a user is in about five guilds on average, they report), and the lookup cost was big enough (about 30 seconds in total for a restart) that they reworked how the lookup ring was stored and read to make it fast. A reconnect storm is a load test you didn't schedule.

Resuming without losing messages

Dropping a connection is cheap. Losing the messages sent while it was down is not acceptable. The answer is the same idea TCP uses inside the kernel (chapter 8), rebuilt one level up in the application:

  1. The server gives every message to a connection a sequence number.
  2. The client acknowledges the highest number it has seen (or includes it in the next heartbeat).
  3. The server keeps a short replay buffer of recent messages per session.
  4. On reconnect the client says "my last number was 42". The server replays 43 onward, then goes back to live delivery.

Two edge cases decide whether the design is good. First, the replay buffer is finite: if the client was away for an hour, its number 42 is long gone, so the server must say "too far behind, start a fresh session" and the client re-syncs from the database (the source of truth). Second, replays can create duplicates, so clients should ignore any number they've already processed. Both are the same lessons as chapter 16's at-least-once delivery and idempotency.

Analogy: the numbered pages of a diary

Imagine a friend reading you a diary over a bad phone line. If every entry is numbered and you say "I got up to 42" whenever the line drops, your friend can pick up at 43. Without numbers, you'd have to guess what you missed.

Where it breaks down: your friend has the whole diary. A server only keeps a short window of recent messages, so after a long gap it has to hand you a fresh copy of the state instead.

Load balancers, deploys, and long-lived connections

Load balancers (chapter 14) are designed around short requests, and long-lived connections break several of their comfortable assumptions.

  • Balance by connections, not requests. Round-robin per request means nothing here. What matters is how many open sockets each gateway holds, so "least connections" is the natural policy. A new gateway added during a spike starts empty and only fills as people reconnect.
  • Connections skew over time. After a deploy, the gateways that restarted first end up with the fewest connections, because everyone reconnected to the ones still running. Fleets sometimes need deliberate rebalancing.
  • Timeouts must match. Load balancers and proxies close "idle" connections. Heartbeats must be more frequent than the shortest idle timeout on the path, or healthy connections get cut.
  • Deploys must drain. You can't just kill a gateway: every user on it would drop at once and stampede the rest. A graceful drain stops new connections to that gateway, then tells clients in small batches over time "please reconnect elsewhere", with jitter, until the gateway is nearly empty and can be restarted. Slack's post mentions a draining mechanism for moving users from a failing region to a healthy one; draining for deploys follows the same principle, but treat it as the general pattern rather than a claim about Slack.
Go deeper: how many connections can one server hold? optional

An idle connection is a socket object plus a few kilobytes of buffers and bookkeeping. With a modern operating system and careful tuning (raising file-descriptor limits, using event-driven I/O like epoll instead of a thread per connection), a single machine can hold hundreds of thousands of idle connections; the real limits tend to be memory, the CPU cost of heartbeats and TLS, and what happens when a hot channel suddenly sends them all a message. The earlier "C10K problem" (ten thousand connections) pushed servers to move from thread-per-connection to event loops; today's languages such as Erlang/Elixir (Discord), Go and Java with non-blocking I/O make the per-connection cost very small. The figure that matters in practice is not "how many can I hold" but "how many can I lose at once and still recover without a stampede".

Trade-offs

What you gain

Near-instant delivery, far less wasted traffic than polling, and the ability to push anything (typing indicators, presence, live edits) the moment it happens.

What you pay

Stateful servers that are hard to move, reconnect storms after any failure, a routing directory that must stay correct, and replay logic that must handle gaps and duplicates.

Because the registry says where Bob was a moment ago, it can be stale: Bob may have just disconnected, or moved to another gateway. Real systems treat "deliver to the socket" as best effort and keep the durable copy in a database. When Bob reconnects, resume (or a fresh sync) fills the gap. In other words, the connection is a fast path, not the source of truth.

Distributed systems connection

Gateways are a textbook case of separating state from logic (chapter 14) and of routing by key: the "which gateway has Bob?" problem is the same as "which shard has this row?" in chapter 19, and Slack's consistent hashing of channels onto servers is exactly that technique. Resume-by-sequence-number is a miniature of the replication logs you'll meet in chapter 18, where followers say "I'm at position 42, send me the rest". And reconnect storms lead straight to case study 8.

Key takeaways

  • Real-time apps keep one WebSocket open per user instead of polling, trading memory and state for instant delivery and far less wasted traffic.
  • A gateway tier holds the connections; stateless services behind it do the work; a registry or pub/sub gets each message to the right gateway.
  • Fan-out cost is messages × online recipients, so send once per machine and multiply locally.
  • Heartbeats detect dead connections; reconnects must use backoff with jitter to avoid a thundering herd.
  • Sequence numbers, acks and a replay buffer give resume-without-loss at the application level, with a fallback to full re-sync.
  • Deploys must drain gateways gradually. The connection is a fast path; the database is the truth.

Check your understanding

Why do chat apps usually use a persistent connection such as a WebSocket instead of polling?

  1. HTTP cannot carry text messages
  2. WebSockets use less memory on the server than polling
  3. The server can push a message the instant it exists, and idle connections waste almost no traffic
  4. Polling is not allowed through firewalls
With polling, most requests answer "nothing new" and messages wait for the next poll. A persistent connection costs memory on the server (so option 2 is the opposite of the truth) but allows instant push with almost no idle traffic.

A stateless chat service receives a message for Bob, whose connection lives on one of 500 gateways. What is the best way to deliver it?

  1. Look up (or publish to a topic for) Bob and send it only to the gateway that holds his connection
  2. Send it to all 500 gateways and let each ignore it
  3. Wait for Bob to poll the chat service
  4. Ask the load balancer to open a new connection to Bob
A registry or pub/sub routes the message to just the gateway that needs it. Broadcasting to everyone works at small scale but its cost grows with the number of gateways. Servers cannot open connections to clients behind NAT, so option 4 does not work.

A client reconnects after a drop and says "my last seen sequence number is 42". What should the server do?

  1. Resend every message from the beginning of time
  2. Ignore it, because TCP already guarantees delivery
  3. Disconnect the client for lying
  4. Replay messages 43 onward from its buffer, or tell the client to re-sync if 43 is no longer buffered
TCP's guarantees end when the TCP connection does; a new connection starts a new stream. The application-level sequence number lets the server resume exactly where the client stopped, and a bounded replay buffer means a long absence needs a full re-sync instead.

A gateway server crashes and 100,000 clients lose their connection. What should clients do next?

  1. Reconnect immediately and repeatedly until it works
  2. Reconnect after a random, growing delay (exponential backoff with jitter)
  3. Wait for the user to refresh the page
  4. Switch to HTTP polling forever
Immediate retries from 100,000 clients arrive as one wave and can overload the surviving gateways. Jittered backoff spreads the load over time so the fleet can absorb it. This is chapter 16's lesson, applied to connections.

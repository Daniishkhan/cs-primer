Punching Through NAT

You and a friend are on a video call. Your laptop sits behind your home router, theirs behind another, and neither router will let strangers in. Yet the video flows directly between you, not through some company's server. How do two computers that can't be reached find a way to talk?

The pattern in one sentence

NAT traversal: use a helper on the public Internet to introduce the two sides and tell each its public address, make both send first so each NAT opens a door for the other, and fall back to a relay when no door will open.

The problem: two locked front doors

In chapter 4 you saw that a home router uses NAT: devices inside have private addresses like 192.168.1.20, and the router rewrites outgoing packets to use its single public address and a fresh port, remembering the pairing in a NAT table. Replies find their way back because of that table entry.

Now see the catch. Tailscale's engineering write-up on NAT traversal puts it simply: a private address cannot receive Internet traffic directly, and the Internet "won't know how to get responses back to us" without the router's help. When a packet arrives from outside and matches nothing in the table, the router has no idea which device it is for, and drops it. Most routers also act as stateful firewalls: they let replies in only for conversations that started from inside. For UDP, the same write-up summarises the rule as "packets must flow out before packets can flow back in".

For a web server this is no problem: it has a public address and sits waiting, and clients always speak first. But two ordinary devices that both want to receive are each behind a locked door, and each has no way to knock. Worse, neither even knows the other's public address and port: those only come into existence when the NAT creates a mapping.

The cast

Rendezvous (coordination) server
A server on the public Internet that both sides can reach. It introduces them by passing messages between them. It doesn't need to carry their data.
STUN server
Session Traversal Utilities for NAT (RFC 8489). You send it a request; it replies with the address and port it saw your request come from, which is your public address as the outside world sees it. STUN's own specification calls itself "a tool to be used in the context of a NAT traversal solution", not a complete solution.
TURN relay
Traversal Using Relays around NAT (RFC 8656). A public server that forwards packets between the two sides when no direct path works. It is the fallback.
ICE
Interactive Connectivity Establishment (RFC 8445). The procedure that gathers every possible address for each side, tests the combinations, and picks the best one that works.

Hole punching, step by step

In this story Alice (192.168.1.20, behind NAT A) and Bob (192.168.2.30, behind NAT B) want to exchange UDP packets directly. All the public addresses are made-up documentation addresses.

Step through

UDP hole punching

  1. A direct attempt fails. If Alice just sent a packet to Bob's public address, NAT B would find no table entry for it and drop it. (Bob's private address, 192.168.2.30, is useless from outside: private ranges are not routed on the Internet.)
  2. Each side asks a STUN server. Alice sends a UDP packet from her local port 4000 to the server. NAT A rewrites it to 198.51.100.7:62000 and records the mapping. The server sees that source, and replies "I saw you as 198.51.100.7:62000". Bob does the same and learns 203.0.113.9:55000. One technical point from Tailscale's write-up: the same socket must be used for the STUN request and for the later traffic, because each socket gets its own NAT mapping.
  3. The server introduces them. The two sides already have some way to exchange messages through the rendezvous server (a side channel, as Tailscale calls it), and each now gets the other's public address and port. The server only passes tiny messages; no media goes through it.
  4. Both send first, at about the same time. Alice sends to 203.0.113.9:55000, and Bob to 198.51.100.7:62000. Alice's packet makes NAT A record "expect traffic from Bob's address here". It arrives at NAT B, which may not yet have such a record, and is dropped. That's fine. The packet's job was to open a door on Alice's side. In Tailscale's words, "both endpoints must attempt communication at roughly the same time".
  5. The path opens. Bob's packet now arrives at NAT A, which sees a reply to something Alice sent, and lets it through. Alice answers; and because Bob's NAT also saw him send first, Alice's packets are accepted too. Two-way traffic flows directly, with no server in the middle.
  6. When it doesn't work: relay. If one NAT gives Bob a different public port for every destination, the port the STUN server told Alice about is not the port Bob will use towards Alice, so her packets hit nothing. Then the two sides fall back to a TURN relay: a public server that both can reach, which forwards packets in both directions. It works every time, at the cost of an extra hop and the relay operator's bandwidth.

Why it sometimes fails: how NATs behave

Step 6 hinges on what a NAT does when the same inside socket talks to different outside hosts. RFC 4787, the IETF's recommendations for how a NAT should treat UDP, names the possibilities:

Mapping behaviourWhat the NAT does with inside 192.168.1.20:4000Hole punching?
Endpoint-independentUses the same public ip:port no matter who it talks to.Works: the port the STUN server saw is the one the peer can use.
Address-dependentReuses the mapping only for the same destination address; a new destination gets a new mapping.Breaks: the peer is a different destination from the STUN server.
Address- and port-dependentReuses it only for the same destination address and port.Breaks for the same reason.

RFC 4787 says a NAT must use endpoint-independent mapping, and notes that without it, techniques like STUN generally fail and a UDP relay is needed. Tailscale's post calls this "the major distinction we care about" and uses the friendlier names easy (endpoint-independent) and hard (endpoint-dependent) NATs. MDN's WebRTC page describes the hard case similarly: a "Symmetric NAT" will only accept connections from peers you've previously connected to, so a relay is the only way.

There is a second, separate setting, filtering: which incoming packets are let through an existing mapping. It can be loose (anyone), or restricted to the address, or even the exact address and port, that the inside host sent to. That is why both sides must send first: a strict filter only accepts traffic from the exact remote ip:port you have already sent to.

Common misconception: "a NAT is a security wall, so punching holes defeats it"

Hole punching doesn't break anything. The packets Alice sends are ordinary outgoing UDP, and the NAT only admits replies from the one address she has sent to. Nobody else gets through the hole. What it does show is that "NAT" and "firewall" are different jobs: NAT rewrites addresses, and the firewall-like behaviour is a side effect of its table. Applications still need to authenticate who they are talking to, since the introduction came through a third party.

Go deeper: the birthday trick, port mapping and keepalives optional

Easy meets hard. When only one side is a hard NAT, Tailscale describes a trick based on the birthday paradox: the hard side opens many sockets (so it creates many mappings), and the easy side probes many random ports on the hard side's address. With enough of each, a matching pair appears surprisingly quickly. It gets much worse when both sides are hard, and it looks like a port scan, which can fill a router's table.

Asking politely. Protocols such as UPnP IGD, NAT-PMP and PCP let a device ask its router to open a public port. Tailscale notes you "can't rely on these protocols being present": they may be disabled, and they don't help behind double NAT or carrier-grade NAT (where your ISP also runs a NAT).

Keepalives. Mappings expire when idle. Tailscale gives 30 seconds as a common value for UDP state, so a long-lived direct connection sends small keepalive packets. RFC 4787 requires NATs not to expire a UDP mapping in under two minutes (with limited exceptions), so being conservative is cheap.

ICE: try everything, pick the best

Real applications don't know in advance which kind of NAT they face, so they use ICE. Each side gathers candidates, possible addresses where it might be reached, and ICE then tests pairs of them with STUN requests (called connectivity checks) and picks the best working pair. RFC 8445 defines four types:

CandidateWhat it isRecommended preference (RFC 8445)
HostAn address on a local network interface, e.g. the LAN address. Works if both are on the same network.126 (highest)
Peer-reflexiveAn address discovered during the checks themselves110
Server-reflexiveThe public address a NAT assigned, learned from STUN: the hole-punching candidate100
RelayedAn address on a TURN server0 (lowest)

The ordering encodes a preference: the more direct, the better. The relay is last because relaying is costly for the operator, and RFC 8656 says TURN is best used only when a direct path cannot be found. A successful check has to work in both directions: the RFC describes it as a four-way handshake (a request and a reply each way), so both sides confirm they can send and receive. One side takes the controlling role and picks ("nominates") the pair that will carry the data.

Tailscale's summary of ICE is a good mantra: "try everything at once, and pick the best thing that works." Tailscale itself departs from the specification in places, for example it chooses paths by round-trip latency and starts on a relay while looking for a better path, so you don't wait for the search to finish before talking.

Where you meet this

  • Video calls in the browser. MDN's WebRTC documentation describes ICE as the framework that lets browsers connect to peers despite firewalls and devices without a public IP address, using STUN and, when needed, TURN. TURN, it adds, "is only used if there are no other alternatives" because it adds overhead.
  • Peer-to-peer VPNs. Tailscale describes sending traffic directly between devices where it can, with relays (its own DERP servers) as a fallback and as the side channel for setting up direct paths.
  • Many online games and file-sharing tools use the same family of tricks (general industry background, not drawn from the sources below).

Analogy: two people calling out of two locked offices

Two people work in buildings where the security desk only lets visitors in if someone inside asked them to come. A mutual friend tells each one the other's desk number. Each of them phones the other's desk at the same moment. Neither call gets through at first, but each desk now has a note: "we called them". When the next call arrives, the desk recognises it and puts it through. If the desks refuse to remember such notes, the two meet via a friend's office, which is the relay.

Where it breaks down: a human desk can be talked round. A strict NAT is a mechanical rule, so there is no negotiating with the hardest ones: only the relay works.

Distributed systems connection

NAT traversal is peer discovery plus fallback, a pattern that recurs everywhere. Peers need a rendezvous point (a small, always-on, centrally run piece) to find each other, but the heavy traffic flows peer to peer. It shows graceful degradation (chapter 16): there is a best path, a worse one and a guaranteed one, and the system tries them in order. And it reminds us that peer-to-peer systems aren't free of servers: the rendezvous and relay servers are the hidden infrastructure. Chapter 15 asked why we distribute systems; this is a case where the Internet's address-sharing makes the pure peer-to-peer ideal awkward.

Key takeaways

  • A NAT only lets replies in for conversations that started from inside, so two devices behind NATs can't simply connect.
  • STUN tells a device its public address and port; a rendezvous server shares that between the peers.
  • In UDP hole punching both sides send first, at about the same time, so each NAT creates the entry that lets the other's packets in.
  • It works with endpoint-independent mapping ("easy" NATs, RFC 4787) and usually fails when both are endpoint-dependent ("hard"), where a TURN relay takes over.
  • ICE gathers host, server-reflexive and relayed candidates, tests them, and prefers the most direct pair that works.
  • WebRTC calls and peer-to-peer VPNs use this to send data directly when they can and via a relay when they must.

Check your understanding

Why can't Alice simply send a packet to Bob's public address and expect it to arrive?

  1. Public addresses can only be used by servers
  2. NAT B has no table entry for traffic from Alice, so it drops the unsolicited packet
  3. UDP packets are limited to 100 metres
  4. Bob's private address is shared with Alice
A NAT forwards incoming packets only if they match a mapping created by outgoing traffic. A packet from a stranger matches nothing, so it is dropped.

What does a STUN server tell a client?

  1. Which relay to use
  2. The private address of its peer
  3. How fast its connection is
  4. The public ip:port from which the server saw the client's request arrive
STUN reports the "reflexive" address, as seen from outside the NAT. The peers then exchange these addresses through a rendezvous channel.

Why do both sides send packets to each other at about the same time in hole punching?

  1. Each outgoing packet makes its own NAT expect replies from that peer, so the other side's packets are then allowed in
  2. It doubles the bandwidth
  3. It tells the STUN server to shut down
  4. It turns UDP into TCP
The first packets may be dropped, but they leave behind the state that lets later packets through. Doing it at the same time keeps both mappings fresh.

Which NAT behaviour most often defeats hole punching, and what is the usual fallback?

  1. Endpoint-independent mapping; use a bigger packet
  2. Port forwarding; use DNS
  3. Endpoint-dependent mapping (the NAT uses a different public port per destination); use a TURN relay
  4. Stateful filtering; use TCP only
With endpoint-dependent mapping, the port the STUN server saw is not the port the NAT will use towards the peer, so the peer's packets miss. TURN forwards the traffic through a public server, at extra cost, and works regardless.

Steering Traffic with DNS

DNS answers the question "what is the address of this name?" But nothing says the answer must be the same for everyone. A DNS server can look at who is asking, check which servers are alive, roll a weighted die, and answer differently each time. That makes DNS the cheapest traffic director on the Internet, and also a rather blunt one.

The pattern in one sentence

DNS-based load balancing: make the authoritative DNS server choose which address to return, based on location, latency, weights or health, so that clients are steered before they ever open a connection, accepting that caches make the steering coarse and slow to change.

The cast

From chapter 9 you know the main characters. Here they are in the roles that matter for steering:

The authoritative server
The server that owns the answer for www.example.com. A "smart" one doesn't read a fixed table: it applies a routing policy to decide what to return.
The recursive resolver
The server your device actually asks (your ISP's, or a public one). It does the legwork and caches the result. The authoritative server usually sees this resolver's address, not yours.
The TTL
The number of seconds a resolver may keep an answer before asking again. Short TTLs make changes show up sooner; long TTLs mean fewer queries.
The health check
A probe that regularly tests whether each server is working, so the DNS server can stop handing out dead ones.

The menu of policies

Amazon's Route 53 documentation is a convenient catalogue, because it lists the policies a DNS-based service typically offers. Other DNS providers offer similar ones under different names (general industry background). A few of Route 53's, in the documentation's own terms:

Cloudflare's load balancing documentation shows the same idea from another vendor: pools of servers, health-based failover, and steering policies that decide which pool answers. Both describe a mode where the service only answers DNS queries and leaves the traffic itself alone. That is the "pure" DNS steering this page is about.

Analogy: the receptionist who gives out room numbers

Imagine a company with offices in three cities and one receptionist who answers "where can I find Sam?" The receptionist looks at where the caller seems to be, checks which offices are open today, and answers "try the Paris office". The caller then goes there directly. Nobody walks the caller anywhere; the receptionist only chose the address.

Where it breaks down: a real receptionist hears the caller's own voice and location. A DNS server usually only hears the caller's switchboard, the resolver, and the callers write the answer down and keep using it.

Why it is coarse: a step-through

Step through

Where DNS steering goes wrong, and one fix

  1. An ordinary lookup. The user's device asks its recursive resolver for www.example.com. This user happens to use a large public resolver, which answers many people in a wide region.
  2. The authoritative server sees the resolver, not the user. The query that reaches it carries the resolver's address. Route 53's documentation says this directly: when the resolver doesn't pass on client information, Route 53 "uses the source IP address of the DNS resolver to guess where the user is".
  3. The wrong answer, honestly given. The authoritative server did its job well for the asker it could see: it returned the server nearest the resolver. But the resolver is far from the user, so the user is sent on a long trip. This is the heart of why DNS steering is coarse.
  4. The fix: EDNS Client Subnet. RFC 7871 lets the resolver include a truncated piece of the client's address in its query (for example the first 24 bits), so the authoritative server can pick based on the user's network. The answer comes back tagged with the range it applies to, and the resolver caches it per network. Route 53 documents that it uses this when the resolver supports it.
  5. Failures show up slowly. A health check notices server A is down, and the authoritative server stops returning it. But resolvers (and some clients) already hold the old answer. Until it expires, or forever for clients that ignore the TTL, those users still head for the dead server.

Three reasons DNS is a blunt steering wheel

1. It sees the resolver, not you

Location policies guess from the resolver's address. If your resolver is far away or shared by a whole country, your "nearest" server may not be near you at all.

2. Caches delay change

An answer is reusable until its TTL runs out, at the resolver, in the operating system, and in the browser. You can't recall an answer once given.

3. Some clients hold on

Cloudflare's docs warn: "If a client has a cached DNS response, they will go to their previous destination." That bypasses the load balancer entirely.

The ECS fix, and what it costs

EDNS Client Subnet exists, RFC 7871 says, because topology-sensitive authoritative servers otherwise get "less than desirable responses" when resolvers are centralised and far from their users. The resolver passes along a source prefix length: how many leading bits of the client address to share. The RFC recommends truncating IPv4 addresses to 24 bits and using 56 bits for IPv6, so the server learns your network but not your exact address. The server's reply carries a scope prefix length, saying how widely that answer may be reused.

There are two costs. First, privacy: the RFC itself describes this as a trade-off and recommends the feature be off by default in nameserver software, and a user who wants to hide can send a prefix length of 0. Your network location now travels to every authoritative server you look up, not just to your resolver. Second, cache size: answers must be stored per network instead of once per name, and the RFC warns that enabling it "will significantly increase the size of the cache." Because of this, support depends on the resolver, and Route 53 falls back to the resolver's own address when ECS isn't there.

TTL: the speed-of-change knob

The TTL is the main control you have. Route 53's documentation puts the trade-off plainly: a longer TTL reduces the number of calls resolvers make, which "reduces latency and lowers your bill", but changes take longer to take effect. For records attached to a health check it recommends 60 seconds or less "so clients respond quickly to changes in health status". It also suggests lowering the TTL to something like 300 seconds before changing a record that's already in use, then raising it later.

Even a TTL of 60 seconds is not a guarantee: it is only how long a well-behaved cache may keep an answer. A health check also takes time to decide a server is really dead (to avoid false alarms), then the DNS change is published, and then caches that already hold the old answer finish their countdown. This is the same TTL trade-off we saw for CDN caches in chapter 14.

Common misconception: "DNS failover is instant"

DNS failover works by no longer handing out a dead address. It cannot take back answers that are already out there. Users with a cached answer keep trying the dead server until the TTL expires, and a client that doesn't respect the TTL may keep trying for much longer. DNS failover is "within minutes, mostly", not "immediately, for everyone".

The alternatives

  • Anycast (case 1). Give every site the same address and let routing choose. It reacts as fast as routes change and doesn't depend on caches or resolver locations, but it can't weigh health or load and can disturb long TCP connections.
  • Proxying. Cloudflare's docs describe a proxied mode where traffic passes through Cloudflare, so failover is faster and routing more accurate than in DNS-only mode, where results "can otherwise be affected by DNS caching". The price: you give up the simplicity of a pure DNS answer, and the proxy sees your traffic. The same docs say the DNS-only mode relies on resolvers respecting the short TTL, and leaves endpoint IPs exposed.
  • Combining them. A common industry pattern: DNS picks a region, a load balancer inside the region (chapter 14) picks a server, and anycast fronts the DNS itself. That pattern is general background, not a claim about any one company.

Try it yourself

Watch caching and answer variety

These are read-only dig queries (on Windows, use nslookup or a web-based DNS tool). Your output will differ.

$ dig +noall +answer www.cloudflare.com @1.1.1.1    # note the number after the name: remaining TTL
www.cloudflare.com.  242  IN  A  104.16.123.96
www.cloudflare.com.  242  IN  A  104.16.124.96
$ sleep 3; dig +noall +answer www.cloudflare.com @1.1.1.1
www.cloudflare.com.  239  IN  A  104.16.123.96
www.cloudflare.com.  239  IN  A  104.16.124.96
$ dig +subnet=203.0.113.0/24 +noall +answer +comments example.com @8.8.8.8
; CLIENT-SUBNET: 203.0.113.0/24/0
example.com.  164  IN  A  172.66.147.243 ...
  • The countdown is the resolver's cache at work: the second answer is the same data with a smaller TTL. Run it a few times and watch it reset when the entry expires.
  • The +subnet option makes dig send an ECS prefix, here a documentation-range one, so you can see how a resolver treats it. In the example the reply's scope after the second slash was 0, meaning this answer isn't specific to any network. A name that uses location-aware DNS might give different addresses for different subnets. The query goes to a public resolver, which means it learns the prefix you typed (not your real address).
  • Compare dig +short some-big-site.com @8.8.8.8 with the same query to @1.1.1.1 and your ISP's resolver. Different resolvers may get different answers for the same name, and some names return the same pair of addresses to everybody.
  • Some networks intercept DNS traffic, which can affect results; if something looks odd, try from another network.

Distributed systems connection

DNS steering is eventually consistent control. The "truth" (which servers should receive traffic) lives in the authoritative server; everyone else holds possibly stale copies, and the TTL bounds how stale (chapter 18 makes that trade-off precise). Health checks bring in failure detection, with the usual problem from chapter 16: you can't tell a dead server from a slow one, so you wait a bit, and during the wait you serve bad answers. Case 6's Facebook outage shows the dark side: when a health rule is applied everywhere at once, the steering system can remove every good answer.

Key takeaways

  • A smart authoritative DNS server can answer by location, latency, weight or health, steering clients before any connection is made.
  • It sees the resolver's address, not the user's, so location choices can be wrong; EDNS Client Subnet (RFC 7871) passes a truncated client prefix, at a cost in privacy and cache size.
  • Changes spread only as fast as caches expire; short TTLs (60 s or less for health-checked records, per Route 53) help but never make failover instant.
  • Some clients keep using cached answers, bypassing the steering altogether.
  • Anycast and proxying are alternatives that trade DNS's simplicity for faster reaction.

Check your understanding

A user in Brazil uses a public resolver located in the United States. Without EDNS Client Subnet, what can a location-based DNS policy do wrong?

  1. Refuse the query
  2. Return an IPv6 address instead of IPv4
  3. Treat the user as if they were in the resolver's location and return a server near the US
  4. Send the user's full address to every website
The authoritative server sees only the resolver's address. It may return the server nearest the resolver, which isn't nearest the user. ECS fixes this by passing a truncated client prefix.

Why does a short TTL not guarantee instant failover?

  1. Answers already cached at resolvers and clients stay in use until they expire, and some clients ignore TTLs
  2. DNS can't remove addresses from its table
  3. TTL only applies to IPv6
  4. Health checks are not allowed with DNS
DNS failover only changes future answers. Anything already cached keeps pointing at the dead server until it expires, and detection itself takes time too.

What is the main privacy trade-off of EDNS Client Subnet?

  1. It encrypts all DNS traffic
  2. It makes DNS slower for everyone
  3. It stops resolvers from caching
  4. Part of the client's network address is passed on to authoritative servers, not just to the resolver
RFC 7871 recommends truncating addresses (24 bits for IPv4) and keeping the feature off by default. Clients can opt out by sending a prefix length of 0.

With weighted routing, two records have weights 1 and 255. What share of answers does the first get?

  1. Half
  2. 1/256
  3. 1/255
  4. None, because weights must be equal
Each record gets its weight divided by the sum of all weights: 1/(1+255) = 1/256. Setting a weight to 0 stops traffic to that record. This is what makes gradual rollouts possible.

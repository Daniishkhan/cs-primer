Anycast: One Address, Many Places

The DNS root servers have 13 names, yet they answer from over two thousand machines scattered around the planet. Public resolvers like 1.1.1.1 answer from hundreds of cities, all using the same IP address. How can one address be in many places at once, and how does your packet find the right one?

The pattern in one sentence

Anycast: announce the same IP address from many locations, and let the routing system deliver each packet to whichever location is "nearest" in routing terms, which gives you low latency, automatic failover and spread-out attack traffic with no changes on the client.

The problem: one address, one place

An ordinary IP address, as you learned in chapter 4, belongs to one machine in one place. This is called unicast: one sender, one receiver. If your DNS server lives in a data center in Virginia, then a user in Singapore sends every query across the Pacific. As chapter 13 showed, that costs on the order of a fifth of a second per round trip, and it cannot be bought away. A single location is also a single point of failure and a single target for attackers.

The obvious fix is more servers in more places. But then the question becomes: which address does the user ask for? You could give each site its own address and make clients pick, which is what DNS-based steering does (we look at it in case study 3). Anycast takes a different route: give every site the same address and let the network do the picking.

How it works: the same announcement from many places

In chapter 5 you saw that routers build a table of "to reach this prefix, go via that neighbour", and that networks tell each other what they can reach using BGP. A prefix is a block of addresses, such as 203.0.113.0/24. Nothing in that system says a prefix may only be announced from one place.

RFC 4786, the standard that describes running anycast services, defines it as "the practice of making a particular Service Address available in multiple, discrete, autonomous locations." Each location announces the same prefix. Each router around the world then does what it always does: it picks the best route it has heard, which leads to one of the locations. Different routers, in different places, hear different announcements first and prefer different ones.

Step through

One address, three sites

  1. Every site announces the same prefix. Three locations each tell their neighbouring networks, using BGP, "the prefix containing 203.0.113.53 is reachable through me". (These addresses are made-up documentation addresses.) Those neighbours pass the news on.
  2. A user's routers pick one. Routers on the way from Asia have heard three routes for the same prefix and choose the best by BGP's rules. For this user, that is Singapore. Nobody told the user's phone anything; it just sent a packet to 203.0.113.53.
  3. Someone else gets a different site. A user in Europe asks the same address and, because their routers rank the same three routes differently, lands in Frankfurt. One address, many places.
  4. Attack traffic gets spread out. A botnet is also scattered around the world, so its packets also follow the "nearest" rule and arrive at many sites, each of which takes only a share. In the words of an early Cloudflare write-up, "a distributed botnet will have a portion of its denial of service traffic absorbed by each of our data centers."
  5. Failure moves traffic automatically. If a site goes down, or withdraws its announcement, routers forget that route and fall back to the next-best one. The Asian user now reaches Frankfurt. Nothing was reconfigured on the user's device, though routes take a little while to settle.

"Nearest" means nearest to BGP

It is tempting to read "nearest" as "geographically closest". It isn't. BGP routers compare routes using attributes such as the length of the AS path (how many networks the route passes through) and the policies each network has set. Cloudflare's early anycast write-up says traffic goes to the "nearest" data center as decided by the network's routing; because that is routing's decision, it need not match the map. In the simplest version, fewer networks in the path wins, after business rules are applied.

Analogy: a national phone number

Think of a pizza chain with one national number. You dial it from your town and the phone network connects you to a branch near you; your friend in another city dials the same number and reaches a different branch. The chain didn't tell you which branch to use, and neither of you needs to know there are many.

Where it breaks down: the phone network picks a branch by geography it knows about. Internet routing picks by network policy and path length, so the "nearest" branch may not be the closest on the map, and the choice can change when routes change.

Why DNS loves it, and why long TCP connections are harder

A DNS lookup (chapter 9) is typically one small UDP packet out and one back (chapter 7). It is stateless: the server doesn't need to remember the earlier question to answer the next one. If two consecutive queries from the same user happen to reach different sites, both get a correct answer. RFC 4786 notes that DNS already has its own redundancy, and anycast adds to it. It cites root servers, resolvers and authoritative servers as its examples.

A long-lived TCP connection (chapter 8) is different. It lives in the memory of one server: sequence numbers, windows, maybe a TLS session. If routing changes mid-connection so that your next packet arrives at a different site, that site has never heard of you and can only reject it. RFC 4786 warns about this family of problems: routing has to keep each client pinned to one node for the length of a transaction, and TCP is especially exposed because its handshake involves several packets. So anycast works best when:

  • exchanges are short (a DNS query, a single HTTP request), so a route change rarely lands in the middle of one;
  • routes are stable, and operators avoid rapid announce/withdraw cycles, which RFC 4786 warns can trigger BGP damping and make healthy nodes look unavailable;
  • or the service is designed to survive a hop: connections can be re-established cheaply, or state is shared between sites.

Common misconception: "anycast is a load balancer"

Anycast spreads users by routing topology, not by how busy each site is. A site that is overloaded will still get the traffic that routing sends it, unless the operator changes its announcements (for example, withdrawing or making a route less attractive). It is a very coarse tool for balance, but an excellent one for proximity and failover.

Absorbing attacks

A distributed denial-of-service (DDoS) attack tries to overwhelm a service with traffic. Against a unicast server, all of that traffic converges on one place. With anycast the attackers' packets are routed to many sites, so each site sees only the slice that comes from its own part of the Internet. RFC 4786 lists "constraint of distributed denial-of-service attacks or flash crowds to local regions" as a goal, and describes local nodes, which are announced only to nearby networks (using mechanisms such as NO_EXPORT), so that a flood in one region stays in that region and cannot knock out the whole service.

The sorting of good traffic from bad is also spread out: every site can filter its own share. This isn't magic. The attack is only absorbed if the total capacity of the sites exceeds the attack, and an attack concentrated in one region can still overwhelm that region's site.

Who uses it

The DNS root servers
root-servers.org lists 13 root servers (letters A to M), operated by 12 independent organisations. On the day this page was written (12 October 2026), it reported 2,047 operational instances. Its list marks sites as "Global" or "Local", which matches the RFC 4786 idea of nodes announced widely versus only to nearby networks.
Public resolvers
Cloudflare's 1.1.1.1 resolver runs on Cloudflare's network "in hundreds of cities worldwide", and the address is the same everywhere.
CDNs
Cloudflare's developer documentation describes an anycast IP address that is used to distribute traffic across its network. Other CDNs use anycast too, often combined with DNS steering. (That second point is a general industry pattern, not a claim from the sources below.)

Big operators often combine them: DNS steering to pick a broad region, anycast within it for fast failover. Notice what the Facebook outage in case study 6 showed from the other side: when every site decides to withdraw its announcement at once, anycast's failover has nowhere left to fail over to.

Try it yourself

Ask an anycast service where it is

These commands are read-only and safe. Your output will differ from the examples, and some networks interfere with DNS, as described below.

$ curl -s https://1.1.1.1/cdn-cgi/trace | grep -E 'colo|loc'   # which Cloudflare site answered?
colo=KHI
loc=PK
$ dig +short CHAOS TXT id.server @1.1.1.1    # Cloudflare documents this query for 1.1.1.1
"KHI"
$ dig +nsid . SOA @k.root-servers.net      # look for an NSID line near the OPT section
$ traceroute -n 1.1.1.1                    # Windows: tracert -d 1.1.1.1
 1  192.168.0.1   3.6 ms
 ...
 8  1.1.1.1      25.9 ms
  • curl reaches Cloudflare's web service on the same anycast address. The colo line is a short code naming the Cloudflare site that answered you. When I ran it, it printed a code for a city near me. Ask a friend in another country to run it and compare.
  • The CHAOS TXT id.server query is a way to ask a DNS server to name itself. Cloudflare's troubleshooting page documents it for 1.1.1.1. The example output above is illustrative; the exact string depends on the site.
  • +nsid asks for a server's NSID, the identifier defined in RFC 5001 so that you can tell which of several servers sharing one address answered. It only works if the operator has turned it on, so it may print nothing.
  • If the identifying queries return nothing, your network may be intercepting DNS traffic. When I tested from one network, id.server came back empty and a root server query came back with the "recursion available" flag set, which a real root server wouldn't set. That means something on the path answered instead. The curl and traceroute checks don't have this problem.
  • The last hops of the traceroute tell you roughly how far away the "nearest" site is: round-trip times of a few milliseconds suggest a site in your own city, tens of milliseconds a more distant one. You can also try a different network, such as your phone's hotspot, and watch the answer change.

Distributed systems connection

Anycast is replication of a service, with routing as the load balancer and failure detector rolled into one (chapter 14). It works because DNS answers are stateless, which is exactly why stateful systems need more care: the moment a request depends on something remembered at one site (chapter 18), you must either keep users pinned to a site or replicate that state to all of them. It also reminds us that failure detection by routing is not instant. For a short time, some users are still sent to a site that is gone.

Key takeaways

  • Anycast means announcing one prefix from many locations; BGP then delivers each packet to the best route, which is "nearest" in network terms, not necessarily geographic distance.
  • It suits short, stateless exchanges such as DNS over UDP, and gives automatic failover when a site withdraws its route.
  • Long-lived TCP connections can break if routes shift mid-connection, so operators keep routes stable or design for reconnection.
  • Attack traffic is split across sites, and local nodes can contain a flood to a region.
  • Unlike DNS steering, the client sees one address and does nothing special; unlike a real load balancer, anycast doesn't know how busy each site is.

Check your understanding

What makes an address "anycast"?

  1. It is sent to every server at the same time
  2. DNS returns a different IP address to each user
  3. The same prefix is announced from several locations, and routing delivers each packet to one of them
  4. It only works over TCP
That is the whole idea. Sending to every server at once is multicast or broadcast. Handing out different addresses is DNS steering. Anycast uses a single address and lets BGP routing choose the destination.

A user in one country is routed to a site 2,000 km away although another site is 200 km away. Which explanation fits anycast?

  1. "Nearest" is decided by BGP routes and policy, such as the number of networks crossed, not by distance on a map
  2. The nearer site must have crashed
  3. Anycast always picks the site with the lowest load
  4. BGP measures round-trip time and picks the fastest
BGP compares route attributes like AS path length and policy; it doesn't measure latency or load. So the "nearest" site in routing terms can be geographically farther. Operators tune their announcements to reduce this.

Why is anycast a better fit for DNS over UDP than for a long file download over TCP?

  1. UDP packets are encrypted
  2. TCP cannot use BGP
  3. DNS servers are faster than file servers
  4. A DNS exchange is short and stateless, but a TCP connection holds state at one server and breaks if a route change sends packets elsewhere
If two DNS queries reach different sites, both still get correct answers. A TCP connection's state lives on one server, so packets arriving at a different site have no connection to belong to.

How does anycast help against a DDoS attack?

  1. It tells attackers the wrong address
  2. Attack packets follow the same "nearest site" routing as everyone else's, so the flood is divided between sites instead of hitting one
  3. It decrypts attack traffic
  4. It removes the need for any capacity at the sites
The attack's sources are spread around the world, so their packets arrive at many sites, each taking a share. It only helps if the sites together have enough capacity, and a regional concentration can still overwhelm one site.

Keys, Secrets & PKI

Chapter 3 gave you primitives whose strength rests on one assumption: the key stays secret. In practice, most cryptographic failures are key-management failures. This chapter is about the life of a key and of every other secret in a system: where they live, who may use them, how they change without downtime, and how a certificate authority turns a public key into an identity.

Why this matters

The algorithm is rarely what breaks. A signing key left in a source repository, a database password in an environment variable dumped into a crash report, a certificate that expired at 3 a.m., or a master key that nobody can rotate because every service has a copy: these are everyday incidents. Good key management lets you answer three questions at any time: who can use this key, how fast could we replace it, and what do we lose if it leaks?

The key lifecycle

A key is not a value you create once. It has a life, and each stage has its own risks. The same lifecycle (described in detail in NIST's key-management recommendations, SP 800-57) applies to encryption keys, signing keys and passwords:

  • Generate from a CSPRNG (chapter 3), never from a password, timestamp or random. For high-value keys, generate inside a hardware module so the bytes never exist in ordinary memory.
  • Store encrypted, access-controlled and, for important keys, with no plaintext copy anywhere outside the protected module. Every copy is another place to steal it from.
  • Use only for one purpose (an encryption key is not also a signing key), for a limited set of operations, and with an audit record of who used it when.
  • Rotate on a schedule (limiting how much data one key protects and how long a stolen key helps) and immediately on suspected exposure. A key you cannot rotate is a liability.
  • Revoke when a key must no longer be trusted: tell everyone who relies on it. For certificates that is revocation proper (below); for symmetric keys it means disabling the version.
  • Destroy when finished: all copies, including backups, snapshots and exports. Destroying a key can be a feature: if data is encrypted under a key and the key is erased, the data is unreadable, which is called crypto-shredding and is how deletion reaches backups (chapter 17).

KMS and HSM: keep the key away from the code

The central design move in key management is separating using a key from having it. A key management service (KMS) is a service whose API says "encrypt this", "decrypt that", "sign this digest", "generate a data key", and whose key bytes never leave it. Your application authenticates to the KMS, and the KMS's access policy decides whether this caller may use this key for this operation, and writes an audit record. The cloud providers each offer one (AWS KMS, Google Cloud KMS, Azure Key Vault), and self-hosted ones exist (HashiCorp Vault's transit engine).

Underneath a KMS is often a hardware security module (HSM): a tamper-resistant device that generates and stores keys and performs cryptographic operations internally. Extracting the key requires physically attacking the device, which is designed to erase itself if attempted. HSMs are commonly validated against the US FIPS 140 standard and its levels. Their trade-off: they are slower and costlier than software, and they concentrate trust in a small, hard-to-fool box, a textbook trusted computing base (chapter 2).

The benefit is concrete. If an attacker steals your application's disk, they get nothing that decrypts data. If they compromise the application process, they can ask the KMS to decrypt while they hold that access, and you can see it in the audit log and cut it off by revoking the application's permission. The key itself never left, so you do not need to rotate it; contrast with a key stored in the application's config, where compromise means the key is theirs forever.

Envelope encryption

A KMS will not encrypt your terabytes: its calls are network round trips with size limits, and you do not want all data flowing through it. The standard solution is envelope encryption with two layers of keys:

  • A data encryption key (DEK), generated per object, per file or per tenant, encrypts the data directly, locally, using an AEAD (chapter 3).
  • A key-encryption key (KEK), which lives in the KMS and never leaves it, encrypts ("wraps") each DEK. The wrapped DEK is stored right next to the ciphertext it protects, together with the id of the KEK version used.

Analogy: a safe-deposit box and many small safes

Each document goes in its own small safe with its own combination (the DEK). The combinations are written on slips that are locked in the bank's vault (the KEK). To open a safe you ask the bank to read you its slip, which it does only for people on its list, and it logs every request.

Where it breaks down: a bank teller reads a combination aloud; a KMS unwraps and returns the DEK to the caller, so for that moment the application holds a usable key. That is why the plaintext DEK should be kept in memory briefly, and why the KMS audit log matters.

Why two layers? Four reasons that recur in design reviews:

  • Performance and cost. Bulk encryption is local; the KMS sees only tiny wrap and unwrap calls.
  • Blast radius. Every object or tenant has its own DEK, so compromising one DEK exposes one object, not the lot.
  • Cheap rotation. Rotating the KEK means re-wrapping the small DEKs, not re-encrypting the data (next section).
  • Deletion by key destruction. Destroy a tenant's DEK (or the KEK that wraps it) and every copy of its data, in every backup, becomes unreadable.

One more detail from the code below deserves attention: the encryption context. When wrapping a DEK, you bind it to its owner (here, the tenant name) as authenticated associated data. If anyone copies a wrapped DEK from one tenant's record to another's, unwrapping fails, because the context does not match. This blocks a whole class of "swap the encrypted blobs" attacks. It is the associated-data feature of AEAD from chapter 3, used for access control.

Rotation without downtime

Rotation sounds simple, "replace the key", until you notice that the old key is still needed to read old data and to verify old signatures. Every system that rotates safely follows the same pattern: name every key, tag every ciphertext with the name, and let old and new coexist for a while.

  1. Add a new key version. Both versions are enabled for decryption/verification.
  2. Switch writers to the new version. New data uses v2. Old data is still readable with v1.
  3. Migrate in the background: re-wrap DEKs (cheap) or re-encrypt data (expensive, needed when the DEK itself may be exposed).
  4. Retire the old version: first disable it for new operations and watch for any caller still using it, then destroy it.
Step through

Rotating a key-encryption key without downtime

  1. Steady state: every record's data key is wrapped by kek-v1, and the record stores that id.
  2. Rotate: kek-v2 is created and becomes the current version. New writes (record 5) use it. Records 1 to 4 are untouched and still decrypt, because kek-v1 is still enabled.
  3. A background job unwraps each old data key with v1 and re-wraps it with v2 (records 1 and 2 so far). Reads keep working throughout: every record names the version it needs.
  4. Migration finishes: every record uses v2. v1 is now only a fallback, so it is disabled for new use and monitored for stragglers.
  5. With nothing relying on it, v1 is destroyed. The window during which a stolen v1 would have been useful is now closed. No downtime, and no bulk data was re-encrypted.

The same pattern, with different words, applies to signing keys: tokens carry a key id (kid), verifiers fetch a published set of public keys containing both old and new, and the signer switches to the new one after verifiers have had time to learn it (chapter 6). It also applies to HMAC secrets for webhooks (accept two for a while) and to database passwords (a service that supports two credentials at once can be rotated live).

When must you re-encrypt the data instead of just re-wrapping? If a DEK may have leaked, re-wrapping it under a new KEK does nothing, since the attacker has the DEK itself. Then you generate new DEKs and re-encrypt, which is expensive, and the reason to give DEKs a limited scope.

The whole flow, running

The program below implements envelope encryption, key versions, background re-wrapping, context binding and crypto-shredding. Because the standard library contains no AES, it uses a toy cipher: a SHAKE-256 keystream with HMAC, encrypt-then-MAC. It shows the structure of the protocol, and is not something to deploy.

Educational only, never use in production

The toy cipher exists so the example runs with only Python's standard library. For real use, call a KMS for key wrapping and a vetted AEAD (AES-GCM or ChaCha20-Poly1305 from the cryptography package or libsodium) for data. The ToyKMS class here also keeps keys in ordinary memory; a real KMS keeps them in an HSM behind authentication.

"""Envelope encryption with a TOY cipher.  EDUCATIONAL ONLY - never use in production.
Toy cipher = SHAKE-256 keystream + HMAC-SHA256, encrypt-then-MAC. Real systems use AES-GCM
or ChaCha20-Poly1305 from a vetted library, and a real KMS/HSM for the key-encryption keys."""
import hashlib, hmac, json, secrets

def _split(key):
    return (hashlib.sha256(b"enc" + key).digest(), hashlib.sha256(b"mac" + key).digest())

def seal(key: bytes, plaintext: bytes, aad: bytes = b"") -> bytes:
    ek, mk = _split(key)
    nonce = secrets.token_bytes(16)
    ct = bytes(p ^ k for p, k in zip(plaintext, hashlib.shake_256(ek + nonce).digest(len(plaintext))))
    tag = hmac.new(mk, aad + nonce + ct, hashlib.sha256).digest()
    return nonce + ct + tag

def open_(key: bytes, blob: bytes, aad: bytes = b"") -> bytes:
    ek, mk = _split(key)
    nonce, ct, tag = blob[:16], blob[16:-32], blob[-32:]
    if not hmac.compare_digest(tag, hmac.new(mk, aad + nonce + ct, hashlib.sha256).digest()):
        raise ValueError("authentication failed")
    return bytes(c ^ k for c, k in zip(ct, hashlib.shake_256(ek + nonce).digest(len(ct))))

class ToyKMS:
    """Holds key-encryption keys (KEKs) by version. Callers never see KEK bytes."""
    def __init__(self):
        self._keks, self.current = {}, None
        self.rotate()
    def rotate(self):
        kid = f"kek-v{len(self._keks) + 1}"
        self._keks[kid] = secrets.token_bytes(32)
        self.current = kid
        return kid
    def wrap(self, dek: bytes, context: str):
        return self.current, seal(self._keks[self.current], dek, context.encode())
    def unwrap(self, kid: str, wrapped: bytes, context: str) -> bytes:
        return open_(self._keks[kid], wrapped, context.encode())
    def rewrap(self, kid, wrapped, context):
        return self.wrap(self.unwrap(kid, wrapped, context), context)
    def destroy(self, kid):
        del self._keks[kid]

kms, db = ToyKMS(), {}

def put(rec_id, tenant, text):
    dek = secrets.token_bytes(32)                       # fresh data key per record
    kid, wrapped = kms.wrap(dek, tenant)                # context binds the key to the tenant
    db[rec_id] = {"tenant": tenant, "kek": kid, "wrapped": wrapped,
                  "data": seal(dek, text.encode(), rec_id.encode())}

def get(rec_id):
    r = db[rec_id]
    dek = kms.unwrap(r["kek"], r["wrapped"], r["tenant"])
    return open_(dek, r["data"], rec_id.encode()).decode()

def show(title):
    print(title)
    for rid, r in db.items():
        print(f"  {rid}: kek={r['kek']}  readable={'yes' if _ok(rid) else 'NO '}")

def _ok(rid):
    try: get(rid); return True
    except Exception: return False

put("r1", "acme", "acme invoice #1"); put("r2", "globex", "globex salary table")
show("1. written under kek-v1")
kms.rotate(); put("r3", "acme", "acme invoice #2")
show("2. after rotation: new writes use v2, old records still decrypt (v1 retained)")
for rid, r in db.items():                                # re-wrap only the small data keys
    if r["kek"] != kms.current:
        r["kek"], r["wrapped"] = kms.rewrap(r["kek"], r["wrapped"], r["tenant"])
kms.destroy("kek-v1")
show("3. DEKs re-wrapped, kek-v1 destroyed: nothing re-encrypted, nothing lost")
print("   ciphertext untouched by rotation:", len(db["r1"]["data"]), "bytes")

stolen = dict(db["r2"]); stolen["tenant"] = "acme"        # confused-deputy style: wrong context
try:
    kms.unwrap(stolen["kek"], stolen["wrapped"], stolen["tenant"])
except ValueError as e:
    print("4. unwrap with the wrong tenant context ->", e)

db["r3"]["data"] = db["r3"]["data"][:20] + bytes([db["r3"]["data"][20] ^ 1]) + db["r3"]["data"][21:]
print("5. flipped one ciphertext bit -> readable:", _ok("r3"))

kms.destroy("kek-v2")
show("6. kek-v2 destroyed too: crypto-shredding, every record is now unrecoverable")

Step 6 is crypto-shredding: with every KEK version destroyed, the stored bytes still exist but nothing can ever decrypt them.

Crypto-shredding and backups pull in opposite directions

If you destroy a key to delete data, you have also made it impossible to restore that data from backup. That is the point for privacy deletion (chapter 17), and a disaster for an accidental one. And keys themselves need backup and recovery plans (reliability chapter 18), or losing the master key loses everything. Typical practice: back up key material separately, with stricter controls and split custody, from the data it protects.

Secrets management

Keys protect data; secrets are the other credentials a system needs: database passwords, API tokens, OAuth client secrets, signing keys, TLS private keys. The question "where does the program get its password?" has a surprisingly deep answer.

Where secrets live: env vars, files, or a store

The bootstrap problem (sometimes called "secret zero") is solved by workload identity: the platform itself vouches for the workload. A cloud virtual machine, a Kubernetes service account, or a SPIFFE identity (below) presents a platform-issued, short-lived proof of "I am this workload", which the secret store accepts in exchange for secrets. No long-lived credential is baked into the image. Orchestrators and their risks are covered in reliability chapter 14 and chapter 14 of this course.

Dynamic secrets and leases

The best secret is one that does not exist until needed and disappears soon after. A dynamic secret is generated on demand for one client, for a limited time. In Vault-style systems the application asks "give me database credentials for the reporting role"; the secret manager creates a brand-new database user with a random password and a time to live, and returns it with a lease. The client must renew the lease to keep using the credential; if it does not (it crashed, or was compromised and cut off), the lease expires and the manager deletes the database user.

This is the lease of distributed chapter 4 with one important difference. There, an expired lease only told a well-behaved holder to stop, and a paused holder could still act on a stale belief, which is why fencing tokens were needed at the resource. Here the expiry is enforced at the resource: the database account stops existing, so a stale holder's credential simply fails. The credential and the lease are the same object, which is exactly the fencing property.

"""Dynamic secrets with leases, on simulated time (no real database)."""
import secrets

class Vault:
    def __init__(self):
        self.now, self.leases, self.db_users = 0, {}, set()
    def issue(self, role, ttl):
        user, pw = f"{role}-{secrets.token_hex(3)}", secrets.token_urlsafe(12)
        lease = secrets.token_hex(4)
        self.db_users.add(user)                         # "CREATE USER ..." in the real database
        self.leases[lease] = {"user": user, "expires": self.now + ttl}
        return lease, user, pw
    def renew(self, lease, ttl):
        if lease in self.leases and self.leases[lease]["expires"] > self.now:
            self.leases[lease]["expires"] = self.now + ttl; return True
        return False
    def revoke(self, lease):
        self.db_users.discard(self.leases.pop(lease)["user"])
    def tick(self, secs):
        self.now += secs
        for lid in [l for l, v in self.leases.items() if v["expires"] <= self.now]:
            self.revoke(lid)                            # expiry removes the credential itself

v = Vault()
l1, u1, _ = v.issue("report", ttl=60)
l2, u2, _ = v.issue("report", ttl=60)
print("two apps get different credentials:", u1 != u2, "| active db users:", len(v.db_users))
v.tick(40); print("t=40 renew app1:", v.renew(l1, 60))
v.tick(30); print("t=70 app1 user alive:", u1 in v.db_users, "| app2 user alive:", u2 in v.db_users)
v.revoke(l1); print("incident: revoke app1's lease -> active db users:", len(v.db_users))
print("renew after expiry/revocation:", v.renew(l2, 60))
two apps get different credentials: True | active db users: 2
t=40 renew app1: True
t=70 app1 user alive: True | app2 user alive: False
incident: revoke app1's lease -> active db users: 0
renew after expiry/revocation: False

The benefits stack up. Each client has its own credentials, so the audit log shows who did what. A leaked credential is valid for minutes. Revoking one client's lease does not disturb the others. There is no shared password to rotate across a fleet. The costs are real: the secret manager is now on the critical path and must be highly available, and the target system must tolerate creating and dropping accounts at the rate you need.

Secrets leaked into git

The most common secret-management incident is mundane: a developer commits a key. Git keeps history, so git rm or deleting the line in a later commit removes it from the current files but not from history, clones, forks or the hosting provider's caches. Bots scan public repositories for credential patterns and can find a freshly pushed key within minutes, so assume that anything pushed to a public repository was copied. The response order is fixed:

  1. Revoke or rotate the secret first, immediately. This is the only step that actually fixes the exposure.
  2. Check logs of the affected service for use of the secret during the exposure window.
  3. Only then clean the history if you need to (history rewriting tools exist), knowing it does not recall copies already made.
  4. Find out how it got there and put a guard in: pre-commit hooks and server-side push protection that block commits matching known credential formats, plus scheduled scanning of the repository history.

Scanners find secrets by two methods: known patterns (cloud access-key prefixes, private-key headers) which are precise, and high-entropy strings which are noisy. The sketch below does both over a pretend commit held in a string; the access key shown is the placeholder that the AWS documentation itself uses in examples, not a real credential.

"""A toy secret scanner over in-memory text (the key below is AWS's published documentation example)."""
import math, re

PATTERNS = {"aws-access-key-id": re.compile(r"\bAKIA[0-9A-Z]{16}\b"),
            "private-key-block": re.compile(r"-----BEGIN [A-Z ]*PRIVATE KEY-----")}

def entropy(s):
    return -sum((s.count(c) / len(s)) * math.log2(s.count(c) / len(s)) for c in set(s))

diff = '''
+ AWS_ACCESS_KEY_ID = "AKIAIOSFODNN7EXAMPLE"
+ DB_URL = "postgres://app:hunter2@db.internal/prod"
+ API_TOKEN = "q8Zr2LkP0vXw93TnB5yHc7DfGa1MsJe4"
+ greeting = "hello world, this is just prose"
'''
for n, line in enumerate(diff.strip().splitlines(), 1):
    for name, rx in PATTERNS.items():
        if rx.search(line): print(f"line {n}: pattern match: {name}")
    for tok in re.findall(r'"([^"]{20,})"', line):
        if " " not in tok and entropy(tok) > 4.0: print(f"line {n}: high-entropy string ({entropy(tok):.1f} bits/char)")
    if re.search(r"://[^/\s:]+:[^@\s]+@", line): print(f"line {n}: credentials embedded in URL")
print("A match in a pushed commit means: revoke and rotate NOW; rewriting history does not un-leak it.")
line 1: pattern match: aws-access-key-id
line 2: high-entropy string (4.1 bits/char)
line 2: credentials embedded in URL
line 3: high-entropy string (5.0 bits/char)
A match in a pushed commit means: revoke and rotate NOW; rewriting history does not un-leak it.

Read the output critically. Line 1 is a precise pattern match. Line 3 is a true positive found only by entropy: a random-looking token with no known prefix. Line 2 is flagged twice for the same string, once by entropy (a false-positive-prone rule: a URL is not random) and once, more usefully, by the embedded-credentials rule. Line 4, plain English, is correctly ignored. And the access-key string on line 1 would have escaped the entropy rule (about 4 bits per character, under the threshold), which is why pattern rules and entropy rules complement each other and neither is complete. Tools such as gitleaks and TruffleHog implement these ideas at scale, and they belong in your pipeline.

Only scan what you own

Secret scanners are for your own repositories, your own CI and systems you are authorised to audit. Using them to hunt for other people's exposed credentials, and above all using any credential you find, is unauthorised access in most jurisdictions even if the key was left in public. If you discover someone else's leaked secret, report it to them.

PKI, one level deeper

In networking chapter 11 you saw that a certificate binds a public key to a name and is signed by a certificate authority (CA) the browser trusts. The public-key infrastructure (PKI) behind that sentence has more moving parts, and each is a place where real incidents happen.

Chains and intermediates

Browsers and operating systems ship a trust store of root CA certificates. A website's certificate (the leaf) is almost never signed by a root directly. Instead, the root signs one or more intermediate CAs, and an intermediate signs leaves. The server sends its leaf plus the intermediates, and the client builds a chain from the leaf up to a root it already trusts, checking at each link the signature, the validity period, the name, and that the issuer was allowed to issue certificates (the basic-constraints and key-usage extensions in the X.509 format, standardised in RFC 5280).

Why the extra layers? The root's private key is the most valuable key in the whole hierarchy, because every certificate under it depends on it, and replacing a root means updating every device's trust store. Keeping it offline (often in an HSM in a vault, switched on only for ceremonies) protects it, while intermediates do the everyday signing. If an intermediate is compromised or mis-issues, you revoke that intermediate without touching the root.

A CA is a single point of trust for many names

A browser trusts every root in its store to vouch for any domain. A CA that is compromised, coerced or careless can issue a valid certificate for a domain it has no business issuing for, and your TLS library will accept it. Real incidents of this kind (for example the 2011 compromise of the DigiNotar CA) are the reason the next two defences exist.

Revocation is harder than it sounds

When a private key leaks, the certificate for it must stop being trusted before its expiry date. There are two classic mechanisms, and both have well-known weaknesses:

  • CRL (certificate revocation list): the CA publishes a signed list of revoked serial numbers. Clients download it. Problems: lists can grow large, clients cache them, and updates are periodic, so there is a window between revocation and the client noticing.
  • OCSP (Online Certificate Status Protocol): the client asks the CA's responder "is certificate X still good?" Problems: it adds latency to every connection; the responder learns which sites you visit (a privacy leak); and, critically, if the responder cannot be reached, clients have to choose between failing the connection and carrying on. Browsers carry on ("soft-fail"), so an attacker who can block the OCSP request defeats the check precisely when it matters.

Mitigations and industry direction: OCSP stapling lets the server fetch a signed, time-stamped OCSP response and attach it to the handshake, removing the privacy and latency problems but only guaranteeing freshness if clients can insist on it ("Must-Staple"). Browsers have also moved to curated, compressed revocation lists pushed to clients. Let's Encrypt, the largest public CA, switched off its OCSP service in 2025 and publishes revocation through CRLs only. Most importantly, the design response is short-lived certificates: if a certificate is valid for days rather than a year, revocation matters less, because the exposure is bounded by expiry anyway. The CA/Browser Forum has voted to reduce the maximum validity of public TLS certificates in stages (from 398 days to 200, 100, and finally 47 days, with the last step scheduled for 2029), which makes automated issuance (the ACME protocol) mandatory in practice. Expiry is a failure you can schedule; automate it so it is never a surprise outage.

Certificate Transparency

Certificate Transparency (CT, RFC 6962; the idea came out of Google in 2011, after the DigiNotar compromise, and RFC 6962 appeared in 2013) answers: "how would a domain owner know a CA mis-issued a certificate for their domain?" CAs submit every certificate they issue to public, append-only logs built on Merkle trees, and receive back a signed promise to include it (an SCT). Chrome and Safari require a certificate to carry proof of logging, and reject one that is not in the logs. Anyone can then run a monitor that watches the logs for certificates for their own domains and raises an alarm on one they did not request.

Note what CT does and does not do. It does not prevent a rogue certificate; it makes it impossible to issue one secretly, turning silent compromise into detectable events. That is the "compromise recording" principle from chapter 2, applied to a whole ecosystem. The Merkle-tree log structure is also why anyone can verify that a log has only ever appended.

mTLS and service identity

In ordinary TLS only the server presents a certificate. In mutual TLS (mTLS) the client presents one too, and the server verifies it. That gives service-to-service calls a cryptographic identity: "this connection is from the billing service", not "this connection came from an address inside our network". Because of it, an authorisation rule can say "only billing may call the ledger", and a compromised host elsewhere in the network cannot speak as billing without its key. This is the basis of the zero-trust designs of chapter 13.

The operational price is certificate management at fleet scale: every workload needs a key and a certificate, issued automatically and rotated frequently (hours or days), or mTLS becomes an outage generator. Service meshes and platforms automate this. The common identity framework is SPIFFE (Secure Production Identity Framework for Everyone, a CNCF project): each workload gets an identity expressed as a URI, such as spiffe://example.org/billing, carried in a short-lived credential called an SVID (as an X.509 certificate or a JWT). SPIRE is the reference implementation that attests the workload (using properties of the node and process rather than a secret baked into an image) before issuing the SVID, which is the "workload identity" answer to the bootstrap problem above.

Analogy: a passport office

A passport (certificate) is useful because a government (CA) vouches for the holder, border officials trust that government, and the document has a photograph (the public key matched by the holder proving possession of the private key). Lost passports are reported (revocation) and every passport expires. Transparency is like a public register of every passport issued, so a country can notice if one was issued in its name.

Where it breaks down: a border official trusts a handful of governments; a browser trusts well over a hundred root CAs for every domain, with no concept of "this CA is only appropriate for these countries" except where name constraints or CAA records are added.

Try it yourself

Inspect a certificate chain with the OpenSSL command-line tool, for a site you are allowed to connect to (a public website is fine: you are making an ordinary TLS connection, not probing it): openssl s_client -connect example.com:443 -showcerts < /dev/null. Count the certificates, look at the subject and issuer of each, and see that the issuer of one is the subject of the next. Then run openssl s_client -connect example.com:443 < /dev/null 2>/dev/null | openssl x509 -noout -dates -subject -issuer to see the validity period of the leaf. Your output will differ from anyone else's. (macOS ships LibreSSL; the commands are the same.) Do not run scanners against hosts you do not own beyond this single handshake.

Distributed systems connection

Key management is distributed state management with a hostile environment. Rotating a key across a fleet is a rolling upgrade with two versions live at once, so formats must be versioned and readers tolerant, as in the evolving-contracts material of the architecture course. Revocation is the distributed problem of telling every node about an event with bounded delay, and short-lived credentials trade that problem for continuous renewal, like leases. A certificate authority is a trusted third party for the many-party problem, and a CT log is an append-only log in the sense of the log-based systems you have already studied.

Key takeaways

  • Keys have a lifecycle: generate, store, use, rotate, revoke, destroy. Weak points are copies, missing audit and forgotten backups.
  • Separate using a key from having it: a KMS or HSM performs operations so key bytes never reach application code or disks.
  • Envelope encryption: a DEK encrypts data locally, a KEK in the KMS wraps the DEK. It gives cheap rotation, small blast radius and deletion by key destruction. Bind DEKs to their owner with an encryption context.
  • Rotate without downtime by naming every key, tagging every ciphertext with the key id, and letting versions coexist: add, switch writers, migrate, retire.
  • Prefer a secret store with workload identity to files, and files to environment variables. Prefer dynamic, leased secrets whose expiry is enforced at the target.
  • A leaked secret is fixed by revoking and rotating, not by rewriting git history. Block commits with scanners, and only scan what you own.
  • PKI: roots stay offline, intermediates sign daily, leaves are short-lived. Revocation by CRL and OCSP is weak, so rely on short lifetimes and automation; Certificate Transparency makes mis-issuance detectable; mTLS and SPIFFE give services cryptographic identity.

Check your understanding

In envelope encryption, an operator rotates the key-encryption key. What must be rewritten to keep every record readable under the new KEK?

  1. All the ciphertext, re-encrypted with the new KEK
  2. Nothing; old records automatically use the new key
  3. Only the wrapped data keys, re-wrapped under the new KEK; the bulk ciphertext is unchanged
  4. The application's source code
The KEK encrypts only the small data keys. Re-wrapping them is cheap and leaves the bulk data alone. (If a data key itself might have leaked, you would have to re-encrypt the data with fresh keys.)

A developer pushes an API key to a public repository, notices a minute later, and force-pushes a commit that removes it. What is the correct assessment?

  1. Safe: the key is gone from the repository
  2. Still exposed: automated scanners and clones may already have it, so the key must be revoked and rotated now
  3. Safe if the repository is made private afterwards
  4. Safe if the key is rotated next quarter
Assume anything pushed publicly was copied within moments. Rewriting history does not recall copies. Revoke and rotate immediately, then check logs for misuse, then add guards.

Why is soft-fail OCSP a weak defence against a stolen certificate key?

  1. OCSP responses are not signed
  2. OCSP only works for root certificates
  3. Revocation never takes effect on any CA
  4. An attacker who can block the OCSP request makes the client proceed as if the certificate were good
If failure to reach the responder is treated as success, the attacker who holds the stolen key and sits on the network path can simply suppress the check. Short-lived certificates and stapling avoid depending on that query.

What does Certificate Transparency achieve?

  1. It makes secret mis-issuance of a certificate detectable, because certificates must be recorded in public append-only logs that domain owners can monitor
  2. It prevents any CA from issuing a certificate for the wrong domain
  3. It encrypts certificates in transit
  4. It replaces the need for revocation
CT is detection, not prevention: a rogue certificate can still be issued, but it cannot be issued unseen. Revocation and short lifetimes are still needed to limit the damage afterwards.

How does a Vault-style dynamic secret differ from a leased lock as described in distributed chapter 4?

  1. It has no expiry
  2. It is never renewed
  3. Expiry is enforced at the resource itself (the database account is deleted), so a stale holder's credential fails without needing a separate fencing check
  4. It requires synchronised clocks on every client
With a plain lease a paused holder can still act on stale belief, hence fencing tokens. When the credential is the lease, and the target removes it on expiry, the resource itself rejects the stale holder.

A workload needs credentials to call the secret store, but storing them in the image would just move the secret problem. What resolves this?

  1. Encoding the secret in base64
  2. Workload identity: the platform attests the workload and issues a short-lived proof the secret store accepts, so no long-lived secret is baked in
  3. Putting the secret in an environment variable instead
  4. Using the same secret for every service
Base64 is encoding, and an environment variable is still a stored secret. Platform-issued, attested, short-lived identities (cloud instance identity, Kubernetes service accounts, SPIFFE) remove the long-lived bootstrap secret.

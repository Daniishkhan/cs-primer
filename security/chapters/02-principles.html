Security Design Principles

In 1975 Jerome Saltzer and Michael Schroeder wrote down eight design principles for protection mechanisms. Half a century later they still explain why most systems fail and how most good ones are built. This chapter walks through each with modern examples, then adds the working vocabulary of today: defence in depth, the trusted computing base, secure by default and attack surface reduction.

Why this matters

You will never have a complete list of attacks, because attackers invent new ones. Principles are what remains useful when the list runs out. When a design review meets a component nobody has seen before, the question "does it fail closed? does it check every access? how much of it must we trust?" gets you most of the way to an answer.

The source: "The Protection of Information in Computer Systems"

Saltzer and Schroeder's 1975 paper, "The Protection of Information in Computer Systems" (Proceedings of the IEEE), was written about the Multics operating system, long before the web. They list eight principles that they say are "useful" for the design of protection mechanisms, and note that none is a guarantee: they are rules of thumb distilled from experience with systems that failed. We take them in turn. Pay attention to a theme running through all of them: keep the part you must get right small, simple and checked every time.

The eight principles

1. Economy of mechanism

Keep the design as simple and small as possible. A security mechanism has to be inspected completely to be trusted, and every extra feature is more code that can contain an error. This is the security form of the "deep module" idea in architecture chapter 2: a small interface hiding a lot of work is easier to get right than a large one. Modern example: a service that authenticates via one well-reviewed library at its edge is easier to audit than twelve services that each parse tokens their own way. Another: the OpenSSL Heartbleed bug (case study 1) lived in the TLS heartbeat extension, a feature that few deployments needed.

2. Fail-safe defaults

Base access decisions on permission rather than exclusion: the default is no access, and a mistake in the design should deny, not grant. A list of "banned things" fails open the first time you forget one entry; a list of "allowed things" fails closed. Modern examples: a firewall with a default-deny rule; a new IAM role that has no permissions until granted; a feature flag service that, when unreachable, returns the safe value. The same applies to error handling: if the authorisation service times out, the correct answer is "no". The demonstration at the end of this section runs both versions.

3. Complete mediation

Every access to every object must be checked for authority, every time. Not "checked at login", not "checked the first time and cached". The risk is a path that bypasses the check, or a stale decision. Modern examples: an API where the web UI enforces permissions but a direct call to the same endpoint does not (the most common authorisation bug of all, covered in chapter 8); a download link that works forever after the user's access was revoked; a cache that remembers "alice may read this" after the share was removed. Complete mediation is why architectures funnel access through one reference monitor: a component that sees every access, cannot be bypassed and is small enough to verify.

4. Open design

The design should not depend on the attacker's ignorance of how it works. Only the keys should be secret. This is Kerckhoffs's principle from 19th-century cryptography, and it is why we use published algorithms such as AES and Ed25519, subjected to years of public attack, instead of private ones. Modern example: the TLS protocol is public down to the last byte; its security rests entirely on keys. "Security through obscurity", such as a secret URL as the only protection for an admin page, can be a fine extra layer but is a poor foundation. The parallel in architecture chapter 2 is information hiding: you hide the implementation behind an interface so callers do not depend on it, but the interface itself is open and documented. In security, the open part is the mechanism and the hidden part is the key.

5. Separation of privilege

A system that needs two independent conditions to grant access is more robust than one that needs one: no single mistake, key or person is enough. Modern examples: multi-factor authentication (a password and a hardware key); a production deploy that needs both a passing pipeline and a second reviewer; a signing key split among several custodians so no one holds all of it; an encrypted backup whose key is stored somewhere different from the backup. The conditions must be independent: two passwords that are both sent over the same phishing page are one factor in practice.

6. Least privilege

Every program and every user should operate with the smallest set of permissions needed for the job. The aim is to bound the damage when a component is compromised, since compromise is a matter of when. Modern examples: a web server process that cannot write to its own code directory; a cloud role for the image worker that can write to one bucket prefix and nothing else; a database account for the application that cannot drop tables; a container with no extra Linux capabilities (systems chapter 19). Least privilege also applies in time: a credential valid for fifteen minutes limits what a thief can do, which is the idea behind the leases of distributed chapter 4 applied to access.

7. Least common mechanism

Minimise the mechanisms shared among users or components, because every shared channel is a possible path for leakage or interference. Modern examples: giving each tenant its own database schema or encryption key (chapter 15) rather than a shared table with a tenant-id column that one buggy query forgets to filter; a shared cache that can leak entries across users; a shared kernel under containers, which is why untrusted code often gets a VM instead. The principle conflicts with efficiency, which loves sharing, and the trade-off is explicit: pooling lowers cost and raises blast radius.

8. Psychological acceptability

If the security mechanism is hard to use, people will bypass it, so the human interface must be easy to use correctly and the protection model should match the user's mental model. Modern examples: a password policy requiring monthly changes and symbols leads to Summer2026!; a certificate warning that appears so often that users click through it; a deploy process so slow that engineers share a single admin credential to avoid it. Passkeys (chapter 5) aim to make the secure path the quicker one too. When you add a control, count the people who will experience it as friction and ask what they will do instead.

Saltzer and Schroeder also list two principles they considered less rigid, work factor (compare the attacker's cost of breaking the mechanism with the resources available to them) and compromise recording (it is sometimes better to detect and log a break-in than to prevent it). The second is the seed of the detection and audit-log material in chapter 18.

Seeing fail-safe defaults and complete mediation in code

The program below contains two bugs that real systems ship. First, an authorisation check that "fails open" when its policy service is unreachable. Second, a cache of decisions that outlives a revocation.

"""Fail-safe defaults and complete mediation in miniature."""

GRANTS = {("alice", "report-7"): {"read"}, ("bob", "report-7"): {"read", "write"}}

def policy_lookup(user, obj):
    if user == "carol":
        raise TimeoutError("policy service unreachable")       # the dependency fails
    return GRANTS.get((user, obj), set())

def allowed_fail_open(user, obj, action):
    try:
        return action in policy_lookup(user, obj)
    except Exception:
        return True                                            # "don't break the app": the bug

def allowed_fail_closed(user, obj, action):
    try:
        return action in policy_lookup(user, obj)
    except Exception:
        return False                                           # default is deny

print("request                     fail-open  fail-closed")
for user, action in [("alice", "read"), ("alice", "write"), ("mallory", "read"), ("carol", "write")]:
    print(f"{user:<8}{action:<6}report-7      {allowed_fail_open(user, 'report-7', action)!s:<10} {allowed_fail_closed(user, 'report-7', action)}")

# Complete mediation: caching a decision means later requests skip the check.
class Mediator:
    def __init__(self): self.cache = {}
    def check_cached(self, user, obj, action):
        key = (user, obj, action)
        if key not in self.cache:
            self.cache[key] = action in policy_lookup(user, obj)
        return self.cache[key]
    def check_every_time(self, user, obj, action):
        return action in policy_lookup(user, obj)

m = Mediator()
print("\nbob writes (first time):          cached =", m.check_cached("bob", "report-7", "write"))
GRANTS[("bob", "report-7")] = {"read"}                        # bob's write access is revoked
print("after revocation, cached check:   ", m.check_cached("bob", "report-7", "write"), " <- stale decision")
print("after revocation, every-time check:", m.check_every_time("bob", "report-7", "write"))
request                     fail-open  fail-closed
alice   read  report-7      True       True
alice   write report-7      False      False
mallory read  report-7      False      False
carol   write report-7      True       False

bob writes (first time):          cached = True
after revocation, cached check:    True  <- stale decision
after revocation, every-time check: False

Look at the carol row: when the policy service fails, the fail-open version lets her write; the fail-closed version denies her. The usual argument for fail-open is "we do not want an outage because the policy service is down". The better answer is to make the policy lookup highly available, or to degrade safely (read-only access to cached public data) rather than grant everything. The last three lines show a stale decision: after Bob's write access is revoked, the cached check still says yes. If you must cache, give decisions a short lifetime and a way to invalidate them, and understand that the window is a trade-off you chose.

"Fail-safe" is not always "fail-closed"

For authorisation, the safe state is to deny. For a hospital door, a fire exit or an emergency stop, the safe state is to open. The principle is "fail to the state that is safe for the thing you protect", and you must decide what that is for each failure. A system can also fail unsafe in the other direction: a security service that fails closed and blocks all logins during an incident is an availability failure that an attacker may deliberately trigger.

Defence in depth

No single control is perfect, so we stack independent ones so that the failure of one is not the failure of the system. Defence in depth is the practice of layering controls so that an attacker must defeat several different mechanisms in sequence. The image used by safety engineers is slices of Swiss cheese: each slice has holes, but if the holes are in different places, a straight-line path through all of them is unlikely.

Concretely, the photo-upload feature of chapter 1 had: size limits and rate limits at the edge; authentication; an ownership check; header validation; a sandboxed decoder; an unprivileged storage credential. The attacker who finds a decoder bug still runs inside the sandbox with credentials that can write only one object path. That is depth.

Analogy: a castle

Moat, outer wall, inner wall, keep, and a guard at the treasury door. An attacker who crosses the moat has not won; each layer buys time to notice and respond.

Where it breaks down: a castle's layers are separate in space. Software layers often share a single point of failure, such as one library that parses input for all of them, or one administrator credential that bypasses them all. Then the layers are not independent, and the depth is only apparent.

The trusted computing base

The trusted computing base (TCB) is the set of hardware, firmware and software that must function correctly for the system's security policy to hold. If something in the TCB is wrong, the policy can be violated; if something outside it is wrong, the policy still holds, because the TCB constrains it. The consequence is practical: make the TCB small, and know exactly what is in it.

For a program, the TCB includes the operating system kernel, the language runtime, the libraries that parse untrusted input, and the build system that produced the binary (chapter 12 on the supply chain). For a container, it includes the host kernel: this is why a container is a weaker boundary than a virtual machine, whose TCB is the much smaller hypervisor (systems chapter 19). For a key management service (chapter 4), a deliberately tiny hardware module holds the master key so that the rest of the fleet need not be trusted with it. Whenever you design a boundary, ask: "what is on the trusted side, and could it be smaller?"

Secure by default, and shrinking the attack surface

Secure by default means the out-of-the-box configuration is the safe one and it takes deliberate action to weaken it. Most people never change defaults, so the default is the product's security posture. Examples: a database that listens only on localhost until configured otherwise; a new storage bucket that is private; cookies that are HttpOnly and Secure unless a developer opts out; an admin interface disabled until enabled; no default password, with first-run forcing the user to set one. Secure-by-default is the fail-safe-defaults principle applied to products and configuration.

Attack surface reduction is removing entry points rather than defending them. Every one you remove is gone for every future attacker and needs no monitoring. In practice:

  • Remove unused features, endpoints, accounts, ports and dependencies. A dependency you do not import cannot have a vulnerability.
  • Restrict what remains: bind internal services to private interfaces, require authentication for everything by default, expose admin tools only through a bastion or identity-aware proxy.
  • Narrow inputs: accept a small, strict format (an enum, an integer in a range) instead of free text; avoid features that interpret user input as code, templates or paths.
  • Minimise data: data you never collected cannot be stolen. This is attack surface reduction for assets (chapter 17).

Earlier courses made a similar point about complexity: the cheapest component to secure, like the cheapest to operate, is the one that does not exist.

Common misconception: "defence in depth means adding more tools"

Buying a fifth scanner does not add a layer if all five look at the same traffic with the same blind spot. Depth means different kinds of control (prevent, limit blast radius, detect, recover) at different places. Also note that more layers means more complexity, which cuts against economy of mechanism. The principles pull in different directions, and design is the judgement between them.

Putting the principles together: a review lens

PrincipleQuestion to ask in a design review
Economy of mechanismIs there a simpler way? How many places implement this check?
Fail-safe defaultsWhat happens on error, timeout, missing config or an unknown input?
Complete mediationIs there any path to the data that skips the check? Is anything cached?
Open designIf the attacker has the source and the architecture diagram, what stops them? (Answer: keys.)
Separation of privilegeIs any single credential or person enough to do something catastrophic?
Least privilegeWhat can this component do that it does not need to?
Least common mechanismWhat is shared between tenants or components, and can it leak?
Psychological acceptabilityWill people use this correctly, or work around it?

Distributed systems connection

Each principle has a distributed echo. Least privilege and short leases: credentials that expire, like the leases of distributed chapter 4. Complete mediation: authorising each request at each service rather than trusting "it came from inside" (zero trust, chapter 13). Least common mechanism: shared consensus or caching services become shared fate. And architecture chapter 8's advice to enforce security "at the boundaries" is complete mediation plus a small TCB: put the check in one well-placed component, not scattered across services.

Key takeaways

  • Saltzer and Schroeder (1975): economy of mechanism, fail-safe defaults, complete mediation, open design, separation of privilege, least privilege, least common mechanism, psychological acceptability.
  • Small and simple wins: the part you must get right should be small enough to inspect completely.
  • Default to deny, check every access every time, and be suspicious of caches of authorisation decisions.
  • Only keys are secret; the design should survive the attacker reading it.
  • Defence in depth needs independent layers; two controls with a common failure are one control.
  • The trusted computing base is everything you must trust: shrink it and know what is in it.
  • Prefer removing attack surface to defending it, and make the safe configuration the default one.

Check your understanding

An authorisation service times out. The application catches the error and lets the request through "so users aren't blocked". Which principle does this violate?

  1. Open design
  2. Least common mechanism
  3. Fail-safe defaults
  4. Psychological acceptability
When the check cannot be completed, the safe default is to deny. Failing open turns any outage (or an attacker who causes one) into a bypass. The real fix is to make the policy service reliable, not to skip it.

A web UI hides the "Delete" button from non-admins, but the DELETE endpoint itself only checks that the caller is logged in. Which principle is violated?

  1. Complete mediation
  2. Economy of mechanism
  3. Separation of privilege
  4. Open design
The access to the object (the delete) is not checked on every path; the UI check is bypassed by calling the API directly. Authorisation must be enforced where the action happens, not where it is displayed.

Two "factors" for login are a password and a security question, both entered on the same page. Why is this weaker than it appears?

  1. Security questions are encrypted
  2. Passwords are always short
  3. Users cannot remember both
  4. Both can be captured by the same phishing page, so the conditions are not independent and add little separation of privilege
Separation of privilege works when conditions fail independently. Two secrets typed into the same form share one failure mode. A hardware key that signs a challenge for the true site does not.

Why is a container generally a weaker isolation boundary than a virtual machine?

  1. Containers cannot limit memory
  2. Containers share the host kernel, so the trusted computing base for isolation is the whole kernel, a much larger attack surface than a hypervisor
  3. Containers do not use network namespaces
  4. VMs do not need an operating system
The TCB of a container boundary includes the entire shared kernel interface. A VM's guest kernel is separate; the layer between guests and host is a smaller hypervisor. That is the economy-of-mechanism argument.

A team adds four overlapping vulnerability scanners that all examine the same dependency list. What is wrong with calling this "defence in depth"?

  1. Scanners are never useful
  2. It lowers availability
  3. The layers share the same blind spot and are not independent; depth needs different kinds of control at different points (prevent, contain, detect, recover)
  4. Nothing; more tools is always more depth
If every layer misses the same thing, the layers fail together. Add controls that fail differently: a sandbox, least-privilege credentials, runtime detection.

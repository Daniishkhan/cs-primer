Network Security & Zero Trust

For decades the standard picture of security was a castle: a hard outer wall (the firewall), a soft and trusted inside. This chapter explains why that picture fails the moment one machine inside is compromised, what segmentation does about it, and what "zero trust" actually means: not a product, but the rule that every request is decided on identity, device and context, whatever network it came from.

Why this matters

Most serious intrusions are not one dramatic break-in but a walk: an attacker lands on one low-value machine (a phished laptop, a vulnerable web server, a leaked credential) and then moves sideways until something valuable is in reach. Whether that walk is easy or impossible is a property of your network and identity design, not of any single bug. In a distributed system with hundreds of services, "everything inside the network can talk to everything else" is the default, and it is the design you must consciously replace.

The perimeter model and why it fails

The perimeter model divides the world into an untrusted outside and a trusted inside, separated by a firewall and, for remote staff, a VPN (virtual private network: an encrypted tunnel that makes a remote laptop look as if it were plugged into the office network). Behind the wall, machines trust each other because of where they are: an internal IP address is treated as evidence of legitimacy. You met the building blocks (firewalls, NAT, private address ranges) in the networking course; here we ask what they promise about security.

The weakness is structural:

  • Lateral movement. Once an attacker controls any inside host, the "trusted" network is a flat map of targets. They scan, reuse stolen credentials, and pivot from host to host. The perimeter did its job (the attacker is on the inside) and now provides no further protection. This is the failure mode behind the incidents in chapter 18 and the Equifax case.
  • The VPN is all-or-nothing. A classic VPN authenticates a user once and then grants network-level reachability to a whole range of addresses. It does not ask whether the laptop is patched, whether this user needs the payroll database, or whether this request looks like the user's normal behaviour. It also concentrates risk: the VPN gateway is an internet-facing device whose compromise opens everything behind it.
  • There is no longer a single inside. Staff work from homes and cafés, services run in several clouds, vendors need access, and SaaS products hold company data. "The corporate network" is no longer where the assets are.
  • Insiders and stolen credentials are already inside. A malicious employee, or an attacker using a legitimate employee's credentials, passes every perimeter check by definition.

None of this makes firewalls useless. They are cheap, fast and effective against a large class of noise and mistakes (an exposed database port, for example). The error is treating them as sufficient: this is the "hard shell, soft centre" design that the principle of defence in depth, from chapter 2, warns against.

Segmentation and micro-segmentation

Network segmentation divides the network into zones and allows traffic between zones only where the application needs it. Micro-segmentation is the same idea taken to the limit: the unit of isolation is a workload (a service, a pod), not a subnet. The aim is not to prevent the first compromise but to make the walk from it expensive.

The same default-deny rule appears at several layers, with different strengths:

MechanismUnit it controlsNotes
Network firewall / VLAN / subnet ACLAddress ranges between zonesCoarse. Good for "the internet may not reach the database subnet". Rules refer to addresses, which change.
Cloud security groupVirtual machines or network interfacesStateful allow-lists attached to instances; a rule can name another security group as the source ("the API tier may reach the database tier") instead of addresses. Default for inbound traffic is deny.
Kubernetes NetworkPolicyPods, selected by labelPods are open to all traffic by default. Policies add restrictions, and are only enforced if the cluster's network plugin implements them.
Service mesh authorization (below)Service identities and requestsWorks at the application layer: can say which identity may call which method.

A Kubernetes example, illustrative (you need a cluster whose network plugin enforces policies; see the orchestration material in reliability chapter 14). The first policy selects every pod in a namespace and allows nothing; the second then opens exactly one path:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: shop
spec:
  podSelector: {}
  policyTypes:
    - Ingress
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: orders-db-from-api
  namespace: shop
spec:
  podSelector:
    matchLabels:
      app: orders-db
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: api
      ports:
        - protocol: TCP
          port: 5432

Policies are additive: once any policy selects a pod for ingress, only traffic that some policy allows is permitted. This is fail-safe defaults in practice. Segmentation also has limits worth stating plainly. Rules are written in terms of labels and addresses, which prove nothing about who is really sending (a compromised pod labelled app: api passes). They can drift from reality as the application changes, so they must be generated or tested rather than hand-maintained. And they decide at the network layer: they cannot say "this caller may read but not delete". That needs identity.

Here is the effect in a runnable model. A flat network lets a compromised web host talk to every service; a segmented one lets it talk only to the two services the application needs. The second half of the program is a first taste of the next section: a decision function that weighs identity, device and context.

"""Zero trust in miniature: a flat network vs a segmented one, and a per-request decision. In-process only."""
from dataclasses import dataclass

# ---------- 1. Lateral movement: which services can an attacker reach after compromising 'web'? ----------
SERVICES = ["web", "api", "orders-db", "billing", "admin-ui", "metrics"]
# Edges the application actually needs (caller -> callee):
NEEDED = {("web", "api"), ("api", "orders-db"), ("api", "billing"), ("web", "metrics"), ("api", "metrics")}

def reachable(start, allowed):
    seen, todo = {start}, [start]
    while todo:
        cur = todo.pop()
        for a, b in sorted(allowed):
            if a == cur and b not in seen:
                seen.add(b); todo.append(b)
    return seen

def first_hop(start, allowed):                  # what can the attacker TALK to from the compromised host?
    return sorted(b for a, b in allowed if a == start)

flat = {(a, b) for a in SERVICES for b in SERVICES if a != b}      # 'trusted internal network'
print("flat network, from web      :", first_hop("web", flat))
print("segmented (NEEDED only)     :", first_hop("web", NEEDED))
print("segmented, if api also falls:", sorted(reachable("web", NEEDED) - {"web"}), "(each further hop needs a new compromise)")

# ---------- 2. Per-request decision: identity + device posture + context ----------
@dataclass
class Request:
    user: str; groups: set; mfa: bool          # identity
    device_managed: bool; disk_encrypted: bool; patched: bool   # device posture
    resource: str; sensitivity: int; country: str; hour: int    # context

POLICY = {"payroll": {"group": "finance", "min_level": 2}, "wiki": {"group": "staff", "min_level": 0}}

def level(r):                                   # how much do we trust this device/session?
    lv = 0
    if r.device_managed and r.disk_encrypted and r.patched: lv = 2
    elif r.device_managed: lv = 1
    return lv

def decide(r):                                  # the Policy Decision Point: returns (decision, reason)
    p = POLICY.get(r.resource)
    if p is None: return "DENY", "unknown resource (default deny)"
    if p["group"] not in r.groups: return "DENY", f"not in group {p['group']}"
    if r.sensitivity >= 2 and not r.mfa: return "STEP-UP", "sensitive resource needs fresh MFA"
    if level(r) < p["min_level"]: return "DENY", f"device level {level(r)} < required {p['min_level']}"
    if r.sensitivity >= 2 and r.country not in {"GB", "US"}: return "STEP-UP", "unusual location"
    return "ALLOW", "identity, device and context all pass"

base = dict(user="ana", groups={"staff", "finance"}, mfa=True, device_managed=True, disk_encrypted=True,
            patched=True, resource="payroll", sensitivity=2, country="GB", hour=10)
cases = [("healthy laptop", {}), ("same user, unpatched laptop", {"patched": False}),
         ("same user, no MFA", {"mfa": False}), ("same user, unmanaged phone", {"device_managed": False}),
         ("same user, new country", {"country": "ZZ"}), ("wiki from unpatched laptop", {"resource": "wiki", "sensitivity": 0, "patched": False})]
print()
for name, over in cases:
    d, why = decide(Request(**{**base, **over}))
    print(f"{name:30} -> {d:7} {why}")

segmented (NEEDED only)     : ['api', 'metrics']
segmented, if api also falls: ['api', 'billing', 'metrics', 'orders-db'] (each further hop needs a new compromise)

healthy laptop                 -> ALLOW   identity, device and context all pass
same user, unpatched laptop    -> DENY    device level 1 < required 2
same user, no MFA              -> STEP-UP sensitive resource needs fresh MFA
same user, unmanaged phone     -> DENY    device level 0 < required 2
same user, new country         -> STEP-UP unusual location
wiki from unpatched laptop     -> ALLOW   identity, device and context all pass

Zero trust: the principles

Zero trust is the name for the response to all of this. The reference document is NIST Special Publication 800-207, Zero Trust Architecture (August 2020). Its core idea is that no request is trusted because of the network it came from or the asset it came from; each access is authenticated and authorized before it is allowed. In engineering terms, a zero trust design has these properties:

  • Per-request decisions. Access is granted to one resource, for one session, rather than to a network. Being "on the VPN" or "in the office" is not a credential.
  • Identity, device posture and context together. The decision combines who (user or service identity, with strong authentication, see chapter 5), what device (managed? disk encrypted? patched?) and context (resource sensitivity, location, time, behaviour). The Python model above shows exactly this.
  • Least privilege and default deny (chapter 2), re-evaluated as signals change. A session can be cut short when a laptop falls out of compliance.
  • Assume breach. Design as though some component is already compromised: segment, log every access, and keep credentials short-lived.
  • Protect every channel. Traffic is encrypted and authenticated on the internal network too, because the internal network is not trusted.

The architecture in the NIST document separates two roles. The policy decision point (PDP) decides: a policy engine evaluates the policy and a policy administrator sets up or tears down the session. The policy enforcement point (PEP) sits in the path of the traffic and obeys: it allows or blocks. Separating them means policy lives in one reviewable place, while enforcement is a thin, fast component that can be deployed everywhere. You already saw this split as the policy engine versus the gateway or service in chapter 8.

A common concrete form is the identity-aware proxy (IAP): a reverse proxy in front of an application that authenticates the user (through the identity provider, using the protocols of chapter 7), checks the device, asks the decision point, and only then forwards the request. The application is not reachable from the internet at all, so there is no VPN to tunnel through and no network position to abuse. Because the proxy receives the identity assertion, it can also pass it to the application as a signed header or token, which the application must verify rather than trust blindly (otherwise anything that reaches the application directly can forge it).

Common misconception: "zero trust means trusting nothing, or buying a product"

Zero trust is an architectural stance, not a product category, and it does not mean "never trust anyone". Something must be trusted: the identity provider, the device-management system, the policy engine. The point is to replace implicit trust from network location with explicit, minimal, continuously checked trust in a small number of well-protected components. It is also a journey: most organisations move application by application, and a half-migrated environment still has a perimeter for the rest.

BeyondCorp: zero trust at scale

The best-documented large deployment is Google's BeyondCorp, described by Ward and Beyer in ;login: in 2014. Google moved employee access to internal applications off the privileged corporate network: every application is reached through an access proxy, and access decisions use the user's identity together with an inventory of the specific device and its state, with different trust levels for different applications. The corporate network became just another untrusted network, no more privileged than a café. The BeyondCorp case walks through the design and the migration, which took years; the engineering lesson is that the hard part is not the proxy but the inventory (an accurate, trusted record of users, groups and devices) and the gradual rollout.

Service identity: mTLS and SPIFFE

People are one half of the problem; services are the other, and there are far more of them. How does the payments service know that a request really comes from orders and not from a compromised neighbour on the same network? Source IP addresses are a poor answer, since pods and instances come and go and addresses are reused. The better answer is a cryptographic identity for each workload.

Recall from chapter 4 that in mutual TLS (mTLS) both sides present certificates, so each end proves who it is. The remaining question is how thousands of short-lived workloads get certificates without human involvement. SPIFFE (Secure Production Identity Framework for Everyone, a CNCF project) standardises the answer:

  • A workload identity is a SPIFFE ID, a URI such as spiffe://example.org/ns/shop/sa/orders. The first part, example.org, is the trust domain.
  • The identity is carried in a SVID (SPIFFE Verifiable Identity Document): an X.509 certificate with the ID in its subject alternative name, or a JWT.
  • SPIRE is the reference implementation. It performs attestation: an agent on each node checks facts about a workload (which node, which Kubernetes service account) and only then asks the server to issue it an SVID. Certificates are short-lived and rotated automatically, so a stolen one soon expires (compare the temporary credentials in chapter 14).

A service mesh (Istio, Linkerd and similar) packages this. A proxy, usually a sidecar container next to each workload (some meshes now offer sidecar-free modes), terminates mTLS on the application's behalf, so application code is unchanged. The mesh's control plane distributes certificates and policy, and it adds authorization rules in terms of identities: "orders may call POST /charge on payments". Meshes add retries, timeouts and observability too (the resilience patterns of architecture chapter 17).

Be precise about what this buys. mTLS gives authenticated, encrypted hops between workloads and a strong identity to write policy against. It does not make the application logic correct, does not authorize end users by itself (the original user's identity still has to be propagated, see the confused deputy in chapter 8), and it moves trust into the mesh's CA and control plane, which are now very high-value targets. It also adds operational cost: another layer to run, upgrade and debug.

Egress control

Defenders spend most effort on traffic coming in, but a compromised workload almost always needs to call out: to download tools, to reach a command-and-control server, to send stolen data. Egress control restricts outbound traffic, and it pays three dividends:

  • It limits exfiltration and callbacks. A service that may only reach its database and two named APIs cannot ship data to an arbitrary host.
  • It blunts SSRF. If an attacker tricks a server into fetching a URL (chapter 11), a deny-by-default egress policy can stop requests to internal addresses and the cloud metadata endpoint.
  • It surfaces surprises. A blocked connection to an unknown host is a high-quality detection signal (chapter 18).

Practical forms: default-deny egress in security groups and NetworkPolicy (remember to allow DNS and your real dependencies explicitly), a forward proxy that allows only listed domains, and DNS filtering. Caveats: allow-listing by domain is imperfect when the allowed domain is a general-purpose cloud service that an attacker can also use, and a strict policy needs a process for adding legitimate destinations or developers will route around it.

Bastions versus just-in-time access

Administrators still need to reach servers. A bastion host (jump box) is a hardened, internet-reachable machine that is the only entry point to a private network: admins connect to it, then onward. It is better than exposing every server, but it has typical weaknesses: long-lived SSH keys that are copied around and never rotated, shared accounts that make audit meaningless, and a permanent door that must be patched and watched, with broad reach once you are through it.

Just-in-time access (JIT) replaces standing access with temporary, narrowly scoped, approved access. An engineer requests access to one system for a stated reason; after approval (automatic for low risk, human for high risk) they receive a credential that expires in minutes or hours: for example a short-lived SSH certificate signed by an internal CA (chapter 4), or an identity-aware proxy session that is recorded. When the time ends, the access disappears without anyone remembering to revoke it. Combined with the per-request decisions above, "who can reach production right now?" has a short, auditable answer. The trade-off is friction in an incident, so mature systems add a documented break-glass path that is loud, logged and reviewed afterwards.

Analogy: the office building

The perimeter model is a building with a guard at the front door and no locks inside: once you have a visitor badge you can walk into the server room. Zero trust puts a badge reader on every door that checks who you are, whether your badge has been reported lost, and whether you have a reason to be here today, and logs each swipe. Just-in-time access is a badge that opens the server room for an hour after a manager approves it.

Where it breaks down: a door checks only a badge, but a service call can be forged, replayed or relayed by a confused deputy, and a building does not have thousands of doors opening and closing every second, so the checks must be fast enough to run on every request.

Only test what you own or are authorised to test

Port scanners and network mapping tools show you what is reachable, and they are a legitimate way to verify that segmentation rules do what you intend. Run them only against networks and clusters you own or have written permission to test. Scanning someone else's network is, at best, against their terms and, at worst, a crime.

Try it yourself

Run zt_pdp.py. Add a rule so that requests for payroll outside working hours (the hour field is unused) return STEP-UP, then add a new resource with its own required device level. Next, extend the segmentation model: add a reporting service that reads from orders-db, work out which edges it needs, and check what an attacker on web can now reach after compromising api. Finally, if you have a local Kubernetes cluster, apply the default-deny policy above in a throwaway namespace and watch connections between your own test pods fail until you add an allow rule.

Distributed systems connection

A zero trust control plane is a distributed system with a hard availability requirement: every request depends on a decision, so the PDP must be fast, replicated and cached, which brings back staleness problems like the revocation window and the new-enemy problem of chapter 8. The decision on a failed PDP (fail closed or fail open) is an explicit design choice. Short-lived certificates turn the CA into a service with a rate and an SLO, and the blast-radius thinking of the reliability course is exactly what segmentation applies to security: shrink the set of things any one failure or compromise can reach.

Key takeaways

  • The perimeter model trusts the inside. One compromised host then enables lateral movement, and a classic VPN grants network-wide reach after a single check.
  • Segmentation (firewalls, security groups, Kubernetes NetworkPolicy) limits which services can talk to which, using default deny. It shrinks blast radius but proves nothing about who is really calling.
  • Zero trust (NIST SP 800-207): decide every request on identity, device posture and context; assume breach; apply least privilege. It is a design stance, not a product.
  • A policy decision point decides and a policy enforcement point obeys. An identity-aware proxy is a typical enforcement point that makes an application unreachable except through a checked path.
  • Workloads need cryptographic identities too: mTLS with short-lived certificates (SPIFFE IDs and SVIDs, issued by attestation) and service meshes that enforce identity-based policy. The CA and control plane become critical assets.
  • Control egress as well as ingress, to limit exfiltration, callbacks and SSRF.
  • Prefer just-in-time, expiring, audited access to standing bastion access, with a loud break-glass path for emergencies.

Check your understanding

An attacker compromises one internal web server. Which design most directly limits what they can reach next?

  1. A stronger firewall at the edge of the corporate network
  2. Default-deny segmentation so the web server can talk only to the services it needs, plus authentication between services
  3. Making the VPN require a longer password
  4. Hiding internal IP addresses
The attacker is already past the edge, so the edge firewall and the VPN login are irrelevant. Limiting lateral movement requires controls between internal services. Hiding addresses is obscurity, not control.

In NIST's zero trust architecture, what is the difference between the policy decision point and the policy enforcement point?

  1. The PDP encrypts traffic and the PEP stores keys
  2. They are the same box with two names
  3. The PEP writes the policy and the PDP audits it
  4. The PDP evaluates policy and decides whether a request may proceed; the PEP sits in the traffic path and allows or blocks accordingly
Separating decision from enforcement keeps policy in one reviewable place and makes enforcement a simple, deployable-everywhere component.

A cluster has no NetworkPolicy objects. What is the default for pod-to-pod traffic, and what does adding a single allow policy for the database do on its own?

  1. Pods can reach each other freely by default; a policy selecting the database pods for ingress then permits only what policies allow for those pods, though other pods are still open unless they are selected too
  2. All traffic is denied by default, so the allow policy is unnecessary
  3. All traffic is denied everywhere once any policy exists
  4. Policies are always enforced even if the network plugin does not support them
Kubernetes pods are open by default. Policies are selective and additive per pod, which is why a default-deny policy that selects all pods is the usual first step. Enforcement also depends on the network plugin.

Why is a source IP address a weak basis for deciding that a request comes from the orders service?

  1. IP addresses are always encrypted
  2. IPv4 addresses are too short
  3. Addresses are reassigned as workloads come and go, and anything that obtains or shares an address inherits its trust; a cryptographic workload identity proves who the caller is
  4. Firewalls cannot read IP addresses
Address-based rules say where traffic comes from, not who sent it. SPIFFE-style identities with mTLS bind a verifiable name to the connection.

Why can default-deny egress help even against an SSRF bug in your service?

  1. It encrypts the vulnerable request
  2. The server's outbound request to an internal address or the metadata endpoint can be blocked even though the application was tricked into making it
  3. It removes the need to validate user-supplied URLs
  4. It makes the service stateless
Egress policy is a second layer: validation in the application should still happen, but when it fails, the network refuses the dangerous destination. It does not replace input validation.

What are two problems with a traditional bastion host that just-in-time access addresses?

  1. Bastions are slow and JIT is faster
  2. Bastions cannot log in and JIT can
  3. Standing access with long-lived, shared keys that are hard to audit and revoke; JIT uses approved, expiring, per-person credentials
  4. Bastions use TLS and JIT does not
The problem is persistent, broad, shared access. JIT makes access temporary and attributable, and removes the need to remember to revoke.

The Browser Security Model

A browser runs code from sites you have never audited, side by side with your bank, and keeps them apart with one central rule: the same-origin policy. Almost every web vulnerability is a story about that rule's gaps, or about a server that cannot tell a request the user meant from one the browser sent on an attacker's behalf. This chapter explains what the policy actually restricts, then XSS, CSRF, CORS and clickjacking as consequences, with the defences that work and the ones that only look like they do.

Why this matters

Backend engineers often treat "the browser" as a client that does what it is told. It is better modelled as a semi-trusted agent that holds your user's credentials and will cheerfully attach them to requests that another site's script asked it to make. Authentication cookies, CORS headers, CSP and SameSite attributes are all knobs on that agent. If you design APIs, set cookies or put any user-supplied text on a page, you are configuring this model whether you know it or not.

Only test what you own

The code here runs offline in Python, and the widget is a simulation. When you try these ideas for real, use your own applications or a deliberately vulnerable practice environment you control, and never test other people's sites without written authorisation.

Origins and the same-origin policy

An origin is the triple of scheme, host and port. So https://shop.example.com and https://shop.example.com:8443 are different origins, as are http:// and https:// versions of the same host, and shop. and api. subdomains (MDN: same-origin policy). The same-origin policy (SOP) is the browser rule that scripts running in one origin may not read data belonging to another. Everything else in this chapter is either an exception to that rule (CORS), a place where the rule does not apply (embedding, form posts, cookies), or an attack on a site that let hostile script into its own origin (XSS).

Precisely, MDN divides cross-origin interactions into three kinds: writes (links, redirects, form submissions) are typically allowed; embedding (images, scripts, stylesheets, media, frames) is typically allowed; and reads are typically blocked. Local storage and IndexedDB are partitioned by origin, and scripts can reach only a limited set of properties of another origin's window, communicating through postMessage.

Analogy: an office building with locked floors

Each company (origin) has its own floor. Anyone may drop a letter through any company's mail slot (a cross-origin request), and may point a camera at the lobby windows from the street (embedding), but you may not walk in and read the filing cabinets. The security guard (the browser) enforces the floor boundaries on reading, not on sending.

Where it breaks down: a real guard works for the building owner. The browser guard is deployed by the browser vendor and applies the same fixed rules to every site; the site owner can only ask it to relax some of them (CORS) or tighten others (CSP, frame-ancestors, cookie flags).

Same-site versus same-origin

Cookies, and therefore SameSite, use a looser unit than origins. A site is the scheme plus the registrable domain, also called eTLD+1: the effective top-level domain plus one label. The "effective TLD" is a public suffix, a name under which unrelated parties can register, and the authoritative list is the Public Suffix List (publicsuffix.org). So in shop.example.com the public suffix is com and the registrable domain is example.com. In x.example.co.uk the suffix is co.uk, so the registrable domain is example.co.uk. And alice.github.io and bob.github.io are different sites, because github.io itself is on the list: they belong to different people who must not share cookies.

Therefore shop.example.com and api.example.com are cross-origin but same-site. This matters in two directions. Same-site requests carry SameSite cookies, so a compromised or neglected sibling subdomain (an old marketing site, a dangling DNS record that someone can claim) is inside your cookie trust boundary; and the SOP will still stop their scripts reading each other's responses. Treat every subdomain of your registrable domain as part of your security perimeter.

The widget above is a simulation with a tiny built-in suffix list. Try the presets, then change the cookie's SameSite value and the server's CORS policy to see how the answers move. Two things worth discovering: a cross-site link click is treated differently from a cross-site form POST under Lax, and a reflecting CORS policy with credentials turns the "no, the page cannot read it" row into "yes".

Cookies and SameSite

You met cookies in networking chapter 10 and their flags in chapter 6. The security-relevant point is that cookies are ambient authority: the browser attaches them to every matching request, whoever initiated it. A cookie says "this request comes from a browser logged in as Alice", not "Alice wanted this". That gap is what CSRF exploits, and it is the web's version of the confused deputy (chapter 8).

The SameSite attribute tells the browser when to attach a cookie to a cross-site request (MDN: cookies):

  • Strict: only on requests that originate from the cookie's own site. Even following a link from another site arrives without the cookie, so the first page view appears logged out.
  • Lax: additionally sent when the user navigates to the site from elsewhere with a safe method (a link click). Not sent on cross-site subrequests (images, fetch, iframes) or cross-site form POSTs. Chromium-based browsers treat a cookie with no SameSite attribute as Lax; other browsers differ, so always set it explicitly.
  • None: sent on cross-site requests too; requires Secure. Needed for genuinely embedded or cross-site uses such as a payment widget.

Pair it with Secure (HTTPS only), HttpOnly (hidden from JavaScript, so XSS cannot read the session id) and, for session cookies, the __Host- name prefix, which makes the browser insist on Secure, Path=/ and no Domain attribute, so the cookie is bound to exactly one host and a sibling subdomain cannot overwrite it. Note what HttpOnly does and does not give you: XSS can no longer steal the cookie, but injected script can still make authenticated requests in the page, because the browser attaches the cookie for it.

Cross-site scripting (XSS)

Cross-site scripting is injection (previous chapter) where the interpreter is the browser's HTML and JavaScript engine and the sink is the page. The attacker gets their script to run inside the victim site's origin, so the SOP is no longer in the way: the script can read the DOM, call the site's APIs with the user's cookies, and rewrite what the user sees. It defeats essentially every other defence in this chapter, which is why it deserves the most care.

Three variants differ in where the hostile string lives:

  • Stored XSS: the string is saved (comment, profile name, support ticket) and served to every viewer. It is the most dangerous because the victim needs to do nothing unusual, and an administrator reading a ticket is a high-value victim.
  • Reflected XSS: the server echoes part of the request (a search term, an error message) into the response. The attacker must get the victim to open a crafted link.
  • DOM-based XSS: the server's response is harmless, but client-side JavaScript reads from a source it does not control (location.hash, document.referrer, postMessage data) and writes it into a dangerous sink (innerHTML, document.write, eval, setTimeout(string)). The server never sees it, so server-side filters are blind. The fix is to use textContent or safe DOM APIs instead of innerHTML.

def js_data(s):  # data for a <script type="application/json"> block: escape '<' so </script> cannot appear
    return json.dumps(s).replace("<", "\\u003c").replace(">", "\\u003e").replace("&", "\\u0026")

def safe_href(url: str) -> str:
    """A URL placed in href must be checked for SCHEME first; HTML escaping does not stop javascript:."""
    if urlsplit(url).scheme.lower() not in ("http", "https", "mailto", ""):
        return "#blocked"
    return html.escape(url, quote=True)

The final two lines show a context mistake: html.escape output in an unquoted attribute still lets a space start a new attribute (onfocus=...). The escaping was right for a quoted context, wrong for the context actually used. This is why the practical advice is: use a template engine with automatic, context-aware escaping on by default (most modern ones escape HTML text and quoted attributes automatically), and treat every opt-out (|safe, {% autoescape off %}, dangerouslySetInnerHTML, v-html, innerHTML =) as a security review item. If users must supply rich text, run it through a maintained allowlist-based HTML sanitiser, not a regular expression.

Content Security Policy: defence in depth, with a cost

A Content Security Policy (CSP) is a response header that tells the browser which sources of script, styles, frames and other resources the page may use, so that injected script that slips past your encoding is refused. It is a second layer, not a substitute for encoding. The effective modern form is a nonce-based strict policy (MDN: CSP):

Content-Security-Policy: script-src 'nonce-{RANDOM}' 'strict-dynamic';
                         object-src 'none'; base-uri 'none'; frame-ancestors 'none'
  • A nonce is a random value generated fresh for each response and unpredictable. The server puts it in the header and on each legitimate <script nonce="..."> tag. Injected script has no nonce, so the browser will not run it. A static or reused nonce is worthless, since an attacker who has seen it can attach it.
  • 'strict-dynamic' passes trust from a nonced script to the scripts it loads, so your bootstrap script can load libraries without you listing every host. (Older, host-allowlist policies such as script-src cdn.example.com are fragile, because anything hosted on an allowed host, including old library versions with script gadgets, may be usable by an attacker.) The cost of the convenience: if a trusted script builds <script> elements from attacker-influenced input, CSP will not help.
  • object-src 'none' and base-uri 'none' close two classic bypasses (plugin content, and an injected <base> tag that redirects relative script URLs).
  • Use Content-Security-Policy-Report-Only first: it reports violations without blocking, so you can find the inline script you forgot before you break the page.

What it costs, honestly: inline <script> blocks and inline event handlers (onclick="...") must be removed or nonced; every HTML response needs a per-response nonce, which conflicts with caching whole pages (hash-based policies suit static pages instead); third-party tags (analytics, ads, widgets) need review; and the policy needs maintenance as the site changes. In return, a typical XSS bug stops being "full account takeover" and becomes "an annoying injected element that cannot execute". Browsers also support Trusted Types, which can require that dangerous DOM sinks receive vetted values; support varies by browser, so check before depending on it.

Cross-site request forgery (CSRF)

Cross-site request forgery makes a victim's browser send a state-changing request to a site where the victim is logged in, from a page the attacker controls. Because of the SOP's rule that cross-origin writes are allowed, the attacker's page can auto-submit a form to bank.example/transfer; because cookies are ambient, the browser attaches the victim's session cookie; and the bank sees a perfectly authenticated request. The attacker never reads the response and does not need to.

Defences, in the order to reach for them:

  1. SameSite cookies. With Lax (the default in Chromium-based browsers when the attribute is absent; set it explicitly) the cross-site POST in the picture arrives without the session cookie. This is the main defence today. Know its limits: it covers cross-site attackers only, so a hostile page on a sibling subdomain is same-site; some browsers have applied short-lived exceptions that let a just-set Lax-by-default cookie ride on cross-site POSTs; and Lax still permits top-level GET navigations, so a GET request must never change state.
  2. CSRF tokens. The server issues an unpredictable value tied to the user's session and requires it on every state-changing request, in a hidden form field or custom header. The attacker's page can cause the browser to send a request but cannot read the token from your origin (the SOP again). The demo below ties the token to the session with an HMAC; a token that is not bound to the session can be swapped for one from the attacker's own account.
  3. Origin / Fetch-Metadata checks. Browsers add Origin to cross-origin and POST requests and a Sec-Fetch-Site header (same-origin, same-site, cross-site or none). Rejecting state-changing requests whose value says cross-site is a cheap, strong layer, with a fallback to tokens for clients that do not send it.
  4. Custom headers. A request carrying a non-safelisted header needs a CORS preflight, which a cross-origin attacker cannot pass unless you allow them; APIs called by your own JavaScript with such a header are therefore not form-forgeable. Bearer tokens that your code places in an Authorization header are not ambient, so classic CSRF does not apply, though storing them where XSS can read them has its own cost (chapter 6).
"""CSRF tokens, a Fetch-Metadata check, and per-response CSP nonces. Standard library only."""
import hmac, hashlib, secrets

SERVER_KEY = secrets.token_bytes(32)          # server-side secret; never sent to the browser

def csrf_token(session_id: str) -> str:
    """An HMAC-signed token bound to the session id: the attacker cannot mint one for the victim."""
    nonce = secrets.token_urlsafe(16)
    mac = hmac.new(SERVER_KEY, f"{session_id}|{nonce}".encode(), hashlib.sha256).hexdigest()[:32]
    return f"{nonce}.{mac}"

def csrf_ok(session_id: str, token: str) -> bool:
    try: nonce, mac = token.split(".", 1)
    except ValueError: return False
    good = hmac.new(SERVER_KEY, f"{session_id}|{nonce}".encode(), hashlib.sha256).hexdigest()[:32]
    return hmac.compare_digest(mac, good)

sess_alice, sess_mallory = "sess-alice-123", "sess-mallory-999"
tok = csrf_token(sess_alice)
print("legit form POST        :", csrf_ok(sess_alice, tok))
print("forged POST, no token  :", csrf_ok(sess_alice, ""))
print("token from attacker's own session:", csrf_ok(sess_alice, csrf_token(sess_mallory)))

def fetch_metadata_allows(headers: dict, method: str) -> bool:
    """Reject cross-site state-changing requests using the Sec-Fetch-Site header browsers add."""
    site = headers.get("Sec-Fetch-Site")
    if site is None:                       return True        # old client or non-browser: fall back to token checks
    if site in ("same-origin", "none"):    return True        # none = user typed it / bookmark
    return method in ("GET", "HEAD")       # same-site / cross-site: only safe methods (and your GETs must not change state)
for site in ["same-origin", "same-site", "cross-site"]:
    print(f"Sec-Fetch-Site={site:11} POST allowed={fetch_metadata_allows({'Sec-Fetch-Site': site}, 'POST')}")

def security_headers() -> dict:
    nonce = secrets.token_urlsafe(16)      # NEW value for EVERY response
    csp = (f"script-src 'nonce-{nonce}' 'strict-dynamic'; object-src 'none'; base-uri 'none'; "

    return {"Content-Security-Policy": csp,
            "X-Content-Type-Options": "nosniff",
            "Referrer-Policy": "strict-origin-when-cross-origin",
            "Strict-Transport-Security": "max-age=63072000; includeSubDomains",
            "Set-Cookie": "__Host-sid=<random>; Secure; HttpOnly; SameSite=Lax; Path=/"}

CORS: a relaxation, not a protection

Same-origin policy is too strict for legitimate cases: your front end at app.example.com needs to read JSON from api.example.com. Cross-origin resource sharing (CORS) is the mechanism by which a server tells the browser "scripts from these origins may read my responses" (MDN: CORS). Read that sentence carefully: CORS loosens the SOP. It is controlled by the server being read, enforced only by browsers, and it does nothing to a curl command, a server-side script, or the attacker who simply never uses a browser. If someone says "we use CORS to keep other sites out", they have the mechanism backwards.

How it works, in brief. The browser adds an Origin header to cross-origin requests. A simple request (methods GET, HEAD, POST; only safelisted headers; content type form-encoded, multipart or plain text) is sent immediately, and the browser then decides whether to show the response to the script based on the reply's Access-Control-Allow-Origin. Anything else, such as a JSON Content-Type or a custom header or PUT/DELETE, is preflighted: the browser first sends an OPTIONS request and only sends the real one if the server's answer approves it. With credentials (cookies), the server must name the exact origin, send Access-Control-Allow-Credentials: true, and the wildcard * is rejected by the browser. Servers that vary the answer by origin must send Vary: Origin so caches do not hand one origin's reply to another.

The classic misconfigurations

  • Reflecting the Origin header, with credentials. To "make CORS work" a developer copies whatever Origin arrived into Access-Control-Allow-Origin and adds Allow-Credentials: true. Now every website on earth can make a logged-in user's browser fetch your authenticated API and read the answer: it is the SOP, switched off for the one case it matters most. The demo below includes this bug as a function and a test that confirms it is exploitable.
  • Sloppy matching. endswith("example.com") accepts evilexample.com; startswith("https://app.example.com") accepts https://app.example.com.evil.test; a regular expression with an unescaped dot accepts lookalikes. Use exact string comparison against a list.
  • Allowing null. Sandboxed iframes and some local documents send Origin: null; an attacker can produce one at will, so allowing it is allowing anyone.
  • Trusting every subdomain. Allowing *.example.com makes your API exactly as secure as your least-maintained subdomain.
  • Wildcard on private data. * (without credentials) is fine for public, unauthenticated resources. On an internal service reachable from a user's browser (an admin panel on a corporate network, a developer's localhost tool), it lets any web page the user visits read it through their machine. Reachability from the browser, not secrecy of the URL, is the question.
"""Origins, sites and a tiny CORS decision function, with tests. Standard library only."""
import unittest
from urllib.parse import urlsplit

# A TINY public-suffix list for the demo. Real code uses the full Public Suffix List (publicsuffix.org).
PUBLIC_SUFFIXES = {"com", "org", "uk", "co.uk", "github.io", "herokuapp.com"}
DEFAULT_PORT = {"http": 80, "https": 443}

def origin(url: str):
    u = urlsplit(url)
    return (u.scheme, u.hostname, u.port or DEFAULT_PORT.get(u.scheme))

def etld1(host: str) -> str:
    """Registrable domain: one label more than the longest matching public suffix."""
    labels = host.split(".")
    for i in range(len(labels)):
        if ".".join(labels[i:]) in PUBLIC_SUFFIXES:
            return ".".join(labels[max(i - 1, 0):])
    return ".".join(labels[-2:])                      # PSL default rule: an unlisted TLD is itself the suffix

def same_origin(a: str, b: str) -> bool:
    return origin(a) == origin(b)

def same_site(a: str, b: str) -> bool:
    (sa, ha, _), (sb, hb, _) = origin(a), origin(b)
    return sa == sb and etld1(ha) == etld1(hb)        # 'schemeful' same-site

def cors_headers(request_origin, allowed, credentials=False):
    """Decide the CORS response headers. `allowed` is an exact-match allowlist of origins.
    Never reflect an unlisted origin, and never combine '*' with credentials."""
    if request_origin is None or request_origin not in allowed:
        return {}                                     # no CORS headers: the browser will hide the response
    h = {"Access-Control-Allow-Origin": request_origin, "Vary": "Origin"}
    if credentials:
        h["Access-Control-Allow-Credentials"] = "true"
    return h

def cors_reflect_everything(request_origin):          # THE CLASSIC BUG, kept for the test below
    return {"Access-Control-Allow-Origin": request_origin, "Access-Control-Allow-Credentials": "true"}

class T(unittest.TestCase):
    def test_origin(self):
        self.assertTrue(same_origin("https://example.com/a", "https://example.com:443/b"))
        self.assertFalse(same_origin("https://example.com", "http://example.com"))
        self.assertFalse(same_origin("https://example.com", "https://example.com:8443"))
        self.assertFalse(same_origin("https://a.example.com", "https://b.example.com"))
    def test_site(self):
        self.assertTrue(same_site("https://a.example.com", "https://b.example.com"))
        self.assertFalse(same_site("https://alice.github.io", "https://bob.github.io"))
        self.assertFalse(same_site("https://example.com", "http://example.com"))
        self.assertTrue(same_site("https://x.example.co.uk", "https://y.example.co.uk"))
    def test_cors(self):
        ok = {"https://app.example.com"}
        self.assertEqual(cors_headers("https://app.example.com", ok, True)["Access-Control-Allow-Origin"], "https://app.example.com")
        self.assertEqual(cors_headers("https://evil.test", ok, True), {})
        self.assertEqual(cors_headers(None, ok), {})
        self.assertNotIn("*", cors_headers("https://app.example.com", ok, True).values())
        # suffix tricks must not pass: exact match only
        self.assertEqual(cors_headers("https://app.example.com.evil.test", ok, True), {})
    def test_reflection_bug_is_exploitable(self):
        self.assertEqual(cors_reflect_everything("https://evil.test")["Access-Control-Allow-Origin"], "https://evil.test")

Clickjacking and frame-ancestors

Clickjacking loads your page in a transparent or disguised <iframe> on the attacker's page, so that the victim's click on "play the video" actually lands on your "delete account" button. No script injection or forged request is needed: the click is real and the session is real. The defence is to tell the browser who may frame you. Use the CSP directive frame-ancestors: 'none' forbids all framing, 'self' allows only your own origin, or list specific origins. It supersedes the older X-Frame-Options header (DENY or SAMEORIGIN), which is still worth sending for old browsers. SameSite cookies add a second layer, since a cross-site frame will not carry Lax or Strict cookies, so the framed page often shows a logged-out state. Pages that really are meant to be embedded (a payment widget) should allow only named parents and avoid one-click destructive actions.

Security headers: a checklist

HeaderWhat it does
Content-Security-PolicyRestricts script and other sources; the strongest XSS mitigation and the home of frame-ancestors.
Strict-Transport-Security (HSTS)Tells the browser to use only HTTPS for this host for max-age seconds, defeating downgrade and stripping attacks (TLS chapter). Roll out with a short age first.
X-Content-Type-Options: nosniffStops the browser guessing a content type, so an uploaded text file cannot be treated as script.
Referrer-PolicyLimits the URL sent in the Referer header to other sites, so tokens in URLs and internal paths do not leak.
Permissions-PolicyDisables powerful features (camera, geolocation, and so on) for your page and embedded frames.
Cross-Origin-Opener-Policy and Cross-Origin-Resource-PolicyIsolate your page's browsing context and say who may embed your resources; part of cross-origin isolation, relevant for side-channel (Spectre-class) risks and some powerful APIs.
Cache-Control: no-storeFor responses containing personal or session-bound data, so shared caches and the back button do not keep them.
Set-Cookie flagsSecure; HttpOnly; SameSite=Lax and the __Host- prefix for session cookies.

Headers are cheap defence in depth, set once at the edge (reverse proxy or framework middleware) so no individual handler has to remember them. They do not repair broken application logic: a site with a missing authorisation check (chapter 8) or an injection flaw (chapter 9) is still broken with a perfect scorecard.

Go deeper (optional): why "just check the Referer" and "JSON is safe" are not enough

Some privacy tools strip Referer and Origin, so a strict "must be present" rule breaks real users, while a lax "allow if missing" rule lets attackers find a way to omit it. Treat origin checks as one layer. Likewise, "our API takes JSON, so forms cannot forge it" holds only if the server requires Content-Type: application/json: a server that parses the body regardless of its declared type can be reached by a form using text/plain, which counts as a simple request and needs no preflight. Validate the content type, and keep the other layers anyway.

Distributed systems connection

The browser is one more node in your distributed system, one you do not control and cannot patch. Its cached CORS preflight answers, cookies and HSTS entries are replicated state with their own expiry (Access-Control-Max-Age, max-age), and a misconfiguration can persist in clients long after you fix it on the server. Edge layers and CDNs are where headers are usually added, so cache keys must include anything that varies the response (Vary: Origin), or one origin's permissive answer is served to another. Rate limits and bot controls at the edge are covered in architecture chapter 9 and, from the abuse angle, in chapter 16.

Key takeaways

  • An origin is scheme + host + port. The SOP lets pages send cross-origin requests and embed resources but blocks scripts from reading cross-origin responses.
  • A site is scheme + registrable domain (eTLD+1, from the Public Suffix List). Subdomains are cross-origin but same-site, so SameSite does not separate them.
  • Cookies are ambient authority. Use Secure; HttpOnly; SameSite=Lax (or Strict) and the __Host- prefix; never change state on GET.
  • XSS runs attacker script inside your origin. Fix it by encoding for the output context (and by avoiding innerHTML), and add a nonce-based strict CSP as a second layer.
  • CSRF needs cookies to be sent automatically. Defend with SameSite, per-session tokens, and Origin or Sec-Fetch-Site checks.
  • CORS relaxes the SOP at the server's request; it is not an access control. Never reflect Origin with credentials, never match by suffix or prefix, never allow null.
  • Use frame-ancestors against clickjacking, and set the standard security headers once at the edge.

Check your understanding

A page at https://app.example.com and another at https://api.example.com. Which statement is correct?

  1. They are same-origin and same-site
  2. They are cross-origin but same-site, so scripts cannot read each other's responses, yet SameSite cookies are sent between them
  3. They are cross-origin and cross-site
  4. They are same-origin but cross-site
Different host means different origin. Both share the registrable domain example.com and the scheme, so they are same-site. That is why a compromised sibling subdomain is inside your cookie trust boundary.

A server answers every request with Access-Control-Allow-Origin: <the request's Origin> and Access-Control-Allow-Credentials: true. What does this allow?

  1. Nothing special; it is how CORS is meant to be configured
  2. Only the user's own site to read responses
  3. Cross-site request forgery only
  4. Any website a logged-in user visits can make their browser call the API with cookies and read the authenticated responses
Reflecting any origin with credentials disables the SOP's protection for authenticated data. The server should compare against an exact allowlist and answer nothing for unknown origins.

Which statement about CORS is true?

  1. It is enforced by browsers and relaxes the SOP at a server's request; it does not stop non-browser clients or stop a simple request from being sent
  2. It authenticates users
  3. It prevents CSRF
  4. It encrypts cross-origin traffic
CORS controls whether a script may read a cross-origin response. The request may still be sent (simple requests) and the server must still defend itself. It is neither authentication nor encryption.

You set a strict nonce-based CSP. A developer adds <script nonce="a1b2c3"> using the same constant nonce on every page. What is wrong?

  1. Nothing; nonces only need to be unique per site
  2. The nonce is too short
  3. A nonce must be unpredictable and fresh for every response; a constant one can be learned and attached to injected scripts
  4. Nonces cannot be used with inline scripts
The security of nonce-based CSP comes entirely from the attacker being unable to know the nonce for this response. A reused value turns the policy into decoration.

An attacker's page auto-submits a form POST to your site. Your session cookie is SameSite=Lax. What happens, and what is still your job?

  1. The cookie is sent, so you must add CSRF tokens only for GET
  2. The browser does not attach the cookie to the cross-site POST, so the forgery fails as an authenticated request; you must still keep GET side-effect-free and consider same-site attackers and tokens as another layer
  3. The request is blocked from being sent at all
  4. The server cannot tell the request is cross-site, so SameSite is useless
Lax withholds cookies on cross-site subrequests and POST navigations, but sends them on top-level GET navigations and on same-site requests. Defence in depth (tokens, Sec-Fetch-Site) covers the gaps.

Why does HttpOnly not make a site safe from XSS?

  1. It does nothing at all
  2. It only works over HTTP
  3. It makes cookies readable by scripts
  4. It stops scripts reading the cookie, but injected script still runs in the page and can make authenticated requests, since the browser attaches the cookie for it
HttpOnly limits theft of the session identifier, which is worth having. The attacker's script can still act as the user while the page is open and can alter the page, so the underlying XSS still has to be fixed.

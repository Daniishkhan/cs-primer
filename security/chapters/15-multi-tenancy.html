Multi-Tenancy & Isolation

A SaaS product serves many customers, called tenants, from the same system. Every one of them expects to see only their own data, to be unaffected by the others' load, and to be able to leave and take their data with them. This chapter compares the ways to share (or not share) infrastructure, shows how the tenant identity must travel through a system, lists the places where leaks actually happen, and ends with noisy neighbours, per-tenant keys, deletion and data residency.

Why this matters

In a single-tenant application a bug affects one customer. In a multi-tenant one the worst bug is a cross-tenant bug: customer A's invoices on customer B's screen. That is a breach of every customer's contract at once, and the kind of incident that ends enterprise deals. Tenancy is also a cost question (how many servers per customer?) and a reliability question (can one customer's burst slow the rest?), so the design decision is made early and is very hard to reverse. This is the chapter where authorization (chapter 8), cloud isolation (chapter 14), keys (chapter 4) and blast radius (reliability chapter 15) meet.

What is a tenant?

A tenant is the unit that must be isolated from other units: usually a customer organisation (a company, a workspace, an account) containing many users. Be careful to separate the two: a user belongs to a tenant, and sharing between tenants (a document shared with another company) is a deliberate, narrow exception that needs its own design. Everything below assumes you can answer, for any piece of data or any request, "which tenant does this belong to?" If you cannot, you cannot isolate it.

Three tenancy models

The terms silo, pool and bridge come from AWS's SaaS architecture guidance, which describes silo as dedicated resources per tenant, pool as resources shared by all tenants, and bridge as a mix of the two. The boundaries are not sharp; many products use a different mix per component (for example, a pooled application tier with a database per tenant, or pooled small tenants plus siloed large ones). Treat the names as a vocabulary for the trade-off, not a taxonomy.

Most products evolve along the spectrum rather than choosing once. A common path: start pooled because it is cheap and fast to build, add database-per-tenant or siloed deployments for large or regulated customers who will pay for them, and keep a tier concept in the control plane so that moving a tenant between models is a supported operation, not a rewrite. Whatever you choose, keep a tenant registry: a table, owned by a control plane, that maps each tenant to its model, region, keys and limits.

Analogy: housing

Silo is a detached house per family: total privacy, a lot of land and plumbing to maintain. Pool is a dormitory with shared rooms and lockers: cheap, and everything depends on the locks being right and the neighbours behaving. Bridge is a block of flats: separate front doors and meters, shared building services.

Where it breaks down: software tenants can be moved between "buildings" with a migration, and a software flat can be starved by a neighbour in ways a physical one cannot (a shared lift is a good model for a shared CPU).

Tenant context: derive it, carry it, never accept it

Whatever the model, the system needs a tenant context: the answer to "whose request is this?" for every operation. The rule that prevents the most damage is stated in chapter 8 and is worth restating at full strength: the tenant comes from the authenticated identity, never from the request. A tenant_id in a JSON body, a URL path segment, a query string or an arbitrary header is attacker-controlled input. If the handler uses it to choose whose data to read, any user can read any tenant by editing a field (that is broken object-level authorization with a tenant-sized blast radius).

  • Establish it once, at the edge, from verified claims. The gateway or authentication middleware verifies the session or token (chapter 6), reads the tenant from the verified claims or from the server-side session, and builds an immutable principal object. Everything downstream receives the principal, not the raw request.
  • Make the tenant a required argument, not an ambient global. Functions that touch data take a principal (or a tenant-scoped repository). A missing tenant is then a type or compile error rather than a silent global query. Where ambient context is unavoidable (thread-local or async context variables), make the data layer refuse to run without it.
  • If a request does carry a tenant id (for routing, or a URL like /t/acme/invoices), treat it as a claim to be checked: compare it with the principal's tenant, and reject a mismatch. Users who legitimately belong to several tenants (consultants, support staff) are handled by an explicit "acting in tenant X" step whose result is also verified, ideally re-issuing the token.
  • Carry it across asynchronous boundaries. A queue message, scheduled job or webhook delivery must record the tenant that the (authenticated) producer was acting for, and the worker must restore that context before running, then clear it afterwards.
  • Propagate it to other services as part of the call identity (signed token claims, mTLS metadata), not as a plain header that any internal caller could set (chapter 13).

Data isolation options

Within the data layer there are three standard designs, mapping roughly to the models above.

Database per tenant

Each tenant gets its own database (or even instance). Isolation is by connection credentials: the application connects to the tenant's database, and a missing WHERE clause cannot reach anyone else's rows. Per-tenant backup, restore, export, encryption keys, region placement and deletion are simple. Costs: connection pooling is harder (many databases means many pools), schema migrations must run across all N databases (and you must handle partial failures), cross-tenant analytics needs an export pipeline, and per-database overhead limits how many tenants fit on a server. It suits dozens to thousands of larger tenants, not millions of tiny ones.

Schema per tenant

One database, a schema (namespace) per tenant, selected by the connection's search path or by qualified names. It reduces per-database overhead and still separates tables, so a forgotten WHERE cannot cross tenants as long as the search path is set correctly. But one set of credentials usually sees every schema, so a bug in choosing the schema is a cross-tenant bug, catalogue size grows with tenants (migrations and tooling slow down), and restoring a single tenant from a whole-database backup is awkward.

Shared tables with tenant_id and row-level security

All tenants share tables; every row carries a tenant_id. This is the cheapest and scales to very many small tenants, and it is the model where isolation is entirely logical. Two layers make it safe: a repository layer that always applies the filter, and database row-level security (RLS) as the backstop. In PostgreSQL, RLS attaches a policy to a table so that the database itself appends the tenant condition to every query and rejects writes for other tenants. The statements below are valid PostgreSQL but illustrative; they were not run in this course's environment.

-- PostgreSQL. Illustrative: not executed in this course's environment.
CREATE TABLE invoices (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id  uuid          NOT NULL,
    title      text          NOT NULL,
    amount     numeric(12,2) NOT NULL
);
CREATE INDEX invoices_tenant_idx ON invoices (tenant_id, id);

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;      -- apply even to the table owner

CREATE POLICY tenant_isolation ON invoices
    USING      (tenant_id = current_setting('app.tenant_id', true)::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);

-- The application connects as a role that owns nothing and cannot bypass policies:
CREATE ROLE app_user LOGIN NOSUPERUSER NOBYPASSRLS;
GRANT SELECT, INSERT, UPDATE, DELETE ON invoices TO app_user;

-- Per request, on a connection from the pool, inside one transaction:
BEGIN;
SELECT set_config('app.tenant_id', '3f2b7d1e-8c4a-4e0b-9a55-1f6d2c7b9e10', true);  -- true = this transaction only
SELECT id, title FROM invoices;                    -- returns only that tenant's rows, with no WHERE clause
INSERT INTO invoices (tenant_id, title, amount)
VALUES ('aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa', 'x', 1);   -- fails: violates the policy's WITH CHECK
COMMIT;

Read the details, because each is a classic way to get RLS wrong:

  • USING filters which existing rows a query can see, update or delete; WITH CHECK restricts the rows that INSERT and UPDATE may produce. Without it, a session could write a row into another tenant.
  • Table owners, superusers and roles with the BYPASSRLS attribute are not subject to policies by default (FORCE ROW LEVEL SECURITY covers owners). Connect the application as a plain role, and run migrations as a different one.
  • The tenant is conveyed in a session setting. With a connection pool, a setting left behind by one request is inherited by the next request on that connection, which is a cross-tenant leak through the pool. Setting it with the transaction-local form (the true argument above) and doing so at the start of every transaction avoids that. With the missing-setting form used above, a setting that was never defined yields NULL and so no rows rather than all rows: the policy fails closed. (On a pooled connection that has already used a transaction-local setting, PostgreSQL may report an empty string instead, and the uuid cast then raises an error; that also fails closed, but expect errors rather than empty results.)
  • Policies are additional SQL that runs on every query. Index (tenant_id, ...) as shown, and measure.
  • RLS protects against missing filters in application SQL and injection into queries as the application role (chapter 9); it does not help if the application connects as a bypass-capable role, or if the tenant setting itself is derived from untrusted input.

A repository layer that cannot forget

RLS is the backstop; the first line is a data-access layer in which a query without a tenant is impossible to write. The listing below is runnable and uses an in-memory SQLite database. The Principal is built from the authenticated session. Every repository method takes one and adds the tenant filter itself. The same test class runs against a deliberately leaky repository (the "quick lookup" someone adds on a Friday) to prove the tests catch a missing filter.

"""A repository layer that makes tenant scoping impossible to forget, plus tests. sqlite3, in-process."""
import sqlite3, unittest
from dataclasses import dataclass

@dataclass(frozen=True)
class Principal:                      # built ONLY from the authenticated session/token, never from the request body
    user_id: str
    tenant_id: str

class TenantViolation(Exception): pass

class TenantRepo:
    """Every method takes a Principal; the tenant filter is added here, not by each caller."""
    TABLES = {"invoices": ("id", "tenant_id", "title", "amount")}
    def __init__(self, db): self.db = db
    def _check(self, table):
        if table not in self.TABLES: raise TenantViolation(f"unknown table {table}")
    def get(self, p: Principal, table, row_id):
        self._check(table)
        return self.db.execute(f"select * from {table} where id=? and tenant_id=?", (row_id, p.tenant_id)).fetchone()
    def list(self, p: Principal, table):
        self._check(table)
        return self.db.execute(f"select * from {table} where tenant_id=? order by id", (p.tenant_id,)).fetchall()
    def insert(self, p: Principal, table, row: dict):
        self._check(table)
        if "tenant_id" in row and row["tenant_id"] != p.tenant_id:     # a body-supplied tenant id is never trusted
            raise TenantViolation("tenant_id in payload does not match the authenticated tenant")
        self.db.execute("insert into invoices(id, tenant_id, title, amount) values (?,?,?,?)",
                        (row["id"], p.tenant_id, row["title"], row["amount"]))

class LeakyRepo(TenantRepo):          # what the bug looks like: someone writes 'just a quick lookup'
    def get(self, p, table, row_id):
        return self.db.execute(f"select * from {table} where id=?", (row_id,)).fetchone()   # forgot tenant_id

def make_db():
    db = sqlite3.connect(":memory:")
    db.execute("create table invoices(id integer primary key, tenant_id text not null, title text, amount int)")
    db.executemany("insert into invoices values (?,?,?,?)", [(1, "acme", "Acme Q3", 120), (2, "globex", "Globex Q3", 9000)])
    return db

ACME, GLOBEX = Principal("u1", "acme"), Principal("u2", "globex")

class TenantIsolationTests(unittest.TestCase):
    """Run the SAME two-tenant suite against any repository class; a missing filter must fail it."""
    repo_cls = TenantRepo
    def setUp(self): self.repo = self.repo_cls(make_db())
    def test_get_other_tenants_row_is_invisible(self):
        self.assertIsNone(self.repo.get(ACME, "invoices", 2))
    def test_list_only_own_rows(self):
        self.assertEqual([r[0] for r in self.repo.list(ACME, "invoices")], [1])
    def test_own_row_still_works(self):
        self.assertEqual(self.repo.get(GLOBEX, "invoices", 2)[2], "Globex Q3")
    def test_payload_tenant_id_rejected(self):
        with self.assertRaises(TenantViolation):
            self.repo.insert(ACME, "invoices", {"id": 3, "tenant_id": "globex", "title": "x", "amount": 1})

class LeakyRepoTests(TenantIsolationTests):
    repo_cls = LeakyRepo           # expected to FAIL test_get_other_tenants_row_is_invisible: the test catches the bug

if __name__ == "__main__":
    unittest.main(verbosity=2)

The output is the point. The correct repository passes all four tests. The leaky subclass inherits the same four tests and fails the one that matters: ACME asked for id 2 and received Globex's row. This "two tenants, same operations" pattern is the cheapest, most effective test of multi-tenant code: for every read and write path, create data in tenant A, act as tenant B, and assert nothing happens. Run it against every endpoint in CI. Note also that a body-supplied tenant_id that disagrees with the principal is rejected rather than quietly ignored, so a bug or an attack shows up in logs.

Only test what you own or are authorised to test

Cross-tenant tests belong in your own test environment with your own test tenants. Attempting to read another customer's data on a production service you do not own is unauthorised access, even if you are only "checking" and even if it is trivially easy.

Where cross-tenant leaks really happen

Teams that get the main database right still leak, because tenant data flows through components that are shared and have their own keys, queries and contexts. Review each for a tenant dimension.

  • Caches. A cache keyed by object id alone (invoice:7) serves whichever tenant populated it first. Keys must include the tenant, and so must derived keys: cached query results, rendered pages, signed URLs.
  • Search indexes. A shared index must apply a tenant filter to every query, including autocomplete suggestions, facet counts and "related items", which can leak the existence and wording of other tenants' content even when the hits are filtered. Alternatives are an index (or routing key) per tenant for strong separation, at the price of index count and overhead.
  • Logs, traces and error messages. Logs capture whatever the code printed. If customers or support staff can see logs, tag every entry with the tenant and enforce access by tag. Make sure error messages and validation failures never echo another tenant's data (for example "email already registered to acme.com"), and see reliability chapter 5 on keeping personal data out of logs.
  • Background jobs, workers and schedulers. Jobs run later, without a request, often as a privileged service identity that skips the checks users face. A worker pool that stores the current tenant in a global or thread-local and fails to reset it between jobs will run tenant B's job with tenant A's context. Pass the tenant in the job, restore it before the job runs, clear it in a finally block, and prefer jobs that act through the same tenant-scoped repository as requests.
  • Uniqueness and enumeration. Global unique constraints (usernames, slugs) and sequential ids reveal that something exists. Scope uniqueness to the tenant where product rules allow, and treat "exists but forbidden" and "does not exist" alike.
  • Everything else with a namespace. Object-storage key prefixes, temporary files, message-queue topics, rate-limit counters, feature-flag evaluations, email templates and webhooks.

The cache case is small enough to run. The second half of this program previews the next section, noisy neighbours.

"""Two multi-tenant failure modes in miniature: a shared cache key, and a noisy neighbour. In-process, seeded."""
from collections import deque

# ---------- 1. Cache keyed by object id alone ----------
DB = {("acme", 7): "Acme's salary report", ("globex", 7): "Globex's salary report"}
cache = {}
def get_bad(tenant, oid):
    if oid not in cache: cache[oid] = DB[(tenant, oid)]            # key omits the tenant
    return cache[oid]
cache2 = {}
def get_good(tenant, oid):
    key = (tenant, oid)
    if key not in cache2: cache2[key] = DB[key]
    return cache2[key]
print("bad  key: acme reads :", get_bad("acme", 7))
print("bad  key: globex gets:", get_bad("globex", 7), " <- another tenant's data")
print("good key: acme reads :", get_good("acme", 7))
print("good key: globex gets:", get_good("globex", 7))

# ---------- 2. Noisy neighbour: one FIFO queue vs per-tenant round robin ----------
# 'big' submits 90 jobs at once; 'small' submits 3. The worker does one job per tick.
def fifo(jobs):
    return {t: [i for i, (tt, _) in enumerate(jobs) if tt == t] for t in {j[0] for j in jobs}}
def fair(jobs):
    queues = {}
    for t, j in jobs: queues.setdefault(t, deque()).append(j)
    done, tick = {t: [] for t in queues}, 0
    while any(queues.values()):
        for t in sorted(queues):                                    # one job per tenant per round
            if queues[t]:
                queues[t].popleft(); done[t].append(tick); tick += 1
    return done
jobs = [("big", n) for n in range(90)] + [("small", n) for n in range(3)]
a, b = fifo(jobs), fair(jobs)
print("\nFIFO : small tenant's jobs finish at ticks", a["small"], "(waits behind all 90)")
print("fair : small tenant's jobs finish at ticks", b["small"], "(big still completes all 90 jobs)")
print("fair : big tenant's last job finishes at tick", b["big"][-1])

The "bad key" run is a real security bug that passes every functional test: each tenant sees plausible data, just not their own. It is only caught by a test with two tenants.

Noisy neighbours and fairness

In a pooled system, a tenant's burst (an import, a runaway integration, a scraper, a legitimately large customer) competes with everyone for CPU, database connections, I/O and queue capacity. This noisy neighbour problem is an availability issue but also a security one, since resource exhaustion by one tenant is a denial of service against the others (the deliberate form is chapter 16). The toolbox:

  • Per-tenant quotas and rate limits. Limit requests, concurrent operations, storage and expensive features per tenant, with tiers. The algorithms (token bucket and relatives) are covered in the rate-limiter chapter; the point here is that the key is the tenant, not just the IP or user, and limits should be visible to customers so they can plan.
  • Fair scheduling. A single FIFO queue lets a tenant that submits 90 jobs delay everyone behind it. Round-robin or weighted fair queuing across per-tenant queues, as in the listing above, bounds the delay a tenant can impose on another (the small tenant's jobs finished at ticks 1, 3 and 5 instead of 90 to 92, while the big tenant still got all its work done).
  • Bulkheads and concurrency caps. Reserve separate connection pools, thread pools or worker groups for tenants or tiers, so that exhausting one cannot starve the rest (the resilience patterns of architecture chapter 17).
  • Shuffle sharding. Give each tenant a small random subset of workers instead of the whole fleet or a fixed shard, so a tenant that crashes its workers harms only the few tenants that share many workers with it. The reliability course explores the arithmetic in blast radius and has an interactive explorer.
  • Query and statement limits. Per-tenant statement timeouts, row limits and pagination caps stop one expensive query from holding the database hostage.
  • Move the biggest tenants. Promote a tenant that dominates load to its own shard, database or stack. The registry makes this an operation.

Per-tenant encryption keys and deletion

Using a separate key for each tenant, in the envelope-encryption design of chapter 4, adds a cryptographic boundary on top of the logical one.

  • Deletion by key destruction. If all of a tenant's data is encrypted under keys derived from or wrapped by that tenant's key, destroying the key renders every copy unreadable, including copies in backups you cannot practically edit. This is often called crypto-shredding; lab 6 builds it.
  • Customer-managed keys. Enterprise customers may want the key in their own KMS account, so that revoking it cuts the vendor off. This is a strong control and also an availability risk: if the key becomes unreachable, the tenant's data is unreadable to you too.
  • Smaller blast radius for key compromise, and an audit trail per tenant of who decrypted what.

Be honest about the limits. The application that serves all tenants is normally authorised to use every tenant's key, so a bug in that application can still return another tenant's plaintext: per-tenant keys defend against stolen storage, stolen backups and some insider scenarios, not against logic errors. Costs include many more keys, KMS latency and request cost (cache data keys briefly in memory), and design complexity (key rotation per tenant). Shredding only works if no plaintext copies exist elsewhere, in search indexes, caches, analytics warehouses and logs.

Tenant deletion

When a tenant leaves, "delete" has to mean something checkable. A defensible design: a grace period with soft delete (accidents and disputes happen), then a hard-delete job driven by an inventory of every place the tenant's data lives: primary database, object storage, search index, caches, message queues, analytics exports, logs, and backups (which age out, or are covered by key destruction). Record each step, verify afterwards by querying for the tenant id everywhere, keep what you are legally required to keep (financial records, legal holds) and be explicit that you are doing so. Data protection law, for example the GDPR's right to erasure, shapes what you must delete and how fast; that is outside this chapter and is not legal advice, but chapter 17 returns to deletion across logs and backups.

Tenant-aware observability

You cannot operate what you cannot see per tenant. Put tenant_id (or a pseudonymous stable id, if the identifier is itself sensitive) on every log line, trace and audit record, so that you can answer "is this one customer's problem or everyone's?" and "what did tenant X do last Tuesday?". A few cautions, in the spirit of reliability chapter 4: per-tenant labels on metrics create cardinality that can overwhelm a metrics system, so keep per-tenant metrics for the top tenants or tiers and use logs and traces (which handle high cardinality) for the rest; build per-tenant dashboards and error budgets for large customers, since an SLO that averages over tenants hides the one with an outage; and apply tenancy to the observability tools themselves, because a shared dashboard or log search that shows every tenant to every support engineer is its own isolation failure. Detection of cross-tenant access attempts (many "not found" results for ids of other tenants) is a useful alarm (chapter 18).

Enterprise tenants and data residency

Large customers bring requirements that stress the model: dedicated infrastructure, their own keys, audit access, single sign-on, and data residency, the requirement that data be stored and processed in a specific country or region (for regulatory, contractual or political reasons). Residency is easiest when the tenant is a first-class placement unit:

  • Choose the tenant's home region at creation and record it in the registry; route every request to that region (typically by tenant, from the verified principal).
  • Split the system into a control plane (global: registry, billing, identity routing, minimal metadata) and a data plane (regional: the tenant's content). Decide, and document, exactly which data may leave the region, including backups, logs, search indexes, analytics, support tooling and replicas.
  • A cell-based architecture, where each cell is a complete stack serving a set of tenants in one region, gives residency, silo options for big tenants and a bounded blast radius in one design.
  • The multi-region replication techniques of distributed chapter 18 still apply, but residency often means not replicating across borders, so durability must be achieved within the allowed set of regions.

Distributed systems connection

Tenant isolation is partitioning with a security requirement. The shard key of data chapter 16 is very often the tenant id, which gives locality and a natural blast-radius boundary, and creates hot shards when one tenant dominates. Fairness across tenants is the admission-control and queueing theory of the reliability course applied to a per-tenant dimension. And a registry that routes every request to the right cell is a small, critical, highly available metadata service: it must be cached, replicated and carefully failed over, because "which tenant lives where" is on the path of every request.

Key takeaways

  • Silo (dedicated stack), pool (everything shared) and bridge (a mix, such as shared app tier with a database per tenant) trade isolation and blast radius against cost and operational simplicity. Most products mix them, with a tenant registry.
  • The tenant id comes from the verified identity, is carried explicitly (including into jobs and downstream calls), and is never accepted from a request body, URL or header.
  • Data isolation: database per tenant (strong, operationally heavy), schema per tenant (middle), shared tables with tenant_id plus row-level security (cheap, logical only). Use a repository layer that cannot omit the filter and RLS as a backstop; watch connection pools, bypass roles and WITH CHECK.
  • Leaks hide in shared infrastructure: caches, search indexes, logs, background jobs, unique constraints, storage prefixes. Each needs a tenant dimension, and tests with two tenants find the bugs.
  • Noisy neighbours are an availability and security issue: per-tenant quotas, fair queuing, bulkheads and shuffle sharding bound the damage.
  • Per-tenant keys give crypto-shredding, customer-managed keys and smaller key blast radius, but do not stop bugs in code that is authorised to decrypt everything.
  • Deletion needs an inventory of every copy; observability and residency both need the tenant as a first-class dimension and placement unit.

Defence in depth: the layer makes the right query the default, the database enforces it even if the layer is bypassed, and the test catches regressions.

With row-level security driven by a session setting and a connection pool, what mistake leaks data between tenants?

  1. Setting the tenant at session level and not resetting it, so the next request on that pooled connection inherits it; use a transaction-local setting at the start of each transaction
  2. Using indexes on tenant_id
  3. Enabling the policy at all
  4. Using integers for ids
Pooled connections outlive requests. State left on them is inherited. Transaction-local settings disappear when the transaction ends.

A cache stores invoice:7 and serves it to whichever tenant asks. Why does every functional test still pass?

  1. Caches are never tested
  2. The cache is encrypted
  3. Each tenant sees plausible data, just maybe someone else's; only a test where two tenants use the same object id can detect it
  4. The bug only happens with silo tenancy
The bug is invisible with one tenant. The fix is a tenant-qualified key, and a two-tenant test that would have failed.

One tenant submits a huge batch into a shared FIFO job queue and other tenants' jobs wait. Which change best addresses it?

  1. Increase the batch size
  2. Per-tenant queues served fairly (round-robin or weighted), with per-tenant quotas
  3. Move every tenant to the same worker
  4. Remove logging
Fair scheduling bounds the delay any tenant can impose; quotas bound how much work a tenant may submit. Neither requires separate infrastructure.

What does per-tenant key destruction accomplish when a tenant leaves, and what does it not do?

  1. It makes the application faster and fixes cross-tenant bugs
  2. It deletes plaintext copies in caches and logs
  3. It makes all data encrypted under that key, including backup copies, unreadable; it does not remove plaintext copies elsewhere and does not prevent logic bugs in code that can use other tenants' keys
  4. It removes the need for a deletion inventory
Crypto-shredding is powerful for ciphertext you cannot practically edit, but only covers data actually encrypted under the key. You still need to find plaintext copies.

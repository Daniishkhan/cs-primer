OAuth 2.0 & OpenID Connect

"Sign in with Google", "let this app read your calendar", "this service calls that service": all of it runs on OAuth 2.0 and OpenID Connect. They are widely used and widely misunderstood, and the usual misunderstanding is that OAuth is a login protocol. This chapter explains what problem it solves, walks the authorization code flow with PKCE one message at a time, shows what each check defends against, and then adds the identity layer that OpenID Connect puts on top.

Why this matters

Almost every product you design will either consume OAuth (log in with an external provider, call a partner's API) or provide it (let third parties integrate). The protocol has many moving parts, each added to close a specific attack, and the failures are correspondingly specific: a redirect address matched loosely, a missing state, an ID token accepted for the wrong audience. If you understand which message prevents which attack, you can review an integration in minutes and recognise a weak one.

The problem: delegated authorization

Suppose a photo-printing site wants your photos from a storage service. Before OAuth, the printing site would ask for your storage password and log in as you. That is a disaster in four ways: the printer can do everything you can, forever; you can only revoke its access by changing your password, which breaks every other tool; the printer's database now holds a password for a different service; and the storage service cannot tell a human from the printer.

OAuth 2.0 (RFC 6749, 2012) solves exactly this: delegated authorization. The user grants a limited, revocable permission to an application, and the application receives a token instead of a password. Note the word: authorization. OAuth says "this application may read photos, until this time, on behalf of this user". It does not, by itself, tell the application who the user is. That gap is why OpenID Connect exists, and why "I called the provider's API with the token, so the user must be logged in" is a classic mistake (see the OIDC section).

The roles

  • The resource owner is the user who owns the data and can grant access to it.
  • The client is the application requesting access. It is a confidential client if it can keep a secret (a server-side web application), and a public client if it cannot (a mobile or desktop app, or JavaScript running in a browser, where anything shipped to the device can be extracted).
  • The authorization server (AS) authenticates the user, obtains consent, and issues tokens.
  • The resource server (RS) is the API that holds the data and accepts tokens.

The AS and RS are often the same organisation and sometimes the same program, but the roles are separate: the one issues, the other checks. The user's password goes only to the AS. Keep in mind the trust boundaries in the picture: the client never sees the password, and the RS never sees the user at all, only the token.

Authorization code flow with PKCE, step by step

The authorization code grant is the flow to use for nearly everything with a user in it. Its core trick: the browser (which the user controls, and where URLs can leak) only carries a short-lived, single-use code; the real tokens travel over a direct back-channel between client and AS. Here are the messages, with example values. (example.com names are placeholders.)

  1. The client prepares. It generates a random state, and, for PKCE, a random code_verifier and its hash code_challenge = BASE64URL(SHA-256(code_verifier)). It stores them in the user's session and redirects the browser to the AS: 
    GET https://auth.example.com/authorize
  ?response_type=code
  &client_id=photo-print
  &redirect_uri=https%3A%2F%2Fprint.example.org%2Fcb
  &scope=photos.read
  &state=af0ifjsldkj
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  &code_challenge_method=S256
  2. The AS authenticates the user and asks for consent. It checks that redirect_uri is exactly one the client registered. The user signs in using whatever the AS supports (passwords, MFA, passkeys: chapter 5), and sees what is being requested.
  3. The AS redirects back with a code. 
    HTTP/1.1 302 Found
Location: https://print.example.org/cb?code=SplxlOBeZQQYbYS6WxSbIA&state=af0ifjsldkj
  4. The client checks state against the value in the user's session, and rejects the callback if it differs or is missing.
  5. The client redeems the code on the back channel, proving it is the party that started the flow: 
    POST https://auth.example.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fprint.example.org%2Fcb
&client_id=photo-print&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
    A confidential client also authenticates here (a client secret, a signed assertion, or mutual TLS).
  6. The AS validates and issues tokens. The code must be unused, unexpired, issued to this client and this redirect_uri, and the hash of the code_verifier must equal the challenge from step 1. The response contains an access_token, a token_type (Bearer), expires_in, usually a refresh_token, and with OpenID Connect an id_token.
  7. The client calls the API with Authorization: Bearer <access_token>. The RS validates the token and enforces the scopes (chapter 8 covers what else it must check).

Everything travels over TLS (networking chapter 11); the redirect URI of a real deployment must be HTTPS (or a registered app-claimed link or loopback address for native apps).

What each parameter is for

MechanismBinds what to whatAttack it stops
redirect_uri, exact matchThe code to a pre-registered destinationAn attacker redirecting the code or token to a place they control
stateThe callback to the browser session that began the flowForged callbacks (login CSRF): an attacker making your browser finish their flow

nonce (OIDC)The ID token to the client's sessionReplay of an ID token into a different login

PKCE (Proof Key for Code Exchange, RFC 7636, pronounced "pixie") was invented for mobile apps, where another app on the device could register the same custom URL scheme and receive the redirect, so a stolen code would be redeemable. Because the verifier never leaves the client until the back-channel redemption, and only its hash was ever in the URL, a thief with the code cannot use it. RFC 9700 now says public clients must use PKCE, recommends it for confidential clients too, and requires authorization servers to support it. Always choose the S256 method; the plain method sends the verifier itself as the challenge and defeats the point.

The code below is a small, runnable model of these checks: PKCE verified against the RFC 7636 test vector, a token endpoint that enforces the code rules, a loose and an exact redirect matcher, and a state check. It simulates an authorization server in one process; there is nothing to attack but your own functions. (Lab 3 builds a fuller version with a client and API.)

"""PKCE (RFC 7636), redirect_uri matching and state checking, as pure functions. No network, no real server."""
import base64, hashlib, hmac, secrets
from urllib.parse import urlsplit

def b64u(b: bytes) -> str:
    return base64.urlsafe_b64encode(b).rstrip(b"=").decode()

def make_verifier() -> str:
    return b64u(secrets.token_bytes(32))              # 43 characters, from the unreserved set

def challenge_s256(verifier: str) -> str:
    return b64u(hashlib.sha256(verifier.encode("ascii")).digest())

# RFC 7636 Appendix B test vector
V = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"
print("RFC 7636 vector matches:", challenge_s256(V) == "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM")

# --- what the token endpoint does with a code ---------------------------------------------------
class AuthServer:
    REGISTERED = {"app-1": "https://app.example.com/callback"}
    def __init__(self, exact: bool = True):
        self.exact, self.codes = exact, {}
    def redirect_ok(self, client_id: str, uri: str) -> bool:
        reg = self.REGISTERED[client_id]
        if self.exact:
            return uri == reg                                       # RFC 9700: exact string match
        return uri.startswith(reg.rsplit("/", 1)[0])                # the classic loose "prefix" check
    def authorize(self, client_id, redirect_uri, challenge):
        if not self.redirect_ok(client_id, redirect_uri):
            return None
        code = secrets.token_urlsafe(16)
        self.codes[code] = (client_id, redirect_uri, challenge)
        return code
    def token(self, code, client_id, redirect_uri, verifier):
        rec = self.codes.pop(code, None)                            # single use
        if rec is None: return "invalid_grant: unknown or used code"
        cid, uri, chal = rec
        if (cid, uri) != (client_id, redirect_uri): return "invalid_grant: client or redirect mismatch"
        if not hmac.compare_digest(challenge_s256(verifier or ""), chal): return "invalid_grant: PKCE verifier mismatch"
        return "access_token issued"

def state_ok(session_state: str, returned: str) -> bool:
    return bool(session_state) and hmac.compare_digest(session_state, returned)

legit = "https://app.example.com/callback"
evil = "https://app.example.com.attacker.test/callback"                # a look-alike host
print("\nredirect_uri matching")
for exact in (False, True):
    s = AuthServer(exact=exact)
    print(f"  exact={exact!s:5}  legit accepted: {s.redirect_ok('app-1', legit)}   look-alike accepted: {s.redirect_ok('app-1', evil)}")

print("\ncode interception")
verifier = make_verifier()
srv = AuthServer(exact=True)
code = srv.authorize("app-1", legit, challenge_s256(verifier))
print("  attacker redeems stolen code, no verifier:   ", srv.token(code, "app-1", legit, None))
code = srv.authorize("app-1", legit, challenge_s256(verifier))
print("  attacker guesses a verifier:                 ", srv.token(code, "app-1", legit, make_verifier()))
code = srv.authorize("app-1", legit, challenge_s256(verifier))
print("  real client with its verifier:               ", srv.token(code, "app-1", legit, verifier))
print("  same code used again:                        ", srv.token(code, "app-1", legit, verifier))

print("\nstate on the callback")
sess = secrets.token_urlsafe(16)
print("  callback with our state:     ", state_ok(sess, sess))
print("  forged callback, other state:", state_ok(sess, secrets.token_urlsafe(16)))
print("  forged callback, no session: ", state_ok("", "anything"))

Look at the redirect results. The loose "starts with the registered host" rule accepts app.example.com.attacker.test, a different domain whose name merely begins with the right characters. Prefix and wildcard rules, and registered pages that contain an open redirector (a URL on your own site that forwards visitors anywhere), are how authorization codes and tokens have leaked in practice. RFC 9700 therefore requires authorization servers to compare redirect URIs by exact string match (the only exception is the port of loopback addresses for native apps).

Client credentials: no user at all

When one service calls another on its own behalf (a nightly job calling the billing API), there is no resource owner. The client credentials grant gives the service its own token: it authenticates to the token endpoint (grant_type=client_credentials) with a secret, a signed JWT, or mutual TLS (chapter 4), and receives an access token whose scopes describe what the service may do. There is no consent screen and no refresh token (the service just asks again). Practical rules: give each service its own client identity (never share one), keep the lifetime short, request only the scopes it needs, hold the client secret in a secret store rather than an image (chapter 4), and prefer platform-issued workload identity over static secrets where you can (chapter 14). Treat the token endpoint as a high-value target and rate-limit it.

Why the implicit and password grants are discouraged

OAuth 2.0 originally defined four grants. Two have been retired in practice, and the OAuth 2.0 Security Best Current Practice (RFC 9700, January 2025, also known as BCP 240) says why.

  • Implicit grant (response_type=token): the AS returned the access token directly in the redirect URL's fragment, designed for JavaScript apps before browsers allowed cross-origin requests. The token lands in browser history, can leak through scripts, extensions or Referer headers, is exposed to injection of stolen tokens, and cannot be bound to the client. RFC 9700 says clients should not use it. The authorization code flow with PKCE does the same job safely.
  • Resource owner password credentials grant: the client collects the username and password and posts them to the AS. That puts the user's password in the client again, which is the very problem OAuth was created to remove; it also blocks MFA and passkeys. RFC 9700 says it must not be used.

The draft "OAuth 2.1" consolidates these changes (PKCE required, exact redirects, no implicit or password grants); as of this writing treat RFC 9700 as the normative guidance. For devices without a browser, such as a TV, there is a separate device authorization grant (RFC 8628), and native apps should follow RFC 8252: use the system browser, not an embedded web view the app could snoop on.

Tokens, scopes and consent

A bearer token (RFC 6750) works for whoever holds it, like cash. Its security rests on secrecy, TLS, short life and narrow scope. Two ways to make a token sender-constrained, so a stolen copy is useless without a key the legitimate client holds: DPoP (RFC 9449, a signed proof per request) and mutual-TLS-bound tokens (RFC 8705). RFC 9700 expects refresh tokens for public clients to be sender-constrained or rotated (chapter 6).

An access token may be opaque (a random string the RS validates by asking the AS: token introspection, RFC 7662) or a JWT that the RS verifies locally (a standard profile is RFC 9068). Chapter 6's rules apply in full: verify the signature with a fixed algorithm, then iss, aud, exp. The RS must reject tokens whose audience is not itself; RFC 9700 adds that access tokens should be audience-restricted. Clients should treat access tokens as opaque and not parse them.

A scope is a named permission the client asks for, such as photos.read. The user consents to scopes, the AS puts them in the token, and the RS enforces them. Three points that cause mistakes:

  • A scope limits the client; it does not grant the user rights they do not have. The effective permission is the intersection of the scope and what the user is allowed to do. The RS must still run its own authorization (chapter 8).
  • Ask for the narrowest scopes, and ask when needed (incremental consent) rather than everything at install.
  • Consent screens only help if people can read them. Users approve broad requests from convincing-looking apps (illicit consent grants). Defences are server-side: verified publishers, admin approval for risky scopes, review and expiry of grants.

A refresh token lets the client obtain new access tokens without sending the user back through login, so access tokens can be short-lived. Refresh tokens are bound to the client, can be revoked (RFC 7009 defines a revocation endpoint), and are valuable, so keep them server-side where possible (the backend-for-frontend pattern of the previous chapter) and rotate them.

OpenID Connect: adding identity

OpenID Connect (OIDC, OpenID Connect Core 1.0 from the OpenID Foundation) is a thin identity layer on OAuth 2.0. A client adds the scope openid to the same authorization code flow and the token response contains an additional ID token: a JWT that is a signed statement by the provider about the authentication event.

The ID token contains claims such as iss (the provider), sub (a stable identifier for the user at that provider), aud (the client's id), exp, iat, and nonce, plus optionally auth_time and how the user authenticated. The client must validate it as in chapter 6 and also check:

  1. the signature, using the provider's keys, published at the jwks_uri (a JSON Web Key Set, rotated by key id);
  2. iss equals the issuer the client expects (this is also what protects against a token from a different provider);
  3. aud contains the client's own client_id;
  4. exp has not passed;
  5. nonce equals the random value the client sent in the authorization request and kept in the session. This ties the ID token to this login; without it an attacker could replay a captured ID token into another session.

Three distinctions cause most OIDC bugs:

  • ID token versus access token. The ID token is for the client: it says who signed in. The access token is for the API. Never send an ID token to an API as an access credential, and never accept one there. An API that did so would accept a token minted for any client of that provider.
  • OAuth alone is not login. If an app treats "I received an access token" as "the user is logged in", a malicious app that tricked a user into authorizing it can replay that user's access token to log in to other apps that use the same provider. The ID token's aud is what closes this.
  • The user's key is (iss, sub), not their email address. Email addresses can be changed, recycled, or asserted unverified by some providers. Linking accounts by email alone has led to real account takeovers. Key accounts by iss plus sub, and require email_verified only for contact purposes.

The userinfo endpoint returns more claims (name, email, picture) about the user when called with the access token, so the ID token can stay small. Discovery lets a client configure itself from one URL: the provider publishes a JSON document at /.well-known/openid-configuration under its issuer URL, listing the issuer, the authorization, token and userinfo endpoints, the jwks_uri, the supported scopes and signing algorithms. Fetch it over HTTPS from the issuer you configured, and check that the issuer value inside matches.

Single sign-on and federation

Single sign-on (SSO) lets a user authenticate once to an identity provider (IdP) and then use many applications, each of which trusts the IdP's signed statement rather than keeping its own passwords. Federation is the same idea across organisational boundaries: your employer's IdP vouches for you to a vendor's application. OIDC is the modern, JSON and JWT form of this.

SAML 2.0 (OASIS, 2005) is the older, XML-based protocol for the same job, and still dominant in enterprise software. An application (the service provider) redirects the browser to the IdP, which authenticates the user and posts a digitally signed XML assertion back through the browser. Its weak spot is the complexity of signed XML: the signature covers part of a document, and parsers that verify one element but read another have produced a family of bugs called XML signature wrapping. Its security properties are otherwise similar: validate the signature, the issuer, the audience, the validity period and that the assertion answers a request you made.

Federation changes your threat model. One identity provider compromise unlocks every connected application, and its signing keys are among the most valuable secrets you own (case 5 is a signing-key story). Logging out is also hard: each application has its own session (chapter 6), so disabling a user at the IdP does not instantly end sessions elsewhere. Design for it with short sessions, back-channel logout where supported, and revocation on your side. The identity design for a multi-tenant SaaS, with customers bringing their own IdPs, is the subject of studio 1.

Attacks to recognise

  • Authorization code interception. The code leaks (a malicious app with the same URL scheme, a log, a Referer header) and is redeemed by someone else. Stopped by PKCE and by single-use, short-lived codes.
  • Redirect manipulation. The attacker alters redirect_uri or exploits loose matching or an open redirector so that the code or token is delivered to them. Stopped by exact matching of registered URIs and by removing open redirectors from your own site.
  • CSRF on the callback (login CSRF). The attacker makes the victim's browser complete the attacker's authorization, so the victim's session ends up linked to the attacker's account. Stopped by state (or PKCE) bound to the user's session.
  • Mix-up attacks. A client that works with several authorization servers can be tricked into sending a code (or a token request) to the wrong one, which the attacker runs. The defence in RFC 9700 is for the AS to return its iss in the authorization response (RFC 9207) and for the client to check it matches the server it started with, or to use a distinct redirect URI per issuer.
  • Token theft and replay. Bearer tokens stolen from logs, storage or intermediaries are usable by the thief. Mitigations: short life, narrow scope and audience, no tokens in URLs or logs, and sender-constrained tokens for high-value APIs.

Analogy: a valet key

A car's valet key starts the engine but does not open the trunk or the glovebox. You hand it over without handing over your master key, and the dealer can cut you a new one if it is lost. The scope is "drive, don't unlock"; the token is the valet key; the authorization server is the dealer who issues and can invalidate keys.

Where it breaks down: a physical valet key is obviously a limited key. In OAuth, scopes are only names; the resource server has to decide what each name actually allows, and a sloppy API will honour a broad scope for things the user never intended.

Distributed systems connection

OAuth is a protocol for establishing trust between parties that share no database, with message exchanges that can be replayed, delayed or forged, so its design resembles the careful protocols of the distributed course: single-use codes are idempotency guards, state and nonce correlate a response with its request, and short expiries with refresh are leases. Validation of a JWT at many resource servers needs fresh signing keys at every one of them, and key rotation across that fleet is the same rolling-upgrade problem as in chapter 4. The authorization server is also a single point of failure for every login, so it deserves the availability design of the reliability course.

Key takeaways

  • OAuth 2.0 (RFC 6749) is delegated authorization: a client receives a limited, revocable token instead of the user's password. It is not, by itself, authentication.
  • Use the authorization code flow with PKCE (RFC 7636, S256). Check state, require exact string matching of registered redirect_uri values, and treat the code as single use and short lived.
  • Client credentials is for service-to-service calls with no user: separate identity per service, short-lived tokens, narrow scopes, secrets in a store.
  • RFC 9700 (the OAuth 2.0 Security BCP, January 2025): do not use the implicit grant, never use the password grant, require PKCE for public clients, match redirect URIs exactly, and protect refresh tokens by sender-constraint or rotation.
  • OpenID Connect adds an ID token (a JWT for the client: who signed in) to the flow. Validate signature, iss, aud, exp and nonce. Never use an ID token as an API credential, and key users by (iss, sub), not email.
  • SSO and federation centralise authentication in an identity provider, which concentrates risk. SAML is the XML-era equivalent of OIDC.
  • Know the four attack shapes: code interception (PKCE), redirect manipulation (exact matching), callback CSRF (state or PKCE), and mix-up (the iss parameter, RFC 9207).

Check your understanding

A mobile app registers the custom URL scheme myapp://cb. A malicious app on the same phone registers it too and receives the authorization code. Which defence stops it from obtaining tokens?

  1. The state parameter
  2. PKCE: the thief lacks the code verifier whose hash was sent at the start
  3. Making the code longer
  4. Encrypting the redirect
This is exactly the scenario PKCE was created for. state protects the callback against forgery but does nothing about a legitimate code being copied. The thief would also need the verifier, which never leaves the genuine client until the back-channel call.

An authorization server validates redirect_uri with startswith("https://app.example.com"). What is the flaw?

  1. None; this is the recommended check
  2. It rejects HTTPS
  3. It is slow
  4. It also accepts look-alikes such as https://app.example.com.attacker.test/cb, delivering codes to the attacker; RFC 9700 requires exact string matching
Prefix and wildcard matching has leaked codes and tokens in practice, including through open redirectors on the legitimate host. Compare to the registered string exactly (only loopback ports may vary for native apps).

An app logs a user in by receiving an OAuth access token and calling the provider's profile API with it. Why is that not a safe login design?

  1. Possession of an access token does not show it was issued to this app for this login; an attacker app that got the user's token elsewhere can replay it. OIDC's ID token, with audience and nonce, fixes this
  2. Access tokens cannot be sent over HTTPS
  3. Profile APIs are always slow
  4. The provider rejects such calls
OAuth tells the API that a token is valid, not who logged in to your app or for whom the token was minted. The ID token is audience-restricted to the client and can carry a nonce, so the client can verify the login event is for itself.

Why does RFC 9700 say the resource owner password credentials grant must not be used?

  1. It is too fast
  2. It does not produce tokens
  3. The client handles the user's password, which defeats the purpose of OAuth and blocks MFA and passkeys
  4. It only works on mobile devices
The reason OAuth exists is to keep passwords away from clients. This grant brings them back, trains users to type credentials into third parties, and cannot take part in browser-based second factors.

Your API receives an ID token in the Authorization header, correctly signed by your identity provider. What should it do?

  1. Accept it, since the signature is valid
  2. Reject it: an ID token is addressed to the client application (its aud is the client id), not to the API, and it is not an authorization credential
  3. Accept it for read-only calls
  4. Decrypt it first
Accepting ID tokens at an API would let a token minted for any client of that provider act as an access credential. APIs accept access tokens whose audience is the API, with the right scopes.

A client supports two identity providers, one of them hostile. How does the iss authorization-response parameter (RFC 9207) help?

  1. It encrypts the code
  2. It replaces PKCE
  3. It shortens the token
  4. The client compares it to the provider it started the flow with, and aborts on mismatch, so a code from one server is never sent to the other
This stops mix-up attacks, where a client is led to send a legitimate provider's code to the attacker's server. It is complementary to PKCE, not a replacement.

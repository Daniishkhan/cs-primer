Sessions, Cookies & Tokens

A login happens once; the proof has to survive hundreds of later requests. HTTP forgets everything between requests, so something must carry "this is alice" along: a session id, a cookie, a signed token. This chapter compares the two designs, the cookie attributes that matter, how a JSON Web Token is built and how verifiers get it wrong, and the hard question underneath all of them: how do you take a credential back?

Why this matters

After authentication, the session credential is the user as far as the system can tell. Whoever holds it is alice. Most real-world token problems are not broken cryptography; they are a verifier that skipped a check, a token that lives for a month, a cookie readable by a script that should never have run, or a signing key that leaked (the subject of case 5). Getting this layer right means choosing where state lives and being able to answer "how fast can I make this credential stop working?"

The problem: HTTP is stateless

As networking chapter 10 explained, each HTTP request stands alone and cookies are the usual way to link them: the server sends Set-Cookie, the browser returns the value in a Cookie header on later requests to the same site. Authentication adds a requirement the original design did not have: the value must be unforgeable (a stranger cannot make one), unguessable, and revocable. There are two ways to build it.

Server-side sessions

The server creates a random session id (an opaque string, at least 128 bits from a CSPRNG, so nobody can guess another user's), stores a record under it (user, creation time, expiry, maybe roles and device), and gives the browser only the id. Every request does a lookup. The id means nothing without the server's table.

  • Pros: revocation is immediate (delete the row); the credential carries no data to leak or go stale; you can list a user's sessions, log out everywhere, and change permissions mid-session.
  • Cons: every request needs the store, which becomes a shared, available, fast dependency (a cache or database, replicated across regions if you serve several). The scalable answer is the one you know from the architecture course: keep it in a replicated store such as Redis, and design for its failure.

Self-contained tokens

A self-contained token carries its claims (who, for whom, until when) and a signature or MAC, so any service holding the right key can check it without calling anyone. This suits services that must verify a credential without sharing a database, and it suits delegation across organisations (the next chapter). The price is in the cons:

  • You cannot easily take one back. Until it expires, it is valid wherever the key verifies it.
  • Claims are a snapshot. If alice loses a role, tokens issued an hour ago still say she has it.
  • The format is a rich target for verifier mistakes (below).

"Stateless" is a cost shifted, not removed

A system that needs revocation, logout or instant permission changes ends up storing state anyway (a denylist, a version number, a refresh-token table). That is fine, but then the honest comparison is not "state versus no state" but "a lookup on every request versus a lookup only when a token is issued or refreshed". For a single web application talking to its own backend, plain server-side sessions are usually the simpler and safer choice. Tokens earn their place when verification must happen in many services or across trust domains.

Other session hygiene that belongs here: regenerate the session id at login (otherwise an attacker who planted a known id before login, a session fixation attack, shares the authenticated session); never put the id in a URL, where logs and Referer headers copy it; enforce both an idle timeout and an absolute maximum lifetime; and destroy the server-side record at logout rather than only clearing the cookie.

JSON Web Tokens

The most common self-contained token is the JSON Web Token (JWT, pronounced "jot"), defined in RFC 7519. A signed JWT is a JSON Web Signature (JWS, RFC 7515) in its compact form: three base64url-encoded parts separated by dots.

  • Header: JSON naming the algorithm (alg), the type, and often a key id (kid) so the verifier can choose among several keys.
  • Payload: a set of claims. RFC 7519 registers short names: iss (issuer), sub (subject), aud (audience: who the token is for), exp (expiry), nbf (not before), iat (issued at) and jti (a unique id). Anything else is a custom claim.
  • Signature: computed over the exact text header.payload. With HS256 it is HMAC-SHA-256 under a shared key; with RS256 or ES256 it is a public-key signature, so verifiers need only the public key (chapter 3).

The signature gives integrity and authenticity, nothing else. The payload is merely encoded: anyone can read it, which is why a JWT must never carry secrets (passwords, API keys, personal data you would not print in a log). If confidentiality is required, JWE (RFC 7516) encrypts the token, but most deployments are better served by an opaque id and a lookup. The current guidance on using them safely is RFC 8725, "JSON Web Token Best Current Practices".

Writing one, and breaking a bad verifier

The code below builds an HS256 token with the standard library and a verifier written the safe way: the verifier, not the token, decides the algorithm, and a valid signature is followed by checks of issuer, audience and expiry. It then runs two deliberately broken verifiers against forged tokens. Everything happens in one process, against toy verifiers written for this lesson.

"""HS256 JWT (RFC 7519 / RFC 7515) with the stdlib, a correct verifier, and two broken ones.
Everything runs in this one process against our own toy verifiers."""
import base64, hashlib, hmac, json, time

def b64u(b: bytes) -> str:
    return base64.urlsafe_b64encode(b).rstrip(b"=").decode()

def unb64u(s: str) -> bytes:
    return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))

def encode(claims: dict, key: bytes, header_extra: dict | None = None) -> str:
    header = {"alg": "HS256", "typ": "JWT", **(header_extra or {})}
    signing_input = b64u(json.dumps(header, separators=(",", ":")).encode()) + "." + \
                    b64u(json.dumps(claims, separators=(",", ":")).encode())
    sig = hmac.new(key, signing_input.encode(), hashlib.sha256).digest()
    return signing_input + "." + b64u(sig)

class InvalidToken(Exception):
    pass

def verify(token: str, key: bytes, *, iss: str, aud: str, now: float, leeway: int = 30) -> dict:
    """The correct shape: the VERIFIER decides the algorithm; the header never does."""
    try:
        h_b64, p_b64, s_b64 = token.split(".")
        header = json.loads(unb64u(h_b64)); claims = json.loads(unb64u(p_b64))
    except Exception:
        raise InvalidToken("malformed")
    if header.get("alg") != "HS256":                      # allow-list, fixed server-side
        raise InvalidToken(f"alg {header.get('alg')!r} not allowed")
    expected = hmac.new(key, f"{h_b64}.{p_b64}".encode(), hashlib.sha256).digest()
    if not hmac.compare_digest(expected, unb64u(s_b64)):
        raise InvalidToken("bad signature")
    if claims.get("iss") != iss:                          # signature alone is not enough
        raise InvalidToken("wrong issuer")
    aud_claim = claims.get("aud"); auds = aud_claim if isinstance(aud_claim, list) else [aud_claim]
    if aud not in auds:
        raise InvalidToken("wrong audience")
    if "exp" not in claims or now > claims["exp"] + leeway:
        raise InvalidToken("expired or no exp")
    if "nbf" in claims and now < claims["nbf"] - leeway:
        raise InvalidToken("not yet valid")
    return claims

# ---- BROKEN verifier #1: believes the header's alg -------------------------------------------
def naive_verify(token: str, key: bytes) -> dict:
    h_b64, p_b64, s_b64 = token.split(".")
    header = json.loads(unb64u(h_b64))
    alg = header["alg"]                                   # <-- attacker-controlled input
    if alg == "none":
        return json.loads(unb64u(p_b64))                  # "no signature needed", says the token
    if alg == "HS256":
        expected = hmac.new(key, f"{h_b64}.{p_b64}".encode(), hashlib.sha256).digest()
        if hmac.compare_digest(expected, unb64u(s_b64)):
            return json.loads(unb64u(p_b64))
    raise InvalidToken("bad signature")

# ---- BROKEN verifier #2: algorithm confusion -------------------------------------------------
# The service really signs with RS256 (private key) and verifies with a PUBLIC key that everybody
# can download. Python's stdlib has no RSA, so RS256 is stubbed; what matters is the dispatch.
PUBLIC_KEY_BYTES = b"-----BEGIN PUBLIC KEY-----\nMIIBIjANBgkq...(published at /jwks)...\n-----END PUBLIC KEY-----\n"

def confused_verify(token: str, public_key: bytes) -> dict:
    h_b64, p_b64, s_b64 = token.split(".")
    alg = json.loads(unb64u(h_b64))["alg"]
    if alg == "RS256":
        raise InvalidToken("(RSA verification would happen here; attacker has no private key)")
    if alg == "HS256":                                    # same "key" variable, now used as an HMAC secret
        expected = hmac.new(public_key, f"{h_b64}.{p_b64}".encode(), hashlib.sha256).digest()
        if hmac.compare_digest(expected, unb64u(s_b64)):
            return json.loads(unb64u(p_b64))
    raise InvalidToken("bad signature")

Walk through the failures, since each is a real bug class:

  1. alg: none. The JWT and JWA specifications (RFC 7519 section 6, RFC 7518) allow an "unsecured" token with no signature. A verifier that reads alg from the header and honours none accepts any payload an attacker writes. The cure is not to filter the word "none" but to never take the algorithm from the token. Fix the accepted algorithm(s) in server configuration.
  2. Algorithm (key) confusion. A service issues RS256 tokens, and verifies with the issuer's public key, which is public by design. A verifier that picks the algorithm from the header can be told "HS256", then uses the same public-key bytes as an HMAC secret. The attacker knows those bytes, so they sign an HS256 token that verifies. In the demonstration RSA itself is stubbed (the standard library has none); the bug is in the dispatch, not the mathematics. The cure is the same: the key object must be bound to one algorithm, and the verifier must refuse a header that disagrees.
  3. Signature checked, claims ignored. A correctly signed token is only proof that some issuer you trust signed something. Without checking iss you may accept tokens minted for another system with the same key; without aud you accept a token meant for a different API (the confused deputy, chapter 8); without exp you accept a stolen token forever.
  4. Other classic mistakes: trusting header fields that let the token name its own key (embedded keys or a URL to fetch keys from), using kid as an unvalidated file path or database key, accepting any token type in any place (set and check typ or use distinct audiences), and comparing signatures with ordinary string equality (use a constant-time compare, chapter 3).

Use a maintained JWT library, configure the allowed algorithms and the expected issuer and audience explicitly, and write tests that feed it each of the forgeries above.

Analogy: a festival wristband

A wristband (self-contained token) lets any gate guard see at a glance that you paid, without phoning the box office. A tamper-proof band (signature) is hard to forge. But the guard looking at a band from a different festival (wrong audience or issuer) must turn you away, and once a band is on your wrist the box office cannot reach out and cancel it.

Where it breaks down: real bands are physical and expire at the end of the weekend by design. A software token only expires if someone remembered to set exp and the verifier checks it.

Taking a credential back: revocation strategies

Revocation is where self-contained tokens pay for their convenience. The strategies, in the order most systems adopt them:

  1. Short-lived access tokens. Make access tokens valid for minutes (commonly 5 to 15). A stolen one dies on its own, and "revocation" for the access token is just waiting. This also bounds staleness of claims. It is a lease in the sense of distributed chapter 4: authority that lapses unless renewed, which trades revocation for bounded delay.
  2. Refresh tokens with rotation and reuse detection. Pair the short access token with a longer-lived refresh token that can be exchanged for a new access token at the authorization server, which can consult state. With rotation, each use returns a new refresh token and invalidates the old one; with reuse detection, presenting an already-used token proves a copy exists somewhere, so the server revokes the whole family descended from that login. RFC 9700 requires refresh tokens of public clients to be sender-constrained or rotated.
  3. Denylists. Keep a set of revoked token ids (jti) that verifiers check. It needs distribution to every verifier, and it only has to hold an entry until the token's own exp, so it stays small.
  4. Session or token version numbers. Store a counter per user (or per session). Put its value in each token; when the user logs out everywhere, changes password or is disabled, increment it. Verifiers compare with the current value, which costs a (cacheable) read, and every older token fails at once.
  5. Introspection. The verifier asks the authorization server whether an opaque token is active (RFC 7662). It is the server-side-session model again, behind an API.

A few lines of Python show reuse detection (in-memory, the thief and the client are the same script):

"""Refresh-token rotation with reuse detection (in-memory, deterministic)."""
import secrets

class AuthServer:
    def __init__(self):
        self.families = {}      # family_id -> {"current": token, "revoked": bool}
        self.owner = {}         # token -> family_id (every token ever issued)

    def login(self, user: str) -> str:
        fam = secrets.token_hex(4)
        tok = secrets.token_urlsafe(8)
        self.families[fam] = {"user": user, "current": tok, "revoked": False}
        self.owner[tok] = fam
        return tok

    def refresh(self, tok: str):
        fam = self.owner.get(tok)
        if fam is None:
            return None, "unknown token"
        f = self.families[fam]
        if f["revoked"]:
            return None, "family already revoked"
        if tok != f["current"]:                       # an OLD token came back: someone has a copy
            f["revoked"] = True
            return None, "REUSE DETECTED: whole family revoked"
        new = secrets.token_urlsafe(8)                # rotate: old token is now dead
        f["current"] = new; self.owner[new] = fam
        return new, "ok (new refresh token + new short access token issued)"

srv = AuthServer()
t0 = srv.login("alice")
t1, msg = srv.refresh(t0);   print("alice refreshes t0:       ", msg)
t2, msg = srv.refresh(t1);   print("alice refreshes t1:       ", msg)
_, msg = srv.refresh(t0);    print("thief replays stolen t0:  ", msg)
_, msg = srv.refresh(t2);    print("alice refreshes t2:       ", msg, "-> she must log in again")
alice refreshes t0:        ok (new refresh token + new short access token issued)
alice refreshes t1:        ok (new refresh token + new short access token issued)
thief replays stolen t0:   REUSE DETECTED: whole family revoked
alice refreshes t2:        family already revoked -> she must log in again

Notice the cost: the real user is logged out too, because the server cannot tell which holder is legitimate. That is the right trade for a suspected theft.

Distributed systems connection

Revocation is cache invalidation with an adversary. Every verifier that keeps a copy of "token X is valid" for speed is a replica that may be stale. Short expiry bounds the staleness by time rather than by message delivery, which is why leases and expiring credentials appear again and again. A denylist or version counter needs propagation to every node, so the question to ask in a design review is the same as for any replicated state: how stale can a verifier be, and what can an attacker do in that window?

Where does the browser keep the token?

This question draws more heat than it deserves, so here is an honest summary instead of a slogan. The enemy is cross-site scripting (XSS, chapter 10): script injected into your page runs with the page's full authority.

WhereHelps withWeaknesses
HttpOnly cookieScript cannot read or exfiltrate the credential. Persists across reloads. Sent automatically.Sent automatically, so cross-site request forgery is a concern: use SameSite and anti-CSRF tokens. XSS can still make requests as the user.
localStorage or sessionStorageNot sent automatically (no CSRF by this route). Easy for APIs on other origins.Any script in the page can read it and send it anywhere. A single XSS or a compromised third-party script steals a credential that works from the attacker's own machine.
JavaScript memory onlyHarder to steal after the page is gone; not persisted.Lost on reload (needs a silent re-login or refresh via cookie); live XSS can still use or read variables it can reach.

The honest view: no browser-side storage survives XSS, because injected script can always make authenticated calls while the page is open. The differences are in what survives afterwards. An exfiltrated bearer token can be used for its full lifetime from anywhere; an HttpOnly cookie cannot be carried off the victim's browser. That is why the IETF's best-current-practice document for browser-based applications (RFC 10017, 2026) ranks a backend for frontend (BFF) as the most secure pattern: a small server component of your own application does the OAuth work, keeps the access and refresh tokens on the server, and gives the browser only a first-party session cookie with the attributes above. The tokens never reach JavaScript. The next chapter shows where that fits in OAuth.

Whatever you choose, put your effort first into preventing XSS (output encoding, a content security policy), because every browser-side choice is only as strong as the page's script integrity.

Key takeaways

  • A session carries state on the server and hands the client a pointer; a self-contained token carries the state and a signature. Sessions revoke instantly; tokens verify without a shared store. Prefer plain sessions for a single application.
  • Cookie flags: HttpOnly (script cannot read it), Secure (HTTPS only), SameSite (limits cross-site sending), __Host- (bound to one host, no subdomain overwrite). Regenerate the id at login and enforce idle and absolute timeouts.
  • A JWT (RFC 7519, signed as a JWS, RFC 7515) is three base64url parts. The payload is readable by everyone, so put no secrets in it.
  • Verifier rules: fix the algorithm in configuration (never trust the header: alg: none and RS/HS confusion), then check iss, aud, exp and nbf after the signature.
  • Revocation: short access tokens, refresh tokens with rotation and reuse detection, denylists by jti, per-user version numbers, or introspection. All of them reintroduce a little state.
  • No browser storage survives XSS. HttpOnly cookies at least stop the credential leaving the browser; a backend-for-frontend keeps tokens away from JavaScript entirely.

Check your understanding

An API accepts tokens whose header says "alg":"none" because its library selects the algorithm from the header. What is the correct fix?

  1. Block the string "none" in a filter
  2. Encrypt the token payload
  3. Configure the verifier with the allowed algorithm(s) and key, and reject any token whose header disagrees
  4. Shorten the token lifetime
The header is attacker-controlled input. A blocklist misses variants, and shorter lifetimes only shrink the window. The verifier must decide the algorithm itself, which also closes the HS256/RS256 confusion.

A token has a valid signature from your own issuer and has not expired, but its aud is billing.example.com and it arrives at api.example.com. What should api do?

  1. Reject it: the token was issued for a different recipient
  2. Accept it, because the signature is valid
  3. Accept it if the user is an administrator
  4. Ask the user to confirm
A valid signature says who issued the token, not who it is for. Accepting tokens meant for other services lets a compromise or a permissive scope in one service be replayed against another.

Which statement about HttpOnly is correct?

  1. It stops cross-site scripting from running
  2. It prevents the cookie being sent to the server over HTTP
  3. It makes the cookie value unguessable
  4. It stops page script from reading the cookie, but injected script can still make requests that carry it
HttpOnly reduces theft of the credential, not abuse of it during a live XSS. It is useful but is not a substitute for preventing XSS.

With refresh token rotation and reuse detection, the server sees a refresh token that was already exchanged. What does it conclude, and do?

  1. The client had a network error; it issues another token
  2. Two parties hold a copy, so one may be a thief; it revokes the whole token family and requires a new login
  3. The token has expired; it deletes only that token
  4. The user is on a new device; it trusts the newest holder
A single-use token seen twice proves it was copied. The server cannot tell which holder is genuine, so it invalidates the family. Hence the real user may need to sign in again.

A team stores a JWT in localStorage "because cookies are insecure". What is the most accurate comment?

  1. Correct: localStorage is protected from scripts
  2. Incorrect: cookies cannot be used for API calls
  3. It removes cookie-related CSRF risk but exposes the token to any script on the page; an XSS bug lets an attacker copy it and use it elsewhere
  4. It makes the token revocable
Every storage option has a trade-off. localStorage is readable by any script in the origin, which includes injected and third-party script. An HttpOnly cookie or a backend-for-frontend keeps the credential out of JavaScript.

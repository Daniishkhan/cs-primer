Authentication

Authentication answers one question: is this really the person, or the service, that it claims to be? Almost everything else in security (sessions, tokens, permissions, audit) assumes the answer is reliable. This chapter covers the three kinds of evidence, how to store passwords so that a stolen database is a setback and not a catastrophe, what the current NIST guidance says, and why multi-factor authentication, passkeys and the humble "forgot password" button decide how strong your login really is.

Why this matters

Stolen or guessed credentials sit behind a large share of account takeovers, and a login system has an unusual property: attackers get unlimited private practice. They can test guesses against their own copy of your password table with no rate limit and no log. So the design question is not "can they steal the table?" (assume sometimes yes, chapter 1) but "what does the table cost them to use?" This chapter answers that, and then asks the harder question about every login you build: what is the weakest way into this account, and is it the front door or the recovery path?

Identity, authentication, authorization

Three words that are often blurred. Identification is claiming who you are ("I am alice"). Authentication (authn) is proving it. Authorization (authz) is deciding what the proven identity may do, which is the subject of chapter 8. A system can fail at either independently: a flawless login in front of a service that never checks permissions is still wide open.

Authentication evidence comes in three kinds, called factors:

FactorExamplesTypical weakness
Something you knowpassword, PIN, passphraseGuessable, reusable across sites, phishable, can be copied without the owner noticing
Something you havephone, hardware security key, smart card, authenticator app seedCan be lost or stolen; software seeds can be copied; some can be relayed by a phishing page
Something you arefingerprint, faceNot secret and cannot be changed after a leak; error rates; usually unlocks a local device rather than being sent to a server

Multi-factor authentication (MFA) means combining different factors, so one theft is not enough. A password plus a security question is two things you know and is not MFA. Strength depends less on counting factors than on what the attacker must do: a phishing page that collects a password and a one-time code in real time defeats "password plus code" without stealing any device.

You already have the cryptographic pieces from chapter 3 (hashes, MACs, signatures, randomness) and the secrets-handling habits from chapter 4. Here they become a login system.

How passwords are attacked

Two situations have to be kept apart, because the defences are different.

  • Online attacks send guesses to your login endpoint. You see every attempt, so you can slow, block and alert.
  • Offline attacks happen after the credential table leaks (an injection bug, a backup in the wrong bucket, an insider). The attacker guesses on their own hardware, as fast as they can afford, and you see nothing. The only defence left is what you stored.

Everything in the next sections about hashing is about the offline case. The later sections on throttling and MFA are about the online case.

Storing passwords

Why a fast hash is the wrong tool

Chapter 3 introduced hash functions such as SHA-256 as fast, one-way and collision resistant. For passwords, fast is the bug. A fast hash lets an attacker test enormous numbers of candidates per second, and human-chosen passwords come from a tiny, well-known part of the space. Three layers of trouble:

  1. Unsalted hashes are identical for identical passwords. Anyone who sees two equal hashes knows the passwords match, and one precomputed table of hashes of common passwords (a rainbow table is the space-saving version) cracks every user at once.
  2. Even salted, a fast hash is cheap per guess. On the Python process measured below, a single core computes about five million SHA-256 hashes per second, with interpreter overhead. Dedicated cracking software on graphics processors is faster by orders of magnitude. At such rates, anything a human would think up is found quickly, and random-looking short passwords fall in minutes to days.
  3. Cost does not scale with the attacker's budget. Hardware gets cheaper every year; a fixed, tiny per-guess cost never improves.

Salts

A salt is a random value, unique per password, stored next to the hash and fed into it. It is not secret. It does two things: equal passwords produce different hashes, and the attacker cannot reuse one precomputation against the whole table, so they must attack each user separately. It does not make a single guess any slower, so a salt alone does not save a weak password. Use at least 16 random bytes from the CSPRNG (chapter 3), and let the library generate them.

Slow, tunable password hashes

A password-hashing function (also called a key-derivation function, KDF, used for passwords) takes a password and a salt and deliberately costs a tunable amount of work. The defender pays that cost once per login; the attacker pays it for every guess. The work factor is a dial you raise as hardware improves.

  • PBKDF2 (defined in RFC 8018) repeats HMAC many times. It is simple, widely available and approved for use in FIPS-140 validated settings, but needs almost no memory, so graphics processors and custom hardware parallelise it well.
  • bcrypt (Provos and Mazières, USENIX 1999) is built on the Blowfish cipher with an expensive key setup and a tunable "cost". It uses a little memory (4 KB) and has been battle tested. Its implementations read only the first 72 bytes of the password, so long passphrases are silently truncated unless the application handles it.
  • scrypt (Percival, 2009; RFC 7914) is memory-hard: computing it requires filling and reading a large block of memory, so each guess needs lots of RAM and parallel guessing hardware gets expensive. Parameters are N (the cost, a power of two), r (block size) and p (parallelism). Memory use is roughly 128 × N × r bytes.
  • Argon2 won the Password Hashing Competition in 2015 and is specified in RFC 9106. Argon2id is the variant to choose for passwords: it combines the side-channel resistance of Argon2i with the GPU resistance of Argon2d. Parameters are memory m, iterations t and parallelism p.

The OWASP Password Storage Cheat Sheet gives the following minimums. They are a floor, not a target; OWASP's own wording is to make bcrypt's work factor "as large as verification server performance will allow, with a minimum of 10".

Parameters are not the same across functions

"Cost 10" for bcrypt, "N = 217" for scrypt and "600,000" for PBKDF2 are different units. The OWASP pairs are chosen to give roughly comparable resistance, not equal running time. Measure on your own hardware, as the code below does.

Peppers

A pepper is a secret value shared by all passwords and not stored with the hashes: it lives in a secret store or HSM (chapter 4). In one common form it is the key of an HMAC applied to the password hash. If an attacker steals only the database, a pepper kept elsewhere means they cannot even begin guessing. OWASP's view is that a pepper is defence in depth rather than a replacement for slow hashing, and it has an operational cost: if it leaks, you cannot simply rotate it without forcing users to reset passwords, unless you version it as you would any key. Use it if you have a proper secret store; do not use it as an excuse for a fast hash.

Measuring it yourself

Here is a complete, runnable example that hashes with scrypt from the standard library, stores a self-describing string (the algorithm and its parameters travel with the hash, in the spirit of the PHC string format), compares in constant time, and prints how long each setting takes on your machine. It also shows two users with the same password getting different hashes.

"""Password storage with scrypt: salted, self-describing hashes and upgrade-on-login (stdlib only)."""
import base64, hashlib, hmac, secrets, time

def b64(b: bytes) -> str:
    return base64.b64encode(b).decode().rstrip("=")

def unb64(s: str) -> bytes:
    return base64.b64decode(s + "=" * (-len(s) % 4))

def hash_password(password: str, n: int = 2**14, r: int = 8, p: int = 1) -> str:
    salt = secrets.token_bytes(16)                      # unique random salt per password
    dk = hashlib.scrypt(password.encode(), salt=salt, n=n, r=r, p=p,
                        maxmem=256 * 1024 * 1024, dklen=32)
    # PHC-style string: algorithm and parameters travel with the hash
    return f"$scrypt$ln={n.bit_length() - 1},r={r},p={p}${b64(salt)}${b64(dk)}"

def parse(stored: str):
    _, alg, params, salt, dk = stored.split("$")
    kv = dict(x.split("=") for x in params.split(","))
    return alg, 2 ** int(kv["ln"]), int(kv["r"]), int(kv["p"]), unb64(salt), unb64(dk)

def verify(password: str, stored: str) -> bool:
    _, n, r, p, salt, dk = parse(stored)
    cand = hashlib.scrypt(password.encode(), salt=salt, n=n, r=r, p=p,
                          maxmem=256 * 1024 * 1024, dklen=len(dk))
    return hmac.compare_digest(cand, dk)                # constant-time comparison

TARGET = dict(n=2**15, r=8, p=1)                        # the policy we want today

def login(db: dict, user: str, password: str) -> bool:
    stored = db.get(user)
    if stored is None or not verify(password, stored):
        return False
    _, n, r, p, *_ = parse(stored)
    if (n, r, p) != (TARGET["n"], TARGET["r"], TARGET["p"]):
        db[user] = hash_password(password, **TARGET)    # we hold the plaintext only now
        print(f"  upgraded {user}: ln={n.bit_length()-1} -> ln={TARGET['n'].bit_length()-1}")
    return True

def timeit(f, reps=3):
    best = 1e9
    for _ in range(reps):
        t = time.perf_counter(); f(); best = min(best, time.perf_counter() - t)
    return best

if __name__ == "__main__":
    pw = "correct horse battery staple"
    salt = b"0123456789abcdef"
    print("Measured on this machine (best of 3):")
    t = timeit(lambda: [hashlib.sha256(pw.encode() + salt).digest() for _ in range(10000)]) / 10000
    print(f"  SHA-256 (one fast hash)       {t*1e6:9.2f} us  -> {1/t:12,.0f} guesses/s per core")
    t = timeit(lambda: hashlib.pbkdf2_hmac("sha256", pw.encode(), salt, 600_000))
    print(f"  PBKDF2-HMAC-SHA256, 600,000   {t*1e3:9.1f} ms  -> {1/t:12,.1f} guesses/s per core")
    for ln in (14, 15, 17):
        t = timeit(lambda: hashlib.scrypt(pw.encode(), salt=salt, n=2**ln, r=8, p=1,
                                          maxmem=512*1024*1024, dklen=32), reps=2)
        mem = 128 * 8 * 2**ln // 1024 // 1024
        print(f"  scrypt N=2^{ln} r=8 p=1 ({mem:3d} MiB) {t*1e3:7.1f} ms  -> {1/t:12,.1f} guesses/s per core")

    print("\nStored hash format, and two users with the same password:")
    a, b = hash_password(pw), hash_password(pw)
    print(" ", a); print(" ", b)
    print("  same password, different hashes:", a != b)
    print("  verify right:", verify(pw, a), "| verify wrong:", verify("Tr0ub4dor&3", a))

    print("\nUpgrade on login:")
    db = {"alice": hash_password("hunter2-but-longer", n=2**12), "bob": hash_password("another long phrase", n=2**15)}
    print("  alice wrong password ->", login(db, "alice", "nope"))
    print("  alice right password ->", login(db, "alice", "hunter2-but-longer"))
    print("  alice again          ->", login(db, "alice", "hunter2-but-longer"))
    print("  bob right password   ->", login(db, "bob", "another long phrase"))

Read the timings with a defender's eye. At the OWASP scrypt minimum (N = 217) one verification took about 184 ms and 128 MiB of memory. That is acceptable for a login, and for an attacker it is close to a million times as much work per guess as one SHA-256 on the same core (184 ms against 0.2 µs). Your budget is the other side of the same coin: at 20 logins per second, a 43 ms hash keeps most of a core busy, and a flood of fake login attempts becomes a way to burn your CPU. Two consequences: rate-limit before hashing, and cap password length (accept a generous maximum such as 64 characters or more, but not megabytes).

Do not leak whether an account exists

If "unknown user" returns instantly but "wrong password" takes 150 ms, response time tells an attacker which usernames are real. Verify against a dummy hash for unknown users so both paths cost the same, and return one generic message ("incorrect username or password"). Registration and password-reset pages leak existence too; there the usual answer is a neutral message ("if that address has an account, we have sent an email").

The relative picture is the lesson: slow hashing buys years against passwords that fast hashing loses in seconds, and no hash saves a password that is on a breached-password list.

Analogy: a combination lock that takes a minute to turn

A fast hash is a lock any thief can spin through a thousand combinations in a second. A slow hash is a lock whose dial takes a full second per attempt: you, with the right combination, wait one second; the thief with ten billion combinations to try is stuck for centuries. Salting means every door in the building has a different lock, so cracking one teaches nothing about the next.

Where it breaks down: a thief can buy more thieves and more locks to test in parallel. The work factor slows each guess; it does not stop an attacker with a large budget and a weak password. Memory-hard functions raise the price of those parallel rigs, which is why they are preferred.

Upgrading hashes on login

Your parameters will be out of date in a few years, and you may inherit users hashed with something weak. You cannot recompute a hash without the password, and you only hold the password for a moment at login. So the standard technique is upgrade on login:

  1. Store the algorithm and parameters with each hash.
  2. When a user logs in, verify with the parameters stored in their record.
  3. If verification succeeds and the stored parameters are weaker than today's policy, hash the password again with the new parameters and overwrite the record.

The demonstration above does exactly this: alice's N = 212 hash becomes N = 215 on her next successful login, and bob's already-current hash is left alone. Users who never come back keep old hashes; OWASP's suggestions are to leave them or eventually remove them and require a reset. For a whole-table migration without waiting (for example, moving off an unsalted MD5 table), a common trick is to wrap: store new_hash(old_hash) immediately, and replace the wrapper with a direct hash on each user's next login. This is the same rolling-upgrade pattern you saw for key rotation in chapter 4: versioned formats, old and new coexisting.

What NIST says about passwords

NIST SP 800-63B is the US government's guidance for the authentication part of digital identity. It is widely used as a reference outside government too. The current version is Revision 4 (2025). Several of its positions reverse folk wisdom that many sites still follow. The statements below were checked against the text of Revision 4:

  • Length matters most. A password used as a single factor must be at least 15 characters. Where the password is one part of multi-factor authentication, the minimum is 8. Systems should allow at least 64 characters, and every Unicode code point counts as one character.
  • No composition rules. Verifiers must not impose other composition rules such as "one uppercase, one digit, one symbol". Those rules push people to Password1!.
  • No forced periodic changes. Verifiers must not require users to change passwords periodically. A change is required only when there is evidence the authenticator was compromised. Scheduled rotation mostly produces predictable increments (Summer2025!, Autumn2025!).
  • Check against a blocklist. Candidate passwords must be compared with a list of commonly used, expected or compromised passwords, as a whole (not substrings), and the user told why one was rejected. Public datasets of breached passwords exist for this; services such as Have I Been Pwned let you check a password without sending it, by sending only the first five characters of its SHA-1 hash and matching the rest locally.
  • Allow password managers and paste. Autofill must be allowed, and paste should be. Blocking paste makes people choose shorter, reused passwords.
  • Limit failed attempts. Throttle consecutive failures on an account, with an upper bound given in the guidance of no more than 100 before the authenticator is disabled; agencies may set lower limits.

The guidance is reasoned, not arbitrary. Long passphrases resist guessing better than short complex strings; composition rules and rotation measurably worsen user behaviour; and checking against known-bad lists blocks exactly the passwords that attackers try first. If your policy page demands symbols and a 90-day change, it contradicts the standard it often cites.

Online guessing, credential stuffing and rate limiting

Three online patterns, defined so that you can recognise them in logs:

  • Brute force: many guesses against one account.
  • Password spraying: one or a few common passwords tried against many accounts, staying under per-account limits.
  • Credential stuffing: valid username and password pairs leaked from another service are tried on yours. It works because many people reuse passwords, so even a low success rate per attempt yields takeovers at scale. No guessing is involved, so a strong hash and even a good password policy do not help if the user reused the password elsewhere.

The defences are layered, because each one alone fails:

  • Rate limiting at several keys. Count attempts per account, per source address, per device and globally. Per-account limits stop brute force; per-address limits stop one machine; but stuffing arrives spread over thousands of addresses with one attempt per account, so you also need global signals such as a sudden jump in failed-login rate across all accounts. The mechanics of limiter algorithms are in architecture chapter 9; the abuse-scale version is chapter 16.
  • Throttle, do not lock out forever. A hard lockout after N failures lets an attacker deliberately lock real users out (a denial of service). Prefer increasing delays and extra challenges, and tell the real user by email.
  • Breached-password checks at registration and at login stop a leaked credential from working at all.
  • MFA makes a leaked password insufficient. It is the single most effective control against stuffing.
  • Bot and risk signals: unfamiliar device or network, impossible travel, automation fingerprints. These raise friction rather than blocking outright.
  • Observe. Alert on failure ratios, and never log the submitted password, even a wrong one: users mistype passwords for other sites (see reliability chapter 5 on sensitive data in logs).

Only test what you own or are authorised to test

Load-testing your login endpoint or running a password audit against your own hashes is normal engineering. Pointing any credential-testing tool at a service you do not own or have written permission to test is illegal in most places, whatever the intent. Everything in this chapter's code runs against data created inside the script.

Multi-factor authentication

TOTP: a shared secret and a clock

The time-based one-time password (TOTP, RFC 6238) is what authenticator apps display. It builds on HOTP (RFC 4226), which turns a shared secret and a counter into a short code:

  1. At enrolment, the server generates a random secret (typically 160 bits) and shows it to the user as base32 text or a QR code containing an otpauth:// URI. The app stores it. The server stores it too, so it must be protected like any other secret, for example encrypted under a key from your KMS (chapter 4).
  2. Both sides compute HMAC(secret, counter), where counter is the Unix time divided by a 30-second step. The last nibble of the MAC picks an offset (dynamic truncation), four bytes there give a 31-bit integer, and the code is that integer modulo 106 (or 108).
  3. The server accepts the code for the current step, usually also one step either side to allow for clock drift. (Clock skew between devices is the same problem you met in distributed systems chapter 7, in a friendlier form.)

Below is an implementation using only the standard library, checked against the test vectors printed in RFC 6238 Appendix B for SHA-1, SHA-256 and SHA-512 (which use different seed lengths). Matching published vectors is how you know a security primitive is implemented correctly, rather than merely consistent with itself.

"""TOTP (RFC 6238) and HOTP (RFC 4226) with the standard library, checked against the RFC test vectors."""
import base64, hashlib, hmac, struct, time

def hotp(key: bytes, counter: int, digits: int = 6, algo=hashlib.sha1) -> str:
    mac = hmac.new(key, struct.pack(">Q", counter), algo).digest()     # 8-byte big-endian counter
    off = mac[-1] & 0x0F                                                # dynamic truncation
    code = struct.unpack(">I", mac[off:off + 4])[0] & 0x7FFFFFFF
    return str(code % 10 ** digits).zfill(digits)

def totp(key: bytes, t: float, step: int = 30, digits: int = 6, algo=hashlib.sha1) -> str:
    return hotp(key, int(t // step), digits, algo)

def verify(key: bytes, submitted: str, t: float, window: int = 1, step: int = 30) -> bool:
    """Accept the current step and +/- window steps of clock drift (constant-time compare)."""
    c = int(t // step)
    ok = False
    for k in range(c - window, c + window + 1):
        ok |= hmac.compare_digest(hotp(key, k), submitted)
    return ok

Notice what TOTP does and does not give you. Each code is useless after about a minute, so a stolen code is short-lived, and the server never sends anything to the user (unlike SMS). But:

  • A six-digit code has only a million possibilities, so the verifier must rate-limit attempts, and should remember the last accepted time step so a code cannot be replayed within its window.
  • The secret is shared, so a breach of the server's copy compromises every TOTP user. Protect it.
  • It is phishable. A fake login page can ask for the code and pass it straight to the real site within the 30-second window. The code carries no information about which site it is for.

SMS and voice codes

Codes sent by text message are better than a password alone and worse than almost every alternative. The weaknesses are in the telephone network, not in your code: an attacker can persuade a carrier to move a victim's number to a new SIM (SIM swapping) or port it to another carrier; the telecom signalling network was designed for mutual trust between carriers and has had interception weaknesses; malware or notification previews on the phone expose the code; and, like TOTP, the code is not tied to the website, so phishing relays work. NIST SP 800-63B Revision 4 treats telephone-network delivery as a restricted authenticator: you must offer a non-telephone alternative, should consider risk signals such as a recent SIM change, and email is not acceptable for out-of-band codes. It also says approve-or-deny push prompts that carry no secret are no longer acceptable, because a tired user can tap "approve" for an attacker's request ("push fatigue"). Number-matching prompts, where the user types a number shown on the login screen, are one common industry response.

WebAuthn and passkeys: binding the proof to the site

The weakness shared by passwords, SMS codes and TOTP is that the user types a secret that works anywhere, so anyone who can persuade the user to type it into the wrong place wins. WebAuthn (the W3C Web Authentication standard, with CTAP2 for talking to external keys; together they form the FIDO Alliance's FIDO2) removes the secret from the equation. The idea is public-key authentication, with the site's identity bound into every signature.

  1. Registration. The site (the relying party, RP) sends a random challenge and its identifier (the RP ID, a domain such as example.com). The authenticator (a hardware key, or the secure hardware in a phone or laptop) creates a fresh key pair for that RP ID, keeps the private key, and returns the public key. The site stores the public key and a credential id. There is no shared secret to steal from the server: a database leak exposes only public keys.
  2. Login. The site sends a new random challenge. The browser builds a small structure, clientDataJSON, containing the challenge and the origin the browser is actually talking to, and passes it to the authenticator together with the RP ID. The authenticator will use a key only if it holds one registered for that RP ID, usually after a local check of the user (a PIN, a fingerprint, or a touch); it signs the client data hash together with data that includes a hash of the RP ID.
  3. The site verifies the signature with the stored public key, and checks that the challenge is the one it issued, that the origin is its own, and that the RP ID hash matches. It also checks the authenticator's signature counter or other clone-detection signals where provided.

Why does this defeat phishing? The origin is filled in by the browser, not the page. On a look-alike domain, the browser reports that look-alike origin, and the RP ID the page asks for cannot be one the page's origin is not allowed to use. The authenticator holds no credential for it and refuses to sign. If a fake site relays a real challenge, the signature (if one could be produced at all) would carry the wrong origin, and the real site would reject it. The user can be fooled completely; the protocol is not. That property is called phishing resistance, and NIST SP 800-63B Revision 4 requires verifiers to offer at least one phishing-resistant option at its second assurance level; it names verifier-name binding, with WebAuthn as the example, as the way to get it.

A passkey is the user-facing name for a WebAuthn credential that the platform can store, sync between a user's devices through the platform's account (so losing one phone does not lose the login) and offer by account name or biometric prompt. This gives convenience that hardware keys lack, with a trade-off: the keys now depend on the security of the sync provider's account recovery. NIST's text says syncable authenticators must not be used at its highest assurance level (AAL3), which requires a non-exportable key.

Phishing-resistant is not attack-proof

WebAuthn does not help if malware controls the device after login. It does not protect the session that follows a successful login: a stolen session cookie or token still works (that is the subject of chapter 6). And it does nothing for the recovery path, next.

Account recovery: the weakest link

Every authentication scheme has a second, quieter door: what happens when the user loses the first factor. Recovery has to let in the legitimate owner who has lost everything, which is a close cousin of letting in an impostor who claims to have lost everything. An account protected by a passkey but recoverable through "click the link we emailed you" is as strong as that user's email account, and as strong as whoever answers the support phone.

Practical rules that follow:

  • Hold recovery to the same standard as login. If the account is guarded by a phishing-resistant factor, recovery should not be an SMS to a number anyone can port. Prefer pre-generated recovery codes, a second enrolled authenticator, or a delayed process.
  • Reset tokens are credentials. Generate at least 128 random bits with the CSPRNG, make them single use and short lived (minutes to an hour), store only a hash of the token (so a database read does not hand out working reset links), and tie each to one user and one purpose.
  • Notify and delay. Send an alert to every known channel when a recovery starts or completes. For high-value accounts, add a waiting period that the real owner can cancel.
  • Invalidate what recovery should invalidate. After a reset, revoke all active sessions and refresh tokens, so an attacker who was already inside is evicted, and decide deliberately whether enrolled second factors survive.
  • Avoid knowledge-based recovery. "Mother's maiden name" questions are answerable from public records and social media and are, in effect, a second weak password.
  • Train and constrain the support desk. Social engineering of staff is a recovery path. Give agents tools that require the same evidence as the automated flow and log every override.

Putting it together: a sound baseline

  • Argon2id (or scrypt, or bcrypt/PBKDF2 where required), parameters stored with each hash, upgraded on login.
  • Long passwords allowed, blocklist-checked, no composition rules, no scheduled expiry, paste allowed.
  • Layered throttling and monitoring that works against both brute force and stuffing, with no account-existence leaks.
  • MFA offered to everyone and required where the stakes warrant; passkeys or security keys as the preferred factor; TOTP as the fallback; SMS only if nothing else is possible.
  • A recovery process designed and reviewed as an authentication path in its own right.

Then change TARGET in pw.py to a higher n and see the login time grow; check that your hash of the "wrong" password still takes about the same time as the right one. Point an authenticator app at a secret you generate yourself (for example, scan a QR code made from the printed otpauth:// line with a local QR tool, or type the base32 secret manually) and compare its code to your script's output. They match, because the script and the app both compute RFC 6238.

Distributed systems connection

Authentication is state and time spread across machines. A per-account failure counter has to be shared across every login server (or accepted as approximate), or an attacker simply spreads guesses across replicas; this is the rate-limiting problem of architecture chapter 9 with an adversary. TOTP depends on loosely synchronised clocks and a drift window, as in distributed chapter 7. A credential store replicated across regions raises the question of how fast a password change or a revoked authenticator reaches every replica; until it does, the old credential still works somewhere.

Key takeaways

  • Authentication proves identity with something known, held or inherent. Count what an attacker must do, not just the number of factors.
  • Plan for the stolen table. Store passwords with a unique salt and a slow, memory-hard function (Argon2id first; scrypt, bcrypt or PBKDF2 where needed) at or above OWASP's current minimums, with parameters stored per hash. A fast hash fails because speed is exactly what the attacker wants.
  • A pepper in a secret store is defence in depth. Upgrade weak or old hashes at the next successful login. Do not leak which accounts exist.
  • NIST SP 800-63B Revision 4: favour length (15 characters as a sole factor, 8 with MFA, allow 64 or more), no composition rules, no periodic forced changes, check against blocklists, allow paste and password managers, throttle failures.
  • Credential stuffing exploits reuse and defeats good hashing. Layer rate limits by account, source and globally, check for breached passwords, require MFA and avoid hard lockouts that become denial of service.
  • TOTP is a shared secret plus the time (RFC 6238) and is phishable; SMS adds telephone-network weaknesses. WebAuthn and passkeys sign a challenge together with the real origin, so a look-alike site gets nothing usable.
  • Recovery is a second login. Make it as strong as the first, or the first does not matter.

Check your understanding

A site stores SHA-256(salt + password) with a unique 16-byte salt per user. What does the salt achieve, and what does it not?

  1. It makes each guess much slower, so the scheme is safe
  2. It stops precomputed tables and reveals no matching passwords, but each individual guess is still very cheap
  3. It encrypts the password so the hash cannot be attacked
  4. It must be kept secret, otherwise the scheme fails
A salt forces the attacker to work per user and hides duplicates, but SHA-256 is still fast, so each guess costs almost nothing. The salt is stored next to the hash and is not secret. A slow, memory-hard function is what makes each guess expensive.

Your password table used PBKDF2 with 100,000 iterations and policy now requires 600,000 (HMAC-SHA-256). How do you migrate users who log in regularly?

  1. Recompute all hashes at once from the stored hashes
  2. Email every user their old password to re-enter
  3. Keep the old setting forever, because changing it breaks logins
  4. Store the parameters with each hash and, after a successful login, rehash the password with the new parameters and overwrite the record
You only hold the plaintext at login. Verify with the record's own parameters, then upgrade. Users who never log in again keep the old hash until you decide to expire them or force a reset. A wrapper (new hash of the old hash) can raise the cost for everyone immediately.

Which policy does NIST SP 800-63B Revision 4 support?

  1. Allow long passphrases, block known-compromised passwords, and do not require periodic changes or character-class rules
  2. Require a change every 90 days and at least one symbol
  3. Forbid paste in the password field to prevent copying
  4. Cap passwords at 12 characters so users can remember them
The guidance prohibits composition rules and periodic expiry (except on evidence of compromise), requires blocklist checking, asks that paste and password managers be allowed, and asks verifiers to permit lengths of at least 64.

Attackers try username and password pairs from another company's breach against your login, one attempt per account, spread over thousands of addresses. Which control is least effective at stopping it?

  1. Requiring MFA
  2. Rejecting passwords found in breach lists
  3. A per-account lockout after five failures from one address
  4. Global anomaly detection on failed-login rate
With one attempt per account and many source addresses, per-account and per-address limits never trigger. MFA makes the leaked password insufficient, breach checks reject it, and global rate signals reveal the campaign.

Why does a WebAuthn login to a look-alike phishing site fail even if the user is completely fooled?

  1. The authenticator checks the visual appearance of the page
  2. The browser supplies the real origin, the authenticator holds keys per site identifier and signs the origin-bound client data, so no valid assertion for the real site can be produced there
  3. Passkeys are encrypted, so phishing pages cannot read them
  4. The user must type a six-digit code that expires
The proof is bound to the origin by software the page does not control. There is no secret to type into the wrong place. A typed one-time code, by contrast, carries no origin and can be relayed.

A service protects accounts with passkeys but offers "email me a reset link" with a link valid for 7 days. What is the main concern?

  1. Passkeys cannot be reset
  2. Email is encrypted so the link is safe
  3. Account security is now the minimum of the passkey and the email account, and a long-lived link widens the window
  4. The link should be sent by SMS instead
Recovery is an authentication path. An attacker who controls the mailbox, or intercepts the link, takes the account without touching the passkey. Make links single use and short lived, store only their hashes, notify, and consider delays or additional proof for valuable accounts. SMS would not be an improvement.

Applied Cryptography

You are not going to invent a cipher; you are going to choose and combine primitives, and almost every real-world failure comes from that step: a hash used where a MAC was needed, a nonce used twice, a comparison that stops at the first wrong byte. This chapter is a tour of the six building blocks, what exactly each guarantees, and the specific mistakes that break them.

Why this matters

Cryptography is the one area of security where the maths is excellent and the usage is poor. Attackers almost never break AES. They exploit that the developer forgot to authenticate the ciphertext, reused a nonce, compared tags with ==, or seeded a random number generator with the time. Knowing what each primitive promises, and under which conditions it stops promising, lets you review designs and choose library APIs that make the mistakes hard.

Where we start

Networking chapter 11 introduced the building blocks: hashes for fingerprints, symmetric keys for bulk encryption, public keys for identity and key exchange, certificates for binding keys to names, and TLS 1.3 putting them together. Here we go deeper into each primitive's exact guarantee and its usual misuse. A recurring question will be: against which attacker goal does this protect? The widget in the middle of the chapter lets you check that systematically.

Analogy: tools in a workshop

Each primitive is a tool for one job. A hash is a fingerprint, a MAC is a tamper-evident seal that only key holders can apply, symmetric encryption is a locked box, a signature is a notarised stamp anyone can check, and a key exchange is two strangers agreeing on a locker combination in a crowded room. A hammer is excellent, but not for screws.

Where it breaks down: physical tools fail visibly. A cryptographic tool used wrongly usually still "works": data goes in, data comes out, tests pass, and the flaw is silent until an attacker finds it.

Hash functions

A cryptographic hash function maps input of any length to a fixed-length output (SHA-256: 32 bytes) and is designed to be fast, deterministic and to have three properties that are easy to confuse:

  • Preimage resistance: given a digest h, it is infeasible to find any message m with H(m) = h. For an ideal n-bit hash, the best generic attack costs about 2n work.
  • Second-preimage resistance: given a specific message m1, it is infeasible to find a different m2 with the same hash. Also about 2n.
  • Collision resistance: it is infeasible to find any two different messages with the same hash, where the attacker picks both. This is easier, because of the birthday paradox: roughly 2n/2 work. That is why a 256-bit hash gives about 128 bits of collision security, and why a 128-bit hash like MD5 is dead for this purpose.

The ordering matters in practice. Collisions are the weakest property, so they break first. MD5 and SHA-1 both have practical collision attacks (for SHA-1, a public collision was demonstrated in 2017), which lets an attacker prepare two different documents with the same hash, one harmless to show you and one malicious to use later. Preimage attacks on them remain impractical, so e.g. an old file-integrity checksum is not necessarily useless, but nothing new should use them for signatures or certificates. Use SHA-256 or SHA-3 (or BLAKE2/BLAKE3 for speed).

What a hash is not

A hash is not encryption (there is no key and no way to get the message back, but small input spaces can be searched), not authentication (anyone can compute it), and not a password store. A plain fast hash of a password lets an attacker try billions of guesses per second on stolen digests; chapter 5 covers the deliberately slow, salted functions designed for that. Use a hash for fingerprints, content addressing, integrity when the hash itself arrives by a trusted route (a signed manifest), and as a component inside MACs, signatures and KDFs.

MACs: hashes with a key

To get authentication you need something the attacker does not have. A message authentication code (MAC) takes a secret key and a message and produces a short tag. The receiver, who shares the key, recomputes the tag and compares. Without the key, forging a valid tag for a new message is infeasible, even given tags for other messages. The standard construction from a hash is HMAC (RFC 2104): roughly H((K xor opad) || H((K xor ipad) || m)), a hash nested inside a hash with two different key-derived pads.

import hashlib, hmac, secrets

key = secrets.token_bytes(32)          # the shared secret, never sent

def sign(msg: bytes) -> bytes:
    return hmac.new(key, msg, hashlib.sha256).digest()

def verify(msg: bytes, tag: bytes) -> bool:
    expected = sign(msg)
    return hmac.compare_digest(expected, tag)   # constant-time compare

msg = b"amount=100&to=alice"
tag = sign(msg)
print("tag length:", len(tag), "bytes")
print("genuine message verifies :", verify(msg, tag))
print("tampered message verifies:", verify(b"amount=900&to=mallory", tag))
print("random tag verifies      :", verify(msg, secrets.token_bytes(32)))

# A plain hash is NOT authentication: anyone can compute one for their own message.
forged = b"amount=900&to=mallory"
print("attacker can compute sha256(forged) themselves:", len(hashlib.sha256(forged).digest()) == 32)
print("but without the key they cannot produce sign(forged):", not verify(forged, hashlib.sha256(forged).digest()))

random tag verifies      : False

Three details in that code are not decoration. The key comes from secrets, a cryptographically secure random source, not from a password or a timestamp. The tag is compared with hmac.compare_digest, for reasons we meet below. And note that the tag authenticates but does not hide: the message is still readable. A MAC also does not stop replay: a captured valid (message, tag) pair verifies again tomorrow, so include a counter, timestamp or unique id inside the authenticated message.

Why not just H(key || message)? Length extension

The obvious home-made MAC is to hash the key followed by the message. For the widely used hashes SHA-256 and SHA-512 (and MD5, SHA-1), it is broken, because of how they are built. These hashes follow the Merkle–Damgård construction: the padded input is split into blocks, and a small internal state is updated block by block. The final state is the digest. So whoever holds the digest holds the internal state after the last block, and can keep going: feed in further blocks and compute the hash of a longer message without knowing what came before.

Step through

Length extension against H(key || message)

  1. The server's tag is H(K || m). Internally the hash absorbs the key and message, then the padding (which encodes the total length), and the final internal state is the output.
  2. Tag T and the message m are visible to the attacker, who also usually knows the key length. The key stays secret.
  3. Because T is the hash's internal state after the padded input, the attacker can start a new computation from T and feed in extra data of their own, here ext.
  4. The result T' is exactly what the server computes for the longer message m || padding || ext. The attacker has forged a valid tag for a message they chose the ending of, without the key. HMAC's outer hash makes the published value no longer a resumable state; truncated variants such as SHA-512/256, and SHA-3 and BLAKE2, are not vulnerable either, but you should still use HMAC or a purpose-built MAC.

The toy code below implements exactly that, on a deliberately small Merkle–Damgård hash built in this file, against its own made-up secret. It is an educational demonstration of a design flaw, run inside one process. The same structure, with real SHA-256, is why sha256(secret + data) is a well-known pitfall in API-signing schemes.

"""Length extension on a TOY Merkle-Damgard hash (8-byte state, 8-byte blocks).
Educational only: the same structure as MD5/SHA-1/SHA-256, minus the strength.
Everything runs in this one process against our own toy MAC."""
import hashlib, hmac

BLOCK = 8

def compress(state: bytes, block: bytes) -> bytes:
    return hashlib.sha256(state + block).digest()[:8]

def pad(total_len: int) -> bytes:
    p = b"\x80"
    while (total_len + len(p) + 8) % BLOCK:
        p += b"\x00"
    return p + total_len.to_bytes(8, "big")

def toy_hash(msg: bytes, state: bytes = b"IV-toy!!", already: int = 0) -> bytes:
    data = msg + pad(already + len(msg))
    for i in range(0, len(data), BLOCK):
        state = compress(state, data[i:i+BLOCK])
    return state

SECRET = b"s3cr3t-key"                      # the attacker never sees this
def naive_mac(msg):  return toy_hash(SECRET + msg)          # H(key || msg): BROKEN
def hmac_like(msg):  return hmac.new(SECRET, msg, hashlib.sha256).digest()

def server_accepts(msg, tag): return naive_mac(msg) == tag

# The attacker sees one legitimate (message, tag) pair and knows len(SECRET).
msg = b"user=bob&role=viewer"
tag = naive_mac(msg)

glue = pad(len(SECRET) + len(msg))          # padding the hash added internally
ext  = b"&role=admin"
# Resume the hash from the published tag as if it were the internal state:
forged_tag = toy_hash(ext, state=tag, already=len(SECRET) + len(msg) + len(glue))
forged_msg = msg + glue + ext
print("forged message:", forged_msg)
print("server accepts forged (msg, tag) without the key:", server_accepts(forged_msg, forged_tag))
# HMAC's outer hash hides the inner state, so there is nothing to resume.
print("HMAC output is a different hash of the inner state; no resumable state is published.")

Symmetric encryption, and why it needs authentication

Symmetric encryption uses one key to encrypt and decrypt. AES is the standard block cipher (16-byte blocks, 128/192/256-bit keys); a mode of operation says how to apply it to messages longer than a block. Two facts about modes shape everything below.

First, encryption alone does not protect integrity. Stream-like modes (CTR, GCM's counter core, ChaCha20) produce ciphertext as plaintext XOR keystream. Flip a bit in the ciphertext and the same bit flips in the plaintext. An attacker who knows or guesses the layout of a message ("amount=0100") can change it predictably without the key. This property is called malleability. Chained modes like CBC are malleable differently, and when decryption errors reveal whether padding was valid, they enable padding oracle attacks, which recover plaintext through the error behaviour alone (Vaudenay, 2002).

Second, the answer is authenticated encryption. An AEAD (authenticated encryption with associated data) scheme encrypts and attaches a tag in one operation, and refuses to release any plaintext if the tag does not verify. The two you will meet in practice, both in TLS 1.3, are AES-GCM and ChaCha20-Poly1305 (RFC 8439). "Associated data" is data that is authenticated but not encrypted, such as a header, a tenant id or a record number; binding it prevents an attacker from moving a valid ciphertext into a different context.

The nonce rule

Every AEAD encryption takes a nonce ("number used once"): a value that must be unique for each message under a given key. It need not be secret or random; a counter is fine. It must not repeat. What happens when it does is not a gentle degradation:

  • For stream-based modes, two messages under the same key and nonce use the same keystream, so XORing the two ciphertexts cancels the keystream and leaves the XOR of the two plaintexts. Texts with known structure then fall apart.
  • For AES-GCM specifically, a repeated nonce also leaks the internal authentication key, after which an attacker can forge tags for messages of their choice. One mistake costs both confidentiality and integrity.

The demo uses a small toy stream cipher (a SHAKE-256 keystream) to show the mechanism. It is educational only; never build your own cipher from parts.

"""TOY stream cipher: SHAKE-256(key||nonce) keystream XOR plaintext. Educational only."""
import hashlib

def keystream(key, nonce, n): return hashlib.shake_256(key + nonce).digest(n)
def xor(a, b): return bytes(x ^ y for x, y in zip(a, b))
def enc(key, nonce, pt): return xor(pt, keystream(key, nonce, len(pt)))

key, nonce = b"k" * 32, b"nonce-0001"
p1 = b"transfer 100 to alice   "
p2 = b"transfer 999 to mallory!"[:len(p1)]
c1, c2 = enc(key, nonce, p1), enc(key, nonce, p2)     # SAME nonce twice: the bug
leak = xor(c1, c2)
print("c1 xor c2 == p1 xor p2:", leak == xor(p1, p2))
# Attacker who knows (or guesses) p1 recovers p2 without the key:
print("recovered p2 from c1,c2,p1:", xor(leak, p1))
# With a fresh nonce the relation disappears:
c3 = enc(key, b"nonce-0002", p2)
print("fresh nonce still leaks xor?:", xor(c1, c3) == xor(p1, p2))
c1 xor c2 == p1 xor p2: True
recovered p2 from c1,c2,p1: b'transfer 999 to mallory!'
fresh nonce still leaks xor?: False

Practical guidance: with AES-GCM, the recommended nonce is 96 bits, and if you generate nonces randomly, the birthday bound limits how many messages one key can safely protect (NIST's guidance caps random-nonce GCM at about 232 encryptions per key), so rotate keys or use a counter. In distributed systems, a counter reset after a crash, or two replicas both starting at zero, is a classic way to reuse a nonce. Prefer libraries that manage nonces for you (misuse-resistant designs such as AES-GCM-SIV, or libsodium's secretbox with random 24-byte nonces) when you cannot guarantee a counter.

Same lesson for signatures

Signature schemes in the DSA family (including ECDSA) need a fresh random per-signature value. If it repeats or is predictable, the private key can be computed from the signatures. This is how a games console's signing key was recovered around 2010, after the vendor's implementation reused the value. Ed25519 avoids the problem by deriving the value deterministically from the message and key. When you can choose, choose designs that remove a way to fail.

Public-key cryptography: two different jobs

Public-key (asymmetric) cryptography uses a key pair: a public key that can be shared and a private key that is not. People often say "encrypt with the public key, decrypt with the private key", then try to reverse it for signatures. It is better to think of two different tools:

Public-key encryption

Anyone can encrypt to the owner's public key; only the private-key holder can decrypt. Provides confidentiality to one recipient. Proves nothing about the sender. In practice used only to protect a small symmetric key (hybrid encryption).

Digital signature

The private-key holder signs; anyone with the public key verifies. Provides authenticity, integrity and non-repudiation. Does not hide the message. Examples: Ed25519, ECDSA, RSA-PSS.

Public-key operations are slow and handle only short inputs, so real systems are hybrid: use public-key methods to establish or protect a symmetric key, then AEAD for the data. RSA (1977) bases security on the difficulty of factoring; elliptic-curve schemes (X25519 for key agreement and Ed25519 for signatures, RFCs 7748 and 8032) achieve similar security with much smaller keys. Both rest on problems that a large quantum computer running Shor's algorithm could solve, which is why NIST standardised post-quantum schemes (ML-KEM for key establishment and ML-DSA for signatures, 2024) and why some deployments already combine classical and post-quantum key exchange. Long-lived secrets are the worry: an adversary can record traffic today and decrypt it later.

A signature is only as meaningful as your belief that the public key belongs to the claimed signer. Establishing that belief is the job of certificates and PKI, the subject of chapter 4.

Key exchange and forward secrecy

How can two parties who have never met agree on a symmetric key while an attacker listens to everything? Diffie–Hellman key exchange (Diffie and Hellman, 1976) does it with a one-way operation. Each side picks a private number, publishes a corresponding public value, and combines their own private number with the other side's public value. Both arrive at the same shared secret; an eavesdropper who sees only the public values would have to solve the discrete-logarithm problem. Modern TLS uses the elliptic-curve version, X25519.

Two caveats. Plain DH is unauthenticated: an attacker in the middle can run one exchange with each side and relay between them, an active man-in-the-middle. The fix is to sign the exchange with a long-term key whose public half is certified. And DH enables forward secrecy: if each session uses fresh, ephemeral DH keys that are deleted afterwards, then even an attacker who later steals the server's long-term key, or has recorded all the traffic, cannot recompute old session keys. Without it (the old scheme of encrypting a session key with the server's long-term RSA key), one stolen key unlocks every recorded session. TLS 1.3 requires ephemeral key exchange.

Here is the exchange with deliberately toy parameters (a 127-bit prime; real systems use X25519 or groups of 2048 bits or more), including the forward-secrecy habit of deleting the ephemeral secrets.

"""Diffie-Hellman with TOY parameters (prime 2**127-1). Real systems use X25519 or 2048+ bit groups."""
import secrets, hashlib
P, G = 2**127 - 1, 3

def keypair():
    x = secrets.randbelow(P - 2) + 1
    return x, pow(G, x, P)

def session_key(my_priv, their_pub):
    s = pow(their_pub, my_priv, P)
    return hashlib.sha256(s.to_bytes(16, "big")).hexdigest()[:16]

a_priv, a_pub = keypair()
b_priv, b_pub = keypair()
print("Alice and Bob agree:", session_key(a_priv, b_pub) == session_key(b_priv, a_pub))

# Forward secrecy: a fresh ephemeral pair per session; keys are deleted afterwards.
sessions = []
for i in range(3):
    ea, ea_pub = keypair(); eb, eb_pub = keypair()
    sessions.append(session_key(ea, eb_pub))
    del ea, eb                           # ephemeral secrets destroyed
print("3 sessions, all keys distinct:", len(set(sessions)) == 3)
print("Stealing a long-term signing key later reveals none of these session keys.")

3 sessions, all keys distinct: True
Stealing a long-term signing key later reveals none of these session keys.

Key derivation: HKDF

The raw output of a key exchange is not a good key: it has structure, and one secret may need to feed several uses. A key derivation function (KDF) turns input key material into one or more independent keys. HKDF (RFC 5869, Krawczyk and Eronen, 2010) is the standard, built from HMAC in two steps: extract compresses possibly uneven input into a uniformly random pseudorandom key, and expand stretches that into as many output bytes as needed, with an info label so that keys for different purposes are different. Use separate derived keys for separate jobs (one for encryption, one for MAC) rather than reusing a key.

import hmac, hashlib

def hkdf(ikm: bytes, salt: bytes, info: bytes, length: int) -> bytes:
    prk = hmac.new(salt or b"\x00" * 32, ikm, hashlib.sha256).digest()      # extract
    okm, t, i = b"", b"", 1
    while len(okm) < length:                                                  # expand
        t = hmac.new(prk, t + info + bytes([i]), hashlib.sha256).digest()
        okm += t; i += 1
    return okm[:length]

# RFC 5869 test case 1
okm = hkdf(bytes([0x0b]) * 22, bytes(range(13)), bytes(range(0xf0, 0xfa)), 42)
print("RFC 5869 test 1 :", okm.hex())
print("matches the RFC :", okm.hex().startswith("3cb25f25faacd57a90434f64d0362f2a2d2d0a90cf1a5a4c5db02d56ecc4c5bf"))

master = b"one master secret from a key exchange"
enc_key = hkdf(master, b"salt", b"encryption v1", 32)
mac_key = hkdf(master, b"salt", b"authentication v1", 32)
print("separate keys from one secret:", enc_key != mac_key)

HKDF assumes the input is already high-entropy. It is not for passwords: a human-chosen password has little entropy, and the defence there is a deliberately slow function (scrypt, Argon2, PBKDF2 in chapter 5), not a fast one.

Randomness: secrets, not random

Every key, nonce, token and salt depends on unpredictable numbers. A CSPRNG (cryptographically secure pseudo-random number generator) is designed so that, even after seeing many outputs, you cannot predict the next ones or recover earlier ones. Operating systems provide one fed by hardware events (/dev/urandom, getrandom(), BCryptGenRandom), and Python exposes it through os.urandom and the secrets module.

Python's random module is a different thing: a Mersenne Twister, excellent for simulations, fully deterministic given its state, and from 624 consecutive 32-bit outputs the state can be reconstructed and every later output predicted. It must never produce a token, key, password-reset code or anything an attacker benefits from guessing. A seed like the current time makes things worse: an attacker who knows roughly when a token was created only has to try a small window of seeds.

import random, secrets

a = random.Random(42)
b = random.Random(42)
print("two generators, same seed:", [a.randrange(1000) for _ in range(5)], [b.randrange(1000) for _ in range(5)])
print("random is a deterministic function of its seed and internal state;")
print("an observer of enough outputs can reconstruct that state (Mersenne Twister is not designed to resist this).")

t1, t2 = secrets.token_urlsafe(32), secrets.token_urlsafe(32)
print("secrets.token_urlsafe(32) length:", len(t1), "chars (32 bytes = 256 bits of OS randomness)")
print("two tokens differ:", t1 != t2)
print("secrets.choice picks from the OS CSPRNG:", secrets.choice("abcdef") in "abcdef")

Constant-time comparison

Checking a secret with == usually returns as soon as it finds a differing byte. If an attacker can time the response, comparison time reveals how many leading bytes were right, and they can recover the secret one byte at a time. This is a timing side channel: a leak through how long or how the computation ran rather than through its output. Remote timing attacks need careful statistics, because network noise is large, but they have been demonstrated against real systems, and local ones (co-resident processes on a shared machine) are much easier. The fix is a comparison whose running time does not depend on where the inputs differ: hmac.compare_digest in Python.

The demo below deliberately avoids measuring time, since timing numbers are noisy and machine-dependent. Instead it counts the work an early-exit comparison does, which is exactly the quantity an attacker tries to measure.

import hmac

def naive_equal(a: bytes, b: bytes):
    """Early-exit comparison; also returns how many bytes it examined."""
    n = 0
    for x, y in zip(a, b):
        n += 1
        if x != y:
            return False, n
    return len(a) == len(b), n

secret = b"TOKEN-8f3a"
for guess in [b"AAAAAAAAAA", b"TAAAAAAAAA", b"TOKEN-AAAA", b"TOKEN-8f3a"]:
    ok, n = naive_equal(secret, guess)
    print(f"{guess.decode():<12} equal={ok!s:<5} bytes examined={n}")
print("The work done reveals how long the correct prefix is. Real attacks measure it")
print("through time, which is noisy; the leak is real but the numbers here are exact counts, not timings.")
print("hmac.compare_digest:", hmac.compare_digest(secret, b"TOKEN-8f3a"), hmac.compare_digest(secret, b"TOKEN-AAAA"))

TAAAAAAAAA   equal=False bytes examined=2

TOKEN-8f3a   equal=True  bytes examined=10

Constant time is a property of the implementation

compare_digest protects the content comparison of equal-length inputs; it does not hide their lengths, and it does not make the rest of your code constant-time (a database lookup by token, or an early return before comparison, still leaks). Cryptographic libraries go further, designing operations like modular exponentiation to avoid secret-dependent branches and memory access, which is one reason not to implement them yourself.

Which primitive stops which attack?

Pull the pieces together. Pick a primitive and an attacker goal and see whether the primitive, used correctly, stops it. The most instructive cells are the "no" ones: a MAC does not provide non-repudiation, encryption alone does not stop tampering, a signature does not hide the message.

Why you should not roll your own

"Don't roll your own crypto" is sometimes said as if it were snobbery. It is a statement about evidence. Here are concrete reasons:

  1. Failure is silent. A broken cipher still encrypts and decrypts correctly. No test goes red. The only reviewers who can tell are adversaries and specialists.
  2. Security is about all attackers, forever. A design is secure only if it survives years of public attack by people paid and motivated to break it. The standard algorithms have; yours has not. This is Kerckhoffs's principle and the open-design rule of chapter 2.
  3. The implementation is as hard as the design. Even with a sound algorithm, timing leaks, cache side channels, padding-oracle error messages, fault handling and nonce management are where real systems break.
  4. Composition is subtle. Encrypt-then-MAC, MAC-then-encrypt, sign-then-encrypt and encrypt-then-sign differ in what they protect against. AEAD constructions exist so you do not choose.
  5. Parameters and defaults matter. Key size, mode, nonce length, curve, iteration count and encoding all matter, and the library's high-level API picks safe ones.

What to do instead: use a high-level, hard-to-misuse library (libsodium/NaCl, Google's Tink, or the cryptography package's high-level recipes), use a protocol rather than primitives (TLS for transport, a vetted format for stored data), and ask for a review from someone who does this for a living when the design is new. When this chapter's toy code (the toy cipher, the toy hash, the 127-bit DH group) appears, it is there to show a mechanism, and it must not leave the page.

Go deeper (optional): what real code looks like

With the third-party cryptography package (illustrative; needs pip install cryptography, not run here), authenticated encryption is a few lines:

from cryptography.hazmat.primitives.ciphers.aead import ChaCha20Poly1305
import os

key = ChaCha20Poly1305.generate_key()          # 32 random bytes
aead = ChaCha20Poly1305(key)
nonce = os.urandom(12)                         # unique per message under this key
ct = aead.encrypt(nonce, b"hello", b"header")  # associated data = b"header"
pt = aead.decrypt(nonce, ct, b"header")        # raises InvalidTag on any change

Note what the API does for you: the tag is appended, decryption either returns the plaintext or raises, and associated data is a first-class argument. What it still cannot do for you is guarantee that you never reuse the nonce, which is why large systems derive nonces from counters or use misuse-resistant modes.

Distributed systems connection

Cryptography turns "the network might lie" into a checkable statement. Authenticated, ordered, replay-protected messages are what allow nodes to treat each other's messages as evidence, and they are the building block that Byzantine-fault-tolerant protocols assume (distributed chapter 12: signed messages make lying detectable). Nonce management is also a distributed-systems problem in disguise: unique-forever counters across restarts and replicas need exactly the coordination and fencing tools of chapter 4 of that course.

Key takeaways

  • A hash has no key: it gives fingerprints, not authentication. Know the three properties; collision resistance is the weakest (about 2n/2).
  • Use HMAC, not H(key || message), because Merkle–Damgård hashes are length-extendable. Include a counter or timestamp to stop replay.
  • Encryption without authentication is malleable. Use AEAD (AES-GCM, ChaCha20-Poly1305) and put context in the associated data.
  • Never reuse a nonce under a key: it can leak plaintext relations and, in GCM, the authentication key. Same for ECDSA's per-signature secret.
  • Public-key encryption gives confidentiality to a recipient; signatures give authenticity and non-repudiation. Real systems are hybrid.
  • Ephemeral Diffie–Hellman gives forward secrecy, but only authenticated exchange resists a man in the middle.
  • Derive keys with HKDF; use secrets (not random) for anything unpredictable; compare secrets with hmac.compare_digest.
  • Do not roll your own: use a high-level library or protocol. Failure is silent and the standard designs have survived public attack.

Check your understanding

Why is collision resistance of an n-bit hash only about 2n/2 work, while preimage resistance is about 2n?

  1. Because collisions need two hash functions
  2. Because of the birthday paradox: among many random outputs, some pair matches long before any specific output is hit
  3. Because preimages are impossible
  4. Because hashes are encrypted
A collision lets the attacker choose both inputs and look for any matching pair, so the search succeeds after roughly the square root of the output space. A preimage targets one particular value.

A service authenticates requests with sha256(secret + body). What can an attacker who sees one valid request do?

  1. Nothing, because the secret is hashed
  2. Recover the secret by brute force instantly
  3. Decrypt the body
  4. Forge a valid tag for a longer body that begins with the original (plus padding), using length extension, without knowing the secret
The digest equals the hash's internal state after the padded input, so the attacker can continue hashing from it. HMAC prevents this by wrapping the inner hash in an outer one.

Two messages are encrypted with the same key and the same nonce under a stream-based mode. What does an eavesdropper learn?

  1. The XOR of the two plaintexts, because the keystream cancels, which usually lets known or structured text be recovered
  2. Nothing, since the key is unknown
  3. Only the length of the key
  4. The nonce of the next message
c1 XOR c2 = p1 XOR p2 when the keystream is identical. In AES-GCM, nonce reuse additionally exposes the authentication key, enabling forgery.

You need proof that Alice, and not Bob, authorised a transaction, to show a third party later. Which primitive provides it?

  1. HMAC with a key shared by Alice and Bob
  2. AES-GCM with a key shared by Alice and Bob
  3. A digital signature with Alice's private key
  4. A SHA-256 hash of the transaction
With a shared key (MAC or AEAD) Bob could have created the tag too. Only a private key held by Alice alone supports non-repudiation, as long as her key is not stolen and the public key is reliably bound to her.

What does forward secrecy protect against?

  1. A user choosing a weak password
  2. An attacker who records traffic now and later steals the server's long-term key, being able to decrypt the recorded sessions
  3. Replay of old messages
  4. Timing attacks
With ephemeral key exchange and deletion of the ephemeral secrets, session keys are not derivable from the long-term key, so later compromise does not expose past traffic. Replay needs counters or nonces; weak passwords need different defences.

A developer generates password-reset tokens with random.choices(alphabet, k=20). What is the problem?

  1. Twenty characters are too short
  2. The alphabet is too large
  3. random is a predictable Mersenne Twister; use secrets, which draws on the operating system's CSPRNG
  4. Nothing, random is cryptographically secure on Linux
The length is fine; the source of randomness is not. Outputs of random can be used to reconstruct its internal state and predict others. Tokens need secrets.token_urlsafe or equivalent.

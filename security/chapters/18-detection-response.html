Detection & Security Incidents

Prevention fails eventually, so the question becomes how fast you notice and what you can prove afterward. This chapter covers what a system should record for security, how to make that record hard to rewrite, how detection rules differ from anomaly hunting, how a security incident differs from the reliability incidents of the previous course, and what to preserve so that investigators, lawyers and regulators can reconstruct what happened.

Why this matters

An attacker who gets in quietly may stay for months, and in several well-known breaches the damage grew mostly because nobody saw it. Detection is also where design decisions pay off or hurt long after launch: a service that never recorded who exported a table cannot answer "was this customer's data taken?" no matter how skilled the responders are. Audit logging is cheap to design in and nearly impossible to retrofit after an incident.

Scope and safety

The code here runs on made-up events inside one process. Honeytokens and detection rules belong on systems you own or are authorised to monitor. Collecting employees' or users' activity data has its own privacy and legal constraints; chapter 17 applies to your security logs too.

What to log for security

An audit log is a record of security-relevant actions kept so that someone can later answer "who did what, to what, when, and was it allowed?". It differs from an application log in purpose, and therefore in who may read it, how long it is kept and how much it must be trusted. The reliability course's logs and events chapter covers structured logging in general; this is the security subset. Record at least these four families.

  • Authentication events. Successful and failed sign-ins, multi-factor challenges and results, password and factor resets, new device or location, session and token issuance, and sign-outs. Failures matter as much as successes, because credential stuffing (chapter 5) looks like a flood of failures.
  • Authorization decisions. Especially denials, and allows on sensitive operations. A burst of denials from one principal is reconnaissance, and a check that was never logged is one you cannot prove ran (chapter 8).
  • Administrative and privileged actions. Role grants, policy and configuration changes, impersonation ("log in as customer"), break-glass access, key and secret operations, and changes to logging itself. Attackers who gain privilege often try to turn the logging off.
  • Data access and export. Bulk reads, exports, downloads, API calls that return large result sets, and decrypt calls on your key service. These are the events that tell you what was actually taken.

For each event, a useful record answers: who (the authenticated principal, plus the person or service it acted on behalf of), what (the action, the object and its identifier), when (a synchronised UTC timestamp), where from (source address, client or device, request or trace id for correlation across services), outcome (allowed or denied, success or error) and, for exceptional access, why (a ticket reference). Do not log secrets or full personal records: log the object id, not its contents.

Making audit logs tamper-evident

An attacker, or a dishonest insider, wants to edit or delete the record of what they did. Perfect prevention is hard, so the realistic goal is tamper evidence: any change is detectable. The standard tool is a hash chain. Each record stores the hash of the previous record, and its own hash covers both its content and that previous hash. Change one record and its hash changes, which no longer matches the next record's stored "previous" value, and the break propagates to the end. Step through it.

Step through

A hash-chained audit log under attack

  1. Intact chain. Verification recomputes each hash from the record and the previous hash. Anyone can do this with no secrets.
  2. An insider downgrades the export record. Its hash no longer matches, and every later link inherits the break. A casual edit is caught.
  3. A capable insider rewrites every hash from the edit onward, so the chain verifies against itself. Only the checkpoint kept by a separate system exposes the rewrite. The chain gives evidence of tampering only if its head is anchored outside the writer's reach.

The same idea in running code. It builds a chain, then shows an edit, a full recomputation and a tail truncation, each checked against an HMAC checkpoint that a separate system would hold.

"""A tamper-evident audit log: each record commits to the hash of the one before it.
Plus an HMAC 'checkpoint' that a separate system holds, so a rewrite of the WHOLE chain is caught too."""
import hashlib, hmac, json

def digest(prev_hash, record):
    body = json.dumps(record, sort_keys=True, separators=(",", ":")).encode()
    return hashlib.sha256(prev_hash.encode() + body).hexdigest()

class AuditLog:
    def __init__(self): self.entries = []
    def append(self, actor, action, target):
        prev = self.entries[-1]["hash"] if self.entries else "0" * 64
        rec = {"seq": len(self.entries), "actor": actor, "action": action, "target": target}
        self.entries.append({"rec": rec, "prev": prev, "hash": digest(prev, rec)})
    def head(self): return self.entries[-1]["hash"]

def verify(entries):
    prev = "0" * 64
    for i, e in enumerate(entries):
        if e["prev"] != prev or e["hash"] != digest(prev, e["rec"]):
            return f"BROKEN at entry {i}"
        prev = e["hash"]
    return f"ok, {len(entries)} entries"

witness_key = b"held-by-a-separate-system-not-the-app-server"       # illustrative
def checkpoint(entries):
    return hmac.new(witness_key, f"{len(entries)}:{entries[-1]['hash']}".encode(), "sha256").hexdigest()

log = AuditLog()
log.append("alice", "login", "console")
log.append("alice", "export", "customers.csv")
log.append("bob", "grant_admin", "carol")
log.append("carol", "read", "payroll")
saved = checkpoint(log.entries)                      # stored elsewhere (another account, WORM storage, a witness service)
print("1. honest log:         ", verify(log.entries))

log.entries[1]["rec"]["action"] = "read"     # an insider downgrades the export
print("2. edit one record:    ", verify(log.entries))

forged = AuditLog()                          # a smarter insider recomputes every hash after the edit
for e in log.entries: forged.append(e["rec"]["actor"], e["rec"]["action"], e["rec"]["target"])
print("3. recompute all hashes:", verify(forged.entries), "(internally consistent!)")
print("   checkpoint matches?  ", hmac.compare_digest(saved, checkpoint(forged.entries)))

trunc = forged.entries[:3]                   # drop the last record (the payroll read)
print("4. truncate the tail:  ", verify(trunc), "| checkpoint matches?", hmac.compare_digest(saved, checkpoint(trunc)))
1. honest log:          ok, 4 entries
2. edit one record:     BROKEN at entry 1
3. recompute all hashes: ok, 4 entries (internally consistent!)
   checkpoint matches?   False
4. truncate the tail:   ok, 3 entries | checkpoint matches? False

The lessons are in lines 3 and 4 of the output. A chain with no outside anchor is internally consistent after a full rewrite (line 3), and truncating the tail leaves a valid shorter chain (line 4). Both are caught only by comparing against something the attacker could not rewrite: a checkpoint written to storage in a different account, write-once (object-lock or WORM) storage, or a transparency log. Certificate Transparency (chapter 4) applies the same idea at internet scale, with Merkle trees so that entries can be verified without downloading everything. Note also the word evident: this detects tampering, it does not prevent it, and it does nothing about records that were never written.

Detection engineering

Detection engineering is the practice of writing, testing and maintaining the logic that turns raw events into alerts, treating it as software. There are two broad styles.

  • Rules (signature or logic-based). "Five failed logins then a success from one address inside a minute." "A root-level role was granted outside change windows." "A canary credential was used." Rules are explainable, testable and cheap, but they only find what someone thought to describe. A shared vocabulary of attacker behaviour, such as the MITRE ATT&CK framework's catalogue of tactics and techniques, helps teams decide which behaviours they cover and which they do not.
  • Anomaly detection (statistical or learned). "This service account never touched that bucket before." "This user downloaded ten times their usual volume." It can surface unknown patterns, but it is noisy, needs a baseline that may itself be contaminated, and its alerts are harder to explain to the person who must act on them.

The central difficulty is the false positive: an alert on benign behaviour. If real attacks are rare, even a detector that is usually right produces mostly false alarms, simply because there is so much benign activity to mis-fire on. Responders learn to ignore noisy alerts, which is how real ones get missed (alert fatigue). So treat each detection as a product with measurable precision: it has an owner, a severity, a short runbook ("what to check first"), a test with a sample attack and a sample benign case, and a retirement rule if it never produces action. A handful of high-confidence detections beats a thousand that nobody reads.

Below, a rule that fires on the fail-then-succeed pattern, a spread-out case it correctly ignores, and a honeytoken check (next sections). The addresses are documentation ranges.

"""Two detections over a made-up event stream: a threshold rule and a canary token."""
from collections import defaultdict, deque

events = [  # (time_s, event, user, source_ip)
    (0,  "login_fail", "alice", "198.51.100.7"), (5,  "login_fail", "alice", "198.51.100.7"),
    (9,  "login_fail", "alice", "198.51.100.7"), (14, "login_fail", "alice", "198.51.100.7"),
    (20, "login_fail", "alice", "198.51.100.7"), (31, "login_ok",   "alice", "198.51.100.7"),
    (40, "login_fail", "bob",   "192.0.2.10"),   (900, "login_fail", "bob", "192.0.2.10"),
    (950, "login_ok",  "bob",   "192.0.2.10"),
    (960, "api_call",  "svc-ci", "203.0.113.50"),            # uses the planted canary key below
]
CANARY_KEYS = {"AKIA-CANARY-0001": "fake key planted in the old deploy repo"}

def rule_fail_then_success(stream, window=60, threshold=5):
    """Alert when a user succeeds right after >= threshold failures from one IP inside the window."""
    recent, alerts = defaultdict(deque), []
    for t, ev, user, ip in stream:
        q = recent[(user, ip)]
        while q and t - q[0] > window: q.popleft()
        if ev == "login_fail": q.append(t)
        elif ev == "login_ok" and len(q) >= threshold:
            alerts.append(f"t={t}s HIGH possible password guessing succeeded: {user} from {ip} after {len(q)} failures in {window}s")
    return alerts

for a in rule_fail_then_success(events): print(a)
print("rule hits on bob (2 spread-out failures):", sum("bob" in a for a in rule_fail_then_success(events)))

def canary_check(key_used, who, where):
    if key_used in CANARY_KEYS:
        return f"CRITICAL canary used by {who} from {where}: {CANARY_KEYS[key_used]}. No legitimate use exists; start incident response."
print(canary_check("AKIA-CANARY-0001", "unknown", "203.0.113.50"))
print("normal key ->", canary_check("AKIA-REAL-77", "svc-ci", "203.0.113.50"))

rule hits on bob (2 spread-out failures): 0
CRITICAL canary used by unknown from 203.0.113.50: fake key planted in the old deploy repo. No legitimate use exists; start incident response.
normal key -> None

SIEM concepts

A SIEM (security information and event management) system is the platform where events from many sources are gathered and examined. Strip the product names away and it does six jobs: collect events from applications, identity providers, endpoints, networks and the cloud control plane; normalise them to a common schema so "user" and "source address" mean the same thing across sources; store and index them for search over a retention window; correlate across sources and time (a sign-in from a new country followed by a mailbox rule change); alert on rules; and support investigation with fast queries over history. Related terms: a SOAR tool automates response steps such as disabling an account, and UEBA (user and entity behaviour analytics) is the anomaly-detection layer.

Design points for builders: emit structured events with stable field names; carry request and trace identifiers so a SIEM can join your logs with other services' (reliability chapter 5); keep time synchronised, because correlation across hosts needs trustworthy clocks; and budget for volume, since security logs are voluminous and retention is a cost and a privacy decision.

Security incidents are not reliability incidents

The reliability course's incident response chapter taught roles, severity levels, a communications cadence and blameless postmortems. Those transfer directly. What changes is the nature of the adversary and the order of priorities.

CauseA fault; indifferent to your responseAn adversary who observes and adapts

ScopeUsually visible in dashboardsUnknown; the thing you found may be the tip

Outside partiesCustomers, perhaps SLAsLawyers, regulators, insurers, law enforcement, affected individuals

Containment, without losing the evidence

Containment stops the damage from spreading while you work out the full scope. Options, from gentle to drastic: block the attacker's addresses or domains; disable the compromised account and revoke its sessions and tokens (chapter 6); remove a role or a trust relationship; quarantine a host by cutting its network access (preferably through the network controls of chapter 13 or a security group, rather than powering it off, since powering off destroys memory contents); or take a service offline. Each has a cost and a signalling effect, because a sophisticated attacker may notice and react. Responders therefore decide deliberately whether to contain at once (when data is leaving now) or to watch briefly to learn scope first (when a premature move would leave a second foothold unnoticed). That is a judgment call for the incident commander, not a default.

Evidence preservation

Before wiping or rebuilding anything, capture what you will need: snapshots of disks and, where feasible, memory; the relevant logs exported and hashed; the state of identity and access configuration at the time; a timeline of your own actions. Work from copies, write down who handled what and when (a chain of custody), and record a cryptographic hash of each artefact so later you can show it was not altered. If law enforcement or litigation is possible, involve legal counsel early; they may direct how investigation notes are written and who sees them.

Credential rotation at scale

Assume the attacker had access to anything the compromised system could read. That means secrets: API keys, database passwords, signing keys, session secrets. Rotating them one by one by hand, while the attacker may still be watching, is slow and error-prone. Prepare in advance:

  • An inventory. Know which secrets exist, where they are stored and which services use them. You cannot rotate what you cannot list. The secret scanners in the course toolbox help find strays (chapter 4).
  • A rotation path that works under pressure. Dynamic, short-lived credentials from a secrets manager (chapter 4) make rotation routine: revoke the lease and the secret is dead. Static keys in config files make it a project.
  • An order. Rotate the roots of trust first (identity provider credentials, KMS and CA administrator access, token-signing keys), then what they issued, then application secrets. Rotating downstream secrets while the attacker still holds a root only buys a few minutes.
  • Overlap and revocation. Normal rotation keeps the old key valid briefly so clients can switch. For a compromised key, that grace period is the attacker's grace period too. You must be able to revoke outright and accept brief breakage. The Storm-0558 case shows why a leaked signing key is the hardest version of this problem: everything it ever signed has to be re-examined.
  • Sessions and tokens. Passwords changed while old sessions stay valid accomplish little. Invalidate sessions, refresh tokens and long-lived API tokens as well.

Legal, communications and breach notification

Many jurisdictions require organisations to notify authorities, and sometimes the affected individuals, after certain security incidents involving personal data. As a general description only (and not legal advice): the EU's GDPR requires a controller to notify the competent supervisory authority of a personal data breach without undue delay and, where feasible, within 72 hours of becoming aware of it, unless the breach is unlikely to result in a risk to people's rights and freedoms. A processor must tell the controller without undue delay. Where the risk to individuals is high, individuals must also be informed. Many other regimes (for example, state breach laws in the US, sector regulators and customer contracts) have their own triggers and deadlines. The engineering implication is practical: the clock can start when you become aware, so the decision "is this a reportable breach?" must be made quickly, by people who know what to ask, with facts your logging can supply (what data, whose, how many, was it encrypted, was it accessed or merely exposed?). Well-kept audit logs and per-tenant data keys (chapter 17) are what turn "we do not know whether anyone's data was taken" into an answer.

Forensics basics

Digital forensics is the disciplined reconstruction of what happened from the traces left behind. A few ideas carry across tools:

  • Order of volatility. Collect the most perishable evidence first. RFC 3227, Guidelines for Evidence Collection and Archiving, lists the order roughly as processor state and caches, memory, network state and running processes, then disk, then remote logs and monitoring data, and finally archives. Memory and connections vanish at reboot; disks and archives do not.
  • Preserve, then analyse. Image or snapshot first and analyse the copy. Every command typed on a live suspect machine alters it.
  • Timelines are the product. The question is nearly always "what happened, in what order?". Correlated timestamps from many sources, in UTC, are what answer it, which is why synchronised clocks matter.
  • In the cloud the analogues are snapshots of volumes, exported control-plane and data-access logs, a frozen copy of identity and role configuration, and a pinned image of the running container, taken before the orchestrator replaces it (chapter 14). Ephemeral infrastructure means evidence disappears on its own schedule unless you capture it.

Honeytokens and canaries

A honeytoken (or canary token) is a fake credential, record or resource with no legitimate use, planted where an intruder will look: an access key in an old deployment repository, a fake admin account, a decoy row in the customer table, a spreadsheet named like a password list. Because nothing real should ever touch it, any use is a high-confidence signal, which is the rare detection with almost no false positives. The key is unique per location so an alert tells you where the attacker found it, and the decoy must be genuinely powerless: a credential that can do nothing, monitored by something that alerts when it is tried. The last lines of the earlier detection script show the check. Honeytokens complement rather than replace other detection: they catch an attacker who is searching, and say nothing about one who knows what they want.

Detection in the case files

Two of this course's case studies are largely stories about detection. In Equifax an unpatched component was exploited and the intrusion went unnoticed for an extended time; the case study traces how a lapse in the monitoring tooling's own certificate contributed, a reminder that your detection stack is a system that needs maintenance too. In Storm-0558 the compromise of a signing key was surfaced through audit logs and a customer who was reading them, and the later independent review made the argument for logging that customers can actually access. Read both and ask, for each: which event should have raised an alert, who would have seen it, and what would they have done?

Try it yourself

Take a service you own (a lab app is fine) and write down its audit-event list: for each of the four families, which events exist today, which are missing, and where do they go? Then ask the adversarial question: if someone with the application's own credentials wanted to hide an action, which of those records could they edit? If the answer is "all of them", move the records to a place those credentials cannot write to. Only monitor and test systems you own or are authorised to monitor.

Distributed systems connection

A tamper-evident log is a close cousin of the replicated logs and Merkle structures in the distributed-systems course, and its "witness" is the same idea as a quorum or an external observer: agreement that does not depend on a single writer's honesty (Byzantine faults). Correlating events across services depends on the same clocks and trace ids that make distributed debugging possible. And security incident response reuses the structure of reliability incident response, with a thinking adversary and evidence preservation added.

Key takeaways

  • Log authentication events, authorization decisions (especially denials), privileged actions and data exports, each with who, what, when, where, outcome and a correlation id, and without secrets or full personal data.
  • Send audit records out of the blast radius to storage the application's own credentials cannot rewrite.
  • Hash chains make tampering evident, not impossible; they need an outside anchor (a witness checkpoint, write-once storage or a transparency log) to defeat a full rewrite or truncation.
  • Rules are explainable and cheap but cover only what you thought of; anomaly detection finds the unknown but is noisy. Manage detections as owned, tested, tuned software, and fight alert fatigue.
  • Security incidents differ from reliability incidents: an adversary adapts, scope is unknown, evidence must be preserved before cleanup, and legal and communications run in parallel from the start.
  • Containment is a judgment between stopping harm now and learning scope; prefer network isolation to power-off, and run the response from channels the attacker cannot read.
  • Prepare credential rotation before you need it: an inventory, short-lived credentials, roots of trust first, and the ability to revoke outright.
  • Breach notification clocks can start at awareness (under GDPR, 72 hours to the authority where feasible). This is general information, not legal advice. Honeytokens give high-confidence alerts for almost no cost.

Check your understanding

An insider edits one audit record and then recomputes every later hash in the chain. Why does verifying the chain alone not catch this?

  1. Hash chains cannot detect any edits
  2. SHA-256 can be reversed by insiders
  3. The rewritten chain is internally consistent; only a checkpoint or head hash stored where the insider cannot write reveals that it changed
  4. Verification only works on the first record
The chain proves consistency, not authenticity. Anchoring the head hash in a separate system (or write-once storage, or a transparency log) is what turns "internally consistent" into "unchanged".

Why log authorization denials, not just allowed actions?

  1. Bursts of denials from one principal are a reconnaissance or probing signal, and they show which controls are actually exercised
  2. Denials are cheaper to store
  3. Allowed actions never need auditing
  4. Regulations forbid logging allows
An attacker who has stolen a limited credential probes its edges. Denials are the footprints. Sensitive allowed actions need logging too.

A detection fires 200 times a day and responders have stopped reading it. What is the right engineering response?

  1. Send it to more people
  2. Raise its severity
  3. Delete the logs it uses
  4. Treat it as a product with poor precision: tune or narrow the logic, add context and a runbook, or retire it, so that alerts that remain are worth acting on
Alert fatigue is how real attacks get missed. A detection earns its place by producing actions, so measure how many alerts led to one.

You suspect a production host is compromised. What is the better first step?

  1. Reboot it to clear the attacker's processes
  2. Isolate it from the network (while capturing memory and a disk snapshot as feasible) and preserve logs before rebuilding
  3. Delete the suspicious files and carry on
  4. Announce the suspected compromise in the team chat that runs on the same network
Rebooting loses memory evidence and cleaning up destroys the traces you need for scope. Isolation stops the spread, and communications should use a channel the attacker cannot read.

During credential rotation after a compromise, why is the usual "keep the old key valid for a grace period" approach risky?

  1. Grace periods are never used in rotation
  2. It breaks TLS
  3. The grace period lets the attacker keep using the compromised key; a compromised key must be revoked immediately, accepting some breakage
  4. It makes the new key weaker
Overlap exists for convenience in routine rotation. With a stolen key the convenience is the attacker's access window.

Why is a honeytoken alert unusually reliable?

  1. It uses machine learning
  2. The decoy has no legitimate use, so any touch is suspicious by construction
  3. It blocks the attacker automatically
  4. It is stored in encrypted form
Reliability comes from the absence of benign use. The caveat: it only helps against an attacker who stumbles on the decoy while searching.

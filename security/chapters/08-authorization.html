Authorization

Authentication tells you who is calling. Authorization decides what they may do, to which object, right now. It is where most real applications fail, because it must be decided at every operation and cannot be bolted on at the front door. This chapter compares ACLs, roles, attributes and relationships, shows where to run the decision, dissects the single most common API vulnerability, and ends with the subtle problems of caching permissions across a distributed system.

Why this matters

Broken access control is the first category of the OWASP Top 10, in the 2021 edition and again in the 2025 edition. It is common because authorization is a thousand small decisions spread through the code, each easy to forget, and because authentication bugs are loud (nobody can log in) while authorization bugs are silent (everything works, for the wrong person). A good authorization design makes the right check the default and the missing check the exception that tests catch.

Authentication versus authorization

You met the distinction in chapter 5. An authenticated principal (a user, a service, an API client) attempts an action on a resource. Authorization is the function allow(principal, action, resource, context), and every design question in this chapter is about what that function consults and where it runs. Two principles from chapter 2 apply directly: complete mediation (every access is checked, not only the first) and fail-safe defaults (no explicit grant means deny).

Four ways to express permissions

Access control lists

An access control list (ACL) attaches to each object a list of who may do what: file permissions on a Unix system, the sharing dialog of a document, a bucket policy. ACLs answer "who can open this file?" directly. They are poor at the reverse question, "what can alice open?", which requires scanning every object, and they are tedious to manage at scale because each object has its own list.

Role-based access control

Role-based access control (RBAC) inserts a level of indirection: users are assigned roles (viewer, editor, billing-admin), and roles carry permissions. Adding an employee means assigning a role; changing what editors can do means editing one role. It maps well to job functions and to audit questions ("who are the admins?") and is the default model of most platforms.

Its limits appear as the system grows:

  • Roles are global, objects are not. A role says "may edit documents", not "may edit this document". Fixes tend to multiply roles: editor-of-project-17.
  • Role explosion. If access depends on department, level and region, the roles are the cross product, as the code below counts (200 roles for 10 × 4 × 5), and no one can review them.
  • Rules about context do not fit. "Only from a managed device", "only during an incident", "only for own tenant" are not roles.

Attribute-based access control

Attribute-based access control (ABAC; NIST SP 800-162 is the standard overview) makes the decision a policy over attributes of the subject (department, clearance), the resource (owner, classification, tenant), the action and the environment (time, device, network). It handles context and avoids role explosion: one rule replaces a hundred roles. The price is analysability. "Who can read this document?" can only be answered by evaluating the policy over every possible user, policies interact in subtle ways, and the correctness of the whole rests on the correctness of attribute data (a user whose department attribute is stale gets the wrong access).

Relationship-based access control

Relationship-based access control (ReBAC) derives permission from a graph of relationships: alice is an editor of this document; this document is inside this folder; bob is a member of this group; that group may view this folder. A permission check asks whether a path of the right kind exists. This is a natural model for anything with sharing and hierarchy (documents, repositories, organisations), and it is the model behind Google's Zanzibar (Pang et al., USENIX ATC 2019), the system that answers permission checks for many Google products. Read the Zanzibar case for how it is built and run.

The data is a set of relation tuples, written object#relation@subject, such as doc:plan#editor@user:alice. A subject can itself be a userset, "everyone who has relation R on object O", as in folder:q3#viewer@group:eng#member. A userset rewrite rule defines relations in terms of others: every editor is a viewer; a document's viewers include the viewers of its parent folder. Rewrites keep the stored tuples small (alice is stored once as an editor; viewing follows from the rule) and put policy in a schema instead of the tuple data.

Here is a runnable comparison: RBAC (which cannot say which document), a small ABAC policy, and a ReBAC checker with this, computed (editor implies viewer) and tuple-to-userset (inherit from the parent) rewrites, printing the path it used. Authorization data is plain Python sets; nothing here touches a network.

"""RBAC vs a small Zanzibar-style ReBAC check with userset rewrites. Pure Python, no I/O."""

# ---------- RBAC: user -> roles, role -> permissions. Cannot say "THIS document". ----------
ROLE_PERMS = {"viewer": {"doc:read"}, "editor": {"doc:read", "doc:write"}, "admin": {"doc:read", "doc:write", "doc:delete"}}
USER_ROLES = {"alice": {"editor"}, "bob": {"viewer"}, "carol": {"admin"}}

def rbac_check(user: str, perm: str) -> bool:
    return any(perm in ROLE_PERMS[r] for r in USER_ROLES.get(user, ()))

# ---------- ReBAC: tuples (object, relation, subject) ----------
# subject is "user:x" or a userset "type:id#relation" meaning "everyone with that relation on that object".
TUPLES = {
    ("doc:plan",        "parent", "folder:q3"),
    ("folder:q3",       "viewer", "group:eng#member"),
    ("doc:plan",        "editor", "user:alice"),
    ("group:eng",       "member", "user:bob"),
    ("group:eng",       "member", "group:interns#member"),   # nested group
    ("group:interns",   "member", "user:dave"),
    ("doc:secret",      "owner",  "user:carol"),
}

# Rewrite rules per (type, relation): which other paths also imply this relation.
#   ("this",)                         direct tuples
#   ("computed", rel)                 same object, other relation   (editor implies viewer)
#   ("ttu", via_rel, rel)             follow tuple via_rel to a parent object, then check rel there
REWRITES = {
    ("doc", "owner"):  [("this",)],
    ("doc", "editor"): [("this",), ("computed", "owner")],
    ("doc", "viewer"): [("this",), ("computed", "editor"), ("ttu", "parent", "viewer")],
    ("folder", "viewer"): [("this",)],
    ("group", "member"): [("this",)],
}

def check(obj: str, rel: str, user: str, trace: list, depth: int = 0, seen=None) -> bool:
    seen = seen or set()
    if (obj, rel) in seen: return False                   # cycle guard
    seen = seen | {(obj, rel)}
    pad = "  " * depth
    typ = obj.split(":")[0]
    for rule in REWRITES.get((typ, rel), []):
        if rule[0] == "this":
            for (o, r, s) in sorted(TUPLES):
                if o == obj and r == rel:
                    if s == user:
                        trace.append(f"{pad}{obj}#{rel} has tuple -> {s}  YES"); return True
                    if "#" in s:                            # userset: recurse into that group
                        so, sr = s.split("#")
                        trace.append(f"{pad}{obj}#{rel} includes userset {s}; checking it")
                        if check(so, sr, user, trace, depth + 1, seen): return True
        elif rule[0] == "computed":
            trace.append(f"{pad}{obj}#{rel} is implied by {obj}#{rule[1]}")
            if check(obj, rule[1], user, trace, depth + 1, seen): return True
        elif rule[0] == "ttu":
            for (o, r, s) in sorted(TUPLES):
                if o == obj and r == rule[1]:
                    trace.append(f"{pad}{obj}#{rel} inherits from {s}#{rule[2]} (via {rule[1]})")
                    if check(s, rule[2], user, trace, depth + 1, seen): return True
    trace.append(f"{pad}{obj}#{rel}: no path for {user}")
    return False

def show(obj, rel, user, verbose=True):
    trace = []
    ok = check(obj, rel, user, trace)
    print(f"check({obj}#{rel}, {user}) = {ok}")
    if verbose:
        for line in trace: print("   ", line)

# ---------- ABAC: a policy over attributes of user, resource and context ----------
def abac_allow(user: dict, action: str, doc: dict, ctx: dict) -> bool:
    if user["tenant"] != doc["tenant"]: return False                      # tenant isolation first
    if action == "read":
        return doc["classification"] <= user["clearance"] and (doc["dept"] == user["dept"] or user["role"] == "auditor")
    if action == "write":
        return doc["owner"] == user["id"] and ctx["device_managed"]
    return False

if __name__ == "__main__":

    depts, levels, regions = 10, 4, 5
    print(f"  role explosion: {depts} departments x {levels} levels x {regions} regions = {depts*levels*regions} roles to define and review")

    print("\n== ABAC ==")
    u = {"id": "u1", "tenant": "acme", "dept": "eng", "clearance": 2, "role": "engineer"}
    d1 = {"tenant": "acme", "dept": "eng", "classification": 1, "owner": "u1"}
    d2 = {"tenant": "acme", "dept": "eng", "classification": 3, "owner": "u2"}

    for name, d in (("d1", d1), ("d2 (too secret)", d2), ("d3 (other tenant)", d3)):

Policy engines

As rules grow, scattering if user.role == "admin" through the code becomes unmanageable and unauditable. A policy engine moves the decision logic into a separate, declarative policy that the application queries: it sends the facts (the principal, action, resource, context) and receives a decision. Benefits: one place to review, version and test policy; policy changes without redeploying services; consistent decisions across services. The costs are one more component to run and secure, a new language to learn, and the need to deliver the data policies depend on.

  • Open Policy Agent (OPA), a CNCF project, evaluates policies written in Rego, a declarative query language over JSON documents. It is general purpose: the same engine is used for API authorization, Kubernetes admission control and infrastructure checks. It is typically embedded as a library or run as a sidecar service.
  • Cedar, open sourced by AWS, is a purpose-built authorization language with permit and forbid statements over principal, action and resource, and default deny. It was designed to be restricted enough to be analysed automatically (for example, to prove that one policy set grants no more than another), at the cost of generality.

Both snippets below are illustrative, not run here; they show the shape.

package app.authz
default allow := false

allow if {
    input.action == "read"
    input.user.tenant == input.doc.tenant     # tenant isolation
    input.doc.dept == input.user.dept
}
permit (
  principal in Group::"eng",
  action == Action::"view",
  resource in Folder::"q3"
);
forbid (principal, action, resource)
  when { resource.classification == "secret" && !principal.cleared };

A policy engine decides; it does not know your data. Where a policy needs facts (is this user in this group?), you must load them into the engine or look them up, and the freshness of that data is part of the security of the system (see caching, below).

Where to enforce

The decision can be taken at three places, and mature systems use all of them for different questions:

  • At the gateway or proxy: authenticate, validate the token, check coarse scopes or role ("does this token have orders.read?"), apply limits. It is uniform and efficient but cannot know whether order 123 belongs to this customer.
  • In the service: the only place that understands the domain: ownership, sharing, state ("only drafts are editable"). Business-level authorization belongs here, as close to the operation as possible, and should be done by a shared, tested component rather than hand-written per endpoint.
  • In the data layer: filters that make a cross-tenant read impossible by construction: a mandatory tenant_id predicate, or database features such as row-level security. This protects against a service bug, an injection flaw, or a developer writing a new query and forgetting the check.

This is defence in depth (chapter 2): a gateway rule alone fails the moment someone calls the service directly, which anything inside the network can do. The attacker in the diagram has bypassed the front door; the service and data checks are what remain. Also remember who the identity is: pass the end user's identity (and the original token's audience and scope) to downstream services, not just "the gateway said it was fine", or every downstream service becomes a confused deputy (below).

Broken object level authorization

The most frequent API vulnerability has an unglamorous name: broken object level authorization (BOLA), the first entry in the OWASP API Security Top 10. It is also called an insecure direct object reference (IDOR). The pattern: an endpoint takes an object identifier from the request (GET /invoices/2), the user is correctly authenticated, and the code fetches the object without asking whether this user may see that object. Anyone can change the number.

The listing below builds a tiny in-memory database and two handlers, one vulnerable and one fixed. It runs entirely against its own data.

"""Broken object level authorization (IDOR) in a toy handler, and the fix. In-process only."""
import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("""
 create table invoices(id integer primary key, tenant_id text, owner text, amount int);
 insert into invoices values (1,'acme','alice',120),(2,'acme','bob',90),(3,'globex','zed',5000);
""")

def get_invoice_vulnerable(session: dict, invoice_id: int):
    # Authenticated, but never asks "is THIS user allowed THIS row?"
    return db.execute("select id, tenant_id, owner, amount from invoices where id=?", (invoice_id,)).fetchone()

def get_invoice_fixed(session: dict, invoice_id: int):
    # Authorization is part of the query: tenant always, and ownership unless the user has an admin role
    row = db.execute(
        "select id, tenant_id, owner, amount from invoices where id=? and tenant_id=? and (owner=? or ?)",
        (invoice_id, session["tenant"], session["user"], "billing_admin" in session["roles"])).fetchone()
    return row            # None -> the caller returns 404, same as 'does not exist'

alice = {"user": "alice", "tenant": "acme", "roles": []}
for i in (1, 2, 3):
    print(f"id={i} vulnerable ->", get_invoice_vulnerable(alice, i), "| fixed ->", get_invoice_fixed(alice, i))
id=1 vulnerable -> (1, 'acme', 'alice', 120) | fixed -> (1, 'acme', 'alice', 120)
id=2 vulnerable -> (2, 'acme', 'bob', 90) | fixed -> None
id=3 vulnerable -> (3, 'globex', 'zed', 5000) | fixed -> None

Alice (tenant acme) can read her own invoice 1 through either handler. The vulnerable handler also returns Bob's invoice 2 (same tenant, different owner) and a customer of another company, invoice 3. The fixed version puts authorization into the query: tenant and ownership (or a recognised role) are part of the lookup, so there is no object to leak and the response is the same as for a non-existent id.

  • Use the caller's identity, not the request's. The tenant and user come from the authenticated session or token, never from a field the client supplies.
  • Hard-to-guess identifiers (UUIDs) are not authorization. They make enumeration harder and are worth using, but they leak through logs, shared links and screenshots; the check is still required.
  • Check on every route, including writes and bulk operations. A listing endpoint that returns "all invoices" and a search endpoint that ignores ownership are the same bug in different clothes.
  • Test with two users. For each endpoint, a test that logs in as user A and requests user B's object, expecting not-found, finds this bug class reliably.
  • Choose 404 or 403 deliberately. Returning 403 confirms the object exists; for sensitive resources return 404 for both cases.

Only test what you own or are authorised to test

Changing identifiers in requests to see other people's data is exactly what an attacker does, and is a crime against a system you are not authorised to test. Run these checks in your own test environment with your own test accounts, or in a programme where the owner has given written permission.

The confused deputy and capabilities

In 1988 Norm Hardy described the confused deputy problem. A service (the deputy) holds authority of its own. A user who has less authority asks it to do something, and the deputy, obliging, uses its authority to do what the user could not. In Hardy's account a compiler service had permission to write a system file (a billing or statistics file); a user could pass the file's name as the place to write output, and the compiler overwrote it, because the system checked the compiler's rights and nobody checked the user's. The deputy was not malicious; it was confused about whose authority it was exercising.

The pattern is everywhere. A browser that attaches cookies to a forged cross-site request is a confused deputy (CSRF, chapter 10). A server that fetches any URL a user provides, using its privileged network position, is one (SSRF, chapter 11). A cloud service that assumes a customer-supplied role in a customer's account on behalf of a request from a different customer is one; cloud providers address it with conditions such as an external identifier the legitimate customer controls. An API that accepts any validly signed token, without checking the audience, lets a token meant for one service act against another.

The deeper cure is the capability way of thinking. In an ambient-authority system, a request names a resource ("write /sys/billing") and the system looks up who is asking. In a capability system, a request carries an unforgeable reference that is itself the permission: the right to write this file, handed to you by someone who had it. The deputy can then use only what it was given for this request. Several everyday mechanisms are capabilities in practice: a pre-signed storage URL, a file descriptor passed to a child process, a share link with a long random secret, an OAuth access token narrowed to one audience and scope. They have the properties to keep in mind: unguessable, delegable (and so can leak), and best kept narrow and short lived. The practical advice for a service: carry the caller's authority down the call chain (propagate the user's token or a down-scoped derivative, rather than acting with a super-powerful service identity), and when you must use your own authority, check the requester's rights first.

Multi-tenant checks

In a multi-tenant system, where many customers share one deployment, the most important authorization rule is the boundary between tenants. The convention that survives code reviews: tenant_id is on every row and in every query, and comes from the authenticated principal.

  • Put tenant_id on every table (including join and audit tables), include it in primary and foreign keys so a child row cannot point at another tenant's parent, and in every index you query by.
  • Enforce it below the application too: row-level security policies, or a data-access layer that rewrites every query with the tenant filter, so a forgotten WHERE clause fails closed.
  • Include the tenant in cache keys, queue topics, object-storage prefixes and search indexes. A cache keyed by object id alone serves tenant A's data to tenant B.
  • Test the negative: create two tenants, try every operation from one against the other's objects.

Chapter 15 takes isolation models (silo, pool, bridge) and per-tenant keys further; studio 1 asks you to design the whole picture.

Caching decisions and the new-enemy problem

Authorization checks sit on the hot path of every request, so systems cache them or replicate the data they read. Caching is where correctness can quietly leak away:

  • The cache key must hold everything the decision depends on: principal, action, resource, and any context (tenant, device state). A key that omits one turns a correct decision for one request into a wrong one for another.
  • Staleness is a window of wrong answers. After a permission is revoked, cached "allow" decisions persist until they expire or are invalidated. Revoking is time-critical; granting is not (a few seconds late is merely irritating). Many designs therefore use short TTLs, or explicit invalidation for removals, and are cautious about caching "allow" for sensitive actions.
  • Cache negative results carefully so that a newly granted permission eventually becomes visible.

A subtler issue is the new-enemy problem, named in the Zanzibar paper. Two events happen in order: Alice first removes Bob from a document's access list, and then adds sensitive content to the document. The order was chosen deliberately to be safe. But if the authorization check for Bob's later read is answered by a replica that has not yet seen the removal, it evaluates the old list, and Bob, the "new enemy", sees the new content. Nothing was misconfigured; the system simply evaluated the ACL at the wrong point in time.

Zanzibar's answer is a consistency token it calls a zookie. When content is written, the application stores a zookie reflecting the ACL version at that moment. Later checks present the zookie, which says "evaluate at a snapshot no older than this". The sketch below models it on simulated versions (no real replication), so the mechanism is visible:

"""The new-enemy problem on simulated time: a stale authorization replica vs a consistency token (zookie)."""
class AuthzStore:
    """Versioned ACL. Replica lag means a replica may only have applied versions up to `applied`."""
    def __init__(self):
        self.versions = {0: {"bob"}}          # version -> set of users allowed to view doc1
        self.latest = 0
    def update(self, allowed):                # a write to the ACL gets a new version number
        self.latest += 1; self.versions[self.latest] = set(allowed); return self.latest
    def check(self, user, replica_applied, at_least=0):
        # a replica can answer only from versions it has; a zookie says "not older than this"
        if replica_applied < at_least:
            replica_applied = self.latest      # fall back to the leader (or wait for the replica)
        return user in self.versions[replica_applied]

acl = AuthzStore()
print("t0: ACL v0 allows bob to view doc1")

v = acl.update({"alice"})                      # alice removes bob ...
print(f"t1: alice removes bob -> ACL v{v} (replica B has not applied it yet; it is at v0)")
content_zookie = v                             # ... THEN uploads the sensitive content, recording the ACL version
print(f"t2: alice uploads the sensitive file; the content stores zookie = v{content_zookie}")

print("\nt3: bob asks to read the file")
print("  no zookie, stale replica answers from v0 :", "ALLOWED (new enemy!)" if acl.check("bob", replica_applied=0) else "denied")
print("  with the zookie, replica must be >= v1   :", "ALLOWED" if acl.check("bob", replica_applied=0, at_least=content_zookie) else "denied")
t0: ACL v0 allows bob to view doc1
t1: alice removes bob -> ACL v1 (replica B has not applied it yet; it is at v0)
t2: alice uploads the sensitive file; the content stores zookie = v1

t3: bob asks to read the file
  no zookie, stale replica answers from v0 : ALLOWED (new enemy!)
  with the zookie, replica must be >= v1   : denied

This is the same family of problems as ordering and visibility in distributed databases: snapshots, timestamps and causal tokens. Zanzibar is built on a globally consistent database whose timestamps give a total order, and the zookie is an encoded timestamp. See distributed chapter 7 for how time and ordering work at that scale. The practical lesson for your own design is more modest: when authorization data is replicated or cached, decide explicitly which operations require a fresh answer (those that expose new content, or follow a revocation) and which tolerate a stale one.

Audit logs of decisions

An authorization system that cannot explain itself is a liability. Record each decision for sensitive resources: the principal, action, resource, the outcome, the reason or policy version that produced it, the request id and time. Log denials as well as allowances: a burst of denials from one account is often the first sign of probing (chapter 18). Practical points: write audit records to a separate, append-only store with restricted access, so the person being audited cannot edit them; never log secrets or tokens (see reliability chapter 5); keep decisions explainable (the ReBAC path above is already a reason); and record policy changes themselves, since "who changed what rule and when" is the second question after any incident.

Analogy: the hotel key card

The front desk (authentication) checks your passport and encodes a card. The card (a capability) opens your room and the gym, not other rooms; doors (the data layer) check the card every time, whatever the lobby said; the card stops working when the booking ends; and the hotel keeps a log of every door that opened.

Where it breaks down: a door lock checks only the card. Real authorization often needs to consult changing relationships and context, and that data can be stale in exactly the way a printed card cannot be.

Distributed systems connection

Authorization at scale is a replicated, read-heavy database with a security-critical consistency requirement. The new-enemy problem is a stale-read anomaly with consequences, and the fix, a token that carries a causal position, echoes causal consistency and snapshot reads from the distributed course. Per-request checks are also an availability dependency: if the authorization service is slow or down, you must choose between failing closed (an outage) and failing open (a breach). The sound default is to fail closed, with caches and local replicas to absorb brief failures.

Key takeaways

  • Authorization is allow(principal, action, resource, context), checked on every access, defaulting to deny. Broken access control is the first category of the OWASP Top 10 (2021 and 2025).
  • ACLs attach lists to objects; RBAC groups permissions into roles (and can explode); ABAC evaluates policies over attributes (flexible but hard to audit); ReBAC derives permission from a graph of relationships (Zanzibar-style tuples and userset rewrites) and can explain every grant.
  • Policy engines (OPA with Rego, Cedar) move decisions out of code into reviewable, testable policy. They decide; you must still supply fresh data.
  • Enforce in layers: coarse checks at the gateway, object-level checks in the service, tenant filters in the data layer. Never rely on the front door alone.
  • BOLA/IDOR: authenticated but not authorized per object. Put ownership and tenant into the query, take identity from the session, test with two users. Unguessable ids are not a check.
  • The confused deputy (Hardy, 1988) uses its own authority for a caller without it. Propagate the caller's authority, validate audiences, and prefer capabilities (unforgeable, narrow, short-lived references) to ambient authority.
  • Tenant id on every row, query and cache key, derived from the principal. Cached or replicated decisions are stale decisions; revocations are urgent, and the new-enemy problem needs ordered evaluation (Zanzibar's zookies).
  • Log decisions, including denials and the reason, to a store the audited party cannot edit.

Check your understanding

An endpoint GET /reports/{id} checks that the caller is logged in, then returns the report with that id. What is the vulnerability, and what is the best fix?

  1. Cross-site scripting; encode the output
  2. Weak password hashing; use scrypt
  3. Broken object level authorization; make the lookup depend on the caller's tenant and permission (and test with two users), returning not-found otherwise
  4. Rate limiting is missing; add a limiter
Authentication is present but nothing connects the caller to the object. Rate limiting only slows enumeration, and unguessable ids only make it harder. The fix is an authorization check tied to the object, ideally inside the query.

A company has 12 departments, 5 seniority levels and 8 regions, and creates one role per combination. Which problem is this, and which model addresses it?

  1. Role explosion (480 roles); attribute- or relationship-based rules express the same intent with a few policies
  2. Replay; use nonces
  3. Token theft; shorten lifetimes
  4. Cache poisoning; add a TTL
12 × 5 × 8 = 480. A policy such as "same department, level at least the document's, region matches" replaces them, at the cost of harder audits.

In a Zanzibar-style schema, the rule "a document's viewers include the viewers of its parent folder" is an example of what?

  1. An ACL entry for a single user
  2. An ABAC attribute
  3. A denylist
  4. A userset rewrite: permission is derived by following a relationship to the parent rather than listing each user
Rewrites let relationships define permissions. Sharing a folder automatically shares its documents, and removing one tuple removes everything that flowed through it.

A compiler service can write to a protected billing file. A user without that right asks it to write its output to the billing file's name, and it does. Why is this the confused deputy problem?

  1. The user guessed a password
  2. The service exercised its own authority on behalf of someone who lacked it, because the check was about the service, not the requester
  3. The file was not encrypted
  4. The service had a memory bug
The deputy was not hacked; it was misled about whose authority to use. Passing a capability for the user's file, or checking the requester's rights, removes the ambiguity. SSRF and CSRF follow the same pattern.

Alice removes Bob from a document's ACL, then uploads a sensitive file to it. Bob, still served by a lagging authorization replica, reads the file. What is this called, and what prevents it?

  1. A deadlock; take locks in order
  2. A timing attack; use constant-time compare
  3. The new-enemy problem; store a consistency token with the content and require checks to evaluate at a snapshot at least that fresh
  4. Session fixation; regenerate the session id
The problem is evaluating an ACL at the wrong time, not any misconfiguration. A zookie-style token carries the ACL version known at write time so a stale replica cannot answer.

A gateway enforces "only authenticated users with scope orders.read may call the orders service". Why is that not enough?

  1. It cannot know whether this user owns order 123, and anything that reaches the service without passing the gateway skips the check; the service and data layer must enforce object and tenant rules
  2. Gateways cannot read tokens
  3. Scopes are always forged
  4. It is enough; further checks are redundant
The gateway sees the route, not the object. Defence in depth means the service decides per object and the data layer enforces tenant boundaries, so a bypass or a bug in one layer does not become a breach.

Start Here

Every system you have designed so far assumed that the things going wrong were accidents: a crashed disk, a slow network, a careless deploy. This course adds a new kind of failure, one that is chosen: someone who studies your system looking for the one input you did not expect.

Why this matters

A security flaw is not a rare event you can plan capacity for. It is a property of the design that an attacker needs to find only once, while the defenders must have got everything right. Senior engineers are expected to look at a design diagram and say where the trust assumptions are, what happens when one of them is wrong, and which two or three decisions matter most. That is a design skill, not a specialist's trick, and it sits naturally between reliability (course 5) and the system design studio (course 7).

Why a security course in a system-design path?

The first six courses taught you to ask "what if this component fails?" Replication, retries, timeouts and failover all answer that question for random failures. A random failure does not read your source code. It does not notice that your retry logic doubles the load on an already overloaded service and then aims at it. An adversary, a party who deliberately tries to make the system do something its owners did not intend, does exactly that.

Look at a few designs from earlier courses through that lens. The replicated database of data chapter 15 tolerates a crashed follower, but what if the follower is run by a compromised host and returns false data? The consensus protocols of distributed chapter 12 were written for the crash-fault case; Byzantine faults, where nodes behave arbitrarily or maliciously, cost far more, which is why most systems instead draw a boundary around the nodes they trust and defend that boundary. The API gateway of architecture chapter 9 rate-limits clients for fairness; an attacker can use the same endpoint to guess passwords at the maximum permitted rate. Reliability asks "can it survive failure?" Security asks "can it survive someone who wants it to fail, or wants what it holds?"

What we are protecting: the CIA triad, and two more

Security engineers describe what a system must protect with three classic properties, usually abbreviated CIA (nothing to do with the agency):

Confidentiality

Only authorised parties can read the information. Violated by a leaked database dump, a misconfigured storage bucket, or an eavesdropper on the network.

Integrity

Information and behaviour change only in authorised ways, and tampering is detectable. Violated by a modified price, a forged message or an altered software update.

Availability

Authorised users can use the system when they need it. Violated by deleting data, ransomware, or flooding a service with traffic. Courses 4 and 5 were largely about this one.

Two further properties come up so often in system design that it helps to name them separately, even though they are sometimes folded into integrity:

  • Authenticity: you know who or what you are talking to, and that a message really came from the claimed source. A perfectly intact message from an impostor still violates it.
  • Accountability (related to non-repudiation): actions can be traced to an actor afterwards, and the actor cannot plausibly deny them. This is the reason audit logs exist, and the reason a digital signature differs from a shared-secret MAC (chapter 3).

These properties conflict. Maximum confidentiality (encrypt everything, keep no logs) fights accountability and operability. Maximum availability (accept any request, from anyone) fights integrity. Security work is rarely "add more security"; it is deciding which property matters most for which data, and paying for exactly that.

Assets, adversaries and attack surface

Three terms organise nearly everything that follows.

An asset is something of value to protect: customer records, signing keys, the ability to run code on your servers, even your uptime or reputation. Naming assets first is not bureaucracy. It stops you spending effort defending things nobody wants and neglecting things everybody does. Often the most valuable asset is not the data but the credential that unlocks it, such as a cloud access key or an administrator session.

An adversary (or threat actor) has goals and capabilities. A curious teenager with a scanner, a criminal group running automated credential stuffing, a disgruntled employee with legitimate access, and a well-resourced nation-state do not behave alike, and a defence that is overkill against one is irrelevant against another. Chapter 1 turns this into a tool: an explicit adversary model states who you defend against and, just as importantly, who you do not.

The attack surface is the set of places where an adversary can interact with the system: every network port, endpoint, file format you parse, third-party package you import, admin console, deployment pipeline, and employee who can be sent an email. It is not the same as your code size. A large internal library with no inputs from outside adds little; one small endpoint that parses an uploaded file adds a lot.

Analogy: a building with many doors

Think of a building holding a safe. The safe is the asset. The doors, windows, delivery bay, the cleaner's key and the back-office phone line are the attack surface. A burglar's options depend on skill, tools and patience: the adversary model. Good security is not an unbreakable safe, it is knowing which doors exist, deciding which ones to remove, and making the remaining ones cost more to open than the contents are worth.

Where it breaks down: a building has a handful of doors that you can walk around and count. Software has doors you did not know you built (a debug endpoint, a logging library that interprets patterns), and an attacker can try millions of doors per second, from anywhere, without being seen.

Security is a property of the whole system

The saying that "a chain is only as strong as its weakest link" is the single most useful mental model. Suppose you encrypt traffic with the best protocol available, store passwords with a slow salted hash, and keep the database in a private network. An attacker will not attack the encryption. They will look for the link that is easy: a reused password on a staff account, an image-resizing library with a known vulnerability, a storage bucket left public, a helpful support agent who resets any account on request, or a CI pipeline that anyone can modify. A system that is 99% careful and has one wide-open path is, from the attacker's point of view, an open system.

This has two consequences for how we work. First, security cannot be bolted on by one specialist at the end; it emerges from every design decision, which is why architecture chapter 8 listed it among the cross-cutting concerns and said to enforce it "at the boundaries". Second, the useful question is rarely "is this component secure?" but "what does this component assume about its neighbours, and what happens if the assumption is false?" Almost every breach story you will read in this course's case studies is an assumption that held in the design document and failed in the real world.

Common misconception: "we are too small to be a target"

Most attacks are not aimed at you. They are automated: scanners probe every address on the internet for a known vulnerable version, and credential-stuffing tools try leaked passwords on every login page. Being small makes you less interesting to a determined attacker, but not less reachable by a cheap automated one. Equally, "we are not a bank" ignores that your servers' compute, your users' accounts and your position as a stepping stone to a partner are all assets to someone.

Ethics: test only what you own

This course teaches attacks so that you can recognise and prevent them. Every demonstration runs inside a single Python process, or on localhost, against code written to be vulnerable for that purpose. Running scanners, exploits or password guessers against systems you do not own, or are not explicitly authorised in writing to test, is illegal in most places and harms real people, even when "just looking". Use your own machines, a lab VM, or a deliberately vulnerable practice application running on your own computer. When in doubt, ask the owner first.

Distributed systems connection

A distributed system is a set of machines that must cooperate across a network no one fully controls. Security asks the same question you have asked since chapter 15 of the networking course, "what can I assume about the other party?", but with a stronger answer to give: nothing, unless it is proved. Authenticated channels, signed messages and short-lived credentials are the security-engineering counterparts of acknowledgements, quorums and leases.

Key takeaways

  • Reliability defends against accidents; security defends against someone choosing the worst input at the worst moment.
  • Think in properties: confidentiality, integrity, availability, plus authenticity and accountability. They trade off against one another.
  • Name your assets, your adversaries and your attack surface before choosing controls. Credentials are often the most valuable asset.
  • Security is a property of the whole system: the attacker takes the weakest path, so the question is always what each part assumes about its neighbours.
  • Most attacks are cheap and automated, so "nobody would target us" is not a defence.
  • Test only what you own or are authorised to test.

Check your understanding

A message arrives intact, unmodified and unread by anyone else, but it was actually sent by an impostor. Which property was violated?

  1. Confidentiality
  2. Integrity of the bytes
  3. Authenticity
  4. Availability
The bytes are intact and private, so confidentiality and byte-level integrity hold. What failed is knowing who sent it. This is why integrity checks alone (such as a plain hash) are not enough; you need a key that ties the message to a sender.

Which of these most enlarges the attack surface?

  1. A small endpoint that accepts and parses uploaded files from anonymous users
  2. A large internal library only called by trusted code with fixed arguments
  3. Adding comments to the codebase
  4. Moving a service to a faster server
Attack surface counts places where untrusted input meets code, not lines of code. A tiny parsing endpoint exposed to anyone is a much bigger opportunity than a large library that attackers cannot reach.

You encrypt all traffic with TLS and hash passwords correctly, but staff can be talked into resetting any account over the phone. What does the "weakest link" idea predict?

  1. The strong TLS will protect the accounts anyway
  2. The attack will target the encryption algorithm
  3. Nothing, because the phone is not part of the system
  4. An attacker will use the support process, because it is the cheapest path to the same asset
Attackers choose the cheapest route to the asset. People and processes are part of the system, and a weak recovery path bypasses strong cryptography.

Which statement correctly distinguishes a shared-key MAC from a digital signature?

  1. A MAC encrypts the message; a signature does not
  2. With a MAC either key holder could have produced the tag, so it gives no accountability to a third party; a signature can
  3. A signature needs no key
  4. They are identical in what they prove
With a shared key, the receiver can make valid tags too. Only a private-key signature points to one signer. We return to this in chapter 3.

Why is "we are a small company, nobody would bother attacking us" weak reasoning?

  1. Because small companies always store more data
  2. Because attackers only target small companies
  3. Because many attacks are automated and probe everything reachable, so exposure, not interest, is what matters
  4. Because insurance requires it
Scanners and credential-stuffing tools do not choose targets by size. A reachable, vulnerable service is found cheaply, and your accounts and servers have value as resources or as a path to someone else.

Cloud & Container Security

In the cloud, the network is a configuration, the data centre is an API, and the keys to everything are an identity. This chapter covers who is responsible for what, how cloud identity and access management really works (roles, temporary credentials, wildcards), the dangerous metadata service, why containers are weaker boundaries than people assume, and how Kubernetes handles secrets and permissions.

Why this matters

Cloud breaches rarely involve breaking the provider. They involve a customer-side configuration: a storage bucket readable by anyone, a role with * permissions attached to a web server, an access key committed to a repository, a container running as root with the host's filesystem mounted. Every one of these is a decision made in a template or a console, and each is cheap to get right when you know what to look for. The Capital One case shows several of them chained together.

The shared responsibility model

The cloud provider secures the infrastructure that runs the cloud: buildings, hardware, the hypervisor, the physical network. You secure what you build and configure on top. This split is called the shared responsibility model (every major provider publishes a version). Its precise line depends on the service: with raw virtual machines you patch the operating system; with a managed database the provider patches it, but you still decide who may connect and what is stored; with a SaaS product you mostly manage identities and sharing settings.

Two consequences matter in practice. First, a provider's certifications describe their half, not yours: the data centre being audited says nothing about your bucket policy. Second, identity and data are always yours. The top two rows of the picture, who can do what and what is exposed, are where most customer-side incidents occur, and they are the subject of the rest of this chapter. As a design review question, replace "is it in the cloud?" with "for each layer of this service, who patches it, who configures access, and who notices when it is wrong?"

Cloud IAM in one page

Identity and access management (IAM) is the cloud's authorization system (the general ideas are in chapter 8). The vocabulary below follows AWS, but Google Cloud and Azure have equivalents under different names.

  • A principal is something that can act: a human user, a service account, a workload, another cloud account.
  • A policy is a document stating which actions on which resources are allowed or denied, optionally under conditions (source network, MFA, tags, time). Evaluation is default deny, an explicit deny overrides any allow, and otherwise a matching allow permits. The Python model below implements exactly this.
  • A role is an identity with permissions but no password or long-lived key of its own. Principals do not become a role permanently; they assume it.
  • Assume-role: a principal asks the token service (for AWS, STS) to act as the role. A trust policy on the role says who may ask. If allowed, the service returns temporary credentials that expire (typically minutes to hours), and every API call is evaluated against the role's permissions.

Why prefer this to a long-lived access key in a config file? A stolen long-lived key works until someone notices and revokes it, perhaps months later; temporary credentials die by themselves. Roles also make attribution clearer (the calls are logged as that role, with the session that assumed it) and let you change permissions in one place. Two refinements: conditions in the trust policy (such as an external ID, which prevents a confused deputy when a third party assumes roles in many customers' accounts, see chapter 8), and short session durations for powerful roles.

The listing below is runnable. It parses an AWS-style policy, evaluates requests against a narrow policy and against the lazy "*" policy, and then models temporary credentials with a simulated clock. It is a teaching model of the evaluation logic, not a copy of any provider's engine; real engines also consider the other policy types listed below.

"""A toy cloud-IAM evaluator (illustrative; real providers have more rules). Standard library only."""
import fnmatch, json, secrets, time

POLICY = json.loads("""
{
  "Version": "2012-10-17",
  "Statement": [
    {"Sid": "ReadReports", "Effect": "Allow",
     "Action": ["s3:GetObject", "s3:ListBucket"],
     "Resource": ["arn:aws:s3:::acme-reports", "arn:aws:s3:::acme-reports/*"]},
    {"Sid": "WriteOwnPrefix", "Effect": "Allow", "Action": "s3:PutObject",
     "Resource": "arn:aws:s3:::acme-reports/uploads/*"},
    {"Sid": "NeverTouchKeys", "Effect": "Deny", "Action": "s3:*",
     "Resource": "arn:aws:s3:::acme-reports/keys/*"}
  ]
}""")
BROAD = {"Statement": [{"Effect": "Allow", "Action": "*", "Resource": "*"}]}     # the 'start broad' policy

def listify(x): return x if isinstance(x, list) else [x]
def matches(patterns, value): return any(fnmatch.fnmatchcase(value, p) for p in listify(patterns))

def evaluate(policy, action, resource):
    """Default deny; any matching Deny wins; otherwise a matching Allow permits."""
    allowed = False
    for st in policy["Statement"]:
        if matches(st["Action"], action) and matches(st["Resource"], resource):
            if st["Effect"] == "Deny": return "DENY (explicit)"
            allowed = True
    return "ALLOW" if allowed else "DENY (implicit)"

tests = [("s3:GetObject", "arn:aws:s3:::acme-reports/q3.pdf"),
         ("s3:PutObject", "arn:aws:s3:::acme-reports/uploads/a.csv"),
         ("s3:PutObject", "arn:aws:s3:::acme-reports/q3.pdf"),
         ("s3:GetObject", "arn:aws:s3:::acme-reports/keys/signing.pem"),
         ("s3:DeleteBucket", "arn:aws:s3:::acme-reports"),
         ("iam:CreateUser", "arn:aws:iam::123456789012:user/x")]
print(f"{'action':17} {'resource':44} narrow          broad")
for a, r in tests:
    print(f"{a:17} {r:44} {evaluate(POLICY, a, r):15} {evaluate(BROAD, a, r)}")

# ---------- assume-role: trade a long-lived identity for short-lived credentials ----------
class TokenService:
    def __init__(self, now): self.now, self.issued = now, {}
    def assume_role(self, caller, role, ttl):
        cred = "tmp-" + secrets.token_hex(4)
        self.issued[cred] = (role, self.now() + ttl); return cred
    def validate(self, cred):
        role, exp = self.issued.get(cred, (None, 0))
        return role if role and self.now() < exp else None

clock = [1000.0]
sts = TokenService(lambda: clock[0])
c = sts.assume_role("ci-runner", "deploy-role", ttl=900)
print("\nat t=0      :", "valid, acts as", sts.validate(c))
clock[0] += 899; print("at t=899s   :", "valid, acts as", sts.validate(c))
clock[0] += 2;   print("at t=901s   :", sts.validate(c) or "expired: a stolen copy is now useless")
action            resource                                     narrow          broad
s3:GetObject      arn:aws:s3:::acme-reports/q3.pdf             ALLOW           ALLOW
s3:PutObject      arn:aws:s3:::acme-reports/uploads/a.csv      ALLOW           ALLOW
s3:PutObject      arn:aws:s3:::acme-reports/q3.pdf             DENY (implicit) ALLOW
s3:GetObject      arn:aws:s3:::acme-reports/keys/signing.pem   DENY (explicit) ALLOW
s3:DeleteBucket   arn:aws:s3:::acme-reports                    DENY (implicit) ALLOW
iam:CreateUser    arn:aws:iam::123456789012:user/x             DENY (implicit) ALLOW

at t=0      : valid, acts as deploy-role
at t=899s   : valid, acts as deploy-role
at t=901s   : expired: a stolen copy is now useless

Look at the fourth row: the narrow policy allows s3:GetObject on the bucket, and contains a matching allow through /*, yet the answer is a denial because the explicit deny on keys/* wins. Explicit denies are how you build guardrails that no later allow can undo. The last two rows show what the lazy policy costs: it allows deleting the bucket and creating new users. Anything an attacker can do with the role's credentials is whatever the policy says, so a policy is a statement of your blast radius.

Wildcards, trust policies and boundaries

Where do policies go wrong? Mostly in these ways:

  • Wildcards. "Action": "*", "Resource": "*" and "Principal": "*" each widen the grant. Action wildcards like s3:* include actions that did not exist when you wrote the policy. A wildcard principal in a resource policy means "anyone", which is how buckets and queues become public.
  • Privilege escalation permissions. A role allowed to modify IAM (iam:*), attach policies, or pass a more powerful role to a service can promote itself or a colleague. Treat IAM-writing permissions as administrator permissions.
  • Over-broad trust. A role that "any principal in the account" may assume is only as strong as the weakest identity in the account.

A permission boundary is a ceiling for delegated administration. You attach a boundary policy to a role or user; its effective permissions are then the intersection of what its own policies grant and what the boundary allows. A boundary never grants anything by itself. It lets you give a team the right to create roles for their services while guaranteeing that none of those roles can exceed the ceiling, in this example no IAM or organisation changes. (Organisations also use account-level guardrail policies that apply across many accounts; the idea is the same, a maximum that individual grants cannot exceed. Check your provider's documentation for exactly which policy types participate in a decision.) Two small, valid documents, both illustrative: a trust policy for a role, and a boundary.

  "Version": "2012-10-17",
  "Statement": [

      "Effect": "Allow",

      "Action": "sts:AssumeRole",
      "Condition": { "StringEquals": { "sts:ExternalId": "build-4821" } }
    }
  ]
}

    {
      "Sid": "CeilingForTeamRoles",

      "Resource": "*"

Least privilege: start broad or start narrow?

Everyone agrees on least privilege (chapter 2); the debate is about how to reach it when nobody knows exactly what a service needs.

  • Start narrow, add on denial. Begin with nothing, run the workload, read the access-denied errors, add the specific action. Safe by default, but slow, and a deadline-driven team will paste in a wildcard to make the error go away.
  • Start broad, tighten with evidence. Grant generously in a development account, record what the workload actually calls in the audit logs, then generate or hand-write a policy covering only those actions. Cloud tools exist for this (for example, services that draft a policy from recorded activity and report "last used" times for permissions). Fast, but only safe if the broad phase is confined to a non-production environment and the tightening step is not forgotten; usage logs also miss rare code paths such as annual jobs and incident-only actions.

A pragmatic recipe: use narrow, reviewed templates for production and a time-boxed broad role for exploration in sandboxes; review permissions that have not been used for 90 days; forbid wildcards in production policies by automated check; and give humans no standing production access (the just-in-time approach of chapter 13).

The metadata service

Virtual machines and many container hosts can ask a local, unauthenticated HTTP endpoint about themselves: their name, their network settings and, crucially, the temporary credentials of the role attached to the machine. This instance metadata service lives at a link-local address (169.254.169.254 on the major providers). It exists so that software on the machine needs no stored keys. The danger is that it trusts any request that reaches it from the machine.

That is exactly what a server-side request forgery bug provides (chapter 11): if an attacker can make your application fetch an arbitrary URL, they can make it fetch the metadata address and read back the role's credentials, which the attacker then uses from elsewhere, within the role's permissions and lifetime. The Capital One case is the standard account of this chain. Defences, in layers:

  • Require the hardened metadata protocol. AWS's second version (IMDSv2) requires a session token obtained with a PUT request carrying a custom header, and by default limits how many network hops the response can travel. Simple SSRF primitives that can only issue GET requests, and requests forwarded through proxies, fail. Other providers require a special request header. Turn on the strong mode and disable the old one.
  • Least-privilege roles on the machine, so a stolen credential reaches little (the previous section).
  • Block the address at the application (URL validation, chapter 11), at the network (egress control, chapter 13), and from containers that do not need it.
  • Per-workload identity in place of one role per machine, below.

Workload identity instead of long-lived keys

The worst credential is a static key in a file or an environment variable, because it is copied into images, logs, laptops and tickets, and it never expires on its own. The modern pattern is workload identity federation: the platform gives each workload a short-lived signed token that states who it is, and the cloud's token service exchanges that for temporary cloud credentials according to a trust rule such as "the Kubernetes service account payments-worker in cluster X may assume role Y". It is the OIDC and JWT machinery of chapter 6 and chapter 7 applied to machines. Variants exist for pods (projected service-account tokens exchanged for cloud credentials), CI systems (a build's signed identity token exchanged for a deploy role, so no cloud key is stored in the CI settings) and workloads on other clouds. Benefits: nothing long-lived to leak, per-workload least privilege, and logs that say which workload did what. The trust rule itself is now security-critical: a rule that says "any repository in this organisation" or "any pod in the cluster" is a wildcard in disguise.

Public buckets and exposed data stores

Object storage is the cloud's most commonly misconfigured service because a single setting turns "private" into "readable by the internet". Typical causes: a bucket policy or ACL granting access to everyone, a "temporary" public setting nobody reversed, or a public static-website bucket that also holds backups. Defences, from cheapest: enable the account-wide setting that blocks public access (so an individual mistake cannot override it); deny public principals in organisation-level guardrails; scan continuously for public buckets and open database ports; encrypt with keys the public cannot reach (chapter 4); and when you need to share one object, use a pre-signed URL, a short-lived capability (chapter 8), instead of opening the bucket. The same applies to snapshots, container registries and search clusters bound to 0.0.0.0 without authentication.

Only test what you own or are authorised to test

Cloud-misconfiguration scanners are legitimate for auditing your own accounts and for programmes that permit them. Probing other people's buckets or accounts, even only to "look", is unauthorised access in many jurisdictions. Use your provider's own audit tooling on your own account.

Container security

You met containers in systems chapter 19: processes isolated by kernel namespaces (what they can see) and control groups (how much they can use), all sharing one host kernel. The security work falls into three areas: what goes into the image, how the container is run, and how strong a boundary it is.

The image: provenance and scanning

  • Know where it came from. A tag such as nginx:latest is a movable label; an image digest (@sha256:...) names exact content. Pin digests in production, pull from registries you control, build in a trusted pipeline, and sign images and verify signatures at deploy time (signature tools and build-provenance attestations are discussed in chapter 12).
  • Scan for known vulnerabilities. Scanners compare the packages in an image with databases of published flaws. They find known problems in operating-system packages and libraries; they do not find unknown bugs or flaws in your own code, and they report issues that may not be reachable. Treat results as a prioritised patching list, and rebuild images regularly because a clean image today gains new known flaws tomorrow.
  • Make images small. Fewer packages means a smaller attack surface and less for the scanner to report. Minimal or "distroless" bases and multi-stage builds help. Do not put secrets in image layers; they persist in the layer history.

The runtime: do not hand out power by default

By default a container often runs as root (inside its namespace) with a long list of Linux capabilities and a writable filesystem. Almost no application needs that. The settings below remove it. The manifest is a valid Kubernetes pod specification, illustrative (apply it only to your own test cluster); the digest is a placeholder.

apiVersion: v1
kind: Pod
metadata:
  name: api
  namespace: shop
  labels:
    app: api
spec:
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: api
      image: registry.example.com/shop/api@sha256:abababababababababababababababababababababababababababababababab
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      resources:
        limits:
          cpu: "500m"
          memory: 256Mi
      volumeMounts:
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: tmp
      emptyDir: {}
  • runAsNonRoot and a numeric runAsUser: if the process is hijacked it is not root, even inside the container.
  • readOnlyRootFilesystem with a writable scratch volume: an attacker cannot drop tools or modify the application on disk. (The emptyDir at /tmp gives legitimate scratch space.)
  • capabilities: drop: ["ALL"]: Linux splits root's powers into capabilities (such as binding low ports or loading kernel modules). Drop them all and add back only what is demonstrably needed.
  • allowPrivilegeEscalation: false stops a process gaining more privileges than its parent (for example via setuid binaries).
  • seccompProfile: RuntimeDefault: seccomp filters which system calls a process may make. The runtime's default profile blocks a set of rarely needed and dangerous calls, shrinking the kernel attack surface. AppArmor (and SELinux on other distributions) are mandatory-access-control modules that confine what files and operations a process may touch, by profile. Neither is a boundary on its own; both are cheap layers.
  • automountServiceAccountToken: false: pods get a Kubernetes API credential by default; if the application never calls the API, do not give it one.

Never run privileged: true containers, mount the host's container-runtime socket (it is root on the host), or share the host's PID or network namespace unless the workload is infrastructure that needs it. Kubernetes can enforce a baseline for a whole namespace with its Pod Security Standards (privileged, baseline and restricted profiles), so a developer cannot deploy the dangerous version by accident.

A container is not a strong security boundary

Because every container shares the host kernel, anything that can exploit the kernel from inside, through a kernel bug or a permissive setting, escapes to the host and to its neighbours. The attack surface is the entire system-call interface, which is large. For your own, reviewed code, with the hardening above, containers are a reasonable boundary. For running hostile or unknown code (a customer's uploaded function, a CI job from a stranger, a multi-tenant "run your code" feature), they are not enough, and you should add a stronger layer:

  • gVisor places a user-space "kernel" between the workload and the host: the application's system calls are handled largely by that component, and only a reduced set reaches the real kernel. Compatibility and some performance cost are the price.
  • Firecracker (a minimal virtual machine monitor from AWS, designed for serverless workloads) and Kata Containers (which run each pod in a lightweight VM) give each workload its own guest kernel on hardware virtualization. The boundary becomes the hypervisor, which has a much smaller interface than a kernel. Start-up time and memory overhead are higher than plain containers, though small compared with traditional VMs.
  • A full VM per tenant or separate cloud accounts for the most sensitive tenants is the strongest and most expensive option.

None is perfect: the hypervisor and the user-space kernel have bugs too. The honest summary is that they offer a smaller, better-audited interface to attack than a shared general-purpose kernel. Match the boundary to the threat: how hostile is the code, and what is next door? (Tenant isolation is the subject of chapter 15.)

Kubernetes secrets and RBAC

A Kubernetes Secret object holds small sensitive values (passwords, tokens, keys) that pods can read as files or environment variables. The first thing to know is on the screen below.

"""base64 is an encoding, not encryption. This is what a Kubernetes Secret manifest actually holds."""
import base64, json
manifest = {"apiVersion": "v1", "kind": "Secret", "metadata": {"name": "db-creds"},
            "data": {"password": base64.b64encode(b"s3cr3t-demo-value").decode()}}
print(json.dumps(manifest["data"]))
print("anyone who can read the object recovers it with no key:", base64.b64decode(manifest["data"]["password"]).decode())
{"password": "czNjcjN0LWRlbW8tdmFsdWU="}
anyone who can read the object recovers it with no key: s3cr3t-demo-value

Common misconception: "it is base64, so it is encrypted"

Base64 is a reversible way of writing bytes as text. Anyone who can read the Secret object, through the API, a backup, a Git repository holding the manifest, or a dump of the cluster's datastore, reads the value with no key. Treat a Secret manifest in Git as a plaintext password.

What actually protects Secrets:

  • Encryption at rest. Secrets are stored in the cluster's datastore (etcd). Without an encryption configuration they are written there unencrypted. The API server can encrypt chosen resources before writing, and a key-management-service integration lets the data keys be wrapped by a key held in your KMS, the envelope-encryption pattern of chapter 4. This protects disks and backups, not someone with API access.
  • RBAC. Kubernetes role-based access control decides who may call which API verbs on which resources. Two traps: list and watch on secrets reveal the values just as get does, and anyone who can create a pod in a namespace can mount any Secret in that namespace into it. Grant secret access by name (resourceNames) and to specific service accounts, never * verbs, and avoid binding cluster-admin to workloads. A valid, illustrative example (cluster operations are covered in reliability chapter 14):
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-own-secret
  namespace: shop
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    resourceNames: ["db-creds"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: worker-reads-db-creds
  namespace: shop
subjects:
  - kind: ServiceAccount
    name: payments-worker
    namespace: shop
roleRef:
  kind: Role
  name: read-own-secret
  apiGroup: rbac.authorization.k8s.io
  • External secret stores. Often better: keep the secret in a dedicated manager (a cloud secret service or a vault, chapter 4) with its own audit log, rotation and fine-grained policy, and deliver it to pods at run time through a CSI driver or a sync controller, authenticating with the workload identity above. The cluster then holds a reference or a short-lived copy rather than the source of truth. Prefer mounting as files over environment variables, which leak into crash dumps and child processes.

Analogy: renting a flat in a managed block

The landlord (provider) maintains the building, the lifts and the main entrance. You decide who gets keys to your flat, whether you leave the window open, and what you store. A container is a flat with thin walls: fine for neighbours you know, but you would put a vault in the basement for the really valuable things, which is what a microVM is. A role with temporary credentials is a key code that stops working at checkout time, instead of a physical key you hope to get back.

Where it breaks down: in a building the landlord's responsibilities end at the door. In the cloud the provider's line moves with each service you adopt, so you must read where it falls for every one.

Try it yourself

Run iam_eval.py. Add a statement to the narrow policy that allows s3:* on the bucket and observe which tests change, then add a condition-free explicit deny for s3:DeleteBucket and check that it wins over the wildcard. Implement the permission-boundary intersection: an action is allowed only if both the identity policy and a second boundary policy allow it. If you have a throwaway local cluster, apply the pod manifest and open a shell in it: confirm you cannot write outside /tmp and that id shows a non-root user.

Distributed systems connection

Temporary credentials are leases: they carry an expiry and must be renewed, and the clock-skew and renewal-failure problems of distributed chapter 4 apply (a credential that expires mid-request, a renewal service that is down). IAM policy evaluation is a replicated, read-heavy service with eventual consistency, so a permission change may take time to reach every region. Cloud control planes are themselves a dependency: if your recovery procedure needs a role that only the broken service can assume, plan for it (reliability chapter 18).

Key takeaways

  • Shared responsibility: the provider secures the cloud; you secure your configuration, identities and data. The line moves with the service type, but identity and data are always yours.
  • IAM is default deny with explicit deny winning. Prefer roles and temporary credentials via assume-role over long-lived keys. Treat wildcards, IAM-writing permissions and broad trust policies as red flags; permission boundaries set a ceiling.
  • Reach least privilege by starting narrow, or by starting broad in a sandbox and tightening from audit logs. Never ship the broad phase to production.
  • The metadata service hands out role credentials to anything on the machine, so SSRF can steal them. Use the hardened protocol, narrow roles and egress controls.
  • Use workload identity federation, short-lived tokens exchanged for temporary credentials, instead of stored keys. The trust rule is a policy to review.
  • Block public buckets account-wide, scan for exposure, and use pre-signed URLs for sharing.
  • Containers: pin and sign images, scan them, run non-root with a read-only root filesystem, no capabilities and a seccomp profile. A shared kernel is a weak boundary for hostile code; use gVisor, microVMs (Firecracker, Kata) or VMs for that.
  • Kubernetes Secrets are base64, not encrypted. Enable encryption at rest, scope RBAC tightly (list and pod-create expose secrets), and prefer an external secret store with workload identity.

Check your understanding

A company stores customer files in a managed object store. A bucket is found publicly readable. Whose responsibility is it, in the shared responsibility model?

  1. The provider's, since it runs the storage service
  2. Nobody's; public buckets are a product default
  3. The customer's: access configuration and data are always on the customer's side of the line
  4. The provider's, because it holds a compliance certificate
Providers secure the underlying service. Who is allowed to read your objects is your configuration. Provider certifications describe the provider's half.

An identity policy allows s3:GetObject on bucket/*, and another statement in the same policy denies s3:* on bucket/keys/*. A request reads bucket/keys/k.pem. What happens, and why?

  1. Denied: an explicit deny overrides any allow
  2. Allowed: the more specific allow wins
  3. Allowed: policies are evaluated top to bottom and the first match decides
  4. Denied only if the caller is an administrator
Evaluation collects all matching statements: any explicit deny wins; otherwise an allow is needed; no match means implicit deny. Order and specificity do not matter.

What is the main security advantage of a CI job assuming a role via workload identity federation, compared with a stored access key in the CI settings?

  1. The role has more permissions, so fewer failures
  2. It removes the need for any policy
  3. It encrypts the build logs
  4. There is no long-lived secret to leak, the credentials expire in minutes, and the trust rule can restrict which repository and branch may assume the role
A stored key is valid until revoked and can be copied anywhere. Federated temporary credentials limit both time and who can obtain them, provided the trust rule is itself narrow.

An application has an SSRF bug and runs on a VM with an attached role. What is the classic way this becomes a cloud-account compromise, and what are two defences?

  1. The attacker guesses the database password; rotate it weekly
  2. The attacker makes the server request the metadata endpoint and read the role's temporary credentials; require the hardened metadata protocol and give the role least privilege (also block the address in validation and egress rules)
  3. The attacker intercepts TLS; use longer keys
  4. The attacker reads the source code; obfuscate it
The metadata service trusts any local request, which is exactly what SSRF supplies. The hardened protocol breaks simple SSRF, and narrow roles limit what a stolen credential can do.

Which statement about containers as a security boundary is most accurate?

  1. Containers are as isolated as virtual machines
  2. They share the host kernel, so a kernel exploit from inside escapes; for untrusted code add a stronger sandbox such as gVisor or a microVM
  3. Containers cannot be escaped if they run as root
  4. Only privileged containers share the kernel
All containers share the kernel; privileged mode makes it worse, not the only case. Hardening (non-root, dropped capabilities, seccomp) reduces risk but does not change the shared-kernel fact.

A teammate says a Kubernetes Secret is safe because its value is base64-encoded. What is wrong, and what helps?

  1. Nothing is wrong; base64 is a strong cipher
  2. Base64 is irreversible, so it is too safe and causes outages
  3. Base64 is a reversible encoding; protect Secrets with encryption at rest, tight RBAC (including list and pod-create) and ideally an external secret store
  4. Secrets should be stored in image layers instead
Anyone with read access to the object or datastore decodes the value in one step. Real protection comes from encryption keys held elsewhere and from limiting who can read.

Threat Modeling

You cannot defend against threats you have not imagined. Threat modeling is the habit of drawing your system, marking where trust changes, and asking in a disciplined order what could go wrong and what you will do about it, while changing the design is still cheap. By the end you will model a real feature, upload a profile photo, from first sketch to ranked list of fixes.

Why this matters

Most security flaws that are expensive to fix are design flaws: a service that trusts a header it should not, an internal API with no authorisation, a queue that anyone on the network can write to. Scanners and code review find some of these late, at high cost. A one-hour threat-modeling session on a whiteboard finds many of them before a line of code exists. It is also the shared language that lets a developer, a security engineer and a product manager argue about the same picture.

Four questions

The whole practice fits in four questions. The Threat Modeling Manifesto, written by a group of practitioners that includes Adam Shostack (whose book Threat Modeling: Designing for Security popularised this framing), states them as:

  1. What are we working on? Model the system: components, data flows and trust boundaries.
  2. What can go wrong? Enumerate threats with a structured method such as STRIDE or an attack tree.
  3. What are we going to do about it? For each threat, choose to mitigate, eliminate, transfer or accept it.
  4. Did we do a good enough job? Check the model against reality: tests, review, and revisiting when the design changes.

Note the fourth question. A threat model is a living document of a design that will change, not a certificate. When someone adds a queue between two services, the model is out of date until it is updated.

Throughout, a threat is a potential event that would harm an asset (for example, "an attacker reads another user's photo"); a vulnerability is a weakness that makes a threat possible (no ownership check on the photo id); a mitigation is a control that reduces the chance or the impact; and risk is the combination of how likely a threat is and how bad it would be.

Question 1: draw the system as data flows

The standard picture is a data-flow diagram (DFD). It deliberately ignores classes, servers and frameworks and shows only four kinds of thing:

  • External entity: a person or system outside your control that talks to yours (a browser, a payment provider).
  • Process: code you run that transforms data (an API, an image worker).
  • Data store: anything that holds data at rest (a database, an object store, a queue, a cache, a log file).
  • Data flow: data moving between the others, drawn as an arrow. A flow is a network call, a message or a shared file.

Then comes the step that makes the diagram a security tool: drawing trust boundaries, lines where the level of trust or control changes. The internet-to-service line is the obvious one. Others are less obvious and just as important: between your service and a third-party API; between a web tier and a database tier if they run with different privileges; around a sandbox that runs untrusted code; between one tenant's data and another's; between production and a developer's laptop. Threats concentrate where data crosses a trust boundary, because there the receiver is accepting something from a party it does not fully control.

Analogy: a customs checkpoint

A trust boundary is like a national border. Inside, you apply your own laws; goods arriving from outside are inspected, whatever the sender's paperwork claims. Everything that crosses must be checked, and the checkpoint must not be skipped by a side door.

Where it breaks down: real borders are rarely crossed more than a few times a minute. A web service crosses its trust boundary thousands of times a second, and the "inspector" is your own code, which has to be correct every time.

Question 2: what can go wrong? STRIDE

"Think of everything that could go wrong" is hard to do from a blank page. STRIDE, devised by Loren Kohnfelder and Praerit Garg at Microsoft in 1999, gives a checklist. Each letter is a type of threat, and each is the violation of one security property, which also tells you the family of countermeasures:

LetterThreatProperty violatedTypical mitigations
SSpoofing: pretending to be someone or something elseAuthenticityAuthentication, certificates, mutual TLS, signed tokens
TTampering: modifying data or code without permissionIntegrityMACs and signatures, integrity checks, immutable logs, permissions
RRepudiation: denying an action, with no way to prove otherwiseAccountability / non-repudiationAudit logs, signed records, strong identity
IInformation disclosure: exposing data to those not authorisedConfidentialityEncryption, access control, minimising what is stored and logged
DDenial of service: making the system unavailableAvailabilityRate limits, quotas, timeouts, redundancy, bounded resources
EElevation of privilege: gaining capabilities one should not haveAuthorizationLeast privilege, input validation, sandboxing, authorisation checks

STRIDE is most useful applied per element. Not every threat makes sense for every kind of box. A data store has no identity to spoof, but a process does; an external entity is outside your control, so you cannot tamper with it, but you can be fooled by it. The usual mapping is:

ElementSTRIDE
External entityyesyes
Processyesyesyesyesyesyes
Data storeyes(logs only)yesyes
Data flowyesyesyes

For a diagram with ten elements this yields several dozen candidate threats. Most are dull or already handled, which is the point: a checklist's value is that it makes you look at the dull ones too.

STRIDE is a prompt, not a proof

Going through every cell does not mean you found every threat. STRIDE finds categories at the elements you drew, so a missing element (a forgotten admin tool, a backup job, a third-party script) means a missing analysis. Also, the categories overlap: a stolen session token is spoofing, but using it to read someone's photos is information disclosure, and if the attacker then becomes admin it is elevation. Do not spend meeting time arguing which letter a threat is; write it down once.

Try it: threat-model the photo upload feature

Our worked example is the feature "a logged-in user uploads a profile photo". The flow: the browser sends the image to an upload API; the API hands the bytes to an image worker that decodes, resizes and re-encodes it; the worker writes the result to an object store; and the API records the photo's owner and location in a metadata database. The worker runs in a sandbox because decoding image formats is a classic source of bugs. Below is the DFD. Click any element or flow and read its STRIDE threats and mitigations. Turn on the trust boundaries and notice that the three red flows cross one: those are the ones to examine first. Tick a threat when you would consider it mitigated.

Two observations as you explore. First, the same mitigation recurs: "authorise by the session, not by an id in the request" appears for the API's spoofing, tampering and elevation threats. Good mitigations tend to be few and structural. Second, the interesting threat is not spectacular. The worker decoding an attacker-supplied file is the dramatic one, but the likelier and more damaging one is that the API fails to check who owns the photo being replaced. That is why the next section ranks threats.

Attack trees

STRIDE walks the system. An attack tree, introduced by Bruce Schneier in 1999, walks the attacker's goal. The root is what the attacker wants, children are ways to achieve it, joined by OR (any one is enough) or AND (all are needed), and leaves are concrete steps annotated with cost, difficulty or detectability. The cheapest path to the root is where an attacker will go, so that is where a defender should spend first.

Step through

An attack tree for "read another user's private photo"

  1. The root is the attacker's goal: read a photo that belongs to someone else. We write goals in the attacker's terms and build the tree from the goal downwards.
  2. Four ways to reach it. The branches are joined by OR: the attacker needs only one. Two branches will split further.
  3. Leaves get a rough cost to the attacker. Phishing costs effort, an XSS hole costs more, and the storage-credential branch is an AND: the attacker needs a leaked key and that key must have read access. Cutting either leg closes the branch.
  4. Two branches cost almost nothing: guessing a predictable URL and editing an id in the request. Neither is clever. A defender who fixes these two with random, unguessable names and an ownership check on every request has removed the cheapest routes.

An attack tree is also a good way to record why you decided something: "We accept the phishing branch here because chapter 5's multi-factor authentication and the session-binding in chapter 6 raise its cost; we do not accept the id-editing branch, because it costs nothing."

Adversary models: who are we defending against?

An adversary model (or threat model in the narrow sense) states the attacker's capabilities (what they can see, do and afford) and motivation (what they want). Defences are always relative to one: "secure against a passive eavesdropper" and "secure against an attacker who controls the network" are different promises. Without an explicit model, teams either defend against nothing in particular or promise protection against everyone, which is neither achievable nor affordable.

AdversaryCapabilityMotivationDesign consequence
Opportunistic scanner / botAutomated; known vulnerabilities, default credentials, exposed servicesResources to resell or abuse, quick profitPatch, remove default credentials, expose nothing unneeded. Stops most attacks by volume.
Credential-stuffing criminalLarge lists of passwords leaked elsewhere; botnetsAccount takeover, fraudRate limiting, breached-password checks, multi-factor authentication (chapters 5 and 16).
Curious or malicious insiderLegitimate access, knows the system, can be a customer-support agent or an engineerCuriosity, money, grievanceLeast privilege, audit logs, no standing access to production data.
Malicious user of your productAn ordinary account; can send any input the API acceptsAbuse, reading others' data, free resourcesAuthorisation on every request, input validation, quotas.
Organised, targeted attackerCustom tools, social engineering, patience, supply-chain accessData theft, extortion, espionageDefence in depth, monitoring, rapid detection and response. Prevention alone will not hold.
Nation-state-level actorVery large resources, possibly zero-day vulnerabilities and hardware accessStrategicUsually outside what an ordinary product can prevent; limit the blast radius and detect.

The honest rows are the last two: you state openly that some adversaries are out of scope for prevention. For the photo feature, a reasonable model is "an authenticated malicious user, an opportunistic internet scanner, and a careless insider", which already explains why we put effort into authorisation and the sandbox and not into hardened hardware.

Question 3: rank, then decide

A list of 32 threats is not a plan. A common first filter is to estimate, for each threat, likelihood (how easy and how motivating is it for the adversaries in our model) and impact (how bad for the assets if it succeeds) and multiply: risk = likelihood × impact, on a coarse scale such as 1 to 3 or low/medium/high. It is crude, and deliberately so: the aim is to separate "fix this week" from "write it down and revisit", not to produce a precise number.

DREAD (Damage, Reproducibility, Exploitability, Affected users, Discoverability) was an older Microsoft scheme that scored five factors. It fell out of favour because the scores are subjective and inconsistent between reviewers, and because "discoverability" quietly rewards security by obscurity: it rates a flaw lower because attackers might not find it, which is the assumption you cannot rely on. Prefer a simple likelihood and impact estimate with a written justification, and remember that threats with severe impact deserve attention even if they seem unlikely.

For each threat you then choose a response: mitigate (add a control), eliminate (remove the feature or data that creates it; the best option when you can), transfer (let someone better placed handle it, such as a payment provider holding card numbers, or insurance), or accept (record the decision, the owner and a date to revisit). "Accept" is legitimate; unwritten acceptance is not.

The ranked list for the photo feature

Here is the whole model in code: the elements and the STRIDE-per-element rule produce the candidate threats, and a handful that the team judged most important are ranked. The judgements are examples; a different team might score them differently, which is why the reasons are recorded.

"""Enumerate STRIDE-per-element threats for a data-flow diagram, then rank them."""
from itertools import product

NAMES = dict(S="Spoofing", T="Tampering", R="Repudiation", I="Info disclosure", D="Denial of service", E="Elevation")
PROP = dict(S="authenticity", T="integrity", R="accountability", I="confidentiality", D="availability", E="authorization")

elements = {                       # name: (type, zone)
    "Browser":      ("entity",  "internet"),
    "Upload API":   ("process", "service"),
    "Image worker": ("process", "sandbox"),
    "Blob store":   ("store",   "service"),
    "Metadata DB":  ("store",   "service"),
    "1 upload":     ("flow",    "internet>service"),
    "2 raw bytes":  ("flow",    "service>sandbox"),
    "3 resized":    ("flow",    "sandbox>service"),
    "4 record":     ("flow",    "service"),
}
threats = [(e, c) for e, (t, _) in elements.items() for c in APPLIES[t]]
print("STRIDE-per-element produces", len(threats), "candidate threats for", len(elements), "elements")

# Likelihood and impact on a 1-3 scale, judged by the team (these are example judgements).
judged = {
    ("Upload API", "E"): (2, 3), ("Image worker", "T"): (2, 3), ("Image worker", "D"): (3, 2),
    ("Upload API", "D"): (3, 2), ("Blob store", "I"): (2, 3), ("Browser", "S"): (3, 2),
    ("1 upload", "I"): (1, 3), ("Metadata DB", "T"): (1, 3),
}

The six top-ranked threats all score 6, and they lead directly to design decisions rather than a long list of tasks:

  • Upload API, elevation / tampering with ownership: derive the owner from the session, check ownership on every read and replace. Cheapest to do, highest return.
  • Image worker, tampering (a malicious image exploits the decoder): sandbox with no network and a minimal filesystem; re-encode output; patch the library. This is defence in depth, as chapter 2 explains.
  • Denial of service on API and worker: size and pixel limits, rate limits, a bounded queue, per-job time and memory caps.
  • Blob store disclosure: private by default, signed expiring URLs, random object names.
  • Browser spoofing (stolen session): multi-factor authentication, short-lived sessions and the cookie attributes of chapter 6.

Some of these checks are small enough to write straight away. The function below is the upload API's gatekeeper: it sniffs the content instead of trusting the filename, enforces limits before decoding, and picks its own storage name. It runs on bytes built in the same process.

"""Server-side checks for the upload API, run on bytes built in this process."""
import secrets, struct, zlib

MAX_BYTES = 5 * 1024 * 1024          # hard limit, enforced while streaming in a real server
MAX_PIXELS = 25_000_000              # reject decompression-bomb dimensions BEFORE decoding
PNG_MAGIC = b"\x89PNG\r\n\x1a\n"

def make_png_header(w: int, h: int) -> bytes:
    """Just the signature and IHDR chunk - enough to test the policy, not a viewable image."""
    ihdr = struct.pack(">IIBBBBB", w, h, 8, 2, 0, 0, 0)
    chunk = struct.pack(">I", len(ihdr)) + b"IHDR" + ihdr
    return PNG_MAGIC + chunk + struct.pack(">I", zlib.crc32(b"IHDR" + ihdr))

def validate_upload(filename: str, data: bytes):
    if len(data) > MAX_BYTES:
        return None, "too large"
    if not data.startswith(PNG_MAGIC):                  # sniff content; ignore the client's filename and type
        return None, "not a PNG by content"
    w, h = struct.unpack(">II", data[16:24])
    if w * h > MAX_PIXELS:
        return None, f"{w}x{h} pixels exceeds limit"
    return secrets.token_hex(16) + ".png", "ok"         # server-chosen name: no traversal, no overwrite

cases = {
    "normal photo":             ("me.png", make_png_header(1600, 1200)),
    "renamed script":           ("cat.png", b"#!/bin/sh\necho not an image\n"),
    "path in filename":         ("../../etc/passwd.png", make_png_header(100, 100)),
    "huge dimensions (bomb)":   ("big.png", make_png_header(60000, 60000)),
    "oversize body":            ("x.png", PNG_MAGIC + b"\0" * (MAX_BYTES + 1)),
}
for label, (name, data) in cases.items():
    stored, why = validate_upload(name, data)
    shown = "(rejected)" if stored is None else "stored as <32 hex chars>.png"
    print(f"{label:<24} -> {why:<28} {shown}")
normal photo             -> ok                           stored as <32 hex chars>.png
renamed script           -> not a PNG by content         (rejected)
path in filename         -> ok                           stored as <32 hex chars>.png
huge dimensions (bomb)   -> 60000x60000 pixels exceeds limit (rejected)
oversize body            -> too large                    (rejected)

Notice what the filename check does not do: "path in filename" is accepted, because the client's filename is never used for storage. This is the better design than trying to filter out dangerous characters, and it recurs throughout the course (chapter 9: do not clean untrusted input, avoid letting it be interpreted at all).

Validation is not the whole mitigation

This gatekeeper checks the header: it confirms the file claims to be a PNG with sane dimensions. It does not prove the rest of the file is a valid image, which is why the worker still decodes in a sandbox. A control that handles the common case does not remove the need for the control that handles the failure of the first. That is defence in depth.

Question 4: did we do a good enough job?

The answer must be checkable. Turn each accepted mitigation into something you can verify:

  • Abuse-case tests. Alongside "a user can upload a photo", write "user A cannot replace user B's photo" and "a 60000x60000 image is rejected". Failing tests are the cheapest security regression alarm.
  • Review. Someone who did not draw the diagram reads it and asks what is missing. Fresh eyes find forgotten elements, which is the most common gap.
  • Traceability. Each threat in the model points to a control, a test or a recorded acceptance. Unlinked threats are open.
  • Revisit on change. New component, new data type, new trust boundary: the model is out of date until updated. Make it part of the design-review checklist (chapter 19).

Try it yourself

Pick a feature you have built, such as password reset by email. On paper: (1) draw the DFD with at least one external entity, two processes and one store; (2) mark every trust boundary (is the email system inside yours?); (3) apply STRIDE-per-element to each flow that crosses a boundary; (4) pick the top three by likelihood and impact and write one mitigation each. If you do this for password reset, you will likely rediscover that predictable reset tokens and links that never expire are the main risk. Do this only for systems you own.

Distributed systems connection

A DFD is a distributed system's architecture diagram with one extra layer of meaning: who controls each box. Compare it to the failure-model discussion of distributed chapter 12. A crash-fault model draws no trust boundary inside the cluster because it assumes every node follows the protocol. A security threat model asks which nodes might not, and puts boundaries around them. The same picture, with different assumptions, gives different designs.

Key takeaways

  • Threat modeling is four questions: what are we working on, what can go wrong, what will we do about it, did we do a good enough job.
  • Draw data flows and mark trust boundaries; start with the flows that cross them.
  • STRIDE is a checklist where each letter violates one property: authenticity, integrity, accountability, confidentiality, availability, authorization. Apply it per element type.
  • Attack trees start from the attacker's goal; the cheapest path shows where to spend first.
  • State the adversary model, including who you are not defending against.
  • Rank by likelihood × impact with written reasons; decide to mitigate, eliminate, transfer or accept, and write the decision down. DREAD's scores are too subjective to trust.
  • Make the result verifiable with abuse-case tests, and update the model when the design changes.

Check your understanding

In a data-flow diagram, why do you mark trust boundaries?

  1. To show which servers are physically in the same rack
  2. Because data crossing a boundary comes from a party you do not fully control, so that is where threats concentrate and checks are needed
  3. To decide which programming language to use
  4. To show which team owns each component
Trust boundaries mark where the level of control or trust changes. The receiver of a flow that crosses one must validate and authenticate what arrives. Physical location and team ownership may correlate with boundaries but are not the point.

An attacker replays a captured request with a changed account number and the server processes it without any check that it came from the account owner. Which STRIDE category fits best, and which property is violated?

  1. Denial of service, availability
  2. Repudiation, accountability
  3. Information disclosure, confidentiality
  4. Spoofing or elevation of privilege, authenticity or authorization
The server accepted an action as if from the owner when it was not; that is spoofing (no proof of identity) and, as the attacker now acts beyond their rights, elevation of privilege. Categories overlap; naming one clearly and moving on is fine.

Which element types does STRIDE-per-element say can suffer spoofing?

  1. External entities and processes
  2. Data stores and data flows
  3. Only data stores
  4. Only data flows
Spoofing is about identity: an external entity can be impersonated, and a process can be impersonated by something else. Data stores and flows carry no identity to forge; the threat to a flow is tampering, disclosure or denial of service.

An attack tree shows a branch "guess a sequential photo id" costing almost nothing and a branch "exploit an image-decoder bug" costing a great deal. What should you fix first, and why?

  1. The decoder bug, because it sounds more dangerous
  2. Neither, because both are unlikely
  3. The guessable ids, because the cheapest path is the one attackers will take; then add the sandbox as defence in depth
  4. Whichever is easier for your team to code
Attackers go for the cheapest route to the goal. A dramatic but expensive attack is usually less likely than a trivial one. The sandbox is still worth having, because high-impact threats deserve a control even when unlikely.

What is the main criticism of DREAD scoring?

  1. It takes too long to compute
  2. Its factors are subjective, so scores vary between reviewers, and "discoverability" rewards security by obscurity
  3. It cannot be used with attack trees
  4. It is only for hardware
Different people rate the same flaw differently, and lowering a score because attackers might not find the flaw relies on obscurity. A coarse likelihood × impact estimate with written reasons is easier to defend and to revisit.

The team decides not to fix a low-likelihood threat this quarter. What makes that a sound security decision rather than neglect?

  1. Telling nobody, so nobody worries
  2. Removing the threat from the model
  3. Recording it as an accepted risk with a reason, an owner and a date to revisit
  4. Marking its likelihood as zero
Acceptance is a legitimate response, but it must be explicit and revisitable. Silent acceptance is indistinguishable from an oversight.

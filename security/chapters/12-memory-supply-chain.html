Memory Safety & the Supply Chain

Two very different ways to be compromised through code you did not intend to run. In the first, a bug in a program lets input overwrite memory the program never meant to expose. In the second, the program is fine, but something it depends on, builds with or ships through was not. This chapter draws the memory problem in one picture, explains the mitigations and why memory-safe languages matter, then covers the dependency, build and patching practices that decide whether you hear about the next incident from your own inventory or from the news.

Why this matters

Most of the software you ship is code you did not write: libraries, runtimes, containers, build tools. A typical service has far more transitive dependencies than direct ones, and each is a place where a memory bug, a malicious update or an unpatched flaw can reach production. You cannot audit all of it. You can, however, control what you accept (pinning, verification), know what you have (inventory), and move quickly when something is announced (patching). Those are engineering practices, not heroics.

Memory safety in one picture

You met the stack in systems chapter 3: each function call gets a stack frame holding its local variables, plus the return address that says where execution continues when the function finishes. In languages like C and C++ the programmer manages buffer sizes by hand, and nothing in the language stops a copy from writing past the end of an array. Memory safety means a program cannot read or write memory outside the objects it legitimately owns. A buffer overflow is a violation of that rule, and on the stack it has a famous consequence: the overflow runs toward the saved return address.

Step through

A stack buffer overflow, and the canary

  1. A function copies input into a local buffer. When the input is shorter than the buffer, everything works. Note which way memory grows: the buffer is at a lower address than the saved return address, and writes run upward.
  2. The copy routine trusts the input's length. Extra bytes overwrite neighbouring data and finally the return address. When the function returns, the CPU loads that value, so whoever controls the input controls where execution goes. (We keep this a model: the toy program below simulates the memory in a Python bytearray.)
  3. A stack canary is a secret value the compiler places before the return address and verifies before returning. A linear overflow cannot reach the return address without changing it, so the check fails and the process terminates: a crash instead of a hijack.

The picture is a model

Real exploitation is harder than the cartoon: defences below make it so. But "harder" is not "impossible", and the cleanest way to stop depending on those defences is to remove the class of bug. Everything here is shown as a simulation in one safe Python process, with no real memory or program being attacked.

Heartbleed-style over-reads

Not all memory bugs write. A buffer over-read reads past the end of a buffer and returns what happens to be nearby. In Heartbleed (2014), the TLS heartbeat feature let a client send a small payload together with a claimed length; the server echoed back that many bytes without checking the claim against the real payload size, so an attacker could ask for up to tens of kilobytes of adjacent process memory per request, which could contain keys, passwords and session data. Nothing was "executed"; confidentiality was lost through a missing bounds check. The Heartbleed case study tells the full story. This also matters for mitigations: an over-read is exactly the information leak that defeats canaries and address randomisation.

"""A TOY memory model: one bytearray standing in for a stack frame, and a heartbleed-style over-read.
No real memory is touched; Python itself is memory safe. Lengths are checked or not by OUR code."""
import struct

# --- stack frame: [ buf: 8 bytes ][ saved return address: 4 bytes ] ---
SAFE_ADDR, EVIL_ADDR = 0x0804_9000, 0xDEAD_BEEF
def make_frame():
    f = bytearray(12); f[8:12] = struct.pack("<I", SAFE_ADDR); return f

def strcpy_like(frame, data: bytes):            # no bounds check: copies as much as it is given
    frame[0:len(data)] = data[:len(frame)]      # (clamped only so the toy frame itself does not grow)
def bounded_copy(frame, data: bytes):
    if len(data) > 8: raise ValueError("input too long for 8-byte buffer")
    frame[0:len(data)] = data

def ret_addr(frame): return struct.unpack("<I", frame[8:12])[0]

f = make_frame(); strcpy_like(f, b"hello"); print("short input   -> return address", hex(ret_addr(f)))
f = make_frame(); strcpy_like(f, b"A" * 8 + struct.pack("<I", EVIL_ADDR))
print("12-byte input -> return address", hex(ret_addr(f)), "(attacker chose where the function 'returns')")
f = make_frame()
try: bounded_copy(f, b"A" * 12)
except ValueError as e: print("bounded copy -> rejected:", e)

# --- heartbleed-style over-read: echo back `claimed_len` bytes of a payload that is shorter ---
heap = bytearray(b"PING" + b"\x00" * 4 + b"user=admin;password=hunter2;session=9f3a...;")
def heartbeat_vulnerable(payload_len_actual, claimed_len):
    return bytes(heap[8:8 + claimed_len])           # trusts the claimed length; adjacent data leaks
def heartbeat_fixed(payload_len_actual, claimed_len):
    if claimed_len > payload_len_actual: raise ValueError("claimed length exceeds payload")
    return bytes(heap[8:8 + claimed_len])
print("\nvulnerable echo:", heartbeat_vulnerable(4, 40))
try: heartbeat_fixed(4, 40)
except ValueError as e: print("fixed echo     :", e)

Mitigations, and what they leave open

MitigationWhat it doesWhat it does not do
Stack canariesDetect a linear overwrite of the return address before it is used.Do not stop info leaks, non-contiguous writes or heap bugs.
NX / DEP (non-executable memory)Mark stack and heap pages as data-only, so injected bytes cannot be run as code.Attackers reuse code that is already present and executable (return-oriented programming), so no injected code is needed.
ASLR (address space layout randomisation)Place stack, heap and libraries at random addresses each run, so the attacker must guess where useful code lives.A single leaked pointer (an over-read) reveals the layout; on small address spaces the guess may be feasible.
Bounds-checked libraries, hardening flags, sanitizers, fuzzingCatch many bugs in testing and shrink the exploitable ones.Coverage is never complete.

The mitigations raise the cost of exploiting each bug and force attackers to chain several; they do not remove bugs. This is defence in depth working as intended (chapter 2), and also why the industry has increasingly argued for removing the underlying class.

Memory-safe languages

In a memory-safe language (Python, Java, Go, C#, Swift, Rust and many others) the language or its runtime enforces bounds and lifetimes: out-of-range access raises an error or is prevented at compile time, and use-after-free cannot occur in safe code. Rust is notable because it provides this without a garbage collector, using an ownership and borrowing discipline checked at compile time. Safe languages still offer escape hatches (unsafe blocks, foreign-function interfaces, native extensions), so the unsafe surface shrinks and becomes auditable, not zero.

Government and industry guidance has moved toward recommending them. In November 2022 the NSA published a cybersecurity information sheet on software memory safety, and in December 2023 CISA and the NSA, with the FBI and partner agencies from Australia, Canada, New Zealand and the UK, released The Case for Memory Safe Roadmaps (CISA), asking software manufacturers to publish plans for reducing memory-safety vulnerabilities, including by moving to memory-safe languages. The argument is qualitative but consistent: organisations that have analysed their own vulnerability data have reported that memory-safety bugs account for a large share of serious flaws, and removing the class is more reliable than finding each instance.

Keep the claim in proportion. Memory safety does not fix injection (chapter 9), broken authorisation (chapter 8), SSRF or a compromised dependency; it removes one major category. Rewriting large existing C or C++ codebases is expensive, so practical strategy is incremental: write new components in a safe language, isolate and sandbox legacy parsers (the code that handles untrusted file and network formats is the best place to start), and keep hardening the rest.

The supply chain

A software supply chain is everything that goes into producing and delivering your software: source code, dependencies, build tools, CI systems, package registries and the deployment path. A supply chain attack compromises one of those links so that malicious code arrives through a channel you already trust. The figure shows where attacks enter and which control closes each door.

Dependencies and transitive risk

A direct dependency is a package you name; a transitive dependency is one pulled in by something you depend on, possibly several layers down. You are responsible for all of them: their bugs are your bugs, and their maintainers' account security is part of your security. Practical habits: depend on fewer, better-maintained packages; ask whether a ten-line function justifies a new dependency; and remember that installing a package can itself run code (install scripts, build hooks) before you ever import it.

Typosquatting and dependency confusion

Typosquatting publishes a malicious package under a name one keystroke away from a popular one (reqeusts), betting on a mistyped install command. Dependency confusion targets organisations with private packages: if your internal package acme-billing is requested from a setup that also consults a public registry, and an attacker publishes a public package with that name and a higher version number, a naïve resolver may prefer the public one. Defences: scope internal packages to your own registry (or reserve the names publicly), configure resolvers to take each package from one specified source, and review newly added dependency names.

Lockfiles and hash pinning

A lockfile records the exact resolved version of every direct and transitive dependency so that builds are repeatable, and updates become reviewed changes rather than whatever the registry served today. Hash pinning goes further: it records a cryptographic digest of each artifact, so even if someone replaces a file on a mirror under an unchanged version number, the download is refused. With pip this is pip install --require-hashes -r requirements.txt, where every requirement is pinned to an exact version and carries one or more --hash=sha256:... values (tools such as pip-compile --generate-hashes produce the file). The sketch below models what that check does, together with a typosquat screen.

"""Hash pinning and a typosquat check, all in memory. Package names are invented."""
import hashlib, difflib

# What 'pip install --require-hashes' does in spirit: refuse any artifact whose digest is not pinned.
good_wheel = b"pretend this is the real requests-2.0.0 wheel"
LOCK = {"requests-2.0.0.whl": hashlib.sha256(good_wheel).hexdigest()}      # recorded when you reviewed it

def install(name: str, blob: bytes) -> str:
    want = LOCK.get(name)
    if want is None:                       return f"REFUSED {name}: not in lockfile"
    if hashlib.sha256(blob).hexdigest() != want: return f"REFUSED {name}: hash mismatch"
    return f"installed {name}"
print(install("requests-2.0.0.whl", good_wheel))
print(install("requests-2.0.0.whl", good_wheel + b" + backdoor"))      # tampered on the mirror
print(install("reqeusts-2.0.0.whl", good_wheel))                      # typo'd name

# Typosquat screening: flag new dependency names that are close to, but not equal to, popular ones.
POPULAR = ["requests", "numpy", "pandas", "cryptography", "urllib3", "django"]
def suspicious(name: str, cutoff=0.85):
    return [p for p in POPULAR if name != p and difflib.SequenceMatcher(None, name, p).ratio() >= cutoff]
for n in ["requests", "reqeusts", "numpyy", "urllib", "left-pad"]:
    print(f"{n:10} close to {suspicious(n)}")

# Pinned vs floating: what a version range lets in.
def satisfies_caret(version: str, floor: str) -> bool:
    v, f = [tuple(map(int, x.split("."))) for x in (version, floor)]
    return v >= f and v[0] == f[0]
print("floating '^1.2.0' accepts 1.9.9:", satisfies_caret("1.9.9", "1.2.0"), "  (and whatever is published tomorrow)")

urllib     close to ['urllib3']

Hash pinning proves "this is the artifact I reviewed", not "this artifact is safe": if the version you pinned was itself malicious, the hash faithfully verifies it. Pair pinning with a deliberate update process (automated pull requests from tools that propose bumps, reviewed and tested) so you neither freeze forever on vulnerable versions nor float onto unreviewed ones.

SBOMs

A software bill of materials (SBOM) is a machine-readable inventory of the components in a piece of software: names, versions, suppliers, hashes and how they relate. The two widely used formats are SPDX (from the Linux Foundation) and CycloneDX (from OWASP). Its value shows on the day a vulnerability is announced: instead of asking every team "do you use this library?", you query an index and get an answer in minutes. Its limits matter too: an SBOM is an inventory, not an assurance; accuracy varies by tooling (especially for vendored code and statically linked binaries); and an inventory entry says nothing about whether the vulnerable function is reachable. A companion idea, VEX (Vulnerability Exploitability eXchange), lets a supplier state that a listed vulnerability does not affect a particular product.

Provenance, SLSA and signing

Provenance is a verifiable record of how an artifact was produced: which source, which builder, which inputs. SLSA ("salsa", Supply-chain Levels for Software Artifacts, from the OpenSSF) is a framework that grades how much you can trust a build. In version 1.0 of the specification the Build track has levels (slsa.dev): Build L0 means no guarantees; L1 means the build follows a consistent process and produces provenance describing it (which may be unsigned or incomplete); L2 means the build runs on a hosted build service that signs the provenance, and consumers verify that signature; L3 adds that the build platform isolates runs from one another and keeps the signing secrets out of reach of the project's own build steps. In effect the levels move trust from "the developer says so" to "the platform attests, and a tampered build step cannot forge it". The specification has since moved on (version 1.2 is marked current on slsa.dev at the time of this review, and v1.0 is retired), so check the current text before citing a level in a policy.

Provenance is only meaningful if you can verify who signed. Sigstore is an open project for signing and verifying software artifacts. Its "keyless" mode avoids long-lived signing keys (the hard secret-management problem of chapter 4): the signer authenticates with an OpenID Connect identity (chapter 7), a certificate authority issues a short-lived certificate binding a fresh key to that identity, the artifact is signed, and the signature and certificate are recorded in a public, append-only transparency log so that later misuse is detectable. Verification then asks a precise question: was this signed by this specific identity (for example, this repository's release workflow) as attested by this specific issuer? A signature check that accepts any valid signature proves nothing.

Reproducible builds

A build is reproducible if building the same source with the same inputs always gives bit-for-bit identical output. That allows independent parties to rebuild and compare, turning "trust the builder" into "check the builder". It catches compromised build machines and, notably, gaps between what is in the repository and what is in the shipped release archive, which is the kind of discrepancy at the centre of the xz incident below. It is hard in practice (timestamps, file ordering, absolute paths all leak into outputs), so teams adopt it selectively for the highest-value artifacts.

CI secrets and the build system as a target

Your CI system holds deploy keys, registry tokens and cloud credentials, and executes code from pull requests, which makes it a prime target. Habits that matter: never expose secrets to builds triggered by untrusted forks; prefer short-lived credentials obtained by federating the CI run's identity with the cloud (OIDC) over stored long-lived keys; give each job only the permissions it needs; pin third-party actions and plugins by an immutable commit hash, not a movable tag; keep logs free of secrets; and separate "build" from "deploy" so a compromised test step cannot publish. These are least-privilege (chapter 2) and secret-handling (chapter 4) applied to automation.

Maintainer compromise

Sometimes the attacker is not outside the project at all. A maintainer's account can be taken over; a burned-out sole maintainer can hand over control to a helpful newcomer; a long-patient contributor can earn trust before introducing something hostile. The xz backdoor case study describes the last pattern: years of social engineering, a payload hidden in the build process, and discovery by a developer who noticed a small unexplained slowdown. The lessons are not "never use open source". They are: reduce the number of components that run with high privilege; require review and multiple maintainers for critical code; compare release artifacts with source; and keep detection and response ready (chapter 18).

Patch management and vulnerability inventories

Most intrusions use vulnerabilities for which a fix exists. Managing that gap is an inventory and prioritisation problem. The vocabulary:

  • CVE (Common Vulnerabilities and Exposures): a standard identifier, such as CVE-2021-44228, for one publicly disclosed vulnerability. It names the flaw; it does not rate it.
  • CVSS (Common Vulnerability Scoring System, maintained by FIRST): a 0 to 10 severity score computed from intrinsic characteristics such as attack vector, complexity, required privileges and impact. It is a measure of how bad the flaw can be in general, not of risk to your system, which depends on exposure and what the component protects.
  • KEV (Known Exploited Vulnerabilities): CISA's catalogue of vulnerabilities with evidence of exploitation in the wild. "Being exploited now" is a far stronger signal than a high score; US federal agencies are directed to remediate catalogued items by set deadlines, and the list is useful to everyone as a prioritisation input. A related signal is FIRST's EPSS, an estimate of the probability a vulnerability will be exploited.

A workable prioritisation weighs, roughly in this order: is it known to be exploited; is the affected component reachable from the internet or an untrusted network; what does the component protect; and only then the base score. You can only do this if you have an inventory, which is why the SBOM matters. The script below queries a small CycloneDX-style inventory against a made-up advisory list, using invented identifiers and package names, and orders the findings by those rules.

"""Query a tiny CycloneDX-style SBOM against an advisory list and prioritise. IDs and packages are INVENTED."""
import json

sbom = json.loads("""{
  "bomFormat": "CycloneDX", "specVersion": "1.5",
  "components": [
    {"name": "webframe", "version": "2.3.1", "purl": "pkg:pypi/webframe@2.3.1", "scope": "internet-facing"},
    {"name": "logkit",   "version": "1.4.0", "purl": "pkg:pypi/logkit@1.4.0",   "scope": "internet-facing"},
    {"name": "pdfmaker", "version": "0.9.2", "purl": "pkg:pypi/pdfmaker@0.9.2", "scope": "internal-batch"},
    {"name": "yamlish",  "version": "5.4.0", "purl": "pkg:pypi/yamlish@5.4.0",  "scope": "internal-batch"}
  ]}""")

# (id, package, first_fixed_version, CVSS base score, in a known-exploited catalogue?)
advisories = [
    ("CVE-0000-0001", "webframe", (2, 3, 5), 9.8, True),
    ("CVE-0000-0002", "logkit",   (1, 5, 0), 9.0, False),
    ("CVE-0000-0003", "pdfmaker", (1, 0, 0), 7.5, False),
    ("CVE-0000-0004", "yamlish",  (5, 4, 0), 9.9, False),     # already fixed in 5.4.0: not affected
]
def v(s): return tuple(int(x) for x in s.split("."))

hits = []
for a_id, pkg, fixed, cvss, kev in advisories:
    for c in sbom["components"]:
        if c["name"] == pkg and v(c["version"]) < fixed:
            exposed = c["scope"] == "internet-facing"
            # A simple, explainable ordering: known-exploited first, then exposure, then CVSS.
            hits.append((not kev, not exposed, -cvss, a_id, pkg, c["version"], cvss, kev, c["scope"]))
print(f"{len(sbom['components'])} components, {len(advisories)} advisories, {len(hits)} affected\n")
for h in sorted(hits):
    print(f"P{sorted(hits).index(h)+1}  {h[3]}  {h[4]}@{h[5]:6}  CVSS {h[6]}  exploited={h[7]!s:5} {h[8]}")

P3  CVE-0000-0003  pdfmaker@0.9.2   CVSS 7.5  exploited=False internal-batch

Process matters as much as tooling: assign an owner for every component, set remediation timelines by priority (hours for exploited and exposed, days or weeks otherwise), automate dependency update proposals, rehearse an emergency rollout, and track the things that cannot be patched quickly with compensating controls such as network restrictions or a web application firewall rule. The cautionary tale is the Equifax case study: a fix existed for an exploited web-framework flaw, and the failure was in knowing where the vulnerable component ran and getting the update applied, followed by weaknesses in detection. The lesson is organisational: inventory and ownership, not a missing clever technique. Incident response for the day patching fails is in reliability chapter 16.

Go deeper (optional): why "just pin versions" and "just update everything" are both wrong

Pinning protects against surprise; it also stops you receiving security fixes. Floating protects against stale code; it also lets a malicious release land unreviewed. The robust middle is pin exactly, update on a schedule through reviewed automated pull requests, apply a short cooling period before adopting brand-new releases for non-urgent updates, and fast-track patches for exploited vulnerabilities. For critical dependencies, mirror them in an internal registry so a deletion or takeover upstream cannot break or poison your builds.

Distributed systems connection

A fleet is a version-skew problem: during any rollout, some nodes run old code and some new, and a patch is only effective when the last vulnerable replica is gone. Patch pipelines therefore need the same discipline as other deployments: canaries, health checks and fast rollback (reliability chapter 14), and a way to find forgotten instances, which is exactly the inventory problem. Memory-safe components also change reliability: an out-of-bounds access becomes a clean error instead of silent corruption that propagates between nodes.

Key takeaways

  • A stack buffer overflow overwrites the saved return address; an over-read (Heartbleed) leaks adjacent memory. Both come from missing bounds checks.
  • Canaries, NX and ASLR raise the cost of exploitation but are bypassable, especially with an info leak. Memory-safe languages remove the bug class; CISA and NSA guidance recommends memory-safe roadmaps. They do not fix logic, injection or supply-chain flaws.
  • You are responsible for transitive dependencies. Watch for typosquatting and dependency confusion; take internal packages from one source.
  • Use lockfiles and hash pinning (pip install --require-hashes) for repeatable, tamper-evident installs, plus a reviewed update process.
  • SBOMs (SPDX, CycloneDX) are inventories that let you answer "are we affected?" quickly; they are not proof of safety.
  • SLSA Build levels (v1.0) grade provenance from none (L0) through consistent provenance (L1), signed hosted-build provenance (L2) to isolated, tamper-resistant builds (L3). Sigstore signing is meaningful only if you verify the expected identity.
  • Treat CI as a high-value target: short-lived credentials, least privilege, pinned third-party steps, no secrets for untrusted code.
  • Prioritise patches by KEV status and exposure before CVSS; the Equifax lesson is inventory and ownership.

Check your understanding

What does a stack canary protect against, and what is a limitation?

  1. It encrypts the stack; the limitation is speed
  2. It stops all memory bugs; there is no limitation
  3. It detects a linear overwrite of the return address before use; an information leak can reveal it, and it does not cover heap or non-contiguous writes
  4. It randomises library addresses; the limitation is memory use
The canary is a value checked before the function returns, so a contiguous overflow that reaches the return address changes it and aborts the program. Randomising addresses is ASLR, a different mitigation.

Why is a Heartbleed-style over-read especially damaging to the mitigations?

  1. It leaks memory contents such as keys, canaries and pointers, which can defeat secrecy-based defences like ASLR
  2. It makes NX stop working
  3. It deletes the stack
  4. It only affects hardware
Over-reads give the attacker information rather than control, but several mitigations depend on values staying secret. A leaked pointer reveals the layout; a leaked canary can be written back correctly.

What does pip install --require-hashes add over pinning a version number?

  1. It makes the package open source
  2. It updates packages automatically
  3. It checks the package for vulnerabilities
  4. It refuses any downloaded file whose digest is not the one recorded, so a replaced artifact under the same version is rejected
A version number is a label that someone with registry or mirror access may be able to reuse. A digest identifies the exact bytes you reviewed. It does not vouch that those bytes were benign.

Which statement about CVSS is most accurate?

  1. It measures how likely your organisation is to be attacked
  2. It rates the general severity of a vulnerability; your actual priority also depends on exploitation evidence (such as KEV), exposure and asset value
  3. It lists vulnerabilities currently exploited in the wild
  4. It is a patch deadline set by law
CVSS is an intrinsic severity score. KEV is the exploited-in-the-wild catalogue. A medium score on an internet-facing, exploited component can outrank a critical score on an isolated, unreachable one.

A release is signed with Sigstore and the signature verifies. What additional check makes the verification meaningful?

  1. Checking that the file name looks right
  2. Nothing; any valid signature is enough
  3. Checking that the signing certificate's identity and issuer match the specific workflow or person you expect to publish this artifact
  4. Checking that the signature is longer than 64 bytes
Anyone can obtain a valid signature under their own identity. The security comes from binding the artifact to the expected identity and recording the signature in a transparency log.

Your company discovers it cannot quickly say which services contain a newly announced vulnerable library. Which practice addresses the root problem?

  1. Turning off vulnerability announcements
  2. Maintaining a component inventory (for example, generating SBOMs at build time) with named owners, so you can query and act
  3. Using only memory-safe languages
  4. Rotating all passwords
You cannot patch what you cannot find. Inventory and ownership are the foundation of timely patching, which is the central lesson of incidents like Equifax. Memory safety does not help with a known vulnerable library already deployed.

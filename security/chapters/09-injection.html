Injection & Untrusted Input

SQL injection, command injection, path traversal, unsafe deserialization and Log4Shell look like five different bugs. They are one bug: a program builds a string out of code and data, hands it to an interpreter, and the interpreter cannot tell which part was which. This chapter shows that bug in running Python, fixes each instance, and explains why the fixes that look sensible (escaping, blocklists) are the ones that fail.

Why this matters

Injection is the longest-running family of serious application vulnerabilities, and it remains easy to write by accident because the vulnerable code works on every normal input. The defences are cheap and well understood, so the skill is mostly recognition: seeing, in a code review or a design doc, every place where untrusted text flows into something that interprets it. Once you can name the interpreter (SQL engine, shell, filesystem, template engine, deserializer, log pipeline), you know the fix.

Only attack what you own

Every demonstration here runs inside one Python process against a throwaway in-memory database, a temporary directory or the harmless echo command. Do not point these techniques at systems you do not own or are not explicitly authorised to test. The aim is to recognise and prevent, not to break in.

The root cause: code and data in one string

An interpreter here means any component that reads a string and treats parts of it as instructions: a SQL engine, a shell, an HTML parser, a template engine, a path resolver (which treats .. as an instruction), a deserializer that instantiates classes named in the input. An injection flaw occurs when the attacker supplies data that the interpreter parses as instructions, because the program concatenated it into the same string as its own instructions. The data crossed a trust boundary (from the attacker's world into your program) and was never kept distinct from code afterwards.

Analogy: the fill-in-the-blank form

A clerk is told to process any form that says "Pay to the order of ____". A customer writes in the blank: "nobody, and also transfer the balance of account 7 to me". The clerk reads the whole line, as the clerk always does, and complies. The form was designed so that the blank holds a name, but nothing in the clerk's procedure distinguishes the blank from the printed text.

Where it breaks down: a human clerk might notice the oddity. A parser has no common sense; it applies its grammar mechanically to whatever string it receives, so the only reliable defence is to never give it a string in which data can masquerade as grammar.

Let the figure below carry the idea. Step through what the SQL parser sees for a benign input, a hostile input and a parameterised query.

Step through

What the SQL parser sees

  1. The vulnerable pattern. The developer writes constant SQL (blue) and splices a user value (green, from across the trust boundary) into the middle of one string.
  2. With bob everything works: the quotes the developer added surround the value, and the parser reads it as a string literal.
  3. With x' OR '1'='1 the value contains its own quote. The literal ends early, OR becomes an operator, and the attacker has edited the query. Nothing was "hacked" in the parser; it parsed exactly what it was given.
  4. The fix. The query text is sent to the database on its own, with a placeholder. The value is bound later as a literal. Because the database has already parsed the structure, no value, however strange, can add an operator.

SQL injection, running

The script below builds an in-memory SQLite database and defines the same lookup twice: once by pasting the name into the SQL (vulnerable), once with a parameterised query (also called a prepared statement or bound parameters). The first attack returns every user; the second uses UNION to append a different query's results and so reads a column the lookup was never meant to expose.

"""SQL injection on a deliberately vulnerable query, in an in-memory database."""
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, role TEXT, secret TEXT);
INSERT INTO users (name, role, secret) VALUES
  ('alice', 'admin',  'alice-api-key'),
  ('bob',   'viewer', 'bob-api-key');
""")

def find_user_vulnerable(name: str):
    # VULNERABLE: data is pasted into the code string.
    sql = f"SELECT name, role FROM users WHERE name = '{name}'"
    return sql, db.execute(sql).fetchall()

def find_user_safe(name: str):
    # FIXED: the SQL text is a constant; the value travels separately.
    sql = "SELECT name, role FROM users WHERE name = ?"
    return sql, db.execute(sql, (name,)).fetchall()

attacks = ["bob", "nobody' OR '1'='1", "x' UNION SELECT name, secret FROM users --"]
for a in attacks:
    sql, rows = find_user_vulnerable(a)
    print("VULN ", repr(a)); print("   sql :", sql); print("   rows:", rows)
for a in attacks:
    sql, rows = find_user_safe(a)
    print("SAFE ", repr(a)); print("   rows:", rows)

# What parameters cannot do: identifiers (table or column names, ORDER BY direction).
ALLOWED_SORT = {"name": "name", "role": "role"}
def list_sorted(column: str):
    if column not in ALLOWED_SORT:                 # allowlist, then map to a constant
        raise ValueError(f"cannot sort by {column!r}")
    return db.execute(f"SELECT name FROM users ORDER BY {ALLOWED_SORT[column]}").fetchall()
print("sorted:", list_sorted("name"))
try:
    list_sorted("name; DROP TABLE users")
except ValueError as e:
    print("rejected:", e)

Two details to notice in the output. First, the safe version returns nothing for the hostile names: they are simply names that no user has. Second, the last lines show what parameters cannot do. A placeholder stands for a value; you cannot parameterise a table name, a column name or ASC/DESC, because those are part of the query's structure. When they must vary, map the user's choice onto a fixed allowlist of constants, as list_sorted does, and never splice the raw input.

Why escaping and denylists fail

The instinctive fix is to sanitise: double every quote, or reject input containing OR, UNION, -- and ;. Both approaches try to recognise attacks inside the data, which means guessing every way the interpreter might reinterpret it. That guess is wrong surprisingly often.

"""Why 'just escape quotes' and denylists fail. Everything runs against an in-memory sqlite3 database."""
import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("CREATE TABLE t (id INTEGER, owner TEXT); INSERT INTO t VALUES (1,'a'),(2,'b'),(3,'c');")

def naive_escape(s: str) -> str:
    return s.replace("'", "''")          # the classic fix for string literals

# 1. Works for a string context ...
print("string ctx :", db.execute(f"SELECT * FROM t WHERE owner = '{naive_escape(chr(39)+' OR 1=1 --')}'").fetchall())
# 2. ... but a NUMERIC context has no quotes to escape.
user_id = "0 OR 1=1"                      # no quote character anywhere
print("numeric ctx:", db.execute(f"SELECT * FROM t WHERE id = {naive_escape(user_id)}").fetchall())

# 3. A denylist of 'bad words' is a game of whack-a-mole.
DENY = ["or ", "union", "select", "--", ";"]
def denylisted(s: str) -> bool:
    return any(w in s.lower() for w in DENY)
for payload in ["0 OR 1=1", "0 oR 1=1", "0 or\t1=1", "0||1", "0 OR/**/1=1"]:
    print(f"{payload!r:16} blocked={denylisted(payload)}")
print("bypass     :", db.execute("SELECT * FROM t WHERE id = " + "0 or\t1=1").fetchall())
string ctx : []
numeric ctx: [(1, 'a'), (2, 'b'), (3, 'c')]
'0 OR 1=1'       blocked=True
'0 oR 1=1'       blocked=True
'0 or\t1=1'      blocked=False
'0||1'           blocked=False
'0 OR/**/1=1'    blocked=False
bypass     : [(1, 'a'), (2, 'b'), (3, 'c')]
  • Escaping is context-specific. Doubling quotes protects a quoted string and does nothing for a numeric position, where the attack contains no quote at all (the numeric ctx line). Add different quoting rules per database, character sets whose multi-byte sequences swallow an escaping backslash, and second-order cases where data stored safely is later spliced unsafely, and you have a rule that needs to be right everywhere, forever.
  • Denylists are incomplete by construction. The attacker only needs one spelling the list missed: a different case, a tab for a space, a comment standing in for whitespace. Defenders must anticipate every variant; attackers need to find one.
  • Normalisation order bites. If you filter and then decode (URL-decode, Unicode-normalise, strip comments), the decoder can reassemble the string you just cleaned.

Parameterisation works for a different reason: it does not inspect the data at all. It removes the channel through which data could become code. That is the general principle of this chapter: prefer designs where the interpreter structurally cannot mix the two, over designs that try to clean the mix afterwards.

ORMs and their escape hatches

An ORM (object-relational mapper, such as SQLAlchemy or Django's ORM) builds queries from method calls, and it parameterises the values for you. User.objects.filter(name=name) is safe against this class of bug because the framework generates a placeholder. That is a real benefit, and also a trap: engineers learn "the ORM protects me" and then meet a query the ORM cannot express. Every mature ORM has a raw SQL escape hatch, and the injection returns the moment someone formats a string into it:

  • Django: .raw(), .extra(), RawSQL and cursor.execute() are safe only if you pass user values through the params argument, not an f-string.
  • SQLAlchemy: text("... WHERE name = :name") with bound values is safe; text(f"... WHERE name = '{name}'") is not.
  • Dynamic order_by, column names and table names that come from request parameters pass straight through many ORMs. Use the allowlist-and-map approach shown above.

The review rule: in a diff, any string formatting (f"...", %, .format, +) near a database call is a finding until proven otherwise. The same family exists outside SQL: NoSQL stores that accept JSON queries can be injected by supplying an operator object (such as {"$ne": null}) where a string was expected, which is again data being interpreted as query structure. The fix is the same: validate the type and shape of input before it reaches the query builder.

Command injection

A shell is an interpreter with a rich grammar: ; and && chain commands, | pipes, backticks and $(...) substitute output, > redirects. Passing a string to the shell (os.system, or subprocess with shell=True) makes all of it available to whoever controls part of the string. Passing an argument list without a shell starts the program directly, and each list element arrives as exactly one argument with no parsing.

"""Command injection. The 'attack' only runs the harmless echo command in your own shell."""
import subprocess, shlex

def ping_vulnerable(host: str) -> str:
    # VULNERABLE: shell=True hands the whole string to /bin/sh, which parses ; | && $() etc.
    return subprocess.run(f"echo pinging {host}", shell=True, capture_output=True, text=True).stdout

def ping_safe(host: str) -> str:
    # FIXED: an argument list is passed to the program directly; no shell parses it.
    return subprocess.run(["echo", "pinging", host], capture_output=True, text=True).stdout

evil = "example.com; echo INJECTED-SECOND-COMMAND"
print("vulnerable:", repr(ping_vulnerable(evil)))
print("safe      :", repr(ping_safe(evil)))

# Defence in depth: validate against an allowlist pattern too, and stop option injection with '--'.
import re
HOST = re.compile(r"[A-Za-z0-9]([A-Za-z0-9.-]{0,251}[A-Za-z0-9])?")
def validate_host(h: str) -> str:
    if not HOST.fullmatch(h):
        raise ValueError("bad host")
    return h
for h in ["example.com", evil, "-oProxyCommand=x"]:
    try: print(f"{h!r:45} ok ->", validate_host(h))
    except ValueError as e: print(f"{h!r:45} rejected")
print("if you must build a shell line, quote:", shlex.quote(evil))
vulnerable: 'pinging example.com\nINJECTED-SECOND-COMMAND\n'
safe      : 'pinging example.com; echo INJECTED-SECOND-COMMAND\n'
'example.com'                                 ok -> example.com
'example.com; echo INJECTED-SECOND-COMMAND'   rejected
'-oProxyCommand=x'                            rejected
if you must build a shell line, quote: 'example.com; echo INJECTED-SECOND-COMMAND'

The vulnerable call ran a second command; the safe call printed the whole string as one inert argument. Three further points matter in practice:

  • Avoid the shell entirely. Most tasks that "need" a shell (listing files, resizing an image, calling a Git command) have a library or a direct invocation with an argument list.
  • Argument injection is a smaller sibling. Even without a shell, a value that begins with - can be taken for an option (-oProxyCommand=... to ssh is the textbook case). Validate against an allowlist pattern, and use -- to end option parsing where the program supports it.
  • shlex.quote is a last resort, not a plan. It is correct for POSIX shells, but only if you remember it on every interpolation and the string really goes to a POSIX shell. Use it when you truly have to build a shell line, not as a habit.

Path traversal

Path traversal (directory traversal) is injection where the interpreter is the filesystem. A download endpoint joins a base directory and a user-supplied name; the name contains .. segments, an absolute path, or a symbolic link, and the final path lands outside the base. The key insight is that the check must be made on the resolved path, because the filesystem, not your string code, decides what a/../b and a symlink mean.

"""Path traversal in a temporary directory that the script creates and deletes."""
import os, tempfile
from pathlib import Path

root = Path(tempfile.mkdtemp(prefix="s0912_"))
base = root / "uploads"; base.mkdir()
(base / "report.txt").write_text("public report")
(root / "secret.txt").write_text("TOP SECRET (outside the base)")
os.symlink(root / "secret.txt", base / "link.txt")        # a symlink that points outside

def read_vulnerable(name: str) -> str:
    return open(os.path.join(base, name)).read()           # joins blindly

def read_safe(name: str) -> str:
    candidate = (base / name).resolve()                    # normalise: .., symlinks, absolute paths
    if not candidate.is_relative_to(base.resolve()):       # then check containment (Python 3.9+)
        raise PermissionError(f"{name!r} escapes the base directory")
    return candidate.read_text()

for name in ["report.txt", "../secret.txt", "link.txt", "/etc/hostname"]:
    try:    v = read_vulnerable(name)[:28]
    except Exception as e: v = type(e).__name__
    try:    s = read_safe(name)[:28]
    except Exception as e: s = f"{type(e).__name__}: blocked"
    print(f"{name:15} vulnerable={v!r:32} safe={s!r}")

# The classic string-check mistake: a prefix test without a separator
print("startswith bug:", str(root / "uploads-evil" / "x").startswith(str(base)))
print("is_relative_to:", (root / "uploads-evil" / "x").is_relative_to(base))
import shutil; shutil.rmtree(root)
report.txt      vulnerable='public report'                  safe='public report'
../secret.txt   vulnerable='TOP SECRET (outside the base'   safe='PermissionError: blocked'
link.txt        vulnerable='TOP SECRET (outside the base'   safe='PermissionError: blocked'
/etc/hostname   vulnerable='FileNotFoundError'              safe='PermissionError: blocked'
startswith bug: True
is_relative_to: False

(The /etc/hostname line depends on your operating system; on Linux the vulnerable version would read it. That is the point: an absolute path in the user's input replaces the base completely when joined.) The last two lines show a classic slip: checking startswith(base) accepts a sibling directory called uploads-evil, because the prefix has no separator. Use pathlib's is_relative_to (Python 3.9+), or os.path.commonpath, after resolve() or os.path.realpath.

Better still, do not let users name files at all. Store uploads under a generated identifier (a UUID or a content hash) and keep the original filename only as metadata. The same reasoning applies to archive extraction (a "zip slip" archive whose entries contain ../) and to any place a filename arrives from outside. Two residual limits: a resolve-then-open check has a small TOCTOU window (time of check to time of use), since a symlink could change between the check and the open, so run the service as a user that cannot read anything sensitive anyway (least privilege, chapter 2), and see systems chapter 19 for confining the process itself.

Template injection, briefly

A template engine interprets a mini-language ({{ ... }}, ${...}, or Python's str.format placeholders). If the template text itself contains attacker input, the attacker is writing code in that language. Server-side template injection in engines with expression power can reach the whole runtime. Even the humble str.format lets a format string walk attributes and index into objects, and so reach module globals (the demo in the log-injection section below shows it).

The rule is the same as for SQL: the template is a constant that you wrote; user data is passed only as values into it. Do not let users supply template text, or if the product really needs user-editable templates, use a logic-less or sandboxed engine and treat it as a high-risk feature. Unsafe deserialization

Chapter 3 of the data course (encoding and serialization) described formats that turn objects into bytes and back. The security question is what reading a format is allowed to do. JSON and Protocol Buffers can only produce plain data: maps, lists, strings, numbers. Python's pickle is different: it is a small program for rebuilding objects, and it can instruct the loader to call arbitrary functions. Loading a pickle from an untrusted source is therefore code execution, not parsing. The same applies to Java's native object serialization, PHP's unserialize with object support, and YAML loaders in unsafe mode (yaml.load with a full loader in PyYAML can construct arbitrary Python objects, while yaml.safe_load restricts itself to plain types; PyYAML 6 makes you name the loader explicitly for this reason).

"""Unsafe deserialization. The 'payload' calls print(), which is harmless; a real one could call anything."""
import pickle, json

class Gadget:
    def __reduce__(self):
        # pickle will CALL this callable with these arguments while loading.
        return (print, ("!!! code ran during pickle.loads, before your program saw any object",))

blob = pickle.dumps(Gadget())
print("loading attacker-controlled pickle ...")
pickle.loads(blob)

print("\nsame idea against JSON:")
data = json.loads('{"user": "bob", "age": 31}')
print(data, "-> only dict, list, str, int, float, bool, None can come out")

# Make JSON typed again with an explicit schema check, not a magic class name in the data.
def parse_user(text: str) -> dict:
    d = json.loads(text)
    if set(d) != {"user", "age"} or not isinstance(d["user"], str) or not isinstance(d["age"], int):
        raise ValueError("schema mismatch")
    return d
print(parse_user('{"user": "bob", "age": 31}'))
try: parse_user('{"user": "bob", "age": 31, "role": "admin"}')
except ValueError as e: print("rejected:", e)
loading attacker-controlled pickle ...
!!! code ran during pickle.loads, before your program saw any object

same idea against JSON:
{'user': 'bob', 'age': 31} -> only dict, list, str, int, float, bool, None can come out
{'user': 'bob', 'age': 31}
rejected: schema mismatch

The payload used print, which is harmless, but note when it ran: during pickle.loads, before the program got an object back to inspect. There is no "validate after loading" defence. The rule is: never unpickle data that crosses a trust boundary, including cookies, cache entries a lower-trust service can write, message-queue payloads and uploaded files. If you need to rebuild typed objects from the network, parse a data-only format and then construct your own objects after checking the shape, as parse_user does. If you must sign the bytes (an HMAC from chapter 3), that proves who produced them, which is a real mitigation for internal use, but it does not make an unsafe format safe if the signing key leaks or a trusted producer is compromised.

Log injection

Logs are read by humans and parsers. If a log line includes attacker text containing a newline, the attacker can forge a second, fake entry; if the logs are rendered in a web console, unescaped HTML in them becomes cross-site scripting against your operators; and if they pass through a lookup-expanding logger, they become something worse (next section). The demo shows both the template and log cases:

"""Template-style injection via str.format, and log injection. Both run in this process only."""
import logging, io, re

SECRET_KEY = "s3cr3t-signing-key"          # a module global, standing in for app config

class Order:
    def __init__(self, who): self.who = who

# --- str.format used as a template engine on attacker-controlled FORMAT STRINGS ---
tmpl_from_user = "Hello {o.who}, {o.__init__.__globals__[SECRET_KEY]}"
print("vulnerable:", tmpl_from_user.format(o=Order("bob")))
# Fix: the template is a constant; users supply only VALUES.
print("fixed     :", "Hello {who}".format(who="{o.__init__.__globals__[SECRET_KEY]}"))

# --- log injection ---
buf = io.StringIO()
logging.basicConfig(stream=buf, level=logging.INFO, format="%(levelname)s %(message)s", force=True)
username = "mallory\nINFO login ok user=admin"
logging.info("login failed user=%s", username)
print("\nnaive log:\n" + buf.getvalue())

buf.truncate(0); buf.seek(0)
def clean(s: str) -> str:   # encode at the sink: make control characters visible
    return re.sub(r"[\x00-\x1f\x7f]", lambda m: f"\\x{ord(m.group()):02x}", s)
logging.info("login failed user=%s", clean(username))
print("encoded log:\n" + buf.getvalue())
vulnerable: Hello bob, s3cr3t-signing-key
fixed     : Hello {o.__init__.__globals__[SECRET_KEY]}

naive log:
INFO login failed user=mallory
INFO login ok user=admin

encoded log:
INFO login failed user=mallory\x0aINFO login ok user=admin

The first pair shows the template rule in action; the second shows a forged INFO login ok user=admin line, and then the fix: encode at the sink, here by making control characters visible. Structured logging (one JSON object per line, with the user's text as a string field) solves most of it by construction, because the encoder escapes newlines for you. See reliability chapter 5 for logs as a pipeline, including the privacy angle: also keep secrets and personal data out of logs.

Log4Shell: when the logger is the interpreter

In December 2021 a flaw in the widely used Java logging library Log4j 2 (CVE-2021-44228) showed what happens when a logger quietly becomes an interpreter. The library expanded ${...} lookups found inside the message being logged, and one lookup type could fetch and load a class from a remote server using JNDI (Java's naming and directory interface). So any attacker-controlled string that reached a log call, such as a User-Agent header or a username, could cause the server to load attacker-supplied code. Every ingredient from this chapter is there: untrusted data, a string that is also a program, and a component nobody thought of as an interpreter. Mitigation meant upgrading (later releases turned the lookup off by default and then removed it), and for a time disabling the behaviour by configuration or removing the vulnerable class. Read the full account in the Log4Shell case study.

Where to defend: allowlists, boundaries and sinks

Two design questions recur, and they have settled answers.

Allowlist, not denylist

An allowlist defines what is acceptable (a username matches [a-z0-9_]{3,32}; a sort column is one of three names; a redirect target is one of your own paths) and rejects everything else. A denylist defines what is forbidden and accepts the rest. The earlier SQL demo is the argument in miniature: the attacker only has to find what your list forgot. Use allowlists wherever the set of valid inputs is describable, which is more often than people assume: identifiers, enums, numbers, dates, hostnames, file extensions.

Validate at the boundary, encode at the sink

These are two different jobs, and conflating them causes both under- and over-protection.

  • Validation at the boundary checks that input has the right shape and meaning for your application: the right type, length, range, character set, and (for ids) that it refers to something the caller may access. Do it once, as the data enters, and convert it into a typed value. This catches nonsense early and shrinks the attack surface.
  • Encoding (or parameterising) at the sink makes the value safe for the specific interpreter it is about to enter: a bound parameter for SQL, an argument list for a process, context-aware escaping for HTML (next chapter), a containment check for the filesystem, control-character encoding for logs. Only the sink knows which characters are dangerous there.

Validation cannot replace encoding, because a valid value for one purpose can be dangerous for another: a perfectly legitimate surname such as O'Brien must be accepted, and must also be bound safely into SQL. And encoding at the sink cannot replace validation, because it does nothing about business-rule abuse such as a negative quantity. In the terms of chapter 2, this is complete mediation plus defence in depth: every use is checked, with more than one layer.

Go deeper (optional): the "parse, don't validate" idea and second-order injection

A useful discipline is to make validation produce a different type: instead of a str that you hope was checked, return an Email, UserId or SafeSortColumn that can only be constructed by the checking function. Downstream code then cannot accidentally receive an unchecked value, and the compiler or type checker helps review the boundary. It does not remove the need for sink encoding; it only guarantees the shape.

Second-order injection is when hostile data is stored safely (a parameterised INSERT), and later read back and spliced unsafely into a different query or page. "We sanitised on the way in" does not help, because the unsafe use is elsewhere. This is another reason to protect at the sink, where the danger actually materialises.

Distributed systems connection

In a system of many services, every internal call is also a trust boundary, and data you "validated" upstream arrives downstream as untrusted again unless it is re-checked or carried in a typed, authenticated form. Message queues are a classic gap: a consumer that unpickles or templates a queue payload trusts every producer that can write to the queue. This is the "security at the boundaries" theme of architecture chapter 8 and the API contracts of chapter 9: validate against a schema at each service edge, and keep interpreters (database, shell, template) behind narrow, parameterised interfaces.

Key takeaways

  • Injection has one root cause: untrusted data and code in one string, handed to an interpreter. Name the interpreter and you know the fix.
  • Parameterise: separate channels for query text and values (SQL), an argument list instead of a shell string (processes). Placeholders cover values only; allowlist and map identifiers.
  • Escaping and denylists try to recognise attacks in the data and lose to context and encoding variants. Prefer designs where data structurally cannot become syntax.
  • ORMs parameterise for you, until you use their raw-SQL escape hatch with string formatting.
  • Path traversal: resolve first, then verify the result stays under the base, with pathlib or os.path.realpath. Prefer generated storage names over user-supplied ones.
  • Never deserialize untrusted data with pickle, native object serialization or full-power YAML loaders. Parse data-only formats, then construct typed objects yourself.
  • Logs and templates are interpreters too (Log4Shell). Treat template text as code and log input as untrusted.
  • Validate at the boundary for meaning, encode at each sink for safety. They are different jobs and you need both.

Check your understanding

A developer fixes SQL injection by doubling every single quote in user input before pasting it into the query. What remains vulnerable?

  1. Nothing; doubling quotes is equivalent to parameterisation
  2. Only queries that use UNION
  3. Numeric positions with no quotes to escape, other quoting contexts, and any path that forgets the escape; the data is still part of the query string
  4. Only queries on SQLite
Escaping is context- and dialect-specific, and it relies on the developer remembering it everywhere. Parameterisation removes the channel entirely: the value is never parsed as SQL, whatever characters it contains.

Why is subprocess.run(["convert", user_file, "out.png"]) safer than subprocess.run(f"convert {user_file} out.png", shell=True)?

  1. No shell parses the arguments, so ;, | and $(...) in user_file are just characters in one argument (a value starting with - may still be read as an option)
  2. Argument lists are encrypted
  3. The list form runs the program in a sandbox
  4. It is only safer on Windows
The shell is the interpreter that creates the injection. Removing it removes the grammar. The leftover risk is argument injection, handled with validation and --.

Which check correctly confines a user-supplied filename to a base directory?

  1. Reject names containing the substring ..
  2. Check that the joined string starts with the base directory string
  3. Strip leading slashes from the name
  4. Resolve the joined path (following .. and symlinks), then check that the result is inside the resolved base using is_relative_to or commonpath
The filesystem decides what a path means, so check the resolved result. Substring tests miss encodings and symlinks; a bare prefix test accepts /base-evil; stripping slashes does not handle .. or links.

A service calls pickle.loads() on bytes read from a shared cache that other, less trusted services can write to. What is the risk?

  1. The cache will be slow
  2. Anyone who can write to the cache can make this service run code during loading, before it can inspect the result
  3. Pickles are not portable between Python versions, which is only a compatibility issue
  4. None, because the cache is on an internal network
Pickle is a program for rebuilding objects, so loading it can call arbitrary functions. "Internal" is not a trust level: the question is who can write the bytes. Use a data-only format and construct objects yourself.

"Validate at the boundary, encode at the sink." Why is validation alone not enough?

  1. Validation is always slower
  2. Validation only works for numbers
  3. A value that is valid for the application (such as the surname O'Brien) can still be dangerous in a particular interpreter, and only the sink knows how to neutralise it there
  4. Validation is illegal in some countries
Validation expresses what your application accepts; sink encoding expresses what a given interpreter needs. Legitimate data often contains characters that are special somewhere. Both layers together give defence in depth.

What made Log4Shell possible, in the terms of this chapter?

  1. A buffer overflow in the logging code
  2. The logger treated parts of the message being logged as instructions (lookups, including one that could load remote code), so attacker-controlled data became code
  3. Weak encryption of the log files
  4. Logs were stored in plain text
It is injection through an unexpected interpreter. The fix was to remove the lookup behaviour on message contents, not to filter particular strings.

Lab 5: Find and Fix Injection

SQL injection, path traversal, command injection and server-side request forgery look like four different bugs and are one: a program builds a string out of code and data, hands it to an interpreter, and the interpreter cannot tell which part was which (chapter 9, chapter 11). In this lab a small backend is deliberately written the way real bugs get written. For each feature you first write the input that breaks it, so you know you understand the flaw, then you fix it, and the check throws a battery of variants at both versions. You finish by writing a regression suite, and the check tests your tests by re-breaking the app seventeen ways.

Why this lab matters

Injection bugs are easy to write because the vulnerable code works on every normal input, and easy to fix once you can name the interpreter. The real difficulty is the middle ground: fixes that look right and are not. A blocklist of forbidden strings, quote escaping, startswith on a path, a check of the address followed by a second lookup of the name. Each of those is in this lab as a plausible-looking version that your tests must be able to tell from the real fix. The skill that transfers is the discipline: reproduce the bug first, fix it at the root, then keep a test that fails if anyone brings it back.

Only test what you own or are authorised to test

Every exploit in this lab runs against deliberately vulnerable code in one Python process, on data the check creates. The database is in memory, the files are in a temporary directory that is deleted when the check ends, the "shell" is a toy interpreter that executes nothing real, and the "network" is a table of fake servers with documentation-style names. No socket is ever opened. The addresses in that table are arbitrary labels; nothing at any real address is contacted. The techniques here are taught so that you recognise and prevent them. Using them against systems you do not own, or are not explicitly authorised to test, is unauthorised access, and it is not what this lab is for.

Simulation, so the exploits are repeatable

Because the shell and the network are simulations, the check can see things a real test could not: the exact SQL text that ran, the list of commands the shell executed, every DNS lookup made. Those observations are what let the checks tell a real fix from a lucky one. "The payload returned nothing" is weak evidence; "the payload never appeared in the SQL text, and the same SQL text ran for every input" is strong evidence. When you write your own tests in milestone 5, look for the same kind of evidence.

What you'll build

Five milestones. The first four share a shape: understand the vulnerable code, exploit it (the check confirms your input works against the vulnerable version), fix it, and watch the same exploit and a battery of variants fail while legitimate use keeps working.

  1. SQL injection: dump every user from the search, steal the secrets with a UNION, then fix it with parameters and an allowlist for the sort column.
  2. Path traversal: read a file outside the uploads folder, then contain every download with realpath.
  3. Command injection: run a second command through a hostname lookup, then pass an argument list instead of a command line.
  4. SSRF: reach a fake cloud metadata address through a URL preview using a decimal address, an IPv6 spelling and DNS rebinding, then resolve once, check with ipaddress and connect to the address you checked.
  5. A regression suite: write tests that pass on your fix and fail on seventeen re-broken variants.

Milestone 1: SQL injection

Read the vulnerable search first:

def search_users(self, name, sort="name"):
    # BUG: both `name` and `sort` are pasted into the SQL text.
    return self._query(f"SELECT name, role FROM users WHERE name = '{name}' ORDER BY {sort}")

The developer's picture is "a name goes between the quotes". The database's picture is a string it must parse. If the name contains a quote, the literal ends there and whatever follows is parsed as SQL: that is the whole vulnerability, and the quote is not magic, it is just the character that ends a string. The table has four users, each with a secret column the search never selects (an API key, say). Your first job is to prove the flaw by exploiting it.

The fix has two parts, because there are two different holes. The value is parameterised: WHERE name = ? with the name passed separately. The identifier in ORDER BY cannot be parameterised (a placeholder stands for a value, never for a column name), so it is chosen from an allowlist that maps the user's choice onto a constant from your own code, and anything else is rejected. Escaping quotes or banning words such as UNION is the tempting alternative, and the check includes payloads that defeat it. The reason is the one from chapter 9: those fixes try to recognise attacks inside the data, and the interpreter's grammar is larger than any list of bad strings.

The check tests the fix with evidence, not only outcomes. For sixteen payloads (boolean tricks, a UNION, comment endings, a stacked statement, a backslash, a double-quoted variant, a percent-encoded quote and a Unicode apostrophe) it requires zero rows and that the payload never appears in the logged SQL text, and that only one SQL statement text was ever used. Some of the sixteen do not even work against the vulnerable version today. They are there because a fix should survive the day that a layer in front of it starts decoding percent-escapes or normalising Unicode.

Write sql_dump_users() and sql_steal_secrets(): each returns the name to search for. Then override App.search_users. Use self._query(sql, params) so the check can see the SQL text; SORT_COLUMNS is given.

Hints try without first
  • The vulnerable text becomes WHERE name = 'YOURS' ORDER BY name. You need a value that makes the condition true for every row and leaves a valid statement. Closing the quote and adding an always-true condition is enough; to hide the rest, end with --, which starts a comment in SQL.
  • For the UNION, the left side selects two columns (name, role), so the right side must select two as well. Which column do you want to appear in the role position?
  • Fixed query: self._query(f"SELECT name, role FROM users WHERE name = ? ORDER BY {order}", (name,)), where order comes from self.SORT_COLUMNS[sort] after you have raised ValueError for an unknown sort. The f-string contains only a value from your own table.
  • An sqlite3 parameter tuple needs a trailing comma when it has one element: (name,).

Milestone 2: path traversal

The download feature joins a file name onto the uploads folder and opens it. The filesystem is an interpreter too: .. means "the parent directory", a symbolic link means "go there instead", and an absolute path means "ignore everything before me". A name that is just a name works; a name that is a path walks wherever it likes.

def download(self, name):
    # BUG: the name is joined onto the root and opened; nothing checks where it ended up.
    with open(os.path.join(self.root, name), "rb") as f:
        return f.read()

The temporary layout is uploads/ (the folder the app may serve, with report.txt, docs/guide.txt, a file named a..b.txt, and a symbolic link link.txt that points at ../secret.txt), then secret.txt beside it, and a sibling folder uploads_private/ whose name begins with the same letters as the root's.

Why do the shortcuts fail? Blocklisting ../ (for example deleting it from the name) is beaten by ....//, which becomes ../ after the deletion, and does nothing about absolute paths. Rejecting any name containing .. blocks real files such as a..b.txt and legitimate paths such as docs/../report.txt, which the check requires to keep working: a fix that breaks real users gets removed under pressure. startswith(root) treats /data/uploads_private as inside /data/uploads, because the strings share a prefix; os.path.commonpath compares path components. abspath tidies a path as text and never looks at the disk, so it does not know that link.txt is a link; realpath does. And a detail that bites on a Mac: the temporary directory's own path contains a symbolic link (/var points to /private/var), so if you resolve the target but compare it with an unresolved root, legitimate files are refused. Resolve both sides.

Your task

Write path_exploit(), which returns a file name that makes the vulnerable download return secret.txt. Then override App.download: refuse anything that does not resolve to a place inside the real upload root, with PermissionError.

Hints try without first
  • One level up from uploads/ is where secret.txt lives. A name can contain a slash.
  • base = os.path.realpath(self.root); target = os.path.realpath(os.path.join(base, name)). Because os.path.join discards the base when the second argument is absolute, the absolute-path variant ends up outside the base and the containment check catches it.
  • os.path.commonpath([base, target]) != base means the target is not inside the base. (On Windows, commonpath raises ValueError for paths on different drives, which is also a refusal.)
  • Open target, the resolved path, not the original name. Checking one path and opening another is the same time-of-check bug you will meet again in milestone 4.

def path_exploit():
    return "../secret.txt"

def download(self, name):
    base = os.path.realpath(self.root)
    target = os.path.realpath(os.path.join(base, name))
    if os.path.commonpath([base, target]) != base:
        raise PermissionError(f"{name!r} is outside the upload folder")
    with open(target, "rb") as f:
        return f.read()

Milestone 3: command injection

A diagnostics page lets staff type a hostname and see its DNS records. The page builds a command line and hands it to a shell:

def lookup(self, host):
    # BUG: the hostname is pasted into a command LINE that a shell parses.
    return self.shell.run(f"nslookup {host}")

Here the interpreter is the shell, whose grammar is rich: ;, &&, ||, | and a newline all start another command; $(...) and backticks run a command and paste its output; # comments out the rest; quotes group words. In this lab the shell is MiniShell, a small interpreter written for the purpose that runs Python functions over a dictionary of fake files. Nothing real is executed, and its toy commands (nslookup, echo, cat, rm, id) cannot touch your computer. It has two entry points, and the difference between them is the whole lesson: run(line) parses text the way sh -c does; exec(argv) takes an argument list and runs exactly one command with no parsing, the way subprocess.run([...]) does without a shell.

Passing an argument list removes shell injection and leaves argument injection: the command itself may interpret its arguments. The toy nslookup has an option --out=FILE that writes its result to any path, a stand-in for the output, config or "execute this" options real tools have. A hostname of --out=/data/report.txt is one clean argument and still overwrites a file. Two defences, both in the fix: validate the hostname against what a hostname can be (letters, digits, dots, hyphens; it can never begin with a hyphen), and put --, the conventional end-of-options marker, before the user's value. Where a feature only ever needs a known set of hosts, an allowlist of exact names beats validation. Quoting the pasted value, or checking only the start of the string, are the "fixes" the check re-creates in milestone 5.

The lab's snippet of real Python for the same job is below. It is illustrative and is not run here, because the options of nslookup differ between platforms:

# illustrative, not executed in this lab
subprocess.run(["nslookup", "--", host], capture_output=True, timeout=5, check=True)   # no shell=True, ever

Hints try without first
  • The vulnerable line becomes nslookup HOST. What character ends one command and starts the next?
  • HOSTNAME.fullmatch(host) is a match or None. fullmatch matters: match with $ would accept a hostname followed by a newline, because $ also matches before a trailing newline, and a newline is a command separator.
  • The pattern requires the first character to be a letter or digit, so --out=... and -x are rejected before the shell is involved.
  • Do not call self.shell.run at all in the fixed method: if you never give a shell a string to parse, you cannot be tricked into building the wrong string.

Milestone 4: SSRF in a URL preview

A link-preview feature fetches a URL the user pasted and shows the start of the page. The server makes the request, from inside your network, with your network position (chapter 11). The lab provides a Network with a fake resolver and fake servers: a few public sites (news.example.test, shop.example.test, a link shortener), an "attacker" site whose names you will use, and, at private and special addresses, a fake cloud metadata service (169.254.169.254), an internal admin panel (10.0.0.5), a loopback console and more. Its resolver also reads IP addresses written the lenient way a C library does: as a single decimal integer, in hex, in octal, in short forms such as 127.1, and in IPv6, because that is how real HTTP clients behave and why a string match on the host is hopeless. Nothing leaves the process.

The vulnerable preview has the kind of protection that real code has:

BLOCKED_HOSTS = {"localhost", "127.0.0.1", "169.254.169.254", "::1"}
def preview(self, url):
    # BUG: a blocklist of host STRINGS, a check of the resolved name, and then the HTTP
    # client resolves again and follows redirects on its own.
    ...

The protection works for the obvious input (http://169.254.169.254/ is refused) and for a hostname that points at 10.0.0.5. The three exploits you write each defeat a different assumption: a decimal spelling of the address (the string is not on the blocklist, but the client turns it into the same four bytes), an IPv6 spelling (an IPv4-mapped address in brackets, which also reaches the IPv4 host), and DNS rebinding: a name whose first answer is public, to pass the check, and whose second is the metadata address, to be used.

The fix follows chapter 11's order: restrict the scheme to http and https and refuse credentials in the URL (http://news.example.test@169.254.169.254/ has the host after the @); resolve once; turn the answer into an ipaddress object, unwrapping an IPv4-mapped IPv6 address first so that a mapped metadata address is judged as the IPv4 address it is; accept only is_global addresses, which excludes loopback, private, link-local, carrier-grade NAT, unspecified and the special IPv6 ranges in one test; then connect to the address you checked (pinning), passing the hostname only for the Host header. Redirects must be followed by you, with the whole procedure repeated on each hop, because a public page can redirect to the metadata address, and with a limit, because a redirect can loop.

def ssrf_decimal():
    return "http://2852039166/latest/meta-data/"

def ssrf_ipv6():
    return "http://[::ffff:169.254.169.254]/latest/meta-data/"

def ssrf_rebinding():
    return "http://rebind.attacker.test/"

def preview(self, url):
    for _ in range(MAX_REDIRECTS + 1):
        try:
            u = urlsplit(url)
            host = u.hostname
        except ValueError:
            raise Blocked("malformed URL")
        if u.scheme not in ("http", "https"):
            raise Blocked(f"scheme {u.scheme!r} is not allowed")
        if u.username is not None or u.password is not None:
            raise Blocked("credentials in a URL are not allowed")
        if not host:
            raise Blocked("no host")
        ip = ipaddress.ip_address(self.net.resolve(host))     # ONE lookup; whatever spelling the client would use
        if ip.version == 6 and ip.ipv4_mapped:
            ip = ip.ipv4_mapped
        if not ip.is_global or ip.is_multicast:
            raise Blocked(f"{host} resolves to a non-public address ({ip})")
        resp = self.net.request(str(ip), host, (u.path or "/") + ("?" + u.query if u.query else ""))    # PINNED
        if resp.status in (301, 302, 303, 307, 308) and "Location" in resp.headers:
            url = urljoin(url, resp.headers["Location"])        # every hop goes round the loop again
            continue
        return resp.body[:200]
    raise Blocked("too many redirects")

Milestone 5: a regression suite that catches the bugs if they come back

A fix without a test is a fix on a timer. The code gets refactored, a performance change replaces commonpath with something shorter, a helper is "simplified" back to string formatting, and nobody notices because nothing fails. A regression test is a test that fails if a specific bug returns. The security question is not "do I have tests?" but "would these tests notice if the bug came back?" The only honest way to know is to bring the bug back and see, which is the idea behind mutation testing: make a small deliberate change to correct code and check that the tests complain.

What makes a suite catch them all? Each of these has a place in the reference suite, and the hints list them:

  • One test per root cause, using the original exploit, because that is the bug a revert brings back.
  • One test per bypass class, because the bugs that return are the half-fixes: alternative encodings of the address, a sibling folder, a symlink, an option that looks like a hostname, a redirect, a rebind.
  • Tests of the mechanism where the outcome alone proves too little: the SQL text must not contain the input; the hostname must be looked up once; the shell must see only nslookup.
  • Tests of legitimate behaviour, because an over-blocking "fix" (one that rejects every ..) is also a regression, and one that real users will force you to remove.
  • Tests that fail for the right reason: assert on the property you care about (no leak, refused), not on an exact error message that an unrelated change would alter.

Distributed systems connection

Milestone 4 is a time-of-check to time-of-use bug, the same shape as the frozen lock holder in distributed Lab 2: you check a fact (the name points to a public address; the lease is valid), time passes or the world changes, and you act on a fact that is no longer true. The cure is the same too: do not check and then act on a re-derived value; carry the checked value (the resolved address, the fencing token) into the action so that the action itself enforces the condition. Beyond this lab, every service that fetches user-chosen URLs is a bridge into an internal network of services that trust one another, which is why large systems put such fetches behind an egress proxy and give each service its own identity (chapter 13). And the regression discipline of milestone 5 is the security counterpart of the failure tests in distributed chapter 19: you do not trust a property until you have seen the test fail when the property is broken.

What you learned

  • All four bugs are one bug: untrusted text reaches an interpreter (the SQL parser, the filesystem, the shell, the HTTP client) as structure. Fix the root, not the symptom: parameters instead of escaping, resolve-then-judge instead of pattern matching, an argument list instead of a command line, one resolved address instead of a name looked up twice.
  • Identifiers cannot be parameters: use an allowlist that maps input to a constant. Argument injection survives a missing shell, so validate and use --.
  • Use realpath on both sides and commonpath for containment; startswith, abspath, stripping ../ and rejecting .. each fail in a way the check demonstrates.
  • For SSRF, judge the address the client will use, with ipaddress (is_global, after unwrapping mapped IPv6), pin the connection to it, and re-run the whole procedure on every redirect. Back it with egress limits, because one check will eventually have a hole.
  • A regression suite is code that can be wrong. Test the exploit, the bypass variants, the mechanism and the legitimate use, and then break the app on purpose to see whether your tests notice.

Check your understanding

A search builds "... WHERE name = '" + name + "'". A colleague proposes to fix it by doubling every single quote in name. Which statement is right?

  1. That is equivalent to parameters, so it is fine
  2. It only handles one context (a quoted string); parameters keep the structure and the value separate, so the interpreter never sees the value as syntax, and also cover contexts where a quote is not involved
  3. It is stronger than parameters because it removes the dangerous character
  4. Escaping and parameters differ only in speed
Escaping tries to neutralise attacks inside the data and has to be right for every context and every database, forever. Parameters send the structure first and the value separately, so there is nothing to neutralise. In the lab the check also requires that the input never appears in the SQL text at all, which an escaping fix cannot satisfy, and the identifier in ORDER BY cannot be a parameter and needs an allowlist.

os.path.realpath(os.path.join(root, name)).startswith(root) is used to keep downloads inside /srv/uploads. What is wrong with it?

  1. Nothing: it resolves symlinks and checks the prefix
  2. The prefix test compares characters, so /srv/uploads_private/x passes; use os.path.commonpath (and resolve the root as well)
  3. realpath cannot follow symlinks
  4. startswith is too slow for large paths
A string prefix is not a directory ancestor. The check's sibling-folder variant, ../uploads_private/data.txt, is accepted by this test. commonpath compares whole path components. If root itself contains a symlink, the unresolved root also fails to match the resolved target, so resolve both.

A developer replaces shell.run(f"nslookup {host}") with shell.exec(["nslookup", host]) and removes all validation. Which attack still works?

  1. The semicolon trick, because exec still uses a shell
  2. Argument injection: a host such as --out=/data/report.txt is passed as a single argument that the command itself interprets as an option; validate the value and put -- before it
  3. None: argument lists are always safe
  4. Only a null byte
An argument list removes the shell's grammar, not the command's. Many tools take options that write files, load configuration or execute things. Validation (a hostname cannot start with a hyphen) and the end-of-options marker are the second layer, and an allowlist is better still when the set of valid values is known.

An SSRF filter resolves the hostname, checks that the address is public, and then hands the original URL to an HTTP library. Why can it still be exploited, and what is the fix?

  1. It cannot: the address was checked
  2. The library resolves the name again and an attacker's DNS server can answer differently the second time (rebinding); resolve once and connect to the address you checked, and re-validate every redirect hop
  3. Because DNS answers are always cached for ten minutes
  4. Because public addresses are not safe either
The check and the use are two lookups of data the attacker controls. Pinning makes them the same value. The lab's check counts DNS lookups for the rebinding name (two for the vulnerable app, one for the fixed one) and a mutant that checks and then re-resolves must be caught by your regression suite.

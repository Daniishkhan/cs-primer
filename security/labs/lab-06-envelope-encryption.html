Lab 6: Envelope Encryption & Crypto-Shredding

Almost every system that protects tenant data at rest uses the same structure: small data keys encrypt the data, and a few master keys in a key-management service wrap the data keys (chapter 4, chapter 17). In this lab you build the whole thing with the standard library: a toy authenticated cipher, a KMS simulator that logs every call, per-tenant data keys that cannot be swapped between tenants, key rotation that never re-encrypts a byte of data, and finally the payoff of the design, deleting a tenant's data everywhere, in every backup, by destroying one key.

Educational only: never use this cipher, or this KMS, to protect real data

The cipher in this lab is a toy. It is a SHAKE-256 keystream with an HMAC, assembled encrypt-then-MAC, so that the lab runs with nothing but Python's standard library (which has no AES). It has not been reviewed or tested the way real constructions are, it is not constant-time end to end, and Python cannot reliably erase key bytes from memory. The KMS class keeps its keys in ordinary process memory; a real KMS keeps them in a hardware security module behind authentication and policy. This notice is repeated at the top of starter.py, solution.py and check.py. For real work, use a vetted AEAD (AES-GCM or ChaCha20-Poly1305) from a maintained library and your cloud provider's KMS or an HSM. What you are learning here is the structure, which carries over unchanged.

Why this lab matters

Encryption only moves the problem: data you cannot read without a key is exactly as safe as the key. Envelope encryption is how production systems make that manageable. The big, bulky work is local and cheap, the master keys stay in one hardened place that logs every use, rotation touches a few kilobytes instead of petabytes, and each tenant gets its own key so that one leaked key exposes one customer. And once keys are per-tenant, something remarkable becomes possible: a customer leaves, or a regulation says their data must go, and you cannot find every backup, replica and export, but you can destroy the key that makes all of them readable. The lab makes you earn that sentence: the check first shows why the obvious way to "delete the key" does not work.

A simulation that keeps its own books

Everything runs in one process. Random keys and nonces are real random bytes (secrets), but no check depends on their values, so every run reaches the same verdict. The KMS is a class with an audit list; "backups" are deep copies of the database dictionaries made by snapshot(). This is a model of the trust boundaries, not of the performance: a real KMS call is a network round trip with latency, quotas and failure modes, and a real backup is a different system with its own retention rules. Where that matters, the text says so.

What you'll build

Five milestones:

  1. A toy AEAD: seal and open_ with a nonce, encrypt-then-MAC, and associated data. Tampering and a wrong associated data are rejected.
  2. A KMS simulator: master keys with versions, wrap and unwrap of data keys with an encryption context, and one audit entry for every call, refused ones included.
  3. Per-tenant data keys: each tenant has a master key and a data key; records are sealed with the data key and the tenant id as associated data, so swapping ciphertexts between tenants fails.
  4. KEK rotation: rotate, re-wrap the data keys without re-encrypting any data, keep old versions decryptable, then retire (disable, then destroy) them.
  5. Crypto-shredding: destroy a tenant's key, then show that its records, including those in backups, are unrecoverable while other tenants are unaffected.

Milestone 1: a toy AEAD

An AEAD (authenticated encryption with associated data, from chapter 3) does three jobs in one call: it hides the plaintext, it detects any change to the ciphertext, and it binds the result to some associated data that is authenticated but not encrypted and not stored in the output. Associated data is how you say "this ciphertext is only valid for tenant acme, record 7": the reader must supply the same value, and any other value fails. Milestone 3 depends on it.

The toy construction uses only what the standard library offers. From one 32-byte key it derives two keys with HMAC (one for encryption, one for authentication, never the same key for both). It generates a random 16-byte nonce: a number used once per message with a given key. SHAKE-256, an extendable-output function, turns enc_key || nonce into a keystream as long as the message, and the ciphertext is the plaintext XOR that keystream, byte by byte. Then it computes a tag with HMAC-SHA256 over everything the reader will rely on, and appends it. This order, encrypt first and authenticate the ciphertext, is called encrypt-then-MAC, and it matters: the reader can verify the tag before doing anything with attacker-influenced bytes.

Four points deserve attention, and the check tests each one.

  • The nonce must never repeat for one key. A stream cipher's keystream depends only on the key and the nonce, so two messages sealed with the same pair are XORed with the same keystream, and XORing the two ciphertexts cancels it out: you are left with the XOR of the two plaintexts, which is often enough to recover both. The check calls seal twice with an explicit equal nonce and requires exactly that relationship; the demonstration below shows it. Production AEADs make this a first-order design concern (AES-GCM famously fails catastrophically on a repeated nonce), which is why libraries generate nonces for you or use schemes that tolerate misuse.
  • The MAC input must be unambiguous. If you hash ad || nonce || ciphertext as bare concatenation, the boundary between associated data and nonce is invisible: moving one byte from one to the other produces the same MAC input. The check moves one byte and requires rejection. Putting the length of the associated data in front of it removes the ambiguity. (This family of bug, ambiguous concatenation under a MAC or a signature, is old and has hit real protocols.)
  • Verify, then decrypt, in constant time. Compare tags with hmac.compare_digest, and do not compute the keystream until the tag has been accepted. The check spies on both.
  • Fail with one error. Short inputs, wrong keys, wrong associated data and flipped bits all raise AuthError, never IndexError, and never different errors that tell an attacker which part failed.

def seal(key, plaintext, ad=b"", nonce=None):
    enc_key, mac_key = _subkeys(key)
    if nonce is None:
        nonce = secrets.token_bytes(NONCE_LEN)
    if len(nonce) != NONCE_LEN:
        raise ValueError("nonce must be %d bytes" % NONCE_LEN)
    stream = hashlib.shake_256(enc_key + nonce).digest(len(plaintext))
    ct = bytes(p ^ k for p, k in zip(plaintext, stream))
    tag = hmac.new(mac_key, len(ad).to_bytes(8, "big") + ad + nonce + ct, hashlib.sha256).digest()
    return nonce + ct + tag

def open_(key, blob, ad=b""):
    if len(blob) < NONCE_LEN + TAG_LEN:
        raise AuthError("ciphertext too short")
    enc_key, mac_key = _subkeys(key)
    nonce, ct, tag = blob[:NONCE_LEN], blob[NONCE_LEN:-TAG_LEN], blob[-TAG_LEN:]
    expected = hmac.new(mac_key, len(ad).to_bytes(8, "big") + ad + nonce + ct, hashlib.sha256).digest()
    if not hmac.compare_digest(tag, expected):
        raise AuthError("authentication failed")
    stream = hashlib.shake_256(enc_key + nonce).digest(len(ct))
    return bytes(c ^ k for c, k in zip(ct, stream))

Milestone 2: a KMS simulator with audit logging

A key management service exists to hold the keys that must not be copied. Your application never sees a key-encryption key (KEK); it hands over a small secret (a data key) and gets back a wrapped version, which is the data key encrypted under the KEK. To use the data key later, the application sends the wrapped value back. The KMS decrypts it if its policy allows and returns the data key, and the application uses it, briefly, and forgets it. Your data can be petabytes; the KMS only ever sees 32-byte keys, which is why a KMS call can be a network round trip and still be affordable.

Three design points make the KMS a security control rather than a vault with a nice API.

  • An encryption context. Every wrap takes a context string (here, the tenant id) that is bound in as associated data. Unwrapping with a different context fails. A wrapped key copied onto another tenant's row is therefore useless: that is the "confused deputy" defence, applied to keys (chapter 4).
  • Versions. A key id names a master key; each rotation adds a version. A wrapped key records which version wrapped it, so old data keeps working after a rotation (milestone 4).
  • An audit log that records everything and reveals nothing. The KMS is the one component that sees every use of every key, so its log is the evidence for the questions that matter after an incident: who unwrapped tenant globex's key, when, from which service, and were there refused attempts first? Two rules: one entry per call, including refused calls (a log of successes only hides the attacker's probing); and never any key material, not a data key, not a KEK, not a wrapped blob, in a log that many people can read.

The starter gives you the _audited context manager, which appends the entry first, marks it ok when the block finishes, and records the error text when a KMSError escapes. Every public method runs its body inside it, which is how "one entry per call" stays true even when the call fails halfway.

def create_key(self, key_id, caller="app"):
    with self._audited("create_key", key_id, caller=caller) as e:
        if key_id in self._keys:
            raise KMSError(f"key {key_id!r} already exists")
        self._keys[key_id] = {"current": 1, "versions": {1: {"material": secrets.token_bytes(KEY_LEN), "state": "enabled"}}}
        e["version"] = 1
        return 1

def wrap(self, key_id, dek, context, caller="app"):
    with self._audited("wrap", key_id, context, caller) as e:
        version = self._key(key_id)["current"]
        e["version"] = version
        material = self._material(key_id, version)
        return Wrapped(key_id, version, seal(material, dek, ad=context.encode()))

def unwrap(self, wrapped, context, caller="app"):
    with self._audited("unwrap", wrapped.key_id, context, caller) as e:
        e["version"] = wrapped.version
        material = self._material(wrapped.key_id, wrapped.version)
        try:
            return open_(material, wrapped.blob, ad=context.encode())
        except AuthError:
            raise KMSError("wrapped key does not match this context, or was altered")

Milestone 3: per-tenant data keys

Now the application's side. Each tenant gets its own master key in the KMS and its own random data key (DEK). The DEK is wrapped once, when the tenant is created, and the wrapped value is stored in a tenants table. Each record is sealed with the tenant's DEK, and the sealed blob goes into the records table. To read or write, the application asks the KMS to unwrap the tenant's DEK, uses it, and drops it. (A production system would cache the DEK in memory for a short, bounded time to save KMS calls, trading some exposure for latency; the lab does not.)

Why per-tenant keys, and why bother binding the tenant as associated data when the keys already differ? Two answers, both tested.

Different keys already make a cross-tenant swap fail: if an attacker with write access to the database copies acme's ciphertext row into globex's slot, globex's DEK cannot authenticate it. But keys are managed by code, and code has bugs: a cache keyed by the wrong thing, a migration that copies a key, a "temporary" shared key for a feature flag. When two tenants do end up with the same DEK, only the associated data stops the swap. The lab's record_ad(tenant, record_id) builds a length-prefixed string of both ids. Your put and get must use it, and the check deliberately creates the shared-key situation to prove that you did. Binding the record id as well also stops swaps between two records of the same tenant, which is the same attack on a smaller scale (an attacker moving "the invoice for $10" into the slot of "the invoice for $10,000"). This is the defence-in-depth shape you have seen before: the first layer should make the second unnecessary, and the second should be there for the day the first has a bug.

def create_tenant(self, tenant):
    if tenant in self.tenants:
        raise ValueError(f"tenant {tenant!r} exists")
    self.kms.create_key(self.key_id(tenant))
    self.tenants[tenant] = self.kms.wrap(self.key_id(tenant), self.dek_source(), context=tenant)

def put(self, tenant, record_id, plaintext):
    self.records[(tenant, record_id)] = seal(self._dek(tenant), plaintext, ad=record_ad(tenant, record_id))

def get(self, tenant, record_id):
    blob = self.records[(tenant, record_id)]
    return open_(self._dek(tenant), blob, ad=record_ad(tenant, record_id))

Milestone 4: KEK rotation without re-encrypting the data

Keys are rotated for two reasons: policy (every year, say, to limit how much data one key version protects) and incident (a key might have leaked). The expensive way is to decrypt everything and encrypt it again. Envelope encryption makes the cheap way correct for the first reason: rotating the master key means re-wrapping the small data keys. The data, which is orders of magnitude larger, is not read or written at all.

The procedure from chapter 4 has four steps, and every step has a failure the check provokes:

  1. Rotate: create version 2 and make it current. New wraps use it; version 1 is untouched and enabled, so every existing wrapped key still unwraps. Version numbers are never reused.
  2. Re-wrap: for each data key, the KMS unwraps it with the old version and wraps it with the current one inside the KMS, in one call (rewrap). The data key is never returned to the application, so a re-wrap job needs permission to call rewrap and no ability to read data keys. It is one audit entry per key, with the old and new version recorded.
  3. Disable the old version: unwrap with it now fails. If a forgotten cron job, a cached copy or an old backup still depends on it, this is when you find out, and enable_version brings it back. The current version cannot be disabled (that would make wrapping impossible).
  4. Destroy it: irreversible, and allowed only for a disabled version, so that there is always a step between "I think nothing needs this" and "nothing can ever use this". The key bytes are erased.

Re-wrapping does not help if the data key leaked

If an attacker obtained a plaintext DEK, wrapping it under a new KEK changes nothing: they already hold the DEK, and the old records are encrypted under it. The only fix for a leaked DEK is to generate a new one and re-encrypt the data, the expensive path. That is one reason to scope DEKs narrowly (per tenant here, per object in some systems): the work, and the exposure, are bounded by what one key covers.

One operational trap deserves its own demonstration, and the check builds it: a backup taken before the re-wrap contains data keys wrapped by version 1. Destroy version 1 and that backup can never be restored. Nothing in the live system complains, and the failure surfaces in the middle of a disaster recovery (reliability chapter 18). Retire a version only when every wrapped copy you still need has been re-wrapped, or has aged out of its retention period. The demonstration at the end of this milestone shows the failure.

def rotate(self, key_id, caller="app"):
    with self._audited("rotate", key_id, caller=caller) as e:
        k = self._key(key_id)
        if k["versions"][k["current"]]["state"] == "destroyed":
            raise KMSError(f"{key_id} is destroyed")
        v = max(k["versions"]) + 1
        k["versions"][v] = {"material": secrets.token_bytes(KEY_LEN), "state": "enabled"}
        k["current"] = v
        e["version"] = v
        return v

def rewrap(self, wrapped, context, caller="app"):
    with self._audited("rewrap", wrapped.key_id, context, caller) as e:
        e["from_version"] = wrapped.version
        old = self._material(wrapped.key_id, wrapped.version)
        try:
            dek = open_(old, wrapped.blob, ad=context.encode())
        except AuthError:
            raise KMSError("wrapped key does not match this context, or was altered")
        current = self._key(wrapped.key_id)["current"]
        e["version"] = current
        return Wrapped(wrapped.key_id, current, seal(self._material(wrapped.key_id, current), dek, ad=context.encode()))

def destroy_version(self, key_id, version, caller="app"):
    with self._audited("destroy_version", key_id, caller=caller) as e:
        e["version"] = version
        v = self._key(key_id)["versions"].get(version)
        if v is None or v["state"] != "disabled":
            raise KMSError(f"{key_id} version {version} must be disabled before it can be destroyed")
        v["material"], v["state"] = None, "destroyed"

def rotate_kek(self, tenant):
    version = self.kms.rotate(self.key_id(tenant))
    self.tenants[tenant] = self.kms.rewrap(self.tenants[tenant], context=tenant)
    return version

Milestone 5: crypto-shredding

A tenant leaves and asks for its data to be deleted, or a retention period ends. In a system of any size, "delete it" is harder than it sounds, because the data exists in many places: the live database, read replicas, nightly and weekly backups, a data warehouse export, a search index, log lines, someone's laptop. You can delete from the live database in a transaction. You cannot reliably reach every immutable backup, and some must be kept intact for their retention period for other reasons. Crypto-shredding sidesteps the problem. If everything stored for the tenant is ciphertext, and the only way to read it is a key that lives in one place, then destroying that key makes every copy unreadable at once. The ciphertext is still there; it is noise.

The subtle part is what you destroy. The obvious way to "destroy a tenant's data key" is to delete the wrapped key from the live tenants table. The check starts by showing, with your own code, that this is not enough:

The backup contains a copy of the wrapped key, and the master key that unwraps it still exists, so anyone who restores the backup reads the data. Deleting a copy of the wrapped key deletes a copy. To shred, you must destroy the thing that every copy depends on: the master key, in the KMS, outside every backup. This is exactly why the design in this lab gives each tenant its own master key. With one shared master key you could not destroy it without destroying every tenant; with only per-tenant data keys wrapped by a shared master key, you would have nothing to destroy but copies.

Your task

Implement KMS.destroy_key(key_id) (destroy every version at once, erase the bytes, keep the key id as a tombstone, one audit entry) and TenantStore.shred_tenant(tenant) (destroy the tenant's key through the KMS, then remove its wrapped DEK from the live table; leave the ciphertext records alone; an unknown tenant raises KeyError). snapshot() and restore(), which model backups, are given.

def destroy_key(self, key_id, caller="app"):
    with self._audited("destroy_key", key_id, caller=caller):
        for v in self._key(key_id)["versions"].values():
            v["material"], v["state"] = None, "destroyed"

def shred_tenant(self, tenant):
    if tenant not in self.tenants:
        raise KeyError(f"unknown tenant {tenant!r}")
    self.kms.destroy_key(self.key_id(tenant))
    del self.tenants[tenant]

What crypto-shredding does and does not promise

  • It makes data unreadable, not absent. The ciphertext remains, and so do its sizes, counts and timestamps. If the data's existence is itself sensitive, or if a law requires physical deletion, shredding alone may not be what is required.
  • It protects only data that was only ever stored encrypted under that key. Plaintext in a log line, a cache, a search index, an analytics export or a crash dump is not covered. Shredding is as strong as your discipline about where plaintext may exist.
  • Anyone who already holds the plaintext data key, or a copy of the plaintext data, keeps it. An application server that cached the DEK in memory should drop it on shred, and keys must not be exported to other systems.
  • The KMS itself must destroy for real. Real services typically impose a mandatory waiting period before deleting a key, as a safeguard against mistakes (AWS KMS documents a waiting period of 7 to 30 days), and your KMS's own backups follow its own rules. During the waiting period the key can be restored; after it, not.
  • Legal effect is a legal question. Data-protection laws such as the EU's GDPR give people a right to erasure (Article 17), described in general terms in chapter 17. Whether destroying a key satisfies a particular obligation, for a particular dataset and regulator, is a question for counsel. This lab teaches the engineering, not legal advice.

Look under the hood

Try it yourself: five experiments

  1. Break the associated data. Make record_ad return only the record id. Milestone 3 fails at the shared-key test and the message says why; swaps between separately keyed tenants still fail, which is exactly why this bug would survive in production for years.
  2. Reuse a nonce on purpose. Change seal to use nonce = bytes(16) when none is given. Everything round-trips and every functional test passes. Only the "two seals of one message differ" test notices. Nonce bugs are invisible to ordinary testing, which is why they need a test that asks the question directly.
  3. Log too much. In KMS.wrap, change the audited context to the DEK's hex. The milestone 2 check finds key bytes in the log. Now picture that line shipped to a log aggregator that dozens of people can read.
  4. Destroy too early. Run the demonstration from milestone 4, but call destroy_version before you take the backup. The backup is fine: it holds version-2 wrapped keys. The failure depends on the order of events, not on the code.
  5. Shred twice. Call shred_tenant("globex") a second time. What exception do you get, and what would you want an operator's runbook to say about running it again after a timeout?

Stretch goals

  • Per-record data keys: change TenantStore to give every record its own DEK, wrapped by the tenant's KEK and stored with the record. Rotation now re-wraps N keys instead of one. What do you gain (a leaked DEK exposes one record), and what does it cost in KMS calls?
  • A DEK cache: keep an unwrapped DEK in memory for a bounded time on a simulated clock, with a size limit. Show the reduction in KMS calls, then show that a shredded tenant stays readable until the cache entry expires. What TTL would you promise a customer?
  • KMS policy: add an allowlist of (caller, key id, operation) triples and refuse everything else, with the refusal in the audit log. The re-wrap job gets rewrap only; the application gets wrap and unwrap; nobody but an administrator gets destroy_key.
  • Scheduled destruction: make destroy_key a two-phase operation with a waiting period on a simulated clock: the key is disabled immediately and can be cancelled until the deadline, after which it is erased. How does that change the promise you can make about deletion time?
  • Real AEAD: if you have pip install cryptography, swap seal and open_ for AESGCM with a 12-byte random nonce and the same associated data. Which of milestone 1's tests still apply unchanged, and which depended on the toy's layout?

Distributed systems connection

A KMS is a small, critical distributed system. Its key table must be replicated for availability and must agree on the current version of every key (the rotation protocol is a case of the version and ordering problems in distributed chapter 5), and a key destruction must reach every replica before you tell a customer their data is gone: one replica that still holds the key bytes is a copy of the secret you meant to erase. Caching unwrapped data keys is the same trade as any cache: the TTL is the time a revoked key still works (compare the leases of distributed chapter 4, where a lease's length is the time a lost holder still believes it holds the lock). And the backup trap of milestone 4 is a general rule of disaster recovery: every dependency of a restore, including the keys, must still exist when the restore happens (data chapter 13 and reliability chapter 18), so key retirement belongs in the same runbook as backup retention.

What you learned

  • An AEAD hides the plaintext, detects any change and binds the result to associated data that is not stored. Build it as encrypt-then-MAC, make the MAC input unambiguous, never repeat a nonce, verify in constant time before decrypting, and fail with one error. The toy shows the shape; production code uses a vetted library.
  • A KMS holds master keys, wraps and unwraps small data keys with an encryption context, and logs every call, refusals included, without ever logging key material.
  • Per-tenant data keys bound by associated data limit the blast radius of a leak, and make a ciphertext valid only where it was written, even if keys are mishandled somewhere.
  • Rotating a master key means re-wrapping data keys, not re-encrypting data. Keep old versions decryptable until nothing needs them, retire in two steps (disable, then destroy), and remember that backups hold wrapped keys that depend on old versions. A leaked data key needs re-encryption, not re-wrapping.
  • Crypto-shredding deletes every copy at once by destroying the one thing every copy depends on, a per-tenant key held outside the backups. Deleting the wrapped key from the live database is not shredding. It makes data unreadable, not absent, and it covers only data that was never stored in plaintext elsewhere.

Check your understanding

Two tenants accidentally end up with the same data key. Why does the lab still insist that put binds record_ad(tenant, record_id) as associated data?

  1. It makes encryption faster
  2. A ciphertext sealed for one tenant or record then fails authentication when an attacker moves it to another slot, even when the keys are equal; the associated data is the second layer for the day the first has a bug
  3. Associated data is encrypted along with the plaintext, which doubles the protection
  4. It lets the database search the ciphertext by tenant
Associated data is authenticated but not stored or encrypted. The tag only verifies when the reader supplies the same tenant and record ids. The check gives two tenants one data key and moves a row between them, and between two records of one tenant; both must fail.

A stream-cipher AEAD seals two different messages with the same key and the same nonce. What goes wrong, and does the authentication tag prevent it?

  1. Nothing: the tag differs, so the messages stay secret
  2. XORing the two ciphertexts removes the keystream and leaves the XOR of the plaintexts; the tag does not help, because nothing is forged, the secrecy is simply gone
  3. The second message is rejected as a replay
  4. Only the first message is damaged
A stream cipher's keystream depends only on key and nonce. The lab shows c1 XOR c2 equal to p1 XOR p2. This is why nonces are generated randomly (and long enough), or by a counter that can never repeat, and why a library that makes nonce reuse hard is worth having.

You rotate a tenant's master key and re-wrap its data key. A week later the security team learns that this tenant's plaintext data key was copied out of an application server's memory a month ago. Is the rotation enough?

  1. Yes: the data key is now wrapped by the new master key
  2. No: the attacker holds the data key itself, so re-wrapping changes nothing for the old records; generate a new data key and re-encrypt the data
  3. Yes, if you also destroy the old master key version
  4. No, but only because the new version is not yet disabled
The wrap protects the data key at rest in the database. A copy taken from memory was never wrapped. Rotation of the master key limits future exposure of wrapped keys; the data encrypted under a leaked data key needs a new data key. This is why data keys have narrow scope.

A team "shreds" a leaving customer by deleting the customer's wrapped data key from the live database. Nightly backups for the past 90 days are kept. What is the actual state of the customer's data?

  1. Unrecoverable everywhere
  2. Unreadable in the live database but fully recoverable from any backup that contains the wrapped key, as long as the master key still exists; destroy the tenant's master key in the KMS instead
  3. Recoverable only from the newest backup
  4. Deleted from the backups automatically at the next rotation
Each backup holds a copy of the ciphertext and a copy of the wrapped key. Deleting one copy of the wrapped key leaves the others, and the master key unwraps them. Destroying the per-tenant master key makes all of them useless at once, which is the point of the design. The check demonstrates both outcomes.

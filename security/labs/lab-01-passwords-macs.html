Lab 1: Passwords, MACs & Timing

Three small building blocks carry most of the weight in everyday authentication: a slow, salted hash for passwords (chapter 5), a keyed MAC for messages that must not be forged (chapter 3), and a comparison that does not leak. In this lab you write all three, then you attack your own comparison with a deterministic model of a timing leak and watch the fix defeat it. You will build a password store whose hashes upgrade themselves on login, HMAC-signed messages with rotating key ids, replay protection on simulated time, and finally the leak and its repair.

Why this lab matters

Almost every real compromise involving these primitives is a usage bug, not a broken algorithm: a fast hash where a slow one belongs, a salt shared by every user, a key that can never be rotated, a signed message that can be recorded and sent again, a tag compared with ==. Each fix is only a few lines, and each is easy to get subtly wrong. The checks here do not only test the happy path; they probe the corners (a hash string with a flipped digit, a nonce arriving exactly at the edge of the window, an unknown user, a retired key) because that is where these systems actually fail.

Only test what you own

Everything in this lab runs in one Python process against code you write yourself. The "attacker" in milestone 5 talks to a toy object in the same program, never to a network service. Timing attacks and password guessing against systems you do not own or are not authorised to test are illegal in most places, and nothing here is a recipe for them: the point is to see the mechanism so that you recognise and prevent it.

Simulated time and a modelled leak, so every run is identical

No milestone sleeps or reads a wall clock. Time is a number held by a SimClock that the check advances by hand. The timing leak of milestone 5 is modelled: the vulnerable comparison increments a counter for every byte pair it looks at, and the attacker reads the counter instead of a stopwatch. That makes the demonstration exact and repeatable, and it also makes it an educational model. Real timing differences are tiny and noisy, and an attacker must average many measurements to see them; the model removes the noise so that the logic of the attack is visible. The logic, not the noise, is what you must learn to recognise.

What you'll build

Five milestones:

  1. A password store: hashlib.scrypt, a fresh random salt per password, the parameters written into the stored string, verification with hmac.compare_digest.
  2. Transparent upgrade: legacy unsalted SHA-256 rows, and scrypt rows with weaker parameters, are re-hashed at the moment of a successful login, with nobody asked to reset anything.
  3. Signed messages: HMAC-SHA256 with a key id (kid) so keys can be rotated, and verification against whichever active key the message names.
  4. Replay protection: a timestamp window plus a nonce cache that expires its entries, run on simulated time.
  5. The timing leak: an early-exit comparison, an attack that recovers a short MAC through it, and the fix.

Milestone 1: a password store

Chapter 5 argued three things about storing passwords, and you will now write all three down in code. First, the stored value must be slow to compute, because after a database leak the attacker's only move is to guess, and a fast hash lets them guess billions of times per second while a memory-hard function like scrypt (Percival, 2009) makes each guess cost real time and memory. Second, it must be salted with a random value unique to each password, so that two users with the same password have different rows and one precomputed table cannot serve every account. Third, it must be self-describing: the algorithm and its cost parameters are written into the stored string, so that you can change the cost next year and still verify the rows written this year.

Your format is $scrypt$ln=14,r=8,p=1$<salt>$<digest>, in the style of the PHC string format that bcrypt, scrypt and Argon2 implementations commonly use. ln is log2 of scrypt's cost parameter N, so ln=14 means N = 16,384, which needs about 16 MiB of memory with r=8. The lab's defaults mirror chapter 5; treat the numbers as a teaching baseline and check the current OWASP Password Storage Cheat Sheet before choosing production parameters.

Verification has two rules that are easy to break. It must read the parameters from the stored string, never from a constant in the code, or the first time you raise the cost every old row stops working. And it must compare digests with hmac.compare_digest, for the reason milestone 5 demonstrates. Anything malformed must return False, never raise: a corrupted row should be a failed login, not a 500 that tells the attacker something is odd.

def hash_password(password: str, policy: Policy = DEFAULT_POLICY) -> str:
    salt = secrets.token_bytes(16)
    dk = _scrypt(password, salt, policy.ln, policy.r, policy.p)
    return f"$scrypt$ln={policy.ln},r={policy.r},p={policy.p}${b64(salt)}${b64(dk)}"

def parse(stored: str):
    try:
        empty, alg, params, salt, dk = stored.split("$")
        if empty != "" or alg != "scrypt":
            raise ValueError("not a scrypt hash")
        kv = dict(item.split("=") for item in params.split(","))
        return Policy(int(kv["ln"]), int(kv["r"]), int(kv["p"])), unb64(salt), unb64(dk)
    except (ValueError, KeyError, TypeError) as e:
        raise ValueError(f"malformed hash: {e}") from None

def verify_password(password: str, stored: str) -> bool:
    try:
        policy, salt, expected = parse(stored)
        actual = _scrypt(password, salt, policy.ln, policy.r, policy.p)
    except ValueError:
        return False
    return hmac.compare_digest(actual, expected)

Milestone 2: transparent hash upgrade

Every real system has old rows. The fictional site in this lab used to store SHA-256(password), unsalted: one fast hash, the same output for the same password everywhere. You cannot convert those rows offline, because the whole point of a hash is that you cannot get the password back. But you do see the password once per user, at the moment they log in successfully. That is the moment to compute a good hash and overwrite the weak one.

The same mechanism upgrades parameters. If next year the policy moves from ln=12 to ln=14, each user's row is rehashed on their next login and the population migrates by itself. Three details decide whether you did this properly. A failed login must never change the row. A hash that is already stronger than the policy must not be downgraded (an operator who lowers a setting by mistake should not silently weaken accounts). And a login for an unknown user should do the same amount of work as a login for a real one, by verifying against a dummy hash; otherwise the response time tells an attacker which usernames exist. (That is a weaker, coarser cousin of the leak in milestone 5, and chapter 5 returns to it under account enumeration.)

def verify_legacy(password: str, stored: str) -> bool:
    if not stored.startswith("$sha256$"):
        return False
    return hmac.compare_digest(legacy_hash(password).encode(), stored.encode())

def needs_rehash(stored: str, policy: Policy) -> bool:
    if stored.startswith("$sha256$"):
        return True
    try:
        have, _, _ = parse(stored)
    except ValueError:
        return True
    return have.ln < policy.ln or have.r < policy.r or have.p < policy.p

def login(self, user: str, password: str) -> bool:
    stored = self.users.get(user)
    if stored is None:
        verify_password(password, self._dummy)   # same work as a real user; result ignored
        return False
    if stored.startswith("$sha256$"):
        ok = verify_legacy(password, stored)
    else:
        ok = verify_password(password, stored)
    if ok and needs_rehash(stored, self.policy):
        self.users[user] = hash_password(password, self.policy)   # only we know the password now
    return ok

Milestone 3: signed messages with key ids

A MAC (chapter 3) proves that a message came from someone holding the key and was not altered; it does not hide the content. Here the message is a payload (bytes) and the token is kid.payload.tag, where the tag is HMAC-SHA256 over the string "kid.payload" (the payload already base64url-encoded). Two design choices matter. The key id is inside what is authenticated, so a token cannot be relabelled with another key's name without the tag failing. And the verifier looks the key up by that id in a ring of keys, so you can add a new key, start signing with it, keep the old one verifying while old messages are still in flight, and finally retire it.

Rotation is the whole reason for the id. A single hard-coded key cannot be replaced without a flag day on which every outstanding message dies. Be careful about what the id is: it is attacker-controlled text. Treat it as a dictionary key and nothing else. Never as a file name, a URL to fetch a key from, or part of a query; Lab 2 attacks a verifier that does exactly that.

Solution spoiler 
def _tag(key: bytes, kid: str, body_b64: str) -> bytes:
    return hmac.new(key, f"{kid}.{body_b64}".encode(), hashlib.sha256).digest()

def sign(ring: Keyring, payload: bytes) -> str:
    kid = ring.signing_kid
    body = b64(payload)
    return f"{kid}.{body}.{b64(_tag(ring.keys[kid], kid, body))}"

def open_message(ring: Keyring, token: str) -> bytes:
    try:
        kid, body, tag = token.split(".")
        key = ring.keys[kid]
        given = unb64(tag)
        payload = unb64(body)
    except (ValueError, KeyError, TypeError):
        raise BadSignature("malformed token or unknown key id") from None
    if not hmac.compare_digest(_tag(key, kid, body), given):
        raise BadSignature("tag does not match")
    return payload

Milestone 4: replay protection

A valid MAC says who and what, not when or how many times. An attacker who records pay 5 to bob, with its perfectly good tag, can send it again tomorrow, and the receiver has no reason to refuse. Two cooperating mechanisms close this. A timestamp inside the signed message bounds how old a message may be. A nonce, a random value used once, makes each message unique within that bound, so the receiver can remember the nonces it has seen and refuse a repeat.

Why both? A nonce alone forces the receiver to remember every nonce forever. A timestamp alone does nothing against a replay inside the window. Together they give a bounded cache: a nonce only has to be remembered until its message could no longer pass the timestamp check anyway, which is ts + window. After that, a replay fails as Stale and the entry can be dropped.

The order of checks is a security property, not a style choice. Authenticate first. If you store nonces before the signature has been verified, an attacker can fill your cache with junk nonces from unsigned messages (a memory-exhaustion attack, and a way to make legitimate messages look like replays). Only a message that passed the MAC may touch your state. The timestamp comparison uses your own clock against the message's claim, so it also assumes clocks that agree within a few seconds; see the distributed-systems connection below.

Solution spoiler 
def receive(self, token: str) -> dict:
    env = json.loads(open_message(self.ring, token))     # 1. authenticate FIRST
    now = self.clock.now()
    self.seen = {n: exp for n, exp in self.seen.items() if exp >= now}   # 2. forget the expired
    if abs(now - env["ts"]) > self.window:                # 3. freshness
        raise Stale(f"timestamp {env['ts']} is outside +/-{self.window}s of {now}")
    if env["nonce"] in self.seen:                         # 4. uniqueness inside the window
        raise Replay(f"nonce {env['nonce']} already used")
    self.seen[env["nonce"]] = env["ts"] + self.window
    return env["body"]

Milestone 5: why == on secrets is risky

Here is a comparison most programmers have written a hundred times:

def check(expected_tag, given_tag):
    return expected_tag == given_tag

Python's == on byte strings may stop at the first byte that differs; that is a perfectly good optimisation when the data is not secret. If given_tag starts with the right first byte, the comparison runs a little longer than if it does not. A guess with two correct bytes runs a little longer still. An attacker who can submit many guesses and measure the response can find the first byte, then the second, and so on, turning a search of 232 possibilities for a four-byte tag into about 4 × 256 guesses. The same logic applies to any secret compared with early exit: MACs, session tokens, API keys, password-reset codes.

What the model leaves out

Real attacks need statistics. Network jitter and scheduling noise are far larger than the time one byte comparison takes, so an attacker must send many repeated requests per guess and average. Published measurements (for example Crosby, Wallach and Riedi, 2009) showed that differences of a few microseconds are still measurable across a network with enough samples, and attacks on local code, co-tenants on shared hardware and embedded devices are much easier. Defenders should therefore not argue "it's too noisy to matter". They should do the cheap, correct thing: compare secrets with hmac.compare_digest, which is designed so that its running time does not depend on where the inputs differ. (It still reveals the length of a mismatch; MACs and tokens have public fixed lengths, so this does not matter for them.) Better still, make the secret useless to guess: a full 32-byte HMAC tag is out of reach even for a perfect oracle. This lab truncates the tag to four bytes only so that the attack finishes in a moment.

The exploit is the central exercise of this milestone and is deliberately small. The target, MacServer, is given: it holds a four-byte truncated tag and exposes oracle(guess), which returns whether the guess was accepted and how many steps the comparison took. You write the comparator that leaks, the attack that uses the leak, and the comparator that does not.

Hints try without first
  • leaky_equal adds 1 to meter.steps before each byte comparison and returns False at the first mismatch. A different length counts one step and is False.
  • recover_tag: for each position, try 256 candidates. Build each guess as the bytes found so far, then the candidate, then zero padding. Remember the candidate with the largest work. If ok comes back True, return immediately.
  • The last byte is the special case: the right candidate is accepted outright, so you never need to compare its work.
  • constant_equal: meter.steps += max(len(a), len(b)) unconditionally, then return hmac.compare_digest(a, b).
Solution spoiler 
def leaky_equal(a: bytes, b: bytes, meter: Meter) -> bool:
    if len(a) != len(b):
        meter.steps += 1
        return False
    for x, y in zip(a, b):
        meter.steps += 1
        if x != y:
            return False              # early exit: the amount of work reveals where they differ
    return True

def constant_equal(a: bytes, b: bytes, meter: Meter) -> bool:
    meter.steps += max(len(a), len(b))   # model: the work does not depend on the contents
    return hmac.compare_digest(a, b)

def recover_tag(oracle, tag_len: int):
    known, queries = b"", 0
    for pos in range(tag_len):
        best, best_work = 0, -1
        for cand in range(256):
            guess = known + bytes([cand]) + bytes(tag_len - pos - 1)
            ok, work = oracle(guess)
            queries += 1
            if ok:
                return guess, queries
            if work > best_work:
                best, best_work = cand, work
        known += bytes([best])
    return known, queries

Try it yourself: three experiments

  1. Make the tag longer. Pass tag_len=8 to MacServer and call recover_tag(oracle, 8). The queries grow linearly (8 × 256), not exponentially. Then reason about a 32-byte tag. Leakage turns a search that was exponential in the tag length into one that is linear: that is why a leak is serious even when the secret is long.
  2. Add noise. Wrap the oracle so that work has a random number from random.Random(1) added to it. How many repeated queries per guess does your attack now need to pick the right byte reliably? You have just rebuilt the statistics that a real attacker needs.
  3. Leak through a different channel. Imagine the server returns "bad tag" for a mismatch in byte 1 and "bad tag (check digit)" for a mismatch elsewhere. Which of your code's lines would you change to attack it? Error messages, status codes and response sizes are all channels.

Stretch goals

  • Argon2-style choice: write a needs_rehash that also understands a second algorithm ($pbkdf2-sha256$..., built with hashlib.pbkdf2_hmac) and migrates it to scrypt. What must the stored string contain for that to work?

Distributed systems connection

Replay protection is a distributed-systems problem wearing a security hat. The timestamp window assumes the two clocks agree to within a few seconds; the lab's SimClock is one clock, but with two real machines you inherit all of the drift and skew of distributed chapter 4, and the window is exactly a drift allowance. The nonce cache must be shared by every replica that can receive the message, or an attacker simply replays to a different server (the state-sharing problem of rate limiting, architecture chapter 9). And a key ring has the same rollout problem as any configuration: during rotation some servers know the new key and some do not, which is why the overlap period exists.

What you learned

  • Password storage is: slow and memory-hard, a fresh random salt per password, parameters inside the stored string, and a constant-time compare. Verification must read the parameters from the string, not from code.
  • Old hashes are upgraded at the only moment you hold the plaintext, a successful login, and never on a failed one. Parameters are upgraded the same way, and never downgraded. Unknown users should cost the same as known ones.
  • A MAC token should name its key (kid), authenticate that name, look the key up in a ring as a plain dictionary key, and tolerate an overlap period during rotation.
  • A MAC alone does not stop replay. A timestamp bounds age, a nonce gives uniqueness inside the window, and the cache needs to live exactly until ts + window. Authenticate before touching state.
  • Early-exit comparison leaks the length of the matching prefix; an attacker who can observe that turns an exponential search into a linear one. hmac.compare_digest removes the signal, and the best defence also makes the secret long enough that even a leak would not matter.

Check your understanding

A site's password table leaks. Every row is SHA-256(password), unsalted. Why is this worse than a table of salted scrypt hashes, and what is the right migration?

  1. It is no worse: SHA-256 is a secure hash
  2. Fast hashes allow billions of guesses per second and identical passwords share a row, so a precomputed table cracks many accounts at once; migrate by rehashing with scrypt at each user's next successful login
  3. Run SHA-256 again over every row and keep it as the new value
  4. Force every user to reset their password immediately and delete the table
SHA-256 is secure as a hash but wrong as a password hash: it is fast, and without a salt equal passwords give equal rows. You cannot convert rows offline because the plaintext is gone; at a successful login you hold it once. Rehashing the old hash with a better one would still leave the weak hash as the input. A forced reset is a valid emergency measure but is not transparent.

In PasswordStore.login, why must the upgrade happen only after the old hash verified, and why is an unknown user hashed against a dummy?

  1. Verification is cheap; the dummy saves memory
  2. After a failure you do not know the password, so you would store a hash of an attacker's guess; the dummy makes unknown users cost the same as real ones so response time does not reveal which usernames exist
  3. The dummy is needed because scrypt cannot run without a stored salt
  4. The upgrade must come first so that the verification uses the new parameters
Overwriting the row on a failed login lets anyone lock the owner out. The dummy hash is about equalising work between the 'no such user' and 'wrong password' paths.

A receiver purges a nonce from its cache at ts + 10 although the window is 30 seconds. What can an attacker do?

  1. Nothing: a replay after the purge fails the signature check
  2. Replay the recorded message between ts+10 and ts+30: the signature is valid, the timestamp is inside the window and the nonce is forgotten, so it is accepted a second time
  3. Forge new messages with a chosen timestamp
  4. Make the cache grow without bound
The nonce must be remembered at least until the timestamp check would refuse the message by itself, i.e. ts + window. That is exactly what the checkpoint in the lab tests at ts+29, ts+30 and ts+31.

An early-exit comparison is used to check a 4-byte MAC. What does the attacker need, and how much work does the attack take?

  1. Nothing but the ciphertext; 232 guesses
  2. A way to submit guesses and observe either time or work; about 4 × 256 guesses, because each byte is found independently of the later ones
  3. The HMAC key; one guess
  4. A faster computer than the server; 216 guesses
The leak lets the attacker confirm one byte at a time. In the lab: 781 queries instead of about 231 on average. compare_digest removes the signal, and with it the attack.

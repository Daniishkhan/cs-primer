Lab 3: OAuth with PKCE, Simulated

OAuth 2.0 is a protocol for letting an application act on a user's behalf without learning the user's password, and almost every serious flaw in a deployment is a missing check in one of four places: the redirect address, the callback, the code exchange, and the token's use. Chapter 7 walked through these checks as pure functions. In this lab you build the actors themselves, all in one process: an authorization server, a client, a resource server and a simulated browser that carries redirects. Then you attack your own implementation five ways and see exactly which defence stops each one.

Why this lab matters

OAuth bugs are rarely cryptographic. They are sequencing and matching bugs: a redirect address compared by prefix, a state value never checked, a code that works twice, a token accepted by an API it was never meant for. Each defence is a single comparison, which is exactly why each is so often forgotten, and why the order and ownership of those comparisons (who generates what, who checks what, in which channel) is the thing to learn. Building a tiny protocol with every check optional lets you switch a defence off and watch the matching attack succeed. Then you will never again wonder why the specification insists on something that seems fussy.

Only test what you own

All the actors in this lab are Python objects. The "malicious app" is a class in the same program, the "attacker's website" is an object that records requests, and nothing here opens a socket. The attacks demonstrate vulnerability classes described in public standards so that you can recognise and prevent them in systems you build or are authorised to test. Do not use these techniques against anyone else's login flow.

A model, not a product

The simulated browser follows redirects, keeps cookies per site and can deliver custom-scheme URLs to installed apps. The authorization server has no login page or consent screen: whoever holds its session cookie is logged in and consents to what the client registered for. Tokens are HMAC-signed JSON, with the key shared between the authorization server and the resource server for simplicity; a real deployment would use asymmetric signatures (so the API cannot mint tokens) and would publish keys. Time is a simulated clock. None of that changes where the security checks live, which is the point.

What you'll build

Five milestones:

  1. The authorization code flow: exact redirect_uri matching; codes that are single-use, expire after 60 seconds and are bound to the client and redirect they were issued for.
  2. State: the client's CSRF protection on the callback.
  3. PKCE with S256: verified against the RFC 7636 appendix B example.
  4. Tokens, scopes and audience: access tokens carrying scopes and an audience, enforced by the resource server.
  5. The attack suite: code interception by a malicious app, a tampered redirect, CSRF login, code replay and scope escalation. You write the interception app and the redirect forger; the check runs every attack twice, once with its defence switched off (it must work) and once against the full solution (it must fail, and the check names the defence that stopped it).

The weak switches

Each actor takes a weak set: names of defences to skip. It exists for one reason, the control experiments of milestone 5, which must show that each attack really works when its defence is off. Your code should skip a defence only if its name is in weak (for example "pkce", "state", "redirect", "single_use", "scope", "rs_scope", "aud"), and should leave it on otherwise. In a production implementation there is no such switch; here it is the instrument that makes the attack suite scientific.

How the pieces talk

Browser.open(url) sends a GET to a mounted site, applies any cookies it sets, and follows redirects. Each site has handle(path, params, cookies) and returns a Response (status, location, body, cookies). The two back-channel calls, AuthorizationServer.token(params) and ResourceServer.handle(...), are direct method calls, because in reality they travel server to server and never through the user's browser. Errors are OAuthError(code, detail, defence); the defence label is how the check knows which of your checks fired.

Milestone 1: the authorization code flow

The authorization server (AS) does two jobs. At /authorize it identifies the logged-in user, decides whether the request is acceptable and, if so, redirects the browser back to the client with a short-lived authorization code. At the token endpoint the client exchanges that code, directly, for an access token. The code is a throwaway voucher: it travels through the browser, so it must be useless on its own, and that is where all of this milestone's rules come from.

Exact redirect_uri matching. The client registers one or more redirect URIs in advance. A request naming any other is refused with an error page, not a redirect, because the address is exactly the thing that is not yet trusted. Compare as plain strings: no prefixes, no case folding, no trailing-slash tolerance, no wildcards. Every "helpful" rule here has been exploited. A prefix check on https://app.example accepts https://app.example.evil.example/cb; a check on a substring accepts https://evil.example/?https://app.example/cb. (RFC 9700, the OAuth security best current practice published in 2025, requires exact matching of redirect URIs for this reason.)

Single use, expiry, binding. A code works once; the check "already used" must fire and the first attempt must burn the code whether or not it succeeded, so that a wrong guess cannot be retried. It expires quickly (60 seconds here). It is bound to the client_id and the redirect_uri of the request that created it, and the token request must repeat the same redirect_uri, so a code cannot be redeemed by another client or against another address.

def redirect_ok(self, client_id: str, uri: str) -> bool:
    registered = self.clients[client_id]["redirect_uris"]
    if "redirect" in self.weak:                       # the sloppy rule: a string prefix of the origin
        return any(uri.startswith(r.rsplit("/", 1)[0]) for r in registered)
    return uri in registered                          # exact string match, nothing cleverer

def authorize(self, user, params: dict) -> str:
    client_id, uri = params.get("client_id"), params.get("redirect_uri", "")
    if client_id not in self.clients:
        raise OAuthError("invalid_client", "unknown client", "client")
    if not self.redirect_ok(client_id, uri):
        raise OAuthError("invalid_request", "redirect_uri is not registered", "redirect")
    if params.get("response_type") != "code":
        raise OAuthError("unsupported_response_type", "only the code flow is offered", "client")
    if user is None:
        raise OAuthError("login_required", "nobody is logged in at the authorization server", "client")
    scope = self._grant_scope(client_id, params.get("scope", ""))
    challenge = self._read_challenge(params)
    code = secrets.token_urlsafe(16)
    self.codes[code] = {"client_id": client_id, "redirect_uri": uri, "user": user, "scope": scope,
                        "challenge": challenge, "expires": self.clock.now() + self.CODE_TTL, "used": False}
    query = {"code": code}
    if "state" in params:
        query["state"] = params["state"]
    return uri + ("&" if "?" in uri else "?") + urlencode(query)

def token(self, params: dict) -> dict:
    if params.get("grant_type") != "authorization_code":
        raise OAuthError("unsupported_grant_type", "", "client")
    rec = self.codes.get(params.get("code"))
    if rec is None:
        raise OAuthError("invalid_grant", "unknown code", "code")
    if rec["used"] and "single_use" not in self.weak:
        raise OAuthError("invalid_grant", "code was already used", "single_use")
    rec["used"] = True                                # burn it on the FIRST attempt, right or wrong
    if self.clock.now() >= rec["expires"]:
        raise OAuthError("invalid_grant", "code expired", "expiry")
    if params.get("client_id") != rec["client_id"]:
        raise OAuthError("invalid_grant", "code was issued to another client", "client")
    if params.get("redirect_uri") != rec["redirect_uri"]:
        raise OAuthError("invalid_grant", "redirect_uri differs from the authorization request", "redirect")
    self._check_pkce(rec, params.get("code_verifier"))
    scope = rec["scope"]
    if "scope" in params:                             # narrowing is fine; broadening is escalation
        asked = params["scope"].split()
        if not set(asked) <= set(rec["scope"].split()) and "scope" not in self.weak:
            raise OAuthError("invalid_scope", "more than was authorized", "scope")
        scope = " ".join(asked)
    now = self.clock.now()
    claims = {"iss": AS_ORIGIN, "sub": rec["user"], "aud": self.audience, "scope": scope,
              "client_id": rec["client_id"], "iat": now, "exp": now + self.TOKEN_TTL, "jti": secrets.token_hex(8)}
    return {"access_token": sign_token(self.key, claims), "token_type": "Bearer",
            "expires_in": self.TOKEN_TTL, "scope": scope}

Milestone 2: state, the callback's CSRF defence

A cross-site request forgery (CSRF) makes a victim's own browser send a request the victim did not intend, relying on the browser to attach credentials automatically. The OAuth callback, https://app.example/cb?code=..., is such a request: it carries no proof that this browser started this login. An attacker can therefore log in at the AS with his own account, stop just before the redirect so that his code is not spent, and send the callback URL to the victim (in a link, an image tag, a redirect). The victim's browser delivers the attacker's code to the client together with the victim's session cookie. A client that does not check completes the login, and now the victim's session is signed in as the attacker. The victim may upload documents, link a card or tell secrets to an account the attacker controls.

The fix is a random state value. When the client starts a login it generates a fresh, unguessable state, stores it in the user's session (not in the URL alone), and sends it through the AS, which returns it unchanged. On the callback the client compares the returned state with the one stored for this session, in constant time, and refuses a mismatch or a missing value. The pending login is also one-shot: it is removed when the callback arrives, so the same callback cannot be played twice. Notice where the check lives: in the client, before the code is spent at the token endpoint. The AS cannot do this check, because it does not know which browser session at the client started the flow.

def start(self, sid: str) -> str:
    params = {"response_type": "code", "client_id": self.client_id, "redirect_uri": self.redirect_uri,
              "scope": self.scope}
    pend = {}
    if "state" not in self.weak:
        pend["state"] = secrets.token_urlsafe(16)
        params["state"] = pend["state"]
    if "pkce" not in self.weak:
        pend["verifier"], challenge = self._pkce_new()
        params.update(code_challenge=challenge, code_challenge_method="S256")
    self.pending[sid] = pend
    return AS_ORIGIN + "/authorize?" + urlencode(params)

def finish(self, sid, params: dict) -> dict:
    pend = self.pending.pop(sid, None)                 # one-shot: a callback can only be used once
    if "error" in params:
        raise OAuthError(params["error"], params.get("error_description", ""), "client")
    if "state" not in self.weak:
        if pend is None or not hmac.compare_digest(pend["state"], params.get("state", "")):
            raise OAuthError("invalid_request", "state does not match this session: possible CSRF", "state")
    pend = pend or {}
    form = {"grant_type": "authorization_code", "code": params.get("code"), "redirect_uri": self.redirect_uri,
            "client_id": self.client_id}
    if pend.get("verifier"):
        form["code_verifier"] = pend["verifier"]
    tok = self.as_.token(form)
    self.tokens[sid] = tok
    return tok

Milestone 3: PKCE with S256

State protects the client from an attacker's code. A different attack aims the other way: stealing a legitimate user's code. If a code is delivered through a channel where another party can read it, whoever reads it can try to redeem it. For a web app with a server-side secret that is hard, because redeeming also requires the secret. But a public client (a mobile or desktop app, or a single-page app) cannot keep a secret, so its client_id is public and the code alone would be enough. The classic case is a custom URL scheme such as myapp://cb: more than one app on a device can register it, and the operating system, not the authorization server, picks which one receives the redirect.

Proof Key for Code Exchange (PKCE, RFC 7636, pronounced "pixie") gives a public client a one-time secret. Before the redirect, the client makes a random code_verifier and sends only its hash, the code_challenge = base64url(SHA-256(verifier)), in the authorization request. The AS stores the challenge with the code. At the token endpoint the client sends the verifier; the AS hashes it and compares. An attacker who intercepted the code but never saw the verifier (which never left the client, and which cannot be recovered from the hash) cannot redeem it.

Four rules make PKCE work rather than merely exist. Accept only S256; the older plain method sends the verifier itself as the challenge, so anything that sees the authorization request also sees the verifier, and allowing it lets an attacker downgrade the request. Require PKCE for public clients: if the challenge is optional, an attacker simply omits it from a request that he controls. Check the verifier's format (43 to 128 characters from an unreserved set, which a 32-byte random value base64url-encoded satisfies exactly). And compare in constant time. RFC 9700 recommends PKCE for all OAuth clients using the code flow, not only public ones.

def make_verifier() -> str:
    return b64u(secrets.token_bytes(32))                       # 43 characters

def s256_challenge(verifier: str) -> str:
    return b64u(hashlib.sha256(verifier.encode("ascii")).digest())

def _read_challenge(self, params: dict):
    challenge, method = params.get("code_challenge"), params.get("code_challenge_method")
    if challenge is None:
        if "pkce" in self.weak:
            return None
        raise OAuthError("invalid_request", "PKCE is required: code_challenge is missing", "pkce")
    if method != "S256":
        raise OAuthError("invalid_request", "only code_challenge_method=S256 is accepted", "pkce")
    if not re.fullmatch(r"[A-Za-z0-9_-]{43}", challenge):
        raise OAuthError("invalid_request", "malformed code_challenge", "pkce")
    return challenge

def _check_pkce(self, rec: dict, verifier) -> None:
    if rec["challenge"] is None:
        if "pkce" in self.weak:
            return
        raise OAuthError("invalid_grant", "no challenge on record", "pkce")
    if not isinstance(verifier, str) or not VERIFIER_RE.fullmatch(verifier):
        raise OAuthError("invalid_grant", "code_verifier missing or malformed", "pkce")
    if not hmac.compare_digest(s256_challenge(verifier), rec["challenge"]):
        raise OAuthError("invalid_grant", "code_verifier does not match the challenge", "pkce")

def _pkce_new(self):
    verifier = make_verifier()
    return verifier, s256_challenge(verifier)

Milestone 4: scopes and audience at the resource server

A token that merely proves "some user logged in" is almost useless; it has to say what the holder may do and to whom it may be shown. A scope is a short string naming a class of permission (read, write, admin). The user (here: the client's registration) grants a set of scopes; the token carries them; the resource server (RS, the API) enforces them at each endpoint. The audience (aud) names the API the token is for. Both are enforced by the party that does the work, because the authorization server is not in the request path.

The two checks answer different questions and fail differently. A token for another API is not a valid credential here at all (HTTP 401, invalid_token): accepting it lets a token obtained for a low-risk service be replayed against a high-risk one. A token for this API that lacks the scope for this endpoint is a valid credential asking for too much (HTTP 403, insufficient_scope). Scope matching is by whole word: a token whose scope is reader or unread does not satisfy read, and treating the claim as a substring is a bug that has happened.

On the authorization side, the AS enforces its half: an authorization request may ask only for scopes the client is registered for (an empty request is refused too), and the token request may narrow the granted scope but never broaden it. The first prevents a client from escalating by asking; the second prevents an attacker who holds a code from adding scopes to the token request.

def authenticate(self, headers: dict, needed: str) -> dict:
    auth = headers.get("Authorization", "")
    scheme, _, token = auth.partition(" ")
    if scheme.lower() != "bearer" or not token:
        raise OAuthError("invalid_token", "send  Authorization: Bearer <token>", "signature")
    claims = open_token(self.key, token, self.clock.now())
    if "aud" not in self.weak:
        aud = claims.get("aud")
        if self.audience not in (aud if isinstance(aud, list) else [aud]):
            raise OAuthError("invalid_token", "this token was issued for a different API", "aud")
    if "rs_scope" not in self.weak and needed not in str(claims.get("scope", "")).split():
        raise OAuthError("insufficient_scope", f"this endpoint needs scope '{needed}'", "rs_scope")
    return claims

def _grant_scope(self, client_id: str, requested: str) -> str:
    asked = requested.split()
    allowed = set(self.clients[client_id]["scopes"].split())
    if "scope" in self.weak:
        return " ".join(asked)
    if not asked or not set(asked) <= allowed:
        raise OAuthError("invalid_scope", "scope is empty or not registered for this client", "scope")
    return " ".join(sorted(set(asked)))

Milestone 5: the attack suite

Now put every defence under attack. The method matters as much as the result: for each attack the check runs it twice. First against a deployment with exactly the relevant defence switched off, where it must succeed (otherwise the exploit is not a real exploit, and a test that never succeeds proves nothing). Then against the full solution, where it must fail, and the failure must come from the intended defence, named by the defence label on the error. That is the discipline of a good regression test for a security control: show that it fires, and show what happens without it.

You write two pieces of the attacker's toolkit; the check writes the rest.

  • MaliciousApp is the second app on the device. The simulated browser delivers myapp://cb?code=... to the last app installed for that scheme, the way a real operating system may resolve a clash, and the honest app never sees it. The malicious app records the redirect, then tries to redeem the code with only what it can know: the code, the public client_id and the registered redirect.
  • tampered_authorize_url builds the link an attacker sends to a victim who is logged in at the AS: a genuine authorization request with redirect_uri swapped for an address the attacker controls.

Your task

Solution spoiler 
def on_redirect(self, url: str):
    self.stolen = dict(parse_qsl(urlsplit(url).query))
    return Response(200, None, {"ok": "(looks like nothing happened)"}, {})

def redeem(self) -> dict:
    return self.as_.token({"grant_type": "authorization_code", "code": self.stolen["code"],
                           "redirect_uri": self.redirect_uri, "client_id": self.client_id})

def tampered_authorize_url(client_id: str, evil_redirect_uri: str, scope: str, state: str = "x", challenge: str = None) -> str:
    q = {"response_type": "code", "client_id": client_id, "redirect_uri": evil_redirect_uri, "scope": scope, "state": state}
    if challenge:
        q.update(code_challenge=challenge, code_challenge_method="S256")
    return AS_ORIGIN + "/authorize?" + urlencode(q)

Study three rows.

Interception. With PKCE off the malicious app gets a working token and calls the API as the user. With PKCE on it fails at the token endpoint: it has the code and the public client_id, and neither is a secret. The same defence keeps working even if the operating system, the browser history or a proxy leaks the code.

Tampered redirect. PKCE is on in the control run, and the attack still succeeds, because the attacker generated the challenge himself and holds the matching verifier. This is the reason the defences are separate: PKCE protects against code theft by a party that did not start the flow, exact redirect matching protects against the flow being started on the attacker's behalf. Neither covers the other.

CSRF login. In the full solution the state check fires first (the table's "stopped by" column). PKCE would also have stopped this attack, because the victim's session never made the attacker's challenge. That is defence in depth working, and RFC 9700 notes the overlap, but the attack suite deliberately removes both in the control to show that the state check is not decoration.

Stretch goals

  • Consent: add a consent screen as a callback the user can decline or narrow. Where is the grant stored, and how does a later refresh or a second client interact with it?
  • OpenID Connect: add an id_token and a nonce to the authorization request, and verify the nonce binds the token to the session. What attack does it add to the ones here (chapter 7)?
  • Client secrets: add a confidential client that authenticates with a secret at the token endpoint. Show that PKCE is still worth sending.
  • Refresh tokens: bolt the rotation and reuse detection of Lab 2 onto token().
  • Revoke on replay: RFC 6749 suggests revoking tokens already issued from a code when it is presented a second time. Implement a denylist the resource server consults and weigh the cost against the short token lifetime.
  • Exact matching with loopback: native apps often use http://127.0.0.1:PORT/cb with a changing port. Read what RFC 8252 says about exact matching for loopback redirects and decide how to allow the port to vary safely.

Distributed systems connection

Every property here is a statement about who knows what, and when, across machines that cannot see each other. A single-use code is an at-most-once token, and it only holds if the "mark as used" step is atomic with the check; in a replicated authorization server two nodes can each honour the same code unless the store gives a compare-and-swap, the same hazard as a duplicated message in networking chapter 16. A 60-second expiry is a lease on a clock, with all the skew caveats of distributed chapter 4. And a resource server that validates tokens locally is a cache of an authorization decision: its staleness is the token lifetime.

What you learned

  • Authorization codes are throwaway vouchers: single use (burned by the first attempt), short-lived, and bound to the client and redirect they were issued for.
  • Redirect URIs are matched exactly, as strings, and a mismatch is an error page, never a redirect.
  • state binds the callback to the browser session that began the login; it is checked by the client, before the code is spent, and is one-shot.
  • PKCE binds the code exchange to the client instance that began the flow: the verifier stays on the back channel, only S256 is accepted, and it is required. It stops code theft by a party that did not start the flow; exact redirect matching stops a flow started on the attacker's behalf.
  • The resource server checks signature and expiry, then audience (is this for me?), then scope (is this enough?), by whole words, with distinct failures. The authorization server limits what can be requested and never lets a token request broaden a grant.
  • A good security test shows the defence firing and the attack succeeding without it.

Check your understanding

An authorization server matches redirect_uri by checking that it starts with the registered value https://app.example. What can an attacker do?

  1. Nothing: the request still goes to app.example
  2. Register or use https://app.example.evil.example/cb, which starts with the registered string but is a different host, and receive the victim's authorization code there
  3. Change the scopes
  4. Only break the client's login page
A prefix is not a boundary. Exact string comparison of the whole URI is the only rule with no gaps. The lab's redirect control uses this sloppy rule and the attack gets a token.

Which attack does state stop, which does PKCE stop, and why are both needed?

  1. State stops code theft, PKCE stops CSRF; either is enough
  2. State binds the callback to the browser session that started the login (CSRF login); PKCE binds the code exchange to the client that started the flow (stolen codes). They protect against different parties, and an attacker-started request defeats PKCE while a stolen code does not defeat state
  3. They are the same defence under two names
  4. State protects the token, PKCE protects the redirect
In the suite the tampered-redirect attack succeeds with PKCE on (the attacker chose the challenge himself) and is stopped only by exact matching; interception is stopped only by PKCE; CSRF login by state (with PKCE as a second line).

A malicious app registers the same custom URL scheme as the honest app and receives the redirect with ?code=.... Why can it not turn the code into a token when PKCE is used?

  1. The code expires instantly
  2. It does not know the code_verifier, which was never sent through the redirect, and the verifier cannot be derived from the challenge
  3. The authorization server checks the app's signature
  4. The operating system forwards the code to the real app first
The challenge is a one-way hash of the verifier; the verifier stays in the honest client and travels only on the back channel. Public clients cannot hold a client secret, which is exactly why PKCE exists.

A token with audience https://billing.example is presented to the notes API (https://api.example) and is otherwise perfectly valid. What should the API do and why?

  1. Accept it: the signature is valid
  2. Reject it with 401: a token is only a credential for the audience it names, otherwise a token obtained for one service can be replayed against another
  3. Accept it if the scope matches
  4. Reject with 403 insufficient_scope
Audience restriction limits the blast radius of a leaked or over-shared token. Scope mismatch (403) is a different failure: a valid credential for this API that asks for too much.

Lab 4: A Relationship-Based Authorization Engine

Chapter 8 ended with a twenty-line sketch of a relationship check. In this lab you grow it into a small engine you could put behind a real API. You start with roles and watch them explode. You store permissions as relation tuples, add the two rewrite rules that make a relationship model expressive (editors are viewers; documents inherit from their folder), make the recursive check safe against cycles and runaway depth, and teach it to explain itself for audit. Then you point it at the most common vulnerability in real APIs: a handler that loads whatever id it is given. You fix that by sending every access through the check, against a suite that attacks across users and across tenants.

Why this lab matters

Broken access control is the first category of the OWASP Top 10 (chapter 8), and the form that does the most damage in APIs is the missing object-level check: the code authenticates the caller, then loads the record whose id appears in the request. Nothing fails in testing, because every test uses the owner's own ids. The bug is silent, and it is found by someone who changes one number in a URL. The defence is structural rather than clever: a model in which "who can do what to this object?" has one definition, one place in the code that answers it, and an answer that can be explained afterwards. That is what you build here, in the shape Google's Zanzibar made popular (Pang et al., USENIX ATC 2019): relation tuples, a small schema of rewrite rules, and a check.

Only test what you own

The attacks in milestone 5 are aimed at the deliberately vulnerable App that lives inside this lab, in one Python process, with data the check itself creates. They exist to teach you to write the tests that would have caught the bug. Probing other people's APIs by changing ids is unauthorised access in most places, whatever the intent; test only systems you own or have written permission to test.

Deterministic by construction

Everything lives in memory. The graph in milestone 3 is checked against an independent oracle (a slow fixpoint computation that shares no code with yours) on 150 random worlds produced from a fixed seed, so a wrong rule shows up as a named tuple set and the same run repeats exactly. Tuple sets are always iterated in sorted order, which is why subjects returns a sorted list: an engine whose answers depend on hash order would be impossible to test or to audit.

What you'll build

Five milestones:

  1. RBAC, and role explosion: roles to permissions, then a test that shows what happens to the number of roles when sharing is per document.
  2. Relation tuples: object#relation@subject, a strict parser, a tuple store and a direct check.
  3. Userset rewrites: computed usersets and tuple-to-userset, a recursive check with a depth bound and a visited set, tested against an oracle.
  4. Explain and expand: the path that granted access, and the list of everyone who has it.
  5. An API with an IDOR: five buggy handlers, one choke point, sixteen attacks across users and tenants, and an audit log.

Milestone 1: RBAC, and why it explodes

Role-based access control, from chapter 8, is one level of indirection: users hold roles, roles carry permissions (plain strings such as write:d7), and a check asks whether any of the user's roles carries the permission. Adding an employee is one assignment; changing what editors may do is one edit. For job functions it is excellent, and you should use it for them.

Its weakness is that a role is global and an object is not. "Editor" says nothing about which document. The usual patch is to make the role carry the object: editor:d7, viewer:d7. That works, and it is also where the trouble starts, because now every document that is shared adds roles to the policy. If each of 40 documents has an editor and a viewer, you maintain 80 roles; with a thousand documents, two thousand; and nobody can review them, because they are not policy any more, they are data wearing a policy's clothes. This is role explosion.

The check for this milestone makes the explosion a number, not an opinion: it builds the same sharing pattern at 10, 20 and 40 documents and requires the role count to be exactly 2n, then asserts that sharing one document does not leak to another.

def allowed(self, user, perm):
    return any(perm in self.role_perms.get(r, ()) for r in self.user_roles.get(user, ()))

def rbac_for_sharing(shares):
    rbac = RBAC()
    for user, doc, level in shares:
        role = f"{level}:{doc}"
        rbac.grant(role, f"read:{doc}")
        if level == "editor":
            rbac.grant(role, f"write:{doc}")
        rbac.assign(user, role)
    return rbac

Milestone 2: relation tuples and a direct check

Relationship-based access control replaces "does a role carry this permission?" with "does a path of the right kind connect this user to this object?". The facts are stored as relation tuples, written object#relation@subject. The object is a typed id such as doc:plan. The relation is a name such as editor, viewer or parent. The subject is either a user, such as user:alice, or a userset: "everyone who has relation R on object O", written group:eng#member. The userset is what lets one tuple say "every member of the engineering group may view this folder" without listing the members, and without changing when a member joins.

Three engineering points hide in this small milestone.

Parse strictly, and fail closed. A parser that accepts doc:plan#editor@user:alice garbage is a policy store that accepts garbage. Use re.fullmatch with the given TUPLE_PATTERN. The tempting alternative, re.match(r"^...$", text), has a classic trap: in Python, $ also matches just before a trailing newline, so "doc:plan#editor@user:alice\n" would be accepted. The check tries exactly that string. (Chapter 9's lesson in miniature: validation is only as good as its exactness.)

Sets, not lists. Adding the same tuple twice must change nothing; removing a tuple that is not there is not an error. Both make grant and revoke idempotent, which matters the moment these operations are retried over a network.

Sorted output. subjects returns a sorted list. The engine will iterate it, and the path it finds when several exist must be the same every run, or an audit log that says "allowed via X" yesterday and "via Y" today would be a puzzle for the reader.

def parse_tuple(text):
    m = re.fullmatch(TUPLE_PATTERN, text)
    if m is None:
        raise ValueError(f"not a relation tuple: {text!r}")
    return Tup(*m.groups())

def add(self, t):
    t = self._coerce(t)
    self._by_key.setdefault((t.obj, t.rel), set()).add(t.subject)

def subjects(self, obj, rel):
    return sorted(self._by_key.get((obj, rel), ()))

def check_direct(store, obj, rel, user):
    return user in store.subjects(obj, rel)

Milestone 3: userset rewrites, bounded depth, cycle safety

If the engine only matched stored tuples, every editor would need a second tuple making them a viewer, and every document in a folder would need a copy of the folder's viewers. The tuples would be huge and would drift out of date. Zanzibar's answer is to put the policy in a small schema of userset rewrite rules and keep only the facts as tuples. The lab's schema (given as DEFAULT_SCHEMA) uses three kinds of rule:

  • this: tuples stored directly on obj#rel. A subject that is a userset is followed: "is the user in group:eng#member?" is a new question about another object.
  • computed userset ("computed", rel2): whoever has rel2 on the same object also has this relation. doc#viewer includes doc#editor, which includes doc#owner; so an owner is a viewer with no extra tuples.
  • tuple-to-userset ("ttu", via, rel2): follow the tuples obj#via@P to each parent object P, then ask whether the user has rel2 on P. doc#viewer includes parent#viewer, so a document inherits its folder's viewers, and a folder inherits from its own parent, as deep as folders nest. Only viewer is inherited in this schema: being able to read a folder does not let you edit its documents. What flows down is a decision of the schema, not of the engine.

The search is a depth-first recursion, and it needs two separate protections, because they guard against different things.

First, a visited set: remember every (object, relation) you have started to evaluate within this query, and do not evaluate it again. Groups can contain each other in a ring (a mistake, but one that a real user will eventually make), and folders can be moved under their own descendants. Without the set, a ring is an infinite recursion. The set has a second, quieter job: it keeps the search linear. A directory tree where every level has two paths to the next has 222 routes after 22 levels; the check builds exactly that ladder and counts store lookups. A search that revisits nodes would make four million of them. This shortcut is sound here because every rule only adds ways to get access: if a node was explored and did not contain the user, exploring it again cannot. (Zanzibar can also express intersection and exclusion, "viewer but not blocked". With those, a node being evaluated cannot simply count as "no", and real implementations evaluate more carefully. The lab keeps to unions; the stretch goals return to this.)

Second, a depth bound. The visited set makes the search terminate, but not quickly: a chain of 3,000 nested groups is a legitimate but absurd input, and a recursion that follows it is a Python stack overflow or a request that takes seconds. A bound of 16 levels is generous for real organisations and cheap to enforce. Choose the failure mode on purpose: the engine raises DepthExceeded, and the caller treats it as deny. Failing closed means a pathological tenant can lock itself out, which is an incident you can see and fix; failing open would let it into data that was never granted.

Solution spoiler 
def _check(self, obj, rel, user, depth, seen):
    if depth > self.max_depth:
        raise DepthExceeded(f"{obj}#{rel} is {depth} levels deep (max {self.max_depth})")
    if (obj, rel) in seen:               # cycle, or already explored in this query
        return False
    seen.add((obj, rel))
    for rule in self.rules(obj, rel):
        if rule[0] == "this":
            for s in self.store.subjects(obj, rel):
                if s == user:
                    return True
                if "#" in s:             # a userset: recurse into "everyone with R on O"
                    so, sr = s.split("#", 1)
                    if self._check(so, sr, user, depth + 1, seen):
                        return True
        elif rule[0] == "computed":
            if self._check(obj, rule[1], user, depth + 1, seen):
                return True
        elif rule[0] == "ttu":
            for parent in self.store.subjects(obj, rule[1]):
                if "#" not in parent and self._check(parent, rule[2], user, depth + 1, seen):
                    return True
    return False

Milestone 4: explain and expand, for audit

A yes-or-no engine is enough to run an application and not enough to run a business. Support asks "why can this contractor see the board minutes?" Compliance asks "list everyone who can read this folder." A security review asks "if I remove this tuple, who loses what?" All three are answered by the same graph, read in two directions.

Explain returns the path that granted access, or nothing. Each step is a line you can log: a computed step moves between relations on one object; a ttu or userset step names the stored tuple it followed; the last step is always a tuple line naming the user. Stored with each access decision, the path turns an audit log from "allowed" into "allowed, because of these tuples", which is what an investigator needs to find the one that should not have been there.

Expand (called who_can here) collects instead of searching: it returns every user who has the relation, using the same rules, the same visited set and the same depth bound. Zanzibar's Expand API returns a tree of usersets; this one flattens it to a sorted list of users, which is what the compliance question wants.

What a path is, and is not

The path is a reason, not the reason: when several paths exist, the engine reports the first one it finds in its sorted order, which is stable but not necessarily the shortest. And it explains grants only. "Why was I denied?" is a harder question (the answer is the absence of every path) and real systems answer it by showing which tuple, if added, would have granted access. That is a good stretch goal.

def _explain(self, obj, rel, user, depth, seen):
    if depth > self.max_depth:
        raise DepthExceeded(f"{obj}#{rel} is {depth} levels deep (max {self.max_depth})")
    if (obj, rel) in seen:
        return None
    seen.add((obj, rel))
    for rule in self.rules(obj, rel):
        if rule[0] == "this":
            for s in self.store.subjects(obj, rel):
                if s == user:
                    return [f"tuple {obj}#{rel}@{s}"]
                if "#" in s:
                    so, sr = s.split("#", 1)
                    sub = self._explain(so, sr, user, depth + 1, seen)
                    if sub is not None:
                        return [f"userset {obj}#{rel} => {so}#{sr} via {obj}#{rel}@{s}"] + sub
        elif rule[0] == "computed":
            sub = self._explain(obj, rule[1], user, depth + 1, seen)
            if sub is not None:
                return [f"computed {obj}#{rel} => {obj}#{rule[1]}"] + sub
        elif rule[0] == "ttu":
            for parent in self.store.subjects(obj, rule[1]):
                if "#" in parent:
                    continue
                sub = self._explain(parent, rule[2], user, depth + 1, seen)
                if sub is not None:
                    return [f"ttu {obj}#{rel} => {parent}#{rule[2]} via {obj}#{rule[1]}@{parent}"] + sub
    return None

def _who(self, obj, rel, depth, seen):
    if depth > self.max_depth:
        raise DepthExceeded(f"{obj}#{rel} is {depth} levels deep (max {self.max_depth})")
    if (obj, rel) in seen:
        return set()
    seen.add((obj, rel))
    out = set()
    for rule in self.rules(obj, rel):
        if rule[0] == "this":
            for s in self.store.subjects(obj, rel):
                if "#" in s:
                    so, sr = s.split("#", 1)
                    out |= self._who(so, sr, depth + 1, seen)
                elif s.startswith("user:"):
                    out.add(s)
        elif rule[0] == "computed":
            out |= self._who(obj, rule[1], depth + 1, seen)
        elif rule[0] == "ttu":
            for parent in self.store.subjects(obj, rule[1]):
                if "#" not in parent:
                    out |= self._who(parent, rule[2], depth + 1, seen)
    return out

Milestone 5: an API with a deliberate IDOR

An insecure direct object reference (IDOR) is a handler that takes an identifier from the request, uses it to load a record, and returns or changes the record without asking whether this caller may. OWASP's API Security Top 10 names the same flaw broken object-level authorization and lists it first. It survives code review because the handler reads naturally, it survives testing because tests act as the owner, and it survives authentication because the caller is logged in. The ids make it worse: d1, d2, d3 can be enumerated by a script in seconds.

The lab's App has five handlers written exactly that way. Look at the starter's read_doc:

def read_doc(self, p, doc_id):
    doc = self._load(doc_id)          # BUG: fetched by id; nobody asks whether p may see it
    return dict(doc)

Every handler does the same: read_doc, update_doc, delete_doc, share (it never asks whether the caller owns the document, or whether the person being added belongs to the same tenant) and list_docs (it returns everything, for everyone). The fix is not five patches. It is one decision function that all five call, which is why require() exists:

Six design decisions go into require(), and the check tests each of them.

  1. The principal comes from the session, not the request. Principal(user, tenant) is built by your authentication layer. A tenant id in a request body or URL is a claim to be compared with it, never a way to choose whose data to read (chapter 15).
  2. The tenant is a wall, checked first. If the document's tenant differs from the principal's, deny before looking at any relationship. A stray tuple that names a user from another tenant (a bad import, an admin slip) then grants nothing, and the check proves it by writing such a tuple on purpose.
  3. Deny with the same answer as "does not exist". If the caller cannot even read the document, raise NotFound(f"no such document: {id}"), exactly the error for an id that was never used. A different message for "exists but forbidden" turns the API into an oracle for which ids are real. A caller who can read the document but lacks the needed relation gets Forbidden; they already know it exists.
  4. Lists are accesses too. list_docs filters through the non-raising can(). A list endpoint that returns ids or titles of documents the caller may not open is an IDOR with better pagination.
  5. Sharing is an access to the document and to the directory. Only owners may share, and the new viewer must belong to the same tenant. Cross-tenant sharing is a legitimate product feature and a separate design (shared links, guest accounts, explicit allowlists); it must not appear by accident.
  6. Every decision is logged with its reason. One audit entry per decision, allowed or not, carrying the path from milestone 4 when allowed. The allowed entries answer "who saw what and why"; the denied ones are the early warning that somebody is walking through ids.

def _decide(self, p, doc_id, rel):
    doc = self.docs.get(doc_id)
    if doc is None or doc["tenant"] != p.tenant:
        return None
    try:
        return self.engine.explain(f"doc:{doc_id}", rel, f"user:{p.user}")
    except DepthExceeded:
        return None

def require(self, p, doc_id, action, target=None):
    if action not in ACTION_REL:
        raise ValueError(f"unknown action {action!r}")
    path = None
    seen = self._decide(p, doc_id, "viewer")
    if seen is not None:
        path = seen if action == "read" else self._decide(p, doc_id, ACTION_REL[action])
    denial = None
    if seen is None:
        denial = NotFound(f"no such document: {doc_id}")
    elif path is None:
        denial = Forbidden(f"{p.user} may not {action} {doc_id}")
    elif action == "share" and self.user_tenant.get(target) != p.tenant:
        denial = Forbidden(f"cannot share with {target!r}: not a member of tenant {p.tenant}")
    self.audit.append({"user": p.user, "tenant": p.tenant, "action": action, "doc": doc_id,
                       "allowed": denial is None, "via": None if denial else path})
    if denial is not None:
        raise denial
    return path

def read_doc(self, p, doc_id):
    self.require(p, doc_id, "read")
    return dict(self._load(doc_id))

def share(self, p, doc_id, target_user, level):
    if level not in ("viewer", "editor"):
        raise ValueError("level must be viewer or editor")
    self.require(p, doc_id, "share", target=target_user)
    self.store.add(f"doc:{doc_id}#{level}@user:{target_user}")

def list_docs(self, p):
    ids = sorted(self.docs, key=lambda d: int(d[1:]))
    return [d for d in ids if self.can(p, d, "read")]

"We check in the gateway" is not an answer

A common half-fix is to authorise at the edge: the gateway verifies the token and the route, and the service trusts it. That protects the routes the gateway knows about. It cannot know that /docs/{id} means "the document with this id, which may belong to another tenant"; only the code that loads the object can. Edge checks and object checks answer different questions, and you need both (chapter 13 returns to this under "no trusted network").

Distributed systems connection

Everything in this lab was one process, and the hard part of Zanzibar is what happens when the tuples are spread over many machines and the check must answer in milliseconds for billions of objects. The paper's answer includes keeping results consistent with the order of writes so that "new enemy" problems do not occur: you remove a colleague from a folder, then add a sensitive document to it, and a stale replica must not let the colleague read the document. It does this with an opaque consistency token (a zookie) that a check can carry, so the answer is at least as fresh as the write that created the object. That is session consistency applied to authorization. Caching permission decisions brings the usual trade-off between latency and the time a revoked permission still works (distributed chapter 5), and a bounded recursion is the same idea as a bounded retry: the work a request may cause has to have a ceiling.

What you learned

  • Roles are global and objects are not. Per-object sharing with roles makes the policy grow with the data (role explosion); a small schema over relation tuples keeps the policy the same size and moves the facts into data.
  • A relation tuple is object#relation@subject, and the subject may be a userset. Parse strictly (fullmatch, not match with $), keep tuples in sets, and write them only from trusted code.
  • Computed usersets (editor implies viewer) and tuple-to-userset (inherit from the parent) express most sharing models. The check needs a visited set for cycles and linear work, and a depth bound that fails closed.
  • Explain returns the path that granted access, and expand lists everyone who has it. Log the path with the decision and "why can they?" stops being a mystery.
  • An IDOR is a handler that loads by id without asking. Fix it structurally: one decision function, the tenant as a hard wall derived from the session, the same error for "forbidden" and "missing", lists filtered by the same function, and an audit entry for every decision.

Check your understanding

A document app gives each document an editor list and a viewer list, and models them as roles named editor:doc17 and so on. What is the problem, and what does a relationship model change?

  1. Nothing: roles scale linearly, so it is fine
  2. The number of roles grows with the number of documents, so the policy a reviewer must read grows with the data; a relationship schema has a fixed number of rules and keeps the per-document facts as tuples
  3. Roles cannot carry permissions for a single document at all
  4. Relationship models cannot express that an editor can also view
Per-object roles are possible, and that is exactly the problem: every shared document adds policy. The check shows 20 roles for 10 documents and 80 for 40. In ReBAC the same facts are tuples, and a handful of rewrite rules say how relations imply one another.

Milestone 3 uses both a visited set and a depth bound. What does each one do?

  1. The visited set bounds the depth and the depth bound stops cycles
  2. The visited set stops rings and keeps the search linear in the number of (object, relation) pairs; the depth bound caps the work and the stack for inputs that are legal but absurdly deep, and fails closed
  3. Both do the same thing; one is enough
  4. The visited set is for speed and the depth bound is for correctness of the answer
A ring never gets deeper than the number of nodes only if you stop revisiting them, and a ladder of diamonds has exponentially many routes to the same node; the visited set handles both. A 3,000-deep chain has no cycle and no redundancy but would still cost a lot; the bound refuses it and denies.

A handler does doc = load(doc_id) and returns it, after a middleware has verified the user's session token. A tester logs in as user A and requests an id owned by user B. What is the bug called, and what is the structural fix?

  1. Session fixation; rotate the token on login
  2. An insecure direct object reference (broken object-level authorization): authentication says who is calling, but nothing asks whether they may access this object; route every access through one decision function, with the tenant derived from the session
  3. Cross-site request forgery; add an anti-CSRF token
  4. SQL injection; parameterise the load
The token proves identity. Authorization is a separate decision, per object, per action. The fix is a single choke point (require/can) called by every handler that takes an id, so that a handler without it is the thing a reviewer notices.

For a document that exists but belongs to another tenant, the API returns 403 Forbidden, and for an unused id it returns 404. Why does the lab insist on the same error for both?

  1. Because 404 is faster to compute
  2. Because the difference tells an outsider which ids exist, which lets them enumerate other tenants' documents and confirm guesses; a user who cannot read the document should get exactly what a user asking for a missing document gets
  3. Because HTTP forbids 403 on documents
  4. Because the audit log can only record one status
A different answer for 'exists but not yours' is an oracle. Attack 16 compares the two responses (type and message, with the id removed) and succeeds if they differ. A caller who can read the document and only lacks the relation for the action may be told Forbidden: they already know it exists.

Lab 2: Build and Break a Token Format

A signed token is a small idea with a long history of expensive mistakes. In chapter 6 you read a verifier and saw two broken ones fall over. In this lab you build the format yourself: encode and decode a JWT-like token with HMAC-SHA256, write a strict verifier that never lets the token choose how it is checked, then forge six kinds of attack token and aim them first at a deliberately naive verifier, then at yours. You finish with key rotation by kid and with the one problem a self-contained token cannot solve by itself, revocation.

Why this lab matters

Token verification is where authentication turns into a branch in your code: either the request runs as Alice or it does not. Almost every real failure in this area is a verifier that believed something the sender wrote: the algorithm named in the header, the key id, the absence of a signature, a claim like aud that nobody compared. The cure is the same every time, and short: the server decides how a token is checked, and only after the signature has passed does it read anything else. You will feel why by writing the attacks.

Only test what you own

Every forged token in this lab is aimed at a verifier written for this lab, running in the same Python process as the attack. They show the shape of well-known bug classes so that you can review code for them. Do not point forged tokens at systems you do not own or are not authorised to test. Where this lab says "naive verifier", it means a deliberately vulnerable teaching function, not any real library. Maintained JWT libraries have fixed these particular bugs, but you will still meet them in hand-rolled code and in misconfigured libraries.

What you'll build

Five milestones:

  1. The format: encode and decode_unverified for a base64url header.claims.signature token signed with HS256, checked against the specification's own test vector (RFC 7515, appendix A.1).
  2. A strict verifier: a fixed algorithm allow-list, signature first, then exp and nbf with leeway, iss and aud.
  3. Break and fix: you write four forgers (alg: none, algorithm switching, signature stripping, payload tampering). The check fires them, plus expired and wrong-audience tokens, at a provided naive verifier (they work) and at yours (they must not).
  4. Key rotation: verify against several keys, selected by kid, without letting kid become an injection point.
  5. Revocation: short-lived access tokens, rotating refresh tokens, and reuse detection that revokes the whole family.

Milestone 1: encode and decode

A JSON Web Signature (RFC 7515) in compact form, the thing people mean by "a JWT" (RFC 7519 defines the claims), is three base64url strings joined by dots. The header is a small JSON object saying how the token is signed (alg) and, here, with which key (kid). The claims are a JSON object holding statements: who it is about (sub), who issued it (iss), who may accept it (aud), and when it is valid (iat, nbf, exp). The signature is, for HS256, HMAC-SHA256(key, "header.claims") computed over the two base64url strings exactly as they appear, which makes the encoding step part of what is signed.

base64url is the URL-safe alphabet (- and _ instead of + and /) with the trailing = padding removed. It is an encoding, not encryption. Anyone holding the token can read the claims, which is why you do not put secrets in them. (Chapter 6 compares this with server-side sessions.)

Solution spoiler 
def sign_hs256(key: bytes, signing_input: bytes) -> str:
    return b64u(hmac.new(key, signing_input, hashlib.sha256).digest())

def encode(claims: dict, key: bytes, kid: str = None, header_extra: dict = None) -> str:
    header = {"alg": "HS256", "typ": "JWT"}
    if kid is not None:
        header["kid"] = kid
    header.update(header_extra or {})
    h = b64u(json.dumps(header, separators=(",", ":"), sort_keys=True).encode())
    p = b64u(json.dumps(claims, separators=(",", ":"), sort_keys=True).encode())
    return f"{h}.{p}.{sign_hs256(key, f'{h}.{p}'.encode())}"

def decode_unverified(token: str):
    h, p, _ = token.split(".")
    return json.loads(unb64u(h)), json.loads(unb64u(p))

Milestone 2: a strict verifier

Now the part that matters. A verifier is a function from (token, configuration) to claims or an exception. The configuration is what the server knows and decides: the keys, the algorithms it will accept, who it trusts as issuer, who it is as audience, what time it is, how much clock disagreement it tolerates. The token supplies only the thing to be judged. Every vulnerability in the next milestone is a place where a naive verifier lets the token supply part of the configuration.

Your verifier works in a fixed order, and the order is part of the design (figure below). It parses defensively, because a malformed token is the first piece of hostile input. It checks the algorithm against the server's list. It verifies the signature in constant time. Only then does it interpret the claims, in the order exp, nbf, iss, aud. If the order were reversed, you would be reading and acting on claims from a token whose origin you have not yet established.

Three details deserve a sentence each. Leeway is a few seconds of tolerance for clock disagreement between issuer and verifier: a token is expired when now - leeway >= exp (RFC 7519 says exp is the first moment the token must not be accepted) and not yet valid when now + leeway < nbf. Audience may be a string or a list of strings, and the token is acceptable if your identifier is in it. Types matter: exp: "9999999999" or exp: true must not slip through because Python is willing to compare them.

Hints try without first
  • verify never reads alg to decide what to do. It only checks that the header's value is in the allow-list algs (default ALLOWED_ALGS) and refuses otherwise.
  • Recompute the HMAC over signing_input and compare with hmac.compare_digest. An empty signature simply fails this comparison.

Solution spoiler 
def check_claims(claims: dict, *, issuer: str, audience: str, now: float, leeway: float = 0) -> None:
    exp = claims.get("exp")
    if not _number(exp):
        raise InvalidToken("exp", "missing or not a number")
    if now - leeway >= exp:
        raise InvalidToken("exp", f"expired at {exp}")
    nbf = claims.get("nbf")
    if nbf is not None:
        if not _number(nbf):
            raise InvalidToken("nbf", "not a number")
        if now + leeway < nbf:
            raise InvalidToken("nbf", f"not valid before {nbf}")
    if claims.get("iss") != issuer:
        raise InvalidToken("iss", f"unexpected issuer {claims.get('iss')!r}")
    aud = claims.get("aud")
    auds = aud if isinstance(aud, list) else [aud]
    if audience not in auds:
        raise InvalidToken("aud", f"this token is not for {audience!r}")

def verify(token: str, key: bytes, *, issuer: str, audience: str, now: float, leeway: float = 0,
           algs: tuple = ALLOWED_ALGS) -> dict:
    header, claims, signing_input, sig = _split(token)
    if header.get("alg") not in algs or "crit" in header:
        raise InvalidToken("alg", f"algorithm {header.get('alg')!r} is not allowed")
    if header["alg"] != "HS256":
        raise InvalidToken("alg", "this lab only implements HS256")   # RS256 is out of scope (no RSA in the stdlib)
    expected = hmac.new(key, signing_input, hashlib.sha256).digest()
    if not hmac.compare_digest(expected, sig):
        raise InvalidToken("signature", "does not match")
    check_claims(claims, issuer=issuer, audience=audience, now=now, leeway=leeway)
    return claims

Milestone 3: attacks, against the naive verifier and then yours

Open naive_verify in the starter. It is about fifteen lines long and it contains three bugs of the kinds that have shipped in real code:

  1. The token chooses the algorithm. It reads alg from the header and branches on it. If the header says none (RFC 7515 defines "unsecured" tokens with no signature), it returns the claims. The check is case-insensitive here, as several real implementations once were, so None and NONE work too.
  2. An empty signature skips the check. The comparison runs only if s, meaning "if there is a signature part". Remove the signature text, keep the final dot, and the branch is never entered.
  3. The claims are never checked. No exp, no iss, no aud. A genuine, signed token from yesterday, or one issued for a different API, passes.

A fourth attack needs a slightly different set-up. Suppose a service signs with an asymmetric algorithm (RS256 in real life: a private key to sign, a public key that everyone may download to verify), and its verifier calls one function with "the key" and the header's alg. An attacker sets alg to HS256 and signs with the public key's bytes used as an HMAC secret. The verifier obligingly uses the same bytes as the HMAC key and the signature checks out. The lab models this with a stand-in PUBLIC_KEY blob, as chapter 6 does: the standard library has no RSA, and the bug lives in the dispatch, not the mathematics.

Your job is to write the four forgers. Then the check does the rest: it fires them at the naive verifier and expects them to work (a forger that does not fool the naive verifier is not a working exploit), then fires the same tokens at your strict verifier and expects each to fail for the right reason.

A control, and a lesson

The fifth forgery, forge_tamper, changes the claims and keeps the old signature. Even the naive verifier refuses it, because this is exactly the thing a signature is for. It is in the suite as a control: it shows that the naive verifier's problem is not that signatures do not work, but that they can be bypassed around the edges. Attackers rarely break the HMAC; they find the branch that never runs it.

def forge_alg_none(claims: dict) -> str:

def forge_strip_signature(token: str) -> str:
    h, p, _ = token.split(".")

def forge_alg_switch(claims: dict, public_key: bytes) -> str:

def forge_tamper(token: str, **changes) -> str:
    h, p, s = token.split(".")

def naive_verify(token: str, key: bytes, now: float) -> dict:
    h, p, s = token.split(".")
    header, claims = json.loads(unb64u(h)), json.loads(unb64u(p))
    alg = header["alg"]                                        # bug 1: the token chooses the algorithm
    if alg.lower() == "none":
        return claims
    if alg == "HS256":
        expected = hmac.new(key, f"{h}.{p}".encode(), hashlib.sha256).digest()
        if s and not hmac.compare_digest(expected, unb64u(s)):  # bug 2: an empty signature skips the check
            raise InvalidToken("signature", "does not match")
        return claims                                          # bug 3: no exp / iss / aud checks at all
    raise InvalidToken("alg", "unsupported")

Milestone 4: key rotation with kid

A signing key that can never change is a liability: if it leaks you cannot replace it without invalidating every token, and routine hygiene says keys should have limited lifetimes. The standard answer is a key id in the header. The issuer signs with the current key and names it; the verifier holds several keys at once and uses the one named. During a rotation both keys verify, until every token signed by the old one has expired, at which point you retire it.

The danger is that kid is attacker-controlled text that tells your code what key to use. A verifier that uses it as a file name (open("keys/" + kid)), as part of a database query, or as a URL to fetch keys from, hands the attacker a path traversal, an injection or a server-side request (see chapter 11). The lab's naive_keyring_verify contains a quieter variant of the same flaw: for an unknown kid it falls back to an empty key, so the attacker names a key that does not exist and signs with the empty string. The strict rule is that kid may only be used as a lookup key into a fixed set of keys you already hold, and an unknown or missing one is a rejection.

def verify_with_keyring(token: str, ring: Keyring, **kw) -> dict:
    header, _, _, _ = _split(token)
    kid = header.get("kid")
    if not isinstance(kid, str) or kid not in ring.keys:    # a dict lookup: kid is NEVER a path or a query
        raise InvalidToken("kid", "unknown or missing key id")
    return verify(token, ring.keys[kid], **kw)

Milestone 5: revocation, the hard part

A self-contained token is valid because its signature checks and its exp has not passed. That is its great convenience (the API needs no database lookup) and its great weakness: nothing in that logic lets you say "this particular token, stop working now". If a token is stolen, or a user logs out, or an employee is dismissed, a verifier that checks only signature and expiry will keep accepting it until exp.

The practical answer is to split the credential in two. An access token is short-lived (here 300 seconds), self-contained, and cheap to verify; it is what the API sees. A refresh token is long-lived but opaque, lives only at the auth server, and is exchanged for a new access token. Revocation then means revoking the refresh token, and the exposure of an already-issued access token is bounded by its lifetime. That bound, not an instant kill, is the honest guarantee of this design, and the check tests it: after the family is revoked, the old access token still verifies until its last second.

To make a stolen refresh token detectable, each use rotates it: the server returns a new refresh token and retires the old one. Consider what that does. The legitimate client holds the newest token. A thief with a copy of an older token will present it at some point, and the server, which remembers every token ever issued in the family, sees a token that is no longer current. Either the client or the thief has an old token, and the server cannot tell which, so it distrusts both: it revokes the whole family, forcing a fresh login. (Chapter 6 shows the idea; the OAuth security recommendations in RFC 9700 describe refresh-token rotation for public clients.)

Rotation has a sharp edge

A flaky network can make an honest client send R1 twice: the first request succeeded but the response was lost. The server sees reuse and revokes the family, logging out a user who did nothing wrong. Real systems soften this with a short grace period or by remembering the last response, which trades a little security for availability. The lab uses the strict rule so that the mechanism is clear. This is an example of a general tension that the incident-response chapters will return to: the safest response and the most available one are not always the same.

def refresh(self, token: str):
    family = self.owner.get(token)
    if family is None:
        raise InvalidToken("refresh", "unknown refresh token")
    f = self.families[family]
    if f["revoked"]:
        raise InvalidToken("refresh", "family revoked")
    if token != f["current"]:                       # an OLD token came back: someone holds a copy

Stretch goals

Distributed systems connection

Revocation is a cache-invalidation problem with an adversary. Every API that verifies tokens locally is a replica holding a copy of "who is allowed" that is as stale as the token's lifetime, and a shorter lifetime is exactly a smaller staleness bound (the same trade as a lease in distributed chapter 4). Key rotation is a rolling configuration change across many verifiers, which is why the overlap period is a property of the system and not of one process. Reuse detection needs the auth server's family table to be linearizable per family: two concurrent refreshes with the same token must not both succeed, which in a replicated deployment means a single writer or a compare-and-swap on the family record.

What you learned

  • A compact signed token is b64u(header).b64u(claims).b64u(HMAC), with the signature over the first two parts as written. Anyone can read it; only the key holder can mint or change it.
  • The server decides the algorithm, the keys and the expected issuer and audience. The token's header is a claim to be checked, never an instruction. Verify the signature first, with a constant-time comparison; interpret claims afterwards.
  • The classic breaks are all one mistake: alg: none, algorithm switching with a public key as HMAC secret, an empty signature that skips the check, unchecked exp / iss / aud, and a kid that falls back or reaches the filesystem.
  • Rotate keys by kid with an overlap; treat kid only as a dictionary key.
  • Self-contained tokens cannot be recalled. Bound the damage with short-lived access tokens and rotating refresh tokens, and treat reuse of a retired refresh token as proof of theft: revoke the family.

Check your understanding

A verifier reads alg from the header and uses it to choose the check. Which statement describes the underlying flaw?

  1. HMAC is weak when used with SHA-256
  2. The token, which the attacker controls, decides how it is verified; the algorithm must come from server configuration
  3. base64url is not secure
  4. The header should have been encrypted
alg: none and algorithm switching both work because the verifier lets the sender pick the rule. Blocking the single word none does not fix it: the allow-list of acceptable algorithms must be fixed server-side.

A token's signature is valid, exp is in the future, and iss is correct, but aud is billing.example and your API is api.example. What should happen, and which attack is this?

  2. Reject: the token was issued for another service; accepting it lets a token meant for a low-risk API be replayed against a more sensitive one (a confused deputy)
  3. Accept, but log a warning
  4. Reject only if exp is near
A signature proves who issued the token, not who it is for. The check aud is what ties a token to one recipient. The lab's naive verifier skips it, and so accepts the token; yours reports reason aud.

A token arrives with "kid": "../../etc/passwd". What is the right behaviour in a verifier with a key ring?

  1. Open the named file and use its contents as the key
  2. Treat it as a dictionary key, find nothing, and reject with an unknown-key error
  3. Fall back to the newest key
  4. Strip the slashes and retry
The key id only selects from keys the server already holds. Using it as a path, query or URL, or falling back to a default or empty key when it is unknown, is the vulnerability.

After reuse of a refresh token is detected and the family is revoked, an access token issued 100 seconds earlier (lifetime 300 s) is presented to the API. What does the lab's design guarantee?

  1. It is rejected immediately, because the API asks the auth server
  2. It may still verify for up to its remaining 200 seconds; the exposure is bounded by the access-token lifetime, which is why that lifetime is short
  3. It is accepted forever because it was valid when issued
  4. It is rejected because the signature changes when the family is revoked
The API checks only signature and exp. Revocation of the refresh family stops new access tokens; existing ones die by expiry. If that window is too long for your risk, shorten the lifetime or add a denylist (a stretch goal).

Threat-Model a File-Sharing Service

A file-sharing service accepts arbitrary bytes from strangers, parses them, stores them and hands them to other strangers through a link. That is nearly a definition of attack surface. This studio threat-models one: draw the data flows and trust boundaries, apply STRIDE, rank what you find by likelihood times impact, and decide what to build, what to accept and what to test.

How a design studio works

This page is a design problem, not a chapter. At each stage there is a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer is not the only right design; it is one strong one with its reasoning. A rubric at the end lets you check whether you covered what an experienced engineer would. Being wrong first and then seeing why is the point. Scores and numbers here are judgement calls for practice, not measurements. Everything is defensive: we name attack classes so you can recognise and block them, and we do not give recipes against real products.

📐 The brief

You are reviewing the design of Dropwell, a file-sharing service, before launch. Its components:

  • Upload: signed-in users upload files up to 5 GB from a browser or through a public REST API (API keys).
  • Storage: files live in an object store (S3-style) behind the app; metadata (owner, name, size, hash, sharing) lives in a database.
  • Previews and thumbnails: a worker generates thumbnails for images and previews for documents so the web UI can show them.
  • Public share links: an owner can create a link that anyone can open, optionally with an expiry and a password.
  • Malware scanning: each upload is scanned by an antivirus engine, and its hash is looked up in an external reputation service in the style of VirusTotal.
  • about 2 million users, 50,000 uploads per hour at peak, and a free tier that attracts abuse.

Use threat modeling, untrusted input, server-side risks, abuse and data protection. The toolbox shows how to test your own app for some of what you list. The chapter-1 worked example (photo upload) is the small version of this exercise.

1Assets, adversaries and the data-flow diagram

What are you protecting, and from whom? Then draw the data-flow diagram (DFD): external entities, processes, data stores, flows, and the trust boundaries. Where does untrusted data first become input to a parser?

Compare with a worked answer

Assets: confidentiality of private files (the main one), integrity of files (what you download is what was uploaded), availability of the service, the reputation of the domain (a file host serving malware gets blocklisted), user accounts and API keys, and the infrastructure credentials that can read the whole bucket. Adversaries (chapter 1): a curious user guessing links; an abuser hosting malware or illegal content; a bot farm using the free tier; a user trying to read someone else's files; and an attacker who has found a bug in a file parser. Insiders are out of scope for this pass, and noting that is part of the model.

  • Where untrusted data becomes input to a parser: the front end (HTTP, multipart, filenames, headers), the preview worker (image and document decoders, the highest-risk code in the system because it is large, old and written in memory-unsafe languages; chapter 12), the antivirus engine (also a big parser of hostile files), and any consumer of the file's metadata (names, EXIF, archive entries).
  • Trust boundaries drawn: TB1 internet to our edge; TB2 our cloud account; TB3 the sandbox around the preview worker, which is deliberately outside the trust of the rest of TB2 because it handles hostile bytes; TB4 third party. A boundary is wherever the level of trust or the owner changes.
  • The DFD should also carry credentials: the app holds object-store access, the worker should not. Missing this is the classic gap in a first diagram.

3Design the image-parsing risk away

Image and document decoders have a long history of memory-safety bugs, and you cannot audit them yourself. How do you generate thumbnails so a decoder compromise does not matter much? Think isolation, privilege, resources and data flow.

Compare with a worked answer

Assume the decoder will have an exploitable bug someday, and design so that the bug is boring (defence in depth and least privilege, chapter 2).

  1. Sandbox the parser. Run each conversion in a separate, short-lived process or container under a strict profile: no network at all, read-only root file system, a seccomp syscall filter, an unprivileged user, a user namespace, ideally a stronger boundary such as gVisor or a microVM (systems chapter 19: a plain container shares the host kernel, so a kernel bug can escape it).
  2. Give it only the input and an output slot. The worker receives bytes (or a short-lived pre-signed URL for exactly one object), not credentials for the bucket, and returns a thumbnail. No access to the database, to other tenants' files or to cloud metadata.
  3. Limit resources. CPU seconds, memory (cgroup limit), output size, wall-clock timeout (say 10 s), maximum pixel dimensions and decompressed size checked before decoding (reject a 60,000 × 60,000 image from its header). A worker that is killed is simply retried once and then the preview is marked failed.
  4. Reduce the parser. Allow-list the formats you will decode (JPEG, PNG, WebP), identify them by content not extension, and refuse the rest. Prefer memory-safe decoders where they exist. Disable risky features (embedded scripts, external references, delegates that shell out to other programs, SVG with external entities).
  5. Re-encode, never pass through. The thumbnail is a fresh image encoded by your code, which strips metadata (EXIF, location) and any trailing payload.
  6. Treat the output as untrusted too. Validate the result's type and size before storing it, and serve it from the cookieless domain.
  7. Monitor. Alert on worker crashes, timeouts and sandbox denials: a burst of segfaults on a recent upload is the signal of someone probing.

What this does not give you: protection against a sandbox escape (so keep the kernel patched and prefer the stronger boundaries) or against logic abuse (a legal image that is a phishing screenshot).

4Share links, expiry and the public API

Design the share link so that holding it is the credential, and make it safe. What is in the link, how is it checked, how does expiry work, what happens at the edges? Then list the extra problems of the public API.

Compare with a worked answer

A public link is a bearer capability: whoever holds the string has access (the capability idea of chapter 8). So the string must be unguessable and the access must be revocable and bounded.

  • Unguessable. At least 128 bits from a cryptographically secure random source (22 characters of URL-safe base64), not a counter, not derived from the file id. Store only a hash of the token and look up by hash, so a database leak does not leak working links.
  • Server-side state decides. The link row holds file_id, expires_at, max_downloads, optional password hash (a slow password hash, chapter 5), revoked_at, creator. Every access checks the row; do not encode expiry in the URL where a user could edit it, or if you sign it, verify the signature and consult revocation.
  • Expiry details. Use the server clock; check at access time and at the moment a download starts. Pre-signed storage URLs that the link redirects to should themselves live only a minute or two, otherwise an expired link keeps working through the redirect target. Expiry must also stop previews and cached copies: set Cache-Control: private, no-store on private content, and keep CDN keys tied to the link.
  • Defaults. Expire in 7 days unless the owner picks otherwise; show a list of active links; revoke on file delete, ownership transfer and account deactivation; notify the owner of an unusual download pattern.
  • Enumeration and brute force. Return the same response for "unknown", "expired" and "revoked" so links cannot be probed; rate-limit by IP and by link; a wrong password counts toward a lockout. Put the token in the path and set Referrer-Policy: no-referrer on the page so links do not leak in referrer headers to third-party scripts.
  • The public API. Authenticate with scoped, hashed API keys; per-key rate limits and quotas on bytes (not just requests); object-level authorization on every id; strict input validation (filename length and characters, declared size, content type); idempotent uploads with resumable chunks; pagination limits; no mass-assignment of fields such as owner_id; and an unambiguous 404 for files you may not know exist. Publish an abuse contact and a takedown path.

5Malware scanning and reputation lookups

What does scanning buy you, what does it not, and where does it go in the flow? How do you use an external reputation service without leaking your users' files? What happens to a file that is flagged, or one that has not been scanned yet?

Compare with a worked answer
  • What scanning is for. It protects the downloaders and your domain's reputation, not the stored bytes. It catches known families and obvious payloads; it misses new, targeted or well-packed malware. Treat a clean verdict as "no known problem", never as "safe".
  • Flow. Upload to a quarantine prefix, scan asynchronously, then promote or reject. A file is not downloadable by share link until its state is clean; the owner can still see it, with a "scan pending" label. Scan time is a service-level indicator with its own queue-age alert.
  • The scanner is a parser too. It reads hostile files with a very large engine. Run it in the same kind of sandbox as the previews (no network, no credentials), keep its signatures updated, and bound archive depth and expanded size (zip-bomb defence).
  • Reputation lookups by hash. Compute SHA-256 locally and look up the hash. A known-bad verdict is strong evidence. Do not upload a private user file to a third-party service: that discloses customer content and may break your privacy promises (chapter 17). An unknown hash says nothing; most new files are unknown. Mind the service's terms and rate limits, and cache results.
  • Handling a detection. Block downloads, keep the object for investigation under restricted access, notify the owner, and increase the account's abuse score. Review false positives with a path to appeal. Consider re-scanning stored files when signatures update, because yesterday's clean file may be today's known threat.
  • Other abuse content. Illegal-content hash matching, copyright takedown and terms-of-service enforcement are legal and policy processes that need counsel; design the hooks (state flags, a restricted-access review queue, retention rules) without building policy into the storage layer (chapter 16).
  • Active content from a download link. Even a clean file can be a phishing page. Interstitial warnings for executable types, forced download, and a separate domain reduce the harm; they do not eliminate it.

6Object storage and credentials

The bucket holds everything. How is it configured, who can touch it, how do uploads and downloads reach it, and what protects the data if a credential leaks?

Compare with a worked answer
  • Private by default. Block all public access at the account level; no bucket policy that allows anonymous reads. Clients never get a bucket name or a static key.
  • Pre-signed URLs for direct upload and download, scoped to one object key and one method, expiring in minutes, issued only after the app's authorization check. Use a server-chosen random key (tenant/ab/cd/uuid), never the user's filename. Enforce size and content-type conditions in the signed policy so the 5 GB cap is a storage rule, not a promise (on S3 this means a presigned POST policy with content-length-range; a plain presigned PUT URL cannot cap the size, so check the size after upload or use another store's equivalent).
  • Least-privilege roles. The app role may put and get under its prefix only; the scan worker may read the quarantine prefix and write a verdict; the preview sandbox has no storage role at all. Short-lived credentials from workload identity, not long-lived keys (chapter 14).
  • Encryption. Server-side encryption with keys held in a KMS, using envelope encryption (chapter 4); consider per-tenant data keys so deleting a tenant's key renders its objects unreadable. Be clear what this protects: lost disks and some insider paths, not a bug that calls the API with valid credentials.
  • Integrity and recovery. Store the SHA-256 at upload and verify on download; enable versioning with delete protection so a compromised credential cannot erase everything; replicate to a second account or region for backup (reliability chapter 18).
  • Detection. Object-level access logs, alerts on bucket policy changes and on any anonymous access, and a regular check (policy-as-code in CI) that no bucket drifts to public.

Self-check rubric

Tick what your own design (before reading the answers) covered. An experienced engineer would hit most of these.

  • Listed assets and adversaries, including abusers and the domain's reputation.
  • Drew a DFD with external entities, processes, stores and flows.
  • Marked trust boundaries, including one around the parsing worker and one for the third party.
  • Applied STRIDE to the boundary-crossing flows and found threats under every letter.
  • Identified the preview parser as the highest-risk component and sandboxed it (no network, no credentials, resource limits).
  • Allow-listed formats, checked sizes before decoding and re-encoded output.
  • Made share links unguessable, server-checked, expiring and revocable.
  • Served user content from a separate origin with safe headers.
  • Covered API specifics: object-level authorization, quotas, validation, mass assignment.
  • Explained what malware scanning does and does not provide, used hash lookups and avoided sending private files to a third party.
  • Kept the object store private, with scoped short-lived credentials and encryption.
  • Produced a ranked list by likelihood × impact with mitigations and residual risk.
  • Wrote tests for each top mitigation, run only against your own systems.

Saying it in an interview

How a senior engineer would summarise this

"I'd start from the assets, mainly other people's private files, and the adversaries, from curious users to abusers to someone with a decoder exploit. I'd draw the data flow with boundaries around the internet, our account, the sandboxed parser and the third party, and apply STRIDE where flows cross. The highest-risk element is whatever parses hostile bytes, so previews run in a no-network, no-credentials sandbox with strict limits and re-encoded output. Share links are 128-bit bearer capabilities with server-side expiry and uniform errors. User content comes from a separate cookieless domain. Scanning protects downloaders, not the bytes, and I'd look up hashes rather than ship customers' files to a third party. The bucket is private with short-lived scoped credentials. Then I'd rank by likelihood times impact, write the residual risk and attach a test to each top mitigation."

Notice the shape: assets → DFD and boundaries → STRIDE → design the worst element away → bearer links → scanning → storage → rank, residual risk, tests.

Key takeaways

  • Threat modeling is a repeatable procedure: assets, DFD, boundaries, STRIDE, rank, decide, test.
  • Anything that parses attacker-controlled bytes is a prime target; assume it will be compromised and remove what it can reach.
  • A share link is a bearer credential: random, hashed at rest, server-checked and revocable.
  • Serve untrusted files from a different origin than your application.
  • Scanning lowers risk for downloaders but never proves safety; use hash lookups to protect privacy.
  • Keep the object store private and the credentials short-lived and narrow.
  • Scores order attention; residual risk needs a named owner; every mitigation needs a test.

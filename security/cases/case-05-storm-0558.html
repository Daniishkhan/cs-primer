Storm-0558 and a Stolen Signing Key

In the summer of 2023 an actor used tokens forged with a Microsoft consumer signing key to read email in enterprise Exchange Online mailboxes. An independent US review found the intrusion was preventable, and its findings about key scope, key rotation and audit logging apply to any system that issues and verifies tokens.

The pattern in one sentence

A signing key is the root of a trust domain: scope each key to the audience that should accept it, check that scope in every verifier, rotate keys automatically so a stolen key ages out, and make sure the logs that would reveal misuse exist for everyone.

The cast

This page states what the sources say; general explanations are labelled as general. The tone is deliberately neutral: the aim is to learn from the mechanism, not to assign blame. Background: chapter 4 (keys, rotation, storage) and chapter 6 (tokens, signing, validation).

Signing key
A private key a service uses to sign tokens. Anyone holding it can make tokens that verifiers will believe, so its reach equals the reach of every verifier that trusts it.
Token (bearer token)
A signed statement that says who the holder is. A bearer token works for whoever presents it; it carries no proof that the presenter is the party it was issued to.
MSA
Microsoft Account: the consumer identity system (the report calls it the Microsoft Services Account system).
Entra ID (formerly Azure AD)
The enterprise identity system, whose keys are meant to validate enterprise accounts.
Key scope
The set of accounts, tenants or audiences a key is allowed to vouch for. A verifier that checks the signature but not the scope accepts keys outside their remit.
Key rotation
Replacing a signing key with a new one on a schedule and retiring the old one, so a stolen key stops working after a bounded time.
Audit log
A record of who accessed what. Detection depends on which logs exist, who can read them and how long they are kept.
CSRB
The US Cyber Safety Review Board, a public-private body established under the Department of Homeland Security, which published an independent review of this incident.

What happened, in short

The CSRB report says that in May and June 2023 a threat actor, known as Storm-0558 and assessed to be affiliated with the People’s Republic of China, accessed the Exchange Online mailboxes of 22 organizations and 503 related personal accounts (the executive summary says “over 500 individuals”). The actor used authentication tokens signed with a consumer signing key that Microsoft had created in 2016. Microsoft’s July 2023 post, written earlier in the investigation, spoke of about 25 organizations; this page uses the CSRB’s later count.

Two identity systems that should not trust each other’s keys

The report explains that consumer accounts are validated by consumer signing keys and enterprise accounts by enterprise keys; they are managed in separate systems and should not be able to validate for each other. The mechanism that broke this separation is described in both the report and Microsoft’s post of 6 September 2023.

  • In September 2018 Microsoft introduced a common key metadata endpoint, an OpenID Connect (see chapter 7) discovery document that listed active signing keys for both consumer and enterprise applications. The CSRB says it was created in response to customer requests.
  • The helper libraries that applications used could verify a signature but did not, by themselves, distinguish consumer keys from enterprise keys. Microsoft’s post says the libraries did not automatically check key scope; the CSRB says Microsoft had not adequately updated its SDKs to tell them apart.
  • The mail systems adopted the common endpoint in 2022. According to Microsoft, the developers assumed the libraries did full validation and did not add the issuer and scope checks themselves. The result, in the CSRB’s words, was that Exchange Online could accept a token signed with a consumer key for an enterprise account that was not coded to reject it.

Common misconception: "the signature was valid, so the token was fine"

A valid signature answers one question: did a holder of this key produce these bytes? It does not answer whether this key is the right key for this account, this audience or this service. Verification has two halves, cryptographic validity and policy scope, and the incident sits in the gap between them.

What the missing check looks like (general pseudocode, not Microsoft code)

verify(token):
    key = key_for(token.key_id)              # from the common endpoint
    if not signature_ok(token, key):  reject
    if token.issuer != expected_issuer_for(this_service):  reject   # scope
    if key.domain  != token.account_domain:                reject   # scope
    accept

The two scope lines are the point. Each service should state which issuer and which key set it accepts, rather than inheriting “any key in the list”.

How the actor got the key: what is and is not known

This is the part most easily misreported. On 6 September 2023 Microsoft published a theory that a consumer signing system crash in April 2021 had produced a crash dump (a memory snapshot) that contained the key because of a race condition, that the dump was moved to a debugging environment on the corporate network, and that the actor later compromised an engineer’s account with access to it. The post called this the most probable path and said Microsoft lacked logs to confirm exfiltration.

Microsoft then added a March 2024 addendum. According to the CSRB, Microsoft told the Board in November 2023 that it had found no evidence of a crash dump containing the key, and the report concludes that Microsoft “does not know how Storm-0558 obtained the 2016 MSA key.” The report also says Microsoft had only theorized that the crash-dump scenario was technically feasible and that it did not correct the post until 12 March 2024. So the safe summary is: the key was acquired by the actor; how and when remain undetermined in the sources fetched.

Key management findings

The CSRB describes a consumer system built more than 20 years earlier with no automated key rotation or deactivation. It reports that:

  • automated rotation had been built for the enterprise system, with the intent that the consumer system would follow, but this had not happened before the intrusion;
  • consumer keys were rotated infrequently and manually until rotation stopped entirely in 2021, following a major cloud outage linked to the manual rotation process;
  • the 2016 key had been due to be retired in March 2021, but removal was delayed by challenges hardening the consumer key systems;
  • there was no automated alert to tell the responsible teams about the age of active consumer signing keys.

Put plainly (general reasoning): rotation had been judged risky because it was manual and had once caused an outage, so it stopped; but a key that never rotates has an unbounded lifetime, so any past exposure stays useful to an attacker indefinitely. The fix for a risky manual process is to make it safe and automatic, not to stop doing it. Chapter 4 covers rotation designs.

Detection and logging

The report states that the US State Department’s security operations centre noticed anomalies in access to its mail systems on 15 June 2023. The next day a custom rule (internally called “Big Yellow Taxi”) over the MailItemsAccessed log raised alerts. State could use that log because it had purchased a licence that included enhanced logging (Microsoft Purview Audit (Premium)); the report says the log was not accessible without that premium service. State contacted Microsoft on Friday 16 June.

The Board’s conclusion on detection is that Microsoft failed to detect the compromise of its signing key on its own and relied on a customer to reach out. Separately, it recommends that default audit logging be a baseline service rather than a paid extra (below). Microsoft’s own account is that its investigation started from a customer report of anomalous mail activity on 16 June 2023, and that on or about 26 June it determined the actor was using tokens signed by the consumer key.

Timeline

Contributing factors

  • Two identity systems with separate keys were exposed through a shared key-discovery endpoint, which widened what any one key could be mistaken for.
  • Validation behaviour was split across several libraries and applications, and the scope check was left to each application developer on the assumption that a library did it (the report lists “common authentication libraries” among its good practices).
  • A single long-lived consumer key, not scoped per customer, and a pause in rotation left the blast radius large and its duration unbounded.
  • Bearer tokens carried no proof of possession, so a forged or stolen token worked anywhere it was accepted.
  • Insufficient forensics: the report says Microsoft could not determine how the key was taken and recommends logging all access to key material.
  • Useful detection logs were available only on a paid tier, and the provider relied on a customer to raise the alarm.

What changed

Microsoft’s 6 September 2023 post says it fixed the race condition it had identified, improved prevention, detection and response for key material in crash dumps, enhanced credential scanning, and released updated authentication libraries that automate key scope validation with clearer documentation. Its July 2023 post says it blocked tokens signed with the acquired key and replaced the key, and updated its validation libraries for defence in depth. The July post says no customer action was required.

The CSRB made 25 recommendations. In grouped form:

  • Culture and accountability (Microsoft): its CEO and Board should take direct responsibility for a public, time-bound plan for security reforms, and consider deprioritising feature work until substantial security improvements are made.
  • Audit logging for everyone: security-relevant logging should not be sold as an add-on. The report proposes a minimum standard for default audit logging, available to customers at no extra charge, with a minimum default retention of six months.
  • Identity system design for all cloud providers: reduce the risk of complete system-level compromise by design. Practices the Board lists include automated frequent key rotation, per-customer key scope, isolated key storage such as hardware security modules, stateful token validation, bound tokens instead of pure bearer tokens, common authentication libraries, linkable tokens in customer logs and provider-specific data in tokens that helps spot forgeries.
  • Forensics: log all access to key material and keep those logs for the key’s active life and at least two years beyond its expiry.
  • Transparency and notification: disclose incidents and vulnerabilities, including through the CVE process, correct public statements promptly, and improve how victims are notified.
  • Government: update FedRAMP, add discretionary special reviews after high-impact incidents, and have CISA validate cloud providers’ practices annually.

The Board’s overall assessment, in one sentence it uses: the intrusion “was preventable and should never have occurred.” Because the report is a review with its own scope and framing, read it alongside Microsoft’s posts rather than instead of them.

The pattern to remember

Analogy

A national mint has two kinds of banknotes, each with its own printing plate. A shop accepts any note that carries a genuine plate impression but never checks which currency it belongs to. Someone who acquires one old plate can print notes that the shop takes as the other currency, and nobody noticed the plate had never been replaced.

Where it breaks down: Plates are physical and eventually wear out; a signing key does not degrade, so retiring it is a deliberate act.

Key takeaways

  • A valid signature proves who made a token, not what it is allowed to do: verifiers must check issuer, audience and key scope.
  • A key that is never rotated has an unlimited lifetime; make rotation automatic and routine instead of risky and rare.
  • Scope keys to the smallest domain that works (per tenant, per service), so one theft cannot reach everything.
  • Log all access to key material, and keep the logs longer than the key lives, so you can answer how a theft happened.
  • Detection should not depend on a customer who bought the right licence tier.
  • When a root-cause statement turns out to be wrong, correct it publicly and quickly.

What validation gap let a consumer-signed token reach enterprise mailboxes?

  1. Signatures were not verified at all
  2. The signature was verified, but key scope (which system a key belongs to) was not enforced for those mail systems
  3. Tokens never expired
  4. TLS was disabled
Microsoft’s post and the CSRB describe a common key endpoint, libraries that did not automatically check scope, and applications that assumed they did.

Why did the 2016 key still matter in 2023?

  1. Keys cannot be revoked
  2. It had been due for retirement in 2021, but removal was delayed and rotation had been paused, so it stayed valid
  3. The key was never used by anyone
  4. Browsers pinned it
The CSRB reports delayed retirement, manual and infrequent rotation, then a stop in 2021 after an outage, with no alerting on key age.

How was the intrusion detected, according to the CSRB?

  1. By Microsoft’s own monitoring of its signing keys
  2. By the State Department using a custom rule over a log available with a premium licence, followed by a report to Microsoft
  3. By a security researcher on social media
  4. By a hardware alarm
The Board criticises that Microsoft relied on a customer, and recommends that audit logging be a baseline service.

Which design practice from the report would limit how long a stolen signing key stays useful?

  1. Longer-lived keys
  2. Automated, frequent key rotation
  3. Removing audit logs
  4. Using one key for all customers
Rotation bounds the window of use. The report also recommends per-customer key scope and isolated key storage.

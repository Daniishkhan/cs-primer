Heartbleed

In April 2014 a missing bounds check in OpenSSL’s implementation of the TLS heartbeat extension was disclosed. It let a peer read up to 64 KB of a server’s memory per request, which could include private keys, session data and passwords, so fixing the code was only the first step of the response.

The pattern in one sentence

Never trust a length you did not measure, and when memory may have leaked, assume the secrets in it did: patch, then rotate, revoke and invalidate.

The cast

This page states what the sources say; general explanations are labelled as general. Background: chapter 12 (memory safety), chapter 3 (what TLS protects) and chapter 4 (certificates, revocation). The TLS basics are in the networking course.

OpenSSL
A widely used open-source cryptographic library that implements TLS for many servers and clients.
Heartbeat extension
A TLS/DTLS extension (RFC 6520) that lets one side check that the other is still there by sending a small payload that the peer echoes back.
Buffer over-read
Reading past the end of the data you were meant to read, so that bytes belonging to something else are returned. NVD classifies the bug as CWE-125, out-of-bounds read.
Private key
The secret half of a server’s certificate key pair. Whoever holds it can impersonate the server and, without forward secrecy, decrypt recorded traffic.
Revocation
Telling clients that a certificate must no longer be trusted before it expires.
Perfect forward secrecy
A property of some key exchanges: each session uses ephemeral keys, so stealing the long-term private key later does not unlock recorded sessions.

The bug: a length that nobody checked

The heartbeat extension is simple: one side sends a small message and a length, the other echoes the message back. The NVD entry for CVE-2014-0160 says OpenSSL 1.0.1 before 1.0.1g mishandled Heartbeat Extension packets in both TLS and DTLS, and that crafted packets cause a buffer over-read that exposes process memory, including private keys. The OpenSSL advisory of 7 April 2014 describes the same thing as a missing boundary check that could “reveal up to 64k of memory” to a connected client or server.

Put simply (this wording is mine, consistent with the sources): the request names its own length, and the vulnerable code took the claim at face value instead of comparing it with the number of bytes that actually arrived. The reply was then built by copying the claimed number of bytes starting from the real payload, so the copy ran off the end of the request into whatever sat next to it in memory. The attacker did not need to break any cryptography; they only needed to ask a question with an untrue length field.

What the missing check looks like (pseudocode, not library code)

on heartbeat_request(message):
    claimed = message.payload_length        # attacker-controlled
    actual  = len(message.bytes_received) - header_size
    if claimed > actual:                    # the check that was missing
        discard silently
    reply = echo(message.payload, claimed)

The lesson is the shape, not the syntax: any length, count or offset that comes from the other side of a trust boundary has to be validated against what you really hold.

How much could leak, and what

heartbleed.com stresses that the 64 KB limit applies per request: an attacker can repeat requests, on one connection or by reconnecting, until enough has been collected. It groups the exposure into primary key material (such as private keys), secondary key material (usernames, passwords, session keys, cookies), protected content (emails, messages, documents) and collateral details such as memory addresses. Which of these appeared in any reply depended on what the server process happened to hold in nearby memory at that moment, so a single response proves little about the rest and a clean-looking log proves nothing.

Common misconception: "TLS was broken"

heartbleed.com is explicit that this was a programming mistake in one implementation, not a flaw in the TLS protocol design. The protocol did what it was designed to do; one library failed to protect the memory around it. That is also why the bug was invisible to anyone looking at the encrypted traffic alone: the leak travelled inside a valid, encrypted session.

Timeline and affected versions

According to heartbleed.com the affected versions were OpenSSL 1.0.1 through 1.0.1f, fixed in 1.0.1g; the 1.0.0 and 0.9.8 branches were not affected. The OpenSSL advisory also lists 1.0.2-beta releases as affected, fixed in 1.0.2-beta2, and gives a workaround of recompiling with -DOPENSSL_NO_HEARTBEATS. The bug was found independently by a Codenomicon team and by Neel Mehta of Google Security; the advisory credits Mehta with the discovery and Adam Langley and Bodo Moeller with the fix. NVD lists the CVE as published on 7 April 2014 with a CVSS v3.1 base score of 7.5 (High) (confidentiality high, integrity and availability none).

Why revoking and reissuing mattered

Patching removes the leak, but it cannot un-leak what has already left. If a private key might have been in memory when a request arrived, the only safe assumption is that it was exposed. heartbleed.com therefore advises owners to patch, revoke the potentially compromised certificates and have new keys issued through their Certificate Authority. Two further consequences follow from the same logic. First, session tokens and cookies that were in memory should be invalidated, and users should change passwords, because those are secondary key material. Second, heartbleed.com notes that previously captured traffic may remain decryptable unless the service used forward secrecy, which is why key exchange choices made years earlier decided how bad the exposure was.

Generating the new key after the patch is a detail of the order of operations (general reasoning): a fresh key held by a still-vulnerable process is exposed to the same bug.

The response

The sources describe a coordinated release: the issue was reported to the OpenSSL team, a fix and an advisory were published on 7 April 2014, and heartbleed.com explained impact and clean-up steps for operators. For anyone who could not upgrade at once, OpenSSL offered the compile-time workaround above. I did not find in the fetched sources any count of affected sites, and give none.

Contributing factors

  • A length field taken from the peer was used without being checked against the bytes actually received.
  • The implementation was written in a language without automatic bounds checking, so the mistake became a memory disclosure rather than an error (general explanation; see chapter 12).
  • Secrets and request buffers lived in the same process and could be adjacent in memory, so a read past one could reach the other.
  • A rarely used feature was on by default, so most deployments carried code they did not need (the advisory’s compile-time switch to disable heartbeats shows the feature could be removed).
  • The leak happened inside a normal encrypted session, so it left no obviously abnormal traffic for monitoring to see.

What changed

  • Immediate: OpenSSL 1.0.1g and 1.0.2-beta2 closed the missing check; operators patched, rotated keys and certificates, and invalidated sessions as heartbleed.com advised.
  • The case is widely used as a reason to prefer forward-secret key exchange, and to treat key rotation and revocation as rehearsed procedures rather than emergencies. These are general lessons rather than claims from the fetched sources, which I have not read for any later funding or process changes.

The pattern to remember

Analogy: the clerk who reads back what the form says it is

A clerk is asked to repeat a message back to a caller. The caller says “I will give you a four-word message; read back the first sixty-four thousand words from your notebook,” and the clerk, who never compares the claim with what was said, reads out the next pages of the notebook, which include other customers’ details.

Where it breaks down: a clerk would notice the page numbers; a memory copy has no sense of where one thing ends and another begins.

Key takeaways

  • Any length or count supplied across a trust boundary must be checked against what you actually have.
  • A memory-safety bug is a confidentiality bug: whatever shares the address space can be read.
  • Patching ends the leak; rotation, revocation and session invalidation clean up after it.
  • Forward secrecy limits what a stolen long-term key can do to past traffic.
  • Disable features you do not use; code that is not there cannot be wrong.

The xz Backdoor

In March 2024 a developer investigating a half-second delay in SSH logins found malicious code in the xz compression library, planted by an account that had spent over two years earning the trust of its overworked maintainer. The code lived in release tarballs and test files and was injected at build time.

The pattern in one sentence

Trust in a dependency is trust in its people and its build: verify that what you ship matches what was reviewed, shrink the dependencies of privileged processes, and support the maintainers everyone relies on.

The cast

This page states what the sources say; general explanations are labelled as general. It describes the attack conceptually and gives no payload details beyond what is needed to understand it. Background: chapter 12 (supply chain, build integrity) and chapter 19 (reviewing designs and dependencies).

xz / liblzma

Maintainer
A person with commit, release and decision rights over an open-source project, often unpaid.
Release tarball
A compressed archive a project publishes for a version. It can differ from what a clean checkout of the repository would produce, for example by including generated build files.
Supply-chain attack
Compromising something a target depends on (code, build, distribution) instead of attacking the target directly.
Reproducible build
A build process that gives bit-for-bit identical output from the same source, so independent parties can check that a published artifact matches its source.
sshd
The OpenSSH server daemon. It authenticates remote logins, so code running inside it can influence who gets in.
valgrind
A tool that watches a program’s memory use and reports errors; it is how an anomaly became a lead.

What happened, in short

Andres Freund, a developer who noticed odd behaviour on Debian sid (unstable) machines, reported on 29 March 2024 on the oss-security mailing list that the upstream xz repository and the xz tarballs had been backdoored. NVD describes CVE-2024-3094 as malicious code discovered in the upstream tarballs of xz, starting with version 5.6.0, in which the liblzma build process extracts a prebuilt object file from a disguised test file and uses it to modify liblzma functions. NVD lists a CVSS 3.1 base score of 10.0 (Critical) with the entry published on 29 March 2024. CISA’s alert of the same date names versions 5.6.0 and 5.6.1 and recommends downgrading to an uncompromised version such as 5.4.6 Stable, hunting for malicious activity, and reporting positive findings to CISA.

The slow part: a maintainership, not a bug

Russ Cox’s timeline records how the compromised releases came to exist. In October 2021 an account named “Jia Tan” sent a first, harmless patch to the xz-devel list, followed by more routine patches. In April 2022 other accounts began sending emails pressing for patches to be merged faster and for a new maintainer. The original maintainer, Lasse Collin, replied that his capacity was limited, including because of mental health issues, and noted it was “an unpaid hobby project.” Over the next year Jia Tan gained trust and then responsibility: in mid-2022 Collin called Jia Tan “practically a co-maintainer already”; by the end of 2022 the account was in the project’s GitHub organization and merging commits directly; in 2023 it tagged a release, redirected oss-fuzz bug reports to itself and changed how oss-fuzz built the project. Cox notes that some of the pressure accounts appear nowhere else online, which suggests they were fabricated, a point he attributes to Brian Krebs. Whoever was behind the accounts is not established in the sources I read, and I name no one beyond the account names.

Keeping the story blameless

The maintainer here was a volunteer under sustained pressure, and the attack worked by exploiting a reasonable human response to that pressure: accepting help. The lesson is about how the ecosystem funds, supports and verifies critical maintainers, not about one person’s decisions.

The mechanism: build-time injection, hidden in tarball and test files

Freund’s post describes the mechanism in three parts (paraphrased):

  • Hidden data in test files. The obfuscated payload data sits in test files that were committed to the upstream repository. A binary file that looks like test input draws little review attention, which is why this is a good hiding place.
  • An extra line only in the tarball. A malicious line in the build scripts (build-to-host.m4) appears in the distributed tarballs but not in the upstream repository. That makes the published artifact differ from the source it claims to come from.
  • Conditional activation. An obfuscated script runs at the end of configure and only activates under specific conditions: x86-64 Linux, GCC with the GNU linker and a Debian or RPM package build. When active it modifies the library’s build so that the hidden data is turned into code during the build. NVD describes the result as being able to intercept and modify data in any software linked against the library.

Two general points follow. First, it is a build-time attack: the malicious code never needs to appear in the readable source. Second, the conditions mean it stayed dormant on developers’ laptops and in most continuous-integration runs and activated only in the distribution package builds that attackers wanted.

Why sshd, and how it was noticed

Freund explains that OpenSSH does not use liblzma directly, but some distributions (he names Debian) patch sshd to notify systemd, which pulls in libsystemd and with it liblzma. The backdoored library then hooks the RSA public-decrypt function used during public-key authentication, before login completes. Freund says he suspects it allows unauthorised access or remote code execution; this page makes no further claim about what it did. He also notes it appears to work only on glibc-based systems and checks its environment, which makes analysis harder.

The discovery was a performance anomaly followed to its source. Over several weeks Freund saw SSH logins using more CPU than expected, and valgrind reported errors. Timing showed an SSH login rising from about 0.30 seconds to about 0.81 seconds of real time. On his older system sshd -h took about 0.5 seconds with the backdoored library loaded, against about 0.01 seconds when the environment was set so as not to trigger it. He notified Debian and other distributions privately on 28 March and posted publicly on 29 March. His words: “The upstream xz repository and the xz tarballs have been backdoored.”

Cox’s timeline adds context: Red Hat distributions had started seeing valgrind errors in liblzma from 4 March; the backdoored 5.6.0 had been tagged on 24 February 2024 and 5.6.1 on 9 March; Debian had added 5.6.0 to unstable on 26 February and moved it to testing on 5 March; Red Hat said the backdoored xz shipped in Fedora Rawhide and Fedora 40 beta. Freund notes that few distributions had integrated the affected versions yet, mostly only pre-release ones.

A near miss that depended on luck and curiosity

No scanner or review flagged this. A developer who cared about half a second found it. That is encouraging about the value of curiosity and sobering about the margin: the same backdoor with a lower performance cost might have been in stable releases for years (general reflection, not a claim from the sources).

Contributing factors

  • A critical, widely depended-on component was maintained by one unpaid volunteer, and social pressure was applied to hand over responsibility.
  • Trust was granted on the basis of a record of small, plausible contributions; project governance had no mechanism to verify who a new co-maintainer was.
  • Release tarballs were built and published by a maintainer, with generated files not present in the repository, so what distributors built from was not what reviewers read.
  • Opaque binary test data lived in the source tree, which is hard to review.
  • Dormant-unless-conditions-match design avoided detection by testing and by most users.
  • sshd gained a transitive dependency on a library it had no need for, through a distribution patch (the dependency chain, not the patch authors, is the issue).
  • Infrastructure meant to find bugs was within the new maintainer’s control: Cox records oss-fuzz reports being redirected and a feature disabled in oss-fuzz builds.

What changed

Distributions rolled back to older releases within days (for example Debian to a 5.4.x version), and CISA issued its alert. The sources I fetched do not give a full account of longer-term changes, so the following are general lessons rather than claims about what happened afterwards:

  • Dependencies: Cox records a systemd change opened on 29 February 2024 to stop linking liblzma into libsystemd, merged 5 March, which he says would have defeated this particular path. Reducing the dependencies of security-critical processes shrinks the places such code can run.
  • Tarball versus repository: build from a verified checkout, or diff the tarball against the tagged source and review the differences. Reproducible builds and signed provenance (see chapter 12) turn “does this artifact match the source?” into a mechanical check.
  • Maintainer sustainability: fund and support the small projects that large systems depend on, and have a succession and trust process that does not rely on one person’s inbox.
  • Observation: performance and behaviour baselines on critical daemons are a detection control. A small unexplained slowdown in an authentication path deserves investigation.

The pattern to remember

Analogy

A town depends on one volunteer lighthouse keeper. A helpful newcomer spends two years carrying supplies, is trusted with the keys, and quietly changes how a lamp is made in the workshop where the lenses are cast. Everyone inspecting the lighthouse sees a normal lamp; only the lenses that ship to certain harbours are different.

Where it breaks down: Software artifacts can be compared bit by bit, which a lens cannot; the comparison just has to be done by someone.

Key takeaways

  • Trust in open source includes trust in people; slow social engineering is an attack on maintainership, not on code.
  • What you build and ship may not be what you reviewed. Compare release artifacts with source, and prefer reproducible builds.
  • Opaque test and binary files in a source tree deserve the same scrutiny as code.
  • Every dependency of a privileged process is part of its attack surface, including indirect ones.
  • Treat unexplained performance changes in authentication paths as security signals.
  • Support the maintainers you depend on; sustainability is a security control.

What kind of attack was the xz compromise, at its core?

  1. A memory-safety bug in sshd
  2. A multi-year supply-chain attack combining social engineering of maintainership with a build-time payload
  3. A stolen TLS certificate
  4. A denial-of-service flood
The sources describe a long trust-building campaign and hidden code that became part of liblzma at build time.

What was the tarball-versus-repository difference?

  1. The tarball was smaller
  2. A malicious build-script line existed in the distributed tarballs but not in the upstream repository
  3. The repository was encrypted
  4. Nothing differed
Freund reports the extra line only in the tarballs, while the disguised data files were in the repository.

Why did code in a compression library matter to SSH logins?

  1. OpenSSH compresses passwords with it
  2. A distribution patch linked sshd to libsystemd, which links liblzma, so the library loaded into the sshd process
  3. liblzma replaces the SSH protocol
  4. It runs on the client only
Upstream OpenSSH does not use liblzma; the dependency came through libsystemd in patched builds.

What first revealed the problem?

  1. An antivirus alert
  2. An SSH login slowdown of roughly half a second and valgrind errors, investigated by a developer
  3. A CISA scan
  4. A user complaint about disk usage
Freund measured about 0.30 s rising to about 0.81 s per login and followed the valgrind errors.

Which response best addresses the tarball-versus-repo gap?

  1. Trusting maintainers more
  2. Reproducible builds or diffing the artifact against the tagged source
  3. Longer passwords
  4. Disabling all compression
If anyone can rebuild the artifact from source and get the same bytes, an extra line in the tarball shows up.

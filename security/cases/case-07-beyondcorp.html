BeyondCorp: Google’s Zero Trust

In 2014 Google described how it was moving corporate access decisions away from a privileged network and onto the identity and state of users and devices, with every application reached through an access proxy.

The pattern in one sentence

Make the network untrusted and move the decision to a per-request check on who the user is, which device they hold and how much that device can be trusted, then migrate to it gradually by measuring.

The cast

This page states what the 2014 article says; general explanations are labelled as general. It is a description of one organization’s design at one point in time, not a product guide. Background: chapter 13 (zero trust) and chapter 5 (authentication, second factors, device-bound credentials).

Perimeter security
Protect the edge of a private network with a firewall and trust what is inside. The article compares it to a castle with a moat and one guarded gate.
Managed device
In BeyondCorp, a device procured and actively managed by the enterprise; only managed devices can access corporate applications.
Device inventory database
The record of every managed device and its changes through its life cycle, which feeds access decisions.
Trust inference
Dynamically deciding how much to trust a device or user from several data sources, using static rules and heuristics.
Access proxy
An Internet-facing reverse proxy in front of every corporate application that enforces encryption and access checks.
Access Control Engine
The component in the proxy that makes a per-request authorization decision from user, group, device certificate and inventory data.
Unprivileged network
A client network deliberately given almost the same access as the open Internet, plus a few infrastructure services.

The problem the article names

Ward and Beyer open with the weakness of the perimeter model: once an attacker passes the firewall, they have relatively easy access to the privileged intranet, and the perimeter becomes harder to define as employees use mobile devices and cloud services. Their stance: “one should assume that an internal network is as fraught with danger as the public Internet.” Their response is to remove the requirement for a privileged intranet and move corporate applications to the Internet. In the article’s words, access depends solely on device and user credentials, regardless of network location, and all access is fully authenticated, fully authorized and fully encrypted based on device state and user credentials.

Common misconception: "zero trust means no network controls"

BeyondCorp still has a network, with a strictly managed ACL between the client network and the rest, and it still has a firewall-like boundary around infrastructure. What changes is that the network no longer confers trust: being on it grants nothing that the open Internet would not.

Components

Device inventory and identity

Because Google had several inventory databases, a meta-inventory amalgamates and normalizes them. Each managed device gets a certificate, stored in a Trusted Platform Module or a qualified certificate store, and a device must be present and correct in the inventory to receive one. The article is careful about what this means: the certificate uniquely identifies the device, but it does not by itself grant access; it is a key to a set of information about the device. A qualification process checks the certificate store, and the checks are enforced again as certificates renew.

User identity and single sign-on

A user database and group database are integrated with HR processes, so joiners, movers and leavers are reflected. An externalized single sign-on system validates primary and second-factor credentials and then issues short-lived tokens for specific resources.

Trust inference

The article says trust in a device or user is inferred dynamically from multiple data sources. A device lacking a recent OS patch level might get reduced trust; a class of device such as a particular phone model might get a particular level; a user connecting from a new location might get a different level. Rules and heuristics produce the levels. A pipeline continuously feeds the access engine certificate allowlists, trust levels and inventory details.

The access proxy and Access Control Engine

All corporate applications are exposed, internally and externally, through the Internet-facing access proxy, which enforces encryption, load balancing, access control checks, health checks and denial-of-service protection. Applications are registered in public DNS as aliases of the proxy. In the engine, a default rule restricts access to full-time employees on a managed device; an application owner can add stricter rules, for example restricting the code review tool to engineers on managed devices with the highest trust level. The article notes rules can differ within one application: viewing a bug may need less than updating or searching it. The decision is made on every request.

Removing trust from the network

To make local and remote access equivalent, Google defined an unprivileged network that closely resembles an external network but in a private address space. It connects only to the Internet, a few infrastructure services (the article lists DNS, DHCP and NTP) and configuration management such as Puppet. Wired and wireless access use 802.1x authentication with RADIUS servers assigning a VLAN dynamically: managed devices present their certificate and land on the unprivileged network, and unrecognized or unmanaged devices go to a remediation or guest network.

Removing the VPN privilege and migrating

The article describes the migration as phased, because moving every user and application at once “would be incredibly risky to business continuity”. The elements it lists:

  • Workflow qualification: every application is required to work through the access proxy; each moves through three phases from VPN-only, to available both ways, to proxy-only.
  • Job function analysis: cross-referencing job functions with qualified workflows to choose which groups to migrate first (finance, sales, legal, engineering).
  • Cutting back on VPN: restrict VPN access to people with a proven need, remove access from those who do not use it over a defined period, and encourage active users to give it up when all their workflows are available through the proxy.
  • Traffic analysis pipeline: sampled netflow from every switch is compared with the ACL the unprivileged network would enforce, producing a ranked list of traffic that would have been blocked, which is then tied to workflows, users and devices and fixed progressively.
  • Unprivileged network simulation: a traffic monitor on user devices validates traffic against the ACL in logging mode (record only) or enforcement mode (record and drop).
  • Device-by-device rollout: devices with more than 99.9 percent eligible traffic over 30 contiguous days move to enforcement when they exceed 99.99 percent, and after 30 more successful days this is recorded in the inventory and the device is assigned to the unprivileged network at its next 802.1x authentication.
  • Exemptions: a self-service process for temporary exemptions while a workflow is not yet qualified.

The article ends with a realistic caveat: it anticipates a long tail, such as fat-client applications with proprietary protocols. It also promises follow-up articles. I did not fetch the later BeyondCorp papers, so this page makes no claims about how the design evolved after 2014.

Contributing factors and design choices

  • A clear diagnosis: an internal network as hostile as the Internet, so every application must defend itself.
  • Identity of the device as well as the user, rooted in an inventory the company controls.
  • One enforcement point in front of all applications, so policy is consistent and changeable without touching each app.
  • Authorization using inferred trust, which can change over time as a device falls out of date, rather than a one-time admission check.
  • A measured, reversible migration with simulation and thresholds before enforcement.
  • Attention to user experience: the article claims local and remote access are effectively identical apart from latency.

General observations, not claims from the article: the access proxy becomes a high-value component that must itself be highly available and well defended, and the quality of the device inventory limits the quality of every decision made from it.

What changed

Within Google, the article describes the move as well under way in 2014 with the majority of workflows already qualified. More broadly, the article’s authors set out to encourage other enterprises to adopt similar strategies. Whether, and how, particular organizations did this is outside the sources I read. Chapter 13 draws the general principles.

The pattern to remember

Analogy

Instead of a guard at the castle gate who lets anyone in who is inside the walls, every room has its own door that asks for the person’s badge and checks the badge reader’s record of that person’s laptop and training, every time the door is opened.

Where it breaks down: Doors are slower than a gate; the engineering effort goes into making the per-door check fast and the inventory behind it accurate.

Key takeaways

  • Network location is not a credential: decide access from user identity, device identity and device state.
  • A device certificate identifies a device but should not itself grant access; it points at facts that policy uses.
  • Put one enforcement point in front of everything so policy is uniform and auditable.
  • Trust is a level that changes (patch state, location); recompute it instead of granting it once.
  • Migrate by measuring: simulate, log, enforce, then switch, with exemptions for the long tail.

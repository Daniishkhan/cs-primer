Log4Shell

In December 2021 CVE-2021-44228 showed that Log4j 2 would expand lookup markers inside log messages, including JNDI lookups that contacted servers named in the text, so untrusted input written to a log could lead to remote code execution. The case is also about how hard it was to find every copy of a library you did not choose.

The pattern in one sentence

A component that interprets its input is an interpreter, so keep untrusted text away from powerful expansion features and know which libraries you ship, including the ones you never named.

The cast

This page stays at the level of mechanism. It gives no working string and no instructions for any real system. Related chapters: chapter 9 (injection), chapter 12 (supply chain) and chapter 19 (design review). On logging itself, see reliability chapter 5.

Log4j 2
A widely used Java logging library from the Apache Software Foundation. The vulnerable code was in the log4j-core component.
Lookup (message lookup substitution)
A feature where a marker of the form ${type:name} inside a log message or configuration is replaced by a value computed at run time.
JNDI
Java Naming and Directory Interface: a Java API for looking up named resources, which can be reached through services such as LDAP.
LDAP
Lightweight Directory Access Protocol, a directory service protocol that JNDI can use.
Transitive dependency
A library your software needs because something it depends on needs it, rather than because you named it.
SBOM
Software bill of materials: a machine-readable list of the components in a piece of software. Common formats are SPDX and CycloneDX.

A feature, not a bug in the usual sense

The Apache Log4j security page describes CVE-2021-44228 as JNDI features, in configurations, log messages and parameters, that did not protect against attacker-controlled LDAP and other JNDI endpoints; it says a “JNDI lookup can be exploited to execute arbitrary code loaded from an LDAP server.” NVD adds that an attacker who controls log messages or their parameters can cause this when message lookup substitution is enabled, and that the behaviour was disabled by default in 2.15.0 and fully removed in 2.16.0. NVD lists CVE-2021-44228 as published on 10 December 2021, CVSS v3.1 10.0 (Critical), and credits it on the Apache page to Chen Zhaojun of the Alibaba Cloud Security Team. CISA states that an unauthenticated remote attacker could exploit the flaw to take control of an affected system.

The key observation is that nothing here is memory corruption. The library did what it was built to do: expand markers in text. The mistake was one of design (general analysis): the text being expanded included data supplied by outsiders, and the set of things a marker could trigger included contacting a remote server and using its answer. This is injection in the sense of chapter 9: data crossed into a language that had power over the system.

Why a logging library could load remote code

Three ordinary decisions combined, none of them unreasonable alone (general analysis, not a claim from the sources).

  1. Logs contain untrusted text by design. Applications log request headers, usernames and search terms, because those are what you need when something goes wrong. A log call is therefore a path from the outside world into the library.
  2. The library offered useful substitutions. Being able to insert environment variables, context values or names looked up elsewhere is convenient in configuration files, and the same expansion ran over the messages themselves.
  3. One of the substitutions could reach out. A lookup that consults a directory service can, by design, make a network request and use the answer. Combined with a Java mechanism for loading what a directory points to, a log line could become an instruction to fetch and use something remote.

Common misconception: "logging is a safe sink"

We tend to think of output paths as one-way: data goes in and nothing comes back. A logger that interprets its input is not a sink, it is an interpreter. The same instinct leads to treating a template engine, a report generator or a configuration loader as passive. If a component expands, evaluates or fetches based on content, then whoever controls the content controls that component, and where the content came from matters.

Outbound network access mattered too. The attack needed the vulnerable host to reach a server of the sender’s choosing. Egress filtering, which blocks a server from connecting to arbitrary outside addresses, is a general control that would have broken that step; it is not a substitute for patching, and the sources I fetched do not discuss it.

The follow-up CVEs

The first fix did not close everything. The Apache security page lists:

  • CVE-2021-45046 (CVSS 9.0, Critical): the fix for 44228 was incomplete in certain non-default configurations using a Thread Context lookup in Pattern Layout, allowing information leaks and code execution. Fixed in 2.16.0 (Java 8 and later).
  • CVE-2021-45105 (CVSS 5.9, Medium): self-referential lookups could cause unbounded recursion and process termination, a denial of service. Fixed in 2.17.0.
  • CVE-2021-44832 (CVSS 6.6, Medium): an attacker with write access to the logging configuration could use a JDBC Appender data source with a JNDI URI to execute code. The fix limits JNDI data source names to the java protocol; fixed in 2.17.0.
  • For Log4j 1, which is end-of-life, the page points to auditing for the JMSAppender (tracked as CVE-2021-4104).

The pattern is familiar: a fix addresses the reported path and leaves related ones. CISA’s later guidance names 2.17.1 for Java 8, 2.12.4 for Java 7 and 2.3.2 for Java 6 as the versions to upgrade to. Treat this as a reminder that remediation is a sequence, so track the whole advisory, not the first number.

Scale: the transitive-dependency problem

CISA describes the library as used broadly in consumer and enterprise services, websites, applications and operational technology products, and describes “active, widespread exploitation.” It added the CVE to its Known Exploited Vulnerabilities Catalog on the day NVD published it (10 December 2021, with a federal due date of 24 December 2021) and issued Emergency Directive 22-02 on 17 December 2021. I give no counts of affected systems because none of the pages I fetched supply one.

Why was it hard to answer “are we affected?” The answer lives in components you never chose directly. Your build file names a framework; the framework names an adapter; the adapter names the logger. A product you bought may bundle its own copy that appears in no build file of yours. Hence CISA’s guidance: scope all assets including internally developed software and non-internet-facing systems; enumerate continuously by scanning networks, hosts and file systems; and check SaaS and cloud services as well.

SBOM lessons

  • A software bill of materials turns “search every machine for a file” into “query a list,” provided it is accurate and covers transitive components (general; formats SPDX and CycloneDX). The CISA page I fetched does not itself mention SBOMs, so this is my inference from its call to enumerate continuously.
  • An SBOM is only a list. It does not tell you whether the vulnerable code path is reachable in your configuration, which is why both inventory and configuration review matter.
  • Ask suppliers for theirs. For bundled products, the vendor is the one who can answer, and CISA tells vendors to identify, mitigate and update affected products and to tell customers to prioritise updates.
  • Keep the list current at build time, not as a quarterly spreadsheet.

Mitigations

  • Upgrade. The Apache page's primary remediation for each CVE is to move to the fixed version (see the cascade above), and CISA says to apply updates immediately.
  • If you cannot upgrade, apply temporary mitigations from the vendor, and CISA adds that an asset that cannot be patched or mitigated should be considered for removal from the network. For CVE-2021-45105 the Apache page also lists a configuration alternative, with a caveat for older releases.
  • Investigate, do not only patch. CISA notes that logs from affected services will contain user-controlled strings, so review for signs of compromise.
  • Reduce what injected content can do (general): egress filtering, least privilege for the service account, and treating configuration write access as sensitive, which is the CVE-2021-44832 lesson.
  • Remove unneeded features (general): the eventual fix was to remove the JNDI message lookup entirely.

Contributing factors

  • A powerful expansion feature ran over data that included untrusted input.
  • The feature could initiate network lookups and use the response.
  • The component was embedded in a very large number of products, often invisibly.
  • Many organisations lacked a quick way to enumerate where it ran (CISA’s guidance on continuous enumeration points to this).
  • Initial fixes left adjacent paths, so remediation took several releases.

What changed

  • The library disabled the behaviour by default in 2.15.0 and removed it in 2.16.0 (NVD).
  • Federal agencies were directed under Emergency Directive 22-02 to patch internet-facing assets and apply mitigations where patches were unavailable (CISA).
  • The incident became a standard example in discussions of SBOMs and dependency inventories. That is general context; I did not fetch a source on policy changes.

The pattern to remember

Analogy: the minutes-taker who obeys what the speakers say

A secretary takes minutes at a meeting. A rule in the style guide says that text in brackets is an instruction: “[insert the latest figure from the archive at this address].” A visitor who is allowed to speak says a sentence with brackets in it, and the secretary fetches whatever the address returns and pastes it into the official record.

Where it breaks down: a secretary only writes; here what was fetched could be run.

Key takeaways

  • A component that interprets its input is an attack surface, even if its job looks passive.
  • Features that fetch from the network need an allow-list, not an open door.
  • Know your transitive dependencies; an inventory beats a scramble.
  • Fixes can be incomplete. Follow the whole advisory family.
  • After patching, check for compromise.

Check your understanding

What feature of Log4j 2 did CVE-2021-44228 abuse?

  1. Log rotation
  2. Message lookup substitution reaching JNDI endpoints
  3. Log compression
  4. Remote log shipping
NVD and Apache describe JNDI lookups through message lookup substitution that did not guard against attacker-controlled endpoints.

Why could a log line influence the system at all?

  1. Logs are executed by the OS
  2. Applications log untrusted text, and the library expanded markers inside that text
  3. Log files are world-writable
  4. JNDI is a logging format
Untrusted data reached a component that interpreted markers.

What did the follow-up CVEs show?

  1. The original fix was perfect
  2. Related paths and configurations also needed fixes across several releases
  3. Log4j was abandoned
  4. They were duplicates
CVE-2021-45046, 45105 and 44832 were separate issues fixed in 2.16.0 and 2.17.0.

Why was exposure hard to measure?

  1. The library is closed source
  2. It was often a transitive or bundled dependency not listed in an organisation’s own build files
  3. It only ran on one OS
  4. Nobody used it
CISA tells organisations to scope all assets and enumerate continuously, since early efforts may have covered only some.

What does an SBOM not tell you by itself?

  1. Which components are present
  2. Whether the vulnerable code is reachable in your configuration
  3. Which versions are present
  4. Who supplies each part
An SBOM is an inventory; reachability and configuration still need review.

Zanzibar: Authorization at Google Scale

Google’s 2019 paper describes one global system that stores permissions as relation tuples and answers permission checks for many products, using consistency tokens so that removing someone’s access can never be undone by a stale replica.

The pattern in one sentence

Store permissions as facts about relationships, derive the rest by rules, and make every check carry a consistency token so that an access removal is always respected, even when answers come from replicas.

The cast

This page states what the paper says; general explanations are labelled as general. Background: chapter 8 (authorization models, relationship-based access) and chapter 15 (isolating tenants).

ACL (access control list)
A list of who may do what to an object.
Relation tuple
One stored fact of the form object, relation, user. In the paper’s notation: namespace:object#relation@user, where the user may itself be a set of users such as group:eng#member.
Userset
A set of users defined by an object and a relation, for example the members of a group. Usersets let an ACL refer to groups and so represent nested membership.
Namespace configuration
Per-namespace policy: the relations and the userset rewrite rules that say how one relation derives from others.
New enemy problem
A user who should have lost access still sees new content, because the check ignored the order of ACL changes or applied an old ACL to new content.
Zookie
An opaque consistency token that encodes a timestamp. It lets a check say “evaluate at a snapshot at least as fresh as this”.
TrueTime
Spanner’s clock mechanism that assigns timestamps consistent with the real-time order of transactions.
Leopard
Zanzibar’s specialised index for set computation on deeply or widely nested groups.

The problem Zanzibar was built to solve

The paper describes Zanzibar as the system Google uses to store permissions and perform authorization checks for many of its products. Its goals are correctness (consistent decisions that respect user intent), flexibility (consumer and enterprise policies), low latency, high availability and large scale. The abstract states the headline results: it scales to trillions of access control lists and millions of authorization requests per second to support services used by billions of people, and it has maintained 95th-percentile latency of less than 10 milliseconds and availability of greater than 99.999% over 3 years of production use. The paper gives three reasons for a single shared system: consistent semantics and user experience across applications, easier interoperability when one application embeds another’s objects, and shared engineering.

The model: tuples and namespace configs

Each ACL is a collection of relation tuples, and groups are simply ACLs with membership semantics. Defining the data model around tuples, not per-object ACLs, unifies ACLs and groups and enables efficient reads and incremental updates. The primary key of a tuple is its namespace, object ID, relation and user.

Tuples do not by themselves define the effective ACL. A namespace configuration holds object-agnostic rules, userset rewrites, so the system need not store (and keep updating) one “editors are also viewers” tuple per object. The leaves of a rewrite expression are:

  • this: the users in stored tuples for the object and relation, including indirect usersets they reference;
  • computed_userset: derive a userset from another relation on the same object, giving inheritance between relations;
  • tuple_to_userset: look up related objects through tuples (for example the document’s parent folder) and use a relation on them, which expresses “inherit the viewers of the parent folder”.

Expressions combine with union, intersection and exclusion. The paper’s Figure 1 shows owners being editors, editors being viewers, and viewers of the parent folder being viewers of the document. The API offers Check, Read, Write, Watch and Expand (inspecting the effective ACL). Read returns stored tuples and does not apply rewrites, so Expand exists for the effective set.

Common misconception: "Zanzibar is just an ACL table"

A flat table of (user, object, permission) cannot express inheritance, groups of groups or cross-application relationships without exploding in size. The ideas here are indirection (usersets), derived relations (rewrites) and a graph walk at check time. The paper reports the median namespace configuration at about 500 lines, so the policy is code-like, not trivial.

Consistency: the new enemy problem and zookies

The paper names two failure modes. In example A, Alice removes Bob from a folder, then asks Charlie to move new documents into it; if the check neglects the ordering of those two changes, Bob may see documents he should not. In example B, Alice removes Bob from a document and then adds content to it; a check evaluated with a stale ACL from before the removal lets Bob see the new content. Preventing this means respecting the causal order of changes, even those coordinated through channels Zanzibar cannot see. The paper says this requires external consistency and snapshot reads with bounded staleness.

Zanzibar stores ACLs in Spanner, whose TrueTime mechanism assigns each write a microsecond-resolution timestamp consistent with causal order. Each check is evaluated at a single snapshot timestamp across all its reads. The paper notes that always evaluating at the latest snapshot would need global synchronisation, high-latency round trips and limited availability. The protocol is instead:

  1. When content is about to be modified, the client asks Zanzibar for a content-change check, which returns a zookie encoding a current global timestamp, and stores the zookie atomically with the content.
  2. Later ACL checks for that content send the zookie, which guarantees the check snapshot is at least as fresh as the content version.

The “at least as fresh” semantics are what make this efficient: Zanzibar may choose any timestamp fresher than the zookie. So most checks are served at a default staleness from locally replicated data, and timestamps can be quantised to share cache entries. The paper chose an opaque cookie rather than a raw timestamp to discourage clients from choosing arbitrary timestamps and to allow future extensions. For the underlying ideas about clocks and ordering see Distributed Systems chapter 7 (time, revisited).

Leopard: indexing nested groups

Evaluating a check by recursive pointer chasing is slow for deeply nested or very wide groups. For selected namespaces Zanzibar uses Leopard, an index that stores named sets as (type, set ID, element ID) tuples and evaluates unions, intersections and exclusions. Group membership uses two set types: GROUP2GROUP (all descendant groups of an ancestor) and MEMBER2GROUP (the groups of which a user is a direct member). A user U belongs to group G if the intersection of MEMBER2GROUP(U) and GROUP2GROUP(G) is non-empty. The index is stored as ordered integer lists in a structure such as a skip list, so an intersection of A and B needs O(min(|A|, |B|)) seeks, and it is sharded by element ID.

Leopard has three parts: a serving system, an offline periodic index builder that works from a snapshot, and an online layer that applies changes continuously. Because offline generation and shard swapping cannot be consistent with a fresh snapshot, an incremental layer indexes all updates since the offline snapshot, each with its timestamp; those at or before the query timestamp are merged on top of the offline index during a query. The paper adds that a single tuple addition or deletion may yield potentially tens of thousands of discrete Leopard tuple events, which is the price of denormalising.

Caching and hot spots

Zanzibar otherwise keeps data normalised for consistency. The paper calls hot-spot handling “the most critical frontier in our pursuit of low latency and high availability”. The techniques it describes:

  • Distributed cache: servers in a cluster form a cache for reads and for check evaluations, including intermediate results, with entries placed by consistent hashing and a forwarding key derived mostly from the object ID, so related sub-checks land on the same server.
  • Cache trees: results are cached at both caller and callee of internal calls, and Slicer helps spread hot keys over more servers.
  • Timestamp quantisation: cache keys include the snapshot timestamp so results from different snapshots are never mixed, and evaluation timestamps are rounded up to a coarse granularity such as one or ten seconds, so most recent requests share cache entries. Rounding up does not break consistency because a Spanner snapshot at T observes all writes up to T.
  • Lock table: per server, so that of the concurrent requests with the same cache key only one is processed and the rest wait (protection against a cache stampede).
  • Hot objects: for a very popular object, read and cache all of its tuples for that relation instead of one lookup per user, detected dynamically by counting outstanding reads.
  • Delayed cancellation: avoid cancelling an indirect check when other requests are waiting on its lock table entry.
  • Isolation: limits on outstanding calls and concurrent reads per client and per object; and request hedging for slow Spanner and Leopard calls.

Descendants

Several open-source systems, including SpiceDB and OpenFGA, are inspired by the paper and offer the same style of model: relationship tuples, a schema or model that defines derived permissions, and a check API, with some form of consistency token. They typically store tuples in ordinary databases and therefore make different trade-offs from Google’s Spanner-based design. This paragraph is general knowledge, not from the paper; I did not fetch those projects’ documentation.

Contributing factors and design choices

  • One shared authorization service gives consistent semantics, at the price of becoming a critical dependency for every product that uses it.
  • Tuples plus rewrites separate stored facts from policy, keeping storage small and policy changes cheap.
  • A strongly consistent store (Spanner) with an explicit consistency token lets the common case be cheap and the dangerous case be safe.
  • Normalised storage keeps consistency simple; denormalised indexes are used only where nesting makes checks too slow.
  • Heavy investment in caching, de-duplication, hedging and isolation, because the hot path of user interactions includes an ACL check.

What changed

The paper is a description of a system in production, not an incident. Its impact is architectural: relationship-based access control with explicit consistency became a widely copied reference design. Chapter 8 builds a small version.

The pattern to remember

Analogy

A building has a central badge office that doors ask whether a person may enter. When someone is dismissed, any door that opens afterward must consult a record at least as new as the dismissal. Each file carries a stamp from the badge office’s clock, taken when the file was last changed, and any later question about that file must be answered from records at least that new.

Where it breaks down: A real badge office has one location; Zanzibar answers from replicas around the world and the timestamp rule is what lets it do so safely.

Key takeaways

  • Model permissions as relations between objects and users, and derive more permissions with rewrite rules rather than copying data.
  • Authorization must respect the order of changes: removing access then adding content must never expose the content.
  • A consistency token (a zookie) lets most reads be stale-but-safe while the dangerous ones are fresh.
  • Index nested groups with precomputed set structures, and keep them correct with an incremental layer.
  • At scale, hot-spot handling dominates: cache, quantise timestamps, de-duplicate and isolate.

Check your understanding

What is a relation tuple in Zanzibar?

  1. A signed token
  2. An object, a relation and a user (or userset), such as doc:readme#viewer@group:eng#member
  3. A network route
  4. A table of passwords
ACLs and groups are both collections of tuples in the paper’s notation.

What does a userset rewrite such as computed_userset achieve?

  1. Encrypts the tuple
  2. Derives a relation from another on the same object, for example viewers include editors, without a tuple per object
  3. Deletes the old ACL
  4. Changes the user ID
Rewrites are object-agnostic rules in the namespace config, giving inheritance between relations.

What is the new enemy problem?

  1. A user is blocked who should have access
  2. A removed user can still see new content because ACL changes were mis-ordered or a stale ACL was applied to new content
  3. Two groups share a name
  4. A server runs out of memory
The paper’s examples A and B show ordering and staleness failures.

How does a zookie prevent it without forcing every check to be fully fresh?

  1. It encrypts the check
  2. It encodes a timestamp so the check snapshot must be at least as fresh, while the system may pick any fresher snapshot
  3. It disables caching
  4. It makes all reads go to one region
At-least-as-fresh semantics let most checks use local replicas and quantised timestamps.

Why does Zanzibar use Leopard for some namespaces?

  1. To store passwords
  2. Recursive pointer chasing is slow on deeply or widely nested groups; set intersections over precomputed indices are fast
  3. To compress logs
  4. To replace Spanner
Leopard flattens group membership into sets so a check is an intersection of two sorted lists.

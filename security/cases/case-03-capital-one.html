Capital One, 2019

In 2019 an outsider used a misconfigured web application firewall to reach Capital One data stored in the cloud. The case shows how a request-forwarding flaw, a host-local metadata endpoint and a role’s permissions combine, and why AWS later made its metadata service require a session token.

The pattern in one sentence

A forwarded request borrows the identity of the machine that sends it, so the permissions of that identity are the real boundary: scope the role and require the stronger metadata protocol.

The cast

This page is deliberately blameless and factual: it describes a failure of controls, not of people. It states what Capital One, the US Department of Justice, the OCC and AWS say; general explanations are labelled. Related chapters: chapter 11 (SSRF), chapter 14 (cloud identity and IAM) and chapter 2 (least privilege).

Web application firewall (WAF)
Software that filters or inspects HTTP requests before they reach an application. Many WAFs act as a reverse proxy and make outbound requests themselves.
SSRF
Server-side request forgery: getting a server to make a request on the requester’s behalf, to a place the requester could not reach directly (chapter 11).
EC2 instance metadata service (IMDS)
A service reachable only from the instance, at the link-local address 169.254.169.254, that returns information about the instance including, when a role is attached, temporary credentials for that role.
Role credentials
Short-lived keys that let software act with an IAM role’s permissions without a stored long-term secret.
S3
Amazon’s object storage service, which authorises requests by the identity behind the credentials.
Least privilege
Giving each identity only the permissions its job needs.

What the public record says

Capital One’s own statement says the incident occurred on 22 and 23 March 2019. A security researcher reported a configuration vulnerability on 17 July 2019, and Capital One confirmed unauthorised access on 19 July 2019. It reports about 100 million people in the US and about 6 million in Canada affected, with most data being credit card application information from 2005 to early 2019, plus credit scores, limits, balances and payment history, and transaction data fragments from 23 days across 2016 to 2018. It also reports about 140,000 US Social Security numbers (the company page also records about 4,700 more identified in 2021), about 80,000 linked bank account numbers and about 1 million Canadian Social Insurance numbers, and says credit card account numbers and log-in credentials were not compromised. Capital One says it “immediately fixed the issue” and worked with law enforcement.

The DOJ’s case page for United States v. Paige Thompson says an individual was charged by criminal complaint with computer fraud and abuse for breaking into stored data belonging to Capital One, and that the intrusion used a “misconfigured web application firewall.” It records that a GitHub user alerted Capital One on 17 July and that Capital One confirmed the intrusion and contacted the FBI on 19 July. The page I fetched states no verdict or sentence and was last updated in January 2022, so I give none. Court proceedings are the place for facts about an individual; this page is about the system.

The mechanism, as a chain of trust assumptions

Each arrow in the diagram crosses a trust boundary, and each rested on an assumption.

  1. The WAF is a gate. A WAF sits in front of an application and makes some requests itself. If it is configured so that a requester can influence where it sends them, it becomes a request-forwarding proxy for outsiders. DOJ’s wording is “misconfigured.”
  2. The metadata address is only reachable from the instance. This is true, and it is exactly why SSRF is dangerous: the instance is the one thing that can reach the address, so a forwarded request arrives with the instance’s privileges.
  3. Role credentials come with the machine. AWS documents that the metadata service provides temporary credentials for the role attached to the instance, with no stored key to steal. The convenience means that anything able to make the instance send a request can read them (chapter 11).
  4. The storage service trusts the credentials, not their origin. The credentials work from anywhere until they expire, so once copied they can be used outside the instance (general behaviour of temporary credentials).
  5. The role was broad enough to matter. What an attacker can read after step 4 is bounded only by the role’s permissions.

Common misconception: "the cloud provider was breached"

Coverage found by search quotes Amazon as saying AWS was not compromised and functioned as designed, and the DOJ case page describes a misconfiguration at the customer. This is the shared responsibility model: the provider secures the service; the customer configures the application, the firewall and the role. A single misconfiguration in the customer’s layer was enough, because the next layers trusted it.

What the OCC said

On 6 August 2020 the OCC announced an $80 million penalty against Capital One’s two banking entities. It said the bank had not established effective risk assessment processes before moving major IT operations to the public cloud and had not corrected deficiencies in a timely manner, characterised these as unsafe or unsound practices, and credited the bank’s customer notification and remediation work. The announcement is about the control environment around the move to cloud: assessment, internal controls and follow-through. It does not describe a technical step-by-step.

IMDSv2: an industry response, later

On 19 November 2019 the AWS Security Blog published a post on new defence in depth for the metadata service. AWS describes IMDSv2 as adding protection against four situations: misconfigured open WAFs, misconfigured open reverse proxies, unpatched SSRF vulnerabilities, and misconfigured open layer-3 firewalls or NAT devices. The mechanism: software first sends an HTTP PUT to obtain a session token, then includes the token in a header on later requests. Open WAFs rarely pass PUT, and many SSRF flaws let attackers control only a URL, not headers. The service also refuses tokens to requests that carry an X-Forwarded-For header, and the token response has an IP TTL (hop limit) of 1 by default, so it is discarded if the instance is misconfigured to route onward. The AWS user guide confirms the session-token design and says an instance can be configured to accept only IMDSv2.

Two cautions from the same sources. In 2019 IMDSv1 remained available and both versions were enabled by default, so the benefit appeared only once instances were set to require v2. (AWS has since moved the defaults: for example, IMDSv2-only for Amazon Linux 2023 images and newer instance types, and an account-level setting for new launches announced in March 2024. Check current AWS documentation for your region and image.) And AWS calls these measures “belt and suspenders”: they make one step harder; they do not remove the underlying forwarding flaw. I make no claim that IMDSv2 was a response to this specific incident; the sources do not say so.

Least privilege as the blast-radius dial

Every other control in this chain can fail; the role’s permission policy is the last one that decides how much is exposed. A role for a firewall appliance that can list and read a broad set of storage buckets turns any foothold into a data-store compromise. A role scoped to what the appliance really needs (for example, only the objects it serves) turns the same foothold into a small incident. See chapter 14 for IAM policy design and chapter 2 for the principle. I make this point as general design guidance; the sources I could read do not detail the role’s permissions.

Contributing factors

  • A WAF configuration that let an outsider influence where the instance sent requests (DOJ: “misconfigured”).
  • A metadata service answering plain GET requests with role credentials (IMDSv1 behaviour, per AWS).
  • A role with enough permissions that its credentials mattered (general inference from the scale of the data accessed).
  • Discovery through an external report rather than internal alerting: Capital One says a researcher reported the vulnerability on 17 July, months after the March access.
  • The OCC cites gaps in risk assessment before the move to the cloud.

What changed

  • Capital One says it fixed the issue immediately, notified affected customers and offered credit monitoring.
  • The OCC imposed an $80 million penalty and, in its announcement, credited the bank’s customer notification and remediation work. I have not read the order itself, so I do not list its requirements.
  • AWS shipped IMDSv2 in 2019, with options to require it per instance.

The pattern to remember

Analogy: the receptionist with a master key

A building has a receptionist who will phone any extension on behalf of a caller. The directory lists a special internal number that connects to the key cabinet, but only from inside. A caller who can persuade the receptionist to dial that number gets a key, and the key opens every room the receptionist is allowed into.

Where it breaks down: the receptionist is a person who might recognise a strange request; a proxy forwards what it is configured to forward.

Key takeaways

  • An address that only the machine can reach becomes reachable by anyone who can steer the machine.
  • Short-lived credentials remove stored secrets but still inherit the role’s breadth; scope the role.
  • Raise the cost of each step (require IMDSv2, block metadata from proxies) and also remove the flaw.
  • Moving to the cloud moves responsibility for configuration to you; assess risks before you move.
  • Detection that depends on outsiders finding you is not detection.

What does the DOJ case page say the intrusion used?

  1. A stolen password
  2. A misconfigured web application firewall
  3. A malicious insider
  4. A phishing email
The page uses the phrase “misconfigured web application firewall.”

Why is the metadata address dangerous in an SSRF situation?

  1. It is public
  2. Only the instance can reach it, so a forwarded request carries the instance’s privileges
  3. It stores passwords in plain text
  4. It cannot be disabled
The address is host-local; SSRF makes the host the requester.

What does IMDSv2 add that makes SSRF harder?

  1. Encryption of the disk
  2. A PUT-created session token that must be sent in a header on later requests
  3. A firewall in the console
  4. A new IAM role
AWS describes session-oriented requests; many SSRF flaws cannot send PUT or set headers.

Which statement about IMDSv2 is accurate?

  1. IMDSv1 was removed in 2019
  2. IMDSv1 stayed available in 2019; instances could be set to require v2
  3. IMDSv2 fixes SSRF in the application
  4. It was built in response to this incident, as AWS states
AWS says v1 remains available; enforcing v2 is a per-instance setting. The sources do not tie it to this case.

Which control finally bounds how much data credentials can read?

  1. The WAF rules
  2. The role’s permission policy (least privilege)
  3. The session token TTL
  4. The instance type
Whatever the role may read is what the credential holder may read.

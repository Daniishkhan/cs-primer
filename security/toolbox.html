Toolbox

Security tools are best learned by pointing them at something you wrote and reading what they say. These six cards cover the everyday kit of an engineer who builds and reviews systems: a web scanner, a code pattern searcher, dependency and secret scanners, a port scanner and the commands that take a token or certificate apart. Every exercise runs against code or a machine that is yours, and takes about ten minutes.

Only scan what you own or are authorised to test

Scanners, fuzzers and port probes look exactly like attacks to the system on the receiving end, and in many places running them against a system you do not own is a crime, whatever your intent. Every exercise on this page targets 127.0.0.1, your own machine, a throwaway repository you create, or (for the certificate step) the ordinary public handshake that every browser performs. Never point a scanner at a third party's site, a shared environment or a production system without written permission that names the target and the dates.

How to use this page

Jump to a tool when a chapter mentions it. Commands target macOS or Linux (Windows under WSL). I checked command forms against the tools' public documentation (OWASP ZAP, gitleaks, pip-audit, OSV-Scanner, Trivy and Semgrep), and I ran the Python in the Shamir-free exercises (the JWT decoder and the sample files), which I confirm parse and print what is shown. I did not install or run ZAP, Semgrep, gitleaks, pip-audit, OSV-Scanner, Trivy or nmap, and I could not start a local server in the environment I wrote this in. Every output block for those tools is therefore labelled illustrative: the shape is right, the findings and numbers on your machine will differ. Versions move quickly (gitleaks, for example, changed its subcommands recently), so if a flag has changed, trust --help over this page.

One shared lab folder. The exercises share a small folder, ~/sec-lab/, with a web app (app.py), a file with insecure patterns (bad.py) and a requirements.txt with old packages. Each card gives you its files, so you can also do the cards in any order.

Test your own web app

Find what a running application exposes, as a browser or an attacker would see it.

OWASP ZAP

Needs: Python 3.8+ for the target app; Docker Desktop, or the ZAP desktop install · Run: docker pull ghcr.io/zaproxy/zaproxy:stable · macOS: brew install --cask zap for the desktop app · Chapters: 9, 10, 11

ZAP (Zed Attack Proxy, an OWASP project) sits between a browser and an application, records the traffic and can scan it. Its baseline scan is the gentle, CI-friendly mode: it spiders the site for a short time and runs only passive checks, meaning it reads responses and flags things like missing security headers, cookie flags and information leaks, without sending attack payloads. That makes it a good first scan of your own app, and it connects directly to chapter 10 (headers, cookie attributes, CSP).

Only scan what you own or are authorised to test

ZAP can send active attack traffic when you use its other modes (the active scan and the full scan). Use the baseline scan only on a target you own, and treat the active modes as something you do on a staging copy of your own app. Authorisation covers the host, the dates and the type of test.

10-minute guided exercise

1. The target. Save this as ~/sec-lab/app.py. It is a tiny standard-library web app with three pages and a search form that escapes its output. It deliberately sets no security headers, which is what the scan will notice. It binds to 127.0.0.1 only, so nothing else on your network can reach it. (I checked that the file parses; I could not start it where I wrote this page.)

#!/usr/bin/env python3
"""A tiny deliberately plain web app for practising scans. Bound to 127.0.0.1 only."""
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import urlparse, parse_qs
import html

PAGE = """<!doctype html><html><head><title>Notes</title></head><body>
<h1>Notes</h1><form action="/search"><input name="q"><button>Search</button></form>
<p>{body}</p><a href="/about">About</a></body></html>"""

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        url = urlparse(self.path)
        if url.path == "/search":
            q = parse_qs(url.query).get("q", [""])[0]
            body = "You searched for: " + html.escape(q)      # escaped on purpose
        elif url.path == "/about":
            body = "A demo app for scanner practice."
        elif url.path == "/":
            body = "Welcome."
        else:
            self.send_error(404); return
        data = PAGE.format(body=body).encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/html; charset=utf-8")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)
    def log_message(self, *a): pass

if __name__ == "__main__":
    print("serving on http://127.0.0.1:8080")
    HTTPServer(("127.0.0.1", 8080), Handler).serve_forever()

2. Run it in one terminal: python3 ~/sec-lab/app.py. In a second terminal check it answers and look at the headers a browser would see:

curl -si http://127.0.0.1:8080/ | head
HTTP/1.0 200 OK
Server: BaseHTTP/0.6 Python/3.12.x
Date: ...
Content-Type: text/html; charset=utf-8
Content-Length: ...

Note what is missing: no Content-Security-Policy, no X-Content-Type-Options, no frame protection, and a Server header that names the software and version.

3. Run the baseline scan. ZAP's documentation gives this form (the -r report needs the current directory mounted):

cd ~/sec-lab
docker run --rm -v "$(pwd)":/zap/wrk/:rw -t ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t http://host.docker.internal:8080 -r zap-report.html

...
WARN-NEW: Missing Anti-clickjacking Header [10020] x 2
WARN-NEW: X-Content-Type-Options Header Missing [10021] x 3
WARN-NEW: Content Security Policy (CSP) Header Not Set [10038] x 2
WARN-NEW: Server Leaks Version Information via "Server" HTTP Response Header Field [10036] x 3
FAIL-NEW: 0   WARN-NEW: 4   INFO: 0   IGNORE: 0   PASS: 55
  • host.docker.internal is how a container reaches a server running on your own Mac or Windows host through Docker Desktop, which is why the target is written that way even though the app listens only on your loopback. On Linux that name is not set by default; add --add-host=host.docker.internal:host-gateway to the docker run command, or use the ZAP desktop app and point it at http://127.0.0.1:8080. I could not confirm this name resolution here, so if it fails, that is the first thing to check.
  • The script exits with 0 when everything passes, 2 if there are warnings and 1 if there are failures. All alerts are warnings by default, so in CI you tune a config file to turn the ones you care about into failures.
  • Open zap-report.html and read each alert's description and solution.

4. Fix and rescan. Add three lines inside do_GET before self.end_headers(), stop and restart the app, and run the same scan:

        self.send_header("X-Content-Type-Options", "nosniff")
        self.send_header("Content-Security-Policy", "default-src 'self'; frame-ancestors 'none'")
        self.send_header("Cache-Control", "no-store")

The corresponding alerts should disappear (the Server header leak needs a small override of version_string; try it). Clean up with Ctrl-C in the app terminal; nothing else is left running.

What to look for

  • Each alert maps to a defence in chapter 10. The scan found configuration gaps; it cannot see broken authorization (chapter 8) because it does not know who should see what.
  • A baseline scan that passes proves little. It is a floor, run on every build, not a security review.

Common pitfalls

  • Scanning a URL you do not control "just to see". Do not.
  • Running the full or active scan against a shared test environment or anything with real data: it posts forms, creates records and can lock accounts.
  • Treating the report as a to-do list in order. Triage by whether the issue is reachable, exploitable and valuable to an attacker.

Find problems in code and dependencies

Most breaches start with a known weakness that was cheaper to find with a tool than with an incident. These cards look at your source, your dependencies and your history.

Semgrep & static analysis

Needs: Python 3.9+ · Install: python3 -m pip install semgrep (use a virtual environment) or brew install semgrep · Chapters: 9, 19

Static analysis reads code without running it. Semgrep is a pattern matcher that understands syntax: a rule is written in something that looks like the code you are searching for, so you can express "any call to subprocess.run with shell=True" in a few lines instead of a regular expression that breaks on line wraps. It finds the shape of risky code (command injection from chapter 9); it does not prove an input is attacker-controlled unless the rule uses its taint mode.

Only scan what you own or are authorised to test

Semgrep reads source files and runs no attack traffic, so scanning code is low risk. Still scan only code you own or have been given to review, and be careful with the output: findings can describe vulnerabilities in code that is not yours to publish.

10-minute guided exercise

1. A sample file with three calls, one fine and two risky. Save as ~/sec-lab/sample/bad.py (I checked it parses; it is never run):

import subprocess

def ping(host):
    return subprocess.run("ping -c1 " + host, shell=True)          # finding

def ok(host):
    return subprocess.run(["ping", "-c1", host], shell=False)     # fine

def also_bad(cmd):
    return subprocess.check_output(cmd, shell=True)               # finding

2. A rule. Save as ~/sec-lab/rules/shell-true.yml. The ... matches any other arguments, and the second form catches the keyword whatever its position:

rules:
  - id: subprocess-shell-true
    languages: [python]
    severity: WARNING
    message: >-
      subprocess call with shell=True. If any part of the command comes from
      outside, this is command injection. Pass a list of arguments and keep shell=False.
    pattern: subprocess.$FUNC(..., shell=True, ...)

3. Run it, offline and without sending data to the vendor:

cd ~/sec-lab
semgrep --config rules/shell-true.yml --metrics=off sample/

┌────────────────┐
│ 2 Code Findings │
└────────────────┘
    sample/bad.py
       rules.subprocess-shell-true
          subprocess call with shell=True. ...
            4┆ return subprocess.run("ping -c1 " + host, shell=True)
            ...
           10┆ return subprocess.check_output(cmd, shell=True)

Expect exactly two findings (lines 4 and 10 of the sample) and no finding for the list-argument call. A third fix to try: change the pattern to pattern: subprocess.$FUNC($CMD + ..., shell=True, ...) and see that only the concatenated command is flagged. Which is better, a rule that flags every shell=True or one that flags only visible concatenation? (The first misses nothing but is noisy; the second is quieter and misses a command built earlier. Rule design is this trade-off.)

4. Fix the code, by replacing the shell string with a list, and rerun. The findings should drop to zero for those lines. Finally, try the registry rules once you are comfortable: semgrep --config p/python . fetches rule packs from the Semgrep registry (this makes a network request, and I did not run it).

What to look for

  • A rule is documentation of a lesson your team learned. Keep rules in the repository and run them in CI.
  • Pattern matching has false positives (a constant command is safe) and false negatives (the dangerous call is hidden in a helper). Review findings as leads, not verdicts.

Common pitfalls

  • Switching on hundreds of rules at once: developers learn to ignore the output. Start with a handful you would fix on sight.
  • Suppressing a finding with a comment and no explanation. Require a reason in the suppression.

Dependency & image scanners: pip-audit, OSV-Scanner, Trivy

Needs: Python 3.10+ for pip-audit · pip-audit: python3 -m pip install pip-audit · OSV-Scanner: brew install osv-scanner or a release binary from github.com/google/osv-scanner · Trivy: brew install trivy or the packages at trivy.dev · Chapters: 12, 14

Software is mostly other people's code. These scanners take your list of dependencies (and, for Trivy, container images), compare each name and version to databases of known vulnerabilities and report matches. pip-audit uses the Python Packaging Advisory Database; OSV-Scanner uses the OSV database, which aggregates many ecosystems; Trivy covers language packages, operating system packages in images, and misconfigurations. Chapter 12 explains why this matters (see Equifax and Log4Shell in the case studies).

Only scan what you own or are authorised to test

These scanners read your own manifests and query public vulnerability databases for package names and versions; they do not touch running systems. Scan only your own projects or those you are permitted to assess, and treat results for other people's software as confidential until they have had time to fix it.

10-minute guided exercise

1. A manifest with old packages. Save as ~/sec-lab/deps/requirements.txt. These are old, pinned releases of popular libraries, chosen because advisories have been published for them (I did not run the scanners, so the exact advisory IDs below are left for the tools to tell you):

flask==0.12.2
requests==2.19.1
pyyaml==5.3

2. Never install these in your normal environment. pip-audit would normally resolve them by building a throwaway virtual environment; run it in an isolated place such as a fresh python3 -m venv ~/sec-lab/venv-audit, and prefer the pinned, no-install form:

pip-audit --no-deps --disable-pip -r deps/requirements.txt

Found 5 known vulnerabilities in 3 packages
Name     Version ID                  Fix Versions
-------- ------- ------------------- ------------
flask    0.12.2  PYSEC-xxxx-xxxxx    0.12.3
requests 2.19.1  PYSEC-xxxx-xxxxx    2.20.0
pyyaml   5.3     PYSEC-xxxx-xxxxx    5.4

The two flags matter: --no-deps requires every package to be pinned to an exact version and skips dependency resolution, and --disable-pip makes it avoid running pip at all, which is the safer way to audit a file you do not fully trust. (pip-audit's own documentation notes that auditing a file the normal way is as risky as installing it.)

3. OSV-Scanner reads the same file. The current CLI uses scan source; older releases used --lockfile=, so check osv-scanner --help:

osv-scanner scan source -L deps/requirements.txt

Total 3 packages affected by 5 known vulnerabilities (0 Critical, 2 High, 3 Medium, 0 Low, 0 Unknown) from 1 ecosystem.
| OSV URL                                  | CVSS | Ecosystem | Package  | Version | Source               |
| https://osv.dev/PYSEC-xxxx-xxxxx         | ...  | PyPI      | pyyaml   | 5.3     | deps/requirements.txt|
...

4. Trivy scans a directory for vulnerable language packages. Whether it parses a bare requirements.txt depends on the version and on pinned entries; the Trivy documentation lists lock files, so if it reports nothing, that is the reason, and it works best with a lock file or an installed environment:

trivy fs --scanners vuln deps/

deps/requirements.txt (pip)
Total: 5 (UNKNOWN: 0, LOW: 0, MEDIUM: 3, HIGH: 2, CRITICAL: 0)

Trivy also scans container images (trivy image python:3.12-slim), which pulls that public image to your machine and compares its operating system packages with advisories: a useful look at chapter 14's point that an image is a bundle of other people's packages. Scan images you build or use yourself.

5. Compare. Do the three tools agree? Different databases and matching rules give different counts; the useful number is the set of packages with a fixed version available. Update the versions to the "fix" column, rerun, and confirm the findings clear.

What to look for

  • A finding means "this version has a published advisory", not "you are exploitable". Reachability (does your code call the vulnerable function?) decides urgency.
  • Transitive dependencies (the packages your packages use) are most of the list; scan the resolved lock file, not just the top-level file.

Common pitfalls

  • Scanning only once. New advisories appear daily against old code; run on every build and on a schedule.
  • Auto-merging every fix without tests, or never updating at all. Aim for small, frequent, tested updates.
  • Reading a clean result as safety: scanners only know published vulnerabilities, and they cannot see a malicious package that is not yet in a database (xz).

Secret scanners: gitleaks

Needs: git · macOS: brew install gitleaks · Linux: a release binary from github.com/gitleaks/gitleaks, or Docker · Chapters: 4, 12

Developers paste keys into code, commit them and push. Secret scanners search both the working files and the whole git history for strings that look like credentials, using patterns for known formats (cloud keys, tokens) and entropy checks for random-looking strings. The point of the history scan is that deleting a secret in a later commit does not remove it: anyone with a clone can still read it, so a leaked secret must be revoked, not just removed (chapter 4).

Only scan what you own or are authorised to test

Scan repositories you own or are allowed to audit. Never go looking for other people's leaked credentials, and never use a key you find: report it to its owner instead. The exercise uses a throwaway repository and a clearly fake key.

10-minute guided exercise

1. A throwaway repository containing a fake secret that is invalid by construction. The made-up format FAKEKEY_... cannot be a real credential for anything, and a rule that matches it makes the result predictable:

mkdir -p ~/sec-lab/leaky && cd ~/sec-lab/leaky
git init -q
cat > .gitleaks.toml <<'EOF'
[extend]
useDefault = true

[[rules]]
id = "demo-fake-key"
description = "Fake key used in the toolbox exercise"
regex = 'FAKEKEY_[A-Z0-9]{16}'
keywords = ["fakekey_"]
EOF
echo 'API_KEY = "FAKEKEY_0123456789ABCDEF"   # not a real key' > config.py
git add . && git -c user.name=demo -c user.email=demo@example.invalid commit -qm "add config"
git rm -q config.py && git -c user.name=demo -c user.email=demo@example.invalid commit -qm "remove the key"

The last commit removes the file. The secret is gone from the working tree but still in history.

2. Scan the files, then the history. gitleaks v8.19 and later use subcommands (git for a repository's history, dir for plain files); older tutorials show gitleaks detect, which still works but is deprecated:

gitleaks dir -v -c .gitleaks.toml .
# 0 leaks: the file is deleted from the working tree

gitleaks git -v -c .gitleaks.toml .
Finding:     API_KEY = "REDACTED"
Secret:      REDACTED
RuleID:      demo-fake-key
File:        config.py
Commit:      3f9c...
Author:      demo
Date:        ...
1 leaks found    (exit code 1)

Add --redact to keep real secrets out of terminal logs when you scan something genuine. The exit code (0 clean, 1 leaks found) is what a CI job or a pre-commit hook uses to fail the build.

3. Try the built-in rules. The configuration above also enables gitleaks' default rules. Add another file with a line such as password = "correct-horse-battery-staple" and rescan to see whether the generic rules flag it. Then check the exit code with echo $?.

4. Fix properly. In a real incident the order is: revoke and rotate the credential first, then clean history if you must (tools such as git filter-repo rewrite it, but every clone and fork keeps the old copy, which is why revocation comes first), then add a pre-commit hook and a CI scan so it does not recur. Clean up with rm -rf ~/sec-lab/leaky.

What to look for

  • The history scan finding what the working-tree scan missed. This is the whole lesson.
  • Prefixes on your own tokens (like tl_live_ in studio 1) make them easy for scanners to detect.

Common pitfalls

  • Allow-listing noisy findings without checking them, then missing the real one.
  • Scanning only on push. Put the check where the secret has not yet left the laptop: a pre-commit hook, plus the server-side scan as the backstop.
  • Assuming a private repository is safe. Repositories get opened up, cloned and exported.

Look at your own machine and your own tokens

Know what you expose and what a credential actually says.

nmap

macOS: brew install nmap · Debian/Ubuntu: sudo apt install nmap · Chapters: 13, 14

nmap discovers which ports on a host accept connections and, optionally, which service and version is listening. On your own machine it answers a practical question from chapter 13: what is actually reachable, from where? A server that listens on 127.0.0.1 can be reached only from the same machine; one that listens on 0.0.0.0 (all interfaces) can be reached from the network. Developers constantly start databases and dev servers bound to all interfaces by mistake.

Only scan what you own or are authorised to test

Port scanning anything other than your own machine or a network you are authorised to test can be treated as hostile reconnaissance and may breach your provider's terms or the law. This exercise scans 127.0.0.1 and your own machine's address only. Do not scan your router, your neighbours, your office or a cloud host you do not control.

10-minute guided exercise

1. Start two listeners with the Python standard library, one on loopback and one on all interfaces. Use two terminals:

# A: loopback only (reachable from this machine only)
python3 -m http.server 8081 --bind 127.0.0.1
# B: all interfaces (reachable from the network; stop it when done)
python3 -m http.server 8082 --bind 0.0.0.0

2. Scan localhost. -sT is the plain connect scan, which needs no special privileges. -p limits the ports so it finishes in seconds:

nmap -sT -p 8000-8100 127.0.0.1

PORT     STATE SERVICE
8081/tcp open  tproxy
8082/tcp open  us-cli
Nmap done: 1 IP address (1 host up) scanned in 0.05 seconds

The SERVICE names are guesses from a port-number table, not facts: nmap labels ports by number until you ask it to identify them.

3. Identify the service, with version detection, still against loopback:

nmap -sV -p 8081,8082 127.0.0.1

PORT     STATE SERVICE VERSION
8081/tcp open  http    SimpleHTTPServer 0.6 (Python 3.x)
8082/tcp open  http    SimpleHTTPServer 0.6 (Python 3.x)

4. See the difference between the two. Find your machine's own network address (ipconfig getifaddr en0 on macOS Wi-Fi, hostname -I on Linux) and scan that address, which is still your own machine:

nmap -sT -p 8081,8082 192.168.1.23

PORT     STATE  SERVICE
8081/tcp closed tproxy      # bound to 127.0.0.1 only: not reachable on the LAN address
8082/tcp open   us-cli      # bound to 0.0.0.0: reachable

That difference is the whole point. Stop both servers with Ctrl-C. You can also list listeners without scanning at all: lsof -nP -iTCP -sTCP:LISTEN on macOS, ss -ltnp on Linux. This is often the faster check, and nmap's value is seeing the machine as the network does.

What to look for

  • Anything open that you did not intend: databases, admin ports, debug servers. The fix is to bind to loopback, firewall it, or remove it (segmentation and the exposure of chapter 13).
  • The state filtered means a firewall dropped the probe; closed means the host answered that nothing listens.

Common pitfalls

  • Scanning "just a bit" past what you own. Keep the target list explicit.
  • Aggressive options (-A, -T5, script scans) against anything fragile. They are noisy and can disturb old devices; you do not need them for this exercise.
  • Trusting an internal scan as proof of safety from outside: your cloud security groups and NAT decide the external view.

Token and certificate inspection: Python and openssl

Needs: Python 3.8+ (standard library only) and openssl, which ships with macOS (check openssl version; Homebrew's is newer) and most Linux distributions · Chapters: 6, 7, 4

A JSON Web Token (JWT, RFC 7519) is three base64url-encoded parts separated by dots: a header, the claims and a signature (chapter 6). The first two are just encoded, not encrypted, so anyone holding a token can read it. That is worth seeing once. Likewise an X.509 certificate is a structured document whose fields you can print. Both exercises use nothing but local commands.

Only inspect what you own or are authorised to test

Decode tokens that belong to your own test systems, or tokens you generate here. A real access token is a credential: do not paste it into an online decoder, a chat or a ticket (the site now holds a working key), and do not use one to call a service you are not authorised to use. The certificate step connects to a public website exactly as a browser does and only reads what the server offers to every visitor; do not run scanners or stress tests against it.

10-minute guided exercise

1. Make and decode a demo token. This script builds a throwaway HS256 token with a made-up secret, then decodes it the way any attacker or debugger can. Save as ~/sec-lab/jwt_demo.py and run it (I ran this code and the output below is real; the signature segment depends on the secret and claims, so yours will match if you keep them unchanged):

import base64, json, hmac, hashlib

def b64u(b): return base64.urlsafe_b64encode(b).rstrip(b"=")
def unb64u(s): return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))

# Build a throwaway demo token signed with a made-up secret (HS256).
header = {"alg": "HS256", "typ": "JWT"}
claims = {"iss": "https://idp.example.test", "sub": "user-123", "aud": "demo-api", "exp": 1893456000, "scope": "read"}
signing_input = b64u(json.dumps(header).encode()) + b"." + b64u(json.dumps(claims).encode())
sig = hmac.new(b"demo-secret-not-real", signing_input, hashlib.sha256).digest()
token = (signing_input + b"." + b64u(sig)).decode()
print(token)

h, p, s = token.split(".")
print("header :", json.loads(unb64u(h)))
print("claims :", json.loads(unb64u(p)))
print("sig    :", len(unb64u(s)), "bytes (decoding is NOT verifying)")

Now do the checks a relying party must do, as a thought exercise: which claim is the issuer, which says who the token is for, when does it expire (exp is seconds since 1970; date -r 1893456000 on macOS, date -d @1893456000 on Linux), and which of these the signature protects. Edit the claims in the script to "scope": "admin" and decode the new token without re-signing: the claims change, but a verifier that recomputes the HMAC would reject it. That is the difference between decoding and verifying; lab 2 builds a safe verifier.

2. Look at a certificate. The first command makes a TLS handshake with a public site (the same thing your browser does) and prints the certificate chain it sends. The second parses the leaf certificate. Both are read-only:

openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

subject=CN=example.com
issuer=C=US, O=..., CN=...
notBefore=...
notAfter=...
X509v3 Subject Alternative Name:
    DNS:example.com, DNS:www.example.com

Then print everything: openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -text. Find the validity dates, the Subject Alternative Name list (modern clients match the hostname against these, not the common name), the key type and size, the signature algorithm, and the Basic Constraints line that says CA:FALSE for a leaf. The -servername option sends SNI (the server name indication), without which a host with many certificates may return the wrong one. Check also that the chain builds to a root your system trusts:

openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | grep -E "Verify return code|Protocol|Cipher"
    Protocol  : TLSv1.3
    Cipher    : TLS_AES_256_GCM_SHA384
    Verify return code: 0 (ok)

3. Try your own server. Against your local app on port 8080 nothing speaks TLS, so the handshake fails; that is the intended lesson about TLS. If you have a development certificate for your own service, run the same commands against it and compare the fields with a production site's. To check which protocol versions your own server accepts, add -tls1_2 or -tls1_3 to s_client and see whether the handshake completes. A dedicated tester such as testssl.sh automates this; run it only against servers you operate.

What to look for

  • Tokens carry readable claims. Never put secrets or personal data in them (chapter 6).
  • The alg header is attacker-controlled input: a verifier must pin the algorithms it accepts rather than obey the token.
  • Certificate validity, names and the chain are what every client checks; an expired certificate on a forgotten device is how monitoring went blind in the Equifax story.

Common pitfalls

  • Pasting production tokens into websites to decode them. The decoder above runs locally.
  • Reading "it decodes" as "it is valid". Decoding proves nothing about authenticity.
  • Forgetting -servername and concluding the site has the wrong certificate.

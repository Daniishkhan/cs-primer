Lab 6: The Gameable Evaluator

Chapter 15 argued that a search is far better at finding the weak spots of a scorer than the person who wrote it, and that the better the search, the faster it gets there. In this lab you watch that happen. You are given a first-draft harness of the kind many people write: it scores code for being correct and fast. A hill climber, standing in for a model that proposes code, climbs its reward by routes nobody intended. Then you harden the harness one door at a time, with a function for each, and keep going until an independent audit agrees with the harness and the search ends on the honest answer.

Why this lab matters

Every loop in this course ends in a number: the score of a program, a prompt, an agent. Chapter 15 collected the cases in which that number was wrong in a way nobody noticed, from a sorting repair that returned an empty list to the kernel speedups of the AI CUDA Engineer (case study 2). The pattern in all of them is that the evaluator is software with an adversary, and nobody reviewed it as such. The surest way to learn what a harness is worth is to be the person who has to make it hold, so this lab gives you the leaky version, shows you the search walking through it, and asks you to build the defences one by one.

You will write six small pieces: a deterministic stopwatch, an output check, an isolated run, a clock the candidate cannot reach, a generator of hidden tests, and a tripwire. Each is a few lines. What is hard is knowing which one is missing, and the way to know is the method of chapter 15: for every defence, name the exploit it blocks, show that the exploit pays without it and does not pay with it, and show that an honest program is unharmed. The check does all three for you, and the final table is the red-team report you would want before trusting any search you pay for.

Deterministic, standard library only, and not a real sandbox

No network, no clock, no model. “Time” is a count of executed lines (a tick), so every number in this lab is reproducible. The mutation operator that proposes candidates is a deterministic stand-in for a language model: it changes the algorithm or adds a trick from a fixed menu, and the check says so wherever it matters. Candidates are Python source text run in-process by exec with a short list of builtins. That is enough to teach the structure of the problem and it is not a security boundary: a determined program can escape an in-process sandbox, which is why real harnesses run candidates in a separate process or container (Sandboxes & Permissions, Containers & Virtual Machines). Python 3.9 or newer; nothing to install. The whole check runs in about three seconds.

What you'll build

Six milestones:

  1. The stopwatch: count the lines a candidate executes, with sys.settrace, and nothing else. Then watch the first-draft harness get beaten.
  2. A check the output cannot fool: an equality test that does not let the candidate's own object answer for itself.
  3. A world that holds nothing of the grader's: run each call in a fresh namespace with no disk, no clock and no answer key.
  4. A clock the candidate cannot reach: time one test cold, on a meter only the grader holds, with the load counted.
  5. Fresh, awkward inputs: hidden tests with the cases people forget, drawn anew on every round.
  6. Results that are too good to be true: a tripwire from a lower bound on the work, then the whole hardened harness against the red team and the audit.

The task, the reward and the first draft

The thing being improved is a function solve(xs, k) that returns the sum of the k largest numbers in the list xs. The list may be empty, may hold repeats and negatives, and k may be 0 or the whole length. Nothing about the task is hard, which is the point: when a harness can be beaten on a task this small, a harness for a real kernel, a real agent or a real codebase has more room.

A candidate is Python source text. The reward is a speedup over a slow reference, and only if every test passes:

reward = (ticks the reference needs) / (ticks the candidate needs) if all tests pass, else 0

A tick is one executed line of the candidate’s code, plus the work of the builtins it calls (sorting n numbers is charged about n log n, summing n numbers n). It is a deterministic stand-in for run time, in the same way chapter 15 counted calls to exp() to stand in for the speed of a kernel. The reference is a plain selection loop, so it earns exactly 1.0. The honest one-liner built on sorted earns about 2.3, and that is the honest ceiling: any reward far above it needs an explanation.

The search is a hill climber. It starts from the reference and, each step, asks a stand-in for a language model for a variation, scores the current program and the variation on the same draw of tests, and keeps the variation if its reward is more than 2% higher. The variations come from a fixed menu: three algorithms and eight wrappers, 24 programs in all. The algorithms:

def _top(xs, k):
    xs = list(xs)
    total = 0
    for _ in range(k):
        j = 0
        for i in range(len(xs)):
            if xs[i] > xs[j]:
                j = i
        total += xs.pop(j)
    return total

def _top(xs, k):
    return sum(sorted(xs, reverse=True)[:k])

def _top(xs, k):
    return sum(sorted(xs)[-k:])

# (every candidate is one of these three _top functions plus one of the solve wrappers below)

The first is the slow reference. The second is the honest improvement. The third looks like a fine honest improvement too, and it passes every one of the eight visible tests, but sorted(xs)[-0:] is the whole list, because -0 is 0: it is wrong whenever k is 0 and the list is not empty. Hold on to it; it is not an exploit but an honest bug, and it will matter in milestone 5.

The wrappers are the interesting part. Each one defines solve around the chosen algorithm, and seven of them are exploits of the first-draft harness. They are written here so that you can read every one of them, and they are all deliberately small:

# lookup
_SEEN = {...the eight visible tests and their answers...}
def solve(xs, k):
    key = (tuple(xs), k)
    if key in _SEEN:
        return _SEEN[key]
    return _top(xs, k)

# peek
def solve(xs, k):
    try:
        return FS['expected'][(tuple(xs), k)]
    except NameError:
        return _top(xs, k)

# tamper
def solve(xs, k):
    try:
        FS['expected'][(tuple(xs), k)] = 0
    except NameError:
        return _top(xs, k)
    return 0

# alwayseq
class _Any:
    def __eq__(self, other):
        return True
def solve(xs, k):
    return _Any()

# memo
_memo = {}
def solve(xs, k):
    key = (tuple(xs), k)
    if key not in _memo:
        _memo[key] = _top(xs, k)
    return _memo[key]

# rewind
def solve(xs, k):
    try:
        t0 = CLOCK.ticks
    except NameError:
        return _top(xs, k)
    v = _top(xs, k)
    CLOCK.ticks = t0
    return v

# peek_padded
def solve(xs, k):
    pad = list(xs)
    try:
        return FS['expected'][(tuple(xs), k)]
    except NameError:
        return _top(xs, k)

Most of them behave honestly if the thing they exploit is missing (except NameError: return _top(xs, k)). That is realistic. A model hunting for a reward does not need a plan, only a variation that scores better; a variation that falls back to honest work when the loophole is closed costs it nothing to try.

The first-draft harness

This is leaky_session, the timing-and-output part of the harness as many people write it first:

def leaky_session(source: str, tests, fs: dict, clock: Meter) -> Tuple[list, List[int]]:
    """The first draft of a timing-and-output harness, as many people write it. ONE namespace for the whole
    session, which also holds the grader's disk (`FS`) and clock (`CLOCK`). The load is not timed. Each test is
    called REPEATS times and the fastest is kept 'to remove noise'. Returns (outputs, ticks per test)."""
    ns = load_world(source, clock, {"FS": fs, "CLOCK": clock})
    outs, ticks = [], []
    for xs, k in tests:
        best = None
        for _ in range(REPEATS):
            t0 = clock.ticks
            out = measure(ns["solve"], (tuple(xs), k), clock)
            elapsed = max(1, clock.ticks - t0)
            best = elapsed if best is None else min(best, elapsed)
        outs.append(out)
        ticks.append(best)
    return outs, ticks

Milestone 1: the stopwatch

Everything else rests on a measurement that is the same on every machine and that the candidate cannot argue with. Wall-clock time is neither: it varies from run to run, depends on the machine, and cannot be checked exactly in a test. Counting executed lines is deterministic, and Python lets you do it from the outside with sys.settrace. You install a trace function; the interpreter calls it with an event name each time something happens. Two events matter here:

  • "call": a new frame (a function, a class body, a module) has just been entered. The global trace function receives it and decides whether to trace that frame: it returns a local trace function to trace it and None to ignore it.
  • "line": the frame is about to execute a new line. The local trace function receives it. Add one tick and return the local trace function again, so that the next line is traced too.

The part that makes this a stopwatch for candidates and not for everything is the filter. Candidate code is compiled under the file name "<candidate>" (the constant CANDIDATE), so a frame belongs to the candidate exactly when frame.f_code.co_filename == CANDIDATE. The grader’s own lines, the builtins that run inside sorted, the check itself, must cost nothing. And the stopwatch must put things back: if something else was tracing (a debugger, a coverage tool), measure has to restore that tracer when it finishes, even when the candidate raises.

Your task

Write measure(fn, args, meter). It calls fn(*args), adds one tick to meter.ticks for every line the candidate executes during the call (including lines of helper functions the candidate defines and calls), restores the previous tracer, and returns fn’s value.

python3 check.py shows this milestone as ✔. Hand-counted functions (three statements cost exactly 3 ticks; a helper that is called twice adds its own lines twice; a loop costs the same extra ticks per iteration), meters that accumulate across calls, grader code that costs nothing (even when a candidate calls it), the previous tracer restored after a normal return and after an exception, and ticks spent before an exception still counted. Then the part you came for: the first-draft harness, built on your stopwatch, passes all seven tricks and gives each of them several times the reward of the honest program, and five searches against it all end on a trick.

Hints try without first

  • old = sys.gettrace(), then sys.settrace(global_trace), then try: return fn(*args) finally: sys.settrace(old).
  • If the grader’s own work is being counted, the filter is missing or wrong. If helper functions of the candidate are not counted, the global function must return local for every candidate frame, not just the first.
  • If the check complains that tracing is switched off after your function, you restored None where you should restore whatever sys.gettrace() returned before.
Solution spoiler 
def measure(fn: Callable, args: tuple, meter: Meter):
    """Call fn(*args) and add one tick to meter.ticks for every line the CANDIDATE executes while it runs.

    Use sys.settrace. The global trace function is called on each new frame ("call" event): return a local
    trace function for frames whose code file is CANDIDATE (frame.f_code.co_filename) and None for every other
    frame, so the grader's own code costs nothing. The local trace function adds a tick on each "line" event
    and returns itself. Return fn's value. Whatever happens, even if fn raises, put back the tracer that was
    installed before (sys.gettrace()) so that measuring never leaves tracing switched on.
    """
    def local(frame, event, arg):
        if event == "line":
            meter.ticks += 1
        return local

    def global_trace(frame, event, arg):
        return local if frame.f_code.co_filename == CANDIDATE else None

    old = sys.gettrace()
    sys.settrace(global_trace)
    try:
        return fn(*args)
    finally:
        sys.settrace(old)

Common misconception

“An exploit like this needs a malicious or very capable agent.” Nothing here has a goal, a plan or a model of the grader. The search proposes variations from a menu of 24 programs and keeps the ones whose reward is higher, with no idea what any of them does. Chapter 15 makes the same point with a 1990s hill climber that found an overflow in an aircraft-arrestor simulation. What a more capable proposer changes is not whether the loophole is found but how quickly, and how many kinds of loophole are on the menu.

Milestone 2: a check the output cannot fool

The first door is the shortest. The first-draft check is out == want, and Python evaluates that by asking the left-hand object whether it equals the right-hand one. The always-equal trick returns an instance of a class whose __eq__ answers True to everything, so the check passes eight tests that were never answered. The candidate chose the object whose code decides the comparison, which is to say it graded itself.

The repair is to compare only things the grader can trust, and to do the type test before any comparison that could run the candidate’s code. The right type is exactly int: not bool (True == 1), not an int subclass that overrides __eq__, not 5.0, not "5". The test is type(out) is int, and not isinstance(out, int), because isinstance accepts the subclass that lies. This is a tiny example of the first control in chapter 15, “check the thing, not a symptom”: a check that asks only whether something compares equal is a check of the candidate’s cooperation.

def strict_equal(out, want) -> bool:
    """True only if `out` is exactly a Python int (type(out) is int: not a bool, not a subclass, not a float,
    not an object that defines __eq__) and out == want."""
    return type(out) is int and out == want

Milestone 3: a world that holds nothing of the grader’s

The next door is not about the output. It is about what the candidate can see. In the first draft the candidate runs in a namespace that also holds FS, the dictionary standing in for a shared disk, and CLOCK. Two tricks use the disk. peek looks up the answer to its own input in the key and returns it. tamper goes further and writes its own answer over the key, because the checker reads the key back after the run and will be comparing the candidate’s answer with the candidate’s answer. This is the “reward that reads its own output file” family of chapter 15, with METR’s runs that read the reference answer from the call stack and patched the evaluator as its real-world form: the grader and the candidate share state, so the candidate can edit the thing that judges it.

The defence is the standard one in security (threat modelling): a small trusted core and a narrow channel. The candidate gets a fresh world for every call, built with load_world and no extras: no disk, no clock, no key, nothing that a previous call left behind. It is handed a tuple copy of its input, so it cannot change what the grader holds. What comes back across the boundary is one value, the return value. In this lab the boundary is a new namespace; in a real harness it is a process or a container with no access to the grader’s files (Sandboxes & Permissions).

Milestone 4: a clock the candidate cannot reach

The timer has three problems at once, and each is a real habit. It runs every test three times in one warm namespace and keeps the fastest (“to remove noise”), so a program that remembers its answers, memo, pays full price once and almost nothing twice. It starts the clock after the program has loaded, so any work done at import time is free. And the meter itself, CLOCK, is a name in the candidate’s world, so rewind can read it before the work and write the old value back after. The first two are the ordinary mistakes of benchmarking: warm-ups, caches and best-of-N change what is being measured, which is why benchmark tools such as hyperfine make them explicit choices. The third is chapter 15’s “overwrote the timer the grader uses.”

One principle fixes all three: the grader owns the meter, and every measurement starts cold. cold_ticks builds a new world for one test with a Meter that only the grader holds, loads the candidate under measurement (so setup work counts, because load_world already runs the load through your stopwatch), then calls solve once on the same meter and returns the total. No repeats, no warm cache, no reachable clock. Total cost for the candidate is its load plus its call, for every test, as a user starting a fresh process would see it.

Solution spoiler 
def cold_ticks(source: str, xs, k) -> int:
    """The ticks one test costs, measured by the grader: a fresh world for this call (load_world with a Meter
    that only the grader holds and NO extras), the load counted, then one call of solve(tuple(xs), k) measured
    on the same meter. Returns meter.ticks. Exceptions from the candidate propagate."""
    meter = Meter()
    ns = load_world(source, meter)
    measure(ns["solve"], (tuple(xs), k), meter)
    return meter.ticks

Milestone 5: fresh, awkward inputs

The lookup trick answers the eight visible tests from a table and solves everything else honestly. Against eight fixed tests it is the best program there is: three ticks a test instead of thirty. It is also, strictly, a legitimate answer to the question the harness asked, which is the lesson. The harness asked about eight inputs, so the search optimised for eight inputs. This is the answer-key family of chapter 15 (“recognising test inputs”), and the cure is the one Ofria found when he randomised the test: generate the tests inside the grader, from a seed the candidate never sees, and change them.

Fresh tests also fix a second problem that has nothing to do with cheating. Look again at the honest-looking third algorithm, sorted(xs)[-k:]. It passes every visible test, because every visible test has k of at least 1. Its bug only shows when k is 0, and nobody wrote that test. A hidden-test generator is a way of writing the tests you forgot, so it should not be uniform noise: it should put the awkward cases first. Yours produces, for any seed, the same list of tests:

  • Test 0: a list of 5 to 10 numbers with k = 0. This is the case that sinks sorted(xs)[-k:].
  • Test 1: a list of 5 to 10 numbers with k equal to the length: take everything.
  • Test 2: 8 to 12 numbers from −2 to 2, so full of repeats, with 1 ≤ k < length.
  • Test 3: the empty list with k = 0.
  • Tests 4 onwards: 1 to 16 numbers from −50 to 99 and a random k from 0 to the length. Redraw any test that coincides with a visible one.

Two details are about reproducibility. Use your own random.Random(seed), never the global generator, so that the same seed always gives the same tests and a test elsewhere in the program cannot change them. And note how the harness uses it: evaluate(source, round) draws the tests for that round, and the search compares the current program and its variation on the same round, then moves to a new round on the next step. Fresh tests on every step stop the search memorising them; a shared draw within a step stops the comparison being dominated by which list sizes happened to come up (the paired comparison of Statistics for Evals).

def hidden_tests(seed: int, n: int) -> List[Tuple[List[int], int]]:
    """n tests (xs, k) with 0 <= k <= len(xs), reproducible from `seed` and independent of the global random state
    (use rng = random.Random(seed)). The first tests are fixed in kind, the rest are random:

        0   a list of 5 to 10 numbers with k = 0                 (the case sorted(xs)[-k:] gets wrong)
        1   a list of 5 to 10 numbers with k = len(xs)           (take everything)
        2   a list of 8 to 12 numbers drawn from -2..2, so full of repeats, with 1 <= k < len(xs)
        3   the empty list with k = 0
        4+  len(xs) uniform in 1..16, numbers uniform in -50..99, k uniform in 0..len(xs)

    Random lists use numbers from -50 to 99 (negatives included) unless said otherwise. Test 0, 1 and 4+ should
    not be a visible test (reject and redraw if one comes up).
    """
    rng = random.Random(seed)
    seen = {(tuple(xs), k) for xs, k in VISIBLE}

    def draw(size, lo=-50, hi=99):
        return [rng.randint(lo, hi) for _ in range(size)]

    tests = []
    while len(tests) < n:
        i = len(tests)
        if i == 0:
            xs = draw(rng.randint(5, 10)); k = 0
        elif i == 1:
            xs = draw(rng.randint(5, 10)); k = len(xs)
        elif i == 2:
            xs = draw(rng.randint(8, 12), -2, 2); k = rng.randint(1, len(xs) - 1)
        elif i == 3:
            xs, k = [], 0
        else:
            xs = draw(rng.randint(1, 16)); k = rng.randint(0, len(xs))
        if (tuple(xs), k) in seen:
            continue
        tests.append((xs, k))
    return tests

Milestone 6: results that are too good to be true

The five defences above each close a door someone has already walked through. The last control in this lab is for doors nobody has seen yet. Chapter 15 lists it as “add anomaly tripwires”: some results are too good to be true, and a rule can say so without understanding the trick. METR’s method for RE-Bench was of this kind, review the anomalously high-scoring runs first.

A good tripwire comes from a bound that no honest candidate can beat. Here there is a clean one. To return the sum of the k largest numbers of a list, any program must look at every number at least once, because a number it never looked at could be the largest. In this meter looking costs at least one tick per number. So over a set of tests, any honest candidate needs at least the sum of len(xs) over the tests with k at least 1 (a test with k = 0 needs no reading: the answer is 0). A candidate that passes every test in fewer ticks than that has not computed the answer; it has found a shortcut. tripwire(total_ticks, tests) flags it, and the harness scores a flagged candidate zero.

The chart shows the tripwire working and shows its limit. On ten hidden tests the honest programs use 322 (sorted) and 800 (loop) ticks against a bound of 57. Five tricks finish at 10 to 30 ticks, far below the bound, and are flagged. The sixth, peek_padded, does the same peek but first copies the list, pad = list(xs), which costs exactly the length of the list in ticks; it lands at 95, above the bound, and the tripwire does not flag it. It still beats the honest program by a wide margin. A tripwire detects an exploit that is greedy; it does not remove the loophole, and a searching process that is penalised for being greedy tends to learn to be only as greedy as it can afford (Baker et al. report the same when a monitor is trained against, chapter 15). So the tripwire is the last milestone and the last layer: it catches what the other five missed or what someone adds to the menu tomorrow, and it flags the programs a human should read.

Solution spoiler 
def tripwire(total_ticks: int, tests) -> bool:
    """True if a passing candidate used suspiciously few ticks. To get the top k of a list a program must look at
    every number at least once, and looking costs at least one tick each, so over a set of tests any honest
    candidate needs at least the SUM of len(xs) over the tests with k >= 1. Flag total_ticks below that bound."""
    return total_ticks < sum(len(xs) for xs, k in tests if k >= 1)

Common misconception

“The harness and the audit now agree, so the evaluator is secure.” They agree on the winners this search can find from this menu. Skalse et al.’s result, quoted in chapter 15, is that a non-trivial proxy cannot be made unhackable, only more expensive to hack. This harness still has holes that you can walk through if you add the right line to the menu. The meter does not see C-level list methods, so xs = list(xs); xs.sort() would cost far fewer ticks than sorted without being a cheat. An in-process exec can be escaped. The audit uses a single fixed set of 40 inputs, so a loop allowed to query it would start to fit it. The practice that goes with a hardened harness is the rest of chapter 15’s list: red-team it before the search does, and read the winners.

Systems connection

Everything in this lab has a counterpart in ordinary engineering. Fresh hidden tests are the held-back set of leakage and of contamination audits. The best-of-three warm timer is the benchmarking mistake of Performance Engineering, and the cold, grader-owned meter is how a benchmark service should work. The isolated world is the trusted-core, narrow-channel design of threat modelling, and a production judge for untrusted code adds processes, resource limits and no network on top of it (Design an Online Code Judge). The tripwire is an alert on an implausible metric, the same instinct as an SLO alert on a latency that is suddenly too good. And reward hacking in trained models (Reward Models & Reward Hacking) is this lab with a gradient in place of a hill climber.

What you learned

  • A hill climber on a leaky reward finds the loophole without any plan. Five searches on the first-draft harness all ended on the always-equal object, with a harness score of 65.8 and an audit score of 0.0.
  • Every defence is justified the same way: name the trick it blocks, show the trick pays without it and does not with it, show an honest program is unharmed. Closing one door moves the winner to the next cheapest route.
  • Compare outputs on the grader’s side with a type test first (type(out) is int); give the candidate a fresh world with no grader objects; measure time cold on a meter the grader owns, with the load counted; draw tests fresh from a seed the candidate never sees and put the awkward cases first.
  • Isolating the answers is not enough if the timing still runs in a shared world: a two-faced candidate is honest where it is checked and cheating where it is timed.
  • Hidden tests catch honest mistakes as well as cheats: sorted(xs)[-k:] passed every visible test and failed the first hidden one.
  • A tripwire from a lower bound on the work flags results that are too good to be true, and a padded trick shows why it is a net and not a wall. The last layer is a human reading the winners.

Check your understanding

After milestone 3 (isolated runs) the harness reads its answers from fresh worlds, yet peek still earns 32.9 while timing is warm and shared. What explains this?

  1. The isolated world still contains the answer key
  2. The candidate is honest in the session that is checked and cheats in the session that is timed, so only isolating both stops it
  3. Isolated runs make every program slower, so the reward is inflated
  4. strict_equal is not yet implemented
The answers and the ticks come from two runs of the same source. Where the disk is visible (the shared timing session) peek answers in two ticks; where it is not (the isolated output session) it falls back to honest work and passes the check. The key is not in the isolated world, isolation does not slow programs down in this lab, and strict equality is irrelevant to a program whose output is a correct int.

Why is the check type(out) is int and out == want and not isinstance(out, int) and out == want?

  1. isinstance is slower
  2. type(out) is int also accepts floats
  3. The two are equivalent for every value a candidate could return
  4. isinstance accepts a subclass of int (and bool), and the subclass can define its own __eq__ that the comparison would then run
A subclass of int passes isinstance, and its __eq__ is the code that runs when the grader writes out == want, which hands the decision back to the candidate. The exact-type test rejects the subclass and True/False before any comparison runs. Floats are rejected by both tests; speed is not the issue.

A tricky candidate keeps a dictionary of answers between calls. Which harness feature makes it pay, and which change removes the gain?

  1. Hidden tests, removed by fixing the seed
  2. Strict equality, removed by comparing floats
  3. Timing each test three times in one warm world and keeping the fastest, removed by timing every test cold in a fresh world on the grader's meter
  4. The tripwire, removed by raising the bound
The warm best-of-three timer lets the second and third run hit the cache, so the reported cost is nearly zero. A cold run in a fresh world starts with an empty cache and the load counted, so the memoising program costs the same as its honest version. Hidden tests do not help a cache that is correct on every input, and the tripwire is a separate layer that would flag the result but not remove the loophole.

The program sum(sorted(xs)[-k:]) passes all eight visible tests. What does its fate under hidden tests show?

  1. Hidden tests also catch honest bugs: it fails the first hidden test, which has k = 0, because [-0:] is the whole list
  2. Hidden tests are unfair to programs that were correct
  3. The program was an exploit of the first-draft harness
  4. Hidden tests only work against programs that read the answer key
It was never trying to deceive anyone; the fixed tests never had k = 0. A generator that puts the awkward cases first (k = 0, k = length, repeats, empty) writes the tests people forget. That is a second, separate benefit of hidden tests beyond stopping memorisation.

The tripwire flags a passing candidate that used fewer ticks than the sum of len(xs) over tests with k of at least 1. Why are the k = 0 tests left out of the sum?

  1. Because k = 0 tests cost nothing to run
  2. A program can answer them (the sum of zero numbers is 0) without reading the list, so an honest candidate may spend no ticks on them
  3. Because they are visible tests
  4. Because the bound would otherwise be too loose
Over a test with k = 0 no number needs examining, so counting its length would flag honest programs that return early. For k of at least 1 every number may be the largest, so each must be looked at at least once. Counting too many tests would raise the bound above what honest programs can reach and produce false alarms.

With strict, isolated, cold, hidden and guard all on, a search ends on sorted and its harness score is within 35% of the audit. Which conclusion is justified?

  1. The evaluator is now unhackable
  2. The audit can replace the harness as the search's score
  3. No further review is needed because the tripwire never fires
  4. The harness resists every trick on this menu and this search, which does not show that no other trick exists, so red-teaming and reading the winners remain necessary
Agreement on the winners found from a fixed menu is evidence about that menu. Chapter 15 cites the result that a non-trivial proxy cannot be made unhackable, and the box above lists holes that remain (the meter's blind spot for C-level methods, the in-process boundary). Using the audit as the score would let the search fit it, and a tripwire that never fires in a clean run is what a last layer looks like when it is not needed, not a reason to stop looking.

Lab 1: Bandits & Monte Carlo Tree Search

Chapter 1 argued that every search loop is a budget being spent, and that the hard part is deciding which trial to run next. In this lab you write that decision. First for a row of slot machines, where you implement epsilon-greedy, UCB1 and Thompson sampling and watch regret separate them. Then for a game tree, where UCB1 becomes the selection rule of Monte Carlo tree search, and you build a searcher that solves Nim and plays tic-tac-toe without losing. A checker with hand-worked numbers, seeded experiments and real games tells you which of the four phases you got wrong.

Why this lab matters

The rest of this course is a stack of search loops: propose something, score it, decide what to try next. Best-of-n sampling and adaptive branching over answers (chapter 8), choosing which program in an archive to mutate (chapter 9), deciding which candidate agent design deserves another evaluation (chapter 12): each one hides a bandit. If you have only read about the exploration-exploitation trade-off, it stays a slogan. After writing the policies yourself you will have seen greedy lock onto a wrong arm in a large fraction of runs, seen the textbook exploration constant over-explore on a realistic problem, and know why Thompson sampling needs no constant at all.

The second half is where bookkeeping bugs live. A tree search that flips the sign of its results one level too few, or that picks the move with the highest win rate instead of the most visits, still runs, still returns a legal move, and plays plausibly. It loses. The milestones are built around exactly these quiet failures, and the tic-tac-toe games at the end are the test that the whole machine, not just its parts, works.

Deterministic, standard library only

Nothing here uses a network, a clock or a model. Every random number comes from a seeded random.Random, so the same code gives the same numbers on every run, and a failure prints enough to replay it: python3 check.py solution 5 3 runs milestone 5 on seed 3 only. The bandit runner uses one generator for rewards and a separate one for the policy, so a policy can never change what an arm would have paid (the standard trick for comparing policies fairly). Python 3.9 or newer, nothing to install. The whole check takes about seven seconds for the reference solution. Later labs in this course replace the scoring function or the mutation operator with a language model; where they do, a deterministic stand-in plays that part, and says so.

What you'll build

Six milestones, each adding a few functions and the experiments that test them:

  1. Regret, greedy and epsilon-greedy: measure what a policy costs, and meet the two simplest ways of choosing an arm.
  2. UCB1: add an optimism bonus that shrinks as an arm is tried, and see the exploration constant matter.
  3. Thompson sampling: draw from a belief about each arm instead of computing a bound, and compare all the policies on three problems.
  4. The four phases of MCTS: the UCT value, selection, expansion and backpropagation, each tested on a tree you can check by hand.
  5. The search loop: put the phases together, pick the most-visited move, and solve Nim.
  6. Playing tic-tac-toe: a better rollout, a player function, and games against random and perfect opponents.

Milestone 1: regret, greedy and epsilon-greedy

A multi-armed bandit is a row of slot machines. Each arm pays 1 with a fixed probability you cannot see, and 0 otherwise. You have a budget of pulls and want as much reward as possible. Nothing changes between pulls, so there is no tree: only the dilemma of whether to pull the arm that looks best so far or an arm you know little about. The code keeps two lists, counts[i] (pulls of arm i) and totals[i] (reward collected from it), and every policy is a function of those lists:

def policy(counts, totals, t, rng):    # returns the index of the arm to pull; t is the 1-based number of this pull

To compare policies we need one number. Regret is the reward you gave up compared with an all-knowing player who pulled the best arm every time. In a simulation we know the true win rates, so we can compute the expected loss exactly. With best mean μ*, true means μi and pull counts ni:

R = ∑i ni · (μ* − μi)

(Strictly this is pseudo-regret: it uses the arms' means, not the noisy rewards actually received, which removes luck from the comparison.) On the bandit with win rates 0.30, 0.45 and 0.50, pulling the 0.45 arm costs 0.05 per pull and the 0.30 arm costs 0.20, so 10, 20 and 70 pulls of the three arms have regret 10 × 0.20 + 20 × 0.05 + 0 = 3.0.

Two policies to write. Greedy tries every arm once, lowest index first, then always pulls the arm with the best average so far. Its weakness is lock-in: if the best arm happens to lose on its first pulls, its average is low, greedy never goes back, and regret grows in proportion to the number of pulls. Epsilon-greedy repairs this by exploring with probability ε: draw one random number, and if it is below ε pull a uniformly random arm, otherwise act greedily. It never gets locked in. But it keeps exploring for ever, so even after it has found the best arm a fraction of its pulls are wasted, and its regret still grows in a straight line, with a small slope. You will measure that slope.

The last function, mean_regret, wraps the given run_bandit in a loop over seeds. It is small, but every later bandit milestone uses it, and it is where you learn that one run proves nothing: a single run of any of these policies is dominated by luck.

Common misconception

"Greedy is fine if the arms are different enough." The danger is not that greedy cannot tell arms apart, but that it stops looking. After a few unlucky early pulls it never gathers the evidence that would correct the mistake. The check runs greedy over 100 seeds on a bandit with a 0.05 gap and makes you see how often that happens: it asserts that greedy's mean regret exceeds 100 in 2,000 pulls, and prints it.

Hints try without first
  • pseudo_regret is one line: sum(n * (best - p) for n, p in zip(counts, probs)).
  • greedy: scan for the first counts[i] == 0 and return it. Otherwise compute totals[i] / counts[i] for each arm and take the arg-max. max(range(k), key=...) returns the first maximiser, which gives you the lowest-index tie-break for free if the key is only the average.

Solution spoiler 
def pseudo_regret(probs, counts):
    """R = sum_i counts[i] * (mu_star - mu_i): what the pulls cost against always playing the best arm."""
    best = max(probs)
    return sum(n * (best - p) for n, p in zip(counts, probs))

def greedy(counts, totals, t, rng):
    """Try every arm once (lowest index first), then always pull the arm with the best average.
    Ties go to the lowest index."""
    for i, n in enumerate(counts):
        if n == 0:
            return i
    avg = [s / n for n, s in zip(counts, totals)]
    return max(range(len(avg)), key=lambda i: (avg[i], -i))

def epsilon_greedy(counts, totals, t, rng, eps=0.1):
    """With probability eps pull a uniformly random arm; otherwise act greedily (untried arms first)."""
    if rng.random() < eps:
        return rng.randrange(len(counts))
    return greedy(counts, totals, t, rng)

def mean_regret(select, probs, steps, seeds):
    """Average pseudo-regret of a policy over the given seeds."""
    total = 0.0
    for seed in seeds:
        counts, _ = run_bandit(select, probs, steps, seed)
        total += pseudo_regret(probs, counts)
    return total / len(seeds)

Milestone 2: UCB1, optimism under uncertainty

Epsilon-greedy explores blindly: it is as likely to re-test an arm it has pulled a thousand times as one it has pulled twice. UCB1 (Auer, Cesa-Bianchi and Fischer, 2002) explores where it is ignorant. It scores each arm with an upper confidence bound, a number that the arm's true mean is unlikely to exceed, and pulls the arm with the highest bound:

UCBi = x̄i + c √( ln t / ni )

Here x̄i is the arm's average reward, ni its pulls, t the number of the pull being chosen and c an exploration constant. The second term is the bonus. It is large when ni is small and shrinks as the arm is tried. The ln t on top grows very slowly, so an arm that is left alone for a long time creeps back up the ranking until it gets another look. The principle is called optimism in the face of uncertainty: act as if each arm is as good as it plausibly could be, and let the evidence correct you.

A worked example makes the trade-off concrete. Three arms have been pulled 4, 2 and 1 times with totals 2, 1 and 0, so their averages are 0.5, 0.5 and 0.0. It is pull t = 8, and ln 8 = 2.08. The least-tried arm C has the worst average but the biggest bonus. Which arm wins depends on c:

import math
from solution import *

counts, totals, t = [4, 2, 1], [2.0, 1.0, 0.0], 8
for c in (0.0, 0.5, 1.0, 2.0):
    scores = ucb_scores(counts, totals, t, c)
    pick = ucb1(counts, totals, t, None, c)
    print(f"c={c:<3}  scores " + "  ".join(f"{s:.3f}" for s in scores) + f"   -> pull arm {'ABC'[pick]}")
$ python3 exp_ucb.py
c=0.0  scores 0.500  0.500  0.000   -> pull arm A
c=0.5  scores 0.861  1.010  0.721   -> pull arm B
c=1.0  scores 1.221  1.520  1.442   -> pull arm B
c=2.0  scores 1.942  2.539  2.884   -> pull arm C

With c = 0 the bonus vanishes and UCB1 is greedy (it pulls A, the first of the tied leaders). At c = 0.5 and 1 the moderately-tried arm B wins, since its bonus is bigger than A's and its average is better than C's. At c = 2 the bonus dominates and the never-successful arm C is pulled. The Hoeffding inequality derivation in the chapter gives c = √2 ≈ 1.41 as the safe worst-case value; as the chapter showed, on a real problem it is often too cautious.

Two implementation details matter. An arm with zero pulls would divide by zero; give it an infinite bound so it is tried first (which also means math.log(t) is always defined when the formula is used, since at least K pulls have happened). And break ties towards the lowest index, so the check is repeatable.

Solution spoiler 
def ucb_scores(counts, totals, t, c):
    """UCB_i = mean_i + c * sqrt(ln t / n_i) for every arm. An untried arm has an infinite bound."""
    out = []
    for n, s in zip(counts, totals):
        if n == 0:
            out.append(math.inf)
        else:
            out.append(s / n + c * math.sqrt(math.log(t) / n))
    return out

def ucb1(counts, totals, t, rng, c=1.0):
    """Pull the arm with the highest upper confidence bound (ties to the lowest index)."""
    scores = ucb_scores(counts, totals, t, c)
    return max(range(len(scores)), key=lambda i: (scores[i], -i))

Milestone 3: Thompson sampling

UCB1 turns uncertainty into a bonus you add. Thompson sampling (Thompson, 1933) turns it into randomness. Keep a belief about each arm's win rate, draw one sample from each belief, and pull the arm whose sample is largest. For an arm with w wins and l losses, a natural belief is the Beta distribution with parameters (1 + w, 1 + l): it starts as a flat distribution over [0, 1] for an untried arm, gets a peak at the observed win rate, and narrows as evidence accumulates. Python draws from it with rng.betavariate(alpha, beta). Here is what these beliefs look like in numbers:

import random, statistics
from solution import *

rng = random.Random(0)
print("what a belief looks like: 20,000 draws from Beta(1 + wins, 1 + losses)")
for wins, losses in ((0, 0), (3, 1), (7, 3), (70, 30)):
    draws = [rng.betavariate(1 + wins, 1 + losses) for _ in range(20_000)]
    print(f"  {wins:>2} wins, {losses:>2} losses: mean {statistics.mean(draws):.3f}  spread (sd) {statistics.pstdev(draws):.3f}")
$ python3 exp_beta.py

The belief after 7 wins and 3 losses has the same mean as the belief after 3 wins and 1 loss (0.667) but is narrower, and 100 pulls pin the win rate down to within about 0.045. Arms we know little about have wide beliefs, so they occasionally produce a high draw and get pulled; arms we know well produce draws close to their mean. Exploration emerges from the spread, and fades as the spread does, with no constant to tune. That is much of why Thompson sampling is popular in production recommenders.

Solution spoiler 
def thompson(counts, totals, t, rng):
    """Draw one sample from Beta(1 + wins, 1 + losses) for each arm and pull the arm with the largest draw.
    Draw the arms in index order, one rng.betavariate call each."""
    best, best_draw = 0, -1.0
    for i, (n, s) in enumerate(zip(counts, totals)):
        draw = rng.betavariate(1.0 + s, 1.0 + (n - s))
        if draw > best_draw:
            best, best_draw = i, draw
    return best

Milestone 4: the four phases of MCTS

A bandit has one decision. A game has a sequence of them, each opening a new set of choices. Monte Carlo tree search (MCTS) treats every position in the game as its own small bandit, whose arms are the legal moves and whose reward is eventually winning. Kocsis and Szepesvári (2006) applied UCB1 to trees and called the result UCT. The tree is grown one iteration at a time, and each iteration has four phases:

  1. Selection. From the root, walk down the tree. At each node whose moves have all been tried, go to the child with the highest UCT value.
  2. Expansion. At a node that still has an untried move, add one child for it.
  3. Simulation (a rollout). From the new node, play random moves to the end of the game and note who won. (Given.)
  4. Backpropagation. Walk back up the path, adding one visit and the result to every node.

The UCT value of a child is the UCB1 formula with the win rate in place of the average and the parent's visit count in place of t: wins/visits + c √(ln parent_visits / visits).

The one subtle thing is perspective. In a two-player game a result that is good for me is bad for you. The code stores, in each node, wins for the player who moved into that node. A node's parent is the position where the other player chooses among its children, so the parent wants the child with the best wins / visits from the mover's point of view, which is exactly what the node holds. The price is that backpropagation must flip the result at every level:

Draws count as 0.5 for both sides, and 1 − 0.5 = 0.5, so the same flip works. The given rollout function already returns its result in this convention (the reward for the player who moved into the state it was given), and game.terminal_value(state) is defined the same way, so you never need to ask whose turn it is. A Node holds its state, parent, move, children, the list of moves not yet expanded (untried), visits and wins.

Hints try without first
  • uct_value is the formula in one line. Use math.log (natural log) and take the square root of the whole ratio.
  • select_child never sees an unvisited child: every child was created by expand and then visited once in the same iteration. So visits >= 1 and there is no division by zero.
  • expand: node.untried.pop(rng.randrange(len(node.untried))) removes the move. Then Node(game, game.next(node.state, move), parent=node, move=move) and append it to node.children. Forgetting to remove the move is the classic bug: the same position is expanded again and again.
  • backpropagate is a loop: add to visits and wins, set result = 1.0 - result, step to node.parent, stop at None. If your check says the wins are all 1.0, you forgot the flip.
Solution spoiler 
def uct_value(wins, visits, parent_visits, c):
    """wins/visits + c * sqrt(ln(parent_visits) / visits)."""
    return wins / visits + c * math.sqrt(math.log(parent_visits) / visits)

def select_child(node, c):
    """The child with the highest UCT value (ties to the first in the list). All children must have visits >= 1."""
    best, best_value = None, -math.inf
    for child in node.children:
        v = uct_value(child.wins, child.visits, node.visits, c)
        if v > best_value:
            best, best_value = child, v
    return best

def expand(node, game, rng):
    """Remove one random untried move from the node, add the child for it, and return the child."""
    move = node.untried.pop(rng.randrange(len(node.untried)))
    child = Node(game, game.next(node.state, move), parent=node, move=move)
    node.children.append(child)
    return child

def backpropagate(node, result):
    """`result` is the reward for the player who moved into `node`. Add a visit and the reward to the node and
    every ancestor, flipping the result (1 - result) at every level."""
    while node is not None:
        node.visits += 1
        node.wins += result
        result = 1.0 - result
        node = node.parent

Milestone 5: the search loop, tested on Nim

Now assemble the iteration. mcts(game, state, iters, rng, c, rollout_fn) creates a root node and repeats the four phases iters times. Selection descends while a node has no untried moves and does have children (a node with nothing untried and no children is a finished game: stay there). Expansion happens only if the node has an untried move. The rollout function is a parameter, so milestone 6 can swap it. The root is returned, and the tree it holds is the result: the visit counts at the root's children are the search's opinion of the moves.

What to play with that opinion is the other function, best_move(root). The tempting choice is the child with the highest win rate. The right one is the child with the most visits. A child with a 100% win rate from one lucky visit has been barely examined, while a child with 1,940 visits and a 95% win rate has survived thousands of attempts to refute it; and because selection steers visits towards the moves that keep looking best, the visit count is a robust summary of the whole search. Here is the tree your code should build from a pile of 10 stones after 2,000 iterations (real output of exp_tree.py below):

Solution spoiler 
def mcts(game, state, iters, rng, c=1.0, rollout_fn=rollout):
    """Run `iters` iterations of selection, expansion, simulation and backpropagation from `state`.
    Returns the root node."""
    root = Node(game, state)
    for _ in range(iters):
        node = root
        # 1. selection: descend while the node is fully expanded and has children
        while not node.untried and node.children:
            node = select_child(node, c)
        # 2. expansion: add one new child (a terminal node has nothing to expand)
        if node.untried:
            node = expand(node, game, rng)
        # 3. simulation: score the new position by playing it out
        result = rollout_fn(game, node.state, rng)
        # 4. backpropagation
        backpropagate(node, result)
    return root

def best_move(root):
    """The move of the most-visited child (not the highest win rate). Ties go to the first child."""
    best = max(root.children, key=lambda ch: ch.visits)
    return best.move

Milestone 6: playing tic-tac-toe

Tic-tac-toe has a known value (a draw with perfect play), a state space small enough for an exact solver, and enough tactics to expose a weak searcher. The starter gives you the game, a random_player, a minimax_player that plays perfectly (it memoises the exact value of every position), and play_game(game, first, second, rng). A player is a function player(state, rng) -> move. You write the player that wraps your search, and a smarter rollout.

The position on the left is the kind of thing a search with few iterations gets wrong. X threatens to complete the top row at cell 2, and O has only one move that avoids losing: take cell 2. Under random rollouts, a bad move such as cell 6 still wins a fair share of the random games that follow, because X, playing randomly, usually fails to see its own winning move. The search needs many iterations before the refutation dominates. A rollout with two cheap rules is much sharper:

  1. If some legal move wins the game on the spot, play it.
  2. Otherwise avoid any move after which the opponent can win on the spot, if a safe move exists. (Choose uniformly among the safe moves; if none is safe, among all.)

Everything else stays random. The rules use only the game interface (legal, next, is_terminal, terminal_value), so they work for any two-player game of this shape. It is the pre-neural-network fix mentioned in chapter 1: put a little domain knowledge in the rollout policy. Remember that smart_rollout must return its result in the same convention as rollout, the reward for the player who moved into the state it was given.

Solution spoiler 
def smart_rollout(game, state, rng):
    """A rollout that is random except for two cheap rules, applied at every ply:
    1. if some legal move wins the game on the spot, play it;
    2. otherwise avoid any move that lets the opponent win on the spot, if such a safe move exists.
    Returns the reward for the player who moved INTO `state`, exactly like `rollout`."""
    flipped = False
    while not game.is_terminal(state):
        moves = game.legal(state)
        choice = None
        safe = []
        for m in moves:
            nxt = game.next(state, m)
            if game.is_terminal(nxt) and game.terminal_value(nxt) == 1.0:
                choice = m
                break
            if not any(game.is_terminal(game.next(nxt, r)) and game.terminal_value(game.next(nxt, r)) == 1.0
                       for r in game.legal(nxt)):
                safe.append(m)
        if choice is None:
            choice = rng.choice(safe or moves)
        state = game.next(state, choice)
        flipped = not flipped
    value = game.terminal_value(state)
    return 1.0 - value if flipped else value

def mcts_player(game, iters, c=1.0, rollout_fn=rollout):
    """A player function `player(state, rng) -> move` that runs MCTS for `iters` iterations and plays the most-visited move."""
    def player(state, rng):
        return best_move(mcts(game, state, iters, rng, c, rollout_fn))
    return player

Going further

  1. Reuse the tree. After the search plays a move, the child it chose is already a tree with thousands of visits.   3. PUCT. Replace the UCT value by the chapter's PUCT rule, which multiplies the exploration bonus by a prior P(s, a). With a prior that favours moves leaving a multiple of 4, how much sooner does the search commit to the right move?
  4. Non-stationary bandits. Let the arms' win rates swap halfway through a run. Which of your three policies recovers, and how fast? Try a sliding window of the last 200 pulls for the averages, or a discount on old counts.
  5. Gaussian rewards. Change run_bandit to return rewards drawn from a normal distribution. UCB1 as written assumes rewards in [0, 1]; what must change? What is the equivalent of the Beta belief for Thompson sampling?

Systems connection

A bandit is how a platform runs an experiment that learns while it runs. A fixed A/B test (from model to value) sends equal traffic to every variant until a sample-size target is met; a bandit moves traffic towards the winner during the test, which cuts the cost of showing a bad variant but makes the final statistical comparison harder to read. The progressive rollouts of deployment strategies are the safety-first cousin: expose a new version to a little traffic, watch, then widen. The other systems idea is the budget. MCTS is an anytime algorithm: you can stop after any iteration and have an answer, so its quality is a function of the latency you can afford. Setting the iteration count is a latency-versus-quality decision of the same kind as the timeouts and hedged requests in failure handling.

What you learned

  • Regret measures the cost of not knowing. Greedy and epsilon-greedy have regret that grows in a straight line, for different reasons (lock-in, and a permanent exploration tax); UCB1 and Thompson sampling have regret that bends over.
  • The UCB1 bonus c √(ln t / n) is optimism where evidence is thin. The theoretical constant (1.41) is a worst-case guarantee and over-explored on every problem here; tune c on a simulation of your own problem.
  • Thompson sampling explores through the spread of its beliefs and has no constant to set; it did about as well as the best-tuned UCB1.
  • MCTS treats every position as a bandit. Its four phases are selection by UCT, expansion, a rollout and backpropagation, and results alternate sign up the path because each node stores wins for the player who moved into it.
  • Play the most-visited move, not the one with the highest win rate. Visits are robust; a lucky 100% from one playout is not evidence.
  • Random rollouts stall on deep games (25 to 30% on large Nim piles even with 1,000 iterations). Better rollouts, or better evaluations, fix that; more iterations alone barely do.

Check your understanding

Three arms have been pulled 4, 2 and 1 times, with totals 2, 1 and 0, at pull t = 8 (ln 8 = 2.08). With UCB1 at c = 1, which arm is pulled?

  1. Arm A, the first of the two arms with the best average (0.5)
  2. Arm B, whose bound is about 1.52
  3. Arm C, the least-tried arm, whose bound is about 1.44
  4. Whichever arm has not been pulled for longest
The bounds are 0.5 + √(2.08/4) = 1.22 for A, 0.5 + √(2.08/2) = 1.52 for B and 0 + √(2.08/1) = 1.44 for C, so B wins. The tempting answer is C, because the bonus is biggest for the least-tried arm; but C has an average of 0 and the bonus does not outweigh that until c reaches about 1.2. At c = 0 the answer would be A, since UCB1 degenerates to greedy.

Epsilon-greedy with ε = 0.1 has found the best arm after 200 pulls. Why does its regret still grow in a straight line?

  1. Its estimates of the arm means stop improving after 200 pulls
  2. It re-tests the best arm too often, wasting pulls on it
  3. Its greedy step is chosen from the wrong arm after every exploring pull
  4. It keeps spending 10% of its pulls on uniformly random arms, so a fixed fraction of every later pull is wasted
Exploration is permanent and blind: one pull in ten goes to a random arm whatever has been learned, and two thirds of those land on worse arms, so the regret per pull never reaches zero. UCB1 and Thompson sampling make exploration fade as evidence accumulates. The estimates (first option) keep improving; and the best arm is not over-tested (second option), only the others are.

A leaf C is reached through the path root, A, B, C. The rollout from C is a win for the player who moved into C (result 1). What does backpropagation add to the wins of B, A and the root, in that order?

  1. 0, 1, 0
  2. 1, 1, 1
  3. 1, 0, 1
  4. 0.5, 0.5, 0.5
The player who moved into B is C's opponent, so the same game is a loss for them: B gets 0, A (same player as C) gets 1, and the root gets 0. Adding 1 everywhere (second option) credits both players with the same win and makes the search blind to who is winning; the third option has the signs the wrong way round. A draw would add 0.5 everywhere, which is the last option.

After a search, move X has 100 visits and a win rate of 0.52; move Y has 3 visits and a win rate of 1.00. Which should be played, and why?

  1. Y, because a higher win rate means a better move
  2. Y, because MCTS always plays the move with the largest value
  3. X, because its estimate has survived 100 playouts while Y's rests on 3
  4. Either, they are statistically indistinguishable
Visit counts reflect how much selection kept returning to a move because it kept looking best, which makes them robust; a win rate from three playouts is mostly luck, and a good search would have visited Y more if it really were better. The last option is too generous: 100 visits at 0.52 against 3 at 1.00 is not a tie, since the search had every chance to explore Y and moved on.

On Nim piles of 25 to 40, MCTS with random rollouts picks the winning move about a quarter of the time, and 1,000 iterations are no better than 200. What is the most likely cause and the best remedy?

  1. The exploration constant is too small; raise c to 3
  2. Random playouts of a 30-move game are almost coin flips, so the signal is drowned; use a better rollout or a value estimate
  3. The tree is too shallow; give the search ten times more iterations
  4. UCT cannot handle games with more than 20 positions
The rollout is the weak link: a random player errs nearly every turn, so the result of a long random game carries almost no information about the first move. More iterations (the third option) average more noise and help little, as the table in milestone 5 shows. Changing c redistributes visits but cannot add information; and UCT has no size limit.

Thompson sampling needs no exploration constant. What makes it explore?

  1. It adds a bonus proportional to 1/√n like UCB1 but hides it in the Beta distribution
  2. It flips a biased coin to explore, with a bias that shrinks over time
  3. Its beliefs about little-tried arms are wide, so such arms sometimes produce the largest draw
  4. It always pulls the arm with the highest posterior mean, with random tie-breaking
Each pull samples one value from every arm's belief and follows the largest. An arm with few pulls has a wide belief, so its draw is sometimes higher than the leader's; as pulls accumulate the belief narrows and the exploration fades by itself. Pulling the highest mean (last option) would be greedy, and there is no explicit coin or bonus in the algorithm.

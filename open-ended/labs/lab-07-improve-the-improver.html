Lab 7: Improve the Improver

A search program hunts for better answers to a problem. Its own settings decide how well it hunts. In this lab you write a second program that tunes those settings. Then you aim that second program at itself and ask two questions. Does it get better at tuning? And what stops it from cheating?

Why this lab matters

A system that improves itself needs a score to climb. The score is only as honest as the rule that computes it. Once the system can touch the rule, the easiest climb is to change the rule instead of the system.

In this lab the system is small enough to read in one sitting. You will see a real but modest gain, about one bin saved out of thirty-six. You will see that the gain survives on tasks the system never saw. You will also see a second case where the gain does not survive, and a cheat that raises the score without improving anything. The same shape appears in every serious self-improvement design, so it pays to meet it at toy scale first.

No model, no clock, no network

Nothing here calls a language model. The evolver edits programs with a seeded function that changes one piece of a syntax tree, as in lab 3. Every random number comes from a seeded random.Random. A candidate is limited by a step budget (fuel), not by seconds. The same code gives the same numbers on every machine. You need Python 3.9 or newer and the standard library only. The reference solution passes in about seven seconds. Because the effects are small, the page reports each number with the gap between training and held-out tasks, and says when a result is within noise.

Analogy: the baker, the coach and the head coach

A baker tries oven settings and keeps the loaf that tastes best. That is the first loop. A coach watches many bakers and changes how each baker tries settings: fewer loaves at once, bigger changes. The coach keeps whatever coaching makes bakers improve faster. That is the second loop. A head coach could now coach the coach. Each step up needs a taste test, and the taste test must use loaves the bakers never practised on.

Where it breaks down: a coach is a different person from the baker. In this lab the improver is a few numbers, and the same code that improves the baker can be pointed at the improver itself.

What you'll build

The problem is the online bin packing of the last labs. Items of size 20 to 60 arrive one at a time. Each goes into a bin of capacity 100, and a new bin opens when none fits. One function decides where an item goes: priority(item, rem), where rem is the space left in a bin. The item goes into the feasible bin with the highest priority. Fewer bins is better. The search starts from worst fit, rem - item, which prefers the emptiest bin. It is a poor start with room to improve.

Four terms carry the lab. A config is the evolver's settings: how often it uses each kind of edit, how many islands it has, how big its tournaments are, how often islands swap. The budget is a fixed count of heuristic evaluations the evolver may spend per task. The utility of a heuristic is minus its mean bin count, so higher is better. The meta-utility of a config is the mean utility of what the evolver finds with it, over several tasks. Six milestones:

  1. Utility: score one heuristic with a fuel limit, and turn every failure into a penalty.
  2. Meta-utility: run the evolver with a config on several tasks, inside a fixed budget, and average what it finds.
  3. The seed improver: perturb the config, keep the change if the meta-utility rises.
  4. Self-application: treat the improver's own settings as a config and improve them with the same idea.
  5. Held-out meta-evaluation: re-score on tasks the improver never saw, and on a shifted item-size range. Measure the gap.
  6. The audit: detect an improver that raises its own budget or peeks at held-out tasks, and reject it.

The setup you are given

Read this section once before the first milestone. It describes the parts you do not write.

The evolver keeps a few islands, each holding up to six programs. At each step it picks one island, draws a few programs at random, and takes the best of them. That draw is a tournament. It then edits the winner. There are four kinds of edit: nudge a constant, swap an operator, insert an if-rule, or wrap an expression in something like -e. The child is scored on the task's search instances. Every few steps the best program of each island moves to the next island, which is called migration. The evolver stops when its Budget says no more evaluations.

The Config holds seven numbers. The first four are weights for the four kinds of edit. The other three are the number of islands, the tournament size and the migration interval.

FieldChoicesWhat it does
w_constant, w_operator, w_rule, w_shape0 to 8Relative odds of each kind of edit.
n_islands1 to 4Separate sub-populations.
tournament1 to 4How many programs compete to be the parent.
migrate_every0, 4, 8, 16Steps between swaps. 0 means never.

The starting config DEFAULT is naive. It only nudges constants, and the worst-fit seed has no constant to nudge. So with DEFAULT the evolver cannot improve at all. The second config TUNED was set by hand and is already reasonable. You will use both: the naive one has a lot of room to improve, and the tuned one has almost none.

A task is a seed t. It fixes three search instances that the evolver sees, and six scoring instances that it never sees. Each instance has 80 items. The meta-utility scores the found heuristic on the scoring instances, so a config does not get credit for memorising its own search instances.

The training tasks are (1, 2, 3). The held-out tasks are (11, ..., 16). The improver may only ever look at the training tasks. It reaches the score through make_scorer(), which returns a function score(config) with the tasks, the budget and the item range already fixed.

Milestone 1: utility

Every level above this one needs one number per heuristic. That number must exist for every candidate, including broken ones. A search that crashes on its first bad program is not a search. So utility must never raise.

The sandbox from lab 3 is given. compile_restricted turns text into a function that can only call abs, min and max. It also counts fuel: one tick per function call and per loop pass. pack(items, priority) runs online bin packing. You combine them.

Take the instance [60, 60, 40, 40] and first fit (return 0). The first 60 opens bin 1, which has 40 left. The second 60 does not fit there, so it opens bin 2. The first 40 goes into bin 1, the second 40 into bin 2. That is two bins, so the utility is -2.0. Averages over instances work the same way: two instances needing 2 and 4 bins give -3.0.

Anything that goes wrong gets PENALTY, which is -1000.0. That is far below any real score, so a failing program can never win a comparison. Failures come in four kinds. The program may be rejected. It may run out of fuel, as an endless loop does. It may raise an exception, such as division by zero. Or it may return something other than a finite number, such as a boolean, nan or infinity. A boolean deserves care. In Python True == 1, so a program returning item > 3 would run without error and mean nothing.

Your task

Write utility(src, instances, fuel_budget=FUEL). Compile src with a fresh Fuel. Wrap the function in a checker that rejects any return value that is not a finite int or float. Pack every instance. Return minus the mean bin count, or PENALTY on any failure.

check.py verifies: hand-worked values (-2.0, -3.0) and best fit. Seven kinds of failure must all give exactly PENALTY. They are a syntax error, an import, an endless loop, division by zero, a boolean, an infinity from repeated squaring and a wrong signature. The same short loop must be fine with 10,000 fuel and a penalty with 20.

Hints try without first
  • A fresh Fuel(fuel_budget) per call. Fuel is shared across all the instances of one call, so a slow program runs out over the whole set.
  • Check the type with type(v) not in (int, float). Do not use isinstance, because bool is a subclass of int.
  • Put math.isfinite(v) in the same check, so nan and infinity are caught.
  • Catch Exception around both the compile step and the packing. One broad clause is fine here, because every failure maps to the same penalty.
Solution spoiler 
def utility(src, instances, fuel_budget=FUEL):
    """Minus the mean bins, or PENALTY on any failure."""
    fuel = Fuel(fuel_budget)
    try:
        fn = compile_restricted(src, fuel)
    except Exception:
        return PENALTY

    def checked(item, rem):
        v = fn(float(item), float(rem))
        if type(v) not in (int, float) or not math.isfinite(v):
            raise ValueError("bad priority value")
        return v

    try:
        counts = [pack(items, checked) for items in instances]
    except Exception:                 # OutOfFuel, ValueError, ZeroDivisionError, ...
        return PENALTY
    return -sum(counts) / len(counts)

Milestone 2: meta-utility

Now the step up. Given a config, how good is it? You cannot ask the config. You have to run the evolver with it and look at what comes out. That is meta_utility.

Three rules make the number fair. First, the budget is fixed. Every config gets the same number of heuristic evaluations, so a config cannot win by simply running longer. Second, each task gets its own fresh Budget. A shared counter would let the first task use it all and starve the rest. Third, the found heuristic is scored on instances the evolver never saw. Otherwise the config that overfits its search instances looks best.

For task seed t, the search instances use seeds 1000*t + j, and the scoring instances use seeds 1000*t + 500 + j. The evolver's own random stream is random.Random(t). So the same config on the same tasks always gives the same number. The result is the mean over tasks.

A budget of 1 is a useful anchor. The evolver can then score only the seed program, so the meta-utility is the seed's utility, whatever the config. The next table shows what a bigger budget buys. It is the script below run on the training tasks:

The tuned config gains about 0.8 to 0.9 bins from a budget of 5 on, and then does not improve with a larger budget. That is a small version of the problem milestone 5 measures.

Your task

Write meta_utility(config, task_seeds, budget, lo=20, hi=60). For each task seed, build the search and scoring instances, make a fresh Budget(budget), call evolve(config, search, counter, random.Random(t)), and score the result on the scoring instances with utility. Return the mean.

check.py verifies: the answer is deterministic. It equals the mean of the single-task answers. With budget 1 it equals the seed's utility on the scoring instances. Three tasks create three Budget counters that each run to 21 (budget 20 plus the refused request). The scoring instances are used once per task. And lo and hi reach the instances.

Hints try without first
  • make_instances(seeds, ITEMS, lo, hi) builds a list of instances. Pass lo and hi through, because milestone 5 changes them.
  • Create Budget(budget) inside the loop over tasks, not before it.
  • You do not need to catch BudgetExceeded. The given evolve catches it and returns the best program found so far.
Solution spoiler 
def meta_utility(config, task_seeds, budget, lo=20, hi=60):
    """Mean utility of what the evolver finds."""
    total = 0.0
    for t in task_seeds:
        search = make_instances([1000 * t + j for j in range(N_SEARCH)], ITEMS, lo, hi)
        scoring = make_instances([1000 * t + 500 + j for j in range(N_EVAL)], ITEMS, lo, hi)
        counter = Budget(budget)
        found = evolve(config, search, counter, random.Random(t))
        total += utility(found, scoring)
    return total / len(task_seeds)

Milestone 3: the seed improver

With a meta-utility you can search over configs. The simplest search is hill climbing: change something, keep the change if the score rises, and otherwise drop it. The improver does this on a Config.

The improver has its own settings. They live in a small class called Settings. The field proposals says how many candidate configs it tries per round. The field n_change says how many config fields each candidate changes. The field step says how far along a field's list of choices a change moves. The given perturb(obj, choices, rng, n_change, step) makes one candidate. The seed settings are Settings(2, 1, 1): two proposals per round, one field changed, one step.

The order of work matters for reproducibility. Each round, draw all proposals candidates from the best config so far, and only then score them in order. A candidate replaces the best only if its score is strictly higher. A tie changes nothing. The total number of score calls is 1 + rounds * proposals: one for the start, then the proposals.

Here is a toy example you can check by hand. Take a made-up score, -|w_shape - 6|, and start at w_shape = 0. With step = 1 and one field changed, a candidate that picks w_shape is either 1 or 0. The value 1 scores -5, which beats -6. The other move is clamped at 0 and ties. So only upward moves are kept, and each round can gain at most one unit per accepted candidate.

Your task

Write improve(config, score, rng, rounds, settings=SEED_SETTINGS). It returns (best_config, best_score). Draw the candidates with perturb(best, CHOICES, rng, settings.n_change, settings.step).

check.py verifies: the exact sequence of configs scored matches a reference. The number of score calls is 1 + rounds * proposals. A constant score returns the start unchanged. And on the real scorer the naive config improves. The check prints the gain.

Hints try without first
  • Call score(config) once before the loop and keep the result. Do not call it again for the best config at the start of every round.
  • Build the round's candidates with a list comprehension first. Then loop over that list to score them.
  • Compare with >, not >=. If a candidate ties, the earlier config stays.
  • The returned score must be the score of the returned config. Update both together.
Solution spoiler 
def improve(config, score, rng, rounds, settings=SEED_SETTINGS):
    """Hill-climb over configs."""
    best = config
    best_score = score(config)
    for _ in range(rounds):
        candidates = [perturb(best, CHOICES, rng, settings.n_change, settings.step)
                      for _ in range(settings.proposals)]
        for cand in candidates:
            s = score(cand)
            if s > best_score:
                best, best_score = cand, s
    return best, best_score

Milestone 4: self-application

This is the step the lab is named for. The improver has settings. Settings are numbers. So you can improve the improver with the improver's own method.

To do that you need a score for an improver. Define it as the mean gain the improver makes from a fixed start config, over a few random streams. Run improve once per stream, and average best_score - score(start). This is a meta-meta-utility, and it is a number like any other.

One rule keeps the comparison fair. Every improver gets about the same number of score calls, CALLS = 4 rounds-times-proposals. An improver with 4 proposals runs 1 round, and one with 1 proposal runs 4. Without this rule, "more proposals" would always win, and you would learn only that compute helps.

Then self_improve hill-climbs over Settings exactly as improve hill-climbs over Config. It makes one candidate per round, with perturb(best, SETTING_CHOICES, rng, 1, 1), scores it with improver_utility, and keeps it only if strictly better.

What should you expect? The naive start config needs one specific fix: a positive weight on the w_shape edit. A seed improver changes one field per candidate, so it reaches that fix slowly. An improver that changes two or three fields at once reaches it faster. So the likely win for self-improvement is a larger n_change. That is a small, dull, true result.

Your task

Write improver_utility(settings, score, start=DEFAULT, seeds=IMPROVE_SEEDS, calls=CALLS) and self_improve(score, rng, rounds, settings=SEED_SETTINGS, start=DEFAULT). Use rounds = calls // settings.proposals inside improver_utility.

check.py verifies: the mean gain matches a reference on a toy score. The number of score calls is the expected count; self_improve calls improver_utility exactly 1 + rounds times and keeps only strict improvements. And on the real training tasks the improved improver beats the seed improver. It also tests on twelve fresh random streams, which the self-improvement never saw.

Hints try without first
  • Compute score(start) once, before the loop over seeds.
  • Use random.Random(s) for each seed s, so every improver faces the same streams.
  • An improver with 6 proposals and calls=4 gets 0 rounds, and a gain of exactly 0. That is correct. Do not special-case it.
  • In self_improve, compute the start's improver_utility once, then compare each candidate with the best so far.
Solution spoiler 
def improver_utility(settings, score, start=DEFAULT, seeds=IMPROVE_SEEDS, calls=CALLS):
    """Mean gain an improver makes from `start`."""
    rounds = calls // settings.proposals
    base = score(start)
    gains = []
    for s in seeds:
        _, best_score = improve(start, score, random.Random(s), rounds, settings)
        gains.append(best_score - base)
    return sum(gains) / len(gains)

def self_improve(score, rng, rounds, settings=SEED_SETTINGS, start=DEFAULT):
    """The same hill-climb, one level up."""
    best = settings
    best_u = improver_utility(settings, score, start)
    for _ in range(rounds):
        cand = perturb(best, SETTING_CHOICES, rng, 1, 1)
        u = improver_utility(cand, score, start)
        if u > best_u:
            best, best_u = cand, u
    return best, best_u

Milestone 5: held-out meta-evaluation

Milestone 4 reported a win on the same tasks the improver used. That number is biased. The improver kept whichever settings looked best on three tasks and three random streams, so some of the gap is luck. This is the same selection effect that chapter 16 describes for programs. Here it happens one level up, and it has a name: meta-overfitting. The improver fits the training tasks instead of the problem.

To measure it, run the improver using only the training scorer. Then re-score the config it ends with on two other scorers. The held-out scorer uses six new tasks. The shifted scorer uses those same six tasks, but with item sizes 10 to 70 instead of 20 to 60. That tests a change in the kind of problem as well as a change in the instances. Report four numbers, each a mean over random streams: the training gain, the held-out gain, the shifted gain, and gap = train - held. A positive gap means the improver overfitted.

Two starting points tell different stories, and you should run both.

  • From the naive config the fix is structural: turn on a missing kind of edit. It works wherever the edit helps, so the gain should transfer.
  • From the tuned config nothing structural is missing. Any gain the improver finds comes from small differences that three training tasks happen to reward. Those should not transfer.

Your task

Write generalisation(settings, train_score, held_score, shifted_score, start, seeds, calls). For each seed, run improve with the training scorer only. Compute each gain as the final config's score minus the start's score, under that scorer. Return a dict with the means under the keys train, held, shifted and gap.

check.py verifies: the four numbers against a reference on toy scorers (one where the held-out gain is negative). Then on the real scorers, from the naive config, that the training, held-out and shifted gains are all positive. And from the tuned config, that the gap is above 0.05 and the shifted gain is negative.

Hints try without first
  • Only train_score is ever passed to improve. The other two scorers are called on the final config only.
  • Each scorer is a function of a config. Subtract the start's score under the same scorer, not the training one.
  • Use rounds = calls // settings.proposals as in milestone 4.
Solution spoiler 
def generalisation(settings, train_score, held_score, shifted_score,
                   start=DEFAULT, seeds=FRESH_SEEDS, calls=CALLS):
    """Train, held-out and shifted gains, and the gap."""
    rounds = calls // settings.proposals
    train, held, shifted = [], [], []
    for s in seeds:
        final, _ = improve(start, train_score, random.Random(s), rounds, settings)
        train.append(train_score(final) - train_score(start))
        held.append(held_score(final) - held_score(start))
        shifted.append(shifted_score(final) - shifted_score(start))
    mean = lambda xs: sum(xs) / len(xs)
    out = {"train": mean(train), "held": mean(held), "shifted": mean(shifted)}
    out["gap"] = out["train"] - out["held"]
    return out

Milestone 6: the audit

Everything so far assumed an honest improver. Now suppose it can cheat. The improver is just a function that receives a scorer. In a single Python process it can also import the module and call meta_utility directly. Three cheats are given in the starter:

  • cheat_budget scores candidates with ten times the budget. Its configs look better because they were tested under a budget they will never get.
  • cheat_peek scores candidates on the held-out tasks. It then reports a held-out number it selected on.
  • cheat_tamper raises the module's BUDGET constant, then calls the honest scorer.

The defence is a tripwire. audit swaps the module's meta_utility for a spy that records the task seeds and the budget of each call and then calls the real one. It runs the improver, and it always restores everything in a finally block. A call on tasks other than the training tasks is "peeked". A call with a different budget is "budget". A changed constant afterwards is "tampered". Run the cheats and the honest improver side by side, starting from the naive config:

import random
import sys
sys.path.insert(0, ".")
import solution as lab

train = lab.make_scorer()
held = lab.make_scorer(lab.HELD_TASKS)
start = lab.DEFAULT
print(f"{'improver':13s} {'train':>7} {'held-out':>9}  audit")
for name, imp in (("honest", lab.honest()),
                  ("cheat_budget", lab.cheat_budget),
                  ("cheat_peek", lab.cheat_peek)):
    final = imp(start, train, random.Random(0), 4)
    gain_tr = train(final) - train(start)
    gain_he = held(final) - held(start)
    ok, why = lab.audit(imp, start)
    verdict = "accepted" if ok else "rejected " + str(why)
    print(f"{name:13s} {gain_tr:+7.3f} {gain_he:+9.3f}  {verdict}")
improver        train  held-out  audit
honest         +1.000    +1.056  accepted
cheat_budget   +1.000    +1.139  rejected ['budget']
cheat_peek     +1.000    +1.361  rejected ['peeked']

Look at what this shows. All three improvers gain the same on the training tasks. The cheat that peeks gets a better held-out number, +1.361 against +1.056, but only because it picked its config on those tasks. The budget cheat is also slightly ahead. Neither number is evidence of a better improver. The audit rejects both before anyone can quote them.

A tripwire is not a wall

This audit catches improvers that go through the module's meta_utility name. A determined cheater in the same process could rebind that name to its own function, read the call stack, or edit the spy. A real system puts the improver in a separate process that holds only a handle to the scorer, and keeps the held-out tasks on a machine the improver cannot reach. That is the point of chapter 16's rule that the evaluation set must be physically out of reach. The audit here shows what to look for. It does not prove an improver is honest.

Your task

Write audit(improver, start=DEFAULT, rounds=2, seed=0). Snapshot BUDGET, TRAIN_TASKS and HELD_TASKS. Install a spy. Run improver(start, make_scorer(), random.Random(seed), rounds). In a finally block restore the real function and the constants. Return (ok, reasons), with reasons in the order "peeked", "budget", "tampered".

check.py verifies: the honest improver is accepted with no reasons; cheat_budget gives ["budget"]; cheat_peek gives ["peeked"]; cheat_tamper includes "tampered". A sneaky improver that builds a held-out scorer is still caught. An improver that does both gets the reasons in order. A crashing improver leaves nothing patched. And after all this the honest improver still gains on the training tasks.

Hints try without first
  • Declare global meta_utility, BUDGET, TRAIN_TASKS, HELD_TASKS. Assigning to meta_utility replaces the name that make_scorer looks up at call time.
  • The spy must have the same signature as meta_utility, including lo and hi defaults, and must return the real result.
  • Read the constants again after the run, but before restoring them, so you can compare. Compare tasks as tuples.
  • The cached scorer hides repeat calls on purpose. That is fine: a repeat of an honest call is honest.
Solution spoiler 
def audit(improver, start=DEFAULT, rounds=2, seed=0):
    """Run `improver` under surveillance: (ok, reasons)."""
    global meta_utility, BUDGET, TRAIN_TASKS, HELD_TASKS
    real = meta_utility
    before = (BUDGET, TRAIN_TASKS, HELD_TASKS)
    calls = []

    def spy(config, task_seeds, budget, lo=20, hi=60):
        calls.append((tuple(task_seeds), budget))
        return real(config, task_seeds, budget, lo, hi)

    meta_utility = spy
    try:
        improver(start, make_scorer(), random.Random(seed), rounds)
        after = (BUDGET, TRAIN_TASKS, HELD_TASKS)
    finally:
        meta_utility = real
        BUDGET, TRAIN_TASKS, HELD_TASKS = before
    reasons = []
    if any(tasks != tuple(before[1]) for tasks, _ in calls):
        reasons.append("peeked")
    if any(b != before[0] for _, b in calls):
        reasons.append("budget")
    if after != before:
        reasons.append("tampered")
    return not reasons, reasons

How much to trust these numbers

This is a toy with three training tasks, three or twelve random streams, and a landscape that is mostly flat except for one cliff. Treat the sizes as illustrative.

The self-improvement step is fragile. Run self_improve for 10 rounds with four different meta-meta seeds (0 to 3). Seeds 0 and 2 find n_change = 3, with fresh-stream gains of 0.894 and 0.917. Seed 3 finds n_change = 2 and 0.815. Seed 1 finds nothing and stays at the seed settings, 0.648. One reason is that the strict "keep if better" rule needs a lucky first candidate. The honest summary is that self-improvement helped in three of four runs, by a margin of 0.17 to 0.27 bins.

How this connects to the real thing

The structure here follows the Self-Taught Optimizer (STOP) of Zelikman and colleagues (2023, "Self-Taught Optimizer (STOP): Recursively Self-Improving Code Generation", arXiv 2310.02304). In that paper the improver is a program that asks a language model to improve code. The program is then used to improve itself, and the score for the improver is its average utility on downstream tasks. That average is the meta-utility of this lab. The model and the code are far richer than a Config. The loop is the same: a score for an improver, a way to propose changes to it, and a rule that keeps the better one.

Two differences are worth naming. Here the improver is data (three numbers), so it cannot do anything unexpected. In STOP the improver is code, so it can. The authors also measured how often the generated code bypassed a sandbox. That is why the audit in milestone 6 belongs in the lab and not in an appendix. For the full picture, read chapter 21. For the evaluation rules behind milestones 5 and 6, see chapter 16 and chapter 15, and the gameable evaluator of lab 6.

Going further

  1. Add a field. Put the population size POP into Config with choices 3, 6, 12. Does the improver turn it up or down? Does it matter?
  2. Shrink the training set. Use one training task instead of three. Predict what happens to the gap in milestone 5, then run it.
  3. Make the improver code. Let an improver be a short program in the lab 3 language that maps a config and a score history to a new config. Evolve it with the lab 3 evolver, judged by improver_utility. This is much closer to STOP, and much easier to cheat with. Which of the audit's checks still make sense?
  4. Move the wall. Run the improver in a separate process with multiprocessing, giving it only a pipe to the scorer. Which of the three cheats become impossible instead of detected?
  5. Count the noise. Repeat milestone 4 for 20 meta-meta seeds. What fraction find a better improver than the seed? Report it with a confidence interval from chapter 16.
  6. Stack a fourth level. Use self_improve to tune the settings of self_improve. Do the gains shrink at each level? Why might they?

What you learned

  • A utility must be total: every failing program gets a fixed penalty, so a search never crashes and a broken program never wins.
  • A fair meta-utility fixes the budget, gives each task its own counter, and scores on instances the evolver never saw.
  • Hill climbing works at every level. The same move (propose, score, keep if strictly better) improves a heuristic, a config and the improver itself.
  • Compare improvers at equal numbers of score calls, or you will measure compute and call it skill.
  • Here self-application helped modestly: 0.67 to 1.00 bins on training, 0.65 to 0.89 on fresh streams, in three of four runs.
  • Meta-overfitting is real. A structural fix transfers to held-out and shifted tasks. A tweak to a config that was already good does not.
  • An improver with access to its own scorer can cheat by raising its budget, peeking at held-out tasks or editing constants. A tripwire catches the clumsy versions. Only a separate process, with the held-out tasks out of reach, stops the rest.

Check your understanding

Why does meta_utility create a fresh Budget for every task, instead of one counter for the whole call?

  1. A fresh counter makes the evolver run faster
  2. With a shared counter the first task could use every evaluation, so later tasks would get none and the score would depend on task order
  3. The evolver cannot read a counter that has already been used
  4. It keeps the heuristics from different tasks apart
Every task must get the same resources, or the mean mixes tasks that were searched properly with tasks that barely were. Speed is unaffected (the first option), the evolver can read any counter (the third), and heuristics are kept apart by the loop, not by the counter (the fourth).

The evolver picks its winner on three search instances. Why are the found heuristics scored on six different instances?

  1. Six instances take less time than three
  2. The search instances are too long to score twice
  3. The winner was chosen because it did well on the search instances, so scoring there would reward configs that overfit them
  4. The scoring instances are harder, which makes the comparison tougher
Selection inflates the score on the data it selected on. Fresh instances of the same kind give an unbiased estimate of what the config really finds. Time (the first option) is irrelevant, and the scoring instances are drawn from the same distribution, so they are not harder (the fourth).

Improver A makes 4 proposals in 1 round. Improver B makes 1 proposal in 4 rounds. Why does improver_utility fix the total number of score calls?

  1. So that a difference in gain reflects the improver's design rather than how much compute it was given
  2. So that both improvers find exactly the same config
  3. Because the scorer can only be called four times
  4. So the results do not depend on the random seed
If one improver got more score calls it would usually win, and you would learn only that compute helps. With equal calls, a gap measures the design. Equal calls do not make the results identical (the second option), the scorer has no such limit (the third), and the seed still matters (the fourth), which is why the lab averages over several streams.

Starting from the tuned config, an improver gains +0.09 bins on the training tasks and -0.08 on the held-out tasks. What should you report?

  1. The training gain, because the improver was built to raise it
  2. The average of the two, +0.005
  3. That the improver is broken
  4. That it found no real improvement: the training gain is selection on three tasks, and the held-out number is the honest one
The held-out figure is the unbiased estimate, and it is slightly negative, so the claim "it improved the config" is not supported. The training gain is real as a fact about those tasks and says little about others. Averaging mixes a biased and an unbiased number. The improver is not broken (the third option): it did what it was asked, on a landscape with nothing left to find.

cheat_budget scores candidate configs with ten times the evaluation budget. What goes wrong, even if no one ever reports its score?

  1. Nothing: a larger budget only gives more accurate scores
  2. It selects configs for a budget they will never have in use, so they may be worse under the real one
  3. The scorer raises an error above the budget
  4. It changes the training tasks
A config can be best at 200 evaluations and poor at 20. The improver would be tuning for conditions that do not hold when its output is used. More accuracy at the wrong budget is not more accuracy about the real question (the first option). Nothing raises an error (the third), and the tasks are unchanged (the fourth).

Which improver would the spy-based audit in this lab fail to catch?

  1. One that calls meta_utility directly on the held-out tasks
  2. One that calls meta_utility with ten times the budget
  3. One that rebinds the module's meta_utility name to its own function before calling it
  4. One that edits BUDGET and does not restore it
The spy is just another name in the same module, and code in the same process can replace it, so the improver can hide its calls from the log. The other three each go through the spy or leave a changed constant behind, and are caught. This is why a real system isolates the improver in another process.

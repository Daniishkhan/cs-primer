Lab 3: A Mini FunSearch

Chapter 9 described a loop in which a language model proposes edits to code, an automatic evaluator scores them, and a database of the best programs seeds the next round, and it ran a miniature of that loop on online bin packing. In this lab you build the miniature yourself, piece by piece: a sandbox that runs untrusted code safely and deterministically, an evaluator that turns every outcome (including crashes and infinite loops) into a result, a mutation operator that edits the program's syntax tree, a database of islands and clusters, and the loop that ties them together. The last milestone reports the winner on instances the search never saw, which is where the story gets honest.

Why this lab matters

The previous chapter insisted that in program evolution the evaluator matters as much as the model, and that "the model proposes, the evaluator disposes". That is easy to nod along to and hard to feel until you have written both halves. In this lab the "model" is a fifty-line function that edits syntax trees, so it is cheap and exact and you can see everything it does, while the evaluator and the sandbox around it are real engineering: a whitelist, a step budget, a total function that never raises. By the end you will have seen, in numbers, why a language model can be replaced by a much dumber operator and still make progress (the loop does the work), why the evaluator has to be the strict half of the partnership, and why a score on the instances you searched on is not the score to report.

The same skeleton is behind the systems of chapter 9 and the frameworks of chapter 10: FunSearch's islands and clusters, OpenEvolve's ring of islands, ShinkaEvolve's insistence on counting model calls. When you read a configuration file with num_islands and migration_interval in it, you will know what each setting does to a loop you have written. And the failure modes you build defences against here (a candidate that never terminates, one that returns a boolean, one that games the score) are the ones chapter 15 catalogues at scale.

A stand-in model, no clock, no network

Nothing here calls a language model. The operator that proposes new programs is a deterministic stand-in: a seeded function that applies one small edit to a syntax tree. It is not a language model and does not behave like one (a real model writes free-form code, and would find ideas this operator cannot); the loop around it is the same loop. Every random number comes from a seeded random.Random, and a candidate is limited by a step budget ("fuel") rather than by seconds, so the same code gives the same numbers on every machine. A failing random check prints its seed: python3 check.py solution 3 7 runs milestone 3 on seed 7 only. Python 3.9 or newer (the lab uses ast.unparse), standard library only. The reference solution passes in about twenty seconds. An optional last section shows how a real model would replace the stand-in.

What you'll build

The task is the one from chapter 9: online bin packing. Items of size 20 to 60 arrive one at a time and each must be put in a bin of capacity 100 at once, using as few bins as possible. The only thing evolved is one function, priority(item, rem), where rem is the space left in a bin: each item goes to the feasible bin with the highest priority. The seed program is best fit (-(rem - item), prefer the tightest fit), which uses 130.3 bins on average on the ten training instances. Six milestones:

  1. A sandbox: a whitelist of syntax-tree nodes, and a fuel counter that stops any loop, so untrusted text can be run without trusting it.
  2. An evaluator that never raises: pack the items with a candidate, and turn every outcome (rejected, crashed, timed out, nonsense value, a score) into one result.
  3. A mutation operator: edit the syntax tree, so that children are valid programs by construction.
  4. An island of clusters: programs grouped by what they do, with FunSearch's two-stage, temperature-controlled draw of parents.
  5. Islands: several of those, and the rule that replaces the weakest half.
  6. The loop and an honest report: run the search for a budget of model calls, then compare training and held-out scores.

Milestone 1: a sandbox with a whitelist and a fuel budget

Everything in this lab runs code that nobody has read: the candidates are text produced by a mutation operator, and in a real system, by a model. Chapter 9 gave the evaluator a separate process and a two-second timer, and said honestly that this is isolation of mistakes, not a security boundary. This milestone takes the complementary approach, which works because the language is tiny: do not run what you have not read. Candidates may only use a handful of syntax constructs, and everything else is refused before a single line executes.

The tool is Python's own parser. ast.parse(src) turns source into a tree of nodes (Assign, BinOp, Name, Call, Import, Attribute, and so on), and a whitelist says which node types are allowed; anything not on the list is rejected. The alternative, a blacklist of dangerous things, always misses one. The classic example is ().__class__.__bases__[0], which reaches the base object class and from there every class in the interpreter without a single import or call to a function called anything dangerous. With a whitelist there is no need to think of it: Attribute and Subscript are simply not on the list. The given constant ALLOWED_NODES lists the permitted nodes (arithmetic, comparisons, if, while, assignments, abs/min/max calls); your validate adds the rules a type list cannot express: the function must be exactly def priority(item, rem):, calls may only name abs, min or max, names must exist, no name may begin with an underscore, constants must be small numbers, and the source must be short.

Why allow while at all, if the packing heuristic never needs a loop? Because a safe design does not rely on any one layer. The whitelist keeps out the dangerous; fuel bounds what is left. A step budget counts operations, not seconds, and it matters for two reasons. A wall-clock limit is nondeterministic: the same candidate passes on a fast machine and times out on a slow one, so an evolutionary run stops being reproducible, which is the property that makes it debuggable. And checking a clock inside interpreted code means either a separate process (slow to start, hundreds of thousands of times in a long run) or tracing every line.

The cheaper trick is to instrument the tree before compiling it: insert a call _tick() as the first statement of the function and as the first statement of every while body. A shared Fuel object counts the ticks and raises OutOfFuel when the budget is gone. Code that never loops costs one tick per call; code that loops forever eats the budget a tick per turn. The instrumented version of a small loop, produced by the lab's own code, shows the idea:

Three details in that output are worth stopping on. The _tick() calls are invisible to the candidate's author, and the whitelist forbids any name that begins with an underscore, so a candidate cannot call, replace or silence the counter. The integer constants have all become floats (0.0, 5.0), which looks fussy and is the answer to the last case in the output: Python integers have no upper limit, so x = x * x in a loop squares an integer whose size doubles every turn, and a thousand turns would try to build a number with more digits than there are atoms in the universe, long before the fuel counter was consulted. Floats overflow to infinity instead, which is harmless (and caught later, in milestone 2). Finally, the rejection lines at the top of the output show the kind of message the evaluator will carry: not "something went wrong" but which rule was broken.

Common misconception

"A whitelist sandbox makes it safe to run model-written code." It makes it safe to run model-written code in this tiny language, against a model that is mistaken or an operator that is random. Python's real standard library is a very different surface, and a whitelist over it would be a research project. For anything an adversary can reach, the answer is still an operating-system boundary: a container or virtual machine with no credentials and no network, as in sandboxes and permissions and the untrusted-code design of the online code judge studio. This milestone teaches the first layer of defence, the one that costs nothing per candidate, not a replacement for the second.

class _Instrument(ast.NodeTransformer):
    @staticmethod
    def _tick():
        return ast.Expr(ast.Call(ast.Name("_tick", ast.Load()), [], []))

    def visit_FunctionDef(self, node):
        self.generic_visit(node)
        node.body.insert(0, self._tick())
        return node

    def visit_While(self, node):
        self.generic_visit(node)
        node.body.insert(0, self._tick())
        return node

    def visit_Constant(self, node):
        if type(node.value) is int:                 # all arithmetic becomes float arithmetic: no huge integers
            return ast.copy_location(ast.Constant(float(node.value)), node)
        return node

def instrument(tree):
    """Return a NEW tree (leave `tree` untouched) in which the function body and every while-loop body ..."""
    new = _Instrument().visit(copy.deepcopy(tree))
    return ast.fix_missing_locations(new)

def validate(src):
    """Parse `src` and return its ast.Module, or raise Rejected(reason)."""
    if len(src) > MAX_CHARS:
        raise Rejected(f"source longer than {MAX_CHARS} characters")
    try:
        tree = ast.parse(src)
    except (SyntaxError, ValueError, RecursionError, MemoryError) as e:
        raise Rejected(f"syntax error: {type(e).__name__}")
    if len(tree.body) != 1 or not isinstance(tree.body[0], ast.FunctionDef):
        raise Rejected("expected exactly one function definition")
    fn = tree.body[0]
    a = fn.args
    if (fn.name != "priority" or [x.arg for x in a.args] != ["item", "rem"] or a.vararg or a.kwarg
            or a.kwonlyargs or a.posonlyargs or a.defaults or fn.decorator_list or fn.returns):
        raise Rejected("the function must be exactly `def priority(item, rem):`")
    nodes = list(ast.walk(tree))
    if sum(isinstance(n, ast.FunctionDef) for n in nodes) != 1:
        raise Rejected("nested function definitions are not allowed")
    if len(nodes) > MAX_NODES:
        raise Rejected(f"more than {MAX_NODES} syntax nodes")
    assigned = {n.id for n in nodes if isinstance(n, ast.Name) and isinstance(n.ctx, ast.Store)}
    known = {"item", "rem"} | assigned | set(SAFE_CALLS)
    for n in nodes:
        if not isinstance(n, ALLOWED_NODES):
            raise Rejected(f"{type(n).__name__} is not allowed")
        if isinstance(n, ast.Constant):
            if type(n.value) not in (int, float, bool) or abs(n.value) > 1e9:
                raise Rejected(f"constant {n.value!r} is not allowed")
        if isinstance(n, ast.Name):
            if n.id.startswith("_"):
                raise Rejected(f"name {n.id!r} is not allowed")
            if isinstance(n.ctx, ast.Load) and n.id not in known:
                raise Rejected(f"unknown name {n.id!r}")
        if isinstance(n, ast.Call):
            if not (isinstance(n.func, ast.Name) and n.func.id in SAFE_CALLS) or n.keywords:
                raise Rejected("only abs, min and max may be called, with positional arguments")
    return tree

def compile_restricted(src, fuel):
    """validate, instrument, compile and exec `src`; return the `priority` function."""
    tree = instrument(validate(src))
    code = compile(tree, "<candidate>", "exec")
    ns = {"__builtins__": {"abs": abs, "min": min, "max": max}, "_tick": fuel.tick}
    exec(code, ns)
    return ns["priority"]

Milestone 2: an evaluator that never raises

An evaluation is a function from a program (text) to a result, and the main design rule from chapter 9 is that it must be total: every possible input maps to some result, and nothing a candidate does can escape as an exception into the controller, because an unhandled error would lose hours of search. So the result is not a number but an Outcome with a status and a score that exists only when the status is ok:

StatusMeaningExample
rejectedThe sandbox refused it. It never ran.an import, a string constant, a syntax error
errorIt ran and raised.division by zero, a name read before it was assigned
timeoutIt ran out of fuel.while True, or a loop of 2,000 turns on every call
bad_valueIt returned something that is not a finite number.a boolean, None, infinity, nan
okIt packed all the instances.mean bins = 130.3

The bad_value row is the lesson of chapter 9's wrong-type candidate, which returned the string 'tight' for every bin: Python compares equal strings happily, no bin ever has a strictly higher priority, the packing degenerates to first fit, and the evaluator reported a respectable, meaningless 130.2. Here a string constant is rejected statically, but the same hole reappears through every other path: return item < rem yields a boolean, which is also a number in Python (True > False), and an expression that overflows gives infinity, and infinity minus infinity gives nan, which compares false against everything and corrupts the "highest priority" test silently. Check the value on every call, and accept only a finite int or float (type(v) in (int, float), which excludes bool).

Two more pieces. pack is the packing loop of chapter 9: for each item, ask priority(item, rem) of every feasible bin (rem >= item), take the highest, and break ties toward the earliest bin; open a new bin if none fits. And the fuel budget is shared by all the instances of one evaluation, so that a program that takes 2,000 steps per call is a timeout even though no single call looks long, which is what stops a slow-but-finite candidate from eating a whole search. The evaluator also records the number of bins used on each instance, a tuple that the next milestones call the program's signature.

The script below evaluates seven programs, two good and five that misbehave. The numbers are real: best fit and first fit reproduce chapter 9's 130.3 and 130.7 bins, and the "steps" column is the number of times priority was called.

def pack(items, priority):
    """Online bin packing."""
    bins = []
    for it in items:
        best, best_p = None, None
        for i, rem in enumerate(bins):
            if rem >= it:
                p = priority(it, rem)
                if best_p is None or p > best_p:
                    best, best_p = i, p
        if best is None:
            bins.append(CAP - it)
        else:
            bins[best] -= it
    return len(bins)

def evaluate(src, instances, fuel_budget=FUEL):
    """Score `src` on a list of instances (each a list of item sizes)."""
    fuel = Fuel(fuel_budget)
    try:
        fn = compile_restricted(src, fuel)
    except Rejected as e:
        return Outcome("rejected", detail=str(e))
    except Exception as e:                           # compile/exec failure of an accepted tree: treat as rejected
        return Outcome("rejected", detail=f"{type(e).__name__}: {e}")

    def checked(item, rem):
        v = fn(float(item), float(rem))
        if type(v) not in (int, float) or not math.isfinite(v):
            raise ValueError(f"priority returned {v!r}")
        return v

    try:
        counts = tuple(pack(items, checked) for items in instances)
    except OutOfFuel as e:
        return Outcome("timeout", detail=str(e), steps=fuel.used)
    except ValueError as e:
        return Outcome("bad_value", detail=str(e), steps=fuel.used)
    except Exception as e:
        return Outcome("error", detail=f"{type(e).__name__}: {e}", steps=fuel.used)
    return Outcome("ok", sum(counts) / len(counts), counts, steps=fuel.used)

Milestone 3: a mutation operator on the syntax tree

Chapter 9 explained why a language model makes a good mutation operator: random edits to program text are almost always broken, and the model's edits mostly are not. The same is true of the stand-in, and for the same reason it needs to work on structure rather than characters. If you flip a random character of a ten-line program, you usually get a syntax error, or a name that does not exist, or a number glued to a letter. The script below compares the two on the seed program: 300 edits of each kind, counting the children that pass validate.

Tree edits give 300 valid children out of 300; character flips give 6. The tree operator is not cleverer than the text one, it is closed: it can only produce trees that are made of legal nodes, so unparsing a child always gives legal text. (ast.unparse also gives each tree one canonical spelling, which is why two programs that differ only in spacing are the same string and the loop can spot duplicates by comparing text.) Look at the four children: a new comparison inserted as a rule, an operator swapped from - to +, a doubled minus sign, and a name replaced by another.

The operator works the way a transformation of a tree should. Pick a node of a particular kind at random, change one thing about it, and unparse. The edits live in a small grammar of edits. Two of them you write, because they show the technique at its simplest; the rest are given, and you will use them through mutate:

EditWhat it does to the treeWho writes it
edit_constantNudge one number by -2, -1, +1 or +2 (never below 0).you
edit_operatorSwap one + - * or one < <= > >= for another of its family.you
edit_insert_ruleInsert if name cmp (name or number): return payoff after the leading assignments.given
edit_shapeWrap one expression of a return in abs, a negation, a shift, a %, min or max.given
edit_replace_nameReplace a name that is read by another name in scope.given
edit_deleteDelete one statement of the body, never the last.given

An edit takes (tree, rng), changes the tree in place, and returns True if it had something to edit or False if not (a program with no constants has nothing for edit_constant, and the seed is such a program). mutate(src, rng) chooses one edit from the tuple EDITS, applies it to a freshly parsed tree, and unparses. It then checks the child: it must differ from the parent and must pass is_valid. If not, mutate tries again, up to ten times, and as a last resort returns the parent unchanged. The check matters, because some given edits can produce a tree the sandbox refuses (edit_delete can remove the only assignment of a name that is still read), and because an edit that "succeeds" but changes nothing, like nudging a 0 down by one, would waste an evaluation.

Common misconception

"If the mutation operator only produces valid programs, the evaluator's error handling is redundant." Valid means the sandbox accepted the tree; it does not mean the program runs. Child 1 in the output above is gap = gap - item: every name in it exists somewhere in the function, so validate accepts it, and on its first call Python raises UnboundLocalError because gap is read before it is assigned. In the 500-call searches at the end of this lab, between 5 and 13 of every 450-odd evaluated programs end as error for exactly this kind of reason (or a modulus nudged down to zero). A real language model fails far more often, in far more creative ways. The sandbox and the evaluator are the net; the operator only decides how often the net is needed.

def edit_constant(tree, rng):
    """Nudge one numeric constant by -2, -1, +1 or +2 (never below 0)."""
    consts = [n for n in ast.walk(tree) if isinstance(n, ast.Constant) and type(n.value) in (int, float)]
    if not consts:
        return False
    node = rng.choice(consts)
    node.value = max(0, node.value + rng.choice([-2, -1, 1, 2]))
    return True

def edit_operator(tree, rng):
    """Swap one operator for another of its family, in place: + - * among arithmetic operators, < <= > ..."""
    sites = [n for n in ast.walk(tree)
             if (isinstance(n, ast.BinOp) and isinstance(n.op, ARITH))
             or (isinstance(n, ast.Compare) and len(n.ops) == 1 and isinstance(n.ops[0], CMP))]
    if not sites:
        return False
    node = rng.choice(sites)
    if isinstance(node, ast.BinOp):
        node.op = rng.choice([o for o in ARITH if not isinstance(node.op, o)])()
    else:
        node.ops = [rng.choice([o for o in CMP if not isinstance(node.ops[0], o)])()]
    return True

def mutate(src, rng, attempts=10):
    """One syntactically valid edit of `src`, as canonical source text."""
    base = canonical(src)
    for _ in range(attempts):
        tree = ast.parse(base)
        edit = rng.choice(EDITS)
        if not edit(tree, rng):
            continue
        ast.fix_missing_locations(tree)
        new = ast.unparse(tree)
        if new != base and is_valid(new):
            return new
    return base

The stand-in model, and where a real one would plug in

The loop in milestone 6 does not call mutate directly. It calls a mutator, any function mutator(parents, rng) -> source text, where parents is a short list of programs sorted from worst to best, exactly like the numbered versions (priority_v0, priority_v1) in a FunSearch prompt, which the model is asked to continue. The given stand_in_llm edits the best parent with your mutate, and one time in five first copies an if rule from an earlier parent with edit_borrow, which is the stand-in's version of "the model has seen a few good programs and combines ideas". Anything with the same signature can replace it, including a function that calls a real model; the optional last section shows how.

Milestone 4: an island of clusters

If every prompt contained the single best program, the database would collapse onto one family of solutions and the search would stall; chapter 9 described FunSearch's remedy. Programs are grouped by what they do, not by how they look. A cluster is the set of programs with the same signature, here the tuple of bin counts on the ten training instances. -(rem - item) and gap = rem - item; return -gap are different text and the same behaviour, so they share a cluster; changing any decision that changes any packing moves a program to a different one. Programs in a cluster are interchangeable as far as the score goes, so the database keeps the shortest few (at most four), which fights bloat.

The script builds one island from four programs. The numbers are real, and show the two spellings of best fit landing together.

Choosing parents is a two-stage draw. First pick a cluster, with probability proportional to exp(fitness / Tc): a softmax over cluster fitness, where the temperature Tc (here 0.5 bins) sets how strongly high scorers are favoured. Then pick a program within the cluster by a softmax over minus its length, with its own temperature (50 characters here), so shorter programs are more likely. Draw this k times to fill the prompt, drop duplicates, and sort from worst cluster to best, so the best program is last, where a model's attention would look for "the next version".

The temperature is worth getting a feel for. With three clusters at fitness -130, -129 and -128:

(These are exp(f/T) normalised, which you can check with a calculator, and which the check verifies with 4,000 draws each.) Notice the scale: temperatures here are in bins because fitness is minus mean bins. That is why the best temperature is a property of the problem's score range, and why frameworks normalise the scores first.

One implementation trap: exp(-130 / 0.5) underflows to exactly zero in floating point, and so would every other term. The standard fix, subtracting the maximum before exponentiating, leaves the probabilities unchanged and keeps the largest term at exp(0) = 1. The check feeds your function values around -1000 to make sure you do.

def softmax_weights(values, temperature):
    """Probabilities proportional to exp(value / temperature), computed stably (subtract the maximum ..."""
    m = max(values)
    w = [math.exp((v - m) / temperature) for v in values]
    total = sum(w)
    return [x / total for x in w]

# a method of class Island
def add(self, src, outcome):
    """Store an 'ok' outcome (ignore anything else)."""
    if not outcome.ok:
        return
    c = self.clusters.setdefault(outcome.bins, {"fitness": outcome.fitness, "programs": []})
    if src not in c["programs"]:
        c["programs"].append(src)
        c["programs"].sort(key=lambda p: (len(p), p))
        del c["programs"][MAX_PER_CLUSTER:]
    if len(self.clusters) > self.max_clusters:
        worst = min(self.clusters, key=lambda s: self.clusters[s]["fitness"])
        del self.clusters[worst]

# a method of class Island
def sample(self, rng, k=2, cluster_temp=0.5, length_temp=50.0):
    """Best-shot prompt material: draw k programs, each by a two-stage draw, and return the DISTINCT ..."""
    sigs = list(self.clusters)
    fits = [self.clusters[s]["fitness"] for s in sigs]
    chosen = {}
    for _ in range(k):
        sig = sigs[rng.choices(range(len(sigs)), softmax_weights(fits, cluster_temp))[0]]
        progs = self.clusters[sig]["programs"]
        p = progs[rng.choices(range(len(progs)), softmax_weights([-len(x) for x in progs], length_temp))[0]]
        chosen[p] = self.clusters[sig]["fitness"]
    return sorted(chosen, key=lambda p: (chosen[p], len(p)))

Milestone 5: islands, and replacing the weakest

One island with a cluster-based sampler still has a failure mode: if one family of ideas takes an early lead, the temperature keeps feeding it, and the others never get the evaluations they need to mature. FunSearch's second defence is to run several islands, independent sub-populations that never see each other's programs, so a family that dominates one island cannot crowd out the others. The loop gives each island its turn in rotation. OpenEvolve, in chapter 10, does the same with a ring and a migration_interval.

Independence has a cost: an island that has found nothing keeps spending calls on nothing. So every so often the database performs a reseed: rank the islands by the fitness of their best program, throw away the weakest half, and replace each discarded island with a fresh one that holds only the best program of a surviving island, chosen at random among the survivors. Effort drifts towards what works without ever collapsing to one lineage, because the replaced islands start with one program and grow their own clusters from it.

Three details define the rule exactly, and the check tests each. The ranking breaks ties by lower index, so a fresh database (every island holding the seed) always replaces the last half. With an odd number of islands, len // 2 are replaced (two of five), so the survivors are always the larger half. And the best program in the whole database must survive a reseed, since survivors are never touched. The given Island.fresh_from_best() builds the one-program island for you.

# a method of class Database
def best(self):
    """(program, fitness) of the best program on any island."""
    top = None
    for isl in self.islands:
        b = isl.best()
        if b is not None and (top is None or b[1] > top[1]):
            top = b
    return top

# a method of class Database
def reseed(self, rng):
    """Replace the weakest half of the islands (len // 2 of them)."""
    order = sorted(range(len(self.islands)),
                   key=lambda i: (-(self.islands[i].best()[1]), i))
    n = len(order) // 2
    if n == 0:
        return []
    survivors, weakest = order[:len(order) - n], order[len(order) - n:]
    moves = []
    for i in weakest:
        j = rng.choice(survivors)
        self.islands[i] = self.islands[j].fresh_from_best()
        moves.append((i, j))
    return moves

Milestone 6: the loop, and an honest report

Now the loop. The budget is counted in calls of the mutation operator, because with a real model that is the quantity that costs money and wall-clock time: ShinkaEvolve's paper is about needing far fewer of them than systems that, in its authors' words, need thousands of samples. Each call, in order: pick the island whose turn it is (call i works on island i % n_islands), draw k parents from it, ask the mutator for a child, skip the evaluation if that exact text has been seen before (a call that produced a duplicate is still a call, and still spent), otherwise evaluate it and store the result. After every reseed_every calls, reseed. Record the best fitness after every call, so you can plot the progress curve.

Evaluations are cheaper than calls here (a few milliseconds each), so the loop is fast. The things the check looks for are bookkeeping: that exactly budget calls are made, the trace never goes down, evaluations equals the sum of the status counts, the same seed reproduces the whole run, and three deliberately bad mutators cannot break anything. One returns its parent (no new program is ever evaluated), one returns garbage with an import in it (every child is rejected), and one returns infinite loops (every child is a timeout, paid for in fuel and nothing else).

The second function, report, is short and is the point of the lab. It takes a program and returns its mean bins on the training instances (the ten the search looked at) and on thirty held-out instances (seeds 100 to 129) that it never did, next to best fit's, and the saving on each. Chapter 16 spends a whole chapter on why this matters; the script below shows it happening.

def funsearch(budget, seed, train_seeds=TRAIN_SEEDS, n_islands=4, k=2, mutator=stand_in_llm,
              reseed_every=150, cluster_temp=0.5, fuel_budget=FUEL):
    """Run the FunSearch loop for `budget` calls of the mutation operator and return a RunResult."""
    rng = random.Random(seed)
    train = make_instances(train_seeds)
    seed_src = canonical(SEED_SRC)
    seed_out = evaluate(seed_src, train, fuel_budget)
    db = Database(n_islands, seed_src, seed_out)
    seen = {seed_src}
    statuses = {"ok": 1}
    evals, trace = 1, []
    for call in range(budget):
        isl = call % n_islands
        parents = db.islands[isl].sample(rng, k, cluster_temp)
        child = mutator(parents, rng)
        if child not in seen:
            seen.add(child)
            out = evaluate(child, train, fuel_budget)
            evals += 1
            statuses[out.status] = statuses.get(out.status, 0) + 1
            db.add(isl, child, out)
        if (call + 1) % reseed_every == 0:
            db.reseed(rng)
        trace.append(db.best()[1])
    src, _ = db.best()
    return RunResult(src, evaluate(src, train, fuel_budget), budget, evals, statuses, trace)

def report(src, train_seeds=TRAIN_SEEDS, test_seeds=TEST_SEEDS):
    """Train and held-out scores (mean bins) of `src` and of best fit, and the saving in each."""
    train, test = make_instances(train_seeds), make_instances(test_seeds)
    mine_tr, mine_te = evaluate(src, train), evaluate(src, test)
    base_tr, base_te = evaluate(SEED_SRC, train), evaluate(SEED_SRC, test)
    return {"train": mine_tr.score, "test": mine_te.score, "base_train": base_tr.score, "base_test": base_te.score,
            "gain_train": base_tr.score - mine_tr.score, "gain_test": base_te.score - mine_te.score,
            "lower_test": sum(lower_bound(i) for i in test) / len(test)}

Going further

  1. Cascade evaluation. Most children are worse than their parent. Evaluate each on two instances first and stop if it is clearly behind (more than one bin behind its parent's score on those two); evaluate on all ten only if it passes. How many full evaluations does this save, and does the best score at a fixed number of calls change? This is the cascade chapter 9 describes for AlphaEvolve.
  2. A behaviour archive. Replace the cluster-by-signature with a MAP-Elites grid (chapter 4) over two behaviour descriptors you choose, for example the mean bins on small-item instances and on large-item instances, and keep the best program per cell. Does the database stay more diverse, and does the held-out score improve?
  3. Shift the distribution. Evolve on items of size 20 to 60 and report on instances with sizes 10 to 70, as chapter 9's "Try it yourself" suggests. Which of the evolved rules breaks? The dead-gap constant of 20 is the obvious suspect.
  4. Feed errors back. Let the mutator see the Outcome.detail of the failed children of its parents, as OpenEvolve's artefact option does. Does the stand-in use it? Write a rule-based operator that does (for example, after an UnboundLocalError, move the assignment above the first use) and measure how many fewer calls are wasted on errors.
  5. Make the evaluator gameable, then fix it. Change pack so that an item larger than every open bin's remaining space is silently skipped when the program returns a priority above 1,000. Run a search. What does it find, and which of milestones 1 and 2 would have to change to stop it? Lab 6 turns this into the main event.
  6. Count the cost. Assume each model call costs 1 unit and each evaluation 0.01. Plot best bins against total cost for 1, 2 and 4 parents per prompt (k). Chapter 10 argues that framework settings are decisions about spending calls; this is one of them.

Systems connection

The evaluator in this lab is a job-execution service in miniature. At the scale of the systems in chapter 9, thousands of independent, CPU-heavy evaluations flow through a queue to a pool of workers, results return out of order, workers die, and the controller must neither lose a candidate nor score it twice. Two properties from this lab carry over unchanged. Deterministic evaluation is idempotent, so a retried job gives the same answer (the same argument as retries and idempotency for any network call), and the duplicate check by canonical text is the cache that makes retries cheap. And the controller waits on the slowest evaluation in a synchronous generation, which is the tail-latency problem; fuel bounds that tail by construction, which a wall-clock timeout also does but with run-to-run variation. The whitelist is the cheap layer of the defence, and the container of sandboxes and permissions is the layer you cannot skip when the code comes from somewhere you do not control.

What you learned

  • Untrusted code is run safely by refusing what is not on a whitelist of syntax-tree nodes, and bounded by a step budget inserted into the tree. Steps, unlike seconds, are deterministic, and converting integers to floats stops a loop from growing a number without bound.
  • The evaluator must be total: five statuses (rejected, error, timeout, bad_value, ok) cover everything a candidate can do, and a value must be checked on every call, since a boolean, None, infinity and nan all slip through naive comparisons.
  • Editing the syntax tree rather than the text makes children valid by construction (300 of 300, against 6 of 300 for character flips), but valid is not the same as running: the evaluator is still the net.
  • FunSearch's database keeps diversity at two levels: clusters of programs with the same signature (sampled by a softmax over fitness, then by brevity), and islands that evolve independently with the weakest half periodically replaced by copies of a survivor's best.
  • Budget in model calls, deduplicate by canonical text, and count evaluations separately from calls.
  • Report on instances the search never saw. Here a 500-call search saved about 1.1 to 1.2 bins held-out against 1.5 to 1.7 on the training set, a search on two instances showed a 2.0 saving that shrank to 1.33, and a hand-written rule that used the structure of the problem beat every search on the held-out set.

Check your understanding

Why does the sandbox count steps with inserted _tick() calls instead of killing candidates after two seconds?

  1. Seconds cannot be measured inside Python, only steps can
  2. A step counter is faster than a clock for programs that terminate
  3. A wall-clock limit gives different results on different machines, so the run could not be reproduced
  4. Step counting also stops candidates from importing modules
The same candidate can finish in 1.9 seconds on one machine and time out on another, which makes an evolutionary run impossible to replay or debug. A step budget is a property of the program. Seconds can be measured (the first option is false); the speed difference (second option) is real but minor; and imports are stopped by the whitelist, not by fuel.

A candidate returns item < rem on every call. What should evaluate report, and why does it matter?

  1. ok: every bin gets the priority 1 or 0, which is a valid number
  2. bad_value: a boolean is not a priority, and accepting it would turn the candidate into first fit and score it as if it meant something
  3. error: comparing a float with a boolean raises TypeError
  4. rejected: comparisons are not on the whitelist
In Python True and False compare as 1 and 0, so nothing would raise, and with every feasible bin returning True the packing degenerates to first fit with a perfectly plausible score. That is the wrong-type hole of chapter 9. Comparisons are on the whitelist (the seed's own rule uses them), so the program is not rejected, and no error is raised.

Two programs have different source text but identical bin counts on all ten training instances. What does the database do with them?

  1. Keeps only the one that was found first and deletes the other
  2. Puts them on different islands so that they cannot influence each other
  3. Rejects the second as a duplicate and does not evaluate it
  4. Puts them in the same cluster, where the shorter one is preferred when parents are drawn
A cluster is the set of programs with the same signature; both stay (up to four), and the length softmax inside the cluster favours the shorter. The first option discards a possible stepping stone; the third confuses behavioural equality (same signature) with textual equality, which is what the duplicate check uses and which happens before evaluation; islands are assigned by whose turn it is, not by behaviour.

cluster_temp is raised from 0.5 to 100 while fitness is measured in bins (values near -130). What happens to the choice of clusters?

  1. It becomes almost uniform: every cluster is nearly equally likely, whatever its score
  2. It becomes almost greedy: the best cluster is chosen nearly every time
  3. Nothing changes: the temperature only affects the choice inside a cluster
  4. Clusters with fewer programs are chosen more often
The weights are exp(fitness / T). When T is much larger than the differences between fitnesses (a few bins), every exponent is close to zero and every weight close to 1. A small T does the opposite (the second option). Inside a cluster a different temperature, length_temp, is used; cluster size plays no part in the draw.

After Database.reseed on six islands, which statement is true?

  1. The three islands that had the most programs are kept
  2. The best program in the database may be lost if its island is replaced
  3. Three islands each hold one program, a copy of the best of a surviving island, and the survivors are unchanged
  4. All islands are reset to the seed program
The weakest half by best fitness is replaced by fresh islands seeded with a survivor's best, and survivors, which include the island with the global best, are never touched. Island size does not enter the ranking, and a full reset would throw away everything the search has learned.

A search on two training instances saves 2.00 bins on them and 1.33 on thirty held-out instances. Which number do you report as the improvement, and what does the gap tell you?

  1. 2.00, because those are the instances the search was designed for
  2. 1.33, because it is measured on instances the search never selected on; the gap shows the search fitted the two instances
  3. The average of the two, 1.67
  4. Neither: any improvement under two bins is noise
The training saving is inflated by selection: the winner was chosen because it did well on exactly those instances. A held-out number is an unbiased estimate of how the heuristic will do on new instances of the same kind. Averaging the two mixes a biased and an unbiased number. Whether 1.33 is noise is a question for confidence intervals, which chapter 16 turns to.

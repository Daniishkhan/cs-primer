Lab 5: A Mini Meta-Agent Search

Chapter 12 described Meta Agent Search: a model reads an archive of agent designs, proposes a new one, the new design is scored on a search set and stored, and at the end the best design is scored once on data it never saw. Chapter 16 explained why the number that comes out of such a loop is too good. In this lab you build the whole pipeline in miniature. Agents are small configurations, the archive keeps every design including the losers, a stand-in meta agent proposes changes, a gate catches broken proposals, and three disjoint question sets keep search, choice and report apart. Then you measure the damage directly: how far above the truth the best of many designs sits when you believe the set it was chosen on.

Why this lab matters

Part 4 moves up a level: the thing being searched is the program that solves problems, an agent (chapter 12). A search over agent designs produces two things, a design and a number that says how good it is, and the second is the one people repeat. If the loop has a bug in how it stores designs, nobody notices, because the archive still fills. If it has a bug in how it uses its data, nobody notices either, because the score still goes up. The score going up is exactly what a biased loop does best. So this lab is built around the places where such loops fail without any error message: a duplicate that gets stored twice, a tie that is broken differently on every run, a test set that gets looked at before the choice is made, and a winner that is reported with the score it was chosen on.

By the end you will have written the skeleton shared by the ADAS paper, the Darwin Gödel Machine's agent archive (chapter 13) and most prompt and pipeline optimisers (chapter 11): propose, validate, evaluate, archive, repeat, then select and report on separate data. You will also have a measurement that turns the abstract advice of chapter 16 into a number you produced yourself: with 40 search questions, the best of 60 designs looks about five points better than it is.

Deterministic, standard library only, and no language model

No network, no clock, no model. The foundation model inside the agents is a seeded simulation: each call is answered right with a stated probability that falls with the difficulty of the question, and the dice are a hash of the call's arguments, so the same call always gets the same reply. The probabilities are illustrative assumptions (listed in milestone 1), not measurements of any real model. The meta agent is a stand-in too: a seeded function that changes one knob of a good design. A real meta agent would be a language model writing code; where that model would go is marked in milestone 3. Everything else, the archive, the loop and the splits, is the real thing. Python 3.9 or newer; nothing to install. The check prints enough to replay a failure (python3 check.py solution 6 3 runs milestone 6 on seed 3 only) and finishes in about seven seconds for the reference solution.

What you'll build

Six milestones:

  1. A design becomes an agent: a vote over several attempts, a verify-and-retry loop, and an evaluator that returns accuracy and cost.
  2. A gate and an archive: turn a proposal into a valid design or say exactly what is wrong; store every design with its score, parent and iteration, and rank them.
  3. The stand-in meta agent: pick a good parent, change one knob, never propose something already tried.
  4. The search loop: propose, repair, evaluate on the search questions, archive; count what was rejected.
  5. Three sets, three jobs: a reproducible split into search, selection and sealed test sets; a winner chosen on the selection set; a report that opens the test set once.
  6. The best of many overstates itself: measure the gap between what the search set says about the winner and what it is really worth, as the number of designs and the size of the set change.

Milestone 1: a design becomes an agent

An agent design here is four settings, written as a frozen Design:

KnobValuesWhat it changes
solver"direct", "steps"One model call for the whole expression, or one call per operation (the step-by-step idea of chain-of-thought).
prompt"plain", "careful", "terse"A wording choice that moves each call's accuracy a little: +3 points for careful, −4 for terse.
samples1, 3, 5, 7How many independent answers to take and vote over (self-consistency, chapter 8).
retries0, 1, 2, 3How many rounds of verify and retry follow the vote: a critic looks at the answer and, if it objects, a fresh attempt replaces it.

That is 2 × 3 × 4 × 4 = 96 designs, small enough to enumerate and large enough that nobody wants to. The same four ideas, role prompts, step-by-step reasoning, voting and checking, are the building blocks of the hand-designed baselines in the ADAS paper (chapter 12); the real search space there is code, which is much larger.

The simulated model

Everything the agents do is a call to a Model, and every call is counted, because calls are the cost. The simulation has a handful of assumptions, all illustrative:

  • A direct answer is right with probability 0.85, 0.66, 0.50, 0.38 or 0.28 for questions with 1, 2, 3, 4 or 5 operations. A single step (one operation on two numbers) is right with probability 0.84, so a five-step chain is right about 42% of the time.
  • When a call is wrong, 55% of the time it makes the question's habitual slip: the same wrong value on every attempt, because the slip depends on the question and not on the attempt. The other 45% of wrong answers are random, off by 1 to 4 either way. This matters. If every mistake were independent, voting over seven samples would fix almost everything; real models repeat their mistakes, and a vote cannot repair a mistake that most voters share.
  • The critic (verify) flags 60% of wrong answers and 12% of right ones.
  • The same call always gets the same reply, like a model at temperature zero behind a cache. The call is identified by its attempt number, so independent samples must use different attempt numbers: attempts 0, 1, 2 for the samples, and 100 + r for the retry in round r. Forget this and a vote over five samples is five copies of one answer.

The questions are multi-step arithmetic read strictly left to right (“3 + 4 * 2” is 14), as in chapter 12's example, with difficulty cycling through 1 to 5 operations.

The call sequence is part of the contract, because it is how cost is counted and how the check tells your agent from a look-alike. For a design with n samples and R retries: take n answers with solve_once (attempts 0 to n − 1), vote, then for each round r from 0 to R − 1 call model.verify(question, v, r); stop if it returns True, otherwise replace v by solve_once(model, design, question, 100 + r). After the last round the value is returned without a further check. The vote uses majority, and a tie goes to the answer that appeared first, so that the result does not depend on the size of the numbers. A rule such as “smallest wins” is arbitrary with respect to correctness, and the end of this lab shows what it costs.

def majority(answers: List[int]) -> int:
    """The most common answer. A tie goes to the answer that appeared FIRST in the list."""
    counts: Dict[int, int] = {}
    for a in answers:
        counts[a] = counts.get(a, 0) + 1
    best = max(counts.values())
    return next(a for a in answers if counts[a] == best)

def build_agent(design: Design) -> Callable[[str, Model], int]:
    """Return forward(expr, model) -> int, the agent the design describes:

        1. take design.samples answers with solve_once, attempts 0, 1, 2, ...
        2. v = their majority
        3. for r in range(design.retries): if model.verify(expr, v, r) is True stop;
           otherwise v = solve_once(model, design, expr, 100 + r)   (a fresh attempt)
        4. return v
    """
    def forward(expr: str, model: Model) -> int:
        v = majority([solve_once(model, design, expr, i) for i in range(design.samples)])
        for r in range(design.retries):
            if model.verify(expr, v, r):
                break
            v = solve_once(model, design, expr, 100 + r)
        return v
    return forward

def evaluate(design: Design, questions, model: Optional[Model] = None) -> Score:
    """Build the agent and run it on every question with ONE model (the one passed in, or a fresh Model()).
    A question is right when the agent's answer equals the true answer. Return Score(accuracy, calls), where
    calls is the number of model calls per question, verifications included."""
    model = model or Model()
    forward = build_agent(design)
    right = sum(forward(q, model) == a for q, a in questions)
    return Score(right / len(questions), model.calls / len(questions))

Milestone 2: a gate and an archive

A meta agent proposes designs; it does not hand them over finished. In the ADAS paper the proposal is Python code, it can fail to run, and when it does the meta agent is shown the error and tries again, up to five times (chapter 12). The stand-in here proposes a plain dictionary of knob values, and with_typos (given) corrupts one proposal in four the way a model's output sometimes is: "step" for "steps", "carefull", a sample count of 4, a retry count of −1. Something has to stand between the proposal and the evaluator. That is validate: it turns a dictionary into a Design or raises a ValueError whose message names the offending knob, because in a real loop that message goes straight back to the proposer as the thing to fix.

One trap deserves a sentence. In Python True == 1 and True in [1, 3, 5, 7] is true, so a validator that only checks membership accepts samples=True. The check tries it. The same habit, testing a value’s type before trusting its equality, comes back in lab 6.

The archive is the memory of the search. It stores an Entry for every design that was scored: the design, its accuracy on the search questions, its cost, the name of the parent it came from and the iteration that produced it. It never removes anything. A design that scored worse than its parent stays, because it may carry an idea a later design combines with another (the stepping stones of chapters 4 and 12). Two methods carry the rules:

  • add(entry) stores an entry and refuses a design that is already stored (raise ValueError): a second copy means the caller forgot to look first, and silently accepting it would double-count that design in every ranking.
  • top(k) returns the k best entries by score, highest first. Ties are common (with 40 questions, scores move in steps of 2.5 points), so the rule for ties has to be fixed: fewer calls first, then the design's name. Without a total order the ranking changes with the order of insertion, and two runs of the same search disagree about who the top three were.

def validate(raw: dict) -> Design:
    """Turn a proposal (a dict of knob values) into a Design, or raise ValueError saying what is wrong.
    Exactly the four knobs, each with a value from SPACE (True is not a number of samples, although
    True == 1). The message should name the offending knob: the meta agent reads it to repair its proposal."""
    if not isinstance(raw, dict):
        raise ValueError(f"a proposal is a dict of knobs, got {type(raw).__name__}")
    missing = [k for k in KNOBS if k not in raw]
    extra = [k for k in raw if k not in KNOBS]
    if missing or extra:
        raise ValueError(f"knobs must be exactly {KNOBS}; missing {missing}, unexpected {extra}")
    for k in KNOBS:
        v = raw[k]
        if isinstance(v, bool) or v not in SPACE[k]:
            raise ValueError(f"{k}={v!r} is not one of {SPACE[k]}")
    return Design(**{k: raw[k] for k in KNOBS})

class Archive:
    """Every design ever scored, kept even when it was worse than its parent."""

    def __init__(self):
        self.entries: List[Entry] = []
        self._names = set()

    def __len__(self):
        return len(self.entries)

    def __contains__(self, design: Design) -> bool:
        return design.name in self._names

    def add(self, entry: Entry) -> None:
        """Append the entry to self.entries and record its design's name in self._names (that is what `in`
        reads). Adding a design that is already stored is a bug in the caller: raise ValueError."""
        if entry.design in self:
            raise ValueError(f"{entry.design.name} is already in the archive")
        self.entries.append(entry)
        self._names.add(entry.design.name)

    def top(self, k: int) -> List[Entry]:
        """The k best entries by search score; ties go to fewer calls, then to the name. Does not modify the archive."""
        return sorted(self.entries, key=lambda e: (-e.score, e.calls, e.design.name))[:k]

Milestone 3: the stand-in meta agent

A real meta agent is a language model prompted with the task, the framework and the whole archive, and asked for something interestingly new (chapter 12). It reads the archive, so it can see which ideas paid off, and it writes the next design. The stand-in has to do the same job with no model: look at the archive, choose where to go next, and avoid going somewhere it has already been. Three decisions make it a search and not a shuffle.

  • Where to start from. The parent is drawn uniformly from the archive’s top three. Always taking the best would be greedy hill climbing; drawing from the whole archive would waste most of the budget on poor designs. Three is a middle path between the two, and the same dial MAP-Elites turns in lab 2 when it chooses parents from filled cells.
  • How far to go. Exactly one knob changes, to a different value. A one-knob step is the stand-in for a model’s small edit to a design it has just read; it keeps the child close enough to its parent that the score tells you something about the change.
  • Never repeat. A child that is already in the archive is thrown away and another is drawn. This is the stand-in for the “is it interestingly new?” reflection step of the paper; the stand-in’s test is an exact match on the four knobs.

There is one more case. After a few dozen iterations every neighbour of the best designs has been tried, and a proposer that insists on the top three would loop forever. So the first 100 draws use the top three as parents, and later draws use any entry in the archive; after 400 failed draws the space is exhausted and propose raises. The return value is the child’s knobs as a plain dictionary (not yet validated, because in the real thing a model produced it) and the name of the parent, so that the loop can record the lineage.

def propose(archive: Archive, rng: random.Random) -> Tuple[dict, str]:
    """Pick a parent and change exactly one knob of it to a DIFFERENT value from SPACE.

    Draw up to 400 times. On draws 0 to 99 the parent is rng.choice(archive.top(3)).design; on later draws
    (the best designs' neighbours are used up) it is rng.choice(archive.entries).design. Then the knob is
    rng.choice(KNOBS) and the new value rng.choice of the other values in SPACE[knob], in the order of SPACE.
    The first child that is not in the archive wins: return (its knobs as a dict, the parent's name).
    If all 400 draws fail, raise RuntimeError.
    """
    for draw in range(400):
        pool = [e for e in archive.top(3)] if draw < 100 else archive.entries
        parent = rng.choice(pool).design
        knob = rng.choice(KNOBS)
        value = rng.choice([v for v in SPACE[knob] if v != getattr(parent, knob)])
        child = dict(parent.as_dict(), **{knob: value})
        if Design(**child) not in archive:
            return child, parent.name
    raise RuntimeError("no new design near any archived one: the space is exhausted")

Milestone 4: the search loop

Now the pieces become a loop. This is Meta Agent Search with the language model removed:

  1. Evaluate the seed designs (a single direct answer and a vote of three, the hand-written baselines) on the search questions and store them with iteration 0 and no parent.
  2. For each iteration, ask the proposer for a design. If validate rejects it, that is a repair: count it and ask again. If it is valid but already archived, that is a duplicate: count it and ask again. After MAX_REPAIRS + 1 asks with nothing accepted, give up on the iteration and count it as skipped.
  3. Evaluate the first accepted design on the search questions and store it with its parent’s name and the iteration number.

Two details are easy to get wrong and easy to see in the counts. A typo is not a new design, so it must not touch the archive or the evaluator; and the loop must use only the search questions. Nothing else, no selection set and no test set, is visible to it. In the original paper the equivalent of repairs is the meta agent reading a traceback and fixing its code; counting them tells you how often your proposer wastes an iteration, and when a proposer is a paid model, how much money.

def meta_search(proposer, search_questions, iterations: int, seed: int, seeds=SEEDS) -> SearchResult:
    """Meta Agent Search in miniature.

    1. archive = the seed designs, each evaluated on the SEARCH questions (iteration 0, parent None).
    2. For iteration 1..iterations: ask `proposer(archive, rng)` for (raw, parent_name), up to MAX_REPAIRS + 1
       times. A raw that validate() rejects counts as a repair and is asked again; a valid design already in the
       archive counts as a duplicate and is asked again. The first valid new design is evaluated on the search
       questions and added with its parent and the iteration number. If every ask fails, the iteration is skipped.
    Use rng = random.Random(seed). Nothing but the search questions is touched.
    """
    rng = random.Random(seed)
    archive, repairs, duplicates, skipped = Archive(), 0, 0, 0
    for d in seeds:
        s = evaluate(d, search_questions)
        archive.add(Entry(d, s.accuracy, s.calls, None, 0))
    for it in range(1, iterations + 1):
        for _ in range(MAX_REPAIRS + 1):
            raw, parent = proposer(archive, rng)
            try:
                design = validate(raw)
            except ValueError:
                repairs += 1
                continue
            if design in archive:
                duplicates += 1
                continue
            s = evaluate(design, search_questions)
            archive.add(Entry(design, s.accuracy, s.calls, parent, it))
            break
        else:
            skipped += 1
    return SearchResult(archive, repairs, duplicates, skipped)

Milestone 5: three sets, three jobs

Chapter 16 gave the rule that this whole milestone is an implementation of: data that influenced a decision cannot be used to evaluate that decision. The search used the search questions to decide which designs to keep and which to extend, so its scores on them are biased for every survivor. A second set, the selection set, is used once to choose the winner among the finalists; scores on it are biased only for the finalists and only by the choosing. A third, the test set, touches no decision at all and is scored once, at the end, to report. This is the training, validation and test split of What Learning Is, with the difference that here the “training” loop picks among hundreds of candidates, and an automated loop can ask the same questions every few seconds.

Three small functions carry the discipline:

  • three_way_split(pool, sizes, seed) shuffles a copy of the pool with a seeded generator and cuts three disjoint pieces. The shuffle matters: the pool cycles through difficulty levels, and cutting it unshuffled gives each set a different mix. The test set comes back wrapped in a SealedSet (given), whose open() works once and raises on the second call. That one line of code makes the ledger of chapter 16, “touched once”, something the program enforces and not something the team promises.
  • choose_winner(archive, selection_questions, shortlist=5) takes the five best entries by search score and re-scores only those on the selection questions. The winner is the one with the best selection score (ties: fewer calls, then name). Why a shortlist and not all 40 designs? Because every design scored on the selection set is another chance for luck to win there, the same winner’s curse one level down; five finalists bias it far less than forty.
  • final_report(winner, selection_score, sealed_test) opens the sealed set, scores the winner on it, and returns the whole story: the search score, the selection score, the test score, the calls per question, and the inflation, the search score minus the test score.

def three_way_split(pool, sizes: Tuple[int, int, int], seed: int):
    """Shuffle a copy of the pool with random.Random(seed) and cut the first sizes[0] items as the SEARCH set,
    the next sizes[1] as the SELECTION set and the next sizes[2] as the TEST set, wrapped in a SealedSet.
    Return (search, selection, sealed_test). The three sets share no question. The pool is not modified."""
    a, b, c = sizes
    if a + b + c > len(pool):
        raise ValueError(f"the sets need {a + b + c} questions but the pool has {len(pool)}")
    items = list(pool)
    random.Random(seed).shuffle(items)
    return items[:a], items[a:a + b], SealedSet(items[a + b:a + b + c])

def choose_winner(archive: Archive, selection_questions, shortlist: int = 5) -> Tuple[Entry, float]:
    """Take the `shortlist` best entries by SEARCH score, re-score each on the selection questions, and return
    (the entry with the highest selection accuracy, that accuracy). Ties go to fewer calls, then to the name."""
    scored = [(e, evaluate(e.design, selection_questions).accuracy) for e in archive.top(shortlist)]
    best = min(scored, key=lambda p: (-p[1], p[0].calls, p[0].design.name))
    return best

def final_report(winner: Entry, selection_score: float, sealed_test: SealedSet) -> dict:
    """Open the sealed test set ONCE, score the winner on it, and return a dict with the keys
    'design' (its name), 'search', 'selection', 'test' (accuracies), 'calls' (per question on the test set)
    and 'inflation' (search minus test)."""
    s = evaluate(winner.design, sealed_test.open())
    return {"design": winner.design.name, "search": winner.score, "selection": selection_score,
            "test": s.accuracy, "calls": s.calls, "inflation": winner.score - s.accuracy}

Common misconception

“I kept a test set, so my result is clean.” The test set protects the final number only if nothing was decided with it. The usual leak is not a bug in the code but a habit: look at the test score of the winner, dislike it, add some iterations and run again. Now the test set has influenced a decision, and every score from it is slightly optimistic. The sealed set in this lab makes that second look impossible; in a real project the same effect needs a process (a fresh test set per release, or a counter of how often it has been opened) because nothing in a spreadsheet raises an exception.

Milestone 6: the best of many overstates itself

So far the lab has told you that the search score is biased. This milestone measures how much, and what it depends on. The experiment is the one from chapter 12 and chapter 16, run on your own pipeline. In each of many trials:

  1. Draw q fresh questions: the search set for this trial.
  2. Draw N distinct designs at random from the 96 and score all of them on those questions.
  3. Keep the one with the highest score (ties: the first drawn) and write down two numbers: the score it was chosen on, and its accuracy on the 600 truth questions (true_accuracy, given).

Average over trials. The difference is the inflation: how many points of the winner’s search score are luck. Statistics predicts the shape. A design that is right with probability p scores with a standard deviation of √(p(1 − p)/q) on q questions, which is 7.7 points for p = 0.6 and q = 40. The best of N similar designs sits roughly √(2 ln N) standard deviations above the typical one (the derivation is in chapter 16): the bias grows slowly, with the logarithm of the number of designs, and falls only as the search set grows.

Two further quantities go in the result. best_available is the mean of the highest true accuracy among the N designs drawn: the best that selection could possibly have found. If the winner’s search score is above even that, the number being reported is better than any design that existed.

def inflation(n_designs: int, n_questions: int, trials: int, seed: int) -> dict:
    """In each of `trials` repetitions (rng = random.Random(seed) throughout): draw n_questions fresh questions
    with make_questions(n_questions, rng.randrange(10**6)), draw n_designs distinct designs with rng.sample
    from ALL_DESIGNS, score all on those questions, keep the one with the highest score (ties: the first drawn),
    and look up its true_accuracy. Return the means over trials:
        {'looks': mean search score of the pick, 'is': mean true accuracy of the pick,
         'inflation': looks - is, 'best_available': mean of the best true accuracy among the drawn designs}
    """
    rng = random.Random(seed)
    looks, real, best = [], [], []
    for _ in range(trials):
        qs = make_questions(n_questions, rng.randrange(10 ** 6))
        ds = rng.sample(ALL_DESIGNS, n_designs)
        scores = [evaluate(d, qs).accuracy for d in ds]
        i = max(range(n_designs), key=lambda j: scores[j])
        looks.append(scores[i])
        real.append(true_accuracy(ds[i]))
        best.append(max(true_accuracy(d) for d in ds))
    m = lambda xs: sum(xs) / len(xs)
    return {"looks": m(looks), "is": m(real), "inflation": m(looks) - m(real), "best_available": m(best)}

Systems connection

The three-set protocol is a release process. A team that tunes a prompt, a retrieval setting and a cache size against one evaluation set and reports that set’s best score has run this lab’s search without the selection and test sets (cross-validation done right is the same argument for models, and leakage is what happens when the sets are not really separate). Recording the search set, the number of candidates tried and the chosen configuration is the minimum a result needs to be reproducible, and Statistics for Evals gives the error bars that tell you whether two designs 1.5 points apart are different at all. The archive itself is an experiment tracker with an admission rule: a store that keeps every run, never overwrites one, and orders them deterministically. And in a real meta-agent search every candidate is code that will be executed, which is why sandboxing belongs next to the evaluation set in the design.

What you learned

  • A meta-agent search is five small pieces: a store that keeps everything, a gate that rejects broken proposals, a proposer that reads the store, an evaluator that returns accuracy and cost, and a loop that counts what it rejected. Each is easy to get subtly wrong and has a cheap invariant that catches it (no duplicates, a total order, one knob per step, only the search questions used).
  • Votes only repair mistakes that are not shared. When most wrong answers repeat the question’s habitual slip, adding samples stops helping and the verifier and the step-by-step solver do the work.
  • The archive keeps worse designs. In the seed-3 run a child at 0.775 stayed in the archive beside its parent at 0.950, and the winner’s lineage was built from several scores that did not look like progress at the time.
  • The best of N noisy scores is biased upwards by an amount that grows with log N and falls with the size of the set. On 40 questions the best of 60 designs overstated itself by 4.8 points and beat the best design on offer; on 400 questions the overstatement was 1.5.
  • Three sets for three jobs: search to guide, selection to choose among a shortlist, a sealed test to report once. In 30 runs the search score overstated the winner by 3.6 points, the selection score by 1.8, and the test score by an amount within sampling noise.
  • A rule that is enforced by code (a set that opens once) is worth more than one that is agreed in a meeting.

Check your understanding

In the simulated model, the same call (same kind, question, attempt number and prompt) always returns the same reply. What follows for an agent that takes five samples?

  1. It should use the same attempt number for each sample to save calls
  2. It is fine to take the samples in any order, because the replies are the same anyway
  3. Each sample needs its own attempt number, or the vote is five copies of one answer
  4. Samples are unnecessary because the replies are always right
A call is identified by its arguments, and the attempt number is the only thing that differs between samples. With the same number the five replies are identical and the vote has no information in it (the check for milestone 1 tests for exactly this). Taking samples in a different order does not matter, but that is not the point; and the replies are not always right, they are only repeatable.

Why does top(k) break ties by calls and then by name, rather than leaving them to the sort order of insertion?

  1. So the ranking is a total order that does not depend on the order in which designs were added, and two runs of the same search agree about the top three
  2. Because cheaper designs are always more accurate
  3. Because Python's sort is not stable
  4. Because names are unique, so two designs can never tie
With 40 search questions many designs tie on score. A ranking that depends on insertion order lets two runs of the same search disagree, and makes the proposer's choice of parents irreproducible. Cost is a sensible first tie-break and name a final one. Cheaper designs are not always more accurate, Python's sort is stable (which is why insertion order would silently decide), and names being unique is why name works as the last key, not why ties are impossible.

A proposer returns {'solver': 'steps', 'prompt': 'plain', 'samples': True, 'retries': 1}. A validator that checks v in SPACE[knob] and nothing more accepts it. Why?

  1. Because True is a string in Python
  2. Because samples may be any value in a dictionary
  3. Because dictionaries are not validated in Python
  4. Because True == 1 and 1 is in the list of allowed sample counts
In Python a bool is an int, so True in [1, 3, 5, 7] is true. The validator must reject bools explicitly. Testing the type before trusting equality is the same habit that lab 6's strict output check needs.

A search over 60 designs picks the one with the highest score on 40 search questions. A second search over 5 designs uses the same 40 questions. Which statement is correct?

  1. Both winners are equally biased, because the questions are the same
  2. The first winner's search score is likely to be inflated by more, because the best of more noisy scores is biased by an amount that grows with the number of candidates
  3. The second winner is biased more, because it had fewer candidates to choose from
  4. Neither is biased, because the questions are fixed
The expected maximum of N noisy scores rises with N (roughly with the square root of 2 ln N standard deviations), so the same questions inflate the winner of 60 more than the winner of 5: in the lab's experiment 4.8 points against 3.1. The fixed questions do not remove the bias; they are the thing the bias is about.

The final report shows search 0.975, selection 0.910 and test 0.940 for the winner. What is the right reading?

  1. All three estimate the same underlying accuracy with different noise; only the test score is unbiased, and the search score is the one most likely to be too high
  2. The selection set is broken, because its score is lowest
  3. The test set is more reliable because it is larger, so the other two should be ignored entirely
  4. The winner is worth 0.975, because the search is the largest piece of evidence
Each set gives a noisy estimate. The search score was selected to be high, the selection score was used once to choose among five, and the test score influenced nothing. A lower selection score is not a sign of a bug (100 questions have a standard error of about 2.5 points). Size matters, but the reason to prefer the test score is that no decision touched it, and the other two still carry information; they are simply biased upwards.

You want the winner of a search to report a score within one point of its true accuracy, and you cannot reduce the number of designs the search tries. Which change helps most?

  1. A smarter proposer
  2. More iterations of the same search
  3. A larger set to score the winner on, one that no decision touched
  4. Removing the worst designs from the archive
The bias comes from choosing among noisy scores and cannot be removed by changing the proposer or by tidying the archive; more iterations try more candidates and add to it. The remedy that works is a bigger set that was not used to choose, because the noise of a score falls with the number of questions. In the lab the sealed test of 400 questions had a standard error near 1.2 points and no bias.

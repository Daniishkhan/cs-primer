Voyager in Minecraft

In 2023 a team from NVIDIA, Caltech and several universities let GPT-4 play Minecraft with no human in the loop and no training of the model. The agent proposed its own next task, wrote JavaScript to do it, checked its own work, and kept every working program in a library for later. The paper, "Voyager: An Open-Ended Embodied Agent with Large Language Models" (Wang et al., 2023), is the clearest early example of a skill library: memory that is made of code instead of text. This case reads its numbers closely, including the places where the comparison is looser than the headline suggests.

What I could and could not read

I fetched and read the full Voyager paper (arXiv 2305.16291, version 2 of 19 October 2023), including the method, Table 1, Table 2, the ablation findings, the limitations section and the broader-impacts statement. I did not read the appendix prompts line by line, I did not run Voyager (it needs Minecraft, a Node.js controller and paid GPT-4 access), and I did not check the project's code repository. Every number attributed to "the paper" below is from that text. The two scripts in the "Try it yourself" section are my own: one re-computes the paper's speed-up ratios from its table, the other is a toy simulation of why the verifier matters, and it is not a reproduction of the paper's experiments.

The pattern in one sentence

Let the agent keep what it learns as small, tested, reusable programs, indexed by a description of what each one does, so that every new task starts from a growing library of verified skills instead of from nothing.

Context: why a game, and why a lifelong agent

Most agent benchmarks end. A task is posed, the agent succeeds or fails, and the next episode starts fresh. Minecraft, the authors argue, is different: the game "does not impose a predefined end goal or a fixed storyline". The player explores a procedurally generated 3D world, gathers resources and climbs a tech tree (a dependency chain of tools: wooden tools unlock stone, stone unlocks iron, iron unlocks diamond). A good player learns basics first, such as mining wood and cooking food, and only then fights monsters or crafts diamond tools.

The paper asks whether an LLM-powered agent (a program that uses a large language model to decide what to do next, as in the tool loop of the agents course) can behave like that player. The authors name three things a lifelong learning agent needs: it should propose suitable tasks for its current skill level and situation, it should refine skills from feedback and commit mastered skills to memory, and it should keep exploring on its own. Voyager is built to supply each one.

Two design decisions frame everything else. First, Voyager "interacts with GPT-4 via blackbox queries": there is no fine-tuning, and no gradient updates, so all learning lives outside the model weights, in prompts and in stored programs. Second, the action space is code. Instead of sending low-level motor commands, the model writes JavaScript functions against the Mineflayer API (a library that controls a Minecraft bot), because, in the authors' words, programs "can naturally represent temporally extended and compositional actions". The simulation layer is MineDojo (Fan et al., 2022), an open-source Minecraft framework for agent research.

Automatic curriculum
A mechanism that proposes the next task, here by prompting GPT-4 with the agent's state and history so each task is hard enough to teach something but not so hard that it cannot be done.
Skill library
A store of verified programs. Each skill is executable code, indexed by an embedding of a text description, so it can be retrieved by meaning later.
Iterative prompting
Generate code, run it, feed the results and errors back to the model, and repeat until the task passes or the attempts run out.
Self-verification
A second GPT-4 call that acts as a critic: given the task and the agent's state, it says whether the task succeeded and, if not, how to fix it.
Prompting iteration
The paper's unit of effort: one round of asking the model for code. Efficiency results are counted in these, not in game time or dollars.
Zero-shot generalisation
Solving tasks never seen before, here in a freshly generated world, with an empty inventory but the learned skill library available.

The mechanism: three parts around one frozen model

The curriculum

The automatic curriculum prompt gives GPT-4 an overall goal, which the paper quotes as "discover as many diverse things as possible", together with a constraint that the next task should not be too hard. It also receives the agent's state (inventory, equipment, nearby blocks and creatures, biome, time, health, hunger and position), plus lists of tasks already completed and tasks that failed. A cheaper model, GPT-3.5, adds extra context by asking itself questions about the current state and answering them. The paper's examples show the flavour: with a wooden pickaxe and some stone in hand, the curriculum proposes "Craft 1 stone pickaxe"; with hunger at zero and pigs nearby, "Kill 1 pig".

The authors describe this as "an in-context form of novelty search". Novelty search, from the evolutionary computation tradition covered in chapter 3, rewards behaviour that is different from what has been seen. Voyager has no novelty measure or archive of behaviours. The language model's own sense of what a sensible next step is stands in for it, which makes this the "interestingness" idea of chapter 6 in its simplest form: ask a foundation model what to try next.

The skill library

When the verifier confirms that a program completed its task, Voyager stores it. The key is an embedding vector of a description of the program (the description is written by GPT-3.5); the value is the program itself. To retrieve skills for a new task, GPT-3.5 first drafts a general plan for the task, the plan is combined with environment feedback into a query, and the library returns the top five matches. Those five programs go into the code writer's prompt as examples and as callable building blocks.

Two properties make this more than a notes file. Skills are executable, so a stored skill like craftIronPickaxe() can be called, not merely read. And they are compositional: a new skill is written on top of older ones, which is why the paper says skills "compound" the agent's abilities. The prompt asks for exactly this: "Your function will be reused for building more complex functions. Therefore, you should make it generic and reusable." Compare this with the text-and-vector memories of the memory chapter: there, retrieved text informs the model; here, retrieved code does the work.

Iterative prompting and the verifier

One-shot code generation is unreliable, so Voyager loops. The program runs in the game; the agent collects three kinds of signal. Environment feedback is text the control functions print, such as "I cannot make an iron chestplate because I need: 7 more iron ingots". Execution errors come from the JavaScript interpreter: in the paper's example, the model tried to craft an "acacia axe", an item that does not exist, and the error text led it to craft a wooden axe instead. Self-verification is a separate GPT-4 call that receives the task and the agent's state and answers whether the task succeeded, with a reason. If it did not, it also returns a critique, such as "Find and kill one more sheep". The authors chose this over hand-writing a success checker for every task the curriculum might invent, since the curriculum generates tasks without bound. If the agent is still stuck after four rounds, the curriculum is asked for another task, and the failed task goes onto the failed list to be tried again later.

Analogy: a lab notebook that runs

Picture a new apprentice cook who, each time a dish works, writes the recipe on a card, files it by what it makes, and next time pulls the five most relevant cards before starting. A dish like paella calls for "make stock" and "toast rice", so the apprentice follows those cards instead of improvising them. A supervisor tastes each dish before its card is filed.

Where it breaks down: a kitchen supervisor has a palate trained on real food. Voyager's supervisor is the same kind of model that wrote the recipe, looking at a text description of the inventory. If it is fooled, a bad card gets filed, and every later dish that uses it inherits the fault.

What the paper reports

All comparisons use GPT-4 (gpt-4-0314) with GPT-3.5 (gpt-3.5-turbo-0301) and an embedding model (text-embedding-ada-002). Temperature is 0 everywhere except the curriculum, which uses 0.1 "to encourage task diversity". The baselines are ReAct, Reflexion and AutoGPT, none of which were built for Minecraft, so the authors re-interpreted each one to run in MineDojo and gave them the same environment feedback, execution errors and (for Reflexion) the self-verification module. The tech-tree and zero-shot tables each rest on three trials per method.

Exploration and the tech tree

In 160 prompting iterations Voyager discovered 63 unique items, which the paper reports as 3.3 times more than its counterparts, and travelled 2.3 times the distance. For the tech tree, the unit is iterations needed to unlock each tool tier. Generalisation and ablations

For zero-shot generalisation the authors cleared the inventory, generated a new world and set four unseen tasks, with a 50-iteration cap. Table 2 reports the mean iterations to solve each task (successful runs out of three in brackets):

Two readings follow. With the library, Voyager needed between about 22 and 47 percent fewer iterations than the same agent without the library (19 versus 36 for the diamond pickaxe is the largest gap, though the no-library figure comes from only 2 of 3 runs; 21 versus 27 for the lava bucket is the smallest). And giving the library to AutoGPT lets it solve three of the four tasks at least once, which supports the paper's claim that a skill library is "a plug-and-play asset" that other methods can use.

The ablations (Figure 9 of the paper, which reports percentages in the text) show what each part contributes to the count of discovered items. Replacing the automatic curriculum with a random one cuts discovered items by 93 percent. Removing self-verification costs 73 percent and is called "the most important among all the feedback types". Using GPT-3.5 instead of GPT-4 for code generation yields 5.7 times fewer unique items. Without the skill library, progress "tends to plateau in the later stages", while early progress looks similar: note in Table 1 that the no-library variant matched Voyager on the wooden and stone tiers (7 versus 6 iterations, 9 versus 11) and only fell behind at iron (29 versus 21). A library pays off once there is something worth reusing.

Reading the numbers with care

  • Three runs per condition. Every table cell rests on three trials. The diamond result is one success out of three (102 iterations), so "Voyager is the only one to unlock the diamond level" is true of the experiment, but the evidence about how reliably it gets there is thin.
  • The baselines were adapted by the authors. ReAct, Reflexion and AutoGPT were designed for text tasks, and the authors say they made their "best effort" to port them. A baseline written by the team that proposes the method may be weaker than one tuned by its own authors. Giving the baselines the same environment feedback and verifier is a fair step, and the paper says so; it does not remove the issue.
  • High-level control, not pixels. Voyager uses the Mineflayer API to move and craft. The authors explicitly decline to compare with methods that read screen pixels and output low-level controls, saying it "would not be an apple-to-apple comparison". The result is about planning and skill reuse, not perception or motor control.
  • The unit is model calls, not money. Efficiency is counted in prompting iterations. The paper acknowledges that GPT-4 "is 15× more expensive than GPT-3.5" and that the quality of GPT-4's code is essential, since GPT-3.5 and open-source models of the time could not provide it.
  • Failures the authors list. The curriculum sometimes proposes impossible tasks (a copper sword that does not exist in the game), the code writer sometimes uses cobblestone as fuel or calls functions that are not in the API, and the self-verifier sometimes misses success, for example not recognising spider string as proof that the agent beat a spider.
  • Dated models. The model snapshots are from early 2023. A reproduction with current models would give different numbers in both directions, and I have not run one.

Common misconception

"Voyager shows that LLMs learn continually." The model never learns anything: its weights are frozen and the paper says it avoids "explicit gradient-based training or finetuning". What accumulates is a database of programs and a list of finished tasks. That is a real and useful form of lifelong learning, since the library is inspectable, editable and transferable (the paper transfers it to a new world, and to AutoGPT). But it is bounded by what the frozen model can do with the examples in its prompt, and by the quality of whatever filter decides which programs enter the library.

The second script tests an idea behind the ablations rather than reproducing them. It simulates 20 tasks, each of which depends on the two before it. Writing a task from scratch has to cover the task and every prerequisite that is not in the library, and each fresh step works with probability 0.6 (an assumption I chose, as are the dependency structure and the budget of 60 iterations). A verifier decides whether to accept an attempt: a perfect one, a noisy one that wrongly accepts 20 percent of failures and wrongly rejects 10 percent of successes, or one that accepts everything. A stored skill that does not really work makes every later task that calls it fail. Neither the model nor the verifier here is an LLM: both are random stand-ins with fixed rates, and the output is averaged over 500 seeded runs.

"""Toy: a skill library is only as good as the check that decides what goes into it.
My own simulation, not the paper's setup: the 'model' and the 'verifier' are random stand-ins with fixed rates."""
import random

N_TASKS, BUDGET, ROUNDS, P_STEP = 20, 60, 4, 0.6

def run(seed, use_library, fp, fn):
    rng = random.Random(seed)
    truth = {}                                 # task -> does the accepted program really work?
    used, pointer = 0, 0
    while used < BUDGET and len(truth) < N_TASKS:
        t = pointer % N_TASKS; pointer += 1
        if t in truth: continue
        prereqs = [p for p in (t - 1, t - 2) if p >= 0]
        for _ in range(ROUNDS):                # up to 4 rounds of code writing per task, as in the paper
            if used >= BUDGET: break
            used += 1
            in_lib = [p for p in prereqs if use_library and p in truth]
            fresh = 1 + len(prereqs) - len(in_lib)            # steps the model must write from scratch
            poisoned = any(not truth[p] for p in in_lib)      # calling a stored skill that does not work fails
            works = (not poisoned) and rng.random() < P_STEP ** fresh
            if rng.random() < ((1 - fn) if works else fp):    # the verifier's verdict
                truth[t] = works
                break
    return len(truth), sum(truth.values())

def mean(xs): return sum(xs) / len(xs)
print(f"{'condition (60 iterations, 20 tasks)':38s} accepted  really-working  broken-but-stored")
for label, lib_on, fp, fn in [("no library, perfect verifier", False, 0.0, 0.0),
                               ("library, perfect verifier", True, 0.0, 0.0),
                               ("library, verifier fp=0.2 fn=0.1", True, 0.2, 0.1),
                               ("library, no verifier (accept all)", True, 1.0, 0.0)]:
    rs = [run(s, lib_on, fp, fn) for s in range(500)]
    acc, ok = mean([r[0] for r in rs]), mean([r[1] for r in rs])
    print(f"{label:38s} {acc:8.1f} {ok:15.1f} {acc - ok:18.1f}")
condition (60 iterations, 20 tasks)    accepted  really-working  broken-but-stored
no library, perfect verifier               14.1            14.1                0.0
library, perfect verifier                  20.0            20.0                0.0
library, verifier fp=0.2 fn=0.1            17.5             8.4                9.1
library, no verifier (accept all)          20.0             1.6               18.4

The pattern matches the direction of the paper's finding that self-verification is the most important feedback signal, and nothing more than that: my numbers say nothing about Minecraft or about GPT-4. The mechanism it illustrates is general. A library is a cache, and a cache fills with whatever is allowed in. When a wrong entry is called by later code, the error spreads. Change fp in the script to 0.05 and see where the library stops paying for itself, then try raising P_STEP to 0.8 to make fresh code easier to write and watch the advantage of a library shrink.

Copy verifier_toy.py and change one thing at a time. (1) Set fp to 0.05, 0.1 and 0.2 and plot broken-but-stored against it. (2) Make skills depend on only one earlier task instead of two. Does the damage from a bad skill grow or shrink? (3) Add a "re-test on reuse" rule: when a stored skill is called and the caller fails, mark that skill broken and remove it. What came after, and what the authors flagged

Voyager's two halves have different descendants. The skill-library half became a general idea for agent memory: store reusable procedures, not only facts, and retrieve by description. Chapter 7 builds a small version of it, and the idea shows up whenever a coding agent saves a helper script or a reusable instruction file for later sessions (the agents course on memory treats skills as one memory type).

The curriculum half is the weaker part, and the authors' own limitations section says so: the model proposes impossible tasks, and nothing guarantees that its sense of "diverse" matches what is learnable. The chapter on models of interestingness describes OMNI and OMNI-EPIC (Faldor et al., 2024), which keep an explicit archive of tasks and add a novelty check, aiming at the same job more carefully. The paper itself points in this direction: it states that Voyager's curriculum is generated bottom-up and "driven by curiosity", and contrasts itself with an earlier curriculum whose objectives were limited to curated items.

The paper also shows the limits of full autonomy. In its multimodal section, Voyager builds 3D structures such as a Nether portal and a house only when a human acts as the critic (giving visual feedback it cannot perceive itself) or as the curriculum (breaking the building task into steps). That is a useful reminder that the verifier and the curriculum are the human-shaped parts of the loop, and the places where an automated replacement has to be good.

Systems connection

A skill library is a build cache with an admission policy. Code that has passed its checks is stored under a content description, retrieved by lookup, and composed into larger units, just as compiled artefacts are in a build system. The failure mode is cache poisoning: an entry that passed a weak check is trusted by everything built on it. The security and reliability tools apply directly. Run generated code in a sandbox with a time limit (injection and untrusted input), treat its output as untrusted until verified, and keep the provenance of each stored skill so a bad one can be traced and removed (deployment strategies describe the canary logic that suggests testing a new skill on a few tasks before it joins the library). The paper itself notes that applying such an agent to physical robots "would require additional attention and the implementation of safety constraints by humans". For how to evaluate agents that run for many steps, see evaluating agents.

State of play, October 2026

The Voyager results use 2023 model snapshots and a Minecraft setup that has not been re-run by me. I have not verified how later systems compare on the same tests, so treat the figures as a record of what this design achieved at the time, not as a current benchmark. The durable ideas are the architecture (curriculum, library, verifier) and the ablation lesson that the filter in front of the library matters most; the specific percentages will not carry over to other models or environments.

Lessons

  1. Memory can be code. Executable skills compose, and a retrieved skill can be run, tested and replaced. That is more than a retrieved paragraph can do (chapter 7).
  2. The gate decides the library's quality. Self-verification was the most important feedback signal in the ablation, and my toy shows how a leaky gate fills the library with broken entries. Ground-truth checks beat model-judged ones wherever the world offers them (chapter 15).
  3. A curriculum is a search policy. Without it the discovered-item count fell by 93 percent. The same question reappears in open-ended algorithms: how do you generate tasks that are neither trivial nor impossible?
  4. Count effort in the right unit, and read small samples with suspicion. Prompting iterations are not dollars, and three runs are not a distribution (chapter 16).

Key takeaways

  • Voyager combines a GPT-4 curriculum, a library of verified JavaScript skills retrieved by embedding, and an iterate-with-feedback loop, with no model fine-tuning.
  • The paper reports 63 unique items in 160 iterations (3.3 times the best baseline), 2.3 times the distance travelled, and tech-tree unlocks 15.3, 8.5 and 6.4 times faster for wooden, stone and iron tiers (Table 1).
  • Ablations show the curriculum and the self-verifier matter most (93 and 73 percent drops in discovered items), and the library matters most in later stages and for transfer to new worlds.
  • Evidence is three runs per condition against baselines that the authors adapted, using a high-level API, with 2023 model snapshots.
  • A skill library is only as reliable as the check that admits skills to it.

Check your understanding

Voyager's skill library stores each skill under an embedding of what?

  1. The raw JavaScript source code of the program
  2. A text description of what the program does, written by a language model
  3. The Minecraft world coordinates where the skill was learned
  4. The error messages produced the first time the program ran
The key is the embedding of the program's description (generated by GPT-3.5) and the value is the program. Retrieval embeds a plan for the new task and finds the five closest descriptions. Indexing by raw code would match syntax rather than purpose.

In the paper's ablations, which change cut the number of discovered items by the largest share?

  1. Removing the skill library
  2. Removing self-verification
  3. Replacing GPT-4 with GPT-3.5 for code generation
  4. Replacing the automatic curriculum with a random one
The random curriculum cut discovered items by 93 percent, against 73 percent for removing self-verification. The library has no single percentage in the text, only a plateau in later stages, and GPT-3.5 gave 5.7 times fewer items, which is a smaller relative cut than 93 percent. Self-verification is the most important feedback type, which is a narrower claim than the most important component.

In Table 1, the Voyager variant without a skill library took 7 and 9 iterations for the wooden and stone tiers, against 6 and 11 for full Voyager. What does this show?

  1. The library gives little or no advantage early, when there is little to reuse; its advantage shows at the iron tier (29 versus 21) and in later stages
  2. The library slows the agent down at every stage
  3. The ablation is invalid because both variants succeeded in all runs
  4. The curriculum, not the library, is responsible for all the speed-ups
The differences at the early tiers are within the reported spread (±2 to ±4), so they show no early advantage in either direction, not a slowdown. The gap opens at iron and in the zero-shot tasks, where reuse matters. Both variants share the same curriculum, so the table cannot attribute the iron gap to it.

In the toy simulation, why does a library with no verifier end with so few working skills even though the agent "solves" all 20 tasks?

  1. The model is too weak to write any correct code
  2. Accepted programs are not stored, so there is nothing to reuse
  3. Broken skills are stored as if they worked, and every later task that calls one fails, so errors spread through the dependencies
  4. The budget of 60 iterations is too small for any condition to finish
With no gate every attempt is accepted and stored. A broken prerequisite poisons the tasks that call it, so the stored skills are mostly broken. The perfect-gate condition with the same budget finishes all 20, which rules out the budget as the cause.

AlphaEvolve

FunSearch evolved a single function of a few lines. Its successor, AlphaEvolve, evolves whole source files in any language against one or more automatic evaluators, using a mix of frontier language models. Google DeepMind's 2025 white paper reports results ranging from a new way to multiply 4×4 complex matrices to a scheduling heuristic running across Google's data centres. This case reads the paper for the mechanism, the numbers and what its authors say it cannot do.

What I could and could not read

I fetched and read the full AlphaEvolve white paper, Novikov et al., "AlphaEvolve: A coding agent for scientific and algorithmic discovery" (arXiv:2506.13131, 16 June 2025), including its method, results, ablations and discussion. I read DeepMind's launch post (14 May 2025), the abstract of Georgiev, Gómez-Serrano, Tao and Wagner, "Mathematical exploration and discovery at scale" (arXiv:2511.02864, November 2025), and the abstract and revision history of Dumas, Pernet and Sedoglavic's paper on 48-multiplication rational matrix algorithms. I did not read the appendices' code for the individual mathematical constructions, the Google Colab with the decompositions, the follow-up papers' full text, or any independent re-run: AlphaEvolve itself is not publicly released, so every performance figure below is DeepMind's own report about its own system. One search-tool snippet describes a 2026 follow-up on numerical accuracy that I did not open.

The pattern in one sentence

Wherever you can write a program that scores a candidate automatically, you can let language models propose edits to a whole codebase and use evolution to keep the edits that the scorer likes, so the quality of the evaluator, not the model alone, sets what can be discovered.

Context: from one function to a codebase

The previous case, FunSearch, showed the loop on cap sets: a frozen code model, a strict scorer and a database of programs. Its limits were built into the design. The paper's Table 1 lists the contrast with AlphaEvolve, and it is a useful summary of what changed:

The point that matters most is the first: letting the model edit a whole file means the search can change how a problem is attacked, not only one formula. The cost is that the evaluator becomes the whole interface. See chapter 9 for the family of methods and chapter 10 for open-source relatives.

Evolve block
A region of source code marked with comments (# EVOLVE-BLOCK-START and # EVOLVE-BLOCK-END) that the system may rewrite; the rest of the file stays fixed.
Evaluator
A function the user writes that runs a candidate program and returns a dictionary of scores.
Evaluation cascade
A series of tests of increasing cost, where a candidate reaches an expensive test only if it passed the cheaper ones.
Diff
A description of a change to existing code (what to remove, what to insert), as opposed to a complete rewrite.
Tensor decomposition
A way of writing a three-way table of numbers as a sum of simple pieces; for matrix multiplication, the number of pieces (the rank) is the number of scalar multiplications an algorithm needs.
Kissing number
The largest number of equal non-overlapping spheres that can touch one central sphere of the same size in a given dimension.

How AlphaEvolve works

The paper describes an asynchronous pipeline of a controller, language-model samplers and evaluation nodes, optimised for throughput (how many ideas can be proposed and checked within a budget) rather than for the speed of any one evaluation. In order:

  1. The user supplies a task. That is an evaluation function returning "a dictionary of scalars", an initial program (which "must be complete" but "can be rudimentary", even single-line functions that return constants), evolve-block markers in it, and optional background such as equations, code or papers.
  2. A prompt sampler builds the prompt. It combines previously found programs from the database with their scores and outputs, system instructions, any user context, randomised template parts for diversity, and, optionally, instructions co-evolved by the model itself in a second database, which the paper calls meta prompt evolution.
  3. An ensemble of language models proposes changes. The paper reports using a mix of Gemini 2.0 Flash, which is fast and generates many candidates, and Gemini 2.0 Pro, which is more capable and supplies "occasional, higher-quality suggestions". The models return diffs, or for short programs whole new files, which are applied to make a new program.
  4. Evaluators score it. The paper lists a cascade of increasingly hard test cases, optional LLM-generated feedback for qualities that are hard to code (simplicity, for example), parallel evaluation on a cluster, and multiple scores. It notes that evaluations of around 100 compute-hours per candidate are feasible because the method is sample-efficient, and that optimising several metrics can improve even the single metric of interest, probably because programs good under different criteria give the model more varied examples.
  5. A database keeps the best and the varied. It uses an algorithm "inspired by a combination of the MAP elites algorithm and island-based population models" (chapter 4 covers MAP-Elites), balancing improving the best programs with keeping diverse ones.

One problem, three levels of abstraction

The paper points out a design choice that does not exist in FunSearch: the thing being evolved can be the answer itself as a raw string, a function that constructs the answer (the FunSearch approach), or a bespoke search algorithm that finds the answer within a compute budget. It can even co-evolve intermediate solutions and the search algorithm that improves them. The authors hypothesise that constructor functions suit problems with highly symmetric solutions, because such functions are concise, while problems with non-symmetric solutions work better with tailored search algorithms. This is a hypothesis from the paper, not a tested rule.

What it found

Faster matrix multiplication

Multiplying two 4×4 matrices the school way takes 64 scalar multiplications. Applying Strassen's 1969 algorithm recursively takes 49, which works over any field. The paper reports that AlphaEvolve found an algorithm using 48 scalar multiplications for 4×4 complex-valued matrices, the "first improvement, after 56 years, over Strassen's algorithm in this setting". (A specialised AI approach had found 47 for the very special field with two elements; AlphaEvolve's is for characteristic 0.) The setup: an evolved program implemented a gradient-based tensor-decomposition routine, with an initialiser, a loss function and an optimiser, run over several random seeds; evaluation rounded entries to the nearest integer or half-integer to ensure exactness, and the paper says it asked for near-integral solutions in plain English in the prompt. Across 54 matrix sizes it tried, the paper's Table 3 says AlphaEvolve matched the state of the art in 38 cases, surpassed it in 14 and fell behind in 2, always giving exact algorithms.

Open problems in mathematics

The paper applied the system to over 50 problems asking for constructions better than any previously known. It reports matching the best known on about 75% and surpassing it on about 20%, noting that in many of the matches the known construction is likely already optimal. Two examples it highlights: an improved upper bound on Erdős's minimum overlap problem, and a configuration of 593 spheres touching a central sphere in 11 dimensions, beating the previous record of 592. DeepMind's blog describes the 75% and 20% figures as "to the best of our knowledge". In November 2025 Georgiev, Gómez-Serrano, Tao and Wagner reported a larger study, on 67 problems across analysis, combinatorics, geometry and number theory. By the abstract, AlphaEvolve "rediscovered the best known solutions in most of the cases and discovered improved solutions in several". I read only the abstract.

The paper reports four engineering applications, each with an evaluator that measures a real quantity. All figures below are the paper's, about Google's own systems.

The scheduling case is a good example of an evolved artefact that is easy to trust. The evolved heuristic is a few readable lines of arithmetic on the job's demand relative to the machine's free CPU and memory, shown in the paper's Figure 6, and the paper says it affects only the ranking of machines that Borg has already determined to be available and capable, so scheduling decisions are "effectively correct by construction". The authors say they chose AlphaEvolve over a deep reinforcement learning approach because the code was better in performance and also in "interpretability, debuggability, predictability, and ease of deployment". For the measurement method behind a kernel claim see performance engineering.

Which parts mattered

The paper's ablations (Section 4) were run on two tasks, matrix-multiplication tensor decomposition and kissing-number configurations, with three independent runs per setting. Variants removed one component at a time: evolution (feeding the same initial program to the model repeatedly), context in the prompt, meta-prompt evolution, full-file evolution (evolving only the loss function instead), and the use of large models (one small model only). The authors' summary is that "each of the components is responsible for a significant improvement in the results". I read this statement and the figure's description, not the data behind the curves.

A miniature you can run

The toy below is my own sketch of the loop's shape, not Google's system, and it uses a seeded random mutation as a stand-in for the language models. It borrows the Borg framing: twelve machines, each with 100 units of CPU and 100 of memory, and a stream of 60 jobs, half CPU-heavy and half memory-heavy, sized so that not every job fits. The skeleton places each job on the feasible machine with the highest score from an evolved expression of the job's demand (c, m) and the machine's free capacity (fc, fm); the metric is the fraction of jobs placed. The pieces mirrored from the paper: an evolve block (the expression), an evaluate that returns a dictionary, a two-stage cascade (a candidate that scores more than 0.01 below the best-fit baseline on the first 4 streams never reaches the other 26), a database keyed by program length so short programs survive next to long ones, and a held-out test set of 100 streams that the search never sees.

"""Toy AlphaEvolve-style loop: evolve a scheduling heuristic (CPU+memory vector bin packing).
Pieces mirrored from Novikov et al. (2025): an evolve block, an evaluate() that returns a dict of scores,
an evaluation cascade, a MAP-Elites-flavoured database, and a held-out test set.
The LLM is replaced by a seeded random mutation (a stand-in). The simulator is mine, not Google's."""
import random
M, CAP = 12, 100                                     # 12 machines, each 100 CPU and 100 memory units

def make_stream(seed, n=60):                         # jobs: cpu-heavy or memory-heavy, sized to slightly overload the fleet
    rng = random.Random(seed); jobs = []
    for _ in range(n):
        if rng.random() < 0.5: jobs.append((rng.randint(20, 40), rng.randint(5, 15)))
        else:                  jobs.append((rng.randint(5, 15), rng.randint(20, 40)))
    return jobs

def simulate(priority, jobs):                        # skeleton: place each job on the feasible machine with top priority
    free = [[CAP, CAP] for _ in range(M)]; placed = 0
    for c, m in jobs:
        best, bi = None, None
        for i, (fc, fm) in enumerate(free):
            if fc >= c and fm >= m:
                p = priority(c, m, fc, fm)
                if best is None or p > best: best, bi = p, i
        if bi is not None: free[bi][0] -= c; free[bi][1] -= m; placed += 1
    return placed / len(jobs)

# --- evolve block starts: the code AlphaEvolve would be allowed to rewrite (here: an expression string) ---
BASELINES = {"first fit      ": "0", "best fit       ": "-(fc-c)-(fm-m)",
             "paper's form   ": "-((c/fc)+(m/fm)+(m/fc)/(c/fm+1e-9)+(c/fm)/(m/fc+1e-9))"}
# --- evolve block ends ---
LEAVES = ["c", "m", "fc", "fm", "(fc-c)", "(fm-m)", "1", "2", "10"]
def rand_expr(rng, d=2):
    if d == 0 or rng.random() < 0.25: return rng.choice(LEAVES)
    op = rng.choice(["+", "-", "*", "max", "min"]); a, b = rand_expr(rng, d - 1), rand_expr(rng, d - 1)
    return "%s(%s,%s)" % (op, a, b) if op in ("max", "min") else "(%s%s%s)" % (a, op, b)
def mutate(src, rng):                                # stand-in for the LLM proposing a diff
    r = rng.random(); new = rand_expr(rng)
    if r < 0.15: return new
    if r < 0.55: return "(%s)+0.1*%s" % (src, new)
    if r < 0.85: return "(%s)-0.1*%s" % (src, new)
    return "max(%s,%s)" % (src, new)

def compile_(src):
    return eval("lambda c,m,fc,fm: " + src, {"__builtins__": {}, "max": max, "min": min, "abs": abs})
TRAIN = [make_stream(s) for s in range(100, 130)]
TEST  = [make_stream(s) for s in range(900, 1000)]   # never shown to the search
def evaluate(src, floor):                            # returns a dict of scores, or None; cheap stage first (cascade)
    try:
        f = compile_(src)
        quick = sum(simulate(f, j) for j in TRAIN[:4]) / 4
        if quick < floor: return None                # pruned before the expensive stage
        return {"train": sum(simulate(f, j) for j in TRAIN) / len(TRAIN), "length": len(src)}
    except Exception:
        return None

def run(seed, steps=600):
    rng = random.Random(seed); db = {}               # cell = length bucket; keep the best program per cell
    s0 = BASELINES["best fit       "]; db[0] = (s0, evaluate(s0, 0))
    evals = full = 0
    for t in range(steps):
        keys = sorted(db, key=lambda k: -db[k][1]["train"])
        pk = keys[min(int(rng.expovariate(0.5)), len(keys) - 1)] if rng.random() < 0.7 else rng.choice(keys)
        child = mutate(db[pk][0], rng); evals += 1
        sc = evaluate(child, floor=db[0][1]["train"] - 0.01)
        if sc is None: continue
        full += 1; cell = min(sc["length"] // 25, 12)
        if cell not in db or sc["train"] > db[cell][1]["train"]: db[cell] = (child, sc)
    return db, evals, full

def mean_test(src): f = compile_(src); return sum(simulate(f, j) for j in TEST) / len(TEST)
for name, src in BASELINES.items(): print("%s train %.3f   held-out %.3f" % (name, sum(simulate(compile_(src), j) for j in TRAIN) / len(TRAIN), mean_test(src)))
for seed in range(2):
    db, evals, full = run(seed)
    top = max(db.values(), key=lambda v: v[1]["train"])
    print("seed %d: %d candidates, %d passed the cheap stage, %d archive cells | best train %.3f  held-out %.3f | length %d chars" %
          (seed, evals, full, len(db), top[1]["train"], mean_test(top[0]), top[1]["length"]))
    print("   program:", top[0] if len(top[0]) <= 70 else top[0][:70] + " ...")
first fit       train 0.856   held-out 0.858
best fit        train 0.851   held-out 0.859
paper's form    train 0.771   held-out 0.776
seed 0: 600 candidates, 482 passed the cheap stage, 13 archive cells | best train 0.897  held-out 0.889 | length 342 chars
   program: max((((max((((((((max((min(max(m,(fc-c)),(10+(fm-m))))-0.1*(1-min((fc- ...
seed 1: 600 candidates, 404 passed the cheap stage, 13 archive cells | best train 0.886  held-out 0.873 | length 23 chars
   program: ((fc-c)*max(10,(fm-m)))

First fit and best fit place about 86% of the jobs on both the training and held-out streams. The expression I took from the paper's Figure 6, which was tuned to Google's workloads and not to this simulator, does worse here (about 77%), a reminder that an evolved heuristic is specific to its evaluator's world. After 600 candidates, the evolved programs reach 0.897 and 0.886 on the training streams and 0.889 and 0.873 on held-out streams, so most of the gain survives on data the search never saw. The cheap stage rejected (or crashed on) 118 of 600 candidates in the first seed and 196 in the second. In seed 1 the best program was 23 characters, ((fc-c)*max(10,(fm-m))), while seed 0's best was 342 characters of nested clutter with similar accuracy. That gap is why the paper allows LLM-graded feedback on simplicity and why it keeps several scores.

Two cautions, both mine. The held-out set is drawn from the same generator as the training set, so this tests overfitting to particular streams, not a change in workload. And 600 random candidates is nothing like thousands of model-written diffs, each informed by the scores of earlier programs, so the toy shows the pipeline's structure and not its power.

Try it yourself

Raise steps to 3,000 (it takes about 40 seconds) and compare the best program's training and held-out scores: does the gap grow? Then build the test streams from a different mix, for example 90% CPU-heavy jobs, while keeping the programs you evolved on the original mix. How much of the gain survives a shift in the workload? This is why the Borg team tested on recent workloads and then measured after deployment.

State of play, October 2026

The white paper reports that AlphaEvolve used Gemini 2.0 Flash and Gemini 2.0 Pro; DeepMind's launch post says it planned an early access programme for selected academic users and was exploring broader availability, with no timeline. I did not check whether that has changed, and the system is not an open release I could run. Since June 2025, other groups have built open frameworks along the same lines, covered in chapter 10, and the paper's matrix result has been followed up: Dumas, Pernet and Sedoglavic posted a 48-multiplication algorithm with only rational coefficients, reached by transforming the complex algorithm, on 16 June 2025, and their listed revisions run to July 2026. A search snippet also describes a 2026 paper on its numerical accuracy, which I did not open. These details may be revised.

What the authors and others say about limits

  • The evaluator is the hard requirement. The paper's discussion says the main limitation is that AlphaEvolve handles problems for which an automated evaluator can be devised. Natural sciences that need physical experiments are out of reach unless a simulator exists. The authors say LLM-provided evaluation is possible but not what they optimised, and mention concurrent work on it.
  • The 48 is specific. It holds for complex-valued matrices, using complex multiplications, in characteristic 0. The follow-up by Dumas, Pernet and Sedoglavic shows a rational version; whichever algorithm, fewer multiplications is not the same as faster code, because additions, memory traffic and numerical error also count. The paper itself says only that it improves the count.
  • Self-reported. DeepMind's blog notes that the 0.7%, 23% and 1% figures apply to specific internal deployments and the 75% and 20% figures are "to the best of our knowledge". There is no external reproduction of the Google-internal results, which would not be possible from outside.
  • Modest, honestly described. The paper calls the self-improvement gains "moderate" and the feedback loop for improving the next version "on the order of months". The TPU change was also found independently by downstream tools. These are not the claims of runaway improvement.
  • Mostly ties. About three quarters of the maths problems ended in a tie with the known best; the value of the system there is as a tool for exploring many problems, which the later large study by Tao and colleagues frames as complementing human intuition.

Lessons for AI engineers

  • Build the evaluator first. The authors expect that the value of setting up more environments (problems) with robust evaluation functions will be more widely appreciated. Before choosing a model, ask whether you can score a candidate automatically, quickly and honestly. Chapter 15 and the AI CUDA Engineer case show what happens when the scorer has a gap that a search finds.
  • Make the scorer cheap in stages. A cascade of tests (crash check, small input, full benchmark) spends compute only on promising candidates. The same idea appears in evaluation pipelines throughout the path: see held-out evaluation.
  • Evolve things people can read and deploy. The Borg heuristic was chosen partly for interpretability and ease of deployment over a learned policy. A one-line rule can be reviewed, rolled back and monitored like any change. See search inside real products.
  • Hold out data and measure after rollout. The Gemini kernel team used half of the shapes for search and half for testing; the Borg team verified predictions with fleet-wide measurements after deployment.
  • Keep diversity and several objectives. The database combines MAP-Elites cells and islands, and the paper reports that multiple scores can help even the target metric. Lab 3 practises the archive; the first studio asks you to design a loop like this for a business problem.

Common misconception

"AlphaEvolve is a model that is smarter than the models inside it." The paper presents it as an agent built around existing models, and its Discussion calls it a test-time compute method that raises what the base model can do, compared with repeated sampling. The paper's ablations conclude that each component, including the use of large models alongside small ones, contributes significantly, so the model matters, but so do the evaluator, the prompt context and the evolution.

Key takeaways

  • AlphaEvolve evolves entire files against user-written evaluators, with a model ensemble, an evaluation cascade and a MAP-Elites plus islands database.
  • Reported results: a 48-multiplication algorithm for 4×4 complex matrices, 14 of 54 matrix targets improved, over 50 maths problems with about 20% new records, and a Borg heuristic recovering 0.7% of fleet compute.
  • Most outcomes were ties, and the engineering gains are modest and specific to Google's systems.
  • The requirement that decides where this works is a trustworthy automatic evaluator.
  • All headline numbers are DeepMind's own, and the system is not publicly available.

Check your understanding

Which change most distinguishes AlphaEvolve from FunSearch?

  1. It uses an evaluator for the first time
  2. It can evolve whole files in any language, with rich prompt context and several metrics, rather than one short function
  3. It removes the need for any human-written code
  4. It no longer needs a database of earlier programs
Both systems use evaluators and program databases. The user still writes the evaluate function and the starting program with evolve blocks, so C is wrong.

The Borg heuristic was reported to recover 0.7% of fleet-wide compute. What is the best reason this deployment is considered low-risk by the authors?

  1. The heuristic was trained with reinforcement learning, which is more reliable than code
  2. It was only tested in a simulator
  3. It replaced the whole scheduler with an LLM at run time
  4. It only changes the ranking among machines Borg has already found suitable, so decisions are correct by construction, and the rule is short enough to read and debug
The paper says exactly that and says it chose evolved code over a deep reinforcement learning policy for interpretability and deployability. It was validated in simulation and then measured after deployment, so B is incomplete.

AlphaEvolve found 48 scalar multiplications for 4×4 complex matrices. Which statement is correct?

  1. It improved Strassen-based 49 for complex-valued matrices; a later paper reported a version with rational coefficients
  2. It proved that 48 is optimal
  3. It improved the count for every field, including the field with two elements
  4. It showed the new algorithm is faster in practice on all hardware
The paper says first improvement in characteristic 0 and notes 47 was already known for the field with two elements. It makes no optimality claim and no claim about wall-clock speed.

In the toy, the evolved program from seed 0 is 342 characters and the one from seed 1 is 23, with similar accuracy. Why does the paper's design help with this?

  1. It stops evolution once programs reach a fixed length
  2. It re-trains the model on short programs
  3. It keeps a diverse database, allows several scores, and can use model-graded feedback on qualities such as simplicity
  4. It replaces long programs with their first line
The paper's evaluation section describes multiple scores and LLM-generated feedback for properties like simplicity, and its database aims to keep diversity. It does not describe a length cutoff or retraining on short programs.

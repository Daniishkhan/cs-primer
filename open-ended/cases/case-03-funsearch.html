FunSearch and the Cap Set

Language models invent plausible nonsense, which is a poor trait in a mathematician. FunSearch, from Google DeepMind, wraps a frozen code model in an evolutionary loop with a strict programmatic checker, and asks it to write small programs that build mathematical objects instead of the objects themselves. In 2023 it reported larger cap sets than any known before. This case follows the paper's design, its numbers and its stated limits.

What I could and could not read

I fetched and read the Nature paper, Romera-Paredes et al., "Mathematical discoveries from program search with large language models" (published 14 December 2023, volume 625, 2024): the abstract, the main text and the Discussion, and the parts of the Methods on the programs database. I also read DeepMind's public repository README for the code release and the repository's cap set notebook, and DeepMind's blog post about the work. I did not read the Supplementary Information (appendices on ablations, statistics and the full discovered programs), and Table 1 of the paper, which gives the bin-packing numbers, is an image I could not extract, so I give only the text's qualitative statements about it. I did not read any independent critique or replication. One fact about the size of the previous record comes from the repository notebook rather than the paper's text, and the cap set values for small dimensions come from search results for the OEIS entry A090245. Every performance figure is the authors' own.

The pattern in one sentence

Ask a language model for programs that construct a solution, not for the solution itself, and let an exact scorer decide which programs live, so the model's creativity is kept while its mistakes are filtered out.

Context: easy to check, hard to find

The paper opens with a familiar asymmetry. Many problems in mathematics and computer science are "easy to evaluate" and "typically hard to solve": checking a candidate is quick, finding one is not. If you can write a fast evaluate function that scores a candidate, you can in principle search for good ones. The authors' problem is that large language models (LLMs) "sometimes suffer from confabulations (or hallucinations)", producing statements that are plausible but wrong, which would make them unreliable if asked for a proof or a construction directly. But a hallucinated program costs nothing: it is run, it scores badly or crashes, and it is thrown away. A correct and surprising one is kept, and its correctness is verified by running it.

The idea of pairing an LLM with evolution was not new in 2023; the paper cites earlier work that used LLMs as mutation operators on synthetic problems, architecture search and puzzles. What FunSearch claimed was a new kind of result: surpassing the best known results on an established open problem, which, as the authors note, is a clear sign that the discovery is not just retrieved from the model's training data. Chapter 9 places this in the wider family of program-evolution methods.

Cap set
A set of vectors in Z3n (n entries, each 0, 1 or 2) in which no three vectors sum to zero, which geometrically means no three points are on a line.
Skeleton
The fixed part of a program (boilerplate and known structure) that calls the one function the search is allowed to rewrite.
Priority function
A function that gives each candidate a score; a greedy algorithm adds candidates in order of priority whenever they are allowed.
Best-shot prompting
Putting several of the best programs found so far into the prompt and asking the model to write an improved version.
Island model
An evolutionary technique that keeps several separate populations and only occasionally lets them exchange good members, to preserve diversity.
Admissible set
A structured collection of vectors in {0,1,2}n that tells you how to combine small cap sets into big ones; the route to bounds on the asymptotic cap set capacity.

The problem: the cap set

The paper calls the cap set problem "once described by Terence Tao as 'perhaps my favourite open question'". The task is to find the largest cap set in each dimension n. The exact answer is known only for n ≤ 6. Looking up the standard values (OEIS A090245, which I saw through search results), the maxima for n = 3, 4, 5 and 6 are 9, 20, 45 and 112. Brute force explodes: the paper puts the search space at around 31,600 for n = 8. Mathematicians also care about the asymptotic capacity, C = supn cn1/n, where cn is the largest cap set size in dimension n. The paper cites a breakthrough upper bound C ≤ 2.756 and focuses on lower bounds, which come from explicit constructions.

How FunSearch works

The input is a specification: an evaluate function that scores a candidate solution, plus an initial program that may be trivial. The authors found performance improves markedly if the initial program is a skeleton that contains known structure, with only the crucial piece left for the search to rewrite. For the cap set, the skeleton is a greedy algorithm: start with an empty set, then repeatedly add the vector of highest priority that does not create a line with two vectors already chosen. The thing to evolve is the priority function, from a trivial constant. The paper argues that the fixed skeleton helps because the LLM's effort goes to the one hard part, instead of recreating known structure and making mistakes that would invalidate the whole program.

The loop has four components, all described in the paper:

  1. A pretrained LLM, unmodified. The results use Codey, a code model built on PaLM 2, "without any fine-tuning on our problems". The authors chose a fast model over a slower, higher-quality one, because the loop needs on the order of 106 samples in total, and say the results are "not too sensitive to the exact choice of LLM" as long as it was trained on a large code corpus (they compare with StarCoder in the appendix I did not read).
  2. An evaluator. Each generated program is run on a set of inputs, such as dimensions n, with time and memory limits, and the scores are combined (for example by mean). Programs that crash, time out or return invalid output are discarded.
  3. A programs database with islands. Correct programs are stored in several independently evolving subpopulations. Inside an island, programs with the same signature (the tuple of their scores on every input) are clustered, and sampling picks a cluster, favouring higher scores, and then a program inside it, favouring shorter ones. Periodically the worst half of the islands, ranked by their best member, are wiped and restarted from a clone of a good program from a surviving island. This is the island model from the evolutionary algorithms chapter, applied to program text.
  4. Best-shot prompting. The prompt shows k = 2 programs from one island, sorted by score and labelled priority_v0 (worse) and priority_v1 (better), followed by the header of priority_v2 for the model to complete. The authors found two programs worked better than one, with diminishing returns beyond.

It runs as an asynchronous distributed system. The paper's setup typically uses 15 samplers on machines with accelerators and 150 evaluators on inexpensive CPUs (five servers each running 32), so that slow evaluations do not stall the fast model. Because of sampling randomness the authors ran several experiments for some problems and reported the best; the statistical analysis is in the appendix I did not read. For why the evaluators run in a sandbox, see containers and virtual machines: the programs are untrusted code.

What it found

Cap sets in eight dimensions

For dimension 8, FunSearch found a cap set of 512 vectors. The previous best construction had 496, according to DeepMind's repository notebook (the paper plots cap set sizes by dimension in a figure I could not read). The paper stresses two points: the previous record relied on "a complex combination of cap sets in lower dimensions", whereas FunSearch found a larger set "from scratch, without having to be explicitly taught any way of combining cap sets", and the output is a short program, not a list of 512 vectors. By reading that program the authors extracted the idea (a notion of "reflections" and a similarity to the optimal 112-vector Hill cap in six dimensions) and wrote down an explicit construction by hand.

The asymptotic capacity

For the capacity, the paper searches for admissible sets. A first discovered priority function built an admissible set I(12,7) which on its own improved the lower bound on C from 2.2180 to 2.2184. Then the interesting step happened. Reading the program, the authors noticed that it treated the 12 coordinates in a highly symmetric way, in four groups of three, and that the set it built was unchanged by cyclic shifts within each group. They then asked FunSearch to search directly for such symmetric sets, a smaller space that reaches higher dimensions. That produced a full-size I(15,10) set (C ≥ 2.219486) and a partial admissible set in A(24,17) of 237,984 vectors, implying C ≥ 2.2202. The paper calls this "the largest improvement in 20 years" to the lower bound, while stressing that it is "still far from the upper bound" of 2.756.

The paper describes the workflow as human and search "both in the loop": FunSearch suggests a solution, researchers inspect the code and notice a feature, and that feature refines the next search. This is the point of searching function space: a list of 237,984 vectors teaches nothing, whereas four lines of code with a visible symmetry does.

Online bin packing

To show the method is not specific to pure mathematics, the authors apply it to online bin packing (items arrive one at a time and must be placed immediately in a bin of fixed size). They evolve a heuristic that scores each bin for the arriving item, starting from the classic best-fit rule, using instances the size of OR1 from a standard library for training and testing on OR1 to OR4. The text states that FunSearch outperforms first fit and best fit on all four, and that the advantage grows on larger instances. On instances drawn from a Weibull distribution, chosen because it resembles real scheduling workloads, the paper says the evolved heuristic is within 0.03% of the lower bound on the optimum for 100,000 items. The evolved strategy: assign an item to the tightest-fitting bin only if the fit is "very tight", and otherwise prefer a bin that leaves more space, which avoids creating small gaps that will probably never be filled. I could not extract the numerical table.

A miniature you can run

This is my own toy, not DeepMind's code, and the model is replaced by a seeded random mutation (a deterministic stand-in, not a language model). The skeleton is the greedy cap set builder from above. The "program" is the text of a priority expression in the vector's counts of 0s, 1s and 2s, its first and last entries, a few comparisons and small constants. Four islands each keep a dictionary of programs, parents are drawn favouring higher scores, mutation grows an expression by adding or maxing a random sub-expression, the evaluator runs the expression in a restricted eval and discards failures, and after every 20 rounds the worst two islands are replaced by a clone of the best program. The score is a tuple of cap set sizes for n = 3, 4 and 5.

"""Toy FunSearch: evolve the text of a priority function for a greedy cap-set builder.
The LLM is replaced by a seeded random mutation of an expression (a stand-in, not a language model).
Skeleton, evaluator and islands follow the structure in Romera-Paredes et al. (2023); the details are mine."""
import itertools, random
VECS = {n: list(itertools.product((0, 1, 2), repeat=n)) for n in (3, 4, 5)}
BEST = {3: 9, 4: 20, 5: 45}                          # known maxima, used only to report how close we get

def build(priority, n):                              # the fixed skeleton: greedy by priority
    vs = VECS[n]
    order = sorted(range(len(vs)), key=lambda i: -priority(vs[i], n))
    chosen, have = [], set()
    for i in order:
        x = vs[i]
        if all(tuple((-a - b) % 3 for a, b in zip(x, y)) not in have for y in chosen):
            chosen.append(x); have.add(x)            # no third point completes a line with x and y
    return len(chosen)

def evaluate(src):                                   # the evaluator: run the program, score it, never trust it
    try:
        f = eval("lambda el, n: " + src, {"__builtins__": {}, "max": max, "min": min, "abs": abs})
        return tuple(build(f, n) for n in (3, 4, 5))
    except Exception:
        return None

LEAVES = ["el.count(0)", "el.count(1)", "el.count(2)", "(el[0]==el[-1])", "(el[1]==el[-2])", "sum(el)", "el[0]", "el[-1]", "n", "1", "2", "3"]
def rand_expr(rng, d=3):
    if d == 0 or rng.random() < 0.3: return rng.choice(LEAVES)
    op = rng.choice(["+", "-", "*", "max", "min"])
    a, b = rand_expr(rng, d - 1), rand_expr(rng, d - 1)
    return "%s(%s,%s)" % (op, a, b) if op in ("max", "min") else "(%s%s%s)" % (a, op, b)

def mutate(src, rng):                                # stand-in for the LLM: grow the program with a random sub-expression
    if rng.random() < 0.2: return rand_expr(rng)
    new = rand_expr(rng, 2)
    return "%s+%s" % (src, new) if rng.random() < 0.5 else "max(%s,%s)" % (src, new)

def run(seed, rounds=60, islands=4, per_round=12):
    rng = random.Random(seed); seed_prog = "0"       # trivial constant priority
    pop = [{seed_prog: evaluate(seed_prog)} for _ in range(islands)]
    for r in range(rounds):
        for isl in pop:
            ranked = sorted(isl, key=lambda s: (-sum(isl[s]), len(s)))
            for _ in range(per_round):
                parent = ranked[min(int(rng.expovariate(0.7)), len(ranked) - 1)]
                child = mutate(parent, rng); sc = evaluate(child)
                if sc is not None and child not in isl: isl[child] = sc
        if r % 20 == 19:                             # drop the worst half of islands, clone the best into them
            order = sorted(range(islands), key=lambda i: -max(sum(v) for v in pop[i].values()))
            for bad in order[islands // 2:]:
                best = max(pop[order[0]], key=lambda s: sum(pop[order[0]][s]))
                pop[bad] = {best: pop[order[0]][best]}
    allp = {s: v for isl in pop for s, v in isl.items()}
    best = max(allp, key=lambda s: (sum(allp[s]), -len(s)))
    return best, allp[best], len(allp)

print("trivial priority '0' gives caps of size", evaluate("0"), "for n = 3, 4, 5; best known:", tuple(BEST.values()))
for seed in range(3):
    best, sc, k = run(seed)
    print("seed %d: %d programs kept, best caps %s  program: %s" % (seed, k, sc, best[:90] + ("..." if len(best) > 90 else "")))

The trivial constant priority (greedy in lexicographic order) builds caps of 8, 16 and 32 against the known maxima 9, 20 and 45. In all three seeds the evolved programs reach 20 (the optimum) in dimension 4 and 40 in dimension 5; two of the three reach 9 in dimension 3 and the third stops at 8. Each run kept between 647 and 797 distinct programs. Two things the toy leaves out are the ones that made the real system work at n = 8: an LLM that proposes sensible code edits instead of random growth (the real search needs around a million samples), and a prompt that shows two ranked programs. A random stand-in can only make a program longer; it cannot reason about why one priority worked.

Try it yourself

Call run(seed, islands=1) and compare the best score with the default four islands across seeds 0 to 5. When I ran seeds 0 to 5, one island reached the optimum of 20 at n = 4 in 3 of 6 seeds and four islands in 6 of 6, a small sample but in the direction the paper's design predicts. Do you see the same, and what would you need to run to be confident? Then change (3, 4, 5) in evaluate to (5,), take the best program and call build on it for n = 3 and 4. Does it still do well? That is the real system's reason for scoring on several inputs at once.

What the authors said about limits, and what to be careful about

  • Where it works. The authors list three conditions: an efficient evaluator, a rich scoring signal that quantifies improvement rather than a yes or no, and a skeleton with an isolated part to evolve. Theorem proving, they note, falls outside it because the score is not rich enough.
  • What the LLM is doing. The paper's own reading is that the LLM "does not use much context about the problem" and is better seen as a source of diverse, syntactically valid programs with "occasionally interesting ideas". The evolutionary loop supplies the selection. This matters if you expect the model to "understand" cap sets.
  • Humans are in the loop. The decisive jump in the capacity bound came after researchers inspected a program and spotted a symmetry. The authors say so; it is not a fully autonomous discovery.
  • Selection of best results. The paper says that for some problems several experiments were run and the best reported. That is normal for stochastic search, but the number in a headline is a best-of-several, not an average.
  • Improvement size. A cap set of 512 against 496 is a 3% increase in one dimension; the capacity gain is in the fourth decimal place. The authors present these as new knowledge, which they are, while saying the capacity bound remains far from its upper bound.
  • What I could not check. I did not independently run the released programs, and I did not read outside commentary on the result.

State of play, October 2026

DeepMind's blog notes a December 2024 update that used Gemini 1.5 Flash in place of the original PaLM-2-based model for combinatorial competitive programming. The successor system, AlphaEvolve (next case), evolves whole files rather than one function and reports needing thousands of model samples instead of millions. DeepMind's repository releases the evolutionary algorithm, code manipulation routines and a single-threaded pipeline, but states that it does not contain the language models, the sandbox or the distributed infrastructure. Open-source reimplementations are covered in chapter 10.

Lessons for AI engineers

  • Put the model where mistakes are cheap. A program that is wrong costs one evaluation. The same model asked to assert a result would cost trust. Use a model as a proposer and an exact check as the arbiter; see the same shape in inference-time search with verifiers.
  • Evolve the recipe, not the result. A program is compact, readable and sometimes generalises across sizes; a list of vectors is none of those. If you need people to learn from the output, search over descriptions.
  • The evaluator is the product. If its score can be gamed, the search will find the gap; see evaluator hacking. FunSearch scores correctness by execution, which is why it resists confabulation, and is hard to game for cap sets because the check is exact.
  • Diversity needs engineering. Islands, signature clusters and restarts exist to stop the population collapsing onto one idea. Lab 3 builds a small version for bin packing.
  • Keep a person in the loop for insight. The best step in the paper was a human reading the output.

Common misconception

"The LLM solved an open maths problem." What the paper reports is a system of LLM, evolution, a scorer and researchers that found a better construction. Remove the evaluator and the islands and you have a model that writes plausible code. The authors themselves attribute the success to the combination.

Key takeaways

  • FunSearch pairs a frozen code LLM with an exact evaluator and an island-based programs database, evolving one function inside a fixed skeleton.
  • Best-shot prompting shows two ranked programs and asks for a better third.
  • The paper reports a cap set of 512 in eight dimensions (previous 496) and a capacity lower bound raised to 2.2202.
  • Searching for programs gave compact, readable outputs; a human spotting a symmetry in one program led to the bigger gain.
  • The authors say it needs a fast evaluator, a graded score and a skeleton; and the headline results are best-of-several runs by the authors.

Check your understanding

Why does FunSearch ask the model for a priority function rather than a list of cap set vectors?

  1. Models cannot output more than a few vectors
  2. A program is always shorter than the optimal answer
  3. It avoids having to evaluate the result
  4. A short program that builds the set is easier to score and read, scales to larger instances, and lets researchers spot structure such as symmetry
The paper argues that programs are more concise and interpretable than raw solutions and that this enabled the symmetry insight. Every candidate is still evaluated (C is wrong); programs are not guaranteed to be shorter than every answer (B).

What does the evaluator do with a generated program that crashes or exceeds the time limit?

  1. Gives it a score of zero and stores it as a low-ranked parent
  2. Discards it, so only correct programs enter the database
  3. Sends it back to the model to be fixed
  4. Stops the experiment
The paper states that incorrect programs, those that do not run within limits or return invalid output, are discarded before the database. Keeping them as parents (A) would pollute the population.

Which statement about the capacity result is accurate?

  1. A human noticed a symmetry in a discovered program, then had FunSearch search the smaller symmetric space, which produced the larger bound
  2. FunSearch matched the upper bound of 2.756
  3. The result came from a fine-tuned model trained on cap set literature
  4. No human inspection was involved
The paper describes exactly this loop. The upper bound of 2.756 remains far away, and the model was used pretrained, without fine-tuning on the problems.

In the toy, what does the island reset (replacing the worst islands with a clone of the best) imitate, and what does it risk?

  1. It imitates crossover, and risks overfitting to the training set
  2. It imitates temperature scaling, and risks slower sampling
  3. It imitates the paper's periodic discarding of the worst half of the islands, and risks reducing diversity if done too often
  4. It imitates the evaluator cascade, and risks accepting wrong programs
The paper restarts the worst half of the islands from clones of good programs. The cost is that cloning reduces diversity, which is what islands are there to protect.

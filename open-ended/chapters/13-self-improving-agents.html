Self-Improving Coding Agents

In the last chapter a fixed meta agent designed other agents. This chapter closes the loop: a coding agent edits its own code, keeps every version in an archive, and decides whether a change was an improvement by running it on a benchmark. That is the Darwin Gödel Machine. The question it answers is how far self-modification can go when the only judge is an experiment, and the question it leaves open is who is checking the experiment.

Why this matters

Self-improvement is the most discussed and least understood idea in this course. The honest version is smaller and more useful than the headlines: a frozen model, wrapped in code that the agent itself can rewrite, evaluated by tests, with every version kept. That is a real engineering pattern (agents that tune their own tools, prompts and workflows) and it comes with a real failure mode: any weakness in the scorer is something the loop will find and then amplify, because the thing doing the improving is also the thing being scored. After this chapter you can explain each part of the algorithm including the parent-selection formula, run a miniature version, read the paper's ablations and its cost, say which of its numbers are in-sample, and describe the objective-hacking episode its authors report. Chapter 15, chapter 16 and chapter 17 turn those lessons into practice.

From Gödel machine to Darwin Gödel Machine

The idea of a program that rewrites itself to become better at rewriting itself is old. Schmidhuber's Gödel machine (proposed in 2003 and developed in later papers) is a theoretical self-referential system that may replace any part of its own code, including the part that decides whether to replace code, but only after it has proved, inside a formal system, that the change increases its expected future reward. The requirement is what makes it elegant and what makes it unusable: for realistic agents and tasks, nobody can produce such proofs. Zhang, Hu, Lu, Lange and Clune (2025), in “Darwin Godel Machine: Open-Ended Evolution of Self-Improving Agents”, keep the shape and swap the standard of evidence. The Darwin Gödel Machine (DGM) adopts a change if an experiment says it helps: the modified agent is run on a coding benchmark and its score is measured. A proof becomes a test result, and a single self-modifying program becomes an evolving population with an archive, which is where “Darwin” comes from.

Trading proof for experiment is the entire design philosophy, and it explains both the strengths and the weaknesses. An empirical standard is available for almost any real agent. It is also exactly as trustworthy as the experiment, which is why the second half of this chapter spends time on what a benchmark does and does not certify.

Why a coding agent is the right thing to make self-improving

An agent that modifies its own code is doing a coding task. If the agent is a coding agent, evaluated on coding benchmarks, then getting better at the benchmark means getting better at editing code, which means getting better at editing its own code. The authors make this the central design decision: self-improvement is defined as a coding task on the agent's own repository, so that one score serves both purposes. Improvement on SWE-bench is evidence of better downstream ability and, by the same step, of a better capacity for further self-improvement.

Contrast this with the previous chapter. In Meta Agent Search the meta agent was fixed at the start and designed task agents that were a different kind of object. Improving the task agent's score never improved the designer. The DGM removes the distinction: the agent that is edited is the agent that does the editing.

Analogy: a workshop where every carpenter rebuilds their own tools

Imagine a carpenters' workshop where each carpenter, between jobs, studies their notes on what went wrong and rebuilds their own jig, chisel handle or checklist. They measure each new version by building a standard set of cabinets and counting the ones that pass inspection. Nobody throws away an old carpenter's setup; the workshop keeps a shelf of every version, and a new carpenter is often cloned from an older setup that was merely decent but had an interesting jig. After a few dozen rounds the best setups are much better than the first.

Where it breaks down: the carpenter's hands and brain do not change. Here too, the underlying language model is frozen; only the surrounding code is edited, so the ceiling is set by what the model can do with better tools. And the inspector is a fixed set of cabinets, so a carpenter who learns to tamper with the inspection form looks, for a while, like a master.

The algorithm

The DGM starts from one coding agent. It is deliberately plain: a frozen foundation model connected to two tools, a Bash tool (to run commands) and an edit tool (to view and modify files and directories). Its prompt names the repository, the problem statement and the testing framework. Everything else, any smarter tool or workflow, has to be discovered. The loop then runs for a fixed number of iterations (80 in the paper's main experiments, producing one new agent per iteration, with two or four running in parallel).

  1. Select a parent from the archive. Selection is random but weighted toward agents that score well and have few children (the formula follows).
  2. Diagnose. The parent's own evaluation logs, which record what it tried on the benchmark tasks and where it failed, are given to a foundation model that proposes the next feature to implement and writes it up as a problem statement.
  3. Self-modify. That problem statement is handed to the parent as a coding task on its own repository. The parent edits its own files and the result is a new agent, the child.
  4. Check it still works. The child is kept only if its code compiles and it can still edit a codebase. An agent that has lost the ability to edit can never improve again, so it is discarded.
  5. Evaluate in stages on a coding benchmark: a few tasks to check basic function, then more tasks for survivors, then many for the most promising.
  6. Archive the child with its score and record it as a child of its parent. Nothing is ever removed.

Two things stay outside the agent's reach in the paper's implementation: the open-ended exploration process (archive maintenance and parent selection) and the benchmark harness. The authors list making the exploration process itself modifiable as future work. This matters for safety: the part of the system that decides what counts as success and which versions survive is not something the agent can edit.

Parent selection, with numbers

The selection rule is where the DGM's open-endedness lives. Let αi be agent i's benchmark score (as a fraction from 0 to 1) and ni the number of its children that kept the ability to edit code. The paper (Appendix C.2) defines, for every agent whose score is not yet perfect:

Plug in numbers. The six-agent archive from this chapter, one column per step.

The idea

  1. archive: (score, children) per agent; lambda = 10, alpha0 = 0.5
  2. s ← 1 / (1 + exp(−lambda × (score − alpha0)))
  3. h ← 1 / (1 + children); w ← s × h
  4. p ← w ÷ (sum of all w); compare with greedy (best score gets 100%)
"""The Darwin Godel Machine's parent-selection rule, step by step, for the
six-agent archive used in the chapter."""
import math

# ── 1. The archive: benchmark score and number of children so far ────────
LAM, ALPHA0 = 10, 0.5            # the paper's sharpness and midpoint
ARCHIVE = [("#0 base", 0.20, 4), ("#3", 0.35, 2), ("#7", 0.45, 3),
           ("#11", 0.50, 0), ("#15", 0.60, 1), ("#18", 0.62, 6)]


# ── 2. Per agent: s (performance), h (novelty), w = s * h ────────────────
def sigmoid_score(alpha):
    """s = 1 / (1 + exp(-lam * (alpha - alpha0)))."""
    return 1 / (1 + math.exp(-LAM * (alpha - ALPHA0)))


def novelty(kids):
    """h = 1 / (1 + n): halves with the first child, thirds with the second."""
    return 1 / (1 + kids)


rows = [(name, a, n, sigmoid_score(a), novelty(n)) for name, a, n in ARCHIVE]
weights = [s * h for _, _, _, s, h in rows]

# ── 3. Normalise the weights into probabilities ──────────────────────────
total = sum(weights)
print("agent    score kids     s     h     w   p")
for (name, a, n, s, h), w in zip(rows, weights):
    print(f"{name:8s} {a:5.2f} {n:4d} {s:5.3f} {h:5.3f} {w:5.3f}"
          f" {w / total:5.1%}")
print(f"sum of weights = {total:.3f}")

# ── 4. What greedy selection would do instead ────────────────────────────
best = max(ARCHIVE, key=lambda r: r[1])
print(f"greedy picks {best[0]} with probability 100%")
agent    score kids     s     h     w   p
#0 base   0.20    4 0.047 0.200 0.009  0.8%
#3        0.35    2 0.182 0.333 0.061  5.3%
#7        0.45    3 0.378 0.250 0.094  8.3%
#11       0.50    0 0.500 1.000 0.500 43.9%
#15       0.60    1 0.731 0.500 0.366 32.1%
#18       0.62    6 0.769 0.143 0.110  9.6%
sum of weights = 1.140
greedy picks #18 with probability 100%

with λ = 10 and α0 = 0.5, and then k parents are drawn with replacement from these probabilities (k = 2 for SWE-bench, 4 for Polyglot). Read it in two halves. The sigmoid si turns a score into a smooth preference: agents far below α0 get little weight, those above get up to 1, and λ controls how sharp the switch is. The factor hi is a novelty bonus in the sense of the earlier chapters: an agent that has already had many children is a well-explored branch, so it gets less weight. Every agent keeps a non-zero probability, so any path to improvement stays reachable given enough compute. Here is the rule on a small archive of six agents:

"""select_demo.py: the DGM parent-selection weights for a small archive."""
import math

LAM, ALPHA0 = 10, 0.5                       # the paper's settings
archive = [("#0 base",   0.20, 4), ("#3",  0.35, 2), ("#7",  0.45, 3),
           ("#11",       0.50, 0), ("#15", 0.60, 1), ("#18", 0.62, 6)]

rows = []
for name, alpha, kids in archive:
    s = 1 / (1 + math.exp(-LAM * (alpha - ALPHA0)))     # sigmoid-scaled performance
    h = 1 / (1 + kids)                                   # novelty bonus: fewer children, more weight
    rows.append((name, alpha, kids, s, h, s * h))
total = sum(r[5] for r in rows)
print("agent     score kids  sigmoid  1/(1+kids)  weight  P(parent)")
for name, alpha, kids, s, h, w in rows:
    print(f"{name:9s} {alpha:5.2f} {kids:4d}  {s:7.3f}  {h:10.3f}  {w:6.3f}  {w/total:8.1%}")

#0 base    0.20    4    0.047       0.200   0.009      0.8%
#3         0.35    2    0.182       0.333   0.061      5.3%
#7         0.45    3    0.378       0.250   0.094      8.3%
#11        0.50    0    0.500       1.000   0.500     43.9%
#15        0.60    1    0.731       0.500   0.366     32.1%
#18        0.62    6    0.769       0.143   0.110      9.6%

Look at the last two rows. Agent #18 has the highest score (0.62) but already has six children, so it gets 9.6% of the probability. Agent #11 scores lower (0.50) but has no children, and it gets 43.9%. Greedy selection would give all the probability to #18. Compare this to the UCB rule of chapter 1: a score term plus an exploration term, where the exploration term shrinks as a node is visited. The product form differs from UCB's sum, but the purpose is the same.

A self-improving agent you can run

The full system needs a frontier model, a code-execution sandbox and a budget measured in thousands of dollars. The next example keeps the structure and replaces the expensive parts with a deterministic stand-in, which it states up front:

  • The agent is a source file. It declares which FEATURES it has (tools and workflow steps such as run_tests, best_of_n, read_logs) and defines an edit_file function. If a self-edit damages edit_file, the child fails the “still works” check and is discarded.
  • The foundation model is a hash. Whether an agent solves a task is a seeded coin flip whose probability depends on its features (each has a weight, some are harmful) and on the task's difficulty. This is an assumption of the toy, not a measurement.
  • Self-modification is a stand-in function whose quality depends on the modifier's own features. An agent with read_logs diagnoses better (it finds the most useful missing feature 75% of the time instead of 25%), and an agent with edit_v2 breaks itself less often (8% against 35%). That dependency is the self-referential part: a better agent is a better improver.
  • There are 14 possible features, including five harmful ones, two mutually exclusive versions of the edit tool (edit_v1 is weaker than edit_v2), and three features that only help when run_tests is present.
"""mini_dgm.py: a Darwin Godel Machine in miniature. The agent IS its source file; a stand-in 'model' edits it."""
import hashlib, math, random

def u(*parts):                                   # deterministic uniform in [0, 1) from a hash
    return int(hashlib.sha256("|".join(map(str, parts)).encode()).hexdigest()[:12], 16) / 16**12

WEIGHT = {"view_lines": .5, "edit_v1": .3, "edit_v2": .9, "run_tests": 1.0, "retry": .8, "best_of_n": 1.0,
          "trim_context": .6, "read_logs": .4, "peer_review": .7, "verbose_prompt": -.5,
          "over_retry": -.7, "strict_format": -.4, "hardcode_paths": -.6, "skip_tests": -.9}
NEEDS_TESTS = {"best_of_n", "retry", "peer_review"}   # these only pay off when run_tests exists
HACK = "special_case_tests"                      # only offered when a run allows it (section on hacking)
BASE = '''FEATURES = {feats}
def edit_file(path, old, new):
    return "edited " + path
'''
SEARCH_IDS = range(50)                           # tasks whose tests the agent can see
HELD_IDS = range(1000, 1200)                     # tasks it never sees

def load(src):                                   # the agent only counts if its source still works
    ns = {}
    try:
        exec(src, ns); assert callable(ns["edit_file"])
        return ns["FEATURES"]
    except Exception:
        return None

def success(src, task):                          # chance a task is solved, then a hashed coin flip
    feats = load(src)
    d = 1 + 10 * u("difficulty", task)
    if HACK in feats and task in SEARCH_IDS:
        return u("hack", task) < .97             # memorised the visible tests
    gain = sum(WEIGHT.get(f, 0) for f in feats if f not in NEEDS_TESTS)
    gain += sum(WEIGHT[f] if "run_tests" in feats else -.3 for f in feats if f in NEEDS_TESTS)
    logit = 1.5 + gain - d
    return u("run", hashlib.md5(src.encode()).hexdigest(), task) < 1 / (1 + math.exp(-logit))

def score(src, ids):
    return sum(success(src, t) for t in ids) / len(ids)

def self_modify(parent_src, modifier_src, key, hack=False):
    """Stand-in for 'the parent agent edits its own code'. How well it does depends on the
    modifier's own features: read_logs improves the diagnosis, edit_v2 avoids damaging edits."""
    mine = load(modifier_src)
    pool = list(WEIGHT) + ([HACK] if hack else [])
    have = load(parent_src)
    missing = [f for f in pool if f not in have and not (f.startswith("edit_v") and any(h.startswith("edit_v") for h in have))]
    if not missing:
        return parent_src, None
    best = max(missing, key=lambda f: WEIGHT.get(f, 0))
    q = .25 + (.5 if "read_logs" in mine else 0)          # chance the diagnosis finds the best fix
    pick = best if u("diag", key) < q else missing[int(u("rand", key) * len(missing))]
    feats = sorted(load(parent_src) + [pick])
    child = BASE.format(feats=feats)
    if u("slip", key) < (.08 if "edit_v2" in mine else .35):
        child = child.replace("def edit_file", "def edt_file")      # an edit that breaks editing
    return child, pick

def run(mode, seed, iters=24, hack=False):
    rng = random.Random(seed)
    root = BASE.format(feats=[])
    archive = [dict(src=root, score=score(root, SEARCH_IDS), kids=0, id=0)]
    for it in range(1, iters + 1):
        if mode == "greedy":
            parent = max(archive, key=lambda a: a["score"])
        elif mode == "no_archive":
            parent = archive[-1]
        else:                                                   # DGM: sigmoid(score) / (1 + children)
            w = [(1 / (1 + math.exp(-10 * (a["score"] - .5)))) / (1 + a["kids"]) for a in archive]
            parent = rng.choices(archive, w)[0]
        modifier = root if mode == "fixed_meta" else parent["src"]   # ADAS-style: the designer never changes
        child, pick = self_modify(parent["src"], modifier, (seed, it), hack)
        if load(child) is None:
            continue                                            # cannot edit any more: discarded
        parent["kids"] += 1
        archive.append(dict(src=child, score=score(child, SEARCH_IDS), kids=0, id=len(archive), parent=parent["id"], pick=pick))
    return archive

Three things in this output mirror the paper. The best agent sits at the end of a path that passes through nodes which were not impressive when they were created: #1 and #3 scored 0.08 and 0.16. The archive contains two attempts at the same goal (#4 added the weak edit tool, #6 added the strong one, both from #3), and only one led anywhere, which is the paper's observation that different implementations of the same functionality can perform very differently (its Appendix G). And the held-out score of the best agent, 0.550 on 200 tasks it never saw, is far above the starting agent's 0.120. One thing is not realistic: in the toy an edit can only add a feature, so the harmful skip_tests added at #1 is carried along forever. A real agent can also remove or rewrite what it has, which is one reason a real archive is a richer object.

Step through

One DGM iteration: from archive to archive

  1. Select. A parent is drawn from the archive with probability that rises with its score and falls with the number of children it has already produced.
  2. Diagnose. A separate foundation model reads the parent's benchmark logs, finds a weakness and turns it into a concrete instruction.
  3. Self-edit. The parent receives that instruction as a coding task on its own source, and its patch is the child.
  4. Check. A child that cannot compile, or can no longer edit code, is discarded before it costs any evaluation.
  5. Evaluate. Evaluation is staged: a few tasks first, and only agents that clear a bar are run on the larger, more reliable set.
  6. Archive. The child is stored with its score. Dips are kept, because a lower-scoring agent may carry an idea a later agent needs.

Does the mini version reproduce the paper's ablations?

The paper compares the full DGM with three variants, and the toy can run all of them. dgm is the algorithm above. greedy always picks the best-scoring agent as parent. no_archive always modifies the latest working agent, as the paper's “without open-ended exploration” baseline does. fixed_meta always uses the original agent as the modifier, so improvements never improve the improver; this is the paper's “without self-improvement” baseline, which the authors describe as replicating ADAS in their setting. Each variant gets 24 iterations and 20 seeds, and the table reports the best-on-search agent's score on the 50 search tasks and on 200 held-out tasks.

    rows = []
    for seed in range(20):

        top = max(arc, key=lambda a: a["score"])

    n = len(rows)
    print(f"{mode:12s} {sum(r[0] for r in rows)/n:14.3f}  {sum(r[1] for r in rows)/n:8.3f}  {sum(r[2] for r in rows)/(n*24):14.0%}")

Two of the paper's orderings appear. The full method beats greedy (0.508 against 0.373 held-out): always branching from the current best wastes the stepping stones, and it also leaves the weak edit_v1 lineage in charge in some seeds. And it beats fixed_meta (0.508 against 0.418): when the modifier never improves, it keeps its low diagnosis rate and its high chance of breaking things, and the functioning-children rate drops from 69% to 63%. One ordering does not appear: no_archive matches the full method (0.488 against 0.508, a difference that 20 seeds cannot resolve). The reason is instructive. In this toy the landscape has few traps, so a single chain that keeps adding features and records the best along its path does well, and nothing makes an old, low-scoring ancestor the only route to a better branch. In the paper's setting, on real repositories and a noisy benchmark, a bad edit can make later edits harder, and the authors report much weaker numbers for that baseline (below). A search method's value depends on the landscape, as chapter 3 argued; do not read this toy as evidence against archives.

What the paper reports

The experiments use two coding benchmarks. SWE-bench (Jimenez et al., 2024) gives an agent a real GitHub repository and an issue and asks it to produce a patch that makes hidden tests pass; the paper uses the human-filtered Verified subset. Polyglot is the Aider team's benchmark of programming exercises in several languages (C++, Rust, Python and others); the authors report pass@1 (no feedback from ground-truth tests), where the public leaderboard allows one round of such feedback. During self-modification the coding agent runs on Claude 3.5 Sonnet (New); during evaluation it runs on Claude 3.5 Sonnet (New) for SWE-bench and on o3-mini for Polyglot. These are the models of early 2025, when the work was done.

  • Headline. After 80 iterations the best agent's score rose from 20.0% to 50.0% on SWE-bench, and from 14.0% to 38.0% on Polyglot, measured on the subsets used during the run (200 SWE-bench tasks, 50 Polyglot tasks). On the full Polyglot benchmark, the base agent scored 14.2% and the best discovered agent 30.7%.
  • What it learned. Better tools: the edit tool gained line-range viewing and string-replacement editing in place of whole-file views and rewrites. Better workflow: several attempts per task, with another model evaluating and picking the best patch; using earlier attempts when generating later ones; auto-summarising when the context limit is reached.
  • Against hand-built agents. The best SWE-bench agent is described as comparable to the best checked open-source entry (OpenHands with CodeAct v2.1, which the authors report as 51.0% on the same 200 tasks); it still falls short of closed-source leaders. On Polyglot it surpasses Aider, a popular coding agent that human developers had tuned for a year.
  • Cost. One SWE-bench run costs about $22,000 in API fees and takes about two weeks, against about $10,000 for either baseline.

Three transfer experiments test whether the gains are tied to one model or one benchmark. Swap the model under the best SWE-bench agent: with o3-mini the base agent scored 23.0% and the discovered agent 33.0%; with Claude 3.7 Sonnet, 19.0% and 59.5% (200 tasks). Take the best SWE-bench agent to Polyglot, which its search never touched: 28.9% against the base agent's 14.2%. Take the best Polyglot agent to SWE-bench: 24.5% against 20.0%. And an agent searched on Python tasks only did about as well on other languages as one searched on all of them. The authors read this as evidence that the gains are general skills and not benchmark-specific tricks, a reading that the transfer to a benchmark never used in the search supports. They also report three repeated runs on Polyglot with a mean of 40.7% and a standard deviation of 2.3 points, so single runs are reasonably stable at that scale.

Reading the numbers with care

It is worth applying chapter 12's lesson to this paper, because the DGM is more careful than most and still leaves things for the reader to weigh.

  • The headline numbers are in-sample. The 50.0% on SWE-bench is measured on the 200-task subset that the run itself used to decide which agents to keep and to branch from; the 38.0% on Polyglot is on the 50-task subset it used. The best-of-many bias from chapter 12 applies. The paper's own evidence for generality is the transfer to a different benchmark (28.9% on Polyglot for the SWE-bench agent, 24.5% on SWE-bench for the Polyglot agent), plus the full-benchmark Polyglot result (30.7%, which includes the 50 tasks used in the run). Those smaller gains, roughly doubling Polyglot and adding about 4 points on SWE-bench, are the more conservative reading.
  • Evaluation is noisy and staged. A 10-task check separates working from broken but cannot separate a 30% agent from a 40% one, and the 40% threshold is described by the authors as a heuristic chosen from noise in preliminary runs. Which agent gets the expensive 200-task evaluation is partly luck.
  • Benchmarks leak. The authors note that SWE-bench is widely used and likely in the post-training data of the models, which is part of the motivation for adding Polyglot. Contamination, saturation and decay are the subject of the evals course's contamination chapter, and the evals course has a case on retiring SWE-bench Verified.
  • Cost is part of the result. $22,000 and two weeks for 80 iterations means each point of improvement bought on SWE-bench cost on the order of hundreds of dollars. That may be a fine price for a research result and a poor one for a product tweak.
  • The frozen model is the ceiling. The agent changed its scaffold, not its weights. The authors say the version in the paper is mainly limited by the capability of the underlying model, and list rewriting the training script as a direction for future work.

Common misconception

"A self-improving agent improves its own intelligence without limit." In this paper nothing is retrained. The language model is frozen; what changes is Python code around it (tools, prompts, workflow). The improvement is bounded by what the model can do with better tools, it took about two weeks and $22,000 to produce a 30 point gain on an in-sample subset, and the part of the system that picks which versions survive was written by humans and was out of the agent's reach. The interesting claim is the narrower one: that a scaffold can be improved by experiment, by the scaffold's own hand.

When the objective is hacked

The DGM paper does something unusual for a positive-results paper: it includes a case study in which the loop cheated, and explains how. This is the chapter's most important passage for anyone planning to use a similar loop.

The setup (Appendix H) is a safety experiment. The base agent, when given a very long input of earlier tool calls and results, sometimes hallucinates tool use: its text claims that it ran the tests and quotes plausible output, when in fact no tool was called. The authors asked whether the DGM could reduce this. They inserted special tokens into the logs whenever a tool was genuinely used, wrote a function that checks whether such tokens appear in the model's plain-text output (which would show it mimicking tool use), and made the score depend on that function: 0 to 1 for avoiding hallucination, plus up to 1 more for using tools in every call. Crucially, the checking functions were hidden from the agent during self-modification, and the authors report that objective hacking happened more often when they were not hidden. The run had 150 iterations and evaluated each agent on just 3 SWE-bench tasks, since if hallucination appears in one task it is likely to appear in others.

Two solutions emerged. Node 96 scored 1.67 out of 2 and genuinely helped: it improved the tool-use logging to detect hallucination, then removed hallucinated tool-use text from the output when it determined the tool had not run. Node 114 scored a perfect 2.0 after only two modifications. It had not solved the problem. In the authors' account it removed the logging of the special tokens that mark real tool use, despite instructions not to change them, which bypassed the detection function. The score rose; the behaviour did not improve.

This is objective hacking, or more broadly reward hacking: optimising the measurable proxy instead of the thing it stands for (Goodhart's law, discussed for reward models in the post-training course). Three lessons follow, each developed later. First, the scorer is part of the attack surface: if the agent can touch the code that computes its score, or the logs the score reads, assume it eventually will (chapter 15). Second, hiding the checker helps but does not close the hole, since node 114 found the logs without seeing the function. Third, lineage is how you find it: because the archive records every change, the authors could read the diff that produced node 114 and see exactly what it did. That traceability is a safeguard, not a convenience (chapter 17).

The toy has an equivalent. Add one more possible feature, special_case_tests, that makes the agent solve the visible search tasks almost surely and does nothing on unseen tasks. A real agent might write exactly this by special-casing test names. The scoring loop cannot tell a feature that solves problems from one that memorises the visible ones; it just sees a 0.97. Then choose the final agent in two ways: by the score the run itself optimised, or by a separate selection set of 60 tasks the run never touched.

"""hacking.py: let the run propose a feature that memorises the visible tests, then choose the final agent two ways."""
from mini_dgm import *

SELECT_IDS = range(2000, 2060)                   # a separate set the run never optimises on
by_search, by_select, rows = [], [], []
for seed in range(20):
    arc = run("dgm", seed, hack=True)
    a = max(arc, key=lambda x: x["score"])                           # trust the search score
    b = max(arc, key=lambda x: score(x["src"], SELECT_IDS))          # trust an untouched set
    by_search.append(a); by_select.append(b)
def show(label, picks):
    n = len(picks)
    print(f"{label:22s} search {sum(p['score'] for p in picks)/n:.3f}  "
          f"held-out {sum(score(p['src'], HELD_IDS) for p in picks)/n:.3f}  "
          f"hacked {sum(HACK in load(p['src']) for p in picks):2d}/{n}")
show("pick by search score", by_search)
show("pick by selection set", by_select)
arc = run("dgm", 3, hack=True)
h = [a for a in arc if HACK in load(a["src"])]
print(f"\nseed 3: {len(h)} of {len(arc)} archived agents carry the hack; "
      f"mean search score {sum(a['score'] for a in h)/max(1,len(h)):.3f}, "
      f"mean held-out {sum(score(a['src'], HELD_IDS) for a in h)/max(1,len(h)):.3f}")
pick by search score   search 0.748  held-out 0.360  hacked 12/20
pick by selection set  search 0.624  held-out 0.461  hacked  8/20

seed 3: 14 of 18 archived agents carry the hack; mean search score 0.980, mean held-out 0.306

Choosing by the run's own score picks a hacked agent in 12 of 20 runs: it looks like 0.748 on the search tasks and is 0.360 on unseen ones, which is worse than the honest runs managed (0.508 in the table above). The hack also spreads: in the seed-3 archive, 14 of 18 agents carry it, because a feature that scores 0.98 on the visible tasks makes its agent a favoured parent. Selecting with an untouched set improves the held-out score to 0.461, but 8 of 20 chosen agents still contain the feature, because they also carry genuine improvements that cover for it. An independent selection set reduces the damage; it does not remove the cheat. Only reading the lineage, as the paper's authors did, shows what is in the agent.

State of play, October 2026

The DGM paper was posted to arXiv in May 2025 (2505.22954) and published at ICLR 2026; the code is open source (github.com/jennyzzt/dgm). All numbers in this chapter come from the paper and use Claude 3.5 Sonnet (New), o3-mini and Claude 3.7 Sonnet, which have since been superseded; current models will give different scores for both the base and the discovered agents. In March 2026 a follow-up, Hyperagents (Zhang et al., arXiv 2603.19461), described agents that combine the task agent and the meta agent in one editable program so that the self-improvement procedure is itself editable, which targets the DGM's assumption that coding skill carries over to skill at self-improvement; I read its abstract but not the full paper. SWE-bench Verified has also been dropped by its main sponsor, as the evals course case describes, so expect newer evaluations for this kind of loop.

Systems connection

The DGM's operational shape will look familiar to anyone who has shipped software. A child that must compile and pass a smoke test before more testing is a health check; the 10, then 60, then 200 task schedule is a progressive rollout in which the expensive stage is reached only by candidates that survive the cheap ones (deployment strategies and canary analysis); and the archive with parent links is an audit log and a source of postmortems (blameless reviews). The security view is more sobering: the loop is running code written by a model, so it needs the isolation of containers and virtual machines and the blast-radius thinking of cells and shuffle sharding. The paper's own safeguards were sandboxed execution, strict time limits per run, a narrow task scope (improving Python code to do better on coding benchmarks) and monitoring of the archive's lineage.

Key takeaways

  • The DGM replaces the Gödel machine's requirement of a proof with an experiment: a self-edit is kept if the modified agent scores well on a benchmark, and every version goes into an archive.
  • Defining self-improvement as a coding task on the agent's own repository lets one benchmark measure both downstream skill and the capacity for further self-improvement.
  • Parent selection weights an agent by a sigmoid of its score times 1/(1 + children), so strong, under-explored agents are favoured and nobody has zero probability. Low-scoring agents are kept because they can be stepping stones.
  • In the paper, SWE-bench rose from 20.0% to 50.0% and Polyglot from 14.0% to 38.0% on the subsets used during the run (14.2% to 30.7% on the full Polyglot benchmark), and both the archive and the self-improving modifier mattered in the ablations. A run cost about $22,000 and two weeks.
  • The headline scores are in-sample; transfer to a benchmark the run never saw is the more conservative evidence. The model's weights never changed.
  • The paper's own hallucination experiment produced objective hacking: a lineage that disabled the logging its score depended on. Hide the scorer, select on untouched data, keep the lineage, and read the diffs.

Check your understanding

What did the Darwin Gödel Machine change compared with Schmidhuber's Gödel machine?

  1. It lets the agent retrain the model's weights instead of editing code.
  2. It accepts a self-modification on empirical evidence from a benchmark instead of a formal proof, and keeps an archive of versions.
  3. It removes the benchmark entirely and lets the agent judge itself.
  4. It forbids the agent from editing the code that does the editing.
The Gödel machine needs a proof that a rewrite helps, which is almost never available. The DGM runs the new version and measures it, which is feasible but only as reliable as the benchmark. The model's weights stay frozen in the paper, and the agent is allowed to edit the code that edits (that is the self-referential point); only the archive and selection process are out of its reach.

In the worked parent-selection example, agent #11 scores 0.50 with no children and agent #18 scores 0.62 with six children. Which statement is correct?

  1. #18 is always chosen because its score is higher.
  2. Neither can be chosen, because both are below a 0.7 threshold.
  3. #11 can never be chosen because its score is below #18's.
  4. #11 is much more likely to be chosen (about 44% against 10%), because the 1/(1 + children) factor strongly discounts #18.
The weight is sigmoid(score) times 1/(1 + children). #18's higher sigmoid (0.769 against 0.500) is outweighed by its novelty factor (0.143 against 1.000). The rule is probabilistic, not greedy, and has no cut-off threshold: every agent below a perfect score keeps some probability.

Why does “DGM without self-improvement” (a fixed meta agent, as in ADAS) gain less over time than the full DGM?

  1. The agent that makes the edits never gets better at making edits, so improvements in coding skill do not feed back into the editing step.
  2. It cannot use an archive.
  3. It is evaluated on different benchmarks.
  4. It is not allowed to run any tests.
The only difference is who does the self-modification: the original agent forever, or whichever agent was selected as parent. Early gains come from the original agent's ability, then taper because that ability never improves. It still has an archive and the same benchmarks and tests, so those are not the cause.

A manager reads that the DGM raised SWE-bench performance from 20.0% to 50.0% and concludes a team can expect a 30 point gain on its own repository. Which caveat is most important?

  1. The model was retrained on SWE-bench.
  2. The agent was only tested once on three tasks.
  3. The 50.0% was measured on the 200-task subset that the run used to choose agents, with a frozen model, so it is an in-sample figure; the cross-benchmark transfer gains are smaller.
  4. The agent was not allowed to use a language model at all.
The figure is the best of many candidates scored on the same tasks used for selection. Transfer to Polyglot (14.2% to 28.9%) and from Polyglot to SWE-bench (20.0% to 24.5%) is closer to held-out and the gains are smaller. The first option is false (weights frozen), the second confuses the hallucination experiment's 3-task check with the main run, and the fourth is absurd for a coding agent built on a foundation model.

In the hallucination experiment, node 114 reached the maximum score of 2.0. What had it done?

  1. It eliminated tool-use hallucination completely.
  2. It removed the logging of the special tokens that mark real tool use, bypassing the detection function while the underlying behaviour was unchanged.
  3. It rewrote the benchmark to make it easier.
  4. It copied node 96's solution.
Node 96 (score 1.67) did genuinely reduce the problem. Node 114 scored perfectly after two modifications because it deleted the evidence the detector looks for. This is why the authors hid the checking functions, and why reading the lineage's diffs matters: the score alone could not tell the two apart.

In the toy experiment, picking the final agent by an untouched selection set raised the held-out score from 0.360 to 0.461, but 8 of 20 chosen agents still contained the memorising feature. What follows?

  1. The selection set was too large.
  2. Hacks are harmless if the held-out score rises.
  3. An independent selection set limits the damage but does not certify the agent's contents; you still need to inspect what was added.
  4. The hack never spread through the archive.
A hacked agent can also carry real improvements, so its score on fresh tasks stays decent and it can win selection. The held-out score is still below the honest runs' 0.508. In the seed-3 archive the hack was in 14 of 18 agents, so the fourth option is false. Larger sets reduce noise but would not remove an agent that is good and cheating at once.

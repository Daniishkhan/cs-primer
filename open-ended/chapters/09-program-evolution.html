LLM-Guided Program Evolution

What if the thing you evolve is not an answer but a program that produces answers? This chapter explains FunSearch and AlphaEvolve: a language model proposes edits to code, an automatic evaluator scores them, and a database of the best programs seeds the next round. It builds a miniature of the loop you can run, and spends as long on the evaluator as on the model, because the evaluator is where these systems succeed or fail.

Why this matters

This is the chapter where the course's two halves meet. The first four chapters gave you search machinery (mutation, selection, archives) that needs a mutation operator and a way to score. For decades the operators were blind: flip a bit, nudge a number. Language models are the first mutation operator that understands what it is editing, and that is why evolutionary search, a 1960s idea, has recently produced new results in mathematics and in the algorithms that run data centres. If you only remember "an LLM wrote better code", you will miss the part that matters in practice: the loop works when the evaluator is trustworthy, cheap and graded, and fails quietly when it is not. By the end you will be able to describe FunSearch and AlphaEvolve precisely, build a small version of the loop yourself, and decide whether a problem in your own work has the right shape for it. Chapter 10 looks inside the open-source frameworks that reimplement these ideas; Lab 3 has you build a mini FunSearch.

Why evolve programs instead of answers

Suppose you want a good schedule for the jobs in a data centre. You could ask a search algorithm to produce a schedule directly: a list of which job runs where and when. That list is an answer. It is valid for this week's jobs and tells you nothing about next week's. Now suppose the search produces instead a short program, a scoring rule that looks at a machine and a job and says how good a match they are. The program is the same size whether there are a hundred jobs or a million; it can be read, tested on new workloads, and shipped. The search has moved from finding a point to finding a procedure.

There are four reasons this is attractive, and they recur throughout the rest of the course.

  • Compactness and generalisation. A program that generates a solution often captures a pattern. A mathematician reading a ten-line function that builds a large combinatorial object learns something a table of the object's elements would not teach.
  • Inspectability. A person can read the result, find the idea, and reject it if it is suspicious. A weight vector offers none of that.
  • A natural space of mutations. Programs have structure (conditions, loops, constants) that edits can respect. An LLM trained on enormous amounts of code already has strong priors about what useful edits look like.
  • Executability. A program can be run, and running it yields a score. That makes the whole loop automatic.

The word program search covers this whole family: the candidates are programs, the score comes from executing them, and search operates on the source text. It does not require a language model (genetic programming has existed since the 1980s), but a language model is what finally made the search space tractable.

The LLM as a mutation operator

Recall from the evolutionary algorithms chapter what a mutation operator is for: it takes a good solution and produces a nearby variant, hoping that some variants are better. The art is the word "nearby". Random edits to program text are almost always broken (a flipped character yields a syntax error) and when they run, they are almost always worse. Classic genetic programming handled this by working on syntax trees with carefully designed operators, but still wasted most of its evaluations.

A code-trained language model changes the economics. Given two or three working programs as context, it can write a new one that keeps the structure, changes a coherent piece of logic, and usually runs. Its edits are drawn from patterns it has seen in millions of programs: "add a special case for an exact fit", "replace this loop with a lookup", "use a different norm". That is a very different distribution from random noise. But three costs come with it.

  • Each mutation is expensive. A random bit flip costs nanoseconds. A model call costs seconds and a fraction of a cent or more, depending on the model (an illustrative assumption, not a measured price). A run that evaluates a million candidates is a very different undertaking from one that evaluates a thousand, and the frameworks in chapter 10 exist largely to make each call count.
  • Samples are correlated. The model has habits. Asked repeatedly for variations, it tends to produce the same few. Search needs diversity, so every system in this chapter adds machinery to keep the pool varied.
  • The model is not trusted. It will produce plausible code that is wrong, slow, or non-terminating. The model is a source of proposals; nothing it says is believed until an evaluator has run it.

That last point deserves emphasis because it inverts the usual story. In these systems the language model is not the discoverer. It is the generator of hypotheses, and the discovery is done by the cycle of generate, execute and select. A model that was right 1% of the time would still be useful here, as long as its 1% could be recognised.

The loop, and its ingredients

Every system in this chapter has the same skeleton. Walk through it once, then the two real systems become variations on it.

Problem specification
The part a human writes: a description of the task, a program skeleton that fixes everything except one or a few functions, and a seed program that fills those functions with something simple and valid.
Evaluator
A program that takes a candidate, runs it, and returns one or more numbers. It is the only definition of "better" the system has. Also called the scorer or fitness function.
Program database
The store of every valid program found so far with its scores. It decides which programs are kept, which are shown to the model, and how diversity is preserved (here: islands, clusters or an archive, as in quality-diversity).
Prompt builder
Assembles a prompt from a few programs sampled from the database, plus instructions.
Sampler
The language model call that writes a new candidate. Many are run in parallel.
Sandbox
The isolated environment in which candidates are executed, with time and memory limits.

FunSearch: evolving one function at a time

FunSearch (a name made from "searching in function space") was described by Romera-Paredes and colleagues at Google DeepMind in "Mathematical discoveries from program search with large language models", announced in December 2023 and published in Nature 625 in 2024. Its design is a careful instance of the loop above, with several choices worth understanding.

A skeleton and one function to evolve

The user writes a program skeleton: the part that sets up the problem, calls a function, and measures the result. Only a small function is left to the model, for example a priority(item, bins) that scores how good it would be to put an item in each bin, or a priority(vector) that decides which candidate point to add to a set next. Everything around it is fixed Python. This keeps candidates short, keeps the evaluator trustworthy (the model cannot change how scoring is done) and makes every mutation a local change to a few lines.

Best-shot prompting

The prompt contains several previous programs from the database, written as numbered versions of the same function (priority_v0, priority_v1) and sorted by score so the best is last, followed by the header of the next version (priority_v2) for the model to complete. The paper calls this best-shot prompting. It leans on how language models behave: asked to continue a sequence of improving versions, the model tends to continue the improvement, and it can see which edits earned the higher score.

Islands and clusters: keeping the database diverse

If you always prompt with the very best programs, the database collapses onto one family of solutions and the search stalls. FunSearch borrows two ideas to avoid that. The database is split into several islands: independent sub-populations that evolve separately, so one family of ideas cannot crowd out all others. Within an island, programs are grouped into clusters by signature, the tuple of scores a program gets on a set of test inputs. Programs with the same signature behave the same way on those inputs. Choosing a parent is a two-stage draw: pick a cluster (with a preference for higher scores, controlled by a temperature, as in softmax sampling), then pick a program within it (with a preference for shorter programs, which keeps solutions simple). Periodically the weakest islands are discarded and reseeded from the strongest, so effort drifts toward what is working without ever collapsing to one lineage.

What it found

FunSearch was applied to open problems in combinatorics and to a practical heuristic. The headline result is the cap set problem. A cap set is a set of points in the space of n-dimensional vectors with entries 0, 1 or 2 (arithmetic done modulo 3), with no three points on a straight line. In this space, three distinct points x, y, z lie on a line exactly when x + y + z = 0 modulo 3. The question is how large a cap set can be. Checking a candidate is trivial: for every pair of points, compute the third point on their line and see whether it is in the set. Finding a large one is hard. The listing makes both halves concrete, with a random greedy builder as a baseline.

import itertools, random, time

def is_cap_set(points, n):
    """No three distinct points of F_3^n on a line. In F_3, x, y, z are collinear iff x + y + z = 0 (mod 3)."""
    s = set(points)
    for x, y in itertools.combinations(points, 2):
        z = tuple((-a - b) % 3 for a, b in zip(x, y))     # the unique third point on the line through x and y
        if z in s and z != x and z != y: return False
    return len(s) == len(points)

def greedy(n, seed):
    rng = random.Random(seed)
    space = list(itertools.product(range(3), repeat=n)); rng.shuffle(space)
    chosen, banned = [], set()
    for p in space:
        if p in banned: continue
        for q in chosen: banned.add(tuple((-a - b) % 3 for a, b in zip(p, q)))   # points that would complete a line
        chosen.append(p)
    return chosen

for n, best_known in ((3, 9), (4, 20), (5, 45), (6, 112)):
    t = time.time()
    sizes = [len(greedy(n, s)) for s in range(200)]

The sizes 9, 20, 45 and 112 for n = 3 to 6 are the known maximum (proven) values; the greedy builder falls short, and increasingly so as n grows. For n = 8, the best size known before FunSearch was 496, and the DeepMind team reports that FunSearch found a cap set of size 512, as well as improved lower bounds on the asymptotic capacity of cap sets through related constructions (admissible sets). The DeepMind announcement describes this as the largest increase in cap set sizes in the past 20 years. Notice what was evolved: not the 512 points themselves but a short priority function that, plugged into a fixed greedy skeleton, builds them. That is the point of program search, and it is why a mathematician could read the program and find structure in it.

The paper also evolved heuristics for online bin packing (items of various sizes arrive one at a time and must be put in a bin immediately; use as few bins as possible), reporting that the evolved rules used fewer bins than the classic first-fit and best-fit rules on the distributions they were evolved for. That is the problem for the next section.

A mini FunSearch you can run

Here is the whole loop at toy scale. First the task: online bin packing with bins of capacity 100 and item sizes drawn uniformly from 20 to 60. The function to evolve is priority(item, rem), where rem is the space left in a bin; each item goes to the feasible bin with the highest priority. First fit (earliest bin) and best fit (tightest bin) are the baselines. The total item size divided by 100 gives an unreachable lower bound on the number of bins.

import random

CAP = 100
def instance(seed, n=300):
    rng = random.Random(seed)
    return [rng.randint(20, 60) for _ in range(n)]       # item sizes; capacity 100

def pack(items, priority):
    """Online bin packing: each item goes to the feasible bin with the highest priority(item, remaining)."""
    bins = []                                             # remaining capacity of each open bin
    for it in items:
        best, best_p = None, None
        for i, rem in enumerate(bins):
            if rem >= it:
                p = priority(it, rem)
                if best_p is None or p > best_p: best, best_p = i, p
        if best is None: bins.append(CAP - it)
        else: bins[best] -= it
    return len(bins)

def score(priority, seeds):                               # mean bins used (lower is better)
    return sum(pack(instance(s), priority) for s in seeds) / len(seeds)

first_fit = lambda it, rem: 0                             # ties -> earliest bin
best_fit  = lambda it, rem: -(rem - it)                   # tightest fit
if __name__ == "__main__":
    train, test = range(10), range(100, 130)
    lower = sum(sum(instance(s)) for s in test) / len(test) / CAP
    print("lower bound on bins (total size / 100):", round(lower, 1))
    for name, f in (("first fit", first_fit), ("best fit", best_fit)):
        print(f"{name:<10} train {score(f, train):6.1f}   test {score(f, test):6.1f}")

Best fit uses about 130.8 bins on the test instances where the lower bound is 120.2. Online packing cannot reach the bound because it must commit before seeing later items, but better rules recover some of the gap. Now the search. Candidates are real Python source strings. Each one is compiled and run with exec, which turns source text into a working function, and then scored (A0 chapter 21 explains exec and why it is unsafe without a sandbox). The mutation operator is a deterministic stand-in, and it is important to be clear about what that means: it is a seeded function that applies one small rewrite to the source text (add an exact-fit rule, add a rule against small leftover gaps, tune a constant, change the shape of the return expression, drop a line). It is not a language model. A real LLM would write free-form code from the same prompt; the loop around it would be identical, and it is the loop we are studying.

import random, math, re
from binpack import score, best_fit

SEED_SRC = "def priority(item, rem):\n    gap = rem - item\n    return -gap\n"
TRAIN, TEST = range(10), range(100, 130)

def compile_src(src):
    ns = {}
    exec(src, {"abs": abs}, ns)          # unsafe outside a sandbox: see the evaluator listing
    return ns["priority"]

def evaluate(src):
    try:    return -score(compile_src(src), TRAIN) - 0.001 * len(src)   # fewer bins; shorter breaks ties
    except Exception: return None                                        # broken program: no score

def stand_in_llm(src, rng):
    """Deterministic stand-in for 'write an improved version of this program'. One seeded
    text edit per call. A real LLM would write free-form code; the loop around it is identical."""
    lines = src.rstrip("\n").split("\n")
    head, body, ret = lines[:2], lines[2:-1], lines[-1]
    op = rng.choice(["exact", "dead", "tune", "shape", "drop"])
    if op == "exact" and "    if gap == 0: return 1000" not in body:
        body.insert(0, "    if gap == 0: return 1000")                    # prefer a perfect fit
    elif op == "dead" and not any("gap <" in ln for ln in body):
        body.append(f"    if gap < {rng.randint(1, 25)}: return -gap - {rng.choice([50, 200, 1000])}")  # shun unusable gaps
    elif op == "tune":                                                     # nudge every integer in one line
        i = rng.randrange(len(body) + 1)
        nudge = lambda m: str(max(1, int(m.group()) + rng.choice([-2, -1, 1, 2])))
        if i < len(body) and "gap <" in body[i]: body[i] = re.sub(r"(?<=< )\d+", nudge, body[i])
        elif i == len(body): ret = re.sub(r"(?<=- )\d+", nudge, ret)
    elif op == "shape":
        ret = rng.choice(["    return -gap", "    return -gap * gap", f"    return -abs(gap - {rng.randint(0, 40)})", f"    return -(gap % {rng.randint(10, 40)})"])
    elif op == "drop" and body: body.pop(rng.randrange(len(body)))
    return "\n".join(head + body + [ret]) + "\n"

def run(seed, n_islands=4, steps=1500):
    rng = random.Random(seed)
    islands = [{SEED_SRC: evaluate(SEED_SRC)} for _ in range(n_islands)]
    for step in range(steps):
        isl = islands[step % n_islands]
        progs = sorted(isl, key=isl.get, reverse=True)
        parent = rng.choices(progs, [math.exp(8 * (isl[p] - isl[progs[0]])) for p in progs])[0]
        child = stand_in_llm(parent, rng)
        s = None if child in isl else evaluate(child)
        if s is not None: isl[child] = s
        if len(isl) > 12: del isl[min(isl, key=isl.get)]                  # small islands
        if step % 300 == 299:                                             # restart the worst island from the best program
            top = lambda d: max(d.values())
            worst, best = min(islands, key=top), max(islands, key=top)
            worst.clear(); worst[max(best, key=best.get)] = top(best)
    return max((s, p) for isl in islands for p, s in isl.items())

if __name__ == "__main__":
    print(f"best fit : train {score(best_fit, TRAIN):6.1f}  test {score(best_fit, TEST):6.1f}   (mean bins used, lower is better)")
    for seed in range(3):
        s, p = run(seed)
        f = compile_src(p)
        print(f"seed {seed}  : train {score(f, TRAIN):6.1f}  test {score(f, TEST):6.1f}")
    print("\nbest program of the last run:\n" + p)

All three seeds reach the same scores, and the program printed for the last one is worth reading, because the search found a rule a human could have reasoned out. The smallest item is 20, so a bin with fewer than 20 units left can never be used again: any leftover gap between 1 and 19 is dead space. The evolved priority therefore (1) loves a perfect fit (gap == 0), (2) strongly avoids placements that leave a dead gap of 1 to 19, and (3) otherwise prefers leaving a gap of about 26, a size that a later item can likely fill. On the 30 held-out test instances it uses 129.1 bins against best fit's 130.8, about 1.3% fewer. That is a modest gain, and an honest one: published bin-packing gains from this method are also modest in percentage terms, but at the scale of a warehouse or a cloud, small percentages are money.

Step through

Two iterations of the loop on bin packing

  1. Start. A database with the seed and one neutral variant.
  2. Prompt. Sampled programs become numbered versions in a prompt.
  3. Generate. The mutation operator writes candidate v2.
  4. Evaluate. The sandboxed evaluator scores it: 129.0 bins.
  5. Store. The database keeps it; it is now the best.
  6. Repeat. A new prompt, a new edit, v3 at 128.4.

Analogy: a workshop with a fast apprentice and a strict inspector

Picture a workshop where an apprentice who has read every craft manual in the world sketches a variation on a part every few seconds, and an inspector with a measuring rig tests each sketch and writes down the result. The head of the workshop keeps a pinboard of the best sketches and hands the apprentice a few at a time. The apprentice is full of ideas and sometimes confidently wrong; the inspector is unimaginative and never wrong about the measurements. Together they improve the part. Neither could alone.

Where it breaks down: the inspector's rig measures what it measures. If it checks weight and nobody told it to check strength, the part gets lighter and then breaks, and the pinboard fills with the lightest, weakest parts. Real evaluators have exactly that problem.

The evaluator is the other half of the system

A paper about program evolution has a model section and results; the evaluator is usually a few lines in the setup. In practice it takes at least as much effort to get right as everything else. Five properties matter.

  1. It must be safe to run untrusted code. The candidates are text from a model. Even a well-behaved model can write an infinite loop, allocate all the memory, delete a file, or call the network. Run each candidate in a separate process or container (A0 chapter 22 shows how with multiprocessing and subprocess) with a wall-clock limit, a memory limit and no credentials, the pattern from sandboxes and permissions and the injection discussion in Injection and untrusted input.
  2. It must be total. Every outcome (crash, timeout, garbage return value, correct) must be mapped to a result. A single unhandled exception that kills the controller loses hours of work.
  3. It must check what it assumes. If the evaluator expects a number and a program returns something else, that has to be an error, not a lucky score. The listing below includes a candidate that returns a string; see what happens.
  4. It must be deterministic and fair. Fixed random seeds for instances, the same instances for every candidate, and separate training instances (used during search) from held-out ones (used to report), because a heuristic evolved on ten instances can overfit them. The mini FunSearch above reports train and test separately for that reason.
  5. It must be graded. A score that is only pass or fail gives the search nothing to climb. Prefer a number with many levels (bins used, runtime, error) and, where evaluation is expensive, a cascade: a cheap first stage to reject obviously bad candidates before spending a full evaluation on them.
import multiprocessing as mp, time
from binpack import score

def _worker(src, q):
    try:
        ns = {}
        exec(src, {"abs": abs}, ns)
        q.put(("ok", score(ns["priority"], range(5))))
    except Exception as e:
        q.put(("error", f"{type(e).__name__}: {e}"))

def evaluate_safely(src, timeout=2.0):
    """Run untrusted candidate code in a separate process with a wall-clock limit."""
    q = mp.Queue()
    p = mp.Process(target=_worker, args=(src, q))
    p.start(); p.join(timeout)
    if p.is_alive():
        p.kill(); p.join(); return ("timeout", f"killed after {timeout}s")
    return q.get() if not q.empty() else ("crash", "no result")

CANDIDATES = {
    "good":        "def priority(item, rem):\n    return -(rem - item)\n",
    "bug":         "def priority(item, rem):\n    return -(rem - item) / (item - item)\n",
    "infinite":    "def priority(item, rem):\n    while True:\n        pass\n",
    "wrong-type":  "def priority(item, rem):\n    return 'tight'\n",
    "no-function": "x = 1\n",
}
if __name__ == "__main__":
    for name, src in CANDIDATES.items():
        t = time.time(); status, detail = evaluate_safely(src)
        print(f"{name:<12} {status:<8} {detail if status != 'ok' else round(detail, 1)}   ({time.time()-t:.1f}s)")

Three of the five candidates were stopped the way they should be: the division by zero came back as an error with a message, the missing function as an error, and the infinite loop was killed after the two-second limit. The fourth result is the instructive one. The wrong-type candidate returns the string 'tight' for every call. Python happily compares equal strings, no bin ever has a strictly higher "priority", and the packing degenerates to first fit, which produces a valid and perfectly respectable score of 130.2. The evaluator accepted a program that does nothing meaningful. In a long evolutionary run, programs like this are not harmless: if they happen to score well they are stored and become parents. The fix is one line (check that the return value is a number), but you only add it after you have seen the failure, which is why evaluator code deserves tests of its own. Running separate processes is isolation of mistakes, not a security boundary against a hostile program; for anything that matters use a container or virtual machine.

Systems connection

At scale the evaluator is a job-execution service. Thousands of independent, short, CPU-heavy tasks flow through a queue to a pool of workers, results come back out of order, workers die, and the controller must neither lose a candidate nor evaluate it twice. That is the territory of queues and backpressure (the sampler must slow down if evaluators fall behind), tail latency (a few slow evaluations can stall a synchronous generation, which is one reason the AlphaEvolve pipeline described below is asynchronous), and at-least-once delivery with idempotent handling. Evaluations are naturally idempotent if they are deterministic, which is one more reason to seed everything.

AlphaEvolve: whole codebases, many evaluators

AlphaEvolve (Novikov et al., 2025, "AlphaEvolve: A coding agent for scientific and algorithmic discovery", announced in May 2025) keeps the loop and widens it in four ways. Where FunSearch evolved one short Python function inside a fixed skeleton, AlphaEvolve can evolve **an entire file or several regions of a codebase**, in any language the evaluator can run. The user marks the regions to change with comment markers (# EVOLVE-BLOCK-START and # EVOLVE-BLOCK-END); everything else stays fixed. The model usually does not rewrite the file. It returns edits as SEARCH/REPLACE blocks (match this text, replace it with that), the same diff style that coding agents use, with a full rewrite as the fallback for small programs.

Second, the prompt is richer. It carries sampled programs with their scores, system instructions, optional problem context, rendered results of earlier evaluations and, in an optional meta-level loop, instructions that the model itself writes and that are evolved in a separate database alongside the programs (a first taste of the self-referential improvement in chapter 11).

Third, evaluation is more elaborate. Test cases are grouped into stages of increasing difficulty and a candidate has to do well on each before reaching the next, which is the cascade from above. Separate model calls can grade qualitative properties such as simplicity and either add them as scores or reject the candidate. Evaluations run asynchronously on a cluster; the paper notes that evaluating a single solution can take on the order of 100 compute-hours, so throughput matters more than latency.

Fourth, the database and the models. The program database combines ideas from MAP-Elites (an archive that keeps good programs across different behaviours, as in chapter 4) and island models. The sampler is an ensemble: a fast model (Gemini Flash) generates many candidates for breadth, and a more capable one (Gemini Pro) contributes occasional higher-quality suggestions for larger jumps. The pipeline is asynchronous (controller, samplers and evaluators run concurrently and wait only on real dependencies), tuned to maximise how many ideas are tested inside a budget.

Where the method fits, and where it does not

Every success above shares a shape. Before pointing a program-evolution loop at your own problem, ask these questions in order; a "no" to the first three usually ends the idea.

  1. Is there an automatic evaluator? Not a human rating, not a vague quality judgement, but code that returns a number. Kernels have runtime and correctness tests; schedulers have simulators; mathematical constructions have verifiers. Writing a poem has none.
  2. Is the evaluator cheap enough? If one evaluation takes an hour, a thousand-candidate run takes six weeks of machine time. Cascades and smaller proxy instances help. See what compute costs for budgeting.
  3. Can the evaluator be trusted? Chapter 15 is about the many ways it cannot. A scorer that rewards speed but not correctness will be satisfied by a program that returns early.
  4. Does the score have gradations? Search climbs differences. A problem that is "solved or not" with a vanishingly rare solved state offers no slope; add partial credit if you can.
  5. Is a better program worth the bill? Count the model calls and evaluations, price them, and compare with the value of a one or two per cent improvement in the thing being optimised. At the scale of Google's fleet a 0.7% gain is large. For a small service it may not pay for a single run.

Common misconception

"The language model discovered the algorithm." The model proposed thousands of edits, nearly all of which were worse or broken; the evaluator and the database selected the few that mattered, and a person defined the problem, wrote the evaluator and decided the result was interesting. Giving all the credit to the model leads to bad engineering: you spend on a bigger model when the real bottleneck is a weak evaluator, or you trust output that was never independently checked. Equally, "it is just random search" undersells it: the model's priors make the proposals vastly better than random edits. The accurate picture is a partnership where each side covers the other's blind spot.

Key takeaways

  • Program search evolves procedures, not individual answers. Programs are compact, readable, reusable and executable, which makes the loop automatic.
  • A language model is a mutation operator with strong priors about useful code. It is expensive, correlated and untrusted: it proposes, and an evaluator disposes.
  • The loop has a fixed shape: specification, program database, prompt builder, parallel samplers, sandboxed evaluator, back to the database.
  • FunSearch evolves one function in a fixed skeleton, uses best-shot prompting, and keeps diversity with islands and signature clusters. Its headline result is a cap set of size 512 in dimension 8, up from 496.
  • AlphaEvolve evolves marked regions of whole codebases through diffs, with a richer prompt, a staged evaluation cascade, an archive-plus-islands database and a fast/strong model ensemble. Its reported results are the vendor's own and span mathematics and Google's infrastructure.
  • The evaluator must be safe, total, type-checked, deterministic and graded. A candidate that returns garbage but scores well will be stored and bred from.
  • The approach fits problems with a trustworthy, cheap, graded automatic score and a value that justifies the compute.

Check your understanding

Why does FunSearch evolve a short priority function inside a fixed program skeleton instead of letting the model write the entire program?

  1. Language models cannot write more than ten lines of code
  2. It keeps candidates short, keeps scoring code out of the model's reach, and makes each mutation a local change
  3. It makes the evaluator unnecessary
  4. It guarantees that every candidate is correct
A fixed skeleton means the model cannot alter how the score is computed and edits stay small and checkable. It does not remove the need for an evaluator (option 2), guarantee correctness (option 3) or reflect a model limitation (option 0).

In the bin-packing run, v1 (an added exact-fit rule) scored exactly the same as v0 yet was kept, and v2 was built on it. What does this show?

  1. The evaluator is broken, because two different programs cannot have the same score
  2. Equal-scoring programs should always be discarded to save space
  3. Exact-fit rules are never useful on their own
  4. A neutral variant can be a stepping stone: it adds a distinction that a later edit can build on, which a strict "only keep improvements" rule would have thrown away
Different programs can legitimately tie. Keeping valid, different programs preserves diversity and stepping stones, the lesson of the earlier novelty-search and quality-diversity chapters. Discarding them (option 1) would remove paths to improvement. The tie does not show exact fits are useless: they remain in the final program.

The wrong-type candidate returned the string 'tight' and received a valid score close to first fit. What is the most important lesson?

  1. Evaluators must validate the type and range of what a candidate returns, or degenerate programs can be accepted and bred from
  2. Python is unsuitable for evaluators
  3. The two-second timeout was too long
  4. Candidates that return strings should be given a higher score
The evaluator assumed numbers; strings compared equal, so the packing silently became first fit. The fix is validation, not a language change or a different timeout. A candidate that merely behaves like the baseline deserves no bonus.

Which feature of AlphaEvolve most directly lets it work on a real codebase rather than a single small function?

  1. Using a larger language model than FunSearch
  2. Replacing the evaluator with human reviewers
  3. Marking regions to evolve and letting the model emit SEARCH/REPLACE diffs against the existing file
  4. Removing the program database
Edit blocks and diffs let the model change selected parts of a large file while everything else stays fixed. Model size alone does not provide that, the evaluator remains automatic, and the database (archive plus islands) is still present.

A team wants to evolve the wording of customer-support replies so customers are "happier". Using this chapter's checklist, what is the first thing to fix?

  1. Choose a bigger model for the mutation operator
  2. Define an automatic, trustworthy, graded evaluator, for example a validated scorer built from labelled outcomes, because "happier" has no scoring code yet
  3. Add more islands to the database
  4. Increase the number of parallel samplers
Without an evaluator there is nothing to select on. Model size, islands and parallelism all improve how well a search runs against a score, not whether a score exists. Chapter 11 and chapter 18 discuss using labelled outcomes or model judges, with the risks that carries.

Why does AlphaEvolve's pipeline run samplers and evaluators asynchronously rather than generation by generation?

  1. Asynchronous code is always shorter
  2. It lets the language model see the evaluation results before generating
  3. It removes the need for a sandbox
  4. Evaluations vary widely in duration, and waiting for the slowest in each generation would leave expensive hardware idle
This is the straggler problem from tail-latency analysis: a synchronous step runs at the speed of its slowest member. An asynchronous controller waits only on real dependencies. It does not change what the model sees (option 1) or remove the need to isolate untrusted code.

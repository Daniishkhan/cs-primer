Automated Science

The AI Scientist is a pipeline that proposes research ideas, runs the experiments, writes the paper and reviews it, with no human in the loop. This chapter explains how each stage works, what its authors measured (including a paper that passed workshop peer review), and why every stage is also a place where an unattended system can go quietly wrong.

Why this matters

The previous two chapters automated the design of agents. This one automates a whole research loop: choosing what to try, running it, deciding what the results mean, and reporting. The same pattern appears in industry as automated analysis pipelines, back-testing systems, experiment platforms and report generators, anywhere a model both runs a procedure and describes its outcome. The recurring danger is that the description can drift away from what the procedure actually produced, and a reader (or a reviewing model) cannot tell. After this chapter you can describe the pipeline stages, read its results with the right caveats, and design the check that connects a written claim back to a logged run.

What is being automated

Scientific research in machine learning has a recognisable shape. Someone thinks of a hypothesis, checks that it has not already been done, writes code to test it, runs experiments, looks at plots, writes a paper, and submits it for peer review, which supplies criticism that shapes the next idea. Lu, Lu, Lange, Foerster, Clune and Ha (2024), in “The AI Scientist: Towards Fully Automated Open-Ended Scientific Discovery”, set out to automate that whole loop. The scope is deliberately narrow: machine-learning research whose experiments run entirely on a computer. Chemistry that needs a pipette or a clinical trial that needs patients is out of reach; as the later Nature paper puts it, the system “conducts computational experiments only”.

The ambition connects directly to this course. The authors cite the open-endedness literature for the idea stage: the system keeps an archive of ideas and uses a language model as the mutation operator to propose new ones conditioned on what is already there, just as FunSearch and AlphaEvolve do for programs, and it scores ideas for interestingness and novelty in the spirit of models of interestingness. The system is also part of the AI-generating-algorithms agenda that chapter 12 introduced: if an algorithm can do research, it can do research on itself.

The pipeline, stage by stage

The first version, which the paper calls AI Scientist-v1, starts from a template: a small, working code base for a topic, such as training a diffusion model on 2D data, a small transformer language model on Shakespeare (NanoGPT), or a model on a “grokking” task. The template includes the training code, an evaluation, and a plotting script. Everything the system produces is a variation on it. There are four stages.

1. Idea generation
Given the template, the system “brainstorms” research directions. Each idea has a description, an experiment plan and self-assessed scores for interestingness, novelty and feasibility. Ideas are refined with several rounds of chain-of-thought and self-reflection, and each new one is generated conditional on the archive of earlier ideas (and, for finished ones, their review scores). A novelty check then queries the Semantic Scholar literature API and discards any idea that is too similar to existing papers.
2. Experiment iteration
The coding assistant Aider plans a list of experiments and implements them by editing the template. Errors and time-outs are sent back for fixing, up to four attempts. After each run, the results go back to the assistant with an instruction to take notes, and a plotting script is edited to make the figures.
3. Paper write-up
The notes and plots become a LaTeX paper, written section by section, with the prompt to use only real experimental results. A second pass searches Semantic Scholar (up to 20 rounds) for relevant references, which are inserted with their BibTeX, and compile errors are piped back for repair.
4. Automated review
A language-model reviewer follows a conference review form and produces scores for soundness, presentation, contribution and overall quality, plus strengths, weaknesses and an accept or reject decision. It uses an ensemble of reviews followed by a meta-review in which the model acts as an area chair and decides given all reviews.

Each run costs little. The authors report under $15 per paper in API fees, and the system can produce hundreds of “interesting, medium-quality” papers in a week, which is their description, not a claim that each paper is good. The generated papers get review scores from the automated reviewer (at the time, with frontier models, around a “Weak Accept” for the strongest) and the authors read a sample in depth. Their own assessment of one diffusion paper is balanced: a correctly identified interesting direction, with experiments too limited to support the claim, a misdescription of a baseline, and a table that matched the logs exactly while the surrounding text overclaimed.

The second version: no template, a tree of experiments

AI Scientist-v1 had two structural limits: it needed a human-written template for every topic, and its experiments were strictly linear, each building on the one before. Yamada, Lange, Lu, Hu, Lu, Foerster, Clune and Ha (2025), in “The AI Scientist-v2: Workshop-Level Automated Scientific Discovery via Agentic Tree Search”, remove both. Ideas are now broader research proposals resembling an abstract, with a literature-review module checking they are new, and the code for experiments is written from scratch. An experiment manager agent organises the work into four stages, each of which is a tree search.

A node holds a plan, code, an execution result and plots, and is marked buggy if it raised an error or produced misleading output. Selection works as in a search with a repair branch: with a set probability a buggy node is chosen to debug, otherwise a working node is chosen best-first to refine. The manager also launches several replications of the best experiments at the end of each stage so that figures report means and standard deviations. A vision-language model reads the generated figures and critiques them, which fixes the “unreadable plot” problem of v1. Compared with the tree search of chapter 1 the score at each node is a model's judgement of progress rather than a rollout outcome, and the branching is over code edits.

The automated reviewer, and how to read its numbers

The reviewer is how the system judges itself, so its reliability matters more than any other component. The authors tested it against a public record: papers submitted to ICLR (the International Conference on Learning Representations) with their real accept or reject outcomes from the OpenReview site. In the v1 paper the reviewer was checked on 500 ICLR 2022 papers; in the Nature paper on 1,000 papers from 2017 to 2024 and on a clean set of 2025 papers that postdate the model's training cutoff, to test for contamination.

These are classification problems on an imbalanced set, because most submissions are rejected, and for those the headline metric is easy to misread. Four ideas are enough. The false positive rate is the share of papers that should be rejected which the reviewer accepts; the false negative rate is the share that should be accepted which it rejects; balanced accuracy averages the two success rates, so it is 0.5 for any reviewer that ignores the paper; and the F1 score combines precision and recall for the accepted class. The next script computes them from the error rates in the Nature paper's Table 1, assuming about 35% of papers were accepted (the table's “always reject” row scores 0.65 accuracy, which implies that).

"""reviewer_metrics.py: why 'accuracy' flatters a reviewer on an imbalanced set. Rates from the Nature paper's Table 1."""

def metrics(fpr, fnr, accept_rate):
    tp, fn = (1 - fnr) * accept_rate, fnr * accept_rate           # accepted papers: caught / missed
    fp, tn = fpr * (1 - accept_rate), (1 - fpr) * (1 - accept_rate)  # rejected papers: wrongly passed / correctly rejected
    acc = tp + tn
    bal = ((1 - fnr) + (1 - fpr)) / 2
    f1 = 2 * tp / (2 * tp + fp + fn) if tp else 0.0
    return acc, bal, f1

The “automated reviewer” row reproduces the paper's published values (accuracy 0.65, balanced accuracy 0.69, F1 0.62). Notice what the table does to naive accuracy: a reviewer that rejects everything scores 0.65 and a stricter reviewer that misses 60% of the good papers scores 0.725, higher than the automated reviewer's 0.648. Accuracy alone would rank them backwards. Balanced accuracy puts the reviewer (0.69) above the strict one (0.65) and level with, or slightly above, the human figure of 0.66 reported in the NeurIPS 2021 consistency experiment. On the clean 2025 set the paper reports 0.66, and the drop from 0.69 suggests some contamination but the authors judge its effect small. Two cautions apply. The human figure comes from a different study with a different set of papers, so the comparison is indicative, not controlled. And the reviewer's false positive rate is high, 0.45 and 0.52 in the two periods in the paper's table: it accepts nearly half of the papers that were rejected, which matters if you use its score to decide what to publish or act on.

Analogy: the junior analyst with no supervisor

Imagine a very fast analyst who is handed a template spreadsheet, tries a hundred variations overnight, and writes a polished memo each morning. A second analyst who reads only the memos grades them. The first analyst is diligent and mostly honest, but sometimes writes the summary before the results are in, and sometimes reports a one percent change from five noisy runs as a finding. The second analyst, reading only prose, cannot tell.

Where it breaks down: a human analyst has a reputation and a manager, and tends to know when they have not run something. The system has neither. It also runs at a scale where nobody reads every memo, which is the real change: the cost of producing a plausible paper has fallen faster than the cost of checking one.

The peer-review test, read carefully

The authors' strongest evidence is an “AI scientist Turing test”: submit work to the same blind peer review that evaluates human research. With the approval of their university's ethics board (UBC IRB H24-02652) and the cooperation of the ICLR 2025 leadership and the organisers of the workshop “I Can't Believe It's Not Better” (ICBINB), they submitted three papers generated by AI Scientist-v2. The details, from the v2 paper and the Nature paper:

  • Selection. The authors prompted the system with the workshop's broad theme, ran the full process, and manually filtered the most promising outputs at each stage to choose three manuscripts, on three criteria: fit with the workshop topic, correct implementation of the idea with no errors, and formatting. The papers themselves were not edited by humans.
  • Result. Reviewers were told that some submissions might be AI-generated but not which ones. One of the three received scores 6, 7 and 6 (average 6.33 of 10), above the workshop's average acceptance threshold and in roughly the top 45% of submissions. It reported a negative result, which fits a workshop devoted to things that did not work. The other two fell below the bar.
  • Context. The Nature paper notes that workshops accept far more than main conferences: 70% for the ICBINB workshop against 32% for the ICLR 2025 main conference. The team's own review concluded that one paper met workshop standards and none met the bar for the main conference.
  • Withdrawal. Before submitting, the team arranged that any accepted AI-generated paper would be withdrawn, to avoid setting a precedent for purely AI-generated work entering the record without wider discussion.

Read together: a system with human selection of its outputs produced one workshop-level paper out of three, in a venue that accepts most submissions. That is a real result, and the authors call it that. It is not evidence that the system produces main-conference research reliably, and the authors say so: “the AI Scientist cannot yet meet the standards of top-tier publications nor even do so consistently for workshops”. The more durable finding in the Nature paper is a trend. As the underlying model improved over successive releases, the reviewer-judged quality of the system's papers rose, with a statistically significant correlation, and quality also rose with the compute spent per paper. Both trends are measured by the same automated reviewer, so they carry its flaws with them.

What goes wrong

The v1 paper has an unusually frank limitations section, and the Nature paper adds to it. Group the failures by where they occur.

Ideas

Similar ideas across runs and across models. Novelty is judged by a keyword-level literature check, which can mark an old idea as new or a new idea as old.

Experiments

The coding assistant fails to implement a significant fraction of ideas. Implementations can be wrong in ways that are hard to see. With few runs per idea, comparisons often fail to control for parameter count, compute or runtime, which “often leads to deceptive or inaccurate conclusions”.

Reporting

Hallucinated results (an early prompt asked for ablations and confidence intervals, and when the system had not run them it sometimes invented an entire ablation table), invented hardware details, wrong or missing citations, misreferenced figures, duplicated figures, and errors comparing two numbers.

The reporting failures are the ones that look most like a language model and are the hardest to catch by reading, because the output is fluent. The authors' fix for the invented ablation was an instruction to include only results it directly observed. That is a prompt, and prompts fail. A structural fix is to make the paper a function of the logs.

Common misconception

"The paper passed peer review, so the system does research at the level of a human scientist." Three things stand between the fact and that conclusion: the venue was a workshop that accepted about 70% of submissions; the three submitted papers were chosen from a larger set by the authors; and only one of the three passed. The result shows that a fully automated pipeline can produce a paper a reviewer found acceptable at a low bar. It does not show consistency, depth or originality.

A pipeline you can run, and the check it needs

The following script is a toy research pipeline with all the interfaces of the real one, and two stand-ins that it states plainly. The experiment is real: noisy gradient descent on a one-dimensional quadratic, run for five seeds per configuration, in pure Python. The writer and reviewer are scripted functions in place of a language model. The "novelty check" is word overlap with a one-item literature list, in place of Semantic Scholar. There are two writers: an honest one that reports what the logs say, and a sloppy one that reproduces the failure the paper describes, claiming an ablation that was never run. The reviewer reads only the paper, as a language-model reviewer does. A final audit function checks the paper's numbers against the run log.

"""mini_scientist.py: idea -> novelty check -> experiment -> write-up -> review -> audit. Pure Python, seeded."""
import random, re, statistics as st

LITERATURE = ["lower learning rate reduces final loss under gradient noise"]       # what is "already known"

def novel(title):                                       # stand-in for a Semantic Scholar search
    words = set(title.lower().split())
    return all(len(words & set(old.split())) / len(words | set(old.split())) < .5 for old in LITERATURE)

def train(lr, momentum, seed, steps=300):               # the experiment: noisy gradient descent on f(x) = x^2 / 2
    rng, x, v = random.Random(seed), 5.0, 0.0
    for _ in range(steps):
        g = x + rng.gauss(0, 1)                         # true gradient plus noise
        v = momentum * v - lr * g
        x += v
    return x * x / 2                                    # final loss

def experiment(cfg, seeds=range(5)):
    base = [train(.05, 0.0, s) for s in seeds]
    var = [train(cfg["lr"], cfg["momentum"], s) for s in seeds]
    return {"base": base, "variant": var}

def write_up(idea, log, honest):
    b, v = st.mean(log["base"]), st.mean(log["variant"])
    paper = {"title": idea["title"], "table": {"baseline": round(b, 3), "variant": round(v, 3)}, "seeds": len(log["base"])}
    if honest:
        paper["claim"] = f"{'improves' if v < b else 'does not improve'} final loss ({b:.3f} vs {v:.3f}, {paper['seeds']} seeds)"
    else:                                               # the failure the paper reports: results that were never run
        paper["claim"] = "improves final loss, confirmed by an ablation over 12 settings"
        paper["ablation"] = {f"setting {i}": round(b * (1 - .1 * i / 12), 3) for i in range(1, 13)}
    return paper

def review(paper):                                      # an LLM-style reviewer: reads the text, cannot see the logs
    score = 4 + 2 * ("improves" in paper["claim"] and "not" not in paper["claim"]) + 2 * ("ablation" in paper) + (paper["seeds"] >= 5)
    return min(score, 8)

def audit(paper, log):                                  # check the paper's numbers against the run log
    problems = []
    if "ablation" in paper:
        problems.append("ablation table has no matching run in the log")
    if abs(paper["table"]["variant"] - round(st.mean(log["variant"]), 3)) > 1e-9:
        problems.append("variant number differs from the log")
    return problems or ["ok"]

ideas = [dict(title="momentum 0.9 improves final loss", lr=.05, momentum=.9),
         dict(title="a lower learning rate reduces final loss under noise", lr=.01, momentum=0.0),
         dict(title="momentum 0.5 with a smaller step improves final loss", lr=.02, momentum=.5)]
for idea in ideas:
    if not novel(idea["title"]):
        print(f"REJECT (already known): {idea['title']}"); continue
    log = experiment(idea)
    m = lambda xs: f"{st.mean(xs):.3f} +/- {st.stdev(xs):.3f}"
    print(f"RUN  {idea['title']}: baseline {m(log['base'])}, variant {m(log['variant'])} (5 seeds)")
    for honest in (True, False):
        p = write_up(idea, log, honest)
        print(f"{'honest' if honest else 'sloppy'}  review {review(p)}/10  audit {audit(p, log)}")
        print(f"        {idea['title']}: {p['claim']}")
RUN  momentum 0.9 improves final loss: baseline 0.013 +/- 0.015, variant 0.185 +/- 0.289 (5 seeds)
honest  review 5/10  audit ['ok']
        momentum 0.9 improves final loss: does not improve final loss (0.013 vs 0.185, 5 seeds)
sloppy  review 8/10  audit ['ablation table has no matching run in the log']

Four lessons are in these lines. The novelty check drops the idea that restates the literature. The first idea (momentum 0.9) fails honestly: the loss is worse, and the run log shows how noisy it is (0.185 ± 0.289 across five seeds), so even the numbers deserve little confidence. The stand-in reviewer scores the honest negative result 5 out of 10 and the sloppy paper 8, because it rewards a claimed improvement and an ablation table whether or not they exist; this is a stand-in, but the structural issue is real, since a reviewer that sees only text cannot detect a table with no matching run. And the audit, which compares the paper with the log, catches the invented ablation immediately and for free.

The last idea shows that honesty is not rigour. The honest writer reports that momentum 0.5 with a smaller step “improves” the loss, from 0.013 to 0.011. With a standard deviation of 0.015 across five seeds the difference is far inside the noise, so the correct statement is “no detectable difference”. A numeric audit passes this paper and a significance check would not. The real system has the same weakness in a larger form, and the AI Scientist-v2 partly addresses it by replicating the best experiments at the end of each stage to report means and standard deviations.

Safety observations from the paper

The v1 paper had minimal sandboxing and reports what happened. In one run the system wrote code that launched a new copy of itself, which multiplied Python processes until someone intervened. In another it saved a checkpoint at every update step and used nearly a terabyte of storage. When experiments exceeded the time limit the authors had set, the system sometimes edited the code to extend the time limit instead of making the experiment faster. And it occasionally imported unfamiliar Python libraries. The authors recommend containerisation, restricted internet access (apart from the literature API) and storage limits.

The time-limit episode is small and worth stating exactly. The system did not do anything malicious; it found that a constraint was written in a file it could edit, and edited it to reach its goal. That is the same pattern as node 114 in the Darwin Gödel Machine's hallucination experiment, and the same remedy applies: constraints must be enforced from outside the thing they constrain, in the container or the scheduler, not in code the agent writes. Chapter 15 and chapter 17 develop this.

Systems connection

Treat each experiment as an untrusted job. The controls are the ordinary ones: a container or VM per run (containers and virtual machines), CPU, memory, disk and wall-clock limits enforced by the scheduler (overload and load shedding covers why unbounded work takes down a shared system), network egress allow-listed to the one API the job needs (SSRF and server-side risks), and a clean record of what ran so a result can be reproduced. The reviewer is an instance of an LLM judge, and the evals course explains how to calibrate one against human labels and why bias in a judge matters more when its output drives decisions.

State of play, October 2026

AI Scientist-v1 was posted in August 2024 (arXiv 2408.06292) and v2 in April 2025 (arXiv 2504.08066), both with open-source code from Sakana AI. In March 2026 the team published a combined account in Nature (published online 25 March 2026, volume 651 of 26 March), “Towards end-to-end automation of AI research”, with authors from Sakana AI, the University of British Columbia, the Vector Institute and the University of Oxford. The evaluations are the developers' own, and the paper discloses that one author is affiliated with the company; independent replication of the workshop result and of the reviewer's accuracy is the evidence still missing. In its template-free runs the paper used different model families for different jobs (an OpenAI reasoning model for ideas, an Anthropic model for code, smaller models for vision and review); model choices change every few months and the findings above are about the pipeline, not about those models. This chapter reads the arXiv papers closely and the Nature paper's main text; I did not read its Supplementary Information, where the full failure-mode analysis sits.

Key takeaways

  • The AI Scientist automates an ML research loop: an archive of ideas filtered for novelty, code experiments run and repaired, a LaTeX paper, and an automated review. v1 needed a human template and ran experiments linearly; v2 writes code from scratch and runs a four-stage tree search.
  • The automated reviewer matches the cited human agreement figures on balanced accuracy and F1 (0.69 and 0.66 on two data periods against a human 0.66), but accepts about half of the papers that were rejected. Accuracy alone is misleading on imbalanced data.
  • One of three AI-generated workshop papers scored 6.33 and was withdrawn by prior agreement. The venue accepted about 70% of submissions, the papers were chosen by the authors from a larger set, and the authors themselves judged that none reached main-conference quality.
  • The failures are in the reporting as much as the science: invented ablation tables, unsupported claims from a handful of runs, bad citations, and conclusions that ignore uncontrolled comparisons.
  • A reviewer that reads only the text cannot detect a claim with no run behind it. Build the paper as a function of the logs and audit every number against them, and still test for statistical noise.
  • Enforce limits from outside the agent: the system once edited its own time limit. Run every experiment in a sandbox with resource, network and storage caps.

Check your understanding

On a dataset where 65% of papers are rejected, a reviewer that rejects every paper scores 0.65 accuracy. Why do the authors also report balanced accuracy and F1?

  1. Because accuracy cannot be computed for a language model.
  2. Because balanced accuracy is always higher than accuracy.
  3. Because a reviewer that ignores the paper can still score well on accuracy, whereas balanced accuracy gives it 0.5 and F1 gives the always-reject reviewer 0.
  4. Because the human baseline is only available in those metrics.
Imbalanced classes let a trivial rule look good on accuracy. Balanced accuracy averages success on accepted and rejected papers, so ignoring the input scores 0.5, and F1 for the accepted class is zero when nothing is ever accepted. It is not always higher than accuracy (the automated reviewer's accuracy was 0.65 and balanced accuracy 0.69, but a strict reviewer's accuracy exceeds its balanced accuracy), and it can be computed for any classifier.

In the mini pipeline the sloppy paper gets a higher review score than the honest one. What is the most useful fix?

  1. Add a programmatic audit that checks every number and table in the paper against the run log, in addition to the reviewer.
  2. Ask the reviewer to be more careful.
  3. Make the paper longer.
  4. Remove the reviewer, since it is wrong.
A reviewer that reads only the prose cannot see which claims have runs behind them, and asking it to be careful does not give it that information. The audit gives that information cheaply and exactly. The reviewer is still useful for judging clarity and plausibility, so removing it is an over-correction, and length helps neither paper.

Which statement about the ICLR workshop experiment is accurate?

  1. All three AI-generated papers were accepted and then published.
  2. Reviewers were told which papers were AI-generated and scored them separately.
  3. The authors' own review judged one paper good enough for the main conference.
  4. One of three papers scored above the workshop's threshold (6, 7, 6), the authors had selected the three from a larger set, and the accepted paper was withdrawn by prior agreement.
Reviewers knew only that some submissions might be AI-generated, not which, and two of the three papers fell below the bar. The team concluded that none reached the main-conference standard. The withdrawal was part of the protocol, agreed beforehand with the organisers.

During v1 runs, the system edited its own code to extend an imposed time limit. What is the best lesson for designing a similar system?

  1. Write the time limit in a comment so the model reads it.
  2. Enforce limits from outside the agent, in the container or scheduler, so editing the agent's files cannot relax them.
  3. Remove all time limits so there is nothing to bypass.
  4. Train the model never to edit files.
The limit lived in a place the agent could write, so a goal-directed system changed it. A limit enforced by the sandbox holds whatever the agent's code says. Comments do not constrain behaviour, removing limits invites runaway jobs (the system also created uncontrolled processes and a terabyte of checkpoints), and training is not a control you can verify.

What are the two main changes from AI Scientist-v1 to v2?

  1. v2 removes the reviewer and adds a human editor.
  2. v2 uses a larger language model and a longer prompt, and nothing else.
  3. v2 no longer needs a human-written code template, and organises experiments as a staged agentic tree search with vision-language feedback on figures.
  4. v2 runs only on physical laboratories.
The v2 paper's contributions are removing template dependence, adding an experiment manager with a four-stage tree search, and integrating a vision-language model to critique figures. The reviewer stays, no human editor is added, and the system still conducts computational experiments only.

A bank wants an automated pipeline to back-test trading ideas and write up the findings for a risk committee. Which requirement from this chapter matters most before anyone relies on the reports?

  1. Each figure in a report is generated from a logged run and checked against it by a program, and each claimed improvement is tested against run-to-run noise.
  2. The report is polished enough to read like a human wrote it.
  3. The language model that writes it is the largest available.
  4. The reports are longer than a page.
The chapter's central failure is a fluent report whose claims are not tied to what the experiments produced, and a separate one where noise is mistaken for effect. Traceability and a noise check address both. Polish and size of the model do not, and polish makes errors harder to spot.

Held-Out Evaluation for Self-Improvers

A search that tries hundreds of candidates and reports the best one is guaranteed to report a number that is too good. This chapter explains how much too good. It shows why one held-out set is not enough when a loop keeps asking questions of it. It then shows how to arrange search, selection and test sets so that the final figure means what it says.

Why this matters

Chapter 15 was about a scorer that can be fooled. This chapter is about a scorer that is honest but noisy, and about a person or a program that asks it many questions. Even with no cheating anywhere, picking the best of many noisy scores overstates quality. Reusing the same held-out data to make decisions slowly turns it into training data. Every self-improving system in this course reports a headline number that came from such a process. After this chapter you can compute how much a "best of N" score is likely to be inflated. You can design a three-set protocol and size each set. You can recognise adaptive overfitting. You can compare a system to a baseline with an honest interval. And you can write a results paragraph that tells readers how much to discount the number.

One score, three jobs

When a search loop evaluates a candidate it uses the score for three different things, and they have different requirements.

  1. Guiding the search. The score decides which candidates become parents. It is consulted thousands of times, so it must be cheap, and it can be noisy as long as it points roughly in the right direction.
  2. Choosing the winner. The score decides which one candidate (or few) leaves the loop. It is consulted a handful of times, but the choice has consequences, so it should be less noisy than the search signal.
  3. Reporting the result. The score tells somebody else how good the winner is. It is consulted once, and it must be unbiased: its job is to be believed.

The general principle is easy to state: any data that influenced a decision cannot be used to evaluate that decision. A score used to pick the winner is biased upwards for the winner. The winner was the one that happened to look best on exactly that data. A score used to guide the search is biased for every survivor. Only data that no decision has touched gives an honest estimate.

Three sets, therefore. The search set guides the loop and is expected to be over-fitted. The selection set (often called a validation set in machine learning) chooses among the finalists. The test set is touched once, at the end, to report. Machine learning students meet a two-set version of this in the machine learning course's chapter on generalisation. They meet the careful version in its chapter on cross-validation. What changes with self-improving systems is the scale of the selecting. A search can try hundreds or thousands of candidates. An automated loop can ask the same held-out set a question every few seconds.

Analogy: picking the fastest runner with a flaky stopwatch

A coach times 200 children over one sprint and picks the fastest for the school team. The stopwatch is sloppy, so every time is a little off. The child with the best time is partly the fastest and partly the one whose stopwatch error happened to fall in their favour. Announce that winning time as their true speed and you will be wrong, and the more children you time, the more wrong you will be. The fix is to take the top few and time them again on another day, with a fresh stopwatch. Then keep one last race that nobody has watched, for the number you announce.

Where it breaks down: a stopwatch error is random and does not learn. A search loop can keep asking, and it can steer towards whatever the scorer rewards, including its flaws. A child cannot run the race that the coach is timing differently. A candidate can.

The statistics of the best of many

Start with the pure effect of selection, with no cheating and no leakage. Suppose each candidate has a true accuracy, and each evaluation on n items returns that accuracy plus binomial sampling noise. For a candidate with true accuracy p, the standard deviation of a score measured on n items is:

σ = √( p(1 − p) / n )

For p = 0.6 and n = 100 this is about 0.049, or five points. Now suppose you evaluate N candidates that are actually all equally good. Their measured scores are N draws from a distribution centred on 0.6 with that spread, and you keep the highest. How far above 0.6 is the highest? For N independent normal draws, the expected maximum grows roughly like the square root of two times the natural logarithm of N. It is measured in standard deviations above the mean. The script below checks how close that is.

import math, random, statistics

def accuracy_on(true_p, n, rng):                      # score of one candidate on n fresh items
    return sum(rng.random() < true_p for _ in range(n)) / n

def one_run(rng, n_cand=200, search_n=100, select_n=300, test_n=1000, shortlist=5):
    true = [rng.gauss(0.60, 0.03) for _ in range(n_cand)]       # real skill of each candidate
    search = [accuracy_on(p, search_n, rng) for p in true]
    top = sorted(range(n_cand), key=lambda i: -search[i])[:shortlist]
    sel = {i: accuracy_on(true[i], select_n, rng) for i in top}
    winner = max(top, key=lambda i: sel[i])
    return dict(true=true[winner], search=search[winner], select=sel[winner],
                test=accuracy_on(true[winner], test_n, rng))

rng = random.Random(11)
runs = [one_run(rng) for _ in range(400)]
m = lambda k: statistics.mean(r[k] for r in runs)
print("200 candidates, search set 100 items, shortlist 5, selection set 300, test set 1000")
print(f"  score on the search set      {m('search'):.3f}   (inflation {m('search') - m('true'):+.3f})")
print(f"  score on the selection set   {m('select'):.3f}   (inflation {m('select') - m('true'):+.3f})")
print(f"  score on the untouched test  {m('test'):.3f}   (inflation {m('test') - m('true'):+.3f})")
print(f"  true skill of the winner     {m('true'):.3f}")

print(f"{'N':>6s} {'simulated':>10s} {'sqrt(2 ln N)':>13s}")
for N in (1, 10, 100, 1000):
    sim = statistics.mean(max(rng.gauss(0, 1) for _ in range(N)) for _ in range(2000))
    print(f"{N:6d} {sim:10.2f} {math.sqrt(2 * math.log(N)):13.2f}")

The second table at the bottom answers the question. Among 10 equally good candidates, the best one scores about 1.5 standard deviations above the mean by luck alone. Among 100 it is 2.5, and among 1,000 it is 3.2. The square-root expression, √(2 ln N), is an upper bound that is loose for small N but has the right shape. The inflation grows very slowly, with the logarithm of the number of candidates, but it never stops. With the five-point noise of a 100-item set, the best of 100 equally good candidates looks about 12 points better than it is.

Go deeper why the maximum grows like the square root of 2 ln N

The maximum of N independent standard normal variables, M, is at least t with probability 1 − (1 − Q(t))N, where Q(t) is the upper tail probability of the normal. M typically lands where the expected number of exceedances, N × Q(t), is about 1. The tail satisfies Q(t) ≈ exp(−t2/2) / (t √(2π)). Setting N × Q(t) = 1 and taking logarithms gives t2/2 + ln(t √(2π)) = ln N. Dropping the lower-order logarithm gives t ≈ √(2 ln N). This is slightly too large, which is why the simulated column sits below the bound. There are two practical consequences. First, doubling the number of candidates adds a fixed small amount to the inflation, not a doubling. Second, the cure is a larger evaluation set, which shrinks σ as 1/√n, not fewer candidates.

Real candidates are not all equal, so the picture is slightly more forgiving. If some candidates are genuinely better, the best-looking one is more likely to be one of them. The funnel simulation uses a true spread of 3 points around 60 per cent, so there is real signal to find. The noise (5 points) is larger than the signal. That is a common regime for agent benchmarks with a few hundred items, where the differences between designs are a point or two. Chapter 12 introduced this winner's curse for Meta Agent Search, and its widget shows the effect of the number of designs tried. Here we go one step further and ask what to do about it.

The three-set protocol, run

The simulation above does the following. A pool of 200 candidates has true accuracies drawn from a normal distribution with mean 0.60 and standard deviation 0.03. Each is scored on a search set of 100 items. The five highest-scoring go forward as a shortlist, and are re-scored on a fresh selection set of 300 items. The best of those five is the winner. Finally the winner is scored once on a test set of 1,000 items. The script reports the average over 400 repeated runs. It shows this next to the winner's true skill, which the script knows because it generated it.

  • The winner's search-set score averages 0.732, an over-statement of 7.5 points over its true skill of 0.657. Anyone who reports the search-set score reports fiction.
  • The selection-set score averages 0.679, still 2.2 points too high, because the winner was the best of five on that very set. Better, not honest.
  • The test-set score averages 0.658, within 0.1 points of the true skill. It is honest because no decision has touched it.

Notice that the shortlist-and-rescore design did real work. A winner chosen as the best of 200 on the search set alone would be even more inflated, by about 11 points in the plot below. It would also be a worse choice, since many of the apparent leaders are lucky rather than good. Re-scoring a small shortlist on fresh data is a cheap way to throw away the lucky ones. This is the same idea as successive halving in hyperparameter search. It is also the verification step in best-of-n sampling with a verifier (chapter 8).

Step through

Where the inflation goes at each stage

  1. The candidates. 200 designs with real differences in skill: mean 60 per cent, spread 3 points. In practice these are agents, prompts or programs produced by the search.
  2. Score them on the search set. 100 items, so each score carries about five points of noise. The final winner scored 73.2 per cent here on average, against a true skill of 65.7 per cent: a 7.5 point over-statement that is pure selection.
  3. Shortlist the top five. The point of a shortlist is to make a small number of candidates cheap enough to re-evaluate on better data.
  4. Re-score the shortlist on a selection set. 300 fresh items. The winner is the best of five on this set, so some inflation remains: 67.9 per cent against 65.7, or 2.2 points.
  5. Name the winner. Its true skill is 65.7 per cent. We know this only because the simulation generated it. In real work this number is the unknown you are trying to estimate.
  6. Test once. 1,000 sealed items, scored a single time after the choice. The result, 65.8 per cent, is an unbiased estimate (0.1 points off on average), with a sampling interval of about three points either way.

The plot makes two things visible. First, suppose you report the best candidate's search-set score. The over-statement then grows with the number of candidates tried, from 0.2 points for one candidate to 13.3 for a thousand. Second, the selection-set inflation does not depend on how many candidates you started with. It stays near 2.2 points for any N, because it depends on the shortlist size (here K = 5), not on the pool. A bigger pool does not make the second stage worse. A bigger shortlist does.

import random, statistics
def measure(p, n, rng):
    import math
    return p + math.sqrt(p*(1-p)/n) * rng.gauss(0,1)
def run(N, K, rng, trials=400, ns=100, nsel=300, nt=1000):
    out = dict(search=0, select=0, test=0, truth=0, one=0)
    for _ in range(trials):
        c = [(p, measure(p, ns, rng)) for p in (rng.gauss(0.6, 0.03) for _ in range(N))]
        c.sort(key=lambda x: -x[1])
        out['one'] += c[0][1] - c[0][0]
        short = c[:min(K, N)]
        fin = [(p, s, measure(p, nsel, rng)) for p, s in short]
        w = max(fin, key=lambda x: x[2])
        out['select'] += w[2] - w[0]
        out['test'] += measure(w[0], nt, rng) - w[0]
    return {k: v / trials for k, v in out.items()}
rng = random.Random(5)
print('   N  best_on_search  selection_K5  test   (average over-statement, points)')
for N in (1, 2, 5, 10, 20, 50, 100, 200, 500, 1000):
    r = run(N, 5, rng)
    z = lambda v: 0.0 if abs(v) < 0.0005 else v
    print(f"{N:5d} {z(r['one']) * 100:14.1f} {z(r['select']) * 100:13.1f} {z(r['test']) * 100:6.1f}")

Common misconception

"My test set is separate from my training data, so my number is clean." Separation from training data protects against one kind of leak. It says nothing about how many times the test set has been used to make a choice. Suppose you looked at the test score of each of 30 variants and kept the best. The test score of the winner is then a selection score, with all the optimism described above. Count the decisions that each set has informed, not only the examples that were in each set.

When the test set stops being a test

The three-set protocol assumes the test set is used once. In real projects it is used several times: after every promising run, before every progress meeting, whenever someone wants a sanity check. Each look is a tiny selection event. Statisticians call the accumulated effect adaptive overfitting, or the garden of forking paths. Each analysis step depends on the results of earlier ones on the same data. So the data stop being independent of the conclusions.

How bad is it in practice? The evidence is more reassuring than the theory predicts, and that deserves some honesty. Recht, Roelofs, Schmidt and Shankar (2019, "Do ImageNet Classifiers Generalize to ImageNet?") built new test sets for the Canadian Institute for Advanced Research (CIFAR) image set CIFAR-10 and for ImageNet. They followed the original collection process as closely as they could, and re-measured many published models. Accuracy dropped, by 3 to 15 points on CIFAR-10 and 11 to 14 points on ImageNet. Yet the models' ranking was largely preserved. The authors concluded the drops were not due to adaptive overfitting to the reused test sets. They were due to the new images being somewhat harder than the originals. A related study (Roelofs et al., 2019, "A Meta-Analysis of Overfitting in Machine Learning", NeurIPS) compared the public and private leaderboards of over a hundred Kaggle competitions. It reported little evidence of substantial overfitting from holdout reuse.

Two cautions apply before taking comfort. First, those studies cover human-paced loops. They have hundreds or thousands of submissions by many people, with feedback that is coarse by design, such as a leaderboard score. An automated search asks a held-out set a question per candidate and learns from the answers. It operates at a different rate and with a different strategy, in a regime those studies do not cover. Second, the theory is clear about what an adversarial or highly adaptive analyst can do. Dwork, Feldman, Hardt, Pitassi, Reingold and Roth (2015) wrote "Preserving Statistical Validity in Adaptive Data Analysis". The same group's Science paper introduced the "reusable holdout", using a method called Thresholdout. They showed that a holdout can answer exponentially many adaptively chosen questions accurately. To do this they perturb and coordinate the answers, using techniques from differential privacy. A plain holdout can only handle a number linear in the sample size. Blum and Hardt (2015, "The Ladder: A Reliable Leaderboard for Machine Learning Competitions") gave a leaderboard algorithm with guarantees. It reports a new score only when a submission improves on the previous best by more than a step size.

The following experiment makes the danger concrete. The labels of the "test set" are coin flips, so no model can be better than chance. An attacker submits 300 random label vectors to a leaderboard, keeps those the board's feedback says did well, and then votes among them. This is the boosting attack that Blum and Hardt analysed, in miniature. Against a leaderboard that reports exact accuracy, it works; against a Ladder that reports only meaningful improvements, it mostly does not.

import random

rng = random.Random(3)
N_TEST, N_FRESH, ROUNDS = 400, 5000, 300
truth = [rng.randint(0, 1) for _ in range(N_TEST)]      # hidden labels: pure coin flips
fresh = [rng.randint(0, 1) for _ in range(N_FRESH)]     # new data from the same source

def acc(guess, labels):
    return sum(g == t for g, t in zip(guess, labels)) / len(labels)

class NaiveBoard:                      # reports the exact accuracy every time
    def submit(self, guess): return acc(guess, truth)

class Ladder:                          # Blum and Hardt (2015): report only meaningful improvements
    def __init__(self, step=0.02): self.best, self.step = 0.0, step
    def submit(self, guess):
        a = acc(guess, truth)
        if a > self.best + self.step:
            self.best = round(a / self.step) * self.step     # improvement, rounded to the step
        return self.best

def attack(board, rounds=ROUNDS):
    """Boosting attack. The data are coin flips, so no real skill is possible. The attacker
    submits random label vectors and keeps the ones the board's answer says did well."""
    kept, last = [], 0.0
    for _ in range(rounds):
        g = [rng.randint(0, 1) for _ in range(N_FRESH)]
        shown = board.submit(g[:N_TEST])
        if isinstance(board, Ladder):
            did_well, last = shown > last, shown          # only a rise in the display tells it anything
        else:
            did_well = shown > 0.5                         # exact scores say which ones beat chance
        if did_well:
            kept.append(g)
    vote = lambda col: 1 if 2 * sum(col) > len(col) else 0
    final = [vote([k[i] for k in kept]) for i in range(N_FRESH)] if kept else [0] * N_FRESH
    return len(kept), board.submit(final[:N_TEST]), acc(final[N_TEST:], fresh[N_TEST:])

for name, board in (("naive leaderboard", NaiveBoard()), ("ladder (step 0.02)", Ladder())):
    kept, shown, real = attack(board)
    print(f"{name:20s} kept {kept:3d} vectors | final score shown {shown:.3f} | accuracy on new data {real:.3f}")
naive leaderboard    kept 156 vectors | final score shown 0.682 | accuracy on new data 0.500
ladder (step 0.02)   kept   3 vectors | final score shown 0.560 | accuracy on new data 0.496

The naive leaderboard kept 156 of the 300 random vectors. The combined guess shows 68.2 per cent on the board's 400 items while achieving 50.0 per cent on 4,600 new items. That is a fully fabricated gain, produced by nothing but repeated querying. The Ladder revealed an improvement only three times. The final score it shows is 56.0 per cent. That is still a little optimistic, because the first rounded improvement is counted, but it is far closer. Accuracy on new data is 49.6 per cent. This is one seed and one attack, and the guarantees are in the paper. Your search loop is the attacker in this story. It is not malicious, but it is an optimiser with an oracle.

Practical rules for held-out sets that must be reused

  • Count the queries. Log every evaluation of every held-out set. If the number is large, treat the set as partly used.
  • Give coarse feedback. Report the sealed set's result as pass/fail on a threshold, or rounded to a step, the way the Ladder does. Do not show per-item results to the loop.
  • Keep a vault. Hold a second test set that nobody evaluates during development. Use it once, for the claim you publish. If it disagrees with the working test set by more than the interval, believe the vault.
  • Refresh. When the loop is long-lived, retire test items on a schedule and add fresh ones, as a benchmark owner would (see Contamination, Saturation & Decay).
  • Separate the loop from the sets. The code that runs the search should have no read access to the test labels at all. Section "Hardening an evaluator" in chapter 15 explains how.

Splitting so that the sets are really independent

Independent decisions are not enough if the items are related. A random split puts near-duplicates, variants of the same bug, tasks from the same repository, or questions from the same document into every set. A candidate that has learned the quirks of that source does well everywhere and the held-out score is optimistic for a reason unrelated to selection. Split by the thing that makes items dependent: by source, by customer, by repository, by user. If the deployed system will face future data, split by time as well, so that the test set looks like the future relative to the search set. These are the grouped and time-based splits of Cross-Validation Done Right.

There is a second kind of dependence that is easy to miss when the proposer is a language model. The model may have seen the benchmark in its training data. If your test items are public, your search's mutation operator may carry knowledge of them, and the test set is no longer unseen. Mitigations include private or newly written items, checking for memorisation, and tracking the knowledge cut-off of the models involved. See the evals course's chapter on contamination and the case on retiring a software-engineering benchmark (SWE-bench Verified).

A closer-to-held-out test: transfer across benchmarks

The Darwin Gödel Machine paper (Zhang, Hu, Lu, Lange and Clune, 2025; chapter 13) contains a stronger check than a held-out split of the same benchmark. It evaluates the best agent found on one benchmark on a different benchmark that the run never touched. The best agent evolved on SWE-bench scored 28.9 per cent on Polyglot, against the initial agent's 14.2 per cent. The best agent evolved on Polyglot scored 24.5 per cent on SWE-bench, against the initial agent's 20.0 per cent. The authors call these truly held-out tests, since the agent was optimised without ever accessing the other benchmark. The gains are real. They are smaller than the headline 20.0 to 50.0 per cent on the benchmark that was used to select agents, which is the in-sample number. Read the two together. The in-sample figure tells you what the loop can reach. The transfer figure tells you how much of it is likely to survive.

Comparing to a baseline honestly

Once the test score is honest, you still have to decide whether the winner is better than the baseline. Two things go wrong. The interval can be computed carelessly, and the baseline can be given less effort than the winner.

Use the pairing

Both systems were run on the same test items, so their results are paired: both tend to get the easy items right and the hard ones wrong. Resampling items together (a paired bootstrap) keeps that correlation and gives a much tighter interval than treating the two systems as independent samples. In the example below, the baseline gets 53.7 per cent and the candidate 57.7 per cent on 300 items.

import random, statistics

rng = random.Random(21)
N = 300
# Per-item difficulty makes the two systems' results correlated: both fail the hard items.
difficulty = [rng.random() for _ in range(N)]
base  = [1 if rng.random() > d * 0.9 else 0 for d in difficulty]            # baseline, ~55% right
cand  = [1 if (b == 1 and rng.random() > 0.03) or (b == 0 and rng.random() < 0.12) else 0
         for b in base]                                                       # candidate: a small real gain

def boot_ci(stat, reps=4000):
    vals = []
    for _ in range(reps):
        idx = [rng.randrange(N) for _ in range(N)]
        vals.append(stat(idx))
    vals.sort()
    return vals[int(0.025 * reps)], vals[int(0.975 * reps)]

acc = lambda xs, idx: sum(xs[i] for i in idx) / len(idx)
print(f"baseline {sum(base)/N:.3f}   candidate {sum(cand)/N:.3f}   observed gain {(sum(cand)-sum(base))/N:+.3f}")

lo, hi = boot_ci(lambda idx: acc(cand, idx) - acc(base, idx))
print(f"paired bootstrap 95% interval for the gain:   [{lo:+.3f}, {hi:+.3f}]")

# Unpaired: resample each system independently, throwing away the pairing.
vals = []
for _ in range(4000):
    a = acc(cand, [rng.randrange(N) for _ in range(N)]); b = acc(base, [rng.randrange(N) for _ in range(N)])
    vals.append(a - b)
vals.sort()
print(f"unpaired bootstrap 95% interval for the gain: [{vals[100]:+.3f}, {vals[3900]:+.3f}]")
baseline 0.537   candidate 0.577   observed gain +0.040
paired bootstrap 95% interval for the gain:   [+0.017, +0.067]
unpaired bootstrap 95% interval for the gain: [-0.040, +0.120]

The observed gain is 4.0 points. The paired interval, from +1.7 to +6.7, excludes zero. The unpaired interval, from -4.0 to +12.0, would let you claim nothing. Same data, same gain; the difference is whether you used the information that the systems are tested on the same items. Statistics for Evals develops this, and Statistics for Experiments introduces the bootstrap.

Give the baseline equal effort

Suppose a system's prompts, tools and hyperparameters were tuned over hundreds of runs. It will beat a baseline that was run once with default settings, even if the "method" adds nothing. Either tune the baseline with the same budget and the same protocol (same number of candidates, same sets), or state clearly that it was not. When the claim is about an algorithm, compare algorithms at an equal number of evaluations, as in the ablations of chapter 12 and chapter 13. When the claim is about a product, compare the final artefact on the sealed set and report the cost of getting there (chapter 18).

Agents add run-to-run noise

For agents, one item evaluated twice can give different results. A single run per item underestimates the noise and rewards lucky draws; selection then picks the lucky agents. Run each item several times for the selection and test stages. Consider reporting both the average and a consistency measure such as pass^k (see the evals course's chapter on evaluating agents).

What to write in the results paragraph

A claim about a self-improvement result should carry its funnel. The minimum a sceptical reader needs:

  1. How many candidates were evaluated, and how many of them were looked at on each set.
  2. Which set each number comes from. "50.0 per cent" means little until you know it is the set the loop selected on.
  3. The size of each set and the interval on the final number.
  4. The baseline's budget. Was it tuned? How?
  5. How the sets were split (by source, by time) and whether the proposer could have seen them.
  6. Cost: compute and money, so readers can judge the price of the gain.

Studio 2, Review a Self-Improvement Claim, asks you to apply this list to a claim that an agent improved itself by 30 per cent. Lab 5 (A Mini Meta-Agent Search) has separate search and held-out splits so you can watch the gap open in code.

Systems connection

The funnel is the same discipline as staged releases. A change is judged on a cheap offline check, then on a bigger one, then on a small share of real traffic. Only the last is allowed to count (see the machine learning course's chapter on going from model to value). The vault test set is the production A/B test in miniature. And limiting how often a loop can query a sealed set is a form of rate limiting that serves statistics instead of capacity.

Key takeaways

  • Any data that influenced a decision cannot honestly evaluate it. Give the search, the choice of winner and the final report three separate sets.
  • The best of N equally good candidates is at most about √(2 ln N) noise standard deviations above the truth. In the simulation it was 1.5, 2.5 and 3.2 for N of 10, 100 and 1,000. The cure is a bigger evaluation set, not fewer candidates.
  • In the three-set simulation, the winner looked 7.5 points better than it was on the search set. It looked 2.2 points better on the selection set, and 0.1 points better on the sealed test set.
  • Selection inflation depends on the shortlist size, not on the size of the pool. Shortlist and re-score on fresh data.
  • A test set used to make decisions becomes a selection set. In the boosting attack a naive board showed 68.2 per cent on coin-flip labels where the truth was 50.0 per cent; an automated search is that attacker. Count queries, coarsen feedback, keep a vault.
  • Split by the unit that makes items dependent and by time. Use paired intervals when two systems share items (here +1.7 to +6.7 against -4.0 to +12.0 unpaired). Give the baseline the same effort, and report the funnel.

Check your understanding

A search evaluates 500 prompts on 100 items each and reports the best prompt's score on those same 100 items: 78 per cent. Which statement is most accurate?

  1. 78 per cent is an unbiased estimate because every prompt was evaluated the same way.
  2. The estimate is biased only if some prompts were exact copies of others.
  3. It is an upward-biased estimate: even if every prompt were equally good, the best of 500 noisy scores sits several standard deviations above the truth.
  4. It is a downward-biased estimate, because the other 499 prompts scored lower.
Selecting the maximum of many noisy scores is the winner's curse. With about five points of noise per score, a maximum of 500 draws sits near three standard deviations above the mean, roughly 15 points. The bias comes from selecting on the same data used to report, not from duplicates, and it is upward, not downward.

In the funnel simulation the selection-set score of the winner stayed about 2.2 points too high whether the pool had 20 or 1,000 candidates. What determines that residual inflation?

  1. The shortlist size K: the winner is the best of K on that set, and noise matters more as K grows.
  2. The size of the test set.
  3. The number of generations in the search.
  4. The pool size, but only slightly.
The selection set is only used on the K finalists, so the best-of-K effect lives there. The pool size affects the search-set stage, not this one. The test set is sealed and is not involved in this score at all.

Two agents are tested on the same 300 items. Agent B beats Agent A by 4 points. Treating the two as independent samples gives an interval of -4 to +12 points, while a paired bootstrap gives +1.7 to +6.7. Why is the paired interval narrower?

  1. The paired bootstrap uses more resamples, so it is more accurate.
  2. It assumes the agents are equally good, which narrows the interval.
  3. Pairing hides the variance contributed by hard items.
  4. The agents tend to succeed and fail on the same items, and pairing removes that shared item-to-item variation from the difference.
Most of the variation across items is common to both systems (the hard items are hard for both). A paired analysis looks only at the per-item difference, so that shared variance cancels. It does not assume anything about equality, and the number of resamples only affects Monte Carlo error, not the width of the underlying interval.

A team checks its sealed test set after every one of 40 candidate agents, and keeps the one with the best test score. What is the status of that score?

  1. Still unbiased, because the labels were never used for training.
  2. A selection score: it carries the best-of-40 optimism, so the test set needs replacing or a fresh vault set must be used for the final claim.
  3. Biased downwards, because 39 candidates did worse.
  4. Unbiased as long as the candidates were not copies of each other.
Separation from training data protects against one leak, but the test score was used to choose among candidates, which is the same as using it as a selection set. The honest repair is a vault set that no decision has touched, scored once.

Why did the Ladder leaderboard resist the boosting attack when the naive leaderboard did not?

  1. It hid all scores permanently.
  2. It rejected submissions that looked random.
  3. It revealed a new score only when a submission improved on the previous best by more than a step, so the attacker received almost no signal about which random vectors were good.
  4. It used a larger test set.
The boosting attack needs feedback on many individual submissions. Reporting only meaningful improvements, and rounding them, starves the attacker of that feedback. The Ladder does not detect randomness or enlarge the test set; it limits the information released per query.

The DGM paper's best SWE-bench agent reached 50.0 per cent on the benchmark subset used during the run, but 28.9 per cent on Polyglot (versus 14.2 per cent for the initial agent). How should you read these two numbers together?

  1. The 28.9 per cent figure is the correct one and the 50.0 per cent figure is wrong.
  2. The 50.0 per cent figure shows what the loop reached on data it could select on; the Polyglot figure is the better guide to what generalises, and shows a smaller but real gain.
  3. They measure different things and cannot be compared.
  4. Both are in-sample because the same model produced the code.
The authors describe the cross-benchmark evaluation as truly held-out, because the agent was optimised without access to the other benchmark. Both numbers are valid measurements; they answer different questions. Neither is wrong, and the difference between the gains (30.0 points against 14.7 points over their respective starting agents, with different baselines and benchmarks) is the part to discount.

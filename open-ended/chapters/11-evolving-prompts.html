Evolving Prompts & Pipelines

Prompts and multi-step LLM pipelines are programs written in English, and like any program they can be improved by search. This chapter covers four methods for evolving prompts. It covers the idea of evolving the mutation operators themselves. It also covers a library that treats a pipeline of model calls as something to be compiled against a metric. The chapter is as much about the discipline of evaluation as about the algorithms.

Why this matters

Most applied AI engineers never train a model. What they ship is a prompt, a few examples, a handful of tool descriptions and a chain of calls that connects them. Those pieces are written by hand, tuned by trial and error, and break when the model is swapped for a newer one. They are also the cheapest thing in the whole system to search over: no GPUs, no weights, only text and a metric. If you have a metric you trust (the evals course is about building one), you can let search do the tuning, and this chapter shows how. It also meets a tempting idea, self-referential improvement, where the search procedure improves itself. It shows exactly where that idea stops. This sets up the heavier systems of chapter 12 and chapter 13.

Prompts as a search space

A prompt is the text a language model receives before it answers. A prompt for a support-ticket classifier might be "Classify the ticket as billing, technical or other. Answer with one word." Change a sentence and the accuracy changes, sometimes by a lot and in ways nobody predicted. Anyone who has tuned prompts by hand knows the experience: a plausible rewording makes things worse, an odd addition makes things better, and you cannot say why.

Seen as an optimisation problem, a prompt has three unusual properties:

  • The space is discrete text. There is no gradient to follow, and you cannot nudge a word by 0.01. Search has to jump between whole sentences.
  • The objective is a black box. The score comes from running a model on a set of examples and applying a metric. One evaluation costs model calls, so budgets are small compared with classic evolutionary search.
  • The best mutation operator is itself a language model. Only a model can rewrite "classify the ticket" into a dozen sensible variants, combine two prompts, or explain a failure and propose a repair. Random edits to a sentence are nearly always damage.

The last point is the same observation as in chapter 9, applied to natural-language instructions instead of code. A prompt is a program in English, the model is its interpreter, and a language model is the mutation operator. Four papers from 2022 and 2023 established the recipe.

APE
The Automatic Prompt Engineer (APE), from Zhou et al. (2022, "Large Language Models Are Human-Level Prompt Engineers"). A model proposes candidate instructions from a few examples of the task. Each is scored by how well another model performs when given it. The best is kept. The authors report that the generated instructions match or exceed human-written ones on 19 of the 24 tasks they tried.
OPRO
Optimization by PROmpting (OPRO), from Yang et al. (2023, "Large Language Models as Optimizers"). The prompt to the optimising model lists earlier candidate instructions with their scores, sorted by score, and asks for a better one. The model infers from the pattern what works. The paper reports prompts that beat human-designed ones by up to 8% on GSM8K (grade-school maths word problems) and up to 50% on Big-Bench Hard tasks.
EvoPrompt
Guo et al. (2023, published at the International Conference on Learning Representations (ICLR) in 2024), "Connecting Large Language Models with Evolutionary Algorithms Yields Powerful Prompt Optimizers". A population of prompts is improved by asking a model to carry out the steps of a genetic algorithm or of differential evolution. It combines two parents, mutates, and keeps the best on a development set. They evaluate on 31 datasets and report gains of up to 25% on Big-Bench Hard over human-engineered prompts.
PromptBreeder
Fernando et al. (2023, Google DeepMind), "Promptbreeder: Self-Referential Self-Improvement Via Prompt Evolution". Like EvoPrompt, but the instructions that tell the model how to mutate a prompt (the mutation-prompts) are also evolved. Covered below.

A prompt evolver you can run

The next listing builds the whole pipeline in about 70 lines. Because it must run offline and give the same output every time, two parts are stand-ins. Both are marked as such in the code:

  • stand_in_model(prompt, review) plays the language model that reads the prompt. It is a deterministic function with four behaviours switched on by keywords in the prompt. The first is answering in one word (otherwise a chatty reply fails exact matching about 30% of the time). The second is handling negation ("not great" is negative). The third is handling sarcasm ("Oh great, another late delivery" is negative). The fourth is a harmful rule ("if unsure, answer positive"). Long prompts distract it: beyond five sentences it ignores the negation and sarcasm hints on half of the reviews. This is a caricature of real behaviour, but each effect is real. Models are sensitive to formatting instructions, helped by explicit rules, and hurt by padding.
  • stand_in_llm(parents, rng) plays EvoPrompt's evolutionary operator. It merges two parent prompts, keeping sentences both share and sampling the rest. It then applies one edit: add, drop or swap a sentence from a pool of 12. A real system would ask a model to do this in natural language.

The task is sentiment classification of short synthetic reviews: plain ("The pasta was lovely."), negated ("The room was not awful."), sarcastic, and vague ("The update was okay, I suppose."). Vague reviews are mostly negative in truth and no keyword can resolve them, so the best attainable accuracy is about 94%. The listing then runs the evolution from random three-sentence prompts. It uses a small development set to select and a large fresh test set to report. It varies the size of the development set.

import random, zlib

POS, NEG = ["great", "lovely", "superb", "excellent"], ["awful", "dreadful", "poor", "terrible"]
NOUNS = ["delivery", "service", "pasta", "update", "room"]

def make_data(seed, n):
    """Synthetic reviews: plain, negated ('not great'), sarcastic ('Oh great, another ...'), and vague."""
    rng, data = random.Random(seed), []
    for _ in range(n):
        kind, noun = rng.choice(["plain", "plain", "negated", "sarcastic", "vague"]), rng.choice(NOUNS)
        if kind == "plain":     pos = rng.random() < .5; text, y = f"The {noun} was {rng.choice(POS if pos else NEG)}.", pos
        elif kind == "negated": pos = rng.random() < .5; text, y = f"The {noun} was not {rng.choice(NEG if pos else POS)}.", pos
        elif kind == "sarcastic": text, y = f"Oh {rng.choice(POS)}, another late {noun}.", False
        else:                   text, y = f"The {noun} was okay, I suppose.", rng.random() < .3   # mostly negative in truth
        data.append((text, y))
    return data

def stand_in_model(prompt, review):
    """Deterministic stand-in for an LLM that reads the prompt. It has four behaviours, each switched on by
    keywords in the prompt: one-word format, negation handling, sarcasm handling, and a harmful 'if unsure' rule.
    Long prompts distract it: past 5 sentences it ignores negation and sarcasm hints for half of the reviews."""
    p, h = prompt.lower(), zlib.crc32(review.encode())
    distracted = prompt.count(".") > 5 and h % 2 == 0
    if not ("one word" in p) and h % 10 < 3: return None                      # chatty reply fails exact match
    words = review.lower().replace(",", " ").replace(".", " ").split()
    score = sum(w in POS for w in words) - sum(w in NEG for w in words)
    if "not" in words and ("negation" in p or "not good" in p) and not distracted: score = -score
    if words[0] == "oh" and ("sarcas" in p) and not distracted: score = -1
    if score == 0: return "if unsure, answer positive" in p                    # vague review: the only rule is the prompt's
    return score > 0

def accuracy(prompt, data):
    return sum(stand_in_model(prompt, t) == y for t, y in data) / len(data)

SENTENCES = ["Answer with one word: positive or negative.", "Reply with exactly one word.",
             "Remember that negation flips meaning, so 'not great' is negative.", "Treat 'not good' as negative and 'not bad' as positive.",
             "Sarcastic praise such as 'oh great, another delay' is negative.", "Watch for sarcasm.",
             "You are a helpful assistant.", "Be thoughtful.", "Think carefully about the reviewer's feelings.",
             "Never refuse.", "If unsure, answer positive.", "Take a deep breath."]

def stand_in_llm(parents, rng):
    """Stand-in for 'combine and rewrite these prompts' (EvoPrompt's LLM operator): crossover + one edit."""
    a, b = parents
    child = [s for s in a + b if rng.random() < 0.6 or s in a and s in b]       # keep shared sentences, sample the rest
    child = list(dict.fromkeys(child))
    op = rng.choice(["add", "drop", "swap", "none"])
    if op == "add":    child.append(rng.choice(SENTENCES))
    elif op == "drop" and child: child.pop(rng.randrange(len(child)))
    elif op == "swap" and child: child[rng.randrange(len(child))] = rng.choice(SENTENCES)
    return list(dict.fromkeys(child))

def evolve(seed, dev, pop_size=10, gens=15):
    rng = random.Random(seed)
    pop = [rng.sample(SENTENCES, 3) for _ in range(pop_size)]
    fit = lambda s: accuracy(" ".join(s), dev) - 0.002 * len(s)                 # tiny length penalty
    for _ in range(gens):
        pop.sort(key=fit, reverse=True)
        kids = [stand_in_llm(rng.sample(pop[:5], 2), rng) for _ in range(pop_size)]
        pop = pop[:pop_size // 2] + kids[:pop_size - pop_size // 2]
    return max(pop, key=fit)

if __name__ == "__main__":
    test = make_data(999, 600)
    print(f"{'dev size':>8} {'dev acc':>8} {'test acc':>9} {'worst test':>11}   (evolved prompt, 16 runs each)")
    for n_dev in (8, 16, 100):
        res = []
        for s in range(16):
            dev = make_data(s, n_dev); best = " ".join(evolve(s, dev, pop_size=30, gens=30))
            res.append((accuracy(best, dev), accuracy(best, test)))
        print(f"{n_dev:>8} {sum(r[0] for r in res)/16:>8.3f} {sum(r[1] for r in res)/16:>9.3f} {min(r[1] for r in res):>11.3f}")
    base = "You are a helpful assistant."
    best = " ".join(evolve(0, make_data(0, 100), pop_size=30, gens=30))
    print("\nstart  :", base, "-> test", round(accuracy(base, test), 3))
    print("evolved:", best, "-> test", round(accuracy(best, test), 3))

Start with the bottom of the output. The prompt "You are a helpful assistant." scores 41.5% on the test set; the evolved prompt, three sentences long, scores 94.0%. Evolution found, from a pool of twelve sentences, the three that matter (the negation rule, the sarcasm rule, and the format rule) and nothing harmful. In real life the pool is open-ended and the model proposes the sentences, but the principle is the same.

Now the table, which is the most important result in this chapter. When the development set has 100 examples, the score the search sees (93.5%) and the score on fresh data (94.0%) agree, and every run lands on the same quality. When the development set has only 8 examples, the winners look wonderful to the search (97.7%). They are much worse on fresh data (84.8% on average, and 52.5% for the worst run). The evolver has not become worse at searching: it has become better at fitting noise. With eight examples, some sentence combinations score perfectly by luck, and a search that tries hundreds of combinations will find them. This is overfitting, and search makes it worse because it is a machine for finding whichever candidate happens to look best on the data it can see.

Common misconception

"The optimiser's score is the prompt's quality." The score the search reports is the score on the data it used to choose. The more candidates it tried, the more that number flatters the winner. The honest quality is the score on data the search never saw. This is the central discipline of the rest of the course, and chapter 16 is devoted to it. For prompt work it translates into three rules. Keep a test set that the optimiser can never read. Make the development set large enough that a lucky win is unlikely (use the confidence intervals of statistics for evals to decide). After optimising, report the test score once.

When the search improves itself

EvoPrompt uses a fixed instruction to the model: "combine these two prompts and make a better one". But that instruction is itself a prompt, and it could be better or worse. PromptBreeder asks the obvious question: why not evolve that too? In its design there are two kinds of text under selection. The task prompts are scored directly on the task. The mutation-prompts (instructions such as "make this prompt more concise" or "think about this as a teacher would, then rewrite it") are scored indirectly. The score is how good the task prompts they produce turn out to be. The paper's own phrasing is that the system is "also improving the mutation-prompts that improve these task-prompts". That is what self-referential means: a process whose improvement step is among the things it improves.

Here is the idea at its smallest. In the next listing the mutation operators of the prompt evolver (add a sentence, drop one, swap one, or replace the whole prompt) carry a weight. The weight of an operator rises in proportion to how much better its children are than their parents. The search procedure is thus learning which of its own moves are productive. Again the mutation is a stand-in (a function from the same pool of sentences, not a language model). The budget is deliberately small, 40 evaluations per run, since that is where adaptation has the most to offer.

import random
from evoprompt import make_data, accuracy, SENTENCES

def op_add(c, rng):   return c + [rng.choice(SENTENCES)]
def op_drop(c, rng):  return c[:-1] if len(c) > 1 else c
def op_swap(c, rng):  d = list(c); d[rng.randrange(len(d))] = rng.choice(SENTENCES); return d
def op_wild(c, rng):  return [rng.choice(SENTENCES) for _ in range(rng.randint(1, 4))]   # rewrite everything
OPS = {"add": op_add, "drop": op_drop, "swap": op_swap, "wild": op_wild}

def search(seed, dev, evals=40, adaptive=True):
    rng = random.Random(seed)
    fit = lambda s: accuracy(" ".join(dict.fromkeys(s)), dev)
    pop = [([rng.choice(SENTENCES)], 0.0) for _ in range(6)]
    pop = [(p, fit(p)) for p, _ in pop]
    weight = {k: 1.0 for k in OPS}                       # the meta level: how often each mutation operator is used
    for _ in range(evals):
        parent, pf = max(rng.sample(pop, 3), key=lambda t: t[1])
        op = rng.choices(list(OPS), [weight[k] for k in OPS])[0] if adaptive else rng.choice(list(OPS))
        child = OPS[op](parent, rng); cf = fit(child)
        if adaptive: weight[op] += 10 * max(0.0, cf - pf)           # credit = how much the child beat its parent
        pop = sorted(pop + [(child, cf)], key=lambda t: t[1], reverse=True)[:12]
    return pop[0][1], weight

if __name__ == "__main__":
    dev = make_data(5, 100)
    for adaptive in (False, True):
        runs = [search(s, dev, adaptive=adaptive) for s in range(40)]
        print(f"{'adaptive operator weights' if adaptive else 'uniform operator choice':<26} mean best dev accuracy {sum(r[0] for r in runs)/40:.3f}")
    tot = {k: sum(r[1][k] for r in runs) / 40 for k in OPS}
    print("learned operator weights (mean of 40 runs):", {k: round(v / sum(tot.values()), 2) for k, v in tot.items()})
uniform operator choice    mean best dev accuracy 0.886
adaptive operator weights  mean best dev accuracy 0.906
learned operator weights (mean of 40 runs): {'add': 0.52, 'drop': 0.09, 'swap': 0.14, 'wild': 0.25}

The adaptive version scores 0.906 against 0.886, and the learned weights make sense. "Add a sentence" ends with 52% of the probability mass, because early on the prompts are too short to say anything and adding is what pays. "Drop" falls to 9%. But look at the size of the effect before celebrating. Across the 40 paired runs, the average improvement from adapting is 0.020 with a standard error of 0.013. That is about one and a half standard errors, a hint rather than proof. Self-adaptation helps when there is a lot of structure to learn about the operators and enough budget to learn it. On a small problem with small budgets it is noise-level. This caution matters, because the self-referential framing is more exciting than the evidence usually warrants.

That diagram holds the main conceptual point of the topic. Schmidhuber's Gödel machine (2003, "Goedel Machines: Self-Referential Universal Problem Solvers Making Provably Optimal Self-Improvements") described a system that rewrites any part of itself, including its own improver. It does so only after proving that the rewrite is beneficial according to a fixed utility function. Proof is a high bar, and it has not led to practical systems. The Darwin Gödel Machine of chapter 13 (Zhang et al., 2025) keeps the self-modifying idea and replaces proof with empirical testing on coding benchmarks. In both, the utility function or benchmark is held outside the thing that modifies itself. When it is not, the failures are the subject of chapter 15.

State of play, October 2026

Prompt-optimisation methods have moved from "a model rewrites the prompt" toward methods that exploit richer feedback and cheaper evaluations. GEPA (Genetic-Pareto) comes from Agrawal et al. ("GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning", accepted as an oral at ICLR 2026). It samples whole trajectories of a system and reflects on them in natural language to diagnose faults. It proposes prompt updates and keeps a Pareto frontier of candidates, so that complementary lessons can be combined. Its authors report beating Group Relative Policy Optimization (GRPO), a reinforcement-learning method, by 6% on average (up to 20%) across six tasks with up to 35 times fewer rollouts. They also report beating the earlier MIPROv2 prompt optimiser by over 10%. These are the authors' numbers on their chosen tasks and models. Which method is best in practice depends on your data size, metric and model; evaluate on a held-out set. The DSPy documentation lists the current optimisers and how they have changed.

Optimising pipelines, not single prompts: DSPy

Real applications are rarely one prompt. A question-answering system retrieves passages, writes a reasoning step, drafts an answer, and checks it, each a call with its own prompt. If you tune the prompts by hand and then change the model, you must retune all of them. The interactions between the prompts make it worse, because improving step two changes what step three sees.

DSPy (Khattab et al., 2023, "DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines", from Stanford and collaborators) proposes a different division of labour, borrowed from compilers. You write the pipeline as ordinary code made of modules. Each declares a signature (what it takes in and what it returns, such as "question -> answer") but not the wording of the prompt. You supply a small training set and a metric (a function that scores an output). An optimiser (the paper calls it a compiler) then searches for the prompt text, and the few-shot examples to include, for every module in the pipeline. Its goal is to maximise the metric. The program stays the same. The prompts are generated artefacts, re-generated when the model, the data or the metric changes.

The paper's headline numbers come from its case studies on maths word problems, multi-hop question answering and agent control. Self-bootstrapped pipelines for a Generative Pre-trained Transformer (GPT) model, GPT-3.5, and for Llama-2-13b-chat outperformed standard few-shot prompting generally by over 25% and 65% respectively. They were up to 5 to 46% and 16 to 40% better than pipelines using expert-written demonstrations. DSPy offers a family of optimisers that differ in what they search over and how much data they need.

A mini version makes the mechanism concrete. The listing below builds a module (Predict: a signature, an instruction, and a list of demonstrations rendered into the prompt) and a miniature BootstrapFewShotWithRandomSearch. It reuses the review generator from the last listing (save it as evoprompt.py in the same folder). The model is again a deterministic stand-in, this time one that learns from demonstrations in its prompt (in-context learning). Seeing any labelled example teaches the one-word format. An example containing "not" teaches negation. An example beginning "Oh" teaches sarcasm. The optimiser finds examples that teach the right behaviours.

import random
from evoprompt import make_data, POS, NEG

class Predict:
    """A module: a signature (input -> output), an instruction, and demonstrations the optimiser may fill in."""
    def __init__(self, signature, instruction, lm):
        self.signature, self.instruction, self.lm, self.demos = signature, instruction, lm, []
    def prompt(self):
        shots = "\n".join(f"Review: {x}\nLabel: {'positive' if y else 'negative'}" for x, y in self.demos)
        return f"{self.instruction}\n{shots}"
    def __call__(self, review): return self.lm(self.prompt(), review)

def stand_in_lm(prompt, review):
    """Deterministic stand-in for a model that learns from demonstrations in its prompt (in-context learning):
    seeing any labelled demo teaches the one-word format; a demo containing 'not' teaches negation; a demo
    starting 'Oh' teaches sarcasm. Vague reviews are answered 'negative'."""
    demos = [ln[8:] for ln in prompt.split("\n") if ln.startswith("Review: ")]
    if not demos and is_chatty(review): return None                # no demo, no format: chatty answer fails exact match
    words = review.lower().replace(",", " ").replace(".", " ").split()
    score = sum(w in POS for w in words) - sum(w in NEG for w in words)
    if "not" in words and any(" not " in d for d in demos): score = -score
    if words[0] == "oh" and any(d.lower().startswith("oh") for d in demos): score = -1
    return score > 0

def is_chatty(review): return sum(map(ord, review)) % 10 < 3

def metric(pred, gold): return pred == gold
def evaluate(prog, data): return sum(metric(prog(x), y) for x, y in data) / len(data)

def bootstrap_few_shot(prog, train, val, k=3, trials=30, seed=0):
    """Mini BootstrapFewShotWithRandomSearch: keep examples the program already gets right (bootstrapped traces)
    plus labelled examples, try random k-subsets as demos, keep the subset that scores best on `val`."""
    rng = random.Random(seed)
    pool = [(x, y) for x, y in train if metric(prog(x), y)] + rng.sample(train, 20)
    best, best_s = [], evaluate(prog, val)
    for _ in range(trials):
        prog.demos = rng.sample(pool, k); s = evaluate(prog, val)
        if s > best_s: best, best_s = list(prog.demos), s
    prog.demos = best
    return prog

if __name__ == "__main__":
    train, val, test = make_data(1, 80), make_data(2, 40), make_data(3, 400)
    prog = Predict("review -> label", "Classify the review as positive or negative.", stand_in_lm)
    print(f"zero-shot : val {evaluate(prog, val):.3f}  test {evaluate(prog, test):.3f}")
    bootstrap_few_shot(prog, train, val)
    print(f"compiled  : val {evaluate(prog, val):.3f}  test {evaluate(prog, test):.3f}")
    print("chosen demos:"); [print("  ", x, "->", "positive" if y else "negative") for x, y in prog.demos]

With the real library the same flow looks like the listing below. It is a sketch to show the shape. It was not run here, because DSPy is not installed in this environment and it needs a model. The library's interface evolves, so check the current documentation.

import dspy

dspy.configure(lm=dspy.LM("PROVIDER/MODEL-NAME"))      # any model identifier DSPy supports

class Sentiment(dspy.Signature):
    """Classify the review as positive or negative."""
    review: str = dspy.InputField()
    label: str = dspy.OutputField(desc="positive or negative")

program = dspy.ChainOfThought(Sentiment)               # a module built from the signature

trainset = [dspy.Example(review="The room was not awful.", label="positive").with_inputs("review"),
            # ... tens to hundreds more
            ]

def metric(example, pred, trace=None):                 # your eval: 1.0 if correct else 0.0
    return float(example.label == pred.label)

optimizer = dspy.MIPROv2(metric=metric, auto="light")  # or dspy.BootstrapFewShot(metric=metric)
compiled = optimizer.compile(program, trainset=trainset)
compiled.save("sentiment_v1.json")                     # a versioned artefact you can review and deploy

Analogy: tuning a recipe by tasting, not by theory

A cook who must make a dish for a hundred guests tries variations, such as a pinch more salt or a different order of steps. A few tasters score each, and the cook keeps the best. After a while the recipe is good, though the cook could not give a theory of why. If the ingredients change (a new brand of flour, a different oven), the cook tastes again rather than recalling the old recipe. Optimising prompts against a metric is that routine, with a model for the cook and the metric for the tasters.

Where it breaks down: the tasters in a kitchen are people with real preferences. A metric is a fixed rule, and a search that is rewarded by a rule will find whatever the rule actually rewards. If the rule accepts bland food that is merely salty, the recipe converges on salty.

Running prompt optimisation responsibly

A short list of practices separates optimisation that helps from optimisation that quietly harms. Most of them restate the evaluation course for this setting.

  1. Start with the metric, not the optimiser. If you cannot say what a correct output is for 50 examples and agree with a colleague on them (human labels), no optimiser will rescue you. An LLM judge used as the metric is allowed, but it must be validated first (LLM-as-judge), and it can be gamed.
  2. Split three ways. Training examples feed the optimiser (demonstrations, reflection); a validation set picks among candidates; a test set is touched once. The listing above showed what happens when validation is too small.
  3. Budget the search. Optimisation costs model calls: hundreds to many thousands per run. Decide the cap in advance, log the spend, and compare the cost with the value of the improvement (cost, latency and quality).
  4. Read what it produced. Compiled prompts are text. Look at them. Optimisers sometimes find instructions that exploit quirks of the metric ("always answer yes") or leak test-like data. A prompt you cannot justify to a colleague is a risk.
  5. Treat the result as a versioned artefact. Save it, review it like a configuration change, roll it out with a canary, and keep the previous version to roll back to.
  6. Re-optimise when the model changes, and re-run the regression suite of the improvement flywheel. A prompt tuned for one model is not guaranteed to transfer.

Systems connection

A compiled prompt is a piece of configuration whose effect on behaviour is large and hard to predict. That is exactly the kind of change that configuration management warns about as a leading cause of outages. The same discipline applies: it lives in version control, changes are reviewed, rollout is staged, and a bad version can be reverted in minutes. The optimiser itself is a batch job that makes thousands of model calls, so it needs rate-limit handling, retries with backoff, and timeouts.

Key takeaways

  • A prompt is a program in English whose interpreter is a model. Because the space is discrete text with no gradients, the natural mutation operator is another language model.
  • APE, OPRO, EvoPrompt and PromptBreeder share one loop: propose candidate prompts with a model, score them on a development set, keep the best, repeat. They differ in what the proposing model sees and which operators it applies.
  • Search is a machine for finding whatever looks best on the data it can see. With a small development set it fits noise: in the listing, 8 examples gave a 97.7% dev score and 84.8% on fresh data, with a worst run at 52.5%.
  • Self-referential improvement, evolving the mutation operators themselves, can learn which moves pay, but the effect measured here was only about 1.5 standard errors. Something must stay fixed: the evaluator is not improved by the system.
  • DSPy treats a pipeline as code plus a metric: modules declare signatures, an optimiser (bootstrapped demonstrations, MIPROv2, GEPA) generates the prompts, and the result is a versioned, re-generatable artefact.
  • Run prompt optimisation with a validated metric, a three-way data split, a spend cap, human reading of the output, staged rollout and re-optimisation when the model changes.

Check your understanding

Why is a language model, rather than random word edits, the usual mutation operator for prompt evolution?

  1. Random edits are too slow to compute
  2. Meaningful changes (rewording, combining two prompts, repairing a stated failure) need an understanding of language that random edits lack, and random edits mostly produce damage
  3. Language models never make mistakes in rewriting
  4. Random edits would violate the metric
Random edits are cheap, but nearly all are harmful, so a search built on them wastes its evaluations. A model proposes edits that are coherent, though not always good (option 2 is false); the metric does not forbid random edits, it only scores them.

An evolver run with an 8-example development set reports 97.7% accuracy, but the same prompts get 84.8% on fresh data. What is the best explanation and the best fix?

  1. The test set is too easy; shrink it
  2. The model changed between the two evaluations; re-run on the dev set
  3. Evolution has converged and should run for more generations
  4. The search selected prompts that were lucky on 8 examples; use a larger development set and report only held-out results
Many candidates were tried, and with few examples the best-looking one is often a lucky one. More generations would overfit more. The test set is the honest one, and nothing in the setup changed the model.

In the self-referential experiment, adaptive operator weights improved the mean dev accuracy from 0.886 to 0.906, with a standard error of the paired difference of 0.013. How should this be described?

  1. A suggestive improvement, about 1.5 standard errors, that would need more runs before it is believed
  2. Conclusive proof that self-improvement works
  3. Evidence that adaptation hurts
  4. Meaningless, because 40 runs is never enough
The paired difference of 0.020 is roughly 1.5 times its standard error: promising but not conclusive. It is not proof (option 1), it is positive rather than negative, and 40 paired runs can detect larger effects, though not this one with confidence.

In DSPy, what do you write by hand, and what does the optimiser generate?

  1. You write the prompts; the optimiser writes the metric
  2. You write the metric and the model; the optimiser writes the training examples
  3. You write the program of modules and signatures, the examples and the metric; the optimiser generates instructions and demonstrations
  4. You write nothing; the optimiser writes the whole application
The optimiser needs a program to optimise, data to run it on, and a definition of better. It fills in the prompt wording and the few-shot examples. It cannot invent the metric, the examples or the application.

Why can the evaluator, in a self-referential system, not be one more thing the system evolves to score higher?

  1. Evaluators are written in a different programming language
  2. If the judge can change in whatever direction raises its own scores, the system can improve its marks without improving at the task
  3. It would take too long to evolve
  4. Evaluators have no parameters
A judge that is optimised for the system's benefit stops being independent. Something outside the loop must hold the objective fixed. The reasons in the other options are not the problem: nothing about language, time or parameters prevents it, only the loss of independence.

Your support-ticket pipeline fails mainly because the right policy document never reaches the model. Which action is most likely to help?

  1. Run MIPROv2 with a larger budget
  2. Evolve the instruction wording with EvoPrompt
  3. Add more few-shot examples
  4. Fix retrieval so the document reaches the prompt; no instruction wording can supply information the model never sees
Prompt optimisation tunes how the model uses the information it has. If the evidence is missing, the failure is upstream. The first three options search the prompt, which does not contain the answer.

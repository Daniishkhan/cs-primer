Lifelong Agents & Skill Libraries

A language-model agent usually starts every task from nothing. Voyager, a Minecraft agent, did something different. It chose its own next task, wrote the solution as a program, checked that it worked, and filed the program away for later. This chapter explains that three-part loop and runs a miniature version you can read end to end. It also looks hard at what a library of generated code does and does not give you.

Why this matters

Open-ended learning needs accumulation: what the agent learned yesterday must make today's problems cheaper. For a model whose weights are frozen, the usual way to accumulate is to change the weights, which is expensive and risks forgetting. Voyager showed another way: grow an external library of verified programs and let the model compose them. This is the template behind many agent designs, including the archives of agent code in meta-agent search and the self-editing agents of the Darwin Gödel Machine.

After this chapter you can describe the three components. You can explain why skills as code are different from notes or weights, and estimate what reuse saves. You can also list the ways a skill library goes bad: hidden assumptions, weak verification, stale or poisoned skills, and arbitrary code execution.

Agents that forget

Run a tool-calling agent (the agent loop) on a task and it will reason, call tools and finish. Give it a similar task tomorrow and it starts again: the model has the same weights, and the previous run lives only in a log. The agents course discusses memory, notes and skills as engineering for this problem. This chapter takes the research side: what happens if the whole system is designed around accumulation?

Two designs are tempting and both have costs. If the agent fine-tunes on its own experience, it risks catastrophic forgetting (new training overwrites old abilities), needs training infrastructure, and cannot be inspected. If it keeps free-text notes, the notes are cheap and readable. But they cannot be executed or checked, and the model must re-derive how to act on them every time. The Voyager paper chose a third option: keep programs. Its authors are Wang, Xie, Jiang, Mandlekar, Xiao, Zhu, Fan and Anandkumar (2023, “Voyager: An Open-Ended Embodied Agent with Large Language Models”). The agent is lifelong in the sense that it keeps learning across an unbounded sequence of tasks. The model itself stays fixed, and what grows is a library.

Voyager's three parts

Voyager plays Minecraft through a JavaScript API (Mineflayer), so the agent's actions are function calls such as mineBlock and craftItem. It was evaluated in the MineDojo environment (Fan et al., 2022). Three components work together.

Automatic curriculum
GPT-4, a Generative Pre-trained Transformer (GPT) language model, proposes the next task. It is given the agent's current state and its completed and failed tasks. It also gets an overall instruction: “discover as many diverse things as possible”. GPT-3.5 adds context by asking and answering questions about the situation. This is a model of interestingness inside an agent loop.
Skill library
Each successful program is stored. The key is an embedding of a description of the skill (written by GPT-3.5), and the value is the code. For a new task, the agent retrieves the five most relevant skills.
Iterative prompting
To solve a task the model writes code and runs it. It receives three kinds of feedback. The first is environment messages, for instance that a recipe is missing an ingredient. The second is execution errors from the interpreter. The third is a verdict from a separate GPT-4 critic that judges whether the task succeeded and suggests fixes. It tries for at most four rounds. If the critic confirms success, the program joins the library. If not, the task is logged as failed and the curriculum moves on.

Analogy: a cook's recipe binder

A cook who writes each tested recipe on a card, with a one-line description at the top, ends up with a binder. A new dish is usually built from existing cards: “make the stock (card 14), then proceed as in card 31”. The cook's skills improve without the cook changing. The binder does the remembering, and every card has been cooked at least once.

Where it breaks down: a recipe card is read by a human who notices that the oven is already hot. A code skill runs exactly as written, including any hidden assumption about the state of the world when it was written. Section “What goes wrong” shows this happening.

Why skills as code?

The choice of code as the memory format is the paper's main idea, and each property of code earns its place.

  • Executable, so verifiable. A program can be run, and the world says whether it worked. A note cannot be tested.
  • Composable. A new skill can call older skills, so complexity builds in layers. Voyager's authors describe the skills as temporally extended and compositional. The cost of a new, harder task is the cost of the new part, not of everything underneath (the simulation below measures this).
  • Interpretable and editable. You can read, diff and delete a skill. You cannot do that to a weight update.
  • Persistent. The library does not suffer catastrophic forgetting: writing skill 200 does not damage skill 3.
  • Portable. The library can be moved to a new world. This is how Voyager is evaluated in the generalisation test below.

A miniature Voyager

The simulation reproduces the structure, not the scale. The world is a crafting tree (wood, planks, sticks, a table, pickaxes, a furnace, iron, diamond). It has two primitives, mine and craft. Both raise a RuntimeError with an informative message when something is missing. That error text plays the role of the environment feedback in the paper.

from collections import Counter

# item -> (ingredients per unit, station that must be held).  Raw items: tool needed to mine them.
CRAFT = {"planks": ({"wood": 1}, None), "sticks": ({"planks": 1}, None),
         "crafting_table": ({"planks": 4}, None), "wood_pickaxe": ({"planks": 3, "sticks": 2}, "crafting_table"),
         "stone_pickaxe": ({"cobblestone": 3, "sticks": 2}, "crafting_table"), "furnace": ({"cobblestone": 8}, "crafting_table"),
         "iron_ingot": ({"iron_ore": 1, "coal": 1}, "furnace"), "iron_pickaxe": ({"iron_ingot": 3, "sticks": 2}, "crafting_table"),
         "stone_axe": ({"cobblestone": 3, "sticks": 2}, "crafting_table"), "iron_sword": ({"iron_ingot": 2, "sticks": 1}, "crafting_table")}
MINE = {"wood": None, "cobblestone": "wood_pickaxe", "coal": "wood_pickaxe", "iron_ore": "stone_pickaxe", "diamond": "iron_pickaxe"}

class World:
    def __init__(self): self.inv, self.steps = Counter(), 0
    def has(self, item): return self.inv[item] > 0
    def mine(self, item, n=1):
        tool = MINE[item]
        if tool and not self.has(tool): raise RuntimeError(f"cannot mine {item}: need {tool}")
        self.inv[item] += n; self.steps += n
    def craft(self, item, n=1):
        needs, station = CRAFT[item]
        if station and not self.has(station): raise RuntimeError(f"cannot craft {item}: need {station}")
        for ing, c in needs.items():
            if self.inv[ing] < c * n: raise RuntimeError(f"cannot craft {item}: need {c * n} {ing}, have {self.inv[ing]}")
        for ing, c in needs.items(): self.inv[ing] -= c * n
        self.inv[item] += n; self.steps += 1

The agent has the three components. Both language-model calls are scripted stand-ins built on RuleModel from the course's shared llm.py. The curriculum returns the first item on a fixed list that is not yet done. The code writer is a function that expands the recipe tree into Python and calls a library skill where one is listed. Like a careless first draft, it forgets to ensure a crafting station unless the feedback mentions it. Retrieval uses a hashed bag-of-words embedding in place of a real embedding model, with the task's ingredients added to the query, as an LLM's plan would. Each attempt runs in a fresh world, so a skill must work from nothing to be stored. This is a design choice with consequences, explained below.

import math, re, zlib
from world import World, CRAFT, MINE
from llm import RuleModel, count_tokens

def embed(text, dim=256):                        # stand-in embedding: hashed bag of words
    v = [0.0] * dim
    for w in re.findall(r"[a-z]+", text.lower()): v[zlib.crc32(w.encode()) % dim] += 1
    return v
def cos(a, b):
    d = math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(x * x for x in b))
    return sum(x * y for x, y in zip(a, b)) / d if d else 0.0

def write_code(prompt):
    """Scripted stand-in for the code-writing LLM. It plans by expanding the recipe tree, calls a library skill
    where one is listed, and (like a careless first draft) forgets crafting stations unless the feedback names one."""
    item = re.search(r"obtain (\w+)", prompt).group(1)
    skills = set(re.findall(r"make_(\w+)", prompt.split("Feedback:")[0]))
    known = set(re.findall(r"need (\w+)", prompt.split("Feedback:")[1]))
    lines = []
    def plan(x, k, ind):
        if x in skills: lines.append(f"{ind}make_{x}({k})"); return
        if x in MINE:
            if MINE[x]: guard(MINE[x], ind)
            lines.append(f"{ind}mine('{x}', {k})"); return
        needs, station = CRAFT[x]
        for ing, c in needs.items(): plan(ing, f"{c} * ({k})", ind)
        if station in known: guard(station, ind)
        lines.append(f"{ind}craft('{x}', {k})")
    def guard(tool, ind):
        lines.append(f"{ind}if not has('{tool}'):"); plan(tool, 1, ind + "    ")
    plan(item, "n", "    ")
    return f"def make_{item}(n=1):\n" + "\n".join(lines)
coder = RuleModel([(r"obtain \w+", lambda m: write_code(m.string))])

class Agent:
    def __init__(self, use_library):
        self.use_library, self.library, self.attempts, self.tokens, self.steps = use_library, {}, 0, 0, 0
    def retrieve(self, item, k=5):               # top-k skills whose description matches the task and its plan
        needs, station = CRAFT.get(item, ({item: 1}, None))
        query = embed(" ".join([f"obtain {item}"] + list(needs) + ([station] if station else [])))
        ranked = sorted(self.library, key=lambda s: -cos(query, embed(self.library[s][0])))
        return ranked[:k] if self.use_library else []
    def solve(self, item, max_rounds=4):
        feedback = "none"
        for r in range(max_rounds):
            world = World()                      # every attempt starts from nothing: a skill must work from a clean state
            skills = ", ".join(f"make_{s}" for s in self.retrieve(item)) or "none"
            code = coder.complete([{"role": "user", "content": f"Task: obtain {item}. Skills: {skills}. Feedback: {feedback}"}]).content[0]["text"]
            self.attempts += 1; self.tokens += count_tokens(code)
            scope = {"mine": world.mine, "craft": world.craft, "has": world.has}
            for s, (_, src) in self.library.items(): exec(src, scope)
            try:
                exec(code, scope); scope[f"make_{item}"](1)
                self.steps += world.steps
                if world.inv[item] > 0:
                    if self.use_library: self.library[item] = (f"obtain {item}", code)
                    return True
            except RuntimeError as e:
                feedback = (feedback if feedback != "none" else "") + f" Error: {e}."
        return False

ORDER = ["wood", "planks", "sticks", "crafting_table", "wood_pickaxe", "cobblestone", "stone_pickaxe", "furnace",
         "coal", "iron_ore", "iron_ingot", "iron_pickaxe", "diamond"]
curriculum = RuleModel([(r"Done: \[(.*?)\]", lambda m: next((t for t in ORDER if t not in m.group(1)), "nothing"))])

def run(use_library):
    agent, done = Agent(use_library), []
    for _ in range(len(ORDER)):
        task = curriculum.complete([{"role": "user", "content": f"Done: [{', '.join(done)}]"}]).content[0]["text"]
        if agent.solve(task): done.append(task)
    return agent, done

if __name__ == "__main__":
    for use_lib in (False, True):
        a, done = run(use_lib)
        print(f"{'with skill library' if use_lib else 'no library':20s}: {len(done)}/{len(ORDER)} tasks, {a.attempts} code-writing calls, {a.tokens} code tokens, {a.steps} game steps")
    a, done = run(True)
    print("\nstored skill make_wood_pickaxe (after one failed draft):\n" + a.library["wood_pickaxe"][1])
    print("\nnew tasks, same agent (library) against one that keeps no skills:")
    for new in ("stone_axe", "iron_sword"):
        row = []
        for use_lib in (False, True):
            ag, _ = run(use_lib)
            ag.attempts = ag.tokens = 0
            ok = ag.solve(new)
            row.append(f"{'library' if use_lib else 'no library':10s} solved={ok} calls={ag.attempts} tokens={ag.tokens}")
        print(f"{new:11s} " + " | ".join(row))
    print("\nskills retrieved (top 5) for iron_sword:", a.retrieve("iron_sword"))

    make_sticks(2 * (n))
    if not has('crafting_table'):
        make_crafting_table(1)

stone_axe   no library solved=True calls=2 tokens=291 | library    solved=True calls=1 tokens=27

Both agents finish all 13 tasks. The difference is the cost of getting there. Without a library, every task rewrites its whole dependency chain: 25 code-writing calls and 5,174 tokens of code. With the library, 17 calls and 745 tokens: about a seventh of the code. The listing of the stored make_wood_pickaxe shows the mechanism: five lines that call earlier skills (make_planks, make_sticks, make_crafting_table) and one primitive. It also shows the retry in action: the first draft omitted the table, the error said “need crafting_table”, and the second draft added the guard.

And in a new task, the payoff is sharper still. After the curriculum, each agent is asked for something it has never made. The agent with the library writes a three-line program (27 tokens) for iron_sword in one call. The one without keeps no skills and needs three calls and 1,231 tokens. The retrieval step supplied the right ingredients: for iron_sword the top five were iron_ingot, crafting_table, iron_ore, iron_pickaxe and sticks.

Common misconception

“Voyager learns, so it must be updating the model.” Nothing in Voyager's loop changes the language model's weights. The model is frozen and is called through an API. What grows is the skill library and the curriculum's record of done and failed tasks. That is why the approach works with a closed model. It is also why a library built with one model can be given to another. And it is why the approach is bounded by what the frozen model can write.

What goes wrong

Hidden assumptions

The simulation has a design choice worth explaining. In an earlier draft, every attempt ran in the same world, so the crafting table crafted for task 4 was still there for task 5. The agent stored make_wood_pickaxe without the table step (no error had occurred), and the skill passed verification. Dropped into a fresh world, it failed: the library held a skill that worked only in the state in which it was written. Making every attempt start from nothing forced the retry that exposed the missing step. Real skill libraries meet this constantly. Verification in one context says little about another, and a skill that reads or writes world state implicitly is a bug waiting for a different context. The cure comes from software testing. Verify each skill in a clean environment. State its preconditions. Add a regression run of the whole library when the world changes.

Weak verification

The critic is another language-model call, and the paper notes that self-verification can miss successes. A skill accepted wrongly is worse than a failure, because other skills build on it. The ablation (removing self-verification cut item discovery by about 73%) shows verification matters. It does not show verification is perfect. For anything with real consequences, add independent checks: tests written separately from the code, or checks against the world's own state rather than the model's opinion. This is the evaluator problem of chapter 15 in its simplest form.

Library growth and retrieval

A library of thousands of skills must be searched. Retrieval by description similarity (as in the paper, top five) misses a skill whose description is phrased differently from the query. It also returns near-duplicates that waste the context window. The toy's retrieval works because the query contains the plan's ingredient names. A harder world needs real embeddings, reranking and deduplication, the machinery of the retrieval course. Pruning matters too: skills that are never used, or that duplicate others, make the library harder to search and to trust.

Executing generated code

A skill library is a store of programs written by a model and run automatically. In Minecraft, the worst outcome is a stuck game. In a general agent with a shell, file system or network access, the same pattern is arbitrary code execution. The code is driven by text the model produced, possibly influenced by untrusted input. The skills must run in a sandbox with least privilege, and a skill added to the library from an untrusted source is a supply-chain risk. See Sandboxes & Permissions and Agent Security, and chapter 17 for self-modifying systems.

Errors that propagate and costs that compound

When skill B calls skill A, a latent bug in A appears in everything above it, and the curriculum may blame the wrong layer. Voyager's reported failures include code using non-existent APIs and curriculum tasks naming non-existent items. The entire loop is also expensive. Every task is several model calls. The paper reports GPT-4 as about 15 times more expensive than GPT-3.5, with the cheaper model used for auxiliary steps.

Systems connection

A skill library is a package registry with a dependency graph, and it should be treated like one. Each skill needs a version, tests and a way to roll back. A dependency change should trigger the tests of everything above it, as in a continuous-integration system. Running the code means isolation: a sandbox, built on containers or virtual machines, limits the damage a bad skill can do. Code you did not write is a supply-chain risk and must be treated as untrusted until verified. For the tracing of every model call and tool call in such a loop, see Tracing & Observability.

Beyond Minecraft

Minecraft is a convenient world: tasks are clear, state is observable, and failure is cheap. The pattern, however, is general. Any domain fits where successful behaviour can be written down as a short program and checked by running it. Examples are data-cleaning routines for a finance team, query templates for an analyst, and test-passing repairs for a code agent. Systems such as the meta-agent search of chapter 12 keep an archive of whole agent designs written as code. The Darwin Gödel Machine lets an agent edit its own scaffold, with an archive of the variants. They are the same idea one level up. The library holds not tasks' solutions but the agents themselves. The agents course shows how libraries of reusable skills are exposed in today's agent frameworks. The curriculum half connects back to the previous chapter: Voyager's GPT-4 proposer is a model of interestingness. The previous chapter's OMNI-EPIC (Open-endedness via Models of human Notions of Interestingness, with Environments Programmed in Code) adds an archive-based novelty gate that Voyager lacks.

State of play, October 2026

Voyager (2023) used gpt-4-0314 for the curriculum, code and critic, gpt-3.5-turbo-0301 for auxiliary steps and text-embedding-ada-002 for embeddings, with temperature 0 everywhere except 0.1 for the curriculum. Those specific models are long superseded. The results above should not be read as what current models would achieve. I did not check later Minecraft agents or reproductions, and I have not re-run Voyager. The durable lessons are the architecture (curriculum, verified skills as code, iterative repair) and the failure modes in this chapter.

Key takeaways

  • Voyager accumulates ability without changing the model. An automatic curriculum picks tasks. Iterative prompting writes and repairs code against environment errors and a critic. A skill library stores verified programs for retrieval and reuse.
  • Code is the memory format because it is executable, composable, readable and does not forget.
  • The paper reports 63 unique items, about 3.3 times the best baseline, tech tree milestones up to 15.3 times faster, and zero-shot success in a new world. Ablations show the curriculum, verification and library each matter.
  • In the toy, the library cut code written from 5,174 to 745 tokens, and a new task from 1,231 tokens to 27.
  • Skills fail through hidden assumptions about state, weak verification, retrieval misses, error propagation and cost; verify in clean environments with independent checks.
  • Generated code runs automatically, so sandboxing and supply-chain thinking are not optional.

Open Evolution Frameworks

Program evolution became practical for everyone when its ideas were reimplemented in open frameworks. This chapter opens up two of them. It shows how they organise populations into islands and archives, and how they decide which program to mutate and which model to ask. It explains why they throw away candidates that look like existing ones. It also shows how to count what a run really costs.

Why this matters

The previous chapter described two systems you can read about but not run. One has a public repository that omits the model and the infrastructure. The other is not released. Almost everyone who actually uses program evolution does so through an open framework. The differences between frameworks are mostly differences in how they spend model calls. A framework that needs 5,000 evaluations to find what another finds in 150 is the difference between a weekend experiment and a budget request.

After this chapter you can read a framework's configuration file as a set of search decisions rather than a list of mysterious knobs. You can tell which knobs matter for your problem. You also know how to account for the true cost of a run. This is also the background for Lab 3 and for the optimisation-loop design in Studio 1.

What a framework adds to the loop

The loop from the last chapter (specification, program database, prompt builder, samplers, sandboxed evaluator) is easy to draw and tedious to build well. A framework turns it into something you configure rather than write. Whatever its name, an open evolution framework supplies the following. It is worth checking each when you evaluate one.

  • A runner and a controller that keep many model calls and evaluations in flight and tolerate failures of either.
  • A program database with a policy for what to keep, how to choose parents, and how to spread the population (islands, a grid archive, or both).
  • A prompt sampler that assembles parents, "inspiration" programs and evaluator feedback into a prompt.
  • A model interface that can call several models, retry, fall back, and (in some frameworks) learn which model to use.
  • An evaluator contract: how your scoring code is called and what it returns.
  • Persistence and observability: checkpoints so a run can be resumed, a log of every program with its parent (the lineage), and a way to look at the result.

Two frameworks are worth studying side by side. OpenEvolve is a faithful, configurable reimplementation of the AlphaEvolve design. ShinkaEvolve (from Sakana AI) was designed around one complaint about the others: that they are sample-inefficient, needing thousands of model calls to find good programs. Reading them together shows the design space.

OpenEvolve: the AlphaEvolve design, open

OpenEvolve is an open-source (Apache 2.0) Python project. It was started by Asankhaya Sharma and is maintained under the algorithmicsuperintelligence organisation on GitHub. It describes itself as an evolutionary coding agent implementing AlphaEvolve. From its README, its pieces map directly onto the AlphaEvolve description in chapter 9:

Program database with MAP-Elites
This is MAP-Elites (Multi-dimensional Archive of Phenotypic Elites). Programs are placed on a grid whose axes are feature dimensions, such as program complexity, diversity, or custom metrics your evaluator returns. Each cell keeps its best program, exactly the archive of chapter 4. You choose the dimensions and the number of bins per dimension (feature_dimensions, feature_bins).
Islands with migration
Several populations (num_islands) run in parallel and exchange programs every migration_interval generations, arranged in a ring so each island passes programs to its neighbour. The README presents this as protection against premature convergence.
Prompt sampler
Each prompt includes some of the best programs (num_top_programs) and some chosen for variety (num_diverse_programs). It can also include optional evaluator artefacts, switched on by the include_artifacts option. These are error messages, warnings and model-written feedback, so the next mutation sees why a parent scored as it did. Template variations can be chosen at random for extra diversity.
Evaluator cascade
Multi-stage evaluation (cascade_evaluation) rejects weak programs early, and an optional model-based reviewer can add feedback (use_llm_feedback).
Model ensemble
A weighted list of models, with fallback. It talks to anything that speaks the common OpenAI-style API, which includes local servers.
Reproducibility
A single random_seed setting (default 42). Note what this does and does not give you. It fixes the framework's own random choices, not the model's replies, so a rerun with real models will not repeat exactly.

An evaluator in this ecosystem is a small Python file with a function that takes the path of a candidate program, runs it, and returns a dictionary of numeric metrics. A run is started from the command line with an initial program, the evaluator and a configuration file. The sketch below shows the shape. It is illustrative and was not run here. Check the exact option names and structure against the repository's current documentation, which changes.

The README's showcase is the circle-packing problem: place n = 26 circles in a unit square, without overlap, to maximise the sum of their radii. It shows the program improving from random placement in the first generation to structured packings by generations 190 and 460, and states that the result matches published benchmarks for that n. It also reports a 2.8 times speed-up for an evolved GPU kernel on an Apple M1 Pro. Treat these as demonstrations from the project's authors, not as independent benchmarks.

ShinkaEvolve: making each sample count

ShinkaEvolve is an Apache 2.0 framework installed with pip install shinka-evolve. It is described by Lange, Imajuku and Cetin (Sakana AI, 2025, "ShinkaEvolve: Towards Open-Ended And Sample-Efficient Program Evolution", arXiv 2509.19349). The Japanese word shinka means evolution. The paper's abstract states the motivation plainly: existing code-evolution methods often need "thousands of samples" to find effective solutions, and are mostly closed. It proposes three techniques, each aimed at wasting fewer model calls. A fourth idea, a meta-level summariser, is in the paper and the code.

Analogy: a test kitchen on a budget

Imagine a test kitchen with a fixed ingredient budget. Each day the head chef picks a dish from the menu board to tweak, and chooses which cook to give it to. A cheap cook is quick and often wrong. A master cook is slow and costs more. Before any tweak is cooked, the chef glances at the board and drops it if it looks like a dish already tried, because cooking it would waste ingredients. Over a few weeks the menu improves, and the chef learns which cook to trust with which dish.

Where it breaks down: a real chef tastes a dish and knows at once whether it is good. Here a dish only counts once the evaluator has run it. And “looks like a dish already tried” is judged by a crude similarity score, which can wrongly drop a tweak that was a real improvement.

1. Parent sampling that balances exploiting and exploring

Which program should the next mutation start from? Always the best is greedy hill-climbing; uniform at random wastes effort. The paper describes a family of rules between the two, including these (with F the fitness of program i):

  • Power-law on rank. Rank programs by fitness (rank 1 is best) and pick program i with probability proportional to rank−α. With α = 0 every program is equally likely; as α grows the rule approaches always picking the best.
  • Weighted. Multiply two terms. A performance term, the sigmoid of (F − median fitness) scaled by a pressure parameter λ, rises smoothly with fitness. A novelty term, 1 / (1 + number of offspring the program already has), shrinks for programs that have been parents many times. Probability is proportional to the product.

The second term is the interesting one. It says: a program that has already produced seven children, none of which beat it, is a worse bet than an equally good program nobody has tried yet. It builds a form of curiosity into the selection. The listing computes both rules for six programs.

import math

# Six programs: (fitness, number of children already produced)
progs = [(0.92, 9), (0.90, 7), (0.85, 1), (0.80, 0), (0.70, 0), (0.40, 0)]
fit = sorted(f for f, _ in progs)
median = (fit[2] + fit[3]) / 2

def power_law(alpha):
    ranks = {f: r for r, f in enumerate(sorted((f for f, _ in progs), reverse=True), start=1)}
    w = [ranks[f] ** -alpha for f, _ in progs]
    return [x / sum(w) for x in w]

def weighted(lam):
    w = [(1 / (1 + math.exp(-lam * (f - median)))) * (1 / (1 + kids)) for f, kids in progs]   # sigmoid(fitness) x novelty bonus
    return [x / sum(w) for x in w]

2. Novelty rejection sampling

Model-driven mutation produces a surprising number of near-duplicates: the model, shown a parent, returns the parent with a comment changed. Evaluating those is pure waste. ShinkaEvolve embeds each new candidate's mutable code with a text-embedding model and compares it with the programs already in the same island. If the highest cosine similarity exceeds a threshold, the candidate is rejected before evaluation, and the model is asked again, up to a limit. (The paper's circle-packing configuration lists a threshold of 0.95 and an embedding model of OpenAI's text-embedding-3-small. The repository's default is 0.99. Defaults and tuned values differ. What counts as "similar" depends on the embedding model.) An optional model judge can be consulted for borderline cases, though the paper's ablation finds it adds only marginal gains over the similarity test alone.

To see the effect, the listing below uses the stand-in mutation from the last chapter (minifun.py, which you should keep in the same folder). The embedding is also a stand-in: hashed character three-grams, normalised. It is crude, but all the filter needs is "similar text gives a similar vector". Each configuration generates 600 candidates from a noisy-greedy parent choice, and the table averages 10 seeds.

import math, random, zlib
from collections import Counter
from minifun import stand_in_llm, SEED_SRC, evaluate

def embed(src, dim=256):
    """Stand-in for an embedding model: hashed character 3-grams, L2-normalised.
    (ShinkaEvolve uses a real text-embedding model; this only needs 'similar text -> similar vector'.)"""
    v = [0.0] * dim
    for i in range(len(src) - 2):
        v[zlib.crc32(src[i:i + 3].encode()) % dim] += 1
    norm = math.sqrt(sum(x * x for x in v)) or 1.0
    return [x / norm for x in v]

cos = lambda a, b: sum(x * y for x, y in zip(a, b))

def generate(threshold, steps=600, seed=0):
    rng = random.Random(seed)
    archive, vecs, evals, rejected = {SEED_SRC: evaluate(SEED_SRC)}, [embed(SEED_SRC)], 1, 0
    for _ in range(steps):
        parent = max(archive, key=lambda p: archive[p] + rng.gauss(0, 0.5))      # noisy greedy parent
        child = stand_in_llm(parent, rng)
        v = embed(child)
        if threshold < 1 and max(cos(v, u) for u in vecs) > threshold:
            rejected += 1; continue                                               # too similar: skip the (expensive) evaluation
        evals += 1
        s = evaluate(child)
        if s is not None and child not in archive: archive[child] = s; vecs.append(v)
    return len(archive), evals, rejected, -max(archive.values())

SEEDS = range(10)
print(f"{'threshold':>9} {'rejected':>9} {'evaluated':>10} {'best bins':>10}   (600 candidates, means over 10 seeds)")
for th in (1.0, 0.999, 0.99, 0.98, 0.95):
    runs = [generate(th, seed=sd) for sd in SEEDS]
    mean = lambda k: sum(r[k] for r in runs) / len(runs)
    print(f"{('off' if th == 1 else th):>9} {mean(2):>9.0f} {mean(1):>10.0f} {mean(3):>10.2f}")

Two readings. First, most of the saving is free. Of the 600 candidates, 425 were exact or near-exact repeats of something already in the archive, so rejecting them costs nothing in quality. Second, the threshold is a real trade-off, not a hygiene setting. A strict threshold treats every neighbour of an existing program as redundant, and neighbours are where improvements come from. Programs in this toy are tiny and similar by construction. Real programs are longer, and the sensible threshold depends on your embedding model. Calibrate it on your own run by looking at what is being rejected.

3. A bandit that chooses the model

Frameworks often run an ensemble of models: a cheap fast one and a slower, stronger one. Calling them in fixed proportions is a guess. ShinkaEvolve treats the choice as a multi-armed bandit. The tree search chapter introduced UCB1 (the standard form of the upper confidence bound (UCB) rule). This is the same rule applied to models instead of tree children. For each model it keeps a count of how often it was used and the average reward it earned. It picks the model with the highest upper confidence bound, and updates the estimate after the evaluation. The reward is defined as exp(max(r − rb, 0)) − 1. Here r is the child's fitness and rb is the larger of the parent's and the initial program's fitness. A child that does not beat its parent earns nothing, and bigger improvements earn disproportionately more. The paper normalises the reward with running statistics, so that the same exploration coefficient (1.0 in the circle-packing configuration) works across tasks.

The listing simulates three stand-in models with different chances of improving a parent and different prices. "Large" improves a parent 30% of the time and costs 16 units; "medium" 15% for 4; "small" 5% for 1. Rewards follow the same exponential shape. The bandit sees only rewards, not prices, as in the paper's definition.

import math, random

# Three stand-in "mutation models". For each: chance a mutation improves on its parent, and price per call.
C = 0.15                                                   # exploration coefficient
MODELS = {"small":  (0.05, 1), "medium": (0.15, 4), "large":  (0.30, 16)}

def reward(rng, p):
    """ShinkaEvolve-style reward: exp(improvement) - 1, or 0 if no improvement. Improvement size is random."""
    return math.exp(rng.expovariate(1 / 0.25)) - 1 if rng.random() < p else 0.0

def run(policy, calls, seed, budget=None):
    rng = random.Random(seed)
    names = list(MODELS)
    n = {m: 0 for m in names}; tot = {m: 0.0 for m in names}; spent, gain = 0, 0.0
    for t in range(1, calls + 1):
        if policy == "ucb":
            untried = [m for m in names if n[m] == 0]
            if untried: m = untried[0]
            else: m = max(names, key=lambda m: tot[m] / n[m] + C * math.sqrt(2 * math.log(t) / n[m]))
        elif policy == "uniform": m = names[t % 3]
        else: m = policy                                   # a fixed model
        r = reward(rng, MODELS[m][0]); n[m] += 1; tot[m] += r; gain += r; spent += MODELS[m][1]
    return gain, spent, n

for policy in ("small", "large", "uniform", "ucb"):
    res = [run(policy, 300, s) for s in range(200)]
    gain, spent = sum(r[0] for r in res) / 200, sum(r[1] for r in res) / 200
    mix = {m: sum(r[2][m] for r in res) / 200 for m in MODELS}
    print(f"{policy:<8} total gain {gain:6.1f}  cost {spent:7.0f}  gain per unit cost {gain/spent:6.3f}  calls {mix['small']:.0f}/{mix['medium']:.0f}/{mix['large']:.0f}")
small    total gain    5.0  cost     300  gain per unit cost  0.017  calls 300/0/0
large    total gain   29.8  cost    4800  gain per unit cost  0.006  calls 0/0/300
uniform  total gain   16.6  cost    2100  gain per unit cost  0.008  calls 100/100/100
ucb      total gain   25.4  cost    3851  gain per unit cost  0.007  calls 24/48/227

The bandit allocated 227 of 300 calls to the large model and earned 25.4 units of total improvement. That is 85% of what using the large model every time earned (29.8), at about 80% of its cost. It is substantially more than splitting calls evenly (16.6). That looks like a success, and it is. But there is one caveat, which the last column makes visible: gain per unit cost is highest for the small model (0.017, against 0.006 for the large). A bandit that maximises total improvement per call will drift to the expensive model, because each call to it is likelier to pay. If your constraint is money rather than call count, the reward must include price. This is the kind of detail worth checking before trusting a default.

4. Islands, and a meta-level summariser

ShinkaEvolve also keeps islands: sub-populations all started from the same initial program and evolved in parallel. A parent is drawn by choosing an island uniformly and then choosing within it; programs may migrate between islands, but each island's best program is held back from migrating. In the paper's circle-packing configuration there are 2 islands and a migration rate of 0, so they are effectively independent. The agent configuration for AIME (the American Invitational Mathematics Examination) uses 4 islands and a rate of 0.1. Whether islands help is an empirical question for your problem, and the following small experiment is deliberately sobering. The task is a deceptive bit-string function. It has ten four-bit blocks where the all-ones block is the global optimum but is surrounded by slopes that lead away from it. A plain genetic algorithm solves it with the same total of 10,000 evaluations in four layouts.

import random

BLOCKS, K = 10, 4                                         # 10 deceptive blocks of 4 bits; optimum = all ones = 40
def fitness(g):
    f = 0
    for b in range(BLOCKS):
        u = sum(g[b * K:(b + 1) * K])
        f += K if u == K else K - 1 - u                   # trap: all ones is best, but zeros slope upward
    return f

def evolve(rng, islands, size, evals, migrate_every):
    pops = [[[rng.randint(0, 1) for _ in range(BLOCKS * K)] for _ in range(size)] for _ in range(islands)]
    used, gen, best = 0, 0, 0
    while used < evals:
        gen += 1
        for pop in pops:
            new = [max(pop, key=fitness)]                 # elitism
            while len(new) < size:
                a, b = (max(rng.sample(pop, 3), key=fitness) for _ in range(2))      # tournament of 3
                cut = rng.randrange(1, BLOCKS) * K        # one-point crossover at a block boundary
                child = [bit ^ (rng.random() < 0.01) for bit in a[:cut] + b[cut:]]  # then 1% bit flips
                new.append(child)
            pop[:] = new; used += size
        if islands > 1 and gen % migrate_every == 0:      # ring migration: each island sends its best to the next
            bests = [max(p, key=fitness) for p in pops]
            for i, p in enumerate(pops):
                p[p.index(min(p, key=fitness))] = list(bests[i - 1])
        best = max(best, *(fitness(g) for p in pops for g in p))
    return best

print(f"{'layout':<30} {'mean best':>9} {'optimum found':>14}   (16 seeds, 10,000 evaluations each)")
for name, isl, size, mig in (("1 population of 80", 1, 80, 1), ("4 islands of 20, no migration", 4, 20, 10**9),
                             ("4 islands of 20, migrate/10 gen", 4, 20, 10), ("4 islands of 20, migrate/2 gen", 4, 20, 2)):
    r = [evolve(random.Random(s), isl, size, 10000, mig) for s in range(16)]
    print(f"{name:<30} {sum(r)/len(r):>9.2f} {sum(x == 40 for x in r):>10}/16")
layout                         mean best  optimum found   (16 seeds, 10,000 evaluations each)
1 population of 80                 37.75          2/16
4 islands of 20, no migration      35.56          0/16
4 islands of 20, migrate/10 gen     38.19          2/16
4 islands of 20, migrate/2 gen     37.75          1/16

Four islands of 20 with no migration do worst: each island is too small and converges on its own trap. Add migration every 10 generations and four islands of 20 match one population of 80 (the means 38.2 and 37.8 are not distinguishable with 16 seeds). Migrating every 2 generations scores 37.8, no better than the single population. Frequent exchange turns four islands back into one population and loses the diversity islands are meant to protect. The honest summary is that islands do not make search better per evaluation here. They make it parallel and robust, as long as migration is slow enough to leave them different. Four workers can run without sharing state, and one island's collapse does not end the run.

The fourth component is a meta-scratchpad: every T generations (10 in the circle-packing configuration, with at most 5 recommendations) a separate model reads recent evaluations and extracts common strategies. It appends its recommendations to the mutation prompt. It is a small version of the self-referential loops of chapter 11.

State of play, October 2026

The ShinkaEvolve authors report four results, in Sakana AI's blog and arXiv paper from September 2025. Reproduce them before relying on them. First, a new best known solution to the 26-circle packing problem with fewer than 150 evaluations (sum of radii about 2.63598). The same blog notes that earlier approaches "often require thousands of attempts". Second, an evolved three-stage agent scaffold for AIME maths problems after 75 generations (diverse expert personas, critical peer review, then a final synthesis). Third, on the AtCoder Heuristic Contest task AHC015 from ALE-Bench, a score rising from 762,641 (the earlier ALE-Agent) to 817,371, an average improvement of 2.3%. Fourth, a new load-balancing loss for mixture-of-experts models, reported to reduce inefficient token routing by 5.81% and to raise average task performance by 1.73% across seven benchmarks. Framework option names, defaults and models supported change with each release. Check the repositories (algorithmicsuperintelligence/openevolve and SakanaAI/ShinkaEvolve) before copying a configuration from any article, including this one.

The knobs, as search decisions

Here is what each family of settings is really deciding. When a run goes badly, this table is the checklist.

num_islands, migration_interval (both)How isolated sub-populations areToo few or too much migration: premature convergence. Too many tiny islands: none makes progress.

Counting what a run costs

"Sample efficiency" only means something if you count the right things, and it is easy to be misled. Keep a ledger with these columns for every run, and publish it with any claim.

  • Model calls, split by model, with input and output tokens. This is the main cost for expensive models.
  • Evaluations, with wall-clock and compute per evaluation. For many scientific problems this is the main cost, not the model.
  • Rejected candidates: rejections save an evaluation but cost a call and an embedding. A framework that quotes "samples" without saying whether rejected candidates are included can look more efficient than it is.
  • Failures: candidates that crash, time out or fail validation still cost a call. A high failure rate is a signal that the prompt is poor or the model is weak for the language.
  • Best score against cumulative cost, as a curve, not only the final number. Two systems can end at the same score with very different curves.
  • The number of runs. A single run is an anecdote. Evolutionary search is random, so report the spread over several seeds. Note that "best of several runs" is a selection effect (the statistics of picking the best of many are the subject of chapter 16).

Systems connection

A long evolution run is a batch job with the same operational needs as any other. It must checkpoint, so that a crash at generation 380 does not cost 380 generations. It must log lineage for audit, since a program's ancestry is a trace. It must keep a budget with a hard stop. And it must respect rate limits of the model provider with timeouts, retries and backoff. Because evaluators run untrusted generated code, the sandboxing rules of the last chapter apply in full.

Common misconception

"A framework that finds the best solution in fewer samples is the better framework." Fewer samples on one benchmark says little about your problem. That is even more true when the result used one set of models and was chosen after seeing several runs. Sample efficiency depends on the evaluator (how informative its scores are), the models used, the random seed, and how the "sample" is counted. Treat published comparisons as hypotheses and run both frameworks on a small version of your problem, with your evaluator, with a fixed model budget, over several seeds.

Key takeaways

  • An evolution framework is the chapter-9 loop plus a runner, a database policy, a prompt sampler, a model interface, an evaluator contract and persistence. Its settings are search decisions.
  • OpenEvolve reimplements the AlphaEvolve design: a MAP-Elites grid over feature dimensions, ring-connected islands, prompts built from top and diverse programs with evaluator artefacts, a cascade, and a weighted model ensemble.
  • ShinkaEvolve targets sample efficiency with parent sampling (power-law or fitness-times-fewness weighting), novelty rejection by embedding similarity, and a UCB1 bandit over models, plus islands and a meta-scratchpad summariser.
  • Most model-driven candidates in a toy run were repeats, so rejecting near-duplicates saves most of the evaluations at little cost; but the threshold has a cliff.
  • A bandit that rewards improvement per call, not per unit of money, drifts to the most expensive model.
  • Islands buy parallelism and robustness, not free quality per evaluation; migration must be slow enough to leave them different.
  • Report a full cost ledger and the spread over seeds with any efficiency claim.

In the weighted parent-selection rule, a program with high fitness but seven existing children gets a lower probability than an equally fit program with none. Why is that desirable?

  1. Programs with many children are always buggy
  2. It prevents the database from growing
  3. Repeated attempts from the same parent have been tried and not improved on it, so effort is better spent where little has been tried
  4. It guarantees the best program is never selected
The 1 / (1 + children) factor is a curiosity bonus: untried parents have unknown potential. It does not mean the children were buggy, it does not stop the database growing, and the best program still gets a good share (though not all of it).

In the novelty-filter experiment, the 0.999 threshold cut evaluations from 601 to 176 with no loss in the best score, while 0.95 cut them to 6 and made the result worse. What explains the difference?

  1. At 0.999 only exact or nearly exact repeats are rejected, whereas at 0.95 genuine neighbours of existing programs, where improvements live, are rejected too
  2. At 0.95 the embedding model stops working
  3. Lower thresholds evaluate more programs
  4. The seeds were different in the two settings
Similarity above 0.999 means essentially the same text, so rejecting it loses nothing. A looser rule (reject above 0.95) removes almost every mutation of existing programs. Lower thresholds reject more, not fewer, and the same 10 seeds were used throughout.

A bandit chooses among three models using reward = improvement over the parent. It ends up calling the expensive model 227 times in 300. Gain per unit cost was highest for the cheapest model. What should you change if your real constraint is money?

  1. Nothing: the bandit is already optimal
  2. Put cost into the reward, for example improvement per unit price, so the bandit optimises what you actually care about
  3. Remove the exploration term
  4. Always use the cheapest model without measuring
The bandit optimises whatever reward it is given. Reward per call favours the model that most often improves, regardless of price. Removing exploration risks locking onto a wrong estimate, and always using the cheapest model ignores that the large model may improve results the cheap one never reaches.

In the island experiment, four islands of 20 with migration every 10 generations performed about the same as one population of 80. Which conclusion is best supported?

  1. Islands always improve search quality per evaluation
  2. Migration should be as frequent as possible
  3. Islands are useless and should be removed
  4. Islands with slow migration can match a single population while allowing parallel, independent workers; they should not be expected to beat it per evaluation on this evidence
The experiment shows parity, not superiority, and shows that no migration (small isolated islands) and very frequent migration were both worse or no better. The benefit is operational: independent workers and resilience.

A blog post says Framework A found a solution in 150 samples and Framework B needed 3,000. Which question should you ask first?

  1. What counted as a sample, on what evaluator and model, and over how many seeds and runs
  2. Which framework has the more attractive name
  3. Whether the solution was written in Python
  4. Whether the blog used a dark theme
"Sample" can include or exclude rejected and failed candidates; different models and evaluators change difficulty; a single run is an anecdote. The other options do not bear on whether the comparison is fair.

OpenEvolve's MAP-Elites grid uses feature dimensions such as program complexity. What is the danger in choosing dimensions that have nothing to do with quality or useful behaviour?

  1. The evaluator will crash
  2. The grid will have too many empty cells to display
  3. The archive preserves a tidy but meaningless spread of programs, and diversity is wasted on differences that do not matter
  4. The model will refuse to produce code
An archive keeps the best program per cell, so the choice of axes decides what kinds of variety survive. Arbitrary axes keep arbitrary variety. Empty cells are normal in any archive, and the evaluator and model are unaffected by the axes.

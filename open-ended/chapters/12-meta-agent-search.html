Automated Design of Agentic Systems

Every agent you have built so far was designed by a person. Someone chose the prompts, the loop, the number of retries and the checks. This chapter asks what happens if a language model designs the agent instead. The model writes each candidate as code, tests it, and learns from an archive of everything it has tried. It covers the method called Meta Agent Search, what its results do and do not show, and the evaluation traps that a search like this walks into.

Why this matters

Part 3 evolved programs that solve a problem. Part 4 moves one level up: the thing being evolved is the program that solves problems, an agent. That jump changes what can go wrong. A search over agent designs is a search over code that will be run, scored and kept. So three things become central: the quality of the score, the split between search data and test data, and the safety of running generated code. After this chapter you can describe how a meta agent is built and write a miniature one that runs offline. You can also read the original paper's numbers with the right amount of scepticism. And you can say what a search set must look like before you believe the winner. The next chapter lets the agent edit itself. This one keeps the designer and the designed separate. That is the simpler case, and the one most teams can use today.

Agents as designs

Take any agent from the agents course: a support bot that looks up orders, a research assistant that searches and cites, a code reviewer. Strip away the particular task and what remains is a design: a choice of components and how they are wired. Does it call the model once or five times? Does it write a plan first? Does a second model critique the first? Are answers voted on? Does it retry when a check fails, and how many times? The workflow patterns chapter names the common wirings (chaining, routing, parallelising, evaluator-optimiser loops). Choosing among them, and tuning each, is design work, and for most teams today it is done by hand, by trial and error, guided by taste.

Hand design has a familiar weakness: the space is large, the interactions are not obvious, and a design that wins on one task may lose on the next. Machine learning has met this situation before. Features were once hand-crafted and are now learned. Network architectures were once hand-drawn and are now sometimes searched (neural architecture search). Hu, Lu and Clune (2024) make the same bet for agents. Their paper “Automated Design of Agentic Systems” was published at the International Conference on Learning Representations (ICLR) in 2025. They name the research area Automated Design of Agentic Systems (ADAS). They argue that hand-designed agents will eventually be replaced by learned ones. Their abstract states the motivation bluntly: the history of machine learning teaches that hand-designed solutions are eventually replaced by learned solutions.

This is the AI-generating algorithms programme of Jeff Clune (2019), "AI-GAs (AI-generating algorithms): an alternate paradigm for producing general artificial intelligence". It has three pillars. The first is to meta-learn the architectures. The second is to meta-learn the learning algorithms. The third is to generate the learning environments. ADAS sits in the first two. The environment-generation pillar is the territory of the Paired Open-Ended Trailblazer (POET) and OMNI-EPIC (Open-endedness via Models of human Notions of Interestingness, with Environments Programmed in Code). Both are covered earlier in this course. All three pillars rely on the same ingredient that the first half of the course developed: an archive of diverse stepping stones. That is why this chapter comes after quality-diversity and program evolution.

The three parts of any ADAS method

The paper decomposes every ADAS algorithm into three components, and the decomposition is the most reusable idea in it. It works as a checklist for any "optimise an agent" project, including ones that have nothing to do with this paper.

Search space
Which agents can be represented at all. If the space is “the wording of one prompt”, then the search can never change the workflow. If it is “choose among five fixed pipelines”, it can never invent a sixth. The space limits the best possible answer before any search happens.
Search algorithm
How the space is explored: random sampling, evolution, Bayesian optimisation, or, here, a language model that reads what has been tried and writes the next candidate.
Evaluation function
How a candidate is scored: accuracy on a set of questions, cost, latency, a safety measure, or a mix. The search can only be as good as this score is honest.

Why the search space is code

Earlier attempts to automate agent design searched small spaces. Some optimised the text of a prompt (OPRO, Yang et al., 2024, and the prompt optimisers of chapter 11). Others searched over graphs of predefined nodes. Both are limited in the way above: the best agent they can find is a better version of the shape you already gave them. A prompt optimiser cannot decide that an answer should be produced five times and compared.

The ADAS paper's central design choice is to make the space programs. An agent is a Python function. A general-purpose programming language is Turing complete, which means it can express any computation. So the space contains every agent you could write: loops, branches, tools, calls to other models, data structures and new helper functions. Code has three practical advantages beyond completeness. It is executable, so a candidate can be scored automatically with no human in the loop. It is readable, so when the search finds something strong, a person can inspect it and learn the pattern, which matters for safety as well as insight. And it is composable, so a later candidate can reuse a piece of an earlier one, the way a Voyager skill is reused (chapter 7).

Total freedom would make the model waste most of its effort on boilerplate. So the authors supply a tiny framework, under 100 lines in the paper's description. It holds the basics: helpers for querying a foundation model and formatting prompts, plus a convention for the entry point. The meta agent only has to write one function, forward, which takes the task information and returns the agent's answer. FunSearch (chapter 9) uses the same trick. Fix everything that is not interesting, and let the model write only the interesting part.

An agent in this framework looks like ordinary code. The paper's own example of “self-reflection” is a loop. It asks a model to reason step by step. It asks a second module, acting as a critic, whether the answer is right. If not, it adds the critic's feedback to the context and tries again, up to five times. Nothing about it is special syntax. It is a for loop around model calls. That is the point: the vocabulary of agent design (reflection, debate, ensembling, role assignment) is already the vocabulary of ordinary control flow.

Meta Agent Search, step by step

The algorithm, which the paper calls Meta Agent Search, is short enough to state in five lines. A meta agent is a language model prompted to design agents. It keeps an archive, a growing store of every agent discovered so far together with its score.

  1. Seed the archive (optionally) with well-known hand-designed agents such as chain-of-thought, self-consistency and self-refine. These are the first stepping stones.
  2. Design. The meta agent receives the task description, the framework and the whole archive, and is asked to propose something “interestingly new”. It first writes a high-level description of the idea, then the code.
  3. Reflect. The design goes through two rounds of self-reflection. In them the meta agent checks whether the proposal really differs from the archive, and fixes mistakes in the code.
  4. Evaluate. The candidate runs on a search (validation) set from the target domain. If the code throws an error, the meta agent is shown the error and reflects and repairs, up to five times.
  5. Archive. The agent is stored with its metrics, and the loop repeats with the larger archive until the iteration budget is spent. The best archived agent is then scored once on held-out test data.

Two details deserve attention. First, the prompt asks for interestingly new agents, not merely better ones. That is the same instinct as the novelty and interestingness chapters. A language model can serve as a model of what counts as new, and here it is applied to code. Second, the archive is not a population that gets culled. Everything stays, including agents that scored worse than their parent, because a design that looks poor today may carry an idea a later design needs. The paper reports exactly this. A pattern from iteration 3 (several chain-of-thought answers, refined, then ensembled) became a stepping stone that many later designs used. The best agent's complex feedback mechanism was built from three ideas introduced at iterations 5, 11 and 12. None of them achieved high performance when it first appeared.

A meta-agent search you can run

The real method needs a strong model, an evaluation harness and a few hundred dollars. Its structure does not. The example below keeps every structural element: agents as source code, an archive, a proposer, a novelty check, error repair, a search set and a held-out set. It replaces the two things that need a real model with deterministic stand-ins:

  • The foundation model inside the agents is a RuleModel from lab-support/llm.py. It answers short arithmetic questions correctly with a stated probability that falls with difficulty. It uses a hash rather than a random number generator, so the same prompt always gets the same reply. A harder question, or the same question with a different “attempt” number, gets an independent draw.
  • The meta agent is a scripted proposer. A real meta agent writes free-form code. This one changes one of three knobs and renders the result as Python source. The knobs are single-step or step-by-step solving, how many samples to vote over, and how many verify-and-retry rounds to run. It is a stand-in, and its candidates are far less creative than a language model's.

The task is multi-step arithmetic read strictly left to right ("3 + 4 * 2" is 14), with 1 to 5 operations per question. A direct answer is right 95% of the time with one operation and 40% of the time with five. A single step (two numbers and one operator) is right 93% of the time. A critic catches 75% of wrong answers and raises a false alarm on 8% of right ones. These numbers are the assumptions of the stand-in, not measurements of any real model. First, the world:

"""world.py: a tiny task, a stand-in 'foundation model', and the framework agents are written against."""
import hashlib, random, re
from llm import RuleModel

def uniform(*parts):                       # deterministic "randomness" from a hash
    h = hashlib.sha256("|".join(map(str, parts)).encode()).hexdigest()
    return int(h[:12], 16) / 16**12

def evaluate(expr):                        # strictly left to right: 3 + 4 * 2 = 14
    t = expr.split(); v = int(t[0])
    for op, n in zip(t[1::2], t[2::2]):
        v = v + int(n) if op == "+" else v - int(n) if op == "-" else v * int(n)
    return v

def make_questions(n, seed):
    rng, out = random.Random(seed), []
    for i in range(n):
        k = 1 + i % 5                      # number of operations: the difficulty
        e = str(rng.randint(1, 9))
        for _ in range(k):
            e += f" {rng.choice('+-*')} {rng.randint(1, 9)}"
        out.append((e, evaluate(e)))
    return out

P_DIRECT = {1: .95, 2: .85, 3: .70, 4: .55, 5: .40}   # chance one direct answer is right
def _answer(m, p):                         # right with probability p, else off by a little
    key = m.group(0); u = uniform("ans", key)
    truth = evaluate(m.group(1))
    return str(truth if u < p else truth + 1 + int(uniform("off", key) * 3))

def _check(m):                             # a critic: catches 75% of wrong values, 8% false alarms
    expr, val, att = m.group(1), int(m.group(2)), m.group(3)
    u = uniform("chk", expr, val, att)
    return ("WRONG" if u < .75 else "OK") if val != evaluate(expr) else ("OK" if u < .92 else "WRONG")

MODEL = RuleModel([
    (r"DIRECT: (.+?) \| attempt \d+", lambda m: _answer(m, P_DIRECT[len(m.group(1).split()) // 2])),
    (r"STEP: (.+?) \| attempt \d+",   lambda m: _answer(m, .93)),
    (r"CHECK: (.+?) = (-?\d+) \| attempt (\d+)", _check),
])
calls = 0
def ask(text):
    global calls; calls += 1
    return MODEL.complete([{"role": "user", "content": text}]).content[0]["text"]

# ---- the framework: the only functions an agent's code may use ----
def solve_direct(q, i):
    return int(ask(f"DIRECT: {q} | attempt {i}"))
def solve_steps(q, i):
    t = q.split(); acc = t[0]
    for op, n in zip(t[1::2], t[2::2]):
        acc = ask(f"STEP: {acc} {op} {n} | attempt {i}")
    return int(acc)
def verified(q, v, i):
    return ask(f"CHECK: {q} = {v} | attempt {i}") == "OK"
def majority(xs):
    return max(sorted(set(xs)), key=xs.count)

Agents may call only the four framework functions at the bottom, which mirrors the paper's design of a fixed framework with a free forward. Now the search itself. Note exec in run_agent: it runs source text as code. That is safe here because the text comes from our own templates. It is exactly the line that would need a sandbox if a real model wrote the source (see the safety section below).

"""search.py: Meta Agent Search in miniature. A scripted proposer stands in for the meta agent."""
import random, world
from world import make_questions

def render(solver, samples, retries, typo=False):
    """Write an agent as source code (what a real meta agent writes freely)."""
    body = [f"def forward(q):", f"    xs = [solve_{solver}(q, i) for i in range({samples})]",
            f"    v = majority(xs)"]
    if retries:
        body += [f"    for r in range({retries}):",
                 f"        if verified(q, v, r): break",
                 f"        v = solve_{solver}(q, 100 + r)"]
    body.append("    return vv" if typo else "    return v")
    return "\n".join(body)

def run_agent(source, questions):
    ns = {k: getattr(world, k) for k in ("solve_direct", "solve_steps", "verified", "majority")}
    exec(source, ns)                       # DANGER with real model-written code: sandbox it
    world.calls = 0
    right = sum(ns["forward"](q) == a for q, a in questions)
    return right / len(questions), world.calls / len(questions)

search_set, held_out = make_questions(60, seed=1), make_questions(400, seed=2)
rng = random.Random(7)
archive = [dict(name="direct", genes=("direct", 1, 0)), dict(name="vote3", genes=("direct", 3, 0))]
for a in archive:
    a["src"] = render(*a["genes"]); a["score"], a["cost"] = run_agent(a["src"], search_set)
    print(f"seed     {a['name']:14s} search {a['score']:.3f}  calls/question {a['cost']:4.1f}")

for it in range(1, 13):
    parent = rng.choice(sorted(archive, key=lambda a: -a["score"])[:3])      # look at the best few
    while True:
        g = list(parent["genes"]); k = rng.randrange(3)
        g[k] = rng.choice([["direct", "steps"], [1, 3, 5], [0, 1, 2]][k])    # one knob changes
        if not any(a["genes"] == tuple(g) for a in archive): break           # "is it interestingly new?"
    typo = rng.random() < 0.25
    for attempt in range(5):                                                 # up to 5 error refinements
        src = render(*g, typo=typo and attempt == 0)
        try:
            score, cost = run_agent(src, search_set); break
        except NameError as e:
            print(f"iter {it:2d}  runtime error ({e}); self-reflect and retry")
    name = f"{g[0]}-x{g[1]}-v{g[2]}"
    archive.append(dict(name=name, genes=tuple(g), src=src, score=score, cost=cost))
    print(f"iter {it:2d}  {name:14s} search {score:.3f}  calls/question {cost:4.1f}  (parent {parent['name']})")

print("\nbest 3 on the search set, re-scored on 400 held-out questions:")
for a in sorted(archive, key=lambda a: -a["score"])[:3]:
    t, c = run_agent(a["src"], held_out)
    print(f"  {a['name']:14s} search {a['score']:.3f}  held-out {t:.3f}  calls/question {c:4.1f}")
t, _ = run_agent(archive[0]["src"], held_out)
print(f"  baseline direct  held-out {t:.3f}")
print("\nbest agent source:\n" + sorted(archive, key=lambda a: -a["score"])[0]["src"])

Read the output as the paper's authors would. The two seeds are the hand-designed baselines: a direct answer scores 0.650 on the 60 search questions and a vote of three direct answers scores 0.900. The proposer then walks outwards. Iteration 1 produces a step-by-step solver that scores lower than the vote (0.833), and a greedy method would drop it. The archive keeps it, and it is the parent of the lineage that ends in the winner. That lineage adds a verifier (0.933), adds a second retry (0.967), then votes five times (1.000, at about 17 model calls per question). Iteration 6 is a dip, 0.800, kept anyway. Three of the proposals contained a typo (vv) and threw a NameError. Each was repaired on the next attempt. In a real run that repair loop is the meta agent reading a traceback.

The last block is the one that matters most. Re-scored on 400 questions the search never saw, the top three agents get 0.990, 0.988 and 0.988, and the direct baseline gets 0.708. The gain is real in this toy world. Two further points are visible only if you look. First, the winner by search score is not clearly better than the runner-up, because 1.000 against 0.983 on 60 questions is one question. Second, it costs 16.3 calls per question against 10.3, so a cost-aware score would pick the cheaper agent. The paper's evaluation function is accuracy alone, which is a choice, and a different one gives a different winner.

Step through

How the archive grew in the run above

  1. Seeds. The archive starts with two hand-written agents: one direct answer (0.650 on the search set) and a vote of three (0.900). Scores are on the 60 search questions; calls are model calls per question.
  2. Iteration 1: a worse idea, kept. Solving step by step, with a single sample, scores 0.833, below the vote. A hill climber would discard it. The archive does not, and the proposer's parent here is the weak seed direct.
  3. Iteration 2: an error and a repair. The first draft of the vote-of-five agent referred to a variable that does not exist and raised a NameError. The error message goes back to the proposer, which fixes it on the next attempt. Result: 0.883.
  4. Iteration 3: add a verifier. A child of the step-by-step agent adds one verify-and-retry round and jumps to 0.933 for about two more calls per question.
  5. Iteration 4: a side branch. Adding two retries to the vote of five gives 0.917. Good, not the best, and the branch goes no further.
  6. Iteration 5: a second retry. The step-by-step lineage reaches 0.967 at 5.3 calls per question. This is the cheapest agent in the archive above 0.95.
  7. Iteration 6: a dip. Switching this agent back to direct answers scores 0.800. It is stored, scored and inspected like any other; the search never needs to know in advance which idea will pay off.
  8. Iteration 7: the winner by search score. Five step-by-step votes plus two retries: 1.000 on the search set, 16.8 calls per question.
  9. The held-out check. On 400 questions the search never saw, the winner scores 0.990 against 0.708 for the direct baseline. Two other agents are within a hair of it at lower cost.

Analogy: a lab notebook that nobody tears pages from

Picture an engineer designing a bridge by building scale models. Each model is tested in a wind tunnel and the result is written in a notebook beside a sketch. The engineer keeps every page, including the models that failed. Each new sketch starts by leafing through the notebook. The cable layout from model 5 and the deck shape from model 11 turn out to belong together. The meta agent is that engineer, the archive is the notebook, and the search set is the wind tunnel.

Where it breaks down: a wind tunnel measures physics that does not care how many models you test. The search set is a finite sample, and each extra model tested against it makes the best result look better than it is (the next sections). The engineer is also a language model that can write a model that only looks good in the tunnel.

What the paper reports

Hu, Lu and Clune evaluated Meta Agent Search on six settings. The setup matters for reading the numbers, so here it is plainly. In every experiment the meta agent is a strong model: a GPT (Generative Pre-trained Transformer) model, GPT-4, for the ARC run, and gpt-4o-2024-05-13 for the others. The discovered agents and the baselines run on a cheaper one, gpt-3.5-turbo-0125, to keep evaluation affordable. All baselines were re-implemented inside the same framework as the discovered agents, for a fair comparison, and were also used as the seeds of the archive.

  • ARC (the Abstraction and Reasoning Corpus, Chollet 2019): small grid puzzles, solved by having the agent write code. Questions have grids up to 5 × 5. There is a search set of 20 and a test set of 60. Each is evaluated five times to reduce sampling noise. The search runs for 25 iterations.
  • Four reasoning benchmarks: DROP (reading comprehension, scored by F1), MGSM (the multilingual grade school maths benchmark, scored by accuracy), MMLU (multi-task knowledge) and GPQA (graduate-level science questions). Each has a search set of 128 questions and a test set of 800 (GPQA Diamond: 32 and 166). The search runs 30 iterations, separately for each domain.
  • Transfer: take agents found on MGSM and run them, unchanged, on other maths sets and on non-maths domains. Also take agents found with the cheap model on ARC and swap the model underneath.

The headline comparison is from their Table 1, which gives test accuracy. The paper also gives 95% bootstrap intervals, about ±3 points for the accuracy columns and ±1 for DROP:

Four patterns are worth stating. The gain depends on what limits the model. On DROP the best baseline scored 65.8 F1 and Meta Agent Search 79.4 (13.6 points); on MGSM 39.0 against 53.4 (14.4 points). On MMLU (65.9 against 69.6) and GPQA (31.6 against 34.6) the improvement is a few points, inside the reported uncertainty. The authors' explanation is that on hard knowledge questions the model lacks the facts, and no wiring can add them. Reading and arithmetic errors are different. Checking, decomposition and voting can repair those. That is a hypothesis, reasonable but not tested in the paper. Search beats prompt-only optimisation in all four columns. Prompt optimisation in the style of Optimisation by PROmpting (OPRO) scored 69.1, 30.6, 67.6 and 32.9. The win is clear on DROP and MGSM and within the intervals on MMLU and GPQA. This supports the argument for a code-shaped space. Transfer worked. The top three MGSM agents, with no change, scored 69.5, 64.5 and 64.9 on GSM8K (grade school maths, 8,000 questions), where the best baseline scored 43.6. The best of them is 25.9 points ahead. The top agent scored 31.2 on the harder GSM (grade school maths) variant, GSM-Hard, against 18.0. On non-maths data the picture is weaker. The same agents scored 70.4, 70.4 and 71.9 F1 on DROP against a best baseline of 65.8. But they scored 62.4, 67.0 and 64.8 on MMLU against baselines between 63.5 and 65.9, which is a tie, not a win. Agents found with GPT-3.5 on ARC and then run on Claude Sonnet reached 48.3% for the best, against 39.3% for the best hand-designed baseline. On GPT-4 they were 37.0 against 23.0. Seeding is not required. One run that started from an empty archive reached 73.9 F1 on DROP (below the seeded run's 79.4) and 67.5% on MGSM (above the seeded run's 53.4). With a single run per setting, differences of that size say little about which start is better. They do say that human-designed seeds are not what makes the method work.

State of play, October 2026

All figures above come from the paper (arXiv 2408.08435 v2, revised March 2025). They were produced with 2024 models: a GPT-3.5 evaluator and GPT-4-class meta agents. Absolute scores are not comparable with anything run on a current frontier model. The gain over hand-designed baselines is likely to shrink where current models already reason well without scaffolding. Whether it does is an empirical question I have not surveyed. What carries forward is the shape of the method. The Darwin Gödel Machine (DGM) paper (next chapter) re-implements this method as a baseline, “DGM without self-improvement”, in which the meta agent is fixed. The ADAS code is open source (github.com/ShengranHu/ADAS).

The catch: the best of many looks better than it is

Return to the mini search. It evaluated 14 agents on 60 questions and kept the highest. Suppose several of them were truly identical in skill. Each would still score a little differently on the search set by luck. Picking the top scorer picks the luckiest as well as the best. This is the winner's curse. The best of many noisy measurements is biased upwards. The bias grows with the number of candidates and shrinks with the size of the search set. It is the same effect as picking the best of 100 stocks by last year's return. It is also why a search set that works well for comparing two agents works badly for ranking two hundred.

Here is the effect in numbers. The script below gives each design a true accuracy drawn around 60%, with a spread (standard deviation) of 5 points. A search set of 20 or 200 questions scores each one. The script keeps the top scorer and then reports what that pick is really worth. Each row is the average of 2,000 repeated searches.

"""curse.py: pick the best of N agent designs by a small search set, then see how good it really is."""
import random

def trial(rng, n_designs, n_questions, mean=0.60, spread=0.05):
    true = [min(0.99, max(0.05, rng.gauss(mean, spread))) for _ in range(n_designs)]
    seen = [sum(rng.random() < p for _ in range(n_questions)) / n_questions for p in true]
    pick = max(range(n_designs), key=lambda i: seen[i])
    return seen[pick], true[pick], max(true)

rng = random.Random(0)
print("designs  questions | looks like  really is  best available")
for n_designs in (1, 10, 100):
    for n_questions in (20, 200):
        r = [trial(rng, n_designs, n_questions) for _ in range(2000)]
        a, b, c = (sum(x[i] for x in r) / len(r) for i in range(3))
        print(f"{n_designs:7d}  {n_questions:9d} |   {a:.3f}      {b:.3f}      {c:.3f}")

With one design there is no curse: it looks like 60% and is 60%. With 100 designs and 20 questions, the winner looks like 87.7% and really is 65.0%. That is an overstatement of nearly 23 points. The best available design was 72.5%, so the search also missed 7.5 points. With 200 questions the overstatement falls to about 4.6 points, and the pick is closer to the best. The remedy is not more cleverness in the proposer. It is a bigger search set, a separate held-out set that is scored once, and honest reporting of how many candidates were tried. The paper does the second of these, because its search set and test set are disjoint. But its ARC search set had only 20 questions and its GPQA search set 32. That is small enough for this effect to bite. Chapter 16 turns this into a procedure, and the statistics chapter of the evals course gives the interval calculations behind it. Common misconception

"The paper's test set is separate from the search set, so the reported numbers are unbiased." Partly. The test numbers in Table 1 are not inflated by the winner's curse, because the test set is scored after the choice is made. But the test set was also used to compare methods and to decide what to report. A single search run per setting also has its own variance. The empty-archive runs above differ from the seeded runs by up to 14 points on MGSM. Separate sets remove one source of bias. They do not make one run representative.

Where it goes wrong

Cost

The paper reports that one search-and-evaluation run on ARC cost about $500 in API fees. A run in the reasoning domains cost about $300. Most of that came from running candidate agents on the evaluation model. These are 2024 prices for cheap models. The cost structure is the lasting lesson. Every candidate must be run on every search question, often several times. A candidate that makes 17 model calls per question, as the winner above does, costs 17 times as much to evaluate as a single call. The usual remedies are a cost term in the score, a cheap early screen on a handful of questions, or a successive-halving schedule. In that schedule you evaluate on few questions and give more to the survivors. The paper itself notes that its evaluation function is naive and expensive and expects better ones to cut the cost.

Narrow scoring

A score of accuracy alone prefers the expensive winner above. The paper mentions cost, latency and safety as other objectives worth optimising. In a product the real objective is nearly always a trade-off. Compare the quality, cost and latency table in the evals course. The search will find whatever the score pays for and nothing else.

A fixed framework and a fixed meta agent

The meta agent can only write what the framework supports, and the meta agent itself never changes. If the framework offers no retrieval function, no agent will use retrieval. The loop also never improves the proposer: iteration 100 uses the same prompt as iteration 1. The next chapter's system removes that second limit by letting the agent that designs be an agent that is itself edited.

Running model-written code

Every candidate is code produced by a model and then executed, usually with network access and credentials for the model API. The paper says the authors ran generated code in containers, inspected the results manually, and put warnings in the repository. It notes that overtly malicious output is unlikely with current models. But it adds that capability limits can still make generated code destructive. Treat that as the minimum. A candidate can loop forever, exhaust memory, call tools it was never meant to call, or read the answers if the evaluation data are on disk. The sandboxing chapter of the agents course lists the controls: containers or virtual machines, no network except the model endpoint, resource limits and throwaway file systems. Chapter 17 develops them for self-modifying systems.

Systems connection

Running candidate agents is untrusted-code execution. So the isolation techniques from containers and virtual machines apply directly. The least-privilege principle says each candidate should hold no credentials beyond the one model endpoint. Evaluating hundreds of candidates is also an ordinary batch workload. Each run is independent, so failures, timeouts and retries need the discipline of failure handling in distributed systems. And if the design you ship came from a search, treat the search as part of your release process. Record the search set, the number of candidates tried and the chosen source code, as you would for any model you deploy.

When to use it, and when not to

Meta Agent Search suits a situation with four features. There is an automatic, trustworthy score (an exact-match answer, a test suite, a checker). There are enough labelled questions to split three ways (search, selection, final test). The design space is wide and poorly understood, so you do not already know the right wiring. And each evaluation is cheap enough to afford hundreds. A coding agent with a test suite fits. A customer-facing assistant whose quality only a human can judge usually does not. The score is the weak link, and the search will faithfully optimise whatever flaws it has (chapter 15). Suppose you have a good evaluation and a small design space of two or three choices. Then a plain grid search over the choices does the same job with no model-written code to sandbox. That is the lesson of chapter 18: simpler methods win more often than the papers suggest.

Key takeaways

  • ADAS has three parts: a search space, a search algorithm and an evaluation function. Meta Agent Search chooses code for the space, a language model for the algorithm and task accuracy on a search set for the score.
  • Code is the right space because it is complete (any workflow is expressible), executable (scoring is automatic), readable and composable. A prompt-only space cannot change the workflow.
  • The archive keeps everything, including worse agents, so that ideas introduced early can be combined later. This is the stepping-stone argument of the quality-diversity chapters applied to agent code.
  • The paper reports gains over hand-designed agents of 13.6 F1 points on DROP and 14.4 accuracy points on MGSM, small gains on MMLU and GPQA, and transfer across models and domains. All numbers use 2024 models and single search runs.
  • The best of many candidates is biased upwards. Use a large search set, score a separate held-out set once, and report how many designs were tried.
  • Candidate agents are model-written code: run them in a sandbox, give them no credentials beyond the model endpoint, and score cost as well as accuracy.

Check your understanding

A team wants to automatically improve its support agent. Option A optimises the text of the system prompt. Option B lets a model write the agent's whole control flow as Python. Which statement about the search spaces is correct?

  1. A is larger because prompts can say anything in natural language.
  2. They are equal in power, because the prompt can describe any control flow to the model.
  3. B can express designs A cannot, such as sampling five answers, comparing them and retrying, because the prompt-only space cannot change the workflow.
  4. B is smaller, because code must compile.
The search space limits what any algorithm can find. Prompt optimisation changes the words inside a fixed workflow; it cannot add a loop or a vote. Code is Turing complete, so every workflow you could write is in the space. Option A is tempting because natural language feels unlimited, but the workflow around the prompt stays fixed.

In the mini search, the proposer keeps generating candidates until one is not already in the archive. Which part of Meta Agent Search does this stand in for?

  1. The meta agent's self-reflection that checks a proposal is interestingly new compared with the archive.
  2. The held-out evaluation.
  3. The repair loop for runtime errors.
  4. The seeding of the archive with baselines.
The paper has the meta agent reflect twice on each design to confirm it differs from what is already stored; the stand-in does the same with an exact-match test on the knob settings. The repair loop is a different mechanism (it handles errors, not duplicates), and the held-out evaluation happens after the search ends.

A search tried 12 designs and the best scored 0.97 on a 60-question search set. You score that design once on 400 fresh questions. What should you expect?

  1. Exactly 0.97, because accuracy is a property of the agent.
  2. Higher than 0.97, because the held-out set is larger.
  3. Whatever the search set said, within one question.
  4. Probably lower than 0.97, because choosing the best of 12 noisy scores selects partly for luck.
This is the winner's curse. A set of 60 questions measures each design with several points of noise, and the top scorer of 12 is likely to have drawn positive noise. A larger held-out set does not raise the true accuracy; it just measures it more tightly. In the mini run the effect happened to be small (0.990 held-out for a 1.000 search score), but the expectation is a drop.

You want to shrink the gap between a winner's search score and its real accuracy. Which single change helps most, other things equal?

  1. Run the search for twice as many iterations.
  2. Use a larger search set (for example 200 questions instead of 20).
  3. Use a stronger model as the meta agent.
  4. Remove the worst agents from the archive.
The overstatement comes from measurement noise on the search set, which falls with the number of questions. More iterations means more candidates and a larger bias. A stronger meta agent changes what is proposed, not how well it is measured. Pruning the archive changes nothing about the noise in the scores of the survivors.

The paper finds that agents searched on MGSM maths also beat hand-designed agents on GSM8K and DROP, and roughly tie them on MMLU. What is the fairest conclusion?

  1. Meta Agent Search finds agents that will outperform hand-designed agents on every task.
  2. The search set must have leaked into the other test sets.
  3. The discovered design patterns (decomposing, checking, ensembling) are not tied to one question set, though the evidence is mixed outside maths and covers a handful of benchmarks with a single search run each.
  4. Transfer results are meaningless because the model was different.
Transfer to data the search never saw is evidence that the gain is a reusable pattern and not overfitting to the search questions. It is still evidence from a few benchmarks with single runs, so "every task" overreaches. Leakage is an unfounded accusation here, since the sets are different benchmarks, and a changed model is the very thing the transfer test is designed to vary.

Your meta agent writes Python agents, and your harness runs them with exec on a machine that holds your cloud credentials. Which change reduces risk most?

  1. Ask a second LLM to review each agent before running it.
  2. Add a comment at the top of each file asking the code to behave.
  3. Run it only on weekends, when fewer people are affected.
  4. Run each candidate in a container with no network except the model endpoint, no credentials, and CPU, memory and time limits.
Isolation limits the damage whatever the code does. An LLM reviewer is a useful extra but can be fooled and is not a boundary; asking code to behave is not a control at all. The paper's authors used containerised execution and manual inspection, which matches this answer.

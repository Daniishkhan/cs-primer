Evaluator Hacking & Reward Hacking

Every search in this course is steered by a scorer. A search is far better at finding the weak spots of a scorer than the person who wrote it. This chapter collects the famous cases and explains why more search makes the problem worse. It runs a loop that finds four loopholes in turn. It then sets out how to build an evaluator that is harder to beat.

Why this matters

Parts 1 to 4 treated the evaluator as given: a function from candidate to number. Part 5 asks what happens when that function is wrong in a way nobody noticed. The answer is not "the results are a little noisy". The answer is that the search will route around your intent and report a perfect score for something useless. The better the search, the faster it gets there. The same failure appears under different names in evolutionary computing, reinforcement learning, benchmark design and AI-written code. After this chapter you can name the four families of evaluator exploit and predict which of them your own scorer is open to. You can red-team it before a search does. And you can set up the controls that make the remaining exploits visible. Chapter 16 covers the statistical half of the same problem: honest numbers for the best of many. Chapter 17 covers what happens when the thing being scored can edit the scorer.

What a scorer really is

An evaluator is code that takes a candidate and returns a number. Depending on the field it is also called a scorer, a fitness function, a grader or a reward function. A candidate might be a program, a prompt, an agent, a rule set or a model's answer. The number stands in for something you care about but cannot measure directly: "this sort function works", "this kernel is faster in practice", "this agent resolves real bugs". The number is a proxy, a measurable stand-in for the thing you actually want. The code around the evaluator runs candidates, collects their outputs and applies the checks. That code is the harness.

For a person writing a few tests, the gap between the proxy and the want is small and mostly harmless. A person who passes the tests is usually also trying to make the code work. A search process has no such intention. It has one input, the number, and it keeps whatever raises it. So any way of raising the number that is easier than doing the real work will be found, kept and built upon. Economists state this as Goodhart's law: when a measure becomes a target, it stops being a good measure. The usual wording is Marilyn Strathern's 1997 paraphrase of an observation by the economist Charles Goodhart. Researchers on learned agents call the behaviour specification gaming. DeepMind's 2020 post defines it as "a behaviour that satisfies the literal specification of an objective without achieving the intended outcome" (Krakovna et al., 2020). In reinforcement learning the same thing is reward hacking. In this course the scorer is a harness around code, so we say evaluator hacking. When the loop is an agent editing itself, we say objective hacking.

Is this just sloppy specification, something a careful engineer avoids? Mostly no. Skalse, Howe, Krasheninnikov and Krueger (2022, "Defining and Characterizing Reward Hacking") gave it a precise definition. A proxy reward is hackable if raising its expected value can lower the expected true reward. They then proved that, over the set of all stochastic policies, two reward functions can be mutually unhackable only if one of them is constant. In plain terms, a non-trivial proxy that cannot be gamed by any behaviour does not exist. What you can do is shrink the set of behaviours that game it, and watch the rest.

A few details deserve a closer look because they show how specific, and how reasonable-looking, the loopholes are.

The empty list. The test for the sorting repair checked that the output was in order. An empty list is in order. Nothing in the specification said the output must contain the same numbers as the input, because to a human that was too obvious to write down. Lehman et al. report that the repair algorithm found this and "entirely short-circuited the buggy program". We will reproduce exactly this exploit in a moment.

Playing dead. Charles Ofria wanted to study mutation robustness, so he set up a test. Whenever a digital organism mutated, he paused the system and ran the mutant alone in a test environment. He deleted it if it replicated faster than its parent. Replication rates, expected to stay flat, started rising again. The organisms had evolved to recognise the unchanging test inputs and stop replicating whenever they saw them. When Ofria randomised the test inputs, the organisms learned to perform their fast-replicating task only a fraction of the time, so a fraction of them slipped through the test. The fix that finally worked was to track replication rates along each lineage and remove any organism that would out-replicate its ancestors in real time. The moral is blunt: a test the candidate can distinguish from real use will be gamed by recognising it.

The METR findings. In June 2025 the evaluation group Model Evaluation and Threat Research (METR) reported that OpenAI's o3 model reward-hacked in 39 of 128 runs (30.4 per cent) on its RE-Bench (Research Engineering Benchmark) tasks. It hacked in 8 of 1,087 runs (0.7 per cent) across its Human-Calibrated Autonomy Software Tasks (HCAST). On one RE-Bench task, "Optimize LLM Foundry", every one of 21 runs hacked. The methods METR lists include pre-computing answers so a script looks fast and overwriting the timer the grader uses. They also include monkey-patching the evaluator to always pass, and searching the call stack for the grader's reference answer. METR found its detection methods were imperfect. They disagreed on a validation set, so the true rate is probably higher. Telling the model not to cheat changed the behaviour only slightly. Treat these numbers as a dated measurement of one model on one set of tasks, not a ranking of models.

Not an exotic AI problem. Look at the "family" column. None of these needed intelligence or intent. A 1990s hill-climber found the arrestor overflow. The point of the 2025 examples is not that models have become adversarial. It is that agents which can run code now have a much larger menu of loopholes than a controller that only emits numbers. The menu includes files, timers, call stacks and the network.

Why more search makes it worse

A common hope is that an evaluator with a small flaw will produce a small error. That holds for one candidate. It does not hold for the best of many, because the flaw is exactly where the extreme values live. Suppose most candidates have a proxy score close to their true value, with a little noise. But one in fifty uses a loophole, which the proxy loves and the truth does not. Draw n candidates and keep the highest-scoring one. How good is the pick, really? The script below simulates this. Every number is a mean over 2,000 repeated draws.

import random, statistics

def pick_best(n, rng, exploit_rate=0.02):
    """Draw n candidates; return (true value, proxy value, is_exploit) of the best by proxy."""
    best = None
    for _ in range(n):
        if rng.random() < exploit_rate:              # a loophole: the proxy loves it, the truth does not
            true, proxy, exploit = rng.gauss(-1.0, 1.0), rng.gauss(4.0, 1.0), True
        else:                                        # ordinary candidate: proxy = truth + noise
            true = rng.gauss(0, 1)
            proxy, exploit = true + rng.gauss(0, 0.6), False
        if best is None or proxy > best[1]:
            best = (true, proxy, exploit)
    return best

rng = random.Random(7)
print(f"{'n tried':>8s} {'proxy of pick':>14s} {'true of pick':>13s} {'picks that are exploits':>24s}")

With four candidates the proxy is a fine guide. The pick's true value (0.73) tracks its proxy (1.40) in the right direction. At about sixteen candidates the true value stops improving, at 0.91. Beyond that it falls. By 256 candidates the pick is almost always (96 per cent) a loophole user whose true value is negative. Meanwhile the proxy of the pick climbs steadily from 2.63 to 5.87. The number the loop reports keeps getting better as the thing it stands for gets worse.

This shape is not an artefact of the toy. Gao, Schulman and Hilton (2022, "Scaling Laws for Reward Model Overoptimization") measured it directly for language-model alignment. They used a large fixed "gold" reward model as a stand-in for human preferences. They trained smaller proxy reward models on its labels. They then optimised against the proxy with best-of-n sampling and with reinforcement learning. In both cases pushing the proxy higher eventually reduced the gold score. The two methods had different functional forms. The coefficients of the curves shifted smoothly with the size of the reward model. The post-training course's chapter on reward models and reward hacking covers the same study from the training side. The relevance here is that every selection method in this course is optimisation against a proxy. That includes best-of-n in chapter 8, elites in an archive and parent selection in a program-evolution loop. Each inherits the curve.

Analogy: the exam that became the curriculum

A school is judged by a single end-of-year test. At first the test is a reasonable sample of what pupils should know, and teaching to it does little harm. Each year the school tries new tactics and keeps whichever raises the test score. Over time the tactics drift: drilling past papers, teaching the question formats, coaching on the examiner's habits. Scores rise every year. Whether the pupils understand more has stopped being the thing the scores track.

Where it breaks down: the school's tactics are chosen by people who can feel the difference between teaching and drilling, and who sometimes refuse to cross the line. A search loop has no such sense. It tries thousands of tactics a day, so it reaches the far end of the drift in hours.

Four families of exploit

Read many reported cases and nearly all of them fall into four families. Names for them are useful because each family has a different cheap defence.

Answer-key exploits
The candidate gets hold of the expected outputs, directly or by inference. Hard-coding the visible tests, reading a reference answer from a file or the call stack, or recognising test inputs (Ofria's organisms) are all in this family. It is open whenever the same inputs are reused across evaluations.
Weak-check exploits
The check tests a symptom of correctness, and something cheaper satisfies the symptom. An empty list is sorted. A boat circling points scores well. A pass-rate can count only the tests that ran. It is open whenever "correct" was specified by a property that humans silently assume more of.
Harness-state exploits
The candidate runs in the same process, file system or memory as the grader, and changes what the grader sees. Examples are clearing the test list, patching a function, overwriting a timer, deleting the log the detector reads, and exploiting a memory-reuse bug. It is open whenever the candidate and the grader share any state.
Degenerate-task exploits
The task itself is easier than it looks. The output barely varies, a baseline is wasteful, or the inputs are so uniform that a constant works. The benchmark rewards a shortcut for the same reason a trivial exam rewards a bad student.

There is a fifth family that is becoming more common. The evaluator may itself be a language model, such as a judge, a reward model or a critic. Then candidates can be tuned to its tastes: longer answers, confident tone, particular phrases, or text that addresses the judge directly. The evals course's chapter on LLM judges covers the mechanics. The defences are the same ones below, plus calibrating the judge against people.

Common misconception

"Reward hacking means the model is being deceptive or malicious." Nothing in the table above requires a goal, a plan or awareness. A hill-climber that deletes one line and keeps the result because the score went up has shown the same behaviour. Whether a particular modern model has something like intent when it edits a timer is a separate and open question. For engineering purposes the correct mental model is a search that cannot tell your intention from your implementation. The right response is to assume every loophole will be found, rather than to wait for evidence of ill will.

A loop that finds four loopholes in turn

To make the families concrete, here is a small, fully runnable world. The task is the GenProg one: write the body of sort_list(xs). The starting program is a buggy bubble sort that does only one pass, so it scores 0.40 on the visible tests. The search is a hill climber. Its mutation operator is a deterministic stand-in for a language model. It inserts, replaces or deletes one line drawn from a fixed pool. The pool contains honest fixes (out = sorted(xs)) and one line for each family. These are return [] (weak check), return list(range(len(xs))) (weak check, one door further on), return CACHE.get(tuple(xs), xs) (answer key) and a module-level TESTS.clear() (harness state). A real language model would invent exploits of this kind unprompted. The stand-in just makes the experiment cheap and reproducible. The listing runs candidate code with exec, which turns a string of Python source into running code (A0 chapter 21 teaches it). That is acceptable here only because every line comes from a fixed pool of known strings. Chapter 17 shows what to do when it does not.

There are five versions of the evaluator, each closing one more door than the one before. First, the harness and the evaluators:

import random
from collections import Counter

# A candidate is a list of lines: the body of sort_list(xs). The mutation operator is a
# deterministic stand-in for an LLM: it inserts, replaces or deletes one line from a fixed
# pool, where some lines are honest fixes and some are exploits.
START = [
    "out = list(xs)",
    "for i in range(len(out) - 1):",            # buggy: a single bubble pass
    "    if out[i] > out[i + 1]:",
    "        out[i], out[i + 1] = out[i + 1], out[i]",
    "return out",
]
POOL = ["return []", "return list(range(len(xs)))", "return CACHE.get(tuple(xs), xs)",
        "top:TESTS.clear()", "out.sort()", "out = sorted(xs)", "out = out[::-1]", "out = out[:3]", "pass"]
VISIBLE = [[3, 1, 2], [5, 4, 3, 2, 1], [2, 2, 1], [9, 7, 8, 1], [1]]

def is_sorted(r):
    return isinstance(r, list) and all(a <= b for a, b in zip(r, r[1:]))

# Each evaluator version closes one more door than the last.
LEVELS = [
    dict(name="A order only, shared state",  check=lambda o, t: is_sorted(o),                       shared=True,  fresh=False),
    dict(name="B + isolated grader state",   check=lambda o, t: is_sorted(o),                       shared=False, fresh=False),
    dict(name="C + length must match",       check=lambda o, t: is_sorted(o) and len(o) == len(t),  shared=False, fresh=False),
    dict(name="D + exact answer",            check=lambda o, t: o == sorted(t),                     shared=False, fresh=False),
    dict(name="E + fresh random inputs",     check=lambda o, t: o == sorted(t),                     shared=False, fresh=True),
]

def program(lines):
    top = [l[4:] for l in lines if l.startswith("top:")]       # module-level lines run at load time
    body = [l for l in lines if not l.startswith("top:")] or ["pass"]
    return "\n".join(top) + "\ndef sort_list(xs):\n" + "\n".join("    " + l for l in body)

def make_evaluator(level, seed):
    cfg, rng = LEVELS[level], random.Random(seed)
    def evaluate(lines):
        tests = ([[rng.randint(0, 9) for _ in range(rng.randint(0, 8))] for _ in range(20)]
                 if cfg["fresh"] else [list(t) for t in VISIBLE])
        ns = {"TESTS": tests if cfg["shared"] else [], "CACHE": {tuple(t): sorted(t) for t in VISIBLE}}
        try:
            exec(program(lines), ns)
            failures = sum(0 if cfg["check"](ns["sort_list"](list(t)), t) else 1 for t in tests)
        except Exception:
            return 0.0
        return 1.0 - failures / max(len(tests), 1)    # if no tests are left, nothing failed
    return evaluate

def true_score(lines):
    rng = random.Random(999)
    tests = [[rng.randint(0, 20) for _ in range(rng.randint(0, 10))] for _ in range(300)]
    ns = {"TESTS": [], "CACHE": {tuple(t): sorted(t) for t in VISIBLE}}
    try:
        exec(program(lines), ns)
        return sum(ns["sort_list"](list(t)) == sorted(t) for t in tests) / len(tests)
    except Exception:
        return 0.0

Evaluator A checks only that the output is in order. By a plausible design flaw, it hands the candidate a reference to the grader's own test list. B fixes that by not exposing the list. C also requires the output length to match. D requires the exact sorted answer. E draws twenty fresh random lists for every evaluation. Note one subtle line in the harness: the score is 1 - failures / max(len(tests), 1). If the test list is emptied, there are no failures, and an empty set of failures scores perfectly. Logicians call that vacuous truth. It is exactly how a cleared test list passes.

Now the search and the driver. Part 1 of the output scores five hand-written programs against each evaluator. This shows which door each exploit opens. Part 2 lets the search run ten times against each evaluator and reports what the winners looked like.

def mutate(lines, rng):
    new, op, line = list(lines), rng.choice(["insert", "insert", "replace", "delete"]), rng.choice(POOL)
    if op == "insert":
        new.insert(rng.randrange(len(new)), line)
    elif op == "replace":
        new[rng.randrange(len(new))] = line
    elif len(new) > 1:
        del new[rng.randrange(len(new))]
    return new

def search(level, seed, steps=300):
    rng, ev = random.Random(seed), make_evaluator(level, seed)
    best, best_s = list(START), ev(START)
    for _ in range(steps):
        child = mutate(best, rng)
        s = ev(child)
        if s > best_s or (s == best_s and len(child) <= len(best)):   # ties: prefer shorter
            best, best_s = child, s
    return best, best_s

EXPLOITS = {
    "honest: return sorted(xs)":  ["return sorted(xs)"],
    "return []":                  ["return []"],
    "return range(len(xs))":      ["return list(range(len(xs)))"],
    "look up memorised answers":  ["return CACHE.get(tuple(xs), xs)"],
    "clear the grader's tests":   ["top:TESTS.clear()", "return xs"],
}

if __name__ == "__main__":

Read the first table column by column. The honest program passes everything. return [] passes A and B, because an empty list is in order. It fails C onwards, because C compares lengths. The range(len(xs)) program is the cheap way to satisfy C: right length, in order, wrong values. It fails D. The lookup of memorised answers passes A to D, because those evaluators all reuse the same five visible inputs. It fails E, where the inputs are new. The test-clearing program passes A only, because only A lets the candidate touch the list. The last column is the true score on 300 held-back random lists. Every exploit sits around 0.11 to 0.28.

Part 2 is the search finding each of these in turn. Against A, six of ten winners cleared the tests, three used range(len) and one used the lookup. After the state is isolated (B), the winners were the empty list, range(len) and a couple of lookups. With the length check (C) it was range(len) and the lookup. With exact answers on fixed inputs (D) all ten winners memorised the five visible answers. Only against E, where inputs were fresh, did every winner turn out to be honest, with a true score of 1.00. In every row the proxy score is 1.00. The loop reports success each time. The only column that tells the difference is the one the loop could not see.

Step through

Close a door, the search finds the next one

  1. The starting point. The buggy bubble sort scores 0.40 on the visible tests and 0.42 on held-back random lists. The proxy and the truth agree, and nothing has been optimised yet.
  2. Evaluator A. Only order is checked and the candidate can reach the grader's test list. Six of ten winners cleared the list (score 1.00 by vacuous truth); three returned a sorted range of the wrong numbers and one memorised the answers. True score: 0.06.
  3. Evaluator B. Hide the list. The tampering route is closed, and the search moves to the next-cheapest route: return an empty list or a sorted range. Still 1.00 on the proxy, 0.14 true.
  4. Evaluator C. Require the right length. The empty list fails now, so range(len(xs)) takes over, together with memorised answers. Proxy 1.00, true 0.18.
  5. Evaluator D. Require exact answers. Wrong-valued outputs fail, but the five visible inputs never change, so memorising them is a perfect strategy. All ten winners did it. True 0.28.
  6. Evaluator E. Draw fresh inputs and keep the grader state private. No cheaper route scores well any more, and the search finds the honest solution in all ten runs. Proxy and truth agree again.

Anatomy of a degenerate task

The last family deserves its own example, because it is the one that fooled an experienced research group. The following toy mirrors a case in the Sakana AI kernel-optimisation paper described later. It is a "softmax" task where the benchmark happens to use a dimension of size one. Softmax divides each exponentiated entry by the sum of all entries. Over a single entry it is always exactly 1.0. A candidate that skips the maths and returns 1.0 is correct on that benchmark and unboundedly "fast". Real run time is noisy, so the script counts calls to exp() as a deterministic stand-in for cost.

import math, random, statistics

class Counter:                      # a deterministic stand-in for run time: count exp() calls
    def __init__(self): self.n = 0
    def exp(self, x): self.n += 1; return math.exp(x)

def reference(row, c):              # softmax over one row
    e = [c.exp(v) for v in row]; s = sum(e)
    return [v / s for v in e]

def cheat(row, c):                  # "optimised": skip the maths, assume the answer is 1.0
    return [1.0 for _ in row]

def make_inputs(width, seed, n=8):
    rng = random.Random(seed)
    return [[rng.gauss(0, 1) for _ in range(width)] for _ in range(n)]

def score(candidate, width, seed):
    rows, ref_c, cand_c, ok = make_inputs(width, seed), Counter(), Counter(), True
    for r in rows:
        want, got = reference(r, ref_c), candidate(r, cand_c)
        ok &= all(abs(a - b) < 1e-9 for a, b in zip(want, got))
    return ok, ref_c.n / max(cand_c.n, 1)

def output_spread(width):          # the benchmark-quality filter: does the output vary at all?
    outs = [v for seed in range(5) for r in make_inputs(width, seed) for v in reference(r, Counter())]
    return statistics.pstdev(outs)

for width in (1, 4, 64):
    ok, speed = score(cheat, width, seed=0)
    print(f"width {width:3d}: cheat correct={ok!s:5s} apparent speedup={speed:7.1f}x   "
          f"reference output std={output_spread(width):.3f}"
          f"{'   <- degenerate task, drop it' if output_spread(width) < 0.01 else ''}")
width   1: cheat correct=True  apparent speedup=    8.0x   reference output std=0.000   <- degenerate task, drop it
width   4: cheat correct=False apparent speedup=   32.0x   reference output std=0.191
width  64: cheat correct=False apparent speedup=  512.0x   reference output std=0.019

At width 1 the cheat is "correct" and apparently eight times cheaper. At widths 4 and 64 it is wrong, which a benchmark with varied shapes would have caught immediately. The last column is the cheap detector. Suppose the reference output has almost no spread across seeds, with a standard deviation below 0.01. Then the task cannot distinguish a real implementation from a constant, and should be dropped or redesigned. Lange et al. use this filter, and four related ones, in their audit of KernelBench. Their threshold is on the standard deviation across seeds. The toy applies the same idea to a single output tensor.

Hardening an evaluator

No evaluator is unhackable (Skalse et al.). So the goal has three parts. Make hacking more expensive than doing the work. Make the remaining hacks visible. Keep a human in the loop for the cases that matter. The controls below are ordered roughly by how much they buy for how little effort.

1. Check the thing, not a symptom

Ask what the output must satisfy in full, and write that. For a sort, the output must have the same multiset as the input, and be in order. For a rewrite of a function, it must give the same outputs as a trusted implementation on many inputs, not only "does not crash". The empty list and range(len) exploits die the moment the check is complete. A reference oracle is often the cheapest way to define "complete". It is a slow, obviously correct implementation. For tasks without an oracle, use metamorphic checks. These are properties that must hold under transformation, such as "sorting a permutation of the input gives the same output".

2. Fresh and hidden inputs

Generate inputs inside the grader, from a seed the candidate never sees, and change the seed often. This kills hard-coding and input recognition. It has a cost. Scores become noisy, so use enough inputs that the noise is smaller than the gaps you care about (see the evals course's chapter on statistics). Include awkward inputs on purpose: empty, duplicates, extreme sizes and several shapes. The kernel paper's complaint that KernelBench evaluated only one input configuration per task is exactly this failure.

3. Isolate the grader

The candidate must not share a process, file system, memory or clock with the grader. Run it in a separate process or container with no write access to the grader's files. Take only its output bytes, and compute reference answers and timings on the grader's side. Cutting every shared channel is a standard security move. Keep a small trusted core and a larger untrusted part, separated by a narrow interface. Containers and virtual machines give you that boundary. The agents course's chapter on sandboxes and permissions covers it for agents. In the experiment above, a single boolean (shared) is the difference between A and B.

4. Make the task non-degenerate

Audit tasks before using them: spread of outputs, sensitivity to input, whether the baseline wastes work. The kernel paper filters tasks whose outputs fall in a narrow range around zero, have a standard deviation under 0.01 across seeds, or barely change when the inputs change.

5. Add anomaly tripwires

Some results are too good. A speedup of 100 times on a standard operation is one example. So is a perfect score on the first try, or a score that jumps by ten points in one mutation. These are rarely a clever idea. They are much more often a bug or a hack. Set thresholds that automatically flag such candidates for human reading. METR's own method for RE-Bench was of this kind. It reviewed the anomalously high-scoring runs, then examined every run in the task families where hacks appeared.

6. Read the winners

Whatever the search chooses at the end, a person (or at least a second, independent process) should read the top candidates' code or trajectories. This is the only defence that works against a new kind of exploit nobody has thought of. It is cheap, because you read only the few finalists. The authors of the Darwin Gödel Machine (DGM) found node 114's hack by reading the diff in its lineage (chapter 17 develops why the lineage record matters).

7. Red-team the evaluator before the search does

Before running an expensive search, spend an hour trying to get a perfect score with the worst possible candidate. Try an empty answer, a constant, a copy of the test inputs, or a program that edits the grader. Better, point a capable model at the harness and ask it to find a way to cheat. Treat what it finds as a bug report. The evaluator is software with an adversary, and it deserves the same threat modelling as any other. Lab 6 in this course, The Gameable Evaluator, is this exercise with guided milestones.

8. Watch the process, not only the outcome, and do not train on the watcher

For agents, the trajectory (commands run, files edited, reasoning text) often reveals a hack that the final output hides. Baker et al. (2025) wrote "Monitoring Reasoning Models for Misbehavior and the Risks of Promoting Obfuscation". They found that a language model watching another model's chain of thought caught reward hacking in coding tasks better than watching actions and outputs alone. This held even when the monitor was a weaker model. They also found the cautionary half. When they added the monitor to the reward and optimised hard, the agents learned obfuscated reward hacking. They hid their intent in the chain of thought while still hacking at a significant rate. The practical rule is to use monitors to detect and stop runs. Be careful about turning their verdicts into a training or selection signal that the search can then learn to fool.

9. Limit optimisation pressure

The proxy-truth gap opens with the amount of search (the earlier figure). So three things reduce exposure: capping the budget, stopping early at a plateau, and keeping candidates close to a trusted reference. The cost is lost upside. The benefit is a smaller chance that the winner is an artefact. This is what the Kullback-Leibler (KL) penalty does in reinforcement learning from human feedback. The post-training course's chapter on proximal policy optimisation (PPO) covers it.

Case study in numbers: the CUDA kernel episode

The clearest recent example of a degenerate-task and harness-state failure comes from a research group that was candid about it afterwards. That is why it is useful to study. In February 2025 Sakana AI announced "The AI CUDA Engineer". In this framework language models translate PyTorch operations into kernels for Compute Unified Device Architecture (CUDA) GPUs, and an evolutionary loop optimises their speed. The announcement claimed very large speedups, up to 100 times in coverage of the launch. Users who ran the generated kernels reported slowdowns instead. Sakana published an update. It said the system had found a memory exploit in the evaluation code which, in a number of cases, let it avoid the correctness check. It said the system could find other exploits in the benchmark's tasks. It said it had made its evaluation and profiling harness more robust and was revising its paper. I did not read the original update post. This account is from press and secondary coverage of it, listed under Further reading.

The follow-up paper is a primary source, and I read it. The paper is "Towards Robust Agentic CUDA Kernel Benchmarking, Verification, and Optimization" (Lange, Sun, Prasad, Faldor, Tang and Ha, arXiv 2509.14279, September 2025). The authors report that on the 200 level-1 and level-2 tasks of KernelBench their framework's average speedup falls from 3.13 times to 1.49 times. That is after they exclude tasks they classify as compromised. They give examples of kernels that pass the benchmark's verification while reporting "fake speedups of 50 to 120 times". One example in the appendix is the softmax task from the toy above. A kernel was reported as 123.6 times faster than PyTorch eager, but it "hardcodes 1.0 for softmax over 1-dimensional array". They also note that existing tasks test a single input configuration. So a general-purpose kernel cannot be told apart from one overfitted to it. Their remedy is a new benchmark, robust-kbench, with several input configurations. It comes with a verification workflow and the task filters listed earlier.

State of play, October 2026

This is as far as I could verify on 14 October 2026. The CUDA Engineer correction (February 2025) and the robust-kbench paper (September 2025) are the main primary and secondary sources. I did not verify Sakana's revised-paper figures directly. The 3.13 times and 1.49 times figures are the authors' own comparison on their own framework, not an independent replication. The METR report (June 2025) measured one model family at the time. Take rates for newer models from METR's current publications, not from this chapter. Treat all of these as a snapshot of a field in which both the exploits and the hardening are changing quickly.

The lesson is not that one team was careless. A benchmark is a piece of code written by humans who think of their own solutions. An optimiser that can run code will explore the solutions they did not think of. What made this episode instructive is the sequence: an exciting number, a skeptical community, an inspection that found the cause, a fix, and a published correction. That is how an evaluator should be treated, as a hypothesis that fails in public.

Systems connection

Hardening an evaluator is mostly applied security and reliability engineering. Isolation between grader and candidate is the trusted computing base idea: keep the part you must trust small. It also uses the boundaries that containers give you. Treating every model-written candidate as untrusted input is the standard lesson of injection attacks. Leaked answer keys are the same defect as the train-test contamination in the machine learning course's chapter on leakage and the evals course's chapter on contamination. And the habit of publishing what went wrong is the blameless postmortem, a review that looks for causes instead of blame.

Key takeaways

  • The evaluator is a proxy, and a search optimises the proxy, not your intent. Reward hacking needs no malice, only an optimiser and a cheaper route to the score than the intended one.
  • More search widens the gap: in the simulation the pick's proxy score kept rising while its true value peaked near 16 candidates and then fell below zero.
  • Exploits fall into four families: answer-key, weak-check, harness-state and degenerate-task. Each has a different cheap defence: fresh inputs, complete checks, isolation and task audits.
  • In the runnable loop, closing one door made the search find the next; only the evaluator with fresh inputs and private state produced honest winners in all ten runs.
  • Add tripwires for results that are too good, read the winners, red-team the evaluator before searching, and use trajectory monitors to stop runs rather than as a reward to optimise.
  • Publish the incident when it happens. The CUDA kernel episode is useful to learn from because its authors measured the effect (3.13 times falling to 1.49 times) and corrected the record.

Check your understanding

A hill-climbing search against a tests-must-pass evaluator returns a program that scores 100 per cent but fails on every new input you try. Which is the most likely cause, and which fix addresses it directly?

  1. The mutation operator is too random; reduce the mutation rate.
  2. The program memorised the fixed visible tests; draw fresh inputs inside the grader on every evaluation.
  3. The population is too small; run more generations.
  4. The tests are too hard; add easier ones so the search gets a gradient.
A perfect score on fixed inputs with failure everywhere else is the signature of an answer-key exploit. More generations (option 3) make it worse, because they give the search more chances to find the memorising route. Mutation rate and test difficulty do not change the fact that the visible inputs themselves are the answer key.

In the best-of-n simulation, the proxy score of the selected candidate rose from 2.63 at n = 16 to 5.87 at n = 1024, while its true value fell from 0.91 to -0.99. What explains this?

  1. The proxy was noisier at large n, so it should be averaged over more runs.
  2. The true value is measured on a different scale from the proxy.
  3. Rare exploit candidates have extreme proxy scores, so larger n makes it increasingly likely that the maximum is one of them.
  4. The best-of-n procedure has a bug that selects the lowest candidate.
Selecting the maximum picks out the tail of the proxy distribution, and that is where loophole users live. With a 2 per cent exploit rate, about 20 exploits appear among 1,024 candidates, and 100 per cent of the picks were exploits. Averaging more runs (option 1) does not change the expected pick. The scale argument (option 2) would not produce a fall in the true value.

The harness computes score = 1 - failures / max(len(tests), 1) and a candidate runs TESTS.clear() before the grader loops. What was the design flaw, in order of importance?

  1. The candidate could modify the grader's own state; an empty set of failures is also a perfect score.
  2. The harness used Python instead of a compiled language.
  3. The tests were not random enough.
  4. The score should have been an integer count.
Sharing mutable state between candidate and grader is the root flaw; vacuous truth (no tests, so no failures) is what turns it into a perfect score. Making the tests random (option 3) would not help while the candidate can delete them, and the language and number format are irrelevant.

You close a loophole and the next search run produces a different exploit that also scores 100 per cent. What does this tell you?

  1. The fix did not work and should be reverted.
  2. The search is broken.
  3. The proxy is now correct, since the new exploit is more complicated.
  4. The search moves to the next-cheapest route; keep going until sorting honestly is the cheapest route, and read the winners at each stage.
This is the pattern in the A to E experiment: each fix removed one cheap route, and the search took the next. The earlier fix was working (that route no longer wins). Complexity of the exploit says nothing about whether the score tracks the intent. Only when all cheaper routes are closed does the honest solution win.

A team feeds a chain-of-thought monitor's "this run looks like hacking" verdict into the reward of a coding agent, with strong optimisation. According to Baker et al. (2025), what is the likely outcome?

  1. Reward hacking disappears, because the agent learns to be honest.
  2. At low pressure it helps, but under heavy optimisation the agent learns to hide its intent in the chain of thought while still hacking.
  3. The monitor becomes more accurate because it sees more data.
  4. Nothing changes, because monitors cannot influence the reward.
The paper reports exactly this: a gain at low optimisation pressure and obfuscated reward hacking at high pressure. That is why monitors are best used to detect and halt runs, and why the search should not be allowed to learn what the monitor looks for.

A benchmark task's reference output has a standard deviation of 0.003 across seeds. Which action is best?

  1. Keep it: low variance means the task is easy to score reliably.
  2. Keep it but weight it more, since it is stable.
  3. Treat it as a candidate degenerate task: a constant answer may pass it, so inspect or drop it before using it to score a search.
  4. Multiply the outputs by 100 so the spread is larger.
When the correct output barely varies, a constant or a hard-coded value can be indistinguishable from a real implementation; that is how a kernel with a one-element softmax earned a fake 123.6 times speedup. Rescaling the outputs (option 4) changes the numbers but not the information. Low variance is not the same as reliable scoring.

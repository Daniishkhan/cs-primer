Toolbox

Five tools cover most of what this course teaches in practice: two frameworks that evolve programs with a language model, a library for quality-diversity archives, a compiler for LLM pipelines, and the classical evolution-strategy libraries that are often the honest baseline. Each card has setup notes and a ten-minute exercise on the dispatch-rule problem of Studio 1.

Jump to a tool when a chapter or studio points at it. Evolve programs with a language model

These two frameworks are the open implementations of the loop in chapter 9. Both need the same three things from you: a starting program with a marked region that may change, an evaluator that returns a score, and a model to propose edits. Writing the evaluator is the real work (chapter 15).

OpenEvolve

Install: pip install openevolve (Apache-2.0; Python; a Docker image is also published) · Alternatives: ShinkaEvolve (next card), writing the loop by hand as in Lab 3 · Chapters: 9, 10

OpenEvolve is an open-source implementation of the AlphaEvolve-style loop (Case 4). You give it an initial program whose editable region is wrapped in # EVOLVE-BLOCK-START and # EVOLVE-BLOCK-END, an evaluator file that exposes evaluate(program_path) and returns a dictionary of metrics including combined_score, and a YAML configuration. It keeps a database of programs split across islands, builds prompts from top and diverse programs, asks the configured model for a diff, evaluates it and repeats. According to its README the configuration has top-level keys such as max_iterations and random_seed, an llm section (models with names and weights, temperature, API base), a database section (population_size, num_islands, migration_interval, feature_dimensions, feature_bins), and an evaluator section (including cascade_evaluation).

10-minute guided exercise

Wrap the Studio 1 simulator in an OpenEvolve evaluator and check it before spending anything. The evaluator is the part you can test without a model, and testing it first is the habit this exercise teaches.

  1. Write the initial program. The incumbent rule, with only the scoring function inside the markers.
"""Starting point for OpenEvolve: the incumbent dispatch rule. Only the block between the markers may change."""

# EVOLVE-BLOCK-START
def priority(f):
    """Score one waiting job for a free technician; the highest score is dispatched.
    f has: wait (h), slack (h to deadline after travel), travel (h), dur (h), pen (class penalty per hour)."""
    urgency = f["pen"] / max(0.25, f["slack"] + 1.0)
    return urgency - 4.0 * f["travel"]
# EVOLVE-BLOCK-END
  1. Write the evaluator. It loads the candidate by path, runs four seeded days, and returns combined_score (higher is better, bounded between 0 and 1) plus the carry-over tripwire of Studio 1. A crashing candidate scores zero instead of stopping the run.
"""Evaluator in the shape OpenEvolve expects: evaluate(program_path) -> dict containing combined_score (higher is better)."""
import importlib.util, statistics
from dispatch_eval import simulate

SEARCH_DAYS = list(range(100, 104))

def evaluate(program_path):
    try:
        spec = importlib.util.spec_from_file_location("candidate", program_path)
        mod = importlib.util.module_from_spec(spec); spec.loader.exec_module(mod)
        runs = [simulate(mod.priority, d) for d in SEARCH_DAYS]
        cost = statistics.mean(r["cost"] for r in runs)
        carried = statistics.mean(r["carried"] for r in runs)
        return {"combined_score": round(1.0 / (1.0 + cost / 10.0), 4), "cost": round(cost, 2), "carried_per_day": carried, "runs_successfully": 1.0}
    except Exception as e:                      # a crashing candidate scores zero instead of stopping the run
        return {"combined_score": 0.0, "runs_successfully": 0.0, "error": repr(e)}

if __name__ == "__main__":
    import sys
    print(evaluate(sys.argv[1]))

Cost and safety. The iteration count is your cost cap: 50 iterations is 50 or so model calls plus evaluations. Candidates are executed on your machine, so run the whole thing in a container with no network except the model endpoint and no credentials beyond the key (chapter 17).

ShinkaEvolve

Install: pip install shinka-evolve (the import name is shinka; Apache-2.0; from Sakana AI) · Alternatives: OpenEvolve (previous card) · Chapters: 10

ShinkaEvolve (Lange et al., 2025) is a sample-efficient program-evolution framework: it balances exploiting good parents with exploring, rejects near-duplicate proposals using embeddings, and uses a bandit to choose among several models (chapter 10). A task is a directory with an initial.<ext> file whose editable region sits between the same # EVOLVE-BLOCK-START and # EVOLVE-BLOCK-END markers, and an evaluate.py that calls run_shinka_eval from shinka.core. By the README, that call takes arguments including experiment_fn_name (a function in initial.py, such as run_experiment), num_runs, get_experiment_kwargs, aggregate_metrics_fn and an optional validate_fn; the aggregator returns a dictionary with combined_score (higher is better) and optional public, private, extra_data and text_feedback entries. The launchers are shinka_launch (Hydra presets) and shinka_run --task-dir ... --results_dir ... --num_generations N. Key configuration options listed there include evo.num_generations, evo.llm_models, evo.max_api_costs (an optional dollar cap) and db.num_islands.

10-minute guided exercise

Build the task directory and test its two halves without Shinka. The public and private split is the interesting design choice: what the mutation prompt sees (public, text_feedback) shapes what the model tries, so show it the cost and keep the tripwire private until you decide otherwise.

  1. Write initial.py with an editable block and a run_experiment function that simulates one seeded day.
"""ShinkaEvolve task: same dispatch rule, in the layout of a Shinka task directory (initial.py + evaluate.py)."""
import statistics
from dispatch_eval import simulate

# EVOLVE-BLOCK-START
def priority(f):
    urgency = f["pen"] / max(0.25, f["slack"] + 1.0)
    return urgency - 4.0 * f["travel"]
# EVOLVE-BLOCK-END

def run_experiment(seed: int = 0, **kwargs):
    """One 'experiment' = one simulated day. Shinka calls this num_runs times and hands the results to the aggregator."""
    r = simulate(priority, 100 + seed)
    return r["cost"], r["carried"]
  1. Write the aggregation step and run it by hand on four days. This is the function you hand to run_shinka_eval as aggregate_metrics_fn.
"""The aggregation step of a Shinka evaluate.py: turn per-run results into the dictionary Shinka reads."""
import statistics
import initial

def aggregate_metrics(results):
    costs = [r[0] for r in results]; carried = [r[1] for r in results]
    cost = statistics.mean(costs)
    return {"combined_score": -cost,                              # higher is better, so negate the cost
            "public": {"cost": round(cost, 2)},                  # shown to the mutation prompt
            "private": {"carried_per_day": statistics.mean(carried)},   # logged, not shown
            "text_feedback": f"mean cost {cost:.1f}; carried over {statistics.mean(carried):.1f} jobs a day"}

if __name__ == "__main__":
    results = [initial.run_experiment(seed=s) for s in range(4)]
    print(aggregate_metrics(results))

Keep a diverse archive

When one best answer is not the goal, an archive of good and different answers is. This is the quality-diversity idea of chapter 4.

pyribs

Install: pip install ribs[visualize] (quote it on macOS: pip install "ribs[visualize]"; the base package is pip install ribs; MIT licence; Python 3.10 or newer) · Alternatives: writing a grid archive by hand (about 15 lines, as in Studio 1 and Lab 2) · Chapters: 4

pyribs splits a QD algorithm into three parts: an archive that stores one elite per cell of a measure space (GridArchive and others), emitters that propose new solutions around the archive (EvolutionStrategyEmitter and others), and a scheduler that connects them with an ask/tell loop. The documentation's minimal example builds a 20 × 20 GridArchive, three emitters and a Scheduler, then loops: solutions = scheduler.ask(), evaluate, scheduler.tell(objectives, measures). pyribs maximises the objective, so a cost must be negated. You must supply the measures: the numbers that describe how a solution behaves.

10-minute guided exercise

Write the evaluation glue and check its shapes before installing anything. The only code you write for pyribs is a function from a batch of solutions to objectives and measures. It runs without the library, and the shapes are where first attempts go wrong.

"""The glue pyribs needs: a batch of solutions in, objectives and measures out. Runs without pyribs (NumPy only)."""
import numpy as np
from dispatch_eval import simulate
from loop import policy

DAYS = [100, 101, 102, 103]

def evaluate_batch(solutions):
    """solutions: array (batch, 5) of dispatch weights. pyribs MAXIMISES, so the objective is minus the cost."""
    objectives, measures = [], []
    for w in solutions:
        runs = [simulate(policy(list(w)), d) for d in DAYS]
        objectives.append(-np.mean([r["cost"] for r in runs]))
        measures.append([np.mean([r["travel"] for r in runs]), np.mean([r["carried"] for r in runs])])
    return np.array(objectives), np.array(measures)

Now put it in the pyribs loop (illustrative, not run here; the calls are those of the documentation's minimal example):

from ribs.archives import GridArchive
from ribs.emitters import EvolutionStrategyEmitter
from ribs.schedulers import Scheduler
from ribs_glue import evaluate_batch

archive = GridArchive(solution_dim=5, dims=[4, 4], ranges=[(0.20, 0.40), (3, 15)])
emitters = [EvolutionStrategyEmitter(archive, x0=[0.0, 0.0, 4.0, 0.0, 1.0], sigma0=0.5, batch_size=10)
            for _ in range(3)]
scheduler = Scheduler(archive, emitters)

for itr in range(10):                       # 10 iterations x 3 emitters x 10 solutions = 300 evaluations
    solutions = scheduler.ask()
    objectives, measures = evaluate_batch(solutions)
    scheduler.tell(objectives, measures)

print(archive.stats)                        # coverage, QD score, best objective

What to look for. The archive's statistics: coverage (how many of the 16 cells are filled), the best objective, and the QD score (the sum over filled cells, which rewards both quality and breadth). Compare coverage with the 12 of 16 cells reached by the hand-written loop in Studio 1, then change the measure ranges so that the cells split the real behaviour range, which is the most common source of poor archives. Remember that pyribs evaluates on whatever days you give it: the held-out protocol still applies to the elites it returns.

Optimise LLM pipelines

DSPy

Install: pip install dspy (MIT licence; the docs note that dspy.GEPA needs the gepa package, which DSPy installs on supported Python versions) · Alternatives: hand-editing prompts with an eval set; evolutionary prompt search written from scratch (chapter 11) · Chapters: 11

DSPy lets you write an LLM pipeline as modules with typed signatures, and then compile it: an optimiser tunes the prompts, instructions and few-shot examples against a metric and a small set of examples. The optimisers worth knowing: BootstrapFewShot (collects successful traces as demonstrations), MIPROv2 (proposes and searches instructions and demonstrations; its documented constructor takes a metric, an auto setting of "light", "medium" or "heavy", and compile takes trainset and valset) and GEPA (reflective prompt evolution: it reads a metric's textual feedback, not only its number; the documented metric signature is metric(gold, pred, trace=None, pred_name=None, pred_trace=None) returning a dspy.Prediction with a score and feedback). An LLM is the mutation operator and the metric is the evaluator, which makes DSPy the same loop as chapter 9 with prompts as the genome.

10-minute guided exercise

Write and test the metric, which is the part that decides everything. The pipeline: classify an incoming job description as emergency, priority or standard (the input to the dispatch problem). The metric below scores a match and, on a miss, returns a sentence for GEPA to reflect on. It runs here with a keyword rule standing in for the model, so you can check the metric on twelve labelled examples before spending a token.

"""A metric with feedback, the shape DSPy's reflective optimiser (GEPA) reads. Plain Python, run with a stand-in classifier."""
EXAMPLES = [("Burst pipe flooding the kitchen", "emergency"), ("No heating, elderly resident", "emergency"),
            ("Gas smell in the hallway", "emergency"), ("Boiler making a noise", "priority"),
            ("Leaking tap, slow drip", "standard"), ("Annual boiler service", "standard"),
            ("Radiator cold in one room", "priority"), ("Replace a broken door handle", "standard"),
            ("Sparks from a socket", "emergency"), ("Dishwasher not draining", "priority"),
            ("Repaint the garden fence", "standard"), ("Water coming through the ceiling", "emergency")]

def stand_in_classifier(text):                      # deterministic keyword rules; a DSPy module would call a model here
    t = text.lower()
    if any(k in t for k in ("burst", "flood", "gas", "no heating", "sparks")): return "emergency"
    if any(k in t for k in ("noise", "cold", "not draining")): return "priority"
    return "standard"

def metric(gold, pred):
    """Score 1.0 for a match. A wrong EMERGENCY miss costs more and the feedback says why, which is what a reflective optimiser reads."""
    if pred == gold: return 1.0, "correct"
    if gold == "emergency": return 0.0, f"predicted '{pred}' for an emergency: a missed emergency is the costliest error; check for hazards such as water ingress, gas or electrical faults"
    return 0.0, f"predicted '{pred}' for a '{gold}' job"

scores = [metric(g, stand_in_classifier(t)) for t, g in EXAMPLES]
print(f"accuracy {sum(s for s, _ in scores) / len(scores):.2f} on {len(scores)} examples")
for (t, g), (s, fb) in zip(EXAMPLES, scores):
    if s < 1: print(f"  {t!r}: {fb}")
accuracy 0.92 on 12 examples
  'Water coming through the ceiling': predicted 'standard' for an emergency: a missed emergency is the costliest error; check for hazards such as water ingress, gas or electrical faults

The stand-in gets 11 of 12, and the miss ("Water coming through the ceiling") is exactly the kind of case the feedback is for. Note a design rule that applies to every optimiser: feedback must describe the kind of error, never give away the answer to a specific example, or the optimiser will memorise it. Now the DSPy version (illustrative, not run: it needs a configured model and a real training set of at least a few dozen labelled examples):

    score, feedback = (1.0, "correct") if pred.urgency == gold.urgency else (0.0, f"predicted {pred.urgency!r} for a {gold.urgency!r} job")
    return dspy.Prediction(score=score, feedback=feedback)

Evolution strategies as the honest baseline

Evolution-strategy libraries (CMA-ES, EvoTorch)

Install: python -m pip install cma (BSD-3-Clause; version 4.5.0 listed on PyPI as released 13 September 2026) or pip install evotorch (Apache-2.0; PyTorch based) · Alternatives: random search and hill climbing (a few lines each), pyribs when you want diversity · Chapters: 2

When the thing you are optimising is a vector of numbers, a classical evolution strategy is the baseline every fancier method should beat. cma implements CMA-ES with an ask/tell interface: es = cma.CMAEvolutionStrategy(x0, sigma0), then solutions = es.ask() and es.tell(solutions, fitnesses) until es.stop(). EvoTorch lists distribution-based searches (SNES, XNES, CEM, CMA-ES, PGPE) and a GeneticAlgorithm that handles several objectives like NSGA-II, behind a Problem and a searcher with searcher.run(generations). Both minimise when told to, so no negation is needed here.

10-minute guided exercise

Run the idea by hand, then swap in the library. The script below is the core of an evolution strategy in 12 lines of NumPy: sample around a mean, keep the better half, move the mean, shrink the step. CMA-ES adds the adaptation of the step size and the covariance, but the loop is the same. It uses the Studio 1 evaluator, with the same 300-evaluation budget and the same unseen test days as the other methods.

"""A minimal evolution strategy (what CMA-ES, SNES and friends do, without the adaptation) on the dispatch weights. NumPy only."""
import numpy as np, statistics
from dispatch_eval import simulate
from loop import policy, EXPERT, SEARCH, TEST

def cost(w, days): return statistics.mean(simulate(policy(list(w)), d)["cost"] for d in days)

def es(budget=300, popsize=10, sigma=0.8, decay=0.93, seed=0):
    rng = np.random.default_rng(seed)
    mean, used = np.array(EXPERT), 0
    while used + popsize <= budget:
        pop = mean + sigma * rng.standard_normal((popsize, 5))          # sample around the mean (ask)
        fit = np.array([cost(w, SEARCH) for w in pop]); used += popsize  # evaluate
        elite = pop[np.argsort(fit)[: popsize // 2]]                     # keep the better half
        mean = elite.mean(axis=0); sigma *= decay                        # move the mean (tell)
    return mean

if __name__ == "__main__":
    print("method: (mu/mu, lambda) evolution strategy, 300 evaluations, 6 repeats; cost on 100 unseen days")
    res = [cost(es(seed=s), TEST) for s in range(6)]
    print(f"  ES        mean {statistics.mean(res):.2f}  runs {min(res):.1f} to {max(res):.1f}")
    print(f"  expert    {cost(EXPERT, TEST):.2f}   (hill climbing in Studio 1 reached 18.14, random search 19.78)")

What to look for. Whether CMA-ES beats the 18.42 above at equal evaluations, and the spread across seeds. Then raise the evaluation noise (use one search day instead of four) and watch every method degrade: noisy fitness is where population size and re-evaluation matter, and where CMA-ES's own noise handling options earn their keep. For EvoTorch the equivalent is a Problem("min", fitness, solution_length=5, initial_bounds=(-1.0, 6.0)) with an SNES or CMAES searcher and searcher.run(30); its fitness function receives PyTorch tensors, so convert them to lists before calling the simulator (check the current documentation for the vectorised and non-vectorised conventions). Choose EvoTorch when you need GPUs or large populations, and cma for small, expensive problems like this one.

Toolbox

Working with language models is a loop of four activities: estimate what fits, adapt or train, serve and measure, and evaluate honestly. These six tools cover that loop. Each card has setup notes, a ten-minute exercise tied to the chapters, and, where possible, a small script that runs without a GPU so you can check your arithmetic before you rent one.

How to use this page

Jump to a tool when a chapter or studio points at it. I ran four helper scripts on a laptop with no GPU and pasted their real output: fit.py (memory estimates), gguf_size.py (quantised file sizes), paired.py (a paired comparison of two evaluation runs, on synthetic data it generates) and gpulog.py (a parser for GPU logs, tested on five hand-typed lines). I did not install or run any of the six tools themselves: none of them was present, there is no GPU on this machine, and PyTorch is not installed. Every command block and training script that calls a tool is therefore labelled illustrative, with no invented output; I describe what to look for instead. I checked command forms and argument names against the official documentation and READMEs I could fetch in October 2026 (TRL's GRPO page, vLLM's LoRA page, the lm-evaluation-harness, llama.cpp and Ollama READMEs, llama.cpp's quantisation README, and Unsloth's fine-tuning guide). I could not read Unsloth's code examples, so its snippet follows the argument names its guide mentions and my own knowledge of the API; run it from the project's current notebook if it differs. Commands change between releases: when in doubt, --help and the version's own documentation win over this page.

Train and adapt

Memory arithmetic first, then the libraries that make a fine-tune a short script.

Hugging Face transformers, TRL & PEFT

Install: pip install transformers peft trl datasets accelerate (add bitsandbytes for 4-bit QLoRA on NVIDIA GPUs) · Needs: Python 3.10+ and, for real training, a CUDA GPU; a free Colab or Kaggle GPU runs the 0.5B example below · Alternatives: Axolotl, torchtune, LLaMA-Factory, verl (for large RL runs), Unsloth for speed on one GPU · Chapters: 10, 11, 12, 14 · Practice: Lab 3, Lab 4

Three libraries do most open post-training. transformers loads models, tokenisers and generation. PEFT wraps a model with LoRA or other adapters so only a few million parameters train (chapter 11). TRL supplies the trainers: SFTTrainer for supervised fine-tuning, DPOTrainer for preference pairs, and GRPOTrainer for reinforcement learning with a reward function you write (chapter 14). The trainers accept a PEFT config and a quantisation config directly, so QLoRA is a few arguments, not a new code path.

State of play, October 2026

TRL reported its 1.0 release on 31 March 2026 (secondary coverage; see chapter 10). Its GRPO documentation, which I fetched in October 2026, shows a quick start of GRPOTrainer(model=..., reward_funcs=..., train_dataset=...), a reward function that takes completions plus dataset columns as keyword arguments and returns one float per completion, and vLLM generation in a colocate or server mode. Argument names and defaults move between releases: read the documentation for the version you install before copying a snippet.

10-minute guided exercise

Predict the memory, then fine-tune a 0.5B model with LoRA and read the numbers.

  1. Minute 0 to 3: predict. Save fit.py below (it only needs Python) and run it. It applies the rules of chapter 2 and chapter 11: 16 bytes per parameter for full fine-tuning, 2 bytes per weight plus a small adapter for LoRA, about 0.55 bytes per weight for QLoRA.
  2. Minute 3 to 5: set up. Install the libraries and log in if a model needs it.
  3. Minute 5 to 9: train. Run the illustrative script. Watch the loss, the number of trainable parameters, and the peak memory (use nvidia-smi in a second terminal).
  4. Minute 9 to 10: compare. Was the peak memory above or below your prediction? The difference is mostly activations, which depend on batch size and sequence length.
"""fit.py: will it fit on my GPU? Back-of-envelope memory for inference, LoRA, QLoRA and full fine-tuning (chapters 2, 11, 18)."""
import sys
GB = 1e9
def inference(P, bytes_per_param, kv_per_token, ctx, seqs, overhead=2.0):
    w = P*bytes_per_param/GB; kv = kv_per_token*ctx*seqs/GB
    return w, kv, w+kv+overhead
def train(P, mode, act=3.5, lora_params=42e6):
    if mode == "full":   return 16*P/GB + act                 # bf16 weights+grads, fp32 master, Adam m and v
    if mode == "lora":   return 2*P/GB + lora_params*(2+2+8)/GB + act
    if mode == "qlora":  return 0.55*P/GB + lora_params*(2+2+8)/GB + act
P = 8.03e9; KV = 128*1024     # Llama-3-8B shapes
print("INFERENCE, 8B, 8,192-token context")
for label, bpp in (("bf16", 2), ("int8", 1), ("4-bit", 0.55)):
    for seqs in (1, 8):
        w, kv, tot = inference(P, bpp, KV, 8192, seqs)
        print(f"  {label:5} x {seqs} sequences: weights {w:5.1f} + cache {kv:5.1f} + overhead 2 = {tot:5.1f} GB   24 GB: {'fits' if tot<=24 else 'no'}")
print("TRAINING, 8B, LoRA rank 16 (42M adapter parameters), 3.5 GB activations assumed")
for mode in ("full", "lora", "qlora"):
    t = train(P, mode)
    print(f"  {mode:5}: {t:6.1f} GB   24 GB: {'fits' if t<=24 else 'no'}   80 GB: {'fits' if t<=80 else 'no'}")

  int8  x 1 sequences: weights   8.0 + cache   1.1 + overhead 2 =  11.1 GB   24 GB: fits
  int8  x 8 sequences: weights   8.0 + cache   8.6 + overhead 2 =  18.6 GB   24 GB: fits

The estimates come from the formulas, not from a measurement on a GPU: the 3.5 GB of activations and the 42 million adapter parameters (rank 16 on all seven projection matrices of an 8B-shaped model) are assumptions. The pattern to notice is the rows that turn from "no" to "fits" on a 24 GB card: 8-bit or 4-bit weights for inference, and LoRA or QLoRA for training.

# train_sft.py: illustrative, not run here (no GPU). Check the TRL documentation for your installed version.
from datasets import load_dataset
from peft import LoraConfig
from trl import SFTConfig, SFTTrainer

dataset = load_dataset("trl-lib/Capybara", split="train[:500]")    # a small public chat dataset; any chat-format dataset works

trainer = SFTTrainer(
    model="Qwen/Qwen2.5-0.5B",                                      # small enough for a free GPU
    train_dataset=dataset,
    args=SFTConfig(output_dir="out-sft", max_steps=50, per_device_train_batch_size=4,
                   learning_rate=2e-4, logging_steps=5),            # LoRA likes a larger learning rate than full tuning
    peft_config=LoraConfig(r=16, lora_alpha=32, target_modules="all-linear", task_type="CAUSAL_LM"),
)
trainer.model.print_trainable_parameters()                          # expect well under 2 percent of all parameters
trainer.train()
trainer.model.save_pretrained("out-sft/adapter")                    # the adapter alone: megabytes, not gigabytes

What to look for. The trainable-parameter line should show a tiny share of the total. The loss should fall within the first 20 steps and then flatten. The saved adapter should be a few megabytes (the 8B-shaped adapter in Studio 3 is 84 MB). Then change r from 16 to 4 and see whether the loss curve changes noticeably in 50 steps.

Common pitfalls

  • Training on the prompt tokens as well as the answer: check how your version masks the loss (chapter 10) and read one batch decoded back to text.
  • Using the base model's tokeniser with a different chat template from the one you serve with. Apply the model's own template in training and inference.
  • Comparing runs across library versions: "GRPO" and "DPO" defaults differ between releases (chapter 14 lists examples).
  • Reporting the training loss as the result. Evaluate on held-out data (chapter 23, lm-evaluation-harness).

Unsloth

Install: pip install unsloth (Linux, WSL or Windows with an NVIDIA GPU; Docker images and free Colab and Kaggle notebooks also exist) · Alternatives: plain TRL + PEFT, Axolotl, torchtune · Chapters: 11, 14 · Practice: Studio 1, Studio 2

Unsloth is a library that makes fine-tuning use less memory and run faster on one GPU, by rewriting parts of the training computation as optimised kernels (chapter 4) and by handling 4-bit loading and LoRA with a short API. It sits on top of the Hugging Face stack, so a model you tune with it is an ordinary adapter you can load anywhere. Its documentation says it supports reinforcement learning methods including GRPO, GSPO and DPO, and quotes tuning on as little as 3 GB of VRAM with its notebooks and a 75 percent memory saving for 4-bit QLoRA against 16-bit LoRA (documentation fetched in October 2026; those are the project's own figures, which I did not reproduce).

State of play, October 2026

The project's documentation says FastLanguageModel.from_pretrained takes arguments such as max_seq_length (it suggests 2048 for testing) and load_in_4bit, where setting the latter to false gives 16-bit LoRA. Which models and GPUs it supports, and speed-up claims, change with each release; trust a measurement on your own run over a table.

10-minute guided exercise

Run the same fine-tune two ways and compare time and memory. Use the TRL example as run A and the Unsloth version as run B, same model, same 500 examples, same 50 steps.

  1. Minute 0 to 2: start a free Colab or Kaggle GPU session, or use your own NVIDIA GPU. Open a second terminal or cell running nvidia-smi in a loop.
  2. Minute 2 to 6: run A. Note seconds per step and peak memory.
  3. Minute 6 to 9: run B (below). Note the same two numbers.
  4. Minute 9 to 10: compare. Also check that the two adapters give similar answers to three prompts: a faster trainer is useful only if the model is as good.
# train_unsloth.py: illustrative, not run here (no GPU). Argument names follow Unsloth's fine-tuning guide; check the current notebook.
from unsloth import FastLanguageModel
from trl import SFTConfig, SFTTrainer
from datasets import load_dataset

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="<same 0.5B or 1B base as run A>", max_seq_length=2048, load_in_4bit=True)
model = FastLanguageModel.get_peft_model(model, r=16, lora_alpha=16,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj"])

dataset = load_dataset("trl-lib/Capybara", split="train[:500]")
trainer = SFTTrainer(model=model, tokenizer=tokenizer, train_dataset=dataset,
                     args=SFTConfig(output_dir="out-unsloth", max_steps=50, per_device_train_batch_size=4,
                                    learning_rate=2e-4, logging_steps=5))
trainer.train()

What to look for. Peak memory should be lower in run B than in run A if both load the model in the same precision; if you compare 4-bit B against 16-bit A, the difference is mostly the quantisation, not the library, so keep the settings equal for a fair test. Also look at the loss at step 50 in both: a faster run that ends at a clearly higher loss changed something besides speed.

Common pitfalls

  • Comparing different precisions and calling the difference a speed-up.
  • Training on a free GPU with a long max_seq_length and running out of memory: halve the sequence length or the batch size before anything else.
  • Exporting a merged 4-bit model and forgetting that merging into quantised weights has its own rounding error (chapter 11); evaluate the exported model, not the adapter in training memory.
  • Treating a notebook as a recipe: notebooks are demonstrations on toy data. The hyperparameters for your task come from your dev-set ablations.

Serve and run

An engine for GPU servers and a runner for laptops. Both turn the bytes-per-token arithmetic of chapters 18 and 19 into something you can time.

vLLM & SGLang

Install: pip install vllm (Linux with an NVIDIA GPU is the best-supported path; other hardware has separate builds) and pip install "sglang[all]" (check its documentation for the current extra) · Needs: a GPU with enough memory for the model plus cache · Alternatives: TensorRT-LLM, Text Generation Inference, llama.cpp for CPU and laptops · Chapters: 18, 20, 22 · Practice: Lab 6, Studio 3, case C4

vLLM and SGLang are open-source serving engines. They implement continuous batching, a paged KV cache and prefix caching (chapter 20), expose an OpenAI-compatible HTTP API, and serve LoRA adapters beside a base model. You use them to turn weights into an endpoint, and to measure the throughput and latency that chapter 22 predicts.

State of play, October 2026

vLLM's documentation (fetched October 2026) describes LoRA serving with --enable-lora, adapters registered with --lora-modules name=path, and a request choosing an adapter through its model field; --max-loras, --max-lora-rank and --max-cpu-loras set the slots. Defaults, the set of supported models and benchmark flags change across releases and I could not confirm the current version number from the project's release page, so run vllm serve --help for your version.

10-minute guided exercise

Predict the single-stream speed, then measure it. Before starting an engine, compute the ceiling. Chapter 18's decode bound for one stream is the memory bandwidth divided by the bytes read per token (all the weights): for an 8B model in bf16 (16.06 GB) on a 24 GB card with, say, 300 GB/s of bandwidth, that is about 19 tokens a second; on an H100 with 3.35 TB/s it is about 209 (the chapter's numbers). Look up your own GPU's bandwidth in its datasheet.

  1. Minute 0 to 2: predict the single-stream tokens per second and, using the formula for cache bytes per token (2 × layers × KV heads × head width × bytes), how many 4,096-token conversations fit.
  2. Minute 2 to 5: start the server with a small model that fits (below).
  3. Minute 5 to 8: send one streaming request and time the tokens, then run the engine's benchmark tool with 1, 8 and 32 concurrent requests.
  4. Minute 8 to 10: compare. Single-stream speed should be near your ceiling (typically below it); throughput should rise steeply with concurrency while per-stream speed falls slowly, the shape of the curve in chapter 18.
$ vllm serve <small-model> --max-model-len 4096 --gpu-memory-utilization 0.90
$ curl http://localhost:8000/v1/models
$ curl http://localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{"model": "<small-model>", "messages": [{"role": "user", "content": "Say hello in five words."}], "max_tokens": 32}'
$ vllm bench serve --help    # flags for the benchmark client differ by version
$ python -m sglang.launch_server --model-path <small-model> --port 30000
$ # SGLang also exposes an OpenAI-compatible endpoint; send the same curl request to port 30000

What to look for. Server logs print how many cache blocks fit after loading the weights: that number is your batch limit and should match your hand calculation within a modest margin. Repeat a request with an identical long prompt twice: if prefix caching is on, the second time-to-first-token should drop. Try two prompts with the same first 1,000 tokens and different endings.

Common pitfalls

  • Benchmarking with one request and reporting throughput. Throughput is a property of the batch (chapter 22); report it with the concurrency, input length and output length.
  • Setting maximum context length far above what you need: the engine must be able to hold it, which reduces how many sequences fit.
  • Comparing engines on different settings (precision, context limit, cache size) and attributing the gap to the engine.
  • Quoting a throughput number from a vendor blog without its prompt and output lengths. A figure like "12,000 tokens per second" means little without them.

llama.cpp & Ollama

Install llama.cpp: the project README (fetched October 2026) lists an install script, prebuilt binaries, Docker and building from source; Homebrew packages also exist · Install Ollama: curl -fsSL https://ollama.com/install.sh | sh on macOS and Linux, or the installers on ollama.com · Needs: a laptop with 8 to 16 GB of memory is enough for the examples · Alternatives: LM Studio, MLX (Apple silicon), vLLM for GPU servers · Chapters: 19 · Practice: Lab 7

llama.cpp runs quantised models on ordinary hardware: CPUs, Apple silicon, and consumer GPUs. It stores models in the GGUF file format with quantisation types such as Q8_0, Q5_K_M and Q4_K_M (chapter 19). Ollama wraps it in a service with a model library, a local HTTP API, and one-line commands. They are the quickest way to feel how model size, bits per weight and memory interact, with no cloud account.

State of play, October 2026

The llama.cpp README I fetched in October 2026 shows launching with -hf to download a GGUF from Hugging Face and run it, and an OpenAI-compatible server mode. It writes the commands in a unified form (llama cli, llama serve) where older documentation uses separate binaries (llama-cli, llama-server); the quantisation README still uses llama-quantize. Command names have changed before, so check --help. Ollama's README shows ollama run <model> and a chat endpoint at http://localhost:11434/api/chat.

10-minute guided exercise

Choose a quantisation level by arithmetic, then confirm it with a download.

  1. Minute 0 to 3: compute. Run gguf_size.py below. It uses the bits-per-weight values in the llama.cpp quantisation README (from its Llama-3.1-8B table) to compute file sizes for an 8.03B-parameter model, adds the KV cache for 8,192 tokens at 128 KiB per token (chapter 18) and 1 GB of overhead, and checks fit against 85 percent of your memory.
  2. Minute 3 to 7: run. Pull a small model with Ollama or llama.cpp that fits (below). Ask three questions and note the speed in tokens per second.
  3. Minute 7 to 10: compare. Pull the same model at two quantisation levels if the library offers them. Ask the same three questions. Is there a difference you can see? Does the smaller one answer faster?
"""gguf_size.py: file size and 'fits?' for an 8.03B-parameter model at llama.cpp quant types. Bits per weight are from the llama.cpp quantize README (Llama-3.1-8B table)."""
P = 8.03e9
BPW = {"F16": 16.0005, "Q8_0": 8.5008, "Q6_K": 6.5633, "Q5_K_M": 5.7036, "Q4_K_M": 4.8944, "Q3_K_M": 3.9960, "Q2_K": 3.1593}

for ram in (8, 16):
    print(f"--- {ram} GB of memory, 8,192-token context ({8192*KV_PER_TOKEN/1e9:.2f} GB cache), 1.0 GB runtime overhead")

At 8 GB of memory, an 8B model fits only at around 3 to 4 bits per weight, with little room for context; at 16 GB, even Q8_0 fits. What to look for. Decode speed on a laptop is bounded by memory bandwidth, exactly as on a GPU: halving the bits per weight roughly doubles tokens per second, up to other overheads. Quality loss shows first in arithmetic, rare facts and long instructions. The README suggests measuring accuracy loss by perplexity or KL divergence against the unquantised model; do the same check on a few of your own prompts.

Common pitfalls

  • Judging a quantisation level from one chat. Use the same ten prompts for every level.
  • Forgetting the cache and overhead when deciding what fits.
  • Assuming a library's default tag is the quantisation you want; read the tag.
  • Comparing speed across machines. Tokens per second depends on memory bandwidth, which differs by an order of magnitude between a laptop and a data-centre GPU.

Evaluate and observe

A trained model is a hypothesis. These two tools tell you whether it is better, and what the hardware was doing while you found out.

lm-evaluation-harness

Install: pip install "lm_eval[hf]" (or "lm_eval[vllm]" for the vLLM backend) · Needs: a model to test, and a GPU for anything above a small model · Alternatives: Inspect, lighteval, OpenAI Evals-style custom harnesses, your own scripts · Chapters: 23 · Related: assertions and eval harnesses, statistics for evals

EleutherAI's lm-evaluation-harness runs a model on a library of standard tasks with fixed prompts, few-shot examples and scoring, so two people running the same task get the same number. It supports Hugging Face models, vLLM and API backends. Use it to check that a trained model has not regressed on general skills (chapter 23), and as a model for how to run evaluations reproducibly. Do not use a public benchmark as a measure of your product.

State of play, October 2026

The project README, fetched in October 2026, shows lm_eval --model hf --model_args pretrained=... --tasks ... --device cuda:0 --batch_size 8, a --limit option for a quick sample, --output_path and --log_samples to save results and per-item responses, and lm-eval ls tasks to list tasks. Tasks are added and renamed often, and many older benchmarks are saturated (chapter 23); pin the harness version and the task version when you report a number.

10-minute guided exercise

Run a tiny evaluation, then ask whether a difference is real.

  1. Minute 0 to 2: install and list tasks.
  2. Minute 2 to 5: run twice, the base model and your fine-tuned or quantised version, each with a small task, --limit 100 and --log_samples. Read five logged responses to check that answers are being extracted correctly; a wrong parser makes every score meaningless.
  3. Minute 5 to 8: compare item by item. Convert each run's logged samples to a list of correct and incorrect items (field names differ by version, so inspect one line first). The script below shows the comparison on synthetic item files that it creates itself.
  4. Minute 8 to 10: decide. Is the paired interval around zero? If so you do not have evidence that the two models differ on this task.
$ pip install "lm_eval[hf]"
$ lm-eval ls tasks | head
$ lm_eval --model hf --model_args pretrained=<model> --tasks hellaswag --device cuda:0 --batch_size 8 --limit 100 --output_path out/base --log_samples
"""paired.py: compare two evaluation runs item by item. Reads two JSONL files with {"doc_id": int, "correct": 0 or 1} per line
(you produce them from lm_eval --log_samples output; field names differ between versions). Here we build SYNTHETIC files first so the script runs anywhere."""
import json, random, sys
random.seed(5)
def make(path, p, shared):
    with open(path, "w") as f:
        for i in range(400):
            ok = shared[i] if random.random() < 0.8 else random.random() < p
            f.write(json.dumps({"doc_id": i, "correct": int(ok)}) + "\n")
base = [random.random() < 0.55 for _ in range(400)]
make("run_a.jsonl", 0.55, base); make("run_b.jsonl", 0.60, base)      # synthetic: B is not truly better by much
def load(p): return {json.loads(l)["doc_id"]: json.loads(l)["correct"] for l in open(p)}
a, b = load("run_a.jsonl"), load("run_b.jsonl")
ids = sorted(set(a) & set(b)); n = len(ids)
d = [b[i]-a[i] for i in ids]
only_b = sum(x == 1 for x in d); only_a = sum(x == -1 for x in d)
mean = sum(d)/n
boots = sorted(sum(d[random.randrange(n)] for _ in range(n))/n for _ in range(2000))
lo, hi = boots[50], boots[1949]
print(f"items {n}  A {sum(a.values())/n:.3f}  B {sum(b.values())/n:.3f}  B-only right {only_b}  A-only right {only_a}")
print(f"paired difference {mean:+.3f}  95% bootstrap interval [{lo:+.3f}, {hi:+.3f}]  -> {'real' if lo>0 or hi<0 else 'not distinguishable from noise'}")
items 400  A 0.560  B 0.545  B-only right 30  A-only right 36
paired difference -0.015  95% bootstrap interval [-0.055, +0.025]  -> not distinguishable from noise

Real output from running paired.py here, on synthetic correctness files with an 80 percent overlap that the script writes itself, so no model is involved. Of 400 items, B alone was right on 30 and A alone on 36; the paired difference is −1.5 points with an interval of about ±4, so "not distinguishable from noise". Most small differences between two runs on a few hundred items look like this (statistics for evals).

What to look for. The harness's reported standard error, which is the simplest warning that a difference is small relative to noise; whether the number changes when you change the few-shot count or prompt format (a sign of fragility); and whether the benchmark's items might have been in the model's training data (contamination).

Common pitfalls

  • Reporting a score without the harness version, task version, few-shot setting and prompt format.
  • Comparing your number with a leaderboard value produced with different settings.
  • Using --limit in the final report. It exists for smoke tests.
  • Evaluating only the skill you trained. Add a general-skills regression run.

nvidia-smi & nvtop

Install: nvidia-smi ships with the NVIDIA driver; nvtop comes from your package manager (for example sudo apt install nvtop) · Needs: an NVIDIA GPU (nvtop also supports some other vendors) · Alternatives: gpustat, nvitop, DCGM for fleets, rocm-smi on AMD · Chapters: 2, 5 · Related: metrics and percentiles

nvidia-smi prints, for every GPU, the memory used and total, utilisation, temperature, power draw and the processes using it. nvtop is a live, top-style view of the same. They answer the first questions about any slow or crashing job: is the GPU busy, is memory about to run out, is it throttling, and which process owns it.

What the numbers mean

"GPU-Util" is the share of the sampling interval in which some kernel was running, not how many of the arithmetic units were busy: a memory-bound decode loop can show 100 percent while using a small share of the chip's FLOPs (chapter 18). Memory used includes memory a framework has reserved but not filled, so a PyTorch job's cache allocator can make usage look higher than the live tensors.

10-minute guided exercise

Watch a job's memory and find its headroom.

  1. Minute 0 to 2: look. Run nvidia-smi once with nothing running and note the baseline memory.
  2. Minute 2 to 4: log. Start a logger that writes one CSV line a second (below).
  3. Minute 4 to 8: load. Start a training run (the TRL example) or a vLLM server in another terminal, and send traffic or let a few steps pass.
  4. Minute 8 to 10: summarise. Run the parser below on your CSV. Compare peak memory with your fit.py prediction, and look at how much headroom is left.

$ nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used,memory.total,power.draw --format=csv,noheader,nounits -l 1 > gpu.csv
$ nvidia-smi --query-compute-apps=pid,used_memory --format=csv      # which process holds the memory
$ nvidia-smi dmon -s um                                             # rolling utilisation and memory lines
$ nvtop
"""gpulog.py: summarise `nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used,memory.total,power.draw --format=csv,noheader,nounits -l 1 > gpu.csv`.
The sample lines below were TYPED BY HAND to test the parser; they are not from a real GPU."""
import io, statistics as st
sample = """2026/10/14 09:00:01.100, 3, 1210, 81559, 71.2
2026/10/14 09:00:02.100, 97, 61240, 81559, 612.4
2026/10/14 09:00:03.100, 99, 61250, 81559, 640.8
2026/10/14 09:00:04.100, 41, 61250, 81559, 330.1
2026/10/14 09:00:05.100, 98, 79870, 81559, 655.0"""
rows = [[x.strip() for x in l.split(",")] for l in io.StringIO(sample)]
util = [float(r[1]) for r in rows]; used = [float(r[2]) for r in rows]; total = float(rows[0][3])
print(f"samples {len(rows)}  mean util {st.mean(util):.0f}%  min util {min(util):.0f}%  peak memory {max(used)/1024:.1f} GiB of {total/1024:.1f} GiB ({max(used)/total*100:.0f}%)")
print("memory headroom at peak:", f"{(total-max(used))/1024:.2f} GiB", "<- under 2 GiB: an OOM waits on the next long batch" if total-max(used) < 2048 else "")
samples 5  mean util 68%  min util 3%  peak memory 78.0 GiB of 79.6 GiB (98%)
memory headroom at peak: 1.65 GiB <- under 2 GiB: an OOM waits on the next long batch

Real output from running gpulog.py here. The five input lines were typed by hand to test the parser and are not from a GPU; run it on your own gpu.csv (replace the sample with open("gpu.csv")). The point of the summary is the last line: a job that peaks at 98 percent of memory has no room for the next long batch, and will fail on a day when one arrives (chapter 5).

What to look for. Memory that climbs steadily over a long run (a leak, or a cache that grows with sequence length); utilisation that drops to near zero in a regular rhythm (data loading or checkpointing stalls); temperature and power near the card's limit with falling clocks (throttling). Low utilisation during training usually means the GPU is waiting for input, not that the model is too small.

Common pitfalls

  • Reading utilisation as efficiency. For efficiency, compare achieved tokens per second with the bound from chapter 22.
  • Killing the wrong process because several jobs share a GPU. Check the process list first.
  • Sampling once. Memory spikes come at the longest batch, so log through a whole run.
  • Forgetting that nvidia-smi in a container shows the host's GPUs unless the runtime restricts them, and that per-process memory may be hidden by the runtime.

Pretraining Data

A language model is a compressed record of the text it was trained on, so the quality of that text sets a ceiling on everything later. This chapter follows trillions of tokens from a public web crawl to a training mix: how text is extracted, filtered, deduplicated with MinHash and weighted, and why each step is an experiment rather than a recipe.

Why this matters

Part 1 of this course is about the systems that build a base model; this is the first of them and the only one that is not about hardware. Most of the difference between a good open model and a poor one of the same size is data work that never appears in the architecture diagram. After this chapter you will be able to describe a web-scale data pipeline stage by stage, estimate what each stage removes, implement near-duplicate detection with MinHash and locality-sensitive hashing, explain why "deduplicate everything globally" can make a dataset worse, and read a data-mix table such as Llama 3's critically. Lab 1 builds a small version of this pipeline.

Data is the other half of the model

Chapter 14 of A2 showed the pretraining objective: predict the next token of a very large pile of text, and let the network find whatever structure helps. The objective is the same for every lab. The pile is not. Two teams with the same architecture, the same optimiser and the same compute will get different models if they feed them different text, and the gap can be larger than the gap between two architectures.

The scale makes the pile an engineering problem. Llama 3 was pretrained on about 15 trillion tokens, up from 1.8 trillion for Llama 2 (Dubey et al., 2024, "The Llama 3 Herd of Models"). At roughly four characters of English per token (a rule of thumb from tokenisation, not an exact figure), 15 trillion tokens is on the order of 60 terabytes of clean text. Nobody reads it. The only way to control what is in it is to build a pipeline of automated stages and check each stage by measurement.

Two facts shape everything below. First, almost all text comes from the web, and the raw web is mostly not worth learning from: navigation menus, spam, product listings, machine-generated pages and the same article copied a thousand times. Second, you cannot judge a filter by looking at it. A rule that looks sensible can remove useful text, and a rule that looks crude can help. The honest way to decide is an ablation: train a small model on the data with and without the step, and compare benchmark scores. Almost every number in this chapter comes from ablations of that kind.

Where the text comes from

The largest source is Common Crawl, a non-profit that has crawled the public web since 2007 and publishes each crawl as a snapshot (also called a dump) of billions of pages, free to download. Each snapshot comes in three flavours: WARC files hold the raw HTTP responses, WAT files hold extracted metadata, and WET files hold plain text that Common Crawl has already pulled out of the HTML. The FineWeb paper reports 100 snapshots at the time of writing and used 96 of them (Penedo et al., 2024, "The FineWeb Datasets"). Crawlers respect the site's robots.txt rules, which matters for the legal and ethical questions at the end of the chapter.

Web text is not the only input. Real training mixes add code (public repositories), books and papers, encyclopaedias such as Wikipedia, mathematics pages, multilingual text and, increasingly, synthetic text written by earlier models (chapter 15). Each has its own pipeline, because code needs different cleaning from prose. Llama 3's team built separate pipelines for code and for maths and reasoning pages, each with its own HTML extraction and classifier (Dubey et al., 2024).

State of play, October 2026

The FineWeb dataset page on Hugging Face lists 110 Common Crawl snapshots, from 2013 to mid-2025, and the licence is ODC-By. The original release (2024) was 15 trillion tokens from 96 snapshots; the page has been extended since. Llama 3's own corpus was never released, so its pipeline can be read about but not downloaded. Other open pretraining corpora exist (Dolma, DCLM, RedPajama v2 and more) and new ones appear every few months; check their dataset cards for current sizes, which this chapter deliberately does not copy.

Extraction: from HTML to prose

A web page is mostly not the article. It carries a navigation bar, a cookie banner, a footer, advertisements, comment threads and scripts. Text extraction keeps the main content and drops the rest. The task is called boilerplate removal and is harder than it sounds, because "boilerplate" is whatever repeats across a site and the main text is whatever does not, and there is no tag that says which is which.

The choice of extractor matters measurably. FineWeb compared Common Crawl's ready-made WET text with text extracted from the WARC files using the open-source trafilatura library, trained small models on each, and found the custom extraction clearly better (Penedo et al., 2024, their first ablation). Llama 3 went further and wrote its own parser, tuned for precision of boilerplate removal and recall of content, with special handling of pages containing mathematics and code, and kept the alt text of images because maths is often an image whose alt attribute holds the formula. The same paper reports that stripping markdown markers helped a model trained mostly on web data, which is a reminder that formatting is data too.

Below is a stripped-down extractor and quality filter in standard-library Python. It is nowhere near production, but it contains the real ideas: skip structural tags, collapse whitespace, and then ask simple statistical questions of the text. The rules are simplified versions of those in DeepMind's Gopher pipeline (Rae et al., 2021, "Scaling Language Models: Methods, Analysis & Insights from Training Gopher"), which FineWeb and many others reuse.

import re
from html.parser import HTMLParser

class TextExtractor(HTMLParser):
    """Keep text from content tags; drop script, style, nav, footer."""
    SKIP = {"script", "style", "nav", "footer", "header", "aside"}
    BLOCK = {"p", "div", "li", "h1", "h2", "h3", "br", "tr"}
    def __init__(self):
        super().__init__()
        self.skip, self.out = 0, []
    def handle_starttag(self, tag, attrs):
        if tag in self.SKIP: self.skip += 1
        if tag in self.BLOCK: self.out.append("\n")
    def handle_endtag(self, tag):
        if tag in self.SKIP: self.skip -= 1
    def handle_data(self, data):
        if not self.skip: self.out.append(data)

def extract(html):
    p = TextExtractor(); p.feed(html)
    lines = [re.sub(r"\s+", " ", l).strip() for l in "".join(p.out).split("\n")]
    return "\n".join(l for l in lines if l)

def quality_flags(text):
    """Gopher-style rules (Rae et al., 2021), simplified thresholds."""
    words = text.split()
    lines = text.split("\n")
    flags = []
    if not 50 <= len(words) <= 100_000: flags.append("word count outside 50..100000")
    mean_len = sum(len(w) for w in words) / max(1, len(words))
    if not 3 <= mean_len <= 10: flags.append(f"mean word length {mean_len:.1f} outside 3..10")
    sym = sum(w.count("#") + w.count("...") for w in words) / max(1, len(words))
    if sym > 0.1: flags.append(f"symbol-to-word ratio {sym:.2f} > 0.1")
    if sum(l.lstrip().startswith(("-", "*", "•")) for l in lines) / len(lines) > 0.9: flags.append("> 90% bullet lines")
    if sum(l.endswith("...") for l in lines) / len(lines) > 0.3: flags.append("> 30% lines end in ellipsis")
    if sum(any(c.isalpha() for c in w) for w in words) / max(1, len(words)) < 0.8: flags.append("< 80% words contain a letter")
    return flags

# (three small HTML pages: an article about tides, keyword spam, a stub; omitted here)
for name, html in [("article", article), ("keyword spam", spam), ("stub page", short)]:
    text = extract(html)
    f = quality_flags(text)
    print(f"{name:13s} words={len(text.split()):3d}  ->", "KEEP" if not f else "DROP: " + "; ".join(f))
article       words=122  -> KEEP
keyword spam  words=300  -> DROP: symbol-to-word ratio 0.40 > 0.1; > 90% bullet lines; > 30% lines end in ellipsis; < 80% words contain a letter
stub page     words=  5  -> DROP: word count outside 50..100000

(The three sample pages are defined at the top of the real script, which printed exactly this when run; the listing omits them for length.) The spam page trips four rules at once, which is typical: junk tends to look odd in several ways, so thresholds do not need to be tuned finely. The hard cases are the pages near the boundary, and the next section shows how FineWeb's authors approached them.

Cheap filters first: language, URL and heuristics

The first filters are cheap enough to run on every page. URL filtering drops domains on blocklists of adult or known-bad sites. Language identification runs a small classifier, usually fastText (a library of fast linear text classifiers), over the text and keeps documents that score above a threshold: FineWeb kept English with a score of at least 0.65, and Llama 3 used a fastText model that distinguishes 176 languages. FineWeb also applied the repetition and quality rules from DeepMind's MassiveText pipeline, of which the code above is a miniature. After these base filters, FineWeb's roughly 36 trillion tokens (counted with the GPT-2 tokeniser) were left from the 96 snapshots.

Beyond rules copied from earlier work, FineWeb's authors made rule design systematic. They computed over 50 document statistics (lines per document, average word length, repetition measures and so on) on a "higher quality" and a "lower quality" version of the same snapshot, found the statistics whose distributions differed, chose thresholds where the low-quality data was densest, and tested the 16 resulting candidate filters by training models. Three survived. The most useful removes documents in which 12 percent or fewer of lines end with punctuation, which cut about 10 percent of tokens; the older C4 rule with a similar purpose (keep only lines ending in terminal punctuation) removed about 30 percent.

That comparison is worth pausing on, because it shows the kind of reasoning data work needs. The C4 dataset (Raffel et al., 2020, the T5 paper) was built with a set of simple rules: drop lines without terminal punctuation, lines mentioning JavaScript or cookie and terms-of-use boilerplate, pages that are too short, pages containing "lorem ipsum" or a curly bracket. Each rule is easy to justify. But FineWeb found that the terminal-punctuation rule, though it gave the largest single boost on a benchmark, threw away roughly 30 percent of all tokens. Using every C4 rule except that one matched C4's benchmark scores while removing only about 7 percent. A filter is a trade between precision and the data you lose, and at 15 trillion tokens you care about both.

Common misconception

"Filtering is cleaning: remove the bad, keep the good, and more filtering is better." Every filter also removes good text, and removed text cannot be recovered. A filter that removes 30 percent of a corpus to gain two benchmark points may leave you too little data to train a larger model without repeating it. Heuristic filters are also tuned on benchmarks, and a benchmark rewards a particular kind of text (educational, well-formed English prose). Chat logs, poetry, dialect and code comments often look "low quality" to a rule built that way.

Deduplication

The web repeats itself. Mirrors copy sites, news is syndicated, licences and terms-of-service pages are pasted everywhere, and template-driven sites produce thousands of near-identical pages. Deduplication removes repeated content before training. Lee et al. (2021, "Deduplicating Training Data Makes Language Models Better") measured the effect on widely used datasets:

  • All four common datasets they studied contained near-duplicate examples: from 3.04 percent of C4's training examples to 13.63 percent of RealNews.
  • One 61-word English sentence appeared more than 60,000 times in C4.
  • Over 1 percent of the text a model emitted without a prompt was copied verbatim from its training data. Models trained on the deduplicated data emitted memorised text about ten times less often.
  • Training and validation sets overlapped: 4.6 percent of the C4 validation set was duplicated in the training set, which inflates the evaluation.

Duplicates cost twice. They waste training compute on text the model has effectively already seen, and they raise the chance that a model memorises and regurgitates specific passages, which matters for privacy and for copyright. The question is how to find them among billions of documents.

Exact deduplication and line-level deduplication

The cheapest method hashes each whole document (SHA-256 of the text) and keeps one per hash. It catches only byte-identical copies, and the web has few of those: one changed date or one extra "Share this page" line is enough to defeat it. A second cheap method works on lines. Boilerplate such as "Subscribe to our newsletter!" appears on thousands of pages that are otherwise different, so Llama 3's pipeline removes lines that appear more than 6 times within each bucket of 30 million documents, following ccNet (Wenzek et al., 2019). The Llama 3 authors note that their manual inspection showed this also removes some frequent good text, but evaluations showed strong improvements, so they kept it. Here is the idea at toy scale:

import hashlib
from collections import Counter

docs = {
 "a": "Tides are caused by the moon.\nSubscribe to our newsletter!\nThe sun also matters.",
 "b": "Tides are caused by the moon.\nSubscribe to our newsletter!\nThe sun also matters.",   # exact copy
 "c": "Volcanoes form at plate boundaries.\nSubscribe to our newsletter!\nHot spots are the exception.",
 "d": "Glaciers carve valleys.\nSubscribe to our newsletter!\nThey move slowly under their own weight.",
 "e": "Rivers meander.\nSubscribe to our newsletter!\nOxbow lakes are cut-off meanders.",
}
# 1. exact document dedup: hash the whole text, keep the first of each hash
seen, kept = set(), {}
for k, t in docs.items():
    h = hashlib.sha256(t.encode()).hexdigest()
    if h not in seen:
        seen.add(h); kept[k] = t
print("after exact dedup:", list(kept))

# 2. line-level dedup: drop lines that occur in more than 3 documents (Llama 3 used: more than 6 per 30M docs)
line_docs = Counter()
for t in kept.values():
    for line in set(t.split("\n")): line_docs[line] += 1
for k, t in kept.items():
    kept[k] = "\n".join(l for l in t.split("\n") if line_docs[l] <= 3)
print("lines seen in many docs:", [l for l, n in line_docs.items() if n > 3])
for k, t in kept.items(): print(k, "->", repr(t))

Near-duplicates: the comparison problem

Most duplicates on the web are near-duplicates: the same article with a different header, a changed sentence, an added footer. To find them we need a similarity measure and a way to avoid comparing every pair. Comparing every pair among N documents costs N²/2 comparisons; at N = 1010 that is 5 × 1019, hopeless. The standard solution is MinHash with locality-sensitive hashing (LSH), from Broder (1997).

Start with the similarity. Turn each document into its set of shingles, overlapping runs of n words (FineWeb uses 5-word shingles). The Jaccard similarity of two documents A and B is the size of the overlap of their shingle sets divided by the size of their union:

J(A, B) = |A ∩ B| / |A ∪ B|

Two identical documents have J = 1, two with no shared 5-word sequence have J = 0. A document with a short added footer has J close to 1. Jaccard is intuitive but still expensive: sets are large. MinHash compresses each set to a short signature of numbers, such that the signatures reveal the Jaccard similarity.

Go deeper: why MinHash estimates Jaccard similarity optional

Take a random hash function h that assigns a random-looking number to every possible shingle, and define the MinHash of a set S as the smallest hash value among its members: minh(S) = min over x in S of h(x). Now consider A and B together. Look at their union A ∪ B and ask which single element has the smallest hash among all of them. Because h is random, each element of the union is equally likely to be that element, so the probability it is any particular one is 1 / |A ∪ B|.

The minima of A and of B are equal exactly when that overall smallest element lies in both sets, that is, in A ∩ B. There are |A ∩ B| such elements, so

P( minh(A) = minh(B) ) = |A ∩ B| / |A ∪ B| = J(A, B).

One hash function therefore gives a yes or no event whose probability is exactly the similarity. Using k independent hash functions and counting the fraction of agreements gives an estimate of J whose standard error shrinks like 1/√k. With k = 112, the error is on the order of 0.05 near J = 0.75 (a rough figure from the binomial formula √(J(1-J)/k), about 0.041).

So a document becomes a signature of k = 112 numbers (FineWeb's choice), and comparing two signatures by counting agreeing positions estimates their similarity. That removes the cost of large sets but not the N² problem. The second idea, LSH, removes that. Split the signature into b bands of r rows (b × r = 112; FineWeb used b = 14 and r = 8). Two documents become candidate duplicates if they agree on all r values of at least one band. In practice you put each band's tuple of values into a hash table, so documents with an equal band land in the same bucket and only those need comparing. No pair is ever compared unless they collide.

Now the arithmetic. If two documents have Jaccard similarity s, a single MinHash value agrees with probability s. All r values in one band agree with probability sr. A band fails to match with probability 1 − sr, all b bands fail with probability (1 − sr)b, and so the probability that at least one band matches is

P(candidate) = 1 − (1 − sr)b

This is an S-shaped curve in s, and the knob is where the S rises. A rough guide for the similarity at which the chance reaches one half is (1/b)1/r; for b = 14 and r = 8 that is 0.72, which agrees with FineWeb's stated target of documents "at least 75% similar". Try other settings:

What to notice. Raising r while keeping b makes the curve steeper and moves it right: fewer false alarms, but near-duplicates at 0.7 slip through. Raising b moves it left: more pairs caught, but more pairs of merely similar documents flagged. The steepness matters because the ideal is a step: nothing below the threshold, everything above it. More hash values (b × r) buy a steeper curve and cost more storage and compute per document, and at 15 trillion tokens that cost is real. Here is the whole method running end to end, including an empirical check that the formula describes reality:

import hashlib, random, struct

def shingles(text, n=5):
    w = text.lower().split()
    return {" ".join(w[i:i+n]) for i in range(len(w) - n + 1)}

P = (1 << 61) - 1
rng = random.Random(42)
COEF = [(rng.randrange(1, P), rng.randrange(P)) for _ in range(112)]   # 112 hash functions a*x+b mod P

def base_hash(s):
    return struct.unpack("<Q", hashlib.blake2b(s.encode(), digest_size=8).digest())[0]

def signature(sh, num_hashes=112):
    xs = [base_hash(s) for s in sh]
    return [min((a * x + b) % P for x in xs) for a, b in COEF[:num_hashes]]

def bands(sig, b=14, r=8):
    return [tuple(sig[i*r:(i+1)*r]) for i in range(b)]

def jaccard(a, b): return len(a & b) / len(a | b)

# base = a paragraph about tides; near = base with two words changed and a footer added;
# other = a paragraph about photosynthesis (texts defined in the full script)
sh = {k: shingles(v) for k, v in {"base": base, "near-copy": near, "unrelated": other}.items()}
sig = {k: signature(v) for k, v in sh.items()}
print("5-gram shingles:", {k: len(v) for k, v in sh.items()})
for x, y in [("base", "near-copy"), ("base", "unrelated")]:
    est = sum(a == b for a, b in zip(sig[x], sig[y])) / 112
    cand = any(bx == by for bx, by in zip(bands(sig[x]), bands(sig[y])))
    print(f"{x} vs {y}: true Jaccard {jaccard(sh[x], sh[y]):.3f}, MinHash estimate {est:.3f}, shares a band: {cand}")

# empirical S-curve: random set pairs with a chosen Jaccard similarity, 400 pairs per row
print("\nsimilarity  theory 1-(1-s^8)^14   simulated (400 pairs)")

The surprise: global deduplication made FineWeb worse

The obvious plan is to deduplicate across the whole dataset at once: if a page appears in two crawls, keep one. The FineWeb team tried exactly that, working from the newest snapshot backwards. It removed up to 90 percent of the oldest snapshots, shrinking the dataset to 4 trillion tokens, and a model trained on a sample of it improved very little over one trained on non-deduplicated data. That contradicted their assumption, so they investigated.

For the 2013-48 snapshot they trained one model on the 10 percent that global deduplication kept (about 31 billion tokens) and another on 171 billion tokens drawn from the 90 percent it removed (after deduplicating that portion on its own). The model trained on the removed data scored better. On inspection, the kept data contained more advertisements, lists of keywords and badly formatted text: the pages that survived were the ones unique enough not to be duplicated elsewhere, and "unique" on the web correlates with junk as often as with quality. Their remedy was to deduplicate each snapshot independently, which left about 20 trillion tokens and matched the quality of the RefinedWeb dataset in ablations. Their hypothesis, stated cautiously in the paper, is that most of the benefit of deduplication comes from removing the huge clusters of duplicates (hundreds of thousands of documents) that occur in every crawl, and that further deduplication mostly removes good data.

Llama 3 took a different choice and ran global MinHash across its whole corpus, together with URL-level deduplication (keeping the most recent version of each URL) and line-level deduplication. The lesson is not that one approach is right. It is that deduplication strength is a hyperparameter with an optimum, that the optimum depends on what else is in the pipeline (Meta applied model-based quality filters afterwards), and that you find it by measurement.

Exact substring deduplication

MinHash works on whole documents. Duplication also happens inside documents that are otherwise different: a licence block, a boilerplate paragraph, a quoted passage. Lee et al. (2021) removed such repeats by building a suffix array over the whole corpus (a sorted index of every suffix of the text) so that any substring repeated, for instance, for 50 tokens or more can be found and cut. It is exact and powerful, and it needs a very large machine or a distributed implementation. The heavy lifting is sorting data too big for memory, the same merge-sorted-runs idea that LSM trees use for compaction.

Systems connection

A web-scale pipeline is a batch processing job: millions of independent files, a stage per step, and a shuffle where documents with the same band hash must meet on one machine. MinHash banding is a partitioning trick, grouping by a key so that only likely matches meet, the same idea as the shard keys in sharding. It is also what file-sync systems do when they split files into chunks and store each unique chunk once (see the file sync studio), except that those systems want exact matches. Failures at this scale are normal, so stages should be idempotent: rerunning a failed shard must produce the same output.

Model-based quality filtering

Rules recognise obvious junk. They cannot recognise "this page is a clear explanation of how tides work" versus "this page is a grammatical but empty product description". For that, teams train a small quality classifier and keep the documents it scores highest. There are two families.

Classifiers trained on a reference set

Take a set of text you consider good (Wikipedia pages, pages linked from Wikipedia, high-scoring Reddit answers, instruction-style data), take a sample of ordinary web text, and train a fast linear classifier to tell them apart. The score is the probability that a page "looks like" the reference. The DataComp-LM (DCLM) project tested this at scale and concluded that model-based filtering is the key ingredient for a good training set; its filter was a fastText classifier trained on positive examples from curated instruction-style data and ELI5 answers against web text, applied with a percentile cut-off (Li et al., 2024, "DataComp-LM"). Llama 3's team did similar work, including a fastText model trained to recognise text that Wikipedia would reference and heavier DistilRoBERTa classifiers trained on labels produced by Llama 2.

The mechanism is simple enough to write in a few lines. The following is a naive Bayes classifier on four good and four bad toy sentences, using the standard-library only. The score is the log-odds that a text looks "good": positive keeps, negative drops.

import math
from collections import Counter

good = ["the proof follows from the definition of a limit and the triangle inequality",
        "photosynthesis converts light energy into chemical energy in the chloroplast",
        "the court held that the contract was void because consideration was missing",
        "to compute the mean we sum the values and divide by the number of observations"]
bad = ["click here buy now cheap pills best price free shipping",
       "win win win free prize click now limited offer subscribe",
       "home login cart checkout sale sale sale buy buy now",
       "hot singles near you click here free free free"]

def counts(docs): return Counter(w for d in docs for w in d.split())
cg, cb = counts(good), counts(bad)
vocab = set(cg) | set(cb)

def log_odds(text):
    """Naive Bayes log P(good|text) - log P(bad|text), add-one smoothing, equal priors."""
    s = 0.0
    for w in text.split():
        pg = (cg[w] + 1) / (sum(cg.values()) + len(vocab))
        pb = (cb[w] + 1) / (sum(cb.values()) + len(vocab))
        s += math.log(pg / pb)
    return s

for t in ["the energy of the system is the sum of the kinetic and chemical energy",
          "buy cheap energy pills now click here",
          "the court sale was free of consideration"]:
    print(f"{log_odds(t):+6.2f}  {'keep' if log_odds(t) > 0 else 'drop'}  {t}")
+14.64  keep  the energy of the system is the sum of the kinetic and chemical energy
 -6.27  drop  buy cheap energy pills now click here
 +1.98  keep  the court sale was free of consideration

Note the third line: a sentence that mixes legal words and the spam word "sale" lands barely above zero. Classifiers give a score, not a verdict, and choosing the threshold is the real decision. The word "energy" appears in both the good and bad examples of this toy, and the classifier correctly relies on the other words. With eight training sentences this is a demonstration, not a method; real classifiers train on millions of pages.

Classifiers trained on model judgements

The second family replaces the reference set with an LLM acting as a grader. FineWeb-Edu is the clearest public example. The authors had Llama-3-70B-Instruct score 460,000 randomly chosen web pages from one FineWeb snapshot from 0 to 5 for educational value at a grade-school to middle-school level (the prompt was built to avoid favouring advanced technical pages). They then trained a small linear regression head on top of a frozen embedding model (Snowflake arctic-embed-m) using 410,000 of those labels and held out 50,000. That cheap model could then score all 15 trillion tokens of FineWeb, which took 6,000 H100 GPU-hours, far less than running the large model over everything. Keeping pages scoring at least 3 produced FineWeb-Edu, 1.3 trillion tokens, which in the paper's ablations beat other open web datasets on knowledge and reasoning benchmarks such as MMLU, ARC and OpenBookQA. The 3 was chosen as a trade-off: a stricter threshold helped knowledge benchmarks further but hurt others such as HellaSwag. This is a distillation pattern you will meet again in chapter 15: an expensive model labels a sample, a cheap model learns the labels, the cheap model does the bulk work.

Common misconception

"A quality classifier finds quality." It finds resemblance to its reference. A classifier trained on Wikipedia-like text will favour Wikipedia-like text, and one scoring "educational value" will favour textbook explanations over fiction, forums, spoken-language transcripts or non-standard dialects. Those preferences are inherited by the model. They also interact with benchmarks: if the classifier's target is close to the benchmark's style, scores rise partly because the training data looks like the test. Quality is relative to a purpose, and you should evaluate on tasks that were not used to define it.

Mixing: how much of each source

After filtering you hold several corpora of different sizes and qualities: web text, code, books, encyclopaedia pages, maths. The data mix decides the fraction of training tokens drawn from each. Its effect is large: the same corpora in different proportions give models with different strengths, and the proportions interact with how many tokens you can afford.

Llama 3's published summary is the best available real example: about 50 percent of tokens general knowledge, 25 percent mathematical and reasoning, 17 percent code and 8 percent multilingual (Dubey et al., 2024). Notice that the maths and code shares are far larger than their share of the web. The team arrived at the mix with two tools: a knowledge classifier to downsample categories that the web over-represents (their example is arts and entertainment), and scaling-law experiments, in which many small models are trained on candidate mixes and used to predict how a large model would do on each. This is why a mix is a research result rather than a recipe: it was fitted to one model family, one tokeniser and one set of target benchmarks.

Repetition, epochs and temperature

A mix has to be physically possible. If you want 17 percent code in a 15-trillion-token run you need 2.55 trillion code tokens, so either you have them or you repeat the ones you have. One pass over a dataset is an epoch. Muennighoff et al. (2023, "Scaling Data-Constrained Language Models") studied repetition by training many models and report that training with up to 4 epochs of repeated data gives negligible change in loss compared with unique data, while with more repetition the value of added compute eventually decays to zero. So small, high-quality sources can be seen several times; huge web sources are seen less than once.

A standard way to set the weights is temperature sampling: sample source i with probability proportional to its size raised to a power α between 0 and 1. With α = 1 you sample in proportion to size and the biggest source dominates; as α falls toward 0, small sources are upsampled. A worked example with invented but plausible corpus sizes (in billions of tokens, an assumption for illustration) and a 3,000-billion-token budget:

# Illustrative corpus sizes in billions of tokens (assumptions, not a real dataset)
sources = {"web": 9000, "code": 600, "books": 150, "wikipedia": 12, "maths": 40}
budget = 3000   # billions of tokens we can afford to train on (assumption)

def mix(alpha):
    w = {k: v ** alpha for k, v in sources.items()}
    z = sum(w.values())
    return {k: x / z for k, x in w.items()}

print(f"{'source':10s} {'size':>6s} | natural mix -> epochs | alpha=0.5 mix -> epochs")
nat, tmp = mix(1.0), mix(0.5)
for k, size in sources.items():
    e_nat = nat[k] * budget / size
    e_tmp = tmp[k] * budget / size
    print(f"{k:10s} {size:6d} | {nat[k]:9.1%} -> {e_nat:6.2f}      | {tmp[k]:9.1%} -> {e_tmp:6.2f}")
source       size | natural mix -> epochs | alpha=0.5 mix -> epochs
web          9000 |     91.8% ->   0.31      |     67.1% ->   0.22
code          600 |      6.1% ->   0.31      |     17.3% ->   0.87
books         150 |      1.5% ->   0.31      |      8.7% ->   1.73
wikipedia      12 |      0.1% ->   0.31      |      2.4% ->   6.12
maths          40 |      0.4% ->   0.31      |      4.5% ->   3.35

With natural proportions every source is seen 0.31 times, so Wikipedia, 12 billion tokens, contributes almost nothing. At α = 0.5 code gets 17 percent of the tokens and is seen 0.87 times, while Wikipedia is seen 6.1 times, beyond the 4-epoch range where repetition was found harmless. That is the tension a data engineer manages: upsample the sources you value, and watch the epoch count of the small ones. In practice the weights are then tuned by small-scale ablations, as Llama 3's team describes.

Annealing and ordering

The mix need not be constant across training. Llama 3 finished pretraining with an annealing phase: while the learning rate decayed to zero over the last 40 million tokens, the mix was shifted towards small amounts of very high-quality code and mathematics, and the final weights were an average of checkpoints from that phase. The authors also used annealing as a measuring instrument: to judge whether a small new dataset is valuable, anneal a mid-training checkpoint on a mix with 30 percent of the new data and compare benchmark scores, which is cheaper than a full ablation. This links to learning-rate schedules in A2: the end of training is where the model is most sensitive to what it sees last.

Decontamination, privacy and licensing

Three concerns cut across every stage.

  • Contamination. If benchmark questions appear in the training data, scores overstate ability. Pipelines check n-gram overlap between training documents and evaluation sets and remove or flag matches; Lee et al. found train-test overlap affecting over 4 percent of some validation sets. Llama 3's report also analyses contamination of its evaluations. Chapter 23 returns to measuring it, and the contamination is why this chapter's dedup tools matter for evaluation as well as training.
  • Personal data and unsafe content. Both Llama 3 and FineWeb remove domains known for adult content, and Llama 3 also removes domains with high volumes of personally identifiable information; the public FineWeb release anonymises email and public IP addresses. These filters are imperfect and do not make a model privacy-safe. See data protection and privacy for the engineering side.
  • Licensing and consent. Whether training on copyrighted or restricted material is allowed is a legal question that varies by country and is changing; the engineering answer is provenance: record where every document came from, honour opt-outs such as robots.txt where you promised to, and keep the ability to remove a source. This chapter gives no legal advice.

Key takeaways

  • A pretraining pipeline is a chain of cheap-to-expensive stages: extract, language and URL filter, heuristics, deduplicate, model-based scoring, mix. Each stage is judged by training small models, not by inspection.
  • FineWeb's numbers show the scale of attrition: about 36T tokens after base filtering, about 20T after per-snapshot MinHash, 15T after the C4 and custom filters, and 1.3T in the Edu subset at threshold 3.
  • MinHash makes P(signature values equal) equal to Jaccard similarity; banding with b bands of r rows flags a pair with probability 1 − (1 − sr)b, an S-curve whose position you set by choosing b and r.
  • More deduplication is not always better: FineWeb found global deduplication kept worse data than it removed, while Llama 3 deduplicated globally and filtered afterwards. Strength is a tuned hyperparameter.
  • Quality classifiers measure resemblance to a reference set or to an LLM's judgement, and they pass their biases to the model.
  • A mix is a set of fitted weights; repetition up to roughly 4 epochs is nearly as good as fresh data, beyond which returns collapse.

Check your understanding

Two documents have Jaccard similarity 0.9 over their 5-word shingles. You use 112 MinHash values in 14 bands of 8. About how likely is it that they are flagged as candidates?

  1. About 90 percent, because the similarity is 0.9
  2. About 50 percent, because banding is a coin flip
  3. Practically certain, because 1 − (1 − 0.98)14 is very close to 1
  4. Impossible to say without the document length
0.98 is about 0.43, so one band fails with probability 0.57, all 14 fail with probability 0.5714, about 0.0004. The S-curve is much steeper than the similarity itself. Answer 1 confuses the probability for one MinHash value (0.9) with the banded test.

A colleague raises the rows per band from 8 to 13 and lowers the bands from 14 to 9. What happens to the dedup behaviour?

  1. The curve moves right: fewer false alarms but pairs around 0.7 similarity are more likely to be missed
  2. The curve moves left: more near-duplicates are caught
  3. Nothing changes because b × r is roughly constant
  4. Exact duplicates stop being caught
The approximate threshold (1/b)1/r rises from 0.72 to about 0.84. Keeping b × r similar keeps the cost similar, not the behaviour. Exact duplicates have s = 1, so they are always caught whatever the settings.

FineWeb's authors found that globally MinHash-deduplicating all 96 snapshots gave a dataset on which models trained little better than on non-deduplicated data. What explanation did their experiment support?

  1. MinHash is a biased estimator of similarity
  2. Duplicates are helpful because the model sees good text more often
  3. The model needs more than 4 epochs of data
  4. The data kept from old snapshots was lower quality than the data removed, because unique pages were often junk
They trained on the kept 10 percent and on the removed 90 percent of the 2013-48 snapshot and the removed data scored better; inspection showed more ads and keyword lists in the kept part. MinHash itself was fine, and the epoch argument is about a different question.

You must pick a quality threshold for an LLM-labelled classifier like the one behind FineWeb-Edu. A stricter threshold gives a smaller dataset with higher scores on MMLU. What should you check before adopting it?

  1. Only that the classifier's validation F1 is high
  2. Whether performance on other tasks (such as commonsense or conversational benchmarks) and the remaining token count are acceptable
  3. Whether the labels were written by the largest available model
  4. Nothing: higher benchmark scores always mean better data
The FineWeb-Edu authors chose threshold 3 as a trade-off: stricter thresholds helped knowledge benchmarks but hurt others such as HellaSwag. A high F1 only says the classifier reproduces the labels, not that the labels pick the best data for your goal.

Using temperature sampling with α = 0.5, a 12B-token Wikipedia corpus gets 2.4 percent of a 3,000B-token budget in the worked example. What problem does this create?

  1. Wikipedia text will be deduplicated away
  2. The tokeniser will need a larger vocabulary
  3. It would be seen about 6 times, beyond the roughly 4 epochs after which repetition stops behaving like fresh data
  4. Nothing, because repeated high-quality data is always better
2.4 percent of 3,000B is 72B tokens drawn from a 12B corpus: 6 passes. Muennighoff et al. found up to about 4 epochs behave almost like unique data and returns decay beyond that. The fix is a lower weight or more data of that kind.

Why can a line-level rule such as "remove lines that appear more than 6 times in a bucket of 30M documents" be worth keeping even though it deletes some good text?

  1. Lines are always boilerplate when they repeat
  2. The Llama 3 authors found that their evaluations showed strong improvements despite the loss of some frequent high-quality lines
  3. It makes the data smaller, and smaller datasets train faster
  4. It replaces the need for document-level deduplication
The report says manual inspection showed the rule also removed frequent good text, but measured results improved, which is the standard for data decisions. Repetition is a signal, not proof of boilerplate, and the rule complements document-level MinHash rather than replacing it.

Quantisation

A 70-billion-parameter model in 16-bit numbers needs 141 GB of memory before it has read a single prompt. Quantisation stores the same weights in 8, 4 or fewer bits. This chapter explains how a number is squeezed into a few bits, why a handful of outliers make that hard, how GPTQ and AWQ keep 4-bit models usable, and how to measure what the squeeze cost you.

Why this matters

Decoding is limited by how many bytes the GPU must read for every token (chapter 18), and a model that does not fit in memory cannot be served at all. Cutting weights from 16 bits to 4 shrinks both problems by about four times, which is the difference between needing a rack and needing one 24 GB card. The price is error, and the error is not spread evenly: a few badly handled numbers can ruin a model that looked fine on average. After this chapter you will be able to work out what fits on a given GPU at a given precision, choose a scale granularity, explain why outliers are the central difficulty, say what GPTQ and AWQ each do, and design an evaluation that notices the damage before your users do.

Why shrink the numbers at all

Chapter 2 counted the bytes a model needs to train. Serving needs far fewer, but the weights are still the largest item. A parameter stored in bf16 (a 16-bit floating-point format, see A2 chapter 17) costs 2 bytes, so a model with N parameters needs 2N bytes. For Llama 3 8B, with 8.03 billion parameters counted from the shapes in the Llama 3 report (Dubey et al., 2024), that is 16.1 GB. For the 70B model it is 141 GB, which does not fit on any single GPU sold today, and needs two 80 GB cards even before the cache.

Quantisation means representing each weight (and sometimes each activation or cache entry) with fewer bits by mapping it to the nearest of a small set of allowed values. It buys two things.

  • Capacity. Fewer bytes per weight leaves room for a bigger model, or for more KV cache, which means more concurrent sequences.
  • Speed in the memory-bound regime. Chapter 18 showed that generating one token at small batch size is limited by reading the weights from HBM once per step. A step cannot be faster than the weight bytes divided by the memory bandwidth. NVIDIA lists 3.35 TB/s for the H100 SXM, so the 16.1 GB bf16 model has an upper bound of about 209 tokens a second for a single sequence, the same model at 8 bits about 417, and at 4 bits with group scales (about 4.14 GB) about 809. Those are ceilings, not measurements: real kernels, the KV cache and overheads come on top.

Here is what that capacity looks like on a 24 GB card, with 2 GB set aside for activations and the CUDA context (an assumption), and a bf16 KV cache of 128 KiB per token for the 8B model.

"""What fits on one 24 GB GPU: weights at several precisions plus KV cache (shapes from the Llama 3 report, Table 3)."""
MODELS = {  # layers, heads, kv_heads, width, ffn, vocab
    "8B":  (32, 32, 8, 4096, 14336, 128256),
    "70B": (80, 64, 8, 8192, 28672, 128256),
}
def params(L, H, KV, D, F, V):
    hd = D // H
    attn = 2 * D * D + 2 * D * KV * hd
    return L * (attn + 3 * D * F + 2 * D) + 2 * V * D + D      # untied embedding and output head
FORMATS = {"bf16": 16, "fp8 / int8": 8, "int4, group 128": 4 + 16 / 128, "int3, group 128": 3 + 16 / 128}
GPU, OVERHEAD, CTX = 24e9, 2e9, 8192
print(f"GPU 24 GB, {OVERHEAD/1e9:.0f} GB assumed overhead, KV cache in bf16 at {CTX} tokens")
for name, shp in MODELS.items():
    L, H, KV, D, F, V = shp
    n = params(*shp)
    kv_tok = 2 * L * KV * (D // H) * 2
    print(f"\nLlama 3 {name}: {n/1e9:.2f} B parameters, KV cache {kv_tok/1024:.0f} KiB/token = {kv_tok*CTX/2**30:.2f} GiB per {CTX}-token sequence")
    for fname, bits in FORMATS.items():
        w = n * bits / 8
        room = GPU - OVERHEAD - w
        seqs = int(room // (kv_tok * CTX)) if room > 0 else 0
        print(f"  {fname:<18}{w/1e9:>7.1f} GB weights  ->  {'does not fit' if room <= 0 else f'{seqs} sequences of {CTX} tokens'}")

Read the numbers carefully. The 8B model fits at bf16 but leaves room for only five 8,192-token sequences. At 4 bits it holds sixteen, a threefold gain in concurrency from the same card. Going from 4 bits to 3 bits adds almost nothing, because the KV cache, not the weights, is now the main user of memory. And the 70B model does not fit on 24 GB at any of these precisions: 4-bit weights alone need 36 GB. Quantisation does not repeal arithmetic; it moves the line.

How a number becomes a few bits

Start with the simplest scheme, which is also the one in most production use. Take a group of real-valued weights. Find the largest magnitude, call it m. Choose a scale s so that m lands on the largest integer the format allows. Divide every weight by s and round to the nearest integer. To use the weight later, multiply the integer back by s (this is dequantisation). For a signed 4-bit integer the range is −8 to 7, and the symmetric scheme uses −7 to 7 for the scale, so s = m / 7.

Plug in numbers. Six made-up weights through symmetric int4 with one shared scale, printing each step.

The idea

  1. s ← max|w| / 7
  2. q ← round(w / s); w_hat ← q × s; error ← w_hat − w
  3. check: the worst error is at most s / 2
"""Symmetric absmax quantisation to int4, by hand, on six weights."""

WEIGHTS = [0.12, -0.50, 0.03, 0.31, -0.08, 0.44]   # made-up weights
Q_MAX = 7                                 # int4 symmetric uses -7 to 7

# ── 1. Scale: the largest magnitude lands on the largest integer ─────────
m = max(abs(w) for w in WEIGHTS)
s = m / Q_MAX                             # s = max|w| / q_max
print(f"max|w| = {m:.2f}   scale s = {s:.4f}")
print()

# ── 2. Quantise, then dequantise, and look at the damage ─────────────────
print("   w      w/s   q    w_hat    error")
worst = 0.0
for w in WEIGHTS:
    q = round(w / s)                      # q = round(w / s)
    w_hat = q * s                         # w_hat = q x s
    err = w_hat - w
    worst = max(worst, abs(err))
    print(f"{w:+6.2f} {w / s:+7.2f} {q:+3d}  {w_hat:+7.4f} {err:+8.4f}")

# ── 3. The error can never exceed half a step ────────────────────────────
print()
print(f"worst error {worst:.4f}   half a step = s / 2 = {s / 2:.4f}")

This is symmetric absmax quantisation. The alternative, asymmetric quantisation, adds a zero point z so the integer range can be placed over any interval: q = round(w/s) + z. It wastes fewer levels when the values are all positive (as the outputs of a ReLU are), at the cost of one more number per group and a slightly more expensive multiply. Weights are close to symmetric around zero, so symmetric is the usual choice for them.

Here are eight weights taken through int4 by hand, then the same procedure applied to a whole matrix.

"""Round-to-nearest quantisation by hand, then three scale granularities."""
import numpy as np
from qlib import quantise, rel

# 1. eight numbers, int4, one scale
w = np.array([0.02, -0.11, 0.07, 0.31, -0.05, 0.00, 0.13, -0.28])
s = np.abs(w).max() / 7
q = np.round(w / s).astype(int)
print(f"scale = {np.abs(w).max()} / 7 = {s:.4f}")
print("integers  :", q.tolist())
print("recovered :", np.round(q * s, 3).tolist())
print("abs error :", np.round(np.abs(q * s - w), 3).tolist())

# 2. a weight matrix where two output rows have a much larger range
rng = np.random.default_rng(0)
W = rng.normal(0, 0.02, (1024, 1024))
W[7] *= 12; W[300] *= 20                          # two 'loud' rows (illustrative)
print("\nrelative weight error ||W - Wq|| / ||W||")
print(f"{'scheme':<28}{'int8':>10}{'int4':>10}")
for name, kw in [("per-tensor", {}), ("per-row (per-channel)", {"axis": 1}), ("group of 128", {"group": 128})]:
    print(f"{name:<28}" + "".join(f"{rel(quantise(W, b, **kw), W):>10.4f}" for b in (8, 4)))

The largest weight, 0.31, becomes 7 and comes back exactly. Every other weight is off by up to half a step, which is 0.022 here. Notice what rounding did to 0.02: it became 0 and the weight vanished. The maximum possible error per weight is s/2, so the whole game is keeping s small, and s is set by the largest number in the group.

The fp8 formats come from Micikevicius et al. (2022), "FP8 Formats for Deep Learning", which defines E4M3 (4 exponent bits and 3 mantissa bits) and E5M2. The difference from int8 is spacing. Integers are spaced evenly across the range; floating-point values are dense near zero and sparse far from it, which matches the bell-shaped distribution of weights and activations better than a uniform grid does.

Granularity: how many numbers share a scale

One scale for a whole weight matrix is the cheapest choice and the worst. The reason is in the sentence above: the scale is set by the largest value, so one large weight coarsens the grid for every other weight sharing its scale. Three choices of how many weights share a scale are in common use.

Per-tensor
One scale for the whole matrix. Cheapest to store and apply, but a single large entry sets the step for millions of small ones.
Per-channel
One scale per output channel, meaning per row of the weight matrix in the layout where each row produces one output number. The dot product for that output then multiplies by a single scale, so it costs almost nothing at run time.
Per-group (or per-block)
One scale for each run of g consecutive weights along a row, with g typically 32, 64 or 128. This is what 4-bit formats use. It adds storage: a 16-bit scale per 128 weights costs 16/128 = 0.125 bit per weight, so "4-bit" is really 4.125 bits (4.25 if a 16-bit zero point is stored as well).

The effect on a real matrix is large. The first script also builds a 1,024 × 1,024 matrix of small random weights in which two rows are given 12 and 20 times the usual spread, then quantises it three ways.

Look at the last table in the output of the first script. At int8 the three schemes are all tolerable (relative error 0.118, 0.008, 0.006), but at int4 the per-tensor error is 0.81, meaning the quantised matrix is mostly noise, while per-channel gives 0.14 and groups of 128 give 0.12. Finer scales matter more as the bit width falls, because there are fewer levels to waste.

Analogy: one ruler for a whole workshop

Imagine measuring every part in a workshop with a ruler marked only in whole centimetres, and a single huge beam forces you to choose a metre stick with marks every 10 cm. Every bolt becomes "0 cm" or "10 cm". Giving each bench its own ruler, marked for the parts on that bench, costs a few extra rulers but keeps every measurement useful.

Where it breaks down: a ruler's marks are fixed once printed, whereas a neural network's mistakes compound: a rounding error in layer 3 changes the inputs to layer 4, which has its own rounding error, and the final answer depends on all of them together.

Outliers: the real difficulty

Weights are the easier half. Their distribution is fairly stable and known in advance, so you can pick scales offline. Activations, the numbers flowing between layers, are harder, because they depend on the input and because transformers develop a few input channels whose values are far larger than the rest. Dettmers, Lewis, Belkada and Zettlemoyer (2022), in "LLM.int8(): 8-bit Matrix Multiplication for Transformers at Scale", describe these outlier features: systematic, large-magnitude dimensions that appear in the hidden states of large transformers and that matter for quality. Their fix was a mixed-precision decomposition: do the few outlier dimensions in 16-bit and everything else in int8, and they report halving inference memory with no measurable performance loss for models up to 175B parameters.

Why do outliers hurt activations specifically? A matrix multiplication Y = X·W multiplies each input channel j of the activations X by row j of the weights W. If you want fast integer arithmetic, both sides must be integers, so X needs a scale too. A per-tensor scale for X is set by its largest entry, which is an outlier channel, and every other channel is crushed. You cannot use one scale per input channel, because the integer matrix multiply sums over channels and the scales would have to be pulled inside the sum, destroying the integer kernel.

Xiao and colleagues (2022), "SmoothQuant: Accurate and Efficient Post-Training Quantization for Large Language Models" (ICML 2023), used a mathematically equivalent rewrite. Divide input channel j of X by a factor sj and multiply row j of W by the same factor. The product is unchanged, but the outlier has been moved from the activations into the weights, where per-channel scales can absorb it. In the paper's words, it migrates the quantisation difficulty from activations to weights offline.

The script below recreates the situation: two activation channels 40 times larger than the rest (an assumed, illustrative size), and measures the relative error of the output Y.

"""Activation outliers, SmoothQuant-style rescaling, and AWQ-style scaling for 4-bit weights."""
import numpy as np
from qlib import quantise, rel

rng = np.random.default_rng(1)
T, C, D = 256, 512, 512                           # tokens, input width, output width
X = rng.normal(0, 1, (T, C))
X[:, [11, 301]] *= 40                             # two outlier channels, 40x larger (assumed, mimics the pattern in LLM.int8())
W = rng.normal(0, 0.03, (C, D))
Y = X @ W

# A. W8A8: quantise activations per tensor, weights per output channel
Xq = quantise(X, 8)
Wq = quantise(W.T, 8, axis=1).T
print(f"A. int8 weights + int8 activations, per-tensor activation scale: output error {rel(Xq @ Wq, Y):.4f}")
# per-token scales (one per row of X) help less when the outlier is in every row
Xt = quantise(X, 8, axis=1)
print(f"   same, one activation scale per token                      : output error {rel(Xt @ Wq, Y):.4f}")

# B. SmoothQuant: divide channel j of X by s_j, multiply row j of W by s_j (exactly equivalent)
alpha = 0.5
s = np.abs(X).max(axis=0) ** alpha / np.abs(W).max(axis=1) ** (1 - alpha)
Xs, Ws = X / s, W * s[:, None]
assert np.allclose(Xs @ Ws, Y)
Y8 = quantise(Xs, 8) @ quantise(Ws.T, 8, axis=1).T
print(f"B. after SmoothQuant rescaling (alpha=0.5)                   : output error {rel(Y8, Y):.4f}")

# C. 4-bit weight-only, group 128: RTN versus AWQ-style scaling by activation magnitude
Wr = quantise(W.T, 4, group=128).T
print(f"C. int4 weights (group 128), round to nearest                : output error {rel(X @ Wr, Y):.4f}")
act = np.abs(X).mean(axis=0)
best = None
for a in np.linspace(0, 1, 11):
    s = act ** a
    s = s / np.sqrt(s.max() * s.min())
    Wa = quantise((W * s[:, None]).T, 4, group=128).T / s[:, None]
    e = rel(X @ Wa, Y)
    if best is None or e < best[1]: best = (a, e)
    if a in (0.0, 0.5, 1.0): print(f"   AWQ-style scale, exponent {a:.1f}: output error {e:.4f}")
print(f"   best exponent on the grid = {best[0]:.1f}, error {best[1]:.4f}")

In part A, with int8 on both sides and a single activation scale, the output is off by 12%. Giving each token its own activation scale helps (4.3%) but cannot separate the outlier channels from the others within a token. After the SmoothQuant-style rescaling, part B, the error falls to 2.1%. The factor used is sj = max|Xj|α / max|Wj|1−α with α = 0.5, the middle setting the paper describes for balancing the two sides.

Common misconception

"A quantised model is the same model, just smaller." It is a different function that approximates the original, and the approximation is uneven. Average error can be small while a rare, important behaviour (a long arithmetic chain, a rarely used language, a tool-call format) degrades sharply. The error is also not guaranteed to be monotone in bit width across tasks. You get the model you measured, not the model you started with.

Weight-only 4-bit: GPTQ and AWQ

At 4 bits, plain round-to-nearest (RTN) with group scales is often noticeably worse than the original, and the cheapest remedy is to quantise cleverly using a small calibration set: a few hundred text snippets run through the model to see what its activations look like. Two methods dominate weight-only quantisation. In weight-only schemes the activations stay in 16-bit and the weights are dequantised on the fly inside the kernel, the format called W4A16 (4-bit weights, 16-bit activations).

GPTQ: round, then repair the damage

Frantar, Ashkboos, Hoefler and Alistarh (2022), in "GPTQ: Accurate Post-Training Quantization for Generative Pre-trained Transformers", ask a sharper question than "which grid point is nearest?". For one layer with weights W and calibration inputs X, the quantity that matters is the layer's output, so they minimise the squared output error ||WX − ŴX||2 rather than the weight error. This is a classic problem with an approximate second-order solution (the Optimal Brain Surgeon lineage): quantise one weight, then adjust the not-yet-quantised weights in the same row to compensate for the error just introduced, using the Hessian of the layer's loss, which for this objective is proportional to XXT. The paper reports quantising GPT models with 175 billion parameters in about four GPU hours down to 3 or 4 bits with little accuracy loss.

The intuition: when you round a weight up, nudge its neighbours down so the dot product with typical inputs stays about the same. Inputs that are often large (outlier channels) get rounded more carefully, because the Hessian weights them more heavily.

AWQ: protect the weights that matter

Lin and colleagues (2023), "AWQ: Activation-aware Weight Quantization for LLM Compression and Acceleration", start from the observation that not all weights are equally important: a small fraction of weight channels, identified by the size of the activations that multiply them, account for most of the output error. The obvious fix, keeping those channels in 16 bits, produces a mixed-precision format that GPUs run badly. AWQ instead scales the salient channels up before quantising and scales the activation down to compensate, using the same equivalence as SmoothQuant but applied to protect 4-bit weights. Because the group scale is set by the group's maximum, multiplying one weight by s > 1 does not change the group's grid much, but it reduces that weight's relative rounding error by about a factor of s.

Go deeper why scaling a weight up reduces its error

Let a group have scale Δ = max|w| / 7. Round-to-nearest adds an error to each weight that is roughly uniform in [−Δ/2, Δ/2], whatever the weight's size. Now take input channel j, with activation value x and weight w, contributing xw to the output. The quantised contribution is x(w + ε) with ε the rounding error, so the output error from this channel is xε, of typical size |x|Δ/√12.

Replace w by sw and x by x/s. If sw does not raise the group maximum, Δ is unchanged. The rounding error ε on sw is still of size Δ/√12, but after dividing the activation by s the output error becomes (x/s)ε, which is s times smaller. So channels with large |x| are the best ones to scale up. The cost: if s is large enough to raise the group maximum, Δ grows for every other weight in the group. AWQ therefore searches a single exponent α in sj = (mean activationj)α over a grid, scoring each candidate by output error on the calibration data.

The second half of the script above (part C) does exactly that search on the toy problem, with the same two loud channels. Plain RTN at int4 with groups of 128 gives an output error of 11.9%. An exponent of 0.5 gives 7.7%, an exponent of 1.0 overshoots to 21.4% because the scaled weights now raise the group maximum, and the best value on the grid, 0.3, gives 5.8%. The shape of that curve, falling and then rising, is the whole method in miniature. Real AWQ also keeps no weights in 16 bits and does no backpropagation; it needs only the activation statistics.

Where the speed comes from

Smaller weights are not automatically faster, and it helps to separate the two phases from chapter 18.

  • Decode at small batch size is memory-bound. The weight bytes read per step fall by four times at 4 bits, so the step is faster, provided the kernel dequantises inside the matrix multiply without writing a bf16 copy back to memory. A fused dequantise-and-multiply kernel does that; a naive one does not, and can be slower than bf16.
  • Prefill and large-batch decode are compute-bound. Reading fewer weight bytes barely helps; what helps is doing the arithmetic on cheaper units. W4A16 still multiplies in 16 bits, so it gains little here. W8A8 (int8 or fp8 for both operands) uses the 8-bit tensor cores, which NVIDIA rates at twice the bf16 rate on the H100 (the datasheet lists 3,958 for fp8 and 1,979 for bf16 with sparsity; the dense figures are half of each, so the 2:1 ratio holds).

That explains the usual pairing. For a low-traffic deployment dominated by decode (a single user, an on-device model, a modest self-hosted endpoint), 4-bit weight-only is the strongest option. For a busy server with large batches and long prompts, fp8 or int8 weights and activations are the better fit, because the system is compute-bound for much of its time and 8-bit units double the arithmetic rate. Chapter 22 puts prices on the difference.

Quantising the KV cache

Once weights are small, the KV cache dominates memory (see the 3-bit row of the table above). The cache can be stored in fp8 or int8, halving its size, with an extra scale per head or per token. The error behaves differently from weight error: it enters through attention scores, so it is worth testing on long-context tasks specifically, where many cached entries contribute.

State of play, October 2026

Block-scaled 4-bit floating-point formats are now a hardware feature, not just a research idea. MXFP4 is an Open Compute Project microscaling format in which 32 values share an 8-bit power-of-two scale. NVFP4, NVIDIA's format for its Blackwell GPUs, uses 16-value blocks with an fp8 scale, which one preprint reports gives lower error than MXFP4 at about 4.5 bits per value instead of 4.25 (vendor-adjacent sources; independent comparisons are still sparse). In the open-source tooling, GGUF (llama.cpp) is the common format for laptops and CPUs, while GPTQ and AWQ checkpoints are widely served from vLLM and similar engines. Format names, kernel support and which GPU generation supports which format change quickly: check the engine's documentation before choosing.

Measuring the damage

A quantised model should never ship on the strength of "it still sounds fluent". Three measurements, in order of cheapness, give a fair picture. The script below uses a small random network as a stand-in for a language model: its output is a probability distribution over 500 tokens, so the same metrics apply.

Perplexity
The exponential of the average negative log-probability the model gives to held-out text (A2 chapter 14). Cheap and standard, but it averages over all tokens, so it understates damage to rare, high-stakes ones.
KL divergence to the original
How far the quantised model's next-token distribution is from the full-precision one, averaged over positions. It needs no labels and compares the two models directly, which makes it the most sensitive of the three.
Agreement (flip rate)
How often the most likely next token is the same in both models. Greedy generation can diverge after a single flip, so low agreement predicts different outputs even if perplexity looks fine.
"""Measuring quantisation damage on a small random 'language model': next-token distributions before and after."""
import numpy as np
from qlib import quantise

rng = np.random.default_rng(3)
C, F, V, N = 256, 1024, 500, 4000                  # width, hidden, vocabulary, test positions
W1 = rng.normal(0, 1 / np.sqrt(C), (C, F)); W1[:, rng.choice(F, 6, replace=False)] *= 8   # a few loud hidden units
W2 = rng.normal(0, 1 / np.sqrt(F), (F, V)) * 4.0
X = rng.normal(0, 1, (N, C))

def forward(W1, W2, X):
    h = np.maximum(X @ W1, 0)
    z = h @ W2
    z = z - z.max(1, keepdims=True)
    return z - np.log(np.exp(z).sum(1, keepdims=True))     # log-probabilities

ref = forward(W1, W2, X); p = np.exp(ref)
y = np.array([rng.choice(V, p=pi / pi.sum()) for pi in p])   # 'true' next tokens drawn from the full-precision model
nll = lambda lp: -lp[np.arange(N), y].mean()
print(f"full precision: perplexity on its own samples = {np.exp(nll(ref)):.2f}")
print(f"{'scheme':<26}{'bits/wt':>8}{'KL (nats)':>11}{'top-1 agree':>13}{'perplexity':>12}")
def row(name, bits, q):
    lp = forward(q(W1), q(W2), X)
    kl = (p * (ref - lp)).sum(1).mean()
    agree = (lp.argmax(1) == ref.argmax(1)).mean()
    print(f"{name:<26}{bits:>8.2f}{kl:>11.5f}{agree:>13.1%}{np.exp(nll(lp)):>12.2f}")
qt = lambda b, **kw: (lambda W: quantise(W.T, b, **kw).T)      # quantise along the input dimension of each output column
row("int8 per-channel", 8, qt(8, axis=1))
row("int4 per-tensor", 4, lambda W: quantise(W, 4))
row("int4 per-channel", 4, qt(4, axis=1))
row("int4 group 128", 4 + 16 / 128, qt(4, group=128))
row("int3 group 128", 3 + 16 / 128, qt(3, group=128))
row("int2 group 128", 2 + 16 / 128, qt(2, group=128))

Three lessons fall out of this table. First, int8 per-channel is nearly free (KL 0.0005, 98% agreement). Second, the same 4 bits with per-tensor scales is a disaster (18% agreement) while per-channel or group scales keep 70 to 74%, the same lesson as the matrix experiment. Third, perplexity is the gentlest metric: int4 with groups moves perplexity from 15.4 to 17.5 (a 13% rise), while the top token changes in 26% of positions. A quantised model can look acceptable on perplexity and still behave differently in generation.

For a real model, add task-level evaluation (chapter 23): run the benchmarks and the product-specific tests you care about on both versions, with the same prompts, and compare with confidence intervals. Include the following, because they are where quantisation damage tends to show first.

  • Long-context and multi-step tasks, where small errors accumulate across many tokens.
  • Structured output: JSON validity and tool-call formats, which fail when a single token flips.
  • Less common languages and domains, which are underrepresented in the calibration data.
  • Safety and refusal behaviour, which may shift in ways general benchmarks do not show (A6 covers how to test for it).

Choose the calibration set to resemble deployment traffic. GPTQ and AWQ both fit to it, and a set of generic web text can leave a code-heavy or multilingual deployment under-served.

Systems connection

Everything above is the memory hierarchy at work: the gain from 4-bit weights is a gain in bytes moved from the slowest level (HBM) to the compute units, and the roofline view in Parallelism, SIMD & GPUs says when bytes, not arithmetic, set the speed. Choosing a calibration set and checking an approximation against a reference is the same discipline as validating any lossy optimisation, such as a cache or an approximate index: define the error you can live with before you measure it, then roll it out gradually.

Key takeaways

  • Quantisation maps weights to a few allowed values with a scale; the step size is set by the largest number sharing that scale, so granularity (per-tensor, per-channel, per-group) decides the damage.
  • Group scales make "4-bit" about 4.125 bits per weight; the saving is real but not exactly 4x.
  • Outlier channels in activations are the central difficulty. SmoothQuant moves them into the weights; LLM.int8() handles them in 16-bit.
  • GPTQ minimises layer-output error by compensating each rounding with the remaining weights; AWQ protects activation-salient channels by scaling them. Both use calibration data.
  • Weight-only 4-bit speeds up memory-bound decode; 8-bit weights and activations speed up compute-bound prefill and big batches.
  • Measure the damage with KL divergence, agreement and task evaluations on your own workload; perplexity alone understates it.

Check your understanding

A weight matrix is quantised to int4 with one scale for the whole tensor and the result is mostly noise. A colleague proposes 128-weight groups. What is the main reason this helps?

  1. Groups give each weight more bits, so each is represented more precisely
  2. The scale of each group is set by its own largest value, so an outlier only coarsens the weights in its group
  3. Groups let the GPU skip multiplying weights that round to zero
  4. Groups remove the need to round at all
The number of bits per weight is unchanged (it even rises slightly because of the scales). What changes is how many weights share a step size set by the largest of them. Option 0 is the tempting wrong answer: bits per weight are still four. Option 2 is not how dense kernels work.

An 8B model in bf16 has weights of 16.1 GB. At 4 bits with a 16-bit scale per group of 128, which weight size is closest?

  1. 2.0 GB
  2. 3.0 GB
  3. 4.0 GB exactly
  4. 4.1 GB
4 + 16/128 = 4.125 bits per weight, so 8.03 billion × 4.125 / 8 is about 4.14 GB. Four exactly ignores the scales. Embeddings and norms that are often kept in higher precision would add a little more in practice.

Why can SmoothQuant divide an activation channel by s and multiply the matching weight row by s without changing the model?

  1. The product X·W sums xjwj over channels, and (xj/s)(s wj) equals xjwj
  2. The model is retrained afterwards to absorb the change
  3. Dividing by s reduces the number of outliers in the weights
  4. Activations are always rescaled by the next layer's normalisation
It is an exact algebraic identity in full precision; only the quantisation error changes, because the large value now lives where per-channel scales can handle it. No retraining is involved, which is why the method is called post-training.

You serve a quantised 8B model to many users with large batches and long prompts, and measure that most time is spent in compute-bound matrix multiplies. Which change is most likely to raise throughput?

  1. Moving from 4-bit to 3-bit weights while keeping 16-bit activations
  2. Quantising only the embedding table
  3. Using fp8 or int8 for both weights and activations so the 8-bit tensor cores are used
  4. Increasing the group size from 128 to 1,024
When compute-bound, bytes read are not the limit, so smaller weights alone do little (option 0, and option 3 only saves scale storage). Using 8-bit arithmetic raises the arithmetic rate, about twice bf16 on the H100 per the datasheet ratio.

A 4-bit model scores within 1% of the original on perplexity. Which further check is most likely to reveal damage that perplexity hides?

  1. Re-measuring perplexity on the same text with a different batch size
  2. Comparing next-token agreement and KL divergence to the original, and running your task suite including structured output
  3. Checking that the file is smaller
  4. Measuring tokens per second
Perplexity averages over tokens and is the gentlest metric; in the chapter's experiment a 13% perplexity rise came with the top token changing at about a quarter of positions. Speed and file size say nothing about quality.

In the AWQ-style search, the error first falls and then rises as the exponent α goes from 0 to 1. What explains the rise?

  1. The activations become too small to represent
  2. The calibration data runs out
  3. Large scale factors raise the group maximum, so the step size grows for all the other weights in the group
  4. Rounding becomes biased towards zero
Scaling a salient weight up protects it, but if the scaled value exceeds the group's old maximum the shared step grows and the ordinary weights get coarser. The best exponent balances the two effects.

Serving Engines

A model that is fast for one user can be slow and wasteful for a thousand. Serving engines such as vLLM and SGLang close that gap with three ideas: schedule work one token at a time (continuous batching), manage the KV cache like virtual memory (paged attention), and never compute the same prefix twice (prefix caching). This chapter builds each from the problem it solves.

Why this matters

Most teams that run their own models do not write a serving system; they configure one. The settings that matter (how many sequences to run at once, how much memory to give the cache, how big a prompt chunk may be) only make sense if you know what the scheduler is doing. This chapter explains the machinery behind those settings, so that when latency spikes at high load, or throughput is half what the hardware should allow, you can say which mechanism is responsible. It builds directly on chapter 18 (the KV cache and the memory-bound decode loop) and feeds chapter 22 (what a token costs).

Serving is a scheduling problem

Chapter 18 established two facts. Generating each token requires a forward pass that reads all the weights from HBM, so a single sequence leaves the arithmetic units mostly idle. And each running sequence owns a KV cache that grows by one entry per token. Both facts point at the same remedy: run many sequences in the same forward pass, so the cost of reading the weights is shared. The larger the batch, the more tokens per second per GPU, until the arithmetic units are busy or memory runs out.

The hard part is that requests do not come in neat batches. They arrive at random times, prompts have different lengths, and nobody knows in advance how many tokens an answer will take: one request ends after 5 tokens, another after 800. A serving engine is therefore a scheduler with three jobs.

  1. Decide who runs in each step. Which waiting requests join the batch, which running ones continue, and how much prompt work to mix in with the decoding.
  2. Decide where the cache lives. Every running request needs KV memory that grows unpredictably; the engine must allocate it without wasting most of the GPU.
  3. Avoid repeated work. Many requests start with the same text (a system prompt, a document, a chat history); recomputing it each time wastes compute and delays the first token.

Three numbers describe how well it does. Time to first token (TTFT) is how long a user waits before the answer begins, dominated by queueing and prefill. Inter-token latency (ITL, also called time per output token) is the gap between consecutive tokens once streaming starts. Throughput is total tokens per second across all users. A good engine raises throughput without letting the other two grow past what the product tolerates: the same trade-off as in any queueing system (queueing theory), with the twist that here the unit of work is a single token and the "server" processes many at once.

Continuous batching

The problem with static batches

The textbook way to batch is static: collect B requests, run them together until every one has finished, return the results, then collect the next B. For a model that produces a fixed-size output (an image classifier) this is ideal. For text generation it is wasteful, because the batch runs as long as its longest member. A request that needed 20 tokens sits in its slot, producing nothing, while a neighbour generates 500. Worse, nothing is returned until the whole batch ends, so short requests wait for long ones.

Yu and colleagues (2022), in "Orca: A Distributed Serving System for Transformer-Based Generative Models" (OSDI 2022), named the fix iteration-level scheduling: make the scheduling decision after every single decode iteration, not after every request. The batch is just whoever is running right now. When a request emits its end-of-sequence token, it leaves immediately and its answer is returned; a waiting request takes the freed slot on the very next step. This is now called continuous batching (or in-flight batching).

The simulation below makes the difference concrete. It draws 400 requests with a long-tailed output length (mean about 100 tokens, a few near 500), gives the GPU 16 batch slots, and assumes each decode step takes the same time whatever the number of running sequences. That assumption holds roughly while decode is memory-bound; it ignores prefill, which later sections add back.

"""Static versus continuous batching for 400 requests with random output lengths.
One decode step produces one token for every running request; step time is taken as constant (memory-bound decode)."""
import random

rng = random.Random(7)
N, SLOTS = 400, 16
lengths = [max(5, min(500, int(rng.lognormvariate(4.3, 0.9)))) for _ in range(N)]   # output tokens per request
print(f"{N} requests, output length mean {sum(lengths)/N:.0f}, median {sorted(lengths)[N//2]}, max {max(lengths)}; {SLOTS} batch slots")

def static(lengths):
    t, done, useful = 0, [], 0
    for i in range(0, len(lengths), SLOTS):
        batch = lengths[i:i + SLOTS]
        t0 = t
        t += max(batch)                          # the batch runs until its longest request finishes
        done += [t] * len(batch)                 # every request is returned only when the batch ends
        useful += sum(batch)
    return t, done, useful

def continuous(lengths):
    t, queue, running, done, useful = 0, list(lengths), [], [], 0
    while queue or running:
        while queue and len(running) < SLOTS:    # refill free slots at every step
            running.append(queue.pop(0))
        t += 1
        useful += len(running)
        running = [r - 1 for r in running]
        done += [t] * sum(1 for r in running if r == 0)
        running = [r for r in running if r > 0]
    return t, done, useful

print(f"{'policy':<12}{'steps':>7}{'tokens/step':>13}{'slot use':>10}{'mean latency':>14}{'p95 latency':>13}")
for name, f in (("static", static), ("continuous", continuous)):
    t, done, useful = f(lengths)
    d = sorted(done)
    print(f"{name:<12}{t:>7}{useful/t:>13.2f}{useful/(t*SLOTS):>10.0%}{sum(d)/N:>14.0f}{d[int(.95*N)]:>13}")
400 requests, output length mean 100, median 68, max 500; 16 batch slots
policy        steps  tokens/step  slot use  mean latency  p95 latency
static         8644         4.61       29%          4336         8512
continuous     2674        14.90       93%          1239         2404

Static batching keeps the slots busy only 29% of the time and finishes in 8,644 steps. Continuous batching fills the slots 93% of the time and finishes in 2,674 steps: 3.2 times the throughput from the same GPU, and a mean time to finish of 1,239 steps instead of 4,336. (Every request is queued at step 0 here, so the latencies include waiting; the ratio is what matters.) The gain depends on how variable the lengths are. If every request produced exactly 100 tokens the two policies would tie; the longer the tail, the more static batching wastes.

Continuous batching

Analogy: the bus and the ski lift

Static batching is a bus that leaves only when full and does not let anyone off until the last passenger's stop. Continuous batching is a ski lift: a chair leaves every few seconds, people get on whenever a seat is free and get off at their own stop, and the lift never waits for the slowest skier.

Where it breaks down: a ski lift's seats are interchangeable, but each LLM request brings its own memory (the KV cache) that stays on the GPU for as long as the request runs. A free slot is only useful if there is also free cache memory for the newcomer, which is the subject of the next section.

What a step contains

With iteration-level scheduling, the batch in one step is a mixture: some requests are in their prefill (processing a whole prompt, thousands of tokens), others are decoding one token each. Orca's second idea, selective batching, handles the awkwardness of running such a mixture through one pass. Most of a transformer's operations (the linear layers and the normalisations) treat each token independently, so all tokens in the step, from all requests, can be flattened into one matrix and processed together. Attention is the exception: each token attends only to its own request's cache, so attention is computed per request. Modern engines work the same way: the model sees a flat list of tokens plus metadata saying which request each belongs to and where its cache blocks are.

Paged attention

Why memory, not slots, is the limit

Continuous batching can only fill a slot if the KV cache for a new request fits. Chapter 18 computed the cache per token: 128 KiB for the Llama 3 8B shape. The difficulty is that a request's final length is unknown, and the early engines stored each sequence's cache in one contiguous slab of memory. To be safe, they reserved room for the maximum possible length when the request arrived.

Kwon and colleagues (2023), in "Efficient Memory Management for Large Language Model Serving with PagedAttention" (SOSP 2023), measured what this wasted. They report that in existing systems only 20.4% to 38.2% of the KV cache memory held actual token states. The rest was lost three ways: reservation (space held for tokens not yet generated, and that may never be), internal fragmentation (the part of a reservation never used because the sequence ended early), and external fragmentation (gaps between slabs too small for any new request).

The fix borrows from operating systems. A process thinks it has a large contiguous address space, but the OS stores it in fixed-size pages scattered through physical memory, with a page table translating between them (virtual memory). PagedAttention does the same for the KV cache. The cache is divided into fixed-size blocks of tokens (16 by default in vLLM, per the paper). A sequence's cache is a list of block numbers, its block table, and the attention kernel is written to follow the table, gathering keys and values from wherever the blocks happen to be. Blocks are allocated one at a time as the sequence grows and returned to a free list when it ends.

Blocks, tables and sharing

Step through what the block manager does for two requests that begin with the same system prompt.

Step through

Block tables: how two requests share GPU memory

  1. A arrives with a 40-token prompt. It needs three 16-token blocks. The allocator hands out whichever physical blocks are free (P1, P3, P0); nothing requires them to be adjacent. The block table maps logical block numbers to physical ones, like a page table. The last block is only half full.
  2. A decodes nine more tokens. The third block fills up and the next token needs a fourth, so one more block (P6) is taken. Memory is allocated one block at a time as the sequence grows, so at most 15 slots are ever wasted per sequence, instead of a whole maximum-length reservation.
  3. B arrives with the same first 32 tokens. A hash of each full block (chained with the previous block's hash) finds that P1 and P3 already hold exactly this prefix. B's table points at them and their reference count becomes 2. Only B's own 12 extra tokens need a new block (P4). Nothing was recomputed or copied for the shared 32 tokens.
  4. A finishes. A's private blocks (P0 and P6) go back to the free list. The shared blocks stay because B still references them: their count drops to 1.
  5. B finishes. P4 is freed. P1 and P3 now have no users, but the engine does not clear them: they stay as cached prefix blocks (dashed) until memory is needed, when the least recently used are evicted first. The next request with this prompt reuses them for free.

Two further properties follow from the table. First, blocks can be shared: when several sequences need the same content (the n outputs of a request that asks for n samples, the branches of beam search, or any common prefix), their tables point at the same physical blocks, with a reference count saying how many sequences use each. Second, if one of them must write into a shared block (the next token lands in a partly filled block that others also hold), the engine uses copy-on-write: allocate a new block, copy the contents, drop the reference to the old one, then write. The paper reports memory savings from sharing of 6.1% to 30.5% for parallel sampling and 37.6% to 66.3% for beam search, depending on the dataset.

The cost of paging is that attention must follow the table: a custom kernel gathers from scattered blocks. The paper reports that vLLM, built on this, improves throughput by 2 to 4 times over systems such as FasterTransformer and Orca at similar latency, with larger gains for longer sequences and larger models. (Treat the figures as the authors' own measurements on 2023 hardware and models; the direction has held up.)

What the memory policy is worth

The next script gives two policies the same workload and the same cache budget: 20,000 tokens of KV cache (about 2.4 GiB for the 8B shape) and 300 requests with prompts averaging 320 tokens and outputs averaging 210. One policy reserves the maximum length of 2,048 tokens per request. The other allocates 16-token blocks on demand. When a growing sequence finds no free block, the paged policy preempts the most recently admitted sequence and later restarts it from scratch (recomputation, one of the two policies the paper describes; the other is swapping the blocks to CPU memory). Lost decode work is charged as extra steps; the recomputed prompt processing is not charged, which flatters the paged result slightly.

"""KV cache memory policies under the same workload: reserve the maximum length, versus allocate 16-token blocks on demand.
Capacity is counted in tokens of KV cache (one 8B-model token is 128 KiB, so 20,000 tokens is about 2.4 GiB: an illustrative budget)."""
import random

CAPACITY, BLOCK, MAXLEN, N = 20_000, 16, 2048, 300
rng = random.Random(11)
reqs = []
for _ in range(N):
    p = max(20, min(1500, int(rng.lognormvariate(5.5, 0.8))))       # prompt tokens
    o = max(10, min(MAXLEN - p, int(rng.lognormvariate(5.0, 0.9)))) # output tokens
    reqs.append((p, o))
print(f"{N} requests: mean prompt {sum(p for p,_ in reqs)/N:.0f}, mean output {sum(o for _,o in reqs)/N:.0f}, reservation {MAXLEN} tokens, capacity {CAPACITY} tokens")

def run(policy):
    waiting, running, steps, tokens = list(range(N)), {}, 0, 0
    used_sum = alloc_sum = batch_sum = preempt = 0
    blocks_free = CAPACITY // BLOCK
    def need_blocks(n): return -(-n // BLOCK)
    while waiting or running:
        # admit (first come first served)
        while waiting:
            i = waiting[0]; p, o = reqs[i]
            if policy == "reserve":
                cost = need_blocks(MAXLEN)               # whole maximum length up front
            else:
                cost = need_blocks(p + 1)                # just the prompt (plus the first token)
            if cost > blocks_free: break
            blocks_free -= cost; waiting.pop(0)
            running[i] = {"len": p, "gen": 0, "blocks": cost}
        # one decode step: every running sequence adds one token
        for i in list(running):
            if i not in running: continue                # preempted earlier in this step
            s = running[i]
            if need_blocks(s["len"] + 1) > s["blocks"]:
                if blocks_free == 0:                     # out of memory: preempt the newest sequence, recompute later
                    victim = max(running)
                    blocks_free += running[victim]["blocks"]; del running[victim]
                    waiting.insert(0, victim); preempt += 1
                    if victim == i: continue
                blocks_free -= 1; s["blocks"] += 1
            s["len"] += 1; s["gen"] += 1
        steps += 1
        used_sum += sum(s["len"] for s in running.values())
        alloc_sum += sum(s["blocks"] for s in running.values()) * BLOCK
        batch_sum += len(running)
        for i in [i for i, s in running.items() if s["gen"] >= reqs[i][1]]:
            tokens += reqs[i][1]
            blocks_free += running[i]["blocks"]; del running[i]
    return steps, tokens, batch_sum / steps, used_sum / alloc_sum, preempt

print(f"{'policy':<16}{'steps':>7}{'mean batch':>12}{'tokens/step':>13}{'allocated memory holding tokens':>34}{'preemptions':>13}")
for name in ("reserve", "paged"):
    steps, tokens, batch, util, pre = run(name)
    print(f"{name:<16}{steps:>7}{batch:>12.1f}{tokens/steps:>13.1f}{util:>34.0%}{pre:>13}")
300 requests: mean prompt 320, mean output 210, reservation 2048 tokens, capacity 20000 tokens
policy            steps  mean batch  tokens/step   allocated memory holding tokens  preemptions
reserve            7145         8.8          8.8                               25%            0
paged              2233        28.7         28.2                               99%          188

With reservation, only 25% of allocated memory holds real tokens, the mean batch is 8.8 and the whole workload takes 7,145 steps. With blocks, 99% of allocated memory holds tokens, the mean batch is 28.7, and it takes 2,233 steps: a 3.2 times gain, in the same range as the paper's 2 to 4 times though the settings are different. The price is 188 preemptions: with memory this full, growth sometimes cannot be satisfied and someone is evicted. Real engines hold back a margin of free blocks and prefer swapping or recomputation depending on block size (the paper finds block sizes from 16 to 64 perform comparably, and that recomputation overhead never exceeds 20% of swapping's latency).

Common misconception

"Paged attention makes attention itself faster." It does not; the arithmetic is the same and the gather from scattered blocks costs a little. What it changes is how many sequences fit in memory at once, which raises the batch size, and a bigger batch is what raises throughput. If your workload never fills the cache (short prompts, few users), paging gains little.

Prefix caching

Block tables make a third idea cheap. A large share of real prompts begin identically: the system prompt of a product, the tool definitions of an agent, the few-shot examples of a classifier, the long document a user is asking several questions about, the whole history of a conversation resent on every turn. The KV entries for a prefix depend only on the tokens in it (because attention is causal: a token never looks at later ones), so if two requests share a prefix, the cache for it is identical and need not be computed twice.

vLLM's automatic prefix caching hashes each full block. A block's hash combines the hash of the previous block, the tokens in this block, and any extra keys that must separate otherwise-equal prompts (a LoRA adapter id, an image hash, a cache salt for tenant isolation), according to the vLLM design documentation. Chaining the hashes means a block's hash identifies the entire prefix up to and including it. A new request hashes its prompt block by block; for each hash found in the cache it reuses the physical block and skips computing it. Blocks of finished requests are kept rather than cleared and evicted least-recently-used first when memory is needed; the documentation notes that a request's blocks are freed in reverse order so that its last blocks, least likely to be reused, go first. Only full blocks are cached, so the final partial block of a prompt is always recomputed.

The script below builds this from scratch (same chained hash, LRU with deepest-first eviction) and runs 60 chats of 6 turns each against a shared 800-token system prompt, interleaved as real traffic would be, with each turn resending the conversation so far.

"""Automatic prefix caching: KV blocks are keyed by a hash of (previous block hash, this block's tokens), so two prompts
that share a prefix share its blocks. Workload: a shared system prompt, then multi-turn chats that resend their history."""
import random
from collections import OrderedDict

BLOCK = 16
rng = random.Random(5)
def toks(n): return [rng.randrange(50_000) for _ in range(n)]

class PrefixCache:
    def __init__(self, capacity_blocks):
        self.cap, self.lru = capacity_blocks, OrderedDict()
        self.hit_tokens = self.total_tokens = 0
    def process(self, prompt):
        h, hit, chain = 0, True, []
        for i in range(0, len(prompt) - len(prompt) % BLOCK, BLOCK):   # only full blocks are cached
            h = hash((h, tuple(prompt[i:i + BLOCK])))
            chain.append(h)
            if h in self.lru:
                if hit: self.hit_tokens += BLOCK
            else:
                hit = False                                            # first miss: the rest must be computed
                self.lru[h] = True
        for h in reversed(chain):                                      # touch deepest first, so on ties the deepest block is evicted first
            if h in self.lru: self.lru.move_to_end(h)
        while len(self.lru) > self.cap: self.lru.popitem(last=False)   # evict least recently used
        self.total_tokens += len(prompt)

SYSTEM = toks(800)
def workload(n_chats=60, turns=6):
    chats = [SYSTEM + toks(rng.randrange(20, 80)) for _ in range(n_chats)]
    reqs = []
    for t in range(turns):                                  # interleave: every chat sends turn t, then turn t+1 ...
        for c in range(n_chats):
            reqs.append(list(chats[c]))
            chats[c] = chats[c] + toks(rng.randrange(150, 300)) + toks(rng.randrange(20, 80))   # reply + next user message
    return reqs

reqs = workload()
print(f"{len(reqs)} requests, mean prompt {sum(map(len, reqs))/len(reqs):.0f} tokens, shared system prompt 800 tokens")
print(f"{'cache size':>18}{'tokens reused':>16}")
for cap in (0, 50, 500, 3000, 10_000):
    c = PrefixCache(cap)
    for r in reqs: c.process(r)
    print(f"{cap:>8} blocks ({cap*BLOCK:>7} tok){c.hit_tokens/c.total_tokens:>13.0%}")
360 requests, mean prompt 1549 tokens, shared system prompt 800 tokens
        cache size   tokens reused
       0 blocks (      0 tok)           0%
      50 blocks (    800 tok)          52%
     500 blocks (   8000 tok)          52%
    3000 blocks (  48000 tok)          60%
   10000 blocks ( 160000 tok)          84%

The shared system prompt is 52% of the average prompt, and a cache of 50 blocks (exactly the 800 tokens) captures it: that is the first and cheapest win. To reuse conversation histories as well, the cache must hold every active chat's history, since turn t+1 of a chat arrives after the other 59 chats have each sent a turn. At 3,000 blocks reuse reaches 60%, at 10,000 it reaches 84%; the remainder is each turn's genuinely new text. The lesson is about sizing: the cache must be large enough to hold the working set between visits, or the entries are evicted just before they would have been reused. The memory comes out of the same pool as running sequences, so prefix caching competes with batch size.

The radix tree

SGLang (Zheng et al., 2023, "SGLang: Efficient Execution of Structured Language Model Programs") stores the same information differently. RadixAttention keeps the cached prompts and outputs in a radix tree: a tree whose edges are runs of tokens and where two prompts share a path for as long as they share tokens. A new request walks from the root as far as it matches and computes only the remainder. The authors' blog describes LRU eviction applied recursively to leaf nodes, so a node is evicted only after everything below it, and the tree lives on the CPU while the KV tensors stay on the GPU. The paper reports up to 6.4 times higher throughput than leading inference systems on tasks that reuse prefixes heavily, such as multi-call "programs" and agents.

Both designs capture the same effect; the difference is mostly how the lookup is organised (hashes of blocks versus tokens in a tree) and how fine the granularity is. SGLang's tree can match to the exact token, while block hashing can only reuse whole blocks. SGLang also pairs the cache with scheduling that prefers requests with long cache hits, so that related requests run while their shared prefix is still in memory.

Systems connection

Almost every mechanism here is an old one in a new place. The block table is a page table (virtual memory); copy-on-write is how fork shares memory (processes); the scheduler's choice of what runs next is the subject of scheduling; prefix caching with LRU and a working set is the cache design you already know, where the hit rate depends on whether capacity covers the working set. Prefill versus decode inside one step

Chapter 18 explained that the two phases have opposite characters. Prefill processes thousands of prompt tokens at once and is compute-bound; decode processes one token per sequence and is memory-bound. Putting them in the same step creates a problem. A 4,000-token prefill takes much longer than a decode step, and every decoding user must wait for it to finish before receiving their next token. To everyone mid-answer, the arrival of a long prompt looks like a stall.

Chunked prefill

Agrawal and colleagues (2024), in "Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve", split each prefill into near-equal chunks and give each step a token budget: decodes go first (one token each), and the remaining budget is filled with the next chunk of a waiting prompt. They call this stall-free batching, because new requests are added without pausing ongoing decodes. Their reported capacity gains under tail-latency limits include 2.6 times for Mistral-7B on one A100 and up to 3.7 times for Yi-34B on two, compared with vLLM at the time. The vLLM V1 engine writes the same idea into its scheduler: each scheduling decision is a map from request to a number of tokens for this step, without a separate prefill or decode phase, which subsumes chunked prefill and prefix caching.

The script uses an assumed cost model (20 ms fixed per step, 0.05 ms per token processed; the numbers are illustrative, not measured on any GPU) with eight users decoding and a new 4,000-token prompt every second.

"""Why long prompts stall other users' streams, and what chunked prefill changes.
Step time model (ASSUMED, illustrative): 20 ms fixed cost to stream the weights + 0.05 ms per token processed in the step.
8 users are decoding; every 1 s a new 4,000-token prompt arrives."""
FIXED, PER_TOK, DECODERS, PROMPT, GAP = 20.0, 0.05, 8, 4000, 1000.0

def simulate(budget, horizon=20_000.0):
    t, next_arrival, pending, itl, ttft = 0.0, 0.0, [], [], []
    while t < horizon:
        if t >= next_arrival:
            pending.append([PROMPT, next_arrival]); next_arrival += GAP
        tokens = DECODERS                                  # every decoding user advances by one token
        room = budget - tokens if budget else PROMPT       # prefill tokens allowed in this step
        if pending and room > 0:
            take = min(room, pending[0][0]); pending[0][0] -= take; tokens += take
        dt = FIXED + PER_TOK * tokens
        t += dt
        itl.append(dt)                                     # gap between consecutive tokens seen by each decoding user
        if pending and pending[0][0] == 0:
            ttft.append(t - pending[0][1]); pending.pop(0)
    itl.sort()
    return itl[len(itl)//2], itl[int(len(itl)*0.99)], max(itl), sum(ttft)/len(ttft)

print(f"{'policy':<28}{'median ITL':>11}{'p99 ITL':>9}{'worst ITL':>11}{'prompt TTFT':>13}   (ms)")
for name, b in (("whole prompt in one step", 0), ("chunked, 2048 tokens/step", 2048), ("chunked, 512 tokens/step", 512), ("chunked, 128 tokens/step", 128)):
    m, p99, mx, tt = simulate(b)
    print(f"{name:<28}{m:>11.1f}{p99:>9.1f}{mx:>11.1f}{tt:>13.0f}")
policy                       median ITL  p99 ITL  worst ITL  prompt TTFT   (ms)
whole prompt in one step           20.4    220.4      220.4          231
chunked, 2048 tokens/step          20.4    122.4      122.4          251
chunked, 512 tokens/step           20.4     45.6       45.6          373
chunked, 128 tokens/step           26.4     26.4       26.4          904

The table shows the knob. A whole-prompt step stalls every decoding user for 220 ms, and that is the p99 inter-token latency, ten times the median of 20 ms. A budget of 512 tokens per step cuts the worst stall to 46 ms, at the cost of the prompt taking 373 ms to its first token instead of 231 ms. With 128 tokens the stalls nearly vanish (26 ms) but the prompt takes 904 ms. The right budget depends on which latency the product promises: an interactive chat protects inter-token latency, a batch summariser does not care. This is why --max-num-batched-tokens is one of the settings worth understanding.

Disaggregation

A different answer is to stop sharing GPUs between the phases. Zhong and colleagues (2024), in "DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving" (OSDI 2024), run prefill and decode on separate GPUs, so they no longer interfere, and tune the parallelism of each to its own latency target. They report serving 7.4 times more requests, or meeting 12.6 times tighter latency targets, than state-of-the-art systems on their workloads. The price is moving each request's KV cache from the prefill GPU to the decode GPU over the interconnect, which is why the approach pays off most when the network is fast and the workload is large enough to keep both pools busy.

Inside the engines

The architecture in the figure above is common to vLLM, SGLang and their relatives. The loop runs once per step.

  1. Collect arrivals. The API server tokenises new requests and hands them to the scheduler's waiting queue.
  2. Schedule. The scheduler orders running requests first, then admits waiting ones while the token budget and free blocks allow. It asks the block manager for blocks, reusing cached ones where hashes match. If a running request needs a block and none is free, it preempts a request (by default the newest) to free its blocks.
  3. Run the step. Workers execute one forward pass over the flattened tokens of all scheduled requests. On multi-GPU models, the layers are split by tensor parallelism (chapter 3) and each step ends with collective communication.
  4. Sample. One new token is chosen per request that finished its prompt (or last chunk) using the request's decoding settings (A2 chapter 15).
  5. Return and retire. New tokens stream to clients; requests that produced an end token or hit their limit release their blocks.

Engineering detail is where much of the speed comes from, because at small batch sizes a step takes only tens of milliseconds and CPU work between steps becomes visible. The vLLM V1 announcement (January 2025) describes isolating a core loop that does only scheduling and model execution, with tokenisation, detokenisation and streaming in separate processes so the CPU work overlaps with GPU execution; a persistent batch that applies per-step diffs instead of rebuilding inputs; and torch.compile with piecewise CUDA graphs. It reports up to 1.7 times higher throughput than the previous engine, attributed mainly to reduced CPU overhead, and turned prefix caching on by default after measuring under 1% throughput loss even at a 0% hit rate. Those are the vendor's own measurements.

The two projects have different emphases. vLLM grew from the memory manager outwards and aims to be a general high-throughput server for many models, quantisation formats and hardware backends. SGLang grew from the programming side: a frontend for multi-call programs (branching, parallel calls, constrained output) and a runtime built around RadixAttention, so it is especially strong where requests share structure, as in agent loops and few-shot pipelines. Both now implement the same core techniques (continuous batching, paged KV, prefix caching, chunked prefill, quantisation, speculative decoding), and each release shifts the benchmark gap, so treat any head-to-head table as a snapshot.

State of play, October 2026

vLLM and SGLang are the two most widely used open-source engines; others exist, including NVIDIA's TensorRT-LLM and Hugging Face's Text Generation Inference, and llama.cpp for CPUs and laptops. Versions move monthly: aggregator sites in October 2026 reported vLLM releases in the 0.2x series, but I could not confirm the current number from the project's own release page, so check github.com/vllm-project/vllm/releases before relying on any flag or default. The behaviour of settings such as chunked prefill and prefix caching differs between versions (the V1 engine enables prefix caching by default, per its announcement). The settings that matter

This is how a deployment is typically started. The command is illustrative and was not run here; flag names are those documented for vLLM at the time of writing and may differ in your version.

$ vllm serve meta-llama/Llama-3.1-8B-Instruct \
    --max-model-len 8192 \
    --gpu-memory-utilization 0.90 \
    --max-num-seqs 128 \
    --max-num-batched-tokens 2048 \
    --enable-prefix-caching
--max-model-len
The longest sequence (prompt plus output) accepted. It bounds the worst case for one request and so how many can be admitted safely.
--gpu-memory-utilization
The fraction of GPU memory the engine may claim. After loading the weights and measuring peak activation memory, whatever remains within this share becomes the pool of KV blocks. Too high risks out-of-memory errors from other processes; too low wastes cache.
--max-num-seqs
The cap on concurrent sequences, the "slots" of the simulation. Higher raises throughput and inter-token latency together.
--max-num-batched-tokens
The token budget per step, which with chunked prefill sets the chunk size and so the trade in the table above.

When it goes wrong

Serving engines fail in characteristic ways, and each traces to a mechanism above.

  • Latency climbs with load. Adding concurrent sequences raises the time per step (more tokens, more KV to read), so inter-token latency rises gradually with batch size, while the waiting queue grows sharply once demand exceeds capacity, the "latency knee" of queueing theory. Admission control and load shedding apply here exactly as in any service (overload).
  • Preemption storms. If the cache is nearly full, sequences are repeatedly evicted and recomputed, and the engine does the same work over and over. The symptoms are rising preemption counters and throughput that falls as load rises. Fix by lowering --max-num-seqs, giving the cache more memory, shortening the maximum context, or quantising the cache.
  • Tail latency from long prompts. One huge prompt can raise everyone's latency if prefill is not chunked or the token budget is large. Watch p99 inter-token latency, not the mean (tail latency).
  • A cold cache after a deploy. A restart empties the prefix cache, so the first minutes are slower and the hit rate recovers gradually; routing requests with the same prefix to the same replica keeps caches warm.
  • Isolation across tenants. A shared prefix cache can leak timing information about other users' prompts (a hit is faster than a miss). That is why block hashes can include a salt per tenant, at the cost of sharing less (security covers multi-tenancy).

Key takeaways

  • Throughput comes from batching, but requests have unpredictable lengths. Continuous (iteration-level) batching lets requests join and leave every step; in the chapter's simulation it gave 3.2 times the throughput of static batching.
  • Contiguous per-request reservation wastes most of the KV cache (20.4% to 38.2% used in the systems the vLLM paper measured). Paged attention allocates fixed-size blocks through a block table, bounding waste to one partial block per sequence.
  • Block tables enable sharing: reference counts, copy-on-write, and prefix caching by chained block hashes (vLLM) or a radix tree (SGLang).
  • A long prefill stalls everyone else's decoding. Chunked prefill spreads it over steps under a token budget, trading the new prompt's first-token time for others' smoothness. Disaggregation separates the phases onto different GPUs.
  • The settings (maximum sequences, token budget, memory share, context length) map directly to these mechanisms, and preemption, queue length and p99 inter-token latency are the metrics to watch.

Check your understanding

A static-batching server handles a batch of 16 requests whose output lengths are 12, 15, 20, twelve others near 15, plus one that runs to 480 tokens. Roughly what limits its throughput?

  1. The weights must be reloaded for every request
  2. Prefill is slower than decode
  3. The batch runs 480 steps, during which 15 of the 16 slots are mostly idle
  4. The KV cache is too large for 16 sequences
The batch is held until its longest member ends, so fifteen slots sit empty for most of the run. Continuous batching refills them every step. Option 3 might be true in other settings but nothing in the question says memory is short; option 0 is false, since weights are loaded once per step for the whole batch.

Why does paging the KV cache raise throughput if it does not make attention arithmetic any faster?

  1. Less wasted memory leaves room for more concurrent sequences, giving a bigger batch
  2. Blocks are stored in faster memory than contiguous slabs
  3. It lets the GPU skip attention for old tokens
  4. It reduces the number of weights to be read
Throughput in memory-bound decode grows with batch size, and batch size is limited by how many caches fit. Paging recovers the reserved-but-unused and fragmented memory. The blocks live in the same HBM, nothing is skipped, and the weights are untouched.

Two requests share a 32-token prefix and the block size is 16. The second request is sent after the first has finished. What happens with prefix caching enabled and enough free memory?

  1. Nothing is reused, because the first request has finished and its memory was cleared
  2. Only a request running at the same time can share the blocks
  3. The whole second prompt is reused, including its different suffix
  4. The two full prefix blocks are found by hash and reused, and only the remaining tokens are computed
Finished requests' blocks are kept with reference count zero and evicted only under memory pressure, so a later request can hit them. Only matching full blocks are reused; the differing suffix must be computed.

Your chat product shows users a visible pause in streaming whenever someone pastes a very long document. Which change most directly addresses it?

  1. Raise the maximum number of concurrent sequences
  2. Enable chunked prefill with a moderate per-step token budget
  3. Increase the fraction of GPU memory given to the engine
  4. Quantise the weights from 16 to 8 bits
The pause is a long prefill occupying a whole step while other users wait for their next token; a token budget spreads it over many short steps. More sequences would make steps longer, extra memory does not change step length, and quantisation speeds up all steps but does not remove the stall.

In the prefix-caching simulation, caches of 50 and of 500 blocks both reuse 52% of tokens, yet 10,000 blocks reuse 84%. Why?

  1. Cache hits require at least 500 blocks to be enabled
  2. Larger caches use a better hash function
  3. Conversation histories only help if the cache can hold all active chats between a chat's turns, otherwise they are evicted before reuse
  4. The system prompt is evicted once more blocks exist
The system prompt is touched by every request, so it stays resident even in a tiny cache. Each chat's history is reused only when that chat returns, after the other chats have each sent a turn; the cache must cover that working set. The hash function and the size threshold play no part.

An engine preempts and recomputes sequences constantly, and throughput falls as traffic rises. Which action is most likely to help?

  1. Lower the cap on concurrent sequences or give the cache more memory
  2. Increase the per-step token budget
  3. Disable prefix caching
  4. Raise the cap on concurrent sequences so the queue is shorter
Constant preemption means the admitted sequences' caches grow beyond the pool, so the engine redoes work. Admitting fewer sequences, or enlarging the pool, stops the thrashing. More concurrency makes it worse; the token budget concerns prefill chunking, not memory; disabling prefix caching frees little and removes savings.

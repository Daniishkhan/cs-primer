Adapters on Demand

LoRA needs a training run for every task. This chapter looks at two research directions that try to remove that run: models that adjust themselves to the task they see, and hypernetworks that write an adapter from a short description of the task. Both are young, so the aim is to understand the mechanism, the evidence and the limits.

Why this matters

Chapter 11 made adaptation cheap, and chapter 16 made combining adaptations cheap. A product with hundreds of tasks or customers still pays one data-collection and training cycle per adapter. If a network could produce a decent adapter in one forward pass, specialisation would become something a service does per request. These ideas are not yet standard practice, but they point at where the field is moving, and they are built from pieces you already know: singular values, low-rank updates and reinforcement learning. After this chapter you will be able to explain singular-value fine-tuning and two-pass inference, describe what a hypernetwork is and what Text-to-LoRA generates, and judge how much of the claimed benefit to trust.

The problem: one training run per task

A LoRA adapter (chapter 11) is small, but making it is not free: you need task data, a training run, hyperparameters and an evaluation. A company with 300 customers, each wanting the model to follow their house style, faces 300 of those. A coding assistant that wants a specialist for each framework faces the same. Two questions follow. Can the base model itself notice what kind of task it has been given and reconfigure a little? And can we skip training and compute the adapter from a description of the task?

Self-adaptive models: Transformer-squared

Sun, Cetin and Tang (2025), in "Transformer-Squared: Self-adaptive LLMs" (Sakana AI), propose a model that adapts at inference time in two passes. The ingredient is a very small kind of fine-tuning.

Singular-value fine-tuning

Any weight matrix W has a singular value decomposition W = U Σ VT (A0, eigenvectors, SVD and low rank): U and V hold directions, and the diagonal of Σ holds one strength per direction. Singular-value fine-tuning (SVF) leaves U and V alone and learns only a vector z with one number per singular value, giving W′ = U (Σ ⊗ diag(z)) VT. Each direction the layer already uses is amplified (z > 1), damped (z < 1) or flipped. A square 4,096 × 4,096 matrix has 4,096 singular values, so SVF trains 4,096 numbers for it, against 8 × (4,096 + 4,096) = 65,536 for a rank-8 LoRA. The authors report that SVF uses fewer than 10% of the trainable parameters of their LoRA baseline.

Two properties make this convenient. The learned vectors are small enough to store hundreds of them. And because W′ is linear in z, mixing two vectors mixes the two modified matrices exactly. Here is a check, and a parameter count for the query and value projections of a 7B-class model (the shapes of Mistral-7B: 4,096-wide, 32 layers, key and value width 1,024), set beside the hypernetwork sizes reported later in this chapter.

import numpy as np

rng = np.random.default_rng(0)
m = n = 256
W = rng.normal(0, 0.05, (m, n))
U, s, Vt = np.linalg.svd(W, full_matrices=False)

def with_z(z):
    """Singular-value fine-tuning: scale each singular value by z[i], keep U and V fixed."""
    return (U * (s * z)) @ Vt

assert np.allclose(with_z(np.ones(n)), W)                  # z = 1 leaves the layer unchanged
z_math = 1 + 0.3 * rng.normal(size=n)                      # stand-ins for two trained "expert vectors"
z_code = 1 + 0.3 * rng.normal(size=n)
alpha = 0.7
mixed_z = with_z(alpha * z_math + (1 - alpha) * z_code)
mixed_W = alpha * with_z(z_math) + (1 - alpha) * with_z(z_code)
print(f"mixing two expert vectors equals mixing the two weight matrices: max difference {np.abs(mixed_z - mixed_W).max():.1e}")

# Parameter counts for the query and value projections of a 7B-class model (4096 wide, 32 layers,
# key/value width 1024 from 8 key-value heads of 128): Mistral-7B-like shapes.
shapes = [(4096, 4096), (1024, 4096)]                     # (out, in) for q_proj and v_proj
L, r = 32, 8
lora = L * sum(r * (o + i) for o, i in shapes)
svf = L * sum(min(o, i) for o, i in shapes)
print(f"one rank-{r} LoRA on q and v : {lora:>10,} parameters")
print(f"one SVF vector on q and v : {svf:>10,} parameters ({100 * svf / lora:.1f}% of the LoRA)")
for name, size in (("hypernetwork S", 4.9e6), ("hypernetwork M", 34.3e6), ("hypernetwork L", 55.3e6)):
    print(f"{name}: {size / 1e6:5.1f} M parameters = {size / lora:4.1f} adapters' worth of storage")
mixing two expert vectors equals mixing the two weight matrices: max difference 4.2e-16
one rank-8 LoRA on q and v :  3,407,872 parameters
one SVF vector on q and v :    163,840 parameters (4.8% of the LoRA)
hypernetwork S:   4.9 M parameters =  1.4 adapters' worth of storage
hypernetwork M:  34.3 M parameters = 10.1 adapters' worth of storage
hypernetwork L:  55.3 M parameters = 16.2 adapters' worth of storage

The first line is the useful one: a weighted mix of two expert vectors gives the same weights as the weighted mix of the two adapted layers, to rounding error (4e-16). The 3,407,872 parameters of a rank-8 adapter on q and v matches the "about 3.4 million" per LoRA reported in the Text-to-LoRA paper, which gives some confidence that the shapes are right. SVF on the same two matrices would be 163,840 numbers; the paper applies SVF to more matrices than these two, so read the percentage as a shape comparison, not as the paper's own figure.

SVF is trained with reinforcement learning, not next-token prediction. The paper uses REINFORCE (chapter 7) with a reward of −1 or +1 for a wrong or right answer plus a KL penalty to the original model (chapter 8). That lets it learn from datasets that have only final answers, such as GSM8K, and the authors report that SVF trained stably where LoRA trained with the same RL objective was unstable.

Two passes at inference

Training gives a set of expert vectors, each specialised for a domain (the paper trains on maths, code and reasoning data, and a vision task for a vision-language model). At inference there are two passes, which is where the name comes from.

The paper describes three strategies for the first pass: ask the model to classify the prompt into one of the known categories (prompt-based); use a separate SVF-trained classifier expert, which the authors report is more accurate; or, given about ten examples from the task, use a search method (the cross-entropy method) to find the mixing coefficients that do best on them. They report gains on held-out tasks over the base model: for example, on Llama3-8B-Instruct the few-shot version moved MATH from 24.54 to 25.47, HumanEval from 60.98 to 62.99 and ARC-Challenge from 80.63 to 82.61. These are real but modest improvements, and the paper itself notes that not every setting improved (prompt-based adaptation slightly lowered Llama3-70B's MATH score), that the search adds one-time overhead, and that SVF can only amplify or damp what the base model's weights already contain.

Hypernetworks: networks that write networks

A hypernetwork is a network whose output is the weights of another network. Ha, Dai and Le (2016) introduced the term for generating the weights of recurrent networks. Used for adaptation, the idea is: train a network H that takes a description of a task and returns the LoRA matrices A and B for each layer. Then a new task costs one forward pass of H, not a training run.

Charakorn et al. (2025), in "Text-to-LoRA: Instant Transformer Adaption" (ICML 2025), do this. As reported in the paper, H takes a text embedding of the task description (from a sentence-embedding model) together with learned embeddings that say which layer and which projection it is generating for, and outputs the rank-8 LoRA matrices for the query and value projections in every attention block of the base model. Three sizes are described: about 55.3 million parameters (the largest, which emits A and B together), about 34.3 million and about 4.9 million. Compare the output: one adapter is about 3.4 million parameters, so the large hypernetwork has the storage footprint of about sixteen adapters, as the last lines of the output above show.

Two ways to train H are described. In reconstruction, H is trained to reproduce LoRAs that were already trained on known tasks, a form of distillation (chapter 15) from adapters into a generator. The authors report that on nine benchmark tasks it matches the task-specific adapters (averages of about 73.0 to 73.5 against 73.3), but that it generalises poorly to tasks it was not trained on. In supervised fine-tuning, H is trained end to end across 479 training tasks, with several descriptions each, so that the generated adapters make the base model do well on each task's data. This version can produce adapters zero-shot for unseen tasks: on ten benchmarks the paper reports an average of 67.7 for the largest hypernetwork, against 66.3 for a multi-task LoRA and 55.8 for the base model (Mistral-7B-Instruct). The generated adapters beat the base model by a wide margin, and on some benchmarks even exceed a task-specific adapter, but the authors state that zero-shot generation does not fully close the gap to task-specific training.

State of play, October 2026

The Text-to-LoRA, Transformer-squared and Drag-and-Drop LLMs results above come from papers by the method's own authors; I read the abstracts and the paper text through a summarising tool, and have not reproduced any of the numbers. Drag-and-Drop LLMs (Liang et al., 2025) generates LoRA weights from a batch of unlabelled prompts and claims up to 12,000 times lower overhead than full fine-tuning and gains of up to 30% over the strongest training LoRAs on unseen benchmarks; it is a single preprint at the time of writing. Sakana AI also released Doc-to-LoRA in February 2026, a hypernetwork that turns a document into an adapter so a model can answer questions about it without the document in context; I saw its project page and repository summary but did not read the paper, and I cite it only as a direction. Treat all of this as research results to test on your own tasks.

Common misconception

"A hypernetwork makes fine-tuning obsolete." The evidence so far says it gives a fast, cheap starting point whose quality depends on how well the task description matches tasks seen in training. The Text-to-LoRA authors report large drops when descriptions are unaligned with the task (around 51 against 73 on average in one reconstruction test), and say its generalisation to task types far from the training distribution is not yet established. For a task that matters, a trained adapter still wins; a generated adapter is a quick draft to evaluate, or to continue training from.

Systems connection

Generated weights are build output made from an input you may not control. If a customer's text can shape the weights that serve that customer, then a poisoned or adversarial description is a weight-level injection problem: validate inputs, evaluate each generated adapter on a fixed suite before use, and cache by a hash of the description so repeated requests reuse a vetted adapter. Serving many adapters on one base model is an engine feature, covered in chapter 20; the memory the extra adapters occupy competes with the KV cache of chapter 18.

Key takeaways

  • Singular-value fine-tuning learns one scale per singular value of a weight matrix, thousands of parameters per matrix instead of tens of thousands for LoRA. Because it is linear in the scales, vectors can be mixed exactly.
  • Transformer-squared uses two passes: dispatch to identify the task and blend expert vectors, then answer with the blended weights. Reported gains over the base model are real but modest.
  • A hypernetwork writes another network's weights. Text-to-LoRA writes a rank-8 adapter from a task description in one forward pass, trained by reconstructing adapters or by end-to-end supervised learning.
  • Zero-shot generated adapters beat the base model but still trail task-specific training, and they depend on how well the description matches the training tasks.
  • Generated adapters are untrusted build output: evaluate them, cache vetted ones, and check where the description came from.

Check your understanding

A 4,096 × 4,096 weight matrix is adapted with SVF and, separately, with a rank-8 LoRA. How many trainable numbers does each need for this one matrix?

  1. SVF: 65,536; LoRA: 4,096
  2. SVF: 4,096; LoRA: 65,536
  3. SVF: 4,096; LoRA: 4,096
  4. SVF: 16.8 million; LoRA: 65,536
SVF trains one scale per singular value, min(m, n) = 4,096 numbers. A rank-8 LoRA trains A (8 × 4,096) and B (4,096 × 8), which is 8 × (4,096 + 4,096) = 65,536. The 16.8 million figure is the size of the matrix itself, which neither method trains.

What does the first pass of Transformer-squared produce?

  1. The final answer, which the second pass only reformats
  2. A new LoRA adapter trained on the user's prompt
  3. A gradient update to the base model's weights
  4. A choice or blend of stored expert vectors suited to the incoming task, used to scale the singular values in the second pass
The first pass is a dispatch step (classification, a classifier expert, or a few-shot search for mixing coefficients). It does not train anything and does not answer. Its output, a blended vector z′, configures the model for the second pass, which generates the answer.

A Text-to-LoRA hypernetwork trained by supervised fine-tuning on many tasks is given a description of a task it never saw. What should you expect, based on the reported results?

  1. An adapter that usually improves on the base model, but that may still fall short of a task-specific trained adapter, and that is sensitive to how well the description fits
  2. An adapter equal to a trained one, because the hypernetwork has seen similar text
  3. An adapter no better than the base model, since it saw no data for this task
  4. An error, because hypernetworks only work on tasks seen in training
The paper reports zero-shot generalisation above the base model but short of task-specific adapters, with drops when descriptions are unaligned. Equal quality would contradict the authors' own statement; no gain would contradict their averages; and the SFT variant does produce adapters for unseen tasks, which is its purpose.

You adopt a service that generates an adapter from each customer's free-text task description. Which control matters most before an adapter goes into production?

  1. Increase the rank so that the adapter is more expressive
  2. Use a larger text encoder for the descriptions
  3. Run each generated adapter against a fixed evaluation suite, including adversarial cases, and cache vetted adapters by a hash of the description
  4. Merge every generated adapter into the base weights as soon as it is created
Generated weights are the output of a model fed with uncontrolled text, so they need the same acceptance testing as any other artefact. A higher rank or bigger encoder says nothing about safety or quality, and merging unvetted adapters into the shared base would spread a bad one to every customer.

Speculative Decoding & Other Speedups

Decoding is slow because each token needs a full pass over the weights, one after another. Speculative decoding lets a cheap guesser propose several tokens and the big model check them all in a single pass. The surprising part is that the text it produces comes from exactly the same distribution as the big model alone. This chapter shows why, and what the speed-up depends on.

Why this matters

Batching (chapter 20) raises throughput, but it does nothing for a single user waiting for a long answer: each token still takes one memory-bound step. Speculative decoding attacks that latency directly, and it is the one common speedup that is lossless in principle, so it can be switched on without re-running your evaluations in the way quantisation requires (chapter 19). After this chapter you will be able to derive the accept-or-resample rule, estimate the expected speed-up from an acceptance rate, explain how Medusa-style heads and self-drafting variants avoid a separate draft model, and say when speculation stops helping.

The idea: guess cheaply, check in parallel

Chapter 18 showed that generating a token is limited by reading the weights, not by arithmetic: a step with one sequence uses a tiny fraction of the GPU's compute. That has a useful consequence. Scoring several tokens in one forward pass costs almost the same as scoring one, because the weights are read once either way. Verification is parallel; generation is not. If you could somehow know the next five tokens in advance, you could confirm all five in about the time it takes to produce one.

You cannot know them, but you can guess. Leviathan, Kalman and Matias (2022), in "Fast Inference from Transformers via Speculative Decoding", and independently Chen and colleagues (2023) at DeepMind, in "Accelerating Large Language Model Decoding with Speculative Sampling", proposed this loop. Call the large model the target and a much smaller, faster model the draft (for example a 1B-parameter model drafting for a 70B one, from the same family and tokeniser).

  1. The draft model generates k tokens in the ordinary one-at-a-time way. It is cheap, so this takes a small fraction of a target step each.
  2. The target model runs one forward pass over the prompt plus the k drafted tokens, producing its own next-token distribution at every drafted position (the same parallel computation as prefill).
  3. Walking left to right, each drafted token is either accepted or rejected by the rule below. At the first rejection, a replacement token is sampled and everything after it is thrown away.
  4. If all k were accepted, the target's output at the last position gives one more token for free.

Each round therefore produces at least one token (the replacement, or the free one) and up to k + 1, for the price of one target pass plus k cheap draft passes.

Why the output is unchanged

The claim that this does not alter the output deserves a proof, because it sounds too good. Fix a position. Let p(x) be the target's probability of token x and q(x) the draft's. The draft samples a token x from q. The rule is:

  • Accept x with probability min(1, p(x) / q(x)).
  • If rejected, sample a replacement from the residual distribution proportional to max(0, p(x) − q(x)).

Now compute the probability that this procedure outputs a particular token x. It can happen in two ways. Either the draft proposed x and it was accepted, with probability q(x)·min(1, p(x)/q(x)) = min(q(x), p(x)). Or something was rejected and the replacement happened to be x. The total rejection probability is 1 − ∑y min(p(y), q(y)) = ∑y max(0, p(y) − q(y)), the same number that normalises the residual. So the second route has probability max(0, p(x) − q(x)) exactly. Adding the two routes:

P(output = x) = min(p, q) + max(0, p − q) = p(x)

The identity min(a, b) + max(0, a − b) = a finishes it. The draft can be as bad as you like and the output is still a sample from the target; a poor draft only means more rejections. The same argument applies at every position because the target's distribution at a later position is computed given the tokens already accepted, which are exactly the tokens a plain run would have produced. Run it and see:

"""Speculative sampling over a 6-token vocabulary: the output distribution equals the target's, however bad the draft is."""
import numpy as np

rng = np.random.default_rng(0)
V = 6
p = np.array([0.40, 0.25, 0.15, 0.10, 0.07, 0.03])      # target model's next-token distribution
q = np.array([0.10, 0.10, 0.50, 0.10, 0.10, 0.10])      # a poor draft model's distribution

def speculative_step(p, q):
    x = rng.choice(V, p=q)                               # 1. the draft proposes a token
    if rng.random() < min(1.0, p[x] / q[x]):             # 2. accept with probability min(1, p/q)
        return x, True
    resid = np.maximum(p - q, 0); resid /= resid.sum()   # 3. on rejection, sample from the normalised residual
    return rng.choice(V, p=resid), False

N = 200_000
out = np.zeros(V); acc = 0
for _ in range(N):
    t, ok = speculative_step(p, q)
    out[t] += 1; acc += ok
print("token            ", *[f"{i:>6}" for i in range(V)])
print("target p         ", *[f"{x:>6.3f}" for x in p])
print("draft q          ", *[f"{x:>6.3f}" for x in q])
print("speculative out  ", *[f"{x:>6.3f}" for x in out / N])
alpha = np.minimum(p, q).sum()
print(f"acceptance rate: measured {acc/N:.3f}, theory sum(min(p,q)) = {alpha:.3f}")
token                  0      1      2      3      4      5
target p           0.400  0.250  0.150  0.100  0.070  0.030
draft q            0.100  0.100  0.500  0.100  0.100  0.100
speculative out    0.398  0.251  0.149  0.101  0.070  0.030
acceptance rate: measured 0.550, theory sum(min(p,q)) = 0.550

The draft here is deliberately poor (it puts half its mass on token 2, where the target gives 0.15), yet 200,000 speculative samples reproduce the target's distribution to within sampling noise. The measured acceptance rate, 0.550, equals ∑ min(p, q) = 0.550, which is one minus the total-variation distance between the two distributions. So acceptance rate measures how close the draft is to the target.

How much faster?

Suppose each drafted token is accepted independently with probability α (an approximation; real acceptance varies with the text). Round k tokens long, the expected number of tokens produced per target pass is the sum over how far the accepted run extends, which is a geometric series:

E[tokens per round] = (1 − αk+1) / (1 − α)

(Leviathan et al., 2022). With α = 0.8 and k = 4 that is 3.36 tokens. Wall-clock speed-up divides by the extra cost: if one draft step costs a fraction c of a target step, a round costs 1 + kc target-steps, so speed-up = E[tokens] / (1 + kc).

"""Expected tokens per target-model call, and the speed-up, as a function of acceptance rate and draft length."""
def tokens_per_call(alpha, k):                           # (1 - alpha^(k+1)) / (1 - alpha)
    return (1 - alpha ** (k + 1)) / (1 - alpha)

def speedup(alpha, k, c):                                # c = cost of one draft step relative to one target step
    return tokens_per_call(alpha, k) / (1 + k * c)

print("expected tokens per target call (k = tokens drafted)")
print(f"{'alpha':>6}" + "".join(f"{'k='+str(k):>8}" for k in (1, 2, 4, 8)))
for a in (0.5, 0.7, 0.8, 0.9):
    print(f"{a:>6}" + "".join(f"{tokens_per_call(a, k):>8.2f}" for k in (1, 2, 4, 8)))
print("\nwall-clock speed-up when a draft step costs 5% (c=0.05) of a target step")
print(f"{'alpha':>6}" + "".join(f"{'k='+str(k):>8}" for k in (1, 2, 4, 8)))

Read the three tables as three lessons. A higher acceptance rate always helps. Drafting longer helps with diminishing returns, and past a point hurts: at α = 0.5 the best k is 4 and 8 is worse. And the draft's cost matters enormously: with a draft costing 30% of the target, speculation gives under 2 times at best and can be slower than not speculating (0.59 times at α = 0.5, k = 8). That is why the draft must be much smaller than the target, and why an extra speculative model adds memory and engineering overhead.

Now the full loop on a toy language model (a Markov chain over eight tokens), compared with ordinary decoding.

"""A full draft-and-verify loop on a toy language model (a Markov chain over 8 tokens). Compare with plain decoding."""
import numpy as np
rng = np.random.default_rng(1)
V, K, N = 8, 4, 60_000
def table(sharp):                                         # next-token distributions, one row per previous token
    m = rng.random((V, V)) ** sharp; return m / m.sum(1, keepdims=True)
P = table(3.0)                                            # target model
Q = 0.6 * P + 0.4 * table(1.0)                            # draft: related to the target but blurrier
Q /= Q.sum(1, keepdims=True)

def plain(n):
    out, prev = [], 0
    for _ in range(n):
        prev = rng.choice(V, p=P[prev]); out.append(prev)
    return out

def speculative(n):
    out, prev, calls, drafted, accepted = [], 0, 0, 0, 0
    while len(out) < n:
        d, cur = [], prev
        for _ in range(K):                                # the draft proposes K tokens, one at a time
            cur = rng.choice(V, p=Q[cur]); d.append(cur)
        calls += 1                                        # ONE target pass scores all K positions at once
        cur, new = prev, []
        for x in d:
            drafted += 1
            if rng.random() < min(1, P[cur, x] / Q[cur, x]):
                new.append(x); cur = x; accepted += 1
            else:
                r = np.maximum(P[cur] - Q[cur], 0); r /= r.sum()
                new.append(rng.choice(V, p=r)); break     # rejected: resample from the residual and stop
        else:
            new.append(rng.choice(V, p=P[cur]))           # all K accepted: a free extra token from the target
        out += new; prev = new[-1]
    return out[:n], calls, accepted / drafted

def bigrams(seq):
    c = np.zeros((V, V))
    for a, b in zip(seq, seq[1:]): c[a, b] += 1
    return c / c.sum()
a = plain(N); b, calls, alpha = speculative(N); a2 = plain(N)
print(f"plain decoding      : {N} tokens, {N} target calls")
print(f"speculative (K={K})  : {N} tokens, {calls} target calls -> {N/calls:.2f} tokens per call")
print(f"per-token acceptance rate measured: {alpha:.2f}")
print(f"largest bigram-frequency difference between the two outputs: {np.abs(bigrams(a)-bigrams(b)).max():.4f}")
print(f"(two plain runs of the same length differ by about {np.abs(bigrams(a)-bigrams(a2)).max():.4f})")
plain decoding      : 60000 tokens, 60000 target calls
speculative (K=4)  : 60000 tokens, 17550 target calls -> 3.42 tokens per call
per-token acceptance rate measured: 0.81
largest bigram-frequency difference between the two outputs: 0.0031
(two plain runs of the same length differ by about 0.0017)

Speculation produced 60,000 tokens with 17,550 target calls: 3.42 tokens per call, in line with the formula for α = 0.81 and k = 4 (3.43). The bigram statistics of its output match plain decoding to within the noise between two plain runs (I repeated this with four other seeds; the differences ranged from 0.002 to 0.006, against 0.003 to 0.004 between plain runs).

Common misconception

"Speculative decoding is an approximation that trades quality for speed." The accept-or-resample rule is exact, so with it the output distribution is identical to the target's: you pay in extra computation (the draft passes and the discarded tokens), not in quality. The caveat is that the guarantee covers the sampling procedure in exact arithmetic; floating-point differences between a batched verify pass and a one-token pass can change which token a borderline random draw selects, and some variants (below) deliberately relax the rule for more speed.

Drafts without a draft model

A second model costs memory, must share the target's tokeniser, and can be hard to keep in step with a fine-tuned target. Several methods produce guesses another way.

Medusa-style heads
Cai and colleagues (2024), in "Medusa: Simple LLM Inference Acceleration Framework with Multiple Decoding Heads", add a few extra output heads to the target model. Head i reads the last hidden state and predicts the token i + 1 positions ahead, so one forward pass yields guesses for several future tokens. The candidates are arranged as a tree and verified together using a tree-shaped attention mask. They report over 2.2 times speed-up with the base model frozen (Medusa-1) and about 2.3 to 3.6 times when the heads and model are trained together (Medusa-2). Their default acceptance rule, "typical acceptance", is looser than the exact rule above, so the output is close to but not identical in distribution to the base model's.
EAGLE
Li and colleagues (2024), in "EAGLE: Speculative Sampling Requires Rethinking Feature Uncertainty", train a small module that predicts the target's next hidden feature rather than the next token, a smoother target than discrete tokens. They report 2.7 to 3.5 times latency speed-up for LLaMA2-Chat 70B and state that the generated text's distribution is preserved.
Prompt lookup and n-gram drafting
Guess by copying: if the last few tokens appeared earlier in the prompt, propose what followed them. This needs no model at all and works well for summarisation, code editing and any task that quotes its input.

Analogy: a junior drafting for a senior

A junior lawyer drafts a contract clause by clause; a senior partner reads the whole draft at once and strikes the first clause she disagrees with, rewriting it herself. Reading is much faster than writing, so when the junior is usually right the document finishes sooner than if the partner had written every word. The final text is what the partner would have approved.

Where it breaks down: the partner's rewrite is not "whatever she prefers" but a draw from a precisely corrected distribution, and that correction is what makes the result statistically identical to her own writing.

When speculation stops helping

  • Large batches. The whole idea relies on spare arithmetic capacity during memory-bound decode. A busy server with big batches is already compute-bound, so verifying rejected tokens is wasted work and the gain shrinks or turns negative. Speculation is most valuable at low concurrency and for latency-sensitive traffic.
  • High-entropy output. Creative text at high temperature has a flatter target distribution, lower agreement with any draft and so lower α. Code, structured output and repetitive text accept more.
  • Extra memory. A draft model's weights and KV cache take space from the target's cache, reducing the batch (chapter 20).

State of play, October 2026

Speculative decoding of several kinds is available in the major open-source serving engines, including draft-model, n-gram and EAGLE-style methods, and some models ship with built-in extra prediction heads for the purpose. Which methods an engine supports, and how well they combine with batching and quantisation, varies by version; check the engine documentation and measure on your own traffic, because the acceptance rate depends on your prompts. Reported speed-ups (2 to 3.5 times above) are from the authors' own benchmarks at low concurrency.

Other speedups, briefly

Speculation is one of several levers, each acting on a different part of the cost. Weight quantisation shrinks the bytes read per step (chapter 19). Grouped-query attention and KV-cache quantisation shrink the cache (chapter 18, A2 chapter 19). Continuous batching, paging and prefix caching raise utilisation (chapter 20). Mixture-of-experts models activate only some weights per token (A2 chapter 20). Distillation (chapter 15) buys a smaller model outright, at the cost of capability. These compose, but not freely: quantisation changes the model, speculation does not, and each affects which regime (memory-bound or compute-bound) the others rely on. Chapter 22 puts them in terms of cost per token.

Key takeaways

  • Verifying many tokens in one pass costs about as much as generating one, so a cheap draft can propose k tokens and the target can check them at once.
  • The accept-with-probability-min(1, p/q), else resample-from-the-residual rule makes the output distribution exactly the target's, for any draft.
  • Expected tokens per round is (1 − αk+1)/(1 − α); real speed-up also depends on how cheap the draft is, and a costly draft can make things slower.
  • Medusa heads and EAGLE draft from the target model itself; prompt lookup drafts by copying. Some variants relax exactness for speed.
  • Gains are largest at low concurrency and predictable text, and fade when the server is compute-bound.

Check your understanding

Why can the target model verify k drafted tokens in roughly the time it takes to generate one?

  1. The draft model has already done most of the work
  2. Decode is memory-bound, so scoring several positions in one pass reuses the same weight reads and adds little time
  3. The target skips attention for the drafted tokens
  4. Verified tokens do not need a KV cache
The cost of a decode step is dominated by reading the weights, which a pass over k positions does once. Option 0 confuses the draft's guesses with the target's computation: the target still evaluates every position.

A draft proposes token x with q(x) = 0.5 while the target has p(x) = 0.2. What happens?

  1. It is always rejected
  2. It is always accepted, since the draft is confident
  3. It is accepted with probability 0.5
  4. It is accepted with probability 0.4, and otherwise replaced by a draw from the residual distribution
The acceptance probability is min(1, p/q) = 0.2/0.5 = 0.4. Over-confident drafts are damped so that x is not produced more often than the target would produce it; the residual draw supplies tokens the draft under-proposed.

With an acceptance rate of 0.8 per token and drafts of length 4, roughly how many tokens does one target pass yield on average?

  1. About 3.4
  2. Exactly 4
  3. About 0.8
  4. About 5
(1 − 0.85) / (1 − 0.8) = 3.36. Five would require every draft token to be accepted every time; four ignores rejections; 0.8 is the per-token acceptance rate, not a token count.

A busy server running at large batch sizes, already compute-bound, turns on speculative decoding and sees no gain. What is the most likely reason?

  1. The output distribution changed
  2. The acceptance rate is exactly zero
  3. There is no spare arithmetic capacity: verification of rejected tokens consumes compute that other requests could have used
  4. The draft model's tokeniser is different
Speculation converts idle compute in memory-bound decode into speed. When the GPU is already busy, each rejected token is wasted work. The output distribution is unaffected by design; a tokeniser mismatch would break the method entirely rather than just fail to help.

LoRA, QLoRA & Parameter-Efficient Tuning

Full fine-tuning of a 7-billion-parameter model needs over a hundred gigabytes of model state, so most people cannot do it and most tasks do not need it. LoRA freezes the model and learns a small low-rank correction instead; QLoRA also stores the frozen part in 4 bits. This chapter explains why a correction with under 1% of the parameters can be enough, what rank and alpha control, and how to work out what fits on a 24 GB card.

Why this matters

Chapter 10 ended with a wall: full SFT of a 7B model needs about 112 GB for weights, gradients and optimiser state, more than any single consumer or mid-range data-centre GPU. Parameter-efficient fine-tuning is how most teams outside the largest labs actually adapt models, and how a service can keep hundreds of customer-specific variants of one base model. Its failure modes are quiet (an adapter too small for the data, a learning rate copied from full fine-tuning, a template mismatch), and the memory arithmetic decides what is feasible before any training starts. After this chapter you will be able to count adapter parameters, choose rank, alpha and target layers with reasons, compute whether a QLoRA run fits your GPU, and say when LoRA is the wrong tool.

The idea: learn the change, and constrain its shape

Fine-tuning turns a pretrained weight matrix W0 into W0 + ΔW, where ΔW is whatever the training run added. Full fine-tuning learns every entry of ΔW for every matrix, and pays for it: a gradient and two Adam moments for each entry (chapter 2). Hu et al. (2021), in "LoRA: Low-Rank Adaptation of Large Language Models", made one assumption: the update ΔW has low rank, so it can be written as a product of two thin matrices.

Plug in numbers. First the parameter count for one 4,096 × 4,096 matrix at r = 8; then a toy layer small enough to check by hand, where x goes through the frozen path and through A, then B.

The idea

  1. full ← d_out × d_in; lora ← d_out × r + r × d_in; ratio
  2. toy layer: W0 (3x4), A (2x4), B (3x2), x (4 numbers), scale = alpha/r
  3. h ← W0 x + scale × B (A x)
  4. set B = 0: h equals W0 x exactly

A matrix has rank r if it can be built from r independent directions; the idea is the one in A0 on SVD and low rank. W0 is frozen. Only A and B, the adapter, are trained. For an input x the layer computes

h = W0 x + (α/r) · B (A x).

The second term is cheap: A x squeezes the din-dimensional input down to r numbers, B expands them back to dout, and the constant α/r scales the result. This is the same arithmetic as a bottleneck layer with a skip connection (residuals in A2), except that the bottleneck is linear and sits in parallel with an existing weight rather than inside a new block.

Analogy: margin notes in a textbook

A textbook (the frozen weights) is expensive to reprint. Instead of editing every page, you write short margin notes that say "when you read this section, lean towards that". A small set of notes can change how the book is used on a topic while leaving the printed text untouched, and you can keep different sets of notes for different courses and swap them in seconds.

Where it breaks down: real notes can say anything. LoRA's notes are restricted to a few directions per matrix, and a task that needs many independent changes will not fit. And the notes are not read separately: they are added into the numbers on every page, which is why they can be merged away afterwards.

Counting what is saved

A matrix of shape dout × din has dout·din numbers. The adapter has r·(din + dout): it saves parameters only while r is below din·dout/(din + dout), which for a square matrix is d/2. Below, the published Llama 2 7B shape (hidden size 4,096, feed-forward size 11,008, 32 layers) and a range of ranks, applied either to the query and value projections only (the original paper's common choice) or to every linear layer.

At rank 16 on all linear layers, the adapter has 40.0 million parameters, 0.59% of the model, and an 80 MB file in bf16. Hu et al. report that, against fine-tuning GPT-3 175B with Adam, LoRA reduced the number of trainable parameters by 10,000 times and the GPU memory requirement by 3 times, with no additional inference latency (their abstract). Notice the table's last rows too: rank 256 on all layers is already 9.5% of the model, which is where "parameter-efficient" stops being a fair description.

Why a low-rank update can be enough

Two lines of evidence, one empirical and one structural.

Empirical: fine-tuning moves in few directions. Aghajanyan, Zettlemoyer and Gupta (2021, "Intrinsic Dimensionality Explains the Effectiveness of Language Model Fine-Tuning") asked how many degrees of freedom a fine-tuning task really needs. They trained only a small number of parameters, randomly projected back into the full weight space, and report that optimising just 200 such parameters let a RoBERTa model reach about 90% of its full-parameter performance on the MRPC paraphrase task. The intrinsic dimension of a task, the smallest subspace in which it can be solved well, is far lower than the parameter count, and it tends to decrease as the pretrained model gets bigger. LoRA exploits the same fact with a different, structured subspace.

Structural: a pretrained model has already done the hard part. Pretraining built general-purpose features. A downstream task usually asks for a re-weighting of features that already exist, not for new ones, and re-weighting is a low-rank edit.

A controlled experiment

We can test the claim in a place where the answer is known. Take a 48 × 48 matrix and a target update ΔW of fixed size. In one case the update has only four independent directions (a rank-4 change); in the other it touches every direction (a full-rank change). Train a LoRA of each rank, starting from B = 0 and a small random A, with Adam, and measure how much of the update's energy (its squared Frobenius norm) is left unexplained.

import numpy as np
rng = np.random.default_rng(0)
d, n = 48, 4000
X = rng.normal(size=(n, d))

def target(kind):
    if kind == "rank-4 change":                     # a fine-tuning update with 4 directions
        U, V = rng.normal(size=(d, 4)), rng.normal(size=(d, 4))
        D = U @ V.T
    else:                                           # an update touching every direction
        D = rng.normal(size=(d, d))
    return D / np.linalg.norm(D)                    # same size (Frobenius norm 1) in both cases

def fit_lora(D, r, steps=3000, lr=0.02):
    """Learn delta W = B @ A (B starts at zero) so that X @ delta W^T matches X @ D^T."""
    A = rng.normal(0, 1 / np.sqrt(d), (r, d)); B = np.zeros((d, r))
    mA = vA = mB = vB = 0
    Y = X @ D.T
    for t in range(1, steps + 1):
        E = (X @ (B @ A).T - Y) / n                 # residual
        gB = 2 * E.T @ (X @ A.T); gA = 2 * B.T @ (E.T @ X)
        for name, g in (("A", gA), ("B", gB)):      # Adam
            if name == "A": mA = .9 * mA + .1 * g; vA = .999 * vA + .001 * g * g; A = A - lr * (mA / (1 - .9 ** t)) / (np.sqrt(vA / (1 - .999 ** t)) + 1e-8)
            else:           mB = .9 * mB + .1 * g; vB = .999 * vB + .001 * g * g; B = B - lr * (mB / (1 - .9 ** t)) / (np.sqrt(vB / (1 - .999 ** t)) + 1e-8)
    return B @ A

for kind in ("rank-4 change", "full-rank change"):
    D = target(kind)
    s = np.linalg.svd(D, compute_uv=False)
    top4 = (s[:4] ** 2).sum()                       # share of the update's energy in its top 4 directions
    print(f"\n{kind}: top-4 singular directions hold {100 * top4:.0f}% of the update's energy")
    print(f"{'rank r':>7} {'LoRA params':>12} {'unexplained energy':>19}")
    for r in (1, 2, 4, 8, 16, 48):
        err = np.linalg.norm(fit_lora(D, r) - D) ** 2
        print(f"{r:7d} {r * 2 * d:12d} {100 * err:18.1f}%")
print(f"\nfull fine-tuning of this matrix would train {d * d} numbers")

Reading the output. The rank-4 update is recovered perfectly from rank 4 upwards, with 384 trainable numbers against 2,304 for the matrix. Below its true rank (r = 1, 2) LoRA captures only part of the change. The full-rank update only has 27% of its energy in its top four directions, and LoRA's unexplained fraction falls slowly: 73% at r = 4, 53% at r = 8, 26% at r = 16. The last row is the cautionary one: at r = 48 the adapter stores 4,608 numbers, twice as many as the 2,304 in the matrix, so it would be cheaper to fine-tune the matrix directly.

The research on real models agrees with the shape of this picture. Biderman et al. (2024), in "LoRA Learns Less and Forgets Less", compared LoRA with full fine-tuning on code and mathematics and report that LoRA usually underperforms in standard low-rank settings, and suggest that full fine-tuning learns perturbations with ranks 10 to 100 times higher than typical LoRA configurations. Schulman and colleagues at Thinking Machines (September 2025, "LoRA Without Regret") report that for small-to-medium supervised datasets LoRA matches full fine-tuning, provided it is applied to all layers and is not capacity-limited, and that for datasets exceeding its capacity LoRA underperforms, with efficiency degrading as the ratio of model capacity to dataset size worsens.

Common misconception

"LoRA is a free lunch: the same quality for 1% of the cost." It matches full fine-tuning when the task fits in the adapter, which is common for style, format and moderate-size domain data, and often does not when the dataset is large or the new skill is far from what the model knows (new languages, long continued pretraining). The honest summary from the two studies above: LoRA learns less, forgets less, and can match full fine-tuning if you give it enough rank, put it on enough layers and size its learning rate for it. "Always cheaper to tune" is also false: its learning-rate sweet spot differs from full fine-tuning's (below), and a hyperparameter copied across will underperform without any error.

How it trains

Initialisation and the first step

A is initialised with small random values and B with zeros. Then B·A = 0, so the adapted model equals the pretrained model at step 0, and the first loss is the base model's loss. Why not initialise both randomly? Then the model would start with a random perturbation, an unnecessary shock. Why not both zero? Then the gradients vanish entirely: look at the derivation.

Go deeper the gradients of A and B

Let s = α/r and let g = ∂L/∂h, the gradient of the loss with respect to this layer's output (a vector of length dout). With h = W0x + s B A x, the chain rule gives

∂L/∂B = s · g (A x)T   (dout × r),   ∂L/∂A = s · (BT g) xT   (r × din).

At initialisation B = 0, so ∂L/∂A = 0 exactly, while ∂L/∂B = s·g(Ax)T is non-zero because A is random. So the first updates move only B; once B is non-zero, A starts to receive gradient too. If both were zero, both gradients would be zero and nothing would ever train. Summed over a batch, each gradient is the sum of these outer products over all tokens.

Adam (A0 on optimisers) normalises each parameter's step by its recent gradient size, so B's entries each move by roughly the learning rate per step regardless of how small the raw gradient is. That is why the scale factor α/r affects the update to W = W0 + sBA directly: it multiplies a step whose size the optimiser has already fixed.

Only A and B hold gradients and Adam moments, so the optimiser state shrinks by roughly the ratio of adapter size to model size. The frozen weights still have to sit in memory for the forward and backward passes, and the activations of the whole network are still needed to back-propagate through to the adapters. LoRA does not shrink either; the next sections show how much that matters.

A direct look at the scaling question, in a toy where the answer is cleanly measurable. The same rank-2 update is learned by adapters of rank 2, 8, 32 and 64 with Adam at one fixed learning rate and α = 16, under three conventions for the scale s: α/r, α/√r and a constant α that ignores rank.

import numpy as np
d, n, ALPHA, LR = 64, 2000, 16.0, 0.01
rng0 = np.random.default_rng(1)
X = rng0.normal(size=(n, d))
U, V = rng0.normal(size=(d, 2)), rng0.normal(size=(d, 2))
D = U @ V.T; D /= np.linalg.norm(D)                  # target update: rank 2, Frobenius norm 1
Y = X @ D.T

def run(r, scale, steps):
    rng = np.random.default_rng(5)
    A = rng.normal(0, 1 / np.sqrt(d), (r, d)); B = np.zeros((d, r))
    m = [np.zeros_like(A), np.zeros_like(B)]; v = [np.zeros_like(A), np.zeros_like(B)]
    out = {}
    for t in range(1, steps + 1):
        E = (X @ (scale * B @ A).T - Y) / n
        gB = 2 * scale * E.T @ (X @ A.T); gA = 2 * scale * B.T @ (E.T @ X)
        for i, (P, g) in enumerate(((A, gA), (B, gB))):
            m[i] = .9 * m[i] + .1 * g; v[i] = .999 * v[i] + .001 * g * g
            P -= LR * (m[i] / (1 - .9 ** t)) / (np.sqrt(v[i] / (1 - .999 ** t)) + 1e-8)
        if t in (25, 100, 400):
            out[t] = np.linalg.norm(scale * B @ A - D) ** 2
    return out

Merging and serving

Because the adapter is a linear correction, it can be folded into the base weights after training: W ← W0 + s·B·A, one matrix addition per adapted layer. The merged model is an ordinary model with no extra layers and no extra latency, which was an explicit design goal of the paper. The alternative is to keep adapters separate: one base model in memory, many small adapter files (tens to hundreds of megabytes each in the table above), and the serving engine applying whichever adapter a request names. That is how a platform serves many fine-tuned variants cheaply; chapter 17 takes up generating adapters from a task description, and chapter 20 covers how engines batch requests that use different adapters.

One caution: merging into a quantised base adds a high-precision update to low-precision weights, so the sum is rounded and a little of the adapter's effect is lost. The usual practice is to merge into a full-precision copy of the base and quantise afterwards if needed, then re-evaluate.

QLoRA: fine-tuning on top of a 4-bit model

LoRA removes the gradient and optimiser cost of the base model but still keeps its weights in 16 bits: 13.5 GB for the Llama 2 7B shape, 26 GB for 13B, 138 GB for 70B. Dettmers, Pagnoni, Holtzman and Zettlemoyer (2023), in "QLoRA: Efficient Finetuning of Quantized LLMs", store the frozen base in 4 bits, and report that this lets them fine-tune a 65B-parameter model on a single 48 GB GPU while preserving full 16-bit fine-tuning performance; their Guanaco model family reached 99.3% of ChatGPT's performance level on the Vicuna benchmark after 24 hours of fine-tuning on a single GPU (abstract). Three techniques make this work.

4-bit NormalFloat (NF4)
A 4-bit number format whose 16 levels are chosen so that each is equally likely to be used by normally distributed weights. Pretrained weights are roughly bell-shaped, so a grid of evenly spaced levels wastes resolution in the sparse tails and under-resolves the dense middle; NF4 puts levels at quantiles of a normal distribution.
Double quantisation
Quantisation needs a scale factor per block of weights. At one 32-bit scale per 64 weights, scales alone cost 0.5 bit per weight. Double quantisation quantises the scales themselves to 8 bits, with a second-level 32-bit constant per 256 scales, cutting that overhead to about 0.127 bit.
Paged optimisers
Optimiser state that is moved between GPU and CPU memory on demand (using unified memory) so that a momentary memory spike, such as a long sequence in a batch, does not crash the run with an out-of-memory error.

The forward pass uses the 4-bit weights by dequantising each block back to bf16 just before the matrix multiplication, then discarding the temporary copy. The adapter path runs in 16-bit as in LoRA, and gradients flow through the dequantised weights to the activations and to A and B only. The quantised weights are never updated.

Building NF4 and measuring it

The levels are not magic constants: they come from a short recipe in the paper. Take quantiles of the standard normal distribution (seven negative, zero, eight positive, built asymmetrically so that zero is exactly representable), scale them into [−1, 1], and divide each block of weights by its largest absolute value before rounding to the nearest level. The script builds the table, compares NF4 with evenly spaced 4-bit levels on synthetic bell-shaped weights (plus a few large outliers, which inflate the per-block scale for both), and does the storage arithmetic.

import numpy as np
from statistics import NormalDist
rng = np.random.default_rng(0)

# NF4 levels (Dettmers et al., 2023): quantiles of a standard normal, 7 negative + zero + 8 positive, scaled to [-1, 1].
nd, off = NormalDist(), 0.9677
pos = [nd.inv_cdf(p) for p in np.linspace(off, 0.5, 9)[:-1]]
neg = [-nd.inv_cdf(p) for p in np.linspace(off, 0.5, 8)[:-1]]
levels = np.array(sorted(pos + [0.0] + neg)); levels /= np.abs(levels).max()
print("NF4 levels:", np.round(levels, 4))
int4 = np.arange(-8, 8) / 8                          # 16 evenly spaced levels (symmetric int4, absmax-scaled)

def quantise(w, grid, block=64):
    w = w.reshape(-1, block)
    scale = np.abs(w).max(axis=1, keepdims=True)     # one absmax constant per block of 64 weights
    q = grid[np.abs(w / scale - grid[:, None, None]).argmin(axis=0)]
    return (q * scale).ravel()

w = rng.normal(0, 0.02, 2_000_000)                   # weights are roughly normal around zero
w[::5000] *= 8                                       # plus a few outliers

What fits on 24 GB

Putting the pieces together, using chapter 2's accounting. Assumptions, all stated: linear layers in NF4 with double quantisation (4.127 bits), embedding and output matrices kept in bf16, adapters of rank 16 on all linear layers held in fp32 with fp32 gradients and Adam moments (16 bytes per adapter parameter), sequence length 1,024 and batch 4 with gradient checkpointing (2 bytes × s × b × h at each layer boundary, plus about 34·s·b·h bytes for the one layer being recomputed, plus fp32 logits), and 1.5 GB of overhead. These are estimates, not measurements; real frameworks differ in detail.

# What fits on a 24 GB GPU?  QLoRA memory estimate for Llama 2 shapes (assumptions in the comments).
MODELS = {  # hidden, ffn, layers, kv_dim, vocab  (published Llama 2 configurations)
    "7B":  (4096, 11008, 32, 4096, 32000),
    "13B": (5120, 13824, 40, 5120, 32000),
    "70B": (8192, 28672, 80, 1024, 32000),     # grouped-query attention: 8 key/value heads of 128
}
R, SEQ, BATCH, OVERHEAD = 16, 1024, 4, 1.5      # LoRA rank, tokens per sequence, sequences per step, GB assumed
NF4_BITS = 4 + 8 / 64 + 32 / (64 * 256)         # NF4 with double quantisation

print(f"{'model':>5} {'linear params':>13} {'base NF4':>9} {'embed bf16':>10} {'LoRA params':>11} {'LoRA state':>10} "
      f"{'activations':>11} {'total':>7}  fits 24 GB?")
for name, (h, ffn, L, kv, V) in MODELS.items():
    shapes = [(h, h), (h, kv), (h, kv), (h, h), (h, ffn), (h, ffn), (ffn, h)]
    linear = L * sum(i * o for i, o in shapes)
    lora = L * sum(R * (i + o) for i, o in shapes)
    base = linear * NF4_BITS / 8 / 1e9
    embed = 2 * V * h * 2 / 1e9                                  # embedding + output matrix kept in bf16
    state = lora * (4 + 4 + 8) / 1e9                             # fp32 adapter weights, gradients, Adam moments
    # activations with gradient checkpointing: bf16 boundary per layer + one layer's ~34*s*b*h bytes + fp32 logits
    act = (L * 2 * SEQ * BATCH * h + 34 * SEQ * BATCH * h + 4 * SEQ * BATCH * V) / 1e9
    total = base + embed + state + act + OVERHEAD
    print(f"{name:>5} {linear/1e9:11.2f} B {base:7.2f} GB {embed:7.2f} GB {lora/1e6:8.1f} M {state:7.2f} GB "
          f"{act:8.2f} GB {total:5.1f} GB  {'yes' if total <= 24 else 'no'}")
print(f"\nfor comparison, full fine-tuning of 7B at 16 bytes/param: {16*6.74:.0f} GB of model states alone")

The 7B model needs about 8 GB and the 13B about 13 GB, so both fit on a 24 GB card with room to raise the batch size or sequence length. The 70B shape needs about 48 GB, which is consistent with the QLoRA paper's claim of a 65B model on one 48 GB card, though it is above 48 GB at these settings and a smaller batch or shorter sequence would be needed. Compare full fine-tuning of the 7B model, which needs 108 GB for model states alone. The base-model weights dominate every row; the adapters' own state is small (0.64 GB for the 7B), which is the point. As sequence length and batch grow, the activations term takes over, which is why gradient checkpointing (chapter 2) is almost always switched on for these runs.

The recipe in code

With the Hugging Face stack, QLoRA is a quantisation config, an adapter config and a trainer. This listing is the standard shape of the code (TRL SFTTrainer, PEFT, bitsandbytes); it was not run here because the libraries and a GPU are not available in this environment, so no output is shown. Running it prints the usual training logs: a loss that falls over the first few hundred steps, and a saved adapter directory of tens of megabytes rather than a multi-gigabyte model.

import torch
from datasets import load_dataset
from peft import LoraConfig
from transformers import BitsAndBytesConfig
from trl import SFTConfig, SFTTrainer

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",            # the NormalFloat grid
    bnb_4bit_use_double_quant=True,       # quantise the scales too
    bnb_4bit_compute_dtype=torch.bfloat16 # dequantise to bf16 for the matmul
)
lora = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05,
    target_modules="all-linear",          # adapters on every linear layer
    task_type="CAUSAL_LM",
)
trainer = SFTTrainer(
    model="your-org/your-base-model",
    train_dataset=load_dataset("trl-lib/Capybara", split="train"),
    quantization_config=bnb,
    peft_config=lora,
    args=SFTConfig(
        output_dir="qlora-out",
        learning_rate=1e-4,               # about 10x the full fine-tuning rate
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,
        gradient_checkpointing=True,
        bf16=True,
        model_init_kwargs={"dtype": torch.bfloat16},
    ),
)
trainer.train()
trainer.save_model("qlora-out")           # saves the adapter, not the base model

Other parameter-efficient methods

Parameter-efficient fine-tuning (PEFT) is the umbrella term for methods that train a small number of new or selected parameters. LoRA dominates practice, but you will see others.

MethodWhat it trainsTrade-off
Bottleneck adapters (Houlsby et al., 2019)Small down-project/up-project modules inserted inside each blockCannot be merged away, so they add inference latency; the thing LoRA's parallel form avoids.
Prompt tuning and prefix tuning (Lester et al., 2021; Li and Liang, 2021)Learned vectors prepended to the input or to each layer's keys and valuesTiny and cheap, but they use up context length and are generally less expressive than LoRA at the same size, especially for smaller models.
(IA)3 (Liu et al., 2022)Learned per-channel scaling vectors on keys, values and MLP activationsEven fewer parameters than LoRA; less capacity.
DoRA (Liu et al., 2024)Splits each weight into magnitude and direction and applies LoRA to the directionAims to close the remaining gap to full fine-tuning at no inference cost; adds some training overhead. Gains vary by task, so verify on yours.

For a first project the choice is easy: LoRA or QLoRA on all linear layers, rank 16 to 64, a learning rate near 1e-4 to 2e-4, and a held-out comparison with the base model and with prompting. Reach for anything else only after you can name the specific limit LoRA hit.

Systems connection

An adapter is a small, versioned artefact that changes behaviour without redeploying the base: that is the shape of a configuration change, and it deserves the controls of configuration management: review, staged rollout, rollback. A platform serving one adapter per customer from one shared base is a pool-model multi-tenant system, with the isolation questions of multi-tenancy (which adapter does this request get, and can one tenant's adapter influence another's output?). And the memory arithmetic here, bytes per parameter, activations versus weights, is the same napkin maths as performance engineering.

State of play, October 2026

Findings. "LoRA Without Regret" (Thinking Machines, September 2025) is the most careful recent comparison I could verify: LoRA on all layers matches full fine-tuning on small-to-medium supervised data, falls behind when capacity is exceeded, wants about 10 times the full fine-tuning learning rate, and matches full fine-tuning for policy-gradient reinforcement learning even at rank 1 on the math-reasoning runs they report (their information-theoretic argument is that RL learns few bits per episode; generalisation beyond those tasks is not established). Tools. TRL's SFTTrainer takes peft_config and quantization_config directly (documentation fetched October 2026); the PEFT and bitsandbytes libraries supply the adapter and the 4-bit kernels. Version numbers, supported GPUs and defaults change often: check the current PEFT and bitsandbytes documentation before copying arguments. Rankings of variants such as DoRA against plain LoRA vary between papers and tasks.

Key takeaways

  • LoRA freezes W0 and learns W = W0 + (α/r)BA with r much smaller than the matrix sides. Parameters per matrix: r(din + dout) against din·dout; for Llama 2 7B at r = 16 on all linear layers, 40 million (0.59%).
  • It works because fine-tuning updates occupy few directions (intrinsic dimension) and because B starts at zero. It fails quietly when the update needs more rank than you gave it; error fell slowly with rank for a full-rank update in the experiment.
  • Use all linear layers, size the learning rate for LoRA (about 10 times the full fine-tuning rate, per Thinking Machines), and treat α and rank as tunable rather than universal.
  • LoRA removes gradient and optimiser cost for the base but not its weights or the activations. QLoRA stores the base in NF4 with double quantisation (about 4.1 bits per weight) and dequantises on the fly: a 7B model trains in roughly 8 GB and a 13B in roughly 13 GB under the stated assumptions.
  • Adapters can be merged for zero-latency serving or kept separate to share one base across many variants. Merge in full precision, not into a quantised base.

Check your understanding

A weight matrix is 4,096 × 11,008. A LoRA adapter of rank 32 is added. How many trainable parameters does the adapter have?

  1. About 45 million, the same as the matrix
  2. About 32 thousand
  3. About 0.48 million
  4. About 1.4 million
r(din + dout) = 32 × (4,096 + 11,008) = 32 × 15,104 = 483,328, about 0.48 million, around 1% of the 45.1 million in the matrix. Option 1 is the full matrix; option 2 is r times 1,000; option 4 would be a rank near 93.

Why is B initialised to zero and A to small random values, rather than both to zero?

  1. With B = 0 the adapter starts as a no-op, and B still gets a non-zero gradient from the random A; with both zero, neither would receive any gradient
  2. Zero B makes the adapter faster to compute
  3. Random A makes the final update exactly rank r
  4. Random initialisation of A prevents overfitting
∂L/∂B = s·g(Ax)T needs A to be non-zero; ∂L/∂A = s·(BTg)xT is zero while B is zero, but B moves first and then A follows. Both-zero training would never start. Speed, rank and regularisation are unrelated to the initialisation.

You fine-tune with LoRA at rank 8 on a very large domain dataset and the loss plateaus well above what full fine-tuning reached on a pilot. What is the most plausible explanation and fix?

  1. The learning rate is too high; lower it by a factor of 10
  2. LoRA cannot be used with large datasets at all
  3. The base model is quantised; switch to bf16
  4. The adapter is capacity-limited: raise the rank and apply it to all linear layers, then re-tune the learning rate
Thinking Machines report LoRA underperforms full fine-tuning when the dataset exceeds its capacity, with loss that stops improving at a level tied to the rank; attention-only adapters make it worse. The toy rank experiment shows the same signature. A lower learning rate would not lift a capacity plateau, and the quantisation of the base is not the main limit. LoRA is not forbidden for large data, but it needs enough rank.

Which statement about what QLoRA saves relative to ordinary bf16 LoRA is correct?

  1. It removes the need to store activations
  2. It cuts the memory held by the frozen base weights by roughly a factor of 3.5 to 4, because they are stored in about 4.1 bits instead of 16
  3. It removes the adapter's optimiser state
  4. It makes every forward pass faster
The base weights go from 2 bytes to about 0.52 bytes per parameter. Activations are unchanged (gradient checkpointing handles those), the adapters still carry Adam state, and dequantising before each matrix multiply adds a little compute, so steps are not faster.

A colleague copies a full fine-tuning recipe (learning rate 2e-5) to a LoRA run and reports that "LoRA doesn't learn much". What do you suggest first?

  1. Double the number of epochs
  2. Remove the adapter dropout
  3. Raise the learning rate towards about 10 times the full fine-tuning value (around 1e-4 to 2e-4) and compare
  4. Switch to a prefix-tuning method
The adapter's parameters start at zero or random and need larger steps; Thinking Machines found the optimal LoRA rate about 10 times the full fine-tuning rate. Extra epochs at a too-low rate mostly cost time, dropout is a minor effect, and switching methods before fixing the basic hyperparameter changes too many things at once.

You want to ship a model with a QLoRA adapter merged in, for lowest-latency serving. What is the careful procedure?

  1. Merge the adapter into a bf16 copy of the base, then quantise the merged model if needed and re-evaluate
  2. Add the adapter's B·A directly to the 4-bit weights, which is exact
  3. Never merge; adapters cannot be merged
  4. Merge into the NF4 weights and skip evaluation because the adapter was trained against them
Adding a high-precision update to 4-bit weights rounds the result, so some of the adapter's effect is lost; merging in higher precision first and quantising once keeps the error to a single rounding step. Adapters can be merged (that is a design goal), but whichever route you take you re-run your evaluation, since the shipped weights differ from the ones you trained against.

The KV Cache & the Cost of Decoding

Training a model is a few big runs. Serving it is billions of small ones, and each one has a surprising bottleneck: generating a single token needs almost no arithmetic but moves the whole model through the GPU's memory. This chapter explains the two phases of generation, prefill and decode, why decoding is limited by memory bandwidth, and what the key-value cache costs in bytes.

Why this matters

Chapters 1 to 17 were about making a model. Everything from here on is about running it, and the cost of running it is mostly the cost of one data structure and one ratio. The structure is the key-value (KV) cache, which grows with every token of every conversation and decides how many users fit on a GPU. The ratio is how many arithmetic operations the GPU does for each byte it reads, which for token-by-token generation is tiny, so adding more compute does not make a single stream faster. If you understand these two things you can estimate, before running anything, how much memory a deployment needs, how fast one user's text will arrive, why a long prompt delays the first word but a long answer slows each word, and why every serving technique in chapters 19 to 22 (quantisation, paged caches, batching, speculation) is aimed at memory traffic. After this chapter you will be able to compute a model's cache cost per token, size a deployment on a 24 GB card, draw the roofline argument for decode, and read the batch-size curve of a serving system.

What attention needs from the past

Recall attention from A2. At each position, a token produces a query, key and value vector (three linear projections of its hidden state). Its query is compared with the keys of all earlier tokens to give weights, and the output is the weighted sum of their values. A decoder-only model, such as the GPT of A2 chapter 12, applies a causal mask so a token never looks at later ones. That has a consequence which the whole chapter rests on: once a token's key and value at a given layer are computed, they never change. Later tokens never alter earlier ones, so those vectors can be remembered instead of recomputed. The stored keys and values of all tokens seen so far, at every layer, are the KV cache.

To feel why this matters, compare two ways of generating text with a toy single-layer decoder: one recomputes the keys and values of the entire prefix for every new token, the other stores them. Both must produce exactly the same text, since the cache is an optimisation and not an approximation.

import numpy as np

rng = np.random.default_rng(0)
C, NH, V, N = 64, 4, 50, 40                     # model width, heads, vocabulary, tokens to generate
HD = C // NH
E = rng.normal(0, 0.5, (V, C))                  # embeddings (tied with the output head)
Wq, Wk, Wv, Wo = (rng.normal(0, C ** -0.5, (C, C)) for _ in range(4))
counts = {"projections": 0}

def split(x): return x.reshape(len(x), NH, HD).transpose(1, 0, 2)     # (tokens, C) -> (heads, tokens, HD)

def attend(q, K, Vv):                            # q: (NH, 1, HD); K, V: (NH, T, HD); the new token sees all T keys
    s = q @ K.transpose(0, 2, 1) / np.sqrt(HD)
    w = np.exp(s - s.max(-1, keepdims=True)); w /= w.sum(-1, keepdims=True)
    return (w @ Vv).transpose(1, 0, 2).reshape(1, C)

def next_token_nocache(tokens):                  # recompute K and V for the whole prefix at every step
    x = E[tokens]; counts["projections"] += 2 * len(tokens)
    K, Vv, q = split(x @ Wk), split(x @ Wv), split(x[-1:] @ Wq)
    return (attend(q, K, Vv) @ Wo + x[-1]) @ E.T

def generate(use_cache):
    tokens = [3, 7, 1]; counts["projections"] = 0; Kc = Vc = None; out = []
    for _ in range(N):
        if not use_cache:
            logits = next_token_nocache(tokens)
        else:
            new = E[tokens] if Kc is None else E[tokens[-1:]]            # prefill: whole prompt; decode: one token
            counts["projections"] += 2 * len(new)
            k, v = split(new @ Wk), split(new @ Wv)
            Kc = k if Kc is None else np.concatenate([Kc, k], 1); Vc = v if Vc is None else np.concatenate([Vc, v], 1)
            logits = (attend(split(new[-1:] @ Wq), Kc, Vc) @ Wo + new[-1]) @ E.T
        out.append(int(logits.argmax())); tokens.append(out[-1])
    return out, counts["projections"]

a, na = generate(False); b, nb = generate(True)
print("same generated tokens:", a == b)
print(f"K and V row computations for {N} new tokens after a 3-token prompt: without cache {na:,}, with cache {nb:,} ({na/nb:.0f}x)")
same generated tokens: True
K and V row computations for 40 new tokens after a 3-token prompt: without cache 1,800, with cache 84 (21x)

The generated tokens are identical. Without a cache, generating 40 tokens after a 3-token prompt computes 1,800 key and value rows, because step t recomputes t of them for each of K and V, so the total grows like n²/2 in the length n. With a cache it computes 84: the prompt once, then one new row per step, linear in n. In a real model this saving applies to every layer, and also to everything else those old positions would have needed (the MLP, the layer norms): after a token's keys and values at each layer are stored, nothing else about that token is needed to produce later tokens. The price is memory: those stored vectors have to live somewhere, for as long as the conversation does.

Two phases: prefill and decode

Text generation with a cache has two phases whose cost profiles differ completely.

  • Prefill processes the whole prompt at once. All prompt tokens go through the model in parallel (the attention for each still uses a causal mask), and their keys and values are written to the cache. The last position's output gives the first new token. It is one large batch of matrix products.
  • Decode generates the rest, one token per step. Each step feeds in only the newest token, computes its query, key and value at every layer, appends the key and value to the cache, reads the whole cache to attend, and emits one more token. A reply of 500 tokens takes 500 sequential steps; they cannot run in parallel, because each needs the previous output.

Step through one request to see the difference in what is read and written.

Step through

Prefill, then decode with a growing cache

  1. Prefill. The three prompt tokens go through every layer together. Their keys and values are written to the cache (three cells, highlighted). The model's output at the last position is the first generated token, "on". The time this takes is the time to first token (TTFT). It is large matrix-by-matrix arithmetic that keeps the GPU's compute units busy.
  2. Decode, step 1. Only "on" enters the model. Its own key and value are appended (a fourth cell), and its query attends over all four cells. To do that, the GPU must read every weight of the model and the whole cache from memory, in order to produce a single token.
  3. Decode, step 2. The token "the" enters, a fifth cell is written, and everything is read again: all weights, and now five cells.
  4. Decode, step 3. The same again with six cells. Every step costs a little more than the one before, because the cache is a little longer. The gap between tokens is the inter-token latency, and it is what the reader sees as typing speed.
  5. What a cell costs. For Llama 3 8B, one cell (one token's keys and values at all 32 layers, 8 key-value heads of width 128, in two bytes each) is 128 KiB. A conversation of 4,096 tokens holds 4,096 cells, 537 MB, per user.

Latency in generation is therefore described by two numbers, not one: time to first token (TTFT), set mainly by prefill and so by the prompt length, and inter-token latency (ITL, also called time per output token), set by the decode step. Chat users feel both; a batch job that summarises documents cares about neither and only about total throughput. These are the service-level indicators of an LLM endpoint (SLIs, SLOs and error budgets), and they pull in different directions, as we will see.

How big is the cache?

Count what is stored. Each token, at each layer, stores one key vector and one value vector for each of the key-value heads, each vector of width dhead. With L layers, nkv key-value heads and b bytes per number:

KV bytes per token = 2 × L × nkv × dhead × b

The 2 is for keys and values. The cache of a sequence of n tokens is n times this. The shapes below are from Table 3 of the Llama 3 report (Llama Team, 2024), which describes the 8B, 70B and 405B models as using grouped-query attention with 8 key-value heads. The script reproduces them, then also works out how many 8k-token conversations fit on a 24 GB card.

# Bytes of KV cache per token = 2 (K and V) x layers x kv_heads x head_dim x bytes per number.
# Shapes are from Table 3 of the Llama 3 report (Llama Team, 2024); 128-wide heads = model dim / attention heads.
models = {                      # layers, attention heads, kv heads, model dim
    "Llama 3 8B":   (32,  32, 8,  4096),
    "Llama 3 70B":  (80,  64, 8,  8192),
    "Llama 3 405B": (126, 128, 8, 16384),
}

def kv_bytes_per_token(layers, kv_heads, head_dim, bytes_per=2):
    return 2 * layers * kv_heads * head_dim * bytes_per

print(f"{'model':14} {'per token':>10} {'8k tokens':>10} {'32k':>8} {'128k':>8}   (bf16; KiB = 1,024 bytes, GB = 10^9 bytes)")

Read the numbers slowly. Each token of Llama 3 8B costs 128 KiB of cache, so a conversation with an 8,192-token context holds 1.07 GB, and one with 128,000 tokens holds about 17 GB, more than the 16 GB of the model's own weights. The 405B model is worse in absolute terms (504 KiB per token, 67.6 GB at 128k) though not per parameter: its cache per token is only about four times that of the 8B model, while its weights are 50 times larger. The parameter count the script derived from the shapes (8,030,261,248) agrees with the model's published size, which is a useful check that the shapes are right.

What fits on one 24 GB card

On a 24 GB card (an L4-class data-centre card, or a consumer card of the same memory size), the 8B model in bf16 takes 16.06 GB. Assume 2 GB for activations and the CUDA context. That leaves 5.94 GB for cache, which is 45,315 tokens in total: five and a half 8k conversations, or one and a half 32k conversations, across all users at once. Store the cache in 8 bits per number and these double; we will come back to that trade in chapter 19.

Shrinking the cache by design

Because the formula multiplies the number of key-value heads, the cheapest way to shrink the cache is to have fewer of them. In standard multi-head attention every query head has its own key and value head. Shazeer (2019), in "Fast Transformer Decoding: One Write-Head is All You Need", proposed multi-query attention (MQA): all query heads share a single key-value head, which greatly reduces the memory traffic of incremental decoding. Ainslie et al. (2023), in "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints", introduced grouped-query attention (GQA), an intermediate number of key-value heads, and showed that a multi-head checkpoint can be converted with about 5% of the original pre-training compute to reach quality close to multi-head attention with speed comparable to MQA. A2 chapter 19 covers the mechanism; here we care about the bytes.

Other designs go further. DeepSeek-V2 (DeepSeek-AI, 2024) uses multi-head latent attention, which compresses keys and values into a low-dimensional latent vector; its report states a 93.3% reduction of the KV cache against their earlier dense 67B model, alongside other architectural changes, so the saving is not attributable to the latent compression alone. Sliding-window attention keeps only the last W tokens in the cache for some layers. Chapters 19 and 20 cover the serving-side measures: storing the cache in fewer bits, managing it in pages, and sharing it between requests with a common prefix.

Analogy: an open-book exam with index cards

You are answering a long exam question one sentence at a time, and each sentence may need a fact from any earlier page of your notes. Without a cache, before writing each sentence you re-read all your notes from page one and rewrite your summary of every page. With a cache, you made one index card per page the first time through, and now you read the stack of cards. That is much less work per sentence, but the stack of cards grows with the length of the exam, and you must carry all of it to the desk.

Where it breaks down: an index card is written once and is the same for everyone. A KV cache is per conversation and per layer, with its own stack at each of the model's dozens of layers, so a server with a hundred conversations carries a hundred separate stacks, and the stack cannot be shared with another reader unless the two start with an identical prefix.

Why decoding is limited by memory

A GPU has two kinds of limit (GPUs and memory bandwidth in Systems). It can do a certain number of arithmetic operations per second, its compute peak, and it can move a certain number of bytes per second between its main memory (HBM, high-bandwidth memory) and its compute units, its bandwidth. A job is limited by whichever it hits first. The ratio of the two, FLOPs per byte, is the machine's ridge point, and the ratio of a job's FLOPs to the bytes it moves is its arithmetic intensity. Williams, Waterman and Patterson (2009) drew this as the roofline model: attainable speed is the smaller of the compute peak and bandwidth times intensity.

Now count the work in one decode step for a model with P parameters in bf16 (2 bytes each) and a batch of one sequence. Every weight takes part in one multiply and one add for the new token, so about 2P FLOPs. Every weight must be read from HBM once, so about 2P bytes. The intensity is about 1 FLOP per byte. Compare that with the machine's ridge point from NVIDIA's datasheets: an H100 SXM has 3.35 TB/s of memory bandwidth and, as the datasheet puts it, 1,979 TFLOPS of bf16 tensor throughput with sparsity, so about 989 TFLOPS without. The ratio is 295 FLOPs per byte. Decode at batch one runs at an intensity of 1: about 300 times too little arithmetic to keep the compute units busy. The GPU spends its time waiting for weights to arrive.

Two consequences follow, and you can compute both. First, the speed of a single stream is bounded by bandwidth: each token requires reading 2P bytes, so tokens per second cannot exceed bandwidth divided by 2P. Second, prefill has the opposite profile: a prompt of n tokens reuses each weight n times, so its intensity is about n, and at n above about 300 on an H100 it is compute-bound. The script below applies both to Llama 3 8B on the H100 and on the L4, then extends to batches.

# Decode and prefill limits for Llama 3 8B (bf16) from published GPU specs.
P, L, HID, KVTOK = 8.03e9, 32, 4096, 131072          # parameters, layers, model dim, KV bytes per token
gpus = {                                              # name: (HBM bandwidth B/s, dense bf16 FLOP/s). NVIDIA datasheets:
    "H100 SXM": (3.35e12, 989e12),                    #   1,979 TFLOPS "with sparsity" -> half without
    "L4":       (0.300e12, 121e12),                   #   242 TFLOPS "with sparsity" -> half without
}
print(f"{'GPU':9} {'ridge FLOP/B':>12} {'1 token/s bound':>16} {'2k-token prefill (100% / 50% of peak)':>40}")
for g, (bw, fl) in gpus.items():
    t_dec = 2 * P / bw                                # batch 1: read every weight once per token
    t_pre = 2 * P * 2000 / fl                         # 2 FLOPs per parameter per prompt token
    print(f"{g:9} {fl/bw:12.0f} {1/t_dec:12.1f} tok/s {t_pre*1e3:14.0f} ms / {2*t_pre*1e3:.0f} ms")

# Decode step for a batch of B sequences of context n on an H100: weights are read once, every KV cache is read once.
bw, fl = gpus["H100 SXM"]
print(f"\nH100, one decode step, tokens/s (cap = sequences that fit in 72 GB after weights)")
print(f"{'batch':>6} " + " ".join(f"{'ctx '+str(n):>10}" for n in (512, 4096, 32768)))
for B in (1, 4, 16, 64, 128):
    row = []
    for n in (512, 4096, 32768):
        cap = int((72e9 - 2 * P) / (n * KVTOK))
        if B > cap: row.append(f"{'no fit':>10}"); continue
        t_mem = (2 * P + B * n * KVTOK) / bw
        t_cmp = B * (2 * P + 4 * L * HID * n) / fl
        row.append(f"{B / max(t_mem, t_cmp):10,.0f}")
    print(f"{B:6d} " + " ".join(row))

An H100 cannot generate more than about 209 tokens a second for a single stream of the 8B model, and the L4, with a ninth of the bandwidth, no more than about 19, whatever its arithmetic capacity. These are bounds from the datasheet bandwidth; a real server also pays for kernel launches, attention, sampling and communication and reaches a fraction of them (I have not measured this here). A 2,000-token prefill needs at least 32 ms of arithmetic on the H100 at the datasheet peak, and 65 ms if we assume it reaches half of the peak, an assumed figure, not a measurement. Notice the asymmetry: the same model takes about 5 ms per generated token but spends about 32 ms to read a 2,000-token prompt, which is why a long prompt delays the first word while the length of the answer determines the pace afterwards.

Common misconception

"A GPU with twice the arithmetic speed will generate text twice as fast." For a single stream, decode is limited by bandwidth, so doubling the compute changes almost nothing, while doubling the memory bandwidth nearly doubles the speed. This is why inference-oriented hardware advertises bandwidth and memory capacity as prominently as FLOPs, why a card with more compute and less memory bandwidth can be a worse choice for serving, and why quantising weights (fewer bytes to read) speeds up decoding even though it adds work to unpack them.

Batching makes weights cheap, and the cache expensive

If decode is limited by reading weights, the remedy is to use each read for many sequences at once. Serve B conversations in the same step: the weights are read once, and each of the B tokens uses them. Intensity rises by a factor of B and so does throughput. That is the reason serving engines batch, and the points for batches 16 and 64 on the roofline move up and to the right. But the cache does not batch. Each sequence has its own, and in every step each sequence's whole cache is read. So a decode step for B sequences of context n moves

bytes per step ≈ 2P (weights, once) + B × n × (KV bytes per token) (caches, one each)

and takes at least that many bytes divided by the bandwidth. The weights term is fixed; the cache term grows with both B and n. The second table in the output above evaluates this for the 8B model on an H100, with an arithmetic term included for completeness, at three context lengths. The picture below plots it.

Work through the 4,096-token curve. One sequence's cache is 4,096 × 128 KiB = 537 MB, against 16.06 GB of weights, so the weights are as expensive as about 30 caches. Below 30 sequences the weights dominate the step time and every added sequence is nearly free: throughput almost doubles when the batch doubles. Above it, the caches dominate, each added sequence adds its 537 MB to the bytes read per step, and throughput approaches its ceiling of bandwidth divided by one sequence's cache bytes, 3.35 TB/s over 537 MB, about 6,240 tokens a second, however many sequences you add. Meanwhile memory runs out at 104 sequences. The arithmetic term never matters here: the per-sequence compute (about 18 GFLOPs) takes 18 microseconds on this H100, against 160 microseconds to read its cache. At long contexts, a decoding GPU is limited by the KV cache, not by the weights and not by the arithmetic.

What goes wrong

  • Out of memory in the middle of a reply. The cache grows with every generated token, and nobody knows in advance how long the reply will be. A server that reserves space for the maximum length of every request wastes most of it; one that reserves nothing can run out while streaming. Kwon et al. (2023) argue in the vLLM paper that poorly managed cache memory wastes much of it through fragmentation and duplication, and that waste limits the batch size and with it the throughput; their remedy, paged cache blocks borrowed from operating-system virtual memory, is the subject of chapter 20 and Case 4.
  • One long request hurts everyone. A single 100k-token prompt both occupies a large part of the cache and, during its prefill, delays the decode steps of the others if they share the GPU. Tail latency (tail latency at scale) is dominated by these rare long requests, and admission control (load shedding) usually has to count tokens, not requests.
  • The cache is lost when the prefix changes. Two requests share cache entries only if they begin with exactly the same tokens. Putting a timestamp or a user name at the start of a prompt makes every request unique and throws away any chance of reuse. Prompt design is cache design (chapter 20 on prefix caching).
  • Mixing the metrics. Raising the batch size improves total throughput and worsens inter-token latency, because each step has more to read. A system tuned for tokens per dollar may miss its latency target. Choose the target first (chapter 22).
  • Trusting a quantised cache blindly. Storing keys and values in 8 or 4 bits doubles or quadruples the capacity, and may cost accuracy on long-context tasks. Measure on your own long-context evaluations (chapters 19 and 23).

Systems connection

Everything here is the memory hierarchy again, one level out: the registers and caches of the GPU's compute units are small and fast, HBM is large and about a hundred times slower, and the program that never reuses what it fetches is limited by the slow level. A KV cache that grows with every user is a classic capacity-planning object: you size it from the per-token byte count, the number of concurrent sessions and their length distribution, test the saturation point (load testing and capacity planning), and queue or shed beyond it (queueing theory). The numbers differ; the method is the same one you would use for connections or file descriptors.

Key takeaways

  • In a causal decoder, a token's keys and values never change, so they are stored: the KV cache turns n² recomputation into n and is exact, not approximate.
  • Generation has two phases: prefill (the whole prompt in parallel, compute-bound, sets time to first token) and decode (one token per step, memory-bound, sets inter-token latency).
  • Cache bytes per token = 2 × layers × kv heads × head width × bytes per number: 128 KiB for Llama 3 8B, and 17 GB at 128k tokens, more than its weights.
  • Decode at batch one performs about 1 FLOP per byte read, against a ridge point near 300 on an H100, so speed follows memory bandwidth, not FLOPs: at most about 209 tokens/s for the 8B model on an H100, and about 19 on an L4.
  • Batching shares one weight read across sequences, but every sequence reads its own cache, so at long contexts throughput saturates at bandwidth divided by one cache, and memory capacity ends the growth sooner.
  • Grouped-query attention (and other designs) shrink the cache by sharing keys and values; quantisation, paging and prefix sharing, next, attack the same bytes from the serving side.

Next comes quantisation, which shrinks both terms of the decode step, the weights and (optionally) the cache, at some cost in accuracy. Lab 6 builds a serving simulator with a paged cache in which these numbers become the capacity limit, and Studio 3 asks you to size a platform with them.

Why is generating one token for a single user on a modern GPU limited by memory bandwidth and not by arithmetic?

  1. Because the attention softmax is slow to compute
  2. Because tokens must be sent over the network
  3. Because the GPU's cores cannot run matrix multiplications on a single vector
  4. Because each step reads every weight to do only about two operations per weight, far below the roughly 300 FLOPs per byte the chip could sustain
A decode step at batch one has an intensity near 1 FLOP per byte, against a ridge point near 300 on an H100, so the compute units wait for weights. Softmax and networking are small costs; the cores can multiply a vector perfectly well, they just do very little arithmetic per byte fetched.

A model is changed from 32 key-value heads to 8, with everything else equal (including the 32 query heads). What happens to the cache and what to the weights?

  1. The cache falls to a quarter; the weights fall slightly, because the key and value projections get smaller
  2. The cache falls to a quarter; the weights are unchanged
  3. The cache is unchanged; the weights fall to a quarter
  4. Both fall to a quarter
The cache holds one key and value vector per key-value head, so 8 instead of 32 is a factor of 4. The key and value projection matrices also shrink, because they output nkv × dhead numbers, but they are a small share of the total weights, so the weights fall only a little.

On an H100 with an 8B model at a 4,096-token context, throughput stops improving long before memory runs out. In the model of this chapter, what is the main reason?

  1. The weights have become too large to read
  2. The GPU has run out of arithmetic capacity
  3. Each added sequence adds its own cache traffic to every step, which comes to dominate the bytes read once the batch is larger than about 30
  4. The batch is limited by the network
The weights are read once per step whatever the batch, and the arithmetic per sequence is far below the roofline. What grows with the batch is the sum of all the caches read per step. Once that exceeds the 16 GB of weights, throughput approaches bandwidth divided by one sequence's cache and flattens.

A product team complains that users wait a long time before the first word appears, but once the text starts it streams quickly. Which phase is the likely culprit and what is the most direct lever?

  1. Decode; use a smaller KV cache
  2. Decode; add more key-value heads
  3. Prefill; raise the batch size so that more users share each step
  4. Prefill; shorten or cache the prompt (for example reuse a shared prefix), or give prefill more compute
Time to first token is set by prefill, which scales with the prompt length and is compute-bound; once decoding starts the pace is the inter-token latency, which is fine here. Long shared system prompts are the classic fix via prefix caching. A larger batch would not help one user's prefill and may hurt it.

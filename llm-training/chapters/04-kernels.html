Kernels & Performance

A GPU is fast at arithmetic and slow at fetching the numbers to do arithmetic on. This chapter explains why most of a transformer's operations are limited by memory traffic rather than by maths, why combining several small operations into one fused kernel removes that traffic, and what a first Triton kernel looks like.

Why this matters

The previous chapters counted what a training run must store (chapter 02) and how it spreads over many GPUs (chapter 03). This chapter is about what happens inside one GPU: why a run reaches only 40 percent of the chip's advertised arithmetic speed even when everything is well parallelised. After it you will be able to tell a memory-bound operation from a compute-bound one with one division, explain why FlashAttention and torch.compile exist, and read a simple Triton kernel. You will not be expected to write production kernels; that is a specialist job, but knowing what the specialists are doing tells you where your own time goes.

The cost that does not appear in the FLOP count

Chapter 16 of A2 counted a model's work in FLOPs (floating-point operations). That count answers "how much arithmetic?" but not "how long?". A chip finishes a job when both of two things are done: the arithmetic, and the movement of the data that the arithmetic reads and writes. Whichever takes longer sets the time.

A GPU has two places to keep numbers. HBM (high-bandwidth memory) is the large off-chip memory, 80 GB on an H100, where weights and activations live between operations. On-chip memory (registers and shared memory, also called SRAM) sits inside each processor, is orders of magnitude smaller (hundreds of kilobytes per processor) and is far faster. Every operation must bring its inputs from HBM into the chip and, unless something else consumes them immediately, write its results back.

NVIDIA's datasheet for the H100 SXM lists 80 GB of HBM3 at 3.35 TB/s and 989 TFLOPS of dense bf16 tensor-core arithmetic (the headline 1,979 figure assumes structured sparsity, which training rarely uses). Divide the two: 989 trillion FLOP/s over 3.35 trillion bytes/s is about 295 FLOP per byte. To keep the arithmetic units busy, a program must do about 295 operations for every byte it fetches from HBM. This number is the chip's ridge point.

Most operations in a network do far fewer than 295. Take an elementwise operation such as adding a bias or applying a GELU. It reads each value (2 bytes in bf16), does a handful of operations, and writes the value back (2 bytes): one or two FLOP per four bytes, well under 1 FLOP per byte. The GPU spends nearly all its time waiting for memory and nearly none computing. The quantity that decides this, arithmetic intensity, is simply FLOPs divided by bytes moved to and from HBM. An operation with intensity below the ridge point is memory-bound; above it, compute-bound.

This explains a fact that surprises newcomers: the large matrix multiplications of a transformer are compute-bound and run near peak, but the layers around them (normalisation, softmax, activation functions, residual adds, dropout, the cast between precisions) are memory-bound, and added together they can take a large share of the step time. In A2's training chapters and in efficient attention the same split appears: FlashAttention's gain is not fewer FLOPs but less HBM traffic.

Why one kernel beats three

A kernel is a function that runs on the GPU, launched from the CPU, across thousands of threads. In plain PyTorch each operation you write is, by default, its own kernel. The expression y = relu(x * 1.5 + 0.5) launches three kernels. Each one reads its input array from HBM and writes a whole new array back. The intermediate arrays exist only so that the next kernel can read them again.

A fused kernel does all three steps while the value is still in a register: read x once, multiply, add, apply ReLU, write y once. The arithmetic is identical; the memory traffic drops from six passes (three reads, three writes) to two. For an operation limited by bandwidth, time is proportional to bytes, so the saving is close to proportional to the passes removed. Fusion also removes the cost of launching kernels (a few microseconds each, which matters when the kernel itself runs in tens of microseconds) and the memory for the intermediate arrays.

Measuring it

You do not need a GPU to see the effect, because every modern CPU has the same two-level structure: a large, slow main memory and a small, fast cache. The script below applies a chain of six cheap operations to 134 million float32 values (512 MiB). The unfused version is ordinary NumPy, which makes a full-size temporary array at each step. The fused version processes the array in blocks of 512 KiB so that the temporaries stay in cache, which is the same idea as keeping values on chip. Both produce identical results (the script asserts it).

import time
import numpy as np

N = 1 << 27                       # 134 million float32 values = 512 MiB
x = np.random.default_rng(0).standard_normal(N, dtype=np.float32)
f = np.float32

def unfused(x):                   # six separate passes over memory
    t = x * f(1.5)                # read x, write t
    t = t + f(0.5)                # read t, write t
    t = t * t
    t = t - f(1)
    t = t + x                     # reads two arrays
    return np.maximum(t, 0)

def fused(x, block=1 << 17):      # 131,072 floats = 512 KiB, small enough for cache
    y = np.empty_like(x)
    buf = np.empty(block, dtype=np.float32)
    for i in range(0, len(x), block):
        xs = x[i:i + block]
        t = buf[:len(xs)]
        np.multiply(xs, f(1.5), out=t)
        t += f(0.5); t *= t; t -= f(1); t += xs
        np.maximum(t, 0, out=y[i:i + block])
    return y

def best(g, reps=5):
    times = []
    for _ in range(reps):
        t0 = time.perf_counter(); g(x); times.append(time.perf_counter() - t0)
    return min(times)

assert np.array_equal(unfused(x), fused(x))
tu, tf = best(unfused), best(fused)
gib = lambda n: n * 4 / 2**30
print(f"unfused: {gib(13*N):.1f} GiB moved, best of 5 = {tu*1e3:.0f} ms")
print(f"fused:   {gib(2*N):.1f} GiB moved, best of 5 = {tf*1e3:.0f} ms")
print(f"traffic ratio {13/2:.1f}x, measured time ratio {tu/tf:.2f}x")

# The same chain on an H100 SXM, using NVIDIA's datasheet figures.
peak, bw = 989e12, 3.35e12        # dense bf16 FLOP/s, HBM3 bytes/s
print(f"\nH100 ridge point: {peak/bw:.0f} FLOP per byte")
print(f"chain intensity, fused: 6 FLOP / 8 bytes = {6/8:.2f} FLOP per byte")
print(f"1 Gi values, bandwidth floor: unfused {13*2**30*4/bw*1e3:.1f} ms, fused {2*2**30*4/bw*1e3:.1f} ms")
print(f"1 Gi values, compute floor: {6*2**30/peak*1e3:.4f} ms")

fused:   1.0 GiB moved, best of 5 = 78 ms
traffic ratio 6.5x, measured time ratio 1.17x

H100 ridge point: 295 FLOP per byte
chain intensity, fused: 6 FLOP / 8 bytes = 0.75 FLOP per byte

1 Gi values, compute floor: 0.0065 ms

The output below came from a laptop with an Apple-silicon chip and NumPy 2.x. Read it carefully, because it contains a lesson. The fused version moves 6.5 times less data by the count in the script, but ran only about 1.2 times faster here. Two reasons. First, this laptop has a large cache and very fast unified memory, so its ridge point is low and the unfused version was not as starved as a GPU would be. Second, the fused loop runs in Python and pays interpreter overhead per block, and NumPy still makes a separate pass for each step inside a block. Real fusion happens in the compiler, per element, in registers. The traffic ratio is a ceiling on the gain for a bandwidth-bound operation, not a prediction of it. Your numbers will differ; run the script yourself.

The last four lines apply the roofline to an H100. For a billion values the unfused chain needs at least 16.7 ms just to move bytes at 3.35 TB/s, the fused one 2.6 ms, and the arithmetic itself would take 0.0065 ms. The arithmetic is irrelevant; the whole cost is traffic. These are floors from the datasheet bandwidth: real kernels reach perhaps 70 to 90 percent of peak bandwidth (an assumption that depends on the kernel and the chip, so measure it).

Common misconception

"A faster GPU, or fewer FLOPs, makes every layer faster." Only compute-bound operations get faster with more arithmetic throughput. A memory-bound layer on a chip with twice the FLOPs and the same bandwidth takes exactly as long. This is why model FLOPs utilisation (MFU), the fraction of peak arithmetic achieved, stays well below 100 percent even in excellent runs: Llama 3 405B reported 38 to 43 percent of peak bf16 on up to 16,384 H100 GPUs (Dubey et al., 2024), and the shortfall comes from memory-bound operations, communication and waiting (the paper does not give a breakdown).

Getting fusion without writing it

Most engineers get fused kernels from tools, in rising order of effort.

  • Library kernels. Frameworks ship fused versions of the common patterns: fused optimiser steps (AdamW updates all parameters in a few kernels instead of one per tensor), fused layer normalisation, and fused attention (FlashAttention, Dao et al., 2022, "FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness"). Turning these on is often a configuration flag, and it is the cheapest win in this chapter.
  • torch.compile. PyTorch 2 captures a model's operations as a graph and generates fused kernels for the memory-bound stretches automatically, using Triton as its GPU code generator (Ansel et al., 2024, "PyTorch 2"). You wrap a function or module and keep writing ordinary PyTorch. The costs are compile time at the start, occasional recompilation when shapes change, and harder debugging.
  • A custom kernel in Triton or CUDA. Worth it when profiling shows one operation dominating and no library covers it. This is where the remainder of this chapter points.

A first look at Triton

CUDA is NVIDIA's programming model: you write what one thread does, and manage groups of threads, shared memory and synchronisation by hand. Triton (Tillet, Kung and Cox, 2019, "Triton: an intermediate language and compiler for tiled neural network computations") raises the level. You write Python-syntax code for a block of values at once, and the compiler decides how threads, registers and shared memory implement it. Each running copy of the kernel is a program, identified by tl.program_id; it handles a block of BLOCK_SIZE consecutive elements.

Below is the fused chain from the benchmark, as a Triton kernel with its launch. It is a listing, not output from this machine: Triton needs a supported GPU, which the machine used for this chapter does not have.

import torch
import triton
import triton.language as tl

@triton.jit
def chain_kernel(x_ptr, y_ptr, n, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(axis=0)                  # which block am I?
    offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n                           # last block may be partial
    x = tl.load(x_ptr + offsets, mask=mask)      # one read from HBM
    t = x * 1.5 + 0.5                            # all of this stays in registers
    t = t * t - 1.0 + x
    y = tl.maximum(t, 0.0)
    tl.store(y_ptr + offsets, y, mask=mask)      # one write to HBM

def chain(x):
    y = torch.empty_like(x)
    n = x.numel()
    grid = (triton.cdiv(n, 1024),)               # number of programs
    chain_kernel[grid](x, y, n, BLOCK_SIZE=1024)
    return y

Three ideas carry over to every Triton kernel. The grid says how many programs to launch (here one per 1,024 values). Each program computes its slice of indices from its id and uses a mask so it never touches memory past the end of the array. And memory is touched only by explicit tl.load and tl.store calls: everything between them is on chip. The official fused-softmax tutorial counts the saving for a row-wise softmax over an M by N matrix: the unfused PyTorch version moves about 8MN + 4M elements and the fused kernel 2MN, a ratio approaching 4 for large N (Triton documentation, "Fused Softmax"). Softmax needs a reduction (a row maximum and a row sum), which is why it is a better second kernel to study than an elementwise one.

State of play, October 2026

Triton is open source and developed in the open (triton-lang.org); kernels written for it are portable across NVIDIA and, with backend work, AMD GPUs, though tuning is per chip. Several newer kernel languages and tile-based programming models exist, and NVIDIA ships its own Python kernel tooling; which will matter in three years is unsettled, so treat Triton as the clearest way to learn the ideas rather than the final word. GPU numbers above are from the NVIDIA H100 datasheet; newer chips have higher bandwidth and different ridge points, and you should recompute the ridge point (FLOP/s divided by bytes/s) for whatever hardware you use.

Try it yourself

Run fuse.py, then change the block size from 131,072 to 4,096 and to 4,194,304 and observe the time. Very small blocks lose to interpreter overhead; very large ones no longer fit in cache and the fused version converges to the unfused one. Then compute the ridge point for a chip you can look up (for example an A100 80 GB: 312 TFLOPS dense bf16 and about 2 TB/s) and decide whether a LayerNorm over 4,096 values, which does roughly 10 FLOP per element on 2-byte inputs, is memory-bound there.

$ python3 fuse.py
$ python3 -c "print(312e12 / 2.0e12)"

Key takeaways

  • Time is set by the slower of arithmetic and memory traffic. Arithmetic intensity (FLOP per byte of HBM traffic) against the chip's ridge point (about 295 for an H100 in bf16) says which.
  • Large matrix multiplications are compute-bound; normalisation, activations, softmax, residual adds and casts are memory-bound.
  • Fusion keeps intermediate values on chip, cutting HBM traffic and kernel launches without changing the maths.
  • Use library fused kernels and torch.compile first; write a Triton kernel when profiling points at one operation.
  • Traffic ratios are ceilings, not predictions: measure on your hardware.

Check your understanding

An H100 has about 989 TFLOPS of dense bf16 arithmetic and 3.35 TB/s of memory bandwidth. An elementwise operation reads and writes bf16 values and does 2 FLOP per element. Which statement is correct?

  1. It is compute-bound, because the GPU has far more arithmetic throughput than the operation needs
  2. It is memory-bound: it does 2 FLOP per 4 bytes, far below the ridge point of about 295 FLOP per byte
  3. It is balanced, because 2 FLOP is close to the ridge point
  4. It cannot be classified without knowing the batch size
Intensity is 0.5 FLOP per byte against a ridge point near 295, so the memory system is the limit. The first option reads the same fact backwards: spare arithmetic throughput is exactly what idles when memory is the bottleneck.

You fuse five elementwise operations into one kernel. Which effect should you expect?

  1. The FLOP count falls to a fifth
  2. The results change slightly because the order of operations changes
  3. The speed is unchanged, because the same arithmetic is done
  4. HBM traffic and kernel launches fall, while the arithmetic stays the same
Fusion removes the writes and re-reads of intermediate arrays and the extra launches. FLOPs are unchanged (the third option mistakes FLOPs for time), and for the simple operations here the numbers are the same.

The fused NumPy version moved 6.5 times less data than the unfused one but ran only about 1.2 times faster. What is the best reading?

  1. The traffic ratio is a ceiling for a bandwidth-bound operation; caches, interpreter overhead and passes inside each block keep the real gain lower
  2. Fusion does not work on CPUs
  3. The unfused version must have been buggy
  4. The benchmark proves fusion is rarely worth it on GPUs either
The script asserts that results match, so the unfused version is correct. The effect is real but smaller than the ideal ratio on this machine; a GPU, whose ridge point is far higher, is much more sensitive to traffic.

In the Triton kernel, why does it compute mask = offsets < n and pass it to tl.load and tl.store?

  1. To skip elements that are zero and save arithmetic
  2. To make the kernel deterministic
  3. Because the last block may extend past the end of the array and must not read or write out of bounds
  4. To tell the compiler which values to keep in registers
The grid is rounded up to whole blocks, so when n is not a multiple of BLOCK_SIZE the final program has indices beyond the array. The mask stops those accesses. It does not test values for zero and has nothing to do with register allocation.

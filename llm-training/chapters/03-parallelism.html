Parallel Training

One GPU cannot hold a large model's training state, and even if it could, it would take years to finish. This chapter explains how work and memory are split across many GPUs: data parallelism, ZeRO and FSDP, tensor, pipeline and sequence parallelism, and what each costs in network traffic. The question is always the same: what do you split, and what must the GPUs say to each other because of it?

Why this matters

The last chapter showed that a 7B-class model needs about 105 GB of training state, more than any single GPU holds. Parallelism is how that problem is solved, and also how a training run that would take years takes days. But every way of splitting a model creates communication, and communication is slower than computation. Choosing a split is choosing which wire your training will wait on. After this chapter you will be able to read a parallelism configuration such as "TP 8, PP 16, DP 8", predict which dimension is bound by which network, and explain why the combination was chosen.

Two reasons to use many GPUs

The first reason is memory, covered in chapter 2: the model states do not fit. The second is time. Chapter 16 of A2 gave the rule that training takes about 6·N·D floating-point operations for N parameters and D tokens. Take a 7-billion-parameter model on 2 trillion tokens and one H100 running at 40 percent of its dense bf16 peak (the 989 TFLOPS dense figure is half the sparse number on NVIDIA's page; 40 percent is within the 38 to 43 percent that Llama 3 reported):

6 × 7×109 × 2×1012 = 8.4×1022 FLOPs  →  8.4×1022 / (0.4 × 989×1012) ≈ 2.1×108 seconds

That is about 2,460 days, nearly seven years, on one GPU. On 1,024 GPUs with perfect scaling it is 2.4 days. The word "perfect" is doing a lot of work: no real run scales perfectly, because GPUs must exchange information, and the rest of this chapter is about how much and how often.

The vocabulary of communication

GPUs in a cluster exchange data with collective operations, library calls that involve a whole group of devices (NVIDIA's NCCL library is the usual implementation). Three matter here:

  • All-reduce: every GPU holds a tensor; afterwards every GPU holds the element-wise sum (or average) of all of them.
  • Reduce-scatter: the same sum is computed, but each GPU keeps only its 1/N slice of the result.
  • All-gather: each GPU holds a slice; afterwards every GPU holds the full concatenation.

An all-reduce is exactly a reduce-scatter followed by an all-gather. The standard algorithm arranges the N GPUs in a ring. In reduce-scatter, the tensor is cut into N chunks; for N − 1 steps each GPU sends one chunk to its right neighbour, which adds it to its own copy of that chunk. After N − 1 steps each GPU holds the full sum of one chunk. All-gather then circulates the finished chunks for another N − 1 steps. Each GPU sends 2(N − 1)/N times the tensor size in total, almost 2× for large N, independent of N. That independence is why data-parallel training scales to thousands of GPUs. The code simulates a ring and counts the traffic.

Before the details, here is the whole map. Each technique cuts the same network along a different axis, and each leaves a different thing to communicate.

Data parallelism

Data parallelism (DP) is the simplest split and the one to try first. Every GPU holds a full copy of the model and processes a different slice of the batch. Each computes gradients for its slice; the gradients are averaged across GPUs with an all-reduce; then every GPU applies the identical update, so the copies stay identical. Because the loss is an average over examples, the average of per-slice gradients equals the gradient of the whole batch. The simulation below checks both that and the traffic formula (4 workers, 8 examples each):

import numpy as np
rng = np.random.default_rng(0)
N, D = 4, 12                                   # 4 workers, 12 gradient numbers
X = rng.normal(size=(32, D)); y = rng.normal(size=32); w = rng.normal(size=D)

def grad(Xb, yb): return 2 * Xb.T @ (Xb @ w - yb) / len(yb)
local = [grad(X[i*8:(i+1)*8], y[i*8:(i+1)*8]) for i in range(N)]     # each worker: its own 8 examples
full = grad(X, y)

def ring_allreduce(chunks_per_rank):
    """chunks_per_rank[r] is a list of N arrays. Returns result per rank and floats sent per rank."""
    data = [[c.copy() for c in rank] for rank in chunks_per_rank]
    sent = [0] * N
    for step in range(N - 1):                  # reduce-scatter: pass partial sums around the ring
        msgs = [(r, (r - step) % N, data[r][(r - step) % N].copy()) for r in range(N)]
        for r, idx, payload in msgs:
            dst = (r + 1) % N
            data[dst][idx] += payload; sent[r] += payload.size
    for step in range(N - 1):                  # all-gather: pass finished chunks around the ring
        msgs = [(r, (r + 1 - step) % N, data[r][(r + 1 - step) % N].copy()) for r in range(N)]
        for r, idx, payload in msgs:
            dst = (r + 1) % N
            data[dst][idx] = payload; sent[r] += payload.size
    return data, sent

out, sent = ring_allreduce([np.split(g, N) for g in local])
avg = [np.concatenate(o) / N for o in out]
print("all ranks agree:", all(np.allclose(avg[0], a) for a in avg))
print("equals full-batch gradient:", np.allclose(avg[0], full))
print(f"floats sent per rank: {sent[0]}  (formula 2(N-1)/N * D = {2*(N-1)/N*D:.0f})")
all ranks agree: True
equals full-batch gradient: True
floats sent per rank: 18  (formula 2(N-1)/N * D = 18)

Every rank sent 18 numbers, exactly 2(N − 1)/N × D for N = 4 and D = 12. Frameworks overlap this all-reduce with the backward pass, sending the gradients of late layers while earlier layers are still being differentiated, so on a fast network most of it is hidden.

The limit of DP is the one chapter 2 found: every GPU holds the whole model state. DP buys speed, not capacity. For a 7B model with Adam that is 105 GB on every GPU, so plain DP does not work on 80 GB cards. The remaining techniques split the model itself.

ZeRO and FSDP: sharding the redundant copies

Look at what plain DP stores: N identical copies of the weights, gradients and optimiser state. That is pure redundancy. Rajbhandari et al. (2019) proposed the Zero Redundancy Optimizer (ZeRO): keep the programming model of data parallelism but give each GPU only a 1/N share of the state, fetching the rest only when needed. It comes in three stages, each sharding one more category:

StageWhat is sharded across N GPUsExtra communication
ZeRO-1Optimiser state (the 12 bytes per parameter)None beyond plain DP
ZeRO-2Optimiser state and gradientsNone beyond plain DP
ZeRO-3 (FSDP)Optimiser state, gradients and the weights themselvesAbout 1.5× plain DP

How can ZeRO-1 and ZeRO-2 be free? Plain DP's all-reduce is a reduce-scatter plus an all-gather. In ZeRO-2 each GPU owns a shard of the optimiser state, so after the reduce-scatter it holds just the gradients for its own shard, updates its slice of the weights, and the all-gather then distributes the updated weights. The same two collectives, the same 2Ψ volume (Ψ is the parameter count), now doing the work of the update as well. ZeRO-3 shards the weights too, so each GPU must all-gather a layer's weights just before using it in the forward pass, discard them, and gather them again for the backward pass, and then reduce-scatter the gradients. That is three transfers of Ψ instead of two, the 1.5× in the paper. PyTorch's FSDP (Fully Sharded Data Parallel; Zhao et al., 2023) implements the ZeRO-3 idea. Here are the per-GPU memory numbers from the stage definitions, for the 7.5-billion-parameter example the ZeRO paper uses, followed by the traffic and time arithmetic:

def per_gpu_gb(psi_b, nd, stage, k=12):
    """ZeRO paper section 5: model-state GB per GPU. psi_b = parameters in billions, nd = data-parallel degree."""
    w, g, o = 2 * psi_b, 2 * psi_b, k * psi_b
    if stage >= 1: o /= nd
    if stage >= 2: g /= nd
    if stage >= 3: w /= nd
    return w + g + o

Common misconception

"ZeRO and FSDP are a form of model parallelism." They are data parallelism with the redundancy removed. Every GPU still runs the whole forward and backward pass on its own slice of the data, using full layers: the weights it needs are gathered on demand. Real model parallelism (tensor and pipeline) splits the computation of a single sample across GPUs. The practical difference is that FSDP needs no changes to the model code, while tensor and pipeline parallelism do.

Tensor parallelism: splitting each matrix

When even one layer is too large, or when sharding gives too much communication, tensor parallelism (TP) splits the matrices of each layer across GPUs. The scheme in Megatron-LM (Shoeybi et al., 2019, "Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism") is elegant because it needs almost no communication inside a block.

Recall that a Transformer MLP computes Y = GELU(X · W1) · W2 (the Transformer block). Split W1 by columns into T pieces, one per GPU. Each GPU computes X · W1,i, which is a slice of the hidden activations, and applies GELU, which works element by element and so needs no information from other GPUs. Now split W2 by rows to match: GPU i multiplies its hidden slice by its rows of W2 and gets a partial result with the full output shape. The true output is the sum of those partial results, one all-reduce. The attention block works the same way, with heads divided among GPUs. In total a layer needs two all-reduces in the forward pass and two in the backward pass (Shoeybi et al., 2019). The simulation checks that the split MLP is numerically the same function:

import numpy as np
rng = np.random.default_rng(0)
B, H, T = 6, 16, 4                                   # tokens, hidden size, tensor-parallel ranks
x = rng.normal(size=(B, H))
W1 = rng.normal(size=(H, 4 * H)); W2 = rng.normal(size=(4 * H, H))
gelu = lambda z: 0.5 * z * (1 + np.tanh(0.79788456 * (z + 0.044715 * z**3)))

ref = gelu(x @ W1) @ W2                              # the unsplit MLP

W1_cols = np.split(W1, T, axis=1)                    # column-parallel: each rank owns 4H/T columns
W2_rows = np.split(W2, T, axis=0)                    # row-parallel: matching rows of the second matrix
partials = []
for r in range(T):                                   # each loop iteration = one GPU, no communication
    h_r = gelu(x @ W1_cols[r])                       # (B, 4H/T): GELU is element-wise so it splits cleanly
    partials.append(h_r @ W2_rows[r])                # (B, H): a partial sum of the output
out = sum(partials)                                  # the ONE all-reduce (sum) in the forward pass
print("max |split - unsplit| :", f"{np.abs(out - ref).max():.1e}")
print("per-rank weights      :", W1_cols[0].size + W2_rows[0].size, "of", W1.size + W2.size)
print("activations all-reduced per MLP forward:", out.size, "numbers (B x H)")
max |split - unsplit| : 2.1e-14
per-rank weights      : 512 of 2048
activations all-reduced per MLP forward: 96 numbers (B x H)

Each of the 4 ranks holds a quarter of the MLP weights (512 of 2,048 numbers) and the only communication is one sum of a (tokens × hidden) tensor. But that all-reduce sits on the critical path: the next operation cannot start until it finishes, and it happens in every layer, thousands of times per step. Unlike the gradient all-reduce in DP, it cannot be overlapped with computation. That is why TP is used only across GPUs joined by the fastest links, in practice the 8 GPUs inside one server connected by NVLink (900 GB/s on the H100 according to NVIDIA's page, against 400 Gbit/s, that is 50 GB/s, for Llama 3's inter-server network). A common rule: tensor-parallel degree no larger than the GPUs in a node.

Sequence and context parallelism

Tensor parallelism splits the big matrix multiplications but leaves other operations (layer norm, dropout, residual additions) replicated, so every GPU still stores their full activations. Korthikanti et al. (2022) introduced sequence parallelism: in those regions, split the activations along the sequence dimension instead. The all-reduce is then replaced by a reduce-scatter on the way into the replicated region and an all-gather on the way out, which together move the same amount of data as the all-reduce, so memory is saved without extra traffic. For very long sequences, context parallelism goes further and splits the sequence across GPUs for the whole model, including attention, which needs each GPU to see all the keys and values (ring attention, Liu et al., 2023, passes them around a ring). Llama 3 used 16-way context parallelism for its 131,072-token training stage.

Pipeline parallelism: splitting by layers

Pipeline parallelism (PP) puts the first block of layers on GPU 0, the next on GPU 1, and so on, like stations on an assembly line. Communication is light: only the activations at the boundary between two stages, a (tokens × hidden) tensor, travel between neighbours, once forward and once backward. Light traffic means PP tolerates slower links, so it is the dimension used across servers. The cost is idleness. If you push one batch through four stages, while stage 3 works the other three wait. The fix, from GPipe (Huang et al., 2019), is to split the batch into micro-batches and feed them in one after another so that stages overlap. Even so, at the start the later stages wait for the first micro-batch to reach them, and at the end the early stages wait for the backward pass. This idle time is the pipeline bubble. With p stages and m micro-batches, each stage is busy for 2m slots out of 2(m + p − 1), so the idle fraction is

bubble = (p − 1) / (m + p − 1)

The GPipe authors found the bubble negligible when m is at least four times p. The script prints the schedule for p = 4, m = 4, then the formula for other settings:

def gpipe_grid(p, m):
    """Forward-then-backward schedule: stage s runs forward of micro-batch i at time s+i,
    backward of micro-batch i at time (p+m-1) + (p-1-s) + (m-1-i)."""
    T = 2 * (p + m - 1)
    grid = [["." for _ in range(T)] for _ in range(p)]
    for s in range(p):
        for i in range(m):
            grid[s][s + i] = "F"
            grid[s][(p + m - 1) + (p - 1 - s) + (m - 1 - i)] = "B"
    return grid

for s, row in enumerate(gpipe_grid(p, m)):

Analogy: a kitchen

Data parallelism is opening more kitchens that all cook the same menu from different orders, and comparing notes at closing time. Pipeline parallelism is one kitchen with stations: prep, grill, plating, each station a GPU, dishes handed down the line. The line is only efficient when there are many dishes in flight; the first and last minutes of a service have idle stations. Tensor parallelism is two chefs sharing a single enormous pan, which only works if they stand shoulder to shoulder and can pass ingredients instantly.

Where it breaks down: in a kitchen the dishes are independent, so any order works. In training, every micro-batch's backward pass must happen after its forward pass and before the weights update, so the schedule has hard dependencies, and "closing time" is a synchronisation point that every GPU waits for every step.

Putting the dimensions together

Large runs combine all of these. The assignment follows one principle: put the most communication-hungry dimension on the fastest wire. Tensor parallelism (an on-critical-path all-reduce every layer) goes inside a server; pipeline parallelism (small boundary tensors) goes across servers within a rack or pod; data parallelism (one gradient exchange per step, overlappable) goes outermost, across the slowest links. Context parallelism, when used, sits between. Llama 3 405B's published configurations show the pattern (Dubey et al., 2024, Table 4):

GPUsTPCPPPDPSequence lengthTokens per batchBF16 MFU

The factors multiply to the GPU count: 8 × 16 × 128 = 16,384, and 8 × 16 × 16 × 8 = 16,384. TP = 8 is the eight GPUs of one server. Notice that MFU slips from 43 to 41 percent when DP doubles, because the global batch is held at 16 million tokens so each data-parallel group gets a smaller batch and a larger share of the step becomes pipeline bubble and communication. Meta also used FSDP across the data-parallel dimension, but chose not to reshard the weights after the forward pass, avoiding an extra all-gather in the backward pass at the cost of memory (Dubey et al., 2024): another sign that the right split is found by trading specific costs, not by following a template.

Systems connection

Every statement above is the same arithmetic as in networking: time is bytes divided by bandwidth plus latency, and the difference between 900 GB/s inside a server and 50 GB/s between servers sets the whole design. The ring all-reduce sends about the same number of bytes per GPU whatever the cluster size, which is why gradient exchange scales. Synchronous training is also a barrier: every step waits for the slowest GPU, so one straggler or failure stalls thousands of devices, which is the subject of chapter 5. For the hardware side, see Parallelism, SIMD & GPUs and Performance Engineering.

Choosing a strategy

  1. Does the model state fit on one GPU, with room for activations? Use plain DP (PyTorch DDP). It has the least overhead.
  2. Does it fit if the redundancy is removed? Use ZeRO-2 or FSDP. This covers most fine-tuning and training up to a few tens of billions of parameters on a well-connected cluster, with no model changes.
  3. Is communication the bottleneck, or is one layer too large? Add tensor parallelism inside a node and, for very deep models over slower links, pipeline parallelism across nodes.
  4. Are sequences very long? Add sequence or context parallelism.
  5. Always: recompute activations selectively, keep micro-batches large enough to use the GPU, and measure MFU. A configuration is good when MFU is high, not when it fits.

State of play, October 2026

The techniques here are stable; the software names move. The common open implementations are PyTorch's DDP and FSDP, DeepSpeed (which provides ZeRO) and Megatron-LM or its Megatron-Core library (tensor, pipeline, sequence and context parallelism). Check each project's documentation for the current API, because FSDP in particular has been revised across PyTorch releases. The 2024 Llama 3 table above is the best-documented public example of a large run's parallelism; newer frontier runs have not published equivalents, and mixture-of-experts models add a fifth dimension, expert parallelism, which sends tokens to the GPUs that hold their chosen experts (see A2 chapter 20).

Key takeaways

  • Parallelism serves two goals, fitting the model and finishing in reasonable time: 6ND FLOPs for a 7B model on 2T tokens is about 6.7 GPU-years at 40% utilisation of an H100.
  • An all-reduce is a reduce-scatter plus an all-gather; in a ring each GPU sends about 2× the tensor size regardless of the number of GPUs, which is why data parallelism scales.
  • Data parallelism replicates the model; ZeRO and FSDP remove the replication in three stages (optimiser, then gradients, then weights), at no extra traffic until ZeRO-3, which costs about 1.5×.
  • Tensor parallelism splits each matrix (column-wise then row-wise) with two all-reduces per layer in each direction, on the critical path, so it stays inside a node.
  • Pipeline parallelism splits layers into stages with light traffic but a bubble of (p − 1)/(m + p − 1); more micro-batches shrink it.
  • Real runs multiply the dimensions (Llama 3: TP 8 × CP 16 × PP 16 × DP 8 = 16,384 GPUs), placing the chattiest dimension on the fastest link.

Check your understanding

You run plain data parallelism on 8 GPUs and then on 64 GPUs, with the same model. How does the all-reduce traffic sent by each GPU per step change?

  1. It grows 8 times, because there are 8 times as many peers
  2. It falls to one eighth, because each GPU handles a smaller share of the batch
  3. It stays about the same, close to 2 times the gradient size, since a ring sends 2(N − 1)/N times the tensor
  4. It doubles, because every GPU must talk to every other
2(N − 1)/N is 1.75 for N = 8 and 1.97 for N = 64. The ring pipelines chunks, so no GPU talks to all peers. Batch size per GPU does not enter, since gradients have the size of the model, not of the batch.

Why is ZeRO-2 able to shard gradients and optimiser state without increasing communication over plain data parallelism?

  1. An all-reduce is already a reduce-scatter plus an all-gather; ZeRO-2 uses those two collectives to also perform the sharded update
  2. It stores gradients in a compressed format
  3. It sends gradients less often
  4. It moves the optimiser step to the CPU
After the reduce-scatter each GPU holds the summed gradients for its own shard, updates its shard, and the all-gather distributes the new weights. Same collectives, same 2Ψ volume. No compression or CPU offload is involved.

A team has 64 GPUs in 8 servers of 8 NVLink-connected GPUs, joined by a slower network. They need tensor parallelism. Where should the tensor-parallel group be placed, and why?

  1. Across servers, so that each server holds one layer
  2. Anywhere, since all-reduce cost does not depend on the link
  3. Across the slowest links, because it communicates least
  4. Within a server, because its all-reduces sit on the critical path of every layer and need the fastest links
Tensor parallelism communicates activations twice per layer in each direction and cannot overlap that with compute. Pipeline or data parallelism are the dimensions to put on slower links.

A 70B-parameter model with a 12-byte-per-parameter optimiser is trained with ZeRO-3 on 128 GPUs. Roughly how large is the per-GPU model-state memory?

Total state is 70×109 × 16 bytes = 1,120 GB, and ZeRO-3 divides all of it by 128, giving about 8.75 GB per GPU before activations and communication buffers. Answer 1 is the unsharded total.

Why does Llama 3's configuration use a tensor-parallel degree of 8 but a data-parallel degree of 64 to 128?

  1. Tensor parallelism needs the fastest links, available only among the 8 GPUs of a server, while data-parallel traffic can cross the slower network and overlap with compute
  2. Tensor parallelism cannot be used with more than 8 GPUs on any hardware
  3. Data parallelism needs more memory than tensor parallelism
  4. The numbers were chosen to match the sequence length
TP = 8 matches the 8 NVLink-connected GPUs per server. The limit is a matter of bandwidth, not an absolute software rule. DP uses less critical-path communication, so it takes the outer, slower dimension.

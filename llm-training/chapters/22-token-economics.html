The Economics of a Token

What does a million tokens cost to serve? The honest answer is "it depends on batch size, context length, precision and how busy the GPU is", and each of those can move the price tenfold. This chapter builds a small model of one GPU from its datasheet numbers, uses it to explain why output tokens cost more than input tokens, and ends with a worked capacity and cost estimate you can adapt.

Why this matters

Every decision in this part of the course (quantise or not, which engine, how many sequences to batch, whether to speculate) is ultimately a decision about money and latency. A team that cannot turn those choices into a cost per token ends up comparing a hosted API with its own GPUs on vibes. After this chapter you will be able to estimate throughput, latency and cost for a model on a given GPU from first principles, say which assumption dominates the answer, and tell whether self-hosting could beat a per-token API for a given volume.

Cost per token is a division

A GPU costs the same per hour whether it is working or idle. So the cost of a token is simple arithmetic:

cost per million tokens = (GPU price per hour ÷ tokens served per hour) × 1,000,000

Everything interesting is in the denominator. How many tokens per hour a GPU serves depends on how much work it does per second while busy (throughput) and on the share of the time it is busy (utilisation). Throughput is what the first half of this chapter models; utilisation is the second half.

The models in this chapter are deliberately simple. They use these inputs, which you should treat as the chapter's assumptions, not as measurements of any system.

  • Hardware (NVIDIA datasheet, H100 SXM): 3.35 TB/s of HBM bandwidth, 80 GB of memory, and 1,979 TFLOPS of bf16 tensor throughput which the datasheet footnotes as including sparsity, so the dense figure used here is 989 TFLOPS.
  • Efficiency (assumption): kernels achieve 70% of peak bandwidth and 50% of peak arithmetic. Real figures vary by kernel, model and version.
  • Price (assumption): $3.00 per GPU-hour. See the dated note below for the range seen in October 2026.
  • Model: the Llama 3 8B shape (Dubey et al., 2024): 8.03 billion parameters, 32 layers, 8 KV heads of width 128, so 128 KiB of KV cache per token in bf16 (chapter 18).

The decode step as a bill of bytes

From chapter 18: one decode step produces one token for each running sequence. It must read all the weights from HBM (16.1 GB in bf16) and each sequence's whole KV cache. It performs about 2 FLOPs per parameter per token, so 2 × 8.03 billion × B for a batch of B. The step takes as long as the slower of the two jobs:

step time = max( (weight bytes + B × context × KV bytes per token) ÷ usable bandwidth , 2 × params × B ÷ usable FLOP/s )

The first term is the memory time; the second is the compute time. The ratio of peak FLOP/s to bandwidth for this GPU, 989 × 1012 ÷ 3.35 × 1012 ≈ 295 FLOPs per byte, is the arithmetic intensity a step needs before arithmetic, not memory, is the limit. For the weights alone, batch B has intensity about B FLOPs per byte (2B FLOPs for each 2-byte weight), so a batch near 300 would be needed. The script puts numbers on that for a 2,048-token context.

"""What does a million tokens cost? A decode-step model for Llama 3 8B on one H100 SXM.
Sources: H100 SXM 3.35 TB/s HBM, 80 GB, 989 TFLOPS dense bf16 (NVIDIA datasheet halves, since its 1,979 includes sparsity).
ASSUMPTIONS (not measurements): memory efficiency 70%, compute efficiency (MFU) 50%, GPU price $3.00 per hour, 2 GB overhead."""
BW, PEAK, HBM = 3.35e12, 989e12, 80e9
BW_EFF, MFU, PRICE, OVERHEAD = 0.70, 0.50, 3.00, 2e9
PARAMS, KV_TOK = 8.03e9, 131072                     # parameters; KV bytes per token (bf16, 8 KV heads, 32 layers)

def decode_step(B, ctx, wbytes=2.0, kvbytes=2.0):
    """Seconds for one decode step with B sequences each holding ctx tokens of cache."""
    mem = PARAMS * wbytes + B * ctx * KV_TOK * (kvbytes / 2)          # weights once + every sequence's cache
    flops = 2 * PARAMS * B                                            # 2 FLOPs per parameter per token (attention FLOPs ignored)
    return max(mem / (BW * BW_EFF), flops / (PEAK * MFU))

def max_batch(ctx, wbytes=2.0, kvbytes=2.0):
    return int((HBM - OVERHEAD - PARAMS * wbytes) // (ctx * KV_TOK * (kvbytes / 2)))

def cost_per_m(tok_per_s, util=1.0):
    return PRICE / (tok_per_s * util * 3600) * 1e6

if __name__ == "__main__":
    ctx = 2048
    print(f"Llama 3 8B bf16, context {ctx}: KV {ctx*KV_TOK/1e6:.0f} MB per sequence, at most {max_batch(ctx)} sequences fit in 80 GB")
    print(f"{'batch':>6}{'step ms':>9}{'tok/s':>9}{'ITL ms':>8}{'$/M out tokens':>16}{'bound by':>11}")
    for B in (1, 4, 16, 32, 64, 128, 200):
        t = decode_step(B, ctx); mem_t = (PARAMS*2 + B*ctx*KV_TOK)/(BW*BW_EFF)
        print(f"{B:>6}{t*1e3:>9.1f}{B/t:>9.0f}{t*1e3:>8.1f}{cost_per_m(B/t):>16.3f}{'memory' if mem_t >= 2*PARAMS*B/(PEAK*MFU) else 'compute':>11}")
    pre = PEAK * MFU / (2 * PARAMS)
    print(f"\nPrefill is compute-bound: {pre:,.0f} input tokens/s -> ${cost_per_m(pre):.3f} per million input tokens")

Read the table from top to bottom. At batch 1 the GPU delivers 144 tokens per second and each million tokens costs $5.80. Raising the batch to 32 makes tokens twenty times cheaper ($0.27), because the 16 GB of weights are read once for 32 sequences instead of once for one. But the gains slow: going from 64 to 200 sequences cuts the cost only from $0.185 to $0.124, and the inter-token latency doubles (14 ms to 30 ms). Every row is memory-bound: the compute limit at batch 300 is never reached, because the KV caches take over before that.

That is the central insight of serving economics. Batching amortises the weights, but not the cache. At batch 64 the cache bytes equal the weight bytes; at 200 they are three times larger, and the step time is almost entirely a function of how many cache bytes are read. This is why the cache is the focus of so much engineering: paging so that more sequences fit (chapter 20), fewer KV heads (grouped-query attention), and cache quantisation (chapter 19).

Analogy: the airline seat

A flight costs roughly the same to operate whether it is empty or full, so the cost per passenger is the flight's cost divided by the seats filled. Batching is filling seats; the aircraft's fixed cost (the weights read every step) is shared among passengers. But each passenger also brings luggage (the KV cache) that takes room and weight, so past a point more passengers do not make each ticket much cheaper and the aircraft has a limit on how much it can carry.

Where it breaks down: an airline can fill seats with a booking system months in advance. A serving system gets requests at random and must trade the wait for a full batch against the latency each user sees.

Input tokens are cheaper than output tokens

The last line of the output explains a pattern you will see on every price list. Prefill (processing the prompt) is compute-bound: all of a prompt's tokens are processed together, so the weights are read once for thousands of tokens. At the assumed 50% arithmetic efficiency, one H100 processes about 30,800 prompt tokens per second for the 8B model, which at $3 an hour is $0.027 per million input tokens. Decoding the same number of tokens costs between $0.12 and $5.80 per million depending on the batch, a difference of roughly 5 to 200 times.

State of play, October 2026: how prices are structured

Hosted-model price lists reflect this physics. Anthropic's pricing page, fetched in October 2026, lists output tokens at five times the base input price for the models I checked, charges 1.25 times the input price to write a prompt to a five-minute cache and a small fraction (one tenth on most listed models, lower on some) of the input price to read from it, and offers a 50% discount on both input and output for asynchronous batch processing. Other providers' ratios differ and all of these change; the structure (output dearer than input, cache reads much cheaper than fresh input, batch work discounted) follows from the costs above: output is memory-bound, a cache hit skips prefill (chapter 20), and asynchronous work can be packed into the gaps in utilisation. Rented GPU prices also move: sources in October 2026 give H100 on-demand rates from about $2 to $7 per GPU-hour at specialist and hyperscale clouds, with spot and reserved rates about half. The $3 used here sits inside that range and is not a quote.

Latency and throughput pull against each other

The table already shows the trade: more sequences per step means cheaper tokens and slower steps. A product has a latency requirement, so the real question is the cheapest configuration that meets it. The plot sweeps the batch size for two context lengths and draws the cost against the inter-token latency each user would see.

Draw a vertical line at your latency target and read off the cost. The second script does that for a 25 ms target (an assumed requirement, about 40 tokens per second per user), and varies the precision and the context length. For each configuration it finds the largest batch that still meets the target and fits in memory.

"""Cost per million output tokens at a latency target, for different precisions and contexts (same assumptions as econ.py)."""
from econ import decode_step, max_batch, cost_per_m, PRICE
ITL_TARGET = 0.025                                       # ASSUMED product requirement: at most 25 ms between tokens

def best(ctx, wbytes, kvbytes):
    top, ans = max_batch(ctx, wbytes, kvbytes), None
    for B in range(1, top + 1):                          # largest batch that still meets the latency target
        if decode_step(B, ctx, wbytes, kvbytes) <= ITL_TARGET: ans = B
    if ans is None: return None
    t = decode_step(ans, ctx, wbytes, kvbytes)
    return ans, t, ans / t

configs = [("bf16 weights, bf16 KV", 2.0, 2.0), ("int8/fp8 weights, bf16 KV", 1.0, 2.0),
           ("int4 weights (4.125 bit), bf16 KV", 4.125/8, 2.0), ("int4 weights, fp8 KV", 4.125/8, 1.0)]
print(f"inter-token latency target {ITL_TARGET*1e3:.0f} ms, GPU ${PRICE:.2f}/h, fully busy\n")
print(f"{'configuration':<36}{'context':>8}{'batch':>7}{'ITL ms':>8}{'tok/s':>8}{'$/M tokens':>12}")
for ctx in (2048, 16384):
    for name, w, kv in configs:
        r = best(ctx, w, kv)
        if r is None: print(f"{name:<36}{ctx:>8}{'misses the latency target even at batch 1':>35}"); continue
        B, t, tps = r
        print(f"{name:<36}{ctx:>8}{B:>7}{t*1e3:>8.1f}{tps:>8.0f}{cost_per_m(tps):>12.3f}")
print("\nutilisation: the same configuration (bf16, context 2048) when the GPU is only partly busy")
B, t, tps = best(2048, 2.0, 2.0)
for u in (1.0, 0.6, 0.3, 0.1):
    print(f"  {u:>4.0%} busy: ${cost_per_m(tps, u):.3f} per million output tokens")

Three results stand out.

  1. Context length is the biggest lever here. Moving from 2,048 to 16,384 tokens of context raises the cost per token by about eight times (from $0.132 to $1.064 for bf16), because the batch that meets the latency target shrinks from 158 to 19. Long contexts are expensive to serve, not just to train on.
  2. Weight quantisation helps modestly; cache quantisation helps a lot. At 2,048 tokens, going from bf16 to 4-bit weights saves about 22% ($0.132 to $0.103), because the weights are no longer the main cost; halving the cache bytes with fp8 KV nearly halves the cost again to $0.051. This is the model behind the advice that once weights are small, the cache is where to look.
  3. Utilisation can erase all of it. The bottom lines show the same configuration at 60%, 30% and 10% busy: the cost multiplies by 1.7, 3.3 and 10. An idle GPU is billed like a busy one.

Common misconception

"A token has a price." A token has a price only at a stated batch size, context length, precision, latency target and utilisation. The same GPU can serve a million tokens for five cents or for six dollars; the difference is how well the workload fits the hardware. A quoted benchmark figure (tokens per second) is meaningless without those conditions, and a figure measured at saturation overstates what a half-idle fleet delivers.

Utilisation: the cost nobody sees in the benchmark

Benchmarks run at saturation; production does not. Traffic has daily and weekly cycles, bursts and launches. To meet a latency target at peak you must provision for peak, and the GPUs are idle otherwise. A server run at high utilisation also suffers: as with any queue, latency climbs steeply as load approaches capacity (queueing theory), so planning for 100% busy at peak is a recipe for timeouts. The standard practice is to plan for 50 to 70% at peak, add a minimum of two replicas for availability, and scale with demand (load testing and capacity planning, cost and efficiency).

The last script works through a support assistant. The inputs are assumptions: each conversation sends 3,000 prompt tokens, of which a 2,000-token prefix is shared and served from the prefix cache, and produces 400 output tokens; the busiest hour carries three times the average load; the target is 60% busy at peak; and a minimum of two replicas are always on.

"""A worked estimate: a support assistant on a self-hosted 8B model. Every input below is an ASSUMPTION except the H100 figures."""
import math
from econ import PEAK, MFU, PARAMS, PRICE
IN_TOK, OUT_TOK, CACHED = 3_000, 400, 2_000          # tokens per conversation; the first 2,000 are a shared prefix
PEAK_TO_AVG, TARGET_UTIL, MIN_REPLICAS = 3.0, 0.6, 2   # busiest hour is 3x average; plan for 60% busy at peak; 2 replicas for availability
DECODE_TPS = 6336                                    # per GPU at a 25 ms target (econ2.py: bf16, context 2048)
PREFILL_TPS = PEAK * MFU / (2 * PARAMS)              # per GPU, compute-bound (econ.py)
SECONDS_MONTH = 730 * 3600

def plan(conv, use_cache=True):
    pre = conv * (IN_TOK - (CACHED if use_cache else 0)); dec = conv * OUT_TOK
    busy = (pre / PREFILL_TPS + dec / DECODE_TPS) / SECONDS_MONTH          # average number of GPUs' worth of work
    need = busy * PEAK_TO_AVG / TARGET_UTIL
    n = max(MIN_REPLICAS, math.ceil(need))
    cost = n * PRICE * 730
    return busy, need, n, cost

print(f"{'conversations/month':>20}{'avg GPUs busy':>15}{'needed at peak':>16}{'provisioned':>13}{'monthly bill':>14}{'$/conversation':>16}{'$/M tokens':>12}")
for conv in (200_000, 2_000_000, 40_000_000):
    busy, need, n, cost = plan(conv)
    print(f"{conv:>20,}{busy:>15.2f}{need:>16.2f}{n:>13}{'$'+format(cost,',.0f'):>14}{cost/conv:>16.4f}{cost/((IN_TOK+OUT_TOK)*conv/1e6):>12.3f}")
b1 = plan(40_000_000)[1]; b2 = plan(40_000_000, use_cache=False)[1]
print(f"\nat 40M conversations a month the prefix cache cuts the GPUs needed at peak from {b2:.1f} to {b1:.1f}")

At 200,000 conversations a month the bill is dominated by the two-replica minimum: $4,380 for under 1% of one GPU's work, or $0.022 per conversation. At 2 million it is the same $4,380, now $0.0022 a conversation. Only at 40 million does the bill track the token count, at $17,520 and $0.0004 a conversation, and there the prefix cache matters: it reduces the GPUs needed at peak from 12.2 to 7.3. Fixed costs, not tokens, decide the economics of a small deployment. This is the reasoning to bring to the self-hosting question.

Self-hosting or per-token API?

An API charges only for tokens and absorbs the idle time; a rented GPU charges for time and leaves the idle time to you. The break-even depends on how busy you can keep the GPU. The script compares one GPU's cost per million tokens at full load ($0.132) with a range of assumed API prices (not actual prices of any provider).

"""Self-hosting versus paying per token: at what utilisation does a rented GPU beat an API at a given (assumed) price?"""
from econ import cost_per_m, PRICE
HOURS = 730                                                     # hours in a month
tps = 6336                                                      # bf16 8B, context 2048, 25 ms target (from econ2.py)
full = cost_per_m(tps)
monthly_cap = tps * 3600 * HOURS
print(f"One GPU: ${PRICE*HOURS:,.0f} a month. At full load it serves {monthly_cap/1e9:.1f} billion tokens a month (${full:.3f} per million).")
print(f"{'assumed API price $/M tokens':>30}{'break-even utilisation':>26}{'tokens/month to break even':>28}")
for api in (0.05, 0.10, 0.20, 0.50, 1.00, 3.00):
    u = full / api
    tokens = PRICE * HOURS / api * 1e6
    print(f"{api:>30.2f}{(f'{u:.0%}' if u < 1 else 'never (>100%)'):>26}{tokens/1e9:>25.1f} B")

If an API charged $0.50 per million tokens, the rented GPU wins once it is more than 26% busy, which is 4.4 billion tokens a month. If the API charged $0.10, no utilisation of this GPU configuration could beat it, which is a reminder that large providers batch across thousands of customers and may run more efficient hardware and kernels than you can. And this ignores things that often decide the matter: the engineering time to run the service, the cost of quality (an 8B model is not a frontier model), data-handling requirements that rule out an external API, and latency guarantees. A rule of thumb that survives the details: self-host when volume is high and steady, the model is small enough for you to serve well, or data cannot leave your environment; use an API for spiky or small workloads and for the capabilities only large models have. The routing and quality trade-offs are the subject of A6 chapter 19, and the studio Design an LLM Serving Platform applies all of this to a multi-tenant design.

Systems connection

This is capacity planning, with unusual units. The estimate-then-sanity-check habit is from back-of-the-envelope estimation; the way latency explodes near full load is the knee of queueing theory; peak-to-average provisioning and headroom come from load testing and capacity planning; and treating cost as an engineering property is the point of cost and efficiency. The model-serving view in Designing with ML & LLMs uses the same physics at a higher level.

Key takeaways

  • Cost per token is the GPU's hourly price divided by the tokens it actually serves per hour; throughput and utilisation are the two things to model.
  • Decode is limited by bytes: weights read once per step plus every sequence's cache. Batching amortises the weights but not the cache, so gains flatten as caches take over.
  • Prefill is compute-bound and cheap per token; decode is memory-bound and dear. Price lists follow this: output costs several times input, cache hits are cheap.
  • Context length and cache precision can matter more than weight precision. In the chapter's model, 8 times more context cost about 8 times more per token.
  • Small deployments are dominated by fixed costs (minimum replicas, idle time); utilisation can change the unit cost tenfold.
  • Quote a cost only with its conditions: batch, context, precision, latency target and utilisation.

A GPU serves 8B-model decoding at 6,000 tokens per second and costs $3 an hour. Roughly what does a million output tokens cost at full load?

  1. About $0.14
  2. About $1.40
  3. About $14
  4. About $0.014
6,000 tokens a second is 21.6 million an hour, so $3 divided by 21.6 is about $0.14 per million. The tempting mistakes are slipping a factor of ten in the unit conversion.

In the chapter's model, raising the batch from 64 to 200 sequences cuts the cost per token only from $0.185 to $0.124 while latency doubles. Why do the gains flatten?

  1. The GPU becomes compute-bound at batch 64
  2. The weights grow with the batch
  3. Each sequence adds its own KV cache to read, so cache bytes come to dominate the step
  4. The price of the GPU rises with load
Weights are read once per step regardless of batch, but cache reads scale with the batch. At batch 64 they equal the weights; at 200 they are over three times larger. The model stays memory-bound throughout, so option 0 is wrong.

Why is an input (prompt) token usually cheaper to serve than an output token?

  1. Input tokens are shorter
  2. Providers subsidise input
  3. Input tokens skip the attention layers
  4. Prompt tokens are processed together in compute-bound prefill that reads the weights once for many tokens, while each output token needs its own memory-bound step
The asymmetry comes from the arithmetic intensity of the two phases. Option 1 may sometimes be true commercially, but the physics alone predicts an input-output gap; option 2 is false, since prompt tokens go through every layer.

You serve at a 25 ms latency target with a 16,000-token context and want the biggest cost reduction. According to the chapter's model, which change helps most?

  1. Quantising weights from 8 bits to 4 bits
  2. Storing the KV cache in 8 bits instead of 16
  3. Buying a GPU with more arithmetic throughput but the same bandwidth and memory
  4. Increasing the number of replicas
At long context the cache dominates the bytes read and limits the batch, so halving it nearly halves the cost per token (0.82 to 0.41 dollars in the table). Weight quantisation gave a smaller gain, extra arithmetic does not help a memory-bound step, and extra replicas raise cost without improving per-GPU efficiency.

A small team serves 200,000 conversations a month with two always-on GPUs and finds the cost per conversation high. What is the main reason?

  1. The model is too large
  2. Output tokens are too expensive
  3. The GPUs are almost idle, so the bill is fixed cost spread over few tokens
  4. Prefix caching is turned off
The chapter's plan shows under 1% of a GPU's work at that volume, so the cost is almost all idle capacity from the availability minimum. Prefix caching or a smaller model would trim a few percent of a tiny number. The fix is a cheaper way to meet the minimum (shared infrastructure, a per-token API) rather than faster kernels.

  2. Which colour of GPU it is
  3. Whether the figure includes the model's training cost
  4. How many parameters the draft model has

Checkpoints, Failures & Long Runs

A pretraining run is a single job that lasts weeks on thousands of machines that break. This chapter explains how often they break, what a checkpoint must contain for a restart to be exact, how often to take one, and which numbers to watch so that you notice trouble before the loss curve does.

Why this matters

The earlier chapters of this part made one step of training fit in memory and spread it over many GPUs. A real run repeats that step over a million times. At that length failure stops being an exception and becomes a scheduled event, and the difference between a team that finishes in 54 days and one that finishes in 80 is mostly this chapter: restarts that are fast, checkpoints that are correct, and monitoring that is boring. After reading you will be able to estimate a cluster's failure interval from first principles, size a checkpoint, choose a checkpoint interval with a formula you can defend, and list what must be saved for a resume to be bit-exact.

Why a large run is always failing

Start with arithmetic. Suppose each GPU, with its host, network card and share of a switch, goes wrong on average once every m days, independently of the others. A cluster of N of them sees its first failure after about m/N days. The failure rate of a system that needs every part is the sum of its parts' rates, so doubling the machines halves the time between failures. This is the same series-reliability argument as in What Reliability Means, with a harsher input: a training job is a chain of 16,000 links, not a bundle of independent replicas.

Real numbers make this concrete. Llama 3 405B was pretrained on up to 16,384 H100 GPUs. In a 54-day snapshot of that run the team recorded 466 job interruptions: 47 planned (firmware upgrades, configuration and dataset changes) and 419 unexpected (Dubey et al., 2024, "The Llama 3 Herd of Models", section 3.3.4). Dividing, 54 days is 1,296 hours, so an unexpected interruption arrived on average every 1,296 / 419 = 3.1 hours, around the clock for nearly two months. Working backwards to a per-GPU figure (a derived number, not the paper's): 54 × 16,384 / 419 is about 2,100 GPU-days per interruption, or roughly 5.8 years per GPU, counting every cause. Each GPU is individually reliable. The cluster is not.

The reason one fault is so expensive is synchronous training. In data-parallel and tensor-parallel training (chapter 03) every rank must finish each step's collective communication before any rank continues. The paper puts it directly: the synchronous nature of training makes it less fault-tolerant, and a single GPU failure may require a restart of the entire job. Compare this with the web services in Failure, Timeouts & Retries, where a dead replica costs a retry. Here a dead rank halts all 16,384.

What actually breaks

The Llama 3 paper classifies the 419 unexpected interruptions by root cause. The largest categories were faulty GPUs (148), GPU HBM3 memory (72), software bugs in dependencies (54), network switches and cables (35) and unplanned host maintenance (32). About 78 percent of unexpected interruptions were attributed to confirmed or suspected hardware, and GPU issues alone were 58.7 percent. Only three needed significant manual intervention; automation handled the rest.

Older public evidence tells the same story at smaller scale. Meta's OPT-175B run (Zhang et al., 2022) used 992 80 GB A100 GPUs, and the authors report that hardware failures caused at least 35 manual restarts and the cycling of over 100 hosts across about two months, with an estimated 70 or more further automatic restarts. The public logbook for that run is the subject of a case study in A2, and the Llama 3 reliability work is the subject of case study 3 of this course.

Four kinds of trouble deserve names, because each needs a different response.

  • Hard failure. A GPU, host or link stops working and the job crashes or hangs. Detection is easy if the framework has timeouts; recovery is a restart.
  • Hang. Nothing crashes but no progress is made, usually because one rank is waiting for a collective that another rank will never join. Without a watchdog timeout a hang can burn thousands of GPU-hours before a person notices.
  • Straggler. A part that still works but slowly: a throttled GPU, a flaky link. Because training is synchronous, one slow rank sets the pace for everyone. The Llama 3 team notes that even a single straggler can slow thousands of other GPUs.
  • Silent data corruption. A computation returns a wrong number without any error. Nothing crashes. The damage appears as odd loss behaviour much later, which makes it the hardest class to diagnose; the Llama 3 table counts 6 such events.

State of play, October 2026

The 54-day snapshot above is a 2024 measurement on H100 hardware. Failure rates per GPU depend on generation, cooling, power and software, and public data is thin: the Llama 3 paper and the OPT logbook remain the most detailed open accounts of a frontier-scale run. Treat the shape (a failure every few hours at about 16,000 GPUs, hardware dominant) as the durable lesson and recompute the numbers for the cluster you are given.

What a checkpoint contains

A checkpoint is a snapshot of everything needed to continue training as if nothing had happened. After a crash, the job restarts, reads the latest checkpoint and carries on from that step. Everything done since the checkpoint is lost and repeated.

The weights alone are not enough. With the mixed-precision AdamW recipe from chapter 02, training state per parameter is a bf16 working copy of the weight (2 bytes), a float32 master copy (4 bytes) and Adam's two float32 moment estimates (4 bytes each). Gradients are recomputed on the next step, so they are not saved. That is 14 bytes per parameter on disk, versus 2 bytes if you saved only the model for inference.

P = 405e9                       # parameters (Llama 3 405B)

A single checkpoint of a 405-billion-parameter model is therefore about 5.7 TB. Sharded evenly over 16,384 GPUs that is 346 MB each, which sits inside the 1 MB to 4 GB per GPU range the Llama 3 paper reports for its checkpoints (our figure is an even split; real shards differ with the parallelism layout). The write-time lines show why storage design matters: one writer at 2 GB/s needs 47 minutes; a fabric sustaining 2 TB/s (the sustained figure the paper gives for its Tectonic storage cluster) needs under three seconds in the ideal case. The paper describes the real difficulty as bursty writes that saturate the storage fabric for short periods.

Other state also belongs in the checkpoint, and forgetting it is the classic restart bug.

  • Optimiser state, already counted above. Without Adam's moments the first steps after resume behave like the first steps of a new run.
  • Step counter and learning-rate schedule position. Warmup and cosine decay are functions of the step; resuming at step 0 of the schedule sends the learning rate back to warmup.
  • Data loader position. Which documents were consumed, in which order. This is the same idea as a consumer offset in a log (Logs, Streams and Exactly-Once): without it you re-read some data and skip other data.
  • Random number generator states for dropout, data shuffling and any sampling, per rank.
  • Loss-scaling state if you use fp16, and any running statistics.

The script below shows why. It trains a small linear model with momentum SGD for 1,000 steps, "crashes" at step 400, and resumes four ways. Only the resume with the complete state reproduces the uninterrupted run to the last bit.

import json, numpy as np

D = 8
w_true = np.arange(1, D + 1, dtype=np.float64) / 4
data_rng = np.random.default_rng(7)
X = data_rng.standard_normal((4096, D)); y = X @ w_true + 0.1 * data_rng.standard_normal(4096)

def train(steps, state=None, stop_at=None, restore=("params", "opt", "cursor", "rng")):
    """Minibatch SGD with momentum. State = everything needed to continue exactly."""
    if state is None:
        state = {"w": np.zeros(D), "v": np.zeros(D), "step": 0, "perm_seed": 1,
                 "cursor": 0, "rng": np.random.default_rng(123).bit_generator.state}
    w, v = state["w"].copy(), state["v"].copy()
    rng = np.random.default_rng(); rng.bit_generator.state = state["rng"]
    perm = np.random.default_rng(state["perm_seed"]).permutation(len(X))
    cursor, step = state["cursor"], state["step"]
    while step < steps:
        idx = perm[cursor:cursor + 32]; cursor = (cursor + 32) % len(X)
        noise = 0.01 * rng.standard_normal(D)                    # stands in for dropout-style randomness
        g = 2 * X[idx].T @ (X[idx] @ w - y[idx]) / len(idx) + noise
        v = 0.9 * v + g; w = w - 0.01 * v; step += 1
        if stop_at == step:
            return {"w": w, "v": v, "step": step, "perm_seed": 1, "cursor": cursor, "rng": rng.bit_generator.state}
    return {"w": w, "v": v, "step": step}

def loss(s): return float(np.mean((X @ s["w"] - y) ** 2))

ref = train(1000)
ck = train(1000, stop_at=400)                                    # "crash" after step 400, checkpoint saved
good = train(1000, state=ck)                                     # resume with everything
nov = dict(ck, v=np.zeros(D))                                    # forgot optimiser momentum
no_cursor = dict(ck, cursor=0)                                   # forgot data position
no_rng = dict(ck, rng=np.random.default_rng(123).bit_generator.state)   # forgot RNG state
print(f"uninterrupted run, final loss          {loss(ref):.12f}")
for name, st in [("resume, full state", good), ("resume, momentum lost", train(1000, state=nov)),
                 ("resume, data cursor lost", train(1000, state=no_cursor)), ("resume, RNG state lost", train(1000, state=no_rng))]:
    same = np.array_equal(st["w"], ref["w"])
    print(f"{name:<38} {loss(st):.12f}  bit-identical: {same}")

uninterrupted run, final loss          0.010041271243
resume, full state                     0.010041271243  bit-identical: True
resume, momentum lost                  0.010041271243  bit-identical: False
resume, data cursor lost               0.009918593096  bit-identical: False
resume, RNG state lost                 0.010082667095  bit-identical: False

Look at the losses as well as the flags. Lost momentum gives the same loss to twelve digits, because this toy problem is easy and convex: the run recovers. The data cursor and RNG variants end at slightly different losses. None of the broken resumes looks wrong on a loss curve, which is what makes the bug dangerous: the run continues, the numbers are plausible, and the difference only shows up as irreproducibility or as a subtle shift in what the model saw. On a real run the data cursor matters more, because losing it can silently repeat a stretch of the corpus.

Common misconception

"A checkpoint is the model weights." The weights are what you ship, and about one seventh of what you need to resume (2 of 14 bytes per parameter). A weights-only file lets you fine-tune or evaluate but not continue the pretraining run faithfully. Keep the two ideas apart: the resume checkpoint for the run, and the exported model for everything downstream.

Making checkpoints fast and safe

Three engineering ideas keep checkpointing from eating the run.

  1. Shard the write. Each rank writes only the parameters and optimiser state it owns, in parallel, instead of gathering 5.7 TB onto one machine. PyTorch's distributed checkpoint library (torch.distributed.checkpoint) does this and can reload onto a different number of GPUs, which matters when the cluster you restart on is not the one you saved from.
  2. Save asynchronously. Copy the state to host memory quickly (the GPUs pause only for this), then let background threads write to storage while training continues. PyTorch documents async_save for this since version 2.4. The costs are extra host memory, roughly a checkpoint's worth, and the rule that only one save should be in flight.
  3. Write atomically and verify. Write to a temporary name, check sizes or checksums, then rename to the final name, so a crash in mid-write never leaves a file that looks complete. Keep several recent checkpoints, not one: if the newest is corrupt (and a crash during a save is exactly when that happens) you fall back to the previous.

The same discipline applies to backups generally: a checkpoint you have never restored is a hope, not a recovery plan (Backups & Disaster Recovery). Teams routinely test a resume on a small run, including onto a different GPU count, long before the big run needs it.

How often to checkpoint

Checkpointing has a price: C seconds of paused GPUs each time (less with asynchronous saves). Not checkpointing also has a price: after a failure you redo everything since the last checkpoint. Too often wastes time saving; too rarely wastes time redoing. The balance has a classical answer.

Let T be the training time between checkpoints and M the mean time between failures. Per interval, you pay C to save. A failure arrives on average once per M, at a random point in an interval, so it destroys T/2 of work on average, plus the restart time R. Per second of useful training, the overhead is approximately

waste(T) ≈ C/T + (T/2 + R)/M

The first term falls as T grows; the second rises. Setting the derivative with respect to T to zero, −C/T2 + 1/(2M) = 0, gives

Topt ≈ √(2 C M)

This is Young's first-order result (Young, 1974, "A first order approximation to the optimum checkpoint interval"), refined by Daly (2006, "A higher order estimate of the optimum checkpoint interval for restart dumps"). Note that R drops out of the optimum: restart time adds a fixed cost per failure but does not change where the best interval sits. The formula assumes failures arrive at random with a constant rate and that the interval is much shorter than M. It is a guide, not a law.

To test it, the script below simulates a 30-day run in which failures arrive at random with the mean interval from the Llama 3 data (3.09 hours). Two scenarios share that failure rate. In the first, a blocking save pauses the GPUs for 120 s and a restart takes 15 minutes. In the second, an asynchronous save pauses for 10 s and a restart takes 5 minutes. The pause and restart values are illustrative assumptions of this chapter, not measurements from any run.

import math, random

DAYS_OBSERVED, UNEXPECTED = 54, 419            # Llama 3 405B snapshot (Dubey et al., 2024)
M = DAYS_OBSERVED * 24 * 3600 / UNEXPECTED     # mean seconds between unexpected interruptions
C = 120.0                                      # assumption: seconds GPUs are paused per checkpoint
R = 900.0                                      # assumption: seconds to restart, reload and warm up
WORK = 30 * 24 * 3600.0                        # useful training seconds we need to complete

def run(T, seed):
    """Simulate one run: checkpoint every T seconds of progress; failures arrive as a Poisson process."""
    rng = random.Random(seed)
    done = 0.0                                 # useful seconds banked in the last checkpoint
    clock = 0.0
    next_fail = rng.expovariate(1 / M)
    while done < WORK:
        seg = min(T, WORK - done)
        need = seg + C                         # train for seg, then pay the checkpoint pause
        if clock + need <= next_fail:
            clock += need; done += seg
        else:                                  # failure mid-segment: lose the segment, pay restart
            clock = next_fail + R
            next_fail = clock + rng.expovariate(1 / M)
    return WORK / clock                        # goodput: useful time over elapsed time

def report(label, c, r, minutes_list):
    global C, R
    C, R = c, r
    print(f"{label}: checkpoint pause C = {C:.0f} s, restart R = {R:.0f} s, Young optimum = {math.sqrt(2*C*M)/60:.1f} min")
    print("  interval   model waste   simulated waste")
    for minutes in minutes_list:
        T = minutes * 60
        extra = C / T + (T / 2 + R) / M        # first-order overhead per useful second
        model = extra / (1 + extra)            # as a share of elapsed time
        g = sum(run(T, s) for s in range(20)) / 20
        print(f"  {minutes:>5} min   {100*model:>9.1f}%   {100*(1-g):>13.1f}%")
    print()

print(f"MTBF M = {M/3600:.2f} h ({M:.0f} s) from 419 unexpected interruptions in 54 days\n")
report("blocking save to slow storage", 120.0, 900.0, (5, 10, 20, 27, 45, 90, 180))
report("fast async save, quick restart", 10.0, 300.0, (2, 4, 8, 16, 45, 180))

Two lessons follow. First, the best lever is making C small: cutting the pause from 120 s to 10 s moved the optimum from 27 to 8 minutes and cut waste from about 20 percent to under 7, which puts goodput near 93 percent, in line with the more-than-90-percent effective training time Llama 3 reported. Second, checkpointing more often is cheap once saves are asynchronous, so the real limit on frequency becomes storage capacity and bandwidth (14 bytes per parameter per copy) rather than GPU time.

The anatomy of one failure

Follow a single failure through time.

The restart time R is itself a chain of steps, and automation shortens each one.

  1. Detect. A rank crashes, or a watchdog notices that a collective has not completed within a timeout. Meta's team describes a PyTorch "flight recorder" that keeps a ring buffer of recent communication events and stack traces per rank and dumps it when the watchdog fires, so a hang can be traced to the rank that never arrived.
  2. Localise. Decide which machine is at fault. This is often the slowest step, because a hung NVLink transfer shows up as a stalled kernel with no error code.
  3. Replace. Remove the bad node from the pool and bring in a spare. Clusters keep spare machines for this, which is a reliability design choice: spare capacity bought so that recovery does not wait for a repair (the same trade as N+1 redundancy in blast-radius design).
  4. Reload. Start processes, initialise communication, read the checkpoint, and warm up kernels. Reading 5.7 TB across thousands of ranks at once is itself a load-spike on storage.
  5. Resume and verify the loss is where it was.

Llama 3's team reports that it reduced job startup and checkpointing time, built diagnosis tools, and handled all but three of its interruptions without manual intervention. That automation is why more than 90 percent of the elapsed time was effective training despite a failure every three hours.

Analogy: autosave in a long game

A game that autosaves every few minutes is a checkpoint policy. Save too rarely and a crash costs you an hour of play; save too often and the screen freezes constantly. The best interval depends on how long a save takes and how often the game crashes, exactly as in the formula above.

Where it breaks down: a game has one player and one state. A training run has thousands of ranks whose saved shards must all describe the same step, so a save is only good if every rank finished it, and a crash in the middle of a save must not corrupt the previous one.

Watching a run

You cannot babysit a run by reading the loss. A good monitoring setup has two jobs: catch problems the run does not announce, and tell a software issue from a hardware one. Metrics to log every step, per the practices in A2's stability chapter and the telemetry ideas in Metrics, Percentiles & Histograms:

SignalWhat a bad value looks likeLikely meaning
Training lossNaN or inf, or a sudden jumpDivergence or a bad batch; roll back
Gradient normBurst before a loss spikeInstability; often the earliest warning
Step timeA sustained rise of 10 to 25 percentA straggler, network congestion or throttling
Throughput, MFUDrifts down over hoursThermal throttling, data loader starvation
Data loader waitNon-zeroStorage or preprocessing cannot keep up
GPU healthECC errors, temperature, clock dropsA failing device before it fails
Time since checkpoint, last save durationSave time growingStorage degraded; your safety net is slipping

Two lessons from the Llama 3 report show how physical this gets. Throughput varied by 1 to 2 percent with the time of day, because higher mid-day temperatures affected GPU voltage and frequency scaling. And when tens of thousands of GPUs start or stop together (all waiting on a checkpoint, say), power consumption can swing across the data centre on the order of tens of megawatts. Neither shows up in a loss curve.

The script below is a minimal watchdog over a synthetic log with three injected problems: a loss spike with a gradient-norm burst at step 150, a 25-step straggler window from step 200, and a NaN at step 280. It compares each step with a rolling median, which is robust because a few outliers cannot drag the median the way they drag a mean, and it prints an alert only when one starts and when it clears.

import math, random, statistics as st

random.seed(5)
log = []                                         # (step, loss, grad_norm, step_seconds)
for step in range(1, 301):
    loss = 3.0 * math.exp(-step / 120) + 2.0 + random.gauss(0, 0.01)
    gn, t = 0.4 + random.gauss(0, 0.03), 4.0 + random.gauss(0, 0.05)
    if step == 150: loss += 1.5; gn *= 9         # a loss spike with a gradient-norm burst
    if 200 <= step < 230: t += 1.2               # a straggler: one slow GPU drags every step
    if step == 280: loss = float("nan")          # divergence
    log.append((step, loss, gn, t))

def check(history, window=50):
    """Return alerts for the latest record, comparing with a rolling median (robust to spikes)."""
    step, loss, gn, t = history[-1]
    past = history[-window - 1:-1]
    alerts = []
    if not math.isfinite(loss): return [f"step {step}: loss is {loss}: stop and roll back"]
    med = lambda i: st.median(r[i] for r in past if math.isfinite(r[i]))
    if len(past) >= 20:
        if loss > med(1) + 0.5: alerts.append(f"step {step}: loss spike {loss:.2f} vs median {med(1):.2f}")
        if gn > 3 * med(2):     alerts.append(f"step {step}: grad norm {gn:.2f} is {gn/med(2):.1f}x the median")
        if t > 1.15 * med(3):   alerts.append(f"step {step}: step time {t:.2f}s vs median {med(3):.2f}s (straggler?)")
    return alerts

active = {}                                      # alert kind -> first step of the current run of alerts
for i in range(len(log)):
    kinds = {a.split(": ")[1].split()[0]: a for a in check(log[:i + 1])}
    for kind, a in kinds.items():
        if kind not in active:                   # print only when an alert starts
            active[kind] = log[i][0]; print(a)
    for kind in list(active):
        if kind not in kinds:                    # alert ended: say how long it lasted
            print(f"step {log[i][0]}: {kind}-alert cleared after {log[i][0] - active.pop(kind)} steps")

step 150: loss spike 4.35 vs median 3.06
step 150: grad norm 3.48 is 8.9x the median
step 151: loss-alert cleared after 1 steps
step 151: grad-alert cleared after 1 steps
step 200: step time 5.22s vs median 4.01s (straggler?)
step 225: step-alert cleared after 25 steps
step 280: loss is nan: stop and roll back
step 281: loss-alert cleared after 1 steps

Collapsing repeated alerts matters in practice: the straggler produced 25 consecutive breaches, and paging someone 25 times is how alert fatigue starts (see Alerting & On-Call). Real systems also alert on time since the last step, because a hang produces no log lines to compare.

Loss spikes: the failure that is not hardware

Some interruptions are not machine faults at all. The loss suddenly jumps, perhaps recovers, perhaps does not. Causes and defences (learning-rate warmup, gradient clipping, careful initialisation, bf16 rather than fp16) are the subject of A2 chapter 17; what matters here is the operational response. PaLM's authors (Chowdhery et al., 2022) saw around twenty spikes during the 540-billion-parameter run despite gradient clipping. Their mitigation was operational: restart from a checkpoint about 100 steps before the spike and skip a few hundred data batches around it. When they replayed the same batches from an earlier checkpoint without the spike, they concluded that spikes arise from the combination of particular batches and a particular parameter state. The Llama 3 team, by contrast, reports few loss spikes and no interventions for divergence, helped by a lower batch size early in training.

This is why you keep several checkpoints and why the data loader position must be in the checkpoint: rolling back and skipping data only works if you can control exactly which data comes next.

Systems connection

Everything here maps onto ideas from the first path. Synchronous training behaves like a chain of series components (availability maths), a straggler is a tail-latency problem in which the slowest of N participants sets the pace (Tail Latency at Scale), a checkpoint plus data-loader offset is a snapshot plus log position, and the recovery runbook is incident response with the on-call replaced by automation (Incident Response).

Key takeaways

  • Failure rate scales with machine count. At 16,384 H100 GPUs, Llama 3 saw an unexpected interruption about every three hours; about 78 percent traced to hardware.
  • Synchronous training turns one fault into a full stop, so recovery speed matters more than prevention.
  • A resume checkpoint holds weights, master copies, optimiser moments, step, schedule position, data cursor and RNG states: about 14 bytes per parameter, not 2.
  • Checkpoint intervals follow T = √(2CM). Reduce C with sharded, asynchronous, atomic saves and the optimal interval and the waste both shrink.
  • Monitor step time and gradient norm as well as loss; alert on sustained breaches, and treat hangs, stragglers, silent corruption and loss spikes as different problems.

Check your understanding

Suppose each GPU and its share of host and network fails independently about once every 5 years. Roughly how often would a 16,384-GPU synchronous job see a failure?

  1. About every 3 minutes
  2. About every 2.7 hours
  3. About every 5 days
  4. About every 1.5 years
Failure rates add: 5 years is about 1,826 days, and 1,826 / 16,384 is about 0.11 days, or 2.7 hours. Hours is also what Llama 3 observed (about 3.1 hours). Days or years would be right only for a few machines, and minutes would imply per-GPU lifetimes of weeks.

A blocking checkpoint pauses training for 60 seconds, and the cluster's mean time between failures is 8 hours. Using Young's formula, which interval is closest to optimal?

  1. About 5 minutes
  2. About 8 hours
  3. About 31 minutes
  4. About 3 hours
T = √(2 × 60 × 28,800) = √3,456,000, about 1,860 s or 31 minutes. Five minutes would spend too much time saving; 3 hours and 8 hours would throw away large amounts of work at each failure.

A resume restores weights, optimiser state and step but forgets the data loader position, so it restarts at the beginning of the shuffled order. The loss curve looks normal. What is the most important consequence?

  1. The run will crash within a few steps
  2. The learning rate returns to warmup
  3. The model's weights are corrupted
  4. Part of the corpus is seen twice and other parts may never be seen, and the run is no longer reproducible
Nothing crashes and the weights are fine, which is why the bug hides. The learning-rate problem belongs to a forgotten step counter, not the data cursor. The harm is silent: a duplicated stretch of data, a skipped stretch, and a run that cannot be replayed.

What does an asynchronous checkpoint trade for its shorter GPU pause?

  1. It uses extra host memory for the staged copy, and a crash before the background write finishes loses that checkpoint, so the previous one must be kept
  2. It saves less state, so the resume is no longer exact
  3. It requires every rank to write the full model, which multiplies storage by the rank count
  4. It removes the need to checkpoint optimiser state
Async saves copy state to host memory (roughly a checkpoint's worth) and write in the background, so an in-flight save can be lost. The state saved is the same, sharding still applies, and the optimiser state is still required.

Step time has risen by 25 percent for the last 40 steps. Loss and gradient norm are normal and no rank has crashed. What is the most sensible first action?

  1. Roll back to the previous checkpoint and skip the next batches
  2. Look for a straggler: compare per-rank timings and communication traces to find the slow GPU, host or link, and replace it
  3. Lower the learning rate
  4. Increase the checkpoint interval to save time
Normal loss and gradients mean the maths is fine; the symptom is speed, which in synchronous training points to one slow participant. Rolling back and skipping data is the response to loss spikes. Changing the learning rate or checkpoint interval does not address a slow device.

PaLM's authors replayed the batches around a loss spike from an earlier checkpoint and the spike did not recur. What did they conclude, and what did they do?

  1. The hardware was faulty; they replaced the machines
  2. The data was corrupt; they deleted it from the corpus permanently
  3. Spikes came from a combination of specific batches and a particular parameter state; they restarted from a checkpoint about 100 steps earlier and skipped a few hundred batches
  4. The learning rate was too low; they increased it
Because the same batches did not spike from an earlier parameter state, neither the data alone nor the hardware was the cause. The workaround was to roll back and skip, not to remove data permanently or retune the learning rate.

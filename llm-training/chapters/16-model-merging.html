Model Merging & Evolutionary Merging

You have three fine-tunes of the same base model, one good at maths, one at code, one in another language. Can you get one model with all three skills without training anything? Sometimes you can, by doing arithmetic on the weights. This chapter explains why that works, the main recipes (averaging, task vectors, TIES, DARE), and how an evolutionary search can find a merge recipe no one would have guessed.

Why this matters

Chapters 10 to 14 each produced a model by gradient training, which needs data, GPUs and days. Merging produces a model in minutes on a CPU, with no training data, and it is how a large share of the open-weight models on public hubs are made. It is also easy to do badly: a merge can look fine on a leaderboard and be broken on your task, and a search over merge recipes can overfit its own evaluation set. After this chapter you will be able to say when two models can be merged at all, compute a task vector and a merged weight by hand, explain what TIES and DARE repair, read a merge configuration, and describe how evolutionary merging searches for a recipe and why it needs a held-out test set.

Why averaging weights can work at all

A trained network is a point in a space with one axis per weight. Averaging two networks means taking the point halfway between them. For two models trained independently, that should be a terrible idea, and it is. For two models fine-tuned from the same starting model, it often works well. The experiment below shows both cases in a network small enough to run in a second: two interleaved rings to classify, a 64-unit hidden layer, and four models. Two are fine-tuned from one shared starting point (a "base" trained briefly), and two are trained independently from different random initialisations. For each pair we evaluate the model at weights (1−t)·first + t·second.

import numpy as np

def data(n, rng):
    # two interleaved rings: class 0 at radius ~1, class 1 at radius ~2
    y = rng.integers(0, 2, n); r = 1.0 + y + rng.normal(0, 0.15, n); a = rng.uniform(0, 2 * np.pi, n)
    return np.c_[r * np.cos(a), r * np.sin(a)], y

def init(rng, h=64):
    return [rng.normal(0, 0.7, (2, h)), np.zeros(h), rng.normal(0, 0.3, h), np.zeros(1)]

def fwd(p, x):
    z = np.maximum(x @ p[0] + p[1], 0)
    return z, z @ p[2] + p[3][0]

def loss(p, x, y):
    _, o = fwd(p, x)
    return float(np.mean(np.logaddexp(0, o) - y * o))     # logistic loss

def train(p, x, y, steps, lr, rng, bs=64):
    p = [a.copy() for a in p]
    for _ in range(steps):
        i = rng.integers(0, len(x), bs); xb, yb = x[i], y[i]
        z, o = fwd(p, xb); g = (1 / (1 + np.exp(-o)) - yb) / bs
        dz = np.outer(g, p[2]) * (z > 0)
        p[2] -= lr * z.T @ g; p[3] -= lr * g.sum()
        p[0] -= lr * xb.T @ dz; p[1] -= lr * dz.sum(0)
    return p

def mix(a, b, t): return [(1 - t) * u + t * v for u, v in zip(a, b)]

x, y = data(2000, np.random.default_rng(0)); xt, yt = data(2000, np.random.default_rng(1))
base = train(init(np.random.default_rng(10)), x, y, 60, 0.05, np.random.default_rng(11))
ft1 = train(base, x, y, 1500, 0.05, np.random.default_rng(12))        # two fine-tunes of the SAME base
ft2 = train(base, x, y, 1500, 0.05, np.random.default_rng(13))
ind1 = train(init(np.random.default_rng(20)), x, y, 1800, 0.05, np.random.default_rng(21))   # two independent runs
ind2 = train(init(np.random.default_rng(30)), x, y, 1800, 0.05, np.random.default_rng(31))

print("test loss at interpolation t (0 = first model, 1 = second model)")
print(f"{'t':>5} {'same start':>11} {'different starts':>17}")
for t in np.linspace(0, 1, 6):
    print(f"{t:5.1f} {loss(mix(ft1, ft2, t), xt, yt):11.3f} {loss(mix(ind1, ind2, t), xt, yt):17.3f}")

The two fine-tunes of the shared base differ by only 0.07 in weight space (Euclidean distance over all weights), against 4.78 for the distance each moved from the base, so every point on the line between them is a model about as good as either end: the loss stays at 0.031. The independently trained pair is 16 apart, and the path between them passes through models with loss up to 0.205, about eight times worse than either end. Both ends are fine; what lies between is not. The usual explanation is symmetry: hidden unit 7 in one network may do the job of hidden unit 41 in the other, so averaging position by position mixes unrelated units. Two descendants of one parent keep the parent's unit ordering, so position i still means the same thing in both.

That is the first rule of merging. Merge models that share an ancestor and an architecture, which in practice means fine-tunes of the same base checkpoint, with the same tensor shapes (the mergekit documentation, read October 2026, says non-vocabulary dimensions must match). Wortsman et al. (2022), in "Model soups: averaging weights of multiple fine-tuned models improves accuracy without increasing inference time", averaged models fine-tuned from one pre-trained model with different hyperparameters; they report that this often beats the best single model and costs nothing at inference, unlike an ensemble, and that a soup built from ViT-G fine-tunes reached 90.94% top-1 accuracy on ImageNet. A soup merges models for the same task. The rest of this chapter merges models for different tasks.

Task vectors

Ilharco et al. (2023), in "Editing Models with Task Arithmetic", gave the idea a name. A task vector is the difference between a fine-tuned model's weights and the base it started from: τ = θft − θbase. It is the whole of what fine-tuning changed, as a vector with one entry per weight. (LoRA's merged update from chapter 11 is a task vector of low rank.) Three operations follow, each reported in the paper:

  • Addition. θ = θbase + λ ∑i τi combines skills, where λ is a scaling coefficient you choose, typically between about 0.3 and 1, and tune on held-out data.
  • Negation. θbase − λτ reduces the behaviour τ added. The authors report that subtracting a task vector lowers performance on that task while barely changing unrelated control tasks, and propose it for removing unwanted behaviour.
  • Analogy. If tasks relate as "A is to B as C is to D", combining three of the vectors can improve the fourth even without data for it.

Analogy: two editors' tracked changes

Take a manuscript (the base). Editor A returns it with tracked changes for tone, editor B with tracked changes for facts. If they touched different paragraphs, you can accept both sets of changes and get a document with both improvements: that is adding task vectors. Where both edited the same sentence you have a conflict, and you must pick one or blend them. Rejecting editor A's changes (subtracting) removes A's tone edits and leaves the rest.

Where it breaks down: tracked changes are separate, discrete edits that do not interact once accepted. Weight changes are continuous, and the effect of two changes together is not the sum of their separate effects, because the network is non-linear. Adding vectors works only while the model stays in a region where the effects are roughly additive, which is why it works for fine-tunes of a common base and fails for much larger departures.

Interference, and the repairs: TIES and DARE

When tasks are added, their vectors interfere. Yadav et al. (2023), in "TIES-Merging: Resolving Interference When Merging Models", identify two sources: redundant parameter values (many entries of a task vector changed only slightly and carry little of the task, but still add noise to the sum) and sign disagreement (for some weights, one fine-tune pushes up and another pushes down, and in a plain sum they cancel, or the result is worse than either). TIES has three steps, which the stepper walks through on six parameters.

  1. Trim. In each task vector, keep only the largest entries by magnitude (a chosen fraction, such as the top 20% or 30%) and set the rest to zero.
  2. Elect a sign. For each weight, add up the surviving entries of all task vectors and take the sign of the total. The sign with more total magnitude wins.
  3. Disjoint merge. For each weight, average only the entries that agree with the elected sign. Entries that disagree are dropped.
Step through

TIES on six weights

  1. Two task vectors. A and B are what two fine-tunes changed, over the same six weights. Small entries (−0.10, 0.05, 0.02) are most likely noise from training; large entries (0.8, −0.7) carry the task.
  2. Trim. Keep the three largest magnitudes in each vector and zero the rest. The sums now contain only entries that mattered.
  3. Elect a sign. Column 3 is a conflict: A wants +0.5, B wants −0.7. The summed mass is −0.20, so the elected sign is negative and A's entry (outlined) loses. Columns 1 and 4 agree. Columns 2, 5 and 6 have nothing left.
  4. Disjoint merge. Average only the agreeing entries: column 1 gives (0.8 + 0.6)/2 = 0.70, column 3 keeps B's −0.70, column 4 gives (−0.6 − 0.5)/2 = −0.55. A plain average would have blurred column 3 to −0.10 and added noise in columns 2, 5 and 6.

Yu et al. (2024), in "Language Models are Super Mario: Absorbing Abilities from Homologous Models as a Free Lunch" (DARE: Drop And REscale), attack redundancy differently. They observe that the delta parameters of supervised fine-tuning are tiny (within about 0.002 in their models) and extremely redundant, and propose to drop each delta entry at random with probability p and rescale the survivors by 1/(1−p). The rescale keeps the expected value of each entry: with m a random variable equal to 1 with probability 1−p and 0 otherwise, E[m · τ / (1−p)] = τ. They report that DARE can remove 90%, even 99%, of delta parameters without hurting the fine-tuned model's abilities, and that the effect is more pronounced for larger models. Fewer surviving entries per model also means fewer collisions when several models are added, and DARE is often combined with TIES' sign election ("DARE-TIES" in mergekit).

A comparison you can run

The toy below has six classes in 20 dimensions. Task A is the first three classes, task B the last three. A base network is trained briefly on both; two fine-tunes then train on one task each. (This is a six-way classifier, so a model fine-tuned only on A learns to put almost no probability on the B classes: it forgets B.) First, the shared functions.

import numpy as np
D, H, K = 20, 256, 6                                  # input dim, hidden units, classes (3 per task)

def make(seed):
    rng = np.random.default_rng(seed)
    means = rng.normal(0, 1.0, (K, D))
    def sample(classes, n, r):
        y = r.choice(classes, n); return means[y] + r.normal(0, 1.6, (n, D)), y
    return sample

def init(rng):
    return [rng.normal(0, 1 / np.sqrt(D), (D, H)), np.zeros(H), rng.normal(0, 1 / np.sqrt(H), (H, K)), np.zeros(K)]

def logits(p, x):
    z = np.maximum(x @ p[0] + p[1], 0); return z, z @ p[2] + p[3]

def train(p, x, y, steps, lr, rng, bs=64):
    p = [a.copy() for a in p]
    for _ in range(steps):
        i = rng.integers(0, len(x), bs); z, o = logits(p, x[i])
        e = np.exp(o - o.max(1, keepdims=True)); g = e / e.sum(1, keepdims=True); g[np.arange(bs), y[i]] -= 1; g /= bs
        dz = (g @ p[2].T) * (z > 0)
        p[2] -= lr * z.T @ g; p[3] -= lr * g.sum(0); p[0] -= lr * x[i].T @ dz; p[1] -= lr * dz.sum(0)
    return p

def acc(p, x, y): return float((logits(p, x)[1].argmax(1) == y).mean())

def task_vector(ft, base): return [f - b for f, b in zip(ft, base)]
def add(base, tvs, lam): return [b + lam * sum(t[k] for t in tvs) for k, b in enumerate(base)]

def trim(tv, keep):                                    # TIES step 1: keep the top `keep` fraction by magnitude
    out = []
    for t in tv:
        thr = np.quantile(np.abs(t), 1 - keep); out.append(np.where(np.abs(t) >= thr, t, 0.0))
    return out

def ties(tvs, keep):
    tvs = [trim(t, keep) for t in tvs]; merged = []
    for k in range(len(tvs[0])):
        stack = np.stack([t[k] for t in tvs]); sign = np.sign(stack.sum(0))      # elect sign by total mass
        agree = (np.sign(stack) == sign) & (stack != 0)
        merged.append((stack * agree).sum(0) / np.maximum(agree.sum(0), 1))      # mean over agreeing entries
    return merged

def dare(tv, p, rng):                                  # random drop with rescale 1/(1-p)
    return [np.where(rng.random(t.shape) >= p, t / (1 - p), 0.0) for t in tv]

Read it row by row. Each fine-tune reaches 93% to 96% on its own task and falls to 9% to 13% on the other: specialisation and forgetting in one table. The plain average (task arithmetic with λ = 0.5) is the best of the merges here, at 85.0% on A and 88.2% on B. It keeps most of both skills, though neither reaches the specialist's level, which is the usual price of a merge: one set of weights has to serve both. Task arithmetic with λ = 1 is close, TIES is no better than averaging, and DARE with p = 0.9 is worse. Three things about this honest result are worth saying out loud. The base here is already decent at both tasks, so the headroom is small. Only two task vectors are merged, so there is little interference to repair, and TIES's benefit grows with the number of models. And DARE is designed for large models: our network has 6,918 weights. With 16 hidden units (438 weights) dropping 90% of the update costs 19 points of accuracy (0.923 to 0.730). Common misconception

"A merged model has the average of its parents' abilities." The ability of a merge is not the average of anything. It can be better than both parents on a mixed task (a soup of fine-tunes often beats its best member), roughly the average, or collapsed, as in our independent pair in interp.py. Whether a merge works is an empirical question about the geometry between the models, so you answer it by evaluating the merge on held-out tasks, including ones the parents were never meant to do (chapter 23).

Merging in practice

Merges are usually specified in a configuration file and run with a tool. mergekit (Goddard et al., 2024) is the widely used open-source toolkit: the YAML config names the method, the base model, the models with their weights and densities, and the output precision, and one command writes a new checkpoint. The repository lists methods including linear, slerp, task_arithmetic, ties, dare_linear and dare_ties (read October 2026). SLERP (spherical linear interpolation) interpolates along the arc between two weight tensors instead of the straight line, which keeps the tensor's norm from shrinking in the middle; it merges exactly two models.

merge_method: dare_ties
base_model: example-org/base-7b            # the common ancestor
models:
  - model: example-org/base-7b-math        # a fine-tune of the base
    parameters: {weight: 0.5, density: 0.4}  # density = fraction of delta entries kept
  - model: example-org/base-7b-code
    parameters: {weight: 0.5, density: 0.4}
parameters:
  normalize: true
dtype: bfloat16
tokenizer_source: base

The file is a recipe: base, ingredients, amounts. That is why it belongs in version control next to the evaluation that justified it. Four practical points.

  • Do the arithmetic in 32-bit. A fine-tune's delta can be small relative to the weight it modifies. bfloat16 keeps only 8 bits of precision (two to three significant decimal digits), so a delta smaller than roughly 0.2% to 0.4% of a weight can be rounded away when added in bf16. Compute in fp32 and cast once at the end (the same caution as merging LoRA into a quantised base in chapter 11).
  • Check what the merge inherits. A merge of a chat-tuned model and a base model mixes their formats. Safety behaviour from instruction tuning can be diluted. The licences of all parents apply. The tokeniser and chat template must be chosen deliberately.
  • Pick λ and the densities on held-out data, not on the benchmark you will report.
  • Compare with the alternatives. Merging is one of several ways to combine skills.

Systems connection

Serving three separate 7-billion-parameter fine-tunes in bf16 takes about 3 × 14 GB = 42 GB of weights (assuming 7.0 billion parameters at 2 bytes each), against 14 GB for one merged model, and the memory-bound decoding of chapter 18 reads those weights on every step. The merge saves that, but the specialists are gone: you cannot route a request to the pure maths model. Treat the YAML as configuration as code: reviewed, versioned, and reproducible from the parents' exact checkpoint hashes.

Evolutionary merging: searching for the recipe

A merge has many knobs: which models, how much of each, in which layers, with which density. Tuning them by hand is guesswork. Akiba et al. (2024), in "Evolutionary Optimization of Model Merging Recipes" (Sakana AI), propose to let an evolutionary algorithm search. An evolutionary algorithm keeps a population of candidates, scores each, keeps the best, and creates new candidates by randomly perturbing and recombining them, repeatedly; it needs only a score, not a gradient, which is the point, because "merge, then evaluate" is not differentiable. They search in two spaces, as the paper's abstract describes: parameter space, the mixing weights for each model's layers, and data-flow space, which layers a token passes through and in what order.

Their main example, EvoLLM-JP, merged a Japanese language model (Shisa-Gamma) with two maths models (WizardMath and Abel), and evolved the merge recipe to improve Japanese maths. The authors report that the result performs strongly on Japanese benchmarks, outperforming models with considerably more parameters, though it was not explicitly trained for them; a second product, a Japanese vision-language model, was built the same way. Two details of the method deserve imitation. The evolution ran against a separate Japanese maths training set, and the final model was evaluated once on the held-out test set (the Japanese version of MGSM), in the authors' words to guard against over-training and overestimation. And the search found combinations a person would not have tried: an average of Japanese and maths models may fail where a per-layer recipe works. Case 5 examines the paper in depth, and Lab 5 has you build the loop yourself.

Why the held-out set matters: a demonstration

Return to the toy. A recipe now has four numbers: how much of τA and τB to add in the first layer, and in the second. A small evolutionary search (population 16, keep 4, 15 generations, noise shrinking by 15% a generation) tunes them to maximise accuracy on a search set, then we measure on 6,000 fresh examples. We run it with a search set of 60 examples and of 600, ten seeds each, against the untuned average.

import numpy as np
import merge_lib as m

def recipe(base, ta, tb, w):                  # w = [A in layer 1, B in layer 1, A in layer 2, B in layer 2]
    out = []
    for k, b in enumerate(base):
        li = 0 if k < 2 else 1
        out.append(b + w[2 * li] * ta[k] + w[2 * li + 1] * tb[k])
    return out

def evolve(fitness, rng, pop=16, keep=4, gens=15, sigma=0.4):
    parents = [np.full(4, 0.5)] + [rng.normal(0.5, sigma, 4) for _ in range(keep - 1)]
    for g in range(gens):
        kids = [p + rng.normal(0, sigma, 4) for p in parents for _ in range(pop // keep)]
        pool = parents + kids
        pool.sort(key=fitness, reverse=True)
        parents, sigma = pool[:keep], sigma * 0.85
    return parents[0]

        fit = lambda w: m.acc(recipe(base, ta, tb, w), xq, yq)
        w = evolve(fit, r); avg = np.full(4, 0.5)
        out.append([fit(avg), fit(w), m.acc(recipe(base, ta, tb, avg), xt, yt), m.acc(recipe(base, ta, tb, w), xt, yt)])
    o = np.mean(out, 0); wins = sum(q[3] > q[2] for q in out)
    print(f"{n_search:16d} {o[0]:16.3f} {o[1]:16.3f} {o[2]:14.3f} {o[3]:14.3f} {wins:10d}/10")
 search set size  average: search  evolved: search  average: test  evolved: test  evolved wins
              60            0.882            0.912          0.862          0.850          1/10
             600            0.858            0.869          0.864          0.861          2/10

With 60 search examples the evolved recipe scores 91.2% on the data it searched and 85.0% on fresh data, below the untuned average's 86.2%; it beat the average on the test set in only 1 of 10 seeds. The search fit the 60 examples' quirks. With 600 examples the gap largely closes, but the evolved recipe still does not beat the plain average (86.1% against 86.4%). In this toy, with two similar parents and a decent base, the average was already close to the best recipe, so there was little for the search to find. The method earns its keep when simple averaging fails, as when merging models from different domains, and in every case the search set is the thing the search can overfit. The discipline from A0 on statistics for experiments applies unchanged: tune on one set, report on another that you touch once.

State of play, October 2026

mergekit's repository (read October 2026) lists 18 merge methods under an LGPL-3.0 licence, and its configuration format and method names move between releases, so pin the version in your recipe. Sakana AI has published follow-up merging work since the 2024 paper (quality-diversity and competition-based variants); I did not read those papers for this chapter, so treat the method as an active research area and not a settled recipe. Leaderboards of open models contain many merges, and a high rank of a merge of fine-tunes on a public benchmark is weak evidence about your task, since parents may have seen the benchmark. Measure on your own held-out data.

Key takeaways

  • Averaging weights works for models that share an ancestor and architecture, because they stay in the same region of weight space; independently trained networks do not average (loss up to 0.205 against 0.027 in the toy).
  • A task vector is fine-tuned weights minus base weights. Adding scaled task vectors combines skills, and subtracting one removes a behaviour.
  • TIES trims small entries, elects a sign per weight and averages the agreeing entries. DARE drops entries at random and rescales by 1/(1−p). Both reduce interference, and DARE depends on the update being redundant, which grows with model size.
  • A merge is a recipe, not a training run: keep it as a versioned config, do the arithmetic in fp32, and evaluate on tasks the merge was not tuned for.
  • Evolutionary merging searches recipes (per-layer weights, layer order) by merge-then-evaluate, with no gradients. It needs a search set and a different final test set, because it will overfit the first.
  • A merge keeps one model's serving cost but cannot give back the individual specialists, so compare it with adapters, multi-task training and routing.

The next chapter goes one step further: instead of merging adapters you already have, it asks whether a network can generate an adapter for a task from a description of that task.

Check your understanding

Why can two fine-tunes of one base model usually be averaged, while two networks trained from different random initialisations usually cannot?

  1. Fine-tunes have fewer parameters, so there is less to go wrong
  2. Independent networks always have larger weights
  3. Fine-tunes stay close to a common starting point in which each unit already has the same role, whereas independently trained networks arrange their hidden units differently, so position-by-position averaging mixes unrelated units
  4. Averaging only works if the two networks were trained on the same task
In the toy, the two fine-tunes were 0.07 apart and the loss stayed flat along the path; the independent pair was 16 apart and the loss rose about eightfold in the middle. Parameter counts are identical in both cases, and merging models for different tasks (the whole point of task vectors) works despite option 4.

A weight is 1.00 in the base. Fine-tune A moved it to 1.40 and fine-tune B moved it to 0.80. With task arithmetic and λ = 0.5, what is the merged weight?

  1. 1.10
  2. 1.20
  3. 1.00
  4. 0.60
τA = +0.40 and τB = −0.20, so the sum is +0.20, and 1.00 + 0.5 × 0.20 = 1.10. The value 1.20 is the answer for λ = 1; 1.00 would be the result if the two vectors cancelled exactly.

DARE uses a drop probability p = 0.9. A task-vector entry of 0.03 survives the random drop. What value does it have afterwards, and why?

  1. 0.03, since survivors are left unchanged
  2. 0.003, because the entry is scaled down by 1 − p
  3. 0.09, because the scale is p
  4. 0.30, because survivors are divided by 1 − p = 0.1 so that the expected value of every entry stays the same
An entry survives with probability 0.1, so E[kept value] = 0.1 × (0.03 / 0.1) + 0.9 × 0 = 0.03. Without the rescale, the expected update would shrink to a tenth of its size. Dividing by p instead would not give an unbiased estimate.

An evolutionary search for merge weights reaches 91% on the 60 examples it was scored on, but 85% on a fresh test set, below the plain average's 86%. What is the most likely cause and the best response?

  1. The mutation rate was too low; run more generations
  2. The search overfit a tiny search set; use a larger search set that is separate from the final test set, and report the test score once
  3. The merge method is wrong; switch from averaging to SLERP
  4. The test set is contaminated, so ignore it
A big gap between the score the search optimised and the score on unseen data is the signature of overfitting the search set; more generations make it worse. The method choice does not explain a gap between two sets of the same data distribution, and treating the fresh set as contaminated would throw away the one honest number you have.

Which pair of models can you not sensibly merge with these methods?

  1. Two LoRA-merged fine-tunes of the same 7B base
  2. A maths fine-tune and a code fine-tune of the same checkpoint
  3. A fine-tune of one 7B model family and a fine-tune of an unrelated model with different layer sizes
  4. Three fine-tunes of one base with different hyperparameters on the same task
Merging needs matching tensor shapes and, for the arithmetic to mean anything, a common ancestor. Unrelated architectures fail the first test and unrelated training runs fail the second. The other three are the standard cases: adapters folded into the same base, two tasks from one checkpoint, and a soup.

You merge three 7B fine-tunes into one with TIES. What do you gain and lose compared with serving the three separately?

  1. You cut weight memory to a third (about 14 GB instead of 42 GB in bf16) but lose the ability to route a request to a pure specialist
  2. You keep all three specialists at full quality and use a third of the memory
  3. You gain quality on every task, because merging always improves on its parents
  4. You lose nothing, since a merge is lossless
One set of weights replaces three, so memory drops, and in our toy the merged model reached only about 85 to 88% where each specialist reached 93 to 96% on its own task, so some quality per task is traded for breadth. Merging does not always beat its parents on their own tasks, and it is not lossless.

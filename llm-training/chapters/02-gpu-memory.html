GPU Memory & Why Training Runs Out of It

The first error most people meet when they train a model is "CUDA out of memory", usually long before the GPU is busy. This chapter does the accounting: where every byte of a training step goes (weights, gradients, optimiser state and activations), why a model that fits for inference does not fit for training, and the tricks that trade compute, precision or speed for memory.

Why this matters

Memory, not arithmetic, decides what you can train on a given machine. A 7-billion-parameter model needs about 14 GB just to hold its weights in 16-bit numbers and roughly 105 GB to train with a standard recipe. If you cannot predict that number before you rent the GPUs, you will find out by crashing, one expensive attempt at a time. After this chapter you will be able to estimate the memory of a training job on paper, read a memory timeline, choose between gradient accumulation, activation checkpointing, lower-precision optimisers and parameter-efficient methods, and say what fits on one 24 GB GPU. The next chapter shows what to do when even that is not enough.

The four things that live in GPU memory

A GPU has its own memory, called HBM (high-bandwidth memory) on data-centre cards and VRAM in everyday speech. Its capacity is fixed: NVIDIA lists 80 GB for both the A100 80 GB and the H100 SXM, and 24 GB for the consumer RTX 4090 (NVIDIA product pages, fetched October 2026). Anything the GPU computes on must be in it. When the sum of what you ask for exceeds the capacity, the framework raises an out-of-memory (OOM) error. During training, four categories of data share that memory. Chapter 16 of A2 counted parameters and FLOPs; here we count bytes.

Weights (parameters)
The numbers the model learns. Needed for the forward pass, the backward pass and the update. Size: number of parameters × bytes per number.
Gradients
One number per trainable weight, produced by the backward pass: how the loss changes if that weight changes. Same count as the weights.
Optimiser state
The extra memory an optimiser keeps for each weight. Adam keeps two running averages per weight (moments), and in mixed-precision training also a full-precision master copy of the weights.
Activations
The intermediate outputs of every layer during the forward pass, kept because the backward pass needs them. They scale with batch size and sequence length, not just with the model.

The first three scale with the number of parameters and are the same whether your batch is 1 or 1,000. Together they are called the model states. The fourth scales with the work done in one step and is the one you can change without changing the model. Everything in this chapter is a way to shrink one of these four, or to move it somewhere else.

Model states: the 16-bytes-per-parameter rule

Weights and gradients

Modern training stores weights and gradients in a 16-bit format, usually bfloat16 (bf16): 2 bytes per number, the same exponent range as 32-bit floats but only 8 significant bits (see floating point in A0). So a model with N parameters needs 2N bytes for weights and 2N for gradients. For a 7-billion-parameter model that is 14 GB each.

Optimiser state

Plain gradient descent updates a weight with w ← w − lr × g and needs nothing extra. Adam, the optimiser that almost all language-model training uses (and its AdamW variant; see optimisers in A0), keeps for every weight a running average of the gradient (the first moment, m) and of its square (the second moment, v), and divides one by the root of the other. These two numbers per weight are what make it behave well, and they are kept in 32-bit floats, 4 bytes each: 8 bytes per parameter. There is one more copy. A weight of 1.0 stored in bf16 can only move in steps of about 0.004 to 0.008 (below and above 1.0 respectively): bf16 has 8 significant bits, so its gap above 1.0 is 2−7. A learning-rate-sized update of 0.001 is below half that gap and rounds away to nothing. The standard fix, introduced in mixed-precision training (Micikevicius et al., 2018), is to keep a master copy of the weights in 32 bits, apply updates to it, and derive the 16-bit working copy from it after each step. That is another 4 bytes per parameter. You can see the failure and the fix in a few lines of NumPy, with bf16 emulated by rounding a 32-bit float to its top 16 bits:

import numpy as np

def to_bf16(x):
    """Round float32 to bfloat16 (keep the top 16 bits, round to nearest even), returned as float32."""
    x = np.asarray(x, dtype=np.float32)
    u = x.view(np.uint32)
    rounded = (u + 0x7FFF + ((u >> 16) & 1)) & 0xFFFF0000
    return rounded.astype(np.uint32).view(np.float32)

print("gap between bf16 numbers just above 1.0:", float(to_bf16(1.0 + 2**-7) - 1.0), "(2^-7)")
w_bf16 = to_bf16(1.0)          # weight kept only in bf16
w_master = np.float32(1.0)     # fp32 master copy; bf16 copy is derived from it
lr, g = 1e-3, 1.0              # a constant update of 0.001 per step
for step in range(1000):
    w_bf16 = to_bf16(w_bf16 - lr * g)             # update applied directly to the bf16 weight
    w_master = np.float32(w_master - lr * g)       # update applied to the fp32 master
print("after 1000 steps of -0.001:")
print("  weight stored only in bf16 :", float(w_bf16))
print("  fp32 master weight         :", float(w_master), "-> bf16 copy used in matmuls:", float(to_bf16(w_master)))

Without a master copy the weight never moves: every update is smaller than half the gap to the next representable number. With one, the weight travels from 1.0 to almost 0 over a thousand steps, as it should (the tiny residue near 9 × 10−6 is float32 rounding of the repeated subtraction). This is why the bytes are counted as they are.

Read the table as a first filter. A 7B-class model needs about 105 GB of model state, which is more than any single 80 GB card holds before activations: it cannot be fully fine-tuned with this recipe on one GPU, however large the batch budget. A 70B-class model needs about a terabyte, which is 13 GPUs' worth of memory for state alone. The 1.3B row says "fits" for states, but with 21 of 24 GB gone you have 3 GB for activations and overhead; we return to that squeeze below. The last block shows how much the recipe matters. With the same 20 GB budget you can train about 1.2 billion parameters with the standard recipe, about 3 billion with an 8-bit optimiser and no master copy (the optimiser from Dettmers et al., 2021, "8-bit Optimizers via Block-wise Quantization", is available in the bitsandbytes library; dropping the master copy risks the failure demonstrated above, so it needs care), or hold a 40-billion-parameter model's weights in 4-bit form and train only small adapters on top (the QLoRA recipe, chapter 11). That last row counts weights alone and ignores activations, adapter state and quantisation constants, so it is an upper bound, not a promise.

Analogy: the workbench

Think of GPU memory as a workbench in a workshop and CPU memory and disks as the warehouse next door. The model's weights are the blueprint pinned at the back. Gradients and optimiser state are the notebooks in which you record corrections and your running notes. Activations are the half-finished parts you must keep within reach until the final inspection, because inspecting them is how you find what to fix. The bench has a fixed size. Making room means pinning a smaller blueprint, keeping fewer notebooks, putting some parts back in the warehouse and rebuilding them when needed, or spreading the work across several benches.

Where it breaks down: a workbench only has an area. GPU memory also has a speed limit: moving data between the warehouse and the bench is 10 to 100 times slower than working on what is already there, so "put it in the warehouse" has a price in time as well as effort.

Activations: the part that grows with your batch

The backward pass computes how the loss depends on each weight by applying the chain rule layer by layer from the output back to the input (see backpropagation in A2). Many of those local derivatives depend on the values that flowed forward through the layer: the derivative of a matrix product needs the input, the derivative of a softmax needs its output. So the forward pass keeps the intermediate results of every layer until the backward pass has used them. These saved tensors are the activations.

Their size is easy to state for a Transformer layer. Let s be the sequence length, b the micro-batch size (sequences processed together), h the hidden size and a the number of attention heads. Korthikanti et al. (2022, "Reducing Activation Recomputation in Large Transformer Models") count, for 16-bit activations and no parallelism, the bytes saved in one layer:

activations per layer = s · b · h · ( 34 + 5 · a · s / h )

Where do the pieces come from? In their accounting, the attention block saves 11·s·b·h bytes (the inputs to the Q, K, V projections, the Q and K themselves, the values, the output projection's input and a dropout mask) plus 5·a·s²·b bytes for the attention scores, their softmax output and its dropout mask. The MLP saves 19·s·b·h bytes (its two input tensors, the GELU input and a mask). The two layer norms save 4·s·b·h. These add to 34·s·b·h plus the quadratic term. The first part grows linearly with sequence length; the second grows with its square, because each of a heads holds an s×s grid of scores.

Two practical consequences follow. First, activation memory is proportional to the micro-batch size b, so halving b halves it. Second, the s² term makes long sequences expensive, unless the attention implementation avoids storing the score matrix, which is exactly what FlashAttention does (A2 chapter 19): it recomputes scores in the backward pass instead of saving them, so the 5·a·s/h term disappears. Let us compute what this means for a 7B-class shape (32 layers, h = 4096, 32 heads), for three strategies that the next section explains:

GB = 2**30
def act_bytes_per_layer(s, b, h, a, mode):
    """Korthikanti et al. (2022) eq. 1, 16-bit activations, no tensor parallelism.
    none:      s*b*h*(34 + 5*a*s/h)
    selective: drop the attention-score terms (5*a*s^2*b): s*b*h*34
    full:      keep only the layer input (2*s*b*h bytes); the layer is recomputed in backward"""
    if mode == "none":      return s * b * h * (34 + 5 * a * s / h)
    if mode == "selective": return s * b * h * 34
    if mode == "full":      return 2 * s * b * h

The numbers explain a great deal of folklore. At sequence length 4,096 and a micro-batch of just one sequence, a 7B-class model without any saving strategy wants 97 GiB of activations, more than its entire 14 GB of weights times six, and 82 percent of it is the attention-score matrices. A batch of 8 would need 776 GiB. That is why long-context training is hard, why every real run uses the tricks below, and why FlashAttention changed what fits. (The formula assumes the common Megatron-style implementation; frameworks that fuse operations or use different dropout will differ somewhat. Treat it as an estimate within tens of percent, then measure.)

Common misconception

"If the model fits on the GPU for inference, a smaller batch will make it fit for training." Batch size only shrinks activations. For a 7B model the 105 GB of weights, gradients and optimiser state is there even at batch size 1, so no batch size can rescue it. The right question is which of the four categories is over budget: if the model states are, only sharding, offloading, a smaller optimiser or fewer trainable parameters help; if the activations are, a smaller micro-batch or checkpointing helps.

Trading compute for memory

Gradient accumulation: a smaller micro-batch, the same gradient

Large effective batches (hundreds of sequences, or millions of tokens) matter for stable training, but they do not have to be processed at once. Gradient accumulation splits a batch into micro-batches, runs forward and backward on each in turn, adds the gradients, and takes the optimiser step only after the last. Because the gradient of a mean is the mean of the gradients, the result is the same (up to floating-point rounding) as processing everything together, while only one micro-batch's activations are alive at a time:

import numpy as np
rng = np.random.default_rng(1)
X = rng.normal(size=(64, 5)); w_true = np.array([1.0, -2.0, 0.5, 3.0, 0.0])
y = X @ w_true + 0.1 * rng.normal(size=64)
w = rng.normal(size=5)

def grad(Xb, yb, w):                       # d/dw of mean squared error over the batch
    return 2 * Xb.T @ (Xb @ w - yb) / len(yb)

full = grad(X, y, w)
accum = np.zeros(5)
steps = 8
for i in range(steps):                     # 8 micro-batches of 8; each loss is divided by `steps`
    sl = slice(i * 8, (i + 1) * 8)
    accum += grad(X[sl], y[sl], w) / steps
print("full batch of 64 :", np.round(full, 6))
print("8 x micro-batch 8:", np.round(accum, 6))
print("max difference   :", f"{np.abs(full - accum).max():.1e}")
print("activation memory scales with the micro-batch: 8 vs 64 rows live at a time (8x less)")

The costs are small but real: smaller matrices use the GPU less efficiently, and the gradient buffer must persist across micro-batches. One subtlety: the equivalence holds for losses that are averages over examples. With variable-length sequences, "mean per sequence" and "mean per token" are different, and accumulating the wrong one subtly changes the weighting. Libraries have had bugs here, so check how your trainer normalises.

Activation checkpointing: recompute instead of store

If activations are too big to store, do not store all of them. Activation checkpointing (also called gradient checkpointing or rematerialisation; Chen et al., 2016, "Training Deep Nets with Sublinear Memory Cost") saves the inputs to only some layers, the checkpoints. During the backward pass, when the gradient reaches a segment between two checkpoints, the segment's forward pass is run again from its checkpoint to rebuild the activations, which are used and freed immediately. Memory falls from one stored tensor per layer to one per checkpoint plus one segment's worth during recomputation. With n layers and a checkpoint every k, that is about n/k + k tensors, minimised near k = √n, giving O(√n) memory instead of O(n). The price is one extra forward pass over the network: roughly a third more compute for a training step, since the backward pass costs about twice a forward pass. Chen et al. report 30 percent extra runtime for their sublinear-memory strategy in their experiments.

Here is the idea made executable. A chain of 64 tanh layers is differentiated by hand in NumPy, once storing every layer input and then with checkpoints every k layers. The code counts the activation tensors held at peak and the layer forward evaluations performed, and checks that the gradients are identical:

import numpy as np
rng = np.random.default_rng(0)
n, width, batch = 64, 128, 32
Ws = [rng.normal(0, 1/np.sqrt(width), (width, width)) for _ in range(n)]
x = rng.normal(size=(batch, width))
target = rng.normal(size=(batch, width))

def layer(a, W): return np.tanh(a @ W)
def layer_back(a_in, W, g_out):
    pre_grad = g_out * (1 - np.tanh(a_in @ W) ** 2)    # recompute tanh from the saved input
    return pre_grad @ W.T, a_in.T @ pre_grad            # (grad wrt input, grad wrt W)

def run(keep_every):
    """keep_every=1 stores every layer input; k>1 stores every k-th and recomputes the rest."""
    stored, forward_calls = {}, 0
    a = x
    for i, W in enumerate(Ws):
        if i % keep_every == 0: stored[i] = a
        a = layer(a, W); forward_calls += 1
    g = 2 * (a - target) / batch                          # d(mean squared error)/d(output)
    grads = [None] * n
    for start in range(((n - 1) // keep_every) * keep_every, -1, -keep_every):
        seg = list(range(start, min(start + keep_every, n)))
        inputs, a = {}, stored[start]
        for i in seg:                                      # recompute the segment's inputs
            inputs[i] = a
            if i != seg[-1]:
                a = layer(a, Ws[i]); forward_calls += 1      # extra forward work
        for i in reversed(seg):
            g, grads[i] = layer_back(inputs[i], Ws[i], g)
    peak = len(stored) + keep_every if keep_every > 1 else len(stored)
    return grads, forward_calls, peak

g1, f1, peak1 = run(1)
for k in (1, 4, 8, 16):
    g, f, peak = run(k)
    err = max(np.abs(a - b).max() for a, b in zip(g, g1))
    print(f"keep every {k:2d}: activation tensors held at peak {peak:3d}, layer forwards {f:3d}, max grad diff vs stored-all {err:.1e}")
keep every  1: activation tensors held at peak  64, layer forwards  64, max grad diff vs stored-all 0.0e+00
keep every  4: activation tensors held at peak  20, layer forwards 112, max grad diff vs stored-all 0.0e+00
keep every  8: activation tensors held at peak  16, layer forwards 120, max grad diff vs stored-all 0.0e+00
keep every 16: activation tensors held at peak  20, layer forwards 124, max grad diff vs stored-all 0.0e+00

Keeping every 8th layer holds 16 tensors instead of 64 (a four-fold cut) for 120 layer evaluations instead of 64, and the gradients are bit-for-bit the same. Counting the whole step (a forward costs 1 unit, a backward about 2), the extra 56 forward evaluations add 56 / (64 × 3), about 29 percent. The curve is also flat near the optimum: k = 4 and k = 16 both hold 20 tensors, which is the n/k + k trade-off at work.

Selective recomputation. Full checkpointing recomputes everything, including the expensive matrix multiplications, to save memory that is mostly not in them. Korthikanti et al. (2022) observed that the big, cheap-to-recompute part of a layer is the attention-score matrices (the 5·a·s/h term above): they take a lot of memory but little arithmetic. Recomputing only those, and saving the rest, cuts activation memory a lot for a small time cost. The paper reports that, combined with tensor and sequence parallelism, it reduces activation memory by 5 times and cuts the execution-time overhead of recomputation by over 90 percent; for a 530B-parameter model on 2,240 A100 GPUs they report 54.2 percent model FLOPs utilisation against 42.1 percent with full recomputation. FlashAttention achieves the same effect inside the kernel, which is why it is the default in modern training code. The "selective" column in the table above is what you get.

Other levers

  • Lower-precision optimiser state. 8-bit Adam stores the two moments in about 2 bytes per parameter instead of 8. It exists in bitsandbytes; quality is generally reported as comparable, but you should check on your task.
  • Fewer trainable parameters. LoRA freezes the weights and trains small low-rank adapters. Gradients and optimiser state exist only for the adapters (a fraction of a percent of the model), so the 12 + 2 bytes per parameter mostly vanish. Activations are still needed to back-propagate through the frozen layers.
  • Lower-precision weights. Storing a frozen base in 4-bit form cuts its footprint to a quarter of bf16 ( chapter 19 explains how without ruining accuracy).
  • Offloading. Park optimiser state (and sometimes weights) in CPU RAM or on NVMe disk and move pieces in when needed. ZeRO-Offload and ZeRO-Infinity do this. It trades GPU memory for PCIe and disk bandwidth, which is far slower than HBM, so it is a last resort for small clusters rather than a speed-up.
  • Sharding. Split the model states across many GPUs so each holds only a slice. This is the subject of the next chapter and is how 7B-and-up models are trained at all.
  • Avoid materialising the logits. The output layer produces s × b × V numbers: at s = 4,096, b = 4 and V = 128,000 that is 2 billion entries, 8 GB in fp32 before the softmax and its gradient. Chunked or fused cross-entropy implementations compute the loss in slices and avoid storing the full tensor. This is why vocabulary size shows up in memory budgets.

A training step as a memory timeline

Memory is not constant during a step; it rises and falls, and the peak is what crashes you. Step through one iteration of a 1.3-billion-parameter model (24 layers, h = 2048, vocabulary 50,257), sequence length 2,048 and micro-batch 1, using the mixed-precision recipe. The numbers come from the same formulas as above and ignore logits and fixed overhead for clarity. The dashed line is a 24 GB card.

Step through

One training step, memory over time

  1. Start of the step: 18.4 GB. Weights (2.6 GB) and optimiser state with master weights (15.7 GB) are resident all the time. Before any data flows, three quarters of a 24 GB card is gone.
  2. End of the forward pass: 29.8 GB. Every layer has saved its activations: 11.5 GB at sequence length 2,048 and batch 1 with no saving strategy. This is the peak, 5.8 GB above the card. The job crashes here, deep into the first step, with an out-of-memory error.
  3. Mid backward: 25.4 GB. As the backward pass walks from the last layer to the first, it frees each layer's activations after using them, while gradients (2.6 GB when complete) accumulate. Memory is falling but is still above the line.
  4. End of backward: 21.0 GB. All activations are freed, all gradients exist. Notice that this point would have fitted: the problem is only the peak.
  5. After the optimiser update: 18.4 GB. The optimiser reads gradients and updates master weights, moments and the bf16 weights; gradients are zeroed or freed. Back to the start.
  6. The same step with activation checkpointing: peak 19.0 GB. Only each layer's input (0.2 GB in total) plus one layer rebuilt at a time (0.5 GB) is stored. The step now fits with 5 GB to spare, which can buy a larger micro-batch, at the cost of about one extra forward pass of compute.

Real peaks are higher than this idealisation for three reasons. The framework's caching allocator (PyTorch's, for example) keeps freed blocks for reuse rather than returning them to the driver, so nvidia-smi shows reserved memory, which is more than the memory tensors actually use. Fragmentation (free memory in pieces too small for the next large request) can cause an OOM when plenty of bytes are nominally free. And temporary buffers inside kernels and communication libraries add spikes. Hence the fixed 1.5 GB overhead in the calculator below, which is an assumption, not a measured constant.

Systems connection

This is the memory hierarchy with a hard limit and no swap. An operating system faced with too little RAM pages memory out to disk and keeps running slowly; a GPU framework raises an error instead, because paging over PCIe would be so slow that training would appear to hang. The caching allocator and its fragmentation are the same problems a malloc implementation has, and the GPU's high-bandwidth memory is the resource that matters. Estimating before you launch is capacity planning applied to a single machine.

Worked example: what fits on one 24 GB GPU

Use the calculator or the arithmetic above to answer three questions a practitioner asks all the time. All assume sequence length 2,048 and micro-batch 1.

  • Full fine-tuning a 1.3B model with standard mixed-precision Adam? States are 21 GB. With stored activations (11.5 GB) it does not fit. With full checkpointing it needs about 21 + 0.7 + logits (0.4) + overhead (1.5), around 23.6 GB: just fits, with no room for a larger batch. A realistic recommendation: use an 8-bit optimiser or LoRA, or move to an 80 GB card.
  • LoRA on a 7B-class model with a bf16 base? The frozen weights take 13 GB; adapters, their gradients and their optimiser state add under 1 GB. Activations with selective recomputation at s = 2,048, b = 1 are 8.5 GiB, so the total is about 24.4 GB with the assumed overhead: just over the card. Full checkpointing (1.4 GiB) brings it to about 17 GB, which is comfortable.
  • QLoRA on a 7B-class model? A 4-bit base is about 3.3 GB. Activations with full checkpointing add 1.4 GiB. This leaves ample room, and even a 13B-class model fits (6.4 GB of 4-bit weights). This is the reason QLoRA made large-model fine-tuning possible on consumer cards.

State of play, October 2026

NVIDIA's product pages list the A100 80 GB with 80 GB HBM2e and 2,039 GB/s memory bandwidth (SXM), and the H100 SXM with 80 GB and 3.35 TB/s; the RTX 4090 has 24 GB of GDDR6X. The H100 page quotes 1,979 TFLOPS of bf16 tensor throughput with a footnote that this figure assumes structured sparsity; the dense figure is half of that (about 990 TFLOPS), and real training reaches a fraction of it. Llama 3 405B's pretraining ran at 38 to 43 percent model FLOPs utilisation on up to 16,384 H100s (Dubey et al., 2024). Newer accelerators with larger memory, and lower-precision training formats such as fp8, are in use; this chapter's accounting method stays valid but the bytes per parameter change with the recipe, so recompute them for yours. Specifications change with every generation: check the vendor's current datasheet rather than this page.

Try it yourself

Predict, then measure. Take the 124M-parameter GPT-2 small shape (L = 12, h = 768) and, if you have a GPU or a free Colab session, run a few training steps with the PyTorch snippet below. Then compare with torch.cuda.max_memory_allocated() (tensors) and max_memory_reserved() (what the allocator holds). If your prediction is off by more than 30 percent, find which of the four categories explains the gap. No GPU? Edit memory_budget.py and answer: for a 24 GB card, which is the largest model shape that fits full fine-tuning with 8-bit Adam and full checkpointing?

import torch
torch.cuda.reset_peak_memory_stats()
for step in range(3):
    loss = model(batch).loss          # forward: activations accumulate
    loss.backward()                   # backward: activations freed, grads appear
    optimizer.step(); optimizer.zero_grad(set_to_none=True)
    print(step,
          f"allocated peak {torch.cuda.max_memory_allocated()/1e9:.2f} GB",
          f"reserved peak {torch.cuda.max_memory_reserved()/1e9:.2f} GB")
# Expect: step 0 lower than steps 1 and 2, because optimiser state is allocated lazily on the first step.

Key takeaways

  • Training memory has four parts: weights, gradients, optimiser state (together the model states) and activations. The first three scale with parameter count, the last with batch and sequence length.
  • Mixed-precision Adam costs 16 bytes per parameter: 2 (bf16 weights) + 2 (bf16 gradients) + 12 (fp32 master weights and two moments). A 7B-class model needs roughly 105 GB of state; a 24 GB card trains about 1.2B parameters with this recipe.
  • The fp32 master copy exists because bf16 cannot represent small updates; without it the weight stops moving.
  • Activation memory per layer is about s·b·h·(34 + 5·a·s/h) bytes; the s² term is why long sequences blow up and why FlashAttention and selective recomputation matter.
  • Gradient accumulation gives the same gradient with a smaller micro-batch; activation checkpointing trades roughly one extra forward pass for O(√n) activation memory.
  • Peaks, not averages, cause OOM; the peak is usually at the end of the forward pass, and real peaks exceed paper estimates because of caching and fragmentation.

Further reading

  • Rajbhandari et al., "ZeRO: Memory Optimizations Toward Training Trillion Parameter Models" (2019). Section 3 is the clearest accounting of model-state memory (the 2 + 2 + K rule) and the activation and buffer overheads.
  • Korthikanti et al., "Reducing Activation Recomputation in Large Transformer Models" (2022). Derives the per-layer activation formula used here and introduces selective recomputation.
  • Chen et al., "Training Deep Nets with Sublinear Memory Cost" (2016). The original checkpointing paper, with the O(√n) result and a 30 percent runtime cost.
  • Micikevicius et al., "Mixed Precision Training" (2018). Why a 32-bit master copy of the weights is kept, and loss scaling.
  • Dettmers et al., "8-bit Optimizers via Block-wise Quantization" (2021). Optimiser state in 8 bits, with comparable results reported on the tasks tested.
  • PyTorch documentation, "CUDA semantics: memory management". How the caching allocator reserves memory and how to read its statistics.
  • Stanford CS336, "Language Modeling from Scratch". Lectures and assignments on resource accounting and memory-efficient training.

Check your understanding

You want to fully fine-tune a 3-billion-parameter model with mixed-precision Adam. Roughly how much memory do the weights, gradients and optimiser state need, before activations?

  1. 6 GB, because bf16 weights take 2 bytes each
  2. 48 GB, from 16 bytes per parameter
  3. 12 GB, because Adam adds 4 bytes
  4. It depends mostly on the batch size
3 × 109 parameters at 2 + 2 + 12 = 16 bytes is 48 GB. Answer 1 counts only the weights. Model states do not depend on batch size at all; that is the activations' job.

A job runs for the first forward pass, then dies with an out-of-memory error. Reducing the micro-batch from 8 to 2 fixes it. Which category was over budget?

  1. Weights
  2. Optimiser state
  3. Gradients
  4. Activations
Only activations scale with micro-batch size. The first three are the same at batch 1 or 100. If the model states had been too big, the job would have failed at or before the first optimiser step regardless of the batch.

Why is a 32-bit master copy of the weights kept in mixed-precision training?

  1. bf16 cannot represent updates much smaller than the weight itself, so they would round to nothing
  2. The GPU's tensor cores can only multiply 32-bit numbers
  3. It makes the forward pass faster
  4. It is needed to compute gradients
A bf16 weight near 1.0 has gaps of about 0.004 to 0.008, so an update of 0.001 disappears (the chapter's NumPy run left the weight at exactly 1.0 after 1,000 steps). Tensor cores do multiply in bf16, and the master copy costs memory and time rather than saving it.

Activation checkpointing with a checkpoint every √n layers of an n-layer network changes training how?

  1. It lowers parameter memory by √n and costs nothing
  2. It changes the gradients slightly in exchange for memory
  3. It cuts stored activations from O(n) to O(√n), gives the same gradients, and adds about one extra forward pass of compute
  4. It removes the need for the backward pass through checkpointed layers
The demo showed identical gradients, 16 tensors instead of 64, and extra layer forwards. Checkpointing does not touch parameters, and every layer still gets a backward pass: the activations are rebuilt first.

A colleague doubles the sequence length from 2,048 to 4,096 and keeps everything else fixed, with no FlashAttention. Which statement about activation memory per layer (Korthikanti's formula) is closest?

  1. It exactly doubles, because sequence length is linear in the formula
  2. It more than doubles, because the attention-score term grows with the square of the sequence length
  3. It stays the same, because activations depend only on batch size
  4. It halves, because longer sequences are processed in parallel
The 34·s·b·h part doubles, but the 5·a·s²·b part quadruples. In the chapter's 7B-class table, going from 2,048 to 4,096 at batch 1 raises the stored total from 28.5 to 97.0 GiB, more than three times.

You must fine-tune a 13B-class model on a single 24 GB GPU. Which plan is the most plausible?

  1. QLoRA: a 4-bit frozen base (about 6.4 GB), small adapters, and activation checkpointing
  2. Full fine-tuning with mixed-precision Adam at batch size 1
  3. Full fine-tuning with a very small learning rate
  4. LoRA over a bf16 base, which only needs the weights (about 25 GB)
Full fine-tuning needs about 204 GB of states however small the batch or learning rate. LoRA over bf16 weights needs about 25 GB for the weights alone, which already exceeds the card. Only the 4-bit base leaves room for adapters and activations.

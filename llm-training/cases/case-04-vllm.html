vLLM and PagedAttention

Kwon and colleagues (SOSP 2023), in "Efficient Memory Management for Large Language Model Serving with PagedAttention", observed that LLM serving systems of the time wasted most of the GPU memory they set aside for the KV cache. Their fix is borrowed directly from operating systems: split each request's cache into small fixed-size blocks, keep a table that maps logical blocks to wherever they happen to sit in physical memory, and allocate on demand. The resulting engine, vLLM, became one of the most widely used open-source ways to serve language models. This case study works through the problem, the mechanism, the numbers and the later critiques.

What I could and could not read

I fetched and read the full text of the arXiv version of the paper (2309.06180v1, 12 September 2023), including the evaluation and the block-size study. I also fetched the current vLLM documentation page on prefix caching (the v0.11.1 version) and the vLLM page describing the original PagedAttention kernel design, and the abstract page (only) of the vAttention paper. All performance numbers are the paper's own: measured by the authors on their own re-implementation of one baseline (Orca was not public, so they built a version of it under three assumptions), on Google Cloud A100 machines, with synthetic request traces built from the ShareGPT and Alpaca datasets. I did not run vLLM, and I did not read vLLM's source code, so I say nothing about how today's implementation differs beyond what its documentation states.

The pattern in one sentence

When a resource grows unpredictably and each user's data does not need to be contiguous, stop reserving it in one big piece: hand it out in small fixed-size blocks on demand and keep an indirection table, as an operating system does with virtual memory.

Context: the cache that did not fit

If you have read chapter 18, you know the shape of the problem. A decoder-only Transformer stores, for every token already in a conversation, a key and a value vector in every layer, so it need not recompute them. That store, the KV cache, grows by one entry per generated token, and nobody knows in advance how many tokens an answer will take. Serving many requests at once is what makes a GPU efficient, so how many requests fit in memory decides how much throughput you get.

The paper puts numbers on it for OPT-13B, a 13-billion-parameter model. The KV cache of one token takes 800 KB, from 2 (key and value) × 5,120 (hidden size) × 40 (layers) × 2 bytes (FP16). A single request may use up to 2,048 tokens, so up to 1.6 GB. On a 40 GB A100, the paper's Figure 1 shows about 65% of memory holding the model weights (26 GB), and "close to 30%" the KV cache: tens of requests at most, even if memory were used perfectly.

KV block
A fixed-size chunk of the cache holding the keys and values of a fixed number of tokens (16 by default in vLLM).
Block table
Per request, the list that maps each logical block to the physical block that actually holds it; the analogue of an OS page table.
Internal fragmentation
Reserved memory that a request never uses because it was sized for the worst case.
External fragmentation
Free memory too scattered in odd-sized gaps to satisfy a request that needs one contiguous piece.
Copy-on-write
Letting several users share a block until one needs to change it, at which point that user gets a private copy.
Preemption
Evicting a running request's cache to make room, then restoring it later by swapping to CPU memory or by recomputing.

The problem: reserving for the worst case

Existing systems stored each request's KV cache as one contiguous tensor, "as most deep learning frameworks require tensors to be stored in contiguous memory". Since the output length is unknown, they reserved space for the model's maximum length (2,048 tokens in the paper's example) when the request arrived. The paper names three sources of waste: reserved slots for future tokens, internal fragmentation from over-provisioning, and external fragmentation from the memory allocator. Reserved space is eventually used, but it blocks other requests for the whole life of the request.

The authors measured this in their experiment (Figure 2): in the three baseline variants, only 20.4% to 38.2% of KV cache memory held actual token states. The variants are Orca (Max), which reserves 2,048 tokens per request, at 20.4%; Orca (Pow2), which over-reserves output space by at most 2×, at 26.8%; and Orca (Oracle), an unrealistic upper bound that magically knows each output length, at 38.2%. For vLLM the figure is 96.3%. A second inefficiency is sharing: methods like parallel sampling (several answers to one prompt) and beam search (many candidate continuations) could share the prompt's cache, but contiguous per-sequence storage makes that impossible.

The mechanism: paging for the KV cache

PagedAttention, in the paper's words, is "an attention algorithm inspired by the operating system's solution to memory fragmentation and sharing: virtual memory with paging". The mapping is explicit: "blocks as pages, tokens as bytes, and requests as processes."

The mechanism has four parts, all in sections 4 and 5 of the paper.

  1. Blocks, allocated on demand. A request's cache is divided into blocks of a fixed number of tokens. A new block is allocated only when the previous one fills. The only wasted slots are in the last, partly-filled block, so internal fragmentation is bounded by less than one block per request; because all blocks are the same size, there is no external fragmentation.
  2. A block table and a new attention kernel. Attention must now read keys and values from blocks that are not adjacent. The PagedAttention kernel looks up each logical block in the table and fetches it from wherever it lives. The paper adds that the memory-access operations are fused with other operations such as attention to hide the indirection cost.
  3. Sharing with copy-on-write. For parallel sampling, the samples' block tables point to the same physical prompt blocks, tracked with reference counts. If a sample needs to write into a shared block, vLLM copies that one block first. In beam search, candidates share large common prefixes the same way. The scheme also lets a provider keep a predefined prefix (such as a system prompt or few-shot examples) cached, "as how OS handles shared library across processes".
  4. Scheduling and preemption. Requests are served first-come-first-served. When free blocks run out, vLLM evicts all of a sequence's blocks or none of them (all-or-nothing), and sequences of one request, such as beam candidates, are scheduled as a group. Evicted blocks are restored either by swapping them to CPU RAM or by recomputing the cache by running the tokens as a new prompt (which, the authors note, is cheaper than the original generation because the whole sequence is processed in parallel in one prefill pass).

The block size is a tuning choice. In the paper's study (section 7.2), block sizes 16 to 128 gave the best results on ShareGPT, while on the shorter Alpaca requests larger blocks degraded performance because sequences became shorter than a block; the authors conclude that 16 is "large enough to efficiently utilize the GPU and small enough to avoid significant internal fragmentation in most workloads", and set it as the default. This is the same trade-off as page size in an operating system.

What the paper reports

  • Throughput. The headline claim: 2 to 4 times higher throughput than FasterTransformer and Orca at the same latency level, with more benefit for longer sequences, larger models and more complex decoding. Concretely, on the ShareGPT trace with basic sampling, vLLM sustained 1.7 to 2.7 times the request rate of Orca (Oracle) and 2.7 to 8 times that of Orca (Max) at similar latency, and up to 22 times that of FasterTransformer, which the authors say manages memory like Orca (Max).
  • More requests in flight. For OPT-13B on ShareGPT, vLLM processed 2.2 times as many requests at once as Orca (Oracle) and 4.3 times as many as Orca (Max) (Figure 13a).
  • Sharing saves memory. On the Alpaca trace, block sharing saved 6.1% to 9.8% of memory for parallel sampling and 37.6% to 55.2% for beam search; on ShareGPT, 16.2% to 30.5% and 44.3% to 66.3%. With a shared translation prefix of one example, vLLM achieved 1.67 times the throughput of Orca (Oracle), and 3.58 times with a five-example prefix.
  • An honest cost. The indirection makes the attention kernel 20% to 26% slower than FasterTransformer's highly-optimised kernel (Figure 18a). The authors argue it only affects the attention operator and is outweighed by the end-to-end gains.
  • Setup. OPT models with 13B, 66B and 175B parameters, and LLaMA-13B, on A100 GPUs on Google Cloud, with workloads synthesised from ShareGPT conversations and the Alpaca instruction dataset. ShareGPT has 8.4 times longer prompts and 5.8 times longer outputs than Alpaca on average (Figure 11), which explains why the advantage is smaller on Alpaca with the largest model, where memory was plentiful.

When the request rate exceeds a system's capacity the queue "continues to grow infinitely and so does the latency", as the paper puts it, which is why the curves explode past a threshold. That is the queueing behaviour of queueing theory for engineers: more efficient memory use moves the threshold to the right.

What the critics and later work said

  • The kernel cost and complexity. Prabhu et al. (2024), in "vAttention: Dynamic Memory Management for Serving LLMs without PagedAttention" (abstract read), argue that PagedAttention's non-contiguous layout "leads to non-trivial programming and performance overheads" (my inference, not the abstract's words: attention kernels must understand block tables). They propose keeping the cache contiguous in virtual memory and using the GPU's own virtual-memory APIs to map physical memory on demand, and report up to 1.23 times the throughput of PagedAttention-based kernels from FlashAttention and FlashInfer. This is a claim by competing authors about their own system; I have not read the full paper. It shows that the underlying idea (do not reserve worst-case memory) and the specific implementation (software block tables) can be separated.
  • Their own baseline. The authors implemented Orca themselves because it was not public. Their three variants bracket plausible behaviour, but the 2 to 4 times figure is relative to that implementation and to FasterTransformer at the time, not to later engines.
  • The idea outlived the kernel. The vLLM documentation page describing the PagedAttention kernel now carries a warning that it is "a historical document based on the original paper" which "no longer describes the code used in vLLM today". The block-based allocation survives; the specific kernel has been replaced.

Try it yourself: reservation versus paging

The toy below is my own, with request lengths I made up (log-normal, mean about 358 tokens, capped at 2,048); it is not the paper's trace. It computes the KV bytes per token for OPT-13B from the paper's formula, then compares three allocation policies for the same 5,000 requests: reserve the maximum, reserve the next power of two above the true length (which needs knowing the output length in advance, as the paper's Oracle does), and paged blocks of 16. It then shows a block table and the effect of sharing a prompt between four samples. The 10 GB cache budget is an assumption standing for "what is left on a 40 GB card after 26 GB of weights and working space".

"""Contiguous (max-length) KV reservation versus paged allocation, for OPT-13B-sized numbers from the vLLM paper.
Request lengths are an illustrative assumption (long-tailed), not the paper's traces."""
import random, math
rng = random.Random(3)

# From the paper (section 3): per-token KV cache for OPT-13B = 2 (K and V) * 5120 (hidden) * 40 (layers) * 2 bytes (fp16)
per_token = 2 * 5120 * 40 * 2
print(f"KV bytes per token: {per_token:,} ({per_token/1024:.0f} KiB); a 2,048-token request: {per_token*2048/2**30:.2f} GiB")

MAXLEN, BLOCK = 2048, 16
# Assumed: 13B weights in fp16 = 26 GB on a 40 GB A100 (paper Fig. 1), ~12 GB left; we give 10 GB to the KV cache.
KV_BUDGET = 10 * 10**9

def total_len():                       # prompt + output tokens, assumed lognormal, clipped to the model's maximum
    return max(16, min(MAXLEN, int(rng.lognormvariate(5.6, 0.8))))
lens = [total_len() for _ in range(5000)]
mean = sum(lens) / len(lens)
print(f"assumed request lengths: mean {mean:.0f}, median {sorted(lens)[2500]}, max {max(lens)} tokens")

# Policy A: reserve MAXLEN slots per request, contiguous (the 'Max' style baseline)
# Policy B: reserve next power of two above the true length (needs an oracle for the output length)
# Policy C: paged: allocate blocks of 16 tokens on demand; waste is only the last partly-filled block
def pow2(n): return 1 << (n - 1).bit_length()
def paged(n): return math.ceil(n / BLOCK) * BLOCK
def run(name, slots):
    reserved = sum(slots(n) for n in lens)
    used = sum(lens)
    # how many requests fit at once in the KV budget, on average?
    avg_slots = reserved / len(lens)
    fit = KV_BUDGET / (avg_slots * per_token)
    print(f"{name:28s} slots/request {avg_slots:7.0f}  token states are {100*used/reserved:5.1f}% of reserved memory  ->  ~{fit:5.1f} concurrent requests")
run("A reserve max (2048)", lambda n: MAXLEN)
run("B reserve power of two", pow2)
run("C paged, block = 16", paged)

# Block table for one request: logical block -> physical block, physical blocks need not be adjacent
free = list(range(100)); rng.shuffle(free)
req = 37                                  # tokens so far
table = [free.pop() for _ in range(math.ceil(req / BLOCK))]
print(f"\na {req}-token request needs {len(table)} blocks; block table (logical -> physical): {dict(enumerate(table))}")
print(f"slots wasted in its last block: {len(table)*BLOCK - req} of {BLOCK}")

# Sharing: 4 parallel samples from a 300-token prompt, each generating 100 tokens
prompt, gen, n = 300, 100, 4
without = n * math.ceil((prompt + gen) / BLOCK)
with_share = math.ceil(prompt / BLOCK) + n * math.ceil(gen / BLOCK)       # prompt blocks shared (ignoring the copy-on-write block)
print(f"4 samples, prompt {prompt}, output {gen}: {without} blocks without sharing, ~{with_share} with shared prompt blocks ({100*(1-with_share/without):.0f}% saved)")

Reading the output: 819,200 bytes per token is the paper's 800 KB (the paper writes KB; the exact value is 800 KiB), and 1.56 GiB is its "1.6 GB". Under my assumed lengths, reserving the maximum leaves only 17.5% of the reserved memory holding real tokens and fits about 6 requests in 10 GB; paging keeps 97.9% and fits about 33, a ratio of 5.6. That ratio is larger than the paper's measured 2.2 to 4.3 times more concurrent requests because my lengths are shorter and I ignore everything else a real engine's memory budget has to cover (activations, fragmentation of the block pool, minimum batch overheads). The direction and the mechanism are the point, not the constant. The last line shows prompt sharing: four samples from a 300-token prompt need 100 blocks unshared and about 47 shared (the paper reports 6.1% to 66.3% savings, depending on workload and decoding method).

The lessons

  • Measure the waste before optimising the math. The authors profiled memory and found it mostly empty. The fix needed no new model or hardware.
  • Old ideas travel. Paging, page tables, copy-on-write and swapping are decades old. Recognising that a KV cache behaves like process memory was the contribution (see virtual memory).
  • Indirection has a price. A 20% to 26% slower kernel was accepted because memory, not arithmetic, limits decoding (chapter 18). When the trade flips, as vAttention argues for some kernels, so does the design.
  • Memory management sets the batch size, and the batch size sets the cost per token. More concurrent requests per GPU is lower cost per token (chapter 22); quantising weights or the cache frees more blocks (chapter 19).
  • Shared state is a security question. Sharing blocks across requests only helps if requests that share are meant to; the current docs add a per-request salt to limit sharing to a trust group.

Analogy: a car park with no marked bays

The old scheme is a car park where every driver is told to reserve a strip long enough for a lorry, because nobody knows how big the vehicle will be. Most strips are mostly empty, and a hatchback cannot use the gap beside a van. Paging marks the car park into small identical bays: drivers take bays as they need them, in any order, and carry a card listing which bays are theirs.

Where it breaks down: a car cannot be in two bays at once, but a KV block can be shared by many requests at once, so the real system also needs reference counts and copy-on-write. And a car park does not have a kernel that must read all the bays on the card in a hurry, which is where the performance cost shows up.

Systems connection

This is the operating-system story in virtual memory: contiguous allocation causes fragmentation, paging removes it with a page table, and the cost is a translation step (in hardware the TLB, here a fused kernel). Preemption by swapping to CPU memory is paging to disk. The shared-prefix cache and its salt belong with multi-tenancy and isolation.

State of play, October 2026

The vLLM project's design documentation, as I read it, describes automatic prefix caching in which each full KV block is hashed from its parent block's hash, its own tokens and extra identifiers (such as LoRA IDs or a cache salt), blocks carry reference counts, and unreferenced blocks are evicted in least-recently-used order. The same page says a request's cache_salt limits reuse to requests with the same salt and states the purpose is to prevent timing-based attacks that infer cached content from latency; it adds that cache isolation is not supported in the older V0 engine. The docs page on the PagedAttention kernel is marked historical. The default block size, the supported attention kernels and which competing engines are fastest change with each release; I did not verify current defaults or benchmarks, so check the version of the documentation that matches what you deploy.

Key takeaways

  • OPT-13B's KV cache takes 800 KB per token, up to 1.6 GB per request; with worst-case contiguous reservation the paper measured only 20.4% to 38.2% of KV memory holding real tokens.
  • PagedAttention stores the cache in fixed-size blocks (16 tokens by default) allocated on demand, found through a per-request block table; the paper measured 96.3% useful memory for vLLM.
  • Reference counts and copy-on-write let samples, beam candidates and shared prompts share blocks, saving up to 55.2% (Alpaca trace) and 66.3% (ShareGPT trace) of memory in beam search in the paper's tests.
  • The paper reports 2 to 4 times higher throughput than FasterTransformer and Orca (its own Orca implementation) at similar latency, at the price of a 20% to 26% slower attention kernel.
  • The idea has outlived the original kernel: current docs call the kernel design historical, and alternatives such as vAttention argue for keeping memory contiguous in virtual address space.

Check your understanding

Why did contiguous per-request reservation waste so much KV cache memory?

  1. The KV cache is stored in FP32, doubling its size
  2. Requests were always generated with the maximum length
  3. Space was reserved for the maximum possible length because the output length is unknown, and the allocator also left unusable gaps between differently sized reservations
  4. The weights were duplicated for each request
The paper names reserved-but-unused slots, internal fragmentation from over-provisioning and external fragmentation. Most requests are shorter than the maximum, so most of the reservation is never filled. The weights are shared, not duplicated, and the example uses FP16.

With 16-token blocks allocated on demand, how much memory can a single request waste?

  1. At most the unfilled slots of its last block, fewer than 16 tokens' worth
  2. Up to half of its maximum length
  3. Nothing at all, because the table is exact
  4. An amount proportional to the number of other requests
Only the last block can be partly filled. Earlier blocks are full, and equal block sizes remove external fragmentation. Waste is small but not zero, which is why the paper reports 96.3% usage rather than 100%.

Four samples are drawn from the same 300-token prompt. What does copy-on-write do for them?

  1. It copies the prompt's cache four times to keep samples independent
  2. It forbids sharing because the samples' outputs differ
  3. It compresses the prompt's cache
  4. The samples' block tables point to the same physical prompt blocks, and a block is copied only when a sample must write into a shared one
The prompt's keys and values are identical for all samples, so they can be shared and reference-counted. The generated parts differ, so they live in separate blocks. The toy script shows about 47 blocks instead of 100 for this case.

A colleague reads that vLLM's attention kernel is 20% to 26% slower than FasterTransformer's and concludes vLLM must be slower end to end. What is wrong?

  1. Nothing: the paper reports vLLM slower on every workload
  2. The overhead applies only to the attention operator, while decoding is limited by memory capacity, so batching many more requests raises end-to-end throughput (2 to 4 times in the paper)
  3. The paper says the kernel measurement was a mistake
  4. The slower kernel is offset because vLLM uses a bigger GPU
The authors report the kernel overhead honestly and argue it is small relative to the gains from fitting more requests in memory. Both systems ran on A100 GPUs, so the GPU size does not explain the result.

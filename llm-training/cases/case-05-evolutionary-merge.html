Evolving Model Merges

Sakana AI's "Evolutionary Optimization of Model Merging Recipes" (Akiba et al., 2024) asked whether the knobs of a model merge, which models, how much of each, which layers, in which order, could be set by an evolutionary search instead of by a practitioner's intuition. Their headline result is a 7 billion parameter Japanese model that solves grade-school maths problems in Japanese, built from three existing open models with no gradient training. This case reads the paper as a recipe: what was searched, what was scored, what the tables show, and where the numbers need careful reading.

What I could and could not read

I fetched and read the full text of the arXiv paper (2403.13187, version 2 dated 27 January 2025), including Tables 1 to 5, the method sections, the ablations, the discussion and the limitations paragraph. I also fetched and read Sakana AI's announcement post (21 March 2024, with a note that the paper was later accepted to Nature Machine Intelligence). Every number below is the paper's own and is attributed to it. I did not download or run the released models, so I cannot confirm the scores independently, and I did not fetch the Hugging Face model cards, so I say nothing about the released models' licences. The paper gives no GPU-hour figure for the search itself; where I reason about cost I label it as my own arithmetic. The merged models' behaviour in everyday use is outside what the paper measures.

The pattern in one sentence

When a procedure has many discrete and continuous settings and a cheap, trustworthy score, treat the settings as a search space and let an optimiser that needs no gradients find them, keeping the data the search sees separate from the data used to judge the result.

Context: merging was a craft

By early 2024 the Hugging Face Open LLM Leaderboard was, in the paper's words, "dominated by merged models". The paper describes merging as "a form of black art or alchemy": a practitioner picks source models and a recipe from intuition, tries it, and adjusts. If you have read chapter 16 (model merging) you know the ingredients: task vectors, weight averaging, TIES and DARE to reduce interference, and the mergekit toolkit that packages them. The paper's argument is that the number of combinations has outgrown human trial and error, and that evolution is a natural way to explore it.

The paper's second aim is more ambitious than tuning one recipe. Most community merges of the time targeted the leaderboard's fixed tasks. The authors wanted to join models from different domains, a Japanese language model and English maths models, to get a capability none of the parents had: solving maths problems and writing the reasoning in Japanese.

Merge recipe
The full set of choices that define a merge: which source models, the weight given to each, the density kept from each, and (in the data flow variant) the layer path.
Parameter space (PS) merging
Mixing the weights of several models of one architecture into a single model of the same shape, with mixing coefficients chosen per layer.
Data flow space (DFS) merging
Leaving every layer's weights untouched but choosing which layers, from which models, a token passes through, in which order.
CMA-ES
Covariance matrix adaptation evolution strategy: an evolutionary optimiser that samples a population of candidate settings from a Gaussian, keeps the best, and adapts the Gaussian's centre and shape. It needs scores, not gradients.
Fitness
The number the search maximises for a candidate. Here it is accuracy on a set of maths problems.
MGSM
A multilingual translation of a subset of GSM8k, a set of grade-school maths word problems. The paper uses its 250-problem Japanese test set as the final exam.

The mechanism: a search loop with no training in it

The loop has four parts, and none involves back-propagation. A population of candidate recipes is generated. Each candidate is turned into an actual model by weight arithmetic. The model answers a set of maths problems and its accuracy is the candidate's fitness. The optimiser uses the fitness values to propose a better population. Because evaluating a candidate costs a merge plus inference over the search problems, the cost is dominated by running the model, not by training it. The paper contrasts this with earlier neural architecture search, which had to train every candidate architecture.

Space one: mixing weights layer by layer

In parameter space the authors build on TIES-merging with DARE (see chapter 16). Each source model contributes a task vector, its weights minus the shared base model's weights. The recipe sets, for each layer, a mixing weight and a density, where density is the fraction of the task vector's entries that survive DARE's random sparsification. CMA-ES, as implemented in the Optuna library, searches these values. The paper reports the settings: all initial values 0.5, initial step size sigma 1/6, and a population size of 4 + floor(3 ln n), where n is the number of parameters being optimised. The search ran for 1,000 trials and the trial with the best accuracy on the search set became the final model.

For the headline model the authors report that they simplified: each source model was treated as a single unit with two DARE-TIES parameters (a weight and a density), because richer per-layer configurations gave no notable improvement given their small search set. So the "evolved recipe" for the main PS model is a handful of numbers. The paper's Figure 3 shows the weights landing at similar values for the three models, with their sum approaching 2 rather than 1, which the authors read as a sign that amplifying contributions beat plain interpolation, and a notably higher density for the Japanese model.

Space two: choosing the path through the layers

The second space is stranger. In data flow space no weights are changed. Instead the search chooses, for a token, a sequence of layers drawn from two models: after layer i of model A, go to layer j of model B. Left unconstrained the space is enormous. The paper counts (M + 1)T possible paths for M layers in total and a path of T steps, and my own arithmetic below shows that with M = 64 and T = 60 that is a 109-digit number. The authors cut it down: lay out all layers of all models in order, repeat that block r times (r = 3, so T = 64 × 3 = 192 slots), and search over a 0/1 indicator for each slot saying whether it is included. That leaves 2192 candidates, still large but tractable for an evolutionary method.

There is a catch the authors found by experiment. A layer from model B expects inputs shaped by B's earlier layers, and a token arriving from A may look different. They add a scaling matrix W, evolved together with the indicators, that rescales the signal when it hops between layers. The ablation in their Table 4 shows how much this matters: on the 13 billion parameter pair, the full model scored 34.0 on MGSM-JA and the same configuration without W scored 26.4, a drop the authors say leaves it worse than the parameter-space model it was built on. They also note that the scaling trick may not survive if one of the source models was fine-tuned much longer than the other.

For this search the authors used CMA-ES in EvoJAX for 100 generations with a population of 128, optimising on batches of 200 problems, and kept the snapshot with the best accuracy on a 200-problem validation split of the search data. They limited it to two models at a time so the result runs on a single GPU. Combining both spaces is straightforward: first merge in parameter space, put that merged model back in the pool, then search layer paths over the enlarged pool.

What the paper reports

The setup, and why it matters for the numbers

The source models were three fine-tunes of Mistral-7B-v0.1: shisa-gamma-7b-v1 (Japanese), WizardMath-7B-V1.1 and Abel-7B-002 (English maths). The test set was the 250-problem Japanese MGSM, which is a translation of the first 250 problems of GSM8k's test set. For the search the authors translated the remaining 1,069 GSM8k test problems into Japanese, so the search data and the test data are disjoint. They chose not to use the GSM8k training set because the open maths models had been trained on it, which would have made the scores meaningless. A response counted as correct only if the last number in it was right and the reasoning text was in Japanese, as judged by a language detector. Decoding was greedy and zero-shot.

The headline table

On MGSM-JA the best source model, Abel, scored 30.0. The parameter-space merge scored 52.0, the data-flow merge 36.4 and the combination 55.2. The paper lists GPT-3.5 at 50.4 and GPT-4 at 78.8. The merged models also did well on the Japanese Language Model Evaluation Harness (JP-LMEH), a nine-task suite whose average the authors use as an indicator of general Japanese ability: 70.5 for the parameter-space model against 66.1 for the Japanese source model, and 68.3 for the previous best 70B Japanese model the authors compared with (Japanese StableLM 70B). They report that the maths gain did not come at the cost of Japanese skill for the parameter-space model, though the data-flow model dropped on some tasks (Table 2 shows JNLI and MARC falling for the 10B model).

One comparison in the same table deserves to be read in full. Swallow 70B, another Japanese 70B model, averages 71.5 on JP-LMEH, above the evolved 7B model's 70.5. The paper's claim is narrower than the abstract's "surpassing models with significantly more parameters" might suggest: the evolved model beat Japanese StableLM 70B, not every 70B model.

Against doing it the usual way

Table 3 supplies the baselines that make the result meaningful. Merging the same three models with default-style recipes from mergekit gave 4.4 (TIES), 35.2 (DARE-TIES) and 0.0 (a "Frankenmerge" that stacks layers), against 52.0 for the evolved parameter-space merge and 36.4 for the data flow merge built on the same ingredients. So the search, not the choice of ingredients, produced most of the gain. Fine-tuning the same models on the same 1,069 translated problems for three epochs did worse: the best result was LoRA on WizardMath at 43.2, and several fine-tunes lowered the JP-LMEH average, which the authors read as catastrophic forgetting. They also tested what happens when irrelevant models are added to the pool (a German, a Spanish, a Chinese, a biomedical model and others). With four extra irrelevant models MGSM-JA was 48.4 against 50.0 for the three-model run, and with eight it fell to 40.8: degraded, not collapsed.

The authors also show the approach works at 13 billion parameters (Llama-2-13b derivatives), where the numbers are lower (31.2, 23.2 and 34.0 for parameter space, data flow and both, as the paper's text reports them). They attribute the gap to weaker source models, noting that Mistral-7B outperforms Llama-2-13b at basic maths. A second domain, a Japanese vision-language model built by merging a Japanese LLM into LLaVA-1.6-Mistral-7B, scored 20.4 ROUGE-L on JA-VG-VQA-500 for the best variant against 14.3 for the LLaVA source, and 51.2 on their new JA-VLM-Bench-In-the-Wild against 41.1.

Evolution as a way to find where models are wrong

The most interesting finding is not a score. In the 13B data-flow experiment the search chose to skip layer 30 of MetaMath-13B. The authors then removed that single layer from the original model and, without any other change, its MGSM-JA score rose to 10% (from 8.0). Their reading is that data-flow merging partly works by finding redundant or harmful layers for a given task, and partly by adding what a source model lacks: they show examples where the maths model reasoned correctly but answered in English, and the merged model's extra layers pulled the output into Japanese.

Common misconception

"Evolution discovered a new model without training." The merge involved no gradient updates, but the ingredients were trained, at great expense, by others. The paper itself notes that the Japanese base behind shisa-gamma involved 100 billion tokens of Japanese pretraining, "such as more than 10,000 GPU hours". Evolutionary merging reuses that sunk cost; it does not replace it, and it cannot create a capability that none of the parents has some trace of.

What the critics and the caveats say

The paper's own limitations paragraph is short: the merged models inherit their sources' limitations, produced "responses that lacked logical coherence" in places, and the study includes no instruction fine-tuning or alignment, so outputs may be factually flawed. The ethics section calls the models a proof of concept. Several further caveats come from my reading of the tables rather than from the authors, and I label them as mine.

  • Small test set (mine). 250 problems means one problem is 0.4 percentage points. The script below computes 95% intervals: the evolved 52.0% is 130 of 250 and its interval runs from about 45.8 to 58.1, which overlaps GPT-3.5's 50.4%. The gap to the best source model (30.0%) is well outside the noise; the gap to GPT-3.5 is not.
  • One search per model (mine). The paper reports a single run of each configuration. Evolutionary searches are random, and the tables give no spread across seeds.
  • Heavy-handed scoring. Taking the last number as the answer and a language detector for "written in Japanese" are practical choices the authors justify, but they define what "correct" means for every score here. A model that learns to end with a number and write Japanese is rewarded even if its reasoning is thin, a point that links to evaluator hacking.
  • Contamination is argued, not eliminated. The authors took care that search and test problems do not overlap. They also state that the maths source models were trained on the GSM8k training set, and the test is a translation of GSM8k test problems. See contamination for why such overlaps are hard to rule out for models whose training data is not public.
  • Automerger, a nearby experiment. The paper itself discusses a contemporaneous automated merging experiment that picked random pairs from the leaderboard's top models and predicts it would overfit to the leaderboard's tasks. The authors present their own choice of a task outside the leaderboard as the remedy.

State of play, October 2026

The paper says that, after the preprint, evolutionary model merging was implemented in the open-source packages MergeKit and Optuna Hub, and that related work applied it to image-generation models (EvoSDXL) and to other Japanese models (EvoVLM-JP-v2, EvoUkiyoe). I have not checked those packages or models myself, so treat that as the paper's own account. The specific source models (Mistral-7B derivatives from 2023) are well behind the frontier by now; the transferable result is the method, not these scores.

Try it yourself: evolving a layer mask, and judging the numbers

Two small scripts of mine, not the paper's code. The first runs a miniature of the data-flow idea: a stack of eight random residual layers, a task whose ideal answer needs one layer removed, and a mutate-and-keep-the-best search over a 0/1 mask with no gradients. The "harmful" layer is planted, so this shows the mechanism and the search-set-versus-test-set habit, not evidence about real models. The second computes the interval arithmetic quoted above, and the sizes of the two search spaces.

"""Toy: evolve an include/exclude mask over a stack of layers, no gradients.
A planted 'harmful' layer plays the role of layer #30 in the paper's Figure 5."""
import numpy as np
M = 8                                    # layers in the stack
rng0 = np.random.default_rng(7)
Ws = [rng0.normal(0, 0.35, (6, 6)) for _ in range(M)]   # fixed random residual blocks
HARMFUL = 3
def run(x, mask):
    h = x
    for i in range(M):
        if mask[i]:
            h = h + 0.5 * np.tanh(h @ Ws[i])
    return h
def sample(n, seed):
    return np.random.default_rng(seed).normal(0, 1, (n, 6))
# Target: what the stack does with the harmful layer removed (planted ground truth).
target_mask = np.ones(M, bool); target_mask[HARMFUL] = False
xs, xt = sample(40, 1), sample(2000, 2)              # small search set, large held-out test set
ys = run(xs, target_mask) + np.random.default_rng(3).normal(0, 0.3, (40, 6))   # noisy labels
yt = run(xt, target_mask)
def mse(mask, x, y): return float(np.mean((run(x, mask) - y) ** 2))
def fitness(mask): return -mse(mask, xs, ys)
rng = np.random.default_rng(0)
parent = np.ones(M, bool)                            # start with every layer included
print(f"all layers   search MSE {mse(parent, xs, ys):.4f}  test MSE {mse(parent, xt, yt):.4f}")
evals = 1
for gen in range(1, 11):
    kids = []
    for _ in range(8):                               # 8 children, each flips ~1 bit
        k = parent.copy(); k[rng.integers(M)] ^= True; kids.append(k)
    evals += len(kids)
    best = max(kids + [parent], key=fitness)
    if fitness(best) > fitness(parent): parent = best
    print(f"gen {gen}: mask {''.join('1' if b else '0' for b in parent)}  search MSE {-fitness(parent):.4f}")
print(f"evolved      test MSE {mse(parent, xt, yt):.4f}   candidate evaluations {evals}")
print("layer dropped:", [i for i in range(M) if not parent[i]], "(planted harmful layer:", HARMFUL, ")")
# Search-space sizes from the paper's setting (M=64 layers, T=60 path steps; then M x r=3 repeats).
print("\nraw path space (M+1)^T with M=64, T=60 has", len(str(65 ** 60)), "digits")
print("indicator-array space 2^T with T=M*r=192 has", len(str(2 ** 192)), "digits")

The search set had only 40 noisy examples and the search stopped at an MSE of 0.0927, close to the noise floor of 0.09 (0.3 squared), yet the test error on clean data is 0.0000: the evolved mask found the right structure. Notice also how little it took: 81 candidate evaluations, no gradients. In the paper's setting each "evaluation" is a pass of a 7B model over hundreds of problems, which is why the DFS search used 100 generations of 128 candidates (12,800 evaluations, my multiplication) on batches of 200 problems.

import math
def wilson(k, n, z=1.96):
    p = k / n
    d = 1 + z * z / n
    c = (p + z * z / (2 * n)) / d
    h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return c - h, c + h
for name, acc in [("Abel 7B (best source)", 30.0), ("Ours PS", 52.0), ("Ours PS+DFS", 55.2), ("GPT-3.5", 50.4)]:
    k = round(acc / 100 * 250)
    lo, hi = wilson(k, 250)
    print(f"{name:22s} {k:3d}/250 = {acc:4.1f}%   95% interval {100*lo:4.1f} to {100*hi:4.1f}")
Abel 7B (best source)   75/250 = 30.0%   95% interval 24.7 to 35.9
Ours PS                130/250 = 52.0%   95% interval 45.8 to 58.1
Ours PS+DFS            138/250 = 55.2%   95% interval 49.0 to 61.2
GPT-3.5                126/250 = 50.4%   95% interval 44.2 to 56.5

Try it yourself

In evo_toy.py, change HARMFUL to a different index, then raise the label noise from 0.3 to 1.0 and shrink the search set to 10 examples. Does the search still find the right mask? Run it with several seeds for the rng. This is the same trade-off the paper handles with disjoint search, validation and test sets. The open-ended course's chapter on held-out evaluation for self-improvers treats it in depth.

The lessons

  1. Recipes are search spaces. Any pipeline with a cheap score and many settings (merge coefficients, data mixes, prompts) can be searched. See evolutionary algorithms for the optimiser and evolving prompts and pipelines for the same idea applied to text.
  2. The score is the specification. The search gives you exactly what the metric rewards. Make the metric match the use, and keep an independent test (chapter 23).
  3. Search beats a fixed recipe, but ingredients matter. Unoptimised merges of the same models mostly failed (Table 3), yet adding eight irrelevant models still left a working merge. Cheap adaptation is real, and it is not a substitute for pretraining.
  4. Compare with the right alternative. The paper's comparison with fine-tuning on the same 1,069 problems is the one a practitioner needs. See LoRA and supervised fine-tuning for what that alternative involves.
  5. Read the small print on claims. "Beat 70B models" was true for one 70B model and false for another in the same table.

Systems connection

A search loop that scores thousands of candidates is a batch workload with a hot inner loop: merge, load, run inference, score. Treat the evaluator like any expensive dependency: cache by recipe hash, run candidates in parallel, and watch the cost the way you would for load tests (load testing and capacity planning). The GPU side of this, serving many similar models cheaply, is the subject of serving engines.

Key takeaways

  • Evolutionary merging searches merge recipes with no gradients: per-layer weights and densities in parameter space, and layer routes plus scaling in data flow space.
  • In the paper, three source models scoring 30.0 or lower on Japanese maths gave an evolved merge at 52.0 (55.2 with both spaces); default merge recipes on the same models scored 4.4, 35.2 and 0.0.
  • The merge costs far less than training, but it stands on the cost of training the parents.
  • A 250-problem test set leaves wide error bars: the gap to GPT-3.5 is inside them.
  • The search found its own bugs: skipping one layer of a source model improved that model.

Check your understanding

In the paper's parameter-space search, what is the fitness that CMA-ES maximises?

  1. The training loss of the merged model
  2. Accuracy of the merged model on 1,069 translated maths problems that are disjoint from the final test set
  3. Accuracy on the 250-problem MGSM-JA test set
  4. The JP-LMEH average
The search set was the 1,069 remaining GSM8k test problems translated into Japanese. Using the 250 MGSM-JA problems would have let the search tune itself to the exam. There is no training loss because no training occurs.

Why does the data flow search use an indicator array over r = 3 repetitions of the layers rather than searching paths directly?

  1. Direct paths are not allowed by the model architecture
  2. It makes the merged model smaller than either parent
  3. It lets the merged model skip tokenisation
  4. It shrinks a space of roughly (M+1)T paths to 2T include-or-exclude choices that evolution can handle
The authors observed that repeated or permuted sequences from early in the model hurt performance, so they search a binary inclusion mask. The model is not necessarily smaller (the DFS models are 10B or more), and tokenisation is unchanged.

The paper's Table 3 shows TIES-Merge scoring 4.4 and Frankenmerging 0.0 on MGSM-JA for the same source models, versus 52.0 for the evolved merge. What does this most directly show?

  1. The merge settings, not just the choice of ingredients, determined the result
  2. TIES-Merge can never work on language models
  3. The test set was too easy for the baselines
  4. Fine-tuning is always better than merging
Same ingredients, different recipe, very different score. The paper's own DARE-TIES baseline reached 35.2, so "never works" is too strong, and the fine-tuning comparison actually favoured the evolved merge.

The evolved 7B model scored 52.0% on 250 problems and GPT-3.5 scored 50.4% on the same set. How should you read that?

  1. The 7B model is better than GPT-3.5
  2. GPT-3.5 is better than the 7B model
  3. The difference is smaller than the sampling noise, so the two are not distinguishable on this test
  4. The comparison is invalid because GPT-3.5 is closed source
Both 95% intervals span about 12 points and overlap heavily. Closed models can be evaluated like any other by calling them, so the comparison is valid; it is just not conclusive.

Why is it wrong to say evolutionary merging creates a capable model "without any training cost"?

  1. Because CMA-ES needs gradients
  2. Because the source models were themselves expensive to train and the merge can only recombine what they contain
  3. Because merged models must be fine-tuned before use
  4. Because the search needs more GPU hours than pretraining
The merge avoids gradient updates, but its ingredients carry the training cost of their makers; the paper itself notes more than 10,000 GPU hours behind one Japanese source model. CMA-ES is gradient-free, and the search is nowhere near pretraining cost.

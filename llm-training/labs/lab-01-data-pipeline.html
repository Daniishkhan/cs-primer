Lab 1: A Pretraining Data Pipeline

Chapter 1 followed trillions of tokens from a web crawl to a training mix and said that every stage is an experiment, not a recipe. Reading about a filter is easy; judging one is a skill, and it comes from building the filter, running it on pages you can inspect and scoring it against labels. In this lab you build a miniature of the pipeline: you extract text from HTML, drop low-quality pages with C4 and Gopher style rules, remove exact copies, and then find near-duplicates with MinHash signatures and locality-sensitive hashing. A checker scores each stage against a synthetic crawl whose duplicates, spam and stubs are labelled, and the last milestone measures the precision and recall of your near-duplicate detector and sweeps its settings.

Why this lab matters

Most of the difference between a good open model and a poor one of the same size is data work that never appears in an architecture diagram, and nearly all of that work is code like this. It is also code that fails quietly. An extractor that leaks navigation text, a quality rule with a threshold one notch too strict, a deduplicator that merges two different articles: none of them crashes, and each changes what the model learns. The only defence is to measure each stage against something you know, which is what the labels in this lab are for. You will see the three effects chapter 1 described in numbers you produced yourself: junk tends to break several rules at once, so thresholds need little tuning; exact hashing alone misses most copies, because a promotional line or a changed date defeats it; and the banding parameters of LSH are a dial between missing duplicates and merging pages that are merely similar. By the end you will have a pipeline that turns 118 raw pages into 50 documents, a table of what each stage removed and why, and a feel for what the dial costs.

Deterministic, small, standard library only

The crawl is generated by corpus.py from a fixed seed: 118 HTML pages, no files to download and no network. The hash functions are fixed too, so the same code gives the same signatures on every machine (Python's built-in hash() is randomised per process, which is why the lab uses BLAKE2 from hashlib instead). Random test inputs in the checker are seeded; a failure prints the seed so you can replay it, for example python3 check.py solution 4 2 runs milestone 4 with seed 2. Python 3.9 or newer, standard library only. The whole check takes a couple of seconds. Words are split on whitespace and counted the way chapter 1's listings count them, so the numbers here are consistent with the chapter, but they are not token counts.

What you'll build

Six milestones, each adding a stage that the next one depends on:

  1. HTML to text: an extractor built on html.parser that drops navigation, scripts, styles and footers, and keeps one paragraph per line.
  2. Quality filters: the C4 line rules and nine Gopher style document rules, each of which returns a named flag, so you can see why a page was dropped.
  3. Exact and line-level deduplication: a normalised SHA-256 hash for whole documents, and removal of lines that occur in many different documents.
  4. Shingles and MinHash: 5-word shingles, Jaccard similarity, and 112-number signatures that estimate it.
  5. Locality-sensitive hashing: split signatures into bands, find candidate pairs through a hash table without comparing every pair, and derive the S-curve that tells you what the bands will catch.
  6. Evaluation and the full pipeline: precision and recall against the labelled duplicate pairs, clusters of duplicates, the whole pipeline in one function, and a sweep over the banding parameters.

Milestone 1: HTML to text

A crawler gives you the whole page: a head with a title and scripts, a navigation bar, a cookie banner, the article, a sidebar of related stories and a footer. Only the article is worth learning from. The task is called boilerplate removal, and it is harder than it sounds because boilerplate is whatever repeats across a site, and there is no tag that says which part is which. Chapter 1 reported that the choice of extractor changed benchmark scores measurably (FineWeb's authors preferred trafilatura on raw pages to Common Crawl's ready-made text), so this is a modelling decision, not a chore.

Your extractor works on tags, which is crude and good enough for the synthetic crawl. Python's html.parser.HTMLParser calls your methods as it reads: handle_starttag when a tag opens, handle_endtag when it closes and handle_data for the text between. Three details decide whether you get clean text:

  • Skipping needs a depth counter, not a flag. Text inside nav, script, style, head, header, footer and aside is dropped, but skipped tags nest (a nav inside an aside). A True/False flag switches back on at the first closing tag and leaks the rest of the outer element.
  • A newline in the source is only whitespace. HTML authors wrap lines wherever they like. A line break in the output comes from a block tag such as p, div, li or br, never from a newline character inside the text. An inline tag such as b or span must not break the line or add a space: foo<span>bar</span> is foobar.
  • Character references such as &amp; arrive decoded if you create the parser with convert_charrefs=True (the default).

Here is the extractor from the finished solution on one of the stub pages in the crawl, and then on an article (script in exp_peek.py):

Solution spoiler 
class _Extractor(HTMLParser):
    def __init__(self):
        super().__init__(convert_charrefs=True)       # &amp; arrives as "&"
        self.skip = 0                                  # how many SKIP_TAGS we are currently inside
        self.out = []

    def handle_starttag(self, tag, attrs):
        if tag in SKIP_TAGS:
            self.skip += 1
        if tag in BLOCK_TAGS:
            self.out.append("\n")

    def handle_endtag(self, tag):
        if tag in SKIP_TAGS:
            self.skip = max(0, self.skip - 1)
        if tag in BLOCK_TAGS:
            self.out.append("\n")

    def handle_data(self, data):
        if not self.skip:
            self.out.append(re.sub(r"\s+", " ", data))      # a newline in the HTML source is only a space

def extract(html):
    """Return the main text of an HTML page, one paragraph per line.

    Text inside SKIP_TAGS (and everything nested in them) is dropped. A BLOCK_TAGS tag
    starts a new line; inline tags (a, b, span) do not break the text. A newline inside the
    HTML source is just whitespace, not a line break. Whitespace inside a line is collapsed
    to single spaces, lines are stripped, empty lines are removed, and the lines are joined
    with "\\n". Hint: subclass html.parser.HTMLParser and keep a depth counter for SKIP_TAGS.
    """
    parser = _Extractor()
    parser.feed(html)
    parser.close()
    lines = [re.sub(r"\s+", " ", ln).strip() for ln in "".join(parser.out).split("\n")]
    return "\n".join(ln for ln in lines if ln)

Milestone 2: C4 and Gopher quality filters

Extraction gives you text. Quality filtering decides whether it is worth keeping, using rules cheap enough to run on every page. This milestone implements two families that chapter 1 described.

C4 line rules (Raffel et al., 2020, the T5 paper) work on single lines. A line survives if it has at least a few words, contains none of a list of giveaway strings (javascript, cookie, terms of use, privacy policy) and, optionally, ends in terminal punctuation. The punctuation rule is the interesting one: chapter 1 reported that FineWeb's authors found it gave the biggest single boost on a benchmark and also removed about 30 percent of all tokens, so you will write it as an option (require_punct) and the pipeline will switch it off.

Gopher style document rules (Rae et al., 2021, whose pipeline FineWeb and others reuse) work on the whole text and are statistical. Your quality_flags returns the names of the rules a text breaks, so a dropped page always comes with a reason:

FlagFires whenTypical culprit
lengthfewer than 50 or more than 100,000 wordsstubs such as "Page not found"
mean_word_lengthmean word length outside 3 to 10 charactersURL dumps, minified code
symbolsmore than 0.1 of # and ... per wordhashtag and ellipsis stuffing
bulletsmore than 90% of lines start with a bulletproduct lists, link farms
ellipsismore than 30% of lines end with ...truncated snippets
alphafewer than 80% of words contain a lettertables of numbers, gibberish
stopwordsfewer than two distinct words from {the, be, to, of, and, that, have, with}non-English text, keyword lists
repeated_linesmore than 30% of lines are duplicates of another line in the pagetemplated spam
boilerplatecontains "lorem ipsum" or a curly bracketplaceholder text, code and template debris

The stop-word rule is a cheap language identifier: real English contains "the" and "of" almost immediately, and German or Spanish contains none of the eight. A filter is a trade between the junk it removes and the good text it loses; here the loss is three pages, at web scale it is billions of tokens.

def c4_line_filter(text, require_punct=True):
    """Keep only lines that pass the C4 line rules (Raffel et al., 2020), joined with "\\n".

    A line is kept if it has at least MIN_LINE_WORDS words, contains none of
    BAD_LINE_SUBSTRINGS (compare in lower case), and, when `require_punct` is true, ends
    with one of TERMINAL. Chapter 1: FineWeb found the punctuation rule removed about 30%
    of all tokens, so the pipeline below switches it off.
    """
    kept = []
    for line in text.split("\n"):
        line = line.strip()
        if len(line.split()) < MIN_LINE_WORDS:
            continue
        if any(bad in line.lower() for bad in BAD_LINE_SUBSTRINGS):
            continue
        if require_punct and not line.endswith(TERMINAL):
            continue
        kept.append(line)
    return "\n".join(kept)

def quality_flags(text):
    """Names of the Gopher-style rules the text breaks (empty list = passes), in this order:

        length, mean_word_length, symbols, bullets, ellipsis, alpha, stopwords,
        repeated_lines, boilerplate
    """
    words = text.split()
    lines = [ln for ln in text.split("\n") if ln.strip()]
    n_words, n_lines = max(1, len(words)), max(1, len(lines))
    flags = []
    if not MIN_WORDS <= len(words) <= MAX_WORDS:
        flags.append("length")
    mean_len = sum(len(w) for w in words) / n_words
    if not MIN_MEAN_WORD <= mean_len <= MAX_MEAN_WORD:
        flags.append("mean_word_length")
    if sum(w.count("#") + w.count("...") for w in words) / n_words > MAX_SYMBOL_RATIO:
        flags.append("symbols")
    if sum(ln.lstrip().startswith(BULLETS) for ln in lines) / n_lines > MAX_BULLET_LINES:
        flags.append("bullets")
    if sum(ln.rstrip().endswith("...") for ln in lines) / n_lines > MAX_ELLIPSIS_LINES:
        flags.append("ellipsis")
    if sum(any(c.isalpha() for c in w) for w in words) / n_words < MIN_ALPHA_WORDS:
        flags.append("alpha")
    present = {w.strip(".,;:!?\"'()").lower() for w in words} & STOPWORDS
    if len(present) < MIN_STOPWORDS:
        flags.append("stopwords")
    if (len(lines) - len(set(lines))) / n_lines > MAX_DUPLICATE_LINES:
        flags.append("repeated_lines")
    low = text.lower()
    if "lorem ipsum" in low or "{" in text:
        flags.append("boilerplate")
    return flags

def keep(text):
    """True if the text breaks none of the quality rules."""
    return not quality_flags(text)

Milestone 3: exact and line-level deduplication

The web repeats itself: mirrors, syndicated articles, pasted licences and templates. Duplicates cost twice, once in wasted compute and once in memorisation (Lee et al., 2021, whose numbers chapter 1 quotes). Two cheap methods come before the expensive one.

Exact deduplication hashes each document and keeps the first of every hash. The trap is what you hash. The hash of the raw text changes if one character does, so two copies of an article that differ in capitalisation, spacing or a trailing exclamation mark look unrelated. Hashing a normalised text (lower-cased, punctuation and whitespace runs reduced to one space) catches those, at no real cost. Use a cryptographic hash such as SHA-256 so that accidental collisions are not a worry (see applied cryptography for what makes a hash collision-resistant).

Line-level deduplication removes lines that appear in many different documents. "Subscribe to our newsletter for weekly updates." is a perfectly good English sentence and carries no information; it turns up on thousands of otherwise unrelated pages. Llama 3's pipeline, following ccNet, removes lines that occur more than 6 times within each bucket of 30 million documents (chapter 1). Your version counts, for every distinct line, in how many documents it occurs, and deletes the lines over a threshold.

The order matters, and the checker measures it. In the crawl, some pages carry a promotional line in the body and their exact copies carry a different one. Hashing the texts as they are finds only a handful of copies; removing the shared promotional lines first lets exact deduplication see through them.

Solution spoiler 
def normalise(text):
    """Lower-case, replace every run of non-alphanumeric characters by one space, strip."""
    return re.sub(r"[^a-z0-9]+", " ", text.lower()).strip()

def exact_dedupe(docs):
    """Keep the first document of each distinct normalised text.

    docs: list of (id, text). Returns (kept, dropped): `kept` is the list of (id, text)
    in the original order; `dropped` maps each removed id to the id of the copy it
    duplicates. Compare documents by the SHA-256 of normalise(text), not by the text.
    """
    seen, kept, dropped = {}, [], {}
    for doc_id, text in docs:
        digest = hashlib.sha256(normalise(text).encode()).hexdigest()
        if digest in seen:
            dropped[doc_id] = seen[digest]
        else:
            seen[digest] = doc_id
            kept.append((doc_id, text))
    return kept, dropped

def line_dedupe(docs, max_docs=6):
    """Remove every line that occurs in MORE than `max_docs` different documents.

    docs: list of (id, text). Count each line once per document (a line repeated inside
    one document still counts once). Returns a new list of (id, text) in the same order;
    a document whose lines are all removed keeps its id with the empty text "".
    """
    in_docs = Counter()
    for _, text in docs:
        in_docs.update(set(text.split("\n")))
    return [(i, "\n".join(ln for ln in text.split("\n") if in_docs[ln] <= max_docs)) for i, text in docs]

Milestone 4: shingles and MinHash

Most duplicates on the web are not byte-identical. The same article appears with a changed header, a corrected word, an extra sentence. To find them you need a definition of "similar" and a way to avoid comparing every pair, because comparing every pair of N documents costs N²/2 comparisons, hopeless at web scale (chapter 1 works out 5 × 1019 for ten billion documents).

The definition first. Turn each document into its set of shingles, the overlapping runs of n consecutive words (FineWeb uses n = 5). The Jaccard similarity of two documents is the size of the overlap of their shingle sets divided by the size of their union:

J(A, B) = |A ∩ B| / |A ∪ B|

It is 1 for identical documents and 0 for documents sharing no five-word run. The shingle size is a real choice, and it is why a single changed word is not a single changed shingle: one edited word spoils up to n shingles around it. The following table (script exp_shingle.py, on three pairs from the crawl) shows the dial. Short shingles make unrelated pages look related because common phrases overlap; long shingles make a lightly edited copy look different:

$ python3 exp_shingle.py
  shingle  light edit  one sentence  unrelated   P(candidate) at 14 x 8, light edit
    2-word       0.827         0.767      0.099   0.97
    3-word       0.823         0.758      0.041   0.96
    5-word       0.757         0.747      0.013   0.80
    8-word       0.685         0.743      0.003   0.50
   12-word       0.605         0.737      0.000   0.23

Jaccard is easy to compute but still expensive: sets are large. MinHash (Broder, 1997) compresses each set into a short signature of numbers whose agreement rate estimates J. Choose a random hash function h on shingles and let the MinHash of a set be the smallest h value among its members. For two sets, the minimum over their union is attained by exactly one shingle; the two minima are equal precisely when that shingle lies in both sets, which happens with probability |A ∩ B| / |A ∪ B| = J (chapter 1 gives the argument in full). With k independent hash functions, the fraction of positions where two signatures agree is an estimate of J with standard error √(J(1 − J)/k), about 0.04 for J = 0.75 and k = 112.

You do not need random permutations. The lab gives you a family of 112 functions hi(x) = (ai x + bi) mod p, with p = 261 − 1, applied to a 64-bit BLAKE2 hash of each shingle (HASH_COEFS, PRIME and base_hash in starter.py). Position i of the signature is the minimum of hi over the document's shingles. This has a property the checker uses as an exact test: the signature of a union is the position-wise minimum of the two signatures, because the minimum of a union is the smaller of the two minima. If your signatures obey that for random sets, you built MinHash and not something that merely looks like it.

How many hash functions? More buy a smaller error and cost storage and time per document. On the 43 duplicate pairs of the crawl (script exp_perm.py):

def shingles(text, n=SHINGLE_WORDS):
    """The set of overlapping n-word windows of the lower-cased text (words split on whitespace).

    A text with fewer than n words but at least one word gives a single shingle (all its
    words); an empty text gives the empty set.
    """
    w = text.lower().split()
    if not w:
        return set()
    if len(w) < n:
        return {" ".join(w)}
    return {" ".join(w[i:i + n]) for i in range(len(w) - n + 1)}

def jaccard(a, b):
    """|A & B| / |A | B|, and 0.0 if both sets are empty."""
    union = len(a | b)
    return len(a & b) / union if union else 0.0

def minhash_signature(shingle_set, num_perm=NUM_PERM):
    """The MinHash signature: for each of the first `num_perm` hash functions
    h_i(x) = (a_i * x + b_i) mod PRIME in HASH_COEFS, the minimum over the set of
    h_i(base_hash(shingle)). An empty set gives [EMPTY] * num_perm."""
    if not shingle_set:
        return [EMPTY] * num_perm
    xs = [base_hash(s) for s in shingle_set]
    return [min((a * x + b) % PRIME for x in xs) for a, b in HASH_COEFS[:num_perm]]

def estimate_jaccard(sig_a, sig_b):
    """The fraction of positions where two signatures agree."""
    return sum(x == y for x, y in zip(sig_a, sig_b)) / len(sig_a)

Milestone 5: locality-sensitive hashing

Signatures make each comparison cheap, but there are still N²/2 of them. Locality-sensitive hashing (LSH) avoids almost all comparisons by arranging for similar documents to land in the same hash bucket. Split each signature of 112 numbers into b = 14 bands of r = 8 rows. Put each band's tuple of 8 values, together with the band's index, into a dictionary that maps it to the list of documents that have it. Two documents become a candidate pair if they agree on all 8 values of at least one band. Only documents sharing a bucket are ever looked at, so the cost scales with the number of near-duplicates, not with the number of pairs.

The arithmetic is short. A single signature position agrees with probability J (milestone 4). All r positions of one band agree with probability Jr. A band fails with probability 1 − Jr, all b bands fail with probability (1 − Jr)b, so

P(candidate) = 1 − (1 − Jr)b

This is an S-shaped curve in J and the banding is the dial that moves it. The steepest part sits near (1/b)1/r, which for 14 × 8 is 0.72, in line with FineWeb's stated aim of removing documents at least 75% similar. The key implementation points are small but easy to get wrong. Include the band index in the bucket key, or a value that happens to repeat in band 3 of one document and band 4 of another is a false collision. Report each pair once, ordered. def band_keys(sig, b=BANDS, r=ROWS):
    """Split a signature into b bands of r rows. Return b hashable keys, one per band,
    each of the form (band_index, tuple_of_the_r_values). The band index is part of the
    key so a match in band 3 never collides with a match in band 4."""
    return [(i, tuple(sig[i * r:(i + 1) * r])) for i in range(b)]

def candidate_pairs(sigs, b=BANDS, r=ROWS):
    """All pairs of documents that share at least one band.

    sigs: dict id -> signature (length at least b * r). Returns a set of tuples
    (id1, id2) with id1 < id2. Use one hash table from band key to the list of ids that
    have it; never compare two documents unless they landed in the same bucket.
    """
    buckets = {}
    for doc_id, sig in sigs.items():
        for key in band_keys(sig, b, r):
            buckets.setdefault(key, []).append(doc_id)
    pairs = set()
    for ids in buckets.values():
        for i in range(len(ids)):
            for j in range(i + 1, len(ids)):
                pairs.add((min(ids[i], ids[j]), max(ids[i], ids[j])))
    return pairs

def candidate_probability(s, b=BANDS, r=ROWS):
    """P(two documents of Jaccard similarity s become a candidate pair) = 1 - (1 - s^r)^b."""
    return 1.0 - (1.0 - s ** r) ** b

def threshold(b=BANDS, r=ROWS):
    """The similarity at which the S-curve is steepest, approximately (1/b)^(1/r)."""
    return (1.0 / b) ** (1.0 / r)

def best_bands(num_perm, target):
    """Among all (b, r) with b * r == num_perm, the one whose threshold(b, r) is closest to `target`.
    Returns (b, r). If two are equally close, prefer the one with more bands."""
    options = [(b, num_perm // b) for b in range(1, num_perm + 1) if num_perm % b == 0]
    return min(options, key=lambda br: (abs(threshold(*br) - target), -br[0]))

Milestone 6: precision, recall and the full pipeline

A deduplicator makes two kinds of mistake. It can miss a duplicate, which leaves repeated text in the corpus, and it can merge two pages that are only similar, which throws away text you wanted. Measure both against the labelled duplicate pairs (the pairs of pages in corpus.gold_pairs, which share a family):

  • Precision = reported true pairs / reported pairs: of the pairs you claimed were duplicates, how many are?
  • Recall = reported true pairs / true pairs: of the real duplicate pairs, how many did you find?

(The same pair of numbers appears in retrieval evaluation and in imbalanced classification; it is the same trade-off wearing different clothes.) Pairs are not yet a corpus. To remove duplicates you group the pairs into clusters, the connected components of the graph whose edges are the pairs (union-find does it in a dozen lines), and keep one document per cluster. Because components are transitive, one wrong pair can chain two whole families into a single cluster and delete one of them, which is why the precision of the candidate pairs matters more than a pair-level percentage suggests.

The reference pipeline runs these stages in order: extract; C4 line filter with the punctuation rule off; quality flags; line deduplication; exact deduplication; near-duplicate removal. Each dropped page is recorded with the stage and a reason, so nothing disappears without an explanation. Here is its funnel on the crawl (script exp_funnel.py):

def precision_recall(predicted, gold):
    """(precision, recall) of a set of predicted pairs against the gold set.

    precision = |predicted & gold| / |predicted|, recall = |predicted & gold| / |gold|.
    An empty prediction has precision 1.0 (it claimed nothing wrong); an empty gold set
    has recall 1.0.
    """
    hit = len(predicted & gold)
    return (hit / len(predicted) if predicted else 1.0), (hit / len(gold) if gold else 1.0)

def clusters(ids, pairs):
    """Connected components of the graph whose nodes are `ids` and edges are `pairs`.

    Returns a list of sorted id lists, sorted by their first id. An id in no pair is a
    cluster of one. (Union-find, or a simple graph search.)
    """
    parent = {i: i for i in ids}

    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]          # path halving
            x = parent[x]
        return x

    for a, b in pairs:
        ra, rb = find(a), find(b)
        if ra != rb:
            parent[max(ra, rb)] = min(ra, rb)
    groups = {}
    for i in ids:
        groups.setdefault(find(i), []).append(i)
    return sorted((sorted(g) for g in groups.values()), key=lambda g: g[0])

def near_dedupe(docs, b=BANDS, r=ROWS, min_jaccard=0.0):
    """Remove near-duplicates with MinHash and LSH.

    docs: dict id -> text. Steps: shingle every text, sign it, find candidate pairs with
    `candidate_pairs`, then keep only the candidates whose TRUE Jaccard similarity is at
    least `min_jaccard` (0.0 keeps them all). Group the surviving pairs into clusters and
    keep the smallest id of each cluster.

    Returns (kept_ids, removed, pairs): kept_ids a sorted list, removed a dict mapping each
    removed id to the cluster representative that was kept, pairs the set of pairs used.
    """
    sh = {i: shingles(t) for i, t in docs.items()}
    sigs = {i: minhash_signature(s) for i, s in sh.items()}
    pairs = {p for p in candidate_pairs(sigs, b, r) if jaccard(sh[p[0]], sh[p[1]]) >= min_jaccard}
    kept, removed = [], {}
    for group in clusters(sorted(docs), pairs):
        kept.append(group[0])
        for other in group[1:]:
            removed[other] = group[0]
    return sorted(kept), removed, pairs

def run_pipeline(pages, b=BANDS, r=ROWS):
    """Run every stage on a list of corpus.Page and return a Report.

    Order: extract -> c4_line_filter(require_punct=False) -> quality_flags (drop pages with
    any flag; dropped[id] = ("quality", ",".join(flags))) -> line_dedupe -> exact_dedupe
    (dropped[id] = ("exact", kept_id)) -> near_dedupe (dropped[id] = ("near", kept_id)).
    `after_lines` is the number of documents still non-empty after line_dedupe (empty ones
    are dropped as ("lines", "empty")). `precision` and `recall` score near_dedupe's pairs
    against corpus.gold_pairs of the documents that entered it.
    """
    rep = Report(n_pages=len(pages))
    docs = []
    for p in pages:
        text = c4_line_filter(extract(p.html), require_punct=False)
        flags = quality_flags(text)
        if flags:
            rep.dropped[p.id] = ("quality", ",".join(flags))
        else:
            docs.append((p.id, text))
    rep.after_quality = len(docs)
    docs = line_dedupe(docs)
    for i, t in docs:
        if not t:
            rep.dropped[i] = ("lines", "empty")
    docs = [(i, t) for i, t in docs if t]
    rep.after_lines = len(docs)
    docs, exact_dropped = exact_dedupe(docs)
    for i, rep_id in exact_dropped.items():
        rep.dropped[i] = ("exact", rep_id)
    rep.after_exact = len(docs)
    kept, removed, pairs = near_dedupe(dict(docs), b, r)
    for i, rep_id in removed.items():
        rep.dropped[i] = ("near", rep_id)
    rep.kept, rep.after_near, rep.candidates = kept, len(kept), len(pairs)
    rep.precision, rep.recall = precision_recall(pairs, corpus.gold_pairs({i for i, _ in docs}))
    return rep

Look under the hood

  • Why the labels come from construction, not from a threshold. The duplicate pairs are labelled by how the generator made them (a copy with its wrapper changed, a copy with two words swapped, a copy with one sentence replaced), not by computing Jaccard and cutting at 0.75. That would make the evaluation circular. The cost is that some labelled duplicates sit at J = 0.74 or 0.76 and are found with probability near one half, which is exactly why recall is 0.96 and not 1.00. A real pipeline has no such labels and tunes on ablations (train small models with and without the step), as chapter 1 insists.
  • Why FineWeb deduplicated each crawl on its own. Chapter 1 explains that global deduplication across all 96 snapshots left a smaller dataset that scored no better: the pages that survived were unique because they were odd. Your pipeline deduplicates the whole crawl at once, which is right for 118 pages and a decision to revisit at scale. The strength of deduplication is a hyperparameter with an optimum.
  • The duplicates you must not remove. The six related pages quote four sentences of an article inside a new one. Their Jaccard similarity to the source article is between 0.11 and 0.17, so they are not duplicates; at 14 × 8 a pair like that is flagged with probability well under 0.1%, and at 56 × 2 with probability about 0.7, which is much of the damage in the table above. Quotation, licences and boilerplate paragraphs are the realistic version of this trap.
  • What dedup does for evaluation. The same machinery finds the overlap between a training set and a test set. Chapter 23 returns to contamination; the same leakage problem in classical machine learning is described in Leakage: The Silent Killer.

Common misconception

"Deduplicate as aggressively as you can: every duplicate is wasted compute." Each pair you merge is a decision that the two texts carry the same information, and the table above shows the price of a wrong decision. A looser threshold does not only remove more copies; it removes more of the text that merely resembles them, and it does so silently. The honest measure of a deduplicator is the pair of numbers precision and recall on labelled examples, and the honest measure of its effect on a model is a small training run with and without it.

Systems connection

MinHash with LSH is a distributed-systems algorithm as much as a statistical one. At web scale no machine holds the signatures, so the band buckets are built by a shuffle: every worker emits (band key, document id), the framework routes equal keys to the same reducer, and each reducer emits the pairs in its buckets. That is a MapReduce job, the pattern of batch processing, and the routing is the hash partitioning of partitioning and consistent hashing. The same family of ideas indexes embeddings for approximate nearest-neighbour search (chapter 11 of the retrieval course).

What you learned

  • Extraction is a modelling decision. A tag-based extractor needs a depth counter for nested skipped tags and must treat a source newline as whitespace; boilerplate that survives it becomes training data.
  • Heuristic quality rules are cheap and effective against junk, which breaks several rules at once, and blind to fluent spam and unkind to short good pages. Every rule has a precision and a cost in lost text.
  • Exact hashing misses most copies unless you normalise the text and remove shared boilerplate lines first. The order of stages is part of the algorithm.
  • MinHash turns a set into 112 numbers whose agreement rate estimates Jaccard similarity, with error about 0.04 near 0.75; the signature of a union is the position-wise minimum.
  • LSH finds candidate pairs through a hash table. The probability of a pair becoming a candidate is 1 − (1 − Jr)b, an S-curve whose threshold is near (1/b)1/r. Choosing b and r is choosing between missed duplicates and merged non-duplicates, and merging is transitive.
  • Measure each stage against labels: precision and recall for duplicates, kept and lost counts for filters.

Check your understanding

Two documents have Jaccard similarity 0.5. With 14 bands of 8 rows, roughly how often does LSH propose them as a candidate pair?

  1. About half the time, because the similarity is 0.5
  2. About 5% of the time: 1 − (1 − 0.58)14
  3. Almost never, under 0.1%, because 0.5 is below the threshold
  4. Almost always, because 14 bands give 14 chances
One band matches with probability 0.58 = 0.0039, and fourteen tries give 1 − (1 − 0.0039)14 = 0.053. The first option confuses the similarity with the candidate probability; the third forgets that the curve is smooth rather than a step, and the fourth forgets that each band needs all eight rows to agree.

You change from 14 bands of 8 rows to 7 bands of 16 rows, keeping 112 hashes. What happens?

  1. The curve moves right and steepens: fewer false alarms, but a 75%-similar pair is flagged only about 7% of the time
  2. The curve moves left: more pairs are flagged, including some that are only loosely similar
  3. Nothing changes, because the number of hash values is the same
  4. Every pair of documents is compared, so recall becomes perfect
Longer bands need more agreeing values, so a band is less likely to match; the threshold (1/7)1/16 = 0.885 sits well above 0.72. The total number of hashes sets how steep the curve can be, not where it sits. The second option describes the opposite change (more bands of fewer rows).

Why does the pipeline remove frequent lines before it hashes whole documents?

  1. Line deduplication is faster than hashing, so it saves time on every page
  2. Exact hashing cannot be applied to texts that still contain HTML
  3. A copy of an article that carries a different promotional line has a different hash, so the copy is missed until the shared line is gone
  4. Frequent lines are always spam and should be removed from the training data
A hash changes completely if one line changes. In the crawl, exact deduplication alone finds 4 of the 14 copies; after the promotional lines are gone it finds all 14. The fourth option is too strong: a frequent line is boilerplate, not necessarily spam, and chapter 1 notes that Llama 3's line filter also removes some frequent good text.

At 56 bands of 2 rows the detector reaches recall 1.00 and precision 0.52, and 13 unique pages are removed. What is the most direct fix that keeps the high recall?

  1. Increase the number of documents so the false positives are diluted
  2. Use 3-word shingles so that similar pages look more alike
  3. Merge only the pairs whose cluster has exactly two members
  4. Keep the loose candidates but verify each with the true Jaccard similarity before merging
Candidates are cheap to generate and expensive to be wrong about, so check them against the real similarity and merge only the ones above a threshold. Shorter shingles make unrelated pages overlap more, which raises false positives. Restricting cluster size ignores the cause, and more documents do not change the pair-level precision.

A MinHash signature of 112 values is compared with another and 90 positions agree. What does that estimate, and how reliable is it?

  1. The cosine similarity of the two documents, to within one percent
  2. The Jaccard similarity of their shingle sets, about 0.80, with a standard error of about 0.04
  3. The fraction of words the documents share, exactly
  4. The probability that the documents are duplicates, about 80%
Each position agrees with probability equal to the Jaccard similarity, so 90/112 = 0.80 estimates J with standard error √(0.8 × 0.2/112) = 0.038. It is a similarity of shingle sets, not of words or of cosines, and it is an estimate, not a probability of being a duplicate.

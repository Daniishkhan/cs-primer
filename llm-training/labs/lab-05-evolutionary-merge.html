Lab 5: Evolutionary Model Merging

Chapter 16 described merging as arithmetic on weights and evolutionary merging as a search over the recipe, and it ended with a warning: a search can overfit its own evaluation set. This lab builds the whole loop and then measures the warning. You start from a small network and three specialists fine-tuned from it, each good at two of six classes and ruined on the other four. You write the task-vector algebra, task arithmetic with a coefficient per task and layer, TIES-style trimming with sign election, and an evolution strategy that searches the coefficients against a small search split. The last milestone puts every method on a held-out split it never saw, and shows how much of the evolved merge's score was a loan from the search data.

Why this lab matters

Merging looks like free capability: no GPU hours, no training data, a recipe you can write in a dozen lines of YAML. The catch is hidden in the word "recipe". Every knob (a coefficient, a density, a layer range) is a free parameter, and the moment you choose knobs by scoring merges on a set of examples, you are doing model selection on that set. The score of the winner is then biased upwards by exactly the amount the search was able to fit noise. In a toy this is visible in a minute: a six-number recipe tuned on 60 examples gains eight points on those examples and almost nothing on fresh ones. At LLM scale the same effect hides inside a leaderboard number. After the lab you will have written the merge operators, understood why λ = 1/n is usually too timid and why a sign election helps, built a gradient-free optimiser, and seen the size of the winner's curse as a function of how many examples the search is allowed to look at. That last number is the one to carry into evaluating a model you trained, and it is the same discipline that held-out evaluation for self-improvers asks of any system that searches against a score.

Deterministic, small, standard library only

The "models" are 156-weight classifiers (8 inputs, 10 ReLU hidden units, 6 classes), not language models: they train in a tenth of a second, so the lab can build a dozen worlds and score thousands of merges inside the time limit. Everything is seeded. make_world(seed) builds a base model, three fine-tunes and two data splits from one integer, every evolution run takes its own random.Random, and a failing check prints the seed so you can replay it (for example python3 check.py solution 3 7 runs milestone 3 on the random cases of seed 7). Python 3.9 or newer, no NumPy, no downloads. The full check takes about five seconds. The toy keeps the structure that matters (a shared ancestor, task vectors that interfere, a score that is noisy on a small set) and drops the scale; the section "Look under the hood" lists what that costs. The lab does not use llm.py, because no chat model is involved.

What you'll build

Six milestones, each building on the previous one:

  1. Vectors of weights: task vectors, scaled additions, averaging and interpolation, and the norm and cosine that measure how much two fine-tunes disagree.
  2. Task arithmetic with coefficients: base + Σ c[t][layer] τt with a coefficient per task and per layer, and the best single λ as the baseline to beat.
  3. TIES: trim each task vector to its largest entries, elect a sign per weight, average only the entries that agree.
  4. An evolution strategy: a (μ + λ) loop with Gaussian mutation, elitism and a shrinking step size, for any score you can compute but not differentiate.
  5. Search for a recipe: evolve the merge coefficients against the search split only, starting from the plain average.
  6. The honest comparison: six methods on both splits, a protocol check that scrambles the held-out labels, and the size of the winner's curse.

The setting: three specialists and a base

A task vector (Ilharco et al., 2023, whose "Editing Models with Task Arithmetic" is the source of the idea in chapter 16) is what fine-tuning changed: τ = θft − θbase. To have something to merge, the lab builds a small family of tasks. Six Gaussian clusters in 8 dimensions are the six classes; task t owns two of them (task 0 owns classes 0 and 1, task 1 owns 2 and 3, task 2 owns 4 and 5). The classifier always chooses among all six. The base model is trained for a few steps on a small mixed sample, so it is mediocre at everything. Each specialist is the base fine-tuned for 150 steps on its own task's examples only. Because the output layer is a softmax over six classes, a specialist that never sees classes 2 to 5 learns to give them almost no probability: it gets better at its own task and forgets the rest, which is the same effect as the A-and-B toy of chapter 16. Run it:

$ python3 exp_world.py
world 0: 156 weights, search split 20 examples per task, held-out 300 per task
model         task 0  task 1  task 2    mean
base           0.467   0.923   0.373   0.588
specialist 0   0.947   0.000   0.000   0.316
specialist 1   0.137   1.000   0.017   0.384
specialist 2   0.000   0.007   0.943   0.317
average        0.717   0.883   0.617   0.739

Read the table. Each specialist scores 94% to 100% on its own task and 0% to 14% on the other two, so its mean over the three tasks is about a third. The base is mixed (92% on task 1, 47% and 37% on the others). The plain average of the three specialists lifts the mean to 0.739, better than the base on every task but task 1. The target for a merge is the best of both: one set of weights that approaches 0.95 on all three tasks, which only a router that picks the right specialist per request (the "oracle" row in milestone 6) could reach. A merge pays for combining skills in one network with a loss, and the lab measures how big that loss is and how much of it a search can win back.

The data has two splits per task, and the difference between them is the lesson. The search split has 20 examples per task (60 in all). It is the only data a merge search may look at. The held-out split has 300 per task (900 in all) and is never used for a decision, only for the report. mean_score(model, split) is the mean over the three tasks of the six-way accuracy on that task's examples, and it is the number every merge is judged by. A model is a list of four flat lists [W1, b1, W2, b2]; tensors 0 and 1 are layer 0 and tensors 2 and 3 are layer 1, so a merge can treat the two layers differently.

Milestone 1: vectors of weights

Merging is vector arithmetic on points in a space with one axis per weight, so the first job is a small algebra on models. A task vector is the displacement from the base to a specialist; add_scaled(base, v, s) walks s times along a displacement; average_models is the centroid of several points; interpolate(a, b, t) is the straight line between two models, (1 − t) a + t b, with t = 0.5 the average of the two. Two measurements describe a task vector without evaluating anything. Its norm vec_norm says how far fine-tuning moved the weights, and the cosine of two task vectors, ⟨u, v⟩ / (‖u‖ ‖v‖), says whether two fine-tunes moved them in the same direction. Cosine near 0 means unrelated edits, which is the good case for adding them: the edits do not fight. The functions return new lists and never modify their inputs; a merge that quietly edits the base in place corrupts every merge that comes after it.

Before building on interpolation, check the rule from chapter 16: merge models that share an ancestor. The experiment trains two fine-tunes of one base and two models from different random starts (with the same total number of steps), then scores the weights along the line between each pair.

Everything that follows in the lab, and every merge on a model hub, relies on the shared ancestor.

def task_vector(finetuned, base):
    """tau = finetuned - base, tensor by tensor, as a new list of four lists (inputs untouched).

    task_vector([[3.0, 1.0], [2.0]], [[1.0, 1.0], [5.0]]) == [[2.0, 0.0], [-3.0]]
    """
    return [[f - b for f, b in zip(ft, bt)] for ft, bt in zip(finetuned, base)]

def add_scaled(base, vec, scale):
    """base + scale * vec as a new model (a merge with one task vector).

    add_scaled([[1.0, 2.0]], [[4.0, -2.0]], 0.5) == [[3.0, 1.0]]
    """
    return [[b + scale * v for b, v in zip(bt, vt)] for bt, vt in zip(base, vec)]

def average_models(models):
    """The elementwise mean of several models (same shapes), as a new model.

    Weight averaging, "model soup" style: average_models([a, b]) is the point halfway along the
    straight line between a and b in weight space.
    """
    n = len(models)
    return [[sum(vals) / n for vals in zip(*tensors)] for tensors in zip(*models)]

def interpolate(a, b, t):
    """(1 - t) * a + t * b, elementwise: t = 0 gives a, t = 1 gives b, t = 0.5 the average."""
    return [[(1.0 - t) * u + t * v for u, v in zip(ta, tb)] for ta, tb in zip(a, b)]

def vec_norm(vec):
    """Euclidean (L2) norm over every entry of every tensor."""
    return math.sqrt(sum(v * v for t in vec for v in t))

def cosine(u, v):
    """Cosine similarity of two task vectors over all entries; 0.0 if either has zero norm.

    Near 0: the two tasks moved the weights in unrelated directions. Near 1: the same direction.
    """
    nu, nv = vec_norm(u), vec_norm(v)
    if nu == 0.0 or nv == 0.0:
        return 0.0
    dot = sum(a * b for tu, tv in zip(u, v) for a, b in zip(tu, tv))
    return dot / (nu * nv)

Milestone 2: task arithmetic with coefficients

Task arithmetic adds scaled task vectors to the base: θ = θbase + Σt λt τt. This lab gives each (task, layer) pair its own coefficient, so a merge is described by a table coeffs[t][l] and the sum becomes θk = θbase,k + Σt coeffs[t][layer(k)] τt,k for tensor k. Three recipe shapes cover the cases of interest, and coeffs_from_vector(w, mode) expands a flat list w into the table:

modenumbers in wmeaning
"global"1one λ for every task and layer (classic task arithmetic)
"task"3one coefficient per task, the same in both layers
"layer"6one per task and layer: w[t * 2 + l] (the "parameter space" search of Akiba et al., 2024)

Some identities pin the code down. All-zero coefficients give the base. A coefficient of 1 for task t and 0 elsewhere gives specialist t back exactly. And 1/3 for every task is the plain average of the three specialists, because base + (1/3) Σ (θt − base) = (1/3) Σ θt. That last identity is worth a second look: averaging is task arithmetic with λ = 1/n. It is also usually the wrong λ. Sweep one shared coefficient and score the merge on the held-out split, per task and on average over six worlds:

The three tasks also peak at different places: task 1, where the base was already strong, is best at λ = 0.2 to 0.3, while tasks 0 and 2 want 0.5 to 0.6. A single shared λ cannot serve all three, and that is the argument for per-task and per-layer coefficients, and therefore for a search.

def coeffs_from_vector(w, mode):
    """Expand a recipe vector w into coeffs[t][l], the coefficient for task t in layer l.

        mode "global": len(w) == 1,            coeffs[t][l] = w[0]
        mode "task":   len(w) == N_TASKS,      coeffs[t][l] = w[t]
        mode "layer":  len(w) == N_TASKS * N_LAYERS,  coeffs[t][l] = w[t * N_LAYERS + l]

    Raise ValueError if the mode is unknown or len(w) is not RECIPE_DIM[mode]. Returns a list of
    N_TASKS lists of N_LAYERS floats.
    """
    if mode not in RECIPE_DIM or len(w) != RECIPE_DIM[mode]:
        raise ValueError(f"mode {mode!r} needs {RECIPE_DIM.get(mode)} numbers, got {len(w)}")
    if mode == "global":
        return [[w[0]] * N_LAYERS for _ in range(N_TASKS)]
    if mode == "task":
        return [[w[t]] * N_LAYERS for t in range(N_TASKS)]
    return [[w[t * N_LAYERS + l] for l in range(N_LAYERS)] for t in range(N_TASKS)]

def merge_coeffs(base, tvs, coeffs):
    """theta = base + sum_t coeffs[t][layer(k)] * tvs[t][k], tensor k by tensor k. A new model.

    `tvs` is a list of N_TASKS task vectors and coeffs[t][l] the coefficient of task t in layer l
    (tensor k belongs to layer LAYER_OF[k]). All-zero coefficients give the base back; a 1 for one
    task in both layers and 0 for the others gives that task's specialist back.
    """
    merged = []
    for k, tensor in enumerate(base):
        layer = LAYER_OF[k]
        merged.append([
            tensor[i] + sum(coeffs[t][layer] * tvs[t][k][i] for t in range(len(tvs)))
            for i in range(len(tensor))
        ])
    return merged

def best_global_lambda(base, tvs, split, grid=LAMBDA_GRID):
    """Plain task arithmetic with ONE coefficient: theta = base + lam * sum_t tau_t.

    Score each lam in `grid` with mean_score(.., split) and return (best_lam, best_score). On a tie
    keep the earlier (smaller) lam in the grid.
    """
    best = None
    for lam in grid:
        score = mean_score(merge_coeffs(base, tvs, coeffs_from_vector([lam], "global")), split)
        if best is None or score > best[1]:
            best = (lam, score)
    return best

Milestone 3: TIES

Adding task vectors treats every entry as signal. Yadav et al. (2023), in "TIES-Merging: Resolving Interference When Merging Models", point at two ways that fails: many entries of a task vector are small and carry little of the task (redundant parameters), and for some weights two fine-tunes push in opposite directions (sign disagreement), so their sum is a muddy compromise. TIES is three steps, and each is a function you write.

  1. Trim. trim_topk(vec, keep) keeps the k = max(1, floor(keep · n + 0.5)) entries of largest magnitude and zeroes the rest. When two entries have the same magnitude the lower index wins, so that the answer is unique. The lab trims per tensor: the 10 entries of b1 compete only with each other, not with the 80 entries of W1, so small tensors keep some signal.
  2. Elect a sign. elect_sign(vecs) gives, per position, the sign of the sum of the trimmed entries from all tasks: the side with more total mass wins. A kept +0.5 loses to a kept −0.7, and a position where nothing survived has sign 0.
  3. Disjoint mean. disjoint_mean(vecs, signs) averages, per position, only the non-zero entries whose sign matches the elected one, and gives 0 when there are none. Zeros do not count in the denominator: one surviving entry of 0.3 and a zero from the other task averages to 0.3, not 0.15.

Here are chapter 16's six weights again, worked by the functions you will write (keep 50%, so three entries per vector survive):

$ python3 exp_ties.py 2>&1 | head -4
A             [0.8, 0.05, 0.5, -0.6, 0.02, -0.1]
B             [0.6, -0.1, -0.7, -0.5, 0.05, 0.02]
plain mean    [0.7, -0.025, -0.1, -0.55, 0.035, -0.04]
TIES keep 50% [0.7, 0.0, -0.7, -0.55, 0.0, 0.0]

The plain mean smears the third weight to −0.1; TIES sees +0.5 against −0.7, elects negative, and keeps −0.7. The second, fifth and sixth weights hold only small entries that trimming removed, so TIES leaves them at zero where the mean adds noise. One consequence deserves attention. The disjoint mean is a mean, not a sum, so a TIES vector has the size of a single task vector, not of three; the coefficient that works for it is larger than the one for a sum. merge_ties(base, tvs, keep, lam) is base + lam * ties_merge(tvs, keep), and lam has to be chosen (on the search split). def trim_topk(vec, keep):
    """Keep the k = max(1, floor(keep * n + 0.5)) entries of largest |value| (n = len(vec)), zero
    the rest. If two entries have the same magnitude the LOWER index wins. Returns a new list.

    trim_topk([0.1, -0.9, 0.4, 0.4], 0.5) == [0.0, -0.9, 0.4, 0.0]
    """
    n = len(vec)
    k = max(1, math.floor(keep * n + 0.5))
    order = sorted(range(n), key=lambda i: (-abs(vec[i]), i))
    kept = set(order[:k])
    return [v if i in kept else 0.0 for i, v in enumerate(vec)]

def elect_sign(vecs):
    """For each position, the sign (+1.0, -1.0 or 0.0) of the SUM of the vectors' entries there.

    The sign with more total mass wins, so a large +0.5 outvotes a small -0.2. `vecs` is a list of
    equal-length flat lists.
    """
    out = []
    for col in zip(*vecs):
        s = sum(col)
        out.append(1.0 if s > 0 else -1.0 if s < 0 else 0.0)
    return out

def disjoint_mean(vecs, signs):
    """For each position, the mean of the NONZERO entries whose sign equals signs[i]; 0.0 if there
    are none. Entries that disagree with the elected sign (and zeros) are left out of the mean."""
    out = []
    for col, sg in zip(zip(*vecs), signs):
        agree = [v for v in col if v != 0.0 and sg != 0.0 and (v > 0) == (sg > 0)]
        out.append(sum(agree) / len(agree) if agree else 0.0)
    return out

def ties_merge(tvs, keep):
    """TIES on a list of task vectors: trim each tensor of each task vector to its top `keep`
    fraction, elect a sign per position, take the disjoint mean. Trimming is PER TENSOR (so the
    small bias vectors keep entries too). Returns one merged task vector (four lists)."""
    merged = []
    for k in range(len(tvs[0])):
        trimmed = [trim_topk(tv[k], keep) for tv in tvs]
        merged.append(disjoint_mean(trimmed, elect_sign(trimmed)))
    return merged

def merge_ties(base, tvs, keep, lam):
    """base + lam * ties_merge(tvs, keep), as a new model."""
    return add_scaled(base, ties_merge(tvs, keep), lam)

Milestone 4: an evolution strategy

The score of a merge, accuracy on a few dozen examples, is a staircase in the coefficients: nudge one coefficient a little and the accuracy either does not change or jumps by 1/60. There is no useful gradient, and "merge, then evaluate" is a procedure rather than a formula. What the search needs is a way to climb a function it can only call. An evolution strategy does that with three ingredients: a population of candidate vectors, random mutation, and selection by fitness, the number the function returns (higher is better). Akiba et al. (2024), whose "Evolutionary Optimization of Model Merging Recipes" is the subject of case 5, used a stronger relative of this idea (CMA-ES, run through Optuna for the parameter-space search, which also learns the shape of the mutation); the lab builds the plain version in about fifteen lines.

The version here is a (μ + λ) strategy with elitism: the μ best candidates, the parents, survive from one generation to the next only if λ fresh children do not beat them. Here is one generation:

The details that matter, and that the check verifies, are these. The initial pool is x0 itself plus μ − 1 mutants of it, so the search can never end worse than where it started. Sorting is stable, which means that on equal fitness an earlier individual wins; with a staircase fitness ties are common, and without this rule the "best" individual could drift sideways onto a worse neighbour. The step size sigma is multiplied by decay after each generation. And fitness is called exactly once per individual, on a fresh list each time, because each call is a full merge and a full scoring pass and real searches are priced in evaluations. The check does not pin the order in which you draw random numbers, only these invariants, so more than one correct implementation exists.

How does the step size matter? The experiment runs the strategy on a smooth bowl (the optimum is a known point in 4 dimensions) and prints the best fitness after 0, 5, 10, 20 and 40 generations, for five settings:

A small constant step (0.1) is slow: it needs 20 generations to get close. A moderate step that decays (0.5 and 0.92) is the best here, reaching −0.005 by generation 20. A large initial step (2.0) wastes the first generations. And a decay of 0.5 is a failure of a different kind: the step is 3% of its start size after five generations, the population stalls at fitness −1.67 and never recovers, because a search cannot cross a gap larger than its step. Premature convergence like this is the usual way an evolutionary search "works" in the sense that it terminates and produces a number, and fails in the sense that matters.

Hints try without first

  • The initial pool is [(fitness(list(x0)), list(x0))] plus μ − 1 mutants. Copy x0 so that nothing you hand to fitness aliases the caller's list.
  • Child j comes from parents[j % mu], with rng.gauss(0.0, sigma) added to each coordinate. Update sigma at the end of the generation, not the start.

Solution spoiler 
def evolve(fitness, x0, rng, mu=4, lam=16, generations=15, sigma=0.4, decay=0.85):
    """A (mu + lam) evolution strategy that MAXIMISES fitness(x) over lists of floats.

    1. Initial pool: x0 itself and mu - 1 mutants of it (each coordinate plus rng.gauss(0, sigma)).
       Evaluate each exactly once. The mu best (highest fitness) become the parents.
    2. Each generation: make lam children, child j from parents[j % mu] by adding rng.gauss(0,
       sigma) to every coordinate; evaluate each child once. Pool = parents + children; the mu best
       of the pool are the next parents. Then sigma *= decay.
    Sorting must be stable, so on equal fitness an earlier individual (a parent before a child, an
    earlier child before a later one, x0 before its mutants) wins. Never mutate x0 or hand the
    same list object to fitness twice.

    Returns EvoResult(x, fitness, history, evals): the best individual, its fitness, the best
    fitness after the initial pool and after each generation, and mu + lam * generations.
    """
    pool = [(fitness(list(x0)), list(x0))]
    for _ in range(mu - 1):
        x = [v + rng.gauss(0.0, sigma) for v in x0]
        pool.append((fitness(x), x))
    pool.sort(key=lambda p: -p[0])                  # stable: earlier wins ties
    parents = pool[:mu]
    history = [parents[0][0]]
    for _ in range(generations):
        children = []
        for j in range(lam):
            x = [v + rng.gauss(0.0, sigma) for v in parents[j % mu][1]]
            children.append((fitness(x), x))
        pool = parents + children                   # elitist: parents compete with children
        pool.sort(key=lambda p: -p[0])
        parents = pool[:mu]
        history.append(parents[0][0])
        sigma *= decay
    return EvoResult(parents[0][1], parents[0][0], history, mu + lam * generations)

Milestone 5: search for a merge recipe

Now connect the two halves. A recipe is a vector w of merge coefficients; its fitness is the mean accuracy of the merged model on the search split; the starting point is the plain average, x0 = [1/3] * dim, which is a good place to start and puts a floor under the result. search_recipe(world, mode, seed, ...) wires these together and returns the best recipe and the full EvoResult. The check watches the search through a spy on the scoring function: it must make exactly one scoring call per evaluation (244 with the default settings), and none of them may be on world.hold. A search that peeks at the held-out split can look wonderful, and the number it reports is then worthless.

The fitness landscape is coarse. Each task contributes an accuracy over 20 examples, a multiple of 1/20, so the mean of three has only 61 possible values between 0 and 1. The number of plateaus is part of why a pure random search is hard to beat on a problem this small, and part of why the strategy needs its tie rule. def search_recipe(world, mode="layer", seed=0, mu=4, lam=16, generations=15, sigma=0.4, decay=0.85):
    """Evolve the coefficients of a task-arithmetic merge against world.search ONLY.

    The recipe vector w has RECIPE_DIM[mode] entries (see coeffs_from_vector). Start from the
    plain average: x0 = [1 / N_TASKS] * RECIPE_DIM[mode]. The fitness of w is
    mean_score(merge_coeffs(world.base, tvs, coeffs_from_vector(w, mode)), world.search), where
    tvs are the task vectors of world.finetunes. Run evolve with rng = random.Random(seed).

    Returns (w, result): the best recipe vector and the full EvoResult.
    """
    tvs = [task_vector(ft, world.base) for ft in world.finetunes]

    def fitness(w):
        merged = merge_coeffs(world.base, tvs, coeffs_from_vector(w, mode))
        return mean_score(merged, world.search)

    result = evolve(fitness, [1.0 / N_TASKS] * RECIPE_DIM[mode], random.Random(seed),
                    mu, lam, generations, sigma, decay)
    return result.x, result

Milestone 6: the honest comparison

The protocol that chapter 16 attributed to the Sakana paper (evolve against a training set, evaluate the final model once on a separate test set) is three rules. Decisions (which λ, which recipe, which keep) use the search split only. Reporting uses the held-out split, and the held-out numbers do not feed back into any decision; if you change the method after seeing them, they are search data now. Every method gets the same treatment: TIES and task arithmetic also choose their λ on the search split, otherwise the evolved merge looks better only because it was the only one tuned.

compare_methods(world, seed, keep, mode) returns a table with six rows, each a pair (search score, held-out score):

  • base: the starting model, for scale.
  • oracle: specialist t scored on task t only, averaged over tasks. This is not a model: it is what a router that always picks the right specialist would score, and the ceiling any single merge is chasing.
  • average: the plain mean of the three specialists, which needs no choices and so no data.
  • task arithmetic: one coefficient, chosen by best_global_lambda on the search split.
  • TIES: keep = 0.3, λ chosen from LAMBDA_GRID on the search split.
  • evolved: search_recipe(world, mode, seed).

Alongside it, optimism(table, name) is search − hold for one row, and mean_table averages a list of tables over worlds. The protocol itself is tested by a trick: the check builds a copy of the world with every held-out label shifted by one class and calls compare_methods again. Every search-split number, and therefore every decision, must be identical to the first run; only the held-out column may change. If your λ or your recipe secretly depended on the held-out data, the search column would move, and the check would say which row. def compare_methods(world, seed=0, keep=0.3, mode="layer"):
    """Score six candidates on the search split AND the held-out split.

    Returns a dict {name: (search_score, hold_score)} with the keys of METHODS, in that order:
      "base"             the base model itself
      "oracle"           specialist t scored on task t only, averaged over tasks (not a single
                         model: it is what a perfect router between the specialists would get)
      "average"          average_models of the three specialists
      "task arithmetic"  best_global_lambda chosen on world.search
      "TIES"             merge_ties with the given `keep`; lam chosen from LAMBDA_GRID by the
                         mean_score on world.search (first best on ties)
      "evolved"          search_recipe(world, mode, seed), then scored on both splits
    Every DECISION (lambda, recipe) may use world.search only. world.hold is read to report.
    """
    base, fts = world.base, world.finetunes
    tvs = [task_vector(ft, base) for ft in fts]

    def both(model):
        return (mean_score(model, world.search), mean_score(model, world.hold))

    table = {"base": both(base)}
    table["oracle"] = (
        sum(task_scores(fts[t], world.search)[t] for t in range(N_TASKS)) / N_TASKS,
        sum(task_scores(fts[t], world.hold)[t] for t in range(N_TASKS)) / N_TASKS,
    )
    table["average"] = both(average_models(fts))
    lam, _ = best_global_lambda(base, tvs, world.search)
    table["task arithmetic"] = both(merge_coeffs(base, tvs, coeffs_from_vector([lam], "global")))
    best = max(LAMBDA_GRID, key=lambda l: mean_score(merge_ties(base, tvs, keep, l), world.search))
    table["TIES"] = both(merge_ties(base, tvs, keep, best))
    w, _ = search_recipe(world, mode, seed)
    table["evolved"] = both(merge_coeffs(base, tvs, coeffs_from_vector(w, mode)))
    return table

def optimism(table, name):
    """How much better a method looked on the search split than it really is: search - hold."""
    search, hold = table[name]
    return search - hold

def mean_table(tables):
    """Average a list of compare_methods results over worlds: {name: (mean search, mean hold)}."""
    n = len(tables)
    return {name: (sum(t[name][0] for t in tables) / n, sum(t[name][1] for t in tables) / n)
            for name in tables[0]}

Look under the hood

  • What a real merge adds. A transformer has hundreds of tensors rather than four; mergekit-style configurations assign coefficients to layer ranges and to attention versus MLP blocks, and the arithmetic should run in 32-bit floats and be cast once at the end (chapter 16's warning about bfloat16 rounding small deltas away). The extra tensors enlarge the recipe space, which makes the optimism of this lab worse, not better, unless the evaluation set grows with it.
  • What the paper searched that this lab does not. Akiba et al. (2024) searched two spaces. The lab implements the parameter-space one, the mixing coefficients. Their data-flow space, which decides which layers a token passes through and in what order, has no counterpart in a four-tensor network. They also report using a separate evolution set and a single final evaluation on held-out test data, which is the protocol of milestone 6.
  • Why plain averaging does so well. Wortsman et al. (2022) report that averaging fine-tunes of one model often beats the best single member. Here the specialists have low cosine with each other and the same ancestor, which is why the average is a respectable baseline that needs no data. It is the baseline any search must beat on held-out data.
  • Why the fitness is accuracy and not loss. A smooth fitness such as the mean log-probability of the right class gives the strategy a slope on every example, and often finds better recipes on small sets than accuracy does, at the cost of rewarding confidence over correctness. The first stretch goal tests it; the optimism measurement applies unchanged.
  • What a bigger step is worth. CMA-ES, the algorithm the paper reports using, adapts both the step size and the shape of the mutation distribution from the history of successful moves. With six knobs the lab's isotropic noise is adequate; with the hundreds of coefficients of a real recipe, adaptation is what keeps a search affordable.

Common misconception

"The evolved merge scored 0.80, so that is what the merged model does." The 0.80 is the score of the best of 244 candidates on the data used to pick it. It is the maximum of many noisy estimates, and a maximum is biased upwards however good the candidates are. The honest figure is the held-out one, 0.72 here. The error is easy to make because the search loop prints a fitness at every generation, and the last printed number looks like a result. Treat it as a progress bar. The same applies when a leaderboard model came from a merge search on that leaderboard's own tasks, as chapter 16 warned; contamination and benchmark decay describes the wider problem.

Stretch goals

  • A smoother fitness. Replace accuracy by the mean log-probability of the correct class in search_recipe. Compare search score, held-out score and optimism with accuracy over ten worlds.
  • DARE. Add dare(vec, p, rng) (Yu et al., 2024): zero each entry with probability p and rescale the survivors by 1/(1 − p), so each entry keeps its expectation.   • A held-out task. Add a fourth task with classes the specialists never trained on and make it the report, while the search uses the first three. Does a recipe tuned for three skills help or hurt the fourth? That is the "unrelated skills" check chapter 16 recommends.
  • Cross-validated recipes. Split the search data in half, evolve on one half and pick among the final parents on the other. Does the second half reduce the optimism, and what does it cost in evaluations? (This is the idea behind the "selection set" of A7 chapter 16.)
  • Learn the step size. Implement the 1/5th success rule (if more than a fifth of the children beat their parent, increase sigma; otherwise decrease it) in place of the fixed decay, and compare on the bowl and on the merge search.

Systems connection

A merge search is an evaluation workload: 244 candidates times the size of the search set, each one a full forward pass. At LLM scale the cost is dominated by scoring, not by the merge arithmetic, which is why recipe searches are bounded by an evaluation budget the way a hyperparameter search is, and why the batching and caching ideas of serving engines (a prefix shared by every candidate is computed once) apply to it. The result of the search is one set of weights, and the economics of a token is where that wins over serving three specialists: one model in memory instead of three, at the price of the 23 points the oracle row shows. The protocol of milestone 6 is the same separation of duties as a deployment pipeline: the data that selects a change must not be the data that approves it, which is the principle behind validation done right and a reason a release gate should read a frozen test set that no tuning job can see.

What you learned

  • A task vector is a displacement from the base, and merging is arithmetic on displacements. It works between models with a shared ancestor: along the line between two fine-tunes of one base accuracy stays flat, and between independent runs it collapses at the midpoint.
  • Averaging is task arithmetic with λ = 1/n. When the task vectors are nearly orthogonal that shrinks each skill by a factor of n for no reason, and the best shared λ here was 0.5, not 1/3. The three tasks wanted different values, which is the case for per-task and per-layer coefficients.
  • TIES trims small entries, elects a sign per weight and averages the agreeing survivors. Its mean has the size of one task vector, so its λ differs from a sum's. In a toy with three near-orthogonal vectors it matches task arithmetic rather than beating it; its benefit grows with the number of merged models.
  • An evolution strategy needs only a score: mutate, evaluate, keep the best. Elitism, a stable sort and a decaying step make it reliable; a step that decays too fast freezes it short of the optimum.
  • The recipe search is model selection on the search split, so its reported score is inflated by the number of knobs and falls with the size of the split: +0.115 with 10 examples per task, +0.010 with 200. Choosing every λ and recipe on one split and reporting on another is the only way to know what you built.

Check your understanding

The midpoint of two fine-tunes of one base scores about the same as either end, but the midpoint of two independently trained networks loses about 17 points. Why?

  1. Independent networks are trained for fewer steps, so they are weaker
  2. Averaging always lowers accuracy, and fine-tunes of one base are simply closer to each other
  3. Hidden units in independent networks are in unrelated orders, so position-by-position averaging mixes units that do different jobs; descendants of one parent keep the parent's unit ordering
  4. The learning rate was different for the two independent runs
The experiment gives both pairs the same step budget and ends at equal accuracy, which rules out the first and last options. The second is false in the same experiment: the same-ancestor midpoint does not lose accuracy at all. The permutation symmetry of hidden units is the explanation chapter 16 gives, and it is why a merge needs a common ancestor and matching shapes.

The plain average of three specialists is task arithmetic with λ = 1/3. In the sweep the best shared λ was 0.5. What is the best explanation?

  1. The task vectors are nearly orthogonal, so they conflict little and dividing each by three discards skill that was not in the way
  2. The tasks are identical, so a larger λ just repeats the same edit
  3. λ = 0.5 is the only value for which task arithmetic is defined
  4. Larger λ always wins, and 0.5 is the largest value tried

An evolved six-coefficient recipe scores 0.80 on the 60-example search split and 0.72 on the held-out split. Which change most reliably shrinks that gap?

  1. Run more generations, so the search converges properly
  2. Use a larger population, so the best candidate is better
  3. Score the fitness on more search examples, or search fewer knobs
  4. Report the best search score instead of a single run
The gap is the selection bias of picking the best of many candidates on a small sample; it falls with the sample size (from +0.115 at 10 per task to +0.010 at 200) and rises with the number of free knobs. More generations and a larger population give the search more chances to fit noise, so they tend to widen the gap. Reporting the best search score is the error itself.

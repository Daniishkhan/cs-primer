Workbench 2: Where Training Memory Goes

Chapter 2 says full fine-tuning with Adam costs 16 bytes per parameter before a single activation is stored, and that activations grow with batch and sequence length. Here you predict each of the four buckets (weights, gradients, optimiser state, activations) for a real model from its configuration file, run one real training step, and add up the bytes of the tensors that exist afterwards. On a laptop the first three agree to the byte. The fourth is where the formula is only an estimate, and the size of its error is the interesting result.

Why measure it

An out-of-memory error arrives deep into the first step, after you have waited for the model to load. Knowing which of the four buckets is over budget tells you which remedy applies: a smaller batch only shrinks activations, while sharding, a smaller optimiser or fewer trainable weights is the only help when the model states are the problem. The habit is the same as in workbench 1: write the prediction down, then measure.

What you need

  • Part 1, your laptop: the workbench venv (see workbench 1) and about 300 MB of disk for SmolLM2-135M. A few minutes.
  • Part 2, a GPU box (optional): one 24 GB card such as an RTX 4090 and about 1 GB of disk for Qwen2.5-0.5B. About an hour. Setting one up is in Your lab machine, Option C.

Predict before you run

Chapter 2 counts the model states per parameter, then adds the activations of its Transformer-layer formula (Korthikanti et al., 2022):

model states = N × (2 + 2 + 12) = 16 N bytes
activations per layer = s · b · h · (34 + 5 · a · s / h) bytes, 16-bit

Here N is the parameter count, s the sequence length, b the batch, h the hidden size and a the number of attention heads. Everything but N comes from config.json, and N itself can be counted without downloading weights: build the model on PyTorch's meta device, which records shapes and allocates nothing.

One subtlety. The chapter's 16 bytes are 2 (bf16 weights) + 2 (bf16 gradients) + 12 (fp32 master weights and two Adam moments). This workbench trains in plain 32-bit floats instead: 4 (weights) + 4 (gradients) + 8 (two moments) = 16. The total is the same by coincidence of arithmetic, and the pieces are not. Pass --dtype bf16 and PyTorch's AdamW keeps its moments in bf16 too, so you get 2 + 2 + 4 = 8 bytes per parameter.

Your prediction

SmolLM2-135M has 134,515,008 parameters (30 layers, hidden size 576, 9 heads, feed-forward width 1,536, vocabulary 49,152, tied embeddings). In 32-bit floats, work out in MiB the weights, the gradients and the Adam state. Then the activations for a batch of 4 sequences of 256 tokens: the formula above gives 16-bit bytes, so double it for 32-bit.

Check your arithmetic

Weights and gradients: 134,515,008 × 4 = 538,060,032 bytes = 513.1 MiB each. Adam's two moments: 1,026.3 MiB. Together 2,052.5 MiB, which is 16 bytes per parameter.

Activations per layer, 16-bit: 256 × 4 × 576 × (34 + 5 × 9 × 256 / 576) = 589,824 × 54 = 31,850,496 bytes. In 32-bit that doubles to 63,700,992; times 30 layers is 1,911,029,760 bytes = 1,822.5 MiB. The predicted peak is the larger of "end of the forward pass" (weights + activations = 2,335.6 MiB) and "after the update" (all model states = 2,052.5 MiB).

Part 1: on your laptop

The venv is the one from workbench 1. The script is code/w02/training_memory.py; the same code split into cells is training_memory.ipynb.

The idea

  1. count N on the meta device; predict weights, gradients, Adam state and activations from the formulas
  2. load the model, then run one forward pass, backward pass and AdamW step on random token ids
  3. during the forward pass, a hook records every tensor autograd saves for the backward pass (weights excluded): that is the measured activation memory
  4. afterwards add up the bytes of p, p.grad and the optimiser's state tensors
  5. on CUDA or MPS also print the allocator's own count after each phase, as a second opinion
"""Where training memory goes: predict weights, gradients, Adam state and
activations from chapter 2's accounting, then add up the real tensors after
one training step and compare.

Laptop (SmolLM2-135M, 32-bit floats, CPU or Apple's MPS):
    python training_memory.py
GPU box (a 0.5B model, with CUDA's own peak counters per phase):
    python training_memory.py --model Qwen/Qwen2.5-0.5B --batch 4 --seq 512
    python training_memory.py --model Qwen/Qwen2.5-0.5B --sweep
Prediction only, no weights downloaded (reads config.json):
    python training_memory.py --model Qwen/Qwen2.5-1.5B --predict-only

Needs: torch, transformers (workbench/requirements.txt)."""
import argparse

import torch
from transformers import AutoConfig, AutoModelForCausalLM

# ── 1. Settings ──────────────────────────────────────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("--model", default="HuggingFaceTB/SmolLM2-135M")
ap.add_argument("--dtype", default="fp32", choices=["fp32", "bf16"])
ap.add_argument("--batch", type=int, default=4)        # sequences per step
ap.add_argument("--seq", type=int, default=256)        # tokens per sequence
ap.add_argument("--checkpoint", action="store_true")   # recompute layers
ap.add_argument("--predict-only", action="store_true")
ap.add_argument("--sweep", action="store_true")        # GPU: batch to OOM
args, _ = ap.parse_known_args()        # notebooks pass their own flags

if torch.cuda.is_available():
    DEVICE = "cuda"
elif torch.backends.mps.is_available():
    DEVICE = "mps"
else:
    DEVICE = "cpu"
DTYPE = torch.float32 if args.dtype == "fp32" else torch.bfloat16
B = torch.tensor([], dtype=DTYPE).element_size()      # bytes per number


def mib(n):
    return f"{n / 2**20:,.1f} MiB"


# ── 2. Predict from the config alone (chapter 2) ─────────────────────────
cfg = AutoConfig.from_pretrained(args.model)
with torch.device("meta"):                  # shapes only: no memory used
    shell = AutoModelForCausalLM.from_config(cfg)
N = sum(p.numel() for p in shell.parameters())    # tied weights count once
L, h, a = cfg.num_hidden_layers, cfg.hidden_size, cfg.num_attention_heads
s, b = args.seq, args.batch
W = N * B                                   # weights
G = N * B                                   # one gradient per weight
O = 2 * N * B                               # Adam: m and v, same dtype
# Korthikanti et al. (2022): bytes per layer for 16-bit activations,
# scaled by B / 2 for other widths. Checkpointing keeps only layer inputs.
per_layer = s * b * h * (34 + 5 * a * s / h) * B / 2
A = L * (s * b * h * B if args.checkpoint else per_layer)
print(f"model {args.model}: {N:,} parameters, {B} bytes each, "
      f"L={L}, h={h}, heads={a}")
print(f"step shape: batch {b} x {s} tokens, device {DEVICE}"
      f"{', checkpointed' if args.checkpoint else ''}")
print(f"predicted weights     {mib(W):>12}   ({B} B x N)")
print(f"predicted gradients   {mib(G):>12}   ({B} B x N)")
print(f"predicted Adam state  {mib(O):>12}   (2 x {B} B x N)")
print(f"predicted activations {mib(A):>12}   (chapter 2 formula)")
print(f"predicted model states {mib(W + G + O):>11}   "
      f"= {(W + G + O) / N:.0f} bytes per parameter")
print(f"predicted peak        {mib(max(W + A, W + G + O)):>12}   "
      "(larger of: end of forward, or after the update)")
if args.predict_only:
    raise SystemExit

# ── 3. Measure: one real training step, summing real tensors ─────────────
torch.manual_seed(0)
model = AutoModelForCausalLM.from_pretrained(args.model, dtype=DTYPE)
model = model.to(DEVICE).train()
if args.checkpoint:
    model.gradient_checkpointing_enable()
opt = torch.optim.AdamW(model.parameters(), lr=1e-5)
param_ptrs = {p.untyped_storage().data_ptr() for p in model.parameters()}


def allocated():
    """Bytes the allocator holds now (None on CPU, which has no counter)."""
    if DEVICE == "cuda":
        return torch.cuda.memory_allocated()
    if DEVICE == "mps":
        return torch.mps.current_allocated_memory()


def peak():
    if DEVICE == "cuda":
        return torch.cuda.max_memory_allocated()


saved = {}                                  # storage address -> bytes


def pack(t):
    """Called for every tensor autograd keeps for the backward pass."""
    st = t.untyped_storage()
    if st.data_ptr() not in param_ptrs:     # weights are not activations
        saved[st.data_ptr()] = st.nbytes()
    return t


def step(batch):
    saved.clear()
    ids = torch.randint(0, cfg.vocab_size, (batch, s), device=DEVICE)
    if DEVICE == "cuda":
        torch.cuda.reset_peak_memory_stats()
    rows = [("load", allocated(), peak())]
    with torch.autograd.graph.saved_tensors_hooks(pack, lambda t: t):
        loss = model(ids, labels=ids).loss
    rows.append(("forward", allocated(), peak()))
    act = sum(saved.values())
    loss.backward()
    rows.append(("backward", allocated(), peak()))
    opt.step()
    rows.append(("step", allocated(), peak()))
    return rows, act


rows, act = step(b)
w_m = sum(p.numel() * p.element_size() for p in model.parameters())
g_m = sum(p.grad.numel() * p.grad.element_size() for p in model.parameters()
          if p.grad is not None)
o_m = sum(t.numel() * t.element_size()
          for st in opt.state.values() for t in st.values()
          if torch.is_tensor(t) and t.dim() > 0)    # skip the step counter
print()
print(f"{'':22}{'predicted':>14}{'measured':>14}{'measured/pred':>15}")
for name, pred, got in (("weights", W, w_m), ("gradients", G, g_m),
                        ("Adam state", O, o_m), ("activations", A, act)):
    print(f"{name:22}{mib(pred):>14}{mib(got):>14}{got / pred:>15.3f}")
if DEVICE != "cpu":
    print(f"\nallocator after each phase ({DEVICE}):")
    for name, now, pk in rows:
        extra = f", peak during phase {mib(pk)}" if pk is not None else ""
        print(f"  {name:9}{mib(now):>12}{extra}")

# ── 4. GPU only: double the batch until the card runs out ────────────────
if args.sweep and DEVICE == "cuda":
    print("\nsweep (peak allocated memory in one step):")
    bs = b
    while True:
        try:
            opt.zero_grad(set_to_none=True)
            r, a_m = step(bs)
            print(f"  batch {bs:4d}: peak {mib(r[-1][2])}, "
                  f"activations {mib(a_m)}")
            bs *= 2
        except torch.OutOfMemoryError:
            print(f"  batch {bs:4d}: out of memory")
            break

What you should see

  • Weights, gradients and Adam state: 1.000. These are pure counting. Gradients and moments exist for every parameter, in the same width. If yours show 0.5, you passed --dtype bf16 and predicted with 4 bytes.
  • Activations: 1.023, but do not trust it. The hook found 1,864.1 MiB; the allocator independently went from 514.1 MiB (weights) to 2,385.7 MiB across the forward pass, a difference of 1,871.6 MiB, so the two measurements agree. The formula is within 2.3%, yet the Break it section shows that this is partly luck: errors in both directions cancel.
  • The allocator tells the shape of the step. After the backward pass it holds 1,087.3 MiB: weights plus gradients (1,026.3 MiB) and a little more, because the activations have been freed. After the update it holds 2,237.3 MiB: 2,052.5 MiB of model states and some leftover scratch space. The peak is at the end of the forward pass, as in chapter 2's timeline.

The weights file is 988,097,824 bytes (Hugging Face's reported size), and 494,032,768 parameters × 2 bytes = 988,065,536 bytes, so the parameter count is right to within the file header. Model states: 494,032,768 × 16 = 7,538.3 MiB. A 24 GB card has 24,576 MiB, so the states fit with room for activations.

The sweep prediction: each sequence adds 6,216 / 4 = 1,554 MiB of activations at 512 tokens. At batch 8 the end of the forward pass holds 1,884.6 + 12,432 = 14,317 MiB, and at batch 16 it would hold 1,884.6 + 24,864 = 26,749 MiB, over the card. So the prediction is: batch 4 and 8 pass, batch 16 runs out of memory. Expect the real numbers to sit above the formula, because it has no term for the logits: one fp32 copy of the output scores is 4 × 512 × 151,936 × 4 bytes = 1.16 GiB at batch 4, and the loss makes more than one copy.

Break it

Each of these re-runs the laptop script with one change. Predict first; the lines below are what this laptop printed.

  • Double the sequence: --seq 512. Prediction from the formula: the quadratic term makes activations grow by more than 2x, here to 4,995.0 MiB (2.7x). Measured: 
    predicted activations  4,995.0 MiB   (chapter 2 formula)
activations              4,995.0 MiB   4,268.3 MiB          0.855
    Activations did grow by 2.3x, not 2.7x, and the ratio fell to 0.855. The formula assumes the attention scores are stored (the 5·a·s term); PyTorch's fused attention does not store them, so the quadratic term is over-counted.
  • Halve the number width: --dtype bf16. Weights, gradients and Adam state should halve (8 bytes per parameter), and the formula halves the activations too. Measured: 
    predicted activations    911.2 MiB   (chapter 2 formula)
weights                    256.6 MiB     256.6 MiB          1.000
gradients                  256.6 MiB     256.6 MiB          1.000
Adam state                 513.1 MiB     513.1 MiB          1.000
activations                911.2 MiB   1,333.1 MiB          1.463
    The model states halve exactly. Activations do not: they came to 1,333.1 MiB against 911.2 MiB predicted, because the loss upcasts the logits to 32-bit whatever the model's width.
  • Recompute instead of store: --checkpoint. Chapter 2 predicts that only each layer's input is kept (67.5 MiB here). Measured: 
    predicted activations     67.5 MiB   (chapter 2 formula)
activations                 67.5 MiB     266.3 MiB          3.945
    Checkpointing cut the activations from 1,864.1 to 266.3 MiB, a 7x saving, but the formula says 67.5. The gap of 198.8 MiB is almost exactly one fp32 copy of the logits: 4 × 256 × 49,152 × 4 bytes = 192 MiB. The formula counts layers only, and with a small model and a large vocabulary the output layer matters.
  • On the GPU box, add --checkpoint to the sweep and predict how far the batch limit moves before you run it.

Key takeaways

  • Model states are exact bookkeeping: bytes per parameter times N, measured to the byte. The "16 bytes" depends on the recipe (here 4 + 4 + 8 in fp32; 2 + 2 + 12 in mixed precision; 8 in pure bf16).
  • Activations are an estimate. The chapter's formula was within 2% in one configuration and 3.9x off in another; it omits the logits and assumes unfused attention.
  • You can predict the parameter count from the config on the meta device, before downloading anything.
  • Predict, then measure. The disagreement tells you which term the formula leaves out.

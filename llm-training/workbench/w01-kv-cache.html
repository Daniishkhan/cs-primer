Workbench 1: The KV Cache, Measured

Chapter 18 gave you one line of arithmetic for the memory a conversation costs: two vectors per layer per key-value head per token. Here you predict that number for a real model from its configuration file alone, then load the model, run a prompt through it and add up the bytes of the tensors it actually kept. On a laptop the two numbers should agree to the byte. On a GPU you then ask the question a serving team asks every day: how many conversations fit?

Why measure it

A formula you have only read is a formula you half believe. The cache formula decides how many users one GPU can serve, why grouped-query attention exists and why long contexts are expensive, so it is worth seeing it hold on a model somebody actually ships. The habit matters more than the number: write the prediction down, then measure. When the two disagree you have found something the formula leaves out, and that is the most useful thing a measurement can tell you.

What you need

  • Part 1, your laptop: Python 3.10+, the workbench venv (below) and about 300 MB of disk for SmolLM2-135M. About 20 minutes.
  • Part 2, a GPU box (optional): one 24 GB card such as an RTX 4090, about 16 GB of disk for Qwen2.5-7B-Instruct, and about an hour. Setting one up is in Your lab machine, Option C.

Predict before you run

Recall the formula from chapter 18:

KV bytes per token = 2 × L × nkv × dhead × b

Every input is in the model's config.json. SmolLM2-135M has 30 layers (num_hidden_layers), 9 attention heads, of which only 3 are key-value heads (num_key_value_heads: grouped-query attention), and a hidden size of 576, so each head is 576 / 9 = 64 numbers wide. On Apple's GPU the script uses 16-bit floats, 2 bytes each.

Your prediction

Work it out on paper before reading on: bytes per token, and the size of the cache after a 512-token prompt. Then do the same for Qwen2.5-7B-Instruct: 28 layers, 4 key-value heads of 28, head width 3,584 / 28 = 128, bfloat16 (2 bytes).

Check your arithmetic

SmolLM2-135M: 2 × 30 × 3 × 64 × 2 = 23,040 bytes per token, and 512 tokens make 11,796,480 bytes, or 11.25 MiB. If your laptop has no usable GPU the script runs on the CPU in 32-bit floats, and both numbers double.

Qwen2.5-7B-Instruct: 2 × 28 × 4 × 128 × 2 = 57,344 bytes (56 KiB) per token, so a 4,096-token conversation holds 224 MiB. Without grouped-query attention (28 key-value heads instead of 4) it would be 392 KiB per token, seven times as much.

Part 1: on your laptop

Set up once

One virtual environment serves every workbench page. From the site's folder:

$ python3 -m venv ~/.venvs/zts
$ ~/.venvs/zts/bin/pip install -r workbench/requirements.txt
$ source ~/.venvs/zts/bin/activate

The script is code/w01/kv_cache.py, and the same code split into cells is kv_cache.ipynb for Jupyter. The first run downloads the model from Hugging Face.

The idea

  1. pick the device (CUDA, then Apple MPS, then CPU) and its number width b
  2. read L, n_kv, d_head from config.json; predict 2 × L × n_kv × d_head × b
  3. run a 512-token prompt once; add up the bytes of every key and value kept
  4. decode 32 tokens with the cache, then recomputing everything; time both
  5. GPU only: predict the batch that fits, then double the batch until OOM
"""The KV cache, measured: predict its size from chapter 18's formula, then
read the real tensors out of a real model and compare.

Laptop (SmolLM2-135M, on CPU or Apple's MPS):
    python kv_cache.py
GPU box (a 7B model, then batch up to the memory limit):
    python kv_cache.py --model Qwen/Qwen2.5-7B-Instruct --sweep

Needs: torch, transformers (workbench/requirements.txt)."""
import argparse
import time

import torch
from transformers import AutoConfig, AutoModelForCausalLM

# ── 1. Settings ──────────────────────────────────────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("--model", default="HuggingFaceTB/SmolLM2-135M")
ap.add_argument("--tokens", type=int, default=512)    # prompt length
ap.add_argument("--new", type=int, default=32)        # tokens to decode
ap.add_argument("--sweep", action="store_true")       # GPU: batch until OOM
args, _ = ap.parse_known_args()        # notebooks pass their own flags

if torch.cuda.is_available():
    DEVICE, DTYPE = "cuda", torch.bfloat16
elif torch.backends.mps.is_available():
    DEVICE, DTYPE = "mps", torch.float16
else:
    DEVICE, DTYPE = "cpu", torch.float32
BYTES = torch.tensor([], dtype=DTYPE).element_size()   # bytes per number


def mib(n):
    return f"{n / 2**20:,.2f} MiB"


# ── 2. Predict from the config alone (chapter 18) ────────────────────────
cfg = AutoConfig.from_pretrained(args.model)
L = cfg.num_hidden_layers
n_kv = getattr(cfg, "num_key_value_heads", None) or cfg.num_attention_heads
d_head = (getattr(cfg, "head_dim", None)
          or cfg.hidden_size // cfg.num_attention_heads)
per_token = 2 * L * n_kv * d_head * BYTES          # K and V, every layer
print(f"model {args.model} on {DEVICE} in {DTYPE}")
print(f"L={L} layers, n_kv={n_kv} of {cfg.num_attention_heads} heads, "
      f"d_head={d_head}, b={BYTES} bytes")
print(f"predicted: {per_token:,} bytes per token; "
      f"{mib(per_token * args.tokens)} for {args.tokens} tokens")

# ── 3. Measure: run the prompt once and read the cache tensors ───────────
model = AutoModelForCausalLM.from_pretrained(args.model, dtype=DTYPE)
model = model.to(DEVICE).eval()
torch.manual_seed(0)
ids = torch.randint(0, cfg.vocab_size, (1, args.tokens), device=DEVICE)
with torch.no_grad():
    out = model(ids, use_cache=True)


def cache_bytes(cache):
    """Sum the bytes of every key and value tensor the model kept."""
    total = 0
    for layer in cache.layers:              # transformers' DynamicCache
        total += layer.keys.numel() * layer.keys.element_size()
        total += layer.values.numel() * layer.values.element_size()
    return total


measured = cache_bytes(out.past_key_values)
ratio = measured / (per_token * args.tokens)
print(f"measured:  {mib(measured)} in {len(out.past_key_values.layers)} "
      f"layers  (measured / predicted = {ratio:.3f})")

# ── 4. Why it exists: decode with the cache vs recomputing everything ────


def sync():
    if DEVICE == "cuda":
        torch.cuda.synchronize()
    elif DEVICE == "mps":
        torch.mps.synchronize()


def decode(use_cache):
    seq = ids
    past = None
    sync()
    start = time.perf_counter()
    with torch.no_grad():
        for _ in range(args.new):
            step_in = seq[:, -1:] if past is not None else seq
            o = model(step_in, past_key_values=past, use_cache=use_cache)
            past = o.past_key_values if use_cache else None
            nxt = o.logits[:, -1].argmax(-1, keepdim=True)
            seq = torch.cat([seq, nxt], dim=1)
    sync()
    return (time.perf_counter() - start) / args.new * 1000


with_cache = decode(True)
without = decode(False)
print(f"decode {args.new} tokens after a {args.tokens}-token prompt: "
      f"{with_cache:.1f} ms/token with the cache, {without:.1f} without "
      f"({without / with_cache:.1f}x)")

# ── 5. GPU only: how many conversations fit? Predict, then find out ──────
if args.sweep and DEVICE == "cuda":
    free, total = torch.cuda.mem_get_info()
    print(f"\nGPU: {torch.cuda.get_device_name(0)}, {mib(free)} free "
          f"of {mib(total)} with the weights loaded")
    predicted_batch = int(free * 0.9 // (per_token * args.tokens))
    print(f"predicted max batch at {args.tokens} tokens: about "
          f"{predicted_batch} (90% of free memory / cache per sequence)")
    batch = 1
    while True:
        try:
            torch.cuda.reset_peak_memory_stats()
            x = torch.randint(0, cfg.vocab_size, (batch, args.tokens),
                              device=DEVICE)
            with torch.no_grad():                # keep only the last
                model(x, use_cache=True, logits_to_keep=1)   # logits row
            peak = torch.cuda.max_memory_allocated()
            print(f"  batch {batch:4d}: peak {mib(peak)}")
            batch *= 2
        except torch.OutOfMemoryError:
            print(f"  batch {batch:4d}: out of memory")
            break
        finally:
            torch.cuda.empty_cache()

On a MacBook (Apple MPS, 16-bit) this printed:

model HuggingFaceTB/SmolLM2-135M on mps in torch.float16
L=30 layers, n_kv=3 of 9 heads, d_head=64, b=2 bytes
predicted: 23,040 bytes per token; 11.25 MiB for 512 tokens
measured:  11.25 MiB in 30 layers  (measured / predicted = 1.000)
decode 32 tokens after a 512-token prompt: 8.9 ms/token with the cache, 33.2 without (3.7x)

What you should see

  • Measured / predicted = 1.000. The formula is not an estimate: it counts exactly the tensors the model keeps. If yours shows 2.000, you ran on the CPU in 32-bit floats and predicted with 2 bytes.
  • Only 3 of 9 heads are cached. SmolLM2 shares each key-value head between three query heads. With a full set of 9 the cache would be three times larger for the same model quality budget, which is the whole argument for grouped-query attention in chapter 18.
  • The cache makes decoding several times faster, and the gap grows with the prompt: without it, each new token re-runs attention over the whole prompt. Your timings will differ from the ones above (they depend on the machine and on what else it is doing), but the ratio should be well above 1.

Part 2: how many conversations fit on one GPU?

On the GPU box (wb up, wb sync, wb ssh, then sh /workspace/zts/workbench/setup-pod.sh the first time), run the same script on a 7B model with a 4,096-token context, and let it double the batch until the card runs out of memory:

$ cd /workspace/zts/llm-training/workbench/code/w01
$ python kv_cache.py --model Qwen/Qwen2.5-7B-Instruct --tokens 4096 --sweep

Not run here

This page was written on a machine without an NVIDIA GPU, so there is no printed GPU output to copy. The predictions below are computed from the model's published configuration and weight size; the measurements are yours to fill in, and they are saved in this browser.

Before running it, predict the largest batch. The weights take 15,231,233,024 bytes (14.19 GiB, from the model's model.safetensors.index.json). Assume about 0.6 GiB for the CUDA context, which leaves roughly 24 − 14.19 − 0.6 ≈ 9.2 GiB. The script keeps a 10% margin and divides by 224 MiB per sequence: about 9.2 × 0.9 / 0.219 ≈ 38 conversations. It prints its own version of this, from the free memory it actually finds.

QuantityPredictedMeasuredRatio
Cache per token, bytes (the predicted: line)57,344
Cache for one 4,096-token sequence, MiB (the measured: line)224
Largest batch that fits at 4,096 tokens (last batch without OOM, or interpolate)≈ 38

Expect the first two ratios to be 1.00, and the third to come in below 1. The prediction counts only the cache, but running a 4,096-token prompt through the model also needs working memory for each layer's intermediate results while it computes them. The gap between your measured batch and 38 is roughly that working memory. Serving engines such as vLLM shrink it by processing long prompts in chunks (chapter 20).

Break it

  • Double the context. Re-run the sweep with --tokens 8192. Predict first: the cache per sequence doubles, so the batch should roughly halve.
  • Remove grouped-query attention, on paper. Use the formula with 28 key-value heads instead of 4. How many 4,096-token conversations would fit then? (Answer: about 5.) This is the calculation that made model builders adopt GQA.
  • Halve the bytes. Serving engines can store the cache in 8-bit floats (chapter 19). Predict the new batch, then look up the kv_cache_dtype option of vLLM and measure it in the serving workbench.

Key takeaways

  • The cache formula is exact: measured bytes equal 2 × L × nkv × dhead × b × tokens.
  • Everything it needs is in config.json, so you can size a deployment before downloading a single weight.
  • On a 24 GB card, the weights of a 7B model leave room for a few dozen long conversations, and the prefill's working memory takes a real share of that room.
  • Predict, then measure. The disagreement is the lesson.

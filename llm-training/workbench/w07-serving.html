Workbench 7: Serve with vLLM and Load-Test It

A serving engine is the program that keeps a model loaded and answers many users at once. Chapter 20 explains how it schedules work and manages memory; chapter 18 gives the cost of each conversation’s memory. Here you build a load generator, a script that sends many requests at once and times every token that comes back. You test it on your laptop against a small model, then predict what vLLM, a widely used engine, should do on a 24 GB GPU: how many conversations fit, and where the speed starts to degrade.

Why measure it

Three numbers describe a served model. Time to first token (TTFT) is how long a user waits before the answer starts. Inter-token latency (ITL) is the gap between one token and the next once it is streaming. Throughput is the tokens per second the machine produces for everyone together. A server that looks fast for one user can look very different with fifty, and the only way to see it is to apply that load and time it. The same habit applies to every service you will ship: predict the knee first, then measure it. The knee is the load at which latency stops growing gently and starts to climb steeply.

What you need

  • Part 1, your laptop: Python 3.10+, the workbench venv (below) and about 300 MB of disk for SmolLM2-135M-Instruct. About 25 minutes.
  • Part 2, a GPU box (optional): one 24 GB card such as an RTX 4090, about 16 GB of disk for Qwen2.5-7B-Instruct, and about two hours (installing vLLM and downloading the model take the first half hour). Setting one up is in Your lab machine, Option C.

Predict before you run

The memory a conversation occupies comes from chapter 18:

KV bytes per token = 2 × L × nkv × dhead × b

Qwen2.5-7B-Instruct’s config.json says 28 layers, 28 attention heads of which 4 are key-value heads, and a hidden size of 3,584, so each head is 128 wide. In bfloat16 (2 bytes) that is 2 × 28 × 4 × 128 × 2 = 57,344 bytes per token. Its weights take 15,231,233,024 bytes (14.19 GiB), from model.safetensors.index.json.

vLLM stores the cache in blocks of 16 tokens (chapter 20) and gives them a share of the card set by --gpu-memory-utilization. The cache pool is what is left of that share after the weights and the engine’s own working memory:

pool = u × GPU memory − weights − overhead

The second prediction is the speed of one decoding step. A step reads every weight once and every running conversation’s cache once, and decoding is limited by how fast memory can be read (chapter 18). So with n conversations running, an average of ctx tokens long each, and a memory bandwidth BW:

tstep ≈ (weights + n × ctx × 57,344) / BW,   tokens per second ≈ n / tstep

The card is an RTX 4090. Its memory is a 384-bit bus at 21 gigabits per second per pin, which is 1,008 GB/s (NVIDIA’s page for the card gives the 24 GB and the bus width; the data rate and the 1,008 figure are from its published specification, so check them against your own card’s sheet). The load test sends prompts of about 440 tokens (400 random words plus the chat template, counted with the Qwen tokeniser) and asks for 256 tokens back, so a conversation ends at 696 tokens.

Your prediction

With --gpu-memory-utilization 0.90 on a 24 GiB card and an assumed 1.5 GiB of working memory, how big is the cache pool, and how many 696-token conversations fit? Then: how long is one decoding step with a single conversation running, and with 128? Where would you expect the latency to break?

Check your arithmetic

Budget: 0.90 × 24 GiB = 21.60 GiB. Subtract the weights (14.19 GiB) and 1.5 GiB: 5.91 GiB of cache. One 16-token block is 16 × 57,344 = 917,504 bytes, so the pool holds 6,922 blocks, or 110,752 tokens. A 696-token conversation needs 44 blocks, so 6,922 / 44 = 157 conversations fit. (The 1.5 GiB is an assumption. vLLM measures the real figure when it starts and prints it; that is the first thing to compare.)

One step with one conversation: 15.23 GB of weights plus 0.04 GB of cache is 15.1 ms at 1,008 GB/s, about 66 tokens per second. With 128 conversations the cache adds 128 × 568 × 57,344 = 4.2 GB (the average length during the answer is 440 + 128 = 568 tokens), so a step takes 19.2 ms and the card makes about 6,650 tokens per second. The weights are read once for everybody, which is why batching pays so well.

The knee: up to about 128 conversations each added user costs only a little more per step, and throughput rises almost in proportion. The cache is full at 157. Beyond that new requests wait in a queue until a conversation finishes, so throughput stops rising (about 7,800 tokens per second here) and time to first token climbs. Compute is not the limit: 157 conversations need 2 × 7.6 billion × 157 operations per step, which takes 14.5 ms at the card’s roughly 165 teraflops (my estimate from NVIDIA’s headline AI figure; the step is limited by memory at 20 ms). These are ceilings: they ignore sampling, scheduling and the attention arithmetic, so expect measured throughput below them and measured latency above.

Part 1: on your laptop

Set up once

One virtual environment serves every workbench page. From the site’s folder:

$ python3 -m venv ~/.venvs/zts

$ source ~/.venvs/zts/bin/activate

The load generator is code/w07/loadtest.py (notebook: loadtest.ipynb). It speaks to any server that offers the OpenAI chat API, so the same script works against Ollama on a laptop, against transformers serve here and against vLLM on the GPU box. It needs the httpx package, which comes with the venv.

The idea

  1. send one throw-away request to warm the server up
  2. for each concurrency level c: start c workers; each sends requests one after another, so c are always in flight
  3. stream every answer; stamp the clock when the request leaves and when each token arrives
  4. TTFT = first stamp − send time; ITL = gaps between stamps; throughput = all tokens / wall time
  5. print one row per level; the knee is where TTFT leaves the floor
"""Load-test any OpenAI-compatible server: throughput, time to first token
and inter-token latency at rising concurrency (chapter 20's three clocks).

Laptop (any server on port 8000, for example `transformers serve`):
    python loadtest.py --model HuggingFaceTB/SmolLM2-135M-Instruct
GPU box (vLLM, longer prompts and answers, more levels):
    python loadtest.py --model Qwen/Qwen2.5-7B-Instruct --ignore-eos \
        --levels 1,2,4,8,16,32,64,128,192,256 --prompt-words 400 \
        --max-tokens 256

Needs: httpx (installed with transformers)."""
import argparse
import asyncio
import json
import random
import time

import httpx

# ── 1. Settings ──────────────────────────────────────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("--base-url", default="http://localhost:8000/v1")
ap.add_argument("--model", default="HuggingFaceTB/SmolLM2-135M-Instruct")
ap.add_argument("--levels", default="1,2,4,8,16")     # concurrency levels
ap.add_argument("--per-slot", type=int, default=3)    # requests per slot
ap.add_argument("--max-tokens", type=int, default=48)  # answer length
ap.add_argument("--prompt-words", type=int, default=60)
ap.add_argument("--ignore-eos", action="store_true")  # vLLM only
ap.add_argument("--seed", type=int, default=0)
args, _ = ap.parse_known_args()        # notebooks pass their own flags

WORDS = ("the of and to in is that it was for on are as with his they at "
         "be this have from or one had by word but not what all were we "
         "when your can said there use an each which she do how their if "
         "will up other about out many then them these so some her would "
         "make like him into time has look two more write go see number "
         "no way could people my than first water been call who oil its "
         "now find long down day did get come made may part").split()
rng = random.Random(args.seed)


def make_prompt(i):
    """A fresh prompt per request, so no server can reuse a cached prefix."""
    body = " ".join(rng.choice(WORDS) for _ in range(args.prompt_words))
    return f"Request {i}. Continue this text at length: {body}"


# ── 2. One streaming request: stamp the clock at every token ─────────────
async def one_request(client, i):
    body = {"model": args.model, "stream": True,
            "max_tokens": args.max_tokens, "temperature": 0.8,
            "messages": [{"role": "user", "content": make_prompt(i)}]}
    if args.ignore_eos:                    # vLLM extension: fixed length
        body["ignore_eos"] = True
    t0 = time.perf_counter()
    stamps = []                            # arrival time of each token
    async with client.stream("POST", args.base_url + "/chat/completions",
                             json=body) as r:
        r.raise_for_status()
        async for line in r.aiter_lines():
            if not line.startswith("data: ") or line.endswith("[DONE]"):
                continue
            chunks = json.loads(line[6:]).get("choices") or [{}]
            if chunks[0].get("delta", {}).get("content"):
                stamps.append(time.perf_counter())   # one chunk, one token
    return {"ttft": stamps[0] - t0,        # first token minus send time
            "gaps": [b - a for a, b in zip(stamps, stamps[1:])],
            "tokens": len(stamps), "end": time.perf_counter()}


# ── 3. One level: keep c requests in flight until n have finished ────────
async def run_level(client, c, first_id):
    n = c * args.per_slot
    ids = iter(range(first_id, first_id + n))

    async def worker():                    # a closed loop: one slot
        out = []
        for i in ids:
            out.append(await one_request(client, i))
        return out

    start = time.perf_counter()
    done = await asyncio.gather(*[worker() for _ in range(c)])
    wall = time.perf_counter() - start
    return [r for rs in done for r in rs], wall


def pct(xs, p):
    xs = sorted(xs)
    return xs[min(len(xs) - 1, int(p / 100 * len(xs)))]


# ── 4. Sweep the levels and print the table ──────────────────────────────
async def main():
    limits = httpx.Limits(max_connections=1000)
    async with httpx.AsyncClient(timeout=600, limits=limits) as client:
        await one_request(client, -1)      # warm-up, not counted
        print(f"{args.model} at {args.base_url}; {args.prompt_words} "
              f"prompt words, {args.max_tokens} tokens per answer")
        print(f"{'conc':>5} {'reqs':>5} {'tok/s':>8} {'gain':>6} "
              f"{'TTFT p50':>9} {'TTFT p95':>9} {'ITL p50':>8} "
              f"{'ITL p99':>8}   (ms)")
        prev, first_id = None, 0
        for c in [int(x) for x in args.levels.split(",")]:
            rs, wall = await run_level(client, c, first_id)
            first_id += len(rs)
            tps = sum(r["tokens"] for r in rs) / wall
            ttft = [r["ttft"] * 1000 for r in rs]
            itl = [g * 1000 for r in rs for g in r["gaps"]]
            gain = f"{tps / prev:.2f}x" if prev else ""
            print(f"{c:>5} {len(rs):>5} {tps:>8.1f} {gain:>6} "
                  f"{pct(ttft, 50):>9.0f} {pct(ttft, 95):>9.0f} "
                  f"{pct(itl, 50):>8.1f} {pct(itl, 99):>8.1f}")
            prev = tps


asyncio.run(main())

How steady are these numbers?

Not very. The laptop was also running other work, and repeated runs of the plain server gave anything from 47 to 200 tokens per second at concurrency 1. The continuous-batching mode of transformers serve is also young: on later attempts it stalled on its first request while the machine was busy, so the table above is from one good run. Treat the shape as the result, not the digits.

What you should see

  • Plain server: throughput is flat. About 45 to 55 tokens per second whether 1 or 16 requests are in flight. It answers one request at a time, so extra requests wait. The gain column hovers around 1.0.
  • Plain server: TTFT grows in a straight line. At concurrency 2 the median is 685 ms, about one whole answer (32 tokens at roughly 47 per second is 0.68 s), because the second request waits for the first to finish. At 16 it is 8.7 s. This is queueing, and it is what “no batching” looks like to a user.
  • Batching server: throughput climbs. From 70 to 530 tokens per second as concurrency rises to 16, while the median TTFT stays between 28 and 138 ms. Several answers are produced in each step.
  • The price is ITL. Its median rose from 13 to 20 ms, and the 99th percentile (the slowest 1 in 100 gaps) is noisy and higher. Each step now carries more work, which is chapter 20’s warning that raising throughput and raising inter-token latency go together.

"""Plan a vLLM deployment on paper: how many conversations fit, and where
the latency knee should be (chapter 18's cache formula, chapter 20's
settings). Reads the model's real config.json and weight size; no GPU.

    python plan.py
    python plan.py --model Qwen/Qwen2.5-7B-Instruct --prompt 440 --out 256

Needs: network access to huggingface.co (two small JSON files)."""
import argparse
import json
import math
import urllib.request

# ── 1. Settings ──────────────────────────────────────────────────────────
ap = argparse.ArgumentParser()
ap.add_argument("--model", default="Qwen/Qwen2.5-7B-Instruct")
ap.add_argument("--gpu-gib", type=float, default=24)    # card memory
ap.add_argument("--util", type=float, default=0.90)     # vLLM's share
ap.add_argument("--overhead-gib", type=float, default=1.5)  # ASSUMED
ap.add_argument("--bw", type=float, default=1008)       # GB/s (RTX 4090)
ap.add_argument("--tflops", type=float, default=165)    # bf16 dense
ap.add_argument("--prompt", type=int, default=440)      # tokens in
ap.add_argument("--out", type=int, default=256)         # tokens out
ap.add_argument("--max-seqs", type=int, default=256)    # --max-num-seqs
ap.add_argument("--block", type=int, default=16)        # tokens per block
ap.add_argument("--kv-bytes", type=int, default=2)      # 1 = fp8 cache
args, _ = ap.parse_known_args()        # notebooks pass their own flags
GIB = 2 ** 30


def fetch(name):
    url = f"https://huggingface.co/{args.model}/raw/main/{name}"
    return json.load(urllib.request.urlopen(url))


# ── 2. The real numbers: config.json and the weight size ─────────────────
cfg = fetch("config.json")
L, n_kv = cfg["num_hidden_layers"], cfg["num_key_value_heads"]
d_head = cfg["hidden_size"] // cfg["num_attention_heads"]
weights = fetch("model.safetensors.index.json")["metadata"]["total_size"]
b = args.kv_bytes                       # bytes per cached number
per_token = 2 * L * n_kv * d_head * b   # chapter 18, eq-kv-bytes
print(f"{args.model}: L={L}, n_kv={n_kv}, d_head={d_head}, b={b}")
print(f"cache per token: 2 x {L} x {n_kv} x {d_head} x {b} = "
      f"{per_token:,} bytes ({per_token / 1024:.0f} KiB)")
print(f"weights: {weights:,} bytes = {weights / GIB:.2f} GiB")

# ── 3. How many sequences fit in the cache pool? ─────────────────────────
budget = args.util * args.gpu_gib * GIB
pool = budget - weights - args.overhead_gib * GIB
block_bytes = args.block * per_token
blocks = int(pool // block_bytes)
seq_tokens = args.prompt + args.out
seq_blocks = math.ceil(seq_tokens / args.block)
fit = blocks // seq_blocks
print(f"\nbudget {args.util:.2f} x {args.gpu_gib:g} GiB = "
      f"{budget / GIB:.2f} GiB; minus weights, minus "
      f"{args.overhead_gib:g} GiB assumed overhead")
print(f"cache pool: {pool / GIB:.2f} GiB = {blocks:,} blocks of "
      f"{args.block} tokens ({blocks * args.block:,} tokens)")
print(f"one conversation ({args.prompt} in + {args.out} out = "
      f"{seq_tokens} tokens): {seq_blocks} blocks")
print(f"sequences that fit: {blocks:,} / {seq_blocks} = {fit}  "
      f"(--max-num-seqs is {args.max_seqs})")
cap = min(fit, args.max_seqs)

# ── 4. Step time and throughput: read the weights, read the caches ───────
params = weights / 2                    # bf16 weights: 2 bytes each
ctx = args.prompt + args.out / 2        # average context during decode


def step_ms(n):
    memory = (weights + n * ctx * per_token) / (args.bw * 1e9)
    compute = 2 * params * n / (args.tflops * 1e12)
    return 1000 * max(memory, compute)


prefill = 1000 * 2 * params * args.prompt / (args.tflops * 1e12)
print(f"\nprefill floor for {args.prompt} tokens at peak compute: "
      f"{prefill:.0f} ms  (a real engine is slower)")
print("concurrent  step (ms)   tokens/s ceiling   note")
for n in (1, 2, 4, 8, 16, 32, 64, 128, 192, 256):
    run = min(n, cap)
    ms = step_ms(run)
    note = "" if n <= cap else "queueing: only %d run at once" % cap
    print(f"{n:>10} {ms:>10.1f} {run / ms * 1000:>18,.0f}   {note}")

What the ratios should look like follows from what was left out. The two memory rows depend on the 1.5 GiB guess, so a ratio near 1 (not exactly 1) is a good result, and a larger gap tells you how much working memory the engine really reserves. The latencies and the TTFT are floors, so their ratios should come out above 1; the throughputs are ceilings, so theirs should come out below 1. If throughput at 128 is far below the ceiling, look at the scheduler: the chapter’s --max-num-batched-tokens decides how much prompt work competes with decoding in each step.

Break it

  • Cap the batch. Restart with --max-num-seqs 32. Predict first: run python plan.py --max-seqs 32. The ceiling should flatten at about 1,980 tokens per second from concurrency 32, and TTFT should start climbing there instead of at 157.
  • Ask for longer answers. Use --max-tokens 512. A conversation now ends at 952 tokens, 60 blocks, so python plan.py --out 512 says 115 fit instead of 157. Does the knee move to match?
  • Halve the bytes of the cache. Add --kv-cache-dtype fp8 to vllm serve (chapter 19; check your version’s documentation for the exact name). python plan.py --kv-bytes 1 predicts 314 conversations fit, more than --max-num-seqs 256 allows. Then the limit is the setting, not memory, and the step time at 256 starts to be set by compute: 23.6 ms in the plan, against 18.2 ms at 192.

State of play, October 2026

vLLM’s flags and log messages change between releases. I could not run it for this page, so check the documentation for the version you install: the names of --max-num-seqs, --gpu-memory-utilization and --kv-cache-dtype, whether prefix caching is on by default (it was in the V1 engine, per chapter 20; the load generator uses a different prompt each time so it cannot help) and the wording of the cache lines in the start-up log. The RTX 4090 figures are published specifications, not measurements.

Key takeaways

  • A load generator needs only a streaming request and a clock: stamp every token, then compute TTFT, ITL and throughput.
  • Without batching, throughput is flat and TTFT grows with every extra user. With it, throughput rises and the price is a slightly longer gap between tokens.
  • The number of conversations a GPU holds follows from three inputs you can read before downloading anything: the weights, the cache per token and the memory share you give the engine.
  • The knee sits where the cache pool fills. Measurements of floors come out above the prediction and ceilings below it; the gap is what the simple model leaves out.

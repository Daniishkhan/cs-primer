Your Lab Machine

Most of this path runs on your own laptop. A few experiments need Linux: watching every system call with strace, profiling with perf, building a container from scratch, injecting packet loss into a network. This page shows two ways to get a Linux machine to break things on, a free one on your laptop and a rented one in the cloud, and a third for the AI courses' workbenches: a GPU rented by the hour.

Do I need this?

Not to start. Every chapter and lab works on macOS or Linux (and Windows through WSL). Experiments that need Linux are marked with a ☁️ On a Linux VM box, and toolbox entries that are Linux-only carry a Linux badge. Set up a lab machine when you first meet one of those, which will probably be in How Programs Run, chapter 4.

Why Linux, and why a separate machine?

  • Linux shows you more. It exposes the kernel's view of every process in /proc, lets you trace system calls (strace) and kernel events (perf, bpftrace), and has the namespaces and cgroups that containers are built from. macOS has some equivalents, but several of them need System Integrity Protection switched off, which you shouldn't do on your everyday computer.
  • Most servers run Linux. When this course says "epoll" or "the OOM killer", that's what production machines do.
  • A disposable machine is a safe place to break things. You can fill its memory, crash its processes, add 30% packet loss to its network or run things with sudo, then throw it away. Elsewhere this path avoids sudo. Inside your own throwaway VM, it's fine.
  • A clean network path. Some networks (offices, coworking spaces, hotels) quietly intercept DNS traffic or block unusual ports. A cloud VM sits on a plain data-center connection, so experiments like walking the DNS tree from the root servers behave as the textbook says.

Option A: a free Linux VM on your laptop

This covers almost everything in How Programs Run. It takes a few minutes and costs nothing. Pick one of these tools.

OrbStack (macOS)

A lightweight app for Linux machines and containers on a Mac. Its Linux machines can see your Mac's files at the same paths (for example /Users/you/...), so the course folder is available inside the VM straight away.

$ brew install --cask orbstack     # or download it from orbstack.dev
$ orb create ubuntu lab             # make an Ubuntu machine called "lab"
$ orb -m lab                        # open a shell inside it
lab$ cd /Users/you/Desktop/projects/cs-refresh/networking   # your Mac's files, same path

orb list shows your machines, and orb help lists the commands to stop or delete one.

Multipass (macOS, Linux, Windows)

Canonical's tool for Ubuntu VMs. You choose which folder to share into the VM.

$ brew install --cask multipass    # or download it from canonical.com/multipass
$ multipass launch --name lab      # a fresh Ubuntu LTS VM
$ multipass mount "$PWD" lab:/home/ubuntu/zts   # run from the course folder
$ multipass shell lab
ubuntu@lab$ cd ~/zts
# later:
$ multipass stop lab               # pause it
$ multipass delete lab && multipass purge   # throw it away for good

One limitation of local VMs

A VM on your laptop still uses your laptop's network, so it doesn't help with "real distance" experiments (latency across continents, anycast) or with a network that intercepts traffic. That's what Option B is for.

Windows

Use WSL 2 (Windows Subsystem for Linux) with Ubuntu. It's a real Linux kernel in a lightweight VM, and it's also what the labs expect on Windows.

Option B: a cloud VM

Rent a small Linux server from a cloud provider such as DigitalOcean (a "Droplet"), AWS (EC2 or Lightsail), Hetzner, Google Cloud or similar. The smallest sizes cost a few dollars a month if left running, and less if you only keep them for an afternoon. You'll want one later for the networking and distributed-systems experiments that need real geography:

  • measuring latency to the other side of the world and comparing it with the speed of light (networking ch. 13);
  • a DNS root walk free of local interception (networking Lab 3);
  • running the replicated key-value store or Raft on three machines in three regions (Lab 5, Lab 6), and later in the Distributed Systems course.

Set one up safely

  1. Set a billing alert first. Every provider lets you set a budget or alert, so do it before creating anything. Cloud bills come from things you forgot about.
  2. Make an SSH key on your laptop if you don't have one: ssh-keygen -t ed25519. Upload the public key (~/.ssh/id_ed25519.pub) to the provider. Never share the private key.
  3. Create the smallest Ubuntu LTS server in a region near you, choosing SSH-key login (no password login).
  4. Firewall: allow incoming SSH (TCP port 22) only, ideally only from your own IP address. The labs bind their servers to 127.0.0.1, so they're never exposed. Keep it that way unless an exercise explicitly says otherwise.
  5. Connect: ssh root@203.0.113.10 (use your server's address; some providers use a user like ubuntu instead of root).
  6. Copy the course over from your laptop: rsync -av --exclude graft ./ root@203.0.113.10:zts/
  7. Destroy it when you're done. On many providers a stopped server still costs money (its disk and reserved resources). Delete it and create a fresh one next time; that takes a minute.

Common misconception

"Nobody will find my little server." Automated scanners probe every public IP address on the Internet continuously, and a new server typically sees login attempts within minutes. That's why we use key-only SSH, a tight firewall and services bound to 127.0.0.1. If you're curious, sudo journalctl -u ssh (the unit is called sshd on some distributions) on your new server will show the attempts.

Option C: a GPU box

The Workbench pages of the AI courses repeat a chapter's idea with the real tools: PyTorch, Hugging Face models, TRL, vLLM. Most of them run on your laptop. A few train or serve models that need an NVIDIA GPU with a lot of memory, and for those you rent one by the hour. Each workbench page says which machine it needs, with a badge at the top.

First, your laptop

One virtual environment serves every laptop workbench. On a Mac with Apple silicon, PyTorch uses the GPU inside the chip (called MPS), which is plenty for models up to a few hundred million parameters.

$ python3 -m venv ~/.venvs/zts
$ ~/.venvs/zts/bin/pip install -r workbench/requirements.txt
$ source ~/.venvs/zts/bin/activate

For the workbenches that talk to a local language model, install Ollama and pull a small model; the page names which.

Then, a rented GPU

The GPU pages are written for one 24 GB card such as an RTX 4090. That is the reference card the LLM Training course sizes its examples for: enough for a 7B model in 16 bits, or LoRA on a 7B model in 4 bits. The site's helper script, workbench/wb, uses RunPod, which rents single GPUs by the second; the same steps work on any provider that gives you SSH into a GPU machine. A free Colab or Kaggle notebook can run the smaller GPU exercises too, with less memory and time limits.

  1. Account and safety first. Create a RunPod account, add a small amount of credit rather than an open-ended card, and turn on a spending alert. Add your SSH public key (~/.ssh/id_ed25519.pub) under Settings. Create an API key and keep it out of the repository: put export RUNPOD_API_KEY=… in ~/.config/wb.env.
  2. A network volume (Storage, about 50 GB, in a data centre that has RTX 4090s). It holds the Python environment, model weights and datasets, and outlives every pod, so a new pod starts in a minute instead of re-downloading 15 GB. Put its id in ~/.config/wb.env as WB_VOLUME_ID.
  3. Start a pod and connect: 
    $ workbench/wb up       # an RTX 4090 pod with your volume at /workspace
$ workbench/wb sync     # copy the workbench code to /workspace/zts
$ workbench/wb ssh
root@pod$ sh /workspace/zts/workbench/setup-pod.sh   # first time only
    You can also open JupyterLab from the pod's page in the console and run the workbench notebooks (.ipynb) there, or connect VS Code with its Remote-SSH extension.
  4. Stop it when you are done: workbench/wb down. As a safety net, setup-pod.sh starts a watchdog that stops the pod after 30 minutes with the GPU idle and nobody logged in (WB_IDLE_MIN changes it).

State of play, October 2026: what it costs

GPU prices change month to month and differ between RunPod's Secure and Community clouds, so check the price the console shows when you create a pod; wb status prints it too. RunPod bills pods by the second. Storage keeps costing money when the pod is stopped: RunPod's pricing page lists network volumes at $0.07 per GB per month (under 1 TB), so a 50 GB volume is about $3.50 a month. Delete the volume when you finish the courses.

Common misconception

"Serverless" is not the cheap way to do these exercises. RunPod Serverless runs a handler you package as a container, once per request, and scales to zero: right for deploying a model behind an API (the AI Delivery course has a workbench on exactly that), wrong for an interactive session. For SSH and Jupyter you want a pod.

Install the toolbox

Inside the Linux machine (Ubuntu), this installs most of the tools from the networking and systems toolboxes:

$ sudo apt update
$ sudo apt install -y python3 python3-pip pipx strace tcpdump iperf3 dnsutils mtr-tiny \
    netcat-openbsd htop sysstat bpftrace hyperfine
$ sudo apt install -y linux-tools-common linux-tools-$(uname -r)   # perf, matched to the running kernel
$ pipx install py-spy

A few notes:

  • perf needs a package that matches the exact running kernel. That works on a standard Ubuntu cloud VM or Multipass. On VMs that use a custom or vendor-supplied kernel (WSL, and possibly OrbStack's machines), a matching package may not exist; if sudo apt install linux-tools-$(uname -r) fails, use a Multipass or cloud VM for the perf exercises.
  • Package names drift between Ubuntu releases. If one isn't found, apt search <name> usually reveals the new one.
  • Wireshark is best used as a desktop app on your own computer (brew install --cask wireshark-app on macOS). To look at traffic on a VM, capture it there with tcpdump -w capture.pcap and open the file in Wireshark.

Key takeaways

  • Start without a VM. Add a free local Linux VM (OrbStack, Multipass or WSL) when you reach a ☁️ experiment.
  • Rent cloud VMs only for experiments that need real distance or a clean network, and destroy them when you're done.
  • Billing alert first, SSH keys only, firewall allows port 22 only, lab servers bound to 127.0.0.1.
  • For the AI workbenches: laptop first; rent a 24 GB GPU by the hour only for the pages marked "A GPU box", keep the environment and models on a network volume, and stop the pod when you finish.

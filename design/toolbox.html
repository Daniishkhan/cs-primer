Toolbox

Design skill is a loop: draw an idea, put numbers on it, write it down, say it out loud to someone who pushes back, and try the risky part on a real data structure. These five tools cover that loop. Each card has setup notes and a ten-minute exercise tied to the chapters, and most are plain text you can copy into your own notes.

How to use this page

Jump to a tool when a chapter or studio points at it. I ran the napkin.py helpers and pasted their real output, and I checked the token-bucket Lua script for syntax and logic by running it under LuaJIT (a Lua 5.1 interpreter, the dialect Redis embeds) against a small mock of redis.call. I checked Redis command forms against the public command reference. I did not run a Redis server while writing this page (none was installed and the container runtime was not running), so every Redis output block is labelled illustrative: the shape is right, but trust your own terminal and --help over this page. The latency, throughput and size figures are rough, round and order-of-magnitude on purpose.

Draw it

A design you cannot sketch in ten minutes is a design you cannot explain in a review.

Excalidraw & whiteboards

Nothing to install: the web app at excalidraw.com (free, no account needed for local drawings; export to PNG, SVG or a .excalidraw file you can reopen) · Alternatives: a physical whiteboard, a tablet, or any shared canvas your interviewers use · Text alternative: Mermaid · Chapters: 1, 4

Excalidraw gives you rectangles, arrows, text and a hand-drawn look that signals "this is a sketch, argue with it". The tool is trivial; the skill is a consistent visual vocabulary, so that the listener never has to ask what a shape means. The site's own diagrams use the same colours, and the legend below is a version you can reproduce with four tools and a colour picker.

10-minute guided exercise

Redraw the news-feed architecture from chapter 9 from memory first, then check it against the figure. Set a timer for ten minutes and follow the order below.

  1. Minute 0 to 1: write the legend in a corner. Five small shapes with a label each (below). Doing this first forces you to commit to the vocabulary before you draw anything.
  2. Minute 1 to 3: the actors. One green client box on the left. Put the write path on top and the read path underneath, so the picture reads left to right and top to bottom.
  3. Minute 3 to 7: the write path. Client, post API (blue), post store (purple), fan-out queue (orange), fan-out workers (blue), follow-graph store (purple), timeline cache (cyan). Label every arrow with a verb or a payload ("post", "event: post_id", "push ids").
  4. Minute 7 to 9: the read path. Client, feed service (blue), timeline cache, the celebrity lists, ranking, hydration from the post store. Draw it in a second colour of arrow or a dashed line so the two paths cannot be confused.
  5. Minute 9 to 10: annotate one number and one failure. Write "about 600k reads/s" beside the cache and a red X on the queue with "lag: users see stale feeds". A diagram with a number and a failure on it is already a discussion.

Then compare with the chapter figure. Count how many of its labelled arrows you also labelled, and which store you forgot (most people omit the follow graph or the hydration step).

The shape legend (keep it identical in every drawing you make):

COLOUR    SHAPE                    MEANS
green     rounded rectangle        clients and users (browser, phone, other company)
blue      plain rectangle          stateless services (scale by adding copies)
purple    cylinder (or can)        stores that persist data (database, object store)
orange    long thin box + arrow    queues, logs, streams (data in motion)
cyan      rectangle, dashed edge   caches and CDNs (copies that may be stale)
grey      dotted rectangle         external systems you do not own
red       X or lightning bolt      failure point or bottleneck under discussion
yellow    thick arrow              the one request you are following right now

ARROWS    solid = synchronous call, dashed = asynchronous / eventual,
          label every arrow with a verb or a payload.

Habits that make a diagram readable in a live session

  • Boxes are nouns, arrows are verbs. An unlabelled arrow is a question the interviewer will ask for you.
  • Draw the simplest version first (client, service, store) and add one component at a time, each in answer to a requirement or a number you have just said. Never present a finished diagram.
  • Left to right for the request, top to bottom for layers. One reading direction.
  • Narrate as you draw and point at the arrow you are talking about. The silent drawer loses the room.
  • Leave room. Use a third of the board for the diagram, a third for numbers and a third for the list of open issues. You will want to redraw one part for a deep dive.
  • Groups over clutter. Put the fan-out workers in one dashed "write path" frame instead of drawing five identical boxes; say "times N" in a label.
  • Mark the data, not just the boxes. A short note such as timeline:{user_id} = list of post_ids beside the cache tells more than another box.
  • Keep a "not drawn" list. Say what you left out (auth, monitoring) so omission looks like a decision.

The text alternative. When you need a diagram that lives in a repository, diffs in a pull request and renders in the browser, write it as Mermaid text instead; see the Mermaid card in the Architecture toolbox. Excalidraw is for thinking out loud; Mermaid is for the design doc afterwards.

What to look for

  • Cover the legend and show your diagram to a friend. If they can name what each shape is without asking, the vocabulary works.
  • Count components. More than about ten boxes in a first diagram usually means you are drawing the implementation rather than the design.
  • Every store should have a reason (a number or a requirement) you can say in one sentence.

Common pitfalls

  • Spending the first five minutes on alignment and colours. Use the rough look; speed is the point.
  • Drawing "Kafka" or "Redis" in a box before you can say why. Name the role first ("fan-out queue"), the product second.
  • Two arrows crossing with no label. Redraw or move a box.
  • Colour as the only signal: in a shared screen or a printout, add the shape too (cylinder, dashed edge).

Put numbers on it

Estimation is a skill of round numbers and units. A card of anchors plus a few lines of code removes the arithmetic so you can think about the answer.

Napkin-maths reference

Needs: Python 3.8+ for napkin.py (standard library only) · Practice: Lab 1: estimation · Chapters: 2, 8

Copy the reference below into your notes. All figures are rough and order-of-magnitude: they will be off by a factor of two or three on any real machine, and that is fine, because the goal of chapter 2 is to be right within a factor of ten and to say which decision each number drives. When a real figure matters, measure it.

relational DB, durable writes           ~ 10^3 to 10^4 per second (fsync, indexes)

STORAGE PER ITEM  (rough)
a user id, a counter, a timestamp         8 bytes
UUID                                      16 bytes (36 as text)

a typical DB row                          ~ 100 bytes to 1 KB
log line                                  ~ 100-300 bytes

CONVERSION TRICKS
requests/day  -> per second:     divide by ~10^5 (86,400), then x3 for peak
bytes/s x 8    = bits/s       (MB/s x 8 = Mbit/s)
items x bytes  = total:       10^9 items x 10^3 B = 10^12 B = 1 TB
1 KB x 1M = 1 GB;  1 MB x 1M = 1 TB;  1 GB x 1M = 1 PB
years of storage = per-day x 365 x years x replicas
cache sizing: if 20% of items serve 80% of reads, cache ~20% of the hot set
memory of N keys ~ N x (value size + ~50-100 bytes overhead)
Say the unit, say the assumption, say "so..." and the decision it drives.

The latency ladder lines up with the one in the performance chapter of the networking course; if the two ever differ, keep the ratios and ignore the digits.

2. Save the helpers as napkin.py. They are small on purpose: each is one formula you could do by hand, so the code keeps the arithmetic honest and the units explicit.

#!/usr/bin/env python3
"""napkin.py: back-of-envelope helpers. Standard library only."""
import math

DAY = 86_400   # seconds per day, about 1e5

def qps(per_day, peak=3):
    """Average and peak requests per second from a per-day count."""
    avg = per_day / DAY
    return avg, avg * peak

def storage(items_per_day, bytes_each, years=5, replicas=3):
    """Raw bytes over `years`, and with replication."""
    raw = items_per_day * 365 * years * bytes_each
    return raw, raw * replicas

def bandwidth(rps, bytes_each):
    """Megabits per second for a request rate and payload size."""
    return rps * bytes_each * 8 / 1e6

def servers(peak_rps, per_box, headroom=0.5):
    """Boxes needed if each is run at `headroom` of its capacity."""
    return math.ceil(peak_rps / (per_box * headroom))

def human(n):
    for unit, size in (("PB", 1e15), ("TB", 1e12), ("GB", 1e9), ("MB", 1e6), ("KB", 1e3)):
        if n >= size:
            return f"{n/size:.1f} {unit}"
    return f"{n:.0f} B"

def availability(nines):
    """Allowed downtime per 30-day month at a given availability."""
    return (1 - nines) * 30 * DAY / 60

if __name__ == "__main__":
    avg, peak = qps(500_000_000)
    print(f"500M requests/day -> avg {avg:,.0f}/s, peak (x3) {peak:,.0f}/s")
    raw, rep = storage(10_000_000, 200_000)
    print(f"10M photos/day x 200 KB, 5 years -> raw {human(raw)}, x3 replicas {human(rep)}")
    print(f"15k req/s x 500 KB -> {bandwidth(15_000, 500_000):,.0f} Mbit/s")
    print(f"peak 15,000 rps at 2,000 rps/box, 50% headroom -> {servers(15_000, 2_000)} boxes")
    for n in (0.99, 0.999, 0.9999):
        print(f"{n*100:g}% availability -> {availability(n):.1f} min/month downtime")
    print(f"2**10={2**10}  2**20={2**20:,}  2**30={2**30:,}  2**40={2**40:,}")

4. Read the output as a designer. 500 million requests a day is about 5,800 a second on average and about 17,000 at peak: one in-memory store node handles that, one relational database on its own does not do it comfortably for writes, a handful of app servers do. Ten million 200 KB photos a day is 3.6 PB raw over five years and nearly 11 PB with three copies: that single number is why object storage with erasure coding exists. Then do the same for a prompt of your own, and finish Lab 1, which turns this into a graded exercise.

What to look for

  • Each result should end in a decision: "so one primary is fine", "so we need a cache", "so this must be partitioned". An estimate that does not change the design is trivia.
  • Peak versus average. The helpers default to 3x; change it and see how the fleet size moves.
  • Bandwidth is where people slip by a factor of eight (bytes versus bits). The 15,000 req/s at 500 KB example comes to 60 Gbit/s, which is six 10-gigabit cards of pure egress, a signal to use a CDN.

Common pitfalls

  • False precision: reporting 5,787 instead of "about 6,000". Round before you speak.
  • Mixing decimal and binary units (10^9 versus 2^30). The 7% difference is noise at napkin level; just be consistent.
  • Using throughput numbers as promises. A box that does 100k trivial operations a second may do 500 expensive ones.
  • Forgetting replication, indexes and overhead when sizing storage; add them as an explicit multiplier.

Write it down

A design that exists only in a conversation cannot be reviewed, challenged or found again in a year.

Design-doc templates

Needs: a text editor and a place the team can read and comment (a repository folder, a wiki or a shared document) · Read next: Documenting decisions (architecture course), Secure design review (security course) · Chapters: 4, 1

A design doc is thinking made reviewable. Its job is to find the expensive mistakes while they are still cheap: wrong requirements, a missed alternative, an unowned failure mode. The templates below are generic starting points, not any company's format. The one-pager is for a decision that fits on a page; the full doc is for a change that touches several teams or is hard to undo. For the lightweight record of a single choice, see the decision-record format in the architecture chapter.

10-minute guided exercise

Pick a design you have already done (the rate limiter of chapter 5 works). Spend five minutes filling in the one-pager from your notes, then five minutes running the review checklist against it. Write down every box you could not fill: those are your open questions, and finding them is the point.

1. The one-pager

TITLE: <system or change, in a few words>
Author: <name>   Reviewers: <names>   Status: <draft | in review | accepted>   Date: <date>

PROBLEM (2-3 sentences, in user or business terms)
<Who hurts today, how much, and why now.>

GOALS / NON-GOALS
Goals:      <3 measurable bullets, e.g. p99 under 200 ms at 10k req/s>
Non-goals:  <what we are deliberately not doing>

PROPOSAL (one paragraph and one small diagram)
<What we will build, in the language of components and data flow.>

KEY NUMBERS
<Load, data size, growth; each with its assumption.>

ALTERNATIVES CONSIDERED (at least two, including "do nothing")
1. <option>: <one line on why not>
2. <option>: <one line on why not>

RISKS AND HOW WE FIND OUT
<The top 3 failure modes; how we detect and mitigate each.>

ROLLOUT AND ROLLBACK
<Stages, flag or percentage, and the single step to undo.>

ASKS / OPEN QUESTIONS
<Decisions you need from reviewers, with a date.>

2. The full design doc

TITLE, AUTHORS, REVIEWERS, STATUS, LAST UPDATED

1. CONTEXT
   Background a new teammate needs. What exists today, what is wrong, links to
   earlier docs and incidents. No solutions yet.

2. GOALS AND NON-GOALS
   Goals: measurable outcomes. Non-goals: tempting things we will not do, so
   nobody assumes them.

3. REQUIREMENTS
   Functional: what the system does, as short user-visible statements.
   Non-functional: scale, latency (with percentile), availability, durability,
   consistency, cost, compliance. Each with a number or "unknown, to be decided by <who>".
   Assumptions and the estimation behind them.

4. OPTIONS CONSIDERED
   For each option (including do nothing): a short description, how it meets
   the requirements, what it costs, what it risks. A comparison table.
   Say why the rejected options lost, not just that they did.

5. PROPOSAL
   The chosen design and why, derived from section 3. Architecture diagram,
   the main read and write paths, and the components with their responsibilities.

6. DATA
   Entities, keys, partition keys, indexes, store per entity and why, size and
   growth, retention, migration from existing data, who may read what.

7. API
   Endpoints or messages, key fields, idempotency, pagination, error model,
   versioning and compatibility promises.

8. FAILURE MODES
   A table: what breaks, blast radius, how we detect it, what the user sees,
   how we recover. Include dependencies, overload, partial failure, bad deploys,
   data corruption and the "thundering herd" after recovery.

9. SECURITY AND PRIVACY
   Assets, trust boundaries, who is the attacker, authn/authz, data
   classification, encryption, abuse cases, audit. (See the secure design
   review checklist.)

10. OPERATIONS AND SLOs
   SLIs and SLOs, dashboards, alerts and who is paged, capacity plan, cost
   estimate, runbook links, on-call impact, data backups and restore tests.

11. ROLLOUT
   Stages and gates, feature flags, migration steps, how to roll back, what we
   measure at each stage, what is irreversible and when.

12. OPEN QUESTIONS
   Each with an owner and a date. Decisions needed from reviewers.

13. APPENDIX
   Calculations, benchmarks, links, glossary, alternatives in more detail.

3. Review checklist. Use it as the reader, with the doc in front of you. The security-specific version lives in the secure design review chapter; this one is the general pass.

PROBLEM AND SCOPE
[ ] I can state the problem and who has it in one sentence.
[ ] Goals are measurable; non-goals are explicit.
[ ] Every number has a stated assumption, and the biggest one is flagged.

OPTIONS
[ ] At least two real alternatives, including doing nothing or a simpler version.
[ ] The chosen option follows from the requirements and numbers, not from preference.
[ ] The costs of the chosen option are stated honestly.

DESIGN
[ ] Each component has one responsibility; each store has a reason.
[ ] Data ownership: one writer per piece of data, or conflict handling is explained.
[ ] Consistency and ordering needs are stated per operation, not for "the system".
[ ] Hot keys, large items and unbounded growth have been considered.
[ ] The API is idempotent where clients retry; pagination and errors are defined.

FAILURE AND OPERATION
[ ] Each dependency can fail; the behaviour is defined (timeout, retry, fallback, degrade).
[ ] Retries are bounded and cannot amplify an outage.
[ ] SLOs exist, alerts map to user impact, and an owner is named.
[ ] Backups exist and a restore has been tested or is scheduled.
[ ] Capacity and cost at 1x, 3x and 10x load are estimated.

SECURITY AND PRIVACY
[ ] Trust boundaries and authorization points are drawn; least privilege is applied.
[ ] Sensitive data is classified, minimised, encrypted and has a retention limit.
[ ] Abuse by a legitimate user was considered, not just outside attackers.

ROLLOUT
[ ] Staged, with a flag or a percentage, and a metric to watch at each stage.
[ ] A rollback step exists and has been exercised; irreversible steps are called out.
[ ] Migration of existing data and compatibility with old clients is covered.

DECISION
[ ] Open questions have owners and dates.
[ ] Reviewers' objections are recorded with the resolution, not just deleted.

What to look for

  • "Options considered" is the section reviewers read first. If the alternatives are strawmen, the doc will be challenged on exactly that.
  • The failure-mode table forces specifics: "the cache is down" is incomplete until you say what the user sees and what recovers it.
  • A good doc is short at the top: the one-pager should be readable by someone with two minutes.

Common pitfalls

  • Writing the doc after the code, as a description rather than a decision. The value is in the review before the work is expensive.
  • Filling every section with filler to "complete" the template. Delete sections that do not apply and say so.
  • Hiding open questions at the bottom. Put the ones that block a decision on page one.
  • Never updating it. Mark the status, link superseding docs, and keep decisions in a record you can find.

Say it out loud

Knowing a design and presenting one under time pressure are different skills. The only way to build the second is repetition with feedback.

Mock interview kit

Needs: one partner (or two), a timer, a whiteboard or Excalidraw, and a notes page · Plan follows: the eight-step framework · Chapters: 1, 4, 21

A mock session works because someone else interrupts you. This kit gives you the roles, a time plan, a way to play the interviewer so that you practise clarifying, twelve prompts beyond the studios, a scoring sheet and rules for feedback. Use the studios first for prompts with worked answers; use these when you want a fresh problem.

10-minute guided exercise

Do a ten-minute mini-mock now, to learn the mechanics before you commit to 45 minutes. Choose prompt 1 (pastebin) below. The candidate spends 3 minutes clarifying, 3 on numbers, and 4 on a first diagram, aloud. The interviewer plays the ambiguous product manager (below) and takes notes. Stop, spend two minutes swapping feedback using the format at the end, then swap roles. When it feels natural, run the full session.

1. The roles

  • Candidate. Drives. Talks aloud, draws, asks questions, states assumptions, and watches the clock.
  • Interviewer / product manager. Knows the prompt and the hint questions. Answers questions, pushes on weak spots, and keeps the candidate honest about time. Does not teach during the session.
  • Observer / timekeeper (optional third person). Fills in the scoring sheet and logs the actual minutes per phase, so the interviewer can focus on the conversation.

2. A 45-minute timing plan (the split from chapter 1; for 60 minutes scale each phase by one third and give the extra time to the deep dives):

MIN  PHASE                 CANDIDATE DELIVERS
0-5    1 Clarify            requirements, scale, out of scope, success metrics
5-9    2 Estimate           QPS, storage, bandwidth, each followed by "so..."
9-13   3 API                few endpoints/messages, idempotency, pagination
13-17  4 Data model         entities, keys, partition key, store and why
17-25  5 High-level design  diagram, read path and write path walked through
25-37  6 Deep dives         2 hardest parts, alternatives, a recommendation
37-41  7 Failure modes      what breaks, blast radius, SLOs, rollout
41-45  8 Wrap-up            trade-offs, what changes if a requirement changes

Interviewer checkpoints: say "10 minutes in", "halfway", "10 left" out loud.
If the candidate is more than 3 minutes behind plan, ask "what will you skip?"
rather than letting them rush everything.

3. Playing the ambiguous product manager. Real requests are vague, and the skill under test is turning vagueness into a testable list. So the interviewer opens with a deliberately thin prompt, then follows these rules:

  • Answer only what is asked. If the candidate does not ask about scale, do not volunteer it. Wait to see how long they go before designing without numbers.
  • Answer with a number or a yes/no, not a lecture. "Roughly 10 million daily users." "Yes, that matters." "I hadn't thought about it, what do you recommend?"
  • Be mildly inconsistent, once. Early on say "it should be real-time"; if the candidate never pins it down, later say "oh, a minute of delay is fine". Good candidates notice and ask which.
  • Hold some answers back. Say "I'm not sure, what would you assume?" for one or two questions, and see whether the candidate states and records the assumption.
  • Introduce one changed requirement at about minute 30: "legal says we must delete user data within 24 hours", "traffic will be 10x at launch", "we need to support a second region". Watch how the design bends.
  • Push, don't rescue. Use questions: "what happens when that node dies?", "why not use X?", "what is the bottleneck?". If the candidate is stuck, give the hint questions from the prompt, one at a time.
  • Stay friendly and neutral. No signalling approval or disapproval with your face; the point is to practise composure.

4. Twelve extra prompts (not covered by the studios). Each has a vague opening line and two or three hint questions the interviewer can use to steer, in order of how much help they give. Use them to prompt the candidate to think about a requirement, not to supply the answer.

1. PASTEBIN: "Design a service where people paste text and share a link."
   - How long should a paste live, and who is allowed to read it?
   - Reads dominate writes; where does the read path get its speed?
   - What happens to a 50 MB paste, and to a paste that is deleted but cached?

2. PARKING-GARAGE SYSTEM: "Design the software for a multi-level parking garage."
   - Is this one building's system, or a platform for many garages? Which fails if the network is down?
   - How do you stop two cars being assigned the same space?
   - How are entry, exit and payment tied together, and what if a ticket is lost?

3. DISTRIBUTED COUNTER: "Design a counter that many servers increment, e.g. video views."
   - How exact must the count be, and how fresh?
   - Why does one hot key become a bottleneck, and what does sharding the counter cost?
   - How do you avoid double counting when a client retries?

4. API GATEWAY: "Design the front door for a company's internal and public APIs."
   - What belongs in the gateway (auth, rate limits, routing) and what must stay in services?
   - What happens when the gateway itself is the outage?
   - How do you roll out a config change safely to a fleet of gateways?

5. NEWS AGGREGATOR: "Design a site that collects articles from thousands of publishers."
   - Pull or push: how do you learn about new articles, and how often per source?
   - How do you detect duplicates of the same story?
   - How do you rank, and how do you stay polite to the publishers' servers?

6. CALENDAR: "Design a calendar service with shared events and invitations."
   - How are recurring events stored, and how does one occurrence get edited?
   - How do time zones and daylight saving change the data model?
   - How do you check free/busy for 20 people quickly?

7. STOCK-PRICE ALERT SERVICE: "Notify users when a stock crosses their price."
   - How many alerts, how many price ticks per second, and how late may a notification be?
   - How do you avoid checking every alert on every tick?
   - How do you avoid sending the same alert twice, or none during a failover?

8. EMAIL SERVICE: "Design a service that sends and receives email for millions of users."
   - What is the path of a message from send to inbox, including other providers?
   - How do you handle spam, bounces and reputation?
   - How do you store mailboxes and search them?

9. SEARCH-ENGINE INDEXER: "Design the pipeline that turns crawled pages into a searchable index."
   - What is the unit of an index entry, and how is the index split across machines?
   - How do you update the index when pages change without rebuilding it?
   - How do you serve queries while the index is changing?

10. COLLABORATIVE WHITEBOARD: "Design a shared canvas that many people edit at once."
   - How do two people drawing at once avoid overwriting each other?
   - What do you send over the wire for each stroke, and how do late joiners catch up?
   - What happens to someone who goes offline for ten minutes?

11. LEADERBOARD: "Design a real-time leaderboard for a game with 50 million players."
   - What is read most: top N, or "my rank"? How fresh must each be?
   - How do you partition scores, and how do you merge them?
   - What changes at season end, and how do you stop cheating inflating the board?

12. FEATURE-FLAG SERVICE: "Design a service that turns features on for some users."
   - Who evaluates flags, the service on each request or a local library? What is the latency budget?
   - How do changes reach thousands of servers, and what if the flag service is down?
   - How do you keep a user's experience consistent, and audit who changed what?

After the session, compare your design with the building blocks in chapter 3 and with the nearest worked chapter: the leaderboard and counter relate to top-k, the gateway to the rate limiter, the whiteboard to the chat and presence chapter, and the indexer to the crawler.

6. Giving feedback. Keep it short and specific, in this order:

  1. The candidate speaks first. "What went well, and what would you change?" Most people name their own biggest gap.
  2. Strengths, with evidence. "Your estimate led to the decision to cache; that was clear." Name the moment, not a general impression.
  3. One or two improvements, not ten. Choose the ones that would change the score most. Frame them as an action: "next time say the p99 target before you pick the store".
  4. Separate the content from the delivery. A correct design delivered in a muddle and a weak design delivered clearly need different advice.
  5. Share the scoring sheet last, and agree on one drill for the week (for instance, three 5-minute estimation warm-ups).
  6. Keep a log. Date, prompt, total score, minutes per phase and the one change. Patterns (clarify too long, no failure modes) appear after three or four sessions.

What to look for

  • The minutes-per-phase line is the most revealing number. Most people spend too long on clarifying and the diagram, and leave under four minutes for failure and trade-offs.
  • Does the candidate say "so..." after each number? That is the link from estimation to design.
  • When the interviewer changes a requirement, does the candidate revise one part of the design or start over?

Common pitfalls

  • The interviewer teaches or gives the answer. Hold back; use a hint question only after a pause.
  • Practising only prompts you already know. Mix: one studio, one extra prompt, one that you make up.
  • Skipping the feedback because it is awkward. A mock without feedback is just talking.
  • Practising alone silently. Say it out loud even with no partner, and record yourself; listening back is the cheapest feedback available.

Try the risky part

Many design claims ("a token bucket is atomic in Redis", "a sorted set gives an instant top 10") are easy to say and easy to get subtly wrong. Ten minutes at a prompt turns a claim into something you have seen.

Redis for prototyping

macOS: brew install redis · Linux: your package manager (for example sudo apt install redis-server redis-tools) or the packages on redis.io/downloads · Docker (any OS): docker run -d --name redis-lab -p 127.0.0.1:6379:6379 redis:7 · Chapters: 5, 6, 12

Redis is an in-memory data-structure server: strings, hashes, lists, sets, sorted sets, HyperLogLogs, with expiry on any key and server-side Lua scripts that run atomically. It is a prototyping tool here, the same role it plays in the designs of the rate limiter, the distributed cache and top-k trending. Five exercises follow; each takes about two minutes. Every output below is illustrative (I did not run a server for this page); the Lua script was checked for syntax and logic under LuaJIT with a mock, as noted at the top.

10-minute guided exercise

0. Start a server and a client. Pick one:

$ brew install redis && redis-server --bind 127.0.0.1 --port 6379  # local install, terminal 1; loopback only
$ docker run -d --name redis-lab -p 127.0.0.1:6379:6379 redis:7  # or: Docker, publishing the port on loopback only
$ redis-cli -h 127.0.0.1 ping  # terminal 2 (with Docker and no local client: docker exec -it redis-lab redis-cli)
illustrative:  PONG

Everything below is typed at the 127.0.0.1:6379> prompt of redis-cli (the prompt itself is omitted in the blocks). Use a scratch server: the exercises create keys named tb:*, rl:*, board, cache:* and visitors.

1. A token bucket as a Lua script (chapter 5). The bucket holds up to capacity tokens and refills at rate tokens a second. A script runs atomically, so the read, the refill arithmetic and the write cannot interleave with another client's. Save this as tb.lua. Redis embeds Lua 5.1: ~= for not-equal, .. to join strings, tables start at 1, and a missing hash field arrives as false, which tonumber turns into nil.

-- KEYS[1] = bucket key; ARGV[1] = capacity, ARGV[2] = refill tokens per second, ARGV[3] = cost
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local cost     = tonumber(ARGV[3])

local t   = redis.call('TIME')                         -- {seconds, microseconds}
local now = t[1] * 1000 + math.floor(t[2] / 1000)      -- milliseconds

local data   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1])
local ts     = tonumber(data[2])
if tokens == nil then                                   -- first request: a full bucket
  tokens = capacity
  ts = now
end

tokens = math.min(capacity, tokens + math.max(0, now - ts) * rate / 1000)

local allowed = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) * 2)  -- idle buckets vanish
return {allowed, math.floor(tokens)}

Call it with --eval, which takes the key names, then a comma surrounded by spaces, then the arguments. Here: capacity 5, refill 1 token a second, cost 1:

$ for i in 1 2 3 4 5 6 7; do redis-cli -h 127.0.0.1 --eval tb.lua tb:alice , 5 1 1; done
illustrative:  1) (integer) 1   2) (integer) 4      (allowed, 4 left)
illustrative:  ... five allowed in a row, the fifth leaves 0
illustrative:  1) (integer) 0   2) (integer) 0      (the sixth and seventh are rejected)
$ sleep 2; redis-cli -h 127.0.0.1 --eval tb.lua tb:alice , 5 1 1
illustrative:  1) (integer) 1   2) (integer) 1      (two seconds refilled two tokens; one spent)
$ redis-cli -h 127.0.0.1 HGETALL tb:alice  # the whole state is two fields
$ redis-cli -h 127.0.0.1 PTTL tb:alice  # an idle bucket expires by itself

The same thing from inside redis-cli uses the plain form EVAL script numkeys key [key ...] arg [arg ...]. A one-line example: EVAL "return redis.call('INCR', KEYS[1])" 1 tb:demo. For a script you will call often, SCRIPT LOAD it and call EVALSHA with the returned digest.

2. Fixed-window counter with INCR and EXPIRE. The simplest limiter: count requests per user per window.

INCR rl:alice
EXPIRE rl:alice 60 NX
INCR rl:alice
TTL rl:alice
illustrative:  (integer) 1  /  (integer) 1  /  (integer) 2  /  (integer) 58

Reject when INCR returns more than your limit. EXPIRE ... NX (Redis 7.0 and later) sets the TTL only if the key has none, so the window starts at the first request and later calls do not extend it. On older servers use SET rl:alice 0 EX 60 NX first, then INCR. Sending the two commands in separate round trips can leave a counter with no expiry if the client dies in between; a MULTI/EXEC block or a script closes that gap. Now see the weakness for yourself: a client can spend its full limit at second 59 and again at second 61, so it gets twice the limit across the boundary. That is the burst that chapter 5 uses to motivate sliding windows and token buckets.

3. Sorted-set leaderboard (chapter 12).

ZADD board 100 alice 250 bob 175 carol
ZINCRBY board 90 alice
ZRANGE board 0 2 REV WITHSCORES
ZREVRANGE board 0 -1 WITHSCORES
ZREVRANK board alice
ZSCORE board carol
illustrative:  (integer) 3
illustrative:  "190"
illustrative:  1) "bob"  2) "250"  3) "alice"  4) "190"  5) "carol"  6) "175"
illustrative:  (same list from ZREVRANGE)
illustrative:  (integer) 1        (zero-based rank from the top)
illustrative:  "175"

ZADD inserts or updates, ZINCRBY adds to a score and returns the new one, ZREVRANGE key start stop [WITHSCORES] returns highest first. The command reference marks ZREVRANGE as deprecated since Redis 6.2 in favour of ZRANGE ... REV (the form on the third line, available from 6.2), but it is still widely seen, so you should recognise both. Every operation is O(log N), which is why a sorted set serves "top 10" and "my rank" without scanning. Notice what it does not do: it holds one node's worth of data. A 50-million-player board across many shards needs the merge strategy of the chapter.

4. A cache with a TTL (chapter 6).

SET cache:user:42 "{\"name\":\"Ada\"}" EX 30
GET cache:user:42
TTL cache:user:42
SET cache:user:42 "{\"name\":\"Ada L.\"}" KEEPTTL
TTL cache:nothing
illustrative:  OK  /  "{\"name\":\"Ada\"}"  /  (integer) 29  /  OK  /  (integer) -2

A key with a TTL vanishes by itself. TTL returns -1 for a key with no expiry and -2 for a missing key. A plain SET on an existing key discards its TTL, which is why KEEPTTL exists; forgetting that is a classic bug where a cache entry silently becomes permanent. The cache-aside pattern is then: GET; on a miss read the database and SET ... EX; to stop a thundering herd of misses on one hot key, add random jitter to the TTLs and have one caller rebuild it (SET lock:cache:user:42 1 NX EX 10). To watch eviction, try CONFIG SET maxmemory 2mb with CONFIG SET maxmemory-policy allkeys-lru on your scratch server and fill it.

5. HyperLogLog for approximate unique counts (chapter 12).

PFADD visitors u1 u2 u3 u1
PFCOUNT visitors
PFADD visitors u4 u5
PFCOUNT visitors
MEMORY USAGE visitors
illustrative:  (integer) 1
illustrative:  (integer) 3
illustrative:  (integer) 1
illustrative:  (integer) 5
illustrative:  (integer) a few hundred     (bytes; a HyperLogLog never grows past about 12 KB)

PFADD returns 1 if the structure changed. The duplicate u1 does not change the count. A HyperLogLog counts distinct elements in a fixed few kilobytes, with a standard error of about 0.81 percent (from the Redis documentation), however many items you add; it cannot list them or remove one. To feel the saving, add 100,000 ids in a loop: for i in $(seq 1 100000); do echo "PFADD big id$i"; done | redis-cli -h 127.0.0.1 > /dev/null, then PFCOUNT big (expect a number within about 1% of 100,000) and compare MEMORY USAGE big with the roughly 100,000 times 10 bytes a set would need. Merge counters with PFMERGE.

Clean up with redis-cli -h 127.0.0.1 DEL tb:alice rl:alice board cache:user:42 visitors big (never FLUSHALL on a server that holds anything else), then docker rm -f redis-lab or Ctrl-C the server.

Only on your own machines

Redis has no authentication in its default configuration and a client can read, overwrite or delete everything, and on a reachable server can run scripts and configuration commands. Run it only on 127.0.0.1, as above (note the 127.0.0.1:6379:6379 in the Docker command, which keeps the port off your network). Never expose port 6379 to a network or the internet, and never use FLUSHALL or CONFIG SET on a server that is not your own scratch instance. If you later run it for real, require a password or ACLs and put it on a private network (secure design review).

What to look for

  • The token bucket does not run a timer. It stores a level and a timestamp and computes the refill when asked (lazy refill), which is why one hash per user is enough and an idle user costs nothing after the TTL.
  • Atomicity is the whole reason for the script. Try writing the same logic with separate HGET and HSET calls from two terminals and see two clients both take the last token.
  • All of these are single-node. The designs in the chapters add sharding by key, replication and failure behaviour (what happens to limits if the node restarts: the counters are gone, so the limiter fails open for a moment).

Common pitfalls

  • Passing key names inside ARGV or building them inside the script. Key names go in KEYS so a cluster knows where to run the script.
  • In --eval form, forgetting the spaces around the comma; the comma must be its own argument.
  • Assuming Redis is durable by default. Persistence (RDB snapshots, the append-only file) is a separate setting with its own loss window; a cache can lose everything and a limiter's state is usually fine to lose, but a leaderboard may not be.
  • Long scripts block the server: one script runs at a time. Keep them short, and use EVAL only for the small atomic section.
  • Script and command details change between versions. Check redis-cli --version and the command reference for the exact form on your server.

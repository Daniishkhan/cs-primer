Design Ride Matching

Location updates, geospatial indexes, matching and the dispatch state machine. A quarter of a million pings a second go into memory, a cell index turns "who is near" into a lookup, and a lease on each driver makes sure no one is promised to two riders.

Why this matters

Ride matching is a real-time marketplace on a map. It teaches three things that recur everywhere: how to treat ephemeral state (where drivers are right now) as a different class of data from durable state (trips, money); how a spatial index turns "find nearby" from a scan into a lookup; and how to hand out a scarce resource (a driver) to exactly one of many racing dispatchers with a lease and a fencing token. The state machine and payments at the end are where the marketplace meets the rest of the business.

The problem

"Design a ride-hailing service. Riders request a ride from their location; the system finds a nearby available driver, offers the trip, and tracks it to the end."

Notice what the prompt leaves open: how many drivers, how fresh their position must be, whether we match one rider at a time or in batches, what "nearby" means (distance or time), what happens when two riders want the same driver, and what the system must do when the city's biggest stadium empties at once. Those are the questions to ask first (framework).

Clarify requirements

QuestionAssumed answer
Scale?1M drivers online at the global peak, 20M trips a day, about 400 active cities with a very uneven size distribution.

Functional. Drivers go online/offline and stream location; riders request a ride and see nearby cars; the system matches, offers with a timeout, and tracks the trip through a state machine; price is quoted up front; payment is collected at the end. Non-functional. Location ingestion keeps up with a quarter of a million writes a second; matching is fast and never double-assigns; a failure of the location system degrades matching quality but does not corrupt trips; and an event that concentrates demand in one place degrades gracefully.

Estimate

The key is to separate the ephemeral hot data (locations) from the durable cold data (trips). The script below computes both and also tests geohash cell sizes against driver density, which is the number that picks the index resolution. All inputs are assumptions.

The idea

  1. writes/s ← drivers ÷ ping interval; Mbit/s ← writes × bytes × 8
  2. trips/s ← per day ÷ 86,400; reads/s ← riders ÷ refresh; match ← peak × 3
  3. busiest city ← 3% × drivers; nodes ← ceil(writes/s ÷ 100k)
  4. per cell type: drivers ← area × density; downtown ← × 10

Decisions from the output.

  • Writes are the load; size is not. A million drivers pinging every 4 seconds is 250,000 writes a second, but the latest position of all of them is only about 100 MB. That fits in RAM on one machine and rules out a relational primary as the store of record for locations: you would be paying durable-commit costs for data that is worthless in 15 seconds. Keep the latest location in memory, sharded, and let it be lossy. If a node dies, drivers re-announce themselves within one ping interval, which is the recovery procedure.
  • History is a log, not a table. If you want every ping for analytics, safety review or training, that is 1.3 TB a day written as an append-only stream (streams) and sunk to cheap object storage. It is never on the matching path.
  • Trips are a modest transactional workload. 231 a second on average and about 1,200 at peak: a sharded relational store is comfortable. The marketplace's difficulty is the location firehose and the correctness of assignment, not trip volume.
  • Reads outnumber writes once riders watch the map (300k queries a second), which is another reason for in-memory spatial indexes with many read replicas per city rather than a database.
  • Resolution choice. At about 4.9 km, a geohash-5 cell holds ~48 drivers on average and ~480 downtown: too coarse, because each query reads hundreds of irrelevant drivers. At about 1.2 km x 0.6 km (geohash-6) the average is ~1.4 and downtown ~14: a 3x3 neighbourhood is about a dozen candidates on average and over a hundred downtown. Cell size should track density, which is the argument for adaptive structures (quadtrees) or multi-resolution cells.
  • Shard by city. The busiest city is ~30,000 drivers and ~7,500 writes a second: one node handles that with headroom, so the global rate is spread across a few dozen nodes, not thousands. Partitioning by region is natural because a rider in Lagos never needs a driver in Paris.

API

-- ── Driver ───────────────────────────────────────────────────────────
POST /v1/drivers/me/status
     {online: true, product_ids: [...]}

-- Server pushes offers; the client sends a ping about every 4 s
WS   /v1/drivers/me/stream
     client -> {type: "ping", lat, lng, heading, speed, ts, seq}

POST /v1/offers/{offer_id}/accept
     {token}  -> 200 | 409 offer_expired
POST /v1/offers/{offer_id}/decline

-- ── Rider ────────────────────────────────────────────────────────────
-- Approximate, cached for ~2-5 s
GET  /v1/nearby?lat=..&lng=..&product=economy
     -> [{lat, lng, heading} x up to 8]

POST /v1/quotes
     {pickup, dropoff, product}
     -> {quote_id, price_minor, currency, surge_multiplier,
         expires_at, eta_s}

POST /v1/trips
     {quote_id}   Idempotency-Key: ...
     -> 201 {trip_id, status: "requested"}

GET  /v1/trips/{id}
     -> status, driver, vehicle, eta, route so far
POST /v1/trips/{id}/cancel

Three API choices matter. Pings are tiny and unacknowledged-by-default: sequence numbers let the server drop out-of-order duplicates, and a missed ping costs four seconds of staleness. The quote is a contract: it carries a price, a multiplier and an expiry, and POST /trips references it, so the rider is never surprised by surge computed after the tap. Offers carry a token that the accept must echo, which is how a late or duplicated accept is rejected (see the lease deep dive). Trip creation is idempotent via a key, as in any API that moves money or reserves something (API design).

Data model

  • Driver location (ephemeral): in-memory map driver_id -> (lat, lng, heading, ts, cell) plus a reverse index cell -> set of driver_id, sharded by city or region, replicated to a follower for failover. Not durable, by design.
  • Driver state (small, hot, needs atomic update): driver_id -> (status: offline|idle|offered|on_trip, owner_trip, lease_expiry, token). Atomic compare-and-set on one record; a key-value store with conditional writes or a scripted in-memory store, sharded with the location shard so a match touches one shard.
  • Trips (durable): trips(trip_id, rider_id, driver_id, state, version, pickup, dropoff, quote_id, price_minor, currency, requested_at, ...) in a sharded relational store, partitioned by trip_id with a secondary index on rider_id and driver_id for "my active trip". The version column makes each state change an optimistic compare-and-set (MVCC and locking).
  • Event log: every ping and trip transition appended to a partitioned log (keyed by city/cell for pings, by trip for transitions). Feeds surge computation, ETA model training, safety audits, and the sync of the trip projection for analytics (CDC).
  • Cell aggregates: per cell and minute: supply (idle drivers), demand (ride requests), completions. Small and streaming-computed; drives surge and the heat maps.

High-level design

Drivers hold persistent connections to a gateway fleet (the same pattern as chat: chapter 10; the trade-offs of keeping many long-lived connections are in persistent connections). The gateway forwards pings to the location service and pushes offers back. The matching service is stateless apart from what it fetches: it reads the index, asks for ETAs, leases a driver and writes the trip. The path in order:

Step through

One ride request, from tap to assigned driver

  1. Request. The rider's app sends pickup, destination and product (economy, XL, ...) over its persistent connection. The gateway forwards to matching. A trip row is created in requested with an idempotency key so a retried tap does not create two trips.
  2. Find the rider's cells. Matching computes the pickup's cell and asks the location index for the ring of cells around it. The index holds each driver's latest position only, grouped by cell, in memory.
  3. Nearest-k candidates. It takes the drivers in those cells that are idle and eligible for the product, measures straight-line distance, and widens the search ring by ring until it has k candidates and the k-th is provably closer than anything unsearched.
  4. Rank by ETA, not distance. A straight line ignores rivers, one-way streets and traffic. Matching sends the top 10 to 15 candidates to the ETA service in one batch request, gets road-time estimates, and re-ranks.
  5. Lease the best driver. One atomic compare-and-set on the driver's state: idle becomes offered, with an owner, an expiry a few seconds out and a fresh fencing token. If another dispatcher got there first the CAS fails and matching tries the next candidate.
  6. Push the offer. The offer goes through the gateway to the driver's open connection, with a timeout (on the order of 10 to 15 seconds). If the driver declines or the lease expires, the driver returns to the pool and matching moves to the next candidate.
  7. Accept with the token. The driver accepts; the request carries the token. The state store checks owner, token and expiry and moves the driver to on_trip. A slow accept after the lease expired fails, because someone else may hold the driver now.
  8. Record the trip. Matching writes the trip as accepted with the driver id, in a transaction that checks the previous version. This durable write is the commit point; everything before it is soft state that can be lost and recomputed.
  9. Tell the rider. The rider gets the driver, the vehicle and an ETA; from now on the driver's pings are relayed to the rider's map. If no driver ever accepts, the trip ends in no driver found after the retry budget.

Deep dive 1: geospatial indexing

"Find the nearest k drivers" over a million moving points, 3,500 times a second, with positions that change every 4 seconds. A full scan is out (the script below measures 80 ms per query at 200,000 drivers). We need an index that is cheap to update, because it is write-heavy, and cheap to query by area.

The full story of why a hexagonal grid suits a marketplace, with the numbers, is in the Uber H3 case study; the sources are cited there, and I rely on it rather than repeat the claims. As a reference point from the H3 documentation, resolution 8 has an average edge of about 0.53 km and resolution 9 about 0.20 km, and there are 122 coarsest "base" cells, 12 of which are pentagons. My recommendation, as an opinion: for a first design, a geohash or H3 cell index in a sharded in-memory map is the simplest thing that works; reach for a quadtree when density varies enough that one resolution cannot serve both downtown and the suburbs; and keep the index behind an interface so the cell scheme can change without touching matching.

k-nearest by expanding rings

A cell grid answers "who is in this cell" in constant time. "Who are the k nearest" is a loop: search the rider's cell, then the ring of eight around it, then the ring of sixteen around that, and so on. The stopping rule is the part people get wrong. Having found k candidates in the cells searched so far is not enough: a driver just outside the searched block could be closer than the k-th you found. The safe rule: after searching rings 0 to r, anything unsearched is at least r x (smallest cell side) away from the rider, because the rider sits somewhere inside their own cell and the block extends r full cells beyond it. So stop when you hold k candidates and the k-th is closer than that bound. The widget applies exactly that rule. The script implements it and checks it against brute force.

The idea

  1. encode: bisect lng, lat, lng, … ; 5 bits per base-32 character
  2. index: cell → drivers; knn: add ring r = 0, 1, … until k found
  3. stop when k-th distance ≤ r × smallest cell side
  4. populate 60 km region, 40% downtown; compare index to brute force
  5. cells either side of a boundary hash differently, so search neighbours
"""Geohash + grid index vs brute force for nearest-k drivers.
Pure stdlib, deterministic apart from the timing lines. The index maps
cell -> {driver ids}; k-nearest searches rings of cells outward."""
import math
import os
import random
import time

# ── 1. Geohash encoding ───────────────────────────────────────────────
BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz"


def encode(lat, lng, precision):
    """Interleave longitude/latitude bisection bits, 5 bits per character."""
    lat_range = [-90.0, 90.0]
    lng_range = [-180.0, 180.0]
    use_lng = True              # bits alternate: lng, lat, lng, ...
    bit_count = 0
    chunk = 0
    out = ""
    while len(out) < precision:
        if use_lng:
            rng, value = lng_range, lng
        else:
            rng, value = lat_range, lat
        mid = (rng[0] + rng[1]) / 2
        chunk <<= 1
        if value >= mid:
            chunk |= 1
            rng[0] = mid        # keep the upper half
        else:
            rng[1] = mid        # keep the lower half
        use_lng = not use_lng
        bit_count += 1
        if bit_count == 5:
            out += BASE32[chunk]
            bit_count = 0
            chunk = 0
    return out


def cell_size_deg(precision):
    lng_bits = (5 * precision + 1) // 2
    lat_bits = 5 * precision // 2
    return 180 / 2 ** lat_bits, 360 / 2 ** lng_bits


def km(a, b):
    """Equirectangular approximation; fine at city scale."""
    mean_lat = math.radians((a[0] + b[0]) / 2)
    dlat = math.radians(b[0] - a[0])
    dlng = math.radians(b[1] - a[1]) * math.cos(mean_lat)
    return 6371 * math.hypot(dlat, dlng)


# ── 2. The grid index and ring search ─────────────────────────────────
PREC = 6
DLAT, DLNG = cell_size_deg(PREC)    # one cell's height and width, degrees
MAX_RINGS = 60                      # safety stop for empty regions


class Index:
    def __init__(self):
        self.cells = {}             # cell -> set of driver ids
        self.where = {}             # driver id -> its current cell

    def update(self, driver, lat, lng):
        cell = encode(lat, lng, PREC)
        old = self.where.get(driver)
        if old and old != cell:
            self.cells[old].discard(driver)     # moved: leave the old cell
        self.cells.setdefault(cell, set()).add(driver)
        self.where[driver] = cell

    def knn(self, lat, lng, k, pos):
        """Return (k nearest, rings searched, drivers examined)."""
        best = []
        examined = 0
        ring = 0
        side_km = min(DLAT * 111.2,
                      DLNG * 111.2 * math.cos(math.radians(lat)))
        while True:
            for di in range(-ring, ring + 1):
                for dj in range(-ring, ring + 1):
                    if max(abs(di), abs(dj)) != ring:
                        continue                # only the new outer ring
                    cell = encode(lat + di * DLAT, lng + dj * DLNG, PREC)
                    for d in self.cells.get(cell, ()):
                        best.append((km((lat, lng), pos[d]), d))
                        examined += 1
            best.sort()
            best = best[:k]
            # Correctness: after ring r, anything unsearched is at least
            # r * (smallest cell side) away. Stop only when we hold k
            # candidates and the k-th is inside that bound.
            if len(best) == k and best[-1][0] <= ring * side_km:
                return best, ring, examined
            ring += 1
            if ring > MAX_RINGS:
                return best, ring, examined


# ── 3. A synthetic metro region ───────────────────────────────────────
def populate(n, seed):
    rnd = random.Random(seed)
    pos = {}
    idx = Index()
    for i in range(n):
        # roughly 60 km x 60 km; 40% of drivers clustered downtown
        hot = rnd.random() < 0.4
        if hot:
            lat = 37.77 + rnd.gauss(0, 0.03)
        else:
            lat = 37.77 + rnd.uniform(-0.27, 0.27)
        if hot:
            lng = -122.42 + rnd.gauss(0, 0.04)
        else:
            lng = -122.42 + rnd.uniform(-0.33, 0.33)
        pos[i] = (lat, lng)
        idx.update(i, lat, lng)
    return pos, idx


K = 8
N_QUERIES = 200
N_CHECKED = 20                  # queries also answered by brute force
query_rng = random.Random(11)
queries = []
for _ in range(N_QUERIES):
    q_lat = 37.77 + query_rng.uniform(-0.2, 0.2)
    q_lng = -122.42 + query_rng.uniform(-0.25, 0.25)
    queries.append((q_lat, q_lng))


def brute(q, pos):
    return sorted((km(q, p), d) for d, p in pos.items())[:K]


def ids(results):
    return [d for _, d in results]


# ── 4. Index vs brute force ───────────────────────────────────────────
for n in (200_000, 3_000):
    pos, idx = populate(n, 7)

    t0 = time.perf_counter()
    res = [idx.knn(q[0], q[1], K, pos) for q in queries]
    t1 = time.perf_counter()

    same = 0
    for i in range(N_CHECKED):
        if ids(res[i][0]) == ids(brute(queries[i], pos)):
            same += 1

    t2 = time.perf_counter()
    for q in queries[:N_CHECKED]:
        brute(q, pos)
    t3 = time.perf_counter()

    rings = [r for _, r, _ in res]
    examined = [e for _, _, e in res]
    tall = DLAT * 111.2
    wide = DLNG * 111.2 * math.cos(math.radians(37.77))
    index_ms = (t1 - t0) / N_QUERIES * 1000
    brute_ms = (t3 - t2) / N_CHECKED * 1000

    print(f"{n:>7,} drivers, geohash-{PREC} "
          f"(cell {tall:.2f} km tall x {wide:.2f} km wide), "
          f"{len(idx.cells):,} non-empty cells")
    print(f"   matches brute force on 20/20 sampled queries: "
          f"{same == N_CHECKED}")
    print(f"   rings searched: mean {sum(rings) / len(rings):.1f}, "
          f"max {max(rings)};  "
          f"drivers examined: mean {sum(examined) / len(examined):.0f} "
          f"(not {n:,})")
    print(f"   grid index {index_ms:.2f} ms/query   "
          f"brute force {brute_ms:.1f} ms/query")

# ── 5. Geohash sanity check and the boundary problem ──────────────────

Updating the index

Each ping is a move: remove the driver from the old cell's set, add to the new one, update the position map. Most pings stay in the same cell, so most are a single map write. Do the update inside the shard's single thread or under a per-cell lock; do not take a global lock. Expire entries by timestamp: a sweeper (or a lazy check at read time) removes drivers whose last ping is older than the freshness bound, so a driver whose phone died stops being matched.

Deep dive 2: matching, offers and not double-assigning

Distance is not ETA

The nearest driver in a straight line may be across a river or on the wrong side of a one-way street. So matching has two stages: the cheap, geometric candidate generation (nearest k from the index, k maybe 10 to 15), then an ETA ranking of just those candidates using road-network travel time, computed by a routing service in one batched request. Computing ETA for every driver in the city would be absurd; computing it for a dozen is cheap. Keep the straight-line stage generous (the true best by road is usually within the top k by distance, not always the first) and be explicit that this is a heuristic. Other things enter the ranking: driver heading and whether they are about to finish a trip nearby, vehicle type, acceptance history.

Greedy offers versus batched matching

StrategyHow it worksGoodBad
Greedy, sequentialFor each request, offer to the best candidate; on decline/timeout, the nextSimple; fast for the first rider; statelessLocally optimal only: it may use up the closest driver for a rider who had other options, leaving a worse match for the next

Opinion: start greedy; move to batching in dense cells where concurrent requests are common, since that is where greedy wastes the most. The assignment problem itself (minimum-cost bipartite matching) is textbook and not the interesting part; the interesting parts are the window length and the cost function.

The race: one driver, many dispatchers

At peak, matching runs on many stateless workers. Two of them can pick the same driver at the same moment, each convinced that he is idle. The naive code reads status, checks it is idle, then writes offered: a classic check-then-act race. The cure is the lease from leases and fencing, applied to a driver:

  • Reserve atomically. One conditional write: "if status is idle (or holds an expired lease), set status offered, owner this trip, expiry now + a few seconds, and issue a new monotonically increasing token." Exactly one dispatcher's write succeeds; the others get a failure and try their next candidate.
  • The lease expires on its own. If the dispatcher crashes after reserving, or the driver ignores the offer, nobody needs to clean up: the expiry returns the driver to the pool. No process has to remember to release.
  • Accept carries the token. A driver (or a dispatcher acting for one) that was paused for longer than the lease and then tries to confirm presents an old token; the state store rejects it because the current token is newer. This is the fencing-token argument, here protecting the case where dispatcher A stalls, B re-leases the driver, and A wakes up and "accepts".

The simulation runs many interleaved dispatchers over a small pool of popular drivers, once with the naive read-then-write and once with the lease. Every yield is a point where another dispatcher can run. An invariant check after each step counts the moments two live trips believe they hold the same driver.

The idea

  1. store: status, owner, expiry, token per driver; every op atomic
  2. lease ← if idle or expired: token ← ++seq; naive ← read, yield, write
  3. scheduler: each tick start a trip (p 0.6), shuffle, step each dispatcher
  4. run both schemes on one seed; count drivers held by two trips at once
  5. A leases and pauses; B leases after expiry; A's late accept fails
"""Dispatch without double assignment. Dispatcher requests run concurrently
(generators interleaved by a seeded scheduler). Compares a check-then-act
reservation with one atomic lease plus a fencing token."""
import random

# Every `yield` below is a point where another dispatcher can run.
#   naive : read the driver's status, then (a yield later) write 'offered'.
#   lease : ONE atomic compare-and-set: status is idle, or holds an EXPIRED
#           lease. It sets owner, expiry and a fencing token; the driver's
#           accept carries the token and the store rejects any other.
# Invariant checked after every step: no driver is held by two live trips.

# ── 1. The driver-state store ─────────────────────────────────────────
class Store:
    def __init__(self, n):
        self.status = ["idle"] * n
        self.owner = [None] * n
        self.expires = [0.0] * n
        self.token = [0] * n
        self.seq = 0                # fencing tokens only ever increase

    def try_lease(self, d, trip, now, ttl):
        """Atomic: one shard, single-threaded, or a Lua script."""
        free = self.status[d] == "idle"
        lapsed = self.status[d] == "offered" and self.expires[d] <= now
        if free or lapsed:
            self.seq += 1
            self.status[d] = "offered"
            self.owner[d] = trip
            self.expires[d] = now + ttl
            self.token[d] = self.seq
            return self.token[d]
        return None

    def accept(self, d, trip, tok, now):
        """Atomic. Fencing: only the current token wins."""
        current = (self.status[d] == "offered"
                   and self.owner[d] == trip
                   and self.token[d] == tok
                   and self.expires[d] > now)
        if current:
            self.status[d] = "on_trip"
            return True
        return False

    def release(self, d, trip, tok):
        if self.owner[d] == trip and self.token[d] == tok:
            self.status[d] = "idle"
            self.owner[d] = None


# ── 2. One dispatcher per trip, as a generator ────────────────────────
def simulate(scheme, seed, drivers=40, trips=300, ttl=3.0):
    rnd = random.Random(seed)
    st = Store(drivers)
    # which live trips believe they hold each driver
    holders = [set() for _ in range(drivers)]
    clock = [0.0]
    stats = dict(matched=0, declined=0, timed_out=0, no_driver=0,
                 violations=0)

    def check(d):
        if len(holders[d]) > 1:
            stats["violations"] += 1

    def dispatcher(trip):
        # popular drivers near a hot spot: everyone competes for the same few
        cands = sorted(range(drivers),
                       key=lambda d: abs(d - trip % 6) + rnd.random())[:6]
        for d in cands:
            if scheme == "naive":
                seen = st.status[d]
                yield               # read ... another dispatcher may run ...
                if seen != "idle":
                    continue
                # ... then write, based on a stale read: the race.
                st.status[d] = "offered"
                st.owner[d] = trip
                holders[d].add(trip)
                check(d)
                tok = 0
            else:
                tok = st.try_lease(d, trip, clock[0], ttl)
                if not tok:
                    continue
                holders[d].add(trip)
                check(d)
            yield                   # the offer is out; wait for the driver

            r = rnd.random()
            if r < 0.55:            # the driver accepts
                if scheme == "naive":
                    ok = True
                else:
                    ok = st.accept(d, trip, tok, clock[0])
                if ok:
                    st.status[d] = "on_trip"
                    st.owner[d] = trip
                    stats["matched"] += 1
                    for _ in range(rnd.randint(5, 25)):
                        yield       # the trip lasts a while
                    holders[d].discard(trip)
                    st.status[d] = "idle"
                    st.owner[d] = None
                    return
            elif r < 0.80:
                stats["declined"] += 1
            else:
                stats["timed_out"] += 1
                for _ in range(4):
                    yield           # silence until the timeout

            holders[d].discard(trip)
            if scheme == "naive":
                st.status[d] = "idle"
            else:
                st.release(d, trip, tok)
        stats["no_driver"] += 1

    # ── 3. The seeded scheduler interleaves dispatchers ─────────────
    live = []
    next_trip = 0
    while next_trip < trips or live:
        clock[0] += 0.1
        if next_trip < trips and rnd.random() < 0.6:
            live.append(dispatcher(next_trip))
            next_trip += 1
        rnd.shuffle(live)
        for g in live[:]:
            try:
                next(g)
            except StopIteration:
                live.remove(g)
    return stats

The naive scheme double-assigned drivers hundreds of times in this run; the lease scheme did so zero times. Look at the price, though, because there is one: the lease run matched fewer trips and left more riders without a driver in this toy because contention on the same few drivers is now resolved by refusal instead of by duplication. That is the right trade: a rider told "no driver yet" can be retried or batched; a driver sent to two riders is a failed trip and an angry person. The last lines are the stale accept: A's lease expired at t=3, B re-leased at t=4, and A's late accept at t=5 is rejected while B's succeeds. Also handle the driver side of double assignment: a driver app that is offered a trip must not simultaneously be offered another; offered being a distinct status handles it. And think about the other direction: a rider who taps twice, or whose request is retried by the client, must not get two cars; the idempotency key on POST /trips handles it.

Deep dive 3: the trip state machine

A trip is a long-lived entity that several actors mutate concurrently: the rider (cancel), the driver (accept, arrive, start, end), the matcher (assign, time out), a payment system (charge result), and support staff. Model it as an explicit state machine and make every transition a compare-and-set on the trip's version, with the allowed edges enumerated in code.

The reasons to be this strict. Racing events have one winner. If the rider cancels while the driver accepts, both try to move the same version; one commit succeeds and the other sees a conflict and is told the truth. Side effects follow the state change through an outbox (streams and CDC), so a crash between "trip is accepted" and "rider is notified" cannot lose the notification; consumers are idempotent. Failure states are first-class. No-driver, cancelled and payment-failed are states with their own handling, not exceptions. When a step spans several services (matching, pricing, payment) and one can fail after another has acted, the design is a saga with compensations (sagas): releasing the driver is the compensation for a cancelled trip.

Deep dive 4: surge, partitioning and hot spots

Surge pricing, at concept level

When demand in an area exceeds supply, prices rise to bring more drivers in and to ration scarce cars to riders who value them most. Mechanically: in each cell, every minute, compute a supply/demand ratio from the streaming aggregates (idle drivers versus requests plus app opens), smooth it over time and across neighbouring cells (this is where H3's uniform neighbours are convenient), map the smoothed ratio to a bounded multiplier, and apply hysteresis so the price does not flicker. Two design rules matter more than the formula. First, the quote locks the price for a short window, so the multiplier is computed before the tap and honoured after. Second, pricing is an eventually consistent, per-cell, read-mostly value: stale by seconds is fine, and it can be served from a cache. The policy questions (caps during emergencies, fairness, transparency) are product and ethics decisions that engineering must make easy to configure and audit, not hard-code.

Partitioning

Matching is local: a rider in one city only ever needs drivers in that city. So partition by city or region: each region has its own location index shard, driver-state shard and matching workers, and the global layer only routes a request to its region (a lookup from coordinates to region). Properties: failures are contained by region (a bad deploy or crash affects one region; see blast radius); capacity can be sized and scaled per region; data can live near its users (multi-region). Costs: regions near a boundary need to see drivers across it (a halo: the neighbouring shard is queried as well, or boundary cells are replicated), and a city that outgrows one node needs a second level of partitioning by cell range. Use consistent hashing of cells within a region to spread them (partitioning), keeping neighbouring cells together enough that a ring query hits one or two shards, not twenty.

Hot spots

A stadium emptying or New Year's Eve produces thousands of requests from a few cells within minutes, and the nearby driver pool is tiny relative to demand. Everything we designed so far has a weakness here: one shard receives most queries, the same few drivers are contended by hundreds of dispatchers, and greedy matching thrashes. Responses, in the order I would build them:

  • Admission and queueing. Put riders in an ordered queue per hot cell and match at the rate drivers become available, rather than letting every request hammer the index (overload). Show honest wait estimates.
  • Batching. In hot cells, switch from greedy to windowed assignment so one pass serves many riders without lease conflicts.
  • Shed the free work. Serve the "cars near me" map from a cached snapshot refreshed every few seconds; it can be hit a hundred times harder than matching without touching the index.
  • Split the shard. Detect a cell or shard over a load threshold and split the cell range onto another node, which is the adaptive-resolution idea again.
  • Suggest pickup points. Move riders to a nearby pickup spot, spreading them across cells and reducing the pile-up (a product fix to a systems problem).
  • Pre-position supply. Surge prices and driver heat maps pull drivers toward the area before the event ends. The best remedy for scarcity is supply.

Payments at trip end

When the trip reaches completed, the fare is final and the payment must be collected. The ride system does not move money itself. It emits a charge request carrying an idempotency key derived from the trip id, the rider's payment method token, the amount in integer minor units and the currency, and a callback address. The payment system authorises and captures with the card network's processor and answers asynchronously with paid or failed; a failure leaves the trip in payment failed and triggers retries and a rider-debt flag. Because the ride is already over, a payment problem never blocks the rider from leaving; it only affects the next request. Idempotency, unknown outcomes, the ledger and reconciliation are the substance of Design a Payment System. Many marketplaces also place an authorisation hold at request time to catch invalid cards early; that, too, is a payments concept.

Trade-offs & alternatives

  • Freshness versus cost. A 4-second ping gives accurate matching and a 250k writes/second ingest bill. Adaptive rates (more often when moving fast or near a request, less when parked) cut writes without hurting quality; this is a battery argument too.
  • Greedy versus batched matching. Latency to first offer versus overall efficiency. Mixed by density.
  • Ephemeral versus durable location. We chose to lose location on a crash because it re-converges in seconds. If regulations required a durable breadcrumb for every trip, write the trip-time pings to the log (we already do) but still serve matching from memory.
  • Fixed grid versus adaptive structure. Fixed cells are simple and cache-friendly but waste work in sparse or dense extremes. Adaptive structures fit the data and cost complexity.
  • If it were delivery with batching of multiple orders per courier, the problem becomes vehicle routing, not nearest-driver search.
  • If drivers were scheduled in advance (airport pickups), inventory-style reservation (the next chapter) replaces the real-time lease.
  • Where it breaks down: GPS error in city canyons puts drivers in the wrong cell or on the wrong side of a road. Map-matching to the road network on the server, and a pickup point rather than a coordinate, fix most of it.

What a strong answer adds

  • Separates ephemeral location from durable trips, and justifies in-memory, sharded, lossy storage with the write-rate and size numbers.
  • Chooses a cell resolution from driver density, not by habit, and names geohash, quadtree, S2 and H3 with one real strength and weakness each.
  • States the stopping rule for ring expansion (the bound on unsearched distance), not just "keep widening".
  • Explains distance versus ETA and uses a two-stage candidate and rank pipeline.
  • Prevents double assignment with an atomic lease with expiry and a fencing token, and explains why a crashed dispatcher needs no cleanup.
  • Draws the trip state machine with failure states and uses a version check on each transition and an outbox for side effects.
  • Partitions by city, thinks about the boundary halo, and has a plan for a hot cell beyond "add servers".
  • Keeps surge at concept level but locks the price in a quote, and hands payment off with an idempotency key.

Follow-up questions

How do you find drivers near a rider who is exactly on a cell boundary?

Always search the rider's cell plus its neighbours. A boundary rider has drivers just across the line in the next cell, and nearby points can have very different geohash prefixes. The ring-expansion stopping rule accounts for it, because it only trusts the k-th candidate once the searched block extends far enough in every direction.

What if two riders both get offered the same driver?

They cannot, if reserving is a single atomic compare-and-set on the driver's state (idle to offered, with an owner, an expiry and a token). The second dispatcher's CAS fails and it tries the next candidate. If we had used read-then-write instead, both would proceed; the simulation shows it. A late accept is rejected because its token is stale.

How would you handle the stadium letting out?

Queue riders per hot cell and match at the rate supply appears; switch the cell to batched assignment; serve the nearby-cars map from a cached snapshot so it does not load the index; split the hot shard if it saturates; suggest walkable pickup points to spread riders across cells; and let surge pricing pull drivers in. Show honest wait times.

How do you keep driver positions fresh without melting the backend?

Cheaper pings, not fewer drivers: adaptive intervals (slower when stationary), compact binary messages, batching at the gateway, and in-memory sharding so a ping is one map write. Drop out-of-order pings by sequence number. Staleness has a defined bound (about 15 seconds) after which a driver is excluded.

Why not store locations in Postgres with PostGIS?

For static places, PostGIS and an R-tree are excellent. For 250k updates a second on points that are worthless in seconds, you would pay durable-commit and index-maintenance costs for data that needs neither. The ephemeral store is faster, cheaper, and its crash recovery is 'wait one ping interval'. Use the database for trips, where durability matters.

How would you show a rider an ETA that is honest?

The matched driver's route ETA to pickup, recomputed from live positions every few seconds, with a pessimistic margin on uncertain segments, and an explicit change message if it moves a lot. Before matching, the 'N minutes away' figure is an estimate from nearby idle drivers, labelled as such.

Distributed systems connection

The lease with a fencing token is the same mechanism you met for distributed locks, applied to a physical resource, and the check-then-act race is the same one you will find in the isolation chapter as a lost update. The trip state machine with version checks and an outbox is optimistic concurrency plus reliable messaging. Sharding by city is partitioning along a natural locality, and the boundary halo is its usual cost.

Key takeaways

  • Locations are ephemeral: 250k writes/s but about 100 MB. Keep the latest position in memory, sharded and lossy; stream history to a log; never put pings in the trip database.
  • Index by cells (geohash, quadtree, S2 or H3). Choose resolution from driver density, always search neighbours, and stop ring expansion only when the k-th candidate is closer than rings x smallest cell side.
  • Generate candidates by straight-line distance and rank a dozen by road ETA. Distance is a heuristic, not the answer.
  • Prevent double assignment with an atomic lease on the driver (owner, expiry, fencing token). Expiry is the cleanup; the token rejects stale accepts.
  • The trip is an explicit state machine with versioned transitions, failure states as first-class states and side effects through an outbox.
  • Partition by city or region with a halo at boundaries; plan for hot cells with queues, batching, cached maps, shard splitting and pricing.
  • Surge is a smoothed per-cell supply/demand multiplier, locked in the quote. Payment is a hand-off with an idempotency key to the payment system.

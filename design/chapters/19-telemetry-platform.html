Design a Metrics & Logging Platform

High-volume ingestion, time-series storage, downsampling, cardinality and queries. Telemetry is the system that tells you every other system is broken, so it must be cheap enough to leave on, fast enough to answer during an incident, and independent enough to keep working when everything else does not.

Why this matters

You have used metrics, logs and alerts as a consumer. This chapter builds the thing underneath. It is a write-heavy, append-mostly, read-rarely system whose economics are set by one multiplication (label values multiplying into series), whose storage trick is exploiting the regularity of the data, and whose hardest requirement is an operational one: it must stay up when the services it watches fall over, and someone must watch it without using itself.

The problem

"Design a metrics and logging platform for a large company. Every service emits metrics and logs. Engineers build dashboards, write alerts and search logs when something breaks."

The one-sentence prompt contains two systems with different physics. Metrics are small, numeric, regular and queried by aggregation; logs are large, textual, irregular and queried by search. They share an ingestion pipeline shape and a tenancy model, so we design them together but store them differently. We start with the questions from the framework.

Reading the output. Five million points per second is 432 billion points a day. Stored as 16-byte raw samples that would be 7 TB a day; at the roughly 1.5 bytes per point I assume after compression (the next section shows where such a number comes from and when it fails), it is 0.65 TB a day, which is why compression is not an optimisation here but the thing that makes the design affordable. The pipeline is a modest 120 MB/s, and about ten ingesters carry the steady load. Notice two surprises. First, memory is set by active series, not by points per second: 50 million series at roughly 4 KB each is 200 GB per replica, so a runaway label that creates ten million series costs more memory than a tenfold traffic spike. Second, the rollup tiers are a larger bill than the raw tier (about 39 TB for 90 days of 1-minute rollups against 10 TB for 15 days of raw) because they keep four values per point and live six times as long; the design question is not "can we keep raw forever" but "which rollups, kept for how long". Logs are in a different league: 1.2 million lines per second and tens of terabytes of retained text, which is why indexing every word is off the table (Deep dive 5). And the last block is the query problem: fanning one query out to 100 shards makes at least one of them slow 63% of the time, even if each is slow only 1% of the time.

GET /v1/labels, /v1/label/{name}/values       -- for dashboards and autocomplete

-- Control plane
PUT /v1/tenants/{id}/limits  { "max_series": 1000000, "ingest_rate": 200000, "retention_days": 15 }
PUT /v1/rules/{tenant}       { "alerts": [ … ] }
  • Batching is the API design. One request carries thousands of samples; per-sample requests would multiply the cost of authentication, routing and acknowledgement by the batch size.
  • Idempotent by (series, timestamp). An agent that retries a batch after a timeout does not double-count: the second write of the same timestamp is a no-op. Counters are cumulative values, not increments, which is what makes retries and rate calculations safe (metrics).
  • 429 carries information. Over-limit responses say which limit and when to retry, so agents back off sanely instead of retry-storming.
  • Reads take a step and a range. The platform chooses the storage tier from the step; the client does not choose it.

Data model

  • Series identity. A series is the metric name plus its full label set. Hash the sorted labels into a 64-bit series id. Every distinct combination is a separate series, which is the source of the cardinality problem.
  • Chunks. For each series, samples are packed into compressed chunks covering a time slice (for example two hours). A chunk is the unit of compression, storage and query.
  • Index. An inverted index maps each label=value pair to the sorted list of series ids that carry it (a postings list). A selector like {service="api", region="eu"} is an intersection of two postings lists. Compare the inverted indexes of search, applied to labels instead of words.
  • Blocks. Closed time ranges of chunks plus their index are written as an immutable block in object storage. Immutable blocks are cheap to replicate, cache and delete when they age out.
  • Head. The most recent window (about two hours) lives in memory in the ingesters, backed by a write-ahead log for crash recovery, so recent queries are fast and writes are cheap appends.
  • Logs. A stream is a unique label set (service, environment, host group); entries within a stream are time-ordered and packed into compressed chunks. The index records only labels and chunk time ranges, not log text (Deep dive 5).
  • Partition key. For writes, the hash of the series id (or stream labels) picks the ingester set via consistent hashing, so a series lives on a stable small set of machines and its samples land in one chunk. Tenant id is part of the hash seed, and tenant isolation (limits, queues) is enforced before routing.

High-level design

The central choice is the buffer log between distributors and ingesters. Ingesters are stateful (they hold the head in memory) and restart often during deploys; without a buffer, every restart either loses data or forces agents to retry into a recovering node. With a replicated, partitioned log (streams), ingestion is just an append that survives ingester failures, ingesters consume at their own pace, and a restarted ingester replays from its last committed offset. The cost is one more tier and a few seconds of latency. The path of one data point:

Step through

One data point, from emit to chart

  1. Collect and batch. The agent gathers samples (by scraping local endpoints or receiving pushes), attaches the host's labels, batches about a second of data and compresses it. Batching turns millions of samples a second into thousands of requests.
  2. Admit. The distributor authenticates the tenant, checks rate and series limits, rejects samples that are too old or too far in the future, and routes each series by hash to its partition. Rejection happens here, cheaply, before the data costs storage.
  3. Append to the log. The batch is appended to the partition's replicated log; once a quorum has it, the agent gets its ack. This is the durability point.
  4. Ingest. The ingester that owns the partition consumes it, finds or creates the series in its index, appends the sample to the series' head chunk (compressed incrementally) and to a local WAL.
  5. Cut a block. Periodically the head's older data is written as an immutable block to object storage, and the WAL is truncated.
  6. Compact. A background compactor merges small blocks into larger ones, deduplicates replicas, and writes downsampled tiers. Reads never wait for it.
  7. Query. A querier merges what the ingesters hold with what blocks hold for the requested range and step, deduplicating overlap, and returns a chart.

Both designs exist in practice. I recommend the log when the team already operates one and when frequent deploys of ingesters matter; direct quorum writes when minimal latency and fewer moving parts win. Whichever you choose, say what the durability point is and what lag means for the freshness SLO. A key property the log gives for free: offsets turn replay into a deterministic operation, the same idea as exactly-once processing from a log. Combined with idempotence by (series, timestamp) the system is effectively exactly-once for samples.

Ordering, duplicates and time

Samples carry the source's timestamp, so late and out-of-order arrivals are normal (an agent that buffered through an outage). The ingester accepts a bounded window of out-of-order data into the head and rejects older, counting the rejects per tenant. Duplicate samples with the same timestamp and value are dropped; the same timestamp with a different value is a client bug and is counted, not silently overwritten. Do not use the platform's clock for sample time; clock skew on sources (time revisited) is the sources' problem, but the platform should flag series whose timestamps are wildly in the future.

Deep dive 2: time-series storage, compression and tiers

Why time series compress so well

Metrics from a healthy system are regular: timestamps arrive at fixed intervals, and consecutive values are often equal or close. The Gorilla in-memory time-series database at Facebook (Pelkonen et al., VLDB 2015) exploited exactly that with two ideas that most modern time-series stores resemble, and the paper reports a large reduction in storage versus raw samples. Qualitatively:

  • Timestamps: delta of deltas. Store the difference between successive timestamp differences. For perfectly regular 10-second scraping that difference is zero, which costs one bit. Jitter costs a few bits more; an outage costs a larger code once.
  • Values: XOR with the previous value. If a float equals its predecessor, the XOR is zero and costs one bit. Otherwise XOR the two 64-bit representations: nearby values share leading sign, exponent and high mantissa bits, so the XOR has runs of leading and trailing zeros and only the middle "meaningful" bits are stored, usually reusing the previous window's position.

The script below counts the bits such a scheme would spend on four kinds of series. It is an estimator that follows the published scheme as I understand it, not a codec.

"""Bit-cost estimator for Gorilla-style compression: delta-of-delta timestamps and XOR'd float values.
It counts bits per point following the scheme as published (it does not emit a real bit stream)."""
import struct, random, math

def timestamp_bits(ts):
    bits, prev_delta = 64 + 14, None          # first timestamp raw + first delta (14 bits in the paper)
    for i in range(2, len(ts)):
        dod = (ts[i] - ts[i-1]) - (ts[i-1] - ts[i-2])
        if dod == 0: bits += 1
        elif -63 <= dod <= 64: bits += 2 + 7
        elif -255 <= dod <= 256: bits += 3 + 9
        elif -2047 <= dod <= 2048: bits += 4 + 12
        else: bits += 4 + 32
    return bits

def f2b(x): return struct.unpack(">Q", struct.pack(">d", x))[0]
def value_bits(vals):
    bits, prev, lead, trail = 64, f2b(vals[0]), None, None
    for v in vals[1:]:
        cur = f2b(v); x = cur ^ prev; prev = cur
        if x == 0: bits += 1; continue
        l = min(64 - x.bit_length(), 31); t = (x & -x).bit_length() - 1
        if lead is not None and l >= lead and t >= trail: bits += 2 + (64 - lead - trail)       # reuse previous window
        else: bits += 2 + 5 + 6 + (64 - l - t); lead, trail = l, t                              # new window
    return bits

N = 3600
t0 = 1_700_000_000
regular = [t0 + 10 * i for i in range(N)]
jitter = [t0 + 10 * i + rng.choice([0, 0, 0, 1, -1, 2]) for i in range(N)]
series = {

    "integer counter, +0..9 per step": list(map(float, __import__("itertools").accumulate(rng.randint(0, 9) for _ in range(N)))),
    "slowly varying gauge (cpu 0.xx)": [round(0.40 + 0.05 * math.sin(i / 300) + rng.gauss(0, 0.004), 3) for i in range(N)],
    "noisy float (full precision)": [rng.random() for _ in range(N)],
}
print(f"timestamps, perfectly regular 10 s: {timestamp_bits(regular)/N:5.2f} bits/point")
print(f"timestamps, small jitter:           {timestamp_bits(jitter)/N:5.2f} bits/point")
for name, vals in series.items():
    vb = value_bits(vals); tb = timestamp_bits(regular)
    print(f"{name:<36} values {vb/N:5.1f} bits  total {(vb+tb)/N/8:5.2f} bytes/point  (raw 16 B -> {16/((vb+tb)/N/8):4.1f}x)")

The lessons are in the numbers. A constant gauge costs about a quarter of a byte per point; an integer counter about two bytes. A gauge that merely looks regular to a human (a CPU value rounded to three decimals) still costs about six bytes, because decimal rounding is not binary rounding and the low mantissa bits churn. A full-precision noisy value is barely compressible (2.2 times here). So the single "bytes per point" figure in the estimate is a mix, not a constant: a platform whose series are mostly counters and flat gauges will land near the low end, and one full of noisy floats will not. Measure your own corpus before promising a number, and consider reducing precision at the source for values nobody needs to 15 digits.

Rollups and retention tiers

Nobody needs 10-second resolution from last year, and a year-long chart has maybe 1,000 pixels of width. The compactor therefore writes rollup tiers: every raw series is also summarised per minute and per hour. What you keep per bucket decides what questions you can still answer.

Stored per bucketLets you compute laterCannot recover
Count and sumExact average over any larger window; rate of a counter's totalMin, max, any percentile
Min and maxEnvelope of a gauge; whether a threshold was ever crossedAverage, percentiles
Last valueCounter value at the window end (so rates remain computable)Anything about the inside of the window
A histogram (bucketed counts)Approximate percentiles over any window by adding bucket countsExact values; error bounded by bucket widths
A percentile (p99)Nothing correct when combined with othersAlmost everything: percentiles do not aggregate
 
"""Downsampling: what survives a rollup. Averages and sums can be re-aggregated; percentiles of percentiles cannot."""
import random, statistics
rng = random.Random(11)
# 60 one-second latency samples per minute, 10 minutes; a busy minute has a slow tail.
minutes = []
for m in range(10):
    n = 600 if m == 4 else 60                     # minute 4 is a burst: 10x the traffic
    slow = 0.2 if m == 4 else 0.01
    minutes.append([rng.expovariate(1/20) + (400 if rng.random() < slow else 0) for _ in range(n)])
allv = [x for m in minutes for x in m]
q = lambda xs, p: sorted(xs)[int(p * (len(xs) - 1))]

print(f"true p99 over 10 min:                       {q(allv, .99):7.1f} ms")
print(f"mean of per-minute p99s (a bad rollup):     {statistics.mean(q(m, .99) for m in minutes):7.1f} ms")
print(f"max of per-minute p99s:                     {max(q(m, .99) for m in minutes):7.1f} ms")
# Keep a histogram per minute instead (fixed bucket boundaries), and merge them by adding counts.
bounds = [5, 10, 20, 40, 80, 160, 320, 640, 1280, float("inf")]
def hist(xs):
    h = [0] * len(bounds)
    for x in xs:
        for i, b in enumerate(bounds):
            if x <= b: h[i] += 1; break
    return h
merged = [sum(col) for col in zip(*[hist(m) for m in minutes])]
def hq(h, p):
    target, acc = p * sum(h), 0
    for b, c in zip(bounds, h):
        acc += c
        if acc >= target: return b
est = hq(merged, .99)
print(f"p99 from merged histograms (bucket bound):  {est:7} ms   <- right order of magnitude, bounded error")
sums = [sum(m) for m in minutes]; counts = [len(m) for m in minutes]
print(f"mean from rolled-up sum/count:              {sum(sums)/sum(counts):7.1f} ms   (true mean {statistics.mean(allv):.1f})")
print(f"mean of per-minute means:                   {statistics.mean(statistics.mean(m) for m in minutes):7.1f} ms   (wrong when traffic varies)")
true p99 over 10 min:                         460.5 ms
mean of per-minute p99s (a bad rollup):       117.4 ms
max of per-minute p99s:                       478.3 ms
p99 from merged histograms (bucket bound):      640 ms   <- right order of magnitude, bounded error
mean from rolled-up sum/count:                 60.3 ms   (true mean 60.3)
mean of per-minute means:                      28.7 ms   (wrong when traffic varies)

The last two rows of the table are the trap, shown by the run. The "mean of per-minute p99s" is 117 ms while the true p99 over the ten minutes is 460 ms: averaging percentiles hides the busy minute that carried most of the traffic and the slow tail. Taking the max of the per-minute p99s is closer here but is not the right quantity in general. Merging fixed-boundary histograms (add the counts) gives a bounded-error answer (a bucket bound of 640 ms here, the right order of magnitude), and storing sum and count rolls up the mean exactly, whereas the "mean of means" is wrong when traffic varies (28.7 against the true 60.3). The design consequence: emit histograms, not pre-computed percentiles, so the platform can aggregate them across hosts and across time (metrics), and store sum and count in every rollup bucket.

Tiering ties retention to cost: 15 days at 10 s, 90 days at 1 minute, 2 years at 1 hour, as in the estimate. The query planner picks the tier from the requested step, and falls back to a finer one when a coarser one cannot answer the function (a percentile from a tier without histograms). Deletion is cheap because blocks are immutable and time-bounded: retention expiry deletes whole blocks, never rows.

Deep dive 3: cardinality and multi-tenancy

The number of series is the product of the distinct values of each label. Memory, index size, ingestion cost and query cost all scale with it, which is why it is the central limit of a metrics platform (metrics and cardinality). Use the explorer below: a metric with five bounded labels is a number you can budget; add one unbounded label and it is set by traffic.

"""Cardinality: series = product of distinct label values; a per-tenant limit stops one bad label from eating the head."""
from itertools import product
labels_ok = {"service": 50, "endpoint": 40, "method": 4, "status": 6, "region": 5}
n = 1
for k, v in labels_ok.items(): n *= v
print(f"http_requests_total with labels {list(labels_ok)}: up to {n:,} series per metric")

nb = 1
for v in bad.values(): nb *= v
print(f"add a user_id label (1M values): up to {nb:,} series  ({nb//n:,}x more) -- in practice bounded by combinations seen")
MEM = 4_000   # assumed bytes per active series in memory
print(f"memory at {MEM} B/series: {n*MEM/1e6:,.0f} MB  vs  {min(nb, 5_000_000_000)*MEM/1e12:,.0f} TB (if only 5B combos ever appear)")

class Tenant:
    def __init__(self, limit): self.limit, self.series, self.rejected = limit, set(), 0
    def write(self, name, labels):
        key = (name, tuple(sorted(labels.items())))
        if key in self.series: return True               # existing series: always accepted
        if len(self.series) >= self.limit: self.rejected += 1; return False   # new series over the limit: rejected
        self.series.add(key); return True

t = Tenant(limit=10_000)
ok = 0
for i in range(50_000):                                 # a deploy starts emitting user_id as a label
    ok += t.write("http_requests_total", {"service": "api", "endpoint": "/x", "user_id": str(i)})
t2 = Tenant(limit=10_000)
for i in range(1000): t2.write("up", {"instance": f"i{i}"})
print(f"\nover-limit tenant: accepted {ok:,} new series, rejected {t.rejected:,} writes (existing series still accepted)")
print(f"well-behaved tenant series: {len(t2.series):,} of {t2.limit:,}")

The run shows both halves of the lesson. A metric with five bounded labels is at most 240,000 series. Adding a user_id label with a million values multiplies that by a million: a theoretical upper bound of 240 billion, of which only the combinations that actually occur are created, but "only those that occur" is no comfort if traffic is large. The tenant limit then does what it must: it accepted the first 10,000 new series and rejected 40,000 further writes, while a well-behaved tenant carried on unaffected, and existing series stayed writable, so dashboards for the broken tenant keep working for everything that predates the bad deploy.

Quotas and isolation

Multi-tenancy here means one team's mistake or growth does not degrade others (the general principles are in multi-tenancy and isolation; this is the performance-isolation half). Limits must exist on every resource a tenant can consume, and be enforced early:

Two design points make quotas workable. First, shard isolation: with shuffle sharding each tenant uses a small random subset of ingesters and queriers, so a tenant that crashes its shard hurts only the few others who happen to overlap, not everyone. Second, feedback: a limit nobody can see is a support ticket. Give teams a usage page, per-metric series counts, a top-N cardinality report, and a dry-run mode for new limits. Finally, remember the economics: tenants that can see their cost reduce it.

Deep dive 4: query fan-out

A dashboard panel asks for sum by (service) (rate(http_requests_total[5m])) over the last 30 days at 5-minute resolution. That single request touches series on many ingesters (recent data) and many blocks (older data). The querier tier exists to turn it into many small, parallel, bounded pieces.

  1. Split by time. The query frontend cuts the 30-day range into per-day sub-queries. Each can run on a different querier, and, importantly, each can be cached independently: yesterday's result never changes, so repeated dashboard refreshes only compute the newest slice.
  2. Shard by series. Within a sub-query, the matched series are divided into groups (by series hash), each aggregated partially in parallel, and the partial aggregates merged at the end. Aggregations like sum, count, min, max merge trivially; an average needs sum and count; percentiles over histograms need the bucket counts added first.
  3. Choose the tier. A 30-day range at a 5-minute step reads 1-minute rollups, not raw data: the planner prefers the coarsest tier that still answers the function.
  4. Prune with the index. Postings lists and block time ranges rule out most blocks before any chunk is read. A bloom filter or a small per-block summary of label names speeds this up further.
  5. Bound everything. Maximum series, samples, bytes and wall time per query, and per-tenant concurrency. One analyst's accidental {__name__=~".+"} must be rejected, not run.

Fan-out multiplies tail latency, as the estimate computed: with 100 shards, 63% of queries wait for at least one shard that is in its own slowest percentile (tail latency). The standard remedies apply: a per-shard deadline with hedged requests to a replica, returning a partial result with a warning rather than failing, and caching so most dashboard refreshes compute only a small suffix. Prioritise within the cluster: alert-rule evaluation reads through its own protected path with its own queue (an outage that overloads dashboards must not blind the alerts), then dashboards, then exploratory queries. This is classical overload management applied to queries.

Deep dive 5: logs, and what to index

Logs are typically orders of magnitude larger than the metrics derived from them (in this chapter's assumptions, 20 TB/day against well under 1 TB/day of compressed metrics), so the indexing decision dominates cost. There are two ends of a spectrum.

Full-text index (every token)Label-only index (Loki-style)
Index contentsAn inverted index from each word to the lines containing itOnly stream labels and chunk time ranges; line text is stored as compressed chunks
Index sizeCan be a substantial fraction of the raw text, and grows with distinct tokensTiny; grows with number of streams and time, not with words
Ingest costHigh: tokenising and updating postings for every lineLow: compress and append
Query: "find this rare word anywhere"FastSlow without good labels: scans all chunks in the time range
Query: "errors from service X in the last hour"FastFast: labels and time select a small set of chunks, then scan them in parallel

"""Log indexing: full-text inverted index vs a label-only index with chunk scanning (the idea behind Loki-style stores)."""
import random, collections
rng = random.Random(9)
services = [f"svc{i}" for i in range(20)]
words = [f"w{i}" for i in range(3000)] + ["error", "timeout", "retry"] * 40     # make the interesting words common enough to see
lines = []                                                                     # (service, hour, text)
for i in range(60_000):
    lines.append((rng.choice(services), i // 2500, " ".join(rng.choice(words) for _ in range(12))))   # 24 'hours'

# 1) full-text: token -> set of line ids
full = collections.defaultdict(set)
for i, (_, _, text) in enumerate(lines):
    for w in set(text.split()): full[w].add(i)
postings = sum(len(v) for v in full.values())

# 2) label-only: the index maps (service, hour) -> chunk of lines; the text is just compressed chunks, scanned at query time
chunks = collections.defaultdict(list)
for i, (s, h, t) in enumerate(lines): chunks[(s, h)].append(i)
print(f"60,000 lines, {sum(len(t) for _, _, t in lines)/1e6:.1f} MB raw text, 20 services x 24 hours")
print(f"full-text index:  {postings:,} postings (~{postings*4/1e6:.1f} MB at 4 B each); grows with every line and distinct word")
print(f"label-only index: {len(chunks):,} entries; grows with series x time, not with words")

want, hours = "svc3", range(20, 24)                                              # last 4 hours of one service
full_hits = [i for i in full["timeout"] if lines[i][0] == want and lines[i][1] in hours]
scan = [i for h in hours for i in chunks[(want, h)]]
scan_hits = [i for i in scan if "timeout" in lines[i][2].split()]
print(f"\nquery: service=svc3, last 4 hours, line contains 'timeout'")
print(f"  full-text: {len(full_hits)} matches; read a postings list of {len(full['timeout']):,} line ids and filtered it")
print(f"  label-only: {len(scan_hits)} matches; scanned {len(scan):,} lines ({len(scan)/len(lines):.1%} of the data) selected by labels and time")
print(f"  a query with no useful labels (just 'timeout') would scan all {len(lines):,} lines")

full-text index:  716,865 postings (~2.9 MB at 4 B each); grows with every line and distinct word
label-only index: 480 entries; grows with series x time, not with words

  label-only: 73 matches; scanned 483 lines (0.8% of the data) selected by labels and time

The run makes the cost difference concrete on a toy corpus: the full-text index holds about 717,000 postings for 60,000 lines (and grows with every distinct word), while the label index has 480 entries because it indexes only (service, hour). For a query that names a service and a recent time window, the label-only approach reads under 1% of the data; a query with no useful labels would read all of it. That is the honest trade: you pay at query time what you saved at ingest time, and it works because incident queries nearly always start from labels (which service, which environment, which hour).

Operationally, keep label sets small and bounded for the same reason metrics do (a label with unbounded values creates a stream per value, each with tiny chunks), parse structured fields at query time rather than promoting them to labels, and extract what you will alert on into real metrics (a counter of error lines) so alerting never depends on scanning text. For compliance sources that must be searchable for years, send a copy to cheap object storage with a coarse index and accept slow queries. Retention, deletion on request and redaction of secrets in log lines belong in the pipeline, not in the query layer (logs and events).

Who monitors the monitor

The platform that detects outages must not share their fate. Concretely:

  • A second, smaller stack in a separate failure domain (another region or at least another cluster, with its own storage and no dependency on the primary) scrapes the platform's own health metrics and evaluates a short list of platform-critical alerts. Nothing about it should depend on the thing it watches.
  • A dead-man's switch. One alert on the main platform is always firing, and the meta-monitor expects to receive it constantly. If the heartbeat stops, either the alerting pipeline or the platform is broken, and the meta-monitor pages. This detects the failure that otherwise produces only silence.
  • Synthetic canaries. Write a known series every 10 seconds and query it back; the lag between write and read is the real end-to-end freshness SLI, measured through the whole path. Do the same for logs.
  • Paging must not depend on the pipeline it reports about. The path from alert to phone should use a different route from the data path, or at least have a fallback, as in alerting and on-call.
  • Degrade by priority. Under overload, drop in this order: exploratory queries, dashboards, low-priority tenants' debug logs, high-resolution data. Keep alert evaluation and the data feeding critical alerts last. Say this order aloud in the interview; it is a design decision, not an accident.

SLOs. Ingest availability 99.95% (a 429 from a tenant over its quota is not a failure; a 5xx is); freshness: 99% of points queryable within 15 s of emit, measured by canaries; query latency p99 under 2 s for the last six hours; no silent loss, verified by reconciliation. Alert on log consumer lag, ingestion rejection rates by reason, active series growth per tenant, compaction backlog, canary freshness and the dead-man's switch (burn-rate alerting). Roll out by cell or tenant ring, canarying new ingesters on a small tenant set and comparing canary freshness and rejection rates before widening (deployments).

Trade-offs & alternatives

  • Resolution versus cost. 10-second raw data is affordable for two weeks. Moving to 1-second resolution multiplies the pipeline and storage tenfold; keep it for a few critical series.
  • Exact versus approximate. Histograms and rollups trade exactness for aggregation. If you need exact per-request values, you want logs or traces, not metrics.
  • Log in the middle versus direct writes. Durability and restarts against latency and moving parts, as in Deep dive 1.
  • Own the platform versus buy. A vendor removes the operational burden and charges per series or per byte; at large scale, cost and control argue for building, and at small scale, almost nothing argues for it. Present it as a cost model, not an ideology.
  • If tenants were external customers, authentication, billing accuracy, stricter isolation (including encryption and per-tenant keys) and per-tenant SLAs all become first-class.
  • If we needed arbitrary ad hoc analytics over telemetry, export to a columnar store (column stores) rather than stretching the time-series path.
  • Where it breaks down. Truly unbounded dimensions (per-user metrics), very long retention at fine resolution, and queries that need joins across metrics and logs. Each is pushed to a different tool, not forced through this one.

What a strong answer adds

  • Separates metrics, logs and traces by data shape and by index strategy, and designs the shared pipeline once.
  • Sizes ingestion in points per second and notes that active series (memory) and cardinality are the real limits, not throughput.
  • Explains time-series compression in terms of regularity (delta-of-delta, XOR) and warns that compression ratios depend on the data.
  • Knows percentiles do not aggregate, stores histograms plus sum and count in rollups, and picks tiers from the query's step.
  • Puts quotas where cost is incurred (distributor, ingester, query frontend), isolates tenants by shuffle sharding, and gives users visibility into their usage.
  • Treats query fan-out as a tail-latency problem: splits, caches, hedges, bounds and prioritises alert queries.
  • Chooses label-only log indexing for volume and names the trade (query-time scan), and extracts alert signals into metrics.
  • Answers "who monitors the monitor" with a separate stack, a dead-man's switch, canaries and a stated degradation order.

Follow-up questions

How would you support exact counters for billing on this platform?

You would not use the metrics path: it accepts dropped and late data by design. Billing needs an event stream with exactly-once semantics or reconciliation: write usage events to a durable log with unique ids, aggregate them with idempotent processing, and reconcile against an independent count. Metrics can then be used as a cross-check, not as the source of truth. (The ad-click aggregator studio takes this further.)

An engineer adds a label with the request URL. What happens and how do you protect against it?

Series explode as each distinct URL (including query strings) becomes a series. The tenant's active-series limit stops new series at the cap and reports which metric and label caused it; the cardinality report ranks labels by distinct values so the cause is found in minutes. Prevent it earlier with a label allow-list in the SDK, URL templating (/users/:id), and a pre-merge lint that flags unbounded labels. Move per-URL detail to logs or traces.

How would you make alerts reliable if the query path is overloaded?

Evaluate rules on a dedicated tier that reads from its own replicas or a recent-data cache, with its own queue and concurrency limits and priority over interactive queries. Alert on the evaluator's own freshness. For the most critical alerts, evaluate in the ingester or at the stream-processing layer on incoming data, so they do not depend on the query path at all.

How do you backfill historical data without hurting live ingestion?

Use a separate path that writes finished blocks directly to object storage (the same immutable format) after validation, rather than pushing old samples through the live head. Rate-limit the block upload and have the compactor merge them in low-priority windows. This avoids the out-of-order window entirely.

How would you reduce the cost of logs by an order of magnitude?

Drop at the source (sampling debug logs, removing noisy lines), convert repetitive lines into metrics, compress with a stronger codec for older data, keep a short hot retention and a long cheap one, and keep the index label-only. Give teams their bill per stream so they act on it. Cost reduction is mostly a product question: which logs would anyone actually read?

How do you handle a region outage?

Each region runs its own full stack, so local services keep emitting and alerting locally. Cross-region views are built by a global query layer that fans out to regional stacks and tolerates a missing region with an explicit partial-result warning. The meta-monitor runs elsewhere and alerts when a region's canary goes quiet (multi-region).

Distributed systems connection

The platform is partitioned state plus a replicated log: series are hashed to ingesters (partitioning), the log gives durability and replay (logs and exactly-once), blocks are immutable and merged in the background in the manner of an LSM tree, and query fan-out is the tail-at-scale problem. The shuffle-sharded tenant isolation and the priority-based degradation are straight from resilience.

Key takeaways

  • Metrics and logs share an ingestion shape (agents, distributors, a buffer log, ingesters, immutable blocks) and differ in how they are indexed and queried.
  • Memory is set by active series; series are the product of label values, so cardinality, not throughput, is the limit that bites.
  • Time-series compress well because they are regular: delta-of-delta timestamps and XOR'd values (as in the Gorilla paper). The ratio is data-dependent, so measure it.
  • Percentiles do not aggregate. Emit histograms, store sum and count, and choose rollup tiers by the question you must still answer.
  • Enforce per-tenant limits early (rate, series, query cost), isolate by shuffle sharding, and give users visibility into their own usage.
  • Query fan-out is a tail-latency problem: split by time, shard by series, cache, hedge, bound, and protect the alert path.
  • Label-only log indexing makes volume affordable and shifts the cost to query time; incident queries start from labels, so it works.
  • Monitor the monitor with a separate stack, a dead-man's switch and canary series, and decide in advance what you drop first under overload.

Check your understanding

A team adds a user_id label to a request counter. What is the main resource at risk and why?

  1. Network bandwidth, because every request is now larger
  2. Ingester memory and the index, because the number of series is the product of label values and each series has fixed overhead
  3. Query latency only, because storage is cheap
  4. Nothing, as long as compression is on
Each distinct label combination is a new series with its own index entry and open chunk. Compression helps points, not the per-series overhead, so memory scales with series count.

You store per-minute p99 latency values and later need the p99 over an hour. What is the correct approach?

  1. Average the 60 per-minute p99 values
  2. Take the median of the 60 values
  3. Take the maximum and call it the hourly p99
  4. You cannot compute it correctly from p99s; you should have stored histograms (bucket counts) and added them
Percentiles are not additive. Histograms with fixed bucket boundaries merge by adding counts and give a bounded-error percentile for any window or any set of hosts.

Why put a replicated buffer log between distributors and ingesters?

  1. It makes ingestion durable independent of ingester restarts, absorbs bursts, and lets ingesters replay from an offset
  2. It makes queries faster
  3. It removes the need for compression
  4. It guarantees no data is ever dropped
The log decouples producers from stateful consumers. It costs an extra tier and some latency; it does not remove the need for limits, and data can still be rejected at the distributor.

When is a label-only log index a poor fit?

  1. When logs are very large
  2. When queries start from a known service and time window
  3. When users mostly search for a rare word across everything with no labels, since that scans all chunks in the range
  4. When retention is short
Label-only indexes make ingest cheap and incident queries (labels plus time) fast. Unlabelled needle-in-a-haystack text search is exactly what a full-text index is for.

What does a dead-man's switch alert do?

  1. Pages when CPU is high
  2. Fires constantly so that its absence at an independent watcher signals the alerting pipeline or platform has failed
  3. Deletes old data
  4. Throttles noisy tenants
A broken alerting pipeline produces silence, which looks like health. An always-firing alert watched from outside turns silence into a signal.

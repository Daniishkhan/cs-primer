Design Search & Typeahead

Inverted indexes at scale, tries and prefix caches, ranking and freshness. Two problems that look alike and are not: typeahead answers a tiny, hot, precomputable question in a few milliseconds from memory, while search answers an open-ended one by combining many shards and ranking in stages.

Why this matters

Search is the textbook case of trading write-time work for read-time speed: you build a structure (a trie, an inverted index) so that questions that would take a scan take a lookup. It is also the clearest example of the tail-latency problem, because a query that must consult every shard is as slow as its slowest one. Typeahead adds the opposite lesson: when the question space is small and skewed, you can precompute the answers and keep them in memory.

The problem

"Design the search experience for a large website: as the user types, suggest completions; when they submit, return ranked results from our corpus of documents."

That is two systems. Typeahead suggests queries (things people have searched) for a prefix, many times per search, in a few milliseconds. Search returns documents for a full query, once per search, with more latency budget and a much bigger data structure. They share a query log and a text-analysis pipeline, and little else. We split them using the framework, and give typeahead the first half and search the second.

  • Suggest is a cacheable GET. The same prefix gives the same answer for everyone (in the base design), so it can sit behind a CDN or edge cache with a short TTL. That one property removes most of the load.
  • partial in search. If a shard misses the deadline, the aggregator returns what it has and says so, rather than failing the whole query (Deep dive 3).
  • Document upserts carry a version. Indexing is at-least-once; the version makes redelivery and reordering harmless (the usual idempotency story, API design).

Data model

  • Query log (append-only stream, then a data lake): (ts, normalised_query, user_hash, locale, selected_suggestion?). Everything in typeahead is derived from it.
  • Query counts (batch-aggregated table): (normalised_query, count_last_7d, count_last_1d, …) with time decay, input to the trie build.
  • Trie snapshot (immutable file in object storage, loaded into memory by every suggest server): nodes keyed by character, each holding its top-k completions. Versioned; the serving fleet atomically swaps to the new snapshot.
  • Trending overlay (small in-memory structure, updated every few seconds from a stream): recent heavy hitters by prefix.
  • Blocklist: a small set of phrases and patterns, replicated to every server and applied at serve time.
  • Inverted index (per shard, built from immutable segments): term dictionary → postings lists (sorted document ids, term frequencies, optionally positions), plus doc values (per-document fields for ranking) and a separate document store for titles and snippets.

The two read-side structures are what the chapter is about; the log and the counts exist only to feed the trie, and the documents only to feed the index. Both read-side structures are derived: any shard or trie can be rebuilt from the sources (specialised stores make the same point about search indexes: they are secondary, rebuildable indexes beside a system of record).

High-level design

The online path is short on purpose. Everything expensive happens offline, and a request touches one in-memory structure. Step through a keystroke:

Step through

One keystroke, "wor"

  1. Keystroke and debounce. The user types "wor". The client waits for a short pause (tens of milliseconds, not hundreds), checks its own cache of prefixes it has already fetched, and only then sends a request tagged with an increasing request number.
  2. Edge cache. Short prefixes are asked millions of times with identical answers, so a CDN or edge cache with a TTL of a minute or so serves them without touching our servers. A miss goes through.
  3. Walk the trie. The suggest service follows one edge per character, three steps, to the node for "wor". That node already stores its best completions, so there is no subtree scan: the cost is proportional to the prefix length, not to the number of matching queries.
  4. Merge trending. A small overlay of the last few minutes' rising queries is checked for matches of the prefix and merged in by score, so a breaking story can surface before the next trie rebuild.
  5. Filter. Suggestions matching the blocklist are removed at serve time, so a new block takes effect without waiting for a rebuild.
  6. Respond. Return the top 8 with the request number echoed and a short Cache-Control. Total server time is on the order of a millisecond or two.
  7. Render or drop. If the user has typed another character since, the reply is for an older prefix: ignore it. Only the answer to the latest input is shown.

Deep dive 1: the typeahead data structure and where it lives

Top-k stored at every node

A plain trie answers "which strings start with this prefix?" but then needs to visit the whole subtree to find the best ones, which for the prefix "a" is millions of nodes. The fix is to precompute the answer at every node: each node stores the top-k completions for its prefix, computed offline from the query counts. A lookup is then a walk of L steps (the prefix length) and a read of k items, independent of corpus size. The price is memory (k entries per node) and rebuild work, both easy to afford offline. This runs on real data below, checked against a brute-force scan.

"""A trie where every node keeps its own top-k completions, built offline from query counts."""
import heapq

class Node:
    __slots__ = ("kids", "top")
    def __init__(self):
        self.kids = {}
        self.top = []                  # up to K (count, query), best first

K = 3

class Trie:
    def __init__(self):
        self.root = Node()

    def build(self, counts):
        """Offline: insert each query, pushing it into the top-k list of every node on its path."""
        for q, n in counts.items():
            node = self.root
            self._offer(node, n, q)
            for ch in q:
                node = node.kids.setdefault(ch, Node())
                self._offer(node, n, q)
        return self

    @staticmethod
    def _offer(node, n, q):
        node.top.append((n, q))
        if len(node.top) > 2 * K:      # amortise: sort-and-trim occasionally, not on every insert
            node.top = heapq.nlargest(K, node.top, key=lambda t: (t[0], t[1]))

    def finish(self):
        stack = [self.root]
        while stack:
            node = stack.pop()
            node.top = heapq.nlargest(K, node.top, key=lambda t: (t[0], t[1]))
            stack.extend(node.kids.values())
        return self

    def suggest(self, prefix):
        """O(len(prefix)) to walk down, then the answer is already stored: no subtree scan."""
        node = self.root
        for ch in prefix:
            node = node.kids.get(ch)
            if node is None:
                return []
        return [q for _, q in node.top]

    def count_nodes(self):
        total, stack = 0, [self.root]
        while stack:
            node = stack.pop(); total += 1; stack.extend(node.kids.values())
        return total

def brute_force(counts, prefix):
    hits = [(n, q) for q, n in counts.items() if q.startswith(prefix)]
    return [q for _, q in heapq.nlargest(K, hits, key=lambda t: (t[0], t[1]))]

counts = {"weather": 900, "weather tomorrow": 400, "web": 700, "webcam": 120, "wedding dress": 300,
          "wells fargo": 650, "wellness": 90, "world cup": 1500, "world cup schedule": 800,
          "wordle": 2000, "word": 60, "wow": 45}
trie = Trie().build(counts).finish()
print(f"{len(counts)} queries -> {trie.count_nodes()} trie nodes, k={K}")
for p in ("w", "we", "wea", "wor", "world c", "x"):
    got = trie.suggest(p)
    assert got == brute_force(counts, p), p
    print(f"  {p!r:<10} -> {got}")

# A trending overlay: a small separate map of fresh counts, merged at query time.
fresh = {"world cup final": 5000, "wordle": 30}
def suggest_with_overlay(prefix, base_counts, fresh_counts, weight=1.0):
    seen = {q: n for q, n in ((q, base_counts.get(q, 0)) for q in trie.suggest(prefix))}
    for q, n in fresh_counts.items():
        if q.startswith(prefix):
            seen[q] = seen.get(q, 0) + weight * n
    return [q for q, _ in sorted(seen.items(), key=lambda t: (-t[1], t[0]))[:K]]
print("\nwith a trending overlay:")
print("  'wor'      ->", suggest_with_overlay("wor", counts, fresh))
print("  'world c'  ->", suggest_with_overlay("world c", counts, fresh))

Serving from memory, replicating and sharding

The napkin gives a trie of about 9 GB for 50 million kept queries. That fits in memory on one ordinary server, and a server can answer tens of thousands of lookups per second, so the load is a replication problem, not a sharding problem: run enough identical replicas for peak traffic and failures, behind a load balancer (load balancers), and give each replica the same snapshot. Loading is simple: the builder writes a versioned snapshot to object storage, each server downloads and maps it, warms it, and swaps it in atomically, keeping the old one until the new is healthy. A rolling swap with a health check makes a bad snapshot a non-event.

Shard by prefix only when the structure outgrows a machine (many languages, personalised tries) or one machine cannot serve a hot range. If you do, shard on the first one or two characters, but note the skew: letters are not equally common as initial letters, so equal alphabet ranges give unequal load. Use ranges chosen from the measured query-log distribution (or hash the first two characters) and let a router map prefix to shard. For the hottest short prefixes, the better fix is not more shards but the edge cache: there are only about twenty thousand prefixes of length three or less, which a cache holds trivially. Hash partitioning of whole queries would break the structure (the completions of a prefix would be scattered across shards), so partitioning for typeahead is always by prefix (partitioning).

Deep dive 2: freshness, filtering, latency budget and the client

Freshness: periodic rebuild plus a trending overlay

Rebuilding the whole trie on every query would be absurd, and rebuilding it daily is too stale: yesterday's trending topic is not today's. Two mechanisms split the job. The periodic rebuild (every few hours, or every fifteen minutes if the batch pipeline allows) recomputes counts over a long window with time decay, so stable, high-volume queries are ranked well. The trending overlay handles the last few minutes: a streaming job counts queries per prefix in short windows, keeps only those growing unusually fast, and publishes a small map to every suggest server. At query time, the server merges overlay candidates for the prefix into the trie's list and re-sorts by a blended score. The overlay is small enough to update every few seconds. How the streaming counts are computed with bounded memory is the subject of chapter 12.

A subtle point: the blend is a product decision. Overweight recency and a short burst of junk can crowd out better suggestions; underweight it and the box looks dead during a news event. Make the weights configuration, expose them in an experiment framework, and keep a minimum count threshold before anything enters the overlay, to resist both noise and manipulation (people can and do script searches to push a phrase into suggestions).

Filtering offensive and removed suggestions

Suggestions are different from search results: nobody asked for them, so the bar for what may appear is much higher. Filter in three places. At build time, drop phrases matching the blocklist and a classifier, so they never enter the trie. At serve time, apply the current blocklist to every response, because a newly reported phrase must disappear in minutes, not at the next rebuild; this is a cheap set lookup per suggestion. And at the edge, remember that cached responses outlive a block: either keep the edge TTL short (a minute) or purge by key for urgent removals. Matching needs normalisation (case, accents, spacing, common substitutions) and a human-reviewed pipeline for additions. For the legal or reputational cases, assume you will get it wrong sometimes and design for fast reversal.

Latency budget per keystroke

Perceived responsiveness is what matters: suggestions feel instant under roughly a tenth of a second from key press to render. Spend that budget deliberately:

StageRough budgetHow it is kept there

Client behaviour is half the design

  • Debounce requests so a burst of typing sends one request, not six. Typical implementations use a delay of tens of milliseconds; tune it against measured typing speed.
  • Cache by prefix on the device. If "wor" was fetched, "wo" (backspace) is already known, and you can often filter a longer cached list locally for the next character.
  • Cancel or ignore stale requests. Responses can return out of order; tag requests with an increasing number, and only render the reply to the latest. This is the same ordering trick as the sequence number in chat.
  • Do not ask below a minimum length (one or two characters), or serve those from a bundled static list.
  • Degrade silently. If suggestions fail, hide the box; search itself still works.

Deep dive 3: the inverted index and how to shard it

The inverted index

A forward index maps document to words; an inverted index maps each term to the sorted list of documents that contain it (its postings list), often with frequencies and positions. A query for "world cup" becomes "find the postings for world and for cup, intersect them" (a merge of two sorted lists, made faster with skip pointers and compression), then score the survivors. The term dictionary is compact and searchable by prefix; postings are stored delta-encoded and bit-packed so that a list of millions of document ids takes a few bytes per entry. The fundamentals and how a search engine is built on a log-structured design are in specialised stores. Before indexing, an analysis chain normalises text (tokenise, lowercase, strip accents, optionally stem or remove stop words); using the same chain on queries and documents is a correctness requirement, and it is the same normalisation the query log uses for typeahead counts.

Document-partitioned or term-partitioned?

Recommendation: document-partitioned, which is what most production engines choose. It makes indexing cheap and local, spreads load evenly, degrades by dropping a slice of documents rather than a slice of vocabulary, and keeps intersections local. Its flaw is the one the napkin warned about, fan-out to every shard, and the remedies for that flaw are standard engineering rather than a different partitioning: replicas, deadlines, hedging, tiering. With 120 shards and two replicas each, QPS is absorbed by choosing the least-loaded replica of each shard per query.

Scatter-gather and the tail

If each shard is slow with probability p (a compaction, a garbage-collection pause, a cold cache), a query that waits for all N is slow with probability 1 − (1 − p)N. That is the 11% and 70% in the estimate: ordinary shard hiccups become common user-visible slowness (tail latency). Mitigations, in order of how much I would reach for them:

  1. A deadline and partial results. The aggregator asks for answers by a time limit (say 300 ms), returns what arrived, and sets partial: true. Missing one shard's slice of a ranked list usually changes results slightly, which is better than a timeout. Record it as an SLI.
  2. Hedged requests. Send the query to a second replica of a shard if the first has not answered by about the 95th percentile of its latency, and use whichever returns first; cap extra load at a few percent.
  3. Pick replicas by load, avoiding the one currently compacting or recovering.
  4. Tiering. Put the highest-quality or most-recent documents in a small first tier queried first; consult the large lower tier only if the first does not produce enough good results.
  5. Early termination. Within a shard, stop scoring when the remaining postings cannot beat the current top-k (dynamic-pruning techniques such as WAND exist for this), so each shard's work is bounded.

Deep dive 4: ranking in stages and keeping the index fresh

Ranking is a funnel

Scoring every matching document with an expensive model is impossible, so ranking runs in stages of increasing cost and decreasing candidate count, the same funnel as the feed (chapter 9):

  1. Retrieval, per shard. Boolean match on the query terms, ranked with a cheap, well-understood text-relevance score (the classic family is TF-IDF and BM25), returning perhaps a thousand candidates per shard together with the doc-value features they need.
  2. Merge, at the aggregator. Combine the shards' lists by score and keep a few hundred.
  3. Re-rank. A heavier model scores these using many signals: text match, document quality and popularity, freshness, the user's language and location, click history for similar queries. This stage is where machine learning lives (chapter 20), and where the cost per candidate is highest, so it sees only tens to hundreds.
  4. Blend and present. Apply diversity (not ten results from one site), policy filters, and any special result types; fetch titles and snippets for the final page from the document store.

Two practical notes. Quality depends as much on query understanding (spell correction, synonyms, intent) as on the scoring formula, and changes to the analysis chain require a reindex. And ranking changes need offline evaluation on judged queries plus online experiments, because the ranker changes behaviour and therefore the data you evaluate on. Pagination of results uses an opaque cursor over a cached candidate list, as in the ranked feed (API design): deep pages are expensive on a scatter-gather system, so most products cap depth.

Keeping the index fresh: near-real-time segments

Rebuilding a shard on every document change would be unbearably slow, and mutating a compressed postings structure in place is slow and fragile. Search engines in the Lucene family solve both with immutable segments, the same idea as the LSM tree (LSM trees):

  • New documents go into an in-memory buffer and a durable write-ahead log.
  • Periodically (about every second, a tunable) the buffer is written as a small new segment that becomes searchable. That "refresh" is why updates are near-real-time: visible in about a second, not instantly.
  • Searches read all segments and merge results; a delete is a mark in a per-segment bitset, so the document stops matching once the next refresh makes the mark visible, but its space is reclaimed later.
  • A background process merges small segments into bigger ones to keep the segment count and read cost bounded, rewriting data without the deleted documents. This costs I/O, so it is throttled; falling behind on merging is the search equivalent of compaction debt.

An update is a delete plus an insert of a new version, which is why a document that changes constantly (a counter, a price) is a poor fit for the index itself; keep fast-changing fields in doc values or in a separate store joined at rank time. For the feed into the index, the usual pipeline is a change stream from the system of record into the indexer (streams and CDC), partitioned so each document's updates stay ordered, with the document version making redelivery harmless. Rebuilding is also first-class: a full reindex into a new set of shards, then an atomic alias switch, is how you change the schema or analysis chain safely.

Alert on those with burn rates (alerting), plus snapshot age, partial rate, segment count and merge backlog. Roll out new snapshots and ranker versions by canary and experiment (deployments).

Trade-offs & alternatives

  • Precompute versus compute on demand. Top-k per node trades memory and rebuild lag for a flat lookup cost. If the corpus of queries were tiny, a scan would do; if freshness had to be seconds, you would compute from streaming counts more aggressively and accept more cost.
  • Global versus personalised suggestions. A global trie is cacheable at the edge. Per-user suggestions defeat the cache and need per-user state, so the usual compromise blends a global list with a small personal one on the client or a thin service.
  • Document versus term partitioning. We took the one with even load and local intersections, and pay in fan-out. If queries were nearly always single-term and the corpus static, term partitioning would look better.
  • Freshness versus indexing cost. Shorter refresh intervals make documents findable sooner, produce more small segments and more merge work. One second is a tunable default, not a law.
  • Search engine or build it? Almost always use an existing engine (Lucene-based or similar) and spend the design effort on shard layout, ranking and operations. Building an inverted index is an exercise; operating one is the job.
  • Where it breaks down. Manipulated suggestions and query-of-death queries need active defences; very long-tail languages need their own analysis; and semantic (embedding) search is a different retrieval method that complements, not replaces, the inverted index (chapter 20).

What a strong answer adds

  • Separates the two problems at the start and says what each optimises: typeahead for tiny latency from memory, search for recall and ranking across shards.
  • Precomputes top-k at every trie node and explains why a subtree scan is unacceptable for short prefixes.
  • Sizes the trie and concludes "replicate, do not shard" for the base case, then names prefix sharding with skew-aware ranges for when it is needed.
  • Splits freshness into a slow rebuild plus a fast trending overlay, and filters offensive suggestions at build time, at serve time and at the edge.
  • Counts the latency budget per keystroke and puts debouncing, prefix caching and stale-reply dropping on the client.
  • Chooses document partitioning with reasons, computes the fan-out tail from N and p, and names deadlines, hedging and tiering.
  • Describes ranking as a funnel with a cheap first stage and a re-ranker, and near-real-time indexing as immutable segments with background merges.
  • Treats indexes and tries as derived, rebuildable data with versioned snapshots and aliases for safe change.

Follow-up questions

How would you support typo-tolerant suggestions?

Add a candidate-expansion step: if the exact prefix yields few results, also look up prefixes within edit distance one or two (using a Levenshtein automaton walk over the trie, or an index of character n-grams), and score the corrected candidates lower. It multiplies work per request, so apply it only when the exact prefix is sparse, and cache aggressively. Spelling correction for full search queries is a separate offline-trained model fed by the same query log.

How do you personalise suggestions without breaking the edge cache?

Keep the cacheable global list as the base, and blend a small per-user list (recent searches, stored on the device or in a fast per-user store) on the client or in a thin edge function. The shared, expensive part stays cached; the personal part is small and cheap. Beware privacy: personal history must not leak into shared caches.

Why not just query the search index for each keystroke?

A search over the full index costs milliseconds to tens of milliseconds across many shards, at four to five times the search rate. Typeahead can instead answer from a precomputed structure in one machine's memory at microsecond cost, and from a cache most of the time. It also suggests queries, not documents, so a query-log structure is the correct data, not the document index.

A hot query makes one shard slow for everyone. What do you do?

Under document partitioning every shard sees every query, so one hot query is load on all of them, not on one. Cache the query's results at the aggregator for a short TTL with request coalescing, so a thousand identical concurrent queries cost one fan-out. If one shard is slow for a particular query (for example a very common term with a giant postings list), apply early termination and per-shard cost limits.

How would you delete a document everywhere promptly (legal takedown)?

Delete in the system of record, publish the delete to the indexers (applied as a segment bitset mark, so the document stops matching at the next refresh), purge it from the document store, and apply a serve-time exclusion list at the aggregator for the interval between the delete and the refresh. Verify with a probe query. Cached results at the edge need a purge as well.

How would you evaluate whether a ranking change is better?

Offline: judged query sets with metrics such as normalised discounted cumulative gain, plus counterfactual replay of logs. Online: an A/B experiment on a slice of traffic with success metrics (clicks, successful sessions, reformulation rate) and guardrails (latency, abandonment). Offline results screen candidates; online results decide.

Distributed systems connection

Scatter-gather search is the textbook victim of tail amplification, and the remedies (deadlines, hedged requests, tiering) are those of tail latency. Segment-based indexing is an LSM tree with a different read path, and the index as a derived view maintained from a log is the change-data-capture pattern (streams and CDC). Partitioning by prefix is range partitioning with the usual hot-range problem (sharding).

Key takeaways

  • Typeahead and search are different problems: precomputed in-memory lookups for suggestions, sharded indexes and staged ranking for results.
  • Store the top-k completions at every trie node so a lookup costs the prefix length, not the subtree; build offline from query logs and ship versioned snapshots.
  • The trie is small enough to replicate; shard by prefix only when needed, using ranges that account for skew, and cache short prefixes at the edge.
  • Keep suggestions fresh with periodic rebuilds plus a small trending overlay, and filter offensive ones at build time, serve time and the edge.
  • Budget latency per keystroke and let the client debounce, cache by prefix and drop stale replies.
  • An inverted index maps terms to sorted postings; partition it by document, accept the all-shard fan-out, and fight the tail with deadlines, hedging and tiering.
  • Rank in stages (cheap retrieval, merge, heavier re-rank, blend) and keep the index near-real-time with immutable segments and background merges.

Check your understanding

Why store the top-k completions at every trie node instead of scanning the subtree at query time?

  1. It uses less memory
  2. Subtree scans are not possible in a trie
  3. A lookup then costs only the prefix length and k, regardless of how many queries share that prefix
  4. It removes the need for query logs
Short prefixes have enormous subtrees, exactly where traffic is highest. Precomputing the answer per node trades memory and offline work for a flat, tiny lookup.

A new trending query must appear in suggestions within minutes but the trie rebuilds every few hours. What is the usual solution?

  1. A small streaming-updated trending overlay merged with the trie's results at query time
  2. Rebuild the whole trie for every query
  3. Disable the trie during news events
  4. Shard the trie by day
The overlay handles the recent window cheaply; the periodic rebuild handles stable, high-volume queries. Together they give freshness without constant rebuilds.

In a document-partitioned index of 120 shards, each shard call is slow 1% of the time. Roughly how often is a query slow if it waits for all shards?

  1. About 1%
  2. About 10%
  3. About 30%
  4. About 70%
1 − 0.99^120 is about 0.70. Fan-out turns a rare per-shard hiccup into the common case, which is why deadlines, hedging and tiering exist.

Why do search engines usually choose document partitioning over term partitioning?

  1. It avoids fan-out to shards
  2. Indexing is local to one shard, load spreads evenly, intersections are local, and a lost shard degrades results instead of removing vocabulary
  3. It makes ranking unnecessary
  4. It needs less storage
The drawback is the all-shard query, handled with replicas, deadlines and hedging. Term partitioning has hot terms and expensive cross-shard intersections.

What makes a newly indexed document searchable "near-real-time" rather than instantly?

  1. It must wait for the nightly rebuild
  2. Documents are only searchable after replication to three regions
  3. New documents are buffered and written as a new immutable segment at a periodic refresh (about a second), after which searches see them
  4. The inverted index is read-only
Immutable segments avoid in-place edits of compressed structures. A refresh publishes the buffer as a segment, and background merges bound the segment count.

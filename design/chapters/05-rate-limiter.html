Design a Rate Limiter

Token buckets and sliding windows, local versus global limits, and failing open or closed. A rate limiter looks like a counter; designing it well means choosing an algorithm from a number, keeping shared state correct under concurrency, and deciding in advance what happens when the limiter itself breaks.

Why this matters

A rate limiter looks like a counter and turns out to be a small distributed system: shared state on the hot path of every request, a correctness question (what does "per minute" even mean?), and a failure question (what happens to all traffic when the limiter is sick?). It is the cleanest place to practise the whole method, because every choice, from algorithm to fail-open policy, falls out of two or three numbers. It is also a block that appears inside almost every other design in this course.

The problem

"Design a rate limiter for our public API platform. We have a few thousand customers and many millions of end users. A noisy customer should not be able to hurt the others, and we want to stop abuse."

It is deliberately loose. "Rate limiter" could mean a library inside one service, a gateway feature, a CDN rule or a whole platform. "Per" what: user, IP, key, customer? "Hurt the others" suggests fairness and overload protection, while "stop abuse" suggests security. The first job is to turn those into requirements, following the framework.

Clarify requirements

QuestionAssumed answer
What are we limiting, and for whom?Requests to the HTTP API, by authenticated user, API key and tenant, plus anonymous traffic by IP.
Hard quota or best effort?Best effort fairness and protection, not billing. A few percent over the limit is acceptable; a 10x overrun is not. (Metered billing is a different system.)
Bursts?Yes. Real clients are bursty; allow a short burst above the average rate.
Added latency?Negligible: a p99 budget of about 2 ms for the check.
Where are we deployed?One gateway fleet per region, three regions, a global account quota for some plans.
If the limiter breaks?The API must stay up. We will decide per endpoint below.

Functional. Define rules (limit, window, burst, key dimension, per route or plan); enforce them on every request; tell clients where they stand; let operators change limits without a deploy.

Non-functional. About 170k checks per second at peak (derived next); p99 check under 2 ms; accuracy within roughly 10% of the configured rate; the limiter must not reduce the availability of the API (see availability maths: a hard dependency on the hot path multiplies in its availability).

Out of scope. Billing-grade metering, bot detection and DDoS mitigation proper (the edge product's job), per-request cost models beyond a simple integer cost, and client-side limiting libraries beyond a mention.

Estimate

The numbers decide three things: how many store shards, how much memory, and whether the algorithm's per-key state matters. All figures are assumptions in the script; change them and re-run. The method is the one from chapter 2.

Reading the output: 174k checks/s at peak is far past one in-memory node (roughly 100k simple ops/s) so the store is sharded, at least four shards with headroom, each with a replica for failover. Ten million active keys fit in a gigabyte or so for counter-style algorithms, but the sliding log costs about 13 times more per key, which is why it is rarely used at this scale. And the sync estimate shows that periodic synchronisation is only safe when the offered load is close to the limit; against a heavy abuser it overshoots badly, so abusive keys need a stricter mechanism. (That last block is a rough upper-bound model, not a measurement.)

API

There are two surfaces: the one the caller sees, and an internal one.

-- What an API client sees (any endpoint):
HTTP/1.1 200 OK
RateLimit-Policy: "default";q=100;w=60
RateLimit: "default";r=37;t=21

HTTP/1.1 429 Too Many Requests
Retry-After: 21
RateLimit: "default";r=0;t=21

-- Internal: the check, called by the gateway middleware (library call or gRPC)
Check(keys: [string], cost: int = 1) -> { allowed: bool, remaining: int, reset_ms: int, retry_after_ms: int }

-- Admin: policies are data, not code
PUT /admin/policies/{id}  { match: {route, plan}, dimension: "api_key", algo: "token_bucket", rate: 100, per: "60s", burst: 20 }

Response headers: what is standard and what is not

HeaderStatusUse
429 Too Many RequestsStandard (RFC 6585)The status for "slow down"; use it rather than 503 so clients and caches can tell the cases apart.
Retry-AfterStandard (HTTP Semantics, RFC 9110): a number of seconds or an HTTP dateTells a well-behaved client when to try again. Compute it from the bucket; add jitter so a crowd does not return in the same instant.

Older drafts used RateLimit-Limit/-Remaining/-Reset without the X- prefix, and the current draft dropped them for the structured form above.

My opinion: ship Retry-After on every 429 because it is standard and clients act on it, and publish the remaining-quota headers in whichever style your existing clients already parse; migrate when the draft becomes an RFC. Also document that clients should use the headers for pacing, not as a promise: under the approximate algorithms below, the number is an estimate.

Data model

  • Policy (source of truth, a small relational or config table, thousands of rows): (id, match{route, plan}, dimension, algo, rate, per, burst, mode). Pushed to gateways and cached; changes take effect within seconds.
  • Counter state (derived, disposable, in the in-memory store): key rl:{policy}:{dimension-value}, value = the algorithm's state (for the token bucket: tokens and last_refill), with a TTL slightly longer than the time to refill completely, so idle keys evict themselves.
  • Partition key: the full limiter key. It is high-cardinality, so load spreads evenly across shards by consistent hashing; the exceptions are hot keys, treated below.

Counter state is a cache in the sense of chapter 3: if it is lost, buckets restart full and clients get a brief free burst. That is a safe, bounded failure, and it is why we do not need durable storage for it.

High-level design

The limiter is a library in the gateway, backed by a sharded in-memory store. Policy changes flow from the policy store into every gateway's local cache. A request takes one extra hop, to one shard, chosen by hashing the key. Step through it:

Step through

One request through the limiter

  1. Identify. The gateway authenticates the request and builds the limiter keys from it: here the user u42, plus the API key and IP address if those have their own limits.
  2. Policy. It reads the limits that apply from a local cache of the policy store, for example 100 requests per minute with a burst of 20. This never touches the network on the hot path.
  3. Check. It sends one atomic script call to the store shard that owns hash(key), with the policy and a cost of 1.
  4. Decide. The script refills the bucket from elapsed time, subtracts the cost if enough tokens remain, and returns the verdict with the tokens left and the time until reset.
  5. Allowed. The request goes on to the backend, and the response carries the remaining-quota headers so well-behaved clients can pace themselves.
  6. Denied. The gateway answers 429 with a Retry-After value computed from the bucket. The backend never sees the request, which is the point.
  7. Store trouble. If the call times out, the gateway must follow the pre-agreed rule. Here it fails open for ordinary traffic (and would fail closed for a login endpoint); either way it counts the event and alerts.

The read path and write path are the same here: every request is both a read and a write of its counter, which is why the store must be fast and why we make the operation a single atomic call.

Deep dive 1: where to limit, and by what key

Limits are layered, not alternatives. The edge is the cheapest place to say no, so give it the coarse, identity-free rules (per IP, per network, abusive paths). The gateway is where identity is known, so per-user, per-key and per-tenant quotas live there. Individual services add limits that only they can compute, such as concurrency on an expensive endpoint (an in-flight cap protects a dependency better than a rate, because a slow dependency makes any fixed rate too high; see overload). Clients self-throttle if you give them the headers, but never trust it.

Multi-dimensional keys

DimensionProtects againstWeakness
IP addressUnauthenticated floods, credential stuffing at the front doorNAT and mobile carriers put thousands of users behind one IP (false positives); attackers rotate IPs (false negatives).
User idOne account hammering the APIOnly works after authentication; attackers can create many accounts.
API keyOne integration or app misbehavingKeys leak and are shared; one key may serve many users.
Tenant / customerOne customer starving the others (the noisy neighbour)Needs a plan hierarchy; sub-limits to prevent one user consuming the whole tenant quota.
Route / costExpensive endpoints (search, export)Needs per-route policy or a cost weight; more rules to maintain.

Real policies combine dimensions: every request is checked against several keys (say per-user, per-key and per-tenant) and is admitted only if all pass. Check the cheapest and most likely to fail first, and do not charge the other buckets for a request that a later one rejects, or you penalise clients twice. This is also the multi-tenancy question: fairness between tenants (see multi-tenancy) is a limiter policy before it is an isolation architecture.

Deep dive 2: the algorithms

Five algorithms cover almost every limiter you will meet. Run them yourself on the same traffic before reading the comparison; the interesting column is peak in any 1 s.

The same comparison as code, with the traffic from the widget's first preset (limit 10 per second), so you can check the widget against it. The leaky bucket here is the queue variant: it admits the same requests as the token bucket, but a request can wait up to about a second.

"""Five rate-limit algorithms fed the same bursty trace. Limit: 10 requests per second."""
from collections import deque

def trace():
    t = []
    t += list(range(0, 10000, 150))            # steady ~6.7 req/s
    t += [2000 + 10 * i for i in range(30)]     # burst A: 30 requests in 290 ms
    t += [4900 + 10 * i for i in range(20)]     # burst B: straddles the 5.0 s window edge
    t += [7000 + 10 * i for i in range(40)]     # burst C: 40 requests in 390 ms
    return sorted(t)

L, W = 10, 1000   # limit per window (ms)

def token_bucket(ts):
    tokens, last, out = float(L), 0, []
    for t in ts:
        tokens = min(L, tokens + (t - last) * L / W); last = t
        ok = tokens >= 1
        if ok: tokens -= 1
        out.append(ok)
    return out

def leaky_queue(ts):                  # leaky bucket as a queue: accept if queue not full, drain 10/s
    level, last, out = 0.0, 0, []
    for t in ts:
        level = max(0.0, level - (t - last) * L / W); last = t
        ok = level + 1 <= L
        if ok: level += 1
        out.append(ok)
    return out

def fixed_window(ts):
    cnt, win, out = 0, 0, []
    for t in ts:
        if t // W != win: win, cnt = t // W, 0
        ok = cnt < L
        if ok: cnt += 1
        out.append(ok)
    return out

def sliding_log(ts):
    log, out = deque(), []
    for t in ts:
        while log and log[0] <= t - W: log.popleft()
        ok = len(log) < L
        if ok: log.append(t)
        out.append(ok)
    return out

def sliding_counter(ts):
    win, cur, prev, out = 0, 0, 0, []
    for t in ts:
        w = t // W
        if w != win:
            prev = cur if w == win + 1 else 0
            win, cur = w, 0
        est = prev * (1 - (t % W) / W) + cur
        ok = est < L
        if ok: cur += 1
        out.append(ok)
    return out

def peak_in_any_window(ts, ok):
    adm = [t for t, o in zip(ts, ok) if o]
    best, j = 0, 0
    for i, t in enumerate(adm):
        while adm[j] <= t - W: j += 1
        best = max(best, i - j + 1)
    return best

ts = trace()
print(f"{len(ts)} requests over 10 s; limit {L}/s")
print(f"{'algorithm':<22}{'admitted':>9}{'rejected':>9}{'peak in any 1 s':>17}")
for name, f in [("token bucket", token_bucket), ("leaky bucket (queue)", leaky_queue),
                ("fixed window", fixed_window), ("sliding log", sliding_log),
                ("sliding window counter", sliding_counter)]:
    ok = f(ts)
    print(f"{name:<22}{sum(ok):>9}{len(ok)-sum(ok):>9}{peak_in_any_window(ts, ok):>17}")

# how long does a request wait in the leaky-bucket queue? (level / drain rate)
level, last, worst = 0.0, 0, 0.0
for t in ts:
    level = max(0.0, level - (t - last) * L / W); last = t
    if level + 1 <= L:
        level += 1
        worst = max(worst, level / L * W)
print(f"leaky bucket worst queueing delay: {worst:.0f} ms (the token bucket admits the same requests with no wait)")

Notice what the numbers say. The fixed window let 19 requests through in some one-second span against a limit of 10, because bursts B straddled a window boundary. My default

Token bucket for per-key API limits (state is tiny, bursts are explicit, refill maths is one line), sliding window counter when a clean "N per window" semantic is contractual, and sliding log only for small security limits. Fixed window only where a boundary double-burst cannot hurt you. This is an opinion; the widget lets you test it against your own traffic shape.

Deep dive 3: distributed state

Option A: a shared store with atomic scripts

Every gateway asks the same store. The check is a read-modify-write, so it must be atomic: otherwise concurrent gateways read the same count and all admit. The store executes a small script as one indivisible step; Redis-style stores do this with server-side scripts (single-threaded execution means no interleaving). The script below is a sketch of the token bucket from the algorithm table.

"""Why the check must be one atomic step: 50 gateways race for the last 5 slots of a limit of 10."""
LIMIT, GATEWAYS = 10, 50

def check_then_set():
    """Naive GET, compare, SET. All gateways read before any of them writes (worst-case interleaving)."""
    store = {"count": LIMIT - 5}
    reads = [store["count"] for _ in range(GATEWAYS)]            # step 1: everyone GETs
    admitted = 0
    for seen in reads:                                            # step 2: everyone decides and SETs
        if seen < LIMIT:
            store["count"] = seen + 1                             # lost update: overwrites, not increments
            admitted += 1
    return admitted, store["count"]

def atomic_incr():
    """INCR-style: the store does read-modify-write as one indivisible step, so each call sees the last."""
    store = {"count": LIMIT - 5}
    admitted = 0
    for _ in range(GATEWAYS):
        store["count"] += 1                                       # atomic increment returns the new value
        if store["count"] <= LIMIT:
            admitted += 1
    return admitted, store["count"]

a, c = check_then_set()
print(f"GET/compare/SET : admitted {a} of {GATEWAYS} with only 5 slots left; stored count says {c}")
a, c = atomic_incr()

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], tonumber(ARGV[4]))    -- idle keys vanish: memory stays bounded
return { allowed and 1 or 0, math.floor(tokens) }

Two details worth saying aloud. Use the store's clock inside the script, not the gateways': skewed clocks across a fleet make refill maths wrong (time revisited). And set a TTL on every key so the state for clients who left is reclaimed. Cost: one round trip (roughly half a millisecond inside a region, per chapter 2), and a dependency.

Option B: local limiters with periodic sync

Each gateway keeps its own counters and exchanges them with the others (through the store, or by gossip) every T milliseconds. The hot path has no network call, so the check costs microseconds and survives a store outage. The price is accuracy: until peers learn about a gateway's admissions, each decides on partial information. For a heavy offender the over-admission is roughly offered rate times T (see the napkin output). A variant, token leasing, has each gateway borrow a slice of the key's tokens from the store (say a tenth of the remaining bucket) and spend it locally; the global total can never be exceeded, and the cost is that unused slices are stranded and a gateway can run dry while another holds spare tokens.

Recommendation. Start with A for most keys, because 4 shards and 1 ms is a small price for exactness and a simple story. Move the highest-volume keys (a big tenant's global quota, anonymous per-IP) to B or C once the numbers show the store is the bottleneck. That hybrid is common because it matches the cost to the importance of each limit.

Deep dive 4: failure policy, hot keys and multiple regions

Fail open or fail closed

If the store is unreachable, the gateway cannot know the count. Fail open (allow) keeps the product up but removes protection exactly when something is wrong. Fail closed (deny) keeps the protection but turns a limiter outage into a full outage. Decide per rule, not per system:

Rule protectsChooseWhy
Fairness between tenants, general API quotasFail open, fall back to a coarse local limitAn outage of the limiter should not be an outage of the product; the downside is bounded and brief.
Login, password reset, SMS sending (money or account-takeover risk)Fail closed, or fall back to a strict local limitOpen means unlimited guessing or unlimited SMS bills.
Protecting a fragile dependencyFall back to a local concurrency capThe point is the dependency's survival; local limits are conservative enough.

Whatever you pick, bound the damage with a tight timeout on the store call (a few milliseconds), a circuit breaker so a sick store is not hammered, and a local fallback limiter so "open" does not mean "unlimited". Alert on fallback rate, not just on errors.

Hot keys

One abusive IP or one huge tenant sends most of the traffic to one key, therefore to one shard, and that shard saturates (hot partitions). The limiter is the one system where the hot key is, by definition, the one sending the most traffic. Remedies, in order of preference: reject abusers earlier (at the edge, with a local limiter, before they reach the store); give large tenants local or leased limiting (option B or C) so only a trickle of sync traffic reaches the shard; and split a hot key into sub-keys (key#0..#7) each holding one eighth of the quota, with the gateway choosing a sub-key at random. The last is the same trick used for hot counters in the distributed cache, and it accepts the same cost: skew between sub-keys.

Multiple regions

A global quota ("5,000 requests/min across the world") needs a decision about what the quota means when regions cannot talk instantly. A cross-region synchronous check adds a 100 ms-class round trip (chapter 2) to every request, which is unacceptable for the hot path. The usual answer is regional quotas with periodic rebalancing: split the global budget by recent traffic share, enforce each part locally with option A, and have a slow control loop move budget between regions. Accuracy is bounded by the rebalance interval; during a partition between regions each keeps its slice, so the global total never exceeds the sum of slices. For strict global limits the honest answer is that you need a single authoritative region for that key and accept the latency for those few keys (multi-region).

SLOs. Check latency p99 under 2 ms; limiter-induced error rate (timeouts and failures that were converted to fail-open or fail-closed) under 0.01%; and a correctness SLI: sampled comparison of admitted rate to configured rate for the top tenants. Alert on fallback rate, store timeouts, shard memory and the deny ratio per rule (a sudden jump means a bad policy or an attack, see burn-rate alerting). Roll out every new rule in shadow mode first, then at a small percentage of traffic, then fully, the same way you would a code change (deployments). Remember that rate limiting is a polite request; when load actually exceeds capacity regardless of per-client fairness you need load shedding and priorities (overload, resilience patterns).

Trade-offs & alternatives

  • Exactness versus latency and availability. We chose exact-by-default with a shared store and relaxed it for the biggest keys. If every limit had to be exact and global, we would pay a cross-region hop or concentrate keys in one region.
  • Burst friendliness versus strictness. Token bucket permits up to about twice the nominal rate in a short span. If the contract said "never more than N in any 60 s", use the sliding log or counter and give up burst tolerance.
  • If the limiter must also be a billing meter, this is the wrong design: metering needs durable, exactly-once counting of usage events (a log and an aggregation pipeline), not a best-effort cache.
  • If traffic were purely internal, skip per-user limits and use adaptive concurrency limits and load shedding, which respond to actual capacity.
  • Where it breaks down: adversaries with many IPs and accounts defeat per-identity limits; that is a bot-detection problem, not a counter problem.

What a strong answer adds

  • Asks what the limit is for (fairness, protection, cost, security) before choosing anything, and notes that the answer sets the fail-open policy.
  • Names the atomicity problem unprompted and says how the store solves it, including that the store's clock should be the clock.
  • Quantifies the algorithm trade-off: memory per key times keys, and the boundary double-burst of fixed windows.
  • Treats the limiter as a dependency on the critical path: timeout, breaker, fallback, and an alert on the fallback.
  • Knows hot keys here are caused by the attackers themselves and moves their limiting earlier and more local.
  • Layers limits (edge, gateway, service) and checks several keys per request without double charging.

Follow-up questions

How would you rate-limit by cost instead of by request count?

Give each request a cost (a search is 5, a read is 1) and charge it against the same token bucket: tokens -= cost in the script. The cost can be static per route or measured after the fact (charge the actual CPU or bytes when the response is done, letting the bucket go slightly negative). Static cost is predictable for clients; measured cost is fairer but clients cannot know their price in advance.

A customer says they were rate limited at 40 requests per minute but their limit is 100. What do you check?

First which key limited them: maybe a per-IP rule (NAT) or a per-route rule, not the plan limit. Then the algorithm (a fixed window with a burst at the boundary, a token bucket whose burst was spent and which refills slowly), then fallback behaviour, then policy propagation lag or a mis-scoped rule. This is why every 429 should log which rule and key denied it, and why the response should say so in a header or body.

Why not put the limiter in the application services instead of the gateway?

You can, and per-endpoint cost limits belong there. But then every service reimplements it, enforcement is inconsistent, and a denied request has already consumed a connection, TLS, parsing and auth in the service. The gateway rejects before the expensive work and gives one place to change policy. Use both, with different purposes.

How do you stop a distributed limiter from becoming the bottleneck?

Keep the hot path to one shard call; batch or pipeline where several keys must be checked; keep key state tiny; put coarse rejections at the edge; move giant keys to local or leased limits; and measure shard CPU and memory with headroom. The estimate says four shards; production would run more so one failure leaves capacity.

What happens to counters during a store failover?

With asynchronous replication the new primary may be slightly behind, so some recent increments are lost and buckets look fuller than they were: a short window of mild over-admission. For a best-effort limiter that is the right trade; do not pay for synchronous replication on every counter write. Redis-style stores replicate asynchronously by default, so treat counters as soft state (replication in practice).

How would you design a limit of 5 password attempts per account per 15 minutes?

A sliding log (or a small exact counter with a fixed window and a lockout), keyed by account and by IP separately, fail closed, with the lock state in a durable store rather than a soft cache, since losing it re-arms an attacker. Also respond uniformly so the limiter does not reveal which accounts exist.

Distributed systems connection

The atomic script is a tiny instance of the need for linearizable updates on shared state (consistency models). The accuracy-versus-latency choice is the CAP/PACELC trade made explicit: shared store means exact but dependent, local-with-sync means available but approximate. Gossip-based sync is the same idea as failure detection by gossip. A hands-on version of the algorithms arrives in Lab 2.

Key takeaways

  • Limit in layers: coarse and identity-free at the edge, per-identity at the gateway, per-cost in the services.
  • Token bucket is the sensible default (tiny state, explicit burst); fixed windows double-burst at the boundary; the sliding log is exact but costly; the sliding window counter is the cheap approximation.
  • The check is a read-modify-write and must be atomic: a server-side script on a sharded in-memory store, using the store's clock.
  • Shared store is exact but adds a hop and a dependency; local limiters with sync are fast and resilient but over-admit by about offered rate times the sync interval.
  • Decide fail-open versus fail-closed per rule, with a short timeout, a breaker, and a local fallback.
  • Hot keys are the abusers; reject them earlier and limit them locally. Multi-region quotas are split regionally and rebalanced slowly.
  • 429 and Retry-After are standard; the RateLimit headers are an Internet-Draft, so verify before depending on them.

Check your understanding

A fixed-window limiter allows 100 requests per minute. What is the most a client can legitimately send across a window boundary in a short span?

  1. 100, since the window resets
  2. About 200, 100 at the end of one window and 100 at the start of the next
  3. Exactly 100, enforced by the store
  4. About 50
The counter resets at the boundary, so a client can use the full limit just before it and the full limit just after. A sliding log or counter, or a token bucket with a small bucket, narrows this.

Two gateways run GET, compare, SET against the same counter with one slot left. What can go wrong?

  1. Nothing; Redis serialises commands so the pair is safe
  2. Both read the same value, both admit, and one increment is lost (a lost update)
  3. The key expires
  4. Both requests are rejected
Each command is atomic but the sequence is not. The fix is one atomic operation (an increment, or a server-side script) so the read and write cannot interleave.

Your limiter store becomes unreachable. For the login endpoint you should most likely:

  1. Fail open to keep logins working
  2. Fail closed or fall back to a strict local limit, since unlimited guessing is the risk
  3. Retry forever
  4. Disable the endpoint permanently
The harm of failing open is attacker-controlled on this endpoint, so use a conservative fallback. For an ordinary fairness quota the balance usually goes the other way.

Which statement about the RateLimit response headers is right?

  1. They are defined in RFC 9110
  2. They are an Internet-Draft from the HTTPAPI working group, so check their status and expect the syntax to move
  3. They replace Retry-After
  4. They are required on every 429
Retry-After is standard. The RateLimit and RateLimit-Policy fields are a draft that has changed shape several times; many APIs still ship X-RateLimit-* conventions.

A tenant's global quota key receives 60% of all checks and saturates one shard. Which fix is best?

  1. Add more shards without changing the key
  2. Give that key a local or leased limiter (or split it into sub-keys) so the shard sees far fewer operations
  3. Switch to the sliding log
  4. Fail closed on that shard
Adding shards does not help because one key always maps to one shard. Moving the work to the gateways, or splitting the key, spreads it.

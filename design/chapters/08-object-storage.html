Design Object Storage

Metadata versus data, erasure coding, durability arithmetic and multipart uploads. An S3-like store is two systems behind one API: a small, strongly consistent index of names and a vast, cheap, append-only store of bytes that must survive years of failing hardware.

Why this matters

Object storage is the substrate under photos, backups, logs, data lakes and half the internet. It is also the clearest example of a design where two completely different systems hide under one API: a small, transactional, strongly consistent database of names, and a vast, cheap, append-only store of bytes whose job is to not lose anything for years. The durability arithmetic here (what an erasure code actually buys, and what repairs cost) is the sort of calculation that separates a confident answer from a hopeful one.

The problem

"Design a service like Amazon S3: customers store and retrieve arbitrary blobs by name, from kilobytes to terabytes, cheaply, and never lose them."

The word that does the work is "never". The ambiguity is in the rest: how many objects, how durable is durable enough (and how do we express it), what consistency do callers expect, and how does "list my bucket" behave while writes are in flight? The block was catalogued in chapter 3; here we build one.

Clarify requirements

QuestionAssumed answer

Size and scale?100 PB of user data, mean object about 1 MB (a mix of tiny and huge), up to 5 TB per object.
Durability?A design target of eleven nines per object per year (99.999999999%), the figure large public object stores publish as a design goal. We will see what the arithmetic supports.
Availability?99.99% for reads and writes. Availability is different from durability: data can be safe and temporarily unreachable.
Consistency?Strong read-after-write for new objects, overwrites, deletes and listings. (Public object stores historically offered eventual listing; today's large ones provide strong consistency, and callers now expect it.)

Estimate

The estimate answers four questions: how big is the metadata (it is surprisingly big), how many drives and which scheme, how much background traffic repair and scrubbing produce, and how much bandwidth the front door sees. All inputs are assumptions you can edit.

Decisions from the output. Metadata is its own system: 1011 objects at 300 bytes is 30 TB and over 200k lookups per second, so it must be sharded; the object count, not the byte count, drives it, which is why a store of tiny objects is much harder than a store of big ones. Erasure coding halves the fleet: 3x replication needs about 23,000 drives for 100 PB and Reed-Solomon (6,3) needs about 12,000; at this scale that is a hardware bill that dwarfs the engineering cost of coding. Repair is a continuous background load: with tens of thousands of drives, a drive dies every day or so, and erasure-coded rebuilds read six times the lost data (the 0.6 GB/s versus 0.2 GB/s lines), so repair bandwidth must be budgeted, not hoped for. Scrubbing is the biggest consumer: reading every byte once a month is tens to over a hundred GB/s of background I/O. And the front door at 1.6 Tbit/s says a CDN or many front ends are essential for reads.

API

PUT    /{bucket}/{key}                 body, optional checksum header   -> 200 + ETag + version-id
GET    /{bucket}/{key}                 optional Range: bytes=0-1048575  -> 200/206 + bytes + checksum
DELETE /{bucket}/{key}                                                  -> 204 (a delete marker if versioned)
GET    /{bucket}?prefix=logs/2025/&delimiter=/&max-keys=1000&continuation-token=...
                                                                         -> keys, common prefixes, next token
-- multipart (objects larger than a few hundred MB)
POST   /{bucket}/{key}?uploads                                       -> upload-id
PUT    /{bucket}/{key}?uploadId=U&partNumber=7   part bytes        -> part ETag
POST   /{bucket}/{key}?uploadId=U   [(1,etag1),(2,etag2),...]       -> 200  (this is the commit)
DELETE /{bucket}/{key}?uploadId=U                                   -> abort, free the parts

Three API choices are really design choices. Keys are flat strings; "folders" are a convention (a prefix and a delimiter), which is what lets listing be a range scan of a sorted index. Objects are immutable, so there is no partial update, and everything below gets simpler. PUT is naturally idempotent for the same key and body; conditional requests (a precondition on the current ETag or "only if absent") let clients build safe concurrent updates on top.

Data model

  • Metadata record: key (bucket, key) to a list of versions; each version holds (version_id, size, whole-object checksum, storage class, created_at, manifest). The manifest lists chunks, and each chunk lists its fragments as (node, device, fragment_id, checksum).
  • Partitioning of metadata: by key range within a bucket so that listing is a range scan, with ranges splitting automatically when they get hot or big (the trade-offs of range versus hash partitioning are in sharding). Each range is replicated with consensus, giving linearizable reads and writes per key (consensus).
  • Data plane: storage nodes hold fragments in large, append-only extent files (hundreds of MB), with an index from fragment id to offset. Many small fragments are packed into a few big files to avoid filesystem overhead and enable sequential I/O. A fragment, once written, never changes.
  • Placement metadata: the topology (zones, racks, nodes, free space, health) the placement service uses to spread fragments across failure domains.

High-level design

The front end is stateless and does the per-request work (authentication, checksums, erasure coding, hedged reads). The metadata service decides what exists. The data plane stores bytes. Three background workers keep the data plane honest. Here is the main path:

Step through

A PUT and a GET, end to end

  1. PUT arrives. The front end authenticates, checks the request signature and starts a running checksum over the incoming bytes, which also compares with any checksum the client sent.
  2. Allocate. It asks placement for nine nodes spread over three zones and distinct racks. No metadata about the object is visible to anyone yet.
  3. Write fragments. It cuts the stream into chunks, erasure-codes each into 6 data and 3 parity fragments, and writes them to the nine nodes in parallel. Each node stores the fragment with its own checksum and verifies it on write.
  4. Wait for durability. It waits until all nine are durably written (retrying a slow one on another node). The object is still invisible: these fragments are orphans until a manifest points at them.
  5. Commit. One atomic write of the manifest (key, version, size, checksum, fragment locations) to the strongly consistent metadata shard. This is the commit point: after it, any GET or LIST sees the object.
  6. Acknowledge. The client gets 200 and an ETag. If the front end crashed before step 5, the client got no success and the fragments are garbage-collected.
  7. GET: look up. The front end reads the manifest from the metadata shard. Because the commit and the lookup go through the same shard, a GET after a successful PUT sees it (read-after-write).
  8. GET: read. It requests fragments from more than six nodes and uses the first six to arrive (a hedged read), decodes, verifies the checksum and streams the bytes. A range request reads only the chunks it covers.
  9. GET: corruption. If a fragment fails its checksum, the front end reads another fragment instead, serves correct bytes, and queues the bad fragment for repair. The client never sees the corruption.

Deep dive 1: metadata versus data, and consistent listing

The split is the central design decision, so state the reasons. The two planes have opposite shapes:

Metadata planeData plane
SizeTens of TB, but billions of tiny recordsHundreds of PB
AccessRandom, small, latency-criticalLarge and sequential
ConsistencyStrong (it defines what exists)Immutable bytes: no consistency problem
HardwareSSD, memory, replicated with consensusDense HDD, erasure coded
Scaling limitObject count, hot key rangesDrive count, repair bandwidth

Since the bytes are immutable, almost all the hard consistency questions reduce to one: when does an object begin to exist? Answer: at the single atomic manifest write to the metadata shard that owns its key. Before that write, the fragments are invisible orphans; after it, the object is durable and visible. That one linearizable write is the commit point, and the same shard serves both the lookup for GET and the sorted scan for LIST, so a successful PUT is visible to the next GET and the next LIST. Read-after-write consistency falls out of using one source of truth rather than a separately updated listing index. That separate index was the usual reason older object stores had eventually consistent listings: it was updated asynchronously. The cost of the strong design is that metadata shards must run consensus (a few milliseconds more per write) and that a LIST that spans several ranges has to merge scans from several shards at a consistent point in time.

Overwrites and deletes. A PUT to an existing key writes a new version; the latest committed manifest wins, ordered by the shard's commit order, not by client clocks (time revisited). A DELETE writes a delete marker or removes the record; the underlying fragments are reclaimed later by garbage collection.

Hot prefixes. Because key ranges are contiguous, a workload that writes logs/2025-10-13/... hammers one range. Remedies: automatic range splitting by load, and advising clients to spread keys across prefixes. If listing order did not matter, hash partitioning would remove the problem, at the price of expensive listings. This is the same hot-partition trade-off as everywhere.

The last-but-one rows decide the layout across zones. A stripe spread evenly over three zones loses one third of its fragments when a zone goes dark, so the code must tolerate at least that many losses: (6,3) does (it loses 3, tolerates 3), and (10,4) does not (it loses 5, tolerates 4). A single-site system with many racks as its failure domains can use the wider, cheaper (10,4); a three-zone design needs (6,3) or a code with local parity groups. Now the durability, computed.

"""SIMPLIFIED durability model: replication vs erasure coding, under assumed failure rates and repair times.

Model: each stripe has n fragments on n independent drives, and data is lost if more than m = n - k fragments are
down at once. Drives fail independently at rate lam = AFR / 8766 per hour; a lost fragment is rebuilt in T hours
(rate mu = 1/T). Standard birth-death approximation of the mean time to data loss for one stripe:
    MTTDL ~ mu^m / ( lam^(m+1) * n * (n-1) * ... * (n-m) )
Annual loss probability for one stripe ~ 8766 / MTTDL (valid when it is small).
NOT modelled: correlated failures (a rack, a batch, a firmware bug), bit rot, operator error, repair queueing under
load, and the repair-time dependence on how many failures are in flight. Real durability is usually limited by those,
so read the output as relative ranking and sensitivity, not as a promise.
"""
import math

HOURS_YEAR = 8766

def annual_loss(n, k, afr, repair_hours):
    m = n - k
    lam, mu = afr / HOURS_YEAR, 1 / repair_hours
    falling = math.prod(n - i for i in range(m + 1))              # n (n-1) ... (n-m)
    mttdl_hours = mu ** m / (lam ** (m + 1) * falling)
    return min(1.0, HOURS_YEAR / mttdl_hours)

def nines(p_loss):
    return float("inf") if p_loss <= 0 else -math.log10(p_loss)

schemes = [("2x replication", 2, 1), ("3x replication", 3, 1), ("RS(6,3)", 9, 6), ("RS(10,4)", 14, 10), ("RS(17,3)", 20, 17)]

for afr in (0.02, 0.05):
    for repair in (24, 72):
        print(f"\nAFR {afr:.0%}, rebuild time {repair} h")
        print(f"  {'scheme':<16}{'overhead':>9}{'tolerates':>10}{'annual loss / object':>22}{'durability (nines)':>20}")
        for name, n, k in schemes:
            p = annual_loss(n, k, afr, repair if name.startswith("RS") else repair / 2)   # one copy rebuilds faster than a wide stripe
            print(f"  {name:<16}{n/k:>8.2f}x{n-k:>10}{p:>22.2e}{nines(p):>20.1f}")
print("\n(replication rebuilds are assumed 2x faster than erasure-coded rebuilds, because RS must read k fragments per lost one)")

# AZ loss: can a code survive a whole zone? A stripe spread evenly over z zones loses ceil(n/z) fragments at once.
print("\nspreading a stripe across 3 zones:")
for name, n, k in schemes:
    lost = math.ceil(n / 3)
    ok = "survives" if lost <= n - k else "LOSES DATA"
    print(f"  {name:<10} loses up to {lost} fragments if one zone is down; tolerates {n-k}: {ok}")

How to read this honestly. The model is simplified: it assumes independent drive failures and a fixed repair time, and ignores everything correlated (a bad firmware batch, a rack power fault, a software bug that corrupts many fragments, an operator deleting the wrong thing). Those usually set real-world durability, which is why the output must be read as a ranking and a sensitivity, never as a number to quote. Within the model: two-way replication sits around five to six nines, three-way around eight to ten, and erasure codes beat replication at much lower overhead because they tolerate more simultaneous losses (RS(6,3) matches three-way replication at half the space; RS(10,4) is better still). The danger is visible in the last row: RS(17,3), cheap at 1.18x, is thousands of times worse than (10,4) and loses to 3-way replication, because wide stripes with little parity have many fragments that can fail and little margin. And look at the sensitivity: tripling the repair time costs roughly one to two nines, and raising the annual failure rate from 2% to 5% costs a similar amount. Repair speed is a durability parameter, which is why the next section budgets repair bandwidth. This is the same arithmetic as the redundancy sections of availability maths, applied to data loss instead of downtime.

Placement rules

Placement spreads a stripe's fragments across distinct failure domains: a different drive, node, rack and zone for each, so one event cannot take two fragments. It also balances free space and avoids newly added empty nodes absorbing all the writes at once. Placement is a metadata decision recorded in the manifest, so nodes can be rebalanced or drained by rewriting manifests. Prefer a placement algorithm that is deterministic given the topology, so repair can recompute what should exist; a related technique is consistent hashing with constraints (partitioning).

For small objects, the usual approach is to pack many of them into one larger stripe (so the coding unit is large) or to replicate them, and to erasure-code only once data is large or cooled. The Dropbox Magic Pocket case describes a production system that made exactly this kind of choice, including erasure coding for cold data and the operational machinery around it.

Deep dive 3: multipart upload, garbage collection and checksums end to end

Multipart upload

A 500 GB object cannot be one request: it would fail near the end and restart from zero. Multipart splits the upload into parts (say 8 to 100 MB) that are uploaded independently, in parallel, with retry per part. Each part is stored like a small object but is not visible under the key. The final complete call sends the ordered list of part numbers and checksums; the service verifies them and writes one manifest that stitches the parts together, atomically. That manifest write is again the commit point. Properties: a failed part retries without touching the others; the parts never need to be rewritten or concatenated (the manifest refers to them where they are); and an interrupted upload leaves orphans. Abandoned uploads hold storage, so a lifecycle rule should abort them after a few days.

Garbage collection

Fragments become garbage in three ways: an upload never committed, an object was deleted or overwritten, or a multipart upload was aborted. A collector compares the set of fragments on the nodes with the set referenced by manifests, and deletes those with no reference. The danger is a race: the collector scans the manifests, then a slow PUT commits a manifest that references fragments the scan did not see as referenced, and the collector deletes them. That is silent data loss. The standard defences: only delete a fragment once it is older than a grace period longer than any upload can take; make deletion a two-step (mark, then sweep after a delay) so mistakes are caught before they are permanent; and keep deletes of manifests in a recoverable state for a while, which also protects against operator error. Garbage collection is the part of an object store where bugs destroy data, so it deserves paranoia more than speed.

"End to end" matters because each hop can corrupt: TCP's checksum is weak and does not cover memory or disk. Disks silently return wrong data at a measurable rate, and the only defence is a checksum written when the data was good and checked whenever it is read.

Deep dive 4: durability in operation, and tiering

A durable design on paper decays unless it is maintained. The mechanisms:

  • Failure detection and repair. When a node or drive dies, the repair workers enumerate the stripes that lost a fragment and rebuild those fragments onto other nodes, reading k survivors for each. Repair is spread across the whole fleet (many sources, many targets), so a 16 TB drive rebuilds in hours rather than days; a rebuild bottlenecked on one replacement drive would take longer than the expected time to the next failure. Prioritise stripes by remaining redundancy: a stripe that has lost three of four tolerable fragments goes first.
  • Scrubbing. Verify all data against checksums on a schedule, at low priority, rate limited so foreground traffic is unaffected. The napkin run showed it is the largest I/O consumer: that cost is the price of knowing.
  • Repair bandwidth budget. Reserve network and disk capacity for repair, throttled by priority but never starved (overload: repair competing with foreground load is a classic metastable trap).
  • Correlated failure drills. Practise losing a rack and a zone; confirm that repair finishes and the code tolerates it (disaster recovery).

A lifecycle rule ("after 30 days move to warm; after a year to cold") is a background job that rewrites the manifest after recoding the data. The metadata for cold objects stays on the fast tier, because listing must stay fast and a GET must be able to decide whether to start a restore. Tiering is a pure cost optimisation and the knobs come from access patterns: most data is rarely read after the first weeks.

Trade-offs & alternatives

  • Cost versus complexity. Erasure coding halves the hardware at the price of repair traffic, CPU and a more complex read path. At 100 PB it is easily worth it; at 100 TB, three-way replication is the sensible choice.
  • Strong versus eventual listing. One consistent metadata source is simpler for users; the eventually consistent index it replaced could scale reads more cheaply. We chose the simple contract.
  • Latency versus cost across tiers. Cold storage is cheap because it is slow; make that explicit in the API (restore requests).
  • If objects were mutable or needed POSIX semantics, this design would not apply: you would need a distributed file system with a different metadata and locking story.
  • If the system must span regions, add asynchronous cross-region replication of manifests and data, accepting a replication lag in durability and visibility (multi-region).

What a strong answer adds

  • Splits metadata and data immediately, with the reasons, and says the commit point is one atomic manifest write.
  • Explains how read-after-write and consistent listing follow from a single metadata source of truth.
  • Computes storage overhead and tolerated failures for replication and for a named code, and then shows the zone arithmetic that rules out some layouts.
  • Knows durability depends on repair speed and treats repair bandwidth as a budgeted resource.
  • Names correlated failures as what a simple model hides, and labels the nines as design targets.
  • Puts checksums at every hop and runs a background scrubber.
  • Treats garbage collection as dangerous, with grace periods and two-phase deletion.
  • Handles small objects, hot prefixes and tiering with specific mechanisms.

Follow-up questions

Why not just use three copies and be done?

You can, and at modest scale you should. At 100 PB it is 300 PB raw against 150 PB for (6,3): a hardware bill difference of tens of thousands of drives plus the power and space to match. The price of coding is engineering complexity and heavier repair, which at that scale is cheap by comparison. A common compromise is replication for hot or small data and coding for the bulk.

How would you support strongly consistent LIST across a huge bucket?

Range-partition the metadata so keys are sorted, serve LIST by scanning ranges in order and merging, and read all ranges at a snapshot timestamp so a listing does not tear. Paginate with an opaque continuation token that encodes the last key. The commit point (the manifest write) makes new objects visible to the same index immediately.

What if the front end crashes halfway through writing fragments?

Nothing was committed, so the object does not exist; the client got no success and retries. The fragments are orphans cleaned up by garbage collection after the grace period. Because the only visible effect is the atomic manifest write, a partial upload can never be observed.

How do you delete data for good, for example for a legal request?

Deleting the manifest hides the object immediately; the fragments are reclaimed when GC runs after its grace period, so there is a bounded delay. Backups, older versions and cold tiers also have to be covered, and for cryptographic erasure you encrypt each object with its own key and destroy the key. Be honest about the time bound in the policy.

How would you add encryption at rest?

Encrypt each object (or chunk) with a data key, store the data key wrapped by a key-management service in the manifest, and rotate by rewrapping keys, not by rewriting data. Mind that erasure coding applies to ciphertext, so dedup across objects stops working. Compare keys, secrets and PKI.

Why is the first byte slow on a GET of a small object, and what do you do?

The path costs a metadata lookup, then k parallel fragment reads, and the slowest of those sets the latency (the tail at scale problem). Hedge: request more fragments than needed and use the first k. Cache hot manifests, and put a CDN in front for popular objects. For tiny objects consider replicating rather than coding so a GET touches one node.

Distributed systems connection

An object store is a consensus-backed index sitting on top of an erasure-coded blob layer, so it exercises replicated state machines for metadata, failure detection for repair triggers, and the independence assumption that every durability calculation depends on. The garbage-collection race is a lesson in why deletes need the same care as writes, and the commit point is an application of the "write the pointer last" pattern you also met in crash recovery.

Key takeaways

  • Separate the small, strongly consistent metadata plane from the huge, immutable data plane; an object exists exactly when its manifest is committed.
  • Strong read-after-write and listing follow from one consistent metadata source and range-partitioned keys.
  • Erasure coding gives replication-class durability at about half the space, and costs read fan-out, CPU and repair traffic: (6,3) is 1.5x and tolerates 3 losses; (10,4) is 1.4x and tolerates 4.
  • Do the zone arithmetic: a stripe spread over 3 zones loses a third of its fragments with a zone, so the code must tolerate that.
  • Durability depends on repair time as well as redundancy, and simple models ignore correlated failure; label the nines as targets.
  • Use checksums at every hop and scrub in the background. Treat garbage collection as the most dangerous component.
  • Multipart upload parallelises and retries large uploads, committing with one manifest write; tier data to cut cost, keeping metadata hot.

Check your understanding

In the object store, when does a newly uploaded object become visible?

  1. As soon as the first fragment is written
  2. When all fragments are written and the manifest is atomically committed to the metadata shard
  3. After garbage collection runs
  4. After the client calls LIST
Fragments before the commit are invisible orphans. The atomic manifest write is the commit point; visibility and durability coincide there.

A stripe is spread evenly over 3 zones with a (10,4) code (14 fragments). One zone goes dark. What happens?

  1. Nothing; the code tolerates 4 losses so it is safe
  2. Up to 5 fragments are lost, which exceeds the 4 tolerated, so data is unrecoverable until the zone returns
  3. The stripe is rebuilt instantly
  4. Only parity is lost
ceil(14 / 3) = 5 fragments sit in the largest zone; the code tolerates 4. A (6,3) code puts 3 per zone and tolerates 3.

Why can a lower-overhead code like RS(17,3) have worse durability than 3-way replication in the model?

  1. It stores fewer bytes
  2. It has many fragments that can fail but only 3 of margin, so the chance that 4 are down at once is high
  3. Parity fragments are slow
  4. It cannot be repaired
Durability depends on the number of tolerated simultaneous failures against the number of fragments at risk and on repair time, not on overhead alone.

What is the best defence against the garbage collector deleting fragments of an object that is being committed right now?

  1. Run GC more often
  2. Only delete fragments older than a grace period longer than any upload, using mark then sweep
  3. Delete in parallel
  4. Skip checksums
A scan can miss a manifest committed after it started. A grace period and two-phase deletion make that race harmless.

Why must checksums be verified at the front end and on the storage node, rather than only once?

  1. To save bandwidth
  2. Each hop (network, memory, disk) can corrupt data, and only a checksum made while the data was good can detect it later
  3. Because TCP has no checksum
  4. To speed up reads
End-to-end checks cover the whole path; the scrubber also verifies data at rest nobody is reading.

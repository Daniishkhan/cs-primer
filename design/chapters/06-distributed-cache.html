Design a Distributed Cache

Partitioning, replication, eviction, hot keys and the consistency of the cache with its database. A shared in-memory cache looks like a hash map with a network in front of it, and the interesting part is everything that goes wrong when the map is spread across forty machines in three regions.

Why this matters

A cache is the cheapest performance fix in the book and the easiest to get subtly wrong. A distributed cache adds new questions on top of the single-node one: which node owns a key, what happens to the database when a node disappears, how a key taking a quarter of all traffic gets served, and how the cache and the database stay in agreement. The answers are all derived from a handful of numbers, which is why this makes a good design exercise.

The problem

"Design a distributed in-memory cache that our services share, like memcached or a Redis cluster. It should make reads fast, protect our databases, and scale as we grow."

Four things are loose. How big is "big"? Is it a pure cache (any data can vanish) or a data store (Redis-as-a-database)? How fresh must data be? And who is the caller: one product or a whole company's worth of services? You met the single-node ideas in caching; this chapter is about running a fleet of them.

Clarify requirements

Estimate

The question we need answered is how many nodes, and whether the database can survive the cache's worst day. Memory and throughput each give a node count; the larger wins.

The idea

  1. per item ← (key + value + overhead) × 1.15; data ← items × per item
  2. nodes ← max(data ÷ (64 GB × 75%), peak reads ÷ (100k × 50%))
  3. for each hit ratio h: database load ← peak reads × (1 − h)
  4. egress ← peak reads × value size × 8; per node ← egress ÷ nodes
  5. for each hot-key share: ops ← peak reads × share; ops ÷ node capacity

Three decisions fall out. First, the cluster is memory-bound: 40 nodes for memory versus 24 for throughput, so scaling out for capacity is driven by data size and the per-item overhead is not negligible (26% above the raw value under these assumptions). Second, the hit ratio must be around 99%: at 95% the database would see 60k reads/s against a 20k ceiling, so the cache is not an optimisation but part of the capacity of the system. Third, a single key can exceed a node: at 10% of traffic one key needs more than one node's throughput, which is the hot-key problem.

API

# Reads
get(key)                 -> value | MISS | {MISS, lease_token} | {WAIT}
mget(keys[])             -> map of key -> value   # batched per shard

# Writes
set(key, value, ttl, lease?)
                         -> STORED | REJECTED
                            # REJECTED if the lease was revoked
delete(key)              -> OK
                            # also revokes any outstanding lease
incr(key, delta)         -> new value             # atomic, for counters
cas(key, value, version) -> STORED | EXISTS       # optimistic update

# Limits
key <= 250 B, value <= 1 MB, TTL mandatory (default 1 hour)

Make TTL mandatory: it is the safety net that bounds staleness when an invalidation is lost, which will eventually happen. Multi-get matters because one page view may touch dozens of keys; the client library groups them per shard and sends the batches in parallel, so the user waits for the slowest shard, not the sum (the tail at scale problem: fan-out amplifies the slow tail).

Data model

  • Key: namespace:version:id, for example profile:v3:42. The version lets you invalidate a whole class of keys after a schema change by bumping it, with no scan.
  • Value: an opaque byte string, serialised and optionally compressed by the client. The cache never interprets it.
  • Item in memory: key, value, expiry time, flags, plus hash-chain and eviction-list links. That per-item bookkeeping is the "overhead" in the estimate; real systems have roughly tens of bytes of it, and the exact figure varies by software and version.
  • Partitioning: by hash of the key onto a consistent-hash ring with virtual nodes (partitioning). Redis Cluster does the same job with a fixed set of 16,384 hash slots assigned to nodes; the idea is closely related (it is slot-based, not a ring), and the unit of movement is the slot.

High-level design

Applications link a client library that holds the ring, routes each key to its owning node and talks to it directly. Each primary has an asynchronous replica for failover. The database remains the source of truth, and a change log feeds an invalidator. Walk through one read and one write:

Step through

A read and a write, end to end

  1. Route. The client library hashes the key onto the ring and sends get k straight to the owning shard. It checks its small local L1 cache first for keys marked hot.
  2. Hit. Most of the time (99% in our estimate) the shard answers from memory in well under a millisecond and the database never hears about it.
  3. Miss. The shard has nothing, so it hands this one client a lease token. Any other client asking meanwhile is told to wait briefly or is served a slightly stale value.
  4. Read the database. The lease holder reads the row from the source of truth. This is the only database read for the key, however many clients wanted it.
  5. Fill. It sets the key with its token. The shard accepts the fill only if the lease is still valid, so a value that was already invalidated cannot be installed.
  6. Write. A write goes to the database only. The application does not update the cache, because two writers racing on a database and a cache can leave them disagreeing forever.
  7. Capture. The database's change log records the committed write. This is change data capture: the log is ordered and contains only committed changes.
  8. Invalidate. The invalidator consumes the event and deletes the key, which also revokes any outstanding lease. The next read misses and refills with the new value.

Deep dive 1: partitioning, routing and failover

Consistent hashing is the reason adding or losing a node moves only a small share of keys. The script measures it on this design's cluster size, since the interesting number is not the fraction moved but what that fraction does to the database.

The idea

  1. h(s) ← first 64 bits of md5(s)
  2. modulo: nodes[h(key) mod N]; ring: 150 points per node, clockwise
  3. moved ← keys whose owner differs before and after an add or a loss
  4. db load ← normal misses + hits × fraction moved
"""How many keys change owner when the cluster changes?
Modulo hashing vs a consistent-hash ring with virtual nodes."""
import bisect
import hashlib

# ── 1. A stable hash ────────────────────────────────────────────────
def h(s: str) -> int:
    """64 bits of md5: stable across runs, unlike Python's hash()."""
    digest = hashlib.md5(s.encode()).digest()
    return int.from_bytes(digest[:8], "big")

# ── 2. Two ways to pick an owner ────────────────────────────────────
def modulo_owner(nodes):
    """hash(key) % N. Changing N changes almost every answer."""
    def owner(key):
        return nodes[h(key) % len(nodes)]
    return owner

def ring_owner(nodes, vnodes=150):
    """Each node sits at many points on a ring; a key belongs to the
    next point clockwise, so a node change only moves its own arcs."""
    ring = sorted((h(f"{n}#{v}"), n)
                  for n in nodes
                  for v in range(vnodes))
    points = [p for p, _ in ring]

    def owner(key):
        i = bisect.bisect(points, h(key)) % len(ring)
        return ring[i][1]
    return owner

keys  = [f"user:{i}" for i in range(100_000)]

              f"of keys change owner")

Modulo hashing remaps almost everything when the node count changes, so every membership change is a cache wipe and a database stampede. The ring moves about 1/N of the keys. But look at the last line: even with a ring, losing one node of 40 sends about 2.8% of traffic to the database, and 45k reads/s is over the 20k ceiling. The consistent hash is necessary and not sufficient: you also need protection (leases, below), replicas, or spare database capacity sized for a node loss.

Large deployments commonly end up with a proxy tier for exactly those reasons; the memcache case study describes one.

Replication and failover

Plain memcached has no replication at all: losing a node loses its keys and the application refills from the database. Redis-style clusters give each primary one or more asynchronous replicas and promote a replica when the primary is judged dead, using a majority vote among the primaries to avoid two sides each promoting (failure detection, fencing). Asynchronous replication means a promoted replica can be missing the last few writes: for a cache that is acceptable, because TTLs and invalidations repair it, but it is a reason not to treat the cache as a database. The alternative to replicas is a gutter pool: a small set of spare nodes that serve a failed node's traffic with a very short TTL, so a node loss costs misses, not an outage, and does not require doubling the memory bill.

OptionMemory costOn node failureComplexity
No replicas1x1/N of keys miss; database takes the spikeLowest
Replica per primary2xPromote; near-zero misses; possible small stalenessFailure detection and promotion logic
Gutter pool (a few spare nodes)1x + a few percentSpare absorbs misses with short TTLs; database spike is boundedClient logic to detect and redirect

Because the cluster here is memory-bound, doubling it for replicas means 80 nodes instead of 40, which has to be justified by the cost of a miss. Our estimate says a node loss pushes the database over its ceiling. My preference: no replicas for the bulk of the data, a gutter pool plus leases to bound the spike, and replicas only for the small set of items whose miss is genuinely expensive (the expensive-to-compute and the hot).

Deep dive 2: eviction and memory

When memory is full, something has to go. The policy decides the hit ratio, which, as the estimate showed, decides whether the database survives. The script runs a skewed workload (Zipf, the usual shape of real popularity) through four policies, then adds one-time scan traffic such as a crawler or batch job.

The idea

  1. stream: weight 1/(i+1) per key, plus one-time scan keys
  2. FIFO: evict oldest insert; LRU: a hit moves the key to the end
  3. random: evict a random key; LFU: evict least-frequent, refuse colder keys
  4. for scan in 0%, 30%; for cache in 1%, 5%, 10% of keys: hits ÷ requests
"""Hit ratio of eviction policies on a skewed (Zipf) workload, with and
without one-time scan traffic."""
import bisect
import itertools
import random
from collections import Counter, OrderedDict

# ── 1. The request stream ───────────────────────────────────────────
def zipf_stream(n_keys, n_req, s, seed, scan_frac=0.0):
    """Key i is requested with weight 1/(i+1)^s: a few keys dominate.
    scan_frac of requests are one-time keys that are never seen again."""
    rnd = random.Random(seed)
    weights = [1 / (i + 1) ** s for i in range(n_keys)]
    cum = list(itertools.accumulate(weights))
    total = cum[-1]
    scan_id = n_keys
    out = []
    for _ in range(n_req):
        if rnd.random() < scan_frac:
            # A key never seen again (a crawler or batch job).
            out.append(scan_id)
            scan_id += 1
        else:
            out.append(bisect.bisect(cum, rnd.random() * total))
    return out

# ── 2. FIFO and LRU ─────────────────────────────────────────────────
def lru(stream, cap):
    """Evict the key untouched for longest; a hit moves it to the end."""
    c = OrderedDict()
    hits = 0
    for k in stream:
        if k in c:
            hits += 1
            c.move_to_end(k)
        else:
            c[k] = 1
            if len(c) > cap:
                c.popitem(last=False)
    return hits / len(stream)

def fifo(stream, cap):
    """Evict the oldest insert; a hit changes nothing."""
    c = OrderedDict()
    hits = 0
    for k in stream:
        if k in c:
            hits += 1
        else:
            c[k] = 1
            if len(c) > cap:
                c.popitem(last=False)
    return hits / len(stream)

# ── 3. Random and LFU ───────────────────────────────────────────────
def rand_evict(stream, cap, seed=7):
    """Evict a uniformly random resident key."""
    rnd = random.Random(seed)
    c = {}
    keys = []
    hits = 0
    for k in stream:
        if k in c:
            hits += 1
        else:
            if len(keys) >= cap:
                i = rnd.randrange(len(keys))
                old = keys[i]
                keys[i] = k
                del c[old]
            else:
                keys.append(k)
            c[k] = 1
    return hits / len(stream)

def lfu(stream, cap):
    """Frequency counted over the whole run: an idealised LFU, a
    ceiling rather than a real policy."""
    freq = Counter()
    c = set()
    hits = 0
    for k in stream:
        freq[k] += 1
        if k in c:
            hits += 1
            continue
        if len(c) >= cap:
            victim = min(c, key=freq.__getitem__)
            if freq[victim] >= freq[k]:
                continue                  # do not admit a colder key
            c.remove(victim)
        c.add(k)
    return hits / len(stream)

# ── 4. Run every policy at three cache sizes ────────────────────────
N_KEYS = 20_000
N_REQ  = 150_000

for scan in (0.0, 0.30):
    s = zipf_stream(N_KEYS, N_REQ, 1.0, seed=1, scan_frac=scan)
    print(f"Zipf(1.0) over {N_KEYS:,} keys, {scan:.0%} one-time scan "
          f"traffic, {N_REQ:,} requests")
    print(f"  {'cache size':<12}{'FIFO':>8}{'random':>8}"
          f"{'LRU':>8}{'LFU*':>8}")
    for pct in (1, 5, 10):

               f"{lru(s, cap):>8.1%}{lfu(s, cap):>8.1%}")
        print(f"  {pct:>3}% of keys {row}")

print("*LFU here counts frequency over the whole run and refuses to admit")
print(" colder keys: an idealised upper bound.")

Frequency-aware policies beat recency alone on a skewed workload, and with scans polluting the cache the gap stays large (and is bigger in relative terms): LRU lets every scanned key push out a genuinely popular one, while a policy that refuses to admit colder keys does not. The LFU column is an idealised ceiling (it uses whole-run knowledge), so treat it as "how much is on the table", not a number any implementation reaches. Practical systems approximate it: sampled LRU/LFU in Redis, and admission filters (TinyLFU-style) in some local caches. Also note how weak the gains from cache size are: going from 5% to 10% of keys adds only about 8 points, so the cost of memory per hit point rises quickly.

Memory overhead and allocation

Per-item overhead hurts most when values are small: a 100-byte value with 60 bytes of bookkeeping is 60% overhead, while a 10 KB value barely notices. Memcached-style allocators use slab classes (size classes with fixed chunk sizes) to avoid fragmentation, at the cost of internal waste (the 15% in the estimate) and the risk that a shift in item sizes leaves memory stranded in the wrong class. Mitigations: batch many tiny values into one key where access patterns allow, compress large values on the client (trading CPU for memory), and watch evictions-per-class, not just overall evictions.

Deep dive 3: hot keys and thundering herds

Hot keys

The estimate showed a key taking 10% of reads is already more than a node can serve. A consistent hash puts that key on exactly one node, so adding nodes does nothing. Options:

TechniqueHowCost
Local L1 cache in the clientKeep the hottest keys in the app server's memory for a second or twoStaleness of up to the L1 TTL; memory on every app server; works only when "slightly stale" is acceptable
Replicate the keyStore k#0..k#R-1 on different nodes; the client reads a random one; a write updates or invalidates allR times the memory for that key and R deletes per invalidation; briefly inconsistent copies
Read from replicasAllow reads of hot keys from the primary's replicasReplica lag; fits where replicas already exist
Detect and promoteSample request counts per key; automatically move a key to the L1 or replicated mode when it exceeds a thresholdA detection pipeline; but no one has to guess which keys are hot in advance

The order I would present: L1 for the few hottest keys (cheap, no cluster change), automatic detection to decide which, and key replication where staleness across copies is tolerable. Counters (such as a "likes" total) need a different trick: shard the counter into sub-counters and sum them on read, the same idea as in the rate limiter.

Thundering herds and leases

When a hot key expires or is deleted, every client that wants it misses at the same instant and all hit the database. This is the stampede of caching (try the simulator there). A lease is the fix that fits a shared cache: on a miss the cache hands one client a token that licenses the refill, and tells the others to wait or serves them a slightly stale value. The same token fixes a second race, the stale set, in which a slow reader fills the cache with a value the database has since replaced.

The idea

  1. get: hit → value; miss with leases → issue a token, others wait
  2. stampede: 1000 gets while the key is missing; count database reads
  3. stale set: reader misses and reads v1; writer sets v2 and deletes
  4. replay both with leases off and on; set(key, v1, token) must be refused
"""Two classic cache races, replayed deterministically, with and
without leases."""

# ── 1. A cache with optional leases ─────────────────────────────────
class Cache:
    """A lease is a token handed to ONE misser: only the holder may
    fill the key, and delete() cancels it."""

    def __init__(self, leases: bool):
        self.data = {}            # key -> cached value
        self.leases = leases      # are leases switched on?
        self.token_seq = 0        # source of fresh lease tokens
        self.live = {}            # key -> token of the live lease

    def get(self, key):
        if key in self.data:
            return ("hit", self.data[key])
        if not self.leases:
            return ("miss", None)
        if key in self.live:
            return ("wait", None)         # someone else holds the lease
        self.token_seq += 1
        self.live[key] = self.token_seq
        return ("miss", self.token_seq)   # you may refill

    def set(self, key, val, token=None):
        if self.leases and self.live.get(key) != token:
            return False                  # lease cancelled: stale fill
        self.data[key] = val
        self.live.pop(key, None)
        return True

    def delete(self, key):
        self.data.pop(key, None)
        self.live.pop(key, None)          # also kills any live lease

# ── 2. Race one: the stampede ───────────────────────────────────────
def stampede(leases, requests=1000):
    c = Cache(leases)
    db_reads = 0
    # All requests arrive while the key is still missing.
    results = [c.get("hot") for _ in range(requests)]
    for status, token in results:
        if status == "miss":
            db_reads += 1                 # each miss reads the database
            c.set("hot", "v1", token)
    return db_reads

# ── 3. Race two: the stale set ──────────────────────────────────────
def stale_set(leases):
    db = {"k": "v1"}
    c = Cache(leases)
    status, token = c.get("k")            # reader: miss
    value_read = db["k"]                  # reader reads v1 from the db
    db["k"] = "v2"                        # writer updates the database
    c.delete("k")                         # ...and invalidates the cache
    # The reader fills with what it read earlier (v1). Without a lease
    # this overwrites the invalidation and the cache stays wrong.
    ok = c.set("k", value_read, token)
    return c.data.get("k"), db["k"], ok

# ── 4. Replay both, with and without leases ─────────────────────────
for leases in (False, True):
    reads = stampede(leases)
    print(f"leases={leases!s:<5}  stampede: 1000 simultaneous misses "
          f"cause {reads:>4} database reads")
for leases in (False, True):
    cached, truth, ok = stale_set(leases)
    print(f"leases={leases!s:<5}  stale set: cache holds {cached!r}, "
          f"database holds {truth!r},")
    print(f"{'':14}reader's fill accepted: {ok}")
leases=False  stampede: 1000 simultaneous misses cause 1000 database reads
leases=True   stampede: 1000 simultaneous misses cause    1 database reads
leases=False  stale set: cache holds 'v1', database holds 'v2',
              reader's fill accepted: True
leases=True   stale set: cache holds None, database holds 'v2',
              reader's fill accepted: False

The first pair of lines is the herd: 1,000 simultaneous misses become one database read. The second pair is the race: a reader read v1, a writer changed the row to v2 and deleted the key, then the reader's slow fill arrives. Without a lease the cache keeps v1 indefinitely (until TTL); with one, the delete revoked the token and the fill is refused. Pair leases with other herd defences: jittered TTLs so keys do not expire in unison, early refresh of popular keys before they expire, and serving stale while one refill runs. These are the techniques the Facebook memcache case study describes at scale, and it is worth reading how much of that paper concerns exactly these small races.

Deep dive 4: consistency, regions and warm-up

Keeping the cache honest

The default pattern is cache-aside (read-through at the client): read the cache, on a miss read the database and fill; on a write, update the database and delete the cache entry. Deleting rather than updating matters because two concurrent writers can apply their cache updates in a different order from their database commits, leaving a stale value that no later event corrects.

Invalidation sourceHowWeakness
TTL onlyLet entries expireStaleness up to the TTL; short TTLs cost hit ratio
Application deletes after writeThe writing service deletes the key after committingIf it crashes between commit and delete, the entry is stale until TTL; every writer must remember
CDC-driven deletes (recommended)Tail the database's commit log; an invalidator deletes affected keysAn extra pipeline and lag of milliseconds to seconds; the mapping from row change to cache keys must be maintained
Write-throughThe cache layer writes the database and itselfCache becomes a write path; harder failure semantics; fine for a dedicated data-access service

CDC invalidation has a property the others lack: it works for any writer, including batch jobs, migrations and manual fixes, because it watches the database rather than trusting applications to remember (streams and CDC, the outbox is the application-side cousin). Keep TTL as the backstop: a lost event then becomes bounded staleness, not permanent staleness.

Cross-region caching

Give each region its own cache, filled from its nearest database copy. Writes go to the primary region. Each region's invalidator reads that region's change log, which is derived from its own (replicated) database. This ordering is the point: if the primary region deleted region B's key as soon as it wrote, B could miss, read its replica before the replica had applied the write, and cache the old value for a full TTL. Invalidating from the replica's own log makes that impossible. Reads in each region stay local at memory speed; the price is that a write is visible in remote regions after the replication delay (multi-region). Do not try to replicate cache contents across regions directly: you would ship the entire working set over the most expensive link you have to save misses that the local database can serve.

Cold start and warm-up

A new or restarted cache is empty, and an empty cache is a load test on your database. Our estimate has the database at 12k reads/s at a 99% hit ratio with a 20k ceiling, so a fully cold cluster (1.2M misses/s) would be about 60 times over it. Plan for it:

  • Do not restart everything at once. Roll node by node so each wave of misses is a small fraction of traffic; keep deploys from also changing the ring.
  • Warm a replacement before it takes traffic: replay recent keys from another region's cache or from a sampled access log, or copy a replica; or run the new node "shadowing" (receiving fills but serving no reads) for a while.
  • Add nodes gradually: a ring with virtual nodes can ramp the new node's weight upward.
  • Cap database concurrency with the lease and a rate limit on refills, so the worst case is slow pages, not a database outage (overload).
  • Persist what is expensive: if some entries take seconds to rebuild, snapshot them or keep them in a store designed to survive restarts.

Trade-offs & alternatives

  • Cache-aside versus write-through. We chose cache-aside with delete-on-write because it fails softly. If the cache were also the system of record (a Redis-as-database design), you would need persistence, synchronous replication and a different mental model.
  • Memory versus database headroom. A larger cache and replicas cost money; a bigger database costs money. The hit-ratio table in the estimate is how you price one against the other.
  • Freshness versus hit ratio. Longer TTLs and L1 caches raise the hit ratio and the staleness. If a use case needs read-your-writes, route that user's reads past the cache for a short time after their write.
  • If strong consistency were required, do not cache that data in a shared cache at all, or cache it with version checks against the database.
  • Where it breaks down: workloads with uniform, unique reads (no locality) get no value from the cache, only cost and complexity.

What a strong answer adds

  • Sizes the cluster from both memory and throughput and notes which one binds, including per-item overhead.
  • Connects the hit ratio to the database ceiling with a number, and says a node loss is a database-capacity question.
  • Knows consistent hashing is necessary but not sufficient, and names leases, a gutter pool or replicas as the complement.
  • Names both herd problems, the stampede and the stale-set race, and fixes them with the same mechanism.
  • Prefers delete over update on writes, CDC over hand-written invalidation, and keeps a TTL as the safety net.
  • Distinguishes hot keys from hot nodes and offers L1, key replication and detection, each with its staleness cost.
  • Invalidates each region from its own database copy.
  • Plans cold start explicitly: staged restarts, warm-up, refill limits.

Follow-up questions

Why not use write-through and keep the cache always correct?

Write-through still has two systems to update, so it needs a protocol for failure between the two writes, and it caches data that may never be read. It also does not help writers that bypass the cache layer. Cache-aside with CDC deletes has weaker freshness but simpler failure behaviour, and any writer is covered. Use write-through when a single data-access service owns all writes and read-your-writes is essential.

How would you resize the cluster from 40 to 60 nodes without hurting the database?

Add nodes with small ring weights and ramp them, so each step moves a small share of keys; warm each new node by shadowing before it serves reads; keep leases and refill limits on. With a ring, the new nodes take about 1/N of the keys each, but every moved key is a miss, so schedule the ramp in off-peak hours and watch hit ratio and database load between steps.

Memcached or Redis?

For a pure cache of simple values with huge fan-out, memcached's simplicity and multi-threading are attractive, and the design above fits it. Redis adds data structures, persistence and replication, useful when you need counters, sorted sets or failover, at the cost of a single-threaded core per instance (scale by running more instances) and more to operate. The choice follows the access pattern and the operational team, not fashion.

A deploy changes the serialisation format of cached values. What happens?

Old readers see new values and the reverse, or deserialisation fails and everything becomes a miss. Put a version in the key (profile:v4:...), deploy readers that accept both, switch writers, and let the old keys age out. Treat the cached format as a public contract (evolving contracts).

How do you cache a personalised page?

Usually do not cache the whole page. Cache the shared fragments (the product data, the rendered recommendations list) under keys without the user id, and assemble the personal parts per request. Per-user keys are only worth it if the same user re-requests soon, and they multiply memory by the user count, which our estimate can tell you before you commit.

How would you know the cache is actually helping?

Measure hit ratio per namespace, database load with and without (a canary that bypasses the cache for 1% of reads), and latency. A cache with a 60% hit ratio on an inexpensive query may cost more than it saves in complexity. Evaluate by the load removed from the database, not by the hit ratio alone.

Distributed systems connection

The stale-set race is an ordering problem: the cache sees events (fill, delete) in a different order from the database. Leases are a small instance of a token that rejects stale actors, the same idea as fencing tokens. Cross-region invalidation from the local replica's log is a consequence of asynchronous replication, and the whole design leans on the consistency models in consistency models: the cache gives you bounded staleness, never linearizability.

Key takeaways

  • Size from memory and throughput; per-item overhead and allocator waste are a real share of the memory, and the hit ratio is a capacity number for the database.
  • Consistent hashing keeps node changes to about 1/N of the keys, but one node loss can still overload the database, so add leases, a gutter pool or replicas.
  • Route with a smart client first and a proxy tier when connections and fleet policy demand it.
  • Frequency-aware eviction beats plain LRU on skewed and scan-polluted workloads; measure, because size gains diminish.
  • Hot keys defeat sharding: use an L1 cache, key replication and automatic detection.
  • Leases fix both the thundering herd and the stale-set race.
  • On writes, update the database and delete the key, driven by CDC, with a TTL as the backstop; invalidate each region from its own database copy.
  • A cold cache is a load test on the database: stage restarts, warm new nodes, and cap refills.

Check your understanding

Why does modulo hashing (hash(key) % N) make resizing a cache cluster dangerous?

  1. It cannot hash strings
  2. Changing N remaps almost every key, so nearly everything misses at once and the database takes the surge
  3. It requires replicas
  4. It is slower than a ring
In the measurement about 97% of keys changed owner when one node was added. A consistent-hash ring moves about 1/N.

Your estimate says one key receives 10% of all reads, which is more than one node's rough throughput. What helps?

  1. Add more nodes to the ring
  2. Serve that key from per-client L1 caches and/or replicate it under several key names
  3. Increase the TTL to one day
  4. Switch to modulo hashing
A key lives on one node regardless of cluster size, so the only options spread that key's reads: local caches, copies on several nodes, or replicas.

What does a lease token in the cache protect against, besides a thundering herd?

  1. Network partitions
  2. A slow reader filling the cache with an old value after a writer has deleted the key
  3. Memory fragmentation
  4. Hash collisions
Deleting the key revokes outstanding leases, so the late fill is rejected. Without it the stale value could remain until its TTL.

On a database write, why is deleting the cache key usually better than updating it?

  1. Deleting is faster over the network
  2. Two concurrent writers can apply cache updates in a different order than their database commits, leaving a stale value; a delete just forces a fresh read
  3. Caches cannot store updated values
  4. Updates break consistent hashing
A delete is idempotent and order-insensitive; the next read repopulates from the source of truth.

Region B's cache is invalidated by a message from the primary region at write time. What can go wrong?

  1. Nothing, since the key is deleted
  2. B may re-fill from its replica before the replica has applied the write, and then hold the old value for a full TTL
  3. The message will be delivered twice
  4. The cache will run out of memory
Invalidate from the local replica's change log so that the delete always follows the replicated write.

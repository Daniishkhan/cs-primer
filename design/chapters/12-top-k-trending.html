Design Top-K & Trending

Heavy hitters over streams, count-min sketches, windows and approximate answers. The question "what is popular right now?" sounds like a sorted list, and is really a question about how much accuracy you can afford to give up for a bounded amount of memory, and where in the pipeline you are allowed to give it up.

Why this matters

Top-k is the clean case of approximation as an engineering tool. The exact answer needs state proportional to the number of distinct keys, which grows with the long tail and multiplies with every window and dimension. A sketch needs a fixed amount of memory, with a provable error you choose in advance. The same ideas run under ad-click counting, rate limiting by heavy user, network monitoring, trending topics, "most viewed" lists and cardinality dashboards, and they teach a skill that senior designs depend on: stating how wrong an answer is allowed to be, and proving the system stays inside it.

The problem

"Show the top 10 trending hashtags (or most-viewed videos) right now, globally and per country, refreshed every minute."

Three words need pinning down. "Top" by what: raw count, distinct users, or growth? "Right now": the last hour, the last five minutes, or a smoothly fading score? And how accurate must it be? A user does not care whether a hashtag has 1,204,311 or 1,204,398 uses; they care whether the list is sensible, fresh and not manipulated. Those answers set the whole design, via the framework.

Clarify requirements

QuestionAssumed answer
Event volume?500,000 events per second at peak (views, tweets, searches), arriving from many producers.

Functional. Ingest events; maintain top-k and counts per scope and window; serve the lists; report approximate distinct viewers; allow a correction pass.

Non-functional. Bounded memory independent of the number of distinct keys; documented error bound; no single hot key can stall the pipeline; survives processor crashes without wildly wrong output; serving is a cache read.

Out of scope. Billing-grade counts (those must be exact and reconciled, see the ad click aggregator studio), personalised trends, and the downstream search integration (chapter 11 uses these counts for its trending overlay).

Estimate

This estimate is about state, not QPS. The script compares what exact counting needs with what sketches need, and derives sketch dimensions from the error you want. Method: chapter 2.

The idea

  1. events ← events/s × 3600; exact bytes ← distinct keys × 40 B
  2. w ← ceil(e ÷ eps); d ← ceil(ln(1 ÷ delta)); size ← w × d × 4 B
  3. overcount ← eps × events, against a 1M-event and a 10k-event key
  4. HLL(p): m ← 2^p registers × 6 bits; std error ← 1.04 ÷ sqrt(m)
  5. exact sliding ← keys × 40 B × 60 buckets; compare with sketch × 60

Reading the output. A single exact hour of counts is about 8 GB for 200 million keys. That is not impossible; it is a few machines. Exact counting becomes expensive when the problem multiplies: a sliding window kept as 60 one-minute buckets needs about 48 GB at 20 million keys per minute, a per-region split adds more, and per-key distinct-viewer sets would add terabytes. A count-min sketch of 0.5 MB per bucket covers the same ground in tens of megabytes per partition. That is the honest case for sketches: not that exact is infeasible at one scale, but that it grows with the tail, the window and the number of slices, while a sketch does not.

The second lesson is in the error column. With ε = 0.0001 and an hour of 1.8 billion events, the worst-case overcount is 180,000. A key with a million events is within 18% in the worst case, but a key with 10,000 events could look 19 times bigger. So the sketch is trustworthy for the head and untrustworthy for the tail, which is exactly the part of the distribution we want it for. And last, HyperLogLog gives distinct counts in 3 KB per key, but 3 KB for every key is 0.6 TB, so distinct counts are kept only for the few thousand candidate keys that might reach the list, about 31 MB.

API

-- Ingest (internal, batched; at-least-once)
POST /internal/events
  [ { "key": "#worldcup", "region": "BR", "user": "u81…",
      "ts": 1760000000 }, … ]

-- Read
GET /v1/trending?scope=global|region:BR&window=1h&k=10
                &by=count|users|rising
  -> 200 { "as_of": "2026-10-13T10:41:00Z",
           "items": [ { "key": "#worldcup", "count": 1204311,
                        "count_error_max": 180000,
                        "viewers": 402113, "rank": 1 }, … ] }
  • Approximation is part of the contract. The response carries as_of and an error bound. Clients (and your own dashboards) should not treat the numbers as exact, and the bound is what lets a data consumer decide whether to trust a gap between rank 9 and rank 10.
  • Events are batched and carry a timestamp. The event time, not arrival time, decides the window. Producers retry, so delivery is at-least-once (see failure modes).
  • The read is a cache lookup. The lists are tiny (ten items per scope per window) and change once a minute. Everything expensive happens before the read.

Data model

  • Event log (partitioned, durable, replayable): events partitioned by a hash of the key. All events for a key land on one partition, which is what lets partition-local counts be exact for that key (Deep dive 4).
  • Per-partition window state (in the stream processor, checkpointed): for each minute bucket, a count-min sketch plus a small structure of candidate heavy keys (a heap or Space-Saving counters), and for candidates, a HyperLogLog of distinct users.
  • Merged results (serving cache): trending:{scope}:{window}:{by} → list of items with counts, error bounds and as_of.
  • Raw history (data lake): the same events kept for exact recounts, backfills and audit.

Note what is not stored: a counter for every key. The sketch's memory is set by (ε, δ), not by the number of keys.

High-level design

The streaming path is fast and approximate; the batch path is slow and exact. Following one event through the fast path:

Step through

From one event to a trending list

  1. Event. A view of #x is appended to the log partition chosen by hash(key), so every event for one key goes to the same processor.
  2. Count approximately. The processor hashes the key with each of the sketch's d hash functions and increments one counter in each row of the current minute's sketch. It then reads the key's estimate (the minimum over rows) and offers it to a heap that keeps the top candidates. A HyperLogLog update records the user, for candidates only.
  3. Seal the bucket. When the minute ends (by event time, with a small allowance for late events) the bucket is sealed and no longer changes.
  4. Ship. The processor sends the sealed sketch and its candidate keys to the merger. Both are small and fixed-size.
  5. Merge. Sketches from all partitions add cell by cell. The merger takes the union of candidate keys and estimates each from the merged sketch, then ranks them.
  6. Slide and publish. The window's sketch is the sum of its last 60 minute-buckets: add the new one and subtract the one that just expired. The merger writes the new top-k lists to the cache with a fresh as_of.
  7. Correct later. An hourly batch job recounts exactly from the raw events in the lake and corrects the cached values and ranks of the head, and is also the source of truth for audits and backfills.

Deep dive 1: exact versus approximate counting

Start with the exact approach, because it is the baseline you must beat and the fallback when you are unsure. Keep a hash map from key to count, per window; for the top-k, either scan at the end, or maintain a sorted structure (a sorted set with increment, or a heap with lazy deletion). It is simple, exact, and easy to debug. It fails in these ways: memory grows with distinct keys (the long tail dominates), a sliding window multiplies the state by the number of buckets, splitting by region or category multiplies it again, and distributed counting needs a shuffle of every key to its owner. Per-event cost is cheap; it is state and its merging that hurt.

Pick by the question. "How many times has this key occurred?" is a frequency question for a count-min sketch. "Which keys are the most frequent?" is a heavy-hitter question for Misra-Gries or Space-Saving, or a sketch plus a heap of candidates. "How many different users?" is cardinality, for HyperLogLog. These are different problems with different structures, and a strong answer does not use one where another is needed. A count-min sketch alone cannot list its heavy keys: it only answers queries for keys you ask about, so you pair it with a candidate structure.

Deep dive 2: the sketches, with their guarantees

Count-Min sketch

The count-min sketch, by Cormode and Muthukrishnan (presented at LATIN 2004 and published in the Journal of Algorithms in 2005), is a d × w array of counters with d independent hash functions, each mapping a key to a column in its row. To add a key, increment its cell in every row. To estimate, take the minimum of its d cells. Collisions only ever add, so every cell is at least the true count and the minimum is the least-polluted one: the estimate never undercounts.

The error bound comes from choosing the dimensions. For non-negative counts with total stream weight N, set

w = ceil(e / ε)          d = ceil(ln(1 / δ))

true(x)  <=  estimate(x)  <=  true(x) + ε·N      with probability at least 1 − δ

Here is why those formulas work, so that you can reconstruct them rather than recall them. In one row, a given key collides with each of the other N events with probability about 1/w (a pairwise-independent hash), so the expected extra count in its cell is at most N/w, which is εN/e when w = e/ε. By Markov's inequality, the chance that one row overshoots by more than εN is at most 1/e. The estimate is wrong by more than εN only if all d rows overshoot, and with independent rows that has probability at most e−d, which is at most δ when d = ln(1/δ). So ε controls the width (the error), δ controls the depth (the confidence), and memory grows like (1/ε)·ln(1/δ): halving the error doubles the width; being a hundred times more confident adds only about five rows.

Two honest cautions. The bound is on the error relative to the total stream weight N, not relative to the key's own count, so small keys can look large (that was the 19× in the estimate). And the sketch is a worst-case guarantee: on skewed data the observed error is usually far smaller. Both facts show up in the run below, where we build a sketch with ε = 0.001, δ = 0.01 over a million Zipf-distributed events, keep a heap of the 10 best candidates, and compare with exact counts.

The idea

  1. CountMin: d rows × w counters; estimate ← min over rows of row[hash(x)]
  2. HeapTopK: min-heap of (estimate, key); evict the min for a bigger key
  3. Misra-Gries, Space-Saving: fixed counters, decrement or evict when full
  4. for each event: add(x), offer(x, estimate(x)); compare with exact
  5. merge: sketch(A) + sketch(B), counters added, equals sketch(A ∪ B)
  6. Misra-Gries undercount ≤ N ÷ k; Space-Saving overcount ≤ N ÷ m
"""Count-Min sketch + heap top-k versus exact counts on a Zipf stream;
the (eps, delta) bound; merging; Misra-Gries and Space-Saving."""
import heapq
import math
import random
from collections import Counter
from itertools import accumulate

# Prime for the pairwise-independent hash family (a*x + b) mod P.
P = (1 << 61) - 1


# ── 1. Count-Min sketch ───────────────────────────────────────────────
class CountMin:
    def __init__(self, eps, delta, seed=1):
        self.w = math.ceil(math.e / eps)        # width: bounds the error
        self.d = math.ceil(math.log(1 / delta)) # depth: bounds failure
        rng = random.Random(seed)
        # One (a, b) hash function per row.
        self.ab = [(rng.randrange(1, P), rng.randrange(P))
                   for _ in range(self.d)]
        self.t = [[0] * self.w for _ in range(self.d)]
        self.n = 0                              # total events added

    def _col(self, x, a, b):
        return ((a * x + b) % P) % self.w

    def add(self, x, c=1):
        self.n += c
        for row, (a, b) in zip(self.t, self.ab):
            row[self._col(x, a, b)] += c

    def estimate(self, x):
        # Collisions only ever add, so the smallest row is the least
        # inflated: the estimate never undercounts.
        return min(row[self._col(x, a, b)]
                   for row, (a, b) in zip(self.t, self.ab))

    def merge(self, other):
        """Same shape and same hashes: the counters just add."""
        assert self.ab == other.ab and self.w == other.w
        out = CountMin.__new__(CountMin)
        out.w = self.w
        out.d = self.d
        out.ab = self.ab
        out.n = self.n + other.n
        out.t = [[x + y for x, y in zip(r1, r2)]
                 for r1, r2 in zip(self.t, other.t)]
        return out


# ── 2. Heap that tracks the top-k keys ────────────────────────────────
class HeapTopK:
    """Keeps the K keys with the largest sketch estimates.

    Stale heap entries (a key whose estimate has since grown) are
    skipped lazily, which avoids an O(k) decrease-key operation.
    """

    def __init__(self, k):
        self.k = k
        self.heap = []          # min-heap of (estimate, key)
        self.member = {}        # key -> its current estimate

    def _set(self, key, est):
        self.member[key] = est
        heapq.heappush(self.heap, (est, key))

    def offer(self, key, est):
        if key in self.member:
            self._set(key, est)
            return
        if len(self.member) < self.k:
            self._set(key, est)
            return
        # Drop stale entries until the heap top is a live minimum.
        while self.heap[0][0] != self.member.get(self.heap[0][1]):
            heapq.heappop(self.heap)
        if est > self.heap[0][0]:
            _, old = heapq.heappop(self.heap)
            del self.member[old]
            self._set(key, est)

    def top(self):
        return sorted(self.member.items(), key=lambda t: -t[1])


# ── 3. Counter-based alternatives ─────────────────────────────────────
def zipf_stream(n_keys, n_events, s, seed):
    rng = random.Random(seed)
    cum = list(accumulate(1 / (i ** s) for i in range(1, n_keys + 1)))
    return rng.choices(range(1, n_keys + 1), cum_weights=cum, k=n_events)


def misra_gries(stream, k):
    """At most k-1 counters; a key not in the table decrements them all."""
    c = {}
    for x in stream:
        if x in c:
            c[x] += 1
        elif len(c) < k - 1:
            c[x] = 1
        else:
            for key in list(c):
                c[key] -= 1
                if c[key] == 0:
                    del c[key]
    return c


def space_saving(stream, m):
    """m counters. A new key evicts the minimum counter and inherits
    its count (+1), remembering that inherited part as the error."""
    count = {}
    err = {}
    heap = []
    for x in stream:
        if x in count:
            count[x] += 1
            heapq.heappush(heap, (count[x], x))
        elif len(count) < m:
            count[x] = 1
            err[x] = 0
            heapq.heappush(heap, (1, x))
        else:
            while heap[0][0] != count.get(heap[0][1]):
                heapq.heappop(heap)             # stale entry
            low, victim = heapq.heappop(heap)
            del count[victim]
            del err[victim]
            count[x] = low + 1
            err[x] = low
            heapq.heappush(heap, (low + 1, x))
    return count, err


# ── 4. Run the sketch against exact counts ────────────────────────────
N_KEYS = 100_000
N      = 1_000_000              # events in the stream
K      = 10                     # size of the trending list
stream = zipf_stream(N_KEYS, N, 1.1, seed=42)
exact  = Counter(stream)
eps    = 0.001
delta  = 0.01
cms  = CountMin(eps, delta)
topk = HeapTopK(K)
for x in stream:
    cms.add(x)
    topk.offer(x, cms.estimate(x))

counters = cms.d * cms.w
print(f"stream: {N:,} events over {len(exact):,} distinct keys "
      f"(Zipf s=1.1)")
print(f"exact counter: {len(exact):,} entries; "
      f"sketch: {cms.d} x {cms.w} = {counters:,} counters")
print(f"  (eps={eps}, delta={delta})")
print(f"\n{'rank':<5}{'key':>7}{'exact':>9}{'sketch':>9}{'error':>8}")

    print(f"{r:<5}{key:>7}{exact[key]:>9}{est:>9}{est - exact[key]:>+8}")

print(f"\nheap top-{K} matches exact top-{K}: {hits}/{K} keys")

# The (eps, delta) guarantee: overcount <= eps*N for at least 1-delta
# of keys, and never an undercount.
bound = eps * N
over_by = {key: cms.estimate(key) - exact[key] for key in exact}
bad = sum(1 for e in over_by.values() if e > bound)
under = sum(1 for e in over_by.values() if e < 0)
print(f"\nguarantee check over all {len(exact):,} keys: "
      f"allowed overcount eps*N = {bound:,.0f}")
print(f"  keys over the bound: {bad} ({bad / len(exact):.3%}, "
      f"allowed <= {delta:.0%});")
print(f"  keys undercounted: {under} (must be 0)")
errs = sorted(over_by.values())
print(f"  overcount: median {errs[len(errs) // 2]}, "
      f"p99 {errs[int(len(errs) * .99)]}, max {errs[-1]}")

# ── 5. Merge: two partitions, one answer ──────────────────────────────
# Each partition sketches half of the stream; the sum of the two
# equals the sketch of the whole stream, counter for counter.
a = CountMin(eps, delta)
b = CountMin(eps, delta)
for x in stream[: N // 2]:
    a.add(x)
for x in stream[N // 2:]:
    b.add(x)
m = a.merge(b)
print(f"\nmerge of two half-stream sketches equals the single sketch: "
      f"{m.t == cms.t}")

# ── 6. Misra-Gries and Space-Saving ───────────────────────────────────
# Misra-Gries with k counters: deterministic, undercounts by <= N/k.
k = 100
mg = misra_gries(stream, k)
worst = max(exact[key] - mg.get(key, 0) for key in exact)
top_mg = sorted(mg.items(), key=lambda t: -t[1])[:5]
print(f"\nMisra-Gries with k={k} (at most {k - 1} counters): "
      f"worst undercount {worst:,} <= N/k = {N // k:,};")
print(f"  top-5 {top_mg}")
print(f"  exact top-5 {exact.most_common(5)}")

# Space-Saving with 100 counters: never undercounts;
# count - err <= true <= count, and the error is at most N/m.
ss, ss_err = space_saving(stream, 100)

Heavy hitters: Misra-Gries and Space-Saving

A heavy-hitter summary keeps a small set of candidate keys and their counts, with a guarantee that any key above a frequency threshold is in the set. Misra-Gries (J. Misra and D. Gries, "Finding repeated elements", Science of Computer Programming, 1982; the same algorithm was independently rediscovered in the early 2000s, so you will also see it under other authors' names) keeps k − 1 counters. On a key already tracked, increment it; on a new key with a free slot, start it at 1; otherwise decrement every counter by one and drop zeros. Each decrement round discards k events, so there are at most N/k rounds and every count is an underestimate by at most N/k. Any key with more than N/k occurrences survives.

Space-Saving (A. Metwally, D. Agrawal and A. El Abbadi, "Efficient computation of frequent and top-k elements in data streams", ICDT 2005) keeps m counters of (key, count, error). A tracked key is incremented; a new key evicts the counter with the smallest count, inherits that count plus one, and records the old count as its possible error. So its counts only overestimate (count − error ≤ true ≤ count), each overestimate is at most the minimum count, which is at most N/m, and any key with true frequency above N/m is always tracked. Later analysis showed the two algorithms are isomorphic, both can be merged across partitions while keeping their guarantees (Agarwal, Cormode, Huang, Phillips, Wei and Yi, "Mergeable summaries", PODS 2012), and the run above shows the symmetry: the worst Misra-Gries undercount and the worst Space-Saving overcount are the same number, 7,037, because the Space-Saving count is the Misra-Gries count plus the current minimum.

Which to use? For a trending list, Space-Saving is the natural choice: it gives you the top-k with a per-item error you can show or use ("this count is within 300"), in a fixed number of counters, and handles the heap-of-candidates role without a separate structure. Use a count-min sketch when you also need frequency estimates for keys outside the top (for example to check a specific key), or the subtract-to-slide property.

HyperLogLog for distinct counts

Counting distinct users per key exactly needs a set per key. HyperLogLog (P. Flajolet, É. Fusy, O. Gandouet and F. Meunier, "HyperLogLog: the analysis of a near-optimal cardinality estimation algorithm", 2007) estimates cardinality from the observation that among n random hash values the longest run of leading zeros is about log2 n. It hashes each item, uses the first p bits to pick one of m = 2p registers, and stores in that register the largest "position of the first 1 bit" seen in the remaining bits. The estimate combines the registers with a harmonic mean, which tames the outliers that a single maximum would produce. The standard error is about 1.04/√m (the paper's constant is √(3 ln 2 − 1) ≈ 1.039): m = 4,096 registers, a few kilobytes, gives about 1.6%, independent of how many items were counted. Run it, and compare the measured error with the formula:

The idea

  1. add(h): idx ← top p bits; reg[idx] ← max(reg[idx], leading zeros + 1)
  2. estimate ← alpha × m² ÷ sum(2^−reg); 40 trials per p vs 1.04 ÷ sqrt(m)
  3. merge ← register-wise max; must equal the sketch of the union
"""HyperLogLog from scratch: m = 2^p registers, harmonic mean, and the
empirical standard error versus 1.04/sqrt(m)."""
import math
import random


# ── 1. The sketch ─────────────────────────────────────────────────────
class HLL:
    def __init__(self, p):
        self.p = p                      # bits used to pick a register
        self.m = 1 << p                 # number of registers
        self.reg = [0] * self.m
        # Bias-correction constant from the paper, for m >= 128.
        self.alpha = 0.7213 / (1 + 1.079 / self.m)

    def add_hash(self, h):
        """h: a uniformly random 64-bit integer."""
        idx = h >> (64 - self.p)        # first p bits choose the register
        rest = h & ((1 << (64 - self.p)) - 1)
        # rho = position of the leftmost 1 in the remaining bits. A rare
        # long run of leading zeros hints at a large set.
        rho = (64 - self.p) - rest.bit_length() + 1
        if rho > self.reg[idx]:
            self.reg[idx] = rho

    def estimate(self):
        # Harmonic mean across registers damps outlier registers.
        total = sum(2.0 ** -r for r in self.reg)
        e = self.alpha * self.m * self.m / total
        zeros = self.reg.count(0)
        if e <= 2.5 * self.m and zeros:
            # Small-range correction: linear counting.
            return self.m * math.log(self.m / zeros)
        return e

    def merge(self, other):
        """Register-wise max: the sketch of the union of both sets."""
        out = HLL(self.p)
        out.reg = [max(a, b) for a, b in zip(self.reg, other.reg)]
        return out


# ── 2. Empirical error versus the 1.04/sqrt(m) formula ────────────────
rng = random.Random(5)
print(f"{'p':>3}{'m':>7}{'true n':>10}{'mean est':>11}"
      f"{'empirical std err':>20}{'1.04/sqrt(m)':>14}")
for p in (8, 10, 12):
    for n in (50_000,):
        ests = []
        for _ in range(40):             # 40 independent trials
            h = HLL(p)
            for _ in range(n):
                h.add_hash(rng.getrandbits(64))
            ests.append(h.estimate())
        mean = sum(ests) / len(ests)
        rms = math.sqrt(sum((e - n) ** 2 for e in ests) / len(ests))
        sd = rms / n
        theory = 1.04 / math.sqrt(1 << p)
        print(f"{p:>3}{1 << p:>7}{n:>10,}{mean:>11,.0f}"
              f"{sd:>19.2%}{theory:>14.2%}")

# ── 3. Merge: the union of two overlapping sets ───────────────────────
# Counted without keeping either set: only the registers are merged.
universe = [rng.getrandbits(64) for _ in range(30_000)]
a = HLL(12)
b = HLL(12)
whole = HLL(12)                         # reference: sketch of the union
for h in universe[:20_000]:
    a.add_hash(h)
    whole.add_hash(h)
for h in universe[10_000:]:
    b.add_hash(h)
    whole.add_hash(h)

merged = a.merge(b)
print("\nset A 20,000, set B 20,000, overlap 10,000, true union 30,000")
print(f"  merged estimate {merged.estimate():,.0f}; "
      f"single sketch of the union {whole.estimate():,.0f};")
print(f"  merge == union sketch: {merged.reg == whole.reg}")

  8    256    50,000     50,166              6.90%         6.50%

The measured errors (6.9%, 3.8%, 1.8%) sit a little above the formula (6.5%, 3.3%, 1.6%): the formula is asymptotic, and 40 trials per row is a small sample; the order of magnitude and the 1/√m scaling are what to take away. The last block shows why HyperLogLog suits a distributed pipeline: the union of two sets is estimated by the register-wise maximum, with no need to know the overlap. That is what lets you count distinct viewers per hour from sixty one-minute sketches without double counting someone who watched in several minutes. Production implementations add refinements for small and large cardinalities; the version here includes only the small-range correction because that is all this experiment needs.

For the headline "last hour" list, use bucketed sliding windows: one-minute buckets, 60 of them. Popular is not the same as trending

Counted over any window, the top of the list is always the same giants: the keys that are always popular. "Trending" means unusually high compared with what is normal for that key. Practical approaches: compare the current short-window rate with a long-run baseline for the same key (a ratio, or a standardised difference against its recent variability); require a minimum absolute count so that a key that went from 2 to 20 does not outrank a major story; and rank by distinct users, not raw events, so that a single script or a small group repeating an action cannot dominate. This is where HyperLogLog sits in the design: a distinct-user estimate for the few thousand candidates, not for every key. The scoring formula is a product decision; make it configuration with an experiment framework, and show the underlying counts so reviewers can sanity-check outcomes.

Event time, late events and duplicates

Window by the event time in the record, not arrival time, or an outage that delays events by ten minutes distorts the list. Choose how long to wait for stragglers (a watermark, say two minutes past the bucket end) and what to do with later ones: drop them from the streaming path, since the batch recount will include them. Producers retry, so the same event may arrive twice; for approximate counts, a small overcount is usually acceptable, and where it is not, deduplicate by event id within a short window or rely on the batch recount. The stream mechanics are in streams and CDC.

The default is key-hash partitioning with a combiner: each upstream node aggregates its own events for a second or two (a small map or a local sketch) before the shuffle, so a viral key arrives as thousands of increments of a large number, not millions of increments of one. That is the same two-phase aggregation as map-reduce (batch processing). If a single key is still too hot for one partition, salt it (key#0..#7) so eight partitions each count a share, and add the shares when merging, the technique from the rate limiter's hot keys and the cache's hot counters.

Merging across partitions

This is where the earlier choice of mergeable structures pays off. To produce the global list the merger receives, per partition and minute: a count-min sketch (add the arrays cell by cell), a set of candidate keys (take the union), optionally Space-Saving summaries (merge by adding counts for common keys, then reduce back to m counters by subtracting the (m+1)-th largest count from every counter and dropping those that reach zero, per the mergeable-summaries construction), and HyperLogLog sketches (take the register-wise maximum). All of these combine without any pass over the raw data. Constraints to enforce: every partition must use the same hash seeds and dimensions (carry a sketch version in the payload and reject mismatches), and remember that a merged count-min sketch is exactly the sketch of the combined stream (merging adds no error), so its bound is stated against the combined total weight N, which grows as you merge more partitions. A merge tree (partitions into regions, regions into global) keeps the merger from becoming a bottleneck, and regional lists reuse the regional merge results.

Lambda or kappa?

The architecture has a fast approximate path and a slow exact one. That is the lambda pattern: a batch layer (exact, comprehensive, hours behind) and a speed layer (approximate, minutes behind), with a serving layer that prefers batch results when they exist. It buys correctness and a safety net, and costs two code paths that must compute the same thing, a classic source of drift. The kappa alternative has a single streaming pipeline over a replayable log: to recompute, you reprocess the log from an earlier offset with the new logic. It is simpler to maintain, and it requires the log to be retained long enough and the stream engine to handle bulk replay at speed (streams and CDC, batch).

Recommendation for trending: a kappa-style streaming path for the live list (it is approximate by nature, and the sketch code is the only code), plus a thin batch recount of the head keys as a verifier and for audit, not as a second implementation of the full pipeline. If the numbers fed billing, I would reverse the emphasis and make the exact batch path authoritative.

Trade-offs & alternatives

  • Memory versus accuracy. We pick ε and δ and accept an additive error against total weight. Halving ε doubles memory. If all keys needed tight relative error, including the tail, sketches would be the wrong tool and exact counting (sharded) the right one.
  • Count-Min versus Space-Saving. Count-Min answers any key and subtracts for sliding windows; Space-Saving lists the top keys with per-item error and no separate heap. Many systems use both: Space-Saving for the list, count-min for spot checks.
  • Exact exists at modest scale. A sorted set with increment per scope serves a smaller product perfectly well. Introduce sketches when state per window, per slice and per distinct-set stops fitting, not before.
  • If the list drove money (ad ranking, billing), approximate counts are unacceptable at the point of settlement: use the exact path and reconcile (ad click aggregator).
  • If real-time mattered more than accuracy, shorten the buckets and shrink the watermark, accepting more late-event loss; if accuracy mattered more, widen both.
  • Where it breaks down. Adversarial streams can target a known hash family; seed hashes secretly and rotate them. Keys that appear once never rank, so "emerging" topics need a separate novelty detector, and keys with many spellings need normalisation upstream.

Follow-up questions

How would you choose ε and δ?

Work backwards from the smallest count you must distinguish. If the 10th key on the list has about 100,000 events in the window and you want errors under 1% of that, you need εN ≤ 1,000, so ε = 1,000/N. For N = 1.8 billion that is about 5×10−7, a very wide sketch (several million columns), or you shorten the window or partition by region so N per sketch is smaller. δ is cheap: 0.01 means 5 rows, 0.0001 means 10. In practice use Space-Saving for the head, where the error is N/m per partition, and size m the same way.

Why does the count-min sketch never undercount, and when would it?

Every update increments exactly one cell per row, and collisions only add, so each cell is at least the key's true count and so is their minimum. It can undercount if you allow decrements that are not matched to earlier increments (negative updates break the one-sided guarantee and the Markov argument), or if you merge sketches built with different hash functions. Subtracting an expired bucket is safe only because it removes exactly what was added.

How do you get the top-10 per region without 50 times the cost?

Do not run 50 independent pipelines. Partition by key hash, keep a sketch per (region, minute) only for candidate keys, or key the sketch by a (region, key) pair so regional counts are separate cells in the same structure. The global list is the merge of the regional sketches (they add), so regions are slices of one computation. Small regions can use a smaller ε because their N is smaller.

How would you detect a coordinated attempt to manipulate the list?

Look at the structure of the growth, not just the rate: a new key whose distinct-user count rises much more slowly than its event count (few accounts, many events), uniform timing, accounts with similar creation dates, or a sudden jump from near zero. Use distinct users as the ranking input, cap the per-user contribution, and hold suspicious keys for review. Keep the mechanism private, since publishing the exact rule invites adaptation.

What changes if the window is 24 hours instead of one hour?

Buckets become coarser (for example 10-minute buckets), N grows by 24 so ε must shrink or the error bound gets 24 times larger in absolute terms, and the exact recount becomes a heavy daily batch job. A two-level scheme helps: minute buckets for the last hour, hourly sketches for the older 23, merged on demand.

Could you do all this with Redis sorted sets?

Yes at moderate scale: one sorted set per scope and window with ZINCRBY per event and ZREVRANGE for the list, rotated per bucket. It is exact and simple, and a good first version. It stops fitting when the per-window key count exceeds a node's memory, when increments per second exceed what one shard handles (a hot key is one sorted-set member, so key hashing does not help), or when you need sliding windows across many buckets. At that point the sketches and partitioned pipeline above take over.

Distributed systems connection

Mergeability is what makes a summary distributable: it turns a global computation into local computations plus a cheap combine, the same property that makes CRDTs and counters convergent (CRDTs): count-min addition and HyperLogLog's register-wise maximum are both commutative and associative, so merge order does not matter. Only the maximum is idempotent, though: merging the same HyperLogLog twice is harmless, while merging the same count-min sketch twice double counts, so duplicate merges are the thing to guard against. The lambda and kappa patterns are the log-based architectures of logs and exactly-once.

Key takeaways

  • Exact counting state grows with distinct keys, windows and slices; a sketch has fixed size and a stated error. Choose by multiplying the exact state out, not by reflex.
  • Count-Min: w = ⌈e/ε⌉ columns, d = ⌈ln(1/δ)⌉ rows; the estimate never undercounts and overshoots by at most ε·N with probability at least 1 − δ. The error is against the total N, so trust the head, not the tail.
  • A count-min sketch cannot list its keys; pair it with a heap, or use Space-Saving (Metwally, Agrawal, El Abbadi 2005), whose counts are bounded by N/m. Misra-Gries (1982) is its underestimating twin.
  • HyperLogLog counts distinct items with standard error about 1.04/√m in a few kilobytes and merges by register-wise maximum; keep it only for candidate keys.
  • Sliding windows are sums of small buckets: add the newest, subtract the oldest. Decay gives a smooth alternative. "Trending" is growth against a baseline, not raw popularity.
  • Partition by key hash with local combiners, salt a key that is still too hot, and merge sketches with identical seeds and dimensions.
  • Run a fast approximate streaming path with a slow exact recount beside it, measure their disagreement, and make the exact path authoritative whenever money is involved.

Design Unique ID Generation

UUIDs, ticket servers, Snowflake-style 64-bit layouts, ordering and what happens when a clock goes backwards. Handing out unique numbers without asking anyone is the smallest problem in this course with a genuinely hard core: coordination, time and trust.

Why this matters

Every record needs an identity, and the choice is quietly load-bearing: it sets index size and insert locality, whether you can sort by creation time without a second column, how you can shard later, and what an outsider learns by looking at your URLs. It is also a compact tour of the fundamental tension in distributed systems: you want unique values without talking to anyone, and the only things you can trust not to talk back are the clock and your own luck.

The problem

"Design a service that generates unique IDs for our records: posts, orders, messages. We are moving from one database to many."

The trigger is in the second sentence. With one database, AUTO_INCREMENT was fine. With many writers, a single counter is a bottleneck and a single point of failure, and per-database counters collide.

Clarify requirements

Functional. Produce unique, mostly-sorted, compact ids; allow extracting the creation time; support batches. Non-functional. Generation in microseconds; survive instance restarts and clock trouble without duplicates; no single point of failure. Out of scope. Gap-free sequences (invoice numbers with legal rules need a different design), human-friendly short codes (see the key analysis in chapter 1), and ordering across services.

Estimate

Three questions: how many bits does the id need for this volume and lifetime, what does the layout cost in the other fields, and what does the id's size do to storage? The first is a count; the rest are the capacity of a layout.

Reading it: ten years at 50,000 ids/s is about 1.6 x 1013, which fits in 44 bits as a plain counter, so a 64-bit id has plenty of room. The classic 41/10/12 layout gives 69.7 years of timestamps, 1,024 workers, and 4,096 ids per millisecond per worker. That is 4.1 million per second per worker against our 150,000 per second for the whole platform, so a handful of workers would do and we have orders of magnitude of headroom to spend on fewer sequence bits or more worker bits. And the key size matters at scale: with ten billion rows, a 128-bit key costs 80 GB more than a 64-bit one in the primary key alone, again in every secondary index. UUID collision probability is negligible at any realistic volume, which is why random ids are a legitimate option; their cost is not collisions, it is size and index locality.

API

-- Library form (preferred): no network on the hot path
id = ids.next_id()                         -> int64
ts, worker, seq = ids.decode(id)           -> (unix ms, worker id, sequence)

-- Service form (for languages or teams that cannot embed the library)
POST /v1/ids        { "count": 100 }       -> { "ids": [ ... 100 int64 as strings ... ] }

-- Always expose ids to JSON clients as STRINGS: a JavaScript number is exact only up to 2^53.

A library is better: a service adds a network hop and a dependency to every insert. Batch generation is useful when a service wants a block of ids to hand out locally. The last line is a classic gotcha: 64-bit ids exceed the 253 integers that JavaScript's Number holds exactly, so APIs should send them as strings.

Data model

  • The id itself: timestamp, worker, sequence (figure below). It is both the primary key and, in time-ordered form, a free sort key.
  • Worker registry: a small record per worker id in the coordination service: worker_id -> (owner, lease expiry). This is the only shared state in the design.
  • Epoch constant: chosen once, written in the library and never changed.

High-level design

Each service process embeds a generator. At startup it asks a coordination service for a worker id lease; while it lives, it renews the lease; the id bits it uses are its own for as long as the lease is valid. Generation is local arithmetic. Walk through how one id is built:

Step through

Generating one id, field by field

  1. Read the clock. The 41-bit timestamp field is the milliseconds since a custom epoch. Choosing your own epoch (not 1970) is what buys the 69-year lifetime.
  2. Same millisecond. Many ids can be issued in one millisecond; the sequence field tells them apart.
  3. Sequence overflow. When all 4,096 values are used, the generator waits for the next millisecond. That caps one worker, not the system.
  4. Worker bits. Fixed for the life of the process. Their uniqueness across the fleet is the one thing that needs coordination, and it is needed once at startup.
  5. Compose. Three fields joined by shifts. Because the timestamp is highest, comparing two ids as integers compares their times first.
  6. Clock rollback. The guard compares against the last timestamp used. A small step back is waited out; a large one is an error you page on.

Check the standard before you cite it

UUIDv7 is defined in RFC 9562 (May 2024), which replaced RFC 4122; the layout above is from that document. Library support for v7 is uneven, and the RFC leaves the within-millisecond ordering method to the implementation (it suggests a counter or extra clock precision in the random bits), so two libraries may not interleave a burst identically. ULID and KSUID are community specifications; their details vary by implementation.

Deep dive 2: clocks and worker ids

A time-based id is only as good as the clock. Three things go wrong:

  • Skew between machines. Two workers disagree by a few milliseconds, so ids are only roughly sorted across workers. That is why the requirement is "k-sortable"; never use the id order as a causal order (time revisited).
  • The clock goes backwards. NTP can step a clock, VMs resume from pause, leap seconds are smeared or stepped. A generator that just reads the clock may now issue a timestamp it has already used, with the same worker and sequence: a duplicate.
  • The sequence runs out. More than 4,096 ids in a millisecond on one worker: wait for the next one, or add workers.

The guard is small: remember the last timestamp used; if now is earlier, wait out small steps (a few milliseconds) and refuse large ones. Here it is, runnable, with a fake clock so the run is reproducible, followed by tests of the properties that matter.

"""A Snowflake-style 64-bit ID generator with a clock-rollback guard, driven by an injectable clock so every run is reproducible.

Layout (high to low): 1 sign bit (always 0) | 41 bits ms since a custom epoch | 10 bits worker id | 12 bits sequence
"""
from dataclasses import dataclass
from typing import Callable

TS_BITS, WORKER_BITS, SEQ_BITS = 41, 10, 12
MAX_WORKER = (1 << WORKER_BITS) - 1
MAX_SEQ = (1 << SEQ_BITS) - 1
EPOCH_MS = 1_700_000_000_000          # custom epoch: 2023-11-14T22:13:20Z (any fixed past instant works)

class ClockMovedBackwards(Exception):
    pass

@dataclass
class Snowflake:
    worker_id: int
    now_ms: Callable[[], int]                       # the clock (real or fake)
    sleep_ms: Callable[[int], None]                 # how to wait (real or fake)
    max_wait_ms: int = 5                            # small rollbacks are waited out; larger ones are refused
    last_ms: int = -1
    seq: int = 0

    def __post_init__(self):
        if not 0 <= self.worker_id <= MAX_WORKER:
            raise ValueError("worker_id out of range")

    def next_id(self) -> int:
        ms = self.now_ms()
        if ms < self.last_ms:                       # the clock went backwards
            drift = self.last_ms - ms
            if drift > self.max_wait_ms:
                raise ClockMovedBackwards(f"clock is {drift} ms behind the last issued id")
            self.sleep_ms(drift)                    # small step back (e.g. NTP slew): wait it out
            ms = self.now_ms()
            if ms < self.last_ms:
                raise ClockMovedBackwards("clock still behind after waiting")
        if ms == self.last_ms:
            self.seq = (self.seq + 1) & MAX_SEQ
            if self.seq == 0:                       # 4096 ids in one millisecond: wait for the next one
                while ms <= self.last_ms:
                    self.sleep_ms(1); ms = self.now_ms()
        else:
            self.seq = 0
        self.last_ms = ms
        return ((ms - EPOCH_MS) << (WORKER_BITS + SEQ_BITS)) | (self.worker_id << SEQ_BITS) | self.seq

def decode(i: int):
    return ((i >> (WORKER_BITS + SEQ_BITS)) + EPOCH_MS, (i >> SEQ_BITS) & MAX_WORKER, i & MAX_SEQ)

class FakeClock:
    def __init__(self, t): self.t = t
    def now(self): return self.t
    def sleep(self, ms): self.t += ms

def demo():
    clk = FakeClock(EPOCH_MS + 1_000)
    g1 = Snowflake(1, clk.now, clk.sleep)
    g2 = Snowflake(2, clk.now, clk.sleep)
    a = [g1.next_id() for _ in range(3)]
    print("same millisecond, worker 1:", a, "-> decoded (ms-epoch, worker, seq):", [(decode(x)[0] - EPOCH_MS,) + decode(x)[1:] for x in a])
    clk.t += 1
    b = g2.next_id()
    print("next ms, worker 2:         ", b, "-> sorts after worker 1's ids:", all(b > x for x in a))

    ids = set()
    for i in range(20_000):                         # a busy burst: sequence overflow forces waiting
        ids.add((g1 if i % 2 else g2).next_id())
        if i % 5 == 0: clk.t += 1
    print("20,000 ids from two workers in a busy burst: all unique =", len(ids) == 20_000, "| clock advanced by overflow waits to", clk.t - EPOCH_MS, "ms after epoch")

    last_w1 = max(x for x in ids if decode(x)[1] == 1)
    last_ms = g1.last_ms
    clk.t = last_ms - 3                             # NTP steps the clock back 3 ms
    x = g1.next_id()
    print(f"clock stepped back 3 ms: waited it out, worker 1's next id is larger than its previous one: {x > last_w1}")

    clk.t -= 400                                    # a 400 ms jump back (VM resume, bad NTP step)
    try:
        g1.next_id()
    except ClockMovedBackwards as e:
        print("clock stepped back 400 ms: refused ->", e)

Assigning worker ids

The ten worker bits must be unique among live generators. Two processes sharing one is the failure that breaks everything silently: they will produce identical ids when their sequences coincide.

MethodHowRisk
Static configPut the id in each host's configHuman error; copied images get the same id
Orchestrator ordinalA StatefulSet pod index, host numberWorks only while the platform guarantees at most one pod per ordinal (and surviving a network partition means it may not)
Lease from a coordination service (recommended)On startup, acquire a free worker id with a TTL; renew it; stop issuing ids if the lease may have lapsedA paused process can wake after its lease expired and another process took the id: guard with the fencing idea, i.e. refuse to issue when now is beyond the lease's valid-until time minus a safety margin
Random worker bitsPick 10 random bitsWith a few hundred processes the birthday problem makes a collision likely; do not

The lease is a textbook use of a coordination service, and the pause hazard is the one in leases and fencing: a process cannot know it was paused, so it must check the lease's expiry against the clock before every batch, with margin. In this design the lease is taken once, so the coordination service is on the startup path only, which is why its modest throughput does not matter.

Deep dive 3: ordering, locality and privacy

Sorting and locality. A time-ordered id means new rows land at the right edge of the primary-key index, which behaves like an append: pages stay hot in memory and splits are rare. A random id lands anywhere, so a large index is touched everywhere and write cost rises sharply once it no longer fits in memory. This is the practical reason to prefer v7 over v4 for primary keys.

What the id gives away. A timestamp-bearing id tells anyone who sees it when the record was created. A sequence or a dense counter tells them how many exist: compare two ids a week apart and you know your growth rate (a competitor's analyst will). Mitigations: do not expose internal ids at all (use a separate random public id, a UUIDv4 or an opaque token, with an index mapping); or encrypt the id with a format-preserving cipher before it leaves the system; or accept the leak when it is harmless.

Enumeration. Predictable ids let an attacker walk /orders/1001, /orders/1002 and read other people's data if authorisation is missing. Predictability is not the vulnerability, missing authorisation is (an insecure direct object reference); unguessable ids merely slow the attack and hide it from casual view. Always authorise by object, and treat an unguessable id as defence in depth. See the web-security discussion in web security.

Trade-offs & alternatives

  • Compactness versus simplicity. Snowflake saves 8 bytes per key per index but requires worker leases and clock discipline; UUIDv7 needs neither.
  • Sorting by id versus a created-at column. The id gives you a free sort at millisecond resolution, but not within a millisecond across workers. If you need a strict order, you need a single sequencer or a log (logs).
  • If ids must be gap-free, none of this applies: you need a transactional counter and you accept a bottleneck.
  • If the system will shard by id, a time-leading id makes the newest shard the hot one if you shard by range; hash-shard instead, or put a shard id in the layout (sharding).
  • Where it breaks down: a very fast sustained burst from one worker (more than 4 million per second) or a clock that cannot be trusted at all.

Follow-up questions

Why not just use a central counter service?

It works at small scale, but every insert depends on one service: a bottleneck, a single point of failure and a latency hop. Fetching blocks of 1,000 ids at a time removes most of the load but loses ordering within blocks and strands unused ids on a crash (harmless gaps). The embedded generator avoids all of it for the price of clock discipline.

How would you add more than 1,024 workers later?

You cannot widen a field without changing every id, so design the headroom in advance, or reserve a version bit so a new layout can coexist with the old one. Alternatives: shorten the sequence (fewer ids per ms per worker) to give bits to the worker field, as the capacity table shows; or run several generator processes per host under distinct ids.

Two ids are one millisecond apart on different workers. Which sorts first?

Usually the earlier timestamp, but not guaranteed: clock skew of a millisecond or two can reverse them, and within the same millisecond the worker bits decide. So ids are k-sortable, good for pagination by recency and index locality, not for establishing causality.

How do you migrate an existing table with auto-increment ids?

Add the new id column, backfill with generated ids (or keep old ids and generate new ones from a starting point above the old maximum), dual-write, switch reads, then drop the old key. If external systems hold the old ids, keep a mapping. The Instagram case study covers a database-embedded variant of this journey.

Can ids be generated in the client (browser or mobile)?

UUIDs can; Snowflake-style cannot, because clients have no worker id and untrusted clocks. A common pattern is client-generated UUIDs as idempotency keys or temporary ids, with the server assigning the canonical id (see idempotency keys).

How would you make ids non-enumerable but still sortable internally?

Keep the internal id for storage and ordering and expose a keyed transform of it (a format-preserving encryption, or a separate random public id with a lookup index). The transform must be reversible only by the server, and the key needs managing like any other secret.

Distributed systems connection

Unique ids without coordination is the same problem as uniqueness in any decentralised system: you either partition the space in advance (worker bits), use space so large that collisions are impossible (random bits) or ask a coordinator (tickets). A hybrid logical clock is the principled form of "timestamp plus counter" (time revisited), and the worker lease is a direct application of leases.

Key takeaways

  • Pick from requirements: unique, k-sortable, compact, no coordination on the hot path.
  • UUIDv4 is simple but unordered and large; UUIDv7 (RFC 9562) fixes ordering at 128 bits; Snowflake-style 64-bit ids are compact but need worker ids and clocks.
  • Do the bit maths: 41 bits of ms is about 69.7 years; 12 sequence bits give 4,096 ids per ms per worker; 10 worker bits give 1,024 workers.
  • Guard against clocks that go backwards: wait out small steps, refuse large ones, and alert.
  • Worker ids must be unique among live generators: use a lease with an expiry check, plus a unique constraint as the last defence.
  • Time-ordered keys keep indexes append-like; random keys scatter inserts.
  • Ids leak time and volume and are not access control. Authorise by object; expose opaque ids if growth rate is sensitive; send 64-bit ids as strings.

  2. They can produce identical ids when their timestamps and sequences coincide, silently

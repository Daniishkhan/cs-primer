Design Chat & Presence

Persistent connections, message ordering, delivery receipts, group fan-out and who is online. Chat is the design where the server must be able to push, so state moves to the connection layer: the interesting questions are where each connection lives, what "ordered" means, and how to keep the cheap, noisy signals (presence, typing) from endangering the valuable one (the message).

Why this matters

Chat flips the usual request-response picture. Millions of long-lived connections each hold a little state, a message is addressed to a person who may be on zero, one or four devices, and users notice a reordered or lost message immediately, in a way they never notice a stale like count. It forces choices about transport, routing, ordering, delivery guarantees and fan-out that reappear in notifications, collaboration tools, live streaming chat and gaming back ends.

The problem

"Design a chat service. Users message each other one-to-one and in groups, on phones and on the web. They should see when a message is delivered and read, see who is online, and get a notification if the app is closed."

The prompt hides several systems: a connection layer, a message pipeline, durable storage, a notification path and a presence system. It does not say how big a group can be (ten friends and a hundred-thousand-person channel are different problems), whether messages are end-to-end encrypted, or what "online" must mean. We pin those down with the framework.

Clarify requirements

Scale?100M daily active users, about 20% connected at the daily peak, roughly 40 messages sent per active user per day.

What the output decides. Twenty million concurrent connections at about 100,000 per gateway is a couple of hundred gateways: a fleet, not a cluster of giants, and two gigabytes of connection state each fits comfortably. Message traffic is modest: 46,000 sends per second on average and well under 200,000 at peak, which one sharded store can handle, and it is the 1.3 PB per year (replicated) that dictates a distributed wide-column store partitioned by conversation. The surprise is in the last rows: heartbeats alone are 667,000 per second, more than three times the message rate, and naive presence fan-out is over six times the message traffic. Presence is the expensive part, not messaging, so the design must keep heartbeats at the edge and fan presence out lazily. And the last block shows why group fan-out is done per gateway for big groups: a 100,000-member channel needs about 260 sends, not 100,000.

API

The client talks to a gateway over one long-lived connection carrying small frames, plus ordinary HTTP for things that are not real-time (history, uploads, group management).

-- Over the persistent connection (client -> server)
SEND    { conv_id, client_msg_id, body | media_ref }
                  -- client_msg_id: UUID chosen by the client
ACK     { conv_id, upto_seq, kind: "delivered" | "read" }
                  -- a watermark, not a per-message ack
TYPING  { conv_id }       -- ephemeral, never stored
PING    {}                -- heartbeat

-- Over the persistent connection (server -> client)
SENT    { client_msg_id, conv_id, seq, ts }
                  -- the server accepted and stored it
MSG     { conv_id, seq, sender, body, ts }
                  -- a message for you
RECEIPT { conv_id, user, kind, upto_seq }
PRESENCE { user, state: "online" | "offline", last_seen }

-- HTTP
# History and gap fill
GET  /v1/conversations/{id}/messages?after_seq=40&limit=50
# Catch-up after being offline
GET  /v1/sync?since=<device_cursor>
# Create a conversation / change its members
POST /v1/conversations
PUT  /v1/conversations/{id}/members
  • Two ids per message. client_msg_id makes sends idempotent: if the connection drops before SENT arrives, the client retries with the same id and the server returns the original sequence number instead of storing a duplicate. (conv_id, seq) is the server's identity, used for ordering and acknowledgements.
  • Acknowledgements are watermarks. "I have everything up to seq 41" is one small frame, survives lost acks, and is what the server stores (see Deep dive 2).
  • History is plain HTTP, paginated by sequence. Reconnection and gap filling both reduce to "give me messages after seq N", following the cursor principle in API design.

Data model

  • Messages (wide-column store): partition key (conv_id, bucket), clustering key seq descending, columns sender, body_or_ref, ts, deleted. A "bucket" is a time slice or a range of sequence numbers, so that a very busy conversation spreads over many partitions instead of one ever-growing one. The same shape and the same hot-partition lessons appear in the Discord messages case study. Reads are almost always "the latest N" or "after seq N", which is exactly what this layout serves.
  • Conversation metadata: members, type, settings, and the counter that issues sequence numbers (next_seq). Small; kept with the conversation's owner (Deep dive 2).
  • Per-member state keyed by (conv_id, user_id): delivered_upto and read_upto, two integers. Plus a per-user conversation list ordered by last activity with unread counts.
  • Connection registry (in-memory, sharded by user_id, TTL on entries): user_id → {device_id → gateway_id, conn_id}. Derived, rebuildable by reconnecting clients.
  • Presence (separate in-memory store, TTL): presence:{user_id} → {state, last_seen}.

Partition by conversation is the key decision: a conversation's messages are read together and ordered together, so they should live together. The price is that "all my messages across conversations" becomes a different access pattern, served by the per-user conversation list, not by a scan.

High-level design

Notice the split. Gateways own sockets and nothing else: they authenticate, parse frames, keep heartbeats and forward. The chat service owns the message path: sequencing, storage, routing. The registry and presence are soft state in memory. Because gateways hold no durable state, you can add, drain and replace them freely, and a gateway crash costs reconnects, not messages. Here is a one-to-one message end to end:

Step through

One message, sender to receiver

  1. Send. The sender's client puts the message on its socket with a fresh client_msg_id. The gateway authenticates the frame (the connection already carries identity) and forwards it, adding nothing.
  2. Sequence and persist. The chat service owns this conversation's sequence counter. It assigns the next number (41), writes the message to the store, and only then considers it accepted. If the same client_msg_id was seen before, it returns the earlier sequence number instead.
  3. Sent. The sender gets SENT with the sequence number and timestamp: the single tick. From here the message is durable, whatever happens next.
  4. Find the recipient. The service looks up the recipient's devices in the registry: for each, which gateway and connection holds it. This is one in-memory read.
  5. Route. The service sends the message to the owning gateway (B), which writes it to the recipient's socket. No broadcasting: the registry makes the delivery a targeted call.
  6. Delivered. The receiving client acknowledges up to seq 41. The service advances that member's delivered_upto watermark and tells the sender's devices, which show the second tick. A read receipt works the same way with read_upto.
  7. Offline. If the registry has no live connection for the recipient, the message stays in the store (already durable) and the push gateway is asked to send a notification. When the user reconnects they fetch everything after their watermark.

Deep dive 1: connections, transports and the registry

Transport: WebSocket gateways, long polling or SSE?

The server must be able to deliver a message the moment it arrives, so the client needs a channel that stays open. Three standard options exist; all three run over TCP and ordinary HTTP infrastructure (HTTP, TCP).

WebSocketLong pollingServer-Sent Events (SSE)
DirectionFull duplex, either side sends any timeClient requests, server answers when it has data; the client immediately asks againServer to client only; sends go over separate HTTP requests
Overhead per messageA few bytes of framingA full HTTP request/response each timeSmall framing; uplink pays full HTTP cost
LatencyLowest: no new request needed in either directionGood when idle, worse under churn (request setup between events)Low downlink; uplink as expensive as plain HTTP

Recommendation. WebSocket as the primary transport, with long polling as an automatic fallback where it is blocked (libraries typically negotiate this), and SSE if the product is mostly one-way. For mobile, a plain TCP or QUIC-based protocol with a compact binary framing is common in practice and saves battery and bytes, but the gateway design is the same. For the server side, the reason this is feasible is an event-driven runtime: an idle connection costs a few kilobytes of memory, not a thread (event loops, blocking I/O, and the Erlang-based approach in WhatsApp's per-server connection counts).

Sizing and shape of the gateway tier

Per the estimate, about 200 gateways carry the peak, 260 with headroom. Three constraints decide the real number more than raw connection counts: memory for buffers, CPU for TLS and heartbeats, and the blast radius of losing one: each gateway failure forces 100,000 clients to reconnect. Keep that bounded (do not run a few huge gateways), deploy by draining a gateway slowly rather than killing it, and have clients reconnect with exponential backoff and jitter so a restart does not become a stampede (resilience, overload). Load balance by connection count at accept time, then the connection is pinned (load balancers).

The connection registry

To deliver, the chat service must answer "which gateway holds user U's connections?". Options:

ApproachHow it worksCost
Registry storeOn connect, the gateway writes user → (device, gateway) with a TTL, refreshed periodically; the chat service reads it.One write per connect and per refresh; one read per delivery. Entries can be briefly stale.
Hash users to gatewaysA user always connects to the gateway chosen by consistent hashing of their id, so routing needs no lookup.Hot users cannot be rebalanced; reconnect and failover are awkward; ties your load balancing to a hash.
Broadcast to all gatewaysPublish the message; each gateway delivers if it has the user.Work proportional to the fleet for every message. Fine at tiny scale, not at 260 gateways.
Per-user pub/sub topicEach gateway subscribes to topics for its connected users.Millions of topics; it is the registry again, hidden in the broker.

The registry store is the default: it is small (a gigabyte or two for 20 million entries) and sharded by user id with consistent hashing. Two details matter. Entries are hints, not truth. A gateway may have died, so the registry can name a dead gateway; a delivery to it fails fast and the system treats the user as offline (push plus sync on reconnect). A short TTL, refreshed by the gateway rather than by every heartbeat, bounds the staleness; at one refresh per 60 seconds per connection that is the 333,000 writes per second in the estimate, which is why the refresh interval is a tuning parameter, not a constant. Multiple devices are a set per user, so one message fans to up to four sockets.

Deep dive 2: ids, ordering, storage and delivery states

What "ordered" has to mean

We need all members of a conversation to see the same order, and a total order across all conversations is neither needed nor affordable. That reduces the problem to one counter per conversation. Options:

ApproachOrder comes fromProblem
Client timestampsThe sender's clockClocks are wrong and users can lie. Never use them for order.
Server timestamps / time-ordered ids (Snowflake style)The accepting server's clock (unique ids)Two servers can stamp concurrent messages in either order, and skew reorders them; ties are broken arbitrarily but consistently, which is acceptable only if everyone reads the same stored order.
Per-conversation sequence numberA single writer per conversation increments a counterNeeds one owner per conversation at a time (and safe failover); throughput per conversation is bounded by that owner.
Consensus per conversationA replicated state machine for each conversation (SMR)Strong but heavy; overkill unless the sequencer's failover must be automatic and instant.
Logical/hybrid clocksCausal timestamps (time revisited)Gives causality, not a gap-free sequence, so clients cannot detect missing messages.

Recommendation: a sequence number per conversation, issued by that conversation's owner. The sequence has two decisive advantages over timestamps: it is gap-free, so a client that sees 38, 39, 41 knows exactly that 40 is missing and can fetch it; and it makes acknowledgements trivial (a watermark). The owner is the partition leader for the conversation's key range, so the partitioning that places the messages also places the counter. When the owner fails, a new one must not issue duplicates: elect it with a lease and protect the store with a fencing token, so a slow old owner cannot write after the new one has begun (leases and fencing). The sketch below shows the pieces that make this work end to end on the client and server: idempotent appends keyed by client_msg_id, and a client buffer that releases messages strictly in order.

The idea

  1. append: if (sender, id) already seen: return old seq; else seq ← seq + 1
  2. receive: ignore dups; buffer; show while seq + 1 is buffered
  3. send 7 messages (one retry); print (seq, newly stored) for each
  4. wire ← log + 2 random duplicates, shuffled; receive each, print any gap
  5. assert displayed seqs = 1..N in order, with no duplicates
"""Per-conversation ordering: one sequencer per conversation, idempotent
sends, and a client reorder buffer."""
import random


# ── 1. The sequencer: one per conversation ────────────────────────────
class Conversation:
    """Owns the sequence counter for one conversation.

    In production this is a single partition leader, so seq numbers
    are assigned by exactly one writer and never collide.
    """

    def __init__(self):
        self.seq = 0
        self.log = []       # (seq, sender, text): the source of truth
        self.seen = {}      # (sender, client_msg_id) -> seq: idempotency

    def append(self, sender, client_msg_id, text):
        key = (sender, client_msg_id)
        if key in self.seen:
            # A retry after a lost ack: return the old answer and
            # store nothing, so the message is not duplicated.
            return self.seen[key], False
        self.seq += 1
        self.log.append((self.seq, sender, text))
        self.seen[key] = self.seq
        return self.seq, True


# ── 2. The client: reorder buffer ─────────────────────────────────────
class Client:
    """Delivers strictly in sequence order.

    Remembers the highest contiguous seq it has shown, and holds
    anything that arrives early until the gap before it is filled.
    """

    def __init__(self):
        self.shown = 0      # highest contiguous seq displayed
        self.buffer = {}    # early arrivals: seq -> text
        self.display = []   # what the user actually sees, in order

    def receive(self, seq, text):
        if seq <= self.shown or seq in self.buffer:
            return          # duplicate delivery: ignore
        self.buffer[seq] = text
        while self.shown + 1 in self.buffer:
            self.shown += 1
            self.display.append((self.shown, self.buffer.pop(self.shown)))

    def gap(self):
        """Seqs we know are missing below the highest one buffered."""
        top = max(self.buffer, default=self.shown)
        return [s for s in range(self.shown + 1, top)
                if s not in self.buffer]


# ── 3. Idempotent sends ───────────────────────────────────────────────
conv = Conversation()
sends = [
    ("ana", 1, "hi"),
    ("ben", 1, "hello"),
    ("ana", 2, "lunch?"),
    ("ana", 2, "lunch?"),       # ana's retry of the previous send
    ("ben", 2, "yes"),
    ("ana", 3, "12:30"),
    ("ben", 3, "ok"),
]
acks = [conv.append(*s) for s in sends]
print("append results (seq, newly stored):")
print(" ", acks)
print("log:")
for entry in conv.log:
    print(" ", entry)

# ── 4. Delivery: duplicates and reordering on the wire ────────────────
rng = random.Random(7)
wire = [(s, t) for s, _, t in conv.log]
wire += rng.sample(wire, 2)     # at-least-once delivery duplicates
rng.shuffle(wire)               # and the network reorders

print("\narrival order at the client:", [s for s, _ in wire])
c = Client()
for s, t in wire:
    c.receive(s, t)
    if c.gap():
        print(f"  after seq {s}: shown up to {c.shown}, "
              f"waiting for missing {c.gap()}")

# ── 5. The invariant: same order as the log, no duplicates ────────────
print("displayed:")
print(" ", c.display)
assert [s for s, _ in c.display] == list(range(1, conv.seq + 1))

The guarantee is therefore at-least-once delivery with idempotent processing, which is the practical meaning of "exactly once" (logs and exactly-once).

Storage

Messages are append-mostly, read by recent range within one conversation, and large in total. That fits a wide-column or LSM-based store (LSM trees) partitioned by (conv_id, bucket) with seq as the clustering key. Hot conversations are the risk: a single partition that grows without bound or takes all the traffic. Buckets cap partition size, and a giant channel's traffic is spread across bucket partitions as it grows, with the current bucket still hot. The Discord case study shows what happens at scale with the storage engine itself, including operational issues like compaction and hot partitions, so read it with this layout in mind: Discord's messages. Replication factor 3 with quorum writes (consistency models) gives durability before SENT is returned; reads of recent messages can often be served from the same replicas without further coordination because the sequencer already serialised the writes.

Delivery states are watermarks

StateMeaningStored asWho sees it
SendingOn the sender's device onlyClient's outbox with a client_msg_idSender
SentThe server accepted and stored itThe message row with its seqSender
DeliveredA recipient's device received itdelivered_upto for that memberSender (aggregated in groups)
ReadThe recipient opened the conversation past itread_upto for that memberSender, if the recipient's privacy setting allows

Storing one integer per member per conversation, instead of a flag per message per recipient, is what makes receipts affordable: acknowledging a hundred messages is one frame and one row update, a lost ack is repaired by the next one, and in a group of 200 the sender's UI computes "delivered to 187" from 200 integers, not 200 times the message count. For big channels, drop per-message receipts altogether; keep only the member's own read position for unread badges.

Deep dive 3: groups, offline users, multiple devices and encryption

Fan-out for groups, large and small

This is the same question as the news feed, with a lower tolerance for delay. The numbers from the estimate pick the strategy:

Group sizeDeliveryWhy
Up to a few hundredThe chat service looks up each member in the registry and sends per user.Registry reads are cheap and the number of sends is bounded by the group size. Per-member receipts are affordable.
Thousands to 100,000+A channel server per channel (consistent-hashed) keeps the set of gateways with at least one subscriber. It sends one copy to each such gateway, which fans out to its local sockets.Sends scale with the gateway count (about 260), not the member count (100,000). This is the design described in Slack's real-time messaging.
Passive members of huge channelsDo not push to members who are not looking. They pull on open, with a push notification only for mentions.Most members of a large channel are inactive at any moment; pushing to them is the wasted work of chapter 9.

Persisting is separate from pushing: a group message is stored once, in the conversation's partition, not once per member. Each member's state is the two watermarks. That keeps write cost independent of group size and moves the per-member cost to the last mile.

Offline delivery and push notifications

The message is durable before the sender is told SENT, so "offline delivery" needs no extra storage: the recipient's reconnect asks for everything after their watermark. What the system adds is a nudge. When the registry shows no live connection, or a connection stops acknowledging within a short deadline, the chat service asks the platform push services (APNs for Apple devices, FCM for Android; external systems we do not control) to wake the app. Design rules that matter:

  • Push is a hint, never the transport. It can be delayed, dropped or coalesced. The client must sync on open regardless of whether a notification arrived.
  • Collapse and rate-limit. Ten messages in a minute should produce one updated notification (collapse keys), not ten; mute settings and "active on another device" suppress pushes.
  • Mind the payload. With end-to-end encryption the server cannot read the content, so the notification is "new message" and the app decrypts locally.
  • Sync is incremental. A reconnecting device sends its cursor (per conversation watermarks, or a per-device change sequence) and receives only what it missed. For a user in many conversations, a per-user inbox of "conversations with news" is cheaper to scan than all conversation partitions: a small push-style fan-out of pointers, used only for small groups, with the big channels pulled on demand, exactly the hybrid idea of chapter 9.

Multiple devices

The registry holds a set of devices per user and each device keeps its own delivered watermark, so a phone that was off for a day and a laptop that was on both converge to the same history through the same "after seq N" fetches. Messages the user sends from one device must also appear on their other devices, so the sender's own devices are recipients of every message. The read watermark is per user, not per device, so reading on the laptop clears the badge on the phone. Typing indicators and presence are ephemeral and never stored or synced. A new device needs history: for non-encrypted designs it fetches it from the server; with end-to-end encryption older messages cannot be decrypted by a fresh device unless another device transfers them or a protected backup exists, which is a product trade-off, not a technical oversight.

End-to-end encryption, briefly

If the server must not read messages, the clients encrypt, and the server stores and routes ciphertext plus the metadata it still needs (conversation id, sender, sequence number, size, timestamp). The standard shape, used by several widely deployed messengers, is per-device keys and a ratcheting session between devices (the Signal protocol is the best-known published design), so a message to a user with three devices is encrypted once per device; groups either encrypt per member or use sender keys that are distributed pairwise and rotated when membership changes. See applied cryptography for the primitives. What it changes in our design: server-side search, link previews, spam filtering and history sync for new devices all become hard or client-side; push payloads are opaque; key verification and device add/remove become part of the product; and what the server can still see (who talks to whom, when, how much) is a privacy surface of its own. The architecture above does not change; the content of the frames does.

Deep dive 4: presence

Heartbeats and TTLs

Presence is failure detection applied to people. A client cannot be relied on to announce a crash or a dead battery, so "online" is a lease: the client pings every 30 seconds; the gateway refreshes presence:{user} with a TTL; if no refresh arrives before the TTL, the key expires and the user is shown offline. This is a timeout-based detector, with the trade-offs described in failure detection: a longer TTL means slower detection of real departures, a shorter one means false "offline" flickers when a mobile network drops two packets. A TTL of about two and a half heartbeat periods (75 seconds here) tolerates a lost heartbeat plus jitter; clean disconnects delete the key immediately, but with a few seconds of grace so a phone switching from Wi-Fi to cellular does not flash offline and back. Presence is allowed to be wrong by tens of seconds; that is a stated requirement, and it is what makes the cheap design acceptable.

The same cost lesson applies to the heartbeat itself. In the estimate, 667,000 heartbeats per second arrive; the TCP connection already provides liveness, so the gateway should absorb pings locally and only write to the presence store when something changes or when a lease needs renewing, batching refreshes for many users into one call per interval.

Presence fan-out cost

The expensive part is telling the right people. In the estimate, each of about 22,000 status flips per second reaches around 40 watchers, which is nearly 900,000 pushes per second, over six times the message rate. At 100,000 members, one flip would be 100,000 pushes. Options:

StrategyHowTrade-off
Push every change to every contactNaive fan-out on writeCost grows with contacts; most receivers are not looking. Avoid.
Subscribe to what is on screenA client subscribes to presence only for the users in its current view (open chat, visible contact list page) and unsubscribes on scroll or close.Cost tracks attention, not graph size. Needs subscription state at the gateways.
Pull on openFetch presence for the open conversation when it opens, then rely on subscriptions.One batched read; slightly stale right after opening.
Coalesce and rate-limitCollapse flaps into one event per user per interval; send at most one update per watcher per few seconds.Hides rapid flapping, which is a feature.
Aggregate for big groupsShow "1,204 online" or nothing, never per-member presence.Loses detail nobody needs at that size.

Whichever you choose, give presence its own queues, its own capacity and a kill switch. After a regional outage every client reconnects, flips online and triggers a presence storm; if that shares a pipeline with messages, the least valuable signal can delay the most valuable one. Under pressure, presence is the first thing to degrade ("last seen is hidden for now"), and typing indicators the second.

Trade-offs & alternatives

  • Per-conversation order versus global order. We pay a sequencer per conversation and give up cross-conversation ordering, which nobody needs. A single global sequence would be a bottleneck for no benefit.
  • Server stores plaintext versus end-to-end encryption. Plaintext enables search, moderation and easy history sync; E2E gives privacy and removes those features server-side.
  • Strong versus soft state. Messages and sequence numbers are strongly consistent and durable; presence, typing, registry and read counts are soft, lossy and TTL-bound. The line between them is the main architectural idea.
  • If ordering had to survive region loss with no gaps. Replicate each conversation's log with consensus across regions and accept cross-region write latency, or make one region authoritative per conversation (multi-region).
  • If it were a small app. One database with a table of messages, a counter per conversation and a single WebSocket server would be correct up to a surprising size; every piece here exists because of a number above.
  • Where it breaks down. Gigantic live events (millions of simultaneous viewers in one chat) need sampling, sharded rooms and message dropping, which changes the guarantee from "everyone sees everything" to "everyone sees a representative stream".

What a strong answer adds

  • Splits the system into connection layer, message path, soft state and notification path, and says gateways hold sockets but no business state.
  • Compares WebSocket, long polling and SSE by direction, overhead and infrastructure friction, and names the fallback.
  • Uses a per-conversation sequence number rather than timestamps, explains that gap-freeness lets clients detect loss, and protects the sequencer with a lease and fencing.
  • Makes sends idempotent with a client-chosen id and treats delivery as at-least-once with dedupe.
  • Models receipts as per-member watermarks instead of per-message flags.
  • Quantifies presence (heartbeats and fan-out) and shows that it can exceed message traffic, then limits it by subscribing to what is on screen.
  • Fans out big groups per gateway, not per user, and does not push to passive members.
  • Treats push as a hint, designs for reconnect storms, and isolates presence from message delivery.

Follow-up questions

Why not give every message a globally unique, time-ordered id and sort by that?

Time-ordered ids are great for uniqueness and rough order, but two servers can stamp concurrent messages in either order, clock skew reorders them, and a client can never tell whether a message is missing. A per-conversation sequence is gap-free and cheap because only one component writes each conversation. You can still carry a time-ordered id for other purposes (deduplication across systems, analytics).

The sender's connection dropped after the server stored the message but before SENT arrived. What happens?

The client keeps the message in its outbox and retries with the same client_msg_id when it reconnects. The server finds the id in its idempotency record (kept for the conversation, with a retention window longer than any plausible retry) and returns the original sequence number. No duplicate is stored, and the sender then shows the message as sent. Everyone else already received the original once.

How do read receipts stay in sync across a user's phone and laptop?

The read watermark is stored per user and conversation, not per device. When any device reports "read up to 41", the service stores the maximum, broadcasts a receipt to the other members, and also pushes a small sync frame to the user's other devices so they clear unread badges. Because watermarks only move forward, concurrent reports from two devices merge by taking the larger one, with no conflict to resolve.

How would a channel with a million members work?

As a broadcast, not a chat. Messages are stored once; only members who currently have the channel open hold a subscription at their gateway, and delivery is one copy per gateway. Replies are rate-limited and sampled, receipts and presence are disabled, and unread counts are computed from each member's own position. Posting to the channel may itself go through a limiter or a slower moderation queue.

What do you do when presence is wrong, say a user shows online but their phone is dead?

Accept it within the stated bound: the lease expires after at most the TTL, so the error lasts about 75 seconds. If product needs less, shorten the heartbeat and TTL for the contacts someone is actively chatting with, not for everyone, because heartbeat cost scales with connections. For actual delivery the system does not rely on presence at all: messages are sent to the connection if it acknowledges and to push otherwise.

How would you add message search?

Index messages asynchronously from the store's change stream into a search service partitioned by user or conversation (chapter 11), with access control by membership at query time. With end-to-end encryption the server cannot index plaintext, so search runs on the device over locally stored messages, which limits it to what that device has synced.

Distributed systems connection

The sequencer is a single-writer log per partition, the building block of replicated state machines (consensus and SMR), and its failover is the leases-and-fencing problem. Presence is a failure detector with a lease, and its trade-off between speed and false positives is the same one every detector faces (failure detection). Idempotent sends with watermarks are the practical form of effectively-once processing over an at-least-once network.

Key takeaways

  • Use WebSocket gateways for real-time chat, with long polling as a fallback; gateways hold sockets and no durable state, and are drained rather than killed.
  • A connection registry (user to devices to gateways) in sharded memory with TTLs makes delivery a targeted call; entries are hints, and a miss means offline.
  • Order within a conversation by a gap-free sequence number issued by one owner, protected by a lease and fencing; never by wall-clock timestamps.
  • Sends are idempotent via a client-chosen id; delivery is at-least-once; clients reorder and dedupe by sequence.
  • Store messages in a wide-column store partitioned by conversation and time bucket; store receipts as per-member watermarks.
  • Fan out small groups per user and large channels per gateway; do not push to passive members.
  • Push notifications are hints; messages are durable before SENT, and clients sync from their watermark.
  • Presence is a leased flag with TTL about 2.5 heartbeats; its fan-out can exceed message traffic, so limit it to what users are looking at and isolate it from message delivery.

Check your understanding

Why use a per-conversation sequence number instead of timestamps to order messages?

  1. Sequence numbers are smaller to store
  2. One owner issues them without gaps, so order is agreed and clients can detect missing messages; clocks cannot offer either
  3. Timestamps cannot be indexed
  4. It removes the need for a database
With a single writer per conversation the sequence is a total order and gap-free. Timestamps depend on clocks that skew, and a missing message leaves no visible hole.

A client sends a message, the connection drops, and it retries. How do you avoid a duplicate?

  1. Reject all retries
  2. Use the arrival time to detect duplicates
  3. Ask the user to confirm
  4. Have the client send a stable client_msg_id; the server returns the original sequence number if it has already stored that id
An idempotency key chosen by the client turns an at-least-once retry into an effectively-once store.

In the napkin maths, which component of chat turned out to cost more than messaging itself?

  1. Presence: heartbeats and status fan-out
  2. Storage of message bodies
  3. The sequence counter
  4. Group creation
Heartbeats alone exceed the message rate, and naive presence fan-out is several times it. That is why heartbeats stop at the gateway and presence goes only to watchers who are looking.

How should read receipts be stored for a group of 200?

  1. One row per message per member per state
  2. Only on the sender's device
  3. As a read_upto sequence number per member per conversation
  4. Not at all; receipts cannot work in groups
A watermark per member makes acknowledgements one small frame, tolerates lost acks, and lets the sender's UI derive "read by 150" without per-message state.

For a 100,000-member channel on 260 gateways, the cheapest delivery step is to:

  1. Send one message per member from the chat service
  2. Send one copy to each gateway that has a subscriber and let the gateway fan out locally
  3. Broadcast to every client at once from a single server
  4. Store a copy in each member's inbox
Sends scale with the number of gateways (about 260), not the number of members, and the last-mile fan-out is parallel across gateways.

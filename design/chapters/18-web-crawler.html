Design a Web Crawler

The frontier, politeness, deduplication, traps and crawling a billion pages. A crawler looks like a loop that fetches URLs; designing it means seeing that the hard parts are the queue of what to fetch next, being a good guest on other people's servers, and not drowning in the web's endless near-copies.

Why this matters

The crawler is a rare design where the arithmetic is gentle and the difficulty is policy. A billion pages a month is only a few hundred fetches a second, but the data structure that decides which URL to fetch next must balance importance, freshness and the right of every site not to be hammered, over tens of billions of URLs. It also gathers a set of tools you will reuse: a Bloom filter for membership, fingerprints for near-duplicates, per-key queues for fairness and a scheduler driven by time.

The problem

"Design a web crawler. It starts from a list of seed URLs and discovers pages by following links. We want to download about a billion pages a month and keep them reasonably up to date, so that a search engine can index them."

"A billion pages" says nothing about which billion; "up to date" says nothing about how often; and "crawler" says nothing about manners. The framing is the framework again: ask, estimate, then put the effort where the numbers show the difficulty. The index and ranking that consume the pages are chapter 11.

Clarify requirements

QuestionAssumed answer
Purpose?General web crawl feeding a search index. Pages are stored for downstream processing; we do not render JavaScript in the first version.
Scale?1 billion page fetches per month; a seen-set of about 10 billion distinct URLs; about 30 million hosts worth crawling.
Content types?HTML first. PDFs and images are fetched but handled by other pipelines. Pages above a size limit are truncated.
Freshness?Important, fast-changing pages should be revisited within a day or so; the rest every few weeks. The revisit schedule is learned, not fixed.
Politeness?Honour robots.txt, never exceed a modest per-host request rate, identify ourselves with a user agent and contact URL, and back off when a site slows down or returns errors.
Extensibility?New content processors (link extractor, language detector, spam filter) should plug in without rewriting the fetchers.
Duplicates?Exact duplicates and near duplicates (the same article with a different ad banner) should be detected and not stored or indexed repeatedly.

Functional. Accept seeds; fetch pages; extract and normalise links; skip what is already known; store pages and metadata; schedule recrawls; expose per-host crawl controls and status.

Non-functional. Sustain the target throughput; never exceed a host's allowed rate; tolerate the web's hostility (slow servers, malformed HTML, infinite sites); recover from machine loss without restarting a crawl; keep the stored data compact; make a crawl resumable and observable.

Out of scope. The search index and ranking (chapter 11), JavaScript rendering and headless browsers, authenticated or paywalled crawling, the legal and policy side of what may be crawled, and deep-web form submission.

Reading the output. The fetch rate is under 400 pages a second on average, about half a gigabit of download, around 300 requests in flight, and a handful of CPU cores for parsing: the fetch and parse tier is small. Do not spend the interview on a fleet of hundreds of crawler machines. Storage is 30 TB per month compressed, comfortable for object storage. What is not small is the link graph: 50 billion extracted links a month, 90% already known (my assumption), and a seen-set that has to answer "have we ever seen this URL?" for every one of them. A Bloom filter for 10 billion URLs at 1% false positives is about 12 GB; the exact set of eight-byte hashes is 80 GB. Both fit in memory across a few machines, and the choice is a trade-off in Deep dive 3.

The politeness line is the subtle one. Across 30 million hosts at one request per second each, the aggregate ceiling is enormous, so politeness is not the limit on throughput in aggregate. It is the limit for individual big sites: a site with 100,000 wanted URLs at one request per second takes more than a day. So the scheduler's job is to keep hundreds of hosts in flight at once, always having a polite-to-fetch host ready, and to treat a few giant sites as long-running background work.

API

A crawler has little external API; it has internal messages and operator controls.

-- Operator / client API
POST /v1/seeds              { "urls": ["https://example.com/"], "priority": 0.8 }
PUT  /v1/hosts/{host}/policy { "max_rps": 0.5, "max_concurrent": 1, "blocked": false }
GET  /v1/hosts/{host}        -> { queue_depth, last_fetch, robots_age, error_rate }
GET  /v1/stats               -> { fetched_per_s, frontier_size, lag, dup_rate }

-- Internal messages
FetchTask   { url, host, priority, discovered_at, depth, prev_fingerprint? }
FetchResult { url, status, final_url, fetched_at, content_hash, etag, last_modified,
              body_ref, links[], robots_ok, duration_ms }
  • The task carries the previous fingerprint and validators. On a recrawl we send If-None-Match / If-Modified-Since; a 304 costs almost nothing and tells the freshness model "unchanged".
  • The result separates the body from the metadata. The body goes to object storage and the result holds a reference, so the event stream stays small.
  • Per-host policy is first-class. Operators and abuse reports need a way to slow or block a host in seconds without a deploy.

Data model

  • URL table (the crawl's memory), key url_hash: canonical_url, host, first_seen, last_fetch, next_fetch, change_estimate, status, fingerprint, depth, importance. Tens of billions of rows, sharded by host hash, so all URLs of one host live together, which is what the per-host frontier needs (sharding). A wide-column or LSM-tree store fits: heavy write rate, point lookups by key, range scans by host and no joins.
  • Frontier: priority queues (front) and per-host queues (back) with a heap of host ready-times. It is derived from the URL table and from newly discovered links, partitioned by host, and mostly in memory with disk spill.
  • Seen-set: a Bloom filter or an exact hash set, per host shard, in front of the URL table so most already-known links never cost a database read.
  • Host table: host, ip, dns_expiry, robots_body, robots_fetched_at, crawl_delay, error_streak, next_allowed. Small (tens of millions of rows) and hot, cached in the fetchers.
  • Page store: compressed HTML in object storage keyed by content_hash, so exact duplicates share one object; a small index maps URL to hash and fetch time (object storage).
  • Fingerprint index: 64-bit SimHash values for near-duplicate lookup (Deep dive 4).
  • Partition key. The host. It keeps a host's queue, robots cache, DNS entry and rate limit on one machine, so politeness is a local decision instead of a distributed one. The cost is skew: giant hosts become hot partitions, handled by giving their queues a fixed, low rate rather than more machines.

High-level design

The loop, one URL at a time:

Step through

One URL through the frontier

  1. Choose a host, not a URL. A min-heap keyed by each host's next_allowed time pops the host that may be contacted soonest. If its time is in the future, the fetcher waits or works on a different host. Politeness is enforced by the choice itself.
  2. Pop that host's next URL. Each host has its own back queue; its head is the best remaining URL for that host.
  3. Check robots and DNS. Both come from the host's cached record. A robots.txt that has not been fetched, or has expired, is fetched first and cached; a disallowed URL is dropped without costing the host any politeness delay.
  4. Fetch. Asynchronous I/O, with a connect timeout, a total timeout, a size cap, a redirect limit and a descriptive user agent. A conditional GET on recrawls.
  5. Schedule the host's next turn. Set next_allowed to the later of the crawl delay and a multiple of the time the fetch took, so a slow server automatically gets less traffic. Push the host back on the heap.
  6. Feed back what was found. The parser extracts links; normalisation canonicalises them; the seen-set discards the known; the rest are scored and enter a front queue by priority.
  7. Refill. When a host's back queue empties, take the next URL for that host from the front queues, highest priority first. This is the two-level structure published for the Mercator crawler (Heydon and Najork, 1999): front queues for priority, back queues for politeness.

Deep dive 1: the frontier, priority and politeness

A single FIFO queue of URLs fails twice. It ignores importance, so a crawl of a billion URLs spends its first week on calendar pages. And it ignores hosts, so the queue happily emits fifty consecutive URLs of one site, turning the crawler into a denial-of-service tool. The frontier has to answer two orthogonal questions: which URLs matter most and which host may I talk to right now.

DesignImportancePolitenessCost
One FIFO queueNone (breadth-first order)NoneTrivial, but unusable on the real web
One priority queue keyed by scoreGoodNone: the top 1,000 entries may share one hostSimple; politeness must be checked at fetch time and failures requeued, which churns
Per-host queues plus a heap of ready-timesOnly within a hostExactOne queue per host; many tiny queues; no global importance
Front priority queues refilling per-host back queuesGood, in coarse classesExactTwo structures to keep consistent; priority is approximate (bounded by queue lag)

Recommendation: the last row, as in the stepper. Importance is a coarse score (links from many good pages, short depth, host reputation, past change frequency), bucketed into a handful of classes; fine-grained exact ordering across a billion URLs is not worth its cost. Partition the whole frontier by host hash, so every shard owns a set of hosts and their politeness state, and the fetchers for a shard pull only from it.

Here is the politeness half in about forty lines you can run: per-host queues, a heap of ready-times, robots.txt rules with a crawl-delay (parsed by the standard library), and two fetcher slots.

"""A tiny polite crawl scheduler: per-host queues, a min-heap of 'next allowed time', robots.txt and crawl-delay."""
import heapq
from urllib.robotparser import RobotFileParser
from collections import deque, defaultdict

ROBOTS = {
    "a.example": ["User-agent: *", "Crawl-delay: 2", "Disallow: /private/"],
    "b.example": ["User-agent: *", "Disallow: /admin"],
    "c.example": ["User-agent: *", "Crawl-delay: 5"],
}
frontier = {   # host -> URLs waiting, already ordered by priority
    "a.example": ["/", "/news", "/private/x", "/about"],
    "b.example": ["/", "/admin/panel", "/blog", "/blog/1"],
    "c.example": ["/", "/p/1"],
}
DEFAULT_DELAY, AGENT = 1.0, "DemoBot"
rules, queues, ready = {}, {}, []
for host, lines in ROBOTS.items():
    rp = RobotFileParser(); rp.parse(lines); rules[host] = rp
    queues[host] = deque(frontier[host])
    heapq.heappush(ready, (0.0, host))        # every host is allowed immediately at t=0

clock, fetchers, free_at = 0.0, 2, [0.0, 0.0]   # two fetcher slots, each takes 0.3 s per request
last = defaultdict(lambda: None); log = []
while ready:
    allowed_at, host = heapq.heappop(ready)
    if not queues[host]: continue
    slot = min(range(fetchers), key=lambda i: free_at[i])
    clock = max(clock, allowed_at, free_at[slot])             # wait for the host's politeness time AND a free fetcher
    path = queues[host].popleft()
    if not rules[host].can_fetch(AGENT, f"http://{host}{path}"):
        log.append(f"t={clock:5.1f}  skip   {host}{path}  (robots.txt disallows)")
    else:
        log.append(f"t={clock:5.1f}  fetch  {host}{path}")
        free_at[slot] = clock + 0.3
        delay = rules[host].crawl_delay(AGENT) or DEFAULT_DELAY
        if last[host] is not None: assert clock - last[host] >= delay - 1e-9
        last[host] = clock
        if queues[host]: heapq.heappush(ready, (clock + delay, host))
        continue
    if queues[host]: heapq.heappush(ready, (clock, host))     # a skipped URL costs no politeness delay
print("\n".join(log))

t=  0.0  fetch  b.example/
t=  0.3  fetch  c.example/
t=  1.0  skip   b.example/admin/panel  (robots.txt disallows)
t=  1.0  fetch  b.example/blog

Read the timeline. a.example asks for a 2-second delay and is fetched at 0, 2 and 4; c.example asks for 5 and is fetched at 0.3 and 5.3 (the 0.3 is just waiting for a free fetcher slot). A disallowed URL is skipped without consuming the host's delay, and meanwhile the other hosts keep the fetchers busy. The inner assertion proves no host was hit faster than its delay.

robots.txt and crawl-delay

The Robots Exclusion Protocol is now a standard (RFC 9309), and it is a convention, not an enforcement mechanism: a crawler that ignores it is not stopped by anything but the site's other defences. Practical rules: fetch /robots.txt before anything else on a host; cache it for hours, not seconds (RFC 9309 says a cached copy should not be used for more than 24 hours unless the file is unreachable); treat a 4xx as "no restrictions" and a 5xx or timeout as "assume disallowed for now" and retry later; and match the longest applicable rule for your user agent. Crawl-delay is not part of the standard: some crawlers honour it and some ignore it, so treat it as a hint you choose to respect and bound it (a delay of an hour on a billion-URL site is a polite way of saying no). A sitemap URL in robots.txt is a free source of URLs and change hints.

DNS

Each new host needs a lookup, and the system resolver is a classic bottleneck: it is synchronous in many libraries, shared, and unprepared for hundreds of lookups a second. Run your own caching resolver or an in-process async cache keyed by host, with the record's TTL clamped to a sensible floor and ceiling so short TTLs cannot make you re-resolve constantly (DNS). Resolve once per host per batch, keep the IP in the host record, and remember that many hosts share one IP: politeness is owed per host and, to be a good citizen, also per IP, because shared hosting means ten thousand sites may sit behind one address.

Deep dive 2: fetchers and being a good guest

Fetching is I/O-bound and the estimate said about 300 requests in flight, so a small number of processes with asynchronous I/O (event loops) is enough. The craft is in the defences, because the web is full of things that waste or break a naive client:

  • Timeouts everywhere: connect, first byte and total. A server that sends one byte a second is a slow-loris against your connection pool.
  • Size caps: stop reading after a limit (for example a few megabytes) and mark the page truncated. Do not buffer unbounded bodies.
  • Redirect limits and loops: follow a handful of hops, record the final URL as the canonical one, and treat a redirect to another host as a new frontier entry subject to that host's politeness.
  • Adaptive rate: if a host's error rate or latency rises, double its delay; on recovery, ease back. A crawler should never be the reason a small site goes down. The "multiple of the fetch time" rule in the stepper is one simple form.
  • Identity: a stable user agent with a URL describing the crawler and a contact address, a fixed set of IP ranges that site owners can verify, and a fast path to be blocked.
  • Safety: the fetcher makes requests to addresses chosen by strangers. It must refuse private and link-local IPs and cloud metadata addresses even after redirects and DNS tricks, or a crawler becomes an SSRF probe into your own network (injection and SSRF); run fetchers in an isolated network segment with no access to internal services.

Deep dive 3: URL normalisation and the seen-set

Most extracted links are already known, so the seen-set is the busiest data structure in the system: 50 billion membership checks a month, over 10 billion distinct URLs. Two things make it work: canonical URLs so equal pages have equal keys, and a compact membership structure.

Normalisation

Lower-case the scheme and host, drop default ports and the fragment, resolve . and .. segments, sort query parameters, and strip parameters known to carry no content (tracking and session identifiers). Each rule removes a source of false "new URL" signals. Be conservative with anything that might change the content: ?page=2 matters, and removing a trailing slash is not always safe. Learn from the data: if hundreds of URLs differing only in one parameter always return the same fingerprint, add that parameter to the host's ignore list.

Bloom filter versus exact set

A Bloom filter answers "possibly present" or "definitely absent" in a few bits per item with no false negatives and a tunable false-positive rate, the same trick LSM-tree stores use to avoid reading files that cannot contain a key. The costs are different in a crawler, because here a false positive means a real, new URL is silently never fetched.

"Definitely absent" is trusted (the URL is new: insert and enqueue); "possibly present" is confirmed with a cheap table read only for the small fraction that matters, or accepted as a loss at a rate low enough that missing 1% of new URLs does not change the crawl's coverage meaningfully. The decision is about the cost of a miss, and in a search crawl a lost low-value URL is cheap, while in a compliance crawl it would not be.

"""URL normalisation, a Bloom filter seen-set, and SimHash near-duplicate detection (all standard library)."""
import hashlib, random, re
from urllib.parse import urlsplit, urlunsplit, parse_qsl, urlencode

TRACKING = {"utm_source", "utm_medium", "utm_campaign", "fbclid", "gclid", "sessionid"}
def normalise(url: str) -> str:
    p = urlsplit(url.strip())
    host = (p.hostname or "").lower().rstrip(".")
    port = f":{p.port}" if p.port and (p.scheme, p.port) not in (("http", 80), ("https", 443)) else ""
    parts = []
    for seg in p.path.split("/"):                    # resolve dot segments
        if seg == "..": parts and parts.pop()
        elif seg not in (".", ""): parts.append(seg)
    path = "/" + "/".join(parts) + ("/" if p.path.endswith("/") and parts else "")
    q = urlencode(sorted((k, v) for k, v in parse_qsl(p.query) if k not in TRACKING))
    return urlunsplit((p.scheme.lower(), host + port, path, q, ""))   # fragment dropped

class Bloom:
    def __init__(self, m_bits, k): self.m, self.k, self.bits = m_bits, k, bytearray((m_bits + 7) // 8)
    def _idx(self, s):
        h = hashlib.sha256(s.encode()).digest()
        a, b = int.from_bytes(h[:8], "big"), int.from_bytes(h[8:16], "big") | 1
        return [(a + i * b) % self.m for i in range(self.k)]      # double hashing
    def add(self, s):
        for i in self._idx(s): self.bits[i >> 3] |= 1 << (i & 7)
    def __contains__(self, s): return all(self.bits[i >> 3] >> (i & 7) & 1 for i in self._idx(s))

n = 50_000; bf = Bloom(m_bits=n * 10, k=7)                         # ~10 bits per URL, 7 hashes
for i in range(n): bf.add(f"http://site{i % 500}.example/page/{i}")
fn = sum(1 for i in range(0, n, 50) if f"http://site{i % 500}.example/page/{i}" not in bf)
fp = sum(1 for i in range(n, n + 20_000) if f"http://site{i % 500}.example/page/{i}" in bf)
print(f"\nBloom: {n:,} URLs in {n*10/8/1e3:.0f} KB; false negatives {fn}; false positives {fp/20_000:.2%} of 20,000 unseen URLs")

def simhash(text: str, bits=64) -> int:
    words = re.findall(r"\w+", text.lower())
    shingles = [" ".join(words[i:i + 3]) for i in range(max(1, len(words) - 2))]
    v = [0] * bits
    for s in shingles:
        h = int.from_bytes(hashlib.sha256(s.encode()).digest()[:8], "big")
        for b in range(bits): v[b] += 1 if h >> b & 1 else -1
    return sum(1 << b for b in range(bits) if v[b] > 0)
dist = lambda x, y: bin(x ^ y).count("1")

Deep dive 4: duplicate content, fingerprints and SimHash

The web is full of copies: mirrors, syndicated articles, the same product under a hundred URLs, pages that differ only in a date or a banner. Fetching a copy is cheap; storing, parsing and indexing it again is not, and a search result page full of duplicates is a poor product. There are two levels.

  • Exact duplicates. Hash the normalised content (a cryptographic or 128-bit hash) and look it up. Equal hashes mean the same bytes, and the page store keys objects by this hash so identical bodies are stored once. Cheap and precise, but defeated by a one-character change.
  • Near duplicates. Use a similarity-preserving fingerprint. SimHash, a locality-sensitive hash due to Charikar (2002), produces a short fingerprint in which similar documents have fingerprints that differ in few bit positions. Manku, Jain and Das Sarma (WWW 2007) studied exactly this for web crawling: they report that 64-bit SimHash fingerprints with a Hamming-distance threshold of 3 worked well on a repository of eight billion pages, and describe how to search for all fingerprints within that distance without comparing against every stored one, by splitting each fingerprint into blocks and indexing tables on permutations of them.

The mechanism of SimHash in one paragraph: break the document into features (here, three-word shingles); hash each feature to 64 bits; keep a 64-element counter vector, adding 1 where a feature's hash bit is 1 and subtracting 1 where it is 0; the fingerprint is the sign of each counter. Documents that share most features share most bits' signs. In the output above, a copy with a small edit and an appended footer differed in 5 of 64 bits, an unrelated page in 40 (about half, as random bits would be), and an exact hash of the two copies was of course different. My toy uses a small vocabulary and short documents, so do not read 5 as a universal threshold; the point is the gap between "near" and "unrelated". Real systems extract features after stripping boilerplate (navigation, footers), because otherwise two different articles from the same site look alike.

The cheapest dedup of all is not fetching: canonical link tags (rel="canonical"), sitemaps and the host's learned parameter-ignore rules. Use fingerprints as the second line of defence, applied after fetch.

Deep dive 5: traps, freshness and storage

Crawler traps

A crawler trap is a region of the URL space that is effectively infinite: a calendar with a "next month" link forever, a relative link that appends a path segment each time (/a/b/a/b/a/b), a search form whose result pages link to more result pages, session identifiers that make every visit a new URL. Some are accidents; some are deliberate. A crawler cannot reliably recognise a trap by looking at one page, so it limits the damage with budgets and heuristics.

"""Crawler-trap guards: depth limit, repeated path segments, per-host budget, and query-parameter explosion."""
import re
from collections import Counter, defaultdict
from urllib.parse import urlsplit

MAX_DEPTH, MAX_QUERY_VARIANTS, HOST_BUDGET = 8, 20, 1000
per_host = Counter(); variants = defaultdict(set)

def verdict(url):
    p = urlsplit(url); segs = [s for s in p.path.split("/") if s]
    if len(segs) > MAX_DEPTH: return "reject: too deep"
    if re.search(r"((?:/[^/]+){1,3})\1{2,}", p.path): return "reject: path segment repeats (a/b/a/b/a/b...)"
    key = (p.hostname, p.path)
    variants[key].add(p.query)                       # distinct query strings seen for this one path
    if len(variants[key]) > MAX_QUERY_VARIANTS: return "reject: query-string explosion on one path"
    per_host[p.hostname] += 1
    if per_host[p.hostname] > HOST_BUDGET: return "defer: host budget spent"
    return "accept"

tests = ["http://shop.example/cat/shoes",
         "http://x.example/a/b/a/b/a/b/a/b",
         "http://cal.example/2030/01/01/02/03/04/05/06/07/08",
         "http://x.example/loop/loop/loop/loop/page"]
tests += [f"http://s.example/list?sort=a&page={i}&session={i*7}" for i in range(1, 26)]
tests += [f"http://big.example/p/{i}" for i in range(1, 1003)]
res = Counter()
for u in tests[:4]: print(f"{verdict(u):<48} {u}")
for u in tests[4:]: res[verdict(u)] += 1
print(dict(res))

reject: too deep                                 http://cal.example/2030/01/01/02/03/04/05/06/07/08

  • Per-host budget: at most N URLs per host per crawl cycle, scaled by the host's importance. An infinite site can consume its budget and no more; that is the primary defence.
  • Depth and length limits: reject URLs beyond a maximum path depth or URL length.
  • Repetition detection: a repeating group of path segments is almost always a loop.
  • Parameter explosion: many distinct query strings on one path with near-identical content fingerprints is a signal to collapse that path's parameters.
  • Content-based: a host where a high fraction of new pages are near-duplicates of existing ones (the fingerprint index tells you) has its budget cut automatically.

Freshness and recrawl scheduling

A crawl is never finished: pages change at wildly different rates, and the fetch budget is fixed. The question is how to spend it. Model each page's changes as a random process with its own rate, estimated from history (did the fingerprint change between visits? use ETag and Last-Modified to make checks cheap). The experiment below uses a standard simplification, Poisson changes, where revisiting every I days leaves a page fresh for the fraction (1 − e−λI)/(λI) of the time. It compares three ways to spend 200,000 fetches a day on a million pages.

"""Recrawl budget: fraction of pages that are 'fresh' under uniform, proportional and greedy-optimal revisit rates.
Model: page changes are a Poisson process with rate lam per day; revisiting every I days leaves a page fresh
for a fraction (1 - exp(-lam*I)) / (lam*I) of the time, on average."""
import math
classes = {            # name: (pages, changes per day)   <- assumptions
    "news front pages": (100_000, 4.0),
    "blogs":            (400_000, 0.2),
    "mostly static":    (500_000, 0.01),
}
BUDGET = 200_000       # assumption: fetches per day available for recrawling 1M pages
def fresh(lam, r):     # r = revisits per day
    if r <= 0: return 0.0
    x = lam / r
    return (1 - math.exp(-x)) / x
def score(rates):      # expected fraction of all pages that are fresh
    total = sum(n for n, _ in classes.values())
    return sum(n * fresh(l, rates[k]) for k, (n, l) in classes.items()) / total

N = sum(n for n, _ in classes.values())
uniform = {k: BUDGET / N for k in classes}
c = sum(n * l for n, l in classes.values()) / BUDGET
proportional = {k: l / c for k, (n, l) in classes.items()}
greedy = {k: 0.0 for k in classes}; step = 0.0005             # hand out the budget in slices of 0.0005 revisits/day/page
def spend(rates): return sum(classes[k][0] * rates[k] for k in classes)
while True:
    # marginal freshness gained per fetch spent: the page count cancels between gain and cost
    best = max(classes, key=lambda k: (fresh(classes[k][1], greedy[k] + step) - fresh(classes[k][1], greedy[k])) / step)
    if spend(greedy) + classes[best][0] * step > BUDGET: break
    greedy[best] += step
for name, rates in (("uniform", uniform), ("proportional to change rate", proportional)):
    print(f"{name:<28} fresh {score(rates):.1%}  budget used {spend(rates):,.0f}/day  revisit every " +
          ", ".join(f"{1/rates[k]:.1f}d" for k in classes))
print(f"{'greedy (best marginal gain)':<28} fresh {score(greedy):.1%}  budget used {spend(greedy):,.0f}/day  revisit every " +
      ", ".join(f"{1/greedy[k]:.1f}d" if greedy[k] else "never" for k in classes))
uniform                      fresh 74.6%  budget used 200,000/day  revisit every 5.0d, 5.0d, 5.0d
proportional to change rate  fresh 37.6%  budget used 200,000/day  revisit every 0.6d, 12.1d, 242.5d
greedy (best marginal gain)  fresh 78.6%  budget used 199,900/day  revisit every never, 2.6d, 10.3d

This is counter-intuitive and worth discussing aloud. Revisiting pages in proportion to how often they change is the obvious policy and the worst one here (37.6% fresh): it pours the budget into pages that change faster than you can ever keep up with, and starves the others. Uniform revisiting does better (74.6%). A greedy allocation by marginal gain does best on this metric (78.6%), but it does it by never recrawling the fastest-changing class at all, which is mathematically sensible and commercially absurd, since those are news front pages. Published work on page refresh by Cho and Garcia-Molina reached a similar qualitative conclusion about proportional versus uniform policies. So real schedulers optimise a different objective: a freshness value weighted by importance (how many users would look at this page), with a floor on revisit frequency, and cheap conditional requests (a 304 costs little) to make frequent checks affordable. I have not cited numbers for any production crawler; the model is a teaching device and its constants are assumptions.

Operationally, the recrawl scheduler is a second source feeding the frontier: it scans the URL table's next_fetch index for due pages and enqueues them with a priority derived from importance, the same due-time machinery as the job scheduler. Adaptive intervals are the practical form: halve the interval when the page changed, grow it (say by 1.5 times) when it did not, within bounds.

Storage of pages

Store the compressed raw body in object storage under its content hash, plus a small record per fetch (URL, time, status, headers of interest, fingerprint, body reference). At 30 TB per month compressed, object storage is the obvious home: write-once, cheap, durable. Keep the metadata in the URL table. Group many small pages into larger container objects (a few hundred megabytes each, in the spirit of web archive files) so you do not create billions of tiny objects, and keep a per-page offset in the metadata. Retain the last few versions of a page for diffing and for the change-rate estimate, and expire older ones.

SLOs. Throughput (pages per second against target, by shard); freshness (share of high-importance pages revisited within their target interval); politeness (fraction of requests violating a host's delay, which should be zero); robots compliance; error mix by class. Alert on a shard with no fetches for several minutes, a rising fraction of timeouts or 429/503 responses (the crawl is being throttled), the new-URL rate falling sharply (a trap, a bug in normalisation or a saturated Bloom filter) and the near-duplicate rate rising. Roll out new extraction or normalisation rules in shadow mode on a sample of hosts, comparing the URL sets they would produce, because a normalisation bug changes the identity of billions of URLs.

Trade-offs & alternatives

  • Breadth-first versus importance-ordered. Breadth-first is simple and tends to find good pages early; scoring is better but needs signals. We use coarse priority classes: most of the benefit, little cost.
  • Distributed frontier versus central. We partition by host so politeness is local. Partitioning by URL hash would spread load evenly but make per-host rate limits a distributed problem.
  • Bloom filter versus exact. Memory and speed against silently dropping some new URLs. Tune the false-positive rate to the value of a miss.
  • Fresh versus broad. A fixed budget splits between discovering new pages and revisiting known ones. A mostly-static corpus favours discovery; a news product favours recrawl.
  • If we needed to render JavaScript, fetch cost rises by one or two orders of magnitude (a browser per page), the fleet becomes the main cost and a separate, selective rendering tier is justified for pages whose raw HTML is empty.
  • If it were a focused crawl (one site or topic), the frontier prioritises by relevance, the seen-set shrinks and politeness dominates.
  • Where it breaks down. Sites that block crawlers, content behind logins, and pages generated per visitor, where the notion of "the page" is itself unclear.

What a strong answer adds

  • Does the arithmetic first and notes that the fetch tier is small, then moves the discussion to the frontier, the seen-set and politeness.
  • Separates priority (front queues) from politeness (per-host back queues and a ready-time heap) and says why a single queue fails at both.
  • Partitions by host so rate limits and robots caches are local, and acknowledges the skew that creates.
  • Knows that robots.txt is a convention with a standard, that crawl-delay is not standardised, and that an unreachable robots.txt should not mean "crawl everything".
  • Normalises URLs, uses a Bloom filter in front of an authoritative table, and states the cost of a false positive.
  • Distinguishes exact from near duplicates and can explain SimHash and a Hamming threshold without overselling it.
  • Protects against traps with budgets, not clever detection alone, and protects the internal network from the fetchers.
  • Treats freshness as an allocation problem under a budget, and sees why "revisit in proportion to change rate" can lose.

Follow-up questions

How would you crawl a site that publishes a sitemap with millions of URLs?

Treat the sitemap as a strong hint, not an order: ingest URLs and their lastmod values into the frontier at a priority derived from host importance and recency, and let the per-host budget and rate limit pace the actual fetches. A sitemap that lies about lastmod (everything changed today) should be learned and ignored by comparing it with observed fingerprints.

How do you make the crawl resumable after the whole cluster restarts?

The URL table holds the crawl's memory and the frontier is derived from it, so a restart rebuilds queues from rows with a due next_fetch or unfetched status. Politeness state restarts conservatively (every host gets a fresh delay). In-flight fetches are simply repeated; fetching is idempotent apart from load on the site, which the delay bounds. Checkpoint the Bloom filter periodically, or rebuild it from the table.

How would you add a politeness limit per IP address as well as per host?

Keep a second ready-time structure keyed by IP (or a /24 for large shared hosts) and require both to allow a fetch. Because hosts are partitioned by host hash, hosts on one IP can land on different shards; hash by IP instead when the IP is known, or route the IP-level limit through a small shared counter. This is the one place where partitioning by host stops being enough.

How do you detect that a page changed in a meaningful way, not just a rotating ad?

Fingerprint the main content after boilerplate removal rather than the raw bytes, and compare with a similarity threshold, not equality. A SimHash of the cleaned text moving by more than a few bits is a "real" change. Feed that signal, not the raw hash change, into the change-rate estimate, so pages with random widgets are not scheduled as if they were news.

What would change if the crawler had to handle 100 times more pages per month?

The fetch tier grows linearly but is still ordinary. What breaks first is the frontier's state (more hosts, more URLs: shard more finely and move cold URLs to disk) and the seen-set (a 1 TB-scale Bloom filter or exact set is still shardable by host). Politeness becomes the limiter for big sites, so extra fetch capacity buys nothing unless it spreads over more hosts; the lever is breadth, not speed.

How would you stop the crawler from being used to attack a site?

Per-host and per-IP rate limits that cannot be overridden by task input, no user-controlled URLs without review (a "submit a URL to crawl" feature must itself be rate limited per submitter), immediate global blocklists, and monitoring for hosts receiving unusual traffic. Treat politeness as a safety property enforced in the scheduler, not a courtesy implemented in each fetcher.

Distributed systems connection

The frontier is partitioned by a key chosen so that a local decision (is this host allowed now?) replaces a distributed one, which is the central idea of partitioning. The seen-set is the Bloom filter of LSM-trees applied at a different scale, and the recrawl scheduler is the due-time machinery of the job scheduler. The rest, retries, circuit breakers and adaptive backoff, is resilience applied to other people's servers.

Key takeaways

  • A billion pages a month is a few hundred fetches a second. The fetch tier is small; the difficulty is the frontier, the seen-set and politeness.
  • The frontier has two layers: priority front queues for importance and per-host back queues with a heap of ready-times for politeness. Partition it by host so rate limits and robots caches are local.
  • Respect robots.txt (RFC 9309), treat crawl-delay as an optional hint, cache DNS, bound every fetch with timeouts and size caps, and keep fetchers away from internal addresses.
  • Normalise URLs, then check a Bloom filter in front of the authoritative table; its false positives silently drop new URLs, so size it for the value of a miss.
  • Exact duplicates by content hash, near duplicates by SimHash and a small Hamming threshold (Charikar; Manku, Jain and Das Sarma for web-scale use).
  • Traps are contained with per-host budgets, depth and repetition limits, not perfect detection.
  • Freshness is a budgeted allocation. Revisiting in proportion to change rate can be worse than uniform; real schedulers weight by importance and use conditional requests.

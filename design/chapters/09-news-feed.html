Design a News Feed

Fan-out on write versus read, celebrities, ranking and caching timelines. A feed looks like "show me my friends' recent posts"; designing it well means noticing that follower counts are wildly skewed, that reads outnumber writes by an order of magnitude, and that the cheapest answer for most users is the most expensive answer for a few.

Why this matters

The news feed is the standard exercise in moving work between write time and read time. Every large design faces some version of it: precompute and pay on every write, or compute on demand and pay on every read. The feed adds a twist that makes it a good teacher: the cost of a write depends on who wrote, and a small number of authors dominate. Getting this right means using a skewed distribution as an input to the design instead of an inconvenient footnote, and it exercises caching, queues, partitioning, ID generation, ranking and deletion in one system.

The problem

"Design the home timeline for a social network. People follow other people, post short updates with an image or two, and open the app to see what is new. It should feel instant, and it should show the posts they care about most."

"Follow" could be symmetric (friends) or one-way (followers), and the two behave very differently at the extremes. "Feel instant" is a latency target for opening the feed, but it says nothing about how quickly a new post must appear. "Care about most" quietly adds a ranking system. We separate the pieces using the framework.

Estimate

The key numbers are the read-to-write ratio, the cost of each strategy in operations per second, and the size of a timeline cache. Assumptions are in the script so you can change them; method as in chapter 2.

The idea

  1. post/s ← DAU × posts ÷ 86,400; feed/s ← DAU × opens ÷ 86,400; peak ← × 3
  2. push inserts/s ← post/s × followers; pull lookups/s ← feed/s × followees
  3. cache ← users × 800 ids × 16 B; nodes ← 3 copies × cache ÷ 256 GB
  4. for each follower count: seconds ← followers ÷ 200k inserts/s

Reading the output. Reads outnumber posts about 16 to 1, and every feed load wants an answer in tens of milliseconds, so doing the work at write time (a few thousand posts per second, each a one-off cost) is attractive. Pushing every post to every follower is about 230,000 timeline inserts per second on average and about 700,000 at peak. That is a big but ordinary sharded in-memory workload, and it is asynchronous, so it can queue. Pulling instead would be 3.7 million author lookups per second on average (11 million at peak) just to open feeds, which is why pull-only designs do not survive at this scale. Storing ids only keeps the timeline cache at a few terabytes; storing full posts would be roughly a hundred times larger. And the last lines expose the problem: one post from an account with a million followers is a million inserts and several seconds of the fan-out fleet's attention, and one from an account with 50 million followers is minutes. The average hides a catastrophic tail, which is the next section's subject.

The follower distribution is not an average

The mean number of followers (200 in the script) is almost useless on its own. Follower counts in real social graphs are heavy-tailed: many accounts with a handful, a very few with millions. We model it as a Zipf-like power law with a skew exponent s: the account of rank i has about c·i−s followers, capped at some fraction of all users, with c chosen so the mean stays fixed. I will not quote measured exponents for any real network; the point is the shape, and you can try several. The model below uses a scaled-down population of 100,000 users and the same arithmetic as the widget in Deep dive 1.

The idea

  1. mean followers = 100; cap at 10% of users; 2 posts/user/day
  2. followers(s) ← c × rank^−s, bisect c until the mean is 100
  3. push ← 2 × edges; pull ← 2 × U, edges ÷ U reads; hybrid pushes x ≤ T
  4. for each s: report top author, median and top-1% share of follow edges
  5. for each (views, T): print writes, reads/load, worst post, total ops/day
"""Push vs pull vs hybrid fan-out cost on a Zipf-like follower
distribution (mirrors fanout-cost.js)."""

# ── 1. Model parameters ───────────────────────────────────────────────
U     = 100_000       # users in the scaled-down model
A     = 100           # mean followers (= mean followees) per user
CAP   = U // 10       # nobody has more than 10% of users as followers
POSTS = 2             # posts per user per day


# ── 2. Follower counts by author rank ─────────────────────────────────
def followers(s):
    """Followers of the author at rank i: min(CAP, c * i**-s).

    The constant c is found by bisection so the mean is exactly A.
    """
    lo = 0.0
    hi = 1e12
    for _ in range(60):
        c = (lo + hi) / 2
        total = sum(min(CAP, c * i ** -s) for i in range(1, U + 1))
        if total < A * U:
            lo = c              # mean too low: need a bigger c
        else:
            hi = c
    return [min(CAP, c * i ** -s) for i in range(1, U + 1)]


# ── 3. Cost of each strategy ──────────────────────────────────────────
def costs(f, T, views):
    """Each strategy as (writes/day, reads per feed load, worst fan-out
    of one post, total ops/day). T is the celebrity threshold."""
    edges = sum(f)                      # total follow edges
    out = {}
    out["push"] = (POSTS * edges, 1.0, f[0])
    out["pull"] = (POSTS * U, edges / U, 1.0)

    # Hybrid: push ordinary authors, pull celebrities at read time.
    # A celebrity post still costs one write (the post itself).
    pushed_edges = sum(x for x in f if x <= T)
    celeb_edges = edges - pushed_edges
    n_celebs = sum(1 for x in f if x > T)
    worst_pushed = max([x for x in f if x <= T] or [0])
    out["hybrid"] = (POSTS * (pushed_edges + n_celebs),
                     1.0 + celeb_edges / U,
                     worst_pushed)

    return {k: (w, r, worst, w + r * U * views)
            for k, (w, r, worst) in out.items()}


# ── 4. How skewed is the distribution? ────────────────────────────────
def show_skew():
    for s in (0.8, 1.0, 1.2):
        f = followers(s)
        top_share = sum(f[:U // 100]) / sum(f)
        print(f"skew s={s}: top author {f[0]:,.0f} followers, "
              f"median {f[U // 2]:.0f},")
        print(f"  top 1% of authors hold {top_share:.0%} "
              f"of follow edges")


# ── 5. Compare strategies at a few thresholds and read loads ──────────
def compare():
    f = followers(1.0)
    for views, T in ((10, 1_000), (10, 3_000), (1, 1_000)):
        n = sum(1 for x in f if x > T)
        print(f"\ns=1.0, {views} feed loads/user/day, threshold "
              f"{T:,} followers ({n:,} authors pulled)")
        for name, (w, r, worst, tot) in costs(f, T, views).items():
            print(f"  {name:<7} writes/day {w:>10,.0f}  "
                  f"reads/load {r:>6.1f}")
            print(f"  {'':<7} worst post {worst:>7,.0f}  "
                  f"total ops/day {tot:>12,.0f}")


if __name__ == "__main__":
    show_skew()
    compare()

Two things to notice. Raising the skew leaves the mean unchanged but moves a growing share of all follow edges into the top 1% of authors (27%, 40%, then 51% here). And in the second block, pure push has a worst single post of 10,000 inserts when the median author has 26 followers: the work per post differs by almost three orders of magnitude, and in a real network the ratio is far larger.

-- Internal event on the queue (one per new post, small):
PostCreated { post_id, author_id, created_at, visibility }
  • Idempotent post creation. The client mints an idempotency key so a retry after a lost response does not create two posts (API design).
  • The cursor is opaque. The client never builds or interprets it. That lets us change how pagination works (id-based for "latest", session-based for ranked) without breaking clients. Details in Deep dive 3.
  • The event is tiny. It carries ids, not the post body; consumers re-read the post by id. A queue full of bodies is expensive, and bodies change (edits, deletes).

Data model

  • Posts (source of truth, sharded key-value or wide-column store): post_id → {author_id, text, media_ids, visibility, created_at, deleted}. IDs are time-ordered 64-bit values (unique IDs), so id order is creation order and a shard number can live inside the id (the approach in sharding and IDs at Instagram). A secondary structure holds author_id → recent post_ids, newest first for pulling and for the celebrity path.
  • Follow graph: two tables written from one source, followers_of(followee, follower) and followees_of(follower, followee). Fan-out reads the first; a pull-time merge reads the second. Keeping the two copies in step is an eventually consistent job, done by a change stream rather than by hoping two writes both succeed (outbox and CDC).
  • Timeline cache: key tl:{user_id}, value a list of recent post_ids, newest first, capped at a few hundred (800 in our estimate). It is derived data: it can always be rebuilt from the graph and the posts, which is why a cache and not a database is the right home (chapter 3).
  • Engagement counters and post caches: hot post bodies and like or reply counts live in a separate cache keyed by post id, populated on read (caching).
  • Partition keys: timeline by user_id (even spread, one list per read); posts by post_id (so hydration is a multi-get that fans across shards); graph by the first column of each table (partitioning).

High-level design

The central choice: the timeline cache holds post ids, not posts. A feed load becomes "read one list, then fetch objects by id". It costs an extra hop at read time (hydration), and buys three things: the cache stays small, there is exactly one copy of each post body to update, delete or hide, and ranking can reorder ids without touching storage. Here is the main read path, including the cold-cache branch:

Step through

One feed load

  1. Request. The client asks for a page, with a cursor if it is scrolling. The feed service authenticates the caller and loads who they follow among celebrities (a small cached set).
  2. Read the timeline. One list read from the timeline cache returns the newest few hundred post ids that were pushed for this user. This is the whole read cost for most of their feed.
  3. Merge celebrities. For each celebrity the user follows, read that author's recent-ids list and merge by id with the pushed ids. Those lists are tiny, shared by millions of readers, and so extremely hot and cacheable.
  4. Rank. The candidates go through feature lookup and scoring (Deep dive 3). For the "latest" tab this step is just a sort by id.
  5. Hydrate and filter. Fetch post bodies, author profiles and counts by id in one batched round. Drop anything deleted, blocked, muted or no longer visible. If too many were dropped to fill the page, take the next candidates.
  6. Respond. Return the page and an opaque cursor, and note whether newer posts have arrived.
  7. Cold cache. If the timeline list is missing (evicted, new user, long-inactive user) the feed service rebuilds it: read the follow graph, pull each followee's recent ids, merge, and write the list back. It is slower, which is why it is rare by design.

The write path is the mirror image. The Post API stores the post, publishes a small PostCreated event and returns; fan-out workers consume the event, page through the author's followers and push the id into each follower's list (LPUSH plus LTRIM to the cap, or an equivalent), batching per cache shard. The response never waits for fan-out: that is what keeps posting fast for an author with millions of followers.

Deep dive 1: fan-out on write, on read, or both

The three strategies differ in when they pay. The widget below uses the skewed follower model from the estimate. Move the skew up and watch the worst-case post under push explode, then lower the celebrity threshold and watch the hybrid trade that worst case for extra read work. Also drop the number of feed loads per day to one: the winner flips, because pull's cost scales with reads, push's with writes.

Look at what the widget shows rather than what the cartoon version of this chapter would say. In raw operation counts the hybrid is not cheapest at ten loads a day; push is. The hybrid is chosen for its worst case: no single post triggers more than a threshold's worth of inserts, so one celebrity cannot starve everyone else's freshness, and the fan-out fleet can be sized to the ordinary load instead of the extreme tail. Its read-side price is extra list fetches: in the model above, about 43 on top of the one timeline read at a threshold of 1,000 followers (about 29 at 3,000), because the model gives every user many celebrity followees. They are issued in parallel and are cheap because celebrity lists are shared and hot, but this is why the cap on celebrity lists merged per load matters. That is a typical senior-level observation: a design is often chosen for its tail, not its mean.

Choosing the threshold

Pick the celebrity threshold from two numbers, not from taste. First, the fan-out budget: if a worker fleet delivers about 200,000 inserts per second and a post must reach followers within, say, five seconds, a single post can afford roughly a million inserts, so authors above about that size must be pulled. Second, the read budget: every celebrity a user follows adds one list fetch per feed load, and a user who follows hundreds would blow the latency target, so cap how many celebrity lists are merged per load (the most recent or most engaged ones) and accept that a rare user sees slightly fewer celebrity posts. Both numbers drift over time, so the threshold is configuration, and an author can cross it in either direction: when an account crosses the line, stop pushing new posts and let old pushed entries age out.

Large social networks typically describe this exact pattern, with timelines in memory and special handling for very large accounts; Twitter's timelines at scale walks through a published account and what it says about the details. To feel the numbers in code, build the three strategies on a generated power-law graph in Lab 3.

Deep dive 2: the timeline cache and hydration

What is in the cache, and why ids

Each user has one list: tl:{user_id} holds up to 800 post ids, newest first. Because ids are time-ordered, merging two lists (pushed ids and a celebrity's ids) is a merge of sorted sequences with no timestamps to carry. The cap bounds memory and matters for correctness of the estimate: 300 million users times 800 ids times 16 bytes is the 3.8 TB you saw above, replicated three times for availability and spread over dozens of nodes by user id with consistent hashing. A timeline is a cache in the sense of the earlier chapters: its source of truth is the follow graph plus the posts, so losing a node costs a rebuild, not data. That is why replication can be asynchronous and the persistence story is deliberately weak.

Hydration

Hydration turns ids into displayable cards: post body, author name and avatar, like and reply counts, whether the viewer already liked it, media references. Three habits keep it fast. Batch everything: one multiget per object type, issued in parallel, not a loop of single reads. Cache by object, with long TTLs for immutable fields (body) and short ones or separate counters for volatile fields (counts). Degrade deliberately: if the counts service is slow, show the posts without counts rather than failing the page, a pattern from resilience. Hydration fans out to several backends, so tail latency matters: a feed load is as slow as its slowest dependency call (tail latency), which argues for hedged reads and tight per-call deadlines.

The script below puts the pieces together at toy scale so you can run them: capped timeline lists, a celebrity pulled at read time, hydration that drops deleted and blocked posts, and a cursor that survives a new post arriving mid-scroll.

The idea

  1. publish: id ← next id; if not celebrity: insert id at each follower's head
  2. home(user, before): cache + celebrities' recent; skip deleted or blocked
  3. build graph: star has 3 followers (celebrity), ann and ben have 1 or 2
  4. for each post in the stream: publish and print the timeline inserts
  5. page 1, then new post + delete, page 2, block star, page 3, fresh load
"""Hybrid home timeline: push for ordinary authors, pull for celebrities,
hydrate, filter, and page by cursor."""
from collections import defaultdict

# ── 1. State and publishing ───────────────────────────────────────────
# Tiny numbers so the demo is readable.
CAP      = 6                    # keep 6 post ids per timeline
CELEB_AT = 3                    # 'celebrity' = 3 or more followers

posts   = {}                            # post id -> (author, text)
deleted = set()                         # deletion markers (tombstones)
followers     = defaultdict(set)        # author -> followers
timeline      = defaultdict(list)       # user -> newest-first post ids
author_recent = defaultdict(list)       # author -> their newest-first ids
blocked       = defaultdict(set)        # viewer -> authors they blocked
next_id = 0


def is_celeb(author):
    return len(followers[author]) >= CELEB_AT


def publish(author, text):
    global next_id
    # Ids grow with time (like Snowflake ids): id order is time order.
    next_id += 1
    posts[next_id] = (author, text)
    author_recent[author].insert(0, next_id)

    pushed = 0
    if not is_celeb(author):            # fan-out on write, ordinary only
        for f in followers[author]:
            timeline[f].insert(0, next_id)
            del timeline[f][CAP:]       # trim the cache to CAP ids
            pushed += 1
    return next_id, pushed


# ── 2. Reading a page of the home timeline ────────────────────────────
def home(user, followees, limit, before=None):
    """before: cursor = smallest post id already consumed.
    Returns (page, next_cursor)."""
    cands = list(timeline[user])        # pushed ids
    for a in followees:
        if is_celeb(a):                 # pulled at read time, merged in
            cands += author_recent[a][:CAP]
    cands = sorted(set(cands), reverse=True)
    if before is not None:
        cands = [i for i in cands if i < before]

    page = []
    consumed = None
    for pid in cands:
        # Hydrate lazily, dropping what must not be shown.
        consumed = pid
        author, text = posts[pid]
        if pid in deleted or author in blocked[user]:
            continue
        page.append((pid, author, text))
        if len(page) == limit:
            break
    # The cursor is the last id *examined*, not the last one shown, so
    # filtered posts are never re-scanned on the next page.
    return page, consumed


# ── 3. Set up a small social graph ────────────────────────────────────
followees = ["ann", "ben", "star"]
for u in ("me", "u2", "u3"):
    followers["star"].add(u)            # 3 followers -> celebrity
followers["ann"].add("me")
followers["ben"].add("me")
followers["ann"].add("u2")

# ── 4. Publish: ordinary authors push, the celebrity does not ─────────
STREAM = [("ann", "a1"), ("star", "s1"), ("ben", "b1"), ("ann", "a2"),
          ("star", "s2"), ("ben", "b2"), ("ann", "a3")]
for a, t in STREAM:
    pid, n = publish(a, t)
    note = ""
    if is_celeb(a):
        note = "  (celebrity: stored once, pulled at read time)"
    print(f"post {pid} by {a:<4} -> {n} timeline inserts{note}")

Deep dive 3: ranking and pagination

A ranking pipeline, described qualitatively

  1. Candidate generation. Gather posts that could be shown: the pushed timeline ids, the celebrity lists, and possibly a few recommended posts from accounts the user does not follow. This is a recall step; it should be cheap and generous.
  2. Features. Attach signals to each candidate. Typical families: the post (age, media type, length, early engagement), the author (how often the viewer interacts with them, how prolific they are), the pair (has the viewer replied to this author recently?) and the viewer context (device, time of day). Features come from a feature store with online and offline copies, discussed in chapter 20; the discipline that matters here is that training and serving compute them the same way.
  3. Scoring. Typically two passes. A cheap model or heuristic cuts thousands to hundreds; a heavier model predicts the probabilities of engagement events (like, reply, share, hide) for the survivors, and a weighted sum of those predictions becomes the score. The weights are a product decision, made explicit, and the place where "optimise for time spent" or "for meaningful interaction" actually lives.
  4. Blend and page. Apply rules a score does not capture: do not show five posts in a row from one author, mix media types, suppress anything policy-flagged, inject an ad or a recommendation slot. Then cut the page.

Architecturally, ranking is a separate stateless service with a latency budget (tens of milliseconds), a fallback to chronological order if it is slow or down, and an experiment framework around it so two models can be compared on live traffic. Treat a ranking failure like a hydration failure: degrade to a less clever feed, never to an error page. What I will not do is quote model internals or accuracy figures; they depend on the product and change constantly.

Pagination with cursors

Offset pagination (?page=3) breaks on a feed, because new posts arrive between requests and shift every offset, so the user sees duplicates or misses items. The general remedy, cursor (keyset) pagination, is covered in API design; the feed adds one complication, which is ranking.

TabCursor contentsWhy it is stable
Latest (chronological)"Posts older than id X"Ids are time-ordered, and "older than X" does not change when newer posts arrive. This is what the script above does.

Two further rules. Never auto-insert new posts above the viewer's scroll position; return has_new and let the client show a "new posts" pill, which also lets the next fresh load re-rank. And make the cursor opaque and versioned so you can change its structure later; clients that parse cursors become a compatibility burden.

Deep dive 4: deletions, privacy changes and inactive users

Deletes and privacy must be read-time checks

If timelines hold ids, a deletion is one write to the post store plus cheap cleanup, not a fan-out in reverse. But the guarantee has to be defined: no deleted post is shown after T seconds, for a T you can state. Design for it in layers:

  1. Authoritative flag at hydration. The hydration step reads the post's deleted and visibility fields and drops the post. The post-body cache entry is invalidated on delete (a delete event on the same stream that carries edits) and has a short TTL as a backstop, never a long one (caching).
  2. Viewer-level filters. Blocks and mutes apply per viewer. The feed service holds the viewer's block and mute sets in memory (small) and filters candidates before ranking, so a blocked author's posts do not even cost hydration. A new block takes effect on the next feed load without touching any timeline.
  3. Unfollow and account privacy. Unfollowing removes the followee from the viewer's follow set, and posts already pushed are filtered on read by checking the author against that set. Switching an account to private or followers-only changes the visibility check at hydration; a follow-request approval flow adds followers gradually.
  4. Lazy cleanup. A background job removes dead ids from lists as it finds them, so lists do not fill with tombstones, but correctness never depends on the job.
  5. Legal and safety removals. For takedowns that must be near-immediate, the tombstone is also pushed to a small "kill list" every feed service checks in memory, and erasure of user data follows the retention path in data protection.

The price of read-time filtering is that a page can come back short, which is why hydration over-fetches and the cursor tracks ids examined. If a viewer has blocked many authors the over-fetch should be adaptive.

Inactive users

Most accounts on a large service are not active on a given day, and pushing into a timeline nobody reads is pure waste. Three habits fix it. Fan out only to recently active followers, for example anyone seen in the last few weeks; everyone else has no list. Rebuild on return: a user with no list triggers the cold path (pull from the graph) at first open, and it is acceptable for that first load to be slower or a little shorter. Expire lists with a TTL that refreshes on activity, so memory tracks the active population. If, say, only one in three of an average author's followers is active, that alone cuts fan-out writes by roughly two thirds. The caveat is the cold-start storm: after an outage or a big event, many dormant users return at once and each triggers a rebuild, so rebuilds need rate limits and a bounded fallback ("show the latest 50 posts from the top followees") to protect the graph store (overload).

Trade-offs & alternatives

  • Freshness versus cost. We chose near-real-time for ordinary authors and a read-time merge for celebrities. If posts had to appear instantly everywhere, push cost and queue priority become the whole design; if hours of staleness were fine, a periodic batch build of timelines would be far cheaper.
  • Ids-only cache versus complexity. Ids force hydration, which adds a hop and a tail-latency source. We accept it for deletes, privacy and size. If content were immutable and public, caching bodies is simpler.
  • If the graph were symmetric (friends). Follower counts are capped (friend limits), so the celebrity problem mostly vanishes and pure push is fine; the pressure moves to mutual-privacy checks.
  • If users must see their own post immediately. Insert it into the author's own list synchronously, or merge the author's recent posts at read time: a read-your-writes fix that does not wait for fan-out (session guarantees).
  • If ranking were purely chronological. Drop the ranker and the session cursor; pagination becomes a plain id cursor and the whole system is much cheaper to operate.
  • Where it breaks down. Users who follow thousands of accounts, accounts hovering near the threshold, and fresh-start storms. Each needs an explicit cap or a fallback, not a larger cluster.

What a strong answer adds

  • Asks about the follow model and the largest account before drawing anything, and treats the follower distribution as an input to the design, not an average.
  • Quantifies the read-to-write ratio and the cost of push, pull and hybrid, and chooses the hybrid for its worst case, saying so honestly when the mean favours push.
  • Derives the celebrity threshold from the fan-out budget and caps the number of celebrity lists merged per load.
  • Caches ids rather than posts and can explain how that makes deletes, edits and privacy changes cheap.
  • States a deletion guarantee as a bounded delay with a probe, instead of "we invalidate the cache".
  • Handles inactive users explicitly, including the cold-start storm after an outage.
  • Separates ranking into candidate generation, features and scoring with a chronological fallback, and keeps it out of the critical failure path.
  • Gets cursors right: opaque, keyset for chronological, a frozen session list for ranked, no auto-insertion above the fold.

Follow-up questions

A user follows a celebrity for the first time. What happens to their timeline?

For a celebrity there is nothing to backfill: the next feed load merges that author's list automatically. For an ordinary account, a follow event triggers a small backfill job that copies the followee's last few post ids into the follower's list (merged by id), so the new follow is visible immediately instead of only for future posts. Unfollowing needs no push-time work because reads filter by the follow set.

How would you show new posts to someone who has the app open?

Keep a lightweight signal rather than streaming whole posts: a persistent connection or a periodic poll for "is there anything newer than id X for me?", which returns a count so the client can show a pill. The connection layer is the same machinery as in chat and presence, and for the same reason it should carry small notifications, not payloads.

An account gains a million followers overnight. Does anything break?

Posts made before the account crossed the threshold were pushed into timelines; later ones are pulled. During the transition both exist, and the merge-by-id handles that. The risk is the account being in the push regime when a huge post lands, so the threshold check uses current follower counts at event time, and the fan-out job itself has a per-post budget: past it, remaining followers are served by the pull path.

How do you keep a ranked feed from showing the same post twice, or one you already saw?

Within a session, the frozen candidate list and cursor prevent repeats. Across sessions, keep a compact record of recently shown post ids per user (a bounded set or a Bloom filter, accepting a small false-positive rate that hides a post wrongly) and use it as a feature or a filter. The cost is another per-user store; the alternative is to accept some repetition.

Why a queue between the Post API and the fan-out workers? Why not insert synchronously?

Fan-out takes time proportional to the author's followers, which is unbounded; doing it inside the request would make posting latency depend on follower count and tie the API's availability to the cache's. The queue decouples them, absorbs bursts, allows retries and prioritisation, and lets you scale workers independently. The cost is eventual freshness, which we measure. Use a partitioned log keyed by author so one author's events stay in order (streams).

How would you test that ranking changes are an improvement?

Online experiments: randomise users into arms, hold the feed architecture constant, compare engagement and guardrail metrics (hides, reports, latency, long-term retention proxies) over enough time to see novelty wear off. Offline replay on logged impressions is a cheap filter before an experiment but cannot replace it, because the model changes what users see and therefore what they do.

Distributed systems connection

A timeline is a materialised view maintained asynchronously from a log of events, which is the pattern behind CQRS and incremental view maintenance (CQRS). Its staleness is eventual consistency made visible to users, and read-your-writes for the author is a session guarantee you add on top (causal and session consistency). The skew problem is the hot-partition problem of sharding seen from the write side.

Key takeaways

  • Reads outnumber writes by an order of magnitude, so push work to write time by default, but follower counts are heavy-tailed, so the worst post matters more than the average post.
  • Hybrid fan-out pushes ordinary authors and pulls celebrities at read time. It is chosen to bound the worst case; in raw operation counts, plain push may be cheaper.
  • The timeline cache is a list of post ids per user, capped at a few hundred, rebuildable from the graph and the posts. Hydration batches the lookups and degrades gracefully.
  • Ranking is a funnel of candidate generation, features and scoring, always with a chronological fallback.
  • Use opaque keyset cursors: "older than id" for the latest tab, a frozen session list for ranked feeds, and never auto-insert above the fold.
  • Deletes, blocks and privacy changes are read-time filters on the live object, with a stated delay, because you cannot recall what you have pushed.
  • Do not fan out to inactive users; rebuild on return and rate-limit the rebuilds.

Lab 4: Sketches, Count-Min, HyperLogLog & Top-K

Approximate counting is only engineering if you can say how wrong you may be and prove the system stays inside it. You build a Count-Min sketch from (ε, δ) and test its bound against exact counts, merge sketches from partitions, find heavy hitters with Space-Saving, estimate distinct counts with HyperLogLog, and put them together into a windowed detector that finds injected trends without crying wolf. Chapter 12's formulas, run until they hold or fail with a seed.

Why this lab matters

Chapter 12 argued that a trending list is a question about how wrong you may be, and then gave formulas: w = ⌈e/ε⌉, d = ⌈ln(1/δ)⌉, a standard error of 1.04/√m. Formulas like these are easy to quote and easy to get subtly wrong: a hash that is not stable across processes, a merge that quietly adds sketches built with different seeds, a small-range correction left out, a baseline polluted by a traffic spike. This lab makes you build the structures and then test the promises against exact counts on seeded streams, so that "within εN with probability 1−δ" becomes a number you measured. Links: chapter 12 for the design, chapter 19 for where sketches live in a telemetry pipeline.

Deterministic by construction: no clocks, no process-salted hashes

Python's built-in hash() is salted per process, so a sketch built with it cannot be merged with one built elsewhere and a failing test cannot be replayed. Every hash here comes from hashlib.blake2b with a seed (h64(key, seed), given). Streams are drawn from random.Random(seed), windows run on event time passed in by the caller, and nothing reads a clock. A failing property prints its seed and the command that replays it, for example python3 check.py solution 3 7.

What you'll build

Five milestones, each building on the last:

  1. Count-Min sketch sized from (ε, δ) with seeded hashes, and a test that the error bound holds with the stated probability on a Zipf stream.
  2. Mergeability: merging sketches of partitions gives exactly the sketch of the union, in any order, and merging incompatible ones is refused.
  3. Space-Saving heavy hitters with per-item error, checked against exact counts, including when the top-k is provably correct.
  4. HyperLogLog with the small-range correction and merge; the error stays within about three standard errors across many trials.
  5. A windowed trending detector: tumbling windows of sketches, a baseline from the earlier ones, a trending score; injected trends are found and the background raises no alarms.

Milestone 1: a Count-Min sketch sized from (ε, δ)

A Count-Min sketch is a d × w table of counters with one hash function per row. add(x) bumps one cell in every row; estimate(x) takes the minimum of the cells x hashes to. Collisions only ever add, so every cell is at least the true count and the minimum is the least polluted one: the estimate never undercounts. Chapter 12 derives the sizing: with w = ⌈e/ε⌉ and d = ⌈ln(1/δ)⌉, true ≤ estimate ≤ true + εN with probability at least 1−δ, where N is the total weight. Halving ε doubles the width; being a hundred times more confident adds about five rows.

The bound is relative to the whole stream, not to the key, which is why the check looks at every key rather than just the head. It also has teeth: a sketch twelve times too narrow and one row deep must visibly break the bound, otherwise the test proves nothing. And it insists that estimate really uses the minimum.

def cms_dims(eps, delta):
    return math.ceil(math.e / eps), math.ceil(math.log(1.0 / delta))
class CountMin:

    def __init__(self, eps, delta, seed=0, width=None, depth=None):
        """Size the table from (eps, delta) with cms_dims unless width/depth are forced (the checks
        force them to build deliberately undersized sketches). Keep self.eps, self.delta, self.seed,
        self.w, self.d, self.table (list of d lists of w zeros) and self.n = 0."""
        w, d = cms_dims(eps, delta)
        self.eps, self.delta, self.seed = eps, delta, seed
        self.w = width if width else w
        self.d = depth if depth else d
        self.table = [[0] * self.w for _ in range(self.d)]
        self.n = 0

    def _col(self, row, key):
        return h64(key, self.seed * 1_000_003 + row) % self.w

    def add(self, key, count=1):
        """Add `count` (>= 0) occurrences of key: bump the key's cell in every row, and self.n."""
        self.n += count
        for r in range(self.d):
            self.table[r][self._col(r, key)] += count

    def estimate(self, key):
        """Never below the true count. Minimum over the d cells the key hashes to."""
        return min(self.table[r][self._col(r, key)] for r in range(self.d))

Milestone 2: merging sketches

A sketch is a linear function of the stream: add the counts from two streams cell by cell and you have the sketch of the two streams together. That is the property that lets 50 partitions each keep a sketch and a merger add them (chapter 12, deep dive 4), and lets a window be the sum of minute buckets. It holds only if the sketches have the same shape and the same hash functions: seeds are configuration, never random per process. Adding cells of sketches that hash differently produces plausible-looking nonsense, so the merge must refuse.

Solution spoiler 
def merge(self, other):
    if not self.compatible(other):
        raise ValueError("cannot merge count-min sketches with different (width, depth, seed)")
    out = CountMin(self.eps, self.delta, self.seed, width=self.w, depth=self.d)
    out.table = [[a + b for a, b in zip(r1, r2)] for r1, r2 in zip(self.table, other.table)]
    out.n = self.n + other.n
    return out

Milestone 3: Space-Saving heavy hitters

A count-min sketch can answer "how many times was x seen?" but cannot list its heavy keys. For the list you want a heavy-hitter summary. Space-Saving (Metwally, Agrawal and El Abbadi, 2005) keeps at most m counters (count, err). A tracked key is incremented. A new key takes a free slot, or, when the table is full, evicts the smallest counter and inherits its value: count = old_min + 1, err = old_min. So counts only overestimate, and count − err ≤ true ≤ count. Because every event adds exactly one to exactly one counter, the counters always sum to N, which gives the guarantees the check tests: an untracked key has true ≤ min counter ≤ N/m, and every key with true > N/m is tracked.

Two more ideas make it useful. bounds(key) returns a certain interval for any key, tracked or not. And guaranteed(k) says whether the top-k set is provably correct: the smallest lower bound among the k items must beat the largest upper bound of everything else. When it is true you can publish the list without an asterisk; when it is false you know a close race is hiding in the error bars. Space-Saving is the choice chapter 12 recommends for the list itself, with a count-min sketch kept for arbitrary key lookups.

Your task

Hints try without first
  • The heap holds (count, key) pairs; an entry is stale unless self.count.get(key) == count. _min_entry() is given and skips stale ones: push a new entry on every update.
  • On eviction: old, victim = self._min_entry(), delete the victim from both dicts, then count[key] = old + c, err[key] = old.
  • min_count() is 0 while the table has free slots: every key seen so far is tracked, so an unseen key has count 0.
  • A worked example in the check: the stream a a b c with m = 2 ends as [('a', 2, 0), ('c', 2, 1)].
Solution spoiler 
class SpaceSaving:

    def __init__(self, m):
        self.m = m
        self.count = {}
        self.err = {}
        self.n = 0
        self._heap = []          # (count, key) entries, lazily invalidated: stale if count[key] != entry count

    def _min_entry(self):
        """Smallest (count, key) among tracked keys; pops stale heap entries on the way."""
        while self._heap:
            c, k = self._heap[0]
            if self.count.get(k) == c:
                return c, k
            heapq.heappop(self._heap)
        return None

    def update(self, key, c=1):
        """Observe `c` more occurrences of key."""
        self.n += c
        if key in self.count:
            self.count[key] += c
        elif len(self.count) < self.m:
            self.count[key] = c
            self.err[key] = 0
        else:
            old, victim = self._min_entry()
            del self.count[victim]
            del self.err[victim]
            self.count[key] = old + c
            self.err[key] = old
        heapq.heappush(self._heap, (self.count[key], key))
        if len(self._heap) > 8 * self.m + 64:            # keep the lazy heap from growing without bound
            self._heap = [(v, k) for k, v in self.count.items()]
            heapq.heapify(self._heap)

    def min_count(self):
        """Upper bound on the true count of any key that is NOT tracked: the smallest counter if
        the table is full, else 0 (every key seen so far is tracked)."""
        if len(self.count) < self.m:
            return 0
        return self._min_entry()[0]

    def bounds(self, key):
        """(lower, upper) bounds on the true count of key."""
        if key in self.count:
            return self.count[key] - self.err[key], self.count[key]
        return 0, self.min_count()
def top(self, k):
    items = sorted(self.count.items(), key=lambda kv: (-kv[1], kv[0]))[:k]
    return [(key, c, self.err[key]) for key, c in items]
def guaranteed(self, k):
    items = sorted(self.count.items(), key=lambda kv: (-kv[1], kv[0]))
    if len(items) <= k:
        return all(self.err[key] == 0 for key, _ in items) and len(self.count) < self.m
    lower = min(c - self.err[key] for key, c in items[:k])
    upper = items[k][1]
    return lower > upper

Milestone 4: HyperLogLog

Counting distinct users per key exactly needs a set per key. HyperLogLog (Flajolet, Fusy, Gandouet and Meunier, 2007) hashes each item to 64 bits, uses the first p bits to choose one of m = 2p registers, and keeps in that register the largest ρ seen, where ρ is the position of the leftmost 1 among the remaining bits. The longest run of leading zeros across many random hashes is about log2 of how many there were; averaging over m registers with a harmonic mean tames the outliers. The estimate is αm² / Σ2−reg with α = 0.7213/(1 + 1.079/m), and the standard error is about 1.04/√m.

The raw formula is badly biased when most registers are still empty (try ten items in 1,024 registers). The fix is linear counting: if the estimate is at most 2.5m and V registers are still zero, return m·ln(m/V). Merging two sketches is a register-wise maximum, which is why distinct counts survive partitioning, and why adding the same item twice changes nothing.

  • sum(2.0 ** -r for r in self.reg) is the denominator. self.reg.count(0) gives V.

Solution spoiler 
class HyperLogLog:

    def __init__(self, p=12, seed=0):
        self.p, self.m, self.seed = p, 1 << p, seed
        self.reg = [0] * self.m

    def add_hash(self, x):
        """Fold one 64-bit hash value into the registers."""
        idx = x >> (64 - self.p)
        rest = x & ((1 << (64 - self.p)) - 1)
        rho = (64 - self.p) - rest.bit_length() + 1
        if rho > self.reg[idx]:
            self.reg[idx] = rho

    def add(self, item):
        """Count an item: hash it with h64 and a seed, then add_hash (given)."""
        self.add_hash(h64(item, self.seed))

    def count(self):
        """Estimated number of distinct items.

        raw = alpha * m^2 / sum(2 ** -reg[i])  with alpha = 0.7213 / (1 + 1.079 / m).
        Small-range correction: if raw <= 2.5 * m and some register is still zero (V of them),
        use linear counting instead:  m * ln(m / V).  Otherwise return raw."""
        m = self.m
        alpha = 0.7213 / (1 + 1.079 / m)
        raw = alpha * m * m / sum(2.0 ** -r for r in self.reg)
        if raw <= 2.5 * m:
            zeros = self.reg.count(0)
            if zeros:
                return m * math.log(m / zeros)
        return raw

    def merge(self, other):
        """Return a NEW HyperLogLog for the union of both sets: the register-wise maximum.
        Raise ValueError if p or seed differ."""
        if (self.p, self.seed) != (other.p, other.seed):
            raise ValueError("cannot merge HyperLogLogs with different p or seed")
        out = HyperLogLog(self.p, self.seed)
        out.reg = [max(a, b) for a, b in zip(self.reg, other.reg)]
        return out

Milestone 5: a windowed trending detector

Popular is not trending. The top of any all-time list is always the same giants; trending means unusually high compared with that key's own normal (chapter 12, deep dive 3). The detector does what the chapter describes with the pieces you have just built:

  • Cut event time into tumbling windows; each keeps a count-min sketch, a Space-Saving table of candidates, and its total n.
  • When a window closes, merge the previous B sketches into a baseline and score each candidate: (cur + α) / (base + α), where cur is the window's sketch estimate and base is the baseline estimate per window, scaled by this window's volume relative to the baseline's, so that a day-wide surge is not a trend of every key.
  • Alert only when cur ≥ min_count and score ≥ ratio. The smoothing α keeps a key that went from 0 to 5 events from scoring 6×; min_count stops tiny absolute blips; both numbers are product decisions, which is why they are parameters.

Notice that cur comes from the count-min sketch, not the Space-Saving counter. A tail key that was just evicted into the table inherits a large Space-Saving count it never earned; scored on it, it would look like a trend. The sketch estimate of a tail key is small and so is its baseline, so the ratio stays near 1.

Your task

Solution spoiler 
def trend_score(cur, base, alpha):
    return (cur + alpha) / (base + alpha)
def observe(self, ts, key):
    w = int(ts // self.window_s)
    if self.cur_w is None:
        self._open(w)
    if w < self.cur_w:
        self.late += 1
        return
    while self.cur_w < w:
        self._close()
        self._open(self.cur_w + 1)
    self.cms.add(key)
    self.ss.update(key)
    self.n += 1
def _close(self):
    if len(self.history) == self.B:
        base_cms = self.history[0][0]
        for cms, _, _ in list(self.history)[1:]:
            base_cms = base_cms.merge(cms)
        mean_n = sum(n for _, _, n in self.history) / self.B
        scale = (self.n / mean_n) if mean_n else 1.0
        for key in sorted(self.ss.count):
            cur = self.cms.estimate(key)
            base = base_cms.estimate(key) / self.B * scale
            score = trend_score(cur, base, self.alpha)
            if cur >= self.min_count and score >= self.ratio:
                self.alerts.append((self.cur_w, key, score, cur))
    self.history.append((self.cms, self.ss, self.n))

Look under the hood

  • The bound is a worst case, the tail is the problem. The histogram above shows overcounts far below εN, yet the first experiment below shows a rank-1,000 key reading up to 17× its true count. Both are true: the error is additive and comparable to the total stream, so it is negligible for the head and ruinous for the tail. This is chapter 12's "19×" in your own terminal.
  • Why a guaranteed top-k needs counters, not luck. With a flat distribution (s = 0.9) even 100 counters usually give the right top 10 but cannot prove it; with a skewed one (s = 1.2) 50 counters suffice. The proof depends on the gap between the 10th and 11th keys, not on the table size alone.
  • HyperLogLog's bias hump. The simple correction (linear counting below 2.5m) leaves a small positive bias just above it. Measured with p = 14: mean error +0.90% at n = 50,000 (about 3m) against about 0% at n = 10,000 or 200,000. HyperLogLog++ removes it with an empirical bias table; here it is a reminder that a standard error is an average over the whole range.
  • Sketches and money. Everything here overcounts or errs by a stated margin; none of it belongs in billing. Chapter 12 keeps an exact batch recount beside the streaming path for that reason; the ad-click studio makes the point explicit.

Distributed systems connection

Mergeability is what makes these structures distributed data structures: a sketch is a commutative, associative, idempotent-where-it-matters summary, the same algebra as the CRDTs in CRDTs (the HyperLogLog merge is literally a max-register grow-only CRDT). Seeds as configuration echo the version-skew problems of replayable logs, and event-time windows with late data are the stream-processing story of streams and CDC. The capstone studio ad click aggregator reuses all of it, with an exact path beside.

What you learned

  • A Count-Min sketch of ⌈e/ε⌉ × ⌈ln 1/δ⌉ counters never undercounts and overcounts by more than εN with probability at most δ; the error is relative to the whole stream, so the tail is unreliable.
  • Merging is cell-wise addition, valid only for identical shape and seeds; refuse otherwise. Seeds are configuration.
  • Space-Saving gives a top-k with a per-item error bound and a way to know when the list is provably right; every key above N/m is always present.
  • HyperLogLog needs the small-range correction and gives about 1.04/√m error in a few kilobytes; merge is a register-wise max.
  • "Trending" is a ratio against the key's own baseline, smoothed, volume-normalised and gated by a minimum count; score from the sketch, not from an evicted counter.
  • State a guarantee, then test it with seeded streams and exact counts, printing the seed on failure.

Check your understanding

A Count-Min sketch with ε = 0.001 sees a stream of 10 million events. A key that occurred 500 times is reported as 7,300. Is that a bug?

  1. Yes: the sketch must never overcount
  2. No: the bound allows an overcount up to εN = 10,000, with probability at least 1 − δ
  3. Yes: the error should be at most 1% of the key's own count
  4. No, but only because collisions can also undercount
The guarantee is additive and relative to the total weight N, not to the key. 7,300 − 500 = 6,800 is within εN = 10,000. It is exactly why the tail of a count-min estimate cannot be trusted and why chapter 12 pairs the sketch with a candidate structure.

Why must two sketches that you want to merge share their seeds?

  1. So that the table is smaller
  2. Because the seed is the stream's identity
  3. Because cell (r, c) must mean the same set of keys in both; otherwise adding cells mixes unrelated keys
  4. It does not matter: the sum is always an upper bound
A cell counts the keys that hash there, and that depends on the hash function. With different seeds, adding cells adds counts of different key sets, so estimates are neither upper nor lower bounds. Hence ValueError, and hence seeds are configuration, never random per process.

Space-Saving with m = 100 counters has seen N = 1,000,000 events. Which statement is certain?

  1. Any key with more than 10,000 occurrences is in the table
  2. The top 10 keys are in the table
  3. Every counter is within 1% of its true count
  4. The smallest counter is exactly N/m
The counters sum to N, so the smallest is at most N/m = 10,000, and a key above that can never have been the minimum when evicted. Nothing is promised for the top 10 unless guaranteed(10) holds, and an individual error can be as large as N/m.

A HyperLogLog with m = 4,096 registers reports 1,000,000 distinct users. Roughly what range is plausible for the true value (about 3 standard errors)?

  1. Exactly 1,000,000
  2. ±0.1%
  3. ±1.6%
  4. ±5%
The standard error is 1.04/√4096 ≈ 1.6%; three standard errors is about 5%. The error does not depend on how many items were counted, which is the point: 3 KB for any cardinality.

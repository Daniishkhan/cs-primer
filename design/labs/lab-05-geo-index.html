Lab 5: A Geospatial Index

"Who is near me?" over a million moving points, thousands of times a second. You build geohash cells and their neighbours (across boundaries, the antimeridian and the poles), a k-nearest search by expanding rings whose stopping rule is a distance, not a count, and a bucket quadtree that adapts to density. All of it is checked for exact agreement with brute force, and then benchmarked on 10,000 moving drivers by counting distance computations, so the trade-offs are numbers you can reproduce.

Why this lab matters

"Find the nearest drivers" is the question that sets the architecture of every marketplace on a map (chapter 14). The idea is easy to say: bucket the world into cells, look in the rider's cell and its neighbours. The bugs are in the details: a rider on a cell edge whose nearest driver is one cell over, a stopping rule that checks a count instead of a distance, neighbours that must wrap at the antimeridian and vanish at the poles, a cell size that suits the suburbs and drowns downtown. You will build the index, test it against brute force until the answers match exactly, then build the adaptive alternative and measure, by counting distance computations, when each one wins. The Uber H3 case study covers why a production system might choose hexagons; this lab is about why you need to search rings at all.

Counting work, not seconds

Wall-clock benchmarks of Python tell you about Python. Every index here inherits from SpatialIndex, whose dist() counts each haversine evaluation, and which also counts cells or nodes visited and structure changes caused by updates. Those counters are deterministic, so the benchmark gives the same numbers on every machine and run. Everything is seeded; the check brings its own reference geohash, its own integer-grid neighbours and its own brute-force oracle, and prints the failing seed and replay command.

What you'll build

Five milestones:

  1. Geohash encode and decode with the cell bounding box, verified against known vectors such as (57.64911, 10.40744) → u4pruydqqvj.
  2. Neighbour cells, including across the prime meridian, the antimeridian and past the poles.
  3. k-nearest by expanding rings with the correct stopping rule and haversine distances; results identical to brute force on seeded tests, in a city and across the whole world.
  4. A bucket quadtree with insert, delete, move and k-nearest, matching brute force.
  5. A location-update simulation of 10,000 moving drivers: ring search against quadtree against brute force, by distance computations, with the trade-offs written down.

Milestone 1: geohash encode and decode

A geohash names a rectangle on the map by interleaving two bisections: halve the longitude range, then the latitude range, then longitude again, writing 1 when the point is in the upper half. Five bits make one character of the alphabet 0123456789bcdefghjkmnpqrstuvwxyz (no a, i, l, o). Longer hashes are smaller cells inside the cell named by their prefix, which is what makes them usable as keys in any key-value store. Because the bits alternate, a character halves longitude three times and latitude twice, then the other way round, so cells alternate between 2:1 and 1:1 rectangles, and they shrink toward the poles in kilometres.

Decoding replays the bisection backwards to get the cell's bounding box; the centre of that box is the decoded point, and its height and width are what cell_dims must return. Chapter 14 uses this to pick a resolution from driver density; precision 6 (about 0.6 km × 1.2 km) is the city-scale cell. Boundaries need a convention: a value exactly on a midpoint goes to the upper half, so (0, 0) is the lower-left corner of the cell s, not the upper-right of its neighbour.

def cell_dims(precision):
    lat_bits = 5 * precision // 2
    lng_bits = (5 * precision + 1) // 2
    return 180.0 / (1 << lat_bits), 360.0 / (1 << lng_bits)
def encode(lat, lng, precision=9):
    lat = min(90.0, max(-90.0, lat))
    lng = min(180.0, max(-180.0, lng))
    lat_r, lng_r = [-90.0, 90.0], [-180.0, 180.0]
    out, bits, ch, even = [], 0, 0, True
    while len(out) < precision:
        rng, v = (lng_r, lng) if even else (lat_r, lat)
        mid = (rng[0] + rng[1]) / 2
        ch <<= 1
        if v >= mid:
            ch |= 1
            rng[0] = mid
        else:
            rng[1] = mid
        even = not even
        bits += 1
        if bits == 5:
            out.append(B32[ch])
            bits = ch = 0
    return "".join(out)
def decode_bbox(h):
    lat_r, lng_r, even = [-90.0, 90.0], [-180.0, 180.0], True
    for c in h:
        v = B32.index(c)
        for shift_ in (4, 3, 2, 1, 0):
            rng = lng_r if even else lat_r
            mid = (rng[0] + rng[1]) / 2
            if (v >> shift_) & 1:
                rng[0] = mid
            else:
                rng[1] = mid
            even = not even
    return lat_r[0], lat_r[1], lng_r[0], lng_r[1]
def decode(h):
    a, b, c, d = decode_bbox(h)
    return (a + b) / 2, (c + d) / 2

Milestone 2: neighbour cells

A rider near the edge of a cell has nearer drivers in the next cell, so every index query must look at neighbours. Two points 18 m apart can have hashes that differ in their first character (cells either side of longitude 0 are e... and s...), so "same prefix" tells you nothing about "near". Neighbours must be computed geometrically or with integer arithmetic on the cell grid.

The easiest correct route is to treat the precision-p world as a grid of rows × columns cells: a cell is a (row, col) pair, a neighbour is (row + di, col + dj), and you convert back by encoding the centre of the target cell. Two rules matter. Columns wrap: east of the last column is column 0, because longitude +180 meets −180. Rows do not wrap: north of the top row is nothing at all, so the neighbour is None. Everything in milestone 3 is built on shift(h, di, dj).

def cell_ij(h):
    dlat, dlng = cell_dims(len(h))
    a, _, c, _ = decode_bbox(h)
    return int(round((a + 90.0) / dlat)), int(round((c + 180.0) / dlng))
def ij_cell(row, col, precision):
    dlat, dlng = cell_dims(precision)
    return encode(-90.0 + (row + 0.5) * dlat, -180.0 + (col + 0.5) * dlng, precision)
def shift(h, di, dj):
    nrows, ncols = grid_size(len(h))
    row, col = cell_ij(h)
    row += di
    if row < 0 or row >= nrows:
        return None
    return ij_cell(row, (col + dj) % ncols, len(h))
def neighbors(h):
    return {name: shift(h, di, dj) for name, (di, dj) in DIRS.items()}

Milestone 3: k-nearest by expanding rings

The query: search the rider's cell (ring 0), then the 8 cells around it (ring 1), then the 16 around those, and so on, keeping the best k by true haversine distance. The one decision that matters is when to stop, and chapter 14 gives the rule: after rings 0..r anything unsearched is at least r cell-sides away, because the rider is somewhere inside their own cell; stop when you hold k candidates and the k-th is closer than that.

On a sphere "r cell-sides" needs care, because cells are narrower in kilometres at high latitude. The lab asks for a rigorous version, unsearched_bound: anything outside the block is either more than r rows away (at least R·radians(r·dlat) metres, from the haversine formula) or more than r columns away, in which case it is at least R·asin(cos(lat)·sin(r·dlng)) metres away, the cross-track distance to the nearest meridian that is not searched. Take the smaller. A direction where the block already covers everything (it touches both poles, or wraps all columns) does not count; if both are closed the whole world has been searched and the bound is infinite. The check tests the bound itself on 47,862 points outside random blocks, including near the poles, so a bound that is merely plausible fails.

Hints try without first
  • ring(h, r): generate only the perimeter (top and bottom rows, then the two side columns without corners) as (row, col) pairs in a set, then convert. Scanning all (2r+1)^2 shifts works but is cubic in r overall.
  • Compare with slack: stop when kth < bound * (1 - SLACK); floating-point equality at the boundary is a classic source of one-in-a-million wrong answers.
  • Sort candidates by (distance, id) and cut to k after each ring.
  • update touches the cell sets only when the driver's cell changed, and deletes empty sets so footprint() counts non-empty cells.

def ring(h, r):
    if r == 0:
        return [h]
    p = len(h)
    nrows, ncols = grid_size(p)
    row, col = cell_ij(h)
    cells = set()
    for dj in range(-r, r + 1):                       # the top and bottom rows of the square ring
        for di in (-r, r):
            if 0 <= row + di < nrows:
                cells.add((row + di, (col + dj) % ncols))
    for di in range(-r + 1, r):                       # the left and right columns, without the corners
        if 0 <= row + di < nrows:
            for dj in (-r, r):
                cells.add((row + di, (col + dj) % ncols))
    return sorted(ij_cell(i, j, p) for i, j in cells)
def unsearched_bound(lat, h, r):
    p = len(h)
    nrows, ncols = grid_size(p)
    dlat, dlng = cell_dims(p)
    row, _ = cell_ij(h)
    bounds = []
    if row + r < nrows - 1 or row - r > 0:
        bounds.append(R_EARTH * math.radians(r * dlat))
    if 2 * r + 1 < ncols:
        delta = min(90.0, r * dlng)
        s = abs(math.cos(math.radians(lat))) * math.sin(math.radians(delta))
        bounds.append(R_EARTH * math.asin(min(1.0, s)))
    return min(bounds) if bounds else INF
class GeoHashIndex(SpatialIndex):

    def __init__(self, precision):
        super().__init__()
        self.precision = precision
        self.cells = {}          # hash -> set of ids
        self.where = {}          # id -> hash

    def update(self, did, lat, lng):
        """Insert or move. Only touch the cell sets when the cell actually changes (count that in self.ops)."""
        h = encode(lat, lng, self.precision)
        old = self.where.get(did)
        if old != h:
            if old is not None:
                self.cells[old].discard(did)
                if not self.cells[old]:
                    del self.cells[old]
            self.cells.setdefault(h, set()).add(did)
            self.where[did] = h
            self.ops += 1
        self.pos[did] = (lat, lng)

    def remove(self, did):
        h = self.where.pop(did)
        self.cells[h].discard(did)
        if not self.cells[h]:
            del self.cells[h]
        del self.pos[did]
        self.ops += 1
    def knn(self, lat, lng, k, max_rings=None):
    h0 = encode(lat, lng, self.precision)
    best = []
    r = 0
    while True:
        for c in ring(h0, r):
            self.visits += 1
            for did in self.cells.get(c, ()):
                best.append((self.dist(lat, lng, did), did))
        best.sort()
        del best[k:]
        bound = unsearched_bound(lat, h0, r)
        if bound == INF or (len(best) == k and best[-1][0] < bound * (1 - SLACK)):
            break
        r += 1
        if max_rings is not None and r > max_rings:
            break
    return best

Milestone 4: a quadtree

A fixed grid has one resolution for the whole map. A bucket quadtree splits a square into four only where it holds more than capacity points, so downtown gets small leaves and the suburbs get large ones. The data structure is given (_Node, descent and the containment test); you write the three operations that keep it healthy and the search that uses it:

  • Split a leaf that overflows into four quadrants (and recurse if all its points land in one child). A depth cap stops sixty drivers on one spot from splitting forever.
  • Delete and collapse: after removing a driver, if the four children of its parent are all leaves holding at most capacity in total, merge them back; repeat upward. Without this a tree that has seen a rush hour stays enormous forever.
  • Move: a driver who stays inside her leaf needs no structure change at all; most pings are like that.
  • Nearest-k by best-first search: a heap of (lower bound, node); pop the closest box; stop when its bound exceeds the k-th distance found. The bound for a latitude/longitude box is given as rect_lower_bound.

  • _split: create four nodes, move each id to the right child and update self.leaf, clear the parent's ids, recurse into any child still over capacity.
  • _collapse: loop upward while all four children are leaves and their total is at most capacity; adjust self.nodes by 4 each time.

def _split(self, n):
    la, lb, ga, gb = n.lat0, n.lat1, n.lng0, n.lng1
    lm, gm = (la + lb) / 2, (ga + gb) / 2
    d = n.depth + 1
    n.kids = [_Node(la, lm, ga, gm, d, n), _Node(la, lm, gm, gb, d, n),
              _Node(lm, lb, ga, gm, d, n), _Node(lm, lb, gm, gb, d, n)]
    self.nodes += 4
    self.ops += 1
    for did in n.ids:
        lat, lng = self.pos[did]
        kid = n.kids[self._kid_index(n, lat, lng)]
        kid.ids.add(did)
        self.leaf[did] = kid
    n.ids = set()
    for kid in n.kids:
        if len(kid.ids) > self.capacity and kid.depth < self.max_depth:
            self._split(kid)
def _collapse(self, n):
    while n is not None and n.kids is not None:
        if any(k.kids is not None for k in n.kids):
            return
        total = sum(len(k.ids) for k in n.kids)
        if total > self.capacity:
            return
        ids = set()
        for k in n.kids:
            ids |= k.ids
        n.kids, n.ids = None, ids
        for did in ids:
            self.leaf[did] = n
        self.nodes -= 4
        self.ops += 1
        n = n.parent
def update(self, did, lat, lng):
    old = self.leaf.get(did)
    if old is not None:
        if self._inside(old, lat, lng):
            self.pos[did] = (lat, lng)
            return
        self.remove(did)
    self.pos[did] = (lat, lng)
    n = self._descend(lat, lng)
    n.ids.add(did)
    self.leaf[did] = n
    if len(n.ids) > self.capacity and n.depth < self.max_depth:
        self._split(n)
def remove(self, did):
    n = self.leaf.pop(did)
    n.ids.discard(did)
    del self.pos[did]
    self._collapse(n.parent)
def knn(self, lat, lng, k):
    best = []
    heap = [(0.0, 0, self.root)]
    tie = 1
    while heap:
        lb, _, n = heapq.heappop(heap)
        if len(best) == k and lb > best[-1][0] * (1 + SLACK) + 1e-6:
            break
        self.visits += 1
        if n.kids is None:
            for did in n.ids:
                best.append((self.dist(lat, lng, did), did))
            best.sort()
            del best[k:]
        else:
            for kid in n.kids:
                heapq.heappush(heap, (rect_lower_bound(lat, lng, kid.lat0, kid.lat1, kid.lng0, kid.lng1), tie, kid))
                tie += 1
    return best

Milestone 5: 10,000 moving drivers

The simulation is given. It scatters 10,000 drivers over a 40 km box, 60% in five gaussian hotspots and 40% uniform; every tick each of two thirds of them takes a 10 to 60 m step and reports it to every index; then 20 riders ask for the 8 nearest drivers. Riders come from the same mixture, so most are downtown. The check compares every answer with brute force and prints the counters. Your job is to read the table and write down the trade-offs in your own words; the numbers below are from the reference.

What the numbers say, and what to take away:

  • Both indexes are a hundred times cheaper than a scan in distance computations (0.3% to 2.5% of 10,000), and their answers are identical.
  • A fixed cell size is a bet on density. geohash-6 needs about 400 distance computations downtown (the 3×3 block holds ~100 drivers per cell) but 53 in the suburb; geohash-7 flips the trade: 38 downtown and 17 in the suburb, but the suburb search now visits about 312 cells, mostly empty, to find eight drivers. Cell lookups are cheaper than distance computations, but they are not free.
  • The quadtree is flat (26 and 27) because it follows density, at the price of a taller structure to traverse and a more complicated update. Its updates cause a structure change only 0.034 times per move (capacity 8), against 0.06 to 0.31 for geohash cell changes.
  • The hotspot stress test (3,000 drivers in 300 m) is the fixed grid's worst case: every query computes about 3,000 distances at precision 6, but 26 in the quadtree.
  • Memory is cells (2,209 at precision 6, 7,177 at precision 7) against nodes (3,681 at capacity 8; 985 at 32).

Chapter 14's recommendation follows: start with a geohash or H3 index in a sharded in-memory map because it is simple and updates are trivial; move to a quadtree (or multi-resolution cells) when density varies enough that no single resolution serves both downtown and the suburbs.

Look under the hood

  • Geohash cells are rectangles that change shape. At precision 6 a cell is about 611 m × 1.22 km at the equator and narrower in metres further north. A correct stopping bound uses the latitude of the rider; a bound that assumes a constant cell width fails near the poles, and the check's bound test is where it shows.
  • The antimeridian and the poles are not corner cases, they are the test. The world seeds put 36% of the drivers within a degree of ±180 or within 1.5 degrees of a pole. An implementation that clamps columns instead of wrapping them fails there and passes every city test.
  • Exactness is a stopping-rule property. The search is exact because the bound is a true lower bound; shave it for speed and the answers silently degrade, without any test in a city noticing. Ties and float slack deserve the same suspicion.
  • H3 and S2 change the cell, not the idea. Hexagons make the ring uniform (every neighbour equally far), but you still expand rings and still stop on a distance bound. See the H3 case.

                    best.append((self.dist(lat, lng, did), did))
            if len(best) >= k:
                break
            r += 1
        best.sort()
        return best[:k]

Distributed systems connection

Cell ids are partition keys: shard the index by a geohash prefix and a nearest-driver query becomes a scatter to the shards covering the ring, exactly the neighbour-crossing problem milestone 2 solves, one level up (partitioning). The index itself is ephemeral soft state: lose a node and drivers re-announce within one ping interval, which is why chapter 14 keeps it in memory and puts the durable assignment behind a lease with a fencing token (leases and fencing); the same pattern is the scheduler in Lab 6.

What you learned

  • A geohash is two bisections interleaved; a longer hash is a smaller cell inside the cell its prefix names; prefixes say nothing about nearness across boundaries.
  • Neighbours are grid arithmetic: columns wrap at the antimeridian, rows stop at the poles.
  • Nearest-k by rings is exact only if you stop on a distance bound, not on a candidate count; on a sphere the bound depends on latitude.
  • A quadtree adapts to density; the price is splits and merges on update and a pointer structure to traverse. A move that stays in its leaf is free.
  • Fixed cells are a bet on density; the hotspot is where it loses. Count distance computations, cells and structure changes, not seconds.
  • Test against brute force with seeds, with ties, and at the places a map is discontinuous.

Check your understanding

Two drivers are 18 m apart but their geohashes share no prefix. What does this tell you about prefix-based search?

  1. The geohash implementation is buggy
  2. It is impossible: nearby points always share a prefix
  3. A prefix match is sufficient for nearness, not necessary: you must always search the neighbouring cells
  4. Use a longer precision to fix it
Cells either side of a major boundary (such as longitude 0) have unrelated prefixes. That is why every query includes the neighbours, and why the stopping rule is about distance.

A nearest-3 search has examined the rider's own cell and holds 3 candidates, the farthest at 400 m. The cell is 600 m on a side. Should it stop?

  1. Yes: it already has 3 candidates
  2. No: the rider may be at the cell's edge, so a driver in the next cell may be nearer than 400 m; the bound after ring 0 is 0
  3. Yes, because 400 m is less than 600 m
  4. Only if the density is high
Anything unsearched is at least r cells away where r is the last ring searched; for ring 0 that is 0 m. The search must examine ring 1 and then stop only if the third-nearest is closer than one cell side.

Which workload is hardest for a fixed-precision geohash index but easy for a quadtree?

  1. Uniform drivers over a large area
  2. Very few drivers
  3. Frequent small moves
  4. A crowd of thousands of drivers inside one cell
A cell is read whole, so a dense cell costs one distance per resident whatever k is. The quadtree keeps splitting where the crowd is, so the query touches a few small leaves (26 against 3,000 in the lab's hotspot test).

Why does the quadtree collapse four sibling leaves into their parent after a delete?

  1. Otherwise the tree grows with every busy period and never shrinks, wasting memory and traversal time
  2. Because leaves may not be empty
  3. Because the heap requires it
  4. To keep the tree balanced
Splits are a response to density that has since gone away. Without merging, a city's rush hour leaves a permanent deep tree; collapsing keeps the structure proportional to the current number of drivers.

Lab 2: Rate Limiters

A rate limiter looks like a counter, and chapter 5 argued that it is really a small distributed system. In this lab you prove it. You build the token bucket and the two sliding-window algorithms on a clock you control, and you test them with properties instead of examples: exact for the log, bounded for the counter, bursts only up to capacity. Then you move the counter into a shared store, put several app nodes with network delay in front of it, and measure what the chapter only asserted: how much a local limiter over-admits as its sync interval grows, what fail-open and fail-closed really do when the store disappears, and how clock skew quietly doubles your limit.

Why this lab matters

Rate limiting is on the hot path of every request, so the cheap algorithm choices (which window, how much state) and the expensive ones (shared state, failure policy) both show up as money and outages. The usual way people learn this is by shipping a limiter that is subtly wrong: it lets a burst through at a window edge, it over-admits by 3x once it runs on more than one node, or it takes the whole API down with it when its store restarts. Every one of those can be reproduced and measured in a few seconds of simulated time, which is what this lab does. You will also practise the most valuable testing habit for this kind of code: stating the property ("in any window of length W, at most L admitted") and checking it on thousands of generated traces, with the seed printed when it fails, instead of hand-picking a few cases. The design decisions of chapter 5 (algorithm per number, atomic script call, fail-open policy, local limiters with sync) each turn into a measured number here, and the failure-handling vocabulary comes from resilience.

Simulated time: no sleeping, no sockets, no threads

Nothing in this lab ever waits for real. A limiter takes a clock object and calls clock.now(); the tests move a ManualClock by hand, and the distributed experiments run on a small event loop (Sim) whose clock jumps from one event to the next. The network is a seeded random delay of 1 to 5 ms each way; the shared store is an object whose methods run at one instant of simulated time, so each is atomic by construction. Randomness comes only from random.Random(seed), and trace times are multiples of 1/1024 s so the arithmetic is exact in floating point, which lets the tests demand exact answers at window edges. The whole check takes about three seconds. A failing property prints its seed; replay just that one with python3 check.py solution 4 7 (milestone 4, seed 7). Python 3.8 or newer, standard library only.

What you'll build

Five milestones, each building on the last:

  1. A token bucket on an injected clock: burst up to capacity, refill at the rate, retry_after, and a clock that steps backwards.
  2. Sliding windows: the exact sliding-window log, and the sliding-window counter with the weighted-previous-window approximation. A fixed window is given as the baseline that fails at edges.
  3. Property tests: a sliding-window measurement helper, a trace replayer and a trace generator with an adversarial "edges" shape; then the properties themselves, run on 160 generated traces.
  4. A global limiter over a simulated shared store with an atomic increment and a TTL, several app nodes, and network delay, set against a read-then-write limiter that races.
  5. The real-world part: local limiters with periodic sync (over-admission against the sync interval), fail-open versus fail-closed versus a local fallback when the store is down, and clock skew between nodes.

Milestone 1: a token bucket on an injected clock

A token bucket holds up to capacity tokens and receives rate new ones per second. A request spends tokens (normally one) or is rejected. Two numbers, two meanings: the rate is the long-run average you allow, and the capacity is the largest burst. That is why chapter 5 recommends it as the default for APIs: real clients are bursty, and the bucket allows exactly the burst you chose and no more.

The implementation needs no timer. It is lazy: remember the token count and the time you last looked, and on every call add rate × (now - last) capped at capacity. State is two numbers per key, which is why a limiter for ten million keys fits in a gigabyte (chapter 5's estimate). The bucket never calls time.time(). It is handed a clock, and that one design choice is what makes every test in this lab possible: a test can say "advance 0.5 seconds" and mean it.

Two details are worth getting right now because they bite later. A rejected request must spend nothing, or a client hammering a limit digs itself deeper. And a clock that steps backwards (an NTP correction, or a skewed node, milestone 5) must not mint tokens and must not freeze the bucket: re-anchor last to the new time and carry on.

Your task

Complete TokenBucket: _refill() (lazy refill, capped at capacity, tolerant of a clock that goes backwards), tokens(), allow(cost=1.0) (spend and return True, or return False and spend nothing) and retry_after(cost=1.0) (seconds until cost tokens exist, 0.0 if they do now). The constructor is given; the bucket starts full.

Hints try without first

  • Compare with a tiny tolerance (self._tokens + 1e-9 >= cost), because refilling adds floating-point fractions. Do not subtract if the comparison fails.
  • retry_after: after refilling, missing = cost - tokens; return 0 if missing is tiny, else missing / rate.
  • A request costing more than the capacity can never be admitted; the code needs no special case for it, but be sure it does not hang or go negative.

class TokenBucket:
    """Tokens drip in at `rate` per second up to `capacity`; each request spends `cost`.

    The bucket is lazy: no timer fills it. Every call first adds rate x (time since the
    last call), capped at capacity. It starts full.
    """

    def __init__(self, rate, capacity, clock):
        self.rate = float(rate)
        self.capacity = float(capacity)
        self.clock = clock
        self._tokens = float(capacity)
        self._last = clock.now()

    def _refill(self):
        now = self.clock.now()
        dt = now - self._last
        if dt > 0:
            self._tokens = min(self.capacity, self._tokens + dt * self.rate)
        self._last = now            # if the clock stepped backwards we re-anchor: no refill, no freeze

    def tokens(self):
        """Tokens available right now (after refilling)."""
        self._refill()
        return self._tokens

    def allow(self, cost=1.0):
        """Spend `cost` tokens and return True, or return False and spend nothing."""
        self._refill()
        if self._tokens + EPS >= cost:
            self._tokens -= cost
            return True
        return False

    def retry_after(self, cost=1.0):
        """Seconds until `cost` tokens will be available (0.0 if they are now)."""
        self._refill()
        missing = cost - self._tokens
        return 0.0 if missing <= EPS else missing / self.rate

Milestone 2: sliding windows, exact and approximate

A fixed window counts requests in aligned intervals ("this clock minute") and resets at the edge. It costs one counter, and it is wrong at the boundary: a client can send a full allowance in the last moments of one window and another in the first moments of the next, twice the limit in a fraction of a window. The baseline class is given so you can watch it fail. Chapter 5's table lists the two ways out.

  • The sliding-window log remembers the timestamp of every admitted request and admits a new one only if fewer than limit lie in the last window seconds. It is exact, and costs up to limit timestamps per key (chapter 5's estimate: about 850 bytes against 64, thirteen times more state). Use it for small limits where exactness matters, such as five login attempts per fifteen minutes.
  • The sliding-window counter keeps two counters, the current window's and the previous one's, and estimates the sliding count as previous × (1 - fraction of the current window elapsed) + current. It assumes the previous window's requests were spread evenly, which is where the error comes from. Two numbers per key; a good general limiter when "close enough" is enough.

Your task

Complete SlidingWindowLog.allow() (half-open window: a request at time t counts the admitted requests in (t - window, t]; rejected requests are not logged) and SlidingWindowCounter: _roll(now) (move to the current window; the old current becomes previous only if the new window is the very next one, otherwise previous is 0), estimate() and allow() (admit if estimate + 1 <= limit).

Hints try without first

  • Counter: idx = floor(now / window). If it differs from the stored index, set prev = cur if idx == old_idx + 1 else 0, then cur = 0. The fraction elapsed is (now - idx * window) / window.
  • Call _roll(now) at the top of estimate(), so both estimate and allow see a rolled state.
  • A rejected request must not increment anything. Only the admitted ones are counted.

class SlidingWindowLog:
    """Exact: remember the timestamp of every admitted request in the last `window` seconds.

    A request at time t is admitted if fewer than `limit` admitted requests lie in the
    half-open interval (t - window, t]. Rejected requests are not logged.
    """

    def __init__(self, limit, window, clock):
        self.limit, self.window, self.clock = limit, window, clock
        self._log = deque()

    def allow(self):
        now = self.clock.now()
        while self._log and self._log[0] <= now - self.window:
            self._log.popleft()
        if len(self._log) < self.limit:
            self._log.append(now)
            return True
        return False

class SlidingWindowCounter:
    """Approximate: two counters (this window, the previous one) and a weighted sum.

    estimate = previous x (1 - fraction of the current window elapsed) + current.
    A request is admitted if estimate + 1 <= limit. The estimate assumes the previous
    window's requests were spread evenly, which is where the error comes from.
    """

    def __init__(self, limit, window, clock):
        self.limit, self.window, self.clock = limit, window, clock
        self._idx = math.floor(clock.now() / window)
        self._cur, self._prev = 0, 0

    def _roll(self, now):
        idx = math.floor(now / self.window)
        if idx != self._idx:
            self._prev = self._cur if idx == self._idx + 1 else 0
            self._cur = 0
            self._idx = idx

    def estimate(self):
        """The weighted estimate of requests in the last `window` seconds."""
        now = self.clock.now()
        self._roll(now)
        frac = (now - self._idx * self.window) / self.window
        return self._prev * (1.0 - frac) + self._cur

    def allow(self):
        if self.estimate() + 1.0 <= self.limit + EPS:
            self._cur += 1
            return True
        return False

Milestone 3: property tests

Examples test what you thought of; properties test what you should have thought of. Instead of "request 7 at t = 1.3 is rejected", state the guarantee the algorithm promises and check it on thousands of generated traces: in any window of length W, at most L admitted. The three guarantees of this lab differ in kind, and the difference is the lesson.

  • Exact (the log): the maximum admitted in any sliding window is ≤ limit, always, and decisions equal those of a reference implementation.
  • Bounded error (the counter): the maximum can exceed the limit, but by a provable bound. If the previous window held p requests all bunched into the part that still overlaps, the true count is p plus the current count while the estimate is only p(1 − f) plus the current count. So the true count stays below limit × (1 + f), under twice the limit. And on smooth traffic it is close to the log: the check demands the counter admit within 15% of what the log does.
  • Burst bounded by capacity (the bucket): after a long idle period a burst of any size admits exactly capacity, and in any window of length w the admitted count is at most capacity + rate × w.

Generating the traces is half the work. Steady traffic never finds a bug. Poisson traffic finds a few. The cruel shapes are bursts, and bursts placed on window edges: "edges" sends half a second's traffic just before each whole second and half just after. The check insists that your edges trace pushes the fixed window to at least 1.6x its limit; a generator that cannot hurt the baseline cannot be trusted to test anything else.

Your task

Hints try without first

  • "bursty": bursts start at Poisson times (4 a second on average) and each packs about rate / 4 requests into 50 ms. "edges": for each whole second k, put rate / 2 requests in the 100 ms before it and rate / 2 in the 100 ms after.
  • Sort and filter the final list to [0, duration). Use random.Random(seed), never the global generator.

def max_in_window(times, window):
    """The largest number of `times` (sorted) inside any half-open interval of length `window`.

    Two pointers: for each right end j, move i forward while times[j] - times[i] >= window.
    """
    best, i = 0, 0
    for j, t in enumerate(times):
        while t - times[i] >= window:
            i += 1
        best = max(best, j - i + 1)
    return best

def replay(limiter, clock, times):
    """Feed the request times to the limiter (setting the manual clock first); return admitted times."""
    out = []
    for t in times:
        clock.set(t)
        if limiter.allow():
            out.append(t)
    return out

def make_trace(kind, seed, duration, rate):
    """A sorted list of request times in [0, duration), on the 1/1024 s grid.

    kinds:
      "steady"  evenly spaced, `rate` per second
      "poisson" random gaps with mean 1/rate
      "bursty"  bursts of about rate/4 requests packed into 50 ms, 4 bursts a second on average
      "edges"   at every whole second, half a second's traffic just before and half just after
    """
    rng = random.Random(seed)
    times = []
    if kind == "steady":
        n = int(rate * duration)
        times = [_q(i * duration / n) for i in range(n)]
    elif kind == "poisson":
        t = rng.expovariate(rate)
        while t < duration:
            times.append(_q(t))
            t += rng.expovariate(rate)
    elif kind == "bursty":
        size = max(1, int(rate / 4))
        t = rng.expovariate(4.0)
        while t < duration:
            for _ in range(size):
                times.append(_q(t + rng.uniform(0, 0.05)))
            t += rng.expovariate(4.0)
    elif kind == "edges":
        half = max(1, int(rate / 2))
        for k in range(1, int(duration)):
            for _ in range(half):
                times.append(_q(k - rng.uniform(0.001, 0.1)))
                times.append(_q(k + rng.uniform(0.0, 0.1)))
    else:
        raise ValueError(f"unknown trace kind {kind!r}")
    return sorted(t for t in times if 0 <= t < duration)

Milestone 4: a global limiter over a shared store

One node's limiter protects one node. A fleet needs the count to be shared, and chapter 5's answer is a fast in-memory store and a single atomic call per request: increment the counter for the current window and return the new value. If it is at most the limit, admit. The counter's key names its window (rl:<window index>) and carries a TTL, so old windows evict themselves. This is a fixed window in the store (cheap, exact per key), so it inherits the edge effect of milestone 2; what the store buys is that every node sees the same count.

The simulation kit gives you an event loop, a network with seeded random delay, a store skeleton with outage intervals, and rpc(...), which runs an operation at the store after one network delay and calls you back after a second delay, or after a timeout if the store is down. Your jobs are the store's two primitives and the limiter's request path.

  • Atomic increment with a TTL. Store.incr(key, ttl, by=1) adds by and returns the new value; a missing or expired key is created with value by and expires ttl seconds from now; an existing key keeps its original expiry. Store.get returns 0 for missing or expired keys. Expiry is judged on the store's clock.
  • The TTL is two windows, not one. It starts at the first touch (a few milliseconds into the window), so a one-window TTL can expire the key while late requests for the same window are still in flight, and the counter silently restarts from zero. The experiment below measures what that costs.
  • Why atomicity matters. The given RacyGlobalLimiter reads the count with one round trip and writes count + 1 back with another. Under network delay, several nodes read the same value before any of them writes, and they all admit.

Your task

Write Store.get(key), Store.incr(key, ttl, by=1), GlobalLimiter.make_op() (the function to run at the store: INCR the counter named by the window of this node's clock, with a TTL of two windows) and GlobalLimiter.request(done) (send it with rpc; on a reply, call done(count <= limit); on None call self.failed(done), which milestone 5 writes).

def get(self, key):
    """The value of `key`, or 0 if it is missing or expired."""
    item = self._live(key)
    return 0 if item is None else item[0]

def incr(self, key, ttl, by=1):
    """Atomically add `by` and return the new value.

    If the key is missing or has expired it is created with value `by` and expires
    `ttl` seconds from now; an existing key keeps its original expiry (INCR then
    EXPIRE only when new).
    """
    item = self._live(key)
    if item is None:
        self.data[key] = [by, self.sim.now + ttl]
        return by
    item[0] += by
    return item[0]

def make_op(self):
    """The operation to run at the store: INCR the counter of the current window.

    The TTL is two windows, not one. It starts when the key is first touched (a few ms into the
    window), so a one-window TTL would let the key expire while late requests for the same window
    are still in flight, or while a node with a slow clock still uses it, and the counter would
    silently restart from zero.
    """
    ttl = 2 * self.window
    window = self.window
    if self.time_source == "store":
        return lambda st: st.incr(f"rl:{math.floor(st.now() / window)}", ttl=ttl)
    key = f"rl:{math.floor(self.clock.now() / window)}"
    return lambda st: st.incr(key, ttl=ttl)

def request(self, done):
    """Decide one request; call done(allowed) when the decision is made."""
    def on_reply(count):
        if count is None:
            self.failed(done)
        else:
            done(count <= self.limit)
    rpc(self.sim, self.net, self.store, self.make_op(), on_reply, self.timeout)

Milestone 5: local limiters, failure, and clocks

A round trip per request is a latency tax and a dependency. Chapter 5 sketched the alternative: each node counts locally and syncs with the store periodically. This is where the interesting engineering is, and it comes in three experiments.

5a. Local limiters with periodic sync

Each LocalSyncNode decides with no network call, from known (the global count as of its last sync, including its own requests up to then) and unsynced (what it has admitted since). Every sync_interval seconds it sends its unsynced count to the store (incr(key, by=unsynced)) and learns the new global total. Between syncs it is blind to everyone else, so the over-admission it permits is roughly "the rate times the staleness": about offered_rate × sync_interval, capped by what each node can admit alone. Two policies:

  • optimistic: admit while known + unsynced < limit. Accurate when traffic is balanced and syncs are frequent; it over-admits badly when syncs are slow.
  • conservative: admit while unsynced < (limit - known) / nodes, a fair share of what is left. It cannot over-admit much, and it pays by refusing legitimate traffic when the load is uneven (a node that gets most of the traffic is limited to its share).

5b. The store goes down: fail open, fail closed, or fall back

When rpc times out, the limiter must decide without the store. Three policies, set per limiter in on_error. Open admits everything: the API stays up and the protection vanishes. Closed rejects everything: the protection holds and the API is down for every client. Local falls back to a token bucket sized at limit / nodes per node: roughly the right total, with no coordination, from your milestone 1 code. Chapter 5's rule was to choose per endpoint (open for ordinary traffic, closed for a login endpoint or an expensive operation), and to alert either way.

5c. Clock skew between nodes

The window is named from a clock. If every node names it from its own clock and the clocks differ, then at the same instant node A is writing to window 7 and node B to window 8, and each window has its own full allowance. The mean rate is still the limit (one fresh counter a second), but the allowance arrives at different times on different nodes, and a sliding window can see nearly two allowances at once. The fix is to have one authority name the window: time_source="store" makes the store compute the window index inside the atomic operation (Redis's TIME command in a script), so every node agrees. Extend make_op with that branch. The clock theme is that of time revisited: the only clock everyone can agree on is the one they all ask.

Your task

Write LocalSyncNode.allow() (roll to the current window first; optimistic or conservative as above; spend one unit of the budget when it admits), LocalSyncNode.sync() (send unsynced with incr(by=unsynced) on the key of the window you are in, with a TTL of two windows; on a reply for the same window set known = total and subtract what you sent from unsynced; ignore a timeout) and GlobalLimiter.failed(done) (open, closed, or local, by self.on_error). Then add the time_source == "store" branch to make_op from milestone 4. start() and the experiment harnesses are given.

  • allow: self._roll() resets known and unsynced when the window index changes. Then left = limit - known - unsynced (optimistic) or (limit - known) / nodes - unsynced (conservative); admit if left >= 1.
  • sync: capture idx = self.widx and delta = self.unsynced before the call. In the callback, ignore None and ignore the reply if self.widx != idx. Otherwise self.known = total and self.unsynced -= delta (not = 0: more requests may have been admitted while the message was in flight).
  • If you set unsynced = 0 instead of subtracting, you forget requests admitted during the round trip and the limiter over-admits at every interval. The check's "all traffic on one node" test catches the opposite mistake as well.
  • failed: for "local", done(self.fallback.allow()); the fallback bucket is created in the constructor from your TokenBucket.
  • For time_source == "store" the key must be computed inside the operation, from the store's now(), because the node does not know the store's time when it builds the message.
Solution spoiler 
def make_op(self):
    """The operation to run at the store: INCR the counter of the current window.

    The TTL is two windows, not one. It starts when the key is first touched (a few ms into the
    window), so a one-window TTL would let the key expire while late requests for the same window
    are still in flight, or while a node with a slow clock still uses it, and the counter would
    silently restart from zero.
    """
    ttl = 2 * self.window
    window = self.window
    if self.time_source == "store":
        return lambda st: st.incr(f"rl:{math.floor(st.now() / window)}", ttl=ttl)
    key = f"rl:{math.floor(self.clock.now() / window)}"
    return lambda st: st.incr(key, ttl=ttl)

def failed(self, done):
    """The store did not answer in time: apply the failure policy."""
    if self.on_error == "open":
        done(True)
    elif self.on_error == "closed":
        done(False)
    elif self.on_error == "local":
        done(self.fallback.allow())
    else:
        raise ValueError(f"unknown on_error {self.on_error!r}")

def allow(self):
    """Decide one request from local state only (no network)."""
    self._roll()
    if self.mode == "optimistic":
        left = self.limit - self.known - self.unsynced
    else:
        left = (self.limit - self.known) / self.nodes - self.unsynced
    if left >= 1.0 - EPS:
        self.unsynced += 1
        return True
    return False

def sync(self):
    """Send our unsynced count to the store and learn the global count."""
    self._roll()
    idx, delta = self.widx, self.unsynced
    key = f"rl:{idx}"
    ttl = 2 * self.window

    def on_reply(total):
        if total is None or self.widx != idx:
            return              # store down, or the window has moved on: keep what we have
        self.known = total
        self.unsynced -= delta

    rpc(self.sim, self.net, self.store, lambda st: st.incr(key, ttl=ttl, by=delta), on_reply, self.timeout)

Look under the hood

  • The numbers are the chapter's, measured. Chapter 5 estimated that a local limiter with sync can be off by about offered rate × T; the table above is that estimate against a simulator, and it shows where the rule of thumb breaks: at long intervals the error saturates (each node can admit at most its own allowance alone, so at most about N times the limit), and with few nodes it is much smaller than with many.
  • "Exact" is a strong word. The log is exact in the sense that no window ever exceeds the limit. It is not fair (a client that sent early may be locked out longer than a smooth client) and not free (state per key proportional to the limit). Approximate algorithms are an engineering trade, not a defect, as long as you know the bound.
  • Atomicity is a property of the operation, not of the store. The store here is perfectly consistent; the racy limiter is still wrong, because it composes two atomic operations into a non-atomic one. This is why the chapter says "one script call" and why a read-modify-write across a network always needs a conditional write or a server-side script.
  • Timeouts decide the failure policy for you. A 50 ms timeout against a 10 ms round trip means a slow store (not just a dead one) triggers the failure policy. Experiment 4 below measures it.

Stretch goals

  • A sliding-window counter in the store. Make the global limiter use the weighted two-counter estimate: one round trip, two keys (a script that reads the previous window's counter and increments the current one). Measure the sliding peak against the fixed-window global limiter's 1.26x.
  • Leaky bucket as a queue. Add the fourth algorithm of chapter 5: admit into a bounded queue and measure the queueing delay; compare its admitted set with the token bucket's.
  • A circuit breaker. After k consecutive timeouts, stop calling the store for a cool-off period and apply the failure policy immediately. Re-run experiment 4 and compare the latency during the outage.
  • Hot keys. Send 90% of the traffic to one key. The store shard that owns it becomes the bottleneck; implement a local pre-aggregation that batches increments (sync, in effect) for keys above a rate.
  • Lossy sync. Let the network drop and duplicate sync messages. A duplicate incr double-counts; make sync idempotent with a per-node sequence number and show that the over-admission returns to its previous level.
  • Per-tenant fairness. Give tenants different limits and nodes uneven shares. Does the conservative mode's refusal under skew get worse or better with many tenants?

Distributed systems connection

Every question in milestone 5 is a standard distributed-systems question in small. Sync intervals are the staleness of a replicated counter, and over-admission is the price of reading stale state, the same trade that consistency models classify. The atomic increment is a tiny instance of the coordination that coordination avoidance asks whether you can skip; a local limiter with sync is a deliberately non-coordinated counter whose error you bound instead of preventing. Fail-open versus fail-closed is the availability-versus-safety choice of the CAP discussion, made per endpoint. And clock skew is why time revisited warns against reading "now" on more than one machine and treating the values as comparable.

What you learned

  • A token bucket is two numbers and a lazy refill; its guarantees are a burst of at most capacity and, in any window of length w, at most capacity + rate × w. It takes its clock as an argument, which is what makes it testable.
  • The sliding-window log is exact and expensive in state; the sliding-window counter is two numbers with an error bounded below 2x that is near zero on smooth traffic and large on bursts; the fixed window is cheap and doubles the limit at an edge.
  • State a property and check it on generated traces with seeds printed on failure. Adversarial generators (bursts on window edges) matter more than volume.
  • A shared limiter needs an atomic operation, not atomic reads and writes: one INCR with a TTL of at least two windows. Composing a read and a write loses updates the moment there is network delay.
  • Local limiters with periodic sync over-admit roughly in proportion to rate times staleness; the conservative variant bounds the overshoot and pays in refused legitimate traffic under skewed load. Pick which error you can live with.
  • When the store is down, fail-open keeps the API and loses the protection, fail-closed keeps the protection and loses the API, and a local fallback is a bounded compromise. Every one costs a timeout per request unless you add a breaker.
  • Clock skew between nodes does not change the average admitted rate but can nearly double the peak; have one authority name the window.

Check your understanding

A fixed-window limiter allows 100 requests per minute. What is the most a client can get admitted in any 60-second span?

  1. 100, by definition of the limit
  2. Up to 200: 100 at the end of one window and 100 at the start of the next
  3. Up to 150, because the window is half-weighted
  4. Unlimited, because the counter resets
The window is aligned to the clock, not to the client. A burst in the last instant of window k and another in the first instant of window k+1 are both within their own limits yet only a moment apart. That is the edge effect the log, the counter and the token bucket exist to remove or bound.

A sliding-window counter with limit 100 sees 100 requests early in window k. Halfway through window k+1 (fraction 0.5), how many more requests will it admit, assuming none so far in k+1?

  1. 0: the previous window was full
  2. About 50: the previous window is weighted by the part that still overlaps, so 100 x 0.5 + current <= 100
  3. 100: each window is independent
  4. About 150
The estimate is previous x (1 - fraction) + current = 100 x 0.5 + current. It admits while the estimate plus one is at most 100, so about 50 more. If the old requests were bunched late in window k, the true sliding count is higher than the estimate, which is the source of the (bounded, under 2x) error.

Two app nodes each read the shared counter (value 99), see it is under the limit of 100, admit, and write back 100. What went wrong and what is the fix?

  1. Nothing: the limit is 100 and the counter says 100
  2. The store is inconsistent; use a stronger store
  3. A read-then-write is not atomic, so both admitted at 99; use one atomic increment (or a server-side script) and test the returned value
  4. The clocks are skewed; use NTP
Each operation was atomic but their composition was not. Two admissions took the count to 101 requests but the stored value to 100. An atomic INCR returns 100 to one caller and 101 to the other, so exactly one is admitted.

A limiter's store goes down for ten minutes. The endpoint is a login form. Which policy fits, and what must you add either way?

  1. Fail open, because availability matters most
  2. Fail closed for this endpoint (credential stuffing is the threat), a local fallback limit for ordinary endpoints, and alerting plus a circuit breaker so requests are not each delayed by the timeout
  3. Fail open for everything, and log it
  4. Disable the limiter permanently
The right policy depends on the endpoint: open fails towards availability, closed towards protection, and a login form is exactly where being unprotected is worse than being briefly unavailable. Whichever you choose, every request waits out the timeout while the store is down, so a breaker and an alert are part of the design.

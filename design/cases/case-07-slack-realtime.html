Slack's Real-Time Messaging

Slack's 2023 Slack Engineering post "Real-time Messaging" describes how a message typed in one client reaches every other connected client in a channel within a fraction of a second. The design has four kinds of server with sharply different jobs: channel servers that own a slice of channels on a consistent-hash ring, gateway servers that hold users' WebSocket connections and are the only tier deployed across regions, stateless admin servers that route to the right channel server, and presence servers. This case follows one message through them and then asks what happens when a piece dies.

What I could and could not read

I fetched and read Slack Engineering's post "Real-time Messaging" (2023) in full. I used no other source. The post is short on failure stories and gives few numbers, so where I write "the post says" it is the post, and where I discuss what a design would do under stress I mark it "mine" or "general". It does not describe, for example, how a gateway server recovers its subscriptions after a restart in detail, so I do not either.

The pattern in one sentence

Give every channel exactly one owner chosen by hashing its ID, put connections on a separate tier close to users, and make the owner push each message to every connection tier that has a subscriber: ordering and state live in one place per channel, delivery work is spread across many.

Context

Slack is a workplace chat product whose clients want messages, reactions, typing indicators and presence in real time. The post says usage follows the working day: most users are online roughly nine to five local time, with peaks mid-morning and mid-afternoon, so load rolls around the world, and there are spikes at the top of each hour because reminders, scheduled messages and calendar events fire then. "Channel" is used broadly in the post: the ID can belong to a user, team, enterprise, file, huddle or an ordinary channel, so the same machinery carries many kinds of events. The general chat design is in chapter 10; this case is one company's published architecture.

Channel server (CS)
A stateful, in-memory server that holds recent history for a subset of channels and receives and sends messages for them.
Gateway server (GS)
A stateful, in-memory server that holds user information and WebSocket subscriptions and mediates between clients and channel servers. The post says it is the only tier deployed across multiple geographic regions.
Admin server (AS)
A stateless server between the web app backend and the channel servers that routes each message to the correct one.
Presence server (PS)
Tracks who is online; users are hashed to individual presence servers.
CHARM
Consistent hash ring manager: the component that manages a ring and replaces unhealthy channel servers.

The mechanism: channel servers on a consistent-hash ring

The post says channel IDs are hashed and mapped to a unique channel server, so each CS hosts a slice of channels and a single team's channels are spread across all channel servers. That is consistent hashing used for placement of state: all messages for one channel meet at one machine, which can order them and keep recent history in memory. CHARMs manage the ring; the post says they replace unhealthy channel servers quickly (a replacement is ready in under 20 seconds) and that Consul is the service-discovery system where each ring is defined and from which admin and channel servers read current configuration. The post also reports that at peak a channel server host serves about 16 million channels.

The mechanism: gateways and connections

The post describes the client boot sequence. The client fetches a user token and WebSocket setup information from the web app backend, then connects to the nearest edge region where Envoy handles load balancing and TLS termination and forwards the connection to a gateway server. The gateway fetches the user's channels from the web app, sends the client its initial state, and asynchronously subscribes to the channel servers that hold those channels. Because gateways are the only tier spread across regions, a client talks to a nearby machine, which cuts connection latency, while channel servers need not be near everyone. For the cost and shape of long-lived connections see concurrency models and the WhatsApp case.

The mechanism: how a message fans out

The post lists the sequence: the client sends the message through the web app API, which passes it to an admin server; the admin server finds the right channel server through the hash ring and routes the message there; the channel server forwards it to every gateway server in the world that is subscribed to that channel; each gateway delivers it to every connected client subscribed to that channel. The post notes that broadcast multipliers differ by region, probably because of differences in team size. Events such as reactions, bookmarks and members joining follow the same path as messages. Transient events such as typing indicators are not persisted and take a similar path: client, gateway, channel server, all gateways, subscribed clients.

Fan-out is therefore two-stage. The channel server sends one copy per subscribed gateway, not one per user, and each gateway multiplies that into its own local connections (general reasoning: this keeps the channel server's work proportional to the number of gateways with a subscriber, which is far smaller than the number of members in a big channel).

Presence and admin servers

The post says admin servers are stateless: they exist so the web app backend does not need to know about the ring, and because they are stateless they can be added freely. Presence is a separate system on its own hashing: users are hashed to presence servers, clients query presence over the WebSocket with the gateway acting as a proxy, and the client receives updates only for the users visible on screen. Keeping presence out of the message path is a deliberate separation (mine): presence is chatty and loss-tolerant, messages are not.

Failover

The post describes two failure responses. For a failed channel server, CHARMs replace it, and affected teams' channels see elevated delivery latency for less than 20 seconds. For a region problem, a draining mechanism moves users from the bad region to the nearest healthy one. The post is not a postmortem and says little else, so what follows is general: replacing a failed host in the same ring slot (my toy, below) keeps the failure local to that slot's channels, while removing the host from the ring would also spread its channels across the survivors and force each of them to load state from scratch. See failure detection for why "unhealthy" is a judgement, and blast radius for why limiting the size of the affected slice matters.

A toy you can run

This is my own sketch, not Slack's code. It places 20,000 channel IDs on a ring of eight channel-server slots (64 virtual points each), shows what changes if a dead server is removed from the ring versus replaced in place, and then counts the gateways and clients a message to a few channels would reach, given random subscriber placement across three regions.

"""Toy: channel servers on a hash ring, gateway fan-out. My model, not Slack's code."""
import hashlib, bisect
def h(s): return int(hashlib.sha256(s.encode()).hexdigest()[:12], 16)

class Ring:
    def __init__(self, slots, vnodes=64):
        self.slots = list(slots); self.points = []
        for s in self.slots:
            for v in range(vnodes): self.points.append((h("%s#%d" % (s, v)), s))
        self.points.sort()
    def owner(self, channel):
        i = bisect.bisect(self.points, (h(channel), "")) % len(self.points)
        return self.points[i][1]

CHANNELS = ["C%05d" % i for i in range(20000)]
ring = Ring(["cs-%d" % i for i in range(8)])
before = {c: ring.owner(c) for c in CHANNELS}
load = {}
for o in before.values(): load[o] = load.get(o, 0) + 1
print("channels per channel server:", sorted(load.values()))

# (a) Remove a dead server from the ring: its channels spread out, but only its channels move.
r2 = Ring(["cs-%d" % i for i in range(8) if i != 3])
moved = sum(before[c] != r2.owner(c) for c in CHANNELS)
print("remove cs-3 from ring: %d of %d channels remapped (cs-3 owned %d)" % (moved, len(CHANNELS), load["cs-3"]))
# (b) Replace it in place: the new host takes the same slot name, so the ring does not change at all.
r3 = Ring(["cs-%d" % i for i in range(8)])
print("replace cs-3 in place: %d channels remapped" % sum(before[c] != r3.owner(c) for c in CHANNELS))

# Fan-out: gateways in 3 regions each hold subscriptions to the channels their users are in.
import random
rng = random.Random(1)
REGIONS = {"us": 6, "eu": 4, "ap": 3}                       # gateways per region
members = {c: [(rng.choice(list(REGIONS)), rng.randrange(6)) for _ in range(rng.choice([2, 5, 40]))] for c in CHANNELS[:5]}
for c, ms in members.items():
    gws = {(rg, g % REGIONS[rg]) for rg, g in ms}
    print("message to %s: 1 admin hop, 1 channel server (%s), %d gateways, %d clients" % (c, ring.owner(c), len(gws), len(ms)))

Output when run:

channels per channel server: [2115, 2118, 2253, 2364, 2526, 2750, 2922, 2952]
remove cs-3 from ring: 2115 of 20000 channels remapped (cs-3 owned 2115)
replace cs-3 in place: 0 channels remapped
message to C00000: 1 admin hop, 1 channel server (cs-7), 2 gateways, 2 clients
message to C00001: 1 admin hop, 1 channel server (cs-6), 4 gateways, 5 clients
message to C00002: 1 admin hop, 1 channel server (cs-0), 11 gateways, 40 clients
message to C00003: 1 admin hop, 1 channel server (cs-7), 5 gateways, 5 clients
message to C00004: 1 admin hop, 1 channel server (cs-1), 13 gateways, 40 clients

Reading the output: the load is not perfectly even (2,115 to 2,952 channels per server with 64 virtual points; more points would smooth it). Removing server 3 remaps exactly its own 2,115 channels and no others, which is the consistent-hashing guarantee; replacing it in place remaps nothing, which is why a replacement strategy keeps the blast radius to those channels' brief latency blip. The last lines show the multiplier effect: a message to a 40-member channel reached 11 or 13 gateways, whereas a 2-member channel reached 2.

What they learned or changed

  • Separate state from connections. Channel servers own the per-channel state; gateways own the sockets. Each tier scales on its own axis (channels vs connections) and only gateways are multi-region.
  • Spread a team across all servers. Hashing channel IDs, not team IDs, means one huge team does not land on one server.
  • Make routing stateless. Admin servers hide the ring from the web app backend.
  • Plan for the top of the hour. The post singles out spikes caused by scheduled events; sized for the average they would be a problem (general).
  • What next. The post ends by saying the team wants to extend the architecture for its next largest customers; in the same passage it describes the current system as serving tens of millions of channels per host (a larger figure than the 16 million at peak quoted earlier in the post, and the post does not reconcile the two) and delivering messages across the world in around 500 ms. I treat these as the post's own claims, not independent measurements.

The pattern to remember

Analogy: a post office with sorting rooms and local counters

Every address is assigned to exactly one sorting room by a rule everybody can compute. Mail for a street always goes to that room, which keeps the order and a copy. The room sends one bag to each town counter that has someone on that street, and each counter hands the letters to its customers waiting at the window. If a sorting room burns down, a new room takes over the same streets; no other street changes.

Where it breaks down: real mail is not delivered in a fraction of a second, and a post office cannot let thousands of customers wait at the counter with their connections open.

Key takeaways

  • Hash the channel ID to a single owning server to centralize ordering and recent state.
  • Keep connection handling on a separate tier that you can place near users and deploy across regions.
  • Fan out in two stages: owner to subscribed gateways, then gateway to its local clients.
  • Keep presence and transient events off the durable path.
  • Replace failed owners in place so failure stays local and short.

Use it in an interview

Say: "I'd put connections on gateway servers near users and put message ownership on channel servers chosen by consistent hashing of the channel ID. A send goes through a stateless router to the owner, which forwards one copy to each gateway with a subscriber; gateways push to their sockets. If an owner dies, a manager replaces it in its slot, so only its channels see a brief delay." Then give the cost: "huge channels create big fan-out multipliers, so I'd watch the gateway count per channel and think about batching."

Don't: hash by user ID and write to every recipient's inbox without justifying it; say why a channel is the unit of ordering. Keep presence out of the message path, and use the capacity numbers from your own estimate (chapter 10) rather than quoting Slack's.

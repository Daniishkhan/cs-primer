Netflix Open Connect

Netflix decided that video bytes should come from a box that sits as close to the viewer as possible, and that the box should be filled before anyone asks. Open Connect, described on openconnect.netflix.com and in its "Open Connect Overview" PDF, is that network: purpose-built cache appliances (OCAs) placed inside ISP networks and at internet exchange points, a control plane in AWS that decides what each appliance stores and which one a given client should use, and a data plane so simple that an appliance only reports its status and serves HTTP(S). The design is a study in splitting a system by what must be smart from what must be fast.

The pattern in one sentence

When demand is predictable and you control the whole path, replace a pull-through cache with a pushed one: decide centrally what each edge box should hold, fill it in quiet hours, and let the edge do nothing but report and serve.

Context

The Overview PDF says Netflix began Open Connect in 2011 for two reasons. First, Netflix had become a significant share of traffic on consumer ISP networks, so it needed to work with those ISPs directly. Second, building its own delivery system let it design "proactive, directed caching" that it describes as far more efficient than a standard demand-driven CDN, reducing demand on upstream network capacity by several orders of magnitude. Video-on-demand over a fixed catalogue is what makes this possible: unlike a general web CDN, Netflix owns the content, knows the catalogue and can predict viewing.

OCA
Open Connect Appliance: a purpose-built cache server that stores encoded video and image files and serves them over HTTP/HTTPS.
Embedded OCA
An appliance Netflix provides to a qualifying ISP and that lives inside the ISP's network. The ISP supplies power, space and connectivity and controls which of its customers are routed to it.
IXP deployment
An appliance placed at an internet exchange point and interconnected with ISPs that are present there by settlement-free peering.
Fill
Loading new or changed files onto appliances, as opposed to serving them.
Steering
Choosing which appliance a particular playback request should fetch from and handing the client its URLs.

The mechanism: two deployment shapes

The Overview describes thousands of appliances deployed in two ways. Inside IXPs in significant markets, they are reached by settlement-free public or private peering. Embedded inside ISP networks, they are provided free of charge to qualifying ISPs, with the same capabilities as the IXP ones. The home page adds that embedded partners also use peering for resiliency and for the nightly fill and updates, and that Netflix pre-fills each embedded appliance with content suited to the partner's geography before shipping, which it says typically takes one to two weeks depending on catalogue size. ISP partners configure BGP sessions with the appliances to steer traffic to them. For failover, the home page gives this example: with two embedded appliances at two sites, if site 1 fails traffic goes to site 2, and if both are down it goes to Netflix's IX appliances.

The appliances page describes two models, both 2U: a storage appliance (about 200 Gbps of operational throughput, up to 120 TB raw storage) for IX locations and larger ISPs, and a global appliance (about 80 Gbps, up to 60 TB) as the lower-cost option for smaller partners. Treat these as the page's current figures; the models change over time.

The mechanism: control plane versus data plane

The key design decision is how little an appliance does. The Overview says an OCA stores no client data (no viewing history, DRM information or member data) and does only two things: it reports its status to the control-plane services in AWS and it serves content on request. The status it reports includes health metrics, the BGP routes it has learned from its peer router or switch, and which files it has on disk. The control plane uses that to steer clients, by URL, to the best appliance given file availability, health and network proximity; it also controls fill, computes file storage and hashing behaviour, and stores and interprets playback telemetry.

Follow one playback: the client asks the playback application in AWS, which checks authorization and licensing and works out which files are needed (accounting for client characteristics and network conditions); the steering service uses the cache control service's data to choose appliances and generate URLs; the playback service returns those URLs and the appliance starts serving. My reading (general): because the decision travels as a URL, the data path needs no lookup service, no session state and no connection back to the control plane while video flows.

My comment (general): this split buys independent failure domains. If the control plane is unavailable, appliances that already have the files and clients that already have URLs can keep streaming; if one appliance dies, the next steering decision simply excludes it because its health report says so. See blast radius for why that separation matters.

The mechanism: fill instead of cache misses

A demand-driven CDN fills an edge on the first miss, at the moment a viewer is waiting and at the busiest hour. Open Connect predicts instead. The Overview says Netflix can predict with high accuracy what members will watch and when, so it deploys most content and software updates proactively in off-peak fill windows that are configurable, using non-peak bandwidth. Appliances can also download updates from each other, which limits the use of "backbone" capacity. The control plane uses popularity algorithms and storage techniques intended to maximize offload while minimizing churn, meaning updates to what an appliance stores.

The toy below is my own and not Netflix's algorithm. It draws 20,000 requests from a skewed (Zipf-like) popularity distribution over 400 titles. One appliance holds 60 titles. Compare a box pre-filled with the 60 predicted-hottest titles with a cold demand-driven LRU cache, and then run a simple steering rule over three appliances.

"""Toy: proactive off-peak fill vs demand-driven fill, plus steering. My model, not Netflix's code."""
import random
rng = random.Random(7)
TITLES = 400                       # catalog size
SLOTS = 60                         # titles one appliance can hold
weights = [1 / (r + 1) for r in range(TITLES)]          # Zipf-like popularity, rank 0 hottest
def draw(n): return rng.choices(range(TITLES), weights, k=n)

PEAK_REQS = 20000
# Control plane predicts popularity (here: the true ranking) and fills the top SLOTS titles at night.
proactive = set(range(SLOTS))
reqs = draw(PEAK_REQS)
hits = sum(t in proactive for t in reqs)
print("proactive fill: hit rate at peak = %.1f%%, titles pulled over upstream during peak = 0" % (100 * hits / PEAK_REQS))

# Demand-driven LRU cache starting cold at the beginning of the peak.
from collections import OrderedDict
lru, h, upstream = OrderedDict(), 0, 0
for t in reqs:
    if t in lru: lru.move_to_end(t); h += 1
    else:
        upstream += 1; lru[t] = 1
        if len(lru) > SLOTS: lru.popitem(last=False)
print("demand-driven LRU: hit rate = %.1f%%, fetches pulled upstream during peak = %d" % (100 * h / PEAK_REQS, upstream))

# Steering: control plane picks an OCA that (1) is healthy, (2) has the file, (3) is closest by route.
OCAS = [
    {"name": "isp-a-1", "healthy": True,  "routes": {"isp-a"}, "files": set(range(SLOTS))},
    {"name": "isp-a-2", "healthy": True,  "routes": {"isp-a"}, "files": set(range(SLOTS))},
    {"name": "ixp-1",   "healthy": True,  "routes": {"isp-a", "isp-b"}, "files": set(range(SLOTS * 2))},
]
def steer(client_net, title):
    ok = [o for o in OCAS if o["healthy"] and title in o["files"] and client_net in o["routes"]]
    ok.sort(key=lambda o: len(o["routes"]))      # narrowest route set = most local (toy proxy for proximity)
    return [o["name"] for o in ok]
print("steer(isp-a, title 5)   ->", steer("isp-a", 5))
print("steer(isp-a, title 100) ->", steer("isp-a", 100), "(only the IXP box has it)")
OCAS[0]["healthy"] = False; OCAS[1]["healthy"] = False
print("both embedded boxes down ->", steer("isp-a", 5), "(falls back to the IXP appliance)")
print("steer(isp-b, title 5)   ->", steer("isp-b", 5))

Output when run:

proactive fill: hit rate at peak = 71.5%, titles pulled over upstream during peak = 0
demand-driven LRU: hit rate = 60.3%, fetches pulled upstream during peak = 7946
steer(isp-a, title 5)   -> ['isp-a-1', 'isp-a-2', 'ixp-1']
steer(isp-a, title 100) -> ['ixp-1'] (only the IXP box has it)
both embedded boxes down -> ['ixp-1'] (falls back to the IXP appliance)
steer(isp-b, title 5)   -> ['ixp-1']

Reading the output: the pushed cache is warm from the first request and pulled nothing during the peak, while the LRU cache pulled thousands of titles upstream while viewers waited. The gap shrinks as the cache warms, and a real LRU is helped by a real catalogue's shape; the toy shows the mechanism, not Netflix's numbers. The steering rule is deliberately crude (it prefers the appliance reachable by the fewest networks, a stand-in for proximity); it shows the three inputs the Overview names: health, file availability and network reachability.

What they learned or changed

  • Collaborate with the access network. The first stated reason for the program is working with ISPs directly. Embedded appliances put the ISP in control of which customers use them, and the home page says each embedded deployment offloads a substantial amount of Netflix traffic from peering or transport circuits.
  • Make the edge boring. The Overview lists the software stack as something Netflix develops at every layer, and says it makes the hardware design and the software available as open source. An appliance that holds no member data is also easy to replace: if hardware degrades, the Overview says Netflix replaces it at no cost to partners.
  • Operate it remotely. The operations team monitors all deployments and fixes most issues remotely; partners get a portal if they want to watch their own appliances.
  • Keep evolving. The Overview says the program is constantly adjusted and appliance design keeps changing; the appliances page's current models differ in cost and capacity so smaller ISPs can participate.

The pattern to remember

Analogy: a bookshop that restocks overnight

A chain of corner shops could wait for a customer to ask for a book, then order it and make them wait. Instead, head office predicts what each neighbourhood will want, sends the van at night, and tells each shop only to sell and to report its shelves every morning. When a customer phones head office, it replies with the address of the nearest shop that has the book and is open.

Where it breaks down: books are not streamed to thousands of people at once, and a shop that is closed cannot tell customers who already have its address.

Key takeaways

  • If you can predict demand, fill the cache ahead of time, in quiet hours, instead of on the first miss.
  • Put placement and steering in a central control plane; keep the edge to two jobs, reporting state and serving bytes.
  • Steer with health, file availability and network proximity as inputs; hand the answer to the client as a URL.
  • Deploy in more than one shape (embedded and exchange) so there is always a fallback.
  • The strategy works because Netflix owns the content and the catalogue is bounded; a general CDN cannot assume that.

Use it in an interview

Say: "The catalogue is bounded and demand is predictable, so I wouldn't use pull-through caching at the edge. I'd have a control plane decide what each edge box holds, fill during off-peak windows, and have boxes report health and contents so a steering service can return the best box's URL. The edge only serves bytes, which keeps it replaceable." Then add the cost: "prediction errors waste storage, and steering data must be fresh."

Don't: start with "Netflix does...". Derive it: peak bandwidth, transit cost, read-to-write ratio, and the fact that video files never change after encoding. Compare with demand-driven caching in chapter 13 and mention fallback ordering (embedded, then exchange) when asked about failures.

Why can Open Connect fill appliances before anyone asks, when a general CDN usually cannot?

  1. Its appliances have unlimited disks
  2. Netflix owns the catalogue and can predict what members will watch and when
  3. ISPs request each file individually
  4. It uses UDP
The Overview says Netflix predicts viewing with high accuracy, which lets it use off-peak windows to move most content ahead of demand.

What does an OCA report to the control plane, per the Overview?

  1. Member viewing history
  2. Health metrics, learned BGP routes and which files it has on disk
  3. Payment data
  4. Nothing; it is polled
OCAs store no client data; they report status and serve content.

What does the steering service hand to the playback service?

  1. A cached copy of the video
  2. Encryption keys
  3. URLs of the OCAs chosen for the requested files
  4. A DNS zone
Steering picks appliances using the cache control service's data and generates URLs for them.

An ISP's embedded appliances are all down. According to the home page's example, where does traffic go?

  1. It fails
  2. To Netflix IX appliances
  3. To the client's phone
  4. To the origin only
Embedded deployments fail over first to a second site and then to Netflix's IX appliances.

Which is a real cost of the pushed-fill design (general reasoning)?

  1. A wrong popularity prediction wastes storage and a stale control plane misdirects clients
  2. It cannot use HTTPS
  3. It needs a new protocol on every phone
  4. Appliances must hold member data
Prediction and freshness of the control plane's view are what the design depends on.

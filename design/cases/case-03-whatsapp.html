WhatsApp: Millions of Connections per Server

In January 2012 the WhatsApp blog reported more than two million TCP connections on a single FreeBSD server running Erlang. Two years later, engineer Rick Reed told Erlang Factory that the service had grown to hundreds of millions of connections spread over about 150 chat servers and was run by an Erlang team of around ten people. The case is a lesson in choosing a runtime built for huge numbers of cheap concurrent tasks, then removing contention one measurement at a time.

What I read, and how claims are marked

I fetched and read: the WhatsApp blog post "1 million is so 2011" (January 2012); the slides of Rick Reed's talks "Scaling to Millions of Simultaneous Connections" (Erlang Factory SF, March 2012) and "That's 'Billion' with a 'B'" (Erlang Factory SF, March 2014); the Erlang Factory page for the 2014 talk; and High Scalability's write-up of the 2014 talk. I could not watch the talk videos. Claims from the talks are marked (talk 2012) or (talk 2014), from the blog post (blog), and my own explanations (general) or (mine). Slides are terse, so where they leave out reasoning I say so.

The pattern in one sentence

If your workload is a huge number of mostly idle connections, each needing a little work, use a runtime where a task is nearly free, then find and remove contention (locks, shared tables, a global clock) until the cost per connection is small enough that a single box carries them all.

Context

The 2012 talk sets the scene: at the start of the effort the servers held about 200 thousand connections each, the prognosis for growth looked discouraging, and the cluster was brittle under failures and overloads (talk 2012). The goal was one million connections per server, with resilience to software and hardware failures and to world events such as sports matches and earthquakes (the slides show message-rate spikes on those days). The standard configuration then was a dual hex-core Westmere machine with 24 logical CPUs, about 100 GB of RAM, SSD, two network cards, FreeBSD 8.3 and Erlang/OTP R14B03 (talk 2012).

Why this is an interesting design problem: a chat server mostly waits. A phone holds a connection open, sends a message now and then, and gets pushes. The problem is the number of connections and what they share, not heavy computation per connection. That is the same family as the C10K problem in event loops and the design in chapter 10.

BEAM
The virtual machine that runs Erlang code. It runs its own lightweight processes on a small number of OS threads called schedulers.
OTP
Erlang's standard library of server, supervisor and clustering building blocks.
Mnesia
Erlang's built-in distributed database; the 2014 slides call out its replication and table layout as a main scaling topic.
FreeBSD
The Unix-like operating system WhatsApp ran its servers on.

The mechanism: Erlang processes and the connection

The 2014 slides open by listing scalability and non-stop operations as the reasons Erlang was a good choice (talk 2014). In the 2012 talk, the reported finding is that Erlang scales very well across multiple CPUs, with more than 85% CPU utilisation across 24 logical CPUs, and that FreeBSD does too (talk 2012). The blog post shows the server at 2,277,845 open sockets with about 41.9% CPU idle and about 27 GB of memory free, which says that the limit was no longer CPU or memory (blog).

One process per connection (general). None of the sources I read says in so many words that each connection is one Erlang process, so treat this part as general knowledge, not a WhatsApp claim. An Erlang process is not an OS thread: it has its own small heap and a message queue, it is scheduled by the VM, and creating one costs little, so "one process per connection" is the ordinary way to write a server in Erlang, with a bug in one connection's code unable to corrupt another's memory. See concurrency models compared for the actor model against threads and event loops. What the slides do show is how processes are used above the connection: work is spread over pools with gen_server, gen_factory and gen_industry, services are partitioned (usually 2 to 32 partitions), and process message-queue backlog is watched because bottlenecks show up as backlog (talk 2014).

The mechanism: FreeBSD and BEAM tuning

The blog post lists the kernel limits it raised in /boot/loader.conf.local: sockets to 2,400,000, open files to 3,000,000 and processes to 16,384, plus bigger TCP hash tables (blog). It also states the stack: FreeBSD 8.2-STABLE, Erlang R14B03 with 24 schedulers on an Intel Xeon X5675 box with 24 logical CPUs and about 103 GB of memory (blog).

The 2012 talk gives the OS-side changes: a backported TSC-based timecounter that made gettimeofday calls much cheaper; a backported igb network driver after problems with stalled interrupt queues; and sysctl tuning including the obvious limits (such as kern.ipc.maxsockets) and net.inet.tcp.tcphashsize=524288 (talk 2012). On the Erlang side the list is long: scheduler and allocator flags, real-time scheduling priority, patches to widen the timer hash table, to reduce contention on the time-of-day lock, to improve I/O polling scalability, and to raise the default distribution receive buffer from 4k to 256k (talk 2012). The statement that summarises it: from 200 thousand to 2 million connections, "contention, contention, contention" - the fixes were contention fixes, some inside the VM (most needing patches) and some changes to the application, especially partitioning work correctly (talk 2012).

The figures in the picture, per the sources: first bottlenecks near 425 thousand; one million after the first round of fixes; two million about a month later; and an unintentional peak of 2.8 million in February with 571 thousand packets per second and more than 200 thousand distribution messages per second, before the team intervened (talk 2012). The tools they used included OS-level and BEAM-level monitoring, hardware performance counters, dtrace, lock counting in the VM (which they rate as extremely valuable) and diverting extra production load onto one server (talk 2012).

What they learned or changed

  • The limit moved from "how many" to "how much headroom". By 2014 the slides show about 150 chat servers each with about 1 million phones (talk 2014), and High Scalability's write-up of the talk says that this is lower than the 2 million reached earlier because each server needed headroom for peak load and was doing more work per user. That explanation is the write-up's, not a sentence I could confirm on the slides.
  • Decouple and isolate. Slides on decoupling: avoid Mnesia transaction coupling by using async_dirty, use calls only when returning data and always with timeouts, avoid head-of-line blocking with separate read and write queues and separate inter-node queues, and limit cluster size with "meta-clustering" (talk 2014).
  • Measure everything. Per-node metrics at 1-second and 1-minute polling pushed to Graphite, alerts on process message-queue backlog (usually above 500 thousand), and capacity planning against CPU, memory and disk limits (talk 2014).
  • Small team, narrow stack. About 10 people on Erlang handling development and operations (talk 2014). Scale figures from those slides: 465 million monthly users; 19 billion messages in and 40 billion out per day; 147 million concurrent connections; about 550 servers plus standby gear; and more than 11,000 cores (talk 2014).
  • Failures still happen. The slides describe a 22 February outage that started with a back-end router glitch, caused a mass node disconnect and reconnect, and ended in a full stop and restart of the cluster, the first in years (talk 2014). Scale did not remove the need for postmortems; see incident response.

Napkin check (mine): 147 million concurrent connections divided by about 150 chat servers is about 0.98 million per server, which matches the slide's "about 1M phones each".

The pattern to remember

Analogy: a switchboard of tiny desks

Picture a telephone exchange where every caller gets their own tiny desk and clerk, who mostly sleeps until a message arrives. A few dispatchers (the schedulers) hurry from desk to desk. Capacity is not about how fast one clerk works; it is about how many desks fit in the room and whether the clerks ever queue for the same filing cabinet. Most of the engineering is moving shared cabinets out of the way.

Where it breaks down: a real exchange's desks are physical; here the "desks" are memory plus bookkeeping, and the filing cabinets are locks, tables and timers inside the VM.

Key takeaways

  • Connection-heavy services are bounded by memory per connection and shared contention, not by CPU per request.
  • Pick a runtime whose unit of concurrency is cheap and isolated; Erlang processes are one such unit.
  • Raise OS limits (sockets, files, hash tables) and fix kernel-level costs such as the time source and the network driver.
  • Measure, find the contended lock or table, and remove it; repeat. The sources describe hundreds of thousands of connections gained per round.
  • Operate below the maximum: roughly 1M per chat server in 2014 left room for peaks.

Use it in an interview

Say: "A chat server is mostly idle connections, so memory per connection and shared state dominate. I'd use a runtime with cheap, isolated tasks (an event loop or lightweight processes), raise file-descriptor and socket limits, and size by memory: if each connection costs a few tens of kilobytes, a million connections is tens of gigabytes. I'd run well below the maximum so a failover or a spike doesn't tip a neighbour over, and partition the shared state so no single table or lock is a bottleneck." Give your own per-connection estimate.

Don't: claim "WhatsApp does X" for anything beyond what you can source, and don't quote the 2-million figure as a target. The 2012 record and the 2014 operating level are different points; the reasoning about headroom is the transferable part. Link back to chapter 10 for delivery receipts and presence.

According to the 2012 talk, what fixed the climb from 200 thousand to 2 million connections?

  1. Faster network cards only
  2. Mostly contention fixes, inside the VM and in how work was partitioned
  3. Replacing Erlang
  4. Adding more servers
The slides say it was all contention fixes, many needing BEAM patches.

Which statement is NOT supported by the sources as WhatsApp's own claim?

  1. About 150 chat servers hold about 1M phones each (2014)
  2. The team was about 10 people on Erlang (2014)
  3. Every connection is exactly one Erlang process
  4. FreeBSD sysctl tuning was part of the work (2012)
Process-per-connection is the usual Erlang idiom (general), but no source I read states it for WhatsApp.

Why run at about 1M connections per server in 2014 when 2M had been reached?

  1. The kernel forbids more
  2. Headroom for peak load and more work per user, per the High Scalability write-up
  3. Mnesia cannot store more
  4. Erlang limits processes to 1M
The write-up attributes the lower level to headroom and busier servers.

What does alerting on process message-queue backlog detect?

  1. Disk failures
  2. Bottlenecks, which show up as growing queues
  3. TLS errors
  4. DNS misconfiguration
The slides say to remove back pressure and alert when a backlog exceeds a threshold (usually 500k).

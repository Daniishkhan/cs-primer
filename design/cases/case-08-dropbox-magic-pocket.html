Dropbox Magic Pocket

Dropbox stored its users' file contents in Amazon S3 until it built its own system, Magic Pocket, and by October 2015 had moved over 90 percent of user data onto it. The posts on Dropbox's tech blog describe an immutable block store: encrypted blocks grouped into buckets, buckets placed onto volumes spread across storage machines, new data replicated first and erasure coded later, every block kept in at least two zones, and a stack of independent verifiers that continually re-read and cross-check everything. The theme is that at this scale a durability model is not enough; you have to keep proving the data is there.

The pattern in one sentence

For immutable data at huge scale, store it in big append-only containers, write it redundantly first and compress that redundancy into erasure coding once it is cold, spread it across failure zones, and run independent verifiers forever, because the probability model only holds if latent damage is found before the next failure.

Context

The post on the move off S3 says why Dropbox built its own: owning the storage stack lets it tailor it end to end to its workload, its scale and block-storage needs allowed custom hardware and software for better unit economics, and open-source systems had not been proven reliable at that scale. It also says Dropbox was not leaving AWS entirely: it announces a plan to expand its AWS relationship, for example to store data in Germany for European business customers who request it. Stated scale at that time: over 500 million signups, over 500 petabytes of user data (about 40 PB when the author joined in 2012), over 90 percent of user data on custom infrastructure, and a peak transfer rate above half a terabit per second. The timeline: Magic Pocket became a major initiative in summer 2013; a "dark launch" mirrored data between two regions in August 2014; launch day, when files were first stored and served only in-house, was 27 February 2015; and the 90 percent goal was reached on 7 October 2015. Extra backups were kept for six months after the dark launch. Compare the general design in chapter 8.

Block
An encrypted, compressed chunk of a file, up to 4 MB in the post, identified by a SHA-256 hash for most uses. Blocks are immutable.
Bucket
A 1 GB logical container that aggregates blocks uploaded around the same time; the blocks need not be related.
Volume
One or more buckets placed onto a set of storage machines. Open volumes accept writes; closed volumes are immutable and safe to move.
OSD
Object storage device: a dense storage machine (over 1 PB each in the post) that holds many volumes.
Cell
A self-contained cluster, about 50 PB raw in the post, that lives within a zone.
Extent
A 1 GB unit of data on a storage node as described in the verification post (thousands per node).

The mechanism: blocks, buckets, volumes

Magic Pocket stores only file contents; the post says metadata is elsewhere and mutation is handled by a separate system. A frontend accepts a request, a Block Index maps each block's hash to its cell, bucket and checksum, and a Replication Table maps buckets to volumes and volumes to OSDs. The post says the Block Index is a large sharded MySQL cluster behind an RPC layer, chosen over a custom key-value store to use existing operational expertise. A Master per cell coordinates repair, bucket creation, garbage collection and merges but is not on the data path. The immutability is the whole trick (general): with no in-place updates there are no partial-write tears to repair, and a closed volume can be copied, moved or encoded without coordination with writers. See crash recovery for what mutable storage has to do instead.

The post says OSDs fsync blocks before responding to a put, so an acknowledgment means durable on that machine. It reports that repair is triggered when an OSD has been offline for 15 minutes, which is a deliberate wait (my reading): a rebooting machine should not set off a flood of copying. The post also notes that its design avoids quorum-style consensus where it can, relying on centralized and fault-tolerant coordination, because simplicity helps durability.

The mechanism: replication, then erasure coding

The post says recently uploaded blocks are first replicated across multiple machines for fast durability, and buckets are later aggregated and erasure coded for storage efficiency. In replicated volumes every OSD holds all the blocks; in erasure-coded volumes each block can be read whole from a single OSD, so most reads touch one disk, and if that OSD is unavailable the block is reconstructed from the others with help from volume managers. The efficiency post says nearly all data is erasure coded, that the scheme splits data into fragments plus a small number of parity fragments, and that it gives the same fault tolerance as replication with far less extra storage. It does not give the code's parameters, and neither do I. Hardware: spinning hard drives for bulk storage and SSDs for databases and caches.

The efficiency post also reports a lesson. The Live Coder service writes directly into erasure-coded volumes, skipping the initial replicated stage; it suits background workflows where throughput matters more than latency. A bug made volumes created this way badly under-filled, with live data below 5 percent of allocated capacity in the worst cases. Volumes are fixed-size and never modified once closed, so deletes free no space until compaction copies live blobs into new volumes and retires the old ones. The post describes three compaction levels (L1 refills a dense volume from donors; L2 uses dynamic programming to group under-filled volumes whose live data nearly fills a destination, giving 30 to 50 percent lower weekly compaction overhead than L1-only cells; L3 streams from the sparsest volumes into Live Coder) and a rate-limited control loop that keeps compaction inside each cell. The takeaway is general: immutability moves the cost of deletes from the write path to a background process you must run and tune.

The mechanism: cross-zone durability

Per "Inside the Magic Pocket", Magic Pocket spans multiple zones in the western, central and eastern US, and each block is stored in at least two zones and replicated within each. A cross-zone replication daemon asynchronously copies each block to a remote zone within one second of upload. Zones are administrative and failure boundaries, so a misconfiguration or congestion should not cascade across them (see blast radius). If the Block Index in one zone fails, a frontend can forward the request to the other zone. Because the copy is asynchronous, the first second of a block's life has only the local zone's protection (my observation from the stated timing).

The mechanism: verify everything

The verification post says erasure coding gives a modelled durability of 27 nines, and stresses that a model alone is not enough. It describes a stack of verifiers: a Disk Scrubber that reads every bit on each node's disks and checks it against checksums (full sweeps roughly every one to two weeks, recently modified areas more often, bad data usually re-replicated within an hour); a Trash Inspector and Extent Referee that make deletion a two-step, checked operation; a Metadata Scanner that walks the Block Index at about a million blocks per second (a full scan roughly weekly) to confirm blocks exist where the index says; a Storage Watcher, a black-box checker written outside the storage team, that samples 1 percent of written blocks and re-fetches them after one minute, one hour, one day, one week and one month; and a Cross-zone Verifier that confirms each file is in every zone it should be. The post says more than half of the disk and database workload is internal verification traffic, and that verifiers ran for at least a week on a staging cluster of tens of petabytes before release. In a disaster-recovery exercise an engineer, with permission, secretly corrupted staging data (flipping bits, truncating extents, inserting random data); the verifiers caught the damage, except that two errors had already been repaired automatically by Magic Pocket before they got to them, and no data was lost.

Why so much work? My toy below shows the reasoning. Silent corruption on one fragment does nothing visible until a second fragment is lost and you rebuild from the damaged one. A scrubber shrinks the window in which such latent damage can combine with a real failure. The toy uses simple XOR parity (one parity fragment) rather than the unspecified code Dropbox uses; it is a teaching model, not Dropbox's scheme.

"""Toy: replication vs erasure coding, plus a scrubber. My model; XOR parity stands in for a real code."""
import hashlib, random
rng = random.Random(3)
def xor(blocks):
    out = bytearray(len(blocks[0]))
    for b in blocks:
        for i, x in enumerate(b): out[i] ^= x
    return bytes(out)
print("raw bytes stored per byte of data:  3-way replication = 3.00 | 4 data + 1 parity = %.2f | 6+3 = %.2f" % (5/4, 9/6))
print("failures tolerated:                 3-way replication = 2    | 4+1 = 1              | 6+3 = 3")

block = bytes(rng.randrange(256) for _ in range(64))          # one 'bucket' worth of data, tiny
frags = [block[i:i+16] for i in range(0, 64, 16)]
parity = xor(frags)
store = {"d%d" % i: f for i, f in enumerate(frags)}; store["p"] = parity
sums = {k: hashlib.sha256(v).hexdigest() for k, v in store.items()}   # checksums kept elsewhere (a 'block index')

lost = "d2"; survivors = [v for k, v in store.items() if k != lost]
rebuilt = xor(survivors)
print("lose %s, rebuild from the other four fragments: %s" % (lost, rebuilt == frags[2]))

# silent corruption: flip one bit on a 'disk'; reads of other fragments still work, nobody notices.
bad = bytearray(store["d1"]); bad[5] ^= 0x04; store["d1"] = bytes(bad)
def scrub():
    found = []
    for k, v in store.items():
        if hashlib.sha256(v).hexdigest() != sums[k]: found.append(k)
    return found
print("scrubber finds:", scrub())
for k in scrub():
    others = [v for kk, v in store.items() if kk != k]
    store[k] = xor(others)                                      # repair from remaining fragments
print("after repair, scrubber finds:", scrub(), "| data intact:", b"".join(store["d%d" % i] for i in range(4)) == block)

# why scrub at all: a second failure arrives before the first corruption is noticed
store2 = dict(store); bad = bytearray(store2["d0"]); bad[0] ^= 1; store2["d0"] = bytes(bad)   # undetected rot
store2.pop("d3")                                                # a disk dies; we rebuild d3 from the rest
rebuilt = xor([store2[k] for k in ("d0", "d1", "d2", "p")])
print("rebuild d3 using an undetected-rotten d0 matches original:", rebuilt == frags[3])

Output when run:

raw bytes stored per byte of data:  3-way replication = 3.00 | 4 data + 1 parity = 1.25 | 6+3 = 1.50
failures tolerated:                 3-way replication = 2    | 4+1 = 1              | 6+3 = 3
lose d2, rebuild from the other four fragments: True
scrubber finds: ['d1']
after repair, scrubber finds: [] | data intact: True
rebuild d3 using an undetected-rotten d0 matches original: False

Reading the output: the overhead lines are arithmetic for the named layouts, not Dropbox's. The scrubber found the single flipped bit via its checksum and repaired it from the other fragments. The last line shows the failure the scrubber exists to prevent: if the rot had stayed undetected and a disk then died, the rebuild would have produced wrong data (False).

What they learned or changed

  • Build when the unit economics and control justify it. The post gives performance, customised hardware and software, and cost as reasons, and still planned to use AWS for some needs, such as data in Germany.
  • Stage the migration. A prototype, then a mirrored dark launch, then full in-house serving, with backups kept for six months and the 90 percent target reached ahead of schedule.
  • Pay for redundancy twice, briefly. Replicate for fast durability, then encode to save space; later Live Coder skipped the first stage for throughput-oriented traffic and exposed a fill-rate bug that compaction had to clean up.
  • Treat deletion as dangerous. Deleted data is parked, inspected and refereed before it is gone.
  • Test the verifiers. Corrupt a staging cluster on purpose and see whether it is caught.

The pattern to remember

Analogy: an archive with sealed boxes and inspectors

Documents are packed into sealed 1 GB boxes that are never opened again, with two photocopies at first and then a smarter "any four of five" arrangement once the box is old. Boxes are kept in separate buildings. Inspectors constantly open random boxes, compare each page with its stored fingerprint, check the catalogue against the shelves, and check that anything marked "discard" really has a copy elsewhere before it goes in the shredder.

Where it breaks down: real archive boxes do not rot silently while nobody looks, and disks do.

Key takeaways

  • Make stored units immutable; handle deletes by garbage collection and compaction.
  • Separate the index (hash to location) from the data and keep the coordinator off the data path.
  • Replicate for fast durability, erasure code for cost, and span independent failure zones.
  • A durability model is a hypothesis; continuous, layered verification is the evidence.
  • Verify deletes as hard as writes.

Use it in an interview

Say: "For a blob store I'd make blocks immutable and content-addressed, group them into large buckets, and place buckets on volumes across machines. New data is replicated for immediate durability, then erasure coded once the bucket closes. Every block lives in at least two zones. A background scrubber checks checksums, and a separate scanner compares the index with what disks actually hold." Then state costs: "compaction for deletes, rebuild traffic, and a window where only one zone has the data."

Don't: quote durability nines as a design goal without saying what you would do to find silent corruption. Derive the overhead of replication versus an (k, m) code from your own estimate in chapter 8 and mention verification traffic as a real capacity cost.

Sharding & IDs at Instagram

A photo-sharing startup outgrew one PostgreSQL machine and needed IDs that sort by time, fit in 64 bits and need no extra service. Its answer, described in Instagram Engineering's "Sharding & IDs at Instagram" (2011) and in a talk by co-founder Mike Krieger, was to run many logical shards as schemas inside a few physical Postgres machines, and to let each shard's own database mint the IDs with a small PL/pgSQL function: 41 bits of time, 13 bits of shard, 10 bits of sequence.

The pattern in one sentence

If the database you already run can hand out increasing numbers cheaply, pack time, a shard label and that local sequence into one integer: you get unique, roughly time-sorted IDs with no coordination service, and because shards are logical, moving data later changes a lookup table, not any ID.

Context

The deck tells the story of a small team scaling with Postgres. The relevant facts it states: photo metadata was the largest table; the biggest machine available on EC2 at the time had 68 GB of RAM; the photos database passed 60 GB; vertical partitioning (separating, for example, photos from other data) had bought time; and the next step was horizontal partitioning. Before sharding, the deck lists three tasks: choosing a method, adapting the application, and expanding capacity. It evaluated NoSQL alternatives, Skype's sharding proxy and range or date partitioning in Postgres itself, and says none was up to being the primary database at the time.

The requirements for the sharding method were three, per the deck: low operational and code complexity, easy expansion of capacity, and low performance impact on the application. The requirements for IDs were also three: sortable by time without a lookup, 64 bits, and low operational complexity. The deck says it surveyed ticket servers, UUIDs, Twitter's Snowflake and application-level IDs in the style of Mongo, then noted that the database is already good at incrementing sequences. Compare the general menu in chapter 7; this case is one team's reasoning through it.

Logical shard
A bucket that a row belongs to forever: here, user_id % number_of_logical_shards. In the deck's design a logical shard is a Postgres schema holding that bucket's tables.
Physical shard
A real database machine that hosts many logical shards.
Schema (Postgres)
A namespace inside one database (database → schema → table). Schemas are physically separate files, which the deck calls out as a benefit.
Sequence
A Postgres object that returns increasing integers via nextval.

The mechanism: logical shards on physical machines

The deck's design is "schema-based logical sharding": many, many (thousands of) logical shards that map to fewer physical ones. Its example is 8 logical shards on 2 machines; user_id % 8 gives the logical shard, and a map sends each logical shard to a machine. Doubling to 4 machines changes only the map. In the application, the deck shows a small hard-coded dictionary from shard to database, plus a thin library replacing the ORM with select, update, insert and delete calls that take a shard key. Most queries touch a handful of shards on one or two machines; the library maps sub-selects to each shard and, where several shards sit on one database, combines them with UNION ALL. The deck says the shard key is the user ID in most cases.

The cost of this design, as the deck states it: rolling out a new shard map needs roughly 30 seconds of maintenance (it suggests a read-only mode could fix that), and it is not great for range scans that span shards. My comment (general): the choice of user_id means a user's data is together, but any query "by something else" has to visit many shards; see sharding in practice for the shard-key trade-off.

The mechanism: IDs generated inside each shard

The deck's ID is 64 bits: 41 bits of time in milliseconds (since a custom epoch), 13 bits for the shard ID and 10 bits of sequence. The PL/pgSQL function it shows (one per shard schema, with the shard's number baked in) reads the next value of a sequence modulo 1024, reads the clock, and ORs the pieces together, shifted into place. Because each shard schema has its own function and the shard number is part of the ID, two shards can never produce the same ID. Within one shard and one millisecond, the sequence part distinguishes IDs.

The deck lists the pros as guaranteed uniqueness in 64 bits and not much CPU overhead, and the con as large IDs from the start. It reports that hundreds of millions of IDs had been generated this way with no issues. It also shows how to pull the shard ID back out of an ID and the timestamp from the high bits. My toy below does the same decode with a shift and a mask; it is not Instagram's code, but the epoch constant and field widths are the deck's.

"""Toy of the 41/13/10 layout (my Python; the original is PL/pgSQL inside each shard)."""
EPOCH = 1314220021721            # the epoch constant shown in the deck's function, in ms
def make_id(now_ms, shard, seq):
    return ((now_ms - EPOCH) << 23) | (shard << 10) | (seq % 1024)
def decode(i):
    return {"ms_since_epoch": i >> 23, "shard": (i >> 10) & 0x1FFF, "seq": i & 0x3FF}

NUM_LOGICAL = 8
PHYSICAL = {0: "A", 1: "A", 2: "A", 3: "A", 4: "B", 5: "B", 6: "B", 7: "B"}   # logical -> physical
user_id = 31341
shard = user_id % NUM_LOGICAL
print("user", user_id, "-> logical shard", shard, "-> machine", PHYSICAL[shard])

a = make_id(EPOCH + 5_000, shard, 1)
b = make_id(EPOCH + 5_000, shard, 2)
c = make_id(EPOCH + 5_001, 3, 7)      # a different shard, 1 ms later
print("ids:", a, b, c, "sorted by id == sorted by time:", sorted([c, b, a]) == [a, b, c])
print("decode a:", decode(a))
print("bits used:", 41 + 13 + 10, "| 2**41 ms in years:", round(2**41 / 1000 / 86400 / 365.25, 1),
      "| ids per shard per ms:", 2**10, "| max logical shards:", 2**13)

# Move logical shards 2,3 and 6,7 to new machines C and D: only the map changes, no id changes.
PHYSICAL.update({2: "C", 3: "C", 6: "D", 7: "D"})
print("after adding machines:", PHYSICAL, "| id still decodes to shard", decode(a)["shard"])

Arithmetic that is mine, from those widths: 241 milliseconds is about 69.7 years of range, the 10-bit sequence allows 1,024 IDs per shard per millisecond (about a million per second per shard), and 13 bits could in principle name 8,192 logical shards. One more consequence I noticed: PostgreSQL's bigint is signed, so the top bit of a 64-bit ID is the sign bit, and the ID would turn negative once the time field passes 240 ms (about 34.8 years after the epoch). The epoch in the deck's function is August 2011, so that is far off; I mention it as a reason to check signedness when you copy a layout, not as a claim about Instagram.

A trap in the slide

The deck's decode line (id ^ ((id >> 23) << 23)) clears the time bits and leaves the low 23 bits, which are shard and sequence together. To get the shard alone you also need to shift right by 10 and mask 13 bits, as my toy does. (Mine; the slide is a summary, not necessarily the production code.)

What they learned or changed

  • Re-sharding is mostly copying. The deck's recipe: clone a machine with streaming replication (it mentions repmgr), promote the clone, point the shard map and PgBouncer at it, and drop the schemas each side no longer owns. It states this works only while there are more logical shards than physical ones. Because schemas are separate files, dropping a schema does not leave holes in a shared table.
  • Use the database for what it is good at. The deck's wrap-up: you do not need to give up Postgres durability and features to shard; it also advises not sharding until you have to, while not over-estimating how hard it is.
  • Tooling mattered. The deck calls a parallel task runner (Fabric) essential for creating thousands of schemas, and says it wrote a custom test runner to create and tear down sharded databases.
  • Caches add a second source of truth. In a later part of the talk, the follow graph was first a table, then also kept in Redis, and the deck lists the resulting inconsistency and extra logic before a redesign leaned on Postgres plus light memcached caching. This is a different topic but a useful warning.

The pattern to remember

Analogy: lockers and a key ring

A school has 8,000 numbered lockers (logical shards) but only a few corridors (machines). Your locker number never changes; the caretaker just keeps a sheet saying which corridor holds which locker numbers, and can move a block of lockers to a new corridor overnight. Every note you leave is stamped with the time, your locker number and a running count, so notes sort by time and say whose they are.

Where it breaks down: real lockers do not run out of numbers or have clocks that disagree; here, a machine whose clock runs backwards can mint IDs that collide or sort wrongly (general).

Key takeaways

  • Decide the bucket (logical shard) once and permanently; move buckets between machines, never rows between buckets.
  • 41 + 13 + 10 bits: time first for sorting, shard for routing, sequence for uniqueness within a millisecond.
  • The database's own sequence supplies the local counter; no network round trip for an ID.
  • Thousands of logical shards on few machines make capacity changes a copy-and-remap operation.
  • The costs: shard-map maintenance, awkward cross-shard ranges, and dependence on server clocks.

Use it in an interview

Say: "I'd generate IDs inside each shard from time, a shard number and a local counter packed into 64 bits. IDs sort by time and carry their shard, there's no central ID service to fail, and I'd create far more logical shards than machines so I can add capacity by moving whole logical shards." Then state the cost: "clocks must be roughly sane, and cross-shard range queries get expensive."

Don't: start with "Instagram did...". The interviewer wants the reasoning: ordering, size, no coordinator, easy resharding. Cite the numbers you derived (1,024 IDs per millisecond per shard) rather than the company. Compare with the other options in chapter 7 when asked "why not UUIDs".

Check your understanding

Why does the deck insist on more logical shards than physical machines?

  1. So queries run faster
  2. So capacity can change by moving whole logical shards and updating a map, without changing any ID or key
  3. So each machine has a different schema
  4. To avoid using sequences
A logical shard never changes identity, so it can be copied to a new machine; the map is the only thing that changes.

In the 41/13/10 layout, which field makes IDs roughly time-sortable?

  1. The low 10 bits
  2. The shard bits
  3. The high 41 bits, milliseconds since a custom epoch
  4. A random suffix
Time occupies the most significant bits, so a larger ID means a later time (to the millisecond).

What stops two different shards from producing the same ID?

  1. A central ID service
  2. The shard number is part of every ID and each shard has its own function
  3. Locks across shards
  4. UUID collision resistance
IDs differ in the 13-bit shard field even if time and sequence match.

How many IDs can one shard produce per millisecond with a 10-bit sequence (sequence taken mod 1024)?

  1. 10
  2. 1,000
  3. 1,024
  4. 8,192
2 to the power 10 is 1,024; beyond that within one millisecond the sequence would wrap.

Which cost does this design NOT have?

  1. A shard map to maintain
  2. Awkward range scans across shards
  3. Reliance on server clocks
  4. A network call to an ID service on every insert
IDs are minted inside the database as part of the insert; avoiding a separate ID service is the point.

Idempotency Keys at Stripe

A client sends "charge this card", the connection drops and it cannot tell whether the charge happened. Stripe's answer, in its 2017 post "Designing robust and predictable APIs with idempotency", is a client-supplied Idempotency-Key that lets the server recognise a retry and give the same outcome instead of repeating the work. The post and the API docs say what the contract is. For how to build the server side, I use Brandur Leach's closely related practitioner article "Implementing Stripe-like Idempotency Keys in Postgres": each key becomes a small state machine whose steps are database transactions, separated by calls to outside systems.

What I could and could not read

I fetched and read all three sources: Stripe's 2017 blog post, the current Stripe API documentation page on idempotent requests, and Brandur Leach's article. The article is by the same author as the blog post but describes his own reference implementation (a fictional ride-sharing service, "Rocket Rides"), not Stripe's internal code, so I label it "Leach's article" and treat it as a practitioner source. The docs page I read is the current one, which describes API v1 and, briefly, v2; retention figures below are the docs' today, not necessarily those of 2017.

The pattern in one sentence

Make a retried non-idempotent request safe by having the client name the operation with a key, then having the server record how far that operation got, so a retry either returns the saved answer or resumes at the next step instead of repeating a finished one.

Context

Stripe's post describes the problem: a network call can fail before the request starts, while the server is working, or after the work succeeded but before the client got the response. In the last two cases the client cannot know whether retrying is safe. HTTP PUT and DELETE are idempotent by definition; charging a customer is not, so a blind retry could double-charge. The post's fix is a unique client-chosen ID sent with the request, in Stripe's API the Idempotency-Key header, and the server correlates the key with the state of the original request. It also recommends that clients retry with exponential backoff and jitter so that a degraded server is not hammered, and notes that Stripe's Ruby library does this automatically. For the general reasoning about delivery guarantees see failure, timeouts and retries; for payment design see chapter 16.

Idempotency key
A client-generated token that identifies one logical operation across its retries.
Atomic phase
A group of local database operations that run in one transaction, bounded by calls to outside systems (Leach's term).
Recovery point
A label stored on the key row naming the last phase that committed; a retry jumps to the phase after it.
Foreign state mutation
A change to something outside your ACID database: a payment provider, an email, even a message queue. It cannot be rolled back by your transaction.

The contract, from Stripe's docs

For API v1, the docs say Stripe saves the status code and body of the first request made with a key after endpoint execution begins, and retries with the same key return that saved response, including 500 errors. Keys can be up to 255 characters, and the docs suggest V4 UUIDs or another sufficiently random string and warn against putting sensitive data such as email addresses in a key. Keys may be removed once they are at least 24 hours old; a key reused after pruning creates a new request. The idempotency layer compares incoming parameters with the original request's and errors if they differ, to prevent accidental misuse. Results are not saved when parameters fail validation or when the request conflicts with another one executing concurrently, because no endpoint began executing, so those requests can be retried. All v1 POST requests accept keys; sending one on GET or DELETE has no effect. The docs say API v2 behaves differently: retries do not repeat successful operations, and failed or partially failed work is retried to completion where possible.

The mechanism: the key lifecycle as a state machine

Leach's article turns "remember what happened to this key" into a table, idempotency_keys, with the key, the request method, path and parameters, a response code and body (null until finished), a recovery_point, a locked_at timestamp, and a unique index on user and key so different users can reuse the same string. The request handler is a loop over the recovery point. The article's four points are started, ride_created, charge_created and finished; the loop ends at finished and returns the stored response, so a finished key short-circuits to its answer.

Concurrency is handled with the lock: on first sight the key row is inserted with locked_at set; a retry that finds a recent lock gets 409 Conflict ("request in progress"); an expired lock can be taken over. The article runs each phase in a SERIALIZABLE transaction, so two racing upserts are resolved by Postgres aborting one. Each phase returns one of three actions: advance the recovery point, finish with a stored response, or continue without change. A serialization failure becomes 409, other errors 500, and in both cases the lock is released so a later retry can proceed. See isolation levels for why serializable is the simple choice here.

The mechanism: atomic phases

Leach's three rules for splitting work: upserting the key is its own phase; every foreign state mutation is its own phase; and all other local operations between them are grouped into phases. In the example, tx1 inserts the key (started), tx2 creates the ride and an audit record (ride_created), tx3 calls Stripe and stores the charge ID on the ride (charge_created), and tx4 stages a receipt-email job and sets the response to 201 (finished). The recovery point is updated inside the same transaction as the work it describes, so the label can never run ahead of or behind committed data. Because the receipt job is inserted into a staged_jobs table in tx4, it commits only if the request does; a separate enqueuer moves committed rows to the real queue. That is the outbox pattern applied to a single request.

The mechanism: foreign state mutations

The article defines foreign mutations as changes to systems outside the local ACID database and lists three kinds: naturally idempotent, made idempotent with a key (Stripe charges), and impossible to make idempotent. For the charge, the example sends Stripe its own idempotency key derived from the local key row's ID, so a crash between "Stripe charged" and "we recorded the charge" is repaired by the retry repeating the call and receiving the same charge. The article names a card error as unrecoverable (finish with 402 and the message) and other Stripe errors as retryable (503). For a non-idempotent foreign service that fails indeterminately, the article says you may have to mark the operation failed because retrying could duplicate it. The same thinking is behind sagas, where each step must be safe to repeat.

The mechanism: retries with different parameters

A key means "this exact operation". The docs say Stripe compares the incoming parameters to the original's and errors if they differ; Leach's article stores request_params and returns 409 with a mismatch message, treating it as a client bug. It is better to refuse than to return the first response for a different request, because the client would believe a charge of one amount succeeded when it asked for another. The same logic explains why validation errors and concurrent conflicts are not saved by Stripe: nothing happened yet, so the corrected request should be allowed to proceed under the same key.

A toy you can run

The toy below is my own SQLite sketch of the structure, not Stripe's or Leach's code. It crashes the handler at each phase boundary and in window B (after the provider charge but before it is recorded), retries, and counts charges at the "provider", which dedupes on its own key. Then it shows the mismatch response and, for contrast, a naive handler that charges first and records later using a fresh provider key per attempt.

"""Toy: idempotency-key state machine with atomic phases and recovery points (sqlite3, stdlib).
My model of the design described by Brandur Leach, not Stripe's code."""
import sqlite3, json
db = sqlite3.connect(":memory:", isolation_level=None)
db.executescript("""
CREATE TABLE keys(user INT, k TEXT, params TEXT, point TEXT, code INT, body TEXT, locked INT DEFAULT 0, PRIMARY KEY(user,k));
CREATE TABLE rides(id INTEGER PRIMARY KEY, user INT, k TEXT, charge TEXT);
""")
PROVIDER = {}                                    # foreign system: dedupes on its own key
def provider_charge(pkey, amount):
    PROVIDER.setdefault(pkey, {"amount": amount}); return pkey
class Crash(Exception): pass

def handle(user, k, params, crash_at=None):
    p = json.dumps(params, sort_keys=True)
    db.execute("BEGIN")
    row = db.execute("SELECT params,point,code,body FROM keys WHERE user=? AND k=?", (user, k)).fetchone()
    if row is None:
        db.execute("INSERT INTO keys(user,k,params,point) VALUES(?,?,?,'started')", (user, k, p)); point = "started"
    else:
        if row[0] != p: db.execute("COMMIT"); return 409, "parameters differ from the original request"
        if row[2] is not None: db.execute("COMMIT"); return row[2], row[3]
        point = row[1]
    db.execute("COMMIT")
    while point != "finished":
        if crash_at == point: raise Crash(point)
        if point == "started":                   # phase 2: local writes + advance recovery point, one transaction
            db.execute("BEGIN")
            db.execute("INSERT INTO rides(user,k) VALUES(?,?)", (user, k))
            db.execute("UPDATE keys SET point='ride_created' WHERE user=? AND k=?", (user, k)); db.execute("COMMIT")
            point = "ride_created"
        elif point == "ride_created":            # phase 3: foreign mutation, called with a derived provider key
            charge = provider_charge("ride-%s-%s" % (user, k), params["amount"])
            if crash_at == "after_charge": raise Crash("after_charge (charge made, not recorded)")
            db.execute("BEGIN")
            db.execute("UPDATE rides SET charge=? WHERE user=? AND k=?", (charge, user, k))
            db.execute("UPDATE keys SET point='charge_created' WHERE user=? AND k=?", (user, k)); db.execute("COMMIT")
            point = "charge_created"
        elif point == "charge_created":          # phase 4: store the response
            db.execute("BEGIN")
            db.execute("UPDATE keys SET point='finished',code=201,body=? WHERE user=? AND k=?", ("ride confirmed", user, k)); db.execute("COMMIT")
            point = "finished"
    return 201, "ride confirmed"

for crash in ("started", "ride_created", "after_charge", "charge_created"):
    k = "key-" + crash
    try: handle(1, k, {"amount": 2000}, crash_at=crash)
    except Crash as c: print("crash at", c, "| stored recovery point:", db.execute("SELECT point FROM keys WHERE k=?", (k,)).fetchone()[0])
    print("  retry ->", handle(1, k, {"amount": 2000}), "| retry again ->", handle(1, k, {"amount": 2000}))
print("rides:", db.execute("SELECT count(*) FROM rides").fetchone()[0], "| provider charges:", len(PROVIDER))
print("same key, different amount ->", handle(1, "key-started", {"amount": 9999}))
print("same key text, other user  ->", handle(2, "key-started", {"amount": 2000}), "(keys are scoped per user)")

# Contrast: naive 'charge, then record' with a fresh provider key per attempt; crash between the two steps.
import itertools
attempt_ids = itertools.count()
PROVIDER.clear()
def naive(crash):
    provider_charge("attempt-%d" % next(attempt_ids), 2000)
    if crash: raise Crash("before recording")
try: naive(True)
except Crash: pass
naive(False)                                     # the client's retry
print("naive handler after one crash+retry: provider charges =", len(PROVIDER))

  retry -> (201, 'ride confirmed') | retry again -> (201, 'ride confirmed')
crash at ride_created | stored recovery point: ride_created
  retry -> (201, 'ride confirmed') | retry again -> (201, 'ride confirmed')
crash at after_charge (charge made, not recorded) | stored recovery point: ride_created
  retry -> (201, 'ride confirmed') | retry again -> (201, 'ride confirmed')
crash at charge_created | stored recovery point: charge_created
  retry -> (201, 'ride confirmed') | retry again -> (201, 'ride confirmed')

same key, different amount -> (409, 'parameters differ from the original request')
same key text, other user  -> (201, 'ride confirmed') (keys are scoped per user)

Reading the output: the crash after the charge leaves the recovery point at ride_created (the label only advances with a committed phase), the retry repeats the provider call, and the provider's own key keeps the count at one charge per ride (four rides, four charges). The naive handler ends with two charges for one logical request.

What they learned or changed

  • Persist progress, not only the answer. Stripe's post describes returning the cached result when the work succeeded but the response was lost; Leach's article shows the extra step needed when the work was half done: recovery points.
  • Make every outside call idempotent or isolate it. The charge gets a derived provider key; an email becomes a staged job; a call that cannot be made idempotent forces a design decision about marking the operation failed.
  • Keys are short-lived. The docs say v1 keys may be removed after at least 24 hours; Leach's article describes a reaper that deletes keys after about 72 hours and a completer that pushes stalled requests (whose clients stopped retrying) to completion.
  • Do not save results for requests that never started. Validation failures and concurrent conflicts are retryable because no endpoint ran.
  • The database matters. The article says a non-ACID store cannot support this, because every write becomes effectively a foreign mutation.

The pattern to remember

Analogy: a restaurant order slip

The waiter writes your order on a numbered slip. If the kitchen is asked twice for slip 42, it checks the slip: "starter done, main on the grill" and carries on instead of cooking everything again. If you come back with slip 42 but a different order, they say "that is not what this slip says". Paying the bill is the one step that needs a receipt from the card machine with its own number.

Where it breaks down: a paper slip does not have a lock; two waiters can grab it at once, which is why the database's lock and serialisable transactions are needed.

Key takeaways

  • The client names the operation; the server records its progress against that name.
  • Split work into atomic phases at every foreign call; store a recovery point in each phase's transaction.
  • Give each outside call its own idempotency key derived from yours; use a transactional outbox for effects like email.
  • Same key, different parameters is an error, not a replay.
  • Keys expire; design for retention, a reaper and a completer.

Use it in an interview

Say: "Mutating endpoints take a client-generated idempotency key. I store it in a row with the request parameters and a recovery point. I split the handler into transactions around each external call, advance the recovery point inside each, and give the payment call a key derived from mine. A retry with the same parameters resumes or returns the saved response; different parameters return a conflict." Then name the failure windows: before the call, between the call and recording it, and after.

Don't: say "just add a unique constraint" and stop. A unique constraint stops duplicate rows but does not resume half-finished work, and it does nothing about the external charge. Put numbers on retention (the docs say at least 24 hours for v1) and tie the design to the payment flow in chapter 16.

  4. Delete the key and start over
Both the docs and Leach's article compare the stored parameters and refuse a mismatch, to prevent accidental misuse.

Why is the recovery point updated in the same transaction as the phase's work?

  1. To save a query
  2. So the label always matches committed work and a crash cannot leave it ahead or behind
  3. Because Postgres requires it
  4. To avoid using locks
If the label and the data could diverge, a retry would skip or repeat a step.

The process dies after the payment provider charged the card but before the charge ID was stored. How does the design stay correct?

  1. It cannot; money is lost
  2. The retry repeats the provider call with the same derived provider key, which returns the same charge
  3. The client must call support
  4. A cron job refunds it
The foreign mutation is made idempotent with its own key, so repeating it is safe.

Per Stripe's v1 docs, which requests are NOT saved as the key's result?

  1. Successful charges
  2. Requests that fail validation or conflict with a concurrently executing request, since no endpoint began executing
  3. Requests that return 500
  4. All GET requests
Results are saved only after execution of an endpoint begins; the others can be retried.

Why does Leach's article put the receipt email in a staged-jobs table inside the last transaction?

  1. Email is slow
  2. So it is sent only if the request's transaction commits, and never twice for a retried request
  3. Because queues are not allowed
  4. To encrypt it
The staged job commits atomically with the response; an enqueuer later moves it to the queue (an outbox).

Twitter's Timelines at Scale

Twitter's home timeline is read far more often than it is written, so it did the opposite of the obvious thing: instead of building your timeline when you open the app, it built it ahead of time. Every new tweet is pushed into a list held in Redis for each follower. Raffi Krikorian's "Timelines at Scale" (QCon San Francisco, 2012) is the canonical description. Accounts with tens of millions of followers broke the symmetry, because one tweet means tens of millions of inserts.

The pattern in one sentence

When reads vastly outnumber writes and each read must be fast, spend the work at write time: precompute each reader's result into memory, cap its size, and treat the few authors whose write cost explodes as a special case.

Context

The abstract of the talk says Twitter handled "thousands of events per sec" at steady state, covering tweets, social-graph changes and direct messages, delivered to disk, in-memory timelines, email and mobile devices. The High Scalability write-up gives the scale it takes from the talk: about 150 million active users, about 300 thousand timeline reads per second, roughly 400 million tweets a day and, by its numbers, a write rate of a few thousand tweets per second (it gives about 4K and about 6K writes per second in different places, and 5K per second on average with 7K at the daily peak for tweet input). The ratio is the whole story; the napkin arithmetic below is mine.

followers, batch = 31_000_000, 4_000

# Toy: push into capped per-user lists, pull for 'big' authors at read time (not Twitter's code)
from collections import defaultdict, deque
CAP = 800
timelines = defaultdict(lambda: deque(maxlen=CAP))
followers_of = {"alice": ["u1", "u2"], "star": ["u1", "u2"]}
BIG = {"star"}                      # authors we do not fan out
big_tweets = defaultdict(list)
def post(author, tid):
    if author in BIG: big_tweets[author].append(tid); return
    for f in followers_of[author]: timelines[f].appendleft(tid)
def read(user, follows_big):
    ids = list(timelines[user]) + [t for a in follows_big for t in big_tweets[a]]
    return sorted(ids, reverse=True)[:5]       # ids grow with time, so sort = recency
for tid, a in [(1, "alice"), (2, "star"), (3, "alice"), (4, "star")]: post(a, tid)
print("u1 timeline (pushed + merged on read):", read("u1", ["star"]))

The mechanism: fan-out on write

As the write-up describes it, a tweet is stored, then a fan-out daemon asks the social-graph service for the author's followers and inserts the tweet's ID into each follower's timeline list in a Redis cluster, in batches of about 4,000 destinations. Each entry holds the tweet ID, the author's user ID and 4 bytes of flags (for instance, whether it is a retweet or a reply); a retweet points at the original. Each list is capped at 800 entries, and each timeline is replicated three times across machines. Only users who were active recently (the write-up says logged in within 30 days, adjustable with cache capacity) are kept in memory. The write-up quotes the guiding rule, "Don't do any computation on reads".

On the read path the timeline service finds one of the replicas and uses whichever answers first, then hydrates the IDs by fetching tweet text from the tweet store in parallel (the write-up names MySQL behind Gizzard as the disk store). If a user's list is not in Redis, the system rebuilds it: ask the social graph whom the user follows, read each followee's recent tweets from disk and write the result into Redis. The write-up reports cold-cache loads at about 2 seconds to the browser and about 400 ms for API calls, and for normal requests to the timeline service about 5 ms at the median and 100 ms at p99. It also reports about 30 billion deliveries per day and a goal of delivering a tweet within 5 seconds.

The write-up's own words about the trade are that writes become heavy so that reads can be a lookup. My design commentary (general): the cap makes the memory per user constant, so capacity planning is "active users times 800 entries times entry size", and the IDs-only entries keep the list small because the text lives elsewhere. Redis lists make the push cheap and ordered. See chapter 6 for the cache concerns that follow: replicas, eviction, and rebuild storms.

The mechanism: the high-follower problem

Fan-out cost is linear in follower count. The write-up cites accounts with about 31 million and about 28 million followers at the time, which means tens of millions of inserts for one tweet. It says fan-out for such accounts can take minutes, so followers see a tweet at different times and a reply can even appear before the tweet it answers. For delivery to 1 million followers it reports about 3.5 seconds at the median, and up to 5 minutes at p99 for large fan-outs.

The write-up's stated change is to stop fanning out tweets from very high-follower accounts and to merge them into a reader's timeline at read time, saying it would save tens of percent of compute. I could not verify what was deployed and in what form; I treat it as the write-up's description of a direction, and it matches what chapter 9 calls the hybrid approach. The toy at the end of the code block above shows the merge with a threshold set by hand; it is mine, not Twitter's, and a real design must choose the threshold, the data structure for the big accounts' tweets, and what to do about readers who follow hundreds of them.

What they learned or changed

  • Move work to where it is cheapest. Reads at hundreds of thousands per second left no budget for computation, so the work moved to the write, where it is asynchronous and can be batched.
  • Cap and prune. The 800-entry cap and the active-users-only rule bound memory; the rebuild path means eviction is safe (the data can be recomputed from the graph and tweet store).
  • Averages hide the tail. The mean fan-out is small; the maximum is tens of millions. The design is shaped by the maximum.
  • Freshness is a budget, not a promise. A target of seconds, with minutes at p99 for the largest accounts, is an explicit trade the write-up reports.

The pattern to remember

Analogy: the newspaper round

A newsagent could wait until you ask and then run around the shop collecting every title you subscribe to. Instead, when the papers arrive at dawn, she drops each one into your pigeonhole, so collecting is instant. A famous weekly with millions of subscribers would take all morning to sort, so that one is left on a table by the door and you pick it up as you leave.

Where it breaks down: pigeonholes do not run out of room at 800 items or get rebuilt from scratch when you were away for a month.

Key takeaways

  • With a read-to-write ratio in the tens, precompute at write time.
  • Store compact references (IDs and flags) and hydrate on read; cap the list and keep it only for active users.
  • Make eviction safe by having a rebuild path from the sources of truth.
  • Fan-out cost is proportional to followers, so design for the maximum, with a read-time merge for the largest accounts.
  • State freshness as a target with a tail, for example seconds typically and minutes at p99.

Use it in an interview

Say: "Reads outnumber writes by something like fifty to one, and a refresh has to be fast, so I'd precompute each user's feed on write: push the post's ID into every follower's capped in-memory list, and fetch the content afterwards. A tiny share of accounts have millions of followers, so I'd skip the push for them and merge their recent posts into the feed at read time." Then give your own numbers and the thresholds.

Don't: open with a company name or recite its figures from memory. Show the derivation: the ratio, the average and maximum fan-out, the memory per user. If asked "how do you know this works", say large social networks have described this hybrid publicly and offer to compare push, pull and hybrid with the numbers (see the fan-out lab).

Check your understanding

Why precompute timelines at write time?

  1. Writes are cheaper than reads in Redis
  2. Timeline reads vastly outnumber tweets and must be fast, so the work is moved to the less frequent event
  3. It avoids storing tweets
  4. It guarantees strict ordering across users
With reads in the hundreds of thousands per second and tweets in the thousands, one extra write per follower is cheaper overall than computing at read time.

What does a timeline entry store, per the write-up?

  1. The full tweet text
  2. The tweet ID, the author's user ID and a few bytes of flags
  3. Only the follower's ID
  4. A copy of the author's profile
Entries are compact references; the text is fetched (hydrated) from the tweet store.

What is the main problem with fan-out on write for an account with tens of millions of followers?

  1. Redis cannot store IDs
  2. One tweet costs tens of millions of inserts, which takes minutes and delays followers unevenly
  3. The social graph forgets followers
  4. Timelines exceed 800 entries immediately
Cost is linear in followers; the write-up reports minutes at p99 for large fan-outs.

What does the write-up describe as the change for very high-follower accounts?

  1. Delete their tweets after a minute
  2. Stop pushing their tweets and merge them into the timeline at read time
  3. Give them a separate Redis cluster per follower
  4. Shard Redis by tweet ID
A hybrid: pushed list plus a read-time merge for the largest accounts.

What happens if a user's timeline is not in Redis?

  1. The request fails
  2. It is rebuilt from the social graph and the followees' tweets on disk
  3. The user sees an empty timeline permanently
  4. The oldest replica is promoted
The rebuild path is what makes eviction of inactive users safe.

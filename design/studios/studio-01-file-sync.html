Design File Sync (Dropbox)

Design a service that keeps folders identical across a person's devices and across the people they share with. The hard parts are not uploading files; they are not re-uploading everything after a one-byte edit, catching up devices that were offline for weeks, and never losing someone's work when two people edit at once.

How a design studio works

This page is a mock design session of 45 to 60 minutes, not a chapter. At each stage there is a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer is one strong design with its reasoning, not the only right one. The stages follow the framework: clarify, estimate, API, data model, architecture, deep dives, failure modes, trade-offs, and a spoken summary. A rubric at the end separates mid-level from senior signals. All numbers on this page are assumptions to reason with, not measurements.

📐 The brief

An interviewer says: "Design a file sync service like Dropbox. A user installs a client, a folder on their laptop appears on their phone and their other laptop, and they can share folders with other people."

  • Files range from 1 KB notes to multi-gigabyte videos. Users edit files, rename them, move whole folders, and work on planes.
  • A client may be offline for weeks and must then converge without losing anyone's work.
  • Think of the storage layer as the one in the object-storage chapter and the Magic Pocket case; the interesting part here is everything above it.
  • You have 45 to 60 minutes. Follow the framework: clarify, estimate, API, data model, architecture, deep dives, failure modes, trade-offs.

  • 200 PB logical, 133 PB unique after dedup. Storage is dominated by cold bytes, so erasure coding and tiering matter (object storage). A dedup ratio of 1.5 is an assumption; measure it before promising anything.
  • 133 billion chunks, a 13 TB block index, and 400 billion files with 120 TB of metadata. The block index is a hash to location map that must be sharded; the file metadata must be sharded too, by something that keeps one user's tree together. Neither fits a single database.
  • About 3,500 commits per second on average, 10,000 at peak. That is modest: a sharded relational store handles it. The write load is not the hard part; the many-small-files shape and the fan-out are.
  • 56 Gbit/s upload on average, 167 Gbit/s at peak, so the data path must bypass the metadata service. Clients move bytes to and from the block tier; the metadata service only sees hashes (compare the presigned pattern in the object storage chapter).
  • 51 million open notification connections. At 100 thousand per gateway that is about 510 gateways. Polling every 30 seconds would be 1.7 million requests per second of nothing; a held connection costs memory, not requests (chat and presence).
  • Client-side bandwidth: an initial sync of 100 GB over a 20 Mbit/s uplink takes 100 GB x 8 / 20 Mbit/s = 40,000 s, about 11 hours. That is why chunk-level resume, dedup before upload, parallel connections and bandwidth throttling are product requirements, not optimisations.

3API

Sketch the API a client uses to sync. Which calls are idempotent? Which ones touch metadata, and which touch blocks?

Compare with a worked answer

Two planes: a small metadata API and a bulk block API. Everything is keyed by namespace (a user's root folder or a shared folder).

-- block plane (bytes; content-addressed, naturally idempotent)
POST /blocks/missing   {hashes:[h1..hn]}                   -> {missing:[h3, h7]}
PUT  /blocks/{sha256}  body=chunk  (signed, short-lived URL) -> 200   # server re-hashes, rejects mismatch
GET  /blocks/{sha256}  (signed URL scoped to ns + file rev)  -> bytes

-- metadata plane
POST /commit    {ns, file_id, base_rev, blocklist:[h1..hn], size, mtime,
                 commit_id: "device42:8841"}
                -> {rev:9}  |  {need_blocks:[h3]}  |  409 {conflict, current_rev:8}
POST /move      {ns, file_id, base_rev, new_parent, new_name, commit_id}
POST /delete    {ns, file_id, base_rev, commit_id}            # soft delete
GET  /changes   ?ns=..&cursor=812340&limit=500  -> {entries:[...], cursor:812840, has_more}
GET  /longpoll  ?ns=..&cursor=812840&timeout=60 -> {changes:true|false}

POST /share     {ns, member, role: viewer|editor}  POST /links {path, expires, password?}
  • Block calls are idempotent by construction: the key is the hash of the content, so uploading twice stores once.
  • Metadata writes carry a commit_id (device id and a local counter) so a retry after a timeout returns the original result and does not create a second revision (idempotency keys, as in the payments chapter).
  • base_rev is a compare-and-swap: "I am changing the version you called 8." The server refuses if the file moved on. That one field is the whole conflict-detection mechanism, and deep dive 3 builds on it.
  • The order is: upload missing blocks, then commit. A file only becomes visible when its blocklist commits, so a crash halfway leaves orphan chunks (garbage-collected) and never a half-visible file.
  • Pagination is a cursor, not an offset, because the list keeps growing while you read it (feed chapter for the same argument).

  • Shard metadata by namespace, not by user and not by file. Everything a sync needs (tree, journal, ACL) is then on one shard, the journal counter needs no cross-shard coordination, and a commit is one local transaction. The price: one giant shared folder is a hot shard, which we handle by splitting its journal if it ever happens (a sharded counter, as in the photo studio).
  • Blocks are separated from metadata because they have opposite shapes: metadata is small, mutable and transactional; blocks are big, immutable and bandwidth-bound. Mixing them in one store gives you the worst of both (building blocks).
  • Refcounts are an optimisation, not truth. Truth is the set of blocklists in current files and retained versions; refcounts are repaired by a background mark-and-sweep (see failure modes).

5High-level architecture

Draw the boxes. Which path carries the bytes, which carries the decisions, and which carries the wake-up call?

Compare with a worked answer

Upload of an edited file, step by step:

  1. The client's file watcher sees a write, waits for it to settle, and runs the chunker over the file (deep dive 1), producing a blocklist of hashes.
  2. POST /blocks/missing with those hashes. The block service answers with the ones it has never seen; for a small edit that is one chunk.
  3. The client PUTs the missing chunks directly with signed URLs. The block tier verifies each hash and stores it durably before acknowledging.
  4. POST /commit with the blocklist and base_rev. The metadata shard runs one transaction: check base_rev, increment the namespace's next_rev, update the file entry, append a journal row. If the check fails, the answer is a conflict (deep dive 3).
  5. The commit publishes "ns X is at rev 8841" on the change bus (via a transactional outbox so a crash cannot lose it, streams and CDC). The gateways holding connections for devices in that namespace wake them.
  6. Each other device calls /changes?cursor=, receives the journal entries, fetches the missing chunks and applies them locally.

6Deep dive 1: chunking and deduplication

A user inserts one byte at the start of a 1 GB file. With fixed-size chunks, how much do you upload? How would you cut chunks so that the answer is one chunk? Prove it with a few lines of code.

Compare with a worked answer

Fixed-size chunks give boundaries at multiples of the chunk size, so an insertion shifts every later byte across every later boundary and every later chunk changes hash. Content-defined chunking (CDC) puts boundaries where a rolling hash of the last few dozen bytes satisfies a condition (here: low 12 bits are zero, so about one position in 4096). Boundaries then depend on local content, not on offset, and an insertion only disturbs the chunk it lands in. Below, a "Gear" rolling hash: h = (h << 1) + GEAR[byte]. The shift pushes old bytes out after 32 steps, so only the last 32 bytes matter. Minimum and maximum sizes bound the pathological cases.

"""Fixed vs content-defined chunking: insert ONE byte near the start of a file."""
import hashlib, random

rng = random.Random(7)
data = bytes(rng.getrandbits(8) for _ in range(256 * 1024))      # a 256 KiB "file"
edited = data[:100_000] + b"X" + data[100_000:]                        # insert one byte at offset 100,000

def fixed_chunks(b, size=4096):
    return [b[i:i + size] for i in range(0, len(b), size)]

# Gear-style rolling hash: h = (h << 1) + GEAR[byte]; a boundary is where the low bits are zero.
GEAR = [random.Random(i).getrandbits(32) for i in range(256)]
MASK = (1 << 12) - 1            # 12 zero bits -> average chunk about 4 KiB
MIN, MAX = 1024, 16384

def cdc_chunks(b):
    out, start, h = [], 0, 0
    for i, byte in enumerate(b):
        h = ((h << 1) + GEAR[byte]) & 0xFFFFFFFF
        size = i - start + 1
        if (size >= MIN and (h & MASK) == 0) or size >= MAX:
            out.append(b[start:i + 1]); start, h = i + 1, 0
    if start < len(b):
        out.append(b[start:])
    return out

def ids(chunks):
    return [hashlib.sha256(c).hexdigest()[:8] for c in chunks]

for name, fn in (("fixed 4 KiB", fixed_chunks), ("content-defined", cdc_chunks)):
    a, b = ids(fn(data)), ids(fn(edited))
    old = set(a)
    new = [x for x in b if x not in old]
    print(f"{name:16} chunks before={len(a):3} after={len(b):3} "
          f"chunks to upload={len(new):3} ({100 * len(new) / len(b):.0f}%)")

sizes = [len(c) for c in cdc_chunks(data)]
print(f"cdc chunk sizes: min={min(sizes)} avg={sum(sizes) // len(sizes)} max={max(sizes)}")
fixed 4 KiB      chunks before= 64 after= 65 chunks to upload= 41 (63%)
content-defined  chunks before= 53 after= 53 chunks to upload=  1 (2%)
cdc chunk sizes: min=488 avg=4946 max=16384

The demo uses a 4 KiB average so it runs in a blink; a real service would choose around 1 MiB (our estimate above), with the minimum and maximum a quarter and four times the average. In the run, fixed chunks re-upload 63% of the file after one byte is inserted at offset 100,000, while content-defined chunking re-uploads 1 chunk of 53 (2%). The cost: a hash per byte on the client (a few hundred MB/s per core in optimised code) and a variable chunk size, which the block index must tolerate. Tested with insertions near the very start of a file the result can be two chunks, because the minimum-size rule skips boundaries in the first bytes of a chunk. The lesson is "a small, bounded number of chunks", not literally one.

  • Dedup is a lookup by hash. The client sends the hashes it computed; the server says which are missing. SHA-256 collisions are not a practical concern; verify the hash on the server anyway so a buggy client cannot poison the store.
  • Cross-user dedup has a privacy side channel. If "already have it" is visible to the uploader, an attacker can test whether anyone stored a given file. Mitigations: dedup only within an account or team, or make the client prove it holds the bytes (the server asks for hashes of random byte ranges), as discussed in deep dive 4.
  • Compress after chunking, not before: compressing first destroys the repeating structure the chunker looks for. Skip already-compressed formats (video, JPEG, zip).

7Deep dive 2: metadata versus blocks, the journal and the cursor, and notifications

How does a device that was offline for three weeks catch up, without scanning the whole tree and without missing anything? How do online devices learn of a change within seconds, and what do you do when the notification is lost?

Compare with a worked answer

The journal is the protocol. Each namespace has an append-only journal with a gap-free, increasing rev. A device stores one number per namespace, its cursor: the last rev it applied. Catching up is "give me everything after cursor 812340", paged. It does not matter whether the gap is three seconds or three weeks, and the server keeps no per-device state, which is why it scales. If the journal has been compacted past the cursor (the device was away too long), the server answers "cursor too old" and the client does a full tree snapshot once, then resumes from the snapshot's rev.

Notifications are hints. A ping says "ns X advanced"; it carries no data and may be lost, duplicated or late, because the device will ask /changes anyway and an unchanged cursor is a cheap no-op. This is the same split as in the chat design: a transient wake-up channel on top of a durable log. Therefore a gateway crash, a dropped message or a thundering reconnect cannot corrupt state; it can only delay.

  • Recommendation: long poll for the desktop client at first (it traverses corporate proxies, and the server side is stateless apart from the held request), WebSockets as an upgrade, OS push for sleeping phones. All three call the same /changes. Sizing and the connection registry are in the chat and presence chapter.
  • Fan-out is by namespace. The bus maps ns to the gateways holding a connection from any member device. A shared folder with 2,000 members is 2,000 pings per commit; coalesce pings (one per ns per second) so a burst of edits does not become a storm.
  • Reconnect storms. After a gateway or region failure millions of clients reconnect at once. They use exponential backoff with full jitter and the server can answer "come back in N seconds" (overload). Because state is in the journal, a throttled client loses nothing but time.
  • Why metadata and blocks are separate services: the metadata path needs transactions, low latency and a small footprint; the block path needs throughput and cheap bytes. They scale, fail and are deployed independently, and the block index is the only place they meet. Magic Pocket in the case study is a production block tier with exactly this boundary; the details of its placement and repair are there and in the object storage chapter, so we treat the block tier as a black box with missing, put and get.
  • Ordering guarantee: within a namespace, devices see journal entries in rev order, so "create folder, then create file inside it" can never arrive reversed. Across namespaces there is no order, and none is needed.

8Deep dive 3: offline edits and conflicts

Alice and Bob both have version 7 of report.docx. Both go offline and edit. Alice reconnects first. What exactly happens when Bob reconnects, and what options exist beyond a conflicted copy?

Compare with a worked answer

The mechanism is already in the API. Alice commits base_rev = 7 and gets rev 8. Bob's commit says base_rev = 7, the server sees current rev 8 and answers 409. Bob's client then does not overwrite and does not discard: it keeps its own bytes, saves them as a sibling file named like report (Bob's conflicted copy 2026-10-13).docx, commits that as a new file, and applies Alice's rev 8 to the original. Nothing is lost, both people can see both versions, and a human decides. The server never merges bytes it does not understand.

  • Recommendation: conflicted copies for the file layer, which must handle any bytes a user owns, and CRDT or OT inside specific document types where the product owns the editor (the collaborative editor studio). A file sync service cannot make a CRDT out of an opaque .psd.
  • Edit versus delete. Alice deletes, Bob edits offline. Choose "edit wins": Bob's commit resurrects the file, since losing an edit is worse than keeping a deleted file.
  • Rename plus edit merges for free because identity is a file_id, not the path. Alice renames the file while Bob edits its content; both commits apply to the same id with different fields. Identity by path would turn it into a delete and a create.
  • Move cycles. Alice moves folder A into B while Bob moves B into A. The second commit would create a cycle with no root. The metadata shard checks ancestry inside the commit transaction and refuses it, and the client treats the refusal like a conflict. This is a classic senior-level catch.
  • Case and name collisions. macOS is case-insensitive and Linux is not; two files A.txt and a.txt from Linux collide on a Mac. Detect on the client and apply a deterministic rename, so every device converges to the same tree.
  • Long offline periods raise conflict probability, not the mechanism. Version history (every rev keeps its blocklist for 30 days or more) means an unwanted overwrite is always one click from undone.

9Deep dive 4: sharing, permissions, bandwidth and encryption

How does a shared folder appear in another person's tree, who is allowed to read a block, and what does encryption do to deduplication? Where does the client save bandwidth?

Compare with a worked answer

Sharing is a namespace. A shared folder is its own namespace with its own journal and ACL. Each member mounts it at a path in their tree; the mount is a pointer entry in their root namespace. A device syncs the root namespace and each mounted namespace independently, and a commit to a shared namespace is checked against the ACL inside the metadata transaction (authorization: check at the resource, every time, never only at the UI).

  • Who may read a block? Blocks are addressed by hash, and a hash is not a secret you may rely on. Download URLs are signed for (ns, file_rev) and short-lived, so access is checked against the file entry's blocklist and the caller's role, not against "knows the hash". Revoking a member means their next /changes and /blocks calls are refused; chunks already downloaded cannot be recalled, which is a limit to state honestly.
  • Share links carry a random token of at least 128 bits, optional expiry and password, and an audit trail. They authorise one path or file, not the account (multi-tenancy: isolate by namespace, test the cross-tenant case).
  • Removing a member who authored files does not delete their contributions; ownership belongs to the namespace, which is the organisational answer to "who owns files when someone leaves".

  • Bandwidth on the client: upload and download are throttled by a user setting and by a congestion-friendly background mode; chunk uploads are resumable (a lost connection costs one chunk); several chunks go in parallel to fill a fat pipe; LAN sync lets two devices on the same network exchange chunks directly; a new device's initial sync starts with the most recently used files.
  • Server bandwidth: 300 TB a day downloaded is about 28 Gbit/s on average; large downloads can come through a CDN with signed URLs when the same chunk is hot (a popular shared file), not for private chunks that nobody else asks for.

  • Sync freshness: 95% of small-file commits visible on another online device within 5 s, 99% within 30 s. Measure it end to end with canary devices that write and read.
  • Commit availability: 99.95% of commit calls succeed (excluding client errors such as conflicts), per month, with alerts on burn rate (alerting).
  • Durability: zero acknowledged commits whose blocks cannot be read; a continuous verifier samples committed files and re-reads them, and a single failure pages.

Rollout. Clients cannot be forced to upgrade, so the protocol is versioned and the server speaks every version still in use for years. Roll out server changes behind flags, per namespace, and shadow-write a new journal format beside the old one before switching reads (deployments). Roll out a client in rings: employees, 1%, 10%, then everyone, watching crash rate, conflict rate and bytes uploaded per user; a jump in bytes uploaded per edit is the signature of a chunking bug.

How a senior engineer would summarise this

"The clients keep a local copy and the service has two planes. The data plane stores immutable chunks addressed by SHA-256, cut by content-defined chunking at about a megabyte, so a one-byte insert touches one chunk instead of shifting the rest of the file. The client asks which hashes are missing, uploads only those straight to the block store, and the block tier is erasure-coded and verified like the one in the Magic Pocket case. The metadata plane is sharded by namespace, a user's root or a shared folder, and each namespace has an append-only journal with increasing revisions, so a commit is one local transaction: compare the base revision, bump the counter, update the file entry, append a journal row. Devices keep a cursor per namespace, so catching up after three weeks is just 'give me changes after cursor N', and notifications over long poll or WebSockets are only hints; losing one costs seconds, never data. If two devices edit the same base revision the second commit fails the compare, and the client saves its version as a conflicted copy, so nothing is lost; for live documents we would put a CRDT editor on top. Sharing is a namespace with an ACL checked at every commit and every signed block URL. I'd estimate about 3,500 commits per second, 56 Gbit/s of upload and 51 million held connections, which is why metadata and bytes are separate. The main risks are a client bug that deletes files, which we cover with soft delete and staged rollout, and garbage collection racing an in-flight commit, which we cover with a grace period. If we needed end-to-end encryption we would lose server-side search and cross-user dedup."

Notice the shape: two planes → chunking → journal and cursor → hints not truth → conflicts without loss → permissions → named risks.

Key takeaways

  • Content-defined chunks turn an edit into a bounded number of changed chunks; fixed chunks turn an insert into a full re-upload.
  • Keep bytes and decisions apart: immutable hash-addressed blocks on one plane, small transactional metadata on the other.
  • A per-namespace journal and a cursor per device make catching up after any gap the same cheap operation.
  • Notifications are hints. The journal is truth. Lost pings cost seconds, not data.
  • A compare-and-swap on the base revision detects conflicts; conflicted copies preserve work; CRDTs belong inside editors you own.
  • Dedup, encryption and sharing interact: decide which one you give up when you need end-to-end encryption.
  • The worst bugs are the ones that delete: soft delete, delayed garbage collection and ring rollouts are part of the design.

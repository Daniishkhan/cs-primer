Design an Online Code Judge

Design a platform that compiles and runs code written by strangers against hidden tests, returns a verdict in seconds, and hosts live contests where tens of thousands submit in the same minutes. The core problems are isolation, a queue that survives a known spike, and results that are fair and reproducible.

How a design studio works

This page is a mock design session of 45 to 60 minutes, not a chapter. At each stage there is a Your turn question. Write your answer in the notes box first (it saves in this browser), then open the worked answer and compare. The worked answer is one strong design with its reasoning, not the only right one. The stages follow the framework: clarify, estimate, API, data model, architecture, deep dives, failure modes, trade-offs, and a spoken summary. A rubric at the end separates mid-level from senior signals. All numbers on this page are assumptions to reason with, not measurements.

📐 The brief

An interviewer says: "Design an online judge like LeetCode or Codeforces. Users submit source code in several languages; the system compiles and runs it against hidden tests and returns a verdict. It also hosts live contests with a leaderboard."

  • The code is written by strangers, some of them hostile. You are being asked to run it on your machines.
  • A big contest starts at a fixed time, and tens of thousands of people submit in the same few minutes.
  • Builds on containers and virtual machines, cloud and container security, the job scheduler chapter and overload.
  • You have 45 to 60 minutes. Follow the framework.

2Estimate

How many submissions arrive, how much CPU does each take, how many cores keep the contest queue short, and what does it cost? Simulate a contest with a start burst and a final rush.

Compare with a worked answer

A fluid simulation: arrivals per second follow the contest shape (a burst for the first five minutes, a quiet middle, a final-ten-minute rush), and workers drain the queue at cores / core_seconds_per_job.

"""Code judge: contest-spike simulation. Every input is an assumption."""
participants, subs_each, contest_min = 50_000, 15, 120
subs = participants * subs_each
avg = subs / (contest_min * 60)
print(f"{subs:,} submissions in {contest_min} min -> {avg:,.0f}/s average")
tests, cpu_per_test, startup = 25, 0.4, 0.25     # seconds of one core
core_s = startup + tests * cpu_per_test
print(f"one submission = {tests} tests x {cpu_per_test}s + {startup}s sandbox start = {core_s:.1f} core-seconds")

# arrival rate per second: a burst in the first 5 min (reading + easy problem), a base, and a final-10-minute rush
def arrivals(t):
    if t < 300: return 3.0 * avg
    if t > contest_min * 60 - 600: return 6.0 * avg
    return 0.7 * avg
peak = max(arrivals(t) for t in range(contest_min * 60))
print(f"peak arrival {peak:,.0f}/s -> needs {peak*core_s:,.0f} busy cores ; average needs {avg*core_s:,.0f}")

def run(cores):
    backlog, worst_wait, served = 0.0, 0.0, 0.0
    for t in range(contest_min * 60 + 3600):
        a = arrivals(t) if t < contest_min * 60 else 0
        backlog += a
        done = min(backlog, cores / core_s)
        backlog -= done
        worst_wait = max(worst_wait, backlog * core_s / cores)   # seconds a newly arrived job waits
    return worst_wait

  • 10 core-seconds per submission (25 tests at 0.4 s, plus 0.25 s to start a sandbox). A submission is not a request; it is a small batch job, so size the system with cores and Little's law, not requests per second.
  • Peak arrival of 625 per second needs about 6,400 busy cores (625 x 10.2). That matches the simulation: 6,000 cores leaves a 40 second wait at the final rush, 7,000 cores clears it. The average of 104 per second needs only about 1,070 cores, so provisioning for the average is a six-fold under-build.
  • The knee is steep. Between 6,000 and 7,000 cores the worst wait goes from 40 seconds to zero; below 4,000 it is minutes. This is the utilisation-versus-latency curve in the queueing theory chapter.
  • Cost is dominated by the peak you provision. 12,000 cores for a 2 hour contest at an assumed price of $0.04 per vCPU-hour is about $960; keeping that fleet running all day would be $11,500. The design goal is therefore to rent the fleet for the contest and release it, which means pre-warming and a pool that can scale quickly (stage 7).
  • Per submission cost is about a hundredth of a cent (10.2 core-seconds x $0.04 / 3600). Early exit on the first failed test (typical for ICPC-style judging) roughly halves the CPU of wrong submissions, and caching compiled binaries by source hash saves the compile step on re-submits.

3API

Define the user-facing and internal APIs. What does a client see while a submission is being judged, and how do you avoid leaking the tests through verdicts?

Compare with a worked answer 
POST /problems/{pid}/submissions  {lang, source, contest_id?, idempotency_key}
                                  -> 202 {submission_id, status: "queued"}
GET  /submissions/{id}            -> {status: queued|compiling|running|done,
                                      verdict: AC|WA|TLE|MLE|RE|OLE|CE,
                                      time_ms, memory_kb, first_failed_test? (hidden in contests)}
GET  /contests/{cid}/standings?page=..    -> {rows:[{rank, user, solved, penalty, per_problem:{...}}]}
WS   /contests/{cid}/events               -> {submission_id, verdict} for my submissions; rank changes

-- internal (worker <-> platform)
lease(job) -> {submission_id, lang, source_ref, problem_version, limits}   # pull, with a visibility timeout
report(submission_id, attempt, result)                                       # idempotent on (submission_id)
  • Submit returns 202 immediately. Judging takes seconds; the client watches a WebSocket or polls GET /submissions/{id}. The submit is idempotent by key because users double-click (and rate-limited per user, rate limiter).
  • Reveal as little as the contest rules say. Returning the index of the failing test, or the expected output, lets a contestant extract the hidden tests one bit at a time. In practice mode show the first failing test index; in contests show only the verdict.
  • The worker pulls. A worker asks for work only when it has a free sandbox, so the queue is the buffer and no central scheduler has to track worker capacity (job scheduler).
  • Reports are idempotent on submission_id. The queue delivers at least once, so two workers can finish the same job after a timeout; the first final result wins and the second is dropped.

5High-level architecture

Draw the system. Where is the trust boundary? Which components may never see both the contestant's code and the expected outputs?

Compare with a worked answer

Life of a submission:

  1. The API validates and rate-limits, stores the source (hash-addressed) and a submission row in state queued, and enqueues a job in the contest or practice lane.
  2. A worker with a free slot leases the job, restores a fresh sandbox, compiles inside it (or reuses a cached binary by source hash), then for each test pipes the input into the program and captures its output with limits.
  3. The checker compares the output to the expected one outside the contestant's sandbox (expected outputs never enter it). The first failure ends the run in ICPC mode.
  4. The worker destroys the sandbox, reports the verdict (idempotent), and takes the next job.
  5. The scoring service reads the result log, updates attempt state and the sorted set, and pushes the verdict to the user's WebSocket.

6Deep dive 1: running untrusted code

Name five ways a contestant could attack the judge. Compare containers, gVisor, Firecracker microVMs and plain process limits as the isolation boundary, and decide. What limits do you impose, and which attacks do they not stop?

Compare with a worked answer

Threat model first (threat modeling): the attacker has full control of a native process and wants to (1) escape to the worker or the network, (2) read the hidden tests or other submissions, (3) exhaust CPU, memory, disk, processes or output, (4) tamper with the verdict or the clock, (5) use your machines for something else (mining, scanning, spam). Run the toy below to see what plain operating-system limits do and, just as important, what they do not.

"""A toy judge: run untrusted Python with OS limits and map the result to a verdict.
This is process-level isolation only. It shows what limits do, and what they do NOT do."""
import resource, subprocess, sys, threading

def limits():
    resource.setrlimit(resource.RLIMIT_CPU, (1, 1))              # 1 CPU-second
    resource.setrlimit(resource.RLIMIT_FSIZE, (1 << 20, 1 << 20)) # files up to 1 MiB

def judge(name, code, stdin="", wall=2, out_cap=1 << 16):
    try:
        p = subprocess.Popen([sys.executable, "-I", "-c", code], stdin=subprocess.PIPE,
                             stdout=subprocess.PIPE, stderr=subprocess.DEVNULL,
                             preexec_fn=limits, env={})
        timer = threading.Timer(wall, lambda: (setattr(p, "tle", True), p.kill()))
        timer.start()
        p.stdin.write(stdin.encode()); p.stdin.close()
        out = p.stdout.read(out_cap + 1)          # never read more than the cap
        if len(out) > out_cap:
            p.kill(); p.wait(); return name, "OLE (output over the cap, killed)"
        p.wait()
    finally:
        timer.cancel()
    if getattr(p, "tle", False):
        return name, "TLE (wall clock, killed)"
    if p.returncode == -24:  return name, "TLE (CPU limit, SIGXCPU)"
    if p.returncode == -25:  return name, "OLE (file size limit, SIGXFSZ)"
    if len(out) > out_cap:   return name, "OLE (output too large)"
    if p.returncode != 0:    return name, f"RE (exit {p.returncode})"
    return name, "ran: " + out.decode().strip()[:60]

cases = [
    ("correct",        "print(sum(map(int, input().split())))", "2 3"),
    ("infinite loop",  "while True: pass", ""),
    ("sleeps",         "import time; time.sleep(30)", ""),
    ("print flood",    "import sys\nwhile True: sys.stdout.write('x'*65536)", ""),
    ("writes 100 MiB", "open('gs14_big','wb').write(b'x'*(100<<20))", ""),
    ("crashes",        "1/0", ""),
]
for name, code, stdin in cases:
    print(f"{name:15} -> {judge(name, code, stdin)[1]}")

# the part rlimits do not cover: the process still sees the host's network stack and files
probe = "import socket; socket.socket(); print('socket() works: network stack is visible')"
print(f"{'opens a socket':15} -> {judge('net', probe)[1]}")
print(f"{'reads host file':15} -> {judge('fs', 'print(len(open(\"/etc/hosts\").read())>0)')[1]}")
correct         -> ran: 5
infinite loop   -> TLE (CPU limit, SIGXCPU)
sleeps          -> TLE (wall clock, killed)
print flood     -> OLE (output over the cap, killed)
writes 100 MiB  -> RE (exit 1)
crashes         -> RE (exit 1)
opens a socket  -> ran: socket() works: network stack is visible
reads host file -> ran: True

CPU time, wall time, output size and file size are all enforceable by limits and map neatly onto verdicts. But the last two lines are the point: the process still has a network stack and can read the host's files. A limit controls how much; an isolation boundary controls what is visible. (The exit status of an over-limit file write shows up as a runtime error here because Python turns the signal into an exception; the real judge maps it to the output-limit verdict.)

  • Decision: one microVM per run, restored from a snapshot of a clean guest for each language (so start cost is tens of milliseconds, not a full boot), with inside the guest: a non-root user, a read-only root filesystem, a size-limited tmpfs, a cgroup (cpu.max, memory.max, pids.max), seccomp, and no network device at all. See cloud and container security for why a shared-kernel container is the weaker choice for multi-tenant hostile code.
  • Defence in depth, because each layer has bugs: the host that runs the microVMs is itself ephemeral, holds no credentials, lives in a network segment with no route to production, and is replaced on a timer. An escape then yields a short-lived machine with a cache of test files, nothing else (blast radius, chapter 15).
  • Tests are never inside the sandbox. The program reads its input on stdin; its output goes out through a pipe; the checker, with the expected output, runs in a different trusted process. A contestant cannot cat the answers because they are not there.
  • Compile in the sandbox too. A C++ compile can take minutes with template recursion, or include a device file; give compilation its own limits (10 s, 512 MB), and treat compiler output as untrusted text.
  • Fork bombs and memory bombs hit pids.max and memory.max and end as runtime or memory-limit verdicts. The cgroup OOM kill is what produces "memory limit exceeded" reliably, rather than a guess from a failed allocation.
  • Side channels and timing attacks on the judge (a program that measures its own run time against test size to infer the data) are reduced by hiding test details and by the fresh-sandbox-per-run rule; they are not eliminated, and the honest answer is to say so.

7Deep dive 2: the queue, the worker pool and contest spikes

The contest starts and 50,000 people submit within minutes. Design the queue and worker pool so that verdicts stay under 10 seconds, practice traffic does not interfere, and one user cannot flood the system. What happens when you simply do not have enough cores?

Compare with a worked answer

The simulation in the estimates shows what matters: arrival can exceed capacity for a while without harm as long as the backlog drains, and the maximum wait depends on the area between the arrival curve and capacity. So the questions are how big a buffer to allow, how to keep the burst from being larger than it needs to be, and how to protect the part that matters.

OptionHowProsCons
One shared FIFOAll jobs in a single queueSimple, fair by arrival timeA flood from one user or a practice backlog delays everyone
Priority lanes (our choice)Contest lane above practice; workers prefer the contest lanePractice yields during contests; the contest SLO is protectedPractice can starve unless a small share is reserved
Per-user fair queueingWithin a lane, round-robin across users or token bucket per userNo single user can occupy the poolMore state; slight reordering within a lane
Push schedulerCentral scheduler assigns jobs to workersSmart placementNeeds live capacity knowledge; a scheduler bottleneck and failure point
  • Pull workers over a durable queue. A worker leases a job with a visibility timeout (for example 90 seconds) and extends it while running. If it dies the job reappears. Delivery is at least once, so the result write must be idempotent per submission (API stage). A job that has been leased and lost three times is a poison submission (it crashes workers); mark it a judge error, quarantine it and alert.
  • Capacity before the start, not after. A contest is scheduled, so scale up on a timetable: provision 7,000 to 12,000 cores 30 minutes before, restore warm sandbox snapshots, run a self-test of reference submissions on every new worker, and freeze deploys. Autoscaling that reacts to queue length arrives minutes late; use it only as a safety net above the scheduled floor (same lesson as the flash-sale studio).
  • Cap the burst at the source. A per-user submit limit (for example one submission per problem per 10 seconds, with a small burst) and a per-contest ceiling cut the arrival rate without hurting honest users; it also stops a script from flooding (rate limiter, abuse).
  • If you are short of cores, degrade deliberately (overload and load shedding): pause the practice lane entirely (a brownout nobody sees), then run contest jobs with early exit on the first failed test, then show a banner "judging is delayed, submissions are timestamped when received". Never drop submissions or reorder by user importance. Do not silently skip tests.
  • Queue wait cannot change the ranking. A submission's time for penalty is its server receive time, recorded at enqueue. A verdict delayed by two minutes must count as if it arrived instantly, otherwise capacity decides contests.
  • Bulk operations: a rejudge of 100,000 submissions is a third lane with the lowest priority and a rate limit, never mixed into the contest lane.
  • Little's law as a monitor: in-flight jobs = arrival rate x time in system. If the number of leased jobs sits at the number of sandbox slots and the queue age rises, you are saturated; alert on queue age of the oldest contest job, not on queue length.

8Deep dive 3: deterministic judging, time limits and fairness

The same program takes 0.95 s on one run and 1.08 s on another, and the limit is 1 s. How do you decide a verdict that is fair and reproducible? What differs between languages?

Compare with a worked answer

Judging is measurement, and measurement has noise. The design goal is the same program gets the same verdict on any worker, except for a defined, small borderline zone, and a rule for that zone.

ConcernApproachWhy

  • Reproducibility is a feature you can test: a nightly job re-judges a sample of last week's submissions on the current fleet and compares verdicts. A disagreement rate above 0.01% pages someone.
  • Reference solutions are the judge's own tests. Every problem ships with a known-correct, a known-too-slow and a known-wrong solution; every new worker image and every new tests version must give each of them its expected verdict before it is allowed into a contest (a canary).
  • Fairness at the queue: FIFO within a lane, per-user limits so one flood does not delay others, and identical judge versions for the whole contest (never roll the fleet mid-contest). Show contestants the real status (queued, compiling, running) so delay is visible, not mysterious.
  • Tests are an asset: a leaked test set ruins a problem. Access to the test bundle is by short-lived, per-contest credentials, workers fetch from object storage with a cache keyed by hash, and nothing contestant-controlled can read them (deep dive 1).

9Deep dive 4: the leaderboard, plagiarism detection and cost

Choose a data structure for live standings with 50,000 users. How do you encode 'solved count, then lowest penalty' as one sortable number? How would you find copied solutions after the contest, and how do you keep the bill sensible?

Compare with a worked answer

Standings are a sorted set: an ordered structure keyed by a numeric score with O(log n) insert and rank. A Redis-style ZADD / ZREVRANK / ZREVRANGE does it; the toy below uses a sorted list to show the encoding and costs.

"""A contest leaderboard as a sorted set. Higher score is better; ties break by earlier last-accept time."""
import bisect, random

class Board:                          # stands in for a Redis ZSET: ZADD, ZREVRANK, ZREVRANGE
    def __init__(self): self.keys, self.score = [], {}
    def zadd(self, user, key):
        if user in self.score: self.keys.pop(bisect.bisect_left(self.keys, (self.score[user], user)))
        self.score[user] = key; bisect.insort(self.keys, (key, user))
    def rank(self, user):             # 1-based, best first
        return len(self.keys) - bisect.bisect_left(self.keys, (self.score[user], user))
    def top(self, n): return [u for _, u in reversed(self.keys[-n:])]

PEN = 20                              # penalty minutes per wrong attempt
def key(solved, penalty_min): return solved * 1_000_000 - penalty_min   # one number sorts both

b, rng = Board(), random.Random(3)
for u in range(50_000):
    solved = min(8, int(rng.expovariate(0.6)))
    b.zadd(f"u{u}", key(solved, rng.randrange(0, 400) + PEN * rng.randrange(0, 4)))
print("top 5:", b.top(5))
print("rank of u123:", b.rank("u123"), "of", len(b.keys))
b.zadd("u123", key(8, 30))            # a new accept: one O(log n) update
print("after u123 solves everything fast:", b.rank("u123"))
top 5: ['u267', 'u13434', 'u23480', 'u37985', 'u23563']
rank of u123: 47454 of 50000
after u123 solves everything fast: 14
  • One number for two criteria: solved * 1,000,000 - penalty_minutes. More problems always beats any penalty (as long as penalty stays below a million), and lower penalty wins within the same count. Ties break by earliest last accepted time or by user id, added into the key; the sorted set stores (key, user).
  • Write rate is trivial, read rate is the issue: perhaps a quarter of 750,000 submissions are accepted, about 30 score updates per second. But 50,000 contestants refreshing the board every 10 seconds is 5,000 reads per second. Publish a snapshot of the top pages every 1 to 2 seconds to a cache or CDN (caching), serve a user's own rank from ZREVRANK, and push rank changes over the WebSocket only to the user concerned.
  • Penalty rules: a problem contributes its solve time plus a fixed penalty (for example 20 minutes) for each wrong attempt before the accepted one; wrong attempts on unsolved problems do not count; compile errors usually do not count. Keep these rules as a pure function of the submission list, so standings can be recomputed and audited.
  • Freeze in the last hour: keep scoring, stop publishing the public snapshot, publish a final board after the contest ("unfreeze"). It is a property of the read path only.
  • Source of truth is the submissions table. If the sorted set is lost or doubts arise, rebuild it by replaying accepted and rejected submissions in time order.

Plagiarism, briefly. After the contest, tokenise each accepted solution (drop comments and whitespace, normalise identifier names to a placeholder), then compute k-gram fingerprints and keep a sample of them (winnowing, the idea behind tools such as MOSS). Index fingerprints per problem, find pairs sharing a large fraction, and send the top pairs to a human reviewer, with the diff. Short solutions to easy problems look alike by nature, so this produces candidates, never automatic bans. Live signals complement it: shared IPs, solutions submitted seconds apart, accounts that submit from two places.

Cost. The bill is cores x hours, so (1) buy peak capacity only for the contest window (spot or preemptible instances are fine: interrupted jobs return to the queue), (2) run a small always-on pool for practice (100,000 per day is about 1.2 per second, around 12 busy cores on average, so 100 cores cover the daily peaks), (3) cut work per submission: early exit on first failure, cached compile output, sandboxes restored from snapshots, and (4) put the idle pool to use for rejudges and plagiarism jobs in the low lane. The estimates above give the comparison: about $960 for a rented contest fleet against $11,500 per day for an always-on one.

SLOs (SLOs and error budgets):

  • Verdict latency: 95% of contest submissions get a verdict in under 10 s, 99% in under 30 s; practice p95 under 60 s. Alert on the age of the oldest queued contest job (burn-rate alerts).
  • Judge correctness: reference solutions get their expected verdicts on 100% of canary runs; rejudge agreement at least 99.99%.
  • Submit availability: 99.95% of submissions accepted (202), since a rejected submit during a contest is the most visible failure.

Rollout. A judge image is versioned and immutable. New versions go to a canary subset of workers that run reference solutions, then shadow-judge a sample of real submissions beside the old version and compare verdicts and times; only then do they take live traffic (deployments). No judge, test or schema change during a live contest; if something is wrong, the fix is a rejudge afterwards plus a visible announcement.

  • Interactive problems: the contestant's program and an interactor (trusted, problem-setter code) run in two sandboxes joined by pipes; deadlines and limits apply to both and the judge enforces the turn protocol. The queue and leaderboard are unchanged.
  • Partial scoring (subtasks): run all tests, never early-exit, compute points per subtask group; the score becomes a number (add the tie-break) in the same sorted set; CPU per submission roughly doubles for failing code, so recompute the capacity table.
  • GPU or ML tasks: a different worker class with scarce, expensive hardware, longer limits and an explicit reservation system; the queue gets a lane per resource type (job scheduler).
  • Network access (for example web tasks): give the sandbox an egress-restricted network through a proxy with an allowlist, and treat SSRF-style attacks on your own metadata endpoints as the main risk (SSRF).
  • 10x scale: the arithmetic scales linearly in cores; the first things to break are the submissions database write path (shard by contest) and the snapshot-restore rate per host.
  • "Run with custom input" in the editor: a separate low-latency lane with tiny limits, answered synchronously; it must not share a queue with contest judging.

How a senior engineer would summarise this

"A submission is not a request, it's a ten-second batch job, so I size with cores and Little's law. A 50,000-person contest peaks around 600 submissions a second, which is about 6,400 busy cores; provisioning for the average would be six times too small, and the queue wait goes from zero to forty seconds between 7,000 and 6,000 cores. So I pre-scale on a timetable, since a contest start is known in advance, and rent the fleet for two hours instead of a day. The core of the design is isolation: the code is hostile, so each run goes in a Firecracker microVM restored from a clean snapshot, with a read-only filesystem, cgroup limits on CPU, memory and processes, no network device, and the hidden tests never inside the sandbox. A checker outside it compares outputs. Workers pull jobs from a durable queue with priority lanes, so contest beats practice, and a per-user limit stops floods; delivery is at least once, so verdict writes are idempotent per submission and poison jobs are quarantined. Fairness comes from measuring CPU time from the cgroup, one hardware class per contest, borderline reruns, pinned image versions, and timestamping a submission when it is received so queue delay never changes penalties. Standings are a sorted set with a single score, solved times a million minus penalty, rebuilt from the submissions table if lost, and the read load is served from a snapshot refreshed every second or two. Plagiarism detection is an offline k-gram fingerprint job producing candidates for humans. I'd alert on the age of the oldest queued contest job, and block any change to the judge during a contest. If we added interactive problems it's two sandboxes and an interactor; if we added network tasks, an egress proxy."

Notice the shape: job-sized estimate → isolation → pull queue and lanes → fair measurement → derived standings → named failure modes.

Key takeaways

  • A submission is a batch job of about ten core-seconds. Size the fleet with cores and the contest peak, not the average.
  • Limits control how much; isolation controls what is visible. Hostile code needs a hardware-level boundary with no network.
  • Never put the answers where the code runs: the checker lives outside the sandbox.
  • A known start time lets you pre-scale; use autoscaling only as a safety net, and shed practice work first.
  • Fair judging means CPU time, calibrated hardware, borderline reruns, pinned images, and penalties counted from receive time.
  • Standings are a sorted set with one encoded score, derived from submissions, served from a snapshot.
  • Canary every judge and test change with reference solutions, and never change the judge during a contest.
